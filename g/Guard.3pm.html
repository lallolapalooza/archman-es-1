Paquete: perl-guard

Licencias: GPL, PerlArtistic

Guard(3pm) Documentación de Perl aportada por el usuario Guard(3pm)

NOMBRE

Guard - bloques de limpieza seguros

SINOPSIS

use Guard;

# cambia temporalmente al directorio "/etc", pero asegúrate
# de volver a "/" sin importar cómo salga myfun:
sub myfun {
   scope_guard { chdir "/" };
   chdir "/etc";

   code_que_puede_fallar_o_hacer_otras_cosas_divertidas;
}
# crea un objeto que, cuando la última referencia a él se haya ido,
# invocará el bloque de código dado:
my $guard = guard { print "¡destruido!\n" };
undef $guard; # probablemente destruido aquí

DESCRIPCIÓN

Este módulo implementa los llamados "guards" (protectores). Un guard es algo (generalmente un objeto) que "protege" un recurso, asegurando que se limpie cuando se espera.

Específicamente, este módulo soporta dos tipos diferentes de guards: objetos guard, que ejecutan un bloque de código dado cuando se destruyen, y guards de ámbito (scoped guards), que están ligados a la salida del ámbito.

FUNCIONES

Este módulo exporta actualmente las funciones "scope_guard" y "guard" por defecto.

scope_guard BLOQUE
scope_guard ($coderef)
Registra un bloque que se ejecuta cuando se sale del ámbito actual (bloque, función, método, eval, etc.).

Ver la sección EXCEPCIONES para una explicación de cómo se manejan las excepciones (es decir, "die") dentro de los bloques guard.

La descripción a continuación suena un poco complicada, pero eso es solo porque "scope_guard" intenta conseguir que incluso los casos límite sean "correctos": el objetivo es proporcionarte una herramienta de limpieza sólida como una roca.

El comportamiento es similar a este fragmento de código:

eval ... código que sigue a scope_guard ...
{
   local $@;
   eval BLOCK;
   eval { $Guard::DIED->() } if $@;
}
die if $@;

Excepto que es mucho más rápido, y todo el asunto se ejecuta incluso cuando el BLOQUE llama a "exit", "goto", "last" o escapa por otros medios.

Si se registran múltiples BLOQUES en el mismo ámbito, se ejecutarán en orden inverso. Otras cosas relacionadas con el ámbito, como "local", se gestionan a través del mismo mecanismo, por lo que las variables "local"izadas después de llamar a "scope_guard" se restaurarán cuando se ejecute el guard.

Ejemplo: cambia temporalmente la zona horaria para el proceso actual, asegurando que se restablecerá cuando se salga del ámbito "if":

use Guard;
use POSIX ();
if ($need_to_switch_tz) {
   # asegúrate de que llamamos tzset después de que $ENV{TZ} se haya restaurado
   scope_guard { POSIX::tzset };
   # localiza después del scope_guard, para que se deshaga a tiempo
   local $ENV{TZ} = "Europe/London";
   POSIX::tzset;
   # haz algo con la nueva zona horaria
}
my $guard = guard BLOQUE
my $guard = guard ($coderef)
Se comporta igual que "scope_guard", excepto que en lugar de ejecutar el bloque al salir del ámbito, devuelve un objeto cuya vida útil determina cuándo se ejecuta el BLOQUE: cuando la última referencia al objeto se destruye, el BLOQUE se ejecuta como con "scope_guard".

Ver la sección EXCEPCIONES para una explicación de cómo se manejan las excepciones (es decir, "die") dentro de los bloques guard.

Ejemplo: adquiere un Coro::Semaphore por un segundo registrando un temporizador. El callback del temporizador hace referencia al guard utilizado para desbloquearlo de nuevo. (Por favor, ignora el hecho de que "Coro::Semaphore" tiene un método "guard" que ya hace esto):

use Guard;
use Coro::AnyEvent;
use Coro::Semaphore;
my $sem = new Coro::Semaphore;
sub lock_for_a_second {
   $sem->down;
   my $guard = guard { $sem->up };
   Coro::AnyEvent::sleep 1;
   # $sem->up se ejecuta al regresar
}

La ventaja de hacer esto con un guard en lugar de simplemente llamar a "$sem->down" en el callback es que puedes optar por no crear el temporizador, o tu código puede lanzar una excepción antes de que pueda crear el temporizador (o el hilo se cancela), o puedes crear múltiples temporizadores u otros observadores de eventos y solo cuando el último se ejecute se desbloqueará el bloqueo. Usando el "guard", no tienes que preocuparte por capturar todos los lugares donde tienes que desbloquear el semáforo.

$guard->cancel
Llamar a esta función "desactivará" el objeto guard devuelto por la función "guard", es decir, liberará el BLOQUE originalmente pasado a "guard " y organizará que el BLOQUE no se ejecute.

Esto puede ser útil cuando usas "guard" para crear un manejador de limpieza que se llamará bajo condiciones fatales y más tarde decides que ya no se necesita.

EXCEPCIONES

Los bloques Guard normalmente no deberían lanzar excepciones (es decir, "die"). Después de todo, se suelen usar para limpiar después de tales excepciones. Sin embargo, si está ocurriendo algo verdaderamente excepcional, un bloque guard debería, por supuesto, poder fallar. Además, los errores de programación son una gran fuente de excepciones, y el programador ciertamente quiere saber sobre ellas.

Dado que en la mayoría de los casos, el código que se ejecuta cuando se ejecuta el guard no conoce o no le importan los bloques guard, tiene poco sentido dejar que el código contenedor maneje la excepción.

Por lo tanto, siempre que un bloque guard lanza una excepción, será capturada por Guard, seguido de la llamada al código de referencia almacenado en $Guard::DIED (con $@ configurado a la excepción real), que es similar a cómo la mayoría de los bucles de eventos manejan este caso.

El valor por defecto para $Guard::DIED es llamar a "warn "$@"", es decir, el error se imprime como una advertencia y el programa continúa.

La variable $@ se restaurará a su valor antes de la llamada al guard en todos los casos, por lo que los guards no interferirán con $@ de ninguna manera.

El código de referencia almacenado en $Guard::DIED no debería fallar (el comportamiento no está garantizado, pero en este momento, la excepción simplemente se ignorará).

VER TAMBIÉN

Scope::Guard y Sub::ScopeFinalizer, que en realidad implementan solo guards de ámbito dinámico, no los guards de ámbito léxico que prometen sus documentaciones, y tienen un costo mucho mayor en CPU, memoria y escritura.

Hook::Scope, que aparentemente nunca se terminó y puede corromper la memoria cuando se usa.

Scope::Guard parece tener una gran sección de VER TAMBIÉN para módulos aún más similares.
