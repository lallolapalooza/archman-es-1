Glib::CodeGen(3) Documentación de Perl contribuida por el usuario Glib::CodeGen(3)

NOMBRE

Glib::CodeGen - utilidades de generación de código para enlaces basados en Glib.

SINOPSIS

# usualmente en Makefile.PL
use Glib::CodeGen;
# lo más común, usa todos los valores predeterminados
Glib::CodeGen->parse_maps ('mi-prefijo');
Glib::CodeGen->write_boot;
# más exótico, cambia todo
Glib::CodeGen->parse_maps ('foo',
                           input => 'foo.maps',
                           header => 'foo-autogen.h',
                           typemap => 'foo.typemap',
                           register => 'register-foo.xsh');
Glib::CodeGen->write_boot (filename => 'bootfoo.xsh',
                           glob => 'Foo*.xs',
                           ignore => '^(Foo|Foo::Bar)$');
# añade un manejador de tipos personalizado (raramente necesario)
Glib::CodeGen->add_type_handler (FooType => \&gen_foo_stuff);
# (ver la sección EXTENDING TYPE SUPPORT para más información.)

DESCRIPCIÓN

Este módulo empaqueta parte del código repetitivo necesario para realizar la generación de código típicamente utilizada por los enlaces de Perl para bibliotecas basadas en gobject, usando el módulo Glib como base.

Los nombres de archivo de salida predeterminados están en el subdirectorio 'build', que generalmente estará presente si estás usando ExtUtils::Depends (como probablemente deberían hacerlo la mayoría de las extensiones basadas en Glib).

MÉTODOS

Glib::CodeGen->write_boot;
Glib::CodeGen->write_boot (KEY => VAL, ...)
Muchas bibliotecas basadas en GObject a enlazar con Perl serán demasiado grandes para ponerlas en un único archivo XS; sin embargo, un único archivo PM típicamente solo inicia el código de un archivo XS. "write_boot" genera un archivo XSH para ser incluido desde la sección BOOT de ese único módulo iniciado, llamando al código de arranque de todos los demás archivos XS del proyecto.

Las opciones se pasan a la función en un conjunto de pares clave/valor, y todas las opciones pueden tener valores predeterminados.

filename     el nombre del archivo de salida a crear.
             el valor predeterminado es 'build/boot.xsh'.
glob         un patrón glob que especifica los nombres de
             los archivos xs a escanear en busca de líneas
             MODULE.
             el valor predeterminado es 'xs/*.xs'.
xs_files     usa esto para proporcionar una lista explícita
             de nombres de archivo (como una referencia a
             un array) para usar en lugar de un patrón
             glob. el valor predeterminado es usar el
             patrón glob.
ignore       expresión regular que coincide con cualquier
             y todos los nombres de módulo que deben ser
             ignorados, es decir, NO incluidos en la lista
             de símbolos a iniciar.
             este parámetro es extremadamente importante
             para evitar bucles infinitos al inicio; ver la
             discusión para una explicación y justificación.
             el valor predeterminado es '^[^:]+$', o, cualquier
             nombre que no contenga dos puntos, es decir,
             cualquier nombre de paquete de nivel superior.

Esta función realiza un glob (usando el operador glob incorporado de Perl) en el patrón especificado por la opción 'glob' para obtener una lista de nombres de archivo. Luego escanea cada archivo de esa lista en busca de líneas que coincidan con el patrón "^MODULE" -- es decir, la directiva MODULE en un archivo XS. Se extrae el nombre del módulo y se compara con la expresión regular especificada por el parámetro ignore. Si este módulo no debe ser ignorado, verificamos si el nombre ya ha sido visto. Si no, el nombre se convertirá en un símbolo de arranque (básicamente, s/:/_/ y prefijo "boot_") y este símbolo se agregará a una llamada a GPERL_CALL_BOOT en el archivo generado; luego se marca como visto para que no lo llamemos de nuevo.

¿De qué trata todo esto, preguntas? Para enlazar una XSub con Perl, la función C debe registrarse en el intérprete. Esta es la función del código "boot", que típicamente se llama en el proceso de arranque. Sin embargo, cuando se usan múltiples archivos XS con un solo archivo PM, algún otro mecanismo debe llamar al código de arranque de cada archivo XS antes de que cualquiera de las funciones contenidas en él esté disponible.

Una configuración típica para un módulo con múltiples XS y un solo PM será llamar a los diversos fragmentos de código de arranque desde la sección BOOT: del archivo XS del módulo principal.

Tomando Gtk2 como ejemplo, cuando haces 'use Gtk2', Gtk2.pm llama a bootstrap en Gtk2, lo que llama a la función C boot_Gtk2. Esta función llama a los símbolos de arranque de todos los demás archivos xs del módulo. La distinción es que el módulo principal, Gtk2, no tiene dos puntos en su nombre.

"xsubpp" genera el nombre de la función de arranque reemplazando los dos puntos en el nombre del MODULE con guiones bajos y anteponiendo "boot_". Debemos tener cuidado de no incluir el código de arranque del módulo iniciado (digamos Toplevel, o Gtk2, o lo que sea), porque el código de arranque en Toplevel.pm llamará a boot_Toplevel cuando se cargue, y boot_Toplevel debería incluir el archivo que estamos creando aquí.

El valor predeterminado para el parámetro ignore ignora cualquier nombre que no contenga dos puntos, porque se asume que será un módulo principal, y cualquier otro paquete/módulo que inicie estará *debajo* de este espacio de nombres, es decir, contendrá dos puntos. Esta suposición se cumple para Gtk2 y Gnome2, pero obviamente falla para algo como Gnome2::Canvas. Para iniciar ese módulo correctamente, debes usar una expresión regular como "^Gnome2::Canvas$".

Ten en cuenta que, por supuesto, puedes coincidir con más de un nombre, por ejemplo, "^(Foo|Foo::Bar)$", si quisieras que Foo::Bar se incluyera en el mismo objeto cargado dinámicamente pero solo se iniciara cuando fuera absolutamente necesario. (Si logras que eso funcione, tienes todo mi respeto.)

Además, dado que este código busca ^MODULE, debes comentar la sección MODULE con marcas de comentarios iniciales si quieres ocultarla de "write_boot".

Glib::CodeGen->parse_maps (PREFIJO, [KEY => VAL, ...])
La convención dentro de Glib/Gtk2 y similares es usar macros de preprocesador al estilo de SvMyType y newSVMyType para obtener valores dentro y fuera de Perl, y usar esas mismas macros tanto desde código escrito a mano como desde los typemaps. Sin embargo, si tienes muchos tipos en tu biblioteca (como los casi 200 tipos en Gtk+ 2.x), escribir esas macros se vuelve increíblemente tedioso, especialmente si se tienen en cuenta todas las variantes y demás.

Por lo tanto, esta función puede convertir un archivo plano que contiene descripciones concisas de los tipos en una cabecera que contiene todas las macros de cast, un archivo typemap que las utiliza y un archivo XSH que contiene el código adecuado para registrar cada uno de esos tipos (para ser incluido por el código BOOT de tu módulo).

El PREFIJO es obligatorio y se utiliza en algunos de los nombres de archivo resultantes. También puedes anular los valores predeterminados proporcionando pares clave=>valor:

input    nombre del archivo de entrada. valor predeterminado
         es 'maps'. si el valor de esta clave es una
         referencia a un array, se escanearán todos los
         nombres de archivo del array.
header   nombre del archivo de cabecera a crear,
         predeterminado es build/$prefijo-autogen.h
typemap  nombre del archivo typemap a crear,
         predeterminado es build/$prefijo.typemap
register nombre del archivo xsh para contener todos los
         registros de tipos, predeterminado es
         build/register.xsh

El archivo maps es una tabla de descripciones de tipos, una por línea, con campos separados por espacios en blanco. los campos deberían ser:

TYPE macro    ej., GTK_TYPE_WIDGET
nombre clase    ej. GtkWidget, nombre del tipo C
tipo base       uno de GObject, GBoxed, GEnum, GFlags.
              para soportar otros tipos base, ver
              EXTENDING TYPE SUPPORT para info sobre
              cómo añadir un manejador de tipos personalizado.
package       nombre del paquete perl al que este
              nombre de clase debería mapearse, ej.,
              Gtk2::Widget

Como caso especial, también puedes usar este mismo formato para registrar dominios de error; en este caso, dos de las cuatro columnas adquieren significados ligeramente diferentes:

macro dominio     ej., GDK_PIXBUF_ERROR
macro tipo enum  ej., GDK_TYPE_PIXBUF_ERROR
tipo base        GError
package          nombre del paquete Perl al que esta
                 nombre de clase debería mapearse, ej.,
                 Gtk2::Gdk::Pixbuf::Error.
