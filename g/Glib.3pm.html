RESUME

N

Este módulo proporciona acceso de Perl a GLib y a las bibliotecas GObject de GLib. GLib es una biblioteca de portabilidad y utilid

ades; GObject proporciona un sistema de tipos genérico con herencia y un potente sistema de señales. Juntas, estas bibliotecas se u
tilizan como base para muchas de las bibliotecas que componen el entorno Gnome, y se utilizan en muchos proyectos no relacionados.

DESCRIPCIÓ

N

Esta envolvente intenta proporcionar una interfaz al estilo de Perl mientras se mantiene lo más fiel posible a la API de C subyacente, de modo que cualquier

material de referencia que encuentres sobre el uso de GLib pueda seguir siendo aplicable al uso de las bibliotecas desde Perl. Este módulo también proporcio
na facilidades para crear envolventes para otras bibliotecas basadas en GObject. La sección "VER TAMBIÉN" contiene enlaces a todo tipo de buena información.

PERL FRENTE A

C

GLib proporciona a los programas C muchas de las mismas facilidades que Perl ofrece de forma nativa. Donde la funcionalidad de GLib se superpone con la de Perl, se prefiere la de Perl. Algunos conceptos se han eliminado por completo, ya que Perl es un lenguaje de más alto nivel que C. En otros casos, hemos tenido que añadir o cambiar APIs para que tengan sentido en Perl. Aquí tienes un resumen

rápido:

Perl Ya Hace

Eso

Los tipos de GLib GList (una lista doblemente enlazada), GSList (lista simplemente enlazada), GHashTable, GArray, etc., han sido reemplazados por tipos de datos nativos de Perl. De hecho, muchas funciones que toman GLists o arrays simplemente aceptan listas en la

pila de Perl. En su mayor parte, los GIOChannels no son más funcionales que los manejadores de archivos de Perl, por lo que no verás ningún GIOChannel. Los GClosures no son visibles a nivel de Perl, porque las referencias a código de Perl hacen lo mismo. Casi cua
lquier función que tome un puntero a función de C o un GClosure aceptará una referencia a código en Perl. (De hecho, probablemente puedas salirte con la tuya usando solo el nombre de un subprocedimiento en muchos lugares, siempre que no estés usando strict subs).

No Te Preocupes Por

Eso

Algunos conceptos se han eliminado; nunca necesitas preocuparte por el conteo de referencias en GObjects ni por tener que liberar estructuras GBoxed. Pe

rl es un lenguaje con recolección de basura, y hemos trabajado mucho para que las envolventes se encarguen de la memoria por ti de una manera que se si
enta natural para un desarrollador de Perl. No verás GValues en Perl (de todos modos, eso es solo una estructura de C con envidia de escalares de Perl).

Esto Ahora Es

Aquello

Otros conceptos de GLib se han convertido en un concepto análogo de

Perl.

El id de GType nunca se verá en Perl, ya que el nombre del paquete sirve para ese propósito. Se han registrado varios paquetes que corresponden a los GTypes de los tipos fundamentales para

ti:

EXCEPCIONES.

Las enumeraciones y los flags se tratan como cadenas y arrays de cadenas, respectivamente. GLib proporciona una forma de registrar apodos para los valores de enumeración, y las envolventes de Perl usan estos apodos para los valores reales, de modo que nunca tenemos que lidiar con números en Perl. Esto puede resultar un poco engorroso para los campos de bits, pero es muy útil cuando olvidas un valor de flag, ya que las envolventes te dirán qué valores se aceptan cuando pasas algo inválido. Además, las envolventes consideran los caracteres - y _ como equivalentes, para que los nombres de señales y propiedades puedan ser correctamente convertidos en cadenas por el operador =>. Por ejemplo, lo siguiente es

equivalente: 
# propiedad foo-matic de tipo FooType, usando el
# valor FOO_SOMETHING_COOL. su apodo sería
# 'something-cool'. puedes usar tanto el nombre completo
# como el apodo al proporcionar valores a perl.
$object->set ('foo-matic', 'FOO_SOMETHING_COOL');
$object->set ('foo_matic', 'something_cool');
$object->set (foo_matic => 'something-cool')
;

Ten cuidado, ya que Perl siempre te devolverá la forma del apodo, con el

guion.

Los flags tienen algunas habilidades mágicas adicionales en forma de operadores

sobrecargados: 
+ o |   unión de dos conjuntos de flags ("añadir")
-        diferencia de dos conjuntos de flags ("restar", "eliminar")
* o &   intersección de dos conjuntos de bits ("y")
/ o ^   diferencia simétrica ("xor", rara vez necesitarás esto)
>=       operador de contención ("¿es el conjunto izquierdo un superconjunto del conjunto derecho?")
==
igualdad

Además, los flags en contexto booleano indican si están vacíos o no, lo que te permite escribir operaciones comunes de forma

natural: 
$widget->set_events ($widget->get_events - "motion_notify_mask");
$widget->set_events ($widget->get_events - ["motion_notify_mask",
                                            "button_press_mask"]);
# shift presionado (ambas funcionan, es cuestión de gusto)
if ($event->state >= "shift-mask") { ...
if ($event->state * "shift-mask") { ...
# ¿shift O control presionado?
if ($event->state * ["shift-mask", "control-mask"]) { ...
# ¿shift Y control presionados?
if ($event->state >= ["shift-mask", "control-mask"]) { ..
.

En general, "+" y "-" funcionan como se espera para añadir o eliminar flags. Para probar si algún bit está establecido en una máscara, usas "$mask * ...", y para probar si todos los bits están establecidos en una máscara, usas "$mask >=

...".

Cuando se desreferencia como un array @$flags o "$flags->[...]", puedes acceder a los valores de los flags directamente como cadenas (pero no se te permite modificar el array), y cuando se convierte en cadena "$flags" un valor de flags produci

rá una versión legib
le de su contenido.

CODIFICACIONES

Perl conoce dos tipos de datos, texto unicode y bytes binarios. Los nombres de archivo en un sistema que no usa un locale utf-8 a menudo se almacenan en una codificación local ("bytes binarios"). Gtk+ y sus descendientes, sin embargo, internamente trabajan en unicode la mayor parte del tiempo, por lo que cuando alimentas un nombre de archivo a una función GLib/Gtk+ que espera un nombre de archivo, primero necesitas convertirlo de la codificación local a

unicode.

Esto implica una elaborada conjetura, que perl actualmente evita, pero GLib y Gtk+ sí hacen. Como excepción, algunas funciones de Gtk+ quieren un nombre de archivo en codificación local, pero la interfaz de perl generalmente soluciona esto convirtiéndolo automáticamente por

ti.

En resumen: Todo debería estar en unicode a nivel de

perl.

EXCEPCIONE

S

El lenguaje C no soporta excepciones; GLib es una biblioteca C, y por supuesto tampoco soporta excepciones. En Perl, usamos die y eval para lanzar y capturar excepciones como una práctica bastante común. Así, los bindings tienen que hacer un poco de magia negra detrás de escena para evitar que GLib explote cuando el programa Perl usa excepciones. Desafortunadamente, un poco de esta magia tiene que filtrarse hasta donde puede verla a nivel de

Perl.

Los manejadores de señales y eventos se ejecutan en un contexto eval; si ocurre una excepción en un manejador de este tipo y usted no la captura, Perl reportará que ocurrió un error, y luego seguirá con su negocio como si nada hubiera

pasado.

Puede registrar subrutinas como manejadores de excepciones, para ser llamadas cuando se capture una excepción de este tipo. Otra función los elimina por

usted. 
$tag = Glib->install_exception_handler (\&my_handler);
Glib->remove_exception_handler ($tag)
;

El manejador de excepciones recibirá una copia fresca del $@ de la excepción ofensiva en la pila de argumentos, y se espera que devuelva distinto de cero si el manejador debe permanecer instalado. Si devuelve falso, el manejador será

eliminado. 
sub my_handler {
    if ($_[0] =~ m/ftang quisinart/) {
         clean_up_after_ftang ();
    }
    1; # vivir para luchar otro día
}

Puede registrar tantos manejadores como desee; todos se ejecutarán independientemente

.

Una cosa importante a recordar es que las excepciones no cruzan los bucles principales. De hecho, las excepciones son completamente d

istintas de los bucles principales. Si necesita salir de un bucle principal cuando ocurre una excepción, instale un manejador que sa
lga del bucle principal, pero también pregúntese si está usando excepciones para el control de flujo o para el manejo de excepciones.

ENTEROS DE 64

BITS

Dado que el tipo de dato entero de perl solo puede contener valores de 32 bits en todas las máquinas de 32 bits e incluso en algunas máquinas de 64 bits, Glib convierte enteros de 64 bits a y desde cadenas si es necesario. Estas cadenas pueden luego ser usadas para alimentar uno de los varios módulos de enteros grandes. Asegúrese de no dejar que sus cadenas entren en contexto numérico antes de pasarlas a una función Glib, porque en este caso, perl convertirá el número a notación científica, la cual en este punto no es entendida por los convertidores de

Glib.

Aquí hay un resumen de qué módulos de enteros grandes están disponibles. Primero, está Math::BigInt. Tiene todo lo que alguna vez necesitará, pero su implementación en puro Perl también es bastante lenta. Sin embargo, hay múltiples formas de sortear

esto.
Math::BigInt::
FastCalc
Math::BigInt::FastCalc puede ayudar a evitar la velocidad glacial de Math::BigInt::Calc estándar. Las versiones recientes de Math::BigInt usarán automáticamente Math::BigInt::FastCalc en lugar de Math::BigInt::Calc cuando esté disponible. Otras opciones incluyen Math::BigInt::GMP o Math::BigInt::Pari, que sin embargo tienen dependencias mucho más
grandes.
Math::BigInt::
Lite
Luego está Math::BigInt::Lite, que usa operaciones de enteros nativas de Perl siempre que los enteros de Perl tengan un rango suficiente, y se actualiza a Math::BigInt cuando los enteros de Perl se desbordarían. Esto debe usarse en lugar de Math::
BigInt.
bigint / bignum /
bigfloat
Finalmente, están los pragmas bigint/bignum/bigfloat, que
cargan automáticamente los módulos Math:: correspondient
es y que harán autoboxing de constantes. bignum/bigint usa
rá automáticamente Math::BigInt::Lite si está disponible.
