Glib::GenPod(3) Documentación de Perl aportada por el usuario Glib::GenPod(3)

NOMBRE

Glib::GenPod - Utilidades de generación de POD para módulos basados en Glib

SINOPSIS

use Glib::GenPod;
# usar los valores predeterminados:
xsdoc2pod ($archivo_salida_xsdocparse, $directorio_destino);
# o tomar las riendas
require $archivo_salida_xsdocparse;
foreach my $paquete (sort keys %$data) {
    print "=head1 NOMBRE\n\n$paquete\n\n";
    print "=head1 MÉTODOS\n\n" . podify_methods ($paquete) . "\n\n";
}

DESCRIPCIÓN

Este módulo incluye varias utilidades para crear POD para módulos Perl basados en XS que se basan en los fundamentos del módulo Glib. Las partes más importantes son la lógica para convertir las estructuras de datos creadas por xsdocparse.pl para describir xsubs y pods en documentación de métodos, con firmas de llamada y descripciones de argumentos, y para convertir nombres de tipos C en nombres de tipos Perl. El resto del módulo es principalmente código de relleno para formatear y dar formato presentable a la información que puede ser consultada desde el sistema de tipos de Glib.

Para facilitar la vida a los mantenedores de módulos, también incluimos una función que hace todo, xsdoc2pod(), que hace casi todo por usted. Todas las piezas que utiliza son de uso público, por lo que puede hacer lo que quiera si no le gusta la salida predeterminada.

DOCUMENTANDO LOS ARCHIVOS XS

Toda la información utilizada como entrada para los métodos incluidos aquí proviene de los archivos XS de su proyecto y es extraída por xsdocparse de Glib::ParseXSDoc. Esta función crea un archivo que contiene código Perl que puede ser evaluado o requerido para recrear las estructuras de datos analizadas, que son una lista de pods de la parte C literal del archivo XS (la documentación de la API XS), y un hash de los datos restantes, indexado por nombre de paquete, e incluyendo los pods y xsubs leídos del resto de cada archivo XS después de la primera línea MODULE.

Se reconocen varias directivas POD personalizadas en la sección XSubs. Tenga en cuenta que cada una se busca como inicio de párrafo y debe seguir a una directiva "=cut".

=for objeto Paquete::Nombre
Todas las xsubs y pods desde aquí hasta la siguiente directiva de objeto o línea MODULE se colocarán bajo la clave 'Paquete::Nombre' en la estructura de datos de xsdocparse. Todo, desde esta línea hasta el siguiente "=cut", se incluye como POD de descripción.
=for objeto Paquete::Nombre (Otro::Paquete::Nombre)
Genera POD en Paquete::Nombre pero para el paquete Otro::Paquete::Nombre. Esto es útil si desea que el POD aparezca en un espacio de nombres diferente pero aún así desea la jerarquía generada automáticamente, la lista de señales y propiedades, etc., del espacio de nombres original. Por ejemplo: 
=for objeto Gnome2::PanelApplet::main (Gnome2::PanelApplet)
=cut

Esto creará Gnome2/PanelApplet/main.pod que contiene la documentación generada automáticamente para Gnome2::PanelApplet (jerarquía, señales, etc.) más la lista de métodos del archivo XS actual.

=for enum Paquete::Nombre
=for flags Paquete::Nombre
Esto hace que xsdoc2pod llame a "podify_values" en Paquete::Nombre al escribir el pod para el paquete actual (como se estableció mediante una directiva de objeto o una línea MODULE). Cualquier texto en este párrafo, hasta el siguiente "=cut", se incluye en esa sección.
=for deprecated_by Paquete::Nombre
Se utiliza para agregar una advertencia de deprecación, indicando Paquete::Nombre como una forma alternativa de lograr la misma funcionalidad. Puede haber un número cualquiera de estos en cada paquete.
=for see_also algo_que_ver
Se utiliza para agregar "ver también" adicionales al final de los padres, si los hay, para un objeto dado. Cualquier cosa después del espacio detrás de "ver también" hasta el final de la línea se colocará en la lista de "ver también". Puede haber un número cualquiera de estos en cada paquete.
=for apidoc
=for apidoc Nombre::Símbolo::Completo
Los párrafos de este tipo documentan xsubs y se asocian con las xsubs por xsdocparse.pl. Si no se incluye el nombre completo del símbolo, el párrafo debe adjuntarse a la declaración de la xsub (sin líneas en blanco entre "=cut" y la xsub).

Dentro de los PODs de apidoc, reconocemos algunas directivas especiales (el "for\s+" es opcional en estas):

=for signature ...
Anula la firma de llamada generada con el texto ... Si incluye múltiples directivas de firma, se usarán todas. Esto es útil cuando desea cambiar el tipo de retorno o enumerar diferentes formas de invocar un método sobrecargado, como esto: 
=for apidoc
=signature bool Class->foo
=signature ($cosa, @otra) = $objeto->foo ($eso, $algo)
El texto aquí se incluye en la documentación generada.
De hecho, puedes incluir directivas de firma y argumento
en cualquier punto de este pod; se eliminan después.
De hecho, cualquier pod es válido aquí, hasta el =cut.
=cut
void foo (...)
    PPCODE:
       /* sigue código loco */
=for arg nombre (tipo) descripción
=for arg nombre descripción
La directiva de argumento agrega o anula una descripción de argumento. La descripción del texto es opcional, al igual que la especificación del tipo (la parte entre paréntesis). Si desea ocultar un argumento, especifique "__hide__" como su tipo. El nombre del argumento no necesita incluir un sigilo, ya que se agregarán los signos de dólar. ¿FIXME qué pasa con @ para listas?

Además, honramos un par de "modificadores" en la línea =for apidoc, después del nombre del símbolo, si están presentes:

- __hide__
No documente esta xsub. Esto es útil en ciertas situaciones, por ejemplo, para funciones privadas. DESTROY siempre tiene esto activado, por ejemplo.
- __gerror__
Esta función o método puede generar una excepción Glib::Error.
- __function__
Genera una firma de estilo función para esta xsub. El valor predeterminado es generar firmas de estilo método.
- __deprecated__
Esta función o método está obsoleto y no debe usarse en código recién escrito.

(Estos son en realidad manejados por Glib::ParseXSDoc, pero los enumeramos aquí porque, bueno, son una parte importante de cómo documenta los archivos XS.)

FUNCIONES

xsdoc2pod ($archivo_datos, $dir_salida='blib/lib', $indice=undef)
Dado un $archivo_datos que contiene la salida de xsdocparse.pl, cree en $dir_salida un archivo pod para cada paquete, que contenga todo lo que podamos imaginar para ese módulo. La salida está controlada por las directivas "=for objeto" y similares en el código fuente.

Si no desea que cada paquete cree un archivo pod separado, entonces use el código de esta función como punto de partida para su propio formateador.

add_types (@nombres_archivos)
Analiza los @nombres_archivos dados para entradas que se agregarán a los %basic_types utilizados para mapear nombres de tipos C a nombres de paquetes Perl de tipos que no están registrados en el sistema de tipos Glib. El formato del archivo es muy simple: se ignoran las líneas en blanco; se elimina /#.*$/ de cada línea como comentarios; el primer token en cada línea se considera un nombre de tipo C, y los tokens restantes son la descripción de ese tipo. Por ejemplo, un archivo válido podría verse así: 
# un par de tipos especiales
FooBar      Foo::Bar
Frob        frobnicador localizado

Se implican las decoraciones de tipos C como "const" y "*" (no las incluya), y la variante _ornull se maneja por usted.

$cadena = podify_properties ($nombre_paquete)
Formatea las propiedades del objeto propiedad del derivado Glib::Object $nombre_paquete y devuelve el texto como una cadena. Devuelve undef si no hay propiedades o si $nombre_paquete no es un Glib::Object.
