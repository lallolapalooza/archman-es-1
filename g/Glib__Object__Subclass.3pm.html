Glib::Object::Subclass(3) Documentación de Perl contribuida por el usuario Glib::Object::Subclass(3)

NOMBRE

Glib::Object::Subclass - registrar una clase perl como una clase GObject

SINOPSIS

use Glib::Object::Subclass
   Some::Base::Class::,   # clase base, derivada de Glib::Object
   signals => {
          something_changed => {
             class_closure => sub { do_something_fun () },
             flags         => [qw(run-first)],
             return_type   => undef,
             param_types   => [],
          },
          some_existing_signal => \&class_closure_override,
   },
   properties => [
      Glib::ParamSpec->string (
         'some_string',
         'Some String Property',
         'This property is a string that is used as an example',
         'default value',
         [qw/readable writable/]
      ),
   ];

DESCRIPCIÓN

Este módulo le permite crear sus propias clases GObject, lo cual es útil para, por ejemplo, implementar sus propios widgets Gtk2.

No "exporta" nada a su espacio de nombres, sino que actúa más bien como un módulo pragmático que modifica su clase para hacer que funcione como una clase GObject.

Quizás se pregunte por qué no puede simplemente hacer bless de un Glib::Object en un paquete diferente y añadir algunas subs. Bueno, si no le interesan los parámetros del objeto, las señales, o que su nueva clase interopere transparentemente con otros módulos basados en GObject (por ejemplo, Gtk2 y compañía), entonces puede simplemente re-hacer bless.

Sin embargo, las señales, propiedades, funciones virtuales y las implementaciones de GInterface de un GObject son específicas de su GObjectClass. Si quiere crear un nuevo GObject que sea un derivado de GtkDrawingArea, pero que añada una nueva señal, debe crear un nuevo GObjectClass al cual añadir la nueva señal. Si no lo hace, entonces todos los GtkDrawingAreas en su aplicación obtendrán esa nueva señal.

Por lo tanto, la única manera de crear una nueva señal u propiedad de objeto en los enlaces de Perl para Glib es registrar una nueva subclase con el sistema de tipos de GLib a través de Glib::Type::register_object(). El módulo Glib::Object::Subclass es una interfaz amigable para el desarrollador de Perl a este poco de incompatibilidad de paradigmas.

USO

Este módulo funciona de manera similar al "use base" pragmático en el que registra el paquete actual como una subclase de alguna otra clase (que debe ser una GObjectClass implementada ya sea en C o en algún otro lenguaje).

El pragmático requiere al menos un argumento, el nombre de la clase padre. Los argumentos restantes son pares clave/valor, en cualquier orden, todos opcionales:

- properties => []
Añade propiedades de objeto; vea "PROPIEDADES".
- signals => {}
Añade o sobreescribe señales; vea "SEÑALES" y "SOBRESCRIBIENDO MÉTODOS BASE".
- interfaces => []
Añade GInterfaces a su clase; vea "INTERFACES".

(En realidad, todos estos parámetros se pasan directamente a Glib::Type::register_object(), añadiendo __PACKAGE__ (el nombre del paquete actual) como el nombre de la nueva clase hija.)

MÉTODOS Y FUNCIONES DE OBJETO

Los siguientes métodos se añaden a su clase bajo petición (aún no implementado), o de forma predeterminada a menos que su propia clase los implemente usted mismo. Esto significa que todos estos métodos y funciones obtendrán implementaciones predeterminadas razonables a menos que sean sobrescritos explícitamente por usted (definiendo su propia versión).

Excepto por "new", todos los siguientes son funciones y no métodos. Eso significa que usted no debe llamar al método de la superclase. En su lugar, el sistema GObject llamará a estas funciones por clase según sea necesario, emulando la herencia normal.

$class->new (attr => value, ...)
El constructor predeterminado simplemente llama a "Glib::Object::new", lo que le permite establecer propiedades en el objeto recién creado. Esto se hace porque muchos "new" métodos heredados por Gtk2 u otras bibliotecas no tienen "new" métodos adecuados para la subclase.
INIT_INSTANCE $self [no es un método]
"INIT_INSTANCE" se llama en cada clase en la jerarquía a medida que se crea el objeto (es decir, desde "Glib::Object::new" o nuestro predeterminado "new"). Use esta función para inicializar cualquier dato de miembro. La implementación predeterminada dejará el objeto intacto.
GET_PROPERTY $self, $pspec [no es un método]
SET_PROPERTY $self, $pspec, $newval [no es un método]
"GET_PROPERTY" y "SET_PROPERTY" se llaman cada vez que alguien hace "$object->get ($propname)" o "$object->set ($propname => $newval)" (también desde otros lenguajes). Las implementaciones predeterminadas mantienen los valores de las propiedades en el hash del objeto, equivalente a 
sub GET_PROPERTY {
  my ($self, $pspec) = @_;
  my $pname = $pspec->get_name;
  return (exists $self->{$pname} ? $self->{$pname}
          : $pspec->get_default_value);  # hasta que se establezca
}
sub SET_PROPERTY {
  my ($self, $pspec, $newval) = @_;
  $self->{$pspec->get_name} = $newval;
}

Debido a que "$pspec->get_name" convierte guiones en guiones bajos, una propiedad "line-style" está en el hash como "line_style".

Estos métodos le permiten almacenar/obtener propiedades de la manera que necesite. No tienen que estar en el hash, puede calcular algo, leer un archivo, lo que sea.

La mayoría de las veces escribirá su propio "SET_PROPERTY" para que pueda actuar cuando una propiedad cambia, como redibujar o redimensionar un widget. Por ejemplo.

sub SET_PROPERTY {
  my ($self, $pspec, $newval) = @_;
  my $pname = $pspec->get_name
  $self->{$pname} = $newval; # listo para el GET_PROPERTY predeterminado
  if ($pname eq 'line_style') {
    $self->queue_draw;  # redibujar con las nuevas líneas
  }
}

Se debe tener cuidado con los tipos boxed no referenciados por conteo como "Gtk2::Gdk::Color". En "SET_PROPERTY" el $newval generalmente es bueno solo durante la duración de la llamada. Use "copy" o similar si lo mantiene más tiempo (vea Glib::Boxed). En "GET_PROPERTY" la memoria devuelta debe durar lo suficiente para llegar al llamador, lo que generalmente significa devolver un campo, no un objeto recién creado (que se destruye con el escalar que lo contiene).

"GET_PROPERTY" es diferente de un método get_property en C en que el método perl devuelve el valor recuperado. Para simetría, los argumentos $newval y $pspec en "SET_PROPERTY" están intercambiados respecto al uso en C.

FINALIZE_INSTANCE $self [no es un método]
"FINALIZE_INSTANCE" se llama a medida que el GObject se está finalizando, es decir, a medida que se está destruyendo realmente. Esto es independiente del DESTROY más común en el objeto perl; de hecho, usted NO debe sobreescribir "DESTROY" (no es útil para usted, en cualquier caso, ¡ya que se llama múltiples veces!).

Use este gancho para liberar cualquier cosa que tenga que limpiar manualmente. FINALIZE_INSTANCE se llamará para cada instancia perl, en orden inverso de construcción.

El finalizador predeterminado no hace nada.

$object->DESTROY [NO SOBRESCRIBIR]
Nunca sobreescriba "DESTROY" ,use "FINALIZE_INSTANCE" en su lugar.

El método DESTROY de todas las clases perl derivadas de GTypes está implementado en el módulo Glib y (ab)usado para sus propósitos internos. Sobrescriting it is not useful as it will be called múltiples veces, y a menudo mucho antes de que el objeto sea realmente destruido. Sobrescribirlo podría ser muy perjudicial para tu programa, así que nunca hagas eso. Ten especial cuidado con otras clases en tu árbol ISA.

PROPIEDADES

Para crear propiedades de gobject, proporciona una lista de objetos Glib::ParamSpec como el valor para la clave 'properties'. Hay muchos constructores de paramspec diferentes, documentados en la página de Parámetros y Valores de la referencia de la API de C, así como en Glib::ParamSpec.

A partir de Glib 1.060, también puedes especificar getters y setters explícitos para tus propiedades en el momento de la creación. Los valores predeterminados en tus propiedades también se respetan si no estableces nada más. Consulta Glib::Type::register_object en Glib::Type para ver un ejemplo.

SEÑALES

Crear nuevas señales para tu nuevo objeto es fácil. Solo proporciona un hash de nombres de señal y descripciones de señal bajo la clave 'signals'. Cada descripción de señal también es un hash, con algunas claves esperadas. Todas las claves pueden omitirse.

flags => GSignalFlags
Si no está presente, se asume que es 'run-first'.
param_types => referencia a una lista de nombres de paquetes
Si no está presente, se asume que está vacía (sin parámetros).
class_closure => referencia a una subrutina a llamar como el closure de clase.
también puede ser una cadena interpretada como el nombre de una subrutina a llamar, pero deberías tener muchísimo cuidado con eso.

Si no está presente, la biblioteca intentará llamar al método llamado "do_signal_name" para la señal "signal_name" (usa guiones bajos).

Querrás tener cuidado de que este método manejador no sea un método públicamente invocable, ni uno que tenga el mismo nombre que algo que emite la señal. Debido a las formas peculiares en que Glib es diferente de Perl, los closures de clase no deberían heredarse a través de la herencia normal de perl.

return_type => nombre del paquete para el valor de retorno.
Si es indefinido o no está presente, la señal no espera ningún valor de retorno. Si está definido, se espera que la señal devuelva un valor; los flags deben estar configurados de modo que la señal no se ejecute solo primero (al menos usa 'run-last').
accumulator => acumulador del valor de retorno de la señal
citando el manual de Glib: "El acumulador de la señal es una función de retorno especial que se puede usar para recopilar los valores de retorno de los diversos callbacks que se llaman durante una emisión de señal."

Si no se especifica, se usa el acumulador predeterminado, y simplemente obtienes el valor de retorno del último manejador en ejecutarse.

Los acumuladores no están realmente documentados en gran medida en la referencia de C, y la interfaz de perl aquí es ligeramente diferente, así que aquí hay una cantidad inusual de detalles para esta característica arcanica:

La función acumuladora se llama para cada manejador como

($cont, $acc) = &$func ($invocation_hint, $acc, $ret)

$invocation_hint es un hash anónimo (incluyendo el nombre de la señal); $acc es el valor de retorno acumulado actual; $ret es el valor del manejador más reciente.

Los dos valores de retorno son un booleano $cont para indicar si la emisión de la señal debe continuar (falso para detener); y un nuevo $acc valor de retorno acumulado. (Esto es diferente de la versión de C, que escribe a través de un return_accu.)

ANULANDO MÉTODOS BASE

GLib usa algunos trucos ingeniosos con punteros de función para implementar métodos en C. Esto no es muy amigable para los enlaces de lenguaje, como podrías imaginar.

Sin embargo, como se describió arriba, cada señal permite un "closure de clase"; puedes anular el closure de clase con tu propia función, y puedes encadenar desde el método anulado al original. Esto sirve para implementar anulaciones virtuales para enlaces de lenguaje.

Entonces, para anular un método, proporcionas una referencia a una subrutina en lugar de un hash de descripción de señal como el valor para el nombre de la señal existente en el hash "signals" descrito en "SEÑALES".

# anular algunos métodos importantes del widget:
use Glib::Object::Subclass
      Gtk2::Widget::,
      signals => {
              expose_event => \&expose_event,
              configure_event => \&configure_event,
              button_press_event => \&button_press_event,
              button_release_event => \&button_release_event,
              motion_notify_event => \&motion_notify_event,
              # nota la elección de nombres aquí... ver la discusión.
              size_request => \&do_size_request,
      }

Es importante notar que los manejadores que proporcionas para estos son específicos de la clase, y que las reglas normales de herencia de métodos de perl no se siguen para invocarlos desde dentro de la biblioteca. Sin embargo, ¡el código de perl todavía puede encontrarlos! Por lo tanto, es bastante importante que elijas los nombres de tus manejadores cuidadosamente, evitando cualquier interfaz pública que puedas llamar desde perl. Como ejemplo, dado que size_request es un método de widget, elegí do_size_request como manejador de anulación.

INTERFACES

GObject soporta solo herencia única; en lugar de herencia múltiple, GObject usa GInterfaces. En los enlaces de Perl hemos disfrazado esto en su mayoría con herencia múltiple (es decir, simplemente agregando la clase GInterface al @ISA de la clase implementadora), pero al derivar nuevos objetos la fachada se rompe y la magia se filtra afuera.

Para derivar un objeto que implementa un GInterface, tienes que decirle al sistema de tipos de GLib que quieres que tu clase incluya un GInterface. Para hacer esto, simplemente pasa una lista de nombres de paquetes a través de la clave "interfaces"; esto agregará estos paquetes a tu @ISA, y hará que perl invoque métodos que debes proporcionar.

package Mup::MultilineEntry;
use Glib::Object::Subclass
    'Gtk2::TextView',
    interfaces => [ 'Gtk2::CellEditable' ],
    ;
# perl ahora invocará estos métodos, que son parte del
# GInterface GtkCellEditable, cuando alguien invoque los
# métodos correspondientes en minúscula en tus objetos.
sub START_EDITING { warn "start editing\n"; }
sub EDITING_DONE { warn "editing done\n"; }
sub REMOVE_WIDGET { warn "remove widget\n"; }
