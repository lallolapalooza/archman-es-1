NOMBRE

Net::OpenSSH - paquete cliente SSH de Perl implementado sobre OpenSSH

SINOPSIS

use Net::OpenSSH;
my $ssh = Net::OpenSSH->new($host);
$ssh->error and
  die "No se pudo establecer la conexión SSH: ". $ssh->error;
$ssh->system("ls /tmp") or
  die "falló el comando remoto: " . $ssh->error;
my @ls = $ssh->capture("ls");
$ssh->error and
  die "falló el comando remoto ls: " . $ssh->error;
my ($out, $err) = $ssh->capture2("find /root");
$ssh->error and
  die "falló el comando remoto find: " . $ssh->error;
my ($rin, $pid) = $ssh->pipe_in("cat >/tmp/foo") or
  die "falló el método pipe_in: " . $ssh->error;
print $rin "hello\n";
close $rin;
my ($rout, $pid) = $ssh->pipe_out("cat /tmp/foo") or
  die "falló el método pipe_out: " . $ssh->error;
while (<$rout>) { print }
close $rout;
my ($in, $out ,$pid) = $ssh->open2("foo");
my ($pty, $pid) = $ssh->open2pty("foo");
my ($in, $out, $err, $pid) = $ssh->open3("foo");
my ($pty, $err, $pid) = $ssh->open3pty("login");
my $sftp = $ssh->sftp();
$sftp->error and die "SFTP falló: " . $sftp->error;

DESCRIPCIÓN

Net::OpenSSH es un paquete cliente de shell seguro implementado sobre el cliente binario de OpenSSH ("ssh").

Bajo el capó

Este paquete está implementado en torno a la característica de multiplexación que se encuentra en las versiones posteriores de OpenSSH. Esa característica permite ejecutar varias sesiones a través de una única conexión SSH (OpenSSH 4.1 fue el primero en proporcionar toda la funcionalidad requerida).

Cuando se crea un nuevo objeto Net::OpenSSH, el cliente "ssh" de OpenSSH se ejecuta en modo maestro, estableciendo una conexión persistente (durante la vida útil del objeto) con el servidor.

Luego, cada vez que se solicita una nueva operación, se inicia un nuevo proceso "ssh" en modo esclavo, reutilizando efectivamente la conexión SSH maestra para enviar la solicitud al lado remoto.

Net::OpenSSH vs. módulos Net::SSH::.*

¿Por qué deberías usar Net::OpenSSH en lugar de cualquiera de los otros clientes SSH de Perl disponibles?

Bueno, esta es mi opinión (sesgada):

Net::SSH::Perl no está bien mantenido hoy en día (actualización: un nuevo mantenedor se ha hecho cargo, ¡¡¡así que esta situación podría cambiar!!!), requiere un montón de módulos (algunos de ellos muy difíciles de instalar) para ser aceptablemente eficiente y tiene una API que está limitada en algunas maneras.

Net::SSH2 es mucho mejor que Net::SSH::Perl, pero aún no es completamente estable. Puede ser muy difícil de instalar en algunos sistemas operativos específicos y su API también es limitada, de la misma manera que Net::SSH::Perl.

Usar Net::SSH::Expect, en general, es una mala idea. Manejar la interacción con un shell a través de Expect de forma genérica simplemente no se puede hacer de manera confiable.

Net::SSH es solo un envoltorio alrededor de cualquier comando SSH binario disponible en la máquina. Puede ser muy lento ya que establecen una nueva conexión SSH por cada operación realizada.

En comparación, Net::OpenSSH es un módulo puramente de Perl que no tiene dependencias obligatorias (obviamente, además de requerir los binarios de OpenSSH).

Net::OpenSSH tiene una interfaz muy perlish. La mayoría de las operaciones se realizan de una manera muy similar a la de las funciones integradas de Perl y módulos comunes (por ejemplo, IPC::Open2).

También es muy rápido. La sobrecarga introducida al lanzar un nuevo proceso ssh por cada operación no es apreciable (al menos en mi caja Linux). El cuello de botella es la latencia intrínseca del protocolo, por lo que Net::OpenSSH es probablemente tan rápido como puede ser un cliente SSH.

Basarse en OpenSSH también es una ventaja: se utiliza una implementación probada, estable, segura (a niveles paranoicos), inseparable y bien mantenida del protocolo SSH.

Por otro lado, Net::OpenSSH no funciona en Windows, ni siquiera bajo Cygwin.

Net::OpenSSH requiere específicamente el cliente SSH de OpenSSH (por lo que sé, la característica de multiplexación no está disponible en ningún otro cliente SSH). Sin embargo, ten en cuenta que interactuará con cualquier software de servidor, no solo con servidores que ejecuten el "sshd" de OpenSSH.

Para la autenticación por contraseña, se debe instalar IO::Pty. Otros módulos y binarios también son necesarios para implementar funcionalidades específicas (por ejemplo, Net::SFTP::Foreign, Expect o rsync(1)).

Net::OpenSSH y Net::SSH2 no soportan la versión 1 del protocolo SSH.

API

Argumentos opcionales

Casi todos los métodos en este paquete aceptan como primer argumento un puntero opcional a un hash que contiene parámetros ("\%opts"). Por ejemplo, estas dos llamadas a métodos son equivalentes:

my $out1 = $ssh->capture(@cmd);
my $out2 = $ssh->capture({}, @cmd);

Manejo de errores

La mayoría de los métodos devuelven undef (o una lista vacía) para indicar un fallo.

El método "error" siempre se puede usar para comprobar explícitamente los errores. Por ejemplo:

my ($output, $errput) = $ssh->capture2({timeout => 1}, "find /");
$ssh->error and die "ssh falló: " . $ssh->error;

Métodos de Net::OpenSSH

Estos son los métodos proporcionados por el paquete:

Net::OpenSSH->new($host, %opts)
Crea una nueva conexión maestra SSH

$host puede ser un nombre de host o una dirección IP. También puede contener el nombre del usuario, su contraseña y el número de puerto TCP en el que escucha el servidor:

my $ssh1 = Net::OpenSSH->new('jack@foo.bar.com');
my $ssh2 = Net::OpenSSH->new('jack:secret@foo.bar.com:10022');
my $ssh3 = Net::OpenSSH->new('jsmith@2001:db8::1428:57ab'); # IPv6

Las direcciones IPv6 opcionalmente pueden ir entre corchetes:

my $ssh4 = Net::OpenSSH->new('jsmith@[::1]:1022');

Este método siempre tiene éxito al devolver un nuevo objeto. La comprobación de errores debe realizarse explícitamente después:

my $ssh = Net::OpenSSH->new($host, %opts);
$ssh->error and die "No se puede hacer ssh a $host: " . $ssh->error;

Si tienes problemas para que Net::OpenSSH se conecte al host remoto, lee el capítulo de solución de problemas cerca del final de este documento.

kill_ssh_on_timeout => 1
Esta opción indica a Net::OpenSSH que mate el proceso SSH esclavo local cuando alguna operación supere el tiempo de espera.

strict_mode => 0
Por defecto, la conexión se abortará si la ruta al socket utilizado para la multiplexión resulta insegura (por ejemplo, cuando alguno de los directorios padre es escribible por otros usuarios).

Esta opción se puede utilizar para deshabilitar esa función. ¡¡¡Úselo con precaución!!!

async => 1
Por defecto, el constructor espera hasta que el socket de multiplexión esté disponible. Esta opción se puede utilizar para aplazar la espera hasta que el socket se utilice realmente.

Por ejemplo, el siguiente código se conecta a varias máquinas remotas en paralelo:

my (%ssh, %ls);
# se establecen múltiples conexiones en paralelo:
for my $host (@hosts) {
    $ssh{$host} = Net::OpenSSH->new($host, async => 1);
}
# luego para ejecutar algún comando en todos los hosts (secuencialmente):
for my $host (@hosts) {
    $ssh{$host}->system('ls /');
}

Habilita el reenvío del agente de autenticación.

Cuando se pasa "always" como argumento, el reenvío del agente estará habilitado por defecto en todos los canales creados desde el objeto. De lo contrario, tendrá que ser solicitado explícitamente al llamar a los métodos de creación de canales (es decir, "open_ex" y sus derivaciones).

Tenga en cuenta que Net::OpenSSH no ejecutará "ssh-agent" por usted. Esto debe hacerse con anticipación y la variable de entorno "SSH_AUTH_SOCK" debe estar configurada apuntando al lugar correcto.

Ejemplo:

Por defecto, cuando se utiliza autenticación por contraseña, el módulo espera que el lado remoto envíe una solicitud de contraseña que coincida con "/[?:]/".

Esta opción se puede utilizar para anular ese valor predeterminado para los casos raros en los que se utiliza una solicitud diferente.

Ejemplos:

login_handler => \&custom_login_handler
Algunos servidores SSH remotos pueden requerir una interacción de inicio de sesión/autenticación personalizada que no es compatible de forma nativa con Net::OpenSSH. En esos casos, puede utilizar esta opción para reemplazar la lógica de inicio de sesión predeterminada.

La devolución de llamada se invocará repetidamente como "custom_login_handler($ssh, $pty, $data)", donde $ssh es el objeto Net::OpenSSH actual, "pty" es un objeto IO::Pty adjunto al TTY del proceso SSH esclavo y $data es una referencia a un escalar que puede utilizar a voluntad.

El manejador de inicio de sesión debe devolver 1 después de que el proc de inicio de sesión

completado exitosamente o 0 en caso de que aún necesite hacer algo más. Si ocurre algún error, debe fallar.

Tenga en cuenta que las operaciones de bloqueo no deben realizarse dentro del manejador de inicio de sesión (al menos si desea que las características "async" y "timeout" funcionen).

Vea también el script de ejemplo "login_handler.pl" en el directorio "examples".

El uso de esta opción es incompatible con las opciones "password" y "passphrase"; deberá manejar la contraseña o las frases secretas desde el manejador personalizado usted mismo.

master_setpgrp => 1
Cuando esta opción está configurada, el proceso maestro se ejecuta como un grupo de procesos diferente. Como consecuencia, no morirá cuando el usuario presione Ctrl-C en la terminal.

Para permitir que el proceso maestro SSH solicite cualquier información al usuario, el módulo puede configurarlo como el proceso de control de la terminal mientras se establece la conexión (usando "tcsetpgrp" en POSIX). Después, el proceso de control de la terminal se restablece.

Esta característica es altamente experimental. Por favor, informe de cualquier problema que encuentre.

master_pty_force => 1
Por defecto, Net::OpenSSH adjunta el proceso maestro SSH a un pty solo cuando se solicita algún tipo de autenticación interactiva. Si esta bandera está configurada, siempre se adjuntará un pty.

Eso permite obtener mejores diagnósticos para algunos tipos de errores (como, por ejemplo, claves de host incorrectas) y también permite recuperar el registro del pty usando get_master_pty_log.

$ssh->error
Devuelve la condición de error para la última operación realizada.

El valor devuelto es un dualvar como $! (ver "$!" en perlvar) que muestra un mensaje informativo cuando se usa en contexto de cadena o un número de error en contexto numérico (los códigos de error aparecen en Net::OpenSSH::Constants).

$ssh->get_master_pty_log
Para manejar la autenticación de contraseña o la entrada de la frase secreta para una clave privada, Net::OpenSSH puede ejecutar el proceso maestro SSH conectado a un pty.

En ese caso y después de que una llamada al constructor devuelva un error de falla de conexión, se puede llamar a este método para recuperar la salida capturada en el pty (el registro se descarta cuando la conexión se establece exitosamente).

Cualquier dato consumido del pty por los manejadores de inicio de sesión personalizados faltará en el registro devuelto.

$ssh->get_user
$ssh->get_host
$ssh->get_port
Devuelve los parámetros de inicio de sesión SSH correspondientes.
$ssh->get_ctl_path
Devuelve la ruta al socket donde el proceso maestro OpenSSH escucha nuevas conexiones multiplexadas.
($in, $out, $err, $pid) = $ssh->open_ex(\%opts, @cmd)
Nota: ¡este es un método de bajo nivel que probablemente no necesite usar!

Este método inicia el comando @cmd en la máquina remota creando nuevas tuberías para los canales de E/S según se especifica en el hash %opts.

Si se omite @cmd, se ejecuta el shell del usuario remoto.

Devuelve cuatro valores, los tres primeros ($in, $out y $err) corresponden al lado local de las tuberías creadas (pueden ser undef) y el cuarto ($pid) al PID del nuevo proceso esclavo de SSH. Se devuelve una lista vacía en caso de fallo.

Tenga en cuenta que se debe usar "waitpid" después para recopilar el proceso esclavo de SSH.

Opciones aceptadas:

stdin_pipe => 1
Crea una nueva tubería y conecta el lado de lectura al flujo stdin del proceso remoto. El lado de escritura se devuelve como el primer valor ($in).
stdin_pty => 1
Similar a "stdin_pipe", pero en lugar de una tubería regular, utiliza un pseudo-tty (pty).

Tenga en cuenta que en algunos sistemas operativos (por ejemplo, HP-UX, AIX), los ttys no son fiables. Pueden desbordarse cuando se escriben grandes trozos o cuando los datos se escriben más rápido de lo que se leen.

stdin_fh => $fh
Duplica $fh y lo utiliza como flujo stdin del proceso remoto.
stdin_file => $filename
stdin_file => \@open_args
Abre el archivo con el nombre dado para lectura y lo utiliza como flujo de entrada estándar del proceso remoto.

Si se pasa una referencia de matriz, sus contenidos se utilizan como argumentos para la llamada subyacente a open. Por ejemplo:

$ssh->system({stdin_file => ['-|', 'gzip -c -d file.gz']}, $rcmd);

Utiliza /dev/null como flujo stdin del proceso remoto.
stdout_pipe => 1
Crea una nueva tubería y conecta el lado de escritura al flujo stdout del proceso remoto. El lado de lectura se devuelve como el segundo valor ($out).
stdout_pty => 1
Conecta el flujo stdout del proceso remoto al pseudo-pty. Esta opción requiere que "stdin_pty" también esté configurado.
stdout_fh => $fh
Duplica $fh y lo utiliza como flujo stdout del proceso remoto.
stdout_file => $filename
stdout_file => \@open_args
Abre el archivo con el nombre de archivo dado y redirige stdout allí.
stdout_discard => 1
Utiliza /dev/null como flujo stdout del proceso remoto.

stdinout_dpipe => $cmd

Ejecuta el comando dado localmente adjuntando sus flujos stdio a los del comando SSH remoto. Conceptualmente, es equivalente al comando de shell dpipe(1).

Crea una nueva tubería y conecta el lado de escritura al flujo stderr del proceso remoto. El lado de lectura se devuelve como el tercer valor ($err).

Duplica $fh y lo utiliza como flujo stderr del proceso remoto.
stderr_file => $filename
Abre el archivo con el nombre dado y redirige stderr allí.
stderr_to_stdout => 1
Hace que stderr apunte a stdout.
tty => $bool
Indica a "ssh" que asigne un pseudo-tty para el proceso remoto. Por defecto, se asigna un tty si el flujo de entrada estándar del comando remoto está conectado a un tty.

Cuando esta bandera está configurada y la entrada estándar no está conectada a un tty, los procesos maestro y esclavo de ssh pueden generar advertencias espurias sobre operaciones de tty fallidas. Esto es causado por un error presente en versiones antiguas de OpenSSH.

close_slave_pty => 0
Cuando se utiliza un pseudo pty para el flujo de entrada estándar, el lado esclavo se cierra automáticamente en el proceso padre después de bifurcar el comando ssh.

Esta opción deshabilita esa característica, de modo que el pty esclavo se pueda acceder en el proceso padre como "$pty->slave". Deberá cerrarse explícitamente (ver IO::Pty)

remote_shell => $shell
Establece el shell remoto. Permite cambiar el mecanismo de comillas de argumentos de forma individual por comando.

Esto puede ser útil al interactuar con una máquina Windows donde el análisis de argumentos puede realizarse a nivel de comando de maneras personalizadas.

Ejemplo:

forward_agent => $bool
Habilita/deshabilita el reenvío del agente de autenticación.

Esta opción solo se puede usar cuando el reenvío del agente se solicitó previamente en el constructor.

forward_X11 => $bool
Habilita/deshabilita el reenvío del protocolo X11.

Esta opción solo se puede usar cuando el reenvío X11 se solicitó previamente en el constructor.

ssh_opts => \@opts
Lista de opciones adicionales para el "ssh" comando.

Esta característica debe usarse con cuidado, ya que las opciones dadas no son verificadas de ninguna manera por el módulo, y podrían interferir con él.

tunnel => $bool
En lugar de ejecutar un comando en el host remoto, esta opción indica a Net::OpenSSH que cree un túnel TCP. Los argumentos se convierten en la IP y el puerto de destino o la ruta remota para un socket Unix.

Ejemplo:

my ($in, $out, undef, $pid) = $ssh->open_ex({tunnel => 1}, $IP, $port);
my ($in, $out, undef, $pid) = $ssh->open_ex({tunnel => 1}, $socket_path);

Ver también "Tunnels".

subsystem => $bool
Solicita una conexión a un subsistema SSH. El nombre del subsistema debe pasarse como argumento, como en el siguiente ejemplo: 
my $s = $ssh->open2socket({subsystem => 1}, 'netconf');
encoding => $encoding
argument_encoding => $encoding
Establece las codificaciones. Ver "Data encoding".

Ejemplo de uso:

# similar a la función open2 de IPC::Open2:
my ($in_pipe, $out_pipe, undef, $pid) =
    $ssh->open_ex( { stdin_pipe => 1,
                     stdout_pipe => 1 },
                   @cmd )
    or die "open_ex falló: " . $ssh->error;

# ...

setpgrp => 1
Llama a "setpgrp" después de bifurcar el proceso hijo. Como resultado, no morirá cuando el usuario presione Ctrl+C en la consola. Ver también "setpgrp" en perlfunc.

Usar esta opción sin establecer también "master_setpgrp" en la llamada al constructor es en gran parte inútil, ya que la señal se entregará al proceso maestro y todos los comandos remotos se abortarán.

Esta característica es experimental.

$ssh->system(\%opts, @cmd)
Ejecuta el comando @cmd en la máquina remota.

Devuelve verdadero en caso de éxito, indefinido en caso contrario.

El estado de error se establece en "OSSH_SLAVE_CMD_FAILED" cuando el comando remoto sale con un código distinto de cero (el código está disponible en $?, ver "$?" en perlvar).

Ejemplo:

$ssh->connect
Intenta establecer la conexión maestra.

Este método se llama automáticamente cuando se invoca el primer método que necesita una conexión (por ejemplo, `open->shell` o `system`). Si se llama explícitamente, esperará a que la conexión se realice. Solo hay una conexión maestra de ida y vuelta por host. Si la conexión maestra ya existe, no se vuelve a intentar y se devuelve verdaderamente.

Puede que se necesite llamar a este método antes de que cualquier otro método sea invocado cuando la opción `async` se establece a verdadero durante la creación del objeto. De otra manera, si no se establece `async` a verdadero, el método `wait_for_master` se llama automáticamente y bloquea el proceso hasta que la conexión maestra esté disponible.

En caso de fallo, este método puede lanzar una excepción o devolver falso. Usa el método `error` para obtener más detalles. Si se ha llamado a `connect` antes, es posible que necesites llamar `wait_for_master` para obtener el estado de la conexión.

Comillas de shell

Por defecto, al invocar comandos remotos, este módulo intenta imitar el comportamiento incorporado de `system` de Perl con respecto al procesamiento de argumentos. Entrecomillando `system` en perlfunc:

El procesamiento de argumentos varía según el número de argumentos. Si
hay más de un argumento en LIST, o si LIST es una matriz con más de un valor,
inicia el programa dado por el primer elemento de la lista con los argumentos
dados por el resto de la lista. Si hay solo un argumento escalar, el argumento
se comprueba si hay metacaracteres de shell y, si los hay, todo el argumento se
pasa al shell de comandos del sistema para su análisis (este es "/bin/sh -c" en
plataformas Unix, pero varía en otras plataformas).

Toma como ejemplo el método `system` de Net::OpenSSH:

$ssh->system("ls -l *");
$ssh->system('ls', '-l', '/');

La primera llamada pasa el argumento sin cambios a ssh y se ejecuta en el lado remoto a través del shell, que interpreta los metacaracteres.

La segunda llamada escapa cualquier metacaracter de shell de modo que, efectivamente, sea equivalente a llamar al comando directamente y no a través del shell.

Bajo el capó, como el protocolo Secure Shell no proporciona este modo de operación y siempre inicia un nuevo shell donde ejecuta el comando dado, Net::OpenSSH entrecomilla cualquier metacaracter de shell en la lista de comandos.

Todos los métodos que invocan un comando remoto (system, open_ex, etc.) aceptan la opción "quote_args" que permite forzar/deshabilitar las comillas de shell.

Por ejemplo:

$ssh->system({quote_args => 1}, "/ruta con espacios/bin/foo");

manejará correctamente los espacios en la ruta del programa.

El mecanismo de comillas de shell implementa algunas extensiones (por ejemplo, realizar redirecciones a /dev/null en el lado remoto) que se pueden deshabilitar con la opción "quote_args_extended":

$ssh->system({ stderr_discard => 1,
               quote_args => 1, quote_args_extended => 0 },
             @cmd);

La opción "quote_args" también puede usarse para deshabilitar las comillas cuando se pasan más de un argumento. Por ejemplo, para expandir algún patrón por el shell remoto:

$ssh->system({quote_args => 0}, 'ls', '-l', "/tmp/files_*.dat");

El método "shell_quote" puede usarse para entrecomillar selectivamente algunos argumentos y dejar otros sin tocar:

$ssh->system({quote_args => 0},
             $ssh->shell_quote('ls', '-l'),
             "/tmp/files_*.dat");

Tiempos de espera

Para detener los procesos remotos cuando exceden el tiempo de espera, la mejor forma sería enviar señales a través de la conexión SSH según el estándar del protocolo. Sin embargo, OpenSSH no implementa esta función, por lo que Net::OpenSSH tiene que usar métodos imperfectos:

  • cerrar los flujos de I/O de la escucha remota

    Cerrando los flujos de entrada estándar (STDIN) y salida estándar (STDOUT) de un proceso remoto inactivo hará que el proceso intente acceder a uno de ellos y se transmitirá un SIGPIPE.

    Los procesos remotos pueden no acceder a STDIN o STDOUT, pero Net::OpenSSH puede cerrar estos canales solo cuando los captura, por lo que este enfoque no siempre funciona.

  • terminar el proceso local de SSH

    Esta acción puede dejar el proceso remoto activo, creando un orfano remoto, por lo que Net::OpenSSH no lo utiliza, a menos que se configure la opción de construcción "kill_ssh_on_timeout".

Afortunadamente, futuras versiones de OpenSSH podrán señalar a los procesos remotos a través del canal mux.

Expansión de variables

La función de expansión de variables permite definir variables que se expanden automáticamente dentro de argumentos de comandos y caminos de archivos.

Esta función se desactiva por defecto y se utiliza con módulos como Net::OpenSSH::Parallel y otros similares.

Las variables se delimitan por un par de signos del porcentaje ("%"), por ejemplo "%HOST%". También, dos signos del porcentaje consecutivos se reemplazan por uno solo.

Las variables especiales "HOST", "USER" y "PORT" son mantenidas internamente por el módulo y toman los valores obvios.

La expansión de variables se realiza antes de la expansión de comandos en la shell (ver "Expansión de comandos en la shell").

Un ejemplo de uso:

my $ssh = Net::OpenSSH->new('server.foo.com', expand_vars => 1);
$ssh->set_var(ID => 42);
$ssh->system("ls >/tmp/ls.out-%HOST%-%ID%");

dirigirá la salida del comando "ls" a "/tmp/ls.out-server.foo.com-42" en el host remoto.

Puertos de túnel

Además de ejecutar comandos en el host remoto, Net::OpenSSH también permite crear puertos de túnel para máquinas remotas accesibles desde el servidor SSH.

Esta funcionalidad se presenta mediante la opción "tunnel" del método "open_ex", así como mediante métodos wrapper "open_tunnel" y "capture_tunnel", y otros donde sea adecuado.

Ejemplo:

$ssh->system({tunnel => 1,
              stdin_data => "GET / HTTP/1.0\r\n\r\n",
              stdout_file => "/tmp/$server.res"},
             $server, 80)
    or die "unable to retrieve page: " . $ssh->error;

o capturar la salida de varias solicitudes en paralelo:

my @pids;
for (@servers) {
  my $pid = $ssh->spawn({tunnel => 1,
                         stdin_file => "/tmp/request.req",
                         stdout_file => "/tmp/$_.res"},
                        $_, 80);
  if ($pid) {
    push @pids, $pid;
  }
  else {
    warn "unable to spawn tunnel process to $_: " . $ssh->error;
  }
}
waitpid ($_, 0) for (@pids);

Más allá de eso, para crear un túnel, se genera un nuevo proceso "ssh" con la opción "-W${address}:${port}" (disponible desde OpenSSH 5.4 y más tarde), lo que lo dirige a la dirección remota dada. A diferencia de cuando se usa "ssh" con la opción "-L" para crear un túnel, no se abre ningún puerto TCP en el lado local, por lo que esta operación es completamente segura.

El PID del nuevo proceso se devuelve mediante métodos nombrados. Debe eliminarse la PID una vez que los manejadores de canal para el lado local hayan sido cerrados.

Es necesario que la versión de OpenSSH sea 5.4 o superior para que la funcionalidad de túnel funcione. También, notar que el forwarding de puertos puede ser administrativamente prohibido en el lado del servidor (ver sshd(8) y sshd_config(5) o la documentación proporcionada por el proveedor del servidor SSH).

Túneles dirigidos a sockets UNIX

Cuando se conecta a hosts que ejecuten una versión reciente de OpenSSH sshd, también se pueden abrir conexiones dirigidas a sockets UNIX.

Por ejemplo:

my $response = $ssh->capture({tunnel => 1, stdin_data => $request },
                             "/tmp/socket-foo");

Actualmente, esta función requiere un cliente OpenSSH con parche. El parche está disponible como "patches/openssh-fwd-stdio-to-streamlocal-1.patch".

Redirección de puertos

Net::OpenSSH no ofrece soporte directo para manejar la redirección de puertos entre servidor y cliente. Sin embargo, puede hacerse fácilmente pasando opciones personalizadas a los métodos.

Por ejemplo, las opciones de túnel pueden pasarse al constructor:

my $ssh = Net::OpenSSH->new(...
                  master_opts => -Llocalhost:1234:localhost:3306');

También se pueden cambiar las redirecciones de puertos para una conexión SSH en ejecución usando el comando Control:

# configurando un túnel:
$ssh->system({ssh_opts => ['-O','forward',
                           '-L127.0.0.1:12345:127.0.0.1:3306']});
# cancelando el túnel:
$ssh->system({ssh_opts => ['-O', 'cancel',
                           '-L127.0.0.1:12345:127.0.0.1:3306']});

Codificación de datos

Net::OpenSSH tiene cierto soporte para convertir transparentemente los datos enviados o recibidos por el servidor remoto a representación interna de Unicode en Perl.

Los métodos que soportan esta funcionalidad son aquellos que mueven datos entre estructuras de Perl (por ejemplo, "capture", "capture2", "capture_tunnel" y métodos que soportan la opción "stdin_data"). Los datos accesibles a través de tuberías, sockets o redirecciones no se ven afectados por las opciones de codificación.

También es posible configurar la codificación del comando y de los argumentos pasados al servidor remoto en la línea de comandos.

Por defecto, si no se proporciona ninguna opción de codificación en el constructor o en las llamadas a métodos, Net::OpenSSH no realizará ninguna transformación de codificación, procesando los datos como "latin1".

Cuando los datos no pueden convertirse entre la representación interna de Perl y la codificación seleccionada dentro de algún método de Net::OpenSSH, se lanzará un error "OSSH_ENCODING_ERROR".

Las opciones de codificación soportadas son las siguientes:

stream_encoding => $encoding
define la codificación de los datos recibidos y enviados en métodos de captura.
argument_encoding => $encoding
define la codificación de los argumentos de la línea de comandos.
encoding => $encoding
define ambas "argument_encoding" y "stream_encoding"

El constructor también acepta "default_encoding", "default_stream_encoding" y "default_argument_encoding" que establecen los valores por defecto.

Desviando la funcionalidad "new"

Cuando se instala una referencia de código en $Net::OpenSSH::FACTORY, las llamadas a "new" se redirigen a través de ella.

Esta característica puede usarse para transportar el flujo de entrada y salida de los procesos.

APLICACIÓN ADICIONAL

Hay varias formas en que Net::OpenSSH puede usarse para hacer las cosas un poco más convenientes. Por ejemplo, la conexión de multiplexación se puede implementar, por ejemplo:

my $old_factory = $Net::OpenSSH::FACTORY;
%cache;
sub factory {
  my ($class, %opts) = @_;
  my $signature = join("\0", $class, map { $_ => $opts{$_} }, sort keys %opts);
  my $old = $cache{$signature};
  return $old if ($old and $old->error != OSSH_MASTER_FAILED);
  local $Net::OpenSSH::FACTORY = $old_factory;
  $cache{$signature} = $class->new(%opts);
}
$Net::OpenSSH::FACTORY = \&factory;

... ¡y estoy seguro de que se puede abusar de él de muchas otras maneras!

my ($pty, $pid) = $ssh->open2pty({stderr_to_stdout => 1})

my $telnet = Net::Telnet->new(-fhopen => $pty,

mod_perl y mod_perl2

mod_perl y mod_perl2 vinculan STDIN y STDOUT a objetos que no están respaldados por descriptores de archivo reales a nivel del sistema operativo. Net::OpenSSH fallará si alguno de estos identificadores se utiliza de forma explícita o implícita al llamar a algún comando remoto.

La solución es redirigirlos a "/dev/null" o a algún archivo:

open my $def_in, '<', '/dev/null' or die "unable to open /dev/null";
my $ssh = Net::OpenSSH->new($host,
                            default_stdin_fh => $def_in);
my $out = $ssh->capture($cmd1);
$ssh->system({stdout_discard => 1}, $cmd2);
$ssh->system({stdout_to_file => '/tmp/output'}, $cmd3);

Además, ten en cuenta que desde el punto de vista de la seguridad, ejecutar "ssh" desde dentro del proceso del servidor web no es una gran idea. Un atacante que explote algún error de Apache podría acceder a las claves y contraseñas SSH y obtener acceso ilimitado a los sistemas remotos.

Si puedes, usa una cola (como TheSchwartz) o cualquier otro mecanismo para ejecutar los comandos ssh desde otro proceso que se ejecute bajo una cuenta de usuario diferente.

Como mínimo, asegúrate de que "~www-data/.ssh" (o similar) no sea accesible a través del servidor web.

AnyEvent (y frameworks similares)

Net::OpenSSH proporciona toda la funcionalidad requerida para integrarse dentro de un framework de programación orientado a eventos como AnyEvent o IO::Async de la siguiente manera:

1. Crear un objeto Net::OpenSSH desconectado:
my $ssh = Net::OpenSSH->new($host, async => 1, ...);
2. Permitir que el objeto se conecte al host remoto:
Utiliza un temporizador para llamar al método "wait_for_master" en modo asíncrono repetidamente hasta que devuelva un valor verdadero que indique éxito.

Además, se debe verificar el estado de error del objeto después de cada llamada para detectar conexiones fallidas. Por ejemplo:

my $ssh = Net::OpenSSH->new(..., async => 1);
my $w;
$w = AE::timer 0.1, 0.1, sub {
  if ($ssh->wait_for_master(1)) {
    # ¡la conexión se ha establecido!
    # ahora se pueden ejecutar comandos remotos
    undef $w;
    on_ssh_success(...);
  }
  elsif ($ssh->error) {
    # no se puede establecer la conexión
    undef $w;
    on_ssh_failure(...);
  }
}
3. Usar el framework de eventos para lanzar los procesos remotos:
Llama a "make_remote_command" de Net::OpenSSH para construir comandos que se puedan ejecutar utilizando las instalaciones regulares del framework para lanzar comandos externos.

La verificación de errores también debe realizarse en este punto porque la conexión SSH podría haberse roto.

Por ejemplo:

if (defined(my $cmd = $ssh->make_remote_command(echo => 'hello!')) {
  AnyEvent::Util::run_cmd($cmd, %run_cmd_opts);
}
else {
  # ¡algo salió mal!
}

Alternativamente, se podrían usar cualquiera de los métodos "open*" proporcionados por Net::OpenSSH para lanzar comandos remotos.

4. Al terminar, desconectar asincrónicamente
Después de iniciar una desconexión asíncrona con disconnect(1), llama repetidamente a "wait_for_master" hasta que obtengas un valor definido pero falso: 
$ssh->disconnect(1);
my $w; $w = AE::timer 0.1, 0.1, sub {
  my $res = $ssh->wait_for_master(1);
  if (defined $res && !$res) {
    undef $w;
    undef $ssh;
  }
};

Ten cuidado de no dejar que el objeto $ssh salga del ámbito hasta que la desconexión haya finalizado, de lo contrario, su destructor esperará y bloqueará tu programa hasta que la desconexión se complete.

Otros módulos

A menudo, es posible instruirlos para que utilicen una conexión multiplexada de Net::OpenSSH empleando alguna opción del constructor disponible. Por ejemplo:

o...

use GRID::Machine;
...
my @cmd = $ssh->make_remote_command('/usr/bin/perl');

En otros casos, los módulos de terceros proporcionan algún tipo de mecanismo de plugin para permitir diferentes transportes. El método "open2" puede usarse para crear un par de tuberías para el transporte en estos casos.

SOLUCIÓN DE PROBLEMAS

Por lo general, Net::OpenSSH funciona sin problemas, pero cuando falla, a algunos usuarios les cuesta encontrar la causa del problema. Esta mini guía de solución de problemas debería ayudarte a encontrarla y resolverla.

1 - Comprueba el mensaje de error
Agrega en tu script, después de la llamada al constructor de Net::OpenSSH, una verificación de errores: 
$ssh = Net::OpenSSH->new(...);
$ssh->error and die "SSH connection failed: " . $ssh->error;

El mensaje de error te dirá qué salió mal.

2 - Comprueba los parámetros de conexión
Lo creas o no, pasar parámetros incorrectos a Net::OpenSSH es una de las principales causas de fallos, así que comprueba que estás utilizando los parámetros correctos.

Específicamente, si los obtienes del exterior, asegúrate de que no tengan espacios adicionales o saltos de línea adjuntos (¿necesitas "chomp"?).

Las contraseñas y las URI pueden contener caracteres de "$" o "@". Si los has codificado en tu script, asegúrate de que estén correctamente entrecomillados (y, por cierto, usa "strict").

3 - Versión de OpenSSH
Asegúrate de tener una versión de "ssh" suficientemente reciente: 
$ ssh -V
OpenSSH_5.1p1 Debian-5, OpenSSL 0.9.8g 19 Oct 2007

OpenSSH versión 4.1 fue la primera en admitir la función de multiplexación y es el mínimo requerido por el módulo para funcionar. Te recomiendo que uses la última versión de OpenSSH (actualmente 7.5).

La opción del constructor "ssh_cmd" te permite seleccionar el binario "ssh" a utilizar. Por ejemplo:

$ssh = Net::OpenSSH->new($host,
                         ssh_cmd => "/opt/OpenSSH/5.8/bin/ssh")

Algunos proveedores de hardware (por ejemplo, Sun, err... Oracle) incluyen versiones personalizadas de OpenSSH empaquetadas con el sistema operativo. En principio, Net::OpenSSH debería funcionar con estos clientes SSH siempre que se deriven de alguna versión de OpenSSH suficientemente reciente. De todos modos, ¡mi consejo es usar el software OpenSSH real si puedes!

4 - Ejecuta ssh desde la línea de comandos
Comprueba que puedes conectarte al host remoto usando los mismos parámetros que estás pasando a Net::OpenSSH. En particular, asegúrate de que estás ejecutando "ssh" como el mismo usuario local.

Si estás ejecutando tu script desde un servidor web, el usuario probablemente sería "www", "apache" o algo similar.

Problemas comunes son:

  • La clave pública del host remoto no está presente en el archivo known_hosts.

    El protocolo SSH utiliza claves públicas para identificar los hosts remotos, de modo que no puedan ser suplantados por terceros malintencionados.

    Para OpenSSH, normalmente la clave pública del servidor se almacena en "/etc/s"

  • "/etc/ssh/ssh_host_dsa_key.pub" o en "/etc/ssh/ssh_host_rsa_key.pub" y qué clave debe copiarse en el archivo "~/.ssh/known_hosts" de la máquina local (otras implementaciones de SSH podrían usar otras ubicaciones de archivos).
  • La clave pública del host remoto en el archivo de conocidos es incorrecta.

    Este es otro problema común que ocurre cuando un servidor es reemplazado o reiniciado de cero y su clave pública cambia a ser diferente a la instalada en el archivo de conocidos.

    La forma más fácil de resolver este problema es eliminar la clave antigua del archivo de conocidos manualmente usando cualquier editor y luego conectar al servidor respondiendo "yes" cuando se le pregunte por la clave nueva.

  • Permisos incorrectos en el directorio "~/.ssh" o sus contenidos.

    El cliente OpenSSH realiza varias comprobaciones sobre los permisos del directorio "~/.ssh" y sus contenidos y rechaza usarlos cuando están mal configurados. Consulte la sección FILES de la página ssh(1) del manual.

  • Configuración incorrecta para la autenticación por contraseña o clave pública.

    Verifique que esté usando la contraseña correcta o que la clave pública del usuario esté correctamente instalada en el servidor.

5 - chequeos de seguridad en el socket de multiplexing
Net::OpenSSH realiza algunos chequeos de seguridad en el directorio donde se va a colocar el socket de multiplexing para asegurarse de que no pueda ser accedido por otros usuarios.

La ubicación predeterminada del socket de multiplexing está bajo "~/.libnet-openssh-perl". Puede modificarse usando los argumentos "ctl_dir" y "ctl_path" del constructor de la clase.

Los requisitos para este directorio y sus padres son:

  • Deben ser todos propiedad del usuario que ejecuta el script o de root.
  • Deben tener un umbral de permisos 0755 o más restrictivo, de manera que nadie más pueda realizar operaciones de escritura en ellos.

La opción del constructor "strict_mode" deshabilita estos chequeos de seguridad, pero no debe usarse a menos que comprenda sus implicaciones.

6 - el sistema de archivos debe soportar sockets
Algunos sistemas de archivos (como por ejemplo FAT o AFS) no soportan colocar sockets dentro de ellos.

Asegúrese de que la ruta "ctl_dir" no esté dentro de esos sistemas de archivos.

DEPURACIÓN

La depuración interna de Net::OpenSSH está controlada por la variable $Net::OpenSSH::debug. Cada bit de esta variable activa la depuración de algunos subsistemas según lo siguiente:

bit 1 - errores
Imprime cambios en el atributo interno del objeto donde se almacenan los errores.
bit 2 - ctl_path
Imprime información sobre el cálculo de ctl_path y las pruebas realizadas en ese directorio para decidir si es seguro colocar el socket de multiplexing dentro de él.
bit 4 - conectando
Imprime información sobre el establecimiento de nuevas conexiones master.
bit 8 - comandos y argumentos
Imprime los comandos y argumentos de cada llamada a sistema/exec.
bit 16 - ejecución de comandos
Imprime información sobre el progreso de la ejecución de comandos.
bit 32 - destrucción
Imprime información sobre la destrucción de objetos de Net::OpenSSH y la terminación de los procesos master de SSH.
bit 64 - bucle_IO
Imprime información sobre el progreso del bucle_IO en operaciones de captura.
bit 128 - hexadumps
Genera hexadumps de la información que viaja por los canales SSH durante las capturas.
bit 512 - rastreo del proceso master en el sistema operativo
Usa el módulo Net::OpenSSH::OSTracer para rastrear el proceso master de SSH a nivel del sistema operativo.

Por ejemplo, para activar todas las banderas de depuración, puede usar:

$Net::OpenSSH::debug = ~0;

Tenga en cuenta que el significado de las banderas y la información generada está destinada únicamente a la depuración del módulo y puede cambiar sin previo aviso entre versiones.

Si está utilizando autenticación por contraseña, habilitar la depuración para IO::Tty también puede mostrar información interesante:

$IO::Tty::DEBUG = 1;

Finalmente, por defecto, la salida de depuración se envía a "STDERR". Puede cambiarlo apuntando $Net::OpenSSH::debug_fh a un manejador de archivo diferente. Por ejemplo:

BEGIN {
  open my $out, '>', '/tmp/debug.txt' or warn $!;
  $Net::OpenSSH::debug_fh = $out;
  $Net::OpenSSH::debug = -1;
}

SEGURIDAD

¿Es seguro este módulo?

¿Sí? ¡Bueno, intenta serlo!

Desde un punto de vista de seguridad, el objetivo de este módulo es ser tan seguro como OpenSSH, su sistema operativo, su shell y su entorno en general.

No toma ninguna medida de cortesía solo para hacer su vida más fácil si eso implica disminuir el nivel de seguridad (por ejemplo, desactivar "StrictHostKeyChecking" por defecto).

En las características de código que no son solo proxies a OpenSSH, el módulo intenta mantener los mismos estándares de seguridad que OpenSSH (por ejemplo, verificar permisos de directorios y archivos al colocar el socket de multiplexing).

Por otro lado, siguiendo la filosofía de OpenSSH, el módulo permite desactivar casi todas estas medidas de seguridad. ¡Pero solo porque permite hacerlo, no significa que sea una buena idea hacerlo!

Si es un programador o usuario nuevo de SSH, y al buscar en Google ha encontrado un parámetro que no entiende pero que parece resolver sus problemas de conexión... ¡confíe en mí, es probable que sea una mala idea usarlo! ¡Pida ayuda a alguien que realmente conozca el tema!

Para que quede claro, si su código contiene alguna de las palabras clave de la siguiente lista (y no sabe por qué), probablemente esté comprometiendo la seguridad del protocolo SSH:

strict_mode
StrictHostKeyChecking
UserKnownHostsFile

Otros aspectos de seguridad que podría conocer son:

Modo Taint
El módulo soporta el modo Taint.

Si está en un entorno expuesto, debería habilitar este modo en su script para capturar cualquier comando no validado que se ejecute en el lado remoto.

Entornos Web
Es una mala idea establecer conexiones SSH desde su servidor web porque si se compromete, el atacante podría usar las credenciales de su script para conectarse al host remoto y hacer lo que desee.
Ejecución de Comandos
El módulo puede realizar el quoting de comandos y argumentos de forma flexible y potente.

Esta es una característica que debería usar ya que reduce la posibilidad de que un atacante pueda inyectar y ejecutar comandos arbitrarios en el host remoto (e incluso para scripts no expuestos, siempre es recomendable habilitar el quoting de argumentos).

Sin embargo, tenga en cuenta que el quoting de argumentos es solo un parche para emular la función de invocación sin shell de funciones de Perl como "system" y similares. Podría haber errores en el código de quoting, su shell podría tener reglas de quoting diferentes a las de casos extremos de un problema o cualquier cosa similar. Si su script está expuesto externamente, debería validar sus entradas y limitar lo que acepta como válido.

[* ¡incluso si esta es una parte intensamente probada del módulo!]

Shellshock
(ver Shellshock http://en.wikipedia.org/wiki/Shellshock_%28software_bug%29)

Cuando se ejecutan comandos locales, el módulo siempre evita llamar al shell, por lo que no se ve afectado por Shellshock.

Sin embargo, algunos comandos ("scp", "rsync" y "ssh" cuando se usa la opción "ProxyCommand") invocan otros comandos bajo el shell del usuario. Esto abre la puerta a la explotación de Shellshock local.

La invocación de shell en el lado remoto es inevitable debido a la arquitectura del protocolo.

Por defecto, SSH no envía variables de entorno, pero algunas distribuciones Linux cambian explícitamente la configuración predeterminada de OpenSSH para habilitar el envío y la aceptación de algunas específicas (por ejemplo, "LANG" y "LC_*" en Debian y derivados, y Fedora lo hace así también). Esto también abre la puerta a la explotación de Shellshock.

Tenga en cuenta que el shell utilizado para invocar comandos no es "/bin/sh" sino el shell del usuario configurado en "/etc/passwd", PAM o cualquier sistema de autenticación que se utilice en el sistema local o remoto. Los usuarios de Debian, ¡no se preocupen por estar afectados porque su "/bin/sh" apunta a "dash"!

PREGUNTAS FRECUENTES

Preguntas frecuentes sobre el módulo:

Conexión a conmutadores, enrutadores, etc.
P: No puedo hacer que el método "system", "capture", etc. funcione al conectarme a algún enrutador, conmutador, etc. ¿Qué estoy haciendo mal?

R: A grandes rasgos, el protocolo SSH permite dos modos de operación: modo comando y modo interactivo.

El modo comando está diseñado para ejecutar comandos individuales en el host remoto. Abre un canal SSH entre ambos hosts, solicita al ordenador remoto que ejecute un comando dado y, cuando termina, el canal se cierra. Es lo que obtienes, por ejemplo, cuando ejecutas algo como...

$ ssh my.unix.box cat foo.txt

...y también es la forma en que Net::OpenSSH ejecuta comandos en el host remoto.

El modo interactivo lanza un shell en los hosts remotos con sus flujos stdio redirigidos a los locales para que el usuario pueda interactuar con él de forma transparente.

Algunos dispositivos (como probablemente el que estás utilizando) no ejecutan un shell estándar de propósito general (por ejemplo, "bash", "csh" o "ksh"), sino algún programa personalizado especialmente enfocado y limitado a la tarea de configurar el dispositivo.

Normalmente, el servidor SSH que se ejecuta en estos dispositivos no admite el modo comando. Conecta incondicionalmente el shell restringido a cualquier conexión SSH entrante y espera a que el usuario introduzca comandos a través del flujo stdin redirigido.

La única forma de solucionar esta limitación es hacer que tu script hable con el shell restringido (1-abrir una nueva sesión SSH, 2-esperar el prompt del shell, 3-enviar un comando, 4-leer la salida hasta que vuelvas al prompt del shell, repetir desde 3). La mejor herramienta para esta tarea es probablemente Expect, utilizada sola o combinada con Net::OpenSSH (ver "Expect").

Hay algunos dispositivos que admiten el modo comando pero que solo aceptan un comando por conexión. En esos casos, usar Expect es también probablemente la mejor opción.

Hoy en día, hay un nuevo actor, Net::CLI::Interact, que puede ser más adecuado que Expect, y Net::Appliance::Session para trabajar específicamente con dispositivos de red.

Falla la conexión
P: No puedo hacer que el módulo se conecte al host remoto...

R: ¿Has leído la sección de solución de problemas? (ver "TROUBLESHOOTING").

Deshabilitar StrictHostKeyChecking
P: ¿Por qué "ssh" no se ejecuta con "StrictHostKeyChecking=no"?

R: Usar "StrictHostKeyChecking=no" relaja el nivel de seguridad por defecto de SSH y será relativamente fácil terminar con una configuración SSH incorrecta (por ejemplo, cuando "known_hosts" no es escribible) que podría ser falsificada para conectarse a un host incorrecto para realizar ataques de intermediario (man-in-the-middle), etc.

Te aconsejo que no uses esa opción a menos que entiendas completamente sus implicaciones desde el punto de vista de la seguridad.

Si aun así quieres usarla, pásala al constructor:

$ssh = Net::OpenSSH->new($host,
         master_opts => [-o => "StrictHostKeyChecking=no"],
         ...);
El proceso hijo STDIN/STDOUT/STDERR no es un manejador de archivos real del sistema
P: Las llamadas a "system", "capture", etc. fallan con el error anterior, ¿qué está pasando?

R: El flujo stdio reportado está cerrado o no está adjunto a un manejador de archivos real (por ejemplo, es un manejador enlazado). Redirigirlo a "/dev/null" o a un archivo real:

my $out = $ssh->capture({stdin_discard => 1, stderr_to_stdout => 1},
                        $cmd);

Ver también la entrada mod_perl anterior.

Solaris (y AIX y probablemente otros)
P: Estaba probando Net::OpenSSH en Solaris y parece que me encuentro con un problema...

R: El cliente SSH incluido con Solaris es una bifurcación temprana de OpenSSH que no proporciona la funcionalidad de multiplexación requerida por Net::OpenSSH. Deberás instalar el cliente OpenSSH.

Hay paquetes precompilados disponibles en Sun Freeware (http://www.sunfreeware.com). Allí, selecciona tu versión de SO y arquitectura de CPU, descarga el paquete OpenSSH y sus dependencias e instálalos. Ten en cuenta que **no** necesitas configurar Solaris para usar el servidor OpenSSH "sshd".

Asegúrate de que el cliente OpenSSH esté en tu ruta antes que el "ssh" del sistema o, alternativamente, puedes codificar la ruta completa en tus scripts de la siguiente manera:

$ssh = Net::OpenSSH->new($host,
                         ssh_cmd => '/usr/local/bin/ssh');

AIX y probablemente otros sistemas Unix también incluyen clientes SSH que carecen de la funcionalidad de multiplexación y requieren la instalación del OpenSSH real.

No se puede cambiar el directorio de trabajo
P: Quiero ejecutar un comando dentro de un directorio remoto dado, pero no puedo cambiar el directorio de trabajo. Por ejemplo: 
$ssh->system('cd /home/foo/bin');
$ssh->systen('ls');

no lista el contenido de "/home/foo/bin".

¿Qué estoy haciendo mal?

R: Net::OpenSSH (y, de hecho, todos los módulos SSH disponibles en CPAN excepto Net::SSH::Expect) ejecutan cada comando en una nueva sesión, por lo que la mayoría de los comandos integrados del shell que se ejecutan por sus efectos secundarios se vuelven inútiles (por ejemplo, "cd", "export", "ulimit", "umask", etc., normalmente, puedes listarlos ejecutando "help" desde el shell).

Una solución es combinar varios comandos en uno, por ejemplo:

$ssh->system('cd /home/foo/bin && ls');

Nota el uso del operador del shell "&&" en lugar de ";" para abortar el comando tan pronto como alguno de los subcomandos falle.

Además, se pueden combinar varios comandos en uno mientras se sigue utilizando la característica de cita de varios argumentos de la siguiente manera:

$ssh->system(@cmd1, \\'&&', @cmd2, \\'&&', @cmd3, ...);
Ejecución de procesos remotos desvinculados
P: Necesito poder conectarme por ssh a varias máquinas desde mi script, lanzar un proceso para que se ejecute en segundo plano allí y luego regresar inmediatamente mientras los programas remotos siguen ejecutándose...

R: Si los sistemas remotos ejecutan alguna variante de Unix/Linux, el enfoque correcto es usar nohup(1), que desconectará el proceso remoto de los flujos stdio y solicitará al shell que ejecute el comando en segundo plano. Por ejemplo:

$ssh->system("nohup $long_running_command &");

Además, puede ser posible demonizar el programa remoto. Si está escrito en Perl puedes usar App::Daemon para ello (de hecho, hay varios módulos CPAN que proporcionan este tipo de funcionalidad).

En cualquier caso, ten en cuenta que no deberías usar "spawn" para esto.

Se alcanzó el límite del servidor MaxSessions
P: Creé un objeto $ssh y luego generé muchos procesos hijos que usan este objeto. Cuando el número de hijos es mayor que "MaxSessions" como se define en la configuración de sshd (por defecto es 10), al intentar generar nuevos comandos remotos se le pedirá al usuario la contraseña.

R: Cuando el cliente SSH esclavo recibe una respuesta de los servidores remotos indicando que se ha alcanzado el número máximo de sesiones para la conexión actual, recurre a abrir una nueva conexión directa sin pasar por el socket de multiplexación.

Para evitar que esto suceda, se puede utilizar el siguiente hack:

$ssh = Net::OpenSSH->new(host,
    default_ssh_opts => ['-oConnectionAttempts=0'],
    ...);
Ejecución de comandos remotos con sudo
P: ¿Cómo puedo ejecutar comandos remotos usando "sudo" para convertirme primero en root?

R: La forma más sencilla es indicar a "sudo" que lea la contraseña desde stdin con la opción "-S" y que no use credenciales cacheadas con la opción "-k". También te puede gustar usar la opción "-p" para indicar a "sudo" que muestre un prompt vacío. Por ejemplo:

my @out = $ssh->capture({ stdin_data => "$sudo_passwd\n" },
                        'sudo', '-Sk',
                        '-p', '',
                        '--',
                        @cmd);

Si la versión de sudo instalada en el host remoto no admite la opción "-S" (que le indica a sudo que lea la contraseña desde su flujo STDIN), puedes hacerlo de la siguiente manera:

my @out = $ssh->capture({ tty => 1,
                          stdin_data => "$sudo_passwd\n" },
                        'sudo', '-k',
                        '-p', '',
                        '--',
                        @cmd);

Esto puede generar una advertencia espuria e inofensiva de la conexión maestra SSH (porque estamos solicitando la asignación de un tty en el lado remoto y localmente lo estamos adjuntando a un par de pipes regular).

Si por alguna razón los métodos descritos anteriormente fallan, siempre puedes recurrir a usar Expect para hablar con el "sudo" remoto. Consulta el script "examples/expect.pl" de la distribución de este módulo.

NAME

Net::OpenSSH::Protocol::Packet - SSH Protocol Packet Handling

SYNOPSIS

use Net::OpenSSH::Protocol::Packet;

DESCRIPTION

This module implements the SSH packet handling, encryption and decryption. It is a low-level component of the Net::OpenSSH module, and is not intended for direct use by end-users.

It handles the framing of data into SSH packets, including length and padding, and interfaces with the encryption modules to encrypt and decrypt packet contents.

API

The API is internal and not documented here. Consult the source code for details.

3rd PARTY MODULE INTEGRATION

This module relies on other modules for encryption (e.g., Crypt::OpenSSL::AES) and might need specific versions or configurations for optimal compatibility.

TROUBLESHOOTING

Issues related to packet handling, such as incorrect padding or encryption/decryption errors, may indicate problems with this module or its dependencies.

DEBUGGING

Debugging this module typically involves inspecting packet contents before and after encryption/decryption. Use of Net::OpenSSH's own debugging flags might provide insights.

SECURITY

This module is critical for the security of the SSH connection. Any vulnerabilities or flaws in its implementation could compromise the entire communication channel. It relies heavily on the security of the underlying cryptographic libraries.

FAQ

Q: Why is my SSH connection failing with packet errors?

A: This could be due to incorrect packet framing, issues with the encryption/decryption process, or network problems interfering with packet integrity. Check debugging output and ensure all dependencies are correctly installed.
