NOMBRE

Net::Server::PreFork - Personalidad de Net::Server

SINOPSIS

use base qw(Net::Server::PreFork);
sub process_request {
    #...código...
}
__PACKAGE__->run();

DESCRIPCIÓN

Por favor, lee primero la documentación de Net::Server y Net::Server::PreForkSimple. Este módulo es una personalidad, o extensión, o subclase de la clase Net::Server::PreForkSimple, que a su vez es una subclase de Net::Server. Ver Net::Server::PreForkSimple.

Esta personalidad se enlaza a uno o más puertos y luego crea "min_servers" procesos hijos. El servidor se asegurará de que en cualquier momento haya "min_spare_servers" disponibles para recibir una solicitud de cliente, hasta un máximo de "max_servers". Cada uno de estos hijos procesará hasta "max_requests" conexiones de clientes. Este tipo es bueno para un sitio con mucho tráfico y debería escalar bien para la mayoría de las aplicaciones. (La aceptación de múltiples puertos se logra utilizando flock para serializar los hijos).

En este momento, no parece que este módulo pase las pruebas en sistemas Win32. Cualquier idea o parche para hacer pasar las pruebas sería bienvenido.

ARGUMENTOS DE LÍNEA DE COMANDOS

Además de los argumentos de línea de comandos de la clase base Net::Server y la clase padre Net::Server::PreForkSimple, Net::Server::PreFork contiene varios parámetros configurables adicionales. Realmente deberías ver también Net::Server::PreForkSimple.

Clave                 Valor                   Por defecto
min_servers         \d+                     5
min_spare_servers   \d+                     2
max_spare_servers   \d+                     10
max_servers         \d+                     50
max_requests        \d+                     1000
serialize           (flock|semaphore
                     |pipe|none)            undef
# serialize por defecto es flock en multi_port o en Solaris
lock_file           "nombre_archivo"              File::Temp->new
check_for_dead      \d+                     30
check_for_waiting   \d+                     10
max_dequeue         \d+                     undef
check_for_dequeue   \d+                     undef
child_communication 1                       undef
min_servers
El número mínimo de servidores a mantener en ejecución.
min_spare_servers
El número mínimo de servidores a tener esperando solicitudes. Los números mínimo y máximo no deben estar muy juntos o el servidor creará y matará hijos con demasiada frecuencia.
max_spare_servers
El número máximo de servidores a tener esperando solicitudes. Ver min_spare_servers.
max_servers
El número máximo de servidores hijos a iniciar. Esto no se aplica a los procesos de dequeue.
check_for_waiting
Segundos a esperar antes de comprobar si podemos eliminar algunos servidores en espera.
check_for_spawn
Segundos entre comprobaciones para ver si necesitamos crear más hijos
min_child_ttl
Número mínimo de segundos entre el inicio de hijos y la finalización de un proceso hijo
child_communication
Habilita la comunicación entre hijos y el padre a través de sockets unix. Si se establece en verdadero, permitirá que los hijos escriban en el socket contenido en $self->{'server'}->{'parent_sock'}. El padre será notificado a través de child_is_talking_hook, donde el primer argumento es el socket al hijo. El socket del hijo se almacena en $self->{'server'}->{'children'}->{$child_pid}->{'sock'}.
serialize
Ver la documentación bajo Net::Server::PreForkSimple.

ARCHIVO DE CONFIGURACIÓN

"Net::Server::PreFork" permite el uso de un archivo de configuración para leer parámetros del servidor. El formato de este archivo de configuración son simples pares clave-valor. Los comentarios y los espacios en blanco se ignoran.

#-------------- archivo test.conf --------------
### información del servidor
min_servers   20
max_servers   80
min_spare_servers 10
min_spare_servers 15
max_requests  1000
### usuario y grupo al que convertirse
user        alguien
group       todos
### ¿registro?
log_file    /var/log/servidor.log
log_level   3
pid_file    /tmp/servidor.pid
### control de acceso
allow       .+\.(net|com)
allow       dominio\.com
deny        a.+
### ¿ejecutar el proceso en segundo plano?
background  1
### puertos a enlazar
host        127.0.0.1
port        localhost:20204
port        20205
### ¿búsquedas inversas?
# reverse_lookups on
### ¿habilitar comunicación entre hijos?
# child_communication
#-------------- archivo test.conf --------------

FLUJO DE PROCESOS

El flujo de procesos sigue a Net::Server hasta la fase de bucle. En este punto, se crean "min_servers" y esperan conexiones. Cuando un hijo acepta una conexión, termina de procesar un cliente o sale, transmite esa información al padre, que la rastrea y se asegura de que haya suficientes hijos para cumplir con "min_servers", "min_spare_servers", "max_spare_servers" y "max_servers".

HOOKS

El servidor PreFork tiene los siguientes hooks además de los hooks proporcionados por PreForkSimple. Ver Net::Server::PreForkSimple.

"$self->run_n_children_hook()"
Este hook ocurre al principio de run_n_children, que se llama cada vez que el servidor va a iniciar más procesos hijos. Esto le da al padre la oportunidad de hacer su propia contabilidad (según sea deseado). La idea para este hook provino de James FitzGibbon.
"$self->parent_read_hook()"
Este hook ocurre cada vez que el padre lee información del hijo. La línea del hijo se envía como argumento.
"$self->child_is_talking_hook()"
Este hook ocurre si child_communication es verdadero y el hijo ha escrito en $self->{'server'}->{'parent_sock'}. El primer argumento será el socket abierto al hijo.
"$self->idle_loop_hook()"
Este hook se llama en cada pasada a través del bucle de espera del proceso principal, cada "check_for_waiting" segundos. El primer argumento es una referencia a un array de descriptores de archivo que se pueden leer en ese momento.
"$self->cleanup_dead_child_hook( $child )"
Este hook se llama cuando se detecta un hijo muerto. Se considera que un hijo está muerto cuando el pid ya no existe. Este hook podría usarse para limpiar posibles archivos temporales o bloqueos dejados por un hijo muerto.

DESPLIEGUE EN CALIENTE

Desde la versión 2.000, el servidor PreFork ha aceptado las señales TTIN y TTOU. Cuando se recibe una TTIN, min y max_servers se incrementan en 1. Si se recibe una señal TTOU, min y max_servers se decrementan en 1. Esto permite ajustar el número de procesos de manejo sin tener que reiniciar el servidor.

ERRORES

Las pruebas no parecen funcionar en Win32. Cualquier idea o parche sería bienvenido.
