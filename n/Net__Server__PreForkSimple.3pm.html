NOMBRE

Net::Server::PreForkSimple - Personalidad de Net::Server

SINOPSIS

use base qw(Net::Server::PreForkSimple);
sub process_request {
    #...código...
}
__PACKAGE__->run();

DESCRIPCIÓN

Por favor, lee primero el pod de Net::Server. Este módulo es una personalidad, o extensión, o subclase del módulo Net::Server.

Esta personalidad se vincula a uno o más puertos y luego crea "max_servers" procesos hijos. El servidor se asegurará de que en cualquier momento haya siempre "max_servers" disponibles para recibir una solicitud de cliente. Cada uno de estos hijos procesará hasta "max_requests" conexiones de cliente. Este tipo es bueno para un sitio con mucho tráfico que pueda mantener "max_servers" procesos dedicados a servir. (La aceptación de múltiples puertos utiliza flock por defecto para serializar los hijos).

Por el momento, no parece que este módulo pase las pruebas en sistemas Win32. Cualquier idea o parche para hacer pasar las pruebas sería bienvenido.

ARGUMENTOS DE LÍNEA DE COMANDOS

Además de los argumentos de línea de comandos de la clase base Net::Server, Net::Server::PreFork contiene varios parámetros configurables adicionales.

Clave               Valor                   Por defecto
max_servers       \d+                     50
max_requests      \d+                     1000
serialize         (flock|semaphore
                   |pipe|none)  undef
# serialize por defecto es flock en multi_port o en Solaris
lock_file         "nombre_archivo"              File::Temp->new
check_for_dead    \d+                     30
max_dequeue       \d+                     undef
check_for_dequeue \d+                     undef
max_servers
El número máximo de servidores hijos a iniciar y mantener. Esto no se aplica a los procesos de dequeue.
max_requests
El número de conexiones de cliente a recibir antes de que un hijo termine.
serialize
Determina si el servidor serializa las conexiones de los hijos. Las opciones son undef, flock, semaphore, pipe, o none. El valor por defecto es undef. En servidores multi_port o en servidores que se ejecutan en Solaris, el valor por defecto es flock. La opción flock utiliza un flock exclusivo bloqueante en el archivo especificado en lock_file (ver más abajo). La opción semaphore utiliza IPC::Semaphore (gracias a Bennett Todd) para proporcionar algún código de ejemplo. La opción pipe lee en una tubería para elegir la siguiente. La opción flock debería ser la más robusta, mientras que la opción pipe debería ser la más portable. (Flock puede liberar el bloqueo si el proceso muere entre la aceptación en el socket y la lectura de la conexión del cliente; semaphore y pipe no). Una opción de none no realizará ninguna serialización. Si se pasa "none" y hay múltiples puertos, se utilizará la serialización por defecto en lugar de "none."
lock_file
Nombre de archivo a utilizar en la aceptación serializada con flock para serializar la secuencia de aceptación entre los hijos. Por defecto será un nombre de archivo temporal generado. Si se utiliza el valor por defecto, el archivo de bloqueo se eliminará cuando el servidor se cierre.
check_for_dead
Segundos a esperar antes de comprobar si un hijo murió sin informar al padre.
max_dequeue
El número máximo de procesos de dequeue a iniciar. Si se proporciona un valor de cero o undef, no se iniciarán procesos de dequeue. El número de procesos de dequeue en ejecución será verificado por la variable check_for_dead.
check_for_dequeue
Segundos a esperar antes de crear un proceso de dequeue. El hook run_dequeue debe definirse cuando se utiliza esta configuración. Está destinado a utilizar el proceso de dequeue para encargarse de elementos como colas de correo. Si se proporciona un valor undef, no se iniciarán procesos de dequeue.

ARCHIVO DE CONFIGURACIÓN

"Net::Server::PreFork" permite el uso de un archivo de configuración para leer los parámetros del servidor. El formato de este archivo de configuración es simple: pares clave-valor. Los comentarios y los espacios en blanco se ignoran.

#-------------- archivo test.conf --------------
### información del servidor
max_servers   80
max_requests  1000
### usuario y grupo al que convertirse
user        alguien
group       todos
### ¿registro?
log_file    /var/log/server.log
log_level   3
pid_file    /tmp/server.pid
### control de acceso
allow       .+\.(net|com)
allow       domain\.com
deny        a.+
### ¿poner el proceso en segundo plano?
background  1
### puertos a vincular
host        127.0.0.1
port        localhost:20204
port        20205
### ¿búsquedas inversas?
# reverse_lookups on
#-------------- archivo test.conf --------------

FLUJO DEL PROCESO

El flujo del proceso sigue a Net::Server hasta la fase de bucle. En este punto, se crean "max_servers" hijos que esperan conexiones. Cuando un hijo acepta una conexión, termina de procesar un cliente o sale, retransmite esa información al padre, que lleva la cuenta y se asegura de que siempre haya "max_servers" en ejecución.

HOOKS

El servidor PreForkSimple tiene los siguientes hooks además de los hooks proporcionados por la clase base Net::Server. Ver Net::Server

"$self->run_n_children_hook()"
Este hook ocurre al principio de run_n_children, que se llama cada vez que el servidor va a iniciar más procesos hijos. Esto permite al padre realizar parte de su propia contabilidad (según se desee). La idea para este hook provino de James FitzGibbon.
"$self->child_init_hook()"
Este hook se realiza inmediatamente después de que el proceso hijo se separa del padre y antes de que el hijo comience a aceptar conexiones. Está destinado a medidas de seguridad adicionales u otras medidas de seguridad. Se sugiere que todos los módulos perl se hayan utilizado en este punto, para que se utilice la mayor cantidad posible de memoria compartida.
"$self->child_finish_hook()"
Este hook se realiza inmediatamente antes de que el hijo informe al padre que está saliendo. Está destinado a guardar información registrada u otra limpieza general.
"$self->run_dequeue()"
Este hook solo se llama junto con la configuración check_for_dequeue.
"$self->idle_loop_hook()"
Este hook se llama en cada pasada por el bucle principal de espera del proceso.

DESPLIEGUE EN CALIENTE

Desde la versión 2.000, el servidor PreForkSimple ha aceptado las señales TTIN y TTOU. Cuando se recibe una TTIN, max_servers se incrementa en 1. Si se recibe una señal TTOU, max_servers se decrementa en 1. Esto permite ajustar el número de procesos de manejo sin tener que reiniciar el servidor.

ERRORES

Las pruebas no parecen funcionar en Win32. Cualquier idea o parche sería bienvenido.
