Net::DNS::SEC::Tools::Donuts::Rule(3) Documentación de Perl contribuida por el usuario Net::DNS::SEC::Tools::Donuts::Rule(3)

NOMBRE

Net::DNS::SEC::Tools::Donuts::Rule - Define reglas de verificación de registros DNS de donuts

DESCRIPCIÓN

Esta clase encapsula la definición de una regla que es utilizada por el verificador de archivos de zona DNS donuts. Almacena los datos que implementan una regla dada.

Las reglas se definen en archivos de configuración de reglas de donuts usando la siguiente sintaxis. Consulte la página del manual de donuts para obtener detalles sobre dónde colocar esos archivos y cómo cargarlos.

FORMATO DEL ARCHIVO DE REGLAS

Cada archivo de reglas puede contener múltiples reglas. Cada regla se compone de un número de partes. Como mínimo, debe contener una parte de nombre y una de prueba. Todo lo demás es opcional y/o tiene valores predeterminados asociados. El formato del archivo de reglas sigue este ejemplo:

nombre: nombre_regla
clase: Advertencia
<prueba>
  my ($registro) = @_;
  return "problema encontrado"
    if ($registro{xxx} != yyy);
</prueba>

Más detalles sobre cada sección se pueden encontrar a continuación. Además de los tokens a continuación, se pueden almacenar otros datos específicos de la regla en tokens y cada regla es un hash de los tokens anteriores como claves y sus datos asociados. Sin embargo, hay algunas excepciones donde tokens especiales implican significados especiales. Estos tokens especiales incluyen prueba e init. Ver abajo para más detalles.

Cada definición de regla dentro de un archivo debe separarse mediante una línea en blanco.

Las líneas que comienzan con el carácter '#' se descartarán como comentarios.

nombre
El nombre de la regla. Esto es obligatorio, ya que el usuario puede necesitar referirse a nombres en el futuro para usarlos con la opción -i, especificar el comportamiento en archivos de configuración y para otros usos.

Por convención, todos los nombres deben especificarse en letras mayúsculas y usando '_' entre las palabras. La palabra más a la izquierda debe indicar una categoría global de prueba, como "DNSSEC". Cuanto mejor nombradas estén las reglas, más poder tendrá el usuario para seleccionar ciertos tipos de reglas a través de donuts -i y otras opciones.

Ejemplo:

nombre: DNSSEC_TEST_ALGUNA_CARACTERISTICA_SEGURA
nivel
El nivel de ejecución de la regla, tal como lo reconoce donuts. donuts ejecutará solo aquellas reglas en o por encima del nivel de ejecución actual de donuts. El nivel de ejecución se especifica con la opción -l de donuts; si no se proporciona, el nivel de ejecución predeterminado es 5.

El nivel predeterminado de cada regla es 5.

En general, los problemas más serios deben recibir números más bajos y los problemas menos serios deben colocarse en un número más alto. El valor máximo es 9, que está reservado solo para reglas de depuración. 8 es el nivel máximo de regla que deben usar las reglas definidas por el usuario.

Ejemplo:

nombre: DNSSEC_TEST_ALGUNA_CARACTERISTICA_SEGURA
nivel: 2
clase
El código de clase indica el tipo de problema asociado con la regla. Por defecto es "Error", y el único otro valor que debe usarse es "Advertencia".

Este valor se muestra al usuario. Técnicamente, se podría especificar cualquier valor, pero usar algo diferente a la convención Error/Advertencia podría romper la portabilidad en versiones futuras.

Ejemplo:
nombre: DNSSEC_TEST_ALGUNA_CARACTERISTICA_SEGURA
clase: Advertencia

tiporegla
Las reglas entran en uno de dos tipos (actualmente): registro o nombre. Las reglas de registro tienen su sección de prueba evaluada para cada registro en un archivo de zona. Las reglas de nombre, por otro lado, se llaman una vez por cada nombre de registro almacenado en la base de datos. Consulte la descripción de prueba a continuación para obtener más detalles sobre los argumentos pasados a cada tipo de regla.

El valor predeterminado para esta cláusula es registro.

Ejemplo:

nombre: DNSSEC_TEST_ALGUNA_CARACTERISTICA_SEGURA
tiporegla: registro
tipo
Las reglas que prueban un tipo particular de registro deben especificar el campo tipo con el tipo de registro que probarán. La regla solo se ejecutará para registros de ese tipo.

Por ejemplo, si una regla está probando un aspecto particular de un registro MX, debería especificar "MX" en este campo.

Ejemplo:

nombre: DNSSEC_TEST_ALGUNA_CARACTERISTICA_SEGURA
tipo: MX
init
Un bloque de código para ser ejecutado inmediatamente a medida que la regla se analiza desde el archivo de definición de reglas. Esto es útil para el código de arranque que se realizará solo al inicio. Por ejemplo, las instrucciones perl "use MODULE::NAME;" o similares deben usarse en las secciones init.

Las secciones init están envueltas en una sintaxis similar a XML que especifica el inicio y el final de la sección de código init.

Ejemplo:

<init>
  use Mi::Modulo;
  $valor = calcular();
</init>
prueba
Un bloque de código que define la prueba a ejecutar para cada registro o nombre de registro. La declaración de prueba sigue la misma especificación de código multilínea descrita en la cláusula init anterior. Específicamente, todas las líneas entre las llaves <prueba> y </prueba> se consideran parte del código de prueba.

El contenido de la prueba debe ser un bloque de código perl. Si no está en forma de una subrutina anónima (rodeada por los marcadores "sub {" y "}"), el código se colocará automáticamente dentro de un bloque de subrutina básico para convertirlo en una subrutina anónima.

POR EJEMPLO, el código resultante para una prueba de registro se verá así:

package main;
no strict;
sub
{
  my ($registro, $regla) = @_;  
  CODIGO_PRUEBA
}

Y para una prueba de nombre será:

package main;
no strict;
sub
{
  my ($registros, $regla, $nombrederegistro) = @_;  
  CODIGO_PRUEBA
}

(Nuevamente, esta estructura solo se crea si la definición de prueba no comienza ya con "sub {")

Cuando se ejecuta el código de prueba y la prueba falla, debe devolver una cadena de error que se mostrará al usuario. El texto se ajustará automáticamente antes de mostrarse (y por lo tanto, debe ser texto sin formato). Si la prueba está verificando múltiples problemas, se puede devolver una referencia a un array de cadenas de error. Un bloque de prueba que no tenga errores que informar debe devolver una cadena vacía o una referencia a un array vacío.

Hay dos tipos de pruebas (actualmente), y el código de prueba se llama con argumentos que dependen de la cláusula tiporegla de la regla. Estos argumentos y convenciones de llamada son los siguientes:

pruebas de registro
Se espera que estos fragmentos de código prueben un único registro Net::DNS::RR.

Se llama con dos argumentos:

1) $registro: El registro que se va a probar
2) $regla: La referencia al objeto Net::DNS::SEC::Tools::Donuts::Rule y la
   información de definición de la regla.

Estos se enlazan automáticamente a $registro y $regla para que el código de prueba los use.

pruebas de nombre
Se espera que estos fragmentos de código prueben todos los registros asociados con un nombre de registro dado.

Se llama con tres argumentos:

1) $registros: Una referencia hash a todos los tipos de registro asociados
   con ese nombre de registro (por ejemplo, 'ejemplo.com' puede tener una
   referencia hash que contiene una entrada para 'A', 'MX', ...). Cada valor
   del hash contendrá un array con todos los registros de ese tipo (por
   ejemplo, la entrada hash para la clave 'A' puede contener un array con 2
   registros Net::DNS::RR, uno por cada registro A adjunto a la entrada
   'ejemplo.com').
2) $regla: La referencia al objeto Net::DNS::SEC::Tools::Donuts::Rule y la
   información de definición de la regla.
3) $nombrederegistro: El nombre del registro que se está comprobando (el
   nombre asociado con los datos de 1) anterior, que podría ser, por ejemplo,
   "ejemplo.com" o "www.ejemplo.com").

Estos se enlazan a $registros

RULE FILE FORMAT

Rules files contain a series of rule definitions. Each rule definition is a set of key/value pairs. The standard keys are:

name: RULE_NAME
This is the name of the rule. It should be unique amongst all rules. The name is used to enable/disable rules from the command line and also used in the help output.
level: NUMBER
This is the level of the rule. It is an integer between 1 and 10. Higher numbers indicate more important rules. This is used to control how verbose the output is.
type: TYPE
This specifies the type of rule. The current rule types are:
record
name
zone
type: record
The rule is applied to each individual DNS record found in the zone file. The test code is given a reference to the record in the variable $record. In addition, the entire hash of records for the name is passed in the variable $records and the name itself is passed in the variable $recordname. The zone is passed in the variable $zone.
type: name
The rule is applied to each unique name found in the zone file. The test code is given a reference to the hash of records for that name in the variable $records. The name itself is passed in the variable $recordname. The zone is passed in the variable $zone.
type: zone
The rule is applied once per zone. The test code is given the zone in the variable $zone and a hash of all records in the zone in the variable $records. The keys of the hash are the names, and the values are the hashes of records for that name.
<test>
This marks the beginning of the test code for the rule. The code is written in Perl. The code block is terminated by the </test> tag.
feature: NAME
The feature tag prevents this rule from running unless the NAME keyword was specified using the --features flag.
desc: DESCRIPTION
A short description of what the rule tests that will be printed to the user in help output or in the error summary when donuts outputs the results.
requires: PERLMODULE1 PERLMODULE2 ...
This allows rules to depend on installed perl modules. They'll be required and imported as the rule starts executing. If they don't exist, an error will be logged using donuts_error() stating that the module is required for that rule to work.
help: TOKEN: TOKEN-HELP
If the rule is configurable via the user's .donuts.conf file, this describes the configuration tokens for the user when they request configuration help via the -H or --help-config flags. Tokens may be used within rules by accessing them using the $rule reference passed to the code (the second argument).

Examples:

1) In the rule file (this is an incomplete rule definition):
   name:           SOME_TEST
   myconfig:       40
   help: myconfig: A special number to configure this test
   <test>
    # ... use $rule->{'myconfig'}
   </test>
2) This allows the user to change the value of myconfig via their
   .donuts.conf file:
   # change SOME_TEST config...
   name:     SOME_TEST
   myconfig: 40
3) and running donuts -H will show the help line for myconfig.
noindent: 1
nowrap: 1
Normally donuts will line-wrap the error summary produced by a rule to enable automatic pretty-printing of error results. Sometimes, however, rules may wish to self-format their outputs. The nowrap option indicates to donuts that the output is pre-formatted but should still be indented to align with the output of the rest of the error text (currently about 15 spaces.) The noindent tag, however, indicates that neither wrapping nor indenting should be performed, but that the error should be printed as is.

The test code can return a string which will be printed to the user as an error message. If the test code returns false, no error is generated. If the test code returns true, no error is generated.

The variables $rule and $recordname are automatically populated with the current rule name and the current record name, respectively, for the test code to use.

Example rules:

# local rule to mandate that each record must have a
# TTL > 60 seconds
name: DNS_TTL_AT_LEAST_60
level: 8
type: record
<test>
  return "TTL for $record->{name} is too small" if ($record->ttl < 60);
</test>
# local policy rule to mandate that anything with an A record
# must have an HINFO record too
name: DNS_MX_MUST_HAVE_A
level: 8
type: name
<test>
  return "$recordname has an A record but does not have an HINFO record"
    if (exists($records->{'A'}) && !exists($records->{'HINFO'}));
</test>
