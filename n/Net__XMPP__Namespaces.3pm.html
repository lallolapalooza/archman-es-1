NOMBRE

Net::XMPP::Namespaces - Discusión profunda sobre cómo se manejan los espacios de nombres

SINOPSIS

Net::XMPP::Namespaces proporciona una mirada en profundidad a cómo Net::XMPP maneja los espacios de nombres y cómo añadir los propios. También sirve como contenedor de almacenamiento para toda la información de espacios de nombres que Net::XMPP requiere.

DESCRIPCIÓN

XMPP como protocolo está muy bien definido. Hay tres paquetes principales de nivel superior (message, iq, y presence). También hay una forma de extender el protocolo de una manera muy clara y estructurada, a través de espacios de nombres.

Dos formas principales en que los espacios de nombres se utilizan en Jabber son para hacer que el <iq/> sea un contenedor genérico, y como una forma de añadir datos a cualquier paquete a través de una etiqueta hija <x/>. Usaremos <x/> para representar el paquete, pero en realidad podría ser cualquier etiqueta hija: <foo/>, <data/>, <error/>, etc.

El paquete Info/Query <iq/> utiliza espacios de nombres para determinar el tipo de información a la que acceder. Normalmente hay una etiqueta <query/> en el <iq/> que representa el espacio de nombres, pero de hecho puede ser cualquier etiqueta. La definición de la parte Query es la primera etiqueta que tiene un espacio de nombres.

<iq type="get"><query xmlns="..."/></iq>

o

<iq type="get"><foo xmlns="..."/></iq>

Después de esa estrofa de Consulta, puede haber cualquier número de otras estrofas (<x/> etiquetas) que desee incluir. El paquete Query se representa y está disponible llamando a GetQuery() o GetChild(), y los otros espacios de nombres están disponibles llamando a GetChild().

La etiqueta X es solo una forma de adjuntar datos a otros paquetes. Como incrustar la marca de tiempo para un mensaje usando jabber:x:delay, o firmar tu presencia para cifrado usando jabber:x:signed.

Para ello, Net::XMPP ha buscado encontrar una forma de definir fácil y claramente las funciones necesarias para acceder al XML de un espacio de nombres. Repasaremos la documentación completa y luego mostraremos dos ejemplos de espacios de nombres reales para que pueda ver a qué nos referimos.

Resumen

Para evitar que muchos módulos desagradables ocupen memoria que no se utilizan, y para evitar tener que cambiar 15 módulos cuando se introduce un cambio menor, los módulos Net::XMPP han llevado AUTOLOAD a extremos. Namespaces.pm no es más que un conjunto de llamadas a funciones que genera un gran hash de hashes. El hash es accedido por la función AUTOLOAD de Stanza.pm para hacer algo. (Esto tendrá sentido, lo prometo).

Antes de continuar, sugiero encarecidamente que lea un libro de Perl sobre AUTOLOAD y cómo funciona. A partir de este momento asumiré que lo entiende.

Cuando crea un objeto Net::XMPP::IQ y le añade una consulta (NewChild), varias cosas suceden en segundo plano. El argumento de NewChild es el espacio de nombres que desea añadir. (custom-namespace)

Ahora que tiene un objeto Query con el que trabajar, llamará a las funciones GetXXX y SetXXX para establecer los datos. No hay funciones GetXXX y SetXXXX definidas. No puede buscar en el archivo Namespaces.pm y encontrarlas. En su lugar, encontrará algo como esto:

&add_ns(ns    => "mynamespace",
        tag   => "mytag",
        xpath => {
                  JID       => { type=>'jid', path => '@jid' },
                  Username  => { path => 'username/text()' },
                  Test      => { type => 'master' }
                 }
       );

Cuando se llama a la función GetUsername(), la función AUTOLOAD busca en el hash de Namespaces.pm una clave "Username". Basándose en el "type" del campo (scalar siendo el predeterminado), utilizará el "path" como un XPath para recuperar los datos y llamar al método XPathGet() en Stanza.pm.

¿Confundido todavía?

Espacios de nombres privados de Net::XMPP

Aquí es donde esto empieza a ser un poco complicado. Cuando ve un espacio de nombres con __netxmpp__, o __netjabber__ de Net::Jabber, al principio, suele ser algo personalizado para Net::XMPP y NO forma parte del protocolo XMPP real.

Hay algunos lugares donde la estructura del XML permite múltiples hijos con el mismo nombre. Los lugares principales donde verá este comportamiento es donde tiene múltiples etiquetas con el mismo nombre y estas tienen hijos debajo de ellas (jabber:iq:roster).

En jabber:iq:roster, la etiqueta <item/> se puede repetir múltiples veces, y es como un mini-espacio de nombres en sí mismo. Para ello, lo tratamos como un espacio de nombres separado y definimos un espacio de nombres __netxmpp__:iq:roster:item para albergarlo. Lo que sucede es esto: en mi código, defino que la etiqueta <item/> es "item" y cualquier cosa con ese nombre de etiqueta debe crear un nuevo objeto Net::XMPP::Stanza con el espacio de nombres __netxmpp__:iq:roster:item, que luego se convierte en un hijo del objeto Stanza jabber:iq:roster. Además, cuando quiera añadir un nuevo elemento a un proyecto jabber:iq:roster, llame a NewQuery con el espacio de nombres privado.

Sé que esto suena complicado. Y si después de leer todo este documento todavía le resulta complicado, envíeme un correo electrónico, haga preguntas y las monitorizaré y ajustaré esta documentación para responder a las preguntas que la gente haga.

add_ns()

Para repetir, aquí hay una llamada de ejemplo a add_ns():

add_ns(ns    => "mynamespace",
        tag   => "mytag",
        xpath => {
                  JID       => { type=>'jid', path => '@jid' },
                  Username  => { path => 'username/text()' },
                  Test      => { type => 'master' }
                 }
       );

ns - Este es el nuevo espacio de nombres que intenta añadir.

tag - Esta es la etiqueta raíz a utilizar para los objetos basados en este espacio de nombres.

xpath - La referencia hash pasada en la llamada a add_ns a cada nombre de entrada le dice a Net::XMPP cómo manejar las llamadas subsiguientes GetXXXX(), SetXXXX(), DefinedXXXX(), RemoveXXXX(), AddXXXX(). Las opciones básicas que puede pasar son:

type - Esto le dice a Stanza cómo manejar la llamada. Los valores posibles son:

         array - El valor a establecer y devuelto es una referencia de
                 array. Por ejemplo, <group/> en jabber:iq:roster.
         child - Esto le dice a Stanza que necesita buscar los hijos con
                 espacio de nombres del estilo __netxmpp__. AddXXX() añade
                 un nuevo hijo, y GetXXX() devolverá un nuevo objeto Stanza
                 que representa el paquete.
         flag - Esto es para elementos hijos que son etiquetas por sí
                mismas: <foo/>. Dado que la presencia de la etiqueta es lo
                importante, y no hay cdata que almacenar, simplemente lo
                llamamos un flag.
         jid - El valor es un Jabber ID. GetXXX() devolverá un objeto
               Net::XMPP::JID a menos que le pase "jid", entonces
               devuelve una cadena.
         master - Las llamadas GetXXX() y SetXXX() devuelven y toman un hash
                  que representa todas las llamadas GetXXX() y SetXXX().
                  Por ejemplo:
                    SetTest(foo=>"bar",
                            bar=>"baz");
                  Se traduce en:
                    SetFoo("bar");
                    SetBar("baz");
                  GetTest() devolvería un hash que contiene lo que contiene
                  el paquete:
                    { foo=>"bar",  bar=>"baz" }
         raw - Esto insertará cualquier XML crudo que especifique directamente
               en el Stanza en el punto donde especifica la ruta.
         scalar - Esto establecerá y obtendrá un valor escalar. Este es el
                  caballo de batalla principal, ya que los atributos y el CDATA
                  se representan mediante un escalar. Esta es la configuración
                  predeterminada si no proporciona una.
         special - El tipo especial es único en que en lugar de una cadena
                   "special", en realidad le da un array:
                     [ "special" , <subtype> ]
                   Esto permite que Net::XMPP pueda manejar la llamada
                   SetXXXX() de manera especial según su elección. En este
                   momento, esto es utilizado principalmente por jabber:iq:time
                   para establecer automáticamente la información de tiempo en el
                   formato correcto, y jabber:iq:version para establecer el
                   sistema operativo de la máquina y añadir la versión de
                   Net::Jabber al paquete de respuesta. Probablemente NO
                   necesitará usar esto, pero quería mencionarlo.
         timestamp - Si llama a SetXXX() pero no le pasa nada,

NAME

Net::XMPP::Namespaces - Handles custom namespaces

SYNOPSIS

  use Net::XMPP::Namespaces;
  my $ns = add_ns(
              ns      => "mynamespace",
              tag     => "mytag",
              xpath   => {
                        JID       => { type=>'jid', path => '@jid' },
                        Username  => { path => 'username/text()' },
                        Test      => { type => 'master' }
                       },
              child   => {
                        ns    => "mynamespace",
                        tag   => "mychildtag",
                        # Other child options
                       },
              calls   => ["Get","Set","Defined","Remove"]
             );

  # Example calls:
  $roster->GetJID();
  $roster->SetJID($jid);
  $roster->DefinedJID();
  $roster->RemoveJID();

  $roster->GetUsername();
  $roster->SetUsername($username);
  $roster->DefinedUsername();
  $roster->RemoveUsername();

  $roster->GetTest(); # Will return the entire XML node
  $roster->SetTest($test_data);
  $roster->DefinedTest();
  $roster->RemoveTest();

  # Example with a child:
  $my_stanza->GetMyChildTag();
  $my_stanza->SetMyChildTag($child_object);
  $my_stanza->DefinedMyChildTag();
  $my_stanza->RemoveMyChildTag();

DESCRIPTION

Net::XMPP allows you to create custom XMPP namespaces that can be used within the XMPP protocol. This is useful for creating custom stanzas or extending existing ones. The core of this functionality is the add_ns() function.

The add_ns() function takes a hash of parameters that define the namespace and how it should be handled by Net::XMPP.

The parameters are as follows:

ns
This is the namespace identifier. It can be a standard XMPP namespace (e.g., jabber:iq:roster) or a custom one (e.g., __netxmpp__:custom:stanza). The double underscore prefix is a convention for custom namespaces.
tag
This is the top-level XML tag name for this namespace. For example, in <iq type='result' from='...' to='...' id='...'><query xmlns='jabber:iq:roster'>...</query></iq>, the tag for the jabber:iq:roster namespace is query.
xpath
This is a hash reference that maps the desired API method names (e.g., JID, Username) to their corresponding XML data locations and types. The keys of this hash will become the base names for your Get/Set/Defined/Remove methods. The values are themselves hash references with the following possible keys:
type
This specifies the data type. The following types are recognized:
jid
Stores and retrieves a JID (Jabber ID) object.
master
Stores and retrieves the raw XML node. This is useful for complex stanzas or when you want to handle the XML parsing yourself.
timestamp
Stores and retrieves a Unix timestamp. If the value is undef or an empty string "", then Net::XMPP will place a timestamp in the xpath location.
path
This is the XPath path to where the data lives. The difference. Now, this is not full XPath due to the nature of how it gets used. Instead of providing a rooted path all the way to the top, it's a relative path ignoring what the parent is. For example, if the "tag" you specified was "foo", and the path is "bar/text()", then the XPath will be rooted in the XML of the <foo/> packet. It will set and get the CDATA from: <foo><bar>xxxxx</bar></foo> For a flag and a child type, just specify the child element. Take a look at the code in this file for more help on what this means. Also, read up on XPath if you don't already know what it is.
child
This is a hash reference that tells Net::XMPP how to handle adding and getting child objects. The keys for the hash are as follows:
ns
The real or custom (__netxmpp__) namesapce to use for this child packet.
skip_xmlns => 1
This tells Net::XMPP not to add an xmlns='' into the XML for the child object.
specify_name => 1
Allows you to call NewChild("ns","tag") and specify the tag to use for the child object. This, IMHO, is BAD XML practice. You should always know what the tag of the child is and use an attribute or CDATA to change the type of the stanza. You do not want to use this.
tag
If you use specify_name, then this is the default tag to use. You do not want to use this.
calls
Array reference telling Net::XMPP what functions to create for this name. For most of the types above you will get Get, Set, Defined, and Remove. For child types you need to decide how you API will look and specify them yourself: ["Get","Defined"] ["Add"] ["Get","Add","Defined"] It all depends on how you want your API to look.

Once more... The following:

  add_ns(ns    => "mynamespace",
          tag   => "mytag",
          xpath => {
                    JID       => { type=>'jid', path => '@jid' },
                    Username  => { path => 'username/text()' },
                    Test      => { type => 'master' }
                   }
         );

generates the following API calls:

  GetJID()
  SetJID()
  DefinedJID()
  RemoveJID()
  GetUsername()
  SetUsername()
  DefinedUsername()
  RemoveUsername()
  GetTest()
  SetTest()

Wrap Up

Well. I hope that I have not scared you off from writing a custom namespace for you application and use Net::XMPP. Look in the Net::XMPP::Protocol manpage for an example on using the add_ns() function to register your custom namespace so that Net::XMPP can properly handle it.
