val set_export_name : t -> string -> unit

NBD.set_export_name t export_name

establecer el nombre de exportación

Algunos servidores NBD pueden servir múltiples imágenes de disco ("exportaciones"). La exportación es elegida por el cliente, solicitando un nombre de exportación durante la fase de negociación. La exportación predeterminada es la cadena vacía "".

Algunos servidores NBD ignoran esto y sirven el mismo contenido independientemente. Esto solo es relevante al conectarse a servidores que utilizan el protocolo newstyle, ya que el protocolo oldstyle no admitía nombres de exportación.

El protocolo NBD limita los nombres de exportación a 4096 bytes, pero los servidores pueden no admitir la longitud completa. La codificación de los nombres de exportación es siempre UTF-8.

Cuando el modo de opciones no está en uso, el nombre de exportación debe establecerse antes de comenzar una conexión. Sin embargo, cuando nbd_set_opt_mode(3) ha habilitado el modo de opciones, es posible cambiar el nombre de exportación antes de nbd_opt_go(3). En particular, el uso de nbd_opt_list(3) durante la negociación se puede utilizar para determinar un nombre que el servidor probablemente acepte, y nbd_opt_info(3) puede usarse para obtener detalles sobre una exportación antes de conectarse.

Esta llamada puede omitirse si se utiliza nbd_connect_uri(3) para conectarse a una URI que incluye un nombre de exportación.

val set_request_block_size : t -> bool -> unit

NBD.set_request_block_size t request

controlar si NBD_OPT_GO solicita el tamaño del bloque

Por defecto, al conectarse a una exportación, libnbd solicita que el servidor informe sobre cualquier restricción de tamaño de bloque. El protocolo NBD establece que un servidor puede proporcionar tamaños de bloque independientemente de si el cliente los solicita o no, y libnbd informará sobre esos tamaños de bloque (ver nbd_get_block_size(3)); por el contrario, si un cliente no solicita tamaños de bloque, el servidor puede rechazar la conexión en lugar de lidiar con un cliente que envía solicitudes desalineadas. Esta función permite probar el comportamiento del servidor emulando clientes más antiguos.

Tenga en cuenta que incluso cuando se solicita el tamaño del bloque, el servidor no está obligado a proporcionar ninguno. Además, si se proporcionan tamaños de bloque (ya sea que el cliente los haya solicitado o no), libnbd impone la alineación a esos tamaños a menos que se utilice nbd_set_strict_mode(3) para omitir las comprobaciones de seguridad del lado del cliente.

NBD.get_request_block_size t

val set_full_info : t -> bool -> unit

NBD.set_full_info t request

controlar si NBD_OPT_GO solicita detalles adicionales

Por defecto, al conectarse a una exportación, libnbd solo solicita los detalles que necesita para atender las operaciones de datos. El protocolo NBD dice que un servidor puede proporcionar información opcional, como un nombre canónico de la exportación (ver nbd_get_canonical_export_name(3)) o una descripción de la exportación (ver nbd_get_export_description(3)), pero que una pista del cliente hace más probable que se proporcione esta información adicional. Esta función controla si libnbd proporcionará esa pista.

Tenga en cuenta que incluso cuando se solicita información completa, el servidor no está obligado a responder con toda la información que libnbd solicitó. De manera similar, libnbd ignorará cualquier información opcional del servidor que libnbd aún no haya aprendido a reconocer. Además, la pista para solicitar tamaños de bloque se controla de forma independiente a través de nbd_set_request_block_size(3).

NBD.get_full_info t

Devuelve el estado del indicador de solicitud de información completa en este manejador.

val get_canonical_export_name : t -> string

NBD.get_canonical_export_name t

devolver el nombre de exportación canónico, si el servidor tiene uno

El protocolo NBD permite que un servidor informe un nombre de exportación canónico opcional, que puede diferir de la solicitud del cliente (como se establece mediante nbd_set_export_name(3) o nbd_connect_uri(3)). Esta función accede a cualquier nombre devuelto por el servidor; puede ser el mismo que la solicitud del cliente, pero es más probable que difiera cuando el cliente solicitó una conexión al nombre de exportación predeterminado (una cadena vacía "").

Es poco probable que algunos servidores informen un nombre canónico a menos que el cliente lo haya indicado específicamente, a través de nbd_set_full_info(3).

NBD.get_export_description t

devolver la descripción de la exportación, si el servidor tiene una

El protocolo NBD permite que un servidor informe una descripción de exportación opcional. Esta función informa cualquier descripción devuelta por el servidor.

Es poco probable que algunos servidores informen una descripción a menos que el cliente la haya indicado específicamente, a través de nbd_set_full_info(3). Para qemu-nbd(8), una descripción se establece con *-D*.

val set_tls : t -> TLS.t -> unit

NBD.set_tls t tls

habilitar o requerir TLS (autenticación y cifrado)

Habilita o requiere TLS (conexiones autenticadas y cifradas) al servidor NBD. La configuración posible es:

"LIBNBD_TLS_DISABLE" Deshabilitar TLS. (La configuración predeterminada, a menos que se utilice nbd_connect_uri(3) con una URI que requiera TLS).

Esta configuración también es necesaria si usa nbd_set_opt_mode(3) y desea interactuar en texto plano con un servidor que implementa el modo "SELECTIVETLS" del protocolo NBD, antes de habilitar TLS con nbd_opt_starttls(3). La mayoría de los servidores NBD con soporte TLS prefieren el modo "FORCEDTLS" del protocolo NBD, por lo que este tipo de interacción manual tiende a ser útil principalmente durante las pruebas de integración.

"LIBNBD_TLS_ALLOW" Habilitar TLS si es posible.

Esta opción es insegura (o de mejor esfuerzo) ya que en algunos casos recurrirá a una conexión sin cifrar y/o sin autenticar si no se pudo establecer TLS. Use "LIBNBD_TLS_REQUIRE" a continuación si la conexión debe cifrarse.

Algunos servidores cerrarán la conexión si TLS falla, por lo que la recuperación puede no ser posible.

"LIBNBD_TLS_REQUIRE" Requerir una conexión TLS cifrada y autenticada. Siempre fallar al conectarse si la conexión no está cifrada y autenticada.

Además de llamar a esto, también puede necesitar proporcionar la ruta al directorio de certificados (nbd_set_tls_certificates(3)), el nombre de usuario (nbd_set_tls_username(3)) y/o el archivo de Claves Precompartidas (PSK) (nbd_set_tls_psk_file(3)). Por ahora, al usar nbd_connect_uri(3), los parámetros de consulta de URI relacionados con TLS no se manejan automáticamente. Establecer el nivel por encima de cero fallará si libnbd no se compiló contra gnutls; puede verificar si este es el caso con nbd_supports_tls(3).

val get_tls_negotiated : t -> bool

NBD.get_tls_negotiated t

averiguar si TLS se negoció en una conexión

Después de conectarse, puede llamar a esto para averiguar si la conexión está utilizando TLS.

Esto normalmente solo es útil si estableció el modo de solicitud TLS en "LIBNBD_TLS_ALLOW" (ver nbd_set_tls(3)), porque en este modo intentamos usar TLS pero recurrimos a texto plano si no estaba disponible. Esta función le dirá si se negoció TLS o no.

En el modo "LIBNBD_TLS_REQUIRE" (el más seguro), la conexión habría fallado si TLS no se hubiera podido negociar. Con el modo "LIBNBD_TLS_DISABLE", TLS no se intenta automáticamente; pero si el servidor NBD utiliza el modo menos común "SELECTIVETLS", esta función informa si una llamada manual a nbd_opt_starttls(3) habilitó TLS o si la conexión sigue siendo en texto plano.

val set_request_extended_headers : t -> bool -> unit

NBD.set_request_extended_headers t request

controlar el uso de cabeceras extendidas

Por defecto, libnbd intenta negociar cabeceras extendidas con el servidor, ya que esta extensión del protocolo permite el uso de acciones de estado como 64-bit zero, trim y bloque. Sin embargo, para pruebas de integración, puede ser útil borrar este flag en lugar de buscar una forma de alterar el servidor para que rechace la solicitud de negociación.

Para la compatibilidad retroactiva, el ajuste de este parámetro se ignora si nbd_set_request_structured_replies(3) también está configurado a false, ya que el uso de cabeceras extendidas implica respuestas estructuradas.

val get_extended_headers_negotiated : t -> bool

NBD.get_extended_headers_negotiated t

ver si se están usando cabeceras extendidas

Después de conectar, puedes llamar a esta función para saber si la conexión usa cabeceras extendidas. Nota: Este ajuste es fijo; puede devolver true incluso después de un segundo nbd_opt_extended_headers(3) devuelve false porque el servidor detectó una solicitud duplicada.

val set_strict_mode : t -> STRICT.t list -> unit

NBD.set_strict_mode t flags

controls how strictly to follow the NBD protocol

By default, libnbd tries to detect requests that would result in indeterminate behavior in the NBD protocol, and rejects them as client requests without sending network traffic. However, for integration testing, it may be useful to relax libnbd's strictness, to force it to send such requests over the network to test the server's robustness.

The "flags" argument is a bitmask, containing zero or more of the following strictness flags:

"LIBNBD_STRICT_COMMANDS" = 0x1 If set, this flag rejects client requests that do not conform to the announced server flags (e.g., attempting a write on a read-only server, or attempting to use "LIBNBD_CMD_FLAG_FUA" when nbd_can_fua(3) returned false). If clear, this flag relies on the server to reject unexpected requests.

"LIBNBD_STRICT_FLAGS" = 0x2 If set, this flag rejects client requests that attempt to set a command flag not recognized by libnbd (those outside "LIBNBD_CMD_FLAG_MASK"), or a flag not normally associated with a command (like using "LIBNBD_CMD_FLAG_FUA" on a read request). If clear, all flags are sent to the server, even if sending such a flag might cause the server to change its reply in ways that confuse libnbd, perhaps leading to a crash or connection termination.

Flags known by libnbd to be associated with a given command (like "LIBNBD_CMD_FLAG_DF" for nbd_pread_structured(3) managed by nbd_can_df(3)) are controlled by "LIBNBD_STRICT_COMMANDS"; and "LIBNBD_CMD_FLAG_PAYLOAD_LEN" is handled automatically by libnbd, unless "LIBNBD_STRICT_AUTO_FLAG" is off.

Note: The NBD protocol only supports 16 bits of command flags, although the libnbd API uses "uint32_t"; bits outside the range allowed by the protocol are always client errors.

"LIBNBD_STRICT_BOUNDS" = 0x4 If set, this flag rejects client requests that exceed export bounds without sending network traffic to the server. If clear, this flag relies on the server to detect out-of-bounds requests.

"LIBNBD_STRICT_ZERO_SIZE" = 0x8 If set, this flag rejects client requests with length 0. If clear, it allows zero-length requests to the server, which may produce indeterminate results.

"LIBNBD_STRICT_ALIGN" = 0x10 If set, and the server provides minimum block sizes (see "LIBNBD_SIZE_MINIMUM" for nbd_get_block_size(3)), this flag rejects client requests that do not have length and offset aligned to the server's minimum requirements. If clear, misaligned requests are sent to the server, where the server decides whether to honour or reject the request.

"LIBNBD_STRICT_PAYLOAD" = 0x20 If set, the client rejects sending a request to the server with more than libnbd's maximum payload length (see "LIBNBD_SIZE_PAYLOAD" for nbd_get_block_size(3)), regardless of whether the server announced a maximum block size. If clear, requests larger than 64MiB may be attempted, although requests larger than 32MiB may cause a disconnection on some servers.

"LIBNBD_STRICT_AUTO_FLAG" = 0x40 If set, requests that accept "LIBNBD_CMD_FLAG_PAYLOAD_LEN" (like nbd_pwrite(3) and nbd_block_status_filter(3)) ignore the presence or absence of that flag from the caller, and send the value over the network that corresponds to the server's expectations based on whether extended headers were negotiated when the connection was established. If clear, the caller assumes responsibility for whether the payload length flag is set or not during the affected request, which can be useful in integration testing but is more likely to generate undefined behaviour.

For convenience, the constant "LIBNBD_STRICT_MASK" is available to describe all strictness flags supported by this build of libnbd. Future versions of libnbd may add more flags, which will likely be enabled by default for additional client filtering. Therefore, when attempting to relax only a specific bit while retaining client-side checks, it is wiser to first call nbd_get_strict_mode(3) and modify that value, rather than simply setting a constant value.

val set_opt_mode : t -> bool -> unit

NBD.set_opt_mode t enable

controls opt mode, to pause during option negotiation

Set this flag to true to request that an "nbd_connect_*" connection will pause during option negotiation instead of proceeding all the way to the ready state, when talking to a new-style server. This setting has no effect when connecting to an old-style server.

Note: libnbd defaults to attempting "NBD_OPT_STARTTLS", "NBD_OPT_EXTENDED_HEADERS", and "NBD_OPT_STRUCTURED_REPLY" before allowing you to control the remaining negotiation steps; if you need control over these steps, first set nbd_set_tls(3) to "LIBNBD_TLS_DISABLE", and nbd_set_request_extended_headers(3) or nbd_set_request_structured_replies(3) to false, before starting the connection attempt.

When opt mode is active, you have fine-grained control over which options are negotiated, as opposed to the server default of negotiating everything in your favor using the settings made before starting the connection. To leave opt mode and proceed to the ready state, you must use nbd_opt_go(3) successfully; a failure in nbd_opt_go(3) returns to the negotiating state to allow an export name change before trying again. You may also use nbd_opt_abort(3) or nbd_shutdown(3) to terminate the connection without completing negotiation.

val opt_starttls : t -> bool

NBD.opt_starttls t

requests that the server start TLS

Requests that the server start a secure TLS connection, by sending "NBD_OPT_STARTTLS". This may only be used if nbd_set_opt_mode(3) enabled opt mode; additionally, if you used nbd_set_tls(3) to request something other than the default "LIBNBD_TLS_DISABLE", libnbd already attempted a TLS connection before allowing you to control option negotiation. This command is disabled if nbd_supports_tls(3) reports false.

This function is primarily useful for integration testing of edge cases in server handling; in particular, using this function when combined with a server that is not careful about resetting stateful commands like nbd_opt_structured_reply(3) could result in a security hole (see CVE-2021-3716 against nbdkit, for example). Therefore, when security is a concern, it should be preferred to use nbd_set_tls(3) with "LIBNBD_TLS_REQUIRE" and allow libnbd to negotiate TLS automatically.

This function returns true if the server successfully responds, false if the server responds with an error, and fails only if the server does not respond (e.g. due to connection loss, which may include when the server rejects credentials provided during the TLS handshake). Note that the NBD protocol documents requesting TLS after it has already been enabled as a client error; servers typically fail the second request gracefully, but that does not break an already established TLS session, as reported by nbd_get_tls_negotiated(3).

conectar al comando del servidor NBD

val connect_systemd_socket_activation : t -> string list -> unit

NBD.connect_systemd_socket_activation t argv

conectar usando activación de socket systemd

Ejecuta el comando como un subproceso y se conecta a él usando la activación de socket de systemd.

Esto es especialmente útil para ejecutar qemu-nbd(1) como un subproceso de libnbd, por ejemplo, para usarlo para abrir archivos qcow2.

Para ejecutar nbdkit como un subproceso, se puede usar esta función, o nbd_connect_command(3).

Para ejecutar nbd-server(1) como un subproceso, esta función no puede usarse, debe usar nbd_connect_command(3).

Activación de socket Libnbd creará un fork del comando "argv" y le pasará un socket NBD usando variables de entorno especiales "LISTEN_*" (según lo definido por el protocolo de activación de socket de systemd).

┌─────────┬─────────┐ ┌───────────────┐ │ programa │ libnbd │ │ qemu-nbd u otro │ │ │ │ │ servidor │ │ │ socket ╍╍╍╍╍╍╍╍▶ │ └─────────┴─────────┘ └───────────────┘

Cuando el manejador NBD se cierra, el subproceso servidor es terminado.

Nombre del socket El protocolo de activación de sockets te permite darle un nombre opcional al socket. Si se usa, el nombre se pasa al servidor NBD usando la variable de entorno "LISTEN_FDNAMES". Para proporcionar un nombre de socket, llama a nbd_set_socket_activation_name(3) antes de llamar a la función de conexión.

Esta llamada retorna cuando se ha establecido la conexión. Por defecto, esto procede hasta la fase de transmisión, pero nbd_set_opt_mode(3) se puede usar para el control manual sobre la negociación de opciones realizada antes de la fase de transmisión.

val aio_get_direction : t -> int

NBD.aio_get_direction t

devuelve la dirección de lectura o escritura

Devuelve la dirección actual de esta conexión, lo que significa si se espera leer datos del servidor a continuación, escribir datos al servidor, o ambos. Devuelve:

0 No se espera que interactuemos con el descriptor de archivo del servidor desde el estado actual. No merece la pena intentar usar poll(2); si la conexión no está muerta, entonces el progreso de la máquina de estados debe venir de alguna otra manera, como nbd_aio_connect(3).

"LIBNBD_AIO_DIRECTION_READ" = 1 Se espera que leamos del servidor a continuación. Si se usa poll(2), se establecería "events = POLLIN". Si "revents" devuelve "POLLIN" o "POLLHUP", entonces llamarías a nbd_aio_notify_read(3).

Ten en cuenta que una vez que libnbd alcanza nbd_aio_is_ready(3), esta dirección se devuelve incluso cuando no hay comandos en curso (ver nbd_aio_in_flight(3)). En un uso de un solo hilo de libnbd, no merece la pena hacer polling hasta después de emitir un comando, ya que de lo contrario el servidor nunca despertará el poll. En un escenario multihilo, puedes tener un hilo iniciando un bucle de polling antes de cualquier comando, pero cualquier otro hilo que emita un comando necesitará una forma de sacar al hilo de polling de poll en caso de que la emisión del comando cambie la dirección de polling necesaria. Las formas posibles de hacerlo incluyen hacer polling de actividad en una tubería a sí mismo, o usar pthread_kill(3) para enviar una señal que se enmascara excepto durante ppoll(2).

"LIBNBD_AIO_DIRECTION_WRITE" = 2 Se espera que escribamos al servidor a continuación. Si se usa poll(2), se establecería "events = POLLOUT". Si "revents" devuelve "POLLOUT", entonces llamarías a nbd_aio_notify_write(3).

"LIBNBD_AIO_DIRECTION_BOTH" = 3 Se espera que leamos o escribamos al servidor a continuación. Si se usa poll(2), se establecería "events = POLLIN|POLLOUT". Si se devuelve solo uno de "POLLIN" o "POLLOUT", entonces ver arriba. Sin embargo, si se devuelven ambos, es mejor llamar solo a nbd_aio_notify_read(3), ya que procesar la respuesta del servidor puede cambiar el estado de la conexión e invalidar la necesidad de escribir más comandos.

val aio_command_completed : t -> int64 -> bool

NBD.aio_command_completed t cookie

comprueba si el comando se completó

Devuelve verdadero si el comando se completó. Si esta función devuelve verdadero, entonces el comando fue exitoso y ha sido retirado. Devuelve falso si el comando todavía está en curso. Esto también puede fallar con un error en caso de que el comando fallara (en cuyo caso el comando también es retirado). Un comando se retira ya sea a través de este comando, o usando un callback de finalización que devuelve 1.

El parámetro "cookie" es la cookie única de 64 bits positiva para el comando, tal como la devuelve una llamada como nbd_aio_pread(3).

val aio_peek_command_completed : t -> int64

NBD.aio_peek_command_completed t

comprueba si algún comando se completó

Devuelve la cookie única de 64 bits positiva del primer comando no retirado pero completado, 0 si hay comandos en curso pero ninguno de ellos está pendiente de ser retirado, o -1 en caso de error, incluyendo cuando no hay comandos en curso. Cualquier cookie devuelta por esta función aún debe pasarse a nbd_aio_command_completed(3) para retirar realmente el comando y saber si el comando fue exitoso.
