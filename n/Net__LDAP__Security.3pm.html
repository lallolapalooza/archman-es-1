NAME

Net::LDAP::Security - Problemas de seguridad relacionados con conexiones a servidores LDAP

SYNOPSIS

none

DESCRIPCIÓN

Este documento discute diversos problemas de seguridad relacionados con el uso de LDAP y la conexión a servidores LDAP, especialmente cómo gestionar estos posibles vulnerabilidades:

  • ¿Conoces que estás conectado al servidor correcto?
  • ¿Puede un atacante escuchar tus contrasenias o identificadores de usuario durante la conexión a un directorio?
  • ¿Puede un atacante escuchar información confidencial de la conexión a un directorio?

Net::LDAP proporciona formas de abordar estas vulnerabilidades: mediante el uso de LDAPS, o LDAPv3 y TLS, y/o el uso de SASL. Cada uno de estos se explicará más adelante.

¿Cómo funciona una conexión LDAP?

Una conexión LDAPv2 o LDAPv3 funciona mediante el cliente conectándose directamente a puerto 389 (por defecto), y luego emitir diversos requisitos LDAP como búsqueda, agregar, etc.

No hay manera de garantizar que un cliente LDAP esté conectado al servidor correcto. Los ciberdelincuentes pueden haber atacado tu DNS, por lo que 'ldap.example.com' podría apuntar a 'ldap.hacker.com'. O pueden haber instalado su propio servidor en el equipo correcto.

Es natural que toda la información se transmita entre el cliente y el servidor en 'texto plano'. Esto es un término usado por criptógrafos para describir datos no encriptados y recuperables, así que incluso aunque LDAP pueda transmitir valores binarios como imágenes JPEG, audios y certificados X.509, todo sigue siendo considerado 'texto plano'.

Si estas vulnerabilidades son un problema, entonces deberías considerar otras alternativas descritas más adelante, como LDAPS, LDAPv3 y TLS, y SASL.

¿Cómo funciona una conexión LDAPS?

LDAPS es un protocolo no oficial. Es a LDAPS como HTTPS es a HTTP, es decir, el mismo protocolo (pero en este caso LDAPv2 o LDAPv3) que se ejecuta sobre una conexión segura («Secure Socket Layer») a puerto 636 (por defecto).

No todas las servidores estarán configuradas para escuchar conexiones LDAPS, pero si lo hacen, suele estar en un puerto diferente del puerto normal de conexión LDAP sin encriptación.

El uso de LDAPS puede potencialmente resolver las vulnerabilidades descritas anteriormente, pero debes tener en cuenta que simplemente usar SSL no es un mago que automaticamente hace tu sistema «seguro».

Primero, LDAPS puede resolver el problema de verificar que estás conectado al servidor correcto. Cuando el cliente y el servidor se conectan, se realizan un handshake especial SSL, parte de lo cual involucra el intercambio de claves criptográficas del servidor y del cliente, que se describen usando certificados X.509. Si el cliente desea confirmar que está conectado al servidor correcto, lo único que necesita hacer es verificar la certificación del servidor que se envía en el handshake. Esto se hace de dos formas:

1.
Verifica que la certificación sea firmada (confiable) por alguien que confías, y que no haya sido revocada. Por ejemplo, la certificación del servidor puede haber sido firmada por Verisign (www.verisign.com), y tú decides que quieres confiar en Verisign para firmar certificados legítimos.
2.
Verifica que el RDN más significativo de la DN del certificado del servidor sea el hostname completo que conectaste cuando creaste la conexión LDAPS. Por ejemplo, si el servidor tiene , el RDN a verificar es .

Puedes hacer esto usando las opciones cafile y capath cuando se crea un objeto Net::LDAPS, y también estableciendo la opción verify a 'require'.

Para evitar que los atacantes escuchen contrasenias y otras información en tu conexión, también debes asegurar que el algoritmo de encriptación utilizado en la conexión SSL sea suficientemente sólido. Esto también se decide durante el handshake SSL. Si el cliente y el servidor no pueden acordar un algoritmo aceptable, la conexión no se establece.

Net::LDAPS utilizará por defecto todos los algoritmos disponibles en tu copia de OpenSSL, excepto aquellos considerados como de baja seguridad, y aquellos que usan la encriptación con clave de exportación. Puedes cambiar esto al crear un objeto Net::LDAPS usando la opción 'ciphers'.

Una vez que hayas establecido la conexión segura, debes también verificar que el algoritmo de encriptación que se está utilizando sea uno que consideres aceptable. Servidores caídos han sido observados que 'fallan' y te dan una conexión no encriptada, así que deberías verificarlo.

¿Cómo funciona LDAP y TLS?

SSL es una solución buena para muchos problemas de seguridad en redes, pero no es estándar. El IETF corrigió algunos defectos en el mecanismo de SSL y publicó un estándar llamado RFC 2246, que describe TLS («Seguridad de Capa de Transporte»), que es simplemente una versión limpia y estandarizada de SSL.

Solo puedes usar TLS con un servidor LDAPv3. Esto es porque el estándar (RFC 4511) para LDAP y TLS requiere que la conexión normal de LDAP (es decir, en puerto 389) pueda ser cambiada de texto plano a una conexión TLS de forma on demand. El mecanismo de cambio utiliza una operación especial de LDAP, y ya que estos no son legales en LDAPv2, solo puedes cambiar a TLS en una conexión LDAPv3.

Por lo tanto, el modo en que usas TLS con LDAPv3 es crear tu conexión normal LDAPv3 usando Net::LDAP::new(), y luego realizas el cambio usando Net::LDAP::start_tls(). El método start_tls() toma casi los mismos argumentos que Net::LDAPS::new(), así que consulta el contenido anterior para detalles.

¿Cómo funciona SASL?

SASL es un marco de autenticación que puede usarse por una variedad de servicios de Internet, incluyendo LDAPv3. Dado que es solo un marco, no ofrece ninguna forma de autenticarse por sí mismo; para autenticarse en un servicio, necesitas usar un mecanismo específico de SASL. Varios mecanismos se definen, como CRAM-MD5.

El uso de un mecanismo como CRAM-MD5 proporciona una solución a la vulnerabilidad de escaneo de contrasenias, ya que estos mecanismos suelen no requerir que el usuario envíe una clave secreta (por ejemplo, una contrasena) en claro en la red. En lugar de eso, la autenticación se lleva a cabo de manera ingeniosa que evita este problema y preven la escaneo de contrasenias.

Net::LDAP soporta SASL mediante la clase Authen::SASL. Actualmente, los únicos subclases disponibles de Authen::SASL (es decir, mecanismos SASL) son CRAM-MD5 y EXTERNAL.

Algunos mecanismos de SASL ofrecen una solución general para el escaneo de toda la información en la red, ya que pueden negociar conexiones de red confidenciales (es decir, encriptadas). Aunque esto es sobre y además de cualquier encriptación SSL o TLS, lamentablemente el código de Authen::SASL de Perl no puede negociar esto.
