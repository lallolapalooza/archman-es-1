NOMBRE

Net::DBus::Tutorial::ExportingObjects - tutoriales sobre cómo proporcionar un servicio DBus

DESCRIPCIÓN

Este documento proporciona un tutorial sobre cómo proporcionar un servicio DBus utilizando los enlaces de aplicación Perl Net::DBus. Los ejemplos en este documento se basarán en el código de la distribución Music::Player, que es un servicio DBus simple que proporciona un reproductor de pistas de música.

CREANDO UN OBJETO

El primer paso para crear un objeto es crear un nuevo paquete que herede de Net::DBus::Object. El objeto Music::Player::Manager proporciona una API para gestionar la colección de backends de reproductores de música para diferentes tipos de pistas. Para empezar, creemos el esqueleto del paquete y su constructor. El constructor del supertipo, Net::DBus::Object, espera recibir dos parámetros: un manejador del servicio Net::DBus que posee el objeto y una ruta bajo la cual se exportará el objeto. Dado que la clase manager está pensada para ser un objeto singleton, podemos codificar su ruta en el constructor:

package Music::Player::Manager;
use base qw(Net::DBus::Object);
sub new {
    my $class = shift;
    my $service = shift;
    my $self = $class->SUPER::new($service, "/music/player/manager");
    bless $self, $class;
    return $self;
}
1;

Ahora, como se mencionó, el gestor manejará un número de diferentes backends de reproductor. Así que necesitamos proporcionar métodos para registrar nuevos backends y consultar por backends capaces de reproducir un tipo de archivo particular. Así que modificando el código anterior agregamos una tabla hash en el constructor para almacenar los backends:

sub new {
    my $class = shift;
    my $service = shift;
    my $self = $class->SUPER::new($service, "/music/player/manager");
    $self->{backends} = {};
    bless $self, $class;
    return $self;
}

Y ahora un método para registrar un nuevo backend. Este toma un nombre de módulo Perl y lo usa para instanciar un backend. Dado que los backends también serán objetos DBus, necesitamos pasar una referencia al servicio al que estamos adjuntos, junto con una ruta bajo la cual registrar el backend. Usamos el método "get_service" para recuperar una referencia al servicio al que está adjunto el gestor y adjuntamos el backend del reproductor a este mismo servicio: Cuando se invoca un método en un objeto DBus, el primer parámetro es la referencia al objeto ($self), y el resto son los parámetros proporcionados a la llamada del método. Por lo tanto, escribir una implementación de método en un DBus no es realmente diferente de Perl orientado a objetos normal (cf perltoot):

sub register_backend {
    my $self = shift;
    my $name = shift;
    my $module = shift;
    eval "use $module";
    if ($@) {
        die "cannot load backend $module: $@" ;
    }
    $self->{backends}->{$name} = $module->new($self->get_service,
                                              "/music/player/backend/$name");
}

Mirando esto, uno podría preguntarse qué sucede si se activa el método "die". En tal escenario, en lugar de terminar el proceso del servicio, el error será capturado y propagado al llamador remoto para que lo maneje.

Los backends del reproductor proporcionan un método "get_track_types" que devuelve una referencia de array de los tipos de pistas de música que soportan. Podemos usar este método para proporcionar una API que permita la recuperación fácil de un backend para un tipo de pista particular. Este método devolverá una ruta con la que se puede acceder al objeto backend

sub find_backend {
    my $self = shift;
    my $extension = shift;
    foreach my $name (keys %{$self->{backends}}) {
       my $backend = $self->{backends}->{$name};
       foreach my $type (@{$backend->get_track_types}) {
          if ($type eq $extension) {
              return $backend->get_object_path;
          }
       }
    }
    die "no backend for type $extension";
}

Tomemos un momento rápido para considerar cómo se usaría este método para reproducir una pista de música. Si aún no lo ha hecho, refresque su memoria de Net::DBus::Tutorial::UsingObjects. Ahora, tenemos un archivo MP3 que deseamos reproducir, así que buscamos la ruta a un backend, luego recuperamos el objeto para él y reproducimos la pista:

...obtener el servicio de reproductor de música...
# Solicitar una ruta a un reproductor para archivos mp3
my $path = $service->find_backend("mp3");
# $path ahora contiene '/music/player/backend/mpg123'
# y podemos obtener el objeto backend
my $backend = $service->get_object($path);
# y finalmente reproducir la pista
$backend->play("/vol/music/beck/guero/09-scarecrow.mp3");

PROPORCIONANDO DATOS DE INTROSPECCIÓN

El código anterior es un objeto funcional completo, listo para ser registrado con un servicio, y dado que los parámetros y valores de retorno de los dos métodos son ambos cadenas simples, podríamos detenernos ahí. En algunos casos, sin embargo, uno podría querer ser más específico sobre los tipos de datos esperados para los parámetros, por ejemplo, enteros con signo vs. sin signo. Agregar tipado explícito de datos también hace que la interacción con otros lenguajes de programación sea más confiable. Proporcionar definiciones de tipos de datos explícitos para métodos exportados se conoce en el mundo DBus como "Introspección", y hace la vida mucho más confiable para los usuarios de uno's servicio que pueden estar utilizando un lenguaje fuertemente tipado como C.

El primer paso para proporcionar datos de introspección para un objeto DBus en Perl es especificar el nombre de la interfaz proporcionada por el objeto. Esta es típicamente una cadena separada por puntos, por convención que contiene el nombre de dominio de la aplicación como su primer componente. Dado que la mayoría de los módulos Perl terminan viviendo en CPAN, uno podría usar "org.cpan" como el primer componente, seguido del nombre del paquete del módulo (reemplazando :: por .), por ejemplo, "org.cpan.music.player.manager". Si no se planea alojar el módulo en CPAN, se podría usar un dominio personal/de proyecto, por ejemplo, "com.berrange.music.player.manager". La interfaz para un objeto se define cargando el módulo Net::DBus::Exporter, proporcionando la interfaz como su primer parámetro. Así que el ejemplo de código anterior se modificaría para verse así:

package Music::Player::Manager;
use base qw(Net::DBus);
use Net::DBus::Exporter qw(com.berrange.music.player.manager)

A continuación, es necesario proporcionar tipos de datos para los parámetros y valores de retorno de los métodos. El módulo Net::DBus::Exporter proporciona un método "dbus_method" para este propósito, que toma tres parámetros, el nombre del método que se está exportando, una referencia de array de tipos de parámetros y una referencia de array de tipos de retorno (este último puede omitirse si no hay valores de retorno). Esto se puede llamar en cualquier momento en el código del módulo, pero por convención es preferible asociar las llamadas a "dbus_method" con la implementación real del método, así:

dbus_method("register_backend", ["string", "string"]);
sub register_backend {
    my $self = shift;
    my $name = shift;
    my $module = shift;
    .. snipped rest of method body ...
}

Y, así:

dbus_method("find_backend", ["string"], ["string"])
sub find_backend {
    my $self = shift;
    my $extension = shift;
    ... snip method body...
}

DEFINIENDO UN SERVICIO

Ahora que los objetos han sido escritos, es hora de definir un servicio. Un servicio no es más que un nombre bien conocido para un contrato de API determinado. Un contrato puede ser pensado como una definición de una lista de rutas de objetos y las interfaces correspondientes que proporcionan. Así, alguien más podría venir y proporcionar una implementación alternativa de reproductor de música usando los enlaces de Python o QT para DBus, y si proporcionaran el mismo conjunto de rutas de objetos e interfaces, podrían justificadamente registrar el mismo servicio en el bus.

El módulo Net::DBus::Service proporciona los medios para registrar un servicio. Su constructor espera una referencia al objeto bus (una instancia de Net::DBus), junto con el nombre del servicio. Al igual que con los nombres de interfaz, el primer componente de un nombre de servicio generalmente se deriva de un nombre de dominio, y luego se le añade el nombre de la aplicación, en nuestro ejemplo formando "org.cpan.Music.Player". Mientras que algunos objetos se crearán sobre la marcha durante la ejecución de la aplicación, otros se crearán al inicio.

CREATING AN OBJECT

As noted before, services are instantiated around objects which provide the functionality required. An object may provide one, or more DBus interfaces. As such, it is typical to have objects which provide specific interfaces, and then to have a main service object which instantiates these objects and registers them with the bus.

In our music player example, we might have a Music::Player::Manager object which handles the actual playing of music, and a Music::Player::Tracklist object which handles the playlist. The service object itself would then instantiate these objects and register them with the bus under the paths required.

The constructor for a service object is responsible for instantiating and registering the objects that the service exports. This is done by calling the export_object method on the service object itself. This method takes the object to export, and the path at which to export it as arguments.

package Music::Player;
use base qw(Net::DBus::Service);
sub new {
    my $class = shift;
    my $bus = shift;
    my $self = $class->SUPER::new($bus, "org.cpan.music.player");
    bless $self, $class;
    $self->{manager} = Music::Player::Manager->new($self);
    $self->export_object($self->{manager}, "/TrackList");
    return $self;
}

The Net::DBus::Service base class takes care of the boilerplate for exposing the objects via DBus. The service object itself is automatically exported under the root path "/", so you don't need to explicitly call export_object for it. You also don't need to explicitly call it for any objects which are instantiated by the service using Net::DBus::Service::new. The Net::DBus::Service base class automatically exports all objects created via its constructor.

PROVIDING INTROSPECTION DATA

As noted previously, DBus uses XML for describing interfaces. This is known as introspection data. A service which wishes to be discoverable must provide this data. This is done by implementing the "org.freedesktop.DBus.Introspectable" interface on the objects being exported.

The interface is simple, containing only one method: "Introspect". This method should return an XML string describing the interfaces provided by the object.

Here is an example of introspection data for the Music::Player::Manager object:

<node>
  <interface name="org.cpan.music.player.Manager">
    <method name="Play">
      <arg direction="in"  type="s" name="filename"/>
    </method>
    <method name="Stop"/>
    <signal name="TrackFinished">
      <arg type="s" name="filename"/>
    </signal>
  </interface>
</node>

The "org.freedesktop.DBus.Exporter" interface, which is automatically provided by "Net::DBus::Service", provides a list of all objects exported by the service. This is useful for clients wishing to discover the objects available within a service.

<node>
  <interface name="org.freedesktop.DBus.Exporter">
    <method name="ListObjects">
      <arg direction="out" type="ao" name="objects"/>
    </method>
  </interface>
</node>

A service which exports multiple objects must aggregate the introspection data from all its exported objects. The root object of the service is responsible for providing this aggregated introspection data.

The "Net::DBus::Service" base class provides a default implementation of the "org.freedesktop.DBus.Introspectable" interface. This default implementation will automatically generate introspection data based on the objects that have been exported by the service. You can override this default implementation if you need to provide custom introspection data.

DEFINING A SERVICE

The Net::DBus::Service base class provides a convenient way to define DBus services. A service is essentially a Perl object that exports one or more DBus interfaces. The service object itself is also exported as a DBus object, typically under the root path "/".

The constructor for a service object is responsible for instantiating and registering the objects that the service exports. This is done by calling the export_object method on the service object itself. This method takes the object to export, and the path at which to export it as arguments.

The following example shows a simple service object that exports a single interface, "org.cpan.music.player.Manager":

package Music::Player;
use base qw(Net::DBus::Service);
sub new {
    my $class = shift;
    my $bus = shift;
    my $self = $class->SUPER::new($bus, "org.cpan.music.player");
    bless $self, $class;
    $self->{manager} = Music::Player::Manager->new($self);
    $self->export_object($self->{manager}, "/TrackList");
    return $self;
}

The Net::DBus::Service base class automatically provides one special object to all services, under the path "/org/freedesktop/DBus/Exporter". This object implements the "org.freedesktop.DBus.Exporter" interface which has a method "ListObject". This enables clients to determine a list of all objects exported within a service. While not functionally necessary for most applications, it is none-the-less a useful tool for developers debugging applications, or wondering what a service provides.

CONNECTING TO THE BUS

The final step in getting our service up and running is to connect it to the bus. This brings up an interesting conundrum, does one export the service on the system bus (shared by all users & processes on the machine), or the session bus (one per user logged into a machine). In some cases the answer, with only one of the two buses conceptually making sense. In other cases, however, both the session & system bus are valid. In the former one would use the "session" or <system> methods on Net::DBus to get a handle to the desired bus, while in the latter case, the "find" method would be used. This applies a heuristic to determine the correct bus based on execution environment. In the case of the music player, either bus is relevant, so the code to connect the service to the bus would look like:

use Net::DBus;
my $bus = Net::DBus->find;
my $player = Music::Player->new($bus);

With the service attached to the bus, it is merely necessary to run the main event processing loop to listen out for & handle incoming DBus messages. So the above code is modified to start a simple reactor:

use Net::DBus;
use Net::DBus::Reactor;
my $bus = Net::DBus->find;
my $player = Music::Player->new($bus);
Net::DBus::Reactor->main->run;
exit 0;

Saving this code into a script "/usr/bin/music-player.pl", coding is complete and the service ready for use by clients on the bus.

SERVICE ACTIVATION

One might now wonder how best to start the service, particularly if it is a service capable of running on both the system and session buses. DBus has the answer in the concept of "activation". What happens is that when a client on the bus attempts to call a method, or register a signal handler against, a service not currently running, it will first try and start the service. Service's which wish to participate in this process merely need stick a simple service definition file into the directory "/usr/share/dbus-1/services". The file should be named to match the service name, with the file extension ".service" appended. eg, "/usr/share/dbus-1/services/org.cpan.music.player.service" The file contains two keys, first the name of the service, and second the name of the executable used to run the service, or in this case the Perl script. So, for our simple service the data file would contain:

[D-BUS Service]
Name=org.cpan.music.player
Exec=/usr/bin/music-player.pl
