NETWORKMANAGER.CONF(5) Configuración NETWORKMANAGER.CONF(5)

NOMBRE

NetworkManager.conf - Archivo de configuración de NetworkManager

SINOPSIS

/etc/NetworkManager/NetworkManager.conf, /etc/NetworkManager/conf.d/nombre.conf, /run/NetworkManager/conf.d/nombre.conf, /usr/lib/NetworkManager/conf.d/nombre.conf, /var/lib/NetworkManager/NetworkManager-intern.conf

DESCRIPCIÓN

NetworkManager.conf es el archivo de configuración para NetworkManager. Se usa para establecer diversos aspectos del comportamiento de NetworkManager. La ubicación del archivo principal y de los directorios de configuración puede ser modificada mediante el uso de los argumentos --config, --config-dir, --system-config-dir y --intern-config de NetworkManager, respectivamente.

Si se proporciona un archivo de configuración por defecto de NetworkManager por parte de las distribuciones, no debes modificarlo, ya que tus cambios pueden ser sobrescritos por actualizaciones de paquetes. En su lugar, puedes agregar archivos .conf adicionales a la carpeta /etc/NetworkManager/conf.d. Estos se leen en orden, con archivos posteriores sobrescribiendo a los anteriores. Los paquetes pueden instalar snippets de configuración adicionales en /usr/lib/NetworkManager/conf.d. Esta carpeta se procesa primero, incluso antes de NetworkManager.conf. Los scripts también pueden colocar configuración por arranque en /run/NetworkManager/conf.d. Esta carpeta se procesa en segundo lugar, también antes de NetworkManager.conf. La carga de un archivo /run/NetworkManager/conf.d/nombre.conf puede ser evitada colocando un archivo /etc/NetworkManager/conf.d/nombre.conf. De igual forma, un archivo /usr/lib/NetworkManager/conf.d/nombre.conf puede ser "sombreado" colocando un archivo del mismo nombre en /etc/NetworkManager/conf.d o /run/NetworkManager/conf.d.

NetworkManager puede sobrescribir ciertas opciones de configuración del usuario mediante D-Bus u operaciones internas. En este caso, escribe esos cambios en /var/lib/NetworkManager/NetworkManager-intern.conf. Este archivo no está diseñado para ser modificado por el usuario, pero se lee por último y puede "sombra" las configuraciones del usuario de NetworkManager.conf.

Ciertas configuraciones del archivo de configuración pueden ser recargadas en tiempo de ejecución ya sea enviando la señal SIGHUP o a través de la llamada D-Bus 'Reload'.

NetworkManager no requiere ninguna configuración en NetworkManager.conf. Según tu caso de uso, podrías eliminar todos los archivos para restaurar la configuración por defecto. Sin embargo, ten en cuenta que tu distribución u otros paquetes podrían eliminar snippets de configuración para NetworkManager como parte de la configuración de fábrica.

FORMATO DE ARCHIVO

El formato del archivo de configuración es un archivo tipo clave-valor (similar al formato ini). Consiste en secciones (grupos) de pares clave-valor. Las líneas que comienzan con un '#' y las líneas vacías se consideran comentarios. Las secciones comienzan con una línea de encabezado que contiene la sección entre corchetes '[...]' y terminan implícitamente al inicio de la siguiente sección o al final del archivo. Cada par clave-valor debe estar contenido dentro de una sección.

Para claves que toman una lista de dispositivos como valor, puedes especificar dispositivos por sus direcciones MAC o nombres de interfaz, o usar el valor '*' para especificar todos los dispositivos. Ver la sección llamada "Formato de lista de dispositivos" a continuación.

Un archivo de configuración simple se ve así:

[main]
plugins=keyfile

Como una extensión del formato keyfile normal, también puedes añadir un valor a un valor de lista previamente establecido haciendo:

plugins+=another-plugin
plugins-=remove-me

SECCIÓN PRINCIPAL

plugins

Lista de nombres de plugins de configuración del sistema separados por comas. Estos plugins se utilizan para leer y escribir configuraciones de perfiles de red del sistema. Cuando se especifican múltiples plugins, las conexiones se leen de todos los plugins especificados. Al escribir una conexión, se pregunta a los plugins por el tipo de conexión a guardar en el orden listado aquí; si el primer plugin no puede escribir esa conexión (o no puede escribir ninguna conexión), se intenta con el siguiente plugin, y así sucesivamente. Si ninguno de los plugins puede guardar la conexión, se devuelve un error al usuario.

El valor por defecto y el número de plugins disponibles dependen de la distribución. Ver la sección llamada "PLUGINS" para los plugins disponibles. Ten en cuenta que el plugin keyfile nativo de NetworkManager siempre se añade al final de esta lista (si no estaba ya presente antes).

monitor-connection-files

Esta configuración ha sido eliminada y no tiene efecto. Los perfiles en disco nunca se recargan automáticamente. Usa, por ejemplo, nmcli connection reload para eso.

SECCIÓN DE REGISTRO

Esta sección controla el registro de NetworkManager. El registro es muy importante para comprender lo que está haciendo NetworkManager. Cuando informe de un error, no filtre ni limite innecesariamente el archivo de registro. Simplemente habilite level=TRACE y domains=ALL para recopilar todo.

La forma recomendada para habilitar el registro es con un archivo /etc/NetworkManager/conf.d/95-logging.conf que contiene

[logging]
level=TRACE
domains=ALL

y reinicie el demonio con systemctl restart NetworkManager. Luego reproduzca el problema. Puede encontrar los registros en syslog (por ejemplo, journalctl, o journalctl -u NetworkManager para mostrar solo los registros de NetworkManager).

Cualquier configuración aquí se anula por las opciones de línea de comandos --log-level y --log-domains. El registro también se puede reconfigurar en tiempo de ejecución con nmcli general logging level "$LEVEL" domains "$DOMAINS". Sin embargo, a menudo es interesante obtener un registro completo desde el principio. Especialmente, al depurar un problema, habilite el registro de depuración en NetworkManager.conf y reinicie el servicio para habilitar el registro detallado desde el principio.

Al establecer nm.debug en la línea de comandos del kernel (ya sea desde /run/NetworkManager/proc-cmdline o /proc/cmdline), se habilita el registro de depuración. Esto anula tanto las opciones de línea de comandos como la configuración de NetworkManager.conf.

El registro de NetworkManager tiene como objetivo no contener datos privados sensibles y debería estar bien compartir los registros de depuración. Aun así, habrá direcciones IP y su configuración de red, si considera que eso es privado, revise el registro antes de compartirlo. Sin embargo, intente no manipular el archivo de registro de forma que distorsione demasiado el significado.

NetworkManager utiliza syslog o systemd-journald, dependiendo de la configuración. En cualquier caso, los registros de depuración son detallados y podrían ser limitados por velocidad o filtrados por el demonio de registro. Para systemd-journald, consulte RateLimitIntervalSec y RateLimitBurst en el manual de journald.conf para saber cómo deshabilitar eso.

level

El nivel de verbosidad del registro predeterminado. Uno de OFF, ERR, WARN, INFO, DEBUG, TRACE, en orden de verbosidad.

OFF deshabilita todo el registro. INFO es la verbosidad predeterminada para la operación regular. TRACE es para depuración.

Los otros niveles, en la mayoría de los casos, no son útiles. Por ejemplo, DEBUG está entre TRACE e INFO, pero es demasiado detallado para la operación regular y carece de mensajes posiblemente interesantes para la depuración. Casi siempre, al depurar un problema o informar de un error, recopile registros TRACE completos para obtener una imagen completa.

Puede configurar múltiples secciones de conexión, teniendo diferentes secciones con un nombre que comience con "connection". Ejemplo:

[connection]
ipv6.ip6-privacy=0
connection.autoconnect-ports=1

[connection-wifi-wlan0]

ipv4.route-metric=50
[connection-wifi-other]
match-device=type:wifi
ipv4.route-metric=55
ipv6.ip6-privacy=1

Las secciones dentro de un archivo se consideran en orden de aparición, con la excepción de que la sección [connection] siempre se considera al final. En el ejemplo anterior, este orden es [connection-wifi-wlan0], [connection-wlan-other] y [connection]. Al buscar un valor de configuración predeterminado, las secciones se buscan hasta que se encuentra el valor solicitado. En el ejemplo anterior, "ipv4.route-metric" para la interfaz wlan0 se establece en 50, y para todas las demás interfaces de tipo Wi-Fi en 55. Además, los dispositivos Wi-Fi tendrían direcciones privadas IPv6 habilitadas por defecto, pero otros dispositivos la tendrían deshabilitada. Tenga en cuenta que también "wlan0" obtiene "ipv6.ip6-privacy=1", porque aunque la sección "[connection-wifi-wlan0]" coincide con el dispositivo, no contiene esa propiedad y la búsqueda continúa.

Al tener diferentes secciones en múltiples archivos, las secciones de archivos que se leen posteriormente tienen mayor prioridad. Por lo tanto, dentro de un archivo, la prioridad de las secciones es de arriba a abajo. En múltiples archivos, las definiciones posteriores tienen precedencia.

Propiedades soportadas

Las siguientes propiedades pueden configurarse por dispositivo.

managed

¿Está el dispositivo gestionado o no? Un dispositivo puede marcarse como gestionado mediante reglas udev (ENV{NM_UNMANAGED}), o mediante el uso de plugins (keyfile.unmanaged-devices). Esta es otra forma de configuración. Nota que esta configuración puede ser sobreescrita en tiempo real mediante D-Bus. También tiene prioridad mayor que las reglas udev.

carrier-wait-timeout

Especifica el tiempo de espera en milisegundos para esperar el carrier en el dispositivo. El valor por defecto es 6000 milisegundos. Esta configuración existe porque ciertos drivers/hardware pueden tardar mucho en detectar si la cabecera está conectada.

Cuando el dispositivo pierde el carrier, NetworkManager no reacciona inmediatamente. En cambio, espera este tiempo antes de considerar que el enlace ha sido perdido.

Además, durante el arranque, NetworkManager considera el dispositivo como ocupado durante este tiempo, siempre que no tenga carrier. Esto retrasa el señal de completar la inicialización y el señal NetworkManager-wait-online. Configurar este valor demasiado alto puede bloquear el señal NetworkManager-wait-online más tiempo del necesario al arrancar con cable desconectado. Configurarlo demasiado bajo significa que NetworkManager declara completado el arranque demasiado pronto, aunque el carrier esté cerca y se activará automáticamente. Nota que si un perfil solo tiene configuración estática de IP o deshabilitada la capa 3, puede ya autoconectar sin carrier en el dispositivo. Una vez que este perfil alcanza el estado completo activado, el señal startup-complete se considera alcanzado incluso si el dispositivo no tiene carrier todavía.

ignore-carrier

Especifica dispositivos para los cuales NetworkManager (parcialmente) ignorará el estado de carrier. Normalmente, para dispositivos que soportan detectar carrier, como Ethernet y InfiniBand, NetworkManager solo permitirá activar una conexión si el carrier está presente (es decir, un cable está conectado), y se desactivará el dispositivo si el carrier cae por más de unos segundos.

Un dispositivo ignorado de carrier permite activar conexiones en ese dispositivo incluso si no tiene carrier, siempre que la conexión use solo direcciones IP configuradas de forma estática. Además, permite que cualquier conexión activa (ya sea estática o dinámica) permanezca activa en el dispositivo cuando el carrier se pierde.

Nota que la propiedad "carrier" de NMDevices y interfaces de dispositivo D-Bus seguirá reflejando el estado real del dispositivo; es simplemente que NetworkManager no utilizará esa información.

Los tipos de master como bond, bridge y team ignoran el carrier por defecto, mientras que otros tipos de dispositivos reaccionan a los cambios de carrier por defecto.

Esta configuración sobreescribe la propiedad antiguamente mencionada como main.ignore-carrier.

keep-configuration

Durante el arranque, NetworkManager intenta no interferir con interfaces que ya están configuradas. Lo hace generando una conexión en memoria basada en la configuración actual de la interfaz.

Si esta conexión coincide con una de las conexiones persistentes existentes, la conexión persistente se activa. Si no hay coincidencia, la conexión se activa como "external", lo que significa que la conexión se considera activa, pero NetworkManager no realmente toca la interfaz.

Es posible desactivar este comportamiento estableciendo keep-configuration a no. En este caso, durante el arranque, NetworkManager siempre intenta activar la conexión más adecuada (la con mayor prioridad de autoconexión o, en caso de empate, la que se activó más recientemente).

Nota que cuando NetworkManager se reinicia, almacena el estado previo en /run/NetworkManager; en particular, guarda la UUID de la conexión que estaba activa anteriormente para poder activarla después del reinicio. Por lo tanto, keep-configuration no tiene efecto en el reinicio del servicio.

allowed-connections

Una lista de conexiones que pueden ser activadas en el dispositivo. Véase la sección llamada "Lista de conexiones" para el formato de especificación de una conexión. Si esta opción no se especifica, todas las conexiones pueden ser potencialmente activadas en el dispositivo, siempre que el tipo de conexión y otros ajustes coincidan.

SECCIÓN CONNECTIVITY

Esta sección controla la función de verificación de conectividad de NetworkManager. Esto permite a NetworkManager detectar si el sistema puede realmente acceder a Internet o si está detrás de un portal cautivo.

La verificación de conectividad tiene dos propósitos. Por un lado, expone un estado de conectividad en D-Bus, que otras aplicaciones puedan usar. Por ejemplo, el helper de portal de Gnome usa esto como señal para mostrar la página de inicio de autenticación de un portal cautivo. Por otro lado, el peso de la ruta predeterminada de dispositivos sin conectividad global recibe una penalización de +20000 en la métrica de ruta. Esto tiene el propósito de proporcionar una ruta predeterminada más adecuada para dispositivos que tienen conectividad global. Por ejemplo, cuando se conecta a un portal cautivo y a una red Wi-Fi que está detrás de un portal cautivo, el portal cautivo sigue siendo preferido hasta que se complete el inicio.

Nota que tu distribución podría haber establecido /proc/sys/net/ipv4/conf/*/rp_filter a filtrado estricto. Esto funciona mal con la verificación de conectividad por dispositivo, que usa SO_BINDDEVICE para enviar solicitudes en todos los dispositivos. Una configuración estricta de rp_filter rechazará cualquier respuesta y la verificación de conectividad en todos los puentes de ruta excepto el mejor fallará.

enabled

¿Está activa la verificación de conectividad? Nota que para activar la verificación de conectividad, también debe haber configurado un URI válido. El valor por defecto es true, pero dado que el URI no está definido por defecto, la verificación de conectividad puede estar desactivada. El propósito principal de esta opción es tener un solo encabezado para desactivar la verificación de conectividad. Nota que este ajuste también puede ser establecido en tiempo real mediante la API D-Bus. En este caso, el valor se almacena en el archivo /var/lib/NetworkManager/NetworkManager-intern.conf.

uri

La URI de una página web para solicitar periódicamente cuando se realice la verificación de conectividad. Esta página debe devolver la cabecera "X-NetworkManager-Status" con un valor de "online". Alternativamente, su contenido de cuerpo debe ser "NetworkManager is online". El contenido de cuerpo puede ser controlado mediante la opción de respuesta. Si esta opción es vacía o no está definida, la verificación de conectividad está desactivada.

interval

Especificado en segundos; controla qué tan a menudo se verifica la conectividad cuando hay una conexión de red. Si se establece en 0, la verificación de conectividad está desactivada. Si no está definida, el valor por defecto es 300 segundos.

timeout

Espera en segundos; controla cuánto tiempo espera por una respuesta antes de marcar la conectividad como limitada. Si no está definida, el valor por defecto es 20 segundos.

response

Si se establece, controla qué contenido de cuerpo NetworkManager verifica al solicitar la URI para la verificación de conectividad. Nota que esto solo compara que la respuesta HTTP comience con el texto especificado, no compara exactamente la cadena. Este comportamiento puede cambiar en el futuro, por lo que evita su dependencia. Si no está definida, el contenido por defecto es "NetworkManager is online". Si se establece a vacío, se espera que el servidor HTTP responda con código 204 o no envíe datos.

HOSTNAME CONFIGURATION

The following options are available to configure hostname resolution.

hostname

A string for the hostname to be used by NetworkManager.

lookup

A string for the hostname lookup behavior. Possible values are "auto", "dns", "file", "disabled". "auto" (default) tries to guess the correct behavior. "dns" enforces DNS lookups. "file" enforces /etc/hosts lookups. "disabled" disables hostname lookups.

options

A list of options to be passed to the hostname resolver.

resolve-mode

String indicating how DNS servers retrieved from global configuration and connections should be used. backup - Indicates that they can be freely merged and used for the same purposes. prefer - Forbids DNS servers retrieved from connections to be used for general queries that are not subdomains of domains set by connection. exclusive - Forbids use of connection DNS servers for any query. Currently relevant only for Dnsconfd plugin.

certification-authority

String specifying absolute path to bundle of CA certificates that must be used for validation of certificates presented by DNS servers when encrypted DNS is used. Currently relevant only for Dnsconfd plugin.

GLOBAL-DNS-DOMAIN SECTIONS

Sections with a name starting with the "global-dns-domain-" prefix allow one to define global DNS configuration for specific domains. The part of section name after "global-dns-domain-" specifies the domain name a section applies to (for example, a section could be named "global-dns-domain-foobar.com"). More specific domains have the precedence over less specific ones and the default domain is represented by the wildcard "*". To be valid, global DNS domains must include a section for the default domain "*". When the global DNS domains are valid, the name servers and domains defined globally override the ones from active connections. If any global DNS domain is defined but a [global-dns] section isn't, an empty [global-dns] section is assumed, thus overwriting its connection specific configurations too.

servers

A list of addresses of DNS servers to be used for the given domain. Each server can be specified either as a plain IP address or with a URI syntax. When it is specified as an URI, the following forms are supported:
dns+udp://ADDRESS[:PORT] : DNS
dns+tls://ADDRESS[:PORT][#SERVERNAME] : DNS over TLS

ADDRESS is an IPv4 or IPv6 address. When it is IPv6, it must be enclosed in square brackets ('[' and ']'). When it is a IPv6 link-local address, the address should be followed by a percent sign ('%') and an interface name.

options

A list of domain-specific DNS options. Not used at the moment.

.CONFIG SECTIONS

This is a special section that contains options which apply to the configuration file that contains the option.

enable

Defaults to "true". If "false", the configuration file will be skipped during loading. Note that the main configuration file NetworkManager.conf cannot be disabled. 
# always skip loading the config file
[.config]
enable=false

You can also match against the version of NetworkManager. For example the following are valid configurations:

# only load on version 1.0.6
[.config]
enable=nm-version:1.0.6
# load on all versions 1.0.x, but not 1.2.x
[.config]
enable=nm-version:1.0
# only load on versions >= 1.1.6. This does not match
# with version 1.2.0 or 1.4.4. Only the last digit is considered.
[.config]
enable=nm-version-min:1.1.6
# only load on versions >= 1.2. Contrary to the previous
# example, this also matches with 1.2.0, 1.2.10, 1.4.4, etc.
[.config]
enable=nm-version-min:1.2
# Match against the maximum allowed version. The example matches
# versions 1.2.0, 1.2.2, 1.2.4. Again, only the last version digit
# is allowed to be smaller. So this would not match on 1.1.10.
[.config]
enable=nm-version-max:1.2.6

You can also match against the value of the environment variable NM_CONFIG_ENABLE_TAG, like:

# only load the file when running NetworkManager with
# environment variable "NM_CONFIG_ENABLE_TAG=TAG1"
[.config]
enable=env:TAG1

More then one match can be specified. The configuration will be enabled if one of the predicates matches ("or"). The special prefix "except:" can be used to negate the match. Note that if one except-predicate matches, the entire configuration will be disabled. In other words, a except predicate always wins over other predicates. If the setting only consists of "except:" matches and none of the negative conditions are satisfied, the configuration is still enabled.

# enable the configuration either when the environment variable
# is present or the version is at least 1.2.0.
[.config]
enable=env:TAG2,nm-version-min:1.2
# enable the configuration for version >= 1.2.0, but disable
# it when the environment variable is set to "TAG3"
[.config]
enable=except:env:TAG3,nm-version-min:1.2
# enable the configuration on >= 1.3, >= 1.2.6, and >= 1.0.16.
# Useful if a certain feature is only present since those releases.
[.config]
enable=nm-version-min:1.3,nm-version-min:1.2.6,nm-version-min:1.0.16

PLUGINS

Settings plugins for reading and writing connection profiles. The number of available plugins is distribution specific.

keyfile

The keyfile plugin is the generic plugin that supports all the connection types and capabilities that NetworkManager has. It writes files out in an .ini-style format in /etc/NetworkManager/system-connections. See nm-settings-keyfile(5) for details about the file format.

The stored connection file may contain passwords, secrets and private keys in plain text, so it will be made readable only to root, and the plugin will ignore files that are readable or writable by any user or group other than root. See "Secret flag types" in nm-settings-nmcli(5) for how to avoid storing passwords in plain text.

This plugin is always active, and will automatically be used to store any connections that aren't supported by any other active plugin.

ifcfg-rh

This plugin is now deprecated; it can be used on the Fedora and Red Hat Enterprise Linux distributions to read and write configuration from the standard /etc/sysconfig/network-scripts/ifcfg-* files. It currently supports reading Ethernet, Wi-Fi, InfiniBand, VLAN, Bond, Bridge, and Team connections. Enabling ifcfg-rh implicitly enables ibft plugin, if it is available. This can be disabled by adding no-ibft. See /usr/share/doc/initscripts/sysconfig.txt and nm-settings-ifcfg-rh(5) for more information about the ifcfg file format.

ifupdown

This plugin is used on the Debian and Ubuntu distributions, and reads Ethernet and Wi-Fi connections from /etc/network/interfaces.

This plugin is read-only; any connections (of any type) added from within NetworkManager when you are using this plugin will be saved using the keyfile plugin instead.

ibft, no-ibft

These plugins are deprecated and their selection has no effect. This is now handled by nm-initrd-generator.

ifcfg-suse, ifnet

These plugins are deprecated and their selection has no effect. The keyfile plugin should be used instead.

Device List Format

The configuration options main.no-auto-default, main.ignore-carrier, keyfile.unmanaged-devices, connection*.match-device and device*.match-device select devices based on a list of matchings. Devices can be specified using the following format:

*

Matches every device.

IFNAME

Case sensitive match of interface name of the device. Globbing is not supported.

HWADDR

Match the permanent MAC address of the device. Globbing is not supported

interface-name:IFNAME, interface-name:~IFNAME

Case sensitive match of interface name of the device. Simple globbing is supported with * and ?. Ranges and escaping is not supported.

interface-name:=IFNAME

Case sensitive match of interface name of the device. Globbing is disabled and IFNAME is taken literally.

mac:HWADDR

Match the permanent MAC address of the device. Globbing is not supported

s390-subchannels:HWADDR

Match the device based on the subchannel address. Globbing is not supported

type:TYPE

Match the device type. Valid type names are as reported by "nmcli -f GENERAL.TYPE device show". Globbing is not supported.

driver:DRIVER

Match the device driver as reported by "nmcli -f GENERAL.DRIVER,GENERAL.DRIVER-VERSION device show". "DRIVER" must match the driver name exactly and does not support globbing. Optionally, a driver version may be specified separated by '/'. Globbing is supported for the version.

dhcp-plugin:DHCP

Match the configured DHCP plugin "main.dhcp".

except:SPEC

Negative match of a device. SPEC must be explicitly qualified with a prefix such as interface-name:. A negative match has higher priority then the positive matches above.

If there is a list consisting only of negative matches, the behavior is the same as if there is also match-all. That means, if none of all the negative matches is satisfied, the overall result is still a positive match. That means, "except:interface-name:eth0" is the same as "*,except:interface-name:eth0".

SPEC[,;]SPEC

Multiple specs can be concatenated with commas or semicolons. The order does not matter as matches are either inclusive or negative (except:), with negative matches having higher priority.

Backslash is supported to escape the separators ';' and ',', and to express special characters such as newline ('\n'), tabulator ('\t'), whitespace ('\s') and backslash ('\\'). The globbing of interface names cannot be escaped. Whitespace is not a separator but will be trimmed between two specs (unless escaped as '\s').

Example:

interface-name:em4
mac:00:22:68:1c:59:b1;mac:00:1E:65:30:D1:C4;interface-name:eth2
