Net::DNS::Nameserver(3) Documentación de Perl aportada por el usuario Net::DNS::Nameserver(3)

NOMBRE

Net::DNS::Nameserver - Clase de servidor DNS

SINOPSIS

use Net::DNS::Nameserver;
my $nameserver = Net::DNS::Nameserver->new(
                LocalAddr       => ['::1', '127.0.0.1'],
                LocalPort       => 15353,
                ZoneFile        => 'nombre_archivo'
                );
my $nameserver = Net::DNS::Nameserver->new(
                LocalAddr       => '10.1.2.3',
                LocalPort       => 15353,
                ReplyHandler    => \&manejador_respuesta
                );
$nameserver->start_server($timeout);
$nameserver->stop_server;

DESCRIPCIÓN

Net::DNS::Nameserver ofrece un mecanismo sencillo para la instanciación de objetos de servidor DNS personalizados destinados a proporcionar respuestas de prueba a las consultas provenientes de un cliente de resolución.

No es, ni será jamás, una implementación de servidor DNS de propósito general.

Véase "EJEMPLOS" a continuación para más detalles.

MÉTODOS

new

$nameserver = Net::DNS::Nameserver->new(
                LocalAddr       => ['::1', '127.0.0.1'],
                LocalPort       => 15353,
                ZoneFile        => "nombre_archivo"
                );
$nameserver = Net::DNS::Nameserver->new(
                LocalAddr       => '10.1.2.3',
                LocalPort       => 15353,
                ReplyHandler    => \&manejador_respuesta,
                Verbose         => 1,
                Truncate        => 0
                );

Instancia un objeto Net::DNS::Nameserver. Se genera una excepción si el objeto no pudo ser creado.

Cada instancia se configura utilizando los siguientes argumentos opcionales:

LocalAddr
Dirección IP en la que escuchar. Por defecto, la dirección de bucle local.
LocalPort
Puerto en el que escuchar.
ZoneFile
Nombre del archivo que contiene los RR accedidos utilizando la subrutina interna de manejo de respuestas.
ReplyHandler
Referencia a una subrutina personalizada de manejo de respuestas.
NotifyHandler
Referencia a una subrutina de manejo de respuestas para consultas con el código de operación NOTIFY (RFC1996).
UpdateHandler
Referencia a una subrutina de manejo de respuestas para consultas con el código de operación UPDATE (RFC2136).
Verbose
Informa sobre la actividad interna. Por defecto, 0 (desactivado).
Truncate
Trunca paquetes UDP que son demasiado grandes para la respuesta. Por defecto, 1 (activado).

El atributo LocalAddr puede especificarse alternativamente como un array de direcciones IP a las que escuchar.

La subrutina ReplyHandler recibe el nombre de consulta, la clase de consulta, el tipo de consulta, el host del par, el registro de consulta y el descriptor de conexión. Debe devolver el código de respuesta y referencias a las secciones de respuesta, autoridad y adicionales de la respuesta, o undef para dejar la consulta sin respuesta. Los códigos de respuesta comunes son:

NOERROR
Sin error
FORMERR
Error de formato
SERVFAIL
Fallo del servidor
NXDOMAIN
Dominio inexistente (el nombre no existe)
NOTIMP
No implementado
REFUSED
Consulta rechazada

Para uso avanzado, también puede contener una máscara de encabezado (headermask) que contiene un hashref con la configuración para los bits de encabezado "aa", "ra" y "ad". El argumento tiene el formato: {ad => 1, aa => 0, ra => 1}

Las opciones EDNS pueden especificarse de manera similar usando la máscara de opciones (optionmask): {$optioncode => $valor, $nombreopcion => $valor}

Consulte RFC1035 y el archivo de parámetros DNS de IANA para obtener más información:

El servidor DNS escuchará conexiones UDP y TCP. En Linux y otros sistemas tipo Unix, a los usuarios no privilegiados se les deniega el acceso a los puertos inferiores a 1024.

La funcionalidad de truncamiento de respuestas UDP se introdujo en Net::DNS 0.66. El límite de tamaño se determina por el tamaño EDNS0 anunciado en la consulta, de lo contrario se utiliza 512. Si desea realizar el truncamiento de paquetes usted mismo, debería establecer Truncate=>0 y truncar el paquete de respuesta en el código de ReplyHandler.

start_server

$ns->start_server( <TIMEOUT_IN_SECONDS> );

Inicia un proceso de servidor para cada uno de los sockets UDP y TCP especificados que responde continuamente a las conexiones de los usuarios.

El parámetro de tiempo de espera especifica el tiempo que el servidor permanecerá activo. Si se llama sin parámetro, se aplica un tiempo de espera predeterminado de 10 minutos.

stop_server

$ns->stop_server();

Termina todos los procesos del servidor de manera ordenada.

EJEMPLOS

Ejemplo 1: Script de prueba con servidor DNS incrustado

El siguiente ejemplo es un script de prueba autocontenido que consulta datos de zona DNS servidos por una instancia incrustada de Net::DNS::Nameserver.

use strict;
use warnings;
use Test::More;
plan skip_all => 'Net::DNS::Nameserver no disponible'
                unless eval { require Net::DNS::Nameserver }
                and Net::DNS::Nameserver->can('start_server');
plan tests => 2;
my $resolver = Net::DNS::Resolver->new(
                nameserver => ['::1', '127.0.0.1'],
                port       => 15353
                );

my $ns = Net::DNS::Nameserver->new(
                LocalAddr => [$resolver->nameserver],
                LocalPort => $resolver->port,
                Verbose   => 0,
                ZoneFile  => \*DATA
                ) or die "no se pudo crear el objeto nameserver";
$ns->start_server(10);
my $reply = $resolver->send(qw(example.com SOA));
is( ref($reply), 'Net::DNS::Packet', 'se recibió paquete de respuesta' );
my ($rr) = $reply->answer;
is( $rr->type, 'SOA', 'la respuesta contiene registro SOA' );
$ns->stop_server();
exit;
__DATA__
$ORIGIN example.com.
@       IN SOA  mname rname 2023 2h 1h 2w 1h
www     IN A    93.184.216.34

Ejemplo 2: Servidor DNS personalizado independiente

El siguiente ejemplo escuchará en el puerto 15353 y responderá a todas las consultas de registros A con la dirección IP 10.1.2.3. Todas las demás consultas serán respondidas con NXDOMAIN. Las secciones de autoridad y adicionales se dejan vacías. La variable $peerhost captura la dirección IP del host de origen, de modo que se puede aplicar un filtrado adicional por host.

use strict;
use warnings;
use Net::DNS::Nameserver;
sub reply_handler {
        my ( $qname, $qclass, $qtype, $peerhost, $query, $conn ) = @_;
        my ( $rcode, @ans, @auth, @add );
        print "Recibida consulta de $peerhost a " . $conn->{sockhost} . "\n";
        $query->print;
        if ( $qtype eq "A" && $qname eq "foo.example.com" ) {
                my ( $ttl, $rdata ) = ( 3600, "10.1.2.3" );
                my $rr = Net::DNS::RR->new("$qname $ttl $qclass $qtype $rdata");
                push @ans, $rr;
                $rcode = "NOERROR";
        } elsif ( $qname eq "foo.example.com" ) {
                $rcode = "NOERROR";
        } else {
                $rcode = "NXDOMAIN";

Net::DNS::Nameserver(3pm) — Arch Linux

NAME

Net::DNS::Nameserver - A non-blocking DNS nameserver

SYNOPSIS

    use Net::DNS::Nameserver;
    my $ns = Net::DNS::Nameserver->new(
        LocalPort    => 53,
        ReplyHandler => \&my_reply_handler,
        Verbose      => 1
    ) or die "couldn't create nameserver object";
    $ns->start_server();

DESCRIPTION

The Net::DNS::Nameserver class implements a non-blocking DNS nameserver. It can be used to implement DNS clients that can answer DNS queries in a non-blocking way, or it can be used to implement DNS servers.

The server listens on the specified port for incoming UDP and TCP DNS queries. When a query is received, the ReplyHandler callback is invoked with the query packet and a reference to the nameserver object.

The ReplyHandler is responsible for processing the query and returning the DNS response packet. The nameserver then sends the response back to the client.

METHODS

new()
Constructs a new Net::DNS::Nameserver object.

Arguments are passed as a hash:

LocalPort
The port number to listen on. Defaults to 53.
ListenAddress
The IP address to listen on. Defaults to all interfaces.
ReplyHandler
A reference to a subroutine that will be called to handle incoming queries. The subroutine will be passed the query packet and a reference to the nameserver object.
Verbose
If true, the nameserver will print debugging information to STDERR.
start_server()
Starts the nameserver. This method will block until the server is stopped.
stop_server()
Stops the nameserver.
send()
Sends a DNS response packet to the client.

EXAMPLES

The following example implements a simple DNS server that always returns a SERVFAIL response.

    use Net::DNS::Nameserver;
    use Net::DNS::Packet;
    use Net::DNS::Header;
    use Net::DNS::Question;
    use Net::DNS::RR;
    my $rcode = 0;
    my @ans;
    my @auth;
    my @add;
    my $headermask = Net::DNS::Header->new(
        qr        => 1,
        aa        => 1,
        opcode    => 0,
        qr        => 1,
        rcode     => 2, # SERVFAIL
        qdcount   => 1,
        ancount   => 0,
        nscount   => 0,
        arcount   => 0
    );
    my $optionmask = {};
    sub reply_handler {
        my ($packet, $ns) = @_;
        my $question = $packet->question;
        print STDERR "Received query for '$question'->[name]'\n";
        # Always return SERVFAIL for demonstration purposes
        my $reply = $packet->new;
        $reply->header->set_qr(1);
        $reply->header->set_aa(1);
        $reply->header->set_rcode(2); # SERVFAIL
        # Optionally, you can populate ans, auth, and add arrays here
        # For a SERVFAIL, typically these would be empty.
        return ( $rcode, \@ans, \@auth, \@add, $headermask, $optionmask );
    }
    my $ns = Net::DNS::Nameserver->new(
        LocalPort    => 15353,
        ReplyHandler => \&reply_handler,
        Verbose      => 1
    ) or die "couldn't create nameserver object";
    $ns->start_server(60);
    exit;   # leaving nameserver processes running for 60 seconds

BUGS

Limitations in perl make it impossible to guarantee that replies to UDP queries from Net::DNS::Nameserver are sent from the IP-address to which the query was directed, the source address being chosen by the operating system based upon its notion of "closest address". This limitation is mitigated to some extent by creating a separate socket and subprocess for each IP address.
