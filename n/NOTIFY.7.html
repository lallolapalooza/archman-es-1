NOMBRE

NOTIFY - generar una notificación

SINOPSIS

NOTIFY canal [ , carga_util ]

DESCRIPCIÓN

El comando NOTIFY envía un evento de notificación junto con una cadena opcional de "carga útil" (payload) a cada aplicación cliente que haya ejecutado previamente LISTEN canal para el canal especificado en la base de datos actual. Las notificaciones son visibles para todos los usuarios.

NOTIFY proporciona un mecanismo simple de comunicación entre procesos para una colección de procesos que acceden a la misma base de datos PostgreSQL. Se puede enviar una cadena de carga útil junto con la notificación, y se pueden crear mecanismos de nivel superior para pasar datos estructurados utilizando tablas en la base de datos para pasar datos adicionales del emisor a el/los oyente/s.

La información que se pasa al cliente para un evento de notificación incluye el nombre del canal de notificación, el PID del proceso del servidor de la sesión que notifica y la cadena de carga útil, que es una cadena vacía si no se especificó.

Depende del diseñador de la base de datos definir los nombres de canal que se utilizarán en una base de datos determinada y lo que significa cada uno. Comúnmente, el nombre del canal es el mismo que el nombre de alguna tabla en la base de datos, y el evento de notificación esencialmente significa "Cambié esta tabla, échale un vistazo para ver qué hay de nuevo". Pero ninguna asociación de este tipo es impuesta por los comandos NOTIFY y LISTEN. Por ejemplo, un diseñador de base de datos podría usar varios nombres de canal diferentes para señalar diferentes tipos de cambios en una única tabla. Alternativamente, la cadena de carga útil podría usarse para diferenciar varios casos.

Cuando se utiliza NOTIFY para señalar la ocurrencia de cambios en una tabla particular, una técnica de programación útil es colocar el NOTIFY en un disparador (trigger) de sentencia que se active por actualizaciones de tabla. De esta manera, la notificación ocurre automáticamente cuando la tabla se modifica, y el programador de la aplicación no puede olvidar hacerlo accidentalmente.

NOTIFY interactúa con las transacciones SQL de maneras importantes. En primer lugar, si se ejecuta un NOTIFY dentro de una transacción, los eventos de notificación no se entregan hasta que la transacción se confirma y solo si se confirma. Esto es apropiado, ya que si la transacción se aborta, todos los comandos dentro de ella no han tenido efecto, incluido NOTIFY. Pero puede ser desconcertante si se esperan los eventos de notificación se entreguen de inmediato. En segundo lugar, si una sesión que escucha recibe una señal de notificación mientras está dentro de una transacción, el evento de notificación no se entregará a su cliente conectado hasta justo después de que la transacción se complete (ya sea confirmada o abortada). Nuevamente, la razón es que si una notificación se entregara dentro de una transacción que luego se abortara, uno querría que la notificación se deshiciera de alguna manera; pero el servidor no puede "retirar" una notificación una vez que la ha enviado al cliente. Por lo tanto, los eventos de notificación solo se entregan entre transacciones. El resultado de esto es que las aplicaciones que usan NOTIFY para señalización en tiempo real deben intentar mantener sus transacciones cortas.

Si el mismo nombre de canal se señala varias veces con cadenas de carga útil idénticas dentro de la misma transacción, solo se entrega una instancia del evento de notificación a los oyentes. Por otro lado, las notificaciones con cadenas de carga útil distintas siempre se entregarán como notificaciones distintas. Del mismo modo, las notificaciones de diferentes transacciones nunca se fusionarán en una sola notificación. Excepto por omitir instancias posteriores de notificaciones duplicadas, NOTIFY garantiza que las notificaciones de la misma transacción se entreguen en el orden en que se enviaron. También se garantiza que los mensajes de diferentes transacciones se entreguen en el orden en que se confirmaron las transacciones.

Es común que un cliente que ejecuta NOTIFY también esté escuchando en el mismo canal de notificación. En ese caso, recibirá un evento de notificación, al igual que todas las demás sesiones que escuchan. Dependiendo de la lógica de la aplicación, esto podría resultar en un trabajo inútil, por ejemplo, leer una tabla de base de datos para encontrar las mismas actualizaciones que esa sesión acaba de escribir. Es posible evitar dicho trabajo adicional al notar si el PID del proceso del servidor de la sesión que notifica (suministrado en el mensaje del evento de notificación) es el mismo que el PID de la propia sesión (disponible desde libpq). Cuando son los mismos, el evento de notificación es el propio trabajo que rebota y puede ignorarse.

PARÁMETROS

canal

Nombre del canal de notificación a ser señalado (cualquier identificador).

carga_util

La cadena de "carga útil" a comunicar junto con la notificación. Debe especificarse como un literal de cadena simple. En la configuración predeterminada, debe tener menos de 8000 bytes. (Si se necesitan comunicar datos binarios o grandes cantidades de información, es mejor colocarlos en una tabla de base de datos y enviar la clave del registro.)

NOTAS

Existe una cola que retiene las notificaciones que se han enviado pero que aún no han sido procesadas por todas las sesiones que escuchan. Si esta cola se llena, las transacciones que llaman a NOTIFY fallarán al confirmar. La cola es bastante grande (8 GB en una instalación estándar) y debería ser suficiente para casi todos los casos de uso. Sin embargo, no se puede realizar ninguna limpieza si una sesión ejecuta LISTEN y luego entra en una transacción durante mucho tiempo. Una vez que la cola está medio llena, verá advertencias en el archivo de registro que le indicarán la sesión que está impidiendo la limpieza. En este caso, debe asegurarse de que esta sesión finalice su transacción actual para que la limpieza pueda continuar.

La función pg_notification_queue_usage devuelve la fracción de la cola que está actualmente ocupada por notificaciones pendientes. Consulte la Sección 9.27 para obtener más información.

Una transacción que ha ejecutado NOTIFY no puede prepararse para el commit en dos fases.

pg_notify

Para enviar una notificación, también puede utilizar la función pg_notify(texto, texto). La función toma el nombre del canal como primer argumento y la carga útil como segundo. La función es mucho más fácil de usar que el comando NOTIFY si necesita trabajar con nombres de canal y cargas útiles no constantes.

EJEMPLOS

Configure y ejecute una secuencia de listen/notify desde psql:

LISTEN virtual;
NOTIFY virtual;
Notificación asíncrona "virtual" recibida del proceso del servidor con PID 8448.
NOTIFY virtual, 'Esta es la carga útil';
Notificación asíncrona "virtual" con carga útil "Esta es la carga útil" recibida del proceso del servidor con PID 8448.
LISTEN foo;
SELECT pg_notify('fo' || 'o', 'pay' || 'load');
Notificación asíncrona "foo" con carga útil "payload" recibida del proceso del servidor con PID 14728.

COMPATIBILIDAD

No existe una sentencia NOTIFY en el estándar SQL.
