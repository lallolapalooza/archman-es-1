Net::Server(3) Documentación de Perl aportada por el usuario Net::Server(3)

NOMBRE

Net::Server - Motor de servidor Perl extensible y general

SINOPSIS

#!/usr/bin/perl -w -T
package MyPackage;
use base qw(Net::Server);
sub process_request {
    my $self = shift;
    while (<STDIN>) {
        s/[\r\n]+$//;
        print "Dijiste '$_'\015\012"; # eco básico
        last if /quit/i;
    }
}
MyPackage->run(port => 160, ipv => '*');
# línea de comandos para empezar rápidamente
perl -e 'use base qw(Net::Server); main->run(port => 20208)'
NOTA: a partir de Net::Server 2.005, el valor por defecto para
      ipv es IPv* lo que significa que si no se pasa ningún host, o
      se pasa un nombre de host, se enlazarán sockets IPv4 e IPv6 disponibles.
      Puedes forzar solo IPv4 añadiendo una configuración ipv => 4
      en cualquiera de las media docena de formas en que te permitimos
      especificarlo.

* Soporte completo de IPv6
* Sockets SSL funcionales y https (con y sin IO::Socket::SSL)
* Modo de Servidor Único
* Modo de Servidor Inetd
* Modo Simple Preforking (PreForkSimple)
* Modo Gestionado Preforking (PreFork)
* Modo Forking
* Modo de Multiplexación usando un solo proceso
* Aceptación de múltiples puertos en modos Single, Preforking y Forking
* Daemon HTTP básico (soporta IPv6, SSL, logs estilo Apache completos)
* Daemon PSGI básico
* Aceptación/recepción simultánea en sockets tcp/udp/unix, ssl/tcp e IPv4/IPv6
* Manejo seguro de señales en modo Fork/PreFork evita problemas de señales en Perl
* Ganchos personalizables por el usuario

* Escrito en Perl
* Protección contra desbordamiento de búfer
* Flujo de proceso limpio
* Extensibilidad

DESCRIPCIÓN

"Net::Server" es un motor de servidor Perl genérico y extensible.

"Net::Server" intenta ser un servidor genérico como "Net::Daemon" y "NetServer::Generic". Incluye la capacidad de ejecutarse como un proceso inetd ("Net::Server::INET"), un servidor de conexión única ("Net::Server" o "Net::Server::Single"), un servidor de forking ("Net::Server::Fork"), un servidor preforking que mantiene un número constante de hijos preforkeados ("Net::Server::PreForkSimple"), o como un servidor preforking gestionado que mantiene el número de hijos basándose en la carga del servidor ("Net::Server::PreFork"). En todos los tipos excepto el tipo inetd, el servidor proporciona la capacidad de conectarse a uno o a múltiples puertos de servidor.

Los tipos de servidor adicionales son posibles a través de "personalidades" o subclases de "Net::Server". Al mover los múltiples tipos de servidores fuera de la clase principal "Net::Server", el concepto "Net::Server" se extiende fácilmente a otros tipos (en el futuro cercano, nos gustaría añadir una personalidad de "Thread").

"Net::Server" toma prestados varios conceptos del Servidor Web Apache. "Net::Server" utiliza "ganchos" para permitir que servidores personalizados como SMTP, HTTP, POP3, etc. se superpongan a la clase base "Net::Server". Además, la clase "Net::Server::PreFork" toma prestados conceptos de min_start_servers, max_servers y min_waiting servers. "Net::Server::PreFork" también utiliza el concepto de un accept serializado con flock al aceptar en múltiples puertos (PreFork puede elegir entre flock, IPC::Semaphore y pipe para controlar la serialización).

PERSONALIDADES

"Net::Server" está construido alrededor de una clase común (Net::Server) y se extiende utilizando subclases, o "personalidades". Cada personalidad hereda, sobrescribe o mejora los métodos base de la clase base.

Incluidas con el paquete Net::Server hay varias personalidades básicas, cada una con su propio uso.

Fork
Se encuentra en el módulo Net/Server/Fork.pm (ver Net::Server::Fork). Este servidor se enlaza a uno o más puertos y luego espera una conexión. Cuando se recibe una solicitud de cliente, el padre hace un fork de un hijo, que luego maneja al cliente y sale. Esto es bueno para servicios moderadamente solicitados.
INET
Se encuentra en el módulo Net/Server/INET.pm (ver Net::Server::INET). Este servidor está diseñado para usarse con inetd. Los métodos "pre_bind", "bind", "accept" y "post_accept" están todos sobrescritos ya que estos servicios son manejados por el demonio INET.
MultiType
Se encuentra en el módulo Net/Server/MultiType.pm (ver Net::Server::MultiType). Este servidor no tiene funcionalidad de servidor propia. Está diseñado para servidores que necesitan una forma sencilla de cambiar entre diferentes personalidades. Se pueden dar múltiples parámetros "server_type" y Net::Server::MultiType ciclara hasta que encuentre una clase que pueda usar.
Multiplex
Se encuentra en el módulo Net/Server/Multiplex.pm (ver Net::Server::Multiplex). Este servidor se enlaza a uno o más puertos. Utiliza IO::Multiplex para multiplexar entre esperar nuevas conexiones y esperar entrada en conexiones actualmente establecidas. Esta personalidad está diseñada para ejecutarse como un solo proceso sin hacer fork. El método "process_request" nunca se usa, pero se usa la devolución de llamada "mux_input" en su lugar (ver también IO::Multiplex). Ver examples/samplechat.pl para un ejemplo que utiliza la mayoría de las características de Net::Server::Multiplex.
PreForkSimple
Se encuentra en el módulo Net/Server/PreFork.pm (ver Net::Server::PreFork). Este servidor se enlaza a uno o más puertos y luego hace fork de "max_servers" procesos hijos. El servidor se asegurará de que en cualquier momento haya siempre "max_servers" disponibles para recibir una solicitud de cliente. Cada uno de estos hijos procesará hasta "max_requests" conexiones de cliente. Este tipo es bueno para un sitio con mucha carga que puede dedicar procesos max_server sin importar la carga. Debería escalar bien para la mayoría de las aplicaciones. La aceptación de múltiples puertos se logra usando flock, IPC::Semaphore o pipe para serializar los hijos. La serialización también puede activarse para un solo puerto con el fin de evitar un SO que no permita que múltiples hijos acepten al mismo tiempo. Para una discusión adicional sobre la serialización ver Net::Server::PreFork.
PreFork
Se encuentra en el módulo Net/Server/PreFork.pm (ver Net::Server::PreFork). Este servidor se enlaza a uno o más puertos y luego hace fork de "min_servers" procesos hijos. El servidor se asegurará de que en cualquier momento haya al menos "min_spare_servers" pero no más de "max_spare_servers" disponibles para recibir una solicitud de cliente, hasta "max_servers". Cada uno de estos hijos procesará hasta "max_requests" conexiones de cliente. Este tipo es bueno para un sitio con mucha carga, y debería escalar bien para la mayoría de las aplicaciones. La aceptación de múltiples puertos se logra usando flock, IPC::Semaphore o pipe para serializar los hijos. La serialización también puede activarse para un solo puerto con el fin de evitar un SO que no permita que múltiples hijos acepten al mismo tiempo. Para una discusión adicional sobre la serialización ver Net::Server::PreFork.
Single
Todos los métodos vuelven a Net::Server. Esta personalidad se proporciona solo como paralelismo para Net::Server::MultiType.
HTTP
Se encuentra en el módulo Net/Server/HTTP.pm (ver Net::Server::HTTP). Este servidor extiende Net::Server::PreFork para proporcionar un servidor HTTP básico. Está diseñado para servir contenido estático, pero puede ser extendido para servir contenido dinámico. Soporta IPv6, SSL y un formato de registro similar al de Apache.
PSGI
Se encuentra en el módulo Net/Server/PSGI.pm (ver Net::Server::PSGI). Este servidor extiende Net::Server::PreFork para proporcionar un servidor PSGI básico. Puede ser utilizado para desplegar aplicaciones PSGI.

EJEMPLO

Aquí hay un ejemplo sencillo que demuestra cómo usar "Net::Server" para crear un servidor de eco básico:

#!/usr/bin/perl -w -T
package EchoServer;
use base qw(Net::Server);
sub process_request {
    my $self = shift;
    # $self->log(LOG_INFO => "Cliente conectado desde " . $self->client_addr());
    while (my $line = $self->get_line()) {
        $self->send_line("Eco: $line");
        last if $line =~ /quit/i;
    }
    # $self->log(LOG_INFO => "Cliente desconectado desde " . $self->client_addr());
}
EchoServer->run(
    port    => 1500,
    ipv     => '\*', # Escucha en todas las interfaces
    log_level => LOG_INFO,
    log_file => '/tmp/echoserver.log',
);

Para probar este servidor, puedes ejecutarlo y luego conectarte a él desde otro terminal usando telnet o netcat:

telnet localhost 1500

Escribe algunos mensajes y presiona Enter. El servidor debería responder con cada mensaje precedido por "Eco: ". Escribe "quit" para desconectar.

MÉTODOS

Cada personalidad de "Net::Server" implementa un conjunto de métodos que controlan el comportamiento del servidor. Los métodos clave incluyen:

run()
El método de clase principal para iniciar el servidor. Acepta argumentos de configuración como port, ipv, server_type, etc. Ejemplo: MyServer->run(port => 8080, server_type => 'Fork')
init_server()
Se llama una vez al inicio del servidor para configurar el entorno. Aquí es donde se pueden establecer las opciones de registro, manejar los permisos, etc.
pre_bind()
Se llama antes de enlazar el socket del servidor. Útil para realizar operaciones previas al enlace, como cambiar el directorio de trabajo o el usuario.
bind()
Enlaza el socket del servidor al puerto y dirección especificados.
post_bind()
Se llama inmediatamente después de enlazar el socket. Útil para configurar opciones de socket después del enlace.
accept()
Espera una conexión entrante y devuelve un nuevo manejador de socket para la conexión.
post_accept()
Se llama inmediatamente después de aceptar una conexión. Útil para realizar operaciones posteriores a la aceptación, como establecer la configuración del cliente.
run_client()
Maneja el ciclo de vida de una conexión de cliente individual. Llama a process_request() para manejar la lógica de la aplicación.
process_request()
Este es el método principal donde se implementa la lógica específica de la aplicación del servidor. Lee datos del cliente, los procesa y envía respuestas. Debe ser sobrescrito por las subclases.
shutdown()
Se llama cuando el servidor se está apagando. Útil para realizar tareas de limpieza.
log()
Un método de utilidad para registrar mensajes. Admite diferentes niveles de registro.
get_line()
Un método de utilidad para leer una línea del socket del cliente (incluyendo el carácter de nueva línea).
send_line()
Un método de utilidad para enviar una línea al socket del cliente (añade automáticamente un retorno de carro y salto de línea).

CONFIGURACIÓN

"Net::Server" es altamente configurable a través de varios parámetros pasados al método run() o mediante un archivo de configuración (ver la documentación de Net::Server::Config).

Algunos parámetros de configuración comunes:

port
El número de puerto en el que escuchar. Puede ser un número o un nombre de servicio (por ejemplo, 'http').
ipv
Especifica la interfaz de red en la que escuchar. Puede ser 4 (solo IPv4), 6 (solo IPv6), '*' o undef (todas las interfaces disponibles IPv4 e IPv6), o una dirección IP específica (por ejemplo, '192.168.1.100').
server_type
Especifica la personalidad del servidor a utilizar (por ejemplo, 'Fork', 'PreFork', 'Single', etc.).
log_level
El nivel de detalle para el registro (por ejemplo, LOG_INFO, LOG_DEBUG).
log_file
La ruta del archivo donde escribir los registros.
pid_file
La ruta del archivo PID. Útil para gestionar el proceso del servidor.
max_servers
(Para personalidades de forking/preforking) El número máximo de procesos hijos que se pueden crear.
max_requests
(Para personalidades de forking/preforking) El número máximo de solicitudes que cada proceso hijo manejará antes de salir.
user
El usuario al que cambiar después de enlazar el socket.
group
El grupo al que cambiar después de enlazar el socket.
chroot
El directorio al que hacer chroot después de enlazar el socket.

ACCESO AL SOCKET

Una vez iniciado, Net::Server se encargará de vincularse al puerto y esperar las conexiones. Una vez recibida una conexión, Net::Server aceptará en el socket y almacenará el resultado (la conexión del cliente) en $self->{server}->{client}. Esta propiedad es un Socket bendecido en las clases IO::Socket. Los servidores UDP son ligeramente diferentes, ya que realizarán una llamada a recv en lugar de una llamada a accept.

Para facilitar la programación, durante la fase post_accept, STDIN y STDOUT se abren a la conexión del cliente. Esto permite que los programas se escriban usando <STDIN> y `print "out\n"` para imprimir en la conexión del cliente. UDP requerirá el uso de una llamada a `->send`.

EJEMPLO DE CÓDIGO

El siguiente es un servidor muy simple. La funcionalidad principal ocurre en la llamada al método process_request, como se muestra a continuación. Tenga en cuenta el uso de tiempos de espera para evitar ataques de Denegación de Servicio al leer. (Otros ejemplos de uso de "Net::Server" pueden, o se incluirán, con esta distribución).

#!/usr/bin/perl -w -T
package MiPaquete;
use strict;
use base qw(Net::Server::PreFork); # cualquier personalidad servirá
MiPaquete->run;
# sobrescribir el manejador de eco predeterminado
sub process_request {
    my $self = shift;
    eval {
        local $SIG{'ALRM'} = sub { die "¡Tiempo Agotado!\n" };
        my $timeout = 30; # dar al usuario 30 segundos para escribir algunas líneas
        my $previous_alarm = alarm($timeout);
        while (<STDIN>) {
            s/\r?\n$//;
            print "Dijiste '$_'\r\n";
            alarm($timeout);
        }
        alarm($previous_alarm);
    };
    if ($@ =~ /tiempo agotado/i) {
        print STDOUT "Tiempo Agotado.\r\n";
        return;
    }
}
1;

La ejecución de este archivo desde la línea de comandos invocará un Net::Server utilizando la personalidad PreFork. Al construir una capa de servidor sobre Net::Server, es importante utilizar características como los tiempos de espera para prevenir ataques de Denegación de Servicio.

Net::Server viene con un servidor de eco incorporado por defecto. Puede probarlo simplemente ejecutando lo siguiente desde la línea de comandos:

net-server

Si quisiera probar otro sabor, podría intentar

net-server PreFork

Si quisiera probar un servidor HTTP básico, podría usar

net-server HTTP

O si quisiera probar un CGI que está escribiendo, podría usar

net-server HTTP --app ../../mycgi.cgi

ARGUMENTOS

Hay al menos cinco formas posibles de pasar argumentos a Net::Server. Son pasar al método new, pasar en la línea de comandos, pasar parámetros a run, usar un archivo de configuración, devolver valores en el método default_values o configurar los valores en post_configure_hook.

El método "options" se utiliza para determinar qué argumentos buscará el servidor y se puede utilizar para extender los parámetros analizados. Cualquier argumento encontrado en la línea de comandos, parámetros pasados a `run` y argumentos encontrados en el archivo de configuración (`conf_file`) se compararán con las claves de la plantilla de opciones. Cualquier parámetro de línea de comandos que no coincida se dejará en su lugar y podrá ser procesado posteriormente por el servidor en los diversos hooks (buscando en @ARGV). Los argumentos pasados a `new` prevalecerán automáticamente sobre cualquier otra opción (esto se puede usar si desea prohibir que un usuario pase otros argumentos).

Los argumentos consisten en pares clave-valor. En la línea de comandos, estos pares siguen el estilo POSIX de "--key value" o "--key=value", y también "key=value". En el archivo de configuración, la forma de pasar parámetros se puede mostrar mejor mediante la siguiente expresión regular: ($key,$val)=~/^(\w+)\s+(\S+?)\s+$/. Pasar argumentos al método `run` se hace de la siguiente manera: "<Net::Server->run(key1 => 'val1')>>". Pasar argumentos a través de un objeto preconstruido se puede mostrar mejor en el siguiente código:

#!/usr/bin/perl -w -T
package MiPaquete;
use strict;
use base qw(Net::Server);
my $server = MiPaquete->new({
    key1 => 'val1',
});
$server->run;

Los cinco métodos para pasar argumentos pueden usarse al mismo tiempo. Una vez que se establece un argumento, no se sobrescribe si otro método pasa el mismo argumento. "Net::Server" buscará argumentos en el siguiente orden:

1) Argumentos pasados al método C<new>.
2) Argumentos pasados en la línea de comandos.
3) Argumentos pasados al método C<run>.
4) Argumentos pasados a través de un archivo de configuración.
5) Argumentos establecidos en el método C<default_values>.

Además, los siguientes hooks están disponibles:

1) Argumentos establecidos en el configure_hook (ocurre después de new
   pero antes de que se verifiquen las otras áreas).
2) Argumentos establecidos y validados en el post_configure_hook
   (ocurre después de que se verifiquen todas las otras áreas).

Cada uno de estos niveles anulará los parámetros del mismo nombre especificados en niveles posteriores. Por ejemplo, especificar `--setsid=0` en la línea de comandos anulará un valor de `"setsid 1"` en el archivo de configuración.

Tenga en cuenta que el método `configure_hook` no devuelve valores para establecer, sino que está ahí para permitir la configuración de valores antes de que se llame al método `configure`.

Los pares clave/valor utilizados por el servidor son eliminados por el proceso de configuración para que las capas de servidor encima de "Net::Server" puedan pasar y leer sus propios parámetros.

AÑADIR ARGUMENTOS PERSONALIZADOS

Es posible agregar sus propios parámetros personalizados a los analizados por Net::Server. El siguiente código muestra cómo se hace:

sub options {
    my $self     = shift;
    my $prop     = $self->{'server'};
    my $template = shift;
    # configurar opciones en las clases padre
    $self->SUPER::options($template);
    # añadir una opción de valor único
    $prop->{'my_option'} ||= undef;
    $template->{'my_option'} = \ $prop->{'my_option'};
    # añadir una opción de múltiples valores
    $prop->{'an_arrayref_item'} ||= [];
    $template->{'an_arrayref_item'} = $prop->{'an_arrayref_item'};
}

Sobrescribir el método "options" permite agregar sus propios campos personalizados. Se pasa un hashref de plantilla, que luego debe modificarse para contener sus campos personalizados. Los campos destinados a recibir un único valor escalar deben contener una referencia al escalar de destino. Los campos destinados a recibir múltiples valores deben hacer referencia al arrayref de destino correspondiente.

Usted es responsable de validar sus opciones personalizadas una vez que hayan sido analizadas. El `post_configure_hook` es un buen lugar para realizar su validación.

Algunos correos electrónicos han preguntado por qué usamos este método de "plantilla". La idea es que usted está creando la estructura de datos para almacenar los valores y también está creando una forma de obtener los valores en la estructura de datos. La plantilla es la forma de llevar los valores a la estructura de datos del servidor. Una de las posibilidades (que probablemente no se usa mucho) es que al permitirle especificar el mapeo, podría construir una estructura de datos anidada, aunque los argumentos pasados sean planos. También le permite configurar alias para sus nombres.

Por ejemplo, una estructura básica podría verse así:

$prop = $self->{'server'}
$prop->{'my_custom_option'} ||= undef;
$prop->{'my_custom_array'}  ||= [];
$template = {
    my_custom_option => \ $prop->{'my_custom_option'},
    mco              => \ $prop->{'my_custom_option'}, # alias
    my_custom_array  => $prop->{'my_custom_array'},
    mca              => $prop->{'my_custom_array'}, # alias
};
$template->{'mco2'} = $template->{'mco'}; # otra forma de alias

Pero también podría tener datos más complejos:

$prop = $self->{'server'};
$prop->{'one_layer'} = {
    two_layer => [
        undef,
        undef,
    ],
};
$template = {
    param1 => \ $prop->{'one_layer'}->{'two_layer'}->[0],
    param2 => \ $prop->{'one_layer'}->{'two_layer'}->[1],
};

Este es, por supuesto, un ejemplo forzado, pero muestra que puede obtener los datos de los argumentos planos pasados a cualquier tipo de estructura que necesite, con solo un poco de esfuerzo.

conf_file

Hay dos formas de especificar un lugar por defecto para conf_file. La primera es pasar el valor por defecto al método run, como:

MiServidor->run({
   conf_file => '/etc/mi_servidor.conf',
});

Si el usuario final pasa --conf_file=/etc/su_servidor.conf, el valor será reemplazado.

La segunda forma fue añadida en la versión 0.96. Usa el método default_values como:

sub default_values {
    return {
        conf_file => '/etc/mi_servidor.conf',
    }
}

Este método tiene la ventaja de poder ser sobreescrito en el método run.

Si no quieres que el usuario pueda especificar un conf_file, puedes pasar conf_file al método new cuando crees tu objeto:

MiServidor->new({
   conf_file => '/etc/mi_servidor.conf',
})->run;

Si lo pasas así, el valor pasado a new superará cualquier otro valor pasado.

log_level
Rango de 0 a 4 en nivel. Especifica qué nivel de error se registrará. "0" significa que el registro está apagado. "4" significa muy detallado. Estos niveles deben correlacionarse con los niveles de syslog. El valor por defecto es 2. Estos niveles correlacionan con los niveles de syslog según los pares clave/valor siguientes: 0=>'err', 1=>'warning', 2=>'notice', 3=>'info', 4=>'debug'.
log_file
Nombre del archivo de registro o sistema de registro a escribir. Si no se especifica un nombre y el write_to_log_hook no se sobrescribe, el log se envía a STDERR. El valor por defecto es undef.

El log_file puede también ser el nombre de una clase de registro conectable de Net::Server. Net::Server viene con Sys::Syslog y Log::Log4perl. Si el log_file parece ser un nombre de módulo, se agregará "Net::Server::Log::" al frente y se requerirá. La clase debe proporcionar un método "initialize" que devuelva una función única que se usará para el registro. Esta función devuelta se pasará el nivel de mensaje y el mensaje.

Si se usa el nombre mágico "Sys::Syslog", todos los registros se realizarán mediante el módulo Net::Server::Log::Sys::Syslog. Si se usa syslog, los parámetros "syslog_logsock", "syslog_ident", y "syslog_logopt" y "syslog_facility" también pueden definirse. Véase Net::Server::Log::Sys::Syslog.

Si se usa el nombre mágico "Log::Log4perl", todos los registros se dirán al sistema Log4perl. Si se usa, se pueden definir "log4perl_conf", "log4perl_poll", "log4perl_logger". Véase Net::Server::Log::Log::Log4per.

Si se especifica un "log_file" o si se establece "setsid", se abrirán automáticamente STDIN y STDOUT a /dev/null y STDERR se abrirá a STDOUT. Esto evitará que cualquier salida se deposite en la terminal.

log_function
Puede tomar un coderef o nombre de método que se llama cuando ocurre un evento de registro. Se pasarán el nivel del mensaje y el mensaje del evento.

Nota: Las funciones dependientes de stdout no funcionarán durante process_request si tie_stdout está activado (como en Net::Server::HTTP).

pid_file
Nombre del archivo donde se almacena el PID del proceso padre. Generalmente se aplica solo a servidores que se bifurcan. El valor por defecto es none (undef).
port
Véase Net::Server::Proto para ejemplos adicionales de configuración.

Puerto local en el que se adjuntará. Si es un puerto bajo, el proceso debe iniciar como root. Si se especifican múltiples puertos, todos se abrirán al iniciar el servidor. Puede ser de la forma "host:port/proto", "host:port/proto/ipv", "host:port", "port/proto", o "port", donde host representa un nombre de host en la máquina local, y port representa el número de puerto (por ejemplo, "80") o la designación del servicio (por ejemplo, "http"), donde ipv representa la versión de protocolo (IPv4 o IPv6 o IPv*) y proto representa el protocolo a utilizar. Véase Net::Server::Proto. Las siguientes son algunas cadenas de puertos válidas:

20203                            # puerto solo
localhost:20203                  # host y puerto
localhost:http                   # localhost con puerto 80
localhost:20203/tcp              # host, puerto, protocolo
localhost:20203/tcp/IPv*         # host, puerto, protocolo y familia
localhost, 20203, tcp, IPv*      # mismo
localhost | 20203 | tcp | IPv*   # mismo
localhost:20203/IPv*             # vincular cualquier interfaz local para IPv4 o 6 (por defecto)
localhost:20203/IPv4/IPv6        # vincular localhost en IPv4 y 6 (falla si no puede hacer ambos)
*:20203                          # vincular todas las interfaces locales

Adicionalmente, cuando se pasa el código (no en línea y no en configuración), el puerto puede pasarse como un hashref o arrayhashref de información:

port => {
    host  => 'localhost',
    port  => '20203',
    ipv   => 6,     # solo IPv6
    proto => 'udp', # protocolo UDP
}
port => [{
    host  => '*',
    port  => '20203',
    ipv   => 4,     # solo IPv4
    proto => 'tcp', # (por defecto)
}, {
    host  => 'localhost',
    port  => '20204',
    ipv   => '*',      # por defecto - todas las interfaces IPv4 e IPv6 enlazadas a localhost
    proto => 'ssleay', # o ssl - usando SSL
}],

Un host explícito en una especificación de puerto sobrescribe una dirección de enlace por defecto (un "host", véase a continuación). La parte host puede estar entre corchetes, pero cuando es una dirección IPv6 numérica debe estar entre corchetes para evitar ambigüedad en el análisis de un número de puerto, por ejemplo: "[::1]:80". Sin embargo, también puedes usar barras verticales, espacios en blanco o comas para separar estos. Nota: El host y el número de puerto deben ir primero.

Si el protocolo no se especifica, proto se utilizará como el "proto" especificado en los argumentos. Si "proto" no se especifica, se utilizará por defecto "tcp". Si host no se especifica, host se utilizará como el "host" especificado en los argumentos. Si "host" no se especifica, se utilizará por defecto "*". El puerto por defecto es 20203. La configuración pasada a new o run puede ser un escalar con un número de puerto o un array de puertos. Si "ipv" no se especifica, se utilizará por defecto "*" (cualquier dirección resuelta bajo IPv4 o IPv6).

Si estás trabajando con sockets Unix, también puedes especificar "socket_file|unix" o "socket_file|type|unix" donde type es SOCK_DGRAM o SOCK_STREAM.

En sistemas que lo soportan, un valor de puerto de 0 puede usarse para hacer que el sistema operativo asigne un puerto automáticamente. El valor del puerto asumido se almacenará en la propiedad NS_port del objeto Net::Server::Proto::TCP y también estará disponible en el método sockport. Cuando el servidor procesa una solicitud, la propiedad $self->{server}->{sockport} contiene el puerto conectado.

host
Host local o dirección en la que se adjuntará el puerto. Si se da un valor de '*' se asignará el puerto a todas las direcciones disponibles en la máquina. El argumento "host" proporciona un host local por defecto si el argumento "port" omite una especificación de host. Véase Net::Server::Proto. Véase IO::Socket. La configuración pasada a new o run puede ser un escalar con un solo host o un array de hosts - si el array de hosts es más corto que el array de puertos, el último registro será usado para reforzar el array de hosts hasta el tamaño del array de puertos.

Si se pasa una dirección IPv4, se creará un socket IPv4. Si se pasa una dirección IPv6, se creará un socket IPv6. Si se pasa un nombre de host, Net::Server verá el valor de ipv (por defecto IPv4) para determinar qué tipo de socket crear. Opcionalmente, la especificación de ipv puede pasarse como parte del nombre de host.

host => "127.0.0.1",  # una dirección IPv4
host => "::1",        # una dirección IPv6
host => 'localhost',  # direcciones que coinciden con localhost (por defecto cualquier IPv4 y/ó IPv6)
host => 'localhost/IPv*',  # mismo
ipv  => 6,
host => 'localhost',  # direcciones que coinciden con localhost (solo IPv6)
ipv  => 4,
host => 'localhost',  # direcciones que coinciden con localhost (solo IPv4)
ipv  => 'IPv4 IPv6',
host => 'localhost',  # direcciones que coinciden con localhost (requiere IPv6 y IPv4)
host => '*',          # cualquier interfaz local (cualquier IPv6 o IPv4)
host => '*/IPv*',     # mismo (cualquier IPv6 o IPv4)
ipv  => 4,
host => '*',          # cualquier interfaz IPv4 local
proto
Véase Net::Server::Proto. Protocolo a utilizar al enlazar puertos. Véase IO::Socket. Desde la versión 2.0, Net::Server soporta tcp, udp, unix, unixdgram, ssl y ssleay. Otros tipos necesitarán ser añadidos más tarde (o se podrán usar módulos personalizados que extiendan la clase Net::Server::Proto). La configuración pasada a new o run puede ser un escalar con un solo proto o un array de protos - si el array de protos es más corto que el array de puertos, el último registro será usado para reforzar el array de protos hasta el tamaño del array de puertos.

Adicionalmente, el proto puede también contener la especificación de ipv.

ipv (IPv4 y IPv6)
Véase Net::Server::Proto.

Este parámetro se usa para especificar el tipo de socket a crear. El valor por defecto es IPv4.

log_level
Rango de 0 a 4 en nivel. Especifica qué nivel de error se registrará. "0" significa que el registro está apagado. "4" significa muy detallado. Estos niveles deben correlacionarse con los niveles de syslog. El valor por defecto es 2. Estos niveles correlacionan con los niveles de syslog según los pares clave/valor siguientes: 0=>'err', 1=>'warning', 2=>'notice', 3=>'info', 4=>'debug'.

IPv6 ya está disponible en Net::Server. Se utilizará automáticamente si se proporciona una dirección IPv6, o si la propiedad ipv se establece explícitamente en IPv6, o si la propiedad ipv se deja como valor predeterminado de IPv*. Esto es un cambio significativo con respecto a la versión 2.004 y anteriores, donde el valor predeterminado era IPv4. Sin embargo, el comportamiento anterior causaba confusión en hosts solo con IPv6 y en hosts que solo tenían entradas IPv6 para un nombre de host local. Intentar pasar una dirección IPv4 cuando ipv está configurado en 6 (solo 6 - no * o 4) generará un error.

localhost:20203 # usará IPv6 si hay una entrada correspondiente para localhost
                # también usará IPv4 si hay una entrada v4 correspondiente para localhost
localhost:20203:IPv*  # lo mismo (predeterminado)
localhost:20203:IPv6  # usará IPv6
[::1]:20203           # usará IPv6 (dirección estilo IPv6)
localhost:20203:IPv4  # usará IPv4
127.0.0.1:20203       # usará IPv4 (dirección estilo IPv4)
localhost:20203:IPv4:IPv6 # se enlazará a v4 y v6 - falla de lo contrario
# o como un hashref
port => {
    host => "localhost",
    ipv  => 6, # solo enlaza IPv6
}
port => {
    host => "localhost",
    ipv  => 4, # solo enlaza IPv4
}
port => {
    host => "::1",
    ipv  => "IPv6", # lo mismo que pasar "6"
}
port => {
    host => "localhost/IPv*",       # cualquier IPv4 o IPv6
}
port => {
    host => "localhost IPv4 IPv6",  # debe crear ambos
}

En muchas soluciones propuestas de Net::Server, IPv* estaba habilitado por defecto. Para las versiones 2.000 a 2.004, se usó el valor predeterminado anterior de IPv4. Hemos intentado facilitar la configuración de IPv4, IPv6 o IPv*. Si no desea o no necesita IPv6, simplemente establezca ipv en 4, pase IPv4 en la especificación del puerto, establezca $ENV{'IPV'}=4; antes de ejecutar el servidor, establezca $ENV{'NO_IPV6'}, o desinstale IO::Socket::IP y/o IO::Socket::INET6.

En mi máquina local, el siguiente comando produce la siguiente salida:

perl -e 'use base qw(Net::Server); main->run(host => "localhost")'
Resolved [localhost]:20203 to [::1]:20203, IPv6
Resolved [localhost]:20203 to [127.0.0.1]:20203, IPv4
Binding to TCP port 20203 on host ::1 with IPv6
Binding to TCP port 20203 on host 127.0.0.1 with IPv4

Mi máquina local tiene IPv6 habilitado y hay entradas para localhost tanto en IPv6 ::1 como en IPv4 127.0.0.1. También podría elegir enlazar puertos explícitamente en lugar de depender de ipv => "*" para resolverlos, como en el siguiente ejemplo:

perl -e 'use base qw(Net::Server); main->run(port => [20203,20203], host => "localhost", ipv => [4,6])'
Binding to TCP port 20203 on host localhost with IPv4
Binding to TCP port 20203 on host localhost with IPv6

Existe un caso especial de uso de host => "*" así como de ipv => "*". El método Net::Server::Proto::_bindv6only se utiliza para verificar la configuración del sistema de "sysctl -n net.ipv6.bindv6only" (o net.inet6.ip6.v6only). Si esta configuración es falsa, entonces un socket IPv6 escuchará la dirección IPv4 correspondiente. Por ejemplo, la dirección [::] (equivalente IPv6 de INADDR_ANY) también escuchará a 0.0.0.0. La dirección ::FFFF:127.0.0.1 (IPv6) también escuchará a 127.0.0.1 (IPv4). En este caso, solo se creará un socket porque manejará ambos casos (se devuelve un error si se intenta escuchar en ambas direcciones cuando bindv6only es falso).

Sin embargo, si net.ipv6.bindv6only (o equivalente) es verdadero, entonces un nombre de host (como *) que se resuelve tanto en una entrada IPv4 como en una IPv6 resultará en un socket IPv4 y un socket IPv6.

En mi máquina Linux, que por defecto tiene net.ipv6.bindv6only=0, la siguiente salida se produce.

perl -e 'use base qw(Net::Server); main->run(host => "*")'
Resolved [*]:8080 to [::]:8080, IPv6
Not including resolved host [0.0.0.0] IPv4 because it will be handled by [::] IPv6
Binding to TCP port 8080 on host :: with IPv6

Si ejecuto "sudo /sbin/sysctl -w net.ipv6.bindv6only=1", la siguiente salida se produce.

perl -e 'use base qw(Net::Server); main->run(host => "*")'
Resolved [*]:8080 to [0.0.0.0]:8080, IPv4
Resolved [*]:8080 to [::]:8080, IPv6
Binding to TCP port 8080 on host 0.0.0.0 with IPv4
Binding to TCP port 8080 on host :: with IPv6

BSD difiere de Linux y generalmente utiliza por defecto net.inet6.ip6.v6only=0. Si no se puede determinar en tu sistema operativo, se establecerá por defecto en falso y el mensaje de registro cambiará de "it will be handled" a "it should be handled" (si tienes una forma de verificarlo que no consuma muchos recursos en tu plataforma, siéntete libre de enviarme un correo electrónico). Asegúrate de revisar los registros mientras pruebas tu servidor para asegurarte de que has enlazado los puertos deseados. Siempre puedes pasar especificaciones de puertos IPv4 e IPv6 explícitas e individuales si lo necesitas. Por ejemplo, si tu sistema tiene interfaces IPv4 e IPv6 pero solo deseas enlazar a entradas IPv6, entonces deberías usar un nombre de host de [::] en lugar de [*].

Si bindv6only (o equivalente) es falso, y recibes una conexión IPv4 en un puerto IPv6 enlazado, la representación textual de la dirección IPv4 del par generalmente tendrá la forma de una dirección IPv6 mapeada a IPv4, por ejemplo, "::FFFF:127.0.0.1".

Se eligió el parámetro ipv porque no entra en conflicto con ningún otro uso existente, es muy similar a ipv4 o ipv6, permite que el código del usuario no necesite conocer Socket::AF_INET o Socket6::AF_INET6 o Socket::AF_UNSPEC, y es corto.

listen
Ver IO::Socket. No se usa con el protocolo udp (o UNIX SOCK_DGRAM).
ipv6_package
Net::Server::Proto intentará determinar la clase de socket apropiada a usar si se necesita un socket v6. Por defecto, intentará IO::Socket::IP primero, y luego IO::Socket::INET6. Especificar este paquete permite usar un paquete específico (ten en cuenta que IO::Socket::SSL, utilizado por Proto::SSL, realiza su propia determinación del paquete de socket ipv6).
reverse_lookups
Especifica si se debe buscar el nombre de host de la IP conectada. La información se almacena en caché en el objeto servidor bajo la propiedad "peerhost". El valor predeterminado es no usar reverse_lookups (undef).

Puede establecerse a los valores "double", "double-detail", "double-autofail", o "double-debug" para establecer double_reverse_lookups.

double_reverse_lookups
Si se establece, también establece reverse_lookups.

Lo mismo que establecer reverse_lookups a "double". Busca las IPs a las que se resuelve el nombre de host para asegurarse de que la IP de conexión sea una de esas IPs.

Establece peerhost_rev como un hashref de direcciones IP a las que se resolvió el nombre durante get_client_info.

Si se establece double_reverse_lookups, el método double_reverse_lookup se llama durante el método allow_deny. Al método double_reverse_lookup se le pasan:

addr  - la dirección IPv4 o IPv6
host  - el nombre de host al que se resolvió addr
addrs - el hashref de direcciones IP a las que se resolvió host
orig  - la dirección original sin filtrar

Hace que allow_deny devuelva falso si no hay nombre de host, no hay IPs inversas, o si una de las direcciones IP no coincide con la dirección IP de conexión. Envía un mensaje de nivel de registro 3.

Puede establecer double_reverse_lookups a uno de los siguientes para ajustar el registro:

detail   - agrega addrs a los mensajes de fallo
autofail - falla en cada conexión y registra
debug    - registra información de direcciones (pero no falla) para conexiones exitosas

Los siguientes comandos de una línea pueden ayudar a depurar:

net-server HTTP --reverse_lookups=double-debug --log_level=3
# curl localhost:8080 en otra ventana
2022/11/30-22:16:45 CONNECT TCP Peer: "[::ffff:127.0.0.1]:44766" (localhost)  Local: "[::ffff:127.0.0.1]:8080"
2022/11/30-22:16:45 Double reverse debug:  addr: 127.0.0.1,  host: localhost,  addrs: (127.0.0.1),  orig_addr: ::ffff:127.0.0.1

El double_reverse_lookup se llama antes de ejecutar cualquier regla de allow/deny.

allow/deny
Puede especificarse varias veces. Contiene expresiones regulares para comparar con incoming peeraddr o peerhost (si se ha habilitado reverse_lookups). Si se proporcionan opciones allow o deny, el cliente entrante debe coincidir con un allow y no coincidir con un deny, o la conexión del cliente se cerrará. Por defecto son arrays vacíos.
cidr_allow/cidr_deny
Puede especificarse varias veces. Contiene un bloque CIDR para comparar con incoming peeraddr. Si se proporcionan opciones cidr_allow o cidr_deny, el cliente entrante debe coincidir con un cidr_allow y no coincidir con un cidr_deny, o la conexión del cliente se cerrará. Por defecto son arrays vacíos.
chroot
Directorio al que cambiar (chroot) después de que el proceso de enlace haya ocurrido y el servidor siga ejecutándose como root. Por defecto es undef.
user
ID de usuario o nombre de usuario al que convertirse después de que haya ocurrido el proceso de enlace. Por defecto es "nobody." Si desea que el servidor se ejecute como root, deberá especificar "user" igual a "root".
group
ID de grupo o nombre de grupo al que convertirse después de que haya ocurrido el proceso de enlace. Por defecto es "nobody." Si desea que el servidor se ejecute como root, deberá especificar "group" igual a "root".

Especifica si el servidor debe hacer fork después del método bind para liberarse de la línea de comandos. Por defecto es undef. El proceso también se ejecutará en segundo plano si se establece "setsid".

no_close_by_child
Booleano. Especifica si un hijo debe cerrar la conexión.

ARGUMENTS

allow_deny_child
Boolean. Default undef (not set). If set to 0, the child process may NOT initiate a denial of service attack on the parent. If set to 1, the child may signal the parent that it does not have permission to shutdown the entire server process. If set to 0, the child may NOT signal the parent to shut down all children. Default is undef (not set).
no_client_stdout
Booleano. Por defecto es undef (no establecido). Especifica que STDIN y STDOUT no se abrirán en el manejador del cliente una vez que se haya aceptado una conexión. Por defecto, Net::Server abrirá STDIN y STDOUT en el socket del cliente, lo que facilita a muchos tipos de scripts leer directamente y escribir directamente en el socket utilizando los métodos normales de impresión y lectura. Deshabilitar esto es útil en clientes que pueden estar abriendo sus propias conexiones a STDIN y STDOUT.

Esta opción no tiene ningún efecto en STDIN y STDOUT, que tienen una propiedad de cliente mágica que está vinculada a los STDIN y STDOUT ya abiertos.

leave_children_open_on_hup
Booleano. Por defecto es undef (no establecido). Si se establece, el progenitor no intentará cerrar los procesos hijos si el progenitor recibe una señal HUP. El progenitor volverá a enlazar el puerto abierto y comenzará a rastrear un nuevo conjunto de hijos.

Los hijos de un servidor Fork saldrán después de su solicitud actual. Los hijos de un servidor de tipo Prefork terminarán la solicitud actual y luego saldrán.

Nota: el progenitor recién reiniciado iniciará un nuevo conjunto de servidores en servidores fork. El nuevo progenitor intentará rastrear a los hijos del progenitor anterior, pero los canales de comunicación personalizados (tuberías abiertas del hijo al progenitor anterior) ya no estarán disponibles para los procesos hijos anteriores. Los nuevos procesos hijos seguirán conectándose correctamente al nuevo progenitor.

sig_passthrough
Por defecto es ninguno. Permite pasar las señales solicitadas a los hijos. Acepta un solo nombre de señal, una lista de nombres separada por comas o una referencia de matriz de nombres de señales. Primero envía las señales a los hijos antes de llamar a cualquier señal registrada actualmente con ese nombre.
tie_client_stdout
Por defecto es undef. Si se establece, utilizará la interfaz enlazada de Net::Server::TiedHandle para STDIN y STDOUT. Esta interfaz permite que SSL y SSLEAY funcionen. También permite interceptar lecturas y escrituras a través de tied_stdin_callback y tied_stdout_callback.
tied_stdin_callback
Por defecto es undef. Se llama durante una lectura de datos de STDIN si se ha establecido tie_client_stdout, o si el método tie_stdout del manejador del cliente devuelve verdadero. La devolución de llamada es entonces responsable de llamar a ese método en el manejador o de realizar alguna otra operación de entrada.

Por defecto es undef. Se llama durante una escritura de datos a STDOUT si se ha establecido tie_client_stdout, o si el método tie_stdout del manejador del cliente devuelve verdadero. Se le pasa la conexión del cliente, el nombre del método que se llamaría y los argumentos que se están pasando. PROPIEDADES

Todos los "ARGUMENTOS" enumerados anteriormente se convierten en propiedades del objeto del servidor bajo el mismo nombre. Estas propiedades, así como otras propiedades internas, están disponibles durante los hooks y otras llamadas a métodos.

La estructura de un objeto Net::Server se muestra a continuación:

$self = bless({
    server => {
        key1 => 'val1',
        # más clave/valor
    },
}, 'Net::Server');

Esta estructura fue elegida para que todas las propiedades relacionadas con el servidor estén agrupadas bajo una única clave del hashref del objeto. Esto es para que otros objetos puedan superponerse a la clase del objeto Net::Server y aún tener un espacio de nombres bastante limpio en el hashref.

Puede obtener y establecer propiedades de dos maneras. La forma sugerida es acceder directamente a las propiedades a través de

my $val = $self->{server}->{key1};

El acceso directo a las propiedades acelerará el proceso del servidor, aunque algunos considerarían esto un mal estilo. Se ha proporcionado una segunda forma para los tipos orientados a objetos que creen en los métodos. La segunda forma consiste en los siguientes métodos:

my $val = $self->get_property( 'key1' );
my $self->set_property( key1 => 'val1' );

Se permiten cambiar las propiedades en cualquier momento con precaución (por favor, no elimine la propiedad de sock o cerrará la conexión del cliente).

ARCHIVO DE CONFIGURACIÓN

"Net::Server" permite el uso de un archivo de configuración para leer parámetros del servidor. El formato de este archivo de configuración son simples pares clave-valor. Los comentarios y las líneas en blanco se ignoran.

  #-------------- archivo test.conf --------------
  ### usuario y grupo al que convertirse
  user        alguien
  group       todos
  # ¿registro?
  log_file    /var/log/servidor.log
  log_level   3
  pid_file    /tmp/servidor.pid
  # directiva opcional de syslog
  # se usa en lugar de log_file arriba
  #log_file       Sys::Syslog
  #syslog_logsock unix
  #syslog_ident   miservidor
  #syslog_logopt  pid|cons
  # control de acceso
  allow       .+\.(net|com)
  allow       dominio\.com
  deny        a.+
  cidr_allow  127.0.0.0/8
  cidr_allow  192.0.2.0/24
  cidr_deny   192.0.2.4/30
  # ¿poner el proceso en segundo plano?
  background  1
  # puertos a enlazar (esto debería enlazar
  # 127.0.0.1:20205 en IPv6 y
  # localhost:20204 en IPv4)

FLUJO DEL PROCESO

El flujo del proceso está escrito de una manera abierta, fácil de anular y fácil de enganchar. El flujo básico se muestra a continuación. Este es el flujo del método "$self->run".

$self->configure_hook;
$self->configure(@_);
$self->post_configure;
$self->post_configure_hook;
$self->pre_bind;
$self->bind;
$self->post_bind_hook;
$self->post_bind;
$self->pre_loop_hook;
$self->loop;
### rutinas dentro de un $self->loop estándar
# $self->accept;
# $self->run_client_connection;
# $self->done;
$self->pre_server_close_hook;
$self->server_close;

Luego el servidor sale.

Durante la fase de procesamiento del cliente ("$self->run_client_connection"), lo siguiente representa el flujo del programa:

$self->post_accept;
$self->get_client_info;
$self->post_accept_hook;
if ($self->allow_deny
    && $self->allow_deny_hook) {
    $self->process_request;
} else {
    $self->request_denied_hook;
}
$self->post_process_request_hook;
$self->post_process_request;
$self->post_client_connection_hook;

El método allow_deny llama a $self->double_reverse_lookup si las búsquedas inversas dobles están habilitadas.

El proceso luego se repite y espera la próxima conexión. Para una discusión más profunda, por favor lea el código.

Durante la fase de cierre del servidor ("$self->server_close"), lo siguiente representa el flujo del programa:

$self->close_children;  # si los hay
$self->post_child_cleanup_hook;
if (Reiniciando servidor) {
    $self->restart_close_hook();
    $self->hup_server;
}
$self->shutdown_sockets;
$self->server_exit;

MÉTODOS PRINCIPALES DEL SERVIDOR

"$self->run"
Este método incorpora el flujo principal del proceso. Este flujo se enumera anteriormente.

El método run puede llamarse de cualquiera de las siguientes maneras.

MyPackage->run(port => 20201);
MyPackage->new({port => 20201})->run;
my $obj = bless {server=>{port => 20201}}, 'MyPackage';
$obj->run;

El método ->run típicamente debería ser la última llamada a método en un script de inicio de servidor (el servidor saldrá al final del método ->run).

"$self->configure"
Este método intenta leer las configuraciones de la línea de comandos, de la llamada al método run, o de un archivo de configuración especificado (el archivo de configuración puede especificarse mediante parámetros pasados, o en los valores predeterminados). Todos los parámetros configurados se almacenan luego en la propiedad {"server"} del objeto Server.
"$self->post_configure"
El hook post_configure inicia el arranque del servidor. Durante la ejecución de este método, se verifican las instancias de servidor en ejecución, se crean los archivos pid, se crean los archivos de registro, se inicializa Sys::Syslog (según sea necesario), se pone en segundo plano el proceso y el servidor cierra STDIN y STDOUT (según sea necesario).
"$self->pre_bind"
Este método se utiliza para inicializar todos los objetos de socket utilizados por el servidor.
"$self->bind"
Este método realmente se enlaza a los sockets inicializados (o se vuelve a enlazar si el servidor ha sido HUPed).
"$self->post_bind"
Durante este método, se pierden los privilegios. Las señales INT, TERM y QUIT se configuran para ejecutar server_close. Sig PIPE se establece en IGNORE. Sig CHLD se establece en sig_chld. Y sig HUP se establece para llamar a sig_hup.

En las personalidades Fork, PreFork y PreFork simple, estas señales se registran utilizando Net::Server::SIG para permitir el manejo seguro de señales.

"$self->loop"
Durante esta fase, el servidor acepta conexiones entrantes. El comportamiento de cómo ocurre la aceptación y si un proceso hijo maneja la conexión se controla según el tipo de personalidad de Net::Server que esté utilizando el servidor.

Net::Server y Net::Server solo aceptan una conexión a la vez.

Net::Server::INET ejecuta una conexión y luego sale (para ser utilizado por daemons inetd o xinetd).

Net::Server::MultiPlex permite que un proceso maneje simultáneamente múltiples conexiones (pero requiere reescribir el código process_request para operar de una manera más "similar a paquetes").

Net::Server::Fork crea un nuevo proceso hijo para cada conexión entrante.

Net::Server::PreForkSimple inicia un número fijo de procesos que todos aceptan conexiones entrantes.

Net::Server::PreFork inicia un número base de procesos hijos que todos aceptan en la entrada

MÉTODOS DE CONTROL DEL SERVIDOR

"$self->configure"
Este método se llama al comienzo de la ejecución del servidor para configurar todos los parámetros y llamar a los hooks. Si no se proporcionan parámetros de línea de comandos, entonces se pasan los parámetros de configuración del archivo. Si se proporcionan parámetros de línea de comandos, estos anulan los parámetros del archivo de configuración.
"$self->run"
Este método inicia el servidor. Crea el objeto de servidor y llama a los métodos `configure`, `pre_startup` y `loop`. Este método se utiliza para ejecutar el servidor en primer plano.
"$self->pre_startup"
Este método se llama inmediatamente antes de que el servidor comience a aceptar conexiones. Se puede utilizar para realizar tareas de configuración adicionales antes de que el servidor comience a procesar solicitudes.
"$self->loop"
Este método es el bucle principal del servidor. Escucha las conexiones entrantes y las pasa al método `run_client_connection`. El servidor limita el número de procesos en ejecución en función del número de solicitudes entrantes (similar al concepto de cómo Apache controla sus procesos hijos en un servidor PreFork).
"$self->server_close"
Este método se llama una vez que se ha señalado al servidor que debe terminar, o que debe reiniciarse (a través de HUP), o que el método `loop` ha finalizado.

Este método se encarga de limpiar los procesos hijos restantes, establecer las banderas apropiadas en los sockets (para HUPing), cerrar el registro y luego cerrar los sockets abiertos.

Opcionalmente, se le puede pasar un valor de salida que se pasará a la llamada a `server_exit`.

"$self->server_exit"
Este método se llama al final de `server_close`. Llama a `exit`, pero puede ser anulado para realizar otras acciones. En este punto, todos los servicios deben estar apagados.

Opcionalmente, se le puede pasar un valor de salida que se pasará a la llamada `exit`.

MÉTODOS PRINCIPALES DE CONEXIÓN DEL CLIENTE

"$self->run_client_connection"
Este método se ejecuta después de que el servidor ha aceptado y recibido una conexión de cliente. El flujo completo del proceso se enumera anteriormente en FLUJOS DE PROCESO. Este método se encarga de manejar cada conexión de cliente.
"$self->post_accept"
Este método abre STDIN y STDOUT al socket del cliente. Esto permite que cualquiera de los métodos durante la fase `run_client_connection` imprima directamente en el socket del cliente y lea directamente de él.
"$self->get_client_info"
Este método busca información sobre la conexión del cliente, como la dirección IP, el tipo de socket y el nombre de host (según sea necesario).

Establece lo siguiente en $self->{'server'} (tenga en cuenta que estos nombres no necesariamente corresponden a los nombres de las bibliotecas de IO::Socket:

sockaddr     - Dirección IP legible por humanos a la que se conectó
sockport     - Puerto local al que se conectó
peeraddr     - Dirección IP legible por humanos de la fuente remota (IPv6 o IPv4)
peerport     - Puerto de origen de la conexión
peerhost     - Dirección IP resuelta a nombre de host (si es posible)
peerhost_rev - Hashref de IPs de la búsqueda inversa de peerhost - solo se establece si double_reverse_lookups
"$self->allow_deny"
Este método utiliza las reglas definidas en los parámetros de configuración `allow` y `deny` para determinar si se debe aceptar la dirección IP.
"$self->double_reverse_lookup"
Se llama si el valor `double_reverse_lookups` está establecido o si `reverse_lookups` está establecido en "double". Utiliza el hashref `peerhost_rev` para verificar que la IP de la conexión sea válida para el nombre de host. Consulte la configuración de `double_reverse_lookups`.
"$self->process_request"
Este método está diseñado para manejar toda la comunicación con el cliente. En este punto, STDIN y STDOUT están abiertos al cliente, la dirección IP ha sido verificada. El servidor puede interactuar con la conexión del cliente según la API o el protocolo que esté implementando el servidor. Tenga en cuenta que la implementación de ejemplo utiliza STDIN y STDOUT y no funcionará si se establece la bandera `no_client_stdout`.

Este es el método principal que se debe anular.

El método predeterminado implementa un servidor de eco simple que repetirá todo lo que se envíe. Saldrá del hijo si se envía "quit" y saldrá del servidor si se envía "exit".

A partir de la versión 2.000, el manejador del cliente se pasa como argumento.

"$self->post_process_request"
Este método se utiliza para limpiar la conexión del cliente y manejar la contabilidad de padres/hijos para los servidores de bifurcación.

HOOKS

"Net::Server" proporciona una serie de "hooks" que permiten que los servidores construidos sobre "Net::Server" respondan en diferentes niveles de ejecución sin tener que llamar a la clase "SUPER" de los métodos integrados principales. La ubicación de los hooks se puede ver en la sección FLUJO DE PROCESO.

Casi todos los métodos de hook predeterminados no hacen nada. Para usar un hook, simplemente necesita anular el método en su subclase. Por ejemplo, para agregar su propio `post_configure_hook` podría hacer algo como lo siguiente:

paquete MiServidor;
sub post_configure_hook {
    mi $self = shift;
    mi $prop = $self->{'server'};
    # hacer alguna validación aquí
}

Lo siguiente describe los hooks disponibles en la clase Net::Server simple (otros como Fork o PreFork tienen hooks adicionales).

"$self->configure_hook()"
Este hook tiene lugar inmediatamente después de que se llama al método "->run()". Este hook permite la configuración del objeto antes de que tenga lugar cualquier configuración integrada. Esto permite una configurabilidad personalizada.
"$self->post_configure_hook()"
Este hook ocurre justo después de leer los parámetros de configuración e iniciar el registro y la creación del archivo pid. También ocurre antes de que se llamen los métodos "->pre_bind()" y "->bind()". Este hook permite verificar los parámetros de configuración.
"$self->post_bind_hook()"
Este hook ocurre justo después del proceso de enlace y justo antes de que ocurran el chroot, el cambio de usuario o el cambio de grupo. En este punto, el proceso seguirá ejecutándose como el usuario que inició el servidor.
"$self->pre_loop_hook()"
Este hook ocurre después de que han ocurrido el chroot, el cambio de usuario y el cambio de grupo. Permite la preparación antes de que comience el bucle.
"$self->can_read_hook()"
Este hook ocurre después de que un socket se vuelve legible en una solicitud `accept_multi_port` (`accept_multi_port` se utiliza si hay varios puertos enlazados para aceptar, o si el parámetro de configuración "multi_port" está establecido en verdadero). Este hook está destinado a permitir el procesamiento de manejadores arbitrarios agregados al IO::Select utilizado para `accept_multi_port`. Estos manejadores podrían haberse agregado durante el `post_bind_hook`. No se agrega soporte interno para procesar estos manejadores o agregarlos a IO::Socket. Se debe tener cuidado con la cantidad de tiempo que ocurre durante el `can_read_hook`, ya que un tiempo de respuesta largo hará que el servidor sea susceptible a ataques DOS. Un valor de retorno verdadero indica que el Servidor no debe pasar el manejador legible a las fases `post_accept` y `process_request`.

En general, se sugiere que se busquen otras vías para enviar mensajes a través de sockets no creados por Net::Server.

"$self->post_accept_hook()"
Este hook ocurre después de que un cliente se ha conectado al servidor. En este punto, STDIN y STDOUT están mapeados al socket del cliente. Este hook ocurre antes del procesamiento de la solicitud.
"$self->allow_deny_hook()"
Este hook permite la verificación de información de IP y host más allá de la rutina "$self->allow_deny()". Si este hook devuelve 1, la solicitud del cliente será procesada, de lo contrario, se denegará el procesamiento de la solicitud.

A partir de la versión 2.000, la conexión del cliente se pasa como argumento.

"$self->request_denied_hook()"
Este hook ocurre si se ha realizado el "$self->allow_deny()" o el "$self->allow_deny_hook()".
"$self->post_process_request_hook()"
Este hook ocurre después del procesamiento de la solicitud, pero antes de que se haya cerrado la conexión del cliente.
"$self->post_client_connection_hook"
Este es un hook final que ocurre al final del método `run_client_connection`. En este punto, todos los demás métodos y hooks que se ejecutarán durante `run_client_connection` han finalizado y la conexión del cliente ya se ha cerrado.

ítem "$self->other_child_died_hook($pid)"

Net::Server toma el control del manejo de señales y la limpieza de procesos hijos; esto hace que sea difícil saber cuándo termina un proceso hijo si ese proceso hijo no fue iniciado por Net::Server. Si Net::Server detecta que otro proceso hijo muere que no inició, activará este hook con el PID del proceso terminado.

"$self->pre_server_close_hook()"
Este hook ocurre antes de que el servidor comience a cerrarse.
"$self->write_to_log_hook"
Este hook maneja la escritura en archivos de registro. El hook predeterminado es escribir en STDERR, o en el nombre de archivo contenido en el parámetro "log_file". Los argumentos que se pasan son un nivel de registro de 0 a 4 (4 siendo muy detallado) y una línea de registro. Si `log_file` es igual a "Sys::Syslog", entonces el registro irá a Sys::Syslog y omitirá el `write_to_log_hook`.
"$self->fatal_hook"
Este hook ocurre cuando el servidor ha encontrado un error irrecuperable. Los argumentos que se pasan son el mensaje de error, el paquete, el archivo y el número de línea. El hook puede cerrar el servidor, pero se sugiere que simplemente regrese y utilice las funciones de cierre integradas.
"$self->post_child_cleanup_hook"
Este hook ocurre en el proceso del servidor padre después de que todos los hijos han sido cerrados y justo antes de que el servidor se reinicie o salga. Está destinado a la limpieza adicional de información. En este punto, los archivos `pid_files` y `lockfiles` aún existen.
"$self->restart_open_hook"
Este hook ocurre si un servidor ha sido HUPed (reiniciado a través de la señal HUP). Ocurre justo antes de volver a abrir los `filenos` de los sockets que ya estaban abiertos.
"$self->restart_close_hook"
Este hook ocurre si un servidor ha sido HUPed (reiniciado a través de la señal HUP). Ocurre justo antes de reiniciar el servidor a través de `exec`.
"$self->child_init_hook()"
Este hook se llama durante los servidores de bifurcación. También se llama durante `run_dequeue`. Se ejecuta justo después de la bifurcación y después de que se hayan limpiado las señales. Si es un proceso de dequeue, se pasará la cadena 'dequeue' como argumento.

Si sus procesos hijos necesitarán números aleatorios, este hook es un buen lugar para inicializar `srand` (los procesos bifurcados mantienen la misma semilla aleatoria a menos que se cambie).

sub child_init_hook {
    # de perldoc -f srand
    srand(time ^ $$ ^ unpack "%L*", `ps axww | gzip -f`);
}

HOOKS

"$self->child_init_hook()"
Called by child process when it is first created. This is after the fork, but before the child begins its work.
"$self->child_pre_run_hook()"
Called by child process just before the child calls the run method. This is after the fork, but before the child begins its work.
"$self->child_accept_hook()"
Called by child process when it has accepted a client connection (prior to calling the run method).
"$self->configure_hook"
Called after the configuration is loaded, but before the server starts. This can be used to modify configuration values or perform other setup actions. This hook is called in the parent process.
"$self->post_configure_hook"
Called after the configuration is loaded and after the server has been configured (e.g. sockets opened). This hook is called in the parent process.
"$self->init_hook"
Called after the server object is created, but before any configuration is loaded. This hook is called in the parent process.
"$self->pre_fork_hook"
Called by the parent process just before a child is forked. This can be used for setup that needs to happen before the fork, but doesn't need to be duplicated in the child.
"$self->register_child($pid, $type)"
Called by the parent process when a child has been forked. Type will be one of dequeue, fork, prefork, or preforksimple depending on where the child was created.
"$self->child_finish_hook()"
Similar to the child_init_hook, but ran when the forked process is about to finish up.

OTHER METHODS

"$self->default_values"
Allow for returning configuration values that will be used if no other value could be found.

Should return a hashref.

sub default_values {
    return {
        port => 20201,
    };
}
"$self->handle_syslog_error"
Called when log_file is set to 'Sys::Syslog' and an error occurs while writing to the syslog. It is passed two arguments, the value of $@, and an arrayref containing the arguments that were passed to the log method when the error occurred.
"$self->log"
Parameters are a log_level and a message.

If log_level is set to 'Sys::Syslog', the parameters may alternately be a log_level, a format string, and format string parameters. (The second parameter is assumed to be a format string if additional arguments are passed along). Passing arbitrary format strings to Sys::Syslog will allow the server to be vulnerable to exploit. The server maintainer should make sure that any string treated as a format string is controlled.

# assuming log_file = 'Sys::Syslog'
$self->log(1, "My Message with %s in it");
# sends "%s", "My Message with %s in it" to syslog
$self->log(1, "My Message with %s in it", "Foo");
# sends "My Message with %s in it", "Foo" to syslog

If log_file is set to a file (other than Sys::Syslog), the message will be appended to the log file by calling the write_to_log_hook.

If the log_file is Sys::Syslog and an error occurs during write, the handle_syslog_error method will be called and passed the error exception. The default option of handle_syslog_error is to die - but could easily be told to do nothing by using the following code in your subclassed server:

sub handle_syslog_error {}

It the log had been closed, you could attempt to reopen it in the error handler with the following code:

sub handle_syslog_error {
    my $self = shift;
    $self->open_syslog;
}
"$self->new"
As of Net::Server 0.91 there is finally a "new" method. This method takes a class name and an argument hashref as parameters. The argument hashref becomes the "server" property of the object. 
package MyPackage;
use base qw(Net::Server);
my $obj = MyPackage->new({port => 20201});
# same as
my $obj = bless {server => {port => 20201}}, 'MyPackage';
"$self->open_syslog"
Called during post_configure when the log_file option is set to 'Sys::Syslog'. By default it use the parsed configuration options listed in this document. If more custom behavior is desired, the method could be overridden and Sys::Syslog::openlog should be called with the custom parameters.
"$self->shutdown_sockets"
This method will close any remaining open sockets. This is called at the end of the server_close method.

RESTARTING

Each of the server personalities (except for INET), support restarting via a HUP signal (see "kill -l"). When a HUP is received, the server will close children (if any), make sure that sockets are left open, and re-exec using the same commandline parameters that initially started the server. (Note: for this reason it is important that @ARGV is not modified until "->run" is called).

The Net::Server will attempt to find out the commandline used for starting the program. The attempt is made before any configuration files or other arguments are processed. The outcome of this attempt is stored using the method "->commandline". The stored commandline may also be retrieved using the same method name. The stored contents will undoubtedly contain Tainted items that will cause the server to die during a restart when using the -T flag (Taint mode). As it is impossible to arbitrarily decide what is taint safe and what is not, the individual program must clean up the tainted items before doing a restart.

sub configure_hook{
    my $self = shift;
    ### see the contents
    my $ref  = $self->commandline;
    use Data::Dumper;
    print Dumper $ref;
    ### arbitrary untainting - VERY dangerous
    my @untainted = map {/(.+)/;$1} @$ref;
    $self->commandline(\@untainted)
}

SHUTDOWN

Each of the Fork and PreFork personalities support graceful shutdowns via the QUIT signal. When a QUIT is received, the parent will signal the children and then wait for them to exit.

All server personalities support the normal TERM and INT signal shutdowns.

HOT DEPLOY

Since version 2.000, the Fork and PreFork personalities have accepted the TTIN and TTOU signals. When a TTIN is received, the max_servers is increased by 1. If a TTOU signal is received the max_servers is decreased by 1. This allows for adjusting the number of handling processes without having to restart the server.

If the log_level is set to at 3, then the new value is displayed in the logs.

NOMBRE

Net::Server

SINOPSIS

Use Net::Server para crear un servidor.

CARACTERÍSTICAS

Características de Net::Server:

  • Servidor multihilo
  • Soporte para IPv4 e IPv6
  • Soporte para múltiples backends
  • Soporte para E/S asíncrona
  • Soporte para programación orientada a eventos
  • Soporte para manejo de señales
  • Soporte para hooks personalizados
  • Soporte para configuración dinámica
  • Soporte para despliegue en caliente
  • Soporte para reinicio

DESCRIPCIÓN

Net::Server es una implementación de servidor que proporciona una forma simple y eficiente de crear un servidor en Perl. Soporta tanto IPv4 como IPv6, y puede ser configurado para usar diferentes backends. También soporta E/S asíncrona y programación orientada a eventos, haciéndolo adecuado para aplicaciones de alto rendimiento.

CÓDIGO DE EJEMPLO

Código de ejemplo para Net::Server:


use Net::Server;

my $server = Net::Server->new(
    listen => '0.0.0.0:8080',
    server => 'my_server',
);

$server->run();
