Net::Server::Multiplex(3) Documentación Perl contribuida por el usuario Net::Server::Multiplex(3)

NOMBRE

Net::Server::Multiplex - multiplexiona varias conexiones dentro de un mismo proceso

SINOPSIS

package MiMultiplexor;
use base qw(Net::Server::Multiplex);
sub mux_input {
    #...código...
}
__PACKAGE__->run();

DESCRIPCIÓN

Esta personalidad está diseñada para manejar múltiples conexiones dentro de un mismo proceso. Solo debe usarse con protocolos que se garantice que pueden responder rápidamente paquete por paquete. Si determinar una respuesta puede llevar mucho tiempo o un período de tiempo desconocido, todas las demás conexiones establecidas se bloquearán hasta que la respuesta se complete. Si esta condición pudiera ocurrir alguna vez, esta personalidad probablemente no debería usarse.

Toma algunas características agradables de Net::Server (como la configuración del socket de escucha del servidor, el procesamiento de archivos de configuración, el manejo seguro de señales, el manejo conveniente de STDIN/STDOUT al estilo inet, las funciones de registro, la demonización y el seguimiento de pids, y la capacidad de reinicio -SIGHUP) y algunas características agradables de IO::Multiplex (IO con búfer automático y objetos por descriptor de archivo) y las combina para una interfaz fácil de usar.

Vea examples/samplechat.pl distribuido con Net::Server para un servidor de chat simple que utiliza varias de estas características.

FLUJO DEL PROCESO

El flujo del proceso está escrito de una manera abierta, fácil de anular y fácil de enganchar. El flujo básico se muestra a continuación.

  $self->configure_hook;
  $self->configure(@_);
  $self->post_configure;
  $self->post_configure_hook;
  $self->pre_bind;
  $self->bind;
  if (Reiniciando servidor) {
      $self->restart_open_hook();
  }
  $self->post_bind_hook;
  $self->post_bind;
  $self->pre_loop_hook;
  $self->loop; # Básicamente solo ejecuta IO::Multiplex::loop
  # Para rutinas dentro de un $self->loop
  # Ver PROCESAMIENTO DEL CLIENTE a continuación
  $self->pre_server_close_hook;
  $self->post_child_cleanup_hook;
  $self->server_close;
  if (Reiniciando servidor) {
      $self->restart_close_hook();
      $self->hup_server;
      # Repetir proceso nuevamente comenzando con configure_hook
}

Luego, el servidor sale.

PROCESAMIENTO DEL CLIENTE

Lo siguiente representa el flujo del programa de procesamiento del cliente:

$self->{server}->{client} = Net::Server::Proto::TCP->accept();  # NOTA: Multiplexionado con mux_input() abajo
if (se ha pasado el tiempo de comprobación para descargar) {
    $self->run_dequeue();
}
$self->get_client_info;
$self->post_accept_hook; # Estilo Net::Server
if ($self->allow_deny
    && $self->allow_deny_hook) {
  # (Nunca se llama a $self->process_request() estilo Net::Server.)
  # Se crea un objeto único específico del cliente
  # para todos los métodos mux_* a partir de este punto.
  $self = __PACKAGE__->new($self, client);
  $self->mux_connection; # Estilo IO::Multiplex
  for (cada paquete recibido) {
    $self->mux_input;  # NOTA: Multiplexionado con accept() arriba
  }
} else {
  $self->request_denied_hook;
  # Nótese que si allow_deny o allow_deny_hook falla, entonces
  # new(), mux_connection(), y mux_input() nunca se llamarán.
  # mux_eof() y mux_close() aún se llamarán, pero usando un
  # objeto de devolución de llamada de socket de escucha común en lugar de un objeto único específico del cliente.
}
$self->mux_eof;
$self->post_process_request_hook;
$self->mux_close;

Este proceso luego se repite, multiplexando entre el **accept()** para la siguiente conexión y **mux_input()** cuando llega entrada para evitar bloquear cualquiera de ellos.

ENGANCHES

Los métodos *_hook mencionados anteriormente están destinados a ser anulados con sus propias subrutinas si desea proporcionar funcionalidad adicional.

El método **loop()** de Net::Server ha sido anulado para ejecutar la rutina de bucle de IO::Multiplex en su lugar. Los métodos Net::Server pueden acceder al objeto IO::Multiplex en "$self->{mux}" si lo desean. Los métodos IO::Multiplex pueden acceder al objeto Net::Server en "$self->{net_server}" si lo desean.

El método **process_request()** nunca se usa con esta personalidad.

Los otros ganchos y métodos de Net::Server deberían funcionar igual.

"$self->run_dequeue()"
Este gancho solo se llama en conjunto con la configuración check_for_dequeue. Se ejecutará cada check_for_dequeue segundos. Dado que no se realiza ramificación, este gancho debería ejecutarse rápidamente para evitar bloquear el resto del procesamiento.

TEMPORIZADORES

set_timeout

Para utilizar la característica opcional de temporizador de IO::Multiplex, debe especificar un tiempo de espera utilizando el método set_timeout.

$self->{net_server}->{mux}->set_timeout($fh, $segundos_desde_ahora);

$fh puede ser un descriptor de archivo de socket de cliente o de escucha dentro del mux. $segundos_desde_ahora puede ser fraccional para lograr temporizadores más precisos. Esto se usa junto con mux_timeout, que debe definir usted mismo.

mux_timeout

La rutina principal **loop()** llamará $obj->mux_timeout($mux, $fh) cuando se alcance el tiempo de espera especificado en set_timeout, donde $fh es el mismo que el especificado en **set_timeout()** y $obj es su objeto correspondiente (ya sea el objeto único específico del cliente o el objeto principal de devolución de llamada de escucha) y $mux es el propio objeto principal de IO::Multiplex.

INTERFAZ DE DEVOLUCIÓN DE LLAMADA

Los objetos de devolución de llamada deben admitir la siguiente interfaz. No tiene que proporcionar todos estos métodos, solo proporcione los que le interesen. Son como los ganchos de IO::Multiplex, excepto que STDOUT está vinculado al descriptor de archivo del socket del cliente correspondiente para su conveniencia y para emular más de cerca el modelo Net::Server. Sin embargo, a diferencia de algunas otras personalidades de Net::Server, nunca debe leer directamente de STDIN. Debe definir uno o más de los siguientes métodos:

mux_connection ($mux,$fh)

(OPCIONAL) Se ejecuta una vez cuando el cliente se conecta por primera vez si allow_deny pasa. Tenga en cuenta que el hash de propiedad "$self->{net_server}->{server}" puede ser modificado por futuras conexiones a través de Net::Server. Cualquier valor dentro de él que este objeto pueda necesitar usar más tarde debe copiarse dentro de su propio objeto en este punto.

Ejemplo:
$self->{peerport} = $self->{net_server}->{server}->{peerport};

mux_input ($mux,$fh,\$data)

(REQUERIDO) Se ejecuta cada vez que se lee un paquete. Debe consumir $data comenzando por la izquierda y dejar datos no consumidos en el escalar para futuras llamadas a mux_input.

mux_eof ($mux,$fh,\$data)

(OPCIONAL) Se ejecuta una vez cuando el cliente termina de escribir. Debe consumir el resto de $data ya que **mux_input()** nunca se volverá a ejecutar.

mux_close ($mux,$fh)

(OPCIONAL) Se ejecuta después de que se haya cerrado todo el socket del cliente. No se deben hacer más intentos de leer o escribir en el cliente o en STDOUT.

mux_timeout ($mux,$fh)

(OPCIONAL) Se ejecuta una vez cuando expira la configuración set_timeout, como se explicó anteriormente.

ERRORES

Esto solo se sabe que funciona con servidores TCP.

Si necesita usar la interfaz set_timeout / mux_timeout al estilo IO::Multiplex, no puede usar el check_for_d

Net::Server::Multiplex(3pm) - Arch Linux man pages

NAME

Net::Server::Multiplex - A multiplexing server class.

SYNOPSIS

  use Net::Server::Multiplex;

  my $server = Net::Server::Multiplex->new(
    Host    => 'localhost',
    Port    => 8080,
    Proto   => 'tcp',
    Max     => 10,
    ReuseAddr => 1,
    Timeout => 60,
    Multiplex => IO::Multiplex->new(
      Handle => \*STDOUT,
      Timeout => 5,
    ),
    Accept => \&handle_client,
  );

  $server->run;

  sub handle_client {
    my ($server, $client) = @_;

    # Process the client connection
    print $client 'Hello, client!';
    close $client;
  }

DESCRIPTION

This is a class for writing network servers that can handle multiple clients concurrently using an IO multiplexing mechanism. It builds upon the base Net::Server class and integrates with an IO::Multiplex object.

The main difference from the standard Net::Server is how it handles client connections. Instead of forking a new process or thread for each client, it uses IO::Multiplex to monitor multiple client sockets for activity.

PROCESS FLOW

1. A Net::Server::Multiplex object is created with configuration parameters like Host, Port, and crucially, a IO::Multiplex object provided via the Multiplex option.

2. The server calls the run method.

3. The server starts listening for incoming connections on the specified Host and Port.

4. When a new connection arrives, the server accepts it and adds the client socket to the IO::Multiplex object's set of handles to monitor.

5. The IO::Multiplex object then waits for activity on any of the monitored handles (including the listening socket for new connections and client sockets for data).

6. When activity is detected on a client socket, the IO::Multiplex object notifies the Net::Server::Multiplex object.

7. The Net::Server::Multiplex object then calls the callback routine (specified by the Accept option) for that specific client.

8. The callback routine handles the client's request, reads data, writes data, and eventually closes the client connection.

9. Once a client connection is closed, it is removed from the IO::Multiplex object's monitoring set.

10. The process repeats from step 5, continuously monitoring all active client connections and the listening socket.

CLIENT PROCESSING

Client processing is handled by the subroutine referenced by the Accept configuration parameter. This subroutine receives two arguments: the server object itself and the client socket handle.

Inside this subroutine, you should read from and write to the client socket handle as needed. The IO::Multiplex object manages when this subroutine is called, ensuring it only happens when there's data to be read or when the client socket is ready for writing (though typically you'll focus on reading).

It is crucial that your Accept routine eventually closes the client connection. Failure to do so will result in the client socket remaining open and being monitored indefinitely by IO::Multiplex.

HOOKS

This class supports the following hooks, inherited from Net::Server:

  • setup: Called after the server is created but before it starts listening. Useful for any initial setup.
  • start: Called just before the main server loop begins.
  • preaccept: Called before waiting for a new client connection.
  • postaccept: Called after a client connection is accepted but before the Accept routine is called.
  • precleanup: Called when the server is shutting down, before any cleanup actions.
  • postcleanup: Called after the server has finished shutting down.

Additionally, it provides:

  • accept: The main callback routine for handling client connections, as described in the CLIENT PROCESSING section.

TIMEOUTS

Two timeout values are relevant:

  • Timeout (server level): This is the overall timeout for the run method. If the server runs for this long without interruption, it will exit. This is less commonly used in multiplexing servers which are typically designed to run indefinitely.
  • Timeout (IO::Multiplex level): This timeout is passed to the IO::Multiplex object during its creation. It determines how long IO::Multiplex will wait for activity on any of the monitored handles before timing out and returning. If it times out, the run method will return (unless the Accept routine is specified, in which case it might continue running if the listener is still active).

The Net::Server::Multiplex class itself does not define a specific timeout for individual client read/write operations within the Accept routine. This needs to be handled manually within your callback using mechanisms like sysread with a timeout or by integrating with other non-blocking I/O libraries if needed.

CALLBACK INTERFACE

The primary callback interface is the Accept subroutine. It is called with the server object and the client socket.

  sub my_accept_handler {
    my ($server, $client_fh) = @_;

    # Read from the client
    my $data = '';
    while (sysread($client_fh, my $buf, 1024) > 0) {
        $data .= $buf;
        # Add logic here to break if enough data is received
        last if $data =~ /\n\n/;
    }

    # Process data...

    # Write response
    print $client_fh "Response: Processed '$data'\n";

    # Close the client connection
    close $client_fh;
  }

Note that the check_for_dequeue option is not supported by this class, as it is fundamentally incompatible with the non-forking, multiplexing approach.

The run_dequeue method is provided solely for compatibility with the Net::Server::Fork style run_dequeue interface. It is implemented using the IO::Multiplex style set_timeout and mux_timeout methods internally.
