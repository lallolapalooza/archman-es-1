Nombre

Net::Ping - verificar la alcanzabilidad de un host remoto

Sintaxis

use Net::Ping;
my $p = Net::Ping->new();
print "$host es vivo.\n" if $p->ping($host);
$p->close();
my $p = Net::Ping->new("icmp");
$p->bind($my_addr); # Especificar el interfaz de origen de los ping
foreach my $host (@host_array)
{
    print "$host es ";
    print "NO " unless $p->ping($host, 2);
    print "reachable.\n";
    sleep(1);
}
$p->close();
my $p = Net::Ping->new("icmpv6");
my $ip = "[fd00:dead:beef::4e]";
print "$ip es vivo.\n" if $p->ping($ip);
my $p = Net::Ping->new("tcp", 2);
# Intentar conectar al puerto de echo de www
$p->port_number(scalar(getservbyname("http", "tcp")));
while ($stop_time > time())
{
    print "$host no es alcanzable ", scalar(localtime()), "\n"
        unless $p->ping($host);
    sleep(300);
}
undef($p);
# Compatible con el protocolo tcp
my $p = Net::Ping->new("syn");
$p->port_number(getservbyname("http", "tcp"));
foreach my $host (@host_array) {
  $p->ping($host);
}
while (my ($host, $rtt, $ip) = $p->ack) {
  print "HOST: $host [$ip] ACKed en $rtt segundos.\n";
}
# Sintaxis de alta precisión (requiere Time::HiRes)
my $p = Net::Ping->new();
$p->hires();
my ($ret, $duration, $ip) = $p->ping($host, 5.5);
printf("$host [ip: $ip] es vivo (tiempo de retorno de paquete: %.2f ms)\n",
        1000 * $duration)
  if $ret;
$p->close();
# Para compatibilidad con el antepasado
print "$host es vivo.\n" if pingecho($host);

Descripción

Esta librería contiene métodos para verificar la alcanzabilidad de hosts remotos en una red. Un objeto ping se crea primero con parámetros opcionales, varios hosts pueden ser píncalos múltiples y luego se cierra la conexión.

Puedes elegir uno de los seis diferentes protocolos para usar en el ping. El protocolo tcp es el por defecto. Debe tener en cuenta que un host remoto vivo puede aún no ser alcanzable por algunos de estos protocolos. Por ejemplo, www.microsoft.com es generalmente vivo pero no es alcanzable por el protocolo icmp.

Con el protocolo tcp, el método ping intenta establecer una conexión con el puerto de echo del host remoto. Si la conexión se establece correctamente, el host remoto se considera alcanzable. No se envía realmente datos. Este protocolo no requiere privilegios especiales pero tiene un mayor overhead que los protocolos udp y icmp.

Si se especifica el protocolo udp, el método ping envía un paquete udp al puerto de echo del host remoto. Si el paquete echo se recibe del host remoto y el paquete recibido contiene los mismos datos que el paquete enviado, el host remoto se considera alcanzable. Este protocolo no requiere privilegios especiales. Debe tener en cuenta que, para un ping udp, un host se reporta como no alcanzable si no está ejecutando el servicio correspondiente de echo. Para sistemas Unix-like, consulte inetd(8) para más información.

Si se especifica el protocolo icmp, el método ping envía un mensaje icmp echo al host remoto, lo cual es lo que hace el programa unix ping. Si el mensaje echo se recibe del host remoto y la información del mensaje echo es correcta, el host remoto se considera alcanzable. Es necesario que se ejecute el programa con root o que se establezca el programa como setuid root.

Si se especifica el protocolo externo, el método ping intenta usar el módulo "Net::Ping::External" para pingear el host remoto. El módulo "Net::Ping::External" se comunica con la utilidad de ping predeterminada de tu sistema y produce resultados relativamente precisos. Si "Net::Ping::External" no está instalado en tu sistema, especificar el protocolo externo resultará en un error.

Si se especifica el protocolo syn, el método ping enviará solo un paquete TCP SYN al host remoto y luego se regresarán inmediatamente. Si el paquete SYN se envía correctamente, retornará un valor verdadero, de lo contrario, retornará falso. NOTA: Aunque el valor de retorno no determina si el host remoto está vivo o no, porque aún no ha completado el tres-way handshake. El host remoto se considera alcanzable solo si recibe un ACK TCP dentro del tiempo especificado. Para comenzar a esperar por los paquetes ACK, use el método ack como se explicó. Use el protocolo syn en lugar del protocolo tcp para determinar la alcanzabilidad de múltiples destinos simultáneamente mediante el envío de paquetes TCP SYN paralelos. No bloquea mientras se prueba cada host remoto. Este protocolo no requiere privilegios especiales.

Funciones

Net::Ping->new([proto, timeout, bytes, device, tos, ttl, family, host, port, bind, gateway, retrans, pingstring, source_verify econnrefused dontfrag IPV6_USE_MIN_MTU IPV6_RECVPATHMTU])
Crea un nuevo objeto ping. Todos los parámetros son opcionales y se pueden pasar como referencia de hash. Todos los opciones excepto los primeros 7 deben pasar como referencia de hash.

El parámetro "proto" especifica el protocolo que se usará cuando se realice un ping. Las opciones actuales son "tcp", "udp", "icmp", "icmpv6", "stream", "syn", o "external". El valor por defecto es "tcp".

Si se proporciona un "timeout" en segundos, se usa cuando no se especifica un tiempo de espera al método ping() (más abajo). El tiempo de espera debe ser mayor que 0 y el valor por defecto, si no se especifica, es 5 segundos.

Si se especifica el número de bytes ("bytes"), se incluyen tantos bytes de datos como se indique en el paquete ping enviado al host remoto. Si el protocolo es "tcp", se ignora el número de bytes. El número mínimo (y por defecto) de bytes de datos es 1 si el protocolo es "udp" y 0 en otro caso. El número máximo de bytes que se puede especificar es 65535, pero se recomienda mantenerlo por debajo del MTU (1472 bytes para ICMP). Muchos dispositivos pequeños no pueden manejar paquetes fragmentados de ICMP.

Si se especifica el "device", este dispositivo se usa para bind el endpoint de origen antes de enviar el paquete ping. Creo que esto solo funciona con privilegios de superusuario y con protocolos udp y icmp en este momento.

Si se especifica "tos", se configura el ToS en el socket.

Para icmp, "ttl" puede especificarse para establecer el TTL del paquete saliente.

Valores válidos para "family" en IPv4:

4, v4, ip4, ipv4, AF_INET (constante)

Valores válidos para "family" en IPv6:

6, v6, ip6, ipv6, AF_INET6 (constante)

El parámetro "host" especifica implícitamente el familia si el parámetro family no se especifica.

El parámetro "port" es solo válido para un ping udp, tcp o stream y no hará lo que se piensa que hace. El ping devuelve true cuando se recibe un mensaje "Connection refused"! El valor por defecto es el puerto de echo.

El parámetro "bind" especifica el local_addr a bind. Al especificar un bind argumento, no se necesita el método bind.

El parámetro "gateway" es solo válido para IPv6 y requiere un dirección IPv6.

El parámetro "retrans" especifica la tasa de retrocedimiento exponencial, por defecto 1.2. Corresponde al valor global $def_factor.

El parámetro "dontfrag" establece el bit IP_DONTFRAG, pero tenga en cuenta que IP_DONTFRAG no está definido aún por Socket y no está disponible en muchos sistemas. Luego se ignora. En Linux también establece IP_MTU_DISCOVER a IP_PMTUDISC_DO, pero no se debe fragmentar paquetes de tamaño excesivo. Debes configurar $data_size manualmente.

$p->ping($host [, $timeout [, $family]]);
Pingea el host remoto y espera una respuesta. $host puede ser el nombre de host o el número IP.

NOTAS

Habrá menos sobrecarga de red (y cierta eficiencia en su programa) si especifica el protocolo udp o icmp. El protocolo tcp generará 2.5 veces más tráfico o más por cada ping que udp o icmp. Si se envían pings a muchos hosts con frecuencia, es posible que desee implementar una pequeña espera (por ejemplo, 25 ms o más) entre cada ping para evitar inundar su red con paquetes.

Los protocolos icmp e icmpv6 requieren que el programa se ejecute como root o que se establezca setuid a root. Los otros protocolos no requieren privilegios especiales, pero no todos los dispositivos de red implementan el eco tcp o udp.

Los hosts locales normalmente deberían responder a los pings en milisegundos. Sin embargo, en una red muy congestionada, puede llevar hasta 3 segundos o más recibir un paquete de eco del host remoto. Si el tiempo de espera se establece demasiado bajo en estas condiciones, parecerá que el host remoto no es accesible (lo cual es casi la verdad).

La accesibilidad no significa necesariamente que el host remoto esté funcionando más allá de su capacidad para enviar paquetes de eco. tcp es ligeramente mejor para indicar el estado de un sistema que icmp porque utiliza más de la pila de red para responder.

Debido a la falta de algo mejor, este módulo utiliza sus propias rutinas para empaquetar y desempaquetar paquetes ICMP. Sería mejor escribir un módulo separado que entienda todos los diferentes tipos de paquetes ICMP.
