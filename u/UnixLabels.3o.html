Interfaz con el sistema Unix.

Para usar la versión etiquetada de este módulo, agregue module Unix = UnixLabels en su implementación.

Nota: todas las funciones de este módulo (excepto UnixLabels.error_message y UnixLabels.handle_unix_error ) pueden lanzar la excepción UnixLabels.Unix_error siempre que la llamada del sistema subyacente señale un error.

exception Unix_error de error * string * string

Lanzada por las llamadas del sistema a continuación cuando se encuentra un error. El primer componente es el código de error; el segundo componente es el nombre de la función; el tercer componente es el parámetro de cadena para la función, si lo tiene, o la cadena vacía en caso contrario.

val execv : prog:string -> args:string array -> 'a

execv prog args ejecuta el programa en el archivo prog, con los argumentos args y el entorno del proceso actual. Tenga en cuenta que el primer argumento, args.(0), es por convención el nombre de archivo del programa que se está ejecutando, al igual que Sys.argv.(0). Estas funciones execv* nunca regresan: en caso de éxito, el programa actual es reemplazado por el nuevo.

En Windows: la CRT simplemente inicia un nuevo proceso y sale del actual. Esto tendrá consecuencias no deseadas si, por ejemplo, otro proceso está esperando al actual. Se recomienda usar UnixLabels.create_process o una de las funciones open_process_* en su lugar.

Eleva Unix_error en caso de fallo.

val execve : prog:string -> args:string array -> env:string array -> 'a

Igual que UnixLabels.execv, excepto que el tercer argumento proporciona el entorno al programa ejecutado.

val execvp : prog:string -> args:string array -> 'a

Igual que UnixLabels.execv, excepto que el programa se busca en la ruta.

val execvpe : prog:string -> args:string array -> env:string array -> 'a

Igual que UnixLabels.execve, excepto que el programa se busca en la ruta.

val fork : unit -> int

Crea un nuevo proceso hijo. El entero devuelto es 0 para el proceso hijo, el pid del proceso hijo para el proceso padre. Falla si el proceso OCaml es multinúcleo (se ha iniciado algún dominio). Además, si se ha iniciado algún hilo del módulo Thread, el proceso hijo podría estar en un estado corrupto.

Eleva Invalid_argument en Windows. Use UnixLabels.create_process o hilos en su lugar.

Eleva Failure si se ha iniciado algún dominio.

val wait : unit -> int * process_status

Espera hasta que uno de los procesos hijos muera y devuelve su pid y estado de terminación.

Eleva Invalid_argument en Windows. Use UnixLabels.waitpid en su lugar.

val waitpid : mode:wait_flag list -> int -> int * process_status

Igual que UnixLabels.wait, pero espera al proceso hijo cuyo pid se proporciona. Un pid de -1 significa esperar a cualquier hijo. Un pid de 0 significa esperar a cualquier hijo en el mismo grupo de procesos que el proceso actual. Los argumentos de pid negativos representan grupos de procesos. La lista de opciones indica si waitpid debe regresar inmediatamente sin esperar y si debe informar de los hijos detenidos.

En Windows: solo puede esperar a un PID dado, no a cualquier proceso hijo.

val system : string -> process_status

Ejecuta el comando dado, espera hasta que termine y devuelve su estado de terminación. La cadena es interpretada por el shell /bin/sh (o el intérprete de comandos cmd.exe en Windows) y, por lo tanto, puede contener redirecciones, comillas, variables, etc. Para citar correctamente los espacios en blanco y los caracteres especiales del shell que ocurren en nombres de archivo o argumentos de comandos, se recomienda el uso de Filename.quote_command. El resultado WEXITED 127 indica que el shell no pudo ser ejecutado.

val _exit : int -> 'a

Termina el proceso llamante inmediatamente, devolviendo el código de estado dado al sistema operativo: generalmente 0 para indicar que no hay errores y un entero positivo pequeño para indicar un fallo. A diferencia de exit, Unix._exit no realiza ninguna finalización: no se llaman a las funciones registradas con at_exit, no se vacían los canales de entrada/salida y el sistema en tiempo de ejecución de C tampoco se finaliza.

El uso típico de Unix._exit es después de una operación Unix.fork, cuando el proceso hijo encuentra un error fatal y debe salir. En este caso, es preferible no realizar ninguna acción de finalización en el proceso hijo, ya que estas acciones podrían interferir con acciones similares realizadas por el proceso padre. Por ejemplo, el proceso padre podría volver a vaciar los canales de salida, lo que resultaría en una salida duplicada.

val in_channel_of_descr : file_descr -> in_channel

Crea un canal de entrada que lee del descriptor dado. El canal está inicialmente en modo binario; usa set_binary_mode_in ic false si se desea modo texto. El modo texto solo se admite si el descriptor se refiere a un archivo o tubería, pero no se admite si se refiere a un socket.

En Windows: set_binary_mode_in siempre falla en los canales creados con esta función.

Ten en cuenta que los canales de entrada están cacheados, por lo que se pueden haber leído más caracteres del descriptor que los accedidos mediante funciones de canal. Los canales también conservan una copia de la posición actual en el archivo.

Cerrar el canal ic devuelto por in_channel_of_descr fd usando close_in ic también cierra el descriptor subyacente fd. Es incorrecto cerrar tanto el canal ic como el descriptor fd.

Si se crean varios canales en el mismo descriptor, uno de los canales debe cerrarse, pero no los demás. Considera, por ejemplo, un descriptor s conectado a un socket y dos canales ic = in_channel_of_descr s y oc = out_channel_of_descr s. El protocolo de cierre recomendado es realizar close_out oc, que vacía la salida en caché al socket y luego cierra el socket. El canal ic no debe cerrarse y será recolectado por el GC eventualmente.

val out_channel_of_descr : file_descr -> out_channel

Crea un canal de salida que escribe en el descriptor dado. El canal está inicialmente en modo binario; usa set_binary_mode_out oc false si se desea modo texto. El modo texto solo se admite si el descriptor se refiere a un archivo o tubería, pero no se admite si se refiere a un socket.

En Windows: set_binary_mode_out siempre falla en los canales creados con esta función.

Ten en cuenta que los canales de salida están cacheados, por lo que es posible que tengas que llamar a flush para asegurarte de que todos los datos se han enviado al descriptor. Los canales también conservan una copia de la posición actual en el archivo.

Cerrar el canal oc devuelto por out_channel_of_descr fd usando close_out oc también cierra el descriptor subyacente fd. Es incorrecto cerrar tanto el canal ic como el descriptor fd.

Ver Unix.in_channel_of_descr para una discusión del protocolo de cierre cuando se crean varios canales en el mismo descriptor.

Operaciones de archivo en archivos grandes. Este submódulo proporciona variantes de 64 bits de las funciones UnixLabels.LargeFile.lseek (para posicionar un descriptor de archivo), UnixLabels.LargeFile.truncate y UnixLabels.LargeFile.ftruncate (para cambiar el tamaño de un archivo), y UnixLabels.LargeFile.stat, UnixLabels.LargeFile.lstat y UnixLabels.LargeFile.fstat (para obtener información sobre archivos). Mapping files into memory

val map_file : file_descr -> ?pos:int64 -> kind:('a, 'b) Bigarray.kind -> layout:'c Bigarray.layout -> shared:bool -> dims:int array -> ('a, 'b, 'c) Bigarray.Genarray.t

Mapeo de memoria de un archivo como un Bigarray. map_file fd ~kind ~layout ~shared ~dims devuelve un Bigarray de tipo kind, diseño layout y dimensiones especificadas en dims. Los datos contenidos en este Bigarray son el contenido del archivo al que se refiere el descriptor de archivo fd (abierto previamente con UnixLabels.openfile, por ejemplo). El parámetro opcional pos es el desplazamiento en bytes en el archivo de los datos que se están mapeando; por defecto es 0 (mapear desde el principio del archivo).

Si shared es true, todas las modificaciones realizadas en la matriz se reflejan en el archivo. Esto requiere que fd se abra con permisos de escritura. Si shared es false, las modificaciones realizadas en la matriz se hacen solo en memoria, utilizando copia en escritura de las páginas modificadas; el archivo subyacente no se ve afectado.

UnixLabels.map_file es mucho más eficiente que leer el archivo completo en un Bigarray, modificar ese Bigarray y escribirlo después.

Para ajustar automáticamente las dimensiones del Bigarray al tamaño real del archivo, la dimensión principal (es decir, la primera dimensión para una matriz con diseño C, y la última dimensión para una matriz con diseño Fortran) se puede dar como -1. UnixLabels.map_file entonces determina la dimensión principal a partir del tamaño del archivo. El archivo debe contener un número integral de sub-arrays según lo determinado por las dimensiones no principales, de lo contrario se lanza Failure.

Si se dan todas las dimensiones del Bigarray, el tamaño del archivo se compara con el tamaño del Bigarray. Si el archivo es más grande que el Bigarray, solo se mapea la porción inicial del archivo al Bigarray. Si el archivo es más pequeño que el Bigarray, el archivo se expande automáticamente al tamaño del Bigarray. Esto requiere permisos de escritura en fd.

Los accesos a la matriz están sujetos a comprobación de límites, pero los límites se determinan por la llamada inicial a map_file. Por lo tanto, debes asegurarte de que ningún otro proceso modifique el archivo mapeado mientras lo estás accediendo, o se puede generar una señal SIGBUS. Esto ocurre, por ejemplo, si el archivo se reduce de tamaño.

Se pueden lanzar Invalid_argument o Failure en casos donde la validación de argumentos falla.

val rename : src:string -> dst:string -> unit

Establece la bandera "no bloqueante" en el descriptor dado. Cuando se establece la bandera no bloqueante, la lectura en un descriptor en el que temporalmente no hay datos disponibles lanza el error EAGAIN o EWOULDBLOCK en lugar de bloquear; la escritura en un descriptor en el que temporalmente no hay espacio para escribir también lanza EAGAIN o EWOULDBLOCK.

Borra la bandera "no bloqueante" en el descriptor dado. Consulte UnixLabels.set_nonblock.

val set_close_on_exec : file_descr -> unit

Establece la bandera "cerrar al ejecutar" en el descriptor dado. Un descriptor con la bandera cerrar al ejecutar se cierra automáticamente cuando el proceso actual inicia otro programa con una de las funciones exec, create_process y open_process.

A menudo es un agujero de seguridad filtrar descriptores de archivo abiertos, por ejemplo, en un archivo privado, a un programa externo: el programa, entonces, obtiene acceso al archivo privado y puede hacer cosas malas con él. Por lo tanto, se recomienda encarecidamente establecer todos los descriptores de archivo "cerrar al ejecutar", excepto en los muy pocos casos en que un descriptor de archivo necesita ser transmitido a otro programa.

La mejor manera de establecer un descriptor de archivo "cerrar al ejecutar" es crearlo en este estado. Para ello, la función openfile tiene las banderas O_CLOEXEC y O_KEEPEXEC para forzar el modo "cerrar al ejecutar" o el modo "mantener al ejecutar", respectivamente. Todas las demás operaciones en el módulo Unix que crean descriptores de archivo tienen un argumento opcional ?cloexec:bool para indicar si el descriptor de archivo debe crearse en modo "cerrar al ejecutar" (escribiendo ~cloexec:true) o en modo "mantener al ejecutar" (escribiendo ~cloexec:false). Por razones históricas, el modo de creación de descriptores de archivo predeterminado es "mantener al ejecutar", si no se proporciona ningún argumento opcional cloexec. Este no es un valor predeterminado seguro, por lo tanto, se recomienda encarecidamente pasar argumentos cloexec explícitos a las operaciones que crean descriptores de archivo.

Los argumentos opcionales cloexec y la bandera O_KEEPEXEC se introdujeron en OCaml 4.05. Anteriormente, la práctica común era crear descriptores de archivo en el modo predeterminado, "mantener al ejecutar", y luego llamar a set_close_on_exec en esos descriptores de archivo recién creados. Esto no es tan seguro como crear el descriptor de archivo en modo "cerrar al ejecutar", ya que, en programas multihilo, existe una ventana de vulnerabilidad entre el momento en que se crea el descriptor de archivo y el momento en que se completa set_close_on_exec. Si otro hilo inicia otro programa durante esta ventana, el descriptor se filtrará, ya que todavía está en modo "mantener al ejecutar".

En cuanto a las garantías de atomicidad proporcionadas por ~cloexec:true o por el uso de la bandera O_CLOEXEC: en todas las plataformas se garantiza que un hilo de Caml que se ejecuta concurrentemente no puede filtrar el descriptor iniciando un nuevo proceso. En Linux, esta garantía se extiende a los hilos de C que se ejecutan concurrentemente. A fecha de febrero de 2017, otros sistemas operativos carecen de las llamadas al sistema necesarias y aún exponen una ventana de vulnerabilidad durante la cual un hilo de C puede ver el descriptor de archivo recién creado en modo "mantener al ejecutar".

Borra la bandera "cerrar al ejecutar" en el descriptor dado. Consulte UnixLabels.set_close_on_exec.

val create_process : prog:string -> args:string array -> stdin:file_descr -> stdout:file_descr -> stderr:file_descr -> int

create_process ~prog ~args ~stdin ~stdout ~stderr crea un nuevo proceso que ejecuta el programa en el archivo prog, con los argumentos args. Tenga en cuenta que el primer argumento, args.(0), es por convención el nombre de archivo del programa que se está ejecutando, al igual que Sys.argv.(0). El pid del nuevo proceso se devuelve inmediatamente; el nuevo proceso se ejecuta de forma concurrente con el proceso actual. La entrada y salida estándar del nuevo proceso están conectadas a los descriptores stdin, stdout y stderr. Pasar, por ejemplo, Unix.stdout para stdout evita la redirección y hace que el nuevo proceso tenga la misma salida estándar que el proceso actual. El archivo ejecutable prog se busca en la ruta. El nuevo proceso tiene el mismo entorno que el proceso actual.

Enlaces simbólicos

val symlink : ?to_dir:bool -> src:string -> dst:string -> unit

symlink ?to_dir ~src ~dst crea el archivo dst como un enlace simbólico al archivo src . En Windows, ~to_dir indica si el enlace simbólico apunta a un directorio o a un archivo; si se omite, symlink examina src usando stat y elige apropiadamente, si src no existe, se asume false (por esta razón, se recomienda que el parámetro ~to_dir se especifique en código nuevo). En Unix, ~to_dir se ignora.

Los enlaces simbólicos de Windows están disponibles en Windows Vista en adelante. Existen algunas diferencias importantes entre los enlaces simbólicos de Windows y sus contrapartes POSIX.

Los enlaces simbólicos de Windows vienen en dos sabores: directorio y regular, que designan si el enlace simbólico apunta a un directorio o a un archivo. El tipo debe ser correcto: un enlace simbólico de directorio que en realidad apunta a un archivo no puede ser seleccionado con chdir y un enlace simbólico de archivo que en realidad apunta a un directorio no puede ser leído o escrito (ten en cuenta que la capa de emulación de Cygwin ignora esta distinción).

Cuando se crean enlaces simbólicos a objetivos existentes, esta distinción no importa y symlink creará automáticamente el tipo correcto de enlace simbólico. La distinción importa cuando se crea un enlace simbólico a un objetivo no existente.

La otra advertencia es que por defecto los enlaces simbólicos son una operación privilegiada. Los administradores siempre necesitarán estar ejecutándose de forma elevada (o con UAC deshabilitado) y por defecto las cuentas de usuario normales necesitarán que se les otorgue el SeCreateSymbolicLinkPrivilege a través de la Política de Seguridad Local (secpol.msc) o a través de Active Directory.

UnixLabels.has_symlink se puede usar para verificar que un proceso puede crear enlaces simbólicos.

En otras plataformas, esto simplemente indica que la llamada al sistema symlink está disponible.

Espera hasta que algunas operaciones de entrada/salida sean posibles en algunos canales. Las tres listas de argumentos son, respectivamente, un conjunto de descriptores para verificar lectura (primer argumento), escritura (segundo argumento), o condiciones excepcionales (tercer argumento). Comandos para UnixLabels.lockf .

val lockf : file_descr -> mode:lock_command -> len:int -> unit

lockf fd ~mode ~len pone un bloqueo en una región del archivo abierto como fd . La región comienza en la posición actual de lectura/escritura para fd (establecida por UnixLabels.lseek ), y se extiende len bytes hacia adelante si len es positivo, len bytes hacia atrás si len es negativo, o hasta el final del archivo si len es cero. Un bloqueo de escritura evita que cualquier otro proceso adquiera un bloqueo de lectura o escritura en la región. Un bloqueo de lectura evita que cualquier otro proceso adquiera un bloqueo de escritura en la región, pero permite que otros procesos adquieran bloqueos de lectura en ella.

Los comandos F_LOCK y F_TLOCK intentan poner un bloqueo de escritura en la región especificada. Los comandos F_RLOCK y F_TRLOCK intentan poner un bloqueo de lectura en la región especificada. Si uno o varios bloqueos puestos por otro proceso impiden que el proceso actual adquiera el bloqueo, F_LOCK y F_RLOCK se bloquean hasta que estos bloqueos se eliminen, mientras que F_TLOCK y F_TRLOCK fallan inmediatamente con una excepción. F_ULOCK elimina cualquier bloqueo que el proceso actual tenga sobre la región especificada. Finalmente, el comando F_TEST prueba si se puede adquirir un bloqueo de escritura en la región especificada, sin poner realmente un bloqueo. Devuelve inmediatamente si tiene éxito, o falla en caso contrario.

¿Qué sucede cuando un proceso intenta bloquear una región de un archivo que

ya está bloqueado por el mismo proceso depende del sistema operativo. En sistemas compatibles con POSIX, la segunda operación de bloqueo tiene éxito y puede "promocionar" el bloqueo anterior de bloqueo de lectura a bloqueo de escritura. En Windows, la segunda operación de bloqueo se bloqueará o fallará.

type setattr_when = Unix.setattr_when =
| TCSANOW
| TCSADRAIN
| TCSAFLUSH

val tcsetattr : file_descr -> mode:setattr_when -> terminal_io -> unit

Establece el estado de la terminal a la que se refiere el descriptor de archivo dado. El segundo argumento indica cuándo se produce el cambio de estado: inmediatamente (TCSANOW), cuando se ha transmitido toda la salida pendiente (TCSADRAIN), o después de vaciar toda la entrada que se ha recibido pero no leído (TCSAFLUSH). Se recomienda TCSADRAIN al cambiar los parámetros de salida; TCSAFLUSH, al cambiar los parámetros de entrada.

val tcsendbreak : file_descr -> duration:int -> unit

Envía una condición de interrupción en el descriptor de archivo dado. El segundo argumento es la duración de la interrupción, en unidades de 0.1s; 0 significa duración estándar (0.25s).

type flush_queue = Unix.flush_queue =
| TCIFLUSH
| TCOFLUSH
| TCIOFLUSH

val tcflush : file_descr -> mode:flush_queue -> unit

Descarta los datos escritos en el descriptor de archivo dado pero aún no transmitidos, o los datos recibidos pero aún no leídos, dependiendo del segundo argumento: TCIFLUSH descarta los datos recibidos pero no leídos, TCOFLUSH descarta los datos escritos pero no transmitidos, y TCIOFLUSH descarta ambos.

Lanza Invalid_argument en Windows

type flow_action = Unix.flow_action =
| TCOOFF
| TCOON
| TCIOFF
| TCION

val tcflow : file_descr -> mode:flow_action -> unit

Suspende o reanuda la recepción o transmisión de datos en el descriptor de archivo dado, dependiendo del segundo argumento: TCOOFF suspende la salida, TCOON reanuda la salida, TCIOFF transmite un carácter STOP para suspender la entrada, y TCION transmite un carácter START para reanudar la entrada.
