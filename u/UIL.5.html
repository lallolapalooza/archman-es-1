DESCRIPCIÓN

El lenguaje UIL se utiliza para describir el estado inicial de una interfaz de usuario para una aplicación basada en widgets. UIL describe los widgets utilizados en la interfaz, los recursos de esos widgets y las llamadas de retorno (callbacks) de esos widgets. El archivo UIL se compila en un archivo UID utilizando el comando uil o por el compilador llamable Uil(). El contenido del archivo UID compilado puede ser accedido por las diversas funciones de Motif Resource Management (MRM) desde dentro de un programa de aplicación.

El archivo UID es independiente de la plataforma en la que se ejecutará finalmente el programa Motif. En otras palabras, el mismo archivo UID puede usarse en cualquier sistema que pueda ejecutar Motif.

Archivo

Un archivo UIL consta de un único módulo completo, descrito en la sintaxis descrita anteriormente, o, si el archivo se va a incluir en un archivo UIL más grande, una "sección" completa, como se describe a continuación. UIL utiliza cinco tipos diferentes de secciones: valor, procedimiento, lista, objeto e identificador.

UIL es un lenguaje de formato libre. Esto significa que las construcciones de alto nivel como las declaraciones de objetos y valores no necesitan comenzar en ninguna columna en particular y pueden abarcar cualquier número de líneas. Las construcciones de bajo nivel como las palabras clave y los caracteres de puntuación también pueden comenzar en cualquier columna; sin embargo, excepto para los literales de cadena y los comentarios, no pueden abarcar líneas.

El compilador UIL acepta líneas de entrada de hasta 132 caracteres de longitud.

MÓDULO nombre_módulo
El nombre por el cual se conoce el módulo UIL en el archivo UID. Este nombre se almacena en el archivo UID para su posterior uso en la recuperación de recursos por parte de MRM. Este nombre siempre se almacena en mayúsculas en el archivo UID.
NOMBRES = CASE_INSENSITIVE | CASE_SENSITIVE
Indica si los nombres deben tratarse como sensibles a mayúsculas/minúsculas o insensibles a mayúsculas/minúsculas. El valor predeterminado es sensible a mayúsculas/minúsculas. La cláusula de sensibilidad a mayúsculas/minúsculas debe ser la primera cláusula en la cabecera del módulo y, en cualquier caso, debe preceder a cualquier declaración que contenga un nombre. Si los nombres son sensibles a mayúsculas/minúsculas en un módulo UIL, las palabras clave de UIL en ese módulo deben estar en minúsculas. Cada nombre se almacena en el archivo UIL con la misma capitalización que aparece en el módulo UIL. Si los nombres son insensibles a mayúsculas/minúsculas, entonces las palabras clave pueden estar en mayúsculas, minúsculas o una mezcla, y el equivalente en mayúsculas de cada nombre se almacena en el archivo UID.
CHARACTER_SET = conjunto_caracteres
Especifica el conjunto de caracteres predeterminado para los literales de cadena en el módulo que no establecen explícitamente su conjunto de caracteres. El conjunto de caracteres predeterminado, en ausencia de esta cláusula, es el componente de código de la variable de entorno LANG, o el valor de XmFALLBACK_CHARSET si LANG no está establecido o no tiene un componente de código. El valor de XmFALLBACK_CHARSET es definido por el proveedor de UIL, pero suele ser ISO8859-1 (equivalente a ISO_LATIN1). El uso de esta cláusula desactiva todo el procesamiento de literales de cadena localizados activado por la bandera del compilador -s o el elemento de datos use_setlocale_flag de la estructura de datos Uil_command_type.
OBJETOS = { nombre_widget = GADGET | WIDGET; }
Indica si se utiliza la forma de widget o gadget del control especificado por nombre_widget por defecto. Por defecto se utiliza la forma de widget, por lo que la palabra clave gadget es la única que se suele utilizar. El control especificado debe ser uno que tenga tanto versión de widget como de gadget: XmCascadeButton, XmLabel, XmPushButton, XmSeparator y XmToggleButton. La forma de más de un control puede especificarse delimitándolos con punto y coma. La forma gadget o widget de una instancia de un control puede especificarse con las palabras clave GADGET y WIDGET en una declaración de objeto particular.

UIL - User Interface Language

This chapter describes the UIL syntax and semantics.

Value declarations

A value declaration creates a named value or object that can be referenced elsewhere in the UIL module or in other modules. It has the following syntax:

VALUE
     value_name [ : value_type ] [ EXPORTED | IMPORTED ] = value_expression;

You can use the keyword VALUE to declare named values or named objects. You can use this declaration in any context where you can use a value expression.

Values declared with the EXPORTED keyword are accessible from other UIL modules. Values declared without the EXPORTED keyword are private value only in the UIL module containing the value declaration. The value or object is directly incorporated into anything in the UIL module that references the declaration.

IMPORTED
A value that you define as imported is one that is defined as a named resource in a UID file. MRM resolves this declaration with the corresponding exported declaration at application run time.

Procedure sections

A procedure section consists of the keyword PROCEDURE followed by a sequence of procedure declarations. It has the following syntax:

PROCEDURE
     procedure_name [ ( [ value_type ]) ];

Use a procedure declaration to declare

•
A routine that can be used as a callback routine for a widget
•
The creation function for a user-defined widget

You can reference a procedure name in declarations that occur later in the UIL module in any context where a procedure can be used. Procedures can be forward referenced. You cannot use a name you used in another context as a procedure name.

In a procedure declaration, you have the option of specifying that a parameter will be passed to the corresponding callback routine at run time. This parameter is called the callback tag. You can specify the data type of the callback tag by putting the data type in parentheses following the procedure name. When you compile the module, the UIL compiler checks that the argument you specify in references to the procedure is of this type. Note that the data type of the callback tag must be one of the valid UIL data types. You can use a widget as a callback tag, as long as the widget is defined in the same widget hierarchy as the callback, that is they have a common ancestor that is in the same UIL hierarchy.

The following list summarizes how the UIL compiler checks argument type and argument count, depending on the procedure declaration.

No parameters
No argument type or argument count checking occurs. You can supply either 0 or one arguments in the procedure reference.
( )
Checks that the argument count is 0 (zero).
(ANY)
Checks that the argument count is 1. Does not check the argument type. Use the ANY type to prevent type checking on procedure tags.
(type)
Checks for one argument of the specified type.
(class_name)
Checks for one widget argument of the specified widget class.

While it is possible to use any UIL data type to specify the type of a tag in a procedure declaration, you must be able to represent that data type in the programming language you are using. Some data types (such as integer, Boolean, and string) are common data types recognized by most programming languages. Other UIL data types (such as string tables) are more complicated and may require that you set up an appropriate corresponding data structure in the application in order to pass a tag of that type to a callback routine.

You can also use a procedure declaration to specify the creation function for a user-defined widget. In this case, you specify no formal parameters. The procedure is invoked with the standard three arguments passed to all widget creation functions. (See the Motif Toolkit documentation for more information about widget creation functions.)

List sections

A list section consists of the keyword LIST followed by a sequence of list declarations. It has the following syntax:

LIST
     list_name: { list_item; [...] }
     [...]

You can also use list sections to group together a set of arguments, controls (children), callbacks, or procedures for later use in the UIL module. Lists can contain other lists, so that you can set up a hierarchy to clearly show which arguments, controls, callbacks, and procedures are common to which widgets. You cannot mix the different types of lists; a list of a particular type cannot contain entries of a different list type or reference the name of a different list type. A list name is always private to the UIL module in which you declare the list and cannot be stored as a named resource in a UID file.

The additional list types are described in the following sections.

Arguments List Structure

An arguments list defines which arguments are to be specified in the arguments list parameter when the creation routine for a particular object is called at run time. An arguments list also specifies the values for those arguments. Argument lists have the following syntax:

LIST
     list_name: ARGUMENTS {
          argument_name = value_expression;
          [...] }
[...]

The argument name must be either a built-in argument name or a user-defined argument name that is specified with the ARGUMENT function.

If you use a built-in argument name as an arguments list entry in an object definition, the UIL compiler checks the argument name to be sure that it is supported by the type of object that you are defining. If the same argument name appears more than once in a given arguments list, the last entry that uses that argument name supersedes all previous entries with that name, and the compiler issues a message.

Some arguments, such as XmNitems and XmNitemCount, are coupled by the UIL compiler. When you specify one of the arguments, the compiler also sets the other. The coupled argument is not available to you.

The Motif Toolkit and the X Toolkit (intrinsics) support constraint arguments. A constraint argument is one that is passed to children of an object, beyond those arguments normally available. For example, the Form widget grants a set of constraint arguments to its children. These arguments control the position of the children within the Form.

Unlike the arguments used to define the attributes of a particular widget, constraint arguments are used exclusively to define additional attributes of the children of a particular widget. These attributes affect the behavior of the children within their parent. To supply constraint arguments to the children, you include the arguments in the arguments list for the child.

See Appendix B for information about which arguments are supported by which widgets. See Appendix C for information about what the valid value type is for each built-in argument.

Callbacks List Structure

Use a callbacks list to define which callback reasons are to be processed by a particular widget at run time. Callback lists have the following syntax:

LIST list_name : CALLBACKS { reason_name = PROCEDURE procedure_name [ ( [ value_expression ] ) ]; | reason_name = procedure_list ; [...] } [...]

For Motif Toolkit widgets, the reason name must be a built-in reason name. For a user-defined widget, you can use a reason name that you previously specified using the REASON function. If you use a built-in reason in an object definition, the UIL compiler ensures that reason is supported by the type of object you are defining. Appendix B shows which reasons each object supports.

If the same reason appears more than once in a callbacks list, the last entry referring to that name supersedes all previous entries using the same reason, and the UIL compiler issues a diagnostic message.

If you specify a named value for the procedure argument (callback tag), the data type of the value must match the type specified for the callback tag in the corresponding procedure declaration. When specifying a widget name as a procedure value expression you must also specify the type of the widget and a space before the name of the widget.

Because the UIL compiler produces a UID file rather than an object module (.o), the binding of the UIL name to the address of the entry point to the procedure is not done by the loader, but is established at run time with the MRM function MrmRegisterNames. You call this function before fetching any objects, giving it both the UIL names and the procedure addresses of each callback. The name you register with MRM in the application program must match the name you specified for the procedure in the UIL module.

Each callback procedure receives three arguments. The first two arguments have the same form for each callback. The form of the third argument varies from object to object.

The first argument is the address of the data structure maintained by the Motif Toolkit for this object instance. This address is called the widget ID for this object.

The second argument is the address of the value you specified in the callbacks list for this procedure. If you do not specify an argument, the address is NULL. Note that, in the case where the value you specified is a string or an XmString, the value specified in the callbacks list already represents an address rather than an actual value. In the case of a simple string, for example, the value is the address of the first character of that string. In these cases, UIL does not add a level of indirection, and the second argument to the callback procedure is simply the value as specified in the callbacks list.

The third argument is the reason name you specified in the callbacks list.

Controls List Structure

A controls list defines which objects are children of, or controlled by

, un objeto en particular. Cada entrada en una lista de controles tiene la siguiente sintaxis: 

LIST
     nombre_lista: CONTROLS {
          [nombre_hijo: ] [MANAGED | UNMANAGED] definición_objeto;
          [...] }
     [...]

Si especificas la palabra clave MANAGED en tiempo de ejecución, el objeto se crea y se gestiona; si especificas UNMANAGED en tiempo de ejecución, el objeto solo se crea. Los objetos se gestionan por defecto.

Puedes usar nombre_hijo para especificar recursos para los hijos creados automáticamente de un control en particular. Los nombres para los hijos creados automáticamente se forman añadiendo Xm_ al nombre del widget hijo. Este nombre se especifica en la documentación del widget padre.

A diferencia de la lista de argumentos y la lista de callbacks, una entrada de lista de controles idéntica a una entrada anterior no reemplaza la entrada anterior. En tiempo de ejecución, cada entrada de lista de controles provoca la creación de un hijo cuando se crea el padre. Si se utiliza la misma definición de objeto para varios hijos, se crean varias instancias del hijo en tiempo de ejecución. Consulta el Apéndice B para obtener una lista de qué tipos de widgets pueden ser controlados por qué otros tipos de widgets.

Estructura de la Lista de Procedimientos

Puedes especificar varios procedimientos para una razón de callback en UIL definiendo una lista de procedimientos. Al igual que con otros tipos de listas, las listas de procedimientos se pueden definir en línea o en una sección de lista y referenciarlas por nombre.

Si defines una razón más de una vez (por ejemplo, cuando la razón se define tanto en una lista de procedimientos referenciada como en la lista de callbacks para el objeto), las definiciones anteriores se anulan por la última definición. La sintaxis de una lista de procedimientos es la siguiente:

LIST
     nombre_lista: PROCEDURES {
          nombre_procedimiento [ ( [ expresión_valor ]) ];
          [...] }
     [...]

Al especificar un nombre de widget como una expresión de valor de procedimiento, también debes especificar el tipo del widget y un espacio antes del nombre del widget.

Secciones de Objetos

Una sección de objeto consta de la palabra clave OBJECT seguida de una secuencia de declaraciones de objetos. Tiene la siguiente sintaxis:

OBJECT nombre_objeto:
     [ EXPORTED | PRIVATE | IMPORTED ] tipo_objeto
          [ PROCEDURE función_creación ]
          [ nombre_objeto [ WIDGET | GADGET ] | {definiciones_lista } ]

Utiliza una declaración de objeto para definir los objetos que se almacenarán en el archivo UID. Puedes referenciar el nombre del objeto en declaraciones que ocurran en otras partes del módulo UIL en cualquier contexto donde se pueda usar un nombre de objeto (por ejemplo, en una lista de controles, como referencia simbólica a un ID de widget, o como el argumento valor_etiqueta para un procedimiento de callback). Los objetos se pueden referenciar previamente; es decir, puedes declarar un nombre de objeto después de referenciarlo. Todas las referencias a un nombre de objeto deben ser consistentes con el tipo del objeto, según se especifica en la declaración del objeto. Puedes especificar un objeto como exportado, importado o privado.

La definición del objeto puede contener una secuencia de listas que definen los argumentos, la jerarquía y los callbacks para el widget. Solo puedes especificar una lista de cada tipo para un objeto. Cuando declares un widget definido por el usuario, debes incluir una referencia a la función de creación del widget para el widget definido por el usuario.

Nota: Varios widgets en el Toolkit Motif consisten en realidad en dos widgets enlazados. Por ejemplo, XmScrolledText y XmScrolledList consisten cada uno en los widgets hijos XmText y XmList bajo un widget XmScrolledWindow. Cuando se crea un widget de este tipo, sus recursos están disponibles para ambos widgets subyacentes. Esto puede causar problemas ocasionalmente, como cuando el programador quiere que una rutina XmNdestroyCallback se active cuando el widget se destruye. En este caso, el recurso de callback estará disponible para ambos sub-widgets, y causará un error cuando el widget se destruya. Para evitar estos problemas, el programador debe crear por separado los widgets padre e hijo, en lugar de depender de estos widgets enlazados.

Utiliza la palabra clave GADGET o WIDGET para especificar el tipo de objeto o para anular la variante predeterminada para este tipo de objeto. Puedes usar el nombre del Toolkit Motif de un tipo de objeto que tenga una variante gadget (por ejemplo, XmLabelGadget) como atributo de una declaración de objeto. El tipo_objeto puede ser cualquier tipo de objeto, incluidos los gadgets. Solo necesitas especificar la palabra clave GADGET o WIDGET en la declaración de un objeto, no cuando referencies el objeto. No puedes especificar la palabra clave GADGET o WIDGET para un objeto definido por el usuario; los objetos definidos por el usuario siempre son widgets.

Secciones de Identificadores

La sección de identificador permite definir un identificador, un mecanismo que logra la vinculación en tiempo de ejecución de datos a nombres que aparecen en un módulo UIL. La sección de identificador consta de la palabra clave reservada IDENTIFIER, seguida de una lista de nombres, cada nombre seguido de un punto y coma.

IDENTIFIER nombre_identificador; [...;]

Posteriormente, puedes usar estos nombres en el módulo UIL como el valor de un argumento de un widget o como el valor de etiqueta para un procedimiento de callback. En tiempo de ejecución, utilizas las funciones de MRM MrmRegisterNames y MrmRegisterNamesInHierarchy para vincular el nombre del identificador con los datos (o, en el caso de callbacks, con la dirección de los datos) asociados con el identificador.

Cada módulo UIL tiene un único espacio de nombres; por lo tanto, no puedes usar un nombre que hayas utilizado para un valor, objeto o procedimiento como nombre de identificador en el mismo módulo.

El compilador UIL no realiza ninguna comprobación de tipos sobre el uso de identificadores en un módulo UIL. A diferencia de un valor UIL, un identificador no tiene un tipo UIL asociado. Independientemente del tipo particular para el que se defina un argumento de widget o una etiqueta de procedimiento de callback, puedes usar un identificador en ese contexto en lugar de un valor del tipo correspondiente.

Para referenciar estos nombres de identificador en un módulo UIL, utilizas el nombre del identificador donde quieras que se utilice su valor.

Directivas de Inclusión

La directiva de inclusión incorpora el contenido de un archivo especificado en un módulo UIL. Este mecanismo permite que varios módulos UIL compartan definiciones comunes. La sintaxis de la directiva de inclusión es la siguiente:

INCLUDE FILE nombre_archivo;

El compilador UIL reemplaza la directiva de inclusión con el contenido del archivo de inclusión y lo procesa como si este contenido hubiera aparecido en el archivo fuente UIL actual.

Puedes anidar archivos de inclusión; es decir, un archivo de inclusión puede contener directivas de inclusión. El compilador UIL puede procesar hasta 100 referencias (incluyendo el archivo que contiene el módulo UIL). Por lo tanto, puedes incluir hasta 99 archivos en un único módulo UIL, incluidos los archivos anidados. Cada vez que se abre un archivo, se cuenta como una referencia, por lo que incluir el mismo archivo dos veces cuenta como dos referencias.

El nombre_archivo es una cadena simple que contiene una especificación de archivo que identifica el archivo a incluir. Las reglas para encontrar el archivo especificado son similares a las reglas para encontrar archivos de encabezado, o archivos .h usando la directiva de inclusión, #include, con una cadena entre comillas en C. UIL usa la opción -I para especificar un directorio de búsqueda para los archivos de inclusión.

•
Si no proporcionas un directorio, el compilador UIL busca el archivo de inclusión en el directorio del archivo fuente principal.
•
Si el compilador no encuentra el archivo de inclusión allí, busca en el mismo directorio que el archivo fuente.
•
Si proporcionas un directorio, el compilador UIL busca solo en ese directorio el archivo.

Nombres y Cadenas

Los nombres pueden constar de cualquiera de los caracteres A a Z, a a z, 0 a 9, $ (signo de dólar) y _ (guion bajo). Los nombres no pueden comenzar con un dígito (0 a 9). La longitud máxima de un nombre es de 31 caracteres.

UIL te da la opción de nombres sensibles o insensibles a mayúsculas y minúsculas a través de una cláusula en la cabecera MODULE. Por ejemplo, si los nombres son sensibles a mayúsculas y minúsculas, los nombres "sample" y "Sample" son distintos entre sí. Si los nombres son insensibles a mayúsculas y minúsculas, estos nombres se tratan como el mismo nombre y se pueden usar indistintamente. Por defecto, UIL asume que los nombres son sensibles a mayúsculas y minúsculas.

En modo CASE-INSENSITIVE, el compilador genera todos los nombres en el archivo UID en mayúsculas. En modo CASE-SENSITIVE, los nombres aparecen en el archivo UIL exactamente como aparecen en la fuente.

Literales de Cadena

Un literal de cadena es una secuencia de cero o más caracteres de 8 o 16 bits o una combinación delimitada por ' (comillas simples) o " (comillas dobles). Los literales de cadena también pueden contener caracteres multibyte delimitados con comillas dobles. Los literales de cadena no pueden tener más de 2000 caracteres de longitud.

Un literal de cadena entre comillas simples puede abarcar varias líneas de origen. Para continuar un literal de cadena entre comillas simples, termine la línea continuada con una \ (barra invertida). El literal continúa con el primer carácter de la siguiente línea.

Los literales de cadena entre comillas dobles no pueden abarcar varias líneas de origen. (Dado que las cadenas entre comillas dobles pueden contener secuencias de escape y otros caracteres especiales, no puede usar el carácter de barra invertida para indicar la continuación de la cadena). Para construir un valor de cadena que deba abarcar varias líneas de origen, use el operador de concatenación descrito más adelante en esta sección.

La sintaxis de un literal de cadena es una de las siguientes:

'[cadena_de_caracteres]'
[#conjunto_de_caracteres]"[cadena_de_caracteres]"

Ambas formas de cadena asocian un conjunto de caracteres con un valor de cadena. UIL utiliza las siguientes reglas para determinar el conjunto de caracteres y el formato de almacenamiento para los literales de cadena:

•
Una cadena declarada como 'cadena' es equivalente a #conj_actual"cadena", donde conj_actual será la parte del codeset del valor de la variable de entorno LANG si está establecida o el valor de XmFALLBACK_CHARSET si LANG no está establecida o no tiene componente de codeset. Por defecto, XmFALLBACK_CHARSET es ISO8859-1 (equivalente a ISO_LATIN1), pero los proveedores pueden definir un valor predeterminado diferente.
•
Una cadena declarada como "cadena" es equivalente a #conj_caracteres"cadena" si especificó conj_caracteres como el conjunto de caracteres predeterminado para el módulo. Si no se ha especificado un conjunto de caracteres predeterminado para el módulo, entonces si se proporciona la opción -s al comando uil o si se establece el indicador use_setlocale_flag para el compilador invocable, Uil(), la cadena se interpretará como una cadena en la configuración regional actual. Esto significa que la cadena se analiza en la configuración regional del usuario llamando a setlocale, su conjunto de caracteres es XmFONTLIST_DEFAULT_TAG, y que si la cadena se convierte a una cadena compuesta, se almacena como un segmento de texto codificado por configuración regional. De lo contrario, "cadena" es equivalente a #conj_actual"cadena", donde conj_actual se interpreta como se describe para las cadenas entre comillas simples.
•
Una cadena de la forma "cadena" o #conj_caracteres"cadena" se almacena como una cadena terminada en nulo.

Si el conj_caracteres en una cadena especificada en la forma anterior no es un conjunto de caracteres incorporado, y no es un conjunto de caracteres definido por el usuario, el conjunto de caracteres de la cadena se establecerá en XmFONTLIST_DEFAULT_TAG, y se emitirá un mensaje informativo al usuario para indicar que se ha realizado esta sustitución.

Literales de cadena compuesta

Una cadena compuesta consta de una cadena de caracteres de 8 bits, 16 bits o multibyte, un conjunto de caracteres con nombre y una dirección de escritura. Su tipo de datos UIL es compound_string.

La dirección de escritura de una cadena compuesta se deduce del conjunto de caracteres especificado para la cadena. Puede establecer explícitamente la dirección de escritura de una cadena compuesta utilizando la función COMPOUND_STRING.

Una cadena compuesta puede consistir en una secuencia de cadenas compuestas concatenadas, cadenas terminadas en nulo o una combinación de ambas, cada una de las cuales puede tener una propiedad de conjunto de caracteres y dirección de escritura diferentes. Utilice el operador de concatenación & (ampersand) para crear una secuencia de cadenas compuestas.

Cada cadena de la secuencia se almacena, incluida la información sobre el conjunto de caracteres y la dirección de escritura.

Generalmente, un literal de cadena se almacena en el archivo UID cuando el literal consta de cadenas concatenadas con diferentes conjuntos de caracteres o direcciones de escritura, o cuando utiliza la cadena para especificar un valor para un argumento que requiere un valor de cadena compuesta. Si desea garantizar que un literal de cadena se almacene como una cadena compuesta, debe utilizar la función COMPOUND_STRING.

Literal booleano

Un literal booleano representa el valor Verdadero (palabra clave reservada TRUE o On) o Falso (palabra clave reservada FALSE o Off). Estas palabras clave están sujetas a las reglas de distinción entre mayúsculas y minúsculas.

En un archivo UID, TRUE se representa con el valor entero 1 y FALSE se representa con el valor entero 0 (cero).

El consumo de almacenamiento de datos para literales booleanos es el mismo que para los literales enteros.

Un literal de punto flotante representa el valor de un número real (o flotante). Los literales de punto flotante tienen la siguiente forma:

Una cadena puede ser una cadena compuesta única o una secuencia de cadenas compuestas. Si las dos cadenas concatenadas tienen propiedades diferentes (como dirección de escritura o conjunto de caracteres), el resultado de la concatenación es una cadena compuesta de múltiples segmentos.

•
Uno de los operandos es una cadena compuesta
•
Los operandos tienen propiedades de conjunto de caracteres diferentes
•
Los operandos tienen direcciones de escritura diferentes

Entonces, la cadena resultante es una cadena compuesta. No puedes usar valores importados o exportados como operandos del operador de concatenación.

El resultado de cada operador tiene el mismo tipo que sus operandos. No puedes mezclar tipos en una expresión sin usar rutinas de conversión.

Puedes usar paréntesis para anular la precedencia normal de los operadores. En una secuencia de operadores unarios, las operaciones se realizan en orden de derecha a izquierda. Por ejemplo, - + -A es equivalente a -(+(-A)). En una secuencia de operadores binarios de la misma precedencia, las operaciones se realizan en orden de izquierda a derecha. Por ejemplo, A*B/C*D es equivalente a ((A*B)/C)*D.

Una declaración de valor le da un nombre a un valor. No puedes redefinir el valor de ese nombre en una declaración de valor posterior. Puedes usar un valor que contenga operadores y funciones en cualquier lugar donde puedas usar un valor en un módulo UIL. No puedes usar valores importados como operandos en expresiones.

Varios de los operadores binarios están definidos para múltiples tipos de datos. Por ejemplo, el operador de multiplicación (*) está definido para operandos de punto flotante y enteros.

Para que el compilador UIL realice estas operaciones binarias, ambos operandos deben ser del mismo tipo. Si proporcionas operandos de diferentes tipos de datos, el compilador UIL convierte automáticamente uno de los operandos al tipo del otro de acuerdo con las siguientes reglas de conversión:

•
Si los operandos son un entero y un booleano, el booleano se convierte a un entero.
•
Si los operandos son un entero y un punto flotante, el entero se convierte a un punto flotante.
•
Si los operandos son un punto flotante y un booleano, el booleano se convierte a un punto flotante.

También puedes convertir explícitamente el tipo de datos de un valor usando una de las funciones de conversión INTEGER, FLOAT o SINGLE_FLOAT.

NAME

UIL, Uil - User Interface Language compiler

SYNOPSIS

uil [-Idirectory] [-w] [-o outputfile] [-s] [-m] [-v] [-x] [-d] [-n] [-p] [-l] [uilfile] ...

DESCRIPTION

The uil command compiles a User Interface Language (UIL) source file into a compiled binary file that can be read by the Motif toolkit widgets.

The UIL compiler translates the source code into an intermediate representation that is specific to the Motif toolkit. This compiled file contains definitions of widgets, controls, actions, and other resources that can be used to create and manage a Motif application's user interface.

The uil command supports several options to control the compilation process:

-Idirectory
Adds a directory to the search path for imported UIL files. This option can be specified multiple times.
-w
Enables warnings for potential issues in the UIL source code.
-o outputfile
Specifies the name of the output file. If not specified, the output file will have the same base name as the input file but with a .uid extension.
-s
Causes the compiler to output a symbol table in addition to the compiled file. This is useful for debugging.
-m
Generates a listing file that includes the source code, line numbers, and any errors or warnings.
-v
Enables verbose output, showing more details about the compilation process.
-x
Prints a summary of the UIL file's contents, such as the number of widgets, controls, and actions defined.
-d
Enables extended debugging information.
-n
Disables the generation of the header file.
-p
Specifies the default value for the XmNtranslations resource. This option is used to handle translation table overrides. By default, duplicate translations are to be ignored. For example, if a translation for <Btn1Down> is already defined in the current translations for a PushButton, the translation defined by new_translations overrides the current definition. If the #augment directive is specified, the current definition takes precedence. The #replace directive replaces all current translations with those specified in the XmNtranslations resource.

Renditions and Render Tables

In addition to the string direction, each compound string carries a great deal of information about how its text is to be rendered. Each compound string contains a "tag," identifying the "rendition" to be used to draw that string. The rendition contains such information as the font, the size, the color, whether the text is to be underlined or crossed out, and the position and style of any tab stops. Many renditions are combined into a "render table," which is specified to any widget with the XmNrenderTable resource, and in the widget's controls list.

UIL implements render tables, renditions, tab lists, and tab stops as a special class of objects, in a form similar to the widget class. These objects are not themselves widgets or gadgets, but the format used by UIL to specify widget resources provides a convenient way to specify the qualities and dependencies of these objects.

For example, a render table, included in some widget's controls list, must also have a controls list in its specification, containing the names of its member renditions. Each rendition, in its specification, will contain an arguments list specifying such qualities as the font, the color, and whether the text is to be underlined. Any of the renditions may also control a tablist, which will itself control one or more tab stops.

Please refer to the Motif Programmer's Guide for a complete description of renditions and render tables, and for an example of how to use them in UIL.
