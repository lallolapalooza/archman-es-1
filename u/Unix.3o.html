exception Unix_error de error * string * string

Lanzada por las llamadas al sistema siguientes cuando se encuentra un error. El primer componente es el código de error; el segundo componente es el nombre de la función; el tercer componente es el parámetro de cadena para la función, si tiene uno, o la cadena vacía en caso contrario.

UnixLabels.Unix_error y Unix.Unix_error son lo mismo, y capturar uno capturará el otro.

val execv : string -> string array -> 'a

**execv prog args** ejecuta el programa en el archivo **prog**, con los argumentos **args** y el entorno del proceso actual. Ten en cuenta que el primer argumento, args.(0), es por convención el nombre del archivo del programa que se está ejecutando, al igual que Sys.argv.(0). Estas funciones **execv*** nunca retornan: en caso de éxito, el programa actual es reemplazado por el nuevo.

En Windows: la CRT simplemente inicia un nuevo proceso y sale del actual. Esto tendrá consecuencias no deseadas si, por ejemplo, otro proceso está esperando al actual. Se recomienda usar **Unix.create_process** o una de las funciones **open_process_*** en su lugar.

**Lanza Unix_error** en caso de error

val fork : unit -> int

Crea un nuevo proceso. El entero devuelto es 0 para el proceso hijo, el pid del proceso hijo para el proceso padre. Falla si el proceso OCaml es multinúcleo (se ha iniciado algún dominio). Además, si se ha iniciado algún hilo del módulo Thread, el proceso hijo podría estar en un estado corrupto.

**Lanza Invalid_argument** en Windows. Usa **Unix.create_process** o hilos en su lugar.

**Lanza Failure** si se ha iniciado algún dominio.

val wait : unit -> int * process_status

Espera hasta que uno de los procesos hijos muera y devuelve su pid y estado de terminación.

**Lanza Invalid_argument** en Windows. Usa **Unix.waitpid** en su lugar.

val waitpid : wait_flag list -> int -> int * process_status

Igual que **Unix.wait**, pero espera al proceso hijo cuyo pid se proporciona. Un pid de **-1** significa esperar a cualquier hijo. Un pid de **0** significa esperar a cualquier hijo en el mismo grupo de procesos que el proceso actual. Los argumentos de pid negativos representan grupos de procesos. La lista de opciones indica si **waitpid** debe devolver inmediatamente sin esperar y si debe informar de los hijos detenidos.

En Windows: solo puede esperar a un PID dado, no a cualquier proceso hijo.

val system : string -> process_status

Ejecuta el comando dado, espera hasta que termine y devuelve su estado de terminación. La cadena es interpretada por el shell **/bin/sh** (o el intérprete de comandos **cmd.exe** en Windows) y, por lo tanto, puede contener redirecciones, comillas, variables, etc. Para citar correctamente los espacios en blanco y los caracteres especiales del shell que aparecen en nombres de archivos o argumentos de comandos, se recomienda el uso de **Filename.quote_command**. El resultado **WEXITED 127** indica que el shell no pudo ser ejecutado.

val _exit : int -> 'a

Termina el proceso que llama inmediatamente, devolviendo el código de estado dado al sistema operativo: generalmente 0 para indicar que no hay errores y un entero positivo pequeño para indicar un fallo. A diferencia de **exit**, **Unix._exit** no realiza ninguna finalización: las funciones registradas con **at_exit** no se llaman, los canales de entrada/salida no se vacían y el sistema de tiempo de ejecución de C tampoco se finaliza.

El uso típico de **Unix._exit** es después de una operación **Unix.fork**, cuando el proceso hijo encuentra un error fatal y debe salir. En este caso, es preferible no realizar ninguna acción de finalización en el proceso hijo, ya que estas acciones podrían interferir con acciones similares realizadas por el proceso padre. Por ejemplo, los canales de salida no deben ser vaciados por el proceso hijo, ya que el proceso padre puede vaciarlos nuevamente más tarde, lo que resultaría en una salida duplicada.

Enlaces simbólicos

val symlink : ?to_dir:bool -> string -> string -> unit

symlink ?to_dir src dst crea el archivo dst como un enlace simbólico al archivo src. En Windows, ~to_dir indica si el enlace simbólico apunta a un directorio o a un archivo; si se omite, symlink examina src usando stat y elige apropiadamente; si src no existe, se asume false (por esta razón, se recomienda especificar el parámetro ~to_dir en código nuevo). En Unix, ~to_dir se ignora.

Los enlaces simbólicos de Windows están disponibles a partir de Windows Vista. Existen algunas diferencias importantes entre los enlaces simbólicos de Windows y sus contrapartes POSIX.

Los enlaces simbólicos de Windows vienen en dos sabores: directorio y regular, que designan si el enlace simbólico apunta a un directorio o a un archivo. El tipo debe ser correcto: un enlace simbólico de directorio que en realidad apunta a un archivo no puede ser seleccionado con chdir y un enlace simbólico de archivo que en realidad apunta a un directorio no puede ser leído ni escrito (tenga en cuenta que la capa de emulación de Cygwin ignora esta distinción).

Cuando se crean enlaces simbólicos a destinos existentes, esta distinción no importa y symlink creará automáticamente el tipo correcto de enlace simbólico. La distinción importa cuando se crea un enlace simbólico a un destino inexistente.

La otra advertencia es que, por defecto, los enlaces simbólicos son una operación privilegiada. Los administradores siempre deberán ejecutarse con privilegios elevados (o con UAC deshabilitado) y, por defecto, las cuentas de usuario normales deberán tener el privilegio SeCreateSymbolicLinkPrivilege a través de la Directiva de Seguridad Local (secpol.msc) o a través de Active Directory.

Unix.has_symlink se puede usar para verificar que un proceso puede crear enlaces simbólicos.

En otras plataformas, simplemente indica que la llamada al sistema symlink está disponible.

val select : file_descr list -> file_descr list -> file_descr list -> float -> file_descr list * file_descr list * file_descr list

Espera hasta que algunas operaciones de entrada/salida sean posibles en algunos canales. Los tres argumentos de lista son, respectivamente, un conjunto de descriptores para verificar lectura (primer argumento), escritura (segundo argumento) o condiciones excepcionales (tercer argumento). El cuarto argumento es el tiempo de espera máximo, en segundos; un cuarto argumento negativo significa sin tiempo de espera (espera ilimitada). El resultado se compone de tres conjuntos de descriptores: los listos para leer (primer componente), listos para escribir (segundo componente) y sobre los cuales hay pendiente una condición excepcional (tercer componente).

En Windows, si una de las listas de descriptores excede los elementos de FD_SETSIZE (64 por defecto), o si se utiliza al menos un descriptor de archivo que no sea un socket, el tiempo de espera máximo se limita a 2^32 milisegundos.

Comandos para Unix.lockf.

val lockf : file_descr -> lock_command -> int -> unit

lockf fd mode len coloca un bloqueo en una región del archivo abierto como fd. La región comienza en la posición actual de lectura/escritura de fd (según lo establecido por Unix.lseek), y se extiende len bytes hacia adelante si len es positivo, len bytes hacia atrás si len es negativo, o hasta el final del archivo si len es cero. Un bloqueo de escritura evita que cualquier otro proceso adquiera un bloqueo de lectura o escritura en la región. Un bloqueo de lectura evita que cualquier otro proceso adquiera un bloqueo de escritura en la región, pero permite que otros procesos adquieran bloqueos de lectura en ella.

Los comandos F_LOCK y F_TLOCK intentan colocar un bloqueo de escritura en la región especificada. Los comandos F_RLOCK y F_TRLOCK intentan colocar un bloqueo de lectura en la región especificada. Si uno o varios bloqueos colocados por otro proceso impiden que el proceso actual adquiera el bloqueo, F_LOCK y F_RLOCK se bloquean hasta que estos bloqueos se eliminen, mientras que F_TLOCK y F_TRLOCK fallan inmediatamente con una excepción. F_ULOCK elimina cualquier bloqueo que el proceso actual tenga sobre la región especificada. Finalmente, el comando F_TEST prueba si se puede adquirir un bloqueo de escritura en la región especificada, sin colocar realmente un bloqueo. Devuelve inmediatamente si tiene éxito, o falla en caso contrario.

Lo que sucede cuando un proceso intenta bloquear una región de un archivo que ya está bloqueada por el mismo proceso depende del sistema operativo. En sistemas compatibles con POSIX, la segunda operación de bloqueo tiene éxito y puede "promocionar" el bloqueo anterior de bloqueo de lectura a bloqueo de escritura. En Windows, la segunda operación de bloqueo se bloqueará o fallará.

sigprocmask mode sigs cambia el conjunto de señales bloqueadas. Si mode es SIG_SETMASK, las señales bloqueadas se establecen a las de la lista sigs.

val open_connection : sockaddr -> in_channel * out_channel

Conéctate a un servidor en la dirección dada. Devuelve un par de canales con búfer conectados al servidor. Recuerda llamar a flush en el canal de salida en los momentos adecuados para asegurar una sincronización correcta.

Los dos canales devueltos por open_connection comparten un descriptor de socket. Por lo tanto, cuando la conexión haya terminado, debes llamar a close_out en el canal de salida, lo que también cerrará el socket subyacente. No llames a close_in en el canal de entrada; será recolectado por el GC eventualmente.

val shutdown_connection : in_channel -> unit

"Cierra" una conexión establecida con Unix.open_connection; es decir, transmite una condición de fin de archivo al servidor que lee en el otro lado de la conexión. Esto no cierra el socket ni los canales utilizados por la conexión. Consulta Unix.open_connection para saber cómo cerrarlos una vez que la conexión haya terminado.

val establish_server : (in_channel -> out_channel -> unit) -> sockaddr -> unit

Establece un servidor en la dirección dada. La función dada como primer argumento se llama para cada conexión con dos canales con búfer conectados al cliente. Se crea un nuevo proceso para cada conexión. La función Unix.establish_server nunca retorna normalmente.

Los dos canales proporcionados a la función comparten un descriptor de socket. La función no necesita cerrar los canales, ya que esto ocurre automáticamente cuando la función retorna. Si la función prefiere un cierre explícito, debe cerrar el canal de salida usando close_out y dejar el canal de entrada sin cerrar, por razones explicadas en Unix.in_channel_of_descr.

Note: The functions provided by this module are system-dependent. Some functions may not be available on all Unix systems, and their behavior may vary from one system to another. Some functions may also be unavailable on non-Unix systems like Windows.

val tcgetattr : file_descr -> terminal_io

Return the status of the terminal referred to by the given file descriptor.

Raises Invalid_argument on Windows

type setattr_when =
| TCSANOW
| TCSADRAIN
| TCSAFLUSH

val tcsetattr : file_descr -> setattr_when -> terminal_io -> unit

Set the status of the terminal referred to by the given file descriptor. The second argument indicates when the status change takes place: immediately ( TCSANOW ), when all pending output has been transmitted ( TCSADRAIN ), or after flushing all input that has been received but not read ( TCSAFLUSH ). TCSADRAIN is recommended when changing the output parameters; TCSAFLUSH , when changing the input parameters.

Raises Invalid_argument on Windows

val tcsendbreak : file_descr -> int -> unit

Send a break condition on the given file descriptor. The second argument is the duration of the break, in 0.1s units; 0 means standard duration (0.25s).

Raises Invalid_argument on Windows

val tcdrain : file_descr -> unit

Waits until all output written on the given file descriptor has been transmitted.

Raises Invalid_argument on Windows

type flush_queue =
| TCIFLUSH
| TCOFLUSH
| TCIOFLUSH

val tcflush : file_descr -> flush_queue -> unit

Discard data written on the given file descriptor but not yet transmitted, or data received but not yet read, depending on the second argument: TCIFLUSH flushes data received but not read, TCOFLUSH flushes data written but not transmitted, and TCIOFLUSH flushes both.

Raises Invalid_argument on Windows

type flow_action =
| TCOOFF
| TCOON
| TCIOFF
| TCION

val tcflow : file_descr -> flow_action -> unit

Suspend or restart reception or transmission of data on the given file descriptor, depending on the second argument: TCOOFF suspends output, TCOON restarts output, TCIOFF transmits a STOP character to suspend input, and TCION transmits a START character to restart input.

Raises Invalid_argument on Windows
