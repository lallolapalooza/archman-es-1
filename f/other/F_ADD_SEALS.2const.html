F_GET_SEALS(2const) F_GET_SEALS(2const)

NOMBRE

F_GET_SEALS, F_ADD_SEALS - obtener/añadir sellos de archivo

BIBLIOTECA

Biblioteca C estándar (libc,-lc)

SINOPSIS

#include <fcntl.h>
int fcntl(int fd, F_ADD_SEALS, int arg);
int fcntl(int fd, F_GET_SEALS);

DESCRIPCIÓN

Los sellos de archivo limitan el conjunto de operaciones permitidas en un archivo determinado. Por cada sello establecido en un archivo, un conjunto específico de operaciones fallará con EPERM en este archivo a partir de ese momento. Se dice que el archivo está sellado. El conjunto predeterminado de sellos depende del tipo del archivo subyacente y del sistema de archivos. Para una descripción general del sellado de archivos, una discusión de su propósito y algunos ejemplos de código, véase memfd_create(2).

Actualmente, los sellos de archivo solo pueden aplicarse a un descriptor de archivo devuelto por memfd_create(2) (si se empleó MFD_ALLOW_SEALING ). En otros sistemas de archivos, todas las operaciones de fcntl() que operan sobre sellos devolverán EINVAL.

Los sellos son una propiedad de un inodo. Por lo tanto, todos los descriptores de archivo abiertos que se refieren al mismo inodo comparten el mismo conjunto de sellos. Además, los sellos nunca pueden eliminarse, solo añadirse.

F_ADD_SEALS
Añade los sellos dados en el argumento de máscara de bits arg al conjunto de sellos del inodo al que se refiere el descriptor de archivo fd. Los sellos no pueden eliminarse de nuevo. Una vez que esta llamada tiene éxito, los sellos son aplicados por el kernel inmediatamente. Si el conjunto actual de sellos incluye F_SEAL_SEAL (véase más abajo), entonces esta llamada será rechazada con EPERM. Añadir un sello que ya está establecido es una operación nula, en caso de que F_SEAL_SEAL no esté ya establecido. Para colocar un sello, el descriptor de archivo fd debe ser escribible.
F_GET_SEALS
Devuelve (como resultado de la función) el conjunto actual de sellos del inodo al que se refiere fd. Si no hay sellos establecidos, se devuelve 0. Si el archivo no soporta sellado, se devuelve -1 y errno se establece en EINVAL.

Los siguientes sellos están disponibles:

F_SEAL_SEAL
Si este sello está establecido, cualquier llamada posterior a fcntl() con F_ADD_SEALS falla con el error EPERM. Por lo tanto, este sello evita cualquier modificación al conjunto de sellos en sí mismo. Si el conjunto inicial de sellos de un archivo incluye F_SEAL_SEAL, esto efectivamente hace que el conjunto de sellos sea constante y bloqueado.
F_SEAL_SHRINK
Si este sello está establecido, el archivo en cuestión no puede reducirse de tamaño. Esto afecta a open(2) con el indicador O_TRUNC así como a truncate(2) y ftruncate(2). Esas llamadas fallan con EPERM si intentas reducir el archivo en cuestión. Aumentar el tamaño del archivo sigue siendo posible.
F_SEAL_GROW
Si este sello está establecido, el tamaño del archivo en cuestión no puede aumentarse. Esto afecta a write(2) más allá del final del archivo, truncate(2), ftruncate(2), y fallocate(2). Estas llamadas fallan con EPERM si las usas para aumentar el tamaño del archivo. Si mantienes el tamaño o lo reduces, esas llamadas seguirán funcionando como se espera.
F_SEAL_WRITE
Si este sello está establecido, no puedes modificar el contenido del archivo. Ten en cuenta que reducir o aumentar el tamaño del archivo sigue siendo posible y permitido. Por lo tanto, este sello normalmente se usa en combinación con uno de los otros sellos. Este sello afecta a write(2) y fallocate(2) (solo en combinación con el indicador FALLOC_FL_PUNCH_HOLE ). Esas llamadas fallan con EPERM si este sello está establecido. Además, intentar crear nuevos mapeos de memoria compartidos y escribibles mediante mmap(2) también fallará con EPERM.
Usar la operación F_ADD_SEALS para establecer el sello F_SEAL_WRITE falla con EBUSY si existe algún mapeo compartido y escribible. Esos mapeos deben ser desmapeados antes de poder añadir este sello. Además, si hay alguna operación de E/S asíncrona (io_submit(2)) pendiente en el archivo, todas las escrituras pendientes serán descartadas.
F_SEAL_FUTURE_WRITE (desde Linux 5.1)
El efecto de este sello es similar a F_SEAL_WRITE, pero el contenido del archivo todavía puede modificarse mediante mapeos compartidos y escribibles que fueron creados antes de que se estableciera el sello. Cualquier intento de crear un nuevo mapeo escribible en el archivo mediante mmap(2) fallará con EPERM. Del mismo modo, un intento de escribir en el archivo mediante write(2) fallará con EPERM.
Usando este sello, un proceso puede crear un búfer de memoria que puede seguir modificando mientras comparte ese búfer en una base de "solo lectura" con otros procesos.

VALOR DE RETORNO

F_GET_SEALS
Una máscara de bits que identifica los sellos que han sido establecidos para el inodo al que se refiere fd.
F_ADD_SEALS
Cero.

En caso de error, se devuelve -1, y errno se establece para indicar el error.

ERRORES

Véase fcntl(2).

EBUSY
op es F_ADD_SEALS, arg incluye F_SEAL_WRITE, y existe un mapeo compartido y escribible en el archivo al que se refiere fd.
EINVAL
op es F_ADD_SEALS y arg incluye un bit de sellado no reconocido.
EINVAL
El sistema de archivos que contiene el inodo al que se refiere fd no soporta sellado.
EPERM
op era F_ADD_SEALS, pero fd no estaba abierto para escritura o el conjunto actual de sellos en el archivo ya incluye F_SEAL_SEAL.
