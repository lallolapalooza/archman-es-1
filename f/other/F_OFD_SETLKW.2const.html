NOMBRE

BIBLIOTECA

Biblioteca C estándar (libc,-lc)

SINOPSIS

#include <fcntl.h>
int fcntl(int fd, F_GETLK, struct flock *lock);
int fcntl(int fd, F_SETLK, const struct flock *lock);
int fcntl(int fd, F_SETLKW, const struct flock *lock);
int fcntl(int fd, F_OFD_GETLK, struct flock *lock);

int fcntl(int fd, F_OFD_SETLKW, const struct flock *lock);

DESCRIPCIÓN

Bloqueo de registros consultivo

Linux implementa los bloqueos de registros UNIX tradicionales ("asociados al proceso"), estandarizados por POSIX. Para una alternativa específica de Linux con mejor semántica, consulte la discisión sobre los bloqueos de descripciones de archivo abierto más abajo.

F_SETLK, F_SETLKWy F_GETLK se utilizan para adquirir, liberar y comprobar la existencia de bloqueos de registro (también conocidos como bloqueos de rango de bytes, de segmento de archivo o de región de archivo). El tercer argumento, lock, es un puntero a una estructura que tiene al menos los siguientes campos (en un orden no especificado).


struct flock {
    ...
    short l_type;    /* Tipo de bloqueo: F_RDLCK,
                        F_WRLCK, F_UNLCK */
    short l_whence;  /* Cómo interpretar l_start:
                        SEEK_SET, SEEK_CUR, SEEK_END */
    off_t l_start;   /* Desplazamiento inicial del bloqueo */
    off_t l_len;     /* Número de bytes a bloquear */
    pid_t l_pid;     /* PID del proceso que bloquea nuestro bloqueo
                        (establecido por F_GETLK y F_OFD_GETLK) */
    ...
};

Los campos l_whence, l_starty l_len de esta estructura especifican el rango de bytes que deseamos bloquear. Se pueden bloquear bytes más allá del final del archivo, pero no bytes antes del inicio del archivo.

l_start es el desplazamiento inicial del bloqueo, y se interpreta en relación con: el inicio del archivo (si l_whence es SEEK_SET); el desplazamiento actual del archivo (si l_whence es SEEK_CUR); o el final del archivo (si l_whence es SEEK_END). En los dos últimos casos, l_start puede ser un número negativo siempre que el desplazamiento no esté antes del inicio del archivo.

l_len especifica el número de bytes a bloquear. Si l_len es positivo, entonces el rango a bloquear cubre los bytes l_start hasta e incluyendo l_start+l_len-1. Especificar 0 para l_len tiene el significado especial: bloquear todos los bytes que comienzan en la ubicación especificada por l_whence y l_start hasta el final del archivo, sin importar cuán grande crezca el archivo.

POSIX.1-2001 permite (pero no requiere) que una implementación soporte un valor l_len negativo; si l_len es negativo, el intervalo descrito por lock cubre los bytes l_start+l_len hasta e incluyendo l_start-1. Esto es soportado desde Linux 2.4.21 y Linux 2.5.49.

El campo l_type se puede usar para colocar un bloqueo de lectura (F_RDLCK) o de escritura (F_WRLCK) en un archivo. Un número arbitrario de procesos pueden mantener un bloqueo de lectura (bloqueo compartido) en una región de archivo, pero solo un proceso puede mantener un bloqueo de escritura (bloqueo exclusivo). Un bloqueo exclusivo excluye todos los demás bloqueos, tanto compartidos como exclusivos. Un solo proceso puede mantener solo un tipo de bloqueo en una región de archivo; si se aplica un nuevo bloqueo a una región ya bloqueada, entonces el bloqueo existente se convierte al nuevo tipo de bloqueo. (Tales conversiones pueden implicar dividir, reducir o fusionar con un bloqueo existente si el rango de bytes especificado por el nuevo bloqueo no coincide exactamente con el rango del bloqueo existente.)

F_SETLK
Adquirir un bloqueo (cuando l_type es F_RDLCK o F_WRLCK) o liberar un bloqueo (cuando l_type es F_UNLCK) en los bytes especificados por los campos l_whence, l_starty l_len de lock. Si otro proceso mantiene un bloqueo en conflicto, esta llamada devuelve -1 y establece errno en EACCES o EAGAIN. (El error devuelto en este caso varía entre implementaciones, por lo que POSIX requiere que una aplicación portátil compruebe ambos errores.)
F_SETLKW
Igual que F_SETLK, pero si se mantiene un bloqueo en conflicto en el archivo, entonces espera a que ese bloqueo sea liberado. Si se captura una señal mientras espera, entonces la llamada se interrumpe y (después de que el manejador de señales haya retornado) retorna inmediatamente (con valor de retorno -1 y errno establecido en EINTR; véase signal(7)).
F_GETLK
En la entrada de esta llamada, lock describe un bloqueo que nos gustaría colocar en el archivo. Si el bloqueo pudiera colocarse, fcntl() no lo coloca realmente, sino que devuelve F_UNLCK en el campo l_type de lock y deja los demás campos de la estructura sin cambios.
Si uno o más bloqueos incompatibles impedirían que este bloqueo se colocara, entonces fcntl() devuelve detalles sobre uno de esos bloqueos en los campos l_type, l_whence, l_starty l_len de lock. Si el bloqueo en conflicto es un bloqueo de registro tradicional (asociado al proceso), entonces el campo l_pid se establece en el PID del proceso que mantiene ese bloqueo. Si el bloqueo en conflicto es un bloqueo de descripción de archivo abierto, entonces l_pid se establece en -1. Tenga en cuenta que la información devuelta puede estar desactualizada para cuando el llamador la inspeccione.

Para colocar un bloqueo de lectura, fd debe estar abierto para lectura. Para colocar un bloqueo de escritura, fd debe estar abierto para escritura. Para colocar ambos tipos de bloqueo, abra un archivo en modo lectura-escritura.

Al colocar bloqueos con F_SETLKW, el kernel detecta interbloqueos(deadlocks), en los que dos o más procesos tienen sus solicitudes de bloqueo mutuamente bloqueadas por bloqueos mantenidos por los otros procesos. Por ejemplo, suponga que el proceso A mantiene un bloqueo de escritura en el byte 100 de un archivo, y el proceso B mantiene un bloqueo de escritura en el byte 200. Si cada proceso intenta entonces bloquear el byte ya bloqueado por el otro proceso usando F_SETLKW, entonces, sin detección de interbloqueos, ambos procesos permanecerían bloqueados indefinidamente. Cuando el kernel detecta tales interbloqueos, hace que una de las solicitudes de bloqueo que causan el bloqueo falle inmediatamente con el error EDEADLK; una aplicación que encuentre tal error debería liberar algunos de sus bloqueos para permitir que otras aplicaciones continúen antes de intentar recuperar los bloqueos que necesita. Los interbloqueos circulares que involucran a más de dos procesos también son detectados. Tenga en cuenta, sin embargo, que hay limitaciones en el algoritmo de detección de interbloqueos del kernel; véase ERRORES.

Además de ser eliminados por un F_UNLCKexplícito, los bloqueos de registro se liberan automáticamente cuando el proceso termina.

Los bloqueos de registro no son heredados por un hijo creado mediante fork(2), pero se conservan a través de un execve(2).

Debido al almacenamiento en búfer realizado por la stdio(3) biblioteca, el uso del bloqueo de registro con rutinas de ese paquete debe evitarse; use read(2) y write(2) en su lugar.

Los bloqueos de registro descritos anteriormente están asociados con el proceso (a diferencia de los bloqueos de descripción de archivo abierto descritos más abajo). Esto tiene algunas consecuencias desafortunadas:

•
Si un proceso cierra cualquier descriptor de archivo que se refiera a un archivo, entonces todos los bloqueos del proceso en ese archivo se liberan, independientemente del descriptor (descriptores) en el que se obtuvieron los bloqueos. Esto es malo: significa que un proceso puede perder sus bloqueos en un archivo como /etc/passwd o /etc/mtab cuando por alguna razón una función de biblioteca decide abrir, leer y cerrar el mismo archivo.
•
Los hilos en un proceso comparten bloqueos. En otras palabras, un programa multihilo no puede usar el bloqueo de registro para asegurar que los hilos no accedan simultáneamente a la misma región de un archivo.

Los bloqueos de descripción de archivo abierto resuelven ambos problemas.

Bloqueos de descripción de archivo abierto (no-POSIX)</h2>

Los bloqueos de descripción de archivo abierto son bloqueos de rango de bytes consultivos cuya operación es en la mayoría de los aspectos idéntica a la de los bloqueos de registro tradicionales descritos anteriormente. Este tipo de bloqueo es específico de Linux y está disponible desde Linux 3.15. (Existe una propuesta ante el Grupo Austin para incluir este tipo de bloqueo en la próxima revisión de POSIX.1.) Para una explicación de las descripciones de archivo abierto, véase open(2).

La diferencia principal entre los dos tipos de bloqueo es que, mientras que los bloqueos de registro tradicionales están asociados con un proceso, los bloqueos de descripción de archivo abierto están asociados con la descripción de archivo abierto con la que se adquieren, de manera muy similar a los bloqueos adquiridos con flock(2). En consecuencia (y a diferencia de los bloqueos de registro consultivos tradicionales), los bloqueos de descripción de archivo abierto se heredan a través de fork(2) (y clone(2) con CLONE_FILES), y solo se liberan automáticamente en el último cierre de la descripción de archivo abierto, en lugar de liberarse en cualquier cierre del archivo.

Las combinaciones de bloqueos conflictivos (es decir, un bloqueo de lectura y un bloqueo de escritura o dos bloqueos de escritura) donde un bloqueo es un bloqueo de descripción de archivo abierto y el otro es un bloqueo de registro tradicional, entran en conflicto incluso cuando son adquiridos por el mismo proceso en el mismo descriptor de archivo.

Los bloqueos de descripción de archivo abierto colocados a través de la misma descripción de archivo abierto (es decir, a través del mismo descriptor de archivo, o a través de un duplicado del descriptor de archivo creado por fork(2), dup(2), F_DUPFD(2const), etc.) son siempre compatibles: si se coloca un nuevo bloqueo en una región ya bloqueada, entonces el bloqueo existente se convierte al nuevo tipo de bloqueo. (Tales conversiones pueden resultar en la división, reducción o fusión con un bloqueo existente, como se discutió anteriormente.)

Por otro lado, los bloqueos de descripción de archivo abierto pueden entrar en conflicto entre sí cuando se adquieren a través de diferentes descripciones de archivo abierto. Así, los hilos en un programa multihilo pueden usar bloqueos de descripción de archivo abierto para sincronizar el acceso a una región de archivo haciendo que cada hilo realice su propio open(2) sobre el archivo y aplique bloqueos a través del descriptor de archivo resultante.

Al igual que con los bloqueos consultivos tradicionales, el tercer argumento de fcntl(), lock, es un puntero a una estructura flock . En contraste con los bloqueos de registro tradicionales, el campo l_pid de esa estructura debe establecerse en cero cuando se usan las operaciones descritas a continuación.

Las operaciones para trabajar con bloqueos de descripción de archivo abierto son análogas a las utilizadas con bloqueos tradicionales:

F_OFD_SETLK
Adquirir un bloqueo de descripción de archivo abierto (cuando l_type es F_RDLCK o F_WRLCK) o liberar un bloqueo de descripción de archivo abierto (cuando l_type es F_UNLCK) sobre los bytes especificados por los campos l_whence, l_starty l_len de lock. Si otro proceso mantiene un bloqueo conflictivo, esta llamada devuelve -1 y establece errno en EAGAIN.
F_OFD_SETLKW
Igual que F_OFD_SETLK, pero si se mantiene un bloqueo conflictivo sobre el archivo, espera a que ese bloqueo sea liberado. Si se captura una señal mientras espera, la llamada se interrumpe y (después de que el manejador de señales haya retornado) retorna inmediatamente (con valor de retorno -1 y errno establecido en EINTR; véase signal(7)).
F_OFD_GETLK
En la entrada a esta llamada, lock describe un bloqueo de descripción de archivo abierto que nos gustaría colocar sobre el archivo. Si el bloqueo pudiera ser colocado, fcntl() no lo coloca realmente, sino que devuelve F_UNLCK en el campo l_type de lock y deja los otros campos de la estructura sin cambios. Si uno o más bloqueos incompatibles evitarían que este bloqueo sea colocado, entonces los detalles sobre uno de estos bloqueos son devueltos a través de lock, como se describió anteriormente para F_GETLK.

En la implementación actual, no se realiza detección de interbloqueos para bloqueos de descripción de archivo abierto. (Esto contrasta con los bloqueos de registro asociados a procesos, para los cuales el kernel sí realiza detección de interbloqueos.)

Bloqueo obligatorio

Advertencia: la implementación en Linux del bloqueo obligatorio es poco fiable. Véase ERRORES más abajo. Debido a estos errores, y al hecho de que se cree que la característica es poco utilizada, desde Linux 4.5, el bloqueo obligatorio se ha convertido en una característica opcional, gobernada por una opción de configuración (CONFIG_MANDATORY_FILE_LOCKING). Esta característica ya no es soportada en absoluto en Linux 5.15 y versiones superiores.

Por defecto, tanto los bloqueos de registro tradicionales (asociados a procesos) como los de descripción de archivo abierto son consultivos. Los bloqueos consultivos no son forzados y son útiles solo entre procesos cooperativos.

Ambos tipos de bloqueo también pueden ser obligatorios. Los bloqueos obligatorios son forzados para todos los procesos. Si un proceso intenta realizar un acceso incompatible (por ejemplo, read(2) o write(2)) sobre una región de archivo que tiene un bloqueo obligatorio incompatible, entonces el resultado depende de si el indicador O_NONBLOCK está habilitado para su descripción de archivo abierto. Si el indicador O_NONBLOCK no está habilitado, entonces la llamada al sistema se bloquea hasta que el bloqueo sea removido o convertido a un modo que sea compatible con el acceso. Si el indicador O_NONBLOCK está habilitado, entonces la llamada al sistema falla con el error EAGAIN.

Para hacer uso de los bloqueos obligatorios, el bloqueo obligatorio debe estar habilitado tanto en el sistema de archivos que contiene el archivo a bloquear, como en el archivo mismo. El bloqueo obligatorio se habilita en un sistema de archivos usando la opción "-o mand" de mount(8), o el indicador MS_MANDLOCK de mount(2). El bloqueo obligatorio se habilita en un archivo deshabilitando el permiso de ejecución para el grupo en el archivo y habilitando el bit de permiso set-group-ID (véase chmod(1) y chmod(2)).

El bloqueo obligatorio no está especificado por POSIX. Algunos otros sistemas también soportan bloqueo obligatorio, aunque los detalles de cómo habilitarlo varían entre sistemas.

Bloqueos perdidos

Cuando se obtiene un bloqueo consultivo en un sistema de archivos en red como NFS, es posible que el bloqueo pueda perderse. Esto puede suceder debido a una acción administrativa en el servidor, o debido a una partición de red (es decir, pérdida de conectividad de red con el servidor) que dura lo suficiente para que el servidor asuma que el cliente ya no está funcionando.

Cuando el sistema de archivos determina que un bloqueo ha sido perdido, las solicitudes futuras de read(2) o write(2) pueden fallar con el error EIO. Este error persistirá hasta que el bloqueo sea removido o el descriptor de archivo sea cerrado. Desde Linux 3.12, esto sucede al menos para NFSv4 (incluyendo todas las versiones menores).

Algunas versiones de UNIX envían una señal (SIGLOST) en esta circunstancia. Linux no define esta señal, y no proporciona ninguna notificación asíncrona de bloqueos perdidos.

VALOR DE RETORNO

Cero.

En caso de error, se devuelve -1, y errno se establece para indicar el error.

ERRORES

Véase fcntl(2).

EBADF
op es F_SETLK o F_SETLKW y el modo de apertura del descriptor de archivo no coincide con el tipo de bloqueo solicitado.
EDEADLK
Se detectó que la operación F_SETLKW especificada causaría un interbloqueo.
EFAULT
lock está fuera de tu espacio de direcciones accesible.
EINTR
op es F_SETLKW o F_OFD_SETLKW y la operación fue interrumpida por una señal; véase signal(7).
EINTR
op es F_GETLK, F_SETLK, F_OFD_GETLKo F_OFD_SETLK, y la operación fue interrumpida por una señal antes de que el bloqueo fuera verificado o adquirido. Lo más probable al bloquear un archivo remoto (por ejemplo, bloqueando sobre NFS), pero a veces puede suceder localmente.
EINVAL
op es F_OFD_SETLK, F_OFD_SETLKWo F_OFD_GETLK, y l_pid no fue especificado como cero.
ENOLCK
Demasiados bloqueos de segmento abiertos, la tabla de bloqueos está llena, o un protocolo de bloqueo remoto falló (por ejemplo, bloqueando sobre NFS).

NOTAS

Bloqueo de archivos

La llamada al sistema original fcntl() de Linux no fue diseñada para manejar desplazamientos de archivo grandes (en la estructura flock ). En consecuencia, se añadió una llamada al sistema fcntl64() en Linux 2.4. La llamada al sistema más reciente emplea una estructura diferente para el bloqueo de archivos, flock64, y operaciones correspondientes, F_GETLK64, F_SETLK64y F_SETLKW64. Sin embargo, estos detalles pueden ser ignorados por las aplicaciones que usan glibc, cuya función envolvente fcntl() emplea transparentemente la llamada al sistema más reciente donde está disponible.

Bloqueos de registro

Desde Linux 2.0, no hay interacción entre los tipos de bloqueo

NOTAS

La funcionalidad de bloqueo de archivos de fcntl(2) está documentada en la página de manual fcntl(2). Los detalles específicos de los bloqueos de registros son los siguientes:

Estructura de flock

La estructura fcntl(2) flock(2) es la siguiente:

struct flock {
    off_t   l_start;    /* Inicio del rango bloqueado */
    off_t   l_len;      /* Longitud del rango bloqueado (0 significa hasta EOF) */
    pid_t   l_pid;      /* PID del proceso que posee el bloqueo */
    short   l_type;     /* Tipo de bloqueo: F_RDLCK, F_WRLCK, F_UNLCK */
    short   l_whence;   /* A partir de dónde: SEEK_SET, SEEK_CUR, SEEK_END */
};

Por lo general, el campo l_pid solo es útil cuando el bloqueo se realiza en un sistema de archivos local. Los bloqueos en sistemas de archivos de red, como NFS, pueden no tener el campo l_pid relleno correctamente o no disponible.

Los bloqueos de registros son mantenidos por el kernel y pueden ser establecidos por fcntl(2) y flock(2).

Varios sistemas tienen campos adicionales en struct flock tales como, por ejemplo, l_sysid (para identificar la máquina donde se detenta el bloqueo). Claramente, l_pid por sí solo no será muy útil si el proceso que detenta el bloqueo puede vivir en una máquina diferente; en Linux, aunque está presente en algunas arquitecturas (como MIPS32), este campo no se utiliza.

La llamada al sistema original de Linux fcntl() no fue diseñada para manejar desplazamientos de archivos grandes (en la estructura flock). En consecuencia, se añadió una llamada al sistema fcntl64() en Linux 2.4. La llamada al sistema más nueva emplea una estructura diferente para el bloqueo de archivos, flock64, y las operaciones correspondientes, F_GETLK64, F_SETLK64, y F_SETLKW64. Sin embargo, estos detalles pueden ser ignorados por aplicaciones que usan glibc, cuya función de envoltorio fcntl() emplea transparente la llamada al sistema más reciente cuando está disponible.

Bloqueo de registros y NFS

Antes de Linux 3.12, si un cliente NFSv4 pierde el contacto con el servidor durante un período de tiempo (definido como más de 90 segundos sin comunicación), podría perder y recuperar un bloqueo sin ser consciente de ello. (El período de tiempo después del cual se asume que el contacto se pierde se conoce como tiempo de concesión de NFSv4. En un servidor NFS de Linux, esto se puede determinar mirando /proc/fs/nfsd/nfsv4leasetime, que expresa el período en segundos. El valor predeterminado para este archivo es 90.) Este escenario potencialmente arriesga la corrupción de datos, ya que otro proceso podría adquirir un bloqueo en el período intermedio y realizar E/S de archivos.

Desde Linux 3.12, si un cliente NFSv4 pierde el contacto con el servidor, cualquier E/S al archivo realizada por un proceso que "piensa" que posee un bloqueo fallará hasta que ese proceso cierre y reabra el archivo. Un parámetro del kernel, nfs.recover_lost_locks, puede establecerse en 1 para obtener el comportamiento anterior a la versión 3.12, mediante el cual el cliente intentará recuperar los bloqueos perdidos cuando se restablezca el contacto con el servidor. Debido al riesgo asociado de corrupción de datos, este parámetro tiene un valor predeterminado de 0 (deshabilitado).

ERRORES

Detección de interbloqueo

El algoritmo de detección de interbloqueos empleado por el kernel al tratar las solicitudes de F_SETLKW puede producir falsos negativos (fallos al detectar interbloqueos, dejando un conjunto de procesos interbloqueados bloqueados indefinidamente) y falsos positivos (errores EDEADLK cuando no hay interbloqueo). Por ejemplo, el kernel limita la profundidad del bloqueo de su búsqueda de dependencias a 10 pasos, lo que significa que las cadenas de interbloqueo circulares que superan ese tamaño no se detectarán. Además, el kernel puede indicar falsamente un interbloqueo cuando dos o más procesos creados utilizando el indicador clone(2) CLONE_FILES establecen bloqueos que parecen (para el kernel) entrar en conflicto.

Bloqueo obligatorio

La implementación de Linux del bloqueo obligatorio está sujeta a condiciones de carrera que la hacen poco fiable: una llamada de write(2) que se superpone con un bloqueo puede modificar datos después de que se adquiera el bloqueo obligatorio; una llamada de read(2) que se superpone con un bloqueo puede detectar cambios en datos que se realizaron solo después de que se adquiriera un bloqueo de escritura. Carreras similares existen entre bloqueos obligatorios y mmap(2). Por lo tanto, no es aconsejable confiar en el bloqueo obligatorio.
