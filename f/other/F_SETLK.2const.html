SINOPSIS

#include <fcntl.h>

DESCRIPCIÓN

Bloqueo de registros con aviso (advisory record locking)

Linux implementa bloqueos de registro UNIX tradicionales (asociados al proceso), según lo estandarizado por POSIX. Para una alternativa específica de Linux con mejores semánticas, ver la discusión de bloqueos de descripción de archivo abierto a continuación.

F_SETLK, F_SETLKW y F_GETLK se utilizan para adquirir, liberar y probar la existencia de bloqueos de registro (también conocidos como bloqueos de rango de bytes, segmento de archivo o región de archivo). El tercer argumento, lock, es un puntero a una estructura que tiene al menos los siguientes campos (en orden no especificado).


struct flock {
    ...
    short l_type;    /* Tipo de bloqueo: F_RDLCK,
                        F_WRLCK, F_UNLCK */
    short l_whence;  /* Cómo interpretar l_start:
                        SEEK_SET, SEEK_CUR, SEEK_END */
    off_t l_start;   /* Desplazamiento de inicio para el bloqueo */
    off_t l_len;     /* Número de bytes a bloquear */
    pid_t l_pid;     /* PID del proceso que bloquea nuestro bloqueo
                        (establecido por F_GETLK y F_OFD_GETLK) */
    ...
};

Los campos l_whence, l_start y l_len de esta estructura especifican el rango de bytes que deseamos bloquear. Se pueden bloquear bytes más allá del final del archivo, pero no bytes antes del inicio del archivo.

l_start es el desplazamiento de inicio para el bloqueo, y se interpreta en relación con: el inicio del archivo (si l_whence es SEEK_SET); el desplazamiento actual del archivo (si l_whence es SEEK_CUR); o el final del archivo (si l_whence es SEEK_END). En los dos últimos casos, l_start puede ser un número negativo siempre que el desplazamiento no se encuentre antes del inicio del archivo.

l_len especifica el número de bytes a bloquear. Si l_len es positivo, entonces el rango a bloquear cubre los bytes l_start hasta e incluyendo l_start+l_len-1. Especificar 0 para l_len tiene el significado especial: bloquear todos los bytes comenzando en la ubicación especificada por l_whence y l_start hasta el final del archivo, sin importar cuánto crezca el archivo.

POSIX.1-2001 permite (pero no requiere) que una implementación admita un valor l_len negativo; si l_len es negativo, el intervalo descrito por lock cubre los bytes l_start+l_len hasta e incluyendo l_start-1. Esto es compatible desde Linux 2.4.21 y Linux 2.5.49.

El campo l_type se puede usar para colocar un bloqueo de lectura (F_RDLCK) o de escritura (F_WRLCK) en un archivo. Cualquier número de procesos puede tener un bloqueo de lectura (bloqueo compartido) en una región del archivo, pero solo un proceso puede tener un bloqueo de escritura (bloqueo exclusivo). Un bloqueo exclusivo excluye todos los demás bloqueos, tanto compartidos como exclusivos. Un solo proceso puede tener solo un tipo de bloqueo en una región del archivo; si se aplica un nuevo bloqueo a una región ya bloqueada, el bloqueo existente se convierte al nuevo tipo de bloqueo. (Tales conversiones pueden implicar dividir, reducir o fusionar con un bloqueo existente si el rango de bytes especificado por el nuevo bloqueo no coincide exactamente con el rango del bloqueo existente).

F_SETLK
Adquirir un bloqueo (cuando l_type es F_RDLCK o F_WRLCK) o liberar un bloqueo (cuando l_type es F_UNLCK) en los bytes especificados por los campos l_whence, l_start y l_len de lock. Si otro proceso tiene un bloqueo conflictivo, esta llamada devuelve -1 y establece errno a EACCES o EAGAIN. (El error devuelto en este caso difiere entre implementaciones, por lo que POSIX requiere que una aplicación portátil verifique ambos errores).
F_SETLKW
Como F_SETLK, pero si hay un bloqueo conflictivo en el archivo, espera a que se libere ese bloqueo. Si se captura una señal mientras se espera, la llamada se interrumpe y (después de que el manejador de señal haya regresado) regresa inmediatamente (con valor de retorno -1 y errno establecido a EINTR; ver signal(7)).
F_GETLK
Al ingresar a esta llamada, lock describe un bloqueo que nos gustaría colocar en el archivo. Si el bloqueo pudiera colocarse, fcntl() no lo coloca realmente, sino que devuelve F_UNLCK en el campo l_type de lock y deja los otros campos de la estructura sin cambiar.
Si uno o más bloqueos incompatibles impidieran colocar este bloqueo, entonces fcntl() devuelve detalles sobre uno de esos bloqueos en los campos l_type, l_whence, l_start y l_len de lock. Si el bloqueo conflictivo es un bloqueo de registro tradicional (asociado al proceso), entonces el campo l_pid se establece al PID del proceso que tiene ese bloqueo. Si el bloqueo conflictivo es un bloqueo de descripción de archivo abierto, entonces l_pid se establece a -1. Tenga en cuenta que la información devuelta puede estar desactualizada cuando el llamador la inspeccione.

Para colocar un bloqueo de lectura, fd debe estar abierto para lectura. Para colocar un bloqueo de escritura, fd debe estar abierto para escritura. Para colocar ambos tipos de bloqueo, abra un archivo de lectura/escritura.

Al colocar bloqueos con F_SETLKW, el kernel detecta deadlocks (interbloqueos), por los cuales dos o más procesos tienen sus solicitudes de bloqueo mutuamente bloqueadas por bloqueos en poder de los otros procesos. Por ejemplo, suponga que el proceso A tiene un bloqueo de escritura en el byte 100 de un archivo, y el proceso B tiene un bloqueo de escritura en el byte 200. Si cada proceso luego intenta bloquear el byte ya bloqueado por el otro proceso usando F_SETLKW, entonces, sin detección de deadlock, ambos procesos permanecerían bloqueados indefinidamente. Cuando el kernel detecta tales deadlocks, hace que una de las solicitudes de bloqueo bloqueantes falle inmediatamente con el error EDEADLK; una aplicación que encuentra dicho error debe liberar algunos de sus bloqueos para permitir que otras aplicaciones procedan antes de intentar recuperar los bloqueos que requiere. Los deadlocks circulares que involucran a más de dos procesos también se detectan. Tenga en cuenta, sin embargo, que existen limitaciones en el algoritmo de detección de deadlocks del kernel; consulte BUGS.

Además de ser eliminados por un F_UNLCK explícito, los bloqueos de registro se liberan automáticamente cuando el proceso termina.

Los bloqueos de registro no son heredados por un hijo creado a través de fork(2), pero se conservan en un execve(2).

Debido al almacenamiento en búfer realizado por la biblioteca stdio(3), se debe evitar el uso de bloqueo de registros con rutinas de ese paquete; utilice read(2) y write(2) en su lugar.

Los bloqueos de registro descritos anteriormente están asociados con el proceso (a diferencia de los bloqueos de descripción de archivo abierto descritos a continuación). Esto tiene algunas consecuencias desafortunadas:

•
Si un proceso cierra *cualquier* descriptor de archivo que se refiera a un archivo, entonces todos los bloqueos del proceso en ese archivo se liberan, independientemente de los descriptores de archivo en los que se obtuvieron los bloqueos. Esto es malo: significa que un proceso puede perder sus bloqueos en un archivo como /etc/passwd o /etc/mtab cuando por alguna razón una función de biblioteca decide abrir, leer y cerrar el mismo archivo.
•
Los hilos en un proceso comparten bloqueos. En otras palabras, un programa multihilo no puede usar el bloqueo de registros para garantizar que los hilos no accedan simultáneamente a la misma región de un archivo.

Los bloqueos de descripción de archivo abierto resuelven ambos problemas.

Bloqueos de descripción de archivo abierto (no POSIX)

Los bloqueos de descripción de archivo abierto son bloqueos de rango de bytes consultivos cuya operación es, en la mayoría de los aspectos, idéntica a los bloqueos de registro tradicionales descritos anteriormente. Este tipo de bloqueo es específico de Linux y está disponible desde Linux 3.15. (Hay una propuesta en el Austin Group para incluir este tipo de bloqueo en la próxima revisión de POSIX.1.) Para una explicación de las descripciones de archivo abierto, consulte open(2).

La principal diferencia entre los dos tipos de bloqueo es que, mientras que los bloqueos de registro tradicionales están asociados con un proceso, los bloqueos de descripción de archivo abierto están asociados con la descripción de archivo abierto en la que se adquieren, de forma muy similar a los bloqueos adquiridos con flock(2). En consecuencia (y a diferencia de los bloqueos de registro consultivos tradicionales), los bloqueos de descripción de archivo abierto se heredan a través de fork(2) (y clone(2) con CLONE_FILES), y solo se liberan automáticamente en el último cierre de la descripción de archivo abierto, en lugar de liberarse en cualquier cierre del archivo.

Las combinaciones de bloqueos conflictivos (es decir, un bloqueo de lectura y un bloqueo de escritura o dos bloqueos de escritura), donde un bloqueo es un bloqueo de descripción de archivo abierto y el otro es un bloqueo de registro tradicional, entran en conflicto incluso cuando son adquiridos por el mismo proceso en el mismo descriptor de archivo.

Los bloqueos de descripción de archivo abierto colocados a través de la misma descripción de archivo abierto (es decir, a través del mismo descriptor de archivo, o a través de un duplicado del descriptor de archivo creado por fork(2), dup(2), F_DUPFD(2const), y así sucesivamente) son siempre compatibles: si se coloca un nuevo bloqueo en una región ya bloqueada, el bloqueo existente se convierte al nuevo tipo de bloqueo. (Dichas conversiones pueden resultar en la división, reducción o coalescencia de un bloqueo existente, como se discutió anteriormente).

Por otro lado, los bloqueos de descripción de archivo abierto pueden entrar en conflicto entre sí cuando se adquieren a través de diferentes descripciones de archivo abierto. Por lo tanto, los hilos en un programa multihilo pueden usar bloqueos de descripción de archivo abierto para sincronizar el acceso a una región de archivo haciendo que cada hilo realice su propia open(2) en el archivo y aplicando bloqueos a través del descriptor de archivo resultante.

Al igual que con los bloqueos consultivos tradicionales, el tercer argumento para fcntl(), lock, es un puntero a una estructura flock. A diferencia de los bloqueos de registro tradicionales, el campo l_pid de esa estructura debe establecerse en cero al usar las operaciones descritas a continuación.

Las operaciones para trabajar con bloqueos de descripción de archivo abierto son análogas a las utilizadas con bloqueos tradicionales:

F_OFD_SETLK
Adquirir un bloqueo de descripción de archivo abierto (cuando l_type es F_RDLCK o F_WRLCK) o liberar un bloqueo de descripción de archivo abierto (cuando l_type es F_UNLCK) en los bytes especificados por los campos l_whence, l_start y l_len de lock. Si otro proceso tiene un bloqueo conflictivo, esta llamada devuelve -1 y establece errno en EAGAIN.
F_OFD_SETLKW
Como en F_OFD_SETLK, pero si se tiene un bloqueo conflictivo en el archivo, entonces se espera a que se libere ese bloqueo. Si se captura una señal mientras se espera, la llamada se interrumpe y (después de que el manejador de señales regrese) devuelve inmediatamente (con valor de retorno -1 y errno establecido en EINTR; consulte signal(7)).
F_OFD_GETLK
A la entrada de esta llamada, lock describe un bloqueo de descripción de archivo abierto que nos gustaría colocar en el archivo. Si el bloqueo pudiera colocarse, fcntl() no lo coloca realmente, sino que devuelve F_UNLCK en el campo l_type de lock y deja los demás campos de la estructura sin cambios. Si uno o más bloqueos incompatibles impidieran colocar este bloqueo, se devuelven detalles sobre uno de estos bloqueos a través de lock, como se describe anteriormente para F_GETLK.

En la implementación actual, no se realiza detección de interbloqueos para bloqueos de descripción de archivo abierto. (Esto contrasta con los bloqueos de registro asociados a procesos, para los cuales el kernel sí realiza detección de interbloqueos).

Bloqueo obligatorio

Advertencia: la implementación de Linux del bloqueo obligatorio no es fiable. Consulte ERRORES a continuación. Debido a estos errores, y al hecho de que se cree que la característica se usa poco, desde Linux 4.5, el bloqueo obligatorio se ha convertido en una característica opcional, regida por una opción de configuración (CONFIG_MANDATORY_FILE_LOCKING). Esta característica ya no se admite en absoluto en Linux 5.15 y posteriores.

Por defecto, tanto los bloqueos de registro tradicionales (asociados a procesos) como los de descripción de archivo abierto son consultivos. Los bloqueos consultivos no se aplican y solo son útiles entre procesos que cooperan.

Ambos tipos de bloqueo también pueden ser obligatorios. Los bloqueos obligatorios se aplican a todos los procesos. Si un proceso intenta realizar un acceso incompatible (por ejemplo, read(2) o write(2)) en una región de archivo que tiene un bloqueo obligatorio incompatible, el resultado depende de si el indicador O_NONBLOCK está habilitado para su descripción de archivo abierto. Si el indicador O_NONBLOCK no está habilitado, la llamada al sistema se bloquea hasta que se elimina el bloqueo o se convierte a un modo compatible con el acceso. Si el indicador O_NONBLOCK está habilitado, la llamada al sistema falla con el error EAGAIN.

Para utilizar bloqueos obligatorios, el bloqueo obligatorio debe estar habilitado tanto en el sistema de archivos que contiene el archivo a bloquear, como en el propio archivo. El bloqueo obligatorio se habilita en un sistema de archivos usando la opción "-o mand" para mount(8), o el indicador MS_MANDLOCK para mount(2). El bloqueo obligatorio se habilita en un archivo deshabilitando el permiso de ejecución de grupo en el archivo y habilitando el bit de permiso set-group-ID (consulte chmod(1) y chmod(2)).

El bloqueo obligatorio no está especificado por POSIX. Algunos otros sistemas también admiten el bloqueo obligatorio, aunque los detalles de cómo habilitarlo varían entre sistemas.

Bloqueos perdidos

Cuando se obtiene un bloqueo consultivo en un sistema de archivos en red como NFS, es posible que el bloqueo se pierda. Esto puede suceder debido a acciones administrativas en el servidor, o debido a una partición de red (es decir, pérdida de conectividad de red con el servidor) que dure lo suficiente como para que el servidor suponga que el cliente ya no funciona.

Cuando el sistema de archivos determina que se ha perdido un bloqueo, las futuras solicitudes de read(2) o write(2) pueden fallar con el error EIO. Este error persistirá hasta que se elimine el bloqueo o se cierre el descriptor de archivo. Desde Linux 3.12, esto ocurre al menos para NFSv4 (incluidas todas las versiones menores).

Algunas versiones de UNIX envían una señal (SIGLOST) en esta circunstancia. Linux no define esta señal y no proporciona ninguna notificación asíncrona de bloqueos perdidos.

VALOR DE RETORNO

Cero.

En caso de error, se devuelve -1 y errno se establece para indicar el error.

ERRORES

Consulte fcntl(2).

EBADF
op es F_SETLK o F_SETLKW y el modo de apertura del descriptor de archivo no coincide con el tipo de bloqueo solicitado.
EDEADLK
Se detectó que la operación F_SETLKW especificada causaría un interbloqueo.
EFAULT
lock está fuera de su espacio de direcciones accesible.
EINTR
op es F_SETLKW o F_OFD_SETLKW y la operación fue interrumpida por una señal; consulte signal(7).
EINTR
op es F_GETLK, F_SETLK, F_OFD_GETLK, o F_OFD_SETLK, y la operación fue interrumpida por una señal antes de que se verificara o adquiriera el bloqueo. Es más probable que ocurra al bloquear un archivo remoto (por ejemplo, al bloquear sobre NFS), pero a veces puede ocurrir localmente.
EINVAL
op es F_OFD_SETLK, F_OFD_SETLKW, o F_OFD_GETLK, y l_pid no se especificó como cero.
ENOLCK
Demasiados bloqueos de segmento abiertos, tabla de bloqueos llena, o protocolo de bloqueo remoto fallido (por ejemplo, bloqueo sobre NFS).

NOTAS

Bloqueo de archivos

La llamada al sistema fcntl() original de Linux no fue diseñada para manejar grandes desplazamientos de archivo (en la estructura flock). En consecuencia, se agregó una llamada al sistema fcntl64() en Linux 2.4. La llamada al sistema más nueva emplea una estructura diferente para el bloqueo de archivos, flock64, y operaciones correspondientes, F_GETLK64, F_SETLK64 y F_SETLKW64. Sin embargo, estos detalles pueden ser ignorados por las aplicaciones que usan glibc, cuya función de envoltura fcntl() emplea de forma transparente la llamada al sistema más reciente donde esté disponible.

Bloqueo de registros y

NFS

Antes de Linux 3.12, si un cliente NFSv4 perdía el contacto con el servidor durante un período de tiempo (definido como más de 90 segundos sin comunicación), podía perder y recuperar un bloqueo sin ser consciente de ello. (El período de tiempo después del cual se asume que se ha perdido el contacto se conoce como leasetime de NFSv4. En un servidor NFS de Linux, esto se puede determinar mirando /proc/fs/nfsd/nfsv4leasetime, que expresa el período en segundos. El valor predeterminado para este archivo es 90.) Este escenario plantea potencialmente un riesgo de corrupción de datos, ya que otro proceso podría adquirir un bloqueo en el período intermedio y realizar E/S en el

archivo.

Desde Linux 3.12, si un cliente NFSv4 pierde el contacto con el servidor, cualquier E/S en el archivo por parte de un proceso que "cree" que mantiene un bloqueo fallará hasta que ese proceso cierre y vuelva a abrir el archivo. Un parámetro del kernel, nfs.recover_lost_locks, se puede establecer en 1 para obtener el comportamiento anterior a 3.12, por el cual el cliente intentar

á recuperar los bloqueos perdidos cuando se restablezca el con
tacto con el servidor. Debido al riesgo de corrupción de datos
, este parámetro tiene un valor predeterminado de 0 (desactivado).
