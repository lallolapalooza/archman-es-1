USO EN

APLICACIONES

Los valores de arg para F_GETFD, F_SETFD, F_GETFL y F_SETFL representan valores de bandera para permitir un crecimiento futuro. Las aplicaciones que usan estas funciones deben realizar una operación de leer-modificar-escribir en ellos, en lugar de asumir que solo los valores definidos por este volumen de POSIX.1‐2017 son válidos. Es un error común olvidar esto, particularmente en el caso de F_SETFD. Algunas implementaciones establecen banderas de estado de archivo adicionales para informar a la aplicación del comportamiento por defecto, aunque la aplicación no solicitó estas

banderas.

En sistemas que no realizan comprobaciones de permisos en el momento de una llamada a fcntl() con F_SETOWN, si las comprobaciones de permisos realizadas en el momento en que se envía la señal prohíben enviar la señal a cualquier proceso, el proceso que llamó a fcntl() no tiene forma de descubrir que esto ha ocurrido. Una llamada a kill() con la señal 0 puede usarse como una comprobación previa de permisos, aunque esto no es una garantía de que el permiso será concedido

en el momento en que se envía una señal, ya que el proceso(s) de destino p
odría cambiar identificadores de usuario o privilegios mientras tanto.

JUSTIFICACIÓ

N

La elipsis en la SINOPSIS es la sintaxis especificada por el estándar ISO C para un número variable de argumentos. Se usa porque System V usa punteros para la implementación de las funciones de bloqueo de

archivos.

Este volumen de POSIX.1‐2017 permite el acceso concurrente de lectura y escritura a los datos de archivos usando la función fcntl(); esto es un cambio respecto al estándar /usr/group de 1984 y las propuestas iniciales. Sin controles de concurrencia, esta característica puede no ser utilizada completamente sin una pérdida ocasional de

datos.

Las pérdidas de datos ocurren de varias maneras. Un caso ocurre cuando varios procesos intentan actualizar el mismo registro, sin controles de secuenciación; varias actualizaciones pueden ocurrir en paralelo y el último escritor ``gana''. Otro caso es una base de datos de árbol de bits u otra basada en listas internas que está siendo reorganizada. Sin uso exclusivo del segmento del árbol por el proceso que actualiza, otros procesos de lectura tienen la posibilidad de perderse en la base de datos cuando los bloques de índice se dividen, condensan, insertan o eliminan. Mientras que fcntl() es útil para muchas aplicaciones, no está destinado a ser excesivamente general y no maneja bien el ejemplo del árbol de

bits.

Esta facilidad solo se requiere para archivos regulares porque no es apropiada para muchos dispositivos como terminales y conexiones de

red.

Dado que fcntl() funciona con ``cualquier descriptor de archivo asociado con ese archivo, sin importar cómo se obtuvo'', el descriptor de archivo puede haber sido heredado a través de un fork() o operación exec y así puede afectar a un archivo que otro proceso también tiene

abierto.

El uso de la descripción de archivo abierto para identificar qué bloquear requiere llamadas adicionales y presenta problemas si varios procesos comparten una descripción de archivo abierto, pero hay demasiadas implementaciones del mecanismo existente para que este volumen de POSIX.1‐2017 use especificaciones

diferentes.

Otra consecuencia de este modelo es que cerrar cualquier descriptor de archivo para un archivo dado (ya sea o no la misma descripción de archivo abierto que creó el bloqueo) causa que los bloqueos sobre ese archivo sean liberados para ese proceso. De manera equivalente, cualquier cierre para cualquier par archivo/proceso libera los bloqueos poseídos sobre ese archivo para ese proceso. Pero note que mientras que una descripción de archivo abierto puede ser compartida a través de fork(), los bloqueos no se heredan a través de fork(). Sin embargo, los bloqueos pueden ser heredados a través de una de las funciones

exec.

La identificación de una máquina en un entorno de red está fuera del alcance de este volumen de POSIX.1‐2017. Por lo tanto, un miembro l_sysid, como se encuentra en System V, no está incluido en la estructura de

bloqueo.

El cambio de tipos de bloqueo puede resultar en que una región previamente bloqueada sea dividida en regiones más

pequeñas.

El bloqueo obligatorio fue una característica principal del estándar /usr/group de

1984.

Para que el bloqueo de registros de archivo consultivo sea efectivo, todos los procesos que tienen acceso a un archivo deben cooperar y usar el mecanismo consultivo antes de realizar E/S en el archivo. El bloqueo de registros en modo de aplicación es importante cuando no se puede asumir que todos los procesos están cooperando. Por ejemplo, si un usuario usa un editor para actualizar un archivo al mismo tiempo que un segundo usuario ejecuta otro proceso que actualiza el mismo archivo y si solo uno de los dos procesos está usando bloqueo consultivo, los procesos no están cooperando. El bloqueo de registros en modo de aplicación protegería contra colisiones

accidentales.

En segundo lugar, el bloqueo de registros consultivo requiere que un proceso que usa bloqueo encadene cada operación de E/S con operaciones de bloqueo (o prueba) y desbloqueo. Con el bloqueo de archivos y registros en modo de aplicación, un proceso puede bloquear el archivo una vez y desbloquear cuando todas las operaciones de E/S han sido completadas. El bloqueo de registros en modo de aplicación proporciona una base que puede ser mejorada; por ejemplo, con bloqueos compartibles. Es decir, el mecanismo podría ser mejorado para permitir que un proceso bloquee un archivo para que otros procesos puedan leerlo, pero ninguno de ellos pueda

escribirlo.

Los bloqueos obligatorios fueron omitidos por varias

razones:
1
.
La configuración de bloqueo obligatorio se hacía multiplexando el bit set-group-ID en la mayoría de las implementaciones; esto era confuso, como
mínimo.
2
.
La relación con la truncación de archivos como se soportaba en 4.2 BSD no estaba bien
especificada.
