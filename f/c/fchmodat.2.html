DESCRIPCIÓ

N

Las llamadas al sistema chmod() y fchmod() cambian los bits de modo de un archivo. (El modo del archivo consiste en los bits de permisos del archivo más los bits set-user-ID, set-group-ID y sticky.) Estas llamadas al sistema difieren solo en la forma en que se especifica el

archivo:
•
chmod() cambia el modo del archivo especificado cuyo nombre de ruta se da en path, el cual se desreferencia si es un enlace
simbólico.
•
fchmod() cambia el modo del archivo al que hace referencia el descriptor de archivo abierto fd
.

El nuevo modo de archivo se especifica en mode, que es una máscara de bits creada mediante la operación OR de cero o más de los

siguientes:
S_ISUID
(04000)
set-user-ID (establece el ID de usuario efectivo del proceso en execve(
2))
S_ISGID
(02000)
set-group-ID (establece el ID de grupo efectivo del proceso en execve(2); bloqueo obligatorio, como se describe en fcntl(2); toma el grupo de un archivo nuevo del directorio padre, como se describe en chown(2) y mkdir(
2))
S_ISVTX
(01000)
bit sticky (indicador de eliminación restringida, como se describe en unlink(
2))
S_IRUSR
(00400)
lectura por el
propietario

(00200)

(00100)

El UID efectivo del proceso que llama debe coincidir con el propietario del archivo, o el proceso debe estar privilegiado (en Linux: debe tener la capacidad CAP_FOWNER)

.

Si el proceso que llama no está privilegiado (en Linux: no tiene la capacidad CAP_FSETID), y el grupo del archivo no coincide con el ID de grupo efectivo del proceso o con uno de sus IDs de grupo suplementarios, el bit S_ISGID se desactivará, pero esto no hará que se devuelva un

error.

Como medida de seguridad, dependiendo del sistema de archivos, los bits de ejecución set-user-ID y set-group-ID pueden desactivarse si se escribe en un archivo. (En Linux, esto ocurre si el proceso que escribe no tiene la capacidad CAP_FSETID.) En algunos sistemas de archivos, solo el superusuario puede establecer el bit sticky, que puede tener un significado especial. Para el bit sticky, y para los bits set-user-ID y set-group-ID en directorios, véase inode(

7).

En los sistemas de archivos NFS, restringir los permisos influirá inmediatamente en los archivos ya abiertos, porque el control de acceso se realiza en el servidor, pero los archivos abiertos son mantenidos por el cliente. Ampliar los permisos puede retrasarse para otros clientes si el almacenamiento en caché de atributos está habilitado en

ellos.

fchmodat(

)

La llamada al sistema fchmodat() opera exactamente de la misma manera que chmod(), excepto por las diferencias descritas

aquí.

Si path es relativo, entonces se interpreta relativo al directorio al que hace referencia el descriptor de archivo dirfd (en lugar de relativo al directorio de trabajo actual del proceso que llama, como lo hace chmod() para un nombre de ruta relativo)

.

Si path es relativo y dirfd es el valor especial AT_FDCWD, entonces path se interpreta relativo al directorio de trabajo actual del proceso que llama (como chmod())

.

Si path es absoluto, entonces dirfd se

ignora.

flags puede ser 0, o incluir los siguientes

indicadores:
AT_EMPTY_PATH (desde Linux
6.6)
Si path es una cadena vacía, operar sobre el archivo al que hace referencia dirfd (que puede haberse obtenido usando el indicador O_PATH de open(2)). En este caso, dirfd puede referirse a cualquier tipo de archivo, no solo a un directorio. Si dirfd es AT_FDCWD, la llamada opera sobre el directorio de trabajo actual. Este indicador es específico de Linux;

Diferencias entre la biblioteca C y el

kernel

La biblioteca C de GNU fchmodat() función envolvente implementa la interfaz especificada por POSIX descrita en esta página. Esta interfaz difiere de la llamada al sistema subyacente de Linux, la cual no tiene un argument
