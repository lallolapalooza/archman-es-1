Libfabric es una biblioteca de software de fabric de alto rendimiento diseñada

para proporcionar interfaces de baja latencia al hardware de fabric. Para
una discusión detallada de la motivación y el diseño, consulte fi_guide(7).

VISIÓN

GENERAL

Libfabric proporciona 'E/S directa de proceso' al software de aplicación que se comunica a través de software y hardware de fabric. La E/S directa de proceso, históricamente referida como RDMA, permite a una aplicación acceder directamente a recursos de red sin intervenciones del sistema operativo. Las transferencias de datos pueden ocurrir directamente hacia y desde la memoria de la

aplicación.

Hay dos componentes en el software de

libfabric:
Proveedores de
Fabric
Conceptualmente, un proveedor de fabric puede ser visto como un controlador de NIC de hardware local, aunque un proveedor no está limitado por esta definición. El primer componente de libfabric es un marco de propósito general capaz de manejar diferentes tipos de hardware de fabric. Todos los dispositivos de hardware de fabric y sus controladores de software deben soportar este marco. Los dispositivos y los controladores que se conectan al marco de libfabric se denominan proveedores de fabric, o simplemente proveedores. Los detalles de los proveedores se pueden encontrar en fi_provider(7)
.
Interfaces de
Fabric
El segundo componente es un conjunto de operaciones de comunicación. Libfabric defi
ne varios conjuntos de funciones de comunicación que los proveedores pueden soporta
r. No es necesario que los proveedores implementen todas las interfaces que están
definidas; sin embargo, los proveedores indican claramente qué interfaces soportan.

INTERFACES DE

FABRIC

Las interfaces de fabric están diseñadas de manera que sean cohesivas y no simplemente una unión de interfaces disjuntas. Las interfaces están lógicamente divididas en dos grupos: interfaces de control y operaciones de comunicación. Las interfaces de control son un conjunto común de operaciones que proporcionan acceso a recursos de comunicación locales, como vectores de dirección y colas de eventos. Las operaciones de comunicación exponen modelos particulares de comunicación y funcionalidad de fabric, como colas de mensajes, acceso remoto a memoria y operaciones atómicas. Las operaciones de comunicación están asociadas con puntos finales de

fabric.

Las aplicaciones típicamente usarán las interfaces de control para descubrir capacidades locales y a

signar los recursos necesarios. Luego asignarán y configurarán un punto final de comunicación para en
viar y recibir datos, o realizar otros tipos de transferencias de datos, con puntos finales remotos.

INTERFACES DE

CONTROL

Las API de interfaces de control proporcionan a las aplicaciones acceso a recursos de red. Esto implica listar todas las interfaces disponibles, obtener las capacidades de las interfaces y abrir un

proveedor.
fi_getinfo - Información de
Fabric
La llamada fi_getinfo es la llamada base utilizada para descubrir y solicitar servicios de fabric ofreci
dos por el sistema. Las aplicaciones pueden usar esta llamada para indicar el tipo de comunicación que d
esean. Los resultados de fi_getinfo, fi_info, se utilizan para reservar y configurar recursos de fabric.

fi_getinfo devuelve una lista de estructuras fi_info. Cada estructura hace referencia a un solo proveedor de fabric, indicando las interfaces que el proveedor soporta, junto con un conjunto nombrado de recursos. Un proveedor de fabric puede incluir múltiples estructuras fi_info en la lista

devuelta.
fi_fabric - Dominio de
Fabric
Un dominio de fabric representa una colección de recursos de hardware y software que acceden a una red física o virtual única. Todos los puertos de red en un sistema que pueden comunicarse entre sí a través del fabric pertenecen al mismo dominio de fabric. Un dominio de fabric comparte direcciones de red y puede abarcar múltiples proveedores. libfabric soporta sistemas conectados a múltiples
fabrics.
fi_domain - Dominios de
Acceso
Un dominio de acceso representa una conexión lógica única en un fabric. Puede mapear a una NIC física o virtual única o a un puerto. Un dominio de acceso define el límite a través del cual los recursos de fabric pueden estar asociados. Cada dominio de acceso pertenece a un solo dominio de
fabric.
fi_endpoint - Punto Final de
Fabric
Un punto final de fabric es un portal de comunicación. Un punto final puede ser activo o pasivo. Los puntos finales pasivos se utilizan para escuchar solicitudes de conexión. Los puntos finales activos pueden realizar transferencias de datos. Los puntos finales se configuran con capacidades de comunicación específicas y interfaces de transferencia de
datos.
fi_eq - Cola de
Eventos
Las colas de eventos se utilizan para recopilar y reportar la finalización de operaciones y eventos asíncronos. Las colas de eventos reportan eventos que no están directamente asociados con operaciones de transferencia de
datos.
fi_cq - Cola de
Finalización
Las colas de finalización son colas de eventos de alto rendimiento utilizadas para reportar la finalización de operaciones de transferencia de
datos.
fi_cntr - Contadores de
Eventos
Los contadores de eventos se utilizan para reportar el número de operaciones asíncronas finalizadas. Los contadores de eventos se consideran de peso ligero, en el sentido de que una finalización simplemente incrementa un contador, en lugar de colocar una entrada en una cola de
eventos.
fi_mr - Región de
Memoria
Las regiones de memoria describen búfers de memoria local de la aplicación. Para que los recursos de fabric accedan a la memoria de la aplicación, la aplicación primero debe otorgar permiso al proveedor de fabric construyendo una región de memoria. Las regiones de memoria son necesarias para tipos específicos de operaciones de transferencia de datos, como transferencias RMA (ver más
abajo).
fi_av - Vector de
Direcciones
Los vectores de dirección se utilizan para mapear direcciones de nivel superior, como direcciones IP, que pueden ser más
naturales para que una aplicación use, en direcciones específicas de fabric. El uso de vectores de dirección permite a
los proveedores reducir la cantidad de memoria requerida para mantener grandes tablas de búsqueda de direcciones
, y eliminar métodos costosos de resolución y búsqueda de direcciones durante las operaciones de transferencia de datos.

INTERFACES DE TRANSFERENCIA DE

DATOS

Los puntos finales de fabric están asociados con múltiples interfaces de transferencia de datos. Cada conjunto de interfaces está diseñado para soportar un estilo específico de comunicación, con un punto final que permite que las diferentes interfaces se usen en conjunto. Las siguientes interfaces de transferencia de datos son definidas por

libfabric.
fi_msg - Cola de
Mensajes
Las colas de mensajes exponen una interfaz simple de cola FIFO basada en mensajes a la aplicación. Las transferencias de datos de mensajes permiten a las aplicaciones enviar y recibir datos con los límites de los mensajes siendo
mantenidos.
fi_tagged - Colas de Mensajes
Etiquetados
Las listas de mensajes etiquetados exponen operaciones de transferencia de datos de envío/recepción construidas sobre el concepto de mensajería etiquetada. La cola de mensajes etiquetados es conceptualmente similar a las colas de mensajes estándar, pero con la adición de etiquetas de 64 bits para cada mensaje. Los mensajes enviados se emparejan con búfers de recepción que están etiquetados con un valor
similar.
fi_rma - Acceso Remoto a
Memoria
Las transferencias RMA son operaciones de un solo lado que leen o escriben datos directamente en una región de memoria remota. Aparte de definir la región de memoria apropiada, las operaciones RMA no requieren interacción en el lado objetivo para que la transferencia de datos se
complete.
fi_atomic -
Atómico
Las operaciones atómicas pueden realizar una de varias operaciones en una región de memoria remota. Las ope
raciones atómicas incluyen funcionalidad bien conocida, como suma atómica e intercambio condicional (compar
e-and-swap), además de varias otras llamadas predefinidas. A diferencia de otras interfaces de transferenci
a de datos, las operaciones atómicas son conscientes del formato de datos en la región de memoria objetivo.

INTERFAZ DE REGISTRO

El registro se puede controlar utilizando las variables de entorno FI_LOG_LEVEL, FI_LOG_PROV y FI_LOG_SUBSYS.

FI_LOG_LEVEL
FI_LOG_LEVEL controla la cantidad de datos de registro que se emiten. Los siguientes niveles de registro están definidos.
- Warn
Warn es la configuración menos detallada y está destinada a informar errores o advertencias.
- Trace
Trace es más detallado y está destinado a incluir una salida no detallada útil para rastrear la ejecución del programa.
- Info
Info es de alto tráfico y está destinado a una salida detallada.
- Debug
Debug es de alto tráfico y es probable que afecte el rendimiento de la aplicación. La salida de depuración solo está disponible si la biblioteca se ha compilado con la depuración habilitada.
FI_LOG_PROV
La variable de entorno FI_LOG_PROV habilita o deshabilita el registro de proveedores específicos. Los proveedores se pueden habilitar listándolos en formato separado por comas. Si la lista comienza con el símbolo `^', la lista se negará. Por defecto, todos los proveedores están habilitados.

Ejemplo: Para habilitar el registro del proveedor psm3 y sockets: FI_LOG_PROV=“psm3,sockets”

Ejemplo: Para habilitar el registro de proveedores distintos de psm3: FI_LOG_PROV=“^psm3”

FI_LOG_SUBSYS
La variable de entorno FI_LOG_SUBSYS habilita o deshabilita el registro a nivel de subsistema. La sintaxis para habilitar o deshabilitar subsistemas es similar a la utilizada para FI_LOG_PROV. Los siguientes subsistemas están definidos.
- core
Proporciona salida relacionada con el marco central y su gestión de proveedores.
- fabric
Proporciona salida específica de las interacciones asociadas con el objeto de tejido (fabric).
- domain
Proporciona salida específica de las interacciones asociadas con el objeto de dominio.
- ep_ctrl
Proporciona salida específica de operaciones de no transferencia de datos de punto final, como operaciones de CM.
- ep_data
Proporciona salida específica de operaciones de transferencia de datos de punto final.
- av
Proporciona salida específica de operaciones de vector de dirección.
- cq
Proporciona salida específica de operaciones de cola de finalización.
- eq
Proporciona salida específica de operaciones de cola de eventos.
- mr
Proporciona salida específica de registro de memoria.

INSTALACIÓN Y SELECCIÓN DE PROVEEDORES

Los scripts de compilación de libfabric instalarán todos los proveedores compatibles con el sistema de instalación. Los proveedores que carezcan de los prerrequisitos de compilación se deshabilitarán. Los proveedores instalados verificarán dinámicamente el hardware necesario al inicializar la biblioteca y responderán adecuadamente a las consultas de la aplicación.

Los usuarios pueden habilitar o deshabilitar los proveedores disponibles a través de opciones de configuración de compilación. Consulte `configure –help' para obtener detalles. En general, un proveedor específico puede controlarse mediante la opción de configuración `–enable-'. Por ejemplo, `–enable-udp' (o `–enable-udp=yes') agregará el proveedor udp a la compilación. Para deshabilitar el proveedor, se puede usar `–enable-udp=no'. Para compilar el proveedor como una biblioteca cargable dinámicamente independiente (es decir, proveedor DL), se puede usar `–enable-udp=dl'.

Los proveedores también se pueden habilitar o deshabilitar en tiempo de ejecución utilizando la variable de entorno FI_PROVIDER. La variable FI_PROVIDER se establece en una lista separada por comas de proveedores a incluir. Si la lista comienza con el símbolo `^', la lista se negará.

Ejemplo: Para habilitar solo los proveedores udp y tcp, establezca: FI_PROVIDER="udp,tcp"

Cuando se instala libfabric, los proveedores DL se colocan bajo la ruta de proveedor predeterminada, que se determina por cómo se compila e instala libfabric. Por lo general, la ruta de proveedor predeterminada es <libfabric-install-dir>/lib/libfabric o <libfabric-install-dir>/lib64/libfabric. Por defecto, libfabric intenta encontrar proveedores DL en el siguiente orden:

1.
Utiliza `dlopen' para cargar bibliotecas de proveedores llamadas lib<prov_name>-fi.so para todos los proveedores habilitados en el momento de la compilación. La ruta de búsqueda de `ld.so' se utiliza para localizar los archivos. Este paso se omite si libfabric se configura con la opción `–enable-restricted-dl'.
2.
Intenta cargar cada archivo bajo la ruta de proveedor predeterminada como un proveedor DL.

La variable FI_PROVIDER_PATH se puede utilizar para cambiar la ubicación de búsqueda de proveedores DL y cómo resolver conflictos si se encuentran varios proveedores con el mismo nombre. Establecer FI_PROVIDER_PATH a cualquier valor, incluso si está vacío, hará que se omita el paso 1 y puede cambiar el directorio de búsqueda utilizado en el paso 2.

En su forma más simple, la variable FI_PROVIDER_PATH se establece en una lista de directorios separados por dos puntos. Estos directorios reemplazan la ruta de proveedor predeterminada utilizada en el paso 2. Por ejemplo:

FI_PROVIDER_PATH=/opt/libfabric:/opt/libfabric2

Por defecto, si se encuentran varios proveedores (incluidos los proveedores integrados) con el mismo nombre, el primero con la versión más alta está activo y todos los demás están ocultos. Esto se puede cambiar estableciendo la variable FI_PROVIDER_PATH para que comience con `@', lo que obliga a que el primero esté activo independientemente de la versión. Por ejemplo:

FI_PROVIDER_PATH=@/opt/libfabric:/opt/libfabric2

La variable FI_PROVIDER_PATH también puede especificar proveedores preferidos proporcionando rutas completas a bibliotecas en lugar de directorios a buscar. Un proveedor preferido tiene prioridad sobre otros proveedores con el mismo nombre. La especificación de un proveedor preferido debe ir precedida de `+'. Por ejemplo:

FI_PROVIDER_PATH=+/opt/libfabric2/libtcp-fi.so:/opt/libfabric:+/opt/libfabric2/libudp-fi.so

Si se establece FI_PROVIDER_PATH, pero no se proporciona ningún directorio, se utiliza la ruta de proveedor predeterminada. Algunos ejemplos:

FI_PROVIDER_PATH=
FI_PROVIDER_PATH=@
FI_PROVIDER_PATH=+/opt/libfabric/libtcp-fi.so
FI_PROVIDER_PATH=@+/opt/libfabric/libtcp-fi.so

La utilidad fi_info, que se incluye como parte del paquete libfabric, puede usarse para obtener información sobre qué proveedores están disponibles en el sistema. Además, puede obtener una lista de todas las variables de entorno que se pueden utilizar para configurar libfabric y cada proveedor. Consulte fi_info(1) para obtener más detalles.

CONTROLES DE VARIABLES DE ENTORNO

Las características principales de libfabric y sus proveedores pueden ser configuradas por un administrador mediante el uso de variables de entorno. Las páginas man generalmente describirán las variables de acceso más común, como las mencionadas anteriormente. Sin embargo, libfabric define interfaces para publicar y obtener variables de entorno. Estas están dirigidas a los proveedores, pero permiten a las aplicaciones y usuarios obtener la lista completa de variables que se pueden establecer, junto con una breve descripción de su uso.

Se puede obtener una lista completa de las variables disponibles ejecutando la aplicación fi_info, con la opción de línea de comandos -e o –env.

NOTAS

Llamadas al Sistema

Dado que libfabric está diseñado para proporcionar a las aplicaciones acceso directo al hardware de tejido, existen límites sobre cómo se pueden utilizar los recursos de libfabric en conjunto con las llamadas al sistema. Estas limitaciones son notables para los desarrolladores que pueden estar familiarizados con la programación de la interfaz de sockets. Aunque los límites son específicos del proveedor, las siguientes restricciones se aplican a muchos proveedores y deben ser respetadas por las aplicaciones que buscan portabilidad entre proveedores.

fork
No se garantiza que los recursos de tejido estén disponibles para los procesos hijos. Esto incluye objetos, como puntos finales y colas de finalización, así como búferes de datos controlados por la aplicación que se han asignado a la red. Por ejemplo, los búferes de datos que se han registrado en un dominio de tejido pueden no estar disponibles en un proceso hijo debido a restricciones de copia en escritura.

Interbloqueo CUDA

En algunos casos, las llamadas a cudaMemcpy() dentro de libfabric pueden resultar en un interbloqueo. Esto ocurre típicamente cuando un kernel CUDA se bloquea hasta que se completa un cudaMemcpy en el host. Las aplicaciones que pueden causar dicho comportamiento pueden restringir la capacidad de Libfabric para invocar operaciones de la API CUDA con la opción de punto final FI_OPT_CUDA_API_PERMITTED. Consulte fi_endpoint(3) para obtener más detalles.

Otro mecanismo que se puede utilizar para evitar el interbloqueo es GDRCopy de Nvidia. El uso de GDRCopy requiere una biblioteca externa y un módulo de kernel disponibles en https://github.com/NVIDIA/gdrcopy. Libfabric debe configurarse con soporte GDRCopy utilizando la opción --with-gdrcopy, y ejecutarse con FI_HMEM_CUDA_USE_GDRCOPY=1. Esto puede no ser compatible con todos los proveedores.

Las versiones de libfabric mantienen la compatibilidad con versiones anteriores, de modo que las aplicaciones compiladas puedan seguir funcionando tal cual, y las aplicaciones escritas previamente compilarán contra versiones más nuevas de la biblioteca sin necesidad de cambios en el código fuente.
