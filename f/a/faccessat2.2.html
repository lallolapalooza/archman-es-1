R_OK, W_OK et X_OK testent si le fichier existe et accorde respectivement les permissions de lecture, d'écriture et d'exécution. La vérification est effectuée en utilisant le UID réel et le GID réel du

processus

appelant, plutôt que les identifiants effectifs comme c'est le cas lors de la tentative réelle d'une opération (par exemple, open(2)) sur le fichier. De même, pour l'utilisateur root, la vérification utilise l'ensemble des capacités permises plutôt que l'ensemble des capacités effectives ; et pour les utilisateurs non root, la vérification utilise un ensemble vide de capacités. Cela permet aux

programmes

set-user-ID et aux programmes dotés de capacités de déterminer facilement l'autorité de l'utilisateur appelant. En d'autres termes, access() ne répond pas à la question « puis-je lire/écrire/exécuter ce fichier ? ». Il répond à une question légèrement différente : « (en supposant que je suis un binaire setuid) l' utilisateur qui m'a invoqué peut-il lire/écrire/exécuter ce fichier ? », ce qui donne aux programmes set-user-ID la possibilité d'empêcher les utilisateurs malveillants de les faire lire des fichiers que les utilisateurs ne

devraient

pas pouvoir lire. Si le processus appelant est privilégié (c'est-à-dire si son UID réel est zéro), alors un test X_OK réussit pour un fichier régulier si la permission d'exécution est activée pour le propriétaire du

Los indicadores AT_EACCESS y AT_SYMLINK_NOFOLLOW están realmente implementados dentro de la función envolvente de glibc para faccessat(). Si se especifica cualquiera de estos indicadores, la función envolvente emplea fstatat(2) para determinar los permis

NOTA

S

Advertencia: Usar estas llamadas para comprobar si un usuario está autorizado a, por ejemplo, abrir un archivo antes de hacerlo realmente usando open(2) crea una brecha de seguridad, porque el usuario podría explotar el breve intervalo de tiempo entre la comprobación y la apertura del archivo para manipularlo. Por esta razón, se debe evitar el uso de esta llamada al sistema. (En el ejemplo descrito anteriormente, una alternativa más segura sería cambiar temporalmente el ID de usuario efectivo del proceso al ID real y luego llamar a open(2).

)

access() siempre desreferencia los enlaces simbólicos. Si necesita comprobar los permisos de un enlace simbólico, use faccessat() con el indicador AT_SYMLINK_NOFOLLOW

.

Estas llamadas devuelven un error si alguno de los tipos de acceso en mode está denegado, incluso si algunos de los otros tipos de acceso en mode están

permitidos.

Un archivo es accesible solo si los permisos de cada uno de los directorios en el prefijo de la ruta de path permiten el acceso de búsqueda (es decir, de ejecución). Si algún directorio es inaccesible, entonces la llamada access() falla, independientemente de los permisos del archivo en

sí.

Solo se comprueban los bits de acceso, no el tipo ni el contenido del archivo. Por lo tanto, si se determina que un directorio es escribible, probablemente significa que se pueden crear archivos en el directorio, y no que el directorio pueda ser escrito como un archivo. De manera similar, un archivo DOS puede ser reportado como ejecutable, pero la llamada execve(2) seguirá

fallando.

Estas llamadas pueden no funcionar correctamente en sistemas de archivos NFSv2 con el mapeo de UID habilitado, por

que el mapeo de UID se realiza en el servidor y se oculta al cliente, que comprueba los permisos. (Las versiones 3
y superiores de NFS realizan la comprobación en el servidor.) Problemas similares pueden ocurrir en montajes FUSE.

ERRORE

S

Debido a que la llamada al sistema faccessat() del núcleo Linux no admite un argumento flags, la función envolvente faccessat() proporcionada en glibc 2.32 y versiones anteriores emula la funcionalidad requerida mediante una combinación de la llamada al sistema faccessat() y fstatat(2). Sin embargo, esta emulación no tiene en cuenta las ACL. A partir de glibc 2.33, la función envolvente evita este error mediante el uso de la llamada al sistema faccessat2() cuando esta es proporcionada por el núcleo

subyacente.

En Linux 2.4 (y anteriores) hay cierta rareza en el manejo de las pruebas X_OK para el superusuario. Si todas las categorías de permiso de ejecución están deshabilitadas para un archivo que no es un directorio, entonces la única prueba access() que devuelve -1 es cuando mode se especifica como simplemente X_OK; si R_OK o W_OK también se especifican en mode, entonces access() devuelve 0 para tales archivos. Las primeras versiones de Linux 2.6 (hasta y incluyendo Linux 2.6.3) también se comportaban de la misma manera que Linux 2.

4.

Antes de Linux 2.6.20, estas llamadas ignoraban el efecto del indicador MS_NOEXEC si se usaba para mount(2) el sistema de archivos subyacente. Desde Linux 2.6.20, el indicador MS_NOEXEC es

resp
etado.
