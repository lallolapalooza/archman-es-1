faccessat(2)

Paquete: man-pages

access(2) Manual de Llamadas al Sistema access(2)

NOMBRE

access, faccessat, faccessat2 - comprobar los permisos de un usuario sobre un archivo

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <unistd.h>
int access(const char *path, int mode);
#include <fcntl.h>            /* Definición de constantes AT_* */
#include <unistd.h>
int faccessat(int dirfd, const char *path, int mode, int flags);
                /* Pero véanse las diferencias entre la biblioteca C/el kernel, abajo */
#include <fcntl.h>            /* Definición de constantes AT_* */
#include <sys/syscall.h>      /* Definición de constantes SYS_* */
#include <unistd.h>
int syscall(SYS_faccessat2,
            int dirfd, const char *path, int mode, int flags);

DESCRIPCIÓN

access() comprueba si el proceso que llama puede acceder al archivo path. Si path es un enlace simbólico, se resuelve.

El mode especifica la(s) comprobación(es) de accesibilidad a realizar, y es el valor F_OK, o una máscara que consiste en el OR bitwise de uno o más de R_OK, W_OK y X_OK. F_OK comprueba la existencia del archivo. R_OK, W_OK y X_OK comprueban si el archivo existe y otorga permisos de lectura, escritura y ejecución, respectivamente.

La comprobación se realiza utilizando el UID y GID *reales* del proceso que llama, en lugar de los IDs efectivos como se hace al intentar una operación (por ejemplo, open(2)) sobre el archivo. De manera similar, para el usuario root, la comprobación utiliza el conjunto de capacidades permitidas en lugar del conjunto de capacidades efectivas; y para los usuarios no-root, la comprobación utiliza un conjunto vacío de capacidades.

Esto permite a los programas set-user-ID y a los programas con capacidades determinar fácilmente la autoridad del usuario invocador. En otras palabras, access() no responde a la pregunta "¿puedo leer/escribir/ejecutar este archivo?". Responde a una pregunta ligeramente diferente: "¿(asumiendo que soy un binario setuid) puede *el usuario que me invocó* leer/escribir/ejecutar este archivo?", lo que da a los programas set-user-ID la posibilidad de impedir que usuarios malintencionados les hagan leer archivos que los usuarios no deberían poder leer.

Si el proceso que llama tiene privilegios (es decir, su UID real es cero), entonces una comprobación X_OK tiene éxito para un archivo regular si el permiso de ejecución está habilitado para el propietario del archivo, el grupo o los otros.

faccessat()

faccessat() funciona exactamente igual que access(), excepto por las diferencias descritas aquí.

Si path es relativo, se interpreta en relación con el directorio al que se refiere el descriptor de archivo dirfd (en lugar de en relación con el directorio de trabajo actual del proceso que llama, como hace access() para un nombre de ruta relativo).

Si path es relativo y dirfd es el valor especial AT_FDCWD, entonces path se interpreta en relación con el directorio de trabajo actual del proceso que llama (como access()).

Si path es absoluto, entonces dirfd se ignora.

flags se construye combinando cero o más de los siguientes valores mediante OR:

AT_EACCESS
Realiza las comprobaciones de acceso utilizando los IDs de usuario y grupo efectivos. Por defecto, faccessat() utiliza los IDs reales (como access()).
AT_EMPTY_PATH (desde Linux 5.8)
Si path es una cadena vacía, opera sobre el archivo al que se refiere dirfd (que puede haber sido obtenido usando el descriptor open(2) O_PATH). En este caso, dirfd puede referirse a cualquier tipo de archivo, no solo a un directorio. Si dirfd es AT_FDCWD, la llamada opera sobre el directorio de trabajo actual. Esta bandera es específica de Linux; define _GNU_SOURCE para obtener su definición.
AT_SYMLINK_NOFOLLOW
Si path es un enlace simbólico, no lo resuelva: en su lugar, devuelve información sobre el propio enlace.

Véase openat(2) para una explicación de la necesidad de faccessat().

faccessat2()

La descripción de faccessat() dada anteriormente corresponde a POSIX.1 y a la implementación proporcionada por glibc. Sin embargo, la implementación de glibc fue una emulación imperfecta (ver BUGS) que encubrió el hecho de que la llamada al sistema faccessat() en bruto de Linux no tiene un argumento flags. Para permitir una implementación adecuada, Linux 5.8 añadió la llamada al sistema faccessat2(), que admite el argumento flags y permite una implementación correcta de la función de envoltura faccessat().

VALOR DE RETORNO

En caso de éxito (todos los permisos solicitados concedidos, o mode es F_OK y el archivo existe), se devuelve cero. En caso de error (al menos un bit en mode solicitó un permiso denegado, o mode es F_OK y el archivo no existe, o ocurrió algún otro error), se devuelve -1 y se establece errno para indicar el error.

ERRORES

EACCES
El acceso solicitado sería denegado al archivo, o se niega el permiso de búsqueda para alguno de los directorios en el prefijo de ruta de path. (Véase también path_resolution(7)).
EBADF
(faccessat()) path es relativo pero dirfd no es AT_FDCWD (faccessat()) ni un descriptor de archivo válido.
EFAULT
path apunta fuera de su espacio de direcciones accesible.
EINVAL
mode se especificó incorrectamente.
EINVAL
(faccessat()) Se especificó una bandera inválida en flags.
EIO
Ocurrió un error de E/S.
ELOOP
Se encontraron demasiados enlaces simbólicos al resolver path.
ENAMETOOLONG
path es demasiado largo.
ENOENT
Un componente de path no existe o es un enlace simbólico colgante.
ENOMEM
No había suficiente memoria del kernel disponible.
ENOTDIR
Un componente utilizado como directorio en path no es, de hecho, un directorio.
ENOTDIR
(faccessat()) path es relativo y dirfd es un descriptor de archivo que se refiere a un archivo que no es un directorio.
EPERM
Se solicitó permiso de escritura para un archivo que tiene establecida la bandera inmutable. Véase también FS_IOC_SETFLAGS(2const).
EROFS
Se solicitó permiso de escritura para un archivo en un sistema de archivos de solo lectura.
ETXTBSY
Se solicitó acceso de escritura a un ejecutable que está siendo ejecutado.

Un archivo es accesible solo si los permisos de cada uno de los directorios en el prefijo de la ruta de path otorgan permiso de búsqueda (es decir, de ejecución). Si algún directorio es inaccesible, entonces la llamada [[44]] access() falla, independientemente de los permisos del archivo en sí. Solo se comprueban los bits de acceso, no el tipo o el

contenido

Por lo tanto, si se determina que un directorio es escribible, probablemente significa que se pueden crear archivos en el directorio, y no que el directorio pueda ser escrito como un archivo. De manera similar, un archivo DOS puede reportarse como ejecutable, pero la llamada [[46]] execve(2) seguirá fallando.
