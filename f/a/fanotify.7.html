NOMBRE

fanotify - monitorización de eventos del sistema de archivos

DESCRIPCIÓN

La API fanotify proporciona notificación e interceptación de eventos del sistema de archivos. Los casos de uso incluyen escaneo de virus y gestión jerárquica de almacenamiento. En la API fanotify original, solo un conjunto limitado de eventos era compatible. En particular, no había soporte para eventos de creación, eliminación o movimiento. El soporte para esos eventos se agregó en Linux 5.1. (Ver inotify(7) para detalles de una API que notificaba esos eventos antes de Linux 5.1).

Las capacidades adicionales en comparación con la API de inotify(7) incluyen la capacidad de monitorizar todos los objetos en un sistema de archivos montado, la capacidad de tomar decisiones de permiso de acceso y la posibilidad de leer o modificar archivos antes de que sean accedidos por otras aplicaciones.

Las siguientes llamadas al sistema se utilizan con esta API: fanotify_init(2), fanotify_mark(2), read(2), write(2) y close(2).

fanotify_init(), fanotify_mark(), y grupos de notificación

La llamada al sistema fanotify_init(2) crea e inicializa un grupo de notificación fanotify y devuelve un descriptor de archivo que hace referencia a él.

Un grupo de notificación fanotify es un objeto interno del kernel que contiene una lista de archivos, directorios, sistemas de archivos y montajes para los cuales se crearán eventos.

Para cada entrada en un grupo de notificación fanotify, existen dos máscaras de bits: la máscara de marcado (mark) y la máscara de ignorar (ignore). La máscara de marcado define las actividades del archivo para las cuales se creará un evento. La máscara de ignorar define las actividades para las cuales no se generará ningún evento. Tener estos dos tipos de máscaras permite que un sistema de archivos, montaje o directorio se marque para recibir eventos, mientras que al mismo tiempo se ignoran eventos para objetos específicos bajo un montaje o directorio.

La llamada al sistema fanotify_mark(2) agrega un archivo, directorio, sistema de archivos o montaje a un grupo de notificación y especifica qué eventos deben informarse (o ignorarse), o elimina o modifica dicha entrada.

Un uso posible de la máscara de ignorar es para una caché de archivos. Los eventos de interés para una caché de archivos son la modificación de un archivo y el cierre del mismo. Por lo tanto, el directorio o montaje cacheados deben marcarse para recibir estos eventos. Después de recibir el primer evento que informa que un archivo ha sido modificado, la entrada de caché correspondiente se invalidará. No son de interés más eventos de modificación para este archivo hasta que el archivo se cierre. Por lo tanto, el evento de modificación se puede agregar a la máscara de ignorar. Al recibir el evento de cierre, el evento de modificación se puede eliminar de la máscara de ignorar y la entrada de caché de archivos se puede actualizar.

Las entradas en los grupos de notificación fanotify se refieren a archivos y directorios a través de su número de inodo y a montajes a través de su ID de montaje. Si los archivos o directorios se renombran o mueven dentro del mismo montaje, las entradas respectivas sobreviven. Si los archivos o directorios se eliminan o mueven a otro montaje o si los sistemas de archivos o montajes se desmontan, las entradas correspondientes se eliminan.

La cola de eventos

A medida que ocurren eventos en los objetos del sistema de archivos monitorizados por un grupo de notificación, el sistema fanotify genera eventos que se recopilan en una cola. Estos eventos pueden luego ser leídos (usando read(2) o similar) desde el descriptor de archivo fanotify devuelto por fanotify_init(2).

Se generan dos tipos de eventos: eventos de notificación y eventos de permiso. Los eventos de notificación son meramente informativos y no requieren ninguna acción por parte de la aplicación receptora, con una excepción: si se proporciona un descriptor de archivo válido dentro de un evento genérico, el descriptor de archivo debe cerrarse. Los eventos de permiso son solicitudes a la aplicación receptora para decidir si se debe otorgar el permiso para un acceso al archivo. Para estos eventos, el destinatario debe escribir una respuesta que decida si el acceso se otorga o no.

Un evento se elimina de la cola de eventos del grupo fanotify cuando ha sido leído. Los eventos de permiso que han sido leídos se mantienen en una lista interna del grupo fanotify hasta que se haya tomado una decisión de permiso escribiendo en el descriptor de archivo fanotify o hasta que se cierre el descriptor de archivo fanotify.

Lectura de eventos fanotify

Llamar a read(2) para el descriptor de archivo devuelto por fanotify_init(2) se bloquea (si la bandera FAN_NONBLOCK no se especifica en la llamada a fanotify_init(2)) hasta que ocurra un evento de archivo o la llamada sea interrumpida por una señal (ver signal(7)).

Después de una llamada exitosa a read(2), el búfer de lectura contiene una o más de las siguientes estructuras:


struct fanotify_event_metadata {
    __u32 event_len;
    __u8 vers;
    __u8 reserved;
    __u16 metadata_len;
    __aligned_u64 mask;
    __s32 fd;
    __s32 pid;
};

Los registros de información son piezas de información suplementarias que pueden proporcionarse junto con la estructura genérica fanotify_event_metadata. Las flags pasadas a fanotify_init(2) influyen en el tipo de registros de información que pueden devolverse para un evento. Por ejemplo, si un grupo de notificación se inicializa con FAN_REPORT_FID o FAN_REPORT_DIR_FID, entonces los oyentes de eventos también deben esperar recibir una estructura fanotify_event_info_fid junto con la estructura fanotify_event_metadata, donde los identificadores de archivo se usan para identificar objetos del sistema de archivos en lugar de descriptores de archivo. Los registros de información también pueden apilarse, lo que significa que el uso de las diversas banderas FAN_REPORT_* en conjunción entre sí es compatible. En tales casos, se pueden devolver múltiples registros de información para un evento junto con la estructura genérica fanotify_event_metadata. Por ejemplo, si un grupo de notificación se inicializa con FAN_REPORT_TARGET_FID y FAN_REPORT_PIDFD, entonces un oyente de eventos debe esperar recibir hasta dos registros de información fanotify_event_info_fid y un registro de información fanotify_event_info_pidfd junto con la estructura genérica fanotify_event_metadata. Es importante destacar que fanotify no proporciona ninguna garantía sobre el orden de los registros de información cuando un grupo de notificación se inicializa con una configuración basada en pila. Cada registro de información tiene una estructura anidada de tipo fanotify_event_info_header. Es imperativo que los oyentes de eventos inspeccionen el campo info_type de esta estructura para determinar el tipo de registro de información que se ha recibido para un evento dado.

En los casos en que un grupo fanotify identifica objetos del sistema de archivos por identificadores de archivo, los oyentes de eventos también deben esperar recibir uno o más de los siguientes objetos de registro de información junto con la estructura genérica fanotify_event_metadata dentro del búfer de lectura:


struct fanotify_event_info_fid {
    struct fanotify_event_info_header hdr;
    __kernel_fsid_t fsid;
    unsigned char handle[];
};

En los casos en que un grupo fanotify se inicializa con FAN_REPORT_PIDFD, los oyentes de eventos deben esperar recibir el siguiente objeto de registro de información junto con la estructura genérica fanotify_event_metadata dentro del búfer de lectura:


struct fanotify_event_info_pidfd {
        struct fanotify_event_info_header hdr;
        __s32 pidfd;
};

En los casos en que un grupo fanotify se inicializa con FAN_REPORT_MNT, los oyentes de eventos deben esperar recibir el siguiente objeto de registro de información junto con la estructura genérica fanotify_event_metadata dentro del búfer de lectura. Esta estructura se define de la siguiente manera:


struct fanotify_event_info_mnt {
    struct fanotify_event_info_header hdr;
    __u64 mnt_id;
};

En caso de un evento FAN_FS_ERROR, se devuelve un registro de información adicional que describe el error que ocurrió junto con la estructura genérica fanotify_event_metadata dentro del búfer de lectura. Esta estructura se define de la siguiente manera:


struct fanotify_event_info_error {
    struct fanotify_event_info_header hdr;
    __s32 error;
    __u32 error_count;
};

En caso de eventos FAN_PRE_ACCESS, se devuelve un registro de información adicional que describe el rango de acceso junto con la estructura genérica fanotify_event_metadata dentro del búfer de lectura. Esta estructura se define de la siguiente manera:


struct fanotify_event_info_range {
    struct fanotify_event_info_header hdr;
    __u32 pad;
    __u64 offset;
    __u64 count;
};

Todos los registros de información contienen una estructura anidada de tipo fanotify_event_info_header. Esta estructura contiene metadatos sobre el registro de información que puede haberse devuelto junto con la estructura genérica fanotify_event_metadata. Esta estructura se define de la siguiente manera:


struct fanotify_event_info_header {
	__u8 info_type;
	__u8 pad;
	__u16 len;
};

Por razones de rendimiento, se recomienda utilizar un tamaño de búfer grande (por ejemplo, 4096 bytes), de modo que se puedan recuperar varios eventos con una única llamada a read(2).

El valor de retorno de read(2) es el número de bytes colocados en el búfer, o -1 en caso de error (pero véase BUGS).

Los campos de la estructura fanotify_event_metadata son los siguientes:

event_len
Este es el tamaño de los datos para el evento actual y el desplazamiento al siguiente evento en el búfer. A menos que el grupo identifique objetos del sistema de archivos por identificadores de archivo, el valor de event_len es siempre FAN_EVENT_METADATA_LEN. Para un grupo que identifica objetos del sistema de archivos por identificadores de archivo, event_len también incluye los registros de identificador de archivo de tamaño variable.
vers
Este campo contiene un número de versión para la estructura. Debe compararse con FANOTIFY_METADATA_VERSION para verificar que las estructuras devueltas en tiempo de ejecución coinciden con las estructuras definidas en tiempo de compilación. En caso de discrepancia, la aplicación debe dejar de intentar usar el descriptor de archivo fanotify.
reserved
Este campo no se utiliza.
metadata_len
Este es el tamaño de la estructura. El campo se introdujo para facilitar la implementación de encabezados opcionales por tipo de evento. No existen tales encabezados opcionales en la implementación actual.
mask
Esta es una máscara de bits que describe el evento (ver más abajo).
fd
Este es un descriptor de archivo abierto para el objeto al que se accede, o FAN_NOFD si se produjo un desbordamiento de la cola. Con un grupo fanotify que identifica objetos del sistema de archivos por identificadores de archivo, las aplicaciones deben esperar que este valor se establezca en FAN_NOFD para cada evento recibido. El descriptor de archivo se puede utilizar para acceder al contenido del archivo o directorio monitorizado. La aplicación receptora es responsable de cerrar este descriptor de archivo.
Al llamar a fanotify_init(2), el llamador puede especificar (a través del argumento event_f_flags) varias banderas de estado de archivo que se establecerán en la descripción de archivo que corresponde a este descriptor de archivo. Además, la bandera de estado de archivo (interna del kernel) FMODE_NONOTIFY se establece en la descripción de archivo. Esta bandera suprime la generación de eventos fanotify. Por lo tanto, cuando el receptor del evento fanotify accede al archivo o directorio notificado utilizando este descriptor de archivo, no se crearán eventos adicionales.
Cuando se inicializa un grupo fanotify utilizando FAN_REPORT_FD_ERROR, este campo contendrá un valor de error negativo en caso de que no se pueda abrir un descriptor de archivo y, en caso de desbordamiento de la cola, el valor será -EBADF.
pid
Si la bandera FAN_REPORT_TID se estableció en fanotify_init(2), este es el TID del hilo que causó el evento. De lo contrario, este es el PID del proceso que causó el evento.

Un programa que escucha eventos fanotify puede comparar este PID con el PID devuelto por getpid(2), para determinar si el evento es causado por el propio oyente, o se debe al acceso a un archivo por otro proceso.

La máscara de bits en mask indica qué eventos han ocurrido para un único objeto del sistema de archivos. Se pueden establecer varios bits en esta máscara, si ocurrieron más de un evento para el objeto del sistema de archivos monitorizado. En particular, los eventos consecutivos para el mismo objeto del sistema de archivos y originados por el mismo proceso pueden fusionarse en un único evento, con la excepción de que dos eventos de permiso nunca se fusionan en una sola entrada de cola.

Los bits que pueden aparecer en mask son los siguientes:

FAN_ACCESS
Se accedió a un archivo o directorio (pero véase BUGS) (lectura).
FAN_OPEN
Se abrió un archivo o directorio.
FAN_OPEN_EXEC
Se abrió un archivo con la intención de ser ejecutado. Véase NOTAS en fanotify_mark(2) para obtener detalles adicionales.
FAN_ATTRIB
Se modificaron los metadatos de un archivo o directorio.
FAN_CREATE
Se creó un archivo o directorio hijo en un padre vigilado.
FAN_DELETE
Se eliminó un archivo o directorio hijo en un padre vigilado.
FAN_DELETE_SELF
Se eliminó un archivo o directorio vigilado.
FAN_RENAME
Un archivo o directorio ha sido movido desde o hacia un directorio padre vigilado.
FAN_MOVED_FROM
Un archivo o directorio ha sido movido desde un directorio padre vigilado.
FAN_MOVED_TO
Un archivo o directorio ha sido movido hacia un directorio padre vigilado.
FAN_MOVE_SELF
Se movió un archivo o directorio vigilado.
FAN_MODIFY
Se modificó un archivo.
FAN_CLOSE_WRITE
Se cerró un archivo que se abrió para escritura (O_WRONLY o O_RDWR).
FAN_CLOSE_NOWRITE
Se cerró un archivo o directorio que se abrió de solo lectura (O_RDONLY).
FAN_MNT_ATTACH
Se adjuntó un montaje al espacio de nombres de montaje.
FAN_MNT_DETACH
Se desadjuntó un montaje del espacio de nombres de montaje.
FAN_FS_ERROR
Se detectó un error del sistema de archivos.
FAN_Q_OVERFLOW
La cola de eventos superó el límite en el número de eventos. Este límite puede ser anulado especificando la bandera FAN_UNLIMITED_QUEUE al llamar a fanotify_init(2).
FAN_ACCESS_PERM
Una aplicación quiere leer un archivo o directorio, por ejemplo usando read(2) o readdir(2). El lector debe escribir una respuesta (como se describe a continuación) que determine si se concede el permiso para acceder al objeto del sistema de archivos.
FAN_OPEN_PERM
Una aplicación quiere abrir un archivo o directorio. El lector debe escribir una respuesta que determine si se concede el permiso para abrir el objeto del sistema de archivos.
FAN_OPEN_EXEC_PERM
Una aplicación quiere abrir un archivo para ejecución. El lector debe escribir una respuesta que determine si se concede el permiso para abrir el objeto del sistema de archivos para ejecución. Véase NOTAS en fanotify_mark(2) para obtener detalles adicionales.

Para comprobar cualquier evento de cierre, se puede utilizar la siguiente máscara de bits:

FAN_CLOSE
Se cerró un archivo. Esto es un sinónimo de:

FAN_CLOSE_WRITE | FAN_CLOSE_NOWRITE

Para comprobar cualquier evento de movimiento, se puede utilizar la siguiente máscara de bits:

FAN_MOVE
Se movió un archivo o directorio. Esto es un sinónimo de:

FAN_MOVED_FROM | FAN_MOVED_TO

Los siguientes bits pueden aparecer en mask solo en conjunción con otros bits de tipo de evento:

FAN_ONDIR
Los eventos descritos en la mask han ocurrido en un objeto de directorio. La notificación de eventos en directorios requiere el establecimiento de esta bandera en la máscara de marca. Véase fanotify_mark(2) para obtener detalles adicionales. La bandera FAN_ONDIR se notifica en una máscara de evento solo si el grupo fanotify identifica objetos del sistema de archivos por identificadores de archivo.

Manejo de eventos de

Para los eventos de permisos, la aplicación debe write(2) una estructura de la siguiente forma en el descriptor de archivo de

struct fanotify_response {
    __s32 fd;
    __u32 response;
}

Los campos de esta estructura son los

Este es el descriptor de archivo de la estructura fanotify_event_metada
ta.
respon
se
Este campo indica si el permiso se va a concedido. Su valor debe contener o bien la bandera FAN_ALLOW para permitir la operación sobre el archivo o FAN_DENY para denegar la o
peración sobr

Si se deniega el acceso, la llamada de la aplicación solicitante recibirá un error EPERM. Desde Linux 6.13, si un grupo de notificaciones se inicializa con la clase FAN_CLASS_PRE_CONTENT, la operación sobre el archivo puede denegarse con errores distintos de EPERM. Por ejemplo, para que la aplicación solicitante obtenga el error EIO, el oyente de eventos puede escribir la respuesta FAN_DENY_ERRNO(EIO). En el momento de escribir, solo los siguientes valores de error podían devolverse a la aplicación con la macro FAN_DENY_ERRNO(e): EPERM, EIO, EBUSY, ETXTBSY, EAGAIN, ENOSPC, EDQUOT

Adicionalmente, si el grupo de notificaciones se ha creado con la bandera FAN_ENABLE_AUDIT, entonces la bandera FAN_AUDIT puede establecerse en el campo response. En ese caso, el subsistema de auditoría registrará información sobre la decisión de acceso en los registros de

auditoría.

Desde Linux 6.3, la bandera FAN_INFO puede establecerse en el campo .response. Indica que un registro de respuesta adicional de longitud variable sigue a la estructura fanotify_response. Los registros de respuesta adicionales comienzan con una cabecera

Monitoreo de sistemas de archivos en busca de

errores

Un solo evento FAN_FS_ERROR se almacena por sistema de archivos a la vez. Los mensajes de error adicionales se suprimen y se contabilizan en el campo error_count del registro de evento FAN_FS_ERROR existente, pero se pierden los detalles sobre los

errores.

Los errores reportados por FAN_FS_ERROR son valores errno genéricos, pero no todos los tipos de errores son reportados por todos los sistemas de

archivos.

Los errores no directamente relacionados con un archivo (es decir, la corrupción del superbloque) se reportan con un handle inválido. Para estos errores, el handle tendrá el campo handle_type establecido a FILEID_INVALID, y el tamaño del búfer del handle establecido a 0

.

Cierre del descriptor de archivo de

fanotify

Cuando se cierran todos los descriptores de archivo que se refieren al grupo de notificaciones de fanotify, el grupo de fanotify se libera y sus recursos se liberan para su reutilización por el kernel. Al close(2), los eventos de permiso pendien

NOTA

S

La API de fanotify solo está disponible si el kernel se compiló con la opción de configuración CONFIG_FANOTIFY habilitada. Además, el manejo de permisos de fanotify solo está disponible si la opción de configuración CONFIG_FANOTIFY_ACCESS_PERMISSIONS está

habilitada.

Limitaciones y

advertencias

Fanotify solo reporta eventos que un programa en espacio de usuario desencadena a través de la API del sistema de archivos. Como resultado, no captura eventos remotos que ocurren en sistemas de archivos de

red.

La API de fanotify no reporta accesos y modificaciones de archivos que pueden ocurrir debido a mmap(2), msync(2) y munmap(

2).

Los eventos para directorios se crean solo si el directorio en sí es abierto, leído y cerrado. Agregar, eliminar o cambiar hijos de un directorio marcado no crea eventos para el directorio monitoreado en

sí.

El monitoreo de directorios con fanotify no es recursivo: para monitorear subdirectorios bajo un directorio, se deben crear marcas adicionales. El evento FAN_CREATE puede usarse para detectar cuándo se ha creado un subdirectorio bajo un directorio marcado. Luego se debe establecer una marca adicional en el subdirectorio recién creado. Este enfoque es propenso a condiciones de carrera, porque puede perder eventos que ocurrieron dentro del subdirectorio recién creado, antes de que se agregue una marca en ese subdirectorio. Monitorear puntos de montaje ofrece la capacidad de monitorear un árbol de directorios completo de manera libre de condiciones de carrera. Monitorear sistemas de archivos ofrece la capacidad de monitorear cambios realizados desde cualquier punto de montaje de una instancia de sistema de archivos de manera libre de condiciones de

carrera.

privilegiados.

El valor de retorno no será -1, y errno no se establecerá. Por lo tanto,

#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <limits.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/types.h>
#include <sys/stat.h>
#include <sys/fanotify.h>
#include <unistd.h>
#define BUF_SIZE 256
int
main(int argc, char *argv[])
{
    int fd, ret, event_fd, mount_fd;
    ssize_t size, path_len;
    char path[PATH_MAX];
    char procfd_path[PATH_MAX];
    char events_buf[BUF_SIZE];
    struct file_handle *file_handle;
    struct fanotify_event_metadata *metadata;
    struct fanotify_event_info_fid *fid;
    const char *file_name;
    struct stat sb;
    if (argc != 2) {
        fprintf(stderr, "Invalid number of command line arguments.\n");
        exit(EXIT_FAILURE);
    }
    mount_fd = open(argv[1], O_DIRECTORY | O_RDONLY);
    if (mount_fd == -1) {
        perror(argv[1]);
        exit(EXIT_FAILURE);
    }
    /* Create an fanotify file descriptor with FAN_REPORT_DFID_NAME as
       a flag so that program can receive fid events with directory
       entry name.  */
    fd = fanotify_init(FAN_CLASS_NOTIF | FAN_REPORT_DFID_NAME, 0);
    if (fd == -1) {
        perror("fanotify_init");
        exit(EXIT_FAILURE);
    }
    /* Place a mark on the filesystem object supplied in argv[1].  */
    ret = fanotify_mark(fd, FAN_MARK_ADD | FAN_MARK_ONLYDIR,
                        FAN_CREATE | FAN_ONDIR,
                        AT_FDCWD, argv[1]);
    if (ret == -1) {
        perror("fanotify_mark");
        exit(EXIT_FAILURE);
    }
    printf("Listening for events.\n");
    /* Read events from the event queue into a buffer.  */
    size = read(fd, events_buf, sizeof(events_buf));
    if (size == -1 && errno != EAGAIN) {
        perror("read");
        exit(EXIT_FAILURE);
    }
    /* Process all events within the buffer.  */
    for (metadata = (struct fanotify_event_metadata *) events_buf;
            FAN_EVENT_OK(metadata, size);
            metadata = FAN_EVENT_NEXT(metadata, size)) {
        fid = (struct fanotify_event_info_fid *) (metadata + 1);
        file_handle = (struct file_handle *) fid->handle;
        /* Ensure that the event info is of the correct type.  */
        if (fid->hdr.info_type == FAN_EVENT_INFO_TYPE_FID ||
            fid->hdr.info_type == FAN_EVENT_INFO_TYPE_DFID) {
            file_name = NULL;
        } else if (fid->hdr.info_type == FAN_EVENT_INFO_TYPE_DFID_NAME) {
            file_name = file_handle->f_handle +
                        file_handle->handle_bytes;
        } else {
            fprintf(stderr, "Received unexpected event info type.\n");
            exit(EXIT_FAILURE);
        }
        if (metadata->mask == FAN_CREATE)
            printf("FAN_CREATE (file created):\n");
        if (metadata->mask == (FAN_CREATE | FAN_ONDIR))
            printf("FAN_CREATE | FAN_ONDIR (subdirectory created):\n");
	/* metadata->fd is set to FAN_NOFD when the group identifies
	   objects by file handles.  To obtain a file descriptor for
	   the file object corresponding to an event you can use the
	   struct file_handle that's provided within the
	   fanotify_event_info_fid in conjunction with the
	   open_by_handle_at(2) system call.  A check for ESTALE se
	   devuelve para acomodar la situación en la que el descriptor de archivo
	   del objeto fue eliminado antes de esta llamada al sistema.  */
        event_fd = open_by_handle_at(mount_fd, file_handle, O_RDONLY);
        if (event_fd == -1) {
            if (errno == ESTALE) {
                printf("File handle is no longer valid.  "
                        "File has been deleted\n");
                continue;
            } else {
                perror("open_by_handle_at");
                exit(EXIT_FAILURE);
            }
        }
        snprintf(procfd_path, sizeof(procfd_path), "/proc/self/fd/%d",
                event_fd);
        /* Retrieve and print the path of the modified dentry.  */
        path_len = readlink(procfd_path, path, sizeof(path) - 1);
        if (path_len == -1) {
            perror("readlink");
            exit(EXIT_FAILURE);
        }
        path[path_len] = '\0';
        printf("\tEl directorio '%s' ha sido modificado.\n", path);
        if (file_name) {
            ret = fstatat(event_fd, file_name, &sb, 0);
            if (ret == -1) {
                if (errno != ENOENT) {
                    perror("fstatat");
                    exit(EXIT_FAILURE);
                }
                printf("\tLa entrada '%s' no existe.\n", file_name);
            } else if ((sb.st_mode & S_IFMT) == S_IFDIR) {
                printf("\tLa entrada '%s' es un subdirectorio.\n", file_name);
            } else {
                printf("\tLa entrada '%s' no es un subdirectorio.\n",
                        file_name);
            }
        }
        /* Close associated file descriptor for this event.  */
        close(event_fd);
    }
    printf("Todos los eventos fueron procesados exitosamente.  El programa está saliendo.\n");
    exit(EXIT_SUCCESS)
;
}
