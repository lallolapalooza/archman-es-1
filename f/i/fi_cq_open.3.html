NOMBRE

fi_cq - Operaciones de la cola de finalización

fi_cq_open / fi_close
Abrir/cerrar una cola de finalización
fi_control
Controlar la operación o atributos de la CQ.
fi_cq_read / fi_cq_readfrom / fi_cq_readerr
Leer una finalización de una cola de finalización
fi_cq_sread / fi_cq_sreadfrom
Una lectura síncrona (bloqueante) que espera hasta que se cumpla una condición especificada antes de leer una finalización de una cola de finalización.
fi_cq_signal
Desbloquear cualquier hilo que esté esperando en fi_cq_sread o fi_cq_sreadfrom.
fi_cq_strerror
Convierte información de error específica del proveedor en una cadena imprimible.

DESCRIPCIÓN

Las colas de finalización se utilizan para informar de eventos asociados con transferencias de datos. Se asocian con envíos y recepciones de mensajes, RMA, operaciones atómicas, mensajes etiquetados y eventos activados. Los eventos informados suelen estar asociados con un punto final de la red, pero también pueden hacer referencia a regiones de memoria utilizadas como destino de una operación RMA o atómica.

fi_cq_open

fi_cq_open asigna una nueva cola de finalización. A diferencia de las colas de eventos, las colas de finalización se asocian con un dominio de recursos y pueden descargarse completamente en el hardware del proveedor.

Las propiedades y el comportamiento de una cola de finalización se definen por struct fi_cq_attr.

struct fi_cq_attr {
    size_t               size;      /* # entradas para CQ */
    uint64_t             flags;     /* indicadores de operación */
    enum fi_cq_format    format;    /* formato de finalización */
    enum fi_wait_obj     wait_obj;  /* objeto de espera solicitado */
    int                  signaling_vector; /* afinidad de interrupción */
    enum fi_cq_wait_cond wait_cond; /* formato de condición de espera */
    struct fid_wait     *wait_set;  /* conjunto de espera opcional, obsoleto */
};
size
Especifica el tamaño mínimo de una cola de finalización. Un valor de 0 indica que el proveedor puede elegir un valor predeterminado.
flags
Indicadores que controlan la configuración de la CQ.
- FI_AFFINITY
Indica que el campo signaling_vector (ver más abajo) es válido.
format
Las colas de finalización permiten a la aplicación seleccionar la cantidad de detalle que debe almacenar e informar. El atributo format permite a la aplicación seleccionar uno de varios formatos de finalización, indicando la estructura de los datos que la cola de finalización debe devolver al leer. Los formatos admitidos y las estructuras que corresponden a cada uno se enumeran a continuación. El significado de los campos de entrada de la CQ se define en la sección Campos de finalización.
- FI_CQ_FORMAT_UNSPEC
Si se solicita un formato no especificado, la CQ utilizará un formato predeterminado seleccionado por el proveedor.
- FI_CQ_FORMAT_CONTEXT
Proporciona solo el contexto especificado por el usuario que se asoció con la finalización.

wait_obj
Las CQs pueden asociarse con un objeto de espera específico. Los objetos de espera permiten a las aplicaciones bloquearse hasta que el objeto de espera se active, lo que indica que hay una finalización disponible para leer. Los usuarios pueden usar fi_control para recuperar el objeto de espera subyacente asociado con una CQ, para usarlo en otras llamadas del sistema. tipo de objeto de espera asociado con una CQ: FI_WAIT_NONE, FI_WAIT_UNSPEC, FI_WAIT_SET, FI_WAIT_FD, FI_WAIT_MUTEX_COND (obsoleto), y FI_WAIT_YIELD. El valor predeterminado es FI_WAIT_NONE.
- FI_WAIT_NONE
Se utiliza para indicar que el usuario no se bloqueará (esperará) por finalizaciones en la CQ. Cuando se especifica FI_WAIT_NONE, la aplicación no puede llamar a fi_cq_sread ni a fi_cq_sreadfrom.
- FI_WAIT_UNSPEC
Especifica que el usuario solo esperará en la CQ utilizando llamadas de la interfaz de fabric, como fi_cq_sread o fi_cq_sreadfrom. En este caso, el proveedor subyacente puede seleccionar el objeto de espera más apropiado o de mayor rendimiento disponible, incluyendo mecanismos de espera personalizados. No se garantiza que las aplicaciones que seleccionan FI_WAIT_UNSPEC puedan recuperar el objeto de espera subyacente.
- FI_WAIT_SET (obsoleto)
Indica que la cola de finalización debe usar un objeto de conjunto de espera para esperar finalizaciones. Si se especifica, el campo wait_set debe referenciar un objeto de conjunto de espera existente.
- FI_WAIT_FD
Indica que la CQ debe usar un descriptor de archivo como su mecanismo de espera. Un objeto de espera de descriptor de archivo debe ser utilizable en las rutinas select, poll y epoll. Sin embargo, un proveedor puede señalar un objeto de espera FD marcándolo como legible, escribible o con un error.
- FI_WAIT_MUTEX_COND (obsoleto)
Especifica que la CQ debe usar un mutex de pthread y una variable de condición como objeto de espera.
- FI_WAIT_YIELD
Indica que la CQ esperará sin un objeto de espera, sino que cederá en cada espera. Permite el uso de fi_cq_sread y fi_cq_sreadfrom a través de un ciclo de espera activo (spin).
signaling_vector
Si se establece el indicador FI_AFFINITY, esto indica el número de CPU lógico (0..max cpu - 1) al que deben dirigirse las interrupciones asociadas con la CQ. Este campo debe tratarse como una sugerencia para el proveedor y puede ser ignorado si el proveedor no admite afinidad de interrupción.
wait_cond
De forma predeterminada, cuando se inserta una finalización en una CQ que admite lecturas bloqueantes (fi_cq_sread/fi_cq_sreadfrom), el objeto de espera correspondiente es señalizado. Los usuarios pueden especificar una condición que debe cumplirse primero antes de que la espera se satisfaga. Este campo indica cómo el proveedor debe interpretar el campo cond, que describe la condición necesaria para señalizar el objeto de espera.

Una condición de espera debe tratarse como una optimización. No se exige a los proveedores que cumplan los requisitos de la condición antes de señalizar el objeto de espera. Las aplicaciones no deben depender de que la condición sea necesariamente verdadera cuando una llamada de lectura bloqueante retorna.

Si wait_cond se establece en FI_CQ_COND_NONE, no se aplican condiciones adicionales a la señalización del objeto de espera de la CQ, y la inserción de cualquier nueva entrada activará la condición de espera. Si wait_cond se establece en FI_CQ_COND_THRESHOLD, el campo cond se interpreta como un valor umbral de size_t. El umbral indica el número de entradas que deben encolarse en la CQ antes de que la espera se satisfaga.

Este campo se ignora si wait_obj se establece en FI_WAIT_NONE.

wait_set (obsoleto)
Si wait_obj es FI_WAIT_SET, este campo referencia un objeto de espera al que la cola de finalización debe adjuntarse. Cuando se inserta un evento en la cola de finalización, el conjunto de espera correspondiente será señalizado si todas las condiciones necesarias se cumplen. El uso de un wait_set permite un método optimizado de espera de eventos en múltiples colas de eventos y finalizaciones. Este campo se ignora si wait_obj no es FI_WAIT_SET.

fi_close

La llamada fi_close libera todos los recursos asociados con una cola de finalización. Cualquier finalización que permanezca en la CQ cuando esta se cierre se perderá.

Al cerrar la CQ, no debe haber puntos finales abiertos, contextos de transmisión ni contextos de recepción asociados con la CQ. Si aún hay recursos asociados con la CQ al intentar cerrarla, la llamada retornará -FI_EBUSY.

fi_control

La llamada fi_control se utiliza para acceder a detalles específicos del proveedor o de la implementación de la cola de finalización. El acceso a la CQ debe ser serializado en todas las llamadas cuando se invoca fi_control, ya que puede redirigir la implementación de las operaciones de la CQ. Los siguientes comandos de control son utilizables con una CQ.

FI_GETWAIT (void **)
Este comando permite al usuario recuperar el objeto de espera de bajo nivel asociado con la CQ. El formato del objeto de espera se especifica durante la creación de la CQ, a través de los atributos de la CQ. El parámetro arg de fi_control debe ser una dirección donde se escribirá un puntero al objeto de espera devuelto. Consulte fi_eq.3 para obtener más detalles sobre el uso de fi_control con FI_GETWAIT.

fi_cq_read

La operación fi_cq_read realiza una lectura no bloqueante de datos de finalización desde la CQ. El formato del evento de finalización se determina utilizando la opción fi_cq_format que se especificó cuando se abrió la CQ. Se pueden recuperar múltiples finalizaciones de una CQ en una sola llamada. El número máximo de entradas a retornar está limitado por el parámetro count especificado, retornando la llamada el número de entradas leídas con éxito de la CQ. (Vea la sección de valores de retorno más abajo.) Un valor de count de 0 puede usarse para impulsar el progreso en los puntos finales asociados cuando el progreso manual está habilitado.

Las CQ están optimizadas para reportar operaciones que se han completado con éxito. Las operaciones que fallan se reportan `fuera de banda'. Dichas operaciones se recuperan utilizando la función fi_cq_readerr. Cuando se encuentra una operación que se completó con un error inesperado, se coloca en una cola de errores temporal. Intentar leer de una CQ mientras hay un elemento en la cola de errores resulta en que fi_cq_read falle con un código de retorno de -FI_EAVAIL. Las aplicaciones pueden usar este código de retorno para determinar cuándo llamar a fi_cq_readerr.

fi_cq_readfrom

La llamada fi_cq_readfrom se comporta de manera idéntica a fi_cq_read, con la excepción de que permite a la CQ retornar información de dirección de origen al usuario para cualquier dato recibido. Los datos de dirección de origen solo están disponibles para aquellos puntos finales configurados con la capacidad FI_SOURCE. Si se llama a fi_cq_readfrom en un punto final para el cual los datos de direccionamiento de origen no están disponibles, la dirección de origen se establecerá en FI_ADDR_NOTAVAIL. El número de entradas de entrada src_addr debe ser el mismo que el parámetro count.

Los datos de direccionamiento de origen retornados se convierten desde la dirección nativa utilizada por el fabric subyacente a un fi_addr_t, que puede usarse en operaciones de transmisión. En la mayoría de las circunstancias, retornar fi_addr_t requiere que la dirección de origen ya haya sido insertada en el vector de direcciones asociado con el punto final de recepción. Esto es cierto para vectores de dirección de tipo FI_AV_TABLE. En algunos proveedores cuando se usa FI_AV_MAP, las direcciones de origen pueden convertirse algorítmicamente en un fi_addr_t utilizable, aunque la dirección de origen no haya sido insertada en el vector de dirección. Esto está permitido por la API, ya que permite al proveedor evitar la búsqueda de direcciones como parte del procesamiento de mensajes recibidos. En ningún caso los proveedores insertan direcciones en un AV de forma separada a que una aplicación llame a fi_av_insert o una llamada similar.

Para los puntos finales asignados utilizando la capacidad FI_SOURCE_ERR, si la dirección de origen no puede convertirse en un valor fi_addr_t válido, fi_cq_readfrom retornará -FI_EAVAIL, incluso si los datos se recibieron con éxito. La finalización será reportada entonces a través de fi_cq_readerr con el código de error -FI_EADDRNOTAVAIL. Consulte fi_cq_readerr para más detalles.

Si FI_SOURCE se especifica sin FI_SOURCE_ERR, las direcciones de origen que no puedan mapearse a un fi_addr_t utilizable serán reportadas como FI_ADDR_NOTAVAIL.

fi_cq_sread / fi_cq_sreadfrom

Las llamadas fi_cq_sread y fi_cq_sreadfrom son las operaciones equivalentes bloqueantes a fi_cq_read y fi_cq_readfrom. Su comportamiento es similar al de las llamadas no bloqueantes, con la excepción de que las llamadas no retornarán hasta que se haya leído una finalización de la CQ o ocurra un error o un tiempo de espera agotado.

Los hilos bloqueados en esta función retornarán al llamador si son señalizados por alguna fuente externa. Esto es cierto incluso si el tiempo de espera no ha ocurrido o se especificó como infinito.

Es inválido para las aplicaciones llamar a estas funciones si la CQ ha sido configurada con un objeto de espera de FI_WAIT_NONE o FI_WAIT_SET.

fi_cq_readerr

La función de lectura de errores, fi_cq_readerr, recupera información sobre cualquier operación asíncrona que se haya completado con un error inesperado. fi_cq_readerr es una llamada no bloqueante, retornando inmediatamente ya sea que se haya encontrado una finalización de error o no.

La información de error se reporta al usuario a través de la estructura fi_cq_err_entry. El formato de esta estructura se define a continuación.

struct fi_cq_err_entry {
    void     *op_context; /* contexto de la operación */
    uint64_t flags;       /* indicadores de finalización */
    size_t   len;         /* tamaño de los datos recibidos */
    void     *buf;        /* búfer de datos de recepción */
    uint64_t data;        /* datos de finalización */
    uint64_t tag;         /* etiqueta del mensaje */
    size_t   olen;        /* longitud de desbordamiento */
    int      err;         /* código de error positivo */
    int      prov_errno;  /* código de error del proveedor */
    void    *err_data;    /*  datos de error */
    size_t   err_data_size; /* tamaño de err_data */
    fi_addr_t src_addr; /* dirección de origen del error */
};

La razón general del error se proporciona a través del campo err. La información de error específica del proveedor también puede estar disponible a través de los campos prov_errno y err_data. Los usuarios pueden llamar a fi_cq_strerror para convertir la información de error específica del proveedor en una cadena imprimible con fines de depuración. Consulte los detalles de los campos más abajo para obtener más información sobre el uso de err_data y err_data_size.

Tenga en cuenta que se generan finalizaciones de error para todas las operaciones, incluyendo aquellas para las cuales no se solicitó una finalización (por ejemplo, un punto final está configuradourado con FI_SELECTIVE_COMPLETION, pero la solicitud no tenía establecido el indicador FI_COMPLETION). En tales casos, los proveedores devolverán toda la información disponible proporcionada por el software y el hardware subyacentes sobre el fallo; los demás campos se establecerán en NULL o 0. Esto incluye el valor de op_context, que puede no haber sido proporcionado o haber sido ignorado en la entrada como parte de la transferencia.

A continuación se indican los códigos de error de finalización notables.

FI_EADDRNOTAVAIL
Este código de error es utilizado por las CQ configuradas con FI_SOURCE_ERR para reportar finalizaciones para las cuales no se pudo encontrar una dirección de origen fi_addr_t utilizable. Un código de error de FI_EADDRNOTAVAIL indica que la transferencia de datos fue recibida y procesada correctamente, con los campos de fi_cq_err_entry que contienen información sobre la finalización. El campo err_data se establecerá con los datos de la dirección de origen. La dirección de origen estará en el mismo formato que el especificado a través del campo addr_format de fi_info para el dominio abierto. Esta puede pasarse directamente a una llamada fi_av_insert para añadir la dirección de origen al vector de direcciones.

Para las versiones de la API 1.20 y posteriores, si el EP está configurado con FI_AV_AUTH_KEY, src_addr se establecerá con el identificador de clave de autorización fi_addr_t o un ID de clave de autorización definido por el usuario correspondiente a la transferencia de datos entrante. De lo contrario, el valor se establecerá en FI_ADDR_NOTAVAIL.

fi_cq_signal

La llamada fi_cq_signal desbloqueará cualquier hilo que esté esperando en fi_cq_sread o fi_cq_sreadfrom. Esto puede usarse para despertar a un hilo que está bloqueado esperando para leer una operación de finalización. La operación fi_cq_signal solo está disponible si la CQ fue configurada con un objeto de espera.

CAMPOS DE FINALIZACIÓN

Las estructuras de datos de las entradas de la CQ comparten muchos de los mismos campos. El significado de estos campos es el mismo para todos los formatos de estructura de entradas de la CQ.

op_context
El contexto de la operación es el valor de contexto especificado por la aplicación que fue proporcionado con una operación asíncrona. El campo op_context es válido para todas las finalizaciones que están asociadas con una operación asíncrona.

Para los eventos de finalización que no están asociados con una operación publicada, este campo se establecerá en NULL. Esto incluye las finalizaciones generadas en el destino en respuesta a operaciones de escritura RMA que llevan datos de CQ (indicadores FI_REMOTE_WRITE | FI_REMOTE_CQ_DATA establecidos), cuando el bit de modo FI_RX_CQ_DATA no es requerido.

flags
Esto especifica los indicadores asociados con la operación completada. El Indicadores de Finalización siguiente sección lista los valores de indicadores válidos. Los indicadores se establecen para todas las finalizaciones relevantes.
len
Este campo len se aplica a las operaciones de recepción completadas (p. ej., fi_recv, fi_trecv, etc.) y a la escritura completada con datos remotos de cq en el lado del respondedor (p. ej., fi_write, con el indicador FI_REMOTE_CQ_DATA). Indica el tamaño de los datos transferidos del mensaje – es decir, cuántos bytes de datos fueron colocados en el búfer de recepción/destino asociado por una llamada correspondiente fi_send/fi_tsend/fi_write, etc. Si un punto final ha sido configurado con el modo FI_MSG_PREFIX, el len también refleja el tamaño del búfer de prefijo.
buf
El campo buf solo es válido para operaciones de recepción completadas, y solo se aplica cuando el búfer de recepción fue publicado con el indicador FI_MULTI_RECV. En este caso, buf apunta a la ubicación de inicio donde se colocaron los datos de recepción.
data
El campo data solo es válido si el indicador de finalización FI_REMOTE_CQ_DATA está establecido, y solo se aplica a las finalizaciones de recepción. Si FI_REMOTE_CQ_DATA está establecido, este campo contendrá los datos de finalización proporcionados por el par como parte de su solicitud de transmisión. Los datos de finalización se darán en el orden de bytes del host.
tag
Una etiqueta (tag) se aplica solo a los mensajes recibidos que ocurren utilizando las interfaces con etiquetas (tagged). Este campo contiene la etiqueta que fue incluida con el mensaje recibido. La etiqueta estará en el orden de bytes del host.
olen
El campo olen se aplica a los mensajes recibidos. Se usa para indicar que un mensaje recibido ha desbordado el espacio de búfer disponible y ha sido truncado. El olen especifica la cantidad de datos que no cabieron en el búfer de recepción disponible y fueron descartados.
err
Este código err es un errno de fabricación positivo asociado con una finalización. El valor err indica la razón general de un error, si ocurrió alguno. Consulte fi_errno.3 para obtener una lista de los códigos de error posibles.
prov_errno
En caso de error, prov_errno puede contener un código de error específico del proveedor. El uso de este campo y su significado es específico del proveedor. Está destinado a usarse como una ayuda para la depuración. Consulte fi_cq_strerror para obtener más detalles sobre cómo convertir este valor de error en una cadena legible para humanos.
err_data
El campo err_data se usa para devolver información específica del proveedor, si está disponible, sobre el error. En la entrada, err_data debe referenciar un búfer de datos de tamaño err_data_size. En la salida, el proveedor rellenará este búfer con cualquier dato específico del proveedor que pueda ayudar a identificar la causa del error. El contenido del campo err_data y su significado es específico del proveedor. Está destinado a usarse como una ayuda para la depuración. Consulte fi_cq_strerror para obtener más detalles sobre cómo convertir estos datos de error en una cadena legible para humanos. Consulte la nota de compatibilidad más abajo sobre cómo se usa este campo en versiones anteriores de libfabric.
err_data_size
En la entrada, err_data_size indica el tamaño del búfer err_data en bytes. En la salida, err_data_size se establecerá con el número de bytes copiados al búfer err_data. La información de err_data se usa típicamente con fi_cq_strerror para proporcionar detalles sobre el tipo de error que ocurrió.

Con fines de compatibilidad, el comportamiento de los campos err_data y err_data_size puede ser modificado respecto a lo listado arriba. Si err_data_size es 0 en la entrada, o si la fabricación fue abierta con una versión < 1.5, entonces cualquier búfer referenciado por err_data será ignorado en la entrada. En esta situación, en la salida err_data se establecerá con un búfer de datos propiedad del proveedor. El contenido del búfer permanecerá válido hasta una llamada de lectura posterior contra la CQ. Las aplicaciones deben serializar el acceso a la CQ al procesar errores para asegurar que el búfer referenciado por err_data no cambie.

src_addr
Se usa para devolver información relacionada con la dirección de origen para eventos de error. Cómo se usa este campo es específico del evento de error.

INDICADORES DE FINALIZACIÓN

Los indicadores de finalización proporcionan detalles adicionales sobre la operación completada. Se definen los siguientes indicadores de finalización.

FI_SEND
Indica que la finalización fue para una operación de envío. Este indicador puede combinarse con un indicador FI_MSG o FI_TAGGED.
FI_RECV
Indica que la finalización fue para una operación de recepción. Este indicador puede combinarse con un indicador FI_MSG o FI_TAGGED.
FI_RMA
Indica que una operación RMA fue completada. Este indicador puede combinarse con un indicador FI_READ, FI_WRITE, FI_REMOTE_READ o FI_REMOTE_WRITE.
FI_ATOMIC
Indica que una operación atómica fue completada. Este indicador puede combinarse con un indicador FI_READ, FI_WRITE, FI_REMOTE_READ o FI_REMOTE_WRITE.
FI_MSG
Indica que una operación basada en mensajes fue completada. Este indicador puede combinarse con un indicador FI_SEND o FI_RECV.
FI_TAGGED
Indica que una operación de mensaje con etiqueta fue completada. Este indicador puede combinarse con un indicador FI_SEND o FI_RECV.
FI_MULTICAST
Indica que una operación de multidifusión fue completada. Este indicador puede combinarse con FI_MSG e indicadores relevantes. Solo se garantiza que este indicador sea válido para los mensajes recibidos si el punto final ha sido configurado con FI_SOURCE.
FI_READ
Indica que una operación de lectura RMA o atómica iniciada localmente ha sido completada. Este indicador puede combinarse con un indicador FI_RMA o FI_ATOMIC.
FI_WRITE
Indica que una operación de escritura RMA o atómica iniciada localmente ha sido completada. Este indicador puede combinarse con un indicador FI_RMA o FI_ATOMIC.
FI_REMOTE_READ
Indica que una operación de lectura RMA o atómica iniciada remotamente ha sido completada. Este indicador puede combinarse con un indicador FI_RMA o FI_ATOMIC.
FI_REMOTE_WRITE
Indica que una operación de escritura RMA o atómica iniciada remotamente ha sido completada. Este indicador puede combinarse con un indicador FI_RMA o FI_ATOMIC.
FI_REMOTE_CQ_DATA
Esto indica que hay datos remotos de CQ disponibles como parte de la finalización.
FI_MULTI_RECV
Este indicador se aplica a los búferes de recepción que fueron publicados con el indicador FI_MULTI_RECV establecido. Este indicador de finalización indica que el búfer de recepción original referenciado por la finalización ha sido consumido y fue liberado por el proveedor. Los proveedores pueden establecer este indicador en el último mensaje que es recibido en el búfer de recepción múltiple (multi-recv), o pueden generar una finalización separada que indique que el búfer ha sido liberado.

Las aplicaciones pueden distinguir entre estos dos casos examinando el campo de indicadores de la entrada de finalización. Si otros indicadores, como FI_RECV, están establecidos, la finalización está asociada con un mensaje recibido. En este caso,

MULTIRECV

El campo `buf` hará referencia a la ubicación donde el mensaje recibido se colocó en el búfer de recepción múltiple. Otros campos en la entrada de finalización se determinarán en función del mensaje recibido. Si otros bits de bandera son cero, el proveedor informa que el búfer de recepción múltiple ha sido liberado y la entrada de finalización no está asociada con un mensaje recibido.

SEMÁNTICA DE EVENTOS DE FINALIZACIÓN

Libfabric define varios `niveles' de finalización, identificados mediante banderas operacionales. Cada bandera indica lo antes posible que un proveedor puede generar un evento de finalización y las suposiciones que una aplicación puede hacer al procesar una finalización. Las banderas operacionales se definen a continuación, junto con un ejemplo de cómo un proveedor podría implementar la semántica. Tenga en cuenta que solo cumplir la semántica es requerido del proveedor y no la implementación. Los proveedores pueden implementar semánticas de finalización más fuertes de lo necesario para una operación dada, pero solo se garantiza el comportamiento definido por el nivel de finalización.

Para ayudar a comprender las diferencias conceptuales en los niveles de finalización, considere enviar una carta por correo. Poner la carta en el buzón local para su recogida es similar a `inject complete'. Que la carta sea recogida y dejada en el buzón de destino es equivalente a `transmit complete'. La semántica de `delivery complete' es una garantía más fuerte, con una persona en el destino firmando la carta. Sin embargo, la persona que firmó la carta no es necesariamente el destinatario previsto. La opción `match complete' es similar a delivery complete, pero requiere que el destinatario previsto firme la carta.

El nivel `commit complete' tiene una semántica diferente a los niveles mencionados anteriormente. Commit complete sería más parecido a que la carta llegue al destino y se guarde en una caja fuerte a prueba de fuego.

Las banderas operacionales para los niveles de finalización descritos se definen a continuación.

FI_INJECT_COMPLETE
Indica que se debe generar una finalización cuando los búferes de origen puedan ser reutilizados. Una finalización garantiza que los búferes no se leerán de nuevo y la aplicación puede reclamarlos. No se hacen otras garantías con respecto al estado de la operación.

Ejemplo: Un proveedor puede generar este evento de finalización después de copiar el búfer de origen a un búfer de red, ya sea en memoria del host o en la NIC. Una finalización de inyección no indica que los datos se hayan transmitido a la red, y podría ocurrir un error local después de que se haya generado el evento de finalización que podría impedir su transmisión.

La inyección completa permite la generación de informes de finalización más rápida (y, por lo tanto, la reutilización de búferes), pero proporciona las garantías más débiles contra errores de red.

Nota: Esta bandera se utiliza para controlar cuándo se inserta una entrada de finalización en una cola de finalización. No se aplica a operaciones que no generan una entrada de cola de finalización, como la operación `fi_inject', y no está sujeta a la restricción del límite de mensajes `inject_size'.

FI_TRANSMIT_COMPLETE
Indica que se debe generar una finalización cuando la operación de transmisión se haya completado en relación con el proveedor local. El comportamiento exacto depende del tipo de punto final.

Para puntos finales fiables:

Indica que se debe generar una finalización cuando la operación se haya entregado al punto final remoto. Una finalización garantiza que la operación ya no depende de la red o de los recursos locales. El estado de la operación en el punto final remoto no está definido.

Ejemplo: Un proveedor puede generar un evento de finalización de transmisión al recibir un acuse de recibo del punto final remoto. El estado del mensaje en el destino es desconocido y puede estar en el búfer de la NIC de destino en el momento en que se generó el acuse de recibo.

Para puntos finales no fiables:

Indica que se debe generar una finalización cuando la operación se haya entregado a la red. Una finalización garantiza que la operación ya no depende de los recursos locales. El estado de la operación dentro de la red no está definido.

FI_DELIVERY_COMPLETE
Indica que no se debe generar una finalización hasta que una operación haya sido procesada por el (los) punto(s) final(es) de destino. Una finalización garantiza que el resultado de la operación está disponible; sin embargo, pueden ser necesarios pasos adicionales en el destino para recuperar los resultados. Por ejemplo, una aplicación puede necesitar proporcionar búferes de recepción para recuperar mensajes que fueron almacenados en búfer por el proveedor.

La finalización de entrega indica que el mensaje ha sido procesado por el par. Si un búfer de aplicación estaba listo para recibir los resultados del mensaje cuando llegó, entonces la finalización de entrega indica que los datos se colocaron en el búfer de la aplicación.

Este modo de finalización se aplica solo a puntos finales fiables. Para operaciones que devuelven datos al iniciador, como lectura RMA o atomic-fetch, el punto final de origen también se considera un punto final de destino. Este es el modo de finalización predeterminado para tales operaciones.

FI_MATCH_COMPLETE
Indica que una finalización solo se generará después de que la operación se haya emparejado con un búfer especificado por la aplicación. Las operaciones que utilizan esta semántica de finalización dependen de que la aplicación en el destino reclame el mensaje o los resultados. Como resultado, el emparejamiento completo puede implicar confirmaciones adicionales a nivel de proveedor o largos retrasos. Sin embargo, este modelo de finalización permite a las aplicaciones del par sincronizar su ejecución. Muchos proveedores pueden no admitir esta semántica.
FI_COMMIT_COMPLETE
Indica que no se generará una finalización (localmente o en el par) hasta que el resultado de una operación se haya hecho persistente. Una finalización garantiza que el resultado está disponible y es duradero, en caso de fallo de alimentación.

Este modo de finalización se aplica solo a operaciones que se dirigen a regiones de memoria persistente sobre puntos finales fiables. Este modo de finalización es experimental.

FI_FENCE
Esta no es una nivel de finalización, pero juega un papel en el orden de finalización entre operaciones que normalmente no se ordenarían. Una operación marcada con la bandera `FI_FENCE' y todas las operaciones publicadas después de la operación cercada se aplazan hasta que todas las operaciones anteriores dirigidas al mismo punto final remoto se hayan completado. Además, la finalización de la operación cercada indica que las operaciones anteriores han cumplido el mismo nivel de finalización que la operación cercada. Por ejemplo, si una operación se publica como `FI_DELIVERY_COMPLETE | FI_FENCE', entonces su finalización indica que las operaciones anteriores han cumplido la semántica requerida para `FI_DELIVERY_COMPLETE'. Esto es cierto incluso si la operación anterior se publicó con un nivel de finalización inferior, como `FI_TRANSMIT_COMPLETE' o `FI_INJECT_COMPLETE'.

Tenga en cuenta que una finalización generada para una operación publicada antes de la operación cercada solo garantiza que se ha cumplido el nivel de finalización solicitado originalmente. Es la finalización de la operación cercada la que garantiza que se han cumplido las semánticas adicionales.

Las semánticas de finalización anteriores se definen con respecto al iniciador de la operación. Las diferentes semánticas son útiles para describir cuándo el iniciador puede reutilizar un búfer de datos y garantizan hasta qué estado debe llegar una transferencia antes de que se genere una finalización. Esto permite a las aplicaciones determinar el manejo de errores apropiado en caso de fallos de comunicación.

SEMÁNTICA DE FINALIZACIÓN DEL DESTINO

La semántica de finalización en el destino se utiliza para determinar cuándo los datos en el destino son visibles para la aplicación del par. La visibilidad indica que una lectura de memoria a la misma dirección que era el destino de una transferencia de datos devolverá los resultados de la transferencia. El destino de una transferencia puede ser identificado por el iniciador, como puede ser el caso de las operaciones RMA y atómicas, o determinado por el destino, por ejemplo, al proporcionar un búfer de recepción coincidente. La visibilidad global indica que los resultados están disponibles independientemente de dónde se origine la lectura de memoria. Por ejemplo, la lectura podría provenir de un proceso que se ejecuta en una CPU host, podría accederse mediante una transferencia de datos posterior a través de la red o leerse desde un dispositivo remoto como una GPU.

En términos de semántica de finalización, la visibilidad generalmente indica que la transferencia cumple los requisitos de `FI_DELIVERY_COMPLETE' desde la perspectiva del destino. La semántica de finalización del destino puede estar, pero no necesariamente, vinculada con la semántica de finalización especificada por el iniciador de la transferencia.

A menudo, los procesos de destino no declaran explícitamente una semántica de finalización deseada y, en su lugar, confían en la semántica predeterminada. El comportamiento predeterminado se basa en varios factores, que incluyen:

•
si se genera un evento de finalización en el destino
•
el tipo de transferencia involucrada (por ejemplo, mensaje frente a RMA)
•
las garantías de ordenación de datos y mensajes del punto final
•
las propiedades del búfer de memoria de destino
•
la semántica de finalización especificada por el iniciador

En términos generales, las semánticas de finalización del destino se agrupan según si la transferencia genera o no un evento de finalización en el destino. Esto incluye escribir una entrada de CQ o actualizar un contador de finalización. En casos de uso comunes, las transferencias que utilizan una interfaz de mensajes (FI_MSG o FI_TAGGED) suelen generar eventos de destino, mientras que las transferencias que involucran una interfaz RMA (FI_RMA o FI_ATOMIC) a menudo no lo hacen. Hay excepciones a ambos casos, dependiendo de las asociaciones de punto final a CQ y contador, y de las banderas operacionales. Por ejemplo, las escrituras RMA que transportan datos de CQ remotos generarán un evento de finalización en el destino, y se utilizan frecuentemente para transmitir visibilidad a la aplicación de destino. Las pautas generales para la semántica del lado del destino se describen a continuación, seguidas de excepciones que modifican ese comportamiento.

Por defecto, las finalizaciones generadas en el destino indican que los datos transferidos están inmediatamente disponibles para ser leídos del búfer de destino. Es decir, el destino ve semántica `FI_DELIVERY_COMPLETE' (o mejor), incluso si el iniciador solicitó semánticas inferiores. Para aplicaciones que solo utilizan búferes de datos asignados de memoria del host, esto suele ser suficiente.

F

o en operaciones que no generan un evento de finalización en el destino, la visibilidad de los datos en el destino puede necesitar inferirse basándose en operaciones posteriores que sí generan finalizaciones en el destino. En ausencia de una finalización en el destino, cuando se escribe en el iniciador la finalización de una operación, la semántica de visibilidad de la operación en el destino se alinea con la semántica de finalización del iniciador. Por ejemplo, si una operación RMA finaliza en el iniciador como FI_INJECT_COMPLETE o FI_TRANSMIT_COMPLETE, no se garantiza la visibilidad de los datos en el destino.

El proceso de destino puede utilizar uno o más de los siguientes mecanismos para garantizar que los resultados de una transferencia de datos que no generó una finalización en el destino ahora son visibles. Esta lista no es exhaustiva de todas las opciones, sino que define usos comunes. En las descripciones siguientes, la primera transferencia no resulta en un evento de finalización en el destino, pero es seguida eventualmente por una transferencia que sí lo hace.

•
Si el punto de extremo garantiza el orden de mensajes entre dos transferencias, la finalización en el destino de una segunda transferencia indicará que los datos de la primera transferencia están disponibles. Por ejemplo, si el punto de extremo admite el orden de escritura después de envío (FI_ORDER_SAW), entonces una finalización de recepción correspondiente al envío indicará que los datos de la escritura están disponibles. Esto se mantiene independientemente de la semántica de finalización del iniciador para la escritura o el envío. Cuando se garantiza el orden, la segunda transferencia puede encolarse en el proveedor inmediatamente después de encolar la primera.
•
Si el punto de extremo no garantiza el orden de mensajes, el iniciador debe tomar pasos adicionales para asegurar la visibilidad. Si el iniciador solicita semántica FI_DELIVERY_COMPLETE para la primera operación, el iniciador puede esperar a que la operación finalice localmente. Una vez que se ha leído la finalización, la finalización en el destino de una segunda transferencia indicará que los datos de la primera transferencia son visibles.
•
Alternativamente, si el punto de extremo no garantiza el orden de mensajes, el iniciador puede usar los indicadores FI_FENCE y FI_DELIVERY_COMPLETE en la segunda transferencia de datos para forzar que las primeras transferencias cumplan la semántica FI_DELIVERY_COMPLETE. Si la segunda transferencia genera una finalización en el destino, eso indicará que los datos son visibles. De lo contrario, una finalización en el destino de cualquier transferencia después de la operación cercada (fenced) indicará que los datos son visibles.

Las semánticas anteriores se aplican a transferencias dirigidas a búferes de memoria de host tradicionales. Sin embargo, el comportamiento puede diferir cuando se involucra memoria de dispositivo y/o memoria persistente (bits de capacidad FI_HMEM y FI_PMEM). Cuando se involucra memoria heterogénea, entra en juego el concepto de dominios de memoria. Los dominios de memoria identifican la separación física de la memoria, que puede o no ser accesible a través del mismo espacio de direcciones virtuales. Consulte la página del manual fi_mr(3) para obtener más detalles sobre los dominios de memoria.

El orden de finalización y la visibilidad de los datos solo están bien definidos para transferencias dirigidas al mismo dominio de memoria. Las aplicaciones deben ser conscientes de las diferencias de orden y visibilidad cuando las transferencias se dirigen a diferentes dominios de memoria. Además, las aplicaciones también deben preocuparse por el dominio de memoria en el que se escriben las finalizaciones mismas y si difiere del dominio de memoria al que se dirige una transferencia. En algunas situaciones, ya sea el proveedor o la aplicación pueden necesitar llamar a APIs específicas del dispositivo para sincronizar o vaciar (flush) las cachés de memoria del dispositivo para lograr la visibilidad de datos deseada.

Cuando se utiliza memoria heterogénea, la semántica de finalización en el destino por defecto para transferencias que generan una finalización en el destino sigue siendo FI_DELIVERY_COMPLETE; sin embargo, las aplicaciones deben ser conscientes de que puede haber un impacto negativo en el rendimiento general para que los proveedores cumplan este requisito.

Por ejemplo, un proceso de destino puede estar usando una GPU para acelerar cálculos. Una región de memoria que mapea a memoria en la GPU puede exponerse a pares como un destino RMA o publicarse localmente como un búfer de recepción. En este caso, la aplicación se preocupa por dos dominios de memoria: sistema y memoria GPU. Las finalizaciones se escriben en la memoria del sistema.

Continuando con el ejemplo, un proceso par envía un mensaje etiquetado. Ese mensaje se empareja con el búfer de recepción ubicado en la memoria de la GPU. La NIC copia los datos de la red al búfer de recepción y escribe una entrada en la cola de finalización. Nótese que se accedió a ambos dominios de memoria como parte de esta transferencia. Los datos del mensaje se dirigieron a la memoria de la GPU, pero la finalización fue a la memoria del host. Debido a que dominios de memoria separados pueden no estar sincronizados entre sí, es posible que la CPU del host vea y procese la entrada de finalización antes de que la transferencia a la memoria de la GPU sea visible para la GPU del host o incluso para el software que se ejecuta en la GPU. Desde la perspectiva del proveedor, la visibilidad de la finalización no implica la visibilidad de los datos escritos en el dominio de memoria de la GPU.

La semántica de finalización por defecto en el destino aplicación para operaciones de mensajes es FI_DELIVERY_COMPLETE. Una implementación anticipada del proveedor en esta situación es que el software del proveedor que se ejecuta en la CPU del host intercepte la entrada de la CQ, detecte que los datos aterrizaron en memoria heterogénea y realice la sincronización o vaciado (flush) necesarios del dispositivo antes de informar la finalización a la aplicación. Esto asegura que los datos sean visibles para el software de la CPU y GPU antes de que la aplicación procese la finalización.

Además del costo del software del proveedor interceptando finalizaciones y verificando si una transferencia se dirigió a memoria heterogénea, la sincronización del dispositivo en sí misma puede afectar el rendimiento. Como resultado, las aplicaciones pueden solicitar una semántica de finalización más baja al publicar recepciones. Eso le indica al proveedor que la aplicación será responsable de manejar cualquier operación de vaciado (flush) específica del dispositivo que pueda ser necesaria. Consulte fi_msg(3) FLAGS.

Para transferencias de datos que no generan una finalización en el destino, como RMA o operaciones atómicas, es responsabilidad de la aplicación asegurar que todos los búferes de destino cumplan los requisitos de visibilidad necesarios de la aplicación. Los métodos con viñetas mencionados anteriormente para notificar al destino que los datos son visibles pueden no ser suficientes, ya que el software del proveedor en el destino podría carecer del contexto necesario para asegurar la visibilidad. Esto implica que la aplicación podría necesitar llamar directamente a las APIs de sincronización/vaciado (flush) del dispositivo.

Por ejemplo, una aplicación par podría realizar varias escrituras RMA que se dirigen a búferes de memoria de GPU. Si el proveedor descarga las operaciones RMA en la NIC, el software del proveedor en el destino no será consciente de que las operaciones RMA han ocurrido. Si el par envía un mensaje a la aplicación de destino que indica que las operaciones RMA están hechas, la aplicación debe asegurar que los datos RMA sean visibles para la CPU o GPU del host antes de ejecutar código que acceda a los datos. La finalización en el destino de haber recibido el mensaje enviado no es suficiente, incluso si se admite el orden de escritura después de envío (send-after-write).

La mayoría de las semánticas de finalización en memoria heterogénea de destino se mapean a FI_TRANSMIT_COMPLETE o FI_DELIVERY_COMPLETE. La memoria persistente (capacidad FI_PMEM), sin embargo, se usa a menudo con semánticas FI_COMMIT_COMPLETE. Los conceptos de finalización heterogénea siguen aplicándose.

Para transferencias marcadas por el iniciador con FI_COMMIT_COMPLETE, una finalización en el destino indica que los resultados son visibles y duraderos. Para transferencias dirigidas a memoria persistente, pero usando una semántica de finalización diferente en el iniciador, la visibilidad en el destino es similar a la descrita anteriormente. La durabilidad solo se asocia con transferencias marcadas con FI_COMMIT_COMPLETE.

Para transferencias dirigidas a memoria persistente que solicitan FI_DELIVERY_COMPLETE, entonces una finalización, ya sea en el iniciador o en el destino, indica que los datos son visibles. La visibilidad en el destino puede transmitirse usando uno de los mecanismos descritos anteriormente: generando una finalización en el destino, enviando un mensaje desde el iniciador, etc. De manera similar, si el iniciador solicitó FI_TRANSMIT_COMPLETE, entonces se necesitan pasos adicionales para asegurar la visibilidad en el destino. Por ejemplo, la transferencia puede generar una finalización en el destino, lo que indicaría visibilidad, pero no durabilidad. El iniciador también puede seguir la transferencia con otra operación que fuerce la visibilidad, como usar FI_FENCE en conjunto con FI_DELIVERY_COMPLETE.

NOTAS

Una cola de finalización debe estar vinculada a al menos un punto de extremo habilitado antes de que se pueda llamar a cualquier operación como fi_cq_read, fi_cq_readfrom, fi_cq_sread, fi_cq_sreadfrom, etc. en ella.

Si una cola de finalización se ha desbordado, se colocará en un estado `overrun'. Las operaciones de lectura continuarán devolviendo cualquier finalización válida y no corrupta, si la hay. Después de que se hayan recuperado todas las finalizaciones válidas, cualquier intento de leer la CQ resultará en que devuelva un evento de error FI_EOVERRUN. Las colas de finalización desbordadas se consideran fatales y no pueden usarse para informar finalizaciones adicionales una vez que ocurre el desbordamiento.

VALORES DE RETORNO

fi_cq_open / fi_cq_signal

: Devuelve 0 en caso de éxito. En caso de error, devuelve un errno de fabric negativo.

fi_cq_read / fi_cq_readfrom

: En caso de éxito, devuelve el número de finalizaciones recuperadas de la cola de finalización. En caso de error, devuelve un errno de fabric negativo, con estos dos errores identificados explícitamente: Si no hay finalizaciones disponibles para leer de la CQ, devuelve -FI_EAGAIN. Si la finalización más superior es para una transferencia fallida (una entrada de error), devuelve -FI_EAVAIL.

fi_cq_sread / fi_cq_sreadfrom

: En caso de éxito, devuelve el número de finalizaciones recuperadas de la cola de finalización. En caso de error, devuelve un errno de fabric negativo, con estos dos errores identificados explícitamente: Si expira el tiempo de espera o el hilo que llama es señalado y no hay datos disponibles para leer de la cola de finalización, devuelve -FI_EAGAIN. Si la finalización más superior es para una transferencia fallida (una entrada de error), devuelve -FI_EAVAIL.

fi_cq_readerr

: En caso de éxito, devuelve el valor positivo 1 (número de entradas de error devueltas). En caso de error, devuelve un errno de fabric negativo, con este error identificado explícitamente: Si no hay finalizaciones de error disponibles para leer de la CQ, devuelve -FI_EAGAIN.

fi_cq_strerror

: Devuelve una interpretación de cadena de caracteres del proveedor error específico devuelto con una finalización.

Los valores de errno de Fabric están definidos en rdma/fi_errno.h.
