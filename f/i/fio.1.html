FORMATO DE ARCHIVO DE

TRABAJO

Cualquier parámetro que siga a las opciones se considerará que es un archivo de trabajo, a menos que coincida con un parámetro de archivo de trabajo. Se pueden listar varios archivos de trabajo y cada uno se considerará un grupo separado. Fio detendrá la ejecución entre cada

grupo.

Fio acepta uno o más archivos de trabajo que describen lo que se supone que debe hacer. El formato del archivo de trabajo es el clásico archivo ini, donde los nombres encerrados en corchetes [] definen el nombre del trabajo. Puedes usar cualquier nombre ASCII que quieras, excepto *global*, que tiene un significado especial. Después del nombre del trabajo sigue una secuencia de cero o más parámetros, uno por línea, que definen el comportamiento del trabajo. Si el primer carácter de una línea es ';' o '#', toda la línea se descarta como un

comentario.

Una sección *global* establece valores predeterminados para los trabajos descritos en ese archivo. Un trabajo puede anular un parámetro de una sección *global*, y un archivo de trabajo puede incluso tener varias secciones *global* si así se desea. Un trabajo solo se ve afectado por una sección *global* que se encuentre por encima de

él.

La opción --cmdhelp también lista todas las opciones. Si se usa con un argumento de comando, --cmdhelp detallará el comando d

ado.

Consulta el directorio `examples/' para inspiración sobre cómo escribir archivos de trabajo. Ten en cuenta que los requisitos de copyright y licencia se aplican actualmente a los archivos de

`examples/'.

Ten en cuenta que la longitud má

xima de una línea en el archivo
de trabajo es de 8192 bytes.

Archivo/dispositivo de destino

directory=str
Antepone filename a este directorio. Se utiliza para colocar archivos en una ubicación diferente a `./'. Puede especificar una cantidad de directorios separando los nombres con un carácter ':'. Estos directorios se asignarán distribuidos equitativamente a los clones de trabajo creados por numjobs siempre que utilicen nombres de archivo generados. Si se establecen filename(s) específicos, fio utilizará el primer directorio listado, y por lo tanto coincidirá con la semántica de filename (que genera un archivo para cada clon si no se especifica, pero permite que todos los clones usen el mismo archivo si se establece).

Consulte la opción filename para obtener información sobre cómo escapar los caracteres ':' dentro de la propia ruta del directorio.

Nota: Para controlar el directorio que fio utilizará para los archivos de estado internos, use --aux-path.

filename=str
Fio normalmente genera un filename basado en el nombre del trabajo, el número de hilo y el número de archivo (ver filename_format). Si desea compartir archivos entre hilos de un trabajo o varios trabajos con rutas de archivo fijas, especifique un filename para cada uno de ellos para anular el valor predeterminado. Si el ioengine está basado en archivos, puede especificar una cantidad de archivos separando los nombres con un ':' dos puntos. Por lo tanto, si quisiera que un trabajo abriera `/dev/sda' y `/dev/sdb' como los dos archivos de trabajo, usaría `filename=/dev/sda:/dev/sdb'. Esto también significa que siempre que se especifica esta opción, se ignora nrfiles. El tamaño de los archivos regulares especificados por esta opción será size dividido por el número de archivos a menos que se especifique un tamaño explícito por filesize.

Cada dos puntos en la ruta deseada debe escaparse con un carácter '\'. Por ejemplo, si la ruta es `/dev/dsk/foo@3,0:c', entonces usaría `filename=/dev/dsk/foo@3,0\:c' y si la ruta es `F:\filename', entonces usaría `filename=F\:\filename'.

En Windows, los dispositivos de disco se acceden como `\\.\PhysicalDrive0' para el primer dispositivo, `\\.\PhysicalDrive1' para el segundo, etc. Nota: Windows y FreeBSD impiden el acceso de escritura a áreas del disco que contienen datos en uso (por ejemplo, sistemas de archivos).

Para acceso HTTP y S3, especifique una ruta de URL válida o una clave S3, respectivamente. Un nombre de archivo para S3 estilo ruta incluye un nombre de bucket (`/bucket/k/e.y') mientras que un nombre de archivo S3 estilo virtual-hosted (`/k/e.y') no lo hace porque su nombre de bucket se especifica en http_host.

El nombre de archivo `-' es un nombre reservado, que significa *stdin* o *stdout*. Cuál de los dos depende de la dirección de lectura/escritura establecida.

filename_format=str
Si se comparten varios archivos entre trabajos, generalmente es necesario que fio genere los nombres exactos que desea. Por defecto, fio nombrará un archivo basándose en la especificación de formato de archivo predeterminada de `jobname.jobnumber.filenumber'. Con esta opción, eso se puede personalizar. Fio reconocerá y reemplazará las siguientes palabras clave en esta cadena:
$jobname
El nombre del hilo o proceso de trabajo.
$clientuid
La IP del proceso fio cuando se usa el modo cliente/servidor.
$jobnum
El número incremental del hilo o proceso de trabajo.
$filenum
El número incremental del archivo para ese hilo o proceso de trabajo.

Para que los trabajos dependientes compartan un conjunto de archivos, esta opción puede configurarse para que fio genere nombres de archivo que se compartan entre ambos. Por ejemplo, si se especifica `testfiles.$filenum', el archivo número 4 para cualquier trabajo se llamará `testfiles.4'. io_submit_mode=s
tr
Esta opción controla cómo fio envía la E/S al motor de E/S. El valor predeterminado es `inline', lo que significa que los hilos de trabajo de fio envían y recogen la E/S directamente. Si se establece en `offload', los hilos de trabajo delegarán el envío de E/S a un grupo dedicado de hilos de E/S. Esto requiere cierta coordinación y por lo tanto tiene un poco de sobrecarga extra, especialmente para E/S con baja profundidad de cola donde puede aumentar las latencias. El beneficio es que fio puede gestionar las tasas de envío independientemente de las tasas de finalización del dispositivo. Esto evita un informe de latencia sesgado si la E/S se acumula endevice: side (el problema de omisión coordinada). thinkcycles=int
Detenga el trabajo durante el número especificado de ciclos después de que una E/S se haya completado antes de emitir la siguiente. Puede usarse para simular el procesamiento que está realizando una aplicación. Esto no se tiene en cuenta para el tiempo a esperar en thinktime. Puede que no tenga ningún efecto en algunas plataformas; esto se puede verificar intentando establecer una cantidad suficientemente alta de thinkcycles.
thinktime=time
Detenga el trabajo durante el período de tiempo especificado después de que una E/S se haya completado antes de emitir la siguiente. Puede usarse para simular el procesamiento que está realizando una aplicación. Cuando se omite la unidad, el valor se interpreta en microsegundos. Consulte thinktime_blocks, thinktime_iotime y thinktime_spin.
thinktime_spin=time
Solo válido si se establece thinktime: simule gastar tiempo de CPU haciendo algo con los datos recibidos, antes de recurrir a dormir durante el resto del período especificado por thinktime. Cuando se omite la unidad, el valor se interpreta en microsegundos.
thinktime_blocks=int
Solo válido si se establece thinktime: controle cuántos bloques emitir, antes de esperar thinktime microsegundos. Si no se establece, por defecto es 1, lo que hará que fio espere thinktime microsegundos después de cada bloque. Esto hace que cualquier configuración de profundidad de cola sea redundante, ya que no se pondrán más de 1 E/S en cola antes de tener que completarla y realizar nuestro thinktime. En otras palabras, esta configuración limita efectivamente la profundidad de cola si esta es mayor.
thinktime_blocks_type=str
Solo válido si se establece thinktime: controle cómo se activa thinktime_blocks. El valor predeterminado es `complete', que activa thinktime cuando fio completa thinktime_blocks bloques. Si se establece en `issue', el disparador ocurre en el lado de emisión.
thinktime_iotime=time
Solo válido si se establece thinktime: controle el intervalo de thinktime por tiempo. La pausa de thinktime se repite después de que las E/S se ejecutan durante thinktime_iotime. Por ejemplo, `--thinktime_iotime=9s --thinktime=1s' repite un ciclo de 10 segundos con E/S durante 9 segundos y pausa durante 1 segundo. Cuando se omite la unidad, thinktime_iotime se interpreta como un número de segundos. Si esta opción se usa junto con thinktime_blocks, la pausa de thinktime se repite después de thinktime_iotime o después de thinktime_blocks E/S, lo que ocurra primero.

Manejo de errores

exitall_on_error
Cuando un trabajo finaliza con error, termina los restantes. El valor predeterminado es esperar a que cada trabajo finalice.
continue_on_error=cadena
Normalmente, fio saldrá del trabajo ante el primer fallo observado. Si esta opción está configurada, fio continuará el trabajo cuando haya un 'error no fatal' (EIO o EILSEQ) hasta que se supere el tiempo de ejecución o se complete el tamaño de I/O especificado. Si se usa esta opción, se agregarán dos estadísticas más: el recuento total de errores y el primer error. El campo de error dado en las estadísticas es el primer error que se encontró durante la ejecución.

Nota: un error de escritura del dispositivo puede pasar desapercibido para fio al usar I/O en búfer, ya que la llamada al sistema `write()` (o similar) simplemente marca las páginas del kernel como sucias, a menos que se use `sync` o `direct`. Los errores de I/O del dispositivo ocurren cuando los datos sucios se escriben realmente en el disco. Si las escrituras síncronas completas no son deseables, también se pueden usar `fsync` o `fdatasync`. Esto es específico para escrituras, ya que las lecturas son siempre síncronas.

none
Salir ante cualquier error de I/O o verificación.
read
Continuar ante errores de lectura, salir ante todos los demás.
write
Continuar ante errores de escritura, salir ante todos los demás.
io
Continuar ante cualquier error de I/O, salir ante todos los demás.
verify
Continuar ante errores de verificación, salir ante todos los demás.
all
Continuar ante todos los errores.
0
Alias compatible con versiones anteriores para 'none'.
1
Alias compatible con versiones anteriores para 'all'.
ignore_error=cadena
A veces querrás ignorar algunos errores durante la prueba, en cuyo caso puedes especificar una lista de errores para cada tipo de error, en lugar de solo poder ignorar el 'error no fatal' predeterminado usando `continue_on_error`. `ignore_error=LISTA_DE_ERRORES_DE_LECTURA,LISTA_DE_ERRORES_DE_ESCRITURA,LISTA_DE_ERRORES_DE_VERIFICACION` los errores para un tipo de error dado se separan con ':'. CLIENTE /

SERVIDOR

Normalmente, fio se invoca como una aplicación independiente en la máquina donde se debe generar la carga de trabajo de E/S. Sin embargo, el backend y el frontend de fio se pueden ejecutar por separado, es decir, el servidor fio puede generar una carga de trabajo de E/S en el "Dispositivo bajo prueba" mientras es controlado por un cliente en otra

máquina.

Inicie el servidor en la máquina que tiene acceso al almacenamiento

DUT:

$ fio

--serve

donde `args' define a qué escucha fio. 4444.
