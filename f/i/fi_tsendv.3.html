DESCRIPCIÓ

N

Los mensajes etiquetados son transferencias de datos que llevan una clave o etiqueta con el búfer del mensaje. La etiqueta se utiliza en el punto de extremo de recepción para hacer coincidir el mensaje entrante con un búfer de recepción correspondiente. Las etiquetas de los mensajes coinciden cuando la etiqueta del búfer de recepción es la misma que la etiqueta del búfer de envío, con los bits ignorados enmascarados. Esto se puede expresar

como: 
send_tag & ~ignore =
= recv_tag & ~ignore
o send_tag | ignore
== recv_tag | ignore

En general, las etiquetas de los mensajes se comprueban contra los búferes de recepción en el orden en que los mensajes se han publicado en el punto de extremo. Véase la discusión sobre el ordenamiento más abajo para más

detalles.

Las funciones de envío – fi_tsend, fi_tsendv, fi_tsendmsg, fi_tinject y fi_tsenddata – se utilizan para transmitir un mensaje etiquetado desde un punto de extremo a otro. La principal diferencia entre las funciones de envío es el número y el tipo de parámetros que aceptan como entrada. De lo contrario, realizan la misma función

general.

Las funciones de recepción – fi_trecv, fi_trecvv, fi_recvmsg – publican un búfer de datos en un punto de extremo para recibir mensajes etiquetados entrantes. De manera similar a las operaciones de envío, las operaciones de recepción se ejecutan de forma asíncrona. Los usuarios no deben tocar los búferes de datos publicados hasta que la operación de recepción se haya completado. Los búferes de recepción publicados se emparejan con los mensajes de envío entrantes basándose en las etiquetas asociadas con los búferes de envío y

recepción.

Un punto de extremo debe estar habilitado antes de que una aplicación pueda publicar operaciones de envío o recepción en él. Para los puntos de extremo conectados, los búferes de recepción pueden publicarse antes de que se llame a connect o accept en el punto de extremo. Esto asegura que los búferes estén disponibles para recibir datos entrantes inmediatamente después de que se haya establecido la

conexión.

Las operaciones de mensajes completadas se informan al usuario a través de uno o más colectores de eventos asociados con el punto de extremo. Los usuarios proporcionan contextos que se asocian con cada operación y se devuelven al usuario como parte del evento de finalización. Véase fi_cq para detalles sobre los eventos de

finalización.

fi_tsen

d

configurado de otra manera, el búfer de datos pasado a fi_tsend no debe ser tocado por la aplicación hasta que la llamada a fi_tsend se complete de forma asíncrona.

fi_trecv

La llamada fi_trecv publica un búfer de datos en la cola de recepción del punto de extremo correspondiente. Las recepciones publicadas se buscan en el orden en que fueron publicadas para hacer coincidir los envíos. Se mantienen los límites de los mensajes. El orden en que se completan las recepciones depende del tipo de punto de extremo y del protocolo.

fi_trecvv

La llamada fi_trecvv añade soporte para una lista de dispersión-agrupamiento a fi_trecv. La fi_trecvv publica el conjunto de búferes de datos referenciados por el parámetro iov para recibir datos entrantes.

fi_trecvmsg

La llamada fi_trecvmsg soporta la publicación de búferes tanto en puntos de extremo conectados como sin conexión, con la capacidad de controlar la operación de recepción en cada llamada mediante el uso de flags. La función fi_trecvmsg toma un struct fi_msg_tagged como entrada.

FLAGS

Las llamadas fi_trecvmsg y fi_tsendmsg permiten al usuario especificar flags que pueden cambiar el manejo predeterminado de mensajes del punto de extremo. Los flags especificados con fi_trecvmsg / fi_tsendmsg anulan la mayoría de los flags configurados previamente con el punto de extremo, excepto donde se indique (ver fi_endpoint). La siguiente lista de flags es utilizable con fi_trecvmsg y/o fi_tsendmsg.

FI_REMOTE_CQ_DATA
Aplica a fi_tsendmsg. Indica que hay datos remotos de CQ disponibles y que deben enviarse como parte de la solicitud. Ver fi_getinfo para detalles adicionales sobre FI_REMOTE_CQ_DATA. Este flag está implícitamente establecido para fi_tsenddata y fi_tinjectdata.
FI_COMPLETION
Indica que debe generarse una entrada de finalización para la operación especificada. El punto de extremo debe estar vinculado a una cola de finalización con FI_SELECTIVE_COMPLETION que corresponda a la operación especificada, o este flag será ignorado.
FI_MORE
Indica que el usuario tiene solicitudes adicionales que serán publicadas inmediatamente después de que la llamada actual retorne. El uso de este flag puede mejorar el rendimiento al permitir al proveedor optimizar su acceso al hardware de la red.
FI_INJECT
Aplica a fi_tsendmsg. Indica que el búfer de datos de salida debe ser devuelto al usuario inmediatamente después de que la llamada de envío retorne, incluso si la operación se maneja de forma asíncrona. Esto puede requerir que la implementación del proveedor subyacente copie los datos en un búfer local y transfiera desde ese búfer. Este flag solo puede usarse con mensajes más pequeños que inject_size.
FI_MULTI_RECV
Aplica a operaciones de recepción etiquetada publicadas cuando la capacidad FI_TAGGED_MULTI_RECV está habilitada. Este flag permite al usuario publicar un solo búfer de recepción etiquetada que recibirá múltiples mensajes entrantes. Los mensajes recibidos serán empaquetados en el búfer de recepción hasta que el búfer se haya consumido. El uso de este flag puede causar que una sola operación de recepción publicada genere múltiples eventos a medida que los mensajes se colocan en el búfer. La colocación de los datos recibidos en el búfer puede estar sujeta a restricciones de alineación específicas del proveedor.

El búfer será liberado por el proveedor cuando el espacio de búfer disponible caiga por debajo del mínimo especificado (ver FI_OPT_MIN_MULTI_RECV). Tenga en cuenta que siempre se generará una entrada en la cola de finalización de recepción asociada cuando el búfer se haya consumido, incluso si otras finalizaciones de recepción han sido suprimidas (es decir, el contexto Rx ha sido configurado para FI_SELECTIVE_COMPLETION). Ver el flag de finalización FI_MULTI_RECV en fi_cq(3).

FI_INJECT_COMPLETE
Aplica a fi_tsendmsg. Indica que debe generarse una finalización cuando el/los búfer(es) de origen puedan ser reutilizados.
FI_TRANSMIT_COMPLETE
Aplica a fi_tsendmsg. Indica que no debe generarse una finalización hasta que la operación haya sido transmitida exitosamente y ya no esté siendo rastreada por el proveedor.
FI_MATCH_COMPLETE
Aplica a fi_tsendmsg. Indica que debe generarse una finalización solo después de que el mensaje haya sido emparejado con un búfer etiquetado o haya sido descartado por la aplicación de destino.
FI_FENCE
Aplica a transmisiones. Indica que la operación solicitada, también conocida como la operación cercada, y cualquier operación publicada después de la operación cercada serán diferidas hasta que todas las operaciones previas dirigidas al mismo punto de extremo par hayan completado. Las operaciones publicadas después del cercado verán y/o reemplazarán los resultados de cualquier operación iniciada antes de la operación cercada.

El orden de las operaciones desde la publicación de la operación cercada (inclusive) hasta la publicación de una operación cercada posterior (exclusivo) está controlado por la semántica de orden del punto de extremo.

FI_AUTH_KEY
Solo válido con dominios configurados con FI_AV_AUTH_KEY y puntos de extremo sin conexión configurados con FI_DIRECTED_RECV o FI_TAGGED_DIRECTED_RECV. Cuando se usa con fi_trecvmsg, este flag denota que src_addr es una clave de autorización fi_addr_t en lugar de un fi_addr_t de punto de extremo.

Los siguientes flags pueden usarse con fi_trecvmsg.

FI_PEEK
El flag peek puede usarse para ver si un mensaje especificado ha llegado. Una solicitud de peek es a menudo útil en puntos de extremo que tienen habilitado el buffering asignado por el proveedor. A diferencia de las operaciones de recepción estándar, una operación de recepción con el flag FI_PEEK establecido no permanece en cola con el proveedor después de que el peek complete exitosamente. La operación de peek opera de forma asíncrona, y los resultados de la operación de peek están disponibles en la cola de finalización asociada con el punto de extremo. Si no se encuentra ningún mensaje que coincida con las etiquetas especificadas en la solicitud de peek, entonces una entrada de error de cola de finalización con el campo err establecido a FI_ENOMSG estará disponible.

Si una solicitud de peek localiza un mensaje coincidente, la operación completará exitosamente. Los datos de finalización retornados indicarán los metadatos asociados con el mensaje, como la longitud del mensaje, los flags de finalización, los datos de CQ disponibles, la etiqueta y la dirección de origen. Los datos disponibles están sujetos al formato de la entrada de finalización (por ejemplo, struct fi_cq_tagged_entry).

FI_CLAIM
Si este flag se usa en conjunto con FI_PEEK, indica que si la solicitud de peek completa exitosamente – indicando que se localizó un mensaje coincidente – el mensaje es reclamado por el llamador. Los mensajes reclamados solo pueden ser recuperados usando una operación de recepción posterior y emparejada con el flag FI_CLAIM establecido. Una operación de recepción con el flag FI_CLAIM establecido, pero FI_PEEK no establecido, se usa para recuperar un mensaje previamente reclamado.

Para usar el flag FI_CLAIM, una aplicación debe proporcionar una estructura struct fi_context como el contexto para la operación de recepción. La misma estructura fi_context usada para una operación FI_PEEK + FI_CLAIM debe ser usada por la solicitud FI_CLAIM emparejada.

FI_DISCARD
Este flag puede usarse en conjunto con FI_PEEK o FI_CLAIM. Si este flag se usa en conjunto con FI_PEEK, indica que si la solicitud de peek completa exitosamente – indicando que se localizó un mensaje coincidente – el mensaje es descartado por el proveedor, ya que los datos no son necesarios por la aplicación. Este flag también puede usarse en conjunto con FI_CLAIM para descartar un mensaje previamente reclamado usando una solicitud FI_PEEK + FI_CLAIM.

Si este flag está establecido, el/los búfer(es) de entrada y los parámetros de longitud son ignorados.

VALOR RETORNADO

Las llamadas de envío y recepción etiquetadas retornan 0 en caso de éxito. En caso de error, se retorna un valor negativo correspondiente al fabric errno Los valores de fabric errno están definidos en fi_errno.h.

ERRORES

-FI_EAGAIN
Ver fi_msg(3) para una descripción detallada del manejo de FI_EAGAIN.
-FI_EINVAL
Indica que el usuario proporcionó un argumento inválido.
-FI_EOTHER
Indica que ocurrió un error no especificado.
