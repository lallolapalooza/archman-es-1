NOMBRE

fi_domain - Abrir un dominio de acceso a la red

SINOPSIS

#include <rdma/fabric.h>
#include <rdma/fi_domain.h>
int fi_domain(struct fid_fabric *fabric, struct fi_info *info,
    struct fid_domain **domain, void *context);
int fi_domain2(struct fid_fabric *fabric, struct fi_info *info,
    struct fid_domain **domain, uint64_t flags, void *context);
int fi_close(struct fid *domain);
int fi_domain_bind(struct fid_domain *domain, struct fid *eq,
    uint64_t flags);
int fi_open_ops(struct fid *domain, const char *name, uint64_t flags,
    void **ops, void *context);
int fi_set_ops(struct fid *domain, const char *name, uint64_t flags,
    void *ops, void *context);

ARGUMENTOS

fabric
Dominio de red.
info
Información de la red, incluyendo capacidades y atributos del dominio. La estructura fi_info debe haber sido obtenida usando fi_getinfo() o fi_dupinfo().
domain
Un dominio de acceso abierto.
context
Contexto especificado por el usuario asociado al dominio. Este contexto se devuelve como parte de cualquier evento asíncrono asociado con el dominio.
eq
Cola de eventos para operaciones asíncronas iniciadas en el dominio.
name
Nombre asociado a una interfaz.
ops
Operaciones de la interfaz de red.

DESCRIPCIÓN

Un dominio de acceso típicamente se refiere a una NIC física o virtual o a un puerto de hardware; sin embargo, un dominio puede abarcar múltiples componentes de hardware para fines de fail-over o striping de datos. Un dominio define el límite para asociar diferentes recursos. Los recursos de red que pertenecen al mismo dominio pueden compartir recursos.

fi_domain

Abre un dominio de acceso a la red, también conocido como dominio de recursos. Los dominios de red se identifican por un nombre. Las propiedades del dominio abierto se especifican usando el parámetro info.

fi_domain2

Similar a fi_domain, pero acepta un parámetro adicional flags. Se usa principalmente para abrir un dominio peer. Ver fi_peer(3).

fi_open_ops

fi_open_ops se utiliza para abrir interfaces específicas del proveedor. Las interfaces del proveedor pueden ser usadas para acceder a recursos de bajo nivel y operaciones que son específicas del dominio de recursos abierto. Los detalles de las interfaces del dominio están fuera del alcance de esta documentación.

fi_set_ops

fi_set_ops asigna callbacks que un proveedor debe invocar en lugar de realizar ciertas tareas. Esto permite a los usuarios modificar o controlar el comportamiento predeterminado de un proveedor. Conceptualmente, permite al usuario enganchar funciones específicas utilizadas por un proveedor y reemplazarlas con las suyas.

Las operaciones que se modifican se identifican usando una cadena de caracteres conocida, pasada como parámetro name. El formato del parámetro ops depende del valor de name. El parámetro ops hará referencia a una estructura que contiene los callbacks y otros campos necesarios para que el proveedor invoque las funciones del usuario.

Si un proveedor acepta la anulación, devolverá FI_SUCCESS. Si la anulación es desconocida o no es compatible, el proveedor devolverá -FI_ENOSYS. Las anulaciones deben establecerse antes de asignar recursos en el dominio.

Las siguientes operaciones de fi_set_ops y sus estructuras de callback correspondientes están definidas.

FI_SET_OPS_HMEM_OVERRIDE – Anulaciones de Memoria Heterogénea

La anulación HMEM permite a los usuarios anular las operaciones relacionadas con HMEM que un proveedor pueda realizar. Actualmente, el alcance de la anulación HMEM es permitir a un usuario definir las funciones de movimiento de memoria que un proveedor debe usar al acceder a un buffer de usuario. Las funciones de movimiento de memoria definidas por el usuario deben tener en cuenta todos los diferentes tipos de iface HMEM que un proveedor pueda encontrar.

Todos los objetos asignados contra un dominio heredarán esta anulación.

A continuación se muestra el nombre de la operación de anulación HMEM y su estructura.

#define FI_SET_OPS_HMEM_OVERRIDE "hmem_override_ops"
struct fi_hmem_override_ops {
    size_t  size;
    ssize_t (*copy_from_hmem_iov)(void *dest, size_t size,
        enum fi_hmem_iface iface, uint64_t device, const struct iovec *hmem_iov,
        size_t hmem_iov_count, uint64_t hmem_iov_offset);
    ssize_t (*copy_to_hmem_iov)(enum fi_hmem_iface iface, uint64_t device,
    const struct iovec *hmem_iov, size_t hmem_iov_count,
        uint64_t hmem_iov_offset, const void *src, size_t size);
};

Todos los campos de la estructura fi_hmem_override_ops deben establecerse (no nulos) a un valor válido.

size
Esto debe establecerse en sizeof(struct fi_hmem_override_ops). El campo size se utiliza para fines de compatibilidad hacia adelante y hacia atrás.
copy_from_hmem_iov
Copia datos del dispositivo/hmem a la memoria del host. Esta función debe devolver un fi_errno negativo en caso de error, o el número de bytes copiados en caso de éxito.
copy_to_hmem_iov
Copia datos de la memoria del host al dispositivo/hmem. Esta función debe devolver un fi_errno negativo en caso de error, o el número de bytes copiados en caso de éxito.

fi_domain_bind

Asocia una cola de eventos con el dominio. Una cola de eventos vinculada a un dominio será la EQ predeterminada asociada con eventos de control asíncronos que ocurran en el dominio o en endpoints activos asignados en un dominio. Esto incluye eventos CM. Los endpoints pueden dirigir sus eventos de control a EQs alternativos vinculándose directamente con la EQ.

Obsoleto: Vincular una cola de eventos a un dominio con la bandera FI_REG_MR indica que el proveedor debe realizar todas las operaciones de registro de memoria de forma asíncrona, con la finalización informada a través de la cola de eventos. Si no se vincula una cola de eventos al dominio con la bandera FI_REG_MR, las solicitudes de registro de memoria se completan de forma síncrona.

fi_close

La llamada fi_close se utiliza para liberar todos los recursos asociados con un dominio o interfaz. Todos los objetos asociados con el dominio abierto deben liberarse antes de llamar a fi_close, de lo contrario, la llamada devolverá -FI_EBUSY.

Soporte de multihilo

(threading)

El modelo de hilos especifica el nivel de serialización requerido de una aplicación al usar las interfaces de transferencia de datos de libfabric. Las interfaces de control siempre se consideran seguras para hilos a menos que el modelo de progreso de control sea FI_PROGRESS_CONTROL_UNIFIED. Una interfaz de control segura para hilos permite que múltiples hilos hagan progreso en la interfaz de control y (dependiendo del modelo de hilos seleccionado) uno o más hilos hagan progreso en las interfaces de datos al mismo tiempo. Las aplicaciones que pueden garantizar la serialización en su acceso a los recursos e interfaces asignados por el proveedor permiten a un proveedor eliminar bloqueos de nivel

inferior.
FI_THREAD_COMPLET
ION
El modelo de hilos de finalización es el más adecuado para aplicaciones multihilo que usan endpoints escalables y desean operación sin bloqueos. Las ap
licaciones deben serializar el acceso a todos los objetos que están asociados por un mecanismo de finalización común (por ejemplo, contextos de transmi
sión y recepción vinculados al mismo CQ o contador). Se recomienda que los proveedores que soportan endpoints escalables soporten este modelo de hilos.

Las aplicaciones que deseen aprovechar FI_THREAD_COMPLETION deben dedicar contextos de transmisión, contextos de recepción, colas de finalización y contadores a hilos

individuales.
FI_THREAD_DOM
AIN
El modelo de hilos de dominio es el más adecuado para aplicaciones de un solo hilo y aplicaciones multihilo que usan endpoints estándar y desean operación sin bloqueos. Las aplicaciones deben serializar el acceso a todos los objetos bajo el mismo dominio. Esto incluye endpoints, contextos de transmisión y recepción, colas de finalización y contadores, y regiones de memoria
registradas.
FI_THREAD_ENDPOINT
(obsoleto)
El modelo de hilos de endpoint es similar a FI_THREAD_FID, pero con la restricción adicional de que se requiere serialización al acceder al mismo endpoint, incluso si se usan múltiples contextos de transmisión y
recepción.
FI_THREAD_FID
(obsoleto)
Un modelo de serialización de descriptor de fabric (FID) requiere que las aplicaciones serialicen el acceso a recursos individuales de fabric asociados con operaciones de transferencia de datos y finalizaciones. Para el acceso a endpoints, la serialización solo se requiere al acceder al mismo flujo de datos del endpoint. Múltiples hilos pueden iniciar transferencias en diferentes contextos de transmisión o el mismo endpoint sin serializar, y no se requiere serialización entre el envío de solicitudes de transmisión de datos y las operaciones de recepción de
datos.
FI_THREAD_SA
FE
Un modelo de serialización seguro para hilos permite que una aplicación multihilo acceda a cualquier recurso asignado a través de cualquier interfaz sin restricciones. Todos los proveedores deben soportar
FI_THREAD_SAFE.

Modelos de progreso

(progress)

El progreso es la capacidad de la implementación subyacente para completar el procesamiento de una solicitud asincrónica. En muchos casos, el procesamiento de una solicitud asincrónica requiere el uso del procesador del host. Por ejemplo, un mensaje recibido puede necesitar ser emparejado con el búfer correcto, o una solicitud agotada por tiempo puede necesitar ser retransmitida. Por razones de rendimiento, puede ser indeseable que el proveedor asigne un hilo para este propósito, lo que competiría con los hilos de la

aplicación.

El progreso de control indica el método que usa el proveedor para avanzar en operaciones de control asincrónicas. Las operaciones de control son funciones que no involucran directamente la transferencia de datos de la aplicación entre endpoints. Incluyen rutinas de vector de direcciones, registro de memoria y gestión de

conexiones.

El progreso de datos indica el método que usa el proveedor para avanzar en operaciones de transferencia de datos. Esto incluye cola de mensajes, RMA, mensajería etiquetada y operaciones atómicas, junto con su procesamiento de

finalización.

El campo de progreso define el comportamiento tanto de las operaciones de control como de las de datos. Para aplicaciones que requieren portabilidad de compilación entre las series de libfabric versión 1 y versión 2, el campo de progreso puede referenciarse como

data_progress.

El progreso frecuentemente requiere que se tomen acciones tanto en el lado de transmisión como en el de recepción de una operación. Esto es a menudo un requisito para transferencias confiables, como resultado del procesamiento de reintentos y

confirmaciones.

Para equilibrar entre rendimiento y facilidad de uso, se definen los siguientes modelos de

progreso.
FI_PROGRESS_A
UTO
Este modelo de progreso indica que el proveedor hará progreso en una operación asincrónica sin mayor intervención de la aplicació
n. Cuando FI_PROGRESS_AUTO se proporciona como salida a fi_getinfo en ausencia de cualquier sugerencia de progreso, a menudo ind
ica que la funcionalidad deseada está implementada por el hardware del proveedor o es un servicio estándar del sistema operativo.

Se recomienda que los proveedores soporten FI_PROGRESS_AUTO. Sin embargo, si un proveedor no soporta nativamente progreso automático, forzar el uso de FI_PROGRESS_AUTO puede resultar en que se asignen hilos debajo de las interfaces de

fabric.

Tenga en cuenta que las versiones anteriores de la biblioteca requerían que los proveedores soportaran FI_PROGRESS_AUTO. Sin embargo, en algunos casos los hilos de progreso no pueden bloquearse cuando la comunicación está inactiva, lo que resulta en hilos girando en funciones de progreso. Como resultado, esos proveedores solo soportaban FI_PROGRESS_MANUAL

.
FI_PROGRESS_MAN
UAL
Este modelo de progreso indica que el proveedor requiere el uso de un hilo de la aplicación para completar una solicitud asincrónica. Cuando se establece progreso manual, e
l proveedor intentará avanzar una operación asincrónica cuando la aplicación intente esperar o leer una cola de eventos, cola de finalización o contador donde se reportará l
a operación completada. El progreso también ocurre cuando la aplicación procesa un conjunto de sondeo o espera que haya sido asociado con la cola de eventos o finalización.

Solo las operaciones de espera definidas por la interfaz de fabric resultarán en que una operación avance. Las funciones de espera del sistema operativo o externas, como select, poll o rutinas pthread, no pueden

hacerlo.

Los requisitos de progreso manual no solo se aplican a endpoints que inician operaciones de transmisión, sino también a endpoints que pueden ser el destino de tales operaciones. Esto es cierto incluso si el endpoint destino no generará eventos de finalización para las operaciones. Por ejemplo, un endpoint que actúa puramente como destino de operaciones RMA o atómicas que usa progreso manual puede aún necesitar asistencia de la aplicación para procesar operaciones

recibidas.
FI_PROGRESS_CONTROL_UNIF
IED
Este modelo de progreso indica que el usuario sincronizará el progreso de las operaciones de datos y control por sí mismo (es decir, esto permite que la interfaz de control NO sea segura para hilos). Implica progreso manual, y cuando se combina con threading=FI_THREAD_DOMAIN/FI_THREAD_COMPLETION permite a Libfabric eliminar todo el bloqueo en la ruta crítica de progreso de
datos.
FI_PROGRESS_UNS
PEC

finido ningún modelo de progreso.

Gestión de recursos

(resource_mgmt)

La gestión de recursos (RM) es soporte de proveedor y protocolo para proteger contra el desbordamiento de recursos locales y remotos. Esto incluye contextos de transmisión y recepción locales y remotos, colas de finalización, y búferes de datos de origen y

destino.

Cuando está habilitada, las aplicaciones reciben cierto nivel de protección contra el desbordamiento de colas del proveedor y búferes de datos locales y remotos. Tal soporte puede estar incorporado directamente en el hardware y/o protocolo de red, pero también puede requerir que se habiliten verificaciones en el software del proveedor. Al deshabilitar la gestión de recursos, la aplicación asume toda la responsabilidad de prevenir el desbordamiento de colas y búferes, pero hacerlo puede permitir a un proveedor eliminar llamadas de sincronización internas, como variables atómicas o

bloqueos.

Debe notarse que incluso si la gestión de recursos está deshabilitada, la implementación del proveedor y el protocolo aún pueden proporcionar algún nivel de protección contra desbordamientos. Sin embargo, dicha protección no está garantizada. Se definen los siguientes valores para la gestión de

recursos.
FI_RM_DISABL
ED
El proveedor es libre de seleccionar una implementación y protocolo que no proteja contra el desbordamiento de recursos. La aplicación es responsable de la protección de
recursos.
FI_RM_ENABL
ED
La gestión de recursos está habilitada para este dominio del
proveedor.
FI_RM_UNSP
EC
Este valor indica que no se ha definido ningún m
odelo de gestión de recursos. Puede usarse en su
gerencias de entrada para la llamada fi_getinfo.

Ctx
Se refiere a los contextos de transmisión/recepción cuando se envía una operación de transferencia de datos. Cuando RM está habilitado, el intento de enviar una solicitud fallará si el contexto está lleno. Si RM está deshabilitado, ocurrirá un error no definido (específico del proveedor). CQ
Se refiere a la cola de completado asociada con el contexto Tx o Rx cuando una operación local se completa. Cuando RM está deshabilitado, las aplicaciones deben asegurarse de que las colas de completado no se desborden. Cuando ocurre un desbordamiento, ocurrirá un error no definido pero fatal que afectará a todos los puntos finales asociados con la CQ. Los desbordamientos se pueden evitar dimensionando las CQ adecuadamente o retrasando la publicación de una operación de transferencia de datos a menos que haya espacio en la CQ para almacenar su completado. Cuando RM está habilitado, los proveedores pueden usar diferentes mecanismos para prevenir desbordamientos de la CQ. Esto incluye fallar (devolver -FI_EAGAIN) la publicación de operaciones que podrían resultar en desbordamientos de la CQ, o reintentar internamente las solicitudes (lo cual será oculto a la aplicación). Véanse las notas al final de esta sección con respecto a las restricciones de gestión de recursos de la
CQ.
EP de destino / Sin búfer
Rx
EP de destino se refiere a los recursos asociados con el punto final que es el destino de una operación de transmisión. Esto incluye la cola de recepción del punto final de destino, los búferes de recepción publicados (sin búferes Rx), la cola de completado del lado de recepción y otras colas de procesamiento de paquetes relacionadas. El comportamiento definido es el que ve el iniciador de una solicitud. Para los puntos finales FI_EP_DGRAM, si las colas del EP de destino no pueden aceptar mensajes entrantes, los mensajes recibidos serán descartados. Para los puntos finales confiables, si RM está deshabilitado, la operación de transmisión se completará con error. Un proveedor puede optar por devolver un completado de error con el código de error FI_ENORX para esa operación de transmisión para que pueda ser reintentada. Si RM está habilitado, el proveedor reintentará internamente la
operación.
Desbordamiento de búfer
Rx
Esto se refiere a los búferes publicados para recibir mensajes etiquetados o no etiquetados entrantes, con el comportamiento definido desde el punto de vista del emisor. El comportamiento para manejar los mensajes recibidos que son más grandes que los búferes proporcionados por la aplicación es específico del proveedor. Los proveedores pueden truncar el mensaje y reportar un completado exitoso, o fallar la operación. Para los puntos finales de datagrama, los envíos fallidos resultarán en que el mensaje sea descartado. Para los puntos finales confiables, las operaciones de envío pueden completarse exitosamente, pero ser truncadas en el lado de recepción. Esto puede ocurrir cuando el lado de destino almacena en búfer los datos recibidos hasta que un búfer de aplicación esté disponible. El estado de completado también puede depender del modelo de completado seleccionado por la aplicación (por ejemplo, FI_DELIVERY_COMPLETE versus FI_TRANSMIT_COMPLETE)
.

RMA

A diferencia de las operaciones de envío, las operaciones RMA que intentan acceder a una dirección de memoria que no está registrada para tales operaciones, o que intentan acceder fuera de la región de memoria de destino, fallarán, resultando en un error de

Punto final inaccesible es un escenario específico de conexión sin conexión donde se emiten operaciones de transmisión a puntos finales de destino inaccesibles. Tales e
scenarios incluyen no-ruta-al-host o tarjeta de red de destino caída. Para los puntos finales FI_EP_DGRAM, las operaciones de transmisión dirigidas a un punto final ina
ccesible tendrán la operación descartada. Para FI_EP_RDM, las operaciones de destino dirigidas a un punto final inaccesible resultarán en un error de transmisión.

Cuando ocurre un error de gestión de recursos en un punto final conectado, el punto final transicionará a un estado deshabilitado y la conexión se desmantelará. Un punto final deshabilitado descartará cualquier operación en cola o en

vuelo.

El comportamiento de los errores de gestión de recursos en los puntos finales sin conexión depende del tipo de error. Si RM está deshabilitado y ocurre uno de los siguientes errores, el punto final será deshabilitado: Tx Ctx, Rx Ctx, Tx CQ o Rx CQ. Para otros errores (EP de destino, sin búfer Rx, etc.), la operación puede fallar, pero el punto final permanecerá habilitado. Un punto final deshabilitado descartará o fallará cualquier operación en cola o en vuelo. Además, un punto final deshabilitado debe ser rehabilitado antes de que acepte nuevas operaciones de transferencia de

datos.

Hay una restricción notable en las protecciones ofrecidas por la gestión de recursos. Esto ocurre cuando la gestión de recursos está habilitada en un punto final que ha sido vinculado a cola(s) de completado usando el indicador FI_SELECTIVE_COMPLETION. Las operaciones publicadas en tal punto final pueden especificar que un completado exitoso no debe gen

erar una entrada en la cola de completado correspondiente. (Es decir, la operación deja el indicador FI_COMPLETION sin establecer). En tales situaciones, el proveedor no está obligado a reservar una entrada en la cola de completado para manejar el caso en que la operación falle y sí genere una entrada de CQ, lo cual requeriría efectivamente rastrea
r la operación hasta su completado. Las aplicaciones preocupadas por evitar desbordamientos de la CQ en la ocurrencia de errores deben asegurar que haya espacio suficiente en la CQ para reportar operaciones fallidas. Esto generalmente se puede lograr dimensionando la CQ al menos del mismo tamaño que la(s) cola(s) del punto final vinculada(s) a ella.

NOTA

S

Los usuarios deben llamar a fi_close para liberar todos los recursos asignados al dominio de

fabric.

Los siguientes recursos de fabric están asociados con dominios: puntos de extremo activos, regiones de memoria, colas de eventos de finalización y vectores de

dirección.

Los atributos del dominio reflejan las limitaciones y capacidades del hardware y/o proveedor de software subyacente. No reflejan las limitaciones del sistema, como el núme

ro de páginas físicas que una aplicación puede fijar o el número de descriptores de archivo que la aplicación puede abrir. Como resultado, los máximos reportados pueden no
ser alcanzables, incluso en sistemas con poca carga, a menos que un administrador configure los recursos del sistema adecuadamente para el/los proveedor(es) instalado(s).
