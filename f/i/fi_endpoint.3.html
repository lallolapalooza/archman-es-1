DESCRIPCIÓN

Los puntos de extremo son portales de comunicación a nivel de transporte. Hay dos tipos de puntos de extremo: activos y pasivos. Los puntos de extremo pasivos pertenecen a un dominio de fabric y se usan con mayor frecuencia para escuchar solicitudes de conexión entrantes. Sin embargo, un punto de extremo pasivo puede usarse para reservar una dirección de fabric que pueda concederse a un punto de extremo activo. Los puntos de extremo activos pertenecen a dominios de acceso y pueden realizar transferencias de datos.

Los puntos de extremo activos pueden ser orientados a conexión o sin conexión, y pueden proporcionar fiabilidad de datos. Las interfaces de transferencia de datos – mensajes (fi_msg), mensajes etiquetados (fi_tagged), RMA (fi_rma) y operaciones atómicas (fi_atomic) – están asociadas con puntos de extremo activos. En configuraciones básicas, un punto de extremo activo tiene colas de transmisión y recepción. En general, las operaciones que generan tráfico en el fabric se publican en la cola de transmisión. Esto incluye todas las operaciones RMA y atómicas, junto con los mensajes enviados y los mensajes etiquetados enviados. Las operaciones que publican búferes para recibir datos entrantes se envían a la cola de recepción.

Los puntos de extremo activos se crean en estado deshabilitado. Deben transicionar a un estado habilitado antes de aceptar operaciones de transferencia de datos, incluida la publicación de búferes de recepción. La llamada fi_enable se usa para transicionar un punto de extremo activo a un estado habilitado. Las llamadas fi_connect y fi_accept también transicionarán un punto de extremo al estado habilitado, si aún no está activo.

Para transicionar un punto de extremo a un estado habilitado, debe enlazarse con uno o más recursos de fabric. Un punto de extremo que genere finalizaciones asíncronas, ya sea a través de operaciones de transferencia de datos o eventos de establecimiento de comunicación, debe enlazarse con las colas de finalización o colas de eventos apropiadas, respectivamente, antes de ser habilitado. Además, los puntos de extremo que usan progreso manual deben asociarse con colas de finalización o eventos relevantes para impulsar el progreso. Para los puntos de extremo que solo se usan como destino de operaciones RMA o atómicas, esto significa enlazar el punto de extremo con una cola de finalización asociada con el procesamiento de recepción. Los puntos de extremo sin conexión deben enlazarse con un vector de direcciones.

Una vez que un punto de extremo ha sido activado, puede asociarse con un vector de direcciones. Se le pueden publicar búferes de recepción y se pueden realizar llamadas a rutinas de establecimiento de conexión. Los puntos de extremo sin conexión también pueden realizar transferencias de datos.

El comportamiento de un punto de extremo puede ajustarse estableciendo sus opciones de control de datos y protocolo. Esto permite que el proveedor subyacente redirija las llamadas de funciones a implementaciones optimizadas para satisfacer el comportamiento deseado de la aplicación.

Si un punto de extremo experimenta un error crítico, transicionará de vuelta a un estado deshabilitado. Los errores críticos se reportan a través de la cola de eventos asociada con el EP. En ciertos casos, un punto de extremo deshabilitado puede volver a habilitarse. La capacidad de transicionar de vuelta a un estado habilitado es específica del proveedor y depende del tipo de error que experimentó el punto de extremo.n un punto de extremo se desactiva como resultado de un error crítico, todas las operaciones pendientes se

descartan.

fi_ep_bind se utiliza para asociar un punto de extremo con otros recursos asignados, como colas de finalización, contadores, vectores de dirección, colas de eventos, contextos compartidos y regiones de memoria. El tipo de objetos que deben vincularse con un punto de extremo depende del tipo de punto de extremo y su

configuración.

Los puntos de extremo pasivos deben vincularse con una EQ que admita eventos de gestión de conexiones. Los puntos de extremo sin conexión deben vincularse a un único vector de dirección. Si un punto de extremo está utilizando un contexto de transmisión y/o recepción compartido, los contextos compartidos deben vincularse al punto de extremo. Las CQ, los contadores, los AV y los contextos compartidos deben vincularse a los puntos de extremo antes de que se habiliten, ya sea de forma explícita o

implícita.

Un punto de extremo debe vincularse con CQ capaces de informar de las finalizaciones de cualquier operación asíncrona iniciada en el punto de extremo. Por ejemplo, si el punto de extremo admite cualquier transferencia de datos saliente (envíos, RMA, operaciones atómicas, etc.), entonces debe vincularse a una cola de finalización que pueda informar de las finalizaciones de transmisión. Esto es cierto incluso si el punto de extremo está configurado para suprimir las finalizaciones exitosas, de modo que las operaciones que finalizan con error puedan informarse al

usuario.

Tamaño Máximo de Ordenación RMA

El tamaño máximo ordenado especifica el orden de entrega de los datos de transporte en la memoria de destino para las operaciones RMA y atómicas. El orden de los datos es independiente, pero depende del orden de los mensajes (definido más abajo). El orden de los datos no está especificado donde el orden de los mensajes no está definido.

El orden de los datos se refiere al acceso a la misma memoria de destino por operaciones posteriores. Cuando operaciones RMA de lectura o escritura consecutivas acceden a la misma ubicación de memoria registrada, el orden de los datos indica si la segunda operación lee o escribe en la memoria de destino después de que la primera operación haya completado. Por ejemplo, ¿una lectura RMA que sigue a una escritura RMA leerá los datos que fueron escritos? De manera similar, ¿una escritura RMA que sigue a una lectura RMA actualizará el búfer de destino después de que la lectura haya transferido los datos originales? El orden de los datos responde a estas preguntas, incluso en presencia de errores, como la necesidad de reenviar datos debido a tráfico de red perdido o corrupto.

La ordenación RMA se aplica entre dos operaciones, y no dentro de una sola transferencia de datos. Por lo tanto, la ordenación se define por ubicación de memoria direccionable por byte. Es decir, la ordenación especifica si la ubicación X es accedida por la segunda operación después de la primera operación. No se implica nada sobre la finalización de la primera operación antes de que la segunda operación sea iniciada. Por ejemplo, si la primera operación actualiza las ubicaciones X e Y, pero la segunda operación solo accede a la ubicación X, no hay garantías definidas con respecto a la ubicación Y y la segunda operación.

Para soportar transferencias de datos grandes que se dividen en múltiples paquetes y se envían usando múltiples rutas a través del fabric, el orden de los datos puede estar limitado a transferencias de un tamaño específico o menor. Los proveedores especifican cuándo se mantiene el orden de los datos a través de los siguientes valores. Nótese que incluso si el orden de los datos no se mantiene, el orden de los mensajes puede mantenerse.

mem_tag_format - Formato de Etiqueta de Memoria

El campo de formato de etiqueta de memoria se usa para transmitir información sobre el uso de los parámetros de etiqueta e ignorar en las llamadas a la API fi_tagged, así como los criterios de coincidencia. Esta información es usada por el proveedor para optimizar el soporte de coincidencia de etiquetas, incluyendo la alineación con protocolos de red. Se definen los siguientes formatos de etiqueta:

FI_TAG_BITS
Si se especifica en la entrada a fi_getinfo, esto indica que las etiquetas contienen hasta 64 bits de datos, y el receptor debe aplicar ignore_bits a las etiquetas al hacer coincidir búferes de recepción con envíos. La salida de fi_getinfo establecerá 0 o más bits superiores de mem_tag_format a 0 para indicar aquellos bits de etiqueta que son ignorados o reservados por el proveedor. Las aplicaciones deben verificar el número de bits superiores que son 0 y establecerlos a 0 en todos los bits de etiqueta e ignorar.

El valor de FI_TAG_BITS es 0, haciendo que este sea el comportamiento por defecto si las sugerencias quedan sin inicializar después de ser asignadas por fi_allocinfo(). Este formato proporciona la mayor flexibilidad a las aplicaciones, pero limita las opciones de optimización del proveedor. FI_TAG_BITS se alinea con el comportamiento definido para las versiones 1.x de libfabric.

FI_TAG_MPI
FI_TAG_MPI es un uso restringido de FI_TAG_BITS. Cuando se selecciona, las aplicaciones tratan la etiqueta como campos de datos, en lugar de bits, con la capacidad de comodín para cada campo. El formato de etiqueta MPI específicamente apunta a implementaciones y aplicaciones basadas en MPI. Una etiqueta con formato MPI consiste en 2 campos: una etiqueta de mensaje y un identificador de carga útil. La etiqueta de mensaje es una etiqueta de 32 bits buscable. La coincidencia en una etiqueta de mensaje requiere buscar a través de una lista de búferes publicados en el receptor, a lo que nos referimos como una etiqueta buscable. La etiqueta entera en mensajes punto a punto de MPI puede mapearse directamente al campo de etiqueta de mensaje de libfabric.

El segundo campo es un identificador que corresponde a la operación o datos que se llevan en la carga útil del mensaje. Por ejemplo, este campo puede usarse para identificar el tipo de operación colectiva asociada con una carga útil de mensaje. Nótese que solo se definen el tamaño y comportamiento para los formatos de etiqueta MPI. El uso descrito de los campos son solo sugerencias.

Las aplicaciones que usan el formato MPI deben inicializar sus etiquetas usando la función fi_tag_mpi(). Los bits de ignorar deben especificarse como FI_MPI_IGNORE_TAG, FI_MPI_PAYLOAD, o su OR bit a bit.

FI_TAG_CCL
El formato FI_TAG_CCL restringe aún más el formato FI_TAG_MPI. Cuando se usa, solo un campo de etiqueta puede ser establecido, el cual debe coincidir exactamente en el destino. El campo no puede ser comodín. El formato de etiqueta CCL apunta a bibliotecas y aplicaciones de comunicación colectiva. El formato CCL consiste en un solo campo: un identificador de carga útil. El identificador corresponde a la operación o datos que se llevan en la carga útil del mensaje. Por ejemplo, este campo puede usarse para identificar si un mensaje es para comunicación punto a punto o parte de una operación colectiva, y en este último caso, el tipo de operación colectiva.

El formato de etiqueta CCL no requiere buscar búferes de recepción coincidentes, solo dirigir el mensaje a la cola de mensajes virtual correcta basándose en el identificador de carga útil.

Las aplicaciones que usan el formato CCL pasan el identificador de carga útil directamente como la etiqueta y establecen los bits de ignorar a 0.

FI_TAG_MAX_FORMAT
Si el valor de mem_tag_format es >= FI_TAG_MAX_FORMAT, el formato de etiqueta se trata como un conjunto de campos de bits. El comportamiento es funcionalmente el mismo que FI_TAG_BITS. La siguiente descricción es para compatibilidad hacia atrás y describe cómo el proveedor puede interpretar el campo mem_tag_format si el valor es >= FI_TAG_MAX_FORMAT.

El formato de etiqueta de memoria puede usarse para dividir el arreglo de bits en campos separados. El mem_tag_format opcionalmente comienza con una serie de bits establecidos en 0, para significar bits que son ignorados por el proveedor. Siguiendo el prefijo inicial de bits ignorados, el arreglo consistirá en grupos alternos de bits establecidos en todos 1 o todos 0. Cada grupo de bits corresponde a un campo etiquetado. La implicación de definir un campo etiquetado es que cuando se aplica una máscara al arreglo de bits etiquetado, todos los bits pertenecientes a un solo campo serán establecidos colectivamente a 1 o 0.

Por ejemplo, un mem_tag_format de 0x30FF indica soporte para 14 bits etiquetados, separados en 3 campos. El primer campo consiste en 2 bits, el segundo campo 4 bits, y el campo final 8 bits. Máscaras válidas para tal campo etiquetado serían un OR bit a bit de cero o más de los siguientes valores: 0x3000, 0x0F00, y 0x00FF. El proveedor puede no validar la máscara proporcionada por la aplicación por razones de rendimiento.

Al identificar campos dentro de una etiqueta, un proveedor puede ser capaz de optimizar sus rutinas de búsqueda. Una aplicación que solicita campos de etiqueta debe proporcionar máscaras de etiqueta que establezcan todos los bits de máscara correspondientes a un campo a todos 0 o todos 1. Al negociar campos de etiqueta, una aplicación puede solicitar un número específico de campos de un tamaño dado. Un proveedor debe devolver un formato de etiqueta que soporte el número solicitado de campos, con cada campo siendo al menos del tamaño solicitado, o fallar la solicitud. Un proveedor puede aumentar el tamaño de los campos. Al reportar finalizaciones (ver FI_CQ_FORMAT_TAGGED), no está garantizado que el proveedor limpiaría cualquier bit de etiqueta no soportado en el campo de etiqueta de la entrada de finalización.

Se recomienda que los tamaños de campo estén ordenados de menor a mayor. Una etiqueta genérica y no estructurada y una máscara pueden lograrse solicitando un arreglo de bits que consista en 1 y 0 alternos.

msg_order - Message

Ordering

Message ordering refers to the order in which transport layer headers (as viewed by the application) are identified and processed. Relaxed message order enables data transfers to be sent and received out of order, which may improve performance by utilizing multiple paths through the fabric from the initiating endpoint to a target endpoint. Message order applies only between a single source and destination endpoint pair. Ordering between different target endpoints is not

defined.

Message order is determined using a set of ordering bits. Each set bit indicates that ordering is maintained between data transfers of the specified type. Message order is defined for [read | write | send] operations submitted by an application after [read | write | send] operations. Value 0 indicates that no ordering is specified. Value 0 may be used as input in order to obtain the default message order supported by the

provider.

Message ordering only applies to the end to end transmission of transport headers. Message ordering is necessary, but does not guarantee, the order in which message data is sent or received by the transport layer. Message ordering requires matching ordering semantics on the receiving side of a data transfer operation in order to guarantee that ordering is

met.

PUNTOS FINALES ESCALABLES

Un punto final escalable es un portal de comunicación que soporta múltiples contextos de transmisión y recepción. Los puntos finales escalables están modelados libremente después del concepto de redes de escalado de transmisión/recepción, también conocido como multi-cola. El soporte para puntos finales escalables es específico del dominio. Los puntos finales escalables pueden mejorar el rendimiento de aplicaciones multi-hilo y paralelas, al permitir que los hilos accedan a colas de transmisión y recepción independientes. Un punto final escalable tiene una única dirección de nivel de transporte, lo que puede reducir los requisitos de memoria necesarios para almacenar datos de direccionamiento remoto, en comparación con el uso de puntos finales estándar. Los puntos finales escalables no pueden usarse directamente para operaciones de comunicación y requieren que la aplicación cree explícitamente contextos de transmisión y recepción como se describe a continuación.

fi_tx_context

Los contextos de transmisión son colas de transmisión independientes. El ordenamiento y la sincronización entre contextos no están definidos. Conceptualmente, un contexto de transmisión se comporta de manera similar a un punto final de solo envío. Un contexto de transmisión puede configurarse con menos capacidades que el punto final base y con diferentes atributos (como requisitos de ordenamiento y tamaño de inyección) que otros contextos asociados con el mismo punto final escalable. Cada contexto de transmisión tiene su propia cola de finalización. El número de contextos de transmisión asociados con un punto final se especifica durante la creación del punto final.

La llamada fi_tx_context se utiliza para recuperar un contexto específico, identificado por un índice (ver arriba para más detalles sobre los atributos del contexto de transmisión). Los proveedores pueden asignar contextos dinámicamente cuando se llama a fi_tx_context, o pueden crear estáticamente todos los contextos cuando se invoca fi_endpoint. Por defecto, un contexto de transmisión hereda las propiedades de su punto final asociado. Sin embargo, las aplicaciones pueden solicitar atributos específicos del contexto a través del parámetro attr. El soporte para atributos por contexto de transmisión es específico del proveedor y no está garantizado. Los proveedores devolverán los atributos reales asignados al contexto a través del parámetro attr, si se proporciona.

fi_rx_context

Los contextos de recepción son colas de recepción independientes para recibir datos entrantes. El ordenamiento y la sincronización entre contextos no están garantizados. Conceptualmente, un contexto de recepción se comporta de manera similar a un punto final de solo recepción. Un contexto de recepción puede configurarse con menos capacidades que el punto final base y con diferentes atributos (como requisitos de ordenamiento y tamaño de inyección) que otros contextos asociados con el mismo punto final escalable. Cada contexto de recepción tiene su propia cola de finalización. El número de contextos de recepción asociados con un punto final se especifica durante la creación del punto final.

Los contextos de recepción a menudo se asocian con flujos de direccionamiento, que especifican qué paquetes entrantes dirigidos a un punto final escalable deben procesarse. Sin embargo, los contextos de recepción pueden ser dirigidos directamente por el iniciador, si lo soporta el protocolo subyacente. Dichos contextos se denominan `nombrados'. El soporte para contextos nombrados debe indicarse estableciendo la capacidad caps FI_NAMED_RX_CTX cuando se crea el punto final correspondiente. El soporte para contextos de recepción nombrados se coordina con los vectores de dirección. Ver fi_av(3) y fi_rx_addr(3).

La llamada fi_rx_context se utiliza para recuperar un contexto específico, identificado por un índice (ver arriba para más detalles sobre los atributos del contexto de recepción). Los proveedores pueden asignar contextos dinámicamente cuando se llama a fi_rx_context, o pueden crear estáticamente todos los contextos cuando se invoca fi_endpoint. Por defecto, un contexto de recepción hereda las propiedades de su punto final asociado. Sin embargo, las aplicaciones pueden solicitar atributos específicos del contexto a través del parámetro attr. El soporte para atributos por contexto de recepción es específico del proveedor y no está garantizado. Los proveedores devolverán los atributos reales asignados al contexto a través del parámetro attr, si se proporciona.

CONTEXTOS COMPARTIDOS

Los contextos compartidos son contextos de transmisión y recepción compartidos explícitamente entre uno o más puntos finales. Un contexto compartible permite a una aplicación usar un único recurso dedicado del proveedor entre múltiples puntos finales direccionables por transporte. Esto puede reducir significativamente los recursos necesarios para gestionar la comunicación sobre múltiples puntos finales al multiplexar el procesamiento de transmisión y/o recepción, con el costo potencial de serializar el acceso a través de múltiples puntos finales. El soporte para contextos compartibles es específico del dominio.

Conceptualmente, los contextos de transmisión compartibles son colas de transmisión a las que pueden acceder muchos puntos finales. El uso de un contexto de transmisión compartido es mayormente opaco para una aplicación. Las aplicaciones deben asignar y vincular contextos de transmisión compartidos a puntos finales, pero las operaciones se publican directamente en el punto final. Los contextos de transmisión compartidos no están asociados con colas de finalización ni contadores. Las operaciones completadas se publican en las CQs vinculadas al punto final. Un punto final solo puede estar asociado con un único contexto de transmisión compartido.

A diferencia de los contextos de transmisión compartidos, las aplicaciones interactúan directamente con los contextos de recepción compartidos. Los usuarios publican búferes de recepción directamente en un contexto de recepción compartido, con los búferes utilizables por cualquier punto final vinculado al contexto de recepción compartido. Los contextos de recepción compartidos no están asociados con colas de finalización ni contadores. Las operaciones de recepción completadas se publican en las CQs vinculadas al punto final. Un punto final solo puede estar asociado con un único contexto de recepción, y todos los puntos finales sin conexión asociados con un contexto de recepción compartido también deben compartir el mismo vector de dirección.

Los puntos finales asociados con un contexto de transmisión compartido pueden usar contextos de recepción dedicados, y viceversa. O un punto final puede usar contextos de transmisión y recepción compartidos. Y no hay requisito de que el mismo grupo de puntos finales que comparte un contexto de un tipo también comparta el contexto de un tipo alternativo. Además, un punto final puede usar un contexto compartido de un tipo, pero un conjunto escalable de contextos del tipo alternativo.

fi_stx_context

Esta llamada se utiliza para abrir un contexto de transmisión compartible (ver arriba para más detalles sobre los atributos del contexto de transmisión). Los puntos finales asociados con un contexto de transmisión compartido deben usar un subconjunto de los atributos del contexto de transmisión. Nótese que esto es lo contrario del requisito para los contextos de transmisión de los puntos finales escalables.

fi_srx_context

Esto asigna un contexto de recepción compartible (ver arriba para más detalles sobre los atributos del contexto de recepción). Los puntos finales asociados con un contexto de recepción compartido deben usar un subconjunto de los atributos del contexto de recepción. Nótese que esto es lo contrario del requisito para los contextos de recepción de los puntos finales escalables.

PUNTOS FINALES DE SOCKET

La siguiente característica y descripción deben considerarse experimentales. Hasta que se elimine la etiqueta experimental, las interfaces, semánticas y estructuras de datos asociadas con los puntos finales de socket pueden cambiar entre versiones de la biblioteca.

Esta sección aplica a puntos finales de tipo FI_EP_SOCK_STREAM y FI_EP_SOCK_DGRAM, comúnmente referidos como puntos finales de socket.

Los puntos finales de socket se definen con semánticas que les permiten ser adoptados más fácilmente por desarrolladores familiarizados con la API de sockets UNIX, o por middleware que expone la API de socket, mientras aún aprovechan características de hardware de alto rendimiento.

La diferencia clave entre los puntos finales de socket y otros puntos finales activos es que los puntos finales de socket usan transferencias de datos síncronas. Los búferes pasados a las operaciones de envío y recepción vuelven al control de la aplicación al regresar de la llamada a la función. Como resultado, no se notifican finalizaciones de transferencia de datos a la aplicación, y los puntos finales de socket no están asociados con colas de finalización ni contadores.

Los puntos finales de socket soportan un subconjunto de operaciones de mensaje: fi_send, fi_sendv, fi_sendmsg, fi_recv, fi_recvv, fi_recvmsg, y fi_inject. Debido a que las transferencias de datos son síncronas, el valor de retorno de las operaciones de envío y recepción indica el número de bytes transferidos en caso de éxito, o un valor negativo en caso de error, incluyendo -FI_EAGAIN si el punto final no puede enviar o recibir ningún dato debido a colas llenas o vacías, respectivamente.

Los puntos finales de socket están asociados con colas de eventos y vectores de dirección, y procesan eventos de gestión de conexiones de forma asíncrona, similar a otros puntos finales. A diferencia de los sockets UNIX, el punto final de socket aún debe declararse como activo o pasivo.

Los puntos finales de socket se comportan como sockets no bloqueantes. Para soportar la semántica de select y poll, los puntos finales de socket activos están asociados con un descriptor de archivo que se señala siempre que el punto final está listo para enviar y/o recibir datos. El descriptor de archivo puede recuperarse usando fi_control.

OPERATION FLAGS

The following flags are used with fabric operations to control behavior and completion semantics. All flags are defined in rdma/fabric.h.

FI_ASYNC
This flag is used to indicate that the operation is asynchronous. Asynchronous operations are expected to return without completing the operation. The operation is considered complete when a completion notification is received from the completion queue. This is the default behavior and does not need to be specified unless other flags require it to be overridden.
FI_COMPACT
Indicates that the underlying provider may reorder messages. This is intended for situations where message ordering is not critical, such as message logging or telemetry. Ordering is not guaranteed with this flag.
FI_CONTINUE
Indicates that the operation should continue from a previously interrupted state. This flag is primarily used with reliable connected endpoints. It allows an application to resume a connection that has been detected as failed and is in the process of being re-established. The operation is intended to be performed on a connection that is assumed to be in a transient failure state.
FI_CONTROL
Indicates that the data transfer is a control message. Control messages are typically used for connection management or other out-of-band signaling. The provider may treat control messages differently from data messages, such as by prioritizing them or handling them with different semantics. The exact behavior of control messages is provider-specific.
FI_DATA64
Indicates that the data length field is 64-bits. This flag is used when transferring large amounts of data, where the data length may exceed the capacity of a 32-bit integer. This flag is applicable to operations that specify a data length, such as send, receive, or read operations.
FI_DIRECTED_RECV
Indicates that the received message should be delivered to a specific receive buffer. This flag is used with posted receive operations to specify the exact buffer where the incoming message should be placed. This can be useful for optimizing data placement and avoiding unnecessary data copying. The provider must support this flag for it to be effective.
FI_ENDPOINT
Indicates that the operation is being performed on an endpoint. This flag is typically used in conjunction with other operation flags to specify that the operation applies to the endpoint itself, rather than a specific communication context or connection. For example, it might be used with fi_close or fi_shutdown to indicate that the entire endpoint should be closed or shut down.
FI_EVENT
Indicates that an event should be generated upon completion of the operation. This flag is used in conjunction with completion queues (CQs) to signal that an event should be posted to the CQ when the operation is finished. This is distinct from the default behavior where operations may complete without generating an explicit event, relying instead on polling or other mechanisms to detect completion.
FI_FLUSH
Indicates that all pending data transfers should be flushed. This flag is typically used with reliable connected endpoints to ensure that all outstanding data is sent before an operation completes or the connection is closed. It forces the provider to drain its internal buffers and transmit any data that has not yet been sent.
FI_LOCAL
Indicates that the operation should be performed locally. This flag is often used in conjunction with other flags to specify that a particular operation should only affect the local endpoint or its resources, without involving any remote communication. For example, it might be used with fi_bind to bind a completion queue to the local endpoint.
FI_MSG
Indicates that the operation is a message-based operation. This flag is used to distinguish message-based operations (like send/receive) from other types of operations, such as RMA (Remote Memory Access) or tagged operations. It helps the provider select the appropriate communication protocol and semantics.
FI_MULTI_EVENT
Indicates that multiple events can be generated for a single operation. This flag is typically used with operations that can result in multiple completion notifications, such as receiving multiple messages with a single posted receive. The provider will generate a separate event for each distinct event that occurs as part of the operation.
FI_NEED_PEER_ADDR
Indicates that the peer address information is required for the operation. This flag is used when an operation needs to know the address of the remote peer, such as for establishing a connection or sending a message to a specific destination. The provider will use the provided peer address to route the operation correctly.
FI_NOCREDITS
Indicates that the operation should not consume any credits. This flag is primarily used in environments where credit-based flow control is employed. By setting this flag, the application can perform an operation without impacting the available credits, which can be useful for certain control messages or management tasks.
FI_NO_DESC
Indicates that the operation does not require a data descriptor. Data descriptors are typically used to describe the memory buffers involved in a data transfer. This flag allows the application to perform operations that do not involve direct data transfer, such as initiating a connection or sending a control message, without the overhead of managing data descriptors.
FI_NO_PROGRESS
Indicates that the operation should not make progress. This flag is used to prevent an operation from consuming resources or consuming progress indications. It is typically used in scenarios where the application wants to defer the operation or ensure that it does not interfere with other ongoing operations. The operation will remain pending until it is explicitly requested to make progress.
FI_OP_WRITE
Indicates that the operation is a write operation. This flag is used to specify that the operation involves writing data to a remote memory location. It is typically used with RMA (Remote Memory Access) operations.
FI_OVERSUBSCRIBE
Indicates that the application is willing to oversubscribe resources. This flag allows the application to request more resources than may be guaranteed to be available. The provider will attempt to satisfy the request, but it may fail if resources are constrained. This can be useful in environments where resource availability fluctuates.
FI_PEEK
Indicates that the receive operation should only peek at the incoming message. This means that the message data will be read into the user buffer, but the message will remain in the network buffers and can be received again. This flag is useful for inspecting messages without consuming them, such as for message filtering or inspection purposes.
FI_RMA
Indicates that the operation is a Remote Memory Access (RMA) operation. This flag is used for operations that directly access memory on a remote node, such as atomic operations, reads, or writes. It signals to the provider that RMA semantics should be applied.
FI_SELECTIVE_COMPLETION
Indicates that completion queue entries should only be generated for operations that explicitly request them (e.g., using FI_COMPLETION). This allows for fine-grained control over when completion events are generated, potentially reducing overhead when completions are not needed for every operation. This flag is typically set when binding an endpoint to a completion queue.
FI_SEND
Indicates that the operation is a send operation. This flag is used to specify that the operation involves sending data to a remote endpoint. It is typically used with message-based communication.
FI_SENDRECV
Indicates that the operation is a send-receive operation. This flag is used for operations that combine sending data and immediately preparing to receive a reply. This can be more efficient than separate send and receive operations, as it may allow the provider to optimize the data path.
FI_TAGGED
Indicates that the operation is a tagged message operation. Tagged messages allow applications to associate a tag with messages, enabling receivers to select specific messages based on their tags. This is useful for multiplexing different types of communication over a single endpoint.
FI_TRANSMIT
Indicates that a transmit operation is requested. This flag is commonly used with message-based communication to signify that data should be transmitted to the destination. It may be used in conjunction with other flags to specify completion semantics.
FI_TRANSMIT_ONLY
Indicates that the operation is a transmit-only operation. This flag is used when data needs to be sent but no immediate response or acknowledgment is expected. It is a specialized form of transmit operation.
FI_UNTAGGED
Indicates that the operation is an untagged message operation. This is the default behavior for message-based communication when tags are not used. It signifies that messages are received in the order they are sent, without any specific tag filtering.
FI_COMPLETION
Indicates that a completion queue entry should be written for data transfer operations. This flag only applies to operations issued on an endpoint that was bound to a completion queue with the FI_SELECTIVE_COMPLETION flag set, otherwise, it is ignored. See the fi_ep_bind section above for more detail.
FI_DELIVERY_COMPLETE
Indicates that a completion should be generated when the operation has been processed by the destination endpoint(s). See fi_cq(3) for additional details on completion semantics.
FI_INJECT
Indicates that all outbound data buffers should be returned to the user’s control immediately after a data transfer call returns, even if the operation is handled asynchronously. This may require that the provider copy the data into a local buffer and transfer out of that buffer. A provider can limit the total amount of send data that may be buffered and/or the size of a single send that can use this flag. This limit is indicated using inject_size (see inject_size above).
FI_INJECT_COMPLETE
Indicates that a completion should be generated when the source buffer(s) may be reused. See fi_cq(3) for additional details on completion semantics.
FI_MULTICAST
Indicates that data transfers will target multicast addresses by default. Any fi_addr_t passed into a data transfer operation will be treated as a multicast address.
FI_MULTI_RECV
Applies to posted receive operations. This flag allows the user to post a single buffer that will receive multiple incoming messages. Received messages will be packed into the receive buffer until the buffer has been consumed. Use of this flag may cause a single posted receive operation to generate multiple completions as messages are placed into the buffer. The placement of received data into the buffer may be subjected to provider specific alignment restrictions. The buffer will be released by the provider when the available buffer space falls below the specified minimum (see FI_OPT_MIN_MULTI_RECV).
FI_TRANSMIT_COMPLETE
Indicates that a completion should be generated when the transmit operation has completed relative to the local provider. See fi_cq(3) for additional details on completion semantics.

NOTES

Users should call fi_close to release all resources allocated to the fabric endpoint.

Endpoints allocated with the FI_CONTEXT or FI_CONTEXT2 mode bits set must typically provide struct fi_context(2) as their per operation context parameter. (See fi_getinfo.3 for details.) However, when FI_SELECTIVE_COMPLETION is enabled to suppress CQ completion entries, and an operation is initiated without the FI_COMPLETION flag set, then the context parameter is ignored. An application does not need to pass in a valid struct fi_context(2) into such data transfers.

Operations that complete in error that are not associated with valid operational context will use the endpoint context in any error reporting structures.

Although applications typically associate individual completions with either completion queues or counters, an endpoint can be attached to both a counter and completion queue. When combined with using selective completions, this allows an application to use counters to track successful completions, with a CQ used to report errors. Operations that complete with an error increment the error counter and generate a CQ completion event.

As mentioned in fi_getinfo(3), the ep_attr structure can be used to query providers that support various endpoint attributes. fi_getinfo can return provider info structures that can support the minimal set of requirements (such that the application maintains correctness). However, it can also return provider info structures that exceed application requirements. As an example, consider an application requesting no msg_order. The resulting output from fi_getinfo may have all the ordering bits set. The application can reset the ordering bits it does not require before creating the endpoint. The provider is free to implement a stricter ordering than is required by the application.

RETURN VALUES

Returns 0 on success. On error, a negative value corresponding to fabric errno is returned. For fi_cancel, a return value of 0 indicates that the cancel request was submitted for processing, a return value of -FI_EAGAIN indicates that the request could not be submitted and that it should be retried once progress has been made. For fi_setopt/fi_getopt, a return value of -FI_ENOPROTOOPT indicates the provider does not support the requested option.

Fabric errno values are defined in rdma/fi_errno.h.

ERRORS

-FI_EDOMAIN
A resource domain was not bound to the endpoint or an attempt was made to bind multiple domains.
-FI_ENOCQ
The endpoint has not been configured with necessary completion queue.
-FI_EOPBADSTATE
The endpoint’s state does not permit the requested operation.
