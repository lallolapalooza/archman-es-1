NOMBRE

fi_export_fid / fi_import_fid
Compartir un objeto de fabric entre diferentes proveedores o recursos
struct fid_peer_av
Un vector de direcciones compartible entre proveedores independientes
struct fid_peer_av_set
Un conjunto de AV compartible entre proveedores independientes
struct fid_peer_cq
Una cola de finalización que puede compartirse entre proveedores independientes
struct fid_peer_cntr
Un contador que puede compartirse entre proveedores independientes
struct fid_peer_srx
Un contexto de recepción compartido que puede compartirse entre proveedores independientes

SINOPSIS

#include <rdma/fabric.h>
#include <rdma/fi_ext.h>
#include <rdma/providers/fi_peer.h>
int fi_export_fid(struct fid *fid, uint64_t flags,
    struct fid **expfid, void *context);
int fi_import_fid(struct fid *fid, struct fid *expfid, uint64_t flags);

ARGUMENTOS

fid
Identificador de fabric devuelto para el objeto abierto.
expfid
Objeto de fabric exportado que puede compartirse con otro proveedor.
flags
Banderas de control para la operación.
*context:
Contexto definido por el usuario que se asociará con un objeto de fabric.

DESCRIPCIÓN

AVISO: Las API de pares descritas en esta página de manual son de desarrollo y pueden cambiar entre versiones de libfabric. Las estructuras de datos y las definiciones de API no deben considerarse estables entre versiones. Los proveedores utilizados como pares deben apuntar a la misma versión de libfabric.

Las funciones definidas en esta página de manual son típicamente utilizadas por los proveedores para comunicarse con otros proveedores, conocidos como proveedores pares, o por otras bibliotecas para comunicarse con el núcleo de libfabric, conocidas como bibliotecas pares. La mayoría del middleware y las aplicaciones no deberían necesitar acceder a esta funcionalidad, ya que la documentación está dirigida principalmente a los desarrolladores de proveedores.

Los proveedores pares son una forma de que proveedores desarrollados de forma independiente se utilicen juntos de una manera estrecha, de modo que se pueda evitar la sobrecarga de capas y la funcionalidad duplicada del proveedor. Los proveedores pares se enlazan al hacer que un proveedor exporte funcionalidad específica a otro. Esto se logra al hacer que un proveedor exporte un objeto de fabric compartible (fid), el cual es importado por uno o más proveedores pares.

Como ejemplo, un proveedor que utiliza TCP para comunicarse con pares remotos puede desear usar el proveedor de memoria compartida para comunicarse con pares locales. Para eliminar la sobrecarga de capas, el proveedor basado en TCP puede exportar su cola de finalización y su contexto de recepción compartido e importarlos en el proveedor de memoria compartida.

Los mecanismos generales utilizados para compartir objetos de fabric entre proveedores pares son similares, independientemente del objeto que se comparta. Sin embargo, dado que el objetivo de usar proveedores pares es evitar la sobrecarga, los proveedores deben estar escritos explícitamente para soportar los mecanismos de proveedor par.

Al importar cualquier objeto de fabric compartido a un par, el propietario creará un fid_peer_* separado para cada proveedor par al que pretenda importar. El propietario pasará este fid_peer_* único a cada par a través del parámetro context de la llamada de inicialización para el recurso (es decir, fi_cq_open, fi_srx_context, fi_cntr_open, etc). El fi_peer_context indicará el fid_peer asignado por el propietario para que el par lo use, pero es temporal para la llamada de inicialización y no puede ser accedido por el par después de la inicialización. El par establecerá solo el peer_ops del fid asignado por el propietario y guardará una referencia al fid_peer_* importado para usarlo en el flujo de la API de pares. El par asignará su propio fid para usos internos y devolverá ese fid al propietario a través del parámetro fid regular de la llamada de inicialización (como si fuera solo otro recurso abierto). El propietario es responsable de guardar el fid del par devuelto desde la llamada de apertura para poder cerrarlo más tarde (o para impulsar el progreso en el caso del cq_fid).

Hay dos modelos de proveedor par. En el ejemplo listado arriba, ambos pares son proveedores completos por derecho propio y utilizables de una manera independiente. En un segundo modelo, uno de los pares es conocido como un proveedor de descarga. Un proveedor de descarga implementa un subconjunto de la API de libfabric y está dirigido al uso de hardware de aceleración específico. Por ejemplo, los conmutadores de red pueden soportar operaciones colectivas, como barrera o difusión. Un proveedor de descarga puede escribirse específicamente para aprovechar esta capacidad; sin embargo, dicho proveedor no es utilizable para propósitos generales. Como resultado, un proveedor de descarga se empareja con un proveedor par principal.

AV DE PARES

El AV de pares permite el intercambio de metadatos de direccionamiento entre proveedores. Está dirigido específicamente al caso de uso de tener un proveedor principal emparejado con un proveedor de descarga, donde el proveedor de descarga aprovecha la comunicación que ya ha sido establecida a través del proveedor principal. En otras situaciones, como la mencionada arriba emparejando un proveedor tcp con un proveedor de memoria compartida, cada par probablemente tendrá su propio AV que no se comparte.

La configuración para un AV de pares es similar a la configuración para una CQ compartida, descrita más abajo. El propietario del AV crea un objeto fid_peer_av que se enlaza de vuelta a su fid_av real. El fid_peer_av es entonces importado por el proveedor de descarga.

Los AV de pares son configurados por el propietario llamando a la llamada fi_av_open() del par, pasando la bandera FI_PEER, y apuntando el parámetro context a struct fi_peer_av_context.

Las estructuras de datos para soportar AV de pares son:

struct fid_peer_av;
struct fi_ops_av_owner {
    size_t  size;
    int (*query)(struct fid_peer_av *av, struct fi_av_attr *attr);
    fi_addr_t (*ep_addr)(struct fid_peer_av *av, struct fid_ep *ep);
};
struct fid_peer_av {
    struct fid fid;
    struct fi_ops_av_owner *owner_ops;
};
struct fi_peer_av_context {
    size_t size;
    struct fid_peer_av *av;
};

fi_ops_av_owner::query()

Esta llamada devuelve los atributos actuales para el AV de pares. El propietario establece los campos de la estructura de entrada fi_av_attr basándose en el estado actual del AV para devolverlos al llamador.

fi_ops_av_owner::ep_addr()

Esta función de búsqueda devuelve el fi_addr de la dirección asociada con el punto final local dado. Si la dirección del punto final local no ha sido insertada en el AV, la función debería devolver FI_ADDR_NOTAVAIL.

CONJUNTO DE AV DE PARES

El conjunto de AV de pares permite el intercambio de datos de direccionamiento colectivo entre proveedores. Está dirigido específicamente al caso de uso de emparejar un proveedor principal con un proveedor de descarga colectiva. La configuración para un conjunto de AV de pares es similar a una CQ compartida, descrita más abajo. El propietario del conjunto de AV crea un objeto fid_peer_av_set que se enlaza de vuelta a su fid_av_set. El fid_peer_av_set es importado por el proveedor de descarga.

Los conjuntos de AV de pares son configurados por el propietario llamando a la llamada fi_av_set_open() del par, pasando la bandera FI_PEER_AV, y apuntando el parámetro context a struct fi_peer_av_set_context.

Las estructuras de datos para soportar conjuntos de AV de pares son:

struct fi_ops_av_set_owner {
    size_t  size;
    int (*members)(struct fid_peer_av_set *av, fi_addr_t *addr,
               size_t *count);
};
struct fid_peer_av_set {
    struct fid fid;
    struct fi_ops_av_set_owner *owner_ops;
};
struct fi_peer_av_set_context {
    size_t size;
    struct fi_peer_av_set *av_set;
};

fi_ops_peer_av_owner::members

Esta llamada devuelve una matriz de direcciones AV que son miembros del conjunto AV. El tamaño de la matriz se especifica a través del parámetro count. Al devolver, count se establece al número de direcciones en el conjunto AV. Si el valor de entrada count es tes demasiado pequeña, la función devuelve -FI_ETOOSMALL. De lo contrario, la función devuelve un array de valores fi_addr.

CQ DE PAR

El CQ de par define un mecanismo por el cual un proveedor par puede insertar finalizaciones en el CQ propiedad de otro proveedor. Esto evita la sobrecarga de que el usuario de libfabric necesite acceder a múltiples CQ.

Para configurar un CQ de par, un proveedor crea un objeto fid_peer_cq, que se enlaza de vuelta al fid_cq real del proveedor. El objeto fid_peer_cq es entonces importado por un proveedor par. El fid_peer_cq define callbacks que los proveedores usan para comunicarse entre sí. El proveedor que asigna el fid_peer_cq se conoce como el propietario, con el otro proveedor referido como el par. Un propietario puede configurar relaciones de par con múltiples proveedores.

Los CQ de par son configurados por el propietario llamando a la función fi_cq_open() del par. El propietario pasa el flag FI_PEER a fi_cq_open(). Cuando se especifica FI_PEER, el parámetro de contexto pasado a fi_cq_open() debe referenciar un struct fi_peer_cq_context. Los proveedores que no soportan CQ de par deben hacer fallar la llamada fi_cq_open() con -FI_EINVAL (indicando un flag inválido). El fid_peer_cq referenciado por struct fi_peer_cq_context debe permanecer válido hasta que el CQ del par sea cerrado.

Las estructuras de datos para soportar CQ de par son definidas como sigue:

struct fi_ops_cq_owner {
    size_t  size;
    ssize_t (*write)(struct fid_peer_cq *cq, void *context, uint64_t flags,
        size_t len, void *buf, uint64_t data, uint64_t tag, fi_addr_t src);
    ssize_t (*writeerr)(struct fid_peer_cq *cq,
        const struct fi_cq_err_entry *err_entry);
};
struct fid_peer_cq {
    struct fid fid;
    struct fi_ops_cq_owner *owner_ops;
};
struct fi_peer_cq_context {
    size_t size;
    struct fid_peer_cq *cq;
};

Para struct fid_peer_cq, el propietario inicializa los campos fid y owner_ops. struct fi_ops_cq_owner es usado por el par para comunicarse con el proveedor propietario.

Si se necesita progreso manual en el CQ de par, el propietario debe impulsar el progreso usando la función fi_cq_read() con el parámetro buf establecido a NULL y count igual a 0. El proveedor par debe establecer otras funciones que intenten leer el CQ del par (es decir, fi_cq_readerr, fi_sread, etc.) para que devuelvan -FI_ENOSYS.

fi_ops_cq_owner::write()

Esta llamada dirige al propietario a insertar nuevas finalizaciones en el CQ. El campo fi_cq_attr::format, junto con otros atributos relacionados, determina qué parámetros de entrada son válidos. Los parámetros que no son reportados como parte de una finalización son ignorados por el propietario, y deben ser establecidos a 0, NULL u otro valor apropiado por el usuario. Por ejemplo, si el direccionamiento de origen no es devuelto con una finalización, entonces el parámetro src debe ser establecido a FI_ADDR_NOTAVAIL e ignorado en la entrada.

El propietario es responsable del bloqueo, la señalización de eventos y el manejo del desbordamiento del CQ. Los datos pasados a través del callback write son relativos al usuario. Por ejemplo, el fi_addr_t es relativo al AV del par. El propietario es responsable de convertir la dirección si se necesita el direccionamiento de origen.

(Por definir: ¿debería el desbordamiento del CQ empujar de vuelta al usuario para el control de flujo? ¿Necesitamos callbacks de backoff / resume en ops_cq_user?)

fi_ops_cq_owner::writeerr()

El comportamiento de esta llamada es similar al de las operaciones write(). Inserta una finalización que indica que una transferencia de datos ha fallado en el CQ.

EJEMPLO CONFIGURACIÓN DE CQ DE PAR

La descripción anterior define el mecanismo genérico para compartir CQ entre proveedores. Esta sección describe una implementación posible para demostrar el uso de las APIs. En el ejemplo, el proveedor A usa al proveedor B como par para transferencias de datos dirigidas a endpoints en el nodo local.

1. El proveedor A está configurado para usar al proveedor B como par. Esto puede estar codificado en el proveedor A o establecido a través de una variable de entorno.
2. La aplicación llama:
   fi_cq_open(domain_a, attr, &cq_a, app_context)
3. El proveedor A asigna cq_a y lo configura automáticamente para ser usado como un cq de par.
4. El proveedor A toma estos pasos:
   asignar peer_cq y referenciar cq_a
   establecer peer_cq_context->cq = peer_cq
   establecer attr_b.flags |= FI_PEER
   fi_cq_open(domain_b, attr_b, &cq_b, peer_cq_context)
5. El proveedor B asigna un cq, pero lo configura de tal manera que todas las finalizaciones son escritas en el peer_cq. Las operaciones del cq para leer del cq son establecidas a llamadas enosys.
6. El proveedor B inserta sus propios callbacks en el objeto peer_cq. Crea una referencia entre el objeto peer_cq y su propio cq.

CONTADOR DE PAR

El contador de par define un mecanismo por el cual un proveedor par puede incrementar el valor o el error en el contador propiedad de otro proveedor.

La configuración de un contador de par es similar a la configuración de un CQ de par descrita arriba. El objeto contador del propietario es importado directamente en el par.

Las estructuras de datos para soportar contadores de par son definidas como sigue:

struct fi_ops_cntr_owner {
    size_t size;
    void (*inc)(struct fid_peer_cntr *cntr);
    void (*incerr)(struct fid_peer_cntr *cntr);
};
struct fid_peer_cntr {
    struct fid fid;
    struct fi_ops_cntr_owner *owner_ops;
};
struct fi_peer_cntr_context {
    size_t size;
    struct fid_peer_cntr *cntr;
};

Similar al CQ de par, si se necesita progreso manual en el contador de par, el propietario debe impulsar el progreso usando fi_cntr_read() y el fi_cntr_read() no debe hacer nada más que impulsar el progreso del cntr del par. El proveedor par debe establecer otras funciones que intenten acceder al cntr del par (es decir, fi_cntr_readerr, fi_cntr_set, etc.) para que devuelvan -FI_ENOSYS.

fi_ops_cntr_owner::inc()

Esta llamada dirige al propietario a incrementar el valor del cntr.

fi_ops_cntr_owner::incerr()

El comportamiento de esta llamada es similar al de las operaciones inc(). Incrementa el error del cntr indicando que una transferencia de datos ha fallado en el cntr.

DOMINIO DE PAR

El dominio de par permite a un proveedor acceder a las operaciones de un objeto dominio de su par. Por ejemplo, un proveedor de descarga puede usar un dominio de par para registrar buffers de memoria con el proveedor principal.

La configuración de un dominio de par es similar a la configuración de un CQ de par descrita arriba. El objeto dominio del propietario es importado directamente en el par.

Los dominios de par son configurados por el propietario llamando a la función fi_domain2() del par. El propietario pasa el flag FI_PEER a fi_domain2(). Cuando se especifica FI_PEER, el parámetro de contexto pasado a fi_domain2() debe referenciar un struct fi_peer_domain_context. Los proveedores que no soportan dominios de par deben hacer fallar la llamada fi_domain2() con -FI_EINVAL. El fid_domain referenciado por struct fi_peer_domain_context debe permanecer válido hasta que el dominio del par sea cerrado.

Las estructuras de datos para soportar dominios de par son definidas como sigue:

struct fi_peer_domain_context {
    size_t size;
    struct fid_domain *domain;
};

EQ DE PAR

El EQ de par define un mecanismo por el cual un proveedor par puede insertar eventos en el EQ propiedad de otro proveedor. Esto evita la sobrecarga de que el usuario de libfabric necesite acceder a múltiples EQ.

La configuración de un EQ de par es similar a la configuración de un CQ de par descrita arriba. El objeto EQ del propietario es importado directamente en el proveedor par.

Los EQ de par son configurados por el propietario llamando a la función fi_eq_open() del par. El propietario pasa el flag FI_PEER a fi_eq_open(). Cuando se especifica FI_PEER, el parámetro de contexto pasado a fi_eq_open() debe referenciar un struct fi_peer_eq_context. Los proveedores que no soportan EQ de par deben hacer fallar la llamada fi_eq_open() con -FI_EINVAL (indicando un flag inválido). El fid_eq referenciado por struct fi_peer_eq_context debe permanecer válido hasta que el EQ del par sea cerrado.

Las estructuras de datos para soportar EQ de par son definidas como sigue:

struct fi_peer_eq_context {
    size_t size;
    struct fid_eq *eq;
};

SRX DE PAR

El SRX de par define un mecanismo por el cual los proveedores par pueden compartir un contexto de recepción compartido común. Esto evita la sobrecarga de tener colas de recepción separadas, puede eliminar copias de memoria y asegura el ordenamiento correcto de mensajes a nivel de aplicación.

La configuración de un SRX de par es similar a la configuración de un CQ de par descrita arriba. Un objeto fid_peer_srx enlaza al propietario del SRX con el proveedor par. Los SRX de par son configurados por el propietario llamando a la función fi_srx_context() del par con el flag FI_PEER establecido. El parámetro de contexto pasado a fi_srx_context() debe ser un struct fi_peer_srx_context.

El proveedor propietario inicializa todos los elementos del fid_peer_srx y las estructuras referenciadas (fi_ops_srx_owner y fi_ops_srx_peer), con la excepción de las funciones callback de fi_ops_srx_peer. Esas deben ser inicializadas por el proveedor par antes de regresar de la llamada fi_srx_contex() y son usadas por el propietario para controlar las acciones del par.

Las estructuras de datos para soportar SRX de par son definidas como sigue:

struct fid_peer_srx;
struct fi_peer_rx_entry {
    struct fi_peer_srx *srx;
    fi_addr_t addr;
    size_t msg_size;
    uint64_t tag;
    uint64_t cq_data;
    uint64_t flags;
    void *context;
    size_t count;
    void **desc;
    void *peer_context;
    void *owner_context;
    struct iovec *iov;
};
struct fi_peer_match_attr {
    fi_addr_t addr;
    size_t msg_size;
    uint64_t tag;
};
struct fi_ops_srx_owner {
    size_t size;
    int (*get_msg)(struct fid_peer_srx *srx,
                   struct fi_peer_match_attr *attr,
                   struct fi_peer_rx_entry **entry);
    int (*get_tag)(struct fid_peer_srx *srx,
                   struct fi_peer_match_attr *attr,
                   uint64_t tag, struct fi_peer_rx_entry **entry);
    int (*queue_msg)(struct fi_peer_rx_entry *entry);
    int (*queue_tag)(struct fi_peer_rx_entry *entry);
    void (*foreach_unspec_addr)(struct fid_peer_srx *srx,
                  fi_addr_t (*get_addr)(struct fi_peer_rx_entry *));
    void (*free_entry)(struct fi_peer_rx_entry *entry);
};
struct fi_ops_srx_peer {
    size_t size;
    int (*start_msg)(struct fi_peer_rx_entry *entry);
    int (*start_tag)(struct fi_peer_rx_entry *entry);
    int (*discard_msg)(struct fi_peer_rx_entry *entry);
    int (*discard_tag)(struct fi_peer_rx_entry *entry);
};
struct fid_peer_srx {
    struct fid_ep ep_fid;
    struct fi_ops_srx_owner *owner_ops;
    struct fi_ops_srx_peer *peer_ops;
};
struct fi_peer_srx_context {
    size_t size;
    struct fid_peer_srx *srx;
};

La propiedad de los valores de los campos de la estructura y de las funciones de retorno de llamada es similar a la definida para las CQs entre pares, en relación con las operaciones del propietario frente a las del par.

El propietario es responsable de adquirir cualquier bloqueo necesario antes de cualquier operación que pueda resultar en llamadas de retorno al par. Las siguientes funciones son funciones a nivel de progreso: get_msg(), get_tag(), queue_msg(), queue_tag(), free_entry(), start_msg(), start_tag(), discard_msg(), discard_tag(). Si es necesario, es responsabilidad del propietario adquirir el bloqueo apropiado antes de llamar a la función fi_cq_read() del par, o similar, que impulsa el progreso.

Las siguientes funciones son funciones a nivel de dominio: foreach_unspec_addr(). Esta función se utiliza fuera del flujo de progreso de mensajes (es decir, durante fi_av_insert()). El propietario del srx es responsable de adquirir el mismo bloqueo, si es necesario.

fi_peer_rx_entry

fi_peer_rx_entry define una entrada de recepción común para su uso entre el propietario y el par. La entrada es asignada y establecida por el propietario y pasada entre el propietario y el par para comunicar los detalles de la entrada de recepción publicada por la aplicación. Todos los campos son inicializados por el propietario, excepto en el caso de mensaje inesperado, donde el par puede inicializar cualquier dato adicional disponible antes de encolar el mensaje con el propietario. Los campos peer_context y owner_context solo son modificables por el par y el propietario, respectivamente, para almacenar información adicional específica del proveedor.

fi_ops_srx_owner::get_msg() / get_tag()

Estas llamadas son invocadas por el proveedor par para obtener el búfer(es) de recepción donde debe colocarse un mensaje entrante. El proveedor par pasará los campos relevantes para solicitar una rx_entry coincidente del propietario. Si se requiere direccionamiento de origen, la dirección (addr) será pasada; de lo contrario, la dirección será establecida a FI_ADDR_NOTAVAIL. El campo msg_size indica el tamaño del mensaje recibido. Este campo puede ser necesario para el propietario al manejar FI_MULTI_RECV o FI_PEEK. El propietario establecerá el campo peer_entry->msg_size en get_msg/tag() para que el propietario y el par lo usen más tarde, si es necesario. Este campo será establecido tanto en la ruta esperada como en la inesperada. El rx_entry->iov devuelto por el propietario se refiere al tamaño completo de la recepción publicada pasada al par. El proveedor par es responsable de verificar que un mensaje entrante quepa dentro del espacio de búfer proporcionado y de generar errores de truncamiento. El parámetro tag solo se usa para mensajes etiquetados pero debe establecerse a 0 en los casos no etiquetados. Un fi_peer_rx_entry es asignado por el propietario, haya o no una coincidencia encontrada. Si se encontró una coincidencia, el propietario devolverá FI_SUCCESS y la rx_entry será rellenada con los campos de recepción conocidos para que el par los procese en consecuencia. Esto incluye la información que fue pasada a las llamadas así como los rx_entry->flags con FI_MSG | FI_RECV (para get_msg()) o FI_TAGGED | FI_RECV (para get_tag()). El proveedor par es responsable de completar con cualquier otro flag, si es necesario. Si no se encontró ninguna coincidencia, el propietario devolverá -FI_ENOENT; la rx_entry seguirá siendo válida pero no coincidirá con una recepción publicada existente. Cuando el par obtenga FI_ENOENT, debe asignar los recursos que necesite para procesar el mensaje más tarde (en start_msg/tag) y establecer el rx_entry->peer_context apropiadamente, seguido de una llamada a la función queue_msg/tag del propietario. Las llamadas de get y queue deben ser serializadas. Cuando el propietario obtenga una recepción coincidente para el mensaje inesperado encolado, llamará a la función de inicio del par para notificar al par del rx_entry actualizado (o a la función de descarte del par si el mensaje debe ser descartado)

fi_ops_srx_owner::queue_msg() / queue_tag()

Llamada por el par para encolar un mensaje entrante inesperado en el srx. Una vez que es encolado por el par, el propietario es responsable de iniciarlo una vez que sea emparejado con un búfer de recepción, o descartarlo si es necesario.

fi_ops_srx_owner::foreach_unspec_addr()

Llamada por el par cuando han ocurrido actualizaciones de direccionamiento con el par. Esto desencadena al propietario a iterar sobre cualquier entrada cuya dirección aún sea desconocida y llamar a la función get_addr proporcionada en cada una para recuperar información de dirección actualizada.

fi_ops_srx_owner:: free_entry()

Llamada por el par cuando ha terminado completamente de usar una entrada de par asignada por el propietario.

fi_ops_srx_peer::start_msg() / start_tag()

Estas llamadas indican que una get_msg() o get_tag() asíncrona ha completado y un búfer está ahora disponible para recibir el mensaje. El control del fi_peer_rx_entry es devuelto al proveedor par y ha sido inicializado para recibir el mensaje entrante.

fi_ops_srx_peer::discard_msg() / discard_tag()

Indica que el mensaje y los datos asociados con el fi_peer_rx_entry especificado deben ser descartados. Esto a menudo indica que la aplicación ha cancelado o descartado la operación de recepción. No debe ser generada ninguna completación por el proveedor par para un mensaje descartado. El control del fi_peer_rx_entry es devuelto al proveedor par.

EJEMPLO CONFIGURACIÓN DE SRX ENTRE PARES

La descripción anterior define el mecanismo genérico para compartir SRXs entre proveedores. Esta sección describe una implementación posible para demostrar el uso de las APIs. En el ejemplo, el proveedor A usa al proveedor B como par para transferencias de datos dirigidas a puntos de conexión en el nodo local.

1. El proveedor A está configurado para usar al proveedor B como par. Esto puede ser codificado
   en el proveedor A o establecido a través de una variable de entorno.
2. La aplicación llama:
   fi_srx_context(domain_a, attr, &srx_a, app_context)
3. El proveedor A asigna srx_a y lo configura automáticamente para ser usado
   como un srx entre pares.
4. El proveedor A toma estos pasos:
   asignar peer_srx y referenciar srx_a
   establecer peer_srx_context->srx = peer_srx
   establecer attr_b.flags |= FI_PEER
   fi_srx_context(domain_b, attr_b, &srx_b, peer_srx_context)
5. El proveedor B asigna un srx, pero lo configura de tal manera que todos los búferes de
   recepción se obtienen del peer_srx. Las operaciones del srx para publicar recepciones son
   establecidas a llamadas enosys.
6. El proveedor B inserta sus propias llamadas de retorno en el objeto peer_srx. Crea
   una referencia entre el objeto peer_srx y su propio srx.

EJEMPLO FLUJO DE RECEPCIÓN CON SRX ENTRE PARES

Lo siguiente describe flujos de software simplificados y de ejemplo para el manejo de mensajes de recepción usando un SRX entre pares. El primer flujo demuestra el caso donde un búfer de recepción está esperando cuando el mensaje llega.

1. La aplicación llama fi_recv() / fi_trecv() en el propietario.
2. El propietario encola el búfer de recepción.
3. Un mensaje es recibido por el proveedor par.
4. El par llama a owner->get_msg() / get_tag().
5. El propietario retira el búfer de recepción encolado y lo devuelve al
   par. La llamada de obtención de entrada se completará con FI_SUCCESS.
6. Cuando el par termina de procesar el mensaje y lo completa en su propia
   CQ, el par llamará a free_entry para liberar la entrada con el propietario.

El segundo caso a continuación muestra el flujo cuando un mensaje llega antes de que la aplicación haya publicado el búfer de recepción coincidente.

1. Un mensaje es recibido por el proveedor par.
2. El par llama a owner->get_msg() / get_tag(). Si la dirección entrante es
   FI_ADDR_UNSPEC, el propietario no puede emparejar este mensaje con una recepción publicada con
   FI_DIRECTED_RECV y solo puede emparejarlo con recepciones publicadas con FI_ADDR_UNSPEC.
3. El propietario no logra encontrar un búfer de recepción coincidente.
4. El propietario asigna una rx_entry con los campos conocidos y devuelve -FI_ENOENT.
5. El par asigna los recursos necesarios para manejar el procesamiento asíncrono
   y establece peer_context en consecuencia, llamando a la función queue
   del propietario cuando esté listo para encolar el mensaje inesperado del par.
6. La aplicación llama fi_recv() / fi_trecv() en el propietario, publicando el
   búfer de recepción coincidente.
7. El propietario empareja la recepción con el mensaje encolado en el par. Nótese que
   el propietario no puede emparejar una recepción dirigida con un mensaje inesperado cuya
   dirección es desconocida.
8. El propietario retira la solicitud encolada, rellena el resto de los campos
   conocidos y llama a la función peer->start_msg() / start_tag().
9. Cuando el par termina de procesar el mensaje y lo completa en su propia
   CQ, el par llamará a free_entry para liberar la entrada con el propietario.

Siempre que el direccionamiento de un par sea actualizado (por ejemplo, a través de fi_av_insert()), necesita llamar a la función foreach_unspec_addr() del propietario para desencadenar cualquier actualización necesaria de las entradas desconocidas. Se espera que el propietario itere sobre las entradas necesarias y llame a la función get_addr() proporcionada en cada una de ellas para obtener información de direccionamiento actualizada. Una vez que la dirección es conocida, el propietario puede proceder a recibir recepciones dirigidas en esas entradas.

fi_export_fid / fi_import_fid

La función fi_export_fid está reservada para uso futuro.

La llamada fi_import_fid puede usarse para importar un objeto de fabric creado y poseído por el usuario de libfabric. Esto permite a bibliotecas de nivel superior o a la aplicación anular o definir el comportamiento de libfabric de bajo nivel. FI_PEER_TRANSFE

R

Los proveedores envían frecuentemente mensajes de control a sus contrapartes remotas como parte de su protocolo de comunicación. Por ejemplo, un proveedor puede enviar un mensaje ACK para garantizar la entrega fiable de un mensaje o para cumplir una semántica de finalización solicitada. Cuando dos o más proveedores se coordinan como pares, puede ser más eficiente si los mensajes de control de ambos proveedores pares viajan por el mismo transporte. En algunos casos, como cuando uno de los pares es un proveedor de descarga (offload), puede incluso ser obligatorio. Las transferencias entre pares definen el mecanismo por el cual ocurre dicha

comunicación.

Las transferencias entre pares permiten a un par enviar y recibir transferencias de datos a través de su par asociado. Los proveedores que requieren esta funcionalidad indican esto estableciendo el indicador FI_PEER_TRANSFER como un bit de modo, es decir, fi_info::

mode.

Para usar un proveedor de este tipo como par, el proveedor principal, u propietario, debe configurar las transferencias entre pares abriendo un punto de finalización de transferencia entre pares y aceptando transferencias con este indicador establecido. La configuración de las transferencias entre pares implica las siguientes estructuras de

datos: 
struct fi_ops_transfer_peer {
    size_t size;
    ssize_t (*complete)(struct fid_ep *ep, struct fi_cq_tagged_entry *buf,
            fi_addr_t *src_addr);
    ssize_t (*comperr)(struct fid_ep *ep, struct fi_cq_err_entry *buf);
};
struct fi_peer_transfer_context {
    size_t size;
    struct fi_info *info;
    struct fid_ep *ep;
    struct fi_ops_transfer_peer *peer_ops;
}
;

Los contextos de transferencia entre pares forman un enlace virtual entre los puntos de finalización asignados en cada uno de los proveedores pares. La configuración de un contexto de transferencia entre pares se realiza a través de la API fi_endpoint(). El proveedor principal llama a fi_endpoint() con el bit de modo FI_PEER_TRANSFER establecido en el parámetro info, y el parámetro context debe hacer referencia a la struct fi_peer_transfer_context definida

anteriormente.

El campo size indica el tamaño de la struct fi_peer_transfer_context que se pasa al par. Esto se utiliza para la compatibilidad con versiones anteriores. El campo info es opcional. Si se proporciona, define los atributos de los objetos del proveedor principal. Puede usarse para informar de las capacidades y restricciones sobre las transferencias entre pares, como si se requiere registro de memoria, tamaños máximos de mensajes, semánticas de ordenación de datos y finalización, etc. Si el proveedor importador no puede cumplir estas restricciones, debe hacer fallar la llamada a fi_endpoint()

.

El campo peer_ops contiene devoluciones de llamada (callbacks) del proveedor principal al par y se utiliza para informar de la finalización (con éxito o fallo) de las transferencias de datos iniciadas por el par. Las funciones de devolución de llamada definidas en struct fi_ops_transfer_peer deben ser establecidas por el proveedor par

antes de regresar de la llamada a fi_endpoint(). Las acciones que el proveedor par puede realizar dentro de las devoluciones de llamada de finalización son en su mayoría ilimitadas, y pueden incluir cualquiera de los siguientes tipos de operaciones: inicio de transferencias de datos adicionales, escritura de eventos en la CQ o EQ del
propietario, y registro/deregistro de memoria. El propietario debe asegurarse de que no pueda ocurrir un bloqueo mutuo (deadlock) antes de invocar la devolución de llamada del par, en caso de que el par invoque alguna de estas operaciones. Además, el propietario debe evitar llamadas recursivas a las devoluciones de llamada de finalización.
