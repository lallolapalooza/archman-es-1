NOMBRE

fi_msg - Operaciones de transferencia de datos de mensajes

fi_recv / fi_recvv / fi_recvmsg
Publica un búfer para recibir un mensaje entrante

fi_send / fi_sendv / fi_sendmsg fi_inject / fi_senddata : Inicia una operación para enviar un mensaje

SINOPSIS

#include <rdma/fi_endpoint.h>
ssize_t fi_recv(struct fid_ep *ep, void * buf, size_t len,
    void *desc, fi_addr_t src_addr, void *context);
ssize_t fi_recvv(struct fid_ep *ep, const struct iovec *iov, void **desc,
    size_t count, fi_addr_t src_addr, void *context);
ssize_t fi_recvmsg(struct fid_ep *ep, const struct fi_msg *msg,
    uint64_t flags);
ssize_t fi_send(struct fid_ep *ep, const void *buf, size_t len,
    void *desc, fi_addr_t dest_addr, void *context);
ssize_t fi_sendv(struct fid_ep *ep, const struct iovec *iov,
    void **desc, size_t count, fi_addr_t dest_addr, void *context);
ssize_t fi_sendmsg(struct fid_ep *ep, const struct fi_msg *msg,
    uint64_t flags);
ssize_t fi_inject(struct fid_ep *ep, const void *buf, size_t len,
    fi_addr_t dest_addr);
ssize_t fi_senddata(struct fid_ep *ep, const void *buf, size_t len,
    void *desc, uint64_t data, fi_addr_t dest_addr, void *context);
ssize_t fi_injectdata(struct fid_ep *ep, const void *buf, size_t len,
    uint64_t data, fi_addr_t dest_addr);

ARGUMENTOS

ep
Punto de conexión de la red en el que iniciar el envío o publicar el búfer de recepción.
buf
Búfer de datos para enviar o recibir.
len
Longitud del búfer de datos a enviar o recibir, especificada en bytes. Las transferencias válidas van desde 0 bytes hasta el max_msg_size del punto de conexión.
iov
Búfer de datos vectorial.
count
Número de entradas de datos vectoriales.
desc
Descriptor asociado con el búfer de datos. Véase fi_mr(3).
data
Datos de CQ remotos a transferir con el mensaje enviado.
dest_addr
Dirección de destino para transferencias sin conexión. Se ignora para los puntos de conexión conectados.
src_addr
Aplica solo a los puntos de conexión sin conexión configurados con FI_DIRECTED_RECV. Para todas las demás configuraciones de puntos de conexión, src_addr se ignora. src_addr define la dirección de origen desde la que recibir. De forma predeterminada, src_addr se trata como una dirección de punto de conexión de origen (es decir, fi_addr_t devuelto por fi_av_insert / fi_av_insertsvc / fi_av_remove). Si se especifica el indicador FI_AUTH_KEY con fi_recvmsg, src_addr se trata como una clave de autorización de origen (es decir, fi_addr_t devuelto por fi_av_insert_auth_key). Si se establece en FI_ADDR_UNSPEC, cualquier dirección de origen puede coincidir.
msg
Descriptor de mensaje para operaciones de envío y recepción.
flags
Indicadores adicionales a aplicar para la operación de envío o recepción.
context
Puntero especificado por el usuario para asociar con la operación. Este parámetro se ignora si la operación no generará una finalización exitosa, a menos que un indicador de operación especifique que el parámetro de contexto debe usarse para la entrada requerida.

DESCRIPCIÓN

Las funciones de envío – fi_send, fi_sendv, fi_sendmsg, fi_inject y fi_senddata – se utilizan para transmitir un mensaje de un punto de conexión a otro. La principal diferencia entre las funciones de envío es el número y tipo de parámetros que aceptan como entrada. De lo contrario, realizan la misma función general. Los mensajes enviados mediante operaciones fi_msg son recibidos por un punto de conexión remoto en un búfer publicado para recibir tales mensajes.

Las funciones de recepción – fi_recv, fi_recvv, fi_recvmsg – publican un búfer de datos en un punto de conexión para recibir mensajes entrantes. De manera similar a las operaciones de envío, las operaciones de recepción funcionan de forma asíncrona. Los usuarios no deben tocar el/los búfer(es) de datos publicados hasta que la operación de recepción haya finalizado.

Un punto de conexión debe estar habilitado antes de que una aplicación pueda publicar operaciones de envío o recepción en él. Para los puntos de conexión conectados, los búferes de recepción pueden publicarse antes de que se llame a connect o accept en el punto de conexión. Esto asegura que los búferes estén disponibles para recibir datos entrantes inmediatamente después de que se haya establecido la conexión.

Las operaciones de mensaje completadas se informan al usuario a través de uno o más colectores de eventos asociados con el punto de conexión. Los usuarios proporcionan contextos que se asocian con cada operación y se devuelven al usuario como parte del evento de finalización. Véase fi_cq para detalles de eventos de finalización.

fi_send

La llamada fi_send transfiere los datos contenidos en el búfer de datos especificado por el usuario a un punto de conexión remoto, manteniendo los límites de los mensajes.

fi_sendv

La llamada fi_sendv añade soporte para una lista de dispersión-agrupamiento (scatter-gather) a fi_send. El fi_sendv transfiere el conjunto de búferes de datos referenciados por el parámetro iov a un punto de conexión remoto como un solo mensaje.

fi_sendmsg

La llamada fi_sendmsg admite transferencias de datos sobre puntos de conexión conectados y sin conexión, con la capacidad de controlar la operación de envío en cada llamada mediante el uso de indicadores. La función fi_sendmsg toma una struct fi_msg como entrada.

struct fi_msg {
    const struct iovec *msg_iov; /* scatter-gather array */
    void               **desc;   /* local request descriptors */
    size_t             iov_count;/* # elements in iov */
    fi_addr_t          addr;     /* optional endpoint address */
    void               *context; /* user-defined context */
    uint64_t           data;     /* optional message data */
};

fi_inject

La llamada de inyección de envío es una versión optimizada de fi_send con las siguientes características. El búfer de datos está disponible para su reutilización inmediatamente al regresar de la llamada, y no se escribirá ninguna entrada de CQ si la transferencia se completa con éxito.

Conceptualmente, esto significa que la función fi_inject se comporta como si el indicador de transferencia FI_INJECT estuviera establecido, las finalizaciones selectivas estuvieran habilitadas y el indicador FI_COMPLETION no estuviera especificado. Nótese que la entrada de CQ se suprimirá incluso si el comportamiento predeterminado del punto de conexión es escribir entradas de CQ para todas las finalizaciones exitosas. Véase la discusión de indicadores más abajo para más detalles. El tamaño de mensaje solicitado que puede usarse con fi_inject está limitado por inject_size.

Si FI_HMEM está habilitado, la llamada fi_inject solo puede aceptar un búfer con iface igual a FI_HMEM_SYSTEM si el proveedor requiere el mr_mode FI_MR_HMEM. Esta limitación se aplica a todas las llamadas fi_*inject* y no afecta cómo se informa inject_size.

fi_senddata

La llamada de envío de datos es similar a fi_send, pero permite el envío de datos de CQ remotos (véase el indicador FI_REMOTE_CQ_DATA) como parte de la transferencia.

fi_injectdata

La llamada de inyección de datos es similar a fi_inject, pero permite el envío de datos de CQ remotos (véase el indicador FI_REMOTE_CQ_DATA) como parte de la transferencia.

fi_recv

La llamada fi_recv publica un búfer de datos en la cola de recepción del punto de conexión correspondiente. Las recepciones publicadas se buscan en el orden en que fueron publicadas para hacer coincidir los envíos. Se mantienen los límites de los mensajes. El orden en que se completan las recepciones depende del tipo de punto de conexión y del protocolo. Para los puntos de conexión sin conexión, el parámetro src_addr puede usarse para indicar que un búfer debe publicarse para recibir datos entrantes de un punto de conexión remoto específico.

NAME

fi_recvmsg, fi_sendmsg

SYNOPSIS

#include <rdma/fabric.h>

SymmetricInvocation:

ssize_t fi_recvmsg(struct fi_endpoint *endpt, struct fi_msg *msg,
    uint64_t flags);
ssize_t fi_sendmsg(struct fi_endpoint *endpt, struct fi_msg *msg,
    uint64_t flags);

ARGUMENTS

endpt
The target fabric endpoint.
msg
The message descriptor containing data buffers, context, and addressing information.
flags
Optional flags that modify the behavior of the send or receive operation.

DESCRIPTION

The fi_recvmsg and fi_sendmsg functions are used to post receive and send operations, respectively. Both functions utilize a struct fi_msg to describe the operation.

The struct fi_msg is defined as follows:

struct fi_msg {
    struct fi_iocontroldata *data; /* Data descriptor for send/recv */
    struct iovec *iov;           /* Array of scatter/gather buffers */
    void **desc;                 /* Array of memory region descriptors */
    size_t iov_count;            /* Number of iovec entries */
    size_t buf_count;            /* Number of buffers */
    struct fi_addr *src_addr;    /* Source address */
    void *addr;                  /* Source address (for connectionless) */
    size_t addrlen;              /* Source address length */
    void *recv_context;          /* User context for receive */
    uint64_t data_tag;           /* Data tag for match */
};

The fi_sendmsg function transmits data from the buffers referenced by the iov parameter to the destination specified in the msg structure. The iov parameter points to an array of iovec structures, each describing a memory buffer. The iov_count member specifies the number of entries in the iov array.

The fi_recvmsg function posts receive buffers that reference the data buffers specified by the iov parameter to receive incoming data.

fi_recvmsg

The fi_recvmsg call supports posting buffers over both connected and connectionless endpoints, with the ability to control the receive operation per call through the use of flags. The fi_recvmsg function takes a struct fi_msg as input.

FLAGS

The fi_recvmsg and fi_sendmsg calls allow the user to specify flags which can change the default message handling of the endpoint. Flags specified with fi_recvmsg / fi_sendmsg override most flags previously configured with the endpoint, except where noted (see fi_endpoint.3). The following list of flags are usable with fi_recvmsg and/or fi_sendmsg.

FI_REMOTE_CQ_DATA
Applies to fi_sendmsg. Indicates that remote CQ data is available and should be sent as part of the request. See fi_getinfo for additional details on FI_REMOTE_CQ_DATA. This flag is implicitly set for fi_senddata and fi_injectdata.
FI_COMPLETION
Indicates that a completion entry should be generated for the specified operation. The endpoint must be bound to a completion queue with FI_SELECTIVE_COMPLETION that corresponds to the specified operation, or this flag is ignored.
FI_MORE
Indicates that the user has additional requests that will immediately be posted after the current call returns. Use of this flag may improve performance by enabling the provider to optimize its access to the fabric hardware.
FI_INJECT
Applies to fi_sendmsg. Indicates that the outbound data buffer should be returned to user immediately after the send call returns, even if the operation is handled asynchronously. This may require that the underlying provider implementation copy the data into a local buffer and transfer out of that buffer. This flag can only be used with messages smaller than inject_size.
FI_MULTI_RECV
Applies to posted receive operations. This flag allows the user to post a single buffer that will receive multiple incoming messages. Received messages will be packed into the receive buffer until the buffer has been consumed. Use of this flag may cause a single posted receive operation to generate multiple events as messages are placed into the buffer. The placement of received data into the buffer may be subjected to provider specific alignment restrictions.

The buffer will be released by the provider when the available buffer space falls below the specified minimum (see FI_OPT_MIN_MULTI_RECV). Note that an entry to the associated receive completion queue will always be generated when the buffer has been consumed, even if other receive completions have been suppressed (i.e. the Rx context has been configured for FI_SELECTIVE_COMPLETION). See the FI_MULTI_RECV completion flag fi_cq(3).

FI_INJECT_COMPLETE
Applies to fi_sendmsg. Indicates that a completion should be generated when the source buffer(s) may be reused.
FI_TRANSMIT_COMPLETE
Applies to fi_sendmsg and fi_recvmsg. For sends, indicates that a completion should not be generated until the operation has been successfully transmitted and is no longer being tracked by the provider. For receive operations, indicates that a completion may be generated as soon as the message has been processed by the local provider, even if the message data may not be visible to all processing elements. See fi_cq(3) for target side completion semantics.
FI_DELIVERY_COMPLETE
Applies to fi_sendmsg. Indicates that a completion should be generated when the operation has been processed by the destination.
FI_FENCE
Applies to transmits. Indicates that the requested operation, also known as the fenced operation, and any operation posted after the fenced operation will be deferred until all previous operations targeting the same peer endpoint have completed. Operations posted after the fencing will see and/or replace the results of any operations initiated prior to the fenced operation.

The ordering of operations starting at the posting of the fenced operation (inclusive) to the posting of a subsequent fenced operation (exclusive) is controlled by the endpoint’s ordering semantics.

FI_MULTICAST
Applies to transmits. This flag indicates that the address specified as the data transfer destination is a multicast address. This flag must be used in all multicast transfers, in conjunction with a multicast fi_addr_t.
FI_AUTH_KEY
Only valid with domains configured with FI_AV_AUTH_KEY and connectionless endpoints configured with FI_DIRECTED_RECV. When used with fi_recvmsg, this flag denotes that the src_addr is an authorization key fi_addr_t instead of an endpoint fi_addr_t.

NOTES

If an endpoint has been configured with FI_MSG_PREFIX, the application must include buffer space of size msg_prefix_size, as specified by the endpoint attributes. The prefix buffer must occur at the start of the data referenced by the buf parameter, or be referenced by the first IO vector. Message prefix space cannot be split between multiple IO vectors. The size of the prefix buffer should be included as part of the total buffer length.

RETURN VALUE

Returns 0 on success. On error, a negative value corresponding to fabric errno is returned. Fabric errno values are defined in rdma/fi_errno.h.

See the discussion below for details handling FI_EAGAIN.

ERRORS

-FI_EAGAIN
Indicates that the underlying provider currently lacks the resources needed to initiate the requested operation. The reasons for a provider returning FI_EAGAIN are varied. However, common reasons include insufficient internal buffering or full processing queues.

Insufficient internal buffering is often associated with operations that use FI_INJECT. In such cases, additional buffering may become available as posted operations complete.

Full processing queues may be a temporary state related to local processing (for example, a large message is being transferred), or may be the result of flow control. In the latter case, the queues may remain blocked until additional resources are made available at the remote side of the transfer.

In all cases, the operation may be retried after additional resources become available. When using FI_PROGRESS_MANUAL, the application must check for transmit and receive completions after receiving FI_EAGAIN as a return value, independent of the operation which failed. This is also strongly recommended when using FI_PROGRESS_AUTO, as acknowledgements or flow control messages may need to be processed in order to resume execution.
