DESCRIPCIÓ

N

Un dominio de acceso generalmente se refiere a una interfaz de red (NIC) física o virtual o un puerto de hardware; sin embargo, un dominio puede abarcar múltiples componentes de hardware para propósitos de conmutación por error o distribución de datos. Un dominio define el límite para asociar diferentes recursos juntos. Los recursos de la fabrica que pertenecen al mismo dominio pueden compartir

recursos.

fi_set_op

s

fi_set_ops asigna devoluciones de llamada que un proveedor debe invocar en lugar de realizar tareas seleccionadas. Esto permite a los usuarios modificar o controlar un comportamiento predeterminado del proveedor. Conceptualmente, permite al usuario enganchar funciones específicas usadas por un proveedor y reemplazarlas con las suyas

propias.

Las operaciones que se modifican se identifican usando una cadena de caracteres conocida, pasada como el parámetro name. El formato del parámetro ops depende del valor name. El parámetro ops hará referencia a una estructura que contiene las devoluciones de llamada y otros campos necesarios por el proveedor para invocar las funciones del

usuario.

Si un proveedor acepta la anulación, devolverá FI_SUCCESS. Si la anulación es desconocida o no está soportada, el proveedor devolverá -FI_ENOSYS. Las anulaciones deben establecerse antes de asignar recursos en el

dominio.

Las siguientes operaciones fi_set_ops y estructuras de devolución de llamada correspondientes están

definidas.

Soporte de multiprocesamiento por hilos

(threading)

El modelo de hilos especifica el nivel de serialización requerido de una aplicación al usar las interfaces de transferencia de datos de libfabric. Las interfaces de control siempre se consideran seguras para hilos, a menos que el modelo de progreso de control sea FI_PROGRESS_CONTROL_UNIFIED. Una interfaz de control segura para hilos permite que múltiples hilos hagan progresar la interfaz de control y (dependiendo del modelo de hilos seleccionado) que uno o más hilos hagan progresar las interfaces de datos al mismo tiempo. Las aplicaciones que pueden garantizar la serialización en su acceso a los recursos e interfaces asignados por el proveedor permiten a un proveedor eliminar bloqueos de nivel

inferior.
FI_THREAD_COMPLET
ION
El modelo de hilos de finalización es el más adecuado para aplicaciones multiproceso que usan puntos de escalabilidad y desean una operación sin bloqueos. L
as aplicaciones deben serializar el acceso a todos los objetos que están asociados por un mecanismo de finalización común (por ejemplo, contextos de transmi
sión y recepción vinculados a la misma CQ o contador). Se recomienda que los proveedores que soportan puntos de escalabilidad soporten este modelo de hilos.

Las aplicaciones que quieran aprovechar FI_THREAD_COMPLETION deben dedicar contextos de transmisión, contextos de recepción, colas de finalización e individuales a hilos

individuales.
FI_THREAD_DOM
AIN
El modelo de hilos de dominio es el más adecuado para aplicaciones de un solo hilo y aplicaciones multiproceso que usan puntos de extremo estándar y desean una operación sin bloqueos. Las aplicaciones deben serializar el acceso a todos los objetos bajo el mismo dominio. Esto incluye puntos de extremo, contextos de transmisión y recepción, colas de finalización y contadores, y regiones de memoria
registradas.
FI_THREAD_ENDPOINT
(obsoleto)
El modelo de hilos de punto de extremo es similar a FI_THREAD_FID, pero con la restricción adicional de que se requiere serialización al acceder al mismo punto de extremo, incluso si se usan múltiples contextos de transmisión y
recepción.
FI_THREAD_FID
(obsoleto)
Un modelo de serialización de descriptor de tejido (FID) requiere que las aplicaciones serialicen el acceso a los recursos individuales del tejido asociados con las operaciones de transferencia de datos y las finalizaciones. Para el acceso al punto de extremo, la serialización solo se requiere al acceder al mismo flujo de datos del punto de extremo. Múltiples hilos pueden iniciar transferencias en diferentes contextos de transmisión o en el mismo punto de extremo sin serializar, y no se requiere serialización entre el envío de solicitudes de transmisión de datos y las operaciones de recepción de
datos.
FI_THREAD_SA
FE
Un modelo de serialización seguro para hilos permite que una aplicación multiproceso acceda a cualquier recurso asignado a través de cualquier interfaz sin restricciones. Se requiere que todos los proveedores soporten
FI_THREAD_SAFE.
FI_THREAD_UNS
PEC
Este valor indica que no se ha definido ningún modelo de hil
os. Puede usarse en sugerencias de entrada para la llamada f
i_getinfo. Cuando se especifica, los proveedores devolverán u

Modelos de progreso

(progress)

El progreso es la capacidad de la implementación subyacente de completar el procesamiento de una solicitud asíncrona. En muchos casos, el procesamiento de una solicitud asíncrona requiere el uso del procesador del host. Por ejemplo, un mensaje recibido puede necesitar ser emparejado con el búfer correcto, o una solicitud agotada por tiempo puede necesitar ser retransmitida. Por razones de rendimiento, puede ser indeseable que el proveedor asigne un hilo para este propósito, lo que competiría con los hilos de la

aplicación.

El progreso de control indica el método que usa el proveedor para avanzar en operaciones de control asíncronas. Las operaciones de control son funciones que no involucran directamente la transferencia de datos de la aplicación entre puntos de extremo. Incluyen rutinas de vector de direcciones, registro de memoria y gestión de

conexiones.

El progreso de datos indica el método que usa el proveedor para avanzar en operaciones de transferencia de datos. Esto incluye cola de mensajes, RMA, mensajería etiquetada y operaciones atómicas, junto con su procesamiento de

finalización.

El campo de progreso define el comportamiento tanto de las operaciones de control como de las de datos. Para aplicaciones que requieren portabilidad de compilación entre las series libfabric versión 1 y versión 2, el campo de progreso puede referenciarse como

data_progress.

El progreso frecuentemente requiere que se tome acción tanto en el lado de transmisión como en el de recepción de una operación. Esto suele ser un requisito para transferencias confiables, como resultado del procesamiento de reintentos y reconocimientos

.

Para equilibrar entre rendimiento y facilidad de uso, se definen los siguientes modelos de

progreso.
FI_PROGRESS_A
UTO
Este modelo de progreso indica que el proveedor hará avanzar una operación asíncrona sin mayor intervención de la aplicación. C
uando FI_PROGRESS_AUTO se proporciona como salida de fi_getinfo en ausencia de cualquier sugerencia de progreso, a menudo indic
a que la funcionalidad deseada está implementada por el hardware del proveedor o es un servicio estándar del sistema operativo.

Se recomienda que los proveedores soporten FI_PROGRESS_AUTO. Sin embargo, si un proveedor no soporta nativamente el progreso automático, forzar el uso de FI_THREAD_AUTO puede resultar en la asignación de hilos por debajo de las interfaces del

tejido.

Tenga en cuenta que las versiones anteriores de la biblioteca requerían que los proveedores soportaran FI_PROGRESS_AUTO. Sin embargo, en algunos casos los hilos de progreso no pueden bloquearse cuando la comunicación está inactiva, lo que resulta en hilos girando en funciones de progreso. Como resultado, esos proveedores solo soportaban FI_PROGRESS_MANUAL

.
FI_PROGRESS_MAN
UAL
Este modelo de progreso indica que el proveedor requiere el uso de un hilo de la aplicación para completar una solicitud asíncrona. Cuando se establece el progreso manual,
el proveedor intentará avanzar una operación asíncrona cuando la aplicación intente esperar o leer una cola de eventos, cola de finalización o contador donde se reportará
la operación completada. El progreso también ocurre cuando la aplicación procesa un conjunto de sondeo o espera que ha sido asociado con la cola de eventos o finalización.

Solo las operaciones de espera definidas por la interfaz del tejido resultarán en que una operación progrese. Las funciones de espera del sistema operativo o externas, como select, poll o rutinas de pthread, no pueden

hacerlo.

Los requisitos de progreso manual no solo se aplican a los puntos de extremo que inician operaciones de transmisión, sino también a los puntos de extremo que pueden ser el destino de tales operaciones. Esto se mantiene verdadero incluso si el punto de extremo destino no generará eventos de finalización para las operaciones. Por ejemplo, un punto de extremo que actúa puramente como destino de operaciones RMA o atómicas que usa progreso manual puede aún necesitar asistencia de la aplicación para procesar operaciones

recibidas.
FI_PROGRESS_CONTROL_UNIF
IED
Este modelo de progreso indica que el usuario sincronizará el progreso de las operaciones de datos y control por sí mismo (es decir, esto permite que la interfaz de control NO sea segura para hilos). Implica progreso manual, y cuando se combina con threading=FI_THREAD_DOMAIN/FI_THREAD_COMPLETION permite a Libfabric eliminar todo el bloqueo en la ruta crítica de progreso de
datos.
FI_PROGRESS_UNS
PEC
Este valor indica que no se ha de
finido ningún modelo de progreso.

Gestión de recursos

(resource_mgmt)

La gestión de recursos (RM) es el soporte del proveedor y del protocolo para proteger contra el desbordamiento de recursos locales y remotos. Esto incluye contextos de transmisión locales y remotos, contextos de recepción, colas de finalización y búfers de datos de origen y

destino.

Cuando está habilitada, las aplicaciones reciben algún nivel de protección contra el desbordamiento de colas del proveedor y búfers de datos locales y remotos. Tal soporte puede estar construido directamente en el hardware y/o protocolo de red, pero también puede requerir que se habiliten verificaciones en el software del proveedor. Al deshabilitar la gestión de recursos, la aplicación asume toda la responsabilidad de prevenir el desbordamiento de colas y búfers, pero hacerlo puede permitir a un proveedor eliminar llamadas de sincronización internas, como variables atómicas o

bloqueos.

Debe notarse que incluso si la gestión de recursos está deshabilitada, la implementación del proveedor y el protocolo aún pueden proporcionar algún nivel de protección contra desbordamientos. Sin embargo, dicha protección no está garantizada. Se definen los siguientes valores para la gestión de

recursos.
FI_RM_DISABL
ED
El proveedor es libre de seleccionar una implementación y protocolo que no protejan contra el desbordamiento de recursos. La aplicación es responsable de la protección de
recursos.
FI_RM_ENABL
ED
La gestión de recursos está habilitada para este dominio del
proveedor.
FI_RM_UNSP
EC
Este valor indica que no se ha definido ningún m
odelo de gestión de recursos. Puede usarse en su
gerencias de entrada para la llamada fi_getinfo.

Ctx
Se refiere a los contextos de transmisión/recepción cuando se envía una operación de transferencia de datos. Cuando RM está habilitado, el intento de enviar una solicitud fallará si el contexto está lleno. Si RM está deshabilitado, ocurrirá un error no definido (específico del proveedor). Dichos errores deben considerarse fatales para el contexto, y las aplicaciones deben tomar medidas para evitar desbordamientos de la

CQ
Se refiere a la cola de finalización asociada con el contexto Tx o Rx cuando una operación local se completa. Cuando RM está deshabilitado, las aplicaciones deben asegurarse de que las colas de finalización no se desborden. Cuando ocurre un desbordamiento, ocurrirá un error no definido, pero fatal, que afectará a todos los puntos finales asociados con la CQ. Los desbordamientos se pueden evitar dimensionando las CQ adecuadamente o retrasando la publicación de una operación de transferencia de datos a menos que haya espacio en la CQ para almacenar su finalización. Cuando RM está habilitado, los proveedores pueden usar diferentes mecanismos para prevenir desbordamientos de CQ. Esto incluye fallar (devolver -FI_EAGAIN) la publicación de operaciones que podrían resultar en desbordamientos de CQ, o reintentar internamente las solicitudes (lo cual será oculto a la aplicación). Vea las notas al final de esta sección con respecto a las restricciones de gestión de recursos de

EP de destino / Sin búfer
Rx
EP de destino se refiere a los recursos asociados con el punto final que es el destino de una operación de transmisión. Esto incluye la cola de recepción del punto final de destino, los búferes de recepción publicados (sin búferes Rx), la cola de finalización del lado de recepción y otras colas de procesamiento de paquetes relacionadas. El comportamiento definido es el que ve el iniciador de una solicitud. Para los puntos finales FI_EP_DGRAM, si las colas del EP de destino no pueden aceptar mensajes entrantes, los mensajes recibidos serán descartados. Para los puntos finales confiables, si RM está deshabilitado, la operación de transmisión se completará con error. Un proveedor puede optar por devolver una finalización con error con el código de error FI_ENORX para esa operación de transmisión para que pueda ser reintentada. Si RM está habilitado, el proveedor reintentará internamente la
operación.
Desbordamiento de búfer
Rx
Esto se refiere a los búferes publicados para recibir mensajes etiquetados o no etiquetados entrantes, con el comportamiento definido desde el punto de vista del emisor. El comportamiento para manejar mensajes recibidos que son más grandes que los búferes proporcionados por la aplicación es específico del proveedor. Los proveedores pueden truncar el mensaje y reportar una finalización exitosa, o fallar la operación. Para los puntos finales de datagrama, los envíos fallidos resultarán en que el mensaje sea descartado. Para los puntos finales confiables, las operaciones de envío pueden completarse con éxito, pero ser truncadas en el lado de recepción. Esto puede ocurrir cuando el lado de destino almacena en búfer los datos recibidos hasta que un búfer de aplicación esté disponible. El estado de finalización también puede depender del modelo de finalización seleccionado por la aplicación (por ejemplo, FI_DELIVERY_COMPLETE versus FI_TRANSMIT_COMPLETE)
.

RMA

A diferencia de las operaciones de envío, las operaciones RMA que intentan acceder a una dirección de memoria que no está registrada para dichas operaciones, o intentan acceder fuera de la región de memoria de destino, fallarán, resultando en un error de
transmisión.

inaccesible
El punto final inaccesible es un escenario específico de conexión sin conexión donde las operaciones de transmisión se emiten a puntos finales de destino inaccesibles.
Dichos escenarios incluyen no hay ruta al host o NIC de destino caído. Para los puntos finales FI_EP_DGRAM, las operaciones de transmisión dirigidas a un punto final ina
ccesible tendrán la operación descartada. Para FI_EP_RDM, las operaciones de destino dirigidas a un punto final inaccesible resultarán en un error de transmisión.

Cuando ocurre un error de gestión de recursos en un punto final conectado, el punto final transicionará a un estado deshabilitado y la conexión se desmantelará. Un punto final deshabilitado descartará cualquier operación en cola o en

vuelo.

El comportamiento de los errores de gestión de recursos en los puntos finales sin conexión depende del tipo de error. Si RM está deshabilitado y uno de los siguientes errores ocurre, el punto final será deshabilitado: Tx Ctx, Rx Ctx, Tx CQ o Rx CQ. Para otros errores (EP de destino, sin búfer Rx, etc.), la operación puede fallar, pero el punto final permanecerá habilitado. Un punto final deshabilitado descartará o fallará cualquier operación en cola o en vuelo. Además, un punto final deshabilitado debe ser re-habilitado antes de que acepte nuevas operaciones de transferencia de

datos.

Hay una restricción notable en las protecciones ofrecidas por la gestión de recursos. Esto ocurre cuando la gestión de recursos está habilitada en un punto final que ha sido vinculado a cola(s) de finalización usando el indicador FI_SELECTIVE_COMPLETION. Las operaciones publicadas en dicho punto final pueden especificar que una finalización exitosa no deb

e generar una entrada en la cola de finalización correspondiente. (Es decir, la operación deja el indicador FI_COMPLETION sin establecer). En tales situaciones, el proveedor no está obligado a reservar una entrada en la cola de finalización para manejar el caso en que la operación falle y sí genere una entrada de CQ, lo que efectivamente requeriría ra
strear la operación hasta su finalización. Las aplicaciones preocupadas por evitar desbordamientos de CQ en la ocurrencia de errores deben asegurar que haya espacio suficiente en la CQ para reportar operaciones fallidas. Esto generalmente se puede lograr dimensionando la CQ al menos al mismo tamaño que la(s) cola(s) de punto final vinculada(s) a ella.

Modo de Registro de Memoria (mr_mode)

Define los bits de modo específicos del registro de memoria utilizados con este dominio. Los detalles completos sobre las opciones del modo MR están disponibles en fi_mr(3). Se pueden especificar los siguientes valores.

FI_MR_ALLOCATED
Indica que el registro de memoria se realiza sobre búferes de datos asignados, y que las páginas físicas deben respaldar todas las direcciones virtuales que se están registrando.
FI_MR_COLLECTIVE
Requiere que los búferes de datos pasados a operaciones colectivas se registren explícitamente para operaciones colectivas utilizando la bandera FI_COLLECTIVE.
FI_MR_ENDPOINT
El registro de memoria se realiza a nivel del punto final, en lugar de a nivel del dominio.
FI_MR_LOCAL
El proveedor está optimizado para que las aplicaciones registren memoria para búferes de datos accedidos localmente. Los búferes de datos utilizados en operaciones de envío y recepción y como búfer de origen para operaciones RMA y atómicas deben ser registrados por la aplicación para los dominios de acceso abiertos con esta capacidad.
FI_MR_MMU_NOTIFY
Indica que la aplicación es responsable de notificar al proveedor cuando las tablas de páginas que hacen referencia a una región de memoria registrada pueden haber sido actualizadas.
FI_MR_PROV_KEY
Las claves de registro de memoria son seleccionadas y devueltas por el proveedor.
FI_MR_RAW
El proveedor requiere una configuración adicional como parte de su proceso de registro de memoria. Este modo es requerido por los proveedores que utilizan una clave de memoria de más de 64 bits.
FI_MR_RMA_EVENT
Indica que las regiones de memoria asociadas con contadores de finalización deben habilitarse explícitamente después de estar enlazadas a cualquier contador.
FI_MR_UNSPEC (obsoleto)
Definido para compatibilidad - versiones de biblioteca 1.4 y anteriores. Establecer mr_mode a 0 indica que se solicitan y soportan FI_MR_BASIC o FI_MR_SCALABLE.
FI_MR_VIRT_ADDR
Las regiones de memoria registradas son referenciadas por pares utilizando la dirección virtual de la región de memoria registrada, en lugar de un desplazamiento basado en 0.
FI_MR_BASIC (obsoleto)
Definido para compatibilidad - versiones de biblioteca 1.4 y anteriores. Solo se solicitan o soportan operaciones básicas de registro de memoria. Este modo es equivalente a que las banderas FI_MR_VIRT_ADDR, FI_MR_ALLOCATED y FI_MR_PROV_KEY estén establecidas en versiones de biblioteca posteriores. Esta bandera no se puede usar en conjunción con otros bits de mr_mode.
FI_MR_SCALABLE (obsoleto)
Definido para compatibilidad - versiones de biblioteca 1.4 y anteriores. Solo se solicitan o soportan operaciones de registro de memoria escalables. El registro escalable utiliza direccionamiento basado en desplazamiento, con claves de memoria seleccionables por la aplicación. Para las versiones de biblioteca 1.5 y posteriores, este es el valor predeterminado si no se establecen bits de mr_mode. Esta bandera no se puede usar en conjunción con otros bits de mr_mode.

Los búferes utilizados en operaciones de transferencia de datos pueden requerir notificar al proveedor de su uso antes de que pueda ocurrir una transferencia de datos. El campo mr_mode indica el tipo de registro de memoria que se requiere y cuándo es necesario el registro. Las aplicaciones que requieren el uso de un modo de registro específico deben establecer el atributo de dominio mr_mode al valor necesario al llamar a fi_getinfo. El valor FI_MR_UNSPEC puede usarse para indicar soporte para cualquier modo de registro.

Tamaño de Clave MR (mr_key_size)

Tamaño de la clave de acceso remoto de la región de memoria, en bytes. Las aplicaciones que solicitan su propia clave MR deben seleccionar un valor dentro del rango especificado por este valor. Los tamaños de clave mayores de 8 bytes requieren el uso del bit de modo FI_RAW_KEY.

Tamaño de Datos CQ (cq_data_size)

Las aplicaciones pueden incluir un pequeño mensaje con una transferencia de datos que se coloca directamente en una cola de finalización remota como parte de un evento de finalización. Esto se conoce como datos CQ remotos (a veces denominado datos inmediatos). Este campo indica el número de bytes que el proveedor soporta para datos CQ remotos. Si es compatible (se devuelve un valor distinto de cero), el tamaño mínimo de los datos CQ remotos debe ser de al menos 4 bytes.

Conteo de Colas de Finalización (cq_cnt)

El número óptimo de colas de finalización soportadas por el dominio, en relación con cualquier atributo de CQ especificado o predeterminado. El valor cq_cnt puede ser un valor fijo del número máximo de CQs soportados por el hardware subyacente, o puede ser un valor dinámico, basado en los atributos predeterminados de una CQ asignada, como el tamaño y el formato de datos de la CQ.

Conteo de Puntos Finales (ep_cnt)

El número total de puntos finales soportados por el dominio, en relación con cualquier atributo de punto final especificado o predeterminado. El valor ep_cnt puede ser un valor fijo del número máximo de puntos finales soportados por el hardware subyacente, o puede ser un valor dinámico, basado en los atributos predeterminados de un punto final asignado, como las capacidades y el tamaño del punto final. El conteo de puntos finales es el número de puntos finales direccionables soportados por el proveedor. Los proveedores devuelven límites de capacidad basados en las capacidades máximas de hardware configuradas. Los proveedores no pueden predecir todas las posibles limitaciones del sistema sin conocimiento a posteriori adquirido durante el tiempo de ejecución que limitará aún más estos máximos de hardware (por ejemplo, consumo de memoria de la aplicación, uso de FD, etc.).

Conteo de Contextos de Transmisión (tx_ctx_cnt)

El número de colas de comandos salientes soportadas de manera óptima por el proveedor. Para un proveedor de bajo nivel, esto representa el número de colas de comandos al hardware y/o el número de motores de transmisión paralelos efectivamente soportados por el hardware y las cachés. Las aplicaciones que asignan más contextos de transmisión que este valor terminarán compartiendo recursos subyacentes. Por defecto, hay un solo contexto de transmisión asociado con cada punto final, pero en un modelo de uso avanzado, un punto final puede configurarse con múltiples contextos de transmisión.

Conteo de Contextos de Recepción (rx_ctx_cnt)

El número de colas de procesamiento entrantes soportadas de manera óptima por el proveedor. Para un proveedor de bajo nivel, esto representa el número de colas de hardware que pueden ser utilizadas efectivamente para procesar paquetes entrantes. Las aplicaciones que asignan más contextos de recepción que este valor terminarán compartiendo recursos subyacentes. Por defecto, un solo contexto de recepción se asocia con cada punto final, pero en un modelo de uso avanzado, un punto final puede configurarse con múltiples contextos de recepción.

Contexto de Transmisión Máximo por Punto Final (max_ep_tx_ctx)

El número máximo de contextos de transmisión que pueden asociarse con un punto final.

Contexto de Recepción Máximo por Punto Final (max_ep_rx_ctx)

El número máximo de contextos de recepción que pueden asociarse con un punto final.

Compartición Máxima de Contexto de Transmisión (max_ep_stx_ctx)

El número máximo de puntos finales que pueden asociarse con un contexto de transmisión compartido.

Compartición Máxima de Contexto de Recepción (max_ep_srx_ctx)

El número máximo de puntos finales que pueden asociarse con un contexto de recepción compartido.

Conteo de Contadores (cntr_cnt)

El número óptimo de contadores de finalización soportados por el dominio. El valor cq_cnt puede ser un valor fijo del número máximo de contadores soportados por el hardware subyacente, o puede ser un valor dinámico, basado en los atributos predeterminados del dominio.

Límite IOV de MR (mr_iov_limit)

Este es el número máximo de vectores IO (elementos de dispersión-agrupación) que puede referenciar una sola operación de registro de memoria.

Capacidades (caps)

Capacidades a nivel de dominio. Las capacidades del dominio indican las características a nivel de dominio que son soportadas por el proveedor.

Las siguientes son las capacidades primarias soportadas: FI_DIRECTED_RECV : Cuando el dominio está configurado con FI_DIRECTED_RECV y FI_AV_AUTH_KEY, las regiones de memoria se pueden limitar a claves de autorización específicas.

FI_AV_USER_ID
Indica que el dominio soporta la capacidad de abrir vectores de dirección con la bandera FI_AV_USER_ID. Si esta capacidad de dominio no está establecida, los vectores de dirección no se pueden abrir con FI_AV_USER_ID. Tenga en cuenta que FI_AV_USER_ID todavía puede ser soportado a través de las llamadas de inserción de AV sin esta capacidad de dominio establecida. Ver fi_av(3).
FI_PEER
Especifica que el dominio debe soportar la importación de recursos para ser utilizados en el flujo de la API peer. El dominio debe soportar la importación de sus propios

NAME

fi_close — Close a fabric resource

SYNOPSIS

#include <rdma/fabric.h>

int fi_close(void *handle);

ARGUMENTS

handle
A pointer to a fabric resource to close. The resource can be a fabric domain, endpoint, completion queue, event queue, address vector, or memory region.

DESCRIPTION

The fi_close call is used to close and release all resources associated with a specified fabric resource handle. The handle parameter is a generic pointer that can refer to any of the Libfabric objects. The function will determine the type of object from the handle and perform the appropriate cleanup.

Closing a fabric resource is a recursive operation. For example, closing a fabric domain will implicitly close all endpoints, CQs, EQs, AVs, and MRs associated with that domain. Closing an endpoint will implicitly close its associated CQs and EQs, if they were created using the endpoint handle.

The order in which resources are closed is important. An application must close child resources before closing their parent resource. For example, an endpoint must be closed before its domain is closed. Likewise, a CQ must be closed before its domain or endpoint is closed.

If a resource is closed while it still has active operations, the behavior is undefined. Applications should ensure that all operations are completed or cancelled before closing a resource.

The fi_close call will free any memory allocated by the provider for the specified resource.

The following are the primary fabric resource types that can be passed to fi_close:

FI_DOMAINS
Fabric domains. Closing a domain will implicitly close all associated endpoints, CQs, EQs, AVs, and MRs.
FI_ENDPOINTS
Endpoints. Closing an endpoint will implicitly close its associated CQs and EQs, if they were created using the endpoint handle.
FI_CQ
Completion queues.
FI_EQ
Event queues.
FI_AV
Address vectors.
FI_MR
Memory regions.

CAPABILITIES

The fi_close call does not directly use or expose capabilities. However, the capabilities of the underlying fabric provider dictate the types of resources that can be created and closed.

For example, if a provider does not support explicit closing of CQs, then fi_close might not be applicable to CQ handles. The capabilities of a domain are described in the fi_domain(3) man page.

FI_LOCAL_COMM
Indicates support for loopback communication. This capability does not directly affect the fi_close operation itself, but it influences the types of endpoints and communication patterns that can be established and subsequently closed.
FI_REMOTE_COMM
Indicates support for network communication. Similar to FI_LOCAL_COMM, this capability affects resource creation and management, but not the fundamental operation of fi_close.
FI_SHARED_AV
Indicates support for shared address vectors. The management and closing of shared AVs follow the general rules for AVs.

Default authorization key (auth_key)

The default authorization key is associated with endpoints and memory registrations. The closing of these resources via fi_close will release any associated authorization keys, subject to the API version and provider implementation.

Default authorization key length (auth_key_size)

This attribute defines the length of the default authorization key. When a resource associated with this domain is closed, the key and its length are released.

Max Error Data Size (max_err_data)

This attribute defines the maximum size of error data. While not directly used by fi_close, it relates to error handling which might occur during resource creation or operations preceding the close operation.

Memory Regions Count (mr_cnt)

This specifies the optimal number of memory regions. When memory regions associated with a domain or endpoint are closed, this count is decremented implicitly.

Traffic Class (tclass)

This attribute specifies the default traffic class for endpoints. Closing an endpoint releases its associated traffic class settings.

Max Authorization Keys per Endpoint (max_ep_auth_key)

This attribute limits the number of authorization keys per endpoint. Closing a connectionless endpoint releases these keys.

Maximum Peer Group Id (max_group_id)

This attribute defines the maximum peer group ID. Closing an AV that uses peer groups will release associated peer group information.

RETURN VALUE

On success, fi_close returns 0. On error, a negative value corresponding to a fabric errno is returned. Fabric errno values are defined in the rdma/fi_errno.h header file.

NOTES

Applications must call fi_close on all fabric resources they create to avoid resource leaks. This includes domains, endpoints, CQs, EQs, AVs, and MRs.

It is recommended that applications perform any necessary cleanup or shutdown operations (e.g., cancelling outstanding operations, waiting for completions) before calling fi_close to ensure a clean shutdown.

Closing a resource that has already been closed results in undefined behavior.

The handle parameter must be a valid pointer to a Libfabric resource structure.
