fi_collective(3) Libfabric v2.3.1 fi_collective(3)

NOMBRE

fi_join_collective
Operación donde un subconjunto de pares se une a un nuevo grupo colectivo.
fi_barrier / fi_barrier2
Operación colectiva que no se completa hasta que todos los pares hayan entrado en la llamada de barrera.
fi_broadcast
Un único remitente transmite datos a todos los pares, incluyéndose a sí mismo.
fi_alltoall
Cada par distribuye una porción de sus datos locales a todos los pares.
fi_allreduce
Operación colectiva donde todos los pares difunden una operación atómica a todos los demás pares.
fi_allgather
Cada par envía una copia completa de sus datos locales a todos los pares.
fi_reduce_scatter
Llamada colectiva donde los datos se recopilan de todos los pares y se combinan (reducen). Los resultados de la reducción se distribuyen de vuelta a los pares, y cada par recibe una porción de los resultados.
fi_reduce
Llamada colectiva donde los datos se recopilan de todos los pares a un par raíz y se combinan (reducen).
fi_scatter
Un único remitente distribuye (dispersa) una porción de sus datos locales a todos los pares.
fi_gather
Todos los pares envían sus datos a un par raíz.
fi_query_collective
Devuelve información sobre qué operaciones colectivas son compatibles con un proveedor, y las limitaciones de la colectiva.

Grupo multicast asociado con la colectiva.
buf
Búfer de datos local que especifica el primer operando de la operación colectiva.
count
El número de elementos referenciados, donde cada elemento es el tipo de dato indicado.
datatype
Tipo de dato asociado con los operandos atómicos.
op
Operación atómica a realizar.
result
Búfer de datos local para almacenar el resultado de la operación colectiva.
desc / result_desc
Descriptor de datos asociado con el búfer de datos local y el búfer de resultado local, respectivamente.
coll_addr
Dirección que hace referencia al grupo colectivo de puntos finales.
root_addr
Punto final único que es la fuente o destino de los datos colectivos.

Banderas adicionales a aplicar para la operación atómica.
context
Puntero especificado por el usuario para asociar con la operación. Este parámetro se ignora si la operación no genera una finalización exitosa, a menos que una bandera de operación especifique que el parámetro de contexto se utilizará para la entrada requerida.

DESCRIPCIÓN

En general, las operaciones colectivas se pueden considerar como operaciones atómicas coordinadas entre un conjunto de puntos finales pares. Los lectores deben consultar la página del manual de fi_atomic(3) para obtener detalles sobre las operaciones atómicas y los tipos de datos definidos por libfabric.

Una operación colectiva es un intercambio de comunicación grupal. Involucra a múltiples pares intercambiando datos con otros pares que participan en la llamada colectiva. Las operaciones colectivas requieren una estrecha coordinación de todos los miembros participantes. Todos los participantes deben invocar la misma llamada colectiva antes de que cualquier miembro individual pueda completar su operación localmente. Como resultado, las llamadas colectivas pueden tensar la red, así como los búferes de datos locales y remotos.

Las interfaces colectivas de Libfabric se dirigen a redes que admiten la descarga de partes de la comunicación colectiva en conmutadores de red, NICs y otros dispositivos. Sin embargo, no se impone ningún requisito de implementación al proveedor.

El primer paso para utilizar una llamada colectiva es identificar los puntos finales pares que participarán. La membresía colectiva sigue uno de dos modelos, ambos compatibles con libfabric. En el primer modelo, la aplicación gestiona la membresía. Esto generalmente significa que la aplicación está realizando una operación colectiva por sí misma utilizando comunicación punto a punto para identificar a los miembros que participarán. Además, la aplicación puede estar interactuando con un administrador de recursos de red para reservar los recursos de red necesarios para ejecutar operaciones colectivas. En este modelo, la aplicación informará a libfabric que la membresía ya se ha establecido.

Un modelo separado traslada la gestión de membresía a libfabric y directamente al proveedor. En este modelo, la aplicación debe identificar qué direcciones de pares serán miembros. Esa información se transmite al proveedor de libfabric, que es responsable de coordinar la creación del grupo colectivo. En el modelo gestionado por el proveedor, el proveedor realizará generalmente la operación colectiva necesaria para establecer el grupo de comunicación e interactuará con cualquier agente de gestión de red.

En ambos modelos, la membresía colectiva se comunica al proveedor creando y configurando un conjunto de vectores de direcciones (conjunto AV). Un conjunto AV representa un subconjunto ordenado de direcciones en un vector de direcciones (AV). Los detalles sobre la creación y configuración de un conjunto AV están disponibles en fi_av_set(3).

Una vez que un conjunto AV ha sido programado con la información de membresía colectiva, un punto final se une al conjunto. Esto utiliza la operación fi_join_collective y funciona de forma asíncrona. Esto difiere de cómo se asocia un punto final de forma síncrona con

libfabric collective operations

NAME

libfabric collectives - libfabric collective operations

SYNOPSIS

```c #include <fabric/fabric.h> ```

DESCRIPTION

Libfabric collective operations are used to implement group communication patterns such as broadcast, reduce, and barrier. Collective operations are typically performed on endpoints that have been bound to an event queue using the fi_ep_bind() call. Upon completion of the fi_join_collective operation, an fi_addr is provided that is used as the target address when invoking a collective operation.

For developer convenience, a set of collective APIs are defined. Collective APIs differ from message and RMA interfaces in that the format of the data is known to the provider, and the collective may perform an operation on that data. This aligns collective operations closely with the atomic interfaces.

Join Collective (fi_join_collective)

This call attaches an endpoint to a collective membership group. Libfabric treats collective members as a multicast group, and the fi_join_collective call attaches the endpoint to that multicast group. By default, the endpoint will join the group based on the data transfer capabilities of the endpoint. For example, if the endpoint has been configured to both send and receive data, then the endpoint will be able to initiate and receive transfers to and from the collective. The input flags may be used to restrict access to the collective group, subject to endpoint capability limitations.

Join collective operations complete asynchronously, and may involve fabric transfers, dependent on the provider implementation. An endpoint must be bound to an event queue prior to calling fi_join_collective. The result of the join operation will be reported to the EQ as an FI_JOIN_COMPLETE event. Applications cannot issue collective transfers until receiving notification that the join operation has completed. Note that an endpoint may begin receiving messages from the collective group as soon as the join completes, which can occur prior to the FI_JOIN_COMPLETE event being generated.

The join collective operation is itself a collective operation. All participating peers must call fi_join_collective before any individual peer will report that the join has completed. Application managed collective memberships are an exception. With application managed memberships, the fi_join_collective call may be completed locally without fabric communication. For provider managed memberships, the join collective call requires as input a coll_addr that refers to either an address associated with an AV set (see fi_av_set_addr) or an existing collective group (obtained through a previous call to fi_join_collective). The fi_join_collective call will create a new collective subgroup. If application managed memberships are used, coll_addr should be set to FI_ADDR_UNAVAIL.

Applications must call fi_close on the collective group to disconnect the endpoint from the group. After a join operation has completed, the fi_mc_addr call may be used to retrieve the address associated with the multicast group. See fi_cm(3) for additional details on fi_mc_addr().

Barrier (fi_barrier)

The fi_barrier operation provides a mechanism to synchronize peers. Barrier does not result in any data being transferred at the application level. A barrier does not complete locally until all peers have invoked the barrier call. This signifies to the local application that work by peers that completed prior to them calling barrier has finished.

Barrier (fi_barrier2)

The fi_barrier2 operations is the same as fi_barrier, but with an extra parameter to pass in operation flags.

Broadcast (fi_broadcast)

fi_broadcast transfers an array of data from a single sender to all other members of the collective group. The input buf parameter is treated as the transmit buffer if the local rank is the root, otherwise it is the receive buffer. The broadcast operation acts as an atomic write or read to a data array. As a result, the format of the data in buf is specified through the datatype parameter. Any non-void datatype may be broadcast.

The following diagram shows an example of broadcast being used to transfer an array of integers to a group of peers.

[9]  [9]  [9]

All to All (fi_alltoall)

The fi_alltoall collective involves distributing (or scattering) different portions of an array of data to peers. It is best explained using an example. Here three peers perform an all to all collective to exchange different entries in an integer array.

[1]   [2]   [3]
[5]   [6]   [7]
[9]  [10]  [11]
   \   |   /
   All to all
   /   |   \
[1]   [5]   [9]
[2]   [6]  [10]
[3]   [7]  [11]

Each peer sends a piece of its data to the other peers.

All to all operations may be performed on any non-void datatype. However, all to all does not perform an operation on the data itself, so no operation is specified.

All Reduce (fi_allreduce)

fi_allreduce can be described as all peers providing input into an atomic operation, with the result copied back to each peer. Conceptually, this can be viewed as each peer issuing a multicast atomic operation to all other peers, fetching the results, and combining them. The combining of the results is referred to as the reduction. The fi_allreduce() operation takes as input an array of data and the specified atomic operation to perform. The results of the reduction are written into the result buffer.

Any non-void datatype may be specified. Valid atomic operations are listed below in the fi_query_collective call. The following diagram shows an example of an all reduce operation involving summing an array of integers between three peers.

 [5]  [5]  [5]
 [9]  [9]  [9]
   \   |   /
      sum
   /   |   \
 [3]  [3]  [3]
[15] [15] [15]
[27] [27] [27]
  All Reduce

All Gather (fi_allgather)

Conceptually, all gather can be viewed as the opposite of the scatter component from reduce-scatter. All gather collects data from all peers into a single array, then copies that array back to each peer.

[1]  [5]  [9]
  \   |   /
 All gather
  /   |   \
[1]  [1]  [1]
[5]  [5]  [5]
[9]  [9]  [9]

All gather may be performed on any non-void datatype. However, all gather does not perform an operation on the data itself, so no operation is specified.

Reduce-Scatter (fi_reduce_scatter)

The fi_reduce_scatter collective is similar to an fi_allreduce operation, followed by all to all. With reduce scatter, all peers provide input into an atomic operation, similar to all reduce. However, rather than the full result being copied to each peer, each participant receives only a slice of the result.

This is shown by the following example:

[1]  [1]  [1]
[5]  [5]  [5]
[9]  [9]  [9]
  \   |   /
     sum (reduce)
      |
     [3]
    [15]
    [27]
      |
   scatter
  /   |   \
[3] [15] [27]

The reduce scatter call supports the same datatype and atomic operation as fi_allreduce.

Reduce (fi_reduce)

The fi_reduce collective is the first half of an fi_allreduce operation. With reduce, all peers provide input into an atomic operation, with the the results collected by a single root endpoint.

This is shown by the following example, with the leftmost peer identified as the root:

[1]  [1]  [1]
[5]  [5]  [5]
[9]  [9]  [9]
  \   |   /
     sum (reduce)
    /
 [3]
[15]
[27]

The reduce call supports the same datatype and atomic operation as fi_allreduce.

Scatter (fi_scatter)

The fi_scatter collective is the second half of an fi_reduce_scatter operation. The data from a single root endpoint is split and distributed to all peers.

This is shown by the following example:

[15]
[27]
    \
   scatter
  /   |   \
[3] [15] [27]

The scatter operation is used to distribute results to the peers. No atomic operation is performed on the data.

Gather (fi_gather)

The fi_gather operation is used to collect (gather) the results from all peers and store them at a root peer.

This is shown by the following example, with the leftmost peer identified as the root.

  \   |   /
    gather

[5]
[9]

The gather operation does not perform any operation on the data itself.

Query Collective Attributes (fi_query_collective)

The fi_query_collective call reports which collective operations are supported by the underlying provider, for suitably configured endpoints. Collective operations needed by an application that are not supported by the provider must be implemented by the application. The query call checks whether a provider supports a specific collective operation for a given datatype and operation, if applicable.

The name of the collective, as well as the datatype and associated operation, if applicable, and are provided as input into fi_query_collective.

The coll parameter may reference one of these collectives: FI_BARRIER, FI_BROADCAST, FI_ALLTOALL, FI_ALLREDUCE, FI_ALLGATHER, FI_REDUCE_SCATTER, FI_REDUCE, FI_SCATTER, or FI_GATHER. Additional details on the collective operation is specified through the struct fi_collective_attr parameter. For collectives that act on data, the operation and related data type must be specified through

los atributos dados.

struct fi_collective_attr {
    enum fi_op op;
    enum fi_datatype datatype;
    struct fi_atomic_attr datatype_attr;
    size_t max_members;
      uint64_t mode;
};

Para una descripción de struct fi_atomic_attr, consulte fi_atomic(3).

op
En la entrada, esto especifica la operación atómica involucrada en la llamada colectiva. Esto debería establecerse en uno de los siguientes valores: FI_MIN, FI_MAX, FI_SUM, FI_PROD, FI_LOR, FI_LAND, FI_BOR, FI_BAND, FI_LXOR, FI_BXOR, FI_ATOMIC_READ, FI_ATOMIC_WRITE, o FI_NOOP. Para colectivos que no intercambian datos de la aplicación (fi_barrier), esto debería establecerse en FI_NOOP.
datatype
En la salida, especifica el tipo de dato de los datos que están siendo modificados por el colectivo. Esto debería establecerse en uno de los siguientes valores: FI_INT8, FI_UINT8, FI_INT16, FI_UINT16, FI_INT32, FI_UINT32, FI_INT64, FI_UINT64, FI_FLOAT, FI_DOUBLE, FI_FLOAT_COMPLEX, FI_DOUBLE_COMPLEX, FI_LONG_DOUBLE, FI_LONG_DOUBLE_COMPLEX, o FI_VOID. Para colectivos que no intercambian datos de la aplicación (fi_barrier), esto debería establecerse en FI_VOID.
datatype_attr.count
El número máximo de elementos que pueden usarse con el colectivo.
datatype_attr.size
El tamaño del tipo de dato tal como lo soporta el proveedor. Las aplicaciones deberían validar el tamaño de los tipos de datos que difieren según la plataforma, como FI_LONG_DOUBLE.
max_members
El número máximo de pares que pueden participar en una operación colectiva.
mode
Este campo está reservado y debería ser 0.

Si una operación colectiva es soportada, la llamada de consulta devolverá FI_SUCCESS, junto con los atributos sobre los límites para usar esa operación colectiva a través del proveedor.

Completados

Las operaciones colectivas se mapean a operaciones fi_atomic subyacentes. Para una discusión de la semántica de completado atómico, consulte fi_atomic(3). El completado, el orden y la atomicidad de las operaciones colectivas coinciden con los definidos para operaciones atómicas de punto a punto.

BANDERAS

Las siguientes banderas están definidas para las operaciones especificadas.

FI_SCATTER
Aplica a fi_query_collective. Cuando se establece, solicita información de atributos sobre la operación colectiva reduce-scatter.

VALOR DE RETORNO

Devuelve 0 en caso de éxito. En caso de error, se devuelve un valor negativo correspondiente a el errno del fabric. Los valores de errno del fabric están definidos en rdma/fi_errno.h.

ERRORES

-FI_EAGAIN
Consulte fi_msg(3) para una descripción detallada del manejo de FI_EAGAIN.
-FI_EOPNOTSUPP
La operación atómica solicitada no es soportada en este punto final.
-FI_EMSGSIZE
El número de operaciones colectivas en una sola solicitud excede el soportado por el proveedor subyacente.

NOTAS

Las operaciones colectivas se mapean a operaciones atómicas. Como tal, siguen la mayoría de las convenciones y restricciones de las operaciones atómicas de par a par. Esto incluye la atomicidad de los datos, la alineación de los datos y la semántica de ordenación de mensajes. Consulte fi_atomic(3) para información adicional sobre los tipos de datos y operaciones definidos para operaciones atómicas y colectivas.
