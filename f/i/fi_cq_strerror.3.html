DESCRIPCIÓ

N

Las colas de finalización se utilizan para informar de eventos asociados con transferencias de datos. Están asociadas con envíos y recepciones de mensajes, RMA, mensajes atómicos, mensajes etiquetados y eventos desencadenados. Los eventos informados suelen estar asociados con un punto de finalización de la red, pero también pueden referirse a regiones de memoria utilizadas como destino de una operación RMA o

atómica.

n

proveedor.

fi_cq_readfro

m

La llamada fi_cq_readfrom se comporta de manera idéntica a fi_cq_read, con la excepción de que permite a la CQ devolver información de dirección de origen al usuario para cualquier dato recibido. Los datos de dirección de origen solo están disponibles para aquellos puntos finales configurados con la capacidad FI_SOURCE. Si se llama a fi_cq_readfrom en un punto final para el cual los datos de direccionamiento de origen no están disponibles, la dirección de origen se establecerá en FI_ADDR_NOTAVAIL. El número de entradas src_addr de entrada debe ser el mismo que el parámetro

count.

Los datos de direccionamiento de origen devueltos se convierten desde la dirección nativa usada por la fabricación subyacente a un fi_addr_t, que puede usarse en operaciones de transmisión. En la mayoría de las circunstancias, devolver fi_addr_t requiere que la dirección de origen ya haya sido insertada en el vector de direcciones asociado con el punto final receptor. Esto es cierto para vectores de direcciones de tipo FI_AV_TABLE. En proveedores selectos cuando se usa FI_AV_MAP, las direcciones de origen pueden convertirse algorítmicamente en un fi_addr_t utilizable, aunque la dirección de origen no haya sido insertada en el vector de direcciones. Esto está permitido por la API, ya que permite al proveedor evitar la búsqueda de direcciones como parte del procesamiento de mensajes recibidos. En ningún caso los proveedores insertan direcciones en un AV separado de una llamada de la aplicación a fi_av_insert o una llamada

similar.

Para puntos finales asignados usando la capacidad FI_SOURCE_ERR, si la dirección de origen no puede convertirse en un valor fi_addr_t válido, fi_cq_readfrom retornará -FI_EAVAIL, incluso si los datos fueron recibidos exitosamente. La finalización será entonces reportada a través de fi_cq_readerr con el código de error -FI_EADDRNOTAVAIL. Véase fi_cq_readerr para

detalles.

Completions

Completions are reported via completion queues (CQs). A completion queue is an endpoint attribute that provides a mechanism for the application to track the progress and status of asynchronous operations. Completions are generated for successfully completed operations and for operations that completed with an error.

The completion queue is associated with an endpoint and is referenced by the fi_cq structure. The fi_cq_strerror function can be used to convert a completion error code into a human-readable string.

fi_cq_read

The fi_cq_read call retrieves a single completion entry from the specified completion queue. If the CQ is empty, the call will return FI_EAGAIN. If the CQ is configured with a wait object, the call will block until a completion is available or the wait object is signaled.

The fi_cq_read call is used to retrieve completions that are associated with asynchronous operations. The operation context associated with the completion is returned in the op_context field of the fi_cq_err_entry structure. If the CQ is configured with FI_SELECTIVE_COMPLETION, but the request did not have the FI_COMPLETION flag set. In such cases, providers will return as much information as made available by the underlying software and hardware about the failure, other fields will be set to NULL or 0. This includes the op_context value, which may not have been provided or was ignored on input as part of the transfer.

Notable completion error codes are given below.

FI_EADDRNOTAVAIL
This error code is used by CQs configured with FI_SOURCE_ERR to report completions for which a usable fi_addr_t source address could not be found. An error code of FI_EADDRNOTAVAIL indicates that the data transfer was successfully received and processed, with the fi_cq_err_entry fields containing information about the completion. The err_data field will be set to the source address data. The source address will be in the same format as specified through the fi_info addr_format field for the opened domain. This may be passed directly into an fi_av_insert call to add the source address to the address vector.

For API versions 1.20 and later, if the EP is configured with FI_AV_AUTH_KEY, src_addr will be set to the fi_addr_t authorization key handle or a user-define authorization key ID corresponding to the incoming data transfer. Otherwise, the value will be set to FI_ADDR_NOTAVAIL.

fi_cq_signal

The fi_cq_signal call will unblock any thread waiting in fi_cq_sread or fi_cq_sreadfrom. This may be used to wake-up a thread that is blocked waiting to read a completion operation. The fi_cq_signal operation is only available if the CQ was configured with a wait object.

COMPLETION FIELDS

The CQ entry data structures share many of the same fields. The meanings of these fields are the same for all CQ entry structure formats.

op_context
The operation context is the application specified context value that was provided with an asynchronous operation. The op_context field is valid for all completions that are associated with an asynchronous operation.

For completion events that are not associated with a posted operation, this field will be set to NULL. This includes completions generated at the target in response to RMA write operations that carry CQ data (FI_REMOTE_WRITE | FI_REMOTE_CQ_DATA flags set), when the FI_RX_CQ_DATA mode bit is not required.

flags
This specifies flags associated with the completed operation. The Completion Flags section below lists valid flag values. Flags are set for all relevant completions.
len
This len field applies to completed receive operations (e.g. fi_recv, fi_trecv, etc.) and the completed write with remote cq data on the responder side (e.g. fi_write, with FI_REMOTE_CQ_DATA flag). It indicates the size of transferred *message* data – i.e. how many data bytes were placed into the associated receive/target buffer by a corresponding fi_send/fi_tsend/fi_write et al call. If an endpoint has been configured with the FI_MSG_PREFIX mode, the len also reflects the size of the prefix buffer.
buf
The buf field is only valid for completed receive operations, and only applies when the receive buffer was posted with the FI_MULTI_RECV flag. In this case, buf points to the starting location where the receive data was placed.
data
The data field is only valid if the FI_REMOTE_CQ_DATA completion flag is set, and only applies to receive completions. If FI_REMOTE_CQ_DATA is set, this field will contain the completion data provided by the peer as part of their transmit request. The completion data will be given in host byte order.
tag
A tag applies only to received messages that occur using the tagged interfaces. This field contains the tag that was included with the received message. The tag will be in host byte order.
olen
The olen field applies to received messages. It is used to indicate that a received message has overrun the available buffer space and has been truncated. The olen specifies the amount of data that did not fit into the available receive buffer and was discarded.
err
This err code is a positive fabric errno associated with a completion. The err value indicates the general reason for an error, if one occurred. See fi_errno.3 for a list of possible error codes.
prov_errno
On an error, prov_errno may contain a provider specific error code. The use of this field and its meaning is provider specific. It is intended to be used as a debugging aid. See fi_cq_strerror for additional details on converting this error value into a human readable string.
err_data
The err_data field is used to return provider specific information, if available, about the error. On input, err_data should reference a data buffer of size err_data_size. On output, the provider will fill in this buffer with any provider specific data which may help identify the cause of the error. The contents of the err_data field and its meaning is provider specific. It is intended to be used as a debugging aid. See fi_cq_strerror for additional details on converting this error data into a human readable string. See the compatibility note below on how this field is used for older libfabric releases.
err_data_size
On input, err_data_size indicates the size of the err_data buffer in bytes. On output, err_data_size will be set to the number of bytes copied to the err_data buffer. The err_data information is typically used with fi_cq_strerror to provide details about the type of error that occurred.

For compatibility purposes, the behavior of the err_data and err_data_size fields is may be modified from that listed above. If err_data_size is 0 on input, or the fabric was opened with release < 1.5, then any buffer referenced by err_data will be ignored on input. In this situation, on output err_data will be set to a data buffer owned by the provider. The contents of the buffer will remain valid until a subsequent read call against the CQ. Applications must serialize access to the CQ when processing errors to ensure that the buffer referenced by err_data does not change.

src_addr
Used to return source addressed related information for error events. How this field is used is error event specific.

COMPLETION FLAGS

Completion flags provide additional details regarding the completed operation. The following completion flags are defined.

FI_SEND
Indicates that the completion was for a send operation. This flag may be combined with an FI_MSG or FI_TAGGED flag.
FI_RECV
Indicates that the completion was for a receive operation. This flag may be combined with an FI_MSG or FI_TAGGED flag.
FI_RMA
Indicates that an RMA operation completed. This flag may be combined with an FI_READ, FI_WRITE, FI_REMOTE_READ, or FI_REMOTE_WRITE flag.
FI_ATOMIC
Indicates that an atomic operation completed. This flag may be combined with an FI_READ, FI_WRITE, FI_REMOTE_READ, or FI_REMOTE_WRITE flag.
FI_MSG
Indicates that a message-based operation completed. This flag may be combined with an FI_SEND or FI_RECV flag.
FI_TAGGED

SEMÁNTICA DE EVENTOS DE

FINALIZACIÓN

Libfabric define varios `niveles' de finalización, identificados mediante indicadores operativos. Cada indicador indica el momento más temprano en que un proveedor puede generar un evento de finalización y las suposiciones que una aplicación puede hacer al procesar una finalización. Los indicadores operativos se definen a continuación, junto con un ejemplo de cómo un proveedor podría implementar la semántica. Tenga en cuenta que solo se requiere que el proveedor cumpla con la semántica, no con la implementación. Los proveedores pueden implementar semánticas de finalización más estrictas de las necesarias para una operación dada, pero solo se garantiza el comportamiento definido por el nivel de

finalización.

Para ayudar a comprender las diferencias conceptuales entre los niveles de finalización, considere el envío de una carta. Colocar la carta en el buzón local para su recogida es similar a `finalización de inyección'. Que la carta sea recogida y depositada en el buzón de destino equivale a `finalización de transmisión'. La semántica de `finalización de entrega' es una garantía más fuerte, con una persona en el destino firmando la recepción de la carta. Sin embargo, la persona que firmó la recepción de la carta no es necesariamente el destinatario previsto. La opción `finalización de coincidencia' es similar a la finalización de entrega, pero requiere que el destinatario previsto firme la recepción de la

carta.

El nivel `finalización de compromiso' tiene una semántica diferente a la de los niveles mencionados anteriormente. La finalización de compromiso sería más cercana a que la carta llegue al destino y se coloque en una caja fuerte a prueba de

fuego.

Los indicadores operativos para los niveles de finalización descritos se definen a

continuación.
FI_INJECT_COMPL
ETE
Indica que se debe generar una finalización cuando el(los) búfer(es) de origen puedan ser reu
tilizados. Una finalización garantiza que los búferes no serán leídos de nuevo y que la aplic
ación puede recuperarlos. No se hacen otras garantias con respecto al estado de la operación.

Ejemplo: Un proveedor puede generar este evento de finalización después de copiar el búfer de origen en un búfer de red, ya sea en la memoria del host o en la NIC. Una finalización de inyección no indica que los datos hayan sido transmitidos a la red, y podría ocurrir un error local después de que se haya generado el evento de finalización que podría impedir que se

transmita.

La finalización de inyección permite la notificación de finalización más rápida (y, por lo tanto, la reutilización de búferes), pero proporciona las garantías más débiles contra los errores de

red.

Nota: Este indicador se utiliza para controlar cuándo se inserta una entrada de finalización en una cola de finalización. No se aplica a las operaciones que no generan una entrada de cola de finalización, como la operación fi_inject, y no está sujeta a la restricción de límite de mensaje

inject_size.

SEMÁNTICAS DE FINALIZACIÓN EN EL

DESTINO

La semántica de finalización en el destino se utiliza para determinar cuándo los datos en el destino son visibles para la aplicación par. La visibilidad indica que una lectura de memoria en la misma dirección que fue el destino de una transferencia de datos devolverá los resultados de la transferencia. El destino de una transferencia puede ser identificado por el iniciante, como puede ser el caso de las operaciones RMA y atómicas, o determinado por el destino, por ejemplo, al proporcionar un búfer de recepción coincidente. La visibilidad global indica que los resultados están disponibles independientemente de dónde provenga la lectura de memoria. Por ejemplo, la lectura podría provenir de un proceso que se ejecuta en una CPU del host, podría ser accedida por una transferencia de datos posterior a través de la red, o leída desde un dispositivo par como una

GPU.

En términos de semánticas de finalización, la visibilidad generalmente indica que la transferencia cumple con los requisitos de FI_DELIVERY_COMPLETE desde la perspectiva del destino. La semántica de finalización en el destino puede estar, pero no necesariamente lo está, vinculada con la semántica de finalización especificada por el iniciante de la

transferencia.

A menudo, los procesos de destino no declaran explícitamente una semántica de finalización deseada y en su lugar se basan en la semántica predeterminada. El comportamiento predeterminado se basa en varios factores,

incluyendo:
•

destino
•
el tipo de transferencia involucrada (p. ej., msg vs
RMA)
•

En términos generales, las semánticas de finalización en el destino se agrupan en función de si la transferencia genera o no un evento de finalización en el destino. Esto incluye la escritura de una entrada en la cola de finalización (CQ) o la actualización de un contador de finalización. En casos de uso comunes, las transferencias que utilizan una interfaz de mensaje (FI_MSG o FI_TAGGED) típicamente generan eventos en el destino, mientras que las transferencias que involucran una interfaz RMA (FI_RMA o FI_ATOMIC) a menudo no lo hacen. Hay excepciones a ambos casos, dependiendo de los enlaces de punto final a CQ y contadores, y de los indicadores operativos. Por ejemplo, las escrituras RMA que llevan datos de CQ remotos generarán un evento de finalización en el destino, y se utilizan frecuentemente para transmitir visibilidad a la aplicación de destino. Las pautas generales para la semántica del lado del destino se describen a continuación, seguidas de excepciones que modifican ese

comportamiento.

Por defecto, las finalizaciones generadas en el destino indican que los datos transferidos están inmediatamente disponibles para ser leídos desde el búfer de destino. Es decir, el destino ve semánticas de FI_DELIVERY_COMPLETE (o mejores), incluso si el iniciante solicitó semánticas más bajas. Para aplicaciones que solo utilizan búferes de datos asignados desde la memoria del host, esto suele ser

suficiente. p">Para operaciones que no generan un evento de finalización en el destino, la visibilidad de los datos en el destino puede necesitar ser inferida basándose en operaciones posteriores que sí generan finalizaciones en el destino. En ausencia de una finalización en el destino, cuando se escribe en el iniciador la finalización de una operación, la semántica de visibilidad de la operación en el destino se alinea con la semántica de finalización del iniciador. Por ejemplo, si una operación RMA se finaliza en el iniciador como FI_INJECT_COMPLETE o FI_TRANSMIT_COMPLETE, la visibilidad de los datos en el destino no está

garantizada.

El proceso de destino puede utilizar uno o más de los siguientes mecanismos para garantizar que los resultados de una transferencia de datos que no generó una finalización en el destino sean ahora visibles. Esta lista no es exhaustiva de todas las opciones, sino que define usos comunes. En las descripciones siguientes, la primera transferencia no resulta en un evento de finalización en el destino, pero es eventualmente seguida por una transferencia que sí lo

hace.
•
Si el punto de extremo garantiza el orden de mensajes entre dos transferencias, la finalización en el destino de una segunda transferencia indicará que los datos de la primera transferencia están disponibles. Por ejemplo, si el punto de extremo soporta el orden de escritura después de envío (FI_ORDER_SAW), entonces una finalización de recepción correspondiente al envío indicará que los datos de la escritura están disponibles. Esto se mantiene independientemente de la semántica de finalización del iniciador para la escritura o el envío. Cuando se garantiza el orden, la segunda transferencia puede encolarse con el proveedor inmediatamente después de encolar la
primera.
•
Si el punto de extremo no garantiza el orden de mensajes, el iniciador debe tomar pasos adicionales para asegurar la visibilidad. Si el iniciador solicita semántica FI_DELIVERY_COMPLETE para la primera operación, el iniciador puede esperar a que la operación se complete localmente. Una vez que se ha leído la finalización, la finalización en el destino de una segunda transferencia indicará que los datos de la primera transferencia son
visibles.
•
Alternativamente, si el punto de extremo no garantiza el orden de mensajes, el iniciador puede usar los indicadores FI_FENCE y FI_DELIVERY_COMPLETE en la segunda transferencia
de datos para forzar que las primeras transferencias cumplan la semántica FI_DELIVERY_COMPLETE. Si la segunda transferencia genera una finalización en el destino, eso indi
cará que los datos son visibles. De lo contrario, una finalización en el destino de cualquier transferencia después de la operación cercada indicará que los datos son visibles.

Las semánticas anteriores se aplican a transferencias dirigidas a búferes de memoria de host tradicionales. Sin embargo, el comportamiento puede diferir cuando se involucra memoria de dispositivo y/o memoria persistente (bits de capacidad FI_HMEM y FI_PMEM). Cuando se involucra memoria heterogénea, entra en juego el concepto de dominios de memoria. Los dominios de memoria identifican la separación física de la memoria, que puede o no ser accesible a través del mismo espacio de direcciones virtuales. Consulte la página del manual fi_mr(3) para más detalles sobre los dominios de

memoria.

El orden de finalización y la visibilidad de datos solo están bien definidos para transferencias dirigidas al mismo dominio de memoria. Las aplicaciones deben ser conscientes de las diferencias de orden y visibilidad cuando las transferencias están dirigidas a diferentes dominios de memoria. Además, las aplicaciones también deben preocuparse por el dominio de memoria en el que se escriben las finalizaciones y si difiere del dominio de memoria al que está dirigida una transferencia. En algunas situaciones, tanto el proveedor como la aplicación pueden necesitar llamar a APIs específicas del dispositivo para sincronizar o vaciar (flush) las cachés de memoria del dispositivo con el fin de lograr la visibilidad de datos

deseada.

Cuando se utiliza memoria heterogénea, la semántica de finalización en el destino por defecto para transferencias que generan una finalización en el destino sigue siendo FI_DELIVERY_COMPLETE, sin embargo, las aplicaciones deben ser conscientes de que puede haber un impacto negativo en el rendimiento general para que los proveedores cumplan este

requisito.

Por ejemplo, un proceso de destino puede estar usando una GPU para acelerar cálculos. Una región de memoria que mapea a memoria en la GPU puede exponerse a pares como un destino RMA o publicarse localmente como un búfer de recepción. En este caso, la aplicación se preocupa por dos dominios de memoria – memoria del sistema y memoria de la GPU. Las finalizaciones se escriben en la memoria del

sistema.

Continuando con el ejemplo, un proceso par envía un mensaje etiquetado. Ese mensaje se empareja con el búfer de recepción ubicado en la memoria de la GPU. La NIC copia los datos de la red al búfer de recepción y escribe una entrada en la cola de finalización. Note que ambos dominios de memoria fueron accedidos como parte de esta transferencia. Los datos del mensaje fueron dirigidos a la memoria de la GPU, pero la finalización fue a la memoria del host. Debido a que dominios de memoria separados pueden no estar sincronizados entre sí, es posible que la CPU del host vea y procese la entrada de finalización antes de que la transferencia a la memoria de la GPU sea visible para la GPU del host o incluso para el software que se ejecuta en la GPU. Desde la perspectiva del proveedor, la visibilidad de la finalización no implica la visibilidad de los datos escritos en el dominio de memoria de la

GPU.

La semántica de finalización por defecto en el destino aplicación para operaciones de mensaje es FI_DELIVERY_COMPLETE. Una implementación anticipada del proveedor en esta situación es que el software del proveedor que se ejecuta en la CPU del host intercepte la entrada de CQ, detecte que los datos aterrizaron en memoria heterogénea, y realice la sincronización o operación de vaciado (flush) necesaria del dispositivo antes de reportar la finalización a la aplicación. Esto asegura que los datos sean visibles para el CPU y el software de la GPU antes de que la aplicación procese la

finalización.

Además del costo del software del proveedor interceptando finalizaciones y verificando si una transferencia está dirigida a memoria heterogénea, la sincronización del dispositivo en sí misma puede impactar el rendimiento. Como resultado, las aplicaciones pueden solicitar una semántica de finalización más baja al publicar recepciones. Eso indica al proveedor que la aplicación será responsable de manejar cualquier operación de vaciado (flush) específica del dispositivo que pueda ser necesaria. Consulte fi_msg(3)

FLAGS.

Para transferencias de datos que no generan una finalización en el destino, como RMA o operaciones atómicas, es responsabilidad de la aplicación asegurar que todos los búferes de destino cumplan los requisitos de visibilidad necesarios de la aplicación. Los métodos con viñetas mencionados anteriormente para notificar al destino que los datos son visibles pueden no ser suficientes, ya que el software del proveedor en el destino podría carecer del contexto necesario para asegurar la visibilidad. Esto implica que la aplicación puede necesitar llamar directamente a las APIs de sincronización/vaciado (flush) del

dispositivo.

Por ejemplo, una aplicación par podría realizar varias escrituras RMA dirigidas a búferes de memoria de GPU. Si el proveedor descarga las operaciones RMA en la NIC, el software del proveedor en el destino no será consciente de que las operaciones RMA han ocurrido. Si el par envía un mensaje a la aplicación de destino que indica que las operaciones RMA están hechas, la aplicación debe asegurar que los datos RMA sean visibles para la CPU o GPU del host antes de ejecutar código que acceda a los datos. La finalización en el destino de haber recibido el mensaje enviado no es suficiente, incluso si se soporta el orden de escritura después de

envío.

La mayoría de las semánticas de finalización de memoria heterogénea en el destino se mapean a FI_TRANSMIT_COMPLETE o FI_DELIVERY_COMPLETE. La memoria persistente (capacidad FI_PMEM), sin embargo, a menudo se usa con semánticas FI_COMMIT_COMPLETE. Los conceptos de finalización heterogénea siguen

aplicándose.

Para transferencias marcadas por el iniciador con FI_COMMIT_COMPLETE, una finalización en el destino indica que los resultados son visibles y duraderos. Para transferencias dirigidas a memoria persistente, pero usando una semántica de finalización diferente en el iniciador, la visibilidad en el destino es similar a la descrita anteriormente. La durabilidad solo está asociada con transferencias marcadas con FI_COMMIT_COMPLETE

.

Para transferencias dirigidas a memoria persistente que solicitan FI_DELIVERY_COMPLETE, entonces una finalización, ya sea en el iniciador o en el destino, indica que los datos son visibles. La visibilidad en el destino puede ser transmitida usando uno de los mecanismos descritos anteriormente – generando una finalización en el destino, enviando un mensaje desde el iniciador, etc. De manera similar, si el iniciador solicitó FI_TRANSMIT_COMPLETE, entonces se necesitan pasos adicionales para asegurar la visibilidad en el destino. Por ejemplo, la transferencia puede generar una finalización en el destino, lo que indicaría visibilidad, pero no durabilidad. El iniciador también puede seguir la transferencia con otra operación que fuerce la visibilidad, como usar FI_FENCE en conjunto con FI_DELIVERY_COMPLET

E
.
