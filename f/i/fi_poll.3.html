fi_poll

(obsoleto)

Progresa todas las colas de finalización y contadores asociados con un conjunto de sondeo y comprueba eventos. Si podrían haber ocurrido eventos, los contextos asociados con las colas de finalización y/o contadores son devueltos. Las colas de finalización devolverán su contexto si no están vacías. El contexto asociado con un contador será devuelto si el valor de éxito o el valor de error del contador han cambiado desde la última vez que se llamó a fi_poll, fi_cntr_set, o fi_cntr_add. El número de contextos está limitado al tamaño del array de contextos, indicado por el parámetro

count.

Tenga en cuenta que fi_poll solo indica que podrían estar disponibles eventos. En algunos casos, los proveedores podrían consumir tales eventos internamente, para impulsar

el progreso, por ejemplo. Esto puede resultar en que fi_poll devuelva falsos positivos. Las aplicaciones deben impulsar su progreso basándose en los resultados de leer eve
ntos de una cola de finalización o leer valores de contador. La función fi_poll siempre devolverá todas las colas de finalización y contadores que sí tengan nuevos eventos.

fi_wait_open

(obsoleto)

fi_wait_open asigna un nuevo conjunto de espera. Un conjunto de espera permite un método optimizado de espera de eventos a través de múltiples colas de finalización y contadores. Siempre que sea posible, un conjunto de espera usa un único objeto de espera subyacente que es señalizado cuando ocurre una condición especificada en una cola de finalización o contador

asociado.

Las propiedades y el comportamiento de un conjunto de espera son definidos por struct

fi_wait_attr. 
struct fi_wait_attr {
    enum fi_wait_obj     wait_obj;  /* requested wait object */
    uint64_t             flags;     /* operation flags
*/
}
;
wait_o
bj
Los conjuntos de espera están asociados con objeto(s) de espera específicos. Los objetos de espera permiten a las aplicaciones bloquearse hasta que el objeto de espera sea señalizado, indicando que un evento está disponible para ser leído. Los siguientes valores pueden usarse para especificar el tipo de objeto de espera asociado con un conjunto de espera: FI_WAIT_UNSPEC, FI_WAIT_FD, FI_WAIT_MUTEX_COND (obsoleto), y
FI_WAIT_YIELD.
- FI_WAIT_UNSP
EC
Especifica que el usuario solo esperará en el conjunto de espera usando llamadas de la interfaz de fabric, como fi_wait. En este caso, el proveedor subyacente puede seleccionar el objeto de espera más apropiado o de mayor rendimiento disponible, incluyendo mecanismos de espera personalizados. Las aplicaciones que seleccionan FI_WAIT_UNSPEC no tienen garantía de recuperar el objeto de espera
subyacente.
- FI_WAIT_
FD
Indica que el conjunto de espera debe usar un único descriptor de archivo como su mecanismo de espera, tal como se expone a la aplicación. Internamente, esto puede requerir el uso de epoll para soportar la espera en un único descriptor de archivo. Los objetos de espera de descriptor de archivo deben ser utilizables en las rutinas POSIX select(2) y poll(2), y Linux epoll(7) (si están disponibles). El proveedor señaliza un objeto de espera FD marcándolo como legible o con un
error.
- FI_WAIT_MUTEX_COND
(obsoleto)
Especifica que el conjunto de espera debe usar un mutex y una variable de condición de pthread como objeto de
espera.
- FI_WAIT_POLL
FD
Esta opción es similar a FI_WAIT_FD, pero permite que el mecanismo de espera use múltiples descriptores de archivo como su mecanismo de espera, tal como lo ve la aplicación. El uso de FI_WAIT_POLLFD puede eliminar la necesidad de usar epoll para abstraer la necesidad de comprobar múltiples descriptores de archivo al esperar eventos. Los descriptores de archivo deben ser utilizables en las rutinas POSIX select(2) y routines de poll(2), y que coinciden directamente con el uso de poll. Vea la sección de NOTAS a continuación para obtener detalles sobre el uso de pollfd.
- FI_WAIT_YIELD
Indica que el conjunto de espera esperará sin un objeto de espera, sino que cederá en cada espera.
flags
Banderas que establecen la operación predeterminada del conjunto de espera. El uso de este campo está reservado y debe establecerse en 0 por el llamador.

fi_close (obsoleto)

La llamada fi_close libera todos los recursos asociados con un conjunto de espera. El conjunto de espera no debe estar vinculado a ningún otro recurso abierto antes de cerrarse, de lo contrario, la llamada devolverá -FI_EBUSY.

fi_wait (obsoleto)

Espera en un conjunto de espera hasta que uno o más de sus objetos de espera subyacentes se activen.

fi_trywait

La llamada fi_trywait se introdujo en la versión 1.3 de libfabric. El comportamiento de usar objetos de espera nativos sin el uso de fi_trywait es específico del proveedor y debe considerarse no determinista.

La llamada fi_trywait() se utiliza en conjunción con las llamadas nativas del sistema operativo para bloquear en objetos de espera, como descriptores de archivo. La aplicación debe llamar a fi_trywait y obtener un valor de retorno de FI_SUCCESS antes de bloquear en un objeto de espera nativo. No hacerlo puede resultar en que el objeto de espera no se active y que la aplicación no observe los eventos deseados. El siguiente pseudocódigo demuestra el uso de fi_trywait en conjunción con la llamada select(2) del SO.

fi_control(&cq->fid, FI_GETWAIT, (void *) &fd);
FD_ZERO(&fds);
FD_SET(fd, &fds);
while (1) {
    if (fi_trywait(&cq, 1) == FI_SUCCESS)
        select(fd + 1, &fds, NULL, &fds, &timeout);
    do {
        ret = fi_cq_read(cq, &comp, 1);
    } while (ret > 0);
}

fi_trywait() devolverá FI_SUCCESS si es seguro bloquear en los objetos de espera correspondientes a los descriptores de fabric, o -FI_EAGAIN si hay eventos en cola en el descriptor de fabric o si el bloqueo pudiera colgar la aplicación.

La llamada toma una matriz de descriptores de fabric. Para cada objeto de espera que se pasará a la rutina de espera nativa, el descriptor de fabric correspondiente debe pasarse primero a fi_trywait. Todos los descriptores de fabric pasados en una sola llamada a fi_trywait deben utilizar el mismo tipo de objeto de espera subyacente.

Los siguientes tipos de descriptores de fabric se pueden pasar a fi_trywait: colas de eventos, colas de finalización, contadores y conjuntos de espera. Las aplicaciones que deseen utilizar llamadas de espera nativas deben seleccionar objetos de espera específicos al asignar dichos recursos. Por ejemplo, estableciendo el valor wait_obj del elemento de creación del elemento en FI_WAIT_FD.

En caso de que el objeto de espera a comprobar pertenezca a un conjunto de espera, solo el conjunto de espera en sí debe pasarse a fi_trywait. Los recursos de fabric asociados con el conjunto de espera no es necesario.

Al recibir un valor de retorno de -FI_EAGAIN de fi_trywait, una aplicación debe leer todas las finalizaciones y eventos en cola, y llamar a fi_trywait nuevamente antes de intentar bloquear. Las aplicaciones pueden utilizar un conjunto de sondeo de fabric para identificar colas de finalización y contadores que puedan requerir procesamiento.

fi_control

La llamada fi_control se utiliza para acceder a detalles específicos del proveedor o de la implementación de un fids que admite llamadas de bloqueo, como conjuntos de espera, colas de finalización, contadores y colas de eventos. El acceso al conjunto de espera o fid debe serializarse en todas las llamadas cuando se invoca fi_control, ya que puede redirigir la implementación de las operaciones del conjunto de espera. Los siguientes comandos de control son utilizables con un conjunto de espera o fid.

FI_GETWAIT (void **)
Este comando permite al usuario recuperar el objeto de espera de bajo nivel asociado con un conjunto de espera o fid. El formato del conjunto de espera se especifica durante la creación del conjunto de espera, a través de los atributos del conjunto de espera. El parámetro arg de fi_control debe ser una dirección donde se escribirá un puntero al objeto de espera devuelto. Esto debería ser un `int *` para FI_WAIT_FD, `struct fi_mutex_cond` para FI_WAIT_MUTEX_COND (obsoleto), o `struct fi_wait_pollfd` para FI_WAIT_POLLFD. El soporte para FI_GETWAIT es específico del proveedor.
FI_GETWAITOBJ (enum fi_wait_obj *)
Este comando devuelve el tipo de objeto de espera asociado con un conjunto de espera o fid.

VALORES DE RETORNO

Devuelve FI_SUCCESS en caso de éxito. En caso de error, se devuelve un valor negativo correspondiente al errno de fabric.

Los valores de errno de fabric se definen en rdma/fi_errno.h.

fi_poll
En caso de éxito, si hay eventos disponibles, devuelve el número de entradas escritas en la matriz de contexto.

NOTAS

En muchas situaciones, las llamadas de bloqueo pueden necesitar esperar señales enviadas a un número de descriptores de archivo. Por ejemplo, este es el caso de los proveedores basados en sockets, como tcp y udp, así como de los proveedores de utilidad como multi-rail. Para simplificar, cuando epoll está disponible, se puede utilizar para limitar el número de descriptores de archivo que una aplicación debe monitorear. El uso de epoll también puede ser necesario para soportar FI_WAIT_FD.

Sin embargo, para soportar la espera en múltiples descriptores de archivo en sistemas donde el soporte de epoll no está disponible, o donde el rendimiento de epoll puede afectar negativamente al rendimiento, FI_WAIT_POLLFD proporciona este mecanismo. Una diferencia significativa entre el uso de POLLFD y los objetos de espera FD es que con FI_WAIT_POLLFD, los descriptores de archivo pueden cambiar dinámicamente. Por ejemplo, los descriptores de archivo asociados con el conjunto de espera de las colas de finalización pueden cambiar a medida que se agregan y eliminan las asociaciones de puntos finales con la CQ.

Struct fi_wait_pollfd se utiliza para recuperar todos los descriptores de archivo para fids que utilizan FI_WAIT_POLLFD para soportar llamadas de bloqueo.

struct fi_wait_pollfd {
    uint64_t      change_index;
    size_t        nfds;
    struct pollfd *fd;
};
change_index
El change_index se puede utilizar para determinar si ha habido algún cambio en la lista de descriptores de archivo. Cada vez que se agrega, elimina o se actualizan sus eventos un descriptor de archivo, este campo es incrementado por el proveedor. Las aplicaciones que deseen esperar directamente en descriptores de archivo deben almacenar en caché el valor de change_index. Antes de bloquear en eventos de descriptores de archivo, la aplicación debe usar fi_control() para recuperar el change_index actual y compararlo con su valor almacenado en caché. Si los valores difieren, la aplicación debe actualizar su lista de descriptores de archivo antes de bloquear.
nfds
En la entrada a fi_control(), esto indica el número de entradas en el array struct pollfd *. En la salida, se establecerá en el número de entradas necesarias para almacenar el número actual de descriptores de archivo. Si el valor de entrada es menor que el valor de salida, fi_control() devolverá el error -FI_ETOOSMALL. Tenga en cuenta que establecer nfds = 0 permite una forma eficiente de verificar change_index.
fd
Esto apunta a una matriz de entradas struct pollfd. El número de entradas se especifica a través del campo nfds. Si el número de entradas necesarias es menor o igual al número de entradas disponibles, la matriz struct pollfd se completará con una lista de descriptores de archivo y eventos correspondientes que se pueden utilizar en las llamadas select(2) y poll(2).

El change_index se actualiza solo cuando los descriptores de archivo asociados con el conjunto de archivos pollfd han cambiado. Verificar el change_index es un paso adicional necesario cuando se trabaja directamente con objetos de espera FI_WAIT_POLLFD. El uso de la función fi_trywait() sigue siendo necesario si se accede directamente a los objetos de espera.
