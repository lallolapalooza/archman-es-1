NOMBRE

fi_cq - Operaciones de cola de finalización

fi_cq_open / fi_close
Abrir/cerrar una cola de finalización
fi_control
Controlar la operación o los atributos de la CQ.
fi_cq_read / fi_cq_readfrom / fi_cq_readerr
Leer una finalización de una cola de finalización
fi_cq_sread / fi_cq_sreadfrom
Una lectura sincrónica (bloqueante) que espera hasta que se haya cumplido una condición especificada antes de leer una finalización de una cola de finalización.
fi_cq_signal
Desbloquear cualquier hilo que espere en fi_cq_sread o fi_cq_sreadfrom.
fi_cq_strerror
Convierte la información de error específica del proveedor en una cadena imprimible

DESCRIPCIÓN

Las colas de finalización se utilizan para informar de eventos asociados con transferencias de datos. Están asociadas con envíos y recepciones de mensajes, RMA, operaciones atómicas, mensajes etiquetados y eventos activados. Los eventos informados suelen estar asociados con un punto final de fabricación, pero también pueden referirse a regiones de memoria utilizadas como destino de una operación RMA o atómica.

fi_cq_open

fi_cq_open asigna una nueva cola de finalización. A diferencia de las colas de eventos, las colas de finalización están asociadas con un dominio de recursos y pueden descargarse por completo en el hardware del proveedor.

Las propiedades y el comportamiento de una cola de finalización se definen por struct fi_cq_attr.

struct fi_cq_attr {
    size_t               size;      /* # entradas para CQ */
    uint64_t             flags;     /* banderas de operación */
    enum fi_cq_format    format;    /* formato de finalización */
    enum fi_wait_obj     wait_obj;  /* objeto de espera solicitado */
    int                  signaling_vector; /* afinidad de interrupción */
    enum fi_cq_wait_cond wait_cond; /* formato de condición de espera */
    struct fid_wait     *wait_set;  /* conjunto de espera opcional, obsoleto */
};
size
Especifica el tamaño mínimo de una cola de finalización. Un valor de 0 indica que el proveedor puede elegir un valor predeterminado.
flags
Banderas que controlan la configuración de la CQ.
- FI_AFFINITY
Indica que el campo signaling_vector (ver más abajo) es válido.
format
Las colas de finalización permiten a la aplicación seleccionar la cantidad de detalle que debe almacenar e informar. El atributo format permite a la aplicación seleccionar uno de varios formatos de finalización, indicando la estructura de los datos que la cola de finalización debe devolver al leer. Los formatos admitidos y las estructuras que corresponden a cada uno se enumeran a continuación. El significado de los campos de la entrada de la CQ se define en la sección Campos de Finalización .
- FI_CQ_FORMAT_UNSPEC
Si se solicita un formato no especificado, la CQ utilizará un formato predeterminado seleccionado por el proveedor.
- FI_CQ_FORMAT_CONTEXT
Proporciona solo el contexto especificado por el usuario que estaba asociado con la finalización.
struct fi_cq_entry {
    void     *op_context; /* contexto de operación */
};

struct fi_cq_msg_entry {

wait_obj
Las CQ pueden estar asociadas con un objeto de espera específico. Los objetos de espera permiten a las aplicaciones bloquearse hasta que el objeto de espera sea señalado, lo que indica que hay una finalización disponible para leer. Los usuarios pueden usar fi_control para recuperar el objeto de espera subyacente asociado con una CQ, para usarlo en otras llamadas al sistema. Los siguientes valores pueden usarse para especificare tipo de objeto de espera asociado con una CQ: FI_WAIT_NONE, FI_WAIT_UNSPEC, FI_WAIT_SET, FI_WAIT_FD, FI_WAIT_MUTEX_COND (obsoleto), y FI_WAIT_YIELD. El valor predeterminado es FI_WAIT_NONE.
- FI_WAIT_NONE
Se utiliza para indicar que el usuario no se bloqueará (esperará) por finalizaciones en la CQ. Cuando se especifica FI_WAIT_NONE, la aplicación no puede llamar a fi_cq_sread ni a fi_cq_sreadfrom.
- FI_WAIT_UNSPEC
Especifica que el usuario solo esperará en la CQ mediante llamadas de interfaz de fabricación, como fi_cq_sread o fi_cq_sreadfrom. En este caso, el proveedor subyacente puede seleccionar el objeto de espera más apropiado o de mayor rendimiento disponible, incluyendo mecanismos de espera personalizados. No se garantiza que las aplicaciones que seleccionan FI_WAIT_UNSPEC puedan recuperar el objeto de espera subyacente.
- FI_WAIT_SET (obsoleto)
Indica que la cola de finalización debe usar un objeto de conjunto de espera para esperar finalizaciones. Si se especifica, el campo wait_set debe referenciar un objeto de conjunto de espera existente.
- FI_WAIT_FD
Indica que la CQ debe usar un descriptor de archivo como su mecanismo de espera. Un objeto de espera de descriptor de archivo debe ser utilizable en las rutinas select, poll y epoll. Sin embargo, un proveedor puede señalar un objeto de espera FD marcándolo como legible, escribible o con un error.
- FI_WAIT_MUTEX_COND (obsoleto)
Especifica que la CQ debe usar un mutex pthread y una variable de condición como objeto de espera.
- FI_WAIT_YIELD
Indica que la CQ esperará sin un objeto de espera, sino que cederá en cada espera. Permite el uso de fi_cq_sread y fi_cq_sreadfrom a través de un bucle de espera activa (spin).
signaling_vector
Si se establece el indicador FI_AFFINITY, esto indica el número de CPU lógico (0..max cpu - 1) al que deben dirigirse las interrupciones asociadas con la CQ. Este campo debe tratarse como una sugerencia para el proveedor y puede ignorarse si el proveedor no admite afinidad de interrupción.
wait_cond
De forma predeterminada, cuando se inserta una finalización en una CQ que admite lecturas bloqueantes (fi_cq_sread/fi_cq_sreadfrom), el objeto de espera correspondiente se señala. Los usuarios pueden especificar una condición que debe cumplirse primero antes de que la espera se satisfaga. Este campo indica cómo debe interpretar el proveedor el campo cond, que describe la condición necesaria para señalar el objeto de espera.

Una condición de espera debe tratarse como una optimización. No se exige a los proveedores que cumplan los requisitos de la condición antes de señalar el objeto de espera. Las aplicaciones no deben depender de que la condición sea necesariamente verdadera cuando una llamada de lectura bloqueante regresa.

Si wait_cond está establecido en FI_CQ_COND_NONE, no se aplican condiciones adicionales al señalado del objeto de espera de la CQ, y la inserción de cualquier nueva entrada activará la condición de espera. Si wait_cond está establecido en FI_CQ_COND_THRESHOLD, el campo cond se interpreta como un valor umbral de tipo size_t. El umbral indica el número de entradas que deben encolarse en la CQ antes de que la espera se satisfaga.

Este campo se ignora si wait_obj está establecido en FI_WAIT_NONE.

wait_set (obsoleto)
Si wait_obj es FI_WAIT_SET, este campo referencia un objeto de espera al que la cola de finalización debe adjuntarse. Cuando se inserta un evento en la cola de finalización, el conjunto de espera correspondiente se señalará si se cumplen todas las condiciones necesarias. El uso de un wait_set permite un método optimizado de espera de eventos en múltiples colas de eventos y finalización. Este campo se ignora si wait_obj no es FI_WAIT_SET.

fi_close

La llamada fi_close libera todos los recursos asociados con una cola de finalización. Cualquier finalización que permanezca en la CQ cuando se cierre se perderá.

Al cerrar la CQ, no debe haber extremos abiertos, contextos de transmisión ni contextos de recepción asociados con la CQ. Si aún hay recursos asociados con la CQ al intentar cerrarla, la llamada devolverá -FI_EBUSY.

fi_control

La llamada fi_control se utiliza para acceder a detalles específicos del proveedor o de la implementación de la cola de finalización. El acceso a la CQ debe serializarse en todas las llamadas cuando se invoca fi_control, ya que puede redirigir la implementación de las operaciones de CQ. Los siguientes comandos de control son utilizables con una CQ.

FI_GETWAIT (void **)
Este comando permite al usuario recuperar el objeto de espera de bajo nivel asociado con la CQ. El formato del objeto de espera se especifica durante la creación de la CQ, a través de los atributos de la CQ. El parámetro arg de fi_control debe ser una dirección donde se escribirá un puntero al objeto de espera devuelto. Consulte fi_eq.3 para obtener detalles adicionales sobre el uso de fi_control con FI_GETWAIT.

fi_cq_read

La operación fi_cq_read realiza una lectura no bloqueante de datos de finalización desde la CQ. El formato del evento de finalización se determina usando la opción fi_cq_format que se especificó cuando se abrió la CQ. Se pueden recuperar múltiples finalizaciones de una CQ en una sola llamada. El número máximo de entradas a devolver está limitado por el parámetro count especificado, con el número de entradas leídas exitosamente de la CQ devuelto por la llamada. (Vea la sección de valores de retorno más abajo.) Un valor de count de 0 puede usarse para impulsar el progreso en extremos asociados cuando el progreso manual está habilitado.

Las CQ están optimizadas para reportar operaciones que se han completado exitosamente. Las operaciones que fallan se reportan 'fuera de banda'. Dichas operaciones se recuperan usando la función fi_cq_readerr. Cuando se encuentra una operación que se ha completado con un error inesperado, se coloca en una cola de errores temporal. Intentar leer de una CQ mientras hay un elemento en la cola de errores resulta en que fi_cq_read falle con un código de retorno de -FI_EAVAIL. Las aplicaciones pueden usar este código de retorno para determinar cuándo llamar a fi_cq_readerr.

fi_cq_readfrom

La llamada fi_cq_readfrom se comporta de manera idéntica a fi_cq_read, con la excepción de que permite a la CQ devolver información de dirección de origen al usuario para cualquier dato recibido. Los datos de dirección de origen solo están disponibles para aquellos extremos configurados con la capacidad FI_SOURCE. Si se llama a fi_cq_readfrom en un extremo para el cual los datos de direccionamiento de origen no están disponibles, la dirección de origen se establecerá en FI_ADDR_NOTAVAIL. El número de entradas src_addr de entrada debe ser el mismo que el parámetro count.

Los datos de direccionamiento de origen devueltos se convierten desde la dirección nativa usada por la fabricación subyacente a un fi_addr_t, que puede usarse en operaciones de transmisión. En la mayoría de las circunstancias, devolver fi_addr_t requiere que la dirección de origen ya haya sido insertada en el vector de direcciones asociado con el extremo receptor. Esto es cierto para vectores de direcciones de tipo FI_AV_TABLE. En algunos proveedores cuando se usa FI_AV_MAP, las direcciones de origen pueden convertirse algorítmicamente en un fi_addr_t utilizable, aunque la dirección de origen no haya sido insertada en el vector de direcciones. Esto está permitido por la API, ya que permite al proveedor evitar la búsqueda de direcciones como parte del procesamiento de mensajes recibidos. En ningún caso los proveedores insertan direcciones en un AV separado de una llamada de la aplicación a fi_av_insert o una llamada similar.

Para extremos asignados usando la capacidad FI_SOURCE_ERR, si la dirección de origen no puede convertirse en un valor fi_addr_t válido, fi_cq_readfrom devolverá -FI_EAVAIL, incluso si los datos fueron recibidos exitosamente. La finalización será entonces reportada a través de fi_cq_readerr con el código de error -FI_EADDRNOTAVAIL. Consulte fi_cq_readerr para más detalles.

Si FI_SOURCE se especifica sin FI_SOURCE_ERR, las direcciones de origen que no puedan mapearse a un fi_addr_t utilizable serán reportadas como FI_ADDR_NOTAVAIL.

fi_cq_sread / fi_cq_sreadfrom

Las llamadas fi_cq_sread y fi_cq_sreadfrom son las operaciones equivalentes bloqueantes a fi_cq_read y fi_cq_readfrom. Su comportamiento es similar al de las llamadas no bloqueantes, con la excepción de que las llamadas no regresarán hasta que se haya leído una finalización de la CQ o ocurra un error o tiempo de espera agotado.

Los hilos bloqueados en esta función regresarán al llamador si son señalados por alguna fuente externa. Esto es cierto incluso si el tiempo de espera no ha ocurrido o se especificó como infinito.

Es inválido para las aplicaciones llamar a estas funciones si la CQ ha sido configurada con un objeto de espera de FI_WAIT_NONE o FI_WAIT_SET.

fi_cq_readerr

La función de lectura de errores, fi_cq_readerr, recupera información sobre cualquier operación asíncrona que se haya completado con un error inesperado. fi_cq_readerr es una llamada no bloqueante, regresando inmediatamente ya sea que se haya encontrado una finalización de error o no.

La información de error se reporta al usuario a través de struct fi_cq_err_entry. El formato de esta estructura se define a continuación.

struct fi_cq_err_entry {
    void     *op_context; /* contexto de operación */
    uint64_t flags;       /* indicadores de finalización */
    size_t   len;         /* tamaño de los datos recibidos */
    void     *buf;        /* búfer de datos de recepción */
    uint64_t data;        /* datos de finalización */
    uint64_t tag;         /* etiqueta de mensaje */
    size_t   olen;        /* longitud de desbordamiento */
    int      err;         /* código de error positivo */
    int      prov_errno;  /* código de error del proveedor */
    void    *err_data;    /*  datos de error */
    size_t   err_data_size; /* tamaño de err_data */
    fi_addr_t src_addr; /* dirección de origen del error */
};

La razón general del error se proporciona a través del campo err. La información de error específica del proveedor también puede estar disponible a través de los campos prov_errno y err_data. Los usuarios pueden llamar a fi_cq_strerror para convertir la información de error específica del proveedor en una cadena imprimible con fines de depuración. Consulte los detalles de los campos más abajo para más información sobre el uso de err_data y err_data_size.

SEMÁNTICA DE EVENTOS DE

FINALIZACIÓN

Libfabric define varios `niveles' de finalización, identificados mediante indicadores operativos. Cada indicador indica el momento más temprano en que un proveedor puede generar un evento de finalización, y las suposiciones que una aplicación puede hacer al procesar una finalización. Los indicadores operativos se definen a continuación, junto con un ejemplo de cómo un proveedor podría implementar la semántica. Tenga en cuenta que solo se requiere que el proveedor cumpla con la semántica, no con la implementación. Los proveedores pueden implementar semánticas de finalización más fuertes de las necesarias para una operación determinada, pero solo se garantiza el comportamiento definido por el nivel de

finalización.

Para ayudar a comprender las diferencias conceptuales entre los niveles de finalización, considere el envío de una carta. Colocar la carta en el buzón local para su recogida es similar a `inyección completa'. Tener la carta recogida y depositada en el buzón de destino es equivalente a `transmisión completa'. La semántica `entrega completa' es una garantía más fuerte, con una persona en el destino firmando el recibo de la carta. Sin embargo, la persona que firmó el recibo de la carta no es necesariamente el destinatario previsto. La opción `coincidencia completa' es similar a entrega completa, pero requiere que el destinatario previsto firme el recibo de la

carta.

El nivel `finalización de confirmación' tiene una semántica diferente a la de los niveles mencionados anteriormente. La finalización de confirmación sería más cercana a que la carta llegue al destino y se coloque en una caja fuerte a prueba de

fuego.

Los indicadores operativos para los niveles de finalización descritos se definen a

continuación.

SEMÁNTICA DE FINALIZACIÓN EN EL

DESTINO

La semántica de finalización en el destino se utiliza para determinar cuándo los datos en el destino son visibles para la aplicación par. La visibilidad indica que una lectura de memoria en la misma dirección que fue el destino de una transferencia de datos devolverá los resultados de la transferencia. El destino de una transferencia puede ser identificado por el iniciador, como puede ser el caso de las operaciones RMA y atómicas, o determinado por el destino, por ejemplo, al proporcionar un búfer de recepción coincidente. La visibilidad global indica que los resultados están disponibles independientemente de dónde se origine la lectura de memoria. Por ejemplo, la lectura podría provenir de un proceso que se ejecuta en una CPU del host, podría ser accedida por una transferencia de datos posterior a través de la red de interconexión, o leída desde un dispositivo par como una

GPU.

En términos de semántica de finalización, la visibilidad generalmente indica que la transferencia cumple los requisitos de FI_DELIVERY_COMPLETE desde la perspectiva del destino. La semántica de finalización en el destino puede estar, pero no necesariamente lo está, vinculada con la semántica de finalización especificada por el iniciador de la

transferencia.

A menudo, los procesos de destino no declaran explícitamente una semántica de finalización deseada y en su lugar dependen de la semántica predeterminada. El comportamiento predeterminado se basa en varios factores, que

incluyen:

En términos generales, las semánticas de finalización en el destino se agrupan en función de si la transferencia genera o no un evento de finalización en el destino. Esto incluye escribir una entrada en la cola de finalización (CQ) o actualizar un contador de finalización. En casos de uso comunes, las transferencias que utilizan una interfaz de mensaje (FI_MSG o FI_TAGGED) típicamente generan eventos en el destino, mientras que las transferencias que involucran una interfaz RMA (FI_RMA o FI_ATOMIC) a menudo no lo hacen. Hay excepciones a ambos casos, dependiendo de los enlaces de punto de extremo a CQ y contadores, y de los indicadores operativos. Por ejemplo, las escrituras RMA que llevan datos de CQ remotos generarán un evento de finalización en el destino, y se utilizan frecuentemente para transmitir visibilidad a la aplicación de destino. Las pautas generales para la semántica del lado del destino se describen a continuación, seguidas de excepciones que modifican ese

comportamiento.

De forma predeterminada, las finalizaciones generadas en el destino indican que los datos transferidos están inmediatamente disponibles para ser leídos desde el búfer de destino. Es decir, el destino ve semánticas de FI_DELIVERY_COMPLETE (o mejores), incluso si el iniciador solicitó semánticas más bajas. Para aplicaciones que utilizan solo búferes de datos asignados desde la memoria del host, esto a menudo es

suficiente. ">Para operaciones que no generan un evento de finalización en el destino, la visibilidad de los datos en el destino puede necesitar ser inferida basándose en operaciones posteriores que sí generan finalizaciones en el destino. En ausencia de una finalización en el destino, cuando se escribe en el iniciador la finalización de una operación, la semántica de visibilidad de la operación en el destino se alinea con la semántica de finalización del iniciador. Por ejemplo, si una operación RMA completa en el iniciador como FI_INJECT_COMPLETE o FI_TRANSMIT_COMPLETE, no se garantiza la visibilidad de los datos en el destino.

El proceso de destino puede utilizar uno o más de los siguientes mecanismos para garantizar que los resultados de una transferencia de datos que no generó una finalización en el destino sean ahora visibles. Esta lista no incluye todas las opciones, sino que define los usos comunes. En las descripciones siguientes, la primera transferencia no resulta en un evento de finalización en el destino, pero es eventualmente seguida por una transferencia que sí lo hace.

•
Si el punto de extremo garantiza el orden de mensajes entre dos transferencias, la finalización en el destino de una segunda transferencia indicará que los datos de la primera transferencia están disponibles. Por ejemplo, si el punto de extremo soporta el orden de escritura después de envío (FI_ORDER_SAW), entonces una finalización de recepción correspondiente al envío indicará que los datos de la escritura están disponibles. Esto se mantiene independientemente de la semántica de finalización del iniciador para la escritura o el envío. Cuando se garantiza el orden, la segunda transferencia puede ser encolada con el proveedor inmediatamente después de encolar la primera.
•
Si el punto de extremo no garantiza el orden de mensajes, el iniciador debe tomar pasos adicionales para asegurar la visibilidad. Si el iniciador solicita semántica FI_DELIVERY_COMPLETE para la primera operación, el iniciador puede esperar a que la operación complete localmente. Una vez que la finalización ha sido leída, la finalización en el destino de una segunda transferencia indicará que los datos de la primera transferencia son visibles.
•
Alternativamente, si el orden de mensajes no está garantizado por el punto de extremo, el iniciador puede usar los flags FI_FENCE y FI_DELIVERY_COMPLETE en la segunda transferencia de datos para forzar que las primeras transferencias cumplan con la semántica FI_DELIVERY_COMPLETE. Si la segunda transferencia genera una finalización en el destino, eso indicará que los datos son visibles. De lo contrario, una finalización en el destino de cualquier transferencia después de la operación cercada (fenced) indicará que los datos son visibles.

Las semánticas anteriores aplican para transferencias que apuntan a búfers de memoria tradicionales del host. Sin embargo, el comportamiento puede diferir cuando se involucra memoria de dispositivo y/o memoria persistente (bits de capacidad FI_HMEM y FI_PMEM). Cuando se involucra memoria heterogénea, el concepto de dominios de memoria entra en juego. Los dominios de memoria identifican la separación física de la memoria, la cual puede o no ser accesible a través del mismo espacio de direcciones virtuales. Vea la página del manual fi_mr(3) para más detalles sobre dominios de memoria.

El orden de finalización y la visibilidad de datos solo están bien definidos para transferencias que apuntan al mismo dominio de memoria. Las aplicaciones deben ser conscientes de las diferencias de orden y visibilidad cuando las transferencias apuntan a diferentes dominios de memoria. Adicionalmente, las aplicaciones también deben preocuparse por el dominio de memoria al que se escriben las finalizaciones mismas y si difiere del dominio de memoria al que apunta una transferencia. En algunas situaciones, ya sea el proveedor o la aplicación pueden necesitar llamar a APIs específicas del dispositivo para sincronizar o vaciar (flush) cachés de memoria de dispositivo para lograr la visibilidad de datos deseada.

Cuando se usa memoria heterogénea, la semántica de finalización en el destino por defecto para transferencias que generan una finalización en el destino sigue siendo FI_DELIVERY_COMPLETE, sin embargo, las aplicaciones deben ser conscientes de que puede haber un impacto negativo en el rendimiento general para que los proveedores cumplan con este requisito.

Por ejemplo, un proceso de destino puede estar usando una GPU para acelerar cálculos. Una región de memoria que mapea a memoria en la GPU puede ser expuesta a pares como un destino RMA o publicada localmente como un búfer de recepción. En este caso, la aplicación está preocupada con dos dominios de memoria – memoria de sistema y memoria de GPU. Las finalizaciones se escriben en memoria de sistema.

Continuando con el ejemplo, un proceso par envía un mensaje etiquetado. Ese mensaje es emparejado con el búfer de recepción ubicado en memoria de GPU. La NIC copia los datos de la red al búfer de recepción y escribe una entrada en la cola de finalización. Note que ambos dominios de memoria fueron accedidos como parte de esta transferencia. Los datos del mensaje fueron dirigidos a la memoria de GPU, pero la finalización fue a memoria host. Debido a que dominios de memoria separados pueden no estar sincronizados entre sí, es posible que la CPU host vea y procese la entrada de finalización antes de que la transferencia a la memoria de GPU sea visible para la GPU host o incluso para el software corriendo en la GPU. Desde la perspectiva del proveedor, la visibilidad de la finalización no implica la visibilidad de los datos escritos al dominio de memoria de la GPU.

La semántica de finalización por defecto en el destino aplicación para operaciones de mensaje es FI_DELIVERY_COMPLETE. Una implementación anticipada del proveedor en esta situación es que el software del proveedor corriendo en la CPU host intercepte la entrada de CQ, detecte que los datos aterrizaron en memoria heterogénea, y realice la operación de sincronización o vaciado (flush) de dispositivo necesaria antes de reportar la finalización hacia la aplicación. Esto asegura que los datos son visibles para el software de la CPU y GPU antes de que la aplicación procese la finalización.

Además del costo de que el software del proveedor intercepte finalizaciones y verifique si una transferencia apuntaba a memoria heterogénea, la sincronización del dispositivo misma puede impactar el rendimiento. Como resultado, las aplicaciones pueden solicitar una semántica de finalización más baja al publicar recepciones. Eso le indica al proveedor que la aplicación será responsable de manejar cualquier operación de vaciado (flush) específica del dispositivo que pueda ser necesaria. Vea fi_msg(3) FLAGS.

Para transferencias de datos que no generan una finalización en el destino, como RMA o operaciones atómicas, es responsabilidad de la aplicación asegurar que todos los búfers de destino cumplan con los requisitos de visibilidad necesarios de la aplicación. Los métodos con viñetas mencionados anteriormente para notificar al destino que los datos son visibles pueden no ser suficientes, ya que el software del proveedor en el destino podría carecer del contexto necesario para asegurar la visibilidad. Esto implica que la aplicación puede necesitar llamar APIs de sincronización/vaciado (flush) de dispositivo directamente.

Por ejemplo, una aplicación par podría realizar varias escrituras RMA que apuntan a búfers de memoria de GPU. Si el proveedor descarga operaciones RMA en la NIC, el software del proveedor en el destino no estará al tanto de que las operaciones RMA han ocurrido. Si el par envía un mensaje a la aplicación de destino que indica que las operaciones RMA están hechas, la aplicación debe asegurar que los datos RMA son visibles para la CPU host o GPU antes de ejecutar código que acceda a los datos. La finalización en el destino de haber recibido el mensaje enviado no es suficiente, incluso si se soporta el orden de escritura después de envío (send-after-write).

La mayoría de las semánticas de finalización en destino de memoria heterogénea se mapean a FI_TRANSMIT_COMPLETE o FI_DELIVERY_COMPLETE. La memoria persistente (capacidad FI_PMEM), sin embargo, es usada a menudo con semántica FI_COMMIT_COMPLETE. Los conceptos de finalización heterogénea aún aplican.

Para transferencias marcadas por el iniciador con FI_COMMIT_COMPLETE, una finalización en el destino indica que los resultados son visibles y durables. Para transferencias que apuntan a memoria persistente, pero que usan una semántica de finalización diferente en el iniciador, la visibilidad en el destino es similar a la descrita anteriormente. La durabilidad solo está asociada con transferencias marcadas con FI_COMMIT_COMPLETE.

Para transferencias que apuntan a memoria persistente que solicitan FI_DELIVERY_COMPLETE, entonces una finalización, ya sea en el iniciador o en el destino, indica que los datos son visibles. La visibilidad en el destino puede ser conveyada usando uno de los mecanismos descritos arriba – generando una finalización en el destino, enviando un mensaje desde el iniciador, etc. De manera similar, si el iniciador solicitó FI_TRANSMIT_COMPLETE, entonces se necesitan pasos adicionales para asegurar la visibilidad en el destino. Por ejemplo, la transferencia puede generar una finalización en el destino, lo cual indicaría visibilidad, pero no durabilidad. El iniciador también puede seguir la transferencia con otra operación que fuerce la visibilidad, como usar FI_FENCE en conjunto con FI_DELIVERY_COMPLETE.

NOTAS

Una cola de finalización debe estar vinculada a al menos un punto de extremo habilitado antes de que cualquier operación como fi_cq_read, fi_cq_readfrom, fi_cq_sread, fi_cq_sreadfrom etc. pueda ser llamada en ella.

Si una cola de finalización ha sido desbordada (overrun), será colocada en un estado `overrun'. Las operaciones de lectura continuarán devolviendo cualquier finalización válida, no corrupta, si está disponible. Después de que todas las finalizaciones válidas han sido recuperadas, cualquier intento de leer la CQ resultará en que devuelva un evento de error FI_EOVERRUN. Las colas de finalización desbordadas se consideran fatales y no pueden ser usadas para reportar finalizaciones adicionales una vez que el desbordamiento ocurre.

DESCRIPCIÓN

La función fi_cq_readerr lee un evento de error de la cola de completado (CQ) especificada. Si se especifica un -1 como destino, el evento se copia en la estructura fi_cq_err proporcionada.

Los eventos de error se devuelven en una cola de completado (CQ). Cada evento de error se devuelve en la estructura fi_cq_err. Esta estructura contiene la información necesaria para identificar el objeto asociado con el error y el código de error.

El parámetro ev debe apuntar a una estructura fi_cq_err válida. Si el evento de error se lee correctamente, la estructura fi_cq_err se llenará con la información del evento. El campo flags de la estructura fi_cq_err se puede utilizar para determinar si se trata de un evento de error específico o de un error general.

El parámetro count especifica el número de eventos de error que se intentarán leer. Si se especifica 0, la función intentará leer todos los eventos de error disponibles en la cola.

Los valores de errno de Fabric se definen en rdma/fi_errno.h.

fi_getinfo(3), fi_endpoint(3), fi_domain(3), fi_eq(3), fi_cntr(3), fi_poll(3)

AUTORES

OpenFabrics.

CAMPOS DE COMPLETADO

Los siguientes campos se definen en la estructura fi_cq_err:

err
El código de error específico devuelto con una solicitud de completado.

FLAGS DE COMPLETADO

Los siguientes campos se definen en la estructura fi_cq_err:

flags
Los flags asociados con el evento de completado. Ver fi_cq_entry para los flags disponibles.

SEMÁNTICA DEL EVENTO DE COMPLETADO

Los eventos de completado pueden contener información sobre el objeto asociado con el error. La información específica varía según el tipo de error y el proveedor.

SEMÁNTICA DEL COMPLETADO DE DESTINO

Cuando se utiliza -1 como destino, el evento de error se copia en la estructura proporcionada.

NOTAS

La función fi_cq_readerr está diseñada para recuperar eventos de error de la cola de completado. Si no hay eventos de error disponibles, la función puede devolver FI_EAVAIL o bloquearse, dependiendo de la configuración de la cola de completado.

Los eventos de error se asocian con objetos específicos, como puntos finales o transferencias de datos. La información sobre el objeto asociado se puede encontrar en la estructura fi_cq_err.

La estructura fi_cq_err es una extensión de la estructura fi_cq_entry y contiene campos adicionales para información de error.

VALORES DE RETORNO

En caso de éxito, fi_cq_readerr devuelve el número de eventos de error leídos. En caso de error, devuelve un número negativo que representa el código de error. Los códigos de error específicos se definen en rdma/fi_errno.h.

Los valores de error comunes incluyen:

FI_EAVAIL
No hay eventos de error disponibles en la cola.
FI_EINVAL
El parámetro ev es NULL o el parámetro count es inválido.
FI_ECANCELLED
La operación fue cancelada.

Consulte la documentación de la estructura fi_cq_err para obtener información sobre cómo interpretar el campo err y el campo flags. Fabric errno values are defined in rdma/fi_errno.h.
