DESCRIPCIÓ

N

La llamada a fi_getinfo() se utiliza para descubrir qué características de comunicación están disponibles en el sistema, así como cómo podrían ser utilizadas mejor por una aplicación. La llamada está libremente modelada en getaddrinfo(). fi_getinfo() permite a una aplicación intercambiar información entre una aplicación y los proveedores de libfabric respecto a su conjunto requerido de comunicación. Proporciona la capacidad de acceder a detalles complejos de red, equilibrando ser expresivo pero también simple de

usar.

fi_getinfo devuelve información sobre los servicios de fabric disponibles para alcanzar un nodo o servicio especificado, sujeto a cualquier sugerencia proporcionada. Los llamadores pueden especificar NULL para node, service, y hints con el fin de recuperar información sobre qué proveedores están disponibles y sus modelos de uso óptimos. Si no hay información de fabric coincidente disponible, info se establecerá en NULL y la llamada devolverá

-FI_ENODATA.

Basado en los parámetros de sugerencias, node, y service de entrada, se devolverá una lista de dominios de fabric y puntos de extremo. Cada estructura fi_info describirá un punto de extremo que cumple con los criterios de comunicación especificados por la aplicación. Cada punto de extremo estará asociado con un dominio. Las aplicaciones pueden restringir el número de puntos de extremo devueltos incluyendo criterios adicionales en sus sugerencias de búsqueda. Relajar o eliminar las sugerencias de entrada aumentará el número y tipo de puntos de extremo disponibles. Los proveedores que devuelvan múltiples puntos de extremo a una sola llamada a fi_getinfo deben devolver primero los puntos de extremo con mayor rendimiento. Los proveedores pueden indicar que un punto de extremo y dominio pueden soportar capacidades adicionales a las solicitadas por el usuario solo si tal soporte no afectará adversamente el rendimiento o la seguridad de la

aplicación.

El parámetro version es usado por la aplicación para solicitar la versión deseada de las interfaces. La versión determina el formato de todas las estructuras de datos usadas por cualquiera de las interfaces de fabric. Las aplicaciones deben usar la macro FI_VERSION(mayor, menor) para indicar la versión, con valores enteros codificados en duro para los valores mayor y menor. Los valores enumerados FI_MAJOR_VERSION y FI_MINOR_VERSION definidos en fabric.h especifican la última versión de la biblioteca instalada. Sin embargo, se recomienda que se usen los valores enteros de FI_MAJOR_VERSION y FI_MINOR_VERSION, en lugar de referenciar los tipos enumerados, para asegurar compatibilidad con futuras versiones de la biblioteca. Esto protege contra la aplicación siendo construida desde el código fuente contra una versión más nueva de la biblioteca que introduce nuevos campos en las estructuras de datos, los cuales no serían inicializados por la

aplicación.

Node, service, o hints pueden ser proporcionados, con cualquier combinación siendo soportada. Si node es proporcionado, fi_getinfo intentará resolver la dirección de fabric al nodo dado. Si node no es dado, fi_getinfo intentará resolver la información de direccionamiento de fabric basándose en las sugerencias proporcionadas. Node es comúnmente usado para proporcionar una dirección de red (como una dirección IP) o nombre de host. Service está usualmente asociado con una dirección de transporte (como un número de puerto TCP). Los parámetros node y service pueden ser mapeados por los proveedores a direcciones de fabric nativas. Las aplicaciones también pueden pasar una dirección con formato FI_ADDR_STR (ver detalles de formato más abajo) como el parámetro node. En tales casos, el parámetro service debe ser

NULL.

El parámetro hints, si es proporcionado, puede ser usado para limitar la salida resultante como se indica a continuación. Como regla general, especificar un valor distinto de cero para las sugerencias de entrada indica que un proveedor debe soportar el valor solicitado o fallar la operación con -FI_ENODATA. Con la excepción de los bits de modo, las sugerencias establecidas en cero se tratan como un comodín. Un valor de sugerencia en cero resulta en que los proveedores devuelvan un valor predeterminado o un valor que funcione mejor para su implementación. Los bits de modo establecidos en cero indican que la aplicación no soporta ningún

modo.

El llamador debe llamar a fi_freeinfo para liberar las estructuras fi_info devueltas por esta

llamada.

La llamada a fi_allocinfo asignará y pondrá en cero una estructura fi_inf

o y todas las subestructuras relacionadas. La fi_dupinfo duplicará u
na sola estructura fi_info y todas las subestructuras dentro de ella.

CAPABILITIES

Interface capabilities are obtained by OR-ing the following flags together. If capabilities in the hint parameter are set to 0, the underlying provider will return the set of capabilities which are supported. Otherwise, providers will return data matching the specified set of capabilities. Providers may indicate support for additional capabilities beyond those requested when the use of expanded capabilities will not adversely affect performance or expose the application to communication beyond that which was requested. Applications may use this feature to request a minimal set of requirements, then check the returned capabilities to enable additional optimizations.

FI_ATOMIC
Specifies that the endpoint supports some set of atomic operations. Endpoints supporting this capability support operations defined by struct fi_ops_atomic. In the absence of any relevant flags, FI_ATOMIC implies the ability to initiate and be the target of remote atomic reads and writes. Applications can use the FI_READ, FI_WRITE, FI_REMOTE_READ, and FI_REMOTE_WRITE flags to restrict the types of atomic operations supported by an endpoint.
FI_AV_USER_ID
Requests that the provider support the association of a user specified identifier with each address vector (AV) address. User identifiers are returned with completion data in place of the AV address. See fi_domain(3) and fi_av(3) for more details.
FI_COLLECTIVE
Requests support for collective operations. Endpoints that support this capability support the collective operations defined in fi_collective(3).
FI_DIRECTED_RECV
Requests that the communication endpoint use the source address of an incoming message when matching it with a receive buffer. If this capability is not set, then the src_addr parameter for msg and tagged receive operations is ignored.
FI_TAGGED_DIRECTED_RECV
Similar to FI_DIRECTED_RECV, but only applies to tagged receive operations.
FI_EXACT_DIRECTED_RECV
Similar to FI_DIRECTED_RECV, but requires the source address to be exact, i.e., FI_ADDR_UNSPEC is not allowed. This capability can be used alone, or in conjunction with FI_DIRECTED_RECV or FI_TAGGED_DIRECTED_RECV as a modifier to disallow FI_ADDR_UNSPEC being used as the source address.
FI_FENCE
Indicates that the endpoint support the FI_FENCE flag on data transfer operations. Support requires tracking that all previous transmit requests to a specified remote endpoint complete prior to initiating the fenced operation. Fenced operations are often used to enforce ordering between operations that are not otherwise guaranteed by the underlying provider or protocol.
FI_HMEM
Specifies that the endpoint should support transfers to and from device memory.
FI_LOCAL_COMM
Indicates that the endpoint support host local communication. This flag may be used in conjunction with FI_REMOTE_COMM to indicate that local and remote communication are required. If neither FI_LOCAL_COMM or FI_REMOTE_COMM are specified, then the provider will indicate support for the configuration that minimally affects performance. Providers that set FI_LOCAL_COMM but not FI_REMOTE_COMM, for example a shared memory provider, may only be used to communication between processes on the same system.
FI_MSG
Specifies that an endpoint should support sending and receiving messages or datagrams. Message capabilities imply support for send and/or receive queues. Endpoints supporting this capability support operations defined by struct fi_ops_msg.

The caps may be used to specify or restrict the type of messaging operations that are supported. In the absence of any relevant flags, FI_MSG implies the ability to send and receive messages. Applications can use the FI_SEND and FI_RECV flags to optimize an endpoint as send-only or receive-only.

FI_MULTICAST
Indicates that the endpoint support multicast data transfers. This capability must be paired with FI_MSG. Applications can use FI_SEND and FI_RECV to optimize multicast as send-only or receive-only.
FI_MULTI_RECV
Specifies that the endpoint must support the FI_MULTI_RECV flag when posting receive buffers.
FI_TAGGED_MULTI_RECV
Specifies that the endpoint must support the FI_MULTI_RECV flag when posting tagged receive buffers.
FI_NAMED_RX_CTX
Requests that endpoints which support multiple receive contexts allow an initiator to target (or name) a specific receive context as part of a data transfer operation.
FI_PEER
Specifies that the provider must support being used as a peer provider in the peer API flow. The provider must support importing owner_ops when opening a CQ, counter, and shared receive queue.
FI_READ
Indicates that the user requires an endpoint capable of initiating reads against remote memory regions. This flag requires that FI_RMA and/or FI_ATOMIC be set.
FI_RECV
Indicates that the user requires an endpoint capable of receiving message data transfers. Message transfers include base message operations as well as tagged message functionality.
FI_REMOTE_COMM
Indicates that the endpoint support communication with endpoints located at remote nodes (across the fabric). See FI_LOCAL_COMM for additional details. Providers that set FI_REMOTE_COMM but not FI_LOCAL_COMM, for example NICs that lack loopback support, cannot be used to communicate with processes on the same system.
FI_REMOTE_READ
Indicates that the user requires an endpoint capable of receiving read memory operations from remote endpoints. This flag requires that FI_RMA and/or FI_ATOMIC be set.
FI_REMOTE_WRITE
Indicates that the user requires an endpoint capable of receiving write memory operations from remote endpoints. This flag requires that FI_RMA and/or FI_ATOMIC be set.
FI_RMA
Specifies that the endpoint should support ROperaciones de lectura y escritura RMA. Los puntos de extremo que admiten esta capacidad admiten operaciones definidas por la estructura fi_ops_rma. En ausencia de cualquier bandera relevante, FI_RMA implica la capacidad de iniciar y ser el destino de lecturas y escrituras de memoria remota. Las aplicaciones pueden usar las banderas FI_READ, FI_WRITE, FI_REMOTE_READ y FI_REMOTE_WRITE para restringir los tipos de operaciones RMA admitidas por un punto de
extremo.

NT

extremo.

EM

Los proveedores conscientes de la memoria persistente deben admitir el registro de memoria respaldada por memoria no volátil, transferencias RMA hacia/desde la memoria persistente y semánticas de finalización mejoradas. Las capacidades pueden agruparse en tres categorías generales: primarias, secundarias y modificadores primarios. Las capacidades primarias deben ser solicitadas explícitamente por una aplicación, y un proveedor debe habilitar el soporte solo para aquellas capacidades primarias que fueron seleccionadas. Los modificadores primarios se utilizan para limitar una capacidad primaria, como restringir un punto de extremo a ser solo de envío. Si no se especifican modificadores para una capacidad aplicable, se asumen todos los modificadores relevantes. Consulte las definiciones anteriores para obtener

detalles.

Las capacidades secundarias pueden ser solicitadas opcionalmente por una aplicación. Si se solicitan, un proveedor debe admitir la capacidad o fallar la solicitud fi_getinfo (FI_ENODATA). Un proveedor puede informar opcionalmente capacidades secundarias no seleccionadas si hacerlo no comprometería el rendimiento o la

seguridad.

MOD

O

Los bits de modo operativo se utilizan para transmitir requisitos que una aplicación debe cumplir al usar las interfaces de la malla. Los modos especifican formas óptimas de acceder al punto de extremo o dominio reportado. Las aplicaciones que están diseñadas para admitir un modo específico de operación pueden ver un rendimiento mejorado cuando ese modo es deseado por el proveedor. Se recomienda que los proveedores admitan aplicaciones que deshabiliten cualquier modo preferido por el

proveedor.

En la entrada a fi_getinfo, las aplicaciones establecen los bits de modo que admiten. En la salida, los proveedores limpiarán los bits de modo que no sean necesarios para lograr un alto rendimiento. Los bits de modo que permanezcan establecidos indican requisitos de la aplicación para usar las interfaces de la malla creadas usando el fi_info devuelto. El conjunto de modos se lista a continuación. Si se proporciona una estructura de sugerencias NULL, entonces el conjunto de modos admitidos por el proveedor será devuelto en la(s) estructura(s) de

información.
FI_ASYNC_I
OV
Las aplicaciones pueden referenciar múltiples buffers de datos como parte de una sola operación mediante el uso de vectores de E/S (SGEs). Típicamente, el contenido de un vector de E/S es copiado por el proveedor a un área de buffer interna, o directamente al hardware subyacente. Sin embargo, cuando se admiten un gran número de entradas IOV, el buffering de IOV puede tener un impacto negativo en el rendimiento y el consumo de memoria. El modo FI_ASYNC_IOV indica que la aplicación debe proporcionar el buffering necesario para los vectores de E/S. Cuando está establecido, una aplicación no debe modificar un vector de E/S de longitud > 1, incluyendo cualquier matriz de descriptores de memoria relacionada, hasta que la operación asociada haya
completado.
FI_CONTE
XT
Especifica que el proveedor requiere que las aplicaciones usen la estructura fi_context como su parámetro de contexto por operación para operaciones que generaron finalizaciones completas. Esta estructura debe ser tratada como opaca para la aplicación. Por razones de rendimiento, esta estructura debe ser asignada por el usuario, pero puede ser usada por el proveedor de la malla para rastrear la operación. Típicamente, los usuarios incrustan struct fi_context dentro de su propia estructura de contexto. La struct fi_context debe permanecer válida hasta que la operación correspondiente complete o sea cancelada exitosamente. Como tal, fi_context NO debe ser asignada en la pila. Hacerlo probablemente resultará en corrupción de la pila que será difícil de depurar. Los usuarios no deben actualizar ni interpretar los campos en esta estructura, ni reutilizarla hasta que la operación original haya completado. Si una operación no genera una finalización (es decir, el punto de extremo fue configurado con FI_SELECTIVE_COMPLETION y la operación no fue iniciada con la bandera FI_COMPLETION), entonces el parámetro de contexto es ignorado por el proveedor de la malla. La estructura está especificada en rdma/fabric.
h.
FI_CONTEX
T2
Este bit es similar a FI_CONTEXT, pero duplica el requisito del proveedor sobre el tamaño de la estructura de contexto por operación. Cuando está establecido, esto especifica que el proveedor requiere que las aplicaciones usen la estructura fi_context2 como su parámetro de contexto por operación. O, opcionalmente, una aplicación puede proporcionar un arreglo de dos estructuras fi_context (por ejemplo, struct fi_context[2]) en su lugar. Los requisitos para usar la estructura fi_context2 son idénticos a los definidos para FI_CONTEXT
arriba.
FI_LOCAL_MR
(obsoleto)
El proveedor está optimizado para que las aplicaciones registren memoria para buffers de datos accedidos localmente. Los buffers de datos usados en operaciones de envío y recepción y como buffer de origen para operaciones RMA y atómicas deben ser registrados por la aplicación para dominios de acceso abiertos con esta capacidad. Esta bandera está definida para compatibilidad y se ignora si la versión de la aplicación es 1.5 o posterior y el mr_mode del dominio está establecido en algo distinto de FI_MR_BASIC o FI_MR_SCALABLE. Consulte el atributo de dominio mr_mode fi_domain(3) y fi_mr(3)

FI_MSG_PREF
IX
El modo de prefijo de mensaje indica que una aplicación proporcionará espacio de buffer delante de todos los buffers de envío y recepción de mensajes para uso del proveedor. Típicamente, el proveedor usa es
te espacio para implementar un protocolo, con los encabezados del protocolo siendo escritos en el área de prefijo. El contenido del espacio de prefijo debe ser tratado como opaco. El uso de FI_MSG_PREFIX
puede mejorar el rendimiento de la aplicación sobre ciertos proveedores al reducir el número de vectores de E/S referenciados por el hardware subyacente y eliminar la asignación de buffers del proveedor.

FI_MSG_PREFIX solo se aplica a operaciones de envío y recepción, incluyendo envíos y recepciones etiquetados. RMA y atómicos no requieren que la aplicación proporcione buffers de prefijo. El espacio de buffer de prefijo debe ser proporcionado con todos los envíos y recepciones, independientemente del tamaño de la transferencia u otras opciones de transferencia. La propiedad de los buffers de prefijo se trata igual que la de los buffers de mensaje correspondientes, pero el tamaño del buffer de prefijo no se cuenta hacia ningún límite de mensaje, incluyendo

inyección.

Las aplicaciones que admiten el modo de prefijo deben proporcionar espacio de buffer antes de sus propios datos de mensaje. El tamaño del espacio que debe ser proporcionado es especificado por el atributo de punto de extremo msg_prefix_size. Los proveedores están obligados a definir un msg_prefix_size que sea un múltiplo de 8 bytes. Adicionalmente, las aplicaciones pueden recibir paquetes generados por el proveedor que no contienen datos de la aplicación. Dichos mensajes recibidos indicarán un tamaño de transferencia que es igual o menor que msg_prefix_size

.

El puntero de búfer dado a todas las operaciones de envío y recepción debe apuntar al inicio de la región de prefijo del búfer (a diferencia de la carga útil). Para operaciones de envío/recepción scatter-gather, el búfer de prefijo debe ser una región contigua, aunque puede o no estar directamente adyacente a la porción de carga útil del

búfer.

NOTA

S

Varias llamadas de libfabric, incluyendo fi_getinfo, toman una struct fi_info como entrada. Las aplicaciones deben usar estructuras fi_info asignadas por libfabric. Una struct fi_info a cero puede ser asignada usando fi_allocinfo, que luego puede ser inicializada por el usuario. Una struct fi_info puede ser copiada para su modificación usando la llamada fi_dupinfo()

.

Si se proporcionan pistas (hints), la operación será controlada por los valores que se proporcionan en los varios campos (ver la sección sobre fi_info). Las aplicaciones que requieren interfaces de comunicación, dominios, capacidades u otros requisitos específicos, pueden especificarlos usando campos en hints. Libfabric devuelve una lista enlazada en info que apunta a una lista de interfaces coincidentes. info se establece en NULL si no hay interfaces de comunicación o ninguna coincide con las pistas de

entrada.

Si se proporciona node, fi_getinfo intentará resolver la dirección de fabric al node dado. Si no se proporciona node, fi_getinfo intentará resolver la información de direccionamiento de fabric basándose en las pistas proporcionadas. El llamador debe llamar a fi_freeinfo para liberar las estructuras fi_info devueltas por

fi_getinfo.

Si no se proporciona node, service ni hints, entonces fi_getinfo simplemente devuelve la lista de todas las interfaces de comunicación

disponibles.

Múltiples hilos pueden llamar a fi

_getinfo simultáneamente, sin ning
ún requisito de serialización.
