fi_poll_open

(obsoleto)

fi_poll_open crea un nuevo conjunto de sondeo. Un conjunto de sondeo permite un método optimizado para progresar operaciones asíncronas a través de múltiples colas de completado y contadores y comprobar sus

completados.

fi_poll

(obsoleto)

Progresa todas las colas de completado y contadores asociados con un conjunto de sondeo y comprueba eventos. Si podrían haber ocurrido eventos, se devuelven los contextos asociados con las colas de completado y/o los contadores. Las colas de completado devolverán su contexto si no están vacías. El contexto asociado con un contador se devolverá si el valor de éxito o el valor de error del contador han cambiado desde la última vez que se llamó a fi_poll, fi_cntr_set o fi_cntr_add. El número de contextos está limitado al tamaño de la matriz de contextos, indicado por el parámetro

count.

Tenga en cuenta que fi_poll solo indica que podrían estar disponibles eventos. En algunos casos, los proveedores podrían consumir tales eventos internamente, para impulsa

r el progreso, por ejemplo. Esto puede resultar en que fi_poll devuelva falsos positivos. Las aplicaciones deben impulsar su progreso basándose en los resultados de leer
eventos de una cola de completado o leer valores de contadores. La función fi_poll siempre devolverá todas las colas de completado y contadores que tengan nuevos eventos.

fi_wait_open

(obsoleto)

fi_wait_open asigna un nuevo conjunto de espera. Un conjunto de espera permite un método optimizado de espera de eventos a través de múltiples colas de completado y contadores. Donde sea posible, un conjunto de espera usa un único objeto de espera subyacente que es señalizado cuando ocurre una condición especificada en una cola de completado o contador

asociado.

Las propiedades y el comportamiento de un conjunto de espera se definen por struct

fi_wait_attr. 
struct fi_wait_attr {
    enum fi_wait_obj     wait_obj;  /* objeto de espera solicitado */
    uint64_t             flags;     /* banderas de operación
*/
}
;

Los conjuntos de espera se asocian con objetos de espera específicos. Los objetos de espera permiten a las aplicaciones bloquearse hasta que el objeto de espera sea señalizado, indicando que hay un evento disponible para leer. Los siguientes valores pueden usarse para especificar el tipo de objeto de espera asociado con un conjunto de espera: FI_WAIT_UNSPEC, FI_WAIT_FD, FI_WAIT_MUTEX_COND (obsoleto) y
FI_WAIT_YIELD.
- FI_WAIT_UNSP
EC
Especifica que el usuario solo esperará en el conjunto de espera usando llamadas de interfaz de fabric, como fi_wait. En este caso, el proveedor subyacente puede seleccionar el objeto de espera más apropiado o de mayor rendimiento disponible, incluyendo mecanismos de espera personalizados. Las aplicaciones que seleccionan FI_WAIT_UNSPEC no tienen garantía de recuperar el objeto de espera
subyacente.
- FI_WAIT_
FD
Indica que el conjunto de espera debe usar un único descriptor de archivo como su mecanismo de espera, tal como se expone a la aplicación. Internamente, esto puede requerir el uso de epoll para soportar la espera en un único descriptor de archivo. Los objetos de espera de descriptor de archivo deben ser utilizables en las rutinas POSIX select(2) y poll(2), y Linux epoll(7) (si están disponibles). Los proveedores señalizan un objeto de espera FD marcándolo como legible o con un
error.
- FI_WAIT_MUTEX_COND
(obsoleto)
Especifica que el conjunto de espera debe usar un mutex pthread y una variable de condición como objeto de
espera.
- FI_WAIT_POLL
FD
Esta opción es similar a FI_WAIT_FD, pero permite que el mecanismo de espera use múltiples descriptores de archivo como su mecanismo de espera, tal como lo ve la aplicación. El uso de FI_WAIT_POLLFD puede eliminar la necesidad de usar epoll para abstraer la necesidad de comprobar múltiples descriptores de archivo al esperar eventos. Los descriptores de archivo deben ser utilizables en el POSIX rutinas poll(2), y coinciden directamente con su uso con poll. Consulte la sección NOTAS a continuación para obtener detalles sobre el uso de
pollfd.
- FI_WAIT_YIE
LD
Indica que el conjunto de espera esperará sin un objeto de espera, sino que cederá en cada
espera.

fi_trywai

t

La llamada fi_trywait se introdujo en la versión 1.3 de libfabric. El comportamiento de usar objetos de espera nativos sin el uso de fi_trywait es específico del proveedor y debe considerarse no

determinista.

La llamada fi_trywait() se utiliza junto con las llamadas nativas del sistema operativo para bloquear en objetos de espera, como descriptores de archivo. La aplicación debe llamar a fi_trywait y obtener un valor de retorno de FI_SUCCESS antes de bloquear en un objeto de espera nativo. El incumplimiento de esto puede resultar en que el objeto de espera no sea señalizado y la aplicación no observe los eventos deseados. El siguiente pseudocódigo demuestra el uso de fi_trywait junto con la llamada select(2) del

SO. 
fi_control(&cq->fid, FI_GETWAIT, (void *) &fd);
FD_ZERO(&fds);
FD_SET(fd, &fds);
while (1) {
    if (fi_trywait(&cq, 1) == FI_SUCCESS)
        select(fd + 1, &fds, NULL, &fds, &timeout);
    do {
        ret = fi_cq_read(cq, &comp, 1);
    } while (ret >
0);
}

fi_trywait() devolverá FI_SUCCESS si es seguro bloquear en el(los) objeto(s) de espera correspondiente(s) al(des) descriptor(es) de fabrica, o -FI_EAGAIN si hay eventos en cola en el descriptor de fabrica o si bloquear podría colgar la

aplicación.

La llamada toma un arreglo de descriptores de fabrica. Para cada objeto de espera que se pasará a la rutina de espera nativa, el descriptor de fabrica correspondiente debe pasarse primero a fi_trywait. Todos los descriptores de fabrica pasados a una sola llamada de fi_trywait deben hacer uso del mismo tipo de objeto de espera

subyacente.

Los siguientes tipos de descriptores de fabrica pueden pasarse a fi_trywait: colas de eventos, colas de finalización, contadores y conjuntos de espera. Las aplicaciones que deseen usar llamadas de espera nativas deben seleccionar objetos de espera específicos al asignar dichos recursos. Por ejemplo, estableciendo el valor del atributo de creación del elemento wait_obj en

FI_WAIT_FD.

En el caso de que el objeto de espera a comprobar pertenezca a un conjunto de espera, solo el conjunto de espera en sí necesita pasarse a fi_trywait. Los recursos de fabrica asociados con el conjunto de espera no es

necesario.

Al recibir un valor de retorno de -FI_EAGAIN de fi_trywait, una aplicación debe leer todas las finalizaciones y even

tos en cola, y llamar a fi_trywait de nuevo antes de intentar bloquear. Las aplicaciones pueden hacer uso de un
conjunto de sondeo de fabrica para identificar colas de finalización y contadores que pueden requerir procesamiento.

La llamada fi_control se utiliza para acceder a detalles específicos del proveedor o de la implementación de los fids que soportan llamadas bloqueantes, como conjuntos de espera, colas de finalización, contadores y colas de eventos. El acceso al conjunto de espera o fid debe serializarse en todas las llamadas cuando se invoca fi_control, ya que puede redirigir la implementación de las operaciones del conjunto de espera. El parámetro arg de fi_control debe ser una dirección donde se escribirá un puntero al objeto de espera devuelto. NOTA

S

En muchas situaciones, las llamadas bloqueantes pueden necesitar esperar señales enviadas a un número de descriptores de archivo. Por ejemplo, este es el caso para los proveedores basados en sockets, como tcp y udp, así como los proveedores de utilidades como multi-rail. Por simplicidad, cuando epoll está disponible, se puede utilizar para limitar el número de descriptores de archivo que una aplicación debe monitorear. El uso de epoll también puede ser necesario para soportar

FI_WAIT_FD.

Sin embargo, para soportar la espera en múltiples descriptores de archivo en sistemas donde el soporte de epoll no está disponible, o donde el rendimiento de epoll puede impactar negativamente el rendimiento, FI_WAIT_POLLFD proporciona este mecanismo. Una diferencia significativa entre usar objetos de espera POLLFD y FD es que con FI_WAIT_POLLFD, los descriptores de archivo pueden cambiar dinámicamente. Como ejemplo, los descriptores de archivo asociados con el conjunto de espera de una cola de finalización pueden cambiar a medida que se añaden y eliminan asociaciones de puntos de extremo con la

CQ.

La estructura fi_wait_pollfd se utiliza para recuperar todos los descriptores de archivo para fids que usan FI_WAIT_POLLFD para soportar llamadas

bloqueantes. 
struct fi_wait_pollfd {
    uint64_t      change_index;
    size_t        nfds;
    struct pollfd
*fd;
}
;
change_ind
ex
El change_index puede usarse para determinar si ha habido cambios en la lista de descriptores de archivo. Cada vez que se añade, elimina o se actualizan los eventos de un descriptor de archivo, este campo se incrementa por el proveedor. Las aplicaciones que deseen esperar en descriptores de archivo directamente deben almacenar en caché el valor de change_index. Antes de bloquear en eventos de descriptor de archivo, la aplicación debe usar fi_control() para recuperar el change_index actual y compararlo con su valor almacenado en caché. Si los valores difieren, la aplicación debe actualizar su lista de descriptores de archivo antes de
bloquear.
nf
ds
En la entrada a fi_control(), esto indica el número de entradas en el arreglo struct pollfd *. En la salida, se establecerá en el número de entradas necesarias para almacenar el número actual de descriptores de archivo. Si el valor de entrada es menor que el valor de salida, fi_control() devolverá el error -FI_ETOOSMALL. Tenga en cuenta que establecer nfds = 0 permite una forma eficiente de comprobar el
change_index.
f
d
Esto apunta a un arreglo de entradas struct pollfd. El número de entradas se especifica a través del campo nfds. Si el númer
o de entradas necesarias es menor o igual al número de entradas disponibles, el arreglo struct pollfd se rellenará con
una lista de descriptores de archivo y eventos correspondientes que pueden usarse en las llamadas select(2) y poll(2).

El change_index se actualiza solo cuando los descriptores de archivo asociados con el conjunto de archivos pollfd han camb

iado. Comprobar el change_index es un paso adicional necesario cuando se trabaja directamente con objetos de espera F
I_WAIT_POLLFD. El uso de la función fi_trywait() sigue siendo necesario si se accede a los objetos de espera directamente.
