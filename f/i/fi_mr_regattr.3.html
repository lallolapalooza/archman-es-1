DESCRIPCIÓ

N

Las regiones de memoria registradas asocian búferes de memoria con permisos concedidos para el acceso por recursos de la fabrica. Un búfer de memoria debe registrarse con un dominio de recursos antes de poder utilizarse como destino de una transferencia de datos RMA o atómica remota. Además, un proveedor de fabrica puede requerir que los búferes de datos se registren antes de ser utilizados en transferencias locales. Las restricciones de registro de memoria se controlan utilizando un conjunto separado de bits de modo, especificados a través de los atributos del dominio (campo mr_mode). Cada bit mr_mode requiere que una aplicación tome pasos específicos para usar búferes de memoria con las interfaces de

libfabric.

Como caso especial, una nueva región de memoria puede crearse a partir de una región de memoria existente. Esta nueva región de memoria se denomina sub-MR, y la región de memoria existente se denomina MR base. Las sub-MR pueden utilizarse para compartir recursos de hardware, como traducciones de direcciones virtuales a físicas y fijación de páginas. Esto puede mejorar el rendimiento al crear y destruir subregiones que requieren diferentes derechos de acceso. La MR base misma también puede ser una sub-MR, permitiendo una jerarquía de regiones de

memoria.

Lo siguiente se aplica al registro de

memoria.
Registro de memoria
predeterminado
Si no se establecen bits mr_mode, se siguen los comportamientos predeterminados descritos a continuación. Históricam
ente, estos valores predeterminados se denominaban colectivamente registro de memoria escalable. Los requisitos pred
eterminados se describen a continuación, seguidos de definiciones de cómo cada bit mr_mode altera la definición.

Compatibilidad: Para versiones de biblioteca 1.4 y anteriores, esto se indicaba estableciendo mr_mode en FI_MR_SCALABLE y el bit de modo fi_info FI_LOCAL_MR en 0. FI_MR_SCALABLE y FI_LOCAL_MR fueron obsoletos en la versión 1.5 de libfabric, aunque se admiten con fines de compatibilidad hacia

atrás.

Por seguridad, se requiere registro de memoria para búferes de datos a los que accede directamente un proceso par. Por ejemplo, se requiere registro para búferes de destino RMA (leídos o escritos), y aquellos a los que acceden operaciones atómicas o

colectivas.

Por defecto, el registro ocurre en rangos de direcciones virtuales. Debido a que el registro se refiere a rangos de direcciones, en lugar de búferes de datos asignados, los rangos de direcciones no necesitan mapearse a búferes de datos asignados por la aplicación en el momento de la llamada de registro. Es decir, una aplicación puede registrar cualquier rango de direcciones en su espacio de direcciones virtuales, independientemente de si esas direcciones están respaldadas por páginas físicas o han sido

asignadas.

Tenga en cuenta que las páginas físicas deben respaldar las direcciones antes de que las direcciones sean accedidas como parte de una operación de transferencia de datos, o las transferencias de datos fallarán. Además, dependiendo de la operación, esto podría resultar en que el proceso local reciba una falla de segmentación por acceder a memoria no

válida.

Una vez registradas, las regiones de memoria resultantes son accesibles por los pares a partir de una dirección base de 0. Es decir, la dirección de destino que se especifica es un desplazamiento de bytes dentro de la región

registrada.

La aplicación también selecciona la clave de acceso asociada con la MR. El tamaño de la clave está restringido a un máximo de 8

bytes.

Con el registro escalable, los búferes de datos accedidos localmente no se registran. Esto incluye búferes de origen para todas las operaciones de transmisión – envíos, envíos etiquetados, RMA y atómicos – así como búferes publicados para operaciones de recepción y recepción

etiquetada.

Aunque el comportamiento predeterminado de registro de memoria es conveniente para los desarrolladores de aplicaciones, es difícil de implementar en hardware. Los intentos de ocultar los requisitos de hardware a la aplicación a menudo resultan en impactos significativos e inaceptables en el rendimiento. Los siguientes bits mr_mode se proporcionan como entrada a fi_getinfo. Si un proveedor requiere el comportamiento definido para un bit mr_mode, dejará el bit establecido en la salida de fi_getinfo. De lo contrario, el proveedor puede limpiar el bit para indicar que el comportamiento no es

necesario.

Al establecer un bit mr_mode, la aplicación ha acordado ajustar su comportamiento según lo indicado. Lo más importante, las aplicaciones que elijan admitir un mr_mode deben estar preparadas para manejar el caso en que el mr_mode no se requiere. Un proveedor limpiará un bit mr_mode si no es

necesario. class="Bl-tag">
FI_MR_LOC
AL
Cuando se establece el bit de modo FI_MR_LOCAL, las aplicaciones deben registrar
todos los búferes de datos a los que accederá el hardware local y proporcionar un parámetro desc válido en las operaciones de transferencia de datos aplicables.

Cuando FI_MR_LOCAL no está establecido, las aplicaciones no están obligadas a registrar los búferes de datos antes de usarlos para operaciones locales (por ejemplo, búferes de datos de envío y recepción). Antes de libfabric 1.22, el parámetro desc era ignorado. En libfabric 1.22 y versiones posteriores, el parámetro desc debe ser válido o NULL. Este comportamiento permite a las aplicaciones pasar opcionalmente un parámetro desc válido. Si el parámetro desc es NULL, cualquier registro de memoria local requerido será manejado por el

proveedor.

Un proveedor puede ocultar los requisitos de registro local a las aplicaciones utilizando una caché de registro interna o mecanismos similares. Sin embargo, estos mecanismos pueden afectar negativamente el rendimiento de algunas aplicaciones, notablemente aquellas que gestionan sus propios búferes de red. Para soportar el mayor rango de aplicaciones posible, sin afectar indebidamente su rendimiento, las aplicaciones que deseen gestionar sus propios registros de memoria local pueden hacerlo utilizando las llamadas de registro de memoria y pasando un parámetro desc

válido.

Nota: el bit mr_mode FI_MR_LOCAL reemplaza al bit de modo fi_info FI_LOCAL_MR. Cuando FI_MR_LOCAL está establecido, FI_LOCAL_MR es

ignorado.

El bit FI_MR_VIRT_ADDR indica que el proveedor referencia las regiones de memoria por dirección virtual, en lugar de un desplazamiento basado en 0. Los pares que se dirigen a regiones de me

FI_MR_ALLOCA
TED
Cuando está establecido, todas las regiones de memoria registradas deben estar respaldadas por páginas de memoria física en el momento en que se realiza la llamada de registro. Además
, las aplicaciones no deben realizar operaciones que puedan resultar en que el mapeo de la dirección virtual subyacente a la página física cambie (por ejemplo, llamar a free() contra
una MR asignada). No adherirse a esto puede resultar en que la dirección virtual apunte a un conjunto de páginas físicas mientras que la MR apunte a otro conjunto de páginas físicas.

Cuando no está establecido, las regiones de memoria registradas no necesitan estar respaldadas por páginas de memoria física en el momento en que se realiza la llamada de registro. Además, se permite que el mapeo subyacente de la dirección virtual a la página física cambie, y el proveedor se asegurará de que la MR correspondiente se actualice en consecuencia. Este comportamiento permite casos de uso de aplicaciones donde la memoria puede ser frecuentemente liberada y realocada, o la memoria del sistema migrando hacia/desde la memoria del

dispositivo.

Cuando no está establecido, la aplicación es responsable de asegurar que una región de memoria registrada referencie páginas físicas válidas mientras una transferencia de datos está activa contra ella, o la transferencia de datos puede fallar. Los cambios de la aplicación en el rango de direcciones virtuales deben coordinarse con el tráfico de red hacia o desde ese

rango.

Si no está establecido y FI_HMEM es soportado, la capacidad del mapeo de dirección virtual a dirección física para cambiar se extiende a las interfaces HMEM también. Si un proveedor no puede soportar un cambio de dirección virtual a dirección física para una interfaz HMEM dada, el proveedor debería soportar una alternativa razonable o la operación debería

fallar.

Las aplicaciones que soportan FI_MR_PROV_KEY pueden obtener la clave del proveedor usando fi_mr_key(), a menos que FI_MR_RAW también esté establecido. La clave devuelta debe ser intercambiada con los pares antes de iniciar una operación RMA o

(Es decir, FI_MR_ALLOCATED es típicamente 0). Sin embargo, dichos proveedores requieren que las aplicaciones notifiquen al proveedor antes de que la MR sea accedida como parte de una operación de transferencia de datos. Esta notificación informa al proveedor que todas las páginas físicas necesarias ahora respaldan la región. La notificación es necesaria para proveedores que no pueden engancharse directamente en las tablas de páginas del sistema operativo o la unidad de gestión de memoria. Consulte fi_mr_refresh() para detalles de la
notificación.

Registro de Memoria Básico
(obsoleto)
El registro de memoria básico fue obsoleto en la versión 1.5 de libfabric, pero se soporta para compatibilidad hacia atrás. El registro de memoria básico se indica estable
ciendo mr_mode igual a FI_MR_BASIC. FI_MR_BASIC debe establecerse solo y no emparejarse con bits mr_mode. A diferencia de otros bits mr_mode, si FI_MR_BASIC está establec
ido en la entrada de fi_getinfo(), no será borrado por el proveedor. Es decir, establecer mr_mode igual a FI_MR_BASIC fuerza el registro básico si el proveedor lo soporta.

El comportamiento del registro básico es equivalente a requerir los siguientes bits mr_mode: FI_MR_VIRT_ADDR, FI_MR_ALLOCATED y FI_MR_PROV_KEY. Adicionalmente, los proveedores que soportan el registro básico usualmente requieren el bit de modo fi_info (obsoleto) FI_LOCAL_MR, que fue incorporado en el bit mr_mode

FI_MR_LOCAL.

Las funciones de registro – fi_mr_reg, fi_mr_regv y fi_mr_regattr – se usan para registrar una o más regiones de memoria con recursos de fabric. La principal diferencia entre las funciones de registro es el número y tipo de parámetros que aceptan como entrada. De lo contrario, realizan la misma función

general.

Obsoleto : Por defecto, el registro de memoria se completa de forma sincrónica. Es decir, la llamada de registro no retornará hasta que el registro se haya completado. El registro de memoria puede completarse de forma asíncrona enlazando el dominio de recursos a una cola de eventos usando el indicador FI_REG_MR. Consulte fi_domain_bind. Cuando el registro de memoria es asíncrono, para evitar una condición de carrera entre el retorno de la llamada de registro y la lectura correspondiente del evento de la cola de eventos (EQ), el parámetro de salida mr será escrito antes de que cualquier evento asociado con la operación pueda ser leído por la aplicación. No se generará un evento asíncrono a menos que la llamada de registro retorne éxito (0)

.

fi_mr_re

g

El fi_mr_reg cregistra el búfer de memoria especificado por el usuario con el dominio de recursos. El búfer se habilita para su acceso por parte del hardware de la fabrica basándose en los permisos de acceso proporcionados. Consulte la descripción del campo de acceso para los atributos de la región de memoria a continuación.

La memoria registrada se asocia con un descriptor de memoria local y, opcionalmente, con una clave de memoria remota. Un descriptor de memoria es un identificador específico del proveedor asociado con la memoria registrada. Los descriptores de memoria a menudo se mapean a índices o claves específicos del hardware asociados con la región de memoria. Las claves de memoria remota proporcionan una protección limitada contra el acceso no deseado por parte de un nodo remoto. Los accesos remotos a una región de memoria deben proporcionar la clave asociada con el registro.

Dado que las claves MR deben ser proporcionadas por un proceso remoto, una aplicación puede usar el parámetro requested_key para indicar que se devuelva un valor de clave específico. El soporte para claves solicitadas por el usuario es específico del proveedor y está determinado por el valor del indicador FI_MR_PROV_KEY en el atributo de dominio mr_mode.

Las operaciones RMA y atómicas remotas indican la ubicación dentro de una región de memoria registrada especificando una dirección. La ubicación se referencia añadiendo el desplazamiento a la dirección virtual base del búfer o a 0, dependiendo del mr_mode.

El parámetro offset está reservado para uso futuro y debe ser 0.

Para solicitudes de registro de memoria asíncronas, el resultado se informará al usuario a través de una cola de eventos asociada con el dominio de recursos. Si es exitosa, la estructura de región de memoria asignada se devolverá al usuario a través del parámetro mr. La dirección mr debe permanecer válida hasta que la operación de registro se complete. El contexto especificado con la solicitud de registro se devuelve con el evento de finalización.

Para dominios abiertos con FI_AV_AUTH_KEY, fi_mr_reg no es compatible y se debe usar fi_mr_regattr.

fi_mr_regv

La llamada fi_mr_regv añade soporte para una lista de dispersión-agrupamiento (scatter-gather) a fi_mr_reg. Se registran múltiples búferes de memoria como una única región de memoria. De lo contrario, la operación es la misma.

Para dominios abiertos con FI_AV_AUTH_KEY, fi_mr_regv no es compatible y se debe usar fi_mr_regattr.

fi_mr_regattr

La llamada fi_mr_regattr es una llamada de registro más genérica y extensible que permite al usuario especificar la solicitud de registro usando una struct fi_mr_attr (definida a continuación).

fi_close

Fi_close se utiliza para liberar todos los recursos asociados con el registro de una región de memoria. Una vez desregistrado, no se garantiza un mayor acceso a la memoria registrada. Las operaciones activas o en cola que referencian una región de memoria que se está cerrando pueden intentar acceder a una región de memoria no válida y fallar. Después de que un MR se cierre, cualquier nueva operación dirigida al MR cerrado también fallará. Las aplicaciones son responsables de asegurarse de que un MR ya no es necesario antes de cerrarlo. Tenga en cuenta que los accesos a un MR cerrado desde un par remoto resultarán en un error en el par. El estado del punto de conexión local no se verá afectado.

Para los MR que están asociados con un punto de conexión (el indicador FI_MR_ENDPOINT está establecido), el MR debe cerrarse antes que el punto de conexión. Si aún hay recursos asociados con el MR al intentar cerrarlo, la llamada devolverá -FI_EBUSY.

Si se utiliza una caché de registro de memoria, el comportamiento de fi_close puede verse afectado. Hay más información sobre la caché de registro de memoria en la sección CACHÉ DE REGISTRO DE MEMORIA.

fi_mr_desc

Obtiene el descriptor de memoria local asociado con un MR. El registro de memoria debe haberse completado con éxito antes de invocar esta llamada.

fi_mr_key

Devuelve la clave de protección remota asociada con un MR. El registro de memoria debe haberse completado con éxito antes de invocar esto. La clave devuelta puede usarse en operaciones de transferencia de datos en un par. Si el bit de modo FI_MR_RAW ha sido establecido para el dominio, entonces la clave de memoria debe obtenerse usando la función fi_mr_raw_key en su lugar. Se devolverá un valor de retorno FI_KEY_NOTAVAIL si el registro no se ha completado o se requiere una clave de memoria cruda (raw).

fi_mr_raw_attr

Devuelve la clave de protección remota cruda (raw) y la dirección base asociada con un MR. El registro de memoria debe haberse completado con éxito antes de invocar esta rutina. El uso de esta llamada es necesario si el bit de modo FI_MR_RAW ha sido establecido por el proveedor; sin embargo, es seguro usar esta llamada con cualquier región de memoria.

En la entrada, el parámetro key_size debe indicar el tamaño del búfer raw_key. Si la clave real es más grande de lo que puede caber en el búfer, devolverá -FI_ETOOSMALL. En la salida, key_size se establece al tamaño del búfer necesario para almacenar la clave, que puede ser mayor que el valor de entrada. El key_size necesario también se puede obtener a través del campo del atributo de dominio mr_key_size (fi_domain_attr).

Una clave cruda (raw) debe ser mapeada por un par antes de que pueda usarse en operaciones de transferencia de datos. Consulte fi_mr_map_raw a continuación.

fi_mr_map_raw

Las claves de protección crudas (raw) deben mapearse a un valor de clave utilizable antes de que puedan usarse para operaciones de transferencia de datos. El mapeo lo realiza el par que inicia la operación RMA o atómica. La función de mapeo toma como entrada la clave cruda y su tamaño, y devuelve la clave mapeada. El uso de la función fi_mr_map_raw es necesario si el par tiene el bit de modo FI_MR_RAW establecido, pero esta rutina puede llamarse con cualquier clave válida. Todas las claves mapeadas deben liberarse llamando a fi_mr_unmap_key cuando el acceso a la región de memoria del par ya no sea necesario.

fi_mr_unmap_key

Esta llamada libera cualquier recurso que pueda haberse asignado como parte del mapeo de una clave de memoria cruda (raw). Todas las claves mapeadas deben liberarse antes de que se cierre el dominio correspondiente.

fi_mr_bind

La función fi_mr_bind asocia una región de memoria con un contador o un punto de conexión. Los enlaces de contador son necesarios para los proveedores que soportan la generación de finalizaciones basadas en operaciones de la fabrica. Los enlaces de punto de conexión son necesarios si el proveedor asocia regiones de memoria con puntos de conexión (ver FI_MR_ENDPOINT).

Al enlazar con un contador, el tipo de eventos rastreados contra la región de memoria se basa en el OR bit a bit de los siguientes indicadores.

FI_REMOTE_WRITE
Genera un evento siempre que una escritura RMA remota u operación atómica modifique la región de memoria. El uso de este indicador requiere que el punto de conexión a través del cual se accede al MR sea creado con la capacidad FI_RMA_EVENT.

Al enlazar la región de memoria con un punto de conexión, los indicadores (flags) deben ser 0.

fi_mr_refresh

El uso de esta llamada es notificar al proveedor de cualquier cambio en las páginas físicas que respaldan una región de memoria registrada. Esta llamada debe ser soportada por los proveedores que requieren FI_MR_MMU_NOTIFY y puede ser soportada opcionalmente por los proveedores que no requieren FI_MR_ALLOCATED.

Esta llamada informa al proveedor que las entradas de la tabla de páginas asociadas con la región pueden haber sido modificadas, y el proveedor debe verificar y actualizar la región registrada en consecuencia. El parámetro iov es opcional y puede usarse para especificar qué porciones de la región registrada requieren actualización.

A los proveedores solo se les garantiza que actualizarán los rangos de dirección especificados. El fallo al actualizar un rango resultará en un error devuelto.

Cuando FI_MR_MMU_NOTIFY está establecido, la operación de refresco tiene el efecto de deshabilitar y volver a habilitar el acceso a la región registrada. Cualquier operación de pares que intente acceder a la región fallará mientras el refresco esté ocurriendo. Adicionalmente, los intentos de acceder a la región por parte del proceso local a través de las API de libfabric pueden resultar en una falta de página u otra operación fatal.

Cuando FI_MR_ALLOCATED no está establecido, se devolverá -FI_ENOSYS si un proveedor no soporta fi_mr_refresh. Si es compatible, el proveedor actualizará atómicamente las páginas físicas del MR asociadas con los rangos de dirección especificados por el usuario. El MR permanecerá habilitado durante este tiempo.

Nota: El comportamiento de FI_MR_MMU_NOTIFY establecido tiene precedencia sobre el comportamiento de FI_MR_ALLOCATED no establecido.

La llamada fi_mr_refresh solo es necesaria si las páginas físicas podrían haberse actualizado después de que se creó la región de memoria.

fi_mr_enable

La llamada enable se usa con el registro de memoria asociado con el bit de modo FI_MR_RMA_EVENT. Las regiones de memoria creadas en el estado deshabilitado deben ser habilitadas explícitamente después de ser configuradas completamente por la aplicación. Cualquier enlace de recursos al MR debe hacerse antes de habilitar el MR.

NOTAS

El acceso directo a la memoria de una aplicación por un par remoto requiere que la aplicación registre el(los) búfer(es) de memoria objetivo. Esto se hace típicamente llamando a una de las rutinas fi_mr_reg*. Para FI_MR_PROV_KEY, el proveedor devolverá una clave que debe usar el par al acceder a la región de memoria. La aplicación es responsable de transferir esta clave al par. Si se ha establecido el modo FI_MR_RAW, la clave debe recuperarse usando la función fi_mr_raw_attr.

FI_MR_RAW permite el soporte para proveedores que requieren más de 8 bytes para sus claves de protección o necesitan una configuración adicional antes de que una clave pueda usarse para transferencias. Después de recuperar una clave en bruto, debe intercambiarse con el par remoto. El par debe usar fi_mr_map_raw para convertir la clave en bruto en una clave de 64 bits utilizable. El mapeo debe hacerse incluso si la clave en bruto tiene 64 bits o menos.

Las funciones de soporte de claves en bruto son utilizables con todas las regiones de memoria registradas, incluso si no se ha establecido FI_MR_RAW. Se recomienda que las aplicaciones portables apunten a usar esas interfaces; sin embargo, su uso conlleva una sobrecarga adicional de mensajes y memoria, lo que lo hace menos deseable para aplicaciones altamente escalables.

Puede haber casos en los que el soporte de par a par de dispositivos no deba usarse o no pueda usarse, como cuando la configuración ACS de PCIe no permite la transferencia. Se puede establecer la variable de entorno FI_HMEM_DISABLE_P2P para notificar a Libfabric que no se deben usar transacciones de par a par. El proveedor puede optar por realizar una copia en su lugar, o fallará el soporte para FI_HMEM si el proveedor no puede hacer eso.

INDICADORES

El siguiente indicador puede especificarse en cualquier llamada de registro de memoria.

FI_RMA_EVENT
Este indicador indica que la región de memoria especificada se asociará con un contador de finalización utilizado para contar las operaciones RMA que acceden a la MR.
FI_RMA_PMEM
Este indicador indica que la región de memoria subyacente está respaldada por memoria persistente y se usará en operaciones RMA. Debe especificarse si se requieren semánticas de finalización persistentes o transferencias de datos persistentes al acceder a la región registrada.
FI_HMEM_DEVICE_ONLY
Este indicador indica que la memoria solo es accesible por un dispositivo. Qué dispositivo está especificado por los campos iface y device de fi_mr_attr. Esto se refiere a regiones de memoria que se asignaron usando una llamada AllocDevice de API de dispositivo (a diferencia de usar la asignación de host o la asignación de memoria unificada/compartida). Este indicador solo es utilizable para dominios abiertos con soporte de capacidad FI_HMEM.
FI_HMEM_HOST_ALLOC
Este indicador indica que la memoria es propiedad solo del host. Si puede ser accedida por el dispositivo depende de la implementación. El campo iface de fi_mr_attr todavía se usa para identificar la API de dispositivo, pero el campo device se ignora. Esto se refiere a regiones de memoria que se asignaron usando una llamada AllocHost de API de dispositivo (a diferencia de usar una asignación de host similar a malloc, asignación de memoria unificada/compartida, o AllocDevice). Este indicador solo es utilizable para dominios abiertos con soporte de capacidad FI_HMEM.
FI_MR_DMABUF
Este indicador indica que la región de memoria a registrar es una región respaldada por DMA-buf. Cuando se establece, la región se especifica a través del campo dmabuf de la estructura fi_mr_attr. Este indicador solo es utilizable para dominios abiertos con soporte de capacidad FI_HMEM.
FI_MR_SINGLE_USE
Este indicador indica que la región de memoria solo se usa para una sola operación. Después de que la operación esté completa, la clave asociada con la región de memoria se invalida automáticamente y ya no puede usarse para acceso remoto.
FI_AUTH_KEY
Solo válido con dominios configurados con FI_AV_AUTH_KEY. Cuando se usa con fi_mr_regattr, este indicador denota que el campo fi_mr_auth_key::src_addr contiene una clave de autorización fi_addr_t (es decir, fi_addr_t devuelto por fi_av_insert_auth_key) en lugar de un fi_addr_t de punto de conexión (es decir, fi_addr_t devuelto por fi_av_insert / fi_av_insertsvc / fi_av_remove).

DOMINIOS DE MEMORIA

Los dominios de memoria identifican la separación física de la memoria que puede o no ser accesible a través del mismo espacio de direcciones virtuales. Tradicionalmente, las aplicaciones solo trataban con un único dominio de memoria, el de la memoria del host estrechamente acoplada con las CPU del sistema. Con la introducción de subsistemas de memoria de dispositivos y no uniformes, las aplicaciones a menudo necesitan ser conscientes de a qué dominio de memoria se mapea una dirección virtual particular.

Como regla general, los dispositivos físicos separados pueden considerarse que tienen sus propios dominios de memoria. Por ejemplo, una NIC puede tener memoria accesible por el usuario, y se consideraría un dominio de memoria separado de la memoria en una GPU. Tanto los dominios de memoria de la NIC como los de la GPU están separados de la memoria del sistema host. Las GPU individuales o los aceleradores de cálculo pueden tener dominios de memoria distintos, o pueden estar conectados de tal manera (por ejemplo, una red específica para GPU) que todas las GPU pertenecerían al mismo dominio de memoria. Desafortunadamente, identificar los dominios de memoria es específico de cada sistema y su configuración física y/o virtual.

Comprender los dominios de memoria en entornos de memoria heterogénea es importante ya que puede impactar el ordenamiento y la visibilidad de los datos tal como los ve una aplicación. También es importante comprender a qué dominio de memoria está más estrechamente acoplada una aplicación. En la mayoría de los casos, las aplicaciones están estrechamente acopladas a la memoria del host. Sin embargo, una aplicación que se ejecuta directamente en una GPU o NIC puede estar más estrechamente acoplada a la memoria asociada con esos dispositivos.

Las regiones de memoria a menudo se asocian con un único dominio de memoria. El dominio a menudo está indicado por los campos iface y device de fi_mr_attr. Aunque es posible que las páginas físicas que respaldan una región de memoria virtual migren entre dominios de memoria basándose en los patrones de acceso. Por ejemplo, las páginas físicas referenciadas por un rango de direcciones virtuales podrían migrar entre la memoria del host y la memoria de la GPU, dependiendo de qué unidad de cálculo la esté usando activamente.

Consulte las páginas de manual fi_endpoint(3) y fi_cq(3) para una discusión adicional sobre la semántica de ordenamiento de mensajes, datos y finalizaciones, incluido el impacto de los dominios de memoria.

CACHÉ DE REGISTRO DE MEMORIA

Muchas NIC de hardware accedidas por libfabric requieren que los búferes de datos se registren con el hardware mientras el hardware accede a ellos. Esto asegura que los mapeos de direcciones virtuales a físicas para esos búferes no cambien mientras ocurre la transferencia. El impacto en el rendimiento de registrar regiones de memoria puede ser significativo. Como resultado, algunos proveedores hacen uso de una caché de registro, particularmente cuando trabajan con aplicaciones que no pueden gestionar sus propios búferes de red. Una caché de registro evita la sobrecarga de registrar y desregistrar un búfer de datos con cada transferencia.

Si se va a usar una caché de registro para la memoria del host y del dispositivo, el dispositivo debe soportar direccionamiento virtual unificado. Si el dispositivo no soporta direccionamiento virtual unificado,r se requiere una caché de registro adicional para rastrear esta memoria del dispositivo, o la memoria del

dispositivo

no se puede almacenar en caché. Como regla general, si el hardware requiere el bit de modo FI_MR_LOCAL descrito anteriormente, pero esto no es compatible con la aplicación, es posible que se esté utilizando una caché de registro de memoria [[2]]. Las
