DESCRIPCIÓ

N

Las funciones de gestión de conexiones se utilizan para conectar un punto final orientado a conexiones (FI_EP_MSG) a un par que

escucha.

fi_liste

n

La llamada fi_listen indica que el punto final especificado debe transicionar a un estado de conexión pasiva, permitiéndole aceptar solicitudes de conexión entrantes. Las solicitudes de conexión contra un punto fina

l que escucha se reportan de forma asíncrona al usuario a través de una cola de eventos CM enlazada usando el tipo de evento FI_CONNREQ. El número de solicitudes de conexión pendientes que pueden encolarse en un pu
nto final está limitado por el parámetro de backlog del punto final que escucha. El backlog se inicializa basándose en valores de configuración administrativa, pero puede ajustarse a través de la llamada fi_control.

fi_connec

t

La llamada fi_connect inicia una solicitud de conexión en un punto

final orientado a conexiones hacia la dirección de destino. fi_con
nect solo puede llamarse en un punto final una vez en su vida útil.

fi_accept /

fi_reject

Las llamadas fi_accept y fi_reject se usan en el lado pasivo (que escucha) de una conexión para aceptar o rechazar una solicitud de conexión, respectivamente. Para aceptar una conexión, la aplicación que escucha primero espera un evento de solicitud de conexión (FI_CONNREQ). Después de recibir dicho evento, la aplicación asigna un nuevo punto final para aceptar la conexión. Este punto final debe asignarse usando una estructura fi_info que referencie el manejador de este evento FI_CONNREQ. Luego se invoca fi_accept con el punto final recién asignado. Si la aplicación que escucha desea rechazar una solicitud de conexión, llama a fi_reject con el punto final que escucha y una referencia a la solicitud de

conexión.

Una solicitud de conexión aceptada con éxito resultará en que el punto final activo (que conecta) vea un evento FI_CONNECTED en su cola de eventos asociada. Una solicitud de conexión rechazada o fallida generará un evento de error. La entrada de error proporcionará detalles adicionales describiendo la razón del intento

fallido.

Un evento FI_CONNECTED también se generará en el lado pasivo para el punto final que acepta una vez que la conexión se haya establecido correctamente. El fid del evento FI_

CONNECTED será el del punto final pasado a fi_accept en lugar del punto final pasivo que escucha. Las transferencias de datos salientes no pueden iniciarse en un punto fin
al orientado a conexiones hasta que se haya generado un evento FI_CONNECTED. Sin embargo, los búferes de recepción pueden asociarse con un punto final en cualquier momento.

fi_shutdow

n

La llamada fi_shutdown se usa para desconectar suavemente un punto final de su par. El parámetro flags está reservado y debe ser

0.

Las operaciones pendientes publicadas en el punto final cuando se llama a fi_shutdown serán canceladas o descartadas. La notificación de operaciones canceladas será reportada por el proveedor a las colas de finalización correspondientes. Las operaciones descartadas se eliminarán silenciosamente, sin generar finalizaciones. La elección de cancelar, versus descartar operaciones, depende del proveedor. Sin embargo, todas las finalizaciones canceladas se escribirán antes de que fi_shutdown

retorne.

Cuando se llama, fi_shutdown no afecta las finalizaciones ya escritas en una cola de finalización. Cualquier finalización encolada asociada con operaciones asíncronas publicadas en el punto final aún puede ser recuperada de las colas de finalización correspondientes después de que un punto final haya sido

desconectado.

Un evento FI_SHUTDOWN se generará para un punto final cuando el par remoto emita una desconexión usando fi_shutdown o cierre abrupta

mente el punto final. Nótese que en el caso de cierre abrupto, un evento FI_SHUTDOWN solo se generará si el sistema del par es alca
nzable y un servicio o agente de kernel en el sistema del par puede notificar al punto final local que la conexión ha sido abortada.

fi_clos

e

Fi_close se usa para desasociar un punto final de un grupo de multidifusi

ón y cerrar todos los recursos asociados con el grupo. Fi_close debe llama
rse en todos los grupos de multidifusión a los que un punto final se une.

fi_setnam

e

La llamada fi_setname puede usarse para modificar o asignar la dirección del punto final local. Es conceptualmente similar a la operación bind de socket. Un punto final puede serle asignada una dirección en su creación, a través de la estructura fi_info. La llamada fi_setname permite que un punto final sea creado sin estar asociado con un servicio específico (por ejemplo, número de puerto) y/o dirección de nodo (por ejemplo, red), con la dirección asignada dinámicamente. El formato de los datos de direccionamiento especificados debe coincidir con el especificado a través de la estructura fi_info cuando se creó el punto

final.

Si no se especifica una dirección de servicio y aún no se ha asignado una dirección de servicio al punto final, entonces el proveedor asignará una dirección de servicio

y la asignará al punto final. Si se especifica una dirección de nodo o de servicio, entonces, tras la finalización exitosa de fi_setname, al punto final se le asignará
el direccionamiento dado. Si no puede asignarse una dirección, o la dirección del punto final no puede modificarse, se devuelve un número de error de fabrica apropiado.

NAME

fi_getname, fi_getpeer — retrieve endpoint addresses

SYNOPSIS

#include <rdma/fi_domain.h>
#include <rdma/fi_endpoint.h>
#include <rdma/fi_errno.h>

ssize_t fi_getname(struct fi_endpoint *endp,
    struct sockaddr *addr,
    size_t *addrlen);
ssize_t fi_getpeer(struct fi_endpoint *endp,
    struct sockaddr *addr,
    size_t *addrlen);

ARGUMENTS

endp
The endpoint object to query.
addr
A buffer to store the endpoint address. The buffer must be large enough to hold the address structure. On output, the buffer is filled with the endpoint address.
addrlen
On input, the size of the buffer referenced by addr. On output, the size of the buffer needed to store the address.

DESCRIPTION

The fi_getname and fi_getpeer calls retrieve the local and peer addresses, respectively, associated with a fabric endpoint.

fi_getname returns the local address of the specified endpoint. This address can be used to identify the endpoint for incoming connections or for other communication protocols that require the source address.

fi_getpeer returns the address of the connected peer for the specified endpoint. This call is only valid for connected endpoints.

On output, addrlen is set to the size of the buffer needed to store the address, which may be larger than the input value.

fi_getname is not guaranteed to return a valid source address until after the specified endpoint has been enabled or has had an address assigned. An endpoint may be enabled explicitly through fi_enable, or implicitly, such as through fi_connect or fi_listen. An address may be assigned using fi_setname. fi_getpeer is not guaranteed to return a valid peer address until an endpoint has been completely connected – an FI_CONNECTED event has been generated.

fi_join

This call attaches an endpoint to a multicast group. By default, the endpoint will join the group based on the data transfer capabilities of the endpoint. For example, if the endpoint has been configured to both send and receive data, then the endpoint will be able to initiate and receive transfers to and from the multicast group. The fi_join flags may be used to restrict access to the multicast group, subject to endpoint capability limitations.

Multicast join operations complete asynchronously. An endpoint must be bound to an event queue prior to calling fi_join. The result of the join operation will be reported to the EQ as an FI_JOIN_COMPLETE event. Applications cannot issue multicast transfers until receiving notification that the join operation has completed. Note that an endpoint may begin receiving messages from the multicast group as soon as the join completes, which can occur prior to the FI_JOIN_COMPLETE event being generated.

Applications must call fi_close on the multicast group to disconnect the endpoint from the group. After a join operation has completed, the fi_mc_addr call may be used to retrieve the address associated with the multicast group.

fi_mc_addr

Returns the fi_addr_t address associated with a multicast group. This address must be used when transmitting data to a multicast group and paired with the FI_MULTICAST operation flag.

FLAGS

Except in functions noted below, flags are reserved and must be 0.

FI_SEND
Applies to fi_join. This flag indicates that the endpoint should join the multicast group as a send only member. The endpoint must be configured for transmit operations to use this flag, or an error will occur.
FI_RECV
Applies to fi_join. This flag indicates that the endpoint should join the multicast group with receive permissions only. The endpoint must be configured for receive operations to use this flag, or an error will occur.

RETURN VALUE

Returns 0 on success. On error, a negative value corresponding to fabric errno is returned. Fabric errno values are defined in rdma/fi_errno.h.

ERRORS

NOTES

For connection-oriented endpoints, the buffer referenced by param will be sent as part of the connection request or response, subject to the constraints of the underlying connection protocol. Applications may use fi_getopt with the FI_OPT_CM_DATA_SIZE endpoint option to determine the size of application data that may be exchanged as part of a connection request or response. The fi_connect, fi_accept, and fi_reject calls will silently truncate any application data which cannot fit into underlying protocol messages. User data exchanged as part of the connection process is available as part of the fi_eq_cm_entry structure, for FI_CONNREQ and FI_CONNECTED events, or as additional err_data to fi_eq_err_entry, in the case of a rejected connection.
