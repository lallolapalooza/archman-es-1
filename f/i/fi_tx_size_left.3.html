DESCRIPCIÓN

Los endpoints son portales de comunicación a nivel de transporte. Existen dos tipos de endpoints: activos y pasivos. Los endpoints pasivos pertenecen a un dominio de fabric y se utilizan con mayor frecuencia para escuchar solicitudes de conexión entrantes. Sin embargo, un endpoint pasivo puede usarse para reservar una dirección de fabric que se puede otorgar a un endpoint activo. Los endpoints activos pertenecen a dominios de acceso y pueden realizar transferencias de datos.

Los endpoints activos pueden ser orientados a conexión o sin conexión, y pueden proporcionar fiabilidad de datos. Las interfaces de transferencia de datos - mensajes (fi_msg), mensajes etiquetados (fi_tagged), RMA (fi_rma) y atómicos (fi_atomic) - están asociadas con endpoints activos. En configuraciones básicas, un endpoint activo tiene colas de transmisión y recepción. En general, las operaciones que generan tráfico en el fabric se publican en la cola de transmisión. Esto incluye todas las operaciones RMA y atómicas, junto con los mensajes enviados y los mensajes etiquetados enviados. Las operaciones que publican búferes para recibir datos entrantes se envían a la cola de recepción.

Los endpoints activos se crean en estado deshabilitado. Deben transicionar a un estado habilitado antes de aceptar operaciones de transferencia de datos, incluida la publicación de búferes de recepción. La llamada fi_enable se utiliza para transicionar un endpoint activo a un estado habilitado. Las llamadas fi_connect y fi_accept también transicionarán un endpoint al estado habilitado, si aún no está activo.

Para poder transicionar un endpoint a un estado habilitado, debe estar enlazado a uno o más recursos de fabric. Un endpoint que generará finalizaciones asíncronas, ya sea a través de operaciones de transferencia de datos o eventos de establecimiento de comunicación, debe estar enlazado a las colas de finalización o colas de eventos apropiadas, respectivamente, antes de ser habilitado. Además, los endpoints que solo utilizan progreso manual deben asociarse con colas de finalización o colas de eventos relevantes para impulsar el progreso. Para los endpoints que solo se utilizan como destino de operaciones RMA o atómicas, esto significa enlazar el endpoint a una cola de finalización asociada con el procesamiento de recepción. Los endpoints sin conexión deben estar enlazados a un vector de direcciones.

Una vez que un endpoint ha sido activado, puede asociarse con un vector de direcciones. Se pueden publicar búferes de recepción y se pueden realizar llamadas a las rutinas de establecimiento de conexión. Los endpoints sin conexión también pueden realizar transferencias de datos.

El comportamiento de un endpoint puede ajustarse estableciendo sus datos de control y opciones de protocolo. Esto permite que el proveedor subyacente redirija las llamadas de función a implementaciones optimizadas para cumplir con el comportamiento de la aplicación deseada.

Si un endpoint experimenta un error crítico, transicionará de nuevo a un estado deshabilitado. Los errores críticos se informan a través de la cola de eventos asociada con el EP. En ciertos casos, un endpoint deshabilitado puede ser re-habilitado. La capacidad de transicionar de nuevo a un estado habilitado es específica del proveedor y depende del tipo de error que experimentó el endpoint.

Cuando un punto de acceso se desactiva como resultado de un error crítico, todas las operaciones pendientes se descartan.

fi_endpoint / fi_passive_ep / fi_scalable_ep

fi_endpoint asigna un nuevo punto de acceso activo. fi_passive_ep asigna un nuevo punto de acceso pasivo. fi_scalable_ep asigna un punto de acceso escalable. Las propiedades y el comportamiento del punto de acceso se definen en función de la estructura fi_info proporcionada. Consulte fi_getinfo para obtener detalles adicionales sobre fi_info. Las banderas de fi_info que controlan el funcionamiento de un punto de acceso se definen a continuación. Consulte la sección PUNTOS DE ACCESO ESCALABLES.

Si se asigna un punto de acceso activo para aceptar una solicitud de conexión, el parámetro fi_info debe ser el mismo que la estructura fi_info proporcionada con el evento de solicitud de conexión (FI_CONNREQ).

Un punto de acceso activo puede adquirir las propiedades de un punto de acceso pasivo estableciendo el campo handle de fi_info en el descriptor de fabrica del punto de acceso pasivo. Esto es útil para aplicaciones que necesitan reservar la dirección de fabrica de un punto de acceso antes de saber si el punto de acceso se utilizará en el lado activo o pasivo de una conexión. Por ejemplo, esta característica es útil para simular la semántica de los sockets. Una vez que un punto de acceso activo adquiere las propiedades de un punto de acceso pasivo, el punto de acceso pasivo ya no está vinculado a ningún recurso de fabrica y no debe usarse más. Se espera que el usuario cierre el punto de acceso pasivo después de abrir el punto de acceso activo para liberar cualquier recurso persistente que haya sido utilizado.

fi_endpoint2

Similar a fi_endpoint, buf acepta un parámetro extra flags. Se utiliza principalmente para abrir puntos de acceso que utilizan la característica de transferencia entre pares. Consulte fi_peer(3)

fi_close

Cierra un punto de acceso y libera todos los recursos asociados con él.

Al cerrar un punto de acceso escalable, no debe haber contextos de transmisión abiertos ni contextos de recepción asociados con el punto de acceso escalable. Si aún hay recursos asociados con el punto de acceso escalable al intentar cerrarlo, la llamada devolverá -FI_EBUSY.

Las operaciones pendientes enviadas al punto de acceso cuando se llama a fi_close serán descartadas. Las operaciones descartadas se eliminarán silenciosamente, sin que se informe de ninguna finalización. Los búferes de memoria que el usuario asoció con el punto de acceso mediante las interfaces de transmisión de libfabric no deben liberarse, desregistrarse ni reutilizarse hasta que se genere una finalización o hasta que fi_close en el punto de acceso respectivo devuelva. Además, un proveedor puede descartar operaciones previamente completadas de las colas de finalización asociadas. El comportamiento para descartar operaciones completadas es específico del proveedor.

fi_ep_bind

fi_ep_bind se utiliza para asociar un punto de acceso con otros recursos asignados, como colas de finalización, contadores, vectores de direcciones, colas de eventos, contextos compartidos y regiones de memoria. El tipo de objetos que deben vincularse con un punto de acceso depende del tipo de punto de acceso y su configuración.

Los puntos de acceso pasivos deben estar vinculados a una cola de eventos (EQ) que admita eventos de gestión de conexiones. Los puntos de acceso sin conexión deben estar vinculados a un solo vector de direcciones. Si un punto de acceso está utilizando un contexto de transmisión y/o recepción compartido, los contextos compartidos deben estar vinculados al punto de acceso. Las colas de finalización (CQ), los contadores, los vectores de direcciones (AV) y los contextos compartidos deben estar vinculados a los puntos de acceso antes de que sean habilitados, ya sea explícita o implícitamente.

Un punto de acceso debe estar vinculado a CQs capaces de informar finalizaciones para cualquier operación asíncrona iniciada en el punto de acceso. Por ejemplo, si el punto de acceso admite cualquier transferencia de salida (envíos, RMA, operaciones atómicas, etc.), entonces debe estar vinculado a una cola de finalización que pueda informar finalizaciones de transmisión. Esto es cierto incluso si el punto de acceso está configurado para suprimir las finalizaciones exitosas, de modo que las operaciones que finalizan con error puedan informarse al usuario.

Un punto de acceso activo puede dirigir las finalizaciones asíncronas a diferentes CQs, en función del tipo de operación. Esto se especifica utilizando las banderas de fi_ep_bind. Las siguientes banderas pueden combinarse con OR al vincular un punto de acceso a una cola de finalización (CQ) del dominio de finalización.

FI_RECV
Dirige la notificación de las transferencias de datos entrantes a la cola de finalización especificada. Esto incluye los mensajes recibidos. Esta vinculación incluye automáticamente FI_REMOTE_WRITE, si es aplicable al punto de acceso.
FI_SELECTIVE_COMPLETION
De forma predeterminada, las operaciones de transferencia de datos escriben entradas de finalización en la cola de finalización asociada después de haberse completado con éxito. Las aplicaciones pueden usar esta bandera de vinculación para habilitar selectivamente cuándo se generan las finalizaciones. Si se especifica FI_SELECTIVE_COMPLETION, las operaciones de transferencia de datos no generarán entradas en la CQ para finalizaciones exitosas a menos que FI_COMPLETION esté establecido como una bandera operativa para la operación dada. Las operaciones que fallan de forma asíncrona seguirán generando finalizaciones, incluso si no se solicita una finalización. FI_SELECTIVE_COMPLETION debe combinarse con OR con las banderas FI_TRANSMIT y/o FI_RECV.

Cuando se establece FI_SELECTIVE_COMPLETION, el usuario debe determinar indirectamente cuándo se ha completado una solicitud que NO tiene FI_COMPLETION establecido, generalmente en función de la finalización de una operación posterior o mediante el uso de contadores de finalización. El uso de esta bandera puede mejorar el rendimiento al permitir al proveedor evitar escribir una entrada de finalización en la CQ para cada operación.

Consulte la sección de Notas a continuación para obtener información adicional sobre cómo interactúa esta bandera con los bits de modo FI_CONTEXT y FI_CONTEXT2.

FI_TRANSMIT
Dirige la finalización de las solicitudes de transferencia de datos de salida a la cola de finalización especificada. Esto incluye operaciones de envío de mensajes, RMA y atómicas.

Un punto de acceso puede vincularse opcionalmente a un contador de finalización. La asociación de un punto de acceso con un contador es adicional a la vinculación del punto de acceso con una CQ. Al vincular un punto de acceso a un contador, se pueden especificar las siguientes banderas.

FI_READ
Incrementa el contador especificado siempre que una operación de lectura RMA, de obtención atómica o de comparación atómica iniciada desde el punto de acceso se haya completado con éxito o con error.
FI_RECV
Incrementa el contador especificado siempre que se recibe un mensaje a través del punto de acceso. Los mensajes recibidos incluyen tanto operaciones de mensajes etiquetados como normales.
FI_REMOTE_READ
Incrementa el contador especificado siempre que una operación de lectura RMA, de obtención atómica o de comparación atómica se inicia desde un punto de acceso remoto que tiene como destino el punto de acceso dado. El uso de esta bandera requiere que el punto de acceso se haya creado utilizando FI_RMA_EVENT.
FI_REMOTE_WRITE
Incrementa el contador especificado siempre que una operación de escritura RMA o atómica base se inicia desde un punto de acceso remoto que tiene como destino el punto de acceso dado. El uso de esta bandera requiere que el punto de acceso se haya creado utilizando FI_RMA_EVENT.
FI_SEND
Incrementa el contador especificado siempre que una transferencia de mensajes iniciada a través del punto de acceso se haya completado con éxito o con error. Los mensajes enviados incluyen tanto operaciones de mensajes etiquetados como normales.
FI_WRITE
Incrementa el contador especificado siempre que una operación de escritura RMA o atómica base iniciada desde el punto de acceso se haya completado con éxito o con error.

Un punto de acceso solo puede vincularse a una sola CQ o contador para un tipo de operación dado. Por ejemplo, un punto de acceso no puede vincularse a dos contadores que usen ambos FI_WRITE. Además, los proveedores pueden limitar las vinculaciones de CQ y contadores a puntos de acceso del mismo tipo de punto de acceso (DGRAM, MSG, RDM, etc.).

fi_scalable_ep_bind

fi_scalable_ep_bind se utiliza para asociar un punto de acceso escalable con un vector de direcciones. Consulte la sección sobre PUNTOS DE ACCESO ESCALABLES. Un punto de acceso escalable tiene una única dirección de nivel de transporte y puede admitir múltiples contextos de transmisión y recepción. Los contextos de transmisión y recepción comparten la dirección de nivel de transporte. Los vectores de direcciones vinculados a puntos de acceso escalables están implícitamente vinculados a cualquier contexto de transmisión o recepción creado utilizando el punto de acceso escalable.

fi_enable

Esta llamada transiciona el punto de acceso a un estado habilitado. Un punto de acceso debe estar habilitado antes de que pueda usarse para realizar transferencias de datos. Habilitar un punto de acceso generalmente resulta en la asignación de recursos de hardware al mismo. Los puntos de acceso que utilizan colas de finalización, contadores, colas de eventos y/o vectores de direcciones deben estar vinculados a ellos antes de ser habilitados.

Llamar a connect o accept en un punto de acceso habilitará implícitamente un punto de acceso si aún no ha sido habilitado.

fi_enable también puede usarse para volver a habilitar un punto de acceso que ha sido deshabilitado como resultado de experimentar un error crítico. Las aplicaciones deben verificar el valor de retorno de fi_enable para ver si un punto de acceso deshabilitado ha sido re-habilitado con éxito.

fi_cancel

fi_cancel intenta cancelar una operación asíncrona pendiente. Cancelar una operación hace que el proveedor de fabrica busque la operación y, si aún está pendiente, la complete como cancelada. Habrá disponible una entrada en la cola de errores asociada con el código de error FI_ECANCELED. Por otro lado, si la operación se completó antes de la llamada a fi_cancel, el estado de finalización de esa operación estará disponible en la cola de finalización asociada. No se publicará ninguna entrada específica relacionada con fi_cancel en sí.

Cancelar utiliza el parámetro de contexto asociado con una operación para identificar la solicitud a cancelar. Las operaciones enviadas sin un parámetro de contexto válido – ya sea que no se especifique un parámetro de contexto o que el valor del contexto haya sido ignorado por el proveedor – no pueden ser canceladas. Si múltiples operaciones pendientes coinciden con el parámetro de contexto, solo una será cancelada. En este caso, la operación que se cancela es específica del proveedor. La operación de cancelación es asíncrona, pero se completará dentro de un período de tiempo acotado.

Esta llamada crea un alias para el punto de conexión especificado. Conceptualmente, un alias de punto de conexión proporciona una ruta de software alternativa desde la aplicación hasta el hardware del proveedor subyacente. Un punto de conexión alias difiere de su punto de conexión principal solo por sus indicadores de transferencia de datos predeterminados. Por ejemplo, un punto de conexión alias puede configurarse para usar un modo de finalización diferente. Por defecto, un punto de conexión alias hereda los mismos indicadores de transferencia de datos que el punto de conexión principal. Una aplicación puede usar fi_control para modificar los indicadores operativos del punto de conexión alias.

Al asignar un alias, una aplicación puede configurar ya sea los indicadores operativos de transmisión o de recepción. Esto evita la necesidad de una llamada separada a fi_control para establecer esos indicadores. Los indicadores pasados a fi_ep_alias deben incluir FI_TRANSMIT o FI_RECV (no ambos) con otros indicadores operativos OR’eados. Esto anulará los indicadores de transmisión o de recepción, respectivamente, para las operaciones publicadas a través del punto de conexión alias. Todos los aliases asignados deben cerrarse para que el punto de conexión subyacente pueda ser liberado.

fi_control

La operación de control se utiliza para ajustar el comportamiento predeterminado de un punto de conexión. Permite al proveedor subyacente redirigir las llamadas a funciones a implementaciones optimizadas para cumplir con el comportamiento deseado de la aplicación. Como resultado, las llamadas a fi_ep_control deben serializarse contra todas las demás llamadas a un punto de conexión.

La operación base de un punto de conexión se selecciona durante la creación usando struct fi_info. Los siguientes comandos de control y argumentos pueden ser asignados a un punto de conexión.

FI_BACKLOG - int *value
Esta opción solo se aplica a los puntos de conexión pasivos. Se utiliza para establecer el fondo de solicitudes de conexión para los puntos de conexión de escucha.
FI_GETOPSFLAG – uint64_t *flags
Se utiliza para recuperar el valor actual de los indicadores asociados con las operaciones de transferencia de datos iniciadas en el punto de conexión. El argumento de control debe incluir los indicadores FI_TRANSMIT o FI_RECV (no ambos) para indicar el tipo de indicadores de transferencia de datos que se devolverán. Vea abajo para una lista de los indicadores de control.
FI_GETWAIT – void **
Este comando permite al usuario recuperar el descriptor de archivo asociado con un punto de conexión de socket. El parámetro arg de fi_control debe ser una dirección donde se escribirá un puntero al descriptor de archivo devuelto. Vea fi_eq.3 para detalles adicionales sobre el uso de fi_control con FI_GETWAIT. El descriptor de archivo puede usarse para notificaciones de que el punto de conexión está listo para enviar o recibir datos.
FI_SETOPSFLAG – uint64_t *flags
Se utiliza para cambiar los indicadores de operación de transferencia de datos asociados con un punto de conexión. El argumento de control debe incluir FI_TRANSMIT o FI_RECV (no ambos) para indicar el tipo de transferencia de datos al que deben aplicarse los indicadores, con otros indicadores OR’eados. Los indicadores dados anularán los atributos de transmisión y recepción previamente establecidos cuando el punto de conexión fue creado. Los indicadores de control válidos se definen a continuación.

fi_getopt / fi_setopt

Las operaciones de protocolo del punto de conexión pueden recuperarse usando fi_getopt o establecerse usando fi_setopt. Las aplicaciones especifican el nivel en el que existe una opción deseada, identifican la opción, y proporcionan búferes de entrada/salida para obtener o establecer la opción. fi_setopt proporciona a una aplicación una forma de ajustar detalles de bajo nivel específicos del protocolo y la implementación de un punto de conexión, y debe llamarse antes de que el punto de conexión sea habilitado (fi_enable).

Se definen los siguientes niveles de opción, nombres de opción y parámetros.

FI_OPT_ENDPOINT • .RS 2

FI_OPT_CM_DATA_SIZE - size_t
Define el tamaño del espacio disponible en los mensajes CM para datos definidos por el usuario. Este valor limita la cantidad de datos que las aplicaciones pueden intercambiar entre puntos de conexión pares usando las operaciones fi_connect, fi_accept y fi_reject. El tamaño devuelto depende de las propiedades del punto de conexión, excepto en el caso de los puntos de conexión pasivos, en los que el tamaño refleja el tamaño máximo de los datos que pueden estar presentes como parte de un evento de solicitud de conexión. Esta opción es de solo lectura.

• .RS 2
FI_OPT_MIN_MULTI_RECV - size_t
Define el espacio mínimo de búfer de recepción disponible por debajo del cual el búfer de recepción es liberado por el proveedor (ver FI_MULTI_RECV). Modificar este valor solo garantiza establecer el espacio mínimo de búfer necesario en las recepciones publicadas después de que el valor haya sido cambiado. Se recomienda que las aplicaciones que deseen anular el valor predeterminado de MIN_MULTI_RECV establezcan esta opción antes de habilitar el punto de conexión correspondiente.

• .RS 2
FI_OPT_FI_HMEM_P2P - int
Define cómo el proveedor debe manejar las transferencias FI_HMEM de par a par para este punto de conexión. Por defecto, el proveedor elegirá si usar soporte de par a par basado en el tipo de transferencia (FI_HMEM_P2P_ENABLED). Los valores válidos definidos en fi_endpoint.h son:
•
FI_HMEM_P2P_ENABLED: El proveedor puede usar soporte de par a par para manejar transferencias FI_HMEM, y qué transferencias se inician usando par a par está sujeto a la implementación del proveedor.
•
FI_HMEM_P2P_REQUIRED: El soporte de par a par debe usarse para las transferencias, las transferencias que no puedan realizarse usando p2p se reportarán como fallidas.
•
FI_HMEM_P2P_PREFERRED: El proveedor debería usar soporte de par a par para todas las transferencias si está disponible, pero el proveedor puede elegir copiar los datos para iniciar la transferencia si el soporte de par a par no está disponible.
•
FI_HMEM_P2P_DISABLED: El soporte de par a par no debe usarse.

fi_setopt() devolverá -FI_EOPNOTSUPP si el modo solicitado no puede ser soportado por el proveedor. La variable de entorno FI_HMEM_DISABLE_P2P discutida en fi_mr(3) tiene prioridad sobre esta opción setopt.
• .RS 2

FI_OPT_CUDA_API_PERMITTED - bool

Tamaño Máximo de Ordenamiento RMA


El tamaño máximo de ordenamiento especifica el orden de entrega de los datos de transporte en la memoria de destino para operaciones RMA y atómicas. El ordenamiento de datos es independiente, pero depende del ordenamiento de mensajes (definido más adelante). El ordenamiento de datos no está especificado donde el orden de los mensajes no está definido.


El ordenamiento de datos se refiere al acceso a la misma memoria de destino por operaciones posteriores. Cuando operaciones RMA de lectura o escritura consecutivas acceden a la misma ubicación de memoria registrada, el ordenamiento de datos indica si la segunda operación lee o escribe la memoria de destino después de que la primera operación haya completado. Por ejemplo, ¿una lectura RMA que sigue a una escritura RMA leerá los datos que fueron escritos? De manera similar, ¿una escritura RMA que sigue a una lectura RMA actualizará el búfer de destino después de que la lectura haya transferido los datos originales? El ordenamiento de datos responde a estas preguntas, incluso en presencia de errores, como la necesidad de reenviar datos debido a tráfico de red perdido o corrupto.


El ordenamiento RMA se aplica entre dos operaciones, y no dentro de una sola transferencia de datos. Por lo tanto, el ordenamiento se define por ubicación de memoria direccionable por byte. Es decir, el ordenamiento especifica si la ubicación X es accedida por la segunda operación después de la primera operación. No se implica nada sobre la finalización de la primera operación antes de que la segunda operación sea iniciada. Por ejemplo, si la primera operación actualiza las ubicaciones X y Y, pero la segunda operación solo accede a la ubicación X, no hay garantías definidas con respecto a la ubicación Y y la segunda operación.


Para soportar transferencias de datos grandes que se dividen en múltiples paquetes y se envían usando múltiples rutas a través del fabric, el ordenamiento de datos puede estar limitado a transferencias de un tamaño específico o menor. Los proveedores especifican cuándo se mantiene el ordenamiento de datos a través de los siguientes valores. Note que incluso si el ordenamiento de datos no se mantiene, el ordenamiento de mensajes puede mantenerse.



  
max_order_raw_size

  
Tamaño de lectura después de escritura. Si se establece, una operación de lectura RMA o atómica emitida después de una operación de escritura RMA o atómica, ambas menores que el tamaño, serán ordenadas. Donde las ubicaciones de memoria de destino se superponen, la operación de lectura RMA o atómica verá los resultados de la escritura RMA o atómica anterior.

  
max_order_war_size

  
Tamaño de escritura después de lectura. Si se establece, una operación de escritura RMA o atómica emitida después de una operación de lectura RMA o atómica, ambas menores que el tamaño, serán ordenadas. La operación de lectura RMA o atómica verá el valor inicial de la ubicación de memoria de destino antes de que una escritura RMA o atómica posterior actualice el valor.

  
max_order_waw_size

  
Tamaño de escritura después de escritura. Si se establece, una operación de escritura RMA o atómica emitida después de una operación de escritura RMA o atómica, ambas menores que el tamaño, serán ordenadas. La ubicación de memoria de destino reflejará los resultados de la segunda escritura RMA o atómica.




Un valor de tamaño de ordenamiento de 0 indica que el ordenamiento no está garantizado. Un valor de -1 garantiza el ordenamiento para cualquier tamaño de datos.






mem_tag_format   - Formato de Etiqueta de Memoria


El campo de formato de etiqueta de memoria se usa para transmitir información sobre el uso de los parámetros de etiqueta e ignorar en las llamadas a la API fi_tagged, así como los criterios de coincidencia. Esta información es usada por el proveedor para optimizar el soporte de coincidencia de etiquetas, incluyendo la alineación con protocolos de red. Se definen los siguientes formatos de etiqueta:



  
FI_TAG_BITS

  
Si se especifica en la entrada a fi_getinfo, esto indica que las etiquetas contienen hasta 64 bits de datos, y el receptor debe aplicar ignore_bits a las etiquetas cuando haga coincidir búferes de recepción con envíos. La salida de fi_getinfo establecerá 0 o más bits superiores de mem_tag_format a 0 para indicar esos bits de etiqueta que son ignorados o reservados por el proveedor. Las aplicaciones deben verificar el número de bits superiores que son 0 y establecerlos a 0 en todos los bits de etiqueta e ignorar.




El valor de FI_TAG_BITS es 0, haciendo este el comportamiento por defecto si las sugerencias quedan sin inicializar después de ser alocadas por fi_allocinfo(). Este formato proporciona la mayor flexibilidad a las aplicaciones, pero limita las opciones de optimización del proveedor. FI_TAG_BITS se alinea con el comportamiento definido para versiones 1.x de libfabric.



  
FI_TAG_MPI

  
FI_TAG_MPI es un uso restringido de FI_TAG_BITS. Cuando se selecciona, las aplicaciones tratan la etiqueta como campos de datos, en lugar de bits, con la capacidad de hacer wildcard en cada campo. El formato de etiqueta MPI específicamente apunta a implementaciones y aplicaciones basadas en MPI. Una etiqueta con formato MPI consiste en 2 campos: una etiqueta de mensaje y un identificador de payload. La etiqueta de mensaje es una etiqueta de 32 bits buscable. La coincidencia en una etiqueta de mensaje requiere buscar a través de una lista de búferes publicados en el receptor, a lo que nos referimos como una etiqueta buscable. La etiqueta entera en mensajes punto a punto de MPI puede mapearse directamente al campo de etiqueta de mensaje de libfabric.




El segundo campo es un identificador que corresponde a la operación o datos que se llevan en el payload del mensaje. Por ejemplo, este campo puede usarse para identificar el tipo de operación colectiva asociada con un payload de mensaje. Note que solo se definen el tamaño y comportamiento para los formatos de etiqueta MPI. El uso descrito de los campos son solo sugerencias.


Las aplicaciones que usan el formato MPI deben inicializar sus etiquetas usando la función fi_tag_mpi(). Los bits de ignorar deben especificarse como FI_MPI_IGNORE_TAG, FI_MPI_IGNORE_PAYLOAD, o su OR bit a bit.



  
FI_TAG_CCL

  
El formato FI_TAG_CCL restringe aún más el formato FI_TAG_MPI. Cuando se usa, solo un campo de etiqueta puede ser establecido, el cual debe coincidir exactamente en el destino. El campo no puede ser wildcard. El formato de etiqueta CCL apunta a bibliotecas y aplicaciones de comunicación colectiva. El formato CCL consiste en un solo campo: un identificador de payload. El identificador corresponde a la operación o datos que se llevan en el payload del mensaje. Por ejemplo, este campo puede usarse para identificar si un mensaje es para comunicación punto a punto o parte de una operación colectiva, y en este último caso, el tipo de operación colectiva.




El formato de etiqueta CCL no requiere buscar búferes de recepción coincidentes, solo dirigir el mensaje a la cola de mensajes virtual correcta basada en el identificador de payload.


Las aplicaciones que usan el formato CCL pasan el identificador de payload directamente como la etiqueta y establecen los bits de ignorar a 0.



  
FI_TAG_MAX_FORMAT

  
Si el valor de mem_tag_format es >= FI_TAG_MAX_FORMAT, el formato de etiqueta se trata como un conjunto de campos de bits. El comportamiento es funcionalmente el mismo que FI_TAG_BITS. La siguiente descricción es para compatibilidad hacia atrás y describe cómo el proveedor puede interpretar el campo mem_tag_format si el valor es >= FI_TAG_MAX_FORMAT.




El formato de etiqueta de memoria puede usarse para dividir el arreglo de bits en campos separados. El mem_tag_format opcionalmente comienza con una serie de bits establecidos a 0, para significar bits que son ignorados por el proveedor. Siguiendo el prefijo inicial de bits ignorados, el arreglo consistirá en grupos alternos de bits establecidos a todos 1's o todos 0's. Cada grupo de bits corresponde a un campo etiquetado. La implicación de definir un campo etiquetado es que cuando se aplica una máscara al arreglo de bits etiquetado, todos los bits pertenecientes a un solo campo serán establecidos colectivamente a 1 o 0.


Por ejemplo, un mem_tag_format de 0x30FF indica soporte para 14 bits etiquetados, separados en 3 campos. El primer campo consiste en 2 bits, el segundo campo 4 bits, y el campo final 8 bits. Máscaras válidas para tal campo etiquetado serían un OR bit a bit de cero o más de los siguientes valores: 0x3000, 0x0F00, y 0x00FF. El proveedor puede no validar la máscara proporcionada por la aplicación por razones de rendimiento.


Al identificar campos dentro de una etiqueta, un proveedor puede ser capaz de optimizar sus rutinas de búsqueda. Una aplicación que solicita campos de etiqueta debe proporcionar máscaras de etiqueta que establezcan todos los bits de máscara correspondientes a un campo a todos 0 o todos 1. Al negociar campos de etiqueta, una aplicación puede solicitar un número específico de campos de un tamaño dado. Un proveedor debe devolver un formato de etiqueta que soporte el número solicitado de campos, con cada campo siendo al menos del tamaño solicitado, o fallar la solicitud. Un proveedor puede aumentar el tamaño de los campos. Al reportar completados (ver FI_CQ_FORMAT_TAGGED), no está garantizado que el proveedor limpiará cualquier bit de etiqueta no soportado en el campo de etiqueta de la entrada de completado.


Se recomienda que los tamaños de campo se ordenen de menor a mayor. Una etiqueta genérica, no estructurada y máscara pueden lograrse solicitando un arreglo de bits que consista en 1's y 0's alternos.

msg_order - Orden de Mensajes


El orden de mensajes se refiere al orden en el que los encabezados de la capa de transporte
    (vistos por la aplicación) se identifican y procesan. Un orden de mensajes relajado
    permite que las transferencias de datos se envíen y reciban fuera de orden,
    lo que puede mejorar el rendimiento al utilizar múltiples rutas a través del fabric
    desde un punto final de origen hasta un punto final de destino. El orden de mensajes se aplica
    solo entre un par de puntos finales de origen y destino únicos. El orden entre
    diferentes puntos finales de destino no está definido.


El orden de mensajes se determina usando un conjunto de bits de orden. Cada bit
    establecido indica que se mantiene el orden entre transferencias de datos del
    tipo especificado. El orden de mensajes se define para operaciones [read | write | send]
    enviadas por una aplicación después de operaciones [read | write | send].
    El valor 0 indica que no se especifica ningún orden. El valor 0 puede
    usarse como entrada para obtener el orden de mensajes predeterminado soportado por el
    proveedor.


El orden de mensajes solo se aplica a la transmisión de extremo a extremo de
    encabezados de transporte. El orden de mensajes es necesario, pero no garantiza,
    el orden en el que los datos del mensaje son enviados o recibidos por la capa de transporte.
    El orden de mensajes requiere semánticas de orden coincidentes en el lado receptor
    de una operación de transferencia de datos para garantizar que se cumpla ese orden.

Clase de tráfico (tclass)


Las clases de tráfico pueden ser un valor de punto de código de
    servicios diferenciados (DSCP), una de las etiquetas definidas siguientes, o
    una definición específica del proveedor. Si tclass no está establecido o está
    establecido en FI_TC_UNSPEC, el punto final usará la clase de tráfico
    predeterminada asociada con el dominio.



  
FI_TC_BEST_EFFORT

  
Este es el valor predeterminado en ausencia de cualquier otra
      configuración local o de la malla. Esta clase transporta el tráfico de
      varias aplicaciones que se ejecutan simultáneamente sobre la misma
      infraestructura de red. Aunque se comparte, la capacidad de la red y la
      asignación de recursos se distribuyen de manera justa entre las
      aplicaciones.

  
FI_TC_BULK_DATA

  
Esta clase está destinada a transferencias de datos grandes asociadas
      con E/S y está presente para separar las transferencias de E/S continuas de
      otras comunicaciones entre procesos de la aplicación.

  
FI_TC_DEDICATED_ACCESS

  
Esta clase opera en la prioridad más alta, excepto la clase de
      gestión. Tiene una asignación de ancho de banda alta, objetivos de latencia
      mínima y la prioridad más alta de programación y arbitraje.

  
FI_TC_LOW_LATENCY

  
Esta clase admite patrones de datos de baja latencia y baja
      fluctuación (jitter) típicamente causados por intercambios de datos
      transaccionales, sincronizaciones de barrera y operaciones colectivas que
      son típicas de las aplicaciones de HPC. Esta clase a menudo requiere
      latencias máximas tolerables que las transferencias de datos deben lograr
      para un rendimiento correcto. El cumplimiento de tales solicitudes en esta
      clase generalmente requerirá limitaciones de ancho de banda y tamaño de
      mensaje para no consumir un ancho de banda excesivo a alta prioridad.

  
FI_TC_NETWORK_CTRL

  
Esta clase está destinada al tráfico directamente relacionado con la
      gestión de la malla (red), que es crítica para el funcionamiento correcto de
      la red. Su uso generalmente está restringido a aplicaciones de gestión de
      red privilegiadas.

  
FI_TC_SCAVENGER

  
Esta clase se usa para datos que se desean pero que no tienen
      requisitos estrictos de entrega, como datos de monitorización de red o de
      nivel de aplicación en banda. El uso de esta clase indica que el tráfico se
      considera de menor prioridad y no debe interferir con flujos de trabajo de
      mayor prioridad.

  
fi_tc_dscp_set / fi_tc_dscp_get

  
Los valores DSCP se admiten a través de las funciones de obtención y

caps - Capacidades


Las capacidades solicitadas del contexto. Las capacidades deben ser
    un subconjunto de las solicitadas del punto final asociado en
    fi_info->caps. Vea la sección CAPABILITIES de fi_getinfo(3) para detalles de

Las siguientes capacidades se aplican a los atributos de recepción:

Muchas aplicaciones podrán ignorar este campo y confiar únicamente en

PUNTOS DE EXTREMO ESCALABLES


Un punto de extremo escalable es un portal de comunicación que soporta múltiples contextos de transmisión y recepción. Los puntos de extremo escalables están modelados libremente después del concepto de redes de escalamiento de transmisión/recepción, también conocido como multi-cola. El soporte para puntos de extremo escalables es específico del dominio. Los puntos de extremo escalables pueden mejorar el rendimiento de aplicaciones multi-hilo y paralelas, al permitir que los hilos accedan a colas de transmisión y recepción independientes. Un punto de extremo escalable tiene una única dirección de nivel de transporte, lo que puede reducir los requisitos de memoria necesarios para almacenar datos de direccionamiento remoto, en comparación con el uso de puntos de extremo estándar. Los puntos de extremo escalables no pueden usarse directamente para operaciones de comunicación, y requieren que la aplicación cree explícitamente contextos de transmisión y recepción como se describe a continuación.




fi_tx_context


Los contextos de transmisión son colas de transmisión independientes. El ordenamiento y la sincronización entre contextos no están definidos. Conceptualmente, un contexto de transmisión se comporta de manera similar a un punto de extremo de solo envío. Un contexto de transmisión puede configurarse con menos capacidades que el punto de extremo base y con diferentes atributos (como requisitos de ordenamiento y tamaño de inyección) que otros contextos asociados con el mismo punto de extremo escalable. Cada contexto de transmisión tiene su propia cola de finalización. El número de contextos de transmisión asociados con un punto de extremo se especifica durante la creación del punto de extremo.


La llamada fi_tx_context se usa para recuperar un contexto específico, identificado por un índice (ver arriba para detalles sobre los atributos del contexto de transmisión). Los proveedores pueden asignar contextos dinámicamente cuando se llama a fi_tx_context, o pueden crear estáticamente todos los contextos cuando se invoca fi_endpoint. Por defecto, un contexto de transmisión hereda las propiedades de su punto de extremo asociado. Sin embargo, las aplicaciones pueden solicitar atributos específicos del contexto a través del parámetro attr. El soporte para atributos por contexto de transmisión es específico del proveedor y no está garantizado. Los proveedores devolverán los atributos reales asignados al contexto a través del parámetro attr, si se proporciona.






fi_rx_context


Los contextos de recepción son colas de recepción independientes para recibir datos entrantes. El ordenamiento y la sincronización entre contextos no están garantizados. Conceptualmente, un contexto de recepción se comporta de manera similar a un punto de extremo de solo recepción. Un contexto de recepción puede configurarse con menos capacidades que el punto de extremo base y con diferentes atributos (como requisitos de ordenamiento y tamaño de inyección) que otros contextos asociados con el mismo punto de extremo escalable. Cada contexto de recepción tiene su propia cola de finalización. El número de contextos de recepción asociados con un punto de extremo se especifica durante la creación del punto de extremo.


Los contextos de recepción a menudo están asociados con flujos de direccionamiento (steering flows), que especifican qué paquetes entrantes dirigidos a un punto de extremo escalable deben procesarse. Sin embargo, los contextos de recepción pueden ser dirigidos directamente por el iniciador, si es soportado por el protocolo subyacente. A tales contextos se les llama `nombrados' (named). El soporte para contextos nombrados debe indicarse estableciendo la capacidad caps FI_NAMED_RX_CTX cuando se crea el punto de extremo correspondiente. El soporte para contextos de recepción nombrados se coordina con los vectores de dirección. Ver fi_av(3) y fi_rx_addr(3).


La llamada fi_rx_context se usa para recuperar un contexto específico, identificado por un índice (ver arriba para detalles sobre los atributos del contexto de recepción). Los proveedores pueden asignar contextos dinámicamente cuando se llama a fi_rx_context, o pueden crear estáticamente todos los contextos cuando se invoca fi_endpoint. Por defecto, un contexto de recepción hereda las propiedades de su punto de extremo asociado. Sin embargo, las aplicaciones pueden solicitar atributos específicos del contexto a través del parámetro attr. El soporte para atributos por contexto de recepción es específico del proveedor y no está garantizado. Los proveedores devolverán los atributos reales asignados al contexto a través del parámetro attr, si se proporciona.








CONTEXTOS COMPARTIDOS


Los contextos compartidos son contextos de transmisión y recepción compartidos explícitamente entre uno o más puntos de extremo. Un contexto compartible permite a una aplicación usar un único recurso dedicado del proveedor entre múltiples puntos de extremo direccionables por transporte. Esto puede reducir en gran medida los recursos necesarios para gestionar la comunicación sobre múltiples puntos de extremo al multiplexar el procesamiento de transmisión y/o recepción, con el costo potencial de serializar el acceso a través de múltiples puntos de extremo. El soporte para contextos compartibles es específico del dominio.


Conceptualmente, los contextos de transmisión compartibles son colas de transmisión a las que pueden acceder muchos puntos de extremo. El uso de un contexto de transmisión compartido es mayormente opaco para una aplicación. Las aplicaciones deben asignar y vincular contextos de transmisión compartidos a puntos de extremo, pero las operaciones se publican directamente en el punto de extremo. Los contextos de transmisión compartidos no están asociados con colas de finalización ni con contadores. Las operaciones completadas se publican en las CQs vinculadas al punto de extremo. Un punto de extremo solo puede estar asociado con un único contexto de transmisión compartido.


A diferencia de los contextos de transmisión compartidos, las aplicaciones interactúan directamente con los contextos de recepción compartidos. Los usuarios publican búferes de recepción directamente en un contexto de recepción compartido, con los búferes utilizables por cualquier punto de extremo vinculado al contexto de recepción compartido. Los contextos de recepción compartidos no están asociados con colas de finalización ni con contadores. Las operaciones de recepción completadas se publican en las CQs vinculadas al punto de extremo. Un punto de extremo solo puede estar asociado con un único contexto de recepción, y todos los puntos de extremo sin conexión asociados con un contexto de recepción compartido deben compartir también el mismo vector de dirección.


Los puntos de extremo asociados con un contexto de transmisión compartido pueden usar contextos de recepción dedicados, y viceversa. O un punto de extremo puede usar contextos de transmisión y recepción compartidos. Y no hay requisito de que el mismo grupo de puntos de extremo que comparte un contexto de un tipo también comparta el contexto de un tipo alternativo. Además, un punto de extremo puede usar un contexto compartido de un tipo, pero un conjunto escalable de contextos del tipo alternativo.




fi_stx_context


Esta llamada se usa para abrir un contexto de transmisión compartible (ver arriba para detalles sobre los atributos del contexto de transmisión). Los puntos de extremo asociados con un contexto de transmisión compartido deben usar un subconjunto de los atributos del contexto de transmisión. Nótese que esto es lo contrario del requisito para los contextos de transmisión de los puntos de extremo escalables.






fi_srx_context


Esto asigna un contexto de recepción compartible (ver arriba para detalles sobre los atributos del contexto de recepción). Los puntos de extremo asociados con un contexto de recepción compartido deben usar un subconjunto de los atributos del contexto de recepción. Nótese que esto es lo contrario del requisito para los contextos de recepción de los puntos de extremo escalables.








PUNTOS DE EXTREMO DE SOCKET


La siguiente característica y descripción deben considerarse experimentales. Hasta que se elimine la etiqueta experimental, las interfaces, semánticas y estructuras de datos asociadas con los puntos de extremo de socket pueden cambiar entre versiones de la biblioteca.


Esta sección aplica a los puntos de extremo de tipo FI_EP_SOCK_STREAM y FI_EP_SOCK_DGRAM, comúnmente referidos como puntos de extremo de socket.


Los puntos de extremo de socket están definidos con semánticas que les permiten ser adoptados más fácilmente por desarrolladores familiarizados con la API de socket UNIX, o por middleware que expone la API de socket, mientras aún aprovechan características de hardware de alto rendimiento.


La diferencia clave entre los puntos de extremo de socket y otros puntos de extremo activos es que los puntos de extremo de socket usan transferencias de datos síncronas. Los búferes pasados a las operaciones de envío y recepción vuelven al control de la aplicación al regresar de la llamada a la función. Como resultado, no se reportan finalizaciones de transferencia de datos a la aplicación, y los puntos de extremo de socket no están asociados con colas de finalización ni con contadores.


Los puntos de extremo de socket soportan un subconjunto de operaciones de mensaje: fi_send, fi_sendv, fi_sendmsg, fi_recv, fi_recvv, fi_recvmsg, y fi_inject. Debido a que las transferencias de datos son síncronas, el valor de retorno de las operaciones de envío y recepción indica el número de bytes transferidos en caso de éxito, o un valor negativo en caso de error, incluyendo -FI_EAGAIN si el punto de extremo no puede enviar o recibir ningún dato debido a colas llenas o vacías, respectivamente.


Los puntos de extremo de socket están asociados con colas de eventos y vectores de dirección, y procesan eventos de gestión de conexiones de forma asíncrona, similar a otros puntos de extremo. A diferencia de los sockets UNIX, el punto de extremo de socket aún debe declararse como activo o pasivo.


Los puntos de extremo de socket se comportan como sockets no bloqueantes. Para soportar las semánticas de select y poll, los puntos de extremo de socket activos están asociados con un descriptor de archivo que se señala cada vez que el punto de extremo está listo para enviar y/o recibir datos. El descriptor de archivo puede recuperarse usando fi_control.






BANDERAS DE OPERACIÓN


Las banderas de operación se obtienen aplicando la operación OR lógico a las siguientes banderas. Las banderas de operación definen las banderas predeterminadas aplicadas a las operaciones de transferencia de datos de un punto de extremo, donde no está disponible un parámetro de banderas. Las operaciones de transferencia de datos que toman banderas como entrada anulan el valor op_flags de los atributos de contexto de transmisión o recepción de un punto de extremo.



  
FI_COMMIT_COMPLETE

  
Indica que una completion no debe generarse (localmente ni en el par) hasta que el resultado de una operación se haya hecho persistente. Consulte fi_cq(3) para obtener más detalles sobre la semántica de finalización.

  
FI_COMPLETION

  
Indica que se debe escribir una entrada en la cola de finalización para las operaciones de transferencia de datos. Este indicador solo se aplica a las operaciones emitidas en un punto de conexión que estaba vinculado a una cola de finalización con el indicador FI_SELECTIVE_COMPLETION establecido; de lo contrario, se ignora. Consulte la sección fi_ep_bind anterior para obtener más detalles.

  
FI_DELIVERY_COMPLETE

  
Indica que se debe generar una finalización cuando la operación haya sido procesada por el(los) punto(s) de conexión de destino. Consulte fi_cq(3) para obtener más detalles sobre la semántica de finalización.

  
FI_INJECT

  
Indica que todos los búferes de datos de salida deben devolverse al control del usuario inmediatamente después de que una llamada de transferencia de datos regrese, incluso si la operación se maneja de forma asíncrona. Esto puede requerir que el proveedor copie los datos en un búfer local y transfiera desde ese búfer. Un proveedor puede limitar la cantidad total de datos de envío que se pueden almacenar en búfer y/o el tamaño de un solo envío que puede usar este indicador. Este límite se indica usando inject_size (consulte inject_size arriba).

  
FI_INJECT_COMPLETE

  
Indica que se debe generar una finalización cuando el(los) búfer(es) de origen pueda(n) ser reutilizado(s). Consulte fi_cq(3) para obtener más detalles sobre la semántica de finalización.

  
FI_MULTICAST

  
Indica que las transferencias de datos se dirigirán a direcciones de multidifusión por defecto. Cualquier fi_addr_t pasado a una operación de transferencia de datos se tratará como una dirección de multidifusión.

  
FI_MULTI_RECV

  
Se aplica a las operaciones de recepción publicadas. Este indicador permite al usuario publicar un solo búfer que recibirá múltiples mensajes entrantes. Los mensajes recibidos se empaquetarán en el búfer de recepción hasta que el búfer se haya consumido. El uso de este indicador puede hacer que una sola operación de recepción publicada genere múltiples finalizaciones a medida que los mensajes se colocan en el búfer. La colocación de los datos recibidos en el búfer puede estar sujeta a restricciones de alineación específicas del proveedor. El búfer será liberado por el proveedor cuando el espacio de búfer disponible caiga por debajo del mínimo especificado (consulte FI_OPT_MIN_MULTI_RECV).

  
FI_TRANSMIT_COMPLETE

  
Indica que se debe generar una finalización cuando la operación de transmisión se haya completado en relación con el proveedor local. Consulte fi_cq(3) para obtener más detalles sobre la semántica de finalización.








NOTAS


Los usuarios deben llamar a fi_close para liberar todos los recursos asignados al punto de conexión de la fabrica.


Los puntos de conexión asignados con los bits de modo FI_CONTEXT o FI_CONTEXT2 establecidos generalmente deben proporcionar struct fi_context(2) como su parámetro de contexto por operación. (Consulte fi_getinfo.3 para más detalles.) Sin embargo, cuando FI_SELECTIVE_COMPLETION está habilitado para suprimir las entradas de finalización de la CQ, y una operación se inicia sin el indicador FI_COMPLETION establecido, el parámetro de contexto se ignora. La aplicación no necesita pasar un struct fi_context(2) válido a tales transferencias de datos.


Las operaciones que finalizan con error y que no están asociadas con un contexto operativo válido usarán el contexto del punto de conexión en cualquier estructura de reporte de errores.


Aunque las aplicaciones típicamente asocian finalizaciones individuales con colas de finalización o contadores, un punto de conexión puede estar adjunto tanto a un contador como a una cola de finalización. Cuando se combina con el uso de finalizaciones selectivas, esto permite a la aplicación usar contadores para rastrear finalizaciones exitosas, con una CQ utilizada para reportar errores. Las operaciones que finalizan con un error incrementan el contador de errores y generan un evento de finalización en la CQ.


Como se mencionó en fi_getinfo(3), la estructura ep_attr puede usarse para consultar proveedores que soportan varios atributos de punto de conexión. fi_getinfo puede devolver estructuras de información del proveedor que pueden soportar el conjunto mínimo de requisitos (de modo que la aplicación mantenga la corrección). Sin embargo, también puede devolver estructuras de información del proveedor que excedan los requisitos de la aplicación. Como ejemplo, considere una aplicación que no solicita ningún msg_order. El resultado de la salida de fi_getinfo puede tener todos los bits de orden establecidos. La aplicación puede restablecer los bits de orden que no requiere antes de crear el punto de conexión. El proveedor es libre de implementar un orden más estricto del que requiere la aplicación.






VALORES DE RETORNO


Devuelve 0 en caso de éxito. En caso de error, se devuelve un valor negativo correspondiente al errno de la fabrica. Para fi_cancel, un valor de retorno de 0 indica que la solicitud de cancelación fue enviada para su procesamiento, un valor de retorno de -FI_EAGAIN indica que la solicitud no pudo ser enviada y que debe reintentarse una vez que se haya hecho progreso. Para fi_setopt/fi_getopt, un valor de retorno de -FI_ENOPROTOOPT indica que el proveedor no soporta la opción solicitada.


Los valores de errno de la fabrica están definidos en rdma/fi_errno.h.






ERRORES



  
-FI_EDOMAIN

  
Un dominio de recursos no fue vinculado al punto de conexión o se intentó vincular múltiples dominios.

  
-FI_ENOCQ

  
El punto de conexión no ha sido configurado con la cola de finalización necesaria.

  
-FI_EOPBADSTATE

  
El estado del punto de conexión no permite la operación solicitada.
