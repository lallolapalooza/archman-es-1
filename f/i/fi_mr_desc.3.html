DESCRIPCIÓ

N

Las regiones de memoria registradas asocian búferes de memoria con permisos concedidos para el acceso por parte de los recursos de la fabric. Un búfer de memoria debe registrarse con un dominio de recursos antes de poder utilizarse como destino de una transferencia de datos RMA o atómica remota. Además, un proveedor de fabric puede requerir que los búferes de datos se registren antes de ser utilizados en transferencias locales. Las restricciones de registro de memoria se controlan utilizando un conjunto separado de bits de modo, especificados a través de los atributos del dominio (campo mr_mode). Cada bit mr_mode requiere que una aplicación tome pasos específicos para utilizar búferes de memoria con las interfaces de

libfabric.

Como caso especial, se puede crear una nueva región de memoria a partir de una región de memoria existente. Esta nueva región de memoria se denomina sub-MR, y la región de memoria existente se denomina MR base. Las sub-MR pueden utilizarse para compartir recursos de hardware, como traducciones de direcciones virtuales a físicas y fijación de páginas. Esto puede mejorar el rendimiento al crear y destruir subregiones que requieren diferentes derechos de acceso. La MR base en sí misma también puede ser una sub-MR, permitiendo una jerarquía de regiones de

memoria.

Lo siguiente se aplica al registro de

memoria.
Registro de memoria
predeterminado
Si no se establece ningún bit mr_mode, se siguen los comportamientos predeterminados descritos a continuación. Históri
camente, estos valores predeterminados se denominaban colectivamente registro de memoria escalable. Los requisitos pr
edeterminados se describen a continuación, seguidos de definiciones de cómo cada bit mr_mode altera la definición.

Compatibilidad: Para las versiones de biblioteca 1.4 y anteriores, esto se indicaba estableciendo mr_mode en FI_MR_SCALABLE y el bit de modo fi_info FI_LOCAL_MR en 0. FI_MR_SCALABLE y FI_LOCAL_MR quedaron obsoletos en la versión 1.5 de libfabric, aunque se admiten con fines de compatibilidad hacia

atrás.

Por seguridad, se requiere el registro de memoria para los búferes de datos a los que accede directamente un proceso par. Por ejemplo, se requiere el registro para los búferes de destino RMA (leídos o escritos), y aquellos a los que acceden operaciones atómicas o

colectivas.

Por defecto, el registro se produce en rangos de direcciones virtuales. Debido a que el registro se refiere a rangos de direcciones, y no a búferes de datos asignados, los rangos de direcciones no necesitan mapearse a búferes de datos asignados por la aplicación en el momento de la llamada de registro. Es decir, una aplicación puede registrar cualquier rango de direcciones en su espacio de direcciones virtuales, independientemente de si esas direcciones están respaldadas por páginas físicas o han sido

asignadas.

Tenga en cuenta que las páginas físicas deben respaldar las direcciones antes de que las direcciones sean accedidas como parte de una operación de transferencia de datos, o las transferencias de datos fallarán. Además, dependiendo de la operación, esto podría resultar en que el proceso local reciba una violación de segmentación por acceder a memoria no

válida.

Una vez registradas, las regiones de memoria resultantes son accesibles por los pares a partir de una dirección base de 0. Es decir, la dirección de destino que se especifica es un desplazamiento en bytes dentro de la región

registrada.

La aplicación también selecciona la clave de acceso asociada con la MR. El tamaño de la clave está restringido a un máximo de 8

bytes.

Con el registro escalable, los búferes de datos accedidos localmente no se registran. Esto incluye los búferes de origen para todas las operaciones de transmisión – envíos, envíos etiquetados, RMA y atómicos – así como los búferes publicados para operaciones de recepción y recepción

etiquetada.

Aunque el comportamiento predeterminado de registro de memoria es conveniente para los desarrolladores de aplicaciones, es difícil de implementar en hardware. Los intentos de ocultar los requisitos de hardware a la aplicación a menudo resultan en impactos significativos e inaceptables en el rendimiento. Los siguientes bits mr_mode se proporcionan como entrada a fi_getinfo. Si un proveedor requiere el comportamiento definido para un bit mr_mode, dejará el bit establecido en la salida de fi_getinfo. De lo contrario, el proveedor puede limpiar el bit para indicar que el comportamiento no es

necesario.

Al establecer un bit mr_mode, la aplicación ha acordado ajustar su comportamiento como se indica. Lo más importante, las aplicaciones que elijan admitir un mr_mode deben estar preparadas para manejar el caso en que el mr_mode no es necesario. Un proveedor limpiará un bit mr_mode si no es

necesario. class="Bl-tag">
FI_MR_LOC
AL
Cuando se establece el bit de modo FI_MR_LOCAL, las aplicaciones deben registrar
todos los búferes de datos a los que accederá el hardware local y proporcionar un parámetro desc válido en las operaciones de transferencia de datos aplicables.

Cuando FI_MR_LOCAL no está establecido, las aplicaciones no están obligadas a registrar los búferes de datos antes de usarlos para operaciones locales (por ejemplo, búferes de datos de envío y recepción). Antes de libfabric 1.22, el parámetro desc era ignorado. En libfabric 1.22 y versiones posteriores, el parámetro desc debe ser válido o NULL. Este comportamiento permite a las aplicaciones pasar opcionalmente un parámetro desc válido. Si el parámetro desc es NULL, cualquier registro de memoria local requerido será manejado por el

proveedor.

Un proveedor puede ocultar los requisitos de registro local de las aplicaciones utilizando una caché de registro interna o mecanismos similares. Sin embargo, dichos mecanismos pueden afectar negativamente el rendimiento de algunas aplicaciones, notablemente aquellas que gestionan sus propios búferes de red. Para soportar el mayor rango posible de aplicaciones, sin afectar indebidamente su rendimiento, las aplicaciones que deseen gestionar sus propios registros de memoria local pueden hacerlo utilizando las llamadas de registro de memoria y pasando un parámetro desc

válido.

Nota: el bit de modo mr_mode FI_MR_LOCAL reemplaza al bit de modo fi_info FI_LOCAL_MR. Cuando FI_MR_LOCAL está establecido, FI_LOCAL_MR es

ignorado.

Las regiones de memoria sin procesar (raw) se utilizan para soportar proveedores con claves mayores de 64 bits o que requieren configuración en el par. Cuando el bit FI_MR_RAW está establecido, las aplicaciones deben usar fi_mr_raw_attr() localmente y fi_mr_map_raw() en el par antes de dirigirse a una región de memoria como parte de cualquier solicitud de transferencia de

El bit FI_MR_VIRT_ADDR indica que el proveedor referencia las regiones de memoria por dirección virtual, en lugar de un desplazamiento basado en 0. Los pares que se dirigen a regiones de me
moria registradas con FI_MR_VIRT_ADDR especifican el búfer de memoria de destino usando la dirección virtual del destino, con cualquier desplazamiento dentro de la región especificado como d
irección virtual + desplazamiento. El soporte de este bit generalmente implica que los pares deben intercambiar datos de direccionamiento antes de iniciar cualquier operación RMA o atómica.

Para las regiones de memoria que están registradas usando FI_MR_DMABUF, la `dirección virtual' inicial de la región DMA-buf se obtiene añadiendo el campo offset al campo base_addr de la estructura fi_mr_dmabuf que fue especificada a través de la llamada de

registro.
FI_MR_ALLOCA
TED
Cuando está establecido, todas las regiones de memoria registradas deben estar respaldadas por páginas de memoria física en el momento en que se realiza la llamada de registro. Además
, las aplicaciones no deben realizar operaciones que puedan resultar en un cambio en el mapeo de la dirección virtual subyacente a la página física (por ejemplo, llamar a free() contra
una MR asignada). No adherirse a esto puede resultar en que la dirección virtual apunte a un conjunto de páginas físicas mientras que la MR apunte a otro conjunto de páginas físicas.

Cuando no está establecido, las regiones de memoria registradas no necesitan estar respaldadas por páginas de memoria física en el momento en que se realiza la llamada de registro. Además, se permite que el mapeo subyacente de la dirección virtual a la página física cambie, y el proveedor se asegurará de que la MR correspondiente se actualice en consecuencia. Este comportamiento permite casos de uso de la aplicación donde la memoria puede ser frecuentemente liberada y realocada o la memoria del sistema migrando hacia/desde la memoria del

dispositivo.

Cuando no está establecido, la aplicación es responsable de asegurar que una región de memoria registrada referencie páginas físicas válidas mientras una transferencia de datos está activa contra ella, o la transferencia de datos puede fallar. Los cambios de la aplicación en el rango de direcciones virtuales deben coordinarse con el tráfico de red hacia o desde ese

rango.

Si no está establecido y FI_HMEM es soportado, la capacidad del mapeo de dirección virtual a dirección física para cambiar se extiende a las interfaces HMEM también. Si un proveedor no puede soportar un cambio de dirección virtual a dirección física para una interfaz HMEM dada, el proveedor debería soportar un respaldo razonable o la operación debería

fallar.
FI_MR_PROV_K
EY
Este modo de región de memoria indica que el proveedor no soporta claves de MR solicitadas por la aplicación. Las claves de MR son devueltas por el proveedor. Las aplicaciones que soportan FI_MR_PROV_KEY pueden obtener la clave del proveedor usando fi_mr_key(), a menos que FI_MR_RAW también esté establecido. La clave devuelta debe ser intercambiada con los pares antes de iniciar una operación RMA o
atómica.
FI_MR_MMU_NOT
IFY
FI_MR_MMU_NOTIFY es típicamente establecido por proveedores que soportan el registro de memoria contra regiones de memoria que no están necesariamente respaldadas por páginas físicas asignadas en el momento en que ocurre el registro de memoria. (Es decir, FI_MR_ALLOCATED es típicamente 0). Sin embargo, dichos proveedores requieren que las aplicaciones notifiquen al proveedor antes de que la MR sea accedida como parte de una operación de transferencia de datos. Esta notificación informa al proveedor que todas las páginas físicas necesarias ahora respaldan la región. La notificación es necesaria para proveedores que no pueden engancharse directamente en las tablas de páginas del sistema operativo o en la unidad de gestión de memoria. Ver fi_mr_refresh() para detalles de la
notificación.

Registro de Memoria Básico
(obsoleto)
El registro de memoria básico fue obsoleto en la versión 1.5 de libfabric, pero es soportado para compatibilidad hacia atrás. El registro de memoria básico está indicado por e
stablecer mr_mode igual a FI_MR_BASIC. FI_MR_BASIC debe establecerse solo y no emparejarse con bits de mr_mode. A diferencia de otros bits de mr_mode, si FI_MR_BASIC está est
ablecido en la entrada a fi_getinfo(), no será borrado por el proveedor. Es decir, establecer mr_mode igual a FI_MR_BASIC fuerza el registro básico si el proveedor lo soporta.

El comportamiento del registro básico es equivalente a requerir los siguientes bits de mr_mode: FI_MR_VIRT_ADDR, FI_MR_ALLOCATED, y FI_MR_PROV_KEY. Adicionalmente, los proveedores que soportan el registro básico usualmente requieren el bit de modo fi_info (obsoleto) FI_LOCAL_MR, que fue incorporado en el bit de modo mr_mode

FI_MR_LOCAL.

Las funciones de registro – fi_mr_reg, fi_mr_regv, y fi_mr_regattr – se usan para registrar una o más regiones de memoria con recursos de fabric. La principal diferencia entre las funciones de registro es el número y tipo de parámetros que aceptan como entrada. De lo contrario, realizan la misma función

general.

Obsoleto : Por defecto, el registro de memoria se completa de forma sincrónica. Es decir, la llamada de registro no retornará hasta que el registro se haya completado. El registro de memoria puede completarse de forma asíncrona enlazando el dominio de recursos a una cola de eventos usando el flag FI_REG_MR. Ver fi_domain_bind. Cuando el registro de memoria es asíncrono, para evitar una condición de carrera entre el retorno de la llamada de registro y la lectura correspondiente del evento de la cola de eventos (EQ), el parámetro de salida mr será escrito antes de que cualquier evento asociado con la operación pueda ser leído por la aplicación. No se generará un evento asíncrono a menos que la llamada de registro retorne éxito (0)

.

fi_mr_re

g

La llamada fi_mr_reg registra el búfer de memoria especificado por el usuario con el dominio de recursos. El búfer se habilita para su acceso por parte del hardware de la malla (fabric) basándose en los permisos de acceso proporcionados. Vea la descripción del campo de acceso para los atributos de la región de memoria a

continuación.

La memoria registrada se asocia con un descriptor de memoria local y, opcionalmente, con una clave de memoria remota. Un descriptor de memoria es un identificador específico del proveedor asociado con la memoria registrada. Los descriptores de memoria a menudo se mapean a índices o claves específicos del hardware asociados con la región de memoria. Las claves de memoria remotas proporcionan una protección limitada contra el acceso no deseado por parte de un nodo remoto. Los accesos remotos a una región de memoria deben proporcionar la clave asociada con el

registro.

Dado que las claves MR deben ser proporcionadas por un proceso remoto, una aplicación puede usar el parámetro requested_key para indicar que se devuelva un valor de clave específico. El soporte para claves solicitadas por el usuario es específico del proveedor y está determinado por el valor del indicador FI_MR_PROV_KEY en el atributo de dominio

mr_mode.

Las operaciones RMA y atómicas remotas indican la ubicación dentro de una región de memoria registrada especificando una dirección. La ubicación se referencia sumando el desplazamiento (offset) a la dirección virtual base del búfer o a 0, dependiendo del

mr_mode.

El parámetro offset está reservado para uso futuro y debe ser

0.

Para solicitudes de registro de memoria asíncronas, el resultado se informará al usuario a través de una cola de eventos asociada con el dominio de recursos. Si tiene éxito, la estructura de la región de memoria asignada se devolverá al usuario a través del parámetro mr. La dirección mr debe permanecer válida hasta que la operación de registro se complete. El contexto especificado con la solicitud de registro se devuelve con el evento de

finalización.

fi_clos

e

Fi_close se utiliza para liberar todos los recursos asociados con el registro de una región de memoria. Una vez desregistrada, no se garantiza el acceso posterior a la memoria registrada. Las operaciones activas o en cola que referencian una región de memoria que se está cerrando pueden intentar acceder a una región de memoria no válida y fallar. Después de que se cierre una MR, cualquier nueva operación dirigida a la MR cerrada también fallará. Las aplicaciones son responsables de asegurarse de que una MR ya no sea necesaria antes de cerrarla. Tenga en cuenta que los accesos a una MR cerrada desde un par remoto resultarán en un error en el par. El estado del punto de extremo local no se verá

afectado.

Para las MR que están asociadas con un punto de extremo (el indicador FI_MR_ENDPOINT está establecido), la MR debe cerrarse antes que el punto de extremo. Si aún hay recursos asociados con la MR al intentar cerrarla, la llamada devolverá

-FI_EBUSY.

Si se utiliza una caché de registro de memoria, el comportamiento

de fi_close puede verse afectado. Hay más información sobre la cac
hé de registro de memoria en la sección MEMORY REGISTRATION CACHE.

NOTES

Direct access to an application’s memory by a remote peer requires that the application register the targeted memory buffer(s). This is typically done by calling one of the fi_mr_reg* routines. For FI_MR_PROV_KEY, the provider will return a key that must be used by the peer when accessing the memory region. The application is responsible for transferring this key to the peer. If FI_MR_RAW mode has been set, the key must be retrieved using the fi_mr_raw_attr function.

FI_MR_RAW allows support for providers that require more than 8-bytes for their protection keys or need additional setup before a key can be used for transfers. After a raw key has been retrieved, it must be exchanged with the remote peer. The peer must use fi_mr_map_raw to convert the raw key into a usable 64-bit key. The mapping must be done even if the raw key is 64-bits or smaller.

The raw key support functions are usable with all registered memory regions, even if FI_MR_RAW has not been set. It is recommended that portable applications target using those interfaces; however, their use does carry extra message and memory footprint overhead, making it less desirable for highly scalable apps.

There may be cases where device peer to peer support should not be used or cannot be used, such as when the PCIe ACS configuration does not permit the transfer. The FI_HMEM_DISABLE_P2P environment variable can be set to notify Libfabric that peer to peer transactions should not be used. The provider may choose to perform a copy instead, or will fail support for FI_HMEM if the provider is unable to do that.

MEMORY DOMAINS

Memory domains identify the physical separation of memory which may or may not be accessible through the same virtual address space. Traditionally, applications only dealt with a single memory domain, that of host memory tightly coupled with the system CPUs. With the introduction of device and non-uniform memory subsystems, applications often need to be aware of which memory domain a particular virtual address maps to.

As a general rule, separate physical devices can be considered to have their own memory domains. For example, a NIC may have user accessible memory, and would be considered a separate memory domain from memory on a GPU. Both the NIC and GPU memory domains are separate from host system memory. Individual GPUs or computation accelerators may have distinct memory domains, or may be connected in such a way (e.g. a GPU specific fabric) that all GPUs would belong to the same memory domain. Unfortunately, identifying memory domains is specific to each system and its physical and/or virtual configuration.

Understanding memory domains in heterogenous memory environments is important as it can impact data ordering and visibility as viewed by an application. It is also important to understand which memory domain an application is most tightly coupled to. In most cases, applications are tightly coupled to host memory. However, an application running directly on a GPU or NIC may be more tightly coupled to memory associated with those devices.

Memory regions are often associated with a single memory domain. The domain is often indicated by the fi_mr_attr iface and device fields. Though it is possible for physical pages backing a virtual memory region to migrate between memory domains based on access patterns. For example, the physical pages referenced by a virtual address range could migrate between host memory and GPU memory, depending on which computational unit is actively using it.

See the fi_endpoint(3) and fi_cq(3) man pages for addition discussion on message, data, and completion ordering semantics, including the impact of memory domains.

MEMORY REGISTRATION CACHE

Many hardware NICs accessed by libfabric require that data buffers be registered with the hardware while the hardware accesses it. This ensures that the virtual to physical address mappings for those buffers do not change while the transfer is occurring. The performance impact of registering memory regions can be significant. As a result, some providers make use of a registration cache, particularly when working with applications that are unable to manage their own network buffers. A registration cache avoids the overhead of registering and unregistering a data buffer with each transfer.

If a registration cache is going to be used for host and device memory, the device must support unified virtual addressing.
