NOMBRE

fi_tagged - Operaciones de transferencia de datos etiquetados

fi_trecv / fi_trecvv / fi_trecvmsg
Publicar un búfer para recibir un mensaje entrante
fi_tsend / fi_tsendv / fi_tsendmsg / fi_tinject / fi_tsenddata
Iniciar una operación para enviar un mensaje

SINOPSIS

#include <rdma/fi_tagged.h>
ssize_t fi_trecv(struct fid_ep *ep, void *buf, size_t len, void *desc,
    fi_addr_t src_addr, uint64_t tag, uint64_t ignore, void *context);
ssize_t fi_trecvv(struct fid_ep *ep, const struct iovec *iov, void **desc,
    size_t count, fi_addr_t src_addr, uint64_t tag, uint64_t ignore,
    void *context);
ssize_t fi_trecvmsg(struct fid_ep *ep, const struct fi_msg_tagged *msg,
    uint64_t flags);
ssize_t fi_tsend(struct fid_ep *ep, const void *buf, size_t len,
    void *desc, fi_addr_t dest_addr, uint64_t tag, void *context);
ssize_t fi_tsendv(struct fid_ep *ep, const struct iovec *iov,
    void **desc, size_t count, fi_addr_t dest_addr, uint64_t tag,
    void *context);
ssize_t fi_tsendmsg(struct fid_ep *ep, const struct fi_msg_tagged *msg,
    uint64_t flags);
ssize_t fi_tinject(struct fid_ep *ep, const void *buf, size_t len,
    fi_addr_t dest_addr, uint64_t tag);
ssize_t fi_tsenddata(struct fid_ep *ep, const void *buf, size_t len,
    void *desc, uint64_t data, fi_addr_t dest_addr, uint64_t tag,
    void *context);
ssize_t fi_tinjectdata(struct fid_ep *ep, const void *buf, size_t len,
    uint64_t data, fi_addr_t dest_addr, uint64_t tag);

ARGUMENTOS

fid
Punto final de tejido sobre el cual iniciar la operación de comunicación etiquetada.
buf
Búfer de datos para enviar o recibir.
len
Longitud del búfer de datos a enviar o recibir, especificada en bytes. Las transferencias válidas van desde 0 bytes hasta el tamaño máximo de mensaje del punto final.
iov
Búfer de datos vectorizados.
count
Número de entradas de datos vectorizados.
tag
Etiqueta asociada con el mensaje.
ignore
Máscara de bits a ignorar aplicada a la etiqueta para operaciones de recepción.
desc
Descriptor de memoria asociado con el búfer de datos. Véase fi_mr(3).
data
Datos de CQ remotos para transferir con los datos enviados.
dest_addr
Dirección de destino para transferencias sin conexión. Ignorado para puntos finales conectados.
src_addr
Se aplica solo a puntos finales sin conexión configurados con FI_DIRECTED_RECV. Para todas las demás configuraciones de puntos finales, src_addr se ignora. src_addr define la dirección de origen desde la cual recibir. Por defecto, src_addr se trata como una dirección de punto final de origen (es decir, fi_addr_t devuelto por fi_av_insert / fi_av_insertsvc / fi_av_remove). Si se especifica el indicador FI_AUTH_KEY con fi_trecvmsg, src_addr se trata como una clave de autorización de origen (es decir, fi_addr_t devuelto por fi_av_insert_auth_key). Si se establece en FI_ADDR_UNSPEC, cualquier dirección de origen puede coincidir.
msg
Descriptor de mensaje para operaciones de envío y recepción.
flags
Indicadores adicionales a aplicar para la operación de envío o recepción.
context
Puntero especificado por el usuario para asociarlo con la operación. Este parámetro se ignora si la operación no generará una finalización exitosa, a menos que un indicador de operación especifique que el parámetro de contexto se utilizará para entrada requerida.

DESCRIPCIÓN

Los mensajes etiquetados son transferencias de datos que llevan una clave o etiqueta con el búfer del mensaje. La etiqueta se utiliza en el punto final receptor para hacer coincidir el mensaje entrante con un búfer de recepción correspondiente. Las etiquetas de mensajes coinciden cuando la etiqueta del búfer de recepción es la misma que la etiqueta del búfer de envío con los bits ignorados enmascarados. Esto se puede expresar como:

send_tag & ~ignore == recv_tag & ~ignore
o
send_tag | ignore == recv_tag | ignore

En general, las etiquetas de mensajes se comparan con los búferes de recepción en el orden en que se han publicado los mensajes en el punto final. Consulte la discusión sobre el orden a continuación para obtener más detalles.

Las funciones de envío — fi_tsend, fi_tsendv, fi_tsendmsg, fi_tinject y fi_tsenddata — se utilizan para transmitir un mensaje etiquetado desde un punto final a otro. La principal diferencia entre las funciones de envío son el número y tipo de parámetros que aceptan como entrada. De lo contrario, realizan la misma función general.

Las funciones de recepción — fi_trecv, fi_trecvv, fi_recvmsg — publican un búfer de datos en un punto final para recibir mensajes etiquetados entrantes. Al igual que las operaciones de envío, las operaciones de recepción funcionan de forma asíncrona. Los usuarios no deben tocar los búferes de datos publicados hasta que la operación de recepción se haya completado. Los búferes de recepción publicados se emparejan con los mensajes de envío entrantes basándose en las etiquetas asociadas con los búferes de envío y recepción.

Un punto final debe estar habilitado antes de que una aplicación pueda publicar operaciones de envío o recepción en él. Para puntos finales conectados, los búferes de recepción pueden publicarse antes de llamar a connect o accept en el punto final. Esto garantiza que los búferes estén disponibles para recibir datos entrantes inmediatamente después de que se haya establecido la conexión.

Las operaciones de mensajes completadas se informan al usuario a través de uno o más recolectores de eventos asociados con el punto final. Los usuarios proporcionan contextos que se asocian con cada operación y se devuelven al usuario como parte de la finalización del evento. Consulte fi_cq para obtener detalles sobre los eventos de finalización.

fi_tsend

La llamada fi_tsend transfiere los datos contenidos en el búfer de datos especificado por el usuario a un punto final remoto, manteniendo los límites del mensaje. El punto final local debe estar conectado a un punto final o destino remoto antes de llamar a fi_tsend. A menos que el punto final se haya configurado de manera diferente, el búfer de datos pasado a fi_tsend no debe ser manipulado por la aplicación hasta que la llamada fi_tsend se complete de forma asíncrona.

fi_tsendv

La llamada fi_tsendv añade soporte para una lista de dispersión-agregación a fi_tsend. fi_sendv transfiere el conjunto de búferes de datos referenciados por el parámetro iov a un punto final remoto como un único mensaje.

fi_tsendmsg

La llamada fi_tsendmsg admite transferencias de datos a través de puntos finales conectados y sin conexión, con la capacidad de controlar la operación de envío por llamada mediante el uso de indicadores. La función fi_tsendmsg toma una estructura fi_msg_tagged como entrada.

struct fi_msg_tagged {
    const struct iovec *msg_iov; /* array scatter-gather */
    void               *desc;    /* descriptor de datos */
    size_t             iov_count;/* # elementos en msg_iov */
    fi_addr_t          addr;    /* dirección de punto final opcional */
    uint64_t           tag;      /* etiqueta asociada con el mensaje */
    uint64_t           ignore;   /* máscara aplicada a la etiqueta para recepciones */
    void               *context; /* contexto definido por el usuario */
    uint64_t           data;     /* datos inmediatos opcionales */
};

fi_tinject

La llamada de inyección etiquetada es una versión optimizada de fi_tsend. Proporciona semántica de finalización similar a fi_inject de fi_msg(3).

fi_tsenddata

La llamada de envío de datos etiquetados es similar a fi_tsend, pero permite el envío de datos de CQ remotos (ver indicador FI_REMOTE_CQ_DATA) como parte de la transferencia.

fi_tinjectdata

La llamada de inyección de datos etiquetados es similar a fi_tinject, pero permite el envío de datos de CQ remotos (ver indicador FI_REMOTE_CQ_DATA) como parte de la transferencia.

NOMBRE

fi_trecv, fi_trecvv, fi_trecvmsg - publicar búferes de recepción con etiquetas

SINOPSIS

#include <rdma/fi_tags.h>

ssize_t fi_trecv(fi_eq_handle_t eq, void *buf, size_t len, void *desc,
    uint64_t tag, uint64_t tag_mask);
ssize_t fi_trecvv(fi_eq_handle_t eq, struct fi_iov *iov, size_t *num_iov,
    void *desc);
ssize_t fi_trecvmsg(fi_eq_handle_t eq, struct fi_msg_tagged *msg, uint64_t flags);

ARGUMENTOS

eq
Handle para la cola de finalización (completion queue) en la que se publicarán las operaciones de recepción. El contexto de recepción debe estar asociado con esta EQ.
buf
Puntero al búfer de datos para la operación de recepción.
len
Longitud del búfer de datos en bytes.
iov
Un arreglo de estructuras fi_iov que especifican los búferes de datos para la operación de recepción (scatter/gather).
num_iov
En la entrada, el número máximo de elementos fi_iov en el arreglo iov. En la salida, el número de elementos fi_iov utilizados para la operación de recepción.
desc
Puntero a un descriptor de operación. Esto se utiliza para asociar la operación de recepción con un descriptor de contexto de memoria (MR) o un búfer de inserción. El descriptor se devuelve con la entrada de finalización asociada con la operación de recepción.
tag
El valor de etiqueta de destino.
tag_mask
La máscara de etiqueta de destino. Las etiquetas de mensajes entrantes se comparan con la etiqueta y la máscara de destino utilizando una operación AND bit a bit. La etiqueta de destino se representa como(incoming_tag & tag_mask) == tag.
msg
Puntero a una estructura `fi_msg_tagged` que contiene los búferes, el contexto y otros parámetros para la operación de recepción con etiquetas.
flags
Banderas que modifican el comportamiento de la operación de recepción. Consulte la sección FLAGS.

DESCRIPCIÓN

fi_trecv

La llamada `fi_trecv` publica un búfer de datos en la cola de recepción del punto final correspondiente. Las recepciones publicadas se buscan en el orden en que se publicaron para que coincidan con los envíos. Los límites de los mensajes se mantienen. El orden en que se completan las recepciones depende del tipo de punto final y del protocolo.

fi_trecvv

La llamada `fi_trecvv` añade soporte para una lista scatter-gather a `fi_trecv`. `fi_trecvv` publica el conjunto de búferes de datos referenciados por el parámetro `iov` para recibir datos entrantes.

fi_trecvmsg

La llamada `fi_trecvmsg` soporta la publicación de búferes tanto en puntos finales conectados como sin conexión, con la capacidad de controlar la operación de recepción por llamada mediante el uso de banderas. La función `fi_trecvmsg` toma una estructura `struct fi_msg_tagged` como entrada.

BANDERA

Las llamadas `fi_trecvmsg` y `fi_tsendmsg` permiten al usuario especificar banderas que pueden cambiar el manejo de mensajes predeterminado del punto final. Las banderas especificadas con `fi_trecvmsg` / `fi_tsendmsg` anulan la mayoría de las banderas configuradas previamente con el punto final, excepto donde se indica (ver `fi_endpoint`). La siguiente lista de banderas son utilizables con `fi_trecvmsg` y/o `fi_tsendmsg`.

FI_REMOTE_CQ_DATA
Se aplica a `fi_tsendmsg`. Indica que los datos de CQ remotos están disponibles y deben enviarse como parte de la solicitud. Ver `fi_getinfo` para más detalles sobre `FI_REMOTE_CQ_DATA`. Esta bandera se establece implícitamente para `fi_tsenddata` y `fi_tinjectdata`.
FI_COMPLETION
Indica que se debe generar una entrada de finalización para la operación especificada. El punto final debe estar enlazado a una cola de finalización con `FI_SELECTIVE_COMPLETION` que corresponda a la operación especificada, o esta bandera se ignora.
FI_MORE
Indica que el usuario tiene solicitudes adicionales que se publicarán inmediatamente después de que la llamada actual regrese. El uso de esta bandera puede mejorar el rendimiento al permitir que el proveedor optimice su acceso al hardware de la red.
FI_INJECT
Se aplica a `fi_tsendmsg`. Indica que el búfer de datos de salida debe devolverse al usuario inmediatamente después de que la llamada de envío regrese, incluso si la operación se maneja de forma asíncrona. Esto puede requerir que la implementación del proveedor subyacente copie los datos a un búfer local y transfiera desde ese búfer. Esta bandera solo se puede usar con mensajes más pequeños que `inject_size`.
FI_MULTI_RECV
Se aplica a operaciones de recepción con etiquetas publicadas cuando la capacidad `FI_TAGGED_MULTI_RECV` está habilitada. Esta bandera permite al usuario publicar un único búfer de recepción con etiquetas que recibirá múltiples mensajes entrantes. Los mensajes recibidos se empaquetarán en el búfer de recepción hasta que se haya consumido el búfer. El uso de esta bandera puede hacer que una única operación de recepción publicada genere múltiples eventos a medida que los mensajes se colocan en el búfer. La colocación de los datos recibidos en el búfer puede estar sujeta a restricciones de alineación específicas del proveedor.

El búfer será liberado por el proveedor cuando el espacio disponible del búfer caiga por debajo del mínimo especificado (ver `FI_OPT_MIN_MULTI_RECV`). Tenga en cuenta que siempre se generará una entrada en la cola de finalización de recepción asociada cuando el búfer se haya consumido, incluso si otras finalizaciones de recepción se han suprimido (es decir, el contexto de Rx se ha configurado para `FI_SELECTIVE_COMPLETION`). Ver la bandera de finalización `FI_MULTI_RECV` en `fi_cq(3)`.

FI_INJECT_COMPLETE
Se aplica a `fi_tsendmsg`. Indica que se debe generar una finalización cuando los búferes de origen puedan reutilizarse.
FI_TRANSMIT_COMPLETE
Se aplica a `fi_tsendmsg`. Indica que no se debe generar una finalización hasta que la operación se haya transmitido con éxito y ya no sea rastreada por el proveedor.
FI_MATCH_COMPLETE
Se aplica a `fi_tsendmsg`. Indica que una finalización solo debe generarse después de que el mensaje haya coincidido con un búfer con etiqueta o haya sido descartado por la aplicación de destino.
FI_FENCE
Se aplica a las transmisiones. Indica que la operación solicitada, también conocida como operación cercada, y cualquier operación publicada después de la operación cercada se pospondrán hasta que todas las operaciones anteriores dirigidas al mismo punto final par hayan completado. Las operaciones publicadas después del cercado verán y/o reemplazarán los resultados de cualquier operación iniciada antes de la operación cercada.

El orden de las operaciones que comienzan con la publicación de la operación cercada (inclusive) hasta la publicación de una operación cercada subsiguiente (exclusiva) está controlado por la semántica de ordenación del punto final.

FI_AUTH_KEY
Solo válido con dominios configurados con `FI_AV_AUTH_KEY` y puntos finales sin conexión configurados con `FI_DIRECTED_RECV` o `FI_TAGGED_DIRECTED_RECV`. Cuando se usa con `fi_trecvmsg`, esta bandera indica que `src_addr` es una clave de autorización `fi_addr_t` en lugar de un punto final `fi_addr_t`.

Las siguientes banderas se pueden usar con `fi_trecvmsg`.

FI_PEEK
La bandera `peek` se puede usar para ver si ha llegado un mensaje especificado. Una solicitud de `peek` es útil a menudo en puntos finales que tienen activado el almacenamiento en búfer asignado por el proveedor. A diferencia de las operaciones de recepción estándar, una operación de recepción con la bandera `FI_PEEK` establecida no permanece en cola con el proveedor después de que `peek` se complete con éxito. La operación de `peek` opera de forma asíncrona, y los resultados de la operación de `peek` están disponibles en la cola de finalización asociada con el punto final. Si no se encuentra ningún mensaje que coincida con las etiquetas especificadas en la solicitud de `peek`, habrá una entrada de error en la cola de finalización con el campo `err` establecido en `FI_ENOMSG`.

Si una solicitud de `peek` localiza un mensaje coincidente, la operación se completará con éxito. Los datos de finalización devueltos indicarán los metadatos asociados con el mensaje, como la longitud del mensaje, las banderas de finalización, los datos de CQ disponibles, la etiqueta y la dirección de origen. Los datos disponibles están sujetos al formato de la entrada de finalización (por ejemplo, `struct fi_cq_tagged_entry`).

FI_CLAIM
Si esta bandera se usa junto con `FI_PEEK`, indica que si la solicitud de `peek` se completa con éxito, lo que indica que se encontró un mensaje coincidente, el mensaje es reclamado por el llamador. Los mensajes reclamados solo se pueden recuperar utilizando una operación de recepción posterior y emparejada con la bandera `FI_CLAIM` establecida. Una operación de recepción con la bandera `FI_CLAIM` establecida, pero sin `FI_PEEK`, se utiliza para recuperar un mensaje reclamado previamente.

Para usar la bandera `FI_CLAIM`, una aplicación debe proporcionar una estructura `struct fi_context` como contexto para la operación de recepción. La misma estructura `fi_context` utilizada para una operación `FI_PEEK` + `FI_CLAIM` debe ser utilizada por la solicitud `FI_CLAIM` emparejada.

FI_DISCARD
Esta bandera se puede usar junto con `FI_PEEK` o `FI_CLAIM`. Si esta bandera se usa junto con `FI_PEEK`, indica que si la solicitud de `peek` se completa con éxito, lo que indica que se encontró un mensaje coincidente, el mensaje es descartado por el proveedor, ya que los datos no son necesarios para la aplicación. Esta bandera también se puede usar junto con `FI_CLAIM` para descartar un mensaje reclamado previamente utilizando una solicitud `FI_PEEK` + `FI_CLAIM`.

Si esta bandera está establecida, los parámetros del búfer de entrada y la longitud se ignoran.

VALOR DE RETORNO

Las llamadas de envío y recepción con etiquetas devuelven 0 en caso de éxito. En caso de error, se devuelve un valor negativo correspondiente al `errno` de la red. Los valores de `errno` de la red se definen en `fi_errno.h`.

ERRORES

-FI_EAGAIN
Ver `fi_msg(3)` para una descripción detallada del manejo de `FI_EAGAIN`.
-FI_EINVAL
Indica que el usuario proporcionó un argumento inválido.
-FI_EOTHER
Indica que ocurrió un error no especificado.
