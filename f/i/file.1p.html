NOMBRE

file - interpretar y clasificar archivo

SINOPSIS

file [-b] [-C] [-c] [-d] [-e esquema] [-f nombrearchivo] [-i] [-k] [-m archivo_mágico] [-N] [-n] [-O] [-p] [-P] [-r] [-s] [-S] [-t] [-v] [-z] [--] archivo...

DESCRIPCIÓN

El programa utilitario file determina el tipo de archivo de cada uno de los argumentos de archivo. Cada archivo se examina y se genera una descripción de su tipo. Si el archivo es legible, file lo examinará para determinar si es un archivo de texto ASCII, o si es un archivo ejecutable binario, etc.

Si el archivo es un archivo de texto, file lo leerá y clasificará los primeros 512 bytes para determinar si contiene caracteres de control de flujo de texto, una línea de texto en inglés, o si parece ser un archivo de algún lenguaje de programación de computadora (por ejemplo, C, Fortran, Lisp, Pascal, etc.).

Si file no puede determinar nada más sobre el archivo, intentará identificarlo usando una tabla de "valores mágicos". Estos son valores conocidos que se encuentran en ubicaciones específicas dentro de los archivos. Por ejemplo, los primeros bytes de un archivo ejecutable estándar de UNIX contienen un número mágico específico.

La salida de file es una descripción textual de la clasificación del archivo. Si el archivo es un archivo de texto regular, la salida contendrá las palabras ``texto'' y, si es posible, el lenguaje programado; de lo contrario, la salida indicará si es un archivo ejecutable o un archivo de datos, y las características de estos. Si se especifica el opción -i, se imprimirá una línea de texto que contiene la información de tipo de archivo en un formato más estructurado.

La siguiente lista muestra los tipos de archivos que file puede identificar:

executable
Archivo ejecutable binario.
directory
Directorio.

Archivo especial de caracteres.
block special file
Archivo especial de bloques.

Archivo FIFO (named pipe).
socket
Archivo socket.
symbolic link
Enlace simbólico.
compressed data
Datos comprimidos.
archive data
Datos de archivo (por ejemplo, tar, cpio).
core file

Archivo ELF (Executable and Linkable Format).
Java class file
Archivo de clase Java.

Documento PostScript.
script

XML document
Documento XML.

Este es solo un subconjunto de los tipos de archivos que file puede reconocer. La lista completa y detallada de los tipos de archivos reconocidos está disponible en la documentación del sistema.

SECCIONES

Las siguientes secciones son normativas.

FORMATO DEL ARCHIVO MAGICO

Un archivo mágico es un archivo de texto que contiene una lista de reglas que se utilizan para identificar los tipos de archivos. Cada regla consta de tres campos, separados por espacios en blanco:

offset
El desplazamiento (en bytes) desde el inicio del archivo donde se buscará el patrón.
type
El tipo de dato a buscar en el desplazamiento especificado. Los tipos posibles son:
byte
Un solo byte.
short
Un entero corto (2 bytes).
long
Un entero largo (4 bytes).
string
Una cadena de caracteres.
date
Un entero largo (4 bytes) interpretado como una fecha y hora.
equal
Una cadena de caracteres que debe ser igual al valor.
regex
Una expresión regular POSIX ERE.
value
El valor que se buscará en el desplazamiento especificado. El formato de este campo depende del tipo especificado.
&&operator
El operador a aplicar al valor del archivo. Los operadores posibles son:
=
Igual.
!=
No igual.
>
Mayor que.
>=
Mayor o igual que.
<
Menor que.
<=
Menor o igual que.
~
Coincide con la expresión regular.
message
El mensaje que se imprimirá si la prueba tiene éxito. El mensaje puede contener secuencias de escape de formato de tipo printf. Si el campo value fue una cadena, entonces el valor del archivo se utilizará como argumento para la especificación de formato de printf; de lo contrario, el valor del archivo se utilizará como argumento.

Las pruebas se realizan en el orden en que aparecen en el archivo mágico. La primera prueba que tiene éxito determina el tipo de archivo.

Los siguientes son ejemplos de pruebas en un archivo mágico:

0 string \177ELF c program executable
Si los primeros 4 bytes del archivo son la cadena ASCII `\177ELF`, entonces se clasifica como un ejecutable de programa C.
4 string UNIX System V text executable
Si los primeros 4 bytes del archivo son la cadena ASCII `UNIX`, entonces se clasifica como un ejecutable del Sistema V de UNIX.
0 long >0 shell script
Si el primer valor largo del archivo es mayor que 0, entonces se clasifica como un script de shell.

USO DE APLICACIÓN

El programa utilitario file solo puede ser requerido para adivinar muchos de los tipos de archivos porque solo una prueba exhaustiva puede determinar algunos tipos con certeza. Por ejemplo, los datos binarios en algunas implementaciones podrían coincidir con el segmento inicial de un archivo ejecutable o un archivo tar.

Tenga en cuenta que la tabla indica que la salida contiene la cadena indicada. Los sistemas pueden agregar texto antes o después de la cadena. Para ejecutables, como ejemplo, la arquitectura de la máquina y varios hechos sobre cómo se enlazó el archivo pueden incluirse. Tenga en cuenta también que en sistemas que reconocen archivos de script de shell que comienzan con "#!" como archivos ejecutables, estos pueden ser identificados como archivos binarios ejecutables en lugar de como scripts de shell.

EJEMPLOS

Determinar si un argumento es un archivo ejecutable binario:

file -- "$1" | grep -q ':.*executable' &&
    printf "%s es ejecutable.\n$1"

RACIOCINIO

Se omitió la opción -f porque el mismo efecto puede (y debe) obtenerse utilizando el programa utilitario xargs.

Versiones históricas del programa utilitario file intentan identificar los siguientes tipos de archivos: enlace simbólico, directorio, especial de caracteres, especial de bloques, socket, archivo tar, archivo cpio, archivo SCCS, biblioteca de archivos, vacío, salida de compress, salida de pack, datos binarios, fuente C, fuente FORTRAN, fuente ensamblador, fuente nroff/troff/eqn/tbl, salida de troff, script de shell, script de shell C, texto en inglés, texto ASCII, varios ejecutables, espacio de trabajo APL, entradas de terminfo compiladas e imágenes de pantalla CURSES. Solo los tipos que están razonablemente bien especificados en POSIX o que están directamente relacionados con utilidades POSIX se enumeran en la tabla.

Los sistemas históricos han utilizado un "archivo mágico" llamado /etc/magic para ayudar a identificar tipos de archivos. Debido a que es generalmente útil para los usuarios y scripts poder identificar tipos de archivos especiales, se ha especificado el flag -m y un formato portable para archivos mágicos creados por el usuario. No se exige que una implementación de file utilice este método de identificación de archivos, solo que a los usuarios se les permita agregar sus propias pruebas de clasificación.

Además, se han agregado tres opciones a la práctica histórica. Se ha agregado el flag -d para permitir a los usuarios que sus pruebas sigan cualquier prueba de sistema predeterminada. Se ha agregado el flag -i para permitir a los usuarios probar de forma portable archivos regulares en scripts de shell. Se ha agregado el flag -M para permitir a los usuarios ignorar cualquier prueba de sistema predeterminada.

La descripción de POSIX.1-2008 de las pruebas de sistema predeterminadas y la interacción entre las opciones -d, -M y -m no indicaron claramente que había dos tipos de "pruebas de sistema predeterminadas". Las "pruebas sensibles a la posición" determinan los tipos de archivos buscando ciertos valores de cadena o binarios en ubicaciones específicas en el archivo que se está examinando. Estas pruebas sensibles a la posición se implementaron en sistemas históricos utilizando el archivo mágico descrito anteriormente. Algunas de estas pruebas ahora están integradas en el programa utilitario file en algunas implementaciones para que la salida pueda proporcionar más detalles de los que se pueden proporcionar con archivos mágicos. Por ejemplo, un archivo mágico puede identificar fácilmente un archivo core en la mayoría de las implementaciones, pero no puede nombrar el archivo del programa que generó el core. Un archivo mágico podría producir una salida como:

/home/dwc/core: ELF 32-bit MSB core file SPARC Version 1

pero al integrar la prueba en el programa utilitario file, podría obtener una salida como:

/home/dwc/core: ELF 32-bit MSB core file SPARC Version 1, from 'testprog'

Estas pruebas extendidas integradas aún deben tratarse como pruebas de sistema predeterminadas sensibles a la posición, incluso si no están listadas en /etc/magic o en cualquier otro archivo mágico.

Las pruebas de sistema predeterminadas sensibles al contexto siempre estuvieron integradas en el programa utilitario file. Estas pruebas buscaban construcciones de lenguaje en archivos de texto intentando identificar scripts de shell, C, FORTRAN y otros archivos fuente de lenguajes de computadora, e incluso archivos de texto plano. Con la adición de las opciones -m y -M, la distinción entre pruebas de sistema predeterminadas sensibles a la posición y sensibles al contexto se volvió importante porque el orden de las pruebas es importante. Las pruebas de sistema predeterminadas sensibles al contexto nunca deben aplicarse antes que cualquier prueba sensible a la posición, incluso si la opción -d se especifica antes de una opción -m o -M, debido a la alta probabilidad de que las pruebas de sistema predeterminadas sensibles al contexto identifiquen incorrectamente archivos de texto arbitrarios como archivos de texto antes de que se apliquen las pruebas sensibles a la posición especificadas por la opción -m o -M para dar una identificación más precisa.

Dejar el significado de -M - y -m - sin especificar permite que un prototipo existente de estas opciones continúe funcionando de manera retrocompatible. (En esa implementación, -M - era aproximadamente equivalente a -d en POSIX.1-2008.)

Se omitió la opción histórica -c por no ser particularmente útil para los usuarios o scripts de shell portables. Además, una implementación razonable del programa utilitario file informaría cualquier error encontrado cada vez que se lea el archivo mágico.

El formato histórico del archivo mágico era el mismo que el especificado por el Raciocinio en el estándar ISO POSIX-2:1993 para los campos offset, value y message; sin embargo, utilizaba campos de tipo menos precisos que el formato especificado por el texto normativo actual. Los nuevos valores del campo de tipo son un superconjunto de los históricos.

El siguiente es un ejemplo de archivo mágico:

0  short     070707              cpio archive
0  short     0143561             Byte-swapped cpio archive
0  string    070707              ASCII cpio archive
0  long      0177555             Very old archive
0  short     0177545             Old archive
0  short     017437              Old packed data
0  string    \037\036            Packed data
0  string    \377\037            Compacted data
0  string    \037\235            Compressed data
>2 byte&0x80 >0                  Block compressed
>2 byte&0x1f x                   %d bits
0  string    \032\001            Compiled Terminfo Entry
0  short     0433                Curses screen image
0  short     0434                Curses screen image

El uso de un tipo de dato entero básico está destinado a permitir que la implementación elija un tamaño de palabra comúnmente utilizado por las aplicaciones en esa arquitectura.

Versiones anteriores de este estándar permitían implementaciones con bytes distintos de ocho bits, pero esto se ha modificado en esta versión.
