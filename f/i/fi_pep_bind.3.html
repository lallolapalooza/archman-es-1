DESCRIPCIÓN

Los puntos de extremo son portales de comunicación de nivel de transporte. Hay dos tipos de puntos de extremo: activos y pasivos. Los puntos de extremo pasivos pertenecen a un dominio de fabric y se usan con mayor frecuencia para escuchar solicitudes de conexión entrantes. Sin embargo, un punto de extremo pasivo puede usarse para reservar una dirección de fabric que pueda concederse a un punto de extremo activo. Los puntos de extremo activos pertenecen a dominios de acceso y pueden realizar transferencias de datos.

Los puntos de extremo activos pueden ser orientados a conexión o sin conexión, y pueden proporcionar fiabilidad de datos. Las interfaces de transferencia de datos — mensajes (fi_msg), mensajes etiquetados (fi_tagged), RMA (fi_rma) y operaciones atómicas (fi_atomic) — están asociadas con puntos de extremo activos. En configuraciones básicas, un punto de extremo activo tiene colas de transmisión y recepción. En general, las operaciones que generan tráfico en el fabric se publican en la cola de transmisión. Esto incluye todas las operaciones RMA y atómicas, junto con los mensajes enviados y los mensajes etiquetados enviados. Las operaciones que publican búferes para recibir datos entrantes se envían a la cola de recepción.

Los puntos de extremo activos se crean en estado deshabilitado. Deben transicionar a un estado habilitado antes de aceptar operaciones de transferencia de datos, incluida la publicación de búferes de recepción. La llamada fi_enable se usa para transicionar un punto de extremo activo a un estado habilitado. Las llamadas fi_connect y fi_accept también transicionarán un punto de extremo al estado habilitado, si aún no está activo.

Para transicionar un punto de extremo a un estado habilitado, debe estar enlazado con uno o más recursos de fabric. Un punto de extremo que genere finalizaciones asíncronas, ya sea a través de operaciones de transferencia de datos o eventos de establecimiento de comunicación, debe estar enlazado con las colas de finalización o colas de eventos apropiadas, respectivamente, antes de ser habilitado. Además, los puntos de extremo que usan progreso manual deben estar asociados con colas de finalización o eventos relevantes para impulsar el progreso. Para los puntos de extremo que se usan solo como destino de operaciones RMA o atómicas, esto significa enlazar el punto de extremo con una cola de finalización asociada con el procesamiento de recepción. Los puntos de extremo sin conexión deben estar enlazados con un vector de direcciones.

Una vez que un punto de extremo ha sido activado, puede asociarse con un vector de direcciones. Se le pueden publicar búferes de recepción y se pueden realizar llamadas a rutinas de establecimiento de conexión. Los puntos de extremo sin conexión también pueden realizar transferencias de datos.

El comportamiento de un punto de extremo puede ajustarse estableciendo sus datos de control y opciones de protocolo. Esto permite que el proveedor subyacente redirija las llamadas de función a implementaciones optimizadas para cumplir con el comportamiento deseado de la aplicación.

Si un punto de extremo experimenta un error crítico, transicionará de vuelta a un estado deshabilitado. Los errores críticos se reportan a través de la cola de eventos asociada con el EP. En ciertos casos, un punto de extremo deshabilitado puede volver a habilitarse. La capacidad de transicionar de vuelta a un estado habilitado es específica del proveedor y depende del tipo de error que experimentó el punto de extremo.n un punto final se desactiva como resultado de un error crítico, todas las operaciones pendientes se

descartan.

fi_ep_bind se utiliza para asociar un punto final con otros recursos asignados, como colas de finalización, contadores, vectores de dirección, colas de eventos, contextos compartidos y regiones de memoria. El tipo de objetos que deben vincularse con un punto final depende del tipo de punto final y su

configuración.

Los puntos finales pasivos deben vincularse con una cola de eventos (EQ) que admita eventos de gestión de conexión. Los puntos finales sin conexión deben vincularse a un único vector de dirección. Si un punto final está utilizando un contexto de transmisión y/o recepción compartido, los contextos compartidos deben vincularse al punto final. Las colas de finalización (CQ), los contadores, el vector de dirección (AV) y los contextos compartidos deben vincularse a los puntos finales antes de que se habiliten, ya sea de forma explícita o

implícita.

Un punto final debe estar vinculado con CQs capaces de informar de las finalizaciones de cualquier operación asíncrona iniciada en el punto final. Por ejemplo, si el punto final admite cualquier transferencia de salida (envíos, RMA, operaciones atómicas, etc.), entonces debe estar vinculado a una cola de finalización que pueda informar de las finalizaciones de transmisión. Esto es cierto incluso si el punto final está configurado para suprimir las finalizaciones exitosas, de modo que las operaciones que se completan con error puedan informarse al

usuario.

fi_cancel intenta cancelar una operación asíncrona pendiente. Cancelar una operación hace que el proveedor de tejido busque la operación y, si aún está pendiente, la complete como cancelada. Habrá una entrada de cola de errores disponible en la cola de errores asociada con el código de error FI_ECANCELED. Por otro lado, si la operación se completó antes de la llamada a fi_cancel, el estado de finalización de esa operación estará disponible en la cola de finalización asociada. No se publicará ninguna entrada específica relacionada con fi_cancel en sí

misma.

fi_ep_alias

Esta llamada crea un alias para el punto de conexión especificado. Conceptualmente, un alias de punto de conexión proporciona una ruta de software alternativa desde la aplicación hasta el hardware del proveedor subyacente. Un punto de conexión alias difiere de su punto de conexión principal solo por sus indicadores de transferencia de datos predeterminados. Por ejemplo, un punto de conexión alias puede configurarse para usar un modo de finalización diferente. De forma predeterminada, un punto de conexión alias hereda los mismos indicadores de transferencia de datos que el punto de conexión principal. Una aplicación puede usar fi_control para modificar los indicadores operativos del punto de conexión

alias.

Al asignar un alias, una aplicación puede configurar los indicadores operativos de transmisión o de recepción. Esto evita la necesidad de una llamada separada a fi_control para establecer esos in

dicadores. Los indicadores pasados a fi_ep_alias deben incluir FI_TRANSMIT o FI_RECV (no ambos) con otros indicadores operativos OR’eados. Esto anulará los indicadores de transmisión o de recepc
ión, respectivamente, para las operaciones publicadas a través del punto de conexión alias. Todos los alias asignados deben cerrarse para que el punto de conexión subyacente pueda ser liberado.

Tamaño de Ordenación RMA Máximo

El tamaño de ordenación máximo especifica el orden de entrega de los datos de transporte en la memoria de destino para las operaciones RMA y atómicas. El ordenación de datos es independiente, pero depende del ordenación de mensajes (definido a continuación). El ordenación de datos no está especificada donde el orden de los mensajes no está definido.

El ordenación de datos se refiere al acceso a la misma memoria de destino por operaciones posteriores. Cuando operaciones RMA de lectura o escritura consecutivas acceden a la misma ubicación de memoria registrada, el ordenación de datos indica si la segunda operación lee o escribe en la memoria de destino después de que la primera operación haya completado. Por ejemplo, ¿una lectura RMA que sigue a una escritura RMA leerá los datos que se escribieron? De manera similar, ¿una escritura RMA que sigue a una lectura RMA actualizará el búfer de destino después de que la lectura haya transferido los datos originales? El ordenación de datos responde a estas preguntas, incluso en presencia de errores, como la necesidad de reenviar datos debido a tráfico de red perdido o corrupto.

El ordenación RMA se aplica entre dos operaciones, y no dentro de una sola transferencia de datos. Por lo tanto, el ordenación se define por ubicación de memoria direccionable por byte. Es decir, el ordenación especifica si la ubicación X es accedida por la segunda operación después de la primera operación. No se implica nada sobre la finalización de la primera operación antes de que se inicie la segunda operación. Por ejemplo, si la primera operación actualiza las ubicaciones X e Y, pero la segunda operación solo accede a la ubicación X, no hay garantías definidas en relación con la ubicación Y y la segunda operación.

Para soportar transferencias de datos grandes que se dividen en múltiples paquetes y se envían usando múltiples rutas a través de la fabric, el ordenación de datos puede estar limitado a transferencias de un tamaño específico o menor. Los proveedores especifican cuándo se mantiene el ordenación de datos a través de los siguientes valores. Tenga en cuenta que incluso si el ordenación de datos no se mantiene, el ordenación de mensajes puede serlo.

max_order_raw_size
Tamaño de lectura después de escritura. Si se establece, una operación de lectura RMA o atómica emitida después de una operación de escritura RMA o atómica, ambas menores que el tamaño, serán ordenadas. Donde las ubicaciones de memoria de destino se superponen, la operación de lectura RMA o atómica verá los resultados de la escritura RMA o atómica anterior.

mem_tag_format - Formato de Etiqueta de Memoria

El campo de formato de etiqueta de memoria se utiliza para transmitir información sobre el uso de los parámetros de etiqueta e ignorar en las llamadas a la API fi_tagged, así como los criterios de coincidencia. Esta información es utilizada por el proveedor para optimizar el soporte de coincidencia de etiquetas, incluyendo la alineación con los protocolos de red. Se definen los siguientes formatos de etiqueta:

FI_TAG_BITS
Si se especifica en la entrada de fi_getinfo, esto indica que las etiquetas contienen hasta 64 bits de datos, y el receptor debe aplicar ignore_bits a las etiquetas al hacer coincidir búferes de recepción con envíos. La salida de fi_getinfo establecerá 0 o más bits superiores de mem_tag_format a 0 para indicar aquellos bits de etiqueta que son ignorados o reservados por el proveedor. Las aplicaciones deben verificar el número de bits superiores que son 0 y establecerlos a 0 en todos los bits de etiqueta e ignorar.

El valor de FI_TAG_BITS es 0, haciendo que este sea el comportamiento por defecto si las sugerencias se dejan sin inicializar después de ser asignadas por fi_allocinfo(). Este formato proporciona la mayor flexibilidad a las aplicaciones, pero limita las opciones de optimización del proveedor. FI_TAG_BITS se alinea con el comportamiento definido para las versiones 1.x de libfabric.

FI_TAG_MPI
FI_TAG_MPI es un uso restringido de FI_TAG_BITS. Cuando se selecciona, las aplicaciones tratan la etiqueta como campos de datos, en lugar de bits, con la capacidad de comodín para cada campo. El formato de etiqueta MPI se dirige específicamente a implementaciones y aplicaciones basadas en MPI. Una etiqueta con formato MPI consiste en 2 campos: una etiqueta de mensaje y un identificador de carga útil. La etiqueta de mensaje es una etiqueta de 32 bits buscable. La coincidencia en una etiqueta de mensaje requiere buscar en una lista de búferes publicados en el receptor, a lo que nos referimos como una etiqueta buscable. La etiqueta entera en los mensajes punto a punto de MPI puede mapearse directamente al campo de etiqueta de mensaje de libfabric.

El segundo campo es un identificador que corresponde a la operación o datos que se transportan en la carga útil del mensaje. Por ejemplo, este campo puede usarse para identificar el tipo de operación colectiva asociada con una carga útil de mensaje. Tenga en cuenta que solo se definen el tamaño y el comportamiento para los formatos de etiqueta MPI. El uso descrito de los campos son solo sugerencias.

Las aplicaciones que usan el formato MPI deben inicializar sus etiquetas usando la función fi_tag_mpi(). Los bits de ignorar deben especificarse como FI_MPI_IGNORE_TAG, FI_MPI_IGNORE_PAYLOAD, o su OR bit a bit.

FI_TAG_CCL
El formato FI_TAG_CCL restringe aún más el formato FI_TAG_MPI. Cuando se usa, solo se puede establecer un campo de etiqueta, que debe coincidir exactamente en el destino. El campo no puede ser comodín. El formato de etiqueta CCL se dirige a bibliotecas y aplicaciones de comunicación colectiva. El formato CCL consiste en un solo campo: un identificador de carga útil. El identificador corresponde a la operación o datos que se transportan en la carga útil del mensaje. Por ejemplo, este campo puede usarse para identificar si un mensaje es para comunicación punto a punto o parte de una operación colectiva, y en este último caso, el tipo de operación colectiva.

El formato de etiqueta CCL no requiere buscar búferes de recepción coincidentes, solo dirigir el mensaje a la cola de mensajes virtual correcta basándose en el identificador de carga útil.

Las aplicaciones que usan el formato CCL pasan el identificador de carga útil directamente como la etiqueta y establecen los bits de ignorar a 0.

FI_TAG_MAX_FORMAT
Si el valor de mem_tag_format es >= FI_TAG_MAX_FORMAT, el formato de etiqueta se trata como un conjunto de campos de bits. El comportamiento es funcionalmente el mismo que FI_TAG_BITS. La siguiente descripción es para compatibilidad con versiones anteriores y describe cómo el proveedor puede interpretar el campo mem_tag_format si el valor es >= FI_TAG_MAX_FORMAT.

El formato de etiqueta de memoria puede usarse para dividir la matriz de bits en campos separados. El mem_tag_format opcionalmente comienza con una serie de bits establecidos en 0, para significar bits que son ignorados por el proveedor. Después del prefijo inicial de bits ignorados, la matriz consistirá en grupos alternos de bits establecidos en todos 1 o todos 0. Cada grupo de bits corresponde a un campo etiquetado. La implicación de definir un campo etiquetado es que cuando se aplica una máscara a la matriz de bits etiquetada, todos los bits que pertenecen a un solo campo se establecerán colectivamente en 1 o 0.

Por ejemplo, un mem_tag_format de 0x30FF indica soporte para 14 bits etiquetados, separados en 3 campos. El primer campo consiste en 2 bits, el segundo campo 4 bits, y el campo final 8 bits. Máscaras válidas para tal campo etiquetado serían un OR bit a bit de cero o más de los siguientes valores: 0x3000, 0x0F00, y 0x00FF. El proveedor puede no validar la máscara proporcionada por la aplicación por razones de rendimiento.

Al identificar campos dentro de una etiqueta, un proveedor puede ser capaz de optimizar sus rutinas de búsqueda. Una aplicación que solicita campos de etiqueta debe proporcionar máscaras de etiqueta que establezcan todos los bits de máscara correspondientes a un campo en todos 0 o todos 1. Al negociar campos de etiqueta, una aplicación puede solicitar un número específico de campos de un tamaño dado. Un proveedor debe devolver un formato de etiqueta que soporte el número solicitado de campos, con cada campo siendo al menos del tamaño solicitado, o fallar la solicitud. Un proveedor puede aumentar el tamaño de los campos. Al reportar finalizaciones (ver FI_CQ_FORMAT_TAGGED), no se garantiza que el proveedor limpiará cualquier bit de etiqueta no soportado en el campo de etiqueta de la entrada de finalización.

Se recomienda que los tamaños de campo se ordenen de menor a mayor. Una etiqueta genérica y no estructurada y una máscara se pueden lograr solicitando una matriz de bits que consista en 1 y 0 alternos.

ENDPOINTS

Un punto final (endpoint) es una comunicación portal que permite a las aplicaciones enviar y recibir datos. Los puntos finales son creados a partir de un dominio de comunicación, y se asocian con una dirección de transporte y recursos de hardware y software subyacentes.

Los puntos finales son creados con un identificador de tipo que describe el comportamiento del punto final y sus capacidades. Los tipos de punto final definidos son:

FI_EP_MSG
Un punto final de mensajes. Los puntos finales de mensajes pueden ser utilizados para comunicación orientada a conexión (fi_connect, fi_accept, fi_listen) y sin conexión (fi_sendmsg, fi_recvmsg).
FI_EP_RDM
Un punto final de datagramas confiables (RDM). Los puntos finales RDM proporcionan una comunicación sin conexión con garantías de entrega y ordenación. Los puntos finales RDM no son compatibles con la comunicación orientada a conexión.
FI_EP_DGRAM
Un punto final de datagramas. Los puntos finales de datagramas son utilizados para comunicación sin conexión. No hay garantías de entrega o ordenación.
FI_EP_STREAM
Un punto final de flujo. Los puntos finales de flujo son utilizados para comunicación orientada a conexión y proporcionan garantías de entrega y ordenación. Los puntos finales de flujo no son compatibles con la comunicación sin conexión.
FI_EP_SOCK_STREAM
Un punto final de flujo de socket. Este tipo de punto final se comporta de forma similar a un socket de flujo UNIX, pero aprovecha las características de hardware de alto rendimiento. Vea la sección de Puntos Finales de Socket para más detalles.
FI_EP_SOCK_DGRAM
Un punto final de datagramas de socket. Este tipo de punto final se comporta de forma similar a un socket de datagramas UNIX, pero aprovecha las características de hardware de alto rendimiento. Vea la sección de Puntos Finales de Socket para más detalles.

Un punto final se asocia con un conjunto de atributos que describen sus capacidades y comportamiento. Los atributos clave incluyen:

tx_size

Este atributo se utiliza para guiar la asignación del tamaño de la cola de transmisión de un punto final. El mapeo del valor de tamaño a los recursos es específico del proveedor, pero está directamente relacionado con el número de entradas de comandos asignadas para el punto final. Un valor de tamaño más pequeño consume menos recursos de hardware y software, mientras que un valor más grande permite poner en cola más solicitudes de transmisión.

rx_size

Este atributo se utiliza para guiar la asignación del tamaño del contexto de recepción del punto final. El mapeo del valor de tamaño a los recursos es específico del proveedor, pero está directamente relacionado con el número de entradas de comandos asignadas para el punto final. Un valor de tamaño más pequeño consume menos recursos de hardware y software, mientras que un valor más grande permite poner en cola más solicitudes de transmisión.

Si bien el atributo de tamaño guía el tamaño de la cola de recepción subyacente del punto final, no existe necesariamente una correspondencia uno a uno entre una operación de recepción y una entrada de cola. Una sola operación de recepción puede consumir múltiples entradas de cola; por ejemplo, una por entrada de scatter-gather. Además, el campo de tamaño está destinado a guiar la asignación del contexto de recepción del punto final. Específicamente, para puntos finales sin conexión, puede haber colas de nivel inferior utilizadas para rastrear la comunicación por par. Los tamaños de cualquier cola de nivel inferior pueden ser solo significativamente más pequeños que el tamaño de recepción del punto final, para reducir la utilización de recursos.

iov_limit

Este es el número máximo de vectores de E/S (elementos scatter-gather) que una sola operación publicada puede referenciar.

ENDPOINTS ESCALABLES

Un punto final escalable es un portal de comunicación que admite múltiples contextos de transmisión y recepción. Los puntos finales escalables se modelan de forma general a partir del concepto de escalado de lado de transmisión/recepción en redes, también conocido como multi-cola. El soporte para puntos finales escalables es específico del dominio. Los puntos finales escalables pueden mejorar el rendimiento de aplicaciones multihilo y paralelas, al permitir que los hilos accedan a colas de transmisión y recepción independientes. Un punto final escalable tiene una única dirección de nivel de transporte, lo que puede reducir los requisitos de memoria necesarios para almacenar datos de direccionamiento remoto, en comparación con el uso de puntos finales estándar. Los puntos finales escalables no se pueden usar directamente para operaciones de comunicación y requieren que la aplicación cree explícitamente contextos de transmisión y recepción, como se describe a continuación.

fi_tx_context

Los contextos de transmisión son colas de transmisión independientes. El orden y la sincronización entre contextos no están definidos. Conceptualmente, un contexto de transmisión se comporta de manera similar a un punto final de solo envío. Un contexto de transmisión puede configurarse con menos capacidades que el punto final base y con atributos diferentes (como requisitos de ordenación y tamaño de inyección) que otros contextos asociados con el mismo punto final escalable. Cada contexto de transmisión tiene su propia cola de finalización. El número de contextos de transmisión asociados con un punto final se especifica durante la creación del punto final.

La llamada fi_tx_context se utiliza para recuperar un contexto específico, identificado por un índice (ver arriba para detalles sobre los atributos del contexto de transmisión). Los proveedores pueden asignar dinámicamente contextos cuando se llama a fi_tx_context, o pueden crear estáticamente todos los contextos cuando se invoca fi_endpoint. Por defecto, un contexto de transmisión hereda las propiedades de su punto final asociado. Sin embargo, las aplicaciones pueden solicitar atributos específicos del contexto a través del parámetro attr. El soporte para atributos por contexto de transmisión es específico del proveedor y no está garantizado. Los proveedores devolverán los atributos reales asignados al contexto a través del parámetro attr, si se proporciona.

fi_rx_context

Los contextos de recepción son colas de recepción independientes para recibir datos entrantes. El orden y la sincronización entre contextos no están garantizados. Conceptualmente, un contexto de recepción se comporta de manera similar a un punto final de solo recepción. Un contexto de recepción puede configurarse con menos capacidades que el punto final base y con atributos diferentes (como requisitos de ordenación y tamaño de inyección) que otros contextos asociados con el mismo punto final escalable. Cada contexto de recepción tiene su propia cola de finalización. El número de contextos de recepción asociados con un punto final se especifica durante la creación del punto final.

Los contextos de recepción a menudo se asocian con el reenvío de flujos, que especifican qué paquetes entrantes dirigidos a un punto final escalable procesar. Sin embargo, los contextos de recepción pueden ser dirigidos directamente por el iniciador, si es compatible con el protocolo subyacente. Dichos contextos se denominan 'nombrados'. El soporte para contextos nombrados debe indicarse estableciendo la capacidad FI_NAMED_RX_CTX al crear el punto final correspondiente. El soporte para contextos de recepción nombrados se coordina con los vectores de dirección. Consulte fi_av(3) y fi_rx_addr(3).

La llamada fi_rx_context se utiliza para recuperar un contexto específico, identificado por un índice (ver arriba para detalles sobre los atributos del contexto de recepción). Los proveedores pueden asignar dinámicamente contextos cuando se llama a fi_rx_context, o pueden crear estáticamente todos los contextos cuando se invoca fi_endpoint. Por defecto, un contexto de recepción hereda las propiedades de su punto final asociado. Sin embargo, las aplicaciones pueden solicitar atributos específicos del contexto a través del parámetro attr. El soporte para atributos por contexto de recepción es específico del proveedor y no está garantizado. Los proveedores devolverán los atributos reales asignados al contexto a través del parámetro attr, si se proporciona.

CONTEXTOS COMPARTIDOS

Los contextos compartidos son contextos de transmisión y recepción explícitamente compartidos entre uno o más puntos finales. Un contexto compartible permite a una aplicación utilizar un único recurso de proveedor dedicado entre múltiples puntos finales direccionables por transporte. Esto puede reducir en gran medida los recursos necesarios para gestionar la comunicación en múltiples puntos finales multiplexando el procesamiento de transmisión y/o recepción, con el costo potencial de serializar el acceso entre múltiples puntos finales. El soporte para contextos compartibles es específico del dominio.

Conceptualmente, los contextos de transmisión compartibles son colas de transmisión a las que pueden acceder muchos puntos finales. El uso de un contexto de transmisión compartido es en su mayoría opaco para una aplicación. Las aplicaciones deben asignar y vincular contextos de transmisión compartidos a puntos finales, pero las operaciones se publican directamente en el punto final. Los contextos de transmisión compartidos no están asociados con colas de finalización ni contadores. Las operaciones completadas se publican en las CQs vinculadas al punto final. Un punto final solo puede estar asociado con un único contexto de transmisión compartido.

A diferencia de los contextos de transmisión compartidos, las aplicaciones interactúan directamente con los contextos de recepción compartidos. Los usuarios publican búferes de recepción directamente en un contexto de recepción compartido, y los búferes son utilizables por cualquier punto final vinculado al contexto de recepción compartido. Los contextos de recepción compartidos no están asociados con colas de finalización ni contadores. Las operaciones de recepción completadas se publican en las CQs vinculadas al punto final. Un punto final solo puede estar asociado con un único contexto de recepción, y todos los puntos finales sin conexión asociados con un contexto de recepción compartido también deben compartir el mismo vector de dirección.

Los puntos finales asociados con un contexto de transmisión compartido pueden usar contextos de recepción dedicados, y viceversa. O un punto final puede usar contextos de transmisión y recepción compartidos. Y no hay requisito de que el mismo grupo de puntos finales que comparten un contexto de un tipo también compartan el contexto de un tipo alternativo. Además, un punto final puede usar un contexto compartido de un tipo, pero un conjunto escalable de contextos del tipo alternativo.

fi_stx_context

Esta llamada se utiliza para abrir un contexto de transmisión compartible (ver arriba para detalles sobre los atributos del contexto de transmisión). Los puntos finales asociados con un contexto de transmisión compartido deben usar un subconjunto de los atributos del contexto de transmisión. Tenga en cuenta que esto es lo inverso del requisito para los contextos de transmisión para puntos finales escalables.

fi_srx_context

Esto asigna un contexto de recepción compartible (ver arriba para detalles sobre los atributos del contexto de recepción). Los puntos finales asociados con un contexto de recepción compartido deben usar un subconjunto de los atributos del contexto de recepción. Tenga en cuenta que esto es lo inverso del requisito para los contextos de recepción para puntos finales escalables.

POINTS FINALES DE SOCKET

La siguiente característica y descripción deben considerarse experimentales. Hasta que se elimine la etiqueta experimental, las interfaces, la semántica y las estructuras de datos asociadas con los puntos finales de socket pueden cambiar entre versiones de la biblioteca.

Esta sección se aplica a puntos finales de tipo FI_EP_SOCK_STREAM y FI_EP_SOCK_DGRAM, comúnmente denominados puntos finales de socket.

Los puntos finales de socket se definen con una semántica que les permite ser adoptados más fácilmente por desarrolladores familiarizados con la API de sockets UNIX, o por middleware que expone la API de sockets, al tiempo que aprovechan las características de hardware de alto rendimiento.

La diferencia clave entre los puntos finales de socket y otros puntos finales activos es que los puntos finales de socket utilizan transferencias de datos síncronas. Los búferes pasados a las operaciones de envío y recepción vuelven al control de la aplicación al regresar de la llamada a la función. Como resultado, no se informan finalizaciones de transferencia de datos a la aplicación, y los puntos finales de socket no están asociados con colas de finalización ni contadores.

Los puntos finales de socket admiten un subconjunto de operaciones de mensajes: fi_send, fi_sendv, fi_sendmsg, fi_recv, fi_recvv, fi_recvmsg e fi_inject. Debido a que las transferencias de datos son síncronas, el valor de retorno de las operaciones de envío y recepción indica el número de bytes transferidos en caso de éxito, o un valor negativo en caso de error, incluido -FI_EAGAIN si el punto final no puede enviar o recibir ningún dato debido a colas llenas o vacías, respectivamente.

Los puntos finales de socket se asocian con colas de eventos y vectores de direcciones, y procesan eventos de gestión de conexiones de forma asíncrona, de manera similar a otros puntos finales. A diferencia de los sockets UNIX, los puntos finales de socket aún deben declararse como activos o pasivos.

Los puntos finales de socket se comportan como sockets no bloqueantes. Para admitir la semántica de select y poll, los puntos finales de socket activos se asocian con un descriptor de archivo que se señaliza siempre que el punto final está listo para enviar y/o recibir datos. El descriptor de archivo se puede recuperar usando fi_control.

OPERATION FLAGS

The following flags are used to control endpoint operations and completion behavior:

FI_ASYNC
Indicates that an operation should be performed asynchronously. This flag is always implied for operations that are not explicitly synchronous. Specifically, it is implied for all operations issued on an endpoint that has been bound to a completion queue. The result of an operation is not guaranteed to be persistent until a completion has been generated. A completion queue entry is generated for all asynchronous operations (i.e. operations that are not FI_SYNC). The completion entry should not be generated (locally or at the peer) until the result of an operation has been made persistent. See fi_cq(3) for additional details on completion semantics.
FI_COMPLETION
Indicates that a completion queue entry should be written for data transfer operations. This flag only applies to operations issued on an endpoint that was bound to a completion queue with the FI_SELECTIVE_COMPLETION flag set, otherwise, it is ignored. See the fi_ep_bind section above for more detail.
FI_DELIVERY_COMPLETE
Indicates that a completion should be generated when the operation has been processed by the destination endpoint(s). See fi_cq(3) for additional details on completion semantics.
FI_INJECT
Indicates that all outbound data buffers should be returned to the user’s control immediately after a data transfer call returns, even if the operation is handled asynchronously. This may require that the provider copy the data into a local buffer and transfer out of that buffer. A provider can limit the total amount of send data that may be buffered and/or the size of a single send that can use this flag. This limit is indicated using inject_size (see inject_size above).
FI_INJECT_COMPLETE
Indicates that a completion should be generated when the source buffer(s) may be reused. See fi_cq(3) for additional details on completion semantics.
FI_MULTICAST
Indicates that data transfers will target multicast addresses by default. Any fi_addr_t passed into a data transfer operation will be treated as a multicast address.
FI_MULTI_RECV
Applies to posted receive operations. This flag allows the user to post a single buffer that will receive multiple incoming messages. Received messages will be packed into the receive buffer until the buffer has been consumed. Use of this flag may cause a single posted receive operation to generate multiple completions as messages are placed into the buffer. The placement of received data into the buffer may be subjected to provider specific alignment restrictions. The buffer will be released by the provider when the available buffer space falls below the specified minimum (see FI_OPT_MIN_MULTI_RECV).
FI_TRANSMIT_COMPLETE
Indicates that a completion should be generated when the transmit operation has completed relative to the local provider. See fi_cq(3) for additional details on completion semantics.

NOTES

Users should call fi_close to release all resources allocated to the fabric endpoint.

Endpoints allocated with the FI_CONTEXT or FI_CONTEXT2 mode bits set must typically provide struct fi_context(2) as their per operation context parameter. (See fi_getinfo.3 for details.) However, when FI_SELECTIVE_COMPLETION is enabled to suppress CQ completion entries, and an operation is initiated without the FI_COMPLETION flag set, then the context parameter is ignored. An application does not need to pass in a valid struct fi_context(2) into such data transfers.

Operations that complete in error that are not associated with valid operational context will use the endpoint context in any error reporting structures.

Although applications typically associate individual completions with either completion queues or counters, an endpoint can be attached to both a counter and completion queue. When combined with using selective completions, this allows an application to use counters to track successful completions, with a CQ used to report errors. Operations that complete with an error increment the error counter and generate a CQ completion event.

As mentioned in fi_getinfo(3), the ep_attr structure can be used to query providers that support various endpoint attributes. fi_getinfo can return provider info structures that can support the minimal set of requirements (such that the application maintains correctness). However, it can also return provider info structures that exceed application requirements. As an example, consider an application requesting no msg_order. The resulting output from fi_getinfo may have all the ordering bits set. The application can reset the ordering bits it does not require before creating the endpoint. The provider is free to implement a stricter ordering than is required by the application.

RETURN VALUES

Returns 0 on success. On error, a negative value corresponding to fabric errno is returned. For fi_cancel, a return value of 0 indicates that the cancel request was submitted for processing, a return value of -FI_EAGAIN indicates that the request could not be submitted and that it should be retried once progress has been made. For fi_setopt/fi_getopt, a return value of -FI_ENOPROTOOPT indicates the provider does not support the requested option.

Fabric errno values are defined in rdma/fi_errno.h.
