DESCRIPCIÓ

N

Los vectores de direcciones se utilizan para mapear direcciones de nivel superior, que pueden ser más naturales para que una aplicación las use, en direcciones específicas del fabric. Por ejemplo, un punto final puede estar asociado con una dirección struct sockaddr_in, indicando que el punto final es alcanzable usando un número de puerto TCP sobre una dirección IPv4. Esto puede mantenerse incluso si el punto final se comunica usando un protocolo de red propietario. El propósito del AV es asociar una dirección de nivel superior con un valor más simple y eficiente que pueda ser usado por la API de libfabric de una manera agnóstica al fabric. La dirección mapeada es de tipo fi_addr_t y se devuelve a través de una llamada de inserción de

AV.

El proceso de mapeo de una dirección es específico del fabric y del proveedor, pero puede involucrar resoluciones de dirección extensas y protocolos de gestión de fabric. Las operaciones de AV son sincrónicas por defecto (la opción asincrónica ha quedado obsoleta, ver abajo). Ver la sección NOTAS para las restricciones de AV sobre direcciones

duplicadas.

Obsoleto: Las operaciones de AV pueden configurarse para operar de forma asincrónica especificando la bandera FI_EVENT a fi_av_open. Al solicitar operación asincrónica, la aplicación debe primero enlazar una cola de eventos al AV antes de insertar

direcciones.

Un tipo de AV corresponde a una implementación conceptual de un vector de direcciones. El tipo especifica cómo una aplicación ve los datos almacenados en el AV, incluyendo cómo pueden ser accedidos. Los valores válidos
son:
- FI_AV_MAP
(obsoleto)
Las direcciones que se insertan en un AV se mapean a una dirección nativa de fabric para su uso por la aplicación. El uso de FI_AV_MAP requiere que una aplicación almacene el valor fi_addr_t devuelto que está asociado con cada dirección insertada. La ventaja de usar FI_AV_MAP es que el valor fi_addr_t devuelto puede contener datos de dirección codificados, que están inmediatamente disponibles al procesar solicitudes de transferencia de datos. Esto puede eliminar o reducir el número de búsquedas de memoria necesarias al iniciar una transferencia. La desventaja de FI_AV_MAP es el aumento en el uso de memoria necesario para almacenar las direcciones devueltas. Las direcciones se almacenan en el AV usando un mecanismo específico del proveedor, incluyendo, pero no limitado a, un árbol, una tabla hash, o mantenidas en el heap. Esta opción está obsoleta, y se anima a los proveedores a alinear el comportamiento de FI_AV_MAP con
FI_AV_TABLE.
- FI_AV_TAB
LE
Las direcciones que se insertan en un AV de tipo FI_AV_TABLE son accesibles usando un índice simple. Conceptualmente, el AV puede ser tratado como un array de direcciones, aunque el proveedor puede implementar el AV usando una variedad de mecanismos. Cuando se usa FI_AV_TABLE, el fi_addr_t devuelto es un índice, con el índice para una dirección insertada siendo el mismo que su orden de inserción en la tabla. El índice de la primera dirección insertada en un FI_AV_TABLE será 0, y las inserciones sucesivas recibirán índices secuenciales. Los índices secuenciales se asignarán a través de llamadas de inserción en el mismo AV. La llamada fi_av_insert inserta cero o más direcciones en un AV. El número de direcciones se especifica a través del parámetro count. El parámetro addr referencia una matriz de direcciones a insertar en el AV. Las direcciones insertadas en un vector de direcciones deben estar en el mismo formato que el especificado en el campo addr_format de la estructura fi_info proporcionada al abrir el dominio correspondiente. Al usar el formato FI_ADDR_STR, el parámetro addr debe referencia una matriz de cadenas (char **)

.

Obsoleto: Para AVs de tipo FI_AV_MAP, una vez que las direcciones insertadas se han mapeado, los valores mapeados se escriben en el búfer referenciado por fi_addr. El búfer fi_addr debe permanecer válido hasta que la inserción del AV se haya completado y se haya generado un evento a una cola de eventos asociada. El valor del fi_addr devuelto debe considerarse opaco por la aplicación para AVs de tipo FI_AV_MAP. El valor devuelto puede apuntar a una estructura interna o a una codificación específica del proveedor de datos de direccionamiento de bajo nivel, por ejemplo. En este último caso, el uso de FI_AV_MAP puede evitar referencias a memoria durante las operaciones de transferencia de

datos.

Para AVs de tipo FI_AV_TABLE, las direcciones se colocan en la tabla en orden. Una dirección se inserta en el índice más bajo que corresponde a una ubicación de tabla no utilizada, con los índices comenzando en 0. Es decir, la primera dirección insertada puede referenciarse en el índice 0, la segunda en el índice 1, y así sucesivamente. Cuando se insertan direcciones en una tabla AV, los valores fi_addr asignados serán índices simples que corresponden a la entrada en la tabla donde se insertó la dirección. Los valores de índice se acumulan a lo largo de llamadas de inserción sucesivas en el orden en que se hacen las llamadas, no necesariamente en el orden en que se completan las

inserciones.

Debido a que las inserciones ocurren en un índice predeterminado, el parámetro fi_addr puede ser NULL. Si fi_addr no es NULL, debe referencia una matriz de fi_addr_t, y el búfer debe permanecer válido hasta que se complete la operación de inserción. Tenga en cuenta que si fi_addr es NULL y se solicita operación síncrona sin usar el indicador FI_SYNC_ERR, los fallos de inserción individuales no pueden informarse y la aplicación debe usar otras llamadas, como fi_av_lookup, para averiguar qué direcciones específicas fallaron al

insertarse.

Si el vector de direcciones está configurado con claves de autorización, el parámetro fi_addr puede usarse como entrada para definir las claves de autorización asociadas con las direcciones de endpoint que se están insertando. Esto se hace estableciendo el fi_addr a una clave de autorización fi_addr_t generada a partir de fi_av_insert_auth_key y estableciendo el indicador FI_AUTH_KEY. fi_av_insert

The fi_av_insert call inserts one or more addresses into an address vector (AV). The addresses are provided as an array of fi_addr_t values. The number of addresses to insert is specified by the count parameter.

FI_MORE
If set, indicates that additional insertion calls with FI_MORE will follow. This is a hint to the provider that the insertion list is not yet complete. Providers are free to ignore FI_MORE.
- FI_SYNC_ERR
This flag applies to synchronous insertions only and is used to retrieve error details of failed insertions. If set, the context parameter of insertion calls references an array of integers. The resulting status of attempting to insert each address will be written to the corresponding array location. Successful insertions will be updated to 0. Failures will contain a fabric errno code.
- FI_AV_USER_ID
For address vectors configured without FI_AV_USER_ID specified, this flag associates a user-assigned identifier with each AV entry that is returned with any completion entry in place of the AV’s address. If a provider does not support FI_AV_USER_ID with insert, requesting this flag during insert will result in a runtime failure.

Using the FI_AV_USER_ID flag per insert is invalid if the AV was opened with FI_AV_USER_ID or if the corresponding domain was configured with FI_AV_AUTH_KEY.

With libfabric 1.20, users are encouraged to specify the FI_AV_USER_ID when opening an AV and use fi_av_set_user_id. • .RS 2

FI_AUTH_KEY
Denotes that the address being inserted should be associated with the passed in authorization key fi_addr_t.

See the user ID section below.
• .RS 2

FI_FIREWALL_ADDR
This flag indicates that the address is behind a firewall and outgoing connections are not allowed. If there is not an existing connection and the provider is unable to circumvent the firewall, an FI_EFIREWALLADDR error should be expected. If multiple addresses are being inserted simultaneously, the flag applies to all of them. Additionally, it is possible that a connection is available at insertion time, but is later torn down. Future reconnects triggered by operations on the ep (fi_send, for example) may also fail with the same error.

fi_av_insertsvc

The fi_av_insertsvc call behaves similarly to fi_av_insert, but allows the application to specify the node and service names, similar to the fi_getinfo inputs, rather than an encoded address. The node and service parameters are defined the same as fi_getinfo(3). node should be a string that corresponds to a hostname or network address. The service string corresponds to a textual representation of a transport address. Applications may also pass in an FI_ADDR_STR formatted address as the node parameter. In such cases, the service parameter must be NULL. See fi_getinfo.3 for details on using FI_ADDR_STR. Supported flags are the same as for fi_av_insert.

fi_av_insertsym

fi_av_insertsym performs a symmetric insert that inserts a sequential range of nodes and/or service addresses into an AV. The svccnt parameter indicates the number of transport (endpoint) addresses to insert into the AV for each node address, with the service parameter specifying the starting transport address. Inserted transport addresses will be of the range {service, service + svccnt - 1}, inclusive. All service addresses for a node will be inserted before the next node is inserted.

The nodecnt parameter indicates the number of node (network) addresses to insert into the AV, with the node parameter specifying the starting node address. Inserted node addresses will be of the range {node, node + nodecnt - 1}, inclusive. If node is a non-numeric string, such as a hostname, it must contain a numeric suffix if nodecnt > 1.

As an example, if node = “10.1.1.1”, nodecnt = 2, service = “5000”, and svccnt = 2, the following addresses will be inserted into the AV in the order shown: 10.1.1.1:5000, 10.1.1.1:5001, 10.1.1.2:5000, 10.1.1.2:5001. If node were replaced by the hostname “host10”, the addresses would be: host10:5000, host10:5001, host11:5000, host11:5001.

The total number of inserted addresses will be nodecnt x svccnt.

Supported flags are the same as for fi_av_insert.

fi_av_remove

fi_av_remove removes a set of addresses from an address vector. The corresponding fi_addr_t values are invalidated and may not be used in data transfer calls. The behavior of operations in progress that reference the removed addresses is undefined.

Note that removing an address may not disable receiving data from the peer endpoint. fi_av_close will automatically cleanup any associated resource.

If the address being removed came from fi_av_insert_auth_key, the address will only be removed if all endpoints, which have been enabled against the corresponding authorization key, have been closed. If all endpoints are not closed, -FI_EBUSY will be returned. In addition, the FI_AUTH_KEY flag must be set when removing an authorization key fi_addr_t.

flags
The following flags may be used when removing an AV entry.
- FI_AUTH_KEY
Denotes that the fi_addr_t being removed is an authorization key fi_addr_t.

fi_av_lookup

This call returns the address stored in the address vector that corresponds to the given fi_addr. The returned address is the same format as those stored by the AV. On input, the addrlen parameter should indicate the size of the addr buffer. If the actual address is larger than what can fit into the buffer, it will be truncated. On output, addrlen is set to the size of the buffer needed to store the address, which may be larger than the input value.

fi_rx_addr

This function is used to convert an endpoint address, returned by fi_av_insert, into an address that specifies a target receive context. The value for rx_ctx_bits must match that specified in the AV attributes for the given address.

Connected endpoints that support multiple receive contexts, but are not associated with address vectors should specify FI_ADDR_NOTAVAIL for the fi_addr parameter.

fi_av_straddr

The fi_av_straddr function converts the provided address into a printable string. The specified address must be of the same format as those stored by the AV, though the address itself is not required to have been inserted. On input, the len parameter should specify the size of the buffer referenced by buf. On output, addrlen is set to the size of the buffer needed to store the address. This size may be larger than the input len. If the provided buffer is too small, the results will be truncated. fi_av_straddr returns a pointer to buf.

fi_av_insert_auth_key

This function associates authorization keys with an address vector. This requires the domain to be opened with FI_AV_AUTH_KEY. FI_AV_AUTH_KEY enables endpoints and memory regions to be associated with authorization keys from the address vector. This behavior enables a single endpoint or memory region to be associated with multiple authorization keys.

When endpoints or memory regions are enabled, they are configured with address vector authorization keys at that point in time. Later authorization key insertions will not propagate to already enabled endpoints and memory regions.

The auth_key and auth_key_size parameters are used to input the authorization key into the address vector. The structure of the authorization key is provider specific. If the auth_key_size does not align with the provider specific structure, -FI_EINVAL will be returned.

The output of fi_av_insert_auth_key is an authorization key fi_addr_t handle representing all endpoint addresses against this specific authorization key. For all operations, including address vector, memory registration, and data transfers, which may accept an authorization key fi_addr_t as input, the FI_AUTH_KEY flag must be specified. Otherwise, the fi_addr_t will be treated as an fi_addr_t returned from the fi_av_insert and related functions.

For endpoints enabled with FI_DIRECTED_RECV, authorization key fi_addr_t’s can be used to restrict incoming messages to only endpoint addresses within the authorization key. This will require passing in the FI_AUTH_KEY flag to fi_recvmsg and fi_trecvmsg.

For domains enabled with FI_DIRECTED_RECV, authorization key fi_addr_t’s can be used to restrict memory region access to only endpoint addresses within the authorization key. This will require passing in the FI_AUTH_KEY flag to fi_mr_regattr.

These authorization key fi_addr_t’s can later be used an input for endpoint address insertion functions to generate an fi_addr_t for a specific endpoint address and authorization key. This will require passing in the FI_AUTH_KEY flag to fi_av_insert and related functions.

For address vectors configured with FI_AV_USER_ID and endpoints with FI_SOURCE_ERR, all subsequent FI_EADDRNOTAVAIL error events will return FI_ADDR_NOTAVAIL until the user defines a user ID for this authorization key fi_addr_t. This is done by using fi_av_set_user_id.

For address vectors configured without FI_AV_USER_ID and endpoints with FI_SOURCE_ERR, all subsequent FI_EADDRNOTAVAIL error events will return the authorization key fi_addr_t handle.

Flags are reserved for future use and must be 0.

NOTA

S

Un AV solo debe almacenar una única instancia de una dirección. Intentar insertar una copia duplicada de la misma dirección en un AV puede resultar en un comportamiento indefinido, dependiendo de la implementación del proveedor. No s

e requiere que los proveedores comprueben duplicados, ya que hacerlo podría incurrir en una sobrecarga significativa en el proceso de inserción. Para la portabilidad, las aplicaciones pueden necesitar rastrear qué direcciones de par
es se han insertado en un AV determinado para evitar entradas duplicadas. Sin embargo, se requiere que los proveedores admitan la eliminación y la posterior reinserción de una dirección. Solo se restringen las inserciones duplicadas.

IDENTIFICADORES DE USUARIO PARA

DIRECCIONES

Como se describió anteriormente, las direcciones de punto final y las claves de autorización que se insertan en un AV se asignan a un valor fi_addr_t. El fi_addr_t de la dirección del punto final se utiliza en las API de transferencia de datos para especificar el destino de una transferencia saliente, en las API de recepción para indicar el origen de una transferencia entrante, y también en los eventos de finalización para informar de la dirección de origen de las transferencias entrantes. Los fi_addr_t de clave de autorización se utilizan en las API de recepción y MR para asignar operaciones entrantes a una clave de autorización específica, y también en los eventos de error de finalización si el punto final está configurado con FI_SOURCE_ERR. El bit de capacidad y el indicador FI_AV_USER_ID proporcionan un mecanismo por el cual el valor fi_addr_t informado por un evento de finalización (éxito o error) se reemplaza con un valor especificado por el usuario. Esto es útil para aplicaciones que necesitan mapear la dirección de origen a su propia estructura de

datos.

El soporte para FI_AV_USER_ID es específico del proveedor, ya que puede no ser factible para un proveedor implementar este soporte sin una sobrecarga significativa. Por ejemplo, algunos proveedores pueden necesitar añadir un mecanismo de búsqueda inversa. Esta función puede no estar disponible si se solicitan AV compartidos, o impactar negativamente la huella de memoria por proceso si se implementa. Para los proveedores que no admiten FI_AV_USER_ID, los usuarios pueden poder compensar el procesamiento de búsqueda con la sobrecarga del protocolo, incluyendo la identificación de origen en un encabezado de

mensaje.

Para los vectores de direcciones abiertos sin FI_AV_USER_ID, los valores fi_addr_t especificados por el usuario se proporcionan como parte de la inserción de direcciones (p. ej., fi_av_insert) a través del parámetro fi_addr. El parámetro fi_addr actúa como entrada/salida en este caso. Cuando se pasa el indicador FI_AV_USER_ID a cualquiera de las llamadas de inserción, el llamador debe especificar un valor identificador fi_addr_t para asociar con cada dirección. El proveedor registrará ese identificador y lo utilizará donde sea necesario como parte de cualquier evento de finalización. Tenga en cuenta que la salida de la llamada de inserción del AV no cambia. El proveedor devolverá un valor fi_addr_t que asigna a cada dirección, y ese valor debe utilizarse para todas las operaciones de transferencia de

datos.

Para los vectores de direcciones abiertos con FI

_AV_USER_ID, se utiliza fi_av_set_user_id para d
efinir el fi_addr_t especificado por el usuario.

GRUPOS DE

PARES

Los grupos de pares proporcionan una asignación directa a las construcciones de comunicador de HPC e

IA.

Las direcciones en un AV representan el conjunto completo de pares con los que un proceso local puede comunicarse. Un grupo de pares representa conceptualmente un subconjunto de esos pares. Un grupo de pares puede utilizarse para identificar pares que trabajan en una tarea común y cuya comunicación necesita estar lógicamente separada del resto del tráfico. Los grupos de pares no son un mecanismo de seguridad, sino que ayudan a separar los datos. Un par determinado puede pertenecer a 0 o más grupos de pares, sin límite en el número de pares que pueden pertenecer a un solo grupo de

pares.

Los grupos de pares se identifican mediante un valor entero, conocido como id de grupo. Los id de grupo los selecciona el usuario y se transmiten como parte de un valor fi_addr_t. La gestión de un id de grupo y su relación con las direcciones insertadas en un AV la controla directamente el usuario. Cuando está habilitado, los mensajes enviados se marcan como pertenecientes a un grupo de pares específico, y los búferes de recepción publicados deben tener un id de grupo coincidente para recibir los

datos.

Los usuarios son responsables de seleccionar un id de grupo de pares válido, sujeto a la limitación negociada usando el atributo de dominio max_group_id. El id de grupo de un fi_addr_t puede establecerse usando la función fi_group_addr()

VALORES DE

RETORNO

Las llamadas de inserción, excluyendo fi_av_insert_auth_key, para un AV abierto para operación síncrona devolverán el número de direcciones que se insertaron correctamente. En caso de fallo, el valor de retorno será menor que el número de direcciones

especificadas.

Obsoleto: Las llamadas de inserción, excluyendo fi_av_insert_auth_key, para un AV abierto para operación asíncrona (con el indicador FI_EVENT especificado) devolverán FI_SUCCESS si la operación se inició correctamente. En caso de fallo, se devolverá un código de error de fabrica negativo. Se permite a los proveedores abortar las operaciones de inserción en caso de error. Las direcciones que no se insertan porque fueron abortadas fallarán con un código de error

FI_ECANCELED.

En ambos modos de operación, síncrono y asíncrono, el búfer fi_addr asociado con una inserción fallida o abortada se establecerá en FI_ADDR_NOTAVAIL

.

Todas las demás llamadas devuelven FI_SUCCESS en caso de éxito, o un valo

r negativo correspondiente al código de error de fabrica en caso de error.
Los valores de código de error de fabrica se definen en rdma/fi_errno.h.
