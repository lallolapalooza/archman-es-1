DESCRIPCIÓ

N

Las colas de eventos se utilizan para reportar eventos asociados con operaciones de control. Están asociadas con el registro de memoria, vectores de dirección, gestión de conexiones y eventos a nivel de fabrica y dominio. Los eventos reportados están asociados con una operación solicitada o afiliados a una llamada que se registra para tipos específicos de eventos, como la escucha de solicitudes de

conexión.

Las colas de eventos (EQ) pueden estar asociadas con un objeto de espera específico. Los objetos de espera permiten a las aplicaciones bloquearse hasta que el objeto de espera sea señalado, indicando que hay un evento disponible para leer. Los usuarios pueden usar fi_control para recuperar el objeto de espera subyacente asociado con una EQ, para usarlo en otras llamadas al sistema. Los siguientes valores pueden usarse para especificar el tipo de objeto de espera asociado con una
EQ:
- FI_WAIT_NO
NE
Se usa para indicar que el usuario no se bloqueará (esperará) por eventos en la EQ. Cuando se especifica FI_WAIT_NONE, la aplicación no puede llamar a fi_eq_sread. Este es el valor predeterminado si no se especifica un objeto de
espera.
- FI_WAIT_UNSP
EC
Especifica que el usuario solo esperará en la EQ usando llamadas a la interfaz de fabrica, como fi_eq_sread. En este caso, el proveedor subyacente puede seleccionar el objeto de espera más apropiado o de mayor rendimiento disponible, incluyendo mecanismos de espera personalizados. No se garantiza que las aplicaciones que seleccionan FI_WAIT_UNSPEC puedan recuperar el objeto de espera
subyacente.
- FI_WAIT_SET (ob
soleto)
Indica que la cola de eventos debe usar un objeto de conjunto de espera para esperar eventos. Si se especifica, el campo wait_set debe referenciar un objeto de conjunto de espera
existente.
- FI_WAIT_
FD
Indica que la cola de eventos (EQ) debe usar un descriptor de archivo como su mecanismo de espera. Un objeto de espera de descriptor de archivo debe ser utilizable en rutinas select, poll y epoll. Sin embargo, un proveedor puede señalar un objeto de espera FD marcándolo como legible o con un
error.
- FI_WAIT_MUTEX_COND
(obsoleto)
Especifica que la cola de eventos (EQ) debe usar un mutex de pthread y una variable de condición como objeto de
espera.
- FI_WAIT_YIE
LD
Indica que la cola de eventos (EQ) esperará sin un objeto de espera, sino que cederá en cada espera. Permite el uso de fi_eq_sread a través de un bucle de espera activa

La llamada fi_close libera todos los recursos asociados con una cola de eventos. Cualquier evento que permanezca en la cola de eventos (EQ) cuando se cierre se

perderá.

La cola de eventos (EQ) no debe estar vinculad

a a ningún otro objeto antes de ser cerrada, d

fi_contro

l

La llamada fi_control se usa para acceder a detalles específicos del proveedor o de la implementación de la cola de eventos. El acceso a la cola de eventos (EQ) debe serializarse en todas las llamadas cuando se invokeado, ya que puede redirigir la implementación de las operaciones EQ. Los siguientes comandos de control son utilizables con un EQ.

FI_GETWAIT (void **)
Este comando permite al usuario recuperar el objeto de espera de bajo nivel asociado con el EQ. El formato del objeto de espera se especifica durante la creación del EQ, a través de los atributos del EQ. El parámetro arg de fi_control debe ser una dirección en la que se escribirá un puntero al objeto de espera devuelto. Esto debe ser un 'int *' para FI_WAIT_FD, o un 'struct fi_mutex_cond' para FI_WAIT_MUTEX_COND (obsoleto).
struct fi_mutex_cond {
    pthread_mutex_t     *mutex;
    pthread_cond_t      *cond;
};

fi_eq_read

La operación fi_eq_read realiza una lectura no bloqueante de datos de eventos desde el EQ. El formato de los datos del evento se basa en el tipo de evento recuperado del EQ, con todos los eventos comenzando con una cabecera struct fi_eq_entry. Se devolverá como máximo un evento por operación de lectura del EQ. El número de bytes leídos con éxito del EQ se devuelve desde la lectura. El flag FI_PEEK puede usarse para indicar que los datos del evento deben leerse del EQ sin ser consumidos. Una lectura posterior sin el flag FI_PEEK eliminaría entonces el evento del EQ.

Los siguientes tipos de eventos pueden ser reportados a un EQ, junto con información respecto al formato asociado con cada evento.

Operaciones de Control Asíncronas
Las operaciones de control asíncronas son peticiones básicas que simplemente necesitan generar un evento para indicar que se han completado. Estos incluyen los siguientes tipos de eventos: registro de memoria, resolución de vectores de dirección y uniones multicast.

Las peticiones de control reportan su completitud insertando un struct fi_eq_entry en el EQ. El formato de esta estructura es:

struct fi_eq_entry {
    fid_t            fid;        /* fid asociado con la petición */
    void            *context;    /* contexto de la operación */
    uint64_t         data;       /* datos específicos de la completitud */
};

Para la completitud de operaciones de control asíncronas básicas, el evento devuelto indicará la operación que se ha completado, y el fid hará referencia al descriptor de fabrica asociado con el evento. Para el registro de memoria, este será un evento FI_MR_COMPLETE y el fid_mr. La resolución de dirección hará referencia a un evento FI_AV_COMPLETE y fid_av. Las uniones multicast reportarán un FI_JOIN_COMPLETE y fid_mc. El campo context se establecerá al contexto especificado como parte de la operación, si está disponible, de lo contrario el contexto estará asociado con el descriptor de fabrica. El campo data se establecerá como se describe en la página del manual para el tipo de objeto correspondiente (por ejemplo, consulte fi_av(3) para una descripción de cómo se completan las inserciones asíncronas de vectores de dirección).

Notificación de Conexión
Las notificaciones de conexión son notificaciones de gestión de conexión utilizadas para establecer o desmantelar conexiones entre puntos finales. Hay tres eventos de notificación de conexión: FI_CONNREQ, FI_CONNECTED y FI_SHUTDOWN. Las notificaciones de conexión se reportan usando struct fi_eq_cm_entry:
struct fi_eq_cm_entry {
    fid_t            fid;        /* fid asociado con la petición */
    struct fi_info  *info;       /* información del punto final */
    uint8_t         data[];     /* datos de conexión de la aplicación */
};

Un evento de petición de conexión (FI_CONNREQ) indica que un punto final remoto desea establecer una nueva conexión a un punto final de escucha, o pasivo. El fid es el punto final pasivo. La información respecto a las capacidades y atributos del punto final activo solicitado está disponible desde el campo info. La aplicación es responsable de liberar esta estructura llamando a fi_freeinfo cuando ya no sea necesaria. El campo connreq de fi_info hará referencia a la petición de conexión asociada con este evento. Para aceptar una conexión, un punto final debe ser creado primero pasando una estructura fi_info que haga referencia a este campo connreq a fi_endpoint(). Este punto final es entonces pasado a fi_accept() para completar la aceptación del intento de conexión. Crear el punto final se logra más fácilmente pasando el fi_info devuelto como parte del evento CM a fi_endpoint(). Si la conexión va a ser rechazada, el connreq se pasa a fi_reject().

Cualquier dato de aplicación intercambiado como parte de la petición de conexión se coloca más allá de la estructura fi_eq_cm_entry. La cantidad de datos disponibles depende de la aplicación y está limitada al espacio de búfer proporcionado por la aplicación cuando se llama a fi_eq_read. La cantidad de datos devueltos puede ser calculada usando el valor de retorno de fi_eq_read. Note que la cantidad de datos devueltos está limitada por el protocolo de conexión subyacente, y la longitud de cualquier dato devuelto puede incluir relleno de protocolo. Como resultado, la longitud devuelta puede ser mayor que la especificada por el par emoto que conecta.

Si una petición de conexión ha sido aceptada, un evento FI_CONNECTED será generado en ambos lados de la conexión. El lado activo – el que llamó a fi_connect() – puede recibir datos de usuario como parte del evento FI_CONNECTED. Los datos de usuario son pasados al gestor de conexiones en el lado pasivo a través de la llamada fi_accept. No se proporcionan datos de usuario con un evento FI_CONNECTED en el lado de escucha de la conexión.

La notificación de que un par remoto se ha desconectado de un punto final activo se hace a través del evento FI_SHUTDOWN. La notificación de apagado usa struct fi_eq_cm_entry como se declaró arriba. El campo fid para una notificación de apagado se refiere al fid_ep del punto final activo.

Notificación de Error Asíncrono
Los errores asíncronos se usan para reportar problemas con recursos de fabrica. Los errores reportados pueden ser fatales o transitorios, basado en el error, y resultan en el recurso quedando deshabilitado. Los recursos deshabilitados fallarán operaciones enviadas contra ellos hasta que sean re-habilitados explícitamente por la aplicación.

Los errores asíncronos pueden ser reportados para colas de completitud y puntos finales de todos los tipos. Los errores de CQ pueden resultar cuando la gestión de recursos ha sido deshabilitada, y el proveedor ha detectado un desbordamiento de cola. Los errores de punto final pueden ser el resultado de numerosas acciones, pero a menudo están asociados con una operación fallida. Las operaciones pueden fallar debido a desbordamientos de búfer, permisos inválidos, claves de memoria incorrectas, fallos de enrutamiento de red, problemas de alcance de red, etc.

Los errores asíncronos se reportan usando struct fi_eq_err_entry, como se define abajo. El descriptor de fabrica (fid) asociado con el error se proporciona como parte de los datos del error. Un código de error también está disponible para determinar la causa del error.

fi_eq_sread

La llamada fi_eq_sread es el equivalente bloqueante (o síncrono) a fi_eq_read. Se comporta de manera similar a la llamada no bloqueante, con la excepción de que las llamadas no retornarán hasta que un evento haya sido leído del EQ o ocurra un error o timeout. Especificar un timeout negativo significa un timeout infinito.

Los hilos bloqueados en esta función retornarán al llamador si son señalados por alguna fuente externa. Esto es verdadero incluso si el timeout no ha ocurrido o fue especificado como infinito.

Es inválido para las aplicaciones llamar a esta función si el EQ ha sido configurado con un objeto de espera de FI_WAIT_NONE o FI_WAIT_SET.

fi_eq_readerr

La función de lectura de errores, fi_eq_readerr, recupera información respecto a cualquier operación asíncrona que haya completado con un error inesperado. fi_eq_readerr es una llamada no bloqueante, retornando inmediatamente ya sea si se encontró una completitud de error o no.

Los EQs están optimizados para reportar operaciones que han completado exitosamente. Las operaciones que fallan son reportadas 'fuera de banda'. Dichas operaciones son recuperadas usando la función fi_eq_readerr. Cuando una operación que completa con un error inesperado es insertada en un EQ, es colocada en una cola de errores temporal. Intentar leer de un EQ mientras un ítem está en la cola de errores resulta en un fallo FI_EAVAIL. Las aplicaciones pueden usar este código de retorno para determinar cuándo llamar a fi_eq_readerr.

La información del error es reportada al usuario a través de struct fi_eq_err_entry. El formato de esta estructura se define abajo.

struct fi_eq_err_entry {
    fid_t            fid;        /* fid asociado con el error */
    void            *context;    /* contexto de la operación */
    uint64_t         data;       /* datos específicos de la completitud */
    int              err;        /* código de error positivo */
    int              prov_errno; /* código de error del proveedor */
    void            *err_data;   /* datos adicionales del error */
    size_t           err_data_size; /* tamaño de err_data */
};

El fid hará referencia al descriptor de fabrica asociado con el evento. Para el registro de memoria, este será el fid_mr, la resolución de dirección hará referencia a un fid_av, y los eventos de CM se referirán a un fid_ep. El campo context se establecerá al contexto especificado como parte de la operación.

El campo data se establecerá como se describe en la página del manual para el tipo de objeto correspondiente (por ejemplo, consulte fi_av(3) para una descripción de cómo se completan las inserciones asíncronas de vectores de dirección).

La razón general del error se proporciona a través del campo err. La información de error específica del proveedor u operativa también puede estar disponible a través de los campos prov_errno y err_data. Los usuarios pueden llamar a fi_eq_strerror para convertir información de error específica del proveedor en una cadena imprimible para propósitos de depuración.

En la entrada, err_data_size indica el tamaño del búfer err_data en bytes. En la salida, err_data_size se establecerá al número de bytes copiados al búfer err_data. La información err_data se usa típicamente con fi_eq_strerror para proporcionar detalles sobre el tipo de error que ocurrió.

Para propósitos de compatibilidad, si err_data_size es 0 en la entrada, o la fabrica fue abierta con una versión < 1.5, err_data será establecido a un búfer de datos propiedad del proveedor. El contenido del búfer permanecerá válido hasta una llamada de lectura posterior contra el EQ. Las aplicaciones deben serializar el acceso al EQ al procesar errores para asegurar que el búfer referenciado por err_data no cambie.

CAMPOS DE EVENTOS

Las estructuras de datos de entrada del EQ comparten muchos de los mismos campos

EVENT FIELDS

Los significados son los mismos o similares para todos los formatos de estructura de EQ, con detalles específicos descritos a continuación.

fid
Esto corresponde al descriptor de tejido asociado con el evento. El tipo de fid depende del evento que se está informando. Para FI_CONNREQ, será el fid del punto final pasivo. FI_CONNECTED y FI_SHUTDOWN harán referencia al punto final activo. FI_MR_COMPLETE y FI_AV_COMPLETE harán referencia al descriptor de tejido MR o AV, respectivamente. FI_JOIN_COMPLETE apuntará al descriptor multicast devuelto como parte de la operación de unión. Las aplicaciones pueden usar el valor context de fid-> para recuperar el contexto asociado con el descriptor de tejido.
context
El valor de contexto se establece en el parámetro de contexto especificado con la operación que generó el evento. Si no hay ningún parámetro de contexto asociado con la operación, este campo será NULL.
data
Data es un valor o conjunto de bytes específico de la operación. Para eventos de conexión, data son datos de aplicación intercambiados como parte del protocolo de conexión.
err
Este código de error es un errno de tejido positivo asociado con un evento. El valor err indica la razón general de un error, si ocurrió alguno. Consulte fi_errno.3 para obtener una lista de posibles códigos de error.
prov_errno
En caso de error, prov_errno puede contener un código de error específico del proveedor. El uso de este campo y su significado son específicos del proveedor. Está destinado a ser utilizado como ayuda para la depuración. Consulte fi_eq_strerror para obtener detalles adicionales sobre la conversión de este valor de error en una cadena legible por humanos.
err_data
En caso de error, err_data puede hacer referencia a una cantidad de datos específica del proveedor asociada con un error. El uso de este campo y su significado son específicos del proveedor. Está destinado a ser utilizado como ayuda para la depuración. Consulte fi_eq_strerror para obtener detalles adicionales sobre la conversión de estos datos de error en una cadena legible por humanos.
err_data_size
En la entrada, err_data_size indica el tamaño del búfer err_data en bytes. En la salida, err_data_size se establecerá en el número de bytes copiados en el búfer err_data. La información de err_data se utiliza típicamente con fi_eq_strerror para proporcionar detalles sobre el tipo de error que ocurrió.

Por motivos de compatibilidad, si err_data_size es 0 en la entrada, o el tejido se abrió con una versión < 1.5, err_data se establecerá en un búfer de datos propiedad del proveedor. El contenido del búfer seguirá siendo válido hasta la siguiente llamada de lectura contra la EQ. Las aplicaciones deben serializar el acceso a la EQ al procesar errores para garantizar que el búfer al que hace referencia err_data no cambie.

NOTAS

Si una cola de eventos se ha desbordado, se pondrá en un estado de `desbordamiento'. Las operaciones de escritura contra una EQ desbordada fallarán con -FI_EOVERRUN. Las operaciones de lectura continuarán devolviendo cualquier evento válido y no corrupto, si está disponible. Después de que se hayan recuperado todos los eventos válidos, cualquier intento de leer la EQ dará como resultado la devolución de un evento de error FI_EOVERRUN. Las colas de eventos desbordadas se consideran fatales y no se pueden utilizar para informar eventos adicionales una vez que ocurre el desbordamiento.

VALORES DE RETORNO

fi_eq_open
Devuelve 0 en caso de éxito. En caso de error, se devuelve un valor negativo correspondiente al errno del tejido.
fi_eq_read / fi_eq_readerr
En caso de éxito, devuelve el número de bytes leídos de la cola de eventos. En caso de error, se devuelve un valor negativo correspondiente al errno del tejido. Si no hay datos disponibles para leer de la cola de eventos, se devuelve -FI_EAGAIN.
fi_eq_sread
En caso de éxito, devuelve el número de bytes leídos de la cola de eventos. En caso de error, se devuelve un valor negativo correspondiente al errno del tejido. Si el tiempo de espera expira o el hilo que llama es señalado y no hay datos disponibles para leer de la cola de eventos, se devuelve -FI_EAGAIN.
fi_eq_write
En caso de éxito, devuelve el número de bytes escritos en la cola de eventos. En caso de error, se devuelve un valor negativo correspondiente al errno del tejido.
fi_eq_strerror
Devuelve una interpretación en cadena de caracteres del error específico del proveedor devuelto con una finalización.

Los valores de errno del tejido se definen en rdma/fi_errno.h.
