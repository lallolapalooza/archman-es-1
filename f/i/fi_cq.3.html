DESCRIPCIÓ

N

Las colas de finalización se utilizan para informar de eventos asociados con las transferencias de datos. Están asociadas con envíos y recepciones de mensajes, RMA, operaciones atómicas, mensajes etiquetados y eventos activados. Los eventos informados suelen estar asociados con un punto final de la fabrica, pero también pueden referirse a regiones de memoria utilizadas como destino de una operación RMA o

atómica.

fi_cq_ope

n

fi_cq_open asigna una nueva cola de finalización. A diferencia de las colas de eventos, las colas de finalización están asociadas con un dominio de recursos y pueden descargarse por completo en el hardware del

proveedor.

Las propiedades y el comportamiento de una cola de finalización están definidos por struct

fi_cq_attr.

wait_o
bj
Las colas de finalización pueden estar asociadas con un objeto de espera específico. Los objetos de espera permiten a las aplicaciones bloquearse hasta que el objeto de espera sea señalizado, lo que indica que hay una finalización disponible para leer. Los usuarios pueden usar fi_control para recuperar el objeto de espera subyacente asociado con una cola de finalización, para usarlo en otras llamadas al sistema. Los siguientes valores pueden usarse para especificar el tipo de objeto de espera asociado con una CQ: FI_WAIT_NONE, FI_WAIT_UNSPEC, FI_WAIT_SET, FI_WAIT_FD, FI_WAIT_MUTEX_COND (obsoleto), y FI_WAIT_YIELD. El valor predeterminado es
FI_WAIT_NONE.
- FI_WAIT_NO
NE
Se utiliza para indicar que el usuario no se bloqueará (esperará) por finalizaciones en la CQ. Cuando se especifica FI_WAIT_NONE, la aplicación no puede llamar a fi_cq_sread ni a
fi_cq_sreadfrom.
- FI_WAIT_UNSP
EC
Especifica que el usuario solo esperará en la CQ mediante llamadas a la interfaz de fabricación, como fi_cq_sread o fi_cq_sreadfrom. En este caso, el proveedor subyacente puede seleccionar el objeto de espera más apropiado o de mayor rendimiento disponible, incluyendo mecanismos de espera personalizados. No se garantiza que las aplicaciones que seleccionan FI_WAIT_UNSPEC puedan recuperar el objeto de espera
subyacente.
- FI_WAIT_SET (ob
soleto)
Indica que la cola de finalización debe usar un objeto de conjunto de espera para esperar finalizaciones. Si se especifica, el campo wait_set debe hacer referencia a un objeto de conjunto de espera
existente.
- FI_WAIT_
FD
Indica que la CQ debe usar un descriptor de archivo como su mecanismo de espera. Un objeto de espera de descriptor de archivo debe ser utilizable en las rutinas select, poll y epoll. Sin embargo, un proveedor puede señalar un objeto de espera FD marcándolo como legible, escribible o con un
error.
- FI_WAIT_MUTEX_COND
(obsoleto)
Especifica que la CQ debe usar un mutex de pthread y una variable de condición como objeto de
espera.
- FI_WAIT_YIE
LD
Indica que la CQ esperará sin un objeto de espera, sino que cederá en cada espera. Permite el uso de fi_cq_sread y fi_cq_sreadfrom a través de un bucle de espera activa (spin)
.
signaling_vec
tor
Si se establece el indicador FI_AFFINITY, esto indica el número de CPU lógico (0..max cpu - 1) al que deben dirigirse las interrupciones asociadas con la CQ. Este campo debe tratarse como una sugerencia para el proveedor y puede ser ignorado si el proveedor no admite afinidad de
interrupción.
wait_co
nd
De forma predeterminada, cuando se inserta una finalización en una CQ que admite lecturas bloqueantes (fi_cq_sread/fi_cq_sreadfrom), el objeto
de espera correspondiente se señala. Los usuarios pueden especificar una condición que debe cumplirse primero antes de que la espera se satisfag
a. Este campo indica cómo debe interpretar el proveedor el campo cond, que describe la condición necesaria para señalar el objeto de espera.

Una condición de espera debe tratarse como una optimización. No se exige a los proveedores que cumplan los requisitos de la condición antes de señalar el objeto de espera. Las aplicaciones no deben confiar en que la condición sea necesariamente verdadera cuando una llamada de lectura bloqueante

regresa.

Si wait_cond está establecido en FI_CQ_COND_NONE, no se aplican condiciones adicionales al señalamiento del objeto de espera de la CQ, y la inserción de cualquier nueva entrada activará la condición de espera. Si wait_cond está establecido en FI_CQ_COND_THRESHOLD, el campo cond se interpreta como un valor umbral de tipo size_t. El umbral indica el número de entradas que deben encolarse en la CQ antes de que la espera se

satisfaga.

Este campo se ignora si wait_obj está establecido en

FI_WAIT_NONE.
wait_set
(obsoleto)
Si wait_obj es FI_WAIT_SET, este campo hace referencia a un objeto de espera al que la cola de finalización debe ad
juntarse. Cuando se inserta un evento en la cola de finalización, el conjunto de espera correspondiente se se
ñalará si se cumplen todas las condiciones necesarias. El uso de un wait_set permite un método optimizado para
esperar eventos en múltiples colas de eventos y finalización. Este campo se ignora si wait_obj no es FI_WAIT_SET.

fi_clos

e

La llamada fi_close libera todos los recursos asociados con una cola de finalización. Cualquier finalización que permanezca en la CQ cuando se cierre se

perderá.

Al cerrar la CQ, no debe haber extremos (endpoints), contextos de transmisión

o contextos de recepción abiertos asociados con la CQ. Si todavía hay recur
sos asociados con la CQ al intentar cerrarla, la llamada devolverá -FI_EBUSY.

fi_contro

l

La llamada fi_control se utiliza para acceder a detalles específicos del proveedor o de la implementación de la cola de finalización. El acceso a la CQ debe serializarse en todas las llamadas cuando se invoca fi_control, ya que puede redirigir la implementación de las operaciones de la CQ. Los siguientes comandos de control son utilizables con una

CQ.
FI_GETWAIT (void
**)
Este comando permite al usuario recuperar el objeto de espera de bajo nivel asociado con la CQ. El format
o del objeto de espera se especifica durante la creación de la CQ, a través de los atributos de la CQ. El
parámetro arg de fi_control debe ser una dirección donde se escribirá un puntero al objeto de esper
a devuelto. Consulte fi_eq.3 para obtener detalles adicionales sobre el uso de fi_control con FI_GETWAIT.

fi_cq_rea

d

La operación fi_cq_read realiza una lectura no bloqueante de datos de finalización desde la CQ. El formato del evento de finalización se determina usando la opción fi_cq_format que se especificó cuando se abrió la CQ. Se pueden recuperar múltiples finalizaciones de una CQ en una sola llamada. El número máximo de entradas a devolver está limitado por el parámetro count especificado, y el número de entradas leídas exitosamente de la CQ es devuelto por la llamada. (Vea la sección de valores de retorno más abajo.) Un valor de count de 0 puede usarse para impulsar el progreso en los extremos asociados cuando el progreso manual está

habilitado.

Las CQ están optimizadas para reportar operaciones que se han completado exitosamente. Las operaciones que fallan se reportan 'fuera de banda' (out of band). Dichas operaciones se recuperan usando

la función fi_cq_readerr. Cuando se encuentra una operación que ha completado con un error inesperado, se coloca en una cola de errores temporal. Intentar leer de una CQ mientras hay un elemento
en la cola de errores resulta en que fi_cq_read falle con un código de retorno de -FI_EAVAIL. Las aplicaciones pueden usar este código de retorno para determinar cuándo llamar a fi_cq_readerr.

fi_cq_readfro

m

La llamada fi_cq_readfrom se comporta de manera idéntica a fi_cq_read, con la excepción de que permite a la CQ devolver información de dirección de origen al usuario para cualquier dato recibido. Los datos de dirección de origen solo están disponibles para aquellos extremos configurados con la capacidad FI_SOURCE. Si se llama a fi_cq_readfrom en un extremo para el cual los datos de direccionamiento de origen no están disponibles, la dirección de origen se establecerá en FI_ADDR_NOTAVAIL. El número de entradas src_addr de entrada debe ser el mismo que el parámetro

count.

Los datos de direccionamiento de origen devueltos se convierten desde la dirección nativa usada por la fabricación subyacente a un fi_addr_t, que puede usarse en operaciones de transmisión. En la mayoría de las circunstancias, devolver un fi_addr_t requiere que la dirección de origen ya haya sido insertada en el vector de direcciones asociado con el extremo receptor. Esto es cierto para vectores de direcciones de tipo FI_AV_TABLE. En algunos proveedores cuando se usa FI_AV_MAP, las direcciones de origen pueden convertirse algorítmicamente en un fi_addr_t utilizable, aunque la dirección de origen no haya sido insertada en el vector de direcciones. Esto está permitido por la API, ya que permite al proveedor evitar la búsqueda de dirección como parte del procesamiento de mensajes recibidos. En ningún caso los proveedores insertan direcciones en un AV separadamente de una llamada de la aplicación a fi_av_insert o una llamada

similar.

Para extremos asignados usando la capacidad FI_SOURCE_ERR, si la dirección de origen no puede convertirse en un valor fi_addr_t válido, fi_cq_readfrom devolverá -FI_EAVAIL, incluso si los datos se recibieron exitosamente. La finalización será reportada entonces a través de fi_cq_readerr con el código de error -FI_EADDRNOTAVAIL. Consulte fi_cq_readerr para más

detalles.

Si FI_SOURCE se especifica sin FI_SOURCE_ERR, las direcciones de origen que no puedan mapearse a un fi_addr_t utilizable serán reportadas como FI_ADDR_NOTAVAI

L
.

fi_cq_sread /

fi_cq_sreadfrom

Las llamadas fi_cq_sread y fi_cq_sreadfrom son las operaciones equivalentes bloqueantes a fi_cq_read y fi_cq_readfrom. Su comportamiento es similar al de las llamadas no bloqueantes, con la excepción de que las llamadas no regresarán hasta que se haya leído una finalización de la CQ o ocurra un error o un tiempo de espera agotado (timeout)

.

Los hilos bloqueados en esta función regresarán al llamador si son señalizados por alguna fuente externa. Esto es cierto incluso si el tiempo de espera no ha ocurrido o se especificó como

infinito.

No es válido que las aplicaciones llamen a estas f

unciones si la CQ ha sido configurada con un o
bjeto de espera de FI_WAIT_NONE o FI_WAIT_SET.

fi_cq_reader

r

La función de lectura de errores, fi_cq_readerr, recupera información sobre cualquier operación asíncrona que haya completado con un error inesperado. fi_cq_readerr es una llamada no bloqueante, regresando inmediatamente ya sea que se haya encontrado una finalización de error o

no.

La información de error es reportada al usuario a través de la estructura fi_cq_err_entry. El formato de esta estructura se define más

abajo. 
struct fi_cq_err_entry {
    void     *op_context; /* contexto de la operación */
    uint64_t flags;       /* indicadores de finalización */
    size_t   len;         /* tamaño de los datos recibidos */
    void     *buf;        /* búfer de datos de recepción */
    uint64_t data;        /* datos de finalización */
    uint64_t tag;         /* etiqueta del mensaje */
    size_t   olen;        /* longitud de desbordamiento */
    int      err;         /* código de error positivo */
    int      prov_errno;  /* código de error del proveedor */
    void    *err_data;    /*  datos de error */
    size_t   err_data_size; /* tamaño de err_data */
    fi_addr_t src_addr; /* dirección de origen del error
*/
}
;

La razón general del error se proporciona a través del campo err. La información de error específica del proveedor también puede estar disponible a través de los campos prov_errno y err_data. Los usuarios pueden llamar a fi_cq_strerror para convertir la información de error específica del proveedor en una cadena imprimible con fines de depuración. Consulte los detalles de los campos más abajo para obtener más información sobre el uso de err_data y

err_data_size.

Tenga en cuenta que se generan finalizaciones de error para todas las operaciones, incluyendo aquellas para las cuales no se solicitó una finalización (por ejemplo, un extremo está configurado con FI_SELECTIVE_COMPLETION, pero la solicitud no tenía establecido el indicador FI_COMPLETION). En tales casos, los proveedores devolverán tanta información como la que ponga a disposición el software y el hardware subyacentes sobre el fallo, los demás campos se establecerán a NULL o 0. Esto incluye el valor de op_context, que puede no haberse proporcionado o haberse ignorado en la entrada como parte de la

transferencia.

A continuación se indican los códigos de error de finalización

notables.
FI_EADDRNOTAV
AIL
Este código de error lo utilizan las CQ configuradas con FI_SOURCE_ERR para informar de finalizaciones para las que no se pudo encontrar una dirección de origen fi_addr_t utilizable. Un código de error de FI_EADDRNOTAVAIL indica que la
transferencia de datos se recibió y procesó correctamente, con los campos de fi_cq_err_entry que contienen información sobre la finalización. El campo err_data se establecerá en los datos de la dirección de origen. La dirección de origen
estará en el mismo formato que el especificado a través del campo addr_format de fi_info para el dominio abierto. Esto puede pasarse directamente a una llamada fi_av_insert para añadir la dirección de origen al vector de direcciones.

Para las versiones de API 1.20 y posteriores, si el EP está configurado con FI_AV_AUTH_KEY, src_addr se establecerá en el identificador de clave de autorización fi_addr_t o en un ID de clave de autorización definido por el usuario correspondiente a la transferencia de datos entrante. De lo contrario, el valor se establecerá en FI_ADDR_NOTAVAI

L
.

Está destinado a usarse como ayuda para la depuración. Consulte fi_cq_strerror para obtener más detalles sobre la conversión de este valor de error en una cadena legible para

El campo err_data se utiliza para devolver información específica del proveedor, si está disponible, sobre el error. En la entrada, err_data debe referenciar un búfer de datos de tamaño err_data_size. En la salida, el proveedor rellenará este búfer con cualquier dato específico del proveedor que pueda ayudar a identificar la causa del error. SEMÁNTICA DE EVENTOS DE FINALIZACIÓN

Libfabric define varios `niveles' de finalización, identificados mediante banderas operativas. Cada bandera indica el momento más temprano en que un proveedor puede generar un evento de finalización, y las suposiciones que una aplicación puede hacer al procesar una finalización. Las banderas operativas se definen a continuación, junto con un ejemplo de cómo un proveedor podría implementar la semántica. Tenga en cuenta que solo se requiere que el proveedor cumpla con la semántica, no con la implementación. Los proveedores pueden implementar semánticas de finalización más fuertes de las necesarias para una operación determinada, pero solo se garantiza el comportamiento definido por el nivel de finalización.

Para ayudar a comprender las diferencias conceptuales entre los niveles de finalización, considere el envío de una carta. Colocar la carta en el buzón local para su recogida es similar a `inyección completa'. Tener la carta recogida y depositada en el buzón de destino es equivalente a `transmisión completa'. La semántica `entrega completa' es una garantía más fuerte, con una persona en el destino firmando por la carta. Sin embargo, la persona que firmó por la carta no es necesariamente el destinatario previsto. La opción `coincidencia completa' es similar a entrega completa, pero requiere que el destinatario previsto firme por la carta.

El nivel `compromiso completo' tiene una semántica diferente a la de los niveles mencionados anteriormente. El compromiso completo sería más cercano a la carta que llega al destino y se coloca en una caja fuerte a prueba de fuego.

Las banderas operativas para los niveles de finalización descritos se definen a continuación.

FI_INJECT_COMPLETE
Indica que se debe generar una finalización cuando el(los) búfer(es) de origen puedan reutilizarse. Una finalización garantiza que no se volverá a leer de los búferes y la aplicación puede reclamarlos. No se hacen otras garantias con respecto al estado de la operación.

Ejemplo: Un proveedor puede generar este evento de finalización después de copiar el búfer de origen en un búfer de red, ya sea en la memoria del host o en la tarjeta de interfaz de red (NIC). Una inyección completa no indica que los datos hayan sido transmitidos a la red, y un error local podría ocurrir después de que se haya generado el evento de finalización, lo que podría evitar que se transmita.

La inyección completa permite el informe de finalización más rápido (y, por lo tanto, la reutilización del búfer), pero proporciona las garantías más débiles contra los errores de red.

Nota: Esta bandera se utiliza para controlar cuándo se inserta una entrada de finalización en una cola de finalización. No se aplica a operaciones que no generan una entrada de cola de finalización, como la operación fi_inject, y no está sujeta a la restricción del límite de mensaje inject_size.

FI_TRANSMIT_COMPLETE
Indica que se debe generar una finalización cuando la operación de transmisión se haya completado con respecto al proveedor local. El comportamiento exacto depende del tipo de punto de extremo.

Para puntos de extremo fiables:

Indica que se debe generar una finalización cuando la operación haya sido entregada al punto de extremo par. Una finalización garantiza que la operación ya no depende de la red o de los recursos locales. El estado de la operación en el punto de extremo par no está definido.

Ejemplo: Un proveedor puede generar un evento de transmisión completa al recibir una confirmación (ack) del punto de extremo par. El estado del mensaje en el par es desconocido y puede estar almacenado en búfer en la NIC de destino en el momento en que se genera la confirmación.

Para puntos de extremo no fiables:

Indica que se debe generar una finalización cuando la operación haya sido entregada a la red. Una finalización garantiza que la operación ya no depende de los recursos locales. El estado de la operación dentro de la red no está definido.

FI_DELIVERY_COMPLETE
Indica que no se debe generar una finalización hasta que una operación haya sido procesada por el(los) punto(s) de extremo de destino. Una finalización garantiza que el resultado de la operación está disponible; sin embargo, pueden ser necesarios pasos adicionales en el destino para recuperar los resultados. Por ejemplo, la aplicación puede necesitar proporcionar búferes de recepción para recuperar mensajes que fueron almacenados en búfer por el proveedor.

La entrega completa indica que el mensaje ha sido procesado por el par. Si un búfer de aplicación estaba listo para recibir los resultados del mensaje cuando llegó, entonces la entrega completa indica que los datos fueron colocados en el búfer de la aplicación.

Este modo de finalización se aplica solo a puntos de extremo fiables. Para operaciones que devuelven datos al iniciador, como lecturas RMA o atomic-fetch, el punto de extremo de origen también se considera un punto de extremo de destino. Este es el modo de finalización predeterminado para tales operaciones.

FI_MATCH_COMPLETE
Indica que se debe generar una finalización solo después de que la operación haya sido emparejada con un búfer especificado por la aplicación. Las operaciones que utilizan esta semántica de finalización dependen de que la aplicación en el destino reclame el mensaje o los resultados. Como resultado, la coincidencia completa puede involucrar confirmaciones adicionales a nivel de proveedor o largas demoras. Sin embargo, este modelo de finalización permite a las aplicaciones pares sincronizar su ejecución. Muchos proveedores pueden no soportar esta semántica.
FI_COMMIT_COMPLETE
Indica que no se debe generar una finalización (localmente o en el par) hasta que el resultado de una operación se haya hecho persistente. Una finalización garantiza que el resultado está tanto disponible como duradero, en caso de fallo de energía.

Este modo de finalización se aplica solo a operaciones que apuntan a regiones de memoria persistente sobre puntos de extremo fiables. Este modo de finalización es experimental.

FI_FENCE
Este no es un nivel de finalización, pero juega un papel en el ordenamiento de finalizaciones entre operaciones que normalmente no estarían ordenadas. Una operación marcada con la bandera FI_FENCE y todas las operaciones publicadas después de la operación cercada se difieren hasta que todas las operaciones anteriores que apuntan al mismo punto de extremo par se hayan completado. Además, la finalización de la operación cercada indica que las operaciones anteriores han alcanzado el mismo nivel de finalización que la operación cercada. Por ejemplo, si una operación se publica como FI_DELIVERY_COMPLETE | FI_FENCE, entonces su finalización indica que las operaciones anteriores han cumplido la semántica requerida para FI_DELIVERY_COMPLETE. Esto es cierto incluso si la operación anterior se publicó con un nivel de finalización más bajo, como FI_TRANSMIT_COMPLETE o FI_INJECT_COMPLETE.

Tenga en cuenta que una finalización generada para una operación publicada antes de la operación cercada solo garantiza que el nivel de finalización originalmente solicitado se ha cumplido. Es la finalización de la operación cercada la que garantiza que se han cumplido las semánticas adicionales.

Las semánticas de finalización anteriores se definen con respecto al iniciador de la operación. Las diferentes semánticas son útiles para describir cuándo el iniciador puede reutilizar un búfer de datos, y garantizan qué estado debe alcanzar una transferencia antes de que se genere una finalización. Esto permite a las aplicaciones determinar el manejo de errores apropiado en caso de fallos de comunicación.

SEMÁNTICA DE FINALIZACIÓN EN EL DESTINO

La semántica de finalización en el destino se utiliza para determinar cuándo los datos en el destino son visibles para la aplicación par. La visibilidad indica que una lectura de memoria en la misma dirección que fue el destino de una transferencia de datos devolverá los resultados de la transferencia. El destino de una transferencia puede ser identificado por el iniciador, como puede ser el caso de las operaciones RMA y atómicas, o determinado por el destino, por ejemplo, proporcionando un búfer de recepción coincidente. La visibilidad global indica que los resultados están disponibles independientemente de dónde se origine la lectura de memoria. Por ejemplo, la lectura podría provenir de un proceso que se ejecuta en una CPU del host, podría ser accedida por una transferencia de datos posterior a través de la red, o leída desde un dispositivo par como una GPU.

En términos de semánticas de finalización, la visibilidad usualmente indica que la transferencia cumple los requisitos de FI_DELIVERY_COMPLETE desde la perspectiva del destino. La semántica de finalización en el destino puede estar, pero no necesariamente está, vinculada con la semántica de finalización especificada por el iniciador de la transferencia.

A menudo, los procesos de destino no declaran explícitamente una semántica de finalización deseada y en su lugar dependen de la semántica predeterminada. El comportamiento predeterminado se basa en varios factores, incluyendo:

•
si se genera un evento de finalización en el destino
•
el tipo de transferencia involucrada (por ejemplo, msg vs RMA)
•
garantías de ordenamiento de datos y mensajes del punto de extremo
•
propiedades del búfer de memoria de destino
•
la semántica de finalización especificada por el iniciador

En términos generales, las semánticas de finalización en el destino se agrupan en función de si la transferencia genera un evento de finalización en el destino o no. Esto incluye escribir una entrada en la cola de finalización (CQ) o actualizar un contador de finalización. En casos de uso comunes, las transferencias que utilizan una interfaz de mensaje (FI_MSG o FI_TAGGED) típicamente generan eventos en el destino, mientras que las transferencias que involucran una interfaz RMA (FI_RMA o FI_ATOMIC) a menudo no lo hacen. Hay excepciones a ambos casos, dependiendo de los enlaces de punto de extremo a CQ y contadores, y las banderas operativas. Por ejemplo, las escrituras RMA que llevan datos de CQ remotos generarán un evento de finalización en el destino, y se usan frecuentemente para transmitir visibilidad a la aplicación de destino. Las pautas generales para la semántica del lado del destino se describen a continuación, seguidas de excepciones que modifican ese comportamiento.

De forma predeterminada, las finalizaciones generadas en el destino indican que los datos transferidos están inmediatamente disponibles para ser leídos desde el búfer de destino. Es decir, el destino ve semánticas de FI_DELIVERY_COMPLETE (o mejores), incluso si el iniciador solicitó semánticas más bajas. Para aplicaciones que usan solo búferes de datos asignados desde la memoria del host, esto a menudo es suficiente.

Paraoperaciones que no generan un evento de finalización en el destino, la visibilidad de los datos en el destino puede necesitar ser inferida basándose en operaciones posteriores que sí generan finalizaciones en el destino. En ausencia de una finalización en el destino, cuando se escribe en el iniciador la finalización de una operación, la semántica de visibilidad de la operación en el destino se alinea con la semántica de finalización del iniciador. Por ejemplo, si una operación RMA finaliza en el iniciador como FI_INJECT_COMPLETE o FI_TRANSMIT_COMPLETE, la visibilidad de los datos en el destino no está

garantizada.

El proceso de destino puede utilizar uno o más de los siguientes mecanismos para garantizar que los resultados de una transferencia de datos que no generó una finalización en el destino ahora sean visibles. Esta lista no es exhaustiva de todas las opciones, pero define usos comunes. En las descripciones a continuación, la primera transferencia no resulta en un evento de finalización en el destino, pero es eventualmente seguida por una transferencia que sí lo

hace.
•
Si el punto de extremo garantiza el orden de mensajes entre dos transferencias, la finalización en el destino de una segunda transferencia indicará que los datos de la primera transferencia están disponibles. Por ejemplo, si el punto de extremo soporta el orden de escritura después de envío (FI_ORDER_SAW), entonces una finalización de recepción correspondiente al envío indicará que los datos de la escritura están disponibles. Esto se mantiene independientemente de la semántica de finalización del iniciador para la escritura o el envío. Cuando se garantiza el orden, la segunda transferencia puede ser encolada con el proveedor inmediatamente después de encolar la
primera.
•
Si el punto de extremo no garantiza el orden de mensajes, el iniciador debe tomar pasos adicionales para asegurar la visibilidad. Si el iniciador solicita la semántica FI_DELIVERY_COMPLETE para la primera operación, el iniciador puede esperar a que la operación se complete localmente. Una vez que la finalización ha sido leída, la finalización en el destino de una segunda transferencia indicará que los datos de la primera transferencia son
visibles.
•
Alternativamente, si el orden de mensajes no está garantizado por el punto de extremo, el iniciador puede usar los indicadores FI_FENCE y FI_DELIVERY_COMPLETE en la segunda transfere
ncia de datos para forzar que las primeras transferencias cumplan la semántica FI_DELIVERY_COMPLETE. Si la segunda transferencia genera una finalización en el destino, eso indicará
que los datos son visibles. De lo contrario, una finalización en el destino para cualquier transferencia después de la operación cercada (fenced) indicará que los datos son visibles.

Las semánticas anteriores se aplican a transferencias dirigidas a búferes de memoria tradicionales del host. Sin embargo, el comportamiento puede diferir cuando se involucra memoria de dispositivo y/o memoria persistente (bits de capacidad FI_HMEM y FI_PMEM). Cuando se involucra memoria heterogénea, el concepto de dominios de memoria entra en juego. Los dominios de memoria identifican la separación física de la memoria, que puede o no ser accesible a través del mismo espacio de direcciones virtuales. Consulte la página del manual fi_mr(3) para más detalles sobre los dominios de

memoria.

El orden de finalización y la visibilidad de los datos solo están bien definidos para transferencias que se dirigen al mismo dominio de memoria. Las aplicaciones deben ser conscientes de las diferencias de orden y visibilidad cuando las transferencias se dirigen a diferentes dominios de memoria. Además, las aplicaciones también deben preocuparse por el dominio de memoria en el que se escriben las finalizaciones mismas y si difiere del dominio de memoria al que se dirige una transferencia. En algunas situaciones, ya sea el proveedor o la aplicación pueden necesitar llamar a APIs específicas del dispositivo para sincronizar o vaciar (flush) las cachés de memoria del dispositivo para lograr la visibilidad de datos

deseada.

Cuando se usa memoria heterogénea, la semántica de finalización en el destino por defecto para transferencias que generan una finalización en el destino sigue siendo FI_DELIVERY_COMPLETE, sin embargo, las aplicaciones deben ser conscientes de que puede haber un impacto negativo en el rendimiento general para que los proveedores cumplan este

requisito.

Por ejemplo, un proceso de destino puede estar usando una GPU para acelerar cálculos. Una región de memoria que mapea a memoria en la GPU puede ser expuesta a pares como un destino RMA o publicada localmente como un búfer de recepción. En este caso, la aplicación se preocupa por dos dominios de memoria – sistema y memoria GPU. Las finalizaciones se escriben en la memoria del

sistema.

Continuando con el ejemplo, un proceso par envía un mensaje etiquetado. Ese mensaje se empareja con el búfer de recepción ubicado en la memoria GPU. La NIC copia los datos de la red en el búfer de recepción y escribe una entrada en la cola de finalización. Note que ambos dominios de memoria fueron accedidos como parte de esta transferencia. Los datos del mensaje fueron dirigidos a la memoria GPU, pero la finalización fue a la memoria del host. Debido a que dominios de memoria separados pueden no estar sincronizados entre sí, es posible que la CPU del host vea y procese la entrada de finalización antes de que la transferencia a la memoria GPU sea visible para la GPU del host o incluso para el software que se ejecuta en la GPU. Desde la perspectiva del proveedor, la visibilidad de la finalización no implica la visibilidad de los datos escritos en el dominio de memoria de la

GPU.

La semántica de finalización por defecto en el destino aplicación para operaciones de mensaje es FI_DELIVERY_COMPLETE. Una implementación anticipada del proveedor en esta situación es que el software del proveedor que se ejecuta en la CPU del host intercepte la entrada de CQ, detecte que los datos aterrizaron en memoria heterogénea, y realice la sincronización o vaciado (flush) necesaria del dispositivo antes de reportar la finalización a la aplicación. Esto asegura que los datos son visibles para la CPU y el software de la GPU antes de que la aplicación procese la

finalización.

Además del costo del software del proveedor interceptando finalizaciones y verificando si una transferencia se dirigió a memoria heterogénea, la sincronización del dispositivo misma puede impactar el rendimiento. Como resultado, las aplicaciones pueden solicitar una semántica de finalización más baja al publicar recepciones. Eso indica al proveedor que la aplicación será responsable de manejar cualquier operación de vaciado (flush) específica del dispositivo que pueda ser necesaria. Consulte fi_msg(3)

FLAGS.

Para transferencias de datos que no generan una finalización en el destino, como RMA o operaciones atómicas, es responsabilidad de la aplicación asegurar que todos los búferes de destino cumplan los requisitos de visibilidad necesarios de la aplicación. Los métodos con viñetas mencionados anteriormente para notificar al destino que los datos son visibles pueden no ser suficientes, ya que el software del proveedor en el destino podría carecer del contexto necesario para asegurar la visibilidad. Esto implica que la aplicación puede necesitar llamar a APIs de sincronización/vaciado (flush) del dispositivo

directamente.

Por ejemplo, una aplicación par podría realizar varias escrituras RMA que se dirigen a búferes de memoria GPU. Si el proveedor descarga las operaciones RMA en la NIC, el software del proveedor en el destino no será consciente de que las operaciones RMA han ocurrido. Si el par envía un mensaje a la aplicación de destino que indica que las operaciones RMA están hechas, la aplicación debe asegurar que los datos RMA son visibles para la CPU o GPU del host antes de ejecutar código que acceda a los datos. La finalización en el destino de haber recibido el mensaje enviado no es suficiente, incluso si se soporta el orden de escritura después de envío (send-after-write)

.

La mayoría de las semánticas de finalización de memoria heterogénea en el destino se mapean a FI_TRANSMIT_COMPLETE o FI_DELIVERY_COMPLETE. La memoria persistente (capacidad FI_PMEM), sin embargo, se usa a menudo con la semántica FI_COMMIT_COMPLETE. Los conceptos de finalización heterogénea aún se

aplican.

Para transferencias marcadas por el iniciador con FI_COMMIT_COMPLETE, una finalización en el destino indica que los resultados son visibles y duraderos. Para transferencias dirigidas a memoria persistente, pero usando una diferente semántica de finalización en el iniciador, la visibilidad en el destino es similar a la descrita anteriormente. La durabilidad solo se asocia con transferencias marcadas con FI_COMMIT_COMPLETE

.

Para transferencias dirigidas a memoria persistente que solicitan FI_DELIVERY_COMPLETE, entonces una finalización, ya sea en el iniciador o en el destino, indica que los datos son visibles. La visibilidad en el destino puede ser transmitida usando uno de los mecanismos descritos anteriormente – generando una finalización en el destino, enviando un mensaje desde el iniciador, etc. De manera similar, si el iniciador solicitó FI_TRANSMIT_COMPLETE, entonces se necesitan pasos adicionales para asegurar la visibilidad en el destino. Por ejemplo, la transferencia puede generar una finalización en el destino, lo que indicaría visibilidad, pero no durabilidad. El iniciador también puede seguir la transferencia con otra operación que fuerce la visibilidad, como usar FI_FENCE en conjunto con FI_DELIVERY_COMPLET

E
.

NAME

fi_cq, fi_cq_open, fi_cq_bind, fi_cq_read, fi_cq_sread, fi_cq_close — Fabric completion queue (CQ)

SYNOPSIS

#include <rdma/fabric.h>

int fi_cq_open(struct fi_fabric *fabric, struct fi_cq_attr *attr,
    struct fi_cq **cq);
int fi_cq_bind(struct fi_cq *cq, void *handle, uint32_t flags);
ssize_t fi_cq_read(struct fi_cq *cq, void *buf, size_t len, uint64_t flags);
ssize_t fi_cq_sread(struct fi_cq *cq, void *buf, size_t len, uint64_t flags,
    void *rdma_context);
int fi_cq_close(struct fi_cq *cq);

ARGUMENTS

fabric
A valid fabric descriptor returned by fi_fabric.
attr
Pointer to a fi_cq_attr structure used to configure the completion queue. If NULL, default attributes are used.
cq
Output parameter for the newly created completion queue descriptor.
handle
The object to which the completion queue will be bound. Valid handles include fi_endpoint, fi_domain, and fi_eq. The specific object type that can be bound to a CQ depends on the fabric provider.
flags
Flags for the operation. Valid flags include:
FI_RECV
Indicates the CQ will be used for receiving operations.
FI_SEND
Indicates the CQ will be used for sending operations.
FI_SELECTIVE_COMPLETION
If set, only operations explicitly associated with this CQ will generate completion events.
FI_CLAIM
If set, the caller claims ownership of the completion events. This flag is used with fi_cq_read and fi_cq_sread.
FI_WAIT
If set, the call will block until a completion event is available. This flag is used with fi_cq_read and fi_cq_sread.
buf
Pointer to the buffer where completion events will be stored.
len
The size of the buffer in bytes.
rdma_context
Optional context for RDMA operations. This is used with fi_cq_sread to retrieve RDMA-specific completion information.

DESCRIPTION

A completion queue (CQ) is an object used to collect status information about operations that have completed. Completion events are generated by the fabric provider when an operation initiated by the application (e.g., send, receive, read, write) is completed. Fabric operations are typically asynchronous, meaning that the application initiates an operation and continues to execute without waiting for the operation to complete. Completion events notify the application that an operation has finished, along with its status (e.g., success, error).

fi_cq_open creates a new completion queue associated with the specified fabric. The attr parameter is used to configure the CQ. If attr is NULL, default attributes are used. The cq parameter is an output parameter that will hold a pointer to the newly created CQ descriptor.

fi_cq_bind binds a completion queue to another fabric object, such as an endpoint or a domain. This allows the CQ to collect completion events for operations associated with the bound object.

fi_cq_read reads one or more completion events from the CQ into the provided buffer. The buf parameter should point to a buffer large enough to hold the requested number of completion events. The len parameter specifies the maximum number of bytes to read. If FI_CLAIM is specified, the caller claims ownership of the completion events. If FI_WAIT is specified, the call will block until at least one completion event is available.

fi_cq_sread is similar to fi_cq_read but is intended for use with RDMA operations. It can retrieve RDMA-specific completion information using the rdma_context parameter.

fi_cq_close closes and releases all resources associated with the completion queue.

COMPLETION FIELDS

The buf parameter in fi_cq_read and fi_cq_sread is expected to be an array of struct fi_completion structures. The structure contains the following fields:

op_context
User-defined context associated with the operation.
flags
Flags associated with the completion event.
error
Error code if the operation failed. If the operation succeeded, this field is zero.
count
Number of bytes transferred for send/recv operations, or number of messages for other operations.
reserved
Reserved for future use.

COMPLETION FLAGS

The flags field in the struct fi_completion structure can contain the following flags:

FI_SUCCESS
The operation completed successfully.
FI_FAILURE
The operation failed.
FI_MORE
Indicates that there are more completion events available in the CQ.
FI_ASYNC_COMPLETION
Indicates that the completion event was generated asynchronously.

COMPLETION EVENT SEMANTICS

Completion events are generated when an operation completes. The fabric provider is responsible for generating these events and making them available to the application through the CQ. The application can then poll the CQ or use event notification mechanisms to retrieve completion events.

TARGET COMPLETION SEMANTICS

Completion events generated for a specific operation are associated with the CQ that was bound to the object initiating the operation (e.g., endpoint, domain). This allows the application to direct completion events to specific CQs for better management and processing.

NOTES

The maximum number of completion events that can be read in a single call to fi_cq_read or fi_cq_sread is determined by the fabric provider and may be limited by the size of the buffer provided.

The fi_cq_read and fi_cq_sread functions return the number of completion events read, or a negative value on error. A return value of 0 indicates that no completion events were available.

Fabric errno values are defined in rdma/fi_errno.h.

RETURN VALUES

fi_cq_open returns 0 on success, or a negative error code on failure.

fi_cq_bind returns 0 on success, or a negative error code on failure.

fi_cq_read and fi_cq_sread return the number of completion events read on success, or a negative error code on failure. A return value of 0 indicates that no completion events were available.

fi_cq_close returns 0 on success, or a negative error code on failure.

On failure, a specific error code is returned with a completion.

Fabric errno values are defined in rdma/fi_errno.h.
