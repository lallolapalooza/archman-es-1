NOMBRE

fi_eq - Operaciones de cola de eventos

fi_eq_open / fi_close
Abrir/cerrar una cola de eventos
fi_control
Controlar la operación de la EQ
fi_eq_read / fi_eq_readerr
Leer un evento de una cola de eventos
fi_eq_write
Escribe un evento en una cola de eventos
fi_eq_sread
Una lectura síncrona (bloqueante) de una cola de eventos
fi_eq_strerror
Convierte información de error específica del proveedor en una cadena imprimible

SINOPSIS

#include <rdma/fi_domain.h>
int fi_eq_open(struct fid_fabric *fabric, struct fi_eq_attr *attr,
    struct fid_eq **eq, void *context);
int fi_close(struct fid *eq);
int fi_control(struct fid *eq, int command, void *arg);
ssize_t fi_eq_read(struct fid_eq *eq, uint32_t *event,
    void *buf, size_t len, uint64_t flags);
ssize_t fi_eq_readerr(struct fid_eq *eq, struct fi_eq_err_entry *buf,
    uint64_t flags);
ssize_t fi_eq_write(struct fid_eq *eq, uint32_t event,
    const void *buf, size_t len, uint64_t flags);
ssize_t fi_eq_sread(struct fid_eq *eq, uint32_t *event,
    void *buf, size_t len, int timeout, uint64_t flags);
const char * fi_eq_strerror(struct fid_eq *eq, int prov_errno,
      const void *err_data, char *buf, size_t len);

Tiempo de espera especificado en milisegundos

DESCRIPCIÓN

Las colas de eventos se utilizan para reportar eventos asociados con operaciones de control. Están asociadas con el registro de memoria, vectores de dirección, gestión de conexiones y eventos de tejido y dominio. Los eventos reportados están asociados con una operación solicitada o afiliados con una llamada que registra tipos específicos de eventos, como esperar solicitudes de conexión.

fi_eq_open

fi_eq_open asigna una nueva cola de eventos.

Las propiedades y el comportamiento de una cola de eventos se definen por struct fi_eq_attr.

struct fi_eq_attr {
    size_t               size;      /* # entradas para EQ */
    uint64_t             flags;     /* flags de operación */
    enum fi_wait_obj     wait_obj;  /* objeto de espera solicitado */
    int                  signaling_vector; /* afinidad de interrupción */
    struct fid_wait     *wait_set;  /* conjunto de espera opcional, obsoleto */
};
size
Especifica el tamaño mínimo de una cola de eventos.
flags
Indicadores que controlan la configuración de la EQ.
- FI_WRITE
Indica que la aplicación requiere soporte para insertar eventos de usuario en la EQ. Si este indicador está activado, la operación fi_eq_write debe ser compatible con el proveedor. Si el indicador FI_WRITE no está activado, la aplicación no puede invocar fi_eq_write.
- FI_AFFINITY
Indica que el campo signaling_vector (ver abajo) es válido.
wait_obj
Las EQ pueden asociarse con un objeto de espera específico. Los objetos de espera permiten a las aplicaciones bloquearse hasta que el objeto de espera se active, indicando que hay un evento disponible para ser leído. Los usuarios pueden usar fi_control para recuperar el objeto de espera subyacente asociado con una EQ, para usarlo en otras llamadas del sistema. Los siguientes valores pueden usarse para especificar el tipo de objeto de espera asociado con una EQ:
- FI_WAIT_NONE
Se utiliza para indicar que el usuario no se bloqueará (esperará) eventos en la EQ. Cuando se especifica FI_WAIT_NONE, la aplicación no puede llamar a fi_eq_sread. Este es el valor predeterminado si no se especifica ningún objeto de espera.
- FI_WAIT_UNSPEC
Especifica que el usuario solo esperará en la EQ utilizando llamadas a la interfaz de tejido, como fi_eq_sread. En este caso, el proveedor subyacente puede seleccionar el objeto de espera más apropiado o de mayor rendimiento disponible, incluidos mecanismos de espera personalizados. Las aplicaciones que seleccionan FI_WAIT_UNSPEC no tienen garantizado recuperar el objeto de espera subyacente.
- FI_WAIT_SET (obsoleto)
Indica que la cola de eventos debe usar un objeto de conjunto de espera para esperar eventos. Si se especifica, el campo wait_set debe hacer referencia a un objeto de conjunto de espera existente.
- FI_WAIT_FD
Indica que la EQ debe usar un descriptor de archivo como su mecanismo de espera. Un objeto de espera de descriptor de archivo debe ser utilizable en rutinas select, poll y epoll. Sin embargo, un proveedor puede activar un objeto de espera de FD marcándolo como legible o con un error.
- FI_WAIT_MUTEX_COND (obsoleto)
Especifica que la EQ debe usar un mutex pthread y una variable condicional como objeto de espera.
- FI_WAIT_YIELD
Indica que la EQ esperará sin un objeto de espera, sino que cederá en cada espera. Permite el uso de fi_eq_sread a través de un spin.
signaling_vector
Si el indicador FI_AFFINITY está activado, este indica el número de CPU lógico (0..máx CPU - 1) al que deben dirigirse las interrupciones asociadas con la EQ. Este campo debe tratarse como una sugerencia para el proveedor y puede ser ignorado si el proveedor no admite la afinidad de interrupciones.
wait_set (obsoleto)
Si wait_obj es FI_WAIT_SET, este campo hace referencia a un objeto de espera al que la cola de eventos debe adjuntarse. Cuando se inserta un evento en la cola de eventos, el conjunto de espera correspondiente se activará si se cumplen todas las condiciones necesarias. El uso de un wait_set permite un método optimizado para esperar eventos en múltiples colas de eventos. Este campo se ignora si wait_obj no es FI_WAIT_SET.

fi_close

La llamada fi_close libera todos los recursos asociados con una cola de eventos. Cualquier evento que quede en la EQ cuando se cierre se perderá.

La EQ no debe estar vinculada a ningún otro objeto antes de cerrarse, de lo contrario, la llamada devolverá -FI_EBUSY.

fi_control

La llamada fi_control se utiliza para acceder a detalles específicos del proveedor o de la implementación de la cola de eventos. El acceso a la EQ debe serializarse en todas las llamadas cuando fi_contr

ol se invoca, ya que puede redirigir la implementación de las operaciones EQ. Los siguientes comandos de control son utilizables con una EQ.

FI_GETWAIT (void **)
Este comando permite al usuario recuperar el objeto de espera de bajo nivel asociado con la EQ. El formato del objeto de espera se especifica durante la creación de la EQ, a través de los atributos de la EQ. El parámetro de control fi_control debe ser una dirección donde se escribirá un puntero al objeto de espera devuelto. Esto debe ser un ’int *’ para FI_WAIT_FD, o `struct fi_mutex_cond' para FI_WAIT_MUTEX_COND (obsoleto).
struct fi_mutex_cond {
    pthread_mutex_t     *mutex;
    pthread_cond_t      *cond;
};

fi_eq_read

La operación fi_eq_read realiza una lectura no bloqueante de datos de eventos de la EQ. El formato de los datos del evento se basa en el tipo de evento recuperado de la EQ, y todos los eventos comienzan con una cabecera struct fi_eq_entry. Como máximo, se devolverá un evento por operación de lectura de EQ. El número de bytes leídos correctamente de la EQ se devuelve de la lectura. El flag FI_PEEK puede usarse para indicar que los datos del evento deben leerse de la EQ sin ser consumidos. Una lectura posterior sin el flag FI_PEEK eliminaría entonces el evento de la EQ.

Los siguientes tipos de eventos pueden ser reportados a una EQ, junto con información sobre el formato asociado con cada evento.

Operaciones de Control Asíncronas
Las operaciones de control asíncronas son solicitudes básicas que simplemente necesitan generar un evento para indicar que se han completado. Estas incluyen los siguientes tipos de eventos: registro de memoria, resolución de vectores de direcciones y uniones multicast.

Las solicitudes de control informan su finalización insertando una struct fi_eq_entry en la EQ. El formato de esta estructura es:

struct fi_eq_entry {
    fid_t            fid;        /* fid asociado con la solicitud */
    void            *context;    /* contexto de la operación */
    uint64_t         data;       /* datos específicos de la finalización */
};

Para la finalización de operaciones de control asíncronas básicas, el evento devuelto indicará la operación que ha finalizado, y el fid hará referencia al descriptor de fabric asociado con el evento. Para el registro de memoria, este será un evento FI_MR_COMPLETE y el fid_mr. La resolución de direcciones hará referencia a un evento FI_AV_COMPLETE y fid_av. Las uniones multicast reportarán un FI_JOIN_COMPLETE y fid_mc. El campo context se establecerá en el contexto especificado como parte de la operación, si está disponible, de lo contrario, el contexto se asociará con el descriptor de fabric. El campo data se establecerá como se describe en la página man del tipo de objeto correspondiente (por ejemplo, consulte fi_av(3) para una descripción de cómo se completan las inserciones asíncronas de vectores de direcciones).

Notificación de Conexión
Las notificaciones de conexión son notificaciones de gestión de conexiones utilizadas para establecer o cerrar conexiones entre puntos finales. Hay tres eventos de notificación de conexión: FI_CONNREQ, FI_CONNECTED y FI_SHUTDOWN. Las notificaciones de conexión se reportan usando struct fi_eq_cm_entry:
struct fi_eq_cm_entry {
    fid_t            fid;        /* fid asociado con la solicitud */
    struct fi_info  *info;       /* información del punto final */
    uint8_t         data[];     /* datos de conexión de la aplicación */
};

Un evento de solicitud de conexión (FI_CONNREQ) indica que un punto final remoto desea establecer una nueva conexión a un punto final que escucha, o pasivo. El fid es el punto final pasivo. La información sobre las capacidades y atributos del punto final remoto solicitado, activo, está disponible en el campo info. La aplicación es responsable de liberar esta estructura llamando a fi_freeinfo cuando ya no sea necesaria. El campo connreq de fi_info hará referencia a la solicitud de conexión asociada con este evento. Para aceptar una conexión, primero se debe crear un punto final pasando una estructura fi_info que haga referencia a este campo connreq a fi_endpoint(). Este punto final se pasa a fi_accept() para completar la aceptación del intento de conexión. La creación del punto final se logra más fácilmente pasando el fi_info devuelto como parte del evento CM a fi_endpoint(). Si la conexión debe ser rechazada, el connreq se pasa a fi_reject().

Cualquier dato de aplicación intercambiado como parte de la solicitud de conexión se coloca más allá de la estructura fi_eq_cm_entry. La cantidad de datos disponibles depende de la aplicación y está limitada al espacio de búfer proporcionado por la aplicación cuando se llama a fi_eq_read. La cantidad de datos devueltos puede ser calculada usando el valor de retorno de fi_eq_read. Tenga en cuenta que la cantidad de datos devueltos está limitada por el protocolo de conexión subyacente, y la longitud de cualquier dato devuelto puede incluir relleno del protocolo. Como resultado, la longitud devuelta puede ser mayor que la especificada por el par de conexión.

Si se ha aceptado una solicitud de conexión, se generará un evento FI_CONNECTED en ambos lados de la conexión. El lado activo – el que llamó a fi_connect() – puede recibir datos del usuario como parte del evento FI_CONNECTED. Los datos del usuario se pasan al gestor de conexiones en el lado pasivo a través de la llamada fi_accept. Los datos del usuario no se proporcionan con un evento FI_CONNECTED en el lado de escucha de la conexión.

La notificación de que un par remoto se ha desconectado de un punto final activo se realiza a través del evento FI_SHUTDOWN. La notificación de cierre utiliza struct fi_eq_cm_entry como se declaró anteriormente. El campo fid para una notificación de cierre se refiere al fid_ep del punto final activo.

Notificación de Errores Asíncronos
Los errores asíncronos se utilizan para informar problemas con los recursos de fabric. Los errores reportados pueden ser fatales o transitorios, según el error, y resultan en que el recurso quede deshabilitado. Los recursos deshabilitados fallarán las operaciones enviadas contra ellos hasta que sean explícitamente re-habilitados por la aplicación.

Los errores asíncronos pueden ser reportados para colas de finalización y puntos finales de todo tipo. Los errores de CQ pueden ocurrir cuando la gestión de recursos se ha deshabilitado y el proveedor ha detectado un desbordamiento de cola. Los errores de punto final pueden ser el resultado de numerosas acciones, pero a menudo se asocian con una operación fallida. Las operaciones pueden fallar debido a desbordamientos de búfer, permisos inválidos, claves de acceso a memoria incorrectas, fallos de enrutamiento de red, problemas de alcance de red, etc.

Los errores asíncronos se reportan utilizando struct fi_eq_err_entry, como se define a continuación. El descriptor de fabric (fid) asociado con el error se proporciona como parte de los datos del error. También hay disponible un código de error para determinar la causa del error.

fi_eq_sread

La llamada fi_eq_sread es el equivalente bloqueante (o síncrono) a fi_eq_read. Se comporta de manera similar a la llamada no bloqueante, con la excepción de que las llamadas no regresarán hasta que se lea un evento de la EQ o ocurra un error o un tiempo de espera. Especificar un tiempo de espera negativo significa un tiempo de espera infinito.

Los hilos que se bloquean en esta función regresarán al llamador si son señalados por alguna fuente externa. Esto es cierto incluso si el tiempo de espera no ha ocurrido o se especificó como infinito.

Es inválido que las aplicaciones llamen a esta función si la EQ se ha configurado con un objeto de espera de FI_WAIT_NONE o FI_WAIT_SET.

fi_eq_readerr

La función de lectura de errores, fi_eq_readerr, recupera información sobre cualquier operación asíncrona que se haya completado con un error inesperado. fi_eq_readerr es una llamada no bloqueante, que regresa inmediatamente si se encontró o no una finalización de error.

Las EQs están optimizadas para informar operaciones que se han completado exitosamente. Las operaciones que fallan se informan "fuera de banda". Dichas operaciones se recuperan utilizando la función fi_eq_readerr. Cuando una operación que se completa con un error inesperado se inserta en una EQ, se coloca en una cola de errores temporal. Intentar leer de una EQ mientras hay un elemento en la cola de errores resulta en una falla FI_EAVAIL. Las aplicaciones pueden usar este código de retorno para determinar cuándo llamar a fi_eq_readerr.

La información del error se informa al usuario a través de struct fi_eq_err_entry. El formato de esta estructura se define a continuación.

struct fi_eq_err_entry {
    fid_t            fid;        /* fid asociado con el error */
    void            *context;    /* contexto de la operación */
    uint64_t         data;       /* datos específicos de la finalización */
    int              err;        /* código de error positivo */
    int              prov_errno; /* código de error del proveedor */
    void            *err_data;   /* datos de error adicionales */
    size_t           err_data_size; /* tamaño de err_data */
};

El fid hará referencia al descriptor de fabric asociado con el evento. Para el registro de memoria, este será el fid_mr, la resolución de direcciones hará referencia a un fid_av, y los eventos CM se referirán a un fid_ep. El campo context se establecerá en el contexto especificado como parte de la operación.

El campo data se establecerá como se describe en la página man del tipo de objeto correspondiente (por ejemplo, consulte fi_av(3) para una descripción de cómo se completan las inserciones asíncronas de vectores de direcciones).

La razón general del error se proporciona a través del campo err. La información de error específica del proveedor u operacional también puede estar disponible a través de los campos prov_errno y err_data. Los usuarios pueden llamar a fi_eq_strerror para convertir la información de error específica del proveedor en una cadena imprimible para fines de depuración.

En la entrada, err_data_size indica el tamaño del búfer err_data en bytes. En la salida, err_data_size se establecerá en el número de bytes copiados al búfer err_data. La información de err_data se usa típicamente con fi_eq_strerror para proporcionar detalles sobre el tipo de error que ocurrió.

Por motivos de compatibilidad, si err_data_size es 0 en la entrada, o si el fabric se abrió con la versión < 1.5, err_data se establecerá en un búfer de datos propiedad del proveedor. El contenido del búfer seguirá siendo válido hasta una llamada de lectura posterior contra la EQ. Las aplicaciones deben serializar el acceso a la EQ al procesar errores para garantizar que el búfer al que se refiere err_data no cambie.

CAMPOS DE EVENTO

Las estructuras de datos de entrada de EQ comparten muchos de los s

campos de nombre. Los significados son los mismos o similares para todos los formatos de estructura EQ, con detalles específicos descritos a continuación.

fid
Esto corresponde al descriptor de fabrica asociado con el evento. El tipo de fid depende del evento que se informa. Para FI_CONNREQ este será el fid del punto de conexión pasivo. FI_CONNECTED y FI_SHUTDOWN harán referencia al punto de conexión activo. FI_MR_COMPLETE y FI_AV_COMPLETE se referirán al descriptor de fabrica MR o AV, respectivamente. FI_JOIN_COMPLETE apuntará al descriptor de multidifusión devuelto como parte de la operación de unión. Las aplicaciones pueden usar el valor fid->context para recuperar el contexto asociado con el descriptor de fabrica.
context
El valor de contexto se establece en el parámetro de contexto especificado con la operación que generó el evento. Si no hay un parámetro de contexto asociado con la operación, este campo será NULL.
data
Data es un valor específico de la operación o un conjunto de bytes. Para eventos de conexión, data son datos de la aplicación intercambiados como parte del protocolo de conexión.
err
Este código err es un errno de fabrica positivo asociado con un evento. El valor err indica la razón general de un error, si ocurrió. Consulte fi_errno.3 para una lista de códigos de error posibles.
prov_errno
En caso de error, prov_errno puede contener un código de error específico del proveedor. El uso de este campo y su significado es específico del proveedor. Está destinado a usarse como una ayuda para la depuración. Consulte fi_eq_strerror para obtener detalles adicionales sobre cómo convertir este valor de error en una cadena legible para humanos.
err_data
En caso de error, err_data puede hacer referencia a una cantidad de datos específica del proveedor asociada con un error. El uso de este campo y su significado es específico del proveedor. Está destinado a usarse como una ayuda para la depuración. Consulte fi_eq_strerror para obtener detalles adicionales sobre cómo convertir estos datos de error en una cadena legible para humanos.
err_data_size
En la entrada, err_data_size indica el tamaño del búfer err_data en bytes. En la salida, err_data_size se establecerá en el número de bytes copiados al búfer err_data. La información err_data se usa típicamente con fi_eq_strerror para proporcionar detalles sobre el tipo de error que ocurrió.

Por compatibilidad, si err_data_size es 0 en la entrada, o la fabrica se abrió con una versión < 1.5, err_data se establecerá en un búfer de datos propiedad del proveedor. El contenido del búfer permanecerá válido hasta una llamada de lectura posterior contra la EQ. Las aplicaciones deben serializar el acceso a la EQ al procesar errores para asegurarse de que el búfer referenciado por err_data no cambie.

NOTAS

Si una cola de eventos se ha desbordado, se colocará en un estado `overrun'. Las operaciones de escritura contra una EQ desbordada fallarán con -FI_EOVERRUN. Las operaciones de lectura continuarán devolviendo cualquier evento válido no corrupto, si está disponible. Después de que se hayan recuperado todos los eventos válidos, cualquier intento de leer la EQ resultará en que devuelva un evento de error FI_EOVERRUN. Las colas de eventos desbordadas se consideran fatales y no pueden usarse para informar eventos adicionales una vez que ocurre el desbordamiento.

VALORES DE RETORNO

fi_eq_open
Devuelve 0 en éxito. En caso de error, se devuelve un valor negativo correspondiente al errno de fabrica.
fi_eq_read / fi_eq_readerr
En éxito, devuelve el número de bytes leídos de la cola de eventos. En caso de error, se devuelve un valor negativo correspondiente al errno de fabrica. Si no hay datos disponibles para leer de la cola de eventos, se devuelve -FI_EAGAIN.
fi_eq_sread
En éxito, devuelve el número de bytes leídos de la cola de eventos. En caso de error, se devuelve un valor negativo correspondiente al errno de fabrica. Si el tiempo de espera expira o el hilo que llama recibe una señal y no hay datos disponibles para leer de la cola de eventos, se devuelve -FI_EAGAIN.
fi_eq_write
En éxito, devuelve el número de bytes escritos en la cola de eventos. En caso de error, se devuelve un valor negativo correspondiente al errno de fabrica.
fi_eq_strerror
Devuelve una interpretación de cadena de caracteres del error específico del proveedor devuelto con una finalización.

Los valores de errno de fabrica están definidos en rdma/fi_errno.h.
