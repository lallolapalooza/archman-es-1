fi_lnx(7) fi_lnx - El proveedor DESCR
NERAL

El proveedor LNX está diseñado para enlazar dos o más proveedores, permitiendo a las aplicaciones usar de forma transparente múltiples proveedores o NICs. Este proveedor utiliza la infraestructura de pares (peer) de libfabric para facilitar el uso de los proveedores subyacentes. Esta versión del proveedor es capaz

de enlazar cualquier proveedor de libfabric que soporte la capacidad FI_PEER.

Capacidades del punto final LNX es una capa de passthrough en la ruta de envío. En la ruta de recepción, LNX utiliza la infraestructura de pares para crear colas de recepción compartidas (SRQ). Las solicitudes de recepción se colocan en la SRQ en lugar de en la cola de recepción del proveedor principal. Cuando el proveedor recibe un mensaje, consulta la SRQ para buscar una coincidencia. Si se encuentra una, la solicitud de recepción se completa; de lo contrario, el mensaje se coloca en la cola compartida de mensajes inesperados (SUQ) de LNX. Las solicitudes de recepción posteriores consultan la
SUQ buscando coincidencias. La primera versión del proveedor solo soporta operaciones etiquetadas (tagged). Otros tipos de mensajes serán soportados en versiones futuras.
Modo
s
El proveedor no requiere el uso de ningún bit de
modo.
Progr
eso
LNX utiliza la infraestructura de pares para proporcionar una cola de finalización compartida. Cada proveedor enlazado aún necesita manejar su propio progreso. Sin embargo, los eventos de finalización se colocarán en la cola de finalización compartida, la cual se pasa a la aplicación
para su acceso.
Formato de
dirección
LNX envuelve las direcciones de los proveedores enlazados en un único blob binario común. No altera ni cambia el formato de dirección de los proveedores enlazados. Los envuelve en una estructura LNX que luego se aplana y se devuelve a la aplicación. Esto se pasa entre diferentes nodos. El proveedor LNX es capaz de analizar el formato aplanado y operar sobre los diferentes enlaces. Esto asume que los nodos en el mismo grupo están todos usando la misma versión del proveedor con exactamente los mismos enlaces. Es decir: no se puede tener un nodo enlazando shm+cxi mientras otro enlaza
shm+rxm.
Operaciones de
mensajes
LNX está diseñado para interceptar operaciones de mensajes como fi_tsenddata y reenviar la operación al proveedor apropiado basándose en criterios específicos. LNX puede enlazar cualquier proveedor que soporte la capacidad FI_PEER. El proveedor SHM es un caso especial en el sentido de que siempre se usa para la comunicación intra-nodo si forma parte del enlace. De lo contrario, todos los demás proveedores en el enlace se usan en round
robin.
Uso del
proveedor
Para usar el proveedor, el usuario necesita establecer la variable de entorno FI_LNX_PROV_LINKS con los proveedores a enlazar; ver la sintaxis bajo la descripción de la variable. Esto permite la definición de múltiples enlaces. Cada enlace define el proveedor a añadir al enlace junto con una lista explícita de dominios. Si solo se especifica el nombre del proveedor, todos los dominios se añaden al enlace. El proveedor devuelve la lista de enlaces especificados a la aplicación en la llamada a fi_getinfo(). Dado que puede haber múltiples proveedores en el enlace, el primer dominio del primer proveedor no-shm fi_info se usa como la información del enlace. Esto significa que si un enlace se define como sigue: - shm+cxi:cxi0,cxi1 La información fi_info de cxi0 se usa como el fi_info del enlace con la modificación de los nombres de proveedor y dominio. Esto es importante ya que la información PCI forma parte del fi_info y algunas aplicaciones podrían usar la información PCI para decidir qué enlace usar. Un criterio de selección común es la interfaz más cercana al núcleo al que el proceso está vinculado. Para hacer esta determinación, la aplicación requiere la información PCI de la
interfaz
LIMITACIONES Y TRABAJO
FUTURO
Soport
e de
ha
rdware

LNX no soporta descarga de hardware; ej. emparejamiento de etiquetas por hardware. Esta es una limitación inherente al usar la infraestructura de pares. Debido al uso de una cola de recepción compartida que los proveedores enlazados necesitan consultar cuando se recibe un mensaje, cualquier descarga de hardware que requiera enviar los búfers de recepción directamente al hardware no funcionará con la cola de recepción compartida. La cola de recepción compartida proporciona dos ventajas; 1) reducir el uso de memoria, 2) coordinar las operaciones de recepción. Para #2 esto es necesario al recibir de FI_ADDR_UNSPEC. En este caso, ambos proveedores que forman parte del enlace pueden competir para obtener acceso al búfer de recepción. Es un trabajo futuro determinar una forma de usar el emparejamiento de etiquetas por hardware y otras capacidades

de descarga de hardware con LNX
Registro de
memoria
Como parte de la operación de registro de memoria, hardware variado puede realizar pasos específicos del hardware como el anclaje (pinning) de memoria. Debido a que las APIs de registro de memoria no especifican las direcciones de origen o destino, no es posible para LNX determinar a qué proveedor reenviar el registro de memoria. Por lo tanto, LNX registra la memoria con todos los proveedores enlazados. Esto podría no ser eficiente y podría tener efectos secundarios imprevistos. Se necesita un método mejor para soportar el registro de memoria. Una opción es tener una caché de registro de memoria en lnx para evitar operaciones
costosas.
Tipos de
operación
Esta versión de LNX soporta solo operaciones etiquetadas. Versiones futuras expandirán el soporte a otros tipos de
operaciones.
Multi-Rai
l
LNX implementa una función multi-rail que permite que los mensajes se transmitan a través de múltiples interfaces, impulsadas por la configuración del enlace. Soporta la configuración de múltiples dominios de proveedores dentro de un solo enlace. Por ejemplo, la siguiente configuración: FI_LNX_PROV_LINKS=“cxi:cxi0,cxi1” Define un enlace que incluye los dominios cxi0 y cxi1. Cuando una aplicación utiliza este enlace, los mensajes se distribuyen de forma round-robin a través de ambos dominios. De manera similar, todas las direcciones de pares disponibles se usan de forma round-robin, asegurando una comunicación equilibrada. Se aplica una excepción al proveedor shm: si está incluido en el enlace, todo el tráfico intra-nodo se enruta a través del proveedor shm. Para la siguiente configuración: FI_LNX_PROV_LINKS=“tcp;ofi_rxm+cxi:cxi0” El enlace consiste de todos los dominios tcp asociados con el proveedor tcp;ofi_rxm, junto con cxi0. Los mensajes se distribuyen uniformemente a través de todos los puntos finales de dominio y direcciones de pares. El proveedor asegura que los tipos de puntos finales locales coincidan con las direcciones remotas correspondientes—por ejemplo, si se usa el proveedor tcp, los mensajes se
dirigen a la dirección tcp del par.

LNX verifica las siguientes variables de entorno: FI_LNX_PROV_LINK

S
Esta variable de entorno se usa para especificar qué proveedores enlazar. Esta debe establecerse para que el proveedor LNX devuelva una lista de bloques fi_info en la llamada a fi_getinfo(). El formato que debe
usarse es: enlace ::= grupo [`|' grupo]
grupo ::= proveedor [`+' proveedor [`:' lista_de_proveedores]] lista_de_proveedores ::= proveedor [`,' proveedor] proveedor ::= [a-zA-Z0-9_]+ Ejemplos: - shm+cxi:cxi0 - shm+cxi:cxi0,cxi1 - shm+cxi:cxi0|shm+cxi:cxi1 - shm+cxi En un sistema con cuatro dominios cxi, el último ejemplo es equivalente a: - shm+cxi:cxi0,cxi1,cxi2,
cxi3
FI_LNX_DISABLE_
SHM
Por defecto, esta variable de entorno está establecida en 0. Sin embargo, el usuario puede establecerla
en uno y entonces el proveedor SHM no será usado. Esto puede ser útil para depuración y análisis de re
ndimiento. El proveedor SHM será usado naturalmente para todas las operaciones intra-nodo. Por lo tanto
, para probar SHM de forma aislada con LNX, los procesos pueden limitarse al mismo nodo únicamente.
