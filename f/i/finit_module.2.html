init_module(2) Manual de llamadas al sistema init_module(2)

NOMBRE

init_module, finit_module - cargar un módulo del kernel

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <linux/module.h>    /* Definición de constantes MODULE_* */
#include <sys/syscall.h>     /* Definición de constantes SYS_* */
#include <unistd.h>
int syscall(unsigned long size;
            SYS_init_module,
            void imagen_modulo[size], unsigned long size,
            const char *valores_param);
int syscall(SYS_finit_module, int fd,
            const char *valores_param, int flags);

Nota: glibc no proporciona envoltorios para estas llamadas al sistema, haciendo necesario el uso de syscall(2).

DESCRIPCIÓN

init_module() carga una imagen ELF en el espacio del kernel, realiza las reubicaciones de símbolos necesarias, inicializa los parámetros del módulo con los valores proporcionados por el llamador, y luego ejecuta la función init del módulo. Esta llamada al sistema requiere privilegio.

El argumento imagen_modulo apunta a un búfer que contiene la imagen binaria a cargar; size especifica el tamaño de ese búfer. La imagen del módulo debe ser una imagen ELF válida, compilada para el kernel en ejecución.

El argumento valores_param es una cadena que contiene especificaciones separadas por espacios de los valores para los parámetros del módulo (definidos dentro del módulo usando module_param() y module_param_array()). El kernel analiza esta cadena e inicializa los parámetros especificados. Cada una de las especificaciones de parámetros tiene el formato:

nombre[=valor[,valor...]]

El nombre del parámetro es uno de los definidos dentro del módulo usando module_param() (ver el archivo fuente del kernel Linux include/linux/moduleparam.h). El valor del parámetro es opcional en el caso de parámetros bool e invbool. Los valores para parámetros de tipo array se especifican como una lista separada por comas.

finit_module()

La llamada al sistema finit_module() es similar a init_module(), pero lee el módulo a cargar desde el descriptor de archivo fd. Es útil cuando la autenticidad de un módulo del kernel puede determinarse por su ubicación en el sistema de archivos; en casos donde esto es posible, se puede evitar la sobrecarga de usar módulos firmados criptográficamente para determinar la autenticidad de un módulo. El argumento valores_param es el mismo que para init_module().

El argumento flags modifica el funcionamiento de finit_module(). Es un valor de máscara de bits creado combinando con OR cero o más de las siguientes banderas:

MODULE_INIT_IGNORE_MODVERSIONS
Ignorar hashes de versiones de símbolos.
MODULE_INIT_IGNORE_VERMAGIC
Ignorar la magia de la versión del kernel.
MODULE_INIT_COMPRESSED_FILE (desde Linux 5.17)
Usar descompresión de módulos en el kernel.

Existen algunas comprobaciones de seguridad integradas en un módulo para asegurar que coincide con el kernel contra el cual se está cargando. Estas comprobaciones se registran cuando se compila el módulo y se verifican cuando se carga el módulo. Primero, el módulo registra una cadena de "vermagic" que contiene el número de versión del kernel y las características prominentes (como el tipo de CPU). Segundo, si el módulo se compiló con la opción de configuración CONFIG_MODVERSIONS habilitada, se registra un hash de versión para cada símbolo que el módulo utiliza. Este hash se basa en los tipos de los argumentos y el valor de retorno de la función nombrada por el símbolo. En este caso, el número de versión del kernel dentro de la cadena "vermagic" se ignora, ya que se asume que los hashes de versión de símbolos son suficientemente fiables.

Usar la bandera MODULE_INIT_IGNORE_VERMAGIC indica que la cadena "vermagic" será ignorada, y la bandera MODULE_INIT_IGNORE_MODVERSIONS indica que los hashes de versión de símbolos serán ignorados. Si el kernel se compiló para permitir la carga forzada (es decir, configurado con CONFIG_MODULE_FORCE_LOAD), la carga continúa, de lo contrario falla con el error ENOEXEC como se espera para módulos malformados.

Si el kernel se compiló con CONFIG_MODULE_DECOMPRESS, se puede usar la función de descompresión en el kernel. El código del espacio de usuario puede verificar si el kernel soporta la descompresión leyendo el atributo /sys/module/compression. Si el kernel soporta la descompresión, el archivo comprimido puede pasarse directamente a finit_module() usando la bandera MODULE_INIT_COMPRESSED_FILE. El descompresor de módulos en el kernel soporta los siguientes algoritmos de compresión:

•
gzip (desde Linux 5.17)
•
xz (desde Linux 5.17)
•
zstd (desde Linux 6.2)

El kernel solo implementa un único método de descompresión. Este se selecciona durante la generación del módulo de acuerdo con el método de compresión elegido en la configuración del kernel.

VALOR DE RETORNO

En caso de éxito, estas llamadas al sistema devuelven 0. En caso de error, devuelven -1 y errno se establece para indicar el error.

ERRORES

EBADMSG (desde Linux 3.7)
La firma del módulo tiene un formato incorrecto.
EBUSY
Tiempo de espera agotado al intentar resolver una referencia de símbolo de este módulo.
EFAULT
Un argumento de dirección se refería a una ubicación que está fuera del espacio de direcciones accesible del proceso.
ENOKEY (desde Linux 3.7)
La firma del módulo es inválida o el kernel no tiene una clave para este módulo. Este error solo se devuelve si el kernel se compiló con CONFIG_MODULE_SIG_FORCE; si el kernel no se compiló con esta opción, un módulo inválido o sin firmar simplemente contamina el kernel.
ENOMEM
Sin memoria.
EPERM
El llamador no tenía privilegios (no tenía la capacidad CAP_SYS_MODULE), o la carga de módulos está deshabilitada (ver /proc/sys/kernel/modules_disabled en proc(5)).

Los siguientes errores pueden ocurrir adicionalmente para init_module():

EEXIST
Ya hay un módulo con este nombre cargado.
EINVAL
valores_param es inválido, o alguna parte de la imagen ELF en imagen_modulo contiene inconsistencias.
ENOEXEC
La imagen binaria proporcionada en imagen_modulo no es una imagen ELF, o es una imagen ELF que es inválida o para una arquitectura diferente.

Los siguientes errores pueden ocurrir adicionalmente para finit_module():

EBADF
El archivo al que se refiere fd no está abierto para lectura.
EFBIG
El archivo al que se refiere fd es demasiado grande.
EINVAL
flags es inválido.
EINVAL
Las comprobaciones de integridad del descompresor fallaron, al cargar un módulo comprimido con la bandera MODULE_INIT_COMPRESSED_FILE establecida.
ENOEXEC
fd no se refiere a un archivo abierto.
EOPNOTSUPP (desde Linux 5.17)
La bandera MODULE_INIT_COMPRESSED_FILE está establecida para cargar un módulo comprimido, y el kernel se compiló sin CONFIG_MODULE_DECOMPRESS.

La llamada al sistema init_module() no es soportada por glibc. No se proporciona ninguna declaración en los encabezados de glibc, pero, a través de una peculiaridad de la historia, las versiones de glibc anteriores a glibc 2.23 sí exportaban una ABI para esta llamada al sistema. Por lo tanto, para emplear esta llamada al sistema, es (antes de glibc 2.23) suficiente declarar manualmente la interfaz en su código; alternativamente, puede invocar la llamada al sistema utilizando syscall

(2).

Linux 2.4 y

anteriores

En Linux 2.4 y anteriores, la llamada al sistema init_module() era bastante

diferente:

#include <linux/module.

h>

int init_module(const char *name, struct module *image)

;

(Las aplicaciones de espacio de usuario pueden detectar qué versión de init_module() está disponible llamando a query_module(); la última llamada falla con el error ENOSYS en Linux 2.6 y posteriores.

)

La versión antigua de la llamada al sistema carga la imagen del módulo reubicado a la que apunta image en el espacio del kernel y ejecuta la función init del módulo. El llamador es responsable de proporcionar la imagen reubicada (desde Linux 2.6, la llamada al sistema init_module() realiza la reubicación)

.

La imagen del módulo comienza con una estructura de módulo y es seguida por código y datos según corresponda. Desde Linux 2.2, la estructura del módulo se define de la siguiente

manera: 


struct module {
    unsigned long         size_of_struct;
    struct module        *next;
    const char           *name;
    unsigned long         size;
    long                  usecount;
    unsigned long         flags;
    unsigned int          nsyms;
    unsigned int          ndeps;
    struct module_symbol *syms;
    struct module_ref    *deps;
    struct module_ref    *refs;
    typeof(int (void))   *init;
    typeof(void (void))  *cleanup;
    const struct exception_table_entry *ex_table_start;
    const struct exception_table_entry *ex_table_end;
#ifdef __alpha__
    unsigned long gp;
#endif
}
;

Se espera que todos los campos de puntero, con la excepción de next y refs, apunten dentro del cuerpo del módulo y estén inicializados

según corresponda para el esp
acio del kernel, es decir, reubic
ados con el resto del módulo.
