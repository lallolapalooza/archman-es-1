DESCRIPCIÓN

Las colas de eventos (EQ) se utilizan para informar a las aplicaciones sobre eventos asíncronos y completadas de operaciones. Las EQs son uno de los constructores más fundamentales de la API de Fabric Interface (FI) y se utilizan en conjunción con otros objetos FI, como los puntos de conexión (endpoints), las colas de finalización (completion queues) y los objetos de memoria.

La función `fi_eq_control` se utiliza para consultar o modificar los atributos o el comportamiento de una cola de eventos. Esta función puede ser invocada, ya que puede redirigir la implementación de las operaciones EQ. Los siguientes comandos de control son utilizables con una EQ.

FI_GETWAIT (void **)
Este comando permite al usuario recuperar el objeto de espera de bajo nivel asociado con la EQ. El formato del objeto de espera se especifica durante la creación de la EQ, a través de los atributos de la EQ. El parámetro `fi_control arg` debe ser una dirección donde se escribirá un puntero al objeto de espera devuelto. Debe ser un `int *` para FI_WAIT_FD, o `struct fi_mutex_cond` para FI_WAIT_MUTEX_COND (obsoleto).
struct fi_mutex_cond {
    pthread_mutex_t     *mutex;
    pthread_cond_t      *cond;
};

fi_eq_read

La operación `fi_eq_read` realiza una lectura no bloqueante de los datos del evento desde la EQ. El formato de los datos del evento se basa en el tipo de evento recuperado de la EQ, con todos los eventos comenzando con una cabecera `struct fi_eq_entry`. Como máximo, se devolverá un evento por operación de lectura de EQ. El número de bytes leídos correctamente de la EQ se devuelve en la lectura. El flag FI_PEEK puede usarse para indicar que los datos del evento deben leerse de la EQ sin ser consumidos. Una lectura posterior sin el flag FI_PEEK eliminaría entonces el evento de la EQ.

Los siguientes tipos de eventos pueden ser reportados a una EQ, junto con información sobre el formato asociado a cada evento.

Operaciones de Control Asíncronas
Las operaciones de control asíncronas son solicitudes básicas que simplemente necesitan generar un evento para indicar que se han completado. Estas incluyen los siguientes tipos de eventos: registro de memoria, resolución de vectores de direcciones y uniones multicast.

Las solicitudes de control informan su finalización insertando una `struct fi_eq_entry` en la EQ. El formato de esta estructura es:

struct fi_eq_entry {
    fid_t            fid;        /* fid asociado con la solicitud */
    void            *context;    /* contexto de la operación */
    uint64_t         data;       /* datos específicos de la finalización */
};

Para la finalización de operaciones de control asíncronas básicas, el evento devuelto indicará la operación que se ha completado, y el `fid` hará referencia al descriptor de fabric asociado con el evento. Para el registro de memoria, este será un evento FI_MR_COMPLETE y el `fid_mr`. La resolución de direcciones hará referencia a un evento FI_AV_COMPLETE y `fid_av`. Las uniones multicast informarán un FI_JOIN_COMPLETE y `fid_mc`. El campo `context` se establecerá en el contexto especificado como parte de la operación, si está disponible, de lo contrario, el contexto se asociará con el descriptor de fabric. El campo `data` se establecerá como se describe en la página man para el tipo de objeto correspondiente (por ejemplo, ver `fi_av(3)` para una descripción de cómo se completan las inserciones de vectores de direcciones asíncronas).

Notificación de Conexión
Las notificaciones de conexión son notificaciones de gestión de conexión utilizadas para establecer o cerrar conexiones entre puntos de conexión. Hay tres eventos de notificación de conexión: FI_CONNREQ, FI_CONNECTED y FI_SHUTDOWN. Las notificaciones de conexión se informan utilizando `struct fi_eq_cm_entry`:
struct fi_eq_cm_entry {
    fid_t            fid;        /* fid asociado con la solicitud */
    struct fi_info  *info;       /* información del punto de conexión */
    uint8_t         data[];     /* datos de conexión de la aplicación */
};

Un evento de solicitud de conexión (FI_CONNREQ) indica que un punto de conexión remoto desea establecer una nueva conexión a un punto de conexión pasivo o en escucha. El `fid` es el punto de conexión pasivo. La información sobre las capacidades y atributos del punto de conexión activo solicitado está disponible en el campo `info`. La aplicación es responsable de liberar esta estructura llamando a `fi_freeinfo` cuando ya no sea necesaria. El campo `connreq` de `fi_info` hará referencia a la solicitud de conexión asociada con este evento. Para aceptar una conexión, un punto de conexión debe crearse primero pasando una estructura `fi_info` que haga referencia a este campo `connreq` a `fi_endpoint()`. Este punto de conexión se pasa luego a `fi_accept()` para completar la aceptación del intento de conexión. Crear el punto de conexión se logra más fácilmente pasando la `fi_info` devuelta como parte del evento CM a `fi_endpoint()`. Si la conexión va a ser rechazada, el `connreq` se pasa a `fi_reject()`.

Cualquier dato de aplicación intercambiado como parte de la solicitud de conexión se coloca después de la estructura `fi_eq_cm_entry`. La cantidad de datos disponibles depende de la aplicación y está limitada al espacio de buffer proporcionado por la aplicación cuando se llama a `fi_eq_read`. La cantidad de datos devueltos puede calcularse utilizando el valor de retorno de `fi_eq_read`. Tenga en cuenta que la cantidad de datos devueltos está limitada por el protocolo de conexión subyacente, y la longitud de cualquier dato devuelto puede incluir relleno de protocolo. Como resultado, la longitud devuelta puede ser mayor que la especificada por el par de conexión.

Si se ha aceptado una solicitud de conexión, se generará un evento FI_CONNECTED en ambos lados de la conexión. El lado activo — el que llamó a `fi_connect()` — puede recibir datos de usuario como parte del evento FI_CONNECTED. Los datos de usuario se pasan al gestor de conexión en el lado pasivo a través de la llamada `fi_accept`. Los datos de usuario no se proporcionan con un evento FI_CONNECTED en el lado de escucha de la conexión.

La notificación de que un par remoto se ha desconectado de un punto de conexión activo se realiza a través del evento FI_SHUTDOWN. La notificación de cierre utiliza `struct fi_eq_cm_entry` como se declara anteriormente. El campo `fid` para una notificación de cierre se refiere al `fid_ep` del punto de conexión activo.

Notificación Asíncrona de Errores
Los errores asíncronos se utilizan para informar problemas con los recursos de fabric. Los errores reportados pueden ser fatales o transitorios, según el error, y resultan en que el recurso quede deshabilitado. Los recursos deshabilitados harán que fallen las operaciones enviadas contra ellos hasta que sean explícitamente re-habilitados por la aplicación.

Los errores asíncronos pueden ser reportados para colas de finalización y puntos de conexión de todos los tipos. Los errores de CQ pueden ocurrir cuando la gestión de recursos ha sido deshabilitada, y el proveedor ha detectado un desbordamiento de cola. Los errores de punto de conexión pueden ser el resultado de numerosas acciones, pero a menudo están asociados con una operación fallida. Las operaciones pueden fallar debido a desbordamientos de buffer, permisos inválidos, claves de acceso a memoria incorrectas, fallos de enrutamiento de red, problemas de alcanzabilidad de red, etc.

Los errores asíncronos se reportan utilizando `struct fi_eq_err_entry`, como se define a continuación. El descriptor de fabric (`fid`) asociado con el error se proporciona como parte de los datos del error. Un código de error también está disponible para determinar la causa del error.

fi_eq_sread

La llamada `fi_eq_sread` es el equivalente bloqueante (o síncrono) a `fi_eq_read`. Se comporta de manera similar a la llamada no bloqueante, con la excepción de que las llamadas no se devolverán hasta que se lea un evento de la EQ o ocurra un error o un tiempo de espera agotado. Especificar un tiempo de espera negativo significa un tiempo de espera infinito.

Los hilos que se bloquean en esta función volverán al llamador si son señalizados por alguna fuente externa. Esto es cierto incluso si el tiempo de espera no ha ocurrido o se especificó como infinito.

Es inválido para las aplicaciones llamar a esta función si la EQ ha sido configurada con un objeto de espera de FI_WAIT_NONE o FI_WAIT_SET.

fi_eq_readerr

La función de lectura de errores, `fi_eq_readerr`, recupera información sobre cualquier operación asíncrona que se haya completado con un error inesperado. `fi_eq_readerr` es una llamada no bloqueante, que devuelve inmediatamente si se encontró o no una finalización de error.

Las EQs están optimizadas para informar operaciones que se han completado con éxito. Las operaciones que fallan se informan "fuera de banda". Dichas operaciones se recuperan utilizando la función `fi_eq_readerr`. Cuando una operación que se completa con un error inesperado se inserta en una EQ, se coloca en una cola de errores temporal. Intentar leer de una EQ mientras hay un elemento en la cola de errores resulta en un fallo FI_EAVAIL. Las aplicaciones pueden usar este código de retorno para determinar cuándo llamar a `fi_eq_readerr`.

La información de error se reporta al usuario a través de `struct fi_eq_err_entry`. El formato de esta estructura se define a continuación.

struct fi_eq_err_entry {
    fid_t            fid;        /* fid asociado con el error */
    void            *context;    /* contexto de la operación */
    uint64_t         data;       /* datos específicos de la finalización */
    int              err;        /* código de error positivo */
    int              prov_errno; /* código de error del proveedor */
    void            *err_data;   /* datos adicionales del error */
    size_t           err_data_size; /* tamaño de err_data */
};

El `fid` hará referencia al descriptor de fabric asociado con el evento. Para el registro de memoria, este será el `fid_mr`, la resolución de direcciones hará referencia a un `fid_av`, y los eventos CM se referirán a un `fid_ep`. El campo `context` se establecerá en el contexto especificado como parte de la operación.

El campo `data` se establecerá como se describe en la página man para el tipo de objeto correspondiente (por ejemplo, ver `fi_av(3)` para una descripción de cómo se completan las inserciones de vectores de direcciones asíncronas).

La razón general del error se proporciona a través del campo `err`. La información de error específica del proveedor u operacional también puede estar disponible a través de los campos `prov_errno` y `err_data`. Los usuarios pueden llamar a `fi_eq_strerror` para convertir la información de error específica del proveedor en una cadena imprimible para fines de depuración.

En la entrada, `err_data_size` indica el tamaño del buffer `err_data` en bytes. En la salida, `err_data_size` se establecerá en el número de bytes copiados al buffer `err_data`. La información `err_data` se utiliza típicamente con `fi_eq_strerror` para proporcionar detalles sobre el tipo de error que ocurrió.

Por motivos de compatibilidad, si `err_data_size` es 0 en la entrada, o la fabric se abrió con una versión < 1.5, `err_data` se establecerá en un buffer de datos propiedad del proveedor. El contenido del buffer permanecerá válido hasta la siguiente llamada de lectura contra la EQ. Las aplicaciones deben serializar el acceso a la EQ al procesar errores para garantizar que el buffer al que hace referencia `err_data` no cambie.
