fileevent(n) Comandos integrados de Tcl fileevent(n)

NOMBRE

fileevent - Ejecutar un script cuando un canal se vuelve legible o escribible

SINOPSIS

fileevent channelId readable ?script?

fileevent channelId writable ?script?

DESCRIPCIÓN

Este comando se utiliza para crear manejadores de eventos de archivo. Un manejador de eventos de archivo es una asociación entre un canal y un script, de modo que el script se evalúa cada vez que el canal se vuelve legible o escribible. Los manejadores de eventos de archivo se usan más comúnmente para permitir que los datos se reciban de otro proceso de manera dirigida por eventos, de modo que el receptor pueda continuar interactuando con el usuario mientras espera a que lleguen los datos. Si una aplicación invoca gets o read en un canal bloqueante cuando no hay datos de entrada disponibles, el proceso se bloqueará; hasta que lleguen los datos de entrada, no podrá atender otros eventos, por lo que parecerá al usuario que se “congela”. Con fileevent, el proceso puede saber cuándo están presentes los datos e invocar gets o read solo cuando no se bloquearán.

El argumento channelId de fileevent se refiere a un canal abierto como un canal estándar de Tcl (stdin, stdouto stderr), el valor de retorno de una invocación de open o socket, o el resultado de un comando de creación de canal proporcionado por una extensión de Tcl.

Si se especifica el argumento script , entonces fileevent crea un nuevo manejador de eventos: script se evaluará cada vez que el canal se vuelva legible o escribible (dependiendo del segundo argumento de fileevent). En este caso, fileevent devuelve una cadena vacía. Los manejadores de eventos readable y writable de un archivo son independientes y pueden crearse y eliminarse por separado. Sin embargo, puede haber como máximo un manejador readable y uno writable para un archivo en un momento dado en un intérprete dado. Si se llama a fileevent cuando el manejador especificado ya existe en el intérprete que invoca, el nuevo script reemplaza al antiguo.

Si no se especifica el argumento script , fileevent devuelve el script actual para channelId, o una cadena vacía si no hay ninguno. Si el argumento script se especifica como una cadena vacía, entonces el manejador de eventos se elimina, de modo que no se invocará ningún script. Un manejador de eventos de archivo también se elimina automáticamente cada vez que su canal se cierra o su intérprete se elimina.

Un canal se considera legible si hay datos sin leer disponibles en el dispositivo subyacente. Un canal también se considera legible si hay datos sin leer en un búfer de entrada, excepto en el caso especial en el que el intento más reciente de leer del canal fue una llamada a gets que no pudo encontrar una línea completa en el búfer de entrada. Esta característica permite leer un archivo una línea a la vez en modo no bloqueante usando eventos. Un canal también se considera legible si hay una condición de fin de archivo o error presente en el archivo o dispositivo subyacente. Es importante que script verifique estas condiciones y las maneje adecuadamente; por ejemplo, si no hay una verificación especial para el fin de archivo, puede ocurrir un bucle infinito donde script no lee datos, retorna y se invoca inmediatamente de nuevo.

Un canal se considera escribible si al menos un byte de datos puede escribirse en el archivo o dispositivo subyacente sin bloquearse, o si hay una condición de error presente en el archivo o dispositivo subyacente.

La E/S dirigida por eventos funciona mejor para canales que se han colocado en modo no bloqueante con el comando fconfigure . En modo bloqueante, un comando puts puede bloquearse si le das más datos de los que el archivo o dispositivo subyacente puede aceptar, y un comando gets o read se bloqueará si intentas leer más datos de los que están listos; un archivo o dispositivo subyacente legible puede no garantizar incluso que un [read 1] bloqueante tenga éxito (contraejemplos siendo codificaciones multibyte, transformaciones de compresión o cifrado). En todos estos casos, no se procesarán eventos mientras los comandos estén bloqueados.

En modo no bloqueante, puts, ready gets nunca se bloquean. Consulte la documentación de los comandos individuales para obtener información sobre cómo manejan los canales bloqueantes y no bloqueantes.

La prueba de la condición de fin de archivo debe hacerse después de cualquier intento de leer los datos del canal. La bandera eof se establece una vez que ha ocurrido un intento de leer el final de los datos, y probar antes de esta lectura requerirá que se dispare un evento adicional.

El script para un evento de archivo se ejecuta a nivel global (fuera del contexto de cualquier procedimiento de Tcl) en el intérprete en el que se invocó el comando fileevent . Si ocurre un error mientras se ejecuta el script, se usa el comando registrado con interp bgerror para informar el error. Además, el manejador de eventos de archivo se elimina si alguna vez retorna un error; esto se hace para prevenir bucles infinitos debido a manejadores defectuosos.

EJEMPLO

En esta configuración, GetData será llamado con el canal como argumento cada vez que $chan se vuelva legible. La llamada a read leerá cualquier dato binario que esté actualmente disponible sin bloquearse. Aquí, el archivo fileevent se elimina cuando ocurre un fin de archivo para evitar ser llamado continuamente (ver arriba). Alternativamente, el canal puede cerrarse en esta condición.

proc GetData {chan} {
    set data [read $chan]
    puts "[string length $data] $data"
    if {[eof $chan]} {
        fileevent $chan readable {}
    }
}
fconfigure $chan -blocking 0 -translation binary
fileevent $chan readable [list GetData $chan]

El siguiente ejemplo demuestra el uso de gets para leer datos orientados a líneas.

proc GetData {chan} {
    if {[gets $chan line] >= 0} {
        puts $line
    }
    if {[eof $chan]} {
        close $chan
    }
}
fconfigure $chan -blocking 0 -buffering line -translation crlf
fileevent $chan readable [list GetData $chan]
