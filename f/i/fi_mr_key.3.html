DESCRIPCIÓ

N

Las regiones de memoria registradas asocian búferes de memoria con permisos otorgados para el acceso por recursos de la fabrica. Un búfer de memoria debe registrarse con un dominio de recursos antes de poder usarse como destino de una transferencia de datos RMA o atómica remota. Además, un proveedor de fabrica puede requerir que los búferes de datos se registren antes de usarse en transferencias locales. Las restricciones de registro de memoria se controlan mediante un conjunto separado de bits de modo, especificados a través de los atributos del dominio (campo mr_mode). Cada bit mr_mode requiere que la aplicación tome pasos específicos para usar búferes de memoria con las interfaces de

libfabric.

Como caso especial, una nueva región de memoria puede crearse a partir de una región de memoria existente. Tal nueva región de memoria se denomina sub-MR, y la región de memoria existente se denomina MR base. Las sub-MR pueden usarse para compartir recursos de hardware, como traducciones de direcciones virtuales a físicas y fijación de páginas. Esto puede mejorar el rendimiento al crear y destruir subregiones que requieren diferentes permisos de acceso. La MR base misma también puede ser una sub-MR, permitiendo una jerarquía de regiones de

memoria.

Lo siguiente se aplica al registro de

memoria.
Registro de memoria
predeterminado
Si no se establecen bits mr_mode, se siguen los comportamientos predeterminados descritos a continuación. Históricam
ente, estos valores predeterminados se denominaban colectivamente registro de memoria escalable. Los requisitos pred
eterminados se describen a continuación, seguidos de definiciones de cómo cada bit mr_mode altera la definición.

Compatibilidad: Para las versiones de la biblioteca 1.4 y anteriores, esto se indicaba estableciendo mr_mode en FI_MR_SCALABLE y el bit de modo fi_info FI_LOCAL_MR en 0. FI_MR_SCALABLE y FI_LOCAL_MR fueron obsoletos en la versión 1.5 de libfabric, aunque se admiten con fines de compatibilidad hacia

atrás.

Por seguridad, se requiere registro de memoria para los búferes de datos a los que accede directamente un proceso par. Por ejemplo, se requiere registro para los búferes de destino RMA (leídos o escritos), y aquellos a los que acceden operaciones atómicas o

colectivas.

Por defecto, el registro ocurre en rangos de direcciones virtuales. Debido a que el registro se refiere a rangos de direcciones, en lugar de búferes de datos asignados, los rangos de direcciones no necesitan mapearse a búferes de datos asignados por la aplicación en el momento en que se realiza la llamada de registro. Es decir, una aplicación puede registrar cualquier rango de direcciones en su espacio de direcciones virtuales, independientemente de si esas direcciones están respaldadas por páginas físicas o han sido

asignadas.

Tenga en cuenta que las páginas físicas deben respaldar las direcciones antes de que las direcciones sean accedidas como parte de una operación de transferencia de datos, o las transferencias de datos fallarán. Además, dependiendo de la operación, esto podría resultar en que el proceso local reciba una violación de segmentación por acceder a memoria no

válida.

Una vez registradas, las regiones de memoria resultantes son accesibles por los pares comenzando en una dirección base de 0. Es decir, la dirección de destino que se especifica es un desplazamiento en bytes dentro de la región

registrada.

La aplicación también selecciona la clave de acceso asociada con la MR. El tamaño de la clave está restringido a un máximo de 8

bytes.

Con el registro escalable, los búferes de datos accedidos localmente no se registran. Esto incluye búferes de origen para todas las operaciones de transmisión – envíos, envíos etiquetados, RMA y atómicos – así como búferes publicados para operaciones de recepción y recepción

etiquetada.

Aunque el comportamiento predeterminado de registro de memoria es conveniente para los desarrolladores de aplicaciones, es difícil de implementar en hardware. Los intentos de ocultar los requisitos de hardware a la aplicación a menudo resultan en impactos significativos e inaceptables en el rendimiento. Los siguientes bits mr_mode se proporcionan como entrada a fi_getinfo. Si un proveedor requiere el comportamiento definido para un bit mr_mode, dejará el bit establecido en la salida de fi_getinfo. De lo contrario, el proveedor puede limpiar el bit para indicar que el comportamiento no es

necesario.

Al establecer un bit mr_mode, la aplicación ha acordado ajustar su comportamiento como se indica. Es importante que las aplicaciones que elijan admitir un mr_mode estén preparadas para manejar el caso en que el mr_mode no es necesario. Un proveedor limpiará un bit mr_mode si no es

necesario.
FI_MR_LOCAL
Cuando el bit de modo FI_MR_LOCAL está activado, las aplicaciones deben registrar todos los búferes de datos que serán accedidos por el hardware local y proporcionar un parámetro desc válido en las operaciones de transferencia de datos aplicables.

Cuando FI_MR_LOCAL está desactivado, las aplicaciones no están obligadas a registrar búferes de datos antes de usarlos para operaciones locales (por ejemplo, búferes de envío y recepción de datos). Antes de libfabric 1.22, el parámetro desc se ignoraba. En libfabric 1.22 y versiones posteriores, el parámetro desc debe ser válido o NULL. Este comportamiento permite a las aplicaciones pasar opcionalmente un parámetro desc válido. Si el parámetro desc es NULL, el proveedor se encargará de cualquier registro de memoria local requerido.

Un proveedor puede ocultar los requisitos de registro local de las aplicaciones utilizando una caché de registro interna o mecanismos similares. Dichos mecanismos, sin embargo, pueden afectar negativamente el rendimiento de algunas aplicaciones, especialmente aquellas que administran sus propios búferes de red. Para dar soporte a una amplia gama de aplicaciones, sin afectar indebidamente su rendimiento, las aplicaciones que deseen administrar sus propios registros de memoria local pueden hacerlo utilizando las llamadas de registro de memoria y pasando un parámetro desc válido.

Nota: el bit de modo mr FI_MR_LOCAL reemplaza al bit de modo fi_info FI_LOCAL_MR. Cuando FI_MR_LOCAL está activado, se ignora FI_LOCAL_MR.

FI_MR_RAW
Las regiones de memoria crudas se utilizan para soportar proveedores con claves mayores de 64 bits o que requieren configuración en el par. Cuando el bit FI_MR_RAW está activado, las aplicaciones deben usar fi_mr_raw_attr() localmente y fi_mr_map_raw() en el par antes de apuntar a una región de memoria como parte de cualquier solicitud de transferencia de datos.
FI_MR_VIRT_ADDR
El bit FI_MR_VIRT_ADDR indica que el proveedor hace referencia a regiones de memoria por dirección virtual, en lugar de un desplazamiento basado en 0. Los pares que apuntan a regiones de memoria registradas con FI_MR_VIRT_ADDR especifican el búfer de memoria de destino utilizando la dirección virtual del destino, con cualquier desplazamiento dentro de la región especificado como dirección virtual + desplazamiento. El soporte de este bit implica típicamente que los pares deben intercambiar datos de direccionamiento antes de iniciar cualquier operación RMA o atómica.

Para las regiones de memoria que se registran usando FI_MR_DMABUF, la 'dirección virtual' de inicio de la región DMA-buf se obtiene sumando el campo de desplazamiento al campo base_addr de la estructura fi_mr_dmabuf que se especificó a través de la llamada de registro.

FI_MR_ALLOCATED
Cuando está activado, todas las regiones de memoria registradas deben estar respaldadas por páginas de memoria física en el momento en que se realiza la llamada de registro. Además, las aplicaciones no deben realizar operaciones que puedan hacer que el mapeo de dirección virtual a página física cambie (por ejemplo, llamar a free() contra una MR asignada). No cumplir con esto puede hacer que la dirección virtual apunte a un conjunto de páginas físicas mientras que la MR apunta a otro conjunto de páginas físicas.

Cuando está desactivado, las regiones de memoria registradas no necesitan estar respaldadas por páginas de memoria física en el momento en que se realiza la llamada de registro. Además, se permite que el mapeo subyacente de dirección virtual a página física cambie, y el proveedor se asegurará de que la MR correspondiente se actualice en consecuencia. Este comportamiento permite casos de uso de aplicaciones donde la memoria puede liberarse y reasignarse con frecuencia o la memoria del sistema migrar de/hacia la memoria del dispositivo.

Cuando está desactivado, la aplicación es responsable de garantizar que una región de memoria registrada haga referencia a páginas físicas válidas mientras se realiza una transferencia de datos contra ella, o la transferencia de datos puede fallar. Los cambios de la aplicación en el rango de direcciones virtuales deben coordinarse con el tráfico de red hacia o desde ese rango.

Si está desactivado y se soporta FI_HMEM, la capacidad de que el mapeo de dirección virtual a dirección física cambie se extiende también a las interfaces HMEM. Si un proveedor no puede soportar un cambio de mapeo de dirección virtual a dirección física para una interfaz HMEM dada, el proveedor debe soportar una solución de respaldo razonable o la operación debería fallar.

FI_MR_PROV_KEY
Este modo de región de memoria indica que el proveedor no soporta claves de MR solicitadas por la aplicación. Las claves de MR son devueltas por el proveedor. Las aplicaciones que soportan FI_MR_PROV_KEY pueden obtener la clave del proveedor usando fi_mr_key(), a menos que FI_MR_RAW también esté activado. La clave devuelta debe luego intercambiarse con los pares antes de iniciar una operación RMA o atómica.
FI_MR_MMU_NOTIFY
FI_MR_MMU_NOTIFY es típicamente activado por proveedores que soportan el registro de memoria contra regiones de memoria que no necesariamente están respaldadas por páginas físicas asignadas en el momento en que ocurre el registro de memoria. (Es decir, FI_MR_ALLOCATED es típicamente 0). Sin embargo, dichos proveedores requieren que las aplicaciones notifiquen al proveedor antes de que la MR sea accedida como parte de una operación de transferencia de datos. Esta notificación informa al proveedor que todas las páginas físicas necesarias respaldan ahora la región. La notificación es necesaria para proveedores que no pueden conectarse directamente a las tablas de páginas del sistema operativo o a la unidad de gestión de memoria. Ver fi_mr_refresh() para detalles de notificación.
FI_MR_RMA_EVENT
Este bit de modo indica que el proveedor debe configurar las regiones de memoria que están asociadas con eventos RMA antes de su uso. Esto incluye todas las regiones de memoria que están asociadas con contadores de finalización. Cuando está activado, las aplicaciones deben indicar si una región de memoria estará asociada con un contador de finalización como parte de la creación de la región. Esto se hace pasando el flag FI_RMA_EVENT a la llamada de registro de memoria.

Dichas regiones de memoria se crearán en un estado deshabilitado y deben asociarse con todos los contadores de finalización antes de ser habilitadas. Para habilitar una región de memoria, la aplicación debe llamar a fi_mr_enable(). Después de llamar a fi_mr_enable(), no se pueden hacer más enlaces de recursos a la región de memoria.

FI_MR_ENDPOINT
Este bit de modo indica que el proveedor asocia regiones de memoria con puntos de conexión en lugar de dominios. Las regiones de memoria que se registran con el proveedor se crean en un estado deshabilitado y deben enlazarse a un punto de conexión antes de ser habilitadas. Para enlazar la MR con un punto de conexión, la aplicación debe usar fi_mr_bind(). Para habilitar la región de memoria, la aplicación debe llamar a fi_mr_enable().
FI_MR_HMEM
Este bit de modo está asociado con la capacidad FI_HMEM.

Si FI_MR_HMEM está activado, la aplicación debe registrar búferes que fueron asignados usando una llamada de dispositivo y proporcionar un parámetro desc válido en las operaciones de transferencia de datos aplicables, incluso si solo se usan para operaciones locales (por ejemplo, búferes de envío y recepción de datos). La memoria del dispositivo debe registrarse usando la llamada fi_mr_regattr, con los campos iface y device completados.

Si FI_MR_HMEM está desactivado, la aplicación no necesita registrar búferes de dispositivo para operaciones locales. Además, no es necesario usar fi_mr_regattr para el registro de memoria de dispositivo. Es responsabilidad del proveedor descubrir los atributos de registro de memoria de dispositivo apropiados, si corresponde.

Similar a si FI_MR_LOCAL está desactivado, si FI_MR_HMEM está desactivado, las aplicaciones pueden pasar opcionalmente un parámetro desc válido. Si el parámetro desc es NULL, el proveedor se encargará de cualquier registro de memoria local requerido.

Si FI_MR_HMEM está activado, pero FI_MR_LOCAL está desactivado, solo los búferes de dispositivo deben registrarse cuando se usan localmente. En este caso, el parámetro desc pasado a las operaciones de transferencia de datos debe ser válido o NULL. De manera similar, si FI_MR_LOCAL está activado, pero FI_MR_HMEM no, el parámetro desc debe ser válido o NULL.

FI_MR_COLLECTIVE
Este bit está asociado con la capacidad FI_COLLECTIVE.

Si FI_MR_COLLECTIVE está activado, el proveedor requiere que las regiones de memoria utilizadas en operaciones colectivas se registren explícitamente para su uso con llamadas colectivas. Esto requiere registrar las regiones pasadas a las llamadas colectivas usando el flag FI_COLLECTIVE.

Si FI_MR_COLLECTIVE está desactivado, el registro de memoria para operaciones colectivas es opcional. Las aplicaciones pueden pasar opcionalmente un parámetro desc válido. Si el parámetro desc es NULL, el proveedor se encargará de cualquier registro de memoria local requerido.

Registro Básico de Memoria (obsoleto)
El registro básico de memoria fue obsoleto en la versión 1.5 de libfabric, pero se soporta por compatibilidad hacia atrás. El registro básico de memoria se indica estableciendo mr_mode igual a FI_MR_BASIC. FI_MR_BASIC debe establecerse solo y no emparejarse con bits de mr_mode. A diferencia de otros bits de mr_mode, si FI_MR_BASIC se establece en la entrada de fi_getinfo(), no será borrado por el proveedor. Es decir, establecer mr_mode igual a FI_MR_BASIC fuerza el registro básico si el proveedor lo soporta.

El comportamiento del registro básico es equivalente a requerir los siguientes bits de mr_mode: FI_MR_VIRT_ADDR, FI_MR_ALLOCATED y FI_MR_PROV_KEY. Además, los proveedores que soportan el registro básico generalmente requieren el bit de modo fi_info (obsoleto) FI_LOCAL_MR, que se incorporó al bit de modo mr FI_MR_LOCAL.

Las funciones de registro — fi_mr_reg, fi_mr_regv y fi_mr_regattr — se utilizan para registrar una o más regiones de memoria con recursos de fabric. La principal diferencia entre las funciones de registro son el número y tipo de parámetros que aceptan como entrada. De lo contrario, realizan la misma función general.

Obsoleto: Por defecto, el registro de memoria se completa de forma síncrona. Es decir, la llamada de registro no devolverá hasta que el registro se haya completado. El registro de memoria puede completarse de forma asíncrona enlazando el dominio de recursos a una cola de eventos usando el flag FI_REG_MR. Ver fi_domain_bind. Cuando el registro de memoria es asíncrono, para evitar una condición de carrera entre el retorno de la llamada de registro y la lectura correspondiente del evento de la EQ, el parámetro de salida mr se escribirá antes de que la aplicación pueda leer cualquier evento asociado con la operación. No se generará un evento asíncrono a menos que la llamada de registro devuelva éxito (0).

fi_mr_reg

La llamada fi_mr_reg

REGISTRO DE MEMORIA

registra el búfer de memoria especificado por el usuario en el dominio de recursos. El búfer se habilita para acceso por el hardware de la red según los permisos de acceso proporcionados. Consulte la descripción del campo de acceso para los atributos de la región de memoria a continuación.

La memoria registrada se asocia con un descriptor de memoria local y, opcionalmente, con una clave de memoria remota. Un descriptor de memoria es un identificador específico del proveedor asociado con la memoria registrada. Los descriptores de memoria a menudo se mapean a índices o claves específicas del hardware asociadas con la región de memoria. Las claves de memoria remota brindan protección limitada contra el acceso no deseado por un nodo remoto. Los accesos remotos a una región de memoria deben proporcionar la clave asociada con el registro.

Dado que las claves de MR deben ser proporcionadas por un proceso remoto, una aplicación puede usar el parámetro requested_key para indicar que se devuelva un valor de clave específico. El soporte para claves solicitadas por el usuario es específico del proveedor y está determinado por el valor del indicador FI_MR_PROV_KEY en el atributo del dominio mr_mode.

Las operaciones remotas de RMA y atómicas indican la ubicación dentro de una región de memoria registrada especificando una dirección. La ubicación se hace referencia sumando el desplazamiento a la dirección virtual base del búfer o a 0, dependiendo del mr_mode.

El parámetro offset está reservado para uso futuro y debe ser 0.

Para las solicitudes de registro de memoria asíncronas, el resultado se informará al usuario a través de una cola de eventos asociada con el dominio de recursos. Si tiene éxito, la estructura de región de memoria asignada se devolverá al usuario a través del parámetro mr. La dirección del mr debe permanecer válida hasta que se complete la operación de registro. El contexto especificado con la solicitud de registro se devuelve con el evento de finalización.

Para dominios abiertos con FI_AV_AUTH_KEY, fi_mr_reg no es compatible y se debe usar fi_mr_regattr.

fi_mr_regv

La llamada fi_mr_regv añade soporte para una lista de dispersión-agregación a fi_mr_reg. Múltiples búferes de memoria se registran como una sola región de memoria. De lo contrario, la operación es la misma.

Para dominios abiertos con FI_AV_AUTH_KEY, fi_mr_regv no es compatible y se debe usar fi_mr_regattr.

fi_mr_regattr

La llamada fi_mr_regattr es una llamada de registro más genérica y extensible que permite al usuario especificar la solicitud de registro utilizando una estructura fi_mr_attr (definida a continuación).

fi_close

Fi_close se utiliza para liberar todos los recursos asociados con el registro de una región de memoria. Una vez desregistrada, no se garantiza el acceso posterior a la memoria registrada. Las operaciones activas o en cola que hacen referencia a una región de memoria que se está cerrando pueden intentar acceder a una región de memoria no válida y fallar. Después de cerrar un MR, cualquier nueva operación dirigida al MR cerrado también fallará. Las aplicaciones son responsables de garantizar que un MR ya no sea necesario antes de cerrarlo. Tenga en cuenta que los accesos a un MR cerrado desde un peer remoto resultarán en un error en el peer. El estado del endpoint local no se verá afectado.

Para MRs que están asociados con un endpoint (el indicador FI_MR_ENDPOINT está configurado), el MR debe cerrarse antes que el endpoint. Si todavía hay recursos asociados con el MR al intentar cerrarlo, la llamada devolverá -FI_EBUSY.

Si se utiliza una caché de registro de memoria, el comportamiento de fi_close puede verse afectado. Más información sobre la caché de registro de memoria en la sección CACHÉ DE REGISTRO DE MEMORIA.

fi_mr_desc

Obtiene el descriptor de memoria local asociado con un MR. El registro de memoria debe haberse completado correctamente antes de invocar esta llamada.

fi_mr_key

Devuelve la clave de protección remota asociada con un MR. El registro de memoria debe haberse completado correctamente antes de invocar esto. La clave devuelta puede usarse en operaciones de transferencia de datos en un peer. Si el bit de modo FI_MR_RAW se ha establecido para el dominio, entonces la clave de memoria debe obtenerse utilizando la función fi_mr_raw_key en su lugar. Se devolverá un valor de retorno de FI_KEY_NOTAVAIL si el registro no se ha completado o si se requiere una clave de memoria raw.

fi_mr_raw_attr

Devuelve la clave de protección remota raw y la dirección base asociada con un MR. El registro de memoria debe haberse completado correctamente antes de invocar esta rutina. El uso de esta llamada es obligatorio si el proveedor ha establecido el bit de modo FI_MR_RAW; sin embargo, es seguro usar esta llamada con cualquier región de memoria.

En la entrada, el parámetro key_size debe indicar el tamaño del búfer raw_key. Si la clave real es más grande de lo que cabe en el búfer, devolverá -FI_ETOOSMALL. En la salida, key_size se establece en el tamaño del búfer necesario para almacenar la clave, que puede ser mayor que el valor de entrada. El key_size necesario también se puede obtener a través del atributo del dominio mr_key_size (fi_domain_attr).

Una clave raw debe ser mapeada por un peer antes de que pueda ser utilizada en operaciones de transferencia de datos. Consulte fi_mr_map_raw a continuación.

fi_mr_map_raw

Las claves de protección raw deben mapearse a un valor de clave utilizable antes de que puedan usarse para operaciones de transferencia de datos. El mapeo lo realiza el peer que inicia la operación RMA o atómica. La función de mapeo toma como entrada la clave raw y su tamaño, y devuelve la clave mapeada. El uso de la función fi_mr_map_raw es obligatorio si el peer tiene el bit de modo FI_MR_RAW establecido, pero esta rutina puede llamarse en cualquier clave válida. Todas las claves mapeadas deben liberarse llamando a fi_mr_unmap_key cuando el acceso a la región de memoria del peer ya no sea necesario.

fi_mr_unmap_key

Esta llamada libera cualquier recurso que pueda haberse asignado como parte del mapeo de una clave de memoria raw. Todas las claves mapeadas deben liberarse antes de que se cierre el dominio correspondiente.

fi_mr_bind

La función fi_mr_bind asocia una región de memoria con un contador o un endpoint. Los enlaces de contador son necesarios para los proveedores que admiten la generación de finalizaciones basadas en operaciones de red. Los enlaces de endpoint son necesarios si el proveedor asocia regiones de memoria con endpoints (consulte FI_MR_ENDPOINT).

Al enlazar con un contador, el tipo de eventos rastreados contra la región de memoria se basa en el OR bit a bit de los siguientes indicadores.

FI_REMOTE_WRITE
Genera un evento cada vez que una operación de escritura RMA remota o atómica modifica la región de memoria. El uso de este indicador requiere que el endpoint a través del cual se accede al MR se cree con la capacidad FI_RMA_EVENT.

Al enlazar la región de memoria a un endpoint, los indicadores deben ser 0.

fi_mr_refresh

El uso de esta llamada es para notificar al proveedor cualquier cambio en las páginas físicas que respaldan una región de memoria registrada. Esta llamada debe ser compatible con los proveedores que requieren FI_MR_MMU_NOTIFY y puede ser opcionalmente compatible con los proveedores que no requieren FI_MR_ALLOCATED.

Esta llamada informa al proveedor que las entradas de la tabla de páginas asociadas con la región pueden haber sido modificadas, y el proveedor debe verificar y actualizar la región registrada en consecuencia. El parámetro iov es opcional y puede usarse para especificar qué porciones de la región registrada requieren actualización.

Los proveedores solo tienen garantizado actualizar los rangos de direcciones especificados. Si no se actualiza un rango, se devolverá un error.

Cuando FI_MR_MMU_NOTIFY está configurado, la operación de actualización tiene el efecto de deshabilitar y volver a habilitar el acceso a la región registrada. Cualquier operación de peers que intente acceder a la región fallará mientras ocurre la actualización. Además, los intentos de acceso a la región por parte del proceso local a través de las API de libfabric pueden resultar en una falla de página u otra operación fatal.

Cuando FI_MR_ALLOCATED no está configurado, se devolverá -FI_ENOSYS si un proveedor no admite fi_mr_refresh. Si es compatible, el proveedor actualizará atmicamente las páginas físicas del MR asociadas con los rangos de direcciones especificados por el usuario. El MR permanecerá habilitado durante este tiempo.

Nota: El comportamiento de FI_MR_MMU_NOTIFY configurado tiene precedencia sobre el comportamiento de FI_MR_ALLOCATED no configurado.

La llamada fi_mr_refresh solo es necesaria si las páginas físicas pueden haber sido actualizadas después de que se creó la región de memoria.

fi_mr_enable

La llamada enable se utiliza con el registro de memoria asociado con el bit de modo FI_MR_RMA_EVENT. Las regiones de memoria creadas en estado deshabilitado deben habilitarse explícitamente después de que la aplicación las haya configurado completamente. Cualquier enlace de recursos al MR debe realizarse antes de habilitar el MR.

ATRIBUTOS DE LA REGIÓN DE MEMORIA

Las regiones de memoria se crean utilizando los siguientes atributos. La estructura fi_mr_attr se pasa a fi_mr_regattr, pero los campos individuales también se aplican a otras llamadas de registro de memoria, con los campos pasados directamente a las llamadas como parámetros de función.

struct fi_mr_attr {
    union {
        const struct iovec *mr_iov;
        const struct fi_mr_dmabuf *dmabuf;
    };
    size_t             iov_count;
    uint64_t           access;
    uint64_t           offset;
    uint64_t           requested_key;
    void               *context;
    size_t             auth_key_size;
    uint8_t            *auth_key;
    enum fi_hmem_iface iface;
    union {
        uint64_t       reserved;
        int            cuda;
        int            ze
        int            neuron;
        int            synapseai;
    } device;
    void               *hmem_data;
    size_t             page_size;
    const struct fid_mr *base_mr;
    size_t             sub_mr_cnt;
};
struct fi_mr_auth_key {
    struct fid_av *av;
    fi_addr_t     src_addr;
};

mr_iov

Este es un vector de E/S de direcciones virtuales y su longitud que representan una sola región de memoria. El número de entradas en el iovec se especifica mediante iov_count.

dmabuf

Las registros dmabuf se utilizan para compartir memoria del dispositivo entre un dispositivo dado y la NIC de la red, y no requieren que la memoria del dispositivo se mapee en el espacio de direcciones virtuales del proceso que llama.

Esta estructura hace referencia a una región de memoria de dispositivo respaldada por dmabuf. Este campo solo es utilizable si la aplicación ha solicitado con éxito soporte para FI_HMEM y el indicador FI_MR_DMABUF se pasa a la llamada de registro de memoria. Las regiones dmabuf son referencias basadas en archivos a la memoria del dispositivo. Dichas regiones se identifican a través de la estructura fi_mr_dmabuf.

struct fi_mr_dmabuf {
    int      fd;
    uint64_t offset;
    size_t   len;
    void     *base_addr;
};

El fd es el descriptor de archivo asociado con la región dmabuf. El offset es el desplazamiento dentro de la región donde debe comenzar el registro de memoria. Y len es el tamaño de la región a registrar, comenzando en el offset. El base_addr es la dirección virtual de inicio alineada por página de la región de memoria asignada por dmabuf. Si no hay una dirección virtual base disponible (porque, por ejemplo, el proceso que llama no ha mapeado la región de memoria en su espacio de direcciones), base_addr se puede establecer en NULL.

La selección de dmabuf sobre el campo mr_iov se controla especificando el indicador FI_MR_DMABUF.

iov_count

El número de entradas en el arreglo mr_iov. El número máximo de búferes de memoria que pueden asociarse con una única región de memoria se especifica como el atributo del dominio mr_iov_limit. Consulte fi_domain(3).

access

Indica el tipo de operaciones que un punto final local o remoto puede realizar en la región de memoria registrada. Los permisos de acceso admitidos son el OR a nivel de bits de los siguientes indicadores:

FI_SEND
El búfer de memoria puede ser utilizado en transferencias de datos de mensajes salientes. Esto incluye operaciones de envío fi_msg y fi_tagged, así como operaciones colectivas fi_collective.
FI_RECV
El búfer de memoria puede ser utilizado para recibir transferencias de mensajes entrantes. Esto incluye operaciones de recepción fi_msg y fi_tagged, así como operaciones colectivas fi_collective.
FI_READ
El búfer de memoria puede ser utilizado como búfer de resultado para operaciones de lectura y atómicas de RMA en el lado del iniciador. Tenga en cuenta que desde el punto de vista de la aplicación, el búfer de memoria está siendo escrito por la red.
FI_WRITE
El búfer de memoria puede ser utilizado como búfer de origen para operaciones de escritura y atómicas de RMA en el lado del iniciador. Tenga en cuenta que desde el punto de vista de la aplicación, el punto final está leyendo desde el búfer de memoria y copiando los datos a la red.
FI_REMOTE_READ
El búfer de memoria puede ser utilizado como búfer de origen de una operación de lectura RMA en el lado del destino. El contenido del búfer de memoria no se modifica con tales operaciones.
FI_REMOTE_WRITE
El búfer de memoria puede ser utilizado como búfer de destino de una operación de escritura o atómica de RMA. El contenido del búfer de memoria puede modificarse como resultado de tales operaciones.
FI_COLLECTIVE
Este indicador proporciona una indicación explícita de que el búfer de memoria puede ser utilizado con operaciones colectivas. Se requiere el uso de este indicador si el bit FI_MR_COLLECTIVE del modo de registro se ha establecido en el dominio. Este indicador debe emparejarse con FI_SEND y/o FI_RECV.

Tenga en cuenta que algunos proveedores pueden no aplicar permisos de acceso de grano fino. Por ejemplo, una región de memoria registrada para acceso FI_WRITE también puede comportarse como si se especificara FI_SEND. La aplicación relajada de dichos accesos está permitida, aunque no garantizada, siempre que se mantenga la seguridad.

offset

El campo offset está reservado para uso futuro y debe ser 0.

requested_key

Una clave de acceso especificada por la aplicación asociada con la región de memoria. La clave MR debe ser proporcionada por un proceso remoto al realizar operaciones RMA o atómicas a una región de memoria. Las aplicaciones pueden usar el campo requested_key para indicar que el proveedor debe usar una clave específica. Esto permite a las aplicaciones usar valores de clave conocidos, lo que puede evitar que las aplicaciones necesiten intercambiar y almacenar claves. El soporte para claves solicitadas por el usuario es específico del proveedor y se determina mediante el indicador FI_MR_PROV_KEY en el campo de atributo de dominio mr_mode. Dependiendo del proveedor, la clave solicitada por el usuario puede ser ignorada si la región de memoria es solo para acceso local. Un proveedor puede no poder hacerlo si el hardware admite claves solicitadas por el usuario y la misma clave se utiliza tanto para acceso local como remoto.

context

Contexto de aplicación asociado con operaciones de registro de memoria asíncronas. Este valor se devuelve como parte de cualquier evento asíncrono asociado con el registro. Este campo se ignora para las llamadas de registro síncronas.

auth_key_size

El tamaño de la clave a la que se hace referencia en el campo auth_key en bytes, o 0 si no se proporciona ninguna clave de autorización. Este campo se ignora a menos que la red se abra con la versión de API 1.5 o superior.

Si el dominio se abre con FI_AV_AUTH_KEY, auth_key_size debe ser igual a sizeof(struct fi_mr_auth_key).

auth_key

Indica la clave a asociar con este registro de memoria. Las claves de autorización se utilizan para limitar la comunicación entre puntos finales. Solo los puntos finales pares que estén programados para usar la misma clave de autorización podrán acceder a la región de memoria. Se utilizará la clave de autorización del dominio si el auth_key_size proporcionado es 0. Este campo se ignora a menos que la red se abra con la versión de API 1.5 o superior.

Si el dominio se abre con FI_AV_AUTH_KEY, auth_key debe apuntar a una estructura definida por el usuario fi_mr_auth_key.

iface

Indica las interfaces de software utilizadas por la aplicación para asignar y administrar la región de memoria. Este campo se ignora a menos que la aplicación haya solicitado la capacidad FI_HMEM.

FI_HMEM_SYSTEM
Utiliza llamadas y bibliotecas estándar del sistema operativo, como malloc, calloc, realloc, mmap y free. Cuando iface se establece en FI_HMEM_SYSTEM, el campo device (descrito a continuación) se ignora.
FI_HMEM_CUDA
Utiliza interfaces Nvidia CUDA como cuMemAlloc, cuMemAllocHost, cuMemAllocManaged, cuMemFree, cudaMalloc, cudaFree.
FI_HMEM_ROCR
Utiliza interfaces AMD ROCR como hsa_memory_allocate y hsa_memory_free.
FI_HMEM_ZE
Utiliza interfaces oneAPI Level Zero como zeDriverAllocSharedMem, zeDriverFreeMem.
FI_HMEM_NEURON
Utiliza el SDK de AWS Neuron para admitir dispositivos AWS Trainium.
FI_HMEM_SYNAPSEAI
Utiliza la API SynapseAI para admitir dispositivos Habana Gaudi.

device

64 bits reservados para el identificador del dispositivo si se utiliza una interfaz HMEM no estándar. Este campo se ignora a menos que el campo iface sea válido. De lo contrario, el campo device se determina según el valor especificado a través de iface.

cuda
Para FI_HMEM_CUDA, esto es equivalente a CUdevice (int).
ze
Para FI_HMEM_ZE, esto es equivalente al índice del dispositivo en el arreglo ze_device_handle_t. Si solo hay un controlador de nivel cero presente, una aplicación puede establecerlo directamente. Sin embargo, se recomienda que este valor se establezca utilizando la macro fi_hmem_ze_device(), que codificará el índice del controlador con el dispositivo.
neuron
Para FI_HMEM_NEURON, el identificador del dispositivo para los dispositivos AWS Trainium.
synapseai
Para FI_HMEM_SYNAPSEAI, el identificador del dispositivo para el hardware Habana Gaudi.

hmem_data

El campo hmem_data está reservado para uso futuro y debe ser nulo.

page_size

El tamaño de página permite a las aplicaciones proporcionar opcionalmente una pista sobre cuál es el tamaño de página óptimo para una asignación de MR. Típicamente, los proveedores pueden seleccionar el tamaño de página óptimo. En casos donde el rango VA tiene cero páginas que lo respaldan, lo cual es compatible con FI_MR_ALLOCATED sin marcar, el proveedor puede no conocer el tamaño de página óptimo durante el registro. En lugar de usar un tamaño de página menos eficiente, este atributo permite a las aplicaciones especificar el tamaño de página a utilizar.

Si el tamaño de página es cero, el proveedor seleccionará el tamaño de página.

Si es distinto de cero, el tamaño de página debe ser compatible con el SO. Si se especifica un tamaño de página específico para una región de memoria durante la creación, todas las páginas asociadas posteriormente con la región deben ser de ese tamaño. Adjuntar una página de memoria de un tamaño diferente a una región puede resultar en transferencias fallidas hacia o desde la región.

Los proveedores pueden optar por ignorar el tamaño de página. Esto resultará en que siempre se utilice un tamaño de página seleccionado por el proveedor.

base_mr

Si es distinto de NULL, cree un sub-MR a partir de una región de memoria existente especificada por el campo base_mr.

El sub-MR debe estar completamente contenido dentro del MR base; sin embargo, el sub-MR tiene sus propias claves de autorización y derechos de acceso. Los siguientes atributos se heredan de la

e base MR, y como resultado, se ignoran al crear el sub-MR:

iface, device, hmem_data, page_size

El sub-MR debe mantener una referencia al MR base. Cuando se llama a fi_close en el MR base, la llamada fallaría si hay sub-MRs pendientes.

El campo base_mr debe ser NULL si se establece el indicador FI_MR_DMABUF.

sub_mr_cnt

El número de sub-MRs que se espera crear a partir de la región de memoria. Este valor no es un límite. En cambio, es una sugerencia para el proveedor para permitir optimizaciones específicas del proveedor en la creación de sub-MRs. Por ejemplo, el proveedor puede reservar claves de acceso o preasignar objetos fid_mr. El proveedor puede ignorar esta sugerencia.

fi_hmem_ze_device

Devuelve un identificador de dispositivo hmem para una tupla <driver, device> de nivel cero. La salida de esta llamada debe usarse para establecer fi_mr_attr::device.ze para interfaces FI_HMEM_ZE. Los valores de índice del driver y del dispositivo representan sus posiciones basadas en cero en las matrices devueltas por zeDriverGet y zeDeviceGet, respectivamente.

av

Para el registro de memoria que se asigna contra un dominio configurado con FI_AV_AUTH_KEY, av se usa para definir el fid_av que contiene las claves de autorización que se asociarán con la región de memoria. Si el dominio también se abre con FI_MR_ENDPOINT, el AV especificado debe ser el mismo AV vinculado al punto final.

Por defecto, la región de memoria se asociará con todas las claves de autorización en el AV.

addr

Si el dominio se abrió con FI_DIRECTED_RECV, addr se puede usar para limitar la región de memoria a un fi_addr_t específico, incluido el fi_addr_t devuelto por fi_av_insert_auth_key.

NOTAS

El acceso directo a la memoria de una aplicación por un par remoto requiere que la aplicación registre el(los) búfer(es) de memoria objetivo. Esto se hace típicamente llamando a una de las rutinas fi_mr_reg*. Para FI_MR_PROV_KEY, el proveedor devolverá una clave que debe usar el par al acceder a la región de memoria. La aplicación es responsable de transferir esta clave al par. Si se ha establecido el modo FI_MR_RAW, la clave debe recuperarse usando la función fi_mr_raw_attr.

FI_MR_RAW permite el soporte para proveedores que requieren más de 8 bytes para sus claves de protección o necesitan una configuración adicional antes de que una clave pueda usarse para transferencias. Después de recuperar una clave en bruto, debe intercambiarse con el par remoto. El par debe usar fi_mr_map_raw para convertir la clave en bruto en una clave de 64 bits utilizable. El mapeo debe hacerse incluso si la clave en bruto tiene 64 bits o menos.

Las funciones de soporte de clave en bruto son utilizables con todas las regiones de memoria registradas, incluso si no se ha establecido FI_MR_RAW. Se recomienda que las aplicaciones portables apunten a usar esas interfaces; sin embargo, su uso conlleva una sobrecarga adicional de mensajes y memoria, lo que lo hace menos deseable para aplicaciones altamente escalables.

Puede haber casos en los que el soporte de par a par del dispositivo no deba usarse o no pueda usarse, como cuando la configuración ACS de PCIe no permite la transferencia. Se puede establecer la variable de entorno FI_HMEM_DISABLE_P2P para notificar a Libfabric que no deben usarse transacciones de par a par. El proveedor puede optar por realizar una copia en su lugar, o fallará el soporte para FI_HMEM si el proveedor no puede hacerlo.

INDICADORES

El siguiente indicador puede especificarse en cualquier llamada de registro de memoria.

FI_RMA_EVENT
Este indicador indica que la región de memoria especificada se asociará con un contador de finalización utilizado para contar operaciones RMA que acceden al MR.
FI_RMA_PMEM
Este indicador indica que la región de memoria subyacente está respaldada por memoria persistente y se usará en operaciones RMA. Debe especificarse si se requieren semánticas de finalización persistentes o transferencias de datos persistentes al acceder a la región registrada.
FI_HMEM_DEVICE_ONLY
Este indicador indica que la memoria solo es accesible por un dispositivo. Qué dispositivo está especificado por los campos iface y device de fi_mr_attr. Esto se refiere a regiones de memoria que se asignaron usando una llamada AllocDevice de una API de dispositivo (en lugar de usar la asignación de host o la asignación de memoria unificada/compartida). Este indicador solo es utilizable para dominios abiertos con soporte de capacidad FI_HMEM.
FI_HMEM_HOST_ALLOC
Este indicador indica que la memoria es propiedad solo del host. Si puede ser accesible por el dispositivo depende de la implementación. El campo iface de fi_mr_attr todavía se usa para identificar la API del dispositivo, pero el campo device se ignora. Esto se refiere a regiones de memoria que se asignaron usando una llamada AllocHost de una API de dispositivo (en lugar de usar una asignación de host tipo malloc, una asignación de memoria unificada/compartida, o AllocDevice). Este indicador solo es utilizable para dominios abiertos con soporte de capacidad FI_HMEM.
FI_MR_DMABUF
Este indicador indica que la región de memoria a registrar es una región respaldada por DMA-buf. Cuando se establece, la región se especifica a través del campo dmabuf de la estructura fi_mr_attr. Este indicador solo es utilizable para dominios abiertos con soporte de capacidad FI_HMEM.
FI_MR_SINGLE_USE
Este indicador indica que la región de memoria solo se usa para una sola operación. Después de que la operación se complete, la clave asociada con la región de memoria se invalida automáticamente y ya no puede usarse para acceso remoto.
FI_AUTH_KEY
Solo válido con dominios configurados con FI_AV_AUTH_KEY. Cuando se usa con fi_mr_regattr, este indicador denota que el campo fi_mr_auth_key::src_addr contiene una clave de autorización fi_addr_t (es decir, fi_addr_t devuelto por fi_av_insert_auth_key) en lugar de un fi_addr_t de punto final (es decir, fi_addr_t devuelto por fi_av_insert / fi_av_insertsvc / fi_av_remove).

DOMINIOS DE MEMORIA

Los dominios de memoria identifican la separación física de la memoria que puede o no ser accesible a través del mismo espacio de direcciones virtuales. Tradicionalmente, las aplicaciones solo trataban con un solo dominio de memoria, el de la memoria del host estrechamente acoplada con las CPU del sistema. Con la introducción de subsistemas de memoria de dispositivos y no uniformes, las aplicaciones a menudo necesitan ser conscientes de a qué dominio de memoria se asigna una dirección virtual particular.

Como regla general, los dispositivos físicos separados pueden considerarse que tienen sus propios dominios de memoria. Por ejemplo, una NIC puede tener memoria accesible por el usuario, y se consideraría un dominio de memoria separado de la memoria en una GPU. Tanto los dominios de memoria de la NIC como los de la GPU están separados de la memoria del sistema host. Las GPU individuales o los aceleradores de computación pueden tener dominios de memoria distintos, o pueden estar conectados de tal manera (por ejemplo, una red específica para GPU) que todas las GPU pertenecerían al mismo dominio de memoria. Desafortunadamente, identificar los dominios de memoria es específico de cada sistema y su configuración física y/o virtual.

Comprender los dominios de memoria en entornos de memoria heterogéneos es importante ya que puede impactar el ordenamiento y la visibilidad de los datos tal como los ve una aplicación. También es importante comprender a qué dominio de memoria está más estrechamente acoplada una aplicación. En la mayoría de los casos, las aplicaciones están estrechamente acopladas a la memoria del host. Sin embargo, una aplicación que se ejecuta directamente en una GPU o NIC puede estar más estrechamente acoplada a la memoria asociada con esos dispositivos.

Las regiones de memoria a menudo se asocian con un solo dominio de memoria. El dominio a menudo está indicado por los campos iface y device de fi_mr_attr. Aunque es posible que las páginas físicas que respaldan una región de memoria virtual migren entre dominios de memoria basándose en los patrones de acceso. Por ejemplo, las páginas físicas referenciadas por un rango de direcciones virtuales podrían migrar entre la memoria del host y la memoria de la GPU, dependiendo de qué unidad de computación la esté usando activamente.

Consulte las páginas de manual fi_endpoint(3) y fi_cq(3) para una discusión adicional sobre la semántica de ordenación de mensajes, datos y finalizaciones, incluyendo el impacto de los dominios de memoria.

VALORES DE RETORNO

Devuelve 0 en caso de éxito. En caso de error, se devuelve un valor negativo correspondiente a un errno de fabric.

Los valores de errno de fabric están definidos en rdma/fi_errno.h.

ERRORES

-FI_ENOKEY
El requested_key ya está en uso.
-FI_EKEYREJECTED
El requested_key no está disponible. La clave puede estar fuera del rango soportado por el proveedor, o el proveedor puede no soportar claves de registro de memoria solicitadas por el usuario.
-FI_ENOSYS
Devuelto por fi_mr_bind si el proveedor no soporta el informe de eventos basado en el acceso a regiones de memoria registradas.
-FI_EBADFLAGS
Devuelto si los indicadores especificados no son soportados por el proveedor.

CACHÉ DE REGISTRO DE MEMORIA

Muchas NIC de hardware accedidas por libfabric requieren que los búferes de datos se registren con el hardware mientras el hardware accede a ellos. Esto asegura que los mapeos de direcciones virtuales a físicas para esos búferes no cambien mientras ocurre la transferencia. El impacto en el rendimiento de registrar regiones de memoria puede ser significativo. Como resultado, algunos proveedores hacen uso de una caché de registro, particularmente cuando trabajan con aplicaciones que no pueden gestionar sus propios búferes de red. Una caché de registro evita la sobrecarga de registrar y desregistrar un búfer de datos con cada transferencia.

Si se va a usar una caché de registro para la memoria del host y del dispositivo, el dispositivo debe soportar direccionamiento virtual unificado.
