DESCRIPCIÓ

N

Las regiones de memoria registradas asocian búferes de memoria con permisos concedidos para el acceso por recursos del fabric. Un búfer de memoria debe registrarse con un dominio de recursos antes de poder usarse como destino de una transferencia de datos RMA o atómica remota. Además, un proveedor de fabric puede requerir que los búferes de datos se registren antes de usarse en transferencias locales. Las restricciones de registro de memoria se controlan usando un conjunto separado de bits de modo, especificados a través de los atributos del dominio (campo mr_mode). Cada bit mr_mode requiere que una aplicación tome pasos específicos para usar búferes de memoria con las interfaces de

libfabric.

Como caso especial, una nueva región de memoria puede crearse a partir de una región de memoria existente. Una nueva región de memoria de este tipo se denomina sub-MR, y la región de memoria existente se denomina MR base. Las sub-MR pueden usarse para compartir recursos de hardware, como traducciones de direcciones virtuales a físicas y fijación de páginas. Esto puede mejorar el rendimiento al crear y destruir subregiones que requieren diferentes permisos de acceso. La MR base misma también puede ser una sub-MR, permitiendo una jerarquía de regiones de

memoria.

Lo siguiente se aplica al registro de

memoria.
Registro de memoria
predeterminado
Si no se establecen bits mr_mode, se siguen los comportamientos predeterminados descritos a continuación. Históricame
nte, estos valores predeterminados se denominaban colectivamente registro de memoria escalable. Los requisitos predete
rminados se describen a continuación, seguidos de las definiciones de cómo cada bit mr_mode altera la definición.

Compatibilidad: Para las versiones de la biblioteca 1.4 y anteriores, esto se indicaba estableciendo mr_mode en FI_MR_SCALABLE y el bit de modo fi_info FI_LOCAL_MR en 0. FI_MR_SCALABLE y FI_LOCAL_MR quedaron obsoletos en la versión 1.5 de libfabric, aunque se admiten con fines de compatibilidad hacia

atrás.

Por seguridad, se requiere registro de memoria para los búferes de datos a los que accede directamente un proceso par. Por ejemplo, se requiere registro para los búferes de destino RMA (lectura o escritura), y para aquellos a los que acceden operaciones atómicas o

colectivas.

Por defecto, el registro ocurre en rangos de direcciones virtuales. Dado que el registro se refiere a rangos de direcciones, en lugar de búferes de datos asignados, los rangos de direcciones no necesitan mapearse a búferes de datos asignados por la aplicación en el momento en que se realiza la llamada de registro. Es decir, una aplicación puede registrar cualquier rango de direcciones en su espacio de direcciones virtuales, independientemente de si esas direcciones están respaldadas por páginas físicas o han sido

asignadas.

Tenga en cuenta que las páginas físicas deben respaldar las direcciones antes de que las direcciones sean accedidas como parte de una operación de transferencia de datos, o las transferencias de datos fallarán. Además, dependiendo de la operación, esto podría resultar en que el proceso local reciba una violación de segmentación por acceder a memoria no

válida.

Una vez registradas, las regiones de memoria resultantes son accesibles por los pares a partir de una dirección base de 0. Es decir, la dirección de destino que se especifica es un desplazamiento en bytes dentro de la región

registrada.

La aplicación también selecciona la clave de acceso asociada con la MR. El tamaño de la clave está restringido a un máximo de 8

bytes.

Con el registro escalable, los búferes de datos accedidos localmente no se registran. Esto incluye los búferes de origen para todas las operaciones de transmisión – envíos, envíos etiquetados, RMA y atómicos – así como los búferes publicados para operaciones de recepción y recepción

etiquetada.

Aunque el comportamiento predeterminado de registro de memoria es conveniente para los desarrolladores de aplicaciones, es difícil de implementar en hardware. Los intentos de ocultar los requisitos de hardware a la aplicación a menudo resultan en impactos significativos e inaceptables en el rendimiento. Los siguientes bits mr_mode se proporcionan como entrada a fi_getinfo. Si un proveedor requiere el comportamiento definido para un bit mr_mode, dejará el bit establecido en la salida de fi_getinfo. De lo contrario, el proveedor puede limpiar el bit para indicar que el comportamiento no es

necesario.

Al establecer un bit mr_mode, la aplicación ha aceptado ajustar su comportamiento según lo indicado. Es importante que las aplicaciones que elijan admitir un mr_mode estén preparadas para manejar el caso en que el mr_mode no es necesario. Un proveedor limpiará un bit mr_mode si no es

necesario.
FI_MR_LOCAL
Cuando el bit de modo FI_MR_LOCAL está establecido, las aplicaciones deben registrar todos los búferes de datos que serán accedidos por el hardware local y proporcionar un parámetro desc válido en las operaciones de transferencia de datos aplicables.

Cuando FI_MR_LOCAL no está establecido, las aplicaciones no están obligadas a registrar búferes de datos antes de usarlos para operaciones locales (por ejemplo, enviar y recibir búferes de datos). Antes de libfabric 1.22, el parámetro desc se ignoraba. En libfabric 1.22 y posteriores, el parámetro desc debe ser válido o NULL. Este comportamiento permite a las aplicaciones pasar opcionalmente un parámetro desc válido. Si el parámetro desc es NULL, cualquier registro de memoria local requerido será manejado por el proveedor.

Un proveedor puede ocultar los requisitos de registro local de las aplicaciones utilizando una caché de registro interna o mecanismos similares. Dichos mecanismos, sin embargo, pueden afectar negativamente el rendimiento de algunas aplicaciones, especialmente aquellas que gestionan sus propios búferes de red. Para admitir la gama más amplia posible de aplicaciones, sin afectar indebidamente su rendimiento, las aplicaciones que deseen gestionar sus propios registros de memoria local pueden hacerlo utilizando las llamadas de registro de memoria y pasando un parámetro desc válido.

Nota: el bit de modo FI_MR_LOCAL reemplaza al bit de modo FI_LOCAL_MR de fi_info. Cuando FI_MR_LOCAL está establecido, FI_LOCAL_MR se ignora.

FI_MR_RAW
Las regiones de memoria cruda se utilizan para soportar proveedores con claves mayores de 64 bits o que requieren configuración en el par. Cuando el bit FI_MR_RAW está establecido, las aplicaciones deben usar fi_mr_raw_attr() localmente y fi_mr_map_raw() en el par antes de apuntar a una región de memoria como parte de cualquier solicitud de transferencia de datos.
FI_MR_VIRT_ADDR
El bit FI_MR_VIRT_ADDR indica que el proveedor hace referencia a las regiones de memoria por dirección virtual, en lugar de un desplazamiento basado en 0. Los pares que apuntan a regiones de memoria registradas con FI_MR_VIRT_ADDR especifican el búfer de memoria de destino utilizando la dirección virtual del destino, con cualquier desplazamiento dentro de la región especificado como dirección virtual + desplazamiento. El soporte de este bit generalmente implica que los pares deben intercambiar datos de direccionamiento antes de iniciar cualquier operación RMA o atómica.

Para las regiones de memoria que se registran usando FI_MR_DMABUF, la 'dirección virtual' de inicio de la región DMA-buf se obtiene sumando el campo de desplazamiento al campo base_addr de la estructura fi_mr_dmabuf que se especificó a través de la llamada de registro.

FI_MR_ALLOCATED
Cuando está establecido, todas las regiones de memoria registradas deben estar respaldadas por páginas de memoria física en el momento en que se realiza la llamada de registro. Además, las aplicaciones no deben realizar operaciones que puedan hacer que el mapeo de dirección virtual a página física subyacente cambie (por ejemplo, llamar a free() contra una MR asignada). No cumplir con esto puede resultar en que la dirección virtual apunte a un conjunto de páginas físicas mientras que la MR apunta a otro conjunto de páginas físicas.

Cuando no está establecido, las regiones de memoria registradas no necesitan estar respaldadas por páginas de memoria física en el momento en que se realiza la llamada de registro. Además, se permite que el mapeo de dirección virtual a página física subyacente cambie, y el proveedor se asegurará de que la MR correspondiente se actualice en consecuencia. Este comportamiento permite casos de uso de aplicaciones donde la memoria puede liberarse y reasignarse con frecuencia o la memoria del sistema migra desde/hacia la memoria del dispositivo.

Cuando no está establecido, la aplicación es responsable de garantizar que una región de memoria registrada haga referencia a páginas físicas válidas mientras se realiza una transferencia de datos contra ella, o la transferencia de datos puede fallar. Los cambios de la aplicación en el rango de direcciones virtuales deben coordinarse con el tráfico de red hacia o desde ese rango.

Si no está establecido y se soporta FI_HMEM, la capacidad de que cambie el mapeo de dirección virtual a dirección física se extiende también a las interfaces HMEM. Si un proveedor no puede soportar un cambio de mapeo de dirección virtual a dirección física para una interfaz HMEM dada, el proveedor debe soportar una solución alternativa razonable o la operación debe fallar.

FI_MR_PROV_KEY
Este modo de región de memoria indica que el proveedor no soporta claves de MR solicitadas por la aplicación. Las claves de MR son devueltas por el proveedor. Las aplicaciones que soportan FI_MR_PROV_KEY pueden obtener la clave del proveedor usando fi_mr_key(), a menos que FI_MR_RAW también esté establecido. La clave devuelta debe ser intercambiada con los pares antes de iniciar una operación RMA o atómica.
FI_MR_MMU_NOTIFY
FI_MR_MMU_NOTIFY generalmente lo establecen los proveedores que soportan el registro de memoria contra regiones de memoria que no están necesariamente respaldadas por páginas físicas asignadas en el momento en que ocurre el registro de memoria. (Es decir, FI_MR_ALLOCATED suele ser 0). Sin embargo, dichos proveedores requieren que las aplicaciones notifiquen al proveedor antes de que la MR sea accedida como parte de una operación de transferencia de datos. Esta notificación informa al proveedor que todas las páginas físicas necesarias respaldan ahora la región. La notificación es necesaria para los proveedores que no pueden conectarse directamente a las tablas de páginas del sistema operativo o a la unidad de gestión de memoria. Consulte fi_mr_refresh() para obtener detalles sobre la notificación.
FI_MR_RMA_EVENT
Este bit de modo indica que el proveedor debe configurar las regiones de memoria asociadas con eventos RMA antes de su uso. Esto incluye todas las regiones de memoria asociadas con contadores de finalización. Cuando está establecido, las aplicaciones deben indicar si una región de memoria estará asociada con un contador de finalización como parte de la creación de la región. Esto se hace pasando el indicador FI_RMA_EVENT a la llamada de registro de memoria.

Dichas regiones de memoria se crearán en un estado deshabilitado y deben asociarse con todos los contadores de finalización antes de ser habilitadas. Para habilitar una región de memoria, la aplicación debe llamar a fi_mr_enable(). Después de llamar a fi_mr_enable(), no se podrán realizar más enlaces de recursos a la región de memoria.

FI_MR_ENDPOINT
Este bit de modo indica que el proveedor asocia regiones de memoria con puntos de conexión en lugar de dominios. Las regiones de memoria que se registran con el proveedor se crean en un estado deshabilitado y deben enlazarse a un punto de conexión antes de ser habilitadas. Para enlazar la MR con un punto de conexión, la aplicación debe usar fi_mr_bind(). Para habilitar la región de memoria, la aplicación debe llamar a fi_mr_enable().
FI_MR_HMEM
Este bit de modo está asociado con la capacidad FI_HMEM.

Si FI_MR_HMEM está establecido, la aplicación debe registrar búferes que fueron asignados usando una llamada al dispositivo y proporcionar un parámetro desc válido en las operaciones de transferencia de datos aplicables, incluso si solo se utilizan para operaciones locales (por ejemplo, enviar y recibir búferes de datos). La memoria del dispositivo debe registrarse utilizando la llamada fi_mr_regattr, con los campos iface y device completados.

Si FI_MR_HMEM no está establecido, la aplicación no necesita registrar búferes del dispositivo para operaciones locales. Además, no es necesario usar fi_mr_regattr para el registro de memoria del dispositivo. Es responsabilidad del proveedor descubrir los atributos de registro de memoria del dispositivo apropiados, si los hubiera.

De manera similar a si FI_MR_LOCAL no está establecido, si FI_MR_HMEM no está establecido, las aplicaciones pueden pasar opcionalmente un parámetro desc válido. Si el parámetro desc es NULL, cualquier registro de memoria local requerido será manejado por el proveedor.

Si FI_MR_HMEM está establecido, pero FI_MR_LOCAL no lo está, solo los búferes del dispositivo deben registrarse cuando se utilizan localmente. En este caso, el parámetro desc pasado en las operaciones de transferencia de datos debe ser válido o NULL. De manera similar, si FI_MR_LOCAL está establecido, pero FI_HMEM no lo está, el parámetro desc debe ser válido o NULL.

FI_MR_COLLECTIVE
Este bit está asociado con la capacidad FI_COLLECTIVE.

Si FI_MR_COLLECTIVE está establecido, el proveedor requiere que las regiones de memoria utilizadas en operaciones colectivas deban registrarse explícitamente para su uso con llamadas colectivas. Esto requiere registrar las regiones pasadas a las llamadas colectivas usando el indicador FI_COLLECTIVE.

Si FI_MR_COLLECTIVE no está establecido, el registro de memoria para operaciones colectivas es opcional. Las aplicaciones pueden pasar opcionalmente un parámetro desc válido. Si el parámetro desc es NULL, cualquier registro de memoria local requerido será manejado por el proveedor.

Registro de Memoria Básico (obsoleto)
El registro de memoria básico fue obsoleto en la versión 1.5 de libfabric, pero se admite para compatibilidad con versiones anteriores. El registro de memoria básico se indica estableciendo mr_mode igual a FI_MR_BASIC. FI_MR_BASIC debe establecerse solo y no emparejarse con bits de modo. A diferencia de otros bits de modo, si FI_MR_BASIC se establece en la entrada de fi_getinfo(), el proveedor no lo borrará. Es decir, establecer mr_mode igual a FI_MR_BASIC fuerza el registro básico si el proveedor lo soporta.

El comportamiento del registro básico es equivalente a requerir los siguientes bits de modo: FI_MR_VIRT_ADDR, FI_MR_ALLOCATED y FI_MR_PROV_KEY. Además, los proveedores que soportan el registro básico generalmente requieren el bit de modo de fi_info (obsoleto) FI_LOCAL_MR, que se incorporó al bit de modo FI_MR_LOCAL.

Las funciones de registro – fi_mr_reg, fi_mr_regv y fi_mr_regattr – se utilizan para registrar una o más regiones de memoria con recursos de red. La principal diferencia entre las funciones de registro son el número y tipo de parámetros que aceptan como entrada. De lo contrario, realizan la misma función general.

Obsoleto: Por defecto, el registro de memoria se completa de forma síncrona. Es decir, la llamada de registro no devolverá hasta que el registro se haya completado. El registro de memoria puede completarse de forma asíncrona enlazando el dominio de recursos a una cola de eventos usando el flag FI_REG_MR. Consulte fi_domain_bind. Cuando el registro de memoria es asíncrono, para evitar una condición de carrera entre el retorno de la llamada de registro y la lectura correspondiente del evento de la EQ, el parámetro de salida mr se escribirá antes de que la aplicación pueda leer cualquier evento asociado con la operación. No se generará un evento asíncrono a menos que la llamada de registro devuelva éxito (0).

fi_mr_reg

La llamada fi_mr_reg registra

registra el búfer de memoria especificado por el usuario con el dominio de recursos. El búfer se habilita para su acceso por parte del hardware de la red (fabric) basándose en los permisos de acceso proporcionados. Consulte la descripción del campo de acceso para los atributos de la región de memoria a

continuación.

La memoria registrada se asocia con un descriptor de memoria local y, opcionalmente, con una clave de memoria remota. Un descriptor de memoria es un identificador específico del proveedor asociado con la memoria registrada. Los descriptores de memoria a menudo se mapean a índices o claves específicos del hardware asociados con la región de memoria. Las claves de memoria remota proporcionan una protección limitada contra el acceso no deseado por parte de un nodo remoto. Los accesos remotos a una región de memoria deben proporcionar la clave asociada con el

registro.

Dado que las claves de MR deben ser proporcionadas por un proceso remoto, una aplicación puede usar el parámetro requested_key para indicar que se devuelva un valor de clave específico. El soporte para claves solicitadas por el usuario es específico del proveedor y está determinado por el valor del indicador FI_MR_PROV_KEY en el atributo de dominio

mr_mode.

Las operaciones RMA y atómicas remotas indican la ubicación dentro de una región de memoria registrada al especificar una dirección. La ubicación se referencia sumando el desplazamiento (offset) a la dirección virtual base del búfer o a 0, dependiendo del

mr_mode.

El parámetro offset está reservado para uso futuro y debe ser

0.

Para solicitudes de registro de memoria asíncronas, el resultado se reportará al usuario a través de una cola de eventos asociada con el dominio de recursos. Si es exitoso, la estructura de la región de memoria asignada se devolverá al usuario a través del parámetro mr. La dirección mr debe permanecer válida hasta que la operación de registro se complete. El contexto especificado con la solicitud de registro se devuelve con el evento de

finalización.

ado y se debe usar fi_mr_regattr.

fi_clos

e

Fi_close se utiliza para liberar todos los recursos asociados con el registro de una región de memoria. Una vez desregistrada, no se garantiza el acceso posterior a la memoria registrada. Las operaciones activas o en cola que referencian una región de memoria que se está cerrando pueden intentar acceder a una región de memoria inválida y fallar. Después de que una MR se cierre, cualquier nueva operación dirigida a la MR cerrada también fallará. Las aplicaciones son responsables de asegurarse de que una MR ya no sea necesaria antes de cerrarla. Tenga en cuenta que los accesos a una MR cerrada desde un par remoto resultarán en un error en el par. El estado del punto de extremo local no se verá

afectado.

Para las MR que están asociadas con un punto de extremo (el indicador FI_MR_ENDPOINT está establecido), la MR debe cerrarse antes que el punto de extremo. Si todavía hay recursos asociados con la MR al intentar cerrarla, la llamada devolverá

-FI_EBUSY.

Si se utiliza una caché de registro de memoria, el comportamiento

de fi_close puede verse afectado. Hay más información sobre la cac
hé de registro de memoria en la sección MEMORY REGISTRATION CACHE.

Devuelve la clave de protección remota asociada con una MR. El registro de memoria debe haberse completado con éxito antes de invocar esto. La clave devuelta puede usarse

en operaciones de transferencia de datos en un par. Si el bit de modo FI_MR_RAW ha sido establecido para el dominio, entonces la clave de memoria debe obtenerse usando la
función fi_mr_raw_key en su lugar. Se devolverá un valor de retorno de FI_KEY_NOTAVAIL si el registro no se ha completado o se requiere una clave de memoria cruda (raw).

fi_mr_raw_att

r

Devuelve la clave de protección remota cruda (raw) y la dirección base asociada con una MR. El registro de memoria debe haberse completado con éxito antes de invocar esta rutina. El uso de esta llamada es requerido si el bit de modo FI_MR_RAW ha sido establecido por el proveedor; sin embargo, es seguro usar esta llamada con cualquier región de

memoria.

En la entrada, el parámetro key_size debe indicar el tamaño del búfer raw_key. Si la clave real es más grande de lo que cabe en el búfer, devolverá -FI_ETOOSMALL. En la salida, key_size se establece al tamaño del búfer necesario para almacenar la clave, que puede ser mayor que el valor de entrada. dmabuf

Los registros de DMA-buf se utilizan para compartir memoria de dispositivo entre un dispositivo dado y la NIC de la red de interconexión, y no requieren que la memoria del dispositivo se mapee (mmap) en el espacio de direcciones virtuales del proceso que llama.

Esta estructura hace referencia a una región de memoria de dispositivo respaldada por DMA-buf. Este campo solo es utilizable si la aplicación ha solicitado con éxito el soporte de FI_HMEM y se ha pasado el indicador FI_MR_DMABUF a la llamada de registro de memoria. Las regiones DMA-buf son referencias basadas en archivos a la memoria del dispositivo. Dichas regiones se identifican a través de la estructura fi_mr_dmabuf.

struct fi_mr_dmabuf {
    int      fd;
    uint64_t offset;
    size_t   len;
    void     *base_addr;
};

El fd es el descriptor de archivo asociado con la región DMA-buf. El offset es el desplazamiento dentro de la región donde debe comenzar el registro de memoria. Y len es el tamaño de la región a registrar, comenzando en el offset. El base_addr es la dirección virtual de inicio alineada a página de la región de memoria asignada por el DMA-buf. Si no hay una dirección virtual base disponible (por ejemplo, porque el proceso que llama no ha mapeado la región de memoria en su espacio de direcciones), base_addr se puede establecer en NULL.

La selección de dmabuf sobre el campo mr_iov se controla especificando el indicador FI_MR_DMABUF.

iov_count

El número de entradas en el array mr_iov. El número máximo de búferes de memoria que pueden estar asociados con una sola región de memoria se especifica como el atributo de dominio mr_iov_limit. Véase fi_domain(3).

access

Indica el tipo de operaciones que un punto de extremo local o de un par puede realizar sobre la región de memoria registrada. Los permisos de acceso admitidos son el OR bit a bit de los siguientes indicadores:

FI_SEND
El búfer de memoria puede usarse en transferencias de datos de mensajes salientes. Esto incluye operaciones de envío de fi_msg y fi_tagged, así como operaciones de fi_collective.
FI_RECV
El búfer de memoria puede usarse para recibir transferencias de mensajes entrantes. Esto incluye operaciones de recepción de fi_msg y fi_tagged, así como operaciones de fi_collective.
FI_READ
El búfer de memoria puede usarse como búfer de resultado para operaciones de lectura RMA y operaciones atómicas en el lado iniciador. Nótese que desde el punto de vista de la aplicación, se está escribiendo en el búfer de memoria desde la red.
FI_WRITE
El búfer de memoria puede usarse como búfer de origen para operaciones de escritura RMA y operaciones atómicas en el lado iniciador. Nótese que desde el punto de vista de la aplicación, el punto de extremo está leyendo del búfer de memoria y copiando los datos en la red.
FI_REMOTE_READ
El búfer de memoria puede usarse como búfer de origen de una operación de lectura RMA en el lado objetivo. El contenido del búfer de memoria no se modifica por dichas operaciones.
FI_REMOTE_WRITE
El búfer de memoria puede usarse como búfer objetivo de una operación de escritura RMA o atómica. El contenido del búfer de memoria puede modificarse como resultado de dichas operaciones.
FI_COLLECTIVE
Este indicador proporciona una indicación explícita de que el búfer de memoria puede usarse con operaciones colectivas. El uso de este indicador es obligatorio si se ha establecido el bit mr_mode FI_MR_COLLECTIVE en el dominio. Este indicador debe combinarse con FI_SEND y/o FI_RECV.

Nótese que algunos proveedores pueden no hacer cumplir permisos de acceso de granularidad fina. Por ejemplo, una región de memoria registrada para acceso FI_WRITE también puede comportarse como si se hubiera especificado también FI_SEND. Se permite, aunque no se garantiza, un cumplimiento relajado de dicho acceso, siempre que se mantenga la seguridad.

offset

El campo offset está reservado para uso futuro y debe ser 0.

requested_key

Una clave de acceso especificada por la aplicación asociada con la región de memoria. La clave MR debe ser proporcionada por un proceso remoto al realizar operaciones RMA o atómicas sobre una región de memoria. Las aplicaciones pueden usar el campo requested_key para indicar que el proveedor use una clave específica. Esto permite a las aplicaciones usar valores de clave bien conocidos, lo que puede evitar que las aplicaciones necesiten intercambiar y almacenar claves. El soporte para claves solicitadas por el usuario es específico del proveedor y está determinado por el indicador FI_MR_PROV_KEY en el campo de atributo de dominio mr_mode. Dependiendo del proveedor, la clave solicitada por el usuario puede ignorarse si la región de memoria es solo para acceso local. Un proveedor puede ser incapaz de hacerlo si el hardware soporta claves solicitadas por el usuario y la misma clave se usa tanto para el acceso local como para el remoto.

context

Contexto de la aplicación asociado con operaciones de registro de memoria asíncronas. Este valor se devuelve como parte de cualquier evento asíncrono asociado con el registro. Este campo se ignora en las llamadas de registro síncronas.

auth_key_size

El tamaño en bytes de la clave referenciada por el campo auth_key, o 0 si no se proporciona ninguna clave de autorización. Este campo se ignora a menos que la red de interconexión se abra con la versión de API 1.5 o superior.

Si el dominio se abre con FI_AV_AUTH_KEY, auth_key_size debe ser igual a sizeof(struct fi_mr_auth_key).

auth_key

Indica la clave a asociar con este registro de memoria. Las claves de autorización se utilizan para limitar la comunicación entre puntos de extremo. Solo los puntos de extremo pares que estén programados para usar la misma clave de autorización pueden acceder a la región de memoria. Se usará la clave de autorización del dominio si el auth_key_size proporcionado es 0. Este campo se ignora a menos que la red de interconexión se abra con la versión de API 1.5 o superior.

Si el dominio se abre con FI_AV_AUTH_KEY, auth_key debe apuntar a una estructura fi_mr_auth_key definida por el usuario.

Indica las interfaces de software utilizadas por la aplicación para asignar y gestionar la región de memoria. Este campo se ignora a menos que la aplicación haya solicitado la capacidad FI_HMEM.

FI_HMEM_SYSTEM
Usa llamadas y bibliotecas estándar del sistema operativo, como malloc, calloc, realloc, mmap y free. Cuando iface está establecido en FI_HMEM_SYSTEM, el campo device (descrito más abajo) se ignora.
FI_HMEM_CUDA
Usa interfaces de Nvidia CUDA como cuMemAlloc, cuMemAllocHost, cuMemAllocManaged, cuMemFree, cudaMalloc, cudaFree.
FI_HMEM_ROCR
Usa interfaces de AMD ROCR como hsa_memory_allocate y hsa_memory_free.
FI_HMEM_ZE
Usa interfaces de oneAPI Level Zero como zeDriverAllocSharedMem, zeDriverFreeMem.
FI_HMEM_NEURON
Usa el SDK de AWS Neuron para soportar dispositivos AWS Trainium.
FI_HMEM_SYNAPSEAI
Usa la API de SynapseAI para soportar dispositivos Habana Gaudi.

64 bits reservados para el identificador del dispositivo si se usa una interfaz HMEM no estándar. Este campo se ignora a menos que el campo iface sea válido. De lo contrario, el campo device se determina por el valor especificado a través de iface.

cuda

ze

Para FI_HMEM_NEURON, el identificador del dispositivo para dispositivos AWS Trainium.
synapseai
Para FI_HMEM_SYNAPSEAI, el identificador del dispositivo para hardware Habana Gaudi.

hmem_data

El campo hmem_data está reservado para uso futuro y debe ser nulo.

page_size

El tamaño de página permite a las aplicaciones proporcionar opcionalmente una pista sobre cuál es el tamaño de página óptimo para una asignación MR. Normalmente, los proveedores pueden seleccionar el tamaño de página óptimo. En casos donde el rango de VA tiene cero páginas que lo respalden, lo cual se soporta con FI_MR_ALLOCATED sin establecer, el proveedor puede no conocer el tamaño de página óptimo durante el registro. En lugar de usar un tamaño de página menos eficiente, este atributo permite a las aplicaciones especificar el tamaño de página a usar.

Si el tamaño de página es cero, el proveedor seleccionará el tamaño de página.

Si es distinto de cero, el tamaño de página debe ser soportado por el SO. Si se especifica un tamaño de página específico para una región de memoria durante su creación, todas las páginas asociadas posteriormente con la región deben tener el tamaño dado. Adjuntar una página de memoria de un tamaño diferente a una región puede resultar en transferencias fallidas hacia o desde la región.

Los proveedores pueden optar por ignorar el tamaño de página. Esto resultará en que siempre se use un tamaño de página seleccionado por el proveedor.

base_mr

Si no es NULL, crea un sub-MR a partir de una región de memoria existente especificada por el campo base_mr.

El sub-MR debe estar completamente contenido dentro del MR base; sin embargo, el sub-MR tiene sus propias claves de autorización y derechos de acceso. Los siguientes atributos se heredan del base MR, y como resultado, se ignoran al crear el sub-MR:

iface, device, hmem_data, page_size

El sub-MR debe mantener una referencia al MR base. Cuando se llama a fi_close en el MR base, la llamada fallaría si hay sub-MR pendientes.

El campo base_mr debe ser NULL si se establece el indicador FI_MR_DMABUF.

sub_mr_cnt

El número de sub-MR que se espera crear a partir de la región de memoria. Este valor no es un límite. En cambio, es una sugerencia para el proveedor para permitir optimizaciones específicas del proveedor en la creación de sub-MR. Por ejemplo, el proveedor puede reservar claves de acceso u objetos fid_mr de preasignación. El proveedor puede ignorar esta sugerencia.

fi_hmem_ze_device

Devuelve un identificador de dispositivo hmem para una tupla <driver, device> de nivel cero. La salida de esta llamada debe usarse para establecer fi_mr_attr::device.ze para interfaces FI_HMEM_ZE. Los valores de índice del driver y del dispositivo representan sus posiciones basadas en cero en las matrices devueltas por zeDriverGet y zeDeviceGet, respectivamente.

av

Para el registro de memoria que se asigna contra un dominio configurado con FI_AV_AUTH_KEY, av se usa para definir el fid_av que contiene las claves de autorización que se asociarán con la región de memoria. Si el dominio también se abre con FI_MR_ENDPOINT, el AV especificado debe ser el mismo AV vinculado al punto de conexión.

De forma predeterminada, la región de memoria se asociará con todas las claves de autorización en el AV.

addr

Si el dominio se abrió con FI_DIRECTED_RECV, addr puede usarse para limitar la región de memoria a un fi_addr_t específico, incluyendo los fi_addr_t devueltos por fi_av_insert_auth_key.

NOTAS

El acceso directo a la memoria de una aplicación por un par remoto requiere que la aplicación registre los búferes de memoria objetivo. Esto se hace típicamente llamando a una de las rutinas fi_mr_reg*. Para FI_MR_PROV_KEY, el proveedor devolverá una clave que debe ser usada por el par al acceder a la región de memoria. La aplicación es responsable de transferir esta clave al par. Si se ha establecido el modo FI_MR_RAW, la clave debe recuperarse usando la función fi_mr_raw_attr.

FI_MR_RAW permite soporte para proveedores que requieren más de 8 bytes para sus claves de protección o necesitan configuración adicional antes de que una clave pueda usarse para transferencias. Después de recuperar una clave en bruto, debe intercambiarse con el par remoto. El par debe usar fi_mr_map_raw para convertir la clave en bruto en una clave de 64 bits utilizable. El mapeo debe hacerse incluso si la clave en bruto es de 64 bits o menos.

Las funciones de soporte de clave en bruto son utilizables con todas las regiones de memoria registradas, incluso si FI_MR_RAW no se ha establecido. Se recomienda que las aplicaciones portables apunten a usar esas interfaces; sin embargo, su uso conlleva una sobrecarga adicional de mensajes y memoria, lo que lo hace menos deseable para aplicaciones altamente escalables.

Puede haber casos en los que el soporte de dispositivo de igual a igual (peer to peer) no deba usarse o no pueda usarse, como cuando la configuración ACS de PCIe no permite la transferencia. La variable de entorno FI_HMEM_DISABLE_P2P puede establecerse para notificar a Libfabric que las transacciones de igual a igual no deben usarse. El proveedor puede optar por realizar una copia en su lugar, o fallará el soporte para FI_HMEM si el proveedor no puede hacer eso.

El siguiente indicador puede especificarse en cualquier llamada de registro de memoria.

FI_RMA_EVENT
Este indicador indica que la región de memoria especificada se asociará con un contador de finalización utilizado para contar operaciones RMA que acceden al MR.
FI_RMA_PMEM
Este indicador indica que la región de memoria subyacente está respaldada por memoria persistente y se usará en operaciones RMA. Debe especificarse si se requieren semánticas de finalización persistentes o transferencias de datos persistentes al acceder a la región registrada.
FI_HMEM_DEVICE_ONLY
Este indicador indica que la memoria solo es accesible por un dispositivo. Qué dispositivo está especificado por los campos iface y device de fi_mr_attr. Esto se refiere a regiones de memoria que fueron asignadas usando una llamada AllocDevice de API de dispositivo (en lugar de usar la asignación de host o la asignación de memoria unificada/compartida). Este indicador solo es usable para dominios abiertos con soporte de capacidad FI_HMEM.
FI_HMEM_HOST_ALLOC
Este indicador indica que la memoria es propiedad solo del host. Si puede ser accedida por el dispositivo depende de la implementación. El campo iface de fi_mr_attr todavía se usa para identificar la API del dispositivo, pero el campo device se ignora. Esto se refiere a regiones de memoria que fueron asignadas usando una llamada AllocHost de API de dispositivo (en lugar de usar una asignación de host tipo malloc, una asignación de memoria unificada/compartida, o AllocDevice). Este indicador solo es usable para dominios abiertos con soporte de capacidad FI_HMEM.
FI_MR_DMABUF
Este indicador indica que la región de memoria a registrar es una región respaldada por DMA-buf. Cuando se establece, la región se especifica a través del campo dmabuf de la estructura fi_mr_attr. Este indicador solo es usable para dominios abiertos con soporte de capacidad FI_HMEM.
FI_MR_SINGLE_USE
Este indicador indica que la región de memoria se usa solo para una sola operación. Después de que la operación se completa, la clave asociada con la región de memoria se invalida automáticamente y ya no puede usarse para acceso remoto.
FI_AUTH_KEY
Solo válido con dominios configurados con FI_AV_AUTH_KEY. Cuando se usa con fi_mr_regattr, este indicador denota que el campo fi_mr_auth_key::src_addr contiene una clave de autorización fi_addr_t (es decir, un fi_addr_t devuelto por fi_av_insert_auth_key) en lugar de un fi_addr_t de punto de conexión (es decir, un fi_addr_t devuelto por fi_av_insert / fi_av_insertsvc / fi_av_remove).

DOMINIOS DE MEMORIA

Los dominios de memoria identifican la separación física de la memoria que puede o no ser accesible a través del mismo espacio de direcciones virtual. Tradicionalmente, las aplicaciones solo trataban con un solo dominio de memoria, el de la memoria del host estrechamente acoplada con las CPU del sistema. Con la introducción de subsistemas de memoria de dispositivo y no uniforme, las aplicaciones a menudo necesitan ser conscientes de a qué dominio de memoria se mapea una dirección virtual particular.

Como regla general, los dispositivos físicos separados pueden considerarse que tienen sus propios dominios de memoria. Por ejemplo, una NIC puede tener memoria accesible por el usuario, y se consideraría un dominio de memoria separado de la memoria en una GPU. Tanto el dominio de memoria de la NIC como el de la GPU están separados de la memoria del sistema host. Las GPU individuales o los aceleradores de cómputo pueden tener dominios de memoria distintos, o pueden estar conectados de tal manera (por ejemplo, un tejido específico de GPU) que todas las GPU pertenecerían al mismo dominio de memoria. Desafortunadamente, identificar los dominios de memoria es específico de cada sistema y su configuración física y/o virtual.

Entender los dominios de memoria en entornos de memoria heterogénea es importante ya que puede impactar en el ordenamiento y visibilidad de los datos tal como los ve una aplicación. También es importante entender a qué dominio de memoria está más estrechamente acoplada una aplicación. En la mayoría de los casos, las aplicaciones están estrechamente acopladas a la memoria del host. Sin embargo, una aplicación que se ejecuta directamente en una GPU o NIC puede estar más estrechamente acoplada a la memoria asociada con esos dispositivos.

Las regiones de memoria a menudo se asocian con un solo dominio de memoria. El dominio a menudo está indicado por los campos iface y device de fi_mr_attr. Aunque es posible que las páginas físicas que respaldan una región de memoria virtual migren entre dominios de memoria basándose en patrones de acceso. Por ejemplo, las páginas físicas referenciadas por un rango de direcciones virtuales podrían migrar entre la memoria del host y la memoria de la GPU, dependiendo de qué unidad de cómputo la esté usando activamente.

Consulte las páginas de manual fi_endpoint(3) y fi_cq(3) para una discusión adicional sobre la semántica de ordenamiento de mensajes, datos y finalizaciones, incluyendo el impacto de los dominios de memoria.

CACHÉ DE REGISTRO DE MEMORIA

Muchas NIC de hardware accedidas por libfabric requieren que los búferes de datos se registren con el hardware mientras el hardware accede a ellos. Esto asegura que los mapeos de direcciones virtual a física para esos búferes no cambien mientras la transferencia está ocurriendo. El impacto en el rendimiento de registrar regiones de memoria puede ser significativo. Como resultado, algunos proveedores hacen uso de una caché de registro, particularmente cuando trabajan con aplicaciones que no son capaces de gestionar sus propios búferes de red. Una caché de registro evita la sobrecarga de registrar y desregistrar un búfer de datos con cada transferencia.

Si se va a usar una caché de registro para la memoria del host y del dispositivo, el dispositivo debe soportar direccionamiento virtual unificado. Si el dispositivo no soporta direccionamiento virtual unificado, ya sea que un additional se requiere una caché de registro para rastrear esta memoria del dispositivo, o la memoria del dispositivo no se puede almacenar en caché.

Como regla general, si el hardware requiere el bit de modo FI_MR_LOCAL descrito anteriormente, pero esto no es compatible con la aplicación, es posible que se utilice una caché de registro de memoria pueda estar en uso. Las siguientes variables de entorno se pueden utilizar para configurar las cachés de registro.

FI_MR_CACHE_MAX_SIZE
Esto define el número total de bytes para todas las regiones de memoria que la caché puede rastrear. Si no se establece, la caché no tiene límite en cuántos bytes se pueden registrar y almacenar en caché. Establecer esto reducirá la cantidad de memoria que no se está utilizando activamente como parte de una transferencia de datos que está registrada con un proveedor. De forma predeterminada, el tamaño de la caché es ilimitado.
FI_MR_CACHE_MAX_COUNT
Esto define el número total de regiones de memoria que se pueden registrar con la caché. Si no se establece, se elige un límite predeterminado. Establecer esto reducirá el número de regiones que se registran, independientemente de su tamaño, que no se están utilizando activamente como parte de una transferencia de datos. Establecer esto en cero desactivará el almacenamiento en caché de registros.
FI_MR_CACHE_MONITOR
El monitor de caché es responsable de detectar cambios en la memoria del sistema (FI_HMEM_SYSTEM) realizados entre las direcciones virtuales utilizadas por una aplicación y las páginas físicas subyacentes. Las opciones de monitor válidas son: userfaultfd, memhooks, kdreg2 y disabled. Seleccionar disabled desactivará la caché de registro. Userfaultfd es una característica del kernel de Linux utilizada para informar los cambios de mapeo de direcciones virtuales a físicas al espacio de usuario. Memhooks funciona interceptando las llamadas relevantes de asignación y liberación de memoria que pueden resultar en cambios en los mapeos, como malloc, mmap, free, etc. Tenga en cuenta que memhooks opera en la capa del enlazador elf y no usa los ganchos de memoria de glibc. Kdreg2 se proporciona como un módulo del kernel de Linux cargable.
FI_MR_CUDA_CACHE_MONITOR_ENABLED
El monitor de caché CUDA es responsable de detectar cambios en la memoria del dispositivo CUDA (FI_HMEM_CUDA) realizados entre las direcciones virtuales del dispositivo utilizadas por una aplicación y las páginas físicas del dispositivo subyacentes. Las opciones de monitor válidas son: 0 o 1. Tenga en cuenta que el monitor de memoria CUDA requiere una versión del toolkit CUDA con direccionamiento virtual unificado habilitado.
FI_MR_ROCR_CACHE_MONITOR_ENABLED
El monitor de caché ROCR es responsable de detectar cambios en la memoria del dispositivo ROCR (FI_HMEM_ROCR) realizados entre las direcciones virtuales del dispositivo utilizadas por una aplicación y las páginas físicas del dispositivo subyacentes. Las opciones de monitor válidas son: 0 o 1. Tenga en cuenta que el monitor de memoria ROCR requiere una versión de ROCR con direccionamiento virtual unificado habilitado.
FI_MR_ZE_CACHE_MONITOR_ENABLED
El monitor de caché ZE es responsable de detectar cambios en la memoria del dispositivo oneAPI Level Zero (FI_HMEM_ZE) realizados entre las direcciones virtuales del dispositivo utilizadas por una aplicación y las páginas físicas del dispositivo subyacentes. Las opciones de monitor válidas son: 0 o 1.

Es posible un acceso más directo a la caché de registro interna a través de la llamada fi_open(), utilizando el nombre de servicio “mr_cache”. Una vez abierto, se pueden instalar monitores de memoria personalizados. Un monitor de memoria es un componente de la caché responsable de detectar cambios en los mapeos de direcciones virtuales a físicas. Es posible cierto nivel de control sobre la caché a través de las variables de entorno mencionadas anteriormente.
