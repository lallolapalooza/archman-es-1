NOMBRE

fi_domain - Abrir un dominio de acceso a la fabrica

SINOPSIS

#include <rdma/fabric.h>
#include <rdma/fi_domain.h>
int fi_domain(struct fid_fabric *fabric, struct fi_info *info,
    struct fid_domain **domain, void *context);
int fi_domain2(struct fid_fabric *fabric, struct fi_info *info,
    struct fid_domain **domain, uint64_t flags, void *context);
int fi_close(struct fid *domain);
int fi_domain_bind(struct fid_domain *domain, struct fid *eq,
    uint64_t flags);
int fi_open_ops(struct fid *domain, const char *name, uint64_t flags,
    void **ops, void *context);
int fi_set_ops(struct fid *domain, const char *name, uint64_t flags,
    void *ops, void *context);

ARGUMENTOS

fabric
Dominio de la fabrica
info
Información de la fabrica, incluyendo capacidades y atributos del dominio. El struct fi_info debe haberse obtenido usando ya sea fi_getinfo() o fi_dupinfo().
domain
Un dominio de acceso abierto.
context
Contexto especificado por el usuario asociado con el dominio. Este contexto se devuelve como parte de cualquier evento asíncrono asociado con el dominio.
eq
Cola de eventos para operaciones asíncronas iniciadas en el dominio.
name
Nombre asociado con una interfaz.
ops
Operaciones de la interfaz de la fabrica.

DESCRIPCIÓN

Un dominio de acceso normalmente se refiere a una tarjeta de red (NIC) física o virtual o a un puerto de hardware; sin embargo, un dominio puede abarcar múltiples componentes de hardware para propósitos de conmutación por error o de distribución de datos. Un dominio define el límite para asociar diferentes recursos juntos. Los recursos de la fabrica que pertenecen al mismo dominio pueden compartir recursos.

fi_domain

Abre un dominio de acceso a la fabrica, también referido como un dominio de recursos. Los dominios de la fabrica se identifican por un nombre. Las propiedades del dominio abierto se especifican usando el parámetro info.

fi_domain2

Similar a fi_domain, pero acepta un parámetro extra flags. Principalmente usado para abrir un dominio par. Vea fi_peer(3).

fi_open_ops

fi_open_ops se usa para abrir interfaces específicas del proveedor. Las interfaces del proveedor pueden usarse para acceder a recursos y operaciones de bajo nivel que son específicas del dominio de recursos abierto. Los detalles de las interfaces del dominio están fuera del alcance de esta documentación.

fi_set_ops

fi_set_ops asigna devoluciones de llamada (callbacks) que un proveedor debería invocar en lugar de realizar tareas seleccionadas. Esto permite a los usuarios modificar o controlar el comportamiento predeterminado de un proveedor. Conceptualmente, permite al usuario enganchar funciones específicas usadas por un proveedor y reemplazarlas con las suyas propias.

Las operaciones que se están modificando se identifican usando una cadena de caracteres de uso general, pasada como el parámetro name. El formato del parámetro ops depende del valor de name. El parámetro ops referenciará una estructura que contiene las devoluciones de llamada y otros campos necesarios para que el proveedor invoque las funciones del usuario.

Si un proveedor acepta la anulación, devolverá FI_SUCCESS. Si la anulación es desconocida o no está soportada, el proveedor devolverá -FI_ENOSYS. Las anulaciones deberían establecerse antes de asignar recursos en el dominio.

Las siguientes operaciones fi_set_ops y estructuras de devolución de llamada correspondientes están definidas.

FI_SET_OPS_HMEM_OVERRIDE – Anulaciones de Memoria Heterogénea

La anulación de HMEM permite a los usuarios anular operaciones relacionadas con HMEM que un proveedor pueda realizar. Actualmente, el alcance de la anulación de HMEM es permitir a un usuario definir las funciones de movimiento de memoria que un proveedor debería usar al acceder a un búfer del usuario. Las funciones de movimiento de memoria definidas por el usuario necesitan tener en cuenta todos los diferentes tipos de interfaz (iface) de HMEM que un proveedor pueda encontrar.

Todos los objetos asignados contra un dominio heredarán esta anulación.

Lo siguiente es el nombre de la operación de anulación de HMEM y la estructura.

#define FI_SET_OPS_HMEM_OVERRIDE "hmem_override_ops"
struct fi_hmem_override_ops {
    size_t  size;
    ssize_t (*copy_from_hmem_iov)(void *dest, size_t size,
        enum fi_hmem_iface iface, uint64_t device, const struct iovec *hmem_iov,
        size_t hmem_iov_count, uint64_t hmem_iov_offset);
    ssize_t (*copy_to_hmem_iov)(enum fi_hmem_iface iface, uint64_t device,
    const struct iovec *hmem_iov, size_t hmem_iov_count,
        uint64_t hmem_iov_offset, const void *src, size_t size);
};

Todos los campos en struct fi_hmem_override_ops deben estar establecidos (no nulos) a un valor válido.

size
Esto debería establecerse a sizeof(struct fi_hmem_override_ops). El campo size se usa para propósitos de compatibilidad hacia adelante y hacia atrás.
copy_from_hmem_iov
Copia datos desde el dispositivo/hmem a la memoria del host. Esta función debería devolver un fi_errno negativo en caso de error, o el número de bytes copiados en caso de éxito.
copy_to_hmem_iov
Copia datos desde la memoria del host al dispositivo/hmem. Esta función debería devolver un fi_errno negativo en caso de error, o el número de bytes copiados en caso de éxito.

fi_domain_bind

Asocia una cola de eventos con el dominio. Una cola de eventos ligada a un dominio será la cola de eventos (EQ) predeterminada asociada con eventos de control asíncronos que ocurren en el dominio o en puntos finales activos asignados en un dominio. Esto incluye eventos de CM (gestión de conexión). Los puntos finales pueden dirigir sus eventos de control a EQs alternativas ligándose directamente con la EQ.

Obsoleto: Ligar una cola de eventos a un dominio con la bandera FI_REG_MR indica que el proveedor debería realizar todas las operaciones de registro de memoria de forma asíncrona, con la finalización reportada a través de la cola de eventos. Si una cola de eventos no está ligada al dominio con la bandera FI_REG_MR, entonces las solicitudes de registro de memoria se completan de forma sincrónica.

fi_close

La llamada fi_close se usa para liberar todos los recursos asociados con un dominio o interfaz. Todos los objetos asociados con el dominio abierto deben ser liberados antes de llamar a fi_close, de lo contrario la llamada devolverá -FI_EBUSY.

La columna de recurso indica el recurso al que accede una operación de transferencia de datos.

Ctx Tx / Ctx Rx
Se refiere a los contextos de transmisión/recepción cuando se envía una operación de transferencia de datos. Cuando RM está habilitado, el intento de enviar una solicitud fallará si el contexto está lleno. Si RM está deshabilitado, ocurrirá un error no definido (específico del proveedor). Dichos errores deben considerarse fatales para el contexto, y las aplicaciones deben tomar medidas para evitar desbordamientos de la cola.
CQ Tx / CQ Rx
Se refiere a la cola de finalización asociada con el contexto Tx o Rx cuando una operación local se completa. Cuando RM está deshabilitado, las aplicaciones deben tener cuidado de asegurarse de que las colas de finalización no se desborden. Cuando ocurre un desbordamiento, ocurrirá un error no definido pero fatal que afectará a todos los puntos finales asociados con la CQ. Los desbordamientos pueden evitarse dimensionando las CQs adecuadamente o posponiendo el envío de una operación de transferencia de datos a menos que haya espacio disponible en la CQ para almacenar su finalización. Cuando RM está habilitado, los proveedores pueden usar diferentes mecanismos para prevenir desbordamientos de la CQ. Esto incluye fallar (devolver -FI_EAGAIN) el envío de operaciones que podrían resultar en desbordamientos de la CQ, o reintentar internamente las solicitudes (lo cual será oculto a la aplicación). Véanse las notas al final de esta sección sobre las restricciones de gestión de recursos de la CQ.
EP destino / Sin búfer Rx
EP destino se refiere a los recursos asociados con el punto final que es el destino de una operación de transmisión. Esto incluye la cola de recepción del punto final destino, los búferes de recepción publicados (sin búferes Rx), la cola de finalización del lado de recepción y otras colas de procesamiento de paquetes relacionadas. El comportamiento definido es el que ve el iniciador de una solicitud. Para los puntos finales FI_EP_DGRAM, si las colas del EP destino no pueden aceptar mensajes entrantes, los mensajes recibidos se descartarán. Para los puntos finales confiables, si RM está deshabilitado, la operación de transmisión se completará con error. Un proveedor puede optar por devolver una finalización de error con el código de error FI_ENORX para esa operación de transmisión para que pueda reintentarse. Si RM está habilitado, el proveedor reintentará internamente la operación.
Desbordamiento de búfer Rx
Esto se refiere a los búferes publicados para recibir mensajes etiquetados o no etiquetados entrantes, con el comportamiento definido desde el punto de vista del emisor. El comportamiento para manejar los mensajes recibidos que son más grandes que los búferes proporcionados por la aplicación es específico del proveedor. Los proveedores pueden truncar el mensaje y reportar una finalización exitosa, o fallar la operación. Para los puntos finales de datagrama, los envíos fallidos resultarán en que el mensaje sea descartado. Para los puntos finales confiables, las operaciones de envío pueden completarse con éxito, pero ser truncadas en el lado de recepción. Esto puede ocurrir cuando el lado destino almacena datos recibidos hasta que un búfer de aplicación está disponible. El estado de finalización también puede depender del modelo de finalización seleccionado por la aplicación (por ejemplo, FI_DELIVERY_COMPLETE versus FI_TRANSMIT_COMPLETE).
RMA no coincidente / Desbordamiento de RMA
RMA no coincidente y desbordamientos de RMA tratan con el procesamiento de operaciones RMA y atómicas. A diferencia de las operaciones de envío, las operaciones RMA que intentan acceder a una dirección de memoria que no está registrada para tales operaciones, o intentan acceder fuera de la región de memoria destino, fallarán, resultando en un error de transmisión.
EP inaccesible
Punto final inaccesible es un escenario específico de conexión sin conexión donde las operaciones de transmisión se emiten a puntos finales destino inaccesibles. Dichos escenarios incluyen no-ruta-al-host o NIC destino caída. Para los puntos finales FI_EP_DGRAM, las operaciones de transmisión dirigidas a un punto final inaccesible tendrán la operación descartada. Para FI_EP_RDM, las operaciones destino dirigidas a un punto final inaccesible resultarán en un error de transmisión.

Cuando ocurre un error de gestión de recursos en un punto final conectado, el punto final transicionará a un estado deshabilitado y la conexión se desmontará. Un punto final deshabilitado descartará cualquier operación en cola o en vuelo.

El comportamiento de los errores de gestión de recursos en puntos finales sin conexión depende del tipo de error. Si RM está deshabilitado y ocurre uno de los siguientes errores, el punto final será deshabilitado: Ctx Tx, Ctx Rx, CQ Tx o CQ Rx. Para otros errores (EP destino, sin búfer Rx, etc.), la operación puede fallar, pero el punto final permanecerá habilitado. Un punto final deshabilitado descartará o fallará cualquier operación en cola o en vuelo. Además, un punto final deshabilitado debe ser rehabilitado antes de que acepte nuevas operaciones de transferencia de datos.

Hay una restricción notable en las protecciones ofrecidas por la gestión de recursos. Esto ocurre cuando la gestión de recursos está habilitada en un punto final que ha sido vinculado a cola(s) de finalización usando el flag FI_SELECTIVE_COMPLETION. Las operaciones enviadas a tal punto final pueden especificar que una finalización exitosa no debe generar una entrada en la cola de finalización correspondiente. (Es decir, la operación deja el flag FI_COMPLETION sin establecer). En tales situaciones, el proveedor no está obligado a reservar una entrada en la cola de finalización para manejar el caso donde la operación falla y sí genera una entrada en la CQ, lo cual requeriría efectivamente rastrear la operación hasta su finalización. Las aplicaciones preocupadas por evitar desbordamientos de la CQ en la ocurrencia de errores deben asegurarse de que hay espacio suficiente en la CQ para reportar operaciones fallidas. Esto generalmente se logra dimensionando la CQ al menos al mismo tamaño que la(s) cola(s) del punto final que están vinculadas a ella.

Tipo AV (av_type)

Especifica el tipo de vectores de dirección que son utilizables con este dominio. Para detalles adicionales sobre el tipo de AV, véase fi_av(3). Los siguientes valores pueden ser especificados.

FI_AV_MAP (obsoleto)
Solo se solicitan o soportan vectores de dirección de tipo AV map.
FI_AV_TABLE
Solo se solicitan o soportan vectores de dirección de tipo AV index.
FI_AV_UNSPEC
Se solicita y soporta cualquier formato de vector de dirección.

Los vectores de dirección solo son usados por puntos finales sin conexión. Las aplicaciones que requieran el uso de un tipo específico de vector de dirección deben establecer el atributo de dominio av_type al valor necesario cuando llamen a fi_getinfo. El valor FI_AV_UNSPEC puede usarse para indicar que el proveedor puede soportar cualquiera de los formatos de vector de dirección. En este caso, un proveedor puede devolver FI_AV_UNSPEC para indicar que cualquiera de los formatos es soportable, o puede devolver otro tipo de AV para indicar el tipo de AV óptimo soportado por este dominio.

Modo de Registro de Memoria (mr_mode)

Define los bits de modo específicos del registro de memoria utilizados con este dominio. Los detalles completos sobre las opciones del modo MR están disponibles en fi_mr(3). Los siguientes valores pueden ser especificados.

FI_MR_ALLOCATED
Indica que el registro de memoria ocurre en búferes de datos asignados, y las páginas físicas deben respaldar todas las direcciones virtuales que se están registrando.
FI_MR_COLLECTIVE
Requiere que los búferes de datos pasados a las operaciones colectivas sean explícitamente registrados para operaciones colectivas utilizando el indicador FI_COLLECTIVE.
FI_MR_ENDPOINT
El registro de memoria ocurre a nivel de punto de extremo (endpoint), más bien que a nivel de dominio.
FI_MR_LOCAL
El proveedor está optimizado para que las aplicaciones registren memoria para los búferes de datos accedidos localmente. Los búferes de datos utilizados en operaciones de envío y recepción y como búfer de origen para operaciones RMA y atómicas deben ser registrados por la aplicación para dominios de acceso abiertos con esta capacidad.
FI_MR_MMU_NOTIFY
Indica que la aplicación es responsable de notificar al proveedor cuando las tablas de páginas que referencian una región de memoria registrada pueden haber sido actualizadas.
FI_MR_PROV_KEY
Las claves de registro de memoria son seleccionadas y devueltas por el proveedor.
FI_MR_RAW
El proveedor requiere configuración adicional como parte de su proceso de registro de memoria. Este modo es requerido por proveedores que utilizan una clave de memoria que es mayor que 64 bits.
FI_MR_RMA_EVENT
Indica que las regiones de memoria asociadas con contadores de finalización deben ser habilitadas explícitamente después de ser vinculadas a cualquier contador.
FI_MR_UNSPEC (obsoleto)
Definido para compatibilidad – versiones de biblioteca 1.4 y anteriores. Establecer mr_mode en 0 indica que se solicita y soporta FI_MR_BASIC o FI_MR_SCALABLE.
FI_MR_VIRT_ADDR
Las regiones de memoria registradas son referenciadas por los pares utilizando la dirección virtual de la región de memoria registrada, en lugar de un desplazamiento basado en 0.
FI_MR_BASIC (obsoleto)
Definido para compatibilidad – versiones de biblioteca 1.4 y anteriores. Solo se solicitan o soportan operaciones básicas de registro de memoria. Este modo es equivalente a que los indicadores FI_MR_VIRT_ADDR, FI_MR_ALLOCATED y FI_MR_PROV_KEY estén establecidos en versiones posteriores de la biblioteca. Este indicador no puede ser utilizado en conjunto con otros bits de mr_mode.
FI_MR_SCALABLE (obsoleto)
Definido para compatibilidad – versiones de biblioteca 1.4 y anteriores. Solo se solicitan o soportan operaciones escalables de registro de memoria. El registro escalable utiliza direccionamiento basado en desplazamientos, con claves de memoria seleccionables por la aplicación. Para versiones de biblioteca 1.5 y posteriores, este es el valor predeterminado si no se establecen bits de mr_mode. Este indicador no puede ser utilizado en conjunto con otros bits de mr_mode.

Los búferes utilizados en operaciones de transferencia de datos pueden requerir notificar al proveedor de su uso antes de que una transferencia de datos pueda ocurrir. El campo mr_mode indica el tipo de registro de memoria que es requerido, y cuando el registro es necesario. Las aplicaciones que requieran el uso de un modo de registro específico deben establecer el atributo de dominio mr_mode al valor necesario al llamar a fi_getinfo. El valor FI_MR_UNSPEC puede ser utilizado para indicar soporte para cualquier modo de registro.

Tamaño de la Clave MR (mr_key_size)

Tamaño de la clave de acceso remoto de la región de memoria, en bytes. Las aplicaciones que soliciten su propia clave MR deben seleccionar un valor dentro del rango especificado por este valor. Tamaños de clave mayores que 8 bytes requieren usar el bit de modo FI_RAW_KEY.

Tamaño de Datos de la Cola de Finalización (cq_data_size)

Las aplicaciones pueden incluir un mensaje pequeño con una transferencia de datos que es colocado directamente en una cola de finalización remota como parte de un evento de finalización. Esto se conoce como datos de CQ remotos (a veces referidos como datos inmediatos). Este campo indica el número de bytes que el proveedor soporta para datos de CQ remotos. Si se soporta (se devuelve un valor distinto de cero), el tamaño mínimo de datos de CQ remotos debe ser al menos 4 bytes.

Recuento de Colas de Finalización (cq_cnt)

El número óptimo de colas de finalización soportadas por el dominio, relativo a cualquier atributo de CQ especificado o predeterminado. El valor cq_cnt puede ser un valor fijo del máximo número de CQs soportadas por el hardware subyacente, o puede ser un valor dinámico, basado en los atributos predeterminados de una CQ asignada, como el tamaño de la CQ y el formato de datos.

Recuento de Puntos de Extremo (ep_cnt)

El número total de puntos de extremo soportados por el dominio, relativo a cualquier atributo de punto de extremo especificado o predeterminado. El valor ep_cnt puede ser un valor fijo del máximo número de puntos de extremo soportados por el hardware subyacente, o puede ser un valor dinámico, basado en los atributos predeterminados de un punto de extremo asignado, como las capacidades y el tamaño del punto de extremo. El recuento de puntos de extremo es el número de puntos de extremo direccionables soportados por el proveedor. Los proveedores devuelven límites de capacidad basados en las capacidades máximas de hardware configuradas. Los proveedores no pueden predecir todas las posibles limitaciones del sistema sin conocimiento a posteriori adquirido durante el tiempo de ejecución que limitará aún más estos máximos de hardware (por ejemplo, consumo de memoria de la aplicación, uso de FD, etc.).

Recuento de Contextos de Transmisión (tx_ctx_cnt)

El número de colas de comandos salientes óptimamente soportadas por el proveedor. Para un proveedor de bajo nivel, esto representa el número de colas de comandos al hardware y/o el número de motores de transmisión paralelos efectivamente soportados por el hardware y las cachés. Las aplicaciones que asignen más contextos de transmisión que este valor terminarán compartiendo recursos subyacentes. Por defecto, hay un solo contexto de transmisión asociado con cada punto de extremo, pero en un modelo de uso avanzado, un punto de extremo puede ser configurado con múltiples contextos de transmisión.

Recuento de Contextos de Recepción (rx_ctx_cnt)

El número de colas de procesamiento entrantes óptimamente soportadas por el proveedor. Para un proveedor de bajo nivel, esto representa el número de colas de hardware que pueden ser efectivamente utilizadas para procesar paquetes entrantes. Las aplicaciones que asignen más contextos de recepción que este valor terminarán compartiendo recursos subyacentes. Por defecto, un solo contexto de recepción es asociado con cada punto de extremo, pero en un modelo de uso avanzado, un punto de extremo puede ser configurado con múltiples contextos de recepción.

Contexto de Transmisión Máximo del Punto de Extremo (max_ep_tx_ctx)

El número máximo de contextos de transmisión que pueden ser asociados con un punto de extremo.

Contexto de Recepción Máximo del Punto de Extremo (max_ep_rx_ctx)

El número máximo de contextos de recepción que pueden ser asociados con un punto de extremo.

Máximo Compartición de Contexto de Transmisión (max_ep_stx_ctx)

El número máximo de puntos de extremo que pueden ser asociados con un contexto de transmisión compartido.

Máximo Compartición de Contexto de Recepción (max_ep_srx_ctx)

El número máximo de puntos de extremo que pueden ser asociados con un contexto de recepción compartido.

Recuento de Contadores (cntr_cnt)

El número óptimo de contadores de finalización soportados por el dominio. El valor cq_cnt puede ser un valor fijo del máximo número de contadores soportados por el hardware subyacente, o puede ser un valor dinámico, basado en los atributos predeterminados del dominio.

Límite de IOV de MR (mr_iov_limit)

Este es el número máximo de vectores de IO (elementos de dispersión-agrupación) que una sola operación de registro de memoria puede referenciar.

Capacidades (caps)

Capacidades a nivel de dominio. Las capacidades del dominio indican características a nivel de dominio que son soportadas por el proveedor.

Las siguientes son las capacidades primarias soportadas: FI_DIRECTED_RECV : Cuando el dominio está configurado con FI_DIRECTED_RECV y FI_AV_AUTH_KEY, las regiones de memoria pueden ser limitadas a claves de autorización específicas.

FI_AV_USER_ID
Indica que el dominio soporta la capacidad de abrir vectores de dirección con el indicador FI_AV_USER_ID. Si esta capacidad de dominio no está establecida, los vectores de dirección no pueden ser abiertos con FI_AV_USER_ID. Tenga en cuenta que FI_AV_USER_ID puede seguir siendo soportado a través de las llamadas de inserción de AV sin esta capacidad de dominio establecida. Vea fi_av(3).
FI_PEER
Especifica que el dominio debe soportar la importación de recursos para ser utilizados en el flujo de la API de pares. El dominio debe soportar la importación owner_ops al abrir un CQ, un contador y una cola de recepción compartida.

Se admiten las siguientes capacidades secundarias:

FI_LOCAL_COMM
A un nivel conceptual, este campo indica que el dispositivo subyacente admite comunicación en bucle (loopback). Más específicamente, este campo indica que un punto final (endpoint) puede comunicarse con otros puntos finales asignados desde el mismo dominio con nombre subyacente. Si este campo no está establecido, una aplicación puede necesitar usar un dominio o mecanismo alternativo (por ejemplo, memoria compartida) para comunicarse con pares que se ejecutan en el mismo nodo.
FI_REMOTE_COMM
Este campo indica que el proveedor subyacente admite la comunicación con nodos que son alcanzables a través de la red. Si este campo no está establecido, entonces el proveedor solo admite la comunicación entre procesos que se ejecutan en el mismo nodo, por ejemplo, un proveedor de memoria compartida.
FI_SHARED_AV
Indica que el dominio admite la capacidad de compartir vectores de dirección (address vectors) entre múltiples procesos utilizando la función de vector de dirección con nombre.

Consulte fi_getinfo(3) para una discusión sobre capacidades primarias frente a secundarias.

Clave de autorización predeterminada (auth_key)

La clave de autorización predeterminada que se asociará con los puntos finales y los registros de memoria creados dentro del dominio. Este campo se ignora a menos que la fabrica se abra con la versión de la API 1.5 o superior.

Si el auth_key_size del dominio está establecido en el valor FI_AV_AUTH_KEY, auth_key debe ser NULL.

Longitud de la clave de autorización predeterminada (auth_key_size)

La longitud en bytes de la clave de autorización predeterminada para el dominio. Si se establece en 0, no se asociará ninguna clave de autorización con los puntos finales y los registros de memoria creados dentro del dominio, a menos que se especifique en los atributos del punto final o del registro de memoria. Este campo se ignora a menos que la fabrica se abra con la versión de la API 1.5 o superior.

Si el tamaño se establece en el valor FI_AV_AUTH_KEY, todos los puntos finales y las regiones de memoria se configurarán para usar claves de autorización asociadas con el AV. Los proveedores que admitan claves de autorización y puntos finales sin conexión (connectionless) deben admitir esta opción.

Tamaño máximo de datos de error (max_err_data)

La cantidad máxima de datos de error, en bytes, que pueden devolverse como parte de un error de cola de finalización (completion) o de eventos. Este valor corresponde al campo err_data_size en struct fi_cq_err_entry y struct fi_eq_err_entry.

Número de regiones de memoria (mr_cnt)

El número óptimo de regiones de memoria admitidas por el dominio, o por el punto final si se ha establecido el bit FI_MR_ENDPOINT en mr_mode. El valor de mr_cnt puede ser un valor fijo del número máximo de MRs admitidas por el hardware subyacente, o puede ser un valor dinámico, basado en los atributos predeterminados del dominio, como los modos de registro de memoria admitidos. Las aplicaciones pueden establecer el mr_cnt en la entrada de fi_getinfo, para indicar sus requisitos de registro de memoria. Hacerlo puede permitir al proveedor optimizar cualquier caché de registro de memoria o tablas de búsqueda.

Clase de tráfico (tclass)

Esto especifica la clase de tráfico predeterminada que se asociará a cualquier punto final creado dentro del dominio. Consulte fi_endpoint(3) para información adicional.

Máximo de claves de autorización por punto final (max_ep_auth_key)

El número máximo de claves de autorización que pueden ser soportadas por cada punto final sin conexión (connectionless).

Identificador máximo de grupo de pares (max_group_id)

El valor máximo que se le puede asignar a un grupo de pares, inclusive. Los identificadores de grupo de pares válidos deben estar entre 0 y max_group_id. Consulte fi_av(3) para información adicional sobre grupos de pares y su uso. Los usuarios pueden solicitar soporte para grupos de pares estableciendo esto en un valor distinto de cero. Los proveedores que no puedan cumplir con el max_group_id solicitado fallarán en fi_getinfo(). En la salida, los proveedores pueden devolver un valor más alto que el solicitado por la aplicación.

VALOR DE RETORNO

Devuelve 0 en caso de éxito. En caso de error, se devuelve un valor negativo correspondiente al errno de la fabrica. Los valores de errno de la fabrica están definidos en rdma/fi_errno.h.

NOTAS

Los usuarios deben llamar a fi_close para liberar todos los recursos asignados al dominio de la fabrica.

Los siguientes recursos de la fabrica están asociados con los dominios: puntos finales activos, regiones de memoria, colas de eventos de finalización y vectores de dirección.

Los atributos del dominio reflejan las limitaciones y capacidades del hardware y/o del proveedor de software subyacente. No reflejan las limitaciones del sistema, como el número de páginas físicas que una aplicación puede fijar (pin) o el número de descriptores de archivo que la aplicación puede abrir. Como resultado, los máximos reportados pueden no ser alcanzables, incluso en sistemas con poca carga, a menos que un administrador configure los recursos del sistema de manera apropiada para el/los proveedor(es) instalado(s).
