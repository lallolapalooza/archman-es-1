NOMBRE

fi_mr - Operaciones de región de memoria

fi_mr_reg / fi_mr_regv / fi_mr_regattr
Registrar búferes de memoria local para acceso directo a la red.
fi_close
Anular el registro de búferes de memoria registrados.
fi_mr_desc
Devolver un descriptor local asociado con una región de memoria registrada.
fi_mr_key
Devolver la clave remota necesaria para acceder a una región de memoria registrada.
fi_mr_raw_attr
Devolver atributos de región de memoria sin procesar.
fi_mr_map_raw
Convierte una clave de región de memoria sin procesar en una clave que se puede utilizar para operaciones de transferencia de datos.
fi_mr_unmap_key
Libera una clave de región de memoria sin procesar previamente mapeada.
fi_mr_bind
Asociar una región de memoria registrada con un contador de finalización o un punto final.
fi_mr_refresh
Actualiza las páginas de memoria asociadas con una región de memoria.
fi_mr_enable
Habilita una región de memoria para su uso.
fi_hmem_ze_device
Devuelve un identificador de dispositivo hmem para un controlador y dispositivo de nivel cero.

DESCRIPCIÓN

Las regiones de memoria registradas asocian búferes de memoria con permisos concedidos para el acceso por parte de recursos de red. Un búfer de memoria debe registrarse con un dominio de recursos antes de que pueda utilizarse como destino de RMA remota o transferencia de datos atómica. Además, un proveedor de red puede requerir que los búferes de datos se registren antes de ser utilizados en transferencias locales. Las restricciones de registro de memoria se controlan mediante un conjunto separado de indicadores de modo, especificados a través de los atributos del dominio (campo mr_mode). Cada indicador mr_mode requiere que una aplicación tome medidas específicas para utilizar los búferes de memoria con las interfaces de libfabric.

Como caso especial, se puede crear una nueva región de memoria a partir de una región de memoria existente. Dicha nueva región de memoria se denomina sub-MR y la región de memoria existente se denomina MR base. Las sub-MR pueden utilizarse para compartir recursos de hardware, como las traducciones de direcciones virtuales a físicas y el anclaje de páginas. Esto puede mejorar el rendimiento al crear y destruir subregiones que necesitan diferentes derechos de acceso. La MR base en sí misma también puede ser una sub-MR, lo que permite una jerarquía de regiones de memoria.

Lo siguiente se aplica al registro de memoria.

Registro de Memoria Predeterminado
Si no se establecen indicadores mr_mode, se siguen los comportamientos predeterminados descritos a continuación. Históricamente, estos predeterminados se denominaban colectivamente registro de memoria escalable. Los requisitos predeterminados se describen a continuación, seguidos de las definiciones de cómo cada indicador mr_mode altera la definición.

Compatibilidad: Para las versiones de biblioteca 1.4 y anteriores, esto se indicaba estableciendo mr_mode en FI_MR_SCALABLE y el indicador de modo fi_info FI_LOCAL_MR en 0. FI_MR_SCALABLE y FI_LOCAL_MR fueron deprecados en la versión 1.5 de libfabric, aunque se admiten por motivos de compatibilidad con versiones anteriores.

Por seguridad, se requiere el registro de memoria para los búferes de datos a los que accede directamente un proceso par. Por ejemplo, el registro es necesario para los búferes de destino de RMA (leídos o escritos), y aquellos a los que acceden las operaciones atómicas o colectivas.

Por defecto, el registro se realiza en rangos de direcciones virtuales. Dado que el registro se refiere a rangos de direcciones, en lugar de a búferes de datos asignados, los rangos de direcciones no necesitan corresponder a búferes de datos asignados por la aplicación en el momento de realizar la llamada de registro. Es decir, una aplicación puede registrar cualquier rango de direcciones en su espacio de direcciones virtual, ya sea que esas direcciones estén respaldadas por páginas físicas o hayan sido asignadas.

Tenga en cuenta que las páginas físicas deben respaldar las direcciones antes de que estas se accedan como parte de una operación de transferencia de datos, o las transferencias de datos fallarán. Además, dependiendo de la operación, esto podría resultar en que el proceso local reciba una falla de segmentación por acceder a memoria inválida.

Una vez registrados, las regiones de memoria resultantes son accesibles por los pares comenzando en una dirección base de 0. Es decir, la dirección de destino especificada es un desplazamiento en bytes dentro de la región registrada.

La aplicación también selecciona la clave de acceso asociada con la MR. El tamaño de la clave se limita a un máximo de 8 bytes.

Con el registro escalable, los búferes de datos accedidos localmente no se registran. Esto incluye los búferes de origen para todas las operaciones de transmisión (envíos, envíos etiquetados, RMA y atómicas), así como los búferes publicados para operaciones de recepción y recepción etiquetada.

Aunque el comportamiento predeterminado de registro de memoria es conveniente para los desarrolladores de aplicaciones, es difícil de implementar en hardware. Los intentos de ocultar los requisitos de hardware a la aplicación a menudo resultan en impactos significativos e inaceptables en el rendimiento. Los indicadores mr_mode siguientes se proporcionan como entrada a fi_getinfo. Si un proveedor requiere el comportamiento definido para un indicador mr_mode, dejará el indicador activado en la salida de fi_getinfo. De lo contrario, el proveedor puede desactivar el indicador para indicar que el comportamiento no es necesario.

Al establecer un indicador mr_mode, la aplicación ha aceptado ajustar su comportamiento según lo indicado. Es importante destacar que las aplicaciones que optan por admitir un mr_mode deben estar preparadas para manejar el caso en que el mr_mode no sea necesario. Un proveedor desactivará un indicador mr_mode si no es necesario.

FI_MR_LOCAL
Cuando se establece el bit de modo FI_MR_LOCAL, las aplicaciones deben registrar todos los búferes de datos a los que accederá el hardware local y proporcionar un parámetro desc válido en las operaciones de transferencia de datos aplicables.

Cuando FI_MR_LOCAL no está establecido, las aplicaciones no están obligadas a registrar los búferes de datos antes de usarlos para operaciones locales (por ejemplo, búferes de datos de envío y recepción). Antes de libfabric 1.22, el parámetro desc era ignorado. En libfabric 1.22 y versiones posteriores, el parámetro desc debe ser válido o NULL. Este comportamiento permite a las aplicaciones pasar opcionalmente un parámetro desc válido. Si el parámetro desc es NULL, cualquier registro de memoria local requerido será manejado por el proveedor.

Un proveedor puede ocultar los requisitos de registro local a las aplicaciones utilizando una caché de registro interna o mecanismos similares. Sin embargo, dichos mecanismos pueden afectar negativamente el rendimiento de algunas aplicaciones, notablemente aquellas que gestionan sus propios búferes de red. Para soportar el mayor rango posible de aplicaciones, sin afectar indebidamente su rendimiento, las aplicaciones que deseen gestionar sus propios registros de memoria local pueden hacerlo utilizando las llamadas de registro de memoria y pasando un parámetro desc válido.

Nota: el bit mr_mode FI_MR_LOCAL reemplaza al bit de modo fi_info FI_LOCAL_MR. Cuando FI_MR_LOCAL está establecido, FI_LOCAL_MR es ignorado.

FI_MR_RAW
Las regiones de memoria sin procesar (raw) se utilizan para soportar proveedores con claves de más de 64 bits o que requieren configuración en el par. Cuando el bit FI_MR_RAW está establecido, las aplicaciones deben usar fi_mr_raw_attr() localmente y fi_mr_map_raw() en el par antes de dirigirse a una región de memoria como parte de cualquier solicitud de transferencia de datos.
FI_MR_VIRT_ADDR
El bit FI_MR_VIRT_ADDR indica que el proveedor referencia las regiones de memoria por dirección virtual, en lugar de un desplazamiento basado en cero. Los pares que se dirigen a regiones de memoria registradas con FI_MR_VIRT_ADDR especifican el búfer de memoria de destino utilizando la dirección virtual del destino, con cualquier desplazamiento dentro de la región especificado como dirección virtual + desplazamiento. El soporte de este bit generalmente implica que los pares deben intercambiar datos de direccionamiento antes de iniciar cualquier operación RMA o atómica.

Para las regiones de memoria que están registradas usando FI_MR_DMABUF, la `dirección virtual' inicial de la región DMA-buf se obtiene añadiendo el campo offset al campo base_addr de la estructura fi_mr_dmabuf que fue especificada a través de la llamada de registro.

FI_MR_ALLOCATED
Cuando está establecido, todas las regiones de memoria registradas deben estar respaldadas por páginas de memoria física en el momento en que se realiza la llamada de registro. Además, las aplicaciones no deben realizar operaciones que puedan resultar en un cambio en el mapeo de la dirección virtual subyacente a la página física (por ejemplo, llamar a free() contra una MR asignada). El incumplimiento de esto puede resultar en que la dirección virtual apunte a un conjunto de páginas físicas mientras que la MR apunta a otro conjunto de páginas físicas.

Cuando no está establecido, las regiones de memoria registradas no necesitan estar respaldadas por páginas de memoria física en el momento en que se realiza la llamada de registro. Además, se permite que el mapeo subyacente de la dirección virtual a la página física cambie, y el proveedor se asegurará de que la MR correspondiente se actualice en consecuencia. Este comportamiento permite casos de uso de la aplicación donde la memoria puede ser frecuentemente liberada y realocada o la memoria del sistema migrando hacia/desde la memoria del dispositivo.

Cuando no está establecido, la aplicación es responsable de asegurar que una región de memoria registrada referencie páginas físicas válidas mientras una transferencia de datos está activa contra ella, o la transferencia de datos puede fallar. Los cambios de la aplicación en el rango de direcciones virtuales deben coordinarse con el tráfico de red hacia o desde ese rango.

Si no está establecido y FI_HMEM es soportado, la capacidad del mapeo de dirección virtual a dirección física para cambiar se extiende a las interfaces HMEM también. Si un proveedor no puede soportar un cambio de dirección virtual a dirección física para una interfaz HMEM dada, el proveedor debería soportar una alternativa razonable o la operación debería fallar.

FI_MR_PROV_KEY
Este modo de región de memoria indica que el proveedor no soporta claves de MR solicitadas por la aplicación. Las claves de MR son devueltas por el proveedor. Las aplicaciones que soportan FI_MR_PROV_KEY pueden obtener la clave del proveedor usando fi_mr_key(), a menos que FI_MR_RAW también esté establecido. La clave devuelta debe ser intercambiada con los pares antes de iniciar una operación RMA o atómica.
FI_MR_MMU_NOTIFY
FI_MR_MMU_NOTIFY es típicamente establecido por proveedores que soportan el registro de memoria contra regiones de memoria que no están necesariamente respaldadas por páginas físicas asignadas en el momento en que ocurre el registro de memoria. (Es decir, FI_MR_ALLOCATED es típicamente 0). Sin embargo, dichos proveedores requieren que las aplicaciones notifiquen al proveedor antes de que la MR sea accedida como parte de una operación de transferencia de datos. Esta notificación informa al proveedor que todas las páginas físicas necesarias respaldan ahora la región. La notificación es necesaria para proveedores que no pueden engancharse directamente en las tablas de páginas del sistema operativo o la unidad de gestión de memoria. Ver fi_mr_refresh() para detalles de la notificación.
FI_MR_RMA_EVENT
Este bit de modo indica que el proveedor debe configurar las regiones de memoria que están asociadas con eventos RMA antes de su uso. Esto incluye todas las regiones de memoria que están asociadas con contadores de finalización. Cuando está establecido, las aplicaciones deben indicar si una región de memoria será asociada con un contador de finalización como parte de la creación de la región. Esto se hace pasando el flag FI_RMA_EVENT a la llamada de registro de memoria.

Dichas regiones de memoria serán creadas en un estado deshabilitado y deben ser asociadas con todos los contadores de finalización antes de ser habilitadas. Para habilitar una región de memoria, la aplicación debe llamar a fi_mr_enable(). Después de llamar a fi_mr_enable(), no se pueden hacer más asignaciones de recursos a la región de memoria.

FI_MR_ENDPOINT
Este bit de modo indica que el proveedor asocia las regiones de memoria con puntos finales (endpoints) en lugar de dominios. Las regiones de memoria que están registradas con el proveedor son creadas en un estado deshabilitado y deben ser vinculadas a un punto final antes de ser habilitadas. Para vincular la MR con un punto final, la aplicación debe usar fi_mr_bind(). Para habilitar la región de memoria, la aplicación debe llamar a fi_mr_enable().
FI_MR_HMEM
Este bit de modo está asociado con la capacidad FI_HMEM.

Si FI_MR_HMEM está establecido, la aplicación debe registrar los búferes que fueron asignados usando una llamada de dispositivo y proporcionar un parámetro desc válido en las operaciones de transferencia de datos aplicables, incluso si solo se usan para operaciones locales (por ejemplo, búferes de datos de envío y recepción). La memoria del dispositivo debe ser registrada usando la llamada fi_mr_regattr, con los campos iface y device completados.

Si FI_MR_HMEM no está establecido, la aplicación no necesita registrar los búferes del dispositivo para operaciones locales. Además, no se requiere el uso de fi_mr_regattr para el registro de memoria del dispositivo. Es responsabilidad del proveedor descubrir los atributos de registro de memoria del dispositivo apropiados, si aplica.

De manera similar a si FI_MR_LOCAL no está establecido, si FI_MR_HMEM no está establecido, las aplicaciones pueden opcionalmente pasar un parámetro desc válido. Si el parámetro desc es NULL, cualquier registro de memoria local requerido será manejado por el proveedor.

Si FI_MR_HMEM está establecido, pero FI_MR_LOCAL no lo está, solo los búferes del dispositivo deben ser registrados cuando se usan localmente. En este caso, el parámetro desc pasado a las operaciones de transferencia de datos debe ser válido o NULL. De manera similar, si FI_MR_LOCAL está establecido, pero FI_MR_HMEM no lo está, el parámetro desc debe ser válido o NULL.

FI_MR_COLLECTIVE
Este bit está asociado con la capacidad FI_COLLECTIVE.

Si FI_MR_COLLECTIVE está establecido, el proveedor requiere que las regiones de memoria usadas en operaciones colectivas deben ser explícitamente registradas para su uso con llamadas colectivas. Esto requiere registrar las regiones pasadas a las llamadas colectivas usando el flag FI_COLLECTIVE.

Si FI_MR_COLLECTIVE no está establecido, el registro de memoria para operaciones colectivas es opcional. Las aplicaciones pueden opcionalmente pasar un parámetro desc válido. Si el parámetro desc es NULL, cualquier registro de memoria local requerido será manejado por el proveedor.

Registro de Memoria Básico (obsoleto)
El registro de memoria básico fue obsoleto en la versión 1.5 de libfabric, pero se soporta para compatibilidad hacia atrás. El registro de memoria básico se indica estableciendo mr_mode igual a FI_MR_BASIC. FI_MR_BASIC debe establecerse solo y no emparejarse con bits mr_mode. A diferencia de otros bits mr_mode, si FI_MR_BASIC está establecido en la entrada a fi_getinfo(), no será borrado por el proveedor. Es decir, establecer mr_mode igual a FI_MR_BASIC fuerza el registro básico si el proveedor lo soporta.

El comportamiento del registro básico es equivalente a requerir los siguientes bits mr_mode: FI_MR_VIRT_ADDR, FI_MR_ALLOCATED, y FI_MR_PROV_KEY. Adicionalmente, los proveedores que soportan el registro básico usualmente requieren el bit de modo fi_info (obsoleto) FI_LOCAL_MR, que fue incorporado en el bit mr_mode FI_MR_LOCAL.

Las funciones de registro – fi_mr_reg, fi_mr_regv, y fi_mr_regattr – se usan para registrar una o más regiones de memoria con recursos de fabric. La principal diferencia entre las funciones de registro es el número y tipo de parámetros que aceptan como entrada. De lo contrario, realizan la misma función general.

Obsoleto : Por defecto, el registro de memoria se completa de forma sincrónica. Es decir, la llamada de registro no retornará hasta que el registro se haya completado. El registro de memoria puede completarse de forma asíncrona vinculando el dominio de recursos a una cola de eventos usando el flag FI_REG_MR. Ver fi_domain_bind. Cuando el registro de memoria es asíncrono, para evitar una condición de carrera entre el retorno de la llamada de registro y la lectura correspondiente del evento de la cola de eventos (EQ), el parámetro de salida mr será escrito antes de que cualquier evento asociado con la operación pueda ser leído por la aplicación. No se generará un evento asíncrono a menos que la llamada de registro retorne éxito (0).

fi_mr_reg

La llamada fi_mr_reg registra el búfer de memoria especificado por el usuario con el dominio de recursos. El búfer se habilita para su acceso por parte del hardware de la red de interconexión (fabric) basándose en los permisos de acceso proporcionados. Consulte la descripción del campo de acceso para los atributos de la región de memoria a

continuación.

La memoria registrada se asocia con un descriptor de memoria local y, opcionalmente, con una clave de memoria remota. Un descriptor de memoria es un identificador específico del proveedor asociado con la memoria registrada. Los descriptores de memoria a menudo se mapean a índices o claves específicos del hardware asociados con la región de memoria. Las claves de memoria remota proporcionan una protección limitada contra el acceso no deseado por parte de un nodo remoto. Los accesos remotos a una región de memoria deben proporcionar la clave asociada con el

registro.

Dado que las claves MR deben ser proporcionadas por un proceso remoto, una aplicación puede usar el parámetro requested_key para indicar que se devuelva un valor de clave específico. El soporte para claves solicitadas por el usuario es específico del proveedor y está determinado por el valor del indicador FI_MR_PROV_KEY en el atributo de dominio

mr_mode.

Las operaciones RMA y atómicas remotas indican la ubicación dentro de una región de memoria registrada especificando una dirección. La ubicación se referencia añadiendo el desplazamiento (offset) tanto a la dirección virtual base del búfer como a 0, dependiendo del

mr_mode.

El parámetro offset está reservado para uso futuro y debe ser

0.

Para solicitudes de registro de memoria asíncronas, el resultado se reportará al usuario a través de una cola de eventos asociada con el dominio de recursos. Si es exitosa, la estructura de la región de memoria asignada se devolverá al usuario a través del parámetro mr. La dirección mr debe permanecer válida hasta que la operación de registro se complete. El contexto especificado con la solicitud de registro se devuelve con el evento de

finalización.

fi_clos

e

Fi_close se utiliza para liberar todos los recursos asociados con el registro de una región de memoria. Una vez desregistrada, no se garantiza el acceso posterior a la memoria registrada. Las operaciones activas o en cola que referencian una región de memoria que se está cerrando pueden intentar acceder a una región de memoria inválida y fallar. Después de que un MR se cierre, cualquier nueva operación dirigida al MR cerrado también fallará. Las aplicaciones son responsables de asegurarse de que un MR ya no sea necesario antes de cerrarlo. Tenga en cuenta que los accesos a un MR cerrado desde un par remoto resultarán en un error en el par. El estado del punto de extremo local no se verá

afectado.

Para los MR que están asociados con un punto de extremo (el indicador FI_MR_ENDPOINT está establecido), el MR debe cerrarse antes que el punto de extremo. Si aún hay recursos asociados con el MR al intentar cerrarlo, la llamada devolverá

-FI_EBUSY.

e fi_close puede verse afectado. Hay más información sobre la caché
de registro de memoria en la sección CACHÉ DE REGISTRO DE MEMORIA.

dmabuf

Los registros de DMA-buf se utilizan para compartir memoria de dispositivo entre un dispositivo dado y la NIC de la red, y no requieren que la memoria de dispositivo se mapee (mmap) en el espacio de direcciones virtuales del proceso que llama.

Esta estructura hace referencia a una región de memoria de dispositivo respaldada por DMA-buf. Este campo solo es utilizable si la aplicación ha solicitado con éxito el soporte para FI_HMEM y se ha pasado el flag FI_MR_DMABUF a la llamada de registro de memoria. Las regiones de DMA-buf son referencias basadas en archivos a la memoria de dispositivo. Dichas regiones se identifican a través de la estructura fi_mr_dmabuf.

struct fi_mr_dmabuf {
    int      fd;
    uint64_t offset;
    size_t   len;
    void     *base_addr;
};

El fd es el descriptor de archivo asociado con la región de DMA-buf. El offset es el desplazamiento dentro de la región donde debe comenzar el registro de memoria. Y len es el tamaño de la región a registrar, comenzando en el offset. El base_addr es la dirección virtual de inicio alineada a página de la región de memoria asignada por el DMA-buf. Si una dirección virtual base no está disponible (por ejemplo, porque el proceso que llama no ha mapeado la región de memoria en su espacio de direcciones), base_addr se puede establecer en NULL.

La selección de dmabuf sobre el campo mr_iov se controla especificando el flag FI_MR_DMABUF.

iov_count

El número de entradas en el array mr_iov. El número máximo de búferes de memoria que pueden estar asociados con una sola región de memoria se especifica como el atributo de dominio mr_iov_limit. Véase fi_domain(3).

access

Indica el tipo de operaciones que el extremo local o un extremo par puede realizar en la región de memoria registrada. Los permisos de acceso admitidos son el OR bit a bit de los siguientes flags:

FI_SEND
El búfer de memoria puede usarse en transferencias de datos de mensajes salientes. Esto incluye operaciones de envío fi_msg y fi_tagged, así como operaciones fi_collective.
FI_RECV
El búfer de memoria puede usarse para recibir transferencias de mensajes entrantes. Esto incluye operaciones de recepción fi_msg y fi_tagged, así como operaciones fi_collective.
FI_READ
El búfer de memoria puede usarse como búfer de resultado para operaciones de lectura RMA y operaciones atómicas en el lado del iniciador. Nótese que desde el punto de vista de la aplicación, se está escribiendo en el búfer de memoria desde la red.
FI_WRITE
El búfer de memoria puede usarse como búfer de origen para operaciones de escritura RMA y operaciones atómicas en el lado del iniciador. Nótese que desde el punto de vista de la aplicación, el extremo está leyendo del búfer de memoria y copiando los datos a la red.
FI_REMOTE_READ
El búfer de memoria puede usarse como búfer de origen de una operación de lectura RMA en el lado objetivo. El contenido del búfer de memoria no se modifica por dichas operaciones.
FI_REMOTE_WRITE
El búfer de memoria puede usarse como búfer objetivo de una operación de escritura RMA o atómica. El contenido del búfer de memoria puede modificarse como resultado de dichas operaciones.
FI_COLLECTIVE
Este flag proporciona una indicación explícita de que el búfer de memoria puede usarse con operaciones colectivas. El uso de este flag es obligatorio si se ha establecido el bit mr_mode FI_MR_COLLECTIVE en el dominio. Este flag debe combinarse con FI_SEND y/o FI_RECV.

Nótese que algunos proveedores pueden no hacer cumplir permisos de acceso de granularidad fina. Por ejemplo, una región de memoria registrada para acceso FI_WRITE puede comportarse también como si se hubiera especificado FI_SEND. Se permite, aunque no se garantiza, un cumplimiento relajado de dicho acceso, siempre que se mantenga la seguridad.

offset

El campo offset está reservado para uso futuro y debe ser 0.

requested_key

Una clave de acceso especificada por la aplicación asociada con la región de memoria. La clave MR debe ser proporcionada por un proceso remoto al realizar operaciones RMA o atómicas en una región de memoria. Las aplicaciones pueden usar el campo requested_key para indicar que se use una clave específica por el proveedor. Esto permite a las aplicaciones usar valores de clave bien conocidos, lo que puede evitar que las aplicaciones necesiten intercambiar y almacenar claves. El soporte para claves solicitadas por el usuario es específico del proveedor y se determina por el flag FI_MR_PROV_KEY en el campo de atributo de dominio mr_mode. Dependiendo del proveedor, la clave solicitada por el usuario puede ignorarse si la región de memoria es solo para acceso local. Un proveedor puede ser incapaz de hacerlo si el hardware soporta claves solicitadas por el usuario y la misma clave se usa tanto para el acceso local como para el remoto.

Contexto de aplicación asociado con operaciones de registro de memoria asíncronas. Este valor se devuelve como parte de cualquier evento asíncrono asociado con el registro. Este campo se ignora en las llamadas de registro síncronas.

El tamaño de página permite a las aplicaciones proporcionar opcionalmente una pista sobre cuál es el tamaño de página óptimo para una asignación de MR. Normalmente, los proveedores pueden seleccionar el tamaño de página óptimo. En casos en los que el rango de VA tiene cero páginas que lo respaldan, lo cual se soporta con FI_MR_ALLOCATED sin establecer, el proveedor puede no conocer el tamaño de página óptimo durante el registro. NOTES

Direct access to an application’s memory by a remote peer requires that the application register the targeted memory buffer(s). This is typically done by calling one of the fi_mr_reg* routines. For FI_MR_PROV_KEY, the provider will return a key that must be used by the peer when accessing the memory region. The application is responsible for transferring this key to the peer. If FI_MR_RAW mode has been set, the key must be retrieved using the fi_mr_raw_attr function.

FI_MR_RAW allows support for providers that require more than 8-bytes for their protection keys or need additional setup before a key can be used for transfers. After a raw key has been retrieved, it must be exchanged with the remote peer. The peer must use fi_mr_map_raw to convert the raw key into a usable 64-bit key. The mapping must be done even if the raw key is 64-bits or smaller.

The raw key support functions are usable with all registered memory regions, even if FI_MR_RAW has not been set. It is recommended that portable applications target using those interfaces; however, their use does carry extra message and memory footprint overhead, making it less desirable for highly scalable apps.

There may be cases where device peer to peer support should not be used or cannot be used, such as when the PCIe ACS configuration does not permit the transfer. The FI_HMEM_DISABLE_P2P environment variable can be set to notify Libfabric that peer to peer transactions should not be used. The provider may choose to perform a copy instead, or will fail support for FI_HMEM if the provider is unable to do that.

FLAGS

The follow flag may be specified to any memory registration call.

FI_RMA_EVENT
This flag indicates that the specified memory region will be associated with a completion counter used to count RMA operations that access the MR.
FI_RMA_PMEM
This flag indicates that the underlying memory region is backed by persistent memory and will be used in RMA operations. It must be specified if persistent completion semantics or persistent data transfers are required when accessing the registered region.
FI_HMEM_DEVICE_ONLY
This flag indicates that the memory is only accessible by a device. Which device is specified by the fi_mr_attr fields iface and device. This refers to memory regions that were allocated using a device API AllocDevice call (as opposed to using the host allocation or unified/shared memory allocation). This flag is only usable for domains opened with FI_HMEM capability support.
FI_HMEM_HOST_ALLOC
This flag indicates that the memory is owned by the host only. Whether it can be accessed by the device is implementation dependent. The fi_mr_attr field iface is still used to identify the device API, but the field device is ignored. This refers to memory regions that were allocated using a device API AllocHost call (as opposed to using malloc-like host allocation, unified/shared memory allocation, or AllocDevice). FI_MR_SINGLE_USE

MEMORY DOMAINS

Memory domains identify the physical separation of memory which may or may not be accessible through the same virtual address space. Traditionally, applications only dealt with a single memory domain, that of host memory tightly coupled with the system CPUs. With the introduction of device and non-uniform memory subsystems, applications often need to be aware of which memory domain a particular virtual address maps to.

As a general rule, separate physical devices can be considered to have their own memory domains. For example, a NIC may have user accessible memory, and would be considered a separate memory domain from memory on a GPU. Both the NIC and GPU memory domains are separate from host system memory. Individual GPUs or computation accelerators may have distinct memory domains, or may be connected in such a way (e.g. a GPU specific fabric) that all GPUs would belong to the same memory domain. Unfortunately, identifying memory domains is specific to each system and its physical and/or virtual configuration.

Understanding memory domains in heterogenous memory environments is important as it can impact data ordering and visibility as viewed by an application. It is also important to understand which memory domain an application is most tightly coupled to. In most cases, applications are tightly coupled to host memory. However, an application running directly on a GPU or NIC may be more tightly coupled to memory associated with those devices.

Memory regions are often associated with a single memory domain. The domain is often indicated by the fi_mr_attr iface and device fields. Though it is possible for physical pages backing a virtual memory region to migrate between memory domains based on access patterns. For example, the physical pages referenced by a virtual address range could migrate between host memory and GPU memory, depending on which computational unit is actively using it.

See the fi_endpoint(3) and fi_cq(3) man pages for addition discussion on message, data, and completion ordering semantics, including the impact of memory domains.

MEMORY REGISTRATION CACHE

Many hardware NICs accessed by libfabric require that data buffers be registered with the hardware while the hardware accesses it. This ensures that the virtual to physical address mappings for those buffers do not change while the transfer is occurring. The performance impact of registering memory regions can be significant. As a result, some providers make use of a registration cache, particularly when working with applications that are unable to manage their own network buffers. A registration cache avoids the overhead of registering and unregistering a data buffer with each transfer.

CACHE DE REGISTRO DE MEMORIA

Se requiere una caché de registro adicional para rastrear esta memoria del dispositivo, o la memoria del dispositivo no puede ser cacheada.

Como regla general, si el hardware requiere el bit de modo FI_MR_LOCAL descrito anteriormente, pero esto no es compatible con la aplicación, es posible que se esté utilizando una caché de registro de memoria. Las siguientes variables de entorno pueden usarse para configurar las cachés de registro.

FI_MR_CACHE_MAX_SIZE
Esto define el número total de bytes para todas las regiones de memoria que pueden ser rastreadas por la caché. Si no está configurado, la caché no tiene límite en cuántos bytes pueden ser registrados y cacheados. Configurar esto reducirá la cantidad de memoria que no se está utilizando activamente como parte de una transferencia de datos que está registrada con un proveedor. Por defecto, el tamaño de la caché es ilimitado.
FI_MR_CACHE_MAX_COUNT
Esto define el número total de regiones de memoria que pueden ser registradas en la caché. Si no está configurado, se elige un límite por defecto. Configurar esto reducirá el número de regiones que se registran, independientemente de su tamaño, que no se están utilizando activamente como parte de una transferencia de datos. Establecer esto a cero deshabilitará el caching de registros.
FI_MR_CACHE_MONITOR
El monitor de caché es responsable de detectar cambios en la memoria del sistema (FI_HMEM_SYSTEM) realizados entre las direcciones virtuales utilizadas por una aplicación y las páginas físicas subyacentes. Las opciones de monitor válidas son: userfaultfd, memhooks, kdreg2 y disabled. Seleccionar disabled desactivará la caché de registro. Userfaultfd es una característica del kernel de Linux utilizada para informar cambios de mapeo de direcciones virtuales a físicas al espacio de usuario. Memhooks opera interceptando llamadas relevantes de asignación y desasignación de memoria que pueden resultar en cambios de mapeo, como malloc, mmap, free, etc. Tenga en cuenta que memhooks opera en la capa del enlazador ELF y no utiliza los ganchos de memoria de glibc. Kdreg2 se suministra como un módulo del kernel de Linux cargable.
FI_MR_CUDA_CACHE_MONITOR_ENABLED
El monitor de caché CUDA es responsable de detectar cambios en la memoria del dispositivo CUDA (FI_HMEM_CUDA) realizados entre las direcciones virtuales del dispositivo utilizadas por una aplicación y las páginas físicas del dispositivo subyacentes. Las opciones de monitor válidas son: 0 o 1. Tenga en cuenta que el monitor de memoria CUDA requiere una versión del kit de herramientas CUDA con direccionamiento virtual unificado habilitado.
FI_MR_ROCR_CACHE_MONITOR_ENABLED
El monitor de caché ROCR es responsable de detectar cambios en la memoria del dispositivo ROCR (FI_HMEM_ROCR) realizados entre las direcciones virtuales del dispositivo utilizadas por una aplicación y las páginas físicas del dispositivo subyacentes. Las opciones de monitor válidas son: 0 o 1. Tenga en cuenta que el monitor de memoria ROCR requiere una versión de ROCR con direccionamiento virtual unificado habilitado.
FI_MR_ZE_CACHE_MONITOR_ENABLED
El monitor de caché ZE es responsable de detectar cambios en la memoria del dispositivo oneAPI Level Zero (FI_HMEM_ZE) realizados entre las direcciones virtuales del dispositivo utilizadas por una aplicación y las páginas físicas del dispositivo subyacentes. Las opciones de monitor válidas son: 0 o 1.

Se puede acceder de forma más directa a la caché de registro interna a través de la llamada fi_open(), utilizando el nombre de servicio "mr_cache". Una vez abierto, se pueden instalar monitores de memoria personalizados. Un monitor de memoria es un componente de la caché responsable de detectar cambios en los mapeos de direcciones virtuales a físicas. Es posible cierto nivel de control sobre la caché a través de las variables de entorno mencionadas anteriormente.
