Paquete: libfabric

NOMBRE

fi_join_collective
Operación en la que un subconjunto de pares se une a un nuevo grupo colectivo.
fi_barrier / fi_barrier2
Operación colectiva que no se completa hasta que todos los pares han entrado en la llamada de barrera.
fi_broadcast
Un único emisor transmite datos a todos los pares, incluido a sí mismo.
fi_alltoall
Cada par distribuye una parte de sus datos locales a todos los pares.
fi_allreduce
Operación colectiva donde todos los pares transmiten una operación atómica a todos los demás pares.
fi_allgather
Cada par envía una copia completa de sus datos locales a todos los pares.
fi_reduce_scatter
Llamada colectiva donde se recopilan datos de todos los pares y se combinan (reducen). El resultado de la reducción se distribuye de vuelta a los pares, recibiendo cada par una parte de los resultados.
fi_reduce
Llamada colectiva donde se recopilan datos de todos los pares a un par raíz y se combinan (reducen).
fi_scatter
Un único emisor distribuye (dispersa) una parte de sus datos locales a todos los pares.
fi_gather
Todos los pares envían sus datos a un par raíz.
fi_query_collective
Devuelve información sobre qué operaciones colectivas son soportadas por un proveedor, y limitaciones sobre el colectivo.

ARGUMENTOS

ep
Punto final de la fabrica en el que iniciar la operación colectiva.
set
Conjunto de vectores de direcciones que define la membresía colectiva.
mc
Grupo de multidifusión asociado con el colectivo.
buf
Búfer de datos local que especifica el primer operando de la operación colectiva
count
El número de elementos referenciados, donde cada elemento es el tipo de datos indicado.
datatype
Tipo de datos asociado con los operandos atómicos
op
Operación atómica a realizar
result
Búfer de datos local para almacenar el resultado de la operación colectiva.
desc / result_desc
Descriptor de datos asociado con el búfer de datos local y el búfer de resultados local, respectivamente.
coll_addr
Dirección que se refiere al grupo colectivo de puntos finales.
root_addr
Punto final único que es la fuente o destino de los datos colectivos.
flags
Banderas adicionales a aplicar para la operación atómica
context
Puntero especificado por el usuario para asociar con la operación. Este parámetro se ignora si la operación no generará una finalización exitosa, a menos que una bandera de operación especifique que el parámetro de contexto debe usarse para la entrada requerida.

DESCRIPCIÓN

En general, las operaciones colectivas pueden considerarse como operaciones atómicas coordinadas entre un conjunto de puntos finales pares. Los lectores deben referirse a la página man fi_atomic(3) para detalles sobre las operaciones atómicas y los tipos de datos definidos por libfabric.

Una operación colectiva es un intercambio de comunicación de grupo. Implica que múltiples pares intercambien datos con otros pares que participan en la llamada colectiva. Las operaciones colectivas requieren una estrecha coordinación de todos los miembros participantes. Todos los participantes deben invocar la misma llamada colectiva antes de que cualquier miembro pueda completar su operación localmente. Como resultado, las llamadas colectivas pueden tensar la fabrica, así como los búferes de datos locales y remotos.

Las interfaces colectivas de Libfabric apuntan a fabricas que soportan la descarga de partes de la comunicación colectiva en conmutadores de red, tarjetas de interfaz de red (NIC) y otros dispositivos. Sin embargo, no se coloca ningún requisito de implementación en el proveedor.

El primer paso para usar una llamada colectiva es identificar los puntos finales pares que participarán. La membresía colectiva sigue uno de dos modelos, ambos soportados por libfabric. En el primer modelo, la aplicación gestiona la membresía. Esto generalmente significa que la aplicación está realizando una operación colectiva en sí misma usando comunicación de punto a punto para identificar a los miembros que participarán. Adicionalmente, la aplicación puede interactuar con un gestor de recursos de la fabrica para reservar recursos de red necesarios para ejecutar operaciones colectivas. En este modelo, la aplicación informará a libfabric que la membresía ya ha sido establecida.

Un modelo separado mueve la gestión de la membresía bajo libfabric y directamente en el proveedor. En este modelo, la aplicación debe identificar qué direcciones de pares serán miembros. Esa información se transmite al proveedor de libfabric, que entonces es responsable de coordinar la creación del grupo colectivo. En el modelo gestionado por el proveedor, el proveedor generalmente realizará la operación colectiva necesaria para establecer el grupo de comunicación e interactuará con cualquier agente de gestión de la fabrica.

En ambos modelos, la membresía colectiva se comunica al proveedor creando y configurando un conjunto de vectores de direcciones (AV set). Un AV set representa un subconjunto ordenado de direcciones en un vector de direcciones (AV). Los detalles sobre cómo crear y configurar un AV set están disponibles en fi_av_set(3).

Una vez que un AV set ha sido programado con la información de la membresía colectiva, un punto final se une al conjunto. Esto usa la operación fi_join_collective y opera de forma asíncrona. Esto difiere de cómo un punto final se asocia sincrónicamenteosamente con un AV utilizando la llamada fi_ep_bind(). Al completar la operación fi_join_collective, se proporciona un fi_addr que se utiliza como dirección de destino al invocar una operación colectiva.

Para la comodidad del desarrollador, se define un conjunto de APIs colectivas. Las APIs colectivas difieren de las interfaces de mensajes y RMA en que el formato de los datos es conocido por el proveedor, y la colectiva puede realizar una operación sobre esos datos. Esto alinea las operaciones colectivas estrechamente con las interfaces atómicas.

Unirse a Colectiva (fi_join_collective)

Esta llamada adjunta un punto final a un grupo de membresía colectiva. Libfabric trata a los miembros colectivos como un grupo de multidifusión, y la llamada fi_join_collective adjunta el punto final a ese grupo de multidifusión. Por defecto, el punto final se unirá al grupo basándose en las capacidades de transferencia de datos del punto final. Por ejemplo, si el punto final ha sido configurado tanto para enviar como para recibir datos, entonces el punto final podrá iniciar y recibir transferencias hacia y desde la colectiva. Los flags de entrada pueden utilizarse para restringir el acceso al grupo colectivo, sujeto a las limitaciones de capacidad del punto final.

Las operaciones de unión colectiva se completan de forma asíncrona y pueden involucrar transferencias de fabricación, dependiendo de la implementación del proveedor. Un punto final debe estar vinculado a una cola de eventos antes de llamar a fi_join_collective. El resultado de la operación de unión se reportará a la EQ como un evento FI_JOIN_COMPLETE. Las aplicaciones no pueden emitir transferencias colectivas hasta recibir la notificación de que la operación de unión ha completado. Tenga en cuenta que un punto final puede comenzar a recibir mensajes del grupo colectivo tan pronto como se complete la unión, lo que puede ocurrir antes de que se genere el evento FI_JOIN_COMPLETE.

La operación de unión colectiva es en sí misma una operación colectiva. Todos los pares participantes deben llamar a fi_join_collective antes de que cualquier par individual reporte que la unión ha completado. Las membresías colectivas gestionadas por la aplicación son una excepción. Con las membresías gestionadas por la aplicación, la llamada fi_join_collective puede completarse localmente sin comunicación de fabricación. Para las membresías gestionadas por el proveedor, la llamada de unión colectiva requiere como entrada una coll_addr que se refiera a una dirección asociada con un conjunto AV (ver fi_av_set_addr) o a un grupo colectivo existente (obtenido a través de una llamada previa a fi_join_collective). La llamada fi_join_collective creará un nuevo subgrupo colectivo. Si se utilizan membresías gestionadas por la aplicación, coll_addr debe establecerse en FI_ADDR_UNAVAIL.

Las aplicaciones deben llamar a fi_close en el grupo colectivo para desconectar el punto final del grupo. Después de que una operación de unión se haya completado, la llamada fi_mc_addr puede utilizarse para recuperar la dirección asociada con el grupo de multidifusión. Consulte fi_cm(3) para obtener detalles adicionales sobre fi_mc_addr().

Barrera (fi_barrier)

La operación fi_barrier proporciona un mecanismo para sincronizar pares. La barrera no resulta en que se transfiera ningún dato a nivel de aplicación. Una barrera no se completa localmente hasta que todos los pares hayan invocado la llamada de barrera. Esto significa a la aplicación local que el trabajo de los pares que completaron antes de que ellos llamaran a la barrera ha finalizado.

Barrera (fi_barrier2)

La operación fi_barrier2 es la misma que fi_barrier, pero con un parámetro extra para pasar flags de operación.

Difusión (fi_broadcast)

fi_broadcast transfiere un arreglo de datos desde un único emisor a todos los demás miembros del grupo colectivo. El parámetro de entrada buf se trata como el búfer de transmisión si el rango local es la raíz, de lo contrario es el búfer de recepción. La operación de difusión actúa como una escritura o lectura atómica a un arreglo de datos. Como resultado, el formato de los datos en buf se especifica a través del parámetro datatype. Cualquier datatype no-void puede ser difundido.

El siguiente diagrama muestra un ejemplo de difusión siendo utilizada para transferir un arreglo de enteros a un grupo de pares.

[1]  [1]  [1]
[5]  [5]  [5]
[9]  [9]  [9]
 |____^    ^
 |_________|
 broadcast

Todos a Todos (fi_alltoall)

La colectiva fi_alltoall implica distribuir (o dispersar) diferentes porciones de un arreglo de datos a los pares. Se explica mejor usando un ejemplo. Aquí tres pares realizan una colectiva todos a todos para intercambiar diferentes entradas en un arreglo de enteros.

[1]   [2]   [3]
[5]   [6]   [7]
[9]  [10]  [11]
   \   |   /
   All to all
   /   |   \
[1]   [5]   [9]
[2]   [6]  [10]
[3]   [7]  [11]

Cada par envía una pieza de sus datos a los otros pares.

Las operaciones todos a todos pueden realizarse en cualquier datatype no-void. Sin embargo, todos a todos no realiza una operación en los datos mismos, por lo que no se especifica ninguna operación.

Reducción Total (fi_allreduce)

fi_allreduce puede describirse como todos los pares proporcionando entrada a una operación atómica, con el resultado copiado de vuelta a cada par. Conceptualmente, esto puede verse como cada par emitiendo una operación atómica de multidifusión a todos los otros pares, obteniendo los resultados y combinándolos. La combinación de los resultados se denomina reducción. La operación fi_allreduce() toma como entrada un arreglo de datos y la operación atómica especificada a realizar. Los resultados de la reducción se escriben en el búfer de resultado.

Se puede especificar cualquier datatype no-void. Las operaciones atómicas válidas se enumeran a continuación en la llamada fi_query_collective. El siguiente diagrama muestra un ejemplo de una operación de reducción total que implica sumar un arreglo de enteros entre tres pares.

 [1]  [1]  [1]
 [5]  [5]  [5]
 [9]  [9]  [9]
   \   |   /
      sum
   /   |   \
 [3]  [3]  [3]
[15] [15] [15]
[27] [27] [27]
  All Reduce

Recolección Total (fi_allgather)

Conceptualmente, la recolección total puede verse como lo opuesto al componente de dispersión de reduce-scatter. La recolección total recopila datos de todos los pares en un solo arreglo, luego copia ese arreglo de vuelta a cada par.

[1]  [5]  [9]
  \   |   /
 All gather
  /   |   \
[1]  [1]  [1]
[5]  [5]  [5]
[9]  [9]  [9]

La recolección total puede realizarse en cualquier datatype no-void. Sin embargo, la recolección total no realiza una operación en los datos mismos, por lo que no se especifica ninguna operación.

Reducción-Dispersión (fi_reduce_scatter)

La colectiva fi_reduce_scatter es similar a una operación fi_allreduce, seguida de todos a todos. Con reduce scatter, todos los pares proporcionan entrada a una operación atómica, similar a reducción total. Sin embargo, en lugar de que el resultado completo se copie a cada par, cada participante recibe solo una porción del resultado.

Esto se muestra en el siguiente ejemplo:

[1]  [1]  [1]
[5]  [5]  [5]
[9]  [9]  [9]
  \   |   /
     sum (reduce)
      |
     [3]
    [15]
    [27]
      |
   scatter
  /   |   \
[3] [15] [27]

La llamada reduce scatter soporta el mismo datatype y operación atómica que fi_allreduce.

Reducción (fi_reduce)

La colectiva fi_reduce es la primera mitad de una operación fi_allreduce. Con reduce, todos los pares proporcionan entrada a una operación atómica, con los resultados recopilados por un único punto final `raíz'.

Esto se muestra en el siguiente ejemplo, con el par más a la izquierda identificado como la raíz:

[1]  [1]  [1]
[5]  [5]  [5]
[9]  [9]  [9]
  \   |   /
     sum (reduce)
    /
 [3]
[15]
[27]

La llamada reduce soporta el mismo datatype y operación atómica que fi_allreduce.

Dispersión (fi_scatter)

La colectiva fi_scatter es la segunda mitad de una operación fi_reduce_scatter. Los datos de un único punto final `raíz' se dividen y distribuyen a todos los pares.

Esto se muestra en el siguiente ejemplo:

 [3]
[15]
[27]
    \
   scatter
  /   |   \
[3] [15] [27]

La operación de dispersión se utiliza para distribuir resultados a los pares. No se realiza ninguna operación atómica en los datos.

Recopilación (fi_gather)

La operación fi_gather se utiliza para recopilar (reunir) los resultados de todos los pares y almacenarlos en un par `raíz'.

Esto se muestra en el siguiente ejemplo, con el par más a la izquierda identificado como la raíz.

[1]  [5]  [9]
  \   |   /
    gather
   /
[1]
[5]
[9]

La operación de recopilación no realiza ninguna operación en los datos mismos.

Consultar Atributos Colectivos (fi_query_collective)

La llamada fi_query_collective reporta qué operaciones colectivas son soportadas por el proveedor subyacente, para puntos finales debidamente configurados. Las operaciones colectivas necesarias por una aplicación que no son soportadas por el proveedor deben ser implementadas por la aplicación. La llamada de consulta verifica si un proveedor soporta una operación colectiva específica para un datatype y operación dados, si aplica.

El nombre de la colectiva, así como el datatype y la operación asociada, si aplica, se proporcionan como entrada a fi_query_collective.

El parámetro coll puede referirse a una de estas colectivas: FI_BARRIER, FI_BROADCAST, FI_ALLTOALL, FI_ALLREDUCE, FI_ALLGATHER, FI_REDUCE_SCATTER, FI_REDUCE, FI_SCATTER, o FI_GATHER. Los detalles adicionales de la operación colectiva se especifican a través del parámetro struct fi_collective_attr. Para las colectivas que actúan sobre datos, la operación y el tipo de datos relacionado deben ser especificados fi_join_collective(3) — Libfabric Programmer’s Manual

NAME

fi_join_collective — initiate a collective operation

SYNOPSIS

#include <rdma/fi_collective.h>
int fi_join_collective(struct fid_ep *ep,
                       struct fi_collective_attr *attr);

ARGUMENTS

ep
Fabric endpoint handle.
attr
Collective operation attributes. See the DESCRIPTION section for details.

DESCRIPTION

The fi_join_collective call is used to initiate a collective operation on a fabric endpoint (EP). This call is used to query the capabilities and limits of the underlying provider for collective operations, rather than to perform the collective operation itself. The input attributes are used to specify the desired collective operation type and its associated parameters.

struct fi_collective_attr
struct fi_collective_attr {
    enum fi_op op;
    enum fi_datatype datatype;
    struct fi_atomic_attr datatype_attr;
    size_t max_members;
      uint64_t mode;
};

For a description of struct fi_atomic_attr, see fi_atomic(3).

op
On input, this specifies the atomic operation involved with the collective call. This should be set to one of the following values: FI_MIN, FI_MAX, FI_SUM, FI_PROD, FI_LOR, FI_LAND, FI_BOR, FI_BAND, FI_LXOR, FI_BXOR, FI_ATOMIC_READ, FI_ATOMIC_WRITE, of FI_NOOP. For collectives that do not exchange application data (fi_barrier), this should be set to FI_NOOP.
datatype
On onput, specifies the datatype of the data being modified by the collective. This should be set to one of the following values: FI_INT8, FI_UINT8, FI_INT16, FI_UINT16, FI_INT32, FI_UINT32, FI_INT64, FI_UINT64, FI_FLOAT, FI_DOUBLE, FI_FLOAT_COMPLEX, FI_DOUBLE_COMPLEX, FI_LONG_DOUBLE, FI_LONG_DOUBLE_COMPLEX, or FI_VOID. For collectives that do not exchange application data (fi_barrier), this should be set to FI_VOID.
datatype_attr.count
The maximum number of elements that may be used with the collective.
datatype_attr.size
The size of the datatype as supported by the provider. Applications should validate the size of datatypes that differ based on the platform, such as FI_LONG_DOUBLE.
max_members
The maximum number of peers that may participate in a collective operation.
mode
This field is reserved and should be 0.

If a collective operation is supported, the query call will return FI_SUCCESS, along with attributes on the limits for using that collective operation through the provider.

Completions

Collective operations map to underlying fi_atomic operations. For a discussion of atomic completion semantics, see fi_atomic(3). The completion, ordering, and atomicity of collective operations match those defined for point to point atomic operations.

FLAGS

The following flags are defined for the specified operations.

FI_SCATTER
Applies to fi_query_collective. When set, requests attribute information on the reduce-scatter collective operation.

RETURN VALUE

Returns 0 on success. On error, a negative value corresponding to fabric errno is returned. Fabric errno values are defined in rdma/fi_errno.h.

ERRORS

-FI_EAGAIN
See fi_msg(3) for a detailed description of handling FI_EAGAIN.
-FI_EOPNOTSUPP
The requested atomic operation is not supported on this endpoint.
-FI_EMSGSIZE
The number of collective operations in a single request exceeds that supported by the underlying provider.

NOTES

Collective operations map to atomic operations. As such, they follow most of the conventions and restrictions as peer to peer atomic operations. This includes data atomicity, data alignment, and message ordering semantics. See fi_atomic(3) for additional information on the datatypes and operations defined for atomic and collective operations.
