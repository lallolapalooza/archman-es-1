DESCRIPCIÓN

Las colas de eventos se utilizan para reportar eventos asociados con operaciones de control. Están asociadas con el registro de memoria, vectores de dirección, gestión de conexiones y eventos a nivel de fabric y dominio. Los eventos reportados están asociados con una operación solicitada o afiliados a una llamada que se registra para tipos específicos de eventos, como la escucha de solicitudes de conexión.

fi_eq_open

fi_eq_open asigna una nueva cola de eventos.

Las propiedades y el comportamiento de una cola de eventos están definidos por struct fi_eq_attr.

struct fi_eq_attr {
    size_t               size;      /* # entradas para la EQ */
    uint64_t             flags;     /* banderas de operación */
    enum fi_wait_obj     wait_obj;  /* objeto de espera solicitado */
    int                  signaling_vector; /* afinidad de interrupción */
    struct fid_wait     *wait_set;  /* conjunto de espera opcional, obsoleto */
};
size
Especifica el tamaño mínimo de una cola de eventos.
flags
Banderas que controlan la configuración de la EQ.
- FI_WRITE
Indica que la aplicación requiere soporte para insertar eventos de usuario en la EQ. Si esta bandera está establecida, entonces la operación fi_eq_write debe ser soportada por el proveedor. Si la bandera FI_WRITE no está establecida, entonces la aplicación no puede invocar fi_eq_write.
- FI_AFFINITY
Indica que el campo signaling_vector (ver abajo) es válido.
wait_obj
Las EQ pueden estar asociadas con un objeto de espera específico. Los objetos de espera permiten a las aplicaciones bloquearse hasta que el objeto de espera sea señalado, indicando que un evento está disponible para ser leído. Los usuarios pueden usar fi_control para recuperar el objeto de espera subyacente asociado con una EQ, para usarlo en otras llamadas del sistema. Los siguientes valores pueden usarse para especificar el tipo de objeto de espera asociado con una EQ:
- FI_WAIT_NONE
Se usa para indicar que el usuario no se bloqueará (esperará) por eventos en la EQ. Cuando se especifica FI_WAIT_NONE, la aplicación no puede llamar a fi_eq_sread. Este es el valor predeterminado si no se especifica ningún objeto de espera.
- FI_WAIT_UNSPEC
Especifica que el usuario solo esperará en la EQ usando llamadas de interfaz de fabric, como fi_eq_sread. En este caso, el proveedor subyacente puede seleccionar el objeto de espera más apropiado o de mayor rendimiento disponible, incluyendo mecanismos de espera personalizados. No se garantiza que las aplicaciones que seleccionan FI_WAIT_UNSPEC puedan recuperar el objeto de espera subyacente.
- FI_WAIT_SET (obsoleto)
Indica que la cola de eventos debe usar un objeto de conjunto de espera para esperar eventos. Si se especifica, el campo wait_set debe referenciar un objeto de conjunto de espera existente.
- FI_WAIT_FD
Indica que la EQ debe usar un descriptor de archivo como su mecanismo de espera. Un objeto de espera de descriptor de archivo debe ser usable en rutinas select, poll y epoll. Sin embargo, un proveedor puede señalar un objeto de espera FD marcándolo como legible o con un error.
- FI_WAIT_MUTEX_COND (obsoleto)
Especifica que la EQ debe usar un mutex pthread y una variable de condición como objeto de espera.
- FI_WAIT_YIELD
Indica que la EQ esperará sin un objeto de espera pero en su lugar cederá en cada espera. Permite el uso de fi_eq_sread a través de un spin.
signaling_vector
Si la bandera FI_AFFINITY está establecida, esto indica el número de CPU lógico (0..máx CPU - 1) al que las interrupciones asociadas con la EQ deben dirigirse. Este campo debe tratarse como una sugerencia para el proveedor y puede ser ignorado si el proveedor no soporta afinidad de interrupción.
wait_set (obsoleto)
Si wait_obj es FI_WAIT_SET, este campo referencia un objeto de espera al que la cola de eventos debe adjuntarse. Cuando se inserta un evento en la cola de eventos, el conjunto de espera correspondiente será señalado si todas las condiciones necesarias se cumplen. El uso de un wait_set habilita un método optimizado para esperar eventos en múltiples colas de eventos. Este campo se ignora si wait_obj no es FI_WAIT_SET.

fi_close

La llamada fi_close libera todos los recursos asociados con una cola de eventos. Cualquier evento que permanezca en la EQ cuando se cierre se perderá.

La EQ no debe estar vinculada a ningún otro objeto antes de ser cerrada, de lo contrario la llamada devolverá -FI_EBUSY.

fi_control

La llamada fi_control se usa para acceder a detalles específicos del proveedor o de la implementación de la cola de eventos. El acceso a la EQ debe serializarse en todas las llamadas cuando fi_controlse invocan, ya que pueden redirigir la implementación de las operaciones EQ. Los siguientes comandos de control son utilizables con un EQ.

FI_GETWAIT (void **)
Este comando permite al usuario recuperar el objeto de espera de bajo nivel asociado con el EQ. El formato del objeto de espera se especifica durante la creación del EQ, a través de los atributos del EQ. El parámetro arg de fi_control debe ser una dirección donde se escribirá un puntero al objeto de espera devuelto. Esto debe ser un 'int *' para FI_WAIT_FD, o `struct fi_mutex_cond' para FI_WAIT_MUTEX_COND (obsoleto).
struct fi_mutex_cond {
    pthread_mutex_t     *mutex;
    pthread_cond_t      *cond;
};

fi_eq_read

La operación fi_eq_read realiza una lectura no bloqueante de datos de eventos desde el EQ. El formato de los datos del evento se basa en el tipo de evento recuperado del EQ, con todos los eventos comenzando con una cabecera struct fi_eq_entry. Se devolverá como máximo un evento por operación de lectura del EQ. El número de bytes leídos con éxito del EQ se devuelve desde la lectura. El flag FI_PEEK puede usarse para indicar que los datos del evento deben leerse del EQ sin ser consumidos. Una lectura posterior sin el flag FI_PEEK eliminaría entonces el evento del EQ.

Los siguientes tipos de eventos pueden ser reportados a un EQ, junto con información respecto al formato asociado con cada evento.

Operaciones de control asíncronas
Las operaciones de control asíncronas son peticiones básicas que simplemente necesitan generar un evento para indicar que se han completado. Estos incluyen los siguientes tipos de eventos: registro de memoria, resolución de vectores de dirección y uniones multicast.

Las peticiones de control reportan su inserción en el EQ mediante la inserción de una struct fi_eq_entry. El formato de esta estructura es:

struct fi_eq_entry {
    fid_t            fid;        /* fid asociado con la petición */
    void            *context;    /* contexto de la operación */
    uint64_t         data;       /* datos específicos de la finalización */
};

Para la finalización de operaciones de control asíncronas básicas, el evento devuelto indicará la operación que se ha completado, y el fid hará referencia al descriptor de fabrica asociado con el evento. Para el registro de memoria, este será un evento FI_MR_COMPLETE y el fid_mr. La resolución de direcciones hará referencia a un evento FI_AV_COMPLETE y fid_av. Las uniones multicast reportarán un FI_JOIN_COMPLETE y fid_mc. El campo context se establecerá al contexto especificado como parte de la operación, si está disponible, de lo contrario el contexto se asociará con el descriptor de fabrica. El campo data se establecerá como se describe en la página del manual para el tipo de objeto correspondiente (por ejemplo, ver fi_av(3) para una descripción de cómo se completan las inserciones asíncronas en el vector de direcciones).

Notificación de conexión
Las notificaciones de conexión son notificaciones de gestión de conexiones utilizadas para establecer o desmantilar conexiones entre puntos finales. Hay tres eventos de notificación de conexión: FI_CONNREQ, FI_CONNECTED y FI_SHUTDOWN. Las notificaciones de conexión se reportan usando struct fi_eq_cm_entry:
struct fi_eq_cm_entry {
    fid_t            fid;        /* fid asociado con la petición */
    struct fi_info  *info;       /* información del punto final */
    uint8_t         data[];     /* datos de conexión de la aplicación */
};

Un evento de petición de conexión (FI_CONNREQ) indica que un punto final remoto desea establecer una nueva conexión a un punto final de escucha, o pasivo. El fid es el punto final pasivo. La información respecto a las capacidades y atributos del punto final activo solicitado está disponible desde el campo info. La aplicación es responsable de liberar esta estructura llamando a fi_freeinfo cuando ya no la necesite. El campo connreq de fi_info hará referencia a la petición de conexión asociada con este evento. Para aceptar una conexión, un punto final debe ser creado primero pasando una estructura fi_info que haga referencia a este campo connreq a fi_endpoint(). Este punto final es entonces pasado a fi_accept() para completar la aceptación del intento de conexión. La creación del punto final se logra más fácilmente pasando el fi_info devuelto como parte del evento CM a fi_endpoint(). Si la conexión va a ser rechazada, el connreq se pasa a fi_reject().

Cualquier dato de aplicación intercambiado como parte de la petición de conexión se coloca más allá de la estructura fi_eq_cm_entry. La cantidad de datos disponibles depende de la aplicación y está limitada al espacio de búfer proporcionado por la aplicación cuando se llama a fi_eq_read. La cantidad de datos devueltos puede calcularse usando el valor de retorno de fi_eq_read. Nótese que la cantidad de datos devueltos está limitada por el protocolo de conexión subyacente, y la longitud de cualquier dato devuelto puede incluir relleno de protocolo. Como resultado, la longitud devuelta puede ser mayor que la especificada por el par conectado.

Si una petición de conexión ha sido aceptada, un evento FI_CONNECTED será generado en ambos lados de la conexión. El lado activo – el que llamó a fi_connect() – puede recibir datos de usuario como parte del evento FI_CONNECTED. Los datos de usuario se pasan al gestor de conexiones en el lado pasivo a través de la llamada fi_accept. No se proporcionan datos de usuario con un evento FI_CONNECTED en el lado de escucha de la conexión.

La notificación de que un par remoto se ha desconectado de un punto final activo se hace a través del evento FI_SHUTDOWN. La notificación de apagado usa struct fi_eq_cm_entry como se declaró arriba. El campo fid para una notificación de apagado se refiere al fid_ep del punto final activo.

Notificación de error asíncrona
Los errores asíncronos se usan para reportar problemas con recursos de fabrica. Los errores reportados pueden ser fatales o transitorios, basados en el error, y resultan en el recurso quedando deshabilitado. Los recursos deshabilitados fallarán en las operaciones enviadas contra ellos hasta que sean explícitamente rehabilitados por la aplicación.

Los errores asíncronos pueden ser reportados para colas de finalización y puntos finales de todos los tipos. Los errores de CQ pueden resultar cuando la gestión de recursos ha sido deshabilitada, y el proveedor ha detectado un desbordamiento de cola. Los errores de punto final pueden ser el resultado de numerosas acciones, pero a menudo están asociados con una operación fallida. Las operaciones pueden fallar debido a desbordamientos de búfer, permisos inválidos, claves de memoria incorrectas, fallos de enrutamiento de red, problemas de alcanzabilidad de red, etc.

Los errores asíncronos se reportan usando struct fi_eq_err_entry, como se define abajo. El descriptor de fabrica (fid) asociado con el error se proporciona como parte de los datos del error. Un código de error también está disponible para determinar la causa del error.

fi_eq_sread

La llamada fi_eq_sread es el equivalente bloqueante (o síncrono) a fi_eq_read. Se comporta de manera similar a la llamada no bloqueante, con la excepción de que las llamadas no retornarán hasta que un evento haya sido leído del EQ o ocurra un error o un tiempo de espera. Especificar un tiempo de espera negativo significa un tiempo de espera infinito.

Los hilos bloqueados en esta función retornarán al llamador si son señalados por alguna fuente externa. Esto es cierto incluso si el tiempo de espera no ha ocurrido o fue especificado como infinito.

Es inválido para las aplicaciones llamar a esta función si el EQ ha sido configurado con un objeto de espera de FI_WAIT_NONE o FI_WAIT_SET.

fi_eq_readerr

La función de lectura de errores, fi_eq_readerr, recupera información respecto a cualquier operación asíncrona que haya completado con un error inesperado. fi_eq_readerr es una llamada no bloqueante, retornando inmediatamente ya sea que se haya encontrado una finalización con error o no.

Los EQs están optimizados para reportar operaciones que han completado con éxito. Las operaciones que fallan se reportan 'fuera de banda'. Tales operaciones se recuperan usando la función fi_eq_readerr. Cuando una operación que completa con un error inesperado es insertada en un EQ, se coloca en una cola de errores temporal. Intentar leer de un EQ mientras un elemento está en la cola de errores resulta en un fallo FI_EAVAIL. Las aplicaciones pueden usar este código de retorno para determinar cuándo llamar a fi_eq_readerr.

La información del error se reporta al usuario a través de struct fi_eq_err_entry. El formato de esta estructura se define abajo.

struct fi_eq_err_entry {
    fid_t            fid;        /* fid asociado con el error */
    void            *context;    /* contexto de la operación */
    uint64_t         data;       /* datos específicos de la finalización */
    int              err;        /* código de error positivo */
    int              prov_errno; /* código de error del proveedor */
    void            *err_data;   /* datos de error adicionales */
    size_t           err_data_size; /* tamaño de err_data */
};

El fid hará referencia al descriptor de fabrica asociado con el evento. Para el registro de memoria, este será el fid_mr, la resolución de direcciones hará referencia a un fid_av, y los eventos CM se referirán a un fid_ep. El campo context se establecerá al contexto especificado como parte de la operación.

El campo data se establecerá como se describe en la página del manual para el tipo de objeto correspondiente (por ejemplo, ver fi_av(3) para una descripción de cómo se completan las inserciones asíncronas en el vector de direcciones).

La razón general del error se proporciona a través del campo err. La información de error específica del proveedor u operativa también puede estar disponible a través de los campos prov_errno y err_data. Los usuarios pueden llamar a fi_eq_strerror para convertir la información de error específica del proveedor en una cadena imprimible para propósitos de depuración.

En la entrada, err_data_size indica el tamaño del búfer err_data en bytes. En la salida, err_data_size se establecerá al número de bytes copiados al búfer err_data. La información err_data se usa típicamente con fi_eq_strerror para proporcionar detalles sobre el tipo de error que ocurrió.

Para propósitos de compatibilidad, si err_data_size es 0 en la entrada, o la fabrica fue abierta con una versión < 1.5, err_data se establecerá a un búfer de datos propiedad del proveedor. El contenido del búfer permanecerá válido hasta una llamada de lectura posterior contra el EQ. Las aplicaciones deben serializar el acceso al EQ al procesar errores para asegurar que el búfer referenciado por err_data no cambie.

DESCRIPTION

An event queue (EQ) is used by the fabric provider to report events to the application. Events are generated by operations on endpoints, domains, memory regions, etc. The application polls or reads events from the EQ. The EQ is created with fi_eq_open and destroyed with fi_eq_close.

fi_eq_open opens a new event queue associated with the specified fabric. The attr parameter is a pointer to a fi_eq_attr structure which specifies the desired characteristics of the EQ. The fi_eq_attr structure is defined as:

struct fi_eq_attr {
    uint64_t    flags;          /* EQ flags */
    enum fi_eq_type type;       /* EQ type */
    size_t      size;           /* EQ size in bytes */
    void        *context;       /* User specified context */
    uint32_t    wait_obj_count; /* Number of wait objects */
    void        **wait_obj;     /* Wait objects */
    enum fi_progress_interval progress_interval; /* progress interval */
};

The following flags are supported for fi_eq_attr:

FI_ASYNC_IOV
If set, the EQ supports asynchronous I/O vectors.
FI_WAIT_UNBARRIERED
If set, the EQ supports unbarriered wait objects.
FI_WAIT_YIELD
If set, the EQ supports yield support for wait objects.

fi_eq_attr.type specifies the type of events the EQ will handle. Supported types include FI_EQ_WAIT_CONFIRM, FI_EQ_WAIT_SELECT, FI_EQ_WAIT_UNBIND, FI_EQ_WAIT_FD. Refer to fi_wait.h for details.

fi_eq_attr.size specifies the requested size of the EQ in bytes. The provider may choose to allocate a different size. The actual size can be retrieved using fi_eq_get_size.

fi_eq_attr.context is an optional user-specified context that can be associated with the EQ.

fi_eq_attr.wait_obj_count and fi_eq_attr.wait_obj are used to specify wait objects that can be used to wait on EQ events. This allows for integration with event loop mechanisms.

fi_eq_open returns a pointer to a newly created fi_eq structure.

fi_eq_close closes an event queue and releases any associated resources.

fi_eq_bind binds a user-provided buffer to the event queue. This is typically used for memory registration of the EQ buffer.

fi_eq_dup duplicates an existing event queue. The duplicated EQ can be used independently by another thread or process.

fi_eq_get_size retrieves the actual size of the event queue in bytes.

fi_eq_read reads events from the event queue. It is a non-blocking operation. If no events are available, it returns -FI_EAGAIN. The read events are placed into the provided buffer buf of size len.

fi_eq_readerr is similar to fi_eq_read but also attempts to read provider-specific error information into errbuf of size errlen.

fi_eq_sread is a synchronous version of fi_eq_read. It blocks until events are available or the specified timeout expires. A timeout of -1 indicates indefinite blocking.

fi_eq_write writes events to the event queue. This is typically used by the fabric provider to inject events into the EQ.

fi_eq_strerror converts a fabric error code and provider-specific error information into a human-readable string.

EVENT FIELDS

The event structure passed to the EQ read/write functions is defined as:

struct fi_eq_entry {
    uint64_t        fid;        /* fabric descriptor */
    void            *context;   /* user context */
    void            *data;      /* event-specific data */
    int             err;        /* fabric errno */
    int             prov_errno; /* provider-specific errno */
    void            *err_data;  /* provider-specific error data */
    size_t          err_data_size; /* size of err_data */
};

The fields of the fi_eq_entry structure are described below. The meanings are the same or similar for all EQ structure formats, with specific details described below.

fid
This corresponds to the fabric descriptor associated with the event. The type of fid depends on the event being reported. For FI_CONNREQ this will be the fid of the passive endpoint. FI_CONNECTED and FI_SHUTDOWN will reference the active endpoint. FI_MR_COMPLETE and FI_AV_COMPLETE will refer to the MR or AV fabric descriptor, respectively. FI_JOIN_COMPLETE will point to the multicast descriptor returned as part of the join operation. Applications can use fid->context value to retrieve the context associated with the fabric descriptor.
context
The context value is set to the context parameter specified with the operation that generated the event. If no context parameter is associated with the operation, this field will be NULL.
data
Data is an operation specific value or set of bytes. For connection events, data is application data exchanged as part of the connection protocol.
err
This err code is a positive fabric errno associated with an event. The err value indicates the general reason for an error, if one occurred. See fi_errno.3 for a list of possible error codes.
prov_errno
On an error, prov_errno may contain a provider specific error code. The use of this field and its meaning is provider specific. It is intended to be used as a debugging aid. See fi_eq_strerror for additional details on converting this error value into a human readable string.
err_data
On an error, err_data may reference a provider specific amount of data associated with an error. The use of this field and its meaning is provider specific. It is intended to be used as a debugging aid. See fi_eq_strerror for additional details on converting this error data into a human readable string.
err_data_size
On input, err_data_size indicates the size of the err_data buffer in bytes. On output, err_data_size will be set to the number of bytes copied to the err_data buffer. The err_data information is typically used with fi_eq_strerror to provide details about the type of error that occurred.

For compatibility purposes, if err_data_size is 0 on input, or the fabric was opened with release < 1.5, err_data will be set to a data buffer owned by the provider. The contents of the buffer will remain valid until a subsequent read call against the EQ. Applications must serialize access to the EQ when processing errors to ensure that the buffer referenced by err_data does no change.

NOTES

If an event queue has been overrun, it will be placed into an `overrun' state. Write operations against an overrun EQ will fail with -FI_EOVERRUN. Read operations will continue to return any valid, non-corrupted events, if available. After all valid events have been retrieved, any attempt to read the EQ will result in it returning an FI_EOVERRUN error event. Overrun event queues are considered fatal and may not be used to report additional events once the overrun occurs.

RETURN VALUES

fi_eq_open
Returns 0 on success. On error, a negative value corresponding to fabric errno is returned.
fi_eq_read / fi_eq_readerr
On success, returns the number of bytes read from the event queue. On error, a negative value corresponding to fabric errno is returned. If no data is available to be read from the event queue, -FI_EAGAIN is returned.
fi_eq_sread
On success, returns the number of bytes read from the event queue. On error, a negative value corresponding to fabric errno is returned. If the timeout expires or the calling thread is signaled and no data is available to be read from the event queue, -FI_EAGAIN is returned.
fi_eq_write
On success, returns the number of bytes written to the event queue. On error, a negative value corresponding to fabric errno is returned.
fi_eq_strerror
Returns a character string interpretation of the provider specific error returned with a completion.

Fabric errno values are defined in rdma/fi_errno.h.
