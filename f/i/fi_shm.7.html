DESCRIPCIÓN

GENERAL

El proveedor SHM es un proveedor completo que puede utilizarse en sistemas Linux que admita

n memoria compartida y las llamadas process_vm_readv/process_vm_writev. El proveedor está de
stinado a proporcionar comunicación de alto rendimiento entre procesos en el mismo sistema.

CARACTERÍSTICAS

ADMITIDAS

El proveedor SHM ofrece el siguiente

soporte:
Tipos de punto
final
El proveedor solo admite el tipo de punto final FI_EP_RD
M.
Capacidades del punto
final
Los puntos finales pueden admitir cualquier combinación de las siguientes capacidades de transferencia de datos: FI_MSG, FI_TAGGED, FI_RMA y FI_ATOMICS. Estas capacidades pueden definirse aún más mediante FI_SEND, FI_RECV, FI_READ, FI_WRITE, FI_REMOTE_READ y FI_REMOTE_WRITE para limitar la dirección de las
operaciones.
Mod
os
El proveedor no requiere el uso de ningún bit de
modo.
Progre
so
El proveedor SHM admite FI_PROGRESS_MANUAL. Los búferes de datos del lado de recepción no se modifican fuera de las rutinas de procesamiento de finalización. El proveedor procesa mensajes utilizando tres métodos diferentes, en función del tamaño del mensaje. Para mensajes de menos de 4096 bytes, las finalizaciones de tx se generan inmediatamente después del envío. Para mensajes más grandes, las finalizaciones de tx no se generan hasta que el lado receptor ha procesado el
mensaje.
Formato de
dirección
El proveedor SHM utiliza el formato de dirección FI_ADDR_STR, que sigue el patrón de formato general "[prefijo]://[dirección]". La aplicación puede proporcionar direc
ciones a través del parámetro node o hints. Siempre que la dirección esté en un formato FI_ADDR_STR válido (contenga "://"), se utilizará tal cual. Si la entrada de la
aplicación tiene un formato incorrecto o no se proporcionó ninguna entrada, el proveedor SHM la resolverá de acuerdo con los siguientes estándares del proveedor SHM:

(flags & FI_SOURCE) ? src_addr : dest_addr = - si (node && service): "fi_ns://node:service" - si (service): "fi_ns://service" - si (node && !service): "fi_shm://node" - si (!node && !service): "fi_shm:

//PID"

!(flags & FI_SOURCE) - src_addr = "fi_shm:

//PID"

En otras palabras, si la aplicación proporciona una dirección de origen y/o destino en un formato FI_ADDR_STR aceptable (contiene "://"), la llamada a util_getinfo completará con éxito src_addr y dest_addr con la entrada proporcionada. Si la entrada no está en un formato ADDR_STR, el proveedor de memoria compartida creará una dirección FI_ADDR_STR adecuada con los prefijos "fi_ns://" (formato node/service) o "fi_shm://" (formato shm), indicando si la dirección es una dirección "única" y si necesita o no un identificador de nombre de punto final adicional para hacerla única. Para el proveedor de memoria compartida, asumimos que el servicio (con o sin un node) es suficiente para hacerla única, pero un node por sí solo no lo es. Si solo se proporciona un node, se utiliza el prefijo "fi_shm://" para indicar que no es una dirección única. Si no se proporciona node ni service (y en el caso de establecer la dirección de origen sin FI_SOURCE y sin hints), se utilizará el ID de proceso como dirección predeterminada. Al crear el punto final, si src_addr tiene el prefijo "fi_shm://", el proveedor añadirá ":[uid]:[ep_idx]" como nombre de punto final único (esencialmente, en lugar de un servicio). En el caso del prefijo "fi_ns://" (o cualquier otro prefijo proporcionado por la aplicación), no se requiere información adicional para hacerlo único y permanecerá solo con la dirección definida por la aplicación. Tenga en cuenta que el nombre real del punto final no incluirá el prefijo FI_ADDR_STR "*://" ya que no puede incluirse en ningún nombre de región de memoria compartida. El proveedor eliminará el prefijo antes de establecer el nombre del punto final. Como resultado, las direcciones "fi_prefix1://my_node:my_service" y "fi_prefix2://my_node:my_service" resultarían en puntos finales y regiones con el mismo nombre. La aplicación también puede anular el nombre del punto final después de crear un punto final usando setname() sin ninguna restricción de formato de

dirección.

Banderas de mensaje El proveedor admite las siguientes banderas de mensaje: - FI_CLAIM - FI_COMPLETION - FI_DELIVERY_COMPLETE - FI_DISCARD - FI_INJECT - FI_MULTI_RECV - FI_PEEK - FI_REMOTE_CQ_DAT

Modo de registro MR El proveedor puede optimizar las llamadas RMA si la aplicación admite FI_MR_VIRT_ADDR. De lo contrario, no se requieren modos MR adicionales. Si se solicita soporte FI_HMEM, el proveedor requerirá

FI_MR_HMEM.

Operaciones atómicas El proveedor admite todas las combinaciones de tipo de datos y operacio

nes siempre que el mensaje sea menor de 4096 b
ytes (o 2048 para operaciones de comparación).

DS

A

Intel Data Streaming Accelerator (DSA) es un acelerador integrado en los procesadores Intel Xeon a partir de la generación Sapphire Rapids. Una de las capacidades de DSA es descargar operaciones de copia de memoria de la CPU. Un sistema puede tener uno o más dispositivos DSA. Cada dispositivo DSA puede tener una o más colas de trabajo. La especificación de DSA se puede encontrar

aquí.

El protocolo SAR del proveedor SHM está habilitado para aprovechar DSA y descargar operaciones de copia de memoria hacia y desde los búferes SAR en regiones de memoria compartida. Para aprovechar al máximo la capacidad de descarga de DSA, las operaciones de copia de memoria se realizan de forma asíncrona. El hilo iniciador de la copia construye los comandos DSA y los envía a las colas de trabajo. Una operación de copia puede consistir en más de un comando DSA. En tal caso, los comandos se distribuyen entre todas las colas de trabajo disponibles de forma circular. El hilo de progreso comprueba las finalizaciones de los comandos DSA. Si el comando de copia se completa correctamente, notifica al par para consumir los datos. Si DSA encuentra una falta de página durante la ejecución del comando, la falta de página se informa a través de los registros de finalización. En tal caso, el hilo de progreso accede a la página para resolver la falta de página y resubmite el comando después de ajustar las finalizaciones parciales. Uno de los beneficios de hacer las operaciones de copia de memoria asíncronas es que ahora las transferencias de datos entre diferentes puntos finales de destino se pueden iniciar en paralelo. El uso de Intel DSA en el protocolo SAR está deshabilitado de forma predeterminada y se puede habilitar usando una variable de entorno. Tenga en cuenta que CMA debe estar deshabilitado, por ejemplo FI_SHM_DISABLE_CMA=0, para que se pueda usar DSA. Consulte la sección PARÁMETROS DE TIEMPO DE

EJECUCIÓN.

Compilar con capacidades DSA depende de la biblioteca accel-config que se puede encontrar aquí. Ejecutar con DSA requiere usar el kernel de Linux 5.19.0-rc3 o

posterior.

Los dispositivos DSA necesitan configurarse solo una vez antes del tiempo de ejecución. Este archivo de configuración(https://github.com/intel/idxd-config/blob/stable/contrib/configs/os_profile.conf) puede

usarse como plantilla con la utilidad accel-
config para configurar los dispositivos DSA.
