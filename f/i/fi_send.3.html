NOMBRE

fi_msg - Operaciones de transferencia de datos de mensajes

fi_recv / fi_recvv / fi_recvmsg
Publicar un búfer para recibir un mensaje entrante

fi_send / fi_sendv / fi_sendmsg fi_inject / fi_senddata: Iniciar una operación para enviar un mensaje

SINOPSIS

#include <rdma/fi_endpoint.h>
ssize_t fi_recv(struct fid_ep *ep, void * buf, size_t len,
    void *desc, fi_addr_t src_addr, void *context);
ssize_t fi_recvv(struct fid_ep *ep, const struct iovec *iov, void **desc,
    size_t count, fi_addr_t src_addr, void *context);
ssize_t fi_recvmsg(struct fid_ep *ep, const struct fi_msg *msg,
    uint64_t flags);
ssize_t fi_send(struct fid_ep *ep, const void *buf, size_t len,
    void *desc, fi_addr_t dest_addr, void *context);
ssize_t fi_sendv(struct fid_ep *ep, const struct iovec *iov,
    void **desc, size_t count, fi_addr_t dest_addr, void *context);
ssize_t fi_sendmsg(struct fid_ep *ep, const struct fi_msg *msg,
    uint64_t flags);
ssize_t fi_inject(struct fid_ep *ep, const void *buf, size_t len,
    fi_addr_t dest_addr);
ssize_t fi_senddata(struct fid_ep *ep, const void *buf, size_t len,
    void *desc, uint64_t data, fi_addr_t dest_addr, void *context);
ssize_t fi_injectdata(struct fid_ep *ep, const void *buf, size_t len,
    uint64_t data, fi_addr_t dest_addr);

ARGUMENTOS

ep
Punto final de la red en el que iniciar la transferencia o publicar el búfer de recepción.
buf
Búfer de datos para enviar o recibir.
len
Longitud del búfer de datos a enviar o recibir, especificada en bytes. Las transferencias válidas van desde 0 bytes hasta el tamaño máximo de mensaje del punto final.
iov
Búfer de datos vectoriales.
count
Número de entradas de datos vectoriales.
desc
Descriptor asociado con el búfer de datos. Ver fi_mr(3).
data
Datos de CQ remotos a transferir con el mensaje enviado.
dest_addr
Dirección de destino para transferencias sin conexión. Ignorado para puntos finales conectados.
src_addr
Se aplica solo a puntos finales sin conexión configurados con FI_DIRECTED_RECV. Para todas las demás configuraciones de puntos finales, src_addr se ignora. src_addr define la dirección de origen desde la que recibir. Por defecto, src_addr se trata como una dirección de punto final de origen (es decir, fi_addr_t devuelto por fi_av_insert / fi_av_insertsvc / fi_av_remove). Si se especifica el indicador FI_AUTH_KEY con fi_recvmsg, src_addr se trata como una clave de autorización de origen (es decir, fi_addr_t devuelto por fi_av_insert_auth_key). Si se establece en FI_ADDR_UNSPEC, cualquier dirección de origen puede coincidir.
msg
Descriptor de mensaje para operaciones de envío y recepción.
flags
Indicadores adicionales a aplicar para la operación de envío o recepción.
context
Puntero especificado por el usuario para asociar con la operación. Este parámetro se ignora si la operación no generará una finalización exitosa, a menos que un indicador de operación especifique que el parámetro de contexto se utilizará para entrada requerida.

DESCRIPCION

Las funciones de envío – fi_send, fi_sendv, fi_sendmsg, fi_inject y fi_senddata – se utilizan para transmitir un mensaje de un punto final a otro. La principal diferencia entre las funciones de envío es el número y el tipo de parámetros que aceptan como entrada. De lo contrario, realizan la misma función general. Los mensajes enviados utilizando operaciones fi_msg son recibidos por un punto final remoto en un búfer publicado para recibir dichos mensajes.

Las funciones de recepción – fi_recv, fi_recvv, fi_recvmsg – publican un búfer de datos en un punto final para recibir mensajes entrantes. De forma similar a las operaciones de envío, las operaciones de recepción son asíncronas. Los usuarios no deben manipular los búferes de datos publicados hasta que la operación de recepción se haya completado.

Un punto final debe estar habilitado antes de que una aplicación pueda publicar operaciones de envío o recepción en él. Para puntos finales conectados, los búferes de recepción pueden publicarse antes de llamar a connect o accept en el punto final. Esto asegura que los búferes estén disponibles para recibir datos entrantes inmediatamente después de que se haya establecido la conexión.

Las operaciones de mensajes completadas se informan al usuario a través de uno o más recolectores de eventos asociados con el punto final. Los usuarios proporcionan contexto que se asocia con cada operación y se devuelve al usuario como parte de la finalización del evento. Ver fi_cq para obtener detalles sobre los eventos de finalización.

fi_send

La llamada fi_send transfiere los datos contenidos en el búfer de datos especificado por el usuario a un punto final remoto, manteniendo los límites del mensaje.

fi_sendv

La llamada fi_sendv agrega soporte para una lista de dispersión y recolección a fi_send. fi_sendv transfiere el conjunto de búferes de datos referenciados por el parámetro iov a un punto final remoto como un único mensaje.

fi_sendmsg

La llamada fi_sendmsg admite transferencias de datos a través de puntos finales conectados y sin conexión, con la capacidad de controlar la operación de envío por llamada mediante el uso de indicadores. La función fi_sendmsg toma una estructura fi_msg como entrada.

struct fi_msg {
    const struct iovec *msg_iov; /* array de dispersión/recolección */
    void               **desc;   /* descriptores de solicitud locales */
    size_t             iov_count;/* nº de elementos en iov */
    fi_addr_t          addr;     /* dirección opcional del punto final */
    void               *context; /* contexto definido por el usuario */
    uint64_t           data;     /* datos de mensaje opcionales */
};

fi_inject

La llamada de inyección de envío es una versión optimizada de fi_send con las siguientes características. El búfer de datos está disponible para su reutilización inmediatamente al regresar de la llamada, y no se escribirá ninguna entrada de CQ si la transferencia se completa con éxito.

Conceptualmente, esto significa que la función fi_inject se comporta como si se hubiera establecido el indicador de transferencia FI_INJECT, se habilitaran las finalizaciones selectivas y no se especificara el indicador FI_COMPLETION. Tenga en cuenta que la entrada de CQ se suprimirá incluso si el comportamiento predeterminado del punto final es escribir entradas de CQ para todas las finalizaciones exitosas. Ver la discusión sobre indicadores a continuación para más detalles. El tamaño del mensaje solicitado que se puede utilizar con fi_inject está limitado por inject_size.

Si FI_HMEM está habilitado, la llamada fi_inject solo puede aceptar búferes con iface igual a FI_HMEM_SYSTEM si el proveedor requiere el modo mr_mode FI_MR_HMEM. Esta limitación se aplica a todas las llamadas fi_*inject* y no afecta a cómo se informa inject_size.

fi_senddata

La llamada de envío de datos es similar a fi_send, pero permite el envío de datos de CQ remotos (ver indicador FI_REMOTE_CQ_DATA) como parte de la transferencia.

fi_injectdata

La llamada de inyección de datos es similar a fi_inject, pero permite el envío de datos de CQ remotos (ver indicador FI_REMOTE_CQ_DATA) como parte de la transferencia.

fi_recv

La llamada fi_recv publica un búfer de datos en la cola de recepción del punto final correspondiente. Las recepciones publicadas se buscan en el orden en que se publicaron para hacer coincidir los envíos. Se mantienen los límites del mensaje. El orden en que se completan las recepciones depende del tipo de punto final y del protocolo. Para puntos finales sin conexión, el parámetro src_addr se puede utilizar para indicar que se debe publicar un búfer para recibir datos entrantes de un punto final remoto específico.

fi_recvmsg

La llamada fi_recvmsg admite la publicación de búferes tanto en extremos conectados como sin conexión, con la capacidad de controlar la operación de recepción en cada llamada mediante el uso de indicadores (flags). La función fi_recvmsg toma un struct fi_msg como entrada.

INDICADORES (FLAGS)

Las llamadas fi_recvmsg y fi_sendmsg permiten al usuario especificar indicadores que pueden cambiar el manejo predeterminado de mensajes del extremo. Los indicadores especificados con fi_recvmsg / fi_sendmsg anulan la mayoría de los indicadores previamente configurados con el extremo, excepto donde se indique (véase fi_endpoint.3). La siguiente lista de indicadores es utilizable con fi_recvmsg y/o fi_sendmsg.

FI_REMOTE_CQ_DATA
Aplica a fi_sendmsg. Indica que hay datos de CQ remoto disponibles y que deben enviarse como parte de la solicitud. Véase fi_getinfo para detalles adicionales sobre FI_REMOTE_CQ_DATA. Este indicador se establece implícitamente para fi_senddata y fi_injectdata.
FI_COMPLETION
Indica que se debe generar una entrada de finalización (completion) para la operación especificada. El extremo debe estar vinculado a una cola de finalizaciones (CQ) con FI_SELECTIVE_COMPLETION que corresponda a la operación especificada, o este indicador se ignora.
FI_MORE
Indica que el usuario tiene solicitudes adicionales que se publicarán inmediatamente después de que la llamada actual regrese. El uso de este indicador puede mejorar el rendimiento al permitir que el proveedor optimice su acceso al hardware de la red (fabric).
FI_INJECT
Aplica a fi_sendmsg. Indica que el búfer de datos de salida debe devolverse al usuario inmediatamente después de que la llamada de envío regrese, incluso si la operación se maneja de forma asíncrona. Esto puede requerir que la implementación subyacente del proveedor copie los datos en un búfer local y transfiera desde ese búfer. Este indicador solo puede usarse con mensajes más pequeños que inject_size.
FI_MULTI_RECV
Aplica a operaciones de recepción publicadas. Este indicador permite al usuario publicar un solo búfer que recibirá múltiples mensajes entrantes. Los mensajes recibidos se empaquetarán en el búfer de recepción hasta que el búfer se haya consumido. El uso de este indicador puede hacer que una sola operación de recepción publicada genere múltiples eventos a medida que los mensajes se colocan en el búfer. La colocación de los datos recibidos en el búfer puede estar sujeta a restricciones de alineación específicas del proveedor.

El búfer será liberado por el proveedor cuando el espacio de búfer disponible caiga por debajo del mínimo especificado (véase FI_OPT_MIN_MULTI_RECV). Nótese que siempre se generará una entrada en la cola de finalizaciones de recepción asociada cuando el búfer se haya consumido, incluso si otras finalizaciones de recepción han sido suprimidas (es decir, el contexto Rx ha sido configurado para FI_SELECTIVE_COMPLETION). Véase el indicador de finalización FI_MULTI_RECV en fi_cq(3).

FI_INJECT_COMPLETE
Aplica a fi_sendmsg. Indica que se debe generar una finalización cuando el(los) búfer(es) de origen puedan ser reutilizados.
FI_TRANSMIT_COMPLETE
Aplica a fi_sendmsg y fi_recvmsg. Para envíos, indica que no debe generarse una finalización hasta que la operación haya sido transmitida exitosamente y ya no esté siendo rastreada por el proveedor. Para operaciones de recepción, indica que una finalización puede generarse tan pronto como el mensaje haya sido procesado por el proveedor local, incluso si los datos del mensaje pueden no ser visibles para todos los elementos de procesamiento. Véase fi_cq(3) para la semántica de finalización del lado destino.
FI_DELIVERY_COMPLETE
Aplica a fi_sendmsg. Indica que se debe generar una finalización cuando la operación haya sido procesada por el destino.
FI_FENCE
Aplica a transmisiones. Indica que la operación solicitada, también conocida como la operación cercada (fenced), y cualquier operación publicada después de la operación cercada, serán diferidas hasta que todas las operaciones anteriores dirigidas al mismo extremo par hayan finalizado. Las operaciones publicadas después del cercado verán y/o reemplazarán los resultados de cualquier operación iniciada antes de la operación cercada.

El orden de las operaciones desde la publicación de la operación cercada (inclusive) hasta la publicación de una operación cercada posterior (exclusivo) está controlado por la semántica de orden del extremo.

FI_MULTICAST
Aplica a transmisiones. Este indicador indica que la dirección especificada como destino de la transferencia de datos es una dirección de multidifusión (multicast). Este indicador debe usarse en todas las transferencias de multidifusión, en conjunto con un fi_addr_t de multidifusión.
FI_AUTH_KEY
Solo válido con dominios configurados con FI_AV_AUTH_KEY y extremos sin conexión configurados con FI_DIRECTED_RECV. Cuando se usa con fi_recvmsg, este indicador denota que src_addr es un fi_addr_t de clave de autorización en lugar de un fi_addr_t de extremo.

NOTAS

Si un extremo ha sido configurado con FI_MSG_PREFIX, la aplicación debe incluir espacio de búfer de tamaño msg_prefix_size, como lo especifican los atributos del extremo. El búfer de prefijo debe ocurrir al inicio de los datos referenciados por el parámetro buf, o ser referenciado por el primer vector de E/S (IO vector). El espacio de prefijo del mensaje no puede dividirse entre múltiples vectores de E/S. El tamaño del búfer de prefijo debe incluirse como parte de la longitud total del búfer.

VALOR DE RETORNO

Devuelve 0 en caso de éxito. En caso de error, se devuelve un valor negativo correspondiente al errno de la red (fabric). Los valores de errno de la red se definen en rdma/fi_errno.h.

Véase la discusión más abajo para detalles sobre el manejo de FI_EAGAIN.

ERRORES

-FI_EAGAIN
Indica que el proveedor subyacente carece actualmente de los recursos necesarios para iniciar la operación solicitada. Las razones por las que un proveedor devuelve FI_EAGAIN son variadas. Sin embargo, las razones comunes incluyen un búfer interno insuficiente o colas de procesamiento llenas.

Un búfer interno insuficiente a menudo está asociado con operaciones que usan FI_INJECT. En tales casos, puede haber búfer adicional disponible a medida que las operaciones publicadas finalicen.

Las colas de procesamiento llenas pueden ser un estado temporal relacionado con el procesamiento local (por ejemplo, se está transfiriendo un mensaje grande), o pueden ser el resultado del control de flujo. En este último caso, las colas pueden permanecer bloqueadas hasta que se hagan disponibles recursos adicionales en el lado remoto de la transferencia.

En todos los casos, la operación puede reintentarse después de que se hagan disponibles recursos adicionales. Al usar FI_PROGRESS_MANUAL, la aplicación debe verificar las finalizaciones de transmisión y recepción después de recibir FI_EAGAIN como valor de retorno, independientemente de la operación que falló. Esto también se recomienda firmemente al usar FI_PROGRESS_AUTO, ya que pueden necesitarse reconocimientos (acknowledgements) o mensajes de control de flujo para reanudar la ejecución.
