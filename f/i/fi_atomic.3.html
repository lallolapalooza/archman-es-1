Operaciones Atómicas

Se definen las siguientes operaciones atómicas. Una operación atómica a menudo actúa sobre un valor objetivo en el búfer de memoria remota y un valor de origen proporcionado con la función atómica. También puede transportar datos de origen para reemplazar el valor objetivo en operaciones de comparación e intercambio. Se proporciona una descripción conceptual de cada operación.

FI_MIN
Mínimo
if (buf[i] < addr[i])
    addr[i] = buf[i]

Máximo

    addr[i] = buf[i]
FI_SUM
Suma
addr[i] = addr[i] + buf[i]
FI_PROD
Producto
addr[i] = addr[i] * buf[i]
FI_LOR
OR Lógico
addr[i] = (addr[i] || buf[i])
FI_LAND
AND Lógico
addr[i] = (addr[i] && buf[i])
FI_BOR
OR a nivel de bits
addr[i] = addr[i] | buf[i]
FI_BAND
AND a nivel de bits
addr[i] = addr[i] & buf[i]
FI_LXOR
OR Exclusivo (XOR) Lógico
addr[i] = ((addr[i] && !buf[i]) || (!addr[i] && buf[i]))
FI_BXOR
OR Exclusivo (XOR) a nivel de bits

    addr[i] = buf[i]

Compara valores y si son menores, intercambia con los datos

    addr[i] = buf[i]

Funciones Atómicas Base

Las funciones atómicas base — fi_atomic, fi_atomicv, fi_atomicmsg — se utilizan para transmitir datos a un nodo remoto, donde se realiza la operación atómica especificada sobre los datos objetivo. El resultado de una función atómica base se almacena en la región de memoria remota. La principal diferencia entre las funciones atómicas es el número y el tipo de parámetros que aceptan como entrada. De lo contrario, realizan la misma función general.

La llamada fi_atomic transfiere los datos contenidos en el búfer de datos especificado por el usuario a un nodo remoto. Para puntos de conexión sin conexión, el punto de conexión de destino se especifica a través del parámetro dest_addr. A menos que el punto de conexión se haya configurado de manera diferente, el búfer de datos pasado a fi_atomic no debe ser manipulado por la aplicación hasta que la llamada fi_atomic se complete de forma asíncrona. El búfer objetivo de una operación atómica base debe permitir acceso de lectura y/o escritura remota, según corresponda.

La llamada fi_atomicv añade soporte para una lista de dispersión-agregación a fi_atomic. fi_atomicv transfiere el conjunto de búferes de datos referenciados por el parámetro ioc al nodo remoto para su procesamiento.

La llamada fi_inject_atomic es una versión optimizada de fi_atomic. La función fi_inject_atomic se comporta como si se estableciera la bandera de transferencia FI_INJECT, y FI_COMPLETION no. Es decir, el búfer de datos está disponible para su reutilización inmediatamente al regresar de fi_inject_atomic, y no se generará ningún evento de finalización para esta operación atómica. El evento de finalización se suprimirá incluso si el punto de conexión no se ha configurado con FI_SELECTIVE_COMPLETION. Consulte la discusión de banderas a continuación para obtener más detalles. El tamaño del mensaje solicitado que se puede utilizar con fi_inject_atomic está limitado por inject_size.

La llamada fi_atomicmsg admite operaciones atómicas tanto en puntos de conexión conectados como sin conexión, con la capacidad de controlar la operación atómica por llamada a través del uso de banderas. La función fi_atomicmsg toma una estructura fi_msg_atomic como entrada.

struct fi_msg_atomic {
    const struct fi_ioc *msg_iov; /* array scatter-gather local */
    void                **desc;   /* descriptores de acceso local */
    size_t              iov_count;/* # elementos en ioc */
    const void          *addr;    /* dirección de punto de conexión opcional */
    const struct fi_rma_ioc *rma_iov; /* SGL remoto */
    size_t              rma_iov_count;/* # elementos en SGL remoto */
    enum fi_datatype    datatype; /* tipo de dato del operando */
    enum fi_op          op;       /* operación atómica */
    void                *context; /* contexto definido por el usuario */
    uint64_t            data;     /* datos opcionales */
};
struct fi_ioc {
    void        *addr;    /* dirección local */
    size_t      count;    /* # operandos objetivo */
};
struct fi_rma_ioc {
    uint64_t    addr;     /* dirección objetivo */
    size_t      count;    /* # operandos objetivo */
    uint64_t    key;      /* clave de acceso */
};

La siguiente lista de operaciones atómicas se puede utilizar con operaciones atómicas base: FI_MIN, FI_MAX, FI_SUM, FI_PROD, FI_LOR, FI_LAND, FI_BOR, FI_BAND, FI_LXOR, FI_BXOR y FI_ATOMIC_WRITE.

Funciones Fetch-Atomic

Las funciones fetch-atomic — fi_fetch_atomic, fi_fetch_atomicv y fi_fetch atomicmsg — se comportan de manera similar a la función atómica base equivalente. La diferencia entre las llamadas fetch y base atómicas es que las rutinas fetch-atomic devuelven al usuario el valor inicial que estaba almacenado en el objetivo. El valor inicial se lee en el búfer de resultado proporcionado por el usuario. El búfer objetivo de las operaciones fetch-atomic debe estar habilitado para acceso de lectura remota.

La siguiente lista de operaciones atómicas se puede utilizar con operaciones fetch-atomic: FI_MIN, FI_MAX, FI_SUM, FI_PROD, FI_LOR, FI_LAND, FI_BOR, FI_BAND, FI_LXOR, FI_BXOR, FI_ATOMIC_READ y FI_ATOMIC_WRITE.

Para operaciones FI_ATOMIC_READ, el operando del búfer de origen (por ejemplo, el parámetro buf de fi_fetch_atomic) se ignora y puede ser NULL. Los resultados se escriben en el búfer de resultados.

Funciones Compare-Atomic

Las funciones compare-atomic — fi_compare_atomic, fi_compare_atomicv y fi_compare_atomicmsg — son similares a las funciones fetch-atomic correspondientes. La diferencia es que las funciones compare-atomic realizan una comparación entre el valor proporcionado por el usuario (a través del parámetro compare) y el valor actual en la ubicación de memoria remota. Si la comparación es verdadera según el tipo de operación atómica, el valor se actualiza con el valor de entrada del usuario (a través del parámetro buf). Al igual que las funciones fetch-atomic, las funciones compare-atomic devuelven el valor original en la ubicación de memoria remota al usuario. El búfer objetivo de las operaciones compare-atomic debe estar habilitado para acceso de lectura y escritura remota.

Las siguientes operaciones atómicas se pueden utilizar con las operaciones compare-atomic: FI_CSWAP, FI_CSWAP_NE, FI_CSWAP_LE, FI_CSWAP_LT, FI_CSWAP_GE y FI_CSWAP_GT.

Las funciones compare atomic – fi_compare_atomic, fi_compare_atomicv, y fi_compare atomicmsg – se utilizan para oper

aciones que requieren comparar los datos de destino con un valor antes de realizar una operación de intercambio. Las func
iones compare atomic admiten: FI_CSWAP, FI_CSWAP_NE, FI_CSWAP_LE, FI_CSWAP_LT, FI_CSWAP_GE, FI_CSWAP_GT, y FI_MSWAP.

Funciones Válidas de

Átomos

Las funciones atomic valid – fi_atomicvalid, fi_fetch_atomicvalid, y fi_compare_atomicvalid – indican qué operaciones admite el proveedor local. Las operaciones necesarias que no sean admitidas por el proveedor deben ser emuladas por la aplicación. Cada llamada valid corresponde a un conjunto de funciones atomic. fi_atomicvalid comprueba si un proveedor admite una operación atomic base específica para un tipo de datos y operación dados. fi_fetch_atomicvalid indica si un proveedor admite una operación fetch-atomic específica para un tipo de datos y operación dados. Y fi_compare_atomicvalid comprueba si un proveedor admite una operación compare-atomic especificada para un tipo de datos y operación

dados.

Si una operación está admitida, una llamada atomic valid

devolverá 0, junto con un recuento de unidades de d
atos atomic que una sola llamada de función operará.

Consultar Atributos de

Átomos

La llamada fi_query_atomic actúa como una operación atomic valid mejorada (véanse las definiciones de la función atomic valid anteriores). Se proporciona, en parte, para una futura extensibilidad. La operación de consulta informa de qué operaciones atomic admite el dominio, para puntos de extremo configurados

adecuadamente.

El comportamiento de fi_query_atomic se ajusta según el parámetro flags. Si flags es 0, entonces la operación informa de los atributos atomic admitidos para operaciones atomic base, similar a fi_atomicvalid para puntos de extremo. Si flags tiene establecido el bit FI_FETCH_ATOMIC, la operación se comporta similar a fi_fetch_atomicvalid. De manera similar, el bit de flag FI_COMPARE_ATOMIC hace que la consulta actúe como fi_compare_atomicvalid. Los bits FI_FETCH_ATOMIC y FI_COMPARE_ATOMIC no pueden estar ambos

establecidos.

Si el bit FI_TAGGED está establecido, el proveedor indicará si admite operaciones atomic en búferes de recepción etiquetados (tagged). El bit FI_TAGGED puede usarse por sí solo, o en conjunto con los flags FI_FETCH_ATOMIC y FI_COMPARE_ATOMIC

.

Completado

s

Las operaciones atomic completadas se informan al iniciador de la solicitud a través de una cola de completados (completion queue) o contador asociado. Cualquier contexto proporcionado por el usuario especificado con la solicitud se devolverá como parte de cualquier evento de completado escrito a una CQ. Véase fi_cq para detalles de los eventos de

completado.

Cualquier resultado devuelto al iniciador como parte de una operación atomic estará disponible antes de que se genere un evento de completado. Esto será cierto incluso si la semántica de completado solicitada proporciona una garantía más débil. Es decir, las operaciones fetch atomic tienen semánticas FI_DELIVERY_COMPLETE. Los completados generados para otros tipos de operaciones atomic indican que es seguro reutilizar los búferes de datos de

origen.

Cualquier actualización de datos en el destino de una operación atomic será visible para los agentes (procesos CPU, tarjetas de red (NICs) y otros dispositivos) en el nodo destino antes de que ocurra uno de los siguientes. Si la operación atomic genera un evento de completado o actualiza un contador de completado en el punto de extremo destino, los resultados estarán disponibles antes de la notificación de completado. Después de procesar un completado para la operación atomic, si el iniciador envía una transferencia entre los mismos puntos de extremo que genera un completado en el destino, los resultados estarán disponibles antes del evento de la transferencia posterior. O, si una transferencia de datos con valla (fenced) del iniciador sigue a la solicitud atomic, los resultados estarán disponibles antes de un completado en el destino para la transferencia con

valla.

La corrección de las operaciones atomic en una región de memoria de destino está garantizada solo cuando son realizadas por un solo actor durante una ventana de tiempo dada. Un actor se define como un solo dominio libfabric en el destino

(identificado por el nombre del dominio, y no una instancia abierta de ese dominio), un complejo CPU coherente, u otro dispositivo (p. ej. GPU) capaz de realizar operaciones atomic sobre la memoria de destino. Los resultados de las op
eraciones atomic realizadas por múltiples agentes simultáneamente son indefinidos. Por ejemplo, emitir operaciones atomic basadas en CPU a una región de destino que está siendo actualizada concurrentemente por operaciones atomic basada
s en NIC puede dejar los datos de la región en un estado desconocido. Los resultados de las operaciones atomic de un primer actor deben ser visibles para un segundo actor antes de que el segundo actor emita sus propias operaciones atomic.

NOTA

S

Las operaciones atomic operan sobre un array de valores de un tipo de datos específico. La atomicidad solo está garantizada para cada operación de tipo de datos, no a través de todo el array. El siguiente pseudocódigo demuestra esta operación para una escritura atomic de 64 bits sin signo. ATOMIC_WRITE_U64 es una macro dependiente de la plataforma que escribe atómicamente 8 bytes en una ubicación de memoria

alineada. 
fi_atomic(ep, buf, count, NULL, dest_addr, addr, key,
      FI_UINT64, FI_ATOMIC_WRITE, context)
{
    for (i = 1; i < count; i ++)
        ATOMIC_WRITE_U64(((uint64_t *) addr)[i],
                 ((uint64_t *) buf)[i]
);
}

El número de elementos del array sobre los que operar se especifica a través del parámetro count. Este debe estar entre 1 y el máximo devuelto a través de la operación valid relevante, inclusive. La operación solicitada y el tipo de datos también deben ser válidos para el proveedor

dado.

El orden de las operaciones atomic transportadas como parte de diferentes mensajes de solicitud está sujeto a las definiciones de orden de mensajes y datos asignadas a los p

untos de extremo de transmisión y recepción. Tanto el orden de mensajes como el de datos son necesarios si los resultados de dos operaciones atomic dirigidas a los mismos búf
eres de memoria deben reflejar la segunda operación actuando sobre los resultados de la primera. Véase fi_endpoint(3) para más detalles y restricciones de tamaño de mensaje.
