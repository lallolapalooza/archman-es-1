DESCRIPCIÓ

N

Un dominio de acceso generalmente se refiere a una NIC física o virtual o un puerto de hardware; sin embargo, un dominio puede abarcar múltiples componentes de hardware para propósitos de conmutación por error o distribución de datos. Un dominio define el límite para asociar diferentes recursos juntos. Los recursos de la fabrica que pertenecen al mismo dominio pueden compartir

recursos.

fi_set_op

s

fi_set_ops asigna callbacks que un proveedor debe invocar en lugar de realizar tareas seleccionadas. Esto permite a los usuarios modificar o controlar el comportamiento predeterminado de un proveedor. Conceptualmente, permite al usuario enganchar funciones específicas usadas por un proveedor y reemplazarlas con las suyas

propias.

Las operaciones que se modifican se identifican usando una cadena de caracteres bien conocida, pasada como el parámetro name. El formato del parámetro ops depende del valor de name. El parámetro ops hará referencia a una estructura que contiene los callbacks y otros campos necesarios por el proveedor para invocar las funciones del

usuario.

Si un proveedor acepta la anulación, devolverá FI_SUCCESS. Si la anulación es desconocida o no está soportada, el proveedor devolverá -FI_ENOSYS. Las anulaciones deben establecerse antes de asignar recursos en el

dominio.

Las siguientes operaciones fi_set_ops y estructuras de callback correspondientes están

definidas.

Soporte de multihilo

(threading)

El modelo de hilos especifica el nivel de serialización requerido de una aplicación al usar las interfaces de transferencia de datos de libfabric. Las interfaces de control siempre se consideran seguras para hilos, a menos que el modelo de progreso de control sea FI_PROGRESS_CONTROL_UNIFIED. Una interfaz de control segura para hilos permite que múltiples hilos hagan progreso en la interfaz de control y (dependiendo del modelo de hilos seleccionado) uno o más hilos hagan progreso en las interfaces de datos al mismo tiempo. Las aplicaciones que pueden garantizar la serialización en su acceso a los recursos e interfaces asignados por el proveedor permiten que este elimine bloqueos de nivel

inferior.
FI_THREAD_COMPLET
ION
El modelo de hilos de finalización es el más adecuado para aplicaciones multihilo que usan endpoints escalables y desean una operación sin bloqueos. Las
aplicaciones deben serializar el acceso a todos los objetos que están asociados por un mecanismo de finalización común (por ejemplo, contextos de transm
isión y recepción vinculados al mismo CQ o contador). Se recomienda que los proveedores que soportan endpoints escalables soporten este modelo de hilos.

Las aplicaciones que deseen aprovechar FI_THREAD_COMPLETION deben dedicar contextos de transmisión, contextos de recepción, colas de finalización y contadores a hilos

individuales.
FI_THREAD_DOM
AIN
El modelo de hilos de dominio es el más adecuado para aplicaciones de un solo hilo y aplicaciones multihilo que usan endpoints estándar y desean una operación sin bloqueos. Las aplicaciones deben serializar el acceso a todos los objetos bajo el mismo dominio. Esto incluye endpoints, contextos de transmisión y recepción, colas de finalización y contadores, y regiones de memoria
registradas.
FI_THREAD_ENDPOINT
(obsoleto)
El modelo de hilos de endpoint es similar a FI_THREAD_FID, pero con la restricción añadida de que se requiere serialización al acceder al mismo endpoint, incluso si se usan múltiples contextos de transmisión y
recepción.
FI_THREAD_FID
(obsoleto)
Un modelo de serialización de descriptor de fabric (FID) requiere que las aplicaciones serialicen el acceso a los recursos individuales de fabric asociados con las operaciones de transferencia de datos y las finalizaciones. Para el acceso al endpoint, la serialización solo se requiere al acceder al mismo flujo de datos del endpoint. Múltiples hilos pueden iniciar transferencias en diferentes contextos de transmisión o en el mismo endpoint sin serializar, y no se requiere serialización entre el envío de solicitudes de transmisión de datos y las operaciones de recepción de
datos.
FI_THREAD_SA

Modelos de progreso

(progress)

El progreso es la capacidad de la implementación subyacente para completar el procesamiento de una solicitud asíncrona. En muchos casos, el procesamiento de una solicitud asíncrona requiere el uso del procesador del host. Por ejemplo, un mensaje recibido puede necesitar ser emparejado con el búfer correcto, o una solicitud con tiempo de espera agotado puede necesitar ser retransmitida. Por razones de rendimiento, puede ser indeseable que el proveedor asigne un hilo para este propósito, lo que competiría con los hilos de la

aplicación.

El progreso de control indica el método que usa el proveedor para avanzar en operaciones de control asíncronas. Las operaciones de control son funciones que no involucran directamente la transferencia de datos de la aplicación entre endpoints. Incluyen rutinas de vector de direcciones, registro de memoria y gestión de

conexiones.

El progreso de datos indica el método que usa el proveedor para avanzar en operaciones de transferencia de datos. Esto incluye cola de mensajes, RMA, mensajaje etiquetada y operaciones atómicas, junto con su procesamiento de

finalización.

El campo de progreso define el comportamiento tanto de las operaciones de control como de las de datos. Para las aplicaciones que requieren portabilidad de compilación entre las series de libfabric versión 1 y versión 2, el campo de progreso puede referenciarse como

data_progress.

El progreso frecuentemente requiere que se tome acción tanto en el lado de transmisión como en el de recepción de una operación. Esto es a menudo un requisito para transferencias confiables, como resultado del procesamiento de reintentos y acuses de

recibo.

Para equilibrar entre rendimiento y facilidad de uso, se definen los siguientes modelos de

progreso.
FI_PROGRESS_A
UTO
Este modelo de progreso indica que el proveedor hará progreso en una operación asíncrona sin mayor intervención de la aplicación
. Cuando FI_PROGRESS_AUTO se proporciona como salida de fi_getinfo en ausencia de cualquier sugerencia de progreso, a menudo indi
ca que la funcionalidad deseada está implementada por el hardware del proveedor o es un servicio estándar del sistema operativo.

Se recomienda que los proveedores soporten FI_PROGRESS_AUTO. Sin embargo, si un proveedor no soporta nativamente el progreso automático, forzar el uso de FI_PROGRESS_AUTO puede resultar en la asignación de hilos por debajo de las interfaces de

fabric.

Tenga en cuenta que las versiones anteriores de la biblioteca requerían que los proveedores soportaran FI_PROGRESS_AUTO. Sin embargo, en algunos casos los hilos de progreso no pueden bloquearse cuando la comunicación está inactiva, lo que resulta en hilos girando en funciones de progreso. Como resultado, esos proveedores solo soportaban FI_PROGRESS_MANUAL

.
FI_PROGRESS_MAN
UAL
Este modelo de progreso indica que el proveedor requiere el uso de un hilo de la aplicación para completar una solicitud asíncrona. Cuando se establece el progreso manual, e
l proveedor intentará avanzar una operación asíncrona cuando la aplicación intente esperar o leer una cola de eventos, cola de finalización o contador donde se informará la
operación completada. El progreso también ocurre cuando la aplicación procesa un conjunto de sondeo o espera que haya sido asociado con la cola de eventos o de finalización.

Solo las operaciones de espera definidas por la interfaz de fabric resultarán en que una operación avance. Las funciones de espera del sistema operativo o externas, como select, poll o rutinas de pthread, no lo

harán.

Los requisitos de progreso manual no solo se aplican a los endpoints que inician operaciones de transmisión, sino también a los endpoints que pueden ser el destino de dichas operaciones. Esto es cierto incluso si el endpoint de destino no generará eventos de finalización para las operaciones. Por ejemplo, un endpoint que actúa puramente como destino de operaciones RMA o atómicas que usa progreso manual puede seguir necesitando la asistencia de la aplicación para procesar las operaciones

recibidas.
FI_PROGRESS_CONTROL_UNIF
IED
Este modelo de progreso indica que el usuario sincronizará el progreso de las operaciones de datos y control por sí mismo (es decir, esto permite que la interfaz de control NO sea segura para hilos). Implica progreso manual, y cuando se combina con threading=FI_THREAD_DOMAIN/FI_THREAD_COMPLETION permite a Libfabric eliminar todos los bloqueos en la ruta crítica de progreso de
datos.
FI_PROGRESS_UNS

Gestión de recursos

(resource_mgmt)

La gestión de recursos (RM) es el soporte del proveedor y del protocolo para proteger contra el agotamiento de recursos locales y remotos. Esto incluye contextos de transmisión y recepción locales y remotos, colas de finalización y búferes de datos de origen y

destino.

Cuando está habilitada, las aplicaciones reciben cierto nivel de protección contra el agotamiento de las colas del proveedor y de los búferes de datos locales y remotos. Dicho soporte puede estar integrado directamente en el hardware y/o el protocolo de red, pero también puede requerir que se habiliten verificaciones en el software del proveedor. Al deshabilitar la gestión de recursos, una aplicación asume toda la responsabilidad de prevenir el agotamiento de colas y búferes, pero hacerlo puede permitir que un proveedor elimine llamadas de sincronización internas, como variables atómicas o

bloqueos.

Debe señalarse que incluso si la gestión de recursos está deshabilitada, la implementación del proveedor y el protocolo aún pueden proporcionar algún nivel de protección contra el agotamiento. Sin embargo, dicha protección no está garantizada. Se definen los siguientes valores para la gestión de

recursos.
FI_RM_DISABL
ED
El proveedor es libre de seleccionar una implementación y un protocolo que no protejan contra el agotamiento de recursos. La aplicación es responsable de la protección de
recursos.
FI_RM_ENABL

proveedor.
FI_RM_UNSP

gerencias de entrada para la llamada fi_getinfo.

El comportamiento definido es el que ve el iniciador de una solicitud. Para los puntos de conexión FI_EP_DGRAM, si las colas del EP destino no pueden aceptar mensajes entrantes, los mensajes recibidos serán descartados. Para los puntos de conexión confiables, si RM está deshabilitado, la operación de transmisión se completará con error. Un proveedor puede optar por retornar un completado de error con el código de error FI_ENORX para esa operación de transmisión para que pueda ser reintentada. El comportamiento para manejar los mensajes recibidos que son más grandes que los búferes proporcionados por la aplicación es específico del proveedor. Los proveedores pueden truncar el mensaje y reportar un completado exitoso, o fallar la operación. Para los puntos de conexión de datagrama, los envíos fallidos resultarán en que el mensaje sea descartado. Para los puntos de conexión confiables, las operaciones de envío pueden completarse exitosamente, pero ser truncadas en el lado de recepción. Esto puede ocurrir cuando el lado destino almacena los datos recibidos hasta que un búfer de aplicación esté disponible. Cuando ocurre un error de gestión de recursos en un punto de conexión conectado, el punto de conexión transicionará a un estado deshabilitado y la conexión será desmantelada. Un punto de conexión deshabilitado descartará cualquier operación en cola o en

vuelo.

El comportamiento de los errores de gestión de recursos en puntos de conexión sin conexión depende del tipo de error. Si RM está deshabilitado y ocurre uno de los siguientes errores, el punto de conexión será deshabilitado: Ctx Tx, Ctx Rx, CQ Tx o CQ Rx. Para otros errores (EP destino, sin búfer Rx, etc.), la operación puede fallar, pero el punto de conexión permanecerá habilitado. Un punto de conexión deshabilitado descartará o fallará cualquier operación en cola o en vuelo. Además, un punto de conexión deshabilitado debe ser rehabilitado antes de que acepte nuevas operaciones de transferencia de

datos.

Hay una restricción notable en las protecciones ofrecidas por la gestión de recursos. Esto ocurre cuando la gestión de recursos está habilitada en un punto de conexión que ha sido vinculado a cola(s) de completado usando el flag FI_SELECTIVE_COMPLETION. Las operaciones publicadas en dicho punto de conexión pueden especificar que un completado exitoso no

debe generar una entrada en la cola de completado correspondiente. (Es decir, la operación deja el flag FI_COMPLETION sin establecer). En tales situaciones, el proveedor no está obligado a reservar una entrada en la cola de completado para manejar el caso donde la operación falla y sí genera una entrada de CQ, lo cual requeriría efectivamente rastrear la
operación hasta su completado. Las aplicaciones preocupadas por evitar desbordamientos de CQ en la ocurrencia de errores deben asegurar que haya espacio suficiente en la CQ para reportar operaciones fallidas. Esto generalmente se puede lograr dimensionando la CQ al menos al mismo tamaño que la(s) cola(s) del punto de conexión que están vinculadas a ella.
