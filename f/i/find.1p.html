FIND(1P) Manual del Programador POSIX FIND(1P)

PROLOG

Esta página del manual forma parte del Manual del Programador POSIX. La implementación de esta interfaz en Linux puede diferir (consulte la página del manual de Linux correspondiente para obtener detalles sobre el comportamiento en Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

find — encontrar archivos

SINOPSIS

find [-H|-L] ruta... [expresión_operando...]

DESCRIPCIÓN

La utilidad find descenderá recursivamente la jerarquía de directorios a partir de cada archivo especificado por ruta, evaluando una expresión booleana compuesta por los primarios descritos en la sección OPERANDOS para cada archivo encontrado. Cada operando de ruta se evaluará sin alterar, tal como se proporcionó, incluyendo todos los caracteres de barra inclinada finales (<slash>); todas las rutas para otros archivos encontrados en la jerarquía consistirán en la concatenación del operando de ruta actual, una barra inclinada (<slash>) si el operando de ruta actual no terminaba en una, y el nombre del archivo relativo al operando de ruta. La porción relativa no contendrá componentes de punto o doble punto, no contendrá caracteres de barra inclinada finales (<slash>), y solo contendrá caracteres de barra inclinada (<slash>) simples entre componentes de la ruta.

La utilidad find será capaz de descender a profundidades arbitrarias en una jerarquía de archivos y no fallará debido a limitaciones de longitud de ruta (a menos que un operando de ruta especificado por la aplicación exceda los requisitos de {PATH_MAX}).

La utilidad find detectará bucles infinitos; es decir, al entrar en un directorio previamente visitado que es un ancestro del último archivo encontrado. Cuando detecte un bucle infinito, find escribirá un mensaje de diagnóstico en el error estándar y recuperará su posición en la jerarquía o terminará.

Si un archivo se elimina o se añade a la jerarquía de directorios que se está buscando, no se especifica si find incluye o no ese archivo en su búsqueda.

OPCIONES

La utilidad find cumplirá con el volumen de Definiciones Base de POSIX.1‐2017, Sección 12.2, Pautas de Sintaxis de Utilidad.

Las siguientes opciones serán compatibles con la implementación:

-H
Provocar que la información del archivo y el tipo de archivo evaluados para cada enlace simbólico encontrado como operando de ruta en la línea de comandos sean los del archivo al que hace referencia el enlace, y no el enlace en sí. Si el archivo referenciado no existe, la información del archivo y el tipo serán los del propio enlace. La información del archivo y el tipo para los enlaces simbólicos encontrados durante el recorrido de una jerarquía de archivos serán los del propio enlace.
-L
Provocar que la información del archivo y el tipo de archivo evaluados para cada enlace simbólico encontrado como operando de ruta en la línea de comandos o encontrado durante el recorrido de una jerarquía de archivos sean los del archivo al que hace referencia el enlace, y no el enlace en sí. Si el archivo referenciado no existe, la información del archivo y el tipo serán los del propio enlace.

Especificar más de una de las opciones mutuamente excluyentes -H y -L no se considerará un error. La última opción especificada determinará el comportamiento de la utilidad. Si no se especifica ni la opción -H ni la -L, entonces la información del archivo y el tipo para los enlaces simbólicos encontrados como operando de ruta en la línea de comandos o encontrados durante el recorrido de una jerarquía de archivos serán los del propio enlace.

OPERANDOS

Se soportarán los siguientes operandos:

El primer operando y los operandos subsiguientes hasta, pero sin incluir, el primer operando que comience con un '-', o sea un '!' o un '(', se interpretarán como operandos de ruta. Si el primer operando comienza con un '-', o es un '!' o un '(', el comportamiento no está especificado. Cada operando de ruta es un nombre de ruta de un punto de partida en la jerarquía de archivos.

El primer operando que comience con un '-', o sea un '!' o un '(', y todos los argumentos subsiguientes se interpretarán como una expresión compuesta por los siguientes primarios y operadores. En las descripciones, dondequiera que se use n como argumento primario, se interpretará como un entero decimal opcionalmente precedido por un signo más (<plus-sign>) ('+') o un guion (<hyphen-minus>) ('-'), como sigue:

+n
Más de n.
n
Exactamente n.
-n
Menos de n.

Se soportarán los siguientes primarios:

-nombre patrón

El primario se evaluará como verdadero si el nombre base de la ruta actual coincide con patrón usando la notación de coincidencia de patrones descrita en la Sección 2.13, Notación de Coincidencia de Patrones. Las reglas adicionales en la Sección 2.13.3, Patrones Usados para la Expansión de Nombres de Archivo no se aplican ya que esta es una operación de coincidencia, no una expansión.
-ruta patrón

El primario se evaluará como verdadero si la ruta actual coincide con patrón usando la notación de coincidencia de patrones descrita en la Sección 2.13, Notación de Coincidencia de Patrones. Las reglas adicionales en la Sección 2.13.3, Patrones Usados para la Expansión de Nombres de Archivo no se aplican ya que esta es una operación de coincidencia, no una expansión.
-sinusuario
El primario se evaluará como verdadero si el archivo pertenece a un ID de usuario para el cual la función getpwuid() definida en el volumen de Interfaces del Sistema de POSIX.1‐2017 (o equivalente) devuelve NULL.
-sindrugrupo
El primario se evaluará como verdadero si el archivo pertenece a un ID de grupo para el cual la función getgrgid() definida en el volumen de Interfaces del Sistema de POSIX.1‐2017 (o equivalente) devuelve NULL.
-xdev
El primario siempre se evaluará como verdadero; provocará que find no continúe descendiendo a través de directorios que tengan un ID de dispositivo diferente (st_dev, véase la función stat() definida en el volumen de Interfaces del Sistema de POSIX.1‐2017). Si se especifica algún primario -xdev, se aplicará a toda la expresión, incluso si el primario -xdev no se evaluaría normalmente.
-podar
El primario siempre se evaluará como verdadero; provocará que find no descienda la ruta actual si es un directorio. Si se especifica el primario -profundidad, el primario -podar no tendrá ningún efecto.
-perm [-]modo

El argumento modo se utiliza para representar los bits de modo del archivo. Será idéntico en formato al operando modo_simbólico descrito en chmod, y se interpretará de la siguiente manera. Para empezar, se asumirá una plantilla con todos los bits de modo de archivo borrados. Un símbolo de op de '+' establecerá los bits de modo apropiados en la plantilla; '-' borrará los bits apropiados; '=' establecerá los bits de modo apropiados, sin tener en cuenta el contenido de la máscara de creación de modo de archivo del proceso. El símbolo de op '-' no puede ser el primer carácter de modo; esto evita la ambigüedad con el guion (<hyphen-minus>) inicial opcional. Dado que el modo inicial tiene todos los bits desactivados, no hay modos simbólicos que necesiten usar '-' como primer carácter.

Si se omite el guion (<hyphen-minus>), el primario se evaluará como verdadero cuando los bits de permiso del archivo coincidan exactamente con el valor de la plantilla resultante.

De lo contrario, si modo va precedido por un guion (<hyphen-minus>), el primario se evaluará como verdadero si al menos todos los bits de la plantilla resultante están establecidos en los bits de permiso del archivo.

JUSTIFICACIÓ

N

El operador -a se mantuvo como un operador opcional para compatibilidad con scripts de shell históricos, aunque es redundante con la concatenación de

expresiones.

Las descripciones del modificador '-' en los argumentos mode y onum del -perm primario coinciden con la práctica histórica en implementaciones BSD y System V. La documentación de System V y BSD ambos lo describen en términos de verificar bits adicionales; de hecho, usa los mismos bits, pero verifica que estén establecidos al menos todos los bits coincidentes en lugar de tener exactamente los bits coincidentes

establecidos.

El formato exacto de las indicaciones interactivas no está especificado. Solo se especifica la naturaleza general del contenido de las indicaciones

porque:
*
Las implementaciones pueden desear indicaciones más descriptivas que las usadas en implementaciones
históricas.
*
Dado que las cadenas de indicaciones históricas no terminan con caracter
es <newline>, no hay una forma portátil para que otro programa inte
ractúe con las indicaciones de esta utilidad a través de tuberías.

Por lo tanto, una aplicación que use esta opción de indicación depende del sistema para proporcionar el diálogo más adecuado directamente con el usuario, basado en las pautas generales

especificadas.

El operando de archivo -name se cambió para usar la notación de coincidencia de patrones del shell para que find sea consistente con otras utilidades que usan coincidencia de

patrones.

El operando -size se refiere al tamaño de un archivo, en lugar del número de bloques que puede ocupar en el sistema de archivos. La intención es que se use el campo st_size definido en el volumen de Interfaces del Sistema de POSIX.1‐2017, no el st_blocks encontrado en implementaciones históricas. Hay al menos dos razones para

esto:
1
.
Tanto en System V como en BSD, find solo usa st_size en los cálculos de tamaño para los operandos especificados por este volumen de POSIX.1‐2017. (BSD usa st_blocks solo al procesar el -ls primario.)
2.
Los usuarios generalmente piensan en el tamaño del archivo en
términos de bytes, que es también la unidad usada por la
utilidad ls para la salida de la opción -l. (Tanto en System V como en BSD, ls usa st_size para el campo de tamaño de la opción -l y usa st_blocks para los cálculos de ls -s. Este volumen de POSIX.1‐2017 no especifica ls -s
.
)

Las descripciones de -atime, -ctime y -mtime se cambiaron de la descripción SVID de n ``días'' a n siendo el resultado de la división entera de la diferencia de tiempo en segundos por 86400. La descripción también es diferente en términos del marco de tiempo exacto para el caso n (versus +n o -n), pero coincide con todas las implementaciones históricas conocidas. Se refiere a un período de 86400 segundos en el pasado, no a cualquier tiempo desde el comienzo de ese período hasta el tiempo actual. Por ejemplo, -atime 2 es verdadero si el archivo fue accedido en cualquier momento en el período desde hace 72 horas hasta hace 48

horas.

Las implementaciones históricas no modifican "{}" cuando aparece como una subcadena de un -exec o -ok utility_name o cadena de argumento. Ha habido numerosas solicitudes de usuarios para esta extensión, por lo que este volumen de POSIX.1‐2017 permite el comportamiento deseado. Al menos una implementación reciente soporta esta característica, pero encontró varios problemas al gestionar la memoria asignación y el manejo de múltiples ocurrencias de "{}" en una cadena mientras se estaba desarrollando, por lo que aún no es un comportamiento

requerido.

Asumiendo la presencia de -print se añadió para corregir una trampa histórica que afecta a usuarios novatos, es totalmente compatible hacia arriba con el histórico System V utilidad find. En su forma más simple (find directorio), podría confundirse con el histórico BSD rápido find. Los desarrolladores de BSD estuvieron de acuerdo en que añadir -print como expresión por defecto fue la decisión correcta y han añadido la funcionalidad de búsqueda rápida find dentro de una nueva utilidad llamada locate

.

Históricamente, la opción -L se implementó usando el primario -follow. Las opciones -H y -L se añadieron por dos razones. Primero, ofrecen un control de mayor granularidad y consistencia con otros programas que recorren jerarquías de archivos. Segundo, el primario -follow siempre evaluaba a verdadero. Como históricamente eran realmente variables globales que entraban en vigor antes de que comenzara el recorrido, algunas expresiones válidas tenían resultados inesperados. Un ejemplo es la expresión -print -o -follow. Debido a que -print siempre evalúa a verdadero, el orden estándar de evaluación implica que -follow nunca sería evaluado. Este nunca fue el caso. La práctica histórica para el primario -follow, sin embargo, no es consistente. Algunas implementaciones siempre siguen enlaces simbólicos en la línea de comandos ya sea que -follow esté especificado o no. Otras siguen enlaces simbólicos en la línea de comandos solo si -follow está especificado. Ambos comportamientos son proporcionados por las opciones -H y -L, pero los scripts que usan el primario -follow actual se romperían si la opción -follow se especifica para funcionar de cualquier

manera.

Dado que la opción -L resuelve todos los enlaces simbólicos y el primario -type l es verdadero para enlaces simbólicos que aún existen después de que los enlaces simbólicos han sido resueltos, el

comando: 
find -
L . -
type l

imprime una lista de enlaces simbólicos alcanzables desde el directorio actual que no resuelven a archivos

accesibles.

Una característica de la utilidad find de SVR4 era el terminador + del primario -exec. Esto permitía que nombres de archivo que contienen caracteres especiales (especialmente caracteres <salto de línea>) se agruparan juntos sin los problemas que ocurren si tales nombres de archivo se envían por tubería a xargs. Otras implementaciones han añadido otras formas de sortear este problema, notablemente un primario -print0 que escribía nombres de archivo con un byte nulo como terminador. Esto se consideró aquí, pero no se adoptó. Usar un terminador nulo significaba que cualquier utilidad que fuera a procesar la salida -print0 de find tenía que añadir una nueva opción para analizar los terminadores nulos que ahora estaría

leyendo.

La sintaxis "-exec...{}+" adoptada fue un resultado de la Interpretación 1003.2 #210 de IEEE PASC. Debe señalarse que esto es un cambio incompatible con IEEE Std 1003.2‐1992. Por ejemplo, el siguiente comando imprimía todos los archivos con un '-' después de su nombre si son archivos regulares, y un '+' en caso

contrario: 
find / -type f -exec echo {} - ';' -o -exec echo {} +
';
'

El cambio invalida el uso como este. Aunque el estándar anterior afirmaba que

este uso funcionaría, en la práctica muchos no lo soportaban y los desarrollado
res del estándar consideraron mejor ahora declarar que esto no era permitible.
