DESCRIPCIÓ

N

Se pueden pasar varias opciones de línea de comandos al programa usando archivos de perfil. Firejail elige el archivo de perfil de la siguiente

manera:

1. Si el usuario proporciona un archivo de perfil con la opción --profile, se carga el archivo de perfil. Si se da un nombre de perfil, se busca primero en el directorio ~/.config/firejail y si no se encuentra, luego en el directorio /etc/firejail. Los nombres de perfil no incluyen el sufijo .profile.

Ejemplo:
$ firejail --profile=/home/netblue/icecat.profile icecat
Leyendo el perfil /home/netblue/icecat.profile
[...
]
$ firejail --profile=icecat icecat-wrapper.sh
Leyendo el perfil /etc/firejail/icecat.profile
[...
]

2. Si está presente un archivo de perfil con el mismo nombre que la aplicación en el directorio ~/.config/firejail o en /etc/firejail, se carga el perfil. ~/.config/firejail tiene prioridad sobre /etc/firejail.

Ejemplo:
$ firejail icecat
Nombre del comando #icecat#
Perfil icecat encontrado en el directorio /home/netblue/.config/firejail
Leyendo el perfil /home/netblue/.config/firejail/icecat.profile
[...
]

3. Use un archivo default.profile si el sandbox es iniciado por un usuario regular, o un archivo server.profile si el sandbox es iniciado por root. Firejail busca estos archivos en el directorio ~/.config/firejail, seguido por el directorio /etc/firejail. Para deshabilitar la carga del perfil predeterminado, use la opción de comando --noprofile.

Ejemplo:
$ firejail
Leyendo el perfil /etc/firejail/default.profile
PID del padre 8553, PID del hijo 8554
Proceso hijo inicializado
[...]

$ firejail --noprofile
PID del padre 8553, PID del hijo 8554
Proceso hijo inicializado
[

.
..
]

Sistema de

archivos

Estas entradas de perfil definen un sistema de archivos chroot construido sobre el sistema de archivos existente del host. Cada línea describe un archivo/directorio que es inaccesible (blacklist), un archivo o directorio de solo lectura (read-only), un tmpfs montado sobre un directorio existente (tmpfs), o un montaje-enlace de un directorio o archivo sobre otro directorio o archivo (bind). Use private para establecer el modo privado. Se admite el comodín de archivos, y se buscan los directorios PATH y HOME, consulte la sección firejail(1) FILE GLOBBING para más detalles.

file_or_directory

whitelist
file_or_directory
Pone en lista blanca un directorio o archivo. Se monta un sistema de archivos temporal en el directorio superior. En el contexto de firejail, directorio superior significa, si la ruta del archivo en la lista blanca es por ejemplo /etc/somedir/somefile, entonces el directorio superior sería /etc. Todos los demás directorios superiores como /opt, /usr y así sucesivamente, no han cambiado, por lo que todos los archivos en ellos siguen siendo accesibles, a menos que un archivo o directorio dentro de ellos también esté en la lista blanca. Por eso a veces es beneficioso usar blacklist en combinación con whitelist, si se usan para diferentes directorios superiores.

Los archivos en la lista blanca se montan-enlazan dentro. Las modificaciones a los archivos en la lista blanca son persistentes, todo lo demás en el mismo directorio superior se descarta cuando se cierra el

sandbox.

El directorio superior puede ser la mayoría de los directorios en /, pero hay algunos casos especiales. Los directorios superiores /proc y /sys no están permitidos, pero /sys/module sí lo está. También /run/user/$UID, $HOME y todos los directorios en /usr se tratan como un directorio

superior.

Manejo de enlaces simbólicos: Al poner en la lista blanca una ruta que es un enlace simbólico, también se pondrá en la lista blanca la ruta a la que apunta. Por ejemplo, si ~/foo está en la lista blanca y apunta a ~/bar, entonces ~/bar también estará en la lista blanca.
Restricciones: Con la excepción del directorio de inicio del usuario, tanto el enlace como el archivo real deben estar en el mismo directorio superior. Para los enlaces simbólicos en el directorio de inicio del usuario, tanto el enlace como el archivo real deben ser propiedad

Filtrado de

DBus

Se puede permitir, filtrar o desactivar el acceso a los sockets UNIX de DBus de sesión y sistema. Para desactivar los sockets abstractos (y forzar a las aplicaciones a usar el socket UNIX filtrado) necesitarías solicitar un nuevo espacio de nombres de red usando el comando --net. Otra opción es eliminar unix del conjunto

--protocol.

El filtrado requiere instalar la utilidad xdg-dbus-proxy. Las reglas de filtrado pueden especificarse para nombres de DBus bien conocidos, pero también se propagan al nombre único propietario. Los permisos son "pegajosos" y se mantienen incluso si el nombre bien conocido correspondiente se libera (sin embargo, las aplicaciones rara vez liberan nombres bien conocidos en la práctica). Los nombres pueden tener un sufijo .* para que coincidan con todos los nombres que estén debajo de ellos, incluyéndose a sí mismos (por ejemplo, "foo.bar.*" coincide con "foo.bar", "foo.bar.baz" y "foo.bar.baz.quux", pero no con "foobar"). Para más información, consulta xdg-dbus-proxy(1)

.
