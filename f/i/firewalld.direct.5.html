NOMBRE

firewalld.direct - Archivo de configuración directa de firewalld

SINOPSIS

/etc/firewalld/direct.xml

OBSOLETO

La interfaz directa ha sido obsoleta. Será eliminada en una versión futura. Está sustituida por las políticas, véase firewalld.policies(5).

DESCRIPCIÓN

La configuración directa proporciona un acceso más directo al firewall. Requiere que el usuario conozca los conceptos básicos de ip(6)tables/ebtables, es decir, tabla (filter/mangle/nat/...), cadena (INPUT/OUTPUT/FORWARD/...), comandos (-A/-D/-I/...), parámetros (-p/-s/-d/-j/...) y objetivos (ACCEPT/DROP/REJECT/...). La configuración directa solo debe usarse como último recurso cuando no sea posible usar firewalld.zone(5). Véase también Opciones directas en firewall-cmd(1).

Un archivo de configuración directa de firewalld contiene información sobre cadenas directas permanentes, reglas y paso...

Esta es la estructura de un archivo de configuración directa:

<?xml version="1.0" encoding="utf-8"?>
<direct>
  [ <chain ipv="ipv4|ipv6|eb" table="tabla" chain="cadena"/> ]
  [ <rule ipv="ipv4|ipv6|eb" table="tabla" chain="cadena" priority="prioridad"> args </rule> ]
  [ <passthrough ipv="ipv4|ipv6|eb"> args </passthrough> ]
</direct>

direct

La etiqueta de inicio y fin obligatoria 'direct' define la configuración directa. Esta etiqueta solo puede usarse una vez en un archivo de configuración directa. No hay atributos para 'direct'.

chain

Es una etiqueta opcional de elemento vacío y puede usarse varias veces. Se puede usar para definir nombres para cadenas adicionales. Una entrada de cadena tiene exactamente tres atributos:

ipv="ipv4|ipv6|eb"

La familia IP en la que se creará la cadena. Puede ser ipv4, ipv6 o eb.

table="tabla"

El nombre de la tabla en la que se creará la cadena. Puede ser una de las tablas que se pueden usar para iptables, ip6tables o ebtables. Para los valores posibles, consulte la sección TABLES en las páginas del manual de iptables, ip6tables o ebtables.

chain="cadena"

El nombre de la cadena que se creará. Asegúrese de que no haya ya otra cadena con este nombre.

Recuerde agregar una regla o una regla de paso con una opción --jump o --goto para conectar la cadena a otra.

rule

Es una etiqueta de elemento opcional y puede usarse varias veces. Se puede usar para agregar reglas a una cadena incorporada o agregada. Una entrada de regla tiene exactamente cuatro atributos:

ipv="ipv4|ipv6|eb"

La familia IP en la que se agregará la regla. Puede ser ipv4, ipv6 o eb.

table="tabla"

El nombre de la tabla en la que se agregará la regla. Puede ser una de las tablas que se pueden usar para iptables, ip6tables o ebtables. Para los valores posibles, consulte la sección TABLES en las páginas del manual de iptables, ip6tables o ebtables.

chain="cadena"

El nombre de la cadena en la que se agregará la regla. Puede ser una cadena incorporada o una cadena que se haya creado con la etiqueta 'chain'. Si el nombre de la cadena es una cadena incorporada, la regla se agregará a cadena_direct, de lo contrario se utiliza el nombre de cadena suministrado. cadena_direct se crea internamente para todas las cadenas incorporadas para asegurar que las reglas agregadas no entren en conflicto con las reglas creadas por firewalld.

priority="prioridad"

La prioridad se utiliza para ordenar las reglas. La prioridad 0 significa agregar la regla en la parte superior de la cadena; con una prioridad mayor, la regla se agregará más abajo. Las reglas con la misma prioridad están en el mismo nivel y el orden de estas reglas no es fijo y puede cambiar. Si desea asegurarse de que una regla se agregue después de otra, use una prioridad baja para la primera y una más alta para las siguientes.

Los args pueden ser cualquier argumento de iptables o ip6tables que no entre en conflicto con los atributos de tabla o cadena.

passthrough

Es una etiqueta de elemento opcional y puede usarse varias veces. Se puede usar para agregar reglas a una cadena incorporada o agregada. Una entrada de regla tiene exactamente un atributo:

ipv="ipv4|ipv6|eb"

La familia IP en la que se agregará la regla de paso. Puede ser ipv4, ipv6 o eb.

Los args pueden ser cualquier argumento de iptables o ip6tables.

La regla de paso se agregará directamente a la cadena. No hay un mecanismo como el de la regla directa anterior. El usuario de la regla de paso debe asegurarse de que no haya conflictos con las reglas creadas por firewalld.

ADVERTENCIAS

Dependiendo del valor de FirewallBackend (véase firewalld.conf(5)), las reglas directas se comportan de manera diferente en algunos escenarios.

Precedencia de aceptación/rechazo de paquetes

Debido a los detalles de implementación de netfilter dentro del kernel, si se utiliza FirewallBackend=nftables, las reglas directas que *ACEPTAN* paquetes no hacen que los paquetes sean aceptados inmediatamente por el sistema. Esos paquetes seguirán sujetos a la regla de nftables de firewalld. Básicamente, esto significa que hay dos firewalls independientes y los paquetes deben ser aceptados por ambos (iptables y nftables). Como nota al margen, este escenario también ocurre dentro de nftables (de nuevo, debido a netfilter) si hay varias cadenas conectadas al mismo hook; no es tan simple como iptables vs nftables.

Hay un puñado de opciones para solucionar el problema de *ACCEPT*:

1.Reglas enriquecidas

Si se puede usar una regla enriquecida, siempre debe preferirse a las reglas directas. Las Reglas Enriquecidas se convertirán al FirewallBackend habilitado. Véase firewalld.richlanguage(5).

2.Aceptación General

Los usuarios pueden agregar una aceptación explícita al conjunto de reglas de nftables. Esto se puede hacer agregando la interfaz o la fuente a la zona trusted.

Esta estrategia a menudo es empleada por cosas que realizan su propio filtrado, tales como: libvirt, podman, docker.

Advertencia: Esto significa que firewalld no realizará ningún filtrado en estos paquetes. Todo debe hacerse a través de reglas directas o reglas de iptables fuera de banda.

3.Aceptación Selectiva

Alternativamente, habilite solo el servicio, puerto, dirección o lo que sea relevante en la zona apropiada.

4.Revertir al backend de iptables

Un último recurso es revertir al backend de iptables estableciendo FirewallBackend=iptables. Los usuarios deben tener en cuenta que el desarrollo de firewalld se centra en el backend de nftables.

Para las reglas directas que *RECHAZAN* paquetes, los paquetes se rechazan inmediatamente independientemente del valor de FirewallBackend. Como tal, no se necesita ninguna consideración especial.

Firewalld garantiza el comportamiento anterior de ACEPTAR/RECHAZAR registrando hooks de nftables con una menor precedencia que los hooks de iptables.

Precedencia de la interfaz directa

Con FirewallBackend=iptables, las reglas internas de nivel superior de firewalld se aplican antes de que se ejecuten las reglas directas. Esto incluye reglas para aceptar conexiones existentes. En el pasado, esto ha sorprendido a los usuarios. Por ejemplo, si un usuario agrega una regla directa para dejar caer el tráfico en el puerto de destino 22, las sesiones SSH existentes continuarían funcionando, pero las nuevas conexiones serían denegadas.

EJEMPLO

Lista de denegación de las redes 192.168.1.0/24 y 192.168.5.0/24 con registro y descarte temprano en la tabla raw:

<?xml version="1.0" encoding="utf-8"?>
<direct>
  <chain ipv="ipv4" table="raw" chain="denylist"/>
  <rule ipv="ipv4" table="raw" chain="PREROUTING" priority="0">-s 192.168.1.0/24 -j denylist</rule>
  <rule ipv="ipv4" table="raw" chain="PREROUTING" priority="1">-s 192.168.5.0/24 -j denylist</rule>
  <rule ipv="ipv4" table="raw" chain="denylist" priority="0">-m limit --limit 1/min -j LOG --log-prefix "denylisted: "</rule>
  <rule ipv="ipv4" table="raw" chain="denylist" priority="1">-j DROP</rule>
</direct>
