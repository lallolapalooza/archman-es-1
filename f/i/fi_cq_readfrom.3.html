DESCRIPCIÓ

N

Las colas de finalización se utilizan para informar de eventos asociados con las transferencias de datos. Están asociadas con envíos y recepciones de mensajes, RMA, operaciones atómicas, mensajes etiquetados y eventos activados. Los eventos informados suelen estar asociados con un punto final de la fabrica, pero también pueden referirse a regiones de memoria utilizadas como destino de una operación RMA o

atómica.

fi_cq_ope

n

proveedor.

Las CQ pueden estar asociadas con un objeto de espera específico. Los objetos de espera permiten a las aplicaciones bloquearse hasta que el objeto de espera sea señalado, lo que indica que hay una finalización disponible para leer. Los usuarios pueden usar fi_control para recuperar el objeto de espera subyacente asociado con una CQ, para usarlo en otras llamadas al sistema. Los siguientes valores pueden usarse para especificarhe tipo de objeto de espera asociado con una CQ: FI_WAIT_NONE, FI_WAIT_UNSPEC, FI_WAIT_SET, FI_WAIT_FD, FI_WAIT_MUTEX_COND (obsoleto), y FI_WAIT_YIELD. El valor predeterminado es
FI_WAIT_NONE.
- FI_WAIT_NO
NE
Se utiliza para indicar que el usuario no se bloqueará (esperará) por finalizaciones en la CQ. Cuando se especifica FI_WAIT_NONE, la aplicación no puede llamar a fi_cq_sread o
fi_cq_sreadfrom.
- FI_WAIT_UNSP
EC
Especifica que el usuario solo esperará en la CQ usando llamadas de interfaz de fabricación, como fi_cq_sread o fi_cq_sreadfrom. En este caso, el proveedor subyacente puede seleccionar el objeto de espera más apropiado o de mayor rendimiento disponible, incluyendo mecanismos de espera personalizados. No se garantiza que las aplicaciones que seleccionan FI_WAIT_UNSPEC puedan recuperar el objeto de espera
subyacente.
- FI_WAIT_SET (ob
soleto)
Indica que la cola de finalización debe usar un objeto de conjunto de espera para esperar finalizaciones. Si se especifica, el campo wait_set debe referenciar un objeto de conjunto de espera
existente.
- FI_WAIT_
FD
Indica que la CQ debe usar un descriptor de archivo como su mecanismo de espera. Un objeto de espera de descriptor de archivo debe ser utilizable en las rutinas select, poll y epoll. Sin embargo, un proveedor puede señalar un objeto de espera FD marcándolo como legible, escribible o con un
error.
- FI_WAIT_MUTEX_COND
(obsoleto)

espera.
- FI_WAIT_YIE

Indica que la CQ esperará sin un objeto de espera, sino que cederá en cada espera. Permite el uso de fi_cq_sread y fi_cq_sreadfrom a través de un bucle de espera activa (spin)

Si se establece el indicador FI_AFFINITY, esto indica el número de CPU lógico (0..max cpu - 1) al que deben dirigirse las interrupciones asociadas con la CQ. Este campo debe tratarse como una sugerencia para el proveedor y puede ignorarse si el proveedor no admite afinidad de
interrupción.
wait_co
nd
De forma predeterminada, cuando se inserta una finalización en una CQ que admite lecturas bloqueantes (fi_cq_sread/fi_cq_sreadfrom), el objeto
de espera correspondiente se señala. Los usuarios pueden especificar una condición que debe cumplirse primero antes de que la espera se satisfag
a. Este campo indica cómo debe interpretar el proveedor el campo cond, que describe la condición necesaria para señalar el objeto de espera.

Una condición de espera debe tratarse como una optimización. No se requiere que los proveedores cumplan los requisitos de la condición antes de señalar el objeto de espera. Las aplicaciones no deben confiar en que la condición sea necesariamente verdadera cuando una llamada de lectura bloqueante

regresa.

Si wait_cond está establecido en FI_CQ_COND_NONE, no se aplican condiciones adicionales al señalamiento del objeto de espera de la CQ, y la inserción de cualquier nueva entrada activará la condición de espera. Si wait_cond está establecido en FI_CQ_COND_THRESHOLD, el campo cond se interpreta como un valor umbral de tipo size_t. El umbral indica el número de entradas que deben encolarse en la CQ antes de que la espera se

satisfaga.

Este campo se ignora si wait_obj está establecido en

FI_WAIT_NONE.

(obsoleto)

rse. Cuando se inserta un evento en la cola de finalización, el conjunto de espera correspondiente se señalará
si se cumplen todas las condiciones necesarias. El uso de un wait_set permite un método optimizado de espera d

fi_clos

e

La llamada fi_close libera todos los recursos asociados con una cola de finalización. Cualquier finalización que permanezca en la CQ cuando se cierre se

perderá.

Al cerrar la CQ, no debe haber puntos finales abiertos, contextos de tran

smisión ni contextos de recepción asociados con la CQ. Si aún hay recurso
s asociados con la CQ al intentar cerrar, la llamada devolverá -FI_EBUSY.

fi_contro

l

La llamada fi_control se utiliza para acceder a detalles específicos del proveedor o de la implementación de la cola de finalización. El acceso a la CQ debe serializarse en todas las llamadas cuando se invoca fi_control, ya que puede redirigir la implementación de las operaciones de CQ. Los siguientes comandos de control son utilizables con una

CQ.
FI_GETWAIT (void
**)
Este comando permite al usuario recuperar el objeto de espera de bajo nivel asociado con la CQ. El format
o del objeto de espera se especifica durante la creación de la CQ, a través de los atributos de la CQ. El
parámetro arg de fi_control debe ser una dirección donde se escribirá un puntero al objeto de esper
a devuelto. Consulte fi_eq.3 para obtener detalles adicionales sobre el uso de fi_control con FI_GETWAIT.

fi_cq_rea

d

La operación fi_cq_read realiza una lectura no bloqueante de datos de finalización desde la CQ. El formato del evento de finalización se determina usando la opción fi_cq_format que se especificó cuando se abrió la CQ. Se pueden recuperar múltiples finalizaciones de una CQ en una sola llamada. El número máximo de entradas a devolver está limitado por el parámetro count especificado, con el número de entradas leídas exitosamente de la CQ devuelto por la llamada. (Vea la sección de valores de retorno más abajo.) Un valor de count de 0 puede usarse para impulsar el progreso en los puntos finales asociados cuando el progreso manual está

habilitado.

Las CQ están optimizadas para reportar operaciones que se han completado exitosamente. Las operaciones que fallan se reportan 'fuera de banda'. Dichas operaciones se recuperan usando la funci

ón fi_cq_readerr. Cuando se encuentra una operación que ha completado con un error inesperado, se coloca en una cola de errores temporal. Intentar leer de una CQ mientras hay un elemento e
n la cola de errores resulta en que fi_cq_read falle con un código de retorno de -FI_EAVAIL. Las aplicaciones pueden usar este código de retorno para determinar cuándo llamar a fi_cq_readerr.

fi_cq_readfro

m

La llamada fi_cq_readfrom se comporta de manera idéntica a fi_cq_read, con la excepción de que permite que la CQ devuelva información de dirección de origen al usuario para cualquier dato recibido. Los datos de dirección de origen solo están disponibles para aquellos puntos finales configurados con la capacidad FI_SOURCE. Si se llama a fi_cq_readfrom en un punto final para el cual no están disponibles datos de direccionamiento de origen, la dirección de origen se establecerá en FI_ADDR_NOTAVAIL. El número de entradas src_addr de entrada debe ser el mismo que el parámetro

count.

Los datos de direccionamiento de origen devueltos se convierten desde la dirección nativa usada por la fabricación subyacente a un fi_addr_t, que puede usarse en operaciones de transmisión. En la mayoría de las circunstancias, devolver fi_addr_t requiere que la dirección de origen ya haya sido insertada en el vector de direcciones asociado con el punto final receptor. Esto es cierto para vectores de direcciones de tipo FI_AV_TABLE. En algunos proveedores, cuando se usa FI_AV_MAP, las direcciones de origen pueden convertirse algorítmicamente en un fi_addr_t utilizable, aunque la dirección de origen no haya sido insertada en el vector de direcciones. Esto está permitido por la API, ya que permite al proveedor evitar la búsqueda de dirección como parte del procesamiento de mensajes recibidos. En ningún caso los proveedores insertan direcciones en un AV separado de una llamada de la aplicación a fi_av_insert o una llamada

similar.

Para los puntos finales asignados usando la capacidad FI_SOURCE_ERR, si la dirección de origen no puede convertirse en un valor fi_addr_t válido, fi_cq_readfrom devolverá -FI_EAVAIL, incluso si los datos se recibieron exitosamente. La finalización será reportada entonces a través de fi_cq_readerr con el código de error -FI_EADDRNOTAVAIL. Consulte fi_cq_readerr para más

detalles.

Si FI_SOURCE se especifica sin FI_SOURCE_ERR, las direcciones de origen que no puedan mapearse a un fi_addr_t utilizable serán reportadas como FI_ADDR_NOTAVAI

fi_cq_sread /

fi_cq_sreadfrom

Las llamadas fi_cq_sread y fi_cq_sreadfrom son las operaciones equivalentes bloqueantes a fi_cq_read y fi_cq_readfrom. Su comportamiento es similar al de las llamadas no bloqueantes, con la excepción de que las llamadas no regresarán hasta que se haya leído una finalización de la CQ o ocurra un error o tiempo de espera

agotado.

Los hilos bloqueados en esta función regresarán al llamador si son señalizados por alguna fuente externa. Esto es cierto incluso si el tiempo de espera no ha ocurrido o se especificó como

infinito.

No es válido que las aplicaciones llamen a estas

funciones si la CQ ha sido configurada con u
n objeto de espera de FI_WAIT_NONE o FI_WAIT_SET.

fi_cq_reader

r

La función de lectura de errores, fi_cq_readerr, recupera información sobre cualquier operación asíncrona que haya completado con un error inesperado. fi_cq_readerr es una llamada no bloqueante, regresando inmediatamente ya sea que se haya encontrado una finalización de error o

no.

continuación.

ERRORES

Los códigos de error de finalización se devuelven en el campo err de la estructura fi_cq_err_entry. La mayoría de los errores de finalización son códigos de error de fabric estándar (consulte fi_errno.3 para obtener una lista completa). Los campos prov_errno y err_data se pueden utilizar para proporcionar información adicional sobre el error. La información devuelta en err_data es específica del proveedor y está pensada para ayudar en la depuración.

Para las terminaciones que no están asociadas con una operación publicada, la estructura de terminación contendrá información sobre el error. En tales casos, los campos op_context y src_addr pueden no ser válidos o contener información útil sobre el error.

Por ejemplo, si un CQ se configura con FI_SELECTIVE_COMPLETION, pero la solicitud no tiene el indicador FI_COMPLETION establecido. En tales casos, los proveedores devolverán tanta información como sea disponible por el software y hardware subyacentes sobre el error, otros campos se establecerán en NULL o 0. Esto incluye el valor op_context, que puede no haber sido proporcionado o fue ignorado en la entrada como parte de la transferencia.

Los códigos de error de finalización notables se dan a continuación.

FI_EADDRNOTAVAIL
Este código de error es utilizado por los CQ configurados con FI_SOURCE_ERR para informar sobre finalizaciones para las cuales no se pudo encontrar una dirección de origen fi_addr_t utilizable. Un código de error de FI_EADDRNOTAVAIL indica que la transferencia de datos se recibió y procesó correctamente, con los campos fi_cq_err_entry que contienen información sobre la finalización. El campo err_data se establecerá en los datos de la dirección de origen. La dirección de origen estará en el mismo formato que se especificó a través del campo fi_info addr_format para el dominio abierto. Esto se puede pasar directamente a una llamada fi_av_insert para agregar la dirección de origen al vector de direcciones.

Para las versiones de API 1.20 y posteriores, si el EP está configurado con FI_AV_AUTH_KEY, src_addr se establecerá en el identificador de clave de autorización fi_addr_t o en un identificador de clave de autorización definido por el usuario que corresponda a la transferencia de datos entrante. De lo contrario, el valor se establecerá en FI_ADDR_NOTAVAIL.

fi_cq_signal

La llamada fi_cq_signal desbloqueará cualquier hilo que esté esperando en fi_cq_sread o fi_cq_sreadfrom. Esto se puede utilizar para activar un hilo que está bloqueado esperando leer una operación de finalización. La operación fi_cq_signal solo está disponible si el CQ se configuró con un objeto de espera.

CAMPOS DE FINALIZACIÓN

Las estructuras de datos de entrada del CQ comparten muchos de los mismos campos. Los significados de estos campos son los mismos para todos los formatos de estructura de entrada del CQ.

op_context
El contexto de la operación es el valor de contexto especificado por la aplicación que se proporcionó con una operación asíncrona. El campo op_context es válido para todas las finalizaciones que están asociadas con una operación asíncrona.

Para los eventos de finalización que no están asociados con una operación publicada, este campo se establecerá en NULL. Esto incluye las finalizaciones generadas en el destino en respuesta a operaciones de escritura RMA que transportan datos de CQ (indicadores FI_REMOTE_WRITE | FI_REMOTE_CQ_DATA establecidos), cuando el bit de modo FI_RX_CQ_DATA no es requerido.

flags
Esto especifica los indicadores asociados con la operación completada. La sección Indicadores de finalización a continuación enumera los valores de indicador válidos. Los indicadores se establecen para todas las finalizaciones relevantes.
len
Este campo len se aplica a las operaciones de recepción completadas (por ejemplo, fi_recv, fi_trecv, etc.) y la escritura completada con datos remotos de CQ en el lado del respondedor (por ejemplo, fi_write, con el indicador FI_REMOTE_CQ_DATA). Indica el tamaño de los datos de mensaje transferidos, es decir, cuántos bytes de datos se colocaron en el búfer de recepción/destino asociado por una llamada correspondiente fi_send/ fi_tsend/ fi_write et al. Si un punto final se ha configurado con el modo FI_MSG_PREFIX, la longitud también refleja el tamaño del búfer de prefijo.
buf
El campo buf solo es válido para operaciones de recepción completadas y solo se aplica cuando el búfer de recepción se publicó con el indicador FI_MULTI_RECV. En este caso, buf apunta a la ubicación inicial donde se colocaron los datos de recepción.
data
El campo data solo es válido si se establece el indicador de finalización FI_REMOTE_CQ_DATA, y solo se aplica a las finalizaciones de recepción. Si se establece FI_REMOTE_CQ_DATA, este campo contendrá los datos de finalización proporcionados por el par como parte de su solicitud de transmisión. Los datos de finalización se proporcionarán en orden de bytes del host.
tag
Una etiqueta se aplica solo a los mensajes recibidos que ocurren utilizando las interfaces etiquetadas. Este campo contiene la etiqueta que se incluyó con el mensaje recibido. La etiqueta estará en orden de bytes del host.
olen
El campo olen se aplica a los mensajes recibidos. Se utiliza para indicar que un mensaje recibido ha superado el espacio disponible del búfer y se ha truncado. olen especifica la cantidad de datos que no cabían en el búfer de recepción disponible y que se descartaron.
err
Este código de error err es un errno de fabric positivo asociado con una finalización. El valor err indica la razón general de un error, si ocurrió uno. Consulte fi_errno.3 para obtener una lista de posibles códigos de error.
prov_errno
En caso de error, prov_errno puede contener un código de error específico del proveedor. El uso de este campo y su significado son específicos del proveedor. Está destinado a ser utilizado como ayuda para la depuración. Consulte fi_cq_strerror para obtener detalles adicionales sobre la conversión de este valor de error en una cadena legible por humanos.
err_data
El campo err_data se utiliza para devolver información específica del proveedor, si está disponible, sobre el error. En la entrada, err_data debe hacer referencia a un búfer de datos del tamaño err_data_size. En la salida, el proveedor llenará este búfer con cualquier dato específico del proveedor que pueda ayudar a identificar la causa del error. El contenido del campo err_data y su significado son específicos del proveedor. Está destinado a ser utilizado como ayuda para la depuración. Consulte fi_cq_strerror para obtener detalles adicionales sobre la conversión de estos datos de error en una cadena legible por humanos. Consulte la nota de compatibilidad a continuación sobre cómo se utiliza este campo para versiones anteriores de libfabric.
err_data_size
En la entrada, err_data_size indica el tamaño del búfer err_data en bytes. En la salida, err_data_size se establecerá en el número de bytes copiados al búfer err_data. La información de err_data se utiliza típicamente con fi_cq_strerror para proporcionar detalles sobre el tipo de error que ocurrió.

Para fines de compatibilidad, el comportamiento de los campos err_data y err_data_size puede modificarse con respecto a lo indicado anteriormente. Si err_data_size es 0 en la entrada, o si la fabric se abrió con una versión < 1.5, entonces cualquier búfer al que haga referencia err_data se ignorará en la entrada. En esta situación, en la salida err_data se establecerá en un búfer de datos propiedad del proveedor. El contenido del búfer seguirá siendo válido hasta una llamada de lectura posterior contra el CQ. Las aplicaciones deben serializar el acceso al CQ al procesar errores para garantizar que el búfer al que hace referencia err_data no cambie.

src_addr
Se utiliza para devolver información relacionada con direcciones de origen para eventos de error. Cómo se utiliza este campo depende del evento de error específico.

INDICADORES DE FINALIZACIÓN

Los indicadores de finalización proporcionan detalles adicionales sobre la operación completada. Se definen los siguientes indicadores de finalización.

FI_SEND
Indica que la finalización fue para una operación de envío. Este indicador puede combinarse con un indicador FI_MSG o FI_TAGGED.
FI_RECV
Indica que la finalización fue para una operación de recepción. Este indicador puede combinarse con un indicador FI_MSG o FI_TAGGED.
FI_RMA
Indica que se completó una operación RMA. Este indicador puede combinarse con un indicador FI_READ, FI_WRITE, FI_REMOTE_READ o FI_REMOTE_WRITE.
FI_ATOMIC
Indica que se completó una operación atómica. Este indicador puede combinarse con un indicador FI_READ, FI_WRITE, FI_REMOTE_READ o FI_REMOTE_WRITE.
FI_MSG
Indica que se completó una operación basada en mensajes. Este indicador puede combinarse con un indicador FI_SEND o FI_RECV.
FI_TAGGED
Indica que se completó una operación de mensaje etiquetado. Este indicador puede combinarse con un indicador FI_SEND o FI_RECV.
FI_MULTICAST
Indica que se completó una operación de multidifusión. Este indicador puede combinarse con FI_MSG e indicadores relevantes. Este indicador solo se garantiza que sea válido para los mensajes recibidos si el punto final se configuró con FI_SOURCE.
FI_READ
Indica que se completó una operación de lectura RMA o atómica iniciada localmente. Este indicador puede combinarse con un indicador FI_RMA o FI_ATOMIC.
FI_WRITE
Indica que se completó una operación de escritura RMA o atómica iniciada localmente. Este indicador puede combinarse con un indicador FI_RMA o FI_ATOMIC.
FI_REMOTE_READ
Indica que se completó una operación de lectura RMA o atómica iniciada remotamente. Este indicador puede combinarse con un indicador FI_RMA o FI_ATOMIC.
FI_REMOTE_WRITE
Indica que se completó una operación de escritura RMA o atómica iniciada remotamente. Este indicador puede combinarse con un indicador FI_RMA o FI_ATOMIC.
FI_REMOTE_CQ_DATA
Esto indica que los datos remotos de CQ están disponibles como parte de la finalización.
FI_MULTI_RECV
Este indicador se aplica a los búferes de recepción que se publicaron con el indicador FI_MULTI_RECV establecido. Este indicador de finalización indica que el búfer de recepción original al que hace referencia la finalización ha sido consumido y liberado por el proveedor. Los proveedores pueden establecer este indicador en el último mensaje que se recibe en el búfer de recepción múltiple, o pueden generar una finalización separada que indique que el búfer ha sido liberado.

Las aplicaciones pueden distinguir entre estos dos casos examinando el campo de indicadores de la entrada de finalización. Si se establecen indicadores adicionales, como FI_RECV, la finalización se asocia con un mensaje recibido. En este ca

ase, el campo buf hará referencia a la ubicación donde se colocó el mensaje recibido en el búfer de recepción múltiple. Los demás campos

de la entrada de finalización se determinarán en función del mensaje recibido. Si los demás bits de indicador son cero, el proveedor está
informando que el búfer de recepción múltiple ha sido liberado y que la entrada de finalización no está asociada con un mensaje recibido.

SEMÁNTICA DE EVENTOS DE

FINALIZACIÓN

Libfabric define varios `niveles' de finalización, identificados mediante indicadores operativos. Cada indicador indica el momento más temprano en que un proveedor puede generar un evento de finalización y las suposiciones que una aplicación puede hacer al procesar una finalización. Los indicadores operativos se definen a continuación, junto con un ejemplo de cómo un proveedor podría implementar la semántica. Tenga en cuenta que solo se requiere que el proveedor cumpla con la semántica, no con la implementación. Los proveedores pueden implementar semánticas de finalización más estrictas de las necesarias para una operación determinada, pero solo se garantiza el comportamiento definido por el nivel de

finalización.

Para ayudar a comprender las diferencias conceptuales entre los niveles de finalización, considere el envío de una carta. Colocar la carta en el buzón local para su recogida es similar a `finalización de inyección'. Tener la carta recogida y depositada en el buzón de destino es equivalente a `finalización de transmisión'. La semántica de `finalización de entrega' es una garantía más fuerte, con una persona en el destino firmando la recepción de la carta. Sin embargo, la persona que firma la recepción de la carta no es necesariamente el destinatario previsto. La opción de `finalización de coincidencia' es similar a la finalización de entrega, pero requiere que el destinatario previsto firme la recepción de la

carta.

El nivel de `finalización de compromiso' tiene una semántica diferente a la de los niveles mencionados anteriormente. La finalización de compromiso sería más parecida a la carta que llega al destino y se coloca en una caja fuerte a prueba de

fuego.

Los indicadores operativos para los niveles de finalización descritos se definen a

continuación.

Una finalización de inyección no indica que los datos hayan sido transmitidos a la red, y podría ocurrir un error local después de que se haya generado el evento de finalización, lo que podría impedir que se

transmita.

La finalización de inyección permite el informe de finalización más rápido (y, por lo tanto, la reutilización del búfer), pero proporciona las garantías más débiles contra los errores de

SEMÁNTICAS DE FINALIZACIÓN EN EL

DESTINO

La semántica de finalización en el destino se utiliza para determinar cuándo los datos en el destino son visibles para la aplicación par. La visibilidad indica que una lectura de memoria en la misma dirección que fue el destino de una transferencia de datos devolverá los resultados de la transferencia. El destino de una transferencia puede ser identificado por el iniciador, como puede ser el caso de las operaciones RMA y atómicas, o determinado por el destino, por ejemplo, al proporcionar un búfer de recepción coincidente. La visibilidad global indica que los resultados están disponibles sin importar desde dónde provenga la lectura de memoria. Por ejemplo, la lectura podría provenir de un proceso que se ejecuta en una CPU del host, podría ser accedida por una transferencia de datos posterior a través de la red de fibra, o leída desde un dispositivo par como una

GPU.

En términos de semánticas de finalización, la visibilidad generalmente indica que la transferencia cumple los requisitos de FI_DELIVERY_COMPLETE desde la perspectiva del destino. La semántica de finalización en el destino puede estar, pero no necesariamente está, vinculada con la semántica de finalización especificada por el iniciador de la

transferencia.

A menudo, los procesos de destino no declaran explícitamente una semántica de finalización deseada y en su lugar dependen de la semántica predeterminada. El comportamiento predeterminado se basa en varios factores,

incluyendo:

el tipo de transferencia involucrada (por ejemplo, msg vs
RMA)

En términos generales, las semánticas de finalización en el destino se agrupan en función de si la transferencia genera o no un evento de finalización en el destino. Esto incluye la escritura de una entrada de CQ o la actualización de un contador de finalización. En casos de uso comunes, las transferencias que utilizan una interfaz de mensaje (FI_MSG o FI_TAGGED) típicamente generan eventos en el destino, mientras que las transferencias que involucran una interfaz RMA (FI_RMA o FI_ATOMIC) a menudo no lo hacen. Hay excepciones a ambos casos, dependiendo de los enlaces de punto de extremo a CQ y contadores, y de los indicadores operativos. Por ejemplo, las escrituras RMA que llevan datos de CQ remotos generarán un evento de finalización en el destino y se utilizan frecuentemente para transmitir visibilidad a la aplicación de destino. Las pautas generales para la semántica del lado del destino se describen a continuación, seguidas de las excepciones que modifican ese

comportamiento.

De forma predeterminada, las finalizaciones generadas en el destino indican que los datos transferidos están inmediatamente disponibles para ser leídos desde el búfer de destino. Es decir, el destino ve semánticas de FI_DELIVERY_COMPLETE (o mejores), incluso si el iniciador solicitó semánticas más bajas. Para aplicaciones que usan solo búferes de datos asignados desde la memoria del host, esto suele ser

suficiente. p">Para operaciones que no generan un evento de finalización en el destino, la visibilidad de los datos en el destino puede necesitar inferirse basándose en operaciones posteriores que sí generan finalizaciones en el destino. Sin una finalización en el destino, cuando se escribe en el iniciador la finalización de una operación, la semántica de visibilidad de la operación en el destino se alinea con la semántica de finalización del iniciador. Por ejemplo, si una operación RMA finaliza en el iniciador como FI_INJECT_COMPLETE o FI_TRANSMIT_COMPLETE, la visibilidad de los datos en el destino no está

garantizada.

El proceso de destino puede utilizar uno o más de los siguientes mecanismos para garantizar que los resultados de una transferencia de datos que no generó una finalización en el destino ahora son visibles. Esta lista no incluye todas las opciones, sino que define los usos comunes. En las descripciones siguientes, la primera transferencia no resulta en un evento de finalización en el destino, pero es seguida eventualmente por una transferencia que sí lo

hace.
•
Si el punto de extremo garantiza el orden de mensajes entre dos transferencias, la finalización en el destino de una segunda transferencia indicará que los datos de la primera transferencia están disponibles. Por ejemplo, si el punto de extremo soporta el orden de escritura después de envío (FI_ORDER_SAW), entonces una finalización de recepción correspondiente al envío indicará que los datos de la escritura están disponibles. Esto se mantiene independientemente de la semántica de finalización del iniciador para la escritura o el envío. Cuando se garantiza el orden, la segunda transferencia puede encolarse con el proveedor inmediatamente después de encolar la
primera.
•
Si el punto de extremo no garantiza el orden de mensajes, el iniciador debe tomar pasos adicionales para asegurar la visibilidad. Si el iniciador solicita la semántica FI_DELIVERY_COMPLETE para la primera operación, el iniciador puede esperar a que la operación finalice localmente. Una vez que se ha leído la finalización, la finalización en el destino de una segunda transferencia indicará que los datos de la primera transferencia son
visibles.
•
Alternativamente, si el punto de extremo no garantiza el orden de mensajes, el iniciador puede usar los indicadores FI_FENCE y FI_DELIVERY_COMPLETE en la segunda transferenc
ia de datos para forzar que la primera transferencia cumpla la semántica FI_DELIVERY_COMPLETE. Si la segunda transferencia genera una finalización en el destino, eso indicar
á que los datos son visibles. De lo contrario, una finalización en el destino de cualquier transferencia después de la operación cercada indicará que los datos son visibles.

Las semánticas anteriores se aplican a transferencias dirigidas a búferes de memoria del host tradicional. Sin embargo, el comportamiento puede diferir cuando se involucra memoria de dispositivo y/o memoria persistente (bits de capacidad FI_HMEM y FI_PMEM). Cuando se involucra memoria heterogénea, el concepto de dominios de memoria entra en juego. Los dominios de memoria identifican la separación física de la memoria, la cual puede o no ser accesible a través del mismo espacio de direcciones virtuales. Consulte la página de manual fi_mr(3) para más detalles sobre dominios de

memoria.

El orden de finalización y la visibilidad de los datos solo están bien definidos para transferencias dirigidas al mismo dominio de memoria. Las aplicaciones deben ser conscientes de las diferencias de orden y visibilidad cuando las transferencias están dirigidas a diferentes dominios de memoria. Además, las aplicaciones también deben preocuparse por el dominio de memoria en el que se escriben las finalizaciones mismas y si difiere del dominio de memoria al que está dirigida una transferencia. En algunas situaciones, tanto el proveedor como la aplicación pueden necesitar llamar a APIs específicas del dispositivo para sincronizar o vaciar (flush) las cachés de memoria del dispositivo para lograr la visibilidad de datos

deseada.

Cuando se usa memoria heterogénea, la semántica de finalización en el destino por defecto para transferencias que generan una finalización en el destino sigue siendo FI_DELIVERY_COMPLETE; sin embargo, las aplicaciones deben ser conscientes de que puede haber un impacto negativo en el rendimiento general para que los proveedores cumplan este

requisito.

Por ejemplo, un proceso de destino puede estar usando una GPU para acelerar cálculos. Una región de memoria que mapea a memoria en la GPU puede exponerse a pares como un destino RMA o publicarse localmente como un búfer de recepción. En este caso, la aplicación se preocupa por dos dominios de memoria: memoria del sistema y memoria de la GPU. Las finalizaciones se escriben en la memoria del

sistema.

Continuando con el ejemplo, un proceso par envía un mensaje etiquetado. Ese mensaje coincide con el búfer de recepción ubicado en la memoria de la GPU. La NIC copia los datos de la red al búfer de recepción y escribe una entrada en la cola de finalización. Nótese que ambos dominios de memoria fueron accedidos como parte de esta transferencia. Los datos del mensaje fueron dirigidos a la memoria de la GPU, pero la finalización fue a la memoria del host. Debido a que dominios de memoria separados pueden no estar sincronizados entre sí, es posible que la CPU del host vea y procese la entrada de finalización antes de que la transferencia a la memoria de la GPU sea visible tanto para la GPU del host como incluso para el software que se ejecuta en la GPU. Desde la perspectiva del proveedor, la visibilidad de la finalización no implica la visibilidad de los datos escritos en el dominio de memoria de la

GPU.

La semántica de finalización por defecto en el destino aplicación para operaciones de mensaje es FI_DELIVERY_COMPLETE. Una implementación anticipada del proveedor en esta situación es que el software del proveedor que se ejecuta en la CPU del host intercepte la entrada de la CQ, detecte que los datos aterrizaron en memoria heterogénea, y realice la sincronización o la operación de vaciado (flush) necesaria del dispositivo antes de reportar la finalización a la aplicación. Esto asegura que los datos son visibles para la CPU y el software de la GPU antes de que la aplicación procese la

finalización.

Además del costo de que el software del proveedor intercepte finalizaciones y verifique si una transferencia está dirigida a memoria heterogénea, la sincronización del dispositivo misma puede impactar el rendimiento. Como resultado, las aplicaciones pueden solicitar una semántica de finalización más baja al publicar recepciones. Eso le indica al proveedor que la aplicación será responsable de manejar cualquier operación de vaciado (flush) específica del dispositivo que pueda ser necesaria. Consulte fi_msg(3)

FLAGS.

Para transferencias de datos que no generan una finalización en el destino, como RMA o operaciones atómicas, es responsabilidad de la aplicación asegurar que todos los búferes de destino cumplan con los requisitos de visibilidad necesarios de la aplicación. Los métodos con viñetas mencionados anteriormente para notificar al destino que los datos son visibles pueden no ser suficientes, ya que el software del proveedor en el destino podría carecer del contexto necesario para asegurar la visibilidad. Esto implica que la aplicación podría necesitar llamar directamente a las APIs de sincronización/vaciado (flush) del

dispositivo.

Por ejemplo, una aplicación par podría realizar varias escrituras RMA dirigidas a búferes de memoria de la GPU. Si el proveedor descarga las operaciones RMA a la NIC, el software del proveedor en el destino no será consciente de que las operaciones RMA han ocurrido. Si el par envía un mensaje a la aplicación de destino que indica que las operaciones RMA están hechas, la aplicación debe asegurar que los datos RMA son visibles para la CPU del host o la GPU antes de ejecutar código que acceda a los datos. La finalización en el destino de haber recibido el mensaje enviado no es suficiente, incluso si se soporta el orden de escritura después de envío (send-after-write)

.

La mayoría de las semánticas de finalización en el destino de memoria heterogénea se mapean a FI_TRANSMIT_COMPLETE o FI_DELIVERY_COMPLETE. La memoria persistente (capacidad FI_PMEM), sin embargo, se usa a menudo con la semántica FI_COMMIT_COMPLETE. Los conceptos de finalización heterogénea aún se

aplican.

Para transferencias marcadas por el iniciador con FI_COMMIT_COMPLETE, una finalización en el destino indica que los resultados son visibles y duraderos. Para transferencias dirigidas a memoria persistente, pero usando una semántica de finalización diferente en el iniciador, la visibilidad en el destino es similar a la descrita anteriormente. La durabilidad solo está asociada con transferencias marcadas con FI_COMMIT_COMPLETE

.

Para transferencias dirigidas a memoria persistente que solicitan FI_DELIVERY_COMPLETE, entonces una finalización, ya sea en el iniciador o en el destino, indica que los datos son visibles. La visibilidad en el destino puede ser conveyada usando uno de los mecanismos descritos anteriormente – generando una finalización en el destino, enviando un mensaje desde el iniciador, etc. De manera similar, si el iniciador solicitó FI_TRANSMIT_COMPLETE, entonces se necesitan pasos adicionales para asegurar la visibilidad en el destino. Por ejemplo, la transferencia puede generar una finalización en el destino, lo cual indicaría visibilidad, pero no durabilidad. El iniciador también puede seguir la transferencia con otra operación que fuerce la visibilidad, como usar FI_FENCE en conjunto con FI_DELIVERY_COMPLET

E
.

NOTA

S

Una cola de finalización debe estar vinculada a al menos un punto de extremo habilitado antes de que cualquier operación como fi_cq_read, fi_cq_readfrom, fi_cq_sread, fi_cq_sreadfrom, etc. pueda ser llamada en

ella.

Si una cola de finalización ha sido desbordada (overrun), será colocada en un estado de `desbordamiento'. Las operaciones de lectura continuarán devolviendo cualquier finalización

válida y no corrupta, si hay disponibles. Después de que todas las finalizaciones válidas han sido recuperadas, cualquier intento de leer la CQ resultará en que devuelva un evento
de error FI_EOVERRUN. Las colas de finalización desbordadas se consideran fatales y no pueden usarse para reportar finalizaciones adicionales una vez que ocurre el desbordamiento.

NAME

fi_cq_readfrom — retrieve completion events from a completion queue

SYNOPSIS

#include <rdma/fabric.h>

ssize_t fi_cq_readfrom(struct fi_cq_entry *buf, size_t len);
ssize_t fi_cq_readfrom(struct fi_cq_entry *buf, size_t len, void *ctx);
ssize_t fi_cq_readfrom(struct fi_cq_entry *buf, size_t len, uint64_t flags);
ssize_t fi_cq_readfrom(struct fi_cq_entry *buf, size_t len, void *ctx,
    uint64_t flags);

ARGUMENTS

buf
Pointer to a buffer where completion events will be copied. The buffer must be large enough to hold at least one struct fi_cq_entry. The size of the buffer is specified by the len argument.
len
The size of the buffer pointed to by buf in bytes.
ctx
User-specified context. This context is returned with the completion event and can be used to identify the operation associated with the completion. This argument is optional and can be NULL.
flags
Flags that control the behavior of the read operation. Supported flags include:
FI_DISP
If set, the completion queue is considered a producer and consumer queue. The underlying fabric provider is responsible for managing the queue. This flag should be used when multiple threads or processes are accessing the same completion queue.
FI_REMOTE_CQ
If set, the completion queue is a remote completion queue. This flag is typically used in multi-node environments where completion events are generated on a remote node and need to be read from a local completion queue.
FI_PEEK
If set, the completion event is not removed from the completion queue. This flag can be used to inspect the next completion event without consuming it.

DESCRIPTION

The fi_cq_readfrom function retrieves one or more completion events from a completion queue (CQ). Completion events indicate the completion of asynchronous operations such as send, receive, or data transfer.

The function attempts to read up to len bytes worth of completion events into the buffer pointed to by buf. Each completion event is represented by a struct fi_cq_entry. If multiple completion events are available and fit within the specified buffer size, they are all returned. If no completion events are available, fi_cq_readfrom will block until an event is available or an error occurs.

The ctx argument allows the caller to associate a context with the completion event. This context is user-defined and can be used to identify the operation that generated the completion.

The flags argument allows the caller to modify the behavior of the fi_cq_readfrom function. For example, FI_PEEK can be used to inspect the next completion event without removing it from the CQ.

COMPLETION FIELDS

The struct fi_cq_entry structure contains the following fields:

fi_cqe_result
The result of the operation. This can be an error code or a status indication.
fi_cqe_data
User-defined data associated with the completion event. This field is typically used to store the context specified in the original operation.
fi_cqe_flags
Flags that provide additional information about the completion event.
fi_cqe_op_err
If the operation resulted in an error, this field contains the specific error code returned by the fabric provider.

COMPLETION FLAGS

The fi_cqe_flags field can contain the following flags:

FI_OP_READ
Indicates that the completion event is for a read operation.
FI_OP_WRITE
Indicates that the completion event is for a write operation.
FI_OP_SEND
Indicates that the completion event is for a send operation.
FI_OP_RECV
Indicates that the completion event is for a receive operation.
FI_REMOTE_ERROR
Indicates that the error occurred on the remote side.

COMPLETION EVENT SEMANTICS

The completion event semantics define how completion events are generated and consumed. The semantics are determined by the flags used when creating the completion queue and the flags used with fi_cq_readfrom.

TARGET COMPLETION SEMANTICS

The target completion semantics define the behavior of the fi_cq_readfrom function when interacting with a remote completion queue. This is typically used in distributed environments where completion events are generated on a remote node and need to be retrieved from a local CQ.

NOTES

The fi_cq_readfrom function is a blocking call. If no completion events are available, the function will suspend execution until an event is received or an error occurs. For non-blocking reads, consider using fi_cq_readfrom with the FI_NONBLOCK flag or polling mechanisms.

The ctx argument can be used to associate arbitrary user data with a completion event. This is useful for tracking the state of asynchronous operations.

Fabric errno values are defined in rdma/fi_errno.h.

RETURN VALUES

Upon successful completion, fi_cq_readfrom returns the number of bytes read, which may be less than or equal to len. If 0 bytes are read, it means no completion events were available.

On failure, fi_cq_readfrom returns a negative error code, such as:

-FI_ENOMSG
No completion events were available in the queue.
-FI_EINVAL
Invalid arguments were provided.
-FI_EAGAIN
The operation would block and non-blocking mode was requested.
-FI_EPROTO
An unspecified protocol error occurred.

The specific error returned with a completion.

Fabric errno values are defined in rdma/fi_errno.h.
