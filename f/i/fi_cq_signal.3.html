fi_cq - Operaciones de cola de finalización

Abrir/cerrar una cola de finalización
fi_control
Controlar la operación o atributos de la CQ.
fi_cq_read / fi_cq_readfrom / fi_cq_readerr
Leer una finalización de una cola de finalización

DESCRIPCIÓN

Las colas de finalización se utilizan para informar eventos asociados con transferencias de datos. Están asociadas con envíos y recepciones de mensajes, RMA, atómicos, mensajes etiquetados y eventos activados. Los eventos informados generalmente están asociados con un punto final de la red, pero también pueden referirse a regiones de memoria utilizadas como destino de una operación RMA o atómica.

fi_cq_open

fi_cq_open asigna una nueva cola de finalización. A diferencia de las colas de eventos, las colas de finalización están asociadas con un dominio de recursos y pueden descargarse completamente en el hardware del proveedor.

Las propiedades y el comportamiento de una cola de finalización se definen mediante struct fi_cq_attr.

struct fi_cq_attr {
    size_t               size;      /* # entradas para CQ */
    uint64_t             flags;     /* marcas de operación */
    enum fi_cq_format    format;    /* formato de finalización */
    enum fi_wait_obj     wait_obj;  /* objeto de espera solicitado */
    int                  signaling_vector; /* afinidad de interrupción */
    enum fi_cq_wait_cond wait_cond; /* formato de condición de espera */
    struct fid_wait     *wait_set;  /* conjunto de espera opcional, obsoleto */
};
size
Especifica el tamaño mínimo de una cola de finalización. Un valor de 0 indica que el proveedor puede elegir un valor predeterminado.
flags
Marcas que controlan la configuración de la CQ.
- FI_AFFINITY
Indica que el campo signaling_vector (ver más abajo) es válido.
format
Las colas de finalización permiten a la aplicación seleccionar la cantidad de detalle que debe almacenar e informar. El atributo format permite a la aplicación seleccionar uno de varios formatos de finalización, indicando la estructura de los datos que la cola de finalización debe devolver al leerse. Los formatos compatibles y las estructuras que corresponden a cada uno se enumeran a continuación. El significado de los campos de la entrada de la CQ se define en la sección Campos de Finalización.
- FI_CQ_FORMAT_UNSPEC
Si se solicita un formato no especificado, la CQ utilizará un formato predeterminado elegido por el proveedor.
- FI_CQ_FORMAT_CONTEXT
Proporciona solo el contexto especificado por el usuario que se asoció con la finalización.
struct fi_cq_entry {
    void     *op_context; /* contexto de operación */
};

wait_obj
Las CQs pueden asociarse con un objeto de espera específico. Los objetos de espera permiten a las aplicaciones bloquearse hasta que el objeto de espera se señale, indicando que hay una finalización disponible para leer. Los usuarios pueden usar fi_control para recuperar el objeto de espera subyacente asociado con una CQ, para usarlo en otras llamadas del sistema. Los siguientes valores se pueden usar para especificar el

objeto de espera:

- FI_WAIT_UNSPEC
El proveedor elegirá un objeto de espera predeterminado.
- FI_WAIT_NONE
No se asociará ningún objeto de espera con la CQ.
- FI_WAIT_EVSET
La CQ se asociará con un conjunto de eventos (event set).
- FI_WAIT_FD
La CQ se asociará con un descriptor de archivo (file descriptor).
signaling_vector
Especifica el vector de interrupción al que se debe vincular la señalización de la CQ. Esto solo es relevante cuando se usa FI_AFFINITY.
wait_cond
Especifica el formato de la condición de espera. Consulte fi_wait(3) para ver los detalles de las condiciones de espera.
wait_set
Un conjunto de espera opcional al que se puede adjuntar la CQ. El uso de conjuntos de espera es obsoleto y se prefiere el uso de la función fi_wait con objetos de espera individuales.

fi_cq_open devuelve un objeto fid_cq que representa la cola de finalización recién creada.

El argumento context se puede usar para asociar un contexto definido por el usuario con la cola de finalización. Este contexto se devuelve en las entradas de finalización y se puede usar para identificar la operación que generó la finalización.

fi_close

fi_close cierra y libera los recursos asociados con un objeto fid. Cuando se llama en un objeto fid_cq, cierra la cola de finalización.

fi_control

fi_control se puede usar para obtener información y controlar diversos aspectos de un objeto fid_cq. Los comandos comunes incluyen:

FI_GETWAIT
Recupera el objeto de espera asociado con la CQ. El argumento arg debe apuntar a un puntero a un struct fid_wait. Si la CQ está asociada con un objeto de espera, este se devolverá en el puntero.
FI_GETINHR
Recupera el descriptor de archivo o el objeto de evento asociado con la CQ. El argumento arg debe apuntar a una estructura que pueda contener el objeto de espera (por ejemplo, struct fi_wait_fd).
FI_ANNUL_OPS
Anula las operaciones de una CQ. El argumento arg debe apuntar a un entero que contenga el valor FI_ANNUL_OPS.

fi_cq_read

fi_cq_read lee hasta count entradas de la cola de finalización y las almacena en el búfer buf. El número de entradas leídas se devuelve como un valor de tamaño. Si no hay finalizaciones disponibles, se devuelve -1 con errno establecido en EAGAIN.

fi_cq_readfrom

fi_cq_readfrom es similar a fi_cq_read, pero también recupera la dirección de origen de la operación de recepción completada, si corresponde. La dirección de origen se almacena en *src_addr.

fi_cq_readerr

fi_cq_readerr lee una entrada de error de la cola de finalización. Las entradas de error se utilizan para informar sobre errores que ocurrieron durante una operación. El búfer buf debe apuntar a una estructura fi_cq_err_entry. El campo flags puede usarse para controlar el comportamiento de la lectura de errores.

struct fi_cq_err_entry {
    void     *op_context; /* contexto de operación */
    uint64_t flags;       /* marcas de finalización */
    int      err;         /* código de error */
    void     *err_data;   /* datos de error específicos del proveedor */
};

fi_cq_sread

fi_cq_sread es una versión síncrona (bloqueante) de fi_cq_read. Espera hasta que se cumpla la condición especificada en *cond o hasta que expire el tiempo de espera especificado por timeout. Si se cumple la condición, lee hasta count entradas de la cola de finalización y las almacena en el búfer buf. El número de entradas leídas se devuelve como un valor de tamaño. Si expira el tiempo de espera sin que se cumpla la condición, se devuelve -1 con errno establecido en ETIME.

El argumento cond especifica la condición que debe cumplirse. El formato exacto de cond depende del campo wait_cond en struct fi_cq_attr.

El argumento timeout especifica el tiempo máximo en milisegundos que la función esperará. Un valor negativo indica un tiempo de espera infinito.

fi_cq_sreadfrom

fi_cq_sreadfrom es la versión síncrona de fi_cq_readfrom. Espera hasta que se cumpla la condición especificada en *cond o hasta que expire el tiempo de espera especificado por timeout. Si se cumple la condición, lee hasta count entradas de la cola de finalización y las almacena en el búfer buf. También recupera la dirección de origen de la operación de recepción completada en *src_addr.

fi_cq_signal

fi_cq_signal se utiliza para señalar una cola de finalización. Esto puede ser útil para despertar a los hilos que están esperando en fi_cq_sread o fi_cq_sreadfrom. Cuando se llama a fi_cq_signal, se genera una entrada de finalización en la cola de finalización, lo que puede hacer que las llamadas de espera a fi_cq_sread o fi_cq_sreadfrom se reanuden.

fi_cq_strerror

fi_cq_strerror convierte un error específico del proveedor en una cadena imprimible. El argumento prov_errno es el valor de error devuelto por el proveedor. El argumento err_data contiene datos de error adicionales específicos del proveedor. El argumento buf es un búfer donde se escribirá la cadena de error resultante, y len especifica la longitud del búfer.

Completion Queue Attributes

The following is a list of attributes that can be specified when creating a completion queue (CQ) via the fi_cq_open call. See fi_cq_open(3) for details on CQ creation.

wait_obj
Specifies the type of wait object associated with a CQ: FI_WAIT_NONE, FI_WAIT_UNSPEC, FI_WAIT_SET (deprecated), FI_WAIT_FD, FI_WAIT_MUTEX_COND (deprecated), and FI_WAIT_YIELD. The default is FI_WAIT_NONE.
- FI_WAIT_NONE
Used to indicate that the user will not block (wait) for completions on the CQ. When FI_WAIT_NONE is specified, the application may not call fi_cq_sread or fi_cq_sreadfrom.
- FI_WAIT_UNSPEC
Specifies that the user will only wait on the CQ using fabric interface calls, such as fi_cq_sread or fi_cq_sreadfrom. In this case, the underlying provider may select the most appropriate or highest performing wait object available, including custom wait mechanisms. Applications that select FI_WAIT_UNSPEC are not guaranteed to retrieve the underlying wait object.
- FI_WAIT_SET (deprecated)
Indicates that the completion queue should use a wait set object to wait for completions. If specified, the wait_set field must reference an existing wait set object.
- FI_WAIT_FD
Indicates that the CQ should use a file descriptor as its wait mechanism. A file descriptor wait object must be usable in select, poll, and epoll routines. However, a provider may signal an FD wait object by marking it as readable, writable, or with an error.
- FI_WAIT_MUTEX_COND (deprecated)
Specifies that the CQ should use a pthread mutex and cond variable as a wait object.
- FI_WAIT_YIELD
Indicates that the CQ will wait without a wait object but instead yield on every wait. Allows usage of fi_cq_sread and fi_cq_sreadfrom through a spin.
signaling_vector
If the FI_AFFINITY flag is set, this indicates the logical cpu number (0..max cpu - 1) that interrupts associated with the CQ should target. This field should be treated as a hint to the provider and may be ignored if the provider does not support interrupt affinity.
wait_cond
By default, when a completion is inserted into a CQ that supports blocking reads (fi_cq_sread/fi_cq_sreadfrom), the corresponding wait object is signaled. Users may specify a condition that must first be met before the wait is satisfied. This field indicates how the provider should interpret the cond field, which describes the condition needed to signal the wait object.

A wait condition should be treated as an optimization. Providers are not required to meet the requirements of the condition before signaling the wait object. Applications should not rely on the condition necessarily being true when a blocking read call returns.

If wait_cond is set to FI_CQ_COND_NONE, then no additional conditions are applied to the signaling of the CQ wait object, and the insertion of any new entry will trigger the wait condition. If wait_cond is set to FI_CQ_COND_THRESHOLD, then the cond field is interpreted as a size_t threshold value. The threshold indicates the number of entries that are to be queued before at the CQ before the wait is satisfied.

This field is ignored if wait_obj is set to FI_WAIT_NONE.

wait_set (deprecated)
If wait_obj is FI_WAIT_SET, this field references a wait object to which the completion queue should attach. When an event is inserted into the completion queue, the corresponding wait set will be signaled if all necessary conditions are met. The use of a wait_set enables an optimized method of waiting for events across multiple event and completion queues. This field is ignored if wait_obj is not FI_WAIT_SET.

fi_close

The fi_close call releases all resources associated with a completion queue. Any completions which remain on the CQ when it is closed are lost.

When closing the CQ, there must be no opened endpoints, transmit contexts, or receive contexts associated with the CQ. If resources are still associated with the CQ when attempting to close, the call will return -FI_EBUSY.

fi_control

The fi_control call is used to access provider or implementation specific details of the completion queue. Access to the CQ should be serialized across all calls when fi_control is invoked, as it may redirect the implementation of CQ operations. The following control commands are usable with a CQ.

FI_GETWAIT (void **)
This command allows the user to retrieve the low-level wait object associated with the CQ. The format of the wait-object is specified during CQ creation, through the CQ attributes. The fi_control arg parameter should be an address where a pointer to the returned wait object will be written. See fi_eq.3 for additional details using fi_control with FI_GETWAIT.

fi_cq_read

The fi_cq_read operation performs a non-blocking read of completion data from the CQ. The format of the completion event is determined using the fi_cq_format option that was specified when the CQ was opened. Multiple completions may be retrieved from a CQ in a single call. The maximum number of entries to return is limited to the specified count parameter, with the number of entries successfully read from the CQ returned by the call. (See return values section below.) A count value of 0 may be used to drive progress on associated endpoints when manual progress is enabled.

CQs are optimized to report operations which have completed successfully. Operations which fail are reported `out of band'. Such operations are retrieved using the fi_cq_readerr function. When an operation that has completed with an unexpected error is encountered, it is placed into a temporary error queue. Attempting to read from a CQ while an item is in the error queue results in fi_cq_read failing with a return code of -FI_EAVAIL. Applications may use this return code to determine when to call fi_cq_readerr.

fi_cq_readfrom

The fi_cq_readfrom call behaves identically to fi_cq_read, with the exception that it allows the CQ to return source address information to the user for any received data. Source address data is only available for those endpoints configured with FI_SOURCE capability. If fi_cq_readfrom is called on an endpoint for which source addressing data is not available, the source address will be set to FI_ADDR_NOTAVAIL. The number of input src_addr entries must be the same as the count parameter.

Returned source addressing data is converted from the native address used by the underlying fabric into an fi_addr_t, which may be used in transmit operations. Under most circumstances, returning fi_addr_t requires that the source address already have been inserted into the address vector associated with the receiving endpoint. This is true for address vectors of type FI_AV_TABLE. In select providers when FI_AV_MAP is used, source addresses may be converted algorithmically into a usable fi_addr_t, even though the source address has not been inserted into the address vector. This is permitted by the API, as it allows the provider to avoid address look-up as part of receive message processing. In no case do providers insert addresses into an AV separate from an application calling fi_av_insert or similar call.

For endpoints allocated using the FI_SOURCE_ERR capability, if the source address cannot be converted into a valid fi_addr_t value, fi_cq_readfrom will return -FI_EAVAIL, even if the data were received successfully. The completion will then be reported through fi_cq_readerr with error code -FI_EADDRNOTAVAIL. See fi_cq_readerr for details.

If FI_SOURCE is specified without FI_SOURCE_ERR, source addresses which cannot be mapped to a usable fi_addr_t will be reported as FI_ADDR_NOTAVAIL.

fi_cq_sread / fi_cq_sreadfrom

The fi_cq_sread and fi_cq_sreadfrom calls are the blocking equivalent operations to fi_cq_read and fi_cq_readfrom. Their behavior is similar to the non-blocking calls, with the exception that the calls will not return until either a completion has been read from the CQ or an error or timeout occurs.

Threads blocking in this function will return to the caller if they are signaled by some external source. This is true even if the timeout has not occurred or was specified as infinite.

It is invalid for applications to call these functions if the CQ has been configured with a wait object of FI_WAIT_NONE or FI_WAIT_SET.

fi_cq_readerr

The read error function, fi_cq_readerr, retrieves information regarding any asynchronous operation which has completed with an unexpected error. fi_cq_readerr is a non-blocking call, returning immediately whether an error completion was found or not.

Error information is reported to the user through struct fi_cq_err_entry. The format of this structure is defined below.

struct fi_cq_err_entry {
    void     *op_context; /* operation context */
    uint64_t flags;       /* completion flags */
    size_t   len;         /* size of received data */
    void     *buf;        /* receive data buffer */
    uint64_t data;        /* completion data */
    uint64_t tag;         /* message tag */
    size_t   olen;        /* overflow length */
    int      err;         /* positive error code */
    int      prov_errno;  /* provider error code */
    void    *err_data;    /*  error data */
    size_t   err_data_size; /* size of err_data */
    fi_addr_t src_addr; /* error source address */
};

The general reason for the error is provided through the err field. Provider specific error information may also be available through the prov_errno and err_data fields. Users may call fi_cq_strerror to convert provider specific error information into a printable string for debugging purposes. See field details below for more information on the use of err_data and err_data_size.

Note that error completions are generated for all operations, including those for which a completion was not requested (e.g., an endpoint is configured with FI_SELECTIVE_COMPLETION and an operation fails).

MANEJO DE COMPLETADOS

Los proveedores se comunican a través de los COMPLETIONs (finalizaciones) de las operaciones de red asíncronas. El objeto Completion Queue (CQ) proporciona una forma de recopilar y consultar finalizaciones. Los proveedores son responsables de colocar entradas en una CQ cuando una operación se completa o falla. Las finalizaciones pueden ser generadas por el nodo local o remoto de una operación. Las finalizaciones se comunican a la aplicación a través de la lectura de las entradas de la CQ.

Las aplicaciones pueden especificar la forma en que desean ser notificadas de las finalizaciones en el momento de la creación de la CQ. Por ejemplo, una aplicación puede solicitar que se genere un evento de señal o que se agregue una entrada en una lista enlazada de finalizaciones cuando una operación se completa. Las aplicaciones pueden desear ser notificadas sobre fallos de red. Las finalizaciones de error se generan cuando una operación no se completa con éxito. Los proveedores devolverán la mayor cantidad de información posible sobre la naturaleza del fallo.

Para las versiones de API 1.18 y posteriores, si una CQ se crea con la bandera FI_SELECTIVE_COMPLETION, se espera que solo se generen finalizaciones de error para los errores de las operaciones de red subyacentes. Si una operación se completa correctamente, no se generará una entrada de finalización para esa operación a menos que la CQ se haya creado con la bandera FI_COMPLETION. En tales casos, los proveedores devolverán tanta información como sea proporcionada por el software y hardware subyacente sobre el fallo; los demás campos se establecerán a NULL o 0. Esto incluye el valor op_context, que puede no haber sido proporcionado o fue ignorado en la entrada como parte de la transferencia.

A continuación, se indican los códigos de error de finalización notables.

FI_EADDRNOTAVAIL
Este código de error es utilizado por las CQ configuradas con FI_SOURCE_ERR para informar finalizaciones para las cuales no se pudo encontrar una dirección de origen fi_addr_t utilizable. Un código de error de FI_EADDRNOTAVAIL indica que la transferencia de datos se recibió y procesó correctamente, con los campos fi_cq_err_entry que contienen información sobre la finalización. El campo err_data se establecerá en los datos de la dirección de origen. La dirección de origen estará en el mismo formato que se especificó a través del campo addr_format de fi_info para el dominio abierto. Esto puede pasarse directamente a una llamada a fi_av_insert para agregar la dirección de origen al vector de direcciones.

Para las versiones de API 1.20 y posteriores, si el EP está configurado con FI_AV_AUTH_KEY, src_addr se establecerá en el identificador de la clave de autorización fi_addr_t o en un identificador de clave de autorización definido por el usuario correspondiente a la transferencia de datos entrante. De lo contrario, el valor se establecerá en FI_ADDR_NOTAVAIL.

fi_cq_signal

La llamada fi_cq_signal desbloqueará cualquier hilo que esté esperando en fi_cq_sread o fi_cq_sreadfrom. Esto se puede utilizar para despertar a un hilo que está bloqueado esperando leer una operación de finalización. La operación fi_cq_signal solo está disponible si la CQ fue configurada con un objeto de espera.

CAMPOS DE FINALIZACIÓN

Las estructuras de datos de entrada de la CQ comparten muchos de los mismos campos. Los significados de estos campos son los mismos para todos los formatos de estructura de entrada de la CQ.

op_context
El contexto de la operación es el valor de contexto especificado por la aplicación que se proporcionó con una operación asíncrona. El campo op_context es válido para todas las finalizaciones que están asociadas con una operación asíncrona.

Para eventos de finalización que no están asociados con una operación publicada, este campo se establecerá en NULL. Esto incluye las finalizaciones generadas en el destino en respuesta a operaciones de escritura RMA que transportan datos de CQ (banderas FI_REMOTE_WRITE | FI_REMOTE_CQ_DATA establecidas), cuando el bit de modo FI_RX_CQ_DATA no es requerido.

flags
Esto especifica las banderas asociadas con la operación completada. La sección Banderas de Finalización a continuación enumera los valores de banderas válidos. Las banderas se establecen para todas las finalizaciones relevantes.
len
Este campo len se aplica a las operaciones de recepción completadas (por ejemplo, fi_recv, fi_trecv, etc.) y a la escritura completada con datos de CQ remotos en el lado del respondedor (por ejemplo, fi_write, con la bandera FI_REMOTE_CQ_DATA). Indica el tamaño de los datos del *mensaje* transferido, es decir, cuántos bytes de datos se colocaron en el búfer de recepción/destino asociado por una llamada fi_send/fi_tsend/fi_write et al correspondiente. Si un endpoint se ha configurado con el modo FI_MSG_PREFIX, len también refleja el tamaño del búfer de prefijo.
buf
El campo buf solo es válido para operaciones de recepción completadas, y solo se aplica cuando el búfer de recepción se publicó con la bandera FI_MULTI_RECV. En este caso, buf apunta a la ubicación de inicio donde se colocaron los datos de recepción.
data
El campo data solo es válido si la bandera de finalización FI_REMOTE_CQ_DATA está establecida, y solo se aplica a las finalizaciones de recepción. Si se establece FI_REMOTE_CQ_DATA, este campo contendrá los datos de finalización proporcionados por el par como parte de su solicitud de transmisión. Los datos de finalización se proporcionarán en orden de bytes del host.
tag
Una etiqueta se aplica solo a los mensajes recibidos que ocurren usando las interfaces etiquetadas. Este campo contiene la etiqueta que se incluyó con el mensaje recibido. La etiqueta estará en orden de bytes del host.
olen
El campo olen se aplica a los mensajes recibidos. Se utiliza para indicar que un mensaje recibido ha excedido el espacio disponible del búfer y ha sido truncado. olen especifica la cantidad de datos que no cabían en el búfer de recepción disponible y que fueron descartados.
err
Este código de error err es un errno de tejido positivo asociado con una finalización. El valor de err indica la razón general de un error, si ocurrió alguno. Consulte fi_errno.3 para una lista de posibles códigos de error.
prov_errno
En caso de error, prov_errno puede contener un código de error específico del proveedor. El uso de este campo y su significado es específico del proveedor. Está destinado a ser utilizado como ayuda para la depuración. Consulte fi_cq_strerror para obtener información adicional sobre cómo convertir este valor de error en una cadena legible por humanos.
err_data
El campo err_data se utiliza para devolver información específica del proveedor, si está disponible, sobre el error. En la entrada, err_data debe hacer referencia a un búfer de datos de tamaño err_data_size. En la salida, el proveedor llenará este búfer con cualquier dato específico del proveedor que pueda ayudar a identificar la causa del error. El contenido del campo err_data y su significado es específico del proveedor. Está destinado a ser utilizado como ayuda para la depuración. Consulte fi_cq_strerror para obtener información adicional sobre cómo convertir estos datos de error en una cadena legible por humanos. Consulte la nota de compatibilidad a continuación sobre cómo se utiliza este campo para versiones anteriores de libfabric.
err_data_size
En la entrada, err_data_size indica el tamaño del búfer err_data en bytes. En la salida, err_data_size se establecerá en el número de bytes copiados al búfer err_data. La información de err_data se utiliza típicamente con fi_cq_strerror para proporcionar detalles sobre el tipo de error que ocurrió.

Por motivos de compatibilidad, el comportamiento de los campos err_data y err_data_size puede modificarse con respecto a lo indicado anteriormente. Si err_data_size es 0 en la entrada, o si el tejido se abrió con una versión < < 1.5, entonces se ignorará cualquier búfer referenciado por err_data en la entrada. En esta situación, en la salida err_data se establecerá en un búfer de datos propiedad del proveedor. El contenido del búfer seguirá siendo válido hasta que una llamada de lectura posterior contra la CQ. Las aplicaciones deben serializar el acceso a la CQ al procesar errores para garantizar que el búfer referenciado por err_data no cambie.

src_addr
Se utiliza para devolver información relacionada con la dirección de origen para eventos de error. Cómo se utiliza este campo depende del evento de error.

BANDERA DE FINALIZACIÓN

Las banderas de finalización proporcionan detalles adicionales sobre la operación completada. Se definen las siguientes banderas de finalización.

FI_SEND
Indica que la finalización fue para una operación de envío. Esta bandera puede combinarse con una bandera FI_MSG o FI_TAGGED.
FI_RECV
Indica que la finalización fue para una operación de recepción. Esta bandera puede combinarse con una bandera FI_MSG o FI_TAGGED.
FI_RMA
Indica que una operación RMA se completó. Esta bandera puede combinarse con una bandera FI_READ, FI_WRITE, FI_REMOTE_READ o FI_REMOTE_WRITE.
FI_ATOMIC
Indica que una operación atómica se completó. Esta bandera puede combinarse con una bandera FI_READ, FI_WRITE, FI_REMOTE_READ o FI_REMOTE_WRITE.
FI_MSG
Indica que una operación basada en mensajes se completó. Esta bandera puede combinarse con una bandera FI_SEND o FI_RECV.
FI_TAGGED
Indica que una operación de mensaje etiquetado se completó. Esta bandera puede combinarse con una bandera FI_SEND o FI_RECV.
FI_MULTICAST
Indica que una operación de multidifusión se completó. Esta bandera puede combinarse con FI_MSG y banderas relevantes. Esta bandera solo se garantiza que sea válida para mensajes recibidos si el endpoint se ha configurado con FI_SOURCE.
FI_READ
Indica que una operación de lectura RMA o atómica iniciada localmente se ha completado. Esta bandera puede combinarse con una bandera FI_RMA o FI_ATOMIC.
FI_WRITE
Indica que una operación de escritura RMA o atómica iniciada localmente se ha completado. Esta bandera puede combinarse con una bandera FI_RMA o FI_ATOMIC.
FI_REMOTE_READ
Indica que una operación de lectura RMA o atómica iniciada remotamente se ha completado. Esta bandera puede combinarse con una bandera FI_RMA o FI_ATOMIC.
FI_REMOTE_WRITE
Indica que una operación de escritura RMA o atómica iniciada remotamente se ha completado. Esta bandera puede combinarse con una bandera FI_RMA o FI_ATOMIC.
FI_REMOTE_CQ_DATA
Esto indica que los datos de CQ remotos están disponibles como parte de la finalización.
FI_MULTI_RECV
Esta bandera se aplica a los búferes de recepción que se publicaron con la bandera FI_MULTI_RECV establecida. Esta bandera de finalización indica que el búfer de recepción original referenciado por la finalización ha sido consumido y liberado por el proveedor. Los proveedores pueden establecer esta bandera en el último mensaje que se recibe en el búfer de recepción múltiple, o pueden generar una finalización separada que indique que el búfer ha sido liberado.

Las aplicaciones pueden distinguir entre estos dos casos examinando el campo de banderas de la entrada de finalización. Si se establecen banderas adicionales, como FI_RECV, la finalización se asocia con un mensaje recibido. En este cas

e, el campo `buf` hará referencia a la ubicación donde se colocó el mensaje recibido en el búfer de recepción múltiple. Los demás campos

de la entrada de finalización se determinarán en función del mensaje recibido. Si los demás bits de indicador son cero, el proveedor está
informando de que el búfer de recepción múltiple ha sido liberado y la entrada de finalización no está asociada con un mensaje recibido.

SEMÁNTICA DE EVENTOS DE

FINALIZACIÓN

Libfabric define varios `niveles' de finalización, identificados mediante indicadores operativos. Cada indicador indica el momento más temprano en que un proveedor puede generar un evento de finalización y las suposiciones que una aplicación puede hacer al procesar una finalización. Los indicadores operativos se definen a continuación, junto con un ejemplo de cómo un proveedor podría implementar la semántica. Nótese que solo se requiere que el proveedor cumpla la semántica, no la implementación. Los proveedores pueden implementar semánticas de finalización más fuertes de las necesarias para una operación determinada, pero solo se garantiza el comportamiento definido por el nivel de

finalización.

Para ayudar a comprender las diferencias conceptuales entre los niveles de finalización, considere el envío de una carta. Colocar la carta en el buzón local para su recogida es similar a `completado por inyección'. Tener la carta recogida y depositada en el buzón de destino es equivalente a `completado en transmisión'. La semántica `completado en entrega' es una garantía más fuerte, con una persona en el destino firmando la recepción de la carta. Sin embargo, la persona que firma la recepción de la carta no es necesariamente el destinatario previsto. La opción `completado en coincidencia' es similar a completado en entrega, pero requiere que el destinatario previsto firme la recepción de la

carta.

El nivel `completado en compromiso' tiene una semántica diferente a la de los niveles mencionados anteriormente. Completado en compromiso estaría más cerca de la carta llegando al destino y siendo colocada en una caja fuerte a prueba de

fuego.

Los indicadores operativos para los niveles de finalización descritos se definen a

continuación.
FI_INJECT_COMPL
ETE
Indica que se debe generar una finalización cuando el(los) búfer(es) de origen pueda(n) ser re
utilizado(s). Una finalización garantiza que no se volverá a leer de los búferes y que la apl
icación puede reclamarlos. No se hacen otras garantías con respecto al estado de la operación.

Ejemplo: Un proveedor puede generar este evento de finalización después de copiar el búfer de origen en un búfer de red, ya sea en memoria del host o en la NIC. Una finalización por inyección no indica que los datos hayan sido transmitidos a la red, y un error local podría ocurrir después de que se haya generado el evento de finalización, lo que podría impedir que se

transmita.

La finalización por inyección permite la notificación de finalización más rápida (y, por lo tanto, la reutilización del búfer), pero proporciona las garantías más débiles contra los errores de

red.

Nota: Este indicador se utiliza para controlar cuándo se inserta una entrada de finalización en una cola de finalización. No se aplica a operaciones que no generan una entrada en la cola de finalización, como la operación `fi_inject`, y no está sujeta a la restricción del límite de mensaje

`inject_size`.
FI_TRANSMIT_COMPL
ETE
Indica que se debe generar una finalización cuando la operación
de transmisión se haya completado con respecto al proveedor local
. El comportamiento exacto depende del tipo de punto de extremo.

Para puntos de extremo

fiables:

Indica que se debe generar una finalización cuando la operación haya sido entregada al punto de extremo par. Una finalización garantiza que la operación ya no depende de la red o de los recursos locales. El estado de la operación en el punto de extremo par no está

definido.

Ejemplo: Un proveedor puede generar un evento de finalización en transmisión al recibir una confirmación (ack) del punto de extremo par. El estado del mensaje en el par es desconocido y puede estar almacenado en el búfer en la NIC de destino en el momento en que se genera la

confirmación.

Para puntos de extremo no

fiables:

Indica que se debe generar una finalización cuando la operación haya sido entregada a la red. Una finalización garantiza que la operación ya no depende de los recursos locales. El estado de la operación dentro de la red no está

definido.
FI_DELIVERY_COMPL
ETE
Indica que no se debe generar una finalización hasta que una operación haya sido procesada por el(los) punto(s) de extremo de destino. Una finalización gar
antiza que el resultado de la operación está disponible; sin embargo, podrían ser necesarios pasos adicionales en el destino para recuperar los resultados.
Por ejemplo, una aplicación podría necesitar proporcionar búferes de recepción para recuperar mensajes que fueron almacenados en el búfer por el proveedor.

La finalización en entrega indica que el mensaje ha sido procesado por el par. Si un búfer de la aplicación estaba listo para recibir los resultados del mensaje cuando este llegó, entonces la finalización en entrega indica que los datos fueron colocados en el búfer de la

aplicación.

Este modo de finalización se aplica solo a puntos de extremo fiables. Para operaciones que devuelven datos al iniciador, como una lectura RMA o un `atomic-fetch`, el punto de extremo de origen también se considera un punto de extremo de destino. Este es el modo de finalización predeterminado para tales

operaciones.
FI_MATCH_COMPL
ETE
Indica que se debe generar una finalización solo después de que la operación haya sido emparejada con un búfer especificado por la aplicación. Las operaciones que utilizan esta semántica de finalización dependen de que la aplicación en el destino reclame el mensaje o los resultados. Como resultado, la finalización en coincidencia puede implicar confirmaciones adicionales a nivel de proveedor o largas demoras. Sin embargo, este modelo de finalización permite a las aplicaciones pares sincronizar su ejecución. Muchos proveedores pueden no soportar esta
semántica.
FI_COMMIT_COMPL
ETE
Indica que no se debe generar una finalización (localmente o en el par) hasta que e
l resultado de una operación se haya hecho persistente. Una finalización garantiza
que el resultado está tanto disponible como duradero, en caso de fallo de energía.

Este modo de finalización se aplica solo a operaciones que apuntan a regiones de memoria persistente sobre puntos de extremo fiables. Este modo de finalización es

experimental.
FI_FEN
CE
Este no es un nivel de finalización, pero juega un papel en el orden de finalización entre operaciones que normalmente no estarían ordenadas. Una operación marcada con el indicador FI_FENCE y todas las operaciones publicadas después de la operación cercada se difieren hasta que todas las operaciones anteriores que apuntan al mismo punto de extremo par se hayan completado. Además, la finalización de la operación cercada indica que las operaciones anteriores han alcanzado el mismo nivel de finalización que la operación cercada. Por ejemplo, si una operación se publica como FI_DELIVERY_COMPLETE | FI_FENCE, entonces su finalización indica que las operaciones anteriores han cumplido la semántica requerida para FI_DELIVERY_COMPLETE. Esto es cierto incluso si la operación anterior se publicó con un nivel de finalización más bajo, como FI_TRANSMIT_COMPLETE o FI_INJECT_COMPLET
E
.

Nótese que una finalización generada para una operación publicada antes de la operación cercada solo garantiza que se ha cumplido el nivel de finalización que se solicitó originalmente. Es la finalización de la operación cercada la que garantiza que se han cumplido las semánticas

adicionales.

Las semánticas de finalización anteriores se definen con respecto al iniciador de la operación. Las diferentes semánticas son útiles par

a describir cuándo el iniciador puede reutilizar un búfer de datos, y garantizan qué estado debe alcanzar una transferencia antes de que
se genere una finalización. Esto permite a las aplicaciones determinar el manejo de errores apropiado en caso de fallos de comunicación.

SEMÁNTICA DE FINALIZACIÓN EN EL

DESTINO

La semántica de finalización en el destino se utiliza para determinar cuándo los datos en el destino son visibles para la aplicación par. La visibilidad indica que una lectura de memoria en la misma dirección que fue el destino de una transferencia de datos devolverá los resultados de la transferencia. El destino de una transferencia puede ser identificado por el iniciador, como puede ser el caso para operaciones RMA y atómicas, o determinado por el destino, por ejemplo, al proporcionar un búfer de recepción coincidente. La visibilidad global indica que los resultados están disponibles independientemente de dónde se origine la lectura de memoria. Por ejemplo, la lectura podría provenir de un proceso que se ejecuta en una CPU del host, podría ser accedida por una transferencia de datos posterior a través de la red, o leída desde un dispositivo par como una

GPU.

En términos de semántica de finalización, la visibilidad usualmente indica que la transferencia cumple los requisitos de FI_DELIVERY_COMPLETE desde la perspectiva del destino. La semántica de finalización en el destino puede estar, pero no necesariamente está, vinculada con la semántica de finalización especificada por el iniciador de la

transferencia.

A menudo, los procesos de destino no declaran explícitamente una semántica de finalización deseada y en su lugar dependen de la semántica predeterminada. El comportamiento predeterminado se basa en varios factores,

incluyendo:

el tipo de transferencia involucrada (por ejemplo, msg vs
RMA)

En términos generales, las semánticas de finalización en el destino se agrupan en función de si la transferencia genera o no un evento de finalización en el destino. Esto incluye escribir una entrada en la CQ (cola de finalización) o actualizar un contador de finalización. En los casos de uso comunes, las transferencias que utilizan una interfaz de mensaje (FI_MSG o FI_TAGGED) típicamente generan eventos en el destino, mientras que las transferencias que involucran una interfaz RMA (FI_RMA o FI_ATOMIC) a menudo no lo hacen. Hay excepciones a ambos casos, dependiendo de los enlaces de punto de extremo a CQ y contadores, y de los indicadores operativos. Por ejemplo, las escrituras RMA que llevan datos de CQ remotos generarán un evento de finalización en el destino, y se usan frecuentemente para transmitir visibilidad a la aplicación de destino. Las pautas generales para la semántica en el lado del destino se describen a continuación, seguidas de excepciones que modifican ese

comportamiento.

Por defecto, las finalizaciones generadas en el destino indican que los datos transferidos están inmediatamente disponibles para ser leídos desde el búfer de destino. Es decir, el destino ve semánticas de FI_DELIVERY_COMPLETE (o mejores), incluso si el iniciador solicitó semánticas más bajas. Para aplicaciones que usan solo búferes de datos asignados desde la memoria del host, esto a menudo es

suficiente. >Para operaciones que no generan un evento de finalización en el destino, la visibilidad de los datos en el destino puede necesitar ser inferida basándose en operaciones subsiguientes que sí generan finalizaciones de destino. En ausencia de una finalización de destino, cuando una finalización de una operación se escribe en el iniciador, la semántica de visibilidad de la operación en el destino se alinea con la semántica de finalización del iniciador. Por ejemplo, si una operación RMA se completa en el iniciador como FI_INJECT_COMPLETE o FI_TRANSMIT_COMPLETE, la visibilidad de los datos en el destino no está garantizada.

Uno o más de los siguientes mecanismos pueden ser utilizados por el proceso de destino para garantizar que los resultados de una transferencia de datos que no generó una finalización en el destino ahora sean visibles. Esta lista no incluye todas las opciones, pero define usos comunes. En las descripciones a continuación, la primera transferencia no resulta en un evento de finalización en el destino, pero eventualmente es seguida por una transferencia que sí lo hace.

•
Si el endpoint garantiza el orden de los mensajes entre dos transferencias, la finalización de destino de una segunda transferencia indicará que los datos de la primera transferencia están disponibles. Por ejemplo, si el endpoint soporta el orden de escritura después de envío (FI_ORDER_SAW), entonces una finalización de recepción correspondiente al envío indicará que los datos de escritura están disponibles. Esto se mantiene independientemente de la semántica de finalización del iniciador para la escritura o el envío. Cuando el orden está garantizado, la segunda transferencia puede ser encolada con el proveedor inmediatamente después de encolar la primera.
•
Si el endpoint no garantiza el orden de los mensajes, el iniciador debe tomar medidas adicionales para asegurar la visibilidad. Si el iniciador solicita las semánticas FI_DELIVERY_COMPLETE para la primera operación, el iniciador puede esperar a que la operación se complete localmente. Una vez que se ha leído la finalización, la finalización de destino de una segunda transferencia indicará que los datos de la primera transferencia son visibles.
•
Alternativamente, si el endpoint no garantiza el orden de los mensajes, el iniciador puede usar las banderas FI_FENCE y FI_DELIVERY_COMPLETE en la segunda transferencia de datos para forzar que las primeras transferencias cumplan con las semánticas FI_DELIVERY_COMPLETE. Si la segunda transferencia genera una finalización en el destino, eso indicará que los datos son visibles. De lo contrario, una finalización de destino para cualquier transferencia después de la operación cercada indicará que los datos son visibles.

Las semánticas anteriores se aplican a transferencias dirigidas a búferes de memoria de host tradicionales. Sin embargo, el comportamiento puede diferir cuando se involucran memorias de dispositivo y/o memorias persistentes (bits de capacidad FI_HMEM y FI_PMEM). Cuando se involucran memorias heterogéneas, entra en juego el concepto de dominios de memoria. Los dominios de memoria identifican la separación física de la memoria, que puede o no ser accesible a través del mismo espacio de direcciones virtual. Consulte la página del manual fi_mr(3) para obtener más detalles sobre los dominios de memoria.

El orden de finalización y la visibilidad de los datos solo están bien definidos para las transferencias que se dirigen al mismo dominio de memoria. Las aplicaciones deben tener en cuenta las diferencias de ordenación y visibilidad cuando las transferencias se dirigen a diferentes dominios de memoria. Además, las aplicaciones también deben preocuparse por el dominio de memoria en el que se escriben las propias finalizaciones y si difiere del dominio de memoria al que se dirige una transferencia. En algunas situaciones, el proveedor o la aplicación pueden necesitar llamar a APIs específicas del dispositivo para sincronizar o vaciar las cachés de memoria del dispositivo con el fin de lograr la visibilidad de datos deseada.

Cuando se utiliza memoria heterogénea, la semántica de finalización de destino predeterminada para las transferencias que generan una finalización en el destino sigue siendo FI_DELIVERY_COMPLETE, sin embargo, las aplicaciones deben ser conscientes de que puede haber un impacto negativo en el rendimiento general para que los proveedores cumplan con este requisito.

Por ejemplo, un proceso de destino puede estar utilizando una GPU para acelerar cálculos. Una región de memoria que se mapea a memoria en la GPU puede exponerse a los pares como un destino RMA o publicarse localmente como un búfer de recepción. En este caso, la aplicación está preocupada por dos dominios de memoria: memoria del sistema y memoria de la GPU. Las finalizaciones se escriben en la memoria del sistema.

Continuando con el ejemplo, un proceso par envía un mensaje etiquetado. Ese mensaje se empareja con el búfer de recepción ubicado en la memoria de la GPU. La tarjeta de red copia los datos de la red al búfer de recepción y escribe una entrada en la cola de finalización. Tenga en cuenta que ambos dominios de memoria fueron accedidos como parte de esta transferencia. Los datos del mensaje se dirigieron a la memoria de la GPU, pero la finalización fue a la memoria del host. Debido a que los dominios de memoria separados pueden no estar sincronizados entre sí, es posible que la CPU del host vea y procese la entrada de finalización antes de que la transferencia a la memoria de la GPU sea visible para el host de la GPU o incluso para el software que se ejecuta en la GPU. Desde la perspectiva del *proveedor*, la visibilidad de la finalización no implica la visibilidad de los datos escritos en el dominio de memoria de la GPU.

La semántica de finalización predeterminada en la *aplicación* de destino para las operaciones de mensajes es FI_DELIVERY_COMPLETE. Una implementación prevista del proveedor en esta situación es que el software del proveedor que se ejecuta en la CPU del host intercepte la entrada de la CQ, detecte que los datos aterrizaron en memoria heterogénea y realice la sincronización del dispositivo o la operación de vaciado necesaria antes de informar la finalización a la aplicación. Esto asegura que los datos sean visibles para el software de la CPU *y* de la GPU antes de que la aplicación procese la finalización.

Además del costo del software del proveedor que intercepte las finalizaciones y verifique si una transferencia se dirigió a memoria heterogénea, la sincronización del dispositivo en sí misma puede afectar el rendimiento. Como resultado, las aplicaciones pueden solicitar una semántica de finalización menor al publicar recepciones. Esto indica al proveedor que la aplicación será responsable de manejar cualquier operación de vaciado específica del dispositivo que pueda ser necesaria. Consulte fi_msg(3) FLAGS.

Para transferencias de datos que no generan una finalización en el destino, como RMA o atómicos, es responsabilidad de la aplicación asegurar que todos los búferes de destino cumplan los requisitos de visibilidad necesarios de la aplicación. Los métodos mencionados anteriormente para notificar al destino que los datos son visibles pueden no ser suficientes, ya que el software del proveedor en el destino podría carecer del contexto necesario para garantizar la visibilidad. Esto implica que la aplicación puede necesitar llamar directamente a las APIs de sincronización/vaciado del dispositivo.

Por ejemplo, una aplicación par podría realizar varias escrituras RMA que se dirigen a búferes de memoria de GPU. Si el proveedor descarga las operaciones RMA en la NIC, el software del proveedor en el destino no será consciente de que las operaciones RMA han ocurrido. Si el par envía un mensaje a la aplicación de destino que indica que las operaciones RMA han finalizado, la aplicación debe asegurarse de que los datos RMA sean visibles para la CPU del host o la GPU antes de ejecutar código que acceda a los datos. La finalización de destino de haber recibido el mensaje enviado no es suficiente, incluso si se soporta el orden envío-después-de-escritura.

La mayoría de las semánticas de finalización de memoria heterogénea de destino se mapean a FI_TRANSMIT_COMPLETE o FI_DELIVERY_COMPLETE. La memoria persistente (capacidad FI_PMEM), sin embargo, a menudo se utiliza con semánticas FI_COMMIT_COMPLETE. Los conceptos de finalización heterogénea todavía se aplican.

Para las transferencias marcadas por el iniciador con FI_COMMIT_COMPLETE, una finalización en el destino indica que los resultados son visibles y duraderos. Para las transferencias dirigidas a memoria persistente, pero utilizando una semántica de finalización diferente en el iniciador, la visibilidad en el destino es similar a la descrita anteriormente. La durabilidad solo se asocia con las transferencias marcadas con FI_COMMIT_COMPLETE.

Para las transferencias dirigidas a memoria persistente que solicitan FI_DELIVERY_COMPLETE, entonces una finalización, ya sea en el iniciador o en el destino, indica que los datos son visibles. La visibilidad en el destino se puede transmitir utilizando uno de los mecanismos descritos anteriormente: generar una finalización de destino, enviar un mensaje desde el iniciador, etc. De manera similar, si el iniciador solicitó FI_TRANSMIT_COMPLETE, entonces se necesitan pasos adicionales para garantizar la visibilidad en el destino. Por ejemplo, la transferencia puede generar una finalización en el destino, lo que indicaría visibilidad, pero no durabilidad. El iniciador también puede seguir la transferencia con otra operación que fuerce la visibilidad, como usar FI_FENCE en conjunto con FI_DELIVERY_COMPLETE.

NOTAS

Una cola de finalización debe estar enlazada a al menos un endpoint habilitado antes de que se pueda llamar a cualquier operación como fi_cq_read, fi_cq_readfrom, fi_cq_sread, fi_cq_sreadfrom, etc. sobre ella.

Si una cola de finalización ha sido sobrescrita, se colocará en un estado de 'sobrescrito'. Las operaciones de lectura continuarán devolviendo cualquier finalización válida y no corrupta, si está disponible. Después de recuperar todas las finalizaciones válidas, cualquier intento de leer la CQ resultará en la devolución de un evento de error FI_EOVERRUN. Las colas de finalización sobrescritas se consideran fatales y no pueden usarse para reportar finalizaciones adicionales una vez que ocurre la sobrescritura.

VALORES DE RETORNO

fi_cq_open / fi_cq_signal

: Devuelve 0 si tiene éxito. En caso de error, devuelve un errno de tejido negativo.

fi_cq_read / fi_cq_readfrom

: En caso de éxito, devuelve el número de finalizaciones recuperadas de la cola de finalización. En caso de error, devuelve un errno de tejido negativo, con estos dos errores identificados explícitamente: Si no hay finalizaciones disponibles para leer de la CQ, devuelve -FI_EAGAIN. Si la finalización superior es para una transferencia fallida (una entrada de error), devuelve -FI_EAVAIL.

fi_cq_sread / fi_cq_sreadfrom

: En caso de éxito, devuelve el número de finalizaciones recuperadas de la cola de finalización. En caso de error, devuelve un errno de tejido negativo, con estos dos errores identificados explícitamente: Si se agota el tiempo de espera o el hilo de llamada se señala y no hay datos disponibles para leer de la cola de finalización, devuelve -FI_EAGAIN. Si la finalización superior es para una transferencia fallida (una entrada de error), devuelve -FI_EAVAIL.

fi_cq_readerr

: En caso de éxito, devuelve el valor positivo 1 (número de entradas de error devueltas). En caso de error, devuelve un errno de tejido negativo, con este error identificado explícitamente: Si no hay finalizaciones de error disponibles para leer de la CQ, devuelve -FI_EAGAIN.

fi_cq_strerror

: Devuelve una interpretación en forma de cadena de caracteres del proveedor

VALORES DE RETORNO

Devuelve 0 con éxito. En caso de error, devuelve un código de error negativo que especifica el motivo del fallo.

Los valores de errno de Fabric se definen en rdma/fi_errno.h.
