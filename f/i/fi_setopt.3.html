DESCRIPCIÓN

Los puntos de extremo son portales de comunicación a nivel de transporte. Hay dos tipos de puntos de extremo: activos y pasivos. Los puntos de extremo pasivos pertenecen a un dominio de fabric y se usan con mayor frecuencia para escuchar solicitudes de conexión entrantes. Sin embargo, un punto de extremo pasivo puede usarse para reservar una dirección de fabric que pueda concederse a un punto de extremo activo. Los puntos de extremo activos pertenecen a dominios de acceso y pueden realizar transferencias de datos.

Los puntos de extremo activos pueden ser orientados a conexión o sin conexión, y pueden proporcionar fiabilidad de datos. Las interfaces de transferencia de datos – mensajes (fi_msg), mensajes etiquetados (fi_tagged), RMA (fi_rma) y operaciones atómicas (fi_atomic) – están asociadas con puntos de extremo activos. En configuraciones básicas, un punto de extremo activo tiene colas de transmisión y recepción. En general, las operaciones que generan tráfico en la fabric se publican en la cola de transmisión. Esto incluye todas las operaciones RMA y atómicas, junto con los mensajes enviados y los mensajes etiquetados enviados. Las operaciones que publican búferes para recibir datos entrantes se envían a la cola de recepción.

Los puntos de extremo activos se crean en estado deshabilitado. Deben transicionar a un estado habilitado antes de aceptar operaciones de transferencia de datos, incluida la publicación de búferes de recepción. La llamada fi_enable se usa para transicionar un punto de extremo activo a un estado habilitado. Las llamadas fi_connect y fi_accept también transicionarán un punto de extremo al estado habilitado, si aún no está activo.

Para transicionar un punto de extremo a un estado habilitado, debe enlazarse con uno o más recursos de fabric. Un punto de extremo que generará finalizaciones asíncronas, ya sea a través de operaciones de transferencia de datos o eventos de establecimiento de comunicación, debe enlazarse con las colas de finalización o colas de eventos apropiadas, respectivamente, antes de ser habilitado. Además, los puntos de extremo que usan progreso manual deben asociarse con colas de finalización o colas de eventos relevantes para impulsar el progreso. Para los puntos de extremo que solo se usan como destino de operaciones RMA o atómicas, esto significa enlazar el punto de extremo con una cola de finalización asociada con el procesamiento de recepción. Los puntos de extremo sin conexión deben enlazarse con un vector de direcciones.

Una vez que un punto de extremo ha sido activado, puede asociarse con un vector de direcciones. Se le pueden publicar búferes de recepción y se pueden realizar llamadas a rutinas de establecimiento de conexión. Los puntos de extremo sin conexión también pueden realizar transferencias de datos.

El comportamiento de un punto de extremo puede ajustarse estableciendo sus datos de control y opciones de protocolo. Esto permite que el proveedor subyacente redirija las llamadas a funciones a implementaciones optimizadas para satisfacer el comportamiento deseado de la aplicación.

Si un punto de extremo experimenta un error crítico, transicionará de vuelta a un estado deshabilitado. Los errores críticos se reportan a través de la cola de eventos asociada con el EP. En ciertos casos, un punto de extremo deshabilitado puede volver a habilitarse. La capacidad de transicionar de vuelta a un estado habilitado es específica del proveedor y depende del tipo de error que experimentó el punto de extremo. Cuando un endpoint se deshabilita como resultado de un error crítico, se descartan todas las operaciones pendientes.

fi_endpoint / fi_passive_ep / fi_scalable_ep

fi_endpoint asigna un nuevo endpoint activo. fi_passive_ep asigna un nuevo endpoint pasivo. fi_scalable_ep asigna un endpoint escalable. Las propiedades y el comportamiento del endpoint se definen en base a la estructura fi_info proporcionada. Consulte fi_getinfo para obtener detalles adicionales sobre fi_info. Las banderas de fi_info que controlan la operación de un endpoint se definen a continuación. Consulte la sección ENDPOINTS ESCALABLES.

Si se asigna un endpoint activo para aceptar una solicitud de conexión, el parámetro fi_info debe ser la misma estructura fi_info proporcionada con el evento de solicitud de conexión (FI_CONNREQ).

Un endpoint activo puede adquirir las propiedades de un endpoint pasivo estableciendo el campo de descriptor de fabric del manejador de fi_info al endpoint pasivo. Esto es útil para aplicaciones que necesitan reservar la dirección de fabric de un endpoint antes de saber si el endpoint se utilizará en el lado activo o pasivo de una conexión. Por ejemplo, esta característica es útil para simular la semántica de sockets. Una vez que un endpoint activo adquiere las propiedades de un endpoint pasivo, el endpoint pasivo ya no está enlazado a ningún recurso de fabric y no debe volver a utilizarse. Se espera que el usuario cierre el endpoint pasivo después de abrir el endpoint activo para liberar cualquier recurso remanente que se hubiera utilizado.

fi_endpoint2

Similar a fi_endpoint, acepta un parámetro adicional flags. Se utiliza principalmente para abrir endpoints que utilizan la característica de transferencia entre pares. Consulte fi_peer(3)

fi_close

Cierra un endpoint y libera todos los recursos asociados con él.

Al cerrar un endpoint escalable, no debe haber contextos de transmisión ni contextos de recepción abiertos asociados con el endpoint escalable. Si todavía hay recursos asociados con el endpoint escalable al intentar cerrarlo, la llamada devolverá -FI_EBUSY.

Las operaciones pendientes publicadas en el endpoint cuando se llama a fi_close serán descartadas. Las operaciones descartadas serán ignoradas silenciosamente, sin informes de finalización. Los buffers de memoria que el usuario asoció con el endpoint llamando a las interfaces de transmisión de libfabric no deben liberarse, desregistrarse ni reutilizarse hasta que se genere una finalización o se devuelva fi_close en el endpoint respectivo. Además, un proveedor puede descartar operaciones previamente completadas de la(s) cola(s) de finalización asociada(s). El comportamiento de descartar operaciones completadas es específico del proveedor.

fi_ep_bind

fi_ep_bind se utiliza para asociar un endpoint con otros recursos asignados, como colas de finalización, contadores, vectores de direcciones, colas de eventos y regiones de memoria. El tipo de objetos que deben enlazarse con un endpoint depende del tipo de endpoint y su configuración.

Los endpoints pasivos deben enlazarse con una EQ que admita eventos de gestión de conexiones. Los endpoints sin conexión deben enlazarse a un único vector de direcciones. Si un endpoint está utilizando un contexto de transmisión y/o recepción compartido, los contextos compartidos deben enlazarse al endpoint. Las CQs, los contadores, los AV y los contextos compartidos deben enlazarse a los endpoints antes de que se habiliten, ya sea explícita o implícitamente.

Un endpoint debe enlazarse con CQs capaces de informar las finalizaciones de cualquier operación asíncrona iniciada en el endpoint. Por ejemplo, si el endpoint admite transferencias de salida (envíos, RMA, atómicas, etc.), entonces debe enlazarse a una cola de finalización que pueda informar las finalizaciones de transmisión. Esto es cierto incluso si el endpoint está configurado para suprimir finalizaciones exitosas, para que las operaciones que se completan con errores puedan informarse al usuario.

Un endpoint activo puede dirigir finalizaciones asíncronas a diferentes CQs, según el tipo de operación. Esto se especifica utilizando banderas de fi_ep_bind. Las siguientes banderas pueden combinarse (|) al enlazar un endpoint a una CQ de dominio de finalización.

FI_RECV
Dirige la notificación de transferencias de datos entrantes a la cola de finalización especificada. Esto incluye mensajes recibidos. Este enlace incluye automáticamente FI_REMOTE_WRITE, si es aplicable al endpoint.
FI_SELECTIVE_COMPLETION
Por defecto, las operaciones de transferencia de datos escriben entradas de finalización de CQ en la cola de finalización asociada después de que se hayan completado con éxito. Las aplicaciones pueden usar esta bandera de enlace para habilitar selectivamente cuándo se generan las finalizaciones. Si se especifica FI_SELECTIVE_COMPLETION, las operaciones de transferencia de datos no generarán entradas de CQ para finalizaciones *exitosas* a menos que FI_COMPLETION se establezca como una bandera operacional para la operación dada. Las operaciones que fallan de forma asíncrona seguirán generando finalizaciones, incluso si no se solicita una finalización. FI_SELECTIVE_COMPLETION debe combinarse (|) con las banderas FI_TRANSMIT y/o FI_RECV.

Cuando se establece FI_SELECTIVE_COMPLETION, el usuario debe determinar cuándo una solicitud que NO tiene FI_COMPLETION establecida se ha completado indirectamente, generalmente basándose en la finalización de una operación subsiguiente o utilizando contadores de finalización. El uso de esta bandera puede mejorar el rendimiento al permitir que el proveedor evite escribir una entrada de finalización de CQ por cada operación.

Consulte la sección Notas a continuación para obtener información adicional sobre cómo esta bandera interactúa con los bits de modo FI_CONTEXT y FI_CONTEXT2.

FI_TRANSMIT
Dirige la finalización de las solicitudes de transferencia de datos de salida a la cola de finalización especificada. Esto incluye operaciones de envío de mensajes, RMA y atómicas.

Un endpoint puede enlazarse opcionalmente a un contador de finalización. Asociar un endpoint con un contador es adicional a enlazar el EP con una CQ. Al enlazar un endpoint a un contador, se pueden especificar las siguientes banderas.

FI_READ
Incrementa el contador especificado cada vez que una operación de lectura RMA, obtención atómica o comparación atómica iniciada desde el endpoint se ha completado con éxito o con error.
FI_RECV
Incrementa el contador especificado cada vez que se recibe un mensaje a través del endpoint. Los mensajes recibidos incluyen operaciones de mensajes normales y etiquetados.
FI_REMOTE_READ
Incrementa el contador especificado cada vez que una operación de lectura RMA, obtención atómica o comparación atómica se inicia desde un endpoint remoto que apunta al endpoint dado. El uso de esta bandera requiere que el endpoint se cree utilizando FI_RMA_EVENT.
FI_REMOTE_WRITE
Incrementa el contador especificado cada vez que una operación de escritura RMA o atómica base se inicia desde un endpoint remoto que apunta al endpoint dado. El uso de esta bandera requiere que el endpoint se cree utilizando FI_RMA_EVENT.
FI_SEND
Incrementa el contador especificado cada vez que una transferencia de mensajes iniciada a través del endpoint se ha completado con éxito o con error. Los mensajes enviados incluyen operaciones de mensajes normales y etiquetados.
FI_WRITE
Incrementa el contador especificado cada vez que una operación de escritura RMA o atómica base iniciada desde el endpoint se ha completado con éxito o con error.

Un endpoint solo puede enlazarse a una única CQ o contador para un tipo de operación dado. Por ejemplo, un EP no puede enlazarse a dos contadores que utilicen FI_WRITE. Además, los proveedores pueden limitar los enlaces de CQ y contador a endpoints del mismo tipo (DGRAM, MSG, RDM, etc.).

fi_scalable_ep_bind

fi_scalable_ep_bind se utiliza para asociar un endpoint escalable con un vector de direcciones. Consulte la sección ENDPOINTS ESCALABLES. Un endpoint escalable tiene una única dirección de nivel de transporte y puede admitir múltiples contextos de transmisión y recepción. Los contextos de transmisión y recepción comparten la dirección de nivel de transporte. Los vectores de direcciones enlazados a endpoints escalables se enlazan implícitamente a cualquier contexto de transmisión o recepción creado utilizando el endpoint escalable.

fi_enable

Esta llamada transiciona el endpoint a un estado habilitado. Un endpoint debe estar habilitado antes de poder utilizarse para realizar transferencias de datos. Habilitar un endpoint generalmente resulta en la asignación de recursos de hardware. Los endpoints que utilizan colas de finalización, contadores, colas de eventos y/o vectores de direcciones deben estar enlazados a ellos antes de ser habilitados.

Llamar a connect o accept en un endpoint habilitará implícitamente un endpoint si aún no ha sido habilitado.

fi_enable también puede usarse para re-habilitar un endpoint que ha sido deshabilitado como resultado de haber experimentado un error crítico. Las aplicaciones deben verificar el valor de retorno de fi_enable para ver si un endpoint deshabilitado ha sido re-habilitado con éxito.

fi_cancel

fi_cancel intenta cancelar una operación asíncrona pendiente. Cancelar una operación hace que el proveedor de fabric busque la operación y, si aún está pendiente, la complete como cancelada. Una entrada en la cola de errores estará disponible en la cola de errores asociada con el código de error FI_ECANCELED. Por otro lado, si la operación se completó antes de la llamada a fi_cancel, entonces el estado de finalización de esa operación estará disponible en la cola de finalización asociada. No se publicará ninguna entrada específica relacionada con fi_cancel en sí.

Cancel utiliza el parámetro de contexto asociado con una operación para identificar la solicitud a cancelar. Las operaciones publicadas sin un parámetro de contexto válido – ya sea que no se especifique ningún parámetro de contexto o que el proveedor haya ignorado el valor del contexto – no pueden ser canceladas. Si múltiples operaciones pendientes coinciden con el parámetro de contexto, solo una será cancelada. En este caso, la operación que se cancela es específica del proveedor. La operación de cancelación es asíncrona, pero se completará dentro de un período de tiempo limitado.

fi_ep_alias

Esta llamada crea un alias al punto de conexión especificado. Conceptualmente, un alias de punto de conexión proporciona una ruta de software alternativa desde la aplicación hasta el hardware del proveedor subyacente. Un EP alias difiere de su punto de conexión padre solo por sus flags de transferencia de datos predeterminados. Por ejemplo, un EP alias puede estar configurado para usar un modo de finalización diferente. De forma predeterminada, un EP alias hereda los mismos flags de transferencia de datos que el punto de conexión padre. Una aplicación puede usar fi_control para modificar los flags operativos del EP

alias.

Al asignar un alias, una aplicación puede configurar ya sea los flags operativos de transmisión o de recepción. Esto evita la necesidad de una llamada separada a fi_control para establece

r esos flags. Los flags pasados a fi_ep_alias deben incluir FI_TRANSMIT o FI_RECV (no ambos) con otros flags operativos OR'eados. Esto anulará los flags de transmisión o recepción, r
espectivamente, para las operaciones publicadas a través del punto de conexión alias. Todos los alias asignados deben cerrarse para que el punto de conexión subyacente pueda ser liberado.

Tamaño Máximo de Ordenación RMA

El tamaño máximo de ordenación especifica el orden de entrega de los datos de transporte en la memoria de destino para operaciones RMA y atómicas. La ordenación de datos es independiente, pero dependiente de la ordenación de mensajes (definida más adelante). La ordenación de datos no está especificada donde el orden de mensajes no está definido.

La ordenación de datos se refiere al acceso a la misma memoria de destino por operaciones posteriores. Cuando operaciones RMA de lectura o escritura consecutivas acceden a la misma ubicación de memoria registrada, la ordenación de datos indica si la segunda operación lee o escribe en la memoria de destino después de que la primera operación haya completado. Por ejemplo, ¿una lectura RMA que sigue a una escritura RMA leerá los datos que fueron escritos? De manera similar, ¿una escritura RMA que sigue a una lectura RMA actualizará el búfer de destino después de que la lectura haya transferido los datos originales? La ordenación de datos responde a estas preguntas, incluso en presencia de errores, como la necesidad de reenviar datos debido a tráfico de red perdido o corrupto.

La ordenación RMA se aplica entre dos operaciones, y no dentro de una sola transferencia de datos. Por lo tanto, la ordenación se define por ubicación de memoria direccionable por byte. Es decir, la ordenación especifica si la ubicación X es accedida por la segunda operación después de la primera operación. No se implica nada sobre la finalización de la primera operación antes de que la segunda operación sea iniciada. Por ejemplo, si la primera operación actualiza las ubicaciones X e Y, pero la segunda operación solo accede a la ubicación X, no hay garantías definidas con respecto a la ubicación Y y la segunda operación.

Para soportar transferencias de datos grandes que se dividen en múltiples paquetes y se envían usando múltiples rutas a través del fabric, la ordenación de datos puede estar limitada a transferencias de un tamaño específico o menor. Los proveedores especifican cuándo se mantiene la ordenación de datos a través de los siguientes valores. Tenga en cuenta que incluso si la ordenación de datos no se mantiene, la ordenación de mensajes puede mantenerse.

max_order_raw_size
Tamaño de lectura después de escritura. Si se establece, una operación de lectura RMA o atómica emitida después de una operación de escritura RMA o atómica, ambas menores que el tamaño, serán ordenadas. Donde las ubicaciones de memoria de destino se superponen, la operación de lectura RMA o atómica verá los resultados de la escritura RMA o atómica anterior.

mem_tag_format - Formato de Etiqueta de Memoria

El campo de formato de etiqueta de memoria se usa para transmitir información sobre el uso de los parámetros de etiqueta e ignorar en las llamadas a la API fi_tagged, así como los criterios de coincidencia. Esta información es usada por el proveedor para optimizar el soporte de coincidencia de etiquetas, incluyendo la alineación con protocolos de red. Se definen los siguientes formatos de etiqueta:

FI_TAG_BITS
Si se especifica en la entrada a fi_getinfo, esto indica que las etiquetas contienen hasta 64 bits de datos, y el receptor debe aplicar ignore_bits a las etiquetas al hacer coincidir búferes de recepción con envíos. La salida de fi_getinfo establecerá 0 o más bits superiores de mem_tag_format a 0 para indicar esos bits de etiqueta que son ignorados o reservados por el proveedor. Las aplicaciones deben verificar el número de bits superiores que son 0 y establecerlos a 0 en todos los bits de etiqueta e ignorar.

El valor de FI_TAG_BITS es 0, haciendo que este sea el comportamiento por defecto si las sugerencias quedan sin inicializar después de ser asignadas por fi_allocinfo(). Este formato proporciona la mayor flexibilidad a las aplicaciones, pero limita las opciones de optimización del proveedor. FI_TAG_BITS se alinea con el comportamiento definido para versiones 1.x de libfabric.

FI_TAG_MPI
FI_TAG_MPI es un uso restringido de FI_TAG_BITS. Cuando se selecciona, las aplicaciones tratan la etiqueta como campos de datos, en lugar de bits, con la capacidad de hacer wildcard en cada campo. El formato de etiqueta MPI específicamente apunta a implementaciones y aplicaciones basadas en MPI. Una etiqueta con formato MPI consiste de 2 campos: una etiqueta de mensaje y un identificador de payload. La etiqueta de mensaje es una etiqueta de 32 bits buscable. La coincidencia en una etiqueta de mensaje requiere buscar a través de una lista de búferes publicados en el receptor, a lo que nos referimos como una etiqueta buscable. La etiqueta entera en mensajes punto a punto de MPI puede mapearse directamente al campo de etiqueta de mensaje de libfabric.

El segundo campo es un identificador que corresponde a la operación o datos siendo transportados en el payload del mensaje. Por ejemplo, este campo puede usarse para identificar el tipo de operación colectiva asociada con un payload de mensaje. Tenga en cuenta que solo se definen el tamaño y comportamiento para los formatos de etiqueta MPI. El uso descrito de los campos son solo sugerencias.

Las aplicaciones que usan el formato MPI deben inicializar sus etiquetas usando la función fi_tag_mpi(). Los bits de ignorar deben especificarse como FI_MPI_IGNORE_TAG, FI_MPI_IGNORE_PAYLOAD, o su OR bit a bit.

FI_TAG_CCL
El formato FI_TAG_CCL restringe aún más el formato FI_TAG_MPI. Cuando se usa, solo un campo de etiqueta puede ser establecido, el cual debe coincidir exactamente en el destino. El campo no puede ser wildcard. El formato de etiqueta CCL apunta a bibliotecas y aplicaciones de comunicación colectiva. El formato CCL consiste de un solo campo: un identificador de payload. El identificador corresponde a la operación o datos siendo transportados en el payload del mensaje. Por ejemplo, este campo puede usarse para identificar si un mensaje es para comunicación punto a punto o parte de una operación colectiva, y en este último caso, el tipo de operación colectiva.

El formato de etiqueta CCL no requiere buscar búferes de recepción coincidentes, solo dirigir el mensaje a la cola de mensajes virtual correcta basándose en el identificador de payload.

Las aplicaciones que usan el formato CCL pasan el identificador de payload directamente como la etiqueta y establecen los bits de ignorar a 0.

FI_TAG_MAX_FORMAT
Si el valor de mem_tag_format es >= FI_TAG_MAX_FORMAT, el formato de etiqueta es tratado como un conjunto de campos de bits. El comportamiento es funcionalmente el mismo que FI_TAG_BITS. La siguiente descricción es para compatibilidad hacia atrás y describe cómo el proveedor puede interpretar el campo mem_tag_format si el valor es >= FI_TAG_MAX_FORMAT.

El formato de etiqueta de memoria puede usarse para dividir el arreglo de bits en campos separados. El mem_tag_format opcionalmente comienza con una serie de bits establecidos en 0, para significar bits que son ignorados por el proveedor. Siguiendo el prefijo inicial de bits ignorados, el arreglo consistirá de grupos alternos de bits establecidos en todos 1's o todos 0's. Cada grupo de bits corresponde a un campo con etiqueta. La implicación de definir un campo con etiqueta es que cuando se aplica una máscara al arreglo de bits con etiqueta, todos los bits pertenecientes a un solo campo serán establecidos colectivamente a 1 o 0.

Por ejemplo, un mem_tag_format de 0x30FF indica soporte para 14 bits con etiqueta, separados en 3 campos. El primer campo consiste de 2 bits, el segundo campo 4 bits, y el campo final 8 bits. Máscaras válidas para tal campo con etiqueta serían un OR bit a bit de cero o más de los siguientes valores: 0x3000, 0x0F00, y 0x00FF. El proveedor puede no validar la máscara proporcionada por la aplicación por razones de rendimiento.

Al identificar campos dentro de una etiqueta, un proveedor puede ser capaz de optimizar sus rutinas de búsqueda. Una aplicación que solicita campos de etiqueta debe proporcionar máscaras de etiqueta que establezcan todos los bits de máscara correspondientes a un campo a todos 0 o todos 1. Al negociar campos de etiqueta, una aplicación puede solicitar un número específico de campos de un tamaño dado. Un proveedor debe devolver un formato de etiqueta que soporte el número solicitado de campos, con cada campo siendo al menos del tamaño solicitado, o fallar la solicitud. Un proveedor puede aumentar el tamaño de los campos. Al reportar completaciones (ver FI_CQ_FORMAT_TAGGED), no está garantizado que el proveedor limpiaría cualquier bit de etiqueta no soportado en el campo de etiqueta de la entrada de completación.

Se recomienda que los tamaños de campo estén ordenados de menor a mayor. Una etiqueta genérica y no estructurada y máscara se puede lograr solicitando un arreglo de bits que consista de 1's y 0's alternos.

The size of the transmit context. The mapping of the size value to resources is provider specific, but it is directly related to the number of command entries allocated for the endpoint. While the size attribute guides the size of underlying endpoint transmit queue, there is not necessarily a one-to-one mapping between a transmit operation and a queue entry. FI_TC_BEST_EFFORT

Even though it is shared, network capacity and resource allocation are distributed fairly across the applications.

PUNTOS FINALES ESCALABLES

Un punto final escalable es un portal de comunicación que soporta múltiples contextos de transmisión y recepción. Los puntos finales escalables están modelados libremente después del concepto de redes de escalado de lado de transmisión/recepción, también conocido como multi-cola. El soporte para puntos finales escalables es específico del dominio. Los puntos finales escalables pueden mejorar el rendimiento de aplicaciones multi-hilo y paralelas, al permitir que los hilos accedan a colas de transmisión y recepción independientes. Un punto final escalable tiene una única dirección de nivel de transporte, lo que puede reducir los requisitos de memoria necesarios para almacenar datos de direccionamiento remoto, en comparación con el uso de puntos finales estándar. Los puntos finales escalables no pueden usarse directamente para operaciones de comunicación, y requieren que la aplicación cree explícitamente contextos de transmisión y recepción como se describe a continuación.

fi_tx_context

Los contextos de transmisión son colas de transmisión independientes. El ordenamiento y la sincronización entre contextos no están definidos. Conceptualmente, un contexto de transmisión se comporta de manera similar a un punto final de solo envío. Un contexto de transmisión puede configurarse con menos capacidades que el punto final base y con diferentes atributos (como requisitos de ordenamiento y tamaño de inyección) que otros contextos asociados con el mismo punto final escalable. Cada contexto de transmisión tiene su propia cola de finalización. El número de contextos de transmisión asociados con un punto final se especifica durante la creación del punto final.

La llamada fi_tx_context se utiliza para recuperar un contexto específico, identificado por un índice (ver arriba para detalles sobre los atributos del contexto de transmisión). Los proveedores pueden asignar contextos dinámicamente cuando se llama a fi_tx_context, o pueden crear estáticamente todos los contextos cuando se invoca fi_endpoint. Por defecto, un contexto de transmisión hereda las propiedades de su punto final asociado. Sin embargo, las aplicaciones pueden solicitar atributos específicos del contexto a través del parámetro attr. El soporte para atributos por contexto de transmisión es específico del proveedor y no está garantizado. Los proveedores devolverán los atributos reales asignados al contexto a través del parámetro attr, si se proporciona.

fi_rx_context

Los contextos de recepción son colas de recepción independientes para recibir datos entrantes. El ordenamiento y la sincronización entre contextos no están garantizados. Conceptualmente, un contexto de recepción se comporta de manera similar a un punto final de solo recepción. Un contexto de recepción puede configurarse con menos capacidades que el punto final base y con diferentes atributos (como requisitos de ordenamiento y tamaño de inyección) que otros contextos asociados con el mismo punto final escalable. Cada contexto de recepción tiene su propia cola de finalización. El número de contextos de recepción asociados con un punto final se especifica durante la creación del punto final.

Los contextos de recepción a menudo se asocian con flujos de enrutamiento, que especifican qué paquetes entrantes dirigidos a un punto final escalable deben procesarse. Sin embargo, los contextos de recepción pueden ser dirigidos directamente por el iniciador, si lo soporta el protocolo subyacente. Dichos contextos se denominan `nombrados' (named). El soporte para contextos nombrados debe indicarse estableciendo la capacidad caps FI_NAMED_RX_CTX cuando se crea el punto final correspondiente. El soporte para contextos de recepción nombrados se coordina con los vectores de dirección. Ver fi_av(3) y fi_rx_addr(3).

La llamada fi_rx_context se utiliza para recuperar un contexto específico, identificado por un índice (ver arriba para detalles sobre los atributos del contexto de recepción). Los proveedores pueden asignar contextos dinámicamente cuando se llama a fi_rx_context, o pueden crear estáticamente todos los contextos cuando se invoca fi_endpoint. Por defecto, un contexto de recepción hereda las propiedades de su punto final asociado. Sin embargo, las aplicaciones pueden solicitar atributos específicos del contexto a través del parámetro attr. El soporte para atributos por contexto de recepción es específico del proveedor y no está garantizado. Los proveedores devolverán los atributos reales asignados al contexto a través del parámetro attr, si se proporciona.

CONTEXTOS COMPARTIDOS

Los contextos compartidos son contextos de transmisión y recepción compartidos explícitamente entre uno o más puntos finales. Un contexto compartible permite a una aplicación usar un único recurso dedicado del proveedor entre múltiples puntos finales direccionables por transporte. Esto puede reducir en gran medida los recursos necesarios para gestionar la comunicación sobre múltiples puntos finales al multiplexar el procesamiento de transmisión y/o recepción, con el costo potencial de serializar el acceso a través de múltiples puntos finales. El soporte para contextos compartibles es específico del dominio.

Conceptualmente, los contextos de transmisión compartibles son colas de transmisión a las que pueden acceder muchos puntos finales. El uso de un contexto de transmisión compartido es mayormente opaco para una aplicación. Las aplicaciones deben asignar y vincular contextos de transmisión compartidos a puntos finales, pero las operaciones se publican directamente en el punto final. Los contextos de transmisión compartidos no están asociados con colas de finalización ni contadores. Las operaciones completadas se publican en las CQs vinculadas al punto final. Un punto final solo puede estar asociado con un único contexto de transmisión compartido.

A diferencia de los contextos de transmisión compartidos, las aplicaciones interactúan directamente con los contextos de recepción compartidos. Los usuarios publican búferes de recepción directamente en un contexto de recepción compartido, siendo utilizables por cualquier punto final vinculado al contexto de recepción compartido. Los contextos de recepción compartidos no están asociados con colas de finalización ni contadores. Las operaciones de recepción completadas se publican en las CQs vinculadas al punto final. Un punto final solo puede estar asociado con un único contexto de recepción, y todos los puntos finales sin conexión asociados con un contexto de recepción compartido también deben compartir el mismo vector de dirección.

Los puntos finales asociados con un contexto de transmisión compartido pueden usar contextos de recepción dedicados, y viceversa. O un punto final puede usar contextos de transmisión y recepción compartidos. Y no hay requisito de que el mismo grupo de puntos finales que comparte un contexto de un tipo también comparta el contexto de un tipo alternativo. Además, un punto final puede usar un contexto compartido de un tipo, pero un conjunto escalable de contextos del tipo alternativo.

fi_stx_context

Esta llamada se utiliza para abrir un contexto de transmisión compartible (ver arriba para detalles sobre los atributos del contexto de transmisión). Los puntos finales asociados con un contexto de transmisión compartido deben usar un subconjunto de los atributos del contexto de transmisión. Nótese que esto es lo contrario del requisito para los contextos de transmisión de los puntos finales escalables.

fi_srx_context

Esto asigna un contexto de recepción compartible (ver arriba para detalles sobre los atributos del contexto de recepción). Los puntos finales asociados con un contexto de recepción compartido deben usar un subconjunto de los atributos del contexto de recepción. Nótese que esto es lo contrario del requisito para los contextos de recepción de los puntos finales escalables.

PUNTOS FINALES DE SOCKET

La siguiente característica y descripción deben considerarse experimentales. Hasta que se elimine la etiqueta experimental, las interfaces, semánticas y estructuras de datos asociadas con los puntos finales de socket pueden cambiar entre versiones de la biblioteca.

Esta sección aplica a los puntos finales de tipo FI_EP_SOCK_STREAM y FI_EP_SOCK_DGRAM, comúnmente referidos como puntos finales de socket.

Los puntos finales de socket se definen con semánticas que les permiten ser adoptados más fácilmente por desarrolladores familiarizados con la API de sockets UNIX, o por middleware que expone la API de socket, mientras aún aprovechan características de hardware de alto rendimiento.

La diferencia clave entre los puntos finales de socket y otros puntos finales activos es que los puntos finales de socket usan transferencias de datos sincrónicas. Los búferes pasados a las operaciones de envío y recepción vuelven al control de la aplicación al regresar de la llamada a la función. Como resultado, no se notifican finalizaciones de transferencia de datos a la aplicación, y los puntos finales de socket no están asociados con colas de finalización ni contadores.

Los puntos finales de socket soportan un subconjunto de operaciones de mensaje: fi_send, fi_sendv, fi_sendmsg, fi_recv, fi_recvv, fi_recvmsg, y fi_inject. Debido a que las transferencias de datos son sincrónicas, el valor de retorno de las operaciones de envío y recepción indica el número de bytes transferidos en caso de éxito, o un valor negativo en caso de error, incluyendo -FI_EAGAIN si el punto final no puede enviar o recibir ningún dato debido a colas llenas o vacías, respectivamente.

Los puntos finales de socket están asociados con colas de eventos y vectores de dirección, y procesan eventos de gestión de conexiones de forma asíncrona, similar a otros puntos finales. A diferencia de los sockets UNIX, el punto final de socket aún debe declararse como activo o pasivo.

Los puntos finales de socket se comportan como sockets no bloqueantes. Para soportar la semántica de select y poll, los puntos finales de socket activos están asociados con un descriptor de archivo que se señala siempre que el punto final está listo para enviar y/o recibir datos. El descriptor de archivo puede recuperarse usando fi_control.
