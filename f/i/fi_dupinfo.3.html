CAPACIDADES (CAPABILITIES)

Las capacidades de la interfaz se obtienen combinando (mediante OR) los siguientes indicadores (flags). Si las capacidades en el parámetro de sugerencia (hint) están establecidas a 0, el proveedor subyacente devolverá el conjunto de capacidades que son soportadas. De lo contrario, los proveedores devolverán datos que coincidan con el conjunto de capacidades especificado. Los proveedores pueden indicar soporte para capacidades adicionales más allá de las solicitadas cuando el uso de capacidades expandidas no afectará adversamente el rendimiento o expondrá a la aplicación a comunicaciones más allá de las que fueron solicitadas. Las aplicaciones pueden usar esta característica para solicitar un conjunto mínimo de requisitos, y luego verificar las capacidades devueltas para habilitar optimizaciones adicionales.

FI_ATOMIC
Especifica que el endpoint soporta algún conjunto de operaciones atómicas. Los endpoints que soportan esta capacidad soportan operaciones definidas por struct fi_ops_atomic. En ausencia de cualquier indicador (flag) relevante, FI_ATOMIC implica la capacidad de iniciar y ser el destino de lecturas y escrituras atómicas remotas. Las aplicaciones pueden usar los indicadores FI_READ, FI_WRITE, FI_REMOTE_READ y FI_REMOTE_WRITE para restringir los tipos de operaciones atómicas soportadas por un endpoint.
FI_AV_USER_ID
Solicita que el proveedor soporte la asociación de un identificador especificado por el usuario con cada dirección de vector de dirección (AV). Los identificadores de usuario son devueltos con los datos de finalización (completion) en lugar de la dirección AV. Vea fi_domain(3) y fi_av(3) para más detalles.
FI_COLLECTIVE
Solicita soporte para operaciones colectivas. Los endpoints que soportan esta capacidad soportan las operaciones colectivas definidas en fi_collective(3).
FI_DIRECTED_RECV
Solicita que el endpoint de comunicación use la dirección de origen de un mensaje entrante al hacer coincidir (match) con un búfer de recepción. Si esta capacidad no está establecida, el parámetro src_addr para las operaciones de recepción de mensajes (msg) y etiquetadas (tagged) será ignorado.
FI_TAGGED_DIRECTED_RECV
Similar a FI_DIRECTED_RECV, pero solo se aplica a operaciones de recepción etiquetadas (tagged).
FI_EXACT_DIRECTED_RECV
Similar a FI_DIRECTED_RECV, pero requiere que la dirección de origen sea exacta, es decir, no se permite FI_ADDR_UNSPEC. Esta capacidad puede usarse sola, o en conjunto con FI_DIRECTED_RECV o FI_TAGGED_DIRECTED_RECV como un modificador para no permitir el uso de FI_ADDR_UNSPEC como la dirección de origen.
FI_FENCE
Indica que el endpoint soporta el indicador (flag) FI_FENCE en las operaciones de transferencia de datos. El soporte requiere rastrear que todas las solicitudes de transmisión previas a un endpoint remoto especificado se completen antes de iniciar la operación cercada (fenced). Las operaciones cercadas se usan a menudo para forzar el ordenamiento entre operaciones que no son garantizadas de otra manera por el proveedor o protocolo subyacente.
FI_HMEM
Especifica que el endpoint debe soportar transferencias hacia y desde la memoria del dispositivo.
FI_LOCAL_COMM
Indica que el endpoint soporta comunicación local del host. Este indicador (flag) puede usarse junto con FI_REMOTE_COMM para indicar que se requieren comunicación local y remota. Si no se especifica ninguno de FI_LOCAL_COMM o FI_REMOTE_COMM, el proveedor indicará soporte para la configuración que afecta mínimamente el rendimiento. Los proveedores que establecen FI_LOCAL_COMM pero no FI_REMOTE_COMM, por ejemplo un proveedor de memoria compartida, solo pueden usarse para la comunicación entre procesos en el mismo sistema.
FI_MSG
Especifica que un endpoint debe soportar el envío y recepción de mensajes o datagramas. Las capacidades de mensaje implican soporte para colas de envío y/o recepción. Los endpoints que soportan esta capacidad soportan operaciones definidas por struct fi_ops_msg.

Las capacidades (caps) pueden usarse para especificar o restringir el tipo de operaciones de mensajería que son soportadas. En ausencia de cualquier indicador (flag) relevante, FI_MSG implica la capacidad de enviar y recibir mensajes. Las aplicaciones pueden usar los indicadores FI_SEND y FI_RECV para optimizar un endpoint como solo de envío o solo de recepción.

FI_MULTICAST
Indica que el endpoint soporta transferencias de datos de multidifusión (multicast). Esta capacidad debe estar emparejada con FI_MSG. Las aplicaciones pueden usar FI_SEND y FI_RECV para optimizar la multidifusión como solo de envío o solo de recepción.
FI_MULTI_RECV
Especifica que el endpoint debe soportar el indicador (flag) FI_MULTI_RECV al publicar búferes de recepción.
FI_TAGGED_MULTI_RECV
Especifica que el endpoint debe soportar el indicador (flag) FI_MULTI_RECV al publicar búferes de recepción etiquetados (tagged).
FI_NAMED_RX_CTX
Solicita que los endpoints que soportan múltiples contextos de recepción permitan a un iniciador apuntar (o nombrar) un contexto de recepción específico como parte de una operación de transferencia de datos.
FI_PEER
Especifica que el proveedor debe soportar ser usado como un proveedor peer en el flujo de la API peer. El proveedor debe soportar la importación de owner_ops al abrir un CQ, contador y cola de recepción compartida.
FI_READ
Indica que el usuario requiere un endpoint capaz de iniciar lecturas contra regiones de memoria remotas. Este indicador (flag) requiere que FI_RMA y/o FI_ATOMIC estén establecidos.
FI_RECV
Indica que el usuario requiere un endpoint capaz de recibir transferencias de datos de mensajes. Las transferencias de mensajes incluyen operaciones básicas de mensajes así como funcionalidad de mensajes etiquetados (tagged).
FI_REMOTE_COMM
Indica que el endpoint soporta comunicación con endpoints ubicados en nodos remotos (a través del fabric). Vea FI_LOCAL_COMM para detalles adicionales. Los proveedores que establecen FI_REMOTE_COMM pero no FI_LOCAL_COMM, por ejemplo NICs que carecen de soporte de loopback, no pueden usarse para comunicarse con procesos en el mismo sistema.
FI_REMOTE_READ
Indica que el usuario requiere un endpoint capaz de recibir operaciones de lectura de memoria desde endpoints remotos. Este indicador (flag) requiere que FI_RMA y/o FI_ATOMIC estén establecidos.
FI_REMOTE_WRITE
Indica que el usuario requiere un endpoint capaz de recibir operaciones de escritura de memoria desde endpoints remotos. Este indicador (flag) requiere que FI_RMA y/o FI_ATOMIC estén establecidos.
FI_RMA
Especifica que el endpoint debe soportar RMOperaciones de lectura y escritura. Los puntos de extremo que admiten esta capacidad admiten las operaciones definidas por la estructura fi_ops_rma. En ausencia de cualquier indicador relevante, FI_RMA implica la capacidad de iniciar y ser el destino de lecturas y escrituras de memoria remota. Las aplicaciones pueden usar los indicadores FI_READ, FI_WRITE, FI_REMOTE_READ y FI_REMOTE_WRITE para restringir los tipos de operaciones RMA admitidas por un punto de
extremo.

NT

extremo.

Los proveedores conscientes de la memoria persistente deben admitir el registro de memoria respaldada por memoria no volátil, transferencias RMA hacia/desde la memoria persistente y semánticas de finalización mejoradas. Las transferencias de mensajes etiquetados asocian una clave o etiqueta especificada por el usuario con cada mensaje que se utiliza para propósitos de emparejamiento en el lado remoto. Los puntos de extremo que admiten esta capacidad admiten las operaciones definidas por la estructura fi_ops_tagged. En ausencia de cualquier indicador relevante, FI_TAGGED implica la capacidad de enviar y recibir mensajes etiquetados. Las aplicaciones pueden usar los indicadores FI_SEND y FI_RECV para optimizar un punto de extremo como solo de envío o solo de
recepción.

.

Las capacidades pueden agruparse en tres categorías generales: primarias, secundarias y modificadores primarios. Las capacidades primarias deben ser solicitadas explícitamente por una aplicación, y un proveedor debe habilitar el soporte solo para aquellas capacidades primarias que fueron seleccionadas. Los modificadores primarios se utilizan para limitar una capacidad primaria, como restringir un punto de extremo a ser solo de envío. Si no se especifican modificadores para una capacidad aplicable, se asumen todos los modificadores relevantes. Consulte las definiciones anteriores para obtener

detalles.

Las capacidades secundarias pueden ser solicitadas opcionalmente por una aplicación. Si se solicitan, un proveedor debe admitir la capacidad o fallar la solicitud fi_getinfo (FI_ENODATA). Un proveedor puede reportar opcionalmente capacidades secundarias no seleccionadas si hacerlo no comprometería el rendimiento o la

seguridad.

MOD

O

Los bits de modo operativo se utilizan para transmitir requisitos que una aplicación debe cumplir al usar las interfaces de la red. Los modos especifican formas óptimas de acceder al punto de extremo o dominio reportado. Las aplicaciones que están diseñadas para admitir un modo de operación específico pueden ver un rendimiento mejorado cuando ese modo es deseado por el proveedor. Se recomienda que los proveedores admitan aplicaciones que deshabiliten cualquier modo preferido por el

proveedor.

En la entrada a fi_getinfo, las aplicaciones establecen los bits de modo que admiten. En la salida, los proveedores limpiarán los bits de modo que no sean necesarios para lograr un alto rendimiento. Los bits de modo que permanezcan establecidos indican requisitos de la aplicación para usar las interfaces de la red creadas usando el fi_info devuelto. El conjunto de modos se lista a continuación. Si se proporciona una estructura de sugerencias NULL, entonces el conjunto de modos admitidos por el proveedor será devuelto en la(s) estructura(s)

info.
FI_ASYNC_I
OV
Las aplicaciones pueden referenciar múltiples búferes de datos como parte de una sola operación mediante el uso de vectores de E/S (SGEs). Típicamente, el contenido de un vector de E/S es copiado por el proveedor a un área de búfer interna, o directamente al hardware subyacente. Sin embargo, cuando se admiten un gran número de entradas de IOV, el buffering de IOV puede tener un impacto negativo en el rendimiento y el consumo de memoria. El modo FI_ASYNC_IOV indica que la aplicación debe proporcionar el buffering necesario para los vectores de E/S. Cuando está establecido, una aplicación no debe modificar un vector de E/S de longitud > 1, incluyendo cualquier arreglo de descriptores de memoria relacionado, hasta que la operación asociada haya
completado.
FI_CONTE
XT
Especifica que el proveedor requiere que las aplicaciones usen la estructura fi_context como su parámetro de contexto por operación para operaciones que generaron finalizaciones completas. Esta estructura debe ser tratada como opaca para la aplicación. Por razones de rendimiento, esta estructura debe ser asignada por el usuario, pero puede ser usada por el proveedor de la red para rastrear la operación. Típicamente, los usuarios incrustan la estructura fi_context dentro de su propia estructura de contexto. La estructura fi_context debe permanecer válida hasta que la operación correspondiente complete o sea cancelada exitosamente. Como tal, fi_context NO debe ser asignado en la pila. Hacerlo probablemente resultará en corrupción de la pila que será difícil de depurar. Los usuarios no deben actualizar ni interpretar los campos en esta estructura, o reutilizarla hasta que la operación original haya completado. Si una operación no genera una finalización (es decir, el punto de extremo fue configurado con FI_SELECTIVE_COMPLETION y la operación no fue iniciada con el indicador FI_COMPLETION), entonces el parámetro de contexto es ignorado por el proveedor de la red. La estructura está especificada en rdma/fabric.

Los búferes de datos usados en operaciones de envío y recepción y como búfer de origen para operaciones RMA y atómicas deben ser registrados por la aplicación para dominios de acceso abiertos con esta capacidad. Este indicador está definido para compatibilidad y es ignorado si la versión de la aplicación es 1.5 o posterior y el mr_mode del dominio está establecido a algo diferente de FI_MR_BASIC o FI_MR_SCALABLE. Vea el atributo del dominio mr_mode en fi_domain(3) y fi_mr(3)

FI_MSG_PREF
IX
El modo de prefijo de mensaje indica que una aplicación proporcionará espacio de búfer delante de todos los búferes de envío y recepción de mensajes para uso por el proveedor. Típicamente, el proveedor usa
este espacio para implementar un protocolo, con las cabeceras del protocolo siendo escritas en el área de prefijo. El contenido del espacio de prefijo debe ser tratado como opaco. El uso de FI_MSG_PREFIX
puede mejorar el rendimiento de la aplicación sobre ciertos proveedores al reducir el número de vectores de E/S referenciados por el hardware subyacente y eliminar la asignación de búferes del proveedor.

FI_MSG_PREFIX solo se aplica a operaciones de envío y recepción, incluyendo envíos y recepciones etiquetados. RMA y operaciones atómicas no requieren que la aplicación proporcione búferes de prefijo. El espacio de búfer de prefijo debe ser proporcionado con todos los envíos y recepciones, independientemente del tamaño de la transferencia u otras opciones de transferencia. La propiedad de los búferes de prefijo se trata igual que la de los búferes de mensaje correspondientes, pero el tamaño del búfer de prefijo no se cuenta hacia ningún límite de mensaje, incluyendo

inyectar.

Las aplicaciones que admiten el modo de prefijo deben proporcionar espacio de búfer antes de sus propios datos de mensaje. El tamaño del espacio que debe ser proporcionado es especificado por el atributo del punto de extremo msg_prefix_size. Los proveedores están obligados a definir un msg_prefix_size que sea un múltiplo de 8 bytes. Adicionalmente, las aplicaciones pueden recibir paquetes generados por el proveedor que no contienen datos de la aplicación. Tales mensajes recibidos indicarán un tamaño de transferencia que es igual o menor que msg_prefix_size

.

El puntero de búfer dado a todas las operaciones de envío y recepción debe apuntar al inicio de la región de prefijo del búfer (a diferencia de la carga útil). Para operaciones de envío/recepción scatter-gather, el búfer de prefijo debe ser una región contigua, aunque puede o no estar directamente adyacente a la porción de carga útil del

búfer.
FI_RX_CQ_DA
TA
Este bit de modo solo se aplica a transferencias de datos que establecen FI_REMOTE_CQ_DATA.
Cuando está establecido, una transferencia de datos que transporta datos de CQ remotos consu

malmente no consumirían búferes de recepción publicados, como operaciones de escritura RMA.

NOTA

S

Varias llamadas de libfabric, incluyendo fi_getinfo, toman una struct fi_info como entrada. Las aplicaciones deben usar estructuras fi_info asignadas por libfabric. Una struct fi_info a cero puede ser asignada usando fi_allocinfo, que luego puede ser inicializada por el usuario. Una struct fi_info puede ser copiada para su modificación usando la llamada fi_dupinfo()

.

Si se proporcionan pistas (hints), la operación será controlada por los valores que se proporcionan en los varios campos (vea la sección sobre fi_info). Las aplicaciones que requieren interfaces de comunicación específicas, dominios, capacidades u otros requisitos, pueden especificarlos usando campos en hints. Libfabric devuelve una lista enlazada en info que apunta a una lista de interfaces coincidentes. info se establece en NULL si no hay interfaces de comunicación o ninguna coincide con las pistas de

entrada.

Si se proporciona node, fi_getinfo intentará resolver la dirección de fabric al nodo dado. Si no se proporciona node, fi_getinfo intentará resolver la información de direccionamiento de fabric basándose en las pistas proporcionadas. El llamador debe llamar a fi_freeinfo para liberar las estructuras fi_info devueltas por

fi_getinfo.

Si no se proporciona node, service ni hints, entonces fi_getinfo simplemente devuelve la lista de todas las interfaces de comunicación

disponibles.

Múltiples hilos pueden llamar a fi

_getinfo simultáneamente, sin ning
ún requisito de serialización.
