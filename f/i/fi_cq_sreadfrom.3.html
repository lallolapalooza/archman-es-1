CQ Attributes

The following attributes are used when creating a completion queue (CQ):

wait_obj
Specifies the type of wait object associated with a CQ: FI_WAIT_NONE, FI_WAIT_UNSPEC, FI_WAIT_SET, FI_WAIT_FD, FI_WAIT_MUTEX_COND (obsoleto), y FI_WAIT_YIELD. El valor predeterminado es FI_WAIT_NONE.
- FI_WAIT_NONE
Se utiliza para indicar que el usuario no se bloqueará (esperará) a las finalizaciones en la CQ. Cuando se especifica FI_WAIT_NONE, la aplicación no puede llamar a fi_cq_sread ni a fi_cq_sreadfrom.
- FI_WAIT_UNSPEC
Especifica que el usuario solo esperará en la CQ utilizando llamadas de interfaz de tejido, como fi_cq_sread o fi_cq_sreadfrom. En este caso, el proveedor subyacente puede seleccionar el objeto de espera más apropiado o de mayor rendimiento disponible, incluidos mecanismos de espera personalizados. Las aplicaciones que seleccionan FI_WAIT_UNSPEC no tienen garantizado recuperar el objeto de espera subyacente.
- FI_WAIT_SET (obsoleto)
Indica que la cola de finalización debe utilizar un objeto de conjunto de espera para esperar las finalizaciones. Si se especifica, el campo wait_set debe hacer referencia a un objeto de conjunto de espera existente.
- FI_WAIT_FD
Indica que la CQ debe utilizar un descriptor de archivo como su mecanismo de espera. Un objeto de espera de descriptor de archivo debe ser utilizable en las rutinas select, poll y epoll. Sin embargo, un proveedor puede señalar un objeto de espera de FD marcándolo como legible, escribible o con un error.
- FI_WAIT_MUTEX_COND (obsoleto)
Especifica que la CQ debe utilizar un mutex y una variable condicional de pthread como objeto de espera.
- FI_WAIT_YIELD
Indica que la CQ esperará sin un objeto de espera, sino que cederá en cada espera. Permite el uso de fi_cq_sread y fi_cq_sreadfrom a través de un bucle de sondeo.
signaling_vector
Si se establece la bandera FI_AFFINITY, esto indica el número de CPU lógico (0..máx. CPU - 1) al que deben dirigirse las interrupciones asociadas con la CQ. Este campo debe tratarse como una pista para el proveedor y puede ser ignorado si el proveedor no admite la afinidad de interrupciones.
wait_cond
Por defecto, cuando se inserta una finalización en una CQ que admite lecturas bloqueantes (fi_cq_sread/fi_cq_sreadfrom), se señala el objeto de espera correspondiente. Los usuarios pueden especificar una condición que debe cumplirse primero antes de que la espera se satisfaga. Este campo indica cómo el proveedor debe interpretar el campo cond, que describe la condición necesaria para señalar el objeto de espera.

Una condición de espera debe tratarse como una optimización. Los proveedores no están obligados a cumplir los requisitos de la condición antes de señalar el objeto de espera. Las aplicaciones no deben depender de que la condición sea necesariamente cierta cuando una llamada de lectura bloqueante regrese.

Si wait_cond se establece en FI_CQ_COND_NONE, no se aplicarán condiciones adicionales al señalamiento del objeto de espera de la CQ, y la inserción de cualquier entrada nueva activará la condición de espera. Si wait_cond se establece en FI_CQ_COND_THRESHOLD, el campo cond se interpreta como un valor de umbral size_t. El umbral indica el número de entradas que se pondrán en cola antes de la CQ antes de que la espera se satisfaga.

Este campo se ignora si wait_obj se establece en FI_WAIT_NONE.

wait_set (obsoleto)
Si wait_obj es FI_WAIT_SET, este campo hace referencia a un objeto de espera al que debe adjuntarse la cola de finalización. Cuando se inserta un evento en la cola de finalización, el conjunto de espera correspondiente se señalará si se cumplen todas las condiciones necesarias. El uso de un wait_set permite un método optimizado de espera de eventos en múltiples colas de eventos y finalizaciones. Este campo se ignora si wait_obj no es FI_WAIT_SET.

fi_close

La llamada fi_close libera todos los recursos asociados con una cola de finalización. Cualquier finalización que permanezca en la CQ cuando se cierre se perderá.

Al cerrar la CQ, no debe haber puntos finales abiertos, contextos de transmisión o contextos de recepción asociados con la CQ. Si todavía hay recursos asociados con la CQ al intentar cerrarla, la llamada devolverá -FI_EBUSY.

fi_control

La llamada fi_control se utiliza para acceder a detalles específicos del proveedor o de la implementación de la cola de finalización. El acceso a la CQ debe serializarse en todas las llamadas cuando se invoque fi_control, ya que puede redirigir la implementación de las operaciones de la CQ. Los siguientes comandos de control son utilizables con una CQ.

FI_GETWAIT (void **)
Este comando permite al usuario recuperar el objeto de espera de bajo nivel asociado con la CQ. El formato del objeto de espera se especifica durante la creación de la CQ, a través de los atributos de la CQ. El parámetro arg de fi_control debe ser una dirección donde se escribirá un puntero al objeto de espera devuelto. Consulte fi_eq.3 para obtener más detalles sobre el uso de fi_control con FI_GETWAIT.

fi_cq_read

La operación fi_cq_read realiza una lectura no bloqueante de datos de finalización desde la CQ. El formato del evento de finalización se determina utilizando la opción fi_cq_format que se especificó cuando se abrió la CQ. Se pueden recuperar múltiples finalizaciones de una CQ en una sola llamada. El número máximo de entradas a devolver está limitado al parámetro count especificado, con el número de entradas leídas con éxito de la CQ devuelto por la llamada. (Consulte la sección de valores de retorno a continuación). Se puede usar un valor de count de 0 para impulsar el progreso en los puntos finales asociados cuando el progreso manual está habilitado.

Las CQs están optimizadas para informar sobre operaciones que han completado exitosamente. Las operaciones que fallan se informan "fuera de banda". Dichas operaciones se recuperan utilizando la función fi_cq_readerr. Cuando se encuentra una operación que ha completado con un error inesperado, se coloca en una cola de error temporal. Intentar leer de una CQ mientras un elemento está en la cola de error resulta en que fi_cq_read falle con un código de retorno de -FI_EAVAIL. Las aplicaciones pueden utilizar este código de retorno para determinar cuándo llamar a fi_cq_readerr.

fi_cq_readfrom

La llamada fi_cq_readfrom se comporta de manera idéntica a fi_cq_read, con la excepción de que permite a la CQ devolver información de la dirección de origen al usuario para cualquier dato recibido. Los datos de la dirección de origen solo están disponibles para aquellos puntos finales configurados con la capacidad FI_SOURCE. Si se llama a fi_cq_readfrom en un punto final para el cual no están disponibles los datos de direccionamiento de origen, la dirección de origen se establecerá en FI_ADDR_NOTAVAIL. El número de entradas src_addr de entrada debe ser el mismo que el parámetro count.

Los datos de direccionamiento de origen devueltos se convierten del formato nativo utilizado por el tejido subyacente a un fi_addr_t, que puede utilizarse en operaciones de transmisión. En la mayoría de las circunstancias, devolver fi_addr_t requiere que la dirección de origen ya se haya insertado en el vector de direcciones asociado con el punto final receptor. Esto es cierto para los vectores de direcciones de tipo FI_AV_TABLE. En proveedores selectos cuando se utiliza FI_AV_MAP, las direcciones de origen pueden convertirse algorítmicamente en un fi_addr_t utilizable, incluso si la dirección de origen no se ha insertado en el vector de direcciones. Esto está permitido por la API, ya que permite al proveedor evitar la búsqueda de direcciones como parte del procesamiento de mensajes de recepción. En ningún caso los proveedores insertan direcciones en un AV por separado de una aplicación que llama a fi_av_insert o una llamada similar.

Para los puntos finales asignados utilizando la capacidad FI_SOURCE_ERR, si la dirección de origen no se puede convertir en un valor fi_addr_t válido, fi_cq_readfrom devolverá -FI_EAVAIL, incluso si los datos se recibieron correctamente. La finalización se informará entonces a través de fi_cq_readerr con el código de error -FI_EADDRNOTAVAIL. Consulte fi_cq_readerr para obtener detalles.

Si se especifica FI_SOURCE sin FI_SOURCE_ERR, las direcciones de origen que no se puedan mapear a un fi_addr_t utilizable se informarán como FI_ADDR_NOTAVAIL.

fi_cq_sread / fi_cq_sreadfrom

Las llamadas fi_cq_sread y fi_cq_sreadfrom son los equivalentes bloqueantes de las operaciones fi_cq_read y fi_cq_readfrom. Su comportamiento es similar al de las llamadas no bloqueantes, con la excepción de que las llamadas no regresarán hasta que se lea una finalización de la CQ o ocurra un error o un tiempo de espera agotado.

Los hilos que se bloquean en esta función regresarán al llamador si son señalados por alguna fuente externa. Esto es cierto incluso si el tiempo de espera no ha ocurrido o se especificó como infinito.

Es inválido para las aplicaciones llamar a estas funciones si la CQ ha sido configurada con un objeto de espera de FI_WAIT_NONE o FI_WAIT_SET.

fi_cq_readerr

La función de lectura de errores, fi_cq_readerr, recupera información sobre cualquier operación asíncrona que haya completado con un error inesperado. fi_cq_readerr es una llamada no bloqueante, que regresa inmediatamente si se encontró una finalización de error o no.

La información de error se informa al usuario a través de la estructura fi_cq_err_entry. El formato de esta estructura se define a continuación.

struct fi_cq_err_entry {
    void     *op_context; /* contexto de la operación */
    uint64_t flags;       /* banderas de finalización */
    size_t   len;         /* tamaño de los datos recibidos */
    void     *buf;        /* búfer de datos de recepción */
    uint64_t data;        /* datos de finalización */
    uint64_t tag;         /* etiqueta del mensaje */
    size_t   olen;        /* longitud de desbordamiento */
    int      err;         /* código de error positivo */
    int      prov_errno;  /* código de error del proveedor */
    void    *err_data;    /* datos de error */
    size_t   err_data_size; /* tamaño de err_data */
    fi_addr_t src_addr; /* dirección de origen del error */
};

La razón general del error se proporciona a través del campo err. La información de error específica del proveedor también puede estar disponible a través de los campos prov_errno y err_data. Los usuarios pueden llamar a fi_cq_strerror para convertir la información de error específica del proveedor en una cadena imprimible para fines de depuración. Consulte los detalles de los campos a continuación para obtener más información sobre el uso de err_data y err_data_size.

Tenga en cuenta que se generan finalizaciones de error para todas las operaciones, incluidas aquellas para las que no se solicitó una finalización (por ejemplo, un punto final está c

configurado con FI_SELECTIVE_COMPLETION, pero la solicitud no tenía establecido el indicador FI_COMPLETION). En tales casos, los proveedores devolverán tanta información como la que pongan a disposición el software y el hardware subyacentes sobre el fallo; los demás campos se establecerán en NULL o 0. Esto incluye el valor de op_context, que puede no haberse proporcionado o haberse ignorado en la entrada como parte de la

transferencia.

SEMÁNTICA DE EVENTOS DE

FINALIZACIÓN

Libfabric define varios `niveles' de finalización, identificados mediante banderas operativas. Cada bandera indica el momento más pronto en que un proveedor puede generar un evento de finalización y las suposiciones que una aplicación puede hacer al procesar una finalización. Las banderas operativas se definen a continuación, junto con un ejemplo de cómo un proveedor podría implementar la semántica. Nótese que solo se requiere que el proveedor cumpla con la semántica, no con la implementación. Los proveedores pueden implementar semánticas de finalización más fuertes de las necesarias para una operación dada, pero solo se garantiza el comportamiento definido por el nivel de

finalización.

Para ayudar a comprender las diferencias conceptuales entre los niveles de finalización, considere el envío de una carta. Colocar la carta en el buzón local para su recogida es similar a `finalización de inyección'. Tener la carta recogida y depositada en el buzón de destino equivale a `finalización de transmisión'. La semántica de `finalización de entrega' es una garantía más fuerte, con una persona en el destino firmando por la carta. Sin embargo, la persona que firma por la carta no es necesariamente el destinatario previsto. La opción de `finalización de coincidencia' es similar a la finalización de entrega, pero requiere que el destinatario previsto firme por la

carta.

El nivel de `finalización de compromiso' tiene una semántica diferente a la de los niveles mencionados anteriormente. La finalización de compromiso sería más cercana a que la carta llegue al destino y sea colocada en una caja fuerte a prueba de

fuego.

Las banderas operativas para los niveles de finalización descritos se definen a

continuación.
FI_INJECT_COMPL
ETE
Indica que se debe generar una finalización cuando el(los) búfer(es) de origen pueda(n) ser re
utilizado(s). Una finalización garantiza que no se volverá a leer de los búferes y que la apl
icación puede reclamarlos. No se hacen otras garantías con respecto al estado de la operación.

Ejemplo: Un proveedor puede generar este evento de finalización después de copiar el búfer de origen en un búfer de red, ya sea en memoria del host o en la NIC. Una finalización de inyección no indica que los datos hayan sido transmitidos a la red, y podría ocurrir un error local después de que se haya generado el evento de finalización que podría impedir que se

transmita.

La finalización de inyección permite el informe de finalización más rápido (y, por lo tanto, la reutilización de búferes), pero proporciona las garantías más débiles contra los errores de

red.

Nota: Esta bandera se utiliza para controlar cuándo se inserta una entrada de finalización en una cola de finalización. No se aplica a operaciones que no generan una entrada de cola de finalización, como la operación `fi_inject`, y no está sujeta a la restricción del límite de mensaje

`inject_size`.

Para puntos de extremo

fiables:

definido.

Para puntos de extremo no

La semántica de finalización en el destino se utiliza para determinar cuándo los datos en el destino son visibles para la aplicación par. La visibilidad indica que una lectura de memoria en la misma dirección que fue el destino de una transferencia de datos devolverá los resultados de la transferencia. El destino de una transferencia puede ser identificado por el iniciador, como puede ser el caso para operaciones RMA y atómicas, o determinado por el destino, por ejemplo, al proporcionar un búfer de recepción coincidente. La visibilidad global indica que los resultados están disponibles independientemente de dónde se origine la lectura de memoria. Por ejemplo, la lectura podría provenir de un proceso que se ejecuta en una CPU del host, podría ser accedida por una transferencia de datos posterior a través de la tela, o leída de un dispositivo par como una

GPU.

En términos de semánticas de finalización, la visibilidad usualmente indica que la transferencia cumple los requisitos de FI_DELIVERY_COMPLETE desde la perspectiva del destino. La semántica de finalización en el destino puede estar, pero no necesariamente lo está, vinculada con la semántica de finalización especificada por el iniciador de la

transferencia.

A menudo, los procesos de destino no declaran explícitamente una semántica de finalización deseada y en su lugar dependen de la semántica predeterminada. El comportamiento predeterminado se basa en varios factores,

En términos generales, las semánticas de finalización en el destino se agrupan en función de si la transferencia genera o no un evento de finalización en el destino. En casos de uso comunes, las transferencias que utilizan una interfaz de mensaje (FI_MSG o FI_TAGGED) típicamente generan eventos en el destino, mientras que las transferencias que involucran una interfaz RMA (FI_RMA o FI_ATOMIC) a menudo no lo hacen. Hay excepciones para ambos casos, dependiendo de los enlaces de punto de extremo a CQ y contadores y las banderas operativas. DESCRIPTION

A completion queue (CQ) is a fabric object used to report the completion of operations initiated by the application or by the fabric provider.

The fabric interface defines two primary ways to create a completion queue:

•
Completion queues are typically created and associated with endpoints. When an endpoint is created, it may specify one or more completion queues to be used for reporting completions related to that endpoint. This is the most common mechanism for creating and associating completion queues.
•
Independent completion queues can be created using fi_cq_open or fi_cq_open_attr. These independent CQs can then be bound to one or more endpoints or other fabric objects using fi_cq_bind. This allows for more flexible sharing and management of completion queues.
The flags field of the fi_cq_attr structure controls how the completion queue is created and operates. Common flags include:

FI_ASYNC_COMPLETION
Indicates that the completion queue should support asynchronous notification mechanisms (e.g., eventfd, signals).
FI_SELECTIVE_COMPLETION
Indicates that the completion queue supports selective completion retrieval, allowing applications to filter completions based on certain criteria.
FI_COMPLETION_IF_POLL
Enables polling of the completion queue, where read operations will return immediately if no completions are available, rather than blocking.
FI_RESIZE
Indicates that the completion queue can be resized after creation.
FI_CLAIM
Allows an application to claim ownership of a completion queue, preventing other applications or threads from accessing it.

The fi_cq_attr structure contains attributes that define the behavior and characteristics of the completion queue, such as the number of entries, the completion entry format, and any associated event notification objects.

fi_cq_bind associates a completion queue with a fabric object, such as an endpoint, a counter, or another completion queue. The handle parameter specifies the object to which the CQ will be bound, and the flags parameter controls the binding behavior.

fi_cq_read and fi_cq_readfrom retrieve completions from the completion queue. The buf parameter points to a buffer where the completion entries will be stored, and the count parameter specifies the maximum number of entries to retrieve. fi_cq_readfrom supports additional flags to control the read operation.

fi_cq_sread and fi_cq_sreadfrom are synchronous read operations that block until a specified timeout expires or completions become available. The timeout parameter specifies the maximum time to wait for completions.

fi_cq_readerr retrieves error completions from the completion queue. Error completions represent failed operations and provide detailed error information.

fi_cq_err_set is a helper function to extract error information from a fi_cq_err structure.

fi_cq_strerror returns a human-readable string representation of a fabric error code.

fi_cq_signal triggers a completion event for the specified completion queue. This can be used to wake up threads waiting on the CQ or to signal that new completions are available.

fi_cq_control allows applications to perform control operations on the completion queue, such as enabling or disabling specific features or querying its status. The command and arg parameters specify the operation to be performed.

fi_cq_close closes and releases resources associated with the completion queue.

fi_cq_attr_get and fi_cq_attr_set retrieve and set the attributes of an existing completion queue, respectively.

The completion semantics and visibility of data are complex and depend on the flags used during operation posting and the capabilities of the fabric provider.

For operations that do not generate a completion event at the target, the visibility of the data at the target may need to be inferred based on subsequent operations that do generate target completions. Absent a target completion, when a completion of an operation is written at the initiator, the visibility semantic of the operation at the target aligns with the initiator completion semantic. For instance, if an RMA operation completes at the initiator as either FI_INJECT_COMPLETE or FI_TRANSMIT_COMPLETE, the data visibility at the target is not guaranteed.

One or more of the following mechanisms can be used by the target process to guarantee that the results of a data transfer that did not generate a completion at the target is now visible. This list is not inclusive of all options, but defines common uses. In the descriptions below, the first transfer does not result in a completion event at the target, but is eventually followed by a transfer which does.

•
If the endpoint guarantees message ordering between two transfers, the target completion of a second transfer will indicate that the data from the first transfer is available. For example, if the endpoint supports send after write ordering (FI_ORDER_SAW), then a receive completion corresponding to the send will indicate that the write data is available. This holds independent of the initiator’s completion semantic for either the write or send. When ordering is guaranteed, the second transfer can be queued with the provider immediately after queuing the first.
•
If the endpoint does not guarantee message ordering, the initiator must take additional steps to ensure visibility. If initiator requests FI_DELIVERY_COMPLETE semantics for the first operation, the initiator can wait for the operation to complete locally. Once the completion has been read, the target completion of a second transfer will indicate that the first transfer’s data is visible.
•
Alternatively, if message ordering is not guaranteed by the endpoint, the initiator can use the FI_FENCE and FI_DELIVERY_COMPLETE flags on the second data transfer to force the first transfers to meet the FI_DELIVERY_COMPLETE semantics. If the second transfer generates a completion at the target, that will indicate that the data is visible. Otherwise, a target completion for any transfer after the fenced operation will indicate that the data is visible.

The above semantics apply for transfers targeting traditional host memory buffers. However, the behavior may differ when device memory and/or persistent memory is involved (FI_HMEM and FI_PMEM capability bits). When heterogenous memory is involved, the concept of memory domains come into play. Memory domains identify the physical separation of memory, which may or may not be accessible through the same virtual address space. See the fi_mr(3) man page for further details on memory domains.

Completion ordering and data visibility are only well-defined for transfers that target the same memory domain. Applications need to be aware of ordering and visibility differences when transfers target different memory domains. Additionally, applications also need to be concerned with the memory domain that completions themselves are written and if it differs from the memory domain targeted by a transfer. In some situations, either the provider or application may need to call device specific APIs to synchronize or flush device memory caches in order to achieve the desired data visibility.

When heterogenous memory is in use, the default target completion semantic for transfers that generate a completion at the target is still FI_DELIVERY_COMPLETE, however, applications should be aware that there may be a negative impact on overall performance for providers to meet this requirement.

For example, a target process may be using a GPU to accelerate computations. A memory region mapping to memory on the GPU may be exposed to peers as either an RMA target or posted locally as a receive buffer. In this case, the application is concerned with two memory domains – system and GPU memory. Completions are written to system memory.

Continuing the example, a peer process sends a tagged message. That message is matched with the receive buffer located in GPU memory. The NIC copies the data from the network into the receive buffer and writes an entry into the completion queue. Note that both memory domains were accessed as part of this transfer. The message data was directed to the GPU memory, but the completion went to host memory. Because separate memory domains may not be synchronized with each other, it is possible for the host CPU to see and process the completion entry before the transfer to the GPU memory is visible to either the host GPU or even software running on the GPU. From the perspective of the provider, visibility of the completion does not imply visibility of data written to the GPU’s memory domain.

The default completion semantic at the target application for message operations is FI_DELIVERY_COMPLETE. An anticipated provider implementation in this situation is for the provider software running on the host CPU to intercept the CQ entry, detect that the data landed in heterogenous memory, and perform the necessary device synchronization or flush operation before reporting the completion up to the application. This ensures that the data is visible to CPU and GPU software prior to the application processing the completion.

In addition to the cost of provider software intercepting completions and checking if a transfer targeted heterogenous memory, device synchronization itself may impact performance. As a result, applications can request a lower completion semantic when posting receives. That indicates to the provider that the application will be responsible for handling any device specific flush operations that might be needed. See fi_msg(3) FLAGS.

For data transfers that do not generate a completion at the target, such as RMA or atomics, it is the responsibility of the application to ensure that all target buffers meet the necessary visibility requirements of the application. The previously mentioned bulleted methods for notifying the target that the data is visible may not be sufficient, as the provider software at the target could lack the context needed to ensure visibility. This implies that the application may need to call device synchronization/flush APIs directly.

For example, a peer application could perform several RMA writes that target GPU memory buffers. If the provider offloads RMA operations into the NIC, the provider software at the target will be unaware that the RMA operations have occurred. If the peer sends a message to the target application that indicates that the RMA operations are done, the application must ensure that the RMA data is visible to the host CPU or GPU prior to executing code that accesses the data. The target completion of having received the sent message is not sufficient, even if send-after-write ordering is supported.

Most target heterogenous memory completion semantics map to FI_TRANSMIT_COMPLETE or FI_DELIVERY_COMPLETE. Persistent memory (FI_PMEM capability), however, is often used with FI_COMMIT_COMPLETE semantics. Heterogenous completion concepts still apply.

For transfers flagged by the initiator with FI_COMMIT_COMPLETE, a completion at the target indicates that the results are visible and durable. For transfers targeting persistent memory, but using a different completion semantic at the initiator, the visibility at the target is similar to that described above. Durability is only associated with transfers marked with FI_COMMIT_COMPLETE.

For transfers targeting persistent memory that request FI_DELIVERY_COMPLETE, then a completion, at either the initiator or target, indicates that the data is visible. Visibility at the target can be conveyed using one of the above describe mechanism – generating a target completion, sending a message from the initiator, etc. Similarly, if the initiator requested FI_TRANSMIT_COMPLETE, then additional steps are needed to ensure visibility at the target. For example, the transfer can generate a completion at the target, which would indicate visibility, but not durability. The initiator can also follow the transfer with another operation that forces visibility, such as using FI_FENCE in conjunction with FI_DELIVERY_COMPLETE.

NOTES

A completion queue must be bound to at least one enabled endpoint before any operation such as fi_cq_read, fi_cq_readfrom, fi_cq_sread, fi_cq_sreadfrom etc. can be called on it.

If a completion queue has been overrun, it will be placed into an `overrun' state. Read operations will continue to return any valid, non-corrupted completions, if available. After all valid completions have been retrieved, any attempt to read the CQ will result in it returning an FI_EOVERRUN error event. Overrun completion queues are considered fatal and may not be used to report additional completions once the overrun occurs.
