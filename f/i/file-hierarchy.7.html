DESCRIPCIÓ

N

Los sistemas operativos que utilizan el systemd(1) gestor de sistema y servicios se organizan basándose en una jerarquía del sistema de archivos inspirada en UNIX, más específicamente la jerarquía descrita en la especificación File System Hierarchy[1] y hier(7), con varias extensiones, parcialmente documentadas en la XDG Base Directory Specification[2] y XDG User Directories[3]. Esta página de manual describe un subconjunto más generalizado, aunque mínimo y modernizado, de estas especificaciones que define de forma más estricta las sugerencias y restricciones que systemd hace sobre la jerarquía del sistema de archivos. Tenga en cuenta que este documento no intenta definir la estructura de directorios de manera exhaustiva, solo documenta un esqueleto de un árbol de directorios, que los proyectos derivados pueden extender. Debido a esto, directorios tradicionales como /usr/include/ o /var/spool/ no están cubiertos, aunque podría (o no) tener mucho sentido incluirlos en la estructura de un SO realmente

desplegado.

Muchas de las rutas descritas aquí se pueden consultar con la herramienta sy

stemd-p
ath(1).

ESTRUCTURA

GENERAL

/
La raíz del sistema de archivos. Generalmente escribible, pero esto no es requerido. Posiblemente un sistema de archivos temporal ("tmpfs"). No compartida con otros hosts (a menos que sea de solo lectura)
.

/boot

/
La partición de arranque utilizada para iniciar el sistema. En sistemas EFI, esta es posiblemente la Partición de Sistema EFI (ESP), véase también systemd-gpt-auto-generator(8). Este directorio suele ser estrictamente local al host, y debe considerarse de solo lectura, excepto cuando se instala un nuevo kernel o un cargador de arranque. Este directorio solo existe en sistemas que se ejecutan en hardware físico o emulado que requiere cargadores de
arranque.

/efi

/
Si la partición de arranque /boot/ se mantiene por separado de la Partición de Sistema EFI (ESP), esta última se monta aquí. Las herramientas que necesiten operar en la partición del sistema EFI deben buscarla primero en este punto de montaje, y recurrir a /boot/ — si la anterior no califica (por ejemplo, si no es un punto de montaje o no tiene el tipo de sistema de archivos correcto MSDOS_SUPER_M
AGIC).

/etc

/
Configuración específica del sistema. Este directorio puede o no ser de solo lectura. Frecuentemente, este directorio se pre-puebla con archivos de configuración proporcionados por el proveedor, pero las aplicaciones no deben hacer suposiciones sobre que este directorio esté completamente poblado o poblado en absoluto, y deben recurrir a valores predeterminados si falta la
configuración.

/home

/
La ubicación para los directorios de inicio de los usuarios normales. Posiblemente compartida con otros sistemas, y nunca de solo lectura. Este directorio solo debe usarse para usuarios normales, nunca para usuarios del sistema. Este directorio y posiblemente los directorios contenidos en él podrían solo estar disponibles o ser escribibles en el arranque tardío o incluso solo después de la autenticación del usuario. Este directorio podría estar ubicado en sistemas de archivos de red con funcionalidad limitada, por lo que las aplicaciones no deben asumir que el conjunto completo de la API de archivos está disponible en este directorio. Las aplicaciones generalmente no deben referenciar este directorio directamente, sino a través de la variable de entorno $HOME por usuario, o a través del campo del directorio de inicio de la base de datos de
usuarios.

/root

/
El directorio de inicio del usuario root. El directorio de inicio del usuario root está ubicado fuera de /home/ para asegurar que el usuario root pueda iniciar sesión incluso sin que /home/ esté disponible y
montado.

/srv

/
El lugar para almacenar la carga útil general del servidor, gestionada por el administrador. No se hacen restricciones sobre cómo se organiza internamente este directorio. Generalmente escribible, y posiblemente compartida entre sistemas. Este directorio podría estar disponible o ser escribible solo muy tarde durante el
arranque.

/tmp

/
El lugar para archivos temporales pequeños. Este directorio generalmente se monta como una instancia de "tmpfs", y por lo tanto no debe usarse para archivos más grandes. (Use /var/tmp/ para archivos más grandes.) Este directorio generalmente se vacía al arrancar. Además, los archivos a los que no se accede dentro de un cierto tiempo pueden ser eliminados automáticamente.

Si las aplicaciones encuentran la variable de entorno $TMPDIR definida, deben usar el directorio especificado en ella en lugar de /tmp/ (véase environ(7) y IEEE Std 1003.1[4] para más detalles)

.

Dado que /tmp/ es accesible para otros usuarios del sistema, es esencial que los archivos y subdirectorios bajo este directorio se creen solo con mkstemp(3), mkdtemp(3), y llamadas similares. Para más detalles, véase Using /tmp/ an

/run

/
Un sistema de archivos "tmpfs" para que los paquetes del sistema coloquen datos de tiempo de ejecución, archivos de socket, y similares. Este directorio se vacía al arrancar, y generalmente es escribible solo para programas privilegiados. Siempre
escribible.

/run/log

/
Registros del sistema en tiempo de ejecución. Los componentes del sistema pueden colocar registros privados en este directorio. Siempre escribible, incluso cuando /var/log/ podría no ser accesible
todavía.

/run/user

/
Contiene directorios de tiempo de ejecución por usuario, cada uno generalmente montado individualmente como instancias de "tmpfs". Siempre escribibles, vaciados en cada reinicio y cuando el usuario cierra sesión. El código del usuario no debe referenciar este directorio directamente, sino a través de la variable de entorno $XDG_RUNTIME_DIR, como se documenta en la XDG Base Directory
Specific

/usr

/
Recursos del sistema operativo proporcionados por el proveedor. Generalmente de solo lectura, pero esto no es requerido. Posiblemente compartida entre múltiples hosts. Este directorio no debe ser modificado por el administrador, excepto al instalar o eliminar paquetes proporcionados por el

No coloque bibliotecas públicas en este directorio, use $libdir (véase abajo), en su

DATOS DEL SISTEMA VARIABLES

PERSISTENTES

/var

/
Datos del sistema variables y persistentes. Escritura durante la operación normal del sistema. Este directorio podría estar pre-poblado con datos proporcionados por el proveedor, pero las aplicaciones deben poder reconstruir los archivos y directorios necesarios en esta subjerarquía si faltan, ya que el sistema podría iniciarse sin que este directorio esté poblado. Se recomienda la persistencia, pero es opcional, para soportar sistemas efímeros. Este directorio podría estar disponible o ser escribible solo muy tarde durante el arranque. Los componentes que se requieren para operar durante el arranque temprano, por lo tanto, no deben depender incondicionalmente de este
directorio.

/var/cache

/
Datos de caché persistentes del sistema. Los componentes del sistema pueden colocar datos no esenciales en este directorio. Vaciar este directorio no debería tener efecto en la operación de los programas, excepto por tiempos de ejecución aumentados necesarios para reconstruir estas
cachés.

/var/lib

/
Datos persistentes del sistema. Los componentes del sistema pueden colocar datos privados en este
directorio.

/var/log

/
Registros persistentes del sistema. Los componentes del sistema pueden colocar registros privados en este directorio, aunque se recomienda hacer la mayor parte del registro a través de las llamadas syslog(3) y sd_journal_pr
int(3).

/var/tmp

/
El lugar para archivos temporales más grandes y persistentes. En contraste con /tmp/, este directorio generalmente se monta desde un sistema de archivos físico persistente y por lo tanto puede aceptar archivos más grandes. (Use /tmp/ para archivos efímeros pequeños.) Este directorio generalmente no se vacía al arrancar, pero se aplica una limpieza basada en el tiempo de archivos que no han sido accedidos durante cierto tiempo.

Si las aplicaciones encuentran la variable de entorno $TMPDIR establecida, deberían usar el directorio especificado en ella en lugar de /var/tmp/ (ver environ(7) para detalles)

.

Se aplican las mismas restricciones de seguridad que con /tmp/: mkstemp(3), mkdtemp(3) y llamadas similares deberían usarse. Para más detalles sobre este directorio, ver Using /tmp/ and

SISTEMAS DE ARCHIVOS VIRTUALES DEL NÚCLEO Y

API

/dev

/
El directorio raíz para nodos de dispositivo. Usualmente, este directorio se monta como una instancia de "devtmpfs", pero podría ser de un tipo diferente en configuraciones encajonadas/contenedorizadas. Este directorio es gestionado conjuntamente por el núcleo y systemd-udevd(8), y no debería ser escrito por otros componentes. Un número de sistemas de archivos virtuales de propósito especial podrían montarse debajo de este
directorio.

/dev/shm

/
Lugar para segmentos de memoria compartida POSIX, como los creados a través de shm_open(3). Este directorio se vacía al arrancar, y es un sistema de archivos "tmpfs". Dado que todos los usuarios tienen acceso de escritura a este directorio, se debe tener especial cuidado para evitar choques de nombres y vulnerabilidades. Para usuarios normales, los segmentos de memoria compartida en este directorio son usualmente eliminados cuando el usuario cierra sesión. Usualmente, es una mejor idea usar archivos mapeados en memoria en /run/ (para programas del sistema) o $XDG_RUNTIME_DIR (para programas de usuario) en lugar de segmentos de memoria compartida POSIX, ya que estos directorios no son escribibles por todos y por lo tanto no son vulnerables a choques de nombres sensibles desde el punto de vista de
seguridad.

/proc

/
Un sistema de archivos virtual del núcleo que expone la lista de procesos y otra funcionalidad. Este sistema de archivos es mayormente una API para interactuar con el núcleo y no un lugar donde se puedan almacenar archivos normales. Para detalles, ver proc(5). Un número de sistemas de archivos virtuales de propósito especial podrían montarse debajo de este
directorio.

/proc/sys

/
Una jerarquía debajo de /proc/ que expone un número de ajustables del núcleo. La forma principal de configurar los ajustes en este árbol de archivos API es a través de archivos sysctl.d(5). En configuraciones encajonadas/contenedorizadas, este directorio generalmente se monta solo
lectura.

/sys

/
Un sistema de archivos virtual del núcleo que expone dispositivos descubiertos y otra funcionalidad. Este sistema de archivos es mayormente una API para interactuar con el núcleo y no un lugar donde se puedan almacenar archivos normales. En configuraciones encajonadas/contenedorizadas, este directorio generalmente se monta solo lectura. Un número de sistemas de archivos virtuales de propósito especial podrían montarse debajo de este
directorio.

/sys/fs/cgroup

/
Un sistema de archivos virtual del núcleo que expone grupos de control de procesos (cgroups). Este sistema de archivos es una API para interactuar con el núcleo y no un lugar donde se puedan almacenar archivos normales. En sistemas actuales que se ejecutan en el modo predeterminado "unificado", este directorio sirve c
omo punto de montaje para el sistema de archivos "cgroup2", que proporciona una jerarquía de cgroup unificada para todos los controladores de recursos. En sistemas con configuraciones no predeterminadas, este directorio podría en su lugar ser un sistema de archivos tmpfs que contiene puntos de montaje para varios contr
oladores de recursos "cgroup" (v1); en tales configuraciones, si "cgroup2" está montado, se montará en /sys/fs/cgroup/unified/, pero cgroup2 no tendrá controladores de recursos adjuntos. En configuraciones encajonadas/contenedorizadas, este directorio podría no existir o podría incluir un subconjunto de funcionalidad.

ACCESO DE

ESCRITURA

Acceso de escritura no

privilegiado

Los procesos no privilegiados generalmente carecen de acceso de escritura a la mayor parte de la

jerarquía.

Las excepciones para usuarios normales son /tmp/, /var/tmp/, /dev/shm/, así como el directorio de inicio $HOME (usualmente encontrado debajo de /home/) y el directorio de tiempo de ejecución $XDG_RUNTIME_DIR (encontrado debajo de /run/user/) del usuario, los cuales son todos

escribibles.

Para procesos del sistema no privilegiados, solo /tmp/, /var/tmp/ y /dev/shm/ son escribibles. Si un proceso del sistema no privilegiado necesita un directorio privado escribible en /var/ o /run/, se recomienda crearlo antes de perder privilegios en el código del demonio, crearlo a través de fragmentos tmpfiles.d(5) durante el arranque, o a través de las directivas StateDirectory= y RuntimeDirectory= de unidades de servicio (ver systemd.unit(5) para detalles)

.

/tmp/, /var/tmp/ y /dev/shm/ deberían montarse con nosuid y nodev, lo que significa que el modo set-user-id y carácter o bloque los dispositivos especiales no se interpretan en esos sistemas de archivos. En general, no es posible montarlos noexec, porque varios programas usan esos directorios para código generado dinámicamente o optimizado, y con esa bandera esos casos de uso se romperían. Usar esta bandera está bien en instalaciones de propósito especial o en sistemas donde todo el software que pueda instalarse es conocido y no requiere dicha funcionalidad.
