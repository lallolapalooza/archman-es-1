NOMBRE

fi_domain - Abrir un dominio de acceso a fabric

SINOPSIS

#include <rdma/fabric.h>
#include <rdma/fi_domain.h>
int fi_domain(struct fid_fabric *fabric, struct fi_info *info,
    struct fid_domain **domain, void *context);
int fi_domain2(struct fid_fabric *fabric, struct fi_info *info,
    struct fid_domain **domain, uint64_t flags, void *context);
int fi_close(struct fid *domain);
int fi_domain_bind(struct fid_domain *domain, struct fid *eq,
    uint64_t flags);
int fi_open_ops(struct fid *domain, const char *name, uint64_t flags,
    void **ops, void *context);
int fi_set_ops(struct fid *domain, const char *name, uint64_t flags,
    void *ops, void *context);

ARGUMENTOS

fabric
Dominio de fabric
info
Información del fabric, incluyendo las capacidades y atributos del dominio. La estructura fi_info debe haber sido obtenida usando fi_getinfo() o fi_dupinfo().
domain
Un dominio de acceso abierto.
context
Contexto especificado por el usuario asociado con el dominio. Este contexto se devuelve como parte de cualquier evento asíncrono asociado con el dominio.
eq
Cola de eventos para operaciones asíncronas iniciadas en el dominio.

Nombre asociado con una interfaz.
ops
Operaciones de interfaz de fabric.

DESCRIPCIÓN

Un dominio de acceso típicamente se refiere a una NIC física o virtual o a un puerto de hardware; sin embargo, un dominio puede abarcar varios componentes de hardware para fines de fail-over o striping de datos. Un dominio define el límite para asociar diferentes recursos juntos. Los recursos de fabric que pertenecen al mismo dominio pueden compartir recursos.

fi_domain

Abre un dominio de acceso a fabric, también conocido como dominio de recursos. Los dominios de fabric se identifican por un nombre. Las propiedades del dominio abierto se especifican usando el parámetro info.

fi_domain2

Similar a fi_domain, pero acepta un parámetro adicional flags. Se usa principalmente para abrir un dominio par. Ver fi_peer(3).

fi_open_ops

fi_open_ops se utiliza para abrir interfaces específicas del proveedor. Las interfaces del proveedor pueden usarse para acceder a recursos y operaciones de bajo nivel que son específicas del dominio de recursos abierto. Los detalles de las interfaces de dominio están fuera del alcance de esta documentación.

fi_set_ops

fi_set_ops asigna callbacks que un proveedor debe invocar en lugar de realizar tareas seleccionadas. Esto permite a los usuarios modificar o controlar el comportamiento predeterminado de un proveedor. Conceptualmente, permite al usuario enganchar funciones específicas utilizadas por un proveedor y reemplazarlas con las suyas.

Las operaciones que se modifican se identifican usando una cadena de caracteres bien conocida, pasada como parámetro name. El formato del parámetro ops depende del valor de name. El parámetro ops hará referencia a una estructura que contiene los callbacks y otros campos necesarios para que el proveedor invoque las funciones del usuario.

Si un proveedor acepta la anulación, devolverá FI_SUCCESS. Si la anulación es desconocida o no es compatible, el proveedor devolverá -FI_ENOSYS. Las anulaciones deben establecerse antes de asignar recursos en el dominio.

Las siguientes operaciones de fi_set_ops y sus estructuras de callback correspondientes están definidas.

FI_SET_OPS_HMEM_OVERRIDE – Anulaciones de Memoria Heterogénea

La anulación HMEM permite a los usuarios anular las operaciones relacionadas con HMEM que un proveedor pueda realizar. Actualmente, el alcance de la anulación HMEM es permitir a un usuario definir las funciones de movimiento de memoria que un proveedor debe usar al acceder a un buffer de usuario. Las funciones de movimiento de memoria definidas por el usuario necesitan tener en cuenta todos los diferentes tipos de interfaz HMEM que un proveedor pueda encontrar.

Todos los objetos asignados contra un dominio heredarán esta anulación.

El siguiente es el nombre de la operación de anulación HMEM y su estructura.

#define FI_SET_OPS_HMEM_OVERRIDE "hmem_override_ops"
struct fi_hmem_override_ops {
    size_t  size;
    ssize_t (*copy_from_hmem_iov)(void *dest, size_t size,
        enum fi_hmem_iface iface, uint64_t device, const struct iovec *hmem_iov,
        size_t hmem_iov_count, uint64_t hmem_iov_offset);
    ssize_t (*copy_to_hmem_iov)(enum fi_hmem_iface iface, uint64_t device,
    const struct iovec *hmem_iov, size_t hmem_iov_count,
        uint64_t hmem_iov_offset, const void *src, size_t size);
};

Todos los campos de la estructura fi_hmem_override_ops deben estar establecidos (no nulos) a un valor válido.

size
Esto debe establecerse al sizeof(struct fi_hmem_override_ops). El campo size se utiliza para fines de compatibilidad hacia adelante y hacia atrás.
copy_from_hmem_iov
Copia datos del dispositivo/hmem a la memoria del host. Esta función debe devolver un fi_errno negativo en caso de error, o el número de bytes copiados en caso de éxito.
copy_to_hmem_iov
Copia datos de la memoria del host al dispositivo/hmem. Esta función debe devolver un fi_errno negativo en caso de error, o el número de bytes copiados en caso de éxito.

fi_domain_bind

Asocia una cola de eventos con el dominio. Una cola de eventos vinculada a un dominio será la EQ predeterminada asociada con eventos de control asíncronos que ocurran en el dominio o en endpoints activos asignados en un dominio. Esto incluye eventos CM. Los endpoints pueden dirigir sus eventos de control a EQs alternativas vinculándose directamente con la EQ.

Obsoleto: Vincular una cola de eventos a un dominio con la bandera FI_REG_MR indica que el proveedor debe realizar todas las operaciones de registro de memoria de forma asíncrona, con la finalización informada a través de la cola de eventos. Si no se vincula una cola de eventos al dominio con la bandera FI_REG_MR, las solicitudes de registro de memoria se completan de forma síncrona.

fi_close

La llamada fi_close se utiliza para liberar todos los recursos asociados con un dominio o interfaz. Todos los objetos asociados con el dominio abierto deben liberarse antes de llamar a fi_close, de lo contrario, la llamada devolverá -FI_EBUSY.

Soporte de multihilo

(threading)

El modelo de hilos especifica el nivel de serialización requerido de una aplicación al usar las interfaces de transferencia de datos de libfabric. Las interfaces de control siempre se consideran seguras para hilos, a menos que el modelo de progreso de control sea FI_PROGRESS_CONTROL_UNIFIED. Una interfaz de control segura para hilos permite que múltiples hilos hagan progreso en la interfaz de control y (dependiendo del modelo de hilos seleccionado) que uno o más hilos hagan progreso en las interfaces de datos al mismo tiempo. Las aplicaciones que pueden garantizar la serialización en su acceso a los recursos e interfaces asignados por el proveedor permiten que este elimine bloqueos de nivel

inferior.
FI_THREAD_COMPLET
ION
El modelo de hilos de finalización es el más adecuado para aplicaciones multihilo que usan puntos finales escalables y desean una operación sin bloqueos. La
s aplicaciones deben serializar el acceso a todos los objetos que están asociados por un mecanismo de finalización común (por ejemplo, contextos de transmisi
ón y recepción vinculados a la misma CQ o contador). Se recomienda que los proveedores que soportan puntos finales escalables soporten este modelo de hilos.

Las aplicaciones que deseen aprovechar FI_THREAD_COMPLETION deben dedicar contextos de transmisión, contextos de recepción, colas de finalización y contadores a hilos

individuales.
FI_THREAD_DOM
AIN
El modelo de hilos de dominio es el más adecuado para aplicaciones de un solo hilo y aplicaciones multihilo que usan puntos finales estándar y desean una operación sin bloqueos. Las aplicaciones deben serializar el acceso a todos los objetos bajo el mismo dominio. Esto incluye puntos finales, contextos de transmisión y recepción, colas de finalización y contadores, y regiones de memoria
registradas.
FI_THREAD_ENDPOINT
(obsoleto)
El modelo de hilos de punto final es similar a FI_THREAD_FID, pero con la restricción añadida de que se requiere serialización al acceder al mismo punto final, incluso si se usan múltiples contextos de transmisión y
recepción.
FI_THREAD_FID
(obsoleto)
Un modelo de serialización de descriptor de tejido (FID) requiere que las aplicaciones serialicen el acceso a los recursos individuales del tejido asociados con operaciones de transferencia de datos y finalizaciones. Para el acceso al punto final, la serialización solo se requiere al acceder al mismo flujo de datos del punto final. Múltiples hilos pueden iniciar transferencias en diferentes contextos de transmisión o el mismo punto final sin serializar, y no se requiere serialización entre el envío de solicitudes de transmisión de datos y las operaciones de recepción de
datos.

Un modelo de serialización seguro para hilos permite que una aplicación multihilo acceda a cualquier recurso asignado a través de cualquier interfaz sin restricciones. Se requiere que todos los proveedores soporten
FI_THREAD_SAFE.

Modelos de progreso

(progress)

El progreso es la capacidad de la implementación subyacente para completar el procesamiento de una solicitud asíncrona. En muchos casos, el procesamiento de una solicitud asíncrona requiere el uso del procesador del host. Por ejemplo, un mensaje recibido puede necesitar ser emparejado con el búfer correcto, o una solicitud que ha agotado el tiempo de espera puede necesitar ser retransmitida. Por razones de rendimiento, puede ser indeseable que el proveedor asigne un hilo para este propósito, ya que competiría con los hilos de la

aplicación.

El progreso de control indica el método que usa el proveedor para avanzar en operaciones de control asíncronas. Las operaciones de control son funciones que no involucran directamente la transferencia de datos de la aplicación entre puntos finales. Incluyen rutinas de vector de direcciones, registro de memoria y gestión de

conexiones.

El progreso de datos indica el método que usa el proveedor para avanzar en operaciones de transferencia de datos. Esto incluye cola de mensajes, RMA, mensajaje etiquetada y operaciones atómicas, junto con su procesamiento de

finalización.

El campo de progreso define el comportamiento tanto de las operaciones de control como de las de datos. Para las aplicaciones que requieren portabilidad de compilación entre las series de libfabric versión 1 y versión 2, el campo de progreso puede referenciarse como

data_progress.

El progreso frecuentemente requiere que se tome acción tanto en el lado de transmisión como en el de recepción de una operación. Esto es a menudo un requisito para transferencias fiables, como resultado del procesamiento de reintentos y acuses de

recibo.

Para equilibrar entre el rendimiento y la facilidad de uso, se definen los siguientes modelos de

progreso.
FI_PROGRESS_A
UTO
Este modelo de progreso indica que el proveedor hará progreso en una operación asíncrona sin mayor intervención de la aplicación
. Cuando FI_PROGRESS_AUTO se proporciona como salida de fi_getinfo en ausencia de cualquier sugerencia de progreso, a menudo indi
ca que la funcionalidad deseada está implementada por el hardware del proveedor o es un servicio estándar del sistema operativo.

Se recomienda que los proveedores soporten FI_PROGRESS_AUTO. Sin embargo, si un proveedor no soporta nativamente el progreso automático, forzar el uso de FI_PROGRESS_AUTO puede resultar en la asignación de hilos por debajo de las interfaces de

tejido.

Tenga en cuenta que las versiones anteriores de la biblioteca requerían que los proveedores soportaran FI_PROGRESS_AUTO. Sin embargo, en algunos casos los hilos de progreso no pueden bloquearse cuando la comunicación está inactiva, lo que resulta en hilos girando en funciones de progreso. Como resultado, esos proveedores solo soportaban FI_PROGRESS_MANUAL

.
FI_PROGRESS_MAN
UAL
Este modelo de progreso indica que el proveedor requiere el uso de un hilo de la aplicación para completar una solicitud asíncrona. Cuando se establece el progreso manual,
el proveedor intentará avanzar una operación asíncrona cuando la aplicación intente esperar o leer una cola de eventos, cola de finalización o contador donde se reportará
la operación completada. El progreso también ocurre cuando la aplicación procesa un conjunto de sondeo o espera que ha sido asociado con la cola de eventos o finalización.

Solo las operaciones de espera definidas por la interfaz de tejido resultarán en que una operación avance. Las funciones de espera del sistema operativo o externas, como select, poll o rutinas de pthread, no lo

harán.

Los requisitos de progreso manual no solo se aplican a los puntos finales que inician operaciones de transmisión, sino también a los puntos finales que pueden ser el destino de tales operaciones. Esto se mantiene cierto incluso si el punto final destino no generará eventos de finalización para las operaciones. Por ejemplo, un punto final que actúa puramente como destino de operaciones RMA o atómicas que usa progreso manual puede aún necesitar asistencia de la aplicación para procesar las operaciones

recibidas.
FI_PROGRESS_CONTROL_UNIF
IED
Este modelo de progreso indica que el usuario sincronizará el progreso de las operaciones de datos y control ellos mismos (es decir, esto permite que la interfaz de control NO sea segura para hilos). Implica progreso manual, y cuando se combina con threading=FI_THREAD_DOMAIN/FI_THREAD_COMPLETION permite a Libfabric eliminar todo el bloqueo en la ruta crítica de progreso de
datos.

Gestión de recursos

(resource_mgmt)

La gestión de recursos (RM) es el soporte del proveedor y del protocolo para proteger contra el desbordamiento de recursos locales y remotos. Esto incluye contextos de transmisión y recepción locales y remotos, colas de finalización, y búferes de datos de origen y

destino.

Cuando está habilitada, las aplicaciones reciben cierto nivel de protección contra el desbordamiento de colas del proveedor y búferes de datos locales y remotos. Tal soporte puede estar integrado directamente en el hardware y/o protocolo de red, pero también puede requerir que se habiliten verificaciones en el software del proveedor. Al deshabilitar la gestión de recursos, una aplicación asume toda la responsabilidad de prevenir el desbordamiento de colas y búferes, pero hacerlo puede permitir que un proveedor elimine llamadas de sincronización internas, como variables atómicas o

bloqueos.

Debe señalarse que incluso si la gestión de recursos está deshabilitada, la implementación del proveedor y el protocolo aún pueden proporcionar cierto nivel de protección contra desbordamientos. Sin embargo, dicha protección no está garantizada. Se definen los siguientes valores para la gestión de

recursos.
FI_RM_DISABL
ED
El proveedor es libre de seleccionar una implementación y un protocolo que no proteja contra el desbordamiento de recursos. La aplicación es responsable de la protección de
recursos.
FI_RM_ENABL
ED
La gestión de recursos está habilitada para este dominio del
proveedor.
FI_RM_UNSP
EC
Este valor indica que no se ha definido ningún m
odelo de gestión de recursos. Puede usarse en su
gerencias de entrada para la llamada fi_getinfo.

EP destino se refiere a los recursos asociados con el punto final que es el destino de una operación de transmisión. Esto incluye la cola de recepción del punto final destino, los búferes de recepción publicados (sin búferes Rx), la cola de finalización del lado de recepción y otras colas de procesamiento de paquetes relacionadas. El comportamiento definido es el que ve el iniciador de una solicitud. Para los puntos finales FI_EP_DGRAM, si las colas del EP destino no pueden aceptar mensajes entrantes, los mensajes recibidos se descartarán. Para los puntos finales confiables, si RM está deshabilitado, la operación de transmisión se completará con error. Un proveedor puede optar por devolver una finalización de error con el código de error FI_ENORX para esa operación de transmisión para que pueda reintentarse. Si RM está habilitado, el proveedor reintentará internamente la

Desbordamiento de búfer
Rx
Esto se refiere a los búferes publicados para recibir mensajes etiquetados o no etiquetados entrantes, con el comportamiento definido desde el punto de vista del emisor. El comportamiento para manejar mensajes recibidos que son más grandes que los búferes proporcionados por la aplicación es específico del proveedor. Los proveedores pueden truncar el mensaje y reportar una finalización exitosa, o fallar la operación. Para los puntos finales de datagrama, los envíos fallidos resultarán en que el mensaje sea descartado. Para los puntos finales confiables, las operaciones de envío pueden completarse con éxito, aunque serán truncadas en el lado de recepción. Esto puede ocurrir cuando el lado destino almacena datos recibidos hasta que un búfer de aplicación esté disponible. arios incluyen no hay ruta hacia el host o tarjeta NIC destino caída. Para los puntos finales FI_EP_DGRAM, las operaciones de transmisión dirigidas a un punto fina
l inaccesible tendrán la operación descartada. Para FI_EP_RDM, las operaciones destino dirigidas a un punto final inaccesible resultarán en un error de transmisión.

Cuando ocurre un error de gestión de recursos en un punto final conectado, el punto final transicionará a un estado deshabilitado y la conexión se cortará. Un punto final deshabilitado descartará cualquier operación en cola o en

vuelo.

El comportamiento de los errores de gestión de recursos en los puntos finales sin conexión depende del tipo de error. Si RM está deshabilitado y ocurre uno de los siguientes errores, el punto final será deshabilitado: Ctx Tx, Ctx Rx, CQ Tx o CQ Rx. Para otros errores (EP destino, sin búfer Rx, etc.), la operación puede fallar, pero el punto final permanecerá habilitado. Un punto final deshabilitado descartará o fallará cualquier operación en cola o en vuelo. Además, un punto final deshabilitado debe ser rehabilitado antes de que acepte nuevas operaciones de transferencia de

datos.

Hay una restricción notable en las protecciones ofrecidas por la gestión de recursos. Esto ocurre cuando la gestión de recursos está habilitada en un punto final que ha sido vinculado a cola(s) de finalización usando el indicador FI_SELECTIVE_COMPLETION. Las operaciones enviadas a dicho punto final pueden especificar que una finalización exitosa no debe gene

rar una entrada en la cola de finalización correspondiente. (Es decir, la operación deja el indicador FI_COMPLETION sin establecer). En tales situaciones, el proveedor no está obligado a reservar una entrada en la cola de finalización para manejar el caso en que la operación falla y sí genera una entrada en la CQ, lo que requeriría efectivamente rastrear la
operación hasta su finalización. Las aplicaciones interesadas en evitar desbordamientos de la CQ en la ocurrencia de errores deben asegurarse de que haya espacio suficiente en la CQ para reportar operaciones fallidas. Esto generalmente se puede lograr dimensionando la CQ al menos al mismo tamaño que la(s) cola(s) del punto final que están vinculadas a ella.
