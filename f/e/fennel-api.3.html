DESCRIPCIÓ

N

El módulo fennel proporciona las siguientes funciones para usar al incrustar Fennel en un programa Lua. Si estás escribiendo un programa puro en Fennel o trabajando en un sistema que ya tiene soporte de Fennel, probablemente no necesites

esto.

Solo el módulo fennel es parte de la API pública. Los otros módulos son detalles de implementación sujetos a cambios. La mayoría de las funciones generarán un error en caso de

fallo.

Cada vez que una función toma un argumento de tabla de opciones , esa tabla generalmente aceptará estos

campos:
•
allowedGlobals: una tabla secuencial de cadenas con los nombres de los globales a los que el compilador permitirá referencias. Establece a false para desactivar las comprobaciones. Por defecto es el contenido de la tabla env, si se proporciona, o el entorno
actual.
•
correlate: cuando está activado, Fennel intenta emitir Lua donde los números de línea coincidan con el código de entrada de Fennel; útil en situaciones donde código que no está bajo tu control imprimirá los rastros de la pila. Está pensado como una ayuda para la depuración y no puede dar números exactos en todos los
casos.
•
useMetadata: habilita o deshabilita los metadatos, permitiendo el uso del comando ,doc de la REPL. Destinado a propósitos de desarrollo (ver nota de rendimiento); por defecto es true solo para la
REPL.
•
requireAsInclude: Aliasar cualquier llamada estática a require con el especial include, incrustando el código del módulo en línea en la salida compilada. Si el nombre del módulo no es un literal de cadena que sea resoluble en tiempo de compilación, recurre a require en tiempo de ejecución. Puede usarse para incrustar tanto módulos Fennel como
Lua.
•
toBeClosed: Usar variables de cierre pendiente de Lua 5.4+ al compilar with-open para evitar interferir con las
trazas.
•
assertAsRepl: Reemplazar las llamadas a assert con assert-repl para permitir la depuración
interactiva.
•
lambdaAsFn: Reemplazar las definiciones de funciones lambda con fn
.
•
env: una tabla de entorno en la que ejecutar el código; ver el manual de
Lua.
•
compilerEnv: una tabla de entorno en la que ejecutar código con ámbito de compilador para definiciones de macros y llamadas a eval-compiler. Las funciones internas de Fennel como list, sym, etc. se expondrán además de esta tabla. Por defecto es una tabla que contiene globales conocidos y seguros limitados. Pasa _G para desactivar el
sandboxing.
•
unfriendly: deshabilitar los mensajes de error amigables del compilador/pars
er.
•
plugins: lista de plugins del
compilador.
•
error-pinpoint: una lista de dos cadenas que indican en qué envolver los errores de
compilación.
•
keywords: una tabla de la forma {:keyword1 true :keyword2 true} que contiene símbolos que deben tratarse como palabras clave reservadas de
Lua.
•
global-mangle: si transformar (manglear) los globales en la salida del compilador; establece a false para convertir las referencias a globales que no sean Lua válido en _G['hello
-worl
d'].

Puedes pasar la cadena "_COMPILER" como valor para env; hará que el código se ejecute/compile en un contexto que tenga disponibles todos los valores con ámbito de compilador. Esto puede ser útil para módulos de macros o plugins del compilador. Si quieres añadir valores adicionales al entorno en este caso, puedes usar la clave extra-env. También puedes usar extra-compiler-env para añadir campos al entorno del compilador usado para las

macros.

Ten en cuenta que solo el módulo fennel es parte de la API pública. Los otros módulos (fennel.utils, fennel.compiler, etc) deben considerarse internos del compilador y sujetos a

cambios.

Si estás incrustando Fennel en un contexto donde los códigos de escape ANSI no se interpretan, puedes establecer error-pinpoint a false para desactivar el resaltado de errores

de compilación y d

DEFINICIÓN DE NODOS

AST

El AST devuelto por el analizador consiste en estructuras de datos que representan el código. Pasar nodos AST a la función fennel.view te dará una cadena que debería pasar por el analizador para devolverte los mismos datos. Lo mismo es cierto con tostring, excepto que no funciona con tablas que no son

secuencias.

La función fennel.ast-source toma un nodo AST y devuelve una tabla con datos de origen alrededor del nombre de archivo, número de línea, etc., si es posible. Algunos nodos AST no pueden proporcionar estos datos, por ejemplo números, cadenas y booleanos, o símbolos construidos dentro de macros usando la función sym en lugar de la comilla

invertida.

Los nodos AST pueden ser cualquiera de estos

tipos:

lis

t

Una lista representa una llamada a una función/macro, o la desestructuración de múltiples valores de retorno en un contexto de enlace. Se representa como una tabla que se puede identificar usando la función predicado fennel.list? o construir usando fennel.list que toma cualquier número de argumentos para los contenidos de la

lista.

Ten en cuenta que las listas son construcciones en tiempo de compilación en Fennel. No existen en tiempo de ejecución, excepto en casos en los que el compilador se usa en tiempo de

ejecución.

La lista también contiene estas claves que indican dónde fue definida: filename, line, col, endcol, bytestart, y byteend. Estos datos se usan para trazas de pila y para localizar mensajes de error del compilador. Ten en cuenta que los números de columna se basan en el

recuento de caracteres, lo cual no siempre corresponde a las columnas visual
es; por ejemplo "วัด" son tres caracteres pero solo dos columnas visuales.

tabla de secuencia/clave-valo

r

Estos son literales de tabla en el código Fennel producidos por corchetes (secuencias) o llaves (tablas k/v). Las secuencias se pueden identificar usando la función fennel.sequence? y construir usando fennel.sequence. No hay predicado ni constructor para tablas k/v; se asume que cualquier tabla que no sea de los otros tipos es una de

estas.

En tiempo de ejecución no hay diferencia entre secuencias y tablas k/v que usan claves monótonaslly increasing integer keys, but the parser is able to distinguish between them to improve error

reporting.

Sequences and k/v tables have their source data in filename, line, etc keys of their metatable. The metatable for k/v tables also includes a keys sequence which tells you which order the keys appeared originally, since k/v tabl

es are unordered and there would otherwi
se be no way to reconstruct this information.

symbo

l

Symbols typically represent identifiers in Fennel code. Symbols can be identified with fennel.sym? and constructed with fennel.sym which takes a string name as its first argument and a source data table as the second. Symbols are represented as tables which store their source data (filename, line, col, etc) in fields on themselves. Unlike the other tables in the AST, they do not represent collections; they are used as scalar

types.

Symbols can refer not just directly to locals, but also to table references like tbl.x for field lookup or access.channel:deny for method invocation. The fennel.multi-sym? function will return a table containing the segments if the symbol if it is one of these, or nil

otherwise.

Note: nil is not a valid AST; code that references nil will have the symbol named "nil" which unfortunately prints in a way that is visually indistinguishable from actual nil

.

The fennel.sym-char? function will tell you if a given c

haracter is allowed to be u
sed in the name of a symbol.

varar

g

This is a special type of symbol-like construct (...) indicating functions using a variable number of arguments. Its meaning is the same as in Lua. It's identified with fennel.varg? and constructed with fennel

.va
rg.

number/string/boolea

n

These are literal types d

efined by Lua. They cann
ot carry source data.

commen

t

By default, ASTs will omit comments. However, when the :comment field is set in the parser options, comments will be included in the parsed values. They are identified using fennel.comment? and constructed using the fennel.comment function. They are represented as tables that have source data as fields inside

them.

In most data contexts, comments just get included inline in a list or sequence. However, in a k/v table, this cannot be done, because k/v tables must have balanced key/value pairs, and including comments inline would imbalance these or cause keys to be considered as values and vice versa. So the comments are stored on the comments field of metatable inst

ead, keyed by the k
ey or value they w

SERIALIZATION

(VIEW)

The fennel.view function takes any Fennel data and turns it into a representation suitable for feeding back to Fennel's parser. In addition to tables, strings, numbers, and booleans, it can produce reasonable output from ASTs that come from the parser. It will emit an unreadable placeholder for coroutines, compiled functions, and userdata, which cannot be understood by the

parser.

.view({abc=12
3}[, options]
) {:abc 123}

accepted:

one-liner
•

go
•

view

All options can be set to {:once some-value} to force their value to be some-value but only for the current level. After that, such option is reset to its default value. Alternatively, {:once value :after other-value} can be used, with the difference that after first use, the options will be set to other-value instead of the default

value.

You can set a __fennelview metamethod on a table to override its serialization behavior. It should take the table being serialized as its first argument, a function as its second argument, options table as third argument, and current amount of indentation as its last

argument: 
(fn [t view options indent]
..
.
)

view function contains a pretty printer that can be used to serialize elements stored within the table being serialized. If your metamethod produces indented representation, you should pass indent parameter to view increased by the amount of additional indentation you've introduced. This function has the same interface as __fennelview metamethod, but in addition accepts colon-string? as last argument. If colon? is true, strings will be printed as colon-strings when possible, and if its value is false, strings will be always printed in double quotes. If omitted or nil will default to value of :prefer-colon?

option.

options table contains options described above, and also visible-cycle? function, that takes a table being serialized, detects and saves information about possible reachable cycle. Should be used in __fennelview to implement cycle

detection.

__fennelview metamethod should always return a table of correctly indented lines when producing multi-line output, or a string when always returning single-line item. fennel.view will transform your data structure to correct multi-line representation when needed. There's no need to concatenate table manually ever - fennel.view will apply general rules for your data structure, depending on current options. By default multiline output is produced only when inner data structures contains newlines, or when returning table of lines as single line results in width greater than line-size o

ption.

Multi-line representation can be forced by returning two values from __fennelview - a table of indented lines as first value, and true as second value, indicating that multi-line representation should be

forced.

There's no need to incorporate indentation beyond needed to correctly align elements within the printed representation of your data structure. For example, if you want to print a multi-line table, like

this: 
@my-table
[1
2
3]

__fennelview should return a sequence of

lines: 
["@my-table[
1" "
2" "
3]"]

Note, since we've introduced inner indent string of length 10, when calling view function from within __fennelview metamethod, in order to keep inner tables indented correctly, indent must be increased by this amount of extra

indentation.

Here's an implementation of such pretty-printer for an arbitrary sequential

table: 
(fn pp-doc-example [t view options indent]
  (let [lines (icollect [i v (ipairs t)]
                (let [v (view v options (+ 10 indent))]
                  (if (= i 1) v
                      (.. "          " v))))]
    (doto lines
      (tset 1 (.. "@my-table[" (or (. lines 1) "")))
      (tset (length lines) (.. (. lines (length lines)) "]
")))
)
)

Estableciendo el método metamethod __fennelview de la tabla a esta función proporcionará resultados correctos independientemente del

anidamiento: 
>> {:my-table (setmetatable [[1 2 3 4 5]
                             {:smalls [6 7 8 9 10 11 12]
                              :bigs [500 1000 2000 3000 4000]}]
                            {:__fennelview pp-doc-example})
    :normal-table [{:c [1 2 3] :d :some-data} 4]}
{:my-table @my-table[[1 2 3 4 5]
                     {:bigs [500 1000 2000 3000 4000]
                      :smalls [6 7 8 9 10 11 12]}]

4]
}

Observa que aunque solo hemos sangrado los elementos internos de nuestra tabla con 10 espacios, el resultado está correctamente sangrado en términos de la tabla externa, y las tablas internas también permanecen correctamente

sangradas.

Al usar la opción :preprocess o el método __fennelview, evita modificar ninguna tabla in-place en la función pasada. Dado que las tablas de Lua son mutables y se pasan sin copiar, cualquier modificación hecha en estas funciones será visible fuera de fennel.v

iew.

Usar :byte-escape para anular el formato de escape de caracteres especiales está destinado a casos de uso donde se sabe que la salida será consumida por algo que no sea Lua/Fennel, y puede resultar en una salida que Fennel ya no pueda analizar. Por ejemplo, para forzar el uso de escapes

hexadecimales: 
(print (fennel.view {:clear-screen "\
027[H\027[2J"} {:
byte-escape #(: "\\x%2x" :format $)}))
;; > {:clear-screen "\x1b[H\x1b[2J"}

Aunque Lua 5.2+ soporta escapes hexadecimales, PUC Lua 5.1

no, así que compilar esto con Fennel más adelante re
sultaría en un código de escape incorrecto en Lua 5.1.

TRABAJAR CON DOCSTRINGS Y

METADATOS

Al ejecutar un REPL o usar compile/eval con metadatos habilitados, cada función declarada con fn o λ/lambda usará la función creada como una clave en fennel.metadata para almacenar el arglist de la función y (si se proporciona) el docstring. La tabla de metadatos tiene referencias débiles por clave, por lo que los metadatos de cada función serán recolectados por el recolector de basura junto con la función

misma.

Puedes trabajar con la API para ver o modificar estos metadatos tú mismo, o usar el comando ,doc del repl para ver la documentación de las

funciones.

Además del acceso directo a las tablas de metadatos, puedes usar los siguientes

métodos:
•
fennel.metadata:get(func, key): obtener un valor de los metadatos de una
función
•
fennel.metadata:set(func, key, val): establecer un valor de
metadatos
•
fennel.metadata:setall(func, key1, val1, key2, val2, ...): establecer
pares
•
fennel.doc(func, fnName): imprimir la documentación formateada de la función usando el nombre. Utilizado por el comando ,doc, el nombre es cualquier símbolo con el que operes que esté vinculado a la
función. 
local greet = fennel.eval('(λ greet [name] "Say hello" (print "Hello," name))',
                          {useMetadata = true})

PLUGIN

S

El sistema de plugins de Fennel es extremadamente experimental y expone los internos del compilador de maneras que ninguna otra parte del compilador lo hace. Debe considerarse inestable; los cambios en el compilador en futuras versiones probablemente romperán los plugins, y cada plugin solo debe asumirse que funciona con versiones específicas del compilador con las que fue probado. Las garantías de compatibilidad hacia atrás del resto de Fennel no se aplican a los

plugins.

Los plugins del compilador permiten que la funcionalidad del compilador sea extendida de varias maneras. Un plugin es un módulo que contiene varias funciones en campos nombrados después de diferentes puntos de extensión del compilador. Cuando el compilador alcanza un punto de extensión, llamará a la función de cada plugin para ese punto de extensión, si está proporcionada, con varios argumentos; usualmente el AST en cuestión y la tabla de ámbito. Cada función de plugin normalmente debe hacer efectos secundarios y devolver nil o generar un error. Si una función devuelve algo que no es nil, hará que el resto de los plugins para un evento dado sean

omitidos.

NAME

fennel-api - Fennel language API

DESCRIPTION

This document describes the Fennel API, including functions for compilation, REPL interaction, and more.

START A CONFIGURABLE REPL

You can start a configurable REPL by running the following command:

$ fennel

This will launch an interactive Fennel environment where you can evaluate Fennel code directly.

EVALUATE A STRING OF FENNEL

The fennel.eval function can be used to evaluate a string containing Fennel code.

(fennel.eval "(+ 1 2)")

This will return the result of the evaluation, which in this case is 3.

EVALUATE A FILE OF FENNEL

To evaluate a file containing Fennel code, you can use the fennel.load function.

(fennel.load "path/to/your/file.fnl")

This will load and execute the Fennel code from the specified file.

USE LUA'S BUILT-IN REQUIRE FUNCTION

Fennel seamlessly integrates with Lua's module system. You can use Lua's require function within your Fennel code to load Lua modules.

(local json (require :json))
(print (json.encode {:a 1 :b 2}))

MACRO SEARCHERS

Fennel supports macro searchers, allowing you to define custom macro loading paths. This is configured via the :macro-searchers option when compiling or running Fennel code.

GET FENNEL-AWARE STACK INFORMATION

When errors occur, Fennel provides enhanced stack traces that are aware of the original Fennel code. This is handled automatically by the Fennel runtime.

COMPILE FENNEL CODE TO LUA

Fennel code can be compiled into Lua code using the fennel.compile function or the fennel command-line tool.

(fennel.compile "(+ 1 2)")
; => "return (1 + 2)\n"

The output is a string containing the equivalent Lua code.

PARSE TEXT INTO AST NODES

The fennel.parse function converts Fennel source code into an Abstract Syntax Tree (AST).

(fennel.parse "(+ 1 2)")
; => { :fn 1 :args { :fn 2 :args { :num 1 :val 1 } :val + } :val + }

AST NODE DEFINITION

AST nodes in Fennel are represented as tables with specific keys indicating the type and value of the node. Common keys include :fn (function call), :args (arguments), :num (number literal), and :val (symbol or operator).

SEARCH THE PATH FOR A MODULE WITHOUT LOADING IT

The fennel.find-module function searches the Lua module path for a given module name without actually loading it.

SERIALIZATION (VIEW)

The fennel.view function provides a way to serialize Fennel data structures into a human-readable string format, similar to how they would be represented in Fennel code.

(fennel.view {:a 1 :b "hello"})
; => "{:a 1 :b \"hello\"}"

WORK WITH DOCSTRINGS AND METADATA

Fennel allows you to attach docstrings and other metadata to your functions and definitions. These can be accessed programmatically.

(fn greet [name]
  "Greets the given name."
  (string.format "Hello, %s!" name))

(fennel.get-docstring greet)
; => "Greets the given name."

DESCRIBE FENNEL SYNTAX

The fennel.syntax module provides information about Fennel's syntax, including keywords and special forms.

LOAD LUA CODE IN A PORTABLE WAY

Fennel's module loading system is designed to be portable across different Lua environments. Using require in Fennel leverages this.

DETECT LUA VM RUNTIME VERSION

Fennel provides ways to detect the underlying Lua VM version, which can be useful for writing version-specific code.

(fennel.version)
; => "0.8.0"
(fennel.lua-version)
; => { :major 5 :minor 4 }

PLUGINS

Fennel supports a plugin system that allows extending its functionality. Plugins can add new REPL commands, modify compilation behavior, and more.

Here is an example of a plugin that adds a ,locals command to the REPL, which lists all local variables in the current scope:

(local fennel (require :fennel)
(fn locals [env read on-values on-error scope chars opts]
  "Print all locals in repl session scope."
  (on-values [(fennel.view env.___replLocals___)]))
{:repl-command-locals locals}

$ fennel --plugin locals-plugin.fnl
Welcome to Fennel 0.8.0 on Lua 5.4!
Use ,help to see available commands.
>> (local x 4)
nil
>> (local abc :xyz)
nil
>> ,locals
{
  :abc "xyz"
  :x 4
}

The docstring of the function will be used as its summary in the ",help" command listing. Unlike other plugin hook fields, only the first plugin to provide a repl command will be used.

Activation

Plugins are activated by passing the --plugin argument on the command line, which should be a path to a Fennel file containing a module that has some of the functions listed above. If you're using the compiler programmatically, you can include a :plugins table in the options table to most compiler entry point functions.

Your plugin should contain a :versions field which either contains a list of strings indicating every version of Fennel which you have tested it with, or a string containing a pattern which is checked against Fennel's version with string.find. If your plugin is used with a version of Fennel that doesn't match :versions it will emit a warning. You should also have a :name field with the plugin's name.
