DESCRIPCIÓ

N

Un lenguaje de programación está compuesto por sintaxis y semántica. La semántica de Fennel varía solo de pequeñas formas respecto a Lua (todas indicadas más abajo). La sintaxis de Fennel proviene de la familia de lenguajes lisp. Los lisps tienen una sintaxis muy uniforme y predecible, lo que facilita escribir código que opera sobre código, así como edición estru

cturada.

Si ya conoces Lua y un lisp, te sentirás como en casa en Fennel. Aunque no, Lua es uno de los lenguajes de programación más simples que existen, así que si has programado antes deberías poder aprenderlo sin demasiados problemas, especialmente si has usado otro lenguaje imperativo con tipado dinámico y con closures. El manual de referencia de Lua es un buen lugar para buscar detalles, pero el Primer de Lua de Fennel es más corto y cubre lo

esencial.

Si ya tienes algún código de ejemplo en Lua y solo quieres ver cómo se vería en Fennel, puedes aprender mucho al ponerlo en antifenne

l

Funciones y

lambdas

Usa fn para crear funciones. Si proporcionas un nombre opcional, la función se vinculará a ese nombre en ámbito local; de lo contrario, simplemente es un valor

anónimo.

Una breve nota sobre los nombres: los identificadores suelen ser en minúsculas separados por guiones (también llamado "kebab-case"). También pueden contener dígitos, siempre que no estén al principio. También puedes usar el signo de interrogación (típicamente para funciones que devuelven verdadero o falso, p. ej., at-max-velocity?). Los guiones bajos (_) se usan a menudo para nombrar una

variable que no
planeamos usar.

La lista de argumentos se proporciona entre corchetes. El valor final del cuerpo se

devuelve.

Las funciones definidas con fn son rápidas; no tienen sobrecarga en tiempo de ejecución en comparación con Lua. Sin embargo, tampoco tienen verificación de aridad. (Es decir, llamar a una función con el número incorrecto de argumentos no causa un error.) MANEJO DE

ERRORES

Los errores en Lua pueden tomar dos formas. Las funciones en Lua pueden devolver cualquier número de valores, y la mayoría de las funciones que pueden fallar indicarán el fallo usando dos valores de retorno: nil seguido de una cadena de mensaje de fallo. Puedes interactuar con este estilo de función en Fennel colocando la llamada a la función en una tabla y haciendo coincidir patrones contra la

tabla: 
(case [(io.open "file")]
  ;; cuando io.open tiene éxito, devolverá un
archivo, pero si falla ;; devolverá nil y una cadena err-msg describi
endo por qué [f] (do (use-file-contents (f:read :*all)) (f
:close)) [nil err-msg] (report-error "Could not open file:" err-msg))

Puedes escribir tu propia función que devuelva múltiples valores llamando a values

. 
(fn use-file [filename]
  (if (valid-file-name? filename)
      (open-file filename)
      (values nil (.. "Invalid filename: " filename)
)
)
)

Nota: mientras que los errores son la razón más común para devolver múltiples valores de una función, se puede usar en otros casos también. Esta es la característica más complicada de Lua, y una discusión completa está fuera del alcance de este tutorial, pero está https://benaiah.me/posts/everything-you-didnt-want-to-know-about-lua-multivals/ bien cubierta en otros

lugares.

El problema con este tipo de error es que no se compone bien; el estado de error debe propagarse a lo largo de toda la cadena de llamadas desde la interna hasta la externa. Para abordar esto, puedes usar error. Esto terminará todo el proceso a menos que esté dentro de una llamada protegida, similar a la forma en otros lenguajes donde lanzar una excepción detendrá el programa a menos que esté dentro de un try/catch. Puedes hacer una llamada protegida con s="Li">pc

all: 
(let [(ok? val-or-msg) (pcall potencialmente-des
astrosa-llamada nombre-archivo)] (if ok?
(print "Se obtuvo el valor" val-or-msg) (pr
int "No se pudo obtener el valor:" val-or-msg)))

La invocación de pcall ahí significa que estás ejecutando (potencialmente-desastrosa-llamada nombre-archivo) en modo protegido. pcall toma un número arbitrario de argumentos que se pasan a la función. Puedes ver que pcall devuelve un booleano (ok? aquí) para indicarte si la llamada tuvo éxito o no, y un segundo valor (val-or-msg) que es el valor real si tuvo éxito o un mensaje de error si no lo

tuvo.

La función assert toma un valor y un mensaje de error; llama a error si el valor es nil y lo devuelve en caso contrario. Esto se puede usar para convertir fallos de múltiples valores en errores (un poco lo inverso de pcall que convierte errores en fallos de múltiples valores)

:

ombre-archivo)) cont
enido (f.read f "*all")]
(f.close f) contenido)

En este ejemplo, como io.open devuelve nil y un mensaje de error en caso de fallo, un fallo provocará un error y detendr

á la ej

FUNCIONES

VARIÁDICAS

Fennel soporta funciones variádicas (en otras palabras, funciones que toman cualquier número de argumentos) como muchos lenguajes. La sintaxis para tomar un número variable de argumentos en una función es el símbolo ..., que debe ser el último parámetro de una función. Esta sintaxis se hereda de Lua en lugar de

Lisp.

La forma ... no es una lista ni un valor de primera clase, se expande a múltiples valores en línea. Para acceder a elementos individuales del vararg, puedes desestructurar con paréntesis, o primero envolverlo en un literal de tabla ([...]) e indexar como una tabla normal, o usar la función select de la biblioteca central de Lua. A menudo, el vararg se puede pasar directamente a otra función como print sin necesidad de

enlazarlo. 
(fn print-each [...]
  (each [i v (ipairs [...])]
    (print (.. "Argumento " i " es " v))))
(print-each :a
:b
:c) 
(fn myprint [prefijo ...]
  (io.writ

#" ...) " argumentos dados: ")) (
print ...)) (myprint ":D " :d :e :f)

Los varargs tienen un ámbito diferente al de otras variables también - solo son accesibles para la función en la que se crean. A diferencia de los valores normales, las funciones no pueden cerrar sobre ellos. Esto significa que el siguiente código NO funcionará, ya que los varargs en la función interna están fuera de

ámbito.

VERIFICACIÓN ESTRICTA DE

GLOBALES

Si obtienes un error que dice global desconocido en modo estricto, significa que estás intentando compilar código que usa un global que el compilador de Fennel no conoce. La mayoría de las veces, esto se debe a un error de codificación. Sin embargo, en algunos casos puedes obtener este error con una referencia global legítima. Si esto sucede, puede deberse a una limitación inherente de la estrategia de Fennel. Puedes usar _G.miglobal para referirte a él de una manera que evite esta verificación y llame la atención sobre el hecho de que esto es de hecho un

global.

La CLI de Fennel tiene el parámetro --globals, que acepta una lista de globales separada por comas para ignorar.

TRAMPA

S

Hay algunas sorpresas que pueden morder a los lispers experimentados. La mayoría de estas resultan necesariamente de la insistencia de Fennel en imponer cero sobrecarga de ejecución sobre

Lua.
•
Los operadores aritméticos, de comparación y booleanos no son funciones de primera clase. Pueden comportarse de maneras sorprendentes con funciones de múltiples valores de retorno, porque el número de argumentos para ellos debe conocerse en tiempo de
compilación.
•
No existe la función apply; en su lugar usa table.unpack o unpack dependiendo de tu versión de Lua: (f 1 3 (table.unpack [4 9])) hace lo que (apply f 1 3 [4 9]) haría en otros
lisps.
•
Las tablas se comparan por igualdad por identidad, no basándose en el valor de su contenido, como en Bake
r.
•
Los valores de retorno en el repl se imprimirán de forma bonita, pero llamar a (print tbl) emitirá una salida como table: 0x55a3a8749ef0. Si no tienes una ya, se recomienda para la depuración definir una función de impresión que llame a fennel.view en su argumento antes de imprimirlo: (local fennel (require :fennel)) (fn _G.pp [x] (print (fennel.view x))). Si añades esta definición a tu archivo ~/.fennelrc estará disponible en el repl
estándar.
•
Los programadores de Lua deb
en tener en cuenta que las
funciones de Fennel no pued
en hacer retornos tempranos.

Para requerir un módulo que está en un subdirectorio, toma el nombre del archivo, reemplaza las barras con puntos y elimina la extensión, y luego pásalo a require. Por ejemplo, un archivo llamado lib/ui/menu.lua se leería al cargar el módulo lib.ui.m

Cuando ejecutas tu programa con el comando fennel, puedes llamar a require para cargar módulos de Fennel o Lua. Pero en otros contextos (como compilar a Lua y luego usar el comando lua, o en programas que embeben Lua) no conocerá los módulos de Fennel. The Lua standard library provides a way to organize code into modules using the require function. Fennel fully supports this, and provides some additional ergonomics on top.

  libs/
    example/
      init.fnl
      module-a.fnl

And the contents of libs/example/init.fnl are:

(local module-a (require :example.module-a))
(fn hello [] (print "hello from example"))
{:hello hello :module-a module-a}

And the contents of libs/example/module-a.fnl are:

(fn hello-a [] (print "hello from a"))
{:hello-a hello-a}

If we then try to require this library from main.fnl like this:

;; main.fnl
(local example (require :libs.example))
(example.module-a.hello-a)

This will fail. The reason is that the library, when placed in the libs/ directory, is expected to be required as :libs.example. However, within the library itself, it tries to require :example.module-a. This module path does not exist, and it should instead be :libs.example.module-a.

If we were to move the example directory out of libs/, and place it in the root of the project, and then require it as :example, it would work, but this is not a good way to organize project structure. If the library itself tries to require modules relative to its own directory, it will be hardcoded to a specific path. This breaks encapsulation, and requires the library user to maintain a specific directory structure.

The require function in Fennel resolves modules relative to the current module's path. This means that if you have a module :libs.example, and it requires :example.module-a, it will look for the module example.module-a relative to the current module's path. If the module is in libs/example/module-a.fnl, and it is required as :libs.example, then it should also require its submodules as :libs.example.module-a.

LuaRocks addresses this problem by enforcing both the directory name and installation path, populating the LUA_PATH environment variable to make the library available. This, of course, can be done manually by setting LUA_PATH per project in the build pipeline, pointing it to the right directory. But this is not very transparent, and when requiring a project local library it's better to see the full path, that directly maps to the project's file structure, rather than looking up where the LUA_PATH is modified.

In the Fennel ecosystem we encourage a simpler way of managing project dependencies. Simply dropping a library into your project's tree or using git submodule is usually enough, and the require paths should be handled by the library itself.

Here's how a relative require path can be specified in the libs/example/init.fnl to make it name/path agnostic, assuming that we've moved our example library there:

;; file libs/example/init.fnl:
(local a (require (.. ... :.module-a)))
{:hello-a a.hello}

Now, it doesn't matter how library is named or where we put it - we can require it from anywhere. It works because when requiring the library with (require :lib.example), the first value in ... will hold the "lib.example" string. This string is then concatenated with the ".module-a", and require will properly find and load the nested module at runtime under the "lib.example.module-a" path. It's a Lua feature, and not something Fennel specific, and it will work the same when the library is AOT compiled to Lua.

Compile-time relative include

Since Fennel v0.10.0 this also works at compile-time, when using the include special or the --require-as-include flag, with the constraint that the expression can be computed at compile time. This means that the expression must be self-contained, i.e. doesn't refer to locals or globals, but embeds all values directly. In other words, the following code will only work at runtime, but not with include or --require-as-include because current-module is not known at compile time:

(local current-module ...)
(require (.. current-module :.other-module))

This, on the other hand, will work both at runtime and at compile time:

(require (.. ... :.other-module))

The ... module args are propagated during compilation, so when the application which uses this library is compiled, all library code is correctly included into the self-contained Lua file.

Compiling a project that uses this example library with --require-as-include will include the following section in the resulting Lua code:

package.preload["libs.example.module-a"] = package.preload["libs.example.module-a"] or function(...)
  local function hello()
    return print("hello from a")
  end
  return {hello = hello}
end

Note that the package.preload entry contains a fully qualified path "libs.example.module-a", which was resolved at compile time.

Requiring modules from modules other than init.fnl

To require a module from a module other than init module, we must keep the path up to the current module, but remove the module name. For example, let's add a greet module in libs/example/utils/greet.fnl, and require it from libs/example/module-a.fnl:

;; file libs/example/utils/greet.fnl:
(fn greet [who] (print (.. "hello " who)))

This module can be required as follows:

;; file libs/example/module-a.fnl
(local greet (require (.. (: ... :match "(.+)%.[^.]+") :.utils.greet)))
(fn hello [] (print "hello from a"))
{:hello hello :greet greet}

The parent module name is determined via calling the match method on the current module name string (...).
