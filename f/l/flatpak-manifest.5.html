DESCRIPCIÓ

N

Flatpak usa archivos manifiesto, o recetas, en formato json o yaml para describir cómo una aplicación y sus dependencias incluidas pueden ser construidas a partir de fuentes. El manifiesto es usado por

flatpak-builder
.

FORMATO DEL

ARCHIVO

El nivel superior del archivo manifiesto describe los atributos globales de la aplicación, cómo puede ser construida, y la lista de módulos que necesitan ser

construidos.

Propiedades de nivel

superior

Estas son las propiedades que son

aceptadas:

id o app-id (ca

dena)
Una cadena que define el id de la aplicación.

Nota, "app-id" está obsoleto

y se conserva solo para
compatibilidad hacia atrás.

branch (ca

dena)
La rama a usar al exportar la aplicación. Si esto no está establecido, el valor por defecto proviene de la opción default-branch.

Esta clave anula tanto la clave default-branch como la opción de línea de comandos --default-branch. A menos que necesites un nombre de rama muy específico (como para un runtime o una extensión) se recomienda usar la clave default-branch en su lugar, ya que esa puede ser anulada por la opción --default-branc

h
.

default-branch

(cadena)
La rama por defecto a usar al exportar la aplicación. Por defecto es master.

Esta clave puede ser anulada por la opción de línea de comandos --default-branc

h
.

collection-id (

cadena)
El ID de colección del repositorio, por defecto no está establecido. Establecer un ID de colección globalmente único permite que las aplicaciones en el repositorio sean compartidas sobre sistemas peer-to-peer sin necesidad de más configuración. Si se construye en un repositorio existente, el ID de colección debe coincidir con el ID de colección configurado existente para ese
repositorio.

extension-tag (

cadena)
Si se está construyendo una extensión, la etiqueta para el punto de extensión a usar. Desde flatpak 0.11.4 un runtime puede definir múltiples ubicaciones para el mismo punto de extensión con la intención de que diferentes ramas para la extensión sean montadas en cada ubicación. Al construir una extensión es necesario saber a qué punto de extensión instalar la extensión. Esta opción resuelve cualquier ambigüedad en qué punto de extensión elegir. Si no se especifica, la elección por defecto es instalar en la única ubicación para el punto de extensión o en la ubicación para el punto de extensión sin etiqueta. Si hay múltiples ubicaciones para el mismo punto de extensión definidas con diferentes etiquetas, ocurrirá un
error.

token-type (e

ntero)
El tipo de token necesario para instalar este commit. Establecer esto a un valor mayor que 0 implica que se necesitará autenticación para instalar el
flatpak.

runtime (ca

dena)
El nombre del runtime que la aplicación
usa.

(cadena)
La versión del runtime que la aplicación usa, por defecto es
master.

sdk (cad

ena)
El nombre del runtime de desarrollo con el que la aplicación se
construye.

var (cad

ena)
Inicializar el /var escribible (de otro modo vacío) en la construcción con una copia de este
runtime.

metadata (c

adena)
Usar este archivo como el archivo de metadatos base al
finalizar.

command (ca

dena)
El nombre de archivo o ruta al binario principal de la aplicación. Nota que esto debe ser un solo ejecutable, no una línea de comandos o una ruta absoluta. Si quieres pasar argumentos, instala un script de shell wrapper y úsalo como el comando.

También nota que el comando se usa cuando la aplicación se ejecuta vía flatpak run, y no afecta lo que se ejecuta cuando la aplicación se ejecuta de ot

ras maneras, por ejemplo vía el archivo de
escritorio o la activación por D-Bus.

(objetos)

Un arreglo de líneas de comandos que se ejecutan después de importar la plataforma base, pero antes de aplicar los nuevos archivos del sdk. Este es un buen lugar para, por ejemplo, eliminar cosas de la base que puedan conflictuar con los archivos agregados en el

build-options (

objeto)
Un objeto de opciones de compilación que puede anular las opciones globales. Tenga en cuenta que esto no es heredado por los módulos
anidados.

build-commands (matriz de

cadenas)
Una matriz de comandos a ejecutar durante la compilación (entre make y make install si se usan estos). Esto es principalmente útil al usar el sistema de compilación "simple". Cada comando se ejecuta en /bin/sh -c, por lo que puede usar sintaxis de shell POSIX estándar como redirigir la salida. Si alguna entrada individual de la matriz falla, todo el proceso de compilación fallará, similar a los comandos en una receta de make(1)
.

post-install (matriz de

cadenas)
Una matriz de comandos de shell que se ejecutan después de la fase de instalación. Puede, por ejemplo, limpiar el directorio de instalación o instalar archivos
adicionales.

cleanup (matriz de

cadenas)
Una matriz de patrones de archivo que deben eliminarse al final. Los patrones que comienzan con / se consideran rutas completas (sin el prefijo /app), de lo contrario, solo coinciden con el nombre base. Tenga en cuenta que cualquier patrón solo coincidirá con los archivos instalados por este
módulo.

ensure-writable (matriz de

cadenas)
La forma en que funciona el constructor es que los archivos en el directorio de instalación son enlaces duros a los archivos en caché, por lo que no se les puede modificar in situ. Si lista un archivo aquí, el enlace duro se romperá y podrá modificarlo. Esta es una solución temporal; idealmente, la instalación de archivos debe reemplazar archivos, no modificar los
existentes.

listadas.

Fuente

s

fuentes.

ENTORNO DE

COMPILACIÓN

Al compilar la aplicación, cada comando se ejecuta en un sandbox separado con acceso solo a las cosas necesarias para él. Esta sección describe los detalles del sandbox. Cualquier opción aquí puede ser sobrescrita globalmente o por módulo con la opción build-args (aunque tal manifiesto no funcionará si inicias flatpak-builder con --sandb

ox).

Sistema de

archivos

Cada módulo se compila en su propio directorio de compilación, almacenado en un sub directorio llamado build/$modulename-$count en el directorio de estado (que es típicamente .flatpak-builder/). Adicionalmente hay un enlace simbólico build/$modulename a la última versión. Para generar compilaciones reproducibles, este directorio también se monta como /run/build/$modulename en el sandbox (o /run/build-runtime/$modulename al compilar runtimes) y también como /run/active-build desde 1.4.7. Esto se usa como directorio de trabajo actual para todas las operaciones de

compilación.

El directorio de destino para la instalación es accesible para escritura en el lugar donde se verá en tiempo de ejecución. En el caso de una aplicación regular, esto será /app. Si se compila un runtime, será /usr, y al compilar una extensión estará en el directorio extensionpoint en algún lugar debajo de /app (para extensión de app) o /usr (para extensiones de runtime)

.

Adicionalmente habrá (según sea necesario, dependiendo de qué se esté compilando)

montajes de solo lectura del sdk en /usr, extensiones del sdk debajo de eso, y la
aplicación en /app. No hay acceso al sistema de archivos disponible de otra forma.
