FLAWFINDER(1) Flawfinder FLAWFINDER(1)

NOMBRE

flawfinder - encuentra léxicamente posibles fallos de seguridad ("hallazgos") en el código fuente

SINOPSIS

flawfinder [--help|-h] [--version] [--listrules]
[--allowlink] [--followdotdir] [--nolink]
[--patch=filename|-P filename]
[--inputs|-I] [ --minlevel=X | -m X ] [--falsepositive|-F]
[--neverignore|-n]
[--regex=PATTERN | -e PATTERN]
[--context|-c] [--columns|-C] [--csv] [--dataonly|-D] [--html|-H] [--immediate|-i] [--sarif] [--singleline|-S] [--omittime] [--quiet|-Q] [--error-level=LEVEL]
[--loadhitlist=F] [--savehitlist=F] [--diffhitlist=F]
[--] [ archivo de código fuente o directorio raíz de código fuente ]+

DESCRIPCIÓN

Flawfinder busca en el código fuente C/C++ en busca de posibles fallos de seguridad. Para ejecutar flawfinder, simplemente proporcione a flawfinder una lista de directorios o archivos. Para cada directorio proporcionado, se examinarán todos los archivos que tengan extensiones de nombre de archivo C/C++ en ese directorio (y sus subdirectorios, de forma recursiva). Por lo tanto, para la mayoría de los proyectos, simplemente proporcione a flawfinder el nombre del directorio superior del código fuente (use ``.'' para el directorio actual), y flawfinder examinará todo el código fuente C/C++ del proyecto. Flawfinder no requiere que usted pueda compilar su software, por lo que puede usarse incluso con código fuente incompleto. Si solo desea que se revisen los cambios, guarde un diff unificado de esos cambios (creado por GNU "diff -u" o "svn diff" o "git diff") en un archivo de parche y use la opción --patch (-P).

Flawfinder producirá una lista de ``hits'' (posibles fallos de seguridad, también llamados hallazgos), ordenados por riesgo; los hits más riesgosos se muestran primero. El nivel de riesgo se muestra entre corchetes y varía de 0, muy poco riesgo, a 5, gran riesgo. Este nivel de riesgo depende no solo de la función, sino de los valores de los parámetros de la función. Por ejemplo, las cadenas constantes a menudo son menos riesgosas que las cadenas totalmente variables en muchos contextos, y en esos contextos el hit tendrá un nivel de riesgo menor. Flawfinder conoce gettext (una biblioteca común para programas internacionalizados) y tratará las cadenas constantes pasadas a través de gettext como si fueran cadenas constantes; esto reduce el número de falsos hits en programas internacionalizados. Flawfinder hará el mismo tipo de cosa con _T() y _TEXT(), macros comunes de Microsoft para manejar programas internacionalizados. Flawfinder ignora correctamente el texto dentro de comentarios y cadenas. Normalmente flawfinder muestra todos los hits con un nivel de riesgo de al menos 1, pero puede usar la opción --minlevel para mostrar solo hits con niveles de riesgo más altos si lo desea. Las descripciones de los hits también anotan los identificadores relevantes de Common Weakness Enumeration (CWE) entre paréntesis, como se discute a continuación. Flawfinder es oficialmente compatible con CWE. Las descripciones de hits con "[MS-banned]" indican funciones que están en la lista de funciones prohibidas publicada por Microsoft; consulte http://msdn.microsoft.com/en-us/library/bb288454.aspx para más información sobre funciones prohibidas.

No todo hit (también llamado hallazgo) es en realidad una vulnerabilidad de seguridad, y no toda vulnerabilidad de seguridad se encuentra necesariamente. Sin embargo, flawfinder puede ser una ayuda para encontrar y eliminar vulnerabilidades de seguridad. Una forma común de usar flawfinder es primero aplicar flawfinder a un conjunto de código fuente y examinar los elementos de mayor riesgo. Luego, use --inputs para examinar las ubicaciones de entrada y verificar que solo se acepten valores de entrada legales y seguros de usuarios no confiables.

Una vez que haya auditado un programa, puede marcar líneas de código fuente que en realidad están bien pero causan advertencias espurias para que flawfinder deje de quejarse de ellas. Para marcar una línea de modo que estas advertencias se supriman, coloque un comentario con formato especial ya sea en la misma línea (después del código fuente) o por sí solo en la línea anterior. El comentario debe tener uno de los dos formatos siguientes:

  • // Flawfinder: ignore
  • /* Flawfinder: ignore */

Por compatibilidad, puede reemplazar "Flawfinder:" con "ITS4:" o "RATS:" en estos comentarios con formato especial. Dado que es posible que tales líneas sean incorrectas, puede usar la opción --neverignore, que hace que flawfinder nunca ignore ninguna línea sin importar lo que digan las directivas de comentario (de manera más confusa, --neverignore ignora los ignores).

Flawfinder usa una base de datos interna llamada ``ruleset''; el ruleset identifica funciones que son causas comunes de fallos de seguridad. El ruleset estándar incluye un gran número de diferentes problemas potenciales, incluidos tanto problemas generales que pueden afectar a cualquier programa C/C++ como una serie de funciones específicas de tipo Unix y Windows que son especialmente problemáticas. La opción --listrules informa la lista de reglas actuales y sus niveles de riesgo predeterminados. Como se señaló anteriormente, cada posible fallo de seguridad encontrado en un archivo de código fuente dado (que coincida con una entrada en el ruleset) se llama ``hit'', y el conjunto de hits encontrados durante cualquier ejecución particular del programa se llama ``hitlist''. Las hitlists se pueden guardar (usando --savehitlist), volver a cargar para volver a mostrarlas (usando --loadhitlist), y puede mostrar solo los hits que son diferentes de otra ejecución (usando --diffhitlist).

Flawfinder es una herramienta simple, lo que conduce a algunas ventajas y desventajas fundamentales. Flawfinder funciona haciendo una tokenización léxica simple (omitiendo comentarios y tokenizando correctamente las cadenas), buscando coincidencias de tokens con la base de datos (particularmente para encontrar llamadas a funciones). Flawfinder es, por lo tanto, similar a RATS e ITS4, que también usan tokenización léxica simple. Flawfinder luego examina el texto de los parámetros de la función para estimar el riesgo. A diferencia de herramientas como splint, las banderas de advertencia de gcc y clang, flawfinder no usa ni tiene acceso a información sobre flujo de control, flujo de datos o tipos de datos al buscar posibles vulnerabilidades o estimar el nivel de riesgo. Por lo tanto, flawfinder necesariamente producirá muchos falsos positivos de vulnerabilidades y no reportará muchas vulnerabilidades. Por otro lado, flawfinder puede encontrar vulnerabilidades en programas que no se pueden compilar o no se pueden enlazar. A menudo puede funcionar con programas que ni siquiera se pueden compilar (al menos con las herramientas del revisor). Flawfinder tampoco se confunde tanto con definiciones de macros y otras rarezas con las que las herramientas más sofisticadas tienen problemas. Flawfinder también puede ser útil como una introducción simple a las herramientas de análisis estático en general, ya que es fácil de empezar a usar y fácil de entender.

Las limitaciones de flawfinder afectan cualquier análisis, pero pueden ser especialmente limitantes al analizar C++. C++ es notoriamente difícil de analizar correctamente. Un sistema léxico como flawfinder está limitado en lo que puede hacer cuando se usan construcciones como espacios de nombres y ámbitos de clase. Flawfinder usa varias heurísticas para mejorar su efectividad. Sin embargo, flawfinder tenderá a ser más efectivo en programas C++ que son "principalmente C con algunas adiciones de C++" y menos efectivo en programas C++ que usan "C++ moderno completo" con uso significativo de estas características.

Flawfinder se puede usar junto con herramientas de análisis de código basadas en IA. La salida de Flawfinder se puede usar para identificar rápidamente qué áreas de código merecen una atención más cercana, que un sistema de IA puede examinar luego con más detalle.

Cualquier nombre de archivo dado en la línea de comandos será examinado (incluso si no tiene una extensión de nombre de archivo C/C++ habitual); por lo tanto, puede forzar a flawfinder a examinar cualquier archivo específico que desee. Mientras busca directorios de forma recursiva, flawfinder solo abre y examina archivos regulares que tienen extensiones de nombre de archivo C/C++. Flawfinder presume que los archivos son archivos C/C++ si tienen las extensiones ".c", ".h", ".ec", ".ecp", ".pgc", ".C", ".cpp", ".CPP", ".cxx", ".c++", ".cc", ".CC", ".pcc", ".hpp" o ".H". El nombre de archivo ``-'' significa la entrada estándar. Para prevenir problemas de seguridad, los archivos especiales (como archivos especiales de dispositivo y tuberías con nombre) siempre se omiten, y por defecto se omiten los enlaces simbólicos (la opción --allowlink sigue los enlaces simbólicos).

Después de la lista de hits hay un breve resumen de los resultados (use -D para eliminar esta información). Mostrará el número de hits, las líneas analizadas (según lo informado por wc -l) y las líneas físicas de código fuente (SLOC) analizadas. Una SLOC física es una línea no vacía y no comentada. Luego mostrará el número de hits en cada nivel; tenga en cuenta que nunca habrá un hit en un nivel inferior a minlevel (1 por defecto). Por lo tanto, "[0] 0 [1] 9" significa que en el nivel 0 se informaron 0 hits, y en el nivel 1 se informaron 9 hits. A continuación mostrará el número de hits en un nivel dado o superior (por lo que el nivel 3+ tiene la suma del número de hits en los niveles 3, 4 y 5). Por lo tanto, una entrada de "[0+] 37" muestra que en el nivel 0 o superior había 37 hits (la entrada 0+ siempre será la misma que el número de "hits" anterior). A continuación se muestra Hits por KSLOC; este es cada uno de los valores de "nivel o superior" multiplicado por 1000 y dividido por la SLOC física. Si se omitieron enlaces simbólicos, se informa el recuento de estos. Si se suprimieron hits (usando la directiva "ignore" en los comentarios del código fuente como se describió anteriormente), se informa el número suprimido. Se muestra el nivel de riesgo mínimo que se incluirá en el informe; por defecto es 1 (use --minlevel para cambiarlo). El resumen termina con recordatorios importantes: No todo hit es necesariamente una vulnerabilidad de seguridad, y puede haber otras vulnerabilidades de seguridad no reportadas por la herramienta.

Flawfinder puede integrarse fácilmente en un sistema de integración continua. Es posible que desee consultar la opción --error-level para ayudar a hacerlo, por ejemplo, usar --error-level=4 hará que se devuelva un error si flawfinder encuentra una vulnerabilidad de nivel 4 o superior.

Flawfinder se publica bajo la licencia GNU GPL versión 2 o posterior (GPLv2+).

Flawfinder funciona de manera similar a otro programa, ITS4, que no es software completamente de código abierto (según se define en la Open Source Definition) ni software libre (según lo define la Free Software Foundation). El autor de Flawfinder nunca ha visto el código fuente de ITS4. Flawfinder es similar en muchos aspectos a RATS, si está familiarizado con RATS.

TUTORIAL BREVE

Aquí hay un breve ejemplo de cómo se podría usar flawfinder. Imagine que tiene el código fuente en C/C++ de algún programa llamado xyzzy (que puede o no haber escrito), y está buscando vulnerabilidades de seguridad (para poder corregirlas antes de que los clientes encuentren las vulnerabilidades). Para este tutorial, asumiré que está usando un sistema tipo Unix, como Linux, OpenBSD o MacOS X.

Si el código fuente está en un subdirectorio llamado xyzzy, probablemente comenzaría abriendo una ventana de texto y usando la configuración predeterminada de flawfinder, para analizar el programa y reportar una lista priorizada de posibles vulnerabilidades de seguridad (el ``less'' solo asegura que los resultados permanezcan en la pantalla):

flawfinder xyzzy | less

En este punto, verá una gran cantidad de entradas. Cada entrada tiene un nombre de archivo, dos puntos, un número de línea, un nivel de riesgo entre corchetes (donde 5 es el más riesgoso), una categoría, el nombre de la función y una descripción de por qué flawfinder cree que la línea es una vulnerabilidad. Flawfinder normalmente ordena por nivel de riesgo, mostrando primero los elementos más riesgosos; si tiene tiempo limitado, probablemente sea mejor comenzar a trabajar en los elementos más riesgosos y continuar hasta que se le acabe el tiempo. Si desea limitar la visualización a riesgos con solo un cierto nivel de riesgo o superior, use la opción --minlevel. Si está obteniendo una cantidad extraordinaria de falsos positivos porque los nombres de las variables parecen nombres de funciones peligrosas, use la opción -F para eliminar los informes sobre ellos. Si no entiende el mensaje de error, consulte documentos como el Secure Programming HOWTO en https://dwheeler.com/secure-programs que proporciona más información sobre cómo escribir programas seguros.

Una vez que identifique el problema y lo entienda, puede corregirlo. Ocasionalmente, es posible que desee volver a realizar el análisis, tanto porque los números de línea cambiarán y para asegurarse de que el nuevo código no introduzca aún otra vulnerabilidad diferente.

Si ha determinado que alguna línea no es realmente un problema, y está seguro de ello, puede insertar justo antes o en la línea infractora un comentario como


/* Flawfinder: ignore */
para evitar que aparezcan en la salida.

Una vez que haya hecho eso, debe volver y buscar las entradas del programa, para asegurarse de que el programa filtre fuertemente cualquiera de sus entradas no confiables. Flawfinder puede identificar muchas entradas del programa usando la opción --inputs, así:

flawfinder --inputs xyzzy

Flawfinder puede integrarse bien con editores de texto y entornos de desarrollo integrados; consulte los ejemplos para obtener más información.

Flawfinder incluye muchas otras opciones, incluidas algunas para crear versiones HTML de la salida (útil para visualizaciones más bonitas) y salida en el Formato de Intercambio de Resultados de Análisis Estático (SARIF) de OASIS. La siguiente sección describe esas opciones con más detalle.

OPTIONS

Flawfinder has a number of options, which can be grouped into options that control its own documentation, select input data, select which hits to display, select the output format, and perform hitlist management. The commonly-used flawfinder options support the standard option syntax defined in the POSIX (Issue 7, 2013 Edition) section ``Utility Conventions''. Flawfinder also supports the GNU long options (double-dash options of form --option) as defined in the GNU C Library Reference Manual ``Program Argument Syntax Conventions'' and GNU Coding Standards ``Standards for Command Line Interfaces''. Long option arguments can be provided as ``--name=value'' or ``-name value''. All options can be accessed using the more readable GNU long option conventions; some less commonly used options can only be accessed using long option conventions.

Documentation

--help
-h
Show usage (help) information.
--version
Shows (just) the version number and exits.
--listrules
List the terms (tokens) that trigger further examination, their default risk level, and the default warning (including the CWE identifier(s), if applicable), all tab-separated. The terms are primarily names of potentially-dangerous functions. Note that the reported risk level and warning for some specific code may be different than the default, depending on how the term is used. Combine with -D if you do not want the usual header. Flawfinder version 1.29 changed the separator from spaces to tabs, and added the default warning field.

Selecting Input Data

--allowlink
Allow the use of symbolic links; normally symbolic links are skipped. Don't use this option if you're analyzing code by others; attackers could do many things to cause problems for an analysis with this option enabled. For example, an attacker could insert symbolic links to files such as /etc/passwd (leaking information about the file) or create a circular loop, which would cause flawfinder to run ``forever''. Another problem with enabling this option is that if the same file is referenced multiple times using symbolic links, it will be analyzed multiple times (and thus reported multiple times). Note that flawfinder already includes some protection against symbolic links to special file types such as device file types (e.g., /dev/zero or C:\mystuff\com1). Note that for flawfinder version 1.01 and before, this was the default.
--followdotdir
Enter directories whose names begin with ".". Normally such directories are ignored, since they normally include version control private data (such as .git/ or .svn/), build metadata (such as .makepp), configuration information, and so on.
--nolink
Ignored. Historically this disabled following symbolic links; this behavior is now the default.
--patch=patchfile
-P patchfile
Examine the selected files or directories, but only report hits in lines that are added or modified as described in the given patch file. The patch file must be in a recognized unified diff format (e.g., the output of GNU "diff -u old new", "svn diff", or "git diff [commit]"). Flawfinder assumes that the patch has already been applied to the files. The patch file can also include changes to irrelevant files (they will simply be ignored). The line numbers given in the patch file are used to determine which lines were changed, so if you have modified the files since the patch file was created, regenerate the patch file first. Beware that the file names of the new files given in the patch file must match exactly, including upper/lower case, path prefix, and directory separator (\ vs. /). Only unified diff format is accepted (GNU diff, svn diff, and git diff output is okay); if you have a different format, again regenerate it first. Only hits that occur on resultant changed lines, or immediately above and below them, are reported. This option implies --neverignore. Warning: Do not pass a patch file without the -P, because flawfinder will then try to treat the file as a source file. This will often work, but the line numbers will be relative to the beginning of the patch file, not the positions in the source code. Note that you must also provide the actual files to analyze, and not just the patch file; when using -P files are only reported if they are both listed in the patch and also listed (directly or indirectly) in the list of files to analyze.

Selecting Hits to Display

--inputs
-I
Show only functions that obtain data from outside the program; this also sets minlevel to 0.
--minlevel=X
-m X
Set minimum risk level to X for inclusion in hitlist. This can be from 0 (``no risk'') to 5 (``maximum risk''); the default is 1.
--falsepositive
-F
Do not include hits that are likely to be false positives. Currently, this means that function names are ignored if they're not followed by "(", and that declarations of character arrays aren't noted. Thus, if you have use a variable named "access" everywhere, this will eliminate references to this ordinary variable. This isn't the default, because this also increases the likelihood of missing important hits; in particular, function names in #define clauses and calls through function pointers will be missed.
--neverignore
-n
Never ignore security issues, even if they have an ``ignore'' directive in a comment.
--regexp=PATTERN
-e PATTERN
Only report hits with text that matches the regular expression pattern PATTERN. For example, to only report hits containing the text "CWE-120", use ``--regex CWE-120''. These option flag names are the same as grep.

Selecting Output Format

--columns
-C
Show the column number (as well as the file name and line number) of each hit; this is shown after the line number by adding a colon and the column number in the line (the first character in a line is column number 1). This is useful for editors that can jump to specific columns, or for integrating with other tools (such as those to further filter out false positives).
--context
-c
Show context, i.e., the line having the "hit"/potential flaw. By default the line is shown immediately after the warning.
--csv
Generate output in comma-separated-value (CSV) format. This is the recommended format for sending to other tools for processing. It will always generate a header row, followed by 0 or more data rows (one data row for each hit). Selecting this option automatically enables --quiet and --dataonly. The headers are mostly self-explanatory. "File" is the filename, "Line" is the line number, "Column" is the column (starting from 1), "Level" is the risk level (0-5, 5 is riskiest), "Category" is the general flawfinder category, "Name" is the name of the triggering rule, "Warning" is text explaining why it is a hit (finding), "Suggestion" is text suggesting how it might be fixed, "Note" is other explanatory notes, "CWEs" is the list of one or more CWEs, "Context" is the source code line triggering the hit, and "Fingerprint" is the SHA-256 hash of the context once its leading and trailing whitespace have been removed (the fingerprint may help detect and eliminate later duplications). If you use Python3, the hash is of the context when encoded as UTF-8.
--dataonly
-D
Don't display the header and footer. Use this along with --quiet to see just the data itself.
--html
-H
Format the output as HTML instead of as simple text.
--immediate
-i
Immediately display hits (don't just wait until the end).
--sarif
Produce output in the OASIS Static Analysis Results Interchange Format (SARIF) format (a JSON-based format). The goals of the SARIF format, as explained in version 2.1.0 (27 March 2020) of its specification, include being able to "comprehensively capture the range of data produced by commonly used static analysis tools." SARIF output identifies the tool name as "Flawfinder". The flawfinder levels 0 through 5 are mapped to SARIF rank (by dividing by 5), SARIF level, and the default viewer action as follows:

Flawfinder 0: SARIF rank 0.0, SARIF level note, Does not display by default

Flawfinder 1: SARIF rank 0.2, SARIF level note, Does not display by default

Flawfinder 2: SARIF rank 0.4, SARIF level note, Does not display by default

Flawfinder 3: SARIF rank 0.6, SARIF level warning, Displays by default, does not break build / other processes

Flawfinder 4: SARIF rank 0.8, SARIF level error, Displays by default, breaks build/ other processes

Flawfinder 5: SARIF rank 1.0, SARIF level error, Displays by default, breaks build/ other processes

A big thanks to Yong Yan implementing SARIF output generation for flawfinder! For more about the SARIF format, see: https://www.oasis-open.org/committees/tc_home.php?wg_abbrev=sarif

--singleline
-S
Display as single line of text output for each hit. Useful for interacting with compilation tools.
--omittime
Omit timing information. This is useful for regression tests of flawfinder itself, so that the output doesn't vary depending on how long the analysis takes.
--quiet
-Q
Don't display status information (i.e., which files are being examined) while the analysis is going on.
--error-level=LEVEL
Return a nonzero (false) error code if there is at least one hit of LEVEL or higher. If a diffhitlist is provided, hits noted in it are ignored. This option can be useful within a continuous integration script, especially if you mark known-okay lines as "flawfinder: ignore". Usually you want level to be fairly high, such as 4 or 5. By default, flawfinder returns 0 (true) on a successful run.

Hitlist Management

--savehitlist=F
Save all resulting hits (the "hitlist") to F.
--loadhitlist=F
Load the hitlist from F instead of analyzing source programs. Hitlists are intended for use by the same user who created them. A hitlist from an untrusted source could contain misleading results, such as fabricated hits or omitted findings. Note that stored hitlists often cannot be read when using an older version of Python, in particular, if savehitlist was used but flawfinder was run using Python 3, the hitlist can't be loaded by running flawfinder with Python 2.
--diffhitlist=F
Show only hits (loaded or analyzed) not in F. F was presumably created previously using --savehitlist. A hitlist from an untrusted source could contain misleading results; use only hitlists you created yourself. If the --loadhitlist option is not provided, this will show the hits in the analyzed source code files that were not previously stored in F. If used along with --loadhitlist, this will show the hits in the loaded hitlist not in F. The difference algorithm is conservative; hits are only considered the ``same'' if they have the same filename, line number, column position, function name, and risk level.

Character Encoding Errors

Flawfinder uses the character encoding rules set by Python. Sometimes source code does not perfectly follow some encoding rules. If you run flawfinder with Python 2 these non-conformities often do not impact processing in practice.

However, if you run flawfinder with Python 3, this can be a problem. Python 3 developers wants the world to always use encodings perfectly correctly, everywhere, and in general wants everyone to only use UTF-8. UTF-8 is a great encoding, and it is very popular, but the world often doesn't care what the Python 3 developers want.

When running flawfinder using Python 3, the program will crash hard if any source file has any non-conforming text. It will do this even if the non-conforming text is in comments or strings (where it often doesn't matter). Python 3 fails to provide useful built-ins to deal with the messiness of the real world, so it's non-trivial to deal with this problem without depending on external libraries (which we're trying to avoid).

A symptom of this problem is if you run flawfinder and you see an error message like this:

Error: encoding error in ,1.c

'utf-8' codec can't decode byte 0xff in position 45: invalid start byte

What you are seeing is the result of an internal UnicodeDecodeError.

If this happens to you, there are several options:

Option #1 (special case): if your system normally uses an encoding other than UTF-8, is properly set up to use that encoding (using LC_ALL and maybe LC_CTYPE), and the input files are in that non-UTF-8 encoding, it may be that Python3 is (incorrectly) ignoring your configuration. In that case, simply tell Python3 to use your configuration by setting the environment variable PYTHONUTF8=0, e.g., run flawfinder as: "PYTHONUTF8=0 python3 flawfinder ...".

Option #2 (special case): If you know what the encoding of the files is, you can force use of that encoding. E.g., if the encoding is BLAH, run flawfinder as: "PYTHONUTF8=0 LC_ALL=C.BLAH python3 flawfinder ...". You can replace "C" after LC_ALL= with your real language locale (e.g., "en_US").

Option #3: If you don't know what the encoding is, or the encoding is inconsistent (e.g., the common case of UTF-8 files with some characters encoded using Windows-1252 instead), then you can force the system to use the ISO-8859-1 (Latin-1) encoding in which all bytes are allowed. If the inconsistencies are only in comments and strings, and the underlying character set is "close enough" to ASCII, this can get you going in a hurry. You can do this by running: "PYTHONUTF8=0 LC_ALL=C.ISO-8859-1 python3 flawfinder ...". In some cases you may not need the "PYTHONUTF8=0". You may be able to replace "C" after LC_ALL= with your real language locale (e.g., "en_US").

Option #4: Convert the encoding of the files to be analyzed so that it's a single encoding - it's highly recommended to convert to UTF-8. For example, the system program "iconv" or the Python program cvt2utf can be used to convert encodings. (You can install cvt2utf with "pip install cvtutf"). This works well if some files have one encoding, and some have another, but they are consistent within a single file. If the files have encoding errors, you'll have to fix them.

Option #5: Run flawfinder using Python 2 instead of Python 3. E.g., "python2 flawfinder ...".

To be clear: I strongly recommend using the UTF-8 encoding for all source code, and use continuous integration tests to ensure that the source code is always valid UTF-8. If you do that, many problems disappear. But in the real world this is not always the situation. Hopefully this information will help you deal with real-world encoding problems.

EJEMPLOS

Aquí hay varios ejemplos de cómo invocar flawfinder. Los primeros ejemplos muestran varias opciones simples de línea de comandos. Flawfinder está diseñado para funcionar bien con editores de texto y entornos de desarrollo integrados, por lo que las siguientes secciones muestran cómo integrar flawfinder en vim y emacs.

Opciones simples de línea de comandos

flawfinder /usr/src/linux-3.16
Examina todos los archivos C/C++ en el directorio /usr/src/linux-3.16 y todos sus subdirectorios (recursivamente), informando sobre todas las detecciones encontradas. Por defecto flawfinder omitirá los enlaces simbólicos y los directorios cuyos nombres comiencen con un punto.
flawfinder --error-level=4 .
Examina todos los archivos C/C++ en el directorio actual y sus subdirectorios (recursivamente); devuelve un código de error si hay vulnerabilidades de nivel 4 y superiores (los dos niveles de riesgo más altos). Esta es una forma plausible de usar flawfinder en un sistema de integración continua.
flawfinder --minlevel=4 .
Examina todos los archivos C/C++ en el directorio actual y sus subdirectorios (recursivamente); solo informa vulnerabilidades de nivel 4 y superiores (los dos niveles de riesgo más altos).
flawfinder --inputs mydir
Examina todos los archivos C/C++ en mydir y sus subdirectorios (recursivamente), e informa las funciones que toman entradas (para que puedas asegurarte de que filtran las entradas adecuadamente).
flawfinder --neverignore mydir
Examina todos los archivos C/C++ en el directorio mydir y sus subdirectorios, incluyendo incluso las detecciones marcadas para ignorar en los comentarios del código.
flawfinder --csv .
Examina el directorio actual hacia abajo (recursivamente), e informa todas las detecciones en formato CSV. Esta es la forma recomendada si deseas procesar posteriormente la salida de flawfinder usando otras herramientas (como herramientas de correlación de datos).
flawfinder -QD mydir
Examina mydir e informa solo los resultados reales (eliminando el encabezado y el pie de la salida). Esta forma puede ser útil si la salida se canaliza a otras herramientas para su posterior análisis, aunque el formato CSV es probablemente la mejor opción en ese caso. Las opciones -C (--columns) y -S (--singleline) también pueden ser útiles si estás canalizando los datos a otras herramientas.
flawfinder -QDSC mydir
Examina mydir, informando solo los resultados reales (sin encabezado ni pie). Cada detección se informa en una línea, y se informan los números de columna. Este puede ser un comando útil si estás alimentando la salida de flawfinder a otras herramientas.
flawfinder --quiet --html --context mydir > results.html
Examina todos los archivos C/C++ en el directorio mydir y sus subdirectorios, y produce una versión con formato HTML de los resultados. Los sistemas de gestión de código fuente (como SourceForge y Savannah) podrían usar un comando como este.
flawfinder --quiet --savehitlist saved.hits *.[ch]
Examina todos los archivos .c y .h en el directorio actual. No informa sobre el estado del procesamiento, y guarda la lista de detecciones resultante (el conjunto de todas las detecciones) en el archivo saved.hits.
flawfinder --diffhitlist saved.hits *.[ch]
Examina todos los archivos .c y .h en el directorio actual, y muestra cualquier detección que no estuviera ya en el archivo saved.hits. Esto se puede usar para mostrar solo las vulnerabilidades ``nuevas'' en un programa modificado, si saved.hits fue creado a partir de la versión anterior del programa que se está analizando.
flawfinder --patch recent.patch .
Examina el directorio actual recursivamente, pero solo informa las líneas que fueron cambiadas o añadidas en el archivo de parche ya aplicado llamado recent.patch.
flawfinder --regex "CWE-120|CWE-126" src/
Examina el directorio src recursivamente, pero solo informa las detecciones donde se apliquen CWE-120 o CWE-126.

Invocación desde vim

El editor de texto vim incluye un mecanismo de "quickfix" que funciona bien con flawfinder, de modo que puedes ver fácilmente los mensajes de advertencia y saltar al código fuente relevante.

Primero, necesitas invocar flawfinder para crear una lista de detecciones, y hay dos formas de hacerlo. La primera forma es iniciar flawfinder primero, y luego (usando su salida) invocar vim. La segunda forma es iniciar (o continuar ejecutando) vim, y luego invocar flawfinder (típicamente desde dentro de vim).

Para la primera forma, ejecuta flawfinder y almacena su salida en algún ARCHIVODEFLAWS (digamos "flawfile"), luego invoca vim usando su opción -q, así: "vim -q flawfile". La segunda forma (iniciar flawfinder después de iniciar vim) se puede hacer de infinidad de maneras. Una es invocar flawfinder usando un comando de shell, ":!flawfinder-command > ARCHIVODEFLAWS", y luego seguir eso con el comando ":cf ARCHIVODEFLAWS". Otra forma es almacenar el comando de flawfinder en tu makefile (como, digamos, un pseudocomando como "flaw"), y luego ejecutar ":make flaw".

En todos estos casos necesitas un comando para que flawfinder se ejecute. Un comando plausible, que coloca cada detección en su propia línea (-S) y elimina los encabezados y pies que podrían confundirlo, es:

flawfinder -SQD .

Ahora puedes usar varios comandos de edición para ver los resultados. El comando ":cn" muestra la siguiente detección; ":cN" muestra la detección anterior, y ":cr" rebobina hasta la primera detección. ":copen" abrirá una ventana para mostrar la lista actual de detecciones, llamada "ventana quickfix"; ":cclose" cerrará la ventana quickfix. Si el búfer en la ventana usada ha cambiado, y el error está en otro archivo, saltar al error fallará. Tienes que asegurarte de que la ventana contenga un búfer que pueda ser abandonado antes de intentar saltar a un nuevo archivo, por ejemplo guardando el archivo; esto evita la pérdida accidental de datos.

Invocación desde emacs

El editor de texto / sistema operativo emacs incluye mecanismos de "modo grep" y "modo compile" que funcionan bien con flawfinder, facilitando ver los mensajes de advertencia, saltar al código fuente relevante y corregir cualquier problema que encuentres.

Primero, necesitas invocar flawfinder para crear una lista de mensajes de advertencia. Puedes usar el "modo grep" o el "modo compile" para crear esta lista. A menudo el "modo grep" es más conveniente; deja el modo compile intacto para que puedas recompilar fácilmente una vez que hayas cambiado algo. Sin embargo, si quieres saltar a la posición exacta de la columna de una detección, el modo compile puede ser más conveniente porque emacs puede usar la salida de columna de flawfinder para saltar directamente a la ubicación correcta sin ninguna configuración especial.

Para usar el modo grep, introduce el comando "M-x grep" y luego introduce el comando de flawfinder necesario. Para usar el modo compile, introduce el comando "M-x compile" e introduce el comando de flawfinder necesario. Este es un comando de meta-tecla, así que necesitarás usar la tecla meta de tu teclado (esta suele ser la tecla ESC). Como con todos los comandos de emacs, necesitarás pulsar RETURN después de escribir "grep" o "compile". Así que en muchos sistemas, el modo grep se invoca escribiendo ESC x g r e p RETURN.

Luego necesitas introducir un comando, eliminando lo que hubiera allí antes si es necesario. Un comando plausible es:

flawfinder -SQDC .

Este comando hace que cada detección informe una sola línea, lo cual es mucho más fácil de manejar para las herramientas. Las opciones quiet y dataonly eliminan la otra información de estado no necesaria para usar dentro de emacs. El punto final significa que el directorio actual y todos sus descendientes se buscan en busca de código C/C++, y se analizan en busca de fallos.

Una vez que hayas invocado flawfinder, puedes usar emacs para saltar por sus resultados. El comando C-x ` (Control-x acento grave) visita la ubicación del código fuente para el siguiente mensaje de advertencia. C-u C-x ` (control-u control-x acento grave) reinicia desde el principio. Puedes visitar el código fuente de cualquier mensaje de error particular moviéndote a ese mensaje de detección en el búfer *compilation* o *grep* y pulsando la tecla return. (Nota técnica: en el búfer de compilación, esto invoca compile-goto-error.) También puedes hacer clic en el botón Mouse-2 sobre el mensaje de error (no necesitas cambiar al búfer *compilation* primero).

Si quieres usar el modo grep para saltar a columnas específicas de una detección, necesitarás configurar emacs especialmente para hacer esto. Para hacerlo, modifica la variable de emacs "grep-regexp-alist". Esta variable le dice a Emacs cómo analizar la salida de un comando "grep", de forma similar a la variable "compilation-error-regexp-alist" que lista varios formatos de mensajes de error de compilación.

ENUMERACIÓN COMÚN DE DEBILIDADES (CWE)

La Enumeración Común de Debilidades (CWE) es ``una lista formal o diccionario de debilidades comunes de software que pueden ocurrir en la arquitectura, el diseño, el código o la implementación del software y que pueden dar lugar a vulnerabilidades de seguridad explotables... creada para servir como un lenguaje común para describir debilidades de seguridad del software'' (https://cwe.mitre.org/about/faq.html). Para más información sobre las CWE, consulte https://cwe.mitre.org.

Flawfinder admite la CWE y es oficialmente compatible con CWE. Las descripciones de los hallazgos suelen incluir un identificador relevante de la Enumeración Común de Debilidades (CWE) entre paréntesis cuando se sabe que existe una CWE relevante. Por ejemplo, muchos de los hallazgos relacionados con búferes mencionan CWE-120, el identificador CWE de ``copia de búfer sin comprobar el tamaño de la entrada'' (también conocido como ``Desbordamiento de búfer clásico''). En algunos casos puede aparecer más de un identificador CWE. El informe HTML también incluye enlaces de hipertexto a las definiciones de CWE alojadas en MITRE. De esta forma, flawfinder está diseñado para cumplir el requisito CWE-Output.

En algunos casos existen desafíos de mapeo y uso de CWE; así es como flawfinder los maneja. Si la misma entrada se asigna a múltiples CWE simultáneamente, todas las asignaciones CWE se listan separadas por comas. Esto ocurre a menudo con CWE-20, Validación de entrada incorrecta; por lo tanto, el informe "CWE-676, CWE-120" se asigna a dos CWE. Además, flawfinder proporciona información adicional para quienes estén interesados en la lista top 25 de CWE/SANS de 2011 (https://cwe.mitre.org/top25/) cuando las asignaciones no son directamente a ellas. Muchas personas querrán buscar CWE específicas en esta lista top 25, como CWE-120 (desbordamiento de búfer clásico). El desafío es que algunos hallazgos de flawfinder se asignan a una CWE más general que incluiría un elemento del top 25, mientras que en otros casos los hallazgos se asignan a una vulnerabilidad más específica que es solo un subconjunto de un elemento del top 25. Para resolver esto, en algunos casos flawfinder listará una secuencia de CWE en el formato "más-general/más-específica", donde la CWE realmente asignada va seguida de un "!". Esto siempre se hace cuando una falla no se asigna directamente a una CWE del top 25, pero la asignación está relacionada con dicha CWE. Así, "CWE-119!/CWE-120" significa que la vulnerabilidad se asigna a CWE-119 y que CWE-120 es un subconjunto de CWE-119. En contraste, "CWE-362/CWE-367!" significa que el hallazgo se asigna a CWE-367, un subconjunto de CWE-362. Tenga en cuenta que este es un cambio sutil de sintaxis respecto a la versión 1.31 de flawfinder; en la versión 1.31 de flawfinder, la forma "más-general:más-específica" significaba lo que ahora se lista como "más-general!/más-específica", mientras que "más-general/más-específica" significaba "más-general/más-específica!". Las herramientas pueden manejar tanto la versión 1.31 como el formato actual, si lo desean, observando que el formato anterior no usaba "!" en absoluto (y por lo tanto esto es fácil de distinguir). Estos mecanismos de mapeo simplifican la búsqueda de ciertas CWE.

Se utilizó la versión 2.7 de CWE (publicada el 23 de junio de 2014) para el mapeo. Las asignaciones CWE actuales seleccionan la CWE más específica que la herramienta puede determinar. En teoría, la mayoría de los elementos de seguridad CWE (firmas/patrones que la herramienta busca) podrían asignarse teóricamente a CWE-676 (Uso de una función potencialmente peligrosa), pero tal asignación no sería útil. Por lo tanto, se prefirieron asignaciones más específicas cuando se podía encontrar una. Flawfinder es una herramienta de análisis léxico; como resultado, es poco práctico que sea más específica que las asignaciones implementadas actualmente. Esto también significa que es poco probable que necesite mucha actualización por vigencia del mapa; simplemente no tiene suficiente información para refinar a un nivel de CWE detallado que los cambios de CWE normalmente afectarían. La lista de identificadores CWE se generó automáticamente usando "make show-cwes", por lo que hay confianza en que esta lista es correcta. Por favor, informe los problemas de mapeo CWE como errores si encuentra alguno.

Flawfinder puede no encontrar una vulnerabilidad, incluso si flawfinder cubre una de estas debilidades CWE. Dicho esto, flawfinder sí encuentra vulnerabilidades listadas por las CWE que cubre, y no reportará líneas sin esas vulnerabilidades en muchos casos. Por lo tanto, como se requiere para cualquier herramienta que pretenda ser compatible con CWE, flawfinder tiene una tasa de falsos positivos menor al 100% y una tasa de falsos negativos menor al 100%. Flawfinder casi siempre reporta cuando encuentra una coincidencia con un elemento de seguridad CWE (una firma/patrón según se define en su base de datos), aunque ciertas construcciones oscuras pueden hacer que falle (consulte ERRORES más abajo).

Flawfinder puede reportar sobre las siguientes CWE (estas son las CWE que cubre flawfinder; ``*'' marca aquellas en la lista top 25 de CWE/SANS):

  • CWE-20: Validación de entrada incorrecta
  • CWE-22: Limitación incorrecta de un nombre de ruta a un directorio restringido (``Salto de ruta'')
  • CWE-78: Neutralización incorrecta de elementos especiales usados en un comando del SO (``Inyección de comandos del SO'')*
  • CWE-119: Restricción incorrecta de operaciones dentro de los límites de un búfer de memoria (un padre de CWE-120*, por lo que se muestra como CWE-119!/CWE-120)
  • CWE-120: Copia de búfer sin comprobar el tamaño de la entrada (``Desbordamiento de búfer clásico'')*
  • CWE-126: Lectura excesiva de búfer
  • CWE-134: Cadena de formato no controlada*
  • CWE-190: Desbordamiento de entero o vuelta atrás*
  • CWE-250: Ejecución con privilegios innecesarios
  • CWE-327: Uso de un algoritmo criptográfico roto o riesgoso*
  • CWE-362: Ejecución concurrente usando un recurso compartido con sincronización incorrecta (``Condición de carrera'')
  • CWE-377: Archivo temporal inseguro
  • CWE-676: Uso de una función potencialmente peligrosa*
  • CWE-732: Asignación incorrecta de permisos para un recurso crítico*
  • CWE-785: Uso de una función de manipulación de rutas sin un búfer de tamaño máximo (hijo de CWE-120*, por lo que se muestra como CWE-120/CWE-785)
  • CWE-807: Dependencia de entradas no confiables en una decisión de seguridad*
  • CWE-829: Inclusión de funcionalidad desde una esfera de control no confiable*

Puede seleccionar un subconjunto específico de CWE para reportar usando la opción ``--regex'' (-e). Esta opción acepta una expresión regular, por lo que puede seleccionar múltiples CWE, por ejemplo, ``--regex "CWE-120|CWE-126"''. Si selecciona múltiples CWE con ``|'' en una línea de comandos, normalmente necesitará entrecomillar los parámetros (ya que un ``|'' sin comillas es el símbolo de tubería). Flawfinder está diseñado para cumplir el requisito CWE-Searchable.

Si su objetivo es reportar un subconjunto de CWE que están listadas en un archivo, eso se puede lograr en un sistema tipo Unix usando la opción ``--regex'' también conocida como ``-e''. El archivo debe estar en formato de expresión regular. Por ejemplo, ``flawfinder -e $(cat file1)'' reportaría solo los hallazgos que coincidieran con el patrón en ``file1''. Si file1 contuviera ``CWE-120|CWE-126'', solo reportaría los hallazgos que coincidieran con esas CWE.

Se puede encontrar una lista de todos los elementos de seguridad CWE (las firmas/patrones que busca flawfinder) usando la opción ``--listrules''. Cada línea lista el token de firma (normalmente un nombre de función) que puede dar lugar a un hallazgo, el nivel de riesgo predeterminado y la advertencia predeterminada (que incluye el identificador CWE predeterminado). Para la mayoría de los propósitos, esto también es suficiente si desea ver qué elementos de seguridad CWE se asignan a qué CWE, o lo contrario. Por ejemplo, para ver la mayoría de las firmas (nombres de funciones) que se asignan a CWE-327, sin ver el nivel de riesgo predeterminado ni el texto detallado de la advertencia, ejecute ``flawfinder --listrules | grep CWE-327 | cut -f1''. También puede ver los tokens sin una asignación CWE de esta manera ejecutando ``flawfinder -D --listrules | grep -v CWE-''. Sin embargo, aunque --listrules lista todos los elementos de seguridad CWE, solo lista las asignaciones predeterminadas de los elementos de seguridad CWE a los identificadores CWE. No incluye los refinamientos que aplica flawfinder (por ejemplo, al examinar los parámetros de las funciones).

Si desea un mapeo detallado y exacto entre los elementos de seguridad CWE y los identificadores CWE, el código fuente de flawfinder (incluido en la distribución) es el mejor lugar para esa información. Esta información detallada es principalmente de interés para esas pocas personas que intentan refinar las asignaciones CWE de flawfinder o refinar CWE en general. El código fuente documenta el mapeo entre los elementos de seguridad y los respectivos identificadores CWE, y es un único archivo Python. El conjunto de datos ``c_rules'' define la mayoría de las reglas, con referencia a una función que puede hacer más refinamientos. Puede buscar en el conjunto de datos nombres de funciones para ver qué CWE genera por defecto; si el primer parámetro no es ``normal'', entonces ese es el nombre de un método Python de refinamiento que puede seleccionar CWE diferentes (dependiendo de información adicional). A la inversa, puede buscar ``CWE-number'' y encontrar qué elementos de seguridad (firmas o patrones) se refieren a ese identificador CWE. Para la mayoría de las personas, esto es mucho más de lo que necesitan; la mayoría de las personas solo quieren escanear su código fuente para encontrar problemas rápidamente.

SEGURIDAD

El objetivo principal de esta herramienta es ayudar a encontrar vulnerabilidades para que puedan ser corregidas. Sin embargo, los desarrolladores y revisores deben saber cómo desarrollar software seguro para usar esta herramienta, porque de lo contrario, un necio con una herramienta sigue siendo un necio. Mi libro en https://dwheeler.com/secure-programs puede ayudar.

Esta herramienta debería ser, como máximo, una pequeña parte de un proceso de desarrollo de software más amplio diseñado para eliminar o reducir el impacto de las vulnerabilidades. Los desarrolladores y revisores necesitan saber cómo desarrollar software seguro, y necesitan aplicar este conocimiento para reducir los riesgos de vulnerabilidades en primer lugar.

Diferentes herramientas de búsqueda de vulnerabilidades tienden a encontrar vulnerabilidades diferentes. Por lo tanto, lo mejor es utilizar la revisión humana y una variedad de herramientas. Esta herramienta puede ayudar a encontrar algunas vulnerabilidades, pero de ninguna manera todas.

Tenga en cuenta que flawfinder está diseñado principalmente para encontrar vulnerabilidades no intencionales (errores comunes) buscando patrones específicos. Como resultado, es mucho menos probable que encuentre código malicioso (como caballos de Troya) que haya sido insertado intencionalmente. Los programadores maliciosos pueden insertar fácilmente código que no sea detectado por este tipo de herramienta. Esta herramienta solo debe usarse para encontrar vulnerabilidades no intencionales; se necesitan otras técnicas (como una revisión humana exhaustiva de todos los cambios) para encontrar código intencionalmente malicioso. (Puede intentar usar IA para analizar código malicioso, pero tenga cuidado, dicho código puede incluir inyecciones dirigidas a la IA que a su vez pueden hacer que la IA sea ineficaz o maliciosa).

Siempre debe analizar una copia del programa fuente que se está analizando, no un directorio que pueda ser modificado por un desarrollador mientras flawfinder realiza el análisis. Esto es especialmente cierto si no necesariamente confía en un desarrollador del programa que se está analizando. Si un atacante tiene control sobre los archivos mientras los está analizando, el atacante podría mover archivos o cambiar su contenido para evitar la exposición de un problema de seguridad (o crear la impresión de un problema donde no lo hay). Si le preocupan los programadores maliciosos, debería hacer esto de todos modos, porque después del análisis necesitará verificar que el código que finalmente se ejecuta es el código que analizó. Además, no use la opción --allowlink en tales casos; los atacantes podrían crear enlaces simbólicos maliciosos a archivos fuera de su área de código fuente (como /etc/passwd).

Los sistemas de gestión de código fuente (como GitHub, SourceForge y Savannah) definitivamente caen en esta categoría; si está manteniendo uno de esos sistemas, primero copie o extraiga los archivos en un directorio separado (que no pueda ser controlado por atacantes) antes de ejecutar flawfinder o cualquier otra herramienta de análisis de código.

Tenga en cuenta que flawfinder solo abre archivos regulares, directorios y (si se solicita) enlaces simbólicos; nunca abrirá otros tipos de archivos, incluso si se crea un enlace simbólico hacia ellos. Esto contrarresta a los atacantes que insertan tipos de archivo inusuales en el código fuente. Sin embargo, esto solo funciona si el sistema de archivos que se está analizando no puede ser modificado por un atacante durante el análisis, como se recomienda anteriormente. Esta protección tampoco funciona en plataformas Cygwin, desafortunadamente.

Los sistemas Cygwin (emulación de Unix sobre Windows) tienen un problema adicional si se usa flawfinder para analizar programas en los que el analista no puede confiar. El problema se debe a un defecto de diseño en Windows (que hereda de MS-DOS). En Windows y MS-DOS, ciertos nombres de archivo (por ejemplo, ``com1'') son tratados automáticamente por el sistema operativo como nombres de periféricos, y esto es cierto incluso cuando se proporciona una ruta completa. Sí, Windows y MS-DOS realmente están diseñados así de mal. Flawfinder aborda esto verificando qué es un objeto del sistema de archivos, y luego solo abriendo directorios y archivos regulares (y enlaces simbólicos si están habilitados). Desafortunadamente, esto no funciona en Cygwin; en al menos algunas versiones de Cygwin en algunas versiones de Windows, simplemente intentar determinar si un archivo es de tipo dispositivo puede hacer que el programa se cuelgue. Una solución alternativa es eliminar o renombrar cualquier nombre de archivo que se interprete como nombre de dispositivo antes de realizar el análisis. Estos llamados ``nombres reservados'' son CON, PRN, AUX, CLOCK$, NUL, COM1-COM9 y LPT1-LPT9, opcionalmente seguidos de una extensión (por ejemplo, ``com1.txt''), en cualquier directorio, y en cualquier caso (Windows no distingue entre mayúsculas y minúsculas).

Las listas de resultados almacenadas están destinadas a ser utilizadas por el mismo usuario que las creó. Una lista de resultados de una fuente no confiable podría contener resultados engañosos, como hallazgos fabricados o hallazgos omitidos; siempre use listas de resultados que usted mismo haya creado. Las listas de resultados se almacenan en el formato "pickle" de Python. Flawfinder ahora toma medidas para bloquear contenido malicioso en las listas de resultados (aunque las versiones antiguas no lo hacían). Sin embargo, flawfinder no puede detectar listas de resultados que contengan datos incorrectos pero estructuralmente válidos.

ERRORES

Flawfinder se basa en una coincidencia de patrones de texto simple, que forma parte de su diseño fundamental y no es fácil de cambiar. Este enfoque de diseño conduce a una serie de limitaciones fundamentales, por ejemplo, una mayor tasa de falsos positivos, y es la causa subyacente de la mayoría de los errores enumerados aquí. En el lado positivo, flawfinder no se confunde con muchas secuencias de preprocesador complicadas con las que otras herramientas a veces se atascan; flawfinder a menudo puede manejar código que no se puede enlazar, y a veces ni siquiera se puede compilar o construir.

Flawfinder está actualmente limitado a C/C++. Además, al analizar C++ se centra principalmente en el subconjunto C de C++. Por ejemplo, flawfinder no informa sobre expresiones como cin >> charbuf, donde charbuf es un arreglo de char. Esto se debe a que flawfinder no tiene información de tipos, y ">>" es seguro con muchos otros tipos; informar sobre todos los ">>" conduciría a demasiados falsos positivos. Dicho esto, está diseñado de modo que agregar soporte para otros lenguajes debería ser fácil donde su enfoque basado en texto pueda aplicarse de manera útil.

Flawfinder puede ser engañado por funciones definidas por el usuario o nombres de métodos que casualmente son iguales a los definidos como ``hits'' en su base de datos, y a menudo se activará con definiciones (así como usos) de funciones con el mismo nombre. Esto normalmente no es un problema para el código C. En el código C, una función con el mismo nombre que el de una rutina de biblioteca común a menudo indica que el desarrollador simplemente está reescribiendo una rutina de biblioteca común con la misma interfaz, digamos por motivos de portabilidad. Los programas C tienden a evitar reutilizar el mismo nombre para un propósito diferente (ya que en C los nombres de funciones son globales por defecto). Hay probabilidades razonables de que estas rutinas reescritas sean vulnerables a los mismos tipos de uso indebido, y por lo tanto, reutilizar estas reglas es un enfoque razonable. Sin embargo, esto puede ser un problema mucho más serio en el código C++ que usa intensivamente clases y espacios de nombres, ya que el mismo nombre de método puede tener muchos significados diferentes. La opción --falsepositive puede ayudar en cierta medida en este caso. Si esto es un problema serio, siéntase libre de modificar el programa, o procesar la salida de flawfinder a través de otras herramientas para eliminar los falsos positivos.

Los comandos del preprocesador incrustados en medio de una lista de parámetros de una llamada pueden causar problemas en el análisis; en particular, si una cadena se abre y luego se cierra varias veces usando una construcción #ifdef .. #else, flawfinder se confunde. Tales construcciones son de mal estilo, y confundirán a muchas otras herramientas también. Si debe analizar tales archivos, reescriba esas líneas. Afortunadamente, estas son bastante raras.

Flawfinder informa vulnerabilidades independientemente de los parámetros de "#if" o "#ifdef". Una construcción "#if VALUE" a menudo tendrá VALUE de 0 en algunos casos, y distinto de cero en otros. De manera similar, "#ifdef VALUE" tendrá VALUE definido en algunos casos, y no definido en otros. Flawfinder informa en todos los casos, lo que significa que flawfinder tiene la posibilidad de informar vulnerabilidades en todas las alternativas. Esto no es un error, es un comportamiento intencionado.

Flawfinder informará hits incluso si están entre un "#if 0" literal y "#endif". Sería posible cambiar esta situación particular, pero usar directamente "#if 0" para comentar código (aparte de durante la depuración) indica (1) que la eliminación es muy temporal (en cuyo caso aún deberíamos informarlo) o (2) prácticas de código muy pobres. Si desea deshacerse permanentemente del código, elimínelo en lugar de usar "#if 0", ya que siempre puede ver lo que era usando su software de control de versiones. Si no usa software de control de versiones, entonces ese es el error que necesita corregir ahora mismo.

Algunas construcciones complejas o inusuales pueden engañar a flawfinder. En particular, si un parámetro comienza con gettext(" y termina con ), flawfinder presumirá que el parámetro de gettext es una constante. Esto significa que se confundirá con patrones como gettext("hi") + function("bye"). En la práctica, esto no parece ser un problema; gettext() generalmente se envuelve alrededor de todo el parámetro.

La rutina para detectar arreglos de caracteres definidos estáticamente usa coincidencia de texto simple; algunas expresiones complicadas pueden hacer que se active o no se active inesperadamente.

Flawfinder busca patrones específicos conocidos por ser errores comunes. Flawfinder (o cualquier herramienta similar) no es una buena herramienta para encontrar código intencionalmente malicioso (por ejemplo, caballos de Troya); los programadores maliciosos pueden insertar fácilmente código que no sería detectado por este tipo de herramienta.

Flawfinder busca patrones específicos conocidos por ser errores comunes en el código de aplicación. Por lo tanto, es probable que sea menos efectivo analizando programas que no son código de capa de aplicación (por ejemplo, código de kernel o código autoalojado). Las técnicas aún pueden ser útiles; siéntase libre de reemplazar la base de datos si su situación es significativamente diferente de lo normal.

El formato de salida predeterminado de flawfinder (nombre de archivo:número de línea, seguido opcionalmente por un :número de columna) puede malinterpretarse si algún archivo fuente tiene nombres de archivo muy extraños. Los nombres de archivo que incrustan un carácter de nueva línea/salto de línea causarán saltos extraños, y es probable que los nombres de archivo que incluyen dos puntos (:) se malinterpreten. Esto es especialmente importante si la salida de flawfinder está siendo utilizada por otras herramientas, como filtros o editores de texto. Si está usando la salida de flawfinder en otras herramientas, considere usar su formato CSV en su lugar (que puede manejar esto). Si está examinando código nuevo, examine los archivos en busca de tales caracteres. Es increíblemente imprudente tener tales nombres de archivo de todos modos; muchas herramientas no pueden manejar tales nombres de archivo en absoluto. La nueva línea y el salto de línea se usan a menudo como delimitadores de datos internos. Los dos puntos se usan a menudo como caracteres especiales en los sistemas de archivos: MacOS lo usa como separador de directorios, Windows/MS-DOS lo usa para identificar letras de unidad, Windows/MS-DOS lo usa de manera inconsistente para identificar dispositivos especiales como CON:, y las aplicaciones en muchas plataformas usan los dos puntos para identificar URI/URL. Los nombres de archivo que incluyen espacios y/o tabulaciones no causan problemas a flawfinder, aunque tenga en cuenta que otras herramientas podrían tener problemas con ellos.

Flawfinder no está internacionalizado, por lo que actualmente no admite localización.

En general, flawfinder intenta pecar de precavido; tiende a informar hits, para que puedan examinarse más a fondo, en lugar de ignorarlos silenciosamente. Por lo tanto, flawfinder prefiere tener falsos positivos (informes que resultan no ser problemas) en lugar de falsos negativos (fallos al informar vulnerabilidades de seguridad). Pero esto es una generalidad; flawfinder usa heurísticas simplistas y simplemente no puede hacer todo "bien".

Es posible que las vulnerabilidades de seguridad no sean identificadas como tales por flawfinder y, a la inversa, algunos hits no son realmente vulnerabilidades de seguridad. Esto es cierto para todos los escáneres de seguridad estáticos, y es especialmente cierto para herramientas como flawfinder que usan un análisis léxico simple y un análisis de patrones para identificar vulnerabilidades potenciales. Aun así, puede servir como una ayuda útil para los humanos, ayudando a identificar lugares útiles para examinar más a fondo, y ese es el punto de esta simple herramienta.
