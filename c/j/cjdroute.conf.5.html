DESCRIPCIÓ

N

El archivo cjdroute.conf configura el motor de enrutamiento de cjdns, cjdns(8), generalmente a través de cjdroute

(1).

La configuración está escrita en una variación del formato JSON que también acepta comentarios tradicionales similares a los de C, como comentarios de una sola línea (//) y comentarios de múltiples líneas (/* y */). Además, los valores JSON no utilizados encontrados en cjdroute.conf son ignorados por cjdns y pueden usarse

como una forma de coment
arios compatibles con JSON.

CONFIGURACIÓ

N

"privateKey": "...

"
La clave privada de tu nodo. Debe mantenerse en secreto porque tu confidencialidad e integridad de datos dependen de
ella.

"publicKey": "...

"
La clave pública de tu nodo. Basada en tu clave privada. Está bien que cualquiera la
conozca.

"ipv6": "...

"
La dirección IPv6 de tu nodo cuando está en la red. Se genera utilizando los primeros 16 bytes de un doble SHA-512 de tu clave pública. Todas las direcciones IPv6 de cjdns deben comenzar con "fc" o de lo contrario son
inválidas.

"authorizedPasswords": [...

]
Un array de contraseñas que pueden usarse para conectarse (peer) a tu nodo.

"password": "...

"
Una contraseña que puede usarse para hacer peer con tu
nodo.

"user": "...

"
Una cadena legible que identifica qué contraseña está usando un peer en la interfaz de administración. Si se omite, la contraseña será identificada por su posición dentro del array (empezando desde
0)

Ejemplo:
"authorizedPasswords":
[
{ "password": "AnExamplePassword", "user": "Bob" },
{ "password": "YetAnotherExample", "user": "Alice" },
{ "password": "j3fus4r3gkhv80xdz1yqc0qvn1p91hr", "user": "Eve" }

]

"admin": {...

}
Un objeto que define dónde enlazar el servidor RPC de administración, así como la contraseña para el servidor RPC de administración. Las dos cadenas requeridas son "bind", que debe estar en el formato "IP:PORT", y "password", que preferiblemente debería ser una larga cadena aleatoria de
caracteres.

"interfaces": {...

}
Un objeto que define a qué interfaces se enlazará cjdns y con qué peers conectará. Hay dos interfaces diferentes, UDPInterface y ETHInterface, ambas son arrays. Dentro de cada array hay una variedad de diferentes opciones

"bind": "...

"
Define a qué debe enlazarse la interfaz. En UDPInterface, el enlace es una cadena IP:PORT, como "0.0.0.0:12345", mientras que en ETHInterface el enlace es una interfaz de red, como
"eth0".

"beacon":

Entero
Esta opción solo se encuentra en ETHInterface y define si se deben enviar o escuchar balizas de autoconexión. Esto es útil para una red local con configuración cero (zeroconf).
0 -- Deshabilitado.
1 -- Aceptar balizas entrantes e intentar conectarse al remitente.
2 -- Aceptar balizas e
ntrantes y transmitir b
alizas a la red local.

"connectTo": {...

}
Define a qué nodos debe conectarse cjdns con la interfaz especificada. Se pueden colocar múltiples nodos en un solo "connectTo" siempre que cada uno esté separado por comas. Si un nodo está fuera de línea o se desconecta durante el tiempo de ejecución, cjdns intentará reconectar a intervalos regulares. La única diferencia en esta opción entre UDPInterface y ETHInterface es que UDPInterface se conecta a un "IP:PORT" mientras que ETHInterface se conecta a una dirección MAC.

Ejemplo de UDPInterface:
"connectTo":

{
"1.2.3.4:54321":
{
"login": "login From Your Peer's authorizedPasswords",
"password": "password From Your Peer's authorizedPasswords",
"publicKey": "Your Peer's publicKey.k"
},
"5.6.7.8:46321":
{
"login": "cueball",
"password": "Correct Horse Battery Staple",
"publicKey": "Other Peer's publicKey.k"
}
}

"router": {...

}
Un objeto que contiene información de configuración sobre el enrutador

"interface": {...

}
Define el tipo de interfaz utilizada para conectarse a la red cjdns. Requiere una cadena "type" y opcionalmente una cadena "tunDevice". La cadena "type" define el tipo de interfaz utilizada, sin embargo, solo "TUNInterface" está soportada en el momento. La cadena "tunDevice" define el nombre de un dispositivo TUN persistente a usar, lo cual es útil para iniciar cjdroute como su propio usuario en lugar de
root.

"ipTunnel": {...

}
Un sistema para tunelizar IPv4 de ICANN e IPv6 de ICANN a través de cjdns. Esto usa la capa de conmutación de cjdns como transportador de VPN.

NOTA: Simplemente editar tu archivo de configuración no es suficiente para configurar una puerta de enlace ipTunnel. Por favor, lee tunnel/README.md en el árbol git de cjdns para más

información

"allowedConnections": [...

]
Nodos permitidos para conectarse a nosotros, especificados por su clave pública, y qué dirección(s) IP darles. Está bien especificar solo una dirección.

Ejemplo

:

"allowedConnections":
[
{
"publicKey": "f64hfl7c4uxt6krmhPutTheRealAddressOfANodeHere7kfm5m0.k",
"ip4Address": "192.168.1.24",
"ip4Prefix": 24,
"ip6Address": "2001:123:ab::10",
"ip6Prefix": 0
},
{
"publicKey": "ydq8csdk8p8ThisIsJustAnExampleAddresstxuyqdf27hvn2z0.k",
"ip4Address": "192.168.1.25",
"ip4Prefix": 24
}

]

"outgoingConnections": [...

]
Un array de nodos a los que conectarse y pedir direcciones IP.

Ejemplo

:

"outgoingConnections":
[
"6743gf5tw80ExampleExampleExampleExamplevlyb23zfnuzv0.k",
"pw9tfmr8pcrExampleExampleExampleExample8rhg1pgwpwf80.k",
"g91lxyxhq0kExampleExampleExampleExample6t0mknuhw75l0.k"

]

"security": [...

]
Un array que define a qué usuario cambiar después del inicio y si excluir al proceso Angel de este cambio de usuario.

"setuser":

"username"
Usuario al que cambiar después del inicio, por razones de seguridad. El valor predeterminado es
"nobody".

"exemptAngel":

Entero
Si se excluye o no al proceso Angel del cambio de usuario. El Angel es una pequeña pieza de código aislada que existe fuera del estricto sandbox del núcleo pero no maneja tráfico de red. Esta opción debe estar habilitada para que ipTunnel establezca automáticamente las direcciones IP para el dispositivo TUN.
