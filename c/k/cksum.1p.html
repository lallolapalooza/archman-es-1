CKSUM(1P) Manual del Programador POSIX CKSUM(1P)

PRÓLOGO

Esta página manual forma parte del Manual del Programador POSIX. La implementación de Linux de esta interfaz puede diferir (consulte la página manual de Linux correspondiente para detalles del comportamiento de Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

cksum — escribe sumas de comprobación y tamaños de archivos

SINOPSIS

cksum [archivo...]

DESCRIPCIÓN

La utilidad cksum calculará y escribirá en la salida estándar una verificación de redundancia cíclica (CRC) para cada archivo de entrada, y también escribirá en la salida estándar el número de octetos de cada archivo. El CRC utilizado se basa en el polinomio utilizado para la verificación de errores CRC en el estándar ISO/IEC 8802‐3:1996 (Ethernet).

La codificación para la suma de comprobación CRC está definida por el polinomio generador:

G(x)=x32+x26+x23+x22+x16+x12+x11+x10+x8+x7+x5+x4+x2+x+1

Matemáticamente, el valor CRC correspondiente a un archivo dado se definirá mediante el siguiente procedimiento:

1.
Los n bits a evaluar se consideran los coeficientes de un polinomio módulo 2 M(x) de grado n-1. Estos n bits son los bits del archivo, siendo el bit más significativo el bit más significativo del primer octeto del archivo y el último bit siendo el bit menos significativo del último octeto, rellenados con bits cero (si es necesario) para alcanzar un número entero de octetos, seguidos de uno o más octetos que representan la longitud del archivo como un valor binario, con el octeto menos significativo primero. Se utilizará el número más pequeño de octetos capaz de representar este entero.
2.
M(x) se multiplica por x32 (es decir, se desplaza a la izquierda 32 bits) y se divide por G(x) usando división módulo 2, produciendo un resto R(x) de grado ≤ 31.
3.
Los coeficientes de R(x) se consideran una secuencia de 32 bits.
4.
La secuencia de bits se complementa y el resultado es el CRC.

OPCIONES

Ninguna.

OPERANDOS

Se admitirá el siguiente operando:

archivo
Una ruta de acceso de un archivo a comprobar. Si no se especifican operandos archivo , se usará la entrada estándar.

ENTRADA ESTÁNDAR

Se usará la entrada estándar si no se especifican operandos archivo , y se usará si un operando archivo es '-' y la implementación trata el '-' como significando entrada estándar. De lo contrario, no se usará la entrada estándar. Vea la sección ARCHIVOS DE ENTRADA.

ARCHIVOS DE ENTRADA

Los archivos de entrada pueden ser de cualquier tipo.

VARIABLES DE ENTORNO

Las siguientes variables de entorno afectarán la ejecución de cksum:

LANG
Proporciona un valor por defecto para las variables de internacionalización que no están definidas o son nulas. (Vea el Volumen de Definiciones Básicas de POSIX.1‐2017, Sección 8.2, Variables de Internacionalización para la precedencia de las variables de internacionalización utilizadas para determinar los valores de las categorías de configuración regional.)
LC_ALL
Si se establece en un valor de cadena no vacío, anula los valores de todas las demás variables de internacionalización.
LC_CTYPE
Determina la configuración regional para la interpretación de secuencias de bytes de datos de texto como caracteres (por ejemplo, caracteres de un solo byte en oposición a multibyte en los argumentos).
LC_MESSAGES

Determina la configuración regional que debe usarse para afectar el formato y el contenido de los mensajes de diagnóstico escritos en la salida de error estándar.
NLSPATH
Determina la ubicación de los catálogos de mensajes para el procesamiento de LC_MESSAGES.

EVENTOS ASÍNCRONOS

Por defecto.

SALIDA ESTÁNDAR

Para cada archivo procesado con éxito, la utilidad cksum escribirá en el siguiente formato:

"%u %d %s\n", <suma de comprobación>, <nº de octetos>, <ruta de acceso>

Si no se especificó ningún operando archivo , la ruta de acceso y su <espacio> inicial se omitirán.

SALIDA DE ERROR ESTÁNDAR

La salida de error estándar se usará solo para mensajes de diagnóstico.

ARCHIVOS DE SALIDA

Ninguno.

Ninguna.

ESTADO DE SALIDA

Se devolverán los siguientes valores de salida:

0
Todos los archivos fueron procesados con éxito.
>0
Ocurrió un error.

USO DE LA APLICACIÓN

La utilidad cksum se usa típicamente para comparar rápidamente un archivo sospechoso contra una versión confiable del mismo, como para asegurar que los archivos transmitidos a través de medios ruidosos llegan intactos. Sin embargo, esta comparación no puede considerarse criptográficamente segura. Las posibilidades de que un archivo dañado produzca el mismo CRC que el original son pequeñas; el engaño deliberado es difícil, pero probablemente no imposible.

Aunque los archivos de entrada a cksum pueden ser de cualquier tipo, los resultados no necesitan ser los que se esperarían en archivos de dispositivo especiales de carácter o en tipos de archivo no descritos por el Volumen de Interfaces del Sistema de POSIX.1‐2017. Dado que este volumen de POSIX.1‐2017 no especifica el tamaño de bloque utilizado al hacer la entrada, las sumas de comprobación de archivos especiales de carácter no necesitan procesar todos los datos en esos archivos.

El algoritmo se expresa en términos de un flujo de bits dividido en octetos. Si un archivo se transmite entre dos sistemas y sufre alguna transformación de datos (como cambiar el orden de bytes little-endian a big-endian), no pueden esperarse valores CRC idénticos. Las implementaciones que realizan tales transformaciones pueden extender cksum para manejar tales situaciones.

unsigned long memcrc(const unsigned char *b, size_t n)
{
/*  Argumentos de entrada:
 *  const unsigned char*   b == secuencia de bytes para calcular la suma de comprobación
 *  size_t                 n == longitud de la secuencia
 */
    register size_t i;
    register unsigned c, s = 0;
    for (i = n; i > 0; --i) {
        c = *b++;
        s = (s << 8) ^ crctab[(s >> 24) ^ c];
    }
    /* Extender con la longitud de la cadena. */
    while (n != 0) {
        c = n & 0377;
        n >>= 8;
        s = (s << 8) ^ crctab[(s >> 24) ^ c];
    }
    return ~s;
}

La práctica histórica de escribir el número de «bloques» ha sido cambiada por escribir el número de octetos, ya que esto último no es solo más útil, sino también porque las implementaciones históricas no han sido consistentes en definir lo que significaba un «bloque».

El algoritmo utilizado fue seleccionado para aumentar la robustez operativa de cksum. No se seleccionó ni el algoritmo de System V ni el de BSD sum . Dado que cada uno de estos era diferente y cada uno era el comportamiento predeterminado en esos sistemas, no había un compromiso realista disponible si se seleccionaba alguno de los dos: alguna serie de aplicaciones históricas se rompería. Por lo tanto, el nombre fue cambiado a cksum. Aunque los comandos sum históricos probablemente continuarán siendo proporcionados por muchos años, los programas diseñados para la portabilidad entre sistemas deberían usar el nuevo nombre.

El algoritmo seleccionado está basado en el utilizado por el estándar ISO/IEC 8802‐3:1996 (Ethernet) para el campo de secuencia de comprobación de trama. El algoritmo utilizado no coincide con la definición técnica de una suma de comprobación; el término se usa por razones históricas. La longitud del archivo se incluye en el cálculo del CRC porque esto paralela la inclusión de un campo de longitud por Ethernet en su CRC, pero también porque protege contra colisiones inadvertidas entre archivos que comienzan con diferentes series de octetos ceros. La probabilidad de que dos archivos diferentes produzcan CRCs idénticos es mucho mayor cuando sus longitudes no se consideran. Mantener la longitud y la suma de comprobación del archivo por separado produciría un algoritmo ligeramente más robusto, pero el uso histórico siempre ha sido que un solo número (la suma de comprobación tal como se imprime) representa la firma del archivo. Se decidió que el uso histórico era la consideración más importante.

Las propuestas tempranas contenían modificaciones al algoritmo Ethernet que implicaban extraer valores de la tabla siempre que un resultado intermedio se volvía cero. Se demostró que esto era menos robusto que el método actual y matemáticamente difícil de describir o justificar.

El cálculo utilizado es idéntico al dado en el pseudocódigo en el artículo de Sarwate referenciado. La versión en pseudocódigo es:

X <- 0; Y <- 0;
for i <- m -1 step -1 until 0 do
    begin
    T <- X(1) ^ A[i];
    X(1) <- X(0); X(0) <- Y(1); Y(1) <- Y(0); Y(0) <- 0;
    comment: f[T] and f'[T] denote the T-th words in the
        table f and f' ;
    X <- X ^ f[T]; Y <- Y ^ f'[T];
    end

El pseudocódigo se reproduce exactamente tal como se dio; sin embargo, tenga en cuenta que en el caso de cksum, A[i] representa un byte del archivo, las palabras X y Y se tratan como un solo valor de 32 bits, y las tablas f y f' son una sola tabla que contiene valores de 32 bits.

El artículo de Sarwate referenciado también discute la generación de la tabla.
