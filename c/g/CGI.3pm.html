N

CGI.pm es una solución estable, completa y madura para procesar y preparar solicitudes y respuestas HTTP. Las características principales incluyen el procesamiento de envíos de formularios, la subida de archivos, la lectura y escritura de cookies, la generación y manipulación de cadenas de consulta, y el procesamiento y preparación de cabeceras

HTTP.

CGI.pm se desempeña muy bien en un entorno CGI.pm estándar y también incluye soporte integrado para mod_perl y mod_perl2, así como

FastCGI.

Tiene la ventaja de haberse desarrollado y refinado durante 20 años con la aportación de docenas de colaboradores y haberse desplegado en miles de sitios web. CGI.pm se incluyó en la distribución de perl desde perl v5.4 hasta v5.20, sin embargo, ahora ha sido eliminado del núcleo de perl.

Estilo de

programación

Hay dos estilos de programación con CGI.pm, un estilo orientado a objetos (OO) y un estilo orientado a funciones. Se recomienda usar el estilo OO, ya que CGI.pm creará un objeto interno por defecto cuando las funciones se llamen proceduralmente y no tendrás que preocuparte por que los nombres de los métodos colisionen con las funciones incorporadas de

perl.

En el estilo orientado a objetos, creas uno o más objetos CGI y luego usas métodos de objeto para crear los diversos elementos de la página. Cada objeto CGI comienza con la lista de parámetros con nombre que fueron pasados a tu script CGI por el servidor. Puedes modificar los objetos, guardarlos en un archivo o base de datos y recrearlos. Como cada objeto corresponde al "estado" del script CGI, y como la lista de parámetros de cada objeto es independiente de las demás, esto te permite guardar el estado del script y restaurarlo más

tarde.

Por ejemplo, usando el estilo orientado a

objetos: 
#!/usr/bin/env perl
use strict;
use warnings;
use CGI;                             # cargar rutinas CGI
my $q = CGI->new;                    # crear nuevo objeto CGI
print $q->header;                    # crear la cabecera
HTTP

En el estilo orientado a funciones, hay un objeto CGI por defecto con el que rara vez tratas directamente. En su lugar, simplemente llamas a funciones para recuperar parámetros CGI, gestionar cookies, y así sucesivamente. El siguiente ejemplo es idéntico al anterior, en términos de salida, pero usa la interfaz orientada a funciones. Las principales diferencias son que ahora necesitamos importar un conjunto de funciones en nuestro espacio de nombres (generalmente las funciones "estándar"), y no necesitamos crear el objeto

CGI. 
#!/usr/bin/env perl
use strict;
use warnings;
use CGI qw/:standard/;           # cargar rutinas CGI estándar
print header();                  # crear la cabecera
HTTP

La mayoría de las rutinas de CGI.pm aceptan varios argumentos, a veces tantos como 20 opcionales. Para simplificar esta interfaz, todas las rutinas usan un estilo de llamada con argumentos con nombre que se ve

así:

Cada nombre de argumento está precedido por un guion. Ni la mayúscula ni el orden importan en la lista de argumentos: -type, -Type y -TYPE son todos aceptables. De hecho, solo el primer argumento necesita comenzar con un guion. Si hay un guion presente en el primer argumento, CGI.pm asume guiones para los siguientes

argumentos.

Varias rutinas se llaman comúnmente con solo un argumento. En el caso de estas rutinas, puedes proporcionar el único argumento sin un nombre de argumento. header() resulta ser una de estas rutinas. En este caso, el único argumento es el tipo de

documento.

;

continuación.

A veces los argumentos con nombre esperan un escalar, a veces una referencia a un array, y a veces una referencia a un hash. A menudo, puedes pasar cualquier tipo de argumento y la rutina hará lo que sea más apropiado. Por ejemplo, la rutina param() se usa para establecer un parámetro CGI a un valor único o multivalorado. use warnings;

    $q->param( -name => 'counter',-value => $_ );

while (!eof($in_fh)) {
    my $q = CGI->new($in_fh);
    print $q->param('counter'),"\n";

GENERANDO DOCUMENTOS

DINÁMICOS

La mayoría de las funciones de CGI.pm tratan sobre la creación de documentos al vuelo. Generalmente producirás la cabecera HTTP primero, seguida del documento en sí. CGI.pm proporciona funciones para generar cabeceras HTTP de varios

tipos.

Cada una de estas funciones produce un fragmento de HTTP que puedes imprimir directamente para que sea procesado por el navegador, añadir a una cadena, o guardar en un archivo para su uso

posterior.

Creando una cabecera http

estándar

Normalmente, lo primero que harás en cualquier script CGI es imprimir una cabecera HTTP. Esto le dice al navegador qué tipo de documento esperar, y proporciona otra información opcional, como el idioma, la fecha de caducidad, y si se debe almacenar en caché el documento. La cabecera también puede ser manipuladed para propósitos especiales, como el push del servidor y páginas de pago por

visión. 
use strict;
use warnings;
use CGI;
my $cgi = CGI->new;
print $cgi->header;
    -o-
print $cgi->header('image/gif');
    -o-
print $cgi->header('text/html','204 No response');
    -o-
print $cgi->header(
    -type       => 'image/gif',
    -nph        => 1,
    -status     => '402 Payment required',
    -expires    => '+3d',
    -cookie     => $cookie,
    -charset    => 'utf-8',
    -attachment => 'foo.gif',
    -Cost       => '$2.00'
)
;

header() devuelve la cabecera Content-type:. Puedes proporcionar tu propio tipo MIME si lo deseas, de lo contrario por defecto es text/html. Un segundo parámetro opcional especifica el código de estado y un mensaje legible para humanos. Por ejemplo, puedes especificar 204, "No response" para crear un script que le diga al navegador que no haga nada en absoluto. Ten en cuenta que RFC 2616 espera que la frase legible para humanos esté presente además del código de estado

numérico.

El último ejemplo muestra el estilo de argumentos con nombre para pasar argumentos a los métodos de CGI usando parámetros con nombre. Los parámetros reconocidos son -type, -status, -expires, y -cookie. Cualquier otro parámetro con nombre será eliminado de sus guiones iniciales y convertido en campos de cabecera, permitiéndote especificar cualquier cabecera HTTP que desees. Los guiones bajos internos serán convertidos en

guiones: 
print $cgi->header( -Content_length => 3002 )
;

La mayoría de los navegadores no almacenarán en caché la salida de los scripts CGI. Cada vez que el navegador recarga la página, el script se invoca de nuevo. Puedes cambiar este comportamiento con el parámetro -expires. Cuando especificas un intervalo de expiración absoluto o relativo con este parámetro, algunos navegadores y servidores proxy almacenarán en caché la salida del script hasta la fecha de expiración indicada. Las siguientes formas son todas válidas para el campo

-expires: 
+30s                                  30 segundos desde ahora
+10m                                  diez minutos desde ahora
+1h                                   una hora desde ahora
-1d                                   ayer (es decir, "¡LO ANTES POSIBLE!")
now                                   inmediatamente
+3M                                   en tres meses
+10y                                  en diez años
Thursday, 25-Apr-2018 00:40:33 GMT    en la fecha y hora
indicadas

El parámetro -cookie genera una cabecera que le dice al navegador que proporcione una "cookie mágica" durante todas las transacciones posteriores con tu script. Algunas cookies tienen un formato especial que incluye atributos interesantes como el tiempo de expiración. Usa el método cookie() para crear y recuperar cookies de

sesión.

El parámetro -nph, si se establece a un valor verdadero, emitirá las cabeceras correctas para funcionar con un script NPH (no-parse-header). Es importante usarlo con ciertos servidores que esperan que todos sus scripts sean

NPH.

El parámetro -charset puede usarse para controlar el juego de caracteres enviado al navegador. Si no se proporciona, por defecto es ISO-8859-1. Como efecto secundario, esto establece también el método charset(). Ten en cuenta que el valor por defecto de ISO-8859-1 puede no tener sentido para todos los tipos de contenido, por

ejemplo: 
Content-Type: image/gif; charset=ISO-8859-
1

En el caso anterior necesitas pasar -charset => '' para evitar que se use el valor por

defecto.

El parámetro -attachment puede usarse para convertir la página en un archivo adjunto. En lugar de mostrar la página, algunos navegadores pedirán al usuario que la guarde en disco. El valor del argumento es el nombre sugerido para el archivo guardado. Para que esto funcione, puede que tengas que establecer el -type a "application/octet-stream"

.

El parámetro -p3p añadirá una etiqueta P3P a la cabecera de salida. El parámetro puede ser una referencia a un array o una cadena delimitada por espacios de etiquetas P3P. Por

ejemplo: 
print $cgi->header( -p3p => [ qw/ CAO DSP LAW CURa / ] );
print $cgi->header( -p3p => 'CAO DSP LAW CURa' )
;

En cualquier caso, la cabecera de salida se formateará

como: 
P3P: policyref="/w3c/p3p.xml" cp="CAO DSP LAW
CURa"

CGI.pm aceptará cabeceras válidas de múltiples líneas cuando cada línea esté separada por un valor CRLF ("\r\n" en la mayoría de las plataformas) seguido de al menos un espacio. Por

ejemplo: 
print $cgi->header( -ingredients => "ham\r\n\seggs\r\n\sbacon" )
;

Una entrada de cabecera de múltiples líneas no válida provocará una excepción. Cuando se reciben cabecer

as de múltiples líneas, CGI.pm siempre las devolverá como una sola línea, de acuerdo con las reglas de p
legado de RFC 2616: los saltos de línea serán eliminados, mientras que el espacio en blanco permanecerá.

Generando una cabecera de

redirección 
print $q->redirect( 'http://somewhere.else/in/movie/land' )
;

A veces no quieres producir un documento tú mismo, sino simplemente redirigir el navegador a otro lugar, quizás eligiendo una URL basada en la hora del día o la identidad del

usuario.

El método redirect() redirige el navegador a una URL diferente. Si usas la redirección de esta manera, deberías no imprimir también una

cabecera.

Se te aconseja usar URLs completas (absolutas con respecto a la URL actual o incluso incluyendo la parte http: o ftp:) en las peticiones de redirección, ya que las URLs relativas son resueltas por el agente de usuario del cliente, por lo que pueden no hacer lo que quieras o esperas que

hagan.

También puedes usar argumentos con

nombre: 
print $q->redirect(
    -uri    => 'http://somewhere.else/in/movie/land',
    -nph    => 1,
    -status => '301 Moved Permanently'
)
;

Todos los argumentos con nombre reconocidos por header() también son reconocidos por redirect(). Sin embargo, la mayoría de las cabeceras HTTP, incluyendo aquellas generadas por -cookie y -target, son ignoradas por el

navegador.

El parámetro -nph, si se establece a un valor verdadero, emitirá las cabeceras correctas para funcionar con un script NPH (no-parse-header). Es importante usarlo con ciertos servidores, como Microsoft IIS, que esperan que todos sus scripts sean

NPH.

El parámetro -status establecerá el estado de la redirección. HTTP define varios códigos de estado de redirección diferentes posibles, y el valor por defecto si no se especifica es 302, que significa "movido temporalmente". Puedes cambiar el estado a otro código de estado si lo

deseas.

Procesamiento de un campo de subida de

archivo

Conceptos

básicos

Cuando se procesa el formulario, puede recuperar un manejador compatible con IO::File para un campo de subida de archivo de esta

manera: 
use autodie;
# Se puede devolver undef si no es un manejador de archivo válido
if ( my $io_handle = $q->upload('field_name') ) {
    open ( my $out_file,'>>','/usr/local/web/users/feedback' );
    while ( my $bytesread = $io_handle->read($buffer,1024) ) {
        print $out_file $buffer;
    }
}

En un contexto de lista, upload() devolverá una lista de manejadores de archivo. Esto hace posible procesar formularios que usan el mismo nombre para múltiples campos de

subida.

Si desea el nombre de archivo introducido para el archivo, simplemente llame a param

(): 
my $filename = $q->param('field_name')
;

Diferentes navegadores devolverán cosas ligeramente diferentes para el nombre. Algunos navegadores devuelven solo el nombre de archivo. Otros devuelven la ruta completa al archivo, usando las convenciones de ruta de la máquina del usuario. Independientemente, el nombre devuelto es siempre el nombre del archivo en la máquina del usuario, y no está relacionado con el nombre del archivo temporal que CGI.pm crea durante el spooling de subida (véase más abajo)

.

Cuando se sube un archivo, el navegador generalmente envía junto con él información en los encabezados Content-Type (tipo MIME) y Content-Disposition (nombre de archivo). Para recuperar esta información, llame a uploadInfo(). Devuelve una referencia a un hash que contiene todos los encabezados del

documento. 
my $filehandle = $q->upload( 'uploaded_file' );
my $type       = $q->uploadInfo( $filehandle )->{'Content-Type'};
if ( $type ne 'text/html' ) {
    die "HTML FILES ONLY!";
}

Tenga en cuenta que debe usar ->upload o ->param para obtener el manejador de archivo que se pasará a uploadInfo, ya que internamente esto está representado como un objeto File::Temp (que es lo que devolverá ->upload o ->param). Al usar ->Vars obtendrá el nombre de archivo literal en lugar del objeto File::Temp, que no devolverá nada cuando se pase a uploadInfo. Así que no use ->

Vars.

Al subir múltiples archivos, llame a ->param() en contexto de lista para recuperar una lista de manejadores de archivo que puede usar al llamar a ->

uploadInfo. 
my @filehandles = $q->param('uploaded_file');
for my $fh (@filehandles) {
  my $info = $q->uploadInfo($fh);
  ...
}

Si está utilizando una máquina que reconoce los modos de datos "texto" y "binario", asegúrese de comprender cuándo y cómo usarlos (véase el libro Camel). De lo contrario, puede encontrar que los archivos binarios se corrompen durante las subidas de

archivos.

Acceso directo a los archivos

temporales

Al procesar un archivo subido, CGI.pm crea un archivo temporal en su disco duro y le pasa un manejador de archivo a ese archivo. Después de que termine con el manejador de archivo, CGI.pm desvincula (elimina) el archivo temporal. Si lo necesita, puede acceder al archivo temporal directamente. Puede acceder al archivo temporal de una subida de archivo pasando el manejador de archivo al método tmpFileName()

: 
my $filehandle  = $q->upload( 'uploaded_file' );
my $tmpfilename = $q->tmpFileName( $filehandle )
;

Al igual que con ->uploadInfo, se prefiere usar la referencia devuelta por ->upload o ->param, aunque a diferencia de ->uploadInfo, los nombres de archivo simples también funcionan si es posible, por compatibilidad hacia

atrás.

El archivo temporal se eliminará automáticamente cuando su programa salga, a menos que lo renombre manualmente o establezca $CGI::UNLINK_TMP_FILES a 0. En algunos sistemas operativos (como Windows NT), necesitará cerrar el manejador de archivo del archivo temporal antes de que su programa salga. De lo contrario, el intento de eliminar el archivo temporal

fallará.

Cambios en el manejo de archivos temporales (v4.

05+)

El manejo de archivos temporales de CGI.pm fue significativamente refactorizado, esta lógica ahora se delega por completo a File::Temp (que está envuelto en un objeto de compatibilidad, CGI::File::Temp - NO USE ESTE PAQUETE DIRECTAMENTE). Como consecuencia, la variable PRIVATE_TEMPFILES ha sido eliminada junto con la obsolescencia de la rutina private_tempfiles y la eliminación completa del paquete CGITempFile. El $CGITempFile::TMPDIRECTORY ya no se usa para establecer el directorio temporal, consulte la documentación de File::Temp si desea anular la configuración predeterminada en ese paquete (la variable de entorno TMPDIR sigue estando disponible en algunas plataformas). Para plataformas de Windows, el orden del directorio temporal permanece como antes: TEMP > TMP > WINDIR ( > TMPDIR ) así que si tiene alguno de estos en uso en scripts existentes, deberían seguir

funcionando.

El paquete Fh todavía existe pero no hace nada, la clase CGI::File::Temp es una subclase tanto de File::Temp como del paquete vacío Fh, así que si tiene algún código que comprueba que el manejador de archivo es isa Fh, esto debería seguir

funcionando.

Cuando obtenga el manejador de archivo interno, recibirá un objeto File::Temp, esto debería ser transparente ya que File::Temp es isa IO::Handle y es isa IO::Seekable, lo que significa que se comporta como antes. Si está haciendo algo fuera de lo ordinario con respecto a los archivos temporales, debería probar su código antes de desplegar esta actualización y consultar la documentación de File::Temp para más

información.

Manejo de subidas de archivo

interrumpidas

Ocasionalmente hay problemas relacionados con el análisis del archivo subido. Esto generalmente sucede cuando el usuario presiona "Detener" antes de que la subida haya terminado. En este caso, CGI.pm devolverá undef para el nombre del archivo subido y establecerá cgi_error() en la cadena "400 Bad request (malformed multipart POST)". Este mensaje de error está diseñado para que pueda incorporarlo en un código de estado para enviarlo al navegador.

Ejemplo: 
my $file = $q->upload( 'uploaded_file' );
if ( !$file && $q->cgi_error ) {
    print $q->header( -status => $q->cgi_error );
    exit 0;
}

Barras de progreso para subidas de archivo y evitar archivos

temporales

CGI.pm le da acceso de bajo nivel a la gestión de subida de archivos a través de un gancho de subida de archivo. Puede usar esta característica para desactivar por completo el almacenamiento en archivo temporal de las subidas de archivos, o potencialmente escribir su propio medidor de progreso de subida de

archivo.

Esto es muy similar a la facilidad UPLOAD_HOOK disponible en Apache::Request, con la excepción de que el primer argumento de la devolución de llamada es un objeto Apache::Upload, aquí es el nombre de archivo

remoto. 
my $q = CGI->new( \&hook [,$data [,$use_tempfile]] );
sub hook {
    my ( $filename, $buffer, $bytes_read, $data ) = @_;
    print "Read $bytes_read bytes of $filename\n";
}

El campo $data es opcional; le permite pasar información de configuración (p. ej., un manejador de base de datos) a su devolución de llamada de

gancho.

El campo $use_tempfile es un indicador que le permite activar y desactivar el uso de CGI.pm de un archivo temporal basado en disco durante la subida de archivo. Si establece esto en un valor FALSO (predeterminado VERDADERO), entonces "$q->param('uploaded_file')" todavía devolverá un typeglob que se puede usar para acceder a un manejador de archivo y el nombre de archivo del archivo subido, sin embargo, el manejador de archivo será un manejador a un archivo vacío. La existencia de su gancho hace que CGI.pm evite escribir en ese manejador de archivo (que probablemente era lo que pretendía cuando estableció $use_tempfile en off)

.

El método uploadInfo() se puede usar en el typeglob que se le devolvió cuando llamó a "$q->param('upload_file')" para devolver información sobre el/los archivo(s) subido(s). Para subidas de múltiples archivos, use el método param() en contexto de lista para recuperar todos los

typeglobs. 
my (@filehandles) = $cgi->param('upfile');
foreach my $fh (@filehandles) {
  my $info = $cgi->uploadInfo($fh);
  ...
}

Si está utilizando la interfaz orientada a funciones, llame al método CGI::upload_hook() antes de llamar a param() o a cualquier otra función

CGI: 
CGI::upload_hook( \&hook [,$data [,$use_tempfile]] )
;

Este método no se exporta de forma predeterminada. Tendrá que importarlo explícitamente si desea usarlo sin el prefijo CGI::

.

Solución de problemas de subidas de archivo en

Windows

Si está utilizando CGI.pm en una plataforma de Windows y encuentra que los archivos binarios se vuelven ligeramente más grandes cuando se suben, pero que los archivos de texto permanecen iguales, entonces se ha olvidado de activar el modo binario en el manejador de archivo de salida. Formas antiguas de procesar subidas de

archivo

Esta sección está aquí por completitud. Si está construyendo una nueva aplicación con CGI.pm, puede

omitirla.

La forma original de procesar subidas de archivo con CGI.pm era usar param(). El valor que devuelve tiene una naturaleza dual como nombre de archivo y como manejador de archivo ligero. Esta naturaleza dual es problemática si sigue la práctica recomendada de tener "use strict" en su código. Perl se quejará cuando intente usar una cadena como manejador de archivo. EVITANDO ATAQUES DE DENEGACIÓN DE

SERVICIO

Un problema potencial con CGI.pm es que, por defecto, intenta procesar envíos de formularios POST sin importar cuán grandes sean. Un hacker astuto podría atacar su sitio enviando a un script CGI un POST enorme de muchos gigabytes. CGI.pm intentará leer todo el POST en una variable, creciendo enormemente en tamaño hasta que se quede sin memoria. Mientras el script intenta asignar la memoria, el sistema puede ralentizarse drásticamente. Esta es una forma de ataque de denegación de

servicio.

Otro posible ataque es que el usuario remoto fuerce a CGI.pm a aceptar una carga de archivo enorme. CGI.pm aceptará la carga y la almacenará en un directorio temporal incluso si su script no espera recibir un archivo cargado. CGI.pm eliminará el archivo automáticamente cuando termine, pero mientras tanto el usuario remoto puede haber llenado el espacio en disco del servidor, causando problemas para otros

programas.

La mejor manera de evitar ataques de denegación de servicio es limitar la cantidad de memoria, tiempo de CPU y espacio en disco que los scripts CGI pueden usar. Algunos servidores web vienen con instalaciones integradas para lograr esto. En otros casos, puede usar los comandos de shell limit o ulimit para poner límites al uso de recursos de

CGI.

CGI.pm también tiene algunas protecciones integradas simples contra ataques de denegación de servicio, pero debe activarlas antes de poder usarlas. Estas toman la forma de dos variables globales en el espacio de nombres de

CGI:
$CGI::POST_MAX
Si se establece en un entero no negativo, esta variable pone un límite al tamaño de los envíos POST, en bytes. Si CGI.pm detecta un POST mayor que el límite, saldrá inmediatamente con un mensaje de error. Este valor afectará tanto a los POST ordinarios como a los POST multiparte, lo que significa que también limita el tamaño máximo de las cargas de archivos. Debería establecer esto en un valor razonablemente alto, como 10
megabytes.
$CGI::DISABLE_UPLOADS
Si se establece en un valor distinto de cero, esto desh
abilitará completamente las cargas de archivos. Los demá
