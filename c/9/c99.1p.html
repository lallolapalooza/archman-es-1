ARCHIVOS DE ENTRADA

Cada archivo de entrada deberá ser uno de los siguientes: un archivo de texto que contenga un programa fuente en lenguaje C, un archivo objeto en el formato producido por c99 -c, o una biblioteca de archivos objeto, en el formato producido por el archivado de cero o más archivos objeto, utilizando ar. Las implementaciones pueden proporcionar utilidades adicionales que produzcan archivos en estos formatos. Los formatos de archivo de entrada adicionales son definidos por la implementación.

VARIABLES DE ENTORNO

Las siguientes variables de entorno afectarán la ejecución de c99:

LANG
Proporciona un valor predeterminado para las variables de internacionalización que no están establecidas o están nulas. (Consulte el volumen de Definiciones Base de POSIX.1‐2017, Sección 8.2, Variables de Internacionalización para conocer la precedencia de las variables de internacionalización utilizadas para determinar los valores de las categorías de localización).
LC_ALL
Si se establece en una cadena de valor no vacía, anula los valores de todas las demás variables de internacionalización.
LC_CTYPE
Determina la localización para la interpretación de secuencias de bytes de datos de texto como caracteres (por ejemplo, caracteres de un solo byte en contraposición a caracteres multibyte en argumentos y archivos de entrada).
LC_MESSAGES

Determina la localización que debe utilizarse para afectar el formato y el contenido de los mensajes de diagnóstico escritos en la salida estándar de error.
NLSPATH
Determina la ubicación de los catálogos de mensajes para el procesamiento de LC_MESSAGES.
TMPDIR
Proporciona una ruta de nombre de archivo que debería anular el directorio predeterminado para archivos temporales, si los hay. En sistemas conformes a XSI, proporciona una ruta de nombre de archivo que anulará el directorio predeterminado para archivos temporales, si los hay.

EVENTOS ASÍNCRONOS

Predeterminado.

STDOUT

Si se proporciona más de un operando pathname que termina en .c (o posiblemente otros sufijos no especificados), para cada uno de esos archivos:

"%s:\n", <pathname>

puede escribirse. Estos mensajes, si se escriben, precederán al procesamiento de cada archivo de entrada; no se escribirán en la salida estándar si se escriben en la salida estándar de error, como se describe en la sección STDERR.

Si se especifica la opción -E, la salida estándar será un archivo de texto que representa los resultados de la etapa de preprocesamiento del lenguaje; puede contener información adicional apropiada para las siguientes pasadas de compilación.

STDERR

La salida estándar de error se utilizará únicamente para mensajes de diagnóstico. Si se proporciona más de un operando pathname que termina en .c (o posiblemente otros sufijos no especificados), para cada uno de esos archivos:

"%s:\n", <pathname>

puede escribirse para permitir la identificación de los mensajes de diagnóstico y advertencia con el archivo de entrada apropiado. Estos mensajes, si se escriben, precederán al procesamiento de cada archivo de entrada; no se escribirán en la salida estándar de error si se escriben en la salida estándar, como se describe en la sección STDOUT.

Esta utilidad puede producir mensajes de advertencia sobre ciertas condiciones que no justifican devolver un valor de salida de error (no cero).

ARCHIVOS DE SALIDA

Se producen archivos objeto o archivos ejecutables o ambos en formatos no especificados. Si la ruta del nombre de archivo de un archivo objeto o archivo ejecutable a crear por c99 se resuelve a una entrada de directorio existente para un archivo que no es un archivo regular, es unspecified si c99 intentará crear el archivo o emitirá un diagnóstico y saldrá con un estado de salida distinto de cero.

DESCRIPCIÓN EXTENDIDA

Bibliotecas Estándar

La utilidad c99 reconocerá las siguientes opciones -l para bibliotecas estándar:

-l c
Esta opción hará disponibles todas las interfaces referenciadas en el volumen de Interfaces del Sistema de POSIX.1‐2017, con la posible excepción de las interfaces listadas como residiendo en <aio.h>, <arpa/inet.h>, <complex.h>, <fenv.h>, <math.h>, <mqueue.h>, <netdb.h>, <net/if.h>, <netinet/in.h>, <pthread.h>, <sched.h>, <semaphore.h>, <spawn.h>, <sys/socket.h>, pthread_kill(), y pthread_sigmask() en <signal.h>, <trace.h>, interfaces marcadas como opcionales en <sys/mman.h>, interfaces marcadas como ADV (Información de Asesoramiento) en <fcntl.h>, y interfaces que comienzan con el prefijo clock_ o timer_ en <time.h>. Esta opción no será requerida para que se busque esta biblioteca.
-l l
Esta opción hará disponibles todas las interfaces requeridas por la salida en lenguaje C de lex que no estén disponibles a través de la opción -l c.
-l pthread
Esta opción hará disponibles todas las interfaces referenciadas en <pthread.h> y pthread_kill() y pthread_sigmask() referenciadas en <signal.h>. Una implementación puede buscar esta biblioteca en ausencia de esta opción.
-l m
Esta opción hará disponibles todas las interfaces referenciadas en <math.h>, <complex.h>, y <fenv.h>. Una implementación puede buscar esta biblioteca en ausencia de esta opción.
-l rt
Esta opción hará disponibles todas las interfaces referenciadas en <aio.h>, <mqueue.h>, <sched.h>, <semaphore.h>, y <spawn.h>, interfaces marcadas como opcionales en <sys/mman.h>, interfaces marcadas como ADV (Información de Asesoramiento) en <fcntl.h>, y interfaces que comienzan con los prefijos clock_ y timer_ en <time.h>. Una implementación puede buscar esta biblioteca en ausencia de esta opción.
-l trace
Esta opción hará disponibles todas las interfaces referenciadas en <trace.h>. Una implementación puede buscar esta biblioteca en ausencia de esta opción.
-l xnet
Esta opción hará disponibles todas las interfaces referenciadas en <arpa/inet.h>, <netdb.h>, <net/if.h>, <netinet/in.h>, y <sys/socket.h>. Una implementación puede buscar esta biblioteca en ausencia de esta opción.
-l y
Esta opción hará disponibles todas las interfaces requeridas por la salida en lenguaje C de yacc que no estén disponibles a través de la opción -l c.

En ausencia de opciones que inhiban la invocación del editor de enlaces, como -c o -E, la utilidad c99 provocará que el equivalente a una opción -l c se pase al editor de enlaces después del último operando pathname o opción -l, haciendo que se busque después de que todos los demás archivos objeto y bibliotecas sean cargados.

Es unspecified si las bibliotecas libc.a, libl.a, libm.a, libpthread.a, librt.a, libtrace.a, libxnet.a, o liby.a existen como archivos regulares. La implementación puede aceptar como argumentos de opción -l nombres de objetos que no existen como archivos regulares.

Símbolos Externos

El compilador C y el editor de enlaces deberán soportar la significancia de los símbolos externos hasta una longitud de al menos 31 bytes; la acción tomada al encontrar símbolos que excedan la longitud máxima de símbolo definida por la implementación es unspecified.

El compilador y el editor de enlaces deberán soportar un mínimo de 511 símbolos externos por archivo fuente u objeto, y un mínimo de 4095 símbolos externos en total. Se deberá escribir un mensaje de diagnóstico en la salida estándar si se excede el límite definido por la implementación; otras acciones son unspecified.

Búsqueda de Cabeceras

Si un archivo con el mismo nombre que una de las cabeceras estándar definidas en el volumen de Definiciones Base de POSIX.1‐2017, Capítulo 13, Cabeceras, no proporcionado como parte de la implementación, se coloca en alguno de los lugares habituales que se buscan por defecto para las cabeceras, los resultados son unspecified.

ERRORES

Cuando c99 encuentra un error de compilación que causa que un archivo objeto no sea creado, deberá escribir un diagnóstico en la salida de error estándar y continuar compilando otros operandos de código fuente, pero no deberá realizar la fase de enlace y devolverá un estado de salida distinto de cero. Si el enlace y la edición no son exitosos, se deberá escribir un mensaje de diagnóstico en la salida de error estándar y c99 sale con un estado distinto de cero. Una aplicación conforme deberá confiar en el estado de salida de c99, en lugar de en la existencia o el modo del archivo

ejecutable.

APLICACIONES

Dado que la utilidad c99 usualmente crea archivos en el directorio actual durante el proceso de compilación, generalmente es necesario ejecutar el utilitario c99 en un directorio en el que se pueda crear un

archivo.

En sistemas que proporcionan Conformidad POSIX (véase el volumen de Definiciones Básicas de POSIX.1‐2017, Capítulo 2, Conformidad) , c99 se requiere solo con la opción de Desarrollo en Lenguaje C; los sistemas conformes con XSI siempre p

roporcionan c99. Algunas implementaciones históricas han creado archivos .o cuando no se especifica -c y se proporciona más de un archivo fuente. Dado que esta área no está especificada, la aplicación no puede confiar en que se creen archivos .o, pero también debe estar preparada para que cualquier archivo relacionado .o que ya exista sea eliminado

al

finalizar la edición de enlace. Existe la posible implicación de que si un usuario proporciona versiones de las funciones estándar (antes de que fueran encontradas por un -l c implícito o un -l m explícito), esas versiones se usarían en lugar de las versiones estándar. Hay varias razones por las que esto podría no ser cierto (funciones definidas como macros, manipulaciones para un espacio de nombres limpio, etc.), por lo que se declara explícitamente que la existencia de archivos con el mismo nombre que las bibliotecas estándar dentro de los directorios

-L

produce un comportamiento no especificado. Todas las funciones especificadas en el volumen de Interfaces de Sistema de POSIX.1‐2017 pueden hacerse visibles por las implementaciones cuando se busca la Biblioteca Estándar de C. Las aplicaciones conformes deben solicitar explícitamente la búsqueda de las otras bibliotecas

99 se basa en el utilitario
c89 introducido origi

POSIX‐2:

A lgunos de los cambios con respecto a c89 incluyen la capacidad de intercalar opciones y operandos

(que

muchas implementaciones de c89 permitían a pesar de que no estaba especificado), la descripción de -l como una opción en lugar de un operando, y la modificación del contenido de la sección de Bibliotecas Estándar para tener en cuenta nuevos encabezados y opciones; por ejemplo, <spawn.h> añadido a la descripción de -l rt, y -l trace añadido para la opción de Trazado. POSIX. 1‐2008 especifica que el utilitario c99 debe poder usar archivos regulares para archivos *.o

y

para archivos a.out. Las implementaciones son libres de sobrescribir archivos existentes de otros tipos al intentar crear archivos de objeto y archivos ejecutables, pero no están obligadas a hacerlo. Si se especifica algo que no sea un archivo regular y su uso falla por cualquier razón, c99 está obligado a emitir un mensaje de diagnóstico y salir con un estado de salida distinto de cero. Pero para algunos tipos de archivo, el problema puede no notarse durante mucho tiempo. Por ejemplo, si existe un FIFO llamado a.out en el directorio actual, c99 puede intentar abrir a.out y se colgará en la llamada open() hasta que otro proceso abra el FIFO para lectura. Entonces c99 puede escribir la mayor parte del archivo a.out en el FIFO y fallar cuando intente buscar hacia atrás cerca del inicio del archivo para insertar una marca de tiempo (los FIFOs no son archivos buscables). El utilitario c99 también tiene permitido emitir un diagnóstico inmediatamente si encuentra un archivo a.out o *.o que no es un archivo regular. Para un uso portable, las aplicaciones deben asegurarse de que cualquier a.out, argumento de la opción -o, o archivos *.o correspondientes a cualquier archivo *. c no entren en conflicto con nombres ya en uso que no sean archivos regulares o enlaces simbólicos que apunten a archivos regulares. En muchos sistemas, las

aplicaciones

multihilo se ejecutan en un entorno de programación que es distinto del usado por las aplicaciones de un solo hilo. Este entorno de programación multihilo (además de necesitar especificar -l pthread en el momento del enlace) puede requerir que se establezcan banderas adicionales cuando se procesan los encabezados en tiempo de compilación ( -D_REENTRANT es común). Este entorno de programación es ortogonal a los entornos de programación de tamaños de tipo discutidos arriba y listados en la Tabla 4-4, Entornos de Programación: Tamaños de Tipo. Esta versión del estándar añade llamadas al utilitario getconf para proporcionar las banderas del compilador de C y las banderas del enlazador/cargador necesarias para admitir aplicaciones multihilo. Nótese que en un sistema donde las aplicaciones de un solo hilo son un caso especial de una aplicación multihilo, ambas de estas llamadas a getconf pueden devolver cadenas NULL; en otras implementaciones ambas cadenas pueden ser cadenas no NULL. El

comité

de estandarización de C inventó los trigrafos (por ejemplo, "??! " para representar '|') para abordar problemas de portabilidad de caracteres en entornos de desarrollo basados en variantes nacionales del juego de caracteres estándar de 7 bits ISO/IEC 646:1991. Sin embargo, estos entornos ya estaban obsoletos cuando se publicó el primer estándar ISO C, y en la práctica los trigrafos no se han usado para su propósito previsto, y usualmente se pretende que tengan su significado original en K&R C. Por ejemplo, en la práctica, una cadena de origen de lenguaje C como "What??!" usualmente se pretende que termine en dos caracteres <question-mark> y un <exclamation-mark>, no en '|'.
