PSEUDO-TAG

S

Los pseudo-tags, almacenados en un archivo de tags, indican cómo ctags generó el archivo de tags: si el archivo de tags está ordenado o no, qué versión del formato de archivo de tags se utiliza, el nombre del generador de tags, etc. El término opuesto de pseudo-tags es regular-tags. Un regular-tag es para un objeto de lenguaje en un archivo de entrada. Un pseudo-tag es para el propio archivo de tags. Las herramientas cliente pueden usar los pseudo-tags como referencia para procesar los

regular-tags.

Un pseudo-tag se almacena en un archivo de tags en el mismo formato que los regular-tags, como se describe en tags(5), excepto que los nombres de los pseudo-tags tienen el prefijo "!_". Para información general sobre los pseudo-tags, ver "TAG FILE INFORMATION" en tags(5)

.

Un ejemplo de un pseudo

tag: 
!_TAG_PROGRAM_NAME
Universal C
tags /Derived fro
m Exuberant Ctags/

patrón.

Universal Ctags extiende el esquema de nomenclatura de los pseudo-tags clásicos disponibles en Exuberant Ctags para emitir información específica del lenguaje como pseudo

Al habilitar/deshabilitar un pseudo tag con la opción, especifique solo el nombre del tag TAG_KIND_DESCRIPTION, sin el prefijo ("!_") o el sufijo ("!C")

UTILIZANDO READTAGS

Consulte readtags(1) para saber cómo usar readtags. Esta sección es para discutir algunos temas notables para las herramientas cliente.

Construir expresiones de filtrado/ordenación

Ciertas secuencias de escape en las expresiones son reconocidas por readtags. Por ejemplo, al buscar una etiqueta que coincida con a\?b, si se utiliza una expresión de filtro como '(eq? $name "a\?b")', dado que \? es traducido a un solo ? por readtags, en realidad busca a?b.

Otro problema es: si las herramientas cliente se comunican con readtags no directamente a través de un subproceso, sino a través de un shell, entonces si aparece una comilla simple en las expresiones de filtro (que también están entrecomilladas con comillas simples), esta terminará la expresión, produciendo expresiones rotas y pudiendo incluso causar inyección de shell no intencionada. Las comillas simples se pueden escapar utilizando '"'"'.

Por lo tanto, las herramientas cliente deben:

  • Reemplazar \ por \\
  • Reemplazar ' por '"'"', si se comunica con readtags a través de un shell.

dentro de las expresiones. Si la expresión también contiene cadenas, " en las cadenas debe ser reemplazado por \".

Otra cosa a tener en cuenta es que los campos que faltan se representan mediante #f, y la aplicación de operadores de cadena a ellos producirá un error. Siempre debe comprobar si falta un campo antes de aplicar operadores de cadena. Consulte la sección "Filtrado" en readtags(1) para saber cómo hacerlo. Ejecute "readtags -H filter" para ver qué operadores aceptan argumentos de cadena.

Construir expresiones de filtrado/ordenación usando lenguajes Lisp

Las herramientas cliente escritas en Lisp podrían construir la expresión utilizando listas. prin1 (en Lisps de estilo Common Lisp) y write (en Lisps de estilo Scheme) pueden traducir la lista a una cadena que se puede utilizar directamente. Por ejemplo, en EmacsLisp:

(let ((name "hi"))
  (prin1 `(eq? $name ,name)))
=> "(eq\\? $name "hi")"

El "?" está escapado y readtags puede manejarlo.

Las secuencias de escape producidas por write en Lisps de estilo Scheme son exactamente las admitidas por readtags, por lo que se pueden utilizar todas las expresiones legales de readtags. Los Lisps de estilo Common Lisp pueden producir secuencias de escape que no son reconocidas por readtags, como \#, por lo que los símbolos que contienen "#" no se pueden utilizar. Readtags proporciona algunos alias para estos Lisps, por lo que deben:

  • Usar true para #t.
  • Usar false para #f.
  • Usar nil o () para ().
  • Usar (string->regexp "PATTERN") para #/PATTERN/. Usar (string->regexp "PATTERN" :case-fold true) para #/PATTERN/i. Tenga en cuenta que string->regexp no requiere escapar "/" en el patrón.

Tenga en cuenta que si la herramienta cliente se comunica con readtags a través de un shell, entonces en la cadena producida, ' todavía debe reemplazarse por '"'"' para evitar expresiones rotas e inyección de shell.

Analizar la salida de Readtags

En la salida de readtags, las tabulaciones pueden aparecer en todos los valores de campo (por ejemplo, el nombre de la etiqueta en sí podría contener tabulaciones), lo que dificulta dividir la línea en campos. Las herramientas cliente deben usar la opción -E, que mantiene las secuencias de escape en el archivo de etiquetas, por lo que el único campo que podría contener tabulaciones es el campo de patrón.

El campo de patrón podría:

  • Usar un número de línea. Se verá como number;" (por ejemplo, 10;").
  • Usar un patrón de búsqueda. Se verá como /pattern/;" o ?pattern?;". Tenga en cuenta que el patrón de búsqueda podría contener tabulaciones.
  • Combinar estos dos, como number;/pattern/;" o number;?pattern?;".

Esto es cierto para los archivos de etiquetas que utilizan el formato extendido, que es el predeterminado. El formato heredado (es decir, --format=1) no incluye los puntos y comas. Es antiguo y apenas se utiliza, por lo que no lo discutiremos aquí.

Las herramientas cliente pueden dividir la línea utilizando los siguientes pasos:

  • Encuentre las dos primeras tabulaciones en la línea, para obtener el campo de nombre y entrada.
  • Desde la segunda tabulación:
  • Si sigue una /, entonces el delimitador del patrón es /.
  • Si sigue una ?, entonces el delimitador del patrón es ?.
  • Si sigue un número, entonces:
  • Si sigue ;/ al número, entonces el delimitador es /.
  • Si sigue ;? al número, entonces el delimitador es ?.
  • Si sigue ;" al número, entonces el campo utiliza solo el número de línea, y no hay delimitador de patrón (ya que no hay un patrón regex). En este caso, el campo de patrón termina en la tercera tabulación.
  • Después del delimitador de apertura, encuentre el siguiente delimitador de patrón no escapado, y ese será el delimitador de cierre. Será seguido por ;" y luego una tabulación. Ese es el final del campo de patrón. Por "delimitador de patrón no escapado", nos referimos a que hay un número par (incluido 0) de barras invertidas antes de él.
  • A partir de aquí, divida el resto de la línea en campos por tabulaciones.

Luego, las secuencias de escape en los campos distintos del campo de patrón deben traducirse. Consulte "Propuesta" en tags(5) para conocer todas las secuencias de escape.

Aprovechar el campo de patrón

El campo de patrón especifica cómo encontrar una etiqueta en su archivo fuente. El código que genera este campo parece tener una larga historia, por lo que hay algunas dificultades y es un poco difícil de manejar. Una herramienta cliente podría simplemente requerir el campo line: y saltar a la línea que especifica, para evitar usar el campo de patrón. Pero de todos modos, discutiremos cómo sacarle el máximo provecho aquí.

Debería tomar las palabras aquí meramente como sugerencias, y no como estándares. Una herramienta cliente definitivamente podría desarrollar formas mejores (o más simples) de usar el campo de patrón.

De la última sección, sabemos que el campo de patrón puede contener un número de línea y un patrón de búsqueda. Cuando solo contiene el número de línea, manejarlo es fácil: simplemente va a esa línea.

El patrón de búsqueda se asemeja a un comando EX, pero como veremos más adelante, en realidad no es válido, por lo que se requiere un trabajo manual para procesarlo.

El patrón de búsqueda podría verse como /pat/, llamado "patrón de búsqueda hacia adelante", o ?pat?, llamado "patrón de búsqueda hacia atrás". Usar un patrón de búsqueda significa que incluso si el archivo fuente se actualiza, siempre que la parte que contiene la etiqueta no cambie, aún podríamos localizar la etiqueta correctamente buscándola.

Cuando el campo de patrón solo contiene el patrón de búsqueda, simplemente lo busca. La dirección de búsqueda (adelante/atrás) no importa, ya que se decide únicamente por si la opción -B está habilitada, y no por el contexto real. Siempre puede iniciar la búsqueda desde, digamos, el principio del archivo.

Cuando tanto el patrón de búsqueda como el número de línea están presentes, puede hacer un buen uso del número de línea, yendo primero a la línea y luego buscando la ocurrencia más cercana del patrón. Una forma de hacerlo es buscar el patrón tanto hacia adelante como hacia atrás, y cuando haya una ocurrencia en ambos lados, ir a la más cercana.

Lo bueno de esto es que cuando hay múltiples líneas idénticas en el archivo fuente (por ejemplo, el bloque COMMON en Fortran), esto podría ayudarnos a encontrar la correcta, incluso después de que el archivo fuente se actualice y la posición de la etiqueta se desplace algunas líneas.

Ahora discutiremos cómo buscar el patrón. Después de recortar las / o ? que lo rodean, el patrón se asemeja a un patrón regex. Debería ser un patrón regex, como se requiere para ser un comando EX válido, pero en realidad no lo es, como verá a continuación.

Podría comenzar con un ^, lo que significa que el patrón comienza desde el principio de una línea. También podría terminar con un no escapado $ que significa que el patrón termina al final de una línea. Mantengamos esta información y también recortémosla.
