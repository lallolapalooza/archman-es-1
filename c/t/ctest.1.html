ETIQUETA

COINCIDENCIA

Las pruebas pueden tener etiquetas asociadas. Las pruebas pueden incluirse o excluirse de una ejecución de pruebas filtrando por las etiquetas. Cada filtro individual es una expresión regular aplicada a las etiquetas asociadas a una

prueba.

Cuando se usa -L, para que una prueba se incluya en una ejecución de pruebas, cada expresión regular debe coincidir con al menos una etiqueta. Usar más de una opción -L significa "coincidir con todas est

as".

La opción -LE funciona igual que -L, pero excluye pruebas en lugar de incluirlas. Una prueba se excluye si cada expresión regular coincide con al menos una

etiqueta.

Si una prueba no tiene etiquetas asociadas, entonces -L nunca incluirá esa prueba, y -LE nunca excluirá esa prueba. Como ejemplo de pruebas con etiquetas, considere cinco pruebas, con las siguientes

etiquetas:
  • test1 tiene las etiquetas tuesday y producti
    • on
  • test2 tiene las etiquetas tuesday y te
    • st
  • test3 tiene las etiquetas wednesday y producti
    • on
  • test4 tiene la etiqueta wednesd
    • ay
  • test5 tiene las etiquetas friday y t
    • e
s
t

Ejecutar ctest con -L tuesday -L test seleccionará test2, que tiene ambas etiquetas. Ejecutar CTest con -L test seleccionará test2 y test5, porque ambas tienen una etiqueta que coincide con esa expresión

regular.

Debido a que la coincidencia funciona con expresiones regulares, tenga en cuenta que ejecutar CTest con -L es coincidirá con las cinco pruebas. Para seleccionar las pruebas tuesday y wednesday juntas, use una sola expresión regular que coincida con cualquiera de ellas, como -L "tu

e|w
ed".

ASIGNACIÓN DE

RECURSOS

CTest proporciona un mecanismo para que las pruebas especifiquen los recursos que necesitan de manera detallada, y para que los usuarios especifiquen los recursos disponibles en la máquina en ejecución. Esto permite a CTest llevar un seguimiento interno de qué recursos están en uso y cuáles están libres, programando las pruebas de una manera que evite que intenten reclamar recursos que no están

disponibles.

Cuando se utiliza la función de asignación de recursos, CTest no sobresuscribirá los recursos. Por ejemplo, si un recurso tiene 8 ranuras, CTest no ejecutará pruebas que colectivamente usen más de 8 ranuras a la vez. Esto tiene el efecto de limitar cuántas pruebas pueden ejecutarse en cualquier momento dado, incluso si se usa un argumento -j alto, si esas pruebas usan todas algunas ranuras del mismo recurso. Además, significa que una prueba que use más de un recurso del que está disponible en una máquina no se ejecutará en absoluto (y será reportada como No Ejecut

ada).

Un caso de uso común para esta función es para pruebas que requieren el uso de una GPU. Múltiples pruebas pueden simultáneamente asignar memoria de una GPU, pero si demasiadas pruebas intentan hacer esto a la vez, algunas de ellas fallarán al asignar, resultando en una prueba fallida, aunque la prueba habría tenido éxito si hubiera tenido la memoria que necesitaba. Al usar la función de asignación de recursos, cada prueba puede especificar cuánta memoria requiere de una GPU, permitiendo a CTest programar las pruebas de manera que ejecutar varias de estas pruebas a la vez no agote la memoria de la

GPU.

Tenga en cuenta que CTest no tiene concepto de lo que es una GPU o cuánta memoria tiene. No tiene ninguna forma de comunicarse con una GPU para obtener esta información o realizar cualquier gestión de memoria, aunque el proyecto puede definir una prueba que proporcione detalles sobre la máquina de prueba (vea Archivo de Especificación de Recursos Generado Dinámicamente)

.

CTest mantiene un seguimiento de una lista de tipos de recursos abstractos, cada uno de los cuales tiene un cierto número de ranuras disponibles para que las pruebas usen. Cada prueba especifica el número de ranuras que requiere de un recurso determinado, y CTest luego las programa de una manera que evita que el número total de ranuras en uso exceda la capacidad listada. Cuando se ejecuta una prueba y se asignan ranuras de un recurso a esa prueba, las pruebas pueden asumir que tienen uso exclusivo de esas ranuras durante la duración del proceso de la

prueba.

La función de asignación de recursos de CTest consiste en al menos dos

entradas:
  • El archivo de especificación de recursos, descrito a continuación, que describe los recursos disponibles en el
    • sistema.
  • La propiedad RESOURCE_GROUPS <#prop_test:RESOURCE_GROU
    • PS> de las pruebas,
que describe los recursos
requeridos por la prueba.

Cuando CTest ejecuta una prueba, los recursos asignados a esa prueba se pasan en la forma de un conjunto de variables de entorno como se describe a continuación. Usar esta información para decidir a qué recurso conectarse se deja al escritor de la

prueba.

La propiedad RESOURCE_GROUPS le dice a CTest qué recursos una prueba espera usar agrupados de una manera significativa para la prueba. La prueba misma debe leer las variables de entorno para determinar qué recursos han sido asignados a cada grupo. Por ejemplo, cada grupo puede corresponder a un proceso que la prueba generará cuando se

ejecute.

Tenga en cuenta que incluso si una prueba especifica una propiedad RESOURCE_GROUPS , todavía es posible que esa prueba se ejecute sin ninguna asignación de recursos (y sin las variables de entorno correspondientes) si el usuario no pasa un archivo de especificación de recursos. Pasar este archivo, ya sea a través del argumento de línea de comandos --resource-spec-file o el argumento RESOURCE_SPEC_FILE de ctest_test() <#command:ctest_test>, es lo que activa la función de asignación de recursos. Las pruebas deben verificar la variable de entorno CTEST_RESOURCE_GROUP_COUNT para averiguar si la asignación de recursos está activada o no. Esta variable siempre (y solo) se definirá si la asignación de recursos está activada. Si la asignación de recursos no está activada, entonces la variable CTEST_RESOURCE_GROUP_COUNT no existirá, incluso si existe para el proceso ctest padre. Si una prueba absolutamente debe tener asignación de recursos, entonces puede devolver un código de salida fallido o usar las propiedades SKIP_RETURN_CODE <#prop_test:SKIP_RETURN_CODE> o SKIP_REGULAR_EXPRESSION <#prop_test:SKIP_REGULAR_EXPRESSION> para indicar una prueba

omitida.
