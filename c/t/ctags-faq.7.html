¿Cuál es la diferencia entre Universal Ctags y Exuberant Ctags?

Universal Ctags es un fork no oficial de Exuberant Ctags. Las diferencias se resumen en la página man ctags-incompatibilities(7).

La más notable es que Universal Ctags no lee el archivo ~/.ctags . En su lugar, lee los archivos *.ctags bajo el directorio ~/.ctags.d .

¿Cómo puedo evitar tener que especificar mi opción favorita cada vez?

Ya sea estableciendo la variable de entorno CTAGS con tus opciones personalizadas, o poniéndolas en un archivo ~/.ctags.d/anyname.ctags en tu directorio de inicio.

¿Qué son estos extraños fragmentos de texto que comienzan con ;" que siguen a muchas de las líneas en el archivo de etiquetas?

Estos son flags de extensión. Se añaden para proporcionar información extra sobre la etiqueta que puede ser utilizada por el editor para manejar las etiquetas de manera más inteligente. Se añaden a la parte del comando EX de la línea de la etiqueta de una manera que proporciona compatibilidad hacia atrás con implementaciones existentes del editor Vi. El punto y coma es un separador de comandos EX y la comilla doble comienza un comentario EX. Así, los flags de extensión aparecen como un comentario EX y deberían ser ignorados por el editor cuando procese el comando EX.

Sin embargo, algunos editores no vi implementan solo el mínimo indispensable de comandos EX para procesar el comando de búsqueda o el número de línea en el tercer campo del archivo de etiquetas. Si encuentras este problema, usa la opción --format=1 para generar un archivo de etiquetas sin estas extensiones (recuerda que puedes establecer la variable de entorno CTAGS con cualquier argumento por defecto que desees proporcionar). Luego pide al proveedor de tu editor que implemente el manejo de esta característica de los comandos EX.

¿Por qué no puedo saltar a class::member?

Porque, por defecto, ctags solo genera etiquetas para los identificadores separados encontrados en los archivos fuente. Si especificas la opción --extra=+q , entonces ctags también generará una segunda etiqueta calificada por la clase para cada miembro de la clase (datos y función/método) en la forma class::member para C++, y en la forma class.method para Eiffel y Java.

¿Por qué termino en la línea equivocada cuando salto a una etiqueta?

Por defecto, ctags codifica el número de línea en el archivo donde se encuentran las etiquetas de macro (#define). Esto se hizo para mantener la compatibilidad con la versión UNIX original de ctags. Si cambias el archivo que contiene la etiqueta sin reconstruir el archivo de etiquetas, la ubicación de la etiqueta en el archivo de etiquetas puede ya no coincidir con la ubicación actual.

Para evitar este problema, puedes especificar la opción --excmd=p, lo que hace que ctags use un patrón de búsqueda para localizar las etiquetas de macro. Nunca he descubierto la razón por la que el ctags UNIX original usaba exclusivamente números de línea para las etiquetas de macro, pero hasta ahora he resistido cambiar el comportamiento por defecto de Exuberant (y Universal) Ctags para que se comporte de manera diferente.

¿Cómo salto a la etiqueta que quiero en lugar de a la equivocada con el mismo nombre?

Un archivo de etiquetas es simplemente una lista de nombres de etiquetas y dónde encontrarlas. Si hay entradas duplicadas, a menudo terminas yendo a la equivocada porque el archivo de etiquetas está ordenado y tu editor localiza la primera en el archivo de etiquetas.

Vi estándar no proporciona ninguna facilidad para alterar este comportamiento. Sin embargo, Vim tiene algunas características agradables para minimizar este problema, principalmente examinando todas las coincidencias y eligiendo la mejor bajo las circunstancias. Vim también proporciona comandos que permiten la selección de la etiqueta coincidente deseada.

¿Cómo puedo localizar todas las referencias a una función o variable específica?

Ya hay varios paquetes disponibles que proporcionan esta capacidad. Es decir, estos son: el sistema de etiquetas de código fuente GLOBAL, GNU id-utils, cscope y cflow. Al momento de escribir esto, se pueden encontrar en las siguientes ubicaciones:

  • GLOBAL: http://www.gnu.org/software/global
  • id-utils: http://www.gnu.org/software/idutils/idutils.html
  • cscope: http://cscope.sourceforge.net
  • cflow: <ftp://www.ibiblio.org/pub/Linux/devel/lang/c>

¿Por qué agregar etiquetas a un archivo de etiquetas tarda tanto?

A veces, en un intento de construir un archivo de etiquetas global para todos los archivos fuente en un árbol de fuentes grande con muchos directorios, alguien intentará ejecutar ctags en modo de anexión (-a) en cada directorio de la jerarquía. Cada vez que se invoca ctags, su comportamiento por defecto es ordenar el archivo de etiquetas una vez que se han añadido las etiquetas de esa ejecución. A medida que el archivo de etiquetas acumulado crece, el tiempo de ordenación aumenta aritméticamente.

La mejor manera de evitar este problema (y la más eficiente) es hacer uso de la opción --recurse (o -R) de ctags ejecutando el siguiente comando en la raíz de la jerarquía de directorios (así ejecutando ctags solo una vez):

ctags -R

Si realmente insistes en ejecutar ctags por separado en cada directorio, puedes evitar la pasada de ordenación cada vez especificando la opción --sort=no. Una vez que el archivo de etiquetas esté completamente construido, usa el comando sort para ordenar manualmente el archivo de etiquetas final, o deja que la invocación final de ctags ordene el archivo.

1.
Un archivo de etiquetas local en cada directorio que contenga solo las etiquetas para los archivos fuente en ese directorio.
2.
Un solo archivo grandearchivo de etiquetas global presente en el directorio raíz de su jerarquía, que contiene todas las etiquetas presentes en todos los archivos fuente en la
jerarquía.

jerarquía.

La capacidad de su editor
para usar múltiples archivos de etiquetas.
Si su editor no puede hacer uso de múltiples archivos de etiquetas (las implementaciones originales de vi no podían), entonces un solo archivo de etiquetas grande es la única forma de proceder si alguna vez desea saltar a etiquetas ubicadas en otros directorios. Si nunca necesita saltar a etiquetas en otro directorio (es decir, el código fuente en cada directorio es completamente autónomo), entonces un archivo de etiquetas local en cada directorio satisfará sus necesidades.

B

.
El tiempo que le lleva a su editor
buscar una etiqueta en el archivo de etiquetas.
La importancia de este factor depende del tamaño de su árbol de código fuente y de si los archivos fuente están ubicados en un sistema de archivos local o remoto. Para los archivos fuente y de etiquetas ubicados en un sistema de archivos local, buscar una etiqueta no es tan costoso como uno podría imaginar inicialmente, ya que las implementaciones de vi típicamente realizan una búsqueda binaria en un archivo de etiquetas ordenado. Esto puede o no ser cierto para el editor que usted usa. Para los archivos ubicados en un sistema de archivos remoto, leer un archivo grande es una operación costosa.

De los enfoques listados arriba, tiendo a favorecer el Enfoque 3. Mi editor de elección es Vim, que proporciona un rico conjunto de características

para manejar múltiples archivos de etiquetas, lo cual influye parcialmente en mi elección. Si usted está trabajando con archivos fuente en un si
stema de archivos remoto, entonces le recomendaría o bien el Enfoque 3 o el Enfoque 4, dependiendo del costo al leer el archivo de etiquetas global.
Las ventajas del Enfoque 3 son muchas (asumiendo que su editor tiene la capacidad de soportar tanto múltiples archivos de etiquetas como etiquetas duplicadas). Todas las búsquedas de etiquetas ubicadas en el directorio actual son rápidas y el archivo de etiquetas local puede ser regenerado rápida y fácilmente en un segundo

Una búsqueda de una etiqueta (necesariamente no estática) encontrada en otro directorio falla en la búsqueda en el archivo de etiquetas local, pero se encuentra en el archivo de etiquetas global, lo cual satisface todas las búsquedas entre directorios. El archivo de etiquetas global puede ser regenerado automáticamente periódicamente con un trabajo de cron (y quizás los archivos de etiquetas locales también).

Sí, los nombres de archivo Unicode son soportados en plataformas tipo unix
    (Linux, macOS, Cygwin, etc.). Sin embargo, en MS Windows, necesita usar Windows 10 versión 1903 o
    posterior para usar nombres de archivo Unicode. (Esta es una característica experimental, sin embargo.)
    En versiones anteriores de Windows, Universal Ctags solo soporta nombres de archivo
    representados en la página de código actual. Si aún desea usar nombres de archivo Unicode
    en ellas, use la versión de Universal Ctags para Cygwin o MSYS2 como una
    solución 
alternativa.
