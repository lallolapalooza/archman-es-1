CARGO-TEST(1) Manual de Comandos Generales CARGO-TEST(1)

NOMBRE

cargo-test — Ejecuta pruebas unitarias y de integración de un paquete

SINOPSIS

cargo test [opciones] [nombre_prueba] [-- opciones_prueba]

DESCRIPCIÓN

Compila y ejecuta pruebas unitarias, de integración y de documentación.

El argumento de filtrado de pruebas NOMBRE_PRUEBA y todos los argumentos que siguen a los dos guiones (--) se pasan a los binarios de prueba y, por lo tanto, a libtest (el framework integrado de pruebas unitarias y micro-benchmarking de rustc). Si estás pasando argumentos tanto a Cargo como al binario, los que van antes de -- van a Cargo, y los que van después van al binario. Para más detalles sobre los argumentos de libtest, consulta la salida de cargo test -- --help y el capítulo del libro de rustc sobre cómo funcionan las pruebas en https://doc.rust-lang.org/rustc/tests/index.html.

Por ejemplo, esto filtrará las pruebas con foo en su nombre y las ejecutará en 3 hilos en paralelo:

cargo test foo -- --test-threads 3

Las pruebas se compilan con la opción --test de rustc, que crea un ejecutable especial enlazando tu código con libtest. El ejecutable ejecuta automáticamente todas las funciones anotadas con el atributo #[test] en múltiples hilos. Las funciones anotadas con #[bench] también se ejecutarán con una iteración para verificar que son funcionales.

Si el paquete contiene múltiples destinos de prueba, cada destino se compila en un ejecutable especial como se mencionó anteriormente, y luego se ejecuta secuencialmente.

El manejador de libtest puede ser deshabilitado estableciendo harness = false en la configuración del manifiesto del destino, en cuyo caso tu código deberá proporcionar su propia función main para gestionar la ejecución de las pruebas.

Pruebas de documentación

Las pruebas de documentación también se ejecutan por defecto, lo que es manejado por rustdoc. Extrae bloques de código de los comentarios de documentación del destino de la biblioteca y luego los ejecuta.

A diferencia de los destinos de prueba normales, cada bloque de código se compila en un ejecutable de prueba de documentación sobre la marcha con rustc. Estos ejecutables se ejecutan en paralelo en procesos separados. La compilación de un bloque de código es en realidad parte de una función de prueba controlada por libtest, por lo que algunas opciones como --jobs podrían no tener efecto. Ten en cuenta que este modelo de ejecución de las pruebas de documentación no está garantizado y puede cambiar en el futuro; ten cuidado al depender de él.

Consulta el libro de rustdoc https://doc.rust-lang.org/rustdoc/ para más información sobre cómo escribir pruebas de documentación.

Directorio de trabajo de las pruebas

El directorio de trabajo al ejecutar cada prueba unitaria y de integración se establece en el directorio raíz del paquete al que pertenece la prueba. Establecer el directorio de trabajo de las pruebas en el directorio raíz del paquete permite que las pruebas accedan de manera fiable a los archivos del paquete usando rutas relativas, independientemente de desde dónde se ejecutó cargo test.

Para las pruebas de documentación, el directorio de trabajo al invocar a rustdoc se establece en el directorio raíz del espacio de trabajo, y también es el directorio que rustdoc utiliza como directorio de compilación de cada prueba de documentación. El directorio de trabajo al ejecutar cada prueba de documentación se establece en el directorio raíz del paquete al que pertenece la prueba, y se controla a través de la opción --test-run-directory de rustdoc.

OPCIONES

Opciones de prueba

--no-run

Compila, pero no ejecutes las pruebas.

--no-fail-fast

Ejecuta todas las pruebas independientemente de si fallan. Sin esta opción, Cargo saldrá después de que el primer ejecutable falle. El manejador de pruebas de Rust ejecutará todas las pruebas dentro del ejecutable hasta su finalización; esta opción solo se aplica al ejecutable en su conjunto.

Selección de paquetes

Por defecto, cuando no se dan opciones de selección de paquetes, los paquetes seleccionados dependen del archivo de manifiesto seleccionado (basado en el directorio de trabajo actual si no se proporciona --manifest-path). Si el manifiesto es la raíz de un espacio de trabajo, se seleccionan los miembros predeterminados del espacio de trabajo; de lo contrario, solo se seleccionará el paquete definido por el manifiesto.

Los miembros predeterminados de un espacio de trabajo se pueden establecer explícitamente con la clave workspace.default-members en el manifiesto raíz. Si esto no está configurado, un espacio de trabajo virtual incluirá todos los miembros del espacio de trabajo (equivalente a pasar --workspace), y un espacio de trabajo no virtual incluirá solo el propio crate raíz.

-p espec…, --package espec…

Prueba solo los paquetes especificados. Consulta cargo-pkgid(1) para el formato ESPEC. Esta opción puede especificarse varias veces y admite patrones de glob comunes de Unix como *, ? y []. Sin embargo, para evitar que tu shell expanda accidentalmente los patrones de glob antes de que Cargo los maneje, debes usar comillas simples o dobles alrededor de cada patrón.

--workspace

Prueba todos los miembros del espacio de trabajo.

--all

Alias obsoleto para --workspace.

--exclude ESPEC…

Excluye los paquetes especificados. Debe usarse junto con la opción --workspace. Esta opción puede especificarse varias veces y admite patrones de glob comunes de Unix como *, ? y []. Sin embargo, para evitar que tu shell expanda accidentalmente los patrones de glob antes de que Cargo los maneje, debes usar comillas simples o dobles alrededor de cada patrón.

Selección de destino

Cuando no se dan opciones de selección de destino, cargo test compilará los siguientes destinos de los paquetes seleccionados:

•lib — se utiliza para enlazar con binarios, ejemplos, pruebas de integración y pruebas de documentación
•bins (solo si se compilan pruebas de integración y se requieren características disponibles)
•ejemplos — para asegurar que compilan
•lib como prueba unitaria
•bins como pruebas unitarias
•pruebas de integración
•pruebas de documentación para el destino lib

El comportamiento predeterminado puede cambiarse estableciendo el marcador test para el destino en la configuración del manifiesto. Establecer ejemplos en test = true compilará y ejecutará el ejemplo como una prueba, reemplazando la función main del ejemplo con el manejador de libtest. Si no quieres que se reemplace la función main, incluye también harness = false, en cuyo caso el ejemplo se compilará y ejecutará tal cual.

Establecer destinos en test = false evitará que se prueben por defecto. Las opciones de selección de destino que toman un destino por nombre (como --example foo) ignoran el marcador test y siempre probarán el destino dado.

Las pruebas de documentación para bibliotecas pueden deshabilitarse estableciendo doctest = false para la biblioteca en el manifiesto.

Consulta Configuración de un destino https://doc.rust-lang.org/cargo/reference/cargo-targets.html#configuring-a-target para más información sobre la configuración por destino.

Los destinos binarios se compilan automáticamente si hay una prueba de integración o benchmark seleccionado para probar. Esto permite que una prueba de integración ejecute el binario para ejercitar y probar su comportamiento. La variable de entorno CARGO_BIN_EXE_<nombre> https://doc.rust-lang.org/cargo/reference/environment-variables.html#environment-variables-cargo-sets-for-crates se establece cuando se compila la prueba de integración para que pueda usar la macro env https://doc.rust-lang.org/std/macro.env.html para localizar el ejecutable.

Pasar opciones de selección de destino probará solo los destinos específicos.

Afirma que se utilizan exactamente las mismas dependencias y versiones que cuando se generó originalmente el archivo Cargo.lock existente. Cargo finalizará con un error cuando ocurra cualquiera de los siguientes escenarios:
•Falta el archivo de bloqueo.
•Cargo intentó cambiar el archivo de bloqueo debido a una resolución de dependencias diferente.

Puede utilizarse en entornos donde se desean compilaciones deterministas, como en canalizaciones de CI.

--offline

Evita que Cargo acceda a la red por cualquier motivo. Sin esta bandera, Cargo se detendrá con un error si necesita acceder a la red y esta no está disponible. Con esta bandera, Cargo intentará proceder sin la red si es posible.

Tenga cuidado, ya que esto puede resultar en una resolución de dependencias diferente a la del modo en línea. Cargo se limitará a los crates que se hayan descargado localmente, incluso si podría haber una versión más reciente como se indica en la copia local del índice. Consulte el comando cargo-fetch(1) para descargar dependencias antes de desconectarse.

También se puede especificar con el valor de configuración net.offline https://doc.rust-lang.org/cargo/reference/config.html.

--frozen

Equivalente a especificar tanto --locked como --offline.

--lockfile-path RUTA

Cambia la ruta del archivo de bloqueo del valor predeterminado (<workspace_root>/Cargo.lock) a RUTA. RUTA debe terminar en Cargo.lock (por ejemplo, --lockfile-path /tmp/temporary-lockfile/Cargo.lock). Tenga en cuenta que proporcionar --lockfile-path ignorará el archivo de bloqueo existente en la ruta predeterminada, y en su lugar utilizará el archivo de bloqueo de RUTA o escribirá un nuevo archivo de bloqueo en la RUTA proporcionada si no existe. Esta bandera se puede utilizar para ejecutar la mayoría de los comandos en directorios de solo lectura, escribiendo el archivo de bloqueo en la RUTA proporcionada.

Esta opción solo está disponible en el canal nightly https://doc.rust-lang.org/book/appendix-07-nightly-rust.html y requiere la bandera -Z unstable-options para habilitarse (consulte #14421 https://github.com/rust-lang/cargo/issues/14421).

Opciones Comunes

+toolchain

Si Cargo se ha instalado con rustup y el primer argumento para cargo comienza con +, se interpretará como un nombre de toolchain de rustup (como +stable o +nightly). Consulte la documentación de rustup https://rust-lang.github.io/rustup/overrides.html para obtener más información sobre cómo funcionan las anulaciones de toolchain.

--config CLAVE=VALOR o RUTA

Anula un valor de configuración de Cargo. El argumento debe estar en la sintaxis TOML de CLAVE=VALOR, o proporcionarse como una ruta a un archivo de configuración adicional. Esta bandera se puede especificar varias veces. Consulte la sección de anulaciones de línea de comandos https://doc.rust-lang.org/cargo/reference/config.html#command-line-overrides para obtener más información.

-C RUTA

Cambia el directorio de trabajo actual antes de ejecutar cualquier operación especificada. Esto afecta, por ejemplo, dónde busca Cargo por defecto el manifiesto del proyecto (Cargo.toml), así como los directorios que se buscan para descubrir .cargo/config.toml. Esta opción debe aparecer antes del nombre del comando, por ejemplo, cargo -C ruta/a/mi-proyecto build.

Esta opción solo está disponible en el canal nightly https://doc.rust-lang.org/book/appendix-07-nightly-rust.html y requiere la bandera -Z unstable-options para habilitarse (consulte #10098 https://github.com/rust-lang/cargo/issues/10098).

-h, --help

Imprime la información de ayuda.

-Z bandera

Banderas inestables (solo nightly) para Cargo. Ejecute cargo -Z help para obtener detalles.

Opciones Misceláneas

El argumento --jobs afecta la compilación del ejecutable de prueba pero no afecta cuántos hilos se utilizan al ejecutar las pruebas. El framework de pruebas de Rust incluye una opción para controlar el número de hilos utilizados:

cargo test -j 2 -- --test-threads=2

-j N, --jobs N

Número de trabajos paralelos a ejecutar. También puede especificarse con el valor de configuración build.jobs https://doc.rust-lang.org/cargo/reference/config.html. Por defecto, el número de CPUs lógicas. Si es negativo, establece el número máximo de trabajos paralelos al número de CPUs lógicas más el valor proporcionado. Si se proporciona la cadena default, restaura el valor a los predeterminados. No debe ser 0.

--future-incompat-report

Muestra un informe de incompatibilidad futura para cualquier advertencia de incompatibilidad futura producida durante la ejecución de este comando.

Consulte cargo-report(1)

Si bien cargo test implica compilación, no proporciona la bandera --keep-going. Utilice --no-fail-fast para ejecutar tantos tests como sea posible sin detenerse en el primer fallo. Para "compilar" tantos tests como sea posible, utilice --tests para compilar los binarios de test por separado. Por ejemplo:

cargo build --tests --keep-going
cargo test --tests --no-fail-fast

ESTADO DE SALIDA

•0: Cargo tuvo éxito.
•101: Cargo no pudo completarse.

EJEMPLOS

1.Ejecutar todas las pruebas unitarias y de integración del paquete actual: 
cargo test
2.Ejecutar solo las pruebas cuyos nombres coincidan con una cadena de filtro: 
cargo test name_filter
3.Ejecutar solo una prueba específica dentro de una prueba de integración específica: 
cargo test --test int_test_name -- modname::test_name
