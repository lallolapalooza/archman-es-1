cap_iab(3)

CAP_IAB(3) Manual del programador de Linux CAP_IAB(3)

NAME

cap_iab_init, cap_iab_dup, cap_iab_get_proc, cap_iab_get_pid, cap_iab_set_proc, cap_iab_to_text, cap_iab_from_text, cap_iab_get_vector, cap_iab_compare, cap_iab_set_vector, cap_iab_fill, cap_proc_root - funciones de soporte para tuplas IAB heredables

SYNOPSIS

#include <sys/capability.h>
cap_iab_t cap_iab_init(void);
cap_iab_t cap_iab_dup(cap_iab_t iab);
cap_iab_t cap_iab_get_proc(void);
cap_iab_t cap_iab_get_pid(pid_t pid);
int cap_iab_set_proc(cap_iab_t iab);
char *cap_iab_to_text(cap_iab_t iab);
cap_iab_t cap_iab_from_text(const char *text);
cap_flag_value_t cap_iab_get_vector(cap_iab_t iab, cap_iab_vector_t vec,
    cap_value_t val);
int cap_iab_compare(cap_iab_t a, cap_iab_t b);
int cap_iab_set_vector(cap_iab_t iab, cap_iab_vector_t vec, cap_value_t val,
    cap_flag_value_t enable);
int cap_iab_fill(cap_iab_t iab, cap_iab_vector_t vec,
    cap_t set, cap_flag_t flag);
char *cap_proc_root(const char *root);

Enlazar con -lcap.

DESCRIPTION

Las funciones definidas en esta página de man concernen los tres vectores de capacidades de proceso heredados de manera ingenua: Inh, Amb y Bound. Esta tupla de 3 elementos IAB de capacidades, capturada en el tipo cap_iab_t, se combina para pasar capacidades de un proceso a otro a través de las llamadas al sistema execve(2). Las reglas de convolución utilizando la tupla IAB son un conjunto de reglas de respaldo cuando el archivo ejecutado no tiene capacidades de archivo configuradas.

Hay algunas restricciones impuestas por el núcleo con respecto a los tres componentes de una tupla IAB y la bandera de capacidad de proceso Permitida (Permitted). Son: el vector Inh (CAP_IAB_INH) es totalmente igual a la bandera de Heredable del proceso en todo momento; el vector Amb (CAP_IAB_AMB) no contiene más valores de capacidad que la intersección del vector Inh y la bandera Permitida del proceso; y el vector Bound (o bloqueado) (CAP_IAB_BOUND) es el complemento a dos del vector de límites del proceso.

En algunos entornos, se considera deseable heredar de manera ingenua las capacidades. Es decir, pasar capacidades, independientemente del estado del binario ejecutado, de padre a hijo a través de las llamadas al sistema exec*. Las capacidades sobrevivientes se convierten en la bandera Permitida para el proceso post-ejecución. Este método de herencia difiere significativamente de la herencia de mano alzada entre un proceso pre-exec* y un ejecutable con capacidad de archivo otorgado por el mecanismo de capacidad tradicional (POSIX.1e).

Las reglas de convolución para la herencia estilo IAB son: I'=I; A'=A&I; P'=A&I&P. Donde P etc. son los valores pre-ejecución y P' etc. son los valores post-ejecución.

Con el entendimiento de estas reglas de convolución, podemos explicar cómo se gestiona el soporte de libcap(3) para la tupla IAB: la API IAB.

cap_iab_init() devuelve un valor IAB vacío. Es decir, una tupla prácticamente inofensiva. No bloqueará ninguna capacidad de archivo Permitida a través de exec, pero tampoco otorgará ninguna. El devuelto cap_iab_t debe liberarse con cap_free(3).

cap_iab_dup() devuelve una copia del valor IAB especificado. El cap_iab_t devuelto debe liberarse con cap_free(3).

cap_iab_get_proc() devuelve una copia del valor IAB para el proceso actual. El cap_iab_t devuelto debe liberarse con cap_free(3).

cap_iab_get_pid() devuelve una copia del valor IAB para el proceso especificado. El cap_iab_t devuelto debe liberarse con cap_free(3). Esta función por defecto busca en /proc/<PID>/status para la información IAB, pero esa ubicación puede sobrescribirse utilizando la función cap_proc_root().

cap_iab_set_proc() se puede usar para establecer el valor IAB transportado por el proceso actual. Tal configuración fallará si el proceso no es lo suficientemente capaz. Para elevar bits I no presentes en la bandera P, o aplicar de nuevo el mapeo B, se requiere que CAP_SETPCAP esté presente en la bandera Permitida (la función elevará temporalmente en la bandera Effective si es necesario). En todos los casos, los valores A elevados deben estar presentes en la intersección de las valores Permitida e Inh.

cap_iab_to_text() convertirá una tupla IAB a una representación de texto IAB canónica. La representación es ligeramente redundante pero libcap(3)intentarágenerar la representación más corta posible que sea capaz.

cap_iab_from_text() genera una tupla IAB desde una cadena de texto (probablemente generada por la función anterior). La tupla IAB devuelta debe liberarse con cap_free().

cap_iab_get_vector() se puede usar para determinar el valor de capacidad específico de un vector IAB.

cap_iab_compare() se puede usar para comparar dos tuplas cap_iab_t. Cuando el valor de retorno no es cero, el macro CAP_IAB_DIFFERS(status, vector) evalúa a no cero si el estado devuelto difiere en sus componentes vector.

cap_iab_set_vector() se puede usar para establecer un valor de vector específico al nivel de habilitación.

cap_iab_fill() se puede usar para copiar de manera integral un valor de bandera cap_t en el vector vec de la tupla IAB. Copiar en Amb (CAP_IAB_AMB) de esta manera puede elevar implícitamente valores Inh (CAP_IAB_INH) en la tupla IAB. De manera similar, copiar en el vector Inh puede bajar implícitamente valores Amb que no están presentes en el vector Inh resultante.

cap_proc_root() se puede usar para determinar la ubicación actual consultada por cap_iab_get_pid(). Los valores devueltos deben liberarse con cap_free(3). Si el argumento a cap_proc_root() no es NULL, una copia de él se convertirá en el reemplazo para /proc. Nota, esta función no es segura de hilos con respecto a llamadas concurrentes a cap_iab_get_pid().

ERRORS

Las funciones que devuelven valores cap_iab_t o asignan memoria en forma de cadena devuelven NULL en caso de error.

Los valores de retorno enteros son -1 en caso de error y 0 en caso de éxito.

En el caso de error consulte errno.

NOTES

A diferencia del conjunto de capacidades tradicional cap_t, la tupla IAB, tomada conjuntamente, es incompatible con las capacidades de sistema de archivos creadas mediante herramientas como setcap(8). Es decir, el vector Amb de la tupla IAB se vuelve irrelevante cuando se ejecuta un ejecutable con capacidad de archivo.

Además, hay modos cap_mode(3) de libcap que desactivan el vector Amb y su método de herencia de proceso.

HISTORY

El formato IAB para las variantes heredables de capacidades fue desarrollado inicialmente como la sintaxis de configuración para el módulo Linux-PAM pam_cap.so en libcap-2.29. Se introdujo para extender la lista separada por comas simple de capacidades de proceso heredables que el módulo podía otorgar a un árbol de procesos autenticado, para incluir límites forzados en el vector Bound y introducir soporte para el vector Ambiente de bits de capacidad.

Si bien los vectores Heredable y Bound fueron anticipados por el borrador POSIX.1e que introdujo las capacidades, el vector Ambiente es una invención de Linux e incompatible con el modelo de capacidad de archivo POSIX.1e. Por lo tanto, se sintió que intentar fusionar todos los 5 vectores de capacidad en una sola representación de texto no funcionaría. En su lugar, la sintaxis de configuración pam_cap.so se generalizó en un conjunto completo de funciones de libcap para agrupar las tres capacidades heredadas de manera ingenua: la tupla IAB. El soporte para esto debutó en libcap-2.33.
