Esta tupla IAB de tres vectores de capacidades, capturada en el tipo cap_iab_t, se combinan para pasar capacidades de un proceso a otro a través de llamadas al sistema execve(2). Las reglas de convolución que usan la tupla IAB son un conjunto de reglas de respaldo cuando el archivo ejecutado no tiene file-capabilities configuradas. El kernel impone algunas restricciones con respecto a los tres componen

tes de

una tupla IAB y el indicador de capacidad de proceso Permitted. Son: el vector Inh ( CAP_IAB_INH) es completamente igual al indicador Inheritable del proceso en todo momento; el vectorAmb ( CAP_IAB_AMB) no contiene más valores de capacidad que la intersección del vector Inh y elindicador Permitted para el proceso; y el vector Bound (o bloqueado) ( CAP_IAB_BOUND) es el complemento a dos del vector de límites del proceso. En algunos entornos, se consideradeseable heredar capacidades de forma ingenua. Es decir, pasar

capacidades,

independientemente del estado del binario ejecutado, del padre al hijo a través de llamadas al sistema exec*. Las capacidades sobrevivientes se convierten en el indicador Permitted para el proceso posterior a la ejecución. Este método de herencia difiere significativamente de la herencia por protocolo entre un proceso pre-exec* y un ejecutable dotado de file-capabilities del mecanismo de capacidades tradicional (POSIX.1e). Las reglas de convolución para la herencia de estilo IAB son: I'=I; A'=A& P'=A&I&P. Donde

P,

etc., son los valores pre-exec y P', etc., son los valores post-exec. Con un entendimiento de estas reglas de convolución, podemos explicar cómo se gestiona

el

soporte de libcap(3) para la tupla IAB: la API de IAB. cap_iab_init() devuelve un valor IAB vacío. Es decir, una tupla mayormente

inofensiva.

No bloqueará ninguna file capability Permitted a través de exec, pero tampoco otorgará ninguna. El cap_iab_t devuelto debe liberarse con cap_free(3). cap_iab_dup() devuelve una copia del valor IAB especificado. El cap_iab_t devuelto

Esta función busca por defecto en /proc/<PID> /status la información de IAB, pero esa ubicación puede anularse usando la función cap_proc_root(). cap_iab_set_proc() puedeusarse para establecer el valor IAB que porta el proceso actual. Dicha configuración fallará si el proceso no

En todos los casos, los valores A elevados deben estar presentes en la intersección de los valores Permitted e Inh. cap_iab_to_text() convertirá una tupla IAB a una representación de texto IAB canónica. HISTORIA

El

formato IAB para las variantes heredables de las capacidades se desarrolló primero como la sintaxis de configuración para el módulo Linux-PAM pam_cap.so en libcap-2.29. Se introdujo para extender la simple lista separada por comas de capacidades Inheritable del proceso, que el módulo podía otorgar a un árbol de procesos autenticado, para incluir límites aplicados al vector Bounding y introducir soporte para el vector Ambient de bits de capacidad. Si

bien

los vectores Inheritable y Bounding fueron anticipados por el borrador POSIX.1e que introdujo las capacidades, el vector Ambient es una invención de Linux e incompatible con el modelo de file capabilities de POSIX.1e. Como tal, se consideró que intentar fusionar todos los 5 vectores de capacidades en una sola representación de texto no iba a funcionar. En su lugar, la sintaxis de configuración de pam_cap.so se generalizó en todo un conjunto de funciones de libcap para agrupar juntas las t

res capacidades heredables de forma ingenua: la tupla
IAB. El soporte para esto debutó en libcap-2.33. INFORME
