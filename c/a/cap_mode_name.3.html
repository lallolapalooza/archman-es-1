kernel de Linux honran la semántica POSIX para establecer capacidades y securebits en presencia de pthreads. Es decir, cambiar conjuntos de capacidades, por defecto, solo afecta al hilo en ejecución. Sin embargo, para ser significativamente seguro, los conjuntos de capacidades deberían reflejarse por todos los hilos dentro de un programa común porque los hilos no están aislados en memoria. Como solución alternativa para esto, libcap se empaqueta con una biblioteca separada de llamadas al sistema con semántica POSIX: libpsx. Si su programa usa hilos POSIX, para lograr una manipulación de capacidades con semántica POSIX significativa, debe vincular su programa

con:

ld ... -lcap $(pkg-config --libs --cflags

libpsx)

o

,

gcc ... -lcap $(pkg-config --libs --cflags

libpsx)

Cuando se vincula de esta manera, debido a la magía del enlazador, libcap usa psx_syscall(3) y psx_syscall6(3) para realizar llamadas al sistema de configuración de estado. Notablemente, esto también asegura que cap_prctlw() pueda usarse para asegurar que los bits de control de proceso se compartan en todos los hilos de un solo

proceso.

La biblioteca también soporta las funciones

capgetp() intenta obtener las capacidades de algún otro proceso; almacenando las capacidades en un cap_d preasignado. Vea cap_init() para información sobre cómo asignar un conjunto de capacidades vacío. Esta función está obsoleta; debería usar cap_get_p

id().

capsetp() intenta establecer las capacidades del proceso que llama o de algún otro proceso(s), pid. Note que establecer las capacidades de otro proceso solo es posible en kernels antiguos que no proporcionan soporte VFS para establecer capacidades de archivo. Vea capset(2) para información sobre qué kernels proporcionan dicho

soporte.

Si pid es positivo, se refiere a un proceso específico; si es cero, se refiere al proceso que llama; -1 se refiere a todos los procesos distintos del proceso que llama y del proceso '1' (típicamente init(8)); otros valores negativos se refieren al grupo de procesos

-pid.

Para usar esta función, el kernel debe soportarla y el proceso que llama debe tener CAP_SETPCAP activado en su conjunto de capacidades Efectivas. Las capacidades establecidas en el proceso(s) destino son las contenidas en cap_d

.

Los kernels que soportan capacidades de sistema de archivos redefinen la semántica de CAP_SETPCAP y en tales sistemas, capsetp() siempre fallará para cualquier destino que no sea igual al proceso que llama. capsetp() devuelve cero para éxito, y -1 en caso de

fallo.

En kernels donde es (era) soportado, capsetp() debe usarse con cuidado. Existía, principalmente, para superar una falta temprana de soporte para capacidades en los sistemas de archivos soportados por Linux. Note que en kernels antiguos donde capsetp() podía usarse para establecer las capacidades de otro proceso, los únicos procesos que tenían CAP_SETPCAP disponible por defecto eran procesos iniciados como hilos del kernel. (Típicamente esto incluye init(8), kflushd y kswapd.) Se necesitaba una
