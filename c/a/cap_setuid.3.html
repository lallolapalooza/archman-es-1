#include <sys/capability.h>

	      long int arg3, long int arg4, long int arg5);

Enlazar con -lcap.

DESCRIPCIÓN

cap_get_proc() asigna un estado de capacidades en el almacenamiento de trabajo, establece su estado al del proceso que lo invoca y devuelve un puntero a este estado de capacidades recién creado. El llamador debe liberar cualquier memoria que pueda liberarse, cuando el estado de capacidades en el almacenamiento de trabajo ya no sea necesario, llamando a cap_free() con el cap_t como argumento.

cap_set_proc() establece los valores para todos los indicadores de capacidades para todas las capacidades en el estado de capacidades identificado por cap_p. El nuevo estado de capacidades del proceso estará completamente determinado por el contenido de cap_p al regresar exitosamente de esta función. Si algún indicador en cap_p está establecido para alguna capacidad que actualmente no esté permitida para el proceso que la invoca, la función fallará, y el estado de capacidades del proceso permanecerá sin cambios.

cap_get_pid() devuelve un cap_t, ver cap_init(3), con las capacidades del proceso conocido por el llamador como pid. Si pid es 0, entonces se devuelven las capacidades del proceso que la invoca. Esta información también se puede obtener del archivo /proc/<pid>/status . (Las entradas en ese archivo pueden traducirse con la línea de comandos capsh --decode=XXX .) Cuando el llamador está operando dentro de un espacio de nombres (CLONE_NEWPID), el argumento numérico pid se interpreta en el rango de ese espacio de nombres. Como tal, la idea del llamador del pid de destino puede diferir de la del proceso de destino cuando están operando en diferentes espacios de nombres de pid. Ver pid_namespaces(7) para más detalles. Además, el valor cap_t devuelto contiene las capacidades que el pid de destino cree que tiene. Si el destino está operando en un espacio de nombres (CLONE_NEWUSER), el privilegio general del sistema de esas capacidades del espacio de nombres de usuario puede estar sustancialmente reducido. Ver user_namespaces(7) para más detalles.

cap_get_bound() con cap como argumento devuelve el valor actual de este indicador de capacidad del conjunto de límites en vigor para el proceso que la invoca. Esta operación no requiere privilegios. Nótese que se proporciona una función macro CAP_IS_SUPPORTED(cap_value_t cap) que evalúa a verdadero (1) si el sistema soporta la capacidad especificada, cap. Si el sistema no soporta la capacidad, esta función devuelve 0. Esta macro funciona probando una condición de error con cap_get_bound().

cap_drop_bound() se puede usar para bajar la capacidad del conjunto de límites especificada, cap. Para completarse exitosamente, el conjunto de capacidades efectivas vigente debe tener un CAP_SETPCAPelevado.

cap_get_ambient() devuelve el valor vigente de la capacidad ambiental especificada, o -1 si el kernel en ejecución no soporta la capacidad. Una macro CAP_AMBIENT_SUPPORTED() usa esta función para determinar si el kernel soporta capacidades ambientales.

cap_set_ambient() establece la capacidad ambiental especificada en un valor específico. Para elevar una capacidad ambiental específica, los indicadores heredables y permitidos del proceso que la invoca deben contener el valor de capacidad especificado. Los bits ambientales elevados solo se retendrán mientras esto siga siendo cierto para los indicadores heredables y permitidos.

cap_reset_ambient() restablece todas las capacidades ambientales del proceso que la invoca a su valor bajo. Nótese que el conjunto ambiental está destinado a operar en un entorno heredado donde la aplicación tiene un conocimiento limitado de las capacidades en general. Al ejecutar un archivo con capacidades de sistema de archivos asociadas, el kernel restablecerá implícitamente el conjunto ambiental del proceso. Además, los cambios en el conjunto heredable por el código del programa sin restablecer explícitamente el conjunto ambiental también pueden bajar bits ambientales.

cap_get_secbits() devuelve los securebits del proceso que la invoca. Estos bits afectan la manera en que el proceso que la invoca implementa cosas como la corrección de setuid-root y las capacidades ambientales.

cap_set_secbits() intenta modificar los securebits del proceso que la invoca. Nótese que CAP_SETPCAP debe estar en el conjunto de capacidades efectivas para que esto sea efectivo. Algunas configuraciones bloquean los subestados de los securebits, por lo que los intentos de establecer valores pueden ser denegados por el kernel incluso cuando la capacidad CAP_SETPCAP está elevada.

Para ayudar a gestionar la complejidad de los securebits, libcap proporciona un concepto combinado de securebit y conjunto de capacidades llamado modo de libcap. cap_get_mode() intenta resumir el entorno de seguridad vigente en forma de un valor numérico cap_mode_t . Se puede obtener una representación de texto del modo a través de la función cap_mode_name() . La gran mayoría de las combinaciones de estos valores no están bien definidas en términos de un modo de libcap, y para estos estados cap_get_mode() devuelve (cap_mode_t)0, que cap_get_name() identifica como ``UNCERTAIN''. Los modos soportados son: CAP_MODE_NOPRIV, CAP_MODE_HYBRID, CAP_MODE_PURE1E y CAP_MODE_PURE1E_INIT.

cap_prctl() se puede usar para leer estado a través de la llamada al sistema prctl() .

cap_prctlw() se puede usar para escribir estado a través de la llamada al sistema prctl() .

cap_set_mode() se puede usar para establecer el modo deseado. Se requiere la capacidad permitida CAP_SETPCAP para que esta función tenga éxito.

cap_setuid() es una función de conveniencia para la llamada al sistema setuid(2) . Donde cap_setuid() se encarga de elevar la capacidad efectiva correcta para realizar la llamada al sistema, y también se encarga de preservar la disponibilidad de las capacidades permitidas después de que el uid haya cambiado. Tras esta llamada, todas las capacidades efectivas se bajan.

cap_setgroups() es una función de conveniencia para realizar las llamadas setgid(2) y setgroups(2) en una sola llamada. La llamada cap_setgroups() eleva la capacidad efectiva correcta durante la duración de la llamada, y vacía el conjunto de capacidades efectivas antes de regresar.

VALOR DE RETORNO

Las funciones cap_get_proc() y cap_get_pid() devuelven un valor no nulo en caso de éxito, y nulo en caso de fallo.

La función cap_get_bound() devuelve -1 si la capacidad solicitada es desconocida, de lo contrario el valor de retorno refleja el estado actual de esa capacidad en el conjunto de límites vigente. Nótese que una función macro,

Todas las funciones de configuración como cap_set_proc() y cap_drop_bound() devuelven cero para éxito, y -1 para fallo.

En caso de fallo, errno se establece a EINVAL, EPERM, o ENOMEM.

CONFORMIDAD

cap_set_proc() y cap_get_proc() están especificadas en el borrador retirado de la especificación POSIX.1e. cap_get_pid() es una extensión de Linux.

NOTAS

Ni glibc, ni el kernel de Linux honran la semántica de POSIX para establecer capacidades y securebits en presencia de pthreads. Es decir, cambiar los conjuntos de capacidades, de forma predeterminada, solo afecta al hilo en ejecución. Sin embargo, para ser significativamente seguros, los conjuntos de capacidades deberían ser reflejados por cap_setuid(3) — libcap — Arch Linux

NAME

cap_setuid, cap_setuid_raw, cap_setgroups, cap_setgroups_raw - set user and group IDs

LIBRARY

libcap

SYNOPSIS

#include <sys/types.h>
#include <sys/capability.h>>

int
cap_setuid(uid_t uid);

int
cap_setuid_raw(uid_t uid);

int
cap_setgroups(gid_t gid, size_t nrealids, const gid_t realids[]);

int
cap_setgroups_raw(gid_t gid, size_t nrealids, const gid_t realids[]);

DESCRIPTION

These functions allow a process to change its user and group IDs. This is normally the exclusive privilege of the superuser, but can be delegated using capabilities. Specifically, the capability CAP_SETUID is required to adjust the real, effective, and saved set user IDs, and CAP_SETGID is required to adjust the real, effective, and saved set group IDs.

The set of processes that can be affected by these calls are determined by the capabilities possessed by the caller. Specifically, the caller must have the CAP_SETUID capability effective in order to change the UID of any process other than itself, and the CAP_SETGID capability effective in order to change the GID of any process other than itself.

The behaviour of these functions is subtly different when using POSIX threads. Without libpsx, all threads within a common program because threads are not memory isolated. As a workaround for this, libcap is packaged with a separate POSIX semantics system call library: libpsx. If your program uses POSIX threads, to achieve meaningful POSIX semantics capability manipulation, you should link your program with:

ld ... -lcap $(pkg-config --libs --cflags libpsx)

or,

gcc ... -lcap $(pkg-config --libs --cflags libpsx)

When linked this way, due to linker magic, libcap uses psx_syscall(3) and psx_syscall6(3) to perform state setting system calls. Notably, this also ensures that cap_prctlw() can be used to ensure process control bits are shared over all threads of a single process.

capgetp() and capsetp()

The library also supports the deprecated functions:

int capgetp(pid_t pid, cap_t cap_d);

int capsetp(pid_t pid, cap_t cap_d);

capgetp() attempts to obtain the capabilities of some other process; storing the capabilities in a pre-allocated cap_d. See cap_init() for information on allocating an empty capability set. This function is deprecated; you should use cap_get_pid().

capsetp() attempts to set the capabilities of the calling process or of some other process(es), pid. Note that setting capabilities of another process is only possible on older kernels that do not provide VFS support for setting file capabilities. See capset(2) for information on which kernels provide such support.

If pid is positive it refers to a specific process; if it is zero, it refers to the calling process; -1 refers to all processes other than the calling process and process '1' (typically init(8)); other negative values refer to the -pid process group.

In order to use this function, the kernel must support it and the calling process must have CAP_SETPCAP raised in its Effective capability set. The capabilities set in the target process(es) are those contained in cap_d.

Kernels that support filesystem capabilities redefine the semantics of CAP_SETPCAP and on such systems, capsetp() will always fail for any target not equal to the calling process. capsetp() returns zero for success, and -1 on failure.

On kernels where it is (was) supported, capsetp() should be used with care. It existed, primarily, to overcome an early lack of support for capabilities in the filesystems supported by Linux. Note that on older kernels where capsetp() could be used to set the capabilities of another process, the only processes that had CAP_SETPCAP available to them by default were processes started as kernel threads. (Typically this includes init(8), kflushd and kswapd.) A kernel recompilation was needed to modify this default.

RETURN VALUE

On success, these functions return 0. On failure, they return -1, and errno is set to indicate the error.

CONFORMING TO

These functions are specific to libcap and do not correspond to any standard system calls.

NOTES

The raw functions, cap_setuid_raw() and cap_setgroups_raw(), do not perform capability checks. They simply call the underlying setuid(2) and setgroups(2) system calls. These should only be used if the caller already knows that it has the necessary capabilities.

The standard functions, cap_setuid() and cap_setgroups(), perform the necessary capability checks before calling the underlying system calls. They also update the capabilities of the target process(es) appropriately.

Note that POSIX threads have their own user and group ID state. Therefore, when using POSIX threads, these functions operate on the user and group ID state of the calling thread, not the entire process. If you need to modify the user and group IDs for all threads in a process, you should use the libpsx library, which provides wrappers for the system calls that correctly interact with the process-wide state.

The target of cap_setuid() and cap_setgroups() is determined by the process context of the capabilities. If the process has namespace support enabled, then the operations are restricted to the current namespace. Without namespace support, the operations apply to the entire system.

EXAMPLE

The code segment below raises the CAP_FOWNER and CAP_SETFCAP effective capabilities for the caller:

    ...
    cap_t caps;
    const cap_value_t cap_list[2] = {CAP_FOWNER, CAP_SETFCAP};
    if (!CAP_IS_SUPPORTED(CAP_SETFCAP))
        /* handle error */
    caps = cap_get_proc();
    if (caps == NULL)
        /* handle error */;
    if (cap_set_flag(caps, CAP_EFFECTIVE, 2, cap_list, CAP_SET) == -1)
        /* handle error */;
    if (cap_set_proc(caps) == -1)
        /* handle error */;
    if (cap_free(caps) == -1)
        /* handle error */;
    ...

Alternatively, to completely drop privilege in a program launched setuid-root but wanting to run as a specific user ID etc. in such a way that neither it, nor any of its children can acquire privilege again:

    ...
    uid_t nobody = 65534;
    const gid_t groups[] = {65534};
    if (cap_setgroups(groups[0], 1, groups) != 0)
        /* handle error */;
    if (cap_setuid(nobody) != 0)
        /* handle error */;
    /*
     * privilege is still available here
     */
    if (cap_set_mode(CAP_MODE_NOPRIV) != 0)
        /* handle error */
    ...

Note, the above sequence can be performed by the capsh tool as follows:

sudo capsh --user=nobody --mode=NOPRIV --print

where --print displays the resulting privilege state.
