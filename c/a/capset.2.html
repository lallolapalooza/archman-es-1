capget(2) Manual de Llamadas al Sistema capget(2)

NOMBRE

capget, capset - establece/obtiene las capacidades de los hilos

BIBLIOTECA

Biblioteca C estándar (libc,-lc)

SINOPSIS

#include <linux/capability.h> /* Definición de las constantes CAP_* y
                                 _LINUX_CAPABILITY_* */
#include <sys/syscall.h>      /* Definición de las constantes SYS_* */
#include <unistd.h>
int syscall(SYS_capget, cap_user_header_t hdrp,
            cap_user_data_t datap);
int syscall(SYS_capset, cap_user_header_t hdrp,
            const cap_user_data_t datap);

Nota: glibc no proporciona envoltorios para estas llamadas al sistema, por lo que es necesario usar syscall(2).

DESCRIPCIÓN

Estas dos llamadas al sistema son la interfaz cruda del kernel para obtener y establecer las capacidades de los hilos. No solo estas llamadas al sistema son específicas de Linux, sino que la API del kernel probablemente cambiará y el uso de estas llamadas (en particular el formato de los tipos cap_user_*_t ) está sujeto a extensión con cada revisión del kernel, pero los programas antiguos seguirán funcionando.

Las interfaces portables son cap_set_proc(3) y cap_get_proc(3); si es posible, debería usar esas interfaces en sus aplicaciones; consulte NOTAS.

Detalles actuales

Ahora que ha sido advertido, algunos detalles actuales del kernel. Las estructuras se definen como sigue.


#define _LINUX_CAPABILITY_VERSION_1  0x19980330
#define _LINUX_CAPABILITY_U32S_1     1
        /* V2 añadido en Linux 2.6.25; obsoleto */
#define _LINUX_CAPABILITY_VERSION_2  0x20071026
#define _LINUX_CAPABILITY_U32S_2     2
        /* V3 añadido en Linux 2.6.26 */
#define _LINUX_CAPABILITY_VERSION_3  0x20080522
#define _LINUX_CAPABILITY_U32S_3     2
typedef struct __user_cap_header_struct {
   __u32 version;
   int pid;
} *cap_user_header_t;
typedef struct __user_cap_data_struct {
   __u32 effective;
   __u32 permitted;
   __u32 inheritable;
} *cap_user_data_t;

Los campos effective, permittedy inheritable son máscaras de bits de las capacidades definidas en capabilities(7). Tenga en cuenta que los valores CAP_* son índices de bits y deben desplazarse antes de hacer OR con los campos de bits. Para definir las estructuras que se pasarán a la llamada al sistema, debe usar los nombres struct __user_cap_header_struct y struct __user_cap_data_struct porque los typedefs son solo punteros.

Los kernels anteriores a Linux 2.6.25 prefieren capacidades de 32 bits con la versión _LINUX_CAPABILITY_VERSION_1. Linux 2.6.25 añadió conjuntos de capacidades de 64 bits, con la versión _LINUX_CAPABILITY_VERSION_2. Sin embargo, hubo un error en la API, y Linux 2.6.26 añadió _LINUX_CAPABILITY_VERSION_3 para corregir el problema.

Tenga en cuenta que las capacidades de 64 bits usan datap[0] y datap[1], mientras que las capacidades de 32 bits usan solo datap[0].

En los kernels que soportan capacidades de archivo (soporte de capacidades VFS), estas llamadas al sistema se comportan de manera ligeramente diferente. Este soporte se añadió como una opción en Linux 2.6.24, y se convirtió en fijo (no opcional) en Linux 2.6.33.

Para las llamadas a capget(), se pueden sondear las capacidades de cualquier proceso especificando su ID de proceso con el valor del campo hdrp->pid .

Para detalles sobre los datos, consulte capabilities(7).

Con soporte de capacidades VFS

Las capacidades VFS emplean un atributo extendido de archivo (consulte xattr(7)) para permitir que las capacidades se adjunten a los ejecutables. Este modelo de privilegios obsoletiza el soporte del kernel para que un proceso asíncronamente establezca las capacidades de otro. Es decir, en los kernels que tienen soporte de capacidades VFS, al llamar a capset(), los únicos valores permitidos para hdrp->pid son 0 o, equivalentemente, el valor devuelto por gettid(2).

Sin soporte de capacidades VFS

En kernels antiguos que no proporcionan soporte de capacidades VFS, capset() puede, si el invocador tiene la capacidad CAP_SETPCAP , usarse para cambiar no solo las capacidades del propio invocador, sino también las capacidades de otros hilos. La llamada opera sobre las capacidades del hilo especificado por el campo pid de hdrp cuando ese es distinto de cero, o sobre las capacidades del hilo invocador si pid es 0. Si pid se refiere a un proceso de un solo hilo, entonces pid puede especificarse como un ID de proceso tradicional; operar sobre un hilo de un proceso multihilo requiere un ID de hilo del tipo devuelto por gettid(2). Para capset(), pid también puede ser: -1, lo que significa realizar el cambio en todos los hilos excepto el invocador y init(1); o un valor menor que -1, en cuyo caso el cambio se aplica a todos los miembros del grupo de procesos cuyo ID es -pid.

VALOR DEVUELTO

En caso de éxito, se devuelve cero. En caso de error, se devuelve -1, y errno se establece para indicar el error.

Las llamadas fallan con el error EINVAL, y establecen el campo version de hdrp al valor preferido por el kernel de _LINUX_CAPABILITY_VERSION_? cuando se especifica una versión no soportada. De esta manera, se puede sondear cuál es la revisión de capacidades preferida actualmente.

ERRORES

EFAULT
Dirección de memoria incorrecta. hdrp no debe ser NULL. datap puede ser NULL solo cuando el usuario intenta determinar el formato de versión de capacidades preferido soportado por el kernel.
EINVAL
Uno de los argumentos era inválido.
EPERM
Se intentó añadir una capacidad al conjunto permitido, o establecer una capacidad en el conjunto efectivo que no está en el conjunto permitido.
EPERM
Se intentó añadir una capacidad al conjunto heredable, y bien:
•
esa capacidad no estaba en el conjunto delimitador del invocador; o
•
la capacidad no estaba en el conjunto permitido del invocador y al invocador le faltaba la capacidad CAP_SETPCAP en su conjunto efectivo.
EPERM
El invocador intentó usar capset() para modificar las capacidades de un hilo distinto de sí mismo, pero carecía de privilegios suficientes. Para los kernels que soportan capacidades VFS, esto nunca está permitido. Para los kernels que carecen de soporte VFS, se requiere la capacidad CAP_SETPCAP . (Un error en los kernels anteriores a Linux 2.6.11 significaba que este error también podía ocurrir si un hilo sin esta capacidad intentaba cambiar sus propias capacidades especificando el campo pid como un valor distinto de cero (es decir, el valor devuelto por getpid(2)) en lugar de 0.)
ESRCH
No existe tal hilo.

ESTÁNDARES

Linux.

NOTAS

La interfaz portable para las funciones de consulta y establecimiento de capacidades es proporcionada por la biblioteca libcap y está disponible aquí:
http://git.kernel.org/cgit/linux/kernel/git/morgan/libcap.git

VÉASE TAMBIÉN
