DESCRIPCIÓ

N

Un lanzador proporciona un mecanismo para que el código ejecute una función de retorno de llamada y/o un ejecutable de programa en un entorno con un contexto de seguridad modificado. Esencialmente, proporciona un mecanismo para que un programa haga fork(2) de un nuevo contexto a partir del del programa principal, manipule las capacidades y otro estado privilegiado en ese proceso tras el fork(2) antes de (opcionalmente) hacer execve(2) de un nuevo programa. Cuando la aplicación se enlaza con -lpsx, se necesita este soporte para ejecutar de forma robusta el código lanzado sin modificar el privilegio de toda la aplicación principal (que respeta la semántica POSIX)

.

Un lanzador se define con una de estas dos funciones: cap_new_launcher() o cap_func_launcher(). El valor de retorno es de un tipo opaco cap_launch_t; un valor de retorno NULL implica que ha ocurrido un

error.

Una vez definido, un valor cap_launch_t puede usarse con cap_launch() para ejecutar ese lanzador. En tales casos, un valor de retorno no negativo indica éxito: cero significa éxito sin que se invoque un programa; un valor no cero es igual al ID del proceso (pid_t) del programa recién

lanzado.

Un cap_launch_t ocupa memoria asignada y debe liberarse con cap_free(3). Antes de ser liberado con cap_free(3), un valor cap_value_t puede reutilizarse para múltiples lanzamientos independientes. El argumento detail de cap_launch(), en conjunto con la función de retorno de llamada del lanzador, puede usarse para personalizar la invocación del lanzamiento. Se debe tener cuidado para aprovechar la memoria compartida personalizada (ver mmap(2)) u otro mecanismo IPC para devolver valores al programa principal a través de detail, ya que la función de retorno de llamada y cualquier ejecución posterior del programa ocurrirán fuera del proceso principal de la aplicación que llama. Un ejemplo de esto sería asignar detail de la siguiente

manera: 
   const char *args[] = { "echo", "hello", NULL };
   cap_launch_t cmd = cap_new_launcher("/usr/bin/echo", args, NULL);
   int *detail = mmap(NULL, sizeof(int), PROT_READ | PROT_WRITE,
                      MAP_SHARED | MAP_ANONYMOUS, -1, 0);
   cap_launcher_callback(cmd, &answer_detail_fn);
   *detail = 41;
   pid_t pid = cap_launch(cmd, detail);
   printf("launcher callback set detail to %d\n", *detail);
   munmap(detail, sizeof(int))
;

A menos que la función de retorno de llamada lo modifique, el código lanzado se ejecutará con las capacidades y el otro contexto de seguridad de la

aplicación.

Si la función de retorno de llamada devuelve algo distinto de cero, un cap_launch() será abortado. Si el detalle del fallo es importante para el llamante, debe comunicarse a través del argumento d

etail.

Las siguientes funciones pueden usarse para instruir al lanzador a modificar el estado de seguridad del programa invocado sin alterar el estado del programa que llama. Dichas modificaciones deben realizarse antes de llamar a cap_launch() si se desea que tengan el efecto deseado. Además, solo se invocan después de que cualquier retorno de llamada instalado haya completado. Por ejemplo, se pueden descartar o modificar capacidades, solo para ejecutar un

archivo.

Las siguientes funciones instruyen al lanzador para realizar algunas tareas comunes de este tipo (note que algunas requieren bits de capacidad permitidos para tener éxito)

:

cap_launcher_callback() puede usarse para instalar o reemplazar la función de retorno de llamada actualmente instalada del

lanzador.

cap_launcher_set_mode() puede usarse para asegurar que el modo libcap del programa lanzado sea el

deseado.

cap_launcher_set_iab() Esta función devuelve el cap_iab_t previamente asociado con el lanzador. Llamar a esta función con un valor IAB de NULL configurará el lanzador para no establecer un valor IAB (el valor predeterminado). Ver cap_iab(3) para detalles sobre el conjunto IAB. Note que el lanzador se asocia directamente con el valor iab proporcionado y no hace una copia de él. Este valor iab está bloqueado para el lanzador y no puede modificarse mientras esté asociado con el lanzador. Establézcalo con NULL para recuperar el control de la memoria asociada con ese valor IAB; de lo contrario, el valor IAB será liberado con cap_free()cuando el lanzador lo

sea.

cap_launcher_set_chroot() Esta función hace que el ejecutable del programa lanzado sea invocado dentro de un directorio raíz chroot .

cap_launcher_setuid() Esta función hace que el ejecutable del programa lanzado sea invocado con el identificador de usuario especificado (uid_t

).

cap_launcher_setgroups() Esta función hace que el ejecutable del programa lanzado sea invocado con los IDs de grupo primario y suplementarios

especificados.

Note que si alguna de las mejoras al lanzador realizadas por las

funciones anteriores no logra surtir efecto (típicamente por falta d
e privilegio suficiente), el lanzamiento fallará y devolverá -1.

ERRORE

S

Un retorno de NULL para un cap_launch_t debe considerarse un

error.

cap_launch() devuelve -1 en caso de

error.

En todos estos casos, un valor de retorno de 0 implica éxito. En otros casos, consulte errno(3) para

más de
talles.

HISTORI

A

La familia de funciones cap_launch() se introdujo en libcap 2.33. Aborda principalmente una complejidad con las aplicaciones pthreads(7) enlazadas con -lpsx que usan capacidades pero también respetan la semántica

POSIX.

Usar -lcap y -lpthread juntos sin el soporte de semántica POSIX de -lpsx introduce una clase sutil de exposición a la escalada de privilegios. (Ver https://sites.google.com/site/fullycapable/w

ho-ordered-libpsx para
una explicación.)
