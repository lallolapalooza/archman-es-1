DESCRIPCIÓN

Las funciones definidas en esta página del manual se refieren a las tres tuplas de vectores de capacidades de proceso ingenuamente heredables: Inh, Amb y Bound. Esta tupla IAB de 3 vectores de capacidades, capturada en el tipo cap_iab_t, se combinan para pasar capacidades de un proceso a otro a través de llamadas al sistema execve(2). Las reglas de convolución que utilizan la tupla IAB son un conjunto de reglas de reserva cuando el archivo ejecutado no tiene capacidades de archivo configuradas.

Existen algunas restricciones impuestas por el kernel con respecto a los tres componentes de una tupla IAB y la bandera de proceso Permitted. Estas son: el vector Inh (CAP_IAB_INH) es enteramente igual a la bandera Inheritable del proceso en todo momento; el vector Amb (CAP_IAB_AMB) no contiene más valores de capacidad que la intersección del vector Inh y la bandera Permitted para el proceso; y el vector Bound (o bloqueado) (CAP_IAB_BOUND) es el complemento a dos del vector de límites del proceso.

En algunos entornos, se considera deseable heredar las capacidades ingenuamente. Es decir, pasar capacidades, independientemente del estado del binario ejecutado, del padre al hijo a través de llamadas al sistema exec*. Las capacidades supervivientes se convierten en la bandera Permitted para el proceso post-ejecución. Este método de herencia difiere significativamente del mecanismo de herencia de saludo entre un proceso pre-exec* y un ejecutable que otorga capacidades de archivo del mecanismo de capacidades tradicional (POSIX.1e).

Las reglas de convolución para la herencia estilo IAB son: I'=I; A'=A&I; P'=A&I&P. Donde P etc son los valores pre-ejecución y P' etc son los valores post-ejecución.

Con una comprensión de estas reglas de convolución, podemos explicar cómo se gestiona el soporte de libcap(3) para la tupla IAB: la API de IAB.

cap_iab_init() devuelve un valor IAB vacío. Es decir, una tupla mayormenote-inocuo. No bloqueará ninguna capacidad de archivo Permitted a través de exec, pero tampoco otorgará ninguna. La cap_iab_t devuelta debe liberarse con cap_free(3).

cap_iab_dup() devuelve una copia del valor IAB especificado. La cap_iab_t devuelta debe liberarse con cap_free(3).

cap_iab_get_proc() devuelve una copia del valor IAB para el proceso actual. La cap_iab_t devuelta debe liberarse con cap_free(3).

cap_iab_get_pid() devuelve una copia del valor IAB para el proceso especificado. La cap_iab_t devuelta debe liberarse con cap_free(3). Esta función, por defecto, busca en /proc/<PID>/status la información IAB, pero esa ubicación puede ser anulada utilizando la función cap_proc_root().

cap_iab_set_proc() puede usarse para establecer el valor IAB que lleva el proceso actual. Dicha configuración fallará si el proceso no es suficientemente capaz. Para elevar los bits I que no están presentes en la bandera P, o para aplicar nuevas máscaras B, se requiere que CAP_SETPCAP esté presente en la bandera Permitted (la función la elevará temporalmente en la bandera Effective si es necesario). En todos los casos, los valores A elevados deben estar presentes en la intersección de los valores Permitted e Inh.

cap_iab_to_text() convertirá una tupla IAB a una representación de texto IAB canónica. La representación es ligeramente redundante pero libcap(3) intentará generar una representación lo más corta posible.

cap_iab_from_text() genera una tupla IAB a partir de una cadena de texto (probablemente generada por la función anterior). La tupla IAB devuelta debe liberarse con cap_free().

cap_iab_get_vector() puede usarse para determinar el valor específico de capacidad de un vector IAB.

cap_iab_compare() puede usarse para comparar dos tuplas cap_iab_t. Cuando el valor de retorno es distinto de cero, la macro CAP_IAB_DIFFERS(status, vector) se evalúa como distinta de cero si el estado devuelto difiere en sus componentes de vector.

cap_iab_set_vector() puede usarse para establecer un valor de vector específico a la configuración de habilitación.

cap_iab_fill() puede usarse para copiar masivamente un valor de bandera cap_t en el vector vec de la tupla IAB. La copia en Amb (CAP_IAB_AMB) de esta manera puede elevar implícitamente los valores Inh (CAP_IAB_INH) en la tupla IAB. De manera similar, la copia en el vector Inh puede disminuir implícitamente los valores Amb que no están presentes en el vector Inh resultante.

cap_proc_root() puede usarse para determinar la ubicación actual consultada por cap_iab_get_pid(). Los valores devueltos deben liberarse con cap_free(3). Si el argumento de cap_proc_root() no es NULL, una copia de él se convertirá en el reemplazo para /proc. Tenga en cuenta que esta función no es segura para hilos con respecto a llamadas concurrentes a cap_iab_get_pid().

ERRORES

Las funciones que devuelven valores cap_iab_t o memoria asignada en forma de cadena devuelven NULL en caso de error.

Los valores de retorno enteros son -1 en caso de error y 0 en caso de éxito.

En caso de error, consulte errno.

NOTAS

A diferencia del conjunto de capacidades cap_t tradicional, la tupla IAB, en conjunto, es incompatible con las capacidades del sistema de archivos creadas mediante herramientas como setcap(8). Es decir, el vector Amb de la tupla IAB se vuelve irrelevante cuando se ejecuta un ejecutable con una capacidad de archivo.

Además, existen modos de libcap cap_mode(3) que hacen que el vector Amb y su método de herencia de procesos queden deshabilitados.

HISTORIA

El formato IAB para variantes heredables de capacidades se desarrolló por primera vez como la sintaxis de configuración para el módulo Linux-PAM pam_cap.so en libcap-2.29. Se introdujo para extender la lista *simple* separada por comas de capacidades Heredables de proceso, que el módulo podía otorgar a un árbol de procesos autenticado, para incluir límites impuestos en el vector Bounding e introducir soporte para el vector Ambient de bits de capacidad.

Si bien los vectores Inheritable y Bounding fueron anticipados por el borrador POSIX.1e que introdujo las capacidades, el vector Ambient es una invención de Linux e incompatible con el modelo de capacidades de archivos de POSIX.1e. Como tal, se consideró que intentar fusionar los 5 vectores de capacidades en una única representación de texto no funcionaría. En su lugar, la sintaxis de configuración de pam_cap.so se generalizó en un conjunto completo de funciones de libcap para agrupar las tres capacidades heredables ingenuamente: la tupla IAB. El soporte para esto debutó en libcap-2.33.
