Si su programa usa hilos POSIX, para lograr una manipulación de capacidades con semántica POSIX significativa, debe vincular su programa con:

Al vincularse de esta manera, debido a la magia del enlazador, libcap usa psx_syscall(3) y psx_syscall6(3) para realizar llamadas al sistema de configuración de estado. Notablemente, esto también asegura que cap_prctlw() pueda usarse para asegurar que los bits de control del proceso se compartan en todos los hilos de un solo proceso.

capgetp() y capsetp()

La biblioteca también soporta las funciones obsoletas:

int capgetp(pid_t pid, cap_t cap_d);

int capsetp(pid_t pid, cap_t cap_d);

capgetp() intenta obtener las capacidades de algún otro proceso; almacenando las capacidades en un cap_dpreasignado. Vea cap_init() para información sobre cómo asignar un conjunto de capacidades vacío. Esta función está obsoleta; debería usar cap_get_pid().

capsetp() intenta establecer las capacidades del proceso que llama o de algún otro u otros procesos, pid. Tenga en cuenta que establecer capacidades de otro proceso solo es posible en núcleos más antiguos que no proporcionan soporte VFS para establecer capacidades de archivos. Vea capset(2) para información sobre qué núcleos proporcionan dicho soporte.

Si pid es positivo, se refiere a un proceso específico; si es cero, se refiere al proceso que llama; -1 se refiere a todos los procesos distintos del proceso que llama y del proceso '1' (típicamente init(8)); otros valores negativos se refieren al -pid grupo de procesos.

Para usar esta función, el núcleo debe soportarla y el proceso que llama debe tener CAP_SETPCAP activado en su conjunto de capacidades Efectivas. Las capacidades establecidas en el proceso(s) destino son las contenidas en cap_d.

Los núcleos que soportan capacidades de sistema de archivos redefinen la semántica de CAP_SETPCAP y en tales sistemas, capsetp() siempre fallará para cualquier destino que no sea igual al proceso que llama. capsetp() devuelve cero para éxito, y -1 para fallo.

En núcleos donde es (era) soportado, capsetp() debe usarse con cuidado. Existía principalmente para superar una temprana falta de soporte para capacidades en los sistemas de archivos soportados por Linux. Tenga en cuenta que en núcleos más antiguos donde capsetp() podía usarse para establecer las capacidades de otro proceso, los únicos procesos que tenían CAP_SETPCAP disponibles por defecto eran procesos iniciados como hilos del núcleo. (Típicamente esto incluye init(8), kflushd y kswapd.) Se necesitaba una recompilación del núcleo para modificar este valor por defecto.

EJEMPLO

El segmento de código siguiente activa las CAP_FOWNER y CAP_SETFCAP capacidades efectivas para el llamador:

    ...
    cap_t caps;
    const cap_value_t cap_list[2] = {CAP_FOWNER, CAP_SETFCAP};
    if (!CAP_IS_SUPPORTED(CAP_SETFCAP))
        /* handle error */
    caps = cap_get_proc();
    if (caps == NULL)
        /* handle error */;
    if (cap_set_flag(caps, CAP_EFFECTIVE, 2, cap_list, CAP_SET) == -1)
        /* handle error */;
    if (cap_set_proc(caps) == -1)
        /* handle error */;
    if (cap_free(caps) == -1)
        /* handle error */;
    ...

Alternativamente, para descartar completamente el privilegio en un programa lanzado con setuid-root pero que quiere ejecutarse con un ID de usuario específico, etc., de tal manera que ni él, ni ninguno de sus hijos puedan adquirir privilegio de nuevo:

    ...
    uid_t nobody = 65534;
    const gid_t groups[] = {65534};
    if (cap_setgroups(groups[0], 1, groups) != 0)
        /* handle error */;
    if (cap_setuid(nobody) != 0)
        /* handle error */;
    /*
     * privilege is still available here
     */
    if (cap_set_mode(CAP_MODE_NOPRIV) != 0)
        /* handle error */
    ...

Nótese, la secuencia anterior puede ser realizada por la capsh herramienta de la siguiente manera:

sudo capsh --user=nobody --mode=NOPRIV --print

donde --print muestra el estado de privilegio resultante.
