capget(2) Manual de llamadas al sistema capget(2)

NOMBRE

capget, capset - obtener/establecer capacidades de hilo(s)

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <linux/capability.h> /* Definición de constantes CAP_* y
                                 _LINUX_CAPABILITY_* */
#include <sys/syscall.h>      /* Definición de constantes SYS_* */
#include <unistd.h>
int syscall(SYS_capget, cap_user_header_t hdrp,
            cap_user_data_t datap);
int syscall(SYS_capset, cap_user_header_t hdrp,
            const cap_user_data_t datap);

Nota: glibc no proporciona envolturas para estas llamadas al sistema, lo que hace necesario el uso de syscall(2).

DESCRIPCIÓN

Estas dos llamadas al sistema son la interfaz del kernel de bajo nivel para obtener y establecer las capacidades de un hilo. No solo son estas llamadas al sistema específicas de Linux, sino que es probable que la API del kernel cambie y el uso de estas llamadas al sistema (en particular, el formato de los tipos cap_user_*_t) esté sujeto a extensiones con cada revisión del kernel, pero los programas antiguos seguirán funcionando.

Las interfaces portátiles son cap_set_proc(3) y cap_get_proc(3); si es posible, deberías usar esas interfaces en las aplicaciones; véase NOTAS.

Detalles actuales

Ahora que ha sido advertido, algunos detalles actuales del kernel. Las estructuras se definen de la siguiente manera.


#define _LINUX_CAPABILITY_VERSION_1  0x19980330
#define _LINUX_CAPABILITY_U32S_1     1
        /* V2 añadido en Linux 2.6.25; obsoleto */
#define _LINUX_CAPABILITY_VERSION_2  0x20071026
#define _LINUX_CAPABILITY_U32S_2     2
        /* V3 añadido en Linux 2.6.26 */
#define _LINUX_CAPABILITY_VERSION_3  0x20080522
#define _LINUX_CAPABILITY_U32S_3     2
typedef struct __user_cap_header_struct {
   __u32 version;
   int pid;
} *cap_user_header_t;
typedef struct __user_cap_data_struct {
   __u32 effective;
   __u32 permitted;
   __u32 inheritable;
} *cap_user_data_t;

Los campos effective, permitted e inheritable son máscaras de bits de las capacidades definidas en capabilities(7). Tenga en cuenta que los valores CAP_* son índices de bits y deben ser desplazados a la izquierda antes de hacer un OR con los campos de bits. Para definir las estructuras a pasar a la llamada al sistema, tiene que usar los nombres struct __user_cap_header_struct y struct __user_cap_data_struct porque los typedef solo son punteros.

Los kernels anteriores a Linux 2.6.25 prefieren capacidades de 32 bits con la versión _LINUX_CAPABILITY_VERSION_1. Linux 2.6.25 añadió conjuntos de capacidades de 64 bits, con la versión _LINUX_CAPABILITY_VERSION_2. Sin embargo, hubo un fallo en la API, y Linux 2.6.26 añadió _LINUX_CAPABILITY_VERSION_3 para solucionar el problema.

Tenga en cuenta que las capacidades de 64 bits usan datap[0] y datap[1], mientras que las capacidades de 32 bits usan solo datap[0].

En kernels que admiten capacidades de archivo (soporte de capacidades VFS), estas llamadas al sistema se comportan de manera ligeramente diferente. Este soporte se añadió como opción en Linux 2.6.24, y se volvió fijo (no opcional) en Linux 2.6.33.

Para las llamadas capget(), se pueden sondear las capacidades de cualquier proceso especificando su ID de proceso con el valor del campo hdrp->pid.

Para más detalles sobre los datos, consulte capabilities(7).

Con soporte de capacidades VFS

Las capacidades VFS emplean un atributo extendido de archivo (véase xattr(7)) para permitir que las capacidades se adjunten a ejecutables. Este modelo de privilegios hace obsoleta la compatibilidad del kernel para que un proceso establezca de forma asíncrona las capacidades de otro. Es decir, en kernels que tienen soporte para capacidades VFS, al llamar a capset(), los únicos valores permitidos para hdrp->pid son 0 o, equivalentemente, el valor devuelto por gettid(2).

Sin soporte de capacidades VFS

En kernels más antiguos que no proporcionan soporte de capacidades VFS, capset() puede, si el llamante tiene la capacidad CAP_SETPCAP, ser utilizado para cambiar no solo las capacidades del propio llamante, sino también las capacidades de otros hilos. La llamada opera sobre las capacidades del hilo especificado por el campo pid de hdrp cuando este es distinto de cero, o sobre las capacidades del hilo llamante si pid es 0. Si pid se refiere a un proceso monohilo, entonces pid puede especificarse como un ID de proceso tradicional; operar sobre un hilo de un proceso multihilo requiere un ID de hilo del tipo devuelto por gettid(2). Para capset(), pid también puede ser: -1, lo que significa realizar el cambio en todos los hilos excepto el llamante y init(1); o un valor menor que -1, en cuyo caso el cambio se aplica a todos los miembros del grupo de procesos cuyo ID es -pid.

VALOR DE RETORNO

En caso de éxito, se devuelve cero. En caso de error, se devuelve -1 y se establece errno para indicar el error.

Las llamadas fallan con el error EINVAL, y establecen el campo version de hdrp al valor preferido del kernel de _LINUX_CAPABILITY_VERSION_? cuando se especifica un valor de version no soportado. De esta manera, se puede sondear cuál es la revisión de capacidades preferida actual.

ERRORES

EFAULT
Mala dirección de memoria. hdrp no debe ser NULL. datap puede ser NULL solo cuando el usuario intenta determinar el formato preferido de la versión de capacidades soportado por el kernel.
EINVAL
Uno de los argumentos era inválido.
EPERM
Se intentó añadir una capacidad al conjunto permitido, o establecer una capacidad en el conjunto efectivo que no está en el conjunto permitido.
EPERM
Se intentó añadir una capacidad al conjunto heredable, y o bien:
•
esa capacidad no estaba en el conjunto límite del llamante; o
•
la capacidad no estaba en el conjunto permitido del llamante y el llamante carecía de la capacidad CAP_SETPCAP en su conjunto efectivo.
EPERM
El llamante intentó usar capset() para modificar las capacidades de un hilo distinto de sí mismo, pero carecía de privilegios suficientes. Para kernels que soportan capacidades VFS, esto nunca está permitido. Para kernels que carecen de soporte VFS, se requiere la capacidad CAP_SETPCAP. (Un error en kernels anteriores a Linux 2.6.11 significó que este error también podía ocurrir si un hilo sin esta capacidad intentaba cambiar sus propias capacidades especificando el campo pid como un valor distinto de cero (es decir, el valor devuelto por getpid(2)) en lugar de 0.)
ESRCH
No existe tal hilo.

ESTANDARES

Linux.
