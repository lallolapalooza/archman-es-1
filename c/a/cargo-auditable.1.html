DESCRIPCIÓ

N

Conoce las versiones exactas de los crates utilizadas para compilar tu ejecutable de Rust. Audita binarios en busca de errores conocidos o vulnerabilidades de seguridad en producción, a gran escala, sin mantenimiento de

registros.

Esto funciona incrustando datos sobre el árbol de dependencias en formato JSON en una sección de enlazador dedicada del ejecutable

compilado.

Linux, Windows y Mac OS son oficialmente soportados. Todos los demás objetivos ELF deberían funcionar, pero no se prueban en CI. WASM actualmente no está soportado, pero los parches son

bienvenidos.

El objetivo final es conseguir que el propio Cargo codifique esta información en los binarios. Existe un RFC para una implementación dentro de Cargo, para la cual este proyecto allana el camino: https://github.com/rust-lang/rfcs/pull/28

PREGUNTAS

FRECUENTES

¿Esto no infla mi

binario?

En una palabra, no. La lista de dependencias incrustada usa menos de 4kB incluso en árboles de dependencias grandes con más de 400 entradas. Esto normalmente se traduce en entre 1/1000 y 1/10,000 del tamaño del

binario.

¿Puedo hacer que cargo siempre compile con cargo

auditable?

¡Sí! Por ejemplo, en Linux/macOS/etc añade esto a tu .

bashrc:

alias cargo="cargo

auditable"

Si estás usando un shell diferente a bash, o si usar un alias no es una opción, consulta https://github.com/rust-secure-code/cargo-auditable/bl

ob/HEAD/REPLACING_CARGO.md.

¿Hay alguna herramienta para consumir estos

datos?

Informe de vulnerabilidade

s


cargo audit v0.17.3+ puede detectar estos datos en binarios y reportar vulnerabilidades. Consulta aquí para más detalles.
trivy v0.31.0+ detecta estos datos en binarios y reporta vulnerabilidades. Consulta las notas de la versión v0.31.0 para un ejemplo de principio a

fin.

Recuperación de la lista de

dependencias


syft v0.53.0+ tiene soporte experimental para detectar estos datos en binarios. Cuando se usa en imágenes o directorios, el soporte de auditoría de Rust debe habilitarse añadiendo la opción CLI --catalogers all, por ejemplo syft --catalogers all <imagen de contenedor que contiene un binario auditable de Rust>.
rust-auditable-info recupera la lista de dependencias de un binario y la imprime en

JSON.

También es interoperable con herramientas existentes que consumen Cargo.lock mediante el convertidor JSON-a-TOML. Sin embargo, recomendamos soportar el formato de forma nativa; el formato está diseñado para ser muy fácil de analizar, incluso si tu lenguaje aún no tiene una biblioteca para

eso.

¿Puedo leer estos datos usando una herramienta escrita en un lenguaje

diferente?

Sí. El formato de datos está diseñado para la interoperabilidad con implementaciones alternativas. De hecho, analizarlo solo toma 5 líneas de Python. Consulta https://github.com/rust-secure-code/cargo-auditable/blob/HEAD/PARSING.md para documentación sobre el análisis de los

datos.

¿Cuál es exactamente el formato de

datos?

El formato de datos está descrito por el esquema JSON https://github.com/rust-secure-code/cargo-auditable/blob/HEAD/cargo-auditable.schema.json. El JSON está comprimido con Zlib y colocado en una sección de enlazador llamada .dep-v0. Puedes encontrar más información sobre cómo analizarlo

aquí.

¿Qué pasa con las plataformas

embebidas?

Las plataformas embebidas donde no puedes permitirte desperdiciar un byte no deberían añadir nada al ejecutable. En su lugar, deberían registrar el hash de cada ejecutable en una base de datos y asociar el hash con su Cargo.lock, versión del compilador, versión de LLVM, fecha de compilación, etc. Esto haría un excelente envoltorio o plugin de Cargo. Dado que eso se puede hacer en un script de shell de 5 líneas, la escritura de esa herramienta se deja como ejercicio para el

lector.

¿Esto afecta a las compilaciones

reproducibles?

El formato de datos está diseñado específicamente para no interrumpir las compilaciones reproducibles. No contiene marcas de tiempo, y el JSON generado está ordenado para asegurar que sea idéntico entre compilaciones. Si acaso, esto ayuda con las compilaciones reproducibles, ya que ahora conoces todas las versiones para un binario

dado.

¿Esto revela alguna información

sensible?

No. Todas las URLs y rutas de archivo están censadas, pero los nombres y versiones de los crates se registran tal cual. Actualmente, los mensajes de pánico ya revelan toda esta información y más. Además, es probable que estés legalmente obligado a revelar el uso de crates de código abierto específicos de todos modos, ya que MIT y muchas otras licencias lo

requieren.

¿Qué pasa con registrar la versión del

compilador?

El propio compilador empezará a incrustarla

pronto.

En versiones antiguas ya está ahí en la información de depuración. En Unix puedes ejecutar strings tu_ejecutable | grep 'rustc version' para

verla.

¿Qué pasa con llevar un registro de las versiones de bibliotecas C enlazadas

estáticamente?

Buena pregunta. No creo que estén expuestas de ninguna manera razonable en este momento. Sería una gran adición, pero no es necesaria para el lanzamiento inicial. Podemos añadirla más tarde de una manera compatible hacia atrás. Adoptar la convención de crates -src haría que ocurriera naturalmente, y también tendrá otros beneficios, así que probablemente sea la mejor

ruta.

¿Qué está bloqueando la incorporación de esto en

Cargo?

El propio Cargo está actualmente en una congelación de

características
