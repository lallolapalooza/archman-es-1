DESCRIPCIÓ

N

ci almacena nuevas revisiones en archivos RCS. Cada nombre de archivo que coincida con un sufijo RCS se considera un archivo RCS. Se asume que todos los demás son archivos de trabajo que contienen nuevas revisiones. ci deposita el contenido de cada archivo de trabajo en el archivo RCS correspondiente. Si solo se proporciona un archivo de trabajo, ci intenta encontrar el archivo RCS correspondiente en un subdirectorio RCS y luego en el directorio del archivo de trabajo. Para más detalles, ver NOMBRES DE ARCHIVO más

abajo.

Para que ci funcione, el inicio de sesión del usuario debe estar en la lista de acceso, a menos que la lista de acceso esté vacía o el usuario sea el superusuario o el propietario del archivo. Para añadir una nueva revisión a una rama existente, la revisión punta de esa rama debe estar bloqueada por el usuario. De lo contrario, solo se puede crear una nueva rama. Esta restricción no se aplica al propietario del archivo si se utiliza bloqueo no estricto (ver rcs(1)). Un bloqueo realizado por otra persona se puede romper con el comando

rcs.

A menos que se proporcione la opción -f, ci comprueba si la revisión a depositar difiere de la anterior. Si no lo está, en lugar de crear una nueva revisión ci vuelve a la anterior. Para volver, el ci normal elimina el archivo de trabajo y cualquier bloqueo; ci -l conserva y ci -u elimina cualquier bloqueo, y luego ambos generan un nuevo archivo de trabajo como si se hubiera aplicado co -l o co -u a la revisión anterior. Al volver, cualquier opción -n y -s se aplica a la revisión

anterior.

Por cada revisión depositada, ci solicita un mensaje de registro. El mensaje de registro debe resumir el cambio y debe terminar con fin de archivo o con una línea que contenga . por sí sola. Si se registran varios archivos, ci pregunta si reutilizar el mensaje de registro anterior. Si la entrada estándar no es un terminal, ci omite el aviso y usa el mismo mensaje de registro para todos los archivos. Ver también -m

.

Si el archivo RCS no existe, ci lo crea y deposita el contenido del archivo de trabajo como la revisión inicial (número por defecto: 1.1). La lista de acceso se inicializa vacía. En lugar del mensaje de registro, ci solicita texto descriptivo (ver -t más abajo)

.

El número rev de la revisión depositada se puede dar con cualquiera de las opciones -f, -i, -I, -j, -k, -l, -M, -q, -r, o -u. rev puede ser simbólico, numérico o mixto. Los nombres simbólicos en rev deben estar ya definidos; ver las opciones -n y -N para asignar nombres durante el registro. Si rev es $, ci determina el número de revisión a partir de los valores de palabra clave en el archivo de

trabajo.

Si rev comienza con un punto, se le antepone la rama predeterminada (normalmente el tronco). Si rev es un número de rama seguido de un punto, se usa la última revisión en esa

rama.

Si rev es un número de revisión, debe ser mayor que la última en la rama a la que rev pertenece, o debe iniciar una nueva

rama.

Si rev es una rama en lugar de un número de revisión, la nueva revisión se añade a esa rama. El número de nivel se obtiene incrementando el número de revisión punta de esa rama. Si rev indica una rama inexistente, esa rama se crea con la revisión inicial numerada rev.1.

Si rev se omite, ci intenta derivar el nuevo número de revisión a partir del último bloqueo del usuario. Si el usuario ha bloqueado la revisión punta de una rama, la nueva revisión se añade a esa rama. El nuevo número de revisión se obtiene incrementando el número de revisión punta. Si el usuario bloqueó una revisión que no es punta, se inicia una nueva rama en esa revisión incrementando el número de rama más alto en esa revisión. Los números de rama y nivel iniciales predeterminados son 1

.

Si rev se omite y el usuario no tiene bloqueo, pero es propietario del archivo y el bloqueo no está configurado en estricto, entonces la revisión se añade a la rama predeterminada (normalmente el tronco; ver la opción -b de rcs(1))

.

Excepción: en el tronco, las

revisiones se pueden añadir
al final, pero no insertarse.

NAME

ci - check in revised files

SYNOPSIS

ci [-lnvx] [-crev] [-ddate] [-ffile] [-I] [-mrev] [-Nname] [-nname] [-rrev] [-sstate] [-tfile | -t-string] [-T] [-wlogin] [-xsuffixes] [-zzone] [file...

DESCRIPTION

The ci utility checks in revised files. It creates a new revision of an RCS file from a working file. If the RCS file does not exist, ci creates it. Otherwise, it checks in a new revision, replacing the working file with the previous revision. If the working file is not writable, ci makes it writable.

The following options are available:

-crev
Specify that the new revision is a branch, numbered rev. The parent revision is the latest revision on the branch that is not pruned.
-ddate
Use the given date instead of the current date for the new revision. The date should be in one of the formats accepted by co(1). The default date is the current date.
-ffile
Same as -t, except that the description text is taken from the given file, and the old descriptive text is kept. This option is ignored if the RCS file does not exist.
-I
Be interactive. This option forces ci to prompt the user for information, even if standard input is not a terminal.
-krev
Specify the revision rev to be checked in. If rev is a number, the revision is created as a branch revision. If rev is a symbolic name, it is assigned to the new revision. If rev is the empty string, it means that the next revision is derived from the latest revision on the same branch.
-l
Lock the checked-in revision. The default is to unlock it.
-mrev
Use the given revision name rev instead of the default one. The default revision name is the latest revision on the same branch.
-rrev
Check in the specified revision rev. If rev is a number, the revision is created as a branch revision. If rev is a symbolic name, it is assigned to the new revision. If rev is the empty string, it means that the next revision is derived from the latest revision on the same branch. This option is ignored if the RCS file does not exist.
-v
Print the RCS file name and the revision number of the checked-in revision.
comments
Comments are ignored by programs like GNU Emacs's vc package. Also, log messages that start with {clumpname} (followed by white space) are meant to be clumped together if possible, even if they are associated with different files; the {clumpname} label is used only for clumping, and is not considered to be part of the log message itself.
-nname
assigns the symbolic name name to the number of the checked-in revision. ci prints an error message if name is already assigned to another number.
-Nname
same as -n, except that it overrides a previous assignment of name.
-sstate
sets the state of the checked-in revision to the identifier state. The default state is Exp.
-tfile
writes descriptive text from the contents of the named file into the RCS file, deleting the existing text. The file cannot begin with -.
-t-string
Write descriptive text from the string into the RCS file, deleting the existing text.

The -t option, in both its forms, has effect only during an initial checkin; it is silently ignored otherwise.

During the initial checkin, if -t is not given, ci obtains the text from standard input, terminated by end-of-file or by a line containing . by itself. The user is prompted for the text if interaction is possible; see -I.

For backward compatibility with older versions of RCS, a bare -t option is ignored.

-T
Set the RCS file's modification time to the new revision's time if the former precedes the latter and there is a new revision; preserve the RCS file's modification time otherwise. If you have locked a revision, ci usually updates the RCS file's modification time to the current time, because the lock is stored in the RCS file and removing the lock requires changing the RCS file. This can create an RCS file newer than the working file in one of two ways: first, ci -M can create a working file with a date before the current time; second, when reverting to the previous revision the RCS file can change while the working file remains unchanged. These two cases can cause excessive recompilation caused by a make(1) dependency of the working file on the RCS file. The -T option inhibits this recompilation by lying about the RCS file's date. Use this option with care; it can suppress recompilation even when a checkin of one working file should affect another working file associated with the same RCS file. For example, suppose the RCS file's time is 01:00, the (changed) working file's time is 02:00, some other copy of the working file has a time of 03:00, and the current time is 04:00. Then ci -d -T sets the RCS file's time to 02:00 instead of the usual 04:00; this causes make(1) to think (incorrectly) that the other copy is newer than the RCS file.
-wlogin
uses login for the author field of the deposited revision. Useful for lying about the author, and for -k if no author is available.
-V
Print RCS's version number.
-Vn
Emulate RCS version n. See co(1) for details.
-xsuffixes
specifies the suffixes for RCS files. A nonempty suffix matches any file name ending in the suffix. An empty suffix matches any file name of the form RCS/frag or frag1/RCS/frag2. The -x option can specify a list of suffixes separated by /. For example, -x,v/ specifies two suffixes: ,v and the empty suffix. If two or more suffixes are specified, they are tried in order when looking for an RCS file; the first one that works is used for that file. If no RCS file is found but an RCS file can be created, the suffixes are tried in order to determine the new RCS file's name. The default for suffixes is installation-dependent; normally it is ,v/ for hosts like Unix that permit commas in file names, and is empty (i.e. just the empty suffix) for other hosts.
-zzone
specifies the date output format in keyword substitution, and specifies the default time zone for date in the -ddate option. The zone should be empty, a numeric UTC offset, or the special string LT for local time. The default is an empty zone, which uses the traditional RCS format of UTC without any time zone indication and with slashes separating the parts of the date; otherwise, times are output in ISO 8601 format with time zone indication. For example, if local time is January 11, 1990, 8pm Pacific Standard Time, eight hours west of UTC, then the time is output as follows:
option	time output
-z	1990/01/12 04:00:00	(default)
-zLT	1990-01-11 20:00:00-08
-z+05:30	1990-01-12 09:30:00+05:30

The -z option does not affect dates stored in RCS files, which are always UTC.

FILE NAMING

Pairs of RCS files and working files can be specified in three ways (see also the example section).

1) Both the RCS file and the working file are given. The RCS file name is of the form frag1/workfileX and the working file name is of the form frag2/workfile where frag1/ and frag2/ are (possibly different or empty) file names, workfile is a file name, and X is an RCS suffix. If X is empty, frag1/ must start with RCS/ or must contain /RCS/.

2) Only the RCS file is given. Then the working file is created in the current directory and its name is derived from the RCS file name by removing frag1/ and the suffix X.

3) Only the working file is given. Then ci considers each RCS suffix X in turn, looking for an RCS file of the form frag2/RCS/workfileX or (if the former is not found and X is nonempty) frag2/workfileX.

If the RCS file is specified without a file name in 1) and 2), ci looks for the RCS file first in the directory ./RCS and then in the current directory.

ci reports an error if an attempt to open an RCS file fails for an unusual reason, even if the RCS file's name is just one of several possibilities. For example, to suppress use of RCS commands in a directory d, create a regular file named d/RCS so that casual attempts to use RCS commands in d fail because d/RCS is not a directory.

EXAMPLES

Suppose ,v is an RCS suffix and the current directory contains a subdirectory RCS with an RCS file io.c,v. Then each of the following commands check in a copy of io.c into RCS/io.c,v as the latest revision, removing io.c.

ci  io.c;    ci  RCS/io.c,v;   ci  io.c,v;
ci  io.c  RCS/io.c,v;    ci  io.c  io.c,v;
ci  RCS/io.c,v  io.c;    ci  io.c,v  io.c;

Suppose instead that the empty suffix is an RCS suffix and the current directory contains a subdirectory RCS with an RCS file io.c. The each of the following commands checks in a new revision.

ci  io.c;    ci  RCS/io.c;
ci  io.c  RCS/io.c;
ci  RCS/io.c  io.c;

FILE MODES

An RCS file created by ci inherits the read and execute permissions from the working file. If the RCS file exists already, ci preserves its read and execute permissions. ci always turns off all write permissions of RCS files.

FILES

Temporary files are created in the directory containing the working file, and also in the temporary directory (see TMPDIR under ENVIRONMENT). A semaphore file or files are created in the directory containing the RCS file. With a nonempty suffix, the semaphore names begin with the first character of the suffix; therefore, do not specify an suffix whose first character could be that of a working file name. With an empty suffix, the semaphore names end with _ so working file names should not end in _.

ci never changes an RCS file or working file. Normally, ci unlinks the file and creates a new one; but instead of breaking a chain of one or more symbolic links to an RCS file, it unlinks the destination file instead. Therefore, ci breaks any hard or symbolic links to any working file it changes; and hard links to RCS files are ineffective, but symbolic links to RCS files are preserved.

The effective user must be able to search and write the directory containing the RCS file. Normally, the real user must be able to read the RCS and working files and to search and write the directory containing the working file; however, some older hosts cannot easily switch between real and effective users, so on these hosts the effective user is used for all accesses. The effective user is the same as the real user unless your copies of ci and co have setuid privileges. As described in the next section, these privileges yield extra security if the effective user owns all RCS files and directories, and if only the effective user can write RCS directories.

Users can control access to RCS files by setting the permissions of the directory containing the files; only users with write access to the directory can use RCS commands to change its RCS files. For example, in hosts that allow a user to belong to several groups, one can make a group's RCS directories writable to that group only. This approach suffices for informal projects, but it means that any group member can arbitrarily change the group's RCS files, and can even remove them entirely. USO DE SETUID

Para evitar que nadie, excepto su administrador de RCS, elimine revisiones, un conjunto de usuarios puede emplear privilegios de setuid de la siguiente manera.

  • Verifique que el host admita el uso de setuid de RCS. Consulte a un experto de confianza si tiene alguna duda. Es mejor si la llamada del sistema seteuid funciona como se describe en Posix 1003.1a Draft 5, ya que RCS puede alternar fácilmente entre usuarios reales y efectivos, incluso si el usuario real es root. De lo contrario, lo segundo mejor es si la llamada del sistema setuid admite el setuid guardado (el comportamiento de {_POSIX_SAVED_IDS} de Posix 1003.1-1990); esto falla solo si el usuario real o efectivo es root. Si RCS detecta algún fallo en setuid, se detiene inmediatamente.
  • Elija un usuario A para que sirva como administrador de RCS para el conjunto de usuarios. Solo A puede invocar el comando rcs en los archivos RCS de los usuarios. A no debe ser root ni ningún otro usuario con poderes especiales. Conjuntos de usuarios mutuamente desconfiados deben usar administradores diferentes.
  • Elija un nombre de archivo B para que sea un directorio de archivos que los usuarios ejecutarán.
  • Haga que A configure B para que contenga copias de ci y co que sean setuid para A copiando los comandos de su directorio de instalación estándar D de la siguiente manera:
mkdir  B
cp  D/c[io]  B
chmod  go-w,u+s  B/c[io]
•
Haga que cada usuario anteponga B a su ruta de búsqueda de comandos de la siguiente manera:
PATH=B:$PATH;  export  PATH  # shell ordinario
set  path=(B  $path)  # shell C
•
Haga que A cree cada directorio RCS R con acceso de escritura solo para A de la siguiente manera:
mkdir  R
chmod  go-w  R
•
Si desea permitir que solo ciertos usuarios lean los archivos RCS, coloque a los usuarios en un grupo G y haga que A proteja aún más el directorio RCS de la siguiente manera:
chgrp  G  R
chmod  g-w,o-rwx  R
  • Haga que A copie los archivos RCS antiguos (si los hay) en R, para asegurarse de que A sea el propietario de ellos.
  • La lista de acceso de un archivo RCS limita quién puede registrar y bloquear revisiones. La lista de acceso predeterminada está vacía, lo que otorga acceso de registro a cualquiera que pueda leer el archivo RCS. Si desea limitar el acceso de registro, haga que A invoque rcs -a en el archivo; consulte rcs(1). En particular, rcs -e -aA limita el acceso solo a A.
  • Haga que A inicialice los nuevos archivos RCS con rcs -i antes del registro inicial, agregando la opción -a si desea limitar el acceso de registro.
  • Conceda privilegios de setuid solo a ci, co y rcsclean; no se los conceda a rcs ni a ningún otro comando.
  • No utilice otros comandos setuid para invocar comandos RCS; ¡setuid es más complicado de lo que piensas!

ENTORNO

RCSINIT
Opciones antepuestas a la lista de argumentos, separadas por espacios. Una barra invertida escapa los espacios dentro de una opción. Las opciones RCSINIT se anteponen a las listas de argumentos de la mayoría de los comandos RCS. Las opciones útiles de RCSINIT incluyen -q, -V, -x y -z.
RCS_MEM_LIMIT
Normalmente, para mayor velocidad, los comandos mapean en memoria o copian en memoria el archivo RCS si su tamaño es inferior al límite de memoria, que actualmente por defecto es "ilimitado". De lo contrario (o si las formas rápidas intentadas inicialmente fallan), los comandos recurren a rutinas de E/S estándar. Puede ajustar el límite de memoria configurando RCS_MEM_LIMIT a un valor numérico lim (medido en kilobytes). Un valor vacío se ignora silenciosamente. Como efecto secundario, especificar RCS_MEM_LIMIT inhibe la recursión a rutinas más lentas.
TMPDIR
Nombre del directorio temporal. Si no está configurado, se inspeccionan las variables de entorno TMP y TEMP y se toma el primer valor encontrado; si ninguna de ellas está configurada, se utiliza un valor predeterminado dependiente del host, normalmente /tmp.

DIAGNÓSTICOS

Para cada revisión, ci imprime el archivo RCS, el archivo de trabajo y el número de la revisión depositada y la anterior. El estado de salida es cero si y solo si todas las operaciones fueron exitosas.
