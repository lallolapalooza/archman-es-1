ORTE DE TIPOS Nota importante: Incluso

los

programas

depurados pueden contener errores de tipo que permanecen sin ser detectados por otros compiladores. Cuando se compilan con la verificación de tipos suprimida usando el compilador CMU Common Lisp, estos errores de tipo pueden causar que dichos programas depurados mueran de forma extraña. Si la verificación de tipos no está suprimida, estos programas morirán con un error de tipo

explícito.

La forma más visible en que Python difiere de compiladores de Common Lisp anteriores es que tiene un mayor conocimiento sobre tipos y un enfoque diferente para la verificación de tipos. En particular, Python implementa una verificación de tipos que es "ansiosa" y "precisa":

--
Ans
iosa
en el sentido de que la verificación de tipos se realiza inmediatamente siempre que hay una declaración, en lugar de retrasarse hasta que el valor se usa realmente. Por ejemplo: (let ((x ...)) 
    (declare (fixnum x))
      ...)

    Aquí, el tipo del valor
inicial de X debe ser un FIXNUM o se señalará un error. -- Precisa en el sentido de que se verifica el
tipo
ex
acto
especificado. Por ejemplo, si una variable se declara de tipo (integer
3 7), entonces el valor debe ser siempre un entero entre 3 y 7. Dado qu
e Python realiza más verificación de tipos, los programas que funcionan

bien cuando se compilan con otros compiladores pueden obtener errores de tipo cuando se compilan con Python. Es importante inicialmente compilar los programas con la política predeterminada (segura), y luego probar esta versión. Si un programa con una declaración errónea se compila con la verificación de tipos suprimida (debido a que la calidad de optimización SAFETY se reduce), entonces el error de tipo puede causar errores oscuros o bucles infinitos. Vea la sección "Cómo hacer que los programas existentes se ejecuten" (6.6) en el capítulo del compilador del manual del usuario. CMU CL se adhiere a la limpieza del

tipo

de función de X3J13, lo que significa que las listas de argumentos entre

EL

INTÉRPRETE

En lo que respecta a la semántica de Common Lisp, no hay intérprete; esto es efectivamente una implementación de solo compilación. Las formas escritas en el bucle de leer-evaluar-imprimir o pasadas a EVAL son efectivamente compiladas antes de ser ejecutadas. En la implementación, hay un intérprete, pero opera sobre la representación interna producida por el front-end del

compilador.

No se recomienda que los programas se depuren ejecutando el programa completo interpretado, ya que Python y el depurador eliminan las razones principales para depurar usando el

intérprete:
-
-
El código compilado realiza mucho más comprobación de errores que el código
interpretado.
-
-
Es tan fácil depurar
código compilado como
código interpretado.

Tenga en cuenta que el depurador actualmente no soporta el paso a paso. Además, el pre-procesamiento del intérprete congela las definiciones de

macro en efecto en el momento en que se define una función interpretada. Hasta que implementemos el reprocesamiento automático cuando se
redefinen las macros, es necesario re-evaluar la definición de una función interpretada para que se noten las nuevas definiciones de macro.

ACERCA DEL PROYECTO CMU COMMON

LISP

Organizativamente, CMU Common Lisp era una pequeña parte, mayormente autónoma, dentro del proyecto del sistema operativo Mach. El proyecto CMU CL era más un esfuerzo de desarrollo de herramientas que un proyecto de investigación. El proyecto comenzó como Spice Lisp, que proporcionaba una implementación moderna de Lisp para uso en la comunidad de CMU. CMU CL ha estado en desarrollo continuo desde principios de la década de 1980 (concurrente con el esfuerzo de estandarización de Common Lisp.) La mayoría de los implementadores de CMU Common Lisp ahora trabajan en el entorno Gwydion para Dylan (ver http://legend.gwydion.cs.cmu.edu

:8001/gwydion/.)

CMU CL fue financiado por DARPA bajo el contrato de CMU "Investigación en Computación Paralela". En lugar de hacer investigación pura sobre lenguajes de programación y entornos, el énfasis estaba en desarrollar herramientas prácticas de programación. A veces esto requería nueva tecnología, pero gran parte del trabajo fue en crear un entorno de Common Lisp que incorpora características de vanguardia de sistemas existentes (tanto Lisp como no Lisp.

)

Debido a que las fuentes están disponibles libremente, CMU Common Lisp h

a sido portado a hardware experimental, y usado como base para inves
tigación en la construcción de lenguajes de programación y entornos.
