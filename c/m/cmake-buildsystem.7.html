Requisitos de Uso del Objetivo

Los requisitos de uso de un objetivo son configuraciones que se propagan a los consumidores, que enlazan al objetivo mediante target_link_libraries() <#command:target_link_libraries>, para compilar y enlazar correctamente con él. Son representados por propiedades transitivas de compilación y enlace.

Nótese que los requisitos de uso no están diseñados como una forma de hacer que los consumidores usen particularmente COMPILE_OPTIONS <#prop_tgt:COMPILE_OPTIONS>, COMPILE_DEFINITIONS <#prop_tgt:COMPILE_DEFINITIONS>, etc. solo por conveniencia. El contenido de las propiedades debe ser requisitos, no meramente recomendaciones.

Vea la sección Creando Paquetes Reubicables <#creating-relocatable-packages> del cmake-packages(7) <#manual:cmake-packages(7)> manual para una discusión del cuidado adicional que debe tomarse al especificar requisitos de uso mientras se crean paquetes para redistribución.

Los requisitos de uso de un objetivo pueden propagarse transitivamente a los dependientes. El target_link_libraries() <#command:target_link_libraries> comando tiene PRIVATE, INTERFACE y PUBLIC palabras clave para controlar la propagación.

add_library(archive archive.cpp)
target_compile_definitions(archive INTERFACE USING_ARCHIVE_LIB)
add_library(serialization serialization.cpp)
target_compile_definitions(serialization INTERFACE USING_SERIALIZATION_LIB)
add_library(archiveExtras extras.cpp)
target_link_libraries(archiveExtras PUBLIC archive)
target_link_libraries(archiveExtras PRIVATE serialization)
# archiveExtras se compila con -DUSING_ARCHIVE_LIB
# y -DUSING_SERIALIZATION_LIB
add_executable(consumer consumer.cpp)
# consumer se compila con -DUSING_ARCHIVE_LIB
target_link_libraries(consumer archiveExtras)

Debido a que archive es una dependencia PUBLIC de archiveExtras, sus requisitos de uso son propagados a consumer también.

Debido a que serialization es una dependencia PRIVATE de archiveExtras, sus requisitos de uso no son propagados a consumer.

Generalmente, una dependencia debe ser especificada en un uso de target_link_libraries() <#command:target_link_libraries> con la palabra clave PRIVATE si es usada solo por la implementación de una biblioteca, y no en los archivos de cabecera. Si una dependencia es adicionalmente usada en los archivos de cabecera de una biblioteca (ej. para herencia de clases), entonces debe ser especificada como una dependencia PUBLIC . Una dependencia que no es usada por la implementación de una biblioteca, sino solo por sus cabeceras, debe ser especificada como una dependencia INTERFACE . El target_link_libraries() <#command:target_link_libraries> comando puede ser invocado con múltiples usos de cada palabra clave:

target_link_libraries(archiveExtras
  PUBLIC archive
  PRIVATE serialization
)

Los requisitos de uso son propagados leyendo las INTERFACE_ variantes de las propiedades del objetivo desde dependencias y añadiendo los valores a las variantes noINTERFACE_ del operando. Por ejemplo, la INTERFACE_INCLUDE_DIRECTORIES <#prop_tgt:INTERFACE_INCLUDE_DIRECTORIES> de las dependencias es leída y añadida a la INCLUDE_DIRECTORIES <#prop_tgt:INCLUDE_DIRECTORIES> del operando. En casos donde el orden es relevante y se mantiene, y el orden resultante de las llamadas target_link_libraries() <#command:target_link_libraries> no permite la compilación correcta, el uso de un comando apropiado para establecer la propiedad directamente puede actualizar el orden.

Por ejemplo, si las bibliotecas enlazadas para un objetivo deben ser especificadas en el orden lib1 lib2 lib3 , pero los directorios de inclusión deben ser especificados en el orden lib3 lib1 lib2:

target_link_libraries(myExe lib1 lib2 lib3)
target_include_directories(myExe
  PRIVATE $<TARGET_PROPERTY:lib3,INTERFACE_INCLUDE_DIRECTORIES>)

Nótese que debe tomarse cuidado al especificar requisitos de uso para objetivos que serán exportados para instalación usando el install(EXPORT) <#export> comando. Vea Creando Paquetes <#creating-packages> para más información.

Propiedades de interfaz compatibles

Se requiere que algunas propiedades de objetivo sean compatibles entre un objetivo y la interfaz de cada dependencia. Por ejemplo, la propiedad de objetivo POSITION_INDEPENDENT_CODE <#prop_tgt:POSITION_INDEPENDENT_CODE> puede especificar un valor booleano que indica si un objetivo debe compilarse como código independiente de posición, lo cual tiene consecuencias específicas de la plataforma. Un objetivo también puede especificar el requisito de uso INTERFACE_POSITION_INDEPENDENT_CODE <#prop_tgt:INTERFACE_POSITION_INDEPENDENT_CODE> para comunicar que los consumidores deben compilarse como código independiente de posición.

add_executable(exe1 exe1.cpp)
set_property(TARGET exe1 PROPERTY POSITION_INDEPENDENT_CODE ON)
add_library(lib1 SHARED lib1.cpp)
set_property(TARGET lib1 PROPERTY INTERFACE_POSITION_INDEPENDENT_CODE ON)
add_executable(exe2 exe2.cpp)
target_link_libraries(exe2 lib1)

Aquí, tanto exe1 como exe2 se compilarán como código independiente de posición. lib1 también se compilará como código independiente de posición porque esa es la configuración predeterminada para las bibliotecas SHARED . Si las dependencias tienen requisitos conflictivos e incompatibles, cmake(1) <#manual:cmake(1)> emite un diagnóstico:

add_library(lib1 SHARED lib1.cpp)
set_property(TARGET lib1 PROPERTY INTERFACE_POSITION_INDEPENDENT_CODE ON)
add_library(lib2 SHARED lib2.cpp)
set_property(TARGET lib2 PROPERTY INTERFACE_POSITION_INDEPENDENT_CODE OFF)
add_executable(exe1 exe1.cpp)
target_link_libraries(exe1 lib1)
set_property(TARGET exe1 PROPERTY POSITION_INDEPENDENT_CODE OFF)
add_executable(exe2 exe2.cpp)
target_link_libraries(exe2 lib1 lib2)

El requisito de lib1 INTERFACE_POSITION_INDEPENDENT_CODE no es "compatible" con la propiedad POSITION_INDEPENDENT_CODE <#prop_tgt:POSITION_INDEPENDENT_CODE> del objetivo exe1 . La biblioteca requiere que los consumidores se compilen como código independiente de posición, mientras que el ejecutable especifica no compilar como código independiente de posición, por lo que se emite un diagnóstico.

Los requisitos de lib1 y lib2 no son "compatibles". Uno de ellos requiere que los consumidores se compilen como código independiente de posición, mientras que el otro requiere que los consumidores no se compilen como código independiente de posición. Dado que exe2 enlaza con ambos y están en conflicto, se emite un mensaje de error de CMake:

CMake Error: The INTERFACE_POSITION_INDEPENDENT_CODE property of "lib2" does
not agree with the value of POSITION_INDEPENDENT_CODE already determined
for "exe2".

Para ser "compatible", la propiedad POSITION_INDEPENDENT_CODE <#prop_tgt:POSITION_INDEPENDENT_CODE>, si está establecida, debe ser igual, en sentido booleano, a la propiedad INTERFACE_POSITION_INDEPENDENT_CODE <#prop_tgt:INTERFACE_POSITION_INDEPENDENT_CODE> de todas las dependencias transitivamente especificadas en las que esa propiedad esté establecida.

Esta propiedad de "requisito de interfaz compatible" puede extenderse a otras propiedades especificando la propiedad en el contenido de la propiedad de objetivo COMPATIBLE_INTERFACE_BOOL <#prop_tgt:COMPATIBLE_INTERFACE_BOOL>. Cada propiedad especificada debe ser compatible entre el objetivo consumidor y la propiedad correspondiente con el prefijo INTERFACE_ de cada dependencia:

add_library(lib1Version2 SHARED lib1_v2.cpp)
set_property(TARGET lib1Version2 PROPERTY INTERFACE_CUSTOM_PROP ON)
set_property(TARGET lib1Version2 APPEND PROPERTY
  COMPATIBLE_INTERFACE_BOOL CUSTOM_PROP
)
add_library(lib1Version3 SHARED lib1_v3.cpp)
set_property(TARGET lib1Version3 PROPERTY INTERFACE_CUSTOM_PROP OFF)
add_executable(exe1 exe1.cpp)
target_link_libraries(exe1 lib1Version2) # CUSTOM_PROP será ON
add_executable(exe2 exe2.cpp)
target_link_libraries(exe2 lib1Version2 lib1Version3) # Diagnóstico

Las propiedades que no son booleanas también pueden participar en los cálculos de "interfaz compatible". Las propiedades especificadas en la propiedad COMPATIBLE_INTERFACE_STRING <#prop_tgt:COMPATIBLE_INTERFACE_STRING> deben estar sin especificar o compararse a la misma cadena entre todas las dependencias transitivamente especificadas. Esto puede ser útil para asegurar que múltiples versiones incompatibles de una biblioteca no se enlacen juntas a través de requisitos transitivos de un objetivo:

add_library(lib1Version2 SHARED lib1_v2.cpp)
set_property(TARGET lib1Version2 PROPERTY INTERFACE_LIB_VERSION 2)
set_property(TARGET lib1Version2 APPEND PROPERTY
  COMPATIBLE_INTERFACE_STRING LIB_VERSION
)
add_library(lib1Version3 SHARED lib1_v3.cpp)
set_property(TARGET lib1Version3 PROPERTY INTERFACE_LIB_VERSION 3)
add_executable(exe1 exe1.cpp)
target_link_libraries(exe1 lib1Version2) # LIB_VERSION será "2"

Bibliotecas de enlace y expresiones de generador

Al igual que las especificaciones de compilación, las bibliotecas de enlace <#prop_tgt:LINK_LIBRARIES> pueden especificarse con condiciones de expresiones de generador. Sin embargo, como el consumo de requisitos de uso se basa en la recopilación desde las dependencias enlazadas, existe una limitación adicional: las dependencias de enlace deben formar un "grafo acíclico dirigido". Es decir, si el enlace a un objetivo depende del valor de una propiedad del objetivo, esa propiedad del objetivo no puede depender de las dependencias enlazadas:

add_library(lib1 lib1.cpp)
add_library(lib2 lib2.cpp)
target_link_libraries(lib1 PUBLIC
  $<$<TARGET_PROPERTY:POSITION_INDEPENDENT_CODE>:lib2>
)
add_library(lib3 lib3.cpp)
set_property(TARGET lib3 PROPERTY INTERFACE_POSITION_INDEPENDENT_CODE ON)
add_executable(exe1 exe1.cpp)
target_link_libraries(exe1 lib1 lib3)

Dado que el valor de la propiedad POSITION_INDEPENDENT_CODE <#prop_tgt:POSITION_INDEPENDENT_CODE> del objetivo exe1 depende de las bibliotecas enlazadas (lib3), y la arista de enlace de exe1 está determinada por la misma propiedad POSITION_INDEPENDENT_CODE <#prop_tgt:POSITION_INDEPENDENT_CODE>, el grafo de dependencias anterior contiene un ciclo. cmake(1) <#manual:cmake(1)> emite un mensaje de error.

Artefactos de salida

Los objetivos del sistema de compilación creados por los comandos add_library() <#command:add_library> y add_executable() <#command:add_executable> crean reglas para generar salidas binarias. La ubicación exacta de la salida de los binarios solo puede determinarse en el momento de la generación, ya que puede depender de la configuración de compilación y el lenguaje de enlace de las dependencias enlazadas, etc. TARGET_FILE, TARGET_LINKER_FILE y expresiones relacionadas pueden usarse para acceder al nombre y ubicación de los binarios generados. Estas expresiones no funcionan para las bibliotecas OBJECT , ya que no hay un único archivo generado por tales bibliotecas que sea relevante para las expresiones.

Hay tres tipos de artefactos de salida que pueden ser construidos por los objetivos, detallados en las siguientes secciones. Su clasificación difiere entre plataformas DLL y no-DLL. Todos los sistemas basados en Windows, incluyendo Cygwin, son plataformas DLL.

Artefactos de salida en tiempo de ejecución

Un artefacto de salida en tiempo de ejecución de un objetivo del sistema de compilación puede ser:

  • El archivo ejecutable (por ejemplo, .exe) de un objetivo ejecutable creado por el comando add_executable() <#command:add_executable>.
  • En plataformas DLL: el archivo ejecutable (por ejemplo, .dll) de un objetivo de biblioteca compartida creado por el add_library() <#command:add_library> con la opción SHARED .

Las propiedades del objetivo RUNTIME_OUTPUT_DIRECTORY <#prop_tgt:RUNTIME_OUTPUT_DIRECTORY> y RUNTIME_OUTPUT_NAME <#prop_tgt:RUNTIME_OUTPUT_NAME> pueden usarse para controlar las ubicaciones y nombres de los artefactos de salida en tiempo de ejecución en el árbol de compilación.

Artefactos de salida de biblioteca

Un artefacto de salida de biblioteca de un objetivo del sistema de compilación puede ser:

  • El archivo de módulo cargable (por ejemplo, .dll o .so) de un objetivo de biblioteca de módulo creado por el comando add_library() <#command:add_library> con la opción MODULE .
  • En plataformas no-DLL: el archivo de biblioteca compartida (por ejemplo, .so o .dylib) de un objetivo de biblioteca compartida creado por el add_library() <#command:add_library> con la opción SHARED .

Las propiedades del objetivo LIBRARY_OUTPUT_DIRECTORY <#prop_tgt:LIBRARY_OUTPUT_DIRECTORY> y LIBRARY_OUTPUT_NAME <#prop_tgt:LIBRARY_OUTPUT_NAME> pueden usarse para controlar las ubicaciones y nombres de los artefactos de salida de biblioteca en el árbol de compilación.

Artefactos de salida de archivo

Un artefacto de salida de archivo de un objetivo del sistema de compilación puede ser:

  • El archivo de biblioteca estática (por ejemplo, .lib o .a) de un objetivo de biblioteca estática creado por el add_library() <#command:add_library> con la opción STATIC .
  • En plataformas DLL: el archivo de biblioteca de importación (por ejemplo, .lib) de un objetivo de biblioteca compartida creado por el add_library() <#command:add_library> con la opción SHARED . Este archivo solo está garantizado que exista si la biblioteca exporta al menos un símbolo no administrado.
  • En plataformas DLL: el archivo de biblioteca de importación (por ejemplo, .lib) de un objetivo ejecutable creado por el add_executable() <#command:add_executable> cuando su ENABLE_EXPORTS <#prop_tgt:ENABLE_EXPORTS> propiedad del objetivo está establecida.
  • En AIX: el archivo de importación del enlazador (por ejemplo, .imp) de un objetivo ejecutable creado por el add_executable() <#command:add_executable> comando cuando su ENABLE_EXPORTS <#prop_tgt:ENABLE_EXPORTS> propiedad del objetivo está establecida.
  • En macOS: el archivo de importación del enlazador (por ejemplo, .tbd) de un objetivo de biblioteca compartida creado por el add_library() <#command:add_library> comando con la opción SHARED y cuando su ENABLE_EXPORTS <#prop_tgt:ENABLE_EXPORTS> propiedad del objetivo está establecida.

Las propiedades del objetivo ARCHIVE_OUTPUT_DIRECTORY <#prop_tgt:ARCHIVE_OUTPUT_DIRECTORY> y ARCHIVE_OUTPUT_NAME <#prop_tgt:ARCHIVE_OUTPUT_NAME> pueden usarse para controlar las ubicaciones y nombres de los artefactos de salida de archivo en el árbol de compilación.

Comandos con ámbito de directorio

Los comandos target_include_directories() <#command:target_include_directories>, target_compile_definitions() <#command:target_compile_definitions> y target_compile_options() <#command:target_compile_options> tienen un efecto en un solo objetivo a la vez. Los comandos add_compile_definitions() <#command:add_compile_definitions>, add_compile_options() <#command:add_compile_options> y include_directories() <#command:include_directories> tienen una función similar, pero operan en el ámbito del directorio en lugar del ámbito del objetivo para mayor comodidad.

CONFIGURACIONES DE COMPILACIÓN

Las configuraciones determinan las especificaciones para un cierto tipo de compilación, como Release o Debug. La forma en que esto se especifica depende del tipo de generador <#manual:cmake-generators(7)> que se esté utilizando. Para generadores de configuración única como los generadores de Makefile <#makefile-generators> y Ninja <#generator:Ninja>, la configuración se especifica en el momento de la configuración mediante la variable CMAKE_BUILD_TYPE <#variable:CMAKE_BUILD_TYPE>. Para generadores de configuración múltiple como Visual Studio <#visual-studio-generators>, Xcode <#generator:Xcode>, y Ninja Multi-Config <#generator:Ninja Multi-Config>, la configuración la elige el usuario en el momento de la compilación y CMAKE_BUILD_TYPE <#variable:CMAKE_BUILD_TYPE> se ignora. En el caso de configuración múltiple, el conjunto de configuraciones disponibles se especifica en el momento de la configuración mediante la variable CMAKE_CONFIGURATION_TYPES <#variable:CMAKE_CONFIGURATION_TYPES>, pero la configuración real utilizada no se puede conocer hasta la etapa de compilación. Esta diferencia se malinterpreta a menudo, lo que lleva a código problemático como el siguiente:

# ADVERTENCIA: Esto es incorrecto para generadores de configuración múltiple porque no usan
#          y normalmente ni siquiera establecen CMAKE_BUILD_TYPE
string(TOLOWER ${CMAKE_BUILD_TYPE} build_type)
if (build_type STREQUAL debug)
  target_compile_definitions(exe1 PRIVATE DEBUG_BUILD)
endif()

Deberían usarse expresiones de generador <#manual:cmake-generator-expressions(7)> en su lugar para manejar correctamente la lógica específica de la configuración, independientemente del generador utilizado. Por ejemplo:

# Funciona correctamente tanto para generadores de configuración única como múltiple
target_compile_definitions(exe1 PRIVATE
  $<$<CONFIG:Debug>:DEBUG_BUILD>
)

En presencia de objetivos IMPORTED <#prop_tgt:IMPORTED>, el contenido de MAP_IMPORTED_CONFIG_DEBUG <#prop_tgt:MAP_IMPORTED_CONFIG_<CONFIG>> también se tiene en cuenta por la expresión $<CONFIG:Debug> <#genex:CONFIG> anterior.

Sensibilidad a mayúsculas/minúsculas

CMAKE_BUILD_TYPE <#variable:CMAKE_BUILD_TYPE> y CMAKE_CONFIGURATION_TYPES <#variable:CMAKE_CONFIGURATION_TYPES> son como otras variables en que cualquier comparación de cadenas hecha con sus valores será sensible a mayúsculas/minúsculas. La $<CONFIG> <#genex:CONFIG> expresión de generador también conserva las mayúsculas/minúsculas de la configuración como la estableció el usuario o los valores predeterminados de CMake. Por ejemplo:

# NOTA: No use estos patrones, son solo para fines ilustrativos.
set(CMAKE_BUILD_TYPE Debug)
if(CMAKE_BUILD_TYPE STREQUAL DEBUG)
  # ... nunca llegará aquí, "Debug" != "DEBUG"
endif()
add_custom_target(print_config ALL
  # Imprime "Config is Debug" en este caso de configuración única
  COMMAND ${CMAKE_COMMAND} -E echo "Config is $<CONFIG>"
  VERBATIM
)
set(CMAKE_CONFIGURATION_TYPES Debug Release)
if(DEBUG IN_LIST CMAKE_CONFIGURATION_TYPES)
  # ... nunca llegará aquí, "Debug" != "DEBUG"
endif()

En contraste, CMake trata el tipo de configuración sin distinguir mayúsculas/minúsculas cuando lo usa internamente en lugares que modifican el comportamiento basado en la configuración. Por ejemplo, la $<CONFIG:Debug>b> La expresión de generador <#genex:CONFIG> se evaluará a 1 para una configuración de no solo Debug , sino también DEBUG , debug o incluso DeBuG . Por lo tanto, puede especificar tipos de configuración en CMAKE_BUILD_TYPE <#variable:CMAKE_BUILD_TYPE> y CMAKE_CONFIGURATION_TYPES <#variable:CMAKE_CONFIGURATION_TYPES> con cualquier mezcla de mayúsculas y minúsculas, aunque existen convenciones fuertes (vea la siguiente sección). Si debe probar el valor en comparaciones de cadenas, siempre convierta el valor a mayúsculas o minúsculas primero y ajuste la prueba en consecuencia. Objetivos

Pseudo

Algunos tipos de objetivos no representan salidas del sistema de compilación, sino solo entradas como dependencias externas, alias u otros artefactos no compilados. Los objetivos pseudo no están representados en el sistema de compilación

generado.

Objetivos Importados Un objetivo IMPORTED <#prop_tgt:IMPORTED> representa una dependencia preexistente. Usualmente, tales objetivos son definidos por un paquete aguas arriba y deben tratarse como inmutables. Después de declarar un IMPORTED <#prop_tgt:IMPORTED>, se pueden ajustar sus propiedades de objetivo utilizando los comandos habituales como target_compile_definitions() <#command:target_compile_definitions>, target_include_directories() <#command:target_include_directories>, target_compile_options(

)

<#command:target_compile_options> o target_link_libraries() <#command:target_link_libraries> igual que con cualquier otro objetivo regular. Los objetivos IMPORTED <#prop_tgt:IMPORTED> pueden tener las mismas propiedades de requisitos de uso pobladas como los objetivos binarios, como INTERFACE_INCLUDE_DIRECTORIES <#prop_tgt:INTERFACE_INCLUDE_DIRECTORIES>, INTERFACE_COMPILE_DEFINITIONS <#prop_tgt:INTERFACE_COMPILE_DEFINITIONS>, INTERFACE_COMPILE_OPTIONS <#prop_tgt:INTERFACE_COMPILE_OPTIONS>, INTERFACE_LINK_LIBRARIES <#prop_tgt:INTERFACE_LINK_LIBRARIES>, y INTERFACE_POSITION_INDEPENDENT_CODE <#prop_tgt:INTERFACE_POSITION_INDEPENDENT_CODE>. Comandos como add_custom_command() <#command:add_custom_command> pueden usar transparentemente un objetivo IMPORTED <#prop_tgt:IMPORTED> EXECUTABLE <#prop_tgt:TYPE> como un ejecutable COMMAND . El ámbito de la definición de un objetivo IMPORTED <#prop_tgt:IMPORTED> es el directorio donde fue definido. Puede ser accedido y usado desde subdirectorios, pero no desde directorios padres o directorios hermanos. El ámbito es similar al ámbito de una variable de cmake. También es posible definir un
