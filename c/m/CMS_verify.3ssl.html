CMS_verify(3ssl)

Paquete: openssl

Licencias: Apache-2.0

CMS_VERIFY(3ssl) OpenSSL CMS_VERIFY(3ssl)

NOMBRE

CMS_verify, CMS_SignedData_verify, CMS_get0_signers - verifica una estructura CMS SignedData

SINOPSIS

#include <openssl/cms.h>
int CMS_verify(CMS_ContentInfo *cms, STACK_OF(X509) *certs, X509_STORE *store,
               BIO *detached_data, BIO *out, unsigned int flags);
BIO *CMS_SignedData_verify(CMS_SignedData *sd, BIO *detached_data,
                           STACK_OF(X509) *scerts, X509_STORE *store,
                           STACK_OF(X509) *extra, STACK_OF(X509_CRL) *crls,
                           unsigned int flags,
                           OSSL_LIB_CTX *libctx, const char *propq);
STACK_OF(X509) *CMS_get0_signers(CMS_ContentInfo *cms);

DESCRIPCIÓN

CMS_verify() es muy similar a PKCS7_verify(3). Verifica una estructura CMS SignedData contenida en una estructura de tipo CMS_ContentInfo. cms apunta a la estructura CMS_ContentInfo a verificar. El parámetro opcional certs se refiere a un conjunto de certificados en el que buscar los certificados de firma. También se utiliza como fuente de certificados de CA intermedios no confiables para la construcción de cadenas. cms puede contener certificados de CA no confiables adicionales que pueden usarse para la construcción de cadenas, así como CRLs que pueden usarse para la validación de certificados. store puede ser NULL o apuntar al almacén de certificados confiables a usar para la verificación de cadenas. detached_data se refiere a los datos firmados si el contenido está separado de cms. De lo contrario, detached_data debe ser NULL y los datos firmados deben estar en cms. El contenido se escribe en el BIO out a menos que sea NULL. flags es un conjunto opcional de indicadores, que pueden usarse para modificar la operación.

CMS_SignedData_verify() es como CMS_verify() excepto que opera con la entrada CMS SignedData en el argumento sd , tiene algunos parámetros adicionales descritos a continuación, y en caso de éxito devuelve el contenido verificado como un BIO de memoria. El parámetro opcional extra puede usarse para proporcionar certificados de CA no confiables que pueden ser útiles para la construcción de cadenas en la validación de certificados. Esta lista de certificados no debe contener duplicados. El parámetro opcional crls puede usarse para proporcionar CRLs adicionales. También la lista de CRLs no debe contener duplicados. Los parámetros opcionales contexto de biblioteca libctx y consulta de propiedad propq se usan al recuperar algoritmos de los proveedores.

CMS_get0_signers() recupera el/los certificado(s) de firma de cms; solo puede llamarse después de una operación exitosa de CMS_verify() o CMS_SignedData_verify() .

PROCESO DE VERIFICACIÓN

Normalmente el proceso de verificación procede de la siguiente manera.

Inicialmente se realizan algunas comprobaciones de coherencia en cms. El tipo de cms debe ser SignedData. Debe haber al menos una firma en los datos y si el contenido está separado detached_data no puede ser NULL.

Se intenta localizar todos los certificados de firma, buscando primero en el parámetro certs (si no es NULL) y luego buscando en cualquier certificado contenido en la estructura cms a menos que CMS_NOINTERN esté establecido. Si no se puede localizar algún certificado de firma, la operación falla.

Cada certificado de firma se verifica en cadena usando el propósito smimesign y usando el almacén de certificados confiables store si se proporciona. Cualquier certificado interno en el mensaje, que puede haberse añadido usando CMS_add1_cert(3), se usa como CA no confiable. Si la verificación de CRL está habilitada en store y CMS_NOCRL no está establecido, cualquier CRL interno, que puede haberse añadido usando CMS_add1_crl(3), se usa además de intentar buscarlo en store. Si store no es NULL y alguna verificación de cadena falla, se devuelve un código de error.

Finalmente se lee el contenido firmado (y se escribe en out a menos que sea NULL) y se comprueba la firma.

Si todas las firmas se verifican correctamente, la función es exitosa.

Cualquiera de los siguientes indicadores (combinados con OR) puede pasarse en el parámetro flags para cambiar el comportamiento de verificación predeterminado.

Si CMS_NOINTERN está establecido, los certificados en el mensaje mismo no se buscan al localizar el/los certificado(s) de firma. Esto significa que todos los certificados de firma deben estar en el parámetro certs .

Si CMS_NOCRL está establecido y la verificación de CRL está habilitada en store entonces cualquier CRL en el mensaje mismo y proporcionado a través del parámetro crls se ignoran.

Si el indicador CMS_TEXT está establecido, se eliminan los encabezados MIME para el tipo "text/plain" del contenido. Si el contenido no es de tipo "text/plain" se devuelve un error.

Si CMS_NO_SIGNER_CERT_VERIFY está establecido, los certificados de firma no se verifican en cadena, a menos que el indicador CMS_CADES también esté establecido.

Si CMS_NO_ATTR_VERIFY está establecido, la firma de los atributos firmados no se verifica, a menos que el indicador CMS_CADES también esté establecido.

Si CMS_CADES está establecido, cada certificado de firmante se comprueba contra la extensión ESS signingCertificate o ESS signingCertificateV2 requerida en los atributos firmados de la firma.

Si CMS_NO_CONTENT_VERIFY está establecido, el resumen del contenido no se comprueba.

NOTAS

Una aplicación de CMS_NOINTERN es aceptar solo mensajes firmados por un pequeño número de certificados. Los certificados aceptables se pasarían en el parámetro certs . En este caso, si el certificado del firmante no es uno de los certificados proporcionados en certs entonces la verificación fallará porque no se puede encontrar al firmante.

En algunos casos, las técnicas estándar para buscar y validar certificados no son apropiadas: por ejemplo, una aplicación puede desear buscar certificados en una base de datos o realizar una verificación personalizada. Esto se puede lograr estableciendo y verificando manualmente los certificados del firmante usando las funciones utilitarias de datos firmados.

Se debe tener cuidado al modificar el comportamiento de verificación predeterminado, por ejemplo, establecer CMS_NO_CONTENT_VERIFY deshabilitará por completo toda la verificación de contenido y cualquier contenido modificado se considerará válido. Esta combinación es sin embargo útil si uno simplemente desea escribir el contenido en out y su validez no se considera importante.

La verificación de cadenas podría argumentarse que debe realizarse usando la hora de firma en lugar de la hora actual. Sin embargo, dado que la hora de firma es proporcionada por el firmante, no se puede confiar en ella sin evidencia adicional (como una marca de tiempo confiable).

VALORES DE RETORNO

CMS_verify() devuelve 1 para una verificación exitosa y 0 si ocurrió un error.

CMS_SignedData_verify() devuelve un BIO de memoria que contiene el contenido verificado, o NULL en caso de error.

CMS_get0_signers() devuelve todos los firmantes o NULL si ocurrió un error.

El error se puede obtener de ERR_get_error(3).

ERRORES

El almacén de certificados confiables no se busca para el certificado de firma. Esto se debe principalmente a las deficiencias de la funcionalidad actual de X509_STORE .

La falta de procesamiento de un solo pase significa que el contenido firmado debe mantenerse todo en memoria si no está separado.

VER TAMBIÉN
