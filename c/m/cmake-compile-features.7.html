Requerir estándares de lenguaje En proyectos que usan un gran número de características comúnmente disponibles de un estándar de lenguaje particular (por ejemplo, C++ 11), se puede especificar una meta-característica (por ejemplo, cxx_std_11 ) que requiere el uso de un modo de compilador que como mínimo sea consciente de ese estándar, pero podría ser mayor. Esto es más simple que especificar todas las características individualmente, pero no garantiza la existencia de ninguna característica particular. El diagnóstico del uso de características no soportadas se retrasará hasta el tiempo de compilación. Por ejemplo, si las características de C++ 11 se usan extensivamente en los archivos de cabecera de un proyecto, entonces los clientes deben usar un modo de compilador que no sea inferior a C++ 11. Esto se puede solicitar con el código: target_compile_features(mylib PUBLIC cxx_std_11) En este ejemplo, CMake se asegurará de que el compilador se invoque en un modo de al menos C++ 11 (o C++ 14, C++ 17, ...), añadiendo banderas como -std=gnu++1

Las bibliotecas pueden proporcionar archivos de cabecera completamente diferentes dependiendo de las características del compilador

solicitadas.

Por ejemplo, una cabecera

en

with_variadics/interface.h puede con

tener: 
template<int I, int... Is>
struct Interface;
template<int I>
struct Interface<I>
{
  static int accumulate()
  {
    return I;
  }
};
template<int I, int... Is>
struct Interface
{
  static int accumulate()
  {
    return I + Interface<Is...>::accumulate();
  }
}
;

mientras que una cabecera en no_variadics/interface.h puede contener:

template<int I1, int I2 = 0, int I3 = 0, int I4 = 0>
struct Interface
{
  static int accumulate() { return I1 + I2 + I3 + I4; }
};

Es posible escribir una abstracción interface.h en el encabezado que contenga algo como:

#ifdef HAVE_CXX_VARIADIC_TEMPLATES
#include "with_variadics/interface.h"
#else
#include "no_variadics/interface.h"
#endif

Sin embargo, esto podría ser difícil de mantener si hay muchos archivos que abstraer. Lo que se necesita es usar directorios de inclusión alternativos dependiendo de las capacidades del compilador.

CMake proporciona una COMPILE_FEATURES expresión generadora <#manual:cmake-generator-expressions(7)> para implementar tales condiciones. Esto puede usarse con los comandos de propiedades de compilación como target_include_directories() <#command:target_include_directories> y target_link_libraries() <#command:target_link_libraries> para establecer las propiedades apropiadas del sistema de compilación <#manual:cmake-buildsystem(7)> :

add_library(foo INTERFACE)
set(with_variadics ${CMAKE_CURRENT_SOURCE_DIR}/with_variadics)
set(no_variadics ${CMAKE_CURRENT_SOURCE_DIR}/no_variadics)
target_include_directories(foo
  INTERFACE
    "$<$<COMPILE_FEATURES:cxx_variadic_templates>:${with_variadics}>"
    "$<$<NOT:$<COMPILE_FEATURES:cxx_variadic_templates>>:${no_variadics}>"
  )

El código consumidor simplemente se enlaza al foo objetivo como de costumbre y usa el directorio de inclusión apropiado para la característica

add_executable(consumer_with consumer_with.cpp)
target_link_libraries(consumer_with foo)
set_property(TARGET consumer_with CXX_STANDARD 11)
add_executable(consumer_no consumer_no.cpp)
target_link_libraries(consumer_no foo)

COMPILADORES SOPORTADOS

CMake es actualmente consciente de los estándares de C++ <#prop_tgt:CXX_STANDARD> y características de compilación <#prop_gbl:CMAKE_CXX_KNOWN_FEATURES> disponibles de los siguientes identificadores de compilador <#variable:CMAKE_<LANG>_COMPILER_ID> a partir de las versiones especificadas para cada uno:

  • AppleClang: Apple Clang para versiones de Xcode 4.4+.
  • Clang: Clang compilador versiones 2.9+.
  • GNU: GNU compilador versiones 4.4+.
  • MSVC: Microsoft Visual Studio versiones 2010+.
  • SunPro: Oracle SolarisStudio versiones 12.4+.
  • Intel: Intel compilador versiones 12.1+.

CMake es actualmente consciente de los estándares de C <#prop_tgt:C_STANDARD> y características de compilación <#prop_gbl:CMAKE_C_KNOWN_FEATURES> disponibles de los siguientes identificadores de compilador <#variable:CMAKE_<LANG>_COMPILER_ID> a partir de las versiones especificadas para cada uno:

  • todos los compiladores y versiones listados arriba para C++.
  • GNU: GNU compilador versiones 3.4+

CMake es actualmente consciente de los estándares de C++ <#prop_tgt:CXX_STANDARD> y sus meta-características asociadas (por ejemplo. cxx_std_11) disponibles de los siguientes identificadores de compilador <#variable:CMAKE_<LANG>_COMPILER_ID> a partir de las versiones especificadas para cada uno:

  • Fujitsu: Fujitsu HPC compilador 4.0+.

BANDERAS DE ESTÁNDAR DE LENGUAJE

Para satisfacer los requisitos especificados por el target_compile_features() <#command:target_compile_features> comando o la CMAKE_<LANG>_STANDARD <#variable:CMAKE_<LANG>_STANDARD> variable, CMake puede pasar una bandera de estándar de lenguaje al compilador, como -std=c++11.

Para los Generadores de Visual Studio <#visual-studio-generators>, CMake no puede controlar con precisión la colocación de la bandera de estándar de lenguaje en la línea de comandos del compilador. Para los Generadores de Ninja <#ninja-generators>, Generadores de Makefile <#makefile-generators>, y Xcode <#generator:Xcode>, CMake coloca la bandera de estándar de lenguaje justo después de las banderas de todo el lenguaje de CMAKE_<LANG>_FLAGS <#variable:CMAKE_<LANG>_FLAGS> y CMAKE_<LANG>_FLAGS_<CONFIG> <#variable:CMAKE_<LANG>_FLAGS_<CONFIG>>.

Cambiado en la versión 3.26: La bandera de estándar de lenguaje se coloca antes de las banderas especificadas por otras abstracciones como el target_compile_options() <#command:target_compile_options> comando. Antes de CMake 3.26, la bandera de estándar de lenguaje se colocaba después de ellas.
