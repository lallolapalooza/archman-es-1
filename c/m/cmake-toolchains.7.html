INTRODUCCIÓ

N

CMake utiliza un toolchain de utilidades para compilar, enlazar bibliotecas y crear archivos, y otras tareas para dirigir la compilación. Las utilidades del toolchain disponibles están determinadas por los lenguajes habilitados. En compilaciones normales, CMake determina automáticamente el toolchain para compilaciones en el host basándose en la introspección del sistema y los valores predeterminados. En escenarios de compilación cruzada, se puede especificar un archivo de toolchain con información sobre las rutas del compilador y las

utilidades.

Añadido en la versión 3.19: Se puede usar cmake-presets(7) <#manual:cmake-presets(

7)> para especificar
archivos de toolchain.

CARACTERÍSTICAS DEL

TOOLCHAIN

CMake proporciona el try_compile() <#command:try_compile> comando y módulos como CheckSourceCompiles <#module:CheckSourceCompiles>, CheckCXXSymbolExists <#module:CheckCXXSymbolExists> y CheckIncludeFile <#module:CheckIncludeFile> para probar la capacidad y disponibilidad de varias características del toolchain. Estas APIs prueban el toolchain de alguna manera y almacenan el resultado en caché para que la prueba no tenga que realizarse de nuevo la próxima vez que se ejecute

CMake.

Algunas características del toolchain tienen un manejo integrado en CMake y no requieren pruebas de compilación. Por ejemplo, POSITION_INDEPENDENT_CODE <#prop_tgt:POSITION_INDEPENDENT_CODE> permite especificar que un destino debe compilarse como código independiente de posición, si el compilador soporta esa característica. El <LANG>_VISIBILITY_PRESET <#prop_tgt:<LANG>_VISIBILITY_PRESET> y VISIBILITY_INLINES_HIDDEN <#prop_tgt:VISIBILITY_INLINES_HIDDEN> propiedades del de

stino añaden banderas para visibilidad ocu

COMPILACIÓN

CRUZADA

Si cmake(1) <#manual:cmake(1)> se invoca con el parámetro de línea de comandos --toolchain path/to/file <#cmdoption-cmake-toolchain> o -DCMAKE_TOOLCHAIN_FILE=path/to/file <#cmdoption-cmake-D>, el archivo se cargará temprano para establecer valores para los compiladores. La CMAKE_CROSSCOMPILING <#variable:CMAKE_CROSSCOMPILING> variable se establece en true cuando CMake está compilando en

cruz.

Tenga en cuenta que usar las CMAKE_SOURCE_DIR <#variable:CMAKE_SOURCE_DIR> o CMAKE_BINARY_DIR <#variable:CMAKE_BINARY_DIR> variables dentro de un archivo de toolchain es generalmente indeseable. El archivo de toolchain se usa en contextos donde estas variables tienen valores diferentes cuando se usan en diferentes lugares (por ejemplo, como parte de una llamada a try_compile() <#command:try_compile>). En la mayoría de los casos, donde hay una necesidad de evaluar rutas dentro de un archivo de toolchain, la variable más apropiada a usar sería CMAKE_CURRENT_LIST_DIR <#variable:CMAKE_CURRENT_LIST_DIR>, ya que siempre tiene un valor inequívoco y

predecible.

    Configure el uso de un NDK de Android con las siguientes variables:

    • CMAKE_SYSTEM_NAME: Se establece en Android. Debe especificarse para habilitar la compilación cruzada para Android.
    • CMAKE_SYSTEM_VERSION: Se establece en el nivel de API de Android. Si no se especifica, el valor se determina de la siguiente manera:
      • Si la variable CMAKE_ANDROID_API está establecida, su valor se utiliza como nivel de API.
      • Si la variable CMAKE_SYSROOT está establecida, el nivel de API se detecta a partir de la estructura de directorios del NDK que contiene el sysroot.
      • De lo contrario, se utiliza el nivel de API más reciente disponible en el NDK.
    • CMAKE_ANDROID_ARCH_ABI: Se establece en el ABI (arquitectura) de Android. Si no se especifica, esta variable se establecerá por defecto en el primer ABI compatible de la lista de armeabi, armeabi-v7a y arm64-v8a. La variable CMAKE_ANDROID_ARCH se calculará automáticamente a partir de CMAKE_ANDROID_ARCH_ABI. Consulte también las variables CMAKE_ANDROID_ARM_MODE y CMAKE_ANDROID_ARM_NEON.
    • CMAKE_ANDROID_NDK: La ruta de acceso completa al directorio raíz del NDK de Android. Si no se especifica, se elegirá un valor predeterminado para esta variable como se especifica anteriormente.
    • CMAKE_ANDROID_NDK_DEPRECATED_HEADERS: Establézcalo a un valor verdadero para usar las cabeceras obsoletas por nivel de API en lugar de las cabeceras unificadas. Si no se especifica, el valor predeterminado será falso a menos que se esté utilizando un NDK que no proporcione cabeceras unificadas.
    • CMAKE_ANDROID_NDK_TOOLCHAIN_VERSION: En NDK r19 o superior, esta variable debe estar sin establecer o establecida en clang. En NDK r18 o inferior, establézcala a la versión de la toolchain NDK que se seleccionará como compilador. Si no se especifica, el valor predeterminado será la última toolchain GCC disponible.
    • CMAKE_ANDROID_STL_TYPE: Establézcalo para especificar qué biblioteca estándar de C++ se utilizará. Si no se especifica, se seleccionará un valor predeterminado como se describe en la documentación de la variable.

    Las siguientes variables se calcularán y proporcionarán automáticamente:

    • CMAKE_<LANG>_ANDROID_TOOLCHAIN_PREFIX: El prefijo de ruta de acceso completa a las binutils en la toolchain del NDK.
    • CMAKE_<LANG>_ANDROID_TOOLCHAIN_SUFFIX: El sufijo de la plataforma host de las binutils en la toolchain del NDK.

Firma de

código

Algunos artefactos de compilación para las plataformas Apple embebidas requieren firma de código obligatoria. Si se está utilizando el generador Xcode <#generator:Xcode> y se requiere o desea firma de código, el ID del equipo de desarrollo puede especificarse a través de la variable CMake CMAKE_XCODE_ATTRIBUTE_DEVELOPMENT_TEAM. Este ID de equipo se incluirá entonces en el proyecto Xcode generado. Por defecto, CMake

evita la necesidad de firma de código durante la fase de configuración
interna (es decir, detección de ID y características del compilador).

Cambiando entre dispositivo y

simulador

Al configurar para cualquiera de las plataformas embebidas, se puede apuntar a dispositivos reales o al simulador. Ambos tienen su propio SDK separado, pero CMake solo admite la especificación de un único SDK para la fase de configuración. Esto significa que el desarrollador debe seleccionar uno u otro en el momento de la configuración. Al usar el generador Xcode <#generator:Xcode>, esto es menos una limitación porque Xcode todavía le permite compilar para un dispositivo o un simulador, aunque la configuración se haya realizado solo para uno de los dos. Desde dentro del IDE de Xcode, las compilaciones se realizan para la plataforma "destino" seleccionada. Al compilar desde la línea de comandos, el SDK deseado puede especificarse directamente pasando una opción -sdk a la herramienta de compilación subyacente (xcodebuild). Por

ejemplo: 
$ cmake --b
uild ... --
-sdk ipho
nesimulator

Tenga en cuenta que las comprobaciones realizadas durante la configuración se realizaron contra el SDK en el momento de la configuración y podrían no ser válidas para otros SDKs. Comandos como find_package() <#command:find_package>, find_library() <#command:find_library>, etc. almacenan y usan detalles solo para el SDK/plataforma configurado, por lo que pueden ser problemáticos si se desea cambiar entre compilaciones de dispositivo y simulador.   • Use la bandera de enlazador -framework explícita, p. ej. target_link_libraries(foo PUBLIC "-framework
    • CoreFoundation")
