cmake-presets(7)

Paquete: cmake

CMAKE-PRESETS(7) CMake CMAKE-PRESETS(7)

NOMBRE

cmake-presets - CMakePresets.json

INTRODUCCIÓN

Añadido en la versión 3.19.

Un problema que los usuarios de CMake a menudo enfrentan es compartir configuraciones con otras personas para formas comunes de configurar un proyecto. Esto puede hacerse para soportar compilaciones de CI, o para usuarios que frecuentemente usan la misma compilación. CMake soporta dos archivos principales, CMakePresets.json y CMakeUserPresets.json, que permiten a los usuarios especificar opciones comunes de configuración y compartirlas con otros. CMake también soporta archivos incluidos con el include campo.

CMakePresets.json y CMakeUserPresets.json viven en el directorio raíz del proyecto. Ambos tienen exactamente el mismo formato, y ambos son opcionales (aunque al menos uno debe estar presente si --preset <#cmdoption-cmake-preset> es especificado). CMakePresets.json está destinado a especificar detalles de compilación de todo el proyecto, mientras CMakeUserPresets.json está destinado para que los desarrolladores especifiquen sus propios detalles locales de compilación.

CMakePresets.json puede ser versionado en un sistema de control de versiones, y CMakeUserPresets.json NO debe ser versionado. Por ejemplo, si un proyecto usa Git, CMakePresets.json puede ser rastreado, y CMakeUserPresets.json debería ser añadido al .gitignore.

Nota:

Para un proyecto CMake que utiliza ExternalProject con un ajuste de configuración que tiene variables de entorno necesarias en el ExternalProject, utilice un ajuste de compilación que herede ese ajuste de configuración o el ExternalProject no tendrá las variables de entorno establecidas en el ajuste de configuración. Ejemplo: suponga que el host por defecto utiliza un compilador (por ejemplo, Clang) y el usuario desea usar otro compilador (por ejemplo, GCC). Establezca las variables de entorno del ajuste de configuración CC y CXX y utilice un ajuste de compilación que herede ese ajuste de configuración. De lo contrario, el ExternalProject puede utilizar un compilador diferente (el predeterminado del sistema) que el proyecto CMake de nivel superior.

Las referencias a paquetes se utilizan para definir dependencias de paquetes de gestores de paquetes externos. Actualmente solo se admite NuGet en combinación con el generador Visual Studio. Si no hay destinos que definan referencias a paquetes, esta opción no hace nada. Los valores válidos son:

off

Las referencias a paquetes se restauran utilizando NuGet. Se puede deshabilitar estableciendo la variable CMAKE_VS_NUGET_PACKAGE_RESTORE a OFF. Esto también se puede hacer desde dentro de un ajuste de configuración.

Una cadena requerida que representa el nombre legible por máquina del ajuste preestablecido. Este identificador se utiliza en la opción ctest --preset <#cmdoption-ctest-preset>. Condición

El campo condition de un preset, permitido en archivos de preset que especifican la versión 3 o superior, se utiliza para determinar si el preset está habilitado o no. Por ejemplo, esto se puede usar para deshabilitar un preset en plataformas distintas de Windows. condition puede ser un booleano, null o un objeto. Si es un booleano, el booleano indica si el preset está habilitado o deshabilitado. Si es null, el preset está habilitado, pero la condición null no es heredada por ningún preset que pueda heredar del preset. Las subcondiciones (por ejemplo, en una condición not, anyOf o allOf) no pueden ser null. Si es un objeto, tiene los siguientes campos:

type
Una cadena requerida con uno de los siguientes valores:
"const"
Indica que la condición es constante. Esto es equivalente a usar un booleano en lugar del objeto. El objeto de condición tendrá los siguientes campos adicionales:
value
Un booleano requerido que proporciona un valor constante para la evaluación de la condición.

Expansión de macros

Como se mencionó anteriormente, algunos campos admiten la expansión de macros. Las macros se reconocen en el formato $<namespace-macro>{<nombre-macro>}. Todas las macros se evalúan en el contexto del preset que se está utilizando, incluso si la macro está en un campo que se heredó de otro preset. Por ejemplo, si el preset Base establece la variable PRESET_NAME a ${presetName}, y el preset Derived hereda de Base, PRESET_NAME se establecerá a Derived.

Es un error no colocar una llave de cierre al final del nombre de una macro. Por ejemplo, ${sourceDir no es válido. Un signo de dólar ($) seguido de algo que no sea una llave de apertura ({) con un posible espacio de nombres se interpreta como un signo de dólar literal.

Las macros reconocidas incluyen:

${sourceDir}
Ruta al directorio de origen del proyecto (es decir, lo mismo que CMAKE_SOURCE_DIR <#variable:CMAKE_SOURCE_DIR>).
${sourceParentDir}
Ruta al directorio padre del directorio de origen del proyecto.
${sourceDirName}
El último componente del nombre de archivo de ${sourceDir}. Por ejemplo, si ${sourceDir} es /ruta/a/origen, esto sería origen.
${presetName}
Nombre especificado en el campo name del preset.

Esta es una macro específica del preset.

${generator}
Generador especificado en el campo generator del preset. Para presets de compilación y prueba, esto se evaluará al generador especificado por configurePreset.

Esta es una macro específica del preset.

${hostSystemName}
El nombre del sistema operativo anfitrión. Contiene el mismo valor que CMAKE_HOST_SYSTEM_NAME <#variable:CMAKE_HOST_SYSTEM_NAME>. Esto está permitido en archivos de preset que especifican la versión 3 o superior.
${fileDir}
Ruta al directorio que contiene el archivo de preset que contiene la macro. Esto está permitido en archivos de preset que especifican la versión 4 o superior.
${dollar}
Un signo de dólar literal ($).
${pathListSep}
Carácter nativo para separar listas de rutas, como : o ;.

Por ejemplo, al establecer PATH a /ruta/a/ninja/bin${pathListSep}$env{PATH}, ${pathListSep} se expandirá al carácter utilizado por el sistema operativo subyacente para la concatenación en PATH.

Esto está permitido en archivos de preset que especifican la versión 5 o superior.

$env{<nombre-variable>}
Variable de entorno con el nombre <nombre-variable>. El nombre de la variable no puede ser una cadena vacía. Si la variable está definida en el campo environment, ese valor se usa en lugar del valor del entorno padre. Si la variable de entorno no está definida, esto se evalúa como una cadena vacía.

Tenga en cuenta que, si bien los nombres de las variables de entorno de Windows no distinguen entre mayúsculas y minúsculas, los nombres de las variables dentro de un preset siguen distinguiendo entre mayúsculas y minúsculas. Esto puede generar resultados inesperados al usar una capitalización inconsistente. Para obtener mejores resultados, mantenga la capitalización de los nombres de las variables de entorno de manera consistente.

$penv{<nombre-variable>}
Similar a $env{<nombre-variable>}, excepto que el valor solo proviene del entorno padre y nunca del campo environment. Esto permite agregar o prefijar valores a las variables de entorno existentes. Por ejemplo, establecer PATH a /ruta/a/ninja/bin:$penv{PATH} antepondrá /ruta/a/ninja/bin a la variable de entorno PATH. Esto es necesario porque $env{<nombre-variable>} no permite referencias circulares.
$vendor{<nombre-macro>}
Un punto de extensión para que los proveedores inserten sus propias macros. CMake no podrá usar presets que tengan una macro $vendor{<nombre-macro>}, e ignora efectivamente dichos presets. Sin embargo, aún podrá usar otros presets del mismo archivo.

CMake no hace ningún intento de interpretar las macros $vendor{<nombre-macro>}. Sin embargo, para evitar colisiones de nombres, los proveedores de IDE deben prefijar <nombre-macro> con un prefijo de identificador de proveedor muy corto (preferiblemente <= 4 caracteres), seguido de un ., seguido del nombre de la macro. Por ejemplo, el IDE de Ejemplo podría tener $vendor{xide.ideInstallDir}.
