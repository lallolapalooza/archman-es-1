DESCRIPCIÓ

N

La función close() debe desasignar el descriptor de archivo indicado por fildes. Desasignar significa hacer que el descriptor de archivo esté disponible para ser devuelto por llamadas posteriores a open() u otras funciones que asignan descriptores de archivo. Todos los bloqueos de registro pendientes propiedad del proceso sobre el archivo asociado con el descriptor de archivo deben ser eliminados (es decir, desbloqueados)

.

Si close() es interrumpida por una señal que debe ser capturada, debe devolver -1 con errno establecido a [EINTR] y el estado de fildes es indeterminado. Si ocurrió un error de E/S mientras se leía de o se escribía en el sistema de archivos durante close(), puede devolver -1 con errno establecido a [EIO]; si se devuelve este error, el estado de fildes es

indeterminado.

Cuando todos los descriptores de archivo asociados con un archivo especial de tubería o FIFO sean cerrados, cualquier dato restante en la tubería o FIFO debe ser

descartado.

Cuando todos los descriptores de archivo asociados con una descripción de archivo abierto hayan sido cerrados, la descripción de archivo abierto debe ser

liberada.

Si el conteo de enlaces del archivo es 0, cuando todos los descriptores de archivo asociados con el archivo sean cerrados, el espacio ocupado por el archivo debe ser liberado y el archivo ya no será

accesible.

Si un fildes basado en STREAMS es cerrado y el proceso llamante estaba previamente registrado para recibir una señal SIGPOLL para eventos asociados con ese STREAM, el proceso llamante debe ser dado de baja del registro para eventos asociados con el STREAM. El último close() para un STREAM debe causar que el STREAM asociado con fildes sea desmantelado. Si O_NONBLOCK no está establecido y no se han publicado señales para el STREAM, y si hay datos en la cola de escritura del módulo, close() debe esperar un tiempo indeterminado (para cada módulo y controlador) para que cualquier salida sea drenada antes de desmantelar el STREAM. El retardo de tiempo puede ser cambiado mediante una solicitud ioctl() I_SETCLTIME. Si la bandera O_NONBLOCK está establecida, o si hay señales pendientes, close() no debe esperar a que la salida sea drenada, y debe desmantelar el STREAM

inmediatamente.

Si la implementación soporta tuberías basadas en STREAMS, y fildes está asociado con un extremo de una tubería, el último close() debe causar que ocurra una desconexión en el otro extremo de la tubería. Además, si el otro extremo de la tubería ha sido nombrado por fattach(), entonces el último close() debe forzar que el extremo nombrado sea desvinculado por fdetach(). Si el extremo nombrado no tiene descriptores de archivo abiertos asociados con él y es desvinculado, el STREAM asociado con ese extremo también debe ser

desmantelado.

Si fildes se refiere al lado maestro de una pseudoterminal, y este es el último cierre, una señal SIGHUP debe ser enviada al proceso de control, si existe, para el cual el lado esclavo de la pseudoterminal es la terminal de control. Es indeterminado si cerrar el lado maestro de la pseudoterminal purga toda la entrada y salida en

cola.

Si fildes se refiere al lado esclavo de una pseudoterminal basada en STREAMS, un mensaje de longitud cero puede ser enviado al

maestro.

Cuando hay una operación de E/S asíncrona cancelable pendiente contra fildes cuando close() es llamada, esa operación de E/S puede ser cancelada. Una operación de E/S que no es cancelada se completa como si la operación close() aún no hubiera ocurrido. Todas las operaciones que no son canceladas deben completarse como si close() se bloqueara hasta que las operaciones se completaran. La operación close() en sí misma no necesita bloquearse esperando tal finalización de E/S. Si alguna operación de E/S es cancelada, y qué operación de E/S puede ser cancelada al cerrar(), es definido por la

implementación.

Si un archivo con mapeo de memoria o un objeto de memoria compartida permanece referenciado en el último cierre (es decir, un proceso lo tiene mapeado), entonces todo el contenido del objeto de memoria debe persistir hasta que el objeto de memoria deje de estar referenciado. Si este es el último cierre de un archivo con mapeo de memoria o un objeto de memoria compartida y el cierre resulta en que el objeto de memoria deje de estar referenciado, y el objeto de memoria ha sido desvinculado, entonces el objeto de memoria debe ser

eliminado.

Si fildes se refiere a un socket, close() debe causar que el socket sea destruido. Si el socket está en modo de conexión, y la opción SO_LINGER está establecida para el socket con un tiempo de espera no nulo, y el socket tiene datos no transmitidos, entonces close() debe bloquearse hasta por el intervalo de es

pera actual hasta que todos
los datos sean transmitidos.

USO EN

APLICACIONES

Una aplicación que haya usado la rutina stdio fopen() para abrir un archivo debe usar la rutina fclose() correspondiente en lugar de close(). Una vez que un archivo es cerrado, el archivo descriptor ya no existe, ya que el entero correspondiente a él ya no se refiere a un

archivo.

Las implementaciones pueden usar descriptores de archivo que deben ser heredados por procesos hijos para que el proceso hijo permanezca conforme, como para catálogos de mensajes o fines de trazado. Por lo tanto, una aplicación que llama a close() en un entero arbitrario arriesga un comportamiento no conforme, y close() solo puede usarse de forma portátil en valores de descriptor de archivo que la aplicación ha obtenido mediante acciones explícitas, así como los tres archivos descriptores correspondientes a los flujos de archivo estándar. En aplicaciones padre con múltiples hilos, la práctica de llamar a close() en un bucle después de fork() y antes de una llamada a exec para evitar una condición de carrera de filtrar un descriptor de archivo no intencionado a un proceso hijo, es por lo tanto insegura, y la carrera debe en cambio ser combatida abriendo todos los descriptores de archivo con el bit FD_CLOEXEC establecido a menos que el descriptor de archivo esté destinado a ser heredado a través de exec

.

El uso de close() en los descriptores de archivo STDIN_FILENO, STDOUT_FILENO o STDERR_FILENO debe ir seguido inmediatamente de una operación para reabrir estos descriptores de archivo. Se producirá un comportamiento inesperado si alguno de estos descriptores de archivo se deja en estado cerrado (por ejemplo, un [EBADF] error de perror()) o si una open() o una llamada similar posterior en la aplicación asigna accidentalmente un archivo a uno de estos descriptores de archivo bien conocidos. Además, un close() seguido de una operación de reapertura (por ejemplo, open(), dup(), etc.) no es atómico; dup2() debe usarse para cambiar lo

s descriptores de
archivo estándar.

JUSTIFICACIÓ

N

Se debe desaconsejar el uso de rutinas de cierre de dispositivos interrumpibles para evitar problemas con los cierres implícitos de descriptores de archivo por exec y exit(). Este volumen de POSIX.1‐2017 solo pretende permitir dicho comportamiento especificando la condición de error [EINTR]

.

Tenga en cuenta que el requisito de que close() en un socket bloquee hasta el intervalo de linger actual no está condicionado por la configuración de

O_NONBLOCK.

Los desarrolladores de estándares rechazaron una propuesta para añadir closefrom() al estándar. Dado que el estándar permite a las implementaciones usar descriptores de archivo heredados como medio para proporcionar un entorno conforme al proces

o hijo, no es posible estandarizar una interfaz que cierre descriptores de archivo arb
itrarios por encima de un cierto valor y al mismo tiempo garantice un entorno conforme.
