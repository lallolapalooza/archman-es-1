El signal de terminación del hijo

Cuando el proceso hijo termina, se puede enviar una señal al padre. La señal de terminación se especifica en el byte bajo de flags (clone()) o en cl_args.exit_signal (clone3()). Si esta señal se especifica como algo diferente a SIGCHLD, entonces el proceso padre debe especificar las opciones __WALL o __WCLONE al esperar al hijo con wait(2). Si no se especifica ninguna señal (es decir, cero), entonces el proceso padre no recibe ninguna señal cuando el hijo termina.

El array set_tid

Por defecto, el kernel elige el siguiente PID secuencial para el nuevo proceso en cada uno de los espacios de nombres PID donde está presente. Al crear un proceso con clone3(), el array set_tid (disponible desde Linux 5.5) se puede usar para seleccionar PIDs específicos para el proceso en algunos o todos los espacios de nombres PID donde está presente. Si el PID del proceso recién creado debe establecerse solo para el espacio de nombres PID actual o en el espacio de nombres PID recién creado (si flags contiene CLONE_NEWPID), entonces el primer elemento del array set_tid tiene que ser el PID deseado y set_tid_size debe ser 1.

Si el PID del proceso recién creado debe tener un valor determinado en múltiples espacios de nombres PID, entonces el array set_tid puede tener múltiples entradas. La primera entrada define el PID en el espacio de nombres PID más anidado y cada una de las siguientes entradas contiene el PID en el espacio de nombres PID ancestro correspondiente. El número de espacios de nombres PID en los que se debe establecer un PID está definido por set_tid_size, que no puede ser mayor que el número de espacios de nombres PID actualmente anidados.

Para crear un proceso con los siguientes PIDs en una jerarquía de espacios de nombres PID:

Nivel del NS PID PID Solicitado Notas
0 31496 Espacio de nombres PID más externo
1 42
2 7 Espacio de nombres PID más interno

Establezca el array en:


set_tid[0] = 7;
set_tid[1] = 42;
set_tid[2] = 31496;
set_tid_size = 3;

Si solo es necesario especificar los PIDs en los dos espacios de nombres PID más internos, establezca el array en:


set_tid[0] = 7;
set_tid[1] = 42;
set_tid_size = 2;

El PID en los espacios de nombres PID fuera de los dos espacios de nombres PID más internos se selecciona de la misma manera que se selecciona cualquier otro PID.

La característica set_tid requiere CAP_SYS_ADMIN o (desde Linux 5.9) CAP_CHECKPOINT_RESTORE en todos los espacios de nombres de usuario propietarios de los espacios de nombres PID de destino.

Los llamadores solo pueden elegir un PID mayor que 1 en un espacio de nombres PID dado si ya existe un proceso init (es decir, un proceso con PID 1) en ese espacio de nombres. De lo contrario, la entrada PID para este espacio de nombres PID debe ser 1.

La máscara flags

Tanto clone() como clone3() permiten una máscara de bits de flags que modifica su comportamiento y permite al llamador especificar qué se comparte entre el proceso llamador y el proceso hijo. Esta máscara de bits (el argumento flags de clone() o el campo cl_args.flags pasado a clone3()) se denomina máscara flags en el resto de esta página.

La máscara flags se especifica como un OR a nivel de bits de cero o más de las constantes listadas a continuación. Excepto donde se indique lo contrario, estas flags están disponibles (y tienen el mismo efecto) tanto en clone() como en clone3().

CLONE_CHILD_CLEARTID (desde Linux 2.5.49)
Borra (pone a cero) el ID del hilo hijo en la ubicación apuntada por child_tid (clone()) o cl_args.child_tid (clone3()) en la memoria del hijo cuando el hijo sale, y realiza un despertar en el futex en esa dirección. La dirección involucrada puede ser cambiada por la llamada al sistema set_tid_address(2). Esto es utilizado por las bibliotecas de hilos.
CLONE_CHILD_SETTID (desde Linux 2.5.49)
Almacena el ID del hilo hijo en la ubicación apuntada por child_tid (clone()) o cl_args.child_tid (clone3()) en la memoria del hijo. La operación de almacenamiento se completa antes de que la llamada clone devuelva el control al espacio de usuario en el proceso hijo. (Tenga en cuenta que la operación de almacenamiento puede no haberse completado antes de que la llamada clone devuelva el control en el proceso padre, lo cual es relevante si la flag CLONE_VM también se emplea).
CLONE_CLEAR_SIGHAND (desde Linux 5.5)
Por defecto, las disposiciones de señales en el hilo hijo son las mismas que en el padre. Si se especifica esta flag, todas las señales que son manejadas en el padre (y no configuradas como SIG_IGN) se restablecen a sus disposiciones predeterminadas (SIG_DFL) en el hijo.
Especificar esta flag junto con CLONE_SIGHAND no tiene sentido y está prohibido.
CLONE_DETACHED (histórico)
Durante un tiempo (durante la serie de desarrollo de Linux 2.5) existió una flag CLONE_DETACHED, que hacía que el padre no recibiera una señal cuando el hijo terminaba. Finalmente, el efecto de esta flag fue absorbido por la flag CLONE_THREAD y para cuando Linux 2.6.0 fue lanzado, esta flag no tenía efecto. Desde Linux 2.6.2, la necesidad de dar esta flag junto con CLONE_THREAD desapareció.
Esta flag todavía está definida, pero generalmente se ignora al llamar a clone(). Sin embargo, consulte la descripción de CLONE_PIDFD para algunas excepciones.
CLONE_FILES (desde Linux 2.0)
Si se establece CLONE_FILES, el proceso llamador y el proceso hijo comparten la misma tabla de descriptores de archivo. Cualquier descriptor de archivo creado por el proceso llamador o por el proceso hijo también es válido en el otro proceso. De manera similar, si uno de los procesos cierra un descriptor de archivo, o cambia sus flags asociadas (usando la operación fcntl(2) F_SETFD), el otro proceso también se ve afectado. Si un proceso que comparte una tabla de descriptores de archivo llama a execve(2), su tabla de descriptores de archivo se duplica (se des-comparte).
Si CLONE_FILES no se establece, el proceso hijo hereda una copia de todos los descriptores de archivo abiertos en el proceso llamador en el momento de la llamada clone. Las operaciones posteriores que abren o cierran descriptores de archivo, o cambian las flags de los descriptores de archivo, realizadas por el proceso llamador o el proceso hijo no afectan al otro proceso. Tenga en cuenta, sin embargo, que los descriptores de archivo duplicados en el hijo se refieren a las mismas descripciones de archivo abiertas que los descriptores de archivo correspondientes en el proceso llamador, y por lo tanto comparten los offsets de archivo y las flags de estado de archivo (ver open(2)).
CLONE_FS (desde Linux 2.0)
Si se establece CLONE_FS, el llamador y el proceso hijo comparten la misma información del sistema de archivos. Esto incluye la raíz del sistema de archivos, el directorio de trabajo actual y la umask. Cualquier llamada a chroot(2), chdir(2), o umask(2) realizada por el proceso llamador o el proceso hijo también afecta al otro proceso.
Si CLONE_FS no se establece, el proceso hijo trabaja con una copia de la información del sistema de archivos del proceso llamador en el momento de la llamada clone. Las llamadas a chroot(2), chdir(2), o umask(2) realizadas posteriormente por uno de los procesos no afectan al otro proceso.
CLONE_INTO_CGROUP (desde Linux 5.7)
Por defecto, un proceso hijo se coloca en el mismo cgroup de versión 2 que su padre. La flag CLONE_INTO_CGROUP permite que el proceso hijo se cree en un cgroup de versión 2 diferente. (Tenga en cuenta que CLONE_INTO_CGROUP solo tiene efecto para los cgroups de versión 2).
Para colocar el proceso hijo en un cgroup diferente, el llamador especifica CLONE_INTO_CGROUP en cl_args.flags y pasa un descriptor de archivo que se refiere a un cgroup de versión 2 en el campo cl_args.cgroup. (Este descriptor de archivo se puede obtener abriendo un directorio cgroup v2 usando la flag O_RDONLY o la flag O_PATH). Tenga en cuenta que todas las restricciones habituales (descritas en cgroups(7)) para colocar un proceso en un cgroup de versión 2 se aplican.
Entre los posibles casos de uso para CLONE_INTO_CGROUP se incluyen los siguientes:
•
Iniciar un proceso en un cgroup diferente al cgroup del padre hace posible que un gestor de servicios inicie directamente nuevos servicios en cgroups dedicados. Esto elimina la fluctuación de contabilidad que causaría si el proceso hijo se creara primero en el mismo cgroup que el padre y luego se moviera al cgroup de destino. Además, iniciar el proceso hijo directamente en un cgroup de destino es significativamente más económico que mover el proceso hijo al cgroup de destino después de que haya sido creado.
•
La flag CLONE_INTO_CGROUP también permite la creación de procesos hijos congelados iniciándolos en un cgroup congelado. (Consulte cgroups(7) para una descripción del controlador freezer.)
•
Para aplicaciones con hilos (o incluso implementaciones de hilos que usan cgroups para limitar hilos individuales), es posible establecer una disposición fija de cgroup antes de iniciar cada hilo directamente en su cgroup de destino.
CLONE_IO (desde Linux 2.6.25)
Si se establece CLONE_IO, entonces el nuevo proceso comparte un contexto de I/O con el proceso llamador. Si esta flag no se establece, entonces (como con fork(2)) el nuevo proceso tiene su propio contexto de I/O.
El contexto de I/O es el ámbito de I/O del planificador de disco
ulador (es decir, lo que el programador de E/S utiliza para modelar la programación de la E/S de un proceso). Si los procesos comparten el mismo contexto de E/S, el programador de E/S los trata como uno solo. Como consecuencia, comparten el tiempo de disco. Para algunos programadores de E/S, si dos procesos comparten un contexto de E/S, se les permitirá intercalar sus accesos al disco. Si varios hilos están realizando E/S en nombre del mismo proceso (aio_read(3) , por ejemplo), deberían emplear CLONE_IO para obtener un mejor rendimiento de E/S. VERSIONES

La función envoltorio clone() de glibc realiza algunos cambios en la memoria apuntada por stack (cambios necesarios para configurar correctamente la pila para el hijo) antes de invocar la llamada al sistema clone(). Por lo tanto, en casos donde clone() se usa para crear hijos recursivamente, no use el búfer empleado para la pila del padre como la pila del hijo.

En i386, clone() no debe llamarse a través de vsyscall, sino directamente a través de int $0x80.

Diferencias entre la biblioteca C y el kernel

La llamada al sistema clone() "cruda" se corresponde más estrechamente con fork(2) en el sentido de que la ejecución en el hijo continúa desde el punto de la llamada. Como tal, los argumentos fn y arg de la función envoltorio clone() se omiten.

En contraste con la función envoltorio de glibc, la llamada al sistema clone() "cruda" acepta NULL como argumento stack (y clone3() permite de manera similar que cl_args.stack sea NULL). En este caso, el hijo usa una copia duplicada de la pila del padre. (La semántica de copia en escritura garantiza que el hijo obtenga copias separadas de las páginas de pila cuando cualquiera de los procesos modifica la pila.) En este caso, para un funcionamiento correcto, la opción CLONE_VM no debe especificarse. (Si el hijo comparte la memoria del padre debido al uso de la bandera CLONE_VM, entonces no se produce duplicación de copia en escritura y es probable que se produzcan caos.)

El orden de los argumentos también difiere en la llamada al sistema "cruda", y hay variaciones en los argumentos entre arquitecturas, como se detalla en los párrafos siguientes.

La interfaz de llamada al sistema "cruda" en x86-64 y algunas otras arquitecturas (incluyendo sh, tile y alpha) es:


long clone(unsigned long flags, void *stack,
           int *parent_tid, int *child_tid,
           unsigned long tls);

En x86-32 y varias otras arquitecturas comunes (incluyendo score, ARM, ARM 64, PA-RISC, arc, Power PC, xtensa y MIPS), el orden de los dos últimos argumentos está invertido:


long clone(unsigned long flags, void *stack,
          int *parent_tid, unsigned long tls,
          int *child_tid);

En las arquitecturas cris y s390, el orden de los dos primeros argumentos está invertido:


long clone(void *stack, unsigned long flags,
           int *parent_tid, int *child_tid,
           unsigned long tls);
