N

Estas llamadas al sistema crean un nuevo proceso ("hijo"), de una manera similar a fork(

2).

A diferencia de fork(2), estas llamadas al sistema proporcionan un control más preciso sobre qué partes del contexto de ejecución se comparten entre el proceso que llama y el proceso hijo. La función envoltorio

clone()

Cuando el proceso hijo se crea con la función envoltorio clone(), comienza la ejecución llamando a la función a la que apunta el argumento fn. (Esto difiere de fork(2), donde la ejecución continúa en el hijo desde el punto de la llamada a fork(2).) El argumento arg se pasa como el argumento de la función fn

.

Cuando la función fn(arg) retorna, el proceso hijo termina. El entero retornado por fn es el estado de salida para el proceso hijo. El proceso hijo también puede terminar explícitamente llamando a exit(2) o después de recibir una señal

fatal.

El argumento stack especifica la ubicación de la pila usada por el proceso hijo. Dado que el hijo y el proceso que llama pueden compartir memoria, no es posible que el proceso hijo ejecute en la misma pila que el proceso que llama. El proceso que llama debe por tanto configurar un espacio de memoria para la pila del hijo y pasar un puntero a este espacio a clone(). Las pilas crecen hacia abajo en todos los procesadores que ejecutan Linux (excepto los procesadores HP PA ), por lo que stack usualmente apunta a la dirección más alta del espacio de memoria configurado para la pila del hijo. Nótese que clone() no provee un medio por el cual el que llama pueda informar al kernel del tamaño del área de la

pila.

La llamada al sistema clone3() provee un superconjunto de la funcionalidad de la interfaz más antigua clone(). También provee una serie de mejoras a la API, incluyendo: espacio para bits de flags adicionales; una separación más clara en el uso de varios argumentos; y la capacidad de especificar el tamaño del área de pila del

hijo.

Al igual que con fork(2), clone3() retorna tanto en el padre como en el hijo. Retorna 0 en el proceso hijo y retorna el PID del hijo en el

padre.

Si CLONE_THREAD está establecido, el hijo se coloca en el mismo grupo de hilos que el proceso que llama. Para hacer más legible el resto de la discusión de CLONE_THREAD, el término "hilo" se usa para re

Los grupos de hilos fueron una característica añadida en Linux 2.4 para soportar la noción de POSIX de un conjunto de hilos que comparten un solo PID. Internamente, este PID compartido es el llamado identificador de grupo de hilos (TGID) para el grupo de hilos. Desde Linux 2.4, las llamadas a getpid(2) devuelven el TGID del que
llama.
Los hilos dentro de un grupo pueden distinguirse por sus identificadores de hilo (TID) únicos (en todo el sistema). El TID de un nuevo hilo está disponible como el resultado de la función devuelto al que llama, y un hilo puede obtener su propio TID usando gettid(
2).
Cuando se hace una llamada clone sin especificar CLONE_THREAD, entonces el hilo resultante se coloca en un nuevo grupo de hilos cuyo TGID es el mismo que el TID del hilo. Este hilo es el líder del nuevo grupo de
hilos.
Un nuevo hilo creado con CLONE_THREAD tiene el mismo proceso padre que el proceso que hizo la llamada clone (es decir, como CLONE_PARENT), de modo que las llamadas a getppid(2) devuelven el mismo valor para todos los hilos en un grupo de hilos. Cuando un hilo CLONE_THREAD termina, al hilo que lo creó no se le envía una señal SIGCHLD (u otra de terminación); ni se puede obtener el estado de dicho hilo usando wait(2). (Se dice que el hilo está desprendi
do.)
Después de que todos los hilos en un grupo de hilos terminen, al proceso padre del grupo de hilos se le envía una señal SIGCHLD (u otra de terminación)
.
Si alguno de los hilos en un grupo de hilos realiza un execve(2), entonces todos los hilos excepto el líder del grupo de hilos son terminados, y el nuevo programa se ejecuta en el líder del grupo de
hilos.
Si uno de los hilos en un grupo de hilos crea un hijo usando fork(2), entonces cualquier hilo en el grupo puede esperar (wait(2)) por ese
hijo.
Desde Linux 2.5.35, la máscara de flags también debe incluir CLONE_SIGHAND si CLONE_THREAD está especificado (y note que, desde Linux 2.6.0, CLONE_SIGHAND también requiere que se incluya CLONE_V
M).
Las disposiciones y acciones de las señales son de todo el proceso: si una señal no manejada se entrega a un hilo, entonces afectará (terminará, detendrá, continuará, será ignorada en) a todos los miembros del grupo de
hilos.
Cada hilo tiene su propia máscara de señales, como la establecida por sigprocmas
k(2).
Una señal puede estar dirigida al proceso o al hilo. Una señal dirigida al proceso está dirigida a un grupo de hilos (es decir, un TGID), y se entrega a un hilo seleccionado arbitrariamente entre aquellos que no están bloqueando la señal. Una señal puede estar dirigida al proceso porque fue generada por el kernel por razones distintas a una excepción de hardware, o porque fue enviada usando kill(2) o sigqueue(3). Una señal dirigida al hilo está dirigida a (es decir, entregada a) un hilo específico. Una señal puede estar dirigida al hilo porque fue enviada usando tgkill(2) o pthread_sigqueue(3), o porque el hilo ejecutó una instrucción de lenguaje de máquina que desencadenó una excepción de hardware (por ejemplo, un acceso a memoria inválido que desencadena SIGSEGV o una excepción de punto flotante que desencadena SIGFP
E).
Una llamada a sigpending(2) devuelve un conjunto de señales que es la unión de las señales dirigidas al proceso pendientes y las señales que están pendientes para el hilo que
llama.
Si una señal dirigida al proceso se entrega a un grupo de hilos, y el grupo de hilos ha instalado un manejador para la señal, entonces el manejador se invoca en exactamente un miembro del grupo de hilos, seleccionado arbitrariamente, que no ha bloqueado la señal. Si múltiples hilos en un grupo están esperando para aceptar la misma señal usando sigwaitinfo(2), el kernel seleccionará arbitr
ariamente uno de estos hi
los para recibir la señal.

kernel

La llamada al sistema cruda clone() corresponde más de cerca a fork(2) en que la ejecución en el hijo continúa desde el punto de la llamada. Como tal, los argumentos fn y arg de la función envolvente clone() son

En este caso, el hijo usa un duplicado de la pila del padre. En este caso, para un funcionamiento correcto, la opción CLONE_VM no debe ser especificada. (Si el hijo comparte la memoria del padre debido al uso del flag CLONE_VM, entonces no ocurre ninguna duplicación copia-en-escritura y es probable que resulte caos.

)

NOMBRE


clone - crear un proceso hijo






SINOPSIS


#define _GNU_SOURCE             /* Descomentar para obtener CLONE_NEW* */
#include <sched.h>

int clone(int (*fn)(void *), void *stack, int flags, void *arg, ...
          /* pid_t *ptid, void *newtls, pid_t *ctid */ );







DESCRIPCIÓN


La llamada al sistema clone() crea un nuevo proceso hijo.
    La diferencia principal entre clone() y fork(2)
    es que clone() permite que el padre controle qué partes del contexto
    de ejecución son compartidas entre el padre y el hijo. Esto permite la
    implementación de hilos (threads) y namespaces.


El argumento fn es un puntero a una función que será
    ejecutada por el hilo hijo. El argumento arg es pasado a esta
    función.


El argumento stack es la dirección del inicio de la pila
    para el hilo hijo. La pila debe ser lo suficientemente grande, y debe
    crecer hacia direcciones de memoria inferiores (es decir, el valor de
    stack debe ser la dirección más alta de la pila del hijo).


El argumento flags es una máscara de bits que especifica
    qué recursos serán compartidos entre el padre y el hijo. La lista completa
    de flags se describe en la página man capabilities(7).
    Algunos flags comunes son:



  
CLONE_VM

  
El hijo comparte el mismo espacio de direcciones de memoria que el padre.
      Los cambios en la memoria realizados por el padre son visibles para el
      hijo y viceversa. Si se usa este flag, no se debe usar un argumento
      stack diferente, ya que ambos procesos compartirían la misma pila.
      Si CLONE_VM se usa, entonces la pila pasada a clone() debe
      ser una pila válida para el proceso actual, y debe ser lo suficientemente
      grande para la ejecución de la función fn y su árbol de llamadas.
      Este flag es comúnmente usado para crear hilos.

  
CLONE_FS

  
El hijo comparte los mismos archivos, sistemas de ficheros y operaciones
      de semáforo de System V (file system, filesystem, and System V semaphore
      undo operations) que el padre. Este flag es requerido para que las
      operaciones de hilos que modifican el sistema de archivos (como crear un
      archivo) funcionen correctamente.

  
CLONE_FILES

  
El hijo comparte la tabla de descriptores de archivo del padre (file
      descriptor table). Los cambios realizados por el padre o el hijo en esta
      tabla (por ejemplo, abriendo o cerrando un archivo) son visibles para
      ambos. Este flag es requerido para que las operaciones de hilos que
      modifican el sistema de archivos (como crear un archivo) funcionen
      correctamente.

  
CLONE_SIGHAND

  
El hijo comparte las tablas de manejadores de señales del padre (signal
      handlers). Los cambios en los manejadores de señales realizados por el
      padre son visibles para el hijo y viceversa. Este flag es requerido para
      que las operaciones de hilos que modifican los manejadores de señales
      (como registrar un manejador de señales) funcionen correctamente. Si se
      usa CLONE_VM, entonces este flag también se usa implícitamente.

  
CLONE_THREAD

  
El hijo pertenece al mismo grupo de hilos que el padre. Esto significa que
      comparten el mismo ID de proceso (PID), pero tienen IDs de hilo (TID)
      distintos. El padre y el hijo pueden enviarse señales entre sí usando
      sus respectivos TID. Si se usa este flag, el padre y el hijo tendrán el
      mismo PID. Además, este flag implica CLONE_SIGHAND y
      CLONE_VM (si la versión del kernel lo soporta).

  
CLONE_PARENT

  
El padre del nuevo hilo es el mismo que el padre del proceso llamante. Por
      defecto, el padre del nuevo hilo es el mismo que el padre del hilo
      llamante. Si CLONE_THREAD se usa, este flag se usa implícitamente.

  
CLONE_NEWUTS

  
Crea un nuevo namespace UTS (Unix Timesharing System) para el hijo. Esto
      permite que el hijo tenga su propio nombre de host, nombre de dominio, etc.,
      independientemente del padre.

  
CLONE_NEWIPC

  
Crea un nuevo namespace IPC (Inter-Process Communication) para el hijo.

  
CLONE_NEWPID

  
Crea un nuevo namespace PID para el hijo. Los procesos dentro de este
      namespace tendrán PIDs que comienzan desde 1.

  
CLONE_NEWNET

  
Crea un nuevo namespace de red para el hijo.

  
CLONE_NEWUSER

  
Crea un nuevo namespace de usuario para el hijo.

  
CLONE_NEWNS

  
Crea un nuevo namespace de montaje (mount namespace) para el hijo.




Si flags incluye CLONE_CHILD_SETTID, entonces el
    valor del TID del hilo hijo (que puede ser obtenido por gettid(2))
    será escrito en la ubicación de memoria apuntada por ctid. Esto es
    útil para que el hilo hijo sepa cuál es su propio TID.


Si flags incluye CLONE_CHILD_CLEARTID, entonces
    cuando el hilo hijo termine, la ubicación de memoria apuntada por ctid
    será puesta a cero. Esto es útil para la sincronización, ya que otros hilos
    pueden esperar a que esta ubicación se ponga a cero para saber que el hilo
    ha terminado.


Los argumentos opcionales ptid y ctid son punteros
    a tipos `pid_t`. Si se especifican los flags apropiados, estos argumentos
    se usan para la comunicación del TID del padre y del hijo.


Si se especifica el flag CLONE_SETTLS, el argumento
    newtls es un puntero a una estructura `struct user_desc` que describe
    la nueva Tarea-Local Storage (TLS) para el hijo. La estructura `user_desc`
    se define en el archivo de cabecera ``. Si CLONE_SETTLS
    no está especificado, newtls es ignorado.


El valor de retorno de clone() es el TID del hilo hijo
    recién creado en el proceso padre. En el proceso hijo, el valor de retorno
    es 0. Si ocurre un error, clone() retorna -1 en el padre y no se crea
    ningún hijo.


La llamada al sistema clone3() (introducida en el kernel
    Linux 5.3) proporciona una interfaz más moderna y flexible para la creación
    de procesos y hilos, utilizando una estructura `struct clone_args` para
    pasar argumentos. Se recomienda usar clone3() en lugar de
    clone() cuando sea posible.




blackfin, m68k y sparc


Las convenciones de paso de argumentos en blackfin, m68k y sparc
    son diferentes a las descripciones anteriores. Para más detalles, consulte
    el código fuente del kernel (y de glibc).

Linux 2.4 y anteriores


En la serie Linux 2.4.x, CLONE_THREAD generalmente no hacía
    que el padre del nuevo hilo fuera el mismo que el padre del proceso llamante.

En Linux 2.4 y anteriores, clone() no acepta los
    argumentos parent_tid, tls y child_tid.






ia64


En ia64, se utiliza una interfaz diferente:



  




int __clone2(typeof(int (void *)) *fn,
             void *stack_base, size_t stack_size,
             int flags, void *arg, ...
          /* pid_t *parent_tid, struct user_desc *tls,
             pid_t *child_tid */ );


El prototipo mostrado arriba es para la función wrapper de glibc;
    para la llamada al sistema en sí, el prototipo se puede describir de la
    siguiente manera (es idéntico al prototipo de clone() en microblaze):



  




long clone2(unsigned long flags, void *stack_base,
            int stack_size,         /* Tamaño de la pila */
            int *parent_tid, int *child_tid,
            unsigned long tls);


__clone2() opera de la misma manera que clone(),
    excepto que stack_base apunta a la dirección más baja del área de pila
    del hijo, y stack_size especifica el tamaño de la pila apuntada por
    stack_base.








NOTAS


Un uso de estas llamadas al sistema es para implementar hilos:
    múltiples flujos de control en un programa que se ejecutan
    concurrentemente en un espacio de direcciones compartido.


La llamada al sistema kcmp(2) puede
    utilizarse para probar si dos procesos comparten varios recursos, como una
    tabla de descriptores de archivo, operaciones de deshacer de semáforos de
    System V, o un espacio de direcciones virtual.


Los manejadores registrados usando pthread_atfork(3)

ERRORES


Las versiones de la biblioteca C de GNU 2.3.4 hasta la 2.24
    incluida contenían una función wrapper para getpid(2)
    que realizaba el almacenamiento en caché de PIDs. Este almacenamiento en
    caché dependía del soporte en el wrapper de glibc para clone(), pero
    las limitaciones en la implementación significaban que la caché no estaba
    actualizada en algunas circunstancias. En particular, si se entregaba una
    señal al hijo inmediatamente después de la llamada a clone(), entonces
    una llamada a getpid(2) en un manejador de
    la señal podría retornar el PID del proceso llamante ("el padre"), si el
    wrapper de clone aún no había tenido la oportunidad de actualizar la caché
    de PID en el hijo. (Esta discusión ignora el caso donde el hijo fue creado
    usando CLONE_THREAD, cuando getpid(2)
    *debería* retornar el mismo valor en el hijo y en el proceso que llamó a
    clone(), ya que el llamante y el hijo están en el mismo grupo de
    hilos. El problema de la caché obsoleta tampoco ocurre si el argumento
    flags incluye CLONE_VM.) Para obtener la verdad, a veces era
    necesario usar código como el siguiente:



  




#include <syscall.h>
pid_t mypid;
mypid = syscall(SYS_getpid);


Debido al problema de la caché obsoleta, así como a otros problemas
    notados en getpid(2), la característica de
    almacenamiento en caché de PID fue eliminada en glibc 2.25.






EJEMPLOS


El siguiente programa demuestra el uso de clone() para
    crear un proceso hijo que se ejecuta en un namespace UTS separado. El hijo
    cambia el nombre de host en su namespace UTS. Tanto el padre como el hijo
    muestran el nombre de host del sistema, lo que hace posible ver que el
    nombre de host difiere en los namespaces UTS del padre y del hijo. Para un
    ejemplo del uso de este programa, vea setns(2).


Dentro del programa de ejemplo, asignamos la memoria que se
    utilizará para la pila del hijo usando mmap(2)
    en lugar de malloc(3) por las siguientes
    razones:



  
•

  
mmap(2) asigna un bloque de memoria que comienza en un límite de
      página y es un múltiplo del tamaño de página. Esto es útil si queremos
      establecer una página de guarda (una página con protección PROT_NONE)
      al final de la pila usando mprotect(2).

  
•

  
Podemos especificar el flag MAP_STACK para solicitar un mapeo
      que sea adecuado para una pila. Por el momento, este flag no tiene
      efecto en Linux, pero existe y tiene efecto en algunos otros sistemas,
      por lo que debemos incluirlo por portabilidad.






Código fuente del programa


#define _GNU_SOURCE
#include <err.h>
#include <sched.h>
#include <signal.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/mman.h>
#include <sys/types.h>
#include <sys/utsname.h>
#include <sys/wait.h>
#include <unistd.h>
static int              /* Función de inicio para el hijo clonado */
childFunc(void *arg)
{
    struct utsname uts;
    /* Cambiar el nombre de host en el namespace UTS del hijo.  */
    if (sethostname(arg, strlen(arg)) == -1)
        err(EXIT_FAILURE, "sethostname");
    /* Recuperar y mostrar el nombre de host.  */
    if (uname(&uts) == -1)
        err(EXIT_FAILURE, "uname");
    printf("uts.nodename en el hijo:  %s\n", uts.nodename);
    /* Mantener el namespace abierto por un tiempo, durmiendo.
       Esto permite cierta experimentación; por ejemplo, otro
       proceso podría unirse al namespace.  */
    sleep(200);
    return 0;           /* El hijo termina ahora */
}
#define STACK_SIZE (1024 * 1024)    /* Tamaño de pila para el hijo clonado */
int
main(int argc, char *argv[])
{
    char            *stack;         /* Inicio del buffer de pila */
    char            *stackTop;      /* Fin del buffer de pila */
    pid_t           pid;
    struct utsname  uts;
    if (argc < 2) {
        fprintf(stderr, "Uso: %s <nombre-host-hijo>\n", argv[0]);
        exit(EXIT_SUCCESS);
    }
    /* Asignar memoria a ser usada para la pila del hijo.  */
    stack = mmap(NULL, STACK_SIZE, PROT_READ | PROT_WRITE,
                 MAP_PRIVATE | MAP_ANONYMOUS | MAP_STACK, -1, 0);
    if (stack == MAP_FAILED)
        err(EXIT_FAILURE, "mmap");
    stackTop = stack + STACK_SIZE;  /* Asumir que la pila crece hacia abajo */
    /* Crear un hijo que tenga su propio namespace UTS;
       el hijo comienza la ejecución en childFunc().  */
    pid = clone(childFunc, stackTop, CLONE_NEWUTS | SIGCHLD, argv[1]);
    if (pid == -1)
        err(EXIT_FAILURE, "clone");
    /* El padre continúa desde aquí */
    if (munmap(stack, STACK_SIZE))
        err(EXIT_FAILURE, "munmap");
    printf("clone() retornó %jd\n", (intmax_t) pid);
    sleep(1);           /* Darle tiempo al hijo para cambiar su nombre de host */
    /* Mostrar el nombre de host en el namespace UTS del padre. Esto será
       diferente del nombre de host en el namespace UTS del hijo.  */
    if (uname(&uts) == -1)
        err(EXIT_FAILURE, "uname");
    printf("uts.nodename en el padre: %s\n", uts.nodename);
    if (waitpid(pid, NULL, 0) == -1)    /* Esperar al hijo */
        err(EXIT_FAILURE, "waitpid");
    printf("el hijo ha terminado\n");
    exit(EXIT_SUCCESS);
}

clone3(2)

NAME

clone3 - crear un proceso hijo

LIBRARY

Biblioteca C estándar (libc)

SYNOPSIS


#define _GNU_SOURCE
#include <sys/types.h>
#include <sys/wait.h>
#include <fcntl.h>
#include <sched.h>

int clone3(struct clone_args *args);

DESCRIPTION

La llamada al sistema clone3 crea un nuevo proceso (hijo) que se ejecuta en el mismo espacio de direcciones que el proceso que realiza la llamada (padre). Los argumentos para la nueva llamada al sistema se pasan a través de una estructura struct clone_args.

La estructura struct clone_args se define de la siguiente manera:


struct clone_args {
    __u64 flags;              /* Señales para controlar el comportamiento de clone3 */
    __u64 parent_tid;         /* Puntero a un tid para el padre */
    __u64 child_tid;          /* Puntero a un tid para el hijo */
    __u64 exit_signal;        /* Señal a enviar al padre cuando el hijo muere */
    __u64 stack;              /* Puntero a la pila del hijo */
    __u64 stack_size;         /* Tamaño de la pila del hijo */
    __u64 tls;                /* Puntero a la información de TLS */
    __u64 setTid;             /* Identificador de conjunto para el hilo */
    __u64 setTid_size;        /* Tamaño de setTid */
    __u64 cgroup;             /* Identificador de cgroup */
    __u64 cgroup_size;        /* Tamaño de cgroup */
};

Los flags controlan qué recursos se comparten entre el padre y el hijo.

CLONE_VM
El hijo comparte el mismo espacio de direcciones de memoria que el padre. Los cambios en la memoria del padre afectan al hijo y viceversa.
CLONE_FS
El hijo comparte el mismo sistema de archivos que el padre. Esto incluye el directorio raíz, el directorio de trabajo actual y la máscara de creación de archivos (umask).
CLONE_FILES
El hijo comparte la misma tabla de descriptores de archivos que el padre. Los cambios en la tabla de descriptores de archivos del padre afectan al hijo y viceversa.
CLONE_SIGHAND
El hijo comparte la misma tabla de manejadores de señales que el padre.
CLONE_THREAD
El hijo se ejecuta en el mismo hilo que el padre.
CLONE_PARENT_SETTID
Si se establece, el campo parent_tid se escribe en el tid del hilo padre.
CLONE_CHILD_SETTID
Si se establece, el campo child_tid se escribe en el tid del hilo hijo.
CLONE_CHILD_CLEARTID
Si se establece, el campo child_tid se borra cuando el hilo hijo sale.
CLONE_NEWNS
Crea un nuevo dominio de montaje para el hijo.
CLONE_NEWUTS
Crea un nuevo dominio de hostname para el hijo.
CLONE_NEWIPC
Crea un nuevo dominio IPC para el hijo.
CLONE_NEWPID
Crea un nuevo dominio PID para el hijo.
CLONE_NEWNET
Crea un nuevo dominio de red para el hijo.
CLONE_NEWUSER
Crea un nuevo dominio de usuario para el hijo.
CLONE_NEWCGROUP
Crea un nuevo dominio de cgroup para el hijo.

RETURN VALUE

En caso de éxito, la llamada al sistema clone3 devuelve el TID del proceso hijo recién creado al proceso padre. Al proceso hijo se le devuelve 0.

En caso de error, se devuelve -1 y la variable global errno se establece para indicar el error.

ERRORS

EAGAIN
No hay suficientes recursos del sistema para crear un nuevo proceso.
EINVAL
Argumentos inválidos proporcionados.
ENOMEM
No hay suficiente memoria para asignar al nuevo proceso.

VERSIONS

clone3 se introdujo en Linux 5.3.

STANDARDS

Esta llamada al sistema no forma parte de ningún estándar.

HISTORY

La llamada al sistema clone3 se introdujo en Linux 5.3 como una alternativa más flexible a la llamada al sistema clone existente.

NOTES

La llamada al sistema clone3 es una herramienta poderosa para crear procesos y gestionar recursos del sistema. Se utiliza a menudo en la implementación de contenedores y otras tecnologías de virtualización.

Es importante tener cuidado al utilizar las diversas banderas proporcionadas por clone3, ya que pueden tener efectos significativos en el comportamiento del proceso hijo y del sistema en general.

BUGS

No se conocen errores en este momento.

EXAMPLES

El siguiente ejemplo demuestra el uso de clone3 para crear un proceso hijo que comparte el espacio de direcciones de memoria con el padre:


#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <sys/types.h>
#include <sys/wait.h>
#include <sched.h>
#include <unistd.h>

// Función que será ejecutada por el proceso hijo
int child_function(void *arg) {
    printf("Hola desde el proceso hijo!\n");
    // Acceder a una variable del padre (si CLONE_VM está establecido)
    int *shared_var = (int *)arg;
    printf("Valor de la variable compartida: %d\n", *shared_var);
    (*shared_var)++; // Modificar la variable compartida
    printf("Proceso hijo terminando.\n");
    return 0;
}

int main() {
    // Pila para el proceso hijo
    size_t stack_size = 1024 * 1024; // 1MB
    char *stack = malloc(stack_size);
    if (!stack) {
        perror("malloc");
        exit(EXIT_FAILURE);
    }
    char *stack_top = stack + stack_size; // La pila crece hacia abajo

    int shared_variable = 10;

    struct clone_args args = {0};
    args.flags = CLONE_VM | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD; // Compartir VM, archivos, señales, hilo
    args.stack = (uintptr_t)stack_top;
    args.stack_size = stack_size;
    // args.child_tid se puede establecer si es necesario

    pid_t pid = clone3(&args);

    if (pid == -1) {
        perror("clone3");
        free(stack);
        exit(EXIT_FAILURE);
    } else if (pid == 0) {
        // Código ejecutado por el proceso hijo
        // En este ejemplo, la función child_function se llama directamente en el hilo principal
        // Si se usara CLONE_VM sin CLONE_THREAD, necesitaríamos crear un hilo separado
        // Para simplificar, aquí demostramos el acceso a la memoria compartida
        printf("Proceso hijo (PID: %ld) ejecutándose.\n", (long)getpid());
        int *shared_var_ptr = (int *)args.child_tid; // Usando child_tid como puntero a la variable compartida para este ejemplo
        child_function(shared_var_ptr);
        // El hijo debe llamar a exit() o ser terminado para que el padre no lo herede
        exit(EXIT_SUCCESS);
    } else {
        // Código ejecutado por el proceso padre
        printf("Proceso padre (PID: %ld) creó un hijo con PID: %d\n", (long)getpid(), pid);

        // Si se establece CLONE_VM, necesitamos pasar un puntero a la variable compartida
        // para que el hijo pueda acceder y modificarla.
        // Una forma común es usar el campo child_tid para pasar el puntero, pero esto es
        // un uso no estándar. En un escenario real, podrías usar IPC o memoria compartida explícita.
        // Para este ejemplo simplificado, vamos a pasar la dirección de shared_variable.
        // Nota: Esto requiere que el padre espere al hijo o que la variable persista.
        // Un uso más robusto implicaría memoria mapeada (mmap).
        // Aquí, para el ejemplo, reinicializamos args.child_tid para que actúe como puntero.
        // Esto es solo para fines demostrativos y puede no ser seguro en todos los casos.
        args.child_tid = (uintptr_t)&shared_variable;
        
        // Esperar a que el proceso hijo termine
        waitpid(pid, NULL, 0);

        printf("Proceso hijo (PID: %d) ha terminado.\n", pid);
        printf("Valor final de la variable compartida en el padre: %d\n", shared_variable);
        
        free(stack);
        exit(EXIT_SUCCESS);
    }

    return 0;
}
