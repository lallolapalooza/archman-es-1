CURLOPT_FOLLOWLOCATION(3)

Paquete: curl

Licencias: MIT

CURLOPT_FOLLOWLOCATION(3) Manual de Funciones de Biblioteca CURLOPT_FOLLOWLOCATION(3)

NOMBRE

CURLOPT_FOLLOWLOCATION - seguir redirecciones HTTP 3xx

SINOPSIS

#include <curl/curl.h>
CURLcode curl_easy_setopt(CURL *handle, CURLOPT_FOLLOWLOCATION, long mode);

DESCRIPCIÓN

Esta opción le indica a la biblioteca que siga Location: header las redirecciones que un servidor HTTP envía en una respuesta 30x. El encabezado Location: header puede especificar una URL relativa o absoluta a seguir. El parámetro largo mode indica cómo debe comportarse libcurl en las solicitudes posteriores.

mode solo tenía un único valor (1L) durante mucho tiempo que habilitaba el seguimiento de redirecciones. Desde la versión 8.13.0, también se admiten dos modos adicionales. Vea más abajo.

Al seguir redirecciones, libcurl emite otra solicitud para la nueva URL y sigue las nuevas Location: redirecciones posteriores hasta que no se devuelvan más encabezados de este tipo o se alcance el límite máximo. CURLOPT_MAXREDIRS(3) se utiliza para limitar el número de redirecciones que libcurl sigue.

libcurl restringe los protocolos a los que sigue automáticamente las redirecciones. Los protocolos de destino aceptados se establecen con CURLOPT_REDIR_PROTOCOLS_STR(3). De forma predeterminada, libcurl permite HTTP, HTTPS, FTP y FTPS en las redirecciones.

Al seguir una redirección, el código de respuesta 30x específico también dicta qué método de solicitud utiliza libcurl en la solicitud posterior: para las respuestas 301, 302 y 303, libcurl cambia el método de POST a GET a menos que CURLOPT_POSTREDIR(3) indique a libcurl lo contrario. Todos los demás códigos de respuesta de redirección hacen que libcurl use el mismo método nuevamente.

Cuando libcurl cambia el método a GET, luego usa ese método sin enviar ningún cuerpo de solicitud. Si no cambia el método, envía la solicitud posterior de la misma manera que la anterior; incluyendo el cuerpo de solicitud si se proporcionó uno.

Para los usuarios que piensan que el seguimiento de ubicaciones existente es demasiado ingenuo, demasiado simple o simplemente carece de funciones, es fácil implementar en su lugar su propia lógica de seguimiento de redirecciones con el uso de curl_easy_getinfo(3)'s CURLINFO_REDIRECT_URL(3) opción en lugar de usar CURLOPT_FOLLOWLOCATION(3).

De forma predeterminada, libcurl solo envía Authentication: o los encabezados establecidos explícitamente Cookie: al host inicial dado en la URL original, para evitar filtrar el nombre de usuario y la contraseña a otros sitios. CURLOPT_UNRESTRICTED_AUTH(3) se proporciona para cambiar ese comportamiento.

Debido a la forma en que funciona HTTP, casi cualquier encabezado puede contener datos que un cliente puede no querer pasar a otros servidores que no sean el host inicialmente previsto, y para todos los demás encabezados que no sean los dos mencionados anteriormente, no hay protección contra esto cuando se le indica a libcurl que siga las redirecciones.

Elija uno de los siguientes modos:

CURLFOLLOW_ALL (1)
Antes de la versión 8.13.0, este bit no tenía nombre y 1L era simplemente el valor para habilitar esta opción. Esto hace que el método personalizado establecido se use en todas las solicitudes HTTP, incluso después de las redirecciones.
CURLFOLLOW_OBEYCODE (2)
Cuando hay un método de solicitud personalizado establecido con CURLOPT_CUSTOMREQUEST(3), ese método establecido reemplaza lo que libcurl usaría de otro modo. Si se devuelve un código de respuesta 301/302/303 para señalar una redirección, el método se cambia de POST a GET. Para 307/308, el método personalizado permanece establecido y se usa.

Tenga en cuenta que solo POST (o un post personalizado) se cambia a GET en 301/302, no se cambia PUT, etc., y por lo tanto tampoco cuando libcurl emite un PUT personalizado. Una respuesta 303 hace que cambie a GET independientemente del método original (excepto para HEAD).

Para controlar para cuál de los códigos de estado 301/302/303 libcurl debería no cambiar de nuevo a GET al hacer un POST personalizado, y en su lugar mantener el método personalizado, use CURLOPT_POSTREDIR(3).

Si prefiere que un método POST personalizado se restablezca exactamente al método POST, use CURLFOLLOW_FIRSTONLY en su lugar.

CURLFOLLOW_FIRSTONLY (3)
Cuando hay un método de solicitud personalizado establecido con CURLOPT_CUSTOMREQUEST(3), ese método establecido reemplaza lo que libcurl usaría de otro modo solo en la primera solicitud saliente. La segunda solicitud se realiza entonces según el código de respuesta de redirección.

Si prefiere que su método personalizado permanezca en uso después de una redirección 307/308, use CURLFOLLOW_OBEYCODE en su lugar.

NOTA

Dado que libcurl cambia o no el método basándose en el código de respuesta HTTP específico, establecer CURLOPT_CUSTOMREQUEST(3) mientras se siguen las redirecciones puede cambiar lo que libcurl haría de otro modo y si no se tiene cuidado, puede incluso hacer que se comporte mal, ya que CURLOPT_CUSTOMREQUEST(3) anula el método que libcurl seleccionaría internamente de otro modo.

Establecer el bit CURLFOLLOW_OBEYCODE hace que libcurl no use el método personalizado establecido después de las redirecciones para las respuestas 301, 302 y 303. A menos que los bits CURLOPT_POSTREDIR(3) estén establecidos para esos códigos de estado.

POR DEFECTO

0, deshabilitado

PROTOCOLOS

Esta funcionalidad afecta solo a http

EJEMPLO

int main(void)
{
  CURL *curl = curl_easy_init();
  if(curl) {
    curl_easy_setopt(curl, CURLOPT_URL, "https://example.com");
    /* example.com es redirigido, así que le decimos a libcurl que siga la redirección */
    curl_easy_setopt(curl, CURLOPT_FOLLOWLOCATION, 1L);
    curl_easy_perform(curl);
  }
}

DISPONIBILIDAD

Añadido en curl 7.1

VALOR DE RETORNO

curl_easy_setopt(3) devuelve un CURLcode que indica éxito o error.

CURLE_OK (0) significa que todo estaba bien, un valor distinto de cero significa que ocurrió un error, vea libcurl-errors(3).
