DESCRIPCIÓ

N

CREATE SUBSCRIPTION añade una nueva suscripción de replicación lógica. El usuario que crea la suscripción se convierte en el propietario de la suscripción. El nombre de la suscripción debe ser distinto del nombre de cualquier suscripción existente en la base de datos

actual.

Una suscripción representa una conexión de replicación al publicador. Por lo tanto, además de añadir definiciones en los catálogos locales, este comando normalmente crea una ranura de replicación en el

publicador.

Se iniciará un trabajador de replicación lógica para replicar datos para la nueva suscripción en la confirmación de la transacción donde se ejecuta este comando, a menos que la suscripción esté inicialmente

deshabilitada.

Para poder crear una suscripción, debes tener los privilegios del rol pg_create_subscription, así como los privilegios CREATE en la base de datos

actual.

Hay información adicional sobre suscripcion

es y replicación lógica en general disp
onible en la Sección 29.2 y el Capítulo 29.

Esta cláusula especifica parámetros opcionales para una suscripción.

Los siguientes parámetros controlan lo que sucede durante la creación de la

suscripción:

connect

(boolean)
Especifica si el comando CREATE SUBSCRIPTION debe conectarse al publicador o no. El valor predeterminado es true. Establecer esto en false forzará los valores de create_slot, enabled y copy_data a false. (No puedes combinar la configuración de connect en false con la configuración de create_slot, enabled o copy_data en true.)

Dado que no se realiza ninguna conexión cuando esta opción es false, no se suscribe ninguna tabla. Para ini

ciar la replicación, debes crear manualmente la ranura de replicación, habilitar el failover si es necesar
io, habilitar la suscripción y actualizar la suscripción. Consulta la Sección 29.2.3 para ver ejemplos.

create_slot

(boolean)
Especifica si el comando debe crear la ranura de replicación en el publicador. El valor predeterminado es true.

Si se establece en false, tú eres responsable de cre

ar la ranura del publicador de alguna otra maner
a. Consulta la Sección 29.2.3 para ver ejemplos.

enabled

(boolean)
Especifica si la suscripción debe estar replicando activamente o si solo debe configurarse pero no iniciarse aún. El valor predeterminado es
true.

slot_name

(string)
Nombre de la ranura de replicación del publicador a usar. El valor predeterminado es usar el nombre de la suscripción como nombre de la ranura.

Establecer slot_name en NONE significa que no habrá ninguna ranura de replicación asociada con la suscripción. Dichas suscripciones también deben tener tanto enabled como create_slot establecidos en false. Usa esto cuando crearás la ranura de replicación más adelante manualmente. Consulta la Sección 29.2.3 para ver

ejemplos.

Al establecer slot_name en un nombre válido y create_slot en false, el valor de la propiedad failover de la ranura nombrada puede diferir del parámetro failover correspondiente especificado en la suscripción. Asegúrate siempre de que la propiedad f

ailover de la ranura coincida con el parámetro correspondiente de la suscripción y viceversa. De lo contrario, la ranura en el publicador puede comportarse de manera diferente a lo que dicen estas opciones de suscripción: por ejemplo, la ranura en
el publicador podría sincronizarse con los standbys incluso cuando la opción failover de la suscripción esté deshabilitada, o podría estar deshabilitada para la sincronización incluso cuando la opción failover de la suscripción esté habilitada.

Los siguientes parámetros controlan el comportamiento de replicación de la suscripción después de haber sido

creada:

binary

(boolean)
Especifica si la suscripción solicitará al publicador enviar los datos en formato binario (en lugar de texto). El valor predeterminado es false. Cualquier copia de sincronización inicial de tablas (ver copy_data) también usa el mismo formato. El formato binario puede ser más rápido que el formato de texto, pero es menos portable entre arquitecturas de máquinas y versiones de PostgreSQL. El formato binario es muy específico del tipo de dato; por ejemplo, no permitirá copiar de una columna smallint a una columna integer, aunque eso funcionaría bien en formato de texto. Incluso cuando esta opción está habilitada, solo los tipos de datos que tienen funciones de envío y recepción binarias se transferirán en binario. Ten en cuenta que la sincronización inicial requiere que todos los tipos de datos tengan funciones de envío y recepción binarias, de lo contrario la sincronización fallará (consulta CREATE TYPE (CREATE_TYPE(7)) para más información sobre las funciones de envío/recepción).

Al hacer replicación entre versiones, podría ser que el publicador tenga una función de envío binario para algún tipo de dato, pero el suscriptor carezca de una función de recepción binaria para ese tipo. En tal caso, la transferencia de datos fallará, y la opción binary no se puede

usar.

Si el publicador es una versión de PostgreSQL anterior a

16, entonces cualquier sincronización inicial de tab
las usará formato de texto incluso si binary = true.

copy_data

(boolean)
Especifica si copiar datos preexistentes en las publicaciones a las que se está suscribiendo cuando comienza la replicación. El valor predeterminado es true.

Si las publicaciones contienen cláusulas WHERE, esto afectará qué datos se copian. Consulta las Notas para más

detalles.

Consulta las Notas para detalles de

cómo copy_data = true puede i
nteractuar con el parámetro origin.

streaming

(enum)
Especifica si habilitar el streaming de transacciones en curso para esta suscripción. El valor predeterminado es parallel, lo que significa que los cambios entrantes se aplican directamente a través de uno de los trabajadores de aplicación paralela, si están disponibles. Si no hay ningún trabajador de aplicación paralela libre para manejar transacciones en streaming, entonces los cambios se escriben en archivos temporales y se aplican después de que la transacción se confirme. Ten en cuenta que si ocurre un error en un trabajador de aplicación paralela, el LSN de finalización de la transacción remota podría no reportarse en el registro del servidor.

Precaución
Existe un riesgo de interbloqueo cuando los esquemas del publicador y el suscriptor difieren, aunque tales casos son raros. El trabajador de aplicación está equipado para reintentar estas transacciones automáticamente.
Si se establece en on, los cambios entrantes se escriben en archivos temporales y luego se aplican solo después de que la transacción se confirme en el publicador y sea recibida por el suscriptor.

Si se establece en off, todas las transacciones se d

ecodifican completamente en el publicador y sol
o entonces se envían al suscriptor como un todo.

synchronous_commit

(enum)
El valor de este parámetro anula la configuración de synchronous_commit dentro de los procesos del trabajador de aplicación de esta suscripción. El valor predeterminado es off.

Es seguro usar off para replicación lógica: Si el suscriptor pierde transacciones debido a una sincronización faltante, los datos se enviarán de nuevo desde el

publicador.

Una configuración diferente podría ser apropiada al hacer replicación lógica síncrona. Los trabajadores de replicación lógica reportan las posiciones de escritura y vaciado al publicador, y al usar replicación síncrona, el publicador esperará el vaciado real. Esto significa que establecer synchronous_commit para el suscriptor en off cuando la suscripción se usa para replicación síncrona podría aumentar la latencia para COMMIT en el publicador. En este escenario, puede ser ven

tajoso establecer synchrono
us_commit en local o superior.

two_phase

(boolean)
Especifica si la confirmación en dos fases está habilitada para esta suscripción. El valor predeterminado es false.

Cuando la confirmación en dos fases está habilitada, las transacciones preparadas se envían al suscriptor en el momento de PREPARE TRANSACTION, y se procesan como transacciones en dos fases en el suscriptor también. De lo contrario, las transacciones preparadas se envían al suscriptor solo cuando se confirman, y luego se procesan inmediatamente por el

suscriptor.

La implementación de la confirmación en dos fases requiere que la replicación haya finalizado con éxito la fase de sincronización inicial de tablas. Así que incluso cuando two_phase está habilitado para una suscription, el estado interno de dos fases permanece temporalmente "pendiente"

hasta que se complete la fase de inicialización. Consulte la columna subt
wophasestate de pg_subscription para conocer el estado real de dos fases.

disable_on_error

(boolean)
Especifica si la suscripción debe deshabilitarse automáticamente si los trabajadores de suscripción detectan algún error durante la replicación de datos desde el publicador. El valor predeterminado es
false.

password_required

(boolean)
Si se establece en true, las conexiones al publicador realizadas como resultado de esta suscripción deben usar autenticación por contraseña y la contraseña debe especificarse como parte de la cadena de conexión. Esta configuración se ignora cuando la suscripción es propiedad de un superusuario. El valor predeterminado es true. Solo los superusuarios pueden establecer este valor en
false.

run_as_owner

(boolean)
Si es true, todas las acciones de replicación se realizan como el propietario de la suscripción. Si es false, los trabajadores de replicación realizarán acciones en cada tabla como el propietario de esa tabla. Esta última configuración es generalmente mucho más segura; para más detalles, consulte la Sección 29.11. El valor predeterminado es
false.

origin

(string)
Especifica si la suscripción solicitará al publicador que envíe solo cambios que no tengan un origen o enviar cambios independientemente del origen. Establecer origin en none significa que la suscripción solicitará al publicador que envíe solo cambios que no tengan un origen. Establecer origin en any significa que el publicador envía cambios independientemente de su origen. El valor predeterminado es any.

Consulte Notas para detalles sobre

cómo copy_data = true puede intera

Especifica si los slots de replicación asociados con la suscripción están habilitados
para sincronizarse con los standbys de modo que la replicación lógica pueda reanuda
rse desde el nuevo primario después de un failover. El valor predeterminado es false.

NOTA

S

Consulte la Sección 29.11 para detalles sobre cómo configurar el control de acceso entre la suscripción y la instancia de

publicación.

Al crear un slot de replicación (el comportamiento predeterminado), CREATE SUBSCRIPTION no puede ejecutarse dentro de un bloque de

transacción.

Crear una suscripción que se conecte al mismo clúster de bases de datos (por ejemplo, para replicar entre bases de datos en el mismo clúster o para replicar dentro de la misma base de datos) solo tendrá éxito si el slot de replicación no se crea como parte del mismo comando. De lo contrario, la llamada a CREATE SUBSCRIPTION se colgará. Para que esto funcione, cree el slot de replicación por separado (usando la función pg_create_logical_replication_slot con el nombre del plugin pgoutput) y cree la suscripción usando el parámetro create_slot = false. Consulte la Sección 29.2.3 para ejemplos. Esta es una restricción de implementación que podría eliminarse en una versión

futura.

Si alguna tabla en la publicación tiene una cláusula WHERE, las filas para las cuales la expresión evalúa a false o NULL no se publicarán. Si la suscripción tiene varias publicaciones en las que la misma tabla se ha publicado con diferentes cláusulas WHERE, una fila se publicará si alguna de las expresiones (refiriéndose a esa operación de publicación) se cumple. En el caso de diferentes cláusulas WHERE, si una de las publicaciones no tiene cláusula WHERE (refiriéndose a esa operación de publicación) o la publicación está declarada como FOR ALL TABLES o FOR TABLES IN SCHEMA, las filas siempre se publican independientemente de la definición de las otras expresiones. Si el suscriptor es una versión de PostgreSQL anterior a la 15, entonces cualquier filtrado de filas se ignora durante la fase de sincronización inicial de datos. Para este caso, el usuario podría querer considerar eliminar cualquier dato copiado inicialmente que sería incompatible con el filtrado posterior. Debido a que la sincronización inicial de datos no tiene en cuenta el parámetro publish de la publicación al copiar los datos existentes de la tabla, algunas filas podrían copiarse que no se replicarían usando DML. Consulte la Sección 29.2.2 para

ejemplos.

No se admiten suscripciones que tengan varias publicaciones en las que la misma tabla se haya publicado con diferentes listas de

columnas.

Permitimos especificar publicaciones que no existen para que los usuarios puedan añadirlas más adelante. Esto significa que pg_subscription puede tener publicaciones que no

existen.

Al usar una combinación de parámetros de suscripción de copy_data = true y origin = NONE, los datos de la tabla de sincronización inicial se copian directamente desde el publicador, lo que significa que no es posible conocer el verdadero origen de esos datos. Si el publicador también tiene suscripciones, entonces los datos de la tabla copiados podrían haberse originado más arriba en la cadena. Este escenario se detecta y se registra una ADVERTENCIA al usuario, pero la advertencia es solo una indicación de un problema potencial; es responsabilidad del usuario realizar las comprobaciones necesarias para asegurarse de que los orígenes de los datos copiados sean realmente los deseados o

no.

Para encontrar qué tablas podrían potencialmente incluir orígenes no locales (debido a otras suscripciones creadas en el publicador) intente esta consulta

SQL: 
# sustituya <pub-names> a continuación con el nombre(s) de su(s) publicación(es) a consultar
SELECT DISTINCT PT.schemaname, PT.tablename
FROM pg_publication_tables PT JOIN pg_class C ON (C.relname = PT.tablename) JOIN pg_namespace N ON (N.nspname = PT.schemaname
), pg_subscription_rel PS WHERE C.relnamespace = N.oid AND (PS.srrelid = C.oid OR C.oid IN (SELECT relid FROM pg_partit
ion_ancestors(PS.srrelid) UNION SELECT relid FROM pg_partition_tree(PS.srrelid))) AND PT.pubname IN (<pub-names>);
