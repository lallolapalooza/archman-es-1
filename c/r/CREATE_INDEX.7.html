Un campo de índice puede ser una expresión calculada a partir de los valores de una o más columnas de la fila de la tabla. Esta característica se puede utilizar para obtener acceso rápido a datos basado en alguna transformación de los datos básicos. Por ejemplo, un índice calculado en upper(col) permitiría que la cláusula WHERE upper(col) = 'JIM' use un

índice.

PostgreSQL proporciona los métodos de índice B-tree, hash, GiST, SP-GiST, GIN y BRIN. Los usuarios también pueden definir sus propios métodos de índice, pero eso es bastante

complicado.

Cuando la cláusula WHERE está presente, se crea un índice parcial. Un índice parcial es un índice que contiene entradas solo para una porción de una tabla, generalmente una porción que es más útil para indexar que el resto de la tabla. Por ejemplo, si tiene una tabla que contiene tanto pedidos facturados como no facturados, donde los pedidos no facturados ocupan una pequeña fracción de la tabla total y sin embargo esa es una sección frecuentemente utilizada, puede mejorar el rendimiento creando un índice solo en esa porción. Otra posible aplicación es usar WHERE con UNIQUE para imponer unicidad sobre un subconjunto de una tabla. Vea la Sección 11.8 para más

discusión.

La expresión usada en la cláusula WHERE puede referirse solo a columnas de la tabla subyacente, pero puede usar todas las columnas, no solo las que están siendo indexadas. Actualmente, las subconsultas y las expresiones de agregación también están prohibidas en WHERE. Las mismas restricciones se aplican a los campos de índice que son

expresiones.

Todas las funciones y operadores usados en una definición de índice deben ser “inmutables”, es decir, sus resultados deben depender solo de sus argumentos y nunca de ninguna influencia externa (como el contenido de otra tabla o la hora actual). Esta restricción asegura que el comportamiento del índice esté bien definido. Para usar una función definida por el usuario en una expresión de índice o en una cláusula WHERE, recuerde marcar la función como inmutable cuando la

cree.

La cláusula opcional INCLUDE especifica una lista de columnas que serán incluidas en el índice como columnas no clave. Una columna no clave no puede usarse en una calificación de búsqueda de escaneo de índice, y se ignora para los propósitos de cualquier restricción de unicidad o exclusión impuesta por el índice. Es prudente ser conservador al agregar columnas no clave a un índice, especialmente columnas anchas. Si una tupla de índice excede el tamaño máximo permitido para el tipo de índice, la inserción de datos fallará. clave.

Parámetros de almacenamiento del índice

La cláusula opcional `WITH` especifica parámetros de almacenamiento para el índice. Cada método de índice tiene su propio conjunto de parámetros de almacenamiento permitidos.

Los métodos de índice B-tree, hash, GiST y SP-GiST aceptan todos este parámetro:

`fillfactor` (entero)

Controla qué tan lleno intentará el método de índice empaquetar las páginas del índice. Para los B-trees, las páginas de hoja se llenan hasta este porcentaje durante las construcciones iniciales del índice, y también al extender el índice por la derecha (añadiendo nuevos valores de clave más grandes). Si las páginas se vuelven completamente llenas posteriormente, se dividirán, lo que lleva a la fragmentación de la estructura del índice en disco. Los B-trees usan un `fillfactor` predeterminado de 90, pero se puede seleccionar cualquier valor entero de 10 a 100.

Los índices B-tree en tablas donde se anticipan muchas inserciones y/o actualizaciones pueden beneficiarse de configuraciones de `fillfactor` más bajas en el momento de `CREATE INDEX` (siguiendo la carga masiva en la tabla). Valores en el rango de 50 - 90 pueden “suavizar” útilmente la tasa de divisiones de páginas durante la vida temprana del índice B-tree (reducir el `fillfactor` así puede incluso reducir el número absoluto de divisiones de páginas, aunque este efecto depende en gran medida de la carga de trabajo). La técnica de eliminación de índices B-tree de abajo hacia arriba descrita en la Sección 65.1.4.2 depende de tener algo de espacio “extra” en las páginas para almacenar versiones de tuplas “extra”, y por lo tanto puede verse afectada por el `fillfactor` (aunque el efecto generalmente no es significativo).

En otros casos específicos podría ser útil aumentar el `fillfactor` a 100 en el momento de `CREATE INDEX` como una forma de maximizar la utilización del espacio. Solo debería considerarse esto cuando esté completamente seguro de que la tabla es estática (es decir, que nunca se verá afectada por inserciones ni actualizaciones). Una configuración de `fillfactor` de 100 de lo contrario arriesga dañar el rendimiento: incluso unas pocas actualizaciones o inserciones causarán una inundación repentina de divisiones de páginas.

Los otros métodos de índice usan el `fillfactor` de diferentes pero aproximadamente análogas maneras; el `fillfactor` predeterminado varía entre métodos.

Los índices B-tree aceptan adicionalmente este parámetro:

`deduplicate_items` (booleano)

Controla el uso de la técnica de deduplicación B-tree descrita en la Sección 65.1.4.3. Establezca en `ON` u `OFF` para habilitar o deshabilitar la optimización. (Se permiten grafías alternativas de `ON` y `OFF` como se describe en la Sección 19.1.) El predeterminado es `ON`.

Nota
Desactivar `deduplicate_items` vía `ALTER INDEX` previene que futuras inserciones activen la deduplicación, pero no por sí mismo hace que las tuplas de listas de publicación existentes usen la representación estándar de tupla.

Los índices GiST aceptan adicionalmente este parámetro:

`buffering` (enum)

Controla si se usa la técnica de construcción con búfer descrita en la Sección 65.2.4.1 para construir el índice. Con `OFF` el búfer está deshabilitado, con `ON` está habilitado, y con `AUTO` inicialmente está deshabilitado, pero se activa dinámicamente una vez que el tamaño del índice alcanza `effective_cache_size`. El predeterminado es `AUTO`. Note que si la construcción ordenada es posible, se usará en lugar de la construcción con búfer a menos que se especifique `buffering=ON`.

Los índices GIN aceptan estos parámetros:

`fastupdate` (booleano)

Controla el uso de la técnica de actualización rápida descrita en la Sección 65.4.4.1. `ON` habilita la actualización rápida, `OFF` la deshabilita. El predeterminado es `ON`.

Nota
Desactivar `fastupdate` vía `ALTER INDEX` previene que futuras inserciones vayan a la lista de entradas de índice pendientes, pero no por sí mismo vacía las entradas existentes. Podría querer `VACUUM` la tabla o llamar a la función `gin_clean_pending_list` después para asegurarse de que la lista pendiente se vacíe.

`gin_pending_list_limit` (entero)

Anula la configuración global de `gin_pending_list_limit` para este índice. Este valor se especifica en kilobytes.

Los índices BRIN aceptan estos parámetros:

`pages_per_range` (entero)

Define el número de bloques de tabla que componen un rango de bloques para cada entrada de un índice BRIN (vea la Sección 65.5.1 para más detalles). El predeterminado es 128.

`autosummarize` (booleano)

Define si se encola una ejecución de resumen para el rango de páginas anterior siempre que se detecta una inserción en el siguiente (vea la Sección 65.5.1.1 para más detalles). El predeterminado es `off`.

Construyendo índices concurrentemente

Crear un índice puede interferir con la operación regular de una base de datos. Normalmente PostgreSQL bloquea la tabla a indexar contra escrituras y realiza toda la construcción del índice con un solo escaneo de la tabla. Otras transacciones aún pueden leer la tabla, pero si intentan insertar, actualizar o eliminar filas en la tabla se bloquearán hasta que la construcción del índice termine. Esto podría tener un efecto severo si el sistema es una base de datos de producción activa. Tablas muy grandes pueden tomar muchas horas en indexarse, e incluso para tablas más pequeñas, una construcción de índice puede bloquear a los escritores por períodos inaceptablemente largos para un sistema de producción.

PostgreSQL soporta construir índices sin bloquear escrituras. Este método se invoca especificando la opción `CONCURRENTLY` de `CREATE INDEX`. Cuando se usa esta opción, PostgreSQL debe realizar dos escaneos de la tabla, y además debe esperar a que todas las transacciones existentes que podrían potencialmente modificar o usar el índice terminen. Por lo tanto este método requiere más trabajo total que una construcción de índice estándar y toma significativamente más tiempo en completarse. Sin embargo, ya que permite que las operaciones normales continúen mientras se construye el índice, este método es útil para añadir nuevos índices en un entorno de producción. Por supuesto, la carga extra de CPU y E/S impuesta por la creación del índice podría ralentizar otras operaciones.

En una construcción de índice concurrente, el índice se registra realmente como un índice “inválido” en los catálogos del sistema en una transacción, luego ocurren dos escaneos de la tabla en dos transacciones más. Antes de cada escaneo de la tabla, la construcción del índice debe esperar a que las transacciones existentes que han modificado la tabla terminen. Después del segundo escaneo, la construcción del índice debe esperar a que terminen cualquier transacción que tenga una instantánea (vea el Capítulo 13) que preceda al segundo escaneo, incluyendo transacciones usadas por cualquier fase de construcciones de índices concurrentes en otras tablas, si los índices involucrados son parciales o tienen columnas que no son referencias simples de columna. Entonces finalmente el índice puede marcarse como “válido” y listo para usar, y el `CREATE INDEX` comando termina. Incluso entonces, sin embargo, el índice puede no ser inmediatamente utilizable para consultas: en el peor caso, no puede usarse mientras existan transacciones que precedan al inicio de la construcción del índice.

Si surge un problema mientras se escanea la tabla, como un interbloqueo o una violación de unicidad en un índice único, el `CREATE INDEX` comando fallará pero dejará un índice “inválido”. Este índice será ignorado para propósitos de consulta porque podría estar incompleto; sin embargo aún consumirá sobrecarga de actualización. El comando psql `\d` reportará tal índice como `INVALID`:

postgres=# \d tab
       Table "public.tab"
 Column |  Type   | Collation | Nullable | Default
--------+---------+-----------+----------+---------
 col    | integer |           |          |
Indexes:
    "idx" btree (col) INVALID

El método de recuperación recomendado en tales casos es eliminar el índice e intentar nuevamente realizar `CREATE INDEX CONCURRENTLY`. (Otra posibilidad es reconstruir el índice con `REINDEX INDEX CONCURRENTLY`).

Otra advertencia al construir un índice único concurrentemente es que la restricción de unicidad ya se está aplicando contra otras transacciones cuando comienza el segundo escaneo de la tabla. Esto significa que las violaciones de restricción podrían reportarse en otras consultas antes de que el índice esté disponible para usar, o incluso en casos donde la construcción del índice eventualmente falle. Además, si ocurre un fallo en el segundo escaneo, el índice “inválido” continúa aplicando su restricción de unicidad después.

Se soportan construcciones concurrentes de índices de expresión e índices parciales. Los errores que ocurran en la evaluación de estas expresiones podrían causar un comportamiento similar al descrito arriba para violaciones de restricciones de unicidad.

Las construcciones regulares de índice permiten que otras construcciones regulares de índice en la misma tabla ocurran simultáneamente, pero solo una construcción de índice concurrente puede ocurrir en una tabla a la vez. En cualquier caso, la modificación de esquema de la tabla no está permitida mientras se está construyendo el índice. Otra diferencia es que un `CREATE INDEX` comando regular puede realizarse dentro de un bloque de transacción, pero `CREATE INDEX CONCURRENTLY` no.

Actualmente no se soportan construcciones concurrentes para índices en tablas particionadas. Sin embargo, puede construir concurrentemente el índice en cada partición individualmente y luego finalmente crear el índice particionado no concurrentemente para reducir el tiempo en que las escrituras a la tabla particionada serán bloqueadas. En este caso, construir el índice particionado es una operación solo de metadatos.

NOTAS

Vea el Capítulo 11 para información sobre cuándo pueden usarse los índices, cuándo no se usan, y en qué situaciones particulares pueden ser útiles.

Actualmente, solo los métodos de índice B-tree, GiST, GIN y BRIN soportan índices de múltiples columnas clave. Si puede haber múltiples columnas clave es independiente de si se pueden añadir columnas `INCLUDE` al índice. Los índices pueden tener hasta 32 columnas, incluyendo columnas `INCLUDE`. (Este límite puede alterarse al compilar PostgreSQL.) Solo B-tree actualmente soporta índices únicos.

Se puede especificar una clase de operador con parámetros opcionales para cada columna de un índice. La clase de operador identifica los operadores a ser usados por el índice para esa columna. Por ejemplo, un índice B-tree sobre enteros de cuatro bytes usaría la clase `int4_ops`; esta clase de operadores incluye funciones de comparación para enteros de cuatro bytes. En la práctica la clase de operador predeterminada para el tipo de datos de la columna generalmente es suficiente. El punto principal de tener clases de operadores es que para algunos tipos de datos, podría haber más de un ordenamiento significativo. Por ejemplo, podríamos querer ordenar un tipo de datos de número complejo ya sea por valor absoluto o por parte real. Podríamos hacer esto definiendo dos clases de operadores para el tipo de datos y luego seleccionando la clase apropiada al crear un índice. Más información sobre Las clases de operadores se encuentran en la Sección 11.10 y en la Sección 36.16.

Cuando se invoca CREATE INDEX en una tabla particionada, el comportamiento por defecto es recurrir a todas las particiones para asegurarse de que todas tengan índices coincidentes. Primero se verifica cada partición para determinar si ya existe un índice equivalente, y si es así, ese índice se adjuntará como índice de partición al índice que se está creando, el cual se convertirá en su índice principal. Si no existe un índice coincidente, se creará un nuevo índice y se adjuntará automáticamente; el nombre del nuevo índice en cada partición se determinará como si no se hubiera especificado ningún nombre de índice en el comando. Si se especifica la opción ONLY, no se realiza ninguna recursión y el índice se marca como inválido. (ALTER INDEX ... ATTACH PARTITION marca el índice como válido, una vez que todas las particiones adquieren índices coincidentes.) Sin embargo, ten en cuenta que cualquier partición que se cree en el futuro usando CREATE TABLE ... PARTITION OF tendrá automáticamente un índice coincidente, independientemente de si se especifica ONLY o no.

Para los métodos de índice que admiten escaneos ordenados (actualmente, solo B-tree), se pueden especificar las cláusulas opcionales ASC, DESC, NULLS FIRST y/o NULLS LAST para modificar el orden de clasificación del índice. Dado que un índice ordenado se puede escanear tanto hacia adelante como hacia atrás, normalmente no es útil crear un índice de una sola columna DESC; esa ordenación ya está disponible con un índice regular. El valor de estas opciones es que se pueden crear índices multicolumna que coincidan con el orden de clasificación solicitado por una consulta de orden mixto, como SELECT ... ORDER BY x ASC, y DESC. Las opciones NULLS son útiles si necesitas admitir el comportamiento de "los nulos se ordenan bajo", en lugar del comportamiento por defecto de "los nulos se ordenan alto", en consultas que dependen de índices para evitar pasos de ordenación.

El sistema recopila regularmente estadísticas sobre todas las columnas de una tabla. Los índices de no expresión recién creados pueden usar estas estadísticas inmediatamente para determinar la utilidad de un índice. Para los nuevos índices de expresión, es necesario ejecutar ANALYZE o esperar a que el demonio autovacuum analice la tabla para generar estadísticas para estos índices.

Mientras CREATE INDEX se está ejecutando, el search_path se cambia temporalmente a pg_catalog, pg_temp.

Para la mayoría de los métodos de índice, la velocidad de creación de un índice depende de la configuración de maintenance_work_mem. Valores más grandes reducirán el tiempo necesario para la creación del índice, siempre que no lo hagas más grande que la cantidad de memoria realmente disponible, lo que llevaría a la máquina a usar el espacio de intercambio (swap).

PostgreSQL puede construir índices aprovechando múltiples CPU para procesar las filas de la tabla más rápido. Esta función se conoce como construcción de índice en paralelo. Para los métodos de índice que admiten la construcción de índices en paralelo (actualmente, B-tree, GIN y BRIN), maintenance_work_mem especifica la cantidad máxima de memoria que puede usar cada operación de construcción de índice en su conjunto, independientemente de cuántos procesos de trabajo se hayan iniciado. Generalmente, un modelo de costes determina automáticamente cuántos procesos de trabajo se deben solicitar, si es que se necesitan.

Las construcciones de índice en paralelo pueden beneficiarse de un aumento de maintenance_work_mem donde una construcción de índice serial equivalente vería poco o ningún beneficio. Ten en cuenta que maintenance_work_mem puede influir en el número de procesos de trabajo solicitados, ya que los trabajadores en paralelo deben tener al menos una participación de 32MB del total del presupuesto de maintenance_work_mem . También debe haber una participación restante de 32MB para el proceso líder. Aumentar max_parallel_maintenance_workers puede permitir el uso de más trabajadores, lo que reducirá el tiempo necesario para la creación del índice, siempre que la construcción del índice no esté limitada por la E/S. Por supuesto, también debe haber suficiente capacidad de CPU que de otro modo estaría inactiva.

Establecer un valor para parallel_workers mediante ALTER TABLE controla directamente cuántos procesos de trabajo en paralelo se solicitarán por un CREATE INDEX contra la tabla. Esto evita por completo el modelo de costes e impide que maintenance_work_mem influya en cuántos trabajadores en paralelo se solicitan. Establecer parallel_workers a 0 mediante ALTER TABLE desactivará las construcciones de índice en paralelo en la tabla en todos los casos.


Consejo

Es posible que desees restablecer parallel_workers después de establecerlo como parte de la optimización de una construcción de índice. Esto evita cambios inadvertidos en los planes de consulta, ya que parallel_workers afecta a todos los escaneos de tablas en paralelo.

Mientras CREATE INDEX con la opción CONCURRENTLY admite construcciones en paralelo sin restricciones especiales, solo el primer escaneo de la tabla se realiza realmente en paralelo.

Usa DROP INDEX para eliminar un índice.

Como cualquier transacción de larga duración, CREATE INDEX en una tabla puede afectar a qué tuplas pueden ser eliminadas por un VACUUM concurrente en cualquier otra tabla.

Las versiones anteriores de PostgreSQL también tenían un método de índice R-tree. Este método se ha eliminado porque no tenía ventajas significativas sobre el método GiST. Si se especifica USING rtree, CREATE INDEX lo interpretará como USING gist, para simplificar la conversión de bases de datos antiguas a GiST.

Cada backend que ejecute CREATE INDEX informará de su progreso en la vista pg_stat_progress_create_index. Consulta la Sección 27.4.4 para obtener más detalles.

EJEMPLOS

Para crear un índice B-tree único en la columna title de la tabla films:

CREATE UNIQUE INDEX title_idx ON films (title);

Para crear un índice B-tree único en la columna title con las columnas incluidas director y rating en la tabla films:

CREATE UNIQUE INDEX title_idx ON films (title) INCLUDE (director, rating);

Para crear un índice B-Tree con la deduplicación desactivada:

CREATE INDEX title_idx ON films (title) WITH (deduplicate_items = off);

Para crear un índice sobre la expresión lower(title), permitiendo búsquedas eficientes sin distinguir mayúsculas de minúsculas:

CREATE INDEX ON films ((lower(title)));

(En este ejemplo hemos optado por omitir el nombre del índice, por lo que el sistema elegirá uno, típicamente films_lower_idx.)

Para crear un índice con una regla de colación no predeterminada:

CREATE INDEX title_idx_german ON films (title COLLATE "de_DE");

Para crear un índice con un orden de clasificación de nulos no predeterminado:

CREATE INDEX title_idx_nulls_low ON films (title NULLS FIRST);

Para crear un índice con un factor de llenado no predeterminado:

CREATE UNIQUE INDEX title_idx ON films (title) WITH (fillfactor = 70);

Para crear un índice GIN con las actualizaciones rápidas desactivadas:

CREATE INDEX gin_idx ON documents_table USING GIN (locations) WITH (fastupdate = off);

Para crear un índice en la columna code de la tabla films y que el índice resida en el tablespace indexspace:

CREATE INDEX code_idx ON films (code) TABLESPACE indexspace;

Para crear un índice GiST en un atributo de punto para que podamos usar eficientemente los operadores de caja en el resultado de la función de conversión:

CREATE INDEX pointloc
    ON points USING gist (box(location,location));
SELECT * FROM points
    WHERE box(location,location) && '(0,0),(1,1)'::box;

Para crear un índice sin bloquear las escrituras en la tabla:

CREATE INDEX CONCURRENTLY sales_quantity_index ON sales_table (quantity);

COMPATIBILIDAD

CREATE INDEX es una extensión del lenguaje de PostgreSQL. El estándar SQL no tiene disposiciones para los índices.
