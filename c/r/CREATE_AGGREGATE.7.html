DESCRIPCIÓ

N

CREATE AGGREGATE define una nueva función de agregación. CREATE OR REPLACE AGGREGATE definirá una nueva función de agregación o reemplazará una definición existente. Algunas funciones de agregación básicas y de uso común se incluyen con la distribución; están documentadas en la Sección 9.21. Si se definen nuevos tipos o se necesita una función de agregación que aún no se proporciona, entonces CREATE AGGREGATE se puede usar para proporcionar las características

deseadas.

Al reemplazar una definición existente, los tipos de argumento, el tipo de resultado y el número de argumentos directos no pueden cambiarse. Además, la nueva definición debe ser del mismo tipo (agregado ordinario, agregado de conjunto ordenado o agregado de conjunto hipotético) que la

anterior.

Si se proporciona un nombre de esquema (por ejemplo, CREATE AGGREGATE myschema.myagg ...) entonces la función de agregación se crea en el esquema especificado. De lo contrario, se crea en el esquema

actual.

Una función de agregación se identifica por su nombre y su(s) tipo(s) de dato de entrada. Dos agregados en el mismo esquema pueden tener el mismo nombre si operan sobre diferentes tipos de entrada. El nombre y el/los tipo(s) de dato de entrada de un agregado también deben ser distintos del nombre y el/los tipo(s) de dato de entrada de cada función ordinaria en el mismo esquema. Este comportamiento es idéntico a la sobrecarga de nombres de funciones ordinarias (ver CREATE FUNCTION (CREATE_FUNCTION(7)))

.

Una función de agregación simple está hecha de una o dos funciones ordinarias: una función de transición de estado sfunc, y una función opcional de cálculo final ffunc. Se usan de la siguiente

manera: 
sfunc( estado_interno, valores_datos_siguientes ) ---> siguiente_estado_interno
ffunc( estado_interno
) ---> val
or_agregado

PostgreSQL crea una variable temporal del tipo de dato stype para mantener el estado interno actual del agregado. En cada fila de entrada, se calcula(n) el(los) valor(es) del argumento del agregado y se invoca la función de transición de estado con el valor de estado actual y el(los) nuevo(s) valor(es) del argumento para calcular un nuevo valor de estado interno. Después de que se han procesado todas las filas, se invoca la función final una vez para calcular el valor de retorno del agregado. Si no hay función final, entonces el valor de estado final se devuelve tal

cual.

Una función de agregación puede proporcionar una condición inicial, es decir, un valor inicial para el valor de estado interno. Esto se especifica y almacena en la base de datos como un valor de tipo text, pero debe ser una representación externa válida de una constante del tipo de dato del valor de estado. Si no se proporciona, entonces el valor de estado comienza siendo

null.

Si la función de transición de estado está declarada como “estricta”, entonces no puede ser llamada con entradas null. Con una función de transición así, la ejecución del agregado se comporta de la siguiente manera. Las filas con cualquier valor de entrada null se ignoran (la función no se llama y se retiene el valor de estado anterior). Si el valor de estado inicial es null, entonces en la primera fila con todos los valores de entrada no null, el primer valor del argumento reemplaza al valor de estado, y la función de transición se invoca en cada fila posterior con todos los valores de entrada no null. Esto es útil para implementar agregados como max. Nótese que este comportamiento solo está disponible cuando state_data_type es el mismo que el primer arg_data_type. Cuando estos tipos son diferentes, se debe proporcionar una condición inicial no null o usar una función de transición no

estricta.

Si la función de transición de estado no es estricta, entonces será llamada incondicionalmente en cada fila de entrada, y debe manejar por sí misma las entradas null y los valores de estado null. Esto permite al autor del agregado tener control total sobre el manejo de valores null del

agregado.

Si la función final está declarada como “estricta”, entonces no será llamada cuando el valor de estado final sea null; en su lugar, se devolverá automáticamente un resultado null. (Por supuesto, este es solo el comportamiento normal de las funciones estrictas.) En cualquier caso, la función final tiene la opción de devolver un valor null. Por ejemplo, la función final para avg devuelve null cuando detecta que hubo cero filas de

entrada.

A veces es útil declarar que la función final tome no solo el valor de estado, sino parámetros adicionales que correspondan a los valores de entrada del agregado. La razón principal para hacer esto es si la función final es polimórfica y el tipo de dato del valor de estado sería inadecuado para determinar el tipo de resultado. Estos parámetros adicionales siempre se pasan como NULL (y por lo tanto la función final no debe ser estricta cuando se usa la opción FINALFUNC_EXTRA), pero sin embargo son parámetros válidos. La función final podría, por ejemplo, hacer uso de get_fn_expr_argtype para identificar el tipo de argumento real en la llamada

actual.

Un agregado puede soportar opcionalmente el modo de agregado móvil, como se describe en la Sección 36.12.1. Esto requiere especificar los parámetros MSFUNC, MINVFUNC y MSTYPE, y opcionalmente los parámetros MSSPACE, MFINALFUNC, MFINALFUNC_EXTRA, MFINALFUNC_MODIFY y MINITCOND. Excepto para MINVFUNC, estos parámetros funcionan como los parámetros correspondientes del agregado simple sin la M; definen una implementación separada del agregado que incluye una función de transición

inversa.

La sintaxis con ORDER BY en la lista de parámetros crea un tipo especial de agregado llamado agregado de conjunto ordenado; o si se especifica HYPOTHETICAL, se crea un agregado de conjunto hipotético. Estos agregados operan sobre grupos de valores ordenados de maneras dependientes del orden, de modo que la especificación de un orden de entrada es una parte esencial de una llamada. Además, pueden tener argumentos directos, que son argumentos que se evalúan solo una vez por agregación en lugar de una vez por fila de entrada. Los agregados de conjunto hipotético son una subclase de los agregados de conjunto ordenados en la que algunos de los argumentos directos deben coincidir, en número y tipos de datos, con las columnas de argumento agregadas. Esto permite que los valores de esos argumentos directos se añadan a la colección de filas de entrada del agregado como una fila “hipotética”

adicional.

Un agregado puede soportar opcionalmente la agregación parcial, como se describe en la Sección 36.12.4. Esto requiere especificar el parámetro COMBINEFUNC. Si el state_data_type es internal, generalmente también es apropiado proporcionar los parámetros SERIALFUNC y DESERIALFUNC para que la agregación en paralelo sea posible. Nótese que el agregado también debe estar marcado como PARALLEL SAFE para habilitar la agregación en

paralelo. class="Pp">Los agregados que se comportan como MIN o MAX a veces pueden optimizarse mirando en un índice en lugar de escanear cada fila de entrada. Si este agregado puede optimizarse de esta manera, indíquelo especificando un operador de ordenación. El requisito básico es que el agregado debe producir el primer elemento en el orden de ordenación inducido por el operador; en otras

palabras: 
SELECT a
gg(col) F
ROM tab;

debe ser equivalente

a: 
SELECT col FROM ta
b ORDER BY col USI
NG sortop LIMIT 1;

Otras suposiciones son que el agregado ignora las entradas nulas, y que entrega un resultado nulo si y solo si no hubo entradas no nulas. Ordinariamente, el operador < de un tipo de datos es el operador de ordenación adecuado para MIN, y > es el operador de ordenación adecuado para MAX. Tenga en cuenta que la optimización nunca se aplicará realmente a menos que el operador especificado sea el miembro de estrategia “menor que” o “mayor que” de una clase de operadores de índice

B-tree.

Para poder crear una función de agregado, debe tener el privilegio USAG

E sobre los tipos de argumento, el/los tipo(s) de estado y el tipo de
retorno, así como el privilegio EXECUTE sobre las funciones de soporte.

NOTA

S

En los parámetros que especifican nombres de funciones de soporte, puede escribir un nombre de esquema si es necesario, por ejemplo SFUNC = public.sum. Sin embargo, no escriba tipos de argumento allí — los tipos de argumento de las funciones de soporte se determinan a partir de otros

parámetros.

Ordinariamente, se espera que las funciones de PostgreSQL sean funciones verdaderas que no modifican sus valores de entrada. Sin embargo, una función de transición agregada, cuando se usa en el contexto de un agregado, se le permite hacer trampa y modificar su argumento de estado de transición in situ. Esto puede proporcionar beneficios de rendimiento sustanciales en comparación con hacer una copia nueva del estado de transición cada

vez.

Del mismo modo, aunque normalmente se espera que una función final de agregado no modifique sus valores de entrada, a veces es impracticable evitar modificar el argumento de estado de transición. Dicho comportamiento debe declararse usando el parámetro FINALFUNC_MODIFY. El valor READ_WRITE indica que la función final modifica el estado de transición de maneras no especificadas. Este valor impide el uso del agregado como función de ventana, y también impide la fusión de estados de transición para llamadas a agregados que comparten los mismos valores de entrada y funciones de transición. El valor SHAREABLE indica que la función de transición no se puede aplicar después de la función final, pero se pueden realizar múltiples llamadas a la función final sobre el valor de estado de transición final. Este valor impide el uso del agregado como función de ventana, pero permite la fusión de estados de transición. (Es decir, la optimización de interés aquí no es aplicar la misma función final repetidamente, sino aplicar diferentes funciones finales al mismo valor de estado de transición final. Esto se permite siempre que ninguna de las funciones finales esté marcada como READ_WRITE.

)

Si un agregado soporta el modo de agregado móvil, mejorará la eficiencia de cálculo cuando el agregado se use como función de ventana para una ventana con inicio de marco móvil (es decir, un modo de inicio de marco diferente de UNBOUNDED PRECEDING). Conceptualmente, la función de transición directa agrega valores de entrada al estado del agregado cuando entran en el marco de la ventana desde abajo, y la función de transición inversa los elimina de nuevo cuando salen del marco por arriba. Así, cuando se eliminan valores, siempre se eliminan en el mismo orden en que se añadieron. Siempre que se invoque la función de transición inversa, recibirá así el/los valor(es) de argumento añadido(s) más temprano pero aún no eliminado(s). La función de transición inversa puede asumir que al menos una fila permanecerá en el estado actual después de que elimine la fila más antigua. (Cuando no fuera el caso, el mecanismo de función de ventana simplemente inicia una agregación nueva, en lugar de usar la función de transición inversa.

)

La función de transición directa para el modo de agregado móvil no está permitida que devuelva NULL como nuevo valor de estado. Si la función de transición inversa devuelve NULL, esto se toma como una indicación de que la función inversa no puede revertir el cálculo del estado para esta entrada en particular, y por lo tanto el cálculo del agregado se rehará desde cero para la posición de inicio del marco actual. Esta convención permite que el modo de agregado móvil se use en situaciones donde hay algunos casos infrecuentes que son impracticables de revertir del valor de estado en

ejecución.

Si no se proporciona una implementación de agregado móvil, el agregado todavía se puede usar con marcos móviles, pero PostgreSQL recalculará toda la agregación cada vez que se mueva el inicio del marco. Note que, ya sea que el agregado soporte o no el modo de agregado móvil, PostgreSQL puede manejar un final de marco móvil sin recálculo; esto se hace al continuar añadiendo nuevos valores al estado del agregado. Por esto es por lo que el uso de un agregado como función de ventana requiere que la función final sea de solo lectura: no debe dañar el valor de estado del agregado, para que la agregación pueda continuar incluso después de que se haya obtenido un valor de resultado del agregado para un conjunto de límites de

marco.

La sintaxis para agregados de conjunto ordenado permite especificar VARIADIC tanto para el último parámetro directo como para el último parámetro agregado (WITHIN GROUP). Sin embargo, la implementación actual restringe el uso de VARIADIC de dos maneras. Primero, los agregados de conjunto ordenado solo pueden usar VARIADIC "any", no otros tipos de matriz variadic. Segundo, si el último parámetro directo es VARIADIC "any", entonces solo puede haber un parámetro agregado y este también debe ser VARIADIC "any". (En la representación usada en los catálogos del sistema, estos dos parámetros se fusionan en un solo elemento VARIADIC "any", ya que pg_proc no puede representar funciones con más de un parámetro VARIADIC.) Si el agregado es un agregado de conjunto hipotético, los argumentos directos que coinciden con el parámetro VARIADIC "any" son los hipotéticos; cualquier parámetro anterior representa argumentos directos adicionales que no están restringidos a coincidir con los argumentos

agregados.

Actualmente, los agregados de conjunto ordenado no necesitan soportar el modo de agregado móvil, ya que no se pueden usar como funciones de

ventana.
