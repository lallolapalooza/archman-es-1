SINOPSI

S 
CREATE PUBLICATION nombre
    [ FOR ALL TABLES
      | FOR publication_object [, ... ] ]
    [ WITH ( publication_parameter [= valor] [, ... ] ) ]
donde publication_object es uno de:
    TABLE [ ONLY ] table_name [ * ] [ ( column_name [, ... ] ) ] [ WHERE ( expression ) ] [, ... ]
    TABLES IN SCHEMA { schema_name | CURRENT_SCHEMA } [, ...
]

DESCRIPCIÓ

N

CREATE PUBLICATION añade una nueva publicación a la base de datos actual. El nombre de la publicación debe ser distinto del nombre de cualquier publicación existente en la base de datos

actual.

Una publicación es esencialmente un grupo de tablas cuyos cambios de datos se preten

de que se repliquen a través de la replicación lógica. Vea la Sección 29.1 para deta
lles sobre cómo encajan las publicaciones en la configuración de replicación lógica.

PARÁMETRO

S

nombr

e
El nombre de la nueva
publicación.

FOR

TABLE
Especifica una lista de tablas para añadir a la publicación. Si se especifica ONLY antes del nombre de la tabla, solo se añade esa tabla a la publicación. Si no se especifica ONLY, se añaden la tabla y todas sus tablas descendientes (si las hay). Opcionalmente, se puede especificar * después del nombre de la tabla para indicar explícitamente que se incluyen las tablas descendientes. Sin embargo, esto no se aplica a una tabla particionada. Las particiones de una tabla particionada siempre se consideran implícitamente parte de la publicación, por lo que nunca se añaden explícitamente a la publicación.

Si se especifica la cláusula opcional WHERE, define una expresión de filtro de filas. Las filas para las cuales la expresión evalúe a falso o null no se publicarán. Tenga en cuenta que se requieren paréntesis alrededor de la expresión. No tiene efecto en los comandos

TRUNCATE.

Cuando se especifica una lista de columnas, solo se replican las columnas nombradas. La lista de columnas también puede contener columnas generadas almacenadas. Si se omite la lista de columnas, la publicación replicará por defecto todas las columnas no generadas (incluyendo cualquier columna añadida en el futuro). Las columnas generadas almacenadas también se pueden replicar si publish_generated_columns está establecido a stored. Especificar una lista de columnas no tiene efecto en los comandos TRUNCATE. Vea la Sección 29.5 para detalles sobre las listas de

columnas.

Solo las tablas base persistentes y las tablas particionadas pueden formar parte de una publicación. Las tablas temporales, las tablas no registradas (unlogged), las tablas foráneas, las vistas materializadas y las vistas normales no pueden formar parte de una

publicación.

No se admite especificar una lista de columnas cuando la publicación también publica FOR TABLES IN

SCHEMA.

Cuando se añade una tabla particionada a una publicación, todas sus particiones existentes y futuras se consi

deran implícitamente parte de la publicación. Por lo tanto, incluso las operaciones realizadas directamente
en una partición también se publican a través de las publicaciones de las que forman parte sus ancestros.

FOR ALL

TABLES
Marca la publicación como una que replica cambios para todas las tablas de la base de datos, incluyendo tablas creadas en el
futuro.

FOR TABLES IN

SCHEMA
Marca la publicación como una que replica cambios para todas las tablas en la lista de esquemas especificada, incluyendo tablas creadas en el futuro.

No se admite especificar un esquema cuando la publicación también publica una tabla con una lista de

columnas.

Solo se incluirán como parte de la publicación las tablas base persistentes y las tablas particionadas presentes en el esquema. Las tablas temporales, las tablas no registradas (unlogged), las tablas foráneas, las vistas materializadas y las vistas normales del esquema no formarán parte de la

publicación.

Cuando una tabla particionada se publica a través de una publicación a nivel de esquema, todas sus particiones existentes y futuras se conside

ran implícitamente parte de la publicación, independientemente de si son del esquema de la publicación o no. Por lo tanto, incluso las ope
raciones realizadas directamente en una partición también se publican a través de las publicaciones de las que forman parte sus ancestros.

WITH ( publication_parameter [= valor] [, ... ]

)
Esta cláusula especifica parámetros opcionales para una publicación. Se admiten los siguientes parámetros:

publish

(string)
Este parámetro determina qué operaciones DML publicará la nueva publicación a los suscriptores. El valor es una lista de operaciones separadas por comas. Las operaciones permitidas son insert, update, delete y truncate. El valor por defecto es publicar todas las acciones, y por lo tanto el valor por defecto de esta opción es 'insert, update, delete, truncate'.

Este parámetro solo afecta a las operaciones DML. En particular, la sincroni

zación inicial de datos (vea la Sección 29.9.1) de la replicación lógica no
tiene en cuenta este parámetro al copiar los datos existentes de las tablas.

publish_generated_columns

(enum)
Especifica si las columnas generadas presentes en las tablas asociadas a la publicación deben replicarse. Los valores posibles son none y stored.

El valor por defecto es none, lo que significa que las columnas generadas presentes en las tablas asociadas a la publicación no se

replicarán.

Si se establece a stored, las columnas generadas almacenadas presentes en las tablas asociadas a la publicación se

replicarán.

Nota
Si el suscriptor es de una versión anterior a la 18, la sincronización inicial de la tabla no copiará las columnas generadas aunque el parámetro publish_generated_columns sea stored en el publicador.
Vea la Sección 29.6 para más detalles sobre la replicación lógica de columnas
generadas.

publish_via_partition_root

(boolean)
Este parámetro determina si los cambios en una tabla particionada (o en sus particiones) contenida en la publicación se publicarán usando la identidad y el esquema de la tabla particionada en lugar de la de las particiones individuales que se cambian realmente; lo último es el valor por defecto. Habilitar esto permite que los cambios se repliquen en una tabla no particionada o en una tabla particionada que consista en un conjunto diferente de particiones.

Puede haber un caso en el que una suscripción combine múltiples publicaciones. Si una tabla particionada es publicada por alguna de las publicaciones suscritas que establecen publish_via_partition_root = true, los cambios en esta tabla particionada (o en sus particiones) se publicarán usando la identidad y el esquema de esta tabla particionada en lugar de la de las particiones

individuales.

Este parámetro también afecta a cómo se eligen los filtros de filas y las listas de columnas para las particiones; vea más abajo para

detalles.

Si esto está habilitado, las

operaciones TRUNCATE realiz
adas directamente en las
particiones no se replican.

Al especificar un parámetro de tipo boolean, la parte valor puede omitirse, lo q

ue equivale a es
pecificar TRUE.

NOTA

S

Si no se especifican FOR TABLE, FOR ALL TABLES o FOR TABLES IN SCHEMA, la publicación comienza con un conjunto vacío de tablas. Esto es útil si se van a añadir tablas o esquemas más

adelante.

La creación de una publicación no inicia la replicación. Solo define una lógica de agrupación y filtrado para los suscriptores

futuros.

Para crear una publicación, el usuario que la invoca debe tener el privilegio CREATE en la base de datos actual. (Por supuesto, los superusuarios omiten esta comprobación.

)

Para añadir una tabla a una publicación, el usuario que la invoca debe tener derechos de propiedad sobre la tabla. Las cláusulas FOR ALL TABLES y FOR TABLES IN SCHEMA requieren que el usuario que la invoca sea un

superusuario.

Las tablas añadidas a una publicación que publica UPDATE y/o DELETE deben tener definida REPLICA IDENTITY. De lo contrario, esas operaciones no estarán permitidas en esas

tablas.

Cualquier lista de columnas debe incluir las columnas de REPLICA IDENTITY para que las operaciones UPDATE o DELETE se publiquen. No hay restricciones de lista de columnas si la publicación solo publica INSERT

operaciones.

Una expresión de filtro de filas (es decir, la cláusula WHERE) debe contener solo columnas que estén cubiertas por REPLICA IDENTITY, para que las operaciones UPDATE y DELETE se publiquen. Para la publicación de INSERT operaciones, se puede usar cualquier columna en la expresión WHERE. El filtro de filas permite expresiones simples que no tengan funciones definidas por el usuario, operadores definidos por el usuario, tipos definidos por el usuario, colaciones definidas por el usuario, funciones incorporadas no inmutables, ni referencias a columnas del

sistema.

Las columnas generadas que forman parte de REPLICA IDENTITY deben sered explícitamente, ya sea listándolas en la lista de columnas o habilitando la opción publish_generated_columns, para que UPDATE y DELETE se

publiquen.

El filtro de fila en una tabla se vuelve redundante si se especifica FOR TABLES IN SCHEMA y la tabla pertenece a la esquema

referida.

Para las tablas particionadas publicadas, el filtro de fila de cada partición se toma de la tabla particionada publicada si el parámetro de publicación publish_via_partition_root es verdadero, o de la propia partición si es falso (el valor predeterminado). Consulte la Sección 29.4 para obtener más información sobre los filtros de fila. De manera similar, para las tablas particionadas publicadas, la lista de columnas de cada partición se toma de la tabla particionada publicada si el parámetro de publicación publish_via_partition_root es verdadero, o de la propia partición si es

falso.

Para un comando INSERT ... ON CONFLICT, la publicación publicará la operación que resulte del comando. Dependiendo del resultado, puede publicarse como INSERT o UPDATE, o puede no publicarse en

absoluto.

Para un comando MERGE, la publicación publicará un INSERT, UPDATE o DELETE por cada fila insertada, actualizada o

eliminada.

Adjuntar (ATTACH) una tabla a un árbol de particiones cuya raíz esté publicada usando una publicación con publish_via_partition_root establecido en true no hace que el contenido existente de la tabla se

replique.

Los comandos COPY ... FROM se publican como operaciones

INSERT.

Las operaciones DDL no se

publican.
