DESCRIPCIÓ

N

Cron se inicia desde /etc/rc.d/init.d o /etc/init.d cuando se utilizan scripts clásicos de sysvinit. En caso de que systemd esté habilitado, entonces el archivo de unidad se instala en /lib/systemd/system/crond.service y el demonio se inicia con el comando systemctl start crond.service. Este retorna inmediatamente, por lo tanto, no es necesario iniciarlo con el parámetro

'&'.

Cron busca en /var/spool/cron los archivos crontab que llevan el nombre de las cuentas en /etc/passwd; Los crontabs encontrados son cargados en la memoria. Cron también busca /etc/anacrontab y cualquier archivo en el directorio /etc/cron.d, que tienen un formato diferente (ver crontab(5)). Cron examina todos los crontabs almacenados y verifica cada tarea para ver si debe ejecutarse en el minuto actual. Al ejecutar comandos, cualquier salida se envía por correo al propietario del crontab (o al usuario especificado en la variable de entorno MAILTO en el crontab, si existe). Cualquier salida de tarea también se puede enviar a syslog utilizando la opción

-s.

Hay dos formas de verificar los cambios en las tablas de cron. El primer método es verificar la hora de modificación (modtime) de un archivo. El segundo método es utilizar el soporte de inotify. El uso de inotify se registra en el registro /var/log/cron después de que el demonio se haya iniciado. El soporte de inotify verifica los cambios en todas las tablas de cron y accede al disco duro solo cuando se detecta un

cambio.

Cuando se utiliza la opción de modtime, Cron verifica las horas de modificación de sus tablas de cron cada minuto para comprobar si hay cambios y recarga las tablas de cron que han cambiado. No es necesario reiniciar Cron después de que algunas de las tablas de cron hayan sido modificadas. La opción de modtime también se utiliza cuando inotify no se puede

inicializar.

Horario de Verano y otros cambios de

hora

Los cambios de hora local de menos de tres horas, como los causados por los cambios de Horario de Verano, se manejan de una manera especial. Esto solo se aplica a las tareas que se ejecutan a una hora específica y a las tareas que se ejecutan con una granularidad mayor a una hora. Las tareas que se ejecutan con más frecuencia se programan

normalmente.

Si la hora se ajustó una hora hacia adelante, aquellas tareas que habrían se ejecutado en el intervalo que se ha omitido se ejecutarán inmediatamente. Por el contrario, si la hora se ajustó hacia atrás, se evita ejecutar la misma tarea dos

veces.

Los cambios de hora de más de 3 horas se consideran correcciones del reloj o de la zona horaria, y la nueva hora se utiliza

inmediatamente.

Es posible utilizar diferentes zonas horarias para las tablas de cron. Ver crontab(5) para

más info
rmación.

SOPORTE DE

CLÚSTER

En esta versión de Cron es posible utilizar un directorio de cron compartido montado en red /var/spool/cron en un clúster de hosts y especificar que solo uno de los hosts debe ejecutar las tareas de crontab en este directorio en un momento dado. Esto se hace iniciando Cron con la opción -c, y haciendo que el archivo /var/spool/cron/.cron.hostname contenga solo una línea, que representa el nombre de host de cualquier host en el clúster que deba ejecutar las tareas. Si este archivo no existe, o el nombre de host en él no coincide con el devuelto por gethostname(2), entonces todos los archivos de crontab en este directorio se ignoran. Esto no tiene efecto sobre las tareas de cron especificadas en el archivo /etc/crontab o en los archivos en el directorio /etc/cron.d. Estos archivos siempre se ejecutan y se consideran específicos del

host.

En lugar de editar /var/spool/cron/.cron.hostname directamente, utilice la opción -n de crontab(1) para especificar el

host.

Debe asegurarse de que todos los hosts en un clúster, y el servidor de archivos desde el que montan el directorio de cron compartido, tengan relojes sincronizados estrechamente, por ejemplo, utilizando ntpd(8), de lo contrario los resultados serán muy

impredecibles.

El uso del clúster compartido deshabilita automáticamente el soporte de inotify, porque inotify no puede confiarse cron(8) — Arch Linux man pages

NAME

cron — daemon para ejecutar comandos programados

SYNOPSIS

cron [-f] [-l] [-m modo] [-p prefijo] [-x extensión] [-d directorio] [-D]

DESCRIPTION

El demonio cron es un demonio que se ejecuta continuamente y ejecuta comandos programados. Los comandos se especifican en archivos crontab. El demonio cron verifica periódicamente los archivos crontab y ejecuta los comandos que han de ejecutarse.

El demonio cron maneja el procesamiento de los archivos crontab para todos los usuarios del sistema, así como los archivos crontab del sistema ubicados en /etc/crontab y en /etc/cron.d/.

OPTIONS

-f: Ejecuta el demonio cron en primer plano. Esto es útil para depurar.

-l: Evita que se carguen las configuraciones de PAM. Esto puede ser necesario en entornos sin PAM.

-m modo: Especifica el modo de envío de correo. Los valores posibles son mail, write y pipe. El valor predeterminado es mail.

-p prefijo: Especifica un prefijo para el nombre del usuario del sistema en la salida de cron. El valor predeterminado es cron.

-x extensión: Activa extensiones específicas. Las extensiones disponibles son stream y log. Se pueden especificar múltiples extensiones separadas por comas.

-d directorio: Especifica un directorio de trabajo para el demonio cron. El valor predeterminado es /var/spool/cron.

-D: Habilita el modo de depuración. Esto equivale a especificar -x stream,log.

SIGNALS

cron responde a las siguientes señales:

  • SIGHUP: Vuelve a cargar los archivos crontab.
  • SIGUSR1: Registra el estado actual del demonio cron en syslog.
  • SIGUSR2: Evita que se vuelva a cargar automáticamente el archivo crontab.

CLUSTERING SUPPORT

El demonio cron admite el uso de un sistema de archivos compartido montado en red.

CAVEATS

Todos los archivos crontab deben ser archivos regulares o enlaces simbólicos a archivos regulares, no deben ser ejecutables ni escribibles por nadie más que el propietario. Este requisito se puede ignorar utilizando la opción -p en la línea de comandos del demonio crond. Si se utiliza la compatibilidad con inotify, los cambios en los archivos crontab enlazados no son notados automáticamente por el demonio cron. El demonio cron debe recibir una señal SIGHUP para recargar los archivos crontab. Esta es una limitación de la API inotify.

La salida de syslog se utilizará en lugar del correo, cuando sendmail no esté instalado.

SEE ALSO

crontab(1), crontab(5), inotify(7), pam(8)
