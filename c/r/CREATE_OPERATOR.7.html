DESCRIPCIÓ

N

CREATE OPERATOR define un nuevo operador, nombre. El usuario que define un operador se convierte en su propietario. Si se proporciona un nombre de esquema, el operador se crea en el esquema especificado. De lo contrario, se crea en el esquema

actual.

El nombre del operador es una secuencia de hasta NAMEDATALEN-1 (63 por defecto) caracteres de la siguiente

lista: 
+ - * / < > = ~ ! @ # % ^ & |
`
?

Hay algunas restricciones en la elección del

nombre:
•-- y /* no pueden aparecer en ninguna parte de un nombre de operador, ya que se tomarán como el inicio de un
comentario.
•Un nombre de operador multicaracter no puede terminar en + o -, a menos que el nombre también contenga al menos uno de estos caracteres: 
~ ! @ # % ^ & |
`
?

Por ejemplo, @- es un nombre de operador permitido, pero *-

no lo es. Esta restricción permite a PostgreSQL analizar coma
ndos compatibles con SQL sin requerir espacios entre tokens.
•El símbolo => está reservado por la gramática de SQL, por lo que no puede usarse como nombre de
operador.

El operador != se asigna a <> en la entrada, por lo que estos dos nombres siempre son

equivalentes.

Para operadores binarios, tanto LEFTARG como RIGHTARG deben definirse. Para operadores prefijados, solo debe definirse RIGHTARG. La función nombre_funcion debe haber sido definida previamente usando CREATE FUNCTION y debe estar definida para aceptar el número correcto de argumentos (uno o dos) de los tipos

indicados.

En la sintaxis de CREATE OPERATOR, las palabras clave FUNCTION y PROCEDURE son equivalentes, pero la función referenciada debe ser en cualquier caso una función, no un procedimiento. El uso de la palabra clave PROCEDURE aquí es histórico y está

obsoleto.

Las otras cláusulas especifican atributos opcionales de optimización del operador. Su significado se detalla en la Sección 36.

15.

Para poder crear un operador, debe tener el privilegio USAGE sobre los tipos de argument

os y el tipo de retorno, así como el privilegio EXECUTE sobre la función subyacente. Si
se especifica un operador conmutador o negador, debe ser propietario de esos operadores.

NOTA

S

Consulte la Sección 36.14 y la Sección 36.15 para más

información.

Cuando define un operador autoconmutativo, simplemente lo hace. Cuando define un par de operadores conmutativos, las cosas son un poco más complicadas: ¿cómo puede el primero en definirse referirse al otro, que aún no ha definido? Hay tres soluciones a este

problema:
•Una forma es omitir la cláusula COMMUTATOR en el primer operador que define, y luego proporcionar una en la definición del segundo operador. Dado que PostgreSQL sabe que los operadores conmutativos vienen en pares, cuando vea la segunda definición volverá automáticamente y rellenará la cláusula COMMUTATOR faltante en la primera
definición.
•Otra forma, más directa, es simplemente incluir cláusulas COMMUTATOR en ambas definiciones. Cuando PostgreSQL procesa la primera definición y se da cuenta de que COMMUTATOR se refiere a un operador inexistente, el sistema hará una entrada ficticia para ese operador en el catálogo del sistema. Esta entrada ficticia solo tendrá datos válidos para el nombre del operador, los tipos de operando izquierdo y derecho, y el propietario, ya que eso es todo lo que PostgreSQL puede deducir en este punto. La entrada del catálogo del primer operador se enlazará a esta entrada ficticia. Más tarde, cuando defina el segundo operador, el sistema actualizará la entrada ficticia con la información adicional de la segunda definición. Si intenta usar el operador ficticio antes de que se haya completado, simplemente obtendrá un mensaje de
error.
•Alternativamente, ambos operadores pueden definirse sin cláusulas COMMUTATOR y luego ALTER OPERATOR puede usarse para establecer sus enlaces conmutadores. Es suficiente con ALTER cualquiera de los dos del
par.

En los tres casos, debe ser propietario de ambos operadores para poder marcarlos como

conmutadores.

Los pares de operadores negadores pueden definirse usando los mismos métodos que para los pares de

conmutadores.

No es posible especificar la precedencia léxica de un operador en CREATE OPERATOR, porque el comportamiento de precedencia del analizador está fijado en el código. Consulte la Sección 4.1.6 para detalles sobre la

precedencia.

Las opciones obsoletas SORT1, SORT2, LTCMP y GTCMP se usaban anteriormente para especificar los nombres de los operadores de ordenación asociados a un operador unible por mezcla (merge-joinable). Esto ya no es necesario, ya que la información sobre los operadores asociados se encuentra mirando las familias de operadores B-tree. Si se da una de estas opciones, se ignora excepto para establecer implícitamente MERGES a

true.

Use DROP OPERATOR para eliminar operadores definidos por el usuario de una base de datos. Use ALTER OPERATOR para modificar o

peradores en un
a base de datos.
