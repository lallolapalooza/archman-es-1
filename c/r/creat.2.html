O_DIRECT (desde Linux 2.4.10)
Intenta minimizar los efectos de la caché de la E/S hacia y desde este archivo. En general esto degradará el rendimiento, pero es útil en situaciones especiales, como cuando las aplicaciones realizan su propia caché. La E/S de archivos se realiza directamente hacia/desde búferes del espacio de usuario. El O_DIRECT flag por sí solo hace un esfuerzo por transferir datos de forma síncrona, pero no da las garantías de la O_SYNC flag de que los datos y los metadatos necesarios se transfieran. Para garantizar E/S síncrona, O_SYNC debe usarse además de O_DIRECT. Ver NOTAS más abajo para una discusión más detallada.
Una interfaz semánticamente similar (pero obsoleta) para dispositivos de bloque se describe en raw(8).
O_DIRECTORY
Si path no es un directorio, hace que open() falle. Este flag se añadió en Linux 2.1.126, para evitar problemas de denegación de servicio si opendir(3) se llama en un FIFO o un dispositivo de cinta.
O_DSYNC
Las operaciones de escritura en el archivo se completarán de acuerdo con los requisitos de la E/S sincronizada data integrity completion.
Para cuando write(2) (y similares) retornan, los datos de salida han sido transferidos al hardware subyacente, junto con cualquier metadato del archivo que se necesitaría para recuperar esos datos (es decir, como si cada write(2)) fuera seguido por una llamada a fdatasync(2)). Ver VERSIONS.
O_EXCL
Asegura que esta llamada crea el archivo: si este flag se especifica en conjunto con O_CREAT, y path ya existe, entonces open() falla con el error EEXIST.
Cuando se especifican estos dos flags, no se siguen los enlaces simbólicos: si path es un enlace simbólico, entonces open() falla independientemente de dónde apunte el enlace simbólico.
En general, el comportamiento de O_EXCL es indefinido si se usa sin O_CREAT. Hay una excepción: en Linux 2.6 y posterior, O_EXCL puede usarse sin O_CREAT si path se refiere a un dispositivo de bloque. Si el dispositivo de bloque está en uso por el sistema (por ejemplo, montado), open() falla con el error EBUSY.
En NFS, O_EXCL se soporta solo cuando se usa NFSv3 o posterior en un kernel 2.6 o posterior. En entornos NFS donde el soporte de O_EXCL no se proporciona, los programas que dependen de él para realizar tareas de bloqueo contendrán una condición de carrera. Los programas portables que quieran realizar bloqueo atómico de archivos usando un lockfile, y necesiten evitar la dependencia del soporte NFS para O_EXCL, pueden crear un archivo único en el mismo sistema de archivos (por ejemplo, incorporando el nombre del host y el PID), y usar link(2) para crear un enlace a el lockfile. Si link(2) retorna 0, el bloqueo es exitoso. De lo contrario, use stat(2) en el archivo único para verificar si su contejo de enlaces ha aumentado a 2, en cuyo caso el bloqueo también es exitoso.
O_LARGEFILE
(LFS) Permite abrir archivos cuyos tamaños no pueden representarse en un off_t (pero pueden representarse en un off64_t). La macro _LARGEFILE64_SOURCE debe definirse (antes de incluir cualquier archivo de cabecera) para obtener esta definición. Establecer la macro de prueba de características _FILE_OFFSET_BITS a 64 (en lugar de usar O_LARGEFILE) es el método preferido para acceder a archivos grandes en sistemas de 32 bits (ver feature_test_macros(7)).
O_NOATIME (desde Linux 2.6.8)
No actualizar la hora de último acceso del archivo (st_atime en el inode) cuando el archivo es read(2).
Este flag puede emplearse solo si una de las siguientes condiciones es verdadera:
•
El UID efectivo del proceso coincide con el UID propietario del archivo.
•
El proceso que llama tiene la capacidad CAP_FOWNER en su espacio de nombres de usuario y el UID propietario del archivo tiene un mapeo en el espacio de nombres.
Este flag está destinado a ser usado por programas de indexación o copia de seguridad, donde su uso puede reducir significativamente la cantidad de actividad de disco. Este flag puede no ser efectivo en todos los sistemas de archivos. Un ejemplo es NFS, donde el servidor mantiene el tiempo de acceso.
O_NOCTTY
Si path se refiere a un dispositivo de terminal—ver tty(4)—no se convertirá en el terminal de control del proceso incluso si el proceso no tiene uno.
O_NOFOLLOW
Si el componente final (es decir, el nombre base) de path es un enlace simbólico, entonces la apertura falla, con el error ELOOP. Los enlaces simbólicos en componentes anteriores de la ruta de acceso seguirán siendo seguidos. (Note que el error ELOOP que puede ocurrir en este caso es indistinguible de el caso donde una apertura falla porque se encontraron demasiados enlaces simbólicos al resolver componentes en el prefijo de la ruta de acceso.)
Este flag es una extensión de FreeBSD, que se añadió en Linux 2.1.126, y posteriormente se ha estandarizado en POSIX.1-2008.
Ver también O_PATH más abajo.
O_NONBLOCK o O_NDELAY
Cuando sea posible, el archivo se abre en modo no bloqueante. Ni el open() ni ninguna operación de E/S posterior en el descriptor de archivo que se retorna harán que el proceso que llama espere.
Note que el establecimiento de este flag no tiene efecto en la operación de poll(2), select(2), epoll(7), y similares, ya que esas interfaces solo informan al llamador sobre si un descriptor de archivo está "listo", lo que significa que una operación de E/S realizada en el descriptor de archivo con el flag O_NONBLOCK clear no bloquearía.
Note que este flag no tiene efecto para archivos regulares y dispositivos de bloque; es decir, las operaciones de E/S bloquearán (brevemente) cuando se requiera actividad del dispositivo, independientemente de si O_NONBLOCK está establecido. Dado que la semántica de O_NONBLOCK podría eventualmente implementarse, las aplicaciones no deberían depender del comportamiento de bloqueo al especificar este flag para archivos regulares y dispositivos de bloque.
Para el manejo de FIFOs (tuberías con nombre), ver también fifo(7). Para una discusión del efecto de O_NONBLOCK en conjunto con bloqueos de archivos obligatorios y con arrendamientos de archivos, ver fcntl(2).
O_PATH (desde Linux 2.6.39)
Obtiene un descriptor de archivo que puede usarse para dos propósitos: para indicar una ubicación en el árbol del sistema de archivos y para realizar operaciones que actúan puramente a nivel de descriptor de archivo. El archivo en sí no se abre, y otras operaciones de archivo (por ejemplo, read(2), write(2), fchmod(2), fchown(2), fgetxattr(2), ioctl(2), mmap(2)) fallan con el error EBADF.
Las siguientes operaciones pueden realizarse en el descriptor de archivo resultante:
•
close(2).
•
fchdir(2), si el descriptor de archivo se refiere a un directorio (desde Linux 3.5).
•
fstat(2) (desde Linux 3.6).
•
fstatfs(2) (desde Linux 3.12).
•
Duplicar el descriptor de archivo (dup(2), fcntl(2) F_DUPFD, etc.).
•
Obtener y establecer flags de descriptor de archivo (fcntl(2) F_GETFD y F_SETFD).
•
Recuperar los flags de estado de archivo abierto usando la operación fcntl(2) F_GETFL : los flags retornados incluirán el bit O_PATH.
•
Pasar el descriptor de archivo como el argumento dirfd de openat() y las demás llamadas al sistema "*at()". Esto incluye linkat(2) con AT_EMPTY_PATH (o a través de procfs usando AT_SYMLINK_FOLLOW) incluso si el archivo no es un directorio.
•
Pasar el descriptor de archivo a otro proceso a través de un socket de dominio UNIX (ver SCM_RIGHTS en unix(7)).
Cuando O_PATH se especifica en flags, los bits de bandera distintos de O_CLOEXEC, O_DIRECTORY, y O_NOFOLLOW son ignorados.
Abrir un archivo o directorio con la O_PATH bandera no requiere permisos en el objeto en sí (pero sí requiere permiso de ejecución en los directorios en el prefijo de la ruta). Dependiendo de la operación posterior, se puede realizar una comprobación de los permisos de archivo adecuados (por ejemplo, fchdir(2) requiere permiso de ejecución en el directorio al que hace referencia su argumento de descriptor de archivo). Por el contrario, obtener una referencia a un objeto del sistema de archivos abriéndolo con la O_RDONLY bandera requiere que el llamador tenga permiso de lectura en el objeto, incluso cuando la operación posterior (por ejemplo, fchdir(2), fstat(2)) no requiere permiso de lectura en el objeto.
Si path es un enlace simbólico y la O_NOFOLLOW bandera también se especifica, entonces la llamada devuelve un descriptor de archivo que hace referencia al enlace simbólico. Este descriptor de archivo se puede usar como el dirfd argumento en llamadas a fchownat(2), fstatat(2), linkat(2), y readlinkat(2) con una ruta vacía para hacer que las llamadas operen sobre el enlace simbólico.
Si path hace referencia a un punto de montaje automático que aún no ha sido activado, de modo que no hay ningún otro sistema de archivos montado en él, entonces la llamada devuelve un descriptor de archivo que hace referencia al directorio de montaje automático sin activar un montaje. fstatfs(2) se puede entonces usar para determinar si es, de hecho, un punto de montaje automático no activado (.f_type == AUTOFS_SUPER_MAGIC).
Un uso de O_PATH para archivos regulares es proporcionar el equivalente de la funcionalidad O_EXEC de POSIX.1. Esto nos permite abrir un archivo para el cual tenemos permiso de ejecución pero no de lectura, y luego ejecutar ese archivo, con pasos algo como los siguientes:

char buf[PATH_MAX];
fd = open("some_prog", O_PATH);
snprintf(buf, PATH_MAX, "/proc/self/fd/%d", fd);
execl(buf, "some_prog", (char *) NULL);

Un O_PATH descriptor de archivo también se puede pasar como el argumento de fexecve(3).
O_SYNC
Las operaciones de escritura en el archivo se completarán de acuerdo con los requisitos de la finalización de la integridad de archivos de E/S sincronizada file (en contraste con la finalización de la integridad de datos de E/S sincronizada data proporcionada por O_DSYNC.)
Para cuando write(2) (o similar) retorna, los datos de salida y los metadatos del archivo asociados se han transferido al hardware subyacente (es decir, como si cada write(2)] fuera seguido por una llamada a fsync(2)). Vea VERSIONES.
O_TMPFILE (desde Linux 3.11)
Crea un archivo temporal regular sin nombre. El path argumento especifica un directorio; se creará un inodo sin nombre en el sistema de archivos de ese directorio. Cualquier cosa escrita en el archivo resultante se perderá cuando se cierre el último descriptor de archivo, a menos que se le dé un nombre al archivo.
O_TMPFILE debe especificarse con uno de O_RDWR o O_WRONLY y, opcionalmente, O_EXCL. Si O_EXCL no se especifica, entonces linkat(2)] se puede usar para vincular el archivo temporal al sistema de archivos, haciéndolo permanente, usando código como el siguiente:

char path[PATH_MAX];
fd = open("/path/to/dir", O_TMPFILE | O_RDWR,
                        S_IRUSR | S_IWUSR);
/* File I/O on 'fd'...  */
linkat(fd, "", AT_FDCWD, "/path/for/file", AT_EMPTY_PATH);
/* If the caller doesn't have the CAP_DAC_READ_SEARCH
   capability (needed to use AT_EMPTY_PATH with linkat(2)),
   and there is a proc(5) filesystem mounted, then the
   linkat(2) call above can be replaced with:
snprintf(path, PATH_MAX,  "/proc/self/fd/%d", fd);
linkat(AT_FDCWD, path, AT_FDCWD, "/path/for/file",
                        AT_SYMLINK_FOLLOW);
*/

En este caso, el open() mode argumento determina el modo de permisos del archivo, como con O_CREAT.
Especificar O_EXCL en conjunto con O_TMPFILE impide que un archivo temporal sea vinculado al sistema de archivos de la manera anterior. (Tenga en cuenta que el significado de O_EXCL en este caso es diferente del significado de O_EXCL en otro caso.)
Hay dos casos de uso principales para O_TMPFILE:
•
Funcionalidad mejorada de tmpfile(3) : creación de archivos temporales sin condiciones de carrera que (1) se eliminan automáticamente al cerrarse; (2) nunca se pueden alcanzar a través de ninguna ruta de acceso; (3) no están sujetos a ataques de enlaces simbólicos; y (4) no requieren que el llamador idee nombres únicos.
•
Creación de un archivo que inicialmente es invisible, que luego se puebla con datos y se ajusta para tener atributos de sistema de archivos apropiados (fchown(2), fchmod(2), fsetxattr(2), etc.) antes de ser vinculado atómicamente al sistema de archivos en un estado completamente formado (usando linkat(2) como se describió arriba).
O_TMPFILE requiere soporte por parte del sistema de archivos subyacente; solo un subconjunto de los sistemas de archivos de Linux proporcionan ese soporte. En la implementación inicial, el soporte se proporcionó en los sistemas de archivos ext2, ext3, ext4, UDF, Minix y tmpfs. El soporte para otros sistemas de archivos se ha añadido posteriormente de la siguiente manera: XFS (Linux 3.15); Btrfs (Linux 3.16); F2FS (Linux 3.16); y ubifs (Linux 4.9)
O_TRUNC
Si el archivo ya existe y es un archivo regular y el modo de acceso permite escribir (es decir, es O_RDWR o O_WRONLY) se truncará a longitud 0. Si el archivo es un FIFO o un archivo de dispositivo de terminal, la O_TRUNC bandera se ignora. De lo contrario, el efecto de O_TRUNC es indeterminado.

creat()

Una llamada a creat() es equivalente a llamar a open() con flags igual a O_CREAT|O_WRONLY|O_TRUNC.

openat()

La openat() llamada al sistema opera exactamente de la misma manera que open(), excepto por las diferencias descritas aquí.

El dirfd argumento se usa en conjunto con el path argumento de la siguiente manera:

•
Si la ruta de acceso dada en path es absoluta, entonces dirfd se ignora.
•
Si la ruta de acceso dada en path es relativa y dirfd es el valor especial AT_FDCWD, entonces path se interpreta en relación con el directorio de trabajo actual del proceso que llama (como open()).
•
Si la ruta de acceso dada en path es relativa, entonces se interpreta en relación con el directorio al que hace referencia el descriptor de archivo dirfd (en lugar de en relación con el directorio de trabajo actual del proceso que llama, como lo hace open() para una ruta de acceso relativa). En este caso, dirfd debe ser un directorio que se abrió para lectura (O_RDONLY) o usando la O_PATH bandera.

Si la ruta de acceso dada en path es relativa, y dirfd no es un descriptor de archivo válido, se produce un error (EBADF). (Especificar un número de descriptor de archivo inválido en dirfd se puede usar como un medio para asegurar que path es absoluta.)

openat2(2)

La openat2(2) llamada al sistema es una extensión de openat(), y proporciona un superconjunto de las características de openat(). Está documentada por separado, en openat2(2).

VALOR DE RETORNO

En caso de éxito, open(), openat(), y creat() retornan el nuevo descriptor de archivo (un entero no negativo). En caso de error, se retorna -1 y errno se establece para indicar el error.

ERRORES

open(), openat(), y creat() pueden fallar con los siguientes errores:

EACCES
El acceso solicitado al archivo no está permitido, o se deniega el permiso de búsqueda para uno de los directorios en el prefijo de la ruta de acceso de path, o el archivo aún no existía y no se permite el acceso de escritura al directorio padre. (Vea también path_resolution(7).)
EACCES
Donde O_CREAT se especifica, el sysctl protected_fifos o protected_regular está habilitado, el archivo ya existe y es un FIFO o un archivo regular, el propietario del archivo no es ni el usuario actual ni el propietario del directorio que lo contiene, y el directorio que lo contiene es tanto escribible por el mundo o por el grupo como pegajoso. Para más detalles, vea las descripciones de /proc/sys/fs/protected_fifos y /proc/sys/fs/protected_regular en proc_sys_fs(5).
EBADF
(openat()) path es relativa pero dirfd no es ni AT_FDCWD ni un descriptor de archivo válido.
EBUSY
O_EXCL se especificó en flags y path hace referencia a un dispositivo de bloque que está en uso por el sistema (por ejemplo, está montado).
EDQUOT
Donde O_CREAT se especifica, el archivo no existe, y la cuota del usuario de bloques de disco o inodos en el sistema de archivos se ha agotado.

E/S Sincronizada

La opción de E/S sincronizada de POSIX.1-2008 especifica diferentes variantes de E/S sincronizada, y especifica los flags open() O_SYNC, O_DSYNC y O_RSYNC para controlar el comportamiento. Independientemente de si una implementación soporta esta opción, debe al menos soportar el uso de O_SYNC para archivos regulares.

Linux implementa O_SYNC y O_DSYNC, pero no O_RSYNC. De forma algo incorrecta, glibc define O_RSYNC para tener el mismo valor que O_SYNC. (O_RSYNC se define en el archivo de cabecera de Linux <asm/fcntl.h> en HP PA-RISC, pero no se utiliza).

O_SYNC proporciona la finalización de la integridad de archivo de E/S sincronizada, lo que significa que las operaciones de escritura vaciarán los datos y todos los metadatos asociados al hardware subyacente. O_DSYNC proporciona la finalización de la integridad de datos de E/S sincronizada, lo que significa que las operaciones de escritura vaciarán los datos al hardware subyacente, pero solo vaciarán las actualizaciones de metadatos que sean necesarias para permitir que una operación de lectura posterior se complete correctamente. La finalización de la integridad de los datos puede reducir el número de operaciones de disco que son necesarias para aplicaciones que no necesitan las garantías de la finalización de la integridad de los archivos.

Para entender la diferencia entre los dos tipos de finalización, considere dos piezas de metadatos de archivo: la marca de tiempo de la última modificación del archivo (st_mtime) y la longitud del archivo. Todas las operaciones de escritura actualizarán la marca de tiempo de la última modificación del archivo, pero solo las escrituras que añaden datos al final del archivo cambiarán la longitud del archivo. La marca de tiempo de la última modificación no es necesaria para garantizar que una lectura se complete correctamente, pero la longitud del archivo sí lo es. Por lo tanto, O_DSYNC solo garantizaría vaciar las actualizaciones a los metadatos de longitud del archivo (mientras que O_SYNC también vaciaría siempre los metadatos de la marca de tiempo de la última modificación).

Antes de Linux 2.6.33, Linux solo implementaba el flag O_SYNC para open(). Sin embargo, cuando se especificaba ese flag, la mayoría de los sistemas de archivos proporcionaban en realidad el equivalente a la finalización de la integridad de datos de E/S sincronizada (es decir, O_SYNC se implementaba en realidad como el equivalente a O_DSYNC).

Desde Linux 2.6.33, se proporciona soporte adecuado para O_SYNC. Sin embargo, para garantizar la compatibilidad binaria hacia atrás, O_DSYNC se definió con el mismo valor que el O_SYNC histórico, y O_SYNC se definió como un nuevo valor de flag (de dos bits) que incluye el valor del flag O_DSYNC. Esto garantiza que las aplicaciones compiladas contra cabeceras nuevas obtengan al menos la semántica de O_DSYNC antes de Linux 2.6.33.

Desde glibc 2.26, la función de envoltura de glibc para open() utiliza la llamada al sistema openat(), en lugar de la llamada al sistema open() del kernel. Para ciertas arquitecturas, esto también es cierto antes de glibc 2.26.
