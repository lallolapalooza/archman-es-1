DESCRIPCIÓ

N

El archivo /etc/crypttab describe los dispositivos de bloque cifrados que se configuran durante el arranque del

sistema.

Se ignoran las líneas vacías y las líneas que comienzan con el carácter "#". Cada una de las líneas restantes describe un dispositivo de bloque cifrado. Los campos están delimitados por espacios en

blanco.

Cada línea tiene la

forma 
nombre-del-volumen dispositivo-cifrado archivo-de-clave opcion
e
s

Los dos primeros campos son obligatorios, los dos restantes son

opcionales.

La configuración de dispositivos de bloque cifrados mediante este archivo admite cuatro modos de cifrado: LUKS, TrueCrypt, BitLocker y plain (simple). Consulte cryptsetup(8) para obtener más información sobre cada modo. Cuando no se especifica ningún modo en el campo de opciones y el dispositivo de bloque contiene una firma LUKS, se abre como un dispositivo LUKS; de lo contrario, se asume que está en formato dm-crypt (modo plain) sin

procesar.

Los cuatro campos de /etc/crypttab se definen de la siguiente

manera:
1.El primer campo contiene el nombre del volumen resultante con los datos descifrados; su dispositivo de bloque se configura debajo de
/dev/mapper/.
2.El segundo campo contiene una ruta al dispositivo de bloque subyacente o al archivo, o una especificación de un dispositivo de bloque mediante "UUID=" seguido del
UUID.
3.El tercer campo especifica una ruta absoluta a un archivo con la clave de cifrado. Opcionalmente, la ruta puede ir seguida de ":" y una especificación de dispositivo al estilo de /etc/fstab (por ejemplo, que comience con "LABEL=" o similar); en cuyo caso, la ruta se toma como relativa a la raíz del sistema de archivos del dispositivo especificado. Si el campo no está presente o es "none" o "-", se carga automáticamente un archivo de clave con el nombre del volumen a desbloquear (es decir, la primera columna de la línea), con el sufijo .key, desde los directorios /etc/cryptsetup-keys.d/ y /run/cryptsetup-keys.d/, si están presentes. De lo contrario, la contraseña debe introducirse manualmente durante el arranque del sistema. Para el cifrado de la memoria de intercambio (swap), puede usarse /dev/urandom como archivo de clave, lo que resulta en una clave aleatoria.

Si la ruta del archivo de clave especificada hace referencia a un socket de flujo AF_UNIX en el sistema de archivos, la clave se adquiere conectándose al socket y leyéndola de la conexión. Esto permite la implementac

ión de un servicio para proporcionar información de clave dinámicamente, en
el momento en que se necesita. Para más detalles, consulte a continuación.
4.El cuarto campo, si está presente, es una li
sta de opciones delimitada por comas. Las op
ciones admitidas se enumeran a continuación.

ADQUISICIÓN DE

CLAVES

Se admiten seis mecanismos diferentes para adquirir la clave de descifrado o la frase de contraseña que desbloquea el volumen cifrado. Específicamente

:
1.Más prominentemente, se puede consultar al usuario interactivamente durante la activación del volumen (es decir, normalmente al arrancar), pidiéndole que introduzca las frases de contraseña
necesarias.
2.La clave (sin cifrar) puede leerse desde un archivo en el disco, posiblemente en un medio extraíble. El tercer campo de cada línea codifica la ubicación; para más detalles, consulte
arriba.
3.La clave (sin cifrar) puede solicitarse a otro servicio, especificando un socket de sistema de archivos AF_UNIX en lugar de un archivo de clave en el tercer campo. Para más detalles, consulte arriba y
abajo.
4.La clave puede adquirirse mediante un token de seguridad de hardware o una tarjeta inteligente compatible con PKCS#11. En este caso, una clave guardada utilizada en el proceso de desbloqueo se almacena en disco/medio extraíble, se adquiere mediante AF_UNIX, o se almacena en el encabezado de metadatos del token JSON de LUKS2. Para RSA, la clave guardada es una clave de volumen cifrada. La clave de volumen cifrada se descifra entonces por el token PKCS#11 con una clave privada RSA almacenada en él, y se utiliza para desbloquear el volumen cifrado. Para la criptografía de curva elíptica (EC), la clave guardada es la clave pública generada en el proceso de inscripción. La clave pública se utiliza entonces para derivar un secreto compartido con una clave privada almacenada en el token PKCS#11. El secreto compartido derivado se utiliza entonces para desbloquear el volumen. Utilice la opción pkcs11-uri= descrita a continuación para usar este
mecanismo.
5.Similarmente, la clave puede adquirirse mediante un token de seguridad de hardware compatible con FIDO2 (que debe implementar la extensión "hmac-secret"). En este caso, una clave generada aleatoriamente durante la inscripción se almacena en disco/medio extraíble, se adquiere mediante AF_UNIX, o se almacena en el encabezado de metadatos del token JSON de LUKS2. La clave aleatoria se procesa mediante una función de hash con clave (HMAC) en el token FIDO2, utilizando una clave secreta almacenada en el token que nunca sale de él. El valor hash resultante se utiliza entonces como clave para desbloquear el volumen cifrado. Utilice la opción fido2-device= descrita a continuación para usar este
mecanismo.
6.Similarmente, la clave puede adquirirse mediante un chip de seguridad TPM2. En este caso, una clave generada aleatoriamente (durante la inscripción) —cifrada por una clave asimétrica derivada de la clave semilla del chip TPM2— se almacena en disco/medio extraíble, se adquiere mediante AF_UNIX, o se almacena en el encabezado de metadatos del token JSON de LUKS2. Utilice la opción tpm2-device= descrita a continuación para usar este
mecanismo.

Para los cinco últimos mecanismos, la fuente del material de clave utilizado para desbloquear el volumen se configura principalmente en el tercer campo de cada línea de /etc/crypttab, pero también puede configurarse en /etc/cryptsetup-keys.d/ y /run/cryptsetup-keys.d/ (consulte arriba) o en el encabezado de metadatos del token JSON de LUKS2 (en el caso de los tres últimos). Utilice la herramienta systemd-cryptenroll(1) para inscribir disp

ositivos PKCS#11, FIDO2
y TPM2 en volúmenes LUKS2.

password-cache=yes|no|read-only

Controla si se utiliza caché para contraseñas o PIN de tokens de seguridad. Acepta un valor booleano o la cadena especial "read-only". El valor predeterminado es "yes".

Si se establece en "read-only", se comprueba el keyring del kernel en busca de una contraseña/PIN antes de solicitarla interactivamente. Si se establece en "yes", además de comprobar el keyring, cualquier contraseña/PIN introducida interactivamente se almacena en caché en el keyring con un tiempo de espera de 2,5 minutos antes de ser purgada.

Tenga en cuenta que esta opción no está permitida para tokens de seguridad PKCS#11. La razón es que los tokens de seguridad PKCS#11 suelen configurarse para bloquearse después de que se les haya proporcionado un PIN incorrecto varias veces, por lo que el uso de la caché podría bloquear inadvertidamente el token.

Añadido en la versión 257.

pkcs11-uri=

Acepta el valor especial "auto" o una URI PKCS#11 RFC7512[2] que apunta a una clave privada que se utiliza para descifrar la clave cifrada especificada en la tercera columna de la línea. Esto es útil para desbloquear volúmenes cifrados a través de tokens de seguridad compatibles con PKCS#11 o tarjetas inteligentes. Consulte a continuación un ejemplo de cómo configurar este mecanismo para desbloquear un volumen LUKS2 con un token de seguridad YubiKey.

Si se especifica como "auto", el volumen debe ser de tipo LUKS2 y debe contener metadatos del token de seguridad PKCS#11 en su sección de tokens JSON de LUKS2. En este modo, la URI y la clave cifrada se leen automáticamente de la cabecera del token JSON de LUKS2. Utilice systemd-cryptenroll(1) como una herramienta sencilla para inscribir tokens de seguridad PKCS#11 o tarjetas inteligentes de forma compatible con "auto". En este modo, la tercera columna de la línea debe permanecer vacía (es decir, especificada como "-").

La URI especificada puede referirse directamente a una clave privada almacenada en un token o, alternativamente, solo a una ranura o token, en cuyo caso se realizará una búsqueda de una clave privada adecuada. En este caso, si se encuentran varios objetos adecuados, se rechaza el token. El archivo de claves configurado en la tercera columna de la línea se utiliza tal cual (es decir, en forma binaria, sin procesar). La clave descifrada resultante (para RSA) o el secreto compartido derivado (para ECC) se codifica en Base64 antes de utilizarse para desbloquear el volumen LUKS.

Utilice systemd-cryptenroll --pkcs11-token-uri=list para listar todos los tokens de seguridad PKCS#11 adecuados actualmente conectados, junto con sus URIs.

Tenga en cuenta que muchos tokens de seguridad más nuevos que pueden usarse como tokens de seguridad PKCS#11 suelen implementar también el estándar más nuevo y sencillo FIDO2. Considere usar fido2-device= (descrito a continuación) para inscribirlo a través de FIDO2 en su lugar. Tenga en cuenta que un token de seguridad inscrito a través de PKCS#11 no se puede utilizar para desbloquear el volumen a través de FIDO2, a menos que también esté inscrito a través de FIDO2, y viceversa.

tpm2-device=

Acepta el valor especial "auto" o la ruta a un nodo de dispositivo (por ejemplo, /dev/tpmrm0) que hace referencia a un chip de seguridad TPM2. Consulte a continuación un ejemplo de cómo configurar este mecanismo para desbloquear un volumen cifrado con un chip TPM2.

Utilice tpm2-pcrs= (ver más abajo) para configurar el conjunto de PCRs de TPM2 a los que se vinculará el desbloqueo del volumen. Utilice systemd-cryptenroll(1) como una herramienta sencilla para inscribir chips de seguridad TPM2 en volúmenes LUKS2.

Si se especifica como "auto", el dispositivo TPM2 se descubre automáticamente. Utilice systemd-cryptenroll --tpm2-device=list para listar todos los dispositivos TPM2 adecuados actualmente disponibles, junto con sus nodos de dispositivo.

Esta opción implementa el siguiente mecanismo: al inscribir un dispositivo TPM2 a través de systemd-cryptenroll en un volumen LUKS2, se genera una clave aleatoria que desbloquea el volumen en el host y se carga en el chip TPM2, donde se cifra con un par de claves "primarias" asimétricas derivadas de la clave "semilla" interna del TPM2. Ni la clave semilla ni la clave primaria tienen permitido salir nunca del chip TPM2 — sin embargo, la clave aleatoria ahora cifrada sí puede hacerlo. Se guarda en la cabecera del token JSON del volumen LUKS2. Al desbloquear el volumen cifrado, el par de claves primarias se genera nuevamente en el chip TPM2 (lo que funciona siempre que la clave semilla del chip sea mantenida correctamente por el chip TPM2), que luego se utiliza para descifrar (en el chip TPM2) la clave cifrada de la cabecera del token JSON del volumen LUKS2 guardada allí durante la inscripción. La clave descifrada resultante se utiliza luego para desbloquear el volumen. Cuando la clave aleatoria se cifra, los valores actuales de las PCRs seleccionadas (ver más abajo) se incluyen en la operación, de modo que un estado de PCR diferente da como resultado claves cifradas diferentes y la clave descifrada solo puede recuperarse si se reproduce el mismo estado de PCR.

SYNOPSIS

/etc/crypttab

DESCRIPTION

The file /etc/crypttab lists additional encrypted block devices that should be set up during boot. It is a text file, with one entry per line. Blank lines and lines starting with the character # are ignored.

Each entry in /etc/crypttab describes one encrypted block device and has the following fields, separated by whitespace:

name
The name for the decrypted mapped device. The actual device node will be created at /dev/mapper/name. It is recommended to use a descriptive name, for example cryptroot for the root device or cryptswap for a swap device. The name must not contain illegal characters like /.
device
The block device that holds the encrypted data. This may be a path to a device node (e.g. /dev/sda2, /dev/vg0/crypt), a path to a file (e.g. /path/to/encrypted.file), or a UUID or LABEL reference (e.g. UUID=..., LABEL=...). For files, the device field may also be specified as none if the file is to be created using systemd-cryptsetup@.service(8). In that case, options must contain size=, fsck-option=, and no-user-setup is recommended. Note that specifying none for the device field is only allowed when name is also none.
password
The location of the key file or passphrase. This may be a path to a device node, a path to a file (e.g. /etc/cryptsetup-keys.d/mykey.key), or one of the special values none, skip, or policy.

If none is specified, systemd-cryptsetup will prompt for the passphrase interactively.

If skip is specified, the device will be ignored. This is useful for commenting out an entry without removing it.

If policy is specified, the systemd-cryptsetup(8) service will try to acquire the key from system policies, such as TPM or FIDO2 devices. This is the default if the field is omitted entirely.

The following special options can be used:

fido2-device=
Specifies the path to a FIDO2 security token. Can be auto to automatically discover the device. This option implies policy.
tpm2-device=
Specifies the path to a TPM2 security chip. Can be auto to automatically discover the device. This option implies policy.
tpm2-pcrs=
Specifies a comma-separated list of TPM2 PCR registers to seal the key to. Defaults to 7.
token=
Specifies the PKCS#11 token URI for a hardware security module. Implies policy.
token-program=
Specifies the path to an executable that will provide the key.
token-program-arg=
Specifies an argument to the token-program. Can be used multiple times.
options
A comma-separated list of configuration options. The following options are recognized:

discard: Enable the discard feature for solid state drives. This allows the underlying block device to discard blocks that are no longer in use.

allow-discards: Same as discard.

readonly: Open the device in read-only mode.

noearly: Do not attempt to unlock the device during early boot. The device will be unlocked later by systemd.

x-systemd.device-timeout=: Sets the timeout for unlocking the device. Defaults to infinity.

x-systemd.unlock-timeout=: Sets the timeout for interactive passphrase prompts. Defaults to infinity.

x-systemd.requires=: Add an additional dependency for the unlock service.

keyscript=: Specifies a script that is called to obtain the key. The script is invoked with the device name as the first argument. The key is read from the standard output of the script.

keyfile-timeout=: Specifies the maximum time in seconds to wait for a key file to become available.

fido2-device=: Same as in the password field.

tpm2-device=: Same as in the password field.

tpm2-pcrs=: Same as in the password field.

token=: Same as in the password field.

token-program=: Same as in the password field.

token-program-arg=: Same as in the password field.

size=: Specifies the size of the encrypted file to create. Required when device is none.

fsck-option=: Specifies an option for the filesystem check. Required when device is none.

no-user-setup: Disable interactive setup for the encrypted file. Recommended when device is none.

cipher=: Specifies the cipher to use for encryption. Defaults to aes-cbc-essiv:sha256.

verify: Enable key verification. This means that the passphrase is not directly used, but instead used to derive a key that is verified against a stored key.

tries=: Number of allowed passphrase attempts. Defaults to 3.

timeout=: Timeout in seconds for passphrase entry. Defaults to 0 (infinite).

master-key=: Specifies a file containing the master key. This is used to unlock the LUKS device.

luks: If specified, the device is treated as a LUKS device. This is the default.

luks-options=: Options to pass to cryptsetup luksOpen.

luks-device=: Specify the LUKS device to open. This is usually the same as the device field, but can be different.

integrity=: Specifies the integrity algorithm to use. For example, poly1305-quatised-etf. This option requires a cipher that supports integrity, like aes-xts.

sector-size=: Specifies the sector size for the encrypted device. Defaults to the sector size of the underlying device.

buffer-size=: Specifies the buffer size for the encrypted device. Defaults to the buffer size of the underlying device.

uuid=: Specifies the UUID of the encrypted device. This is used to ensure the correct device is unlocked.

label=: Specifies the LABEL of the encrypted device. This is used to ensure the correct device is unlocked.

cancel=: Specifies a device node that, when written to, will cancel the unlock operation. This is useful for preventing boot loops in case of a lost passphrase.

swap: Treat the device as a swap device. This implies noearly.

swap-priority=: Sets the priority for the swap device. Defaults to 0.

fstab: If specified, the device will be automatically mounted according to the settings in /etc/fstab after unlocking.

no-fstab: If specified, the device will not be mounted according to /etc/fstab. This is the default.

systemd.automount: If specified, the device will be automatically mounted using systemd.automount units. This is equivalent to adding x-systemd.automount to the mount options in /etc/fstab.

systemd.idle-timeout=: Sets the idle timeout for the automount unit. Defaults to 1min.

systemd.mount-timeout=: Sets the mount timeout for the mount unit. Defaults to infinity.

systemd.mount-timeout-active=: Sets the active mount timeout for the mount unit. Defaults to infinity.

systemd.mount-timeout-inactive=: Sets the inactive mount timeout for the mount unit. Defaults to infinity.

systemd.mount-timeout-noauto=: Sets the noauto mount timeout for the mount unit. Defaults to infinity.

systemd.mount-timeout-remount=: Sets the remount timeout for the mount unit. Defaults to infinity.

systemd.mount-timeout-start=: Sets the start mount timeout for the mount unit. Defaults to infinity.

systemd.mount-timeout-stop=: Sets the stop mount timeout for the mount unit. Defaults to infinity.
