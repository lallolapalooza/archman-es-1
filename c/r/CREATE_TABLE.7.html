DESCRIPCIÓ

N

CREATE TABLE creará una nueva tabla, inicialmente vacía, en la base de datos actual. La tabla será propiedad del usuario que emita el

comando.

Si se proporciona un nombre de esquema (por ejemplo, CREATE TABLE myschema.mytable ...) entonces la tabla se crea en el esquema especificado. De lo contrario, se crea en el esquema actual. Las tablas temporales existen en un esquema especial, por lo que no se puede proporcionar un nombre de esquema al crear una tabla temporal. El nombre de la tabla debe ser distinto del nombre de cualquier otra relación (tabla, secuencia, índice, vista, vista materializada o tabla externa) en el mismo

esquema.

CREATE TABLE también crea automáticamente un tipo de datos que representa el tipo compuesto correspondiente a una fila de la tabla. Por lo tanto, las tablas no pueden tener el mismo nombre que cualquier tipo de datos existente en el mismo

esquema.

Las cláusulas de restricción opcionales especifican restricciones (pruebas) que las filas nuevas o actualizadas deben satisfacer para que una operación de inserción o actualización tenga éxito. Una restricción es un objeto SQL que ayuda a definir el conjunto de valores válidos en la tabla de diversas

maneras.

Hay dos formas de definir restricciones: restricciones de tabla y restricciones de columna. Una restricción de columna se define como parte de una definición de columna. Una definición de restricción de tabla no está vinculada a una columna particular, y puede abarcar más de una columna. Toda restricción de columna también se puede escribir como una restricción de tabla; una restricción de columna es solo una conveniencia notacional para usar cuando la restricción solo afecta a una

columna.

Para poder crear una tabla, debe tener el privilegio USAGE en todos los tipos de columna o el tipo en la cláusula OF,

respectivamente
.

Si se especifica, la tabla se crea como una tabla temporal. Las tablas temporales se eliminan automáticamente al final de una sesión, o opcionalmente al final de la transacción actual (véase ON COMMIT más abajo). La search_path predeterminada incluye primero el esquema temporal y por lo tanto las tablas permanentes existentes con el mismo nombre no se eligen para los nuevos planes mientras la tabla temporal existe, a menos que se referencien con nombres calificados por esquema. Cualquier índice creado en una tabla temporal es automáticamente temporal también.

El demonio autovacuum no puede acceder y por lo tanto no puede hacer vacuum o analyze en tablas temporales. Por esta razón, se deben realizar las operaciones de vacuum y analyze apropiadas mediante comandos SQL de sesión. Por ejemplo, si una tabla temporal se va a usar en consultas complejas, es aconsejable ejecutar ANALYZE en la tabla temporal después de que se haya

INHERITS ( parent_table [, ... ]

)
La cláusula opcional INHERITS especifica una lista de tablas de las que la nueva tabla hereda automáticamente todas las columnas. Las tablas principales pueden ser tablas normales o tablas foráneas.

El uso de INHERITS crea una relación persistente entre la nueva tabla hija y su(s) tabla(s) principal(es). Las modificaciones de esquema en la(s) principal(es) normalmente se propagan a las hijas también, y de forma predeterminada los datos de la tabla hija se incluyen en los escaneos de la(s) principal(es)

.

Si el mismo nombre de columna existe en más de una tabla principal, se informa de un error a menos que los tipos de datos de las columnas coincidan en cada una de las tablas principales. Si no hay conflicto, las columnas duplicadas se fusionan para formar una sola columna en la nueva tabla. Si la lista de nombres de columnas de la nueva tabla contiene un nombre de columna que también se hereda, el tipo de datos debe coincidir igualmente con la(s) columna(s) heredada(s), y las definiciones de columna se fusionan en una. Si la nueva tabla especifica explícitamente un valor predeterminado para la columna, este valor predeterminado anula cualquier valor predeterminado de las declaraciones heredadas de la columna. De lo contrario, cualquier tabla principal que especifique valores predeterminados para la columna debe especificar todos el mismo valor predeterminado, o se informará de un

error.

Las restricciones CHECK se fusionan de esencialmente la misma manera que las columnas: si múltiples tablas principales y/o la definición de la nueva tabla contienen restricciones CHECK con el mismo nombre, estas restricciones deben tener todas la misma expresión de comprobación, o se informará de un error. Las restricciones con el mismo nombre y expresión se fusionarán en una sola copia. Una restricción marcada como NO INHERIT en una tabla principal no se considerará. Tenga en cuenta que una restricción CHECK sin nombre en la nueva tabla nunca se fusionará, ya que siempre se elegirá un nombre único para

ella.

Los ajustes de STORAGE de las columnas también se copian de las tablas

principales.

Si una columna en la tabla principal es una columna de iden

tidad, esa propiedad no se hereda. Una columna en la tabla h
ija puede declararse como columna de identidad si se desea.

PARTITION BY { RANGE | LIST | HASH } ( { column_name | ( expression ) } [ opclass ] [, ...]

)
La cláusula opcional PARTITION BY especifica una estrategia de partición de la tabla. La tabla así creada se llama tabla particionada. La lista entre paréntesis de columnas o expresiones forma la clave de partición para la tabla. Al usar partición por rango o hash, la clave de partición puede incluir múltiples columnas o expresiones (hasta 32, pero este límite se puede alterar al compilar PostgreSQL), pero para la partición por lista, la clave de partición debe consistir en una sola columna o expresión.

La partición por rango y por lista requieren una clase de operadores btree, mientras que la partición por hash requiere una clase de operadores hash. Si no se especifica explícitamente una clase de operadores, se utilizará la clase de operadores predeterminada del tipo apropiado; si no existe una clase de operadores predeterminada, se generará un error. Cuando se usa partición por hash, la clase de operadores utilizada debe implementar la función de soporte 2 (consulte la Sección 36.16.3 para más detalles)

.

Una tabla particionada se divide en subtablas (llamadas particiones), que se crean usando comandos CREATE TABLE separados. La tabla particionada está en sí misma vacía. Una fila de datos insertada en la tabla se enruta a una partición basándose en el valor de las columnas o expresiones en la clave de partición. Si ninguna partición existente coincide con los valores en la nueva fila, se informará de un

error.

Consulte la Sección 5.12

para más discusión sobre
la partición de tablas.

PARTITION OF parent_table { FOR VALUES partition_bound_spec | DEFAULT

}
Crea la tabla como una partición de la tabla principal especificada. La tabla puede crearse como una partición para valores específicos usando FOR VALUES o como una partición predeterminada usando DEFAULT. Cualquier índice, restricciones y disparadores a nivel de fila definidos por el usuario que existan en la tabla principal se clonan en la nueva partición.

El partition_bound_spec debe corresponder al método de partición y la clave de partición de la tabla principal, y no debe solaparse con ninguna partición existente de esa tabla principal. La forma con IN se usa para la partición por lista, la forma con FROM y TO se usa para la partición por rango, y la forma con WITH se usa para la partición por

hash.

partition_bound_expr es cualquier expresión libre de variables (no se permiten subconsultas, funciones de ventana, funciones agregadas y funciones que devuelven conjuntos). Su tipo de datos debe coincidir con el tipo de datos de la columna de clave de partición correspondiente. La expresión se evalúa una vez en el momento de la creación de la tabla, por lo que incluso puede contener expresiones volátiles como CURRENT_TIMESTAMP

.

Al crear una partición por lista, se puede especificar NULL para indicar que la partición permite que la columna de clave de partición sea nula. Sin embargo, no puede haber más de una partición por lista de este tipo para una tabla principal dada. No se puede especificar NULL para particiones por

rango.

Al crear una partición por rango, el límite inferior especificado con FROM es un límite inclusivo, mientras que el límite superior especificado con TO es un límite exclusivo. Es decir, los valores especificados en la lista FROM son valores válidos de las columnas de clave de partición correspondientes para esta partición, mientras que los de la lista TO no lo son. Tenga en cuenta que esta declaración debe entenderse de acuerdo con las reglas de comparación por filas (Sección 9.25.5). Por ejemplo, dado PARTITION BY RANGE (x,y), un límite de partición FROM (1, 2) TO (3, 4) permite x=1 con cualquier y>=2, x=2 con cualquier y no nula, y x=3 con cualquier

y<4.

Los valores especiales MINVALUE y MAXVALUE pueden usarse al crear una partición por rango para indicar que no hay límite inferior o superior en el valor de la columna. Por ejemplo, una partición definida usando FROM (MINVALUE) TO (10) permite cualquier valor menor que 10, y una partición definida usando FROM (10) TO (MAXVALUE) permite cualquier valor mayor o igual que

10.

Al crear una partición por rango que involucre más de una columna, también puede tener sentido usar MAXVALUE como parte del límite inferior, y MINVALUE como parte del límite superior. Por ejemplo, una partición definida usando FROM (0, MAXVALUE) TO (10, MAXVALUE) permite cualquier fila donde la primera columna de clave de partición sea mayor que 0 y menor o igual que 10. De manera similar, una partición definida usando FROM ('a', MINVALUE) TO ('b', MINVALUE) permite cualquier fila donde la primera columna de clave de partición comience con

"a".

Tenga en cuenta que si se usa MINVALUE o MAXVALUE para una columna de un límite de partición, el mismo valor debe usarse para todas las columnas siguientes. Por ejemplo, (10, MINVALUE, 0) no es un límite válido; debería escribir (10, MINVALUE, MINVALUE)

.

Tenga en cuenta también que algunos tipos de elementos, como timestamp, tienen la noción de "infinito", que es simplemente otro valor que se puede almacenar. Esto es diferente de MINVALUE y MAXVALUE, que no son valores reales que se puedan almacenar, sino que son formas de decir que el valor es ilimitado. MAXVALUE se puede pensar como mayor que cualquier otro valor, incluyendo "infinito", y MINVALUE como menor que cualquier otro valor, incluyendo "menos infinito". Así, el rango FROM ('infinity') TO (MAXVALUE) no es un rango vacío; permite almacenar exactamente un valor —

"infinito".

Si se especifica DEFAULT, la tabla se creará como la partición predeterminada de la tabla principal. Esta opción no está disponible para tablas particionadas por hash. Un valor de clave de partición que no encaje en ninguna otra partición de la tabla principal dada se enrutará a la partición

predeterminada.

Cuando una tabla tiene una partición DEFAULT existente y se le añade una nueva partición, la partición predeterminada debe ser escaneada para verificar que no contiene ninguna fila que pertenezca correctamente a la nueva partición. Si la partición predeterminada contiene un gran número de filas, esto puede ser lento. El escaneo se omitirá si la partición predeterminada es una tabla foránea o si tiene una restricción que demuestra que no puede contener filas que deberían colocarse en la nueva

partición.

Al crear una partición por hash, se debe especificar un módulo y un residuo. El módulo debe ser un entero positivo, y el residuo debe ser un entero no negativo menor que el módulo. Típicamente, al configurar inicialmente una tabla particionada por hash, debería elegir un módulo igual al número de particiones y asignar a cada tabla el mismo módulo y un residuo diferente (consulte los ejemplos, más abajo). Sin embargo, no se requiere que cada partición tenga el mismo módulo, solo que cada módulo que ocurra entre las particiones de una tabla particionada por hash es un factor del siguiente módulo más grande. Esto permite aumentar el número de particiones de forma incremental sin necesidad de mover todos los datos de una vez. Por ejemplo, supongamos que tiene una tabla particionada por hash con 8 particiones, cada una con módulo 8, pero encuentra necesario aumentar el número de particiones a 16. Puede desacoplar una de las particiones con módulo 8, crear dos nuevas particiones con módulo 16 que cubran la misma porción del espacio de claves (una con un resto igual al resto de la partición desacoplada, y la otra con un resto igual a ese valor más 8), y repoblarlas con datos. Luego puede repetir esto -- quizás en un momento posterior -- para cada partición con módulo 8 hasta que no queden. Aunque esto todavía puede implicar una gran cantidad de movimiento de datos en cada paso, sigue siendo mejor que tener que crear una tabla nueva completa y mover todos los datos de una

vez.

Una partición debe tener los mismos nombres de columnas y tipos que la tabla particionada a la que pertenece. Las modificaciones a los nombres de columnas o tipos de una tabla particionada se propagarán automáticamente a todas las particiones. Las restricciones CHECK se heredarán automáticamente por cada partición, pero una partición individual puede especificar restricciones CHECK adicionales; restricciones adicionales con el mismo nombre y condición que en la padre se fusionarán con la restricción padre. Los valores predeterminados pueden especificarse por separado para cada partición. Pero tenga en cuenta que el valor predeterminado de una partición no se aplica al insertar una tupla a través de una tabla

particionada.

Las filas insertadas en una tabla particionada serán automáticamente enrutadas a la partición correcta. Si no existe una partición adecuada, ocurrirá un

error.

Operaciones como TRUNCATE que normalmente afectan a una tabla y a todos sus hijos de herencia se propagarán a todas las particiones, pero también pueden realizarse en una partición

individual.

Tenga en cuenta que crear una partición usando PARTITION OF requiere tomar un bloqueo ACCESS EXCLUSIVE en la tabla particionada padre. Del mismo modo, eliminar una partición con DROP TABLE requiere tomar un bloqueo ACCESS EXCLUSIVE en la tabla padre. Es posible usar ALTER TABLE ATTACH/DETACH PARTITION para realizar estas operaciones con un bloqueo más déb

il, reduciendo así la interferencia con ope
raciones concurrentes en la tabla particionada.

LIKE source_table [ like_option ...

La cláusula LIKE especifica una tabla de la que la nueva tabla copiará automáticamente todos los nombres de columnas, sus tipos de datos y sus restricciones not-null.

A diferencia de INHERITS, la nueva tabla y la tabla original quedan completamente desacopladas una vez finalizada la creación. Los cambios en la tabla original no se aplicarán a la nueva tabla, y no es posible incluir datos de la nueva tabla en búsquedas de la tabla

original.

También a diferencia de INHERITS, las columnas y restricciones copiadas por LIKE no se fusionan con columnas y restricciones de nombre similar. Si se especifica el mismo nombre explícitamente o en otra cláusula LIKE, se señala un

error.

Las cláusulas opcionales like_option especifican qué propiedades adicionales de la tabla original copiar. Especificar INCLUDING copia la propiedad, especificar EXCLUDING omite la propiedad. EXCLUDING es el predeterminado. Si se hacen múltiples especificaciones para el mismo tipo de objeto, se usa la última. Las opciones disponibles

son:

UNIQUE [ NULLS [ NOT ] DISTINCT ] (restricción de columna)
UNIQUE [ NULLS [ NOT ] DISTINCT ] ( column_name [, ... ] [, column_name WITHOUT OVERLAPS ] ) [ INCLUDE ( column_name [, ...]) ] (restricción de

tabla)
La restricción UNIQUE especifica que un grupo de una o más columnas de una tabla solo puede contener valores únicos. El comportamiento de una restricción única de tabla es el mismo que el de una restricción única de columna, con la capacidad adicional de abarcar múltiples columnas. La restricción por lo tanto garantiza que cualquier dos filas deben diferir en al menos una de estas columnas.

Si se especifica la opción WITHOUT OVERLAPS para la última columna, entonces esa columna se verifica en busca de superposiciones en lugar de igualdad. En ese caso, las otras columnas de la restricción permitirán duplicados siempre que los duplicados no se superpongan en la columna WITHOUT OVERLAPS. (Esto a veces se llama clave temporal, si la columna es un rango de fechas o marcas de tiempo, pero PostgreSQL permite rangos sobre cualquier tipo base.) En efecto, tal restricción se garantiza con una restricción EXCLUDE en lugar de una restricción UNIQUE. Así por ejemplo UNIQUE (id, valid_at WITHOUT OVERLAPS) se comporta como EXCLUDE USING GIST (id WITH =, valid_at WITH &&). La columna WITHOUT OVERLAPS debe tener un tipo de rango o multirango. Los rangos/multirangos vacíos no están permitidos. Las columnas que no son WITHOUT OVERLAPS de la restricción pueden ser de cualquier tipo que pueda compararse por igualdad en un índice GiST. Por defecto, solo se admiten tipos de rango, pero puede usar otros tipos agregando la extensión btree_gist (que es la forma esperada de usar esta característica)

.

Para el propósito de una restricción única, los valores nulos no se consideran iguales, a menos que se especifique NULLS NOT

DISTINCT.

Cada restricción única debe nombrar un conjunto de columnas que sea diferente del conjunto de columnas nombrado por cualquier otra restricción única o clave primaria definida para la tabla. (De lo contrario, las restricciones únicas redundantes serán descartadas.

)

Al establecer una restricción única para una jerarquía de partición de múltiples niveles, todas las columnas en la clave de partición de la tabla particionada de destino, así como las de todas sus tablas particionadas descendientes, deben incluirse en la definición de la

restricción.

Agregar una restricción única creará automáticamente un índice btree único en la columna o grupo de columnas usado en la restricción. Pero si la restricción incluye una cláusula WITHOUT OVERLAPS, usará un índice GiST. El índice creado tiene el mismo nombre que la restricción

única.

La cláusula opcional INCLUDE agrega a ese índice una o más columnas que son simplemente “carga útil”: no se garantiza la unicidad en ellas, y el índice no puede buscarse en f

unción de esas columnas. Sin embargo, pueden recuperarse mediante un escaneo de solo índice. Tenga en cuenta que aunque la restricción no se garantiza en las columnas incluida
s, aún depende de ellas. En consecuencia, algunas operaciones en tales columnas (por ejemplo, DROP COLUMN) pueden causar la eliminación en cascada de restricciones e índices.

La restricción PRIMARY KEY especifica que una columna o columnas de una tabla solo pueden contener valores únicos (no duplicados), no nulos. Solo se puede especificar una clave primaria para una tabla, ya sea como restricción de columna o como restricción de tabla.

La restricción de clave primaria debe nombrar un conjunto de columnas que sea diferente del conjunto de columnas nombrado por cualquier restricción única definida para la misma tabla. (De lo contrario, la restricción única es redundante y será descartada.

PRIMARY KEY garantiza las mismas restricciones de datos que una combinación de UNIQUE y NOT NULL. Sin embargo, identificar un conjunto de columnas como la clave primaria también proporciona metadatos sobre el diseño del esquema, ya que una clave primaria implica que otras tablas pueden depender de este conjunto de columnas como un identificador único para las

filas.

Cuando se coloca en una tabla particionada, las restricciones PRIMARY KEY comparten las restricciones descritas anteriormente para las restricciones

UNIQUE.

Agregar una restricción PRIMARY KEY creará automáticamente un índice btree único en la columna o grupo de columnas usado en la restricción, o GiST si se especificó WITHOUT

OVERLAPS.

La cláusula opcional INCLUDE agrega a ese índice una o más columnas que son simplemente “carga útil”: no se garantiza la unicidad en ellas, y el índice no puede buscarse en f

unción de esas columnas. Sin embargo, pueden recuperarse mediante un escaneo de solo índice. Tenga en cuenta que aunque la restricción no se garantiza en las columnas incluida
s, aún depende de ellas. En consecuencia, algunas operaciones en tales columnas (por ejemplo, DROP COLUMN) pueden causar la eliminación en cascada de restricciones e índices.

La cláusula EXCLUDE define una restricción de exclusión, que garantiza que si se comparan dos filas en la(s) columna(s) o expresión(es) especificada(s) usando el/los operador(es) especificado(s), no todas estas comparaciones devolverán TRUE. Estas cláusulas especifican una restricción de clave foránea, que requiere que un grupo de una o más columnas de la nueva tabla solo contenga valores que coincidan con valores en la(s) columna(s) referenciada(s) de alguna fila de la tabla referenciada. Si la última columna está marcada con PERIOD, se trata de una manera especial. Mientras las columnas que no son PERIOD se comparan por igualdad (y debe haber al menos una de ellas), la columna PERIOD no lo hace. En otras palabras, la referencia debe tener un referente para toda su duración. Esta columna debe ser un tipo de rango o multirango. Además, la tabla referenciada debe tener una clave primaria o restricción única declarada con WITHOUT OVERLAPS. D

El comando CREATE TABLE se ajusta al estándar SQL, con las excepciones listadas a

Tablas

Temporales

Aunque la sintaxis de CREATE TEMPORARY TABLE se asemeja a la del estándar SQL, el efecto no es el mismo. En el estándar, las tablas temporales se definen una sola vez y existen automáticamente (comenzando con contenidos vacíos) en cada sesión que las necesite. PostgreSQL, en cambio, requiere que cada sesión emita su propio comando CREATE TEMPORARY TABLE para cada tabla temporal que vaya a utilizar. Esto permite que diferentes sesiones usen el mismo nombre de tabla temporal para diferentes propósitos, mientras que el enfoque del estándar obliga a que todas las instancias de un nombre de tabla temporal dado tengan la misma estructura de

tabla.

La definición del estándar sobre el comportamiento de las tablas temporales es ampliamente ignorada. El comportamiento de PostgreSQL en este punto es similar al de varias otras bases de datos

SQL.

El estándar SQL también distingue entre tablas temporales globales y locales, donde una tabla temporal local tiene un conjunto separado de contenidos para cada módulo SQL dentro de cada sesión, aunque su definición sigue siendo compartida entre sesiones. Dado que PostgreSQL no soporta módulos SQL, esta distinción no es relevante en

PostgreSQL.

Por compatibilidad, PostgreSQL aceptará las palabras clave GLOBAL y LOCAL en una declaración de tabla temporal, pero actualmente no tienen ningún efecto. El uso de estas palabras clave se desaconseja, ya que versiones futuras de PostgreSQL podrían adoptar una interpretación más conforme al estándar de su

significado.

La cláusula ON COMMIT para tablas temporales también se asemeja al estándar SQL, pero tiene algunas diferencias. Si se o

mite la cláusula ON COMMIT, SQL especifica que el comportamiento predeterminado es ON COMMIT DELETE ROWS. Sin embarg
o, el comportamiento predeterminado en PostgreSQL es ON COMMIT PRESERVE ROWS. La opción ON COMMIT DROP no existe en SQL.
