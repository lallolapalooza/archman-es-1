DESCRIPCIÓ

N

CREATE CAST define una nueva conversión. Una conversión especifica cómo realizar una transformación entre dos tipos de datos. Por

ejemplo, 
SELECT CA
ST(42 AS
float8);

convierte la constante entera 42 al tipo float8 invocando una función previamente especificada, en este caso float8(int4). (Si no se ha definido una conversión adecuada, la transformación falla.

)

Dos tipos pueden ser coercibles binarios, lo que significa que la conversión se puede realizar “gratis” sin invocar ninguna función. Esto requiere que los valores correspondientes usen la misma representación interna. Por ejemplo, los tipos text y varchar son coercibles binarios en ambos sentidos. La coercibilidad binaria no es necesariamente una relación simétrica. Por ejemplo, la conversión de xml a text se puede realizar gratis en la implementación actual, pero la dirección inversa requiere una función que realice al menos una comprobación de sintaxis. (Dos tipos que son coercibles binarios en ambos sentidos también se denominan binariamente compatibles.

)

Puedes definir una conversión como una conversión de E/S usando la sintaxis WITH INOUT. Una conversión de E/S se realiza invocando la función de salida del tipo de datos de origen y pasando la cadena resultante a la función de entrada del tipo de datos de destino. En muchos casos comunes, esta característica evita la necesidad de escribir una función de conversión separada. Una conversión de E/S actúa igual que una conversión basada en función regular; solo la implementación es

diferente.

Por defecto, una conversión solo puede ser invocada por una solicitud de conversión explícita, es decir, una construcción explícita CAST(x AS nombre_tipo) o x::nombre_tipo

.

Si la conversión está marcada como AS ASSIGNMENT, puede ser invocada implícitamente al asignar un valor a una columna del tipo de datos de destino. Por ejemplo, suponiendo que foo.f1 es una columna de tipo text,

entonces: 
INSERT INTO
foo (f1) V
ALUES (42);

se permitirá si la conversión del tipo integer al tipo text está marcada como AS ASSIGNMENT, de lo contrario no. (Generalmente usamos el término conversión de asignación para describir este tipo de conversión.

)

Si la conversión está marcada como AS IMPLICIT, puede ser invocada implícitamente en cualquier contexto, ya sea de asignación o internamente en una expresión. (Generalmente usamos el término conversión implícita para describir este tipo de conversión.) Por ejemplo, considera esta

consulta: 
SELEC
T 2 +
4.0;

El analizador inicialmente marca las constantes como siendo de tipo integer y numeric respectivamente. No hay un operador integer + numeric en los catálogos del sistema, pero sí hay un operador numeric + numeric. La consulta por lo tanto tendrá éxito si hay disponible una conversión de integer a numeric y está marcada como AS IMPLICIT — lo cual de hecho lo está. El analizador aplicará la conversión implícita y resolverá la consulta como si se hubiera

escrito 
SELECT CAST
( 2 AS nume
ric ) + 4.0;

Ahora, los catálogos también proporcionan una conversión de numeric a integer. Si esa conversión estuviera marcada como AS IMPLICIT — lo cual no está — entonces el analizador se enfrentaría a elegir entre la interpretación anterior y la alternativa de convertir la constante numeric a integer y aplicar el operador integer + integer. Sin ningún conocimiento de qué elección preferir, se rendiría y declararía la consulta ambigua. El hecho de que solo una de las dos conversiones sea implícita es la forma en que enseñamos al analizador a preferir la resolución de una expresión mixta de numeric e integer como numeric; no hay conocimiento incorporado sobre

eso.

Es prudente ser conservador al marcar conversiones como implícitas. Un exceso de rutas de conversión implícitas puede causar que PostgreSQL elija interpretaciones sorprendentes de los comandos, o que no pueda resolver comandos en absoluto porque hay múltiples interpretaciones posibles. Una buena regla general es hacer que una conversión sea invocable implícitamente solo para transformaciones que preserven información entre tipos en la misma categoría de tipo general. Por ejemplo, la conversión de int2 a int4 puede razonablemente ser implícita, pero la conversión de float8 a int4 probablemente debería ser solo de asignación. Las conversiones entre categorías de tipo, como text a int4, es mejor hacerlas solo

explícitas.

Nota

A veces es necesario por razones de usabilidad o cumplimiento de estándares proporcionar múltiples conversiones implícitas entre un conjunto de tipos, resultando en ambigüedad que no se puede evitar como arriba. El analizador tiene una heurística de respaldo basada en categorías de tipos y tipos preferidos que puede ayudar a proporcionar el comportamiento deseado en tales casos. Ver CREATE TYPE (CREATE_TYPE(7)) pa

ra más inf
ormación.

Para poder crear una conversión, debes ser propietario del tipo de datos de origen o del destino y tener el priv

ilegio USAGE sobre el otro tipo. Para crear una conversión coercible binaria, debes ser superusuario. (Esta res
tricción se hace porque una conversión coercible binaria errónea puede fácilmente hacer fallar al servidor.)

Las funciones de implementación de conversión pueden tener de uno a tres argumentos. El tipo del primer argumento debe ser idéntico al tipo de origen de la conversión o coercible binariamente desde él. El segundo argumento, si está presente, debe ser de tipo integer; recibe el modificador de tipo asociado con el tipo de destino, o -1 si no hay ninguno. El tercer argumento, si está presente, debe ser de tipo boolean; recibe true si la conversión es una conversión explícita, false en caso contrario. (Extrañamente, el estándar SQL exige comportamientos diferentes para conversiones explícitas e implícitas en algunos casos. Este argumento se proporciona para funciones que deben implementar tales conversiones. No se recomienda que diseñes tus propios tipos de datos de modo que esto importe.

)

El tipo de retorno de una función de conversión debe ser idéntico al tipo de destino de la conversión o coercible binariamente a

él.

Ordinariamente una conversión debe tener tipos de datos de origen y destino diferentes. Sin embargo, se permite declarar una conversión con tipos de origen y destino idénticos si tiene una función de implementación de conversión con más de un argumento. Esto se usa para representar funciones de coerción de longitud específicas de tipo en los catálogos del sistema. La función nombrada se usa para forzar un valor del tipo al valor del modificador de tipo dado por su segundo

argumento.

Cuando una conversión tiene tipos de origen y destino diferentes y una función que toma más de un argumento, soporta convertir de un tipo a otro y aplicar una coerción de longitud en un solo paso. Cuando no hay disponible tal entrada, la coerción a un tipo que usa un modificador de tipo implica dos pasos de conversión, uno para convertir entre tipos de datos y un segundo para aplicar el

modificador.

NOTA

S

Usa DROP CAST para eliminar conversiones definidas por el

usuario.

Recuerda que si quieres poder convertir tipos en ambos sentidos necesitas declarar conversiones en ambos sentidos

explícitamente.

Normalmente no es necesario para crear conversiones entre tipos definidos por el usuario y los tipos de cadena estándar (text,varchar y char( n)), así como tipos definidos por el usuario que están definidos para estar en la categoría de cadenas). PostgreSQL proporciona conversiones automáticas de E/S para eso. Las conversiones automáticas a tipos de cadena se tratan como conversiones de asignación, mientras que las conversiones automáticas desde tipos de cadena son solo explícitas. Puedes anular este comportamiento declarando tu propia conversión para reemplazar una automática, pero generalmente la única razón para hacerlo es si quieres que la conversión sea más fácil de invocar que la configuración estándar de solo asignación o solo explícita. Otra posible razón es que quieres que la conversión se comporte de manera diferente a la función de E/S del tipo; pero eso es lo suficientemente sorprendente como para que pienses dos veces sobre si es una buena idea. (Un pequeño número de tipos integrados sí

tienen

comportamientos diferentes para las conversiones, principalmente debido a requisitos del estándar SQL). Aunque no es obligatorio, se recomienda que continúes siguiendo esta convención antigua de nombrar las funciones de implementación de la conversión con elnombre del tipo de datos de destino. Muchos usuarios están acostumbrados a poder convertir tipos de datos usando una notación de estilo de función, es decir, nombre_tipo( x). Esta notación es de hecho nada más ni nada menos que una llamada a la función de implementación de la conversión; no se trata especialmente como una conversión.
