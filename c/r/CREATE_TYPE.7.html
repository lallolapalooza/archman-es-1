DESCRIPCIÓ

N

CREATE TYPE registra un nuevo tipo de datos para su uso en la base de datos actual. El usuario que define un tipo se convierte en su

propietario.

Si se proporciona un nombre de esquema, el tipo se crea en el esquema especificado. De lo contrario, se crea en el esquema actual. El nombre del tipo debe ser distinto del nombre de cualquier tipo o dominio existente en el mismo esquema. (Debido a que las tablas tienen tipos de datos asociados, el nombre del tipo debe ser también distinto del nombre de cualquier tabla existente en el mismo esquema.

)

Existen cinco formas de CREATE TYPE, como se muestra en la sinopsis de sintaxis anterior. Estas crean respectivamente un tipo compuesto, un tipo enum, un tipo de rango, un tipo base o un tipo de cáscara. Los primeros cuatro de estos se discuten a continuación. Un tipo de cáscara es simplemente un marcador de posición para un tipo a definir más adelante; se crea emitiendo CREATE TYPE sin parámetros excepto el nombre del tipo. Los tipos de cáscara son necesarios como referencias hacia adelante al crear tipos de rango y tipos base, como se discute en esas

secciones.

Tipos

compuestos

La primera forma de CREATE TYPE crea un tipo compuesto. El tipo compuesto se especifica mediante una lista de nombres de atributos y tipos de datos. La colación de un atributo también puede especificarse, si su tipo de datos es colacionable. Un tipo compuesto es esencialmente lo mismo que el tipo de fila de una tabla, pero usar CREATE TYPE evita la necesidad de crear una tabla real cuando todo lo que se quiere es definir un tipo. Un tipo compuesto independiente es útil, por ejemplo, como el argumento o el tipo de retorno de una

función.

Para poder crear un tipo compuesto

, debe tener el privilegio USAGE
en todos los tipos de atributos.

Tipos

enumerados

La segunda forma de CREATE TYPE crea un tipo enumerado (enum), como se describe en la Sección 8.7. Los tipos enum toman una lista de etiquetas entre comillas, cada una de las cuales debe tener menos de NAMEDATALEN bytes de longitud (64 bytes en una compilación estándar de PostgreSQL). (Es posible crear un tipo enumerado con cero etiquetas, pero dicho tipo no se puede usar para contener valores antes de que se agregue al menos una etiqueta usando ALTER

TYP
E.)

Tipos de

rango

La tercera forma de CREATE TYPE crea un nuevo tipo de rango, como se describe en la Sección 8.

17.

El subtipo del tipo de rango puede ser cualquier tipo con una clase de operadores b-tree asociada (para determinar el ordenamiento de los valores para el rango del tipo). Normalmente se usa la clase de operadores b-tree predeterminada del subtipo para determinar el ordenamiento; para usar una clase de operadores no predeterminada, especifique su nombre con subtype_opclass. Si el subtipo es colacionable, y desea usar una colación no predeterminada en el ordenamiento del rango, especifique la colación deseada con la opción coll

ation.

La función canónica opcional debe tomar un argumento de el tipo de rango que se está definiendo, y devolver un valor del mismo tipo. Esto se usa para convertir valores de rango a una forma canónica, cuando corresponda. Vea la Sección 8.17.8 para más información. Crear una función canónica es un poco complicado, ya que debe definirse antes de que el tipo de rango pueda declararse. Para hacer esto, primero debe crear un tipo de cáscara, que es un tipo de marcador de posición que no tiene propiedades excepto un nombre y un propietario. Esto se hace emitiendo el comando CREATE TYPE nombre, sin parámetros adicionales. Luego, la función puede declararse usando el tipo de cáscara como argumento y resultado, y finalmente el tipo de rango puede declararse usando el mismo nombre. Esto reemplaza automáticamente la entrada del tipo de cáscara con un rango de tipo

válido.

La función subtype_diff opcional debe tomar dos valores de el tipo subtipo como argumento, y devolver un valor de precisión doble que represente la diferencia entre los dos valores dados. Aunque esto es opcional, proporcionarlo permite una mayor eficiencia de los índices GiST en columnas del tipo de rango. Vea la Sección 8.17.8 para más

información.

El parámetro multirange_type_name opcional especifica el nombre del tipo multirango correspondiente. Si no se especifica, este nombre se elige automáticamente de la siguiente manera. Si el nombre del tipo de rango contiene el subcadena range, en

tonces el nombre del tipo multirango se forma reemplazando la subcadena range con multirange en el nombre del tipo de rang
o. De lo contrario, el nombre del tipo multirange se forma añadiendo un sufijo _multirange al nombre del tipo de rango.

Tipos

base

La cuarta forma de CREATE TYPE crea un nuevo tipo base (tipo escalar). Para crear un nuevo tipo base, debe ser un superusuario. (Esta restricción se hace porque una definición de tipo errónea podría confundir o incluso hacer fallar al servidor.

)

Los parámetros pueden aparecer en cualquier orden, no solo en el ilustrado anteriormente, y la mayoría son opcionales. Debe registrar dos o más funciones (usando CREATE FUNCTION) antes de definir el tipo. Las funciones de soporte input_function y output_function son requeridas, mientras que las funciones receive_function, send_function, type_modifier_input_function, type_modifier_output_function, analyze_function, y subscript_function son opcionales. Generalmente estas funciones deben estar codificadas en C u otro lenguaje de bajo

nivel.

La función input_function convierte la representación textual externa del tipo a la representación interna usada por los operadores y funciones definidas para el tipo. La función output_function realiza la transformación inversa. La función de entrada puede declararse como tomando un argumento de tipo cstring, o como tomando tres argumentos de tipos cstring, oid, integer. El primer argumento es el texto de entrada como una cadena C, el segundo argumento es el OID del propio tipo (excepto para los tipos de array, que en su lugar reciben el OID de su tipo de elemento), y el tercero es el typmod de la columna de destino, si se conoce (-1 se pasará si no). La función de entrada debe devolver un valor del propio tipo de datos. Usualmente, una función de entrada debe declararse como STRICT; si no lo es, se llamará con un primer parámetro NULL cuando se lea un valor de entrada NULL. La función debe seguir devolviendo NULL en este caso, a menos que lance un error. (Este caso está destinado principalmente a soportar funciones de entrada de dominio, que podrían necesitar rechazar entradas NULL.) La función de salida debe declararse como tomando un argumento del nuevo tipo de datos. La función de salida debe devolver el tipo cstring. Las funciones de salida no se invocan para valores

NULL.

La función receive_function opcional convierte la representación binaria externa del tipo a la representación interna. Si esta función no se proporciona, el tipo no puede participar en la entrada binaria. La representación binaria debería elegirse para ser barata de convertir a forma interna, siendo razonablemente portable. (Por ejemplo, los tipos de datos enteros estándar usan el orden de bytes de la red como la representación binaria externa, mientras que la representación interna está en el orden de bytes nativo de la máquina.) La función de recepción debe realizar una verificación adecuada para asegurar que el valor es válido. La función de recepción puede declararse como tomando un argumento de tipo internal, o como tomando tres argumentos de tipos internal, oid, integer. El primer argumento es un puntero a un búfer StringInfo que contiene el recrecibido cadena de bytes; los argumentos opcionales son los mismos que para la función de entrada de texto. La función de recepción debe devolver un valor del propio tipo de datos. Normalmente, una función de recepción debe declararse como STRICT; si no lo está, se llamará con un primer parámetro NULL cuando se lea un valor de entrada NULL. La función aún debe devolver NULL en este caso, a menos que lance un error. (Este caso está destinado principalmente a soportar funciones de recepción de dominios, que podrían necesitar rechazar entradas NULL.) De manera similar, el opcional send_function convierte de la representación interna a la representación binaria externa. Si esta función no se proporciona, el tipo no puede participar en la salida binaria. La función de envío debe declararse como tomando un argumento del nuevo tipo de datos. La función de envío debe devolver el tipo bytea. Las funciones de envío no se invocan para valores

NULL.

En este punto, debería estar preguntándose cómo las funciones de entrada y salida pueden declararse para tener resultados o argumentos del nuevo tipo, cuando deben crearse antes de que el nuevo tipo pueda crearse. La respuesta es que el tipo debe definirse primero como un tipo de cáscara, que es un tipo de marcador de posición que no tiene propiedades excepto un nombre y un propietario. Esto se hace emitiendo el comando CREATE TYPE name, sin parámetros adicionales. Luego, las funciones de E/S en C pueden definirse haciendo referencia al tipo de cáscara. Finalmente, CREATE TYPE con una definición completa reemplaza la entrada de la cáscara con una definición de tipo completa y válida, después de la cual el nuevo tipo puede usarse

normalmente.

El opcional type_modifier_input_function y type_modifier_output_function son necesarios si el tipo soporta modificadores, es decir, restricciones opcionales adjuntas a una declaración de tipo, como char(5) o numeric(30,2). PostgreSQL permite que los tipos definidos por el usuario tomen una o más constantes simples o identificadores como modificadores. Sin embargo, esta información debe ser capaz de empaquetarse en un único valor entero no negativo para almacenarse en los catálogos del sistema. El type_modifier_input_function recibe el(los) modificador(es) declarado(s) en forma de un array de cstring. Debe verificar la validez de los valores (lanzando un error si son incorrectos) y, si son correctos, devolver un único valor entero no negativo que se almacenará como la columna “typmod”. Los modificadores de tipo se rechazarán si el tipo no tiene un type_modifier_input_function. El type_modifier_output_function convierte el valor entero interno typmod de vuelta a la forma correcta para la visualización del usuario. Debe devolver un valor cstring que sea la cadena exacta a añadir al nombre del tipo; por ejemplo, la función de numeric podría devolver (30,2). Se permite omitir el type_modifier_output_function, en cuyo caso el formato de visualización predeterminado es simplemente el valor entero typmod almacenado encerrado entre

paréntesis.

El opcional analyze_function realiza la recopilación de estadísticas específicas del tipo para columnas del tipo de datos. Por defecto, ANALYZE intentará recopilar estadísticas usando los operadores “equals” y “less-than” del tipo, si hay una clase de operador b-tree predeterminada para el tipo. Para tipos no escalares, este comportamiento probablemente no sea adecuado, por lo que puede ser anulado especificando una función de análisis personalizada. La función de análisis debe declararse para tomar un único argumento de tipo internal y devolver un resultado booleano. La API detallada para las funciones de análisis aparece en src/include/commands/vacuum.

h.

El opcional subscript_function permite que el tipo de datos sea subíndice en comandos SQL. Especificar esta función no hace que el tipo sea considerado un tipo de array “verdadero”; por ejemplo, no será un candidato para el tipo de resultado de constructos ARRAY[]. Pero si subíndicear un valor del tipo es una notación natural para extraer datos de él, entonces un subscript_function puede escribirse para definir lo que eso significa. La función de subíndice debe declararse para tomar un único argumento de tipo internal y devolver un resultado internal, que es un puntero a una estructura de métodos (funciones) que implementan el subíndice. La API detallada para las funciones de subíndice aparece en src/include/nodes/subscripting.h. También puede ser útil leer la implementación de arrays en src/backend/utils/adt/arraysubs.c, o el código más simple en contrib/hstore/hstore_subs.c. Información adicional aparece en Tipos de Array más

abajo.

Si bien los detalles de la representación interna del nuevo tipo solo son conocidos por las funciones de E/S y otras funciones que cree para trabajar con el tipo, hay varias propiedades de la representación interna que deben declararse a PostgreSQL. La más importante de estas es internallength. Los tipos de datos base pueden ser de longitud fija, en cuyo caso internallength es un entero positivo, o de longitud variable, indicado por establecer internallength a VARIABLE. (Internamente, esto se representa estableciendo typlen a -1.) La representación interna de todos los tipos de longitud variable debe comenzar con un entero de 4 bytes que indique la longitud total de este valor del tipo. (Tenga en cuenta que el campo de longitud a menudo está codificado, como se describe en la Sección 66.2; no es prudente acceder a él directamente.

)

El indicador opcional PASSEDBYVALUE indica que los valores de este tipo de datos se pasan por valor, en lugar de por referencia. Los tipos pasados por valor deben ser de longitud fija, y su representación interna no puede ser mayor que el tamaño del tipo Datum (4 bytes en algunas máquinas, 8 bytes en otras)

.

El parámetro alignment especifica la alineación de almacenamiento requerida para el tipo de datos. Los valores permitidos equivalen a una alineación en límites de 1, 2, 4 u 8 bytes. Tenga en cuenta que los tipos de longitud variable deben tener una alineación de al menos 4, ya que necesariamente contienen un int4 como su primer

componente.

El parámetro storage permite la selección de estrategias de almacenamiento para tipos de datos de longitud variable. (Solo se permite plain para tipos de longitud fija.) plain especifica que los datos del tipo siempre se almacenarán en línea y no se comprimirán. extended especifica que el sistema primero intentará comprimir un valor de datos largo, y moverá el valor fuera de la fila principal de la tabla si aún es demasiado largo. external permite que el valor se mueva fuera de la tabla principal, pero el sistema no intentará comprimirlo. main permite la compresión, pero desaconseja mover el valor fuera de la tabla principal. (Los elementos de datos con esta estrategia de almacenamiento podrían moverse aún fuera de la tabla principal si no hay otra manera de hacer que una fila quepa, pero se mantendrán en la tabla principal preferentemente sobre elementos extended y external.

)

Todos los valores de storage distintos de plain implican que las funciones del tipo de datos pueden manejar valores que han sido toasteados, como se describe en la Sección 66.2 y la Sección 36.13.1. El valor específico de otro tipo dado simplemente determina la estrategia de almacenamiento TOAST predeterminada para columnas de un tipo de datos toasteable; los usuarios pueden elegir otras estrategias para columnas individuales usando ALTER TABLE SET

STORAGE.

El parámetro like_type proporciona un método alternativo para especificar las propiedades básicas de representación de un tipo de datos: copiarlas de algún tipo existente. Los valores de internallength, passedbyvalue, alignment y storage se copian del tipo nombrado. (Es posible, aunque generalmente indeseable, anular algunos de estos valores especificándolos junto con la cláusula LIKE.) Especificar la representación de esta manera es especialmente útil cuando la implementación de bajo nivel del nuevo tipo “aprovecha” un tipo existente de alguna

manera.

Los parámetros category y preferred pueden usarse para ayudar a controlar qué conversión implícita se aplicará en situaciones ambiguas. Cada tipo de datos pertenece a una categoría nombrada por un solo carácter ASCII, y cada tipo es “preferred” o no dentro de su categoría. El analizador preferirá convertir a tipos preferidos (pero solo desde otros tipos dentro de la misma categoría) cuando esta regla sea útil para resolver funciones u operadores sobrecargados. Para más detalles, véase el Capítulo 10. Para tipos que no tienen conversiones implícitas hacia o desde ningún otro tipo, es suficiente dejar estas configuraciones en sus valores predeterminados. Sin embargo, para un grupo de tipos relacionados que tienen conversiones implícitas, a menudo es útil marcarlos todos como pertenecientes a una categoría y seleccionar uno o dos de los tipos “más generales” como preferidos dentro de la categoría. El parámetro category es especialmente útil al añadir un tipo definido por el usuario a una categoría incorporada existente, como los tipos numéricos o de cadena. Sin embargo, también es posible crear nuevas categorías de tipos completamente definidas por el usuario. Seleccione cualquier carácter ASCII que no sea una letra mayúscula para nombrar tal

categoría.

Se puede especificar un valor predeterminado, en caso de que un usuario desee que las columnas del tipo de datos tengan un valor predeterminado distinto del valor nulo. Especifique el valor predeterminado con la palabra clave DEFAULT. (Tal valor predeterminado puede ser anulado por una cláusula DEFAULT explícita adjunta a una columna particular.

)

Para indicar que un tipo es un tipo de array de longitud fija, especifique el tipo de los elementos del array usando la palabra clave ELEMENT. Por ejemplo, para definir un array de enteros de 4 bytes (int4), especifique ELEMENT = int4. Para más detalles, véase Tipos de Array más

abajo.

Para indicar el delimitador a usar entre valores en la representación externa de arrays de este tipo, delimiter puede establecerse a un carácter específico. El delimitador predeterminado es la coma (,). Tenga en cuenta que el delimitador está asociado con el tipo de elemento del array, no con el tipo de array en

sí.

Si el parámetro booleano opcional collatable es verdadero, las definiciones de columna y expresiones del tipo pueden llevar información de colación a través del uso de la cláusula COLLATE. Corresponde a las imp

lementaciones de las funciones que operan sobre el tipo hacer uso real de la información de
colación; esto no ocurre automáticamente simplemente al marcar el tipo como colacionable.

Tipos de

Array

Siempre que se crea un tipo definido por el usuario, PostgreSQL crea automáticamente un tipo de array asociado, cuyo nombre consiste en el nombre del tipo de elemento precedido por un guion bajo, y truncado si es necesario para mantenerlo con menos de NAMEDATALEN bytes de longitud. (Si el nombre así generado colisiona con un nombre de tipo existente, el proceso se repite hasta que se encuentra un nombre que no colisione.) Este tipo de array creado implícitamente es de longitud variable y usa las funciones de entrada y salida incorporadas array_in y array_out. Además, este tipo es el que el sistema usa para constructos como ARRAY[] sobre el tipo definido por el usuario. El tipo de array rastrea cualquier cambio en el propietario o esquema de su tipo de elemento, y se elimina si el tipo de elemento se

elimina.

Podría preguntarse razonablemente por qué existe una opción ELEMENT, si el sistema crea automáticamente el tipo de array correcto. El caso principal donde es útil usar ELEMENT es cuando está haciendo un tipo de longitud fija que internamente es un array de una cantidad de cosas idénticas, y quiere permitir que estas cosas se accedan directamente por subíndice, además de cualquier operación que planee proporcionar para el tipo como un todo. Por ejemplo, typunto se representa como solo dos números de punto flotante, a los que se puede acceder usando point[0] y point[1]. Tenga en cuenta que esta funcionalidad solo funciona para tipos de longitud fija cuya forma interna es exactamente una secuencia de campos idénticos de longitud fija. Por razones históricas (es decir, esto es claramente incorrecto pero ya es demasiado tarde para cambiarlo), el indexado de tipos de matriz de longitud fija comienza desde cero, en lugar de desde uno

como

en las matrices de longitud variable. Especificar la opción SUBSCRIPT permite que un tipo de datos sea indexado, aunque el sistema no lo considere de otro modo como un tipo de matriz. El comportamiento descrito anteriormente para las matrices de longitud fija está realmente implementado por el manejador de SUBSCRIPT raw_array_subscript_handler, que se usa automáticamente si especifica ELEMENT para un tipo de longi

tud

fija sin escribir también SUBSCRIPT. Al especificar una función SUBSCRIPT personalizada, no es necesario especificar ELEMENT a menos que el manejador de SUBSCRIPT necesite consultar typelem para saber qué devolver. Tenga en cuenta que especificar ELEMENT hace que el sistema asuma que el nuevo tipo contiene, o depende físicam

ejemplo, no se permitirá cambiar las propiedades del

NOTAS Debido a que no hay restricciones en el uso de un tipo de datos una vez que ha sido creado, crear un tipo base o un tipo de rango equivale a otorgar permiso de ejecución público sobre las funciones mencionadas en la definición del tipo. Esto generalmente no es un problema para los tipos de funciones que son útiles en una definición de tipo. Aunque este sigue siendo generalmente el caso, el nombre del tipo de matriz puede variar de esto en caso de nombres de longitud máxima o colisiones con nombres de tipo de usuario que comienzan con guion bajo. Por lo tanto, está desaconsejado escribir código que dependa de esta convención. En su lugar, use pg_type.

Antes de la versión 8.2 de PostgreSQL, la sintaxis de creación de tipo de carcasa CREATE TYPE name no existía. La forma de crear un nuevo tipo base era crear primero su función de entrada. En este enfoque, PostgreSQL primero verá el nombre del nuevo tipo de datos como el tipo de retorno de la función de entrada. El tipo de carcasa se crea implícitamente en esta situación, y luego puede ser referenciado en las definiciones de las demás funciones de E/S. Este enfoque todavía funciona, pero está desaconsejado y podría no permitirse en alguna versión futura.
