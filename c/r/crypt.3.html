DESCRIPCIÓ

N

Las funciones crypt, crypt_r, crypt_rn y crypt_ra "hashean" de forma irreversible la frase de contraseña para almacenarla en la base de datos de contraseñas del sistema (shadow(5)) utilizando un "método de hash" criptográfico. El resultado de esta operación se denomina "frase de contraseña hasheada" o simplemente "hash". Los métodos de hash se describen en crypt(

5).

setting controla qué método de hash usar, y también proporciona varios parámetros al método elegido, siendo el más importante una "sal" aleatoria que asegura que no haya dos hashes almacenados iguales, incluso si las frases de contraseña son las

mismas.

El argumento data de crypt_r es una estructura de tipo struct crypt_data. Tiene al menos estos

campos: 
struct crypt_data {
    char output[CRYPT_OUTPUT_SIZE];
    char setting[CRYPT_OUTPUT_SIZE];
    char input[CRYPT_MAX_PASSPHRASE_SIZE];
    char initialized;
}
;

Tras un retorno exitoso de crypt_r, la frase de contraseña hasheada se almacenará en output. Se anima a las aplicaciones, aunque no es obligatorio, a usar los campos input y setting para almacenar las cadenas que pasarán como frase de contraseña de entrada y setting a crypt_r. Esto facilitará borrar todos los datos sensibles cuando ya no sean

necesarios.

El campo initialized debe establecerse a cero antes de la primera vez que un objeto struct crypt_data se use en una llamada a crypt_r(). Recomendamos poner a cero todo el objeto, no solo initialized y no solo los campos documentados, antes del primer uso. (Por supuesto, hágalo antes de almacenar algo en setting y input

.)

El argumento data de crypt_rn también debe apuntar a un objeto struct crypt_data, y size debe ser el tamaño de ese objeto, convertido a int. Cuando se usa con crypt_rn, todo el objeto data (excepto los campos input y setting) debe ponerse a cero antes de su primer uso; esto no es solo una recomendación, como lo es para crypt_r. De lo contrario, los campos del objeto tienen los mismos usos que para crypt_r

.

En la primera llamada a crypt_ra, data debe ser la dirección de una variable void * establecida en NULL, y size debe ser la dirección de una variable int establecida en cero. crypt_ra asignará e inicializará un objeto struct crypt_data, usando malloc(3), y escribirá su dirección y tamaño en las variables apuntadas por data y size. Estos pueden reutilizarse en llamadas posteriores. Después de que la aplicación termine de hashear frases de contraseña, debe desasignar el objeto struct crypt_data usando free

(3
).

VALORES DE

RETORNO

Tras una finalización exitosa, crypt, crypt_r, crypt_rn y crypt_ra devuelven un puntero a una cadena que codifica tanto la frase de contraseña hasheada como la configuración utilizada para codificarla. Esta cadena es directamente utilizable como setting en otras llamadas a crypt, crypt_r, crypt_rn y crypt_ra, y como prefijo en llamadas a crypt_gensalt, crypt_gensalt_rn y crypt_gensalt_ra. Será completamente ASCII imprimible y no contendrá espacios en blanco ni los caracteres ‘:’, ‘;’, ‘*’, ‘!’ o ‘\’. Vea crypt(5) para más detalles sobre el formato de las frases de contraseña

hasheadas.

crypt coloca su resultado en un área de almacenamiento estática, que será sobrescrita por llamadas posteriores a crypt. No es seguro llamar a crypt desde múltiples hilos simultáneamente. Tampoco se recomienda usar el puntero devuelto como argumento para otra llamada a crypt, ya que algunas implementaciones, incluyendo versiones anteriores de libxcrypt, pueden sobrescribir el búfer de salida estático subyacente antes de calcular el

hash.

crypt_r, crypt_rn y crypt_ra colocan su resultado en el campo output de su argumento data. Es seguro llamarlos desde múltiples hilos simultáneamente, siempre que se use un objeto data separado para cada hilo. Tampoco se recomienda usar el puntero devuelto como argumento para otra llamada a crypt_r, crypt_rn y crypt_ra usando el mismo objeto data para llamadas posteriores, ya que algunas implementaciones, incluyendo versiones anteriores de libxcrypt, pueden sobrescribir el campo output del argumento data pasado antes de calcular el hash. Llamar a crypt_ra con los parámetros frase de contraseña y/o setting ubicados dentro de un objeto data pasado que sea más pequeño que el tamaño de struct crypt_data no se recomienda, ya que algunas implementaciones, incluyendo versiones anteriores de libxcrypt, pueden no preservar los literales pasados, si el objeto data necesita ser

alterado.

Tras un error, crypt_r, crypt_rn y crypt_ra escriben un hash inválido en el campo output de su argumento data, y crypt escribe un hash inválido en su área de almacenamiento estática. Esta cadena será más corta que 13 caracteres, comenzará con un ‘*’ y no se comparará igual a setting

.

Tras un error, crypt_rn y crypt_ra devuelven un puntero nulo. crypt_r y crypt también pueden devolver un puntero nulo, o pueden devolver un puntero al hash inválido, dependiendo de cómo se configuró libcrypt. (La opción de devolver el hash inválido es para compatibilidad con aplicaciones antiguas que asumen que crypt no puede devolver un puntero nulo. Véase NOTAS DE PORTABILIDAD más abajo.

)

NOTAS DE

PORTABILIDAD

crypt está incluido en POSIX, pero crypt_r, crypt_rn y crypt_ra no forman parte de ningún

estándar.

POSIX no especifica ningún método de hash, y no requiere que las frases de contraseña con hash sean portables entre sistemas. En la práctica, las frases de contraseña con hash son portables siempre que ambos sistemas soporten el método de hash que se utilizó. Sin embargo, el conjunto de métodos de hash soportados varía considerablemente de un sistema a

otro.

El comportamiento de crypt en caso de error no está bien estandarizado. Algunas implementaciones simplemente no pueden fallar (excepto haciendo que el programa se bloquee), otras devuelven un puntero nulo o una cadena fija. La mayoría de las implementaciones no establecen errno, pero algunas sí. POSIX especifica devolver un puntero nulo y establecer errno, pero solo define un error posible, ENOSYS, en el caso de que crypt no esté soportado en absoluto. Algunas aplicaciones antiguas no están preparadas para manejar punteros nulos devueltos por crypt. El comportamiento descrito anteriormente para esta implementación, establecer errno y devolver un hash inválido diferente de la configuración, se elige para hacer que estas aplicaciones fallen de forma segura cuando ocurre un

error.

Debido a restricciones históricas sobre la exportación de software criptográfico desde los Estados Unidos, crypt es un componente opcional de POSIX. Las aplicaciones deben estar preparadas para que crypt no esté disponible, o para que siempre falle (estableciendo errno a ENOSYS) en tiempo de

ejecución.

POSIX especifica que crypt se declara en <unistd.h>, pero solo si la macro _XOPEN_CRYPT está definida y tiene un valor mayor o igual a cero. Dado que libcrypt no proporciona <unistd.h>, declara crypt, crypt_r, crypt_rn y crypt_ra en <crypt.h> en su

lugar.

En una minoría de sistemas (notablemente versiones recientes de Solaris), crypt usa un búfer de almacenamiento estático específico de hilo, lo que lo hace seguro para llamar desde múltiples h

ilos simultáneamente, pero no evita que cada llamada dent
ro de un hilo sobrescriba los resultados de la anterior.

ERRORES

CONOCIDOS

Algunas implementaciones de crypt, en caso de error, devuelven un hash inválido almacenado en una ubicación de solo lectura o que solo se inicializa una vez, lo que significa que solo es seguro borrar el búfer apuntado por el valor de retorno de crypt si no ocurrió un

error.

struct crypt_data puede ser bastante grande (32kB en esta implementación de libcrypt; más de 128kB en algunas otras implementaciones). Es lo suficientemente grande como para que pueda ser imprudente asignarlo en la

pila.

Algunos métodos de hash diseñados recientemente necesitan aún más memoria temporal, pero la interfaz crypt_r hace imposible cambiar el tamaño de struct crypt_data sin romper la compatibilidad binaria. La interfaz crypt_rn podría acomodar asignaciones más grandes para métodos de hash específicos, pero el llamador de crypt_rn no tiene forma de saber cuánta memoria asignar. crypt_ra hace la asignación por sí misma, pero solo puede hacer una sola llamada a mallo

c(3
).
