NOMBR

CREATE_POLICY - define una n

ueva política de seguridad a
nivel de fila para una tabla

SINOPSI

S 
CREATE POLICY nombre ON nombre_tabla
    [ AS { PERMISSIVE | RESTRICTIVE } ]
    [ FOR { ALL | SELECT | INSERT | UPDATE | DELETE } ]
    [ TO { nombre_rol | PUBLIC | CURRENT_ROLE | CURRENT_USER | SESSION_USER } [, ...] ]
    [ USING ( expresión_using ) ]
    [ WITH CHECK ( expresión_check )
]

DESCRIPCIÓ

N

El comando CREATE POLICY define una nueva política de seguridad a nivel de fila para una tabla. Tenga en cuenta que la seguridad a nivel de fila debe estar habilitada en la tabla (usando ALTER TABLE ... ENABLE ROW LEVEL SECURITY) para que las políticas creadas se

apliquen.

Una política otorga el permiso para seleccionar, insertar, actualizar o eliminar filas que coincidan con la expresión de política relevante. Las filas existentes de la tabla se verifican contra la expresión especificada en USING, mientras que las nuevas filas que se crearían mediante INSERT o UPDATE se verifican contra la expresión especificada en WITH CHECK. Cuando una expresión USING devuelve true para una fila dada, esa fila es visible para el usuario, mientras que si devuelve false o null, la fila no es visible. Cuando una expresión WITH CHECK devuelve true para una fila, esa fila se inserta o actualiza, mientras que si devuelve false o null, se produce un

error.

Para las sentencias INSERT, UPDATE y MERGE, las expresiones WITH CHECK se aplican después de que se disparen los disparadores BEFORE y antes de que se realicen modificaciones reales de datos. Así, un disparador BEFORE ROW puede modificar los datos a insertar, afectando el resultado de la verificación de la política de seguridad. Las expresiones WITH CHECK se aplican antes que cualquier otra

restricción.

Los nombres de las políticas son por tabla. Por lo tanto, un nombre de política puede usarse para muchas tablas diferentes y tener una definición para cada tabla que sea apropiada para esa

tabla.

Las políticas pueden aplicarse para comandos específicos o para roles específicos. El valor predeterminado para las políticas recién creadas es que se apliquen a todos los comandos y roles, a menos que se especifique lo contrario. Varias políticas pueden aplicarse a un solo comando; consulte más abajo para más detalles. La Tabla 300 resume cómo los diferentes tipos de política se aplican a comandos

específicos.

Para las políticas que pueden tener tanto expresiones USING como WITH CHECK (ALL y UPDATE), si no se define una expresión WITH CHECK, la expresión USING se usará tanto para determinar qué filas son visibles (caso USING normal) como qué nuevas filas se permitirán agregar (caso WITH CHECK)

.

Si la seguridad a nivel de fila está habilitada para una tabla, pero no

existen políticas aplicables, se asume una política de "denegación pre
determinada", de modo que no será visible ni actualizable ninguna fila.

PARÁMETRO

S

nombr

e
El nombre de la política a crear. Este debe ser distinto del nombre de cualquier otra política de la
tabla.

nombre_tabl

a
El nombre (opcionalmente calificado por esquema) de la tabla a la que se aplica la
política.

PERMISSIV

E
Especifica que la política debe crearse como una política permisiva. Todas las políticas permisivas aplicables a una consulta dada se combinarán usando el operador booleano "OR". Al crear políticas permisivas, los administradores pueden agregar al conjunto de registros que pueden ser accedidos. Las políticas son permisivas por
defecto.

RESTRICTIV

E
Especifica que la política debe crearse como una política restrictiva. Todas las políticas restrictivas aplicables a una consulta dada se combinarán usando el operador booleano "AND". Al crear políticas restrictivas, los administradores pueden reducir el conjunto de registros que pueden ser accedidos, ya que todas las políticas restrictivas deben ser superadas para cada registro.

Tenga en cuenta que debe haber al menos una política permisiva para otorgar acceso a los registros antes de que las políticas restrictivas puedan usarse

de manera útil para reducir ese acceso. Si solo existen políticas restrictivas, no será accesible ningún registro. Cuando hay una mezcla de políticas pe
rmisivas y restrictivas, un registro solo es accesible si al menos una de las políticas permisivas se supera, además de todas las políticas restrictivas.

comman

d
El comando al que se aplica la política. Las opciones válidas son ALL, SELECT, INSERT, UPDATE y DELETE. ALL es el valor predeterminado. Consulte más abajo para conocer los detalles sobre cómo se
aplican.

nombre_ro

l
El rol o roles a los que se aplicará la política. El valor predeterminado es PUBLIC, lo que aplicará la política a todos los
roles.

expresión_usin

g
Cualquier expresión condicional SQL (que devuelva booleano). La expresión condicional no puede contener ninguna función de agregado o de ventana. Esta expresión se agregará a las consultas que se refieran a la tabla si la seguridad a nivel de fila está habilitada. Las filas para las que la expresión devuelve true serán visibles. Cualquier fila para la que la expresión devuelva false o null no será visible para el usuario (en un SELECT), y no estará disponible para su modificación (en un UPDATE o DELETE). Dichas filas se suprimen silenciosamente; no se informa ningún
error.

expresión_chec

k
Cualquier expresión condicional SQL (que devuelva booleano). La expresión condicional no puede contener ninguna función de agregado o de ventana. Esta expresión se usará en las consultas INSERT y UPDATE contra la tabla si la seguridad a nivel de fila está habilitada. Solo se permitirán las filas para las que la expresión se evalúe como true. Se lanzará un error si la expresión se evalúa como false o null para cualquiera de los registros insertados o de los registros que resulten de la actualización. Tenga en cuenta que la expresión_check se evalúa contra el nuevo contenido propuesto de la fila, no contra el contenido
original.

Políticas por

Comando

AL

L
Usar ALL para una política significa que se aplicará a todos los comandos, independientemente del tipo de comando. Si existe una política ALL y existen políticas más específicas, se aplicarán tanto la política ALL como la política (o políticas) más específica. Además, las políticas ALL se aplicarán tanto al lado de selección de una consulta como al lado de modificación, usando la expresión USING en ambos casos si solo se ha definido una expresión USING.

Como ejemplo, si se emite un UPDATE, la política ALL será aplicable tanto a lo que el UPDATE podrá seleccionar como filas a actualizar (aplicando la expresión USING), como a las filas resultantes actualizadas, para verificar si se les permite agregarlas a la tabla (aplicando la expresión WITH CHECK, si está definida, y la expresión USING en caso contrario). Si un comando INSERT o UPDATE intenta agregar filas a la tabla que no superan la expresió

n WITH CHECK de la política ALL,
el comando completo se abortará.

SELEC

T
Usar SELECT para una política significa que se aplicará a las consultas SELECT y siempre que se requieran permisos SELECT en la relación para la que se define la política. El resultado es que solo se devolverán durante una consulta SELECT aquellos registros de la relación que superen la política SELECT, y que las consultas que requieren permisos SELECT, como UPDATE, también verán solo los registros que permita la política SELECT. Una política SELECT no puede tener una expresión WITH CHECK, ya que solo se aplica en los casos en que se recuperan registros de la
relación.

INSER

T
Usar INSERT para una política significa que se aplicará a los comandos INSERT y a los comandos MERGE que contengan acciones INSERT. Las filas que se inserten y no superen esta política resultarán en un error de violación de política, y el comando INSERT completo se abortará. Una política INSERT no puede tener una expresión USING, ya que solo se aplica en los casos en que se agregan registros a la relación.

Tenga en cuenta que INSERT con ON CONFLICT DO UPDATE verifi

ca las expresiones WITH CHECK de las políticas INSERT solo
para las filas agregadas a la relación por la ruta INSERT.

UPDAT

E
Usar UPDATE para una política significa que se aplicará a los comandos UPDATE, SELECT FOR UPDATE y SELECT FOR SHARE, así como a las cláusulas auxiliares ON CONFLICT DO UPDATE de los comandos INSERT. Los comandos MERGE que contengan acciones UPDATE también se ven afectados. Dado que UPDATE implica obtener un registro existente y reemplazarlo con un nuevo registro modificado, las políticas UPDATE aceptan tanto una expresión USING como una expresión WITH CHECK. La expresión USING determina qué registros verá el comando UPDATE para operar sobre ellos, mientras que la expresión WITH CHECK define qué filas modificadas se permiten almacenar de vuelta en la relación.

Cualquier fila cuyos valores actualizados noss la expresión WITH CHECK causará un error, y el comando completo se abortará. Si solo se especifica una cláusula USING, entonces esa cláusula se usará tanto para los casos USING como para los casos WITH

CHECK.

Normalmente, un comando UPDATE también necesita leer datos de columnas en la relación que se está actualizando (por ejemplo, en una cláusula WHERE o una cláusula RETURNING, o en una expresión en el lado derecho de la cláusula SET). En este caso, también se requieren permisos SELECT en la relación que se está actualizando, y se aplicarán las políticas SELECT o ALL apropiadas además de las políticas UPDATE. Por lo tanto, el usuario debe tener acceso a la(s) fila(s) que se actualizan a través de una política SELECT o ALL además de tener permiso para actualizar la(s) fila(s) a través de una política UPDATE o

ALL.

Cuando un comando INSERT tiene una cláusula auxiliar ON CONFLICT DO UPDATE , si se toma la ruta UPDATE, la fila que se va a actualizar se verifica primero contra las expresiones USING de cualquier política UPDATE, y luego la nueva fila actualizada se verifica contra las expresiones WITH CHECK. Sin embargo, ten en cuenta que, a diferencia de un comando UPDATE independiente, si la fila existente no pasa las expresiones USING, se lanzará un error (la ruta UPDATE nunca se evitar

á en si
lencio).

DELET

E
Usar DELETE para una política significa que se aplicará a comandos DELETE. Solo las filas que pasen esta política serán vistas por un comando DELETE. Puede haber filas que sean visibles a través de un SELECT pero que no estén disponibles para ser eliminadas, si no pasan la expresión USING para la política DELETE.

En la mayoría de los casos, un comando DELETE también necesita leer datos de columnas en la relación de la que está eliminando (por ejemplo, en una cláusula WHERE o una cláusula RETURNING). En este caso, también se requieren permisos SELECT en la relación, y se aplicarán las políticas SELECT o ALL apropiadas además de las políticas DELETE. Por lo tanto, el usuario debe tener acceso a la(s) fila(s) que se eliminan a través de una política SELECT o ALL además de tener permiso para eliminar la(s) fila(s) a través de una política DELETE o

ALL.

Una política DELETE no puede tener una expresión WITH CHECK, ya que

solo se aplica en los casos en que se están eliminando registros
de la relación, de modo que no hay una nueva fila que verificar.

Aplicación de Múltiples

Políticas

Cuando se aplican múltiples políticas de diferentes tipos de comando al mismo comando (por ejemplo,
políticas SELECT y UPDATE aplicadas a un comando UPDATE), entonces el usuario debe tener ambos tipos de permisos (por ejemplo, permiso para seleccionar filas de la relación así como permiso para actualizarlas). Por lo tanto, las expresiones para un tipo de política se combinan con las expresiones para el otro tipo de política usando el operador

AND.

Cuando se aplican múltiples políticas del mismo tipo de comando al mismo comando, entonces debe haber al menos una política PERMISSIVE que otorgue acceso a la relación, y todas las políticas RESTRICTIVE deben pasar. Por lo tanto, todas las expresiones de política PERMISSIVE se combinan usando OR, todas las expresiones de política RESTRICTIVE se combinan usando AND, y los resultados se combinan usando AND. Si no hay políticas PERMISSIVE, entonces se deniega el

acceso.

Ten en cuenta que, para los fines de combinar múltiples políticas, las políticas ALL se tratan como si tuvieran el mismo tipo que cualquier otro tipo de política que se esté

aplicando.

Por ejemplo, en un comando UPDATE que requiere tanto permisos SELECT como UPDATE, si hay múltiples políticas aplicables de cada tipo, se combinarán de la siguiente

manera: 
expresión de la política RESTRICTIVE SELECT/ALL 1
AND
expresión de la política RESTRICTIVE SELECT/ALL 2

NOTA

S

Debes ser el propietario de una tabla para crear o cambiar políticas para

ella.

Aunque se aplicarán políticas para consultas explícitas contra tablas en la base de datos, no se aplican cuando el sistema está realizando comprobaciones internas de integridad referencial o validando restricciones. Esto significa que hay formas indirectas de determinar que un valor dado existe. Un ejemplo de esto es intentar insertar un valor duplicado en una columna que es una clave primaria o tiene una restricción única. Si la inserción falla, entonces el usuario puede inferir que el valor ya existe. (Este ejemplo asume que la política permite al usuario insertar registros que no le está permitido ver.) Otro ejemplo es cuando se permite a un usuario insertar en una tabla que hace referencia a otra, de lo contrario oculta. La existencia puede ser determinada por el usuario insertando valores en la tabla que hace referencia, donde el éxito indicaría que el valor existe en la tabla referenciada. Estos problemas se pueden abordar creando cuidadosamente políticas para evitar que los usuarios puedan insertar, eliminar o actualizar registros en absoluto que podrían posiblemente indicar un valor que no pueden ver de otra manera, o usando valores generados (por ejemplo, claves sustitutas) en lugar de claves con significados

externos.

Generalmente, el sistema hará cumplir las condiciones de filtro impuestas usando políticas de seguridad antes de las calificaciones que aparecen en las consultas del usuario, para evitar la exposición inadvertida de los datos protegidos a funciones definidas por el usuario que podrían no ser confiables. Sin embargo, las funciones y operadores marcados por el sistema (o el administrador del sistema) como LEAKPROOF pueden ser evaluados antes de las expresiones de política, ya que se asume que son

confiables.

Dado que las expresiones de política se añaden directamente a la consulta del usuario, se ejecutarán con los permisos del usuario que ejecuta la consulta general. Por lo tanto, los usuarios que usan una política dada deben poder acceder a cualquier tabla o función referenciada en la expresión o simplemente recibirán un error de permiso denegado al intentar consultar la tabla que tiene habilitada la seguridad a nivel de fila. Sin embargo, esto no cambia cómo funcionan las vistas. Como con consultas y vistas normales, las comprobaciones de permisos y las políticas para las tablas que son referenciadas por una vista usarán los permisos del propietario de la vista y cualquier política que se aplique al propietario de la vista, excepto si la vista está definida usando la opción security_invoker (ver CREATE VI

EW).

No existe una política separada para MERGE. En su lugar, las políticas definidas para SELECT, INSERT, UPDATE y DELETE se aplican mientras se ejecuta MERGE, dependiendo de las acciones que se

realicen.
