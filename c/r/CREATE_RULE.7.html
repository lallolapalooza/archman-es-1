NOMBRE

CREATE_RULE - define una nueva regla de reescritura

SINOPSIS

CREATE [ OR REPLACE ] RULE nombre AS ON evento
    TO nombre_tabla [ WHERE condición ]
    DO [ ALSO | INSTEAD ] { NOTHING | comando | ( comando ; comando ... ) }
donde evento puede ser uno de los siguientes:
    SELECT | INSERT | UPDATE | DELETE

DESCRIPCIÓN

CREATE RULE define una nueva regla que se aplica a una tabla o vista especificada. CREATE OR REPLACE RULE creará una nueva regla o reemplazará una regla existente con el mismo nombre para la misma tabla.

El sistema de reglas de PostgreSQL permite definir una acción alternativa que se realizará en inserciones, actualizaciones o eliminaciones en tablas de bases de datos. En términos generales, una regla hace que se ejecuten comandos adicionales cuando se ejecuta un comando determinado en una tabla determinada. Alternativamente, una regla INSTEAD puede reemplazar un comando dado por otro, o hacer que un comando no se ejecute en absoluto. Las reglas también se utilizan para implementar vistas SQL. Es importante darse cuenta de que una regla es realmente un mecanismo de transformación de comandos, o una macro de comandos. La transformación ocurre antes de que comience la ejecución del comando. Si realmente desea una operación que se active de forma independiente para cada fila física, probablemente desee usar un disparador (trigger), no una regla. Puede encontrar más información sobre el sistema de reglas en el Capítulo 39.

Actualmente, las reglas ON SELECT solo pueden adjuntarse a vistas. Dicha regla debe llamarse "_RETURN", debe ser una regla INSTEAD incondicional y debe tener una acción que consista en un único SELECT comando. Este comando define los contenidos visibles de la vista. (La vista en sí es básicamente una tabla ficticia sin almacenamiento). Lo mejor es considerar dicha regla como un detalle de implementación. Aunque se puede redefinir una vista mediante CREATE OR REPLACE RULE "_RETURN" AS ..., es mejor estilo usar CREATE OR REPLACE VIEW.

Puede crear la ilusión de una vista actualizable definiendo reglas ON INSERT, ON UPDATE y ON DELETE (o cualquier subconjunto de ellas que sea suficiente para sus propósitos) para reemplazar las acciones de actualización en la vista con actualizaciones apropiadas en otras tablas. Si desea admitir INSERT RETURNING y demás, asegúrese de incluir una cláusula RETURNING adecuada en cada una de estas reglas.

Hay un inconveniente si intenta usar reglas condicionales para actualizaciones complejas de vistas: debe existir una regla INSTEAD incondicional para cada acción que desee permitir en la vista. Si la regla es condicional o no es INSTEAD, el sistema aún rechazará los intentos de realizar la acción de actualización, porque cree que podría terminar intentando realizar la acción en la tabla ficticia de la vista en algunos casos. Si desea manejar todos los casos útiles en reglas condicionales, agregue una regla incondicional DO INSTEAD NOTHING para asegurarse de que el sistema entienda que nunca se le pedirá que actualice la tabla ficticia. Luego haga que las reglas condicionales no sean INSTEAD; en los casos en que se apliquen, se suman a la acción INSTEAD NOTHING predeterminada. (Sin embargo, este método no funciona actualmente para admitir consultas RETURNING.)


Nota

Una vista que sea lo suficientemente simple como para ser automáticamente actualizable (ver CREATE VIEW (CREATE_VIEW(7))) no requiere una regla creada por el usuario para ser actualizable. Aunque puede crear una regla explícita de todos modos, la transformación de actualización automática generalmente superará el rendimiento de una regla explícita.

Otra alternativa que vale la pena considerar es usar disparadores INSTEAD OF (ver CREATE TRIGGER (CREATE_TRIGGER(7))) en lugar de reglas.

PARÁMETROS

nombre

El nombre de la regla a crear. Este debe ser distinto del nombre de cualquier otra regla para la misma tabla. Se aplican múltiples reglas en la misma tabla y del mismo tipo de evento en orden alfabético de nombre.

evento

El evento es uno de SELECT, INSERT, UPDATE o DELETE. Tenga en cuenta que un INSERT que contenga una cláusula ON CONFLICT no puede usarse en tablas que tengan reglas INSERT o UPDATE. Considere usar una vista actualizable en su lugar.

nombre_tabla

El nombre (opcionalmente calificado por esquema) de la tabla o vista a la que se aplica la regla.

condición

Cualquier expresión condicional SQL (que devuelva booleano). La expresión de condición no puede referirse a ninguna tabla excepto NEW y OLD, y no puede contener funciones de agregación.

INSTEAD

INSTEAD indica que los comandos deben ejecutarse en lugar de el comando original.

ALSO

ALSO indica que los comandos deben ejecutarse además de el comando original.

Si no se especifica ALSO ni INSTEAD, ALSO es el valor predeterminado.

comando

El comando o comandos que componen la acción de la regla. Los comandos válidos son SELECT, INSERT, UPDATE, DELETE, o NOTIFY.

Dentro de condición y comando, se pueden usar los nombres de tablas especiales NEW y OLD para referirse a valores en la tabla referenciada. NEW es válido en reglas ON INSERT y ON UPDATE para referirse a la fila que se está insertando o actualizando. OLD es válido en reglas ON UPDATE y ON DELETE para referirse a la fila existente que se está actualizando o eliminando.

NOTAS

Debe ser el propietario de una tabla para crear o cambiar reglas para ella.

En una regla para INSERT, UPDATE o DELETE en una vista, puede agregar una cláusula RETURNING que emita las columnas de la vista. Esta cláusula se usará para calcular las salidas si la regla es activada por un INSERT RETURNING, UPDATE RETURNINGo DELETE RETURNING comando respectivamente. Cuando la regla es activada por un comando sin RETURNING, la cláusula RETURNING de la regla será ignorada. La implementación actual solo permite que las reglas INSTEAD incondicionales contengan RETURNING; además, puede haber como máximo una cláusula RETURNING entre todas las reglas para el mismo evento. (Esto asegura que solo haya una cláusula RETURNING candidata para usar al calcular los resultados.) Las consultas RETURNING en la vista serán rechazadas si no hay ninguna cláusula RETURNING en ninguna regla disponible.

Es muy importante tener cuidado de evitar reglas circulares. Por ejemplo, aunque cada una de las dos definiciones de reglas siguientes es aceptada por PostgreSQL, el SELECT comando haría que PostgreSQL informara un error debido a la expansión recursiva de una regla:

CREATE RULE "_RETURN" AS
    ON SELECT TO t1
    DO INSTEAD
        SELECT * FROM t2;
CREATE RULE "_RETURN" AS
    ON SELECT TO t2
    DO INSTEAD
        SELECT * FROM t1;
SELECT * FROM t1;

Actualmente, si una acción de regla contiene un NOTIFY comando, el NOTIFY comando se ejecutará incondicionalmente, es decir, el NOTIFY se emitirá incluso si no hay filas a las que la regla deba aplicarse. Por ejemplo, en:

CREATE RULE notify_me AS ON UPDATE TO mytable DO ALSO NOTIFY mytable;
UPDATE mytable SET name = 'foo' WHERE id = 42;

un NOTIFY evento se enviará durante el UPDATE, haya o no filas que coincidan con la condición id = 42. Esta es una restricción de implementación que podría corregirse en versiones futuras.

COMPATIBILIDAD

CREATE RULE es una extensión del lenguaje PostgreSQL, al igual que todo el sistema de reescritura de consultas.

VER TAMBIÉN
