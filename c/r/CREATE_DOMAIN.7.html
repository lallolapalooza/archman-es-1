DESCRIPCIÓ

N

CREATE DOMAIN crea un nuevo dominio. Un dominio es esencialmente un tipo de datos con restricciones opcionales (restricciones sobre el conjunto permitido de valores). El usuario que define un dominio se convierte en su

propietario.

Si se proporciona un nombre de esquema (por ejemplo, CREATE DOMAIN myschema.mydomain ...) entonces el dominio se crea en el esquema especificado. De lo contrario, se crea en el esquema actual. El nombre del dominio debe ser único entre los tipos y dominios existentes en su

esquema.

Los dominios son útiles para abstraer las restricciones comunes de los campos en un solo lugar para su mantenimiento. Por ejemplo, varias tablas podrían contener columnas de dirección de correo electrónico, todas requiriendo la misma restricción CHECK para verificar la sintaxis de la dirección. Defina un dominio en lugar de configurar la restricción de cada tabla individualmente

.

Para poder crear un dominio, d

ebe tener el privilegio USAGE
sobre el tipo subyacente.

PARÁMETRO

S

nombr

e
El nombre (opcionalmente calificado por esquema) de un dominio a ser
creado.

tipo_de_dato

s
El tipo de datos subyacente del dominio. Esto puede incluir especificadores de
matriz.

ordenació

n
Una ordenación opcional para el dominio. Si no se especifica ninguna ordenación, el dominio tiene el mismo comportamiento de ordenación que su tipo de datos subyacente. El tipo subyacente debe ser ordenable si se especifica
COLLATE.

DEFAULT expresió

n
La cláusula DEFAULT especifica un valor predeterminado para las columnas del tipo de datos del dominio. El valor es cualquier expresión sin variables (pero no se permiten subconsultas). El tipo de datos de la expresión predeterminada debe coincidir con el tipo de datos del dominio. Si no se especifica un valor predeterminado, entonces el valor predeterminado es el valor nulo.

La expresión predeterminada se utilizará en cualquier operación de inserción que no especifique un valor para la columna. Si se d

efine un valor predeterminado para una columna particular, este anula cualquier valor predeterminado asociado con el dominio.
A su vez, el valor predeterminado del dominio anula cualquier valor predeterminado asociado con el tipo de datos subyacente.

CONSTRAINT nombre_de_restricció

n
Un nombre opcional para una restricción. Si no se especifica, el sistema genera un
nombre.

NOT

NULL
Se impide que los valores de este dominio sean nulos (pero vea las notas a continuación)
.

NUL

L
Se permite que los valores de este dominio sean nulos. Este es el valor predeterminado.

Esta cláusula está destinada solo a la compati

bilidad con bases de datos SQL no estándar.
Su uso se desaconseja en nuevas aplicaciones.

CHECK (expresión

)
Las cláusulas CHECK especifican restricciones de integridad o pruebas que los valores del dominio deben satisfacer. Cada restricción debe ser una expresión que produzca un resultado booleano. Debe usar la palabra clave VALUE para referirse al valor que se está probando. Las expresiones que evalúan a TRUE o UNKNOWN tienen éxito. Si la expresión produce un resultado FALSE, se informa un error y no se permite que el valor sea convertido al tipo de dominio.

Actualmente, las expresiones CHECK no pueden contener subconsultas ni referirse a variables distintas de

VALUE.

Cuando un dominio tiene múltiples restricciones CHECK, se

probarán en orden alfabético por nombre. (Las versiones de
PostgreSQL anteriores a la 9.5 no respetaban ningún orden
de activación particular para las restricciones CHECK.)

NOTA

S

Las restricciones de dominio, particularmente NOT NULL, se verifican al convertir un valor al tipo de dominio. Es posible que una columna que nominalmente es del tipo de dominio se lea como nula a pesar de que exista tal restricción. Por ejemplo, esto puede suceder en una consulta de unión externa, si la columna del dominio está en el lado anulable de la unión externa. Un ejemplo más sutil

es 
INSERT INTO tab (domcol) VALUES ((SELECT domcol FROM tab WHERE false)
)
;

La sub-SELECT escalar vacía producirá un valor nulo que se considera que es del tipo de dominio, por lo que no se aplica ninguna verificación de restricción adicional a ella, y la inserción tendrá

éxito.

Es muy difícil evitar tales problemas, debido a la suposición general del SQL de que un valor nulo es un valor válido de cada tipo de datos. La mejor práctica, por lo tanto, es diseñar las restricciones de un dominio de modo que se permita un valor nulo, y luego aplicar restricciones NOT NULL a las columnas del tipo de dominio según sea necesario, en lugar de aplicarlas directamente al tipo de

dominio.

PostgreSQL asume que las condiciones de las restricciones CHECK son inmutables, es decir, siempre darán el mismo resultado para el mismo valor de entrada. Esta suposición es lo que justifica examinar las restricciones CHECK solo cuando un valor se convierte por primera vez a un tipo de dominio, y no en otros momentos. (Esto es esencialmente lo mismo que el tratamiento de las restricciones CHECK de tabla, como se describe en la Sección 5.5.1.

)

Un ejemplo común de cómo romper esta suposición es referirse a una función definida por el usuario en una expresión CHECK, y luego cambiar el comportamiento de esa función. PostgreSQL no lo prohíbe, pero no notará si hay valores almacenados del tipo de dominio que ahora violan la restricción CHECK. Eso causaría que un volcado y restauración posteriores de la base de datos fallaran. La forma recomendada de manejar tal cambio es eliminar la restricción (usando ALTER DOMAIN), ajustar la definición de la función, y volver a añadir la restricción, re-verificándola así contra los datos

almacenados.

También es una buena práctica asegu

rarse de que las expresiones CH
ECK del dominio no generen errores.

:

   VALUE ~ '^\d{5}$'
