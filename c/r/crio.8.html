DESCRIPCIÓN

Implementación basada en OCI del Demonio de la Interfaz de Runtime de Contenedores de Kubernetes

crio está diseñado para proporcionar una ruta de integración entre los runtimes conformes con OCI y el kubelet. Específicamente, implementa la Interfaz de Runtime de Contenedores (CRI) de Kubelet utilizando runtimes conformes con OCI. El alcance de crio está ligado al alcance de la CRI.

1.
Soporta múltiples formatos de imagen, incluyendo los formatos de imagen existentes de Docker y OCI.
2.
Soporte para múltiples medios para descargar imágenes, incluyendo confianza y verificación de imágenes.
3.
Gestión de imágenes de contenedores (gestión de capas de imagen, sistemas de archivos de superposición, etc.).
4.
Gestión del ciclo de vida de los procesos de los contenedores.
5.
Monitoreo y registro necesarios para satisfacer la CRI.
6.
Aislamiento de recursos según lo requiera la CRI.

Uso:

crio [OPCIONES GLOBALES] comando [OPCIONES DE COMANDO] [ARGUMENTOS...]

OPCIONES GLOBALES

--absent-mount-sources-to-reject="": Una lista de rutas que, cuando estén ausentes en el host, causarán que la creación de un contenedor falle (a diferencia del comportamiento actual de crear un directorio).

--add-inheritable-capabilities: Añade capacidades al conjunto heredable, así como al grupo por defecto de permitidas, de límite y efectivas.

--additional-devices="": Dispositivos para añadir a los contenedores.

--allowed-devices="": Dispositivos que un usuario tiene permitido especificar con la anotación permitida "io.kubernetes.cri-o.Devices". (por defecto: "/dev/fuse", "/dev/net/tun")

--apparmor-profile="": Nombre del perfil de apparmor a usar como el perfil por defecto del runtime. Esto solo tiene efecto si el usuario no especifica un perfil a través de la anotación de metadatos del Pod de Kubernetes. (por defecto: "crio-default")

--auto-reload-registries: Si es verdadero, CRI-O recargará automáticamente el registro de mirrors cuando haya una actualización en el directorio 'registries.conf.d'. El valor por defecto está establecido en 'false'.

--big-files-temporary-dir="": Ruta al directorio temporal a usar para almacenar archivos grandes, utilizado para almacenar blobs de imágenes y flujos de datos relacionados con la gestión de imágenes de contenedores.

--bind-mount-prefix="": Un prefijo a usar para el origen de los montajes de enlace (bind mounts). Esta opción sería útil si estuvieras ejecutando CRI-O en un contenedor. Y tuvieras '/' montado en '/host' en tu contenedor. Entonces, si ejecutaras CRI-O con la opción '--bind-mount-prefix=/host', CRI-O añadiría /host a cualquier montaje de enlace que se le entregue a través de CRI. Si Kubernetes pidiera tener '/var/lib/foobar' montado por enlace en el contenedor, entonces CRI-O montaría por enlace '/host/var/lib/foobar'. Dado que CRI-O en sí mismo se está ejecutando en un contenedor con '/' o el host montado en '/host', el contenedor terminaría con '/var/lib/foobar' del host montado en el contenedor en lugar de '/var/lib/foobar' del contenedor de CRI-O.

--blockio-config-file="": Ruta al archivo de configuración de clases de blockio para configurar el controlador de blockio de cgroup.

--blockio-reload: Recarga blockio-config-file y vuelve a escanear los dispositivos blockio en el sistema antes de aplicar los parámetros de blockio.

--cdi-spec-dirs="": Directorios para escanear en busca de archivos de especificación CDI. (por defecto: "/etc/cdi", "/run/cdi")

--cgroup-manager="": Gestor de cgroup (cgroupfs o systemd). (por defecto: "systemd")

--clean-shutdown-file="": Ubicación para que CRI-O coloque el archivo de apagado limpio. Indica si hemos tenido tiempo para sincronizar los cambios en el disco antes de apagar. Si no se encuentra, crio wipe borrará el directorio de almacenamiento. (por defecto: "/var/lib/crio/clean.shutdown")

--cni-config-dir="": Directorio de archivos de configuración de CNI. (por defecto: "/etc/cni/net.d/")

--cni-default-network="": Nombre de la red CNI por defecto a seleccionar. Si no está establecido o es "", entonces CRI-O seleccionará el primero que encuentre en --cni-config-dir.

--cni-plugin-dir="": Directorio de binarios de plugins de CNI.

--collection-period="": El número de segundos entre la recopilación de estadísticas de pods/contenedores y métricas de sandbox de pods. Si se establece en 0, las métricas/estadísticas se recopilan bajo demanda. (por defecto: 0)

--config, -c="": Ruta al archivo de configuración (por defecto: "/etc/crio/crio.conf")

--config-dir, -d="": Ruta al directorio de configuración drop-in.
Este directorio se iterará recursivamente y cada archivo se aplicará
a la configuración en su orden de procesamiento. Esto significa que un
archivo de configuración llamado '00-default' tiene una prioridad más baja que un archivo
llamado '01-my-overwrite'.
El archivo de configuración global, proporcionado a través de '--config,-c' o por defecto en
/etc/crio/crio.conf, asiempre tiene una prioridad inferior que los archivos en el directorio especificado por '--config-dir,-d'.
Además de eso, los parámetros de línea de comandos proporcionados tienen una prioridad más alta
que cualquier archivo de configuración. (predeterminado: "/etc/crio/crio.conf.d") --conmon ="": Ruta al binario de conmon, utilizado para monitorear el runtime OCI. Se buscará usando $PATH si está vacío. Esta opción está obsoleta y será eliminada en el futuro.

Cada archivo '*.json' en la ruta configura un hook para los contenedores de

Para más detalles sobre la sintaxis de los archivos JSON y la semántica de la inyección de hooks, ver 'oci-hooks(5)'.

CRI-O

actualmente soporta tanto los esquemas de hooks 1.0.0 y 0.1.0, aunque el esquema 0.1.0 está obsoleto. Esta opción puede establecerse múltiples veces; las rutas de las opciones

posteriores

tienen mayor precedencia ('oci-hooks(5)' discute la precedencia de los directorios).
Para las condiciones de anotación, CRI-O usa las anotaciones de Kubernetes, que son un subconjunto de las anotaciones pasadas al
runtime OCI. Por ejemplo, 'io.kubernetes.cri-o.Volumes' es parte de las anotaciones de configuración del runtime OCI, pero no es parte de
las anotaciones de Kubernetes que se emparejan para los hooks.
Para las condiciones de montaje bind, solo se consideran los montajes solicitados explícitamente por la configuración de Kubernetes. Los montajes bind que CRI-O inserta por defecto (por ejemplo, '/dev/shm') no se consideran.
