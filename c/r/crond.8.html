CRON(8) Administración del Sistema CRON(8)

NOMBRE

crond - demonio para ejecutar comandos programados

SINOPSIS

crond [-c | -h | -i | -n | -p | -P | -s | -m<comandocorreo>]
crond -x [ext,sch,proc,pars,load,misc,test,bit]
crond -V

DESCRIPCIÓN

Cron se inicia desde /etc/rc.d/init.d o /etc/init.d cuando se utilizan scripts sysvinit clásicos. En caso de que systemd esté habilitado, entonces el archivo de unidad se instala en /lib/systemd/system/crond.service y el demonio se inicia con el comando systemctl start crond.service. Retorna inmediatamente, por lo tanto, no es necesario iniciarlo con el parámetro '&'.

Cron busca en /var/spool/cron los archivos crontab que llevan el nombre de las cuentas en /etc/passwd; los crontabs encontrados se cargan en memoria. Cron también busca en /etc/anacrontab y en cualquier archivo en el directorio /etc/cron.d, que tienen un formato diferente (ver crontab(5)). Cron examina todos los crontabs almacenados y verifica cada trabajo para ver si necesita ejecutarse en el minuto actual. Al ejecutar comandos, cualquier salida se envía por correo al propietario del crontab (o al usuario especificado en la variable de entorno MAILTO en el crontab, si existe). Cualquier salida de trabajo también puede enviarse a syslog usando la opción -s.

Hay dos formas de verificar los cambios en los crontables. El primer método es verificar la marca de tiempo de un archivo. El segundo método es usar el soporte inotify. El uso de inotify se registra en el registro /var/log/cron después de que se inicia el demonio. El soporte inotify verifica los cambios en todos los crontables y accede al disco solo cuando se detecta un cambio.

Cuando se utiliza la opción de marca de tiempo, Cron verifica las marcas de tiempo de sus crontables cada minuto para buscar cambios y recarga los crontables que han cambiado. No es necesario reiniciar Cron después de que se modificaron algunos de los crontables. La opción de marca de tiempo también se utiliza cuando inotify no se puede inicializar.

Cron verifica estos archivos y directorios:

/etc/crontab
crontab del sistema. Hoy en día, el archivo está vacío por defecto. Originalmente, se usaba comúnmente para ejecutar trabajos diarios, semanales y mensuales. Por defecto, estos trabajos ahora se ejecutan a través de anacron, que lee el archivo de configuración /etc/anacrontab. Ver anacrontab(5) para más detalles.
/etc/cron.d/
directorio que contiene cronjobs del sistema almacenados para diferentes usuarios.
/var/spool/cron
directorio que contiene crontables de usuario creados por el comando crontab.

Tenga en cuenta que el comando crontab(1) actualiza la marca de tiempo del directorio spool cada vez que cambia un crontab.

Horario de verano y otros cambios de hora

Los cambios de hora local de menos de tres horas, como los causados por los cambios de horario de verano, se manejan de manera especial. Esto solo se aplica a los trabajos que se ejecutan a una hora específica y a los trabajos que se ejecutan con una granularidad mayor a una hora. Los trabajos que se ejecutan con más frecuencia se programan normalmente.

Si la hora se ajustó una hora hacia adelante, los trabajos que se habrían ejecutado en el intervalo que se omitió se ejecutarán inmediatamente. A la inversa, si la hora se ajustó hacia atrás, se evita ejecutar el mismo trabajo dos veces.

Los cambios de hora de más de 3 horas se consideran correcciones del reloj o de la zona horaria, y la nueva hora se utiliza de inmediato.

Es posible utilizar diferentes zonas horarias para los crontables. Ver crontab(5) para más información.

Control de acceso PAM

Cron admite el control de acceso con PAM si el sistema tiene PAM instalado. Para más información, ver pam(8). Un archivo de configuración PAM para crond se instala en /etc/pam.d/crond. El demonio carga el entorno PAM del módulo pam_env. Esto puede ser anulado definiendo configuraciones específicas en el archivo crontab apropiado.

OPCIONES

-h
Muestra un mensaje de ayuda y sale.
-i
Deshabilita el soporte inotify.
-m
Esta opción te permite especificar un comando de shell para usar al enviar la salida de correo de Cron en lugar de usar sendmail(8). Este comando debe aceptar un mensaje de correo completamente formateado (con encabezados) en la entrada estándar y enviarlo como un mensaje de correo a los destinatarios especificados en los encabezados de correo. Especificar la cadena off (es decir, crond -m off) deshabilitará el envío de correo.
-n
Indica al demonio que se ejecute en primer plano. Esto puede ser útil al iniciarlo desde init. Con esta opción, es necesario cambiar la configuración de pam. /etc/pam.d/crond no debe habilitar el módulo pam_loginuid.so.
-f
lo mismo que -n, consistente con otras implementaciones de crond.
-p
Permite a Cron aceptar cualquier crontable establecido por el usuario.
-P
No establecer PATH. PATH se hereda del entorno.
-c
Esta opción habilita el soporte de clúster, como se describe a continuación.
-s
Esta opción dirigirá Cron a enviar la salida del trabajo al registro del sistema utilizando syslog(3). Esto es útil si su sistema no tiene sendmail(8) instalado o si el correo está deshabilitado.
-x
Esta opción te permite establecer indicadores de depuración.
-V
Imprime la versión y sale.

SEÑALES

Cuando se recibe SIGHUP, el demonio Cron cerrará y reabrirá su archivo de registro. Esto resulta útil en scripts que rotan y archivan archivos de registro. Naturalmente, esto no es relevante si Cron fue compilado para usar syslog(3).

SOPORTE DE CLÚSTER

En esta versión de Cron es posible utilizar un /var/spool/cron compartido montado en red a través de un clúster de hosts y especificar que solo uno de los hosts ejecute los trabajos del crontab en este directorio a la vez. Esto se hace iniciando Cron con la opción -c, y haciendo que el archivo /var/spool/cron/.cron.hostname contenga una sola línea, que representa el nombre de host del host en el clúster que debe ejecutar los trabajos. Si este archivo no existe, o el nombre de host en él no coincide con el devuelto por gethostname(2), entonces se ignoran todos los archivos crontab en este directorio. Esto no tiene ningún efecto en los cronjobs especificados en el archivo /etc/crontab ni en los archivos del directorio /etc/cron.d. Estos archivos siempre se ejecutan y se consideran específicos del host.

En lugar de editar directamente /var/spool/cron/.cron.hostname, use la opción -n de crontab(1) para especificar el host.

Debe asegurarse de que todos los hosts de un clúster, y el servidor de archivos desde el cual montan el directorio crontab compartido, tengan relojes estrechamente sincronizados, por ejemplo, usando ntpd(8), de lo contrario los resultados serán muy impredecibles.

El uso compartido de clúster deshabilita automáticamente el soporte inotify, ya que no se puede confiar en inotify con sistemas de archivos compartidos montados en red.

ADVERTENCIAS

Todos los archivos crontab deben ser archivos regulares o enlaces simbólicos a archivos regulares, no deben ser ejecutables ni escribibles para nadie más que el propietario.
