DESCRIPCIÓ

N

La Herramienta de Base de Datos de Certificados, certutil, es una utilidad de línea de comandos que puede crear y modificar bases de datos de certificados y claves. Específicamente, puede listar, generar, modificar o eliminar certificados, crear o cambiar la contraseña, generar nuevos pares de claves pública y privada, mostrar el contenido de la base de datos de claves o eliminar pares de claves dentro de la base de datos de

claves.

La emisión de certificados, parte del proceso de gestión de claves y certificados, requiere que las claves y certificados se creen en la base de datos de claves. Este documento discute la gestión de bases de datos de certificados y claves. Para información sobre la gestión de la base de datos del módulo de seguridad, consulta la página del man

ual de m
odutil.

Creación de Nuevas Bases de Datos de Seguridad

Los certificados, claves y módulos de seguridad relacionados con la gestión de certificados se almacenan en tres bases de datos relacionadas:

•cert8.db o cert9.db
•key3.db o key4.db
•secmod.db o pkcs11.txt

Estas bases de datos deben crearse antes de que se puedan generar certificados o claves.

certutil -N -d directory

Creación de una Solicitud de Certificado

Una solicitud de certificado contiene la mayor parte o toda la información que se utiliza para generar el certificado final. Esta solicitud se envía por separado a una autoridad de certificación y luego se aprueba mediante algún mecanismo (automáticamente o mediante revisión humana). Una vez aprobada la solicitud, se genera el certificado.

$ certutil -R -k key-type-or-id [-q pqgfile|curve-name] -g key-size -s subject [-h tokenname] -d directory [-p phone] [-o output-file] [-a]

Las opciones de comando -R requieren cuatro argumentos:

•-k para especificar el tipo de clave a generar o, al renovar un certificado, el par de claves existente a utilizar
•-g para establecer el tamaño de clave de la clave a generar
•-s para establecer el nombre del sujeto del certificado
•-d para proporcionar el directorio de la base de datos de seguridad

La nueva solicitud de certificado puede exportarse en formato ASCII (-a) o escribirse en un archivo especificado (-o).

Por ejemplo:

$ certutil -R -k rsa -g 1024 -s "CN=John Smith,O=Example Corp,L=Mountain View,ST=California,C=US" -d $HOME/nssdb -p 650-555-0123 -a -o cert.cer
Generando clave. Esto puede tardar unos momentos...

Creación de un Certificado

Un certificado válido debe ser emitido por una CA confiable. Esto se puede hacer especificando un certificado de CA (-c) que esté almacenado en la base de datos de certificados. Si no hay un par de claves de CA disponible, puede crear un certificado autofirmado usando el argumento -x con la opción de comando -S.

$ certutil -S -k rsa|dsa|ec -n certname -s subject [-c issuer |-x] -t trustargs -d directory [-m serial-number] [-v valid-months] [-w offset-months] [-p phone] [-1] [-2] [-3] [-4] [-5 keyword] [-6 keyword] [-7 emailAddress] [-8 dns-names] [--extAIA] [--extSIA] [--extCP] [--extPM] [--extPC] [--extIA] [--extSKID]

La serie de números y las opciones --ext* establecen extensiones de certificado que se pueden agregar al certificado cuando es generado por la CA. Se mostrarán indicaciones interactivas.

Por ejemplo, esto crea un certificado autofirmado:

$ certutil -S -s "CN=Example CA" -n my-ca-cert -x -t "C,C,C" -1 -2 -5 -m 3650

Las indicaciones interactivas para el uso de la clave y si alguna extensión es crítica, así como las respuestas, se omiten por brevedad.

A partir de ahí, los nuevos certificados pueden hacer referencia al certificado autofirmado:

$ certutil -S -s "CN=My Server Cert" -n my-server-cert -c "my-ca-cert" -t ",," -1 -5 -6 -8 -m 730

Generación de un Certificado a partir de una Solicitud de Certificado

Cuando se crea una solicitud de certificado, se puede generar un certificado utilizando la solicitud y luego haciendo referencia a un certificado firmante de la autoridad de certificación (el *emisor* especificado en el argumento -c). El certificado emisor debe estar en la base de datos de certificados en el directorio especificado.

certutil -C -c issuer -i cert-request-file -o output-file [-m serial-number] [-v valid-months] [-w offset-months] -d directory [-1] [-2] [-3] [-4] [-5 keyword] [-6 keyword] [-7 emailAddress] [-8 dns-names]

Por ejemplo:

$ certutil -C -c "my-ca-cert" -i /home/certs/cert.req -o cert.cer -m 010 -v 12 -w 1 -d $HOME/nssdb -1 nonRepudiation,dataEncipherment -5 sslClient -6 clientAuth -7 jsmith@example.com

Actualizando o Fusionando las Bases de Datos de

Seguridad

Muchas redes o aplicaciones pueden estar usando versiones antiguas de BerkeleyDB de la base de datos de certificados (cert8.db). Las bases de datos pueden actualizarse a la nueva versión SQLite de la base de datos (cert9.db) usando la opción de comando --upgrade-merge o las bases de datos existentes pueden fusionarse con las nuevas bases de datos cert9.db usando la comando ---

merge.

La comando --upgrade-merge debe dar información sobre la base de datos original y luego usar los argumentos estándar (como -d) para dar la información sobre las nuevas bases de datos. NSS DATABASE TYPES

En versiones anteriores de NSS, las bases de datos de seguridad se almacenaban en archivos de tipo DBM (base de datos de Berkeley) con los siguientes nombres:

•cert8.db for certificates
•key3.db for keys
•secmod.db for PKCS #11 module information

BerkeleyDB tiene limitaciones de rendimiento, sin embargo, lo que impide que sea utilizado fácilmente por múltiples aplicaciones simultáneamente. NSS tiene cierta flexibilidad que permite a las aplicaciones utilizar su propio motor de base de datos independiente mientras mantienen una base de datos compartida y sortean los problemas de acceso. Aun así, NSS requiere más flexibilidad para proporcionar una base de datos de seguridad verdaderamente compartida.

En 2009, NSS introdujo un nuevo conjunto de bases de datos que son bases de datos SQLite en lugar de BerkeleyDB. Estas nuevas bases de datos proporcionan más accesibilidad y rendimiento:

•cert9.db for certificates
•key4.db for keys
•pkcs11.txt, a listing of all of the PKCS #11 modules, contained in a new subdirectory in the security databases directory

Dado que las bases de datos SQLite están diseñadas para ser compartidas, estos son el tipo de base de datos *compartida*. Se prefiere el tipo de base de datos compartida; el formato heredado se incluye por compatibilidad retroactiva.

Por defecto, las herramientas (certutil, pk12util, modutil) asumen que las bases de datos de seguridad dadas utilizan el tipo SQLite. Las bases de datos heredadas deben especificarse manualmente utilizando el prefijo dbm: con el directorio de seguridad dado. Por ejemplo:

$ certutil -L -d dbm:/home/my/sharednssdb

Para establecer el tipo de base de datos heredada como el tipo predeterminado para las herramientas, establezca la variable de entorno NSS_DEFAULT_DB_TYPE a dbm:

export NSS_DEFAULT_DB_TYPE="dbm"

Esta línea se puede añadir al archivo ~/.bashrc para hacer que el cambio sea permanente.

•https://wiki.mozilla.org/NSS_Shared_DB_Howto

Para un borrador de ingeniería sobre los cambios en las bases de datos compartidas de NSS, consulte el wiki del proyecto NSS:

•https://wiki.mozilla.org/NSS_Shared_DB
