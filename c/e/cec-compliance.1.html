CEC-COMPLIANCE(1) Comandos de Usuario CEC-COMPLIANCE(1)

NOMBRE

cec-compliance - Una aplicación para verificar dispositivos CEC remotos

SINOPSIS

cec-compliance [-h] [-d <dev>] [otras opciones]

DESCRIPCIÓN

La utilidad cec-compliance se puede usar para probar qué tan bien los dispositivos CEC remotos cumplen con la especificación CEC. También se puede usar para probar el adaptador CEC local (con la opción -A).

Por defecto, ejecutará todas las pruebas, pero si se proporciona una o más de las opciones de prueba de características, solo se realizarán esas pruebas. Siempre se ejecuta un conjunto de pruebas centrales.

El adaptador CEC debe configurarse antes de usarlo para ejecutar pruebas con cec-compliance. Utilice cec-ctl para la configuración.

Si el adaptador CEC ha reclamado varias direcciones lógicas, el conjunto de pruebas se ejecuta desde cada dirección lógica sucesivamente. El dispositivo remoto debe informar una dirección física válida para ejecutar pruebas en él.

Al ejecutar pruebas de cumplimiento, cec-follower debe ejecutarse en el mismo adaptador. cec-follower responderá a los mensajes que no sean manejados por cec-compliance. cec-follower también monitoreará el dispositivo bajo prueba en busca de comportamientos que no cumplan con la especificación. Antes de cada ejecución de prueba, cec-follower debe reiniciarse si ya está en ejecución, para inicializar el dispositivo emulado con un estado inicial limpio y conocido.

Algunas pruebas requieren el modo interactivo (con la opción -i) para confirmar que la prueba pasó. Cuando está en modo interactivo, se le pide al usuario que observe o realice acciones en el dispositivo remoto. Algunas pruebas también dan resultados de prueba concluyentes cuando se ejecutan en modo interactivo.

Al probar el cumplimiento del adaptador CEC local con la API CEC, debe haber al menos un dispositivo remoto presente para probar la transmisión y recepción.

Las pruebas de cumplimiento pueden tener varios resultados posibles además de pasar y fallar:


OK La prueba pasó.


OK (Inesperado) La prueba pasó, pero era inesperado que el dispositivo
bajo prueba lo soportara. Esto podría ocurrir, por ejemplo,
cuando un televisor responde a mensajes en la característica
de Control de Reproductor.


OK (No Soportado) La característica probada no es soportada por el
dispositivo bajo prueba, y esa característica no era obligatoria
para que el dispositivo pasara.


OK (Presunto) Nada salió mal durante la prueba, pero la prueba no puede
verificar positivamente que ocurrieron los efectos requeridos de la
prueba. El ejecutor de la prueba debe verificar que la prueba
pasó observando manualmente el dispositivo bajo prueba. Este es
típicamente el resultado de la prueba para pruebas que envían
mensajes a los que no se responde, pero que inducen algún
efecto secundario en el dispositivo bajo prueba, como un televisor
cambiando a otra entrada o enviando un comando de Control Remoto.


OK (Rechazado) El dispositivo soporta la característica o mensaje que se
está probando, pero respondió <Feature Abort> ["Refused"] para
indicar que no puede realizar la operación dada. Esto podría
ocurrir, por ejemplo, al intentar probar la característica
One Touch Record en un televisor con protección contra copia
activada.


FAIL La prueba falló y se esperaba que pasara en el dispositivo.


OK (Fallo Esperado) Falló pero esto era esperado. Esto solo puede suceder
si se usó la opción --expect que especificó que una prueba
particular devolvería un resultado FAIL.


FAIL (Esperado X, obtenido Y) La prueba devolvió un resultado diferente al esperado.
Esto solo puede suceder si se usó la opción --expect
que especificó que una prueba particular devolvería un resultado
específico no-FAIL.

Algunas pruebas dependen de que otras pruebas sean exitosas. Estas no se ejecutan si las pruebas de las que dependen fallaron, y no se mostrarán en la lista de pruebas.

OPCIONES

-d, --device <dev>
Usa el dispositivo <dev> como dispositivo CEC. Si <dev> es un número, entonces se usa /dev/cec<dev>.
-D, --driver <drv>
Usa un dispositivo cec que tenga el nombre de controlador <drv>, tal como lo devuelve el ioctl CEC_ADAP_G_CAPS. Esta opción se puede combinar con -a para identificar de forma única un dispositivo CEC sin tener que depender del número del nodo del dispositivo.
-a, --adapter <nombre-adaptador>
Usa un dispositivo cec que tenga el nombre de adaptador <nombre-adaptador>, tal como lo devuelve el ioctl CEC_ADAP_G_CAPS. Esta opción se puede combinar con -D para identificar de forma única un dispositivo CEC sin tener que depender del número del nodo del dispositivo.
-E, --exit-on-fail
Sale de esta aplicación cuando ocurre la primera falla en lugar de continuar con un estado posiblemente inconsistente.
-l, --list-tests
Lista todas las pruebas y los resultados posibles. Esto es utilizado por la opción --expect.
-e, --expect <prueba>=<resultado>
-n, --expect-with-no-warnings <prueba>=<resultado> Falla si la prueba devolvió un resultado diferente. La opción --list-tests lista todas las pruebas posibles y qué valores de resultado se pueden usar.

Esto se puede usar en scripts de prueba para verificar que se devolvió un resultado específico de la prueba. Un caso de uso es verificar que una característica opcional es realmente compatible, por lo que se espera un resultado OK en lugar de un resultado OK (No Soportado).

También se puede usar para aceptar fallas conocidas. En ese caso, la prueba no fallará, sino que devolverá un resultado OK (Fallo Esperado).

La variante --expect-with-no-warnings es más estricta y también verificará que la prueba no produjo advertencias.

-v, --verbose
Activa los informes detallados.
--version
Muestra la información de la versión.
-w, --wall-clock
Muestra las marcas de tiempo como hora del reloj.
-S, --show-timestamp
Para cada prueba, muestra la marca de tiempo de cuándo comenzó la prueba.
-T, --trace
Rastrea todos los ioctls llamados. Útil para depuración.
-h, --help
Imprime el mensaje de ayuda.
-W, --exit-on-warn
Sale de esta aplicación cuando ocurre la primera advertencia en lugar de continuar.
-s, --skip-info
Omite la sección de salida de Información del Controlador.
-C, --color <cuándo>
Resalta las cadenas OK/warn/fail/FAIL con colores. OK se marca en verde, warn se marca en negrita, y fail/FAIL se marcan en rojo brillante si están habilitados. <cuándo> puede ser always, never, o auto (el predeterminado).
-N, --no-warnings
Desactiva los mensajes de advertencia.
-r, --remote <la>
Como iniciador, prueba la dirección lógica remota <la> o todas las LA si no se proporcionó ninguna LA.
-i, --interactive
Modo interactivo al realizar pruebas remotas.
-R, --reply-threshold <tiempo_espera>
Advierte si las respuestas tardan más que este umbral (predeterminado 1000ms).
-t, --timeout <seg>
Establece el tiempo de espera de espera/reanudación al número dado de segundos. El valor predeterminado es 60s.
-A, --test-adapter
Prueba la API del adaptador CEC.
-F, --test-fuzzing
Prueba el adaptador CEC remoto creando mensajes CEC aleatoriamente. Esto se ejecuta para siempre hasta que ocurra un error.

EJEMPL

O

Queremos probar la conformidad de un televisor cuando interactúa con un dispositivo de Reproducción. El nodo de dispositivo del adaptador CEC al que está conectado el televisor es

/dev/cec1.

El adaptador CEC local primero necesita ser configurado como un dispositivo de Reproducción, y debe tener una dirección física apropiada. Es importante que la dirección física sea correcta, para no confundir al dispositivo bajo prueba. Por ejemplo, si el adaptador CEC está conectado a la primera entrada del televisor, generalmente se debe usar la dirección física 1.0.0.
