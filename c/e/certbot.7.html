El certificado se utiliza tanto para cifrar la etapa inicial de la comunicación (intercambio seguro de claves) como para identificar al servidor. El certificado incluye información sobre la clave, información sobre la identidad del servidor y la firma digital del emisor del certificado. Si el emisor es de confianza para el software que inicia la comunicación, y la firma es válida, entonces la clave puede usarse para comunicarse de forma segura con el servidor identificado por el certificado. Usar un certificado es una buena forma de prevenir ataques de "hombre en el medio", en los que alguien entre tú y el servidor con el que crees estar hablando es capaz de insertar su propio contenido (dañino). Recreación y actualización de certificados

existentes

Puedes usar los subcomandos certonly o run para solicitar la creación de un único certificado nuevo incluso si ya tienes un certificado existente con algunos de los mismos nombres de

dominio.

Si se solicita un certificado con run o certonly especificando un nombre de certificado que ya existe, Certbot actualiza el certificado existente. De lo contrario, se crea un nuevo certificado y se le asigna el nombre

especificado.

Las opciones --force-renewal, --duplicate y --expand controlan el comportamiento de Certbot al recrear un certificado con el mismo nombre que un certificado existente. Si no especificas un comportamiento solicitado, Certbot puede preguntarte qué

pretendías.

--force-renewal le indica a Certbot que solicite un nuevo certificado con los mismos dominios que un certificado existente. Cada dominio debe especificarse explícitamente mediante -d. Si tiene éxito, este certificado se guarda junto al anterior y los enlaces simbólicos (la referencia "live") se actualizarán para apuntar al nuevo certificado. Este es un método válido para renovar un certificado individual

específico.

--duplicate le indica a Certbot que cree un certificado separado e independiente con los mismos dominios que un certificado existente. Este certificado se guarda completamente separado del anterior. La mayoría de los usuarios no necesitarán emitir este comando en circunstancias

normales.

--expand le indica a Certbot que actualice un certificado existente con un nuevo certificado que contiene todos los dominios antiguos y uno o más dominios nuevos adicionales. Con la opción --expand, usa la opción -d para especificar todos los dominios existentes y uno o más dominios

nuevos.

Certbot soporta una acción renew para verificar todos los certificados instalados en busca de caducidad inminente e intentar renovarlos. La forma más simple es

simplemente

certbot

renew

Este comando intenta renovar cualquier certificado obtenido previamente que esté listo para la renovación. A partir de Certbot 4.0.0, un certificado se considera listo para la renovación cuando queda menos de 1/3 de su tiempo de vida. Para certificados con un tiempo de vida de 10 días o menos, ese umbral es 1/2 del tiempo de vida. Antes de Certbot 4.0.0, el umbral era un fijo de 30

días.

Se utilizará el mismo plugin y las mismas opciones que se usaron en el momento en que se emitió originalmente el certificado para el intento de renovación, a menos que especifique otros plugins u opciones. A diferencia de certonly, renew actúa sobre múltiples certificados y siempre tiene en cuenta si cada uno está cerca de caducar. Debido a esto, renew es adecuado (y está diseñado) para su uso automatizado, para permitir que su sistema renueve automáticamente cada certificado cuando corresponda. Dado que renew solo renueva certificados que están cerca de caducar, se puede ejecutar con la frecuencia que desee, ya que normalmente no tomará ninguna

acción.

El comando renew incluye ganchos para ejecutar comandos o scripts antes o después de que se renueve un certificado. Por ejemplo, si tiene un solo certificado obtenido usando el plugin standalone, es posible que necesite detener el servidor web antes de renovar para que standalone pueda vincularse a los puertos necesarios, y luego reiniciarlo después de que el plugin termine.

Ejemplo: 
certbot renew --pre-
hook "service nginx
stop" --post-hook "
service nginx start"

Si un gancho sale con un código de salida distinto de cero, el error se imprimirá en stderr pero la renovación se intentará de todos modos. Un gancho que falla no causa directamente que Certbot salga con un código de salida distinto de cero, pero dado que Certbot sale con un código de salida distinto de cero cuando las renovaciones fallan, un gancho fallido que cause fallos de renovación resultará indirectamente en un código de salida distinto de cero. Los ganchos solo se ejecutarán si un certificado está pendiente de renovación, por lo que puede ejecutar el comando anterior frecuentemente sin detener su servidor web innecesariamente

.

Cuando Certbot detecta que un certificado está pendiente de renovación, los ganchos --pre-hook y --post-hook se ejecutan antes y después de cada intento de renovarlo. Si desea que su gancho se ejecute solo después de una renovación exitosa, use --deploy-hook en un comando como

este.

certbot renew --deploy-hook /path/to/deploy-hook-scrip

t

También puede especificar ganchos colocando archivos en subdirectorios del directorio de configuración de Certbot. Asumiendo que su directorio de configuración es /etc/letsencrypt, cualquier archivo ejecutable encontrado en /etc/letsencrypt/renewal-hooks/pre, /etc/letsencrypt/renewal-hooks/deploy y /etc/letsencrypt/renewal-hooks/post se ejecutarán como ganchos pre, deploy y post respectivamente. Estos ganchos se ejecutan en orden alfabético. (El orden en que se ejecutan los ganchos está determinado por el valor de byte de los caracteres en sus nombres de archivo y no depende de su configuración regional.

)

Antes de certbot 3.2.0, los ganchos en directorios solo se ejecutaban cuando los certificados se renovaban con el subcomando renew, pero a partir de 3.2.0, se ejecutan para cualquier

subcomando.

Los ganchos especificados en la línea de comandosne, archivo de configuración, o archivos de configuración de renovación se ejecutan como de costumbre después de ejecutar todos los hooks en estos directorios. Una pequeña excepción a esto es si un hook especificado en otro lugar es simplemente la ruta a un archivo ejecutable en el directorio de hooks del mismo tipo (por ejemplo, su pre-hook es la ruta a un ejecutable en /etc/letsencrypt/renewal-hooks/pre), el archivo no se ejecuta una segunda vez. Puede evitar que Certbot ejecute automáticamente los ejecutables encontrados en estos directorios incluyendo --no-directory-hooks en la línea de

comandos.

Se puede encontrar más información sobre los hooks ejecutando certbot --hel

p renew.

Si está seguro de que este comando se ejecuta con éxito sin intervención humana, puede agregar el comando a crontab (ya que los certificados solo se renuevan cuando se determina que están cerca de su vencimiento, el comando puede ejecutarse con regularidad, como cada semana o cada día). En ese caso, probablemente querrá usar el -q o --quiet quiet flag para silenciar toda la salida excepto los

errores.

Si está renovando manualmente todos sus certificados, la --force-renewal flag puede ser útil; hace que el tiempo de vencimiento del certificado se ignore al considerar la renovación, e intenta renovar cada uno de los certificados instalados independientemente de su antigüedad. (Esta forma no es apropiada para ejecutarla diariamente porque cada certificado se renovará todos los días, lo que rápidamente alcanzará el límite de tasa de la autoridad de certificación.

)

A partir de Certbot 2.7.0, certbot proporciona las variables de entorno RENEWED_DOMAINS y FAILED_DOMAINS a todos los post renewal hooks. Estas variables contienen una lista de dominios separados por espacios. Estas variables se pueden usar para determinar si una renovación ha tenido éxito o ha fallado como parte de su post renewal

hook.

Tenga en cuenta que las opciones proporcionadas a certbot renew se aplicarán a cada certificado para el que se intente la renovación; por ejemplo, certbot renew --rsa-key-size 4096 intentaría reemplazar cada certificado próximo a vencer con un certificado equivalente usando una clave pública RSA de 4096 bits. Cambiar el Servidor ACME

Por defecto, Certbot utiliza el servidor de producción de Let's Encrypt en https://acme-v02.api.letsencrypt.org/directory. Puedes indicar a Certbot que utilice una CA diferente proporcionando --server en la línea de comandos o en un archivo de configuración con la URL del directorio ACME del servidor. Por ejemplo, si deseas utilizar el servidor de staging de Let's Encrypt, añadirías --server https://acme-staging-v02.api.letsencrypt.org/directory a la línea de comandos.

Nota:

--dry-run utiliza el servidor de staging de Let's Encrypt, a menos que se especifique --server en la línea de comandos o en el archivo de configuración cli.ini. Ten cuidado al usar --dry-run con un servidor personalizado, ya que puede provocar que se emitan y descarten certificados reales.

Si Certbot no confía en el certificado SSL utilizado por el servidor ACME, puedes utilizar la variable de entorno REQUESTS_CA_BUNDLE https://requests.readthedocs.io/en/latest/user/advanced/#ssl-cert-verification para anular los certificados raíz en los que confía Certbot. Certbot utiliza la biblioteca requests, que no utiliza el almacén de raíces de confianza del sistema operativo. Asegúrate de que REQUESTS_CA_BUNDLE esté configurado globalmente en el entorno y no solo en la línea de comandos, o la renovación programada no tendrá éxito.

Archivos de Bloqueo

Al procesar una validación, Certbot escribe varios archivos de bloqueo en tu sistema para evitar que múltiples instancias sobrescriban los cambios de las otras. Esto significa que, por defecto, dos instancias de Certbot no podrán ejecutarse en paralelo.

Dado que los directorios utilizados por Certbot son configurables, Certbot escribirá un archivo de bloqueo para todos los directorios que utiliza. Esto incluye el --work-dir, --logs-dir y --config-dir de Certbot. Por defecto, estos son /var/lib/letsencrypt, /var/log/letsencrypt y /etc/letsencrypt respectivamente. Además, si estás utilizando Certbot con Apache o nginx, bloqueará la carpeta de configuración de ese programa, que normalmente también se encuentra en el directorio /etc.

Ten en cuenta que estos archivos de bloqueo solo impedirán que otras instancias de Certbot utilicen esos directorios, no otros procesos. Si deseas ejecutar varias instancias de Certbot simultáneamente, deberías especificar diferentes directorios como --work-dir, --logs-dir y --config-dir para cada instancia de Certbot que desees ejecutar.

Además, debido a cómo se analizan los argumentos en cli.ini, las opciones que no se desean establecer no deben enumerarse. Las opciones establecidas en falso se leerán como si estuvieran establecidas en verdadero por versiones anteriores de Certbot, ya que se han enumerado en el archivo de configuración.

Rotación de Registros

Por defecto, certbot almacena los registros de estado en /var/log/letsencrypt. Por defecto, certbot comenzará a rotar los registros una vez que haya 1000 registros en el directorio de registros. Esto significa que una vez que haya 1000 archivos en /var/log/letsencrypt, Certbot eliminará el más antiguo para dejar espacio a nuevos registros. El número de registros subsiguientes se puede cambiar pasando el número deseado al indicador de línea de comandos --max-log-backups. Establecer este indicador en 0 deshabilita completamente la rotación de registros, haciendo que certbot siempre añada al mismo archivo de registro.

Nota:

Algunas distribuciones, como Debian y Ubuntu, deshabilitan la rotación de registros interna de certbot en favor de un script de logrotate más tradicional. Si estás utilizando los paquetes de una distribución y deseas modificar la rotación de registros, consulta /etc/logrotate.d/ para ver un script de rotación de certbot.

Arquitectura de

plugins

Certbot tiene una arquitectura de plugins para facilitar el soporte de diferentes servidores web, otros servidores TLS y sistemas operativos. Las interfaces disponibles para que los plugins implementen están definidas en interfaces.py https://github.com/certbot/certbot/blob/main/certbot/src/certbot/interfaces.py y plugins/common.py https://github.com/certbot/certbot/blob/main/certbot/src/c

ertbot/plugins/common.py#L45.

Las dos interfaces principales de plugins son Authenticator, que implementa varias formas de probar el control del dominio a una autoridad de certificación, y Installer, que configura un servidor para usar un certificado una vez emitido. Algunos plugins, como los plugins integrados de Apache y Ngin

x, implementan ambas interfaces y realizan ambas tareas. Otros, como el
autenticador integrado Standalone, implementan solo una interfaz.

Autenticadore

s

Los autenticadores son plugins que prueban el control de un nombre de dominio resolviendo un challenge proporcionado por el servidor ACME. ACME define actualmente dos tipos de challenges: HTTP y DNS, representados por clases en acme.challenges https://acme-python.readthedocs.io/en/latest/api/challenges.html#module-acme.challenges. Un plugin de autenticador debe implementar soporte para al menos un tipo de

challenge.

Un Authenticator indica qué challenges soporta implementando get_chall_pref(domain) para devolver una lista ordenada de tipos de challenges en orden de

preferencia.

Un Authenticator también debe implementar perform(achalls), que "realiza" una lista de challenges, por ejemplo, aprovisionando un archivo en un servidor HTTP, o estableciendo un registro TXT en DNS. Una vez que todos los challenges hayan tenido éxito o fallado, Certbot llamará al método cleanup(achalls) del plugin para eliminar cualquier archivo o

registro DNS que solo fue nece
sario durante la autenticación.

Instalado

r

Los plugins de instalador existen para realmente configurar el certificado en un servidor, posiblemente ajustar la configuración de seguridad para hacerla más correcta y segura (arreglar algunos problemas de contenido mixto, activar HSTS, redirigir a HTTPS, etc). Los plugins de instalador le cuentan al cliente principal sobre sus habilidades para hacer lo último a través de la llamada supported_enhancements(). Actualmente tenemos dos Instaladores en el árbol, el ApacheConfigurator. y el NginxConfigurator. Proyectos externos han hecho algo de progreso hacia el soporte de IIS, Icecast y

Plesk.

Los instaladores y autenticadores a menudo serán la misma clase/objeto (porque por ejemplo ambas tareas pueden ser realizadas por un servidor web como nginx) aunque no siempre es el caso (el plugin standalone es un autenticador que escucha en el puerto 80, pero no puede instalar certificados; un plugin de postfix sería un instalador pero no un autenticador)

. ">Los instaladores y los autenticadores se mantienen separados porque debería ser posible usar el StandaloneAuthenticator (configura su propio servidor Python para realizar los desafíos) c

por sí mismo (como los instaladores de MTA).

Escribiendo tu propio plugin

snap

Si deseas que tu plugin se use junto con el snap de Certbot, también tendrás que publicar tu plugin como un snap. Los snaps de plugins son snaps confinados regulares, pero normalmente no proporcionan ninguna "app" en sí mismos. Los snaps de plugins exportan módulos de Python cargables al snap de

Certbot.

Cuando el snap de Certbot se ejecuta, usará su propia versión de Python y preferirá los módulos de Python contenidos en su propio snap sobre los módulos contenidos en snaps externos. Esto significa que tu snap no tiene que contener cosas como una copia extra de Python, Certbot o sus dependencias, pero también significa que si necesitas una versión diferente de una dependencia de la que ya está instalada en el snap de Certbot, el snap de Certbot tendrá que ser

actualizado.

Los snaps de plugins de Certbot exponen sus módulos de Python al snap de Certbot a través de una interfaz de contenido (content interface) de snap https://snapcraft.io/docs/content-interface donde certbot-1 es el valor para el atributo content. El snap de Certbot solo usa esto para encontrar los nombres de los snaps de plugins conectados y espera encontrar los módulos de Python a cargar bajo lib/python3.12/site-packages/ en el snap del plugin. Esta ubicación es la predeterminada al usar el snap base core24 https://snapcraft.io/docs/base-snaps y el plugin snapcraft de python https://snapcraft.io/docs/python-plugin

.

El snap de Certbot también proporciona una interfaz de contenido separada que puedes usar para obtener metadatos sobre el snap de Certbot usando el identificador de contenido metadata-1

El script utilizado para generar los archivos snapcraft.yaml para nuestros propios plugins externos snap puede encontrarse en https://github.com/certbot/certbot/blob/main/tools/snap/gen

Para más información sobre la construcción de plugins externos snap, ver la sección sobre Construir los snaps de Certbot y de los plugins

COMPATIBILIDAD HACIA

ATRÁS

Todos los componentes de Certbot, incluyendo acme https://acme-python.readthedocs.io/, Certbot y los plugins que no son de terceros <#plugins>, siguen el Versionado Semántico https://semver.org/ tanto para su API de Python <> como para la aplicación en sí. Esto significa que no cambiaremos el comportamiento de una manera incompatible hacia atrás excepto en una nueva versión principal del

proyecto.

Nota

:
Nada de esto se aplica al comportamiento de los mecanismos de distribución de Certbot como nuestros snaps <
#snap-install> o paquetes de SO cuyo comportamiento puede cambiar en cualquier momento. El versionado semánt
ico solo se aplica a los componentes comunes de Certbot que se instalan por varios métodos de distribución.

Para Certbot como aplicación, la interfaz de línea de comandos y el comportamiento no interactivo se pueden considerar estables con dos excepciones. La primera es que ningún aspecto de la salida de consola o de registro de Certbot debe considerarse estable y puede cambiar en cualquier momento. La segunda es que el comportamiento de Certbot solo debe considerarse estable con ciertos archivos pero no con todos. Los archivos con los que los usuarios deben esperar que Certbot mantenga su comportamiento actual

son:
  • /etc/letsencrypt/live/$domain/{cert,chain,fullchain,privkey}.pem, donde $domain es el nombre del certificado (vea ¿Dónde están mis certificados? <#where-certs> para más
    • detalles)
  • Archivos de configuración de la CLI
    • <#config-file>
  • Directorios de hooks en /etc/letsencrypt/renewal-ho
    • o
k
s

El comportamiento de Certbot con otros archivos puede cambiar en cualquier

momento.

Otra área donde Certbot no debe considerarse estable es su comportamiento cuando no se ejecuta en modo no interactivo, lo cual también puede cambiar en cualquier

momento.

En general, si hacemos un cambio que esperamos que rompa a algunos usuarios, incrementaremos la versión principal y lo habre

mos advertido en una versión anterior cuando sea posible. Para nuestra API de Python, emitiremos advertencias usando el
módulo de advertencias de Python. Para cambios a nivel de aplicación, imprimiremos y registraremos mensajes de advertencia.
