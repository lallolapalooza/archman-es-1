Generador CPack AppImage

Añadido en la versión 4.2.

El generador CPack AppImage https://appimage.org permite empaquetar una aplicación en el formato AppImage. Utiliza appimagetool para empaquetar la aplicación y patchelf para establecer el RPATH de la aplicación a una ruta relativa basada en dónde se montará el AppImage.

La herramienta appimagetool no busca dependencias de bibliotecas. Solo empaqueta el contenido instalado y comprueba si el archivo .desktop proporcionado se creó correctamente. Para una mejor compatibilidad, se recomienda compilar en una distribución LTS antigua e incluir cualquier dependencia en el archivo generado.

El siguiente fragmento se puede añadir a tu archivo CMakeLists.txt. Reemplaza my_application_target con el objetivo de tu aplicación. El ejemplo hará todo lo posible por identificar las bibliotecas a las que enlaza tu aplicación y copiarlas a la ubicación de instalación.

install(CODE [[
    file(GET_RUNTIME_DEPENDENCIES
        EXECUTABLES $<TARGET_FILE:my_application_target>
        RESOLVED_DEPENDENCIES_VAR resolved_deps
    )
    foreach(dep ${resolved_deps})
        # copy the symlink
        file(COPY ${dep} DESTINATION ${CMAKE_INSTALL_PREFIX}/lib)
        # Resolve the real path of the dependency (follows symlinks)
        file(REAL_PATH ${dep} resolved_dep_path)
        # Copy the resolved file to the destination
        file(COPY ${resolved_dep_path} DESTINATION ${CMAKE_INSTALL_PREFIX}/lib)
    endforeach()
]])

El generador CPack AppImage generará un AppRun predeterminado https://docs.appimage.org/introduction/software-overview.html#apprun basado en la entrada .desktop proporcionada. Alternativamente, si se instala un AppRun personalizado, por ejemplo, mediante el comando install() <#command:install>, se utilizará en lugar del generado.

Para proyectos basados en Qt, se recomienda llamar a qt_generate_deploy_app_script() o qt_generate_deploy_qml_app_script() e instalar los archivos generados por el script. Esto instalará los plugins de Qt.

También debe establecer CPACK_PACKAGE_ICON <#variable:CPACK_PACKAGE_ICON> con el mismo valor listado en el archivo Desktop.

    Agregado en la versión 3.1.

  • 7Z_BZ2 - 7zip - (.7z) - comprimido con BZip2

  • 7Z_DEFLATE - 7zip - (.7z) - comprimido con Deflate

  • 7Z_LZMA - 7zip - (.7z) - comprimido con LZMA

  • 7Z_LZMA2 - 7zip - (.7z) - comprimido con LZMA2

    Añadido en la versión 4.3.

  • ZIP_LZMA (.zip) - comprimido con LZMA

    Añadido en la versión 4.3.

  • ZIP_LZMA2 (.zip) - comprimido con LZMA2

    Añadido en la versión 4.3.

  • ZIP_STORE (.zip) - no se utiliza compresión

    Añadido en la versión 4.3.

Cuando este generador se invoca desde CPackSourceConfig.cmake (o mediante el objetivo package_source), el archivo generado contendrá todos los archivos del directorio del proyecto, excepto los especificados en CPACK_SOURCE_IGNORE_FILES <#variable:CPACK_SOURCE_IGNORE_FILES>. El siguiente es un ejemplo de empaquetado de todos los archivos fuente de un proyecto:

set(CPACK_SOURCE_GENERATOR "TGZ")
set(CPACK_SOURCE_IGNORE_FILES
  \\.git/
  build/
  ".*~$"
)
set(CPACK_VERBATIM_VARIABLES YES)
include(CPack)

Cuando este generador se invoca desde CPackConfig.cmake (o mediante el objetivo package), el archivo generado contendrá todos los archivos que se hayan instalado mediante el comando install() <#command:install> de CMake (y los comandos obsoletos install_files() <#command:install_files>, install_programs() <#command:install_programs> e install_targets() <#command:install_targets>).

El número de hilos que se usarán al realizar la compresión.

Predeterminado

Si se establece en 0, se usará en su lugar el número de núcleos disponibles en la máquina. Tenga en cuenta que no todos los modos de compresión admiten subprocesos en todos los entornos.

Predeterminado

El nombre del bundle generado. Aparece en el Finder de macOS como el nombre del bundle. Obligatorio.
CPACK_BUNDLE_PLIST
Ruta a un archivo Property List (.plist) de macOS que se utilizará para el bundle generado. Esto supone que quien lo invoca ha generado o especificado su propio archivo Info.plist. Obligatorio.

Ruta a un archivo de icono de macOS que se utilizará como icono del bundle generado. Este es el icono que aparece en el Finder de macOS para el bundle, y en el dock de macOS cuando se abre el bundle. Obligatorio.

Ruta a un script de inicio. Es una ruta a un ejecutable o script que se ejecutará cada vez que un usuario final haga doble clic en el bundle generado en el Finder de macOS. Opcional.

Añadido en la versión 3.2.

El nombre de su certificado de firma de código proporcionado por Apple para la aplicación. El nombre suele tener la forma Developer ID Application: [Name] o 3rd Party Mac Developer Application: [Name]. Si esta variable no se establece, la aplicación no se firmará.

CPACK_BUNDLE_APPLE_ENTITLEMENTS
Añadido en la versión 3.2.

El nombre del archivo Property List (.plist) que contiene sus derechos de Apple para el sandboxing de su aplicación. Este archivo es necesario para enviarla al App Store de macOS.

CPACK_BUNDLE_APPLE_CODESIGN_FILES
Añadido en la versión 3.2.

Una lista de archivos adicionales que desea que se firmen. No necesita enumerar la carpeta principal de la aplicación ni el ejecutable principal. Debe enumerar cualquier framework y plugin que se incluya en el bundle de su aplicación.

CPACK_BUNDLE_APPLE_CODESIGN_PARAMETER
Añadido en la versión 3.3.

Parámetro adicional que se pasará a codesign. Valor predeterminado: --deep -f

Añadido en la versión 3.2.

Ruta al comando codesign(1) utilizado para firmar aplicaciones con un certificado de Apple. Esta variable se puede utilizar para anular el comando detectado automáticamente (o especificar su ubicación si la detección automática no lo encuentra).

Generador CPack DEB

El generador CPack DEB (binario) integrado (solo Unix)

Variables específicas del generador CPack Debian (DEB)

El generador CPack DEB se puede utilizar para crear paquetes DEB usando CPack <#module:CPack>. El generador CPack DEB es un generador de CPack <#module:CPack>, por lo que utiliza las variables CPACK_XXX usadas por CPack <#module:CPack>.

El generador CPack DEB debería funcionar en cualquier host Linux, pero producirá mejores paquetes deb cuando las herramientas específicas de Debian dpkg-xxx estén disponibles en el sistema de compilación.

El generador CPack DEB tiene características específicas que se controlan mediante las variables específicas CPACK_DEBIAN_XXX.

Las variables CPACK_DEBIAN_<COMPONENT>_XXXX se pueden usar para tener valores específicos de componente. Tenga en cuenta, sin embargo, que <COMPONENT> se refiere al nombre de agrupación escrito en mayúsculas. Puede ser un nombre de componente o un nombre de GRUPO de componentes.

Aquí hay algunos recursos wiki del generador CPack DEB que están aquí por razones históricas y ya no se mantienen, pero que aún pueden resultar útiles:

  • https://gitlab.kitware.com/cmake/community/-/wikis/doc/cpack/Configuration
  • https://gitlab.kitware.com/cmake/community/-/wikis/doc/cpack/PackageGenerators#deb-unix-only

Generador externo de CPack

Añadido en la versión 3.13.

CPack proporciona muchos generadores para crear paquetes para una variedad de plataformas y sistemas de empaquetado. La intención es que CMake/CPack sea una solución completa de extremo a extremo para compilar y empaquetar un proyecto de software. Sin embargo, puede que no siempre sea posible usar CPack para todo el proceso de empaquetado, debido a limitaciones técnicas o a políticas que requieren el uso de ciertas herramientas. Por esta razón, CPack proporciona el generador "External", que permite que el software de empaquetado externo aproveche algunas de las funcionalidades proporcionadas por CPack, como la instalación de componentes y el grafo de dependencias.

Integración con herramientas de empaquetado externas

El generador CPack External genera un archivo .json que contiene los metadatos internos de CPack, lo que proporciona al software externo información sobre cómo empaquetar el software. El software de empaquetado externo puede invocar a CPack por sí mismo, consumir los metadatos generados, instalar y empaquetar archivos según sea necesario.

Alternativamente, CPack puede invocar un software de empaquetado externo mediante un script de CMake personalizado opcional en CPACK_EXTERNAL_PACKAGE_SCRIPT.

La preparación de los archivos de instalación también puede ser gestionada opcionalmente por el generador cuando se habilita mediante la variable CPACK_EXTERNAL_ENABLE_STAGING.

Formato JSON

El archivo de metadatos JSON contiene una lista de componentes y grupos de componentes de CPack, las diversas opciones pasadas a cpack_add_component() <#command:cpack_add_component> y cpack_add_component_group() <#command:cpack_add_component_group>, las dependencias entre los componentes y los grupos de componentes, y diversas otras opciones pasadas a CPack.

El objeto raíz del JSON siempre proporcionará dos campos: formatVersionMajor y formatVersionMinor, que siempre son enteros que describen el formato de salida del generador. Los cambios compatibles hacia atrás en el formato de salida (por ejemplo, agregar un nuevo campo que no existía antes) hacen que la versión menor se incremente, y los cambios incompatibles hacia atrás (por ejemplo, eliminar un campo o cambiar su significado) hacen que la versión mayor se incremente y la versión menor se restablezca a 0. La versión del formato siempre tiene el formato mayor.menor. En otras palabras, siempre tiene exactamente dos partes, separadas por un punto.

Puede solicitar una o más versiones específicas del formato de salida como se describe a continuación con CPACK_EXTERNAL_REQUESTED_VERSIONS. El formato de salida tendrá una versión mayor que coincida exactamente con la versión mayor solicitada, y una versión menor que sea mayor o igual que la versión menor solicitada. Si no se solicita ninguna versión con CPACK_EXTERNAL_REQUESTED_VERSIONS, se utiliza por defecto la última versión mayor conocida. Actualmente, el único formato admitido es 1.0, que se describe a continuación.

Variables específicas del generador CPack External

CPACK_EXTERNAL_REQUESTED_VERSIONS
Esta variable se utiliza para solicitar una versión específica del generador CPack External. Es una lista de valores mayor.menor, separados por punto y coma.

Si esta variable se establece en un valor no vacío, el generador CPack External iterará a través de cada elemento de la lista para buscar una versión que sepa generar. Las versiones solicitadas deben enumerarse en orden de preferencia descendente por el software cliente, ya que se generará la primera versión coincidente de la lista.

El generador sabe cómo generar la versión si tiene un generador versionado cuya versión mayor coincide exactamente con la versión mayor solicitada, y cuya versión menor es mayor o igual que la versión menor solicitada. Por ejemplo, si CPACK_EXTERNAL_REQUESTED_VERSIONS contiene 1.0, y el generador CPack External sabe cómo generar 1.1, generará 1.1. Si el generador no sabe cómo generar una versión de la lista, omite la versión y pasa a la siguiente. Si no sabe cómo generar ninguna de las versiones solicitadas, se produce un error.

Si esta variable no está establecida, o está vacía, el generador CPack External generará la versión mayor y menor más alta que sepa generar.

Si se encuentra una versión no válida en CPACK_EXTERNAL_REQUESTED_VERSIONS (una que no coincida con major.minor, donde major y minor son enteros), se ignora.

CPACK_EXTERNAL_ENABLE_STAGING
Esta variable se puede establecer en true para habilitar la instalación opcional en un área de preparación temporal que luego puede ser recogida y empaquetada por una herramienta de empaquetado externa. El directorio de nivel superior utilizado por CPack para la tarea de empaquetado actual está contenido en CPACK_TOPLEVEL_DIRECTORY. Se limpia automáticamente en cada ejecución antes de iniciar el empaquetado y se puede utilizar para archivos temporales personalizados requeridos por la herramienta de empaquetado externa. También contiene el área de preparación CPACK_TEMPORARY_DIRECTORY en la que CPack realiza la instalación cuando la preparación está habilitada.
CPACK_EXTERNAL_PACKAGE_SCRIPT
Esta variable puede especificar opcionalmente la ruta completa a un archivo de script de CMake que se ejecutará como parte de la invocación de CPack. Se invoca después de que tenga lugar la preparación (opcional) y puede ejecutar una herramienta de empaquetado externa. El script tiene acceso a las variables definidas por el archivo de configuración de CPack.
CPACK_EXTERNAL_BUILT_PACKAGES
Añadido en la versión 3.19.

El script CPACK_EXTERNAL_PACKAGE_SCRIPT puede establecer esta variable de lista en las rutas completas de los archivos de paquete generados. CPack copiará estos archivos desde el directorio de preparación de vuelta al directorio de compilación superior y posiblemente producirá archivos de suma de comprobación si CPACK_PACKAGE_CHECKSUM <#variable:CPACK_PACKAGE_CHECKSUM> está establecido.

El generador CPack FreeBSD se puede utilizar para crear paquetes pkg(8) -- estos se pueden usar en FreeBSD, DragonflyBSD, NetBSD, OpenBSD, pero también en Linux o OSX, dependiendo de las herramientas de gestión de paquetes instaladas -- usando CPack <#module:CPack>.

Variables Específicas de Archivo

Aunque todos los archivos que se instalan mediante una instrucción install() <#command:install> se procesan y agregan automáticamente al instalador, existen algunas variables para personalizar el proceso de instalación.

Antes de usar ejecutables (solo .exe o .com) en accesos directos (p. ej., CPACK_CREATE_DESKTOP_LINKS <#variable:CPACK_CREATE_DESKTOP_LINKS>) o entradas de [Run], debe agregar el nombre de archivo sin procesar (sin ruta ni extensión) a CPACK_PACKAGE_EXECUTABLES <#variable:CPACK_PACKAGE_EXECUTABLES> y crear un acceso directo en el menú de inicio para ellos.

Si tiene dos archivos con el mismo nombre sin procesar (p. ej., a/executable.exe y b/executable.com), se crea una entrada en la sección dos veces. Esto dará como resultado un comportamiento indefinido y no se recomienda.

CPACK_INNOSETUP_CUSTOM_INSTALL_INSTRUCTIONS
Esta variable debe contener una lista separada por punto y coma <#cmake-language-lists> de pares path, instruction y se puede usar para personalizar el comando de instalación que se crea automáticamente para cada archivo o directorio.

CPack crea la siguiente instrucción de Inno Setup para cada archivo...

Source: "absolute\path\to\my_file.txt"; DestDir: "{app}"; Flags: ignoreversion

...y la siguiente línea para cada directorio:

Name: "{app}\my_folder"

Es posible que desee cambiar el directorio de destino o los flags de my_file.txt. Como también podemos proporcionar una ruta relativa, la línea que le gustaría tener es la siguiente:

Source: "my_file.txt"; DestDir: "{userdocs}"; Flags: ignoreversion uninsneveruninstall

Haría esto usando my_file.txt como path y Source: "my_file.txt"; DestDir: "{userdocs}"; Flags: ignoreversion uninsneveruninstall como instruction.

Debe encargarse del problema de escape https://cmake.org/cmake/help/book/mastering-cmake/chapter/Packaging%20With%20CPack.html#adding-custom-cpack-options. Así que el comando de CMake sería:

set(CPACK_INNOSETUP_CUSTOM_INSTALL_INSTRUCTIONS "my_file.txt;Source: \\\"my_file.txt\\\"\\; DestDir: \\\"{userdocs}\\\"\\; Flags: ignoreversion uninsneveruninstall")

Para mejorar la legibilidad, debería evitar el problema de escape usando CPACK_VERBATIM_VARIABLES <#variable:CPACK_VERBATIM_VARIABLES> o colocando la instrucción en un archivo de configuración de proyecto de CPack separado.

Si personaliza la instrucción de instalación de un archivo específico, pierde la conexión con su componente. Para evitarlo, agregue manualmente Components: <component>. También debe agregar sus accesos directos y entradas de [Run] usted mismo en una sección personalizada, ya que el ejecutable ya no será encontrado por CPACK_PACKAGE_EXECUTABLES <#variable:CPACK_PACKAGE_EXECUTABLES>.

Aquí hay otro ejemplo (Nota: debe evitar el problema de escape para que el ejemplo funcione):

set(CPACK_INNOSETUP_CUSTOM_INSTALL_INSTRUCTIONS
    "component1/my_folder" "Name: \"{userdocs}\\my_folder\"\; Components: component1"
    "component2/my_folder2/my_file.txt" "Source: \"component2\\my_folder2\\my_file.txt\"\; DestDir: \"{app}\\my_folder2\\my_file.txt\"\; Flags: ignoreversion uninsneveruninstall\; Components: component2")
Obligatorio

Generador CPack IFW

Agregado en la versión 3.1.

Configure y ejecute Qt Installer Framework para generar un instalador de Qt.

Descripción general

Este generador de cpack <#manual:cpack-generators(7)> genera configuración e metainformación para Qt Installer Framework https://doc.qt.io/qtinstallerframework/index.html (QtIFW), y ejecuta las herramientas de QtIFW para generar un instalador de Qt.

Otras configuraciones

Instalador en línea

De forma predeterminada, este generador genera un instalador sin conexión. Esto significa que todos los archivos empaquetados están completamente contenidos en el ejecutable del instalador.

Por el contrario, un instalador en línea descargará algunos o todos los componentes desde un servidor remoto.

La opción DOWNLOADED en el comando cpack_add_component() <#command:cpack_add_component> especifica que un componente debe descargarse. Alternativamente, la opción ALL en el comando cpack_configure_downloads() <#command:cpack_configure_downloads> especifica que todos los componentes deben descargarse.

El comando cpack_ifw_add_repository() <#command:cpack_ifw_add_repository> y la variable CPACK_IFW_DOWNLOAD_ALL permiten una configuración más específica.

Cuando hay componentes en línea, CPack los escribirá en archivos de almacenamiento. La página de ayuda del módulo CPackComponent <#module:CPackComponent>, especialmente la sección sobre la función cpack_configure_downloads() <#command:cpack_configure_downloads>, explica cómo hacer que estos archivos sean accesibles desde una URL de descarga.

Internacionalización

Añadido en la versión 3.9.

Algunas variables y argumentos de comandos admiten la internacionalización mediante script de CMake. Esta es una función opcional.

Los instaladores creados por las herramientas de QtIFW tienen soporte integrado para la internacionalización y muchas frases están localizadas a muchos idiomas, pero esto no se aplica a la descripción de sus componentes y grupos.

La localización de la descripción de sus componentes y grupos es útil para los usuarios de sus instaladores.

Una variable o argumento localizado puede contener un único valor predeterminado y, después de eso, un conjunto de pares con el nombre de la configuración regional y el valor localizado.

Por ejemplo:

set(LOCALIZABLE_VARIABLE "Valor predeterminado"
  en "Valor en inglés"
  en_US "Valor estadounidense"
  en_GB "Valor de Gran Bretaña"
  )

set(CPACK_GENERATOR NuGet)
# Set up package metadata
set(CPACK_PACKAGE_NAME SamplePackage)
set(CPACK_PACKAGE_VERSION "1.0.0")
set(CPACK_PACKAGE_VENDOR "Example Inc")
set(CPACK_NUGET_PACKAGE_AUTHORS "ExampleInc")
set(CPACK_PACKAGE_DESCRIPTION "A .NET wrapper around the foobar library for frobbling bratchens")
set(CPACK_PACKAGE_HOMEPAGE_URL "https://www.example.com")
set(CPACK_NUGET_PACKAGE_REPOSITORY_URL "https://github.com/example/libfoobar.git")
set(CPACK_NUGET_PACKAGE_REPOSITORY_TYPE git)
set(CPACK_NUGET_PACKAGE_LICENSE_EXPRESSION "MIT")
# Set up dependencies
set(CPACK_NUGET_PACKAGE_TFMS "net4;net6.0")
set(CPACK_NUGET_PACKAGE_DEPENDENCIES_net4 "Foo;Bar")
# NB: If a version number is omitted, the dependency will not be created
set(CPACK_NUGET_PACKAGE_DEPENDENCIES_net4_Foo_VERSION "1.23")
set(CPACK_NUGET_PACKAGE_DEPENDENCIES_net4_Bar_VERSION "4.3.2")
# NB: General dependencies (not framework-specific) go in this variable
set(CPACK_NUGET_PACKAGE_DEPENDENCIES "Baz")
set(CPACK_NUGET_PACKAGE_DEPENDENCIES_Baz_VERSION "9.8.6")
# NB: Since "net6.0" was listed but no dependencies have been specified, an empty group
# will be added to the nuspec file for this framework. This can be used to address warning NU5128.
include(CPack)

Los valores predeterminados son los que se muestran arriba, pero se pueden sobrescribir con CPACK_PRODUCTBUILD_DOMAINS_ANYWHERE, CPACK_PRODUCTBUILD_DOMAINS_USER y CPACK_PRODUCTBUILD_DOMAINS_ROOT.

CPACK_PRODUCTBUILD_DOMAINS_ANYWHERE
Añadido en la versión 3.23.

CPACK_PRODUCTBUILD_DOMAINS debe establecerse en true para que esta variable tenga algún efecto.

CPACK_PRODUCTBUILD_DOMAINS_USER
Añadido en la versión 3.23.

Puede usarse para sobrescribir el atributo enable_currentUserHome en el elemento domains del XML de Distribution. Cuando se establece en true, el producto se puede instalar en el directorio home del usuario actual. Tenga en cuenta que al instalar en el directorio home del usuario, se aplicarán los siguientes requisitos adicionales:

  • El instalador no puede escribir fuera del directorio home del usuario.
  • La instalación se realizará como el usuario actual en lugar de como root. Esto puede tener implicaciones para CPACK_PREFLIGHT_<COMP>_SCRIPT y CPACK_POSTFLIGHT_<COMP>_SCRIPT.
  • No se necesitarán privilegios administrativos para realizar la instalación.

CPACK_PRODUCTBUILD_DOMAINS debe establecerse en true para que esta variable tenga algún efecto.

CPACK_PRODUCTBUILD_DOMAINS_ROOT
Añadido en la versión 3.23.

Puede usarse para sobrescribir el atributo enable_localSystem en el elemento domains del XML de Distribution. Cuando se establece en true, el producto se puede instalar en el directorio raíz. Esto normalmente debería establecerse en true a menos que el producto deba instalarse solo en el directorio home del usuario.

CPACK_PRODUCTBUILD_DOMAINS debe establecerse en true para que esta variable tenga algún efecto.

Plantilla de XML de Distribution

CPack usa un archivo de plantilla para generar el archivo distribution.dist usado internamente por este generador de paquetes. Normalmente, CMake proporciona el archivo de plantilla, pero los proyectos pueden suministrar el suyo propio colocando un archivo llamado CPack.distribution.dist.in en uno de los directorios listados en la variable CMAKE_MODULE_PATH <#variable:CMAKE_MODULE_PATH>. CPack entonces tomará el archivo de plantilla del proyecto en lugar de usar el suyo propio.

El archivo distribution.dist se genera realizando sustituciones similares al comando configure_file() <#command:configure_file>. Cualquier variable establecida cuando se ejecuta CPack estará disponible para sustitución usando la forma habitual @...@. Igual que CPACK_RESOURCE_FILE_WELCOME <#variable:CPACK_RESOURCE_FILE_WELCOME> excepto sin la ruta. El archivo nombrado estará disponible en el mismo directorio que el archivo distribution.dist generado.

Variables específicas del generador CPack RPM

El generador CPack RPM puede usarse para crear paquetes RPM usando CPack <#module:CPack>. El generador CPack RPM es un generador de CPack <#module:CPack>, por lo que usa las variables CPACK_XXX usadas por CPack <#module:CPack>.

El generador CPack RPM tiene características específicas que se controlan mediante las variables específicas CPACK_RPM_XXX.

Las variables CPACK_RPM_<COMPONENT>_XXXX pueden usarse para tener valores específicos de componente. Tenga en cuenta, sin embargo, que <COMPONENT> se refiere al nombre de agrupación escrito en mayúsculas. Puede ser un nombre de componente o un nombre de GRUPO de componente. Normalmente, esas variables corresponden a entidades del archivo spec de RPM. Se puede encontrar información sobre los archivos spec aquí https://rpm.org/documentation.

Cambiado en la versión 3.6: Se prefiere que la parte <COMPONENT> de las variables esté en mayúsculas (p. ej., si el componente se llama foo, entonces use el formato de nombre de variable CPACK_RPM_FOO_XXXX) como ocurre con otras variables CPACK_<COMPONENT>_XXXX. Por motivos de compatibilidad retroactiva (CMake/CPack versión 3.5 y anteriores) todavía se admite la compatibilidad con componentes con el mismo uso de mayúsculas y minúsculas (p. ej., fOo se usaría como CPACK_RPM_fOo_XXXX) para variables definidas en versiones anteriores de CMake/CPack, pero no está garantizado para variables que se añadirán en el futuro. Por compatibilidad retroactiva, las variables de componente con el mismo uso de mayúsculas y minúsculas también anulan las versiones en mayúsculas cuando ambas están presentes.

  • https://gitlab.kitware.com/cmake/community/-/wikis/doc/cpack/Configuration
  • https://gitlab.kitware.com/cmake/community/-/wikis/doc/cpack/PackageGenerators#rpm-unix-only

Empaquetado de Enlaces Simbólicos

Añadido en la versión 3.3.

El generador CPack RPM admite el empaquetado de enlaces simbólicos:

execute_process(COMMAND ${CMAKE_COMMAND}
  -E create_symlink <relative_path_location> <symlink_name>)
install(FILES ${CMAKE_CURRENT_BINARY_DIR}/<symlink_name>
  DESTINATION <symlink_location> COMPONENT libraries)

Los enlaces simbólicos se optimizarán (las rutas se acortarán si es posible) antes de agregarse al paquete o, si se detectan múltiples rutas de reubicación, se generará un script de reubicación de enlaces simbólicos posterior a la instalación.

Los enlaces simbólicos pueden apuntar a ubicaciones que no están empaquetadas por el mismo paquete (ya sea un componente diferente o incluso que no estén empaquetadas en absoluto), pero esas ubicaciones se tratarán como si fueran parte del paquete al determinar si el enlace simbólico debe crearse o estar presente en un script posterior a la instalación, dependiendo de las rutas de reubicación.

Cambiado en la versión 3.6: los enlaces simbólicos que apuntan a ubicaciones fuera de la ruta de empaquetado producen una advertencia y se tratan como enlaces simbólicos permanentes no reubicables. Las versiones anteriores de CMake producían un error en este caso.

Actualmente existen algunas limitaciones:

  • Para el empaquetado basado en componentes, no se verifica la interdependencia entre componentes al procesar enlaces simbólicos. Los enlaces simbólicos que apuntan al contenido de un componente diferente se tratan de la misma manera que si apuntaran a una ubicación que no será empaquetada.
  • Los enlaces simbólicos que apuntan a una ubicación a través de uno o más enlaces simbólicos intermedios no se manejarán de forma diferente: si los enlaces simbólicos intermedios también están en una ruta reubicable, reubicarlos durante la instalación del paquete puede hacer que el enlace simbólico inicial apunte a una ubicación no válida.

mkdir -p build_dir/{BUILD,BUILDROOT,RPMS,SOURCES,SPECS,SRPMS}
rpmbuild --define "_topdir <path_to_build_dir>" --rebuild <SRPM_file_name>

Los paquetes generados se ubicarán en el directorio build_dir/RPMS o en sus subdirectorios.

CMake puede decidir esto, por ejemplo, leyendo variables de entorno establecidas por el gestor de paquetes antes de iniciar el proceso de generación de paquetes rpm binarios. De esta manera, un único paquete SRPM puede usarse para producir diferentes paquetes rpm binarios en diferentes plataformas según las reglas de empaquetado de la plataforma.

CPack selecciona una de las siguientes variantes del conjunto de herramientas WiX según la variable CPACK_WIX_VERSION:

  • Herramientas WiX .NET
  • Conjunto de herramientas WiX v3

Herramientas WiX .NET

El empaquetado se realiza utilizando las siguientes herramientas:

wix build
Compila los archivos de origen WiX directamente en una base de datos .msi del Instalador de Windows.

Las invocaciones pueden personalizarse utilizando variables específicas de la herramienta:

  • CPACK_WIX_BUILD_EXTENSIONS
  • CPACK_WIX_BUILD_EXTRA_FLAGS

Las extensiones de WiX deben nombrarse con la forma WixToolset.<Name>.wixext.

CPack espera que la herramienta .NET wix esté disponible para su uso en la línea de comandos con todas las extensiones de WiX necesarias ya instaladas. Asegúrese de que la versión de wix sea compatible con CPACK_WIX_VERSION, y de que las versiones de las extensiones de WiX coincidan con la versión de la herramienta wix. Por ejemplo:

1.
Instale la herramienta de línea de comandos wix usando dotnet.
Para instalar wix globalmente para el usuario actual: 
dotnet tool install --global wix --version 4.0.4

Esto coloca wix.exe en %USERPROFILE%\.dotnet\tools y añade el directorio a la variable de entorno PATH del usuario actual.

O bien, para instalar wix en una ruta específica, por ejemplo, en c:\WiX:

dotnet tool install --tool-path c:\WiX wix --version 4.0.4

Esto coloca wix.exe en c:\WiX, pero no lo añade a la variable de entorno PATH del usuario actual. La variable de entorno WIX puede establecerse para indicar a CPack dónde encontrar la herramienta, por ejemplo, set WIX=c:\WiX.

2.
Añada la extensión UI de WiX, necesaria para la plantilla WiX predeterminada de CPack:
wix extension add --global WixToolset.UI.wixext/4.0.4

Las extensiones añadidas globalmente se almacenan en %USERPROFILE%\.wix, o si la variable de entorno WIX_EXTENSIONS está establecida, en %WIX_EXTENSIONS%\.wix.

Compila los archivos de origen WiX en archivos .wixobj.

Las invocaciones pueden personalizarse utilizando variables específicas de la herramienta:

  • CPACK_WIX_CANDLE_EXTENSIONS
  • CPACK_WIX_CANDLE_EXTRA_FLAGS
light
Enlaza los archivos .wixobj en una base de datos .msi del Instalador de Windows.

Las invocaciones pueden personalizarse utilizando variables específicas de la herramienta:

  • CPACK_WIX_LIGHT_EXTENSIONS
  • CPACK_WIX_LIGHT_EXTRA_FLAGS

CPack invoca ambas herramientas según sea necesario. Los archivos intermedios .wixobj se consideran detalles de implementación.

Las extensiones de WiX deben nombrarse con la forma Wix<Name>Extension.

CPack espera que las herramientas anteriores estén disponibles para su uso en la línea de comandos a través de PATH. O bien, si la variable de entorno WIX está establecida, CPack busca las herramientas en %WIX% y %WIX%\bin.

Variables específicas del generador CPack WIX

Las siguientes variables son específicas de los instaladores creados en Windows usando WiX.

CPACK_WIX_VERSION
Añadido en la versión 3.30.

Especifica la versión del conjunto de herramientas WiX para la cual está escrita la configuración. El valor debe ser uno de

4
Empaquetar usando las herramientas WiX .NET.
3
Empaquetar usando el conjunto de herramientas WiX v3. Este es el valor predeterminado.
CPACK_WIX_UPGRADE_GUID
GUID de actualización (Product/@UpgradeCode)

Se generará automáticamente a menos que se proporcione explícitamente.

Debe establecerse explícitamente a un identificador único global (GUID) constante generado para permitir que sus instaladores reemplacen instalaciones existentes que usan el mismo GUID.

Puede, por ejemplo, establecer explícitamente esta variable en su CMakeLists.txt al valor que se ha generado por defecto. No debe usar GUIDs que no haya generado usted mismo o que puedan pertenecer a otros proyectos.

Un GUID debe tener la siguiente sintaxis de longitud fija:

XXXXXXXX-XXXX-XXXX-XXXX-XXXXXXXXXXXX

(cada X representa un dígito hexadecimal en mayúscula)

CPACK_WIX_PRODUCT_GUID
GUID del producto (Product/@Id)

Se generará automáticamente a menos que se proporcione explícitamente.

Si se proporciona explícitamente, esto establecerá el Id. del producto de su instalador.

El instalador abortará si detecta una instalación preexistente que use el mismo GUID.

El GUID debe usar la sintaxis descrita para CPACK_WIX_UPGRADE_GUID.

CPACK_WIX_LICENSE_RTF
Archivo de licencia RTF

Si CPACK_RESOURCE_FILE_LICENSE tiene una extensión .rtf, se usa tal cual.

Si CPACK_RESOURCE_FILE_LICENSE tiene una extensión .txt, se convierte implícitamente a RTF por el generador WIX. La codificación esperada del archivo .txt es UTF-8.

Con CPACK_WIX_LICENSE_RTF puede anular el archivo de licencia usado por el generador WIX en caso de que CPACK_RESOURCE_FILE_LICENSE esté en un formato no compatible o la conversión .txt -> .rtf no funcione como se espera.

CPACK_WIX_PRODUCT_ICON
El icono que se muestra junto al nombre del programa en Agregar o quitar programas.

Si se establece, este icono se usa en lugar del icono predeterminado.

CPACK_WIX_UI_REF
Especifica el conjunto de diálogos de la extensión UI de WiX:
  • Con las herramientas WiX .NET, este es el Id. del elemento <ui:WixUI> en la plantilla WiX predeterminada.
  • Con el conjunto de herramientas WiX v3, este es el Id. del elemento <UIRef> en la plantilla WiX predeterminada.

El valor predeterminado es WixUI_InstallDir en caso de que no se hayan definido componentes de CPack y WixUI_FeatureTree en caso contrario.

CPACK_WIX_UI_BANNER
El mapa de bits aparecerá en la parte superior de todas las páginas del instalador excepto en los diálogos de bienvenida y finalización.

Si se establece, esta imagen reemplazará la imagen de banner predeterminada.

Esta imagen debe ser de 493 por 58 píxeles.

CPACK_WIX_UI_DIALOG
Mapa de bits de fondo utilizado en los diálogos de bienvenida y finalización.

Si esta variable se establece, el instalador reemplazará la imagen de diálogo predeterminada.

Esta imagen debe ser de 493 por 312 píxeles.

CPACK_WIX_PROGRAM_MENU_FOLDER
Nombre de la carpeta del menú Inicio para el lanzador.

Si esta variable no se establece, se inicializará con CPACK_PACKAGE_NAME

Añadido en la versión 3.16: Si esta variable se establece en ., entonces los accesos directos de la aplicación se crearán directamente en el menú Inicio y se omitirá el acceso directo del desinstalador.

CPACK_WIX_CULTURES
Idioma(s) del instalador

Los idiomas se compilan en la biblioteca de extensión UI de Wix. Para usarlos, simplemente proporcione el nombre de la cultura. Si especifica más de un identificador de cultura en una lista delimitada por comas o puntos y comas, se utilizará el primero que se encuentre. Puede encontrar una lista de idiomas compatibles en: https://docs.firegiant.com/wix3/wixui/wixui_localization/

CPACK_WIX_TEMPLATE
Archivo de plantilla para la generación de WiX

Si esta variable se establece, la plantilla especificada se utilizará para generar el archivo wxs de WiX. Esto debe usarse si se requiere una personalización adicional de la salida. El contenido de la plantilla anulará el efecto de la mayoría de las variables CPACK_WIX_.

Si esta variable no se establece, se utilizará la plantilla MSI predeterminada incluida con CMake.

CPACK_WIX_PATCH_FILE
Lista opcional de archivos XML con fragmentos que se insertarán en las fuentes WiX generadas.

Añadido en la versión 3.5: Soporte para listar múltiples archivos de parche.

Esta variable opcional se puede utilizar para especificar un archivo XML que el generador WIX utilizará para inyectar fragmentos en sus archivos fuente generados.

Los archivos de parche entendidos por el generador CPack WIX siguen aproximadamente este esquema compacto RELAX NG:

start = CPackWiXPatch
CPackWiXPatch = element CPackWiXPatch { CPackWiXFragment* }
CPackWiXFragment = element CPackWiXFragment
{
    attribute Id { string },
    fragmentContent*
}
fragmentContent = element * - CPackWiXFragment
{
    (attribute * { text } | text | fragmentContent)*
}

Actualmente, los fragmentos se pueden inyectar en la mayoría de los elementos Component, File, Directory y Feature.

Añadido en la versión 3.3: Se pueden utilizar los siguientes Ids especiales adicionales:

  • #PRODUCT para el elemento <Product>.
  • #PRODUCTFEATURE para el elemento raíz <Feature>.

Añadido en la versión 3.7: Soporte para parchear elementos <Feature> arbitrarios.

Añadido en la versión 3.9: Permitir establecer atributos adicionales.

El siguiente ejemplo ilustra cómo funciona esto.

Dado que el generador WIX crea el siguiente elemento XML:

<Component Id="CM_CP_applications.bin.my_libapp.exe" Guid="*"/>

Se puede utilizar el siguiente archivo de parche XML para inyectar un elemento Environment en él:

<CPackWiXPatch>
  <CPackWiXFragment Id="CM_CP_applications.bin.my_libapp.exe">
    <Environment Id="MyEnvironment" Action="set"
      Name="MyVariableName" Value="MyVariableValue"/>
  </CPackWiXFragment>
</CPackWiXPatch>

Archivos de objeto o bibliotecas WiX adicionales para usar con WiX Toolset v3.

Esta variable proporciona una lista opcional de archivos de objeto WiX adicionales (.wixobj) y/o archivos de biblioteca WiX (.wixlib). Las rutas deben ser absolutas.

CPACK_WIX_CMAKE_PACKAGE_REGISTRY

La siguiente lista contiene algunas propiedades de ejemplo que se pueden usar para personalizar la información en "Programas y características" (también conocido como "Agregar o quitar programas")

Agregado en la versión 3.7.

Establece el nombre de la característica de instalación raíz en el instalador WIX. Igual que CPACK_COMPONENT_<compName>_DISPLAY_NAME para los componentes.

CPACK_WIX_ROOT_FEATURE_DESCRIPTION
Agregado en la versión 3.7.

Establece la descripción de la característica de instalación raíz en el instalador WIX. Igual que CPACK_COMPONENT_<compName>_DESCRIPTION para los componentes.

CPACK_WIX_SKIP_PROGRAM_FOLDER
Agregado en la versión 3.7.

Si esta variable se establece en true, la ubicación de instalación predeterminada del paquete generado será directamente CPACK_PACKAGE_INSTALL_DIRECTORY. La ubicación de instalación no se ubicará relativamente debajo de ProgramFiles o ProgramFiles64.

Nota:

Los instaladores creados con esta característica no tienen en cuenta las diferencias entre el sistema en el que se crea el instalador y el sistema en el que podría usarse el instalador.

Por lo tanto, es posible que el instalador, por ejemplo, intente instalar en una unidad que no está disponible o no es la deseada, o en una ruta que no sigue la localización o convención del sistema en el que se realiza la instalación.

CPACK_WIX_ROOT_FOLDER_ID
Agregado en la versión 3.9.

Esta variable permite especificar un ID de carpeta raíz personalizado. El token específico del generador <64> se puede usar para IDs de carpeta que vienen en variantes de 32 y 64 bits. En compilaciones de 32 bits el token se expandirá vacío mientras que en compilaciones de 64 bits se expandirá a 64.

Cuando no se establece, los instaladores generados se instalarán en LocalAppDataFolder si CPACK_WIX_INSTALL_SCOPE es perUser, y en ProgramFiles<64>Folder en caso contrario.

CPACK_WIX_ROOT
Esta variable se puede establecer opcionalmente en el directorio raíz de una instalación personalizada de WiX Toolset.

Cuando no se especifica, CPack intentará localizar una instalación de WiX Toolset mediante la variable de entorno WIX en su lugar.

CPACK_WIX_CUSTOM_XMLNS
Agregado en la versión 3.19.

Esta variable proporciona una lista de declaraciones de espacio de nombres personalizadas que son necesarias para usar extensiones de WiX. Cada declaración debe estar en la forma nombre=url, donde nombre es el espacio de nombres simple sin el prefijo xmlns: habitual y url es una url de espacio de nombres sin comillas. Se puede encontrar una lista de esquemas de WiX comúnmente conocidos aquí: https://docs.firegiant.com/wix3/xsd/

CPACK_WIX_SKIP_WIX_UI_EXTENSION
Agregado en la versión 3.23.

Si esta variable se establece en true, se omite la inclusión predeterminada de la extensión UI de WiX, es decir, el indicador -ext WixUIExtension o -ext WixToolset.UI.wixext no se pasa a las herramientas de WiX.

CPACK_WIX_ARCHITECTURE
Agregado en la versión 3.24.

Esta variable se puede establecer opcionalmente para especificar la arquitectura de destino del instalador. Por ejemplo, se puede establecer en x64 o arm64.

Cuando no se especifica, CPack usará por defecto x64 o x86.

CPACK_WIX_INSTALL_SCOPE
Agregado en la versión 3.29.

Esta variable se puede establecer opcionalmente para especificar el InstallScope del instalador (consulte https://docs.firegiant.com/wix3/xsd/wix/package/):

perMachine
Crea un instalador que se instala para todos los usuarios y requiere privilegios administrativos. Las entradas del menú Inicio creadas por el instalador son visibles para todos los usuarios.

Este es el valor predeterminado. Consulte la política CMP0172 <#policy:CMP0172>.

perUser
Crea un instalador que se instala solo para el usuario actual y no requiere privilegios administrativos. Las entradas del menú Inicio creadas por el instalador son visibles solo para el usuario actual.

Para habilitar la instalación por usuario, el instalador debe generar algunas entradas de registro adicionales que sirvan como "rutas clave" para los componentes instalados (consulte https://learn.microsoft.com/en-us/windows/win32/msi/ice38). Estas entradas de registro se crean bajo HKEY_CURRENT_USER, usando la ruta especificada por la variable CPACK_WIX_COMPONENT_KEYS_REGISTRY_PATH.

Cambiado en la versión 4.3: Antes de CMake 4.3, este valor estaba reservado para uso futuro y no era compatible.

NONE
Crea un instalador sin ningún atributo InstallScope.

Esto solo es compatible si CPACK_WIX_VERSION no está establecido, o está establecido en 3.

Obsoleto desde la versión 3.29: Este valor es solo para compatibilidad con el comportamiento inconsistente usado por CPack 3.28 y anteriores. El instalador resultante requiere privilegios administrativos y se instala en el directorio ProgramFiles de todo el sistema, pero la entrada del menú Inicio y el registro del desinstalador se crean solo para el usuario actual.

Advertencia:

Las instalaciones realizadas por instaladores creados con diferentes valores de InstallScope no se pueden actualizar ni reemplazar limpiamente entre sí. Por ejemplo, para hacer la transición de los instaladores de un proyecto de NONE a perMachine, o de perMachine a perUser, el último instalador debe distribuirse con instrucciones para desinstalar primero manualmente cualquier versión anterior.
CPACK_WIX_COMPONENT_KEYS_REGISTRY_PATH
Agregado en la versión 4.3.

Esta variable determina la ruta del registro bajo HKEY_CURRENT_USER donde el instalador creará entradas del registro para servir como "rutas de clave" para los componentes si CPACK_WIX_INSTALL_SCOPE está establecido en perUser.

Utilice barras inclinadas (/) como separadores de ruta para evitar problemas con los escapes; serán convertidas en barras invertidas (\) por el generador de WIX.

El valor predeterminado es Software/<Vendor>/<PackageName>/Components, donde <Vendor> se toma de CPACK_PACKAGE_VENDOR <#variable:CPACK_PACKAGE_VENDOR>, y <PackageName> se toma de CPACK_PACKAGE_NAME <#variable:CPACK_PACKAGE_NAME>.

Ejemplo: Software/MyCompany/MyProduct/Components

CPACK_WIX_CAB_PER_COMPONENT
Añadido en la versión 4.2.

Si esta variable se establece en true, se crea un archivo .cab por componente. El valor predeterminado es crear un único archivo .cab para todos los archivos del instalador.

WiX crea los archivos .cab en paralelo, por lo que múltiples archivos .cab pueden ser deseables para un empaquetado más rápido.
