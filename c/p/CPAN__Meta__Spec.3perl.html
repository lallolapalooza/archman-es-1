DESCRIPCIÓN

Este documento describe la versión 2 de la especificación de metadatos de distribución de CPAN, también conocida como "CPAN Meta Spec".

Se pueden emitir revisiones de esta especificación para correcciones de errores tipográficos y aclaraciones en el texto como CPAN::Meta::Spec 2.x. Estas revisiones nunca cambiarán la semántica ni añadirán ni eliminarán comportamiento especificado.

Los metadatos de la distribución describen propiedades importantes de las distribuciones de Perl. Herramientas de construcción de distribuciones como Module::Build, Module::Install, ExtUtils::MakeMaker o Dist::Zilla deberían crear un archivo de metadatos de acuerdo con esta especificación e incluirlo con la distribución para su uso por herramientas automatizadas que indexan, examinan, empaquetan o instalan distribuciones de Perl.

TERMINOLOGÍA

distribución
Este es el objeto principal descrito por los metadatos. En el contexto de este documento, normalmente se refiere a una colección de módulos, scripts y/o documentos que se distribuyen juntos para que otros desarrolladores los usen. Ejemplos de distribuciones son "Class-Container", "libwww-perl", o "DBI".
módulo
Se refiere a una biblioteca reutilizable de código contenida en un solo archivo. Los módulos normalmente contienen uno o más paquetes y a menudo se les hace referencia por el nombre de un paquete principal que se puede mapear al nombre del archivo. Por ejemplo, uno podría referirse a "File::Spec" en lugar de File/Spec.pm
paquete
Se refiere a un espacio de nombres declarado con la declaración de Perl "package" . En Perl, los paquetes a menudo tienen una propiedad de número de versión dada por la variable $VERSION en el espacio de nombres.
consumidor
Se refiere a código que lee un archivo de metadatos, lo deserializa en una estructura de datos en memoria, o interpreta una estructura de datos de elementos de metadatos.
productor
Se refiere a código que construye una estructura de datos de metadatos, la serializa en un flujo de bytes y/o la escribe en disco.
debe, debería, puede, etc.
Estos términos se interpretan como se describe en IETF RFC 2119.

TIPOS DE DATOS

Los campos en la sección "ESTRUCTURA" describen elementos de datos, cada uno de los cuales tiene un tipo de datos asociado como se describe aquí. Hay cuatro tipos primitivos: Boolean, String, List y Map. Otros tipos son subtipos de primitivos y definen estructuras de datos compuestas o definen restricciones sobre los valores de un elemento de datos.

Boolean

Un Boolean se usa para proporcionar un valor verdadero o falso. Debe representarse como un valor definido que sea "1" o "0" o que se convierta en cadena a esos valores.

String

Un String es un elemento de datos que contiene una secuencia de caracteres Unicode de longitud distinta de cero, como un escalar Perl ordinario que no es una referencia.

List

Un List es una colección ordenada de cero o más elementos de datos. Los elementos de un List pueden ser de tipos mixtos.

Los productores deben representar los elementos de List usando una estructura de datos que indique inequívocamente que se pueden tener múltiples valores, como una referencia a un arreglo Perl (un "arrayref").

Los consumidores que esperan un List deben considerar un String como equivalente a un List de longitud 1.

Map

Un Map es una colección no ordenada de cero o más elementos de datos ("valores"), indexados por elementos String asociados ("claves"). Los elementos de valor del Map pueden ser de tipos mixtos.

License String

Un License String es un subtipo de String con un conjunto restringido de valores. Los valores válidos se describen en detalle en la descripción del campo "license".

URL

URL es un subtipo de String que contiene un Localizador o Identificador de Recurso Uniforme. [ Este tipo se llama URL y no URI por razones históricas. ]

Version

Un Version es un subtipo de String que contiene un valor que describe el número de versión de paquetes o distribuciones. Las restricciones sobre el formato se describen en detalle en la sección "Formatos de Versión".

Version Range

El tipo Version Range es un subtipo de String. Describe un rango de Versiones que pueden estar presentes o instaladas para cumplir con los prerrequisitos. Se especifica en detalle en la sección "Rangos de Versión".

ESTRUCTURA

La estructura de metadatos es un elemento de datos de tipo Map. Esta sección describe las claves válidas dentro del Map.

Cualquier clave no descrita en este documento de especificación (ya sea de nivel superior o dentro de estructuras de datos compuestas descritas aquí) se considera clave personalizada y debe comenzar con una "x" o "X" seguida de un guion bajo; es decir, deben coincidir con el patrón: "qr{\Ax_}i". Si una clave personalizada se refiere a una estructura de datos compuesta, las subclaves dentro de ella no necesitan el prefijo "x_" o "X_".

Los consumidores de metadatos pueden ignorar alguna o todas las claves personalizadas. Todas las demás claves no descritas aquí son inválidas y deberían ser ignoradas por los consumidores. Los productores no deben generar ni emitir claves inválidas.

Para cada clave, se proporciona un ejemplo seguido de una descripción. La descripción comienza con la versión de la especificación en la que se añadió la clave o en la que se modificó la definición, si la clave es requerida u opcional y el tipo de datos del elemento de datos correspondiente. Estos elementos están en paréntesis, corchetes y llaves, respectivamente.

Si un tipo de datos es un Mapr Mapa de subtipo, las subclaves válidas serán descritas

también.

Algunos campos están marcados Obsoleto . Estos se muestran por contexto histórico y no deben producirse en ni consumirse de ninguna estructura de metadatos de la versión 2 o superior. CAMPOS OBLIGATORIOS

Los números de versión deben tratarse como cadenas, no números. Por ejemplo, 1.200" no debe serializarse como 1.2"
    . La comparación de versiones debería delegarse al módulo de versión de Perl, versión 0.80 o más 
reciente.

A menos que se especifique lo contrario, venúmeros de versión deben aparecer en
    uno de dos formatos: Versiones
    decimales Las versiones decimales son "números decimales" regulares, con algunas
      limitaciones. Deben ser no negativos y 
deben

version => '.1'          # Ilegal
      Versiones de
    enteros separados por puntos Las versiones de enteros separados por puntos (también conocidas como
      decimales separados por puntos) consisten en enteros positivos separados
      por caracteres de punto (es decir, "puntos",
      "puntos" o "puntos decimales"). Son equivalentes en

Comparando   Números de Versión


El módulo version proporciona la forma más fiable de comparar
    números de versiones de todas las diversas maneras en las que podrían ser proporcionados o podrían
    existir dentro de los módulos. Dadas dos cadenas que contienen números de versión,
    $v1 y $v2, deberían ser
    convertidas a objetos "version" antes de
    usar los operadores de comparación ordinarios. Por ejemplo:


use version;
if ( version->new($v1) <=> version->new($v2) ) {
  print "Las versiones no son iguales\n";
}


Si la única comparación necesaria es si un módulo instalado tiene
    una versión suficientemente alta, se puede realizar una prueba directa usando la forma de cadena
    de "eval" y la función
    "use" . Por ejemplo, para el módulo
    $mod y el prerrequisito de versión
    $prereq:


if ( eval "use $mod $prereq (); 1" ) {
  print "La versión del módulo $mod es correcta.\n";
}


Sin embargo, si los valores de $mod y
    $prereq no han sido depurados, esto
    presenta implicaciones de seguridad.






Prerrequisitos   para distribuciones configuradas dinámicamente


Cuando "dynamic_config" es verdadero,
    es un error presumir que los prerrequisitos dados en los metadatos de la distribución
    tendrán alguna relación en absoluto con los prerrequisitos reales
    de la distribución.


En la práctica, sin embargo, generalmente se puede esperar que tales prerrequisitos
    sean una de dos cosas:


    
  
  • Los prerrequisitos mínimos para la distribución, a los cuales la configuración
      dinámica solo añadirá elementos
    • 
  
  • Lo que sea con lo que la distribución fue configurada en la máquina del publicador en el momento de la publicación
    • 



El segundo caso a menudo resulta tener resultados idénticos al
    primer caso, aunque solo por accidente.


Como tal, los consumidores pueden usar estos datos para análisis informativo,
    pero presentarlos al usuario como canónicos o depender de ellos como tales es
    invariablemente la máxima locura.






Indexando   distribuciones al estilo de PAUSE


Mientras que no_index te dice qué debe ignorarse al indexar, esta
    especificación no tiene opinión sobre cómo debes obtener tu lista inicial de candidatos de
    cosas para posiblemente indexar. Para distribuciones "normales" podrías
    considerar simplemente indexar el contenido de lib/, pero hay muchas
    rarezas fascinantes en CPAN y muchas distribuciones de los días en que era normal
    poner el archivo .pm principal en la raíz del archivo de la distribución - así que PAUSE
    actualmente indexa todos los archivos .pm y .PL que no son (a) específicamente
    excluidos por no_index (b) en los directorios "inc",
    "xt", o
    "t" , o directorios comunes de 'errores'
    como "perl5".


O: Si estás intentando ser similar a PAUSE, asegúrate de omitir
    "inc",
    "xt" y
    "t" así como cualquier cosa marcada como
    no_index.


Recuerda también: Si el archivo META contiene un campo provides, no
    deberías indexar nada en primer lugar - simplemente úsalo.
