Comandos de CVS

Guía de los comandos de CVS

Este apéndice describe la estructura general de los comandos de cvs y describe algunos comandos en detalle (otros se describen en otro lugar; para una referencia rápida de los comandos de cvs , consulte el nodo `Invocando CVS' en el manual de CVS).

Estructura

Estructura general de los comandos de CVS

El formato general de todos los comandos de cvs es:

cvs [ cvs_options ] cvs_command [ command_options ] [ command_args ]
cvs
El nombre del programa cvs .
cvs_options
Algunas opciones que afectan a todos los subcomandos de cvs. Se describen más abajo.
cvs_command
Uno de varios subcomandos diferentes. Algunos comandos tienen alias que se pueden usar en su lugar; esos alias se anotan en el manual de referencia de ese comando. Solo hay dos situaciones en las que puede omitir cvs_command: cvs -H muestra una lista de los comandos disponibles, y cvs -v muestra la información de versión de cvs en sí mismo.
command_options
Opciones específicas del comando.
command_args
Argumentos de los comandos.

Desafortunadamente, hay cierta confusión entre cvs_options y command_options. Cuando se dan como cvs_option, algunas opciones solo afectan a algunos de los comandos. Cuando se dan como command_option , pueden tener un significado diferente y ser aceptadas por más comandos. En otras palabras, no tome la categorización anterior demasiado en serio. En su lugar, consulte la documentación.

Estado de salida

Estado de salida de CVS

cvs puede indicar al entorno de llamada si tuvo éxito o falló configurando su estado de salida. La forma exacta de probar el estado de salida variará de un sistema operativo a otro. Por ejemplo, en un script de shell de unix, la variable $? será 0 si el último comando devolvió un estado de salida exitoso, o mayor que 0 si el estado de salida indicaba un fallo.

Si cvs tiene éxito, devuelve un estado exitoso; si hay un error, imprime un mensaje de error y devuelve un estado de fallo. La única excepción a esto es el comando cvs diff . Devolverá un estado exitoso si no encontró diferencias, o un estado de fallo si hubo diferencias o si hubo un error. Debido a que este comportamiento no proporciona una buena manera de detectar errores, es posible que en el futuro cvs diff se cambie para comportarse como los otros comandos de cvs .

~/.cvsrc

Opciones predeterminadas y el archivo ~/.cvsrc

Hay algunas command_options que se usan tan a menudo que podría haber configurado un alias u otro medio para asegurarse de que siempre especifique esa opción. Un ejemplo (el que impulsó la implementación del soporte de .cvsrc , en realidad) es que muchas personas encuentran que la salida predeterminada del comando diff es muy difícil de leer, y que tanto los diffs de contexto como los unidiffs son mucho más fáciles de entender.

El archivo ~/.cvsrc es una manera en la que puede agregar opciones predeterminadas a los cvs_commands dentro de cvs, en lugar de depender de aliases u otros scripts de shell.

El formato del archivo ~/.cvsrc es simple. Se busca en el archivo una línea que comience con el mismo nombre que el cvs_command que se está ejecutando. Si se encuentra una coincidencia, el resto de la línea se divide (en caracteres de espacio en blanco) en opciones separadas y se agrega a los argumentos del comando antes de cualquier opción de la línea de comandos.

Si un comando tiene dos nombres (por ejemplo, checkout y co), se usará el nombre oficial, no necesariamente el que se usa en la línea de comandos, para hacer coincidir con el archivo. Así que si este es el contenido del archivo ~/.cvsrc del usuario:

log -N
diff -uN
rdiff -u
update -Pd
checkout -P
release -d

el comando cvs checkout foo tendría la opción -P agregada a los argumentos, así como cvs co foo.

Con el archivo de ejemplo de arriba, la salida de cvs diff foobar estará en formato unidiff. cvs diff -c foobar proporcionará diffs de contexto, como de costumbre. Obtener diffs en formato "antiguo" sería un poco más complicado, porque diff no tiene una opción para especificar el uso del formato "antiguo", así que necesitaría cvs -f diff foobar.

En lugar del nombre del comando, puede usar cvs para especificar opciones globales (consulte el nodo `Opciones globales' en el manual de CVS). Por ejemplo, la siguiente línea en .cvsrc

cvs -z6

hace que cvs use el nivel de compresión 6.

add

Añadir archivos y directorios al repositorio

  • Sinopsis: add [-k rcs-kflag] [-m message] archivos...
  • Requiere: repositorio, directorio de trabajo.
  • Cambia: repositorio, directorio de trabajo.

    El comando add se usa para presentar nuevos archivos y directorios para su adición al repositorio cvs . Cuando add se usa en un directorio, se crea un nuevo directorio en el repositorio inmediatamente. Cuando se usa en un archivo, solo se actualiza el directorio de trabajo. No se realizan cambios en el repositorio hasta que se usa el comando commit en el archivo recién añadido.

    El comando add también resucita archivos que han sido eliminados previamente. Esto se puede hacer antes o después de que se use el comando commit para finalizar la eliminación de archivos. Los archivos resucitados se restauran en el directorio de trabajo en el momento en que se ejecuta el comando add .

opciones de add

Estas opciones estándar son soportadas por add (vea el nodo `Common options' en el manual de CVS, para una descripción completa de ellas):

-k kflag
Procesar palabras clave de acuerdo a kflag. Vea `Keyword substitution' en el manual de CVS. Esta opción es persistente; las futuras actualizaciones de este archivo en este directorio de trabajo usarán el mismo kflag. El comando status puede ser visto para ver las opciones persistentes. Para más información sobre el status comando, vea el nodo `Invoking CVS' en el manual de CVS.
-m message
Usar message como el mensaje de registro, en lugar de invocar un editor.

admin

Administración

  • Requiere: repositorio, directorio de trabajo.
  • Cambia: repositorio.
  • Sinónimo: rcs

    Esta es la interfaz de cvs para diversas instalaciones administrativas. Algunas de ellas tienen una utilidad cuestionable para cvs pero existen por razones históricas. Algunas de las opciones cuestionables probablemente desaparecerán en el futuro. Este comando sí funciona recursivamente, por lo que se debe usar con extrema precaución.

    En unix, si existe un grupo llamado cvsadmin, solo los miembros de ese grupo pueden ejecutar cvs admin (excepto para el cvs admin -k comando, que puede ser ejecutado por cualquiera). Este grupo debe existir en el servidor, o en cualquier sistema que ejecute el cvs no cliente/servidor cvs. Para deshabilitar cvs admin para todos los usuarios, cree un grupo sin usuarios en él. En NT, la característica cvsadmin no existe y todos los usuarios pueden ejecutar cvs admin.

opciones de admin

Algunas de estas opciones tienen una utilidad cuestionable para cvs pero existen por razones históricas. Algunas incluso hacen imposible usar cvs ¡hasta que deshaga el efecto!

-Aoldfile
Puede no funcionar junto con cvs. Añadir la lista de acceso de oldfile a la lista de acceso del rcs archivo.
-alogins
Puede no funcionar junto con cvs. Añadir los nombres de inicio de sesión que aparecen en la lista separada por comas logins a la lista de acceso del rcs archivo.
-b[rev]
Establecer la rama por defecto a rev. En cvs, normalmente no manipula ramas por defecto; las etiquetas persistentes (vea el nodo `Sticky tags' en el manual de CVS) son una mejor manera de decidir en qué rama quiere trabajar. Hay una razón para ejecutar cvs admin -b: para revertir a la versión del proveedor al usar ramas de proveedor (vea el nodo `Reverting local changes' en el manual de CVS). No puede haber un espacio entre -b y su argumento.
-cstring
Establecer el líder de comentario a string. El líder de comentario no es usado por las versiones actuales de cvs o rcs 5.7. Por lo tanto, casi con seguridad no tiene que preocuparse por ello. Vea `Keyword substitution' en el manual de CVS.
-e[logins]
Puede no funcionar junto con cvs. Borrar los nombres de inicio de sesión que aparecen en la lista separada por comas logins de la lista de acceso del archivo RCS. Si logins se omite, borra toda la lista de acceso. No puede haber un espacio entre -e y su argumento.
-I
Ejecutar interactivamente, incluso si la entrada estándar no es un terminal. Esta opción no funciona con el cvs cliente/servidor y probablemente desaparezca en una versión futura de cvs.
-i
Inútil con cvs. Esto crea e inicializa un nuevo rcs archivo, sin depositar una revisión. Con cvs, añada archivos con el comando cvs add (vea el nodo `Adding files' en el manual de CVS).
-ksubst
Establecer la sustitución de palabras clave por defecto a subst. Vea `Keyword substitution' en el manual de CVS. Dar una opción -k explícita a cvs update, cvs export, o cvs checkout anula este valor por defecto.
-l[rev]
Bloquear la revisión con el número rev. Si se da una rama, bloquear la última revisión en esa rama. Si rev se omite, bloquear la última revisión en la rama por defecto. No puede haber un espacio entre -l y su argumento.

Esto se puede usar en conjunto con el script rcslock.pl en el directorio contrib de la distribución de fuentes de cvs para proporcionar comprobaciones reservadas (donde solo un usuario puede estar editando un archivo dado a la vez). Vea los comentarios en ese archivo para detalles (y vea el archivo README en ese directorio para descargos sobre la naturaleza no soportada de contrib). De acuerdo con los comentarios en ese archivo, el bloqueo debe establecerse en estricto (que es el valor por defecto).

-L
Establecer el bloqueo en estricto. El bloqueo estricto significa que el propietario de un archivo RCS no está exento del bloqueo para el checkin. Para uso con cvs, el bloqueo estricto debe ser establecido; vea la discusión bajo la opción -l arriba.
-mrev:msg
Reemplazar el mensaje de registro de la revisión rev con msg.
-Nname[:[rev]]
Actuar como -n, excepto que anula cualquier asignación previa de name. Para su uso con ramas mágicas, véase `Magic branch numbers' en el manual de CVS.
-nname[:[rev]]
Asociar el nombre simbólico name con la rama o revisión rev. Normalmente es mejor usar cvs tag o cvs rtag en su lugar. Eliminar el nombre simbólico si tanto : como rev se omiten; de lo contrario, imprimir un mensaje de error si name ya está asociado con otro número. Si rev es simbólico, se expande antes de la asociación. Un rev que consista en un número de rama seguido de un . representa la última revisión actual de la rama. Un : con un rev vacío representa la última revisión actual en la rama predeterminada, normalmente el tronco. Por ejemplo, cvs admin -nname: asocia name con la última revisión actual de todos los archivos RCS; esto contrasta con cvs admin -nname:$ que asocia name con los números de revisión extraídos de las cadenas de palabras clave en los archivos de trabajo correspondientes.
-orange
Elimina (desactualiza) las revisiones dadas por range.

Nótese que este comando puede ser bastante peligroso a menos que se sepa exactamente lo que se está haciendo (por ejemplo, véanse las advertencias más abajo sobre cómo la sintaxis rev1:rev2 es confusa).

Si se tiene poco espacio en disco, esta opción podría ayudar. Pero piénselo dos veces antes de usarla—¡no hay forma de deshacer este comando salvo restaurando la última copia de seguridad! Si se eliminan revisiones distintas de las planeadas, ya sea por descuido o (Dios no lo quiera) por un error de cvs , no hay oportunidad de corregir el error antes de que las revisiones sean eliminadas. Probablemente sería una buena idea experimentar primero en una copia del repositorio.

Especificar range de una de las siguientes maneras:

rev1::rev2
Colapsar todas las revisiones entre rev1 y rev2, de modo que cvs solo almacene las diferencias asociadas con ir de rev1 a rev2, no los pasos intermedios. Por ejemplo, después de -o 1.3::1.5 se puede recuperar la revisión 1.3, la revisión 1.5, o las diferencias para ir de 1.3 a 1.5, pero no la revisión 1.4, ni las diferencias entre 1.3 y 1.4. Otros ejemplos: -o 1.3::1.4 y -o 1.3::1.3 no tienen efecto, porque no hay revisiones intermedias que eliminar.
::rev
Colapsar revisiones entre el comienzo de la rama que contiene rev y rev misma. El punto de bifurcación y rev se dejan intactos. Por ejemplo, -o ::1.3.2.6 elimina la revisión 1.3.2.1, la revisión 1.3.2.5, y todo lo que hay en medio, pero deja 1.3 y 1.3.2.6 intactos.
rev::
Colapsar revisiones entre rev y el final de la rama que contiene rev. La revisión rev se deja intacta pero la revisión principal es eliminada.
rev
Eliminar la revisión rev. Por ejemplo, -o 1.3 es equivalente a -o 1.2::1.4.
rev1:rev2
Eliminar las revisiones desde rev1 hasta rev2, inclusive, en la misma rama. No se podrá recuperar rev1 ni rev2 ni ninguna de las revisiones en medio. Por ejemplo, el comando cvs admin -oR_1_01:R_1_02 . rara vez es útil. Significa eliminar revisiones hasta, e incluyendo, la etiqueta R_1_02. ¡Pero cuidado! Si hay archivos que no han cambiado entre R_1_02 y R_1_03, el archivo tendrá el mismo número de revisión numérico asignado a las etiquetas R_1_02 y R_1_03. Así que no solo será imposible recuperar R_1_02; ¡R_1_03 también tendrá que ser restaurada desde las cintas! En la mayoría de los casos se quiere especificar rev1::rev2 en su lugar.
:rev
Eliminar revisiones desde el comienzo de la rama que contiene rev hasta e incluyendo rev.
rev:
Eliminar revisiones desde la revisión rev, incluyendo rev misma, hasta el final de la rama que contiene rev.

Ninguna de las revisiones a eliminar puede tener ramas o bloqueos.

Si alguna de las revisiones a eliminar tiene nombres simbólicos, y se especifica una de las sintaxis :: , entonces cvs dará un error y no eliminará ninguna revisión. Si realmente se quiere eliminar tanto los nombres simbólicos como las revisiones, primero eliminar los nombres simbólicos con cvs tag -d, luego ejecutar cvs admin -o. Si se especifican las sintaxis no-:: , entonces cvs eliminará las revisiones pero dejará los nombres simbólicos apuntando a revisiones inexistentes. Este comportamiento se preserva por compatibilidad con versiones anteriores de cvs, pero como no es muy útil, en el futuro podría cambiar para ser como el caso :: .

Debido a la forma en que cvs maneja las ramas, rev no puede especificarse simbólicamente si es una rama. Véase `Magic branch numbers' en el manual de CVS para una explicación.

Asegurarse de que nadie haya hecho una copia de la revisión que se desactualiza. Ocurrirán cosas extrañas si alguien empieza a editarla y trata de hacer check-in de nuevo. Por esta razón, esta opción no es una buena forma de deshacer un commit erróneo; en su lugar, hacer commit de una nueva revisión que deshaga el cambio erróneo (véase el nodo `Merging two revisions' en el manual de CVS).

    commit

    Incorporate changes from working files into repository

    • Synopsis: commit [-lR] [-r rev] [-F file | -m msg] [-d msg] [-v] [-p] [files...]
    • Requires: working directory, repository.
    • Changes: repository.
    • Synonym: ci

      Use commit when you want to incorporate changes from your working source files into the source repository.

      If you don't specify particular files to commit, all of the files in your working current directory are examined. commit is careful to change in the repository only those files that you have really changed. By default (or if you explicitly specify the -R option), files in subdirectories are also examined and committed if they have changed; you can use the -l option to limit commit to the current directory only.

      commit verifies that the selected files are up to date with the current revisions in the source repository; it will notify you, and exit without committing, if any of the specified files must be made current first with update (see node `update' in the CVS manual). commit does not call the update command for you, but rather leaves that for you to do when the time is right.

      When all is well, an editor is invoked to allow you to enter a log message that will be written to one or more logging programs (see node `modules' in the CVS manual, and see node `loginfo' in the CVS manual) and placed in the rcs file inside the repository. This log message can be retrieved with the log command; see node `log' in the CVS manual. You can specify the log message on the command line with the -m message option, and thus avoid the editor invocation, or use the -F file option to specify that the argument file contains the log message.

    commit options

    These standard options are supported by commit (see node `Common options' in the CVS manual for a complete description of them):

    -l
    Local; run only in current working directory.
    -R
    Commit directories recursively. This is on by default.
    -r revision
    Commit to revision. revision must be either a branch, or a revision on the main trunk that is higher than any existing revision number (see node `Assigning revisions' in the CVS manual). You cannot commit to a specific revision on a branch.

    commit also supports these options:

    -F file
    Read the log message from file, instead of invoking an editor.
    -f
    Note that this is not the standard behavior of the -f option as defined in `Common options' in the CVS manual.

    Force cvs to commit a new revision even if you haven't made any changes to the file. If the current revision of file is 1.7, then the following two commands are equivalent:

    $ cvs commit -f file
    $ cvs commit -r 1.8 file

    The -f option disables recursion (i.e., it implies -l). To force cvs to commit a new revision for all files in all subdirectories, you must use -f -R.

    -m message
    Use message as the log message, instead of invoking an editor.

    commit examples

    Committing to a branch

    You can commit to a branch revision (one that has an even number of dots) with the -r option. To create a branch revision, use the -b option of the rtag or tag commands (see node `Branching and merging' in the CVS manual). Then, either checkout or update can be used to base your sources on the newly created branch. From that point on, all commit changes made within these working sources will be automatically added to a branch revision, thereby not disturbing main-line development in any way. For example, if you had to create a patch to the 1.2 version of the product, even though the 2.0 version is already under development, you might do:

    $ cvs rtag -b -r FCS1_2 FCS1_2_Patch product_module
    $ cvs checkout -r FCS1_2_Patch product_module
    $ cd product_module
    [[ hack away ]]
    $ cvs commit

    This works automatically since the -r option is sticky.

    Creating the branch after editing

    Say you have been working on some extremely experimental software, based on whatever revision you happened to checkout last week. If others in your group would like to work on this software with you, but without disturbing main-line development, you could commit your change to a new branch. Others can then checkout your experimental stuff and utilize the full benefit of cvs conflict resolution. The scenario might look like:

    [[ hacked sources are present ]]
    $ cvs tag -b EXPR1
    $ cvs update -r EXPR1
    $ cvs commit

    The update command will make the -r EXPR1 option sticky on all files. Note that your changes to the files will never be removed by the update command. The commit will automatically commit to the correct branch, because the -r is sticky. You could also do like this:

    [[ hacked sources are present ]]
    $ cvs tag -b EXPR1
    $ cvs commit -r EXPR1

    but then, only those files that were changed by you will have the -r EXPR1 sticky flag. If you hack away, and commit without specifying the -r EXPR1 flag, some files may accidentally end up on the main trunk.

    To work with you on the experimental change, others would simply do

    $ cvs checkout -r EXPR1 whatever_module

      Cuando usa import para actualizaciones de código fuente que ha sido modificado en su repositorio de código fuente (desde una importación anterior), le notificará de cualquier archivo que entre en conflicto en las dos ramas del desarrollo; use checkout -j para reconciliar las diferencias, como import le indica que haga.
