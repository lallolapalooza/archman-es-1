cvs(5) Manual de Formatos de Archivo cvs(5)

NOMBRE

cvs - Archivos de soporte del Sistema de Versiones Concurrentes

NOTA

Esta documentación puede que ya no esté actualizada. Por favor, consulte el Cederqvist (Manual de CVS) como se especifica en cvs(1).

SINOPSIS

$CVSROOT/CVSROOT/commitinfo,v
$CVSROOT/CVSROOT/cvsignore,v
$CVSROOT/CVSROOT/cvswrappers,v
$CVSROOT/CVSROOT/editinfo,v
$CVSROOT/CVSROOT/history
$CVSROOT/CVSROOT/loginfo,v
$CVSROOT/CVSROOT/modules,v
$CVSROOT/CVSROOT/rcsinfo,v
$CVSROOT/CVSROOT/taginfo,v

DESCRIPCIÓN

cvs es un sistema para proporcionar control de versiones a colecciones jerárquicas de directorios de código fuente. Los comandos y procedimientos para usar cvs se describen en cvs(1).

cvs gestiona repositorios de código fuente, los directorios que contienen copias maestras de los archivos bajo control de revisiones, copiando revisiones particulares de los archivos a los directorios de trabajoprivados de los desarrolladores (y las modificaciones de vuelta desde ellos). En términos de estructura de archivos, cada repositorio de código fuente individual es un subdirectorio inmediato de $CVSROOT.

Los archivos descritos aquí son archivos de soporte; no tienen que existir para que cvs opere, pero le permiten hacer que la operación de cvs sea más flexible.

Puede usar el archivo `modules' para definir nombres simbólicos para colecciones de código fuente mantenidas con cvs. Si no existe el archivo `modules', los desarrolladores deben especificar rutas de archivo completas (absolutas, o relativas a $CVSROOT) para los archivos que desean gestionar con los comandos de cvs .

Puede usar el archivo `commitinfo' para definir programas a ejecutar siempre que `'cvs commit' esté a punto de ejecutarse. Estos programas se usan para la verificación de ``pre-commit'' para verificar que los archivos modificados, añadidos y eliminados están realmente listos para ser confirmados. Algunos usos para esta verificación podrían ser desactivar una parte (o todo) del repositorio de código fuente a una persona o grupo particular. O, tal vez, verificar que los archivos cambiados se ajustan a los estándares del sitio para la práctica de codificación.

Puede usar el archivo `cvswrappers' para registrar comandos de cvs wrapper a usar al introducir y extraer archivos del repositorio. Los wrappers permiten que el archivo o directorio sea procesado en el camino hacia adentro y hacia afuera de CVS. Los usos previstos son muchos, un uso posible sería reformatear un archivo C antes de que el archivo sea introducido, para que todo el código en el repositorio se vea igual.

Puede usar el archivo `loginfo' para definir programas a ejecutar después de cualquier commit, que escribe una entrada de registro para los cambios en el repositorio. Estos programas de registro podrían usarse para añadir el mensaje de registro a un archivo. O enviar el mensaje de registro por correo electrónico a un grupo de desarrolladores. O, tal vez, publicar el mensaje de registro en un grupo de noticias particular.

Puede usar el archivo `taginfo' para definir programas a ejecutar después de cualquier operación tagortag . Estos programas podrían usarse para añadir un mensaje a un archivo que liste el nuevo nombre de etiqueta y el programador que la creó, o enviar correo a un grupo de desarrolladores, o, tal vez, publicar un mensaje en un grupo de noticias particular.

Puede usar el archivo `rcsinfo' para definir formularios para los mensajes de registro.

Puede usar el archivo `editinfo' para definir un programa a ejecutar para editar/validar las entradas de registro de `'cvs commit'. Esto es más útil cuando se usa con una especificación de formularios `rcsinfo', ya que puede verificar que los campos adecuados del formulario hayan sido rellenados por el usuario que confirma el cambio.

Puede usar el archivo `cvsignore' para especificar la lista predeterminada de archivos a ignorar durante update.

Puede usar el archivo `history' para registrar los comandos de cvs que afectan al repositorio. La creación de este archivo habilita el registro del historial.

ARCHIVOS

modules
El archivo `modules' registra sus definiciones de nombres para colecciones de código fuente. cvs usará estas definiciones si usa cvs para introducir un archivo con el formato correcto en `'$CVSROOT/CVSROOT/modules,v'.

El archivo `modules' puede contener líneas en blanco y comentarios (líneas que comienzan con `'#') así como definiciones de módulos. Las líneas largas pueden continuarse en la siguiente línea especificando una barra invertida (``\'') como el último carácter de la línea.

Una definición de módulo es una sola línea del archivo `modules', en cualquiera de dos formatos. En ambos casos, mname representa el nombre simbólico del módulo, y el resto de la línea es su definición.

mname -a aliases...
Esto representa la forma más simple de definir un módulo mname. El `'-a' marca la definición como un alias simple: cvs tratará cualquier uso de mname (como argumento de comando) como si se hubiera especificado la lista de nombres aliases en su lugar. aliases puede contener otros nombres de módulos o rutas. Cuando usa rutas en aliases, `'cvs checkout' crea todos los directorios intermedios en el directorio de trabajo, como si la ruta se hubiera especificado explícitamente en los argumentos de cvs .

mname [ options ] dir [ files... ] [ &module... ]

En el caso más simple, esta forma de definición de módulo se reduce a `'mname dir'. Esto define todos los archivos en el directorio dir como el módulo mname. dir es una ruta relativa (desde $CVSROOT) a un directorio de código fuente en uno de los repositorios de código fuente. En este caso, en checkout, se crea un solo directorio llamado mname como directorio de trabajo; no se usan niveles de directorio intermedios por defecto, incluso si dir era una ruta que involucraba varios niveles de directorio.

Al especificar explícitamente files en la definición del módulo después de dir, puede seleccionar archivos particulares del directorio dir. La definición de ejemplo para modules es un ejemplo de un módulo definido con un solo archivo de un directorio particular. Aquí hay otro ejemplo:

m4test  unsupported/gnu/m4 foreach.m4 forloop.m4

Con esta definición, ejecutar `'cvs checkout m4test' creará un solo directorio de trabajo `m4test' que contiene los dos archivos listados, que provienen ambos de un directorio común varios niveles adentro en el cvs repositorio de código fuente.

Una definición de módulo puede referirse a otros módulos incluyendo `'&module' en su definición. checkout crea un subdirectorio para cada modulede este tipo, en su directorio de trabajo.
Nuevo en cvs 1.3; evite esta característica si comparte definiciones de módulos con versiones más antiguas de cvs.

Finalmente, puede usar una o más de las siguientes opciones en las definiciones de módulos:

`'-d name', para nombrar el directorio de trabajo de otra manera que no sea el nombre del módulo.
Nuevo en cvs 1.3; evite esta característica si comparte definiciones de módulos con versiones más antiguas de cvs.

`'-i prog' le permite especificar un programa prog a ejecutar siempre que se confirman archivos en un módulo. prog se ejecuta con un solo argumento, la ruta de archivo completa del directorio afectado en un repositorio de código fuente. Los archivos `commitinfo', `loginfo' y `editinfo' proporcionan otras formas de llamar a un programa en commit.

`'-o prog' le permite especificar un programa prog a ejecutar siempre que se extraen archivos de un módulo. prog se ejecuta con un solo argumento, el nombre del módulo.

`'-e prog' le permite especificar un programa prog a ejecutar siempre que se exportan archivos de un módulo. prog se ejecuta con un solo argumento, el nombre del módulo.

`'-t prog' le permite especificar un programa prog a ejecutar siempre que se etiquetan archivos de un módulo. prog se ejecuta con dos argumentos: el nombre del módulo y la etiqueta simbólica especificada a rtag.

`'-u prog' le permite especificar un programa prog a ejecutar siempre que se ejecuta `'cvs update' desde el directorio de nivel superior del módulo extraído. prog se ejecuta con un solo argumento, la ruta completa al repositorio de código fuente para este módulo.

commitinfo, loginfo, rcsinfo, editinfo
Todos estos archivos especifican programas a llamar en diferentes puntos del proceso de `cvs commit'. Tienen una estructura común. Cada línea es un par de campos: una expresión regular, separada por espacio en blanco de un nombre de archivo o plantilla de línea de comandos. Siempre que una de las expresiones regulares coincida con un nombre de directorio en el repositorio, se usa el resto de la línea. Si la línea comienza con el carácter # , toda la línea se considera un comentario y se ignora. El espacio en blanco entre los campos también se ignora.

Para `loginfo', el resto de la línea es una plantilla de línea de comandos a ejecutar. Las plantillas pueden incluir no solo un nombre de programa, sino cualquier lista de argumentos que desee. Si escribe `%s' en algún lugar de la lista de argumentos, cvs proporciona, en ese punto, la lista de archivos afectados por el commit. La primera entrada de la lista es la ruta relativa dentro del repositorio de código fuente donde se está realizando el cambio. Los argumentos restantes enumeran los archivos que están siendo modificados, agregados o eliminados por esta invocación de commit .

Para `taginfo', el resto de la línea es una plantilla de línea de comandos a ejecutar. Los argumentos pasados al comando son, en orden, el nombre de etiqueta (tagname), la operación (es decir, add para `tag', mov para `tag -F', y del para `tag -d'), el repositorio, y cualquier resto son pares de nombre de archivo revisión (filename revision). Una salida distinta de cero del programa filtro hará que la etiqueta sea abortada.

Para `commitinfo', el resto de la línea es una plantilla de línea de comandos a ejecutar. La plantilla puede incluir no solo un nombre de programa, sino cualquier lista de argumentos que desee. La ruta completa al repositorio de código fuente actual se agrega a la plantilla, seguida de los nombres de archivo de cualquier archivo involucrado en el commit (archivos agregados, eliminados y modificados).

Para `rcsinfo', el resto de la línea es la ruta completa a un archivo que debe ser cargado en la plantilla del mensaje de registro (log).

Para `editinfo', el resto de la línea es una plantilla de línea de comandos a ejecutar. La plantilla puede incluir no solo un nombre de programa, sino cualquier lista de argumentos que desee. La ruta completa al archivo de plantilla de mensaje de registro actual se agrega a la plantilla.

Puede usar una de dos cadenas especiales en lugar de una expresión regular: `ALL' especifica una plantilla de línea de comandos que siempre debe ser ejecutada, y `DEFAULT' especifica una plantilla de línea de comandos a usar si ninguna expresión regular coincide.

El archivo `commitinfo' contiene comandos a ejecutar antes de cualquier otra actividad de commit , para permitirle verificar cualquier condición que deba ser satisfecha antes de que el commit pueda proceder. El resto del commit se ejecutará solo si todos los comandos seleccionados de este archivo terminan con un estado de salida 0.

El archivo `rcsinfo' le permite especificar plantillas de registro (log templates) para la sesión de registro de commit ; puede usar esto para proporcionar un formulario para editar al llenar el registro de commit . El campo después de la expresión regular, en este archivo, contiene nombres de archivos (de archivos que contienen los formularios de registro) en lugar de plantillas de comandos.

El archivo `editinfo' le permite ejecutar un script antes de que el commit comience, pero después de que la información de registro sea registrada. Estos scripts de "edición" pueden verificar la información registrada en el archivo de registro. Si el script de edición termina con un estado de salida distinto de cero, el commit es abortado.

El archivo `loginfo' contiene comandos a ejecutar al final de un commit. El texto especificado como mensaje de registro de commit es pasado por tubería (pipe) a través del comando; los usos típicos incluyen enviar correo, archivar un artículo en un grupo de noticias, o agregarlo a un archivo central.

cvsignore, .cvsignore
La lista predeterminada de archivos (o patrones de nombre de archivo de sh(1)) a ignorar durante `cvs update'. Al inicio, cvs carga la lista predeterminada compilada de patrones de nombre de archivo (ver cvs(1)). Luego se carga la lista por repositorio incluida en $CVSROOT/CVSROOT/cvsignore , si existe. Luego se carga la lista por usuario desde `$HOME/.cvsignore'. Finalmente, a medida que cvs recorre sus directorios, cargará cualquier archivo `.cvsignore' por directorio siempre que encuentre uno. Estos archivos por directorio solo son válidos exactamente para el directorio que los contiene, no para ningún subdirectorio.
history
Cree este archivo en $CVSROOT/CVSROOT para habilitar el registro de historial (ver la descripción de `cvs history').
