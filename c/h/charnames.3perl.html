Comme mentionné ci-dessus sous « ALIAS », Unicode 6.1 définit des noms supplémentaires (synonymes ou alias) pour certains points de code, dont la plupart étaient déjà disponibles en tant qu'extensions Perl. Tous ceux-ci sont acceptés par « \N{...} » et les autres fonctions de ce module, mais « viacode » doit choisir quel nom retourner pour un point de code donné, donc il retourne le nom « le meilleur ». Pour comprendre comment cela fonctionne, il est utile d'en savoir plus sur les propriétés de nom Unicode. Tous les points de code n'ont en réalité qu'un seul nom, qui (à partir d'Unicode 2.0) ne peut jamais changer une fois qu'un caractère a été attribué au point de code. Mais des erreurs ont été commises dans l'attribution des noms, par exemple parfois une erreur de copie a été faite lors de la publication de el Estándar, lo que provocó que algunas palabras se escribieran mal, y no había forma de corregirlas. Posteriormente se creó la propiedad Name_Alias para manejar estas situaciones. Si un nombre era incorrecto, se publicaba un sinónimo corregido para él, usando Name_Alias. "viacode" devolverá ese sinónimo corregido como el "mejor" nombre para un punto de código. (Incluso es posible, aunque aún no ha ocurrido, que la corrección en sí misma necesite ser corregida, y así se pueda crear otro Name_Alias para ese punto de código; "viacode" devolverá la corrección más reciente.)

El nombre Unicode para cada uno de los caracteres de control (como LINE FEED) es la cadena vacía. Sin embargo, casi todos tenían nombres asignados por otros estándares, como el Estándar ASCII, o estaban en uso común. "viacode" devuelve estos nombres como los "mejores" disponibles. Unicode 6.1 ha creado Name_Aliases para cada uno de ellos, incluyendo nombres alternativos, como NEW LINE. "viacode" usa el nombre original, "LINE FEED" en preferencia al alternativo. De manera similar, el nombre devuelto para U+FEFF es "ZERO WIDTH NO-BREAK SPACE", no "BYTE ORDER MARK".

Hasta Unicode 6.1, los 4 caracteres de control U+0080, U+0081, U+0084 y U+0099 no tenían nombres ni alias. Para preservar la compatibilidad hacia atrás, cualquier alias que definas para estos puntos de código será devuelto por esta función, en preferencia al nombre oficial.

Algunos puntos de código también tienen nombres abreviados, como "LF" o "NL". "viacode" nunca los devuelve.

Debido a que puede añadirse una corrección de nombre en futuras versiones de Unicode, el nombre que "viacode" devuelve puede cambiar como resultado. Este es un evento raro, pero ocurre.

TRADUCTORES PERSONALIZADOS

El mecanismo de traducción de "\N{...}" escapes es general y no está incorporado en charnames.pm. Un módulo puede instalar traducciones personalizadas (dentro del ámbito en el que "use"a el módulo) con la siguiente invocación mágica:

sub import {
    shift;
    $^H{charnames} = \&
}

Aquí translator() es una subrutina que toma CHARNAME como argumento, y devuelve texto para insertar en la cadena en lugar del "\N{CHARNAME}" escape.

Esta es la única forma en que puedes crear una secuencia de puntos de código con nombre personalizada.

Dado que el texto a insertar debería ser diferente en el modo "bytes" y fuera de él, la función debería comprobar el estado actual del indicador "bytes"como en:

use bytes ();                      # for $bytes::hint_bits
sub translator {
    if ($^H & $bytes::hint_bits) {
        return bytes_translator(@_);
    }
    else {
        return utf8_translator(@_);
    }
}

Ver "ALIAS PERSONALIZADOS" arriba para las restricciones sobre CHARNAME.

Por supuesto, "vianame", "viacode", y "string_vianame" también necesitarían ser sobrescritos.

ERRORES

vianame() normalmente devuelve un punto de código ordinal, pero cuando el nombre de entrada es de la forma "U+...", devuelve un chr en su lugar. En este caso, si "use bytes" está en efecto y el carácter no cabe en un byte, devuelve "undef" y genera una advertencia.

Dado que la evaluación de la función de traducción (ver "TRADUCTORES PERSONALIZADOS") ocurre en medio de la compilación (de un literal de cadena), la función de traducción no debería hacer ningún "eval"ni "require". Esta restricción debería eliminarse (pero tiene baja prioridad) en una versión futura de Perl.
