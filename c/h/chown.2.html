chown(2) Manual de Llamadas al Sistema chown(2)

NOMBRE

chown, fchown, lchown, fchownat - cambiar la propiedad de un archivo

BIBLIOTECA

Biblioteca C estándar (libc,-lc)

SINOPSIS

#include <unistd.h>
int chown(const char *path, uid_t owner, gid_t group);
int fchown(int fd, uid_t owner, gid_t group);
int lchown(const char *path, uid_t owner, gid_t group);
#include <fcntl.h>           /* Definition of AT_* constants */
#include <unistd.h>
int fchownat(int dirfd, const char *path,
             uid_t owner, gid_t group, int flags);
Requisitos de la macro de prueba de características para glibc (ver feature_test_macros(7)):

fchown(), lchown():

    /* Since glibc 2.12: */ _POSIX_C_SOURCE >= 200809L
        || _XOPEN_SOURCE >= 500
        || /* glibc <= 2.19: */ _BSD_SOURCE

fchownat():

    Since glibc 2.10:
        _POSIX_C_SOURCE >= 200809L
    Before glibc 2.10:
        _ATFILE_SOURCE

DESCRIPCIÓN

Estas llamadas al sistema cambian el propietario y el grupo de un archivo. Las llamadas al sistema chown(), fchown(), y lchown() difieren solo en cómo se especifica el archivo:

•
chown() cambia la propiedad del archivo especificado por path, el cual se desreferencia si es un enlace simbólico.
•
fchown() cambia la propiedad del archivo al que se refiere el descriptor de archivo abierto fd.
•
lchown() es como chown(), pero no desreferencia enlaces simbólicos.

Solo un proceso privilegiado (Linux: uno con la capacidad CAP_CHOWN ) puede cambiar el propietario de un archivo. El propietario de un archivo puede cambiar el grupo del archivo a cualquier grupo del cual ese propietario sea miembro. Un proceso privilegiado (Linux: con CAP_CHOWN) puede cambiar el grupo arbitrariamente.

Si owner o group se especifican como -1, entonces ese ID no se cambia.

Cuando el propietario o el grupo de un archivo ejecutable es cambiado por un usuario no privilegiado, los bits de modo S_ISUID y S_ISGID se limpian. POSIX no especifica si esto también debería suceder cuando root hace el chown(); el comportamiento de Linux depende de la versión del kernel, y desde Linux 2.2.13, root es tratado como otros usuarios. En el caso de un archivo no ejecutable por el grupo (es decir, uno para el cual el bit S_IXGRP no está establecido), el bit S_ISGID indica bloqueo obligatorio, y no es limpiado por un chown().

Cuando el propietario o el grupo de un archivo ejecutable es cambiado (por cualquier usuario), todos los conjuntos de capacidades para el archivo son limpiados.

fchownat()

La llamada al sistema fchownat() opera exactamente de la misma manera que chown(), excepto por las diferencias descritas aquí.

Si path es relativo, entonces se interpreta relativo al directorio al que se refiere el descriptor de archivo dirfd (en lugar de relativo al directorio de trabajo actual del proceso que llama, como lo hace chown() para una ruta relativa).

Si path es relativo y dirfd es el valor especial AT_FDCWD, entonces path se interpreta relativo al directorio de trabajo actual del proceso que llama (como chown()).

Si path es absoluto, entonces dirfd es ignorado.

El argumento flags es una máscara de bits creada por la unión lógica (OR) de 0 o más de los siguientes valores;

AT_EMPTY_PATH (desde Linux 2.6.39)
Si path es una cadena vacía, opera en el archivo al que se refiere dirfd (el cual pudo haberse obtenido usando el indicador open(2) O_PATH ). En este caso, dirfd puede referirse a cualquier tipo de archivo, no solo a un directorio. Si dirfd es AT_FDCWD, la llamada opera en el directorio de trabajo actual. Este indicador es específico de Linux; define _GNU_SOURCE para obtener su definición.
AT_SYMLINK_NOFOLLOW
Si path es un enlace simbólico, no lo desreferencias: en su lugar opera en el enlace mismo, como lchown(). (Por defecto, fchownat() desreferencia enlaces simbólicos, como chown().)

Ver openat(2) para una explicación de la necesidad de fchownat().

VALOR DE RETORNO

En caso de éxito, se devuelve cero. En caso de error, se devuelve -1, y errno se establece para indicar el error.

ERRORES

Dependiendo del sistema de archivos, se pueden devolver errores distintos a los listados abajo.

Los errores más generales para chown() se listan abajo.

EACCES
Se deniega el permiso de búsqueda en un componente del prefijo de la ruta. (Ver también path_resolution(7).)
EBADF
(fchown()) fd no es un descriptor de archivo abierto válido.
EBADF
(fchownat()) path es relativo pero dirfd no es ni AT_FDCWD ni un descriptor de archivo válido.
EFAULT
path apunta fuera de tu espacio de direcciones accesible.
EINVAL
(fchownat()) Se especificó un indicador inválido en flags.
EIO
(fchown()) Ocurrió un error de E/S de bajo nivel mientras se modificaba el inode.
ELOOP
Se encontraron demasiados enlaces simbólicos al resolver path.
ENAMETOOLONG
path es demasiado largo.
ENOENT
El archivo no existe.
ENOMEM
No había suficiente memoria de kernel disponible.
ENOTDIR
Un componente del prefijo de la ruta no es un directorio.
ENOTDIR
(fchownat()) path es relativo y dirfd es un descriptor de archivo que se refiere a un archivo que no es un directorio.
EPERM
El proceso que llama no tenía los permisos requeridos (ver arriba) para cambiar el propietario y/o el grupo.
EPERM
El archivo está marcado como inmutable o de solo añadir. (Ver FS_IOC_SETFLAGS(2const).)
EROFS
El archivo nombrado reside en un sistema de archivos de solo lectura.

VERSIONES

La versión 4.4BSD solo puede ser usada por el superusuario (es decir, los usuarios ordinarios no pueden ceder archivos).

NOTAS

Propiedad de archivos nuevos

Cuando se crea un archivo nuevo (por ejemplo, mediante open(2) o mkdir(2)), su propietario se establece igual que el ID de usuario del sistema de archivos del proceso creador. El grupo del archivo depende de una serie de factores, incluido el tipo de sistema de archivos, las opciones utilizadas para montar el sistema de archivos y si el bit de modo set-group-ID está habilitado o no en el directorio padre. Si el sistema de archivos admite las opciones de montaje -o grpid (o, sinónimamente, -o bsdgroups) y -o nogrpid (o, sinónimamente, -o sysvgroups) de mount(8), las reglas son las siguientes:

•
Si el sistema de archivos se monta con -o grpid, el grupo de un archivo nuevo se establece igual que el del directorio padre.
•
Si el sistema de archivos se monta con -o nogrpid y el bit set-group-ID está deshabilitado en el directorio padre, el grupo de un archivo nuevo se establece igual que el GID del sistema de archivos del proceso.
•
Si el sistema de archivos se monta con -o nogrpid y el bit set-group-ID está habilitado en el directorio padre, el grupo de un archivo nuevo se establece igual que el del directorio padre.

Hasta Linux 4.12, las opciones de montaje -o grpid y -o nogrpid son compatibles con ext2, ext3, ext4 y XFS. Los sistemas de archivos que no admiten estas opciones de montaje siguen las reglas de -o nogrpid.

Notas de glibc

En kernels más antiguos donde fchownat() no está disponible, la función de envoltura de glibc recurre al uso de chown() y lchown(). Cuando path es relativo, glibc construye un nombre de ruta basado en el enlace simbólico en /proc/self/fd que corresponde al argumento dirfd.

NFS

La semántica de chown() se viola deliberadamente en los sistemas de archivos NFS que tienen habilitado el mapeo de UID. Además, la semántica de todas las llamadas al sistema que acceden al contenido del archivo se viola, porque chown() puede causar una revocación de acceso inmediata en archivos ya abiertos. La caché del lado del cliente puede provocar un retraso entre el momento en que se ha cambiado la propiedad para permitir el acceso a un usuario y el momento en que el archivo puede ser realmente accedido por el usuario en otros clientes.

Detalles históricos

Las llamadas al sistema originales de Linux chown(), fchown() y lchown() solo admitían IDs de usuario y grupo de 16 bits. Posteriormente, Linux 2.4 añadió chown32(), fchown32() y lchown32(), compatibles con IDs de 32 bits. Las funciones de envoltura de glibc chown(), fchown() y lchown() manejan transparentemente las variaciones entre versiones del kernel.

Antes de Linux 2.1.81 (excepto 2.1.46), chown() no seguía los enlaces simbólicos. Desde Linux 2.1.81, chown() sigue los enlaces simbólicos, y hay una nueva llamada al sistema lchown() que no sigue los enlaces simbólicos. Desde Linux 2.1.86, esta nueva llamada (que tiene la misma semántica que el antiguo chown()) tiene el mismo número de syscall, y chown() obtuvo el número introducido recientemente.

EJEMPLOS

El siguiente programa cambia la propiedad del archivo nombrado en su segundo argumento de línea de comandos al valor especificado en su primer argumento de línea de comandos. El nuevo propietario puede especificarse como un ID de usuario numérico o como un nombre de usuario (que se convierte en un ID de usuario utilizando getpwnam(3) para realizar una búsqueda en el archivo de contraseñas del sistema).

Fuente del programa

#include <pwd.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/types.h>
#include <unistd.h>
int
main(int argc, char *argv[])
{
    char           *endptr;
    uid_t          uid;
    struct passwd  *pwd;
    if (argc != 3 || argv[1][0] == '\0') {
        fprintf(stderr, "%s <owner> <file>\n", argv[0]);
        exit(EXIT_FAILURE);
    }
    uid = strtol(argv[1], &endptr, 10);  /* Permite una cadena numérica */
    if (*endptr != '\0') {         /* No era una cadena puramente numérica */
        pwd = getpwnam(argv[1]);   /* Intenta obtener UID para el nombre de usuario */
        if (pwd == NULL) {
            perror("getpwnam");
            exit(EXIT_FAILURE);
        }
        uid = pwd->pw_uid;
    }
    if (chown(argv[2], uid, -1) == -1) {
        perror("chown");
        exit(EXIT_FAILURE);
    }
    exit(EXIT_SUCCESS);
}
