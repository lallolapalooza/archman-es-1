Soporte local CGI en Chawan

Chawan admite la invocación de scripts CGI ubicados en un directorio especificado en la opción de configuración external.cgi-dir. Por defecto, está configurado a $CHA_DIR/cgi-bin (es decir, ~/.chawan/cgi-bin o ~/.config/chawan/cgi-bin, dependiendo de la ubicación de config.toml) y /usr/local/libexec/chawan/cgi-bin.

Se puede ejecutar un script CGI en uno de estos directorios visitando la URL cgi-bin:nombre-script. $PATH_INFO y $QUERY_STRING se establecen como de costumbre, es decir, cgi-bin:nombre-script/abcd?defgh=ijkl establecerá $PATH_INFO a /abcd, y $QUERY_STRING a defgh=ijkl.

Notas adicionales sobre el procesamiento de rutas CGI:

  • La URL debe ser opaca, por lo que no debes agregar una doble barra después del esquema. Por ejemplo, cgi-bin://nombre-script NO funcionará, solo cgi-bin:nombre-script.
  • Las rutas que comienzan con /cgi-bin/ o /$LIB/ se les quita automáticamente este segmento. Así, por ejemplo, cgi-bin:/cgi-bin/nombre-script se convierte en cgi-bin:nombre-script.
  • Si external.w3m-cgi-compat es verdadero, las URL file: se convierten en URL cgi-bin: si el nombre de la ruta comienza con /cgi-bin/, /$LIB/, o la ruta de un script CGI local. Nota: esto no es seguro, por favor no lo use a menos que sea necesario.
  • Se aceptan rutas absolutas, por ejemplo, cgi-bin:/ruta/a/directorio/cgi/nombre-script. Sin embargo, ten en cuenta que esto solo funciona si /ruta/a/directorio/cgi ya se ha especificado como un directorio CGI en external.cgi-dir.

Cabeceras

Los scripts CGI locales pueden enviar algunas cabeceras que Chawan interpretarará especialmente (y, por lo tanto, no las pasará hacia adelante, por ejemplo, a la API fetch, etc.):

  • Status: interpretada como el código de estado HTTP.
  • Cha-Control: cabecera especial, ver más abajo.

Estas cabeceras **deben** enviarse antes que cualquier cabecera regular. Las cabeceras recibidas después de una cabecera regular o una cabecera Cha-Control: ControlDone se tratarán como cabeceras regulares.

El valor de la cabecera Cha-Control se analiza de la siguiente manera:

Cha-Control-Value = Command *Parameter
Command = ALPHA *ALPHA
Parameter = SPACE *CHAR

En otras palabras, es Comando [Param1] [Param2] ....

Los comandos disponibles actualmente son:

  • Connected: No toma parámetros. Debe ser la primera cabecera reportada; significa que la conexión con el servidor se ha establecido con éxito, pero aún no se han recibido datos. Cuando se envía cualquier otra cabecera primero, Chawan actuará como si se hubiera enviado implícitamente una cabecera Cha-Control: Connected antes de ella.
  • ConnectionError: Debe ser la primera cabecera reportada. El Parámetro 1 es el código de error, ver más abajo. Si se proporcionan parámetros adicionales, se concatenan para formar un mensaje de error personalizado.

Nota: se prefieren mensajes de error cortos y descriptivos; los mensajes que no caben en la pantalla se truncan actualmente.

•
ControlDone: Señala que no se enviarán más cabeceras especiales; esto significa que las cabeceras Cha-Control y Status enviadas después de esto deben interpretarse como cabeceras regulares (y, por lo tanto, por ejemplo, estarán disponibles para código JS que llame al script usando la API fetch).

ADVERTENCIA: esta cabecera debe enviarse antes que cualquier cabecera no codificada que tome entrada externa. Por ejemplo, un cliente HTTP tendría que enviar Cha-Control: ControlDone antes de devolver las cabeceras recuperadas.

A continuación, se muestra una lista de códigos de error y sus contrapartes de cadena. Los scripts CGI pueden usar cualquiera de los dos (pero no ambos) en una cabecera ConnectionError.

  • 1 InternalError: Un error interno impidió que el script recuperara el recurso solicitado. Los scripts CGI también pueden usar esto para indicar que no tienen información sobre lo que salió mal.
  • 2 InvalidMethod: El cliente solicitó datos usando un método no compatible con este protocolo.
  • 3 InvalidURL: La URL de la solicitud no pudo interpretarse como una URL válida para este formato.
  • 4 FileNotFound: No se encontró ningún archivo en la dirección solicitada, por lo que la solicitud no tiene sentido. Nota: esto solo debe ser utilizado por protocolos que no dependen de una arquitectura cliente-servidor, por ejemplo, acceso a archivos locales, bases de datos locales o mecanismos de recuperación de archivos peer-to-peer. Un servidor que responde con "archivo no encontrado" NO es un error de conexión y se representa mejor como una respuesta con un código de estado 404.
  • 5 ConnectionRefused: El servidor rechazó el establecimiento de una conexión.
  • 6 ProxyRefusedToConnect: El proxy rechazó el establecimiento de una conexión.
  • 7 FailedToResolveHost: El nombre de host no pudo ser resuelto.
  • 8 FailedToResolveProxy: El proxy no pudo ser resuelto.
  • 9 ProxyAuthFail: El proxy rechazó el nombre de usuario/contraseña proporcionados.
  • 10 InvalidResponse: La respuesta del servidor se desvía tanto de la especificación que no se puede procesar de forma significativa.
  • 11 ProxyInvalidResponse: La respuesta del proxy se desvía tanto de la especificación que no se puede procesar de forma significativa.

Variables de entorno

Chawan establece las siguientes variables de entorno:

  • SERVER_SOFTWARE="Chawan"
  • SERVER_PROTOCOL="HTTP/1.0"
  • SERVER_NAME="localhost"
  • SERVER_PORT="80"
  • REMOTE_HOST="localhost"
  • REMOTE_ADDR="127.0.0.1"
  • GATEWAY_INTERFACE="CGI/1.1"
  • SCRIPT_NAME="/cgi-bin/nombre-script" si se llama con una ruta relativa, y "/ruta/a/script/nombre-script" si se llama con una ruta absoluta.
  • SCRIPT_FILENAME="/ruta/a/script/nombre-script"
  • QUERY_STRING= la cadena de consulta (es decir, URL.search). Esta variable está codificada en porcentaje.
  • PATH_INFO= todo después del nombre de la ruta del script, por ejemplo, para cgi-bin:nombre-script/abcd/efgh "/abcd/efgh". Esta variable NO está codificada en porcentaje.
  • REQUEST_URI="$SCRIPT_NAME/$PATH_INFO?$QUERY_STRING
  • REQUEST_METHOD= método HTTP utilizado para realizar la solicitud, por ejemplo, GET o POST
  • REQUEST_HEADERS= Una lista separada por saltos de línea de todas las cabeceras de esta solicitud.
  • CHA_LIBEXEC_DIR= El directorio libexec para el que se configuró Chawan en tiempo de compilación. Ver la sección de herramientas a continuación para más detalles sobre por qué esto es útil.
  • CONTENT_TYPE= para solicitudes POST, la cabecera Content-Type. No se establece para otros tipos de solicitud (por ejemplo, GET).
  • CONTENT_LENGTH= la longitud del contenido, si $CONTENT_TYPE se ha establecido.
  • ALL_PROXY= si se ha establecido un proxy, la URL del proxy. ADVERTENCIA: por razones de seguridad, esto **debe** respetarse al realizar conexiones externas. Si un script CGI no admite proxies, nunca debe realizar conexiones externas cuando la variable ALL_PROXY esté establecida, sino que debe devolver un mensaje de error.
  • HTTP_COOKIE= si está establecida, la cabecera Cookie.
  • HTTP_REFERER=

    Si example://username:password@example.org:1234/path/name.html?example es la URL original, entonces:

    • MAPPED_URI_SCHEME= el esquema de la URL original, en este caso example.
    • MAPPED_URI_USERNAME= la parte del nombre de usuario, en este caso username. Si no se especificó ningún nombre de usuario, la variable se establece a la cadena vacía.
    • MAPPED_URI_PASSWORD= la parte de la contraseña, en este caso password. Si no se especificó ninguna contraseña, la variable se establece a la cadena vacía.
    • MAPPED_URI_HOST= la parte del host, en este caso host.org Si no se especificó ningún host, la variable se establece a la cadena vacía. (Un ejemplo de URL sin host: about:blank, aquí blank es el nombre de la ruta.)
    • MAPPED_URI_PORT= el puerto, en este caso 1234. Si no se especificó ningún puerto, la variable se establece a la cadena vacía. (En este caso, se espera que el script CGI use el puerto predeterminado para el esquema, si lo hay.)
    • MAPPED_URI_PATH= el nombre de la ruta, en este caso /path/name.html?example. Si no se especificó ninguna ruta, la variable se establece a la cadena vacía. El nombre de la ruta está codificado porcentaje.
    • MAPPED_URI_QUERY= la cadena de consulta, en este caso example. A diferencia de en JavaScript, no se antepone un signo de interrogación a la cadena. La cadena de consulta también está codificada por porcentaje.

    Cuerpo de la solicitud

    Si el cuerpo de la solicitud no está vacío, se transmite al programa a través de la entrada estándar.

    Tenga en cuenta que esta puede ser tanto una solicitud application/x-www-form-urlencoded como una multipart/form-data; CONTENT_TYPE almacena información sobre el tipo de solicitud y, en el caso de una solicitud multipart, también el límite (boundary).

    Herramientas

    Chawan proporciona ciertos binarios auxiliares que pueden ser útiles para los scripts CGI. Se puede acceder a ellos de forma portátil ejecutando "$CHA_LIBEXEC_DIR"/[program].

    Actualmente, están disponibles las siguientes herramientas:

    • urldec: decodifica porcentaje las cadenas pasadas por la entrada estándar.
    • urlenc: codifica porcentaje las cadenas pasadas por la entrada estándar, tomando un conjunto de codificación por porcentaje como primer parámetro.

    Resolución de problemas

    Tenga en cuenta que la salida de error estándar se redirige a la consola del navegador (por predeterminado, M-cM-c). Esto facilita la depuración de un script CGI que no se comporta correctamente, pero también puede ralentizar el navegador en caso de un registro excesivo. Si este no es el comportamiento deseado, envuelva su script en un script de shell que redirija stderr a /dev/null.

    Mi script devuelve un mensaje de error “Failed to execute script”. error message.

    Esto significa que la llamada execl al script falló. Asegúrese de que el bit de ejecución de su script CGI esté activado, es decir, ejecute chmod +x /path/to/cgi/script.

    Mi script devuelve un mensaje de error “invalid CGI path”.

    Asegúrese de que no haya incluido barras iniciales. Recordatorio: cgi-bin://script-name no funciona, use cgi-bin:script-name.

    Mi script devuelve un mensaje de error “CGI file not found”. error message.

    Verifique dos veces que su script CGI esté en la ubicación correcta. Además, asegúrese de no estar llamando accidentalmente al script con una ruta absoluta a través de cgi-bin:/script-name (en lugar de la correcta cgi-bin:script-name).

    También es posible que external.cgi-dir no esté realmente configurado al directorio donde se encuentra su script. Tenga en cuenta que, de forma predeterminada, esto depende de la ruta del binario, por lo que, por ejemplo, si su binario está en ~/src/chawan/target/release/bin/cha, pero puso su script CGI en /usr/local/libexec/chawan/cgi-bin, entonces no funcionará.

    Mi script devuelve un mensaje de error “failed to set up CGI script”.

    Esto significa que o bien pipe o fork falló. ¿Quizás se le está acabando la memoria?
