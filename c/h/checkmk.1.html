CHECKMK(1) CHECKMK(1)

NOMBRE

checkmk - Script Awk para generar pruebas unitarias de C para su uso con el marco de pruebas unitarias Check.

SINOPSIS

checkmk [ clean_mode=1 ] [ archivo-de-entrada ]

DESCRIPCIÓN

Genera archivos de código fuente en lenguaje C que contienen pruebas unitarias para su uso con el marco de pruebas unitarias Check. El objetivo de este script es automatizar parte del código repetitivo típico que uno debe escribir al crear una suite de pruebas usando Check: específicamente, la instanciación de un SRunner, Suite(s), y TCase(s), y la construcción de relaciones entre estos objetos y las funciones de prueba.

Esta herramienta está destinada a ser utilizada por aquellos que están familiarizados con el marco de pruebas unitarias Check. Se asumirá familiaridad con el marco a lo largo de este manual.

El marco Check, junto con información sobre él, está disponible en https://libcheck.github.io/check/ <URL:https://libcheck.github.io/check/>.

El archivo-de-entrada argumento de checkmk usa una sintaxis simple, similar a la del preprocesador de C, para declarar funciones de prueba y para describir sus relaciones con Suites y TCases en Check. checkmk luego usa esta información para escribir automáticamente una main() función que contiene todas las declaraciones necesarias y cualquier código necesario para ejecutar las suites de pruebas. La salida final en lenguaje C se imprime en la checkmksalida estándar.

Se proporcionan facilidades para la inserción de código de usuario en la generada main() función, para permitir el uso de registro (logging), fixtures de prueba o valores de salida especializados.

Si bien es posible omitir el archivo-de-entrada argumento de checkmk y proporcionar el archivo de entrada en la checkmkentrada estándar en su lugar, generalmente se recomienda proporcionarlo como argumento. Hacer esto permite que checkmk conozca el nombre del archivo, para colocar referencias a él en los comentarios iniciales de la salida en lenguaje C, y para intercalar directivas C #line en todo el archivo, para facilitar la depuración de problemas al dirigir al usuario al archivo de entrada original.

OPCIONES

La única opción oficialmente soportada es especificar un valor verdadero (usando la definición de Awk para "true") para la variable clean_mode. Esto hace que checkmk no coloque las directivas #line apropiadas en el código fuente, lo que algunos podrían considerar un desorden innecesario.

El autor recomienda no usar esta opción, ya que hará que los compiladores y herramientas de depuración de C se refieran a líneas en la salida generada automáticamente, en lugar de a los archivos de entrada originales de checkmk. Esto animaría a los usuarios a editar los archivos de salida en lugar de los archivos de entrada originales, dificultaría que los editores inteligentes o los IDE abran el archivo correcto para editar, y podría resultar en que las correcciones se sobrescriban cuando los archivos de salida se regeneren.

Las directivas #line se suprimen automáticamente cuando el archivo de entrada se proporciona en la entrada estándar en lugar de como un argumento de línea de comandos.

EJEMPLO BÁSICO

En su forma más básica, un archivo de entrada puede ser simplemente un prólogo y una función de prueba. Cualquier cosa que aparezca antes de la primera función de prueba está en el prólogo, y se copiará en la salida verbatim. La función de prueba comienza con una línea en la forma:

#test nombre_de_la_prueba

Donde nombre_de_la_prueba es el nombre de tu función de prueba. Este nombre se utilizará para nombrar una función C, por lo que debe ser un identificador C válido.

Aquí hay un pequeño ejemplo completo:

--------------------------------------------------
/* Un ejemplo de prueba completo */
#include <stdio.h>
#test the_test
    int nc;
    const char msg[] = "\n\n    Hello, world!\n";
    nc = printf("%s", msg);
    ck_assert(nc == (sizeof(msg) - 1)); /* por el NUL terminante. */
--------------------------------------------------

Si colocas lo anterior en un archivo llamado basic_complete.ts y lo procesas usando el siguiente comando:

$ checkmk basic_complete.ts > basic_complete.c

basic_complete.c contendrá una salida similar a:

--------------------------------------------------
/*
 * NO EDITE ESTE ARCHIVO. Generado por checkmk.
 * Edite el archivo de código fuente original "in" en su lugar.
 */
#include <check.h>
/* Un ejemplo de prueba completo */
#include <stdio.h>
START_TEST(the_test)
{
    int nc;
    const char msg[] = "\n\n    Hello, world!\n";
    nc = printf("%s", msg);
    ck_assert(nc == (sizeof(msg) - 1)); /* por el NUL terminante. */
}
END_TEST
int main(void)
{
    Suite *s1 = suite_create("Core");
    TCase *tc1_1 = tcase_create("Core");
    SRunner *sr = srunner_create(s1);
    int nf;
    suite_add_tcase(s1, tc1_1);
    tcase_add_test(tc1_1, the_test);
    srunner_run_all(sr, CK_ENV);
    nf = srunner_ntests_failed(sr);
    srunner_free(sr);
    return nf == 0 ? 0 : 1;
}
--------------------------------------------------

En el uso real, basic_complete.c también contendría directivas #line.

RESUMEN DE DIRECTIVAS

Aquí hay un resumen completo de todas las directivas estilo preprocesador de C que son entendidas por checkmk. Vea más abajo para más detalles.

# test nombre_de_la_prueba
# test-signal(señal) nombre_de_la_prueba
# test-exit(código_de_salida) nombre_de_la_prueba
# test-loop(inicio, fin) nombre_de_la_prueba
# test-loop-signal(señal, inicio, fin) nombre_de_la_prueba
# test-loop-exit(código_de_salida, inicio, fin) nombre_de_la_prueba
# suite NombreDeLaSuiteDePruebas
# tcase NombreDelCasoDePrueba
# main-pre
# main-post

Todas las directivas no distinguen entre mayúsculas y minúsculas. Puede haber espacios en blanco al principio de la línea antes del #, entre el # y la directiva, entre la directiva y cualquier argumento, y al final de la línea.

DIRECTIVAS QUE DEFINEN PRUEBAS

Aquí hay una explicación más detallada de las directivas que pueden usarse para definir funciones de prueba y sus contenedores.

FUNCIONES DE PRUEBA

# test nombre_de_la_prueba
# test-signal(señal) nombre_de_la_prueba
# test-exit(código_de_salida) nombre_de_la_prueba
# test-loop(inicio, fin) nombre_de_la_prueba
# test-loop-signal(señal, inicio, fin) nombre_de_la_prueba
# test-loop-exit(código_de_salida, inicio, fin) nombre_de_la_prueba

Estas son las directivas más básicas para crear una plantilla para la entrada de checkmk. Son las únicas directivas requeridas: debe haber al menos una directiva #test* que aparezca en la plantilla, o checkmk fallará con un mensaje de error. Las directivas #test* pueden especificarse varias veces, cada una comenzando la definición de una nueva función de prueba.

El nombre_de_la_prueba argumento se usará como el nombre de una función de prueba en la salida en lenguaje C, por lo que debe ser un identificador C válido. Es decir, debe comenzar con un carácter alfabético o el guion bajo (_), seguido de caracteres alfanuméricos y/o guiones bajos opcionales.

También se permiten los Nombres de Caracteres Universales (introducidos en C99), de la forma \uXXXX o \UXXXXXXXX, donde las X representan dígitos hexadecimales.

Es un error especificar el mismo nombre_de_la_prueba en más de una directiva #test*, independientemente de si están asociados con diferentes casos de prueba o suites.

Vea IDENTIFICADORES DE CHECKMK para la lista de identificadores que deben evitarse para usar como nombres de funciones de prueba.

SUITES DE PRUEBAS

# suite NombreDeLaSuiteDePruebas

Esta directiva especifica el nombre de la suite de pruebas (objeto Suite en el marco de pruebas Check) al que se añadirán todos los casos de prueba futuros (y sus funciones de prueba).

El NombreDeLaSuiteDePruebas es una cadena de texto, y puede contener cualquier tipo de caracteres (excepto el carácter NUL ASCII y el salto de línea, que terminaría la directiva). Cualquier espacio en blanco inicial o final se omitirá del nombre de la suite de pruebas.

Comenzar una nueva suite de pruebas también comienza un nuevo caso de prueba, cuyo nombre es idéntico al de la nueva suite de pruebas. Este nombre de caso de prueba puede ser sobrescrito por una directiva #tcase posterior.

Tenga en cuenta que un objeto Suite no será realmente definido por chcheckmk en la salida de C, a menos que sea seguido en algún momento por una directiva #test (sin un #suite intermedio). No es un error que un #suite no tenga #test's asociados; el #suite (y cualquier #tcase asociado) simplemente no resultará en ninguna acción por parte de checkmk (y por lo tanto sería inútil).

Es un error que una directiva #suite especifique la misma suite (distinguiendo mayúsculas y minúsculas) múltiples veces, a menos que los usos anteriores no hayan sido instanciados por la presencia de al menos una directiva #test asociada.

Si no especifica una directiva #suite antes de la primera directiva #test, checkmk realiza el equivalente de una directiva #suite implícita, con la cadena "Core" como valor para TestSuiteName (esto también implica un objeto de caso de prueba "Core"). Esto se demuestra arriba en EJEMPLO BÁSICO.

CASOS DE PRUEBA

# tcase TestCaseName

Esta directiva especifica el nombre del caso de prueba (TCase objeto en el marco de pruebas de Check) al cual se añadirán todas las funciones de prueba futuras.

El #tcase funciona de una manera muy similar a #suite. El TestCaseName es una cadena de texto, y puede contener caracteres arbitrarios; y un TCase objeto no se definirá realmente a menos que sea seguido por una directiva #test asociada.

Es un error que una directiva #tcase especifique el mismo caso de prueba (distinguiendo mayúsculas y minúsculas) múltiples veces, a menos que los usos anteriores no hayan sido instanciados por la presencia de al menos una directiva #test asociada.

Véase también la directiva #suite, descrita arriba.

CÓDIGO DEL USUARIO EN MAIN()

El C main() es generado automáticamente por checkmk, definiendo los SRunner's, Suite's, yTCase's necesarios por las directivas de definición de pruebas especificadas por el usuario.

Para la mayoría de las situaciones, este main() completamente automatizado es bastante adecuado tal cual. Sin embargo, hay situaciones en las que uno podría desear añadir código personalizado al main(). Por ejemplo, si el usuario desea:

•
cambiar el valor de tiempo de espera de la prueba mediante tcase_set_timeout(),
•
especificar el "modo sin bifurcación" de Check mediante srunner_set_fork_status(),
•
configurar fixtures de prueba para algunos casos de prueba, mediante tcase_add_checked_fixture() otcase_add_unchecked_fixture(),
•
configurar el registro de pruebas para el ejecutor de la suite, mediante srunner_set_log() osrunner_set_xml(), o
•
realizar un cierre personalizado después de que se hayan ejecutado las suites de pruebas.

Para estos propósitos, se han proporcionado las directivas #main-pre y #main-post.

PRÓLOGO DE MAIN()

# main-pre

El texto que sigue a esta directiva se colocará textualmente en el cuerpo de la función main() generada, justo después de las declaraciones de variables locales de checkmk, y antes de que haya tenido lugar la ejecución de cualquier prueba (de hecho, antes incluso de que se establezcan las relaciones entre las pruebas, los casos de prueba y las suites de pruebas, aunque ese hecho no debería suponer mucha diferencia). Dado que checkmk acaba de terminar de hacer sus declaraciones, es permisible, incluso bajo las estrictas directrices ISO C 1990, hacer declaraciones de variables personalizadas aquí.

A diferencia de las directivas descritas anteriormente, #main-pre puede especificarse como máximo una vez. No puede ser precedido por la directiva #main-post, y ninguna directiva #suite, #tcase o #test puede aparecer después de ella.

#main-pre es un buen lugar para ajustar configuraciones o configurar fixtures de prueba. Por supuesto, para hacerlo, necesita saber qué nombres checkmk ha utilizado para instanciar los SRunner's, Suite's, yTCase's.

IDENTIFICADORES DE CHECKMK

Los punteros a Suite's se declaran usando el patrón sX, donde X es un número que comienza en 1, y se incrementa para cada directiva #suite posterior. s1 siempre existe, y contiene la función de prueba declarada por la primera directiva #test. Si esa directiva no fue precedida por un #suite, se le dará el nombre "Core".

Los punteros a TCase's se declaran usando el patrón tcX_Y, donde X corresponde al número usado para el nombre del Suite que contendrá este TCase; y Y es un número que comienza en 1 para cada nuevo Suite, y se incrementa para cada TCase en ese Suite.

Un puntero a SRunner se declara usando el identificador sr; también hay un entero llamado nf que contiene el número de fallos de prueba (después de que las pruebas se hayan ejecutado).

Por razones obvias, el usuario no debe intentar declarar identificadores locales en main(), ni definir macros o funciones de prueba, cuyos nombres puedan entrar en conflicto con los nombres de variables locales utilizados por checkmk. Para resumir, estos nombres son:

sX

tcX_Y

sr

nf.

EPÍLOGO DE MAIN()

# main-post

Aunque no es tan útil, checkmk también proporciona una directiva #main-post para insertar código personalizado al final de main(), después de que las pruebas se hayan ejecutado. Esto podría usarse para limpiar recursos que fueron asignados en el prólogo, o para imprimir información sobre las pruebas fallidas, o para proporcionar un código de estado de salida personalizado.

Tenga en cuenta que, si hace uso de esta directiva, checkmk no proporcionará una sentencia return: tendrá que proporcionar una usted mismo.

La directiva #main-post no puede ser seguida por ninguna otra directiva reconocida por checkmk.

EJEMPLO COMPLETO

Ahora que ha obtenido las descripciones detalladas de las diversas directivas, veamos todo en acción con esta plantilla bastante completa.

--------------------------------------------------
#include "mempool.h"  /* defines MEMPOOLSZ, prototypes for
                         mempool_init() and mempool_free() */
void *mempool;
void mp_setup(void)
{
    mempool = mempool_init(MEMPOOLSZ);
    ck_assert_msg(mempool != NULL, "Couldn't allocate mempool.");
}
void mp_teardown(void)
{
    mempool_free(mempool);
}
/* end of prologue */
#suite Mempool
#tcase MP Init
#test mempool_init_zero_test
    mempool = mempool_init(0);
    ck_assert_msg(mempool == NULL, "Allocated a zero-sized mempool!");
    ck_assert_msg(mempool_error(), "Didn't get an error for zero alloc.");
/* "MP Util" TCase uses checked fixture. */
#tcase MP Util
#test mempool_copy_test
    void *cp = mempool_copy(mempool);
    ck_assert_msg(cp != NULL, "Couldn't perform mempool copy.");
    ck_assert_msg(cp != mempool, "Copy returned original pointer!");
#test mempool_size_test
    ck_assert(mempool_getsize(mempool) == MEMPOOLSZ);
#main-pre
    tcase_add_checked_fixture(tc1_2, mp_setup, mp_teardown);
    srunner_set_log(sr, "mplog.txt");
#main-post
    if (nf != 0) {
      printf("Hey, something's wrong! %d whole tests failed!\n", nf);
    }
    return 0; /* Harness checks for output, always return success
                 regardless. */
--------------------------------------------------

Al introducir esto en checkmk, obtendremos una salida aproximadamente como la siguiente:

--------------------------------------------------
/*
 * DO NOT EDIT THIS FILE. Generated by checkmk.
 * Edit the original source file "comprehensive.ts" instead.
 */
#include <check.h>
#include "mempool.h"
void *mempool;
void mp_setup(void)
{
...
}
void mp_teardown(void)
{
...
}
/* end of prologue */
START_TEST(mempool_init_zero_test)
{
...
}
END_TEST
START_TEST(mempool_copy_test)
{
...
}
END_TEST
START_TEST(mempool_size_test)
{
...
}
END_TEST
int main(void)
{
    Suite *s1 = suite_create("Mempool");
    TCase *tc1_1 = tcase_create("MP Init");
    TCase *tc1_2 = tcase_create("MP Util");
    SRunner *sr = srunner_create(s1);
    int nf;
    /* User-specified pre-run code */
    tcase_add_checked_fixture(tc1_2, mp_setup, mp_teardown);
    srunner_set_log(sr, "mplog.txt");
    suite_add_tcase(s1, tc1_1);
    tcase_add_test(tc1_1, mempool_init_zero_test);
    suite_add_tcase(s1, tc1_2);
    tcase_add_test(tc1_2, mempool_copy_test);
    tcase_add_test(tc1_2, mempool_size_test);
    srunner_run_all(sr, CK_ENV);
    nf = srunner_ntests_failed(sr);
    srunner_free(sr);
    /* User-specified post-run code */
    if (nf != 0) {
      printf("Hey, something's wrong! %d whole tests failed!\n", nf);
    }
    return 0; /* Harness checks for output, always return success
                 regardless. */
}

    checkmk(1)

    checkmk - A tool for checking host and service states from Checkmk

    SYNOPIS

    checkmk
    [options] <host> [<host> ...]

    DESCRIPTION

    The checkmk utility is used to query the status of hosts and services from a Checkmk (formerly Check_MK) monitoring system. It retrieves the latest check results and presents them in a human-readable format.

    OPTIONS

    -h, --help
    Show help message and exit.
    -V, --version
    Show program's version number and exit.
    -v, --verbose
    Increase output verbosity.
    -u, --url URL
    The URL of the Checkmk XML API. For example: http://monitoring.example.com/monitoring/checkmk/webapi.py. This option is mandatory if the CHECKMK_URL environment variable is not set.
    -U, --username USERNAME
    The username for authentication with the Checkmk API. This option is mandatory if the CHECKMK_USERNAME environment variable is not set.
    -P, --password PASSWORD
    The password for authentication with the Checkmk API. This option is mandatory if the CHECKMK_PASSWORD environment variable is not set.
    -s, --services
    Also retrieve and display information about the services running on the specified hosts.
    -S, --service-name SERVICE_NAME
    Only display information for the specified service(s) on a host. This option can be used multiple times to specify multiple services. If this option is used, -s is implied.
    -t, --timeout TIMEOUT
    Set the timeout in seconds for the API request. Defaults to 10 seconds.
    -e, --encoding ENCODING
    Specify the encoding of the output. Defaults to UTF-8.
    -F, --filter FILTER
    Apply a filter to the results. The filter syntax depends on the Checkmk API capabilities.
    -j, --json
    Output the results in JSON format.

    ENVIRONMENT VARIABLES

    CHECKMK_URL
    The URL of the Checkmk XML API.
    CHECKMK_USERNAME
    The username for authentication.
    CHECKMK_PASSWORD
    The password for authentication.

    EXAMPLES

    checkmk -u http://localhost/cmk/webapi.py -U apiuser -P secret server1 server2
    Get the status of hosts server1 and server2 from the Checkmk instance at http://localhost/cmk/webapi.py using the provided username and password.
    checkmk -s -S http_requests server3
    Get the status of host server3 and specifically the http_requests service on that host. Assumes URL, username, and password are set via environment variables.
    CHECKMK_URL=http://cmk.example.com/checkmk/webapi.py CHECKMK_USERNAME=readonly checkmk --password=noprint -s -j webserver
    Get the status of host webserver and its services in JSON format. The password is not printed to the console.

    MAIN()

    The MAIN() function is the entry point of the checkmk script. It handles command-line argument parsing, sets up the necessary configuration (like URL, username, password), constructs the API request, sends it to the Checkmk server, and processes the received data for output. It includes error handling for network issues, authentication failures, and invalid responses.

    COMPREHENSIVE EXAMPLE

    This section would typically contain a more detailed and complex example demonstrating various options and scenarios, such as filtering, handling multiple hosts and services, and different output formats.

    This manual page was written by the Arch Linux packager for the checkmk utility. The utility itself is part of the Checkmk monitoring system.
