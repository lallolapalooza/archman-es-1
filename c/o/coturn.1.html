GENERAL

El proyecto TURN Server contiene el código fuente de un servidor TURN y una biblioteca de mensajería para clientes TURN. Además, se proporcionan algunos programas adicionales, solo con fines de

prueba.

Nota sobre las opciones: turnserver tiene nombres de opciones largos y cortos, para la mayoría de las opciones. Algunas opciones solo tienen forma larga, otras solo forma corta. Su sintaxis es algo diferente si se requiere un

La forma corta debe usarse así (por ejemplo)

  $ turnserver -L 12.34.56.78
El equivalente de forma larga debe usar el carácter "=": 
  $ turnserver --listening-ip=12.34.56.78
Si es una opción de bandera (no requiere argumento), entonces su uso es el mismo, por ejemplo: 
 $ turnserver -a
es equivalente a:

API REST de

TURN

En WebRTC, el navegador obtiene la información de conexión TURN del servidor web. Esta información es información segura, porque contiene las credenciales TURN necesarias. Dado que estas credenciales se transmiten a través de redes públicas, tenemos una posible vulnerabilidad de

seguridad.

Si tenemos que transmitir información valiosa a través de la red pública, entonces esta información debe tener una vida útil limitada. Así, la persona que obtenga esta información sin autorización solo podrá causar un daño

limitado.

Así es como surgió la idea de la API REST de TURN: credenciales TURN con tiempo limitado. Este mecanismo de seguridad se basa en el mecanismo de credenciales de largo plazo. La idea principal de la API REST es que el servidor web proporciona las credenciales al cliente, pero esas credenciales solo pueden ser utilizadas por un tiempo limitado por una aplicación que necesita crear una conexión con el servidor

TURN.

El mecanismo "clásico" de credenciales de largo plazo (LTCM) se describe

aquí:

http://tools.ietf.org/html/rfc5389#section-10.

2

http://tools.ietf.org/html/rfc5389#section-15.

4

Para la autenticación, cada usuario debe conocer dos cosas: el nombre de usuario y la contraseña. Opcionalmente, el usuario debe proporcionar el valor ORIGIN, para que el servidor pueda determinar el realm a utilizar para el usuario. El nonce y los valores de realm son proporcionados por el servidor TURN. Pero el LTCM no dice nada sobre la naturaleza y la persistencia del nombre de usuario y de la contraseña; y esto es lo que utiliza la API

REST.

En la API REST de TURN, no hay contraseñas persistentes para los usuarios. Un usuario solo tiene el nombre de usuario. La contraseña es siempre temporal, y es generada por el servidor web bajo demanda, cuando el usuario accede a la página WebRTC. De hecho, solo se proporciona al usuario un nombre de usuario de sesión temporal de un solo

uso.

El usuario temporal se genera

como:

usuario-temporal="timestamp" + ":" +

"usuario"

donde usuario es el nombre de usuario persistente, y el formato del timestamp es simplemente segundos desde 1970, el mismo valor que time(NULL)

devuelve.

La contraseña temporal se obtiene como una función HMAC-SHA1 sobre el usuario temporal, con el secreto compartido como clave HMAC, y luego el resultado se

codifica:

contraseña-temporal = base64_encode(hmac-sha1(secreto-compartido, usuario-temporal)

)

Tanto el servidor TURN como el servidor web conocen el mismo secreto compartido. Cómo se distribuye el secreto compartido entre las entidades involucradas se deja a los detalles de la implementación de WebRTC, esto está fuera del alcance de la API REST de

TURN.

Así, se utiliza un timestamp para el cálculo de la contraseña temporal, y este timestamp se puede recuperar del usuario temporal. Esta información es valiosa, pero solo temporal, mientras el timestamp no haya expirado. Sin el conocimiento del secreto compartido, no se puede generar una nueva contraseña

temporal.

Todo esto está formalmente descrito en el documento de API REST de TURN de Justin Uberti, que se puede obtener siguiendo el enlace "TURN REST API" en la página del proyecto del servidor TURN https://github.com/coturn/coturn/

.

Una vez que la aplicación cliente (navegador) obtiene el usuario y la contraseña temporales, el resto es simplemente el mecanismo "clásico" de credenciales de largo plazo. Para los desarrolladores, lo describiremos paso a paso a

continuación:
  • un nuevo cliente TURN envía un comando de solicitud al servidor TURN. Opcionalmente, añade el campo ORIGIN a la
    • solicitud.
  • el servidor TURN ve que se trata de un nuevo cliente y que el mensaje no está
    • autenticado.
  • el servidor TURN genera una cadena de nonce aleatoria y devuelve el error 401 al cliente, incluyendo el nonce y el realm. Si el campo ORIGIN estaba presente en la solicitud del cliente, puede afectar al valor de realm que el servidor elige para el
    • cliente.
  • el cliente ve el error 401 y extrae dos valores de la respuesta de error: el nonce y el
    • realm.
  • el cliente usa el nombre de u
    • suario, el realm y la contra
seña para producir una clave: 
         clave = MD5(usuario ":" realm ":" SASLprep(contraseña))
(SASLprep se describe aquí: http://tools.ietf.org/html/rfc4013)
  • el cliente forma una nueva solicitud, añade el nombre de usuario, el realm y el nonce a la solicitud. Luego, el cliente calcula y añade el campo de integridad a la solicitud. Esta es la parte más complicada del proceso, y se describe en el final de la sección 15.4: http://tools.ietf.org/html/rfc5389#section-15.
    • 4
  • el cliente, opcionalmente, añade el campo de huella digital (fingerprint). Este también puede ser un procedimiento complicado, descrito en la sección 15.5 del mismo documento. WebRTC normalmente usa mensajes TURN con huella
    • digital.
  • el servidor TURN recibe la solicitud y lee el nombre de
    • usuario.
  • luego el servidor TURN comprueba que el nonce y el realm en la solicitud son los
    • válidos.
  • luego el servidor TURN calcula la
    • clave.
  • luego el servidor TURN calcula el campo de
    • integridad.
  • luego el servidor TURN compara el campo de int
    • egridad calculado con el recibido, deben
ser iguales. Si los campos de integridad difie
ren, entonces la solicitud es rechazada.

En comunicaciones posteriores, el cliente puede seguir exactamente la misma secuencia, pero para optimizar, normalmente el cliente, teniendo ya información sobre el realm y el nonce, precalcula la cadena de integridad para cada solicitud, de modo que la respuesta de error 401 se vuelve innecesaria. El servidor TURN puede usar la opción--stale-nonce para mayor seguridad: con el tiempo, el nonce expira y el cliente obtendrá una respuesta de error 438 con el nuevo nonce, y el cliente tendrá que empezar a usar el nuevo

nonce.

En comunicaciones posteriores, el servidor y el cliente asumirán siempre la misma contraseña, la contraseña original se convierte en un parámetro de sesión y nunca expira. Así que la contraseña no cambia mientras la sesión es válida y no ha expirado. Por lo tanto, si la sesión se mantiene correctamente, puede durar para siempre, incluso si la contraseña del usuario ya ha sido cambiada (en la base de datos). La sesión simplemente usa la contraseña antigua. Una vez que la sesión se desconecta, el cliente tendrá que usar la nueva contraseña para reconectarse (si la contraseña ha sido cambiada)

.

Se proporciona un ejemplo en el script examples/scripts/restapi/shared_secret_maintainer.pl, donde se genera un nuevo secreto compartido cada hora por la caja del servidor TURN y luego se suministra de forma remota al servidor

web.

Una cosa muy importante es que el nonce debe se

r totalmente aleatorio y debe ser diferente
para diferentes clientes y diferentes sesiones.

Para la base de datos de usuarios, el turnserver tiene las siguientes opciones

Los usuarios se pueden configurar en la línea de comandos, con múltiples -u o --user opciones. Obviamente, solo se pueden configurar de esa manera unos pocos usuarios, y sus credenciales son fijas durante la vida del proceso

2

Esta es la opción si necesitas la mejor escalabilidad. El esquema de la base de datos se puede encontrar en el archivo schema.sql. Para credenciales de largo plazo, tienes que configurar las "claves" para los usuarios; las "claves" son generadas por la utilidad turnadmin. ejemplo.
4
)
Lo mismo es cierto para la base de datos MySQL. El mismo archivo de esquema es aplicable. Las mismas consideraciones son

5
)

También, en Redis puedes almacenar tanto "claves" como contraseñas abiertas (para credenciales de largo plazo), la opción de "contraseña abierta" es menos segura pero más conveniente para entornos de baja seguridad. Consulta el archivo turndb/testredisdbsetup.sh como
ejemplo.
6
)
Si se usa una base de datos, entonces los usuarios se pueden dividir en múltiples realms independientes. Cada realm se puede administrar por separado, y cada realm puede tener su propio conjunto de usuarios y su propio rendimiento opciones (max-bps, user-quota, total-quota)
.
7
)
Si usas MongoDB, la base de datos se configurará automáticamente para
ti.
8
)
Por supuesto, el turnserver se puede usar en modo no seguro, cuando se permite a los usuarios establecer se
siones de forma anónima. Pero en la mayoría de

Para la base de datos de estado y estadísticas, hay dos

)
