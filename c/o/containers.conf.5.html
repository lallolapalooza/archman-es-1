containers.conf(5) configuración containers.conf(5)

NOMBRE

containers.conf - El archivo de configuración del motor de contenedores especifica opciones de configuración predeterminadas y banderas de línea de comandos para motores de contenedores.

DESCRIPCIÓN

Motores de contenedores como Podman y Buildah leen el archivo containers.conf, si existe, y modifican los valores predeterminados para ejecutar contenedores en el host. containers.conf usa un formato TOML que puede ser fácilmente modificado y versionado.

Los motores de contenedores leen los archivos /usr/share/containers/containers.conf, /etc/containers/containers.confy /etc/containers/containers.conf.d/*.conf para la configuración global que afecta a todos los usuarios. Para la configuración global que solo afecta a usuarios sin privilegios (rootless), use /etc/containers/containers.rootless.conf, /etc/containers/containers.rootless.d/*.conf y /etc/containers/containers.rootless.d/\$UID/*.conf. El UID es el uid del usuario bajo el que se ejecuta podman, por lo que se puede usar para especificar una configuración para un solo usuario sin tener que colocar la configuración en el directorio de inicio del usuario. Para la configuración específica del usuario, lee los archivos \$XDG_CONFIG_HOME/containers/containers.conf y \$XDG_CONFIG_HOME/containers/containers.conf.d/*.conf . Cuando $XDG_CONFIG_HOME no está definido, recurre a usar $HOME/.config en su lugar.

Los campos especificados en containers.conf anulan las opciones predeterminadas, así como las opciones en los archivos containers.conf leídos previamente.

Los archivos de configuración en los directorios .d se añaden en orden alfanumérico y deben terminar en .conf.

No todas las opciones están soportadas en todos los motores de contenedores.

Tenga en cuenta que los motores de contenedores también usan otros archivos de configuración para configurar el entorno.

  • storage.conf para la configuración del almacenamiento de contenedores e imágenes.
  • registries.conf para la definición de registros de contenedores donde buscar al descargar imágenes de contenedores.
  • policy.conf para controlar qué imágenes se pueden descargar al sistema.

Nota: Si Podman se está ejecutando en una máquina virtual usando podman machine (esto incluye hosts Mac y Windows), asegúrese de que los archivos de configuración se editen en la máquina virtual usando podman machine ssh.

VARIABLES DE ENTORNO

Si la variable de entorno CONTAINERS_CONF está definida, todos los archivos de configuración del sistema y del usuario se ignoran y solo se cargará el archivo de configuración especificado.

Si la variable de entorno de ruta CONTAINERS_CONF_OVERRIDE está definida, el archivo de configuración se cargará al final incluso cuando CONTAINERS_CONF esté definida.

Los valores de ambas variables de entorno pueden ser rutas absolutas o relativas, por ejemplo, CONTAINERS_CONF=/tmp/my_containers.conf.

MÓDULOS

Un módulo es un archivo containers.conf ubicado directamente en uno de los siguientes tres directorios o en un subdirectorio de ellos:
- \$XDG_CONFIG_HOME/containers/containers.conf.modules o \$HOME/.config/containers/containers.conf.modules si $XDG_CONFIG_HOME no está definida.
- /etc/containers/containers.conf.modules
- /usr/share/containers/containers.conf.modules

Los archivos en esas ubicaciones no se cargan de forma predeterminada, sino solo bajo demanda. Se cargan después de todos los archivos de configuración del sistema y del usuario, pero antes de CONTAINERS_CONF_OVERRIDE , lo que permite anular las configuraciones del sistema y del usuario.

Los módulos son soportados actualmente por podman(1). La bandera podman --module permite cargar un módulo y se puede especificar varias veces. Si el valor especificado es una ruta absoluta, el archivo de configuración se cargará directamente. Las rutas relativas se resuelven en relación con los tres directorios de módulos mencionados anteriormente y en el orden especificado, de modo que los módulos en $XDG_CONFIG_HOME/$HOME permitan anular a aquellos en /etc y /usr/share.

AÑADIENDO A ARREGLOS DE CADENAS

El comportamiento predeterminado durante la secuencia de carga de varios archivos containers.conf es anular los datos anteriores. Para cambiar el comportamiento de anular a añadir, puede establecer el atributo append de la siguiente manera: array=["item-1", "item=2", ..., {append=true}]. Establecer el atributo append indica añadir a este arreglo de cadenas específico para el paso de carga actual y también para los posteriores. Para volver a anular, establezca {append=false}.

Considere el siguiente ejemplo:

modules1.conf: env=["1=true"]
modules2.conf: env=["2=true"]
modules3.conf: env=["3=true", {append=true}]
modules4.conf: env=["4=true"]

Después de cargar los archivos en el orden dado, el contenido final es env=["2=true", "3=true", "4=true"]. Si modules4.conf estableciera {append=false}, el contenido final sería env=["4=true"].

FORMATO

Se usa el formato TOML ⟨https://github.com/toml-lang/toml⟩ como la codificación del archivo de configuración. Cada opción está anidada bajo su tabla. No se usan opciones sin tabla. El formato de TOML se puede simplificar como:

[table1]
option = value
[table2]
option = value
[table3]
option = value
[table3.subtable1]
option = value

TABLA NETWORK

La tabla network contiene ajustes relativos a la gestión de los plugins CNI.

network_backend=""

El backend de red determina qué controlador de red se utilizará para configurar y desmontar las redes de los contenedores. Los valores válidos son "cni" y "netavark". El valor predeterminado está vacío, lo que significa que se elegirá automáticamente CNI o netavark. Si ya hay contenedores/imagenes o redes CNI preestablecidas, se elegirá CNI.

Antes de cambiar este valor, todos los contenedores deben estar detenidos; de lo contrario, es probable que las reglas de iptables y las interfaces de red se filtren en el host. Un reinicio solucionará esto.

cni_plugin_dirs=[]

Lista de rutas a los directorios donde se encuentran los binarios de los plugins CNI.

La lista predeterminada es:

cni_plugin_dirs = [
  "/usr/local/libexec/cni",
  "/usr/libexec/cni",
  "/usr/local/lib/cni",
  "/usr/lib/cni",
  "/opt/cni/bin",
]

netavark_plugin_dirs=[]

Lista de directorios en los que se buscarán los plugins de netavark.

La lista predeterminada es:

netavark_plugin_dirs = [
  "/usr/local/libexec/netavark",
  "/usr/libexec/netavark",
  "/usr/local/lib/netavark",
  "/usr/lib/netavark",
]

default_network="podman"

El nombre de la red predeterminada tal como aparece en podman network ls. Esta opción solo afecta a la asignación de red cuando se selecciona el modo de red puente, es decir, --network bridge. Es la predeterminada para los contenedores con privilegios de root, pero no para los que no lo tienen. Para cambiar el modo de red predeterminado, utilice la opción netns en la tabla [containers] .

Nota: No se debe cambiar mientras haya contenedores utilizando esta red.

default_subnet="10.88.0.0/16"

La subred que se utilizará para la red predeterminada (nombrada anteriormente en default_network).

Nota: No se debe cambiar si hay contenedores en ejecución actualmente en la red predeterminada.

DefaultSubnetPools es una lista de subredes y tamaños que se utilizan para asignar subredes automáticamente para podman network create. Iterará a través de la lista y elegirá la primera subred libre con el tamaño dado. Esto solo se utiliza para subredes ipv4, las subredes ipv6 se asignan siempre aleatoriamente.

La lista predeterminada es (10.89.0.0-10.255.255.0/24):

  {"base" = "10.89.0.0/16", "size" = 24},
  {"base" = "10.90.0.0/15", "size" = 24},
  {"base" = "10.92.0.0/14", "size" = 24},
  {"base" = "10.96.0.0/11", "size" = 24},
  {"base" = "10.128.0.0/9", "size" = 24},
]

Configura qué programa de red sin privilegios de root se utilizará de forma predeterminada. Las opciones válidas son slirp4netns y pasta (predeterminado).

Ruta al directorio donde se encuentran los archivos de configuración de red. Para el backend CNI, el valor predeterminado es /etc/cni/net.d como root y $HOME/.config/cni/net.d sin privilegios de root. Para el backend netavark, se utiliza "/etc/containers/networks" como root y "$graphroot/networks" sin privilegios de root.

El controlador de firewall que utilizará netavark. El valor predeterminado está vacío, lo que significa que netavark elegirá uno en consecuencia. add_compression=[]

Lista de algoritmos de compresión. Si se establece, se asegura de que la variante de compresión solicitada para cada plataforma se añada a la lista de manifiestos, manteniendo la instancia original intacta en la misma lista de manifiestos en cada manifest push. Los valores admitidos son (gzip, zstd y zstd:chunked). zstd:chunked es incompatible con el cifrado de imágenes y se tratará como zstd con una advertencia en ese caso.

Nota: Esto es diferente de compression_format , que permite a los usuarios seleccionar un formato de compresión predeterminado para push y manifest push, mientras que add_compression se limita a manifest push y permite a los usuarios añadir nuevas instancias a la lista de manifiestos con los algoritmos de compresión especificados en add_compression para cada plataforma.

Determina si el motor reservará puertos en el host cuando se reenvíen a los contenedores. Sin embargo, esto puede causar un uso significativo de memoria si un contenedor tiene muchos puertos reenviados a él. Desactivar esto puede ahorrar memoria.

Los campos especificados en un archivo containers.conf sobreescriben las opciones predeterminadas, así como las opciones en archivos containers.conf cargados previamente. storage.

El archivo /etc/containers/storage.conf es el archivo de configuración de almacenamiento predeterminado. Los usuarios sin raíz pueden sobreescribir campos en la configuración de almacenamiento creando $HOME/.config/containers/storage.conf . Si la variable de entorno de ruta CONTAINERS_STORAGE_CONF está establecida, esta ruta se usa

para el archivo storage.conf en lugar de la predeter
minada. Esto se usa principalmente para pruebas.
