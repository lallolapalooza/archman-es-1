Desde Linux 2.6.19, Linux soporta

una

Si el primer carácter de este archivo es un símbolo de canalización ( |), entonces el resto de la línease interpreta como la línea de comandos para un programa de espacio de usuario (o script) que va a ser ejecutado. Desde Linux 5.3.0, la

plantilla

de canalización se divide por espacios en una lista de argumentos antes de que se expandan los parámetros de la plantilla. En kernels anteriores, los parámetros de la plantilla se expanden primero y la cadena resultante se divide por espacios en una lista de argumentos. Esto significa que en kernels anteriores los nombres de ejecutable añadidos por los %e y %E parámetros de plantilla podían quedardividido en múltiples argumentos. Por lo tanto, el manejador de volcados de memoria (core dump) necesita colocar los nombres de los ejecutables como el último argumento y asegurarse de unir todas las partes del nombre del ejecutable usando espacios. Los nombres de ejecutables con múltiples espacios no se representan correctamente en versiones anteriores del kernel, lo que significa que el manejador de volcados de memoria necesita usar mecanismos para encontrar el nombre del

ejecutable.

En lugar de escribirse en un archivo, el volcado de memoria se proporciona como entrada estándar al programa. Tenga en cuenta los siguientes

puntos:
•
El programa debe especificarse utilizando una ruta de acceso absoluta (o una ruta de acceso relativa al directorio raíz, /), y debe seguir inmediatamente al carácter
'|'.
•
Los argumentos de la línea de comandos pueden incluir cualquiera de los especificadores % listados arriba. Por ejemplo, para pasar el PID del proceso que se está volcando, especifique %p en un
argumento.
•
El proceso creado para ejecutar el programa se ejecuta como usuario y grupo roo
t.
•
Ejecutarse como root no otorga ninguna excepción de evasión de seguridad. Es decir, los LSM (p. ej., SELinux) siguen activos y pueden impedir que el manejador acceda a detalles sobre el proceso que ha fallado a través de /proc/pi
d.
•
La ruta de acceso del programa se interpreta con respecto al espacio de nombres de montaje inicial, ya que siempre se ejecuta allí. No se ve afectado por la configuración (p. ej., directorio raíz, espacio de nombres de montaje, directorio de trabajo actual) del proceso que ha
fallado.
•
El proceso se ejecuta en los espacios de nombres iniciales (PID, montaje, usuario, etc.) y no en los espacios de nombres del proceso que ha fallado. Se pueden utilizar especificadores como %P para encontrar el directorio /proc/pid correcto y sondear/entrar en los espacios de nombres del proceso que ha fallado si es
necesario.
•
El proceso comienza con su directorio de trabajo actual como directorio raíz. Si se desea, es posible cambiar al directorio de trabajo del proceso que está volcando utilizando el valor proporcionado por el especificador %P para cambiar a la ubicación del proceso que está volcando a través de /proc/pid/cw
d.
•
Se pueden proporcionar argumentos de la línea de comandos al programa (desde Linux 2.6.24), delimitados por espacios en blanco (hasta una longitud total de línea de 128 bytes)
.
•

Al recopilar volcados de memoria a través de una tubería hacia un programa en espacio de usuario, puede ser útil para el programa que recopila obtener datos sobre el proceso que ha fallado desde el directorio /proc/pid de ese proceso. Para hacer esto de forma segura, el kernel debe esperar a que el programa que recopila el volcado de memoria salga, para no eliminar los archivos /proc/pid del proceso que ha fallado prematuramente. Esto a su vez crea la posibilidad de que un programa de recopilación que se comporte mal bloquee la recolección de un proceso que ha fallado simplemente por no salir

nunca.

Desde Linux 2.6.32, el /proc/sys/kernel/core_pipe_limit se puede utilizar para defenderse de esta posibilidad. El valor en este archivo define cuántos procesos que han fallado de forma concurrente pueden canalizarse a programas en espacio de usuario en paralelo. Si se supera este valor, entonces esos procesos que han fallado por encima de este valor se anotan en el registro del kernel y sus volcados de memoria se

omiten.

Un valor de 0 en este archivo es especial. Indica que se pueden capturar un número ilimitado de procesos en paralelo, pero que no se realizará ninguna espera (es decir, no se garantiza que el programa de recopilación tenga acceso a /proc/<PID-que-ha-fallado>). El valor p

redeterminado para
este archivo es 0.

Volcados de memoria y

systemd

En sistemas que utilizan el systemd(1) framework de init, los volcados de memoria pueden colocarse en una ubicación determinada por systemd(1). Para hacer esto, systemd(1) emplea la característica core_pattern que permite canalizar volcados de memoria a un programa. Se puede verificar esto comprobando si los volcados de memoria se canalizan al programa systemd-co

redump(8): 


$ cat /proc/sys/kernel/core_pattern;
|/usr/lib/systemd/systemd-coredump %P %u %g %s %t %c
%e

En este caso, los volcados de memoria se colocarán en la ubicación configurada para systemd-coredump(8), típicamente como archivos comprimidos con lz4(1) en el directorio /var/lib/systemd/coredump/. Se pueden listar los volcados de memoria que han sido registrados por systemd-coredump(8) utilizando coredumpct

l(1): 
$ coredumpctl list | tail -5;
Wed 2017-10-11 22:25:30 CEST  2748 1000 1000 3 present  /usr/bin/sleep
Thu 2017-10-12 06:29:10 CEST  2716 1000 1000 3 present  /usr/bin/sleep
Thu 2017-10-12 06:30:50 CEST  2767 1000 1000 3 present  /usr/bin/sleep
Thu 2017-10-12 06:37:40 CEST  2918 1000 1000 3 present  /usr/bin/cat
Thu 2017-10-12 08:13:07 CEST  2955 1000 1000 3 present
/usr/bin/cat

La información mostrada para cada volcado de memoria incluye la fecha y hora del volcado, el PID, UID y GID del proceso que está volcando, el número de señal que causó el volcado de memoria y la ruta de acceso del ejecutable que estaba siendo ejecutado por el proceso volcado. Varias opciones de coredumpctl(1) permiten extraer un archivo de volcado de memoria especificado desde la ubicación de systemd(1) a un archivo especificado. Por ejemplo, para extraer el volcado de memoria para el PID 2955 mostrado arriba a un archivo llamado core en el directorio actual, se podría

usar: 


$ coredumpctl dump 295
5 -o core;

Para obtener detalles más extensos, véase la página del manual de coredumpct

l(1).

Para (persistentemente) desactivar el mecanismo de systemd(1) que archiva los volcados de memoria, restaurando algo más parecido al comportamiento tradicional de Linux, se puede establecer una anulación para el mecanismo de systemd(1), utilizando algo

como: 


# echo "kernel.core_pattern=core.%p" > \;
               /etc/sysctl.d/50-coredump.conf
# /lib/systemd/systemd-sysctl
;

También es posible cambiar temporalmente (es decir, hasta el próximo reinicio) la configuración de core_pattern utilizando un comando como el siguiente (que hace que los nombres de los archivos de volcado de memoria incluyan el nombre del ejecutable así como el número de la señal que desencadenó el volcado de memoria)

# sysctl -w kernel.

S

El comando gcore de gdb(1) se puede utilizar para obtener un volcado de memoria de un proceso en

En las versiones de Linux hasta e incluyendo 2.6.27, si un proceso multihilo (o, más precisamente, un proceso que comparte su memoria con otro proceso al ser creado con el indicador CLONE_VM de clone(2)) vuelca su memoria, entonces el ID de proceso siempre se añade al nombre de archivo del volcado de memoria, a menos que el ID de proceso ya estuviera incluido en otra parte del nombre de archivo a través de una especificación %p en /proc/sys/kernel/core_pattern. (Esto es principalmente útil al emplear la impleme

S

El programa siguiente se puede utilizar para demostrar el uso de la sintaxis de tubería en el archivo /proc/sys/kernel/core_pattern. La siguiente sesión de shell demuestra el uso de este programa (compilado para crear un ejecutable llamado core_pattern_pip

fuente 
/* core_pattern_pipe_test.c */
#define _GNU_SOURCE
#include <sys/stat.h>
#include <fcntl.h>
#include <limits.h>
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#define BUF_SIZE 1024
int
main(int argc, char *argv[])
{
    ssize_t nread, tot;
    char buf[BUF_SIZE];
    FILE *fp;
    char cwd[PATH_MAX];
    /* Change our current working directory to that of the
       crashing process.  */
    snprintf(cwd, PATH_MAX, "/proc/%s/cwd", argv[1]);
    chdir(cwd);
    /* Write output to file "core.info" in that directory.  */
    fp = fopen("core.info", "w+");
    if (fp == NULL)
        exit(EXIT_FAILURE);
    /* Display command-line arguments given to core_pattern
       pipe program.  */
    fprintf(fp, "argc=%d\n", argc);
    for (size_t j = 0; j < argc; j++)
        fprintf(fp, "argc[%zu]=<%s>\n", j, argv[j]);
    /* Count bytes in standard input (the core dump).  */
    tot = 0;
    while ((nread = read(STDIN_FILENO, buf, BUF_SIZE)) > 0)
        tot += nread;
    fprintf(fp, "Total bytes in core dump: %zd\n", tot);
    fclose(fp);
    exit(EXIT_SUCCESS)
;
}
