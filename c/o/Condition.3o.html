Variables de condición.

Las variables de condición son útiles cuando varios hilos desean acceder a una estructura de datos compartida que está protegida por un mutex (un candado de exclusión mutua).

Una variable de condición es un canal de comunicación. En el lado del receptor, uno o más hilos pueden indicar que desean esperar a que cierta propiedad se vuelva verdadera. En el lado del emisor, un hilo puede señalar que esta propiedad se ha vuelto verdadera, causando que uno (o más) hilos en espera sean despertados.

Por ejemplo, en la implementación de una estructura de datos de cola, si un hilo que desea extraer un elemento encuentra que la cola está actualmente vacía, entonces este hilo espera a que la cola se vuelva no vacía. Un hilo que inserta un elemento en la cola señala que la cola se ha vuelto no vacía. Una variable de condición se utiliza para este propósito. Este canal de comunicación transmite la información de que la propiedad "la cola está no vacía" es verdadera, o más precisamente, puede ser verdadera. (Explicamos más abajo por qué el receptor de una señal no puede estar seguro de que la propiedad se cumple.)

Para continuar el ejemplo de la cola, asumiendo que la cola tiene una capacidad máxima fija, entonces un hilo que desea insertar un elemento puede encontrar que la cola está llena. Entonces, este hilo debe esperar a que la cola se vuelva no llena, y un hilo que extrae un elemento de la cola señala que la cola se ha vuelto no llena. Otra variable de condición se utiliza para este propósito.

En resumen, una variable de condición c se utiliza para transmitir la información de que cierta propiedad P sobre una estructura de datos compartida D, protegida por un mutex m , puede ser verdadera.

Las variables de condición proporcionan una alternativa eficiente a la espera activa (busy-waiting). Cuando se desea esperar a que la propiedad P sea verdadera, en lugar de escribir un bucle de espera activa:

     Mutex.lock m;
     while not P do
       Mutex.unlock m; Mutex.lock m
     done;
     <actualizar la estructura de datos>;
     Mutex.unlock m
se utiliza Condition.wait en el cuerpo del bucle, de la siguiente manera: 
     Mutex.lock m;
     while not P do
       Condition.wait c m
     done;
     <actualizar la estructura de datos>;
     Mutex.unlock m
El bucle de espera activa es ineficiente porque el hilo en espera consume tiempo de procesamiento y crea contención del mutex m . Llamar a Condition.wait permite que el hilo en espera sea suspendido, de modo que no consume ningún recurso de cómputo mientras espera.

Con una variable de condición c , exactamente un mutex m está asociado. Esta asociación es implícita: el mutex m no se pasa explícitamente como argumento a Condition.create . Corresponde al programador saber, para cada variable de condición c , cuál es el mutex asociado m .

Con un mutex m , varias variables de condición pueden estar asociadas. En el ejemplo de la cola acotada, una variable de condición se utiliza para indicar que la cola está no vacía, y otra variable de condición se utiliza para indicar que la cola no está llena.

Con una variable de condición c , exactamente una propiedad lógica P debe estar asociada. Ejemplos de tales propiedades incluyen "la cola está no vacía" y "la cola no está llena". Corresponde al programador llevar la cuenta, para cada variable de condición, de la propiedad correspondiente P. Se envía una señal en la variable de condición c como una indicación de que la propiedad P es verdadera, o puede ser verdadera. En el extremo receptor, sin embargo, un hilo que es despertado no puede asumir que P es verdadera; después de que una llamada a Condition.wait termina, se debe probar explícitamente si P es verdadera. Hay varias razones por las que es así. Una razón es que, entre el momento en que se envía la señal y el momento en que un hilo en espera recibe la señal y es programado, la propiedad P puede ser falsificada por algún otro hilo que es capaz de adquirir el mutex m y alterar la estructura de datos D. Otra razón es que pueden ocurrir despertares espurios: un hilo en espera puede ser despertado incluso si no se envió ninguna señal.

Aquí hay un ejemplo completo, donde un mutex protege una cola secuencial ilimitada, y donde una variable de condición se utiliza para señalar que la cola está no vacía.

     type 'a safe_queue =
       { queue : 'a Queue.t; mutex : Mutex.t; nonempty : Condition.t }
     let create () =
       { queue = Queue.create(); mutex = Mutex.create();
         nonempty = Condition.create() }
     let add v q =
       Mutex.lock q.mutex;
       let was_empty = Queue.is_empty q.queue in
       Queue.add v q.queue;
       if was_empty then Condition.broadcast q.nonempty;
       Mutex.unlock q.mutex
     let take q =
       Mutex.lock q.mutex;
       while Queue.is_empty q.queue do Condition.wait q.nonempty q.mutex done;
       let v = Queue.take q.queue in (* no puede fallar ya que la cola no está vacía *)
       Mutex.unlock q.mutex;
       v
Debido a que la llamada a Condition.broadcast tiene lugar dentro de la sección crítica, la siguiente propiedad se cumple siempre que el mutex está desbloqueado: si la cola está no vacía, entonces ningún hilo está esperando, o, en otras palabras, si algún hilo está esperando, entonces la cola debe estar vacía. Esta es una propiedad deseable: si un hilo que intenta ejecutar una operación take pudiera permanecer suspendido aunque la cola estuviera no vacía, esa sería una situación problemática, conocida como interbloqueo (deadlock).

type t

El tipo de las variables de condición.

val create : unit -> t

create() crea y devuelve una nueva variable de condición. Esta variable de condición debe estar asociada (en la mente del programador) con cierto mutex m y con cierta propiedad P de la estructura de datos que está protegida por el mutex m .

val wait : t -> Mutex.t -> unit

La llamada wait c m está permitida solo si m es el mutex asociado con la variable de condición c , y solo si m está actualmente bloqueado. Esta llamada desbloquea atómicamente el mutex m y suspende el hilo actual en la variable de condición c . Este hilo puede ser despertado más tarde después de que la variable de condición c haya sido señalizada mediante Condition.signal o Condition.broadcast ; sin embargo, también puede ser despertado sin razón alguna. El mutex m se bloquea de nuevo antes de que wait retorne. No se puede asumir que la propiedad P asociada con la variable de condición c se cumple cuando wait retorna; se debe probar explícitamente si P se cumple después de llamar a wait .

val signal : t -> unit

signal c despierta a uno de los hilos que esperan en la variable de condición c , si hay alguno. Si no hay ninguno, esta llamada no tiene efecto.

Se recomienda llamar a signal c dentro de una sección crítica, es decir, mientras el mutex m asociado con c está bloqueado.

val broadcast : t -> unit

broadcast c despierta a todos los hilos que esperan en la variable de condición c . Si no hay ninguno, esta llamada no tiene efecto.

Se recomienda llamar a broadcast c dentro de una sección crítica, es decir, mientras el mutex m asociado con c está bloqueado.
