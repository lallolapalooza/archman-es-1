DESCRIPCIÓ

N

conntrackd.conf es el archivo de configuración principal para el demonio conntrackd(8). Se carga mediante la llamada a `conntrackd -C conntrackd.

conf'.

El formato de este archivo es simple, usando corchetes para las secciones y pares clave-valor para las directivas de configuración

concretas: 
section1 {
	option1 value1
	option2 value2
}
section2 {
	option3 value3
	subsection1 {
		option4 value4
	}
}

Debe considerar este archivo como sensible a mayúsculas y minúsculas. Las líneas vacías y las líneas que comienzan con el carácter '#' se

ignoran.

Antes de comenzar a desarrollar una nueva configuración, es posible que desee aprender los conceptos detrás de esta tecnología en http://conntrack-tools.netfilter.

org/manual.html.

Esta sección de nivel superior define cómo conntrackd(8) debe manejar la sincronización con otros nodos del

clúster.

Hay 3 modos o protocolos principales de sincronización: NOTRACK, ALARM y FTFW

.

También hay 3 protocolos de transporte: TCP, Multicast y UDP

.

Debe elegir un modo de sincronización y un protocolo de

transporte.

Además, hay algunas opciones generales en esta

sección.

Mode

FTFW

Este modo se basa en un protocolo fiable que realiza el seguimiento de mensajes. Por lo tanto, el protocolo puede recuperarse de la pérdida de mensajes, la reordenación y la

corrupción.

En este modo de sincronización puede configurar ResendQueueSize, CommitTimeout, PurgeTimeout, ACKWindowSize , DisableExternalCache y StartupResync

.
ResendQueueSize
<value>
Tamaño de la cola de reenvío (en objetos). Este es el número máximo de objetos que pueden almacenarse a la espera de ser confirmados mediante un acuse de recibo. Si mantiene este valor bajo, el demonio tendrá menos posibilidades de recuperar cambios de estado bajo la omisión de mensajes. Por otro lado, si mantiene este valor alto, el demonio consumirá más memoria para almacenar objetos muertos.

Ejemplo: ResendQueueSize

131072

objetos.
CommitTimeout
<seconds>
Este parámetro le permite establecer un tiempo de espera fijo inicial para las entradas confirmadas cuando este nodo pasa de copia de seguridad a primario. Este mecanismo proporciona una forma de purgar entradas que no fueron recuperadas adecuadamente después del tiempo de espera fijo especificado. Si establece un valor bajo, las entradas TCP en estado Establecido sin tráfico pueden colgarse. Por ejemplo, una conexión SSH sin KeepAlive habilitado.

Ejemplo: CommitTimeout

180

De forma predeterminada, esta opción no está establecida (el demonio usa un mecanismo de cálculo aproximado del tiempo

de espera)

PurgeTimeout
<seconds>
Si la réplica del firewall pasa de primario a copia de seguridad, el `comando conntrackd -t ' se invoca en el script. Este comando programa un vaciado de la tabla en N segundos.

Esto es útil para purgar la tabla de seguimiento de conexiones de entradas zombi y evitar conflictos con entradas antiguas si se producen varios traspasos

consecutivos.

El valor predeterminado es

60

ACKWindowSize
<value>
Establece el tamaño de la ventana de acuse de recibo. Si disminuye este valor, el número de acuses de recibo aumenta. Más acuses de recibo significan más sobrecarga ya que conntrackd(8) tiene que manejar más mensajes de control. Por el contrario, si aumenta este valor, la cola de reenvío se llena más. Esto resulta en más sobrecarga en la liberación de la cola.

Ejemplo: ACKWindowSize

<yes|no>

Esta sección indica a conntrackd(8) que use multicast como mecanismo de transporte entre los nodos del clúster de

firewall.

Tenga en cuenta que puede especificar más de un enlace dedicado. Así, si un enlace dedicado falla, el demonio puede hacer failover a otro. Nótese que añadir más de un enlace dedicado no significa que las actualizaciones de estado se enviarán a todos ellos. Solo hay un enlace dedicado activo en un momento

redundantes.

Filtrado de eventos. Esta cláusula le permite filtrar cierto

tráfico.

Actualmente hay tres conjuntos de filtros (filter-sets): Protocol, Address y State. El filtro se adjunta a una acción que puede ser: Accept o Ignore. Así, puede definir la política de filtrado de eventos de los conjuntos de filtros en lógica positiva o negativa, dependiendo de sus

necesidades.

Puede seleccionar si conntrackd(8) filtra los mensajes de eventos desde el espacio de usuario (user-space) o el espacio del kernel (kernel-space). El filtrado de eventos en el espacio del kernel ahorra algunos ciclos de CPU al evitar la copia del mensaje de evento del espacio del kernel al espacio de usuario. El filtrado en el espacio del kernel es preferible, sin embargo, se requiere un Linux kernel >= 2.6.29 para filtrar desde el espacio del

kernel.

La sintaxis para esta sección es: Filter From <from> { }
