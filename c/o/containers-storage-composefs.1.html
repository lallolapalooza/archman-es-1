NOMBRE

containers-storage-composefs - Información sobre composefs y containers/storage

DESCRIPCIÓN

Para habilitar composefs en un nivel base se requiere la siguiente configuración en containers-storage.conf:

[storage.options.overlay]
use_composefs = "true"

Este valor debe ser un "string booleano", no puede ser un booleano nativo de TOML.

Sin embargo, en este momento, composefs requiere imágenes zstd:chunked, por lo que primero debes asegurarte de que zstd:chunked esté habilitado. Para más información, consulta zstd:chunked ⟨containers-storage-zstd-chunked.md⟩.

Adicionalmente, no hay muchas imágenes en formato zstd:chunked. Para reducir esta brecha, se puede especificar convert_images = "true", que realiza una conversión dinámica; esto añade latencia a las descargas de imágenes.

Juntando estas cosas, lo siguiente es necesario (además de la configuración anterior).

[storage.options.pull_options]
convert_images = "true"

Este valor debe ser un "string booleano", no puede ser un booleano nativo de TOML.

IMPLEMENTACIÓN

Como se implica en la configuración use_composefs = "true", actualmente composefs se implementa como una "opción" para el controlador overlay. Algunos formatos de archivo permanecen sin cambios y se heredan del controlador overlay, incluso cuando se usa composefs. Las principales diferencias se enumeran a continuación.

El directorio diff/ para cada capa ya no es un simple desempaquetado del tarball, sino que se convierte en un "directorio de hashes de objetos", donde cada nombre de archivo es el sha256 de su contenido. Este directorio diff/ es el almacén de respaldo para un composefs-data/composefs.blob creado para cada capa, que es el "superbloque" de composefs que contiene todo el contenido que no es un archivo regular (es decir, metadatos) del tarball.

Al igual que con zstd:chunked, las capas existentes se escanean en busca de objetos coincidentes y se reutilizan (mediante hardlink o reflink según la configuración) si se encuentran objetos con un "sha256 completo" coincidente.

Actualmente no hay soporte para integridad forzada con composefs; se intenta habilitar fsverity para los archivos de respaldo y el archivo composefs, pero no es un error si no es compatible. Todavía no existe un mecanismo definido para verificar el digest de fsverity del bloque composefs antes de montarlo; algunos trabajos al respecto están en curso.

Para montar una capa (o una imagen completa, con todas sus dependencias), se monta cualquier capa que tenga un blob composefs y se incluye en la pila de overlayfs "final". Esto es opcional; cualquier capa que no esté en formato "composefs" sino en el formato "overlay predeterminado" (desempaquetado) se reutilizará tal como está.

NOTAS AL PIE

El proyecto Containers Storage está comprometido con la inclusividad, un valor fundamental del código abierto. La terminología de propagación de montaje master y slave se utiliza en este repositorio. Este lenguaje es problemático y divisivo, y debería cambiarse. Sin embargo, estos términos se utilizan actualmente en el kernel de Linux y deben usarse tal como están en este momento. Cuando los mantenedores del kernel rectifiquen este uso, Containers Storage hará lo mismo inmediatamente.
