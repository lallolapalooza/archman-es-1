Vue d'ensemble de haut niveau La signature fournit une affirmation
authentifiée de bout en bout qu'une image de conteneur a été

approuvée par une

partie

spécifique (par exemple, le créateur de l'image en tant que son travail, un système de construction automatisée comme résultat d'une construction automatisée, le service informatique d'une entreprise approuvant l'image pour la production) sous une identité spécifiée (par exemple, une image de base d'OS / une application spécifique, avec une version spécifique). Une signature de conteneur se compose d'une signature

cryptographique

qui identifie et authentifie qui a signé l'image, et porte en tant que charge utile signée un document JSON. Le document JSON identifie l'image qui est signée, revendique une identité spécifique de l'image et, le cas échéant, contient d'autres informations sur l'image. Les signatures ne modifient pas l'image du conteneur (les couches, la configuration, le

manifeste,

…) ; par exemple, leur présence ne change pas l'empreinte du manifeste utilisée pour identifier l'image dans les serveurs docker/distribution ; plutôt, les

signatures sont associées à une image immuable. Une image peut avoir un nombre quelconque de signatures, donc les systèmes de distribution de signatures DE
VRAIENT prendre en charge l'association de plus d'une signature à une image. La signature cryptographique En tant que distribuée, la signature de conteneur est

un blob qui contient une

signature

cryptographique dans un format standard de l'industrie, portant une charge utile JSON signée (c'est-à-dire que le blob contient à la fois le document JSON et une signature du document JSON ; ce n'est pas une « signature détachée » avec des blobs indépendants contenant le document JSON et une signature cryptographique). Actuellement, le seul format de signature cryptographique défini est

une

signature OpenPGP (RFC 4880), mais d'autres peuvent être ajoutés à l'avenir. (Le blob ne contient pas de métadonnées identifiant le format de signature cryptographique. On s'attend à ce que la plupart des formats soient suffisamment auto-descriptifs pour que cela ne soit pas nécessaire et la clé publique attendue configurée fournit une autre indication du format de signature cryptographique attendu. De telles métadonnées peuvent être ajoutées à l'avenir pour les formats de signature cryptographique nouvellement ajoutés, si nécessaire.)
