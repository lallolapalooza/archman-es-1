Kit de Desarrollo de Software

Hay cuatro niveles de participación con el módulo PDF::Builder. Dependiendo de lo que quieras hacer, se recomiendan diferentes tipos de instalaciones.

1.
Simplemente instala PDF::Builder como una dependencia para ejecutar otro paquete. Solo tienes que instalar el paquete CPAN de PDF::Builder, y se cargarán los archivos .pm en tu biblioteca Perl. Si el otro paquete requiere PDF::Builder, su instalador puede automatizar la instalación de PDF::Builder.
2.
Quieres escribir un programa Perl que use funciones de PDF::Builder. Además de instalar PDF::Builder desde CPAN, necesitas documentación. Obtén una copia del producto desde GitHub (https://github.com/PhilterPaper/Perl-PDF-Builder) o como un archivo tar.gz de CPAN. Esto incluye una utilidad para construir (desde POD) un conjunto de documentos HTML, así como ejemplos (directorio examples) y programas de ejemplo contribuidos (directorio contrib/).
3.
Quieres modificar los archivos de PDF::Builder. Además de los distribuidores CPAN y GitHub, puedes mantener un repositorio local de Git para registrar tus cambios. Dependiendo de si tu copia de PDF::Builder se usa en producción, puedes editar y probar en la instalación de la biblioteca Perl (en vivo) o en otro lugar. Las pruebas "t" (directorio t/) y los ejemplos ofrecen buenas pruebas de regresión para asegurar que no hayas hecho daño. Si editas en el código en vivo, ¡no olvides copiar los cambios de vuelta a la versión maestra que guardas!
4.
Quieres contribuir al desarrollo de PDF::Builder. Necesitas un repositorio local de Git (y una cuenta de GitHub), así que cuando hayas terminado, puedes realizar una "Solicitud de Extracción" (Pull Request) para hacerlo visible. No podemos garantizar que tus cambios se integren en el proyecto, pero al menos nos gustaría verlo. A veces se emite una nueva versión CPAN.

Si quieres hacer cambios significativos para uso público y no puedes llegar a un acuerdo de mente a mente con nosotros, puedes incluso iniciar tu propio proyecto de GitHub y registrar un nuevo proyecto CPAN (esto es lo que hicimos, "forking" PDF::API2). Por favor, no asumas que no queremos tus cambios — al menos propón lo que quieres hacer por escrito, así podríamos considerarlo. Buscamos siempre personas que ayuden y expandan PDF::Builder.

Librerías Opcionales

PDF::Builder puede utilizar algunas librerías opcionales, que no son *requeridas* para una instalación exitosa. Si quieres mejorar la velocidad y las capacidades de ciertas funciones, podrías instalar y usar estas librerías:

  • Graphics::TIFF

    PDF::Builder heredó una biblioteca de imágenes lenta, limitada y de Perl puro de PDF::API2. Si Graphics::TIFF (disponible en CPAN, utiliza libtiff.a) está instalada, PDF::Builder usará esa biblioteca en lugar de la antigua biblioteca Perl pura. La única vez que podrías considerar esto es cuando necesites pasar un archivo de descriptores de archivo a "image_tiff" en lugar de un nombre de archivo. Consulta los informes de errores resueltos RT 84665 y RT 118047, así como "image_tiff" para más información.

  • Image::PNG::Libpng

    PDF::Builder heredó una biblioteca de imágenes pura Perl lenta y limitada de PDF::API2. Si Image::PNG::Libpng (disponible en CPAN, utiliza libpng.a) está instalada, PDF::Builder usará esa biblioteca en lugar de la antigua biblioteca Perl pura. Usar la nueva biblioteca te dará mejor velocidad, la capacidad de usar muestras de 16 bits y la capacidad de leer archivos PNG entrelazados. Consulta el informe de errores resuelto RT 124349, así como "image_png" para más información.

  • HarfBuzz::Shaper

    Esta librería permite a PDF::Builder manejar scripts complejos (árabe, Devanagari, etc.) así como sistemas de escritura no LTR. También es útil para scripts latinos y otros scripts simples, para ligaduras y mejoras en el kerning. HarfBuzz::Shaper se basa en una serie de bibliotecas HarfBuzz, que intentará construirlas si no las encuentra. Consulta "textHS" para más información.

  • Text::Markdown

    Esta librería se usa si deseas formatear código estilo Markdown en PDF::Builder mediante el método "column()". Traduce un dialecto específico de Markdown a HTML, que luego se procesa.

  • HTML::TreeBuilder

    Esta librería se usa para formatear entrada HTML en una estructura de datos que PDF::Builder puede interpretar, mediante el método "column()". Nota: si se utiliza entrada Markdown, también se necesita HTML::TreeBuilder para manejar el HTML que la Markdown traduce.

  • Pod::Simple::XHTML

    Esta librería se usa si deseas generar la documentación HTML a partir de los archivos POD y PM, usando "docs/buildDoc.pl". Nota: la documentación completa también se puede encontrar en línea en https://www.catskilltech.com/FreeSW/product/PDF-Builder/title/PDF%3A%3ABuilder/freeSW_full bajo el enlace "Documentation". Esta documentación en línea se actualiza cada vez que se publica una versión CPAN, pero no siempre cuando se actualiza el repositorio GitHub.

Nota: El proceso de instalación no intentará instalar estas librerías automáticamente. Si no quieres usar alguna de ellas, puedes elegir no instalar las librerías opcionales. Si deseas hacer uso de alguna, considera instalarlas *antes* de instalar PDF::Builder, para que cualquier prueba t y/o ejemplos que utilicen estas librerías puedan ejecutarse durante la instalación y el checkout de PDF::Builder. Recuerda, puedes *siempre* instalar una librería opcional más tarde, si lo deseas.

Cadenas (Texto Carácter)

Perl, y por lo tanto PDF::Builder, usan cadenas que soportan el rango completo de caracteres Unicode. Cuando importas cadenas en un programa Perl, por ejemplo al leer texto de un archivo, debes ser consciente de qué tipo de codificación de caracteres utilizan. Las codificaciones de un solo byte (por defecto, 'latin1'), representadas como bytes de valor 0x00 a 0xFF (0..255), producirán resultados diferentes si estás realizando alguna operación que dependa de la codificación, como ordenar, buscar o comparar dos caracteres no ASCII. Esto también se aplica a cualquier carácter (texto) codificado directamente en el programa Perl.

Siempre puedes decodificar el texto de entrada externa (ASCII, UTF-8, Latin-3, etc.) a la codificación interna de Perl UTF-8 (multibyte). Esto utiliza de uno a cuatro bytes para representar cada carácter. Consulta el pragma "utf8" y el módulo "Encode" para detalles sobre la decodificación de texto. Nota: Solo los tipos de fuentes TrueType ("ttfont"), pueden usar texto codificado en UTF-8 directamente. Otros tipos de fuentes (core, T1, etc.) solo pueden usar texto codificado en un solo byte. Si tu texto es ASCII, Latin-1 o CP-1252, puedes simplemente dejar las cadenas Perl como la codificación por defecto (un solo byte).

Luego, está el asunto de codificar la *salida* para que coincida con los conjuntos de caracteres de las fuentes disponibles. No estás *traduciendo* el texto en la salida, sino que le estás diciendo al sistema de salida (y al lector) qué codificación representa el flujo de bytes de salida y qué glifos deben generar.

Si confías tu texto solo a ASCII (0x00 .. 0x7F) o incluso a Latin-1 o CP-1252 (0x00 .. 0xFF), puedes usar las cadenas Perl por defecto (no UTF-8) y usar la codificación de salida por defecto (WinAnsiEncoding), que es más o menos Windows CP-1252 (un superconjunto en sí mismo de ISO-8859-1 Latin-1). Si tu texto utiliza cualquier otro carácter, tendrás que ser consciente de qué codificación utilizan tus cadenas de texto (en el texto de Perl y para declarar la codificación de los glifos de salida). Ve a "Core Fonts", "PS Fonts" y "TrueType Fonts" en "FONT METHODS" para información adicional.

Detalles Internos

Algunas de las siguientes informaciones pueden ser un poco aterradoras o confusas para los principiantes, así que no tengas miedo de saltártelas hasta que estés listo para ellas...

Perl (y PDF::Builder) internamente usan cadenas que son de un solo byte (ISO-8859-1/Latin-1) o codificadas en UTF-8 multibyte (hay una bandera interna que marca la cadena como UTF-8 o no). Si trabajas *estrictamente* en ASCII o Latin-1 o CP-1252 (cada uno es un superconjunto del anterior), deberías estar bien sin hacer nada especial sobre la codificación de tus cadenas. Puedes usar simplemente las cadenas de un solo byte por defecto de Perl (marcadas internamente como *no* UTF-8) y la codificación de salida por defecto (WinAnsiEncoding).

Si tienes la intención de usar entradas de una variedad de fuentes, deberías considerar la decodificación (conversión) de tu texto a UTF-8, lo que proporcionará una representación internamente consistente (y tu propio código Perl debería guardarse en UTF-8, en caso de que quieras usar caracteres no ASCII codificados en duro). En cualquier cadena, los caracteres no ASCII (0x80 o superior) se convertirían a la representación interna UTF-8 de Perl, a través de "Encode::decode(MY_ENCODING, $input);". "MY_ENCODING" sería una cadena como 'latin1', 'cp-1252', 'utf8', etc. Capacidades similares están disponibles para declarar un *archivo* en una codificación determinada.

Ten en cuenta que si usas codificación UTF-8 para tu texto, solo la salida de fuentes TrueType ("ttfont") puede manejarla directamente. La salida de fuentes Corefont y Type1 requerirá que el texto tenga que ser convertido de nuevo a una codificación de un solo byte (usando "Encode::encode"), que puede necesitar ser declarada con "encode" (para "corefont" o "psfont"). Si tienes algún carácter *no* encontrado en la *codificación* de un solo byte seleccionada (pero *sí* encontrado en la propia fuente), necesitarás usar "automap" para dividir los glifos de la fuente en planos de 256 caracteres, mapear dichos caracteres a 0x00 .. 0xFF en el plano apropiado, y cambiar entre planos de fuentes según sea necesario.

Las fuentes Core y Type1 (salida) usan los valores de bytes en la cadena (¡solo codificación de un solo byte!) y proporcionan un registro de mapeo de byte a glifo para cada plano. TrueType genera un grupo de cuatro dígitos hexadecimales que representan el "CId" (identificador de carácter) de cada carácter. El CId no corresponde ni a las representaciones internas de un solo byte ni a las de UTF-8 de los caracteres.

La conclusión es que necesitas saber cuál es la representación interna de tu texto, para que las rutinas de salida puedan informar al lector de PDF sobre ello (a través del archivo PDF). El texto no se traducirá en la salida, pero el lector de PDF necesita saber qué codificación se está utilizando, para saber a qué glifo asociar cada byte (o secuencia de bytes).

Ten en cuenta que se dice que algunos sistemas operativos y sabores de Perl son estrictos con los nombres de codificación. Por ejemplo, "latin1" (un alias) puede ser rechazado como inválido, mientras que "iso-8859-1" (un valor canónico) funcionará.

Por cierto, se recomienda que utilices *al menos* Perl 5.10 si vas a utilizar caracteres no ASCII. Perl 5.8 puede ser un poco impredecible al manejar dicho texto.

Orden de Renderizado

Para bien o para mal, por motivos de compatibilidad, PDF::Builder continúa el mismo modelo de renderizado que usaba PDF::API2 (y posiblemente sus predecesores). Es decir, todos los gráficos *para un objeto gráfico* se colocan en un registro, y toda la salida de texto *para un objeto de texto* va a otro registro. Cuál se saca primero es el que se declara primero. Esto puede llevar a resultados inesperados, donde los elementos se renderizan en un orden (aparentemente) incorrecto. Es decir, los elementos de texto y gráficos no se sacan (renderizan) necesariamente en el mismo orden en que se crearon en el código. Dos elementos en el mismo objeto (por ejemplo, $text) *se renderizarán* en el mismo orden en que se codificaron, pero los elementos de diferentes objetos pueden no renderizarse en el orden esperado. El siguiente ejemplo (código fuente y fragmentos de PDF anotados) esperemos que ilustre el problema:

use strict;
use warnings;
use PDF::Builder;
# demostrar el orden de los objetos de texto y gráficos
#
my $fname = "objorder";
my $paper_size = "Letter";
# ver los contenidos de los flujos de texto y gráficos
my $pdf = PDF::Builder->new(compress => 'none');
$pdf->mediabox($paper_size);
my $page = $pdf->page();
# ajustar la ruta para tu sistema operativo
my $fontTR = $pdf->ttfont('C:\\Windows\\Fonts\\timesbd.ttf');

Para el primer grupo, podrías esperar que se saque la línea "under", luego el círculo (disco) relleno que la cubre parcialmente, luego la línea "over" que cubre el disco, y finalmente un rectángulo (barra) relleno sobre ambas líneas. Lo que realmente sucedió es que el objeto gráfico $grfx se declaró primero, por lo que todo en ese objeto (el disco y la barra) se saca primero, y el objeto de texto $text (ambas líneas) viene después. El resultado es que las líneas de texto están *encima* de los dibujos gráficos.

Verificación de integridad

Los métodos PDF::Builder que abren un archivo PDF existente, lo pasan a través del método de verificación de integridad, "$self->IntegrityCheck(level, content)". Este método tiene dos funciones: 1) encontrar cualquier "/Version" que sobrescriba la versión del PDF encontrada en la cabecera del documento, y 2) realizar algunas validaciones básicas en el contenido del PDF.

El parámetro "level" acepta los siguientes valores:

0
No mostrar mensajes de diagnóstico; solo devolver cualquier versión de sobrescritura.
1
Mostrar mensajes de diagnóstico de nivel de error (grave), así como devolver cualquier versión de sobrescritura.

Los errores incluyen, que no se especificó ningún objeto "/Root", o si se especificó, no se encontró el objeto indicado. Un objeto reclama a otro objeto como hijo ("/Kids"), pero otro objeto ya reclamó ese hijo. Un objeto reclama un hijo, pero ese hijo no tiene padre o el hijo indica un padre diferente.

2
Mostrar mensajes de diagnóstico de nivel de error (grave) y advertencia (menos grave), así como devolver cualquier versión de sobrescritura. Este es el valor predeterminado.
3
Mostrar mensajes de diagnóstico de nivel de error (grave), advertencia (menos grave) y nota (informativo), así como devolver cualquier versión de sobrescritura.

Las notas incluyen que no se especificó ningún objeto opcional "/Info", o si se especificó, no se encontró el objeto indicado. Se hizo referencia a un objeto, pero no se encontró un registro para él. (Esto puede ser aceptable si el objeto no está definido, o está en la lista libre, ya que la referencia será ignorada entonces.) Un objeto está definido, pero parece que ningún otro objeto lo referencia.

4
Mostrar mensajes de diagnóstico de nivel de error, advertencia y nota, así como devolver cualquier versión de sobrescritura. También imprime la estructura de diagnóstico.
5
Mostrar mensajes de diagnóstico de nivel de error, advertencia y nota, así como devolver cualquier versión de sobrescritura. También imprime la estructura de diagnóstico y el $self (generalmente útil solo si ya ha leído el archivo PDF).

La versión es una cadena (por ejemplo, "1.5") si se encuentra, de lo contrario se devuelve "undef" (valor indefinido). Para controlar la llamada automática a IntegrityCheck (a través de opens), el nivel se puede proporcionar con la opción (flag) "diaglevel =>n", donde "n" está entre 0 y 5.

MÉTODOS "BOX"

Nota general: Tenga cuidado si especifica un Media Box (u otra "caja") diferente para una página que la configuración global de "caja", para evitar sorpresas. Por ejemplo, definir un Media Box global (tamaño del papel) y un Crop Box global, y luego definir un Media Box a nivel de página sin definir un Crop Box a nivel de página, puede dar resultados extraños en el recorte resultante. Dichas combinaciones no están bien definidas.

Todas las dimensiones en las cajas tienen como valor predeterminado la Unidad de Usuario predeterminada, que son puntos (1/72 de pulgada). Tenga en cuenta que la especificación PDF limita los tamaños y las coordenadas a 14400 Unidades de Usuario (200 pulgadas, para la Unidad de Usuario predeterminada de un punto), y Adobe products (hasta ahora) siguen este límite para Acrobat y Distiller. Vale la pena señalar que otros escritores y lectores de PDF pueden optar por ignorar el límite de 14400 unidades, con o sin el uso de una Unidad de Usuario especificada. Por lo tanto, PDF::Builder no aplica ningún límite a las coordenadas: es su responsabilidad considerar qué lectores y otras herramientas PDF se pueden usar con un PDF que usted produce. Tenga en cuenta también que los lectores de Acrobat anteriores tenían límites de coordenadas tan pequeños como 3240 Unidades de Usuario (45 pulgadas), y un tamaño de medio mínimo de 72 o 3 Unidades de Usuario.

Unidades de Usuario (userunit)

$pdf->userunit($numero)
La Unidad de Usuario predeterminada en el sistema de coordenadas PDF es un punto (1/72 de pulgada). Puede pensar en ella como un factor de escala para permitir documentos más grandes (o incluso más pequeños). Este método se puede utilizar (para PDF 1.6 y superior) para establecer la Unidad de Usuario en un número de puntos. Por ejemplo, userunit(72) establecerá el multiplicador de escala en 72.0 puntos por Unidad de Usuario, o 1 pulgada por Unidad de Usuario. Cualquier número mayor que cero es aceptable, aunque algunos lectores y herramientas pueden no manejar muy bien las Unidades de Usuario menores que 1.0.

No todos los lectores respetan la Unidad de Usuario, si le da una, o la manejan exactamente de la misma manera. Adobe Distiller, por ejemplo, no la usa. Cómo se manejan las Unidades de Usuario puede variar de un lector a otro. Adobe Acrobat, en este momento, respeta la Unidad de Usuario en la versión 7.0 y superior, pero la limita a 75000 (lo que da un tamaño máximo de documento de 15 millones de pulgadas o 236.7 millas o 381 km). Otros lectores y herramientas PDF pueden permitir un límite más grande (o más pequeño).

Sus resultados pueden variar: Algunos lectores ignoran una configuración global de Unidad de Usuario y no hacen que las páginas la hereden (PDF::Builder la duplica en cada página para simular la herencia). Algunos lectores pueden dar advertencias espurias sobre contenido truncado cuando se cambia un Media Box mientras se utilizan Unidades de Usuario. Algunos lectores hacen cosas extrañas con los Crop Boxes cuando una Unidad de Usuario está en vigor.

Dependiendo del lector utilizado, el efecto de una Unidad de Usuario más grande (mayor que 1) puede significar una menor resolución (apariencia más tosca o granulada) en el documento renderizado. Si está imprimiendo algo del tamaño de una valla publicitaria, esto puede no importarle, pero debe ser consciente de la posibilidad (incluso con coordenadas fraccionarias). Por el contrario, una Unidad de Usuario menor que 1.0 (si está permitida) reduce el tamaño permitido de su documento, pero puede resultar en una mayor resolución.

Una configuración global de Unidad de Usuario (nivel PDF) es heredada por cada página (una acción de PDF::Builder, no necesariamente realizada automáticamente por el lector), o puede ser anulada llamando a userunit en la página. No proporcione más de una configuración global de userunit, ya que solo se utilizará la última. Se permite establecer la Unidad de Usuario de una página (si se llama "$page->" en su lugar) (anulando la configuración global para esta página). Sin embargo, muchas fuentes recomiendan no hacer esto, ya que los resultados pueden no ser los esperados (una vez más, dependiendo de las peculiaridades del lector).

Recuerde llamar a "userunit" antes de llamar a cualquier cosa relacionada con tamaños de página o caja, o coordenadas. Especialmente al establecer tamaños de caja 'nombrados', los métodos necesitan conocer la Unidad de Usuario actual para que los tamaños de página nombrados (en puntos) puedan escalarse hacia abajo a la Unidad de Usuario actual.

Media Box (mediabox)

$pdf->mediabox($nombre)
$pdf->mediabox($nombre, orient => 'orientacion' )
$pdf->mediabox($ancho,$alto)
$pdf->mediabox($llx,$lly, $urx,$ury)
($llx,$lly, $urx,$ury) = $pdf->mediabox()
Establece el Media Box global (o el Media Box de la página, si se usa "$page->" en su lugar). Esto define el ancho y alto (o por coordenadas de esquina, o por nombre estándar) de la página de salida en sí, como el tamaño físico del papel. Este es normalmente el más grande de los "boxes". Si alguna caja subsidiaria (dentro de ella) excede el media box, la porción del material o las cajas fuera del Media Box serán ignoradas. Es decir, el Media Box es El Único Box que los Domina a Todos, y es el límite general para otras cajas (alguna documentación se refiere al Media Box como "recortando" otras cajas). Además, el Media Box define el sistema de coordenadas general para las operaciones de texto y gráficos.

Si no se proporcionan argumentos, se devuelven en su lugar las coordenadas del Media Box (global o de página) actual. La función anterior "get_mediabox" (solo página) estaba obsoleta y ha sido eliminada. Además, al establecer el Media Box, se devuelven las coordenadas resultantes. Esto le permite especificar el tamaño de la página por un nombre (alias) y obtener las dimensiones de vuelta, todo en una sola llamada.

Tenga en cuenta que muchas impresoras no pueden imprimir hasta el borde físico del papel, por lo que debe planificar dejar un margen en blanco, incluso fuera de cualquier marca de corte y sangrado. Las impresoras y los lectores en pantalla son libres de descartar cualquier contenido que se encuentre fuera del Media Box, y las impresoras pueden descartar material justo dentro del Media Box.

La especificación PDF requiere un Media Box global; si no se proporciona explícitamente, PDF::Builder establecerá el Media Box global al tamaño US Letter (8.5in x 11in). Este es el tamaño del medio que se utilizará para todas las páginas si no especifica una llamada a "mediabox" en una página. Es decir, una configuración de mediabox global (nivel PDF) es heredada por cada página, o puede ser anulada estableciendo mediabox en la página. No proporcione más de una configuración global de mediabox, ya que solo se utilizará la última.

Si proporciona un nombre de cadena único (por ejemplo, 'A4'), puede opcionalmente agregar una orientación para girar la página 90 grados en modo Horizontal: "orient => 'L'" o "orient => 'l'". "orient" es la única opción reconocida, y una cadena que comienza con 'L' o 'l' (para Horizontal) es el único valor de interés (cualquier otra cosa se trata como modo Vertical). El eje y todavía va de 0 en la parte inferior de la página a lo que solía ser el ancho de la página (ahora, la altura) en la parte superior, y lo mismo para el eje x: 0 a la izquierda hasta la (antigua) altura a la derecha. Es decir, el sistema de coordenadas es el mismo que antes, excepto que la altura y el ancho son diferentes.

La esquina inferior izquierda no tiene que ser 0,0. Puede ser cualquier valor que desee, incluidos valores negativos (siempre que los lados del medio resultante tengan al menos un punto de longitud). "mediabox" establece el sistema de coordenadas (incluido el origen) de los gráficos y textos que se dibujarán, así como para los "boxes" posteriores. Incluso es posible dar dos esquinas opuestas cualesquiera (como la superior izquierda y la inferior derecha). El sistema de coordenadas será reorganizado (por el Lector) para que siga siendo el mínimo convencional de "x" e "y" en la inferior izquierda (es decir, ¡no se puede hacer que "y" aumente de arriba a abajo!).

Ejemplo:

$pdf = PDF::Builder->new();
$pdf->mediabox('A4'); # Tamaño A4 (595 Pts de ancho por 842 Pts de alto)
...
$pdf->saveas('nuestro/nuevo.pdf');
$pdf = PDF::Builder->new();
$pdf->mediabox(595, 842); # Tamaño A4, con esquina inferior izquierda implícita 0,0
...
$pdf->saveas('nuestro/nuevo.pdf');
$pdf = PDF::Builder->new;
$pdf->mediabox(0, 0, 595, 842); # Tamaño A4, con esquina inferior izquierda explícita 0,0
...
$pdf->saveas('nuestro/nuevo.pdf');
Consulte el código fuente de PDF::Builder::Resource::PaperSizes para obtener la lista completa de nombres admitidos (alias) y sus dimensiones en puntos. Puede agregar tamaños de papel adicionales a este archivo si lo desea. Es posible que desee hacerlo si utiliza con frecuencia un tamaño de página estándar en modo horizontal (apaisado). Establece la caja de recorte (o la caja de recorte de la página, si se usa "$page->"). Esto definirá la dimensión del medio a la que se recortará el resultado posterior. Ten en cuenta que esto no emite ningún marco de recorte para guiar el corte de la hoja de papel. Los lectores de PDF deben considerar esto como la parte visible de la página, y cualquier contenido encontrado fuera de ella puede ser recortado (invisible). Por defecto, es igual a la Caja de Medios, pero puede definirse como menor, en el sistema de coordenadas definido por la Caja de Medios. Un ajuste global será heredado por cada página, pero puede ser anulado por un ajuste por página. Un lector o impresor puede optar por descartar cualquier parte recortada (invisible) de la página y mostrar solo el área dentro de la caja de recorte. Por ejemplo, si tu Caja de Medios es A4 (0,0 a 595,842 Puntos), y tu Caja de Recorte es (100,100 a 495,742), un lector como Adobe Acrobat Reader puede mostrar una página de 395 por 642 Puntos (es decir, solo la parte visible de tu página). Otros lectores pueden mostrar la dimensión completa del medio (Caja de Medios) y un área de 100 Puntos de ancho (en este ejemplo) alrededor del contenido visible. Si no se proporcionan argumentos, se devuelven las coordenadas actuales de la caja de recorte (global o de la página). La función anterior "get_cropbox" (solo página) está **obsoleta** y ha sido eliminada. Si no se ha definido una caja de recorte, se devuelven las coordenadas de la Caja de Medios (que siempre existen). Además, al definir la caja de recorte, se devuelven las coordenadas resultantes. Esto permite especificar la caja de recorte por nombre (alias) y obtener las dimensiones de vuelta, todo en una sola llamada. No confundas la caja de recorte con la "Trim Box", que muestra dónde se espera que la hoja de papel sea cortada en la realidad. Algunos lectores de PDF podrían reducir el fondo visible del "papel" a la dimensión de la caja de recorte; otros podrían simplemente omitir cualquier contenido fuera de ella. De cualquier manera, perderías cualquier marca de recorte o instrucción de corte, instrucciones de impresión, marcas de registro de color, o contenido fuera de la caja de recorte. Una buena utilización de la caja de recorte sería limitar la impresión a un área donde un impresor pueda confiablemente depositar tinta, y dejar las áreas de borde donde los mecanismos de manejo de papel evitan que se aplique tinta o tóner. Esto te evitaría colocar accidentalmente contenido valioso en un área donde un impresor se negaría a imprimir, pero permitirías incluir un área de sangrado y espacio para marcas de impresión e instrucciones. Aunque no lo mencioné, si tu impresor no puede imprimir hasta el borde mismo de la hoja de papel, necesitarás cortar (recortar) las hojas impresas para obtener los bordes reales. Un ajuste global (nivel PDF) de la caja de recorte es heredado por cada página, o puede ser anulado estableciendo "cropbox" en la página. Al igual que con "mediabox", solo se puede establecer una caja de recorte en este nivel (PDF). Al igual que con "mediabox", un tamaño de medio con nombre puede tener un oriente (l o L) para el modo de orientación horizontal. Ten en cuenta que el nivel global de la caja de recorte del PDF se utilizará incluso si la página obtiene su propia caja de recorte. Es decir, la caja de recorte de la página hereda el nivel global de la caja de recorte, no la caja de medios de la página, ¡incluso si la página tiene su propio tamaño de medio! Si estableces tu propia caja de medios o caja de recorte, deberías considerar también establecer explícitamente la caja de recorte de la página (y otros elementos).

Cajas

Las cajas se pueden especificar cuando se abre un nuevo documento, en un nivel global, o por página individual. Si no se definen, las cajas de la página heredan las cajas globales.

Los métodos de acceso son:

  • set_media_box()

  • set_crop_box()

  • set_bleed_box()

  • set_trim_box()

  • set_art_box()

Y los métodos de consulta son:

  • media_box()

  • crop_box()

  • bleed_box()

  • trim_box()

  • art_box()

Todos los cuadros se definen mediante un objeto Rectangle de PDF::Builder. Se crea de la siguiente manera:

my $rect = PDF::Builder::Rectangle->new( $x1, $y1, $x2, $y2 );
# or
my $rect = PDF::Builder::Rectangle->new( x1=>$x1, y1=>$y1, x2=>$x2, y2=>$y2 );
# or
my $rect = PDF::Builder::Rectangle->new( llx => $llx, lly => $lly, urx => $urx, ury => $ury );

Tenga en cuenta que las coordenadas se miden desde la esquina inferior izquierda de la página y se expresan en puntos (72 puntos por pulgada). Si se omite la caja de medios, se asume que el tamaño es US Letter (8.5x11).

Tenga en cuenta también que la mayoría de las impresoras profesionales no recortarán el papel hasta el tamaño final del documento, sino que lo cortarán ("guillotined") y lo encuadernarán en libros o revistas. Normalmente, solo proporcionaría un PDF con todas las páginas; ellos se encargarían de la disposición de las firmas (que incluye desplazamientos y rotaciones de 180 grados).

(Como aparte, no cuente con que una imprenta comercial tenga ninguna fuente en particular, así que asegúrese de preguntar. Normalmente, querrán que incruste todas las fuentes utilizadas, ¡pero pregunte primero y verifique antes de entregar el trabajo de impresión! Las fuentes TTF/OTF (ttfont()) se incrustan de forma predeterminada, pero otras fuentes (core, ps, bdf, cjk) no lo están. Una imprenta *puede* tener una colección de fuentes básicas, pero son libres de sustituir una fuente "similar" para cualquier fuente básica dada, ¡y los resultados pueden no coincidir con lo que vio en su PC!)

Asumiendo que está utilizando una impresora láser o de inyección de tinta de una sola hoja (US Letter o A4), ¿planea recortar cada hoja a un tamaño final más pequeño? Si es así, puede hacer sangrados verdaderos definiendo una Trim Box y una Bleed Box ligeramente más grande. Imprimiría sangrados (hasta el borde final) hasta la Bleed Box, pero no se aplica nada a la Bleed Box. En el otro extremo del espectro, definiría la Media Box al tamaño físico del papel que se está imprimiendo. La mayoría de las impresoras reservan un pequeño espacio en los lados (y posiblemente arriba y abajo) para el manejo del papel, por lo que a menudo es bueno definir su Crop Box como el área imprimible. Recuerde que la Media Box establece el sistema de coordenadas utilizado, por lo que aún debe evitar salirse de la Crop Box con contenido (la mayoría de los lectores e impresoras no mostrarán tinta fuera de la Crop Box). Ya sea que defina o no una Crop Box, casi siempre terminará con papel blanco en al menos los lados.

Para trabajos pequeños internos, probablemente no necesitará puntos de alineación de color y otra información e instrucciones profesionales entre la Bleed Box y la Crop Box, pero las marcas de corte para el recorte (si se usan) deben ir justo fuera de la Trim Box (parcial o totalmente dentro de la Bleed Box), y dibujarse *después* de todo el contenido. Si *no* va a recortar el papel, no intente hacer ningún efecto de sangrado (incluidas páginas/portadas con color de fondo sólido), ya que normalmente tendrá un borde blanco alrededor de la hoja de todos modos (las impresoras dejan una ruta limpia y seca para los rodillos de alimentación). No cuente con que un documento PDF *nunca* se imprima físicamente, y no solo se muestre (donde puede hacer cosas como sangrar hasta el borde del medio). Finalmente, para la impresión de una sola hoja, una Art Box probablemente sea innecesaria, pero si está combinando páginas en impresiones N-up, o realizando otras manipulaciones, puede ser útil.

Herencia de Cajas

Qué Cajas de Medios, Cultivo, Sangrado, Recorte y Arte obtiene una página puede ser un poco complicado. Tenga en cuenta que, por lo general, solo las Cajas de Medios y Cultivo tendrán un efecto visual claro. El efecto visual de las otras cajas (si las hay) puede ser muy sutil.

Primero, todo se establece en el nivel global (PDF). La Media Box siempre se define y, por defecto, es US Letter (8,5 pulgadas de ancho por 11 pulgadas de alto). La Crop Box global hereda la Media Box, a menos que se defina explícitamente. Las Bleed, Trim y Art Boxes heredan la Crop Box, a menos que se definan explícitamente. Solo se debe definir una caja global una vez, ya que la última definida es la que se escribirá en el PDF.

Segundo, una página hereda las cajas globales, para su configuración inicial. Puede llamar a cualquiera de los métodos de configuración de caja ("cropbox", "trimbox", etc.) para establecer explícitamente (anular) cualquier caja para *esta* página. Tenga en cuenta que establecer una nueva Media Box para la página *no* restablece la Crop Box de la página; todavía utiliza lo que heredó de la Crop Box global. Necesitaría establecer explícitamente la Crop Box de la página si desea una configuración diferente. Del mismo modo, las Bleed, Trim y Art Boxes de la página no se restablecerán con una nueva Crop Box de página; seguirán heredando de la configuración global (PDF).

Tercero, la Media Box de la página (la que realmente se usa para las páginas de salida) recorta o limita todas las demás cajas para que no se extiendan más allá de su tamaño. Por ejemplo, si la Media Box es US Letter y usted establece una Crop Box de tamaño A4, se aplicará la menor de las dos alturas (11 pulgadas) y la menor de las dos anchuras (8,26 pulgadas, 595 puntos). Las dimensiones *dadas* de una caja se devuelven en la consulta (get), no las dimensiones *efectivas* recortadas por la Media Box.

Esquemas (Marcadores)

Es posible crear *esquemas* (también conocidos como *marcadores*) en un documento PDF. No está limitado a páginas enteras como destinos, sino que puede ajustar el destino dest() para mostrar una parte específica de una página.

Conjunto simple de Esquema de Nivel Único

Inserta tres esquemas (al mismo nivel) en una lista simple de 12 páginas (ejemplo 055_outlines):

my $doc = PDF::Builder-> open($infile);
$doc-> outlines
    -> outline
        -> dest( $doc-> openpage( 1 ))
        -> title( '1ª página (i)' );
$doc-> outlines
    -> outline
        -> dest( $doc-> openpage( 4 ))
        -> title( '4ª página (1)' );
$doc-> outlines
    -> outline
        -> dest( $doc-> openpage( 11 ))
        -> title( '11ª página (7)' );

dest() por defecto es un enlace a una página completa (dada como el número ordinal de página, *no* el número de página formateado del documento). El title() es lo que ves en la sección Esquema o Marcadores de tu Lector de PDF.

Un ejemplo de Esquema Multinivel

También es posible definir esquemas anidados (de varios niveles). Para el mismo conjunto de páginas que el anterior, agregaremos dos páginas anidadas debajo de la página *i* y tres páginas anidadas debajo de la página *1*. Tenga en cuenta que es una práctica común hacer las *secciones* de nivel superior (por ejemplo, *prefacio, cuerpo, material final*) y colocar todas las páginas reales debajo de ellas, pero aún así necesita tener cada "encabezado" de sección que mapee a una página real. Por lo tanto, *prefacio* podría apuntar a la página *i*, y tener esquemas para *i, ii,* e *iii* anidados debajo de él.

my $doc = PDF::Builder-> open($infile);
my $root =  # Objeto Outlines (raíz de todo)
    $doc-> outlines();
my $top0 =  # Objeto Outline en el nivel superior, inicialmente colapsado (cerrado)
$root -> outline($root)
        -> is_open(0)        
        -> dest( $doc-> openpage( 1 ))
        -> title( '1ª página (i)' );
my $top1 =  # Objeto Outline en el nivel superior
$root -> outline($root)
        -> dest( $doc-> openpage( 4 ))
        -> title( '4ª página (1)' );
my $top2 =  # Objeto Outline en el nivel superior. sin hijos
$root -> outline($root)
        -> dest( $doc-> openpage( 11 ))
        -> title( '11ª página (7)' );
# añadir marcadores de nivel inferior aquí. no hay razón para que no pudieran ser
# mezclados con los niveles superiores anteriores, siempre que vengan después
# de que su padre sea definido.
# dos páginas debajo de la primera página de nivel superior (i)
$top0 -> outline($top0)
          -> dest( $doc-> openpage( 2 ))
          -> title( '2ª página (ii)' );

$top0 -> outline($top0)
          -> dest( $doc-> openpage( 3 ))
          -> title( '3ª página (iii)' );
# tres páginas debajo de la segunda página de nivel superior (1). la tercera es
# insertada después de la primera y antes de la segunda.
my $first =
$top1 -> outline($top1)
          -> dest( $doc-> openpage( 5 ))
          -> title( '5ª página (2)' );

$top1 -> outline($top1)
          -> dest( $doc-> openpage( 6 ))
          -> title( '6ª página (3)' );

$first -> insert_after()
          -> dest( $doc-> openpage( 7 ))
          -> title( '7ª página (4)' );

Es posible definir un solo esquema (enlace) como *cerrado*, en cuyo caso todos los esquemas anidados debajo de él estarán ocultos (con un indicador "cerrado"). Intente evitar ir más de dos niveles de profundidad (un nivel de anidamiento), ya que la columna de Esquemas/Marcadores suele ser bastante estrecha.

MÉTODOS DE FUENTE

Fuentes Básicas

Estas son las fuentes "incorporadas", en el sentido de que cualquier lector de PDF garantiza que las proporcionará y las admitirá. Las *métricas* de las fuentes admitidas se envían con PDF::Builder, pero no las fuentes en sí mismas.

Las fuentes básicas se limitan a *codificaciones de un solo byte*. La codificación predeterminada para las fuentes básicas es WinAnsiEncoding (aproximadamente el superconjunto CP-1252/Windows-1252 de ISO-8859-1/Latin-1). Consulte la opción "encode" a continuación para cambiar esta codificación.

Hay unas 14 fuentes básicas (variantes normal, *itálica*, **negrita**, y **_negrita-itálica_**) para Times [serif], Helvetica [sans serif], Courier [pitch fijo]; además de dos fuentes de símbolos, Symbol y Zapf Dingbats) que se supone que están disponibles en cualquier lector de PDF, *aunque a menudo se sustituyen fuentes con métricas muy similares*.

Las máquinas con Windows tienen 14 "fuentes básicas" adicionales (15 si cuentas Bank Gothic): Georgia [serif], Verdana [sans serif] y Trebuchet [sans serif] en 4 variantes cada una, junto con Webdings y Wingdings). Estas *suelen* estar disponibles en una plataforma Windows (¡pero no están garantizadas!). Normalmente no están instaladas por defecto en plataformas Linux, Mac y otras no Windows, así que tenga cuidado al especificar estas fuentes.

Ejemplos

$font1 = $pdf->corefont('Times-Roman', encode => 'latin2');
$font2 = $pdf->corefont('Times-Bold');
$font3 = $pdf->corefont('Helvetica');
$font4 = $pdf->corefont('ZapfDingbats');

Las fuentes básicas también se pueden solicitar a través del método font()

$font5 = $pdf->font('Courier-Oblique');

así como estar integradas en FontManager

$font6 = $pdf->get_font('face'=>'Times', 'italic'=>1, 'bold'=>0);

Notas y Limitaciones

  • *No puede* usar codificaciones UTF-8 u otras multibyte con fuentes básicas, *solo* codificaciones de un solo byte (máximo 256 caracteres). Un lector de PDF simplemente no sabe qué hacer con un carácter multibyte y probablemente lo representará como una secuencia de caracteres individuales (produciendo basura). Aunque la mayoría de las codificaciones de un solo byte, al menos para idiomas europeos, son compatibles, es posible que encuentre una codificación que incluya un carácter *no* encontrado en un archivo de fuente dado, o viceversa (la fuente incluye caracteres a los que la codificación no le da acceso).
  • No confunda los puntos de código de caracteres Unicode (como los dados con una entidad HTML) con valores de un solo byte o caracteres multibyte. La única forma de acceder a un carácter definido para una codificación dada es con un *único* valor de byte en el rango de 0 a 255. Por ejemplo, si no puede escribir directamente un símbolo de "Euro", es "\x80" en muchas codificaciones; usaría eso en lugar del punto de código Unicode "\x{20AC}" o "x\{E282AC}" UT
F-8 Cadena de bytes. Se trata de proporcionar un valor de byte único que el lector de PDF pueda buscar en su definición de fuente para obtener el carácter deseado. Notes and Limitations

  • CAUTION: There is a "gotcha" with TrueType fonts that you need to be aware of when using them. PDF::Builder outputs to the text stream a list of glyph IDs as four-digit hex codes, rather than the list of character byte codes used by other font types. The intent is to allow more than the standard Unicode points (alternate glyphs for ligatures and other uses). Don't count on it as encryption to hide your content (the PDF Reader will just display it anyway!), even though it does make it hard to find specific text in a PDF using a text editor.
  • The Tw operator, if used ("$text->wordspace(n)") to adjust inter-word spacing, will be ignored by most, if not all, PDF Readers (including Adobe products). This is because this operator is looking for actual ASCII spaces (x20 bytes) in the stream, to apply the width change to. Note that only ASCII spaces are affected (not other spaces), and not at all for TrueType and OpenType fonts (because they have 4-digit glyph IDs, not x20 bytes)! PDF::Builder has been updated to attempt to respect the Tw operator when using TTF/OTF fonts. If the "Tw" amount is non-zero, it will split up sentences on ASCII spaces (x20) and individually place words on the page. This necessarily bloats the PDF file size, but is the only way to adjust word spacing via the wordspace() method. Note that again, only ASCII spaces (x20) are affected (to match the behavior of the Tw operator for other font types), and other spaces (xA0 required/non-breaking space, thin space, etc.) are not handled.
  • Warning: BaseEncoding is not set by default for TrueType fonts, so text in the PDF isn't searchable (by the PDF reader) unless a ToUnicode CMap is included. A ToUnicode CMap is included by default (unicodemap set to 1) by PDF::Builder, but allows it to be disabled (for performance and file size reasons) by setting unicodemap to 0. This will produce non-searchable text, which, besides being annoying to users, may prevent screen readers and other aids to disabled users from working correctly!
  • Do not confuse Unicode character points (such as given with an HTML entity) with single byte values or multibyte characters. The only way to access a character defined for a given encoding is with a single code value in the allowable range. For example, if you can't directly type a "Euro" symbol, it is "\x80" in many encodings -- you would use that for a single-byte encoding, or for UTF-8, the Unicode "\x{20AC}" code point. You would never give the UTF-8 byte string "x\{E282AC}". It needs to be understandable in the context of the current encoding, so that the 4-digit glyph code can be output.
  • Be aware of what a given platform (operating system) and editor is using for its code page when it creates a file with your text to be turned into a PDF! If you typed a "Euro" but it's, say, a UTF-8 byte string in the file, and you are using a single-byte encoding, you probably won't get a "Euro" in your PDF.

Where is the font I just added?

Well, sometimes you get lucky and can specify the exact directory that the ".ttf" or ".otf" file will reside in, making it easy to specify the path to the font file (for uses such as ttfont(), font(), or Font Manager calls). Other times, the operating system will play hide and seek with you, leaving you to expend much time and energy to track down where the file is. Linux distributions tend to have their own favorite hiding places for font files, but at least they tend to be consistent! On the other hand, Windows often decides that it knows better than you, and will put files in an unexpected place, and under an unexpected name!

To find out where your TTF or OTF file ended up, if you don't see an obvious entry in /Windows/Fonts (even if you drag and dropped the font file there), you need to look in /Users/XXXX/AppData/Local/Microsoft/Windows/Fonts, depending on what user name you were signed on as when you installed the font. Even then, you may not be done, as the name may have been changed to something unrecognizable. You may need to look at Windows' mapping of font name to filename.

In the command shell (command line), or whatever equivalent you like to use, enter "regedit" to bring up the registry editor. For the top level, choose (click on) either "HKEY_LOCAL_MACHINE" (for global font settings, in /Windows/Fonts) or "HKEY_CURRENT_USER" (for fonts installed by whoever is currently signed on, in /Users/XXXX/AppData...). From there, both have the same path: "SOFTWARE > Microsoft > Windows NT > CurrentVersion > Fonts". This should bring up a listing of all the installed fonts (full name, e.g. "Papyrus Regular") and their actual filename ("PAPYRUS.TTF"). For instance, I just installed (drag and drop into /Windows/Fonts) a blackletter "Gothic" font named English Towne Medium. It ended up in my /Users/XXXX... directory as "EnglishTowne.ttf".

You don't need to change anything in the registry, just look. You do have the capability to change things, including hiding/showing the font, if you care to get into those things.

La librería HarfBuzz::Shaper puede instalarse opcionalmente para usar las capacidades de formateo de texto de la librería HarfBuzz. Estas incluyen ligaduras y kerning para scripts occidentales (como el alfabeto latino). Scripts más complejos como los de árabe e indígenas también pueden ser manejados, donde múltiples formas de un carácter pueden ser seleccionadas automáticamente, los caracteres pueden reordenarse y otras modificaciones pueden realizarse. El ejemplo/HarfBuzz.pl da algunos ejemplos de lo que se puede hacer.

Aun así, HarfBuzz solo funciona con fuentes TrueType (.ttf) y OpenType (.otf). No funciona con fuentes PostScript (Type1), core, de mapa de bits, o CJK. No todas las fuentes .ttf tienen las instrucciones necesarias para guiar a HarfBuzz, pero la mayoría de las fuentes .otf las tienen. En otras palabras, ¡no hay garantía de que un archivo de fuente específico funcione con Shaper!

La idea básica es dividir el texto en "bloques" de la misma script (alfabeto), idioma, dirección, fuente, tamaño de fuente y variante (itálica, negrita, etc.). Estos pueden ir desde un solo carácter hasta cadenas de texto de párrafo. Estos se envían a HarfBuzz::Shaper junto con los indicadores, el archivo de fuente a usar y otra información de soporte, para crear una matriz de caracteres de salida. Cada elemento es un hash que describe el carácter a mostrar, incluyendo su nombre (si está disponible), su identificador de carácter (número) en la fuente seleccionada, sus posiciones x e y (generalmente 0), y sus valores de avance x e y, todos en puntos. Para idiomas horizontales (LTR y RTL), el avance y es normalmente 0 y el avance x es el ancho del carácter de la fuente, menos cualquier kerning.

Shaper intentará determinar la script utilizada y la dirección del texto, basándose en el rango Unicode; y una estimación razonable del idioma. El idioma puede ser anulado, pero actualmente la script y la dirección del texto no pueden ser anuladas.

Noticia importante: ¡El número de caracteres (elementos de la matriz) puede no ser igual al número de puntos (caracteres) dados en la cadena de texto de un bloque! A veces un carácter se descompone en varias partes (múltiples caracteres); a veces múltiples caracteres pueden combinarse en una sola ligadura; y los caracteres pueden reordenarse (especialmente en scripts de derecha a izquierda como hebreo y árabe). Además, para scripts de derecha a izquierda (bidireccionales) como hebreo y árabe, el texto se muestra en orden de izquierda a derecha (inverso de la entrada).

Con cuidado, una matriz de Shaper puede ser manipulada en código. Los elementos son más o menos independientes entre sí, por lo que pueden modificarse, reorganizarse, insertarse o eliminarse. Puedes ajustar la posición de un carácter con los elementos hash 'dx' y 'dy'. El valor 'ax' debería dejarse como está, para evitar errores

kerning no se calcula, pero podrías necesitar ajustar el valor de "advance x" mediante uno de los siguientes:

axs
es un valor a sustituir por 'ax' (puntos)
axsp
es un valor sustituido (porcentaje) del 'ax' original
axr
reduce 'ax' en el valor (puntos). Si es negativo, aumenta 'ax'
axrp
reduce 'ax' en el porcentaje dado. De nuevo, un valor negativo aumenta 'ax'

Precaución: el ID de glifo de un carácter determinado *no* es necesariamente el mismo entre dos fuentes cualesquiera. Por ejemplo, un espacio ASCII (U+0020) podría ser "<0001>" en una fuente y "<0003>" en otra (¡incluso una muy relacionada!). Un espacio requerido U+00A0 (espacio de no separación) puede ser generado como un espacio ASCII regular U+0020. Ten cuidado si necesitas encontrar un glifo específico en el array, especialmente si el número de elementos no coincide. Considera crear una cadena de texto de caracteres "marcador" (espacio, espacio de no separación, guion, guion suave, etc.) y procesarla a través de HarfBuzz::Shaper para obtener los números de glifo correspondientes. Puede que tengas que contar espacios, por ejemplo, para ver dónde puedes dividir un array de glifos para que encaje en una línea.

El método advancewidthHS() utiliza las mismas entradas que textHS(). Al igual que advancewidth(), devuelve la longitud del fragmento en puntos. A diferencia de advancewidth(), no puedes sobrescribir la fuente del array de glifos, el tamaño de la fuente, etc.

Una vez que tengas tu array de glifos (posiblemente modificado), lo introduces en el método textHS() para renderizarlo en la página. Recuerda que este método solo maneja una línea de texto; no hace división ni ajuste de línea — eso lo tienes que hacer tú manualmente. Para scripts occidentales (por ejemplo, latín), eso puede no ser muy difícil, pero para otros scripts que implican una modificación extensa de los caracteres en bruto, puede ser bastante difícil dividir *palabras*, aunque todavía podrías dividir en espacios interpalabra.

Un conjunto útil, aunque no exhaustivo, de funciones están permitidas por textHS(). El soporte incluye la configuración de dirección (direcciones de arriba a abajo y de abajo a arriba, por ejemplo, para lenguas del Lejano Oriente en orientación tradicional), y nombres de script y lenguaje explícitos (dependiendo del soporte que HarfBuzz mismo proporcione). Aún *no* se soportan características como ligaduras discrecionales y selección manual de glifos (por ejemplo, adornos y formas alternativas).

Actualmente, textHS() solo puede manejar una única cadena de texto. Estamos investigando cómo se podría hacer el ajuste a una longitud de línea (dividiendo un array), así como cómo se podrían dividir las palabras en guiones fuertes y suaves. En algún momento, la composición completa de párrafos y páginas podría ser posible.

MARKUP

Esta sección documenta las capacidades de marcado del método column(). Se espera que se actualice con el tiempo a medida que se añada más funcionalidad.

Se soporta un cierto tipo de Markdown, tal como lo traduce el paquete Text::Markdown a HTML. Ese HTML (y más, como entrada directa), junto con un subconjunto de CSS, es soportado por column(). Esto *no* es el lenguaje completo de Markdown o HTML, ni mucho menos, ¡así que verifica antes de usar! Además, se proporciona un pequeño marcado de none que solo maneja párrafos (separados por líneas vacías).

En todos los casos de marcado, se pueden dar ciertas configuraciones de CSS como parámetros u opciones a la llamada column(), incluyendo una sección <style> de CSS que se aplica tanto a la fuente 'none' como a la fuente Markdown.

Otros formatos de entrada

PDF::Builder actualmente solo soporta los lenguajes de marcado descritos anteriormente. Si deseas utilizar otra cosa (por ejemplo, POD de Perl, formato man, o incluso MS Word u otro formato WYSIWYG), necesitarás encontrar una utilidad de conversión para convertirlo a un tipo compatible de Markdown o HTML. Muchos de estos convertidores ya existen, así que echa un vistazo (aunque probablemente tendrás que hacer alguna limpieza antes de que column() lo acepte).

Quizás en el futuro, PDF::Builder soporte directamente formatos adicionales, pero no hay promesas. Probablemente nunca verás entrada TeX/LaTeX, ya que estos ya tienen una excelente salida PDF (y sería una tarea masiva procesarlos).

SOME SPECIAL NOTES

The column() method is the most interesting, as it gives you a method to lay out arbitrary text, potentially containing markup, within a specified column or set of columns. The text may be provided directly, or drawn from a file. The text can contain a number of markup tags which will be processed by the method, affecting the appearance of the text or the layout thereof.

The Font Manager system is used to supply the requested fonts, so it is up to the application to pre-load the desired font information before column() is called. Any request to change the encoding within column() will be ignored, as the fonts have already been specified for a specific encoding. Needless to say, the encoding used in creating the input text needs to match the specified font encoding.

Absent any markup changing the font face or styling, whatever is defined by Font Manager as the current font will be what is used. This way, you may inherit the font from the previous column(), or call "$text-"font($pdf->get_font(), size)> to set both the font and size, or just call "$pdf-"get_font()> to set only the font, relying on the "font_size" option or CSS markup to set the size.

Line fitting (paragraph shaping) is currently quite primitive. Words will not be split (hyphenated). It is planned to eventually add Knuth-Plass paragraph shaping, along with proper language-dependent hyphenation.

Each change of font automatically supplies its maximum ascender and minimum descender, the extents above and below the text line's baseline. Each block of text with a given face and variant, or change of font size, will be given the same vertical extents -- the extents are font-wide, and not determined on a per-glyph basis. So, unfortunately, a block of text "acemnorsuvwz" will have the same vertical extents as a block of text "bdfghijklpqty". For a given line of text, the highest ascender and the lowest descender (plus leading) will be used to position the line at the appropriate distance below the previous line (or the top of the column). No attempt is made to "fit" projections into recesses (jigsaw-puzzle like). If there is an inset into the side of a column, or it is otherwise not a straight vertical line, so long as the baseline fits within the column outline, no check is made whether descenders or ascenders will fall outside the defined column (i.e., project into the inset). We suggest that you try to keep font sizes fairly consistent, to keep reasonably consistent text vertical extents.
