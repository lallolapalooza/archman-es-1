NOMBRE

PCPINTRO - Introducción al Performance Co-Pilot (PCP)

INTRODUCCIÓN

El Performance Co-Pilot (PCP) es un conjunto de herramientas diseñado para monitorear y gestionar el rendimiento del sistema. Estos servicios son distribuidos y escalables para adaptarse a las configuraciones de sistema y problemas de rendimiento más complejas.

El PCP soporta varias plataformas, incluyendo (pero no limitado a) Linux, macOS, Solaris y Windows. Desde un nivel general, el PCP puede considerarse como que contiene dos clases de utilidades:

Recolectores PCP
Estas son las partes del PCP que recogen y extraen datos de rendimiento de fuentes diversas, por ejemplo, el kernel del sistema operativo.
Monitores PCP
Estas son las partes del PCP que muestran los datos recogidos de hosts (o archivos de historial) donde está instalado el Recolector PCP. Muchas herramientas de monitoreo están disponibles como parte de la distribución estándar de PCP, mientras que otras (generalmente herramientas gráficas) están disponibles en el paquete de GUI de PCP.

Este documento de manuales describe las características y opciones comunes a la mayoría de las utilidades de PCP disponibles en todas las plataformas.

VISIÓN GENERAL

La arquitectura de PCP es distribuida en el sentido de que cualquier herramienta de PCP puede ejecutarse remotamente. En el host (o hosts) que se está monitoreando, cada dominio de métricas de rendimiento, ya sea el núcleo del sistema, un nivel de servicio, un sistema de gestión de bases de datos, un servidor web, una aplicación, etc., requiere un Agente de Dominio de Métricas de Rendimiento (PMDA) que se encargue de recopilar mediciones de rendimiento de ese dominio. Todos los PMDA son controlados por el Servidor de Recolección de Métricas de Rendimiento (pmcd(1)) en el mismo host.

Las aplicaciones cliente (las herramientas de monitoreo) se conectan a pmcd(1), que actúa como un enrutador para las solicitudes, enviando solicitudes a los PMDA correspondientes y devolviendo las respuestas a los clientes. Los clientes también pueden acceder a datos de rendimiento de archivos de archivo de PCP (creados con pmlogger(1)) para análisis retrospectivos.

SEGURIDAD

PCP redistribuye una cantidad considerable de información de rendimiento dentro del host y en sus redes. La filosofía de seguridad subyacente de varios valores predeterminados controla cuánta información se envía y recibe.

Por defecto, la información que PMCD expone sobre un host es aproximadamente de la misma confidencialidad que está disponible para un usuario sin privilegios en ese host. Por lo tanto, los datos de rendimiento que se pueden leer libremente en una máquina pueden ser expuestos por PMCD a través de la red.

Sin embargo, el host que ejecuta PMCD y su red no se asumen como solo aplicaciones amigables. Por lo tanto, las operaciones de escritura, incluidas las del propio host, no están permitidas por defecto.

Estos valores predeterminados se pueden anular (ampliar o reducir) de varias maneras, que incluyen la especificación de listas de control de acceso en pmcd.conf, la activación de PMDA no predeterminados, o mediante conexiones de PMCD que pasan credenciales de usuario. Por ejemplo, algunos PMDA proporcionan automáticamente información adicional para usuarios o grupos con credenciales específicas.

APLICACIONES

Las siguientes herramientas de monitoreo de rendimiento son principalmente de tipo consola, generalmente ejecutadas directamente desde la línea de comandos, y son solo una pequeña parte de las herramientas disponibles como parte del paquete base de PCP.

Cada herramienta o comando está documentado completamente en su propia página de referencia.

pmstat
Imprime un resumen ASCII de alto nivel del rendimiento del sistema.
pmie
Un motor de inferencia que evalúa reglas de acción-predicado para activar alarmas y automatizar tareas de gestión del sistema.
pminfo
Consulta métricas de rendimiento específicas y los metadatos que las describen.
pmlogger
Genera archivos de archivo de métricas de rendimiento compatibles con la mayoría de las herramientas de PCP.
pmrep
Un generador de informes de métricas de rendimiento altamente personalizable con soporte para múltiples modos de salida.
pmval
Informe periódico de algunas o todas las instancias de una métrica de rendimiento, con control opcional de tiempo de VCR.

Si se ha instalado el paquete de GUI de PCP, se pueden utilizar las siguientes herramientas adicionales.

pmchart
Visualiza tendencias a lo largo del tiempo de métricas de rendimiento seleccionadas arbitrariamente de uno o más hosts.
pmtime
Una utilidad de control de tiempo que coordina el tiempo entre múltiples herramientas (incluyendo pmchart y pmval).
pmdumptext
Genera informes ASCII para combinaciones arbitrarias de métricas de rendimiento.

COMANDOS DE LÍNEA PREDETERMINADOS

Hay un conjunto de comandos de línea que son utilizados consistentemente por la mayoría de las herramientas de PCP.

-a archivo, --archive=archivo
La información de métricas de rendimiento se obtiene retrospectivamente del conjunto de archivos de PCP identificado por archivo, generado previamente por pmlogger(1). Consulte LOGIMPORT(3) y LOGARCHIVE(5) para obtener información sobre la creación de archivos y documentación del formato.

archivo es una lista separada por comas de nombres de archivo, cada uno de los cuales puede ser el nombre de un directorio que contiene uno o más archivos, el nombre base común a todos los archivos físicos creados por una instancia de pmlogger(1), o cualquier archivo físico individual, por ejemplo, /ruta/a/misarchivos (directorio) o miarchivo (nombre base) o miarchivo.meta (el archivo de metadatos) o miarchivo.index (el índice temporal) o miarchivo.0 (el primer volumen de datos de archivo) o miarchivo.0.bz2 o miarchivo.0.bz (el primer volumen de datos comprimido con bzip2(1)) o miarchivo.0.gz o miarchivo.0.Z o miarchivo.0.z (el primer volumen de datos comprimido con gzip(1)), miarchivo.1 o miarchivo.3.bz2 o miarchivo.42.gz etc.

-h host, --host=host
A menos que se especifique otro host mediante la opción -h (o --host), o se especifique un conjunto de archivos mediante la opción -a (o --archive), la fuente de las métricas de rendimiento será el Servidor de Recolección de Métricas de Rendimiento (PMCD) en el host local. Consulte la sección ESPECIFICACIÓN DE HOST PMCD más adelante para más detalles sobre las muchas opciones disponibles al formar la especificación del host, así como una descripción detallada de la conexión predeterminada del host local. Las opciones -a (o --archive) y -h (o --host) son mutuamente excluyentes.
-s muestras, --samples=muestras
El argumento muestras define el número de muestras a recuperar y reportar. Si muestras es 0 o -s (o --samples) no se especifica, la aplicación muestreará y reportará continuamente (en modo en tiempo real) o hasta el final de la serie de archivos de PCP (en modo de archivo).
-z, --hostzone
Cambia la hora de presentación a la zona horaria del host que es la fuente de las métricas de rendimiento, identificado mediante la opción -h (o --host) o -a (o --archive)
-Z zona-horaria
Cambia la hora de presentación a la zona horaria especificada por zona-horaria del host que es la fuente de las métricas de rendimiento, identificado mediante la opción -h (o --host) o -a (o --archive)

OPTIONS

-Z timezone, --timezone=timezone
Por defecto, las aplicaciones informan la hora del día según la zona horaria local del sistema donde se ejecuta la aplicación. La opción -Z (o --timezone) cambia la zona horaria a timezone en el formato de la variable de entorno TZ, como se describe en environ(7).
-D debugspec, --debug=debugspec
Establece las opciones de depuración de PCP a debugspec para habilitar diagnósticos y rastreo que son más útiles para los desarrolladores o al intentar diagnosticar el mal funcionamiento de una aplicación PCP. debugspec debe ser una lista separada por comas de nombres de opciones de depuración y/o enteros decimales, consulte pmdbg(1) para una descripción de los nombres y valores de las opciones admitidas.

En ausencia de una fuente de métricas en vivo o de archivo, se puede invocar una búsqueda heurística de archivos para el host local a través de la opción -O (o --origin). Al usar esta opción sin una fuente explícita de métricas, las herramientas de monitoreo intentan usar archivos de una ubicación de archivo del sistema como $PCP_LOG_DIR/pmlogger/`hostname`. Consulte la sección ESPECIFICACIÓN DE LA VENTANA DE TIEMPO a continuación para obtener detalles sobre la sintaxis aceptable para la opción de origen, pero una invocación típica en este modo sería -O today o --origin yesterday.

ESPECIFICACIÓN Y ALINEACIÓN DE INTERVALOS

La mayoría de las herramientas de PCP operan con muestreo o informes periódicos, y las opciones -t (o --interval) y -A (o --align) se pueden usar para controlar la duración del intervalo de muestra y la alineación de los tiempos de muestra.

-t interval, --interval=interval
Establece el intervalo de actualización o informe.

El argumento interval se especifica como una secuencia de uno o más elementos de la forma

number[units]
donde number es una constante entera o de punto flotante (analizada usando strtod(3)) y la units opcional es una de: seconds, second, secs, sec, s, minutes, minute, mins, min, m, hours, hour, h, days, day y d. Si la unit está vacía, se asume second.

Además, la versión en mayúsculas (o mixta) de cualquiera de las anteriores también es aceptable.

Los espacios en cualquier lugar del interval se ignoran, por lo que 4 days 6 hours 30 minutes, 4day6hour30min, 4d6h30m y 4d6.5h son equivalentes.

Múltiples especificaciones son aditivas, por ejemplo, ``1hour 15mins 30secs'' se interpreta como 3600+900+30 segundos.

-A align, --align=align
Por defecto, las muestras no están necesariamente alineadas en ninguna unidad natural de tiempo. La opción -A o --align se puede usar para forzar que la muestra inicial esté alineada en el límite de una unidad natural de tiempo. Por ejemplo, -A 1sec, -A 30min y --align 1hour especifican la alineación en segundos enteros, medias y horas enteras respectivamente.

El argumento align sigue la sintaxis de un argumento interval descrito anteriormente para la opción -t o --interval.

Tenga en cuenta que la alineación ocurre al avanzar el tiempo según sea necesario, y que -A (o --align) actúa como un modificador para avanzar tanto el inicio de la ventana de tiempo (consulte la siguiente sección) como la hora de origen (si se especifica la opción -O o --origin).

ESPECIFICACIÓN DE LA VENTANA DE TIEMPO

Muchas herramientas de PCP están diseñadas para operar en alguna ventana de tiempo de interés, por ejemplo, para definir un tiempo de terminación para el monitoreo en tiempo real o para definir un tiempo de inicio y fin dentro de un conjunto de archivos de PCP.

En ausencia de las opciones -O (o --origin) y -A (o --align) para especificar un origen de tiempo de muestra inicial y una alineación de tiempo (ver arriba), la aplicación PCP recuperará la primera muestra al inicio de la ventana de tiempo.

Las siguientes opciones se pueden usar para especificar una ventana de tiempo de interés.

-S starttime, --start=starttime
Por defecto, la ventana de tiempo comienza inmediatamente en modo de tiempo real, o coincide con la hora de inicio del conjunto de archivos de PCP en modo de archivo. La opción -S o --start se puede usar para especificar una hora posterior para el inicio de la ventana de tiempo.

El parámetro starttime se puede dar en una de tres formas (interval es el mismo que para la opción -t o --interval como se describe arriba, datetime se describe a continuación):

interval
Para especificar un desplazamiento desde la hora actual (en modo de tiempo real) o el principio de un conjunto de archivos de PCP (en modo de archivo), simplemente especifique el intervalo de tiempo como argumento. Por ejemplo, -S 30min establecerá el inicio de la ventana de tiempo exactamente 30 minutos a partir de ahora en modo de tiempo real, o exactamente 30 minutos desde el inicio de un conjunto de archivos de PCP.
-interval
Para especificar un desplazamiento desde el final de un conjunto de archivos de PCP, prefije el argumento interval con un signo menos. En este caso, el inicio de la ventana de tiempo precede a la hora del final del conjunto de archivos por el intervalo dado. Por ejemplo, -S -1hour establecerá el inicio de la ventana de tiempo exactamente una hora antes de la hora de la última muestra en un conjunto de archivos de PCP.
@datetime
Para especificar la fecha y hora del calendario (hora local en la zona horaria de informe) para el inicio de la ventana de tiempo, use la sintaxis de fecha y hora precedida por una arroba. Consulte la descripción de fecha y hora a continuación para obtener información detallada.
-T endtime, --finish=endtime
Por defecto, el final de la ventana de tiempo no tiene límites (en modo de tiempo real) o está alineado con la hora de finalización de un conjunto de archivos de PCP (en modo de archivo). La opción -T o --finish se puede usar para especificar una hora anterior para el final de la ventana de tiempo.

El parámetro endtime se puede dar en una de tres formas (interval es el mismo que para la opción -t o --interval como se describe arriba, datetime se describe a continuación):

interval
Para especificar un desplazamiento desde el inicio de la ventana de tiempo, simplemente use el intervalo de tiempo como argumento. Por ejemplo, -T 2h30m establecerá el final de la ventana de tiempo 2 horas y 30 minutos después del inicio de la ventana de tiempo.
-interval
Para especificar un desplazamiento hacia atrás desde la hora de finalización de un conjunto de archivos de PCP, prefije el argumento interval con un signo menos. Por ejemplo, -T -90m establecerá el final de la ventana de tiempo 90 minutos antes de la hora de la última muestra en un conjunto de archivos de PCP.
@datetime
Para especificar la fecha y hora del calendario (hora local en la zona horaria de informe) para el final de la ventana de tiempo, use la sintaxis de fecha y hora precedida por una arroba. Consulte la descripción de fecha y hora a continuación para obtener información detallada.
-O origin, --origin=origin
Por defecto, las muestras se obtienen desde el inicio de la ventana de tiempo (ver descripción de la opción -S o --start) hasta el final de la ventana de tiempo (ver descripción de la opción -T o --finish). La opción -O o --origin permite la especificación de un origen dentro de la ventana de tiempo que se utilizará como tiempo de muestra inicial. Esto es útil para el uso interactivo de una herramienta de PCP con la instalación de reproducción de video pmtime(1).

El argumento origin aceptado por -O (o --origin) se ajusta a la misma sintaxis y semántica que el argumento starttime para la opción -T (o --finish).

Por ejemplo, --origin -0 especifica que la posición inicial debe estar al final de la ventana de tiempo; esto es más útil cuando se desea reproducir "hacia atrás" dentro de la ventana de tiempo.

El argumento datetime para las opciones -O (o --origin), -S (o --start) y -T (o --finish) consiste en:
fecha hora zona día relativo
Una fecha puede ser: AA-MM-DD, MM/DD/AA, DD Mes AAAA, o Mes DD AAAA. Una hora puede ser: HH:MM:SS, HH:MM. HH:MM puede usar la convención de 12 horas (mediante un sufijo am o pm) o la de 24 horas. Un día de la semana puede ser un día de la semana escrito, opcionalmente precedido por un número ordinal como segundo martes. Una zona es un valor de zona horaria especificado por el comando tzselect(8). Un tiempo relativo puede ser una unidad de tiempo que: esté precedida por un número cardinal como 1 año o 2 meses, precedida por una de las palabras de tiempo this o last, o seguida por la palabra de tiempo ago. Un tiempo relativo también puede ser una de las palabras de tiempo: yesterday, today, tomorrow, now. Ejemplos de cadenas de fecha y hora son: 1996-03-04 13:07:47 EST Mon, 1996-03-05 14:07:47 EST -1hour, Mon Mar 4 13:07:47 1996, Mar 4 1996, Mar 4, Mar, 13:07:50 o 13:08.

Para campos de orden inferior faltantes, se asume el valor predeterminado de 0 para horas, minutos y segundos, 1 para el día del mes y enero para los meses. Por lo tanto, los siguientes son equivalentes: --start '@ Mar 1996' y --start '@ Mar 1 00:00:00 1996'.

Si faltan campos de orden superior, se completan comenzando con el año, mes y día de la hora actual (modo de tiempo real) o la hora de inicio del conjunto de archivos de PCP (modo de archivo) y avanzando el tiempo hasta que coincida con los campos especificados. Por lo tanto, por ejemplo, si la ventana de tiempo comienza por defecto en ``Mon Mar 4 13:07:47 1996'', entonces --start @13:10 corresponde a las 13:10:00 del lunes 4 de marzo de 1996, mientras que --start @10:00 corresponde a las 10:00:00 del martes 5 de marzo de 1996 (tenga en cuenta que es el día siguiente).

FECHAS Y ZONAS HORARIAS

Las fechas y horas se especifican mediante los argumentos de línea de comandos de las herramientas de PCP. Las fechas y horas también pueden especificarse para controlar el rango de tiempo de los datos de rendimiento que se van a extraer de los archivos de PCP que se van a recopilar. La sintaxis específica para las fechas y horas puede variar de una herramienta a otra, pero todas admiten fechas y horas en los siguientes formatos:

  • El formato de fecha y hora predeterminado es YYYY-MM-DDTHH:MM:SS.

  • Se admiten los nombres de los meses abreviados y completos (por ejemplo, "Jan", "Jan.", "January", "January.").

  • Se admiten los nombres de los días de la semana abreviados y completos (por ejemplo, "Mon", "Monday", "Monday.").

  • Los siguientes símbolos tienen significados especiales:

    °
    Grados.
    ±
    Desplazamiento del UTC (por ejemplo, +00:00).
    ¹
    Minutos.
    ²
    Segundos.

La opción -S o --startime especifica la hora de inicio, y la opción -T o --endtime especifica la hora de fin. Si solo se especifica una hora de inicio (o fin), se asume que la otra es la hora actual. Si no se especifica ninguna hora, se asume que tanto la hora de inicio como la hora de fin son la hora actual.

Los valores de fecha y hora pueden especificarse con precisión de segundo, milisegundo o microsegundo. Las herramientas de PCP intentarán deducir el formato y la granularidad de la entrada de fecha y hora proporcionada.

Una zona horaria se puede especificar mediante la opción -Z o --timezone. Si no se proporciona una zona horaria, las herramientas de PCP intentarán deducir la zona horaria de la información de la zona horaria del sistema operativo. Si la información de la zona horaria del sistema no está disponible, las herramientas de PCP utilizarán UTC como zona horaria predeterminada. Los valores de zona horaria pueden ser nombres de zonas horarias de la base de datos de zonas horarias IANA (por ejemplo, "America/Los_Angeles" o "Europe/London") o desplazamientos del UTC (por ejemplo, "+0000" o "-0800").

Cuando se utilizan varias herramientas de PCP juntas, pueden surgir diferencias en la forma en que se tratan las fechas, horas y zonas horarias. Siempre es una buena práctica verificar la documentación específica de cada herramienta para comprender cómo maneja estos valores.

Por ejemplo, si desea ver métricas de rendimiento para un período de dos horas que comenzó a las 9:30 AM en la zona horaria del Pacífico, podría utilizar un comando como:

$ pcp last -S 9:30AM -T 11:30AM -Z Pacific/Los_Angeles

Si la zona horaria no se incluye en una fecha y hora, existen varias interpretaciones disponibles según las otras opciones de línea de comandos utilizadas. El valor predeterminado es usar la zona horaria local en el sistema donde se está ejecutando la herramienta de PCP. Una opción -Z o --timezone especifica una zona horaria explícita, de lo contrario, una opción -z o --hostzone cambia la zona horaria a la zona horaria local en el host que es la fuente de las métricas de rendimiento.

MÉTRICAS DE RENDIMIENTO - IDENTIFICADORES, NOMBRES, VALORES

El número de nombres de métricas de rendimiento admitidos por PCP en la mayoría de las plataformas varía de varios cientos a varios miles. Las bibliotecas y aplicaciones de PCP utilizan un esquema de identificación interno que asocia de forma inequívoca un solo entero con cada métrica de rendimiento conocida. Este entero se conoce como Identificador de Métrica de Rendimiento, o PMID. Aunque no es un requisito, los PMID tienden a tener consistencia global en todos los sistemas, por lo que una métrica de rendimiento particular suele tener el mismo PMID.

Para todos los usuarios y la mayoría de las aplicaciones, el uso directo de los PMID sería inapropiado (esto limitaría el rango de métricas accesibles, haría que el código fuera difícil de mantener, obligaría a que la interfaz de usuario fuera particularmente barroca, etc.). Por lo tanto, se utiliza un Espacio de Nombres de Métricas de Rendimiento (PMNS) para proporcionar nombres externos y una clasificación jerárquica para las métricas de rendimiento. Un PMNS se representa como un árbol, donde cada nodo tiene una etiqueta, un puntero a un PMID (para nodos hoja) o un conjunto de nodos descendientes en el PMNS (para nodos no hoja).

Una etiqueta de nodo debe comenzar con un carácter alfabético, seguido de cero o más caracteres extraídos del alfabeto, los dígitos y el carácter ``_'' (guión bajo). Para los caracteres alfabéticos en una etiqueta de nodo, se distinguen mayúsculas y minúsculas.

Por convención, el nombre de una métrica de rendimiento se construye concatenando las etiquetas de los nodos en una ruta a través del PMNS desde el nodo raíz hasta un nodo hoja, con un ``.'' como separador. El nodo raíz en el PMNS no tiene etiqueta, por lo que todos los nombres comienzan con la etiqueta asociada con uno de los nodos descendientes debajo del nodo raíz del PMNS, por ejemplo kernel.percpu.syscall. Típicamente (aunque esto no es un requisito) habría como máximo un nombre para cada PMID en un PMNS. Por ejemplo kernel.all.cpu.idle y disk.dev.read son los nombres únicos para dos métricas de rendimiento distintas, cada una con un PMID único.

Grupos de PMID relacionados pueden ser nombrados al nombrar un nodo no hoja en el árbol PMNS, por ejemplo disk.

El PMNS local predeterminado utilizado por pmcd se encuentra en $PCP_VAR_DIR/pmns/root sin embargo, la variable de entorno PMNS_DEFAULT puede establecerse en la ruta completa de un PMNS diferente que luego se utilizará como PMNS local predeterminado.

La mayoría de las aplicaciones no utilizan el PMNS local directamente, sino que importan partes del PMNS según sea necesario del mismo lugar de donde se obtienen las métricas de rendimiento, es decir, de pmcd(1) para la monitorización en vivo o de un conjunto de archivos de PCP para la monitorización retrospectiva.

Para explorar el PMNS, utilice pminfo(1), o si está instalado el paquete GUI de PCP, las ventanas New Chart y Metric Search dentro de pmchart(1).

Algunas métricas de rendimiento tienen un valor singular. Por ejemplo, la memoria disponible o el número de cambios de contexto tienen un valor por fuente de métrica de rendimiento, es decir, un valor por host. El descriptor de métrica (metadatos) para cada métrica hace que este hecho sea conocido por las aplicaciones que procesan los valores de estas métricas de valor único.

Algunas métricas de rendimiento tienen un conjunto de valores o instancias en cada dominio de métrica de rendimiento que lo implementa. Por ejemplo, un valor por cada disco, un valor por cada proceso, un valor por cada CPU, o un valor por cada activación de una aplicación dada. Cuando una métrica tiene varias instancias, el PMNS no lo representa en los nombres de las métricas; en su lugar, una sola métrica puede tener un conjunto de valores asociado. Múltiples valores se asocian con los miembros de un dominio de instancia, de tal manera que cada instancia tiene un identificador de instancia único dentro del dominio de instancia asociado. Por ejemplo, el dominio de instancia ``por CPU'' puede usar los identificadores de instancia 0, 1, 2, 3, y así sucesivamente para identificar los procesadores configurados en el sistema. Internamente, los identificadores de instancia se codifican como valores binarios, pero cada dominio de métrica de rendimiento también admite cadenas correspondientes como nombres externos para los identificadores de instancia, y estos nombres se utilizan en la interfaz de usuario de las utilidades de PCP.

Múltiples métricas de rendimiento pueden asociarse con un único dominio de instancia. Por ejemplo, las métricas por proceso bajo proc comparten todas el mismo dominio de instancia.

PCP se encarga de que la información que describe los dominios de instancia sea exportada desde los dominios de métricas de rendimiento a las aplicaciones que requieren esta información. Las aplicaciones también pueden optar por recuperar valores para todas las instancias de una métrica de rendimiento, o para un subconjunto arbitrario de las instancias disponibles.

Los nombres de métricas y el concepto de dominio de instancia proporcionan dos dimensiones para la modelización de métricas de rendimiento. Este es un modelo claro y simple, sin embargo, en ocasiones no es suficiente. Por ejemplo, una métrica puede desear representar datos de mayor dimensión como contadores ``por CPU'' para cada proceso en ejecución. En estos casos, es común crear una instancia compuesta, donde el nombre se compone de cada componente con un separador en medio (por ejemplo, ``87245::cpu7'' podría usarse para separar el ID del proceso del ID de la CPU) para crear nombres de instancia aplanados. Adicionalmente, tales casos se benefician del uso de etiquetas de instancias de métricas para mostrar explícitamente los componentes separados (continuando el ejemplo anterior, se podrían usar etiquetas ``{"pid":87245,"cpu":7}'').

ESPECIFICACIONES DE MÉTRICAS DE RENDIMIENTO

En los archivos de configuración y (en menor medida) en las opciones de línea de comandos, las especificaciones de métricas se adhieren a las siguientes reglas de sintaxis para la mayoría de las herramientas. Consulte las páginas del manual específicas de la herramienta para conocer la sintaxis exacta admitida.

Si la fuente de las métricas de rendimiento es en tiempo real desde pmcd(1), entonces la sintaxis aceptada es
host:métrica[instancia1,instancia2,...]

Si la fuente de las métricas de rendimiento es un conjunto de archivos de PCP, entonces la sintaxis aceptada es
archivo/métrica[instancia1,instancia2,...]

Los componentes host:, archivo/ y [instancia1,instancia2,...] son opcionales.

El delimitador , en la lista de nombres de instancia puede ser reemplazado por espacio en blanco.

Los caracteres especiales en los nombres de instancia pueden ser escapados rodeando el nombre entre comillas dobles o anteponiendo el carácter con una barra invertida.

Se ignora el espacio en blanco en todas partes, excepto dentro de un nombre de instancia entre comillas.

Una instancia vacía se ignora silenciosamente y, en particular, ``[]'' es lo mismo que ninguna instancia, mientras que ``[one,,,two]'' se analiza como especificar solo las dos instancias ``one'' y ``two''.

Como caso especial, si el host es el carácter único ``@'' entonces esto se refiere a una fuente PM_CONTEXT_LOCAL, ver pmNewContext(3).

CONEXIONES SEGURAS A PMCD

Desde la versión 3.6.11 de PCP, un monitor puede solicitar explícitamente una conexión segura a un host colector que ejecute pmcd(1) o pmproxy(1) utilizando la marca de contexto PM_CTXFLAG_SECURE. Si el host colector de PCP admite esta característica (consulte la métrica pmcd.feature.secure para confirmarla), se puede establecer una conexión TLS/SSL (Transport Layer Security o Secure Sockets Layer) que utiliza criptografía de clave pública y técnicas relacionadas. Estas características pretenden prevenir el espionaje y la manipulación de datos por parte de un tercero malicioso, además de proporcionar autenticación del lado del servidor (identificación segura de un servidor por parte de un cliente) que puede utilizarse para proteger contra ataques de intermediario (man-in-the-middle).

Una conexión segura a pmcd requiere el uso de autenticación basada en certificados. Las características de seguridad ofrecidas por pmcd y pmproxy se implementan utilizando las API y utilidades de OpenSSL. La herramienta openssl(1) se puede utilizar para crear certificados adecuados para establecer confianza entre el monitor de PCP y los hosts colectores.

Una descripción completa está fuera del alcance de este documento, consulte las secciones ENTORNO PCP, ARCHIVOS y VER TAMBIÉN para obtener información detallada. Esto incluye enlaces a tutoriales sobre los pasos involucrados en la configuración de las características de seguridad disponibles.

ESPECIFICACIÓN DE HOST PMCD

En ausencia de una especificación explícita de nombre de host, la mayoría de las herramientas utilizarán por defecto el host local en modo de actualización en vivo. En las versiones de PCP posteriores a la 3.8.4, esto resulta en la selección de un protocolo local eficiente, típicamente un socket de dominio Unix. Si se utiliza esta opción (que también se puede solicitar explícitamente a través de la especificación de host unix: descrita a continuación), es importante tener en cuenta que todas las conexiones se autenticarán automáticamente. En otras palabras, las credenciales del usuario que invoca una herramienta cliente se pondrán automáticamente a disposición de pmcd(1) y todas sus PMDA, en nombre del usuario, de modo que los resultados puedan personalizarse para los niveles de privilegios de usuarios individuales.

Por supuesto, también se pueden proporcionar nombres de hosts remotos que ejecutan el demonio pmcd(1) para solicitar el uso de un host remoto. La forma más básica de especificación de host de pmcd es un simple nombre de host, que posiblemente incluya el nombre de dominio si es necesario. Sin embargo, esto se puede extender de varias maneras para refinar aún más los atributos de la conexión realizada a pmcd.

El número de puerto de pmcd y también el nombre de host y el número de puerto opcionales de pmproxy(1), pueden proporcionarse como parte de la especificación del host, desde la versión 3.0 de PCP. Estos reemplazan (y anulan) las variables de entorno antiguas PMCD_PORT, PMPROXY_HOST y PMPROXY_PORT.

CONNECTION EXAMPLES

This section provides examples of how to connect to a Performance Co-Pilot (PCP) collector (pmcd(1)) using the --host option. These examples illustrate various ways of specifying the target host, including:

  • Directly specifying the hostname or IP address.
  • Specifying the port number for pmcd.
  • Routing the connection through a firewall, and with IPv6 and IPv4 addresses as shown.


$ pcp --host nas1.acme.com:44321,4321@firewall.acme.com:44322
$ pcp --host nas1.acme.com:44321@firewall.acme.com:44322
$ pcp --host nas1.acme.com:44321@firewall.acme.com
$ pcp --host nas1.acme.com@firewall.acme.com
$ pcp --host nas1.acme.com:44321
$ pcp --host [fe80::2ad2:44ff:fe88:e4f1%p2p1]
$ pcp --host 192.168.0.103

In addition, ``connection attributes'' can also be specified. These include username, password (can be given interactively and may depend on the authentication mechanism employed), whether to target a specific running container, whether to use secure (encrypted) or native (naked) protocol, and so on. The previous examples all default to native protocol, and use no authentication. This can be altered, as in the following examples.


$ pcp --host pcps://app2.acme.com?container=cae8e6edc0d5
$ pcp --host pcps://nas1.acme.com:44321?username=tanya&method=gssapi
$ pcp --host pcps://nas2.acme.com@firewalls.r.us?method=plain
$ pcp --host pcp://nas3.acme.com
$ pcp --host 192.168.0.103?container=cae8e6edc0d5,method=scram-sha-256
$ pcp --host unix:
$ pcp --host local:

The choice of authentication method, and other resulting parameters like username, optionally password, etc, depends on the SASL2 configuration used by each (remote) pmcd. Tutorials are available specifying various aspects of configuring the authentication module(s) used, these fine details are outside the scope of this document.

In all situations, host names can be used interchangeably with IPv4 or IPv6 addressing (directly), as shown above. In the case of an IPv6 address, the full address must be enclosed by square brackets and the scope (interface) must also be specified.

The final local: example above is now the default for most tools. This connection is an automatically authenticated local host connection on all platforms that support Unix domain sockets. No password is required and authentication is automatic. This is also the most efficient (lowest overhead) communication channel.

The difference between unix: and local: is that the former is a strict Unix domain socket specification (connection fails if it cannot connect that way), whereas the latter has a more forgiving fallback to using localhost (i.e. a regular Inet socket connection is used when Unix domain socket connections are unavailable).

Archivo de control para pmcd(1).

Opciones de línea de comandos pasadas a pmcd(1) cuando se inicia desde $PCP_RC_DIR/pmcd. Todas las líneas de opciones de línea de comandos deben comenzar con un guion como primer carácter. Este archivo también puede contener configuraciones de variables de entorno del formato "VARIABLE=valor".

Ubicación de las utilidades de PCP para recopilar y mantener archivos de PCP, texto de ayuda de PMDA, archivos PMNS, etc.

Ubicación predeterminada de los archivos de registro para pmcd(1), directorio actual para los PMDA en ejecución. Los archivos generados por pmlogger(1) generalmente se encuentran debajo de $PCP_LOG_DIR/pmlogger.

Registro de diagnóstico y estado para el proceso pmcd(1) en ejecución actual. El primer lugar al que acudir cuando hay problemas asociados con pmcd.
$PCP_LOG_DIR/pmcd/pmcd.log.prev
Registro de diagnóstico y estado para la instancia anterior de pmcd(1).
$PCP_LOG_DIR/NOTICES
Registro de inicios, paradas, adiciones y eliminaciones de pmcd(1) y PMDA.
$PCP_VAR_DIR/config
Contiene directorios de archivos de configuración para varias herramientas de PCP.
$PCP_SYSCONF_DIR/pmcd/rc.local
Script local para controlar las acciones de arranque, apagado y reinicio de PCP.
$PCP_VAR_DIR/pmns
Directorio que contiene el conjunto de archivos PMNS para todos los PMDA instalados.
$PCP_VAR_DIR/pmns/root
El archivo PMNS de ASCII PMNS(5) exportado por pmcd(1) por defecto. Este PMNS es el superconjunto de todos los demás archivos PMNS instalados en $PCP_VAR_DIR/pmns.

Archivo de control para las instancias de pmlogger(1) iniciadas desde $PCP_RC_DIR/pmlogger y/o gestionadas por pmlogger_check(1) y pmlogger_daily(1) como parte de una configuración de recopilación de archivos PCP de producción.

ENTORNO

Además del entorno de ejecución de PCP y las variables de configuración descritas en la sección ENTORNO DE PCP a continuación, las siguientes variables de entorno se aplican a todas las instalaciones.

Tenga en cuenta que la mayoría de los usos de estas variables de entorno están optimizados para verificar el entorno solo la primera vez que la variable podría ser utilizada. Como el entorno generalmente no se verifica de nuevo, la única estrategia segura es asegurarse de que todas las variables de entorno relacionadas con PCP se establezcan antes de la primera llamada a cualquiera de las bibliotecas de PCP.

PCP_ALLOW_BAD_CERT_DOMAIN
Cuando se establece, permite a los clientes aceptar certificados con nombres de dominio que no coinciden sin solicitarlo cuando son enviados por pmcd u otros componentes del servidor. Ver PCP_SECURE_SOCKETS.
PCP_ALLOW_SERVER_SELF_CERT
Cuando se establece, permite a los clientes aceptar certificados autofirmados sin solicitarlo cuando son enviados por pmcd u otros componentes del servidor. Ver PCP_SECURE_SOCKETS.
PCP_CONSOLE
Cuando se establece, esto cambia la consola predeterminada de /dev/tty (en Unix) o CON: (en Windows) a la consola especificada. El valor especial de none se puede usar para indicar que no hay consola disponible para su uso. Esto se utiliza en lugares donde las herramientas basadas en consola necesitan interactuar con el usuario, y en particular se utiliza cuando se está realizando la autenticación.
PCP_DEBUG
Cuando se establece, esta variable proporciona una alternativa a la opción de línea de comandos -D descrita anteriormente para inicializar las opciones de diagnóstico y depuración para aplicaciones que utilizan pmGetOptions(3) para procesar opciones y argumentos de línea de comandos. El valor de $PCP_DEBUG es el mismo que para la opción de línea de comandos -D, es decir, una lista separada por comas de nombres de opción(es) de depuración y/o enteros decimales, ver pmdbg(1) para una descripción de los nombres y valores de opciones admitidos.
PCP_DERIVED_CONFIG
Cuando se establece, esta variable define una lista separada por dos puntos de archivos y/o directorios (la sintaxis es la misma que para la variable $PATH para sh(1)). Los componentes se expanden a una lista de archivos de la siguiente manera: si un componente de $PCP_DERIVED_CONFIG es un archivo, entonces ese archivo se agrega a la lista; de lo contrario, si un componente es un directorio, se utiliza el descenso recursivo para enumerar todos los archivos debajo de ese directorio y estos se agregan a la lista.

Se asume que cada archivo en la lista resultante contiene definiciones de métricas derivadas según la sintaxis descrita en pmLoadDerivedConfig(3), y estas se cargan en orden.

Las métricas derivadas se pueden utilizar para extender las métricas disponibles con nuevas métricas (derivadas) utilizando expresiones aritméticas simples.

Si PCP_DERIVED_CONFIG está establecido, las definiciones de métricas derivadas se procesan automáticamente cada vez que se establece una nueva fuente de métricas de rendimiento (es decir, cada vez que se llama a un pmNewContext(3)) o cuando se realizan solicitudes contra el PMNS.

Cualquier componente en la lista $PCP_DERIVED_CONFIG o en la lista expandida de archivos que no sea un archivo, o que no sea un directorio o que no sea accesible (debido a permisos o un enlace simbólico incorrecto) será ignorado silenciosamente.

PCP_IGNORE_MARK_RECORDS
Cuando se registran archivos de registro de PCP, puede haber brechas temporales asociadas con discontinuidades en la serie temporal de datos registrados, por ejemplo, cuando pmcd(1) se reinicia o cuando se concatenan varios archivos con pmlogextract(1). PCP ENVIRONMENT

The Performance Co-Pilot environment is configured using the file /etc/pcp.conf (for global settings) and environment variables.

A number of environment variables are used by PCP. On each installation, the file /etc/pcp.conf contains the local values for these variables. The $PCP_CONF variable may be used to specify an alternative configuration file, as described in pcp.conf(5).

For environment variables affecting PCP tools, see pmGetOptions(3).
