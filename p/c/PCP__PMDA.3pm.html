PMDA(3) Documentación de Perl Contribuida por el Usuario PMDA(3)

NOMBRE

PCP::PMDA - Extensión de Perl para Agentes de Dominio de Métricas de Rendimiento

SINOPSIS

use PCP::PMDA;
$pmda = PCP::PMDA->new('mi_nombre', $MI_DOMINIO);
$pmda->connect_pmcd;
$pmda->add_metric($pmid, $tipo, $indom, $sem, $unidades, 'nombre', '', '');
$pmda->add_indom($indom, [0 => 'blanco', 1 => 'negro', ...], '', '');
$pmda->set_fetch(\&metodo_obtener);
$pmda->set_refresh(\&metodo_refrescar);
$pmda->set_instance(\&metodo_instancia);
$pmda->set_fetch_callback(\&metodo_callback_obtener);
$pmda->set_store_callback(\&metodo_callback_almacenar);
$pmda->set_user('pcp');
$pmda->run;

DESCRIPCIÓN

El módulo Perl PCP::PMDA contiene los enlaces de lenguaje para construir Agentes de Dominio de Métricas de Rendimiento (PMDAs) utilizando Perl. Cada PMDA exporta datos de rendimiento para un dominio específico, por ejemplo el kernel del sistema operativo, routers Cisco, una base de datos, una aplicación, etc.

MÉTODOS

PCP::PMDA->new(nombre, dominio)
Constructor de la clase PCP::PMDA. nombre es una cadena que se convierte en el nombre del PMDA para los mensajes y prefijo por defecto para los nombres de los archivos externos utilizados por el PMDA. dominio es un número de dominio entero para el PMDA, usualmente del registro de números de dominio que se encuentra en $PCP_VAR_DIR/pmns/stdpmid.
$pmda->run()
Una vez que toda la configuración local está completa (es decir, se registran los dominios de instancia y las métricas, se registran las callbacks - como se discute a continuación) el PMDA debe conectarse a pmcd(1) para completar su inicialización y empezar a responder a las solicitudes de los clientes para sus métricas. Este es el rol que desempeña run, y al invocarlo toda la interacción dentro del PMDA se realiza a través de rutinas de callback (es decir, en circunstancias normales, la rutina run no retorna).

El comportamiento del método run es diferente en presencia de las variables de entorno PCP_PERL_PMNS o PCP_PERL_DOMAIN. Estas pueden usarse para generar los archivos de namespace o número de dominio, que se utilizan como parte del proceso de instalación del PMDA.

$pmda->connect_pmcd()
Permite al PMDA configurar el canal IPC a pmcd(1) y completar el handshake de credenciales con pmcd(1). Si connect_pmcd no se llama explícitamente, la configuración y el handshake se realizarán al llamar al método run.

La ventaja de llamar explícitamente a connect_pmcd temprano en la vida del PMDA es que esto reduce el riesgo de un timeout fatal durante el handshake de credenciales, lo que puede ser un problema si el PMDA tiene trabajo considerable que hacer, por ejemplo, determinar qué métricas y dominios de instancia están disponibles, antes de llamar a run.

$pmda->add_indom(indom, insts, ayuda, ayudalarga)
Define un nuevo dominio de instancia. El identificador del dominio de instancia es indom, que es un entero y único entre todos los dominios de instancia para un único PMDA.

Las instancias del dominio de instancia se definen por insts, que pueden especificarse como una lista o un hash.

En forma de lista, el contenido de la lista debe proporcionar pares consecutivos de identificador (un entero, único entre todas las instancias en el dominio de instancia) y nombre de instancia externo (una cadena, debe ser único hasta el primer espacio, si lo hay, entre todas las instancias en el dominio de instancia). Por ejemplo:

@colores = [0 => 'rojo', 1 => 'verde', 2 => 'azul'];

En forma de hash, el identificador de instancia externo (cadena) se usa como clave del hash. Se puede almacenar un valor arbitrario junto con la clave (este valor se usa a menudo como un lugar conveniente para mantener el último valor para cada instancia de métrica, por ejemplo).

%intervalos_tiempo = ('seg' => 42, 'min' => \&func_min, 'hora' => '0');

Las cadenas ayuda y ayudalarga se interpretan como el texto de ayuda de una línea y expandido que se utilizará para este dominio de instancia, como se describe más adelante en pmLookupInDomText(3).

Consulte también la discusión de replace_indom() a continuación para obtener más detalles sobre la manipulación de dominios de instancia.

$pmda->add_metric(pmid, tipo, indom, sem, unidades, nombre, ayuda, ayudalarga)
Define una nueva métrica identificada por el PMID pmid y el nombre completo de la métrica nombre.

Los metadatos de la métrica se definen por tipo, indom, sem y unidades y estos parámetros se utilizan para configurar la estructura pmDesc como se describe en pmLookupDesc(3).

Las cadenas ayuda y ayudalarga se interpretan como el texto de ayuda de una línea y expandido que se utilizará para la métrica, como se describe más adelante en pmLookupText(3).

$pmda->replace_indom(indice, insts)
Cada vez que un dominio de instancia identificado por indice, registrado previamente usando add_indom(), cambia de alguna manera, este cambio debe reflejarse reemplazando el mapeo existente con uno nuevo (insts).

El mapeo de reemplazo debe ser un hash si el dominio de instancia se registró inicialmente con add_indom() como un hash, de lo contrario debe ser una lista.

Consulte la discusión anterior sobre add_indom() sobre estos dos tipos diferentes de definiciones de dominios de instancia.

$pmda->load_indom(indice)
Cuando se usan dominios de instancia basados en hash, los cambios se persisten automáticamente al usar replace_indom() - este indom persistido se puede restaurar (por ejemplo, al inicio) usando esta interfaz.

El dominio de instancia a cargar se identifica por indice, registrado previamente usando add_indom().

Consulte la discusión anterior sobre add_indom() sobre los dos tipos diferentes de definiciones de dominios de instancia - solo se persisten los dominios de instancia basados en hash.

$pmda->add_pipe(comando, callback, datos)
Permite que los datos se inyecten en el PMDA usando una pipe(2).

El comando dado se ejecuta al principio de la vida del PMDA, y se forma una tubería entre el PMDA y el comando. Se asume salida orientada a líneas (de lo contrario ocurrirá truncamiento), y al recibir cada línea de texto en la tubería, se llamará a la función callback.

El parámetro opcional datos se puede usar para especificar datos adicionales para pasar a la rutina de callback.

$pmda->add_sock(hostname, puerto, callback, datos)
Crea una conexión de socket(2) al par hostname, puerto. Cada vez que llegan datos (como arriba, un protocolo orientado a líneas es lo mejor) se llamará a la función callback.

El parámetro opcional datos se puede usar para especificar datos adicionales para pasar a la rutina de callback.

Se devolverá un identificador opaco del tamaño de un entero para el socket, que posteriormente se puede usar en llamadas a put_sock() como se discute a continuación.

$pmda->put_sock(id, salida)
Escribe una cadena de salida al socket identificado por id, que debe referirse a un socket registrado previamente usando add_sock().
$pmda->add_tail(archivo, callback, datos)
Monitorea el archivo dado para la llegada de información recién añadida. Se asume entrada orientada a líneas (de lo contrario ocurrirá truncamiento), y al recibir cada línea de texto en la tubería, se llamará a la función callback.

El parámetro opcional datos se puede usar para especificar datos adicionales para pasar a la rutina de callback.

Esta interfaz se encarga del problema de que el archivo sea renombrado (como en la rotación de archivos de registro diarios), e intentará redirigir automáticamente la información del nuevo archivo de registro si esto ocurre.

$pmda->add_timer(timeout, callback, datos)
Registra un temporizador con el PMDA, de modo que al expirar un timeout se llamará a una rutina de callback. Este es un temporizador repetitivo.

El parámetro opcional datos se puede usar para especificar datos adicionales para pasar a la rutina de callback.

$pmda->err(mensaje)
Reporta un mensaje de error con fecha y hora en el archivo de registro del PMDA.
$pmda->error(mensaje)
Reporta un mensaje de error con fecha y hora en el archivo de registro del PMDA.
$pmda->log(mensaje)
Reporta un mensaje informativo con fecha y hora.

PCP::PMDA(3pm) — Arch manual pages

NAME

PCP::PMDA - Perl bindings for Performance Metrics Domain Agents

SYNOPSIS

    use PCP::PMDA;
    my $pmda = PCP::PMDA->new(domain=>100);
    # ... set callbacks and register metrics ...
    $pmda->run();

DESCRIPTION

This module provides a Perl API to create Performance Metrics Domain Agents (PMDAs) for the Performance Co-Pilot (PCP) framework. A PMDA is a daemon that exports performance metrics from a specific subsystem to the PCP collector daemon, pmcd(1).

Using this module, PMDAs can be implemented entirely in Perl, allowing for rapid development and easier integration with existing Perl codebases.

The typical lifecycle of a PMDA implemented with this module is:

  1. Instantiate the PCP::PMDA(3pm) object.
  2. Register necessary callback functions for fetching metric values, discovering instances, and handling configuration.
  3. Register the metrics that the PMDA will export using helper functions like PCP::PMDA::add_metric().
  4. Enter the main event loop using the PCP::PMDA::run() method, which listens for requests from pmcd(1).

See the PCP::PMDA(3pm) documentation for detailed information on the API.

METHODS

$pmda = PCP::PMDA->new(domain => $domain_num, [debug => $debug_mask])
Constructs and initializes a new PCP::PMDA(3pm) object. The required domain argument specifies the unique domain number for this PMDA. The optional debug argument can be used to enable debugging output, similar to the -D option for other PCP clients. See the DEBUGGING section below.
$pmda->run()
Starts the PMDA's main event loop, listening for connections and requests from pmcd(1). This method typically runs until the PMDA is terminated.
$pmda->log(level, message)
Logs a message to the PMDA log file. The level can be one of LOG_INFO, LOG_DEBUG, LOG_ERR, LOG_WARN, or LOG_NOTICE. The message is formatted and written to the PMDA log file.
$pmda->set_fetch_callback(cb_function)
Registers a callback function, similar to pmdaSetFetchCallBack(3). This function is called when pmcd(1) requests metric values.
$pmda->set_fetch(function)
Registers a fetch function, as used by pmdaInit(3).
$pmda->set_instance(function)
Registers an instance function, as used by pmdaInit(3).
$pmda->set_refresh(function)
Registers a refresh function, which will be called once per metric cluster, during the fetch operation. Only clusters being requested during this fetch will be refreshed, allowing selective metric value updates within the PMDA.
$pmda->set_store_callback(cb_function)
Registers a store function, used indirectly by pmdaInit(3). The cb_function is called once for each metric/instance pair into which a pmStore(3) is performed.
$pmda->set_inet_socket(port)
Specifies the IPv4 socket port to be used for communication with pmcd(1).
$pmda->set_ipv6_socket(port)
Specifies the IPv6 socket port to be used for communication with pmcd(1).
$pmda->set_unix_socket(socket_name)
Specifies the filesystem socket_name path to be used for communication with pmcd(1).
$pmda->set_user(username)
Runs the PMDA under the username user account, instead of the default (root) user.

HELPER METHODS

pmda_pmid(cluster, item)
Constructs a Performance Metric Identifier (PMID) from the domain number (passed as an argument to the new constructor), the cluster (an integer in the range 0 to 2^12-1) and the item (an integer in the range 0 to 2^10-1).

Every performance metric exported from a PMDA must have a unique PMID.

pmda_pmid_name(cluster, item)
Performs a reverse metric identifier to name lookup - given the metric cluster and item numbers, returns the metric name string.
pmda_pmid_text(cluster, item)
Returns the one-line metric help text string - given the metric cluster and item numbers, returns the help text string.
pmda_inst_name(index, instance)
Performs a reverse instance identifier to instance name lookup for the instance domain identified by index. Given the internal instance identifier, returns the external instance name string.
pmda_inst_lookup(index, instance)
Given an internal instance identifier (key) for the instance domain identified by index with an associated indom hash, returns the value associated with that key. The value can be any scalar value (this includes references, of course, so complex data structures can be referenced).
pmda_units(dim_space, dim_time, dim_count, scale_space, scale_time, scale_count)
Constructs a pmUnits structure suitable for registering a metrics metadata via add_metric().
pmda_config(name)
Looks up the value for configuration variable name from the /etc/pcp.conf file, using pmGetConfig(3).
pmda_uptime(now)
Returns a human-readable uptime string, based on now seconds since the epoch.
pmda_long()
Returns either PM_TYPE_32 or PM_TYPE_64 depending on the platform size for a signed long integer.
pmda_ulong()
Returns either PM_TYPE_U32 or PM_TYPE_U64 depending on the platform size for an unsigned long integer.
pmda_install()
Boolean result indicating whether PMDA installation is in progress, or if this is an actual PMDA invocation via pmcd(1).

MACROS

Most of the PM_* macros from the PCP C headers are available.

For example the type of a metric's value may be directly specified as one of PM_TYPE_32, PM_TYPE_U32, PM_TYPE_64, PM_TYPE_U64, PM_TYPE_FLOAT, PM_TYPE_DOUBLE, PM_TYPE_STRING or PM_TYPE_NOSUPPORT.

DEBUGGING

Perl PMDAs do not follow the -D convention of other PCP applications for enabling run-time diagnostics and tracing. Rather the environment variable PCP_PERL_DEBUG needs to be set to a string value matching the syntax accepted for the option value for -D elsewhere, see pmSetDebug(3).

This requires a little trickery. The pmcd(1) configuration file (PCP_PMCDCONF_PATH from /etc/pcp.conf) needs hand editing. This is best demonstrated by example.

Replace this line

foo  242  pipe  binary  python  /somepath/foo.py

with

foo  242  pipe  binary  python  \
    sh -c "PCP_PERL_DEBUG=pdu,fetch /usr/bin/python /somepath/foo.py"
