Sintaxis Pegex

El término "Pegex" puede usarse para referirse tanto al Framework de Parseo Pegex como a la Sintaxis del Lenguaje de Gramática Pegex que se utiliza para escribir archivos de gramática Pegex. Este documento detalla la Sintaxis Pegex.

Pegex es un lenguaje auto-hospedado. Esto significa que la gramática para definir el Lenguaje Pegex está escrita en el propio Lenguaje Pegex. Puedes verlo tú mismo aquí: https://github.com/ingydotnet/pegex-pgx/blob/master/pegex.pgx.

Te animo a que eches un vistazo rápido a ese enlace incluso ahora. Una gramática Pegex (como esta) consta de 2 partes: una sección meta y una sección de reglas.

La sección meta solo contiene atributos meta de palabra clave/valor sobre la gramática. Cosas como el nombre y la versión de la gramática.

La verdadera sustancia de una gramática Pegex reside en sus reglas. La primera regla de la gramática anterior es (básicamente):

grammar: meta_section rule_section

Lo que dice es que una gramática ES una sección meta seguida por una sección de reglas. ¡Pero bueno, eso ya lo sabíamos!

Sección Meta

Las declaraciones meta al principio de un archivo de gramática se ven así:

%palabraClavePegex valor

Veamos la parte superior de la gramática pegex.pgx:

# ¡Esta es la gramática Pegex para las gramáticas Pegex!
%grammar pegex
%version 0.1.0

Esto define dos valores meta: "grammar" y "version", que especifican el nombre y la versión de la gramática, respectivamente.

También notarás que la primera línea es un comentario. Los comentarios comienzan con un "#" y continúan hasta el final de la línea. Los comentarios están permitidos casi en cualquier lugar de la gramática, tanto en sus propias líneas, después de las declaraciones, e incluso dentro de las definiciones de expresiones regulares como veremos más adelante.

La Sección Meta de Pegex termina cuando comienza la Sección de Reglas de Pegex (con la primera definición de regla).

Sección de Reglas

El resto de una gramática Pegex es un conjunto de reglas nombradas. Cada regla es un nombre de regla, seguido de un ':', seguido de la definición de la regla, seguido de un ';' o una nueva línea.

Aquí hay un par de reglas de la gramática pegex.pgx. (Estas son las reglas que comienzan a definir una regla).

rule_definition:
    rule_start
    rule_group
    ending
rule_start: /
    ( rule_name )     # Captura el nombre de la regla
    BLANK*
    COLON -
/

Las definiciones de reglas son expresiones infijas. Consisten en tokens separados por operadores, con paréntesis para desambiguar la precedencia de enlace. Hay 3 tipos de tokens distintos y 3 operadores.

Los 3 tipos de tokens son: referencia a regla, expresión regular y mensaje de error. Los 3 operadores son Y (' '), O ('|') y ALT ('%', '%%').

Aquí hay un ejemplo de una gramática Pegex para parsear JSON:

json: hash | array
array: / LSQUARE / ( node* % / COMMA / ) (
    / RSQUARE / | `falta ']'` )

Esto dice: "json es un hash o un array. array es '[', cero o más nodos separados por comas, y un ']'. error si no hay ']'".

"hash", "array" y "node" son referencias a reglas, lo que significa que se refieren a reglas nombradas dentro de la gramática que deben coincidir en ese punto. El texto rodeado por un par de caracteres '/' forma una expresión regular. El texto rodeado por comillas invertidas es un mensaje de error.

"LSQUARE", "RSQUARE" y "COMMA" también son referencias a reglas. Las reglas pueden ser referenciadas dentro de expresiones regulares, siempre y cuando se refieran a expresiones regulares en sí mismas. De esta manera, las expresiones regulares grandes pueden ensamblarse a partir de otras más pequeñas, lo que conduce a la reutilización y la legibilidad. Finalmente, el '*' después de "node" se llama "cuantificador". Más sobre eso más adelante.

Referencias a Reglas

Una referencia a regla es el nombre de una regla entre corchetes angulares. Los corchetes son generalmente opcionales. Dentro de una expresión regular, una referencia a regla sin "<>" debe ir precedida por un carácter de espacio en blanco.

<nombre_subregla>
nombre_subregla

Cuando se usa fuera de una expresión regular, una referencia puede tener varios modificadores de prefijo. Ten en cuenta que los corchetes angulares no son necesarios aquí, pero añaden legibilidad.

=regla  # Aserto de ancho cero positivo (look-ahead)
!regla  # Aserto de ancho cero negativo (look-ahead)
.regla  # Saltar (es decir: parsear pero no capturar un subpatrón)
-regla  # Plano (aplanar las capturas de array)
+regla  # Siempre envolver

(Saltar y envolver se explican en [Valores de Retorno].)

Una referencia también puede tener varios cuantificadores sufijados. Similar a la sintaxis de expresiones regulares, un cuantificador indica cuántas veces debe coincidir una regla (referencia).

regla?      # opcional
regla*      # 0 o más veces
regla+      # 1 o más veces
<regla>8    # exactamente 8 veces
<regla>2+   # 2 o más veces
<regla>2-3  # 2 o 3 veces
<regla>0-6  # 0 a 6 veces

Ten en cuenta que debes usar corchetes angulares si estás usando un modificador numerado:

regla8    # ¡INCORRECTO! Coincidiría con la regla "regla8".
regla2+   # ¡INCORRECTO! Coincidiría con la regla "regla2", 1 o más veces.
regla2-3  # ¡INCORRECTO! Error de sintaxis de Pegex

Hay un conjunto especial de "Átomos" predefinidos que se refieren a fragmentos de expresiones regulares. Los átomos existen para cada carácter de puntuación y para caracteres que se encuentran comúnmente en expresiones regulares. Los átomos mejoran la legibilidad en los textos de gramática y permiten que caracteres especiales (como la barra o el numeral) se utilicen como sintaxis de Pegex.

Por ejemplo, una expresión regular para coincidir con un comentario podría ser '#' seguido de cualquier cosa, seguido de una nueva línea. En Pegex, escribirías:

comentario: / HASH CUALQUIER* FIN_LINEA /

en lugar de:

comentario: /#.*\r?\n/

Pegex compilaría lo primero en lo segundo.

Aquí hay algunos átomos:

GUION    # -
MAS      # +
tilde   # ~
barra   # /
numeral  # # (literal)
interrogacion # ? (literal)
asterisco # * (literal)
parentesis_izq # ( (literal)
parentesis_der # ) (literal)
PALABRA    # \w
ESPACIO_BLANCO # \s

La lista completa se puede encontrar en el [código fuente de Átomos|<https://metacpan.org/source/Pegex::Grammar::Atoms].>

Expresiones Regulares

En Pegex, llamamos a la sintaxis de una expresión regular una "regex". Es decir, cuando se usa el término "regex", se refiere a la sintaxis de Pegex, y cuando se usa el término "expresión regular", se refiere a la expresión regular real en la que se compila la regex.

Una regex es una cadena dentro de barras inclinadas.

/expresion_regular/

La sintaxis de expresiones regulares sigue en su mayoría a Perl, con las siguientes excepciones:

# Cualquier regla entre corchetes angulares se referencia en la regex
/ ( <regla1> | 'no_regla' ) /  # 'no_regla' se interpreta literalmente
# La sintaxis implica un modificador /x, por lo que los espacios en blanco y los comentarios
# se ignoran.
/ (
    regla1+   # Coincidir con regla1 una o más veces
    |
    regla2
) /
# Los espacios en blanco se declaran con guion y signo más.
/ - regla3 + /  # - = \s*, + = \s+, etc.
# Cualquier sintaxis (?XX ) puede tener el signo de interrogación eliminado
/ (: a | b ) /  # igual que / (?: a | b ) /

Mensaje de Error

Un mensaje de error es una cadena entre comillas invertidas. Si el analizador llega a un mensaje de error en la gramática, lanza un error de análisis con ese mensaje.

`mensaje de error`

Operadores

Los operadores de Pegex en orden de precedencia descendente son: ALT, AND y OR.

AND y OR son los operadores más comunes. AND se representa por la ausencia de un operador. Como en estas reglas:

r1: <a><b>
r2: a b

Ambas son iguales. Significan la regla "a" Y (seguida inmediatamente por) la regla "b".

OR significa coincidir una o la otra.

r: a | b | c

significa coincidir la regla "a" O la regla "b" O la regla "c". Las reglas se comprueban en orden y si una coincide, las otras se omiten.

Pegex::Syntax(3pm)

Pegex Syntax

This section details the syntax of the Pegex module.

Meta Section

The meta section is defined by the "meta" keyword. It contains rules that are outside of the main grammar and are used for configuration or metadata.

meta:
  version: '1.0'
  description: 'A simple grammar example'

Rule Section

The rule section defines the grammar rules. Rules are defined with a name, followed by a colon, and then the rule definition. The rule definition can be a sequence of terminals and non-terminals, alternatives, or other constructs.

rule_name:
  term1 term2 (term3)? term4* term5+

Terminals are literal strings or regular expressions. Non-terminals are other rule names.

Optional elements are denoted by "?". Zero or more repetitions are denoted by "*". One or more repetitions are denoted by "+".

Alternatives are denoted by "|".

rule_name:
  term1 | term2 | term3

The "%%" means that a trailing separator is optional.

r: a+ %% b

would match these:

a
ab
aba
abab

ANY operators take precedence over everything else, similar to other parsers. These rules have the same binding precedence:

r1: a b | c % d
r2: (a b) | (c % d)

Parens are not only used for indicating binding precedence; they also can create quantifiable groups:

r1: (a b)+ c

would match:

abababac

Return Values

All return values are based on the capture groups ("$1/$2/$3/etc." type variables) of parsed RE statements. The exact structure of the result tree depends on the type of Receiver used. For example, Pegex::Tree will return:

$1              # single capture group
[ @+[1..$#+] ]  # multiple capture groups

This would be a match directly from the RE rule. As rules go further back, things are put into arrays, but only if there is more than one result. For example:

r: (a b)+ % +
a: /( ALPHA+ )/
b: /( DIGIT+ )( PLUS )/
# input = foobar123+
# output (using Pegex::Tree) = [
#     'foobar', [ '123', '+' ]
# ]
#
# input = foobar123+ boofar789+
# output (using Pegex::Tree) = [
#     [ 'foobar', [ '123', '+' ] ],
#     [ 'boofar', [ '789', '+' ] ],
# ]

Skipping

Any rule can use the skip modifier (DOT) to completely skip the return from that rule (and any children below it). The rule is still processed, but nothing is put into the tree. (This is different from, say, putting "undef" into the return.) This can also affect the number of values returned, and thus, whether a value comes as an array:

r: (a .b)+ % +
a: /( ALPHA+ )/
b: /( DIGIT+ )( PLUS )/
# input = foobar123+ boofar789+
# output (using Pegex::Tree) = [
#     'foobar',
#     'boofar',
# ]

The skip modifier can also be used with groups. (This is the only group modifier allowed so far.)

r: .(a b)+ % +
a: /( ALPHA+ )/
b: /( DIGIT+ )( PLUS )/
# output (using Pegex::Tree) = []

Wrapping

You can also turn on "wrapping" with the Pegex::Tree::Wrap receiver. This will wrap all match values in a hash with the rule name, like so:

{ rule_A => $match }
{ rule_B => [ @matches ] }

Note that this behavior can be "hard set" with the "+/-" rule modifiers:

-rule  # Flatten array captures
+rule  # Always wrap (even if using Pegex::Tree)

This is simply a check in the "gotrule" for the receiver. So, any specific "got_*" receiver methods will override even these settings, and choose to pass the match as-is. In this case, the "got_*" sub return value dictates what ultimately gets put into the tree object:

+rule_A   # in this case, the + is useless here
sub got_rule_A {
    my ($self, $matches_arrayref) = @_;
    return $matches_arrayref;
    # will be received as [ @matches ]
}

You can "correct" this behavior by passing it back to "gotrule":

+rule_A   # now + is honored
sub got_rule_A {
    my ($self, $matches_arrayref) = @_;
    return $self->gotrule($matches_arrayref);
    # will be received as { rule_A => [ @matches ] }
}
