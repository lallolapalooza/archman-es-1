Ambos hacen lo mismo pero utilizando diferentes enfoques de análisis. Los cubriremos ambos en detalle. Espero que encuentres que Pegex maneja el análisis de precedencia de operadores de manera elegante.

El Problema

Los analizadores de precedencia son interesantes porque necesitas lidiar con operadores que tienen la misma precedencia, diferentes precedencias y asociatividad tanto izquierda como derecha.

Considera la ecuación:

1 - 2 ^ 3 ^ 4 + 5 * 6 / 7

Las reglas normales de precedencia y asociatividad hacen que esto sea lo mismo que:

(1 - (2 ^ (3 ^ 4)) + ((5 * 6) / 7))

Nuestra calculadora debería producir el mismo resultado para ambos. Ten en cuenta que esto significa que analizaremos números, 5 operadores, paréntesis y espacios en blanco separadores.

Aquí tienes un ejemplo del programa calculadora en acción:

Introduce una ecuación: (1 + 2) * 3
(1 + 2) * 3 = 9

Las Soluciones

La mayoría de las soluciones que leerás en la web implican (o asumen) un paso de lexing/tokenización antes del análisis. Pegex siempre analiza un flujo de entrada directamente, extrayendo los "tokens" que necesita usando capturas de expresiones regulares. Así que el análisis ocurre como una sola operación, lo que tiene muchas ventajas.

Pero, ¿cómo incorporamos las reglas de precedencia de operadores en esto? Bueno, tenemos 2 formas diferentes:

calculator1.pl - Escalada de Precedencia de Operadores

Nota: El código en este ejemplo se copia y pega de "calculator/" en los archivos de ejemplo. El código en esos archivos en ejecución es ligeramente diferente, pero reescrito para tener más sentido en este documento.

Nuestra primera calculadora de ejemplo utiliza lo que se conoce como el método de Escalada de Precedencia de Operadores. Ver: http://en.wikipedia.org/wiki/Operator-precedence_parser#Precedence_climbing_method.

Esta es básicamente una técnica inteligente para especificar nuestras reglas gramaticales de tal manera que impliquen precedencia. Aquí está la gramática pegex del código:

expr: add-sub
add-sub: mul-div+ % /- ( [ '+-' ])/
mul-div: power+ % /- ([ '*/' ])/
power: token+ % /- '^' /
token: /- '(' -/ expr /- ')'/ | number
number: /- ( '-'? DIGIT+ )/

Es un poco extraña pero funciona. Dice que cualquier expresión es una suma/resta y que una suma/resta es en realidad una multiplicación/división etc. Finalmente, después del último operador viene el token numérico y los paréntesis.

Se siente un poco al revés. Uno de los mayores inconvenientes de PCM es que se vuelve cada vez menos eficiente con más y más operadores. Necesita recorrer todo el árbol, solo para encontrar cada número.

Pero funciona y el código es mínimo. La clase receptora recibe los números en el orden correcto, evalúa la respuesta inmediatamente y devuelve la respuesta para cada nivel. Sea cual sea el valor de retorno de la operación final, se convierte en el resultado del análisis. Aquí está la clase receptora:

{
    package Calculator;
    use base 'Pegex::Tree';
    sub gotrule {
        my ($self, $list) = @_;
        return $list unless ref $list;
        # Asociativa a la derecha:
        if ($self->rule eq 'power') {
            while (@$list > 1) {
                my ($a, $b) = splice(@$list, -2, 2);
                push @$list, $a ** $b;
            }
        }
        # Asociativa a la izquierda:
        else {
            while (@$list > 1) {
                my ($a, $op, $b) = splice(@$list, 0, 3);
                unshift @$list,
                    ($op eq '+') ? ($a + $b) :
                    ($op eq '-') ? ($a - $b) :
                    ($op eq '*') ? ($a * $b) :
                    ($op eq '/') ? ($a / $b) :
                    die;
            }
        }
        return @$list;
    }
}

Como puedes ver, tiene un método de acción para cada nivel o precedencia. Recorre la expresión, evaluándola. Si recorre de izquierda a derecha o de derecha a izquierda depende de la asociatividad que queramos usar.

Nuestro código de ejecución se ve así:

while (1) {
    print "\nIntroduce una ecuación: ";
    my $expr = <> || '';
    chomp $expr;
    last unless length $expr;
    calc($expr);
}
sub calc {
    my ($expr) = @_;
    my $result = pegex($grammar, 'Calculator')->parse($expr);
    if ($@) {
        warn $@;
        return;
    }
    print "$expr = $result\n";
}

¡Y eso es todo! Tenemos una calculadora funcional según lo especificado.

Sin embargo, el verdadero propósito de esto es explorar buenas técnicas de análisis sintáctico, y el PCM nos deja con ganas de probar algo más eficiente. Probemos otro enfoque...

calculator2.pl - Algoritmo Shunting-Yard

Una forma antigua de analizar expresiones es de alguna manera poner los números y operadores en una pila RPN (Notación Polaca Inversa), que es cada operando seguido de su operador. Una vez en esa forma, se tiene en cuenta la precedencia y la asociatividad.

Por ejemplo:

1 / 2 - ( -3 * 4 )

se convierte en:

1, 2, /, -3, 4, *, -

Para evaluar una RPN, sacas un operador y luego intentas sacar un operando. Si el operando es otro operador, recursas. Cuando tienes 2 operandos, realizas la operación y pones el resultado de nuevo en la pila. Cuando solo queda 1 elemento en la pila, has terminado. Ese es tu resultado.

Veamos nuestra nueva gramática en "calculator2.pl":

expr: operand (operator operand)*
operator: /- (['+-*/^'])/
operand: num | /- '('/ expr /- ')'/
num: /- ('-'? DIGIT+)/

Esto es mucho más fácil de entender. Simplemente estamos extrayendo los tokens. En un sentido (muy real), estamos usando Pegex como un lexer.

Ahora veamos la clase receptora:

{
    package Calculator;
    use base 'Pegex::Tree', 'Precedence';
    my $operator_precedence_table = {
        '+' => {p => 1, a => 'l'},
        '-' => {p => 1, a => 'l'},
        '*' => {p => 2, a => 'l'},
        '/' => {p => 2, a => 'l'},
        '^' => {p => 3, a => 'r'},
    };
    sub got_expr {
        my ($self, $expr) = @_;
        $self->precedence_rpn($expr, $operator_precedence_table);
    }
}

Esto también es mucho más simple. Solo hay un método. ¿Qué está pasando? Bueno, el secreto es que puse el código para convertir los tokens en RPN en una clase base separada llamada "lib/Precedence.pm" en el ejemplo.

¡Esta es una implementación del famoso Algoritmo Shunting-Yard de Edsger Dijkstra de 1961! Son solo 20 líneas de Perl. No lo incluiré en línea aquí, pero échale un vistazo por ti mismo. https://github.com/ingydotnet/pegex-pm/blob/master/eg/calculator/lib/Precedence.pm

El algoritmo Shunting-yard simplemente toma una lista de tokens de expresión y los transforma en una pila RPN. Utiliza información de una tabla de precedencia/asociatividad como la anterior.

Pero estamos escribiendo una calculadora y todavía necesitamos evaluar este cachorrito. Cambié el código del ejecutor para que se vea así:

sub calc {
    my $expr = shift;
    my $calculator = pegex($grammar, 'Calculator');
    my $rpn = eval { $calculator->parse($expr) };
    my $result = RPN::evaluate($rpn);
    print $@ || "$expr = $result\n";
}

Así que, en general, esta segunda solución fue un poco más de código, pero también se siente más sólida en varios niveles.

Conclusión

Pegex se esfuerza por ser la forma más agradable y reutilizable de escribir nuevos analizadores. Los analizadores de precedencia de operadores son una parte necesaria del análisis de expresiones matemáticas y lenguajes informáticos. Este tutorial le mostró 2 formas de hacerlo. A medida que las demandas de Pegex crezcan, podemos ver aún más formas de hacerlo.
