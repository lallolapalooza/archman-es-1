Perl::Critic::Policy::ErrorHandling::RequireCheckingReturnValueOfEval(3pm) Documentación de Perl aportada por el usuario Perl::Critic::Policy::ErrorHandling::RequireCheckingReturnValueOfEval(3pm)

NOMBRE

Perl::Critic::Policy::ErrorHandling::RequireCheckingReturnValueOfEval - No puedes depender del valor de "$@"/"$EVAL_ERROR" para saber si un "eval" falló.

AFILIACIÓN

Esta Política es parte de la distribución principal de Perl::Critic.

DESCRIPCIÓN

Un idioma común en perl para lidiar con posibles errores es usar "eval" seguido de una comprobación de $@/$EVAL_ERROR:

eval {
    ...
};
if ($EVAL_ERROR) {
    ...
}

Hay un problema con esto: el valor de $EVAL_ERROR puede cambiar entre el final del "eval" y la "if". El problema son los destructores de objetos:

package Foo;
...
sub DESTROY {
    ...
    eval { ... };
    ...
}
package main;
eval {
    my $foo = Foo->new();
    ...
};
if ($EVAL_ERROR) {
    ...
}

Suponiendo que no se crean otras referencias a $foo, cuando el bloque "eval" en "main" se sale, se invocará Foo::DESTROY(), independientemente de si el "eval" terminó normalmente o no. Si el "eval" en "main" falla, pero el "eval" en Foo::DESTROY() tiene éxito, entonces $EVAL_ERROR estará vacío cuando se ejecute el "if". Surgen problemas adicionales si dependes del contenido exacto de $EVAL_ERROR y ambos "eval" fallan, porque los mensajes de ambos se concatenarán.

Incluso si no hay un "eval" directamente en el código del método DESTROY(), puede invocar código que use "eval" o que afecte de otra manera a $EVAL_ERROR.

La solución es asegurarse de que, al salir normalmente, un "eval" devuelva un valor verdadero y probar ese valor:

# Los constructores no son un problema.
my $object = eval { Class->new() };
# Para cubrir la posibilidad de que una operación pueda devolver correctamente un
# valor falso, termina el bloque con "1":
if ( eval { something(); 1 } ) {
    ...
}
eval {
    ...
    1;
}
    or do {
        # Manejo de errores aquí
    };

Desafortunadamente, no puedes usar la función "defined" para probar el resultado; "eval" devuelve una cadena vacía en caso de fallo.

Se han escrito varios módulos para aliviar un poco el dolor de localizar y comprobar correctamente $@/$EVAL_ERROR. Por ejemplo:

use Try::Tiny;
try {
    ...
} catch {
    # Manejo de errores aquí;
    # La excepción está en $_/$ARG, no en $@/$EVAL_ERROR.
};  # Nota el punto y coma.

"¡Pero no usamos DESTROY() en ninguna parte de nuestro código!" dices. Ese puede ser el caso, pero ¿tienen alguno de los módulos de terceros que usas? ¿Qué pasa con los que puedas usar en el futuro o las versiones actualizadas de los que ya usas?

CONFIGURACIÓN

Esta Política no es configurable, excepto por las opciones estándar.

VER TAMBIÉN

Para una forma agradable, fácil y no mágica de manejar excepciones correctamente, consulta Try::Tiny.
