NAME

PMWEBAPI - introduction to the Performance Metrics Web Application Programming Interface

HTTP SYNOPSIS

GET /metrics
GET /series/...
GET /search/...
GET /pmapi/...
POST /logger/...

C SYNOPSIS

#include <pcp/pmwebapi.h>

... assorted routines ...

cc ... -lpcp_web -lpcp

DESCRIPTION

The PMWEBAPI is a collection of interfaces providing Performance Co-Pilot services for web applications. It consists of APIs for web applications querying and analysing both live and historical performance data, as well as APIs used by web servers.

The usual HTTP URL-encoded optional parameter rules apply and PMWEBAPI REST requests always follow the convention:

/api/endpoint?parameter1=value1&parameter2=value2

Examples in all following sections use the curl(1) command line utility with a local pmproxy(1) server listening on port 44322 (default port). The pmjson(1) utility is used to neatly format any JSON output, as opposed to the compact (minimal whitespace) form provided by default. The examples in the scalable time series section use historical data recorded by the pmlogger(1) service, in conjunction with a local key-value server.

OPEN METRICS AND OPEN TELEMETRY

Exporting of live performance metrics in either Open Metrics (https://openmetrics.io) or Open Telemetry (https://opentelemetry.io) formats is available.

All requests are performed on the web server host by default, unless a hostspec parameter is provided.

GET /metrics

Parameters Type Explanation
names string Comma-separated list of metric names
filter string Comma-separated list of excluded metric names
match string Pattern matching style (exact, glob or regex)
times boolean Append sample times (milliseconds since epoch)
hostspec string Host specification as described in PCPIntro(1)

Fetches current values and metadata for all metrics, or only metrics indicated by a comma-separated list of names.

For all numeric metrics with the given NAME prefixes, create an open text export format giving their current value and related metadata.

Choice of output format is selected using the HTTP Accept header. With no header, the default response format is Open Metrics text. Using the header with value application/json switches the response to the Open Telemetry JSON format.

In Open Telemetry response mode, sample timestamps are always included and are reported using nanosecond precision.

$ curl -H Accept:application/json -s http://localhost:44322/metrics?names=disk.dev,filesys | pmjson
{
    "resourceMetrics": [
        {
            "resource": {
                "attributes": [ ... ]
            },
            "scopeMetrics": [
                {
                    "scope": { ... },
                    "metrics": [
                        {
                            "name": "disk.dev.total.bytes",
                            "description": "per-disk count of total bytes read and written",
                            "unit": "KiBy",
                            "sum": {
                                "aggregationTemporality": "CUMULATIVE",
                                "isMonotonic": true,
                                "dataPoints": [
                                    {
                                        "attributes": [ ... ]
                                        "timeUnixNano": "1753934255798173",
                                        "asInt": "68927569"
                                    }
                                ]
                            }
                        },
                        ...

In Open Metrics response mode, the native PCP metric metadata (metric name, type, indom, semantics and units) is first output for each metric with # PCP prefix. The metadata reported is of the form described on pmTypeStr(3), pmInDomStr(3), pmSemStr(3) and pmUnitsStr(3) respectively. If the pmUnitsStr(3) units string is empty, then none is output. The units metadata string may contain spaces and extends to the end of the line.

PCP metric names are mapped so that the . separators are exchanged with _ (':' in back-compatibility mode, where "# PCP" is the identifying line suffix). Both metric labels and instances are represented as Open Metrics labels, with external instance names being quoted and the flattened PCP label hierarchy being presented with each value.

When metric names pattern matching is performed using the filter option, the default mode is glob-based matching. The match option can be used to instead request regex-based or exact-match metric filtering.

$ curl -s http://localhost:44322/metrics?names=proc.nprocs,kernel.pernode.cpu.intr,filesys.blocksize
# PCP5 proc.nprocs 3.8.99 u32 PM_INDOM_NULL instant none
# HELP proc_nprocs instantaneous number of processes
# TYPE proc_nprocs gauge
proc_nprocs {hostname="app1"} 7
# PCP5 kernel.pernode.cpu.intr 60.0.66 u64 60.19 counter millisec
# HELP kernel_pernode_cpu_intr total interrupt CPU [...]
# TYPE kernel_pernode_cpu_intr counter
kernel_pernode_cpu_intr{hostname="app1",instname="node0"} 25603
# PCP5 filesys.blocksize 60.5.9 u32 60.5 instant byte
# HELP filesys_blocksize Size of each block on mounted file[...]
# TYPE filesys_blocksize gauge
filesys_blocksize{hostname="app1",instname="/dev/sda1"} 4096
filesys_blocksize{hostname="app1",instname="/dev/sda2"} 4096

SCALABLE TIME SERIES

The fast, scalable time series query capabilities provided by the pmseries(1) command are also available through a REST API. These queries provide access to performance data (metric metadata and values) from multiple hosts simultaneously, and in a fashion suited to efficient retrieval by any number of web applications.

All requests in this group can be accompanied by an optional client parameter. The value passed in the request will be sent back in the response - all responses will be in JSON object form in this case, with top level "client" and "result" fields.

REST API clients can optionally submit an URL-encoded query string in the body of the HTTP request unless otherwise noted. In this case the POST method must be used instead of the GET method.

GET /series/ping

Simple liveness test for clients to check whether the server is up and supports the /series API.

GET /series/query - pmSeriesQuery(3)

Parameters Type Explanation
hostspec string Host specification as described in PCPIntro(1)
start string Start time (ISO8601 date-time, or seconds since epoch)
end string End time (ISO8601 date-time, or seconds since epoch)
interval string Sample interval (e.g. "10s", "1m")
metrics string Comma-separated list of metric names
client string Client identifier to return in response

A full description of the query parameters and output format can be found in the pmSeriesQuery(3) manual page.

Below is an example using the historical data collected by pmlogger(1)

$ cat query.json
{
    "client": "mybrowser",
    "query": "1m.host.disk.total_bytes",
    "start": "2023-10-27T10:00:00Z",
    "end": "2023-10-27T10:05:00Z",
    "interval": "10s"
}
$ curl -d @query.json -H "Content-Type: application/json" -s http://localhost:44322/series/query | pmjson
{
    "client": "mybrowser",
    "result": {
        "metric_0": {
            "name": "disk.total_bytes",
            "values": [
                { "time": 1698386400, "value": 100000 },
                { "time": 1698386410, "value": 101000 },
                ...
            ]
        }
    }
}

PMAPI

The PMWEBAPI also provides access to the full Performance Co-Pilot API (PMAPI) via a REST interface. This is intended for web applications that need direct access to raw performance data.

GET /pmapi/ping

Simple liveness test for clients to check whether the server is up and supports the /pmapi API.

GET /pmapi/query - pmapi(1)

Parameters Type Explanation
hostspec string Host specification as described in PCPIntro(1)
start string Start time (ISO8601 date-time, or seconds since epoch)
end string End time (ISO8601 date-time, or seconds since epoch)
interval string Sample interval (e.g. "10s", "1m")
names string Comma-separated list of metric names
client string Client identifier to return in response

This endpoint mirrors the functionality of the pmapi(1) command-line tool, allowing clients to query raw performance metrics.

$ curl -s http://localhost:44322/pmapi/query?names=proc.nprocs | pmjson
{
    "proc.nprocs": {
        "bytes": 7
    }
}

LOGGER

This interface provides access to the Performance Co-Pilot logging daemon, pmlogger(1).

POST /logger/control

Allows clients to control the pmlogger(1) daemon. This includes starting, stopping, and querying the status of loggers.

$ curl -X POST -d '{"operation": "start", "pmcd": "localhost", "archive": "/tmp/my.log"}' -s http://localhost:44322/logger/control
{
    "status": "success",
    "pid": 12345
}

The following operations are supported:

  • start: Start a new logger. Requires pmcd and archive parameters. Optionally accepts interval and metrics parameters.
  • stop: Stop a running logger. Requires pid parameter.
  • status: Query the status of a logger. Optionally accepts pid parameter to query a specific logger, otherwise returns status of all loggers.

A full description of the parameters and response format can be found in the pmlogger_control(1) manual page.

GET /series/query - pmSeriesQuery(3)

Parámetros Tipo Explicación
expr cadena Cadena de consulta en formato pmseries(1)
client cadena Identificador de solicitud devuelto con la respuesta

Realiza una consulta de series temporales para identificadores coincidentes, o para identificadores coincidentes con series de valores con marca de tiempo.

La consulta tiene el formato descrito en pmseries(1) y se pasa al servidor a través del parámetro expr (HTTP GET) o a través del cuerpo del mensaje (HTTP POST).

Al consultar solo coincidencias de series temporales, no se especifican opciones de ventana de tiempo y los identificadores de series coincidentes se devuelven en un array JSON.

BUSQUEDA DE TEXTO COMPLETO

Las capacidades de búsqueda de texto completo proporcionadas por el comando pmsearch(1) también están disponibles a través de una API REST. Estas consultas proporcionan acceso a un índice sobre nombres de métricas de rendimiento, instancias, dominios de instancias y texto de ayuda, adecuado para un motor de búsqueda de métricas y de una manera adecuada para la consulta eficiente por parte de cualquier número de aplicaciones web.

Para utilizar esta funcionalidad, el módulo opcional ValkeySearch debe cargarse en el servidor clave-valor en el momento en que se inicia pmproxy, de modo que las métricas, instancias y texto de ayuda que descubre puedan indexarse automáticamente.

GET /search/text - pmSearchTextQuery(3)

Parámetros Tipo Explicación
query cadena Cadena de consulta en formato de pmsearch(1)
highlight campos Incluir marcado coincidente en los campos de respuesta
offset número Cursor de compensación de resultados para paginación
limit número Máximo de resultados a incluir en la respuesta
field campos Campos consultados (por defecto todos)
return campos Campos a devolver realmente (por defecto todos)
type tipos Tipos de entidad a filtrar (por defecto todos)

Realiza una consulta de búsqueda de texto a través de métricas y dominios de instancias: todas las formas de nombres y textos de ayuda.

La cadena de búsqueda obligatoria se describe con más detalle en pmsearch(1) y se pasa al servidor a través del parámetro query (HTTP GET).

$ curl -s http://localhost:44322/search/text?query=halt | pmjson
{
  "total": 2,
  "offset": 0,
  "limit": 10,
  "elapsed": 0.000504,
  "results": [
    {
      "name": "kvm.halt_exits",
      "type": "metric",
      "indom": "95.0.4",
      "oneline": "Number of guest exits due to halt calls.",
      "helptext": "This type of exit is usually seen when a guest is idle."
    },
    {
      "name": "kvm.halt_wakeup",
      "type": "metric",
      "indom": "95.0.6",
      "oneline": "Number of wakeups from a halt.",
    }
  ]
}

Los tipos de entidad de búsqueda disponibles son metric, indom e instance. Los parámetros de consulta highlight y field toman name, oneline y helptext. El parámetro de consulta return toma name, type, oneline, helptext, indom. Normalmente hay un nombre y un texto de ayuda asociados con las métricas. Los contenidos de estos se comparan con query. Un dominio de instancias tiene texto de ayuda y un identificador numérico, mientras que las instancias solo tienen un nombre (que se puede buscar).

PMAPI SERVICIOS DE HOST

Las instalaciones de recolección de rendimiento en vivo disponibles desde pmcd(1) también se pueden acceder a través de una API REST.

Todas las solicitudes se realizan en el host del servidor web de forma predeterminada, a menos que se proporcione un parámetro hostspec o context. Se puede usar hostname en lugar de hostspec.

Los identificadores de contexto se utilizan como una forma persistente de referirse a contextos PMAPI en solicitudes web relacionadas. Estos contextos expiran después de un período configurable de inactividad, y se asignan explícitamente usando la interfaz /pmapi/context o se asignan implícitamente usando otras interfaces.

El intervalo de tiempo de espera es configurable en el momento de la creación del contexto, y como tal, el parámetro polltimeout puede utilizarse en cualquier lugar donde se especifique hostspec. Establece el tiempo de espera del contexto en términos de duración de la inactividad. La unidad para el valor de tiempo de espera son segundos y el predeterminado es 5.

Para especificar un contexto existente específico en cualquier solicitud web PMAPI, los puntos finales se pueden acceder con el parámetro context o incrustados en la propia URL del punto final, como /pmapi/[número]/fetch.

WEBHOOK DE ARCHIVO - LOGARCHIVE(5)

La funcionalidad de envío remoto de archivos está disponible a través de las utilidades pmlogger(1) y pmlogpush(1). Esto se logra a través de una serie de operaciones POST HTTP a los puntos finales de la API descritos aquí.

Todas las solicitudes de este grupo pueden acompañarse de un parámetro opcional de cliente. El valor pasado en la solicitud se devolverá en la respuesta; todas las respuestas están en formato de objeto JSON e incluirán un campo de nivel superior adicional "client".

GET /logger/ping

Prueba básica de disponibilidad para que los clientes comprueben si el servidor está en funcionamiento y admite la API de /logger.

POST /logger/label

El cuerpo de esta API es la representación binaria (en disco) agnóstica de la máquina de una etiqueta de archivo PCP, como se describe en LOGARCHIVE(5). Se aceptan las versiones 2 y 3, y se ignorará el campo volume de esta estructura; una llamada a la API es suficiente para todos los volúmenes de un archivo, pmproxy garantiza que se escriba el contenido correcto para cada uno.

Esta API devuelve un token numérico (LOGID) que debe utilizarse en todas las interacciones posteriores de la API para este archivo, como se describe a continuación.

POST /logger/meta/LOGID

El cuerpo de la solicitud contiene registros de archivos de metadatos como se describe en LOGARCHIVE.

POST /logger/index/LOGID

El cuerpo de la solicitud contiene registros de índices temporales como se describe en LOGARCHIVE.

POST /logger/volume/VOLID/LOGID

El cuerpo de la solicitud contiene muestras de valores de métricas con marca de tiempo, como se describe en LOGARCHIVE. El volumen numérico (VOLID) al que se van a escribir estos registros es una parte obligatoria del punto final de la API.

NOTAS

Para las API REST, los errores generalmente resultan en respuestas de error a nivel HTTP. Siempre que sea posible, también se proporcionará una cadena de error de PMAPI en un mensaje junto con la respuesta.

Todas las respuestas se devolverán utilizando el protocolo HTTP 1.1 y se utilizará la codificación fragmentada para transmitir respuestas que sean más grandes que un tamaño máximo configurado. La compresión se utilizará en las respuestas siempre que el cliente indique el soporte adecuado.

Se añade una cabecera Access-Control-Allow-Origin: * a todas las respuestas de la API REST.

#include <pcp/pmwebapi.h>

DESCRIPCIÓN

La API web de PCP, pmwebapi, es un servidor web que expone las métricas de Performance Co-Pilot (PCP) a través de una interfaz RESTful. Está diseñado para ser una forma sencilla y conveniente de acceder a datos de monitorización en tiempo real y a archivos de historial de PCP desde aplicaciones y scripts.

El servidor web pmwebapi puede ser iniciado con el comando pmwebapi. Por defecto, escucha en el puerto 8889. La comunicación se realiza a través de peticiones HTTP/1.1.

La API expone varias rutas para consultar diferentes tipos de datos:

  • /pcp/v1/metric/{metric_name}: Recupera los valores actuales de una métrica específica. Se pueden usar parámetros opcionales como host para especificar un host remoto, y instance para filtrar por una instancia particular de la métrica.
  • /pcp/v1/pmtime[/{time_type}]: Recupera información relacionada con el tiempo del sistema. Se puede especificar un tipo de tiempo como offset, boot, monotonic, wall, etc.
  • /pcp/v1/host[/{service_name}]: Enumera los hosts disponibles o recupera información sobre un servicio específico en todos los hosts.
  • /pcp/v1/host/{service_name}/{metric_name}: Recupera información sobre una métrica específica para un servicio dado en todos los hosts.

Los datos se devuelven típicamente en formato JSON. La API también soporta la consulta de métricas y servicios específicos en hosts remotos, siempre que el cliente PCP esté configurado correctamente para comunicarse con los demonios PMCD remotos.

OPEN METRICS Y OPEN TELEMETRY

pmwebapi puede configurarse para exponer métricas en formatos Open Metrics y Open Telemetry. Esto permite la integración con sistemas de monitorización modernos que utilizan estos estándares.

La configuración para estos formatos se realiza a través de argumentos de línea de comandos o archivos de configuración, especificando los puertos y las rutas para los endpoints correspondientes.

SERIES TEMPORALES ESCALABLES

La arquitectura de PCP, y por extensión pmwebapi, está diseñada para manejar y consultar grandes volúmenes de datos de series temporales de manera eficiente. Esto es crucial para la monitorización a largo plazo y el análisis de tendencias.

BÚSQUEDA DE TEXTO COMPLETO

Aunque pmwebapi se centra principalmente en datos numéricos de series temporales, PCP soporta la indexación y búsqueda de texto completo en logs y otros datos textuales. pmwebapi puede interactuar con estas capacidades para recuperar información basada en texto.

SERVICIOS DE HOST PMAPI

pmwebapi puede consultar el estado y las métricas de diversos servicios de PCP que se ejecutan en hosts remotos. Esto incluye servicios como pmcd, pmlogger, pmproxy y varios DAEMONs de métricas (pmda).

La capacidad de consultar servicios específicos y sus métricas (por ejemplo, /pcp/v1/host/pmwebapi/cpu) permite una visión detallada de la infraestructura de monitorización.

WEBHOOK DE ARCHIVO - LOGARCHIVE(5)

pmwebapi puede actuar como un receptor de webhooks para notificaciones relacionadas con archivos de historial de PCP. Esto permite que otras aplicaciones o servicios se suscriban a eventos como la finalización de la grabación de un archivo o la detección de anomalías dentro de un archivo.

La configuración de estos webhooks se gestiona a través de las opciones de LOGARCHIVE.5 y la configuración de pmwebapi.

NOTAS

El servidor web pmwebapi requiere que los daemons PMCD y PMNS estén en ejecución y configurados adecuadamente. Debe haber un archivo pmcd.conf disponible para que pmwebapi pueda cargar los nombres de métricas y la información de host.

La seguridad es una consideración importante. Se recomienda configurar pmwebapi detrás de un proxy inverso (como Nginx o Apache) que maneje la autenticación y el cifrado SSL/TLS.
