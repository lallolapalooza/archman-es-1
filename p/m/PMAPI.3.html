PMAPI(3) Manual de funciones de biblioteca PMAPI(3)

NOMBRE

PMAPI - introducción a la Interfaz de Programación de Aplicaciones de Métricas de Rendimiento

C SINOPSIS

#include <pcp/pmapi.h>

... varias rutinas ...

cc ... -lpcp

DESCRIPCIÓN

Dentro del marco del Sistema de Recopilación de Rendimiento (PCP), las aplicaciones cliente se desarrollan utilizando la Interfaz de Programación de Aplicaciones de Métricas de Rendimiento (PMAPI) que define una interfaz procedural con servicios adecuados para el desarrollo de aplicaciones con un interés particular en métricas de rendimiento.

Esta descripción presenta una visión general de la PMAPI y el contexto en el que se ejecutan las aplicaciones de la PMAPI. La PMAPI se describe con más detalle en la Guía del programador de Performance Co-Pilot, y en las páginas del manual de las rutinas individuales de la PMAPI.

MÉTRICAS DE RENDIMIENTO - NOMBRES E IDENTIFICADORES

Para obtener una descripción del Espacio de Nombres de Métricas de Rendimiento (PMNS) y los términos y conceptos asociados, consulte PCPIntro(1).

No todos los PMID deben estar representados en el PMNS de cada aplicación. Por ejemplo, una aplicación que monitoriza el tráfico del disco probablemente utilizará un espacio de nombres que haga referencia solo a los PMID para estadísticas de E/S.

Las aplicaciones que utilizan la PMAPI pueden tener versiones independientes de un PMNS, construidas a partir de un archivo de inicialización cuando la aplicación se inicia; consulte pmLoadASCIINameSpace(3), pmLoadNameSpace(3) y PMNS(5).

Internamente (debajo de la PMAPI), la implementación del Sistema de Recopilación de Métricas de Rendimiento (PMCS) utiliza solo los PMID, y un PMNS proporciona un mapeo externo de una taxonomía jerárquica de nombres a PMID que es conveniente en el contexto de un sistema particular o un uso particular de la PMAPI. Para el programador de aplicaciones, las rutinas pmLookupName(3) y pmNameID(3) traducen entre nombres en un PMNS y PMID, y viceversa. El PMNS puede ser recorrido utilizando pmGetChildren(3) ypmTraversePMNS. Las funciones pmFetchGroup(3) combinan las operaciones de búsqueda de nombres de métricas, obtención y conversión.

CONTEXTO DE LA PMAPI

Una aplicación que utiliza la PMAPI puede manipular varios contextos concurrentes, cada uno asociado con una fuente de métricas de rendimiento, por ejemplo, pmcd(1) en algún host, o un conjunto de archivos de métricas de rendimiento tal como los crea pmlogger(1).

Los contextos se identifican mediante un "manejador", un valor entero pequeño que se devuelve cuando se crea el contexto; consulte pmNewContext(3) y pmDupContext(3). Algunas funciones de la PMAPI requieren un "manejador" explícito para identificar el contexto correcto, pero más comúnmente la función de la PMAPI se ejecuta en el contexto "actual". El contexto actual puede descubrirse utilizando pmWhichContext(3) y cambiarse utilizando pmUseContext(3).

Si no se ha establecido explícitamente un contexto de la PMAPI (o si el contexto anterior se ha cerrado utilizando pmDestroyContext(3)), el contexto actual de la PMAPI no está definido.

Además de la fuente de las métricas de rendimiento, el contexto también incluye el perfil de instancias y el tiempo de recolección (ambos descritos a continuación) que controla cuánta información se devuelve y cuándo se recolectó la información.

DOMINIOS DE INSTANCIA

Cuando los valores de las métricas de rendimiento se devuelven a través de la PMAPI a una aplicación solicitante, puede haber más de un valor para una métrica particular. Múltiples valores, o instancias, para una sola métrica son típicamente el resultado de la instrumentación implementada para cada instancia de un conjunto de componentes o servicios similares en un sistema, por ejemplo, recuentos independientes para cada CPU, o cada proceso, o cada disco, o cada tipo de llamada al sistema, etc. Esta multiplicidad de valores no se enumera en el espacio de nombres, sino que, cuando las métricas de rendimiento son entregadas a través de la PMAPI por pmFetch(3), el formato del resultado acomoda valores para una o más instancias, con un par instancia-valor que codifica el valor de la métrica para una instancia particular.

Las instancias se identifican mediante un identificador interno asignado por el agente responsable de instanciar los valores para la métrica de rendimiento asociada. Cada identificador de instancia tiene un nombre de identificador de instancia externo correspondiente (una cadena ASCII). Las rutinas pmGetInDom(3), pmLookupInDom(3) y pmNameInDom(3) pueden usarse para enumerar todos los identificadores de instancia y para traducir entre identificadores de instancia internos y externos.

Todos los identificadores de instancia para una métrica de rendimiento particular se conocen colectivamente como un dominio de instancia. Múltiples métricas de rendimiento pueden compartir el mismo dominio de instancia.

Si solo hay una instancia disponible para una métrica de rendimiento particular, el identificador de instancia en el resultado de pmFetch(3) asume el valor especial PM_IN_NULL y puede ser ignorado por la aplicación, y solo aparece un par instancia-valor en el resultado para esa métrica. En estas circunstancias, el dominio de instancia asociado (tal como se devuelve a través de pmLookupDesc(3)) se establece en PM_INDOM_NULL para indicar que los valores para esta métrica son singulares.

El difícil problema de las métricas de rendimiento transitorias (por ejemplo, información por sistema de archivos, módulos de hardware reemplazables en caliente, etc.) significa que las solicitudes repetidas para el mismo PMID pueden devolver un número diferente de valores, y/o algunos cambios en los identificadores de instancia particulares devueltos. Esto significa que las aplicaciones deben ser conscientes de que la instanciación de métricas solo se garantiza que sea válida en el momento de la recolección. Reglas similares se aplican a la semántica transitoria de los valores de métricas asociados. En general, sin embargo, se espera que la mayor parte de las métricas de rendimiento tengan una semántica de instanciación que sea fija durante el tiempo de ejecución de cualquier cliente de la PMAPI.

EL TIPO DE VALORES DE MÉTRICA

La PMAPI admite una amplia gama de codificaciones de formato y tipo para los valores de las métricas de rendimiento, a saber, enteros con signo y sin signo, números de punto flotante, codificaciones de 32 bits y 64 bits de todos los anteriores, cadenas ASCII (estilo C, terminadas con byte NULL) y agregados arbitrarios de datos binarios.

El campo tipo en la estructura pmDesc devuelta por pmLookupDesc(3) identifica el formato y tipo de los valores para una métrica de rendimiento particular dentro de un contexto de PMAPI particular.

Tenga en cuenta que la codificación de valores para una métrica de rendimiento particular puede ser diferente para diferentes contextos de PMAPI, debido a diferencias en la implementación subyacente para diferentes contextos. Sin embargo, se espera que la gran mayoría de las métricas de rendimiento tengan una codificación de valores consistente en todas las versiones de todas las implementaciones, y por lo tanto, en todos los contextos de PMAPI.

La PMAPI admite rutinas para automatizar el manejo de los diversos formatos y tipos de valores, particularmente para el caso común en el que se desea la conversión a un formato canónico, consulte pmExtractValue(3) y pmPrintValue(3).

LA DIMENSIONALIDAD Y LA ESCALA DE LOS VALORES DE MÉTRICA

Independientemente de cómo se codifique el valor, se supone que el valor de una métrica de rendimiento se extrae de un conjunto de valores que pueden describirse en términos de su dimensionalidad y escala mediante una codificación compacta de la siguiente manera. La dimensionalidad se define por una potencia, o índice, en cada una de las 3 dimensiones ortogonales, a saber, Espacio, Tiempo y Conteo (o Eventos, que no tienen dimensión). Por ejemplo, el rendimiento de E/S podría representarse como Espacio/Tiempo, mientras que el total acumulado de llamadas al sistema es Conteo, la asignación de memoria es Espacio y el tiempo de servicio promedio es Tiempo/Conteo. DIMENSIONALITY AND SCALE

There are a number of common scale values that may be used to better encode ranges that might otherwise exhaust the precision of a 32-bit value. This information is encoded in the pmUnits structure which is embedded in the pmDesc structure returned from pmLookupDesc(3).

The routine pmConvScale(3) is provided to convert values in conjunction with the pmUnits structures that defines the dimensionality and scale of the values for a particular performance metric as returned from pmFetch(3), and the desired dimensionality and scale of the value the PMAPI client wishes to manipulate. Alternatively, the pmFetchGroup(3) functions can perform data format and unit conversion operations, specified by textual descriptions of desired unit / scales.

PERFIL DE INSTANCIA

El conjunto de instancias para métricas de rendimiento devueltas por una llamada a pmFetch(3) puede ser filtrado o restringido usando un perfil de instancia. Hay un perfil de instancia por cada contexto PMAPI que la aplicación crea, y cada perfil de instancia puede incluir instancias de uno o más dominios de instancia.

Las rutinas pmAddProfile(3) y pmDelProfile(3) pueden ser usadas para ajustar dinámicamente el perfil de instancia.

TIEMPO DE RECOPILACIÓN

Para cada conjunto de valores de métricas de rendimiento devueltos a través de pmFetch(3) hay una "marca de tiempo" asociada que sirve para identificar cuándo se recopilaron los valores de las métricas de rendimiento; para métricas que se entregan desde una fuente en tiempo real (es decir, pmcd(1) en algún host) esto típicamente no sería mucho antes de que se exportaran a través de PMAPI, y para métricas que se entregan desde un conjunto de archivos, sería el momento en que las métricas se escribieron en el archivo.

Hay un problema aquí sobre cuándo se pueden haber recopilado las métricas individuales, especialmente dada su origen en dominios de métricas de rendimiento potencialmente diferentes y la variabilidad en la frecuencia de actualización de las métricas en el nivel más bajo del dominio de métricas de rendimiento. El PMCS opta por el enfoque pragmático, en el cual la implementación de PMAPI se compromete a devolver todas las métricas con valores precisos a partir de la marca de tiempo, lo mejor que podamos. La creencia es que la imprecisión que esto introduce es pequeña, y la carga adicional de una marca de tiempo individual precisa para cada valor de métrica devuelto no está justificada ni es práctica (desde el punto de vista de la implementación).

Por supuesto, en el caso de la recopilación de métricas de múltiples hosts, el cliente de PMAPI debe asumir que la validez de las marcas de tiempo está limitada por el grado en que se implementan los protocolos de sincronización de relojes en la red.

Una aplicación de PMAPI puede llamar a pmSetMode(3) para variar el tiempo de recopilación solicitado, por ejemplo, para reescanear los valores de las métricas de rendimiento del pasado reciente, o para "avanzar rápido" a través de un conjunto de archivos.

TEMAS GENERALES DEL ESTILO DE PROGRAMACIÓN DE PMAPI

En todo el PMAPI, todos los argumentos y resultados que involucran una "lista de algo" se declaran como arrays con un argumento asociado o valor de función para identificar el número de elementos en la lista. Esto se ha hecho para evitar tanto el enfoque de varargs(3) como las listas terminadas por centinela.

Cuando el tamaño de un resultado se conoce en el momento de una llamada, es responsabilidad del llamador asignar (y posiblemente liberar) el almacenamiento, y la función llamada asumirá que el argumento de resultado tiene un tamaño apropiado. Donde un resultado es de tamaño variable y ese tamaño no se puede conocer de antemano (por ejemplo, para pmGetChildren(3), pmGetInDom(3), pmNameInDom(3), pmNameID(3), pmLookupLabels(3), pmLookupText(3) y pmFetch(3)), la implementación de PMAPI utiliza una variedad de esquemas de asignación dinámica en la rutina llamada, siendo el llamador responsable de liberar posteriormente el almacenamiento cuando ya no sea necesario. En algunos casos, esto implica simplemente llamadas a free(3), pero en otros (especialmente para el resultado de pmFetch(3)), se deben utilizar rutinas especiales (por ejemplo, pmFreeResult(3) y pmFreeLabelSets(3)) para liberar el almacenamiento.

Como regla general, si la rutina llamada devuelve un estado de error, no se habrá realizado ninguna asignación y cualquier puntero a un resultado de tamaño variable no estará definido.

DIAGNÓSTICOS

Donde puedan surgir condiciones de error, las funciones que componen el PMAPI se ajustan a un esquema de notificación de errores simple y único, como sigue;

+
la función devuelve un entero
+
los valores >= 0 indican que no hay error, y quizás algún estado positivo, por ejemplo, el número de cosas realmente procesadas
+
los valores < 0 indican un error, con una tabla global de condiciones de error y mensajes de error

La rutina PMAPI pmErrStr(3) traduce las condiciones de error en mensajes de error. Por convención, se asume que los pequeños valores negativos son versiones negadas de los códigos de error de Unix tal como se definen en <errno.h> y las cadenas devueltas son como las de strerror(3). Los códigos de error negativos más grandes son condiciones de error de PMAPI.

Un error, común a todas las rutinas de PMAPI que interactúan con pmcd(1) en algún host es PM_ERR_IPC, que indica que se ha perdido el enlace de comunicación con pmcd(1).

APLICACIONES MULTIHILO

El diseño original para PCP se basó en aplicaciones de un solo hilo, o más estrictamente en aplicaciones en las que solo se esperaba que un hilo llamara a las bibliotecas de PCP. Esta restricción se ha relajado para **libpcp** para permitir que las rutinas PMAPI más comunes se llamen de forma segura desde cualquier hilo en una aplicación multihilo.

Sin embargo, los siguientes grupos de funciones y servicios en **libpcp** todavía están restringidos a ser llamados desde un solo hilo, y esto se aplica devolviendo **PM_ERR_THREAD** cuando se detecta un intento de llamar a las rutinas de cada grupo desde más de un hilo.

1.
Cualquier uso de un contexto **PM_CONTEXT_LOCAL**, ya que los PMDA de DSO que se llaman directamente desde **libpcp** pueden no ser seguros para hilos.

ENTORNO PCP

La mayoría de las variables de entorno se describen en PCPIntro(1). Además, las variables de entorno con el prefijo **PCP_** se utilizan para parametrizar los nombres de archivos y directorios utilizados por PCP. En cada instalación, el archivo /etc/pcp.conf contiene los valores locales para estas variables. La variable **$PCP_CONF** puede usarse para especificar un archivo de configuración alternativo, como se describe en pcp.conf(5). Los valores de estas variables se pueden obtener programáticamente utilizando la función pmGetConfig(3).
