POE::Filter(3) User Contributed Perl Documentation POE::Filter(3)

NOMBRE

POE::Filter - abstracciones de protocolo para POE::Wheel y uso independiente

SINOPSIS

Para usar con clases POE::Wheel, pasa un objeto POE::Filter a uno de los parámetros del constructor "...Filter":

#!perl
use POE qw(Filter::Line Wheel::FollowTail);
POE::Session->create(
  inline_states => {
    _start => sub {
      $_[HEAP]{tailor} = POE::Wheel::FollowTail->new(
        Filename => "/var/log/system.log",
        InputEvent => "got_log_line",
        Filter => POE::Filter::Line->new(),
      );
    },
    got_log_line => sub {
      print "Log: $_[ARG0]\n";
    }
  }
);
POE::Kernel->run();
exit;

Uso independiente sin POE:

#!perl
use warnings;
use strict;
use POE::Filter::Line;
my $filter = POE::Filter::Line->new( Literal => "\n" );
# Imprime tres líneas: one, two three.
$filter->get_one_start(["one\ntwo\nthr", "ee\nfour"]);
while (1) {
  my $line = $filter->get_one();
  last unless @$line;
  print $line->[0], "\n";
}
# Imprime dos líneas: four, five.
$filter->get_one_start(["\nfive\n"]);
while (1) {
  my $line = $filter->get_one();
  last unless @$line;
  print $line->[0], "\n";
}

DESCRIPCIÓN

Los objetos POE::Filter se conectan a las ruedas (wheels) y definen cómo se serializarán los datos para escritura y se analizarán después de la lectura. Los objetos POE::Wheel son responsables de mover datos, y los objetos POE::Filter definen cómo deben verse esos datos.

Los objetos POE::Filter son simples por diseño. No usan POE internamente, por lo que se limitan a la serialización y el análisis. Esto puede complicar la implementación de ciertos protocolos (como HTTP 1.x), pero permite que los filtros se utilicen en programas independientes.

El uso independiente es muy importante. Permite a los desarrolladores de aplicaciones crear bibliotecas de bloqueo ligeras que pueden usarse como clientes simples para servidores POE. POE::Component::IKC::ClientLite es un ejemplo notable. Este cliente ligero y de bloqueo de paso de eventos soporta clientes delgados para aplicaciones POE en rejilla. El caso de uso canónico es inyectar eventos en una aplicación IKC o rejilla desde interfaces CGI, que requieren un uso ligero de recursos.

Los filtros y drivers de POE pasan datos en referencias a arreglos. Esto es un poco incómodo, pero minimiza la cantidad de datos que deben copiarse en la pila de Perl.

INTERFAZ PÚBLICA

Todas las clases POE::Filter deben soportar la interfaz mínima, definida aquí. Filtros específicos pueden implementar y documentar métodos adicionales.

PARÁMETROS DE new

new() crea e inicializa un nuevo filtro. Los parámetros del constructor varían de una subclase de POE::Filter a otra, así que por favor consulta la documentación de tu filtro deseado.

clone

clone() crea e inicializa un nuevo filtro basado en los parámetros del constructor del existente. El nuevo filtro es una copia casi idéntica, excepto que sus búferes están vacíos.

Ciertos componentes, como POE::Component::Server::TCP, usan clone(). Estos componentes aceptan un filtro maestro o plantilla en el momento de la creación, y luego clonan ese filtro para cada nueva conexión.

my $new_filter = $old_filter->clone();

get_one_start ARRAYREF

get_one_start() acepta una referencia a un arreglo que contiene fragmentos de flujo sin procesar. Los fragmentos se agregan al búfer interno del filtro para ser analizados por get_one().

La "SINOPSIS" muestra get_one_start() en uso.

get_one

get_one() analiza cero o un ítem completo del búfer interno del filtro. Los datos se devuelven como un ARRAYREF adecuado para pasarlo a otro filtro o a un objeto POE::Wheel. Los filtros devolverán ARRAYREFs vacíos si no tienen suficientes datos crudos para construir un ítem completo.

get_one() es la forma perezosa (lazy) de get(). Solo analiza un ítem a la vez del búfer del filtro. Esto es vital para aplicaciones que pueden cambiar filtros a mitad de transmisión, ya que asegura que el filtro correcto esté en uso en cualquier momento dado.

La "SINOPSIS" muestra get_one() en uso. Nota cómo asume que el retorno es siempre un ARRAYREF, y maneja implícitamente los vacíos.

get ARRAYREF

get() es la forma codiciosa (greedy) de get_one(). Acepta una referencia a un arreglo que contiene fragmentos de flujo sin procesar, y agrega esos datos al búfer interno del filtro. Luego, analiza tantos ítems completos como sea posible del búfer y los devuelve en otra referencia a arreglo. Cualquier dato sin procesar permanece en el búfer del filtro para la próxima llamada.

Al igual que con get_one(), get() devolverá una referencia a arreglo vacía si el filtro no contiene suficientes datos crudos para construir un ítem completo.

De hecho, get() se implementa en POE::Filter en términos de get_one_start() y get_one().

Aquí está la forma get() del ejemplo independiente de la SINOPSIS:

#!perl
use warnings;
use strict;
use POE::Filter::Line;
my $filter = POE::Filter::Line->new( Literal => "\n" );
# Imprime tres líneas: one, two three.
my $lines = $filter->get(["one\ntwo\nthr", "ee\nfour"]);
foreach my $line (@$lines) {
  print "$line\n";
}
# Imprime dos líneas: four, five.
$lines = $filter->get(["\nfive\n"]);
foreach my $line (@$lines) {
  print "$line\n";
}

get() no debe usarse con ruedas que soporten el cambio de filtros. Su naturaleza codiciosa significa que a menudo analiza transmisiones con mucha antelación a los eventos de una rueda. Para cuando una aplicación cambia el filtro de la rueda, es demasiado tarde: el filtro antiguo ya ha analizado el resto de los datos recibidos.

Considere una transmisión de letras, números y puntos. Los puntos indican cuándo cambiar los filtros de uno que analiza letras a uno que analiza números.

En nuestra aplicación hipotética, las letras deben manejarse una por una, pero los números pueden manejarse en fragmentos. Usaremos POE::Filter::Block con un BlockSize de 1 para analizar letras, y POE::Filter::Line con un terminador Literal de "." para manejar números.

Aquí está la transmisión de ejemplo:

abcdefg.1234567.hijklmnop.890.q

Comenzaremos con una rueda ReadWrite configurada para analizar caracteres.

$_[HEAP]{wheel} = POE::Wheel::ReadWrite->new(
  Filter => POE::Filter::Block->new( BlockSize => 1 ),
  Handle => $socket,
  InputEvent => "got_letter",
);

El manejador "got_letter" será llamado 8 veces. Una por cada letra de la a a la g, y una por el punto que sigue a la g. Al recibir el punto, cambiará la rueda a modo de números.

sub handle_letter {
  my $letter = $_[ARG0];
  if ($letter eq ".") {
    $_[HEAP]{wheel}->set_filter(
      POE::Filter::Line->new( Literal => "." )
    );
    $_[HEAP]{wheel}->event( InputEvent => "got_number" );
  }
  else {
    print "Got letter: $letter\n";
  }
}

Si se usara el método get() codicioso, toda la transmisión de entrada habría sido analizada como caracteres antes de la primera llamada a handle_letter(). La llamada a set_filter() habría sido inútil, ya que no habría quedado datos para ser analizados.

El manejador "got_number" recibe secuencias continuas de dígitos como líneas terminadas por punto. El método get() codicioso causaría un problema similar al anterior.

sub handle_numbers {
  my $numbers = $_[ARG0];
  print "Got number(s): $numbers\n";
  $_[HEAP]->{wheel}->set_filter(
    POE::Filter::Block->new( BlockSize => 1 )
  );
  $_[HEAP]->{wheel}->event( InputEvent => "got_letter" );
}

¡Así que no lo hagas!

put ARRAYREF

put() serializa ítems en una transmisión de octetos que puede ser escrita en un archivo o enviada a través de un socket. Acepta una referencia a una lista de ítems y devuelve una referencia a una lista de fragmentos de transmisión serializados. El número de fragmentos de salida no está necesariamente relacionado con el número de ítems de entrada.

POE::Filter(3pm)

NAME

POE::Filter - A framework for creating POE input/output filters

SYNOPSIS

  package My::Filter;
  use base 'POE::Filter';
  sub new { ... }
  sub get_pending { ... }
  sub get_one { ... }
  sub put { ... }
  sub flush { ... }
  1;

DESCRIPTION

POE filters are used to transform data as it passes between POE components, or between POE components and the outside world. They are particularly useful for implementing protocols, such as HTTP, IRC, or simple line-based protocols.

Filters are objects that implement a common interface, so they can be stacked.

A filter must implement the methods get_one(), put(), and flush(). It may optionally implement get_pending().

POE::Filter is the base class for filters. It doesn't do much itself, but it provides a place to store shared functionality, and to enforce the filter interface.

Filters are composed of two parts: a serialization part and a deserialization part. The serialization part is implemented by put() and flush(). The deserialization part is implemented by get_one() and get_pending().

The serialization methods are concerned with converting Perl data structures into a stream of bytes. The deserialization methods are concerned with converting a stream of bytes back into Perl data structures.

A filter's state is stored in its input and output buffers. The input buffer holds data that has been received from the outside world but has not yet been processed. The output buffer holds data that has been processed but has not yet been sent to the outside world.

Filters may be chained together to form a pipeline. For example, a filter that compresses data could be placed before a filter that encrypts data. The data would then be compressed and then encrypted before being sent to the outside world.

Filters are typically used in conjunction with POE::Wheel objects. A POE::Wheel object can be configured to use a filter to process its input and output data.

PUBLIC INTERFACE

put

put( $data ) takes a Perl data structure, serializes it into a stream of bytes, and appends it to the filter's output buffer. It returns a list reference of any complete, ready-to-send data fragments that result from this operation. The list reference it returns may be passed directly to a driver or filter.

  my $filter = POE::Filter::Line->new();
  my @things_to_send = ( "hello", "world\n", "how are you?" );
  my $outgoing_data = $filter->put(\@things_to_send);
  # $outgoing_data might be ['hello\n', "how are you?"] or similar,
  # depending on the filter type. It's guaranteed to be a list ref.
  # POE::Filter::Line, for example, will add newlines if they are missing.
  #
  # The output may be sent directly:
  print $outgoing_data->[0] if @$outgoing_data;
  print $outgoing_data->[1] if @$outgoing_data > 1;

The list reference it returns may be passed directly to a driver or filter. Drivers and filters deliberately share the same put() interface so that things like this are possible:

  $driver->put(
    $transfer_encoding_filter->put(
      $content_encoding_filter->put(
        \@items
      )
    )
  );
  1 while $driver->flush(\*STDOUT);

get_pending

get_pending() returns any data remaining in a filter's input buffer. The filter's input buffer is not cleared, however. get_pending() returns a list reference if there's any data, or undef if the filter was empty.

POE::Wheel objects use get_pending() during filter switching. Unprocessed data is fetched from the old filter with get_pending() and injected into the new filter with get_one_start().

  use POE::Filter::Line;
  use POE::Filter::Stream;
  my $line_filter = POE::Filter::Line->new();
  $line_filter->get_one_start([ "not a complete line" ]);
  my $stream_filter = POE::Filter::Stream->new();
  my $line_buffer = $line_filter->get_pending();
  $stream_filter->get_one_start($line_buffer) if $line_buffer;
  print "Stream: $_\n" foreach (@{ $stream_filter->get_one });

Full items are serialized whole, so there is no corresponding "put" buffer or accessor.

BUGS

In theory, filters should be interchangeable. In practice, stream and block protocols tend to be incompatible.
