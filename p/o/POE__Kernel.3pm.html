POE::Kernel(3) Documentación de Perl aportada por el usuario POE::Kernel(3)

NOMBRE

POE::Kernel - un kernel de aplicación basado en eventos en Perl

SINOPSIS

use POE; # incluye automáticamente POE::Kernel y POE::Session
POE::Session->create(
  inline_states => {
    _start => sub { $_[KERNEL]->yield("next") },
    next   => sub {
      print "tick...\n";
      $_[KERNEL]->delay(next => 1);
    },
  },
);
POE::Kernel->run();
exit;

Siguiendo el espíritu de Perl, existen muchas otras formas de usar POE.

DESCRIPCIÓN

POE::Kernel es el corazón de POE. Proporciona las características de nivel más bajo: E/S multiplexada no bloqueante, temporizadores y observadores de señales son las más significativas. Todo lo demás se construye sobre esta base.

POE::Kernel no es un bucle de eventos en sí mismo. Para eso utiliza uno de varios módulos de interfaz POE::Loop disponibles. Consulte CPAN para ver módulos en el espacio de nombres POE::Loop.

La documentación de POE asume que el lector entiende las constantes de desplazamiento de @_ (KERNEL, HEAP, ARG0, etc.). El lector curioso o confundido encontrará una explicación más detallada en POE::Session.

USANDO POE

Usando POE Literalmente

POE.pm es poco más que un cargador de clases. Implementa algo de magia para reducir el trabajo de configuración.

Los parámetros para "use POE" no se tratan como importaciones normales. Más bien, son módulos abreviados a incluir junto con POE.

use POE qw(Component::Client::TCP).

Como puede ver, el prefijo "POE::" se puede omitir de esta manera.

POE.pm también incluye POE::Kernel y POE::Session por defecto. Estos dos módulos son utilizados por casi todos los programas basados en POE. Por lo tanto, el ejemplo anterior es en realidad el equivalente de:

use POE;
use POE::Kernel;
use POE::Session;
use POE::Component::Client::TCP;

Usando POE::Kernel

POE::Kernel necesita saber qué bucle de eventos desea utilizar. Esto se admite de tres maneras diferentes:

La primera forma es usar un módulo de bucle de eventos antes de usar POE::Kernel (o POE, que carga POE::Kernel por usted):

use Tk; # o uno de varios otros
use POE::Kernel.

POE::Kernel escanea la lista de módulos ya cargados y carga un adaptador POE::Loop apropiado si encuentra un bucle de eventos conocido.

La siguiente forma es cargar explícitamente la clase POE::Loop que desea:

use POE qw(Loop::Gtk);

Finalmente, la importación de import() de POE::Kernel admite una configuración más amigable para el programador:

use POE::Kernel { loop => "Gtk" };
use POE::Session;

Anatomía de una Aplicación Basada en POE

Los programas que usan POE funcionan como cualquier otro. Cargan los módulos necesarios, realizan alguna configuración, ejecutan código y, eventualmente, salen. Aparte de los inconvenientes de la detención.

Una aplicación basada en POE carga algunos módulos, configura una o más sesiones, ejecuta el código en esas sesiones y, eventualmente, sale.

use POE;
POE::Session->create( ... mapear eventos a código aquí ... );
POE::Kernel->run();
exit;

Singleton de POE::Kernel

El POE::Kernel es un objeto singleton; solo puede haber una instancia de POE::Kernel dentro de un proceso. Esto permite que muchos métodos de objeto también sean métodos de paquete.

Sesiones

POE implementa compartimentos aislados llamados sesiones. Las sesiones desempeñan el papel de tareas o hilos dentro de POE. POE::Kernel actúa como el planificador de tareas de POE, distribuyendo tiempos de ejecución a cada sesión invocando devoluciones de llamada dentro de ellas.

Las devoluciones de llamada no son preemptivas. Mientras una esté en ejecución, ninguna otra será despachada. Esto se conoce como multitarea cooperativa. Cada sesión debe cooperar regresando al kernel de despacho central.

La multitarea cooperativa simplifica enormemente el intercambio de datos, ya que no hay dos fragmentos de código que puedan modificar datos al mismo tiempo.

Una sesión también puede tomar el control exclusivo del tiempo de un programa, si es necesario, simplemente sin regresar a tiempo. Incluso es posible escribir programas completamente bloqueantes que usen POE como una máquina de estados en lugar de un despachador cooperativo.

Cada aplicación basada en POE necesita al menos una sesión. El código no puede ejecutarse dentro de POE sin ser parte de alguna sesión. Asimismo, un programa con hilos siempre tiene un "hilo cero".

Las sesiones en POE::Kernel no deben confundirse con POE::Session, aunque ambas están inextricablemente asociadas. POE::Session adapta el despachador de POE::Kernel a una convención de llamada particular. Existen otras clases de POE::Session en CPAN. Algunas alteran radicalmente la forma en que se llaman los manejadores de eventos. http://search.cpan.org/search?query=poe+session.

Recursos

Los recursos son eventos y cosas que pueden crear nuevos eventos, como temporizadores, observadores de E/S e incluso otras sesiones.

POE::Kernel rastrea los recursos en nombre de sus sesiones activas. Genera eventos correspondientes a la actividad de estos recursos, notificando a las sesiones cuando es el momento de hacer cosas.

La conversación es algo así:

Sesión: Sé amable, Kernel, y avísame cuando alguien haga clic en
        este widget. ¡Muchas gracias!
[PASAN TIEMPO]  [SFX: CLIC DEL RATÓN]
Kernel: Bien, entonces. Alguien hizo clic en tu widget.
        Aquí tienes.

Además, dado que el Kernel hace un seguimiento de todo lo que hacen las sesiones, sabe cuándo una sesión se ha quedado sin tareas que realizar. Cuando esto sucede, el Kernel emite un evento "_stop" en la sesión inactiva para que pueda limpiarse y cerrarse.

Kernel: Por favor, apaga las luces y cierra; es hora de irse.

Del mismo modo, si una sesión se detiene por sí sola y todavía hay observadores de recursos abiertos, el Kernel lo sabe y los limpia en nombre de la sesión. POE se destaca en servicios de larga duración porque rastrea y limpia los recursos de manera tan meticulosa.

POE::Resources y las clases POE::Resource implementan cada tipo de recurso, que se resumen aquí y se cubren con más detalle más adelante.

Eventos.
Un evento es un mensaje para una sesión. Publicar un evento mantiene vivas tanto al remitente como al destinatario hasta después de que el evento haya sido despachado. Esto solo está garantizado si tanto el remitente como el destinatario están en el mismo proceso. Los complementos de paso de mensajes entre Kernels pueden tener otras garantías. Consulte su documentación para obtener más detalles.

La razón es que el evento está en juego, por lo que el destinatario debe permanecer activo para que se despache. El remitente permanece activo en caso de que el destinatario desee enviar una respuesta.

Los eventos publicados no pueden cancelarse de forma preemptiva. Tienden a ser de corta duración en la práctica, por lo que esto generalmente no es un problema.

Temporizadores.
Los temporizadores permiten que una aplicación envíe un mensaje al futuro. Una vez configurado, un temporizador mantendrá activa la sesión de destino hasta que expire y se despache el evento resultante.
Alias.
Los alias de sesión son una forma controlada por la aplicación de direccionar una sesión. Los alias actúan como observadores de eventos pasivos. Siempre que una sesión tenga un alias, otra sesión puede enviar eventos a esa sesión por ese nombre. Los alias mantienen vivas las sesiones mientras un proceso tenga sesiones activas.

Si las únicas sesiones restantes se mantienen activas únicamente por sus alias, POE::Kernel les enviará una señal terminal "IDLE". En la mayoría de los casos, esto terminará las sesiones restantes y permitirá que el programa salga. Si las sesiones permanecen en memoria sin activarse con la señal "IDLE", POE::Kernel les enviará una señal "ZOMBIE" no enmascarable. Luego se eliminan por la fuerza y el programa finalmente saldrá.

Gestión de Recursos de Sesión

Un objeto POE::Session tendrá que permanecer activo mientras tenga recursos que necesiten ser administrados. POE::Kernel se encarga de esto, y se detendrá la sesión cuando todos los recursos hayan sido destruidos o liberados.

Los recursos que mantendrán una sesión activa incluyen:

Descriptores de archivo y sus observadores asociados.
Una sesión que está observando un descriptor de archivo (por ejemplo, usando POE::Kernel->select_read o POE::Kernel->select_write) se mantendrá activa mientras el descriptor de archivo esté siendo observado. Esto se aplica tanto a los descriptores de archivo que se pasan al sistema operativo como a los que son manejados internamente por un componente, como por ejemplo, un controlador de cliente de red. Una sesión que está manejando dichos descriptores de archivo se mantendrá activa hasta que se detenga el controlador y se cierren los descriptores de archivo.
Sesiones hijas.
Una sesión que actúa como padre de una o más sesiones hijas permanecerá activa hasta que todas las sesiones hijas se detengan. Esto puede ser ignorado desconectando las hijas del padre.
Procesos hijos.
Los procesos hijos son observados por sig_child(). El observador sig_child() mantendrá la sesión observadora activa hasta que el proceso hijo haya sido recuperado por POE::Kernel y el evento resultante haya sido despachado.

Todos los demás observadores de señales, incluido el uso de "sig" para observar "CHLD", no mantienen sus sesiones activas. Si necesita que una sesión permanezca activa cuando solo está observando señales, haga que establezca un alias o uno de sus propios contadores de referencia públicos.

Contadores de referencia públicos.
Una sesión permanecerá activa siempre que tenga uno o más contadores de referencia públicos (o externos) distintos de cero.

Vidas de las Sesiones

"Sesión" como término está algo sobrecargado. Hay dos conceptos relacionados que comparten el nombre. Primero está la clase POE::Session, y los objetos creados con ella o clases relacionadas. Segundo, es una estructura de datos dentro de POE::Kernel que rastrea los objetos POE::Session en juego y los diversos recursos propiedad de cada uno.

La forma en que funciona el recolector de basura de POE es que un objeto de sesión se entrega a POE::Kernel en el momento de la creación. El Kernel retiene ese objeto mientras existan recursos que requieran que la sesión permanezca activa. Cuando todos estos recursos son destruidos o liberados, el objeto de sesión no tiene nada más que desencadene actividad. POE::Kernel notifica al objeto que ha terminado y limpia su contexto de sesión interno. El objeto de sesión es liberado y se autodestruye de la manera habitual de Perl.

Las sesiones pueden detenerse incluso si tienen recursos activos. Por ejemplo, una sesión puede no manejar una señal terminal. En este caso, POE::Kernel fuerza la detención de la sesión y se liberan todos los recursos asociados con la sesión de forma preventiva.

Eventos

Un evento es un mensaje que se envía de una parte de la aplicación POE a otra. Un evento consta del nombre del evento, parámetros opcionales específicos del evento e información OOB (fuera de banda). Un evento puede ser enviado desde el kernel, desde una rueda (wheel) o desde una sesión.

Una aplicación crea un evento con "post", "yield", "call" o incluso "signal". POE::Kernel crea eventos en respuesta a estímulos externos (señales, select, etc.).

Manejadores de eventos

Un evento es manejado por una función llamada manejador de eventos, que es algún código designado para ser llamado cuando se despacha un evento particular. Ver "Gestión de Manejadores de Eventos" y POE::Session.

El término estado se usa a menudo en lugar de manejador de eventos, especialmente al tratar las sesiones como máquinas de estado impulsadas por eventos.

Los manejadores siempre se llaman en contexto escalar para eventos asíncronos (es decir, a través de post()). Los eventos síncronos, invocados con call(), se manejan en el mismo contexto en el que se llamó a call().

Los manejadores de eventos no pueden devolver directamente referencias a objetos en el espacio de nombres "POE". POE::Kernel convertirá estas referencias a cadenas para evitar problemas de temporización con la destrucción de ciertos objetos. Por ejemplo, este manejador de errores causaría errores porque una rueda eliminada no se destruiría cuando uno podría pensar:

sub handle_error {
  warn "Got an error";
  delete $_[HEAP]{wheel};
}

La llamada delete() devuelve el miembro de la rueda eliminado, que luego es devuelto implícitamente por handle_error().

Usando POE con Otros Bucles de Eventos

POE::Kernel soporta cualquier número de bucles de eventos. Dos están incluidos en la distribución base. Históricamente, POE incluía otros bucles, pero fueron movidos a una distribución separada. Puedes encontrarlos y otros bucles en CPAN.

Las interfaces públicas de POE permanecen iguales independientemente del bucle de eventos que se esté utilizando. Dado que la mayoría de los kits de herramientas gráficos incluyen alguna forma de bucle de eventos, el código de backend debería ser portable a todos ellos.

La cooperación de POE con otros bucles de eventos permite que POE se integre en otro software. El bucle de eventos subyacente común impulsa tanto la aplicación como POE. Por ejemplo, al usar POE::Loop::Glib, uno puede integrar POE en Vim, irssi, y así sucesivamente. Los scripts de aplicación pueden entonces aprovechar POE::Component::Client::HTTP (y todo lo demás) para realizar trabajos a gran escala sin bloquear el resto del programa.

Dado que esto es Perl, hay múltiples formas de cargar un bucle de eventos alternativo. La forma más sencilla es cargar el bucle de eventos antes de cargar POE::Kernel.

use Gtk;
use POE;

Recuerda que POE carga POE::Kernel internamente.

POE::Kernel examina los módulos cargados antes que él y detecta que Gtk ha sido cargado. Si POE::Loop::Gtk está disponible, POE lo carga y lo conecta automáticamente a POE::Kernel.

Es menos misterioso cargar directamente la clase POE::Loop apropiada. Sus nombres siguen el formato "POE::Loop::$loop_module_name", donde $loop_module_name es el nombre del módulo del bucle de eventos después de que cada "::" haya sido sustituido por un guión bajo. Se puede abreviar usando la magia del cargador de POE.

use POE qw( Loop::Event_Lib );

POE también reconoce bucles XS, residen en el espacio de nombres "POE::XS::Loop::$loop_module_name". Usarlos puede darte una mejora de rendimiento en tu plataforma, ya que los bucles de eventos son parte del código más usado del sistema. Como siempre, evalúa tu aplicación contra varios bucles para ver cuál es el mejor para tu carga de trabajo y plataforma.

use POE qw( XS::Loop::EPoll );

Por favor, no cargues los módulos de bucle directamente, porque POE no tendrá la oportunidad de inicializar sus estructuras internas todavía. El código escrito de esta manera lanzará errores al inicio. Podría parecer un error en POE, pero es simplemente la forma en que POE está diseñado.

use POE::Loop::IO_Poll;
use POE;

POE::Kernel también soporta directivas de configuración en su propia línea de "use". Un bucle especificado explícitamente de esta manera anulará la lógica de búsqueda.

use POE::Kernel { loop => "Glib" };

Finalmente, uno puede especificar la clase del bucle configurando el nombre de la clase POE::Loop o POE::XS:Loop en la variable de entorno POE_EVENT_LOOP. Este mecanismo se agregó para pruebas que necesitan especificar el bucle desde la distancia.

BEGIN { $ENV{POE_EVENT_LOOP} = "POE::XS::Loop::Poll" }
use POE;

Por supuesto, esto también puede configurarse desde tu shell:

% export POE_EVENT_LOOP='POE::XS::Loop::Poll'
% make test

Muchos bucles de eventos externos soportan sus propios mecanismos de retrollamada. Los métodos "postback()" y "callback()" de POE::Session devuelven referencias de código Perl simples que generarán eventos POE cuando se llamen. Las aplicaciones pueden pasar estas referencias de código a los bucles de eventos para usarlas como retrollamadas.

La distribución de POE incluye dos interfaces de bucle de eventos. CPAN contiene varias más:

POE::Loop::Select (incluido)

Por defecto, POE usa su bucle basado en select() para impulsar su sistema de eventos. Este es quizás el bucle menos eficiente, pero también es el más portable. POE optimiza para la corrección por encima de todo.

POE::Loop::IO_Poll (incluido)

El bucle de eventos IO::Poll proporciona una alternativa que teóricamente escala mejor que select().

POE::Loop::Event (distribución separada)

Este bucle de eventos proporciona interoperabilidad con otros módulos que usan Event. También puede proporcionar una mejora de rendimiento porque Event está escrito en un lenguaje compilado. Desafortunadamente, esto hace que Event sea menos portable que el select() incorporado de Perl.

POE::Loop::Gtk (distribución separada)

Este bucle de eventos permite que los programas funcionen bajo el kit de herramientas gráfico Gtk.

POE::Loop::Tk (distribución separada)

Este bucle de eventos permite que los programas funcionen bajo el kit de herramientas gráfico Tk. Tk tiene algunas restricciones que requieren que POE se comporte de manera extraña.

El bucle de eventos de Tk no se ejecutará a menos que se creen uno o más widgets. Por lo tanto, POE debe crear dicho widget antes de poder ejecutarse. POE::Kernel exporta $poe_main_window para que el desarrollador de la aplicación pueda usar el widget (que es una Ventana Principal), ya que POE no lo necesita más que para despachar eventos.

Crear y usar una Ventana Principal diferente a menudo tiene un resultado indeseado.

POE::Loop::EV (distribución separada)

POE::Loop::EV permite que los programas basados en POE utilicen la biblioteca de eventos EV con pocos o ningún cambio.

POE::Loop::Glib (distribución separada)

POE::Loop::Glib permite que los programas basados en POE utilicen Glib con pocos o ningún cambio. También soporta la integración de programas basados en POE en aplicaciones que ya usan Glib. Por ejemplo, hemos oído que POE se ha integrado con éxito en vim, irssi y xchat a través de este bucle.

POE::Loop::Kqueue (distribución separada)

POE::Loop::Kqueue permite que los programas basados en POE utilicen transparente la biblioteca de eventos kqueue de BSD en sistemas operativos que la soportan.

POE::Loop::Prima (distribución separada)

POE::Loop::Prima permite que los programas basados en POE utilicen el bucle de eventos de Prima con pocos o ningún cambio. Permite que las bibliotecas de POE se utilicen dentro de aplicaciones Prima.

POE::Loop::Wx (distribución separada)

POE::Loop::Wx permite que los programas basados en POE utilicen el bucle de eventos de Wx con pocos o ningún cambio. Permite que las bibliotecas de POE se utilicen dentro de aplicaciones Wx, como Padre.

POE::XS::Loop::EPoll (distribución separada)

POE::XS::Loop::EPoll permite que los componentes de POE utilicen transparente la biblioteca de eventos EPoll en sistemas operativos que la soportan.

POE::XS::Loop::Poll (distribución separada)

POE::XS::Loop::Poll es un bucle de eventos libpoll basado en C de mayor rendimiento. Reemplaza parte del código caliente de Perl de POE con C para un mejor rendimiento.

Otros Bucles de Eventos (distribuciones separadas)

POE puede ser extendido para manejar otros bucles de eventos. Se invita a los desarrolladores a trabajar con nosotros para soportar sus bucles favoritos.

MÉTODOS PÚBLICOS

POE::Kernel encapsula una gran cantidad de funcionalidades. La documentación para cada conjunto de funcionalidades está agrupada por propósito.

Gestión y Acceso al Kernel

ID

ID() actualmente devuelve el identificador único de POE::Kernel. Cada instancia de Kernel recibe un ID globalmente único al nacer. has_forked() altera el ID para que cada proceso hijo también tenga uno único.

% perl -wl -MPOE -e 'print $poe_kernel->ID'
macbookpoe.local-4d5305de-0000e6b8-00000001

El contenido de estos IDs puede cambiar con el tiempo. Tu código no debe depender del formato actual.

Advertencia de Deprecación 2011-02-09

Tu código no debe depender de que ID() siga siendo único. La unicidad se eliminará en una futura versión de POE. Si requieres IDs únicos, por favor consulta alguno de los excelentes módulos GUID y/o UUID en CPAN:

http://search.cpan.org/search?query=GUID&mode=dist
http://search.cpan.org/search?query=UUID&mode=dist

POE no requiere IDs de kernel global o universalmente únicos. La creación y el mantenimiento de estos IDs añade una sobrecarga al método has_forked() de POE::Kernel. Otros módulos lo hacen mejor, bajo demanda, sin incurrir en sobrecarga para aquellos que no los necesitan.

run

run() ejecuta el despachador de eventos de POE::Kernel. No devolverá el control hasta que todas las sesiones hayan terminado. run() es un método de clase, por lo que no se necesita una referencia a POE::Kernel para iniciar la ejecución de un programa.

use POE;
POE::Session->create( ... ); # una o más
POE::Kernel->run();          # ponerlos todos en marcha
exit;

POE implementa el patrón Reactor en su núcleo. Los eventos se despachan a funciones y métodos a través de callbacks. El código detrás de run() espera y despacha eventos.

run() no devolverá el control hasta que cada sesión haya terminado. Esto incluye las sesiones que se crearon mientras run() estaba en ejecución.

POE::Kernel imprimirá un mensaje fuerte si un programa crea sesiones pero no llama a run(). Antes de esta advertencia, recibimos toneladas de informes de errores del tipo "mi programa POE no hace nada". Resultó que la gente olvidaba iniciar un despachador de eventos, por lo que los eventos nunca se despachaban.

Si la falta de una llamada a run() es deliberada, quizás porque algún otro bucle de eventos ya tiene el control, puedes evitar el mensaje llamándolo antes de crear una sesión. run() en ese momento inicializará POE y devolverá el control inmediatamente. POE::Kernel se dará por satisfecho de que se llamó a run(), aunque POE no haya tomado el control del bucle de eventos.

use POE;
POE::Kernel->run(); # silenciar la advertencia
POE::Session->create( ... );
exit;

Sin embargo, ten en cuenta que esto varía de un bucle de eventos a otro. Si una implementación particular de POE::Loop no lo soporta, eso es probablemente un error. Por favor, presenta un informe de error al propietario del módulo POE::Loop relevante.

run_one_timeslice

run_one_timeslice() despacha cualquier evento que esté listo para ser entregado. Estos eventos incluyen temporizadores que están listos, mensajes asíncronos que necesitan ser entregados, señales que requieren manejo y notificaciones para archivos con E/S pendiente. No confíes demasiado en el orden de los eventos. run_one_timeslice() está definido por el bucle de eventos subyacente, y su temporización puede variar.

run() se implementa de manera similar a

run_one_timeslice() while $session_count > 0;

run_one_timeslice() se puede utilizar para mantener ejecutándose el despachador de POE::Kernel mientras se emula un comportamiento bloqueante. El patrón se implementa con una bandera que se establece cuando ocurre algún evento asíncrono. Un bucle llama a run_one_timeslice() hasta que se establece esa bandera. Por ejemplo:

my $done = 0;
sub handle_some_event {
  $done = 1;
}
$kernel->run_one_timeslice() while not $done;

Ten cuidado. El ejemplo anterior entrará en un bucle infinito si POE::Kernel ha terminado pero $done nunca se establece. El bucle nunca terminará, aunque no quede nada que establezca $done.

run_while SCALAR_REF

run_while() es una versión **experimental** de run_one_timeslice() que solo devolverá el control cuando no queden más sesiones activas, o el valor del escalar referenciado se vuelva falso.

Aquí hay una versión del ejemplo de run_one_timeslice() usando run_while() en su lugar:

my $job_count = 3;
sub handle_some_event {
  $job_count--;
}
$kernel->run_while(\$job_count);

has_forked

my $pid = fork();
die "Unable to fork" unless defined $pid;
unless( $pid ) {
    $poe_kernel->has_forked;
}

Informa al kernel que ahora se está ejecutando en un nuevo proceso. Esto permite al kernel restablecer algunos datos internos para ajustarse a la nueva situación.

has_forked() debe ser llamado en el proceso hijo si deseas ejecutar el mismo kernel. Sin embargo, si deseas que el proceso hijo tenga un nuevo kernel, debes llamar a "stop" en su lugar.

Nota: Los internos de POE detectarán si ocurrió un fork antes de run() y llamarán a has_forked() automáticamente. Si no estás seguro de si necesitas llamarlo o no, por favor habilita "ASSERT_USAGE" y POE emitirá una advertencia si es necesario.

stop

stop() hace que POE::Kernel->run() devuelva el control prematuramente. Lo hace vaciando la cola de eventos, liberando todos los recursos utilizados y deteniendo cada sesión activa. stop() no está diseñado para usarse a la ligera. Procede con precaución.

Advertencias:

La sesión que llama a stop() no será completamente DESTRUIDA hasta que devuelva el control. Invocar un manejador de eventos en la sesión requiere una referencia a esa sesión, y las referencias débiles están prohibidas en POE por razones de compatibilidad con versiones anteriores, por lo que tiene sentido que la última sesión no sea recolectada por el recolector de basura de inmediato.

Las sesiones no son notificadas sobre su destrucción. Si algo depende de que se entregue _stop, se romperá y/o tendrá fugas de memoria.

stop() todavía se considera experimental. Se añadió para mejorar el soporte de fork() para POE::Wheel::Run. Si resulta ser problemático e irresoluble, se eliminará sin mucho aviso.

stop() es magia avanzada. Se invita a los programadores que creen necesitarlo a familiarizarse con su código fuente.

Ver "Running POE::Kernel in the Child" en POE::Wheel::Run para un ejemplo de cómo usar esta funcionalidad.

Mensajes Asíncronos (Eventos FIFO)

Los mensajes asíncronos son eventos que se despachan en el orden en que fueron encolados (el primero en entrar es el primero en salir, también conocido como orden first-in/first-out, o FIFO). Estos métodos encolan nuevos mensajes para su entrega. El acto de encolar un mensaje mantiene al remitente vivo al menos hasta que el mensaje sea entregado.

post DESTINATION, EVENT_NAME [, PARAMETER_LIST]

post() encola un mensaje para ser despachado a una sesión DESTINATION particular. El mensaje será manejado por el código asociado con EVENT_NAME. Si se incluye una PARAMETER_LIST, sus valores también serán pasados.

POE::Session->create(
  inline_states => {
    _start => sub {
      $_[KERNEL]->post( $_[SESSION], "event_name", 0 );
    },
    event_name => sub {
      print "$_[ARG0]\n";
      $_[KERNEL]->post( $_[SESSION], "event_name", $_[ARG0] + 1 );
    },
  }
);

post() devuelve un valor booleano que indica si el mensaje se encoló con éxito. Si post() devuelve falso, $! se establece para explicar el fallo:

ESRCH ("No such process") - La sesión DESTINATION no existía en el momento en que se llamó a post().

yield EVENT_NAME [, PARAMETER_LIST]

yield() es un atajo para post() donde la sesión destino es la misma que la remitente. Este ejemplo es equivalente al de post():

POE::Session->create(
  inline_states => {
    _start => sub {
      $_[KERNEL]->yield( "event_name", 0 );
    },
    event_name => sub {
      print "$_[ARG0]\n";
      $_[KERNEL]->yield( "event_name", $_[ARG0] + 1 );
    },
  }
);

Al igual que con post(), yield() devuelve el control inmediatamente, y el EVENT_NAME encolado se despacha más tarde. Esto puede ser confuso si ya estás familiarizado con la concurrencia.

yield() siempre debería tener éxito, por lo que no devuelve un valor significativo.

Mensajes Síncronos

A veces es necesario que el código se invoque de inmediato. Por ejemplo, algunos recursos deben ser atendidos de inmediato, o de lo contrario seguirán informando fielmente de su disponibilidad. Estos informes aparecerían como un flujo de eventos duplicados. Los eventos síncronos también pueden evitar que los datos se vuelvan obsoletos entre el momento en que se encola un evento y el momento en que se entrega.

Los manejadores de eventos síncronos tienen prioridad sobre la cola de eventos de POE, por lo que deben realizar tareas simples de duración limitada. Los eventos síncronos que necesitan hacer más que solo atender un recurso deben pasar la información del recurso a un manejador asíncrono. De lo contrario, las operaciones síncronas ocurrirán fuera de orden en relación con los eventos asíncronos. Es muy fácil tener condiciones de carrera o romper la causalidad de esta manera, así que trata de evitarlo a menos que estés de acuerdo con las consecuencias.

POE proporciona estas formas de llamar a los manejadores de mensajes de inmediato.

call DESTINATION, EVENT_NAME [, PARAMETER_LIST]

La semántica de call() es casi idéntica a la de post(). call() invoca el manejador de un DESTINATION asociado con un EVENT_NAME. Se pasará una PARAMETER_LIST opcional al manejador del mensaje. La diferencia, sin embargo, es que el manejador se invocará inmediatamente, incluso antes de que call() devuelva el control.

call() devuelve el valor devuelto por el manejador de EVENT_NAME. Puede hacer esto porque el manejador se invoca antes de que call() devuelva el control. Por lo tanto, call() puede usarse como un accesor, aunque hay mejores formas de lograr un comportamiento de acceso simple.

POE::Session->create(
  inline_states => {
    _start => sub {
      print "Got: ", $_[KERNEL]->call($_[SESSION], "do_now"), "\n";
    },
    do_now => sub {
      return "some value";
    }
  }
);

Las clases POE::Wheel utilizan call() para entregar síncronamente notificaciones de E/S. Esto evita un flujo de

call() puede fallar de la misma manera y por las mismas razones que post(). En caso de fallo, $! se establecerá en algún valor distinto de cero que indique el motivo. Dado que call() puede devolver undef como algo habitual, se recomienda que $! se compruebe tanto para la condición de error como para la explicación.

ESRCH ("No such process") - La sesión DESTINATION no existía en el momento en que se llamó a post().

Eventos de temporizador (mensajes retrasados)

A menudo es útil esperar un tiempo determinado o hasta que haya transcurrido una cierta cantidad de tiempo. POE admite esto con eventos que se posponen hasta un tiempo absoluto ("alarmas") o hasta que haya transcurrido una cierta duración de tiempo ("retrasos").

Las interfaces de temporizador se dividen además en dos grupos. Un grupo identifica los temporizadores por los nombres de sus eventos asociados. Otro grupo identifica los temporizadores por un identificador único devuelto por los constructores de temporizadores. Técnicamente, ambos se basan en nombres, pero los temporizadores "basados en identificadores" proporcionan un segundo identificador más específico para identificar temporizadores individuales.

Los temporizadores solo se pueden configurar para la sesión actual. Este diseño se modeló a partir de alarm() y SIGALRM, que solo afectan al proceso UNIX actual. Cada sesión tiene un espacio de nombres separado para los nombres de los temporizadores. Los métodos de temporizador llamados en una sesión no pueden afectar a los temporizadores de otra. Como habrás notado, gran parte de la API de POE está diseñada para evitar que las sesiones interfieran entre sí.

La mejor manera de simular mensajes inter-sesión diferidos es enviar un mensaje inmediato que haga que el destino establezca un temporizador. El temporizador del destino difiere entonces la acción solicitada. Esta forma es preferible porque el tiempo dedicado a comunicar la solicitud entre sesiones puede no ser trivial, especialmente si las sesiones están separadas por una red. El destino puede determinar cuánto tiempo queda en el temporizador solicitado y ajustar su tiempo de espera en consecuencia.

Temporizadores basados en nombres

Los temporizadores basados en nombres se identifican por los nombres de eventos utilizados para configurarlos. Es posible que diferentes sesiones utilicen los mismos nombres de eventos de temporizador, ya que cada sesión es un compartimento separado con su propio espacio de nombres de temporizadores. Es posible que una sesión tenga varios temporizadores para un determinado evento, pero los resultados pueden ser sorprendentes. Tenga cuidado al utilizar los métodos de temporizador correctos.

Los métodos de temporizador basados en nombres son alarm(), alarm_add(), delay() y delay_add().

alarm NOMBRE_EVENTO [, TIEMPO_EPOCH [, LISTA_PARAMETROS] ]

alarm() borra todos los temporizadores existentes en la sesión actual con el mismo NOMBRE_EVENTO. Luego establece un nuevo temporizador, llamado NOMBRE_EVENTO, que se activará con NOMBRE_EVENTO en la sesión actual cuando se alcance TIEMPO_EPOCH. Se puede pasar una LISTA_PARAMETROS opcional al manejador del temporizador.

Omitir TIEMPO_EPOCH y los parámetros posteriores hace que alarm() borre los temporizadores NOMBRE_EVENTO en la sesión actual sin establecer uno nuevo.

TIEMPO_EPOCH es la hora epoch de UNIX. Ya sabes, segundos desde la medianoche del 1 de enero de 1970. POE utiliza Time::HiRes::time(), que permite que TIEMPO_EPOCH sea (o incluya) segundos fraccionarios.

POE admite segundos fraccionarios, pero la precisión disminuye drásticamente después de 1/100 de segundo. El rendimiento variará según la velocidad de tu CPU y la resolución de tiempo de tu sistema operativo.

Asegúrate de utilizar Time::HiRes::time() en lugar del método incorporado time() de Perl si la precisión sub-segundo es importante. El método incorporado time() devuelve floor( Time::HiRes::time()), que casi siempre es una fracción de segundo en el pasado. Por ejemplo, la hora de alta resolución podría ser 1200941422.89996. En ese mismo instante, time() sería 1200941422. Una alarma para time() + 0.5 estaría 0.39996 segundos en el pasado, por lo que se enviaría inmediatamente (si no antes).

La cola de eventos de POE está ordenada por tiempo, por lo que un temporizador cuya fecha de vencimiento sea anterior a time() se entregará antes que otros eventos, pero no antes que los temporizadores con fechas de vencimiento aún más tempranas. Por lo tanto, una llamada a alarm() con un TIEMPO_EPOCH anterior a time() salta al frente de la cola.

Todos los temporizadores se implementan de forma idéntica internamente, independientemente de cómo se configuren. Por lo tanto, alarm() borrará tranquilamente los temporizadores configurados por otros medios.

POE::Session->create(
  inline_states => {
    _start => sub {
      $_[KERNEL]->alarm( tick => time() + 1, 0 );
    },
    tick => sub {
      print "tick $_[ARG0]\n";
      $_[KERNEL]->alarm( tock => time() + 1, $_[ARG0] + 1 );
    },
    tock => sub {
      print "tock $_[ARG0]\n";
      $_[KERNEL]->alarm( tick => time() + 1, $_[ARG0] + 1 );
    },
  }
);

alarm() devuelve 0 en caso de éxito o un valor verdadero en caso de fallo. Generalmente EINVAL para indicar un parámetro no válido, como un NOMBRE_EVENTO indefinido.

alarm_add NOMBRE_EVENTO, TIEMPO_EPOCH [, LISTA_PARAMETROS]

alarm_add() se utiliza para añadir un nuevo temporizador de alarma llamado NOMBRE_EVENTO sin borrar los temporizadores existentes. TIEMPO_EPOCH es un parámetro obligatorio. Por lo demás, la semántica es idéntica a la de alarm().

Un programa puede utilizar alarm_add() sin utilizar primero alarm().

POE::Session->create(
  inline_states => {
    _start => sub {
      $_[KERNEL]->alarm_add( tick => time() + 1.0, 1_000_000 );
      $_[KERNEL]->alarm_add( tick => time() + 1.5, 2_000_000 );
    },
    tick => sub {
      print "tick $_[ARG0]\n";
      $_[KERNEL]->alarm_add( tock => time() + 1, $_[ARG0] + 1 );
    },
    tock => sub {
      print "tock $_[ARG0]\n";
      $_[KERNEL]->alarm_add( tick => time() + 1, $_[ARG0] + 1 );
    },
  }
);

alarm_add() devuelve 0 en caso de éxito o EINVAL si NOMBRE_EVENTO o TIEMPO_EPOCH es indefinido.

delay NOMBRE_EVENTO [, SEGUNDOS_DURACION [, LISTA_PARAMETROS] ]

delay() borra todos los temporizadores existentes en la sesión actual con el mismo NOMBRE_EVENTO. Luego establece un nuevo temporizador, llamado NOMBRE_EVENTO, que se activará con NOMBRE_EVENTO en la sesión actual cuando hayan transcurrido SEGUNDOS_DURACION desde "ahora". Se puede pasar una LISTA_PARAMETROS opcional al manejador del temporizador.

Omitir SEGUNDOS_DURACION y los parámetros subsiguientes hace que delay() borre los temporizadores NOMBRE_EVENTO en la sesión actual sin establecer uno nuevo.

SEGUNDOS_DURACION puede ser o incluir segundos fraccionarios. Como con todos los temporizadores de POE, la precisión disminuye drásticamente después de 1/100 de segundo. El rendimiento variará según la velocidad de tu CPU y la resolución de tiempo de tu sistema operativo.

La cola de eventos de POE está ordenada por tiempo, por lo que un temporizador cuya fecha de vencimiento sea anterior a time() se entregará antes que otros eventos, pero no antes que los temporizadores con fechas de vencimiento aún más tempranas. Por lo tanto, una llamada a delay() con una SEGUNDOS_DURACION cero o negativa salta al frente de la cola.

delay() puede considerarse una forma abreviada de alarm(), pero existen sutiles diferencias en los problemas de tiempo. Este código es aproximadamente equivalente al ejemplo de alarm().

POE::Session->create(
  inline_states => {
    _start => sub {
      $_[KERNEL]->delay( tick => 1, 0 );
    },
    tick => sub {
      print "tick $_[ARG0]\n";
      $_[KERNEL]->delay( tock => 1, $_[ARG0] + 1 );
    },
    tock => sub {
      print "tock $_[ARG0]\n";
      $_[KERNEL]->delay( tick => 1, $_[ARG0] + 1 );
    },
  }
);

delay() devuelve 0 en caso de éxito o un motivo de fallo: EINVAL si NOMBRE_EVENTO es indefinido.

delay_add NOMBRE_EVENTO, SEGUNDOS_DURACION [, LISTA_PARAMETROS]

delay_add() se utiliza para añadir un nuevo temporizador de retraso llamado NOMBRE_EVENTO sin borrar los temporizadores existentes. SEGUNDOS_DURACION es un parámetro obligatorio. Por lo demás, la semántica es idéntica a la de delay().

Un programa puede utilizar delay_add() sin utilizar primero delay().

POE::Session->create(
  inline_states => {
    _start => sub {
      $_[KERNEL]->delay_add( tick => 1.0, 1_000_000 );
      $_[KERNEL]->delay_add( tick => 1.5, 2_000_000 );
    },
    tick => sub {
      print "tick $_[ARG0]\n";
      $_[KERNEL]->delay_add( tock => 1, $_[ARG0] + 1 );
    },
    tock => sub {
      print "tock $_[ARG0]\n";
      $_[KERNEL]->delay_add( tick => 1, $_[ARG0] + 1 );
    },
  }
);

delay_add() devuelve 0 en caso de éxito o EINVAL si NOMBRE_EVENTO o TIEMPO_EPOCH es indefinido.

Temporizadores basados en identificadores

Una segunda forma de gestionar los temporizadores es a través de identificadores. Configurar una alarma o un retraso con los métodos "identificador" permite a un programa manipular varios temporizadores con el mismo nombre en la misma sesión. Sin embargo, como se ha tratado en alarm() y delay(), es posible mezclar llamadas de temporizadores nombrados e identificados, pero las consecuencias pueden no ser siempre las esperadas.

alarm_set NOMBRE_EVENTO, TIEMPO_EPOCH [, LISTA_PARAMETROS]

alarm_set() establece una alarma, devolviendo un identificador único que se puede utilizar para ajustar o eliminar la alarma más tarde. A diferencia de alarm(), no borra previamente los temporizadores existentes con el mismo NOMBRE_EVENTO. Por lo demás, la semántica es idéntica a la de alarm().

POE::Session->create(
  inline_states => {
    _start => sub {
      $_[HEAP]{alarm_id} = $_[KERNEL]->alarm_set(
        party => time() + 1999
      );
      $_[KERNEL]->delay(raid => 1);
    },
    raid => sub {
      $_[KERNEL]->alarm_remove( delete $_[HEAP]{alarm_id} );
    },
  }
);

alarm_set() devuelve falso si falla y establece $! con la explicación. $! será EINVAL si NOMBRE_EVENTO o TIEMPO es indefinido.

alarm_adjust ID_ALARMA, DELTA_SEGUNDOS

alarm_adjust() ajusta la hora de vencimiento de un temporizador existente en DELTA_SEGUNDOS, que puede ser positivo o negativo. Incluso puede ser cero, pero eso no es muy útil. En caso de éxito, devuelve la nueva hora de vencimiento del temporizador desde el inicio de la época de UNIX.

Es posible utilizar alarm_adjust() en temporizadores creados por delay_set(), así como por alarm_set().

Este ejemplo adelanta la hora de vencimiento de una alarma diez segundos.

use POSIX qw(strftime);
POE::Session->create(
  inline_states => {
    _start => sub {
      $_[HEAP]{alarm_id} = $_[KERNEL]->alarm_set(
        party => time() + 1999
      );
      $_[KERNEL]->delay(postpone => 1);
    },
    postpone => sub {
      my $new_time = $_[KERNEL]->alarm_adjust(
        $_[HEAP]{alarm_id}, -10
      );
      print(
        "Now we're gonna party like it's ",
        strftime("%F %T", gmtime($new_time)), "\n"
      );
    },
  }
);

alarm_adjust() devuelve falso booleano si falla, estableciendo $! en el motivo. $! puede ser EINVAL si ID_ALARMA o DELTA_SEGUNDOS son indefinidos. Puede ser ESRCH si ID_ALARMA ya no se refiere a un temporizador pendiente. $! también puede contener EPERM si ID_ALARMA es válido pero pertenece a otra sesión.

alarm_remove ID_ALARMA

alarm_remove() elimina la alarma identificada por ALARM_ID. ALARM_ID proviene de una llamada anterior a alarm_set() o delay_set().

Al tener éxito, alarm_remove() devuelve algo verdadero según su contexto. En un contexto de lista, devuelve tres elementos: el nombre del evento de la alarma eliminada, la hora UNIX en la que debía activarse y una referencia a la LISTA_DE_PARÁMETROS (si la hay) asignada al temporizador cuando se creó. Si es necesario, el temporizador puede volver a configurarse con esta información.

POE::Session->create(
  inline_states => {
    _start => sub {
      $_[HEAP]{alarm_id} = $_[KERNEL]->alarm_set(
        party => time() + 1999
      );
      $_[KERNEL]->delay(raid => 1);
    },
    raid => sub {
      my ($name, $time, $param) = $_[KERNEL]->alarm_remove(
        $_[HEAP]{alarm_id}
      );
      print(
        "Se eliminó la alarma para el evento $name programada para las $time con @$param\n"
      );
      # O volver a configurarla, si lo deseas. Posiblemente después de modificarla.
      $_[KERNEL]->alarm_set($name, $time, @$param);
    },
  }
);

En un contexto escalar, devuelve una referencia a una lista de los tres elementos anteriores.

# Eliminar y restablecer una alarma.
my $alarm_info = $_[KERNEL]->alarm_remove( $alarm_id );
my $new_id = $_[KERNEL]->alarm_set(
  $alarm_info[0], $alarm_info[1], @{$alarm_info[2]}
);

Sin embargo, al fallar, alarm_remove() devuelve un valor booleano falso y establece $! con la razón por la que la llamada falló:

EINVAL ("Argumento inválido") indica un problema con uno o más parámetros, generalmente un ALARM_ID indefinido.

ESRCH ("No such process") indica que ALARM_ID no se refería a una alarma pendiente.

EPERM ("Operation not permitted"). Una sesión no puede eliminar una alarma que no le pertenece.

alarm_remove_all

alarm_remove_all() elimina todos los temporizadores pendientes para la sesión actual, independientemente del método de creación o tipo. Este método no toma argumentos. Devuelve información sobre las alarmas que fueron eliminadas, ya sea como una lista de alarmas o una referencia a una lista, dependiendo de si alarm_remove_all() se llama en contexto escalar o de lista.

La información de cada alarma eliminada es idéntica al formato explicado en alarm_remove().

sub some_event_handler {
  my @removed_alarms = $_[KERNEL]->alarm_remove_all();
  foreach my $alarm (@removed_alarms) {
    my ($name, $time, $param) = @$alarm;
    ...;
  }
}

delay_set EVENT_NAME, DURATION_SECONDS [, PARAMETER_LIST]

delay_set() establece un temporizador para DURATION_SECONDS en el futuro. El temporizador se enviará al código asociado con EVENT_NAME en la sesión actual. Una LISTA_DE_PARÁMETROS opcional se pasará al manejador. Devuelve el mismo tipo de información que alarm_set().

POE::Session->create(
  inline_states => {
    _start => sub {
      $_[KERNEL]->delay_set("later", 5, "hello", "world");
    },
    later => sub {
      print "@_[ARG0..#$_]\n";
    }
  }
);

delay_adjust ALARM_ID, SECONDS_FROM_NOW

delay_adjust() cambia la hora de vencimiento de un temporizador a SECONDS_FROM_NOW. Es útil para actualizar temporizadores de tipo watchdog o de tiempo de espera. En caso de éxito, devuelve la nueva hora absoluta UNIX en la que vencerá el temporizador.

Es posible que delay_adjust() ajuste temporizadores creados por alarm_set(), así como por delay_set().

use POSIX qw(strftime);
POE::Session->create(
  inline_states => {
    # Configuración.
    # ... omitido.
    got_input => sub {
      my $new_time = $_[KERNEL]->delay_adjust(
        $_[HEAP]{input_timeout}, 60
      );
      print(
        "Se actualizó el tiempo de espera de entrada. El próximo puede ocurrir a las ",
        strftime("%F %T", gmtime($new_time)), "\n"
      );
    },
  }
);

En caso de fallo, devuelve falso booleano y establece $! a una razón para el fallo. Consulte la explicación de $! para alarm_adjust().

delay_remove no es necesario

No existe delay_remove(). Todos los temporizadores son internamente idénticos, por lo que alarm_remove() funcionará con los IDs de temporizador devueltos por delay_set().

delay_remove_all no es necesario

No existe delay_remove_all(). Todos los temporizadores son internamente idénticos, por lo que alarm_remove_all() los borra a todos, independientemente de cómo fueron creados.

Identificadores de Sesión (IDs y Alias)

Una sesión puede ser referenciada por sus referencias de objeto (ya sean bendecidas o convertidas a cadena), un ID de sesión o uno o más nombres simbólicos que llamamos alias.

Cada sesión está representada por un objeto, por lo que las referencias de sesión son bastante sencillas. POE::Kernel puede referenciar estos objetos. Por ejemplo, post() puede usar $_[SENDER] como destino:

POE::Session->create(
  inline_states => {
    _start => sub { $_[KERNEL]->alias_set("echoer") },
    ping => sub {
      $_[KERNEL]->post( $_[SENDER], "pong", @_[ARG0..$#_] );
    }
  }
);

POE también reconoce objetos de Sesión convertidos a cadena para mayor comodidad y como una forma de referencia débil. Aquí $_[SENDER] se envuelve en comillas para convertirlo a cadena:

POE::Session->create(
  inline_states => {
    _start => sub { $_[KERNEL]->alias_set("echoer") },
    ping => sub {
      $_[KERNEL]->post( "$_[SENDER]", "pong", @_[ARG0..$#_] );
    }
  }
);

Cada sesión recibe un ID único en el momento de su creación. No habrá dos sesiones activas con el mismo ID, pero los IDs pueden reutilizarse con el tiempo. La combinación de un ID de kernel y un ID de sesión debería ser suficiente como identificador único global.

POE::Session->create(
  inline_states => {
    _start => sub { $_[KERNEL]->alias_set("echoer") },
    ping => sub {
      $_[KERNEL]->delay(
        pong_later => rand(5), $_[SENDER]->ID, @_[ARG0..$#_]
      );
    },
    pong_later => sub {
      $_[KERNEL]->post( $_[ARG0], "pong", @_[ARG1..$#_] );
    }
  }
);

Los kernels también mantienen un espacio de nombres o diccionario global de sesiones que puede usarse para mapear un alias simbólico a una sesión. Una vez que se ha creado un mapeo de alias, ese alias puede usarse para referirse a la sesión donde sea que se pueda especificar una sesión.

En los ejemplos anteriores, cada servicio de eco ha establecido un alias de "echoer". Otra sesión puede enviar una solicitud de ping a la sesión de eco utilizando ese alias en lugar de un objeto de sesión o un ID. Por ejemplo:

POE::Session->create(
  inline_states => {
    _start => sub { $_[KERNEL]->post(echoer => ping => "whee!" ) },
    pong => sub { print "@_[ARG0..$#_]\n" }
  }
);

Una sesión con un alias no se detendrá hasta que toda la demás actividad se haya detenido. Los alias se tratan como una especie de observador de eventos. Los eventos provienen de sesiones activas. Por lo tanto, los alias se vuelven inútiles cuando ya no quedan sesiones activas. En lugar de dejar el programa en ejecución en un estado de "zombi", POE detecta esta condición de interbloqueo y activa una limpieza. Consulte "Signal Classes" para obtener más información.

alias_set ALIAS

alias_set() mapea un ALIAS en el diccionario de POE::Kernel a la sesión actual. El ALIAS puede usarse posteriormente casi en cualquier lugar donde se espere una referencia de sesión, una referencia convertida a cadena o un ID.

Las sesiones pueden tener más de un alias. Cada alias debe definirse en una llamada separada a alias_set(). Un solo alias no puede hacer referencia a más de una sesión.

Se muestran ejemplos de alias múltiples anteriormente.

alias_set() devuelve 0 en caso de éxito, o un indicador de error distinto de cero: EEXIST ("File exists") indica que el alias ya está asignado a otra sesión diferente.

alias_remove ALIAS

alias_remove() elimina un ALIAS para la sesión actual del diccionario de POE::Kernel. El ALIAS ya no hará referencia a la sesión actual. Esto no afecta negativamente a los eventos que ya se han enviado a la cola de POE. La resolución de alias ocurre en el momento de post(), no en el momento de la entrega.

POE::Session->create(
  inline_states => {
    _start => sub {
      $_[KERNEL]->alias_set("short_window");
      $_[KERNEL]->delay(close_window => 1);
    },
    close_window => {
      $_[KERNEL]->alias_remove("short_window");
    }
  }
);

alias_remove() devuelve 0 en caso de éxito o un código de error distinto de cero: ESRCH ("No such process") indica que el ALIAS no está actualmente en el diccionario de POE::Kernel. EPERM ("Operation not permitted") significa que la sesión actual no puede eliminar el ALIAS porque está en uso por alguna otra sesión.

alias_resolve ALIAS

alias_resolve() devuelve una referencia de sesión que corresponde a un ALIAS dado. De hecho, el ALIAS puede ser una referencia de sesión convertida a cadena, un ID de sesión o un alias registrado previamente por alias_set().

Un uso para alias_resolve() es detectar si otra sesión ha desaparecido:

unless (defined $_[KERNEL]->alias_resolve("Elvis")) {
  print "Elvis ha dejado el edificio.\n";
}

Como se mencionó anteriormente, alias_resolve() devuelve una referencia de sesión o undef en caso de fallo. El fallo también establece $! a ESRCH ("No such process") cuando el ALIAS no está actualmente en el diccionario de POE::Kernel.

alias_list [SESSION_REFERENCE]

alias_list() devuelve una lista de alias asociados con una SESIÓN específica, o con la sesión actual si se omite SESSION. alias_list() devuelve una lista vacía si la SESIÓN solicitada no tiene alias.

SESSION puede ser una referencia de sesión (bendecida o convertida a cadena), un ID de sesión o un alias de sesión.

POE::Session->create(
  inline_states => {
    $_[KERNEL]->alias_set("mi");
    print(
      "Los nombres que me doy: ",
      join(", ", $_[KERNEL]->alias_list()),
      "\n"
    );
  }
);

DESCRIPTION

POE::Kernel is the heart of the POE event loop. It's responsible for dispatching events, managing timers and I/O watchers, and generally keeping things running.

There is only one POE::Kernel instance, and it's available via the special variable $_[KERNEL].

Kernel Methods

All POE::Kernel methods are available to any session. If you are calling a POE::Kernel method from within a POE::Session state, you may access it as $_[KERNEL]. Otherwise, you may call it as POE::Kernel->instance()->method().

The following methods are available:

Session IDs and References

ID()

ID() returns the session ID of the current session. This is primarily used when a session needs to keep track of other sessions, or when it needs to pass its session ID to another process.

ID_id_to_session SESSION_ID

ID_id_to_session() converts a session ID into a POE::Session object. This is useful when a session needs to interact with another session whose ID it already knows.

This is the inverse of ID(). This method is a wrapper around the Kernel's internal session hash, which is slightly more efficient than calling POE::Session->resolve_ids(), but less flexible. Use this method when you are certain that you have the correct session ID and want the fastest possible lookup. The POE::Session->solve() method is also available and is also slightly faster and somewhat less flexible.

unless (defined $_[KERNEL]->ID_id_to_session($session_id)) {
  print "Session $session_id doesn't exist.\n";
}

ID_id_to_session() returns undef if a lookup failed. $! will be set to ESRCH ("No such process").

ID_session_to_id SESSION_REFERENCE

ID_session_to_id() converts a blessed or stringified SESSION_REFERENCE into a session ID. It's more practical for stringified references, as programs can call the POE::Session ID() method on the blessed ones. These statements are equivalent:

$id = $_[SENDER]->ID();
$id = $_[KERNEL]->ID_session_to_id($_[SENDER]);
$id = $_[KERNEL]->ID_session_to_id("$_[SENDER]");

As with other POE::Kernel lookup methods, ID_session_to_id() returns undef on failure, setting $! to ESRCH ("No such process").

I/O Watchers (Selects)

No event system would be complete without the ability to asynchronously watch for I/O events. POE::Kernel implements the lowest level watchers, which are called "selects" because they were historically implemented using Perl's built-in select(2) function.

Applications handle I/O readiness events by performing some activity on the underlying filehandle. Read-readiness might be handled by reading from the handle. Write-readiness by writing to it.

All I/O watcher events include two parameters. "ARG0" contains the handle that is ready for work. "ARG1" contains an integer describing what's ready.

sub handle_io {
  my ($handle, $mode) = @_[ARG0, ARG1];
  print "File $handle is ready for ";
  if ($mode == 0) {
    print "reading";
  }
  elsif ($mode == 1) {
    print "writing";
  }
  elsif ($mode == 2) {
    print "out-of-band reading";
  }
  else {
    die "unknown mode $mode";
  }
  print "\n";
  # ... do something here
}

The remaining parameters, @_[ARG2..$%_], contain additional parameters that were passed to the POE::Kernel method that created the watcher.

POE::Kernel conditions filehandles to be 8-bit clean and non-blocking. Programs that need them conditioned differently should set them up after starting POE I/O watchers. If you are running a Perl older than 5.8.1 and is using tied filehandles, you need to set non-blocking mode yourself as IO::Handle does not work well. See https://rt.cpan.org/Ticket/Display.html?id=67545 for more info.

I/O watchers will prevent sessions from stopping.

select_read FILE_HANDLE [, EVENT_NAME [, ADDITIONAL_PARAMETERS] ]

select_read() starts or stops the current session from watching for incoming data on a given FILE_HANDLE. The watcher is started if EVENT_NAME is specified, or stopped if it's not. ADDITIONAL_PARAMETERS, if specified, will be passed to the EVENT_NAME handler as @_[ARG2..$#_].

POE::Session->create(
  inline_states => {
    _start => sub {
      $_[HEAP]{socket} = IO::Socket::INET->new(
        PeerAddr => "localhost",
        PeerPort => 25,
      );
      $_[KERNEL]->select_read( $_[HEAP]{socket}, "got_input" );
      $_[KERNEL]->delay(timed_out => 1);
    },
    got_input => sub {
      my $socket = $_[ARG0];
      while (sysread($socket, my $buf = "", 8192)) {
        print $buf;
      }
    },
    timed_out => sub {
      $_[KERNEL]->select_read( delete $_[HEAP]{socket} );
    },
  }
);

select_read() does not return anything significant.

select_write FILE_HANDLE [, EVENT_NAME [, ADDITIONAL_PARAMETERS] ]

select_write() follows the same semantics as select_read(), but it starts or stops a watcher that looks for write-readiness. That is, when EVENT_NAME is delivered, it means that FILE_HANDLE is ready to be written to.

select_write() does not return anything significant.

select_expedite FILE_HANDLE [, EVENT_NAME [, ADDITIONAL_PARAMETERS] ]

select_expedite() does the same sort of thing as select_read() and select_write(), but it watches a FILE_HANDLE for out-of-band data ready to be input from a FILE_HANDLE. Hardly anybody uses this, but it exists for completeness' sake.

An EVENT_NAME event will be delivered whenever the FILE_HANDLE can be read from out-of-band. Out-of-band data is considered "expedited" because it is often ahead of a socket's normal data.

select_expedite() does not return anything significant.

select_pause_read FILE_HANDLE

select_pause_read() is a lightweight way to pause a FILE_HANDLE input watcher without performing all the bookkeeping of a select_read(). It's used with select_resume_read() to implement input flow control.

Input that occurs on FILE_HANDLE will backlog in the operating system buffers until select_resume_read() is called.

A side effect of bypassing the select_read() bookkeeping is that a paused FILE_HANDLE will not prematurely stop the current session.

select_pause_read() does not return anything significant.

select_resume_read FILE_HANDLE

select_resume_read() resumes a FILE_HANDLE input watcher that was previously paused by select_pause_read(). See select_pause_read() for more discussion on lightweight input flow control.

Data backlogged in the operating system due to a select_pause_read() call will become available after select_resume_read() is called.

select_resume_read() does not return anything significant.

select_pause_write FILE_HANDLE

select_pause_write() pauses a FILE_HANDLE output watcher the same way select_pause_read() does for input. Please see select_pause_read() for further discussion.

select_resume_write FILE_HANDLE

select_resume_write() resumes a FILE_HANDLE output watcher the same way that select_resume_read() does for input. See select_resume_read() for further discussion.

select FILE_HANDLE [, EV_READ [, EV_WRITE [, EV_EXPEDITE [, ARGS] ] ] ]

POE::Kernel's select() method sets or clears a FILE_HANDLE's read, write and expedite watchers at once. It's a little more expensive than calling select_read(), select_write() and select_expedite() manually, but it's significantly more convenient.

Defined event names enable their corresponding watchers, and undefined event names disable them. This turns off all the watchers for a FILE_HANDLE:

sub stop_io {
  $_[KERNEL]->select( $_[HEAP]{file_handle} );
}

This statement:

$_[KERNEL]->select( $file_handle, undef, "write_event", undef, @stuff );

is equivalent to:

$_[KERNEL]->select_read( $file_handle );
$_[KERNEL]->select_write( $file_handle, "write_event", @stuff );
$_[KERNEL]->select_expedite( $file_handle );

POE::Kernel's select() should not be confused with Perl's built-in select() function.

As with the other I/O watcher methods, select() does not return a meaningful value.

Session Management

Sessions are dynamic. They may be created and destroyed during a program's lifespan. When a session is created, it becomes the "child" of the current session. The creator -- the current session -- becomes its "parent" session. This is loosely modeled after UNIX processes.

The most common session management is done by creating new sessions and allowing them to eventually stop.

Every session has a parent, even the very first session created. Sessions without obvious parents are children of the program's POE::Kernel instance.

Child sessions will keep their parents active. See "Session Lifespans" for more about why sessions stay alive.

The parent/child relationship tree also governs the way many signals are dispatched. See "Common Signal Dispatching" for more information on that.

Session Management Events (_start, _stop, _parent, _child)

POE::Kernel provides four session management events: _start, _stop, _parent and _child. They are invoked synchronously whenever a session is newly created or just about to be destroyed.

_start
_start should be familiar by now. POE dispatches the _start event to initialize a session after it has been registered under POE::Kernel. What is not readily apparent, however, is that it is invoked before the POE::Session constructor returns.

Within the _start handler, the event's sender is the session that created the new session. Otherwise known as the new session's parent. Sessions created before POE::Kernel->run() is called will be descendents of the program's POE::Kernel singleton.

The _start handler's return value is passed to the parent session in a _child event, along with the notification that the parent's new child was created successfully. See the discussion of _child for more details.

POE::Session->create(
  inline_states => { _start=> \&_start },
  args => [ $some, $args ]
);
sub _start {
  my ( $some, $args ) = @_[ ARG0, ARG1 ];
  # ....
}
_stop
_stop is a little more mysterious. POE calls a _stop handler when a session is irrevocably about to be destroyed. Part of session destruction is the forcible reclamation of its resources (events, timers, message events, etc.) so it's not possible to post() a message from _stop's handler. A program is free to try, but the event will be destroyed before it has a chance to be dispatched.

the _stop handler's return value is passed to the parent's _child event. See _child for more details.

_stop is usually invoked when a session has no further reason to live, although signals may cause them to stop sooner.

The corresponding _child handler is invoked synchronously just after _stop returns.

_parent
_parent is used to notify a child session when its parent has changed. This usually happens when a session is first created. It can also happen when a child session is detached from its parent. See detach_child and "detach_myself".

_parent's ARG0 contains

el padre anterior de la sesión, y ARG1 contiene su nuevo padre.

sub _parent {
  my ( $old_parent, $new_parent ) = @_[ ARG0, ARG1 ];
  print(
    "Sesión ", $_[SESSION]->ID,
    " padre cambiado de sesión ", $old_parent->ID,
    " a sesión ", $new_parent->ID,
    "\n"
  );
}
_child
_child notifica a una sesión cuando una sesión hija ha sido creada, destruida, o reasignada a o desde otro padre. Se despacha usualmente cuando las sesiones son creadas o destruidas. También puede ocurrir cuando una sesión es desvinculada de su padre.

_child incluye información en la porción de "argumentos" de @_. Típicamente ARG0, ARG1 y ARG2, pero estos pueden ser sobreescritos por una clase POE::Session diferente:

ARG0 contiene una cadena que describe lo que ha sucedido con el hijo. La cadena puede ser 'create' (la sesión hija ha sido creada), 'gain' (el hijo ha sido entregado por otra sesión), o 'lose' (la sesión hija se ha detenido o ha sido entregada).

En todos los casos, ARG1 contiene una referencia a la sesión hija.

En el caso 'create', ARG2 contiene el valor devuelto por el manejador _start de la sesión hija. De igual manera, ARG2 contiene el valor de retorno del manejador _stop para el caso 'lose'.

sub _child {
  my( $reason, $child ) = @_[ ARG0, ARG1 ];
  if( $reason eq 'create' ) {
    my $retval = $_[ ARG2 ];
  }
  # ...
}

Los eventos se entregan en órdenes específicos.

Cuando se crea una nueva sesión:

1.
Se llama al constructor de la sesión.
2.
La sesión se pone en juego. Es decir, POE::Kernel la incluye en su contabilidad.
3.
La nueva sesión recibe _start.
4.
La sesión padre recibe _child ('create'), la referencia a la nueva sesión, y el valor de retorno del _start de la nueva sesión.
5.
El constructor de la sesión devuelve.

Cuando una sesión antigua se detiene:

1.
Si la sesión tiene hijos propios, estos son entregados al padre de la sesión. Esto activa uno o más eventos _child ('gain') en el padre, y un _parent en cada hijo.
2.
Una vez despojada de sus hijos, la sesión que se detiene recibe un evento _stop.
3.
El padre de la sesión detenida recibe un evento _child ('lose') con la referencia del hijo saliente y el valor de retorno del manejador _stop.
4.
La sesión detenida se elimina del juego, al igual que todos sus recursos restantes.
5.
Se comprueba si el padre de la sesión está inactivo. Si es así, comenzará la recolección de basura sobre él, y también se detendrá.

Cuando una sesión es desvinculada de su padre:

1.
El padre de la sesión que se desvincula es notificado con un evento _child ('lose'). El valor de retorno del manejador _stop es undef ya que el hijo no se está deteniendo realmente.
2.
La sesión desvinculada es notificada con un evento _parent de que su nuevo padre es el propio POE::Kernel.
3.
Los datos de contabilidad de POE::Kernel se ajustan para reflejar el cambio de paternidad.
4.
Se comprueba si el padre anterior de la sesión está inactivo. Si es así, comenzará la recolección de basura sobre él, y también se detendrá.

Métodos de Gestión de Sesiones

Estos métodos permiten desvincular sesiones de sus padres en los raros casos en que la relación padre/hijo se interpone.

detach_child CHILD_SESSION

detach_child() desvincula una CHILD_SESSION específica de la sesión actual. Si tiene éxito, CHILD_SESSION se convertirá en hija de la instancia POE::Kernel, y detach_child() devolverá verdadero. Sin embargo, en caso de fallo, detach_child() devuelve falso y establece $! para explicar la naturaleza del fallo:

ESRCH ("No such process").
La CHILD_SESSION no es una sesión válida.
EPERM ("Operation not permitted").
La CHILD_SESSION existe, pero no es hija de la sesión actual.

detach_child() generará eventos "_parent" y/o "_child" a las sesiones apropiadas. Ver Eventos de Gestión de Sesiones para una explicación detallada de estos eventos. Ver arriba el orden en que se generan los eventos.

detach_myself

detach_myself() desvincula la sesión actual de su padre actual. El nuevo padre será la instancia POE::Kernel en ejecución. Devuelve verdadero en caso de éxito. En caso de fallo, devuelve falso y establece $! para explicar la naturaleza del fallo:

EPERM ("Operation not permitted").
La sesión actual ya es hija de POE::Kernel, por lo que no puede ser desvinculada.

detach_child() generará eventos "_parent" y/o "_child" a las sesiones apropiadas. Ver Eventos de Gestión de Sesiones para una explicación detallada de estos eventos. Ver arriba el orden en que se generan los eventos.

Señales

POE::Kernel proporciona métodos a través de los cuales un programa puede registrar interés en las señales que llegan, puede entregar sus propias señales sin recurrir a llamadas al sistema, y puede indicar que las señales han sido manejadas para que los comportamientos predeterminados no sean necesarios.

Las señales son por naturaleza una *acción a distancia*, y su implementación requiere sincronización generalizada entre sesiones (y reentrancia en el despachador, pero ese es un detalle de implementación). Perfeccionar la semántica ha demostrado ser difícil, pero POE intenta hacer lo Correcto siempre que es posible.

POE no registra manejadores de %SIG para señales hasta que se llama a sig() para vigilarlas. Por lo tanto, el comportamiento predeterminado de una señal ocurre para las señales no manejadas. Es decir, SIGINT detendrá el programa sin piedad, SIGWINCH no hará nada, SIGTSTP pausará un programa, y así sucesivamente.

Clases de Señales

Hay tres clases de señales. Cada clase define un comportamiento predeterminado para la señal y si el predeterminado puede ser sobreescrito. Son:

Señales benignas, consultivas o informativas

Estos son tres nombres para la misma clase de señal. Las señales de esta clase notifican a una sesión de un evento pero no terminan la sesión si no se manejan.

Es posible que una aplicación cree sus propias señales benignas. Ver "signal" abajo.

Señales terminales

Las señales terminales matarán sesiones si no son manejadas por una llamada a "sig_handled"(). Las señales del SO que usualmente matan o volcan un proceso se consideran terminales en POE, pero nunca activan un coredump. Estas son: HUP, INT, QUIT y TERM.

Hay dos señales terminales creadas y usadas dentro de POE:

DIE
"DIE" notifica a las sesiones que ha ocurrido una excepción de Perl. Ver "Manejo de Excepciones" para detalles.
IDLE
La señal "IDLE" se utiliza para notificar a las sesiones restantes que un programa se ha quedado sin cosas que hacer.

Señales no enmascarables

Las señales no enmascarables son terminales independientemente de si se llama a sig_handled(). El término proviene de "NMI", la interrupción de CPU no enmascarable generada usualmente por una excepción de hardware irrecuperable.

Las sesiones que reciben una señal no enmascarable se detendrán inevitablemente. POE implementa dos señales no enmascarables:

ZOMBIE
Esta señal no enmascarable se dispara si un programa ha recibido una señal "IDLE" pero no se ha reiniciado ni ha salido. El programa se ha convertido en un zombi (es decir, no está ni muerto ni vivo, y solo existe para consumir cerebros... er... memoria). La señal "ZOMBIE" actúa como un bate de cricket en la cabeza, derribando al zombi, para siempre.
UIDESTROY
Esta señal no enmascarable indica que la interfaz de usuario de un programa se ha cerrado, y el programa debe tomar la indirecta del usuario y desaparecer también. Generalmente se genera cuando se cierra un widget GUI particular.

Despacho Común de Señales

La mayoría de las señales no se despachan a una única sesión. La linaje de sesiones de POE (padres e hijos) forma una especie de árbol familiar. Cuando se envía una señal a una sesión, primero pasa a través de cualquier hijo (y nieto, y así sucesivamente) que también esté interesado en la señal.

En el caso de señales terminales, si alguna de las sesiones por las que pasa una señal llama a "sig_handled"(), entonces la señal se considera atendida. Sin embargo, si ninguna de ellas lo hace, todo el árbol de sesiones con raíz en la sesión de destino se termina. Por ejemplo, consideremos este árbol de sesiones:

POE::Kernel
  Sesión 2
    Sesión 4
    Sesión 5
  Sesión 3
    Sesión 6
    Sesión 7

POE::Kernel es el padre de las sesiones 2 y 3. La sesión 2 es el padre de las sesiones 4 y 5. Y la sesión 3 es el padre de 6 y 7.

Una señal enviada a la Sesión 2 también puede ser despachada a las sesiones 4 y 5 porque son hijos de 2. Las sesiones 4 y 5 solo recibirán la señal si han registrado el observador apropiado. Si la señal es terminal, y ninguno de los observadores de señales en las sesiones 2, 4 y 5 llamó a sig_handled(), las 3 sesiones serán terminadas.

La instancia POE::Kernel del programa se considera una sesión para fines de despacho de señales. Por lo tanto, cualquier señal enviada a POE::Kernel se propagará a través de cada sesión interesada en todo el programa. De hecho, así es como se manejan las señales del SO: se registra un manejador de señales global para reenviar la señal a POE::Kernel.

Semántica de Señales

Todas las señales vienen con el nombre de la señal en ARG0. El nombre de la señal es tal como aparece en %SIG, con una excepción: las señales de procesos hijos son siempre "CHLD" incluso si el sistema operativo actual las reconoce como "CLD".

Ciertas señales tienen semántica especial:

SIGCHLD

SIGCLD

Tanto "SIGCHLD" como "SIGCLD" indican que un proceso hijo ha salido o ha sido terminado por alguna señal. El nombre real de la señal varía entre sistemas operativos, pero POE usa "CHLD" independientemente.

El interés en "SIGCHLD" se registra utilizando el método "sig_child". El método "sig"() también funciona, pero no es tan conveniente.

El evento "SIGCHLD" incluye tres parámetros:

ARG0
"ARG0" contiene la cadena 'CHLD' (incluso si el sistema operativo lo llama SIGCLD, SIGMONKEY o algo más).
ARG1
"ARG1" contiene el ID del proceso del proceso hijo finalizado.
ARG2
Y "ARG2" contiene el valor de $? para el proceso finalizado.

Ejemplo:

sub sig_CHLD {
  my( $name, $PID, $exit_val ) = @_[ ARG0, ARG1, ARG2 ];
  # ...
}

SIGPIPE

SIGPIPE rara vez se usa, ya que POE proporciona eventos que hacen lo mismo. Sin embargo, SIGPIPE es compatible si lo necesita. A diferencia de la mayoría de los eventos, SIGPIPE se distribuye directamente a la sesión activa cuando se captura. Salvo condiciones de carrera, la sesión activa debería ser la que provocó que el sistema operativo enviara la señal en primer lugar.

La señal SIGPIPE todavía se propagará a las sesiones hijas.

ARG0 es "PIPE". No hay otra información asociada a esta señal.

SIGWINCH

Los cambios de tamaño de ventana pueden generar una gran cantidad de señales muy rápidamente. Esto puede no ser un problema al usar perl 5.8.0 o posterior, pero las versiones anteriores pueden no aceptar bien tal abuso. Ha sido advertido.

ARG0 es "WINCH". No hay otra información asociada a esta señal.

Manejo de Excepciones

POE::Kernel solo proporciona una forma de manejo de excepciones: la señal "DIE".

Cuando el manejo de excepciones está habilitado (por defecto), POE::Kernel envuelve la invocación del estado en "eval{}". Si el manejador de eventos genera una excepción, generalmente con "die", POE::Kernel enviará una señal "DIE" a la sesión de destino del evento.

"ARG0" es el nombre de la señal, "DIE".

"ARG1" es un hashref que describe la excepción:

error_str
El texto de la excepción. En otras palabras, $@.
dest_session
Objeto de sesión del estado que generó la excepción. En otras palabras, $_[SESSION] en la función que murió.
event
Nombre del evento que murió.
source_session
Objeto de sesión que envió el evento original. Es decir, $_[SENDER] en la función que murió.
from_state
Estado desde el cual se envió el evento original. Es decir, $_[CALLER_STATE] en la función que murió.
file
Nombre del archivo desde el que se envió el evento. Es decir, $_[CALLER_FILE] en la función que murió.
line
Número de línea desde el que se envió el evento. Es decir, $_[CALLER_LINE] en la función que murió.

Tenga en cuenta que la discusión anterior asume que está utilizando la semántica de llamada de POE::Session.

Tenga en cuenta que la señal "DIE" se envía a la sesión que generó la excepción, no a la sesión que envió el evento que causó que se generara la excepción.

sub _start {
  $poe_kernel->sig( DIE => 'sig_DIE' );
  $poe_kernel->yield( 'some_event' );
}
sub some_event {
  die "¡No me gustó eso!";
}
sub sig_DIE {
  my( $sig, $ex ) = @_[ ARG0, ARG1 ];
  # $sig es 'DIE'
  # $ex es el hash de la excepción
  warn "$$: error in $ex->{event}: $ex->{error_str}";
  $poe_kernel->sig_handled();
  # Enviar la señal a la sesión que envió el evento original.
  if( $ex->{source_session} ne $_[SESSION] ) {
    $poe_kernel->signal( $ex->{source_session}, 'DIE', $sig, $ex );
  }
}

El manejo de excepciones incorporado de POE::Kernel se puede deshabilitar estableciendo la constante "POE::Kernel::CATCH_EXCEPTIONS" a cero. Al igual que con otras constantes de configuración en tiempo de compilación, debe establecerse antes de que se compile POE::Kernel:

BEGIN {
  package POE::Kernel;
  use constant CATCH_EXCEPTIONS => 0;
}
use POE;

o

sub POE::Kernel::CATCH_EXCEPTIONS () { 0 }
use POE;

Métodos del Vigilante de Señales

Y finalmente los métodos mismos.

sig NOMBRE_SEÑAL [, NOMBRE_EVENTO [, LISTA] ]

sig() registra o anula el registro de un evento NOMBRE_EVENTO para una NOMBRE_SEÑAL particular, con una LISTA opcional de parámetros que se pasarán al manejador de la señal, después de cualquier dato que venga con la señal.

Si NOMBRE_EVENTO está definido, se registra el manejador de señal. De lo contrario, se anula su registro.

Cada sesión puede registrar solo un manejador por NOMBRE_SEÑAL. Las registraciones posteriores reemplazarán a las anteriores. Sin embargo, múltiples sesiones pueden vigilar la misma señal.

Los NOMBRE_SEÑAL son generalmente los mismos que los miembros de %SIG, con dos excepciones. Primero, "CLD" es un alias de "CHLD" (aunque vea "sig_child"). Y segundo, es posible enviar y manejar señales creadas por la aplicación y que no tengan base en el sistema operativo.

sub handle_start {
  $_[KERNEL]->sig( INT => "event_ui_shutdown" );
  $_[KERNEL]->sig( bat => "holy_searchlight_batman" );
  $_[KERNEL]->sig( signal => "main_screen_turn_on" );
}

El sistema operativo puede que nunca sea capaz de generar las dos últimas señales, pero una sesión POE puede hacerlo usando el método "signal"() de POE::Kernel.

Más tarde, la sesión puede decidir no manejar las señales:

sub handle_ui_shutdown {
  $_[KERNEL]->sig( "INT" );
  $_[KERNEL]->sig( "bat" );
  $_[KERNEL]->sig( "signal" );
}

Más de una sesión puede registrar interés en la misma señal, y una sesión puede eliminar sus propios vigilantes de señales sin afectar a los de otras sesiones.

sig() no devuelve un valor significativo.

sig_child ID_PROCESO [, NOMBRE_EVENTO [, LISTA] ]

sig_child() es una forma conveniente de entregar un evento NOMBRE_EVENTO cuando un ID_PROCESO particular ha terminado. Una LISTA opcional de parámetros se pasará al manejador de señales después de la información de waitpid().

El vigilante puede ser eliminado en cualquier momento llamando a sig_child() solo con el ID_PROCESO.

Una sesión puede registrar tantos manejadores de sig_child() como sea necesario, pero una sesión solo puede tener uno por ID_PROCESO.

Los vigilantes de sig_child() son de un solo uso. Se eliminan automáticamente una vez que se ha entregado el NOMBRE_EVENTO. No tiene sentido seguir vigilando una señal que nunca volverá a llegar. Otros manejadores de señales persisten hasta que se eliminan.

Los vigilantes de sig_child() mantienen una sesión activa mientras estén activos. Esto es único entre los vigilantes de señales de POE.

Los programas que deseen cosechar procesos hijos de manera confiable deben asegurarse de llamar a sig_child() antes de devolver el control del manejador de eventos que bifurcó el proceso. De lo contrario, POE::Kernel puede tener la oportunidad de llamar a waitpid() antes de que se haya registrado un vigilante de eventos apropiado.

Los programas que cosechan procesos con waitpid() deben eliminar los vigilantes de POE para los mismos IDs de proceso, de lo contrario, POE esperará indefinidamente a procesos que nunca envían señales.

sig_child() no devuelve un valor significativo.

sub forked_parent {
  my( $heap, $pid, $details ) = @_[ HEAP, ARG0, ARG1 ];
  $poe_kernel->sig_child( $pid, 'sig_child', $details );
}
sub sig_child {
  my( $heap, $sig, $pid, $exit_val, $details ) = @_[ HEAP, ARG0..ARG3 ];
  my $details = delete $heap->{ $pid };
  warn "$$: Child $pid exited"
  # .... también, $details ha sido pasado desde forked_parent()
  # a través de sig_child()
}

sig_handled

sig_handled() informa a POE::Kernel que la señal que se está distribuyendo actualmente ha sido manejada por la sesión activa actualmente. Si la señal es terminal, la llamada a sig_handled() evita que POE::Kernel detenga las sesiones que recibieron la señal.

Una única señal puede distribuirse a varias sesiones. Solo una necesita llamar a sig_handled() para evitar que todo el grupo se detenga. Sin embargo, si ninguna de ellas la llama, entonces todas se detienen juntas.

sig_handled() no devuelve un valor significativo.

sub _start {
  $_[KERNEL]->sig( INT => 'sig_INT' );
}
sub sig_INT {
  warn "$$ SIGINT";
  $_[KERNEL]->sig_handled();
}

signal SESIÓN, NOMBRE_SEÑAL [, LISTA_ARGUMENTOS]

signal() publica una señal NOMBRE_SEÑAL a una SESIÓN específica con una LISTA_ARGUMENTOS opcional que se pasará a todos los manejadores interesados. Como se mencionó en otros lugares, la señal puede entregarse a los hijos, nietos, etc. de SESIÓN. Y si SESIÓN es el propio POE::Kernel, entonces todas las sesiones interesadas recibirán la señal.

Es posible enviar una señal en POE que no exista en el sistema operativo. signal() coloca la señal directamente en la cola de eventos de POE como si proviniera del sistema operativo, pero no se limita a las señales reconocidas por kill(). POE utiliza algunas de estas señales ficticias para sus propias notificaciones globales.

Por ejemplo:

sub some_event_handler {
  # Enciende todas las pantallas principales.
  $_[KERNEL]->signal( $_[KERNEL], "signal" );
}

signal() devuelve verdadero en caso de éxito. En caso de fallo, devuelve falso después de establecer $! para explicar la naturaleza del fallo:

ESRCH ("No such process")
La SESIÓN no existe.

Debido a que todas las sesiones son hijas de POE::Kernel, enviar una señal al kernel propagará la señal a todas las sesiones. Esta es una forma barata de multidifusión.

$_[KERNEL]->signal( $_[KERNEL], 'shutdown' );

Gestión de Manejadores de Eventos

Los métodos de gestión de manejadores de eventos permiten a las sesiones intercambiar sus manejadores de eventos en tiempo de ejecución. Por ejemplo, los objetos POE::Wheel utilizan state() para mezclar dinámicamente sus propios manejadores de eventos en las sesiones que los crean.

Estos métodos solo afectan a la sesión actual; sería descortés cambiar los manejadores de otra sesión.

Solo hay un método en este grupo. Dado que puede ser llamado de varias maneras diferentes, puede ser más fácil de entender si cada uno se documenta por separado.

state EVENT_NAME [, REFERENCIA_DE_CÓDIGO]

state() establece o elimina un manejador para EVENT_NAME en la sesión actual. La función a la que se refiere REFERENCIA_DE_CÓDIGO será llamada cada vez que los eventos EVENT_NAME se distribuyan a la sesión actual. Si se omite REFERENCIA_DE_CÓDIGO, se eliminará el manejador para EVENT_NAME.

Una sesión solo puede tener un manejador para un EVENT_NAME dado. Los intentos posteriores de establecer un manejador para EVENT_NAME reemplazarán a los manejadores anteriores con el mismo nombre.

# Dejar de prestar atención a la entrada. Decir adiós, y
# activar un cierre de socket cuando se envía el mensaje.
sub send_final_response {
  $_[HEAP]{wheel}->put("KTHXBYE");
  $_[KERNEL]->state( 'on_client_input' );
  $_[KERNEL]->state( on_flush => \&close_connection );
}

state EVENT_NAME [, REFERENCIA_DE_OBJETO [, NOMBRE_DE_MÉTODO_DE_OBJETO] ]

Establece o elimina un manejador para EVENT_NAME en la sesión actual. Si se proporciona REFERENCIA_DE_OBJETO, ese objeto manejará el evento. Se puede proporcionar un NOMBRE_DE_MÉTODO_DE_OBJETO opcional. Si no se proporciona el nombre del método, POE buscará un método que coincida con EVENT_NAME. Si se omite REFERENCIA_DE_OBJETO, se eliminará el manejador para EVENT_NAME.

Una sesión solo puede tener un manejador para un EVENT_NAME dado. Los intentos posteriores de establecer un manejador para EVENT_NAME reemplazarán a los manejadores anteriores con el mismo nombre.

$_[KERNEL]->state( 'some_event', $self );
$_[KERNEL]->state( 'other_event', $self, 'other_method' );

state EVENT_NAME [, NOMBRE_DE_CLASE [, NOMBRE_DE_MÉTODO_DE_CLASE] ]

Esta forma de llamada a state() es virtualmente idéntica a la forma de objeto.

Establece o elimina un manejador para EVENT_NAME en la sesión actual. Si se proporciona NOMBRE_DE_CLASE, esa clase manejará el evento. Se puede proporcionar un NOMBRE_DE_MÉTODO_DE_CLASE opcional. Si no se proporciona el nombre del método, POE buscará un método que coincida con EVENT_NAME. Si se omite NOMBRE_DE_CLASE, se eliminará el manejador para EVENT_NAME.

Una sesión solo puede tener un manejador para un EVENT_NAME dado. Los intentos posteriores de establecer un manejador para EVENT_NAME reemplazarán a los manejadores anteriores con el mismo nombre.

$_[KERNEL]->state( 'some_event', __PACKAGE__ );
$_[KERNEL]->state( 'other_event', __PACKAGE__, 'other_method' );

Contadores de Referencias Públicas

Los métodos de esta sección manipulan los contadores de referencias en la sesión actual u otra sesión.

Cada sesión tiene un espacio de nombres para los contadores de referencias manipulados por el usuario. Estos espacios de nombres están asociados con el SESSION_ID de destino para los métodos de contador de referencias, no con el llamador. Actualmente, nada impide que una sesión disminuya un contador de referencias que fue incrementado por otra, pero no se garantiza que este comportamiento continúe. Por ahora, depende de los usuarios de estos métodos elegir nombres de contador oscuros para evitar conflictos.

El conteo de referencias es una gran parte de la magia de POE. Varios objetos (principalmente observadores de eventos y componentes) mantienen referencias a las sesiones a las que pertenecen. "Ciclos de Vida de Sesión" explica el concepto con más detalle.

La capacidad de mantener una sesión activa es a veces útil en una aplicación o biblioteca. Por ejemplo, un componente puede mantener una referencia pública a otra sesión mientras procesa una solicitud de esa sesión. Al hacerlo, el componente garantiza que el solicitante todavía esté presente cuando una respuesta esté eventualmente lista. Mantener una referencia al objeto de la sesión no es suficiente. POE::Kernel tiene su propio mecanismo interno de conteo de referencias.

refcount_increment SESSION_ID, NOMBRE_DE_CONTADOR

refcount_increment() aumenta el valor del contador de referencias NOMBRE_DE_CONTADOR para la sesión identificada por un SESSION_ID. Para disuadir el uso de referencias de sesión, la sesión de destino de refcount_increment() debe especificarse por su ID de sesión.

La sesión de destino no se detendrá hasta que el valor de todos y cada uno de sus contadores de referencias NOMBRE_DE_CONTADOR sea cero. (En realidad, puede detenerse en algunos casos, como no poder manejar una señal terminal).

Los contadores de referencias negativos son legales. Todavía deben incrementarse a cero antes de que una sesión sea elegible para detenerse.

sub handle_request {
  # Entre otras cosas, mantenga un recuento de referencias del remitente.
  $_[KERNEL]->refcount_increment( $_[SENDER]->ID, "pending request");
  $_[HEAP]{requesters}{$request_id} = $_[SENDER]->ID;
}

Para que esto funcione, la sesión necesita una forma de recordar el ID de $_[SENDER] para una solicitud dada. Acostumbrados, la sesión genera un ID de solicitud y lo usa para rastrear la solicitud hasta que se complete.

refcount_increment() devuelve el recuento de referencias resultante (que puede ser cero) en caso de éxito. En caso de fallo, devuelve undef y establece $! como la razón del error.

ESRCH: El SESSION_ID no se refiere a una sesión activa actualmente.

refcount_decrement SESSION_ID, NOMBRE_DE_CONTADOR

refcount_decrement() reduce el valor del contador de referencias NOMBRE_DE_CONTADOR para la sesión identificada por un SESSION_ID. Es el contrapunto de refcount_increment(). Consulte refcount_increment() para obtener más contexto.

sub finally_send_response {
  # Entre otras cosas, liberar el recuento de referencias para el
  # solicitante.
  my $requester_id = delete $_[HEAP]{requesters}{$request_id};
  $_[KERNEL]->refcount_decrement( $requester_id, "pending request");
}

El ID de $_[SENDER] del solicitante se recuerda y se elimina del heap (para evitar fugas de memoria). Se utiliza para disminuir el contador de referencias que se incrementó al inicio de la solicitud.

refcount_decrement() devuelve el recuento de referencias resultante (que puede ser cero) en caso de éxito. En caso de fallo, devuelve undef y $! se establecerá como la razón del fallo:

ESRCH: El SESSION_ID no se refiere a una sesión activa actualmente.

No es posible descubrir referencias públicas activas actualmente. Consulte POE::API::Peek.

Accesorios de Estado del Kernel

POE::Kernel proporciona algunos accesorios a su masivo cerebro para que los desarrolladores de bibliotecas puedan tener un acceso conveniente a los datos necesarios sin depender de sus llamadores para proporcionarlos.

Estos accesorios exponen formas de romper la encapsulación de la sesión. Úselos con moderación y cuidado.

get_active_session

get_active_session() devuelve una referencia a la sesión que se está ejecutando actualmente, o una referencia a la instancia de POE::Kernel del programa si no se está ejecutando ninguna sesión en ese momento. El valor es equivalente a $_[SESSION] de POE::Session.

Este método se agregó para bibliotecas que necesitan $_[SESSION] pero no quieren incluirlo como un parámetro en sus API.

sub some_housekeeping {
  my( $self ) = @_;
  my $session = $poe_kernel->get_active_session;
  # hacer algo de mantenimiento en $session
}

get_active_event

get_active_event() devuelve el nombre del evento que se está distribuyendo actualmente. Devuelve una cadena vacía cuando se llama fuera de la distribución de eventos. El valor es equivalente a $_[STATE] de POE::Session.

sub waypoint {
  my( $message ) = @_;
  my $event = $poe_kernel->get_active_event;
  print STDERR "$$:$event:$mesage\n";
}

get_event_count

get_event_count() devuelve el número de eventos pendientes en la cola de eventos de POE. Se expone para autores de clases de POE::Loop. Puede ser obsoleto en el futuro.

get_next_event_time

get_next_event_time() devuelve la hora en que vence el próximo evento, en un formato compatible con la función time() de UNIX. Se expone para autores de clases de POE::Loop. Puede ser obsoleto en el futuro.

poe_kernel_loop

poe_kernel_loop() devuelve el nombre de la clase POE::Loop que se utiliza para detectar y distribuir eventos.

session_alloc OBJETO_SESION [, ARGUMENTOS_INICIO]

DESCRIPTION

POE provides the following variables and constants for your convenience and use.

$poe_kernel

It's the POE::Kernel singleton. POE::Kernel is the heart of any POE application, and $poe_kernel is a global variable that contains a reference to it. If you are writing a POE kernel helper library you will probably need to use this.

Otherwise, you will probably want to use $_[KERNEL] instead. POE::Kernel methods are passed as the first argument to event handlers.

When POE::Kernel is loaded, it sets $poe_kernel to a reference to itself. This is not done in a BEGIN block so that it may be done on demand. For example, if you use POE you get POE::Kernel for free, and thus you get $poe_kernel for free.

$poe_main_window

This variable is used by POE::Loop::Tk, and potentially by other POE::Loop implementations that require an initial widget to be created. It is not used by POE itself, but is passed to the application's session code as part of the _THEME hash.

It is initially undef. POE::Loop::Tk will create a Tk::Window widget and assign it to $poe_main_window. This widget is then passed to the application's session in _THEME->{main_window}.

POE will shut down if the widget in $poe_main_window is destroyed. This behaviour can be changed with POE::Kernel's signal_ui_destroy() method.

DEBUGGING POE AND PROGRAMS USING IT

POE includes a great deal of debugging code, both in the form of fatal assertions and run-time traces. These may be enabled at compile time, but there is no way to toggle them at run-time. This was done to avoid run-time penalties in programs where debugging is not necessary. That is, in most production cases.

Traces are verbose reminders of what's going on within POE. Each is prefixed with a four-character field describing the POE subsystem that generated it.

Assertions (asserts) are quiet but deadly, both in performance (they cause a significant run-time performance hit) and because they cause fatal errors when triggered.

The assertions and traces are useful for developing programs with POE, but they were originally added to debug POE itself.

Each assertion and tracing group is enabled by setting a constant in the POE::Kernel namespace to a true value.

  BEGIN {
    package POE::Kernel;
    use constant ASSERT_DEFAULT => 1;
  }
  use POE;

Or the old-fashioned (and more concise) "constant subroutine" method. This doesn't need the BEGIN block since subroutine definitions are done at compile time.

  sub POE::Kernel::ASSERT_DEFAULT () { 1 }
  use POE;

The switches must be defined as constants before POE::Kernel is first loaded. Otherwise Perl's compiler will not see the constants when first compiling POE::Kernel, and the features will not be properly enabled.

Assertions and traces may also be enabled by setting shell environment variables. The environment variables are named after the POE::Kernel constants with a "POE_" prefix.

  POE_ASSERT_DEFAULT=1 POE_TRACE_DEFAULT=1 ./my_poe_program

In alphabetical order:

ASSERT_DATA

ASSERT_DATA enables run-time data integrity checks within POE::Kernel and the classes that mix into it. POE::Kernel tracks a lot of cross-referenced data, and this group of assertions ensures that it's consistent.

Prefix: <dt>

Environment variable: POE_ASSERT_DATA

ASSERT_DEFAULT

ASSERT_DEFAULT specifies the default value for assertions that are not explicitly enabled or disabled. This is a quick and reliable way to make sure all assertions are on.

No assertion uses ASSERT_DEFAULT directly, and this assertion flag has no corresponding output prefix.

Turn on all assertions except ASSERT_EVENTS:

  sub POE::Kernel::ASSERT_DEFAULT () { 1 }
  sub POE::Kernel::ASSERT_EVENTS  () { 0 }
  use POE::Kernel;

Prefix: (none)

Environment variable: POE_ASSERT_DEFAULT

ASSERT_EVENTS

ASSERT_EVENTS mainly checks for attempts to dispatch events to sessions that don't exist. This assertion can assist in the debugging of strange, silent cases where event handlers are not called.

Prefix: <ev>

Environment variable: POE_ASSERT_EVENTS

ASSERT_FILES

ASSERT_FILES enables some run-time checks in POE's filehandle watchers and the code that manages them.

Prefix: <fh>

Environment variable: POE_ASSERT_FILES

ASSERT_RETVALS

ASSERT_RETVALS upgrades failure codes from POE::Kernel's methods from advisory return values to fatal errors. Most programmers don't check the values these methods return, so ASSERT_RETVALS is a quick way to validate one's assumption that all is correct.

Prefix: <rv>

Environment variable: POE_ASSERT_RETVALS

ASSERT_USAGE

ASSERT_USAGE is the counterpoint to ASSERT_RETVALS. It enables run-time checks that the parameters to POE::Kernel's methods are correct. It's a quick (but not foolproof) way to verify a program's use of POE.

Prefix: <us>

Environment variable: POE_ASSERT_USAGE

TRACE_DEFAULT

TRACE_DEFAULT specifies the default value for traces that are not explicitly enabled or disabled. This is a quick and reliable way to ensure your program generates copious output on the file named in TRACE_FILENAME or STDERR by default.

To enable all traces except a few noisier ones:

  sub POE::Kernel::TRACE_DEFAULT () { 1 }
  sub POE::Kernel::TRACE_EVENTS  () { 0 }
  use POE::Kernel;

Prefix: (none)

Environment variable: POE_TRACE_DEFAULT

TRACE_DESTROY

TRACE_DESTROY causes every POE::Session object to dump the contents of its $_[HEAP] when Perl destroys it. This trace was added to help developers find memory leaks in their programs.

Prefix: A line that reads "----- Session $self Leak Check -----".

Environment variable: POE_TRACE_DESTROY

TRACE_EVENTS

TRACE_EVENTS enables messages pertaining to POE's event queue's activities: when events are enqueued, dispatched or discarded, and more. It's great for determining where events go and when. Understandably this is one of POE's more verbose traces.

Prefix: <ev>

Environment variable: POE_TRACE_EVENTS

TRACE_FILENAME

TRACE_FILENAME specifies the name of a file where POE's tracing and assertion messages should go. It's useful if you want the messages but have other plans for STDERR, which is where the messages go by default.

POE's tests use this so the trace and assertion code can be instrumented during testing without spewing all over the terminal.

Prefix: (none)

Environment variable: POE_TRACE_FILENAME

TRACE_FILES

TRACE_FILES enables or disables traces in POE's filehandle watchers and the POE::Loop class that implements the lowest-level filehandle multiplexing. This may be useful when tracking down strange behavior related to filehandles.

Prefix: <fh>

Environment variable: POE_TRACE_FILES

TRACE_REFCNT

TRACE_REFCNT governs whether POE::Kernel will trace sessions' reference counts. As discussed in "Session Lifespans", POE does a lot of reference counting, and the current state of a session's reference counts determines whether the session lives or dies. It's common for developers to wonder why a session stops too early or remains active too long. TRACE_REFCNT can help explain why.

Prefix: <rc>

Environment variable: POE_TRACE_REFCNT

TRACE_RETVALS

TRACE_RETVALS can enable carping whenever a POE::Kernel method is about to fail. It's a non-fatal but noisier form of ASSERT_RETVALS.

Prefix: <rv>

Environment variable: POE_TRACE_RETVALS

TRACE_SESSIONS

TRACE_SESSIONS enables trace messages that pertain to session management. Notice will be given when sessions are created or destroyed, and when the parent or child status of a session changes.

Prefix: <ss>

Environment variable: POE_TRACE_SESSIONS

TRACE_SIGNALS

TRACE_SIGNALS turns on (or off) traces in POE's signal handling subsystem. Signal dispatch is one of POE's more complex parts, and the trace messages may help application developers understand signal propagation and timing.

Prefix: <sg>

Environment variable: POE_TRACE_SIGNALS

USE_SIGCHLD

Whether to use $SIG{CHLD} or to poll at an interval.

This flag is enabled by default on Perl >= 5.8.1 as it has support for "safe signals". Please see perlipc for the gory details.

You might want to disable this if you are running a version of Perl that is known to have bad signal handling, or if anything hijacks $SIG{CHLD}. One module that is known to do this is Apache.

Enabling this flag will cause child reaping to happen almost immediately, as opposed to once per "CHILD_POLLING_INTERVAL".

CHILD_POLLING_INTERVAL

El intervalo en el que se llama a "wait" para determinar si los procesos hijos necesitan ser eliminados y la señal "CHLD" emulada.

Por defecto es 1 segundo.

USE_SIGNAL_PIPE

La única forma segura de manejar señales es implementar un modelo de compartir nada. POE construye una tubería de señales que se comunica entre los manejadores de señales y el bucle del kernel de POE de manera segura y atómica. La tubería de señales se implementa con POE::Pipe::OneWay, utilizando una conduit de "pipe" en Unix. Desafortunadamente, la tubería de señales no es compatible con Windows y no se usa en esa plataforma.

Si desea volver al comportamiento anterior de señales inseguro, debe establecer "USE_SIGNAL_PIPE" a 0, o la variable de entorno "POE_USE_SIGNAL_PIPE".

CATCH_EXCEPTIONS

Si POE debe ejecutar código del manejador de eventos dentro de un eval { } y entregar la señal "DIE" en caso de errores.

Ver "Manejo de Excepciones".

VARIABLES DE ENTORNO PARA PRUEBAS

Las pruebas de POE son encantadoras, oscuras y profundas. Estas variables de entorno permiten a los probadores tomar caminos menos transitados.

POE_DANTIC

Windows y los Perls construidos para él tienden a ser malos haciendo cosas UNIXy, aunque lo intentan. POE, al ser muy UNIXy, debe omitir muchas pruebas de Windows. La variable de entorno POE_DANTIC, cuando es verdadera, habilitará todas estas pruebas. Está destinada a ser utilizada de vez en cuando para ver si Windows ha mejorado en alguna área.
