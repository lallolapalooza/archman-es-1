POE::Wheel::ReadWrite(3pm) Documentación de Perl contribuida por el usuario POE::Wheel::ReadWrite(3pm)

NOMBRE

POE::Wheel::ReadWrite - mezcla de E/S de búfer no bloqueante para POE::Session

SINOPSIS

#!perl
use warnings;
use strict;
use IO::Socket::INET;
use POE qw(Wheel::ReadWrite);
POE::Session->create(
  inline_states => {
    _start => sub {
      # Nota: IO::Socket::INET bloqueará. Recomendamos
      # POE::Wheel::SocketFactory o POE::Component::Client::TCP si
      # el bloqueo está contraindicado.
      $_[HEAP]{client} = POE::Wheel::ReadWrite->new(
        Handle => IO::Socket::INET->new(
          PeerHost => 'www.yahoo.com',
          PeerPort => 80,
        ),
        InputEvent => 'on_remote_data',
        ErrorEvent => 'on_remote_fail',
      );
      print "Conectado. Enviando solicitud...\n";
      $_[HEAP]{client}->put(
        "GET / HTTP/0.9",
        "Host: www.yahoo.com",
        "",
      );
    },
    on_remote_data => sub {
      print "Recibido: $_[ARG0]\n";
    },
    on_remote_fail => sub {
      print "La conexión falló o terminó. Cerrando...\n";
      delete $_[HEAP]{client};
    },
  },
);
POE::Kernel->run();
exit;

DESCRIPCIÓN

POE::Wheel::ReadWrite encapsula un patrón de diseño común: manejar E/S de búfer de forma no bloqueante y orientada a eventos.

El patrón es algo así:

Dado un manejador de archivo, vigílalo en busca de datos entrantes. Cuando se notifique de datos entrantes, léelos, almacénalos en búfer y analízalos según algún protocolo de bajo nivel (como línea por línea). Genera eventos de nivel superior "aquí hay líneas", uno por cada línea analizada.

En la otra dirección, acepta bloques de datos completos (como líneas) para su salida. Reformátalos según algún protocolo de bajo nivel (como añadiendo saltos de línea), y almacénalos en búfer para su salida. Vacía los datos del búfer cuando el manejador de archivo esté listo para transmitirlos.

MÉTODOS PÚBLICOS

Constructor

Las subclases de POE::Wheel tienden a realizar mucha configuración para que se ejecuten de manera más ligera y rápida. El constructor de POE::Wheel::ReadWrite no es una excepción.

new

new() crea y devuelve una nueva instancia de POE:Wheel::ReadWrite. En la mayoría de las circunstancias, la rueda seguirá leyendo/escribiendo en uno o más manejadores de archivo hasta que sea destruida.

Handle

Handle define el manejador de archivo del que un objeto POE::Wheel::ReadWrite leerá y escribirá. La "SINOPSIS" incluye un ejemplo usando Handle.

Un único objeto POE::Wheel::ReadWrite puede leer y escribir en diferentes manejadores de archivo. Consulte "InputHandle" para más información y un ejemplo.

InputHandle

InputHandle y OutputHandle se pueden usar para especificar diferentes manejadores para entrada y salida. Por ejemplo, la entrada puede ser de STDIN y la salida puede ir a STDOUT:

$_[HEAP]{console} = POE::Wheel::ReadWrite->new(
  InputHandle => \*STDIN,
  OutputHandle => \*STDOUT,
  InputEvent => "console_input",
);

InputHandle y OutputHandle no se pueden usar con Handle.

OutputHandle

InputHandle y OutputHandle se pueden usar para especificar diferentes manejadores para entrada y salida. Consulte "InputHandle" para más información y un ejemplo.

Driver

Driver especifica cómo POE::Wheel::ReadWrite realmente leerá y escribirá en sus manejadores de archivo. Driver debe ser un objeto que herede de POE::Driver.

POE::Driver::SysRW, que implementa sysread() y syswrite(), es el valor predeterminado. Se usa en casi todos los casos, por lo que no tiene sentido especificarlo.

Filter

Filter es el analizador que POE::Wheel::ReadWrite utilizará para reconocer los datos de entrada y el serializador que utiliza para preparar los datos para la escritura. Por defecto, es una nueva instancia de POE::Filter::Line, ya que muchos protocolos de red se basan en líneas.

InputFilter

InputFilter y OutputFilter se pueden usar para especificar filtros diferentes para entrada y salida.

OutputFilter

InputFilter y OutputFilter se pueden usar para especificar filtros diferentes para entrada y salida. Consulte "InputFilter" para más información y un ejemplo.

InputEvent

InputEvent especifica el nombre del evento que se enviará por cada unidad de entrada completa (según lo analizado por InputFilter o Filter).

Cada evento de entrada incluye dos parámetros:

"ARG0" contiene la unidad de entrada analizada, y "ARG1" contiene el ID único del objeto POE::Wheel::ReadWrite que generó el evento.

InputEvent es opcional. Si se omite, el objeto POE::Wheel::ReadWrite no vigilará su Handle o InputHandle en busca de entrada, y no se generarán eventos de entrada.

Un manejador de ejemplo para InputEvent:

sub handle_input {
  my ($heap, $input, $wheel_id) = @_[HEAP, ARG0, ARG1];
  print "Haciendo eco de la entrada del wheel $wheel_id: $input\n";
  $heap->{wheel}->put($input); # Poner... la entrada... de vuelta!
}

FlushedEvent

FlushedEvent especifica el evento que emitirá un objeto POE::Wheel::ReadWrite cada vez que su búfer de salida pase de contener datos a estar vacío.

FlushedEvent viene con un solo parámetro: "ARG0" contiene el ID único del objeto POE::Wheel::ReadWrite que generó el evento. Esto puede usarse para correlacionar el evento con una rueda en particular.

Los eventos "Flushed" se usan a menudo para cerrar E/S después de que se ha enviado un mensaje de "adiós". Por ejemplo, el siguiente input_handler() responde a "quit" instruyendo a la rueda para que diga "Adiós." y luego envíe un evento de "shutdown" cuando eso se haya vaciado en el socket.

sub handle_input {
  my ($input, $wheel_id) = @_[ARG0, ARG1];
  my $wheel = $_[HEAP]{wheel}{$wheel_id};
  if ($input eq "quit") {
    $wheel->event( FlushedEvent => "shutdown" );
    $wheel->put("Adiós.");
  }
  else {
    $wheel->put("Eco: $input");
  }
}

Aquí está el manejador de shutdown. Simplemente destruye la rueda para finalizar la conexión:

sub handle_flushed {
  my $wheel_id = $_[ARG0];
  delete $_[HEAP]{wheel}{$wheel_id};
}

ErrorEvent

ErrorEvent nombra el evento que un objeto POE::Wheel::ReadWrite emitirá cada vez que ocurra un error. Cada ErrorEvent incluye cuatro parámetros:

"ARG0" describe qué falló, ya sea "read" o "write". No nombra una función en particular ya que POE::Wheel::ReadWrite delega la lectura y escritura real a un objeto POE::Driver.

"ARG1" y "ARG2" contienen valores numéricos y de cadena para $! en el momento del fallo. El código de la aplicación no puede probar $! directamente ya que su valor puede haber cambiado entre el momento del error y el momento en que se despacha el evento de error.

"ARG3" contiene el ID único de la rueda. El ID de la rueda se utiliza para diferenciar entre muchas ruedas gestionadas por una sola sesión.

ErrorEvent también puede indicar EOF en un FileHandle devolviendo un error de operación "read" 0. Para sockets, esto significa que el extremo remoto ha cerrado la conexión.

Un manejador de ejemplo para ErrorEvent:

sub error_state {
  my ($operation, $errnum, $errstr, $id) = @_[ARG0..ARG3];
  if ($operation eq "read" and $errnum == 0) {
    print "EOF de la rueda $id\n";
  }
  else {
    warn "La rueda $id encontró un error de $operation $errnum: $errstr\n";
  }
  delete $_[HEAP]{wheels}{$id}; # cerrar esa rueda
}

HighEvent

HighEvent y LowEvent se usan junto con HighMark y LowMark para controlar el flujo de salida en streaming.

Se envía un HighEvent cuando el búfer de salida de un objeto POE::Wheel::ReadWrite excede un cierto tamaño (la marca de "agua alta", o HighMark). Esto aconseja a una aplicación que deje de transmitir salida. A POE y a Perl realmente no les importa si la aplicación continúa, pero es posible que el proceso se quede sin memoria si un búfer crece sin límites.

Un objeto POE::Wheel::ReadWrite continuará vaciando su búfer incluso después de que una aplicación deje de transmitir datos, hasta que el búfer esté vacío. CONTROL DE FLUJO

POE::Wheel::ReadWrite objetos incluyen un mecanismo de control de flujo. Permite que una aplicación detenga temporalmente el envío de datos a un POE::Wheel::ReadWrite cuando su búfer de salida está "demasiado lleno".

El control de flujo se implementa mediante los eventos HighEvent y LowEvent. Estos eventos son generados por el objeto POE::Wheel::ReadWrite para advertir a la aplicación cuándo su búfer de salida ha alcanzado un umbral alto o ha caído por debajo de un umbral bajo.

Una aplicación puede recibir HighEvent cuando el búfer de salida de un POE::Wheel::ReadWrite alcanza un cierto tamaño (la marca de "agua alta", o HighMark). Esto suele ser una señal para que la aplicación detenga temporalmente el envío de más datos.

Si una aplicación continúa enviando datos a un POE::Wheel::ReadWrite después de que se ha alcanzado el HighMark, el método put() devolverá un valor verdadero. Esto puede ser útil para enviar datos de forma masiva, pero con el riesgo de agotar la memoria del proceso.

Una aplicación puede recibir LowEvent cuando el búfer de salida de un POE::Wheel::ReadWrite cae por debajo de un cierto tamaño (la marca de "agua baja", o LowMark). Esto indica a la aplicación que es seguro reanudar el envío de datos.

El problema del "tartamudeo" ocurre cuando una aplicación solo envía datos hasta que el búfer de salida está casi vacío, y luego espera una FlushedEvent antes de enviar más datos. Esto puede causar pausas e inconsistencias en el flujo de datos.

El LowEvent resuelve el problema del tartamudeo. Un objeto POE::Wheel::ReadWrite enviará un LowEvent cuando su búfer de salida descienda por debajo de cierto nivel (la marca de "agua baja", o LowMark). Esto notifica a una aplicación que el búfer es lo suficientemente pequeño como para que pueda reanudar la transmisión de datos.

El problema del tartamudeo se resuelve porque el búfer de salida nunca llega a estar completamente vacío.

HighEvent y LowEvent son activados por flanco, no por nivel. Esto significa que se emiten una vez cada vez que el búfer de salida de un objeto POE::Wheel::ReadWrite cruza el HighMark o LowMark. Si una aplicación continúa enviando datos después de que se alcanza el HighMark, no provocará el envío de otro HighEvent.

El HighEvent generalmente no es necesario. El método put() devolverá el estado de la marca de agua alta: verdadero si el búfer está en o por encima de la marca de agua alta, o falso si el búfer tiene espacio para más datos. Aquí hay una forma rápida de inicializar el búfer de salida de un objeto POE::Wheel::ReadWrite:

1 while not $_[HEAP]{readwrite}->put(get_next_data());

Los objetos POE::Wheel::ReadWrite siempre comienzan en un estado de bajo nivel de agua.

HighEvent y LowEvent son opcionales. Omítelos si no se necesita control de flujo.

LowEvent

HighEvent y LowEvent se utilizan junto con HighMark y LowMark para controlar el flujo de salida transmitida. Consulte "HighEvent" para obtener más información y ejemplos.

put RECORDS

put() acepta una lista de REGISTROS, que serán serializados por el Filtro de la rueda y almacenados en búfer y escritos por su Controlador.

put() devuelve verdadero si se ha establecido una marca alta y el búfer de salida del Controlador ha alcanzado o superado el límite. Se devuelve falso si no se ha establecido la marca alta, o si el búfer del Controlador es menor que ese límite.

El valor de retorno de put() es puramente informativo; una aplicación puede continuar almacenando datos más allá de la marca alta, con el riesgo de exceder los límites de memoria del proceso. ¡No utilice la sintaxis "<1 while not $wheel-"put()>> si no está establecida la marca alta: ¡la aplicación fallará espectacularmente!

event EVENT_TYPE => EVENT_NAME, ...

event() permite a una aplicación modificar los eventos emitidos por un objeto POE::Wheel::ReadWrite. Todos los parámetros del constructor que terminan en "Event" pueden cambiarse en tiempo de ejecución: "InputEvent", "FlushedEvent", "ErrorEvent", "HighEvent" y "LowEvent".

Establecer un evento en undef deshabilitará el código dentro de la rueda que genera el evento. Por ejemplo, detener InputEvent también detendrá la lectura del manejador de archivos. Sin embargo, "pause_input" y "resume_input" pueden ser una mejor manera de gestionar los eventos de entrada.

set_filter POE_FILTER

set_filter() cambia la forma en que un objeto POE::Wheel::ReadWrite analiza la entrada y serializa la salida. Cualquier dato pendiente que no se haya enviado a la aplicación se analizará con el nuevo POE_FILTER. La información que se ha enviado con put() pero que no se ha vaciado no se volverá a serializar.

set_filter() realiza el mismo acto que llamar a set_input_filter() y set_output_filter() con el mismo objeto POE::Filter.

Cambiar filtros puede ser complicado. Consulte la discusión de get_pending() en POE::Filter. Algunos filtros pueden no admitir la carga o descarga dinámica.

set_input_filter POE_FILTER

set_input_filter() cambia el filtro de entrada de un objeto POE::Wheel::ReadWrite, dejando inalterado el filtro de salida. Esto altera la forma en que se analizan los datos sin afectar la forma en que se serializan para la salida.

set_output_filter POE_FILTER

set_output_filter() cambia la forma en que un objeto POE::Wheel::ReadWrite serializa su salida, pero no afecta la forma en que se analizan los datos.

get_input_filter

get_input_filter() devuelve el objeto POE::Filter utilizado actualmente por un objeto POE::Wheel::ReadWrite para analizar los datos entrantes. El objeto devuelto puede ser inspeccionado o alterado a través de sus propios métodos.

No existe un método get_filter() porque no hay un valor de retorno sensato cuando los filtros de entrada y salida difieren.

get_output_filter

get_output_filter() devuelve el objeto POE::Filter utilizado actualmente por un objeto POE::Wheel::ReadWrite para serializar los datos salientes. El objeto devuelto puede ser inspeccionado o alterado a través de sus propios métodos.

No existe un método get_filter() porque no hay un valor de retorno sensato cuando los filtros de entrada y salida difieren.

set_high_mark HIGH_MARK_OCTETS

Establece la marca de agua alta: el número de octetos que designa un búfer de salida "suficientemente lleno". Un objeto POE::Wheel::ReadWrite emitirá un HighEvent cuando su búfer de salida se expanda hasta alcanzar este punto. Todas las llamadas a put() devolverán verdadero cuando el búfer de salida sea igual o mayor que HIGH_MARK_OCTETS.

Tanto HighEvent como put() indican que no es seguro continuar escribiendo cuando el búfer de salida se expande a al menos HIGH_MARK_OCTETS.

set_low_mark LOW_MARK_OCTETS

Establece la marca de agua baja: el número de octetos que designa un búfer de salida "suficientemente vacío". Este evento informa a una aplicación que es seguro reanudar la escritura.

Los objetos POE::Wheel::ReadWrite emitirán un LowEvent cuando sus búferes de salida se reduzcan a LOW_MARK_OCTETS después de haber alcanzado HIGH_MARK_OCTETS.

ID

ID() devuelve el ID único de un objeto POE::Wheel::ReadWrite. Normalmente se llama a ID() después de crear el objeto para que pueda ser almacenado por su ID. Los eventos generados por el objeto POE::Wheel::ReadWrite incluirán el ID del objeto, para que puedan ser emparejados con sus fuentes.

pause_input

pause_input() instruye a un objeto POE::Wheel::ReadWrite a dejar de vigilar la entrada y, por lo tanto, a dejar de emitir eventos InputEvent. Es mucho más eficiente que destruir el objeto directamente, especialmente si una aplicación tiene la intención de resume_input() más tarde.

resume_input

resume_input() vuelve a activar el vigilante de entrada de un objeto POE::Wheel::ReadWrite. Se utiliza para reanudar la vigilancia de la entrada y, por lo tanto, reanudar el envío de eventos InputEvent. pause_input() y resume_input() implementan una forma de control de flujo de entrada, impulsada por la propia aplicación.

get_input_handle

get_input_handle() devuelve el manejador de archivos que se está vigilando para la entrada.

La manipulación de manejadores de archivos que son administrados por POE puede causar efectos secundarios desagradables, que pueden cambiar de una versión de POE a otra. Utilice con precaución.

get_output_handle

get_output_handle() devuelve el manejador de archivos que se está vigilando para la salida.

La manipulación de manejadores de archivos que son administrados por POE puede causar efectos secundarios desagradables, que pueden cambiar de una versión de POE a otra. Utilice con precaución.

shutdown_input

Llama a shutdown($fh,0) en el manejador de entrada de un objeto POE::Wheel::ReadWrite. Esto solo funciona para sockets; no sucederá nada para otros tipos de manejadores de archivos.

Ocasionalmente, el objeto POE::Wheel::ReadWrite dejará de monitorear su manejador de entrada para nuevos datos. Esto ocurre independientemente del tipo de manejador de archivos.

shutdown_output

Llama a shutdown($fh,1) en el manejador de salida de un objeto POE::Wheel::ReadWrite. Esto solo funciona para sockets; no sucederá nada para otros tipos de manejadores de archivos.

Ocasionalmente, el objeto POE::Wheel::ReadWrite dejará de monitorear su manejador de salida para nuevos datos. Esto ocurre independientemente del tipo de manejador de archivos.

get_driver_out_octets

Los objetos POE::Driver contienen búferes de salida que se vacían de forma asíncrona. get_driver_out_octets() devuelve el número de octetos restantes en el búfer de salida del controlador de la rueda.

get_driver_out_messages

Los búferes de salida de los objetos POE::Driver pueden basarse en mensajes. Cada llamada a put() puede ser almacenada en búfer individualmente. get_driver_out_messages() devolverá el número de mensajes pendientes de put() que quedan por enviar.

Los controladores basados en streams simplemente devolverán 1 si quedan datos por vaciar. Esto se debe a que operan con un mensaje potencialmente grande.

flush

flush() intenta vaciar manualmente la salida de una rueda de forma síncrona. Esto se puede utilizar para vaciar mensajes pequeños. Tenga en cuenta, sin embargo, que no se garantiza un vaciado completo; hacerlo significaría potencialmente bloquear indefinidamente, lo cual es indeseable en la mayoría de las aplicaciones POE.

Si una aplicación debe garantizar un vaciado completo del búfer, puede repetir las llamadas a flush():

$wheel->flush() while $wheel->get_driver_out_octets();

NAME

POE::Wheel::ReadWrite - A wheel for doing input/output.

SYNOPSIS

  use POE::Wheel::ReadWrite;

  my $rh = POE::Wheel::ReadWrite->new(
    Handle => $handle,
    InputFilter => \&my_input_filter,
    OutputFilter => \&my_output_filter,
  );

  # ...

  $poe_kernel->yield( $rh->get );
  $poe_kernel->yield( $rh->put( $data ) );

DESCRIPTION

POE::Wheel::ReadWrite is a concrete implementation of the POE::Wheel API. It is suitable for performing input and output on a filehandle.

It is designed to be a drop-in replacement for POE::Wheel::Read and POE::Wheel::Write, providing the functionality of both.

POE::Wheel::ReadWrite will use POE::Filter::Line if no input or output filter is specified.

PUBLIC METHODS

The public methods are:

  • new
  • get
  • put
  • dequeue
  • flush
  • error
  • destruct

For a complete description of these methods, see the documentation for POE::Wheel and POE::Wheel::Read.

The only difference from the base class methods is that this class does not document its own methods. It inherits them all.

This method is experimental. Its behavior may change or it may disappear outright. Please let us know whether it's useful.
