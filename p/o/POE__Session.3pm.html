POE::Session(3) Documentación de Perl contribuida por el usuario POE::Session(3)

NOMBRE

POE::Session - una tarea genérica basada en eventos

SINOPSIS

use POE; # incluye automáticamente POE::Kernel y POE::Session
POE::Session->create(
  inline_states => {
    _start => sub { $_[KERNEL]->yield("next") },
    next   => sub {
      print "tick...\n";
      $_[KERNEL]->delay(next => 1);
    },
  },
);
POE::Kernel->run();
exit;

POE::Session también puede enviar a métodos de objetos y clases a través de las devoluciones de llamada "object_states" y "package_states".

DESCRIPCIÓN

POE::Session y sus subclases traducen eventos del despachador genérico de POE::Kernel a las convenciones de llamada particulares adecuadas para el código de la aplicación. En términos de patrones de diseño, las clases POE::Session son adaptadores entre POE::Kernel y el código de la aplicación.

Las sesiones que gestiona POE::Kernel son más parecidas a estructuras de tareas genéricas. Desafortunadamente, estos dos conceptos dispares tienen nombres virtualmente idénticos.

Una nota sobre la nomenclatura

Esta documentación se referirá a los manejadores de eventos como "estados" en ciertas situaciones inevitables. Las sesiones se concibieron originalmente como máquinas de estado basadas en eventos, pero sus propósitos evolucionaron con el tiempo. Parte del vocabulario heredado perdura en la API por compatibilidad con versiones anteriores, sin embargo.

Confusamente, POE::NFA es una clase para implementar máquinas de estado basadas en eventos reales. Su documentación utiliza "estado" en el sentido correcto.

USANDO POE::Session

POE::Session tiene dos propósitos principales. Primero, mapea nombres de eventos al código que los manejará. Segundo, mapea una interfaz de despacho de eventos consistente a esos manejadores.

Considere el "SINOPSIS" como ejemplo. Se crea una instancia de POE::Session con dos "inline_states", cada uno mapeando un nombre de evento ("_start" y "next") a una subrutina en línea. POE::Session asegura que "$_[KERNEL]" y así sucesivamente tengan sentido dentro de un manejador de eventos.

Los manejadores de eventos también pueden ser métodos de objetos o de clases, usando respectivamente "object_states" y "package_states". La sintaxis de create() es diferente a la de "inline_states", pero la convención de llamada es casi idéntica.

Observe que el objeto POE::Session creado no se ha guardado en una variable. El nuevo objeto POE::Session se entrega a sí mismo a POE::Kernel, que luego lo administra a él y a todos los recursos que utiliza.

Es posible mantener referencias a nuevos objetos POE::Session, pero normalmente no es necesario. Si una aplicación no tiene cuidado al limpiar estas referencias, creará referencias circulares, lo que provocará fugas de memoria cuando POE::Kernel normalmente destruiría el objeto POE::Session. Se recomienda que en su lugar conserve el ID de la sesión.

Convención de llamada de POE::Session

El mayor obstáculo sintáctico que la mayoría de la gente tiene con POE es la convención de llamada poco convencional de POE::Session. Por ejemplo:

sub handle_event {
  my ($kernel, $heap, $parameter) = @_[KERNEL, HEAP, ARG0];
  ...;
}

O el uso de $_[KERNEL], $_[HEAP] y $_[ARG0] en línea, como se hace en la mayoría de los ejemplos.

Lo que está sucediendo aquí es bastante básico. Perl pasa parámetros a las subrutinas o métodos usando el array @_. "KERNEL", "HEAP", "ARG0" y otros son constantes exportadas por POE::Session (que se incluye de forma gratuita cuando un programa utiliza POE).

Así que $_[KERNEL] es el KERNELésimo parámetro de un manejador de eventos. @_[HEAP, ARG0] es una porción de @_ que contiene los parámetros HEAPésimo y ARG0ésimo.

Si bien esto parece extraño, es una sintaxis de Perl perfectamente clara y legal. POE la utiliza por varias razones:

1.
En el caso común, pasar parámetros en @_ es más rápido que pasar referencias de hash o array y luego desreferenciarlas en el manejador.
2.
Los errores tipográficos en las listas de parámetros basadas en hash son errores sutiles en tiempo de ejecución o requieren una verificación constante en tiempo de ejecución. Las constantes se conocen en tiempo de compilación o son errores claros en tiempo de compilación.
3.
La referencia a los desplazamientos de @_ mediante constantes permite que los parámetros se muevan en el futuro sin romper el código de la aplicación.
4.
La mayoría de los manejadores de eventos no necesitan todo @_. Las porciones permiten a los manejadores usar solo los parámetros que les interesan.

Parámetros de POE::Session

Los manejadores de eventos reciben la mayor parte de su contexto de tiempo de ejecución en hasta nueve parámetros de devolución de llamada. POE::Kernel proporciona muchos de ellos.

$_[OBJECT]

$_[OBJECT] es $self para manejadores de eventos que son métodos de objeto. Es el nombre de la clase (paquete) para manejadores de eventos basados en clases. Es undef para simples devoluciones de llamada de coderef, que no tienen un valor especial similar a $self.

"OBJECT" es siempre cero, ya que $_[0] es siempre $self o $class en métodos de objeto y de clase. Los manejadores de coderef se llaman con un marcador de posición "undef" en $_[0] para que los otros desplazamientos sigan siendo válidos.

A menudo es útil que los manejadores de eventos basados en métodos llamen a otros métodos del mismo objeto. $_[OBJECT] ayuda a que esto suceda.

sub ui_update_everything {
  my $self = $_[OBJECT];
  $self->update_menu();
  $self->update_main_window();
  $self->update_status_line();
}

También puede usar la herencia de métodos. Aquí invocamos $self->a_method(@_). Dado que el operador "->" de Perl antepone $self al principio de @_, debemos primero extraer una copia para mantener los desplazamientos de parámetros de POE:

sub a_method {
  my $self = shift;
  $self->SUPER::a_method( @_ );
  # ... más trabajo ...
}

$_[SESSION]

$_[SESSION] es una referencia al objeto de sesión actual. Esto permite que los manejadores de eventos accedan a los métodos de su sesión. Los programas también pueden comparar $_[SESSION] con $_[SENDER] para verificar que los eventos dentro de la sesión no provienen de otras sesiones.

$_[SESSION] también se puede utilizar como destino para post() y call() dentro de la sesión. Sin embargo, yield() es marginalmente más conveniente y eficiente que "post($_[SESSION], ...)".

Es una mala práctica acceder directamente a otra sesión. El enfoque recomendado es manipular una sesión a través de un manejador de eventos.

sub enable_trace {
  my $previous_trace = $_[SESSION]->option( trace => 1 );
  my $id = $_[SESSION]->ID;
  if ($previous_trace) {
    print "Sesión $id: el rastro de despacho sigue activado.\n";
  }
  else {
    print "Sesión $id: el rastro de despacho se ha activado.\n";
  }
}

$_[KERNEL]

El parámetro KERNELésimo es siempre una referencia a la instancia singleton de POE::Kernel de la aplicación. Se utiliza con mayor frecuencia para llamar a métodos de POE::Kernel desde manejadores de eventos.

# Establece un temporizador de 10 segundos.
$_[KERNEL]->delay( time_is_up => 10 );

$_[HEAP]

Cada objeto POE::Session contiene su propio espacio de nombres de variables conocido como el "HEAP" de la sesión. Está modelado y nombrado como los montones de memoria de procesos (no montones de prioridad). Los montones son, por defecto, referencias de hash anónimas, pero pueden inicializarse en create() para ser casi cualquier cosa. POE::Session en sí mismo nunca utiliza $_[HEAP], aunque algunos componentes de POE sí lo hacen.

Los montones no se superponen entre sesiones, aunque el parámetro "heap" de create() puede usarse para que esto suceda.

sub _start_handler {

$_[STATE]

El parámetro STATE del manejador contiene el nombre del evento que se está enviando en la devolución de llamada actual. Esto puede ser importante ya que los nombres de los eventos y manejadores pueden diferir significativamente. Además, un solo manejador puede asignarse a más de un evento.

POE::Session->create(
  inline_states => {
    one => \&some_handler,
    two => \&some_handler,
    six => \&some_handler,
    ten => \&some_handler,
    _start => sub {
      $_[KERNEL]->yield($_) for qw(one two six ten);
    }
  }
);
sub some_handler {
  print(
    "Session ", $_[SESSION]->ID,
    ": some_handler() handled event $_[STATE]\n"
  );
}

Cabe señalar, sin embargo, que tener nombres de eventos y manejadores que coincidan hará que su código sea más fácil de navegar.

$_[SENDER]

Los eventos deben provenir de algún lugar. $_[SENDER] contiene la fuente del evento que se está enviando actualmente.

$_[SENDER] se usa comúnmente como una dirección de retorno para las respuestas. También puede compararse con $_[KERNEL] para verificar que los temporizadores y otros eventos generados por POE::Kernel no hayan sido falsificados.

Este echo_handler() responde al remitente con un evento "echo" que contiene todos los parámetros que recibió. Evita un bucle de retroalimentación asegurándose de que la sesión y el evento (STATE) del remitente no sean idénticos a los actuales.

sub echo_handler {
  return if $_[SENDER] == $_[SESSION] and $_[STATE] eq "echo";
  $_[KERNEL]->post( $_[SENDER], "echo", @_[ARG0..$#_] );
}

$_[CALLER_FILE], $_[CALLER_LINE] y $_[CALLER_STATE]

Estos parámetros son una forma de caller(), pero describen de dónde se originó el evento que se está enviando actualmente. CALLER_FILE y CALLER_LINE son bastante simples. CALLER_STATE contiene el nombre del evento que se estaba manejando cuando se creó el evento, o cuando se registró el observador de eventos que finalmente creó el evento.

@_[ARG0..ARG9] o @_[ARG0..$#_]

Los parámetros $_[ARG0] hasta el final de @_ contienen los parámetros proporcionados por el código de la aplicación, los observadores de eventos o las bibliotecas de nivel superior. Estos parámetros están garantizados para estar al final de @_ para que @_[ARG0..$#_] siempre los capture a todos.

$#_ es el índice del último valor en @_. Culpa a Perl si parece extraño. Es meramente la sintaxis $#array donde el nombre de la matriz es un guión bajo.

Considere

$_[KERNEL]->yield( ev_whatever => qw( zero one two three ) );

El manejador para ev_whatever será llamado con "zero" en $_[ARG0], "one" en $_[ARG1], y así sucesivamente. @_[ARG0..$#_] contendrá todas las cuatro palabras.

sub ev_whatever {
  $_[OBJECT]->whatever( @_[ARG0..$#_] );
}

Usando POE::Session con Objetos

Una sesión puede manejar eventos de muchos objetos. O mirándolo de otra manera, múltiples objetos pueden combinarse en una sola sesión. Y para qué negarlo, adelante y mezcle algo de código en línea también.

POE::Session->create(
  object_states => [
    $object_1 => { event_1a => "method_1a" },
    $object_2 => { event_2a => "method_2a" },
  ],
  inline_states => {
    event_3 => \&piece_of_code,
  },
);

Sin embargo, solo un manejador puede asignarse a un nombre de evento dado. Los duplicados sobrescribirán los anteriores.

event_1a se maneja llamando a "$object_1->method_1a(...)". $_[OBJECT] es $object_1 en este caso. $_[HEAP] pertenece a la sesión, lo que significa que cualquier cosa almacenada allí estará disponible para cualquier otro manejador de eventos, independientemente del objeto.

event_2a se maneja llamando a "$object_2->method_2a(...)". En este caso, $_[OBJECT] es $object_2. Sin embargo, $_[HEAP] es el mismo hashref anónimo que se pasó al manejador de event_1a. Los métodos se resuelven cuando se maneja el evento (enlace tardío).

event_3 se maneja llamando a piece_of_code(...). $_[OBJECT] es "undef" aquí porque no hay objeto. Y una vez más, $_[HEAP] es el mismo hashref compartido que vieron los manejadores de event_1a y event_2a.

Curiosamente, no hay ninguna razón técnica por la que un solo objeto no pueda manejar eventos de más de una sesión:

for (1..2) {
  POE::Session->create(
    object_states => [
      $object_4 => { event_4 => "method_4" },
    ]
  );
}

Ahora "$object_4->method_4(...)" puede ser llamado para manejar eventos de una de dos sesiones. En ambos casos, $_[OBJECT] será $object_4, pero $_[HEAP] contendrá datos para una sesión particular.

Lo mismo ocurre con los estados en línea. Una subrutina puede manejar eventos de muchas sesiones. $_[SESSION] y $_[HEAP] se pueden usar dentro del manejador para acceder fácilmente al contexto de la sesión en la que se está manejando el evento.

MÉTODOS PÚBLICOS

POE::Session tiene solo unos pocos métodos públicos.

create MUCHA_COSA

create() inicia una nueva sesión en ejecución. Devuelve un nuevo objeto POE::Session al éxito, pero la mayoría de las aplicaciones no necesitarán guardarlo.

create() invoca el manejador de eventos _start de la sesión recién iniciada antes de devolver.

create() también pasa el nuevo objeto POE::Session a POE::Kernel. El kernel de POE retiene el objeto para poder enviarle eventos. POE::Kernel liberará el objeto cuando detecte que el objeto se ha vuelto moribundo. Esto debería hacer que Perl destruya el objeto si el código de la aplicación no ha guardado una copia de él.

create() acepta varios parámetros nombrados, la mayoría de los cuales son opcionales. Tenga en cuenta, sin embargo, que los parámetros no forman parte de un hashref.

args => ARRAYREF

El parámetro "args" acepta una referencia a una lista de parámetros que se pasarán al manejador de eventos _start de la sesión en las posiciones "ARG0" hasta $#_ (el final de @_).

Este ejemplo imprimiría "arg0 arg1 etc.":

POE::Session->create(
  inline_states => {
    _start => sub {
      print "Session started with arguments: @_[ARG0..$#_]\n";
    },
  },
  args => [ 'arg0', 'arg1', 'etc.' ],
);

heap => ANYTHING

El parámetro "heap" permite que el heap de una sesión se inicialice de manera diferente en el momento de la instanciación. Los heaps suelen ser hashrefs anónimos, pero "heap" puede configurarlos para que sean referencias a arrays o incluso objetos.

Este ejemplo imprime "tree":

POE::Session->create(
  inline_states => {
    _start => sub {
      print "Slot 0 = $_[HEAP][0]\n";
    },
  },
  heap => [ 'tree', 'bear' ],
);

Tenga cuidado al inicializar el heap con algo que no se comporte como un hashref. Algunas bibliotecas asumen semánticas de heap hashref y fallarán si el heap no funciona de esa manera.

inline_states => HASHREF

"inline_states" mapea nombres de eventos a las subrutinas que los manejarán. Su valor es un hashref que mapea nombres de eventos a los coderefs de sus manejadores correspondientes:

POE::Session->create(
  inline_states => {
    _start => sub {
      print "arg0=$_[ARG0], arg1=$_[ARG1], etc.=$_[ARG2]\n";
    },
    _stop  => \&stop_handler,
  },
  args => [qw( arg0 arg1 etc. )],
);

El término "inline" proviene del hecho de que los coderefs pueden ser subrutinas anónimas en línea.

Sin embargo, tenga mucho cuidado con los cierres. "Tenga cuidado con las referencias circulares".

object_states => ARRAYREF

"object_states" asocia uno o más objetos a una sesión y mapea nombres de eventos a los métodos de objeto que los manejarán. Su valor es una "ARRAYREF"; "HASHREFs" convertirían los objetos a cadenas, arruinándolos para la invocación de métodos.

Aquí, _start es manejado por "$object->_session_start()" y _stop activa "$object->_session_stop()":

POE::Session->create(
  object_states => [
    $object => {
      _start => '_session_start',
      _stop  => '_session_stop',
    }
  ]
);

POE::Session también admite una forma abreviada donde los nombres de eventos y métodos son idénticos. Aquí, _start invoca $object->_start(), y _stop activa $object->_stop():

POE::Session->create(
  object_states => [
    $object => [ '_start', '_stop' ],
  ]
);

Los métodos se verifican cuando se crea la sesión, pero también se resuelven cuando se llama al manejador (enlace tardío). La mayoría de las veces, un método no cambiará. Pero en algunas circunstancias, como la herencia dinámica, un método podría resolverse a una subrutina diferente.

options => HASHREF

Las sesiones de POE::Session admiten un pequeño número de opciones, que pueden configurarse inicialmente con el parámetro del constructor "option" y cambiarse en tiempo de ejecución con el método "option()|/option".

"option" toma un hashref con pares de opción => valor:

POE::Session->create(
  ... set up h
andlers ..., options => { trace => 1, debug => 1 }, ); ```

Esto es equivalente al ejemplo anterior:

POE::Session->create(
  ... configurar manejadores ...,
)->option( trace => 1, debug => 1 );

Las opciones y valores admitidos se documentan con el método "option()|/option".

package_states => ARRAYREF

"package_states" asocia una o más clases a una sesión y mapea nombres de eventos a los métodos de clase que los manejarán. Su función es análoga a "object_states", pero se especifican nombres de paquetes en lugar de objetos.

De hecho, la siguiente documentación es una copia de la descripción de "object_states" con algunas sustituciones de palabras.

El valor para "package_states" es un ARRAYREF para ser coherente con "object_states", aunque los nombres de clase (también conocidos como nombres de paquetes) ya son cadenas, por lo que no es necesario evitar su conversión a cadenas.

Aquí _start es manejado por "$class_name->_session_start()" y _stop desencadena "$class_name->_session_stop()":

POE::Session->create(
  package_states => [
    $class_name => {
      _start => '_session_start',
      _stop  => '_session_stop',
    }
  ]
);

POE::Session también admite una forma abreviada donde los nombres de evento y método son idénticos. Aquí _start invoca "$class_name->_start()", y _stop desencadena "$class_name->_stop()":

POE::Session->create(
  package_states => [
    $class_name => [ '_start', '_stop' ],
  ]
);

ID

ID() devuelve el identificador único de la instancia de la sesión. Es un entero que comienza en 1 y cuenta hacia arriba para siempre, o hasta que el número se desborde.

Es teóricamente posible que un ID de sesión no sea único, pero esto requiere la creación de al menos 4.29 mil millones de sesiones dentro del ciclo de vida de un programa. Sin embargo, POE garantiza que no habrá dos sesiones con el mismo ID al mismo tiempo; su computadora no tiene suficiente memoria para almacenar 4.29 mil millones de objetos de sesión.

El ID de una sesión es único dentro de un proceso en ejecución, pero es probable que múltiples procesos tengan los mismos IDs de sesión. Si se requiere un ID global, deberá incluir tanto "$_[KERNEL]->ID" como "$_[SESSION]->ID".

option OPTION_NAME [, OPTION_VALUE [, OPTION_NAME, OPTION_VALUE]... ]

option() establece y/o recupera los valores de varias opciones de sesión. Las opciones en cuestión son implementadas por POE::Session y no tienen ningún significado especial en ningún otro lugar.

Puede ser llamado con un solo OPTION_NAME para recuperar el valor de esa opción.

my $trace_value = $_[SESSION]->option('trace');

option() establece el valor de una opción cuando se llama con un par de OPTION_NAME, OPTION_VALUE. En este caso, option() devuelve el valor anterior de la opción.

my $previous_trace = $_[SESSION]->option(trace => 1);

option() también puede usarse para establecer los valores de múltiples opciones a la vez. En este caso, option() devuelve los valores anteriores de todas las opciones especificadas en un hashref anónimo:

my $previous_values = $_[SESSION]->option(
  trace => 1,
  debug => 1,
);
print "Previous option values:\n";
while (my ($option, $old_value) = each %$previous_values) {
  print "  $option = $old_value\n";
}

POE::Session actualmente admite tres opciones:

La opción "debug".

La opción "debug" está destinada a habilitar advertencias adicionales cuando suceden cosas extrañas dentro de POE::Session. En este momento, solo hay una advertencia adicional:

•
Redefinir un manejador de eventos generalmente no causa una advertencia, pero lo hará cuando la opción "debug" esté establecida.

La opción "default".

Habilitar la opción "default" hace que los eventos desconocidos se conviertan en advertencias, si no hay un manejador _default para capturarlos.

El indicador de nivel de clase "POE::Session::ASSERT_STATES" se implementa habilitando la opción "default" en todas las sesiones nuevas.

La opción "trace".

Activa la opción "trace" para volcar un registro de todos los eventos distribuidos a una sesión particular. Esta es una opción de rastreo específica de la sesión que permite depurar sesiones individuales.

El rastreo a nivel de sesión también indica cuándo los eventos se redireccionan a _default. Esto se puede usar para descubrir errores de nomenclatura de eventos.

Opciones definidas por el usuario.

option() no verifica si los nombres de OPCIÓN son conocidos, por lo que option() puede usarse para almacenar y recuperar información definida por el usuario.

Elija los nombres de opción con precaución. No existe una convención establecida para evitar colisiones de nombres entre opciones definidas por el usuario y futuras opciones internas.

postback EVENT_NAME, EVENT_PARAMETERS

postback() crea devoluciones de llamada que envían eventos POE. Devuelve una referencia de código anónima que enviará EVENT_NAME a la sesión de destino, con EVENT_PARAMETERS opcionales en una referencia de array en ARG0. Los parámetros pasados a la devolución de llamada se enviarán en una referencia de array en ARG1.

En otras palabras, ARG0 permite al creador del postback pasar contexto a través del postback. ARG1 permite al llamador devolver información.

Este ejemplo crea un coderef que, al ser llamado, envía "ok_button" a $some_session con ARG0 que contiene "[ 8, 6, 7 ]".

my $postback = $some_session->postback( "ok_button", 8, 6, 7 );

Aquí hay un ejemplo de manejador de eventos para "ok_button".

sub handle_ok_button {
  my ($creation_args, $called_args) = @_[ARG0, ARG1];
  print "Postback created with (@$creation_args).\n";
  print "Postback called with (@$called_args).\n";
}

Llamar a $postback->(5, 3, 0, 9) realizaría el equivalente a...

$poe_kernel->post(
  $some_session, "ok_button",
  [ 8, 6, 7 ],
  [ 5, 3, 0, 9 ]
);

Esto se mostraría cuando "ok_button" se distribuyera a handle_ok_button():

Postback created with (8 6 7).
Postback called with (5 3 0 9).

Los postbacks mantienen referencias a sus sesiones de destino. Por lo tanto, las sesiones con postbacks pendientes permanecerán activas. Bajo todos los bucles de eventos excepto Tk, los postbacks son bendecidos para que DESTROY pueda ser llamado cuando sus usuarios hayan terminado. Esto activa una disminución en sus recuentos de referencia, permitiendo que las sesiones se detengan.

Los postbacks tienen un método, weaken(), que puede usarse para reducir sus recuentos de referencia a demanda. weaken() devuelve el postback, por lo que puede hacer:

my $postback = $session->postback("foo")->weaken();

Los postbacks se crearon como un adaptador delgado entre las bibliotecas de devolución de llamada y POE. El problema en cuestión era cómo convertir las devoluciones de llamada de los widgets del toolkit gráfico de Tk en eventos POE sin tener que subclassificar varias clases de Tk. La solución fue proporcionar a Tk devoluciones de llamada simples que enviaran eventos POE.

Dado que postback() y callback() son métodos de Sesión, pueden ser llamados en $_[SESSION] o $_[SENDER], dependiendo de las necesidades particulares. Sin embargo, generalmente hay mejores maneras de interactuar entre sesiones que abusar de los postbacks.

Aquí hay un breve ejemplo de cómo adjuntar un botón Gtk2 a un manejador de eventos POE:

my $btn = Gtk2::Button->new("Clear");
$btn->signal_connect( "clicked", $_[SESSION]->postback("ev_clear") );

Puntos a recordar: La sesión permanecerá viva mientras $btn exista y mantenga una copia del postback de $_[SESSION]. Cualquier parámetro pasado por el botón Gtk2 estará en ARG1.

callback EVENT_NAME, EVENT_PARAMETERS

callback() crea devoluciones de llamada que usan "$poe_kernel->call()" para entregar eventos POE en lugar de "$poe_kernel->post()". Es idéntico a postback() en todos los demás aspectos.

callback() se creó para evitar condiciones de carrera que surgen cuando las bibliotecas externas asumen que las devoluciones de llamada se ejecutarán de forma síncrona. File::Find es un ejemplo obvio (pero no necesariamente apropiado). Proporciona mucha información en variables locales que dejan de ser válidas después de la devolución de llamada. La información no estaría disponible para cuando se distribuya un evento post()ed.

get_heap

get_heap() devuelve una referencia al heap de una sesión. Este es el mismo valor que $_[HEAP] para la sesión de destino. get_heap() está destinado a ser utilizado con $poe_kernel y get_active_session() de POE::Kernel para que las bibliotecas no necesiten que estos tres valores comunes se les pasen explícitamente.

Es decir, evita la necesidad de:

sub some_helper_function {
  my ($kernel, $session, $heap, @specific_parameters) = @_;
  ...;
}

En su lugar, las funciones auxiliares pueden usar:

use POE::Kernel; # exporta $poe_kernel
sub some_helper_function {
  my (@specific_parameters) = @_;
  my $session = $poe_kernel->get_active_session();
  my $heap = $session->get_heap();
}

Esto no es muy conveniente para las personas que escriben bibliotecas, pero hace que las bibliotecas sean mucho más convenientes de usar.

Se desaconseja encarecidamente el uso de get_heap() para romper la encapsulación de otra sesión.

NAME

POE::Session - POE Session objects

SYNOPSIS

  my $session = POE::Session->create(
    'file'            => $some_filehandle,
    'heap'            => {},
    'leaked_objects'  => 1, # or 0
    'options'         => { 'some_option' => 1 },
    'package_name'    => 'MySessionPackage',
    'session_id'      => 1234, # usually not specified
    'state'           => \&my_state_handler,
    'states'          => {
      'connect' => \&my_connect_handler,
      'disconnect' => \&my_disconnect_handler,
      # etc.
    },
    # Other parameters are passed to instantiate() and try_alloc()
    'new_option'      => 'some_value',
  );
  # ... later ...
  $kernel->post($session, 'some_event', @event_args);

DESCRIPTION

POE::Session objects encapsulate a single "session" within a POE program. They are the fundamental unit of concurrency in POE.

Every POE program is composed of one or more sessions. Each session runs independently of the others, processing events that are sent to it by the POE::Kernel.

Sessions are created via the POE::Kernel->spawn() or POE::Session->create() methods. These methods accept a hash of parameters that are used to configure the session.

Each session is identified by a unique session ID. Session IDs are arbitrary integers.

See POE::Kernel for more on how sessions interact with the kernel.

USING POE::Session

Generally, you don't interact directly with POE::Session objects. You create them using POE::Session->create() and then send them events using POE::Kernel->post().

The parameters passed to create() are used to initialize the session:

file
A filehandle for the session to use. If not specified, POE::Session will use STDOUT.

This parameter is passed to the session's _start handler as $_[OUTPUT].

heap
A hash reference for session-specific private data. It is passed to the session's event handlers as $_[HEAP].

If not specified, an empty hash reference is created.

leaked_objects
A boolean value. If true, POE will not attempt to automatically garbage collect objects that the session has referenced. This is useful for objects that may be used by multiple sessions, or for objects that should persist for the lifetime of the program. Defaults to false.
options
A hash reference of options to be passed to the session. These options are session-specific and are accessed via the option() method.
package_name
The name of the package that the session belongs to. This is used for event dispatching. If not specified, POE::Session will be used.
session_id
The session ID to use. This is normally generated by the POE::Kernel. You should not specify this unless you have a very specific reason to do so.
state
A single state handler subroutine. This is equivalent to specifying a _default handler in the states parameter.
states
A hash reference mapping event names to subroutine references (handlers). When an event is dispatched to the session, POE::Kernel will look for a handler with the same name as the event. If found, it will be called.

For example:

  states => {
    'connect' => \&handle_connect,
    'disconnect' => \&handle_disconnect,
  }

If no handler is found for an event, POE::Kernel will try to dispatch it to the session's _default handler, if one is defined.

Any parameters not explicitly recognized by POE::Session->create() will be passed to the instantiate() and try_alloc() methods of the session's class.

PUBLIC METHODS

POE::Session provides the following methods:

option

The option() method may be used to get or set session options.

  my $value = $session->option('some_option');
  $session->option('another_option' => 'some_value');

Options are typically set when a session is created using the options parameter.

ID

ID() returns the session's unique ID.

  my $session_id = $session->ID;

package_name

package_name() returns the name of the session's package.

  my $package = $session->package_name;

yield

yield() is a convenience method that posts an event back to the current session.

  # Inside an event handler:
  $_[KERNEL]->yield('some_event', @args);

This is equivalent to:

  $_[KERNEL]->post($_[SESSION], 'some_event', @args);

Using yield() can be slightly more efficient than post() in this specific case.

instantiate CREATE_PARAMETERS

instantiate() creates and returns an empty POE::Session object. It is called with the CREATE_PARAMETERS in a hash reference just before create() processes them. Modifications to the CREATE_PARAMETERS will affect how create() initializes the new session.

Subclasses may override instantiate() to alter the underlying session's structure. They may extend instantiate() to add new parameters to create().

Any parameters not recognized by create() must be removed from the CREATE_PARAMETERS before instantiate() returns. create() will croak if it discovers unknown parameters.

Be sure to return $self from instantiate.

sub instantiate {
  my ($class, $create_params) = @_;
  # Have the base class instantiate the new session.
  my $self = $class->SUPER::instantiate($create_parameters);
  # Extend the parameters recognized by create().
  my $new_option = delete $create_parameters->{new_option};
  if (defined $new_option) {
    # ... customize $self here ...
  }
  return $self;
}

try_alloc START_ARGS

try_alloc() calls POE::Kernel's session_alloc() to allocate a session structure and begin managing the session within POE's kernel. It is called at the end of POE::Session's create(). It returns $self.

It is a subclassing hook for late session customization prior to create() returning. It may also affect the contents of @_[ARG0..$#_] that are passed to the session's _start handler.

sub try_alloc {
  my ($self, @start_args) = @_;
  # Perform late initialization.
  # ...
  # Give $self to POE::Kernel.
  return $self->SUPER::try_alloc(@args);
}

POE::Session's EVENTS

Please do not define new events that begin with a leading underscore. POE claims /^_/ events as its own.

POE::Session only generates one event, _default. All other internal POE events are generated by (and documented in) POE::Kernel.

_default

_default is the "AUTOLOAD" of event handlers. If POE::Session can't find a handler at dispatch time, it attempts to redirect the event to _default's handler instead.

If there's no _default handler, POE::Session will silently drop the event unless the "default" option is set.

To preserve the original information, the original event is slightly changed before being redirected to the _default handler: The original event parameters are moved to an array reference in ARG1, and the original event name is passed to _default in ARG0.

sub handle_default {
  my ($event, $args) = @_[ARG0, ARG1];
  print(
    "Session ", $_[SESSION]->ID,
    " caught unhandled event $event with (@$args).\n"
  );
}

_default is quite flexible. It may be used for debugging, or to handle dynamically generated event names without pre-defining their handlers. In the latter sense, _default performs analogously to Perl's "AUTOLOAD".

_default may also be used as the default or "otherwise" clause of a switch statement. Consider an input handler that throws events based on a command name:

sub parse_command {
  my ($command, @parameters) = split /\s+/, $_[ARG0];
  $_[KERNEL]->post( "cmd_$command", @parameters );
}

A _default handler may be used to emit errors for unknown commands:

sub handle_default {
  my $event = $_[ARG0];
  return unless $event =~ /^cmd_(\S+)/;
  warn "Unknown command: $1\n";
}

The _default behavior is implemented in POE::Session, so it may be different for other session types.

POE::Session's Debugging Features

POE::Session contains one debugging assertion, for now.

ASSERT_STATES

Setting ASSERT_STATES to true causes every Session to warn when they are asked to handle unknown events. Session.pm implements the guts of ASSERT_STATES by defaulting the "default" option to true instead of false. See the option() method earlier in this document for details about the "default" option.

BUGS

There is a chance that session IDs may collide after Perl's integer value wraps. This can occur after as few as 4.29 billion sessions.

Beware circular references

As you're probably aware, a circular reference is when a variable is part of a reference chain that eventually refers back to itself. Perl will not reclaim the memory involved in such a reference chain until the chain is manually broken.

Here a POE::Session is created that refers to itself via an external scalar. The event handlers import $session via closures which are in turn stored within $session. Even if this session stops, the circular references will remain.

my $session;
$session = POE::Session->create(
  inline_states => {
    _start => sub {
      $_[HEAP]->{todo} = [ qw( step1 step2 step2a ) ],
      $_[KERNEL]->post( $session, 'next' );
    },
    next => sub {
      my $next = shift @{ $_[HEAP]->{todo} };
      return unless $next;
      $_[KERNEL]->post( $session, $next );
    }
    # ....
  }
);

Reduced to its essence:

my %event_handlers;
$event_handler{_start} = sub { \%event_handlers };

Note also that an anonymous sub creates a closure on all lexical variables in the scope it was defined in, even if it doesn't reference them. $session is still being held in a circular reference here:

my $self = $package->new;
my $session;
$session = POE::Session->create(
  inline_state => {
    _start => sub { $self->_start( @_[ARG0..$#_] ) }
  }
);

To avoid this, a session may set an alias for itself. Other parts of the program may then refer to it by alias. In this case, one needn't keep track of the session themselves (POE::Kernel will do it anyway).

POE::Session->create(
  inline_states => {
    _start => sub {
      $_[HEAP]->{todo} = [ qw( step1 step2 step2a ) ],
      $_[KERNEL]->alias_set('step_doer');
      $_[KERNEL]->post( 'step_doer', 'next' );
    },
    next => sub {
      my $next = shift @{ $_[HEAP]->{todo} };
      return unless $next;
      $_[KERNEL]->post( 'step_doer', $next );
    }
    # ....
  }
);

Aliases aren't even needed in the previous example because the session refers to itself. One could instead use POE::Kernel's yield() method to post the event back to the current session:

next => sub {
  my $next = shift @{ $_[HEAP]->{todo} };
  return unless $next;
  $_[KERNEL]->yield( $next );
}

Or the "$_[SESSION]" parameter passed to every event handler, but yield() is more efficient.

next => sub {
  my $next = shift @{ $_[HEAP]->{todo} };
  return unless $next;
  $_[KERNEL]->post( $_[SESSION], $next );
}

Along the same lines as "$_[SESSION]", a session can respond back to the sender of an event by posting to "$_[SENDER]". This is great for responding to requests.

If a program must hold onto some kind of dynamic session reference, it's recommended to use the session's numeric ID rather than the object itself. A session ID may be converted back into its object, but post() accepts session IDs as well as objects and aliases:

my $session_id;
$session_id = POE::Session->create(
  inline_states => {
    _start => sub {
      $_[HEAP]->{todo} = [ qw( step1 step2 step2a ) ],
      $_[KERNEL]->post( $session_id, 'next' );
    },
    # ....
  }
)->ID;
