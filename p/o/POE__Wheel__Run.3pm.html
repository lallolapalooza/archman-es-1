NOMBRE

POE::Wheel::Run - ejecutar de forma portable código bloqueante y programas en subprocesos

SINOPSIS

#!/usr/bin/perl
use warnings;
use strict;
use POE qw( Wheel::Run );
POE::Session->create(
  inline_states => {
    _start           => \&on_start,
    got_child_stdout => \&on_child_stdout,
    got_child_stderr => \&on_child_stderr,
    got_child_close  => \&on_child_close,
    got_child_signal => \&on_child_signal,
  }
);
POE::Kernel->run();
exit 0;
sub on_start {
  my $child = POE::Wheel::Run->new(
    Program => [ "/bin/ls", "-1", "/" ],
    StdoutEvent  => "got_child_stdout",
    StderrEvent  => "got_child_stderr",
    CloseEvent   => "got_child_close",
  );
  $_[KERNEL]->sig_child($child->PID, "got_child_signal");
  # Los eventos de la rueda incluyen el ID de la rueda.
  $_[HEAP]{children_by_wid}{$child->ID} = $child;
  # Los eventos de señal incluyen el ID del proceso.
  $_[HEAP]{children_by_pid}{$child->PID} = $child;
  print(
    "El proceso hijo con PID ", $child->PID,
    " se inició como rueda ", $child->ID, ".\n"
  );
}
# Evento de rueda, incluyendo el ID de la rueda.
sub on_child_stdout {
  my ($stdout_line, $wheel_id) = @_[ARG0, ARG1];
  my $child = $_[HEAP]{children_by_wid}{$wheel_id};
  print "PID ", $child->PID, " STDOUT: $stdout_line\n";
}
# Evento de rueda, incluyendo el ID de la rueda.
sub on_child_stderr {
  my ($stderr_line, $wheel_id) = @_[ARG0, ARG1];
  my $child = $_[HEAP]{children_by_wid}{$wheel_id};
  print "PID ", $child->PID, " STDERR: $stderr_line\n";
}
# Evento de rueda, incluyendo el ID de la rueda.
sub on_child_close {
  my $wheel_id = $_[ARG0];
  my $child = delete $_[HEAP]{children_by_wid}{$wheel_id};
  # Puede haber sido recogido por on_child_signal().
  unless (defined $child) {
    print "La rueda $wheel_id cerró todas las tuberías.\n";
    return;
  }
  print "PID ", $child->PID, " cerró todas las tuberías.\n";
  delete $_[HEAP]{children_by_pid}{$child->PID};
}
sub on_child_signal {
  print "El PID $_[ARG1] salió con estado $_[ARG2].\n";
  my $child = delete $_[HEAP]{children_by_pid}{$_[ARG1]};
  # Puede haber sido recogido por on_child_close().
  return unless defined $child;
  delete $_[HEAP]{children_by_wid}{$child->ID};
}

DESCRIPCIÓN

POE::Wheel::Run ejecuta un programa o un bloque de código en un subproceso, creado de la forma habitual: usando fork(). El proceso padre puede intercambiar información con el hijo a través de los manejadores de archivos STDIN, STDOUT y STDERR del hijo.

En el proceso padre, el objeto POE::Wheel::Run representa al subproceso. Tiene métodos como PID() y kill() para consultar y gestionar el subproceso.

El método put() de POE::Wheel::Run envía datos al STDIN del hijo. La salida del hijo en STDOUT y STDERR puede ser despachada como eventos dentro del padre, si se solicita.

POE::Wheel::Run también puede notificar al padre cuando el hijo ha cerrado sus manejadores de archivos de salida. Algunos programas permanecen activos, pero cierran sus manejadores de archivos de salida para indicar que han terminado de escribir.

Una forma más fiable de detectar la salida del hijo es usar el método sig_child() de POE::Kernel para esperar a que se recoja el proceso de la rueda. De hecho, es vital usar sig_child() en todas las circunstancias, ya que sin él, POE no intentará recoger los subprocesos.

No usar sig_child() ha llevado en el pasado a máquinas bloqueadas. Los programas de larga ejecución han filtrado procesos, consumiendo eventualmente todas las ranuras disponibles en la tabla de procesos y requiriendo reinicios.

Dado que las fugas de procesos son tan graves, POE::Kernel verificará esta condición al salir y mostrará un aviso si encuentra que los procesos se están filtrando. Los desarrolladores deben prestar atención a estas advertencias.

POE::Wheel::Run se comunica con el subproceso de forma basada en líneas por defecto. Los programas pueden anular esto especificando algún otro objeto POE::Filter en "StdinFilter", "StdoutFilter", "StdioFilter" y/o "StderrFilter".

MÉTODOS PÚBLICOS

Constructor

Las subclases de POE::Wheel tienden a realizar mucha configuración para que funcionen de manera más ligera y rápida. El constructor de POE::Wheel::Run no es una excepción.

new

new() crea y devuelve un nuevo objeto POE::Wheel::Run. Si tiene éxito, el objeto representará un subproceso con ciertas cualidades especificadas. También proporciona una interfaz orientada a objetos y basada en eventos para interactuar de forma asíncrona con el proceso.

Conduit

Conduit especifica el mecanismo de comunicación entre procesos que se utilizará para pasar datos entre el proceso padre y el hijo. Conduit puede ser uno de "pipe", "socketpair", "inet", "pty" o "pty-pipe". POE::Wheel::Run utilizará el Conduit más apropiado para el sistema operativo en tiempo de ejecución (no en tiempo de compilación), pero esto varía de un sistema operativo a otro.

Internamente, POE::Wheel::Run pasa el tipo de Conduit a POE::Pipe::OneWay y POE::Pipe::TwoWay. Estas clases auxiliares se crearon para hacer que la IPC sea portable y reutilizable. No requieren el resto de POE.

Tres tipos de Conduit utilizan tuberías o comunicación entre procesos similar a tuberías: "pipe", "socketpair" y "inet". Determinan si la IPC interna utiliza pipe(), socketpair() o sockets de Internet. Estos valores de Conduit se pasan a POE::Pipe::OneWay o POE::Pipe::TwoWay internamente.

El tipo de conduit "pty" ejecuta el subproceso bajo un pseudo-tty, que es creado por IO::Pty. Los pseudo-ttys (ptys) convencen a los subprocesos de que están interactuando con terminales en lugar de tuberías. Esto puede usarse para engañar a programas como ssh para que crean que es seguro solicitar una contraseña, aunque las identidades sin contraseña podrían ser mejores para eso.

El conduit "pty" no puede separar STDERR de STDOUT, pero el modo "pty-pipe" sí puede.

El conduit "pty-pipe" utiliza un pty para STDIN y STDOUT y una tubería unidireccional para STDERR. La tubería adicional mantiene la salida de STDERR separada de STDOUT.

El módulo IO::Pty solo se carga si se utiliza "pty" o "pty-pipe". No es una dependencia hasta que realmente se necesita.

Winsize

Winsize establece el tamaño de la terminal del subproceso. Su valor debe ser un arrayref con cuatro elementos. Los primeros dos elementos deben ser el número de líneas y columnas para la ventana del terminal del hijo, respectivamente. El último par de elementos describe las dimensiones X e Y del terminal en píxeles. Si falta el último par, se calcularán a partir de las líneas y columnas usando un tamaño de celda de 9x16.

$_[HEAP]{child} = POE::Wheel::Run->new(
  # ... entre otras cosas ...
  Winsize => [ 25, 80, 720, 400 ],
);

Winsize solo es válido para conduits que utilizan pseudo-ttys: "pty" y "pty-pipe". Otros conduits no simulan terminales, por lo que no tienen tamaños de ventana.

Winsize por defecto es el tamaño de la ventana del proceso padre, asumiendo que el proceso padre tiene un terminal para consultar.

CloseOnCall

CloseOnCall, cuando es verdadero, activa la emulación de cerrar al ejecutar para subprocesos que en realidad no llaman a exec(). Estos serían casos en los que el hijo está ejecutando un bloque de código en lugar de ejecutar un programa externo. Por ejemplo:

$_[HEAP]{child} = POE::Wheel::Run->new(
  # ... entre otras cosas ...
  CloseOnCall => 1,
  Program => \&some_function,
);

CloseOnCall está desactivado (0) por defecto.

CloseOnCall funciona cerrando todos los descriptores de archivo mayores que $^F en el proceso hijo antes de llamar al código de la aplicación. Para más detalles, por favor consulte la discusión sobre $^F en perlvar.

StdioDriver

StdioDriver especifica un único objeto POE::Driver que se utilizará tanto para STDIN como para STDOUT. Es equivalente a establecer "StdinDriver" y "StdoutDriver" al mismo objeto POE::Driver.

POE::Wheel::Run creará y usará un controlador POE::Driver::SysRW si no se especifica uno. Este es, con mucho, el caso de uso más común, por lo que es el valor predeterminado.

StdinDriver

"StdinDriver" establece el POE::Driver utilizado para escribir en el conducto IPC de STDIN del proceso hijo. Casi nunca se necesita. Omitirlo permitirá a POE::Wheel::Run usar un objeto POE::Driver::SysRW creado internamente.

StdoutDriver

"StdoutDriver" establece el objeto POE::Driver que se utilizará para leer desde el STDOUT del proceso hijo

Casi nunca es necesario. Si se omite, POE::Wheel::Run creará y utilizará internamente un objeto POE::Driver::SysRW.

StderrDriver

"StderrDriver" establece el controlador que se utilizará para leer desde el conducto STDERR del proceso hijo. Al igual que con "StdoutDriver", casi siempre es preferible dejar que POE::Wheel::Run instancie su propio controlador.

CloseEvent

CloseEvent contiene el nombre de un evento que la rueda emitirá cuando el proceso hijo cierre su último conducto de salida abierto. Esta es una notificación consistente de que el hijo ha terminado de enviar salida. Tenga en cuenta que no señala cuándo ha finalizado el proceso hijo. Los programas deben utilizar sig_child() para detectarlo.

Si bien es imposible que ErrorEvent o StdoutEvent ocurran después de CloseEvent, no hay tal garantía para CHLD, que puede ocurrir antes o después de CloseEvent.

Además de los parámetros habituales de POE, cada CloseEvent viene con uno propio:

contiene el ID único de la rueda. Esto se puede utilizar para mantener separados varios procesos hijos cuando son gestionados por la misma sesión.

Un manejador de eventos de cierre de ejemplo: 

sub close_state {
  my ($heap, $wheel_id) = @_[HEAP, ARG0];
  my $child = delete $heap->{child}->{$wheel_id};
  print "Child ", $child->PID, " has finished.\n";
}
 ErrorEvent

ErrorEvent contiene el nombre de un evento que se emitirá si algo falla. Es opcional; si se omite, la rueda no notificará a su sesión si ocurre algún error. Sin embargo, POE::Wheel::Run->new() seguirá lanzando una excepción si falla.

contiene el nombre de la operación que falló. Puede ser 'read', 'write', 'fork', 'exec' o el nombre de alguna otra función o tarea. Los valores reales aún no están definidos. Probablemente no se corresponderán tan claramente con los nombres de las funciones integradas de Perl.

y contienen valores numéricos y de cadena para "$!" será igual a para el error de lectura 0 (el proceso hijo cerró el manejador de archivos).

contiene el ID único de la rueda.

contiene el nombre del archivo del hijo que tiene el error. Puede ser "STDIN", "STDOUT" o "STDERR". El sentido de será lo opuesto a lo que normalmente esperaría para estos manejadores. Por ejemplo, POE::Wheel::Run informará un error de "lectura" en "STDOUT" porque intentó leer datos del STDOUT del hijo.

Un manejador de eventos de error de ejemplo: 

sub error_state {
  my ($operation, $errnum, $errstr, $wheel_id) = @_[ARG0..ARG3];
  $errstr = "remote end closed" if $operation eq "read" and !$errnum;
  warn "Wheel $wheel_id generated $operation error $errnum: $errstr\n";
}

Tenga en cuenta que a menos que desactive la tubería de señales, también podría ver un error "EIO" (5) durante las operaciones de lectura.

StdinEvent

StdinEvent contiene el nombre de un evento que Wheel::Run emite cada vez que todo lo que se ha puesto en cola con su método put() se ha enviado al manejador STDIN del hijo. Es el equivalente al FlushedEvent de POE::Wheel::ReadWrite.

StdinEvent viene con solo un parámetro adicional: contiene el ID único de la rueda que envió el evento.

StdoutEvent

StdoutEvent contiene el nombre de un evento que Wheel::Run emite cada vez que el proceso hijo escribe algo en su manejador de archivos STDOUT. En otras palabras, todo lo que el hijo imprime en STDOUT, el padre recibe un StdoutEvent, siempre que el hijo imprima algo compatible con el StdoutFilter del padre.

StdoutEvent viene con dos parámetros. contiene la información que el hijo escribió en STDOUT. contiene el ID único de la rueda que leyó la salida. 

sub stdout_state {
  my ($heap, $input, $wheel_id) = @_[HEAP, ARG0, ARG1];
  print "Child process in wheel $wheel_id wrote to STDOUT: $input\n";
}
 StderrEvent

StderrEvent se comporta exactamente como StdoutEvent, excepto por los datos que el proceso hijo escribe en su manejador de archivos STDERR.

StderrEvent viene con dos parámetros. contiene la información que el hijo escribió en STDERR. contiene el ID único de la rueda que leyó la salida. 

sub stderr_state {
  my ($heap, $input, $wheel_id) = @_[HEAP, ARG0, ARG1];
  print "Child process in wheel $wheel_id wrote to STDERR: $input\n";
}
 RedirectStdout

Este es un manejador de archivos o un nombre de archivo al que se redirigirá la salida estándar. Es un error utilizar esta opción junto con StdoutEvent. Esto es útil en caso de que su programa necesite tener E/S estándar, pero en realidad no le importa que su contenido sea visible para el padre.

RedirectStderr

Al igual que RedirectStdout, pero con el error estándar. Es un error utilizar esto junto con StderrEvent.

RedirectStdin

Este es un manejador de archivos o un nombre de archivo que el proceso hijo utilizará como entrada estándar. Es un error utilizar esta opción con StdinEvent.

RedirectOutput

Esto redirigirá stderr y stdout al mismo manejador de archivos. Es equivalente a hacer algo como 

$ something > /path/to/output 2>&1

en el shell de bourne.

NoStdin

Mientras que los manejadores de archivos de salida se cerrarán si no hay eventos que recibir en ellos, stdin está abierto por defecto, ya que la falta de un manejador de eventos no significa necesariamente que no haya un flujo de entrada deseado. Esta opción deshabilita explícitamente la creación de un conducto de entrada estándar IPC.

StdioFilter

StdioFilter, si se utiliza, debe contener una instancia de una subclase de POE::Filter. Este filtro describe cómo el padre formateará los datos de put() para STDIN del hijo y cómo el padre analizará STDOUT del hijo.

Si STDERR también se va a analizar, entonces también se necesitará un StderrFilter separado.

StdioFilter tiene como valor predeterminado una instancia de POE::Filter::Line, pero solo si no se especifican ni StdinFilter ni StdoutFilter. Si se utiliza StdinFilter o StdoutFilter, entonces StdioFilter es ilegal.

StdinFilter

StdinFilter se puede utilizar para especificar un serializador STDIN particular que sea diferente del analizador STDOUT. Si se especifica, entra en conflicto con StdioFilter. El valor de StdinFilter, si se especifica, debe ser una instancia de una subclase de POE::Filter.

Sin un StdinEvent, StdinFilter es ilegal.

StdoutFilter

StdoutFilter se puede utilizar para especificar un analizador STDOUT particular que sea diferente del serializador STDIN. Si se especifica, entra en conflicto con StdioFilter. El valor de StdoutFilter, si se especifica, debe ser una instancia de una subclase de POE::Filter.

Sin un StdoutEvent, StdoutFilter es ilegal.

StderrFilter

StderrFilter se puede utilizar para especificar un filtro para la salida STDERR de un proceso hijo. Si se omite, POE::Wheel::Run creará y utilizará su propia instancia de POE::Filter::Line, pero solo si se especifica un StderrEvent.

Sin un StderrEvent, StderrFilter es ilegal.

Group

Group contiene un ID de grupo numérico dentro del cual debe ejecutarse el proceso hijo. Por defecto, el proceso hijo se ejecutará en el mismo grupo que el padre.

Group no es totalmente portátil. Puede que no funcione en sistemas que no tengan el concepto de grupos de usuarios. Además, el proceso padre puede necesitar ejecutarse con privilegios elevados para que el hijo pueda cambiar de grupo.

User

User contiene un ID de usuario numérico que debe ser el propietario del proceso hijo. Por defecto, el proceso hijo se ejecutará como el mismo usuario que el padre.

User no es totalmente portátil. Puede que no funcione en sistemas que no tengan el concepto de usuarios. Además, el proceso padre puede necesitar ejecutarse con privilegios elevados para que el hijo pueda cambiar de usuario.

NoSetSid

Cuando es verdadero, NoSetSid deshabilita setsid() en el proceso hijo. Por defecto, se llama a setsid() para que el proceso hijo se ejecute en una sesión UNIX separada.

Esta opción está obsoleta. Como IO::Pty utiliza Priority

Priority ajusta la "niceness" o el nivel de prioridad del proceso hijo, dependiendo de cuál (si alguno) sea compatible con el sistema operativo subyacente. Priority contiene un desplazamiento numérico que se agregará a la prioridad del padre para determinar la del hijo.

El desplazamiento de prioridad puede ser negativo, lo que en UNIX representa una prioridad mayor. Sin embargo, UNIX requiere privilegios elevados para aumentar la prioridad de un proceso.

Program

Program especifica el programa a exec() o el bloque de código a ejecutar en el proceso hijo. El tipo de Program es significativo.

Si Program contiene un escalar, su valor se ejecutará como exec($program). Los metacaracteres del shell son significativos, según las semánticas de exec(SCALAR).

Si Program contiene una referencia a matriz, se ejecutará como exec(@$program). Según exec(ARRAY), los metacaracteres del shell no serán significativos.

Si Program contiene una referencia de código, ese código se llamará en el proceso hijo. Este modo permite a POE::Wheel::Run ejecutar código interno de larga duración de forma asíncrona, mientras que los modos habituales ejecutan programas externos. El proceso hijo saldrá después de que ese código haya finalizado, de manera que se evite la ejecución de bloques DESTROY y END. Consulte "Efectos secundarios de la ejecución de coderef" para obtener más detalles.

perlfunc tiene más información sobre exec() y las diferentes formas de llamarlo.

Evite llamar explícitamente a exit() al ejecutar una subrutina. El proceso hijo hereda todos los objetos del padre, incluidos aquellos que pueden realizar efectos secundarios. POE::Wheel::Run toma medidas especiales para evitar destructores de objetos y bloques END en el proceso hijo, pero llamar a exit() los activará.

ProgramArgs

Si se especifica, ProgramArgs debe referirse a una lista de parámetros para el programa que se está ejecutando. 

my @parameters = qw(foo bar baz);  # se pasará a Program
ProgramArgs => \@parameters;

event EVENT_TYPE => EVENT_NAME, ...

event() permite a los programas cambiar los eventos que Wheel::Run emite cuando ocurren ciertas actividades. EVENT_TYPE puede ser uno de los parámetros de evento descritos en el constructor de POE::Wheel::Run.

Este ejemplo cambia los eventos que $wheel emite para el vaciado de STDIN y la actividad de STDOUT:

$wheel->event(
  StdinEvent  => 'new-stdin-event',
  StdoutEvent => 'new-stdout-event',
);

Los EVENT_NAME indefinidos deshabilitan los eventos.

put RECORDS

put() pone en cola una lista de RECORDS que se enviarán al descriptor de archivo STDIN del proceso hijo. Estos registros se serializarán primero según el StdinFilter de la rueda. Los RECORDS serializados se enviarán de forma asíncrona una vez que el manejador de eventos actual regrese.

get_stdin_filter

get_stind_filter() devuelve el objeto POE::Filter que se está utilizando actualmente para serializar los registros de put() para el STDIN del proceso hijo. El objeto devuelto puede usarse de acuerdo con su propia interfaz.

get_stdout_filter

get_stdout_filter() devuelve el objeto POE::Filter que se está utilizando actualmente para analizar lo que el proceso hijo escribe en STDOUT.

get_stderr_filter

get_stderr_filter() devuelve el objeto POE::Filter que se está utilizando actualmente para analizar lo que el proceso hijo escribe en STDERR.

set_stdio_filter FILTER_OBJECT

Establece StdinFilter y StdoutFilter en el mismo nuevo FILTER_OBJECT. Los datos de STDOUT no analizados se analizarán más tarde con el nuevo FILTER_OBJECT. Sin embargo, los datos que ya se enviaron con put() seguirán serializados por el filtro antiguo.

set_stdin_filter FILTER_OBJECT

Establece StdinFilter en un nuevo FILTER_OBJECT. Los datos que ya se enviaron con put() seguirán serializados por el filtro antiguo.

set_stdout_filter FILTER_OBJECT

Establece StdoutFilter en un nuevo FILTER_OBJECT. Los datos de STDOUT no analizados se analizarán más tarde con el nuevo FILTER_OBJECT.

set_stderr_filter FILTER_OBJECT

Establece StderrFilter en un nuevo FILTER_OBJECT. Los datos de STDERR no analizados se analizarán más tarde con el nuevo FILTER_OBJECT.

pause_stdout

Pausa la lectura de STDOUT del proceso hijo. El proceso hijo puede bloquearse si el conducto de comunicación entre procesos (IPC) de STDOUT se llena. La lectura puede reanudarse con resume_stdout().

pause_stderr

Pausa la lectura de STDERR del proceso hijo. El proceso hijo puede bloquearse si el conducto de comunicación entre procesos (IPC) de STDERR se llena. La lectura puede reanudarse con resume_stderr().

resume_stdout

Reanuda la lectura del descriptor de archivo STDOUT del proceso hijo. Esto solo tiene sentido si se ha llamado a pause_stdout() y sigue vigente.

resume_stderr

Reanuda la lectura del descriptor de archivo STDERR del proceso hijo. Esto solo tiene sentido si se ha llamado a pause_stderr() y sigue vigente.

shutdown_stdin

shutdown_stdin() cierra el STDIN del proceso hijo y detiene la rueda de informar StdinEvent. Es extremadamente útil para ejecutar utilidades que esperan recibir EOF en STDIN antes de responder.

ID

ID() devuelve el ID único de la rueda. Cada evento generado por un objeto POE::Wheel::Run incluye un ID de rueda para que pueda ser emparejado con la rueda que lo emitió. Esto permite que una sola sesión gestione varias ruedas sin confundirse sobre cuál generó qué evento.

ID() no es lo mismo que PID().

PID

PID() devuelve el ID del proceso para el hijo representado por el objeto POE::Wheel::Run. A menudo se utiliza como parámetro para sig_child().

PID() no es lo mismo que ID().

kill SIGNAL

El método kill() de POE::Wheel::Run envía una SEÑAL al proceso hijo que representa el objeto. kill() se utiliza a menudo para forzar la terminación de un programa reacio. SIGNAL es uno de los nombres de señales del sistema operativo presentes en %SIG.

kill() devuelve el número de procesos señalados con éxito: 1 en caso de éxito o 0 en caso de fallo, ya que el objeto POE::Wheel::Run solo afecta a un proceso como máximo.

kill() envía SIGTERM si SIGNAL es indefinido u omitido.

get_driver_out_messages

get_driver_out_messages() devuelve el número de registros de put() que quedan total o parcialmente en la cola de salida POE::Driver de POE::Wheel::Run. A menudo se utiliza para saber si la rueda tiene más entrada para el proceso hijo.

En la mayoría de los casos, StdinEvent se puede utilizar para activar la actividad cuando todos los datos se han enviado al proceso hijo.

get_driver_out_octets

get_driver_out_octets() devuelve el número de octetos serializados que quedan en la cola de salida POE::Driver de POE::Wheel::Run. A menudo se utiliza para saber si la rueda tiene más entrada para el proceso hijo.

CONSEJOS Y TRUCOS

Soporte MSWin32

En el pasado, POE::Wheel::Run no admitía MSWin32 y los usuarios tenían que usar soluciones personalizadas. Luego llegó Chris Williams ( BINGOS ) y salvó el día con su módulo POE::Wheel::Run::Win32. Después de algunas pruebas, se decidió fusionar el código de win32 en POE::Wheel::Run. ¡Todos estaban contentos!

Sin embargo, después de algunas investigaciones, Apocalypse ( APOCAL ) descubrió que en algunas situaciones todavía no se comportaba correctamente. La causa raíz fue que la ruta de código win32 en POE::Wheel::Run no se cerraba limpiamente. ¡Esto significa que los bloques DESTROY y END se ejecutaron! Después de hablar con más gente, la solución no fue bonita.

El problema es que no existe un equivalente de POSIX::_exit() para MSWin32. ¡Esperemos que en una futura versión de Perl esto se pueda solucionar! Mientras tanto, POE::Wheel::Run utilizará CORE::kill() para terminar el proceso hijo. Sin embargo, esto tiene una advertencia: filtrará alrededor de 1KB por exec. El código ha sido mejorado para reducir la probabilidad de que esto ocurra.

A partir de ahora, la forma más fiable de desencadenar esto es ejecutar un binario inválido. La definición de "binario inválido" depende de diferentes cosas, pero lo que significa es que Win32::Job->spawn() no pudo ejecutarse. Esto obligará a POE::Wheel::Run a usar la solución alternativa para salir del proceso hijo. Si esto sucede, se imprimirá una gran advertencia en STDERR del proceso hijo y el proceso padre la recibirá.

Si eres un hacker de Perl para MSWin32, ¡POR FAVOR, ayúdanos en esta situación! Lee el bug #56417 de rt.cpan.org y habla con nosotros/p5p para ver dónde puedes contribuir.

¡Gracias de nuevo por tu paciencia mientras continuamos mejorando POE::Wheel::Run en MSWin32!

kill() y ClosedEvent en Windows

Windows a menudo no informa EOF en las tuberías cuando se matan los subprocesos. La solución es capturar la señal en el subproceso y salir normalmente:

my $child = POE::Wheel::Run->new(
  Program => sub {
    $SIG{INT} = sub { exit };
    ...;
  },
  ...,
);

Asegúrate de kill() el subproceso utilizando la misma señal que captura y con la que sale. Recuerda que no todas las señales pueden ser capturadas por código de usuario.

$child->kill("INT");

Entorno de Ejecución

Es común limpiar el entorno de un proceso hijo, de modo que solo existan los valores necesarios y seguros. Esto equivale a borrar el contenido de %ENV y repoblarlo.

La limpieza del entorno es fácil cuando el proceso hijo está ejecutando una subrutina, pero no es tan fácil —o al menos no tan intuitiva— cuando se ejecutan programas externos.

La forma en que lo hacemos es ejecutar una pequeña subrutina en el proceso hijo que realiza la llamada exec() por nosotros.

Program => \&exec_with_scrubbed_env,
sub exec_with_scrubbed_env {
  delete @ENV{keys @ENV};
  $ENV{PATH} = "/bin";
  exec(@program_and_args);
}

Eso elimina todo del entorno y establece una ruta PATH simple y segura antes de ejecutar un programa.

Efectos Colaterales de la Ejecución de Coderef

El proceso hijo se crea mediante fork(), que duplica el proceso padre, incluyendo una copia de POE::Kernel, todas las instancias de Sesión en ejecución, eventos en la cola, observadores, descriptores de archivo abiertos, etc.

Al ejecutar un programa externo, la llamada exec() de UNIX reemplaza inmediatamente la copia del padre con un programa completamente nuevo.

Sin embargo, al ejecutar coderefs internos, debemos preservar el código y cualquier memoria a la que pueda hacer referencia. Esto conduce a algunos efectos colaterales potenciales.

POE::Wheel::Run(3pm)

NAME

POE::Wheel::Run - run other programs as POE components

SYNOPSIS

    use POE::Wheel::Run;

    # Launch a program in a sub-process.
    my $wheel = POE::Wheel::Run->new(
        program       => 'some_program',
        args          => [ 'arg1', 'arg2' ],
        # Called when the program exits.
        close_handler => \&on_program_exit,
        # Called when the program writes to STDOUT.
        output_handler => \&on_program_output,
        # Called when the program writes to STDERR.
        error_handler => \&on_program_error,
        # Called when the program exits with an error.
        # Note: This is not called if close_handler is defined.
        #       If an error handler is defined, then it is called.
        #       Then, close_handler is called.
        #       If no error handler is defined, then POE::Kernel will
        #       call _default_error_handler.
        #       This handler IS NOT CALLED if the child process exits
        #       normally.
        # error_handler => \&on_program_error_exit,
    );

    # To access the child's STDIN, STDOUT, and STDERR.
    # STDOUT is already being handled by output_handler, and STDERR by
    # error_handler. So these are useful for feeding STDIN.
    my $stdin = $wheel->get_child_stdin();
    my $stdout = $wheel->get_child_stdout();
    my $stderr = $wheel->get_child_stderr();

    # To send output to the child's STDIN.
    $stdin->print("hello world\n");

    # Wait for the program to finish.
    # This call will block until the program has exited.
    # POE::Kernel may be run in the interim.
    POE::Kernel->run();

DESCRIPTION

POE::Wheel::Run is a POE wheel that runs an external program in a sub-process. It provides handlers for the program's STDOUT and STDERR, and allows you to send input to the program's STDIN.

The program is run using POE::Pipe, which is a POE wrapper around pipes.

POE::Wheel::Run is useful for managing external processes, like shell commands, daemons, or any other program that can be run from the command line.

TIPS AND TRICKS

Exiting the child process

When a child process exits, its `DESTROY` and `END` blocks are executed. This can lead to problems if the child process is intended to be short-lived and doesn't need to run these blocks.

POE::Wheel::Run attempts to mitigate this by using `POSIX::_exit()` to bypass the execution of `DESTROY` and `END` blocks in the child. If this fails, it may even `kill()` itself.

If your application needs to exit explicitly, for example, to return an error code to the parent process, please use `POSIX::_exit()` rather than Perl's core `exit()`.

POE::Kernel's `run()` method was never called

This warning is displayed from POE::Kernel's `DESTROY` method. It's a side effect of calling `exit()` in a child process that was started before "POE::Kernel->run()" could be called. The child process receives a copy of POE::Kernel where `run()` wasn't called, even if it was called later in the parent process.

The most direct solution is to call `POSIX::_exit()` rather than `exit()`. This will bypass POE::Kernel's `DESTROY`, and the message it emits.

Running POE::Kernel in the Child

Calling "POE::Kernel->run()" in the child process effectively resumes the copy of the parent process. This is rarely (if ever) desired.

More commonly, an application wants to run an entirely new POE::Kernel instance in the child process. This is supported by first `stop()`ping the copied instance, starting one or more new sessions, and calling `run()` again. For example:

    Program => sub {
      # Wipe the existing POE::Kernel clean.
      $poe_kernel->stop();
      # Start a new session, or more.
      POE::Session->create(
        ...
      );
      # Run the new sessions.
      POE::Kernel->run();
    }

Strange things are bound to happen if the program does not call "stop" in POE::Kernel before "run" in POE::Kernel. However this is vaguely supported in case it's the right thing to do at the time.

CAVEATS & TODOS

POE::Wheel::Run's constructor should emit proper events when it fails. Instead, it just dies, carps or croaks. This isn't necessarily bad; a program can trap the death in new() and move on.

Priority is a delta, not an absolute niceness value.

It might be nice to specify User by name rather than just UID.

It might be nice to specify Group by name rather than just GID.

POE::Pipe::OneWay and Two::Way don't require the rest of POE. They should be spun off into a separate distribution for everyone to enjoy.

If StdinFilter and StdoutFilter seem backwards, remember that it's the filters for the child process. StdinFilter is the one that dictates what the child receives on STDIN. StdoutFilter tells the parent how to parse the child's STDOUT.
