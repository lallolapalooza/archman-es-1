POE::Wheel(3) Documentación Perl Contribuida por Usuarios POE::Wheel(3)

NOMBRE

POE::Wheel - mixins orientados a eventos para POE::Session

SINOPSIS

Esta clase base no tiene sinopsis. Por favor, consulte una de las subclases en su lugar.

DESCRIPCIÓN

Un objeto POE::Wheel encapsula un conjunto de manejadores de eventos que realizan una tarea específica. También gestiona los observadores de eventos que activan dichos manejadores.

La vida útil del objeto es muy importante para las ruedas POE. En el momento de la creación, la mayoría de las ruedas añadirán manejadores de eventos anónimos a la sesión activa actual. En otras palabras, la sesión que creó la rueda se modifica para manejar nuevos eventos. También se pueden inicializar observadores de eventos según sea necesario para activar los nuevos manejadores. Estos observadores de eventos también son propiedad de la sesión que creó la rueda.

Las sesiones no deben exponer sus ruedas a otras sesiones. Hacerlo probablemente cause problemas ya que las ruedas están estrechamente integradas con las sesiones que las crearon. Por ejemplo, llamar a put() en una instancia de POE::Wheel::ReadWrite puede habilitar un observador de escritura-permitida. El manejador para este observador ya está definido en el propietario de la rueda. Llamar a put() fuera de esa sesión habilitará el observador de escritura-permitida en la sesión incorrecta, y el evento nunca será manejado.

Del mismo modo, las ruedas deben destruirse desde dentro de sus sesiones creadoras. De lo contrario, ocurrirán fallos cuando los métodos DESTROY de las ruedas intenten desregistrar manejadores y observadores de eventos de las sesiones incorrectas. Para simplificar las cosas, se recomienda almacenar instancias de POE::Wheel en los heaps de las sesiones que las crearon.

Por ejemplo, crear un objeto POE::Wheel::FollowTail registrará un manejador de eventos que sondea periódicamente un archivo en busca de nueva información. También iniciará el temporizador que activa el sondeo periódico.

use POE;
use POE::Wheel::FollowTail;
my @files_to_tail = qw( messages maillog security );
foreach my $filename (@files_to_tail) {
  POE::Session->create(
    inline_states => {
      _start => sub {
        push @{$_[HEAP]{messages}}, POE::Wheel::FollowTail->new(
          Filename   => "/var/log/$filename",
          InputEvent => "got_input",
        );
      },
      got_input => sub {
        print "$filename: $_[ARG0]\n";
      },
    }
  );
}
POE::Kernel->run();
exit;

Como se ilustra en el ejemplo anterior, es posible —a veces recomendable— crear más de una POE::Wheel de un tipo particular en la misma sesión. Una sesión con múltiples ruedas puede escalar mejor que sesiones separadas con una rueda cada una. En caso de duda, haga benchmarking.

A diferencia de los componentes (o el queso), las ruedas no son autónomas. Cada rueda debe ser creada por una sesión para registrar observadores y manejadores de eventos dentro de esa sesión. Las ruedas están así estrechamente acopladas a sus sesiones creadoras y no pueden ser pasadas a otras sesiones.

FILTROS, Y CONTROLADORES

Muchas ruedas realizan operaciones de transferencia de datos en filehandles (que, como probablemente sepa, incluyen sockets, pipes y casi cualquier otra cosa que pueda almacenar o transferir datos).

Para evitar el infierno de subclases, los objetos POE::Wheel pueden ser personalizados en el momento de la creación incluyendo otros objetos de los espacios de nombres POE::Filter y POE::Driver.

Filtros

Los "filtros" de POE implementan analizadores y serializadores de datos. Por ejemplo, POE::Filter::Line analiza flujos en registros separados por alguna cadena (la tradicional nueva línea de red por defecto). El filtro Line también añade separadores de registro a los datos que se envían.

POE::Filter::HTTPD es un ejemplo más complejo. Implementa un subconjunto del lado del servidor del protocolo HTTP. Los flujos de entrada se analizan en solicitudes HTTP y se envuelven en objetos HTTP::Request. El código del servidor envía objetos HTTP::Response al cliente, que se serializan para poder enviarlos a un socket.

La mayoría de las ruedas utilizan POE::Filter::Line por defecto.

Controladores

Los "controladores" de POE implementan estrategias para enviar datos a un filehandle y recibirlos de él. Una única clase POE::Wheel puede interactuar con archivos, pipes, sockets o dispositivos utilizando el controlador apropiado.

POE::Driver::SysRW es el único controlador que viene con POE. sysread() y syswrite() pueden manejar casi cualquier tipo de interacción de flujo, por lo que no ha habido mucha demanda para otro tipo de controlador.

MÉTODOS

POE::Wheel define una interfaz común que la mayoría de las subclases utilizan. Las subclases pueden implementar otros métodos, especialmente para ayudar a realizar sus tareas únicas. Si algo útil no está documentado aquí, consulte la subclase antes de implementar una característica.

Métodos Requeridos

Estos métodos son requeridos por todas las subclases.

new LOTS_OF_STUFF

new() instancia e inicializa un nuevo objeto wheel y lo devuelve. La nueva rueda continuará funcionando mientras exista, aunque otros métodos pueden alterar la forma en que funciona.

Parte de la construcción de cualquier rueda es el registro de manejadores de eventos anónimos para realizar tareas específicas de la rueda. También se inician observadores de eventos para activar los manejadores cuando ocurre actividad relevante.

Cada rueda tiene un propósito diferente y requiere diferentes parámetros de constructor, por lo que LOTS_OF_STUFF está documentado en cada subclase particular.

DESTROY

DESTROY es el Viejo Destructor de Objetos Perl. Cuando la última referencia fuerte de la rueda se libera, DESTROY activa la limpieza de la rueda. El objeto se elimina a sí mismo de la sesión que lo creó: Los observadores de eventos activos se detienen y los manejadores de eventos anónimos se desregistran.

event TIPO_DE_EVENTO, NOMBRE_DE_EVENTO [, TIPO_DE_EVENTO, NOMBRE_DE_EVENTO, ....]

event() cambia los eventos que emitirá una rueda. Sus parámetros son uno o más pares de TIPO_DE_EVENTO y NOMBRE_DE_EVENTO a emitir cuando ocurra cada tipo de evento. Si un NOMBRE_DE_EVENTO es indefinido, entonces la rueda dejará de emitir ese tipo de evento. O la rueda puede lanzar un error si el tipo de evento es requerido.

Los TIPO_DE_EVENTO difieren para cada rueda y corresponden a los parámetros del constructor que coinciden con /.*Event$/. Por ejemplo, POE::Wheel::ReadWrite puede emitir hasta cinco tipos diferentes de evento: InputEvent, ErrorEvent, FlushedEvent, HighEvent, LowEvent. El nombre de cada evento emitido puede cambiarse en tiempo de ejecución.

Este ejemplo cambia los eventos a emitir en nueva entrada y cuando se vacía la salida. Detiene la emisión de eventos por parte de la rueda cuando ocurren errores.

$wheel->event(
  InputEvent   => 'new_input_event',
  ErrorEvent   => undef,
  FlushedEvent => 'new_flushed_event',
);

Métodos de E/S

Las ruedas que realizan entrada y salida pueden implementar algunos o todos estos métodos. El método put() es una omisión común. Las ruedas que no realizan salida no tienen métodos put().

put REGISTRO [, REGISTRO [, ....]]

put() envía uno o más REGISTROS a la rueda para su transmisión. Cada REGISTRO es serializado por el POE::Filter asociado de la rueda para que esté listo para transmitir. El flujo serializado puede ser transmitido inmediatamente por el objeto POE::Driver de la rueda, o puede ser almacenado en búfer en el POE::Driver hasta que pueda ser vaciado al filehandle de salida.

La mayoría de las ruedas utilizan POE::Filter::Line y POE::Driver::SysRW por defecto, por lo que no es necesario especificarlos en la mayoría de los casos.

Funciones Estáticas de Clase

Estas funciones exponen información común a todas las ruedas. No son métodos, por lo que **no** deben ser llamadas como métodos.

my $new_wheel_id = POE::Wheel::allocate_wheel_id();
POE::Wheel::free_wheel_id($new_wheel_id);

allocate_wheel_id

**No es un método de clase.**

Cada rueda tiene un ID único. allocate_wheel_id() devuelve el siguiente ID de rueda único disponible. Los constructores de ruedas lo usan para establecer sus IDs internamente.

package POE::Wheel::Example;
use base qw(POE::Wheel);
sub new {
  # ... entre otras cosas ...
  $self->[MY_WHEEL_ID] = POE::Wheel::allocate_wheel_id();
  return $self;
}

NAME

POE::Wheel - A base class for objects that handle I/O and other long-running tasks.

SYNOPSIS

  package POE::Wheel::MyWheel;
  use base qw(POE::Wheel);
  # ... wheel-specific methods ...
  sub new {
    my ($class, %args) = @_;
    my $self = $class->SUPER::new(%args);
    # ... initialize wheel ...
    return $self;
  }

DESCRIPTION

POE::Wheel is a base class for objects that handle I/O and other long-running tasks. Wheels are POE's primary mechanism for dealing with things that cannot be handled by simple event callbacks.

Wheels are designed to be subclassed. The base POE::Wheel class provides the core functionality for managing wheel IDs and basic event dispatch. Subclasses will typically implement methods to interact with specific I/O sources, such as files, sockets, or external processes.

When an event is generated by a wheel, it is sent to the POE kernel. The kernel then dispatches the event to the appropriate session. The event will contain a reference to the wheel that generated it, allowing the session to handle the event accordingly.

Wheels can be thought of as persistent objects that encapsulate resources and provide an interface for interacting with them in a non-blocking manner. They are essential for building complex POE applications that require interaction with the outside world.

FILTERS, AND DRIVERS

Wheels often use POE::Filter and POE::Driver objects to handle data parsing and low-level I/O, respectively. This separation of concerns allows wheels to focus on managing the lifecycle of the I/O resource, while filters and drivers handle the specifics of data transformation and communication.

For example, a POE::Wheel::ReadWrite might use a POE::Filter::Line to parse incoming data into lines, and a POE::Driver::Socket to handle the actual network communication.

METHODS

POE::Wheel provides several methods for managing wheel IDs and state.

wheel_id

This is a class method.

wheel_id() returns the next available wheel ID. This ID is guaranteed to be unique among all currently active wheels. It is often used to tag events generated by the wheel, allowing receiving sessions to identify the source of the event.

  package POE::Wheel::Example;
  use base qw(POE::Wheel);
  sub _create {
    my ($class, %args) = @_;
    my $wheel_id = $class->wheel_id;
    # ... use $wheel_id to store state ...
    return $wheel_id;
  }

Wheel IDs are automatically allocated when a new wheel is created and automatically freed when the wheel is destroyed. However, if a wheel object is manually destroyed or its state is otherwise discarded, its ID must be explicitly freed using free_wheel_id() to prevent memory leaks and ID collisions.

Wheel IDs are often used to store wheel-local state in a session's heap.

sub handle_error {
  my $wheel_id = $_[ARG3];
  print "Wheel $wheel_id caught an error.  Shutting it down.\n";
  delete $_[HEAP]{wheels}{$wheel_id};
}

It is vital for wheels to free their allocated IDs when they are destroyed. POE::Wheel class keeps track of allocated wheel IDs to avoid collisions, and they will remain in memory until freed. See free_wheel_id().

free_wheel_id WHEEL_ID

This is not a class method.

free_wheel_id() deallocates a wheel's ID so that it stops consuming memory and may be reused later. This is often called from a wheel's destructor.

package POE::Wheel::Example;
use base qw(POE::Wheel);
sub DESTROY {
  my $self = shift;
  # ... among other things ...
  POE::Wheel::free_wheel_id($self->[MY_WHEEL_ID]);
}

Wheel IDs may be reused, although it has never been reported. Two active wheels will never share the same ID, however.

ID

This is usually implemented in the subclass!

The ID() method returns a wheel's unique ID. It is commonly used to match events with the wheels which generated them.

Again, this method is not implemented in this class! If it's missing from the subclass, please go pester that module author---thanks!
