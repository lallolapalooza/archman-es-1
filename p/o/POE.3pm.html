POE(3pm) Documentación de Perl aportada por el usuario POE(3pm)

NOMBRE

POE - framework de multitarea y redes portátil para cualquier bucle de eventos

SINOPSIS

#!/usr/bin/perl
use warnings;
use strict;
use POE;  # Incluye automáticamente POE::Kernel y POE::Session.
sub handler_start {
  my ($kernel, $heap, $session) = @_[KERNEL, HEAP, SESSION];
  print "La sesión ", $session->ID, " ha comenzado.\n";
  $heap->{count} = 0;
  $kernel->yield('increment');
}
sub handler_increment {
  my ($kernel, $heap, $session) = @_[KERNEL, HEAP, SESSION];
  print "La sesión ", $session->ID, " contó hasta ", ++$heap->{count}, ".\n";
  $kernel->yield('increment') if $heap->{count} < 10;
}
sub handler_stop {
  print "La sesión ", $_[SESSION]->ID, " se ha detenido.\n";
}
for (1..10) {
  POE::Session->create(
    inline_states => {
      _start    => \&handler_start,
      increment => \&handler_increment,
      _stop     => \&handler_stop,
    }
  );
}
POE::Kernel->run();
exit;

DESCRIPCIÓN

POE es un framework para multitarea cooperativa impulsada por eventos y redes en Perl. Otros lenguajes tienen frameworks similares. Python tiene Twisted. TCL tiene "el bucle de eventos".

POE proporciona una interfaz unificada para varios bucles de eventos, incluidos select(), IO::Poll, Glib, Gtk, Tk, Wx y Gtk2. Muchas de estas interfaces de bucle de eventos fueron escritas por otros, con la ayuda de POE::Test::Loops. Se pueden encontrar en CPAN.

POE logra su alto grado de portabilidad a diferentes sistemas operativos y versiones de Perl al estar escrito completamente en Perl. CPAN aloja módulos XS opcionales para POE si la velocidad es más deseable que la portabilidad.

POE está diseñado en capas. Cada capa se construye sobre las inferiores. Los programas son libres de usar POE en cualquier nivel de abstracción, y diferentes niveles pueden combinarse sin problemas dentro de un mismo programa. Recuerda, sin embargo, que las abstracciones de nivel superior a menudo requieren más recursos que las de nivel inferior. Las conveniencias que proporcionan no son gratuitas.

Las capas de abstracción incluidas en POE son la punta de un iceberg en crecimiento. Sprocket, POE::Stage y otras distribuciones de CPAN se basan en este trabajo. Te animamos a que explores.

Sin importar cuán alto subas, todo se reduce a llamadas a POE::Kernel. Así, tu código práctico puede cooperar fácilmente con sistemas estratosféricos.

Capa 1: Kernel y Sesiones

La capa pública más baja está compuesta por POE::Kernel, POE::Session y otros tipos de sesiones.

POE::Kernel hace la mayor parte del trabajo pesado. Proporciona una interfaz portátil para la detección de actividad de manejadores de archivos, múltiples alarmas y otros temporizadores, manejo de señales y otras características menos comunes.

POE::Session y las clases derivadas encapsulan la noción de una tarea impulsada por eventos. También personalizan la distribución de eventos a una convención de llamada particular. POE::NFA, por ejemplo, es más una máquina de estados adecuada. CPAN tiene varios otros tipos de sesiones.

Todo se basa en última instancia en estas clases o en los conceptos que implementan. Si tienes poco tiempo, lo que debes leer además de esto son POE::Kernel y POE::Session.

Capa 2: Ruedas, Filtros y Controladores

Los objetos POE::Wheel son mezclas dinámicas para instancias de POE::Session. Estas "ruedas" realizan tareas muy comunes y genéricas de manera altamente reutilizable y personalizable. POE::Wheel::ReadWrite, por ejemplo, implementa E/S con búfer no bloqueante. Casi todos necesitan esto, entonces, ¿por qué requerir que las personas lo reinventen todo el tiempo?

Los objetos POE::Filter personalizan las ruedas de manera modular. Los filtros actúan como capas de E/S, convirtiendo flujos crudos en datos estructurados y serializando estructuras en algo adecuado para flujos. CPAN también tiene varios de estos.

Los controladores son donde las ruedas se encuentran con el camino. En este caso, el camino es algún tipo de manejador de archivos. Los controladores realizan la lectura y escritura real de manera estándar para que las ruedas no necesiten saber la diferencia entre send() y syswrite().

Los objetos POE::Driver reciben relativamente poca atención porque se necesitan muy pocos. El controlador más común, POE::Driver::SysRW, es ubicuito y también el predeterminado, por lo que la mayoría de las personas nunca necesitarán especificar uno.

Capa 3: Componentes

Las clases POE::Component son esencialmente clases Perl que utilizan POE para realizar tareas de manera no bloqueante o cooperativa. Esta es una definición muy amplia, y los componentes de POE están en todo el mapa de abstracción.

Muchos componentes, como POE::Component::Server::SMTP, encapsulan los detalles genéricos de una aplicación completa. Otros realizan tareas bastante estrechas, como POE::Component::DirWatch::Object.

Los componentes de POE son a menudo objetos Perl simples. POE::Component::DirWatch::Object, mencionado anteriormente, utiliza Moose. Otros frameworks de objetos y metaobjetos son compatibles.

También de interés es POE::Component::Generic, que te permite crear un componente POE a partir de casi cualquier módulo bloqueante.

Hay bastantes componentes en CPAN. <http://search.cpan.org/search?query=poe+component&mode=all>

Capa 4 y Superiores: Frameworks y Metáforas de Objetos

Es posible abstraer POE completamente detrás de un framework diferente. De hecho, animamos a la gente a escribir abstracciones específicas del dominio que oculten completamente POE si es necesario. Lo bueno aquí es que incluso en estos altos niveles de abstracción, las cosas continuarán interoperando hasta la capa 1.

Dos ejemplos de abstracción ultra-alto nivel son Sprocket, un framework de redes que hace lo suyo, y POE::Stage, que es el intento del creador de POE de formalizar y estandarizar los componentes de POE.

También es posible comunicarse entre procesos POE. Esto se llama IKC, de *Inter-Kernel Communication* (Comunicación Inter-Kernel). Hay algunos componentes IKC en CPAN (<http://search.cpan.org/search?query=IKC&mode=all>), notablemente POE::Component::IKC y POE::TIKC.

Capa 0: Internos de POE

La arquitectura en capas de POE continúa bajo la superficie. Las entrañas de POE se dividen en clases POE::Loop específicas para cada bucle de eventos que soporta. Los internos se dividen por tipo, dando clases POE::Resource para Alias, Controles, Eventos, Extrefs, FileHandles, SIDs, Sesiones y Señales.

Las APIs de POE::Kernel son extensibles a través de clases de mezcla POE::API. Algunos valientes incluso han publicado nuevas APIs en CPAN, como POE::API::Peek (que te da acceso a algunos de los métodos internos de POE::Resource).

Por diseño, es posible implementar nuevas entrañas de POE::Kernel creando otra clase POE::Resource. Luego, se puede exponer la funcionalidad con una nueva mezcla POE::API.

Introducción

POE es una biblioteca de Perl que facilita la creación de aplicaciones de red de alto rendimiento con un modelo de programación orientado a eventos. Es una alternativa más ligera y más simple a otros enfoques, como los servidores de subprocesos que tienen que tener en cuenta la concurrencia y la gestión de otros detalles. Las aplicaciones de POE suelen ser más fáciles de escribir, mantener y depurar.

POE está diseñado para ser lo más sencillo posible. La idea principal es que sus aplicaciones de POE se basan en una única instancia del objeto POE::Kernel. Este objeto se ejecuta en un bucle, esperando a que ocurran eventos. Cuando ocurre un evento, el kernel llama a una rutina de gestión de eventos apropiada para la sesión que lo generó.

Este documento es un recorrido rápido por las principales bibliotecas de POE. Si recién está comenzando con POE, podría ser un buen lugar para comenzar. Sin embargo, si tiene experiencia previa con el desarrollo de aplicaciones de red, es posible que se sienta más cómodo yendo directamente a las secciones de Referencia.

Conceptos Básicos

Las aplicaciones de POE se construyen a partir de POE::Kernel, un objeto POE::Session y uno o más objetos POE::State. Una POE::Session es una colección de POE::State que gestionan eventos. Los POE::State son simplemente punteros a subrutinas de Perl. El kernel llama a estos punteros a subrutinas cuando ocurren eventos.

POE::Kernel se encarga de la mayor parte del trabajo pesado. Crea sesiones, les pasa eventos y se asegura de que los programas no se bloqueen. Es la columna vertebral de POE.

Una POE::Session es el objeto principal de su aplicación POE. Cada sesión tiene un número de estado y un estado actual. El estado actual de una sesión es el POE::State que está gestionando eventos para ella. Cuando ocurre un evento, el kernel llama al POE::State actual de la sesión para manejarlo.

Un POE::State es simplemente un puntero a una subrutina de Perl. Es el código que realmente maneja los eventos. Cuando ocurre un evento, el kernel llama al POE::State actual de la sesión para manejarlo.

Los POE::Wheel son objetos que le permiten ejecutar código en un proceso separado. Son útiles para realizar operaciones de larga duración que no deben bloquear el bucle principal de eventos.

Los POE::Driver son objetos que le permiten interactuar con dispositivos de entrada/salida, como archivos, sockets o tuberías. Se encargan de las complejidades de las operaciones de E/S, permitiéndole centrarse en la lógica de su aplicación.

Los POE::Filter son objetos que puede utilizar para transformar los datos que entran y salen de un controlador o rueda. Por ejemplo, podría usar un filtro para cifrar o descifrar datos, o para comprimirlos y descomprimirlos.

Los POE::Component son colecciones de sesiones y estados relacionados. Son útiles para organizar aplicaciones POE complejas en partes manejables.

Bibliotecas de Nivel Superior

POE es una biblioteca grande con muchas partes móviles. Si bien el objetivo es que cada biblioteca sea fácil de entender, puede ser difícil saber por dónde empezar. Las siguientes secciones desglosan las bibliotecas principales y explican sus funciones.

POE::Kernel es el corazón de POE. Aquí es donde se ejecuta el bucle de eventos y donde se despachan los eventos. Es una buena idea al menos familiarizarse con él, ya que es la base de todas las aplicaciones POE.

POE::Session es un objeto que representa una sesión en el kernel. Las sesiones se utilizan para organizar el código en unidades manejables. Cada sesión tiene un número de estado y un puntero a la subrutina que se llamará cuando ocurra un evento.

POE::State es un objeto que representa un estado en una sesión. Los estados se utilizan para gestionar eventos. Un estado es simplemente un puntero a una subrutina de Perl. Cuando ocurre un evento, el kernel llama al estado actual de la sesión para manejarlo.

POE::Wheel es un objeto que le permite ejecutar código en un proceso separado. Son útiles para realizar operaciones de larga duración que no deben bloquear el bucle principal de eventos.

POE::Driver es un objeto que le permite interactuar con dispositivos de entrada/salida, como archivos, sockets o tuberías. Se encargan de las complejidades de las operaciones de E/S, permitiéndole centrarse en la lógica de su aplicación.

POE::Filter es un objeto que puede utilizar para transformar los datos que entran y salen de un controlador o rueda. Por ejemplo, podría usar un filtro para cifrar o descifrar datos, o para comprimirlos y descomprimirlos.

POE::Component es una colección de sesiones y estados relacionados. Son útiles para organizar aplicaciones POE complejas en partes manejables.

POE::Loop, POE::Alarm, y POE::Signal ofrecen formas de gestionar el tiempo y las señales. La mayoría de los programas no necesitan hacer uso de ellos directamente, ya que son utilizados por el kernel para gestionar el tiempo y las señales por sí mismo.

Las clases de documentación como POE::Docs y POE::Tutorial son útiles para aprender POE. Le guiarán a través de los conceptos básicos y le mostrarán cómo escribir sus propias aplicaciones POE.

Otras bibliotecas, como POE::Test, se utilizan para probar las aplicaciones POE. No necesita preocuparse por ellas a menos que esté escribiendo pruebas para sus propias aplicaciones.

Finalmente, POE::Exception y otras clases relacionadas se utilizan para el manejo de excepciones. Son útiles para asegurarse de que sus aplicaciones POE sean robustas y puedan recuperarse de los errores.

Clases Base Documento Características Comunes

Las clases base POE::Wheel, POE::Driver, POE::Filter y POE::Component describen lo que es común entre cada clase. Es una buena idea al menos hojear la documentación de la clase base, ya que las subclases tienden a no repetir las cosas comunes.

POE::Queue, POE::Resource y POE::Loop documentan los conceptos y, a veces, las interfaces estándar detrás de múltiples subclases. Se le anima a echar un vistazo.

Clases Auxiliares

POE incluye algunas clases auxiliares para la portabilidad. POE::Pipe y sus subclases POE::Pipe::OneWay y POE::Pipe::TwoWay son tuberías portátiles.

Puentes de Bucle de Eventos

POE::Loop documenta y especifica la interfaz para todos los puentes de bucle de eventos de POE. Las clases individuales pueden documentar detalles específicos, pero en general se adhieren a la especificación lo suficientemente fuerte como para no necesitarlo.

Muchos de los puentes POE::Loop existentes proporcionados en la distribución base de POE se trasladarán a distribuciones separadas en breve. Sin embargo, la documentación probablemente seguirá siendo la misma.

POE::Queue y POE::Queue::Array

La cola de eventos de POE es básicamente un montículo de prioridad implementado como un array ordenado. POE::Queue documenta la interfaz estándar para las colas de eventos de POE, y POE::Queue::Array implementa la cola de array ordenado. Tony Cook ha lanzado POE::XS::Queue::Array, que es un reemplazo de C "plug and play" para POE::Queue::Array. Podría intentarlo si necesita más rendimiento. La cola de eventos de POE es parte del código más rápido del sistema.

REQUISITOS DEL SISTEMA

Los requisitos básicos de POE son bastante ligeros. La mayoría están incluidos en las versiones modernas de Perl, y el resto (si los hay) deberían ser generalmente portátiles a estas alturas.

Se recomienda encarecidamente Time::HiRes, incluso para versiones antiguas de Perl que no lo incluyen. POE funcionará sin él, pero las alarmas y otras funciones serán mucho más precisas si se incluye. POE::Kernel utilizará Time::HiRes automáticamente si está disponible.

POE::Filter::Reference necesita un módulo para serializar datos para transportarlos a través de una red. Utilizará Storable, FreezeThaw, YAML o algún otro paquete con métodos freeze() y thaw(). También puede usar Compress::Zlib para conservar el ancho de banda y reducir la latencia en enlaces lentos, pero no es obligatorio.

Si desea escribir servidores web, necesitará instalar libwww-perl, que requiere libnet. Este es un pequeño mundo de módulos que incluye HTTP::Status, HTTP::Request, HTTP::Date y HTTP::Response. En general, son buenos de tener, y las versiones modernas de Perl incluso los incluyen.

Los programas que utilizan POE::Wheel::Curses, por supuesto, requerirán el módulo Curses, que a su vez requiere algún tipo de biblioteca Curses.

Si está utilizando POE con Tk, necesitará tener Tk instalado.

Y otras cosas obvias. Háganos saber si hemos pasado por alto algún detalle no obvio.

PROBLEMAS DE COMPATIBILIDAD

Uno de los objetivos de diseño de POE es ser lo más portable posible. Por eso está escrito en "Plain Perl". Las versiones XS de los módulos POE están disponibles como distribuciones de terceros. Las partes de POE que requieren bibliotecas no estándar son opcionales, y no tener esas bibliotecas no debería impedir la instalación de POE.

A pesar de los esfuerzos de Chris Williams, no podemos probar POE en todas partes. Por favor, consulte la sección OBTENER AYUDA si encuentra un problema.

Se espera que POE funcione en la mayoría de las formas de UNIX, incluyendo FreeBSD, MacOS X, Linux, Solaris. Quizás incluso AIX y QNX, pero no estamos seguros.

POE también se prueba en Windows XP, utilizando la última versión de ActiveState, Strawberry y Cygwin Perl. POE es totalmente compatible con Strawberry Perl, ya que está incluido en la distribución de Strawberry.

Se ha informado que OS/2 y MacOS 9 funcionaron en el pasado, pero parece que ya nadie está probando allí. Todavía se aceptan informes y parches.

Las versiones anteriores de POE se han probado con versiones de Perl desde 5.6.2 hasta "blead", la versión de desarrollo actual. Ya no podemos garantizar que cada versión funcione en todas partes, pero estaremos encantados de trabajar con usted si necesita soporte especial para un sistema realmente antiguo. Siempre puede usar versiones anteriores de POE que funcionen en su versión, consulte BackPAN http://backpan.perl.org/authors/id/R/RC/RCAPUTO/.

La calidad de POE se debe en gran medida al excelente trabajo de Chris Williams y los otros probadores de CPAN. Han dedicado recursos para garantizar que las distribuciones de CPAN superen sus propias pruebas, y seguimos sus informes religiosamente. Usted también puede hacerlo. Los últimos informes de pruebas de POE se pueden encontrar en http://cpantesters.org/distro/P/POE.html.

También agradecemos a Benjamin Smith y al Google Summer of Code de 2006. Ben recibió una subvención para mejorar el conjunto de pruebas de POE, lo cual hizo de manera admirable.

Problemas de Windows

POE parece funcionar muy bien con Perl compilado para Cygwin. Si debe usar ActiveState Perl, utilice la versión más reciente. La compatibilidad de ActiveState Perl fluctúa de una compilación a otra, por lo que tendemos a no dar soporte a versiones anteriores.

Windows y ActiveState Perl se consideran una plataforma esotérica debido a las complejas interacciones entre varias versiones. Por lo tanto, POE se basa en la retroalimentación y el soporte del usuario aquí.

Varias personas han ayudado a llevar el soporte de Windows de POE hasta este punto, a través de contribuciones de tiempo, parches y otros recursos. Algunos de ellos son: Sean Puckett, Douglas Couch, Andrew Chen, Uhlarik Ondoej, Nick Williams y Chris Williams (sin parentesco).

NAME

POE - Perl Object Environment

SYNOPSIS

use POE;

my $heap = POE::Kernel->run;

DESCRIPTION

POE (Perl Object Environment) is an event-driven, object-oriented framework for writing highly concurrent, network-enabled, and multi-threaded applications in Perl.

It provides a robust and flexible platform for building complex applications by managing event loops, tasks, and inter-process communication.

DOCUMENTATION ROADMAP

The POE documentation is organized into several sections:

  • Core Modules: Modules that form the foundation of POE, including POE::Kernel, POE::Session, POE::Component, and POE::Loop.

  • Utilities: Helper modules for common tasks, such as POE::Queue, POE::Driver, and POE::Filter.

  • Components: Pre-built components for network services (e.g., HTTP, IRC, SMTP), databases, and other functionalities.

  • Cookbook: Practical examples and tutorials demonstrating how to use POE for various application types.

Refer to the POD (Plain Old Documentation) for each module for detailed information.

SYSTEM REQUIREMENTS

POE requires a working Perl installation (version 5.8 or later is recommended). Some components may have additional dependencies.

COMPATIBILITY ISSUES

While POE aims for broad compatibility, specific components or older versions might have platform-specific issues. Always check the documentation for the specific modules you are using.

GETTING HELP

The POE community is available through several channels:

  • Mailing List: The primary forum for discussion and support.

  • IRC: Real-time chat and assistance.

  • Bug Tracker: For reporting issues and tracking development.

Details can be found on the POE website.
