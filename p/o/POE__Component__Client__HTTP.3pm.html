NOMBRE

POE::Component::Client::HTTP - un componente de agente de usuario HTTP

VERSIÓN

versión 0.949

SINOPSIS

use POE qw(Component::Client::HTTP);
POE::Component::Client::HTTP->spawn(
  Agente     => 'SpiffCrawler/0.90',   # por defecto es algo largo
  Alias     => 'ua',                  # por defecto es 'weeble'
  De         => 'spiffster@perl.org',  # por defecto es undef (sin cabecera)
  Protocol  => 'HTTP/0.9',            # por defecto es 'HTTP/1.1'
  Timeout   => 60,                    # por defecto es 180 segundos
  MaxSize   => 16384,                 # por defecto es toda la respuesta
  Streaming => 4096,                  # por defecto es 0 (desactivado)
  FollowRedirects => 2,               # por defecto es 0 (desactivado)
  Proxy     => "http://localhost:80", # por defecto es variable HTTP_PROXY
  NoProxy   => [ "localhost", "127.0.0.1" ], # por defecto es NO_PROXY
  BindAddr  => "12.34.56.78",         # por defecto es INADDR_ANY
);
$kernel->post(
  'ua',        # envía a 'ua'
  'request',   # envía a estado 'request' de 'ua'
  'response',  # cual estado recibirá la respuesta
  $request,    # objeto HTTP::Request
);
# Este es el sub que se llama cuando el sesión recibe un evento 'response'.
sub response_handler {
  my ($request_packet, $response_packet) = @_[ARG0, ARG1];
  # HTTP::Request
  my $request_object  = $request_packet->[0];
  # HTTP::Response
  my $response_object = $response_packet->[0];
  my $stream_chunk;
  if (! defined($response_object->content)) {
    $stream_chunk = $response_packet->[1];
  }
  print(
    "*" x 78, "\n",
    "*** mi solicitud:\n",
    "-" x 78, "\n",
    $request_object->as_string(),
    "*" x 78, "\n",
    "*** su respuesta:\n",
    "-" x 78, "\n",
    $response_object->as_string(),
  );
  if (defined $stream_chunk) {
    print "-" x 40, "\n", $stream_chunk, "\n";
  }
  print "*" x 78, "\n";
}

DESCRIPCIÓN

POE::Component::Client::HTTP es un componente de agente de usuario HTTP para POE. Permite que otras sesiones ejecuten mientras se procesan transacciones HTTP y permite procesar varias transacciones HTTP en paralelo.

Soporta keep-alive mediante POE::Component::Client::Keepalive, que a su vez utiliza POE::Component::Resolver para resolución asincrónica de direcciones IP IPv4 y IPv6.

Los componentes de cliente HTTP no son objetos propios. En lugar de ser creados, se spawn como sesiones separadas. Para evitar la confusión (y esperar que no cause otra confusión), deben ser spawn con el método "spawn", no creado con "new").

CONSTRUCTOR

spawn

El método "spawn" de PoCo::Client::HTTP toma varios parámetros nombrados:

Agente => $cadena_agente_usuario
Agente => \@lista_de_agentes
Si no hay cabecera de UserAgent en el HTTP::Request, se usará un agente aleatorio de los especificados por el parámetro "Agente". Si no se especifican, POE::Component::Client::HTTP advertirá su presencia al servidor.
Alias => $alias_sesión
"Alias" establece el nombre por el cual se conoce la sesión. Si no se especifica un alias, el componente usa por defecto el nombre "weeble". El alias permite que varias sesiones interactúen con componentes de HTTP sin mantener (o incluso conocer) referencias hard a ellos. Es posible spawn múltiples componentes de HTTP con nombres diferentes.
ConnectionManager => $poco_client_keepalive
"ConnectionManager" establece el gestor de pool de conexiones de este componente. Espera que el gestor de conexión sea un objeto de POE::Component::Client::Keepalive. El componente de cliente HTTP llamará a allocate() en el gestor de conexión mismo, por lo que no debe haber hecho esto ya.
CookieJar => $jar_de_cookies
"CookieJar" establece el jar de cookies del componente. Espera que el jar sea un objeto de HTTP::Cookies.
From => $dirección_administrador
"From" contiene un correo electrónico donde se pueda llegar al administrador y/o mantenidor del cliente. Por defecto es undef, lo que significa que no se incluirá la cabecera From en solicitudes.
MaxSize => OCTETOS
"MaxSize" especifica el tamaño máximo de respuesta que puede aceptar del servidor. El contenido de respuestas más grandes se truncará a OCTETOS octetos. Este ha sido utilizado para devolver la sección <head></head> de páginas web sin tener que navegar por <body></body>.
NoProxy => [ $host_1, $host_2, ..., $host_N ]
NoProxy => "host1,host2,hostN"
"NoProxy" especifica un listado de hosts del servidor que no serán proxyeados. Es útil para hosts locales y hosts que no soportan proxying correctamente. Si NoProxy no se especifica, se tomará un listado de hosts de la variable de entorno NO_PROXY.
BindAddr => $ip_local
Indica "BindAddr" para que todas las sockets de cliente estén vinculadas a una dirección local específica. El valor de BindAddr será pasado a POE::Component::Client::Keepalive para POE::Wheel::SocketFactory (como "bind_address"). Ver la documentación de ese módulo para detalles de implementación.
Protocol => $cadena_protocolo_http
"Protocol" indica el protocolo que el cliente desea ver. Normalmente, se deja a su valor por defecto: "HTTP/1.1".
Proxy => [ $host_proxy, $puerto_proxy ]
Proxy => $url_proxy
Proxy => $url_proxy,$url_proxy,...
"Proxy" especifica uno o más hosts de proxy a través de los cuales se pasarán las solicitudes. Si no se especifica, se tomarán servidores proxy de la variable de entorno HTTP_PROXY (o http_proxy). No se realizará proxying si se especifica Proxy o una de las variables de entorno.

El proxy puede especificarse como un host y puerto, o como una o más URLs. Las URLs de proxy deben especificar el puerto del proxy, incluso si es 80.

Proxy => [ "127.0.0.1", 80 ],
Proxy => "http://127.0.0.1:80/",

"Proxy" puede especificar múltiples proxies separados por comas. POE::Client::HTTP elegirá proxies de esta lista. El componente de cliente HTTP se comportará de acuerdo con esta lista.

Proxy => "http://127.0.0.1:80/,http://127.0.0.1:81/",
Streaming => OCTETS
"Streaming" Cambia permite que Client::HTTP devuelva contenido grande en fragmentos (de OCTETS octetos cada uno) en lugar de combinar todo el contenido en un único objeto HTTP::Response.

Por defecto, Client::HTTP lee todo el contenido de una respuesta en memoria antes de devolver un objeto HTTP::Response. Esto es obviamente malo para aplicaciones como clientes de streaming de MP3, porque a menudo obtienen canciones que nunca terminan. Sí, continúan y continúan, amigo mío.

Sin embargo, cuando "Streaming" se establece en un valor distinto de cero, el manejador de respuestas recibe fragmentos de hasta OCTETS octetos cada uno. El manejador de respuestas acepta parámetros ligeramente diferentes en este caso. ARG0 es también un objeto HTTP::Response pero no contiene contenido de respuesta, y ARG1 contiene un fragmento de contenido de respuesta crudo, o undef si el stream ha terminado.

sub streaming_response_handler {
  my $response_packet = $_[ARG1];
  my ($response, $data) = @$response_packet;
  print SAVED_STREAM $data if defined $data;
}
FollowRedirects => $number_of_hops_to_follow
"FollowRedirects" especifica cuántas redirecciones (por ejemplo, 302 Moved) seguir. Si no se especifica, el valor por defecto es 0, y por lo tanto no se sigue ninguna redirección. Esto mantiene la compatibilidad con el comportamiento anterior, que era no seguir las redirecciones en absoluto.

Si se siguen las redirecciones, se construirá una cadena de respuestas, y se podrá acceder a ella a través de $response_object->previous(). Ver HTTP::Response para más detalles.

Timeout => $query_timeout
"Timeout" establece cuánto tiempo POE::Component::Client::HTTP tiene para procesar una solicitud de la aplicación, en segundos. "Timeout" por defecto es 180 (tres minutos) si no se especifica.

Es importante notar que el tiempo de espera comienza cuando el componente recibe una solicitud de la aplicación, no cuando intenta conectarse al servidor web.

Los tiempos de espera pueden resultar de enviar demasiadas solicitudes al componente a la vez. Cada solicitud necesitaría ser recibida y seguida. Considere esto:

$_[KERNEL]->post(component => request => ...) for (1..15_000);

15.000 solicitudes se ponen en cola juntas en un único y enorme lote. El componente las recibiría e inicializaría en orden. La primera actividad del socket no llegaría hasta que la solicitud 15.000 fuera configurada. Si eso tomara más tiempo que "Timeout", entonces las solicitudes que han esperado demasiado fallarían.

"ConnectionManager"'s propio tiempo de espera y límites de concurrencia también afectan cuántas solicitudes pueden procesarse a la vez. Por ejemplo, la mayoría de las 15.000 solicitudes esperarían en el pool del gestor de conexiones hasta que los sockets estuvieran disponibles. Mientras tanto, el "Timeout" estaría contando hacia atrás.

Las aplicaciones pueden optar por controlar la concurrencia fuera del "Timeout" del componente. Pueden hacerlo de algunas maneras.

La forma más fácil es limitar el número inicial de solicitudes a algo más manejable. A medida que llegan las respuestas, la aplicación debe procesarlas e iniciar nuevas solicitudes. Esto limita la concurrencia al número de solicitudes iniciales.

Una aplicación también puede externalizar la limitación de trabajo a otro módulo, como POE::Component::JobQueue.

En cualquier caso, "Timeout" y "ConnectionManager" pueden ser ajustados para maximizar los tiempos de espera y los límites de concurrencia. Esto puede ayudar en algunos casos. Los desarrolladores deben ser conscientes de que hacerlo aumentará el uso de memoria. POE::Component::Client::HTTP y KeepAlive rastrean las solicitudes en memoria, mientras que las aplicaciones son libres de mantener las solicitudes pendientes en disco.

EVENTOS ACEPTADOS

Las sesiones se comunican asíncronamente con PoCo::Client::HTTP. Le envían solicitudes y él envía respuestas de vuelta.

request

Las solicitudes se envían al estado "request" del componente. Incluyen un objeto HTTP::Request que define la solicitud. Por ejemplo:

$kernel->post(
  'ua', 'request',            # alias de sesión http y estado
  'response',                 # mi estado para recibir respuestas
  GET('http://poe.perl.org'), # una solicitud http simple
  'unique id',                # una etiqueta para identificar la solicitud
  'progress',                 # un evento para indicar el progreso
  'http://1.2.3.4:80/'        # proxy a usar para esta solicitud
);

Las solicitudes incluyen el estado al que se enviarán las respuestas. En el ejemplo anterior, se llamará al manejador de un estado 'response' con cada respuesta HTTP. El parámetro "progress" es opcional y si se instala, el componente proporcionará métricas de progreso (ver manejador de ejemplo abajo). El parámetro "proxy" es opcional y si no se define, se utilizará un proxy por defecto si está configurado. No se utilizará ningún proxy si no se define ni uno por defecto ni un parámetro "proxy".

pending_requests_count

También hay un estado pending_requests_count que devuelve el número de solicitudes que se están procesando actualmente. Para recibir el valor de retorno, debe invocarse con $kernel->call().

my $count = $kernel->call('ua' => 'pending_requests_count');

NOTA: A veces el recuento podría no ser el que esperabas, porque las respuestas están actualmente en la cola de POE y aún no las has procesado. Esto podría suceder si configuras la concurrencia del "ConnectionManager" a un valor suficientemente alto.

cancel

Cancela una solicitud HTTP específica. Requiere una referencia a la solicitud original (bendecida o convertida a cadena) para que sepa cuál cancelar. Ver "progress handler" abajo para notas sobre la cancelación de solicitudes de streaming.

Para cancelar una solicitud basada en su objeto HTTP::Request bendecido:

$kernel->post( component => cancel => $http_request );

Para cancelar una solicitud basada en su objeto HTTP::Request convertido a cadena:

$kernel->post( component => cancel => "$http_request" );

shutdown

Responde a todas las solicitudes pendientes con 408 (tiempo de espera agotado de la solicitud), y luego cierra el componente y todos los subcomponentes.

EVENTOS ENVIADOS

response handler

Además de todos los parámetros habituales de POE, las respuestas HTTP vienen con dos referencias a listas:

my ($request_packet, $response_packet) = @_[ARG0, ARG1];

$request_packet contiene una referencia al objeto HTTP::Request original. Esto es útil para relacionar las respuestas con las solicitudes que las generaron.

my $http_request_object = $request_packet->[0];
my $http_request_tag    = $request_packet->[1]; # del post 'request'

$response_packet contiene una referencia al objeto HTTP::Response resultante.

my $http_response_object = $response_packet->[0];

Por favor, consulte las páginas de manual de HTTP::Request y HTTP::Response para más información.

progress handler

El manejador de progreso de ejemplo muestra cómo calcular un porcentaje de finalización de la descarga.

sub progress_handler {
  my $gen_args  = $_[ARG0];    # argumentos pasados a todas las llamadas
  my $call_args = $_[ARG1];    # argumentos específicos de la llamada
  my $req = $gen_args->[0];    # objeto HTTP::Request que se está atendiendo
  my $tag = $gen_args->[1];    # etiqueta de ID de solicitud de.
  my $got = $call_args->[0];   # número de bytes recuperados hasta ahora.
  my $tot = $call_args->[1];   # total de bytes a recuperar.
  my $oct = $call_args->[2];   # fragmento de octetos crudos recibidos esta vez.
  my $percent = $got / $tot * 100;
  printf(
    "-- %.0f%% [%d/%d]: %s\n", $percent, $got, $tot, $req->uri()
  );
  # Para cancelar la solicitud:
  # $_[KERNEL]->post( component => cancel => $req );
}

ADVERTENCIA DE DEPRECACIÓN

El tercer argumento de retorno (los octetos crudos recibidos) ha sido desaprobado. En lugar de él, use el parámetro Streaming para obtener fragmentos de contenido en el manejador de respuestas.

CALLBACKS DE SOLICITUD

El objeto HTTP::Request pasado al evento de solicitud puede contener una referencia a una FUNCIÓN como "content". Esto permite enviar archivos grandes sin desperdiciar memoria. Su callback debe devolver un fragmento de datos cada vez que se llama, y una cadena vacía cuando se termina. No olvide establecer la cabecera Content-Length correctamente. Ejemplo:

my $request = HTTP::Request->new( PUT => 'http://...' );
my $file = '/path/to/large_file';
open my $fh, '<', $file;
my $upload_cb = sub {
  if ( sysread $fh, my $buf, 4096 ) {
    return $buf;
  }
  else {
    close $fh;
    return '';
  }
};
$request->content_length( -s $file );
$request->content( $upload_cb );
$kernel->post( ua => request, 'response', $request );

CODIFICACIÓN Y COMPRESIÓN DE CONTENIDO

La decodificación transparente de contenido ha sido deshabilitada a partir de la versión 0.84. Esto también elimina el soporte para la solicitud y descompresión gzip transparentes.

Para volver a habilitar la compresión gzip, especifique la codificación de contenido gzip y use el método decoded_content() de HTTP::Response en lugar de content():

my $request = HTTP::Request->new(
  GET => "http://www.yahoo.com/", [
    'Accept-Encoding' => 'gzip'
  ]
);
# ... pasa el tiempo ...
my $content = $response->decoded_content();

CONTENIDO CODIFICADO Y COMPRESIÓN

El comportamiento anterior fue provocado por cambios en HTTP::Response que sacaron a la luz un error en el manejo transparente de gzip del componente.

Permitir que la aplicación especifique y maneje las codificaciones de contenido parece ser la resolución más confiable y flexible.

Para más información sobre el problema y discusiones relativas a la solución, ver: http://www.perlmonks.org/?node_id=683833 y http://rt.cpan.org/Ticket/Display.html?id=35538

CABECERAS DEL CLIENTE

POE::Component::Client::HTTP establece sus propias cabeceras de respuesta con información adicional. Todas sus cabeceras comienzan con "X-PCCH".

X-PCCH-Errmsg

POE::Component::Client::HTTP puede fallar debido a un error interno del cliente en lugar de un error del protocolo HTTP. X-PCCH-Errmsg contendrá una razón legible por humanos para fallos del cliente, si ocurren.

El texto de X-PCCH-Errmsg también puede repetirse en el contenido de la respuesta.

X-PCCH-Peer

X-PCCH-Peer contiene la dirección IPV4 remota y el puerto, separados por un punto. Por ejemplo, "127.0.0.1.8675" representa el puerto 8675 en localhost.

El proxy hará que X-PCCH-Peer sea casi inútil, ya que el socket se conectará a un proxy en lugar del servidor en sí.

Esta característica fue añadida a petición de Doreen Grey. Doreen quería un medio para encontrar la dirección del servidor remoto sin tener que hacer una solicitud adicional.

ENTORNO

POE::Component::Client::HTTP utiliza dos variables de entorno estándar: HTTP_PROXY y NO_PROXY.

HTTP_PROXY establece el servidor proxy a través del cual Client::HTTP reenviará las solicitudes. NO_PROXY establece una lista de hosts que no serán reenviados a través de un proxy.

Ver los parámetros del constructor Proxy y NoProxy para más información sobre estas variables.

VER TAMBIÉN

Este componente está construido sobre HTTP::Request, HTTP::Response, y POE. Por favor, consulte su código fuente y la documentación de sus módulos base para aprender más. Si desea utilizar cookies, también necesitará leer sobre HTTP::Cookies.

También vea el programa de pruebas, t/01_request.t, en la distribución PoCo::Client::HTTP.

ERRORES

No hay soporte para CGI_PROXY o CgiProxy.

El proxy de HTTP seguro (https) no es compatible en este momento.

No hay una interfaz orientada a objetos. Ver POE::Component::Client::Keepalive y POE::Component::Resolver para ejemplos de una interfaz OO decente.
