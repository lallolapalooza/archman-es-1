NOMBRE

POE::Loop - documentación de la interfaz del puente del bucle de eventos de POE

SINOPSIS

$kernel->loop_initialize();
$kernel->loop_finalize();
$kernel->loop_do_timeslice();
$kernel->loop_run();
$kernel->loop_halt();
$kernel->loop_watch_signal($signal_name);
$kernel->loop_ignore_signal($signal_name);
$kernel->loop_attach_uidestroy($gui_window);
$kernel->loop_resume_time_watcher($next_time);
$kernel->loop_reset_time_watcher($next_time);
$kernel->loop_pause_time_watcher();
$kernel->loop_watch_filehandle($handle, $mode);
$kernel->loop_ignore_filehandle($handle, $mode);
$kernel->loop_pause_filehandle($handle, $mode);
$kernel->loop_resume_filehandle($handle, $mode);

DESCRIPCIÓN

POE::Loop es una clase base virtual que define una interfaz estándar de bucle de eventos. Las subclases de POE::Loop se mezclan con POE::Kernel e implementan las funcionalidades necesarias para gestionar los bucles de eventos subyacentes de forma coherente. Esta documentación cubre la interfaz, que es compartida por todas las subclases.

A medida que POE::Kernel se carga, busca en %INC módulos de bucle de eventos. POE::Kernel carga la subclase de POE::Loop más adecuada para el bucle de eventos que encuentra. La subclase inserta sus métodos en POE::Kernel, completando la clase en tiempo de carga. POE y POE::Kernel proporcionan formas de indicar el bucle de eventos deseado en caso de que la autodetección cometa un error o el desarrollador prefiera ser explícito. Consulte "Usando POE con Otros Bucles de Eventos" en POE::Kernel para obtener instrucciones sobre cómo usar POE con otros bucles de eventos, convenciones de nomenclatura de bucles de eventos y otros detalles.

Existen subclases de POE::Loop para muchos de los bucles de eventos que soporta Perl: select(), IO::Poll, WxWindows, EV, Glib, Event, y así sucesivamente. Consulte CPAN para obtener una lista completa.

NOTAS GENERALES

Como se mencionó anteriormente, las subclases de POE::Loop proporcionan métodos adicionales a POE::Kernel y no son objetos en sí mismas.

Cada subclase de POE::Loop primero define su propio espacio de nombres y versión dentro de él. De esta manera, CPAN y otras herramientas pueden rastrear su versión. Luego cambian al paquete POE::Kernel para definir sus métodos adicionales.

POE::Loop está diseñado como una clase de mezcla (mix-in) porque Perl imponía una penalización de rendimiento por herencia de métodos en el momento en que se diseñó la clase. Esto podría cambiarse en el futuro, pero requerirá cambios en cascada en varias otras clases.

Aquí hay un esqueleto de una subclase de POE::Loop:

use strict;
# Tu puente de YourToolkit para POE::Kernel;
package POE::Loop::YourToolkit;
use vars qw($VERSION);
$VERSION = '1.000'; # NOTA - Debería ser #.### (tres decimales)
package POE::Kernel;
# Define datos léxicos privados aquí.
# Implementa la interfaz de POE::Loop aquí.
1;
__END__

INTERFAZ PÚBLICA

La interfaz pública de POE::Loop se divide en cuatro partes: métodos administrativos, métodos de manejo de señales, métodos de gestión del tiempo y métodos de observador de manejadores de archivos. Cada grupo y sus miembros se describirán en detalle en breve.

Las subclases de POE::Loop utilizan variables léxicas para hacer un seguimiento de las cosas. La implementación exacta queda a cargo del autor de la subclase. POE::Loop::Select mantiene sus vectores de bits para las llamadas a select() en variables léxicas con alcance de clase (estáticas). POE::Loop::Gtk rastrea un único observador de tiempo y varios observadores de archivos allí.

Los puentes a menudo emplean métodos privados como devoluciones de llamada desde sus bucles de eventos. Los puentes Event, Gtk y Tk hacen esto. Los nombres de las devoluciones de llamada privadas deben comenzar con "_loop_" para evitar colisiones con otros métodos.

Los desarrolladores deben examinar los puentes existentes para tener una idea de las cosas. El indicador "-m" para perldoc mostrará un módulo en su totalidad.

perldoc -m POE::Loop::Select
perldoc -m POE::Loop::Gtk
...

Métodos administrativos

Estos métodos inicializan y finalizan un bucle de eventos, ejecutan el bucle para procesar eventos y lo detienen.

loop_initialize

Inicializa el bucle de eventos. Los kits de herramientas gráficos, en particular, necesitan algún tipo de llamada o secuencia init() para configurarse. Por ejemplo, Tk requiere que se cree un widget antes de que se procesen los eventos, y la interfaz de usuario del programa se considerará destruida si se cierra ese widget.

sub loop_initialize {
  my $self = shift;
  $poe_main_window = Tk::MainWindow->new();
  die "no se pudo crear una ventana principal de Tk" unless defined $poe_main_window;
  $self->signal_ui_destroy($poe_main_window);
}

POE::Loop::Select inicializa sus vectores de bits de select().

sub loop_initialize {
  @loop_vectors = ( '', '', '' );
  vec($loop_vectors[MODE_RD], 0, 1) = 0;
  vec($loop_vectors[MODE_WR], 0, 1) = 0;
  vec($loop_vectors[MODE_EX], 0, 1) = 0;
}

loop_finalize

Finaliza el bucle de eventos. La mayoría de los bucles de eventos no requieren nada aquí ya que se han detenido antes de que se llame a loop_finalize(). Sin embargo, este es un buen lugar para verificar que un puente no ha filtrado memoria o datos. Este ejemplo proviene de POE::Loop::Event.

sub loop_finalize {
  my $self = shift;
  foreach my $fd (0..$#fileno_watcher) {
    next unless defined $fileno_watcher[$fd];
    foreach my $mode (MODE_RD, MODE_WR, MODE_EX) {
      POE::Kernel::_warn(
        "El observador del modo $mode para el fileno $fd está definido durante la finalización del bucle"
      ) if defined $fileno_watcher[$fd]->[$mode];
    }
  }
  $self->loop_ignore_all_signals();
}

loop_do_timeslice

Espera a que pase el tiempo o ocurran nuevos eventos, y despacha cualquier evento que venza. Si el bucle de eventos subyacente hace esto a través de devoluciones de llamada, entonces loop_do_timeslice() proporcionará una unión mínima o no hará nada.

Por ejemplo, loop_do_timeslice() para POE::Loop::Select configura y llama a select(). Si algún archivo u otros recursos se activan, pone en cola eventos para ellos. Finalmente, activa el despacho para cualquier evento que venza.

Por otro lado, el bucle de eventos Gtk maneja todo esto, por lo que loop_do_timeslice() está vacío para el puente Gtk.

No se presenta una implementación de ejemplo de loop_do_timeslice() aquí porque sería bastante grande o vacía. Vea cada POE::Loop::IO_Poll o Select para ver los grandes. Event y Gtk están vacíos.

Los puentes para Poll y Select son grandes. Los de Event y Gtk están vacíos, y el de Tk (en POE::Loop::TkCommon) es bastante pequeño.

loop_run

Ejecuta un bucle de eventos hasta que POE no tenga más sesiones a las que manejar eventos. Este método tiende a ser bastante pequeño y a menudo se implementa en términos de loop_do_timeslice(). Por ejemplo, POE::Loop::IO_Poll lo implementa:

sub loop_run {
  my $self = shift;
  while ($self->_data_ses_count()) {
    $self->loop_do_timeslice();
  }
}

Este método es aún más trivial cuando un bucle de eventos lo maneja. Esto es del puente Gtk:

sub loop_run {
  unless (defined $_watcher_timer) {
    $_watcher_timer = Gtk->idle_add(\&_loop_resume_timer);
  }
  Gtk->main;
}

loop_halt

loop_halt() hace lo que dice: detiene el bucle de eventos subyacente de POE. Tiende a ser trivial para bucles de eventos externos o vacío para aquellos que se implementan en el propio puente (IO_Poll, Select).

Por ejemplo, el método loop_run() en el puente Poll sale cuando se agotan las sesiones, por lo que su método loop_halt() está vacío:

sub loop_halt {
  # no hace nada
}

Gtk, sin embargo, necesita detenerse porque no sabe cuándo ha terminado POE.

sub loop_halt {
  Gtk->main_quit();
}

Métodos de gestión de señales

Estos métodos habilitan y deshabilitan los observadores de señales. Son utilizados por POE::Resource::Signals para gestionar los observadores de señales de un bucle de eventos.

La mayoría de los bucles de eventos utilizan el %SIG de Perl para observar señales. Esto es tan común que POE::Loop::PerlSignals implementa la interfaz en nombre de otras subclases.

loop_watch_signal NOMBRE_SEÑAL

Observa un NOMBRE_SEÑAL dado. NOMBRE_SEÑAL es la versión que se encuentra en %SIG, que tiende a ser el nombre de la señal del sistema al que se le ha quitado el prefijo "SIG".
