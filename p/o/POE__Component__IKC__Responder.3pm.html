NOMBRE

POE::Component::IKC::Responder - Manejador de estado para POE IKC

SINOPSIS

use POE;
use POE::Component::IKC::Responder;
create_ikc_responder();
...
$kernel->post('IKC', 'post', $to_state, $state);
$ikc->publish('my_name', [qw(state1 state2 state3)]);

DESCRIPCIÓN

Este módulo implementa el manejo de estado para POE IKC. El responde envía estados a kernels externos y llama a estados en el kernel local a la solicitud de kernels externos.

Hay dos interfaces para el responde. Una enviando estados a la sesión 'IKC' o a través de la interfaz de objeto. Aunque la segunda es más rápida, es preferible comportarse de forma cooperativa, ya que POE es un sistema cooperativo.

ESTADOS/MÉTODOS

"spawn"

POE::Component::IKC::Responder->spawn();

Esta función crea la sesión del responde y el objeto. Normalmente, POE::Component::IKC::Client o POE::Component::IKC::Server lo hacen por usted. Sin embargo, en algunas aplicaciones querrá asegurarse de que el responde esté activo antes de hacerlo.

"post"

Envía una solicitud de estado a un kernel externo. Devuelve un valor booleano indicando si el estado fue enviado y otro valor booleano si no pudo enviar la solicitud al kernel externo. Esto no significa necesariamente que el kernel externo haya podido publicar el estado, aunque así lo haga. Los parámetros son los siguientes:

"foreign_state"
Espejo para el estado del kernel externo. Véase POE::Component::IKC::Specifier.
"parameters"
Un puntero a cualquier cosa que desee que el estado externo reciba como ARG0. Si desea especificar varios parámetros, use una referencia a un array y deje que el estado externo los desreferencie. 
$kernel->post('IKC', 'post', 
    {kernel=>'Syslog', session=>'logger', state=>'log'},
    [$faculty, $priority, $message];

o

$ikc->post('poe://Syslog/logger/log', [$faculty, $priority, $message]);

Esto registraría un estado con un logger hipotético.

Véase el "PROXY SENDER" más abajo.

"call"

Esto es idéntico a "post", excepto que tiene un tercer parámetro que describe qué estado recibirá el valor de retorno del kernel externo.

$kernel->post('IKC', 'call', 
            'poe://Pulse/timeserver/time', '',
            'poe:get_time');

o

$ikc->call({kernel=>'Pulse', session=>'timeserver', state=>'time'},
            '', 'poe://me/get_time');

Esto solicita al kernel externo 'Pulse' la hora. El estado 'get_time' de la sesión actual se publicará con lo que devolvió el estado externo.

No tiene que publicar mensajes de retorno, ya que se publican temporalmente. ¿Cuánto temporal? Solo se pueden publicar desde un kernel externo una vez. Esto, por supuesto, es un problema porque alguien podría publicar antes del retorno. Así es la vida.

"foreign_state"
Idéntico al parámetro "post".
"parameters"
Idéntico al parámetro "post".
"rsvp"
Identificador de evento para el retorno. Es decir, este estado se llamará con el valor devuelto por el estado externo. Puede ser un espejo de "foreign_state" o simplemente el nombre de un estado en la sesión actual.
$kernel->call('IKC', 'post', 
    {kernel=>'e-comm', session=>'CC', state=>'check'},
    {CC=>$cc, expiry=>$expiry}, folder=>$holder},
    'is_valid');
# o
$ikc->call('poe://e-comm/CC/check',
    {CC=>$cc, expiry=>$expiry}, folder=>$holder},
    'poe://me/is_valid');

Esto solicita al servidor de e-comm que verifique si un número de tarjeta de crédito es "válido". Sí, esto probablemente sería un uso excesivo.

El estado "rsvp" no necesita ser publicado. IKC se encarga de registrar el estado "rsvp" y permite que el kernel externo publique en él.

Véase el "PROXY SENDER" más abajo.

"default"

Establece el kernel externo por defecto. Debe estar conectado al kernel externo primero.

El único parámetro es el nombre del kernel externo.

Devuelve un valor booleano en caso de éxito.

"register"

Registra nombres de kernels externos con el responde. Esto se realiza durante la fase de negociación de IKC y normalmente es gestionado por POE::Component::IKC::Channel. Definirá el kernel por defecto si no hay uno previo.

El primer parámetro es un nombre de kernel único. El segundo parámetro es una referencia a un array de alias de kernel para registrar.

"unregister"

Anula el registro de nombres de kernels externos con el responde. Esto se realiza cuando el kernel externo se desconecta por POE::Component::IKC::Channel. Si este es el kernel por defecto, ya no habrá un kernel por defecto.

El primer parámetro es un nombre de kernel o alias. El segundo parámetro es una referencia a un array de alias de kernel para anular el registro. El segundo parámetro es un poco redundante, porque si se anula el registro de un kernel remoto, todos sus alias también se anularán.

"register_local"

Registra nuevos alias locales con el responde. Esto se realiza internamente por POE::Component::IKC::Server y POE::Component::IKC::Client. No definirá el kernel por defecto.

El primer y único parámetro es una referencia a un array de alias de kernel para registrar.

"publish"

Indica a IKC que algunos estados de la sesión actual están disponibles para ser utilizados por sesiones externas.

"session"
Un alias de sesión por el cual las sesiones externas llamarán. El alias debe estar ya registrado con el kernel local.
"states"
Referencia a un array de estados que pueden ser publicados por sesiones externas. 
$kernel->post('IKC', 'publish', 'me', [qw(foo bar baz)]);
# o
$ikc->publish('me', [qw(foo bar baz)]);

"retract"

Indica a IKC que algunos estados ya no deben ser utilizados por sesiones externas. No es necesario desactivar todos los estados publicados.

"session"
Idéntico al parámetro "session" en "publish"
"states"
Idéntico al parámetro "states" en "publish". Si no se especifica, *todos* los estados publicados se retirarán. 
$kernel->post('IKC', 'retract', 'me', [qw(foo mibble dot)]);
# o
$ikc->retract('me', [qw(foo)]);

"published"

$list=$kernel->call(IKC=>'published', $session);

Devuelve una lista de todos los estados publicados.

$hash=$kernel->call(IKC=>'published');

Devuelve una referencia a un hash, con clave por IDs de sesión. Los valores son referencias a arrays de estados publicados por esa sesión.

"session"
Un alias de sesión para el que se desea la lista de estados.

"subscribe"

Suscríbete a sesiones o estados externos.

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

"unsubscribe"

Inverso de la metodología de suscripción. Sin embargo, no está bien documentada actualmente.

"ping"

Responde con 'PONG'. Es auto-publicado, por lo que puede llamarse desde kernels remotos para ver si el kernel local está aún activo. De hecho, no veo otra utilidad para esto.

$kernel->post('poe://remote/IKC', 'ping', 'some_state');
$kernel->delay('some_state', 60);   # timeout

sub some_state
{
    my($pong)=$_[ARG0];
    return if $pong;            # todo todo todo

    # YOW!  Kernel remoto se timeout.  RUN AROUND SCREAMING!
}

"shutdown"

Se espera que cause que IKC y todas las sesiones periféricas se desvanezcan en un chispazo de humo. En el peor de los casos, cualquier sesión restante será no relacionada con IKC o apenas respirará (es decir, solo tendrá alias para evitar la recolección de lucha).

"monitor"

Permite a una sesión monitorear el estado de kernels remotos. Actualmente, una sesión se informa cuando un kernel remoto se registra, desregistra, suscribe o desuscribe. Debe asegurarse de que el alias IKC exista antes de monitorear. Esto se puede hacer llamando a POE::Component::IKC::Responder->spawn o en un callback de on_connect.

$kernel->post('IKC', 'monitor', $remote_kernel_id, $states);
$remote_kernel_id
Nombre o alias o especificador de IKC del kernel remoto que deseas monitorear. También puedes especificar *&* para monitorear todos los kernels remotos. Si lo haces, tu monitoreo se llamará varias veces por un kernel dado. Esto es porque un kernel tiene un nombre único y múltiples alias. Por ejemplo, un kernel remoto tendrá un ID único dentro del kernel local, un nombre (pasado a o generado por create_ikc_{kernel,client}) y un ID global asignado por el kernel remoto mediante $kernel->ID. Esto sorprende a algunos, pero vea la nota corta después de la explicación de los parámetros de los callbacks.
$states
Un hashref que especifica qué callbacks se llaman cuando algo interesante ocurre. Si $state es vacío o undef, la sesión dejará de monitorear el kernel remoto dado.

Callback states

Los siguientes estados pueden ser monitoreados:

"channel"
Se llama cuando un canal se hace ready o sale. ARG3 es o bien "ready" o "close". ARG4 es el ID numérico de la sesión del canal. Véase "CHANNELS" a continuación.
"register"
Se llama cuando un kernel o alias es registrado. Esto es equivalente a cuando la fase de conexión está completada.
"unregister"
Se llama cuando un kernel o alias es desregistrado. Esto es equivalente a cuando el kernel remoto se desconecta.
"subscribe"
Se llama cuando IKC es exitoso en suscribirse a una sesión remota. ARG3 es un IKC::Specifier de lo que se suscribió. Usa este para publicar a la sesión proxy.
"unsubscribe"
Se llama cuando IKC es exitoso en desuscribirse de una sesión remota.
"shutdown"
Se informa cuando alguien intenta hacer un desenchufado sano de IKC y todas las sesiones periféricas. Esta se llama solo una vez, después de que alguien publique un evento IKC/shutdown.
"error"
Se informan errores en kernels locales y remotos. ARG3 es la operación que falló. ARG4 es el mensaje de error. Véase "ERRORS" a continuación.
"data"
Un poco de datos (puede ser escalar o referencia) que se pasa al callback. Esto permite más magia.

Los estados de callback se llaman con los siguientes parámetros:

"ARG0"
Nombre del kernel que se pasó a poe://*/IKC/monitor
"ARG1"
ID o alias del kernel remoto desde el punto de vista de IKC.
"ARG2"
Un flag. Si es verdadero, entonces ARG1 es el ID único del kernel remoto, si es falso, entonces ARG1 es un alias. Esto es principalmente útil cuando se monitorea *&*, y en realidad es un poco de estancamiento.
"ARG3"
"$state->{data}" es decir, cualquier dato que quieras.
"ARG4" ... "ARGN"
Parámetros específicos del callback. Véase arriba.

La mayoría del tiempo, ARG0 y ARG1 serán iguales. Las excepciones son si estás monitoreando *&* o si has proporcionado un especificador completo de evento IKC a IKC/monitor en lugar de solo un nombre de kernel.

Nota corta sobre el monitoreo de todos los kernels con "*"

Hay dos razones por las que estarás monitoreando todos los kernels remotos: conocimiento previo de los nombres y nombres desconocidos previamente.

Si conoces los nombres de los kernels previamente, podrías estar mejor monitoreando un nombre dado. Sin embargo, podrías preferir hacer una comparación similar con ARG1 (usando regexes, por ejemplo). Esto sería útil para clustering, donde varios kernels redundantes podrían seguir una convención de nombres como [aplicación]-[host], así podrías comparar "ARG1" con "/^credit-/" para ver si quieres configurar cosas específicas para ese kernel.

Sin conocer el nombre de un kernel previamente, podrías estar haciendo algún tipo de autodescubrimiento o simplemente monitoreando para depuración, registro o contabilidad. Claramente no quieres hacer autodescubrimiento para cada alias de cada kernel, solo para el nombre canónico, por lo que se requiere ARG2.

Nota corta la segunda

Puedes usar los mismos estados de callback cuando monitorees varios kernels. En este caso, encontrarás ARG0 útil para diferenciarlos.

$kernel->post('IKC', 'monitor', '*',
                {register=>'remote_register',
                 unregister=>'remote_unregister',
                 subscribe=>'remote_subscribe',
                 unsubscribe=>'remote_unsubscribe',
                 data=>'magic box'});

Ahora los remot_{register,unregister,subscribe,unsubscribe} se llaman para cualquier kernel remoto.

$kernel->post('IKC', 'monitor', 'Pulse', {register=>'pulse_connected'});

"pulse_connected" se llamará en la sesión actual cuando hayas conectado a un kernel llamado 'Pulse' con éxito.

$kernel->post('IKC', 'monitor', '*');

La sesión ya no monitorea a todos los kernels, solo a 'Pulse'.

$kernel->post('IKC', 'monitor', 'Pulse', {});

Ahora ya no nos importa 'Pulse';
