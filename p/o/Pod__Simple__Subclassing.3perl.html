NOMBRE

Pod::Simple::Subclassing -- escribir un formateador como una subclase de Pod::Simple

SINOPSIS

paquete Pod::SomeFormatter;
usar Pod::Simple;
@ISA = qw(Pod::Simple);
$VERSION = '1.01';
usar estricto;
sub _handle_element_start {
  mi($parser, $element_name, $attr_hash_r) = @_;
  ...
}
sub _handle_element_end {
  mi($parser, $element_name, $attr_hash_r) = @_;
  # NOTA: $attr_hash_r solo está presente cuando $element_name es "over" o "begin"
  # Los fragmentos de código restantes mayormente ignorarán este $attr_hash_r, ya que es
  # mayormente inútil. Está documentado dónde se documentan los eventos "over-*" y "begin".
  ...
}
sub _handle_text {
  mi($parser, $text) = @_;
  ...
}
1;

DESCRIPCIÓN

Este documento trata sobre el uso de Pod::Simple para escribir un procesador de Pod, generalmente un formateador de Pod. Si solo quieres saber cómo usar un formateador de Pod existente, consulta su documentación y también la documentación en Pod::Simple.

El paso cero al escribir un formateador de Pod es asegurarse de que ya no exista uno decente en CPAN. Consulta http://search.cpan.org/ y realiza una búsqueda con el nombre del formato que deseas renderizar. Considera también unirte a la lista Pod People http://lists.perl.org/showlist.cgi?name=pod-people y preguntar si alguien tiene un formateador para ese formato; tal vez alguien haya creado uno pero aún no lo haya lanzado.

El primer paso al escribir un procesador de Pod es leer perlpodspec, que contiene información sobre cómo escribir un analizador de Pod (que ha sido en gran medida resuelto por Pod::Simple), pero también muchos requisitos y recomendaciones para escribir un formateador.

El segundo paso es aprender realmente el formato al que planeas dar formato, o al menos todo lo que necesitas saber para representar Pod, que probablemente no sea mucho.

El tercer paso es elegir cuál de las interfaces de Pod::Simple deseas utilizar:

Pod::Simple
La interfaz básica de Pod::Simple que utiliza _handle_element_start(), _handle_element_end() y _handle_text().
Pod::Simple::Methody
La interfaz Pod::Simple::Methody está basada en eventos, similar a los "Handlers" de HTML::Parser o XML::Parser.
Pod::Simple::PullParser
Pod::Simple::PullParser proporciona una interfaz de flujo de tokens, similar a la interfaz de HTML::TokeParser.
Pod::Simple::SimpleTree
Pod::Simple::SimpleTree proporciona una interfaz de árbol simple, bastante similar a la interfaz "Tree" de XML::Parser. Los usuarios familiarizados con el manejo de XML se sentirán cómodos con esta interfaz. Los usuarios interesados en generar XML deberían investigar los módulos que producen una representación XML del flujo de Pod, notablemente Pod::Simple::XMLOutStream; puedes alimentar la salida de una clase así con el sistema de análisis XML con el que te sientas más cómodo.

El último paso es escribir tu código basándote en cómo los eventos (o tokens, o nodos de árbol, o el XML, o como sea que estés analizando) se mapearán a las construcciones en el formato de salida. También asegúrate de considerar cómo escapar los nodos de texto que contienen texto arbitrario y qué hacer con los nodos de texto que representan texto preformateado (de secciones verbatim).

En la siguiente sección, usamos XML para representar la estructura de eventos asociada con una construcción particular. Es decir, una etiqueta de apertura representa el inicio del elemento, los atributos de esa etiqueta de apertura son los atributos pasados al callback y la etiqueta de cierre representa el fin del elemento.

Tres métodos de callback deben ser proporcionados por una clase que extienda Pod::Simple para recibir el evento correspondiente:

"$parser->_handle_element_start( nombre_elemento, hashref_atributos )"
"$parser->_handle_element_end( nombre_elemento )"
"$parser->_handle_text( cadena_texto )"

Aquí está la lista completa de valores que puedes esperar como nombre_elemento en tu implementación de "_handle_element_start" y "_handle_element_end"::

eventos con un nombre_elemento de Documento
El análisis de un documento produce esta estructura de eventos: 
<Document start_line="543">
  ...todos los eventos...
</Document>

El valor del atributo start_line será el número de línea de la primera directiva de Pod en el documento.

Si no hay Pod en el documento dado, entonces la estructura de eventos será esta:

<Document contentless="1" start_line="543">
</Document>

En ese caso, el valor del atributo start_line no será significativo; bajo las implementaciones actuales, probablemente será el número de línea de la última línea del archivo.

eventos con un nombre_elemento de Para
El análisis de un párrafo simple (no verbatim, no directiva, no de datos) en un documento Pod produce esta estructura de eventos: 
<Para start_line="543">
  ...todos los eventos en este párrafo...
</Para>

El valor del atributo start_line será el número de línea del inicio del párrafo.

Por ejemplo, el análisis de este párrafo de Pod:

El valor del atributo I<start_line> será el
número de línea del inicio del párrafo.

produce esta estructura de eventos:

<Para start_line="129">
  El valor del
  <I>
    start_line
  </I>
  atributo será el número de línea de la primera directiva de Pod
  en el documento.
</Para>
eventos con un nombre_elemento de B, C, F, o I.
El análisis de un código de formato B<...> (o por supuesto cualquiera de sus variantes sintácticas semánticamente idénticas B<< ... >>, o B<<<< ... >>>>, etc.) produce esta estructura de eventos: 
<B>
  ...contenido...
</B>

Actualmente, no se transmiten atributos.

El análisis de códigos C, F, o I produce la misma estructura, solo con un nombre de elemento diferente.

Si tu objeto analizador ha sido configurado para aceptar otros códigos de formato, entonces se presentarán como estos códigos B/C/F/I, es decir, sin atributos.

eventos con un nombre_elemento de S
Normalmente, el análisis de una secuencia S<...> produce esta estructura de eventos, al igual que si fuera un código B/C/F/I: 
<S>
  ...contenido...
</S>

Sin embargo, Pod::Simple (y presumiblemente todos los analizadores derivados) ofrece la opción "nbsp_for_S" que, si está habilitada, suprimirá todos los eventos S y, en su lugar, cambiará todos los espacios en el contenido a espacios de no separación. Esto está destinado a formateadores que generan salida a un formato que no tiene un código que signifique lo mismo que S<...>, pero que tiene un código/carácter que significa espacio de no separación.

eventos con un nombre_elemento de X
Normalmente, el análisis de una secuencia X<...> produce esta estructura de eventos, al igual que si fuera un código B/C/F/I: 
<X>
  ...contenido...
</X>

Sin embargo, Pod::Simple (y presumiblemente todos los analizadores derivados) ofrece la opción "nix_X_codes" que, si está habilitada, suprimirá todos los eventos X e ignorará su contenido. Para formateadores/procesadores que no utilizan eventos X, esto es presumiblemente bastante útil.

eventos con un nombre_elemento de L
Dado que L<...> es la construcción más compleja del lenguaje, no debería sorprenderte que los eventos que genera sean los más compl
ex: en: description: | in the language. Most of the complexity is hidden in attribute values, so for those writing a Pod formatter that produces a non-hypertext format, they can ignore attributes and treat an L event structure as a formatting element that (presumably) produces no change in formatting. This is to say, the content of an L event structure (as opposed to its attributes) will always be what should be displayed as text.

There are, at first blush, three kinds of L links: URL, man, and pod.

When parsing code L<some_url>, this event structure is produced:

<L content-implicit="yes" raw="that_url" to="that_url" type="url">
            that_url
          </L>

The attribute "type="url"" is always specified for this sort of L code.

For example, this Pod code:

L<http://www.perl.com/CPAN/authors/>

produces this event structure:

<L content-implicit="yes" raw="http://www.perl.com/CPAN/authors/" to="http://www.perl.com/CPAN/authors/" type="url">
            http://www.perl.com/CPAN/authors/
          </L>

When parsing code L<manpage(section)> (and these are rather rare and not very useful), this event structure is produced:

<L content-implicit="yes" raw="manpage(section)" to="manpage(section)" type="man">
            manpage(section)
          </L>

The attribute "type="man"" is always specified for this sort of L code.

For example, this Pod code:

L<crontab(5)>

produces this event structure:

<L content-implicit="yes" raw="crontab(5)" to="crontab(5)" type="man">
            crontab(5)
          </L>

In reasonable cases where a manpage link has a section specified, the text will appear in the section attribute. For example, this Pod code:

L<crontab(5)/"ENVIRONMENT">

generates this event structure:

<L content-implicit="yes" raw="crontab(5)/&quot;ENVIRONMENT&quot;" section="ENVIRONMENT" to="crontab(5)" type="man">
            "ENVIRONMENT" in crontab(5)
          </L>

In reasonable cases where the Pod document has code like L<sometext|manpage(section)>, the sometext text will appear as the content of the element, while the manpage(section) text will appear only as the value of the to attribute, and there will be no "content-implicit="yes"" attribute (its presence indicates that the Pod parser had to infer what text should appear as link text, as opposed to cases where that attribute is absent, indicating that the Pod parser did not have to infer the link text, because the L code explicitly specified link text).

For example, this Pod code:

L<hell itself!|crontab(5)>

generates this event structure:

<L raw="hell itself!|crontab(5)" to="crontab(5)" type="man">
            hell itself!
          </L>

The last sort of L event structure is for links to/within Pod documents. It is the most complex, in that it can have a to attribute, or a section attribute, or both. The attribute "type="pod"" is always specified for this sort of L code.

In the most common case, the simple L<podpage> event structure generates this event structure:

<L content-implicit="yes" raw="podpage" to="podpage" type="pod">
            podpage
          </L>

For example, this Pod code:

L<Net::Ping>

generates this event structure:

<L content-implicit="yes" raw="Net::Ping" to="Net::Ping" type="pod">
            Net::Ping
          </L>

In cases where link text is explicitly specified, it will be found in the content of the element (and not in the attributes), as in the L<sometext|manpage(section)> case discussed above. For example, this Pod code:

L<Perl Error Messages|perldiag>

generates this event structure:

<L raw="Perl Error Messages|perldiag" to="perldiag" type="pod">
            Perl Error Messages
          </L>

In cases of links to a section of the current document, there is a section attribute instead of a to attribute. For example, this Pod code:

L</"Member Data">

generates this event structure:

<L content-implicit="yes" raw="/&quot;Member Data&quot;" section="Member Data" type="pod">
            "Member Data"
          </L>

As another example, this Pod code:

L<the various attributes|/"Member Data">

generates this event structure:

<L raw="the various attributes|/&quot;Member Data&quot;" section="Member Data" type="pod">
            the various attributes
          </L>

In cases of links to a section of a different Pod document, there are both section and to attributes. For example, this Pod code:

L<perlsyn/"Basic BLOCKs and Switch Statements">

generates this event structure:

<L content-implicit="yes" raw="perlsyn/&quot;Basic BLOCKs and Switch Statements&quot;" section="Basic BLOCKs and Switch Statements" to="perlsyn" type="pod">
            "Basic BLOCKs and Switch Statements" in perlsyn
          </L>

As another example, this Pod code:

L<SWITCH statements|perlsyn/"Basic BLOCKs and Switch Statements">

generates this event structure:

<L raw="SWITCH statements|perlsyn/&quot;Basic BLOCKs and Switch Statements&quot;" section="Basic BLOCKs and Switch Statements" to="perlsyn" type="pod">
            SWITCH statements
          </L>

Although in fact, you will note that we do not distinguish between these syntaxes:

L</"Member Data">
L<"Member Data">
L</Member Data>
L<Member Data>    [obsolete syntax]

This is to say, all produce the same event structure (in general), namely:

<L content-implicit="yes" raw="$depends_on_syntax" section="Member Data" type="pod">
            &#34;Member Data&#34;
          </L>

The raw attribute depends on the original content of the "L<>" formatting code, so the event structure is the same in general.

If you haven't guessed by now, the raw attribute contains the original, unescaped content of the "L<>" formatting code. Besides the examples above, pay attention to the following event structure generated by the following "L<>" formatting code:

L<click B<here>|page/About the C<-M> switch>
          <L raw="click B<here>|page/About the C<-M> switch" section="About the -M switch" to="page" type="pod">
            click B<here>
          </L>

It is also important to note that formatting codes are present and unescaped in the raw attribute.

There is a known bug in the raw attribute that any surrounding whitespace is condensed to a single space. For example, given L< link>, the raw attribute will be " link".

events with an element_name of E or Z
While there are Pod codes E<...> and Z<>, these do not produce any E or Z events -- that is, there are no such events as E or Z.
events with an element_name of Verbatim
When a Pod verbatim paragraph (AKA "codeblock") is parsed, it produces this event structure: 
<Verbatim start_line="543" xml:space="preserve">
          ...text...
        </Verbatim>

The value of the start_line attribute will be the line number of the first line of this verbatim block. The xml:space attribute is always present, and always has the value "preserve".

The text content will have tabs already expanded.

events with an element_name of head1 .. head4
When a "=head1 ..." directive is parsed, it produces this event structure: 
<head1>
          ...stuff...
        </head1>

For example, a directive consisting of this:

=head1 Options to C<new> et al.

will produce this event structure:

<head1 start_line="543">
          Options to
          <C>
            new
          </C>
          et al.
        </head1>

"=head2" through "=head4" directives are the same, except for the element names in the event structure.

events with an element_name of encoding
In the default case, the events corresponding to "=encoding" directives are not emitted. They are emitted if "keep_encoding_directive" is true. In that case they produce event structures like "events with an element_name of head1 .. head4" above.
events with an element_name of over-bullet
When an "=over ... =back" block is parsed where the items are a bulleted list, it will produce this event structure:

            ...Stuff...
          </item-bullet>
          ...more item-bullets...
        </over-bullet fake-closer="1">

Pod::Simple Events

Pod::Simple works by calling various methods on a parser object. These methods have names like para, h1, comment, and so on. They are called at appropriate times during the parsing of the Pod source file.

The following are the events (method calls) that Pod::Simple generates. These are grouped by the content of the tag that generated them.

events with an element_name of text
These are the contents of paragraphs, list items, and so on. This is text that has been Pod-processed (that is, things like B<foo> have been converted to their appropriate event structures).
events with an element_name of formatted_code
These events are generated by things like B<bold>, I<italic>, etc.
events with an element_name of C
Events generated by C<...> sections.
events with an element_name of X
Events generated by X<...> sections.
events with an element_name of code
Events generated by code sections, like:
=code
    print "hello world\n";
=end code

This is generally only used for very short code snippets.

events with an element_name of verbatim
Events generated by verbatim sections, like:
=verbatim
This is verbatim text.
It is not processed in any way,
except for the expansion of tabs.
=end verbatim

Note that this is what is generated by default if you don't specify a Pod formatter. So if you just parse the Pod source above, you'll get a single verbatim event.

events with an element_name of comment
Events generated by Pod comments (lines starting with #).
events with an element_name of para
Events generated by paragraphs.
events with an element_name of h1, h2, h3, h4, h5, h6
Events generated by headings.
events with an element_name of over-bullet
These events are generated by =over and =back blocks that contain =item * (or other non-number/non-text items).
events with an element_name of over-number
These events are generated by =over and =back blocks that contain =item 1 (or other numbers).
events with an element_name of over-text
These events are generated by =over and =back blocks that contain =item Foo` (or other text items).
events with an element_name of over-block
These events are generated by =over and =back blocks that do not contain any =item directives.
events with an element_name of over-empty
These events are generated by empty =over and =back blocks.
events with an element_name of item-bullet
These events are generated by =item * directives within an =over block.
events with an element_name of item-number
These events are generated by =item 1 directives within an =over block.
events with an element_name of item-text
These events are generated by =item Foo directives within an =over block.
events with an element_name of end-block
These events are generated by =end<tag> directives.
events with an element_name of for
These events are generated by =for<tag> directives.
events with an element_name of begin_block
These events are generated by =begin<tag> directives.
events with an element_name of end-block
These events are generated by =end<tag> directives.
events with an element_name of Unknown
Events generated by unknown directives or formatting codes.

The over-* events have a couple of special attributes:

the fake-closer attribute
This attribute is true if the =back tag was missing, and thus Pod::Simple had to invent one. It's false otherwise.
the indent attribute
This attribute is the number of spaces that were used to indent the contents of the =over block. If no indentation was specified (e.g., =over with no number after it), then the value is 4.

Here's an example of how over-bullet events are generated:

=over
=item * foo
=item * bar
=back

This generates:

<over-bullet indent="4" start_line="1">
  <item-bullet start_line="2">
    foo
  </item-bullet>
  <item-bullet start_line="3">
    bar
  </item-bullet>
</over-bullet>

If the =back tag is missing:

=over
=item * foo
=item * bar

This generates:

<over-bullet fake-closer="1" indent="4" start_line="1">
  <item-bullet start_line="2">
    foo
  </item-bullet>
  <item-bullet start_line="3">
    bar
  </item-bullet>
  <fake-marker start_line="3"/>
</over-bullet>

Note the fake-closer="1" attribute on the over-bullet element, and the fake-marker element. This signifies that the =over did not have a matching =back, and thus Pod::Simple had to create a fake closer.

For example, this Pod source:

=over
=item *
Something
=back

Would produce an event structure that does not have the fake-closer attribute, whereas this Pod source:

=over
=item *
Gasp! An unclosed =over block!

would. The rest of the over-* examples will not demonstrate this attribute, but they all can have it. See Pod::Checker's source for an example of this attribute being used.

The value of the indent attribute is whatever value is after the "=over" directive, as in "=over 8". If no such value is specified in the directive, then the indent attribute has the value "4".

For example, this Pod source:

=over
=item *
Stuff
=item *
Bar I<baz>!
=back

produces this event structure:

<over-bullet indent="4" start_line="1">
  <item-bullet start_line="3">
    Stuff
  </item-bullet>
  <item-bullet start_line="5">
    Bar <I>baz</I>!
  </item-bullet>
</over-bullet>
events with an element_name of over-number
When an "=over ... =back" block is parsed where the items are a numbered list, it will produce this event structure: 
<over-number indent="4" start_line="1">
  <item-number number="1" start_line="2">
    ...Stuff...
  </item-number>
  ...more item-number...
</over-number>

This is like the "over-bullet" event structure; but note that the contents are "item-number" instead of "item-bullet", and note that they will have a "number" attribute, which some formatters/processors may ignore (since, for example, there's no need for it in HTML when producing an "<UL><LI>...</LI>...</UL>" structure), but which any processor may use.

Note that the values for the number attributes of "item-number" elements in a given "over-number" area will start at 1 and go up by one each time. If the Pod source doesn't follow that order (even though it really should!), whatever numbers it has will be ignored (with the correct values being put in the number attributes), and an error message might be issued to the user.

events with an element_name of over-text
These events are somewhat unlike the other over-* structures, as far as what their contents are. When an "=over ... =back" block is parsed where the items are a list of text "subheadings", it will produce this event structure: 
<over-text indent="4" start_line="1">
  <item-text start_line="2">
    ...stuff...
  </item-text>
  ...stuff (generally Para or Verbatim elements)...
  <item-text start_line="4">
  ...more item-text and/or stuff...
</over-text>

The indent and fake-closer attributes are as with the other over-* events.

For example, this Pod source:

=over
=item Foo
Stuff
=item Bar I<baz>!
Quux
=back

produces this event structure:

<over-text indent="4" start_line="1">
  <item-text start_line="2">
    Foo
  </item-text>
  <Para start_line="4">
    Stuff
  </Para>
  <item-text start_line="5">
    Bar
      <I>
        baz
      </I>
    !
  </item-text>
  <Para start_line="7">
    Quux
  </Para>
</over-text>
events with an element_name of over-block
These events are somewhat unlike the other over-* structures, as far as what their contents are. When an "=over ... =back" block is parsed where there are no items, it will produce this event structure: 
<over-block indent="4" start_line="1">
  ...stuff (generally Para or Verbatim elements)...
</over-block>

The indent and fake-closer attributes are as with the other over-* events.

For example, this Pod source:

=over
For cutting off our trade with all parts of the world
For transporting us beyond seas to be tried for pretended offenses
He is at this time transporting large armies of foreign mercenaries to
complete the works of death, desolation and tyranny, already begun with
circumstances of cruelty and perfidy scarcely paralleled in the most
barbarous ages, and totally unworthy the head of a civilized nation.
=back

will produce this event structure:

<over-block indent="4" start_line="1">
  <Para start_line="2">
    For cutting off our trade with all parts of the world
  </Para>
  <Para start_line="3">
    For transporting us beyond seas to be tried for pretended offenses
  </Para>
  <Para start_line="4">
    He is at this time transporting large armies of [...more text...]
  </Para>
</over-block>
events with an element_name of over-empty
Note: These events are only triggered if parse_empty_lists() is set to a true value.

These events are somewhat unlike the other over-* structures, as far as what their contents are. When an "=over ... =back" block is parsed where there is no content, it will produce this event structure:

<over-empty indent="4" start_line="1">
</over-empty>

The indent and fake-closer attributes are as with the other over-* events.

For example, this Pod source:

=over
=over
=back
=back

will produce this event structure:

<over-block indent="4" start_line="1">
  <over-empty indent="4" start_line="2">
  </over-empty>
</over-block>

Note that the outer "=over" is a block because it has no "=item"s but still has content: the inner "=over". The inner "=over", in turn, is completely empty, and is treated as such.

events with an element_name of item-bullet
See "events with an element_name of over-bullet", above.

See "events with an element_name of over-number", above.

More Pod::Simple Methods

Pod::Simple provides a lot of methods that aren't generally interesting to the end user of an existing Pod formatter, but some of which you might find useful in writing a Pod formatter. They are listed below. The first several methods (the accept_* methods) are for declaring the capabilities of your parser, notably what "=for targetname" sections it's interested in, what extra N<...> codes it accepts beyond the ones described in the perlpod.

"$parser->accept_targets( SOMEVALUE )"
As the parser sees sections like: 
=for html  <img src="fig1.jpg">

or

=begin html
  <img src="fig1.jpg">
=end html

...the parser will ignore these sections unless your subclass has specified that it wants to see sections targeted to "html" (or whatever the formatter name is).

If you want to process all sections, even if they're not targeted for you, call this before you start parsing:

$parser->accept_targets('*');
"$parser->accept_targets_as_text( SOMEVALUE )"
This is like accept_targets, except that it specifies also that the content of sections for this target should be treated as Pod text even if the target name in "=for targetname" doesn't start with a ":".

At time of writing, I don't think you'll need to use this.

"$parser->accept_codes( Codename, Codename... )"
This tells the parser that you accept additional formatting codes, beyond just the standard ones (I B C L F S X, plus the two weird ones you don't actually see in the parse tree, Z and E). For example, to also accept codes "N", "R", and "W": 
$parser->accept_codes( qw( N R W ) );

"$parser->accept_directive_as_data( directive_name )"
"$parser->accept_directive_as_verbatim( directive_name )"
"$parser->accept_directive_as_processed( directive_name )"
In the unlikely situation that you need to tell the parser that you will accept additional directives ("=foo" things), you need to first set the parser to treat its content as data (i.e., not really processed at all), or as verbatim (mostly just expanding tabs), or as processed text (parsing formatting codes like B<...>).

For example, to accept a new directive "=method", you'd presumably use:

$parser->accept_directive_as_processed("method");

so that you could have Pod lines like:

=method I<$whatever> thing B<um>

Making up your own directives breaks compatibility with other Pod formatters, in a way that using "=for target ..." is not.

METHODS

"$parser->is_standard_pod()"
Este método devuelve verdadero si el parser está configurado para tratar el archivo de entrada como POD estándar. Por defecto, esto es falso, y el parser tratará de la misma forma cualquier cosa que se le arroje, hasta que se encuentre una línea que comience con "=begin pod". En ese momento, el resto del archivo se considerará POD. Si el archivo NO comienza con "=begin pod", y este método devuelve falso, el parser ignorará todo hasta que se encuentre un bloque de POD, y el resto del archivo se procesará como POD.
"$parser->parse_mode( SOMEVALUE )"
Establece el modo de análisis. Consulte la documentación de Pod::Parser para obtener una lista de los modos disponibles.
"$parser->false_deletion_attributes( SOMEVALUE )"
Establece un valor booleano. Si es verdadero, los atributos que por defecto son falsos se eliminarán de los eventos de salida. Esto es útil si está creando un superconjunto del formato Pod donde no necesita preocuparse por la compatibilidad.
"$parser->nbsp_for_S( BOOLEAN )"
Establecer este atributo a un valor verdadero (y por defecto es falso) convertirá las secuencias "S<...>" en secuencias de palabras separadas por caracteres de espacio no rompible ("\xA0"). Por ejemplo, tomará esto: 
I like S<Dutch apple pie>, don't you?
Y lo tratará como si fuera: 
I like DutchE<nbsp>appleE<nbsp>pie, don't you?
Esto es útil para formatos de salida que no tienen algo parecido al código "S<...>", pero que sí tienen un código para espacio no rompible. Actualmente no hay un método para hacer lo contrario; pero probablemente pueda proporcionar uno si se solicita.
"$parser->version_report()"
Esto devuelve una cadena que informa el valor de $VERSION de su módulo (y su nombre de clase), así como el valor de $VERSION de Pod::Simple. Tenga en cuenta que perlpodspec requiere que los formatos de salida (siempre que sea posible) anoten este detalle en un comentario en el formato de salida. Por ejemplo, para algún tipo de formato de salida SGML: 
print OUT "<!-- \n", $parser->version_report, "\n -->";
"$parser->pod_para_count()"
Esto devuelve la cuenta de párrafos de Pod vistos hasta ahora.
"$parser->line_count()"
Este es el número de línea actual que se está analizando. Pero podría encontrar el atributo de evento "line_number" más preciso, cuando esté presente.
"$parser->nix_X_codes( SOMEVALUE )"
Este atributo, cuando se establece en un valor verdadero (y es falso por defecto) ignora cualquier secuencia "X<...>" en el documento que se está analizando. Muchos formatos en realidad no usan el contenido de estos códigos, por lo que no tienen ninguna razón para procesarlos.
"$parser->keep_encoding_directive( SOMEVALUE )"
Este atributo, cuando se establece en un valor verdadero (es falso por defecto) mantendrá "=encoding" y su contenido en la estructura de eventos. La mayoría de los formatos en realidad no necesitan procesar el contenido de una directiva de "=encoding", incluso cuando esta directiva establece la codificación y el procesador utiliza la información de codificación. De hecho, es posible conocer la codificación sin procesar el contenido de la directiva.
"$parser->merge_text( SOMEVALUE )"
Este atributo, cuando se establece en un valor verdadero (y es falso por defecto) se asegura de que solo se cree un evento (o token, o nodo) para cualquier secuencia contigua de texto. Por ejemplo, considere este ejemplo algo forzado: 
I just LOVE Z<>hotE<32>apple pie!
Cuando esto se analiza y los eventos están a punto de ser llamados, puede parecer que son cuatro eventos de texto diferentes, uno tras otro: un evento para "I just LOVE ", uno para "hot", uno para " ", y uno para "apple pie!". Pero si tiene merge_text activado, entonces se garantiza que se activará como un solo evento de texto: "I just LOVE hot apple pie!".
"$parser->code_handler( CODE_REF )"
Esto especifica el código que debe llamarse cuando se ve una línea de código (es decir, una línea fuera del Pod). Normalmente esto es undef, lo que significa que no se debe llamar a ningún código. Si proporciona una rutina, debería comenzar así: 
sub get_code_line {  # o como quiera llamarla
  my($line, $line_number, $parser) = @_;
  ...
}
Sin embargo, tenga en cuenta que a veces los eventos de Pod no se procesan en exactamente el mismo orden que las líneas de código; es decir, si tiene un archivo con Pod, luego código, luego más Pod, a veces el código se procesará (a través de lo que sea que llame code_handler) antes de que todo el Pod precedente haya sido procesado.
"$parser->cut_handler( CODE_REF )"
Esto es igual que el atributo code_handler, excepto que es para líneas "=cut", no para líneas de código. Se aplican las mismas advertencias. Es poco probable que las líneas "=cut" sean interesantes, pero se incluyen para completitud.
"$parser->pod_handler( CODE_REF )"
Esto es igual que el atributo code_handler, excepto que es para líneas "=pod", no para líneas de código. Se aplican las mismas advertencias. Es poco probable que las líneas "=pod" sean interesantes, pero se incluyen para completitud.
"$parser->whiteline_handler( CODE_REF )"
Esto es igual que el atributo code_handler, excepto que es para líneas que aparentemente están en blanco pero tienen espacios en blanco (" " y/o "\t") en ellas, no para líneas de código. Se aplican las mismas advertencias. Es poco probable que estas líneas sean interesantes, pero se incluyen para completitud.
"$parser->whine( linenumber, complaint string )"
Esto señala un problema en el Pod, que se informará en la sección "Errores de Pod" del documento y/o se enviará a STDERR, dependiendo de los valores de los atributos "no_whining", "no_errata_section" y "complain_stderr".
"$parser->scream( linenumber, complaint string )"
Esto señala un error como lo hace "whine", excepto que no es suprimible con "no_whining". Esto solo debe usarse para errores muy graves.
"$parser->source_dead(1)"
Esto aborta el análisis del documento actual, activando la bandera que indica que se ha visto el final del archivo. En casos particularmente drásticos, es posible que desee hacer esto. ¡Es bastante mejor que simplemente llamar a "die"!
"$parser->hide_line_numbers( SOMEVALUE )"
Algunas subclases que volcán indiscriminadamente atributos de eventos (bueno, excepto por los que comienzan con "~") pueden usar este atributo del objeto para abstenerse de volcar el atributo "start_line".
"$parser->no_whining( SOMEVALUE )"
Este atributo, si se establece en verdadero, suprimirá los informes de mensajes de error no fatales. El valor por defecto es falso, lo que significa que las quejas sí se informan. Cómo se informan depende de los valores de los atributos "no_errata_section" y "complain_stderr".
"$parser->no_errata_section( SOMEVALUE )"
Este atributo, si se establece en verdadero, suprimirá la generación de una sección de erratas. El valor por defecto es falso, es decir, se generará una sección de erratas.
"$parser->complain_stderr( SOMEVALUE )"
Este atributo, si se establece en verdadero, enviará quejas a STDERR. El valor por defecto es falso, es decir, las quejas no van a STDERR.
"$parser->bare_output( SOMEVALUE )"
Algunas subclases formateadoras utilizan esto como una bandera para indicar si la salida debe omitir el código de prólogo y epílogo. Por ejemplo, establecer esto en verdadero para una clase formateadora HTML debería omitir el prólogo de "<html><head><title>...</title><body>..." y el epílogo de "</body></html>". Si desea establecer esto en verdadero, probablemente también debería establecer "no_whining" o al menos "no_errata_section" en verdadero.
"$parser->preserve_whitespace( SOMEVALUE )"
Si establece este atributo a un valor verdadero, el analizador intentará preservar los espacios en blanco en la salida. Esto significa que convenciones de formato como dos espacios después de los puntos serán preservadas por el analizador. Esto es principalmente útil para formatos de salida que tratan los espacios en blanco como significativos (como texto o *roff, pero no HTML).
"$parser->parse_empty_lists( SOMEVALUE )"
Si este atributo se establece en verdadero, el analizador no ignorará los bloques vacíos de "=over"/"=back". El tipo de "=over" será *vacío*, documentado arriba, "eventos con un nombre de elemento de over-empty".

VER TAMBIÉN

Pod::Simple -- framework de análisis de Pod basado en eventos

Pod::Simple::Methody -- similar a Pod::Simple, pero cada tipo de evento llama a su propio método (como "start_head3")

Pod::Simple::PullParser -- un framework de análisis de Pod similar a Pod::Simple, pero con una interfaz de flujo de tokens

Pod::Simple::SimpleTree -- un framework de análisis de Pod similar a Pod::Simple, pero con una interfaz de árbol

Pod::Simple::Checker -- una subclase simple de Pod::Simple que lee documentos y luego realiza un informe en texto plano de cualquier error encontrado en el documento

Pod::Simple::DumpAsXML -- para volcar documentos de Pod como XML ordenadamente indentado, mostrando cada evento en su propia línea

Pod::Simple::XMLOutStream -- volca un documento de Pod como XML (sin introducir espacios en blanco adicionales como lo hace Pod::Simple::DumpAsXML).

Pod::Simple::DumpAsText -- para volcar documentos de Pod como texto ordenadamente indentado, mostrando cada evento en su propia línea

Pod::Simple::LinkSection -- clase para objetos que representan los valores de los atributos TODO y TODO de elementos L<...>

Pod::Escapes -- el módulo que utiliza Pod::Simple para evaluar contenido E<...>

Pod::Simple::Text -- un formateador simple de texto plano para Pod

Pod::Simple::TextContent -- similar a Pod::Simple::Text, pero no hace ningún esfuerzo por indentar o envolver el texto que se está formateando

Pod::Simple::HTML -- un formateador HTML simple para Pod
