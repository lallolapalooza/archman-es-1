NOMBRE

POE::NFA - una máquina de estados orientada a eventos (autómata finito no determinista)

SINOPSIS

use POE::Kernel;
use POE::NFA;
use POE::Wheel::ReadLine;
# Inicia una NFA y entra en su estado inicial.
POE::NFA->spawn(
  inline_states => {
    initial => {
      setup => \&setup_stuff,
    },
    state_login => {
      on_entry => \&login_prompt,
      on_input => \&save_login,
    },
    state_password => {
      on_entry => \&password_prompt,
      on_input => \&check_password,
    },
    state_cmd => {
      on_entry => \&command_prompt,
      on_input => \&handle_command,
    },
  },
)->goto_state(initial => "setup");
POE::Kernel->run();
exit;
sub setup_stuff {
  $_[RUNSTATE]{io} = POE::Wheel::ReadLine->new(
    InputEvent => 'on_input',
  );
  $_[MACHINE]->goto_state(state_login => "on_entry");
}
sub login_prompt { $_[RUNSTATE]{io}->get('Login: '); }
sub save_login {
  $_[RUNSTATE]{login} = $_[ARG0];
  $_[MACHINE]->goto_state(state_password => "on_entry");
}
sub password_prompt { $_[RUNSTATE]{io}->get('Password: '); }
sub check_password {
  if ($_[RUNSTATE]{login} eq $_[ARG0]) {
    $_[MACHINE]->goto_state(state_cmd => "on_entry");
  }
  else {
    $_[MACHINE]->goto_state(state_login => "on_entry");
  }
}
sub command_prompt { $_[RUNSTATE]{io}->get('Cmd: '); }
sub handle_command {
  $_[RUNSTATE]{io}->put("  <<$_[ARG0]>>");
  if ($_[ARG0] =~ /^(?:quit|stop|exit|halt|bye)$/i) {
    $_[RUNSTATE]{io}->put('Bye!');
    $_[MACHINE]->stop();
  }
  else {
    $_[MACHINE]->goto_state(state_cmd => "on_entry");
  }
}

DESCRIPCIÓN

POE::NFA implementa un tipo diferente de sesión POE: un autómata finito no determinista. Desglosémoslo.

Un autómata finito es una máquina de estados con un número limitado de estados y transiciones. Técnicamente, los objetos POE::NFA pueden modificarse a sí mismos en tiempo de ejecución, por lo que realmente no son "finitos". La modificación en tiempo de ejecución no es compatible actualmente con la API, ¡así que se mantiene la negación plausible!

Las máquinas de estados deterministas son aquellas en las que todas las transiciones posibles se conocen en tiempo de compilación. POE::NFA es "no determinista" porque las transiciones pueden cambiar según las condiciones en tiempo de ejecución.

Pero, más sencillamente, POE::NFA es como POE::Session pero con bancos de manejadores de eventos que pueden intercambiarse según el estado de ejecución de la sesión. Considere el ejemplo de la SINOPSIS, que tiene manejadores "on_entry" y "on_input" que hacen cosas diferentes dependiendo del estado en tiempo de ejecución. POE::Wheel::ReadLine lanza "on_input", pero suceden cosas diferentes dependiendo de si la sesión está en su estado de "login", "password" o "command".

POE::NFA toma mucho prestado de POE::Session, por lo que este documento solo discutirá las diferencias. Consulte POE::Session para ver las cosas que son similares.

MÉTODOS PÚBLICOS

Este documento se centra principalmente en las diferencias con respecto a POE::Session.

get_current_state

Cada estado de la máquina tiene un nombre. get_current_state() devuelve el nombre del estado actual de la máquina. get_current_state() se utiliza principalmente para recuperar el estado de alguna otra máquina. Es más fácil (y rápido) usar $_[STATE] en los propios manejadores de eventos de una máquina.

get_runstate

get_runstate() devuelve el estado de ejecución actual de la máquina. Los estados de ejecución son equivalentes a los HEAPS de POE::Session, por lo que este método hace prácticamente lo mismo que el get_heap() de POE::Session. Sin embargo, es más fácil (y rápido) usar $_[RUNSTATE] en los propios manejadores de eventos de una máquina.

spawn NOMBRE_ESTADO => REFERENCIA_HASH_MANEJADORES[, ...]

spawn() es el constructor de POE::NFA. El nombre refleja la idea de que las nuevas máquinas de estados se inician como hilos o procesos en lugar de instanciarse como objetos.

La máquina en sí se define como una lista de nombres de estados y hashes que mapean eventos a manejadores dentro de cada estado.

my %states = (
  state_1 => {
    event_1 => \&handler_1,
    event_2 => \&handler_2,
  },
  state_2 => {
    event_1 => \&handler_3,
    event_2 => \&handler_4,
  },
);

Un solo evento puede ser manejado por muchos estados. El manejador apropiado se llamará según el estado actual de la máquina. Por ejemplo, si se envía "event_1" mientras la máquina está en "state_2", se llamará a handler_3() para manejar el evento. El mapa estado -> evento -> manejador se ve así:

$machine{state_2}{event_1} = \&handler_3;

En lugar de "inline_states", se pueden usar "object_states" o "package_states". Estos mapean los eventos de un estado a un método de objeto o paquete respectivamente.

object_states => {
  state_1 => [
    $object_1 => [qw(event_1 event_2)],
  ],
  state_2 => [
    $object_2 => {
      event_1 => method_1,
      event_2 => method_2,
    }
  ]
}

En el ejemplo anterior, en el caso de que llegue "event_1" mientras la máquina está en "state_1", se llamará al método "event_1" en $object_1. Si la máquina está en "state_2", se llamará al método "method_1" en $object_2.

"package_states" es muy similar, pero en lugar de usar un $object, se pasa un "Package::Name"

El parámetro "runstate" permite que "RUNSTATE" se inicialice de manera diferente en el momento de la instanciación. "RUNSTATE", al igual que los heaps, suelen ser referencias hash anónimas, pero "runstate" puede configurarlas para que sean referencias de arrays o incluso objetos.

Las transiciones de estado no se ejecutan necesariamente de inmediato por defecto. En su lugar, se colocan en la cola de eventos de POE detrás de cualquier evento pendiente actualmente. Habilitar la opción "immediate" hace que las transiciones de estado ocurran inmediatamente, independientemente de cualquier evento en cola.

goto_state NUEVO_ESTADO[, EVENTO_ENTRADA[, ARGUMENTOS_EVENTO]]

goto_state() pone la máquina en un nuevo estado. Si se especifica un EVENTO_ENTRADA, ese evento se enviará después de que la máquina entre en el nuevo estado. Los ARGUMENTOS_EVENTO, si se incluyen, se pasarán al manejador del evento de entrada a través de "ARG0..$#_".

# Cambia al siguiente estado.
$_[MACHINE]->goto_state( 'next_state' );
# Cambia al siguiente estado y llama a un punto de entrada específico.
$_[MACHINE]->goto_state( 'next_state', 'entry_event' );
# Cambia al siguiente estado; llama a un punto de entrada con algunos valores.
$_[MACHINE]->goto_state( 'next_state', 'entry_event', @parameters );

stop

stop() fuerza a una máquina a detenerse. La máquina también se detendrá de forma elegante si se queda sin cosas que hacer, al igual que POE::Session.

stop() es una medida drástica. Forzará la limpieza de los recursos. Sin embargo, las referencias circulares en el "RUNSTATE" de la máquina no son responsabilidad de POE y pueden causar fugas de memoria.

$_[MACHINE]->stop();

call_state EVENTO_RETORNO, NUEVO_ESTADO[, EVENTO_ENTRADA[, ARGUMENTOS_EVENTO]]

call_state() es similar a goto_state(), pero empuja el estado actual a una pila. En algún momento posterior, un manejador puede llamar a return_state() para sacar la pila de llamadas y devolver la máquina a su estado anterior. En ese momento, un evento llamado EVENTO_RETORNO se enviará a la máquina.

return_state

return_state() saca el último estado de la pila de llamada y lo restituye como el estado actual de la máquina. Si se especifica un EVENTO_RETORNO cuando se llama a call_state(), ese evento se enviará al estado que se está reanudando.

NAME

POE::NFA – a state machine for POE

SYNOPSIS

    use POE::NFA;

    my $machine = POE::NFA::State->spawn(
        -package => 'My::States',
        -state   => 'initial_state',
    );

    # In My::States.pm:
    package My::States;
    use strict;
    use POE::NFA::State; # Or inherit from it

    sub initial_state {
        my ($machine, $args) = @_;
        # ...
        $machine->goto_state( 'next_state', 'some_event' );
        # ...
    }

    sub next_state {
        my ($machine, $args) = @_;
        # ...
    }

DESCRIPTION

POE::NFA provides a way to implement state machines within POE sessions. It is a subclass of POE::Session.

It provides methods to transition between states, and to call and return from states, similar to subroutines.

States

States are simply Perl subroutines. They are passed two arguments: a reference to the state machine object itself, and a hash reference of arguments. The arguments hash reference contains information about the current event, such as the event name, the session ID, and any data associated with the event.

Transitions

State transitions are performed using methods like goto_state(), call_state(), and return_state().

PUBLIC METHODS

spawn

This is the constructor for POE::NFA. It is equivalent to POE::Session::spawn(), but with additional parameters:

-package PACKAGE
The package that contains the state subroutines.
-state STATE
The initial state to enter.
-session_id ID
The session ID for the state machine.
-alias ALIAS
An alias for the session.

goto_state([RETURN_ARGS])

The goto_state() method is used to transition to a new state. It takes the new state's name as its first argument, and an event name as its second argument. Optional arguments can be passed to the new state's handler via "ARG0..$#_".

$machine->goto_state( 'new_state', 'entry_event', $arg1, $arg2 );

"ENTRY_EVENT" is the event that will be emitted once the machine enters its new state. "ENTRY_ARGS" are parameters passed to the "ENTRY_EVENT" handler via "ARG0..$#_".

If goto_state() is called from within a state that was entered via call_state(), the return event and arguments from the original call_state() call will be ignored.

call_state([RETURN_EVENT], [RETURN_ARGS])

The call_state() method is similar to goto_state(), but it allows the state machine to return to the previous state after the called state has finished.

The first argument is the name of the state to call. The second argument is the event name that will be emitted when the machine returns to the current state. Subsequent arguments are passed to the called state's handler.

$machine->call_state( 'called_state', 'return_here', 'new_state', 'entry_event', $arg1, $arg2 );

When the called state finishes (by calling return_state()), the machine will transition to "new_state" and emit "entry_event". The original state's handler will not be invoked again.

If the call to call_state() is followed by a goto_state(), the return event and arguments will be discarded. The "RETURN_EVENT" will be posted to notify the old state of the return.

$machine->call_state( 'return_here', 'new_state', 'entry_event' );

As with goto_state(), "ENTRY_EVENT" is the event that will be emitted once the machine enters its new state. "ENTRY_ARGS" are parameters passed to the "ENTRY_EVENT" handler via "ARG0..$#_".

return_state [RETURN_ARGS]

return_state() returns to the most recent state in which call_state() was invoked. If the preceding call_state() included a return event then its handler will be invoked along with some optional "RETURN_ARGS". The "RETURN_ARGS" will be passed to the return handler via "ARG0..$#_".

$_[MACHINE]->return_state( 'success', @success_values );

Methods that match POE::Session

The following methods behave identically to the ones in POE::Session.

ID
option
postback
callback

About new() and create()

POE::NFA's constructor is spawn(), not new() or create().

PREDEFINED EVENT FIELDS

POE::NFA's predefined event fields are the same as POE::Session's with the following three exceptions.

MACHINE

"MACHINE" is equivalent to Session's "SESSION" field. It holds a reference to the current state machine, and is useful for calling its methods.

See POE::Session's "SESSION" field for more information.

$_[MACHINE]->goto_state( $next_state, $next_state_entry_event );

RUNSTATE

"RUNSTATE" is equivalent to Session's "HEAP" field. It holds an anonymous hash reference which POE is guaranteed not to touch. Data stored in "RUNSTATE" will persist between handler invocations.

STATE

"STATE" contains the name of the machine's current state. It is not equivalent to anything from POE::Session.

EVENT

"EVENT" is equivalent to Session's "STATE" field. It holds the name of the event which invoked the current handler. See POE::Session's "STATE" field for more information.

PREDEFINED EVENT NAMES

POE::NFA defines four events of its own. These events are used internally and may not be overridden by application code.

See POE::Session's "PREDEFINED EVENT NAMES" section for more information about other predefined events.

The events are: "poe_nfa_goto_state", "poe_nfa_push_state", "poe_nfa_pop_state", "poe_nfa_stop".

Yes, all the internal events begin with "poe_nfa_". More may be forthcoming, but they will always begin the same way. Therefore please do not define events beginning with "poe_nfa_".
