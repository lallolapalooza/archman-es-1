PHYSFS_enumerate

Esto es lo mismo que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, excepto que puede devolver un resultado del callback: específicamente: si estás buscando algo específico, una vez que lo encuentres, puedes indicar a PhysicsFS que deje de enumerar más. Esto se usa con PHYSFS_enumerate(), que esperemos que hayamos hecho bien esta vez. :)

Parámetros

data Puntero a datos definidos por el usuario, pasado desde la API que finalmente llamó al callback.
origdir Una cadena que contiene la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio sobre el cual solicitaste la enumeración, pasado en el callback para tu conveniencia.
fname El nombre del archivo que se está enumerando. Puede que no esté en orden alfabético en comparación con otros callbacks que se hayan ejecutado, y no contendrá la ruta completa. Puedes recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

Devoluciones

Un valor de PHYSFS_EnumerateCallbackResult. Todos los demás valores (actualmente) no están definidos; no los uses.

typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Firma de función para callbacks que enumeran archivos.

Advertencia

A partir de PhysicsFS 2.1, usa PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; te da más control sobre el proceso.

Estos se utilizan para informar una lista de entradas de directorio a un llamador original, un archivo/directorio/enlace simbólico por callback. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de ninguna cadena.

Estos callbacks se utilizan, a partir de PhysicsFS 1.1, como una alternativa a las funciones que devolverían listas que necesitarían ser limpiadas con PHYSFS_freeList(). El callback significa que la biblioteca no necesita asignar una lista completa y todas las cadenas de antemano.

Ten en cuenta que el orden de los datos prometido en las versiones de lista no es necesariamente así en las versiones de callback. Consulta la documentación de las APIs específicas, pero es posible que las cadenas no estén ordenadas como esperas y podrías obtener cadenas duplicadas.

Parámetros

data Puntero a datos definidos por el usuario, pasado desde la API que finalmente llamó al callback.
origdir Una cadena que contiene la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio sobre el cual solicitaste la enumeración, pasado en el callback para tu conveniencia.
fname El nombre del archivo que se está enumerando. Puede que no esté en orden alfabético en comparación con otros callbacks que se hayan ejecutado, y no contendrá la ruta completa. Puedes recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

enum PHYSFS_ErrorCode

Valores que representan causas específicas de fallo. La mayoría de las veces, solo deberías preocuparte por si una operación dada falló o no, pero puede haber ocasiones en las que planees manejar un caso de fallo específico con gracia, así que proporcionamos códigos de error específicos.

La mayoría de estos errores son un poco vagos, y la mayoría no son cosas que puedas arreglar... si hay un error de permisos, por ejemplo, todo lo que realmente puedes hacer es pasar esa información al usuario y dejar que él decida cómo manejarlo. En la mayoría de estos casos, tu programa solo debería preocuparse de que no logró sus objetivos, y no preocuparse específicamente por qué.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Get a file listing of a search path's directory, using an application-defined callback, with errors reported. Internally, PHYSFS_enumerateFiles() just calls this function and then builds a list before returning to the application, so functionality is identical except for how the information is represented to the application.

Unlike PHYSFS_enumerateFiles(), this function does not return an array. Rather, it calls a function specified by the application once per element of the search path:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Items sent to the callback are not guaranteed to be in any order whatsoever. There is no sorting done at this level, and if you need that, you should probably use PHYSFS_enumerateFiles() instead, which guarantees alphabetical sorting. This form reports whatever is discovered in each archive before moving on to the next. Even within one archive, we can't guarantee what order it will discover data. Any sorting you find in these callbacks is just pure luck. Do not rely on it. As this walks the entire list of archives, you may receive duplicate filenames.

This API and the callbacks themselves are capable of reporting errors. Prior to this API, callbacks had to accept every enumerated item, even if they were only looking for a specific thing and wanted to stop after that, or had a serious error and couldn't alert anyone. Furthermore, if PhysicsFS itself had a problem (disk error or whatnot), it couldn't report it to the calling app, it would just have to skip items or stop enumerating outright, and the caller wouldn't know it had lost some data along the way.

Now the caller can be sure it got a complete data set, and its callback has control if it wants enumeration to stop early. See the documentation for PHYSFS_EnumerateCallback for details on how your callback should behave.

Parameters

dir Directory, in platform-independent notation, to enumerate.
c Callback function to notify about search path elements.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Añade un archivo o directorio a la ruta de búsqueda. Si es un duplicado, la entrada no se añade de nuevo, aunque la función tenga éxito. No puede añadir el mismo archivo a dos puntos de montaje diferentes: la comprobación de duplicados se realiza contra el archivo y no contra el punto de montaje.

Cuando monta un archivo, se añade a un sistema de archivos virtual... todos los archivos de todos los archivos se interpolan en un único árbol de archivos jerárquico. Dos archivos montados en el mismo lugar (o un archivo con archivos que se superponen con otro punto de montaje) pueden tener archivos superpuestos: en tal caso, se selecciona el archivo anterior en la ruta de búsqueda y los otros archivos son inaccesibles para la aplicación. Esto permite utilizar archivos para sobrescribir revisiones anteriores; puede usar el mecanismo de montaje para colocar archivos en un punto específico del árbol de archivos y evitar superposiciones; esto es útil para mods descargables que podrían pisar datos de la aplicación o entre sí, por ejemplo.

El punto de montaje no necesita existir antes de montarlo, lo cual es diferente de lo que pueden esperar aquellos familiarizados con el concepto de "montaje" de Unix. Además, se pueden montar varios archivos en el mismo punto de montaje, o los contenidos de puntos de montaje y archivos pueden superponerse... el mecanismo de interpolación sigue funcionando como de costumbre.

Se permite especificar un enlace simbólico a un archivo o directorio aquí, independientemente del estado de PHYSFS_permitSymbolicLinks(). Esa función solo se ocupa de los enlaces simbólicos dentro del directorio o archivo montado.

void PHYSFS_permitSymbolicLinks (int allow)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas físicos y archivados contienen archivos que son simplemente referencias a otros archivos. Al abrir un enlace simbólico en un sistema físico, este abrirá transparentemente el archivo al que se refiere.

Por defecto, PhysicsFS verificará si un archivo es realmente un enlace simbólico durante las llamadas de apertura y fallará si es así. De lo contrario, el enlace podría llevarte fuera de las rutas de lectura y escritura, poniendo en peligro la seguridad.

Si deseas asumir ese riesgo, llama a esta función con un valor distinto de cero. Ten en cuenta que esto es más para contenedores de programas que para lenguajes de scripting no confiables que intentan comprometer el sistema. Generalmente, un usuario podría tener una razón legítima para crear un enlace simbólico, así que no deberías permitirlo, a menos que sientas que hay un peligro específico.

Los enlaces simbólicos se verificarán explícitamente solo cuando se trabaje con nombres de archivo en notación independiente de plataforma. Es decir, cuando se establezcan tus rutas de búsqueda y escritura, etc., los enlaces simbólicos nunca se verificarán.

Nota: PHYSFS_stat() siempre verificará la ruta especificada; si esa ruta es un enlace simbólico, no la seguirá en ningún caso. Si no se permiten enlaces simbólicos a través de esta función, PHYSFS_stat() los ignorará y tratará la consulta como si la ruta no existiera.

La permisión de enlaces simbólicos se puede habilitar o deshabilitar en cualquier momento después de haber llamado PHYSFS_init(), y está deshabilitada por defecto.

Parámetros

allow distinto de cero para permitir enlaces simbólicos, cero para deshabilitar el enlace.

int PHYSFS_setRoot(const char *archive, const char *subdir)

int PHYSFS_utf8stricmp (const char * str1, const char * str2)

Compara dos cadenas en UTF-8 sin distinguir entre mayúsculas y minúsculas. Este es un reemplazo para strcasecmp/stricmp que espera que ambas cadenas estén en formato UTF-8. Realiza un "plegado de mayúsculas" para determinar si los códigos Unicode en las cadenas coinciden.

Si ambas cadenas son solo caracteres ASCII de bajo nivel, esto hará lo correcto, ya que también es UTF-8 válido. ¡Si hay algún carácter ASCII de alto nivel, esto no hará lo que esperas!

Informará cuál de las dos cadenas es "menor" que la otra, pero debes ser consciente de que esto no significa necesariamente nada: 'a' puede ser "menor que" 'b', pero un kuten japonés no tiene una relación alfabética significativa con un lambda griego, pero tener una asignación confiable de un "valor" permite que los algoritmos de ordenación sean posibles, aunque no sean completamente racionales. La mayoría de los casos deberían tratar el valor devuelto como "igual" o "no igual".

Al igual que stricmp, esta función espera que ambas cadenas estén terminadas en nulo.

str1 Cadena a comparar.
str2 Cadena a comparar.

Devuelve

-1 si str1 es "menor que" str2, 1 si es "mayor que", 0 si son iguales.

Convierte una cadena en UTF-8 a una cadena en UCS-2.

Advertencia

Casi con seguridad deberías usar PHYSFS_utf8ToUtf16(), que estuvo disponible en PhysicsFS 2.1, a menos que sepas lo que estás haciendo.

Esta función no informará un error si hay secuencias inválidas en la cadena de origen. Las reemplazará con un carácter '?' y continuará.

Las cadenas en UCS-2 son de 16 bits por carácter: TCHAR en Windows, cuando se compila con soporte de Unicode. void PHYSFS_utf8ToUtf16 (const char * src, PHYSFS_uint16 * dst, PHYSFS_uint64 len)

Convierte una cadena UTF-8 a una cadena UTF-16.

Advertencia

Esta función no informará de un error si hay secuencias UTF-8 inválidas en la cadena fuente. Las reemplazará con un carácter '?' y continuará.

Las cadenas UTF-16 tienen 16 bits por carácter (excepto algunos caracteres, que tienen 32 bits): TCHAR en Windows, cuando se compila con soporte Unicode. Las versiones modernas de Windows usan UTF-16. Las versiones de Windows anteriores a 2000 usaban TCHAR, pero solo manejaban UCS-2. UTF-16 *es* UCS-2, excepto para los caracteres que tienen 4 bytes, que de todos modos no son representables en UCS-2. Si no estás seguro, deberías estar usando UTF-16 en este momento en Windows.

Para asegurar que el búfer de destino sea lo suficientemente grande para la conversión, por favor, asigna un búfer que sea el doble del tamaño del búfer fuente. UTF-8 usa de uno a cuatro bytes por carácter, pero UTF-16 siempre usa de dos a cuatro, ¡así que una cadena completamente ASCII de bajo nivel duplicará su tamaño! Las cadenas que no caben en el búfer de destino serán truncadas, pero siempre estarán terminadas en nulo y nunca tendrán un par sustituto UTF-16 incompleto al final. Si la longitud del búfer es 0, esta función no hace nada.

PHYSFS_sint64 PHYSFS_writeBytes (PHYSFS_File * handle, const void * buffer, PHYSFS_uint64 len)

Escribe datos en un manejador de archivo PhysicsFS. El archivo debe estar abierto para escritura.

Por favor, ten en cuenta que aunque (len) es un entero sin signo de 64 bits, estás limitado a 63 bits (9223372036854775807 bytes), por lo que podemos devolver un valor negativo en caso de error.
