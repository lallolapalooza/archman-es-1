1.0 API compatibility define. PHYSFS_file is identical to PHYSFS_File. This #define is here for backwards compatibility with the 1.0 API, which had an inconsistent capitalization convention in this case. New code should use PHYSFS_File, as this #define may go away someday.

    (x)->minor = PHYSFS_VER_MINOR; \
    (x)->patch = PHYSFS_VER_PATCH; \

Macro to determine PhysicsFS version program was compiled against. This macro fills in a PHYSFS_Version structur

con la versión de la biblioteca con la que compiló. Esto se determina por qué encabezado utiliza el compilador. Tenga en cuenta que si vinculó la biblioteca dinámicamente, puede tener una versión ligeramente más nueva o más antigua en tiempo de ejecución. Esa versión se puede determinar con PHYSFS_getLinkedVersion(), que, a diferencia de PHYSFS_VERSION, no es una macro.

PHYSFS_enumerate

Esto es lo mismo que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, excepto que puede devolver un resultado de la devolución de llamada: a saber: si está buscando algo específico, una vez que lo encuentra, puede indicar a PhysicsFS que deje de enumerar más. Esto se usa con PHYSFS_enumerate(), que esperamos que hayamos hecho bien esta vez. :)

Parámetros

data Puntero a datos definido por el usuario, pasado desde la API que finalmente llamó a la devolución de llamada.
origdir Una cadena que contiene la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio sobre el que solicitó la enumeración, pasado en la devolución de llamada para su conveniencia.
fname El nombre del archivo que se está enumerando. Puede que no esté en orden alfabético en comparación con otras devoluciones de llamada que se han activado, y no contendrá la ruta completa. Puede recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

Devuelve

Un valor de PHYSFS_EnumerateCallbackResult. Todos los demás valores están (actualmente) indefinidos; no los use.

typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Firma de la función para devoluciones de llamada que enumeran archivos.

Advertencia

A partir de PhysicsFS 2.1, use PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; le da más control sobre el proceso.

Estos se utilizan para informar una lista de entradas de directorio a un llamador original, un archivo/directorio/enlace simbólico por devolución de llamada. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de ninguna cadena.

Estas devoluciones de llamada se utilizan, a partir de PhysicsFS 1.1, como una alternativa a las funciones que devolverían listas que deben limpiarse con PHYSFS_freeList(). La devolución de llamada significa que la biblioteca no necesita asignar una lista completa y todas las cadenas por adelantado.

Tenga en cuenta que el orden de los datos prometido en las versiones de lista no es necesariamente así en las versiones de devolución de llamada. Consulte la documentación de las API específicas, pero es posible que las cadenas no estén ordenadas como espera y que reciba cadenas duplicadas.

fname El nombre del archivo que se está enumerando. Puede que no esté en orden alfabético en comparación con otras devoluciones de llamada que se han activado, y no contendrá la ruta completa. Puede recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

int PHYSFS_deinit (void )

Desinicializa la biblioteca PhysicsFS. Esto cierra todos los archivos abiertos a través de PhysicsFS, vacía las rutas de búsqueda/escritura, libera memoria e invalida todos tus manejadores de archivo.

Ten en cuenta que esta llamada puede FALLAR si hay un archivo abierto para escritura que se niega a cerrarse (por ejemplo, el sistema operativo subyacente estaba almacenando en búfer escrituras a un sistema de archivos de red, y el servidor de archivos se ha caído, o ha fallado un disco duro, etc.). Generalmente es mejor cerrar todos los manejadores de escritura tú mismo antes de llamar a esta función, para poder manejar graciosamente un fallo específico.

Una vez desinicializado correctamente, se puede volver a llamar a PHYSFS_init() para reiniciar el subsistema. Todos los estados predeterminados de la API se restauran en este punto, con la excepción de cualquier asignador personalizado que puedas haber especificado, el cual sobrevive entre inicializaciones.

Devoluciones

distinto de cero si tiene éxito, cero si hay un error. Los detalles del error se pueden obtener de PHYSFS_getLastError(). Si falla, el estado de PhysFS es indefinido y probablemente esté muy dañado.

Elimina un archivo o directorio. (filename) se especifica en notación independiente de la plataforma en relación con el directorio de escritura.

Un directorio debe estar vacío antes de que esta llamada pueda eliminarlo.

La eliminación de un symlink eliminará el enlace, no lo que apunta, independientemente de si "permitirSymLinks" está activado o no.

Así que si tienes el directorio de escritura establecido en "C:\mygame\writedir" y llamas a PHYSFS_delete("downloads/maps/level1.map"), entonces el archivo "C:\mygame\writedir\downloads\maps\level1.map" se elimina del sistema de archivos físico, si existe y el sistema operativo permite la eliminación.

Lo más probable es que los bits que componen el archivo aún existan, simplemente se ponen a disposición para ser sobrescritos más tarde. No lo consideres un método de seguridad ni nada parecido. :)

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtener una lista de archivos de la carpeta de un camino de búsqueda, usando una callback definida por el aplicador, con errores reportados. Internamente, PHYSFS_enumerateFiles() solo llama a esta función y luego construye una lista antes de devolver a la aplicación, así que la funcionalidad es idéntica, a menos de cómo la información se representa a la aplicación.

A diferencia de PHYSFS_enumerateFiles(), esta función no devuelve un arreglo. En lugar de eso, llama a una función especificada por el aplicador una vez por cada elemento del camino de búsqueda:

static physfs_EnumResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // me da más datos, por favor.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Los elementos enviados a la callback no están garantizados de estar en ningún orden. No se realiza ningún ordenamiento en este nivel, y si lo necesitas, deberías usar PHYSFS_enumerateFiles(), que garantiza el orden alfabético. Esta forma reporta lo que encuentra en cada archive antes de moverse al siguiente. Even though within one archive, we can't guarantee the order in which data is discovered. Cualquier orden que encuentres en estas callbacks es pura suerte. No dejes de confiar en ello. Como esta camina por toda la lista de archivados, podrías recibir nombres de archivos duplicados.

Esta API y las callbacks mismas pueden reportar errores. Antes de esta API, las callbacks tenían que aceptar cada elemento enumerado, incluso si solo buscaban un objeto específico y querían detenerse después de eso, o si había un error serio y no podían notificar a nadie. Además, si PhysicsFS mismo tenía un problema (error de disco, etc.), no podía reportarlo a la aplicación, simplemente se podría saltar los elementos o dejar de enumerar, y el llamador no sabría que había perdido algunos datos durante el camino.

Ahora el llamador puede estar seguro de que obtuvo un conjunto completo de datos, y si quiere detener la enumeración temprano, su callback tendrá control. Ve la documentación para PHYSFS_EnumerateCallback para detalles de cómo debe comportarse tu callback.

Parámetros

dir Carpeta a enumerar en notación independiente del sistema de archivos.
c Función de callback para notificar sobre elementos de camino.
d Datos definidos por el aplicador que se pasa a la callback. Puede ser NULL.

Retorno

No cero si es exitoso, cero si falla. Usa PHYSFS_getLastErrorCode() para obtener el error específico. Si el callback devuelve PHYSFS_ENUM_STOP, esto se considera exitoso. Callbacks devolviendo PHYSFS_ENUM_ERROR harán esta función retornar cero y establecerá el código de error como PHYSFS_ERR_APP_CALLBACK.

char ** PHYSFS_enumerateFiles (const char * dir)

Obtener una lista de archivos de una carpeta de un camino de búsqueda.

Advertencia

En versiones de PhysicsFS anteriores a 2.1, esta función devolvería tantos elementos como pudiera en caso de falla (error de memoria, error de I/O del disco, etc). Como resultado, los aplicadores no podían distinguir entre éxito completo y fracaso parcial, y ya que la función podía devolver NULL para reportar fallos catastróficos, en PhysicsFS 2.1 esta política cambió: devolverá una lista completa de resultados o NULL en caso de cualquier fallo, así podemos garantizar que la enumeración se completó y no hay huecos en sus resultados.

Las carpetas que se coincidan se interpolan. Es decir, si "C:\mydir" está en el camino de búsqueda y contiene una carpeta "savegames" que contiene "x.sav", "y.sav" y "z.sav", y también hay una "C:\userdir" en el camino de búsqueda que tiene una subcarpeta "savegames" con "w.sav", entonces el siguiente código:

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);
PHYSFS_freeList(rc);
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav].

Puedes ordenar la lista como quieras. Sin embargo, los datos devueltos nunca contendrán duplicados, y siempre estarán ordenados alfabéticamente (o más bien, en orden Unicode sensible a mayúsculas y minúsculas) para ti.

No olvides llamar a PHYSFS_freeList() con el valor devuelto por esta función cuando hayas terminado con él.

Parámetros

dir Carpeta a enumerar en notación independiente del sistema de archivos.

Retorno

Array de strings terminado en NULL, o NULL en caso de fallo.

Obtiene información de error legible por humanos.

Obsoleto

Usa PHYSFS_getLastErrorCode() y PHYSFS_getErrorByCode() en su lugar.

Advertencia

A partir de PhysicsFS 2.1, esta función ha sido limitada. Antes de PhysicsFS 2.1, esta función era la única forma de obtener detalles de error más allá del valor de retorno básico de una función dada. Se suponía que era una cadena legible por humanos en uno de varios idiomas, y no era útil para el análisis de aplicaciones. Esto fue un problema, ya que el desarrollador y no el usuario elegía el idioma en tiempo de compilación, y los mantenedores de PhysicsFS tenían que mantener (mal) una cantidad significativa de trabajo de localización. La aplicación no podía analizar las cadenas, incluso si contaban con un idioma específico, ya que algunas se generaban dinámicamente. Obtiene el último mensaje de error de PhysicsFS como una cadena legible por humanos y terminada en NULL. Devolverá NULL si no ha habido ningún error desde la última llamada a esta función. El puntero devuelto por esta llamada apunta a un búfer interno. Cada hilo tiene un estado de error único asociado con él, pero cada vez que se establece un nuevo mensaje de error, sobrescribirá el anterior asociado con ese hilo. Es seguro llamar a esta función en cualquier momento, incluso antes de PHYSFS_init().

En general, las aplicaciones solo deberían preocuparse por si una función dada falló; sin embargo, si tu código requiere más detalles específicos, debes usar PHYSFS_getLastErrorCode() en lugar de esta función.

int PHYSFS_mount(const char *newDir, const char *mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

mountPoint Location in the interpolated tree that this archive will be "mounted", in platform-independent notation. NULL or "" is equivalent to "/".
appendToPath nonzero to append to search path, zero to prepend.

Agrega un archivo, contenido en un manejador de PHYSFS_File, a la ruta de búsqueda.

Advertencia

A menos que tenga alguna necesidad especial de bajo nivel, debería usar PHYSFS_mount() en lugar de esto.

¡Los archivos dentro de archivos pueden ser muy lentos! Si bien un PHYSFS_File puede buscar incluso cuando los datos están comprimidos, puede hacerlo rebobinando hasta el principio y descomprimiendo todo antes del punto de búsqueda. El uso normal de archivos puede realizar muchas búsquedas en segundo plano. Como tal, puede encontrar que el uso normal de archivos es extremadamente doloroso si se monta de esta manera. Planifique en consecuencia: si, por ejemplo, tiene un archivo .zip autoextraíble y desea montar algo dentro de él, comprima el contenido del archivo interno y asegúrese de que el archivo .zip externo no comprima también el archivo interno.

Esta función opera igual que PHYSFS_mount(), pero toma un manejador de PHYSFS_File en lugar de una ruta de archivo. Este manejador contiene todos los datos del archivo y se utiliza en lugar de un archivo real en el sistema de archivos físico. El PHYSFS_File puede estar respaldado por un archivo real en el sistema de archivos físico, pero no necesariamente. El uso más popular para esto es probablemente montar archivos almacenados dentro de otros archivos.

(newDir) debe ser una cadena única para identificar este archivo. Se utiliza para optimizar la selección del archivero (si lo nombra XXXXX.zip, podríamos intentar primero el archivero ZIP, por ejemplo, o elegir directamente un archivero que solo pueda confiar en que los datos son válidos por extensión de nombre de archivo). No necesita referirse a un archivo real en absoluto. Si la extensión del nombre del archivo no es útil, el sistema intentará con todos los archiveros hasta que uno funcione o ninguno de ellos lo haga. Este nombre de archivo debe ser único, ya que el sistema no le permitirá tener dos archivos con el mismo nombre.

void PHYSFS_permitSymbolicLinks (int allow)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y archivos contienen archivos que son solo punteros a otros archivos. En el sistema de archivos físico, abrir un enlace de este tipo abrirá (transparente) el archivo al que apunta.

Por defecto, PhysicsFS comprobará si un archivo es realmente un enlace simbólico durante las llamadas de apertura y fallará si lo es. De lo contrario, el enlace podría sacarte de las rutas de escritura y búsqueda, y comprometer la seguridad.

Si quieres asumir ese riesgo, llama a esta función con un parámetro distinto de cero. Ten en cuenta que esto es más para aislar el lenguaje de scripting de un programa, en caso de que scripts no confiables intenten comprometer el sistema. En términos generales, un usuario podría tener una razón legítima para configurar un enlace simbólico, por lo que, a menos que sientas que hay un peligro específico al permitirlos, deberías permitirlos.

Los enlaces simbólicos solo se comprueban explícitamente cuando se tratan nombres de archivo en notación independiente de la plataforma. Es decir, al configurar tus rutas de búsqueda y escritura, etc., nunca se comprueban los enlaces simbólicos.

Ten en cuenta que PHYSFS_stat() siempre comprobará la ruta especificada; si esa ruta es un enlace simbólico, no se seguirá en ningún caso. Si los enlaces simbólicos no están permitidos a través de esta función, PHYSFS_stat() los ignora y trataría la consulta como si la ruta no existiera en absoluto.

El permiso de enlaces simbólicos se puede habilitar o deshabilitar en cualquier momento después de haber llamado a PHYSFS_init(), y está deshabilitado por defecto.

Set the buffering mode for a file handle.

If bufsize is zero, any existing buffer will be freed, and the file will be unbuffered. If bufsize is non-zero, a buffer of that size will be allocated (or reallocated if one already exists). The file will be flushed before the buffer is resized or freed.

PhysicsFS file handles are unbuffered by default.

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convierte una cadena UTF-8 a una cadena Latin1. Las cadenas Latin1 tienen 8 bits por carácter: una codificación popular de "ASCII alto".

Para asegurarse de que el búfer de destino sea lo suficientemente grande para la conversión, asigne un búfer que sea el doble del tamaño del búfer de origen. UTF-8 expande los puntos de código latin1 mayores de 127 de 1 a 2 bytes, por lo que la cadena puede crecer en algunos casos.

Las cadenas que no quepan en el búfer de destino se truncarán, pero siempre estarán terminadas en nulo y nunca tendrán una secuencia UTF-8 incompleta al final. Si la longitud del búfer es 0, esta función no hace nada.

Tenga en cuenta que no proporcionamos un conversor de UTF-8 a Latin1, ya que Latin1 no puede expresar la mayoría de los puntos de código Unicode. Es una codificación heredada; debe alejarse de ella en todo momento.

Parámetros

src Cadena de origen terminada en nulo en formato Latin1.
dst Búfer para almacenar la cadena UTF-8 convertida.
len Tamaño, en bytes, del búfer de destino.

NAME

PHYSFS_writeUBE16, PHYSFS_writeUBE32, PHYSFS_writeUBE64, PHYSFS_writeULE16, PHYSFS_writeULE32, PHYSFS_writeULE64 - write data in platform-independent endianness.

SYNOPSIS

#include <physfs.h>
int PHYSFS_writeUBE16(PHYSFS_File *file, PHYSFS_uint16 val);
int PHYSFS_writeUBE32(PHYSFS_File *file, PHYSFS_uint32 val);
int PHYSFS_writeUBE64(PHYSFS_File *file, PHYSFS_uint64 val);
int PHYSFS_writeULE16(PHYSFS_File *file, PHYSFS_uint16 val);
int PHYSFS_writeULE32(PHYSFS_File *file, PHYSFS_uint32 val);
int PHYSFS_writeULE64(PHYSFS_File *file, PHYSFS_uint64 val);

Detailed Description

These functions are convenience functions for writing primitive numeric types to a PHYSFS_File. They convert the value from the platform's native byte order to the specified endianness (big-endian or little-endian) and then write it to the file.

On failure, you can find out what went wrong from PHYSFS_getLastErrorCode().
