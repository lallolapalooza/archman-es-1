DESCRIPTION

The PhysicsFS library provides a platform-independent interface for accessing data files. It can read data from regular directories, zip archives, and other archive formats. It can also write data to regular directories.

This library is designed to be used by games and other applications that need to manage large numbers of data files. It simplifies the process of reading and writing files, and it provides a consistent interface across different platforms.

The library supports the following features:

  • Mounting multiple archives and directories.
  • Reading files from any mounted archive or directory.
  • Writing files to regular directories.
  • Support for various archive formats (e.g., zip, tar).
  • Platform-independent file access.
  • Unicode support.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Get a file listing of a search path's directory, using an application-defined callback, with errors reported. Internally, PHYSFS_enumerateFiles() just calls this function and then builds a list before returning to the application, so functionality is identical except for how the information is represented to the application.

Unlike PHYSFS_enumerateFiles(), this function does not return an array. Rather, it calls a function specified by the application once per element of the search path:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Items sent to the callback are not guaranteed to be in any order whatsoever. There is no sorting done at this level, and if you need that, you should probably use PHYSFS_enumerateFiles() instead, which guarantees alphabetical sorting. This form reports whatever is discovered in each archive before moving on to the next. Even within one archive, we can't guarantee what order it will discover data. Any sorting you find in these callbacks is just pure luck. Do not rely on it. As this walks the entire list of archives, you may receive duplicate filenames.

This API and the callbacks themselves are capable of reporting errors. Prior to this API, callbacks had to accept every enumerated item, even if they were only looking for a specific thing and wanted to stop after that, or had a serious error and couldn't alert anyone. Furthermore, if PhysicsFS itself had a problem (disk error or whatnot), it couldn't report it to the calling app, it would just have to skip items or stop enumerating outright, and the caller wouldn't know it had lost some data along the way.

Now the caller can be sure it got a complete data set, and its callback has control if it wants enumeration to stop early. See the documentation for PHYSFS_EnumerateCallback for details on how your callback should behave.

Parameters

dir Directory, in platform-independent notation, to enumerate.
c Callback function to notify about search path elements.
d Application-defined data passed to callback. Can be NULL.

Returns

non-zero on success, zero on failure. Use PHYSFS_getLastErrorCode() to obtain the specific error. If the callback returns PHYSFS_ENUM_STOP to stop early, this will be considered success. Callbacks returning PHYSFS_ENUM_ERROR will make this function return zero and set the error code to PHYSFS_ERR_APP_CALLBACK.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Agrega un archivo o directorio a la ruta de búsqueda. Si es un duplicado, la entrada no se agrega de nuevo, a pesar de que la función tiene éxito. No puede agregar el mismo archivo a dos puntos de montaje diferentes: la verificación de duplicados se realiza contra el archivo y no contra el punto de montaje.

Cuando monta un archivo, se agrega a un sistema de archivos virtual... todos los archivos en todos los archivos se interpolan en un único árbol de archivos jerárquico. Dos archivos montados en el mismo lugar (o un archivo con archivos que se superponen con otro punto de montaje) pueden tener archivos superpuestos: en tal caso, se selecciona el archivo anterior en la ruta de búsqueda y los otros archivos son inaccesibles para la aplicación. Esto permite que los archivos se utilicen para anular revisiones anteriores; puede utilizar el mecanismo de montaje para colocar archivos en un punto específico del árbol de archivos y evitar la superposición; esto es útil para modificaciones descargables que podrían pisotear los datos de la aplicación o entre sí, por ejemplo.

El punto de montaje no necesita existir antes de montar, lo que es diferente de lo que aquellos familiarizados con el concepto de "montar" de Unix pueden esperar. Además, se pueden montar varios archivos en el mismo punto de montaje, o los puntos de montaje y el contenido de los archivos pueden superponerse... el mecanismo de interpolación sigue funcionando como de costumbre.

Se permite especificar un enlace simbólico a un archivo o directorio aquí, independientemente del estado de PHYSFS_permitSymbolicLinks(). Esa función solo se ocupa de enlaces simbólicos dentro del directorio o archivo montado.

void PHYSFS_permitSymbolicLinks (int allow)

Activa o desactiva el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y archivados contienen archivos que son simplemente referencias a otros archivos. Al abrir un enlace simbólico físico, se abrirá transparentemente el archivo al que se refiere.

Por defecto, PhysicsFS verificará si un archivo es realmente un enlace simbólico durante las llamadas de abrir y fallará si es así. En cambio, el enlace podría llevarte fuera de los caminos de lectura y escritura, comprometiendo la seguridad.

Si deseas tomar ese riesgo, llama a esta función con un valor no cero. Nota que esto es más para sandboxear el lenguaje de scripting del programa, en caso de que scripts no confiados intenten comprometer el sistema. Generalmente, un usuario podría tener una razón legítima para crear un enlace simbólico, por lo que no deberías desactivarlo, a menos que te sientas que hay un riesgo específico en permitirlo.

Los enlaces simbólicos se verifican solo cuando se esté trabajando con nombres de archivos en notación independiente de plataforma. Es decir, cuando se establezca tu ruta de búsqueda y la ruta de escritura, etc., los enlaces simbólicos nunca se verifican.

Nota importante: PHYSFS_stat() siempre verifica el camino especificado; si ese camino es un enlace simbólico, se lo omitirá en cualquier caso. Si los enlaces simbólicos no son permitidos a través de esta función, PHYSFS_stat() los ignora y trataría la consulta como si el camino no existiera.

El permiso de enlaces simbólicos puede ser activado o desactivado en cualquier momento después de haber llamado PHYSFS_init(), y está desactivado por defecto.

Parámetros

allow no cero para permitir enlaces simbólicos, cero para desactivar el enlace.

int PHYSFS_setAllocator (const PHYSFS_Allocator * allocator)

Establece tus propias rutinas de asignación en PhysicsFS. (Esto es para uso limitado y avanzado. Si no ves inmediatamente una necesidad para ello, puedes ignorarlo para siempre).

Por defecto, PhysicsFS utilizará lo que sea razonable para la gestión de memoria dinámica en una plataforma (generalmente malloc/realloc/free, pero algunos sistemas podrían usar algo diferente). La rutina se mantiene intacta entre llamadas de desinicialización/inicialización. Si deseas volver a utilizar la rutina predeterminada de la plataforma, pasa NULL aquí.

Si no estás seguro de qué hacer con esta función, puedes ignorarla por completo.

allocator Una estructura que contiene los puntos de entrada de tu rutina de asignación.

Para asegurar que el búfer de destino sea lo suficientemente grande para la conversión, por favor, asigna un búfer que sea el doble del tamaño del búfer de origen. UTF-8 expande los puntos de código latin1 mayores a 127 de 1 a 2 bytes, por lo que la cadena puede crecer en algunos casos.

Por favor, ten en cuenta que no proporcionamos un conversor de UTF-8 a Latin1, ya que Latin1 no puede expresar la mayoría de los puntos de código Unicode. Es una codificación heredada; deberías estar convirtiendo lejos de ella en todo momento.

Esta función no reportará un error si hay secuencias de UTF-8 inválidas en la cadena de entrada. Las reemplazará con un '?' y continuará.

Las cadenas UTF-16 tienen 16 bits por carácter (a menos que algunos caracteres sean de 32 bits): TCHAR en Windows, cuando se compila con soporte Unicode. Las versiones modernas de Windows usan UTF-16. Las versiones antiguas de Windows (anteriores a 2000) usaban TCHAR, pero solo manejaron UCS-2. UTF-16 *es* UCS-2, a menos que los caracteres que ocupan 4 bytes no puedan ser representados en UCS-2. Si no estás seguro, deberías estar usando UTF-16 en Windows.

Para asegurar que el buffer de destino sea suficientemente grande para la conversión, por favor asigna un buffer que sea el doble del tamaño del buffer de entrada. UTF-8 usa de 1 a 4 bytes por carácter, pero UTF-16 usa siempre de 2 a 4 bytes, por lo que una cadena ASCII completamente baja duplicará su tamaño. Los caracteres UTF-16 que necesitan 4 bytes también ocupan 4 bytes en UTF-8, por lo que no necesitas asignar el 4x el espacio, solo duplicar.

Las cadenas que no caben en el buffer de destino se truncarán, pero siempre se terminarán con cero y nunca tendrán un par de sustitución UTF-16 incompleto al final. Si el tamaño del buffer es 0, esta función no hace nada.

Parámetros

src Cadena de entrada terminada en nulo de UTF-8.
dst Buffer para almacenar la cadena UTF-16 convertida.
len Tamaño en bytes del buffer de destino.

PHYSFS_sint64 PHYSFS_writeBytes (PHYSFS_File * handle, const void * buffer, PHYSFS_uint64 len)

Escribe datos en un archivo PhysicsFS. El archivo debe estar abierto para escritura.

Nota: aunque (len) es un entero sin signo de 64 bits, estás limitado a 63 bits (9223372036854775807 bytes), por lo que podrías devolver un valor negativo en caso de error. Si la longitud es mayor que 0x7FFFFFFFFFFFFFFF, esta función fallará inmediatamente. Para sistemas sin tipos de 64 bits, estás limitado a 31 bits (0x7FFFFFFF, o 2147483647 bytes). Confiamos en que no se necesitarán múltiples gigabytes de E/S en una sola llamada, pero ¿por qué limitar las cosas?

Parámetros

buffer Buffer de (len) bytes para escribir (handle).

Devoluciones

Número de bytes escritos. Esto puede ser menor que (len); en caso de error, el sistema podría intentar escribir tantos bytes como sea posible, por lo que podría ocurrir una escritura incompleta.
