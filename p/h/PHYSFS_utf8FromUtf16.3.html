You can find function prototypes and documentation for all of the library's functions within this header file.

This is the same thing as PHYSFS_EnumFilesCallback from PhysicsFS 2.0, except it can return a result from the callback: namely: if you're looking for something specific, once you find it, you can tell PhysicsFS to stop enumerating further. Parameters

typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Function signature for callbacks that enumerate files.

Warning

As of PhysicsFS 2.1, Use PHYSFS_EnumerateCallback with PHYSFS_enumerate() instead; it gives you more control over the process.

These are used to report a list of directory entries to an original caller, one file/dir/symlink per callback. All strings are UTF-8 encoded. Functions should not try to modify or free any string's memory.

These callbacks are used, starting in PhysicsFS 1.1, as an alternative to functions that would return lists that need to be cleaned up with PHYSFS_freeList(). The callback means that the library doesn't need to allocate an entire list and all the strings up front.

Be aware that promised data ordering in the list versions are not necessarily so in the callback versions. Check the documentation on specific APIs, but strings may not be sorted as you expect and you might get duplicate strings.

Parameters

data User-defined data pointer, passed through from the API that eventually called the callback.
origdir A string containing the full path, in platform-independent notation, of the directory containing this file. In most cases, this is the directory on which you requested enumeration, passed in the callback for your convenience.
fname The filename that is being enumerated. It may not be in alphabetical order compared to other callbacks that have fired, and it will not contain the full path. You can recreate the fullpath with $origdir/$fname ... The file can be a subdirectory, a file, a symlink, etc.

enum PHYSFS_ErrorCode

Values that represent specific causes of failure. Most of the time, you should only concern yourself with whether a given operation failed or not, but there may be occasions where you plan to handle a specific failure case gracefully, so we provide specific error codes.

Most of these errors are a little vague, and most aren't things you can fix...if there's a permission error, for example, all you can really do is pass that information on to the user and let them figure out how to handle it. In most these cases, your program should only care that it failed to accomplish its goals, and not care specifically why.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Get a file listing of a search path's directory, using an application-defined callback, with errors reported. Internally, PHYSFS_enumerateFiles() just calls this function and then builds a list before returning to the application, so functionality is identical except for how the information is represented to the application.

Unlike PHYSFS_enumerateFiles(), this function does not return an array. Rather, it calls a function specified by the application once per element of the search path:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Items sent to the callback are not guaranteed to be in any order whatsoever. There is no sorting done at this level, and if you need that, you should probably use PHYSFS_enumerateFiles() instead, which guarantees alphabetical sorting. This form reports whatever is discovered in each archive before moving on to the next. Even within one archive, we can't guarantee what order it will discover data. Any sorting you find in these callbacks is just pure luck. Do not rely on it. As this walks the entire list of archives, you may receive duplicate filenames.

This API and the callbacks themselves are capable of reporting errors. Prior to this API, callbacks had to accept every enumerated item, even if they were only looking for a specific thing and wanted to stop after that, or had a serious error and couldn't alert anyone. Furthermore, if PhysicsFS itself had a problem (disk error or whatnot), it couldn't report it to the calling app, it would just have to skip items or stop enumerating outright, and the caller wouldn't know it had lost some data along the way.

Now the caller can be sure it got a complete data set, and its callback has control if it wants enumeration to stop early. See the documentation for PHYSFS_EnumerateCallback for details on how your callback should behave.

Parameters

dir Directory, in platform-independent notation, to enumerate.
c Callback function to notify about search path elements.
d Application-defined data passed to callback. Can be NULL.

Returns

non-zero on success, zero on failure. Use PHYSFS_getLastErrorCode() to obtain the specific error. If the callback returns PHYSFS_ENUM_STOP to stop early, this will be considered success. Callbacks returning PHYSFS_ENUM_ERROR will make this function return zero and set the error code to PHYSFS_ERR_APP_CALLBACK.

char ** PHYSFS_enumerateFiles (const char * dir)

Get a file listing of a search path's directory.

Warning

In PhysicsFS versions prior to 2.1, this function would return as many items as it could in the face of a failure condition (out of memory, disk i/o error, etc). int PHYSFS_getLastErrorCode (void )

Get the last error code.

This function returns an integer that represents the last error that occurred. This value is specific to the thread that called it.

Note that PHYSFS_getLastErrorCode() and PHYSFS_getErrorByCode() are related, but *not* the same. One is a functions that returns the last error code, the other is a function that translates a code into a human-readable string.

Warning

Both PHYSFS_getLastErrorCode() and PHYSFS_getErrorByCode() reset the same thread-specific error state. Calling one will wipe out the other's data. If you need both, call PHYSFS_getLastErrorCode(), then pass that value to PHYSFS_getErrorByCode().

Generally, applications should only concern themselves with whether a given function failed; however, if you require more specifics, you can try this function to glean information, if there's some specific problem you're expecting and plan to handle. But with most things that involve file systems, the best course of action is usually to give up, report the problem to the user, and let them figure out what should be done about it. For that, you might prefer PHYSFS_getErrorByCode() instead.

Enumeration value that represents last reported error.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Agrega un archivo o directorio a la ruta de búsqueda. Si es un duplicado, la entrada no se agrega de nuevo, aunque la función tenga éxito. No puede agregar el mismo archivo a dos puntos de montaje diferentes: la comprobación de duplicados se realiza contra el archivo y no contra el punto de montaje.

Cuando monta un archivo, se agrega a un sistema de archivos virtual... todos los archivos en todos los archivos se interpolan en un único árbol de archivos jerárquico. Dos archivos montados en el mismo lugar (o un archivo con archivos que se superponen con otro punto de montaje) pueden tener archivos superpuestos: en tal caso, se selecciona el archivo que aparece antes en la ruta de búsqueda, y los otros archivos son inaccesibles para la aplicación. Esto permite que los archivos se utilicen para anular revisiones anteriores; puede utilizar el mecanismo de montaje para colocar archivos en un punto específico del árbol de archivos y evitar la superposición; esto es útil para mods descargables que podrían pisotear datos de la aplicación o entre sí, por ejemplo.

El punto de montaje no necesita existir antes de montarlo, lo cual es diferente de lo que pueden esperar quienes están familiarizados con el concepto de "montaje" de Unix. Además, se puede montar más de un archivo en el mismo punto de montaje, o los puntos de montaje y el contenido de los archivos pueden superponerse... el mecanismo de interpolación sigue funcionando como de costumbre.

Se permite especificar un enlace simbólico a un archivo o directorio aquí, independientemente del estado de PHYSFS_permitSymbolicLinks(). Esa función solo se ocupa de los enlaces simbólicos dentro del directorio o archivo montado.

appendToPath distinto de cero para agregar a la ruta de búsqueda, cero para anteponer.

Por defecto, PhysicsFS verificará si un archivo es realmente un enlace simbólico durante las llamadas de apertura y fallará si lo es. De lo contrario, el enlace podría sacarte de las rutas de escritura y de búsqueda, y comprometer la seguridad.

Si quieres asumir ese riesgo, llama a esta función con un parámetro distinto de cero. Ten en cuenta que esto es más para aislar el lenguaje de script de un programa, en caso de que scripts no confiables intenten comprometer el sistema. En términos generales, un usuario podría tener una razón legítima para configurar un enlace simbólico, por lo que, a menos que sientas que hay un peligro específico en permitirlos, deberías permitirlos.

Los enlaces simbólicos solo se verifican explícitamente cuando se trata con nombres de archivo en notación independiente de la plataforma. Es decir, al configurar tus rutas de búsqueda y escritura, etc., nunca se verifican los enlaces simbólicos.

Por favor, ten en cuenta que PHYSFS_stat() siempre verificará la ruta especificada; si esa ruta es un enlace simbólico, no se seguirá en ningún caso. Si los enlaces simbólicos no están permitidos a través de esta función, PHYSFS_stat() los ignora y trataría la consulta como si la ruta no existiera en absoluto.

El permiso de enlace simbólico se puede habilitar o deshabilitar en cualquier momento después de haber llamado a PHYSFS_init(), y está deshabilitado por defecto.

allow distinto de cero para permitir enlaces simbólicos, cero para denegar enlaces.

The write dir will be set to the pref dir returned by

, which is created if it doesn't exist.

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convierte una cadena UTF-8 a una cadena Latin1. Las cadenas Latin1 tienen 8 bits por carácter: una codificación popular de "ASCII alto".

Para asegurar que el búfer de destino sea lo suficientemente grande para la conversión, por favor, asigna un búfer que sea el doble del tamaño del búfer de origen. UTF-8 expande los puntos de código de latin1 mayores de 127 de 1 a 2 bytes, por lo que la cadena puede crecer en algunos casos.

Las cadenas que no quepan en el búfer de destino serán truncadas, pero siempre estarán terminadas en nulo y nunca tendrán una secuencia UTF-8 incompleta al final. Si la longitud del búfer es 0, esta función no hace nada.

Por favor, ten en cuenta que no proporcionamos un conversor de UTF-8 a Latin1, ya que Latin1 no puede expresar la mayoría de los puntos de código Unicode. Es una codificación heredada; deberías alejarte de ella en todo momento.

Parámetros

src Cadena de origen terminada en nulo en formato Latin1.
dst Búfer para almacenar la cadena UTF-8 convertida.
len Tamaño, en bytes, del búfer de destino.

void PHYSFS_utf8FromUtf16 (const PHYSFS_uint16 * src, char * dst, PHYSFS_uint64 len)

Advertencia

Esta función no informará de un error si hay secuencias UTF-16 inválidas en la cadena de origen. Las reemplazará con un carácter '?' y continuará.

Las cadenas UTF-16 tienen 16 bits por carácter (excepto algunos caracteres, que tienen 32 bits): TCHAR en Windows, cuando se compila con soporte Unicode. Las versiones modernas de Windows utilizan UTF-16. Las versiones de Windows anteriores al 2000 utilizaban TCHAR, pero solo manejaban UCS-2. Para asegurar que el búfer de destino sea lo suficientemente grande para la conversión, por favor, asigna un búfer que sea el doble del tamaño del búfer de origen. UTF-8 nunca usa más de 32 bits por carácter, por lo que aunque puede reducir una cadena UTF-16, también puede expandirla.

Convertir una cadena UTF-8 en una cadena UTF-16.

Advertencia

Esta función no reportará un error si hay secuencias de UTF-8 inválidas en la cadena de entrada. Reemplazará las mismas con un carácter '?' y continuará.

PHYSFS_writeUBE16, PHYSFS_writeUBE32, PHYSFS_writeUBE64, PHYSFS_writeULE16, PHYSFS_writeULE32, PHYSFS_writeULE64 - Convert and write big/little endian values.

Detailed Description

These functions convert unsigned integers from the host machine's native byte order to either big-endian or little-endian byte order, and then write them to the specified file handle.

These are convenience functions. For example, PHYSFS_writeUBE16 is equivalent to calling PHYSFS_writeEndian16 with PHYSFS_ENDIAN_BIG.
