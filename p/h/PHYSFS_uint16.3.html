DESCRIPTION

The PhysicsFS library is a library that abstracts file I/O from the user. It allows an application to read from archives (like ZIP files, tarballs, etc.) as if they were regular directories. It can also handle multiple archives and directories simultaneously, which can be mounted in a specified order.

The library implements functions for opening, reading, writing, closing, and enumerating files. It can also handle character encoding conversions and byte order swaps.

Key features:

  • Mounting of archives and directories.
  • Abstraction of file I/O operations.
  • Support for various archive formats (e.g., ZIP, tar).
  • Character encoding conversion (UTF-8, UCS-2, UCS-4, Latin1).
  • Byte order swapping for different endianness.
  • Error handling and reporting.
  • Customizable memory allocation.
  • Symbolic link handling (configurable).

The functions are generally named with a PHYSFS_ prefix. Common patterns include:

  • PHYSFS_swap*: Functions to swap byte order for numerical types.
  • PHYSFS_read*: Functions to read data from a file handle, performing necessary conversions.
  • PHYSFS_write*: Functions to write data to a file handle, performing necessary conversions.
  • PHYSFS_mount*: Functions to add archives or directories to the search path.
  • PHYSFS_get*: Functions to retrieve information about the library's state or configuration.
  • PHYSFS_set*: Functions to configure the library's behavior.
  • PHYSFS_is*: Functions to check certain conditions.
  • PHYSFS_utf*: Functions for character encoding conversions.

The library uses a callback mechanism for certain operations, such as enumerating files or receiving directory names.

Error handling is done via return codes and an error code query function (PHYSFS_getLastErrorCode).

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Get a file listing of a search path's directory, using an application-defined callback, with errors reported. Internally, PHYSFS_enumerateFiles() just calls this function and then builds a list before returning to the application, so functionality is identical except for how the information is represented to the application.

Unlike PHYSFS_enumerateFiles(), this function does not return an array. Rather, it calls a function specified by the application once per element of the search path:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Items sent to the callback are not guaranteed to be in any order whatsoever. There is no sorting done at this level, and if you need that, you should probably use PHYSFS_enumerateFiles() instead, which guarantees alphabetical sorting. This form reports whatever is discovered in each archive before moving on to the next. Even within one archive, we can't guarantee what order it will discover data. Any sorting you find in these callbacks is just pure luck. Do not rely on it. As this walks the entire list of archives, you may receive duplicate filenames.

This API and the callbacks themselves are capable of reporting errors. Prior to this API, callbacks had to accept every enumerated item, even if they were only looking for a specific thing and wanted to stop after that, or had a serious error and couldn't alert anyone. Furthermore, if PhysicsFS itself had a problem (disk error or whatnot), it couldn't report it to the calling app, it would just have to skip items or stop enumerating outright, and the caller wouldn't know it had lost some data along the way.

Now the caller can be sure it got a complete data set, and its callback has control if it wants enumeration to stop early. See the documentation for PHYSFS_EnumerateCallback for details on how your callback should behave.

Parameters

dir Directory, in platform-independent notation, to enumerate.
c Callback function to notify about search path elements.
d Application-defined data passed to callback. Can be NULL.

Returns

non-zero on success, zero on failure. Use PHYSFS_getLastErrorCode() to obtain the specific error. If the callback returns PHYSFS_ENUM_STOP to stop early, this will be considered success. Callbacks returning PHYSFS_ENUM_ERROR will make this function return zero and set the error code to PHYSFS_ERR_APP_CALLBACK.

char ** PHYSFS_enumerateFiles (const char * dir)

Get a file listing of a search path's directory.

Warning

In PhysicsFS versions prior to 2.1, this function would return as many items as it could in the face of a failure condition (out of memory, disk i/o error, etc). Since this meant apps couldn't distinguish between complete success and partial failure, and since the function could always return NULL to report catastrophic failures anyway, in PhysicsFS 2.1 this function's policy changed: it will either return a list of complete results or it will return NULL for any failure of any kind, so we can guarantee that the enumeration ran to completion and has no gaps in its results.

Matching directories are interpolated. That is, if "C:\mydir" is in the search path and contains a directory "savegames" that contains "x.sav", "y.sav", and "z.sav", and there is also a "C:\userdir" in the search path that has a "savegames" subdirectory with "w.sav", then the following code:

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);
PHYSFS_freeList(rc);
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..

Feel free to sort the list however you like. However, the returned data will always contain no duplicates, and will be always sorted in alphabetic (rather: case-sensitive Unicode) order for you.

Don't forget to call PHYSFS_freeList() with the return value from this function when you are done with it.

Parameters

dir directory in platform-independent notation to enumerate.

Returns

Null-terminated array of null-terminated strings, or NULL for failure cases.

Obtiene la ruta específica del usuario y de la aplicación donde se pueden escribir archivos. Función auxiliar.

Obtiene el "directorio de preferencias". Esto está destinado a ser donde los usuarios pueden escribir archivos personales (preferencias y partidas guardadas, etc.) que son específicos de su aplicación. Este directorio es único por usuario, por aplicación.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Añadir un archivo o directorio a la ruta de búsqueda. Si es un duplicado, la entrada no se añade de nuevo, aunque la función tenga éxito. No puede añadir el mismo archivo a dos puntos de montaje diferentes: la comprobación de duplicados se realiza contra el archivo y no contra el punto de montaje.

Cuando monta un archivo, se añade a un sistema de archivos virtual... todos los archivos en todos los archivos se interpolan en un solo árbol de archivos jerárquico. Dos archivos montados en el mismo lugar (o un archivo con archivos que se superponen con otro punto de montaje) pueden tener archivos superpuestos: en tal caso, se selecciona el archivo anterior en la ruta de búsqueda, y los otros archivos son inaccesibles para la aplicación. Esto permite que los archivos se utilicen para reemplazar revisiones anteriores; puede usar el mecanismo de montaje para colocar archivos en un punto específico del árbol de archivos y evitar la superposición; esto es útil para mods descargables que podrían pisotear datos de aplicaciones o entre sí, por ejemplo.

El punto de montaje no necesita existir antes de montarlo, lo que es diferente de lo que los familiarizados con el concepto de montaje de Unix pueden esperar. Por ejemplo, si tienes x.zip con un archivo en y/z.txt, montado en /a, si llamas a PHYSFS_setRoot("x.zip", "/y"), entonces la llamada PHYSFS_openRead("/a/z.txt") tendrá éxito.

Puedes cambiar la raíz de un archivo en cualquier momento, alterando el árbol de archivos interpolado (dependiendo de dónde cambien las rutas, un archivo diferente puede estar proporcionando varios archivos). Si estableces la raíz a NULL o "/", el archivo se tratará como si no hubiera una raíz especial establecida (como si el archivo se hubiera montado normalmente).

Cambiar la raíz solo afecta a las operaciones futuras en los nombres de ruta; un archivo que se abrió desde una ruta que cambió debido a un setRoot no se verá afectado.

Establecer una nueva raíz no se limita a los archivos en la ruta de búsqueda; también puedes establecer una en el directorio de escritura, lo cual podría ser útil si tienes archivos abiertos para escritura y, por lo tanto, no puedes cambiar el directorio de escritura en este momento.

No es un error establecer un subdirectorio que no existe como la raíz de un archivo; sin embargo, en este caso no se verán archivos. Si los directorios faltantes terminan creándose (un mkdir al sistema de archivos físico, etc.) entonces esto se reflejará en el árbol interpolado.

Parámetros

archive directorio/archivo en el que cambiar la raíz.
subdir nuevo subdirectorio que se convertirá en la raíz de este archivo.

Retorna

distinto de cero si tiene éxito, cero si falla. Usa PHYSFS_getLastErrorCode() para obtener el error específico.

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convert a Latin1 string to a UTF-8 string. Latin1 strings are 8-bits per character: a popular "high ASCII" encoding.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 expands latin1 codepoints over 127 from 1 to 2 bytes, so the string may grow in some cases.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-8 sequence at the end. If the buffer length is 0, this function does nothing.

Please note that we do not supply a UTF-8 to Latin1 converter, since Latin1 can't express most Unicode codepoints. It's a legacy encoding; you should be converting away from it at all times.

Parameters

src Null-terminated source string in Latin1 format.
dst Buffer to store converted UTF-8 string.
len Size, in bytes, of destination buffer.

void PHYSFS_utf8ToUtf16 (const char * src, PHYSFS_uint16 * dst, PHYSFS_uint64 len)

Convierte una cadena UTF-8 a una cadena UTF-16.

Advertencia

Esta función no informará de un error si hay secuencias UTF-8 no válidas en la cadena fuente. Las reemplazará con un carácter '?' y continuará.

Las cadenas UTF-16 tienen 16 bits por carácter (excepto algunos caracteres, que tienen 32 bits): TCHAR en Windows, cuando se compila con soporte Unicode. Las versiones modernas de Windows usan UTF-16. Las versiones de Windows anteriores a 2000 usaban TCHAR, pero solo manejaban UCS-2. UTF-16 *es* UCS-2, excepto por los caracteres que tienen 4 bytes, los cuales no son representables en UCS-2 de ninguna manera. Las cadenas que no quepan en el búfer de destino serán truncadas, pero siempre estarán terminadas en nulo y nunca tendrán un par sustituto UTF-16 incompleto al final. Si la longitud del búfer es 0, esta función no hace nada.

Esta función nunca aclaró qué sucedería si lograbas escribir un objeto parcial, así que trabajar a nivel de byte lo hace más claro para todos, especialmente ahora que las interfaces de PHYSFS_Io pueden ser suministradas por la aplicación.

Parámetros

handle valor de retorno de PHYSFS_openWrite() o PHYSFS_openAppend().
buffer búfer de bytes para escribir en (handle).
objSize tamaño en bytes de los objetos que se escriben en (handle).
objCount número de objetos (de tamaño objSize) para escribir en (handle).

Devuelve

número de objetos escritos. PHYSFS_getLastErrorCode() puede aclarar la razón por la cual este valor podría ser menor que (objCount). -1 si el fallo es completo.

PHYSFS_sint64 PHYSFS_writeBytes (PHYSFS_File * handle, const void * buffer, PHYSFS_uint64 len)

Escribe datos en un manejador de archivos PhysicsFS. El archivo debe estar abierto para escritura.

Por favor, ten en cuenta que aunque (len) es un entero sin signo de 64 bits, estás limitado a 63 bits (9223372036854775807 bytes), por lo que podemos devolver un valor negativo en caso de error. Si la longitud es mayor que 0x7FFFFFFFFFFFFFFF, esta función fallará inmediatamente. Para sistemas sin un tipo de dato de 64 bits, estás limitado a 31 bits (0x7FFFFFFF, o 2147483647 bytes). Confiamos en que la mayoría de las cosas no necesitarán realizar múltiples gigabytes de E/S en una sola llamada, pero ¿por qué limitar las cosas?

Parámetros

handle valor de retorno de PHYSFS_openWrite() o PHYSFS_openAppend().
buffer búfer de (len) bytes para escribir en (handle).
len número de bytes que se escriben en (handle).

Devuelve

número de bytes escritos. Esto puede ser menor que (len); en caso de error, el sistema puede intentar escribir tantos bytes como sea posible, por lo que puede ocurrir una escritura incompleta. PHYSFS_getLastErrorCode() puede aclarar la razón por la cual este valor podría ser menor que (len). -1 si el fallo es completo.
