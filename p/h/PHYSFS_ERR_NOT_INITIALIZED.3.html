DESCRIPTION

The PhysicsFS library provides an abstraction layer over the file system that allows applications to treat archives (like ZIP, PK3, RAR, etc.) as directories. This can be useful for games, to pack resources into archives, and for applications that need to distribute large numbers of files and want to keep the directory structure clean.

PhysicsFS supports multiple archives and directories on the search path simultaneously. It will search them in the order they were mounted.

If you need to write files, you can specify directories that are writeable. They will be checked for write access before any archives are mounted.

The library also provides a set of helper functions for byte swapping and Unicode character conversions.

Initialization and Shutdown:

PHYSFS_init()
Initializes the PhysicsFS library. Must be called before any other PhysicsFS function. The argv0 parameter is used to determine the location of the main executable, which helps PhysicsFS locate default configuration files and archives.
PHYSFS_deinit()
Frees all resources allocated by PhysicsFS. Should be called when the application is exiting.

Configuration and Search Path:

PHYSFS_permitSymbolicLinks()
Controls whether symbolic links are followed when accessing files. By default, they are not.
PHYSFS_setSaneConfig()
A convenience function that tries to set up a sane default configuration. It finds the application's base directory, sets it as the root, and then tries to mount archives in standard locations (e.g., next to the executable, in user directories).
PHYSFS_addConfigPath()
Adds a directory to PhysicsFS's configuration search path. PhysicsFS will look for configuration files in this directory.
PHYSFS_addPriorityConfigPath()
Adds a directory to the front of the configuration search path.
PHYSFS_removeConfigPath()
Removes a directory from the configuration search path.
PHYSFS_getBaseDir()
Returns the base directory of the application (usually where the executable resides).
PHYSFS_getUserDir()
Returns the user's home directory.
PHYSFS_getPrefDir()
Returns the platform-specific preference directory for the application. This is the recommended place to store user configuration files and saved games.
PHYSFS_mount()
Adds a directory or archive to the search path. newDir is the path to the directory or archive. mountPoint is the virtual directory within the PhysicsFS hierarchy where this archive will be mounted. If mountPoint is NULL, the archive is mounted at the root. appendToPath specifies whether to add it to the end of the search path (true) or the beginning (false).
PHYSFS_mountIo()
Similar to PHYSFS_mount, but takes a PHYSFS_Io structure instead of a directory path. This allows mounting archives from arbitrary sources (e.g., network streams).
PHYSFS_mountMemory()
Mounts an archive contained within a memory buffer. The buffer is specified by buf and len. The del callback function is called when the archive is unmounted to free the buffer if necessary. The other parameters are the same as PHYSFS_mount.
PHYSFS_mountHandle()
Mounts an archive contained within a PHYSFS_File handle. The other parameters are the same as PHYSFS_mount.
PHYSFS_unmount()
Removes a directory or archive from the search path. oldDir is the path to the directory or archive to unmount.
PHYSFS_getCdRomDirsCallback()
Calls the callback function c for each CD-ROM directory that PhysicsFS knows about. d is a user-defined pointer passed to the callback.
PHYSFS_getSearchPathCallback()
Calls the callback function c for each directory in the current search path. d is a user-defined pointer passed to the callback.
PHYSFS_getMountPoint()
Returns the mount point for a given directory or archive path, or NULL if the path is not mounted.

PHYSFS_openWrite()

PHYSFS_write()

PHYSFS_eof()

PHYSFS_fileLength()

PHYSFS_seek()

PHYSFS_fgets()

PHYSFS_fputs()

PHYSFS_delete()

PHYSFS_mkdir()

PHYSFS_rmdir()

PHYSFS_rename()
Renames a file or directory.

Enumerating Files:

PHYSFS_enumerate()
Iterates over the files in a directory, calling the provided callback function for each file found. The callback receives the directory name, the filename, and a user-defined pointer.
PHYSFS_enumerateFilesCallback()
Similar to PHYSFS_enumerate, but the callback function only receives the filename.
PHYSFS_stat()
Retrieves information about a file or directory, such as its size, modification time, and type.

Endian Swapping and Direct I/O:

These functions are useful for reading and writing binary data in a platform-independent way. They handle the conversion between the platform's native byte order and little-endian or big-endian formats.

PHYSFS_swapSLE16(), PHYSFS_swapULE16(), PHYSFS_swapSLE32(), PHYSFS_swapULE32(), PHYSFS_swapSLE64(), PHYSFS_swapULE64()
Swap little-endian signed/unsigned 16/32/64-bit values to the platform's native byte order.
PHYSFS_swapSBE16(), PHYSFS_swapUBE16(), PHYSFS_swapSBE32(), PHYSFS_swapUBE32(), PHYSFS_swapSBE64(), PHYSFS_swapUBE64()
Swap big-endian signed/unsigned 16/32/64-bit values to the platform's native byte order.
PHYSFS_readSLE16() through PHYSFS_readUBE64()
Read and convert signed/unsigned 16/32/64-bit values from a file handle in either little-endian or big-endian format.
PHYSFS_writeSLE16() through PHYSFS_writeUBE64()
Convert and write signed/unsigned 16/32/64-bit values to a file handle in either little-endian or big-endian format.

MACROS

#define PHYSFS_VERSION( x)

This macro fills in a PHYSFS_Version structure with the major, minor, and patch version numbers of the PhysicsFS library that the application was compiled against.

Example:

    PHYSFS_Version version;
    PHYSFS_VERSION(&version);
    if (version.major < 2) {
        // Handle older versions...
    }

See also PHYSFS_VERSION_MAJOR, PHYSFS_VERSION_MINOR, PHYSFS_VERSION_PATCH.

#define PHYSFS_file PHYSFS_File

Compatibility define for version 1.0 API.

RETURN VALUES

Most functions return 1 on success and 0 on failure. Check the return value and use PHYSFS_getLastErrorCode() and PHYSFS_getErrorByCode() to determine the cause of failure.

Functions that return pointers return NULL on failure.

Functions that return PHYSFS_sint64 return -1 on error.

Desinicializar la biblioteca PhysicsFS. Esto cierra todos los archivos abiertos a través de PhysicsFS, borra las rutas de búsqueda/escritura, libera memoria e invalida todos tus manejadores de archivo.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtiene una lista de archivos de un directorio de ruta de búsqueda, utilizando una función de devolución de llamada definida por la aplicación, con errores reportados. Internamente, PHYSFS_enumerateFiles() simplemente llama a esta función y luego crea una lista antes de devolverla a la aplicación, por lo que la funcionalidad es idéntica, excepto por cómo se representa la información a la aplicación.

A diferencia de PHYSFS_enumerateFiles(), esta función no devuelve una matriz. En cambio, llama a una función especificada por la aplicación una vez por elemento de la ruta de búsqueda:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Tenemos [%s] en [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // dame más datos, por favor.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

No se garantiza que los elementos enviados a la función de devolución de llamada estén en ningún orden. No se realiza ningún ordenamiento a este nivel, y si lo necesita, probablemente debería usar PHYSFS_enumerateFiles() en su lugar, que garantiza el ordenamiento alfabético. Esta forma reporta lo que se descubre en cada archivo antes de pasar al siguiente. Incluso dentro de un archivo, no podemos garantizar el orden en que descubrirá los datos. Cualquier ordenamiento que encuentre en estas devoluciones de llamada es pura suerte. No dependa de él. Dado que esto recorre toda la lista de archivos, puede recibir nombres de archivo duplicados.

Esta API y las propias devoluciones de llamada son capaces de reportar errores. Antes de esta API, las devoluciones de llamada tenían que aceptar cada elemento enumerado, incluso si solo buscaban algo específico y querían detenerse después de eso, o tenían un error grave y no podían alertar a nadie. Además, si el propio PhysicsFS tenía un problema (error de disco o similar), no podía informarlo a la aplicación que lo llamaba, solo tenía que omitir elementos o dejar de enumerar por completo, y el que llamaba no sabría que había perdido algunos datos en el camino.

Ahora el que llama puede estar seguro de que obtuvo un conjunto de datos completo, y su devolución de llamada tiene el control si desea que la enumeración se detenga antes. Consulte la documentación de PHYSFS_EnumerateCallback para obtener detalles sobre cómo debe comportarse su devolución de llamada.

Parámetros

dir Directorio, en notación independiente de la plataforma, para enumerar.
c Función de devolución de llamada para notificar sobre elementos de la ruta de búsqueda.
d Datos definidos por la aplicación pasados a la devolución de llamada. Puede ser NULL.

Devuelve

Distinto de cero en caso de éxito, cero en caso de fallo. Utilice PHYSFS_getLastErrorCode() para obtener el error específico. Si la devolución de llamada devuelve PHYSFS_ENUM_STOP para detenerse antes, esto se considerará un éxito. Las devoluciones de llamada que devuelven PHYSFS_ENUM_ERROR harán que esta función devuelva cero y establezca el código de error en PHYSFS_ERR_APP_CALLBACK.

Advertencia

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * Tenemos [%s].\n", *i);
PHYSFS_freeList(rc);

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.
