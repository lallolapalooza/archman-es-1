1.0 API compatibility define. PHYSFS_file is identical to PHYSFS_File. This #define is here for backwards compatibility with the 1.0 API, which had an inconsistent capitalization convention in this case. New code should use PHYSFS_File, as this #define may go away someday.

#define PHYSFS_VERSION( x)

Value:

{ \
    (x)->major = PHYSFS_VER_MAJOR; \
    (x)->minor = PHYSFS_VER_MINOR; \
    (x)->patch = PHYSFS_VER_PATCH; \
}

Macro to determine PhysicsFS version program was compiled against. This macro fills in a PHYSFS_Version structure

con la versión de la biblioteca con la que se compiló. Esto se determina por el encabezado que utiliza el compilador. Tenga en cuenta que si vinculó la biblioteca dinámicamente, puede tener una versión ligeramente más nueva o más antigua en tiempo de ejecución. Esa versión se puede determinar con PHYSFS_getLinkedVersion(), que, a diferencia de PHYSFS_VERSION, no es una macro.

typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Firma de función para callbacks que enumeran archivos.

Advertencia

A partir de PhysicsFS 2.1, use PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; le da más control sobre el proceso.

Estos se utilizan para informar una lista de entradas de directorio a un llamador original, un archivo/directorio/enlace simbólico por callback. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de ninguna cadena.

Estos callbacks se utilizan, a partir de PhysicsFS 1.1, como una alternativa a las funciones que devolverían listas que necesitan ser liberadas con PHYSFS_freeList(). El callback significa que la biblioteca no necesita asignar una lista completa y todas las cadenas por adelantado.

Tenga en cuenta que el orden de los datos prometido en las versiones de lista no es necesariamente así en las versiones de callback. Consulte la documentación sobre APIs específicas, pero es posible que las cadenas no estén ordenadas como espera y que reciba cadenas duplicadas.

data Puntero a datos definido por el usuario, pasado desde la API que finalmente llamó al callback.
origdir Una cadena que contiene la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio sobre el cual solicitó la enumeración, pasado en el callback para su conveniencia.
fname El nombre del archivo que se está enumerando. Puede que no esté en orden alfabético en comparación con otros callbacks que se hayan ejecutado, y no contendrá la ruta completa. Puede recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

enum PHYSFS_ErrorCode

Valores que representan causas específicas de fallo. La mayoría de las veces, solo debería preocuparse por si una operación determinada falló o no, pero puede haber ocasiones en las que planee manejar un caso de fallo específico con gracia, por lo que proporcionamos códigos de error específicos.

La mayoría de estos errores son un poco vagos, y la mayoría no son cosas que pueda arreglar... si hay un error de permiso, por ejemplo, todo lo que realmente puede hacer es pasar esa información al usuario y dejar que descubra cómo manejarlo. En la mayoría de estos casos, su programa solo debería preocuparse de que no logró sus objetivos, y no preocuparse específicamente por qué.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Get a list of files from a search path, using a user-defined callback, with error reporting. Internally, PHYSFS_enumerateFiles() simply calls this function and then builds a list before returning to the application, so the functionality is identical, except for how the information is presented to the application.

Different from PHYSFS_enumerateFiles(), this function does not return an array, but instead calls a user-specified function once for each item in the search path:

static physfs_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // Give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

The items sent to the callback are not guaranteed to be in any order. No sorting is performed at this level, and if you need it, you should use PHYSFS_enumerateFiles(), which guarantees alphabetical order. This form reports what is found in each archive before moving on to the next. Even within one archive, we can't guarantee the order in which data is discovered. *Any ordering you find in these callbacks is pure luck. You must not depend on it.* Since this walks the entire file list, you might receive duplicate filenames.

This API and the callbacks themselves can report errors. Before this API, callbacks had to accept every enumerated item, even if they were just looking for a specific object and wanted to stop afterwards, or had a fatal error and couldn't notify anyone. Additionally, if PhysicsFS itself had a problem (disk error or similar), it couldn't report it to the calling app; it would simply have to skip items or stop altogether, and the caller wouldn't know that it had lost data along the way.

Now the caller can be sure that they got a complete set of data, and if they want, their callback has control over whether to stop enumeration early. See the documentation for PHYSFS_EnumerateCallback for details on how your callback should behave.

Parameters

dir Directory in platform-independent notation, to enumerate.
c Callback function to notify about items in the search path.
d Application-defined data that is passed to the callback. Can be NULL.

Returns

Non-zero on success, zero on failure. Use PHYSFS_getLastErrorCode() to get the specific error. If the callback returns PHYSFS_ENUM_STOP to stop early, this is considered success. Callbacks returning PHYSFS_ENUM_ERROR will cause this function to return zero and set the error code to PHYSFS_ERR_APP_CALLBACK.

Get the user-and-app-specific path where files can be written. Helper function.

Get the "pref dir". This is meant to be where users can write personal files (preferences and save games, etc) that are specific to your application. This directory is unique per user, per application.

This function will decide the appropriate location in the native filesystem, create the directory if necessary, and return a string in platform-dependent notation, suitable for passing to PHYSFS_setWriteDir().

On Linux, this might look like: "/home/bob/.local/share/My Program Name"

On Mac OS X, this might look like: "/Users/bob/Library/Application Support/My Program Name"

(etc.)

You should probably use the pref dir for your write dir, and also put it near the beginning of your search path. Older versions of PhysicsFS offered only PHYSFS_getUserDir() and left you to figure out where the files should go under that tree. This finds the correct location for whatever platform, which not only changes between operating systems, but also versions of the same operating system.

You specify the name of your organization (if it's not a real organization, your name or an Internet domain you own might do) and the name of your application. These should be proper names.

  • Try to use the same org string (including case-sensitivity) for all your applications that use this function.

  • Unicode characters are legal, as long as it's UTF-8 encoded, but...
  • ...only use letters, numbers, and spaces. Avoid punctuation like "Game Name 2: Bad Guy's Revenge!" ... "Game Name 2" is sufficient.

You should assume the path returned by this function is the only safe place to write files (and that PHYSFS_getUserDir() and PHYSFS_getBaseDir(), while they might be writable, or even parents of the returned path, aren't where you should be writing things).

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Añade un archivo o directorio a la ruta de búsqueda. Si es un duplicado, el elemento no se añade de nuevo, incluso si el función es exitosa. Puedes no añadir el mismo archivo a dos diferentes puntos de montaje: la verificación de duplicados se hace contra el archivo y no contra el punto de montaje.

Al montar un archivo, se lo añade a un sistema de archivos virtual... todos los archivos de todos los archivos montados se interpolan en una sola arboléntica de directorios. Dos archivos montados en el mismo lugar (o un archivo con archivos que superponen un punto de montaje) pueden tener archivos superpuestos: en tal caso, el archivo más temprano en la ruta de búsqueda es seleccionado, y los otros archivos no son accesibles para la aplicación. Esto permite usar archivos para reemplazar revisiones previas; puedes usar el mecanismo de montaje para colocar archivos en un punto específico en el árbol de archivos y prevenir superposiciones; esto es útil para modos descargables que puedan pisar datos de aplicación o sí mismos, por ejemplo.

El punto de montaje no necesita existir antes de montar, lo cual es diferente de lo que se espera con el concepto Unix de "montar" conocido por los usuarios. Además, más de un archivo puede montarse en el mismo punto de montaje, o los puntos de montaje y los contenidos de los archivos pueden superponerse... el mecanismo de interpolación todavía funciona normally.

void PHYSFS_permitSymbolicLinks (int allow)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y archivos contienen archivos que son solo punteros a otros archivos. En el sistema de archivos físico, la apertura de dicho enlace abrirá (transparentemente) el archivo al que apunta.

Por defecto, PhysicsFS verificará si un archivo es realmente un enlace simbólico durante las llamadas de apertura y fallará si lo es. De lo contrario, el enlace podría llevarte fuera de las rutas de escritura y búsqueda, y comprometer la seguridad.

Si desea asumir ese riesgo, llame a esta función con un parámetro distinto de cero. Tenga en cuenta que esto es más para aislar el lenguaje de scripting de un programa, en caso de que scripts no confiables intenten comprometer el sistema. En términos generales, un usuario podría tener una razón legítima para crear un enlace simbólico, por lo que a menos que sienta que hay un peligro específico en permitirlos, debería permitirlos.

Los enlaces simbólicos solo se verifican explícitamente cuando se tratan nombres de archivo en notación independiente de la plataforma. Es decir, al configurar las rutas de búsqueda y escritura, etc., los enlaces simbólicos nunca se verifican.

Tenga en cuenta que PHYSFS_stat() siempre verificará la ruta especificada; si esa ruta es un enlace simbólico, no se seguirá en ningún caso. Si los enlaces simbólicos no están permitidos a través de esta función, PHYSFS_stat() los ignora y trataría la consulta como si la ruta no existiera en absoluto.

El permiso de enlace simbólico se puede habilitar o deshabilitar en cualquier momento después de haber llamado a PHYSFS_init(), y está deshabilitado por defecto.

allow distinto de cero para permitir enlaces simbólicos, cero para denegar enlaces.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Establece un subdirectorio de un archivo como directorio raíz. Esto le permite reducir los archivos accesibles en un archivo específico. Por ejemplo, si tiene x.zip con un archivo en y/z.txt, montado en /a, si llama a PHYSFS_setRoot("x.zip", "/y"), entonces la llamada PHYSFS_openRead("/a/z.txt") tendrá éxito.

Puede cambiar la raíz de un archivo en cualquier momento, alterando el árbol de archivos interpolado (dependiendo de dónde cambien las rutas, un archivo diferente puede estar proporcionando varios archivos). Establecer una nueva raíz no se limita a los archivos en la ruta de búsqueda; también puede establecer una en el directorio de escritura, lo cual podría ser útil si tiene archivos abiertos para escritura y, por lo tanto, no puede cambiar el directorio de escritura en este momento.

archive directorio/archivo en el que cambiar la raíz.
subdir nuevo subdirectorio que se convertirá en la raíz de este archivo.

distinto de cero en caso de éxito, cero en caso de fallo. Use PHYSFS_getLastErrorCode() para obtener el error específico.

int PHYSFS_setSaneConfig (const char * organization, const char * appName, const char * archiveExt, int includeCdRoms, int archivesFirst)

Configura rutas predeterminadas y sensatas. Función auxiliar.

El directorio de escritura se establecerá en el pref dir devuelto por

PHYSFS_getPrefDir(organization, appName)

, que se crea si no existe.

Lo anterior es suficiente para asegurarse de que el directorio de configuración de su programa esté separado de otro desorden y sea independiente de la plataforma.

La ruta de búsqueda será:

  • El Directorio de Escritura (creado si no existe)
  • El Directorio Base (PHYSFS_getBaseDir())
  • Todos los directorios de CD-ROM encontrados (opcionalmente)

Estos directorios se buscan luego para encontrar archivos que terminen con la extensión (archiveExt), que, si son archivos válidos y compatibles, también se agregarán a la ruta de búsqueda. Si especificó "PKG" para (archiveExt), y hay un archivo llamado data.PKG en el directorio base, se verificará. Los archivos pueden agregarse o anteponerse a la ruta de búsqueda en orden alfabético, independientemente de los directorios en los que se encontraron. Todos los archivos se montan en la raíz del sistema de archivos virtual ("/") .

Todo esto puede ser logrado por la aplicación, pero esto simplemente lo hace todo por usted. Siéntase libre de agregar más a la ruta de búsqueda manualmente también.

archiveExt Extensión de archivo utilizada por su programa para especificar un archivo. Por ejemplo, Quake 3 usa "pk3", aunque solo son archivos zip. Especifique NULL para no buscar archivos automáticamente. No especifique el carácter '.' Si desea buscar archivos ZIP, especifique "ZIP" y no ".ZIP" ... la búsqueda de archivos no distingue entre mayúsculas y minúsculas.
includeCdRoms Distinto de cero para incluir CD-ROM en la ruta de búsqueda, y (si (archiveExt) != NULL) buscarlos para ver si contienen archivos. Esto puede causar una cantidad significativa de bloqueo mientras se accede a los discos, y si no hay discos en la unidad (o incluso si no están montados en sistemas Unix), es posible que no estén disponibles de todos modos. Es posible que desee especificar cero y manejar la configuración del disco usted mismo.
archivesFirst Distinto de cero para anteponer los archivos a la ruta de búsqueda. Cero para agregarlos. Ignorado si !(archiveExt).

Convierte una cadena UTF-8 a una cadena Latin1. Las cadenas Latin1 tienen 8 bits por carácter: una codificación popular de "alto ASCII".

Para asegurar que el búfer de destino sea lo suficientemente grande para la conversión, por favor, asigna un búfer que sea el doble del tamaño del búfer de origen. UTF-8 expande los puntos de código Latin1 mayores de 127 de 1 a 2 bytes, por lo que la cadena puede crecer en algunos casos.

Las cadenas que no quepan en el búfer de destino serán truncadas, pero siempre terminarán en nulo y nunca tendrán una secuencia UTF-8 incompleta al final. Si la longitud del búfer es 0, esta función no hace nada.

Por favor, ten en cuenta que no proporcionamos un convertidor de UTF-8 a Latin1, ya que Latin1 no puede expresar la mayoría de los puntos de código Unicode. Es una codificación heredada; deberías estar convirtiendo lejos de ella en todo momento.

Detailed Description

These functions convert an integer value from the host's native byte order to a specific endianness (big-endian for `UBE' functions, little-endian for `ULE' functions), and then write the result to a PhysicsFS file.

These are convenience functions; they simply wrap PHYSFS_write after performing the necessary byte swapping.
