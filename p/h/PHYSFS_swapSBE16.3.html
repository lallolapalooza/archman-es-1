PHYSFS_enumerate

Esto es lo mismo que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, excepto que puede devolver un resultado del callback: a saber, si estás buscando algo específico, una vez que lo encuentras, puedes indicarle a PhysicsFS que deje de enumerar más. Un valor de PHYSFS_EnumerateCallbackResult. Todos los demás valores están (actualmente) indefinidos; no los uses.

typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Firma de función para callbacks que enumeran archivos.

Advertencia

A partir de PhysicsFS 2.1, usa PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; te da más control sobre el proceso.

Se utilizan para informar una lista de entradas de directorio a un llamador original, un archivo/directorio/enlace simbólico por callback. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de ninguna cadena.

Estos callbacks se utilizan, a partir de PhysicsFS 1.1, como una alternativa a las funciones que devolverían listas que necesitan ser limpiadas con PHYSFS_freeList(). El callback significa que la biblioteca no necesita asignar una lista completa y todas las cadenas por adelantado.

Ten en cuenta que las promesas de orden de datos en las versiones de lista no son necesariamente así en las versiones de callback. Consulta la documentación sobre APIs específicas, pero las cadenas pueden no estar ordenadas como esperas y podrías obtener cadenas duplicadas.

Parámetros

data Puntero a datos definido por el usuario, pasado desde la API que finalmente llamó al callback.
origdir Una cadena que contiene la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio sobre el que solicitaste la enumeración, pasado en el callback para tu conveniencia.
fname El nombre del archivo que se está enumerando. Puede que no esté en orden alfabético en comparación con otros callbacks que se han ejecutado, y no contendrá la ruta completa. Puedes recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

enum PHYSFS_ErrorCode

Valores que representan causas específicas de fallo. La mayoría de las veces, solo deberías preocuparte por si una operación dada falló o no, pero puede haber ocasiones en las que planees manejar un caso de fallo específico con gracia, por lo que proporcionamos códigos de error específicos.

La mayoría de estos errores son un poco vagos, y la mayoría no son cosas que puedas arreglar... si hay un error de permisos, por ejemplo, lo único que realmente puedes hacer es pasar esa información al usuario y dejar que él decida cómo manejarlo. En la mayoría de estos casos, tu programa solo debería preocuparse por haber fallado en lograr sus objetivos, y no importarle específicamente por qué.

Obtener una lista de archivos de un directorio de una ruta de búsqueda, utilizando una callback definida por el usuario, con errores reportados. Internamente, PHYSFS_enumerateFiles() simplemente llama a esta función y luego construye una lista antes de devolver a la aplicación, así que la funcionalidad es idéntica, pero la información se presenta de forma diferente.

Diferente de PHYSFS_enumerateFiles(), esta función no devuelve un array. En lugar de eso, llama a una función especificada por el usuario una vez por cada elemento de la ruta de búsqueda:

{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSfs_ENUM_OK;  // me daría más datos, por favor.
}
// ...

Los elementos enviados a la callback no están garantizados para estar en ningún orden. No se realiza ningún ordenamiento en este nivel, y si lo necesitas, deberías usar PHYSFS_enumerateFiles(), que garantiza el orden alfabético. Esta forma reporta lo que encuentra en cada archivado antes de pasar a la siguiente. Even within one archive, we can't guarantee the order in which data is discovered. Any sorting you find in these callbacks is just pure luck. Do not rely on it. Como este camina por toda la lista de archivados, podrías recibir nombres de archivos duplicados.

Esta API y las callbacks mismas pueden reportar errores. Antes de esta API, las callbacks tenían que aceptar cada elemento enumerado, incluso si solo buscaban un elemento específico y querían detenerse después de eso, o tenían un error grave y no podían notificar a nadie. Además, si PhysicsFS mismo tenia un problema (error de disco, etc.), no podía reportarlo a la aplicación llamada, simplemente tendría que saltar los elementos o detener la enumeración por completo, y la llamada no sabría que perdió algunos datos en el camino.

Ahora el llamador puede estar seguro de que obtuvo un conjunto completo de datos, y su callback controla si quiere detener la enumeración temprano. Véase la documentación para PHYSFS_EnumerateCallback para detalles de cómo debería comportarse su callback.

Obtener una lista de archivos de un directorio de una ruta de búsqueda.

Nota

En versiones de PhysicsFS anteriores a 2.1, esta función devolvería tantos elementos como fuera posible en condiciones de error (error de memoria, error de i/o, etc.). Dado que esto impedía a los aplicativos diferenciar entre éxito completo y fracaso parcial, y dado que la función podía siempre devolver NULL para reportar fallos catastróficos, en PhysicsFS 2.1 esta política cambió: devolverá una lista completa de resultados o NULL en cualquier fallo, así que podemos garantizar que la enumeración se completó y no hay gaps en sus resultados.

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);
PHYSFS_freeList(rc);
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

void PHYSFS_permitSymbolicLinks (int allow)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y arquitecturas contienen archivos que son simplemente referencias a otros archivos. Al abrir un enlace simbólico físico, este se abrirá de manera transparente, apuntando al archivo al que se refiere.

Por defecto, PhysicsFS comprobará si un archivo es realmente un enlace simbólico durante las llamadas de abertura y fallará si es así. De lo contrario, el enlace podría llevarte fuera de las rutas de lectura y escritura, comprometiendo la seguridad.

Si deseas asumir el riesgo, llama a esta función con un valor distinto de cero. Ten en cuenta que esto es más para el sandboxing de un lenguaje de scripting de un programa, en caso de que scripts no confiables intenten comprometer el sistema. En general, un usuario podría tener una razón legítima para establecer un enlace simbólico, por lo que no deberías deshabilitarlo, a menos que sientas que existe un peligro específico.

Los enlaces simbólicos solo se verán cuando se trate de nombres de archivos en notación independiente de plataforma. Es decir, cuando configures tus rutas de búsqueda y escritura, etc., los enlaces simbólicos nunca se verán.

Por favor, ten en cuenta que PHYSFS_stat() siempre verificará la ruta especificada; si esa ruta es un enlace simbólico, no se seguirá en ningún caso. Si los enlaces simbólicos no están permitidos mediante esta función, PHYSFS_stat() los ignorará y tratará la consulta como si la ruta no existiera.

El permiso de enlaces simbólicos se puede habilitar o deshabilitar en cualquier momento después de haber llamado PHYSFS_init(), y está deshabilitado por defecto.

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convierte una cadena UTF-8 a una cadena Latin1. Las cadenas Latin1 tienen 8 bits por carácter: una codificación popular de "ASCII superior".

Para asegurar que el búfer de destino sea lo suficientemente grande para la conversión, por favor, asigna un búfer que sea el doble del tamaño del búfer de origen. UTF-8 expande los puntos de código latin1 mayores de 127 de 1 a 2 bytes, por lo que la cadena puede crecer en algunos casos.

Las cadenas que no quepan en el búfer de destino serán truncadas, pero siempre estarán terminadas en nulo y nunca tendrán una secuencia UTF-8 incompleta al final. Si la longitud del búfer es 0, esta función no hace nada.

Ten en cuenta que no proporcionamos un conversor de UTF-8 a Latin1, ya que Latin1 no puede expresar la mayoría de los puntos de código Unicode. Es una codificación heredada; deberías estar convirtiendo desde ella en todo momento.

Parámetros

src Cadena de origen terminada en nulo en formato Latin1.
dst Búfer para almacenar la cadena UTF-8 convertida.
len Tamaño, en bytes, del búfer de destino.

Detailed Description

These functions write integer values to the given file handle in a specific endian format. They convert the value from the platform's native byte order to the specified format (big-endian or little-endian) before writing.

The PHYSFS_swapSBE* and PHYSFS_swapULE* functions are provided as convenience functions. They swap the byte order of the given value if the platform's native byte order is different from the target endianness (big-endian for SBE, little-endian for ULE). They do *not* write to a file.

The PHYSFS_writeUBE* and PHYSFS_writeULE* functions write the converted value directly to the specified file handle.
