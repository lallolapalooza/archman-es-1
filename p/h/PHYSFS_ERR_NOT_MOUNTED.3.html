typedef PHYSFS_EnumerateCallbackResult(* PHYSFS_EnumerateCallback) (void *data, const char *origdir, const char *fname)

Valores posibles de retorno de PHYSFS_EnumerateCallback. Firma de funciones para callbacks que enumeran y devuelven resultados.

Estos valores determinan si un callback de enumeración debe continuar emitiendo o detenerse (y por qué).

Ver también

PHYSFS_EnumerateCallback

PHYSFS_enumerate

Este es el mismo que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, excepto que puede devolver un resultado del callback: por ejemplo, si estás buscando algo específico, una vez que lo encuentres, puedes decirle a PhysicsFS que detenga la enumeración. Esto se usa con PHYSFS_enumerate(), que esperamos que hayas obtenido correctamente. :)

Parámetros

data Puntero de datos del usuario, pasado por la API que finalmente llamó al callback.
origdir Cadena que contiene el camino completo, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio en el que solicitaste la enumeración, pasado en el callback para tu conveniencia.
fname El nombre del archivo que se está enumerando. Puede no estar en orden alfabético en comparación con otros callbacks que se hayan emitido, y no contendrá el camino completo. Puedes reconstruir el camino completo con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

Retorno

Un valor de PHYSFS_EnumerateCallbackResult. Todos los demás valores son (actualmente) indefinidos; no los uses.

typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Firma de función para callbacks que enumeran archivos.

Advertencia

Desde PhysicsFS 2.1, utiliza PHYSFS_EnumerateCallback con PHYSFS_enumerate(); esto te da más control sobre el proceso.

Estos se utilizan para informar una lista de entradas de directorio a un llamador original, una entrada por callback. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de las cadenas.

Estos callbacks se utilizan, a partir de PhysicsFS 1.1, como alternativa a las funciones que devuelven listas que deben liberarse con PHYSFS_freeList(). El callback significa que la biblioteca no necesita asignar una lista completa y todas las cadenas por adelantado.

Ten en cuenta que las promesas de ordenamiento de datos en las versiones de lista no se cumplen necesariamente en las versiones de callback. Consulta la documentación de las API específicas, pero es posible que las cadenas no estén ordenadas como esperas y puedas obtener cadenas duplicadas.

data Puntero de datos del usuario, pasado por la API que finalmente llamó al callback.
origdir Cadena que contiene el camino completo, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio en el que solicitaste la enumeración, pasado en el callback para tu conveniencia.
fname El nombre del archivo que se está enumerando. Puede no estar en orden alfabético en comparación con otros callbacks que se hayan emitido, y no contendrá el camino completo. Puedes reconstruir el camino completo con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

enum PHYSFS_ErrorCode

Valores que representan causas específicas de fallo. La mayoría de las veces, deberías preocuparte solo por si una operación falló o no, pero puede haber ocasiones en las que planees manejar un caso específico de fallo con elegancia, por lo que ofrecemos códigos de error específicos.

La mayoría de estos errores son un poco vagos, y la mayoría no son cosas que puedas corregir... si hay un error de permisos, por ejemplo, lo único que podrías hacer es pasar esa información al usuario y dejar que él descubra cómo manejarlo. En la mayoría de estos casos, tu programa solo debería preocuparse de que no alcanzó sus objetivos, y no preocuparse específicamente por qué.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtiene una lista de archivos de un directorio de ruta de búsqueda, utilizando una función de devolución de llamada definida por la aplicación, con notificación de errores. Internamente, PHYSFS_enumerateFiles() simplemente llama a esta función y luego construye una lista antes de devolverla a la aplicación, por lo que la funcionalidad es idéntica excepto por la forma en que la información se presenta a la aplicación.

A diferencia de PHYSFS_enumerateFiles(), esta función no devuelve una matriz. En cambio, llama a una función especificada por la aplicación una vez por cada elemento de la ruta de búsqueda:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Tenemos [%s] en [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // dame más datos, por favor.
}
// ...
PHYSFS_enumerate("/alguna/ruta", printDir, NULL);

No se garantiza que los elementos enviados a la función de devolución de llamada estén en ningún orden determinado. No se realiza ninguna ordenación a este nivel, y si la necesita, probablemente debería usar PHYSFS_enumerateFiles() en su lugar, que garantiza la ordenación alfabética. Esta forma informa lo que se descubre en cada archivo antes de pasar al siguiente. Incluso dentro de un solo archivo, no podemos garantizar el orden en que descubrirá los datos. Cualquier ordenación que encuentre en estas llamadas de devolución es pura suerte. No confíe en ella. A medida que recorre toda la lista de archivos, puede recibir nombres de archivo duplicados.

Esta API y las propias funciones de devolución de llamada son capaces de informar errores. Antes de esta API, las funciones de devolución de llamada tenían que aceptar cada elemento enumerado, incluso si solo buscaban algo específico y querían detenerse después de eso, o tenían un error grave y no podían alertar a nadie. Además, si PhysicsFS tenía un problema (error de disco o similar), no podía informarlo a la aplicación que llama, solo tendría que omitir elementos o detener la enumeración sin más, y el llamador no sabría que había perdido algunos datos en el camino.

Ahora el llamador puede estar seguro de que obtuvo un conjunto de datos completo, y su función de devolución de llamada tiene el control si desea que la enumeración se detenga antes. Consulte la documentación de PHYSFS_EnumerateCallback para obtener detalles sobre cómo debe comportarse su función de devolución de llamada.

Parámetros

dir Directorio, en notación independiente de la plataforma, a enumerar.
c Función de devolución de llamada para notificar sobre elementos de la ruta de búsqueda.
d Datos definidos por la aplicación pasados a la función de devolución de llamada. Puede ser NULL.

Devuelve

Distinto de cero en caso de éxito, cero en caso de fallo. Utilice PHYSFS_getLastErrorCode() para obtener el error específico. Si la función de devolución de llamada devuelve PHYSFS_ENUM_STOP para detenerse antes, esto se considerará un éxito. Las funciones de devolución de llamada que devuelvan PHYSFS_ENUM_ERROR harán que esta función devuelva cero y establezca el código de error en PHYSFS_ERR_APP_CALLBACK.

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * Tenemos [%s].\n", *i);
PHYSFS_freeList(rc);

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Añade un archivado o directorio a la ruta de búsqueda. Si es un duplicado, el registro no se añade de nuevo, incluso si la función tiene éxito. No puedes añadir el mismo archivado a dos diferentes mountpoints: el control de duplicados se realiza contra el archivado y no contra el mountpoint.

Al montar un archivado, se añade a un sistema de archivos virtual... todos los archivos de todos los archivados se interpolan en una única arborescencia hierárquica. Dos archivados montados en el mismo lugar (o un archivado con archivos que superponen un mountpoint) pueden tener archivos superpuestos: en ese caso, el archivo más temprano en la ruta de búsqueda se selecciona, y los demás archivos no están accesibles para el aplicativo. Esto permite utilizar los archivados para reemplazar revisiones previas; puedes utilizar el mecanismo de montaje para colocar archivados en un punto específico en el árbol de archivos y evitar superposiciones; es útil para modos descargados que podrían pisar datos de aplicación o sí mismos.

El mountpoint no necesita existir previamente al montaje, lo cual es diferente de lo que se espera en el concepto Unix de "montaje" que conocen. También, más de un archivado puede montarse en el mismo mountpoint, o los mountpoints y los contenidos de archivados pueden superponerse... el mecanismo de interpolación aún funciona.

Es permitido especificar un enlace simbólico a un archivado o directorio, independientemente del estado de PHYSFS_permitSymbolicLinks(). Esta función solo maneja enlaces simbólicos dentro del directorio o archivado montado.

Parámetros

newDir archivado o directorio a añadir a la ruta, en notación independiente del sistema.
mountPoint ubicación en la arborescencia interpolada donde se montará este archivado, en notación independiente. NULL o "" es equivalente a "/".
appendToPath no cero para append a la ruta de búsqueda, cero para prepend.

Retorna

no cero si se añade a la ruta, cero en error (bogus archivado, directorio faltante, etc). Usa PHYSFS_getLastErrorCode() para obtener el error específico.

void PHYSFS_permitirEnlacesSimbolicos (int permitir)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y archivos contienen archivos que son solo punteros a otros archivos. En el sistema de archivos físico, abrir un enlace de este tipo abrirá (transparente) el archivo al que apunta.

Por defecto, PhysicsFS verificará si un archivo es realmente un enlace simbólico durante las llamadas de apertura y fallará si lo es. De lo contrario, el enlace podría sacarte de las rutas de escritura y búsqueda, y comprometer la seguridad.

Si deseas asumir ese riesgo, llama a esta función con un parámetro distinto de cero. Ten en cuenta que esto es más para aislar el lenguaje de scripting de un programa, en caso de que scripts no confiables intenten comprometer el sistema. En general, un usuario podría tener una razón legítima para configurar un enlace simbólico, así que, a menos que sientas que hay un peligro específico al permitirlos, deberías permitirlos.

Los enlaces simbólicos solo se verifican explícitamente cuando se tratan nombres de archivo en notación independiente de la plataforma. Es decir, al configurar tus rutas de búsqueda y escritura, etc., nunca se verifican los enlaces simbólicos.

Ten en cuenta que PHYSFS_stat() siempre verificará la ruta especificada; si esa ruta es un enlace simbólico, no se seguirá en ningún caso. Si los enlaces simbólicos no están permitidos a través de esta función, PHYSFS_stat() los ignora y trataría la consulta como si la ruta no existiera en absoluto.

El permiso de enlace simbólico se puede habilitar o deshabilitar en cualquier momento después de haber llamado a PHYSFS_init(), y está deshabilitado por defecto.

Parámetros

permitir distinto de cero para permitir enlaces simbólicos, cero para denegar el enlace.

Si ambas cadenas son exclusivamente caracteres ASCII de bajo nivel, esto hará lo correcto, ya que también es UTF-8 válido. Si hay algún carácter ASCII de alto nivel, ¡esto no hará lo que esperas!

Al igual que stricmp, esto espera que ambas cadenas estén terminadas en nulo.

str1 Primera cadena a comparar.
str2 Segunda cadena a comparar.

Devuelve

-1 si str1 es "menor que" str2, 1 si es "mayor que", 0 si son iguales.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.
