1.0 API compatibility define. PHYSFS_file is identical to PHYSFS_File. This #define is here for backwards compatibility with the 1.0 API, which had an inconsistent capitalization convention in this case. New code should use PHYSFS_File, as this #define may go away someday.

PHYSFS_enumerate

Esto es lo mismo que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, excepto que puede devolver un resultado del callback: a saber: si estás buscando algo específico, una vez que lo encuentras, puedes indicarle a PhysicsFS que deje de enumerar más. Esto se usa con PHYSFS_enumerate(), que esperamos haberlo hecho bien esta vez. :)

Parámetros

data Puntero a datos definido por el usuario, pasado desde la API que eventualmente llamó al callback.
origdir Una cadena que contiene la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio sobre el cual solicitaste la enumeración, pasado en el callback para tu conveniencia.
fname El nombre del archivo que se está enumerando. Puede que no esté en orden alfabético en comparación con otros callbacks que se han ejecutado, y no contendrá la ruta completa. Puedes recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

Devuelve

Un valor de PHYSFS_EnumerateCallbackResult. Todos los demás valores son (actualmente) indefinidos; no los uses.

typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Firma de función para callbacks que enumeran archivos.

Advertencia

A partir de PhysicsFS 2.1, usa PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; te da más control sobre el proceso.

Se utilizan para informar una lista de entradas de directorio a un llamador original, un archivo/directorio/enlace simbólico por callback. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de ninguna cadena.

Estos callbacks se utilizan, a partir de PhysicsFS 1.1, como una alternativa a las funciones que devolverían listas que deben limpiarse con PHYSFS_freeList(). El callback significa que la biblioteca no necesita asignar una lista completa y todas las cadenas por adelantado.

Ten en cuenta que el orden de los datos prometido en las versiones de lista no es necesariamente así en las versiones de callback. Consulta la documentación de las APIs específicas, pero es posible que las cadenas no estén ordenadas como esperas y que obtengas cadenas duplicadas.

enum PHYSFS_ErrorCode

Valores que representan causas específicas de fallo. La mayoría de las veces, solo deberías preocuparte por si una operación dada falló o no, pero puede haber ocasiones en las que planees manejar un caso de fallo específico graciosamente, por lo que proporcionamos códigos de error específicos.

La mayoría de estos errores son un poco vagos, y la mayoría no son cosas que puedas arreglar... si hay un error de permisos, por ejemplo, todo lo que realmente puedes hacer es pasar esa información al usuario y dejar que averigüe cómo manejarlo. En la mayoría de estos casos, tu programa solo debería preocuparse de que no logró sus objetivos, y no preocuparse específicamente por qué.

Deinitialize the PhysicsFS library. This closes any files opened via PhysicsFS, blanks the search/write paths, frees memory, and invalidates all of your file handles.

Note that this call can FAIL if there's a file open for writing that refuses to close (for example, the underlying operating system was buffering writes to network filesystem, and the fileserver has crashed, or a hard drive has failed, etc). int PHYSFS_delete(const char * filename)

Delete a file or directory. (filename) is specified in platform-independent notation in relation to the write dir.

A directory must be empty before this call can delete it.

Deleting a symlink will remove the link, not what it points to, regardless of whether you "permitSymLinks" or not.

So if you've got the write dir set to "C:\mygame\writedir" and call PHYSFS_delete("downloads/maps/level1.map") then the file "C:\mygame\writedir\downloads\maps\level1.map" is removed from the physical filesystem, if it exists and the operating system permits the deletion.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Get a file listing of a search path's directory, using an application-defined callback, with errors reported. Internally, PHYSFS_enumerateFiles() just calls this function and then builds a list before returning to the application, so functionality is identical except for how the information is represented to the application.

Unlike PHYSFS_enumerateFiles(), this function does not return an array. Rather, it calls a function specified by the application once per element of the search path:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Items sent to the callback are not guaranteed to be in any order whatsoever. There is no sorting done at this level, and if you need that, you should probably use PHYSFS_enumerateFiles() instead, which guarantees alphabetical sorting. This form reports whatever is discovered in each archive before moving on to the next. Even within one archive, we can't guarantee what order it will discover data. Any sorting you find in these callbacks is just pure luck. Do not rely on it. As this walks the entire list of archives, you may receive duplicate filenames.

This API and the callbacks themselves are capable of reporting errors. Prior to this API, callbacks had to accept every enumerated item, even if they were only looking for a specific thing and wanted to stop after that, or had a serious error and couldn't alert anyone. Furthermore, if PhysicsFS itself had a problem (disk error or whatnot), it couldn't report it to the calling app, it would just have to skip items or stop enumerating outright, and the caller wouldn't know it had lost some data along the way.

Now the caller can be sure it got a complete data set, and its callback has control if it wants enumeration to stop early. See the documentation for PHYSFS_EnumerateCallback for details on how your callback should behave.

Parameters

dir Directory, in platform-independent notation, to enumerate.
c Callback function to notify about search path elements.
d Application-defined data passed to callback. Can be NULL.

Returns

non-zero on success, zero on failure. Use PHYSFS_getLastErrorCode() to obtain the specific error. If the callback returns PHYSFS_ENUM_STOP to stop early, this will be considered success. Callbacks returning PHYSFS_ENUM_ERROR will make this function return zero and set the error code to PHYSFS_ERR_APP_CALLBACK.

Get a file listing of a search path's directory.

Warning

In PhysicsFS versions prior to 2.1, this function would return as many items as it could in the face of a failure condition (out of memory, disk i/o error, etc). Since this meant apps couldn't distinguish between complete success and partial failure, and since the function could always return NULL to report catastrophic failures anyway, in PhysicsFS 2.1 this function's policy changed: it will either return a list of complete results or it will return NULL for any failure of any kind, so we can guarantee that the enumeration ran to completion and has no gaps in its results.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

Advertencia

A menos que tenga alguna necesidad especial de bajo nivel, debería usar PHYSFS_mount() en lugar de esta función.

Los archivos dentro de archivos pueden ser muy lentos. Si bien un PHYSFS_File puede buscar incluso cuando los datos están comprimidos, puede hacerlo rebobinando al principio y descomprimiendo todo antes del punto de búsqueda. El uso normal de archivos puede realizar muchas búsquedas en segundo plano. Como tal, es posible que el uso normal de archivos resulte extremadamente molesto si se monta de esta manera. Planifique en consecuencia: si, por ejemplo, tiene un archivo .zip que se autoextrae y desea montar algo dentro de él, comprima el contenido del archivo interior y asegúrese de que el archivo .zip exterior no comprima también el archivo interior.

void PHYSFS_permitSymbolicLinks (int allow)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y archivos contienen archivos que son solo punteros a otros archivos. En el sistema de archivos físico, abrir un enlace de este tipo abrirá (transparennmente) el archivo al que apunta.

Por defecto, PhysicsFS verificará si un archivo es realmente un enlace simbólico durante las llamadas de apertura y fallará si lo es. De lo contrario, el enlace podría sacarte de las rutas de escritura y búsqueda, y comprometer la seguridad.

Si deseas asumir ese riesgo, llama a esta función con un parámetro distinto de cero. Ten en cuenta que esto es más para aislar el lenguaje de scripting de un programa, en caso de que scripts no confiables intenten comprometer el sistema. En términos generales, un usuario podría tener una razón legítima para configurar un enlace simbólico, por lo que a menos que sientas que hay un peligro específico en permitirlos, deberías permitirlos.

Los enlaces simbólicos solo se verifican explícitamente cuando se trata con nombres de archivo en notación independiente de la plataforma. Es decir, al configurar tus rutas de búsqueda y escritura, etc., los enlaces simbólicos nunca se verifican.

Ten en cuenta que PHYSFS_stat() siempre verificará la ruta especificada; si esa ruta es un enlace simbólico, no se seguirá en ningún caso. Si los enlaces simbólicos no están permitidos a través de esta función, PHYSFS_stat() los ignora y trataría la consulta como si la ruta no existiera en absoluto.

El permiso de enlace simbólico se puede habilitar o deshabilitar en cualquier momento después de haber llamado a PHYSFS_init(), y está deshabilitado por defecto.

Parámetros

allow distinto de cero para permitir enlaces simbólicos, cero para denegar enlaces.

void PHYSFS_setErrorCode (PHYSFS_ErrorCode code)

Establece el código de error del hilo actual. Esto le permite establecer el valor que devolverá la próxima llamada a PHYSFS_getLastErrorCode(). Esto reemplazará cualquier código de error existente, ya sea establecido por su aplicación o internamente por PhysicsFS.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Hace que un subdirectorio de un archivo sea su directorio raíz. Esto le permite acotar los archivos accesibles en un archivo específico. Por ejemplo, si tiene x.zip con un archivo en y/z.txt, montado en /a, si llama a PHYSFS_setRoot("x.zip", "/y"), entonces la llamada PHYSFS_openRead("/a/z.txt") tendrá éxito.

Puede cambiar la raíz de un archivo en cualquier momento, alterando el árbol de archivos interpolado (dependiendo de dónde cambien las rutas, un archivo diferente puede estar proporcionando varios archivos). Si establece la raíz a NULL o "/", el archivo se tratará como si no se hubiera establecido ninguna raíz especial (como si el archivo se hubiera montado normalmente).

Cambiar la raíz solo afecta a las operaciones futuras en los nombres de ruta; un archivo que se abrió desde una ruta que cambió debido a un setRoot no se verá afectado.

Establecer una nueva raíz no se limita a los archivos en la ruta de búsqueda; también puede establecer una en el directorio de escritura, lo que podría ser útil si tiene archivos abiertos para escritura y, por lo tanto, no puede cambiar el directorio de escritura en este momento.

No es un error establecer un subdirectorio que no existe como raíz de un archivo; sin embargo, no se verán archivos en este caso. Si los directorios faltantes terminan creándose (un mkdir en el sistema de archivos físico, etc.), esto se reflejará en el árbol interpolado.

Parámetros

archive directorio/archivo en el que cambiar la raíz.
subdir nuevo subdirectorio que será la raíz de este archivo.

Retorna

distinto de cero en caso de éxito, cero en caso de fallo. Use PHYSFS_getLastErrorCode() para obtener el error específico.

int PHYSFS_ucs4stricmp (const PHYSFS_uint32 * str1, const PHYSFS_uint32 * str2)

Case-insensitive compare of two UCS-4 strings. This is a strcasecmp/stricmp replacement that expects both strings to be in UCS-4 (aka UTF-32) encoding. It will do "case folding" to decide if the Unicode codepoints in the strings match.

It will report which string is "greater than" the other, but be aware that this doesn't necessarily mean anything: 'a' may be "less than" 'b', but a Japanese kuten has no meaningful alphabetically relationship to a Greek lambda, but being able to assign a reliable "value" makes sorting algorithms possible, if not entirely sane. Parameters

str1 First string to compare.
str2 Second string to compare.

Returns

-1 if str1 is "less than" str2, 1 if "greater than", 0 if equal.

Si no estás seguro, deberías estar usando UTF-16 en este punto en Windows.

Para asegurar que el búfer de destino sea lo suficientemente grande para la conversión, por favor, asigna un búfer que sea el doble del tamaño del búfer de origen. UTF-8 usa de uno a cuatro bytes por carácter, pero UTF-16 siempre usa de dos a cuatro, ¡así que una cadena completamente ASCII baja duplicará su tamaño! Los caracteres UTF-16 que tomarían cuatro bytes también toman cuatro bytes en UTF-8, así que no necesitas asignar 4x el espacio por si acaso: el doble será suficiente.

Las cadenas que no caben en el búfer de destino serán truncadas, pero siempre estarán terminadas en nulo y nunca tendrán un par sustituto UTF-16 incompleto al final. Si la longitud del búfer es 0, esta función no hace nada.

Parámetros

src Cadena de origen terminada en nulo en formato UTF-8.
dst Búfer para almacenar la cadena UTF-16 convertida.
len Tamaño, en bytes, del búfer de destino.

PHYSFS_writeUBE16, PHYSFS_writeUBE32, PHYSFS_writeUBE64, PHYSFS_writeULE16, PHYSFS_writeULE32, PHYSFS_writeULE64 — convert and write a value in a specified byte order.

Detailed Description

These functions are convenience wrappers for writing integers to files. They convert the integer from the platform's native byte order to the specified byte order (either big-endian or little-endian) and then write it to the supplied file handle.

These functions are useful for writing data to files in a platform- independent format.
