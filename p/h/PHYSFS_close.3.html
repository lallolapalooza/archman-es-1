int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

"Fold" a Unicode codepoint to a lowercase equivalent. (This is for limited, hardcore use. If you don't immediately see a need for it, you can probably ignore this forever.)

This will convert a Unicode codepoint into its lowercase equivalent. Bogus codepoints and codepoints without a lowercase equivalent will be returned unconverted.

Note that you might get multiple codepoints in return! The German Eszett, for example, will fold down to two lowercase latin 's' codepoints. The theory is that if you fold two strings, one with an Eszett and one with "SS" down, they will match.

Warning

Anyone that is a student of Unicode knows about the "Turkish I" problem. This API does not handle it. Assume this one letter in all of Unicode will definitely fold sort of incorrectly. If you don't know what this is about, you can probably ignore this problem for most of the planet, but perfection is impossible.

Parameters

from The codepoint to fold.
to Buffer to store the folded codepoint values into. This should point to space for at least 3 PHYSFS_uint32 slots.

Returns

The number of codepoints the folding produced. Between 1 and 3.

int PHYSFS_deinit (void )

Deinitialize the PhysicsFS library. This closes any files opened via PhysicsFS, blanks the search/write paths, frees memory, and invalidates all of your file handles.

Note that this call can FAIL if there's a file open for writing that refuses to close (for example, the underlying operating system was buffering writes to network filesystem, and the fileserver has crashed, or a hard drive has failed, etc). It is usually best to close all write handles yourself before calling this function, so that you can gracefully handle a specific failure.

Once successfully deinitialized, PHYSFS_init() can be called again to restart the subsystem. All default API states are restored at this point, with the exception of any custom allocator you might have specified, which survives between initializations.

Returns

nonzero on success, zero on error. Specifics of the error can be gleaned from PHYSFS_getLastError(). If failure, state of PhysFS is undefined, and probably badly screwed up.

int PHYSFS_delete (const char * filename)

Delete a file or directory. (filename) is specified in platform-independent notation in relation to the write dir.

A directory must be empty before this call can delete it.

Deleting a symlink will remove the link, not what it points to, regardless of whether you "permitSymLinks" or not.

So if you've got the write dir set to "C:\mygame\writedir" and call PHYSFS_delete("downloads/maps/level1.map") then the file "C:\mygame\writedir\downloads\maps\level1.map" is removed from the physical filesystem, if it exists and the operating system permits the deletion.

Note that on Unix systems, deleting a file may be successful, but the actual file won't be removed until all processes that have an open filehandle to it (including your program) close their handles.

Chances are, the bits that make up the file still exist, they are just made available to be written over at a later point. Don't consider this a security method or anything. :)

Parameters

filename Filename to delete.

Returns

nonzero on success, zero on error. Use PHYSFS_getLastErrorCode() to obtain the specific error.

Obtener una lista de archivos de un directorio de la ruta de búsqueda, utilizando una función de devolución de llamada definida por la aplicación, con informes de errores. Internamente, PHYSFS_enumerateFiles() simplemente llama a esta función y luego construye una lista antes de devolverla a la aplicación, por lo que la funcionalidad es idéntica, excepto por cómo se representa la información a la aplicación.

A diferencia de PHYSFS_enumerateFiles(), esta función no devuelve una matriz. Más bien, llama a una función especificada por la aplicación una vez por elemento de la ruta de búsqueda:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Tenemos [%s] en [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // dame más datos, por favor.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

No se garantiza que los elementos enviados a la función de devolución de llamada estén en ningún orden. No se realiza ninguna ordenación en este nivel y, si la necesita, probablemente debería usar PHYSFS_enumerateFiles() en su lugar, que garantiza la ordenación alfabética. Esta forma informa lo que se descubre en cada archivo antes de pasar al siguiente. Incluso dentro de un archivo, no podemos garantizar el orden en que se descubrirán los datos. Cualquier ordenación que encuentre en estas devoluciones de llamada es pura suerte. No confíe en ella. Dado que recorre toda la lista de archivos, puede recibir nombres de archivo duplicados.

Esta API y las propias devoluciones de llamada son capaces de informar errores. Antes de esta API, las devoluciones de llamada tenían que aceptar cada elemento enumerado, incluso si solo buscaban algo específico y querían detenerse después de eso, o si tenían un error grave y no podían alertar a nadie. Además, si PhysicsFS en sí tenía un problema (error de disco o similar), no podía informarlo a la aplicación que lo llamaba, solo tenía que omitir elementos o dejar de enumerar por completo, y el llamador no sabría que había perdido algunos datos en el camino.

Ahora el llamador puede estar seguro de que obtuvo un conjunto de datos completo, y su devolución de llamada tiene control si desea que la enumeración se detenga temprano. Consulte la documentación de PHYSFS_EnumerateCallback para obtener detalles sobre cómo debe comportarse su devolución de llamada.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Añade un archivo o directorio a la ruta de búsqueda. Si es un duplicado, la entrada no se añade de nuevo, aunque la función tenga éxito. No puedes añadir el mismo archivo a dos puntos de montaje diferentes: la comprobación de duplicados se realiza contra el archivo y no contra el punto de montaje.

Cuando montas un archivo, se añade a un sistema de archivos virtual... todos los archivos de todos los archivos se interpolan en un único árbol de archivos jerárquico. Dos archivos montados en el mismo lugar (o un archivo con archivos que se superponen a otro punto de montaje) pueden tener archivos que se superponen: en tal caso, se selecciona el archivo anterior en la ruta de búsqueda, y los otros archivos son inaccesibles para la aplicación. Esto permite que los archivos se utilicen para anular revisiones anteriores; puedes usar el mecanismo de montaje para colocar archivos en un punto específico del árbol de archivos y evitar la superposición; esto es útil para mods descargables que podrían pisotear datos de la aplicación o entre sí, por ejemplo.

El punto de montaje no necesita existir antes de montarlo, lo que es diferente a lo que aquellos familiarizados con el concepto de "montaje" de Unix pueden esperar. Además, más de un archivo puede montarse en el mismo punto de montaje, o los contenidos de puntos de montaje y archivos pueden superponerse... el mecanismo de interpolación sigue funcionando como de costumbre.

Especificar un enlace simbólico a un archivo o directorio está permitido aquí, independientemente del estado de PHYSFS_permitSymbolicLinks(). Esa función solo trata con enlaces simbólicos dentro del directorio o archivo montado.

Parameters

newDir directorio o archivo a añadir a la ruta, en notación dependiente de la plataforma.
mountPoint Ubicación en el árbol interpolado donde este archivo será "montado", en notación independiente de la plataforma. NULL o "" es equivalente a "/".
appendToPath Distinto de cero para añadir a la ruta de búsqueda, cero para preponer.

Returns

Distinto de cero si se añadió a la ruta, cero si hay un fallo (archivo inválido, directorio faltante, etc.). Usa PHYSFS_getLastErrorCode() para obtener el error específico.

Añade un archivo, contenido en un manejador PHYSFS_File, a la ruta de búsqueda.

Advertencia

A menos que tengas alguna necesidad especial de bajo nivel, deberías usar PHYSFS_mount() en lugar de esto.

¡Los archivos dentro de archivos pueden ser muy lentos! Mientras que un PHYSFS_File puede buscar incluso cuando los datos están comprimidos, puede hacerlo retrocediendo al principio y descomprimiendo todo antes del punto de búsqueda. El uso normal de archivos puede realizar muchas búsquedas en segundo plano. Como tal, podrías encontrar que el uso normal de archivos es extremadamente doloroso si se monta de esta manera. Planifica en consecuencia: si, por ejemplo, tienes un archivo .zip autoextraíble y quieres montar algo dentro de él, comprime el contenido del archivo interior y asegúrate de que el archivo .zip exterior no comprima también el archivo interior.

Esta función opera igual que PHYSFS_mount(), pero toma un manejador PHYSFS_File en lugar de una ruta de archivo. Este manejador contiene todos los datos del archivo y se utiliza en lugar de un archivo real en el sistema de archivos físico. El PHYSFS_File puede estar respaldado por un archivo real en el sistema de archivos físico, pero no es necesariamente así. El uso más popular para esto es probablemente montar archivos almacenados dentro de otros archivos.

(newDir) debe ser una cadena única para identificar este archivo. Se utiliza para optimizar la selección del archivador (si lo nombras XXXXX.zip, podríamos intentar primero el archivador ZIP, por ejemplo, o elegir directamente un archivador que solo pueda confiar en que los datos son válidos por la extensión del nombre del archivo). No necesita referirse a un archivo real en absoluto. Si la extensión del nombre del archivo no es útil, el sistema intentará con cada archivador hasta que uno funcione o ninguno lo haga. Este nombre de archivo debe ser único, ya que el sistema no te permitirá tener dos archivos con el mismo nombre.

(file) debe permanecer hasta que el archivo se desmonte. Cuando el archivo se desmonte, el sistema llamará a PHYSFS_close(file). Si necesitas que este manejador sobreviva, tendrás que envolverlo en un PHYSFS_Io y usar PHYSFS_mountIo() en su lugar.

Si esta función falla, PHYSFS_close(file) no se llama.

appendToPath distinto de cero para añadir a la ruta de búsqueda, cero para anteponer.

Devoluciones

Distinto de cero si se añadió a la ruta, cero en caso de fallo (archivo inválido, etc.). Usa PHYSFS_getLastErrorCode() para obtener el error específico.

int PHYSFS_registerArchiver (const PHYSFS_Archiver * archiver)

Añade un nuevo archivador al sistema.

Advertencia

Esto es algo avanzado y complejo. No lo necesitarás a menos que realmente sepas lo que estás haciendo. La mayoría de las aplicaciones no lo necesitarán.

Si deseas proporcionar tu propio archivador (por ejemplo, un formato de archivo personalizado, o algo virtual que quieras que parezca un sistema de archivos al que puedas acceder a través de las API habituales de PhysicsFS), aquí es donde empiezas. Internamente, PhysicsFS usa esta función para registrar sus propios archivadores integrados, como el soporte para .zip, etc.

Los datos en (archiver) se copian; puedes liberar este puntero cuando esta función retorne.

Una vez que esta función retorne con éxito, PhysicsFS podrá admitir archivos de este tipo hasta que desregistres el archivador nuevamente.

Cero en caso de error, distinto de cero en caso de éxito.

int PHYSFS_setAllocator (const PHYSFS_Allocator * allocator)

Conecta tus propias rutinas de asignación a PhysicsFS. (Esto es para uso limitado y avanzado. Si no ves inmediatamente una necesidad, probablemente puedes ignorarlo para siempre).

Por defecto, PhysicsFS usará lo que sea razonable para una plataforma para gestionar la memoria dinámica (generalmente malloc/realloc/free de ANSI C, pero algunas plataformas pueden usar algo más), pero en algunos casos poco comunes, la aplicación podría querer más control sobre la gestión de memoria de la biblioteca. Esto te permite redirigir PhysicsFS para que use tus propias rutinas de asignación en su lugar. Solo puedes llamar a esta función antes de PHYSFS_init(); si la biblioteca está inicializada, rechazará tus esfuerzos para cambiar el asignador a mitad de camino. Puedes llamar a esta función después de PHYSFS_deinit() si estás dispuesto a cerrar la biblioteca y reiniciarla con un nuevo asignador; esta es una operación segura y soportada. El asignador permanece intacto entre las llamadas de deinit/init. Si deseas volver al asignador predeterminado de la plataforma, pasa un NULL aquí.

Si no estás seguro de qué hacer con esta función de inmediato, puedes ignorarla por completo.

Parámetros

allocator Estructura que contiene los puntos de entrada de tu asignador.

Retorna

Cero en caso de fallo, distinto de cero en caso de éxito. Esta llamada solo falla cuando se usa entre las llamadas a PHYSFS_init() y PHYSFS_deinit().
