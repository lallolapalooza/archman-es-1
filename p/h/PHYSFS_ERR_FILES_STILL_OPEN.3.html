typedef PHYSFS_EnumerateCallbackResult(* PHYSFS_EnumerateCallback) (void *data, const char *origdir, const char *fname)

Possible return values from PHYSFS_EnumerateCallback. Function signature for callbacks that enumerate and return results.

These values dictate if an enumeration callback should continue to fire, or stop (and why it is stopping).

See also

PHYSFS_EnumerateCallback

PHYSFS_enumerate

This is the same thing as PHYSFS_EnumFilesCallback from PhysicsFS 2.0, except it can return a result from the callback: namely: if you're looking for something specific, once you find it, you can tell PhysicsFS to stop enumerating further. This is used with PHYSFS_enumerate(), which we hopefully got right this time. :)

Parameters

data User-defined data pointer, passed through from the API that eventually called the callback.
origdir A string containing the full path, in platform-independent notation, of the directory containing this file. In most cases, this is the directory on which you requested enumeration, passed in the callback for your convenience.
fname The filename that is being enumerated. It may not be in alphabetical order compared to other callbacks that have fired, and it will not contain the full path. You can recreate the fullpath with $origdir/$fname ... The file can be a subdirectory, a file, a symlink, etc.

Returns

A value from PHYSFS_EnumerateCallbackResult. All other values are (currently) undefined; don't use them.

typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Function signature for callbacks that enumerate files.

Warning

As of PhysicsFS 2.1, Use PHYSFS_EnumerateCallback with PHYSFS_enumerate() instead; it gives you more control over the process.

These are used to report a list of directory entries to an original caller, one file/dir/symlink per callback. All strings are UTF-8 encoded. Functions should not try to modify or free any string's memory.

These callbacks are used, starting in PhysicsFS 1.1, as an alternative to functions that would return lists that need to be cleaned up with PHYSFS_freeList(). The callback means that the library doesn't need to allocate an entire list and all the strings up front.

Be aware that promised data ordering in the list versions are not necessarily so in the callback versions. Check the documentation on specific APIs, but strings may not be sorted as you expect and you might get duplicate strings.

Parameters

data User-defined data pointer, passed through from the API that eventually called the callback.
origdir A string containing the full path, in platform-independent notation, of the directory containing this file. In most cases, this is the directory on which you requested enumeration, passed in the callback for your convenience.
fname The filename that is being enumerated. It may not be in alphabetical order compared to other callbacks that have fired, and it will not contain the full path. You can recreate the fullpath with $origdir/$fname ... The file can be a subdirectory, a file, a symlink, etc.

enum PHYSFS_ErrorCode

Values that represent specific causes of failure. Most of the time, you should only concern yourself with whether a given operation failed or not, but there may be occasions where you plan to handle a specific failure case gracefully, so we provide specific error codes.

Most of these errors are a little vague, and most aren't things you can fix...if there's a permission error, for example, all you can really do is pass that information on to the user and let them figure out how to handle it. In most these cases, your program should only care that it failed to accomplish its goals, and not care specifically why.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtener una lista de archivos de un directorio de la ruta de búsqueda, utilizando un callback definido por la aplicación, con errores reportados. Internamente, PHYSFS_enumerateFiles() simplemente llama a esta función y luego crea una lista antes de devolverla a la aplicación, por lo que la funcionalidad es idéntica excepto por cómo se representa la información a la aplicación.

A diferencia de PHYSFS_enumerateFiles(), esta función no devuelve una matriz. En su lugar, llama a una función especificada por la aplicación una vez por cada elemento de la ruta de búsqueda:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Tenemos [%s] en [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // dame más datos, por favor.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

No se garantiza que los elementos enviados al callback estén en ningún orden específico. No hay ordenación en este nivel, y si la necesitas, probablemente deberías usar PHYSFS_enumerateFiles() en su lugar, que garantiza la ordenación alfabética. Esta forma informa lo que se descubre en cada archivo antes de pasar al siguiente. Incluso dentro de un archivo, no podemos garantizar el orden en que descubrirá los datos. *Cualquier ordenación que encuentres en estos callbacks es pura suerte. No confíes en ella.* A medida que recorre toda la lista de archivos, puedes recibir nombres de archivo duplicados.

Esta API y los propios callbacks son capaces de reportar errores. Antes de esta API, los callbacks tenían que aceptar cada elemento enumerado, incluso si solo buscaban algo específico y querían detenerse después, o tenían un error grave y no podían alertar a nadie. Además, si PhysicsFS en sí tenía un problema (error de disco o similar), no podía informarlo a la aplicación que llamaba, solo tendría que omitir elementos o dejar de enumerar por completo, y el llamador no sabría que perdió algunos datos en el camino.

Ahora el llamador puede estar seguro de que obtuvo un conjunto de datos completo, y su callback tiene control si desea que la enumeración se detenga pronto. Consulte la documentación de PHYSFS_EnumerateCallback para obtener detalles sobre cómo debe comportarse su callback.

Parámetros

dir Directorio, en notación independiente de la plataforma, a enumerar.
c Función de callback para notificar sobre los elementos de la ruta de búsqueda.
d Datos definidos por la aplicación pasados al callback. Puede ser NULL.

Devoluciones

Distinto de cero en caso de éxito, cero en caso de fallo. Usa PHYSFS_getLastErrorCode() para obtener el error específico. Si el callback devuelve PHYSFS_ENUM_STOP para detenerse anticipadamente, esto se considerará un éxito. Los callbacks que devuelvan PHYSFS_ENUM_ERROR harán que esta función devuelva cero y establezca el código de error en PHYSFS_ERR_APP_CALLBACK.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Añadir un archivo o directorio a la ruta de búsqueda. Si es un duplicado, la entrada no se añade de nuevo, aunque la función tenga éxito. No puede añadir el mismo archivo a dos puntos de montaje diferentes: la comprobación de duplicados se realiza contra el archivo y no contra el punto de montaje.

Cuando monta un archivo, se añade a un sistema de archivos virtual... todos los archivos en todos los archivos se interpolan en un único árbol de archivos jerárquico. Dos archivos montados en el mismo lugar (o un archivo con archivos que se solapan con otro punto de montaje) pueden tener archivos superpuestos: en tal caso, se selecciona el archivo más temprano en la ruta de búsqueda, y los otros archivos son inaccesibles para la aplicación. Esto permite que los archivos se utilicen para reemplazar revisiones anteriores; puede utilizar el mecanismo de montaje para colocar archivos en un punto específico del árbol de archivos y evitar la superposición; esto es útil para mods descargables que podrían pisar datos de la aplicación o entre sí, por ejemplo.

El punto de montaje no necesita existir antes de montarlo, lo cual es diferente de lo que pueden esperar aquellos familiarizados con el concepto de "montaje" de Unix. Además, más de un archivo puede ser montado en el mismo punto de montaje, o los puntos de montaje y el contenido de los archivos pueden superponerse... el mecanismo de interpolación aún funciona como de costumbre.

Se permite especificar un enlace simbólico a un archivo o directorio aquí, independientemente del estado de PHYSFS_permitSymbolicLinks(). Esa función solo trata con enlaces simbólicos dentro del directorio o archivo montado.

void PHYSFS_permitSymbolicLinks (int allow)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y archivos contienen archivos que son solo punteros a otros archivos. En el sistema de archivos físico, abrir dicho enlace abrirá (transparentemente) el archivo al que se apunta.

Por defecto, PhysicsFS comprobará si un archivo es realmente un enlace simbólico durante las llamadas de apertura y fallará si lo es. De lo contrario, el enlace podría sacarte de las rutas de escritura y búsqueda, y comprometer la seguridad.

Si quieres asumir ese riesgo, llama a esta función con un parámetro distinto de cero. Ten en cuenta que esto es más para sandboxear el lenguaje de scripting de un programa, en caso de que scripts no confiables intenten comprometer el sistema. En general, un usuario podría tener una razón legítima para configurar un enlace simbólico, por lo que a menos que sientas que hay un peligro específico en permitirlos, deberías permitirlos.

Los enlaces simbólicos solo se comprueban explícitamente cuando se trata con nombres de archivo en notación independiente de la plataforma. Es decir, al configurar tus rutas de búsqueda y escritura, etc., nunca se comprueban los enlaces simbólicos.

Ten en cuenta que PHYSFS_stat() siempre comprobará la ruta especificada; si esa ruta es un enlace simbólico, no se seguirá en ningún caso. Si los enlaces simbólicos no están permitidos a través de esta función, PHYSFS_stat() los ignora y trataría la consulta como si la ruta no existiera en absoluto.

El permiso de enlace simbólico se puede habilitar o deshabilitar en cualquier momento después de haber llamado a PHYSFS_init(), y está deshabilitado por defecto.

allow distinto de cero para permitir enlaces simbólicos, cero para denegar el enlace.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Make a subdirectory of an archive its root directory. This lets you narrow down the accessible files in a specific archive. For example, if you have x.zip with a file in y/z.txt, mounted to /a, if you call PHYSFS_setRoot("x.zip", "/y"), then the call PHYSFS_openRead("/a/z.txt") will succeed.

Set up sane, default paths. Helper function.

The write dir will be set to the pref dir returned by

PHYSFS_getPrefDir(organization, appName)

, which is created if it doesn't exist.

The above is sufficient to make sure your program's configuration directory is separated from other clutter, and platform-independent.

The search path will be:

  • The Write Dir (created if it doesn't exist)
  • The Base Dir (PHYSFS_getBaseDir())
  • All found CD-ROM dirs (optionally)

These directories are then searched for files ending with the extension (archiveExt), which, if they are valid and supported archives, will also be added to the search path. If you specified "PKG" for (archiveExt), and there's a file named data.PKG in the base dir, it'll be checked. Archives can either be appended or prepended to the search path in alphabetical order, regardless of which directories they were found in. All archives are mounted in the root of the virtual file system ("/") .

All of this can be accomplished from the application, but this just does it all for you. Feel free to add more to the search path manually, too.

NAME

PHYSFS_writeUBE16, PHYSFS_writeUBE32, PHYSFS_writeUBE64, PHYSFS_writeULE16, PHYSFS_writeULE32, PHYSFS_writeULE64 - convert and write integers in specific byte order

SYNOPSIS

int PHYSFS_writeUBE16(PHYSFS_File *file, PHYSFS_uint16 val)

int PHYSFS_writeUBE32(PHYSFS_File *file, PHYSFS_uint32 val)

int PHYSFS_writeUBE64(PHYSFS_File *file, PHYSFS_uint64 val)

int PHYSFS_writeULE16(PHYSFS_File *file, PHYSFS_uint16 val)

int PHYSFS_writeULE32(PHYSFS_File *file, PHYSFS_uint32 val)

int PHYSFS_writeULE64(PHYSFS_File *file, PHYSFS_uint64 val)

DESCRIPTION

These functions are convenience functions for writing unsigned integer types to a PHYSFS_File in a specific byte order. They convert the value from the platform's native byte order to the specified order (big endian or little endian), and then write it to the file.

The functions are named according to the following convention:

  • U: Unsigned integer.
  • B: Big endian byte order.
  • L: Little endian byte order.
  • E: Endianness conversion (always present).
  • The number indicates the number of bits in the integer type (16, 32, or 64).

For example, PHYSFS_writeUBE16 writes an unsigned 16-bit integer in big endian format.

These functions are useful when dealing with file formats that specify a particular byte order, independent of the host machine's architecture.

PARAMETERS

file
A pointer to the PHYSFS_File structure representing the file to which the data will be written.
val
The unsigned integer value to be converted and written. The type of this parameter corresponds to the size specified in the function name (e.g., PHYSFS_uint16 for PHYSFS_writeUBE16).

RETURN VALUES

All these functions return non-zero on success and zero on failure. If a failure occurs, the specific error can be retrieved using PHYSFS_getLastErrorCode.

WARNINGS

The PHYSFS_uint64 type is only 32 bits wide on platforms that do not have native 64-bit integer support. Be mindful of this limitation when using PHYSFS_writeUBE64 or PHYSFS_writeULE64 on such platforms.
