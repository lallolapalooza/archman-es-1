int PHYSFS_deinit (void )

Desinicializa la biblioteca PhysicsFS. Esto cierra todos los archivos abiertos a través de PhysicsFS, borra las rutas de búsqueda/escritura, libera memoria e invalida todos sus manejadores de archivos.

Tenga en cuenta que esta llamada puede FALLAR si hay un archivo abierto para escritura que se niega a cerrarse (por ejemplo, el sistema operativo subyacente estaba almacenando en búfer escrituras en un sistema de archivos de red, y el servidor de archivos ha fallado, o un disco duro ha fallado, etc.). Generalmente es mejor cerrar todos los manejadores de escritura usted mismo antes de llamar a esta función, para poder manejar con gracia un fallo específico.

Una vez desinicializado con éxito, se puede llamar a PHYSFS_init() nuevamente para reiniciar el subsistema. Todos los estados predeterminados de la API se restauran en este punto, con la excepción de cualquier asignador personalizado que haya especificado, que sobrevive entre inicializaciones.

Devuelve

distinto de cero si tiene éxito, cero si hay un error. Los detalles del error se pueden obtener de PHYSFS_getLastError(). Si falla, el estado de PhysFS no está definido y probablemente muy dañado.

int PHYSFS_delete (const char * filename)

Elimina un archivo o directorio. (filename) se especifica en notación independiente de la plataforma en relación con el directorio de escritura.

Un directorio debe estar vacío antes de que esta llamada pueda eliminarlo.

La eliminación de un enlace simbólico eliminará el enlace, no lo que apunta, independientemente de si "permiteEnlaceSimbolico" o no.

Entonces, si tienes el directorio de escritura configurado en "C:\mygame\writedir" y llamas a PHYSFS_delete("downloads/maps/level1.map") entonces el archivo "C:\mygame\writedir\downloads\maps\level1.map" se elimina del sistema de archivos físico, si existe y el sistema operativo permite la eliminación.

Tenga en cuenta que en sistemas Unix, la eliminación de un archivo puede tener éxito, pero el archivo real no se eliminará hasta que todos los procesos que tengan un manejador de archivo abierto para él (incluido su programa) cierren sus manejadores.

Lo más probable es que los bits que componen el archivo aún existan, simplemente se ponen a disposición para ser sobrescritos en un momento posterior. No considere esto como un método de seguridad ni nada parecido. :)

Parámetros

filename Nombre del archivo a eliminar.

Devuelve

distinto de cero si tiene éxito, cero si hay un error. Use PHYSFS_getLastErrorCode() para obtener el error específico.

int PHYSFS_deregisterArchiver (const char * ext)

Elimina un archivador del sistema. Si por alguna razón, solo necesita que su archivador registrado previamente viva durante una parte de la vida útil de su aplicación, puede eliminarlo del sistema una vez que haya terminado con él a través de esta función.

Esto falla si todavía hay archivos abiertos que usan este archivador.

Esta función también puede eliminar archivadores proporcionados internamente, como el soporte para .zip o similar. int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

mountPoint Location in the interpolated tree that this archive will be "mounted", in platform-independent notation. NULL or "" is equivalent to "/".
appendToPath nonzero to append to search path, zero to prepend.

void PHYSFS_permitSymbolicLinks(int allow)

Activa o desactiva el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y archivados contienen archivos que son simplemente enlaces a otros archivos. Al abrir un enlace simbólico en un sistema físico, este se abrirá transparentemente para el archivo al que se refiere.

Por defecto, PhysicsFS verifica si un archivo es realmente un enlace simbólico durante las llamadas de apertura y falla si lo es. De lo contrario, el enlace podría llevarte fuera de los caminos de lectura y escritura, comprometiendo la seguridad.

Si quieres asumir ese riesgo, llama a esta función con un valor distinto de cero. Ten en cuenta que esto es más para el sandboxing de lenguajes de script de un programa, en caso de que scripts no confiables intenten comprometer el sistema. En general, un usuario podría tener una razón legítima para crear un enlace simbólico, así que no deberías desactivarlos, a menos que sientas un peligro específico.

Los enlaces simbólicos solo se verán explícitamente cuando se manejan nombres de archivo en notación independiente de la plataforma. Es decir, cuando estableces tus caminos de búsqueda y escritura, etc., los enlaces simbólicos nunca se verán.

Nota: PHYSFS_stat() siempre verifica la ruta especificada; si esa ruta es un enlace simbólico, no se seguirá en ningún caso. Si los enlaces simbólicos no están permitidos a través de esta función, PHYSFS_stat() los ignora y trataría la consulta como si la ruta no existiera.

El permiso de enlaces simbólicos puede ser activado o desactivado en cualquier momento después de haber llamado a PHYSFS_init(), y está desactivado por defecto.

Parámetros

allow distinto de cero para permitir enlaces simbólicos, cero para deshabilitar el enlace.

Ver también

Advertencia

Esto es para uso avanzado y profundo. No lo necesita a menos que sepa realmente lo que está haciendo. La mayoría de las aplicaciones no lo necesitarán.

Si desea proporcionar su propio archivador (por ejemplo, un formato de archivo personalizado, o algo virtual que desee que parezca un sistema de archivos al que pueda acceder a través de las APIs habituales de PhysicsFS), aquí es donde empieza. Una vez que un archivador se registra correctamente, puede utilizar PHYSFS_mount() para añadir archivos que su archivador soporta a la ruta de búsqueda, o quizás utilizarlo como directorio de escritura. Internamente, PhysicsFS utiliza esta función para registrar sus propios archivadores integrados, como el soporte para .zip, etc.

No puede tener dos archivadores que manejen la misma extensión. Si va a haber un conflicto, puede desregistrar el otro archivador (incluidos los integrados) con PHYSFS_deregisterArchiver().

Los datos en (archiver) se copian; puede liberar este puntero cuando esta función retorne.

Una vez que esta función retorne con éxito, PhysicsFS podrá dar soporte a archivos de este tipo hasta que vuelva a desregistrar el archivador.

Parámetros

archiver El archivador a registrar.

Retorno

cero en caso de error, distinto de cero en caso de éxito.

int PHYSFS_removeFromSearchPath (const char * oldDir)

Obsoleto

A partir de PhysicsFS 2.1, utilice PHYSFS_unmount() en su lugar. Esta función simplemente lo envuelve de todos modos. No hay ninguna diferencia funcional excepto que el vocabulario cambió de "añadir a la ruta de búsqueda" a "montar" cuando esa funcionalidad se extendió, y por lo tanto, la forma preferida de realizar el trabajo de esta función ahora se llama "desmontar".

Esta función es equivalente a:

PHYSFS_unmount(oldDir);

Debe utilizar esta y no PHYSFS_unmount si la compatibilidad binaria con PhysicsFS 1.0 es importante (lo cual puede que no sea para muchas personas).

int PHYSFS_setAllocator (const PHYSFS_Allocator * allocator)

Conecta tus propias rutinas de asignación en PhysicsFS. (Esto es para un uso limitado y profundo. Si no ve inmediatamente una necesidad para ello, probablemente pueda ignorarlo para siempre.)

Por defecto, PhysicsFS utilizará lo que sea razonable para una plataforma para gestionar la memoria dinámica (generalmente malloc/realloc/free de ANSI C, pero algunas plataformas pueden usar algo diferente), pero en algunos casos poco comunes, la aplicación puede querer un mayor control sobre la gestión de memoria de la biblioteca. Esto le permite redirigir PhysicsFS para que utilice sus propias rutinas de asignación. Solo puede llamar a esta función antes de PHYSFS_init(); si la biblioteca está inicializada, rechazará sus esfuerzos por cambiar el asignador a mitad de camino. Puede llamar a esta función después de PHYSFS_deinit() si está dispuesto a cerrar la biblioteca y reiniciarla con un nuevo asignador; esta es una operación segura y soportada. El asignador permanece intacto entre las llamadas de deinit/init. Si desea volver al asignador por defecto de la plataforma, pase un NULL aquí.

Si no está seguro de qué hacer con esta función de inmediato, puede ignórala por completo sin riesgo.

Parámetros

allocator Estructura que contiene los puntos de entrada de su asignador.

Retorno

cero en caso de fallo, distinto de cero en caso de éxito. Esta llamada solo falla cuando se utiliza entre llamadas a PHYSFS_init() y PHYSFS_deinit().

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convert a Latin1 string to a UTF-8 string. Latin1 strings are 8-bits per character: a popular "high ASCII" encoding.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 expands latin1 codepoints over 127 from 1 to 2 bytes, so the string may grow in some cases.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-8 sequence at the end. If the buffer length is 0, this function does nothing.

Please note that we do not supply a UTF-8 to Latin1 converter, since Latin1 can't express most Unicode codepoints. It's a legacy encoding; you should be converting away from it at all times.

Parameters

src Null-terminated source string in Latin1 format.
dst Buffer to store converted UTF-8 string.
len Size, in bytes, of destination buffer.

Advertencia

Esta función no informará de un error si hay secuencias UTF-8 inválidas en la cadena fuente. Las reemplazará con un carácter '?' y continuará.

NAME

PHYSFS_writeUBE16, PHYSFS_writeUBE32, PHYSFS_writeUBE64, PHYSFS_writeULE16, PHYSFS_writeULE32, PHYSFS_writeULE64 - Write endian-specific values to an archive.

SYNOPSIS

#include <physfs.h>

int PHYSFS_writeUBE16( PHYSFS_File * file, PHYSFS_uint16 val );

int PHYSFS_writeUBE32( PHYSFS_File * file, PHYSFS_uint32 val );

int PHYSFS_writeUBE64( PHYSFS_File * file, PHYSFS_uint64 val );

int PHYSFS_writeULE16( PHYSFS_File * file, PHYSFS_uint16 val );

int PHYSFS_writeULE32( PHYSFS_File * file, PHYSFS_uint32 val );

int PHYSFS_writeULE64( PHYSFS_File * file, PHYSFS_uint64 val );

Detailed Description

These functions are convenience functions that simplify writing multi-byte values to disk. They convert the value from the platform's native byte order to the specified endianness and then write the bytes to the file.

All of these functions are equivalent to:

    return PHYSFS_write(file, &byteOrderedValue, sizeof(byteOrderedValue), 1);

where byteOrderedValue is the value after it has been converted to the specified endianness.
