typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Firma de función para callbacks que enumeran archivos.

Advertencia

A partir de PhysicsFS 2.1, usa PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; te da más control sobre el proceso.

Estos se utilizan para informar una lista de entradas de directorio a un llamador original, un archivo/directorio/enlace simbólico por callback. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de ninguna cadena.

Estos callbacks se utilizan, a partir de PhysicsFS 1.1, como una alternativa a las funciones que devolverían listas que necesitan ser limpiadas con PHYSFS_freeList(). El callback significa que la biblioteca no necesita asignar una lista completa y todas las cadenas por adelantado.

Ten en cuenta que el orden de los datos prometido en las versiones de lista no es necesariamente el mismo en las versiones de callback. Consulta la documentación de APIs específicas, pero es posible que las cadenas no estén ordenadas como esperas y podrías obtener cadenas duplicadas.

fname El nombre del archivo que se está enumerando. Puede que no esté en orden alfabético en comparación con otros callbacks que se han ejecutado, y no contendrá la ruta completa. Puedes recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtiene una lista de archivos de un directorio de la ruta de búsqueda, utilizando una función de devolución de llamada definida por la aplicación, con informes de errores. Internamente, PHYSFS_enumerateFiles() simplemente llama a esta función y luego crea una lista antes de devolverla a la aplicación, por lo que la funcionalidad es idéntica excepto por la forma en que se representa la información a la aplicación.

A diferencia de PHYSFS_enumerateFiles(), esta función no devuelve una matriz. En su lugar, llama a una función especificada por la aplicación una vez por cada elemento de la ruta de búsqueda:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Tenemos [%s] en [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // dame más datos, por favor.
}
// ...
PHYSFS_enumerate("/alguna/ruta", printDir, NULL);

No se garantiza que los elementos enviados a la función de devolución de llamada estén en ningún orden específico. No se realiza ninguna ordenación a este nivel, y si la necesita, probablemente debería usar PHYSFS_enumerateFiles() en su lugar, que garantiza la ordenación alfabética. Esta forma informa lo que se descubre en cada archivo antes de pasar al siguiente. Incluso dentro de un mismo archivo, no podemos garantizar el orden en que descubrirá los datos. Cualquier orden que encuentre en estas devoluciones de llamada es pura suerte. No confíe en ello. Dado que recorre toda la lista de archivos, es posible que reciba nombres de archivo duplicados.

Esta API y las propias funciones de devolución de llamada son capaces de informar errores. Antes de esta API, las funciones de devolución de llamada tenían que aceptar cada elemento enumerado, incluso si solo buscaban algo específico y querían detenerse después, o si tenían un error grave y no podían alertar a nadie. Además, si PhysicsFS en sí tenía un problema (error de disco o similar), no podía informarlo a la aplicación que lo llamaba, solo tenía que omitir elementos o dejar de enumerar directamente, y el que lo llamaba no sabría que había perdido algunos datos en el camino.

Ahora, el que llama puede estar seguro de que obtuvo un conjunto completo de datos, y su función de devolución de llamada tiene control si desea que la enumeración se detenga antes. Consulte la documentación de PHYSFS_EnumerateCallback para obtener detalles sobre cómo debe comportarse su función de devolución de llamada.

Parámetros

dir Directorio, en notación independiente de la plataforma, a enumerar.
c Función de devolución de llamada para notificar sobre elementos de la ruta de búsqueda.
d Datos definidos por la aplicación pasados a la función de devolución de llamada. Puede ser NULL.

Devoluciones

Distinto de cero en caso de éxito, cero en caso de fallo. Utilice PHYSFS_getLastErrorCode() para obtener el error específico. Si la función de devolución de llamada devuelve PHYSFS_ENUM_STOP para detenerse antes, esto se considerará un éxito. Las funciones de devolución de llamada que devuelvan PHYSFS_ENUM_ERROR harán que esta función devuelva cero y establezca el código de error en PHYSFS_ERR_APP_CALLBACK.

Obtiene el "directorio de preferencias". Se pretende que sea donde los usuarios puedan escribir archivos personales (preferencias y partidas guardadas, etc.) que sean específicos de tu aplicación. Este directorio es único por usuario, por aplicación.

PHYSFS_mount

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

¡Los archivos dentro de archivos pueden ser muy lentos! Mientras que un PHYSFS_File puede buscar incluso cuando los datos están comprimidos, puede hacerlo rebobinando al principio y descomprimiendo todo antes del punto de búsqueda. El uso normal de archivos puede implicar muchas búsquedas en segundo plano. Como tal, podría encontrar que el uso normal de archivos es extremadamente doloroso si se monta de esta manera. Planifique en consecuencia: si, por ejemplo, tiene un archivo .zip autoextraíble y desea montar algo en él, comprima el contenido del archivo interno y asegúrese de que el archivo .zip externo no comprima también el archivo interno.

Set the buffering for a given file handle. This function allows you to control buffering for a specific file handle. By default, all file handles are unbuffered.

The actual buffer size allocated may be larger than requested. This is because we allocate space for padding, and also because we don't want to have to do a buffer flush during a write when the buffer is full. We want to guarantee that we can write to the buffer until it's full.

If you call this on a file that has already been written to, the previous buffer will be flushed and discarded. If you are writing to a file, and you change the buffer size, this will implicitly cause a flush...check your return values!

Seeking, etc transparently accounts for buffering.

You can resize an existing buffer by calling this function more than once on the same file. Setting the buffer size to zero will free an existing buffer.

PhysicsFS file handles are unbuffered by default.

Please check the return value of this function! Failures can include not being able to seek backwards in a read-only file when removing the buffer, not being able to allocate the buffer, and not being able to flush the buffer to disk, among other unexpected problems.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Haz que un subdirectorio de un archivo sea su directorio raíz. Esto te permite delimitar los archivos accesibles en un archivo específico. Por ejemplo, si tienes x.zip con un archivo en y/z.txt, montado en /a, si llamas a PHYSFS_setRoot("x.zip", "/y"), entonces la llamada PHYSFS_openRead("/a/z.txt") tendrá éxito.

Puedes cambiar la raíz de un archivo en cualquier momento, alterando el árbol de archivos interpolado (dependiendo de dónde cambien las rutas, un archivo diferente puede estar proporcionando varios archivos). Si estableces la raíz a NULL o "/", el archivo se tratará como si no se hubiera establecido ninguna raíz especial (como si el archivo se hubiera montado normalmente).

Cambiar la raíz solo afecta a las operaciones futuras en los nombres de ruta; un archivo que se abrió desde una ruta que cambió debido a un setRoot no se verá afectado.

Establecer una nueva raíz no se limita a los archivos en la ruta de búsqueda; también puedes establecer una en el directorio de escritura, lo que podría ser útil si tienes archivos abiertos para escritura y por lo tanto no puedes cambiar el directorio de escritura en este momento.

No es un error establecer un subdirectorio que no existe como raíz de un archivo; sin embargo, no se verán archivos en este caso. Si los directorios faltantes terminan siendo creados (un mkdir en el sistema de archivos físico, etc.), esto se reflejará en el árbol interpolado.

archive directorio/archivo sobre el cual cambiar la raíz.
subdir nuevo subdirectorio para hacer la raíz de este archivo.

Retorna

distinto de cero en caso de éxito, cero en caso de fallo. Usa PHYSFS_getLastErrorCode() para obtener el error específico.

void PHYSFS_utf8ToUtf16 (const char * src, PHYSFS_uint16 * dst, PHYSFS_uint64 len)

Convert a UTF-8 string to a UTF-16 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UTF-16 strings are 16-bits per character (except some chars, which are 32-bits): TCHAR on Windows, when building with Unicode support. Modern Windows releases use UTF-16. Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-16 surrogate pair at the end. If the buffer length is 0, this function does nothing.

Parameters

src Null-terminated source string in UTF-8 format.
dst Buffer to store converted UTF-16 string.
len Size, in bytes, of destination buffer.

Detailed Description

These functions are convenience wrappers for writing integers to a file in a specific endianness. They convert the value from the platform's native byte order to the specified endianness (big-endian or little-endian) before writing it to the file handle.
