#define PHYSFS_file PHYSFS_File

1.0 API compatibility define. PHYSFS_file is identical to PHYSFS_File. This #define is here for backwards compatibility with the 1.0 API, which had an inconsistent capitalization convention in this case. New code should use PHYSFS_File, as this #define may go away someday.

    (x)->minor = PHYSFS_VER_MINOR; \
    (x)->patch = PHYSFS_VER_PATCH; \

Macro to determine PhysicsFS version program was compiled against. This macro fills in a PHYSFS_Version structure w

con la versión de la biblioteca con la que compilaste. Esto se determina por el encabezado que utiliza el compilador. Ten en cuenta que si vinculaste la biblioteca dinámicamente, es posible que tengas una versión ligeramente más nueva o más antigua en tiempo de ejecución. Esa versión se puede determinar con PHYSFS_getLinkedVersion(), que, a diferencia de PHYSFS_VERSION, no es una macro.

PHYSFS_enumerate

Esto es lo mismo que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, excepto que puede devolver un resultado del callback: es decir, si estás buscando algo específico, una vez que lo encuentras, puedes indicar a PhysicsFS que deje de enumerar más. Esto se utiliza con PHYSFS_enumerate(), que esperamos que hayamos hecho bien esta vez. :)

Parámetros

data Puntero de datos definido por el usuario, pasado desde la API que finalmente llamó al callback.
origdir Una cadena que contiene la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio sobre el que solicitaste la enumeración, pasado en el callback para tu conveniencia.
fname El nombre del archivo que se está enumerando. Puede que no esté en orden alfabético en comparación con otros callbacks que se hayan ejecutado, y no contendrá la ruta completa. Puedes recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

Retorna

Un valor de PHYSFS_EnumerateCallbackResult. Todos los demás valores están (actualmente) indefinidos; no los uses.

typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Firma de función para callbacks que enumeran archivos.

Advertencia

A partir de PhysicsFS 2.1, utiliza PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; te da más control sobre el proceso.

Estos se utilizan para informar una lista de entradas de directorio a un llamador original, un archivo/directorio/enlace simbólico por callback. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de ninguna cadena.

Estos callbacks se utilizan, a partir de PhysicsFS 1.1, como una alternativa a las funciones que devolverían listas que necesitan ser liberadas con PHYSFS_freeList(). El callback significa que la biblioteca no necesita asignar una lista completa y todas las cadenas por adelantado.

Ten en cuenta que el orden de los datos prometido en las versiones de lista no es necesariamente así en las versiones de callback. Consulta la documentación de APIs específicas, pero las cadenas pueden no estar ordenadas como esperas y podrías obtener cadenas duplicadas.

Parámetros

data Puntero de datos definido por el usuario, pasado desde la API que finalmente llamó al callback.
origdir Una cadena que contiene la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio sobre el que solicitaste la enumeración, pasado en el callback para tu conveniencia.
fname El nombre del archivo que se está enumerando. Puede que no esté en orden alfabético en comparación con otros callbacks que se hayan ejecutado, y no contendrá la ruta completa. Puedes recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

int PHYSFS_deinit(void)

Deinitialize the PhysicsFS library. This closes any files opened via PhysicsFS, blanks the search/write paths, frees memory, and invalidates all of your file handles.

Note that this call can FAIL if there's a file open for writing that refuses to close (for example, the underlying operating system was buffering writes to network filesystem, and the fileserver has crashed, or a hard drive has failed, etc). It is usually best to close all write handles yourself before calling this function, so that you can gracefully handle a specific failure.

Once successfully deinitialized, PHYSFS_init() can be called again to restart the subsystem. All default API states are restored at this point, with the exception of any custom allocator you might have specified, which survives between initializations.

int PHYSFS_delete(const char *filename)

Delete a file or directory. (filename) is specified in platform-independent notation in relation to the write dir.

A directory must be empty before this call can delete it.

Deleting a symlink will remove the link, not what it points to, regardless of whether you "permitSymLinks" or not.

So if you've got the write dir set to "C:\mygame\writedir" and call PHYSFS_delete("downloads/maps/level1.map") then the file "C:\mygame\writedir\downloads\maps\level1.map" is removed from the physical filesystem, if it exists and the operating system permits the deletion.

Note that on Unix systems, deleting a file may be successful, but the actual file won't be removed until all processes that have an open filehandle to it (including your program) close their handles.

Chances are, the bits that make up the file still exist, they are just made available to be written over at a later point. Don't consider this a security method or anything. :)

Parameters

filename Filename to delete.

Returns

nonzero on success, zero on error. Use PHYSFS_getLastErrorCode() to obtain the specific error.

int PHYSFS_enumerate(const char *dir, PHYSFS_EnumerateCallback c, void *d)

Obtiene una lista de archivos de un directorio de ruta de búsqueda, utilizando una devolución de llamada definida por la aplicación, con errores informados. Internamente, PHYSFS_enumerateFiles() simplemente llama a esta función y luego crea una lista antes de devolverla a la aplicación, por lo que la funcionalidad es idéntica excepto por cómo se representa la información a la aplicación.

A diferencia de PHYSFS_enumerateFiles(), esta función no devuelve una matriz. En su lugar, llama a una función especificada por la aplicación una vez por elemento de la ruta de búsqueda:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Tenemos [%s] en [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // dame más datos, por favor.
}
// ...
PHYSFS_enumerate("/alguna/ruta", printDir, NULL);

No se garantiza que los elementos enviados a la devolución de llamada estén en ningún orden específico. No se realiza ninguna ordenación a este nivel, y si la necesita, probablemente debería usar PHYSFS_enumerateFiles() en su lugar, que garantiza la ordenación alfabética. Esta forma informa lo que se descubre en cada archivo antes de pasar al siguiente. Incluso dentro de un archivo, no podemos garantizar el orden en que descubrirá los datos. *Cualquier ordenación que encuentre en estas devoluciones de llamada es pura suerte. No dependa de ella.* A medida que recorre toda la lista de archivos, puede recibir nombres de archivo duplicados.

Esta API y las devoluciones de llamada en sí mismas son capaces de informar errores. Antes de esta API, las devoluciones de llamada tenían que aceptar cada elemento enumerado, incluso si solo buscaban algo específico y querían detenerse después de eso, o tenían un error grave y no podían alertar a nadie. Además, si PhysicsFS en sí mismo tenía un problema (error de disco o similar), no podía informarlo a la aplicación que lo llamaba, solo tendría que omitir elementos o detener la enumeración directamente, y el llamador no sabría que había perdido algunos datos en el camino.

Ahora el llamador puede estar seguro de que obtuvo un conjunto de datos completo, y su devolución de llamada tiene control si desea que la enumeración se detenga anticipadamente. Consulte la documentación de PHYSFS_EnumerateCallback para obtener detalles sobre cómo debe comportarse su devolución de llamada.

Parámetros

dir Directorio, en notación independiente de la plataforma, a enumerar.
c Función de devolución de llamada para notificar sobre elementos de la ruta de búsqueda.
d Datos definidos por la aplicación pasados a la devolución de llamada. Puede ser NULL.

Devoluciones

Distinto de cero en caso de éxito, cero en caso de fallo. Utilice PHYSFS_getLastErrorCode() para obtener el error específico. Si la devolución de llamada devuelve PHYSFS_ENUM_STOP para detenerse anticipadamente, esto se considerará un éxito. Las devoluciones de llamada que devuelvan PHYSFS_ENUM_ERROR harán que esta función devuelva cero y establezca el código de error en PHYSFS_ERR_APP_CALLBACK.

char **PHYSFS_enumerateFiles(const char *dir)

Obtiene una lista de archivos de un directorio de ruta de búsqueda.

Advertencia

En las versiones de PhysicsFS anteriores a la 2.1, esta función devolvía tantos elementos como podía ante una condición de fallo (falta de memoria, error de E/S de disco, etc.). Dado que esto significaba que las aplicaciones no podían distinguir entre el éxito completo y el fallo parcial, y dado que la función siempre podía devolver NULL para informar fallos catastróficos de todos modos, en PhysicsFS 2.1 la política de esta función cambió: devolverá una lista de resultados completos o devolverá NULL para cualquier tipo de fallo, para que podamos garantizar que la enumeración se completó y no tiene lagunas en sus resultados.

Los directorios coincidentes se interpolan. Es decir, si "C:\midir" está en la ruta de búsqueda y contiene un directorio "guardados" que contiene "x.sav", "y.sav" y "z.sav", y también hay un "C:\dirusuario" en la ruta de búsqueda que tiene un subdirectorio "guardados" con "w.sav", entonces el siguiente código:

char **rc = PHYSFS_enumerateFiles("guardados");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * Tenemos [%s].\n", *i);
PHYSFS_freeList(rc);
* Tenemos [x.sav].
* Tenemos [y.sav].
* Tenemos [z.sav].
* Tenemos [w.sav].
Siéntase libre de ordenar la lista como prefiera. Sin embargo, los datos devueltos siempre estarán libres de duplicados, y siempre estarán ordenados alfabéticamente (o más bien, por orden Unicode sensible a mayúsculas y minúsculas).
No olvide llamar a PHYSFS_freeList() con el valor devuelto por esta función cuando haya terminado con él.
Parámetros
dir directorio en notación independiente de la plataforma a enumerar.
Devoluciones
Matriz terminada en nulo de cadenas terminadas en nulo, o NULL para casos de fallo.

const char *physFS_getPrefDir (const char *org, const char *app)

Obtener la ruta específica del usuario y la aplicación donde se pueden escribir archivos. Función de ayuda.

Obtiene el "directorio de preferencias". Está destinado a ser donde los usuarios pueden escribir archivos personales (preferencias, partidas guardadas, etc.) que son específicos de su aplicación. Este directorio es único por usuario y por aplicación.

Esta función determinará la ubicación apropiada en el sistema de archivos nativo, creará el directorio si es necesario y devolverá una cadena en notación dependiente de la plataforma, adecuada para pasar a PHYSFS_setWriteDir().

En Linux, podría parecer: "/home/bob/.local/share/Mi Nombre de Programa"

En Mac OS X, podría parecer: "/Users/bob/Library/Application Support/Mi Nombre de Programa"

(etc.)

Probablemente debería usar el directorio de preferencias para su directorio de escritura, y también ponerlo cerca del principio de su ruta de búsqueda. Las versiones anteriores de PhysicsFS ofrecían solo PHYSFS_getUserDir() y le dejaban descubrir dónde debían ir los archivos dentro de ese árbol. Esto encuentra la ubicación correcta para cualquier plataforma, que no solo cambia entre sistemas operativos, sino también entre versiones del mismo sistema operativo.

  • Intente usar la misma cadena de organización (incluida la distinción entre mayúsculas y minúsculas) para todas sus aplicaciones que utilizan esta función.
  • Siempre use una cadena de aplicación única para cada una, y asegúrese de que nunca cambie para una aplicación una vez que haya decidido cuál usar.
  • Los caracteres Unicode son legales, siempre que estén codificados en UTF-8, pero...
  • ... solo use letras, números y espacios. Evite la puntuación como "Nombre del juego 2: La venganza del malo!" ... "Nombre del juego 2" es suficiente.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Añadir un archivo o directorio a la ruta de búsqueda. Si es un duplicado, la entrada no se añade de nuevo, aunque la función tenga éxito. No puedes añadir el mismo archivo a dos puntos de montaje diferentes: la comprobación de duplicados se realiza contra el archivo y no contra el punto de montaje.

Cuando montas un archivo, se añade a un sistema de archivos virtual...todos los archivos de todos los archivos se interpolan en un único árbol de archivos jerárquico. Dos archivos montados en el mismo lugar (o un archivo con archivos que se superponen a otro punto de montaje) pueden tener archivos superpuestos: en tal caso, se selecciona el archivo que está más temprano en la ruta de búsqueda, y los otros archivos son inaccesibles para la aplicación. Esto permite que los archivos se utilicen para anular revisiones anteriores; puedes usar el mecanismo de montaje para colocar archivos en un punto específico del árbol de archivos y evitar superposiciones; esto es útil para mods descargables que podrían pisotear datos de la aplicación o entre sí, por ejemplo.

El punto de montaje no necesita existir antes de montar, lo cual es diferente de lo que los familiarizados con el concepto de "montaje" de Unix podrían esperar. Además, más de un archivo puede ser montado en el mismo punto de montaje, o los puntos de montaje y el contenido de los archivos pueden superponerse... el mecanismo de interpolación sigue funcionando como de costumbre.

Especificar un enlace simbólico a un archivo o directorio está permitido aquí, independientemente del estado de PHYSFS_permitSymbolicLinks(). Esa función solo se ocupa de enlaces simbólicos dentro del directorio montado o archivo.

Parámetros

newDir directorio o archivo a añadir a la ruta, en notación dependiente de la plataforma.
mountPoint Ubicación en el árbol interpolado donde este archivo se "montará", en notación independiente de la plataforma. NULL o "" es equivalente a "/".

Agrega un archivo, contenido en un manejador de PHYSFS_File, a la ruta de búsqueda.

Advertencia

A menos que tenga una necesidad especial de bajo nivel, debería usar PHYSFS_mount() en lugar de esto.

¡Los archivos dentro de otros archivos pueden ser muy lentos! Mientras que un PHYSFS_File puede buscar incluso cuando los datos están comprimidos, puede hacerlo retrocediendo al inicio y descomprimiendo todo antes del punto de búsqueda. El uso normal de archivos puede implicar muchas búsquedas en segundo plano. Como tal, podría encontrar el uso normal de archivos extremadamente tedioso si se monta de esta manera. Planifique en consecuencia: si, por ejemplo, tiene un archivo .zip autoextraíble y desea montar algo dentro de él, comprima el contenido del archivo interno y asegúrese de que el archivo .zip externo no comprima también el archivo interno.

El uso más popular para esto es probablemente montar archivos almacenados dentro de otros archivos.

void PHYSFS_permitSymbolicLinks(int allow)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y archivos contienen archivos que son solo punteros a otros archivos. En el sistema de archivos físico, abrir un enlace de este tipo abrirá (transparentemente) el archivo al que apunta.

Por defecto, PhysicsFS verificará si un archivo es realmente un enlace simbólico durante las llamadas de apertura y fallará si lo es. De lo contrario, el enlace podría sacarte de las rutas de escritura y búsqueda, y comprometer la seguridad.

Si quieres asumir ese riesgo, llama a esta función con un parámetro distinto de cero. Ten en cuenta que esto es más para aislar el lenguaje de script de un programa, en caso de que scripts no confiables intenten comprometer el sistema. En términos generales, un usuario podría tener una razón legítima para configurar un enlace simbólico, por lo que a menos que sientas que hay un peligro específico al permitirlos, deberías permitirlos.

Los enlaces simbólicos solo se verifican explícitamente al tratar con nombres de archivo en notación independiente de la plataforma. Es decir, al configurar tus rutas de búsqueda y escritura, etc., nunca se verifican los enlaces simbólicos.

Por favor, ten en cuenta que PHYSFS_stat() siempre verificará la ruta especificada; si esa ruta es un enlace simbólico, no se seguirá en ningún caso. Si los enlaces simbólicos no están permitidos a través de esta función, PHYSFS_stat() los ignora y trataría la consulta como si la ruta no existiera en absoluto.

El permiso de enlace simbólico se puede habilitar o deshabilitar en cualquier momento después de haber llamado a PHYSFS_init(), y está deshabilitado por defecto.

Parámetros

allow distinto de cero para permitir enlaces simbólicos, cero para denegar el enlace.

void PHYSFS_setBuffer(PHYSFS_File *handle, unsigned int bufsize)

Set the buffering characteristics for a file handle.

By default, PhysicsFS does not buffer file I/O. This means that every read and write operation will be performed directly against the underlying filesystem or archive. This can be very inefficient for many operations.

You can enable buffering for a specific file handle by calling this function. The bufsize parameter is the size, in bytes, of the buffer to allocate. A value of 0 will disable buffering, freeing any existing buffer associated with the handle.

When buffering is enabled, read and write operations will be performed against the buffer in memory. The buffer will only be flushed to the underlying storage when it is full (for writes), when the file is closed, or when explicitly flushed by calling PHYSFS_flush. Reading past the end of the buffer will cause the buffer to be refilled from the underlying storage. Seeking will also cause the buffer to be flushed and refilled.

Note that certain operations, like seeking backwards in a file opened for writing, might implicitly cause a flush... check your return values!

Seeking, etc transparently accounts for buffering.

You can resize an existing buffer by calling this function more than once on the same file. Setting the buffer size to zero will free an existing buffer.

PhysicsFS file handles are unbuffered by default.

Please check the return value of this function! Failures can include not being able to seek backwards in a read-only file when removing the buffer, not being able to allocate the buffer, and not being able to flush the buffer to disk, among other unexpected problems.

handle handle returned from PHYSFS_open*().
bufsize size, in bytes, of buffer to allocate.

PHYSFS_writeUBE16, PHYSFS_writeUBE32, PHYSFS_writeUBE64, PHYSFS_writeULE16, PHYSFS_writeULE32, PHYSFS_writeULE64 - convert and write an unsigned N-bit endian value.

Detailed Description

These functions are convenience wrappers around PHYSFS_write(3) that convert an unsigned integer from the platform's native byte order to a specific endian format (big-endian or little-endian), and then write it to a file.

For example, PHYSFS_writeUBE16 will convert a 16-bit unsigned integer from the platform's native byte order to big-endian byte order and then write it to the specified file handle.

The other functions are analogous, just operating on different integer sizes and endian formats.

These functions are useful when writing data to files that need to conform to a specific endian format, such as network protocols or file formats that mandate a specific byte order.
