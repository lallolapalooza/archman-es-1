#define PHYSFS_file PHYSFS_File

1.0 API compatibility define. PHYSFS_file is identical to PHYSFS_File. This #define is here for backwards compatibility with the 1.0 API, which had an inconsistent capitalization convention in this case. New code should use PHYSFS_File, as this #define may go away someday.

Firma de función para callbacks que enumeran archivos.

Advertencia

A partir de PhysicsFS 2.1, usa PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; te da más control sobre el proceso.

Estos se utilizan para informar a un llamador original una lista de entradas de directorio, un archivo/directorio/enlace simbólico por callback. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de ninguna cadena.

Estos callbacks se utilizan, a partir de PhysicsFS 1.1, como una alternativa a las funciones que devolverían listas que necesitan ser liberadas con PHYSFS_freeList(). El callback significa que la biblioteca no necesita asignar una lista completa y todas las cadenas por adelantado.

Ten en cuenta que el orden de los datos prometido en las versiones de lista no es necesariamente el mismo en las versiones de callback. Consulta la documentación de las API específicas, pero las cadenas pueden no estar ordenadas como esperas y podrías obtener cadenas duplicadas.

Parámetros

data Puntero de datos definido por el usuario, pasado desde la API que finalmente llamó al callback.
origdir Una cadena que contiene la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio sobre el cual solicitaste la enumeración, pasado en el callback para tu conveniencia.
fname El nombre del archivo que se está enumerando. Puede que no esté en orden alfabético en comparación con otros callbacks que se hayan activado, y no contendrá la ruta completa. Puedes recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtener una lista de archivos de un directorio de la ruta de búsqueda, utilizando una función de retorno de llamada definida por la aplicación, con informe de errores. Internamente, PHYSFS_enumerateFiles() simplemente llama a esta función y luego construye una lista antes de devolverla a la aplicación, por lo que la funcionalidad es idéntica excepto por la forma en que la información se representa a la aplicación.

A diferencia de PHYSFS_enumerateFiles(), esta función no devuelve una matriz. En su lugar, llama a una función especificada por la aplicación una vez por elemento de la ruta de búsqueda:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Tenemos [%s] en [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // dame más datos, por favor.
}
// ...
PHYSFS_enumerate("/alguna/ruta", printDir, NULL);

No se garantiza que los elementos enviados a la función de retorno de llamada estén en ningún orden. No se realiza ninguna ordenación a este nivel, y si la necesita, probablemente debería usar PHYSFS_enumerateFiles() en su lugar, que garantiza la ordenación alfabética. Esta forma informa de lo que se descubre en cada archivo antes de pasar al siguiente. Incluso dentro de un mismo archivo, no podemos garantizar el orden en que descubrirá los datos. *Cualquier ordenación que encuentre en estas llamadas de retorno es pura suerte. No dependa de ella.* A medida que recorre toda la lista de archivos, es posible que reciba nombres de archivo duplicados.

Esta API y las propias funciones de retorno de llamada son capaces de informar de errores. Antes de esta API, las funciones de retorno de llamada tenían que aceptar cada elemento enumerado, incluso si solo buscaban algo específico y querían detenerse después, o si tenían un error grave y no podían alertar a nadie. Además, si PhysicsFS en sí tenía un problema (error de disco o similares), no podía informarlo a la aplicación que lo llamaba, solo tenía que omitir elementos o dejar de enumerar por completo, y el llamador no sabría que había perdido algunos datos en el camino.

Ahora el llamador puede estar seguro de que obtuvo un conjunto de datos completo, y su función de retorno de llamada tiene el control si quiere que la enumeración se detenga pronto. Consulte la documentación de PHYSFS_EnumerateCallback para obtener detalles sobre cómo debe comportarse su función de retorno de llamada.

Parámetros

dir Directorio, en notación independiente de la plataforma, a enumerar.
c Función de retorno de llamada para notificar sobre los elementos de la ruta de búsqueda.
d Datos definidos por la aplicación pasados a la función de retorno de llamada. Puede ser NULL.

Devuelve

Distinto de cero en caso de éxito, cero en caso de fallo. Use PHYSFS_getLastErrorCode() para obtener el error específico. Si la función de retorno de llamada devuelve PHYSFS_ENUM_STOP para detenerse temprano, esto se considerará un éxito. Las funciones de retorno de llamada que devuelvan PHYSFS_ENUM_ERROR harán que esta función devuelva cero y establezcan el código de error en PHYSFS_ERR_APP_CALLBACK.

Advertencia

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)

PHYSFS_freeList(rc);

    usted.

On Linux, this might look like: "/home/bob/.local/share/My Program Name"

On Mac OS X, this might look like: "/Users/bob/Library/Application Support/My Program Name"

(etc.)

You should probably use the pref dir for your write dir, and also put it near the beginning of your search path. Older versions of PhysicsFS offered only PHYSFS_getUserDir() and left you to figure out where the files should go under that tree. You specify the name of your organization (if it's not a real organization, your name or an Internet domain you own might do) and the name of your application. These should be proper names.

  • Try to use the same org string (including case-sensitivity) for all your applications that use this function.
  • Always use a unique app string for each one, and make sure it never changes for an app once you've decided on it.
  • Unicode characters are legal, as long as it's UTF-8 encoded, but...
  • ...only use letters, numbers, and spaces. Avoid punctuation like "Game Name 2: Bad Guy's Revenge!" ... "Game Name 2" is sufficient.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

void PHYSFS_permitSymbolicLinks (int allow)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y archivos contienen archivos que son solo punteros a otros archivos. En el sistema de archivos físico, abrir un enlace de este tipo abrirá (de forma transparente) el archivo al que apunta.

Por defecto, PhysicsFS comprobará si un archivo es realmente un enlace simbólico durante las llamadas de apertura y fallará si lo es. De lo contrario, el enlace podría sacarte de las rutas de escritura y búsqueda, y comprometer la seguridad.

Si quieres asumir ese riesgo, llama a esta función con un parámetro distinto de cero. Ten en cuenta que esto es más para aislar el lenguaje de scripting de un programa, en caso de que scripts no confiables intenten comprometer el sistema. En términos generales, un usuario podría tener una razón legítima para configurar un enlace simbólico, por lo que, a menos que sientas que hay un peligro específico en permitirlos, deberías hacerlo.

Los enlaces simbólicos solo se comprueban explícitamente cuando se trata con nombres de archivo en notación independiente de la plataforma. Es decir, al configurar tus rutas de búsqueda y escritura, etc., nunca se comprueban los enlaces simbólicos.

Ten en cuenta que PHYSFS_stat() siempre comprobará la ruta especificada; si esa ruta es un enlace simbólico, no se seguirá en ningún caso. Si los enlaces simbólicos no están permitidos a través de esta función, PHYSFS_stat() los ignora y trataría la consulta como si la ruta no existiera en absoluto.

El permiso de enlace simbólico se puede habilitar o deshabilitar en cualquier momento después de haber llamado a PHYSFS_init(), y está deshabilitado por defecto.

Parámetros

allow distinto de cero para permitir enlaces simbólicos, cero para denegar enlaces.

int PHYSFS_registerArchiver (const PHYSFS_Archiver * archiver)

Agrega un nuevo archivador al sistema.

Advertencia

Esto es para usuarios avanzados y experimentados. No lo necesitas a menos que sepas muy bien lo que estás haciendo. La mayoría de las aplicaciones no lo necesitarán.

Si quieres proporcionar tu propio archivador (por ejemplo, un formato de archivo personalizado, o algo virtual que quieras que parezca un sistema de archivos al que se pueda acceder a través de las API habituales de PhysicsFS), aquí es donde empiezas. Una vez que un archivador se registra con éxito, puedes usar PHYSFS_mount() para agregar archivos que tu archivador soporta a la ruta de búsqueda, o quizás usarlo como directorio de escritura. Internamente, PhysicsFS utiliza esta función para registrar sus propios archivadores incorporados, como el soporte para .zip, etc.

No puedes tener dos archivadores que manejen la misma extensión. Si va a haber un conflicto, puedes anular el registro del otro archivador (incluidos los incorporados) con PHYSFS_deregisterArchiver().

Los datos en (archiver) se copian; puedes liberar este puntero cuando esta función retorne.

Una vez que esta función retorna con éxito, PhysicsFS podrá soportar archivos de este tipo hasta que anules el registro del archivador nuevamente.

archiver El archivador a registrar.

Retorna

Cero en caso de error, distinto de cero en caso de éxito.

int PHYSFS_setAllocator (const PHYSFS_Allocator * allocator)

Engancha tus propias rutinas de asignación en PhysicsFS. (Esto es para un uso limitado y avanzado. Si no ves inmediatamente una necesidad para ello, probablemente puedes ignorarlo para siempre).

Por defecto, PhysicsFS utilizará lo que sea razonable para la plataforma para gestionar la memoria dinámica (generalmente `malloc`/`realloc`/`free` de ANSI C, pero algunas plataformas pueden usar algo más), pero en algunos casos poco comunes, la aplicación podría querer más control sobre la gestión de memoria de la biblioteca. Esto te permite redirigir PhysicsFS para que use tus propias rutinas de asignación en su lugar. Solo puedes llamar a esta función antes de PHYSFS_init(); si la biblioteca está inicializada, rechazará tus esfuerzos por cambiar el asignador a mitad de camino. Puedes llamar a esta función después de PHYSFS_deinit() si estás dispuesto a cerrar la biblioteca y reiniciarla con un nuevo asignador; esta es una operación segura y compatible. El asignador permanece intacto entre las llamadas de `deinit`/`init`. Si quieres volver al asignador predeterminado de la plataforma, pasa un `NULL` aquí.

Si no estás seguro de inmediato qué hacer con esta función, puedes ignorarla de forma segura.

Parámetros

allocator Estructura que contiene los puntos de entrada de tu asignador.

Retorna

Cero en caso de fallo, distinto de cero en caso de éxito. Esta llamada solo falla cuando se utiliza entre las llamadas a PHYSFS_init() y PHYSFS_deinit().

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convierte una cadena UTF-8 a una cadena Latin1. Las cadenas Latin1 tienen 8 bits por carácter: una codificación popular de "alto ASCII".

Para asegurar que el buffer de destino sea lo suficientemente grande para la conversión, por favor, asigna un buffer que sea el doble del tamaño del buffer de origen. UTF-8 expande los puntos de código latin1 mayores a 127 de 1 a 2 bytes, por lo que la cadena puede crecer en algunos casos.

Las cadenas que no quepan en el buffer de destino serán truncadas, pero siempre terminarán en nulo y nunca tendrán una secuencia UTF-8 incompleta al final. Si la longitud del buffer es 0, esta función no hace nada.

Por favor, ten en cuenta que no proporcionamos un conversor de UTF-8 a Latin1, ya que Latin1 no puede expresar la mayoría de los puntos de código Unicode. Es una codificación heredada; deberías estar convirtiendo lejos de ella en todo momento.

Parámetros

src Cadena de origen terminada en nulo en formato Latin1.
dst Buffer para almacenar la cadena UTF-8 convertida.
len Tamaño, en bytes, del buffer de destino.

Obsoleto

A partir de PhysicsFS 2.1, usa PHYSFS_writeBytes() en su lugar. Esta función simplemente lo envuelve de todos modos. Esta función nunca aclaró qué sucedería si lograbas escribir un objeto parcial, por lo que trabajar a nivel de byte hace esto más limpio para todos, especialmente ahora que las interfaces PHYSFS_Io pueden ser suministradas por la aplicación.

Parámetros

handle valor de retorno de PHYSFS_openWrite() o PHYSFS_openAppend().
buffer búfer de bytes a escribir en (handle).
objSize tamaño en bytes de los objetos que se están escribiendo en (handle).
objCount número de objetos (objSize) a escribir en (handle).

Devuelve

número de objetos escritos. PHYSFS_getLastErrorCode() puede arrojar luz sobre la razón por la que esto podría ser < (objCount). -1 si falla por completo.

PHYSFS_sint64 PHYSFS_writeBytes (PHYSFS_File * handle, const void * buffer, PHYSFS_uint64 len)

Escribe datos en un manejador de archivo de PhysicsFS. El archivo debe estar abierto para escritura.

Por favor, ten en cuenta que aunque (len) es un entero sin signo de 64 bits, estás limitado a 63 bits (9223372036854775807 bytes), por lo que podemos devolver un valor negativo en caso de error. Si la longitud es mayor que 0x7FFFFFFFFFFFFFFF, esta función fallará inmediatamente. Para sistemas sin un tipo de dato de 64 bits, estás limitado a 31 bits (0x7FFFFFFF, o 2147483647 bytes). Confiamos en que la mayoría de las cosas no necesitarán hacer varios gigabytes de E/S en una sola llamada de todos modos, ¡pero ¿por qué limitar las cosas?

Parámetros

handle valor de retorno de PHYSFS_openWrite() o PHYSFS_openAppend().
buffer búfer de (len) bytes a escribir en (handle).
len número de bytes que se están escribiendo en (handle).

Devuelve

número de bytes escritos. Esto puede ser menor que (len); en caso de error, el sistema puede intentar escribir tantos bytes como sea posible, por lo que podría ocurrir una escritura incompleta. PHYSFS_getLastErrorCode() puede arrojar luz sobre la razón por la que esto podría ser < (len). -1 si falla por completo.
