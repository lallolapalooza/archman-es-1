DESCRIPCIÓN

PHYSFS_getBaseDir() devuelve una cadena que contiene la ruta del directorio base de la aplicación. Esto suele ser el directorio donde se ejecuta el ejecutable de la aplicación.

Esta ruta es importante porque PhysicsFS intentará buscar en ella archivos de configuración, por ejemplo. El valor devuelto por esta función no debe ser modificado y es válido hasta que se llame a PHYSFS_deinit().

Nota: El valor devuelto puede ser NULL si no se pudo determinar la ruta base.

EJEMPLO

const char *baseDir = PHYSFS_getBaseDir();
if (baseDir) {
    printf("La ruta base es: %s\n", baseDir);
} else {
    printf("No se pudo determinar la ruta base: %s\n", PHYSFS_getLastError());
}

alias de tipo void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Firma de función para devoluciones de llamada que enumeran archivos.

Advertencia

A partir de PhysicsFS 2.1, usa PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; te da más control sobre el proceso.

Estos se utilizan para informar una lista de entradas de directorio a un llamador original, un archivo/directorio/enlace simbólico por devolución de llamada. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de ninguna cadena.

Estas devoluciones de llamada se utilizan, a partir de PhysicsFS 1.1, como alternativa a las funciones que devolverían listas que deben limpiarse con PHYSFS_freeList(). La devolución de llamada significa que la biblioteca no necesita asignar una lista completa y todas las cadenas por adelantado.

Ten en cuenta que el orden de los datos prometido en las versiones de lista no es necesariamente así en las versiones de devolución de llamada. Consulta la documentación de APIs específicas, pero es posible que las cadenas no estén ordenadas como esperas y podrías obtener cadenas duplicadas.

Valores que representan causas específicas de fallo. La mayoría de las veces, solo deberías preocuparte por si una operación dada falló o no, pero puede haber ocasiones en las que planees manejar un caso de fallo específico con gracia, por lo que proporcionamos códigos de error específicos.

La mayoría de estos errores son un poco vagos, y la mayoría no son cosas que puedas arreglar... si hay un error de permisos, por ejemplo, todo lo que realmente puedes hacer es pasar esa información al usuario y dejar que descubra cómo manejarlo. En la mayoría de estos casos, tu programa solo debería preocuparse de que no logró sus objetivos, y no preocuparse específicamente por qué.

Internamente, PHYSFS_enumerateFiles() simplemente llama a esta función y luego crea una lista antes de devolverla a la aplicación, por lo que la funcionalidad es idéntica, excepto por cómo se representa la información a la aplicación.

{
    printf(" * Tenemos [%s] en [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // dame más datos, por favor.
}
// ...

No se garantiza que los elementos enviados a la devolución de llamada estén en ningún orden. Incluso dentro de un archivo, no podemos garantizar el orden en que descubrirá los datos. * Cualquier ordenación que encuentre en estas devoluciones de llamada es pura suerte. No confíe en ella. * A medida que recorre toda la lista de archivos, puede recibir nombres de archivo duplicados.

There are two error-reporting mechanisms in PhysFS: return codes and thread-specific error states. Many functions return a boolean or an integer that indicates success or failure. If a function fails, it may set an internal error state. This internal error state is associated with the thread that called the function.

Generally, applications should only concern themselves with whether a given function failed; however, if you require more specifics, you can try this function to glean information, if there's some specific problem you're expecting and plan to handle. const char * PHYSFS_getPrefDir (const char * org, const char * app)

Get the user-and-app-specific path where files can be written. Helper function.

Get the "pref dir". This is meant to be where users can write personal files (preferences and save games, etc) that are specific to your application. This directory is unique per user, per application.

This function will decide the appropriate location in the native filesystem, create the directory if necessary, and return a string in platform-dependent notation, suitable for passing to PHYSFS_setWriteDir().

On Linux, this might look like: "/home/bob/.local/share/My Program Name"

On Mac OS X, this might look like: "/Users/bob/Library/Application Support/My Program Name"

(etc.)

You should probably use the pref dir for your write dir, and also put it near the beginning of your search path. Older versions of PhysicsFS offered only PHYSFS_getUserDir() and left you to figure out where the files should go under that tree. This finds the correct location for whatever platform, which not only changes between operating systems, but also versions of the same operating system.

You specify the name of your organization (if it's not a real organization, your name or an Internet domain you own might do) and the name of your application. These should be proper names.

  • Try to use the same org string (including case-sensitivity) for all your applications that use this function.

  • Unicode characters are legal, as long as it's UTF-8 encoded, but...

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Agregar un archivo o directorio a la ruta de búsqueda. Si es un duplicado, la entrada no se agrega de nuevo, a pesar de que la función tenga éxito. No puede agregar el mismo archivo a dos puntos de montaje diferentes: la verificación de duplicados se realiza contra el archivo y no contra el punto de montaje.

Cuando monta un archivo, se agrega a un sistema de archivos virtual... todos los archivos en todos los archivos se interpolan en un único árbol de archivos jerárquico. Dos archivos montados en el mismo lugar (o un archivo con archivos que se superponen con otro punto de montaje) pueden tener archivos superpuestos: en tal caso, se selecciona el archivo anterior en la ruta de búsqueda, y los otros archivos son inaccesibles para la aplicación. Esto permite que los archivos se utilicen para anular revisiones anteriores; puede usar el mecanismo de montaje para colocar archivos en un punto específico del árbol de archivos y evitar la superposición; esto es útil para mods descargables que podrían pisotear datos de la aplicación o entre sí, por ejemplo.

El punto de montaje no necesita existir antes de montarlo, lo que es diferente de lo que los familiarizados con el concepto de montaje de Unix pueden esperar. Además, se pueden montar más de un archivo en el mismo punto de montaje, o los puntos de montaje y el contenido de los archivos pueden superponerse... el mecanismo de interpolación sigue funcionando como de costumbre.

Se permite especificar un enlace simbólico a un archivo o directorio aquí, independientemente del estado de PHYSFS_permitSymbolicLinks(). Esa función solo se ocupa de los enlaces simbólicos dentro del directorio montado o archivo.

appendToPath distinto de cero para agregar a la ruta de búsqueda, cero para anteponer.

void PHYSFS_permitirEnlacesSimbolicos (int permitir)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y archivos contienen archivos que son solo punteros a otros archivos. En el sistema de archivos físico, abrir dicho enlace abrirá (transparentemente) el archivo al que apunta.

Por defecto, PhysicsFS comprobará si un archivo es realmente un enlace simbólico durante las llamadas de apertura y fallará si lo es. De lo contrario, el enlace podría llevarte fuera de las rutas de escritura y búsqueda, y comprometer la seguridad.

Si quieres asumir ese riesgo, llama a esta función con un parámetro distinto de cero. Ten en cuenta que esto es más para aislar el lenguaje de scripting de un programa, en caso de que scripts no confiables intenten comprometer el sistema. En términos generales, un usuario podría tener una razón legítima para configurar un enlace simbólico, por lo que a menos que sientas que hay un peligro específico en permitirlos, deberías permitirlos.

Los enlaces simbólicos solo se comprueban explícitamente cuando se trata con nombres de archivo en notación independiente de la plataforma. Es decir, al configurar tus rutas de búsqueda y escritura, etc., nunca se comprueban los enlaces simbólicos.

Ten en cuenta que PHYSFS_stat() siempre comprobará la ruta especificada; si esa ruta es un enlace simbólico, no se seguirá en ningún caso. Si los enlaces simbólicos no están permitidos a través de esta función, PHYSFS_stat() los ignora y trataría la consulta como si la ruta no existiera en absoluto.

El permiso de enlace simbólico se puede habilitar o deshabilitar en cualquier momento después de haber llamado a PHYSFS_init(), y está deshabilitado por defecto.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Hace un subdirectorio de un archivo como directorio raíz. Esto permite que te acerques a los archivos accesibles en un archivo específico. Por ejemplo, si tienes x.zip con un archivo en y/z.txt, montado en /a, si llamas a PHYSFS_setRoot("x.zip", "/y"), entonces la llamada a PHYSFS_openRead("/a/z.txt") se satisfará.

Puedes cambiar la raíz de un archivo en cualquier momento, alterando la arborescencia interpolada (dependiendo de donde se muevan las rutas, un archivo diferente puede proporcionar diferentes archivos). Si estableces la raíz en NULL o "/", el archivo se tratará como si no hubiera raíz especial (como si el archivo se montara normalmente).

Cambiar la raíz solo afecta las operaciones futuras en rutas de archivos; un archivo que fue abierto desde una ruta que cambió debido a un setRoot no será afectado.

Establecer una nueva raíz no está limitado a archivos en el directorio de búsqueda; puedes establecer una en el directorio de escritura, lo cual podría ser útil si tienes archivos abiertos para escribir y no puedes cambiar el directorio de escritura en este momento.

No es un error establecer un subdirectorio que no exista como raíz de un archivo, aunque en ese caso no se verán archivos. Si los directorios que se omiten se crean (una mkdir al sistema de archivos físico, etc), esto se reflejará en la arborescencia interpolada.

Parámetros

archive Directorio/archivo en el cual se cambiará la raíz.
subdir Subdirectorio nuevo para hacer la raíz de este archivo.

Devuelve

no cero en caso de éxito, cero en error. Usa PHYSFS_getLastErrorCode() para obtener el error específico.

Configura rutas sanas por defecto. Función de ayuda.

El directorio de escritura se establecerá en el directorio de prefijo devuelto por

, que se crea si no existe.

La información anterior es suficiente para asegurar que la carpeta de configuración de tu programa esté separada de otros desordenados y sea independiente de la plataforma.

La ruta de búsqueda será:

  • Directorio de escritura (creado si no existe)
  • Directorio de base (PHYSFS_getBaseDir())
  • Todo el directorio de CD-ROM encontrado (opcional)

Estos directorios se buscan por extensiones (archiveExt), que, si son válidas y apoyadas, también se añaden a la ruta de búsqueda. Todos los archivados se montan en la raíz del sistema de archivos virtual ("/").
