Main header file for PhysicsFS.

Macro Definition Documentation

#define PHYSFS_file PHYSFS_File

1.0 API compatibility define. PHYSFS_file is identical to PHYSFS_File. This #define is here for backwards compatibility with the 1.0 API, which had an inconsistent capitalization convention in this case. New code should use PHYSFS_File, as this #define may go away someday.

#define PHYSFS_VERSION( x)

Value:

{ \
    (x)->major = PHYSFS_VER_MAJOR; \
    (x)->minor = PHYSFS_VER_MINOR; \
    (x)->patch = PHYSFS_VER_PATCH; \
}

Macro to determine PhysicsFS version program was compiled against. This macro fills in a PHYSFS_Version structure

con la versión de la biblioteca con la que compilaste. Esto se determina por la cabecera que utiliza el compilador. Ten en cuenta que si vinculaste dinámicamente la biblioteca, podrías tener una versión ligeramente más nueva o más antigua en tiempo de ejecución. Esa versión se puede determinar con PHYSFS_getLinkedVersion(), que, a diferencia de PHYSFS_VERSION, no es una macro.

Parámetros

x Un puntero a una estructura PHYSFS_Version para inicializar.

PHYSFS_enumerate

Esto es lo mismo que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, excepto que puede devolver un resultado del callback: es decir: si estás buscando algo específico, una vez que lo encuentras, puedes indicarle a PhysicsFS que deje de enumerar más. Esto se utiliza con PHYSFS_enumerate(), que esperemos que hayamos hecho bien esta vez. :)

Parámetros

data Puntero de datos definido por el usuario, transmitido desde la API que finalmente llamó al callback.
origdir Una cadena que contiene la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio sobre el cual solicitaste la enumeración, pasado en el callback para tu conveniencia.
fname El nombre del archivo que se está enumerando. Puede que no esté en orden alfabético en comparación con otros callbacks que se han ejecutado, y no contendrá la ruta completa. Puedes recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

Un valor de PHYSFS_EnumerateCallbackResult. Todos los demás valores (actualmente) no están definidos; no los uses.

typedef void(* physfs_EnumFilesCallback)(void *data, const char *origdir, const char *fname)

Firma de función para callbacks que enumeran archivos.

Advertencia

A partir de PhysicsFS 2.1, usa PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; te da más control sobre el proceso.

Estos se utilizan para informar a un llamante original una lista de entradas de directorio, un archivo/directorio/enlace simbólico por callback. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de ninguna cadena.

Estos callbacks se utilizan, a partir de PhysicsFS 1.1, como una alternativa a las funciones que devolverían listas que necesitan ser limpiadas con PHYSFS_freeList(). El callback significa que la biblioteca no necesita asignar una lista completa y todas las cadenas por adelantado.

Ten en cuenta que el orden prometido de los datos en las versiones de lista no es necesariamente así en las versiones de callback. Consulta la documentación de APIs específicas, pero las cadenas pueden no estar ordenadas como esperas y podrías obtener cadenas duplicadas.

Parámetros

origdir Una cadena que contiene la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio sobre el cual solicitaste la enumeración, pasado en el callback para tu conveniencia.
fname El nombre del archivo que se está enumerando. Puede que no esté en orden alfabético en comparación con otros callbacks que se han ejecutado, y no contendrá la ruta completa. Puedes recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

enum PHYSFS_ErrorCode

Valores que representan causas específicas de fallo. La mayoría de las veces, solo deberías preocuparte por si una operación dada falló o no, pero puede haber ocasiones en las que planees manejar un caso de fallo específico con gracia, por lo que proporcionamos códigos de error específicos.

La mayoría de estos errores son un poco vagos, y la mayoría no son cosas que puedas arreglar... si hay un error de permiso, por ejemplo, todo lo que realmente puedes hacer es pasar esa información al usuario y dejar que él descubra cómo manejarlo. En la mayoría de estos casos, tu programa solo debería importarle que falló en lograr sus objetivos, y no importarle específicamente por qué.

int PHYSFS_enumerate(const char *dir, PHYSFS_EnumerateCallback c, void *d)

Obtener una lista de archivos de un directorio de una ruta de búsqueda, utilizando un callback definido por el aplicativo, con errores reportados. Internamente, PHYSFS_enumerateFiles() simplemente llama a esta función y luego construye una lista antes de devolver al aplicativo, por lo que la funcionalidad es idéntica, salvo cómo la información se presenta al aplicativo.

Diferente de PHYSFS_enumerateFiles(), esta función no devuelve un array. En lugar de eso, llama a una función especificada por el aplicativo una vez por cada elemento de la ruta de búsqueda:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK; // me da más datos, por favor.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Los elementos enviados al callback no están garantizados para estar en ningún orden. No se realiza ningún ordenamiento en este nivel, y si lo necesitas, deberías usar PHYSFS_enumerateFiles(), que garantiza el orden alfabético. Esta forma reporta lo que se descubre en cada archiver antes de pasar a la siguiente. Incluso dentro de un archivo, no podemos garantizar el orden en que se descubren los datos. Cualquier orden que encuentres en estos callbacks es pura suerte. No debes depender de ello. Como esta camina por toda la lista de archivers, podrías recibir nombres de archivos duplicados.

Esta API y los callbacks mismos pueden reportar errores. Antes de esta API, los callbacks tenían que aceptar cada elemento enumerado, incluso si solo buscaban un objeto específico y querían detenerse después de eso, o tenían un error serio y no podían alertar a nadie. Además, si PhysicsFS mismo tenía un problema (error de disco, etc.), no podría reportarlo al aplicativo, simplemente pasaría a los elementos o detendría la enumeración, y el llamador no sabría que había perdido algunos datos durante el camino.

Ahora el llamador puede estar seguro de que obtuvo un conjunto completo de datos, y si quiere detener la enumeración tempranamente, su callback tiene control. Consulta la documentación de PHYSFS_EnumerateCallback para detalles sobre cómo debería comportarse su callback.

Retorno

No cero en caso de éxito, cero en caso de falla. Usa PHYSFS_getLastErrorCode() para obtener el error específico. Si el callback devuelve PHYSFS_ENUM_STOP, se considera éxito. You specify the name of your organization (if it's not a real organization, your name or an Internet domain you own might do) and the name of your application. These should be proper names.

  • Try to use the same org string (including case-sensitivity) for all your applications that use this function.
  • Always use a unique app string for each one, and make sure it never changes for an app once you've decided on it.
  • Unicode characters are legal, as long as it's UTF-8 encoded, but...
  • ...only use letters, numbers, and spaces. Avoid punctuation like "Game Name 2: Bad Guy's Revenge!" ... "Game Name 2" is sufficient.

The pointer returned by this function remains valid until you call this function again, or call PHYSFS_deinit(). This is not necessarily a fast call, though, so you should call this once at startup and copy the string if you need it.

You should assume the path returned by this function is the only safe place to write files (and that PHYSFS_getUserDir() and PHYSFS_getBaseDir(), while they might be writable, or even parents of the returned path, aren't where you should be writing things).

const char * PHYSFS_getRealDir (const char * filename)

Figure out where in the search path a file resides. The file is specified in platform-independent notation. The returned filename will be the element of the search path where the file was found, which may be a directory, or an archive. Even if there are multiple matches in different parts of the search path, only the first one found is used, just like when opening a file.

So, if you look for "maps/level1.map", and C:\mygame is in your search path and C:\mygame\maps\level1.map exists, then "C:\mygame" is returned.

If a any part of a match is a symbolic link, and you've not explicitly permitted symlinks, then it will be ignored, and the search for a match will continue.

If you specify a fake directory that only exists as a mount point, it'll be associated with the first archive mounted there, even though that directory isn't necessarily contained in a real archive.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system... all files in all of the archives are interpolated into a single hierarchical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap... the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

newDir directory or archive to add to the path, in platform-dependent notation.
mountPoint Location in the interpolated tree that this archive will be "mounted", in platform-independent notation. NULL or "" is equivalent to "/".
appendToPath nonzero to append to search path, zero to prepend.

Returns

nonzero if added to path, zero on failure (bogus archive, dir missing, etc). Use PHYSFS_getLastErrorCode() to obtain the specific error.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Convierte un subdirectorio de un archivo en su directorio raíz. Esto te permite reducir los archivos accesibles en un archivo específico. Por ejemplo, si tienes x.zip con un archivo en y/z.txt, montado en /a, si llamas a PHYSFS_setRoot("x.zip", "/y"), entonces la llamada PHYSFS_openRead("/a/z.txt") tendrá éxito.

Puedes cambiar la raíz de un archivo en cualquier momento, alterando el árbol de archivos interpolado (dependiendo de dónde cambien las rutas, un archivo diferente puede estar proporcionando varios archivos). Cambiar la raíz solo afecta a las operaciones futuras sobre nombres de ruta; un archivo que se abrió desde una ruta que cambió debido a un setRoot no se verá afectado.

Establecer una nueva raíz no se limita a los archivos en la ruta de búsqueda; también puedes establecer una en el directorio de escritura, lo que podría ser útil si tienes archivos abiertos para escritura y por lo tanto no puedes cambiar el directorio de escritura en este momento.

No es un error establecer un subdirectorio que no existe como raíz de un archivo; sin embargo, no se verán archivos en este caso. Si los directorios faltantes terminan creándose (un mkdir en el sistema de archivos físico, etc.), esto se reflejará en el árbol interpolado.

archive directorio/archivo sobre el que cambiar la raíz.

distinto de cero si tiene éxito, cero en caso de fallo. Usa PHYSFS_getLastErrorCode() para obtener el error específico.

int PHYSFS_setSaneConfig (const char * organization, const char * appName, const char * archiveExt, int includeCdRoms, int archivesFirst)

Configura rutas sensatas por defecto. Función auxiliar.

El directorio de escritura se establecerá en el directorio de preferencias devuelto por

PHYSFS_getPrefDir(organization, appName)

, que se crea si no existe.

Lo anterior es suficiente para asegurar que el directorio de configuración de tu programa esté separado de otro desorden y sea independiente de la plataforma.

La ruta de búsqueda será:

  • El Directorio de Escritura (creado si no existe)
  • El Directorio Base (PHYSFS_getBaseDir())
  • Todos los directorios de CD-ROM encontrados (opcionalmente)

Estos directorios se buscan para encontrar archivos que terminen con la extensión (archiveExt), que, si son archivos válidos y compatibles, también se agregarán a la ruta de búsqueda. Si especificaste "PKG" para (archiveExt), y hay un archivo llamado data.PKG en el directorio base, se comprobará. Los archivos pueden añadirse o anteponerse a la ruta de búsqueda en orden alfabético, independientemente de los directorios en los que se encontraron. Todos los archivos se montan en la raíz del sistema de archivos virtual ("/").

Todo esto puede ser realizado por la aplicación, pero esto simplemente lo hace todo por ti. Siéntete libre de añadir más a la ruta de búsqueda manualmente también.

Parámetros

organization Nombre de tu empresa/grupo/etc. que se utilizará como nombre de directorio, así que mantenlo corto y sencillo.
appName Nombre específico del programa para tu programa, para separarlo de otros programas que usan PhysicsFS.
archiveExt Extensión de archivo utilizada por tu programa para especificar un archivo. Por ejemplo, Quake 3 usa "pk3", aunque solo son archivos zip. Especifica NULL para no buscar archivos automáticamente. No especifiques el punto '.'; si quieres buscar archivos ZIP, especifica "ZIP" y no ".ZIP"... la búsqueda de archivos no distingue entre mayúsculas y minúsculas.
includeCdRoms Distinto de cero para incluir CD-ROMs en la ruta de búsqueda, y (si (archiveExt) != NULL) buscarlos para encontrar archivos. Esto puede causar una cantidad significativa de bloqueo mientras se accede a los discos, y si no hay discos en la unidad (o incluso no montados en sistemas Unix), entonces pueden no estar disponibles de todos modos. Puede que quieras especificar cero y manejar la configuración del disco tú mismo.
archivesFirst Distinto de cero para anteponer los archivos a la ruta de búsqueda. Cero para añadirlos al final. Ignorado si !(archiveExt).

distinto de cero si tiene éxito, cero en caso de error. Usa PHYSFS_getLastErrorCode() para obtener el error específico.

NAME

PHYSFS_writeUBE16, PHYSFS_writeUBE32, PHYSFS_writeUBE64, PHYSFS_writeULE16, PHYSFS_writeULE32, PHYSFS_writeULE64 — write big/little endian integer values to a file

LIBRARY

PhysicsFS library (-lphysfs)

SYNOPSIS

#include <physfs.h>
int PHYSFS_writeUBE16 (PHYSFS_File *file, PHYSFS_uint16 val);
int PHYSFS_writeUBE32 (PHYSFS_File *file, PHYSFS_uint32 val);
int PHYSFS_writeUBE64 (PHYSFS_File *file, PHYSFS_uint64 val);
int PHYSFS_writeULE16 (PHYSFS_File *file, PHYSFS_uint16 val);
int PHYSFS_writeULE32 (PHYSFS_File *file, PHYSFS_uint32 val);
int PHYSFS_writeULE64 (PHYSFS_File *file, PHYSFS_uint64 val);

DESCRIPTION

These functions are convenience functions that convert an unsigned integer from the platform's native byte order to either big-endian or little-endian byte order, and then write that value to the specified
PhysicsFS file handle.

PHYSFS_writeUBE16 writes an unsigned 16-bit value in big-endian format.

PHYSFS_writeUBE32 writes an unsigned 32-bit value in big-endian format.

PHYSFS_writeUBE64 writes an unsigned 64-bit value in big-endian format.

PHYSFS_writeULE16 writes an unsigned 16-bit value in little-endian format.

PHYSFS_writeULE32 writes an unsigned 32-bit value in little-endian format.

PHYSFS_writeULE64 writes an unsigned 64-bit value in little-endian format.

These functions are intended to make it easier to write data in a consistent format across different platforms, regardless of the native byte order of the CPU.

PARAMETERS

PHYSFS_File *file
A pointer to the PHYSFS_File structure representing the file handle to which the data should be written.
PHYSFS_uintXX val
The unsigned integer value to be converted and written to the file. The type of this parameter corresponds to the size of the integer being written (e.g., PHYSFS_uint16 for PHYSFS_writeUBE16 and PHYSFS_writeULE16).

RETURN VALUES

All of these functions return non-zero on success and zero on failure. If a function fails, you can use PHYSFS_getLastErrorCode() to determine the specific error that occurred.

WARNINGS

On platforms that do not support 64-bit integers natively, PHYSFS_uint64 will typically be defined as a 32-bit integer type. Be aware of this limitation when writing 64-bit values on such platforms.
