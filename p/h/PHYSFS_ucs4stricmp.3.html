#define PHYSFS_file PHYSFS_File

1.0 API compatibility define. PHYSFS_file is identical to PHYSFS_File. This #define is here for backwards compatibility with the 1.0 API, which had an inconsistent capitalization convention in this case. New code should use PHYSFS_File, as this #define may go away someday.

#define PHYSFS_VERSION( x)

Value:

{ \
    (x)->major = PHYSFS_VER_MAJOR; \
    (x)->minor = PHYSFS_VER_MINOR; \
    (x)->patch = PHYSFS_VER_PATCH; \
}

Macro to determine PhysicsFS version program was compiled against. This macro fills in a PHYSFS_Version struct

PHYSFS_Version

Structure representing a version number.

This structure is used to represent version numbers. It has three members: major, minor, and patch.

It is primarily used by the PHYSFS_VERSION macro, which expands to a PHYSFS_Version structure representing the version of the library you compiled against. This is determined by what header the compiler uses. Note that if you dynamically linked the library, you might have a slightly newer or older version at runtime. That version can be determined with PHYSFS_getLinkedVersion(), which, unlike PHYSFS_VERSION, is not a macro.

Parameters

x A pointer to a PHYSFS_Version struct to initialize.

typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Firma de función para callbacks que enumeran archivos.

Warning

A partir de PhysicsFS 2.1, usa PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; te da más control sobre el proceso.

Estos se utilizan para informar una lista de entradas de directorio a un llamador original, un archivo/directorio/enlace simbólico por callback. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de ninguna cadena.

Estos callbacks se utilizan, a partir de PhysicsFS 1.1, como una alternativa a las funciones que devolverían listas que necesitan ser limpiadas con PHYSFS_freeList(). El callback significa que la biblioteca no necesita asignar una lista completa y todas las cadenas por adelantado.

Ten en cuenta que el orden de los datos prometido en las versiones de lista no es necesariamente el mismo en las versiones de callback. Consulta la documentación de APIs específicas, pero las cadenas pueden no estar ordenadas como esperas y podrías obtener cadenas duplicadas.

Parameters

data Puntero de datos definido por el usuario, pasado desde la API que finalmente llamó al callback.
origdir Una cadena que contiene la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio sobre el cual solicitaste la enumeración, pasado en el callback para tu conveniencia.
fname El nombre del archivo que se está enumerando. Puede que no esté en orden alfabético en comparación con otros callbacks que se han ejecutado, y no contendrá la ruta completa. Puedes recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

enum PHYSFS_ErrorCode

Valores que representan causas específicas de falla. La mayoría de las veces, solo deberías preocuparte por si una operación dada falló o no, pero puede haber ocasiones en las que planees manejar un caso de falla específico de manera elegante, por lo que proporcionamos códigos de error específicos.

La mayoría de estos errores son un poco vagos, y la mayoría no son cosas que puedas arreglar...si hay un error de permisos, por ejemplo, todo lo que realmente puedes hacer es pasar esa información al usuario y dejar que él decida cómo manejarlo. En la mayoría de estos casos, tu programa solo debería preocuparse de que no logró cumplir sus objetivos, y no preocuparse específicamente por qué.

Deinitialize the PhysicsFS library. This closes any files opened via PhysicsFS, blanks the search/write paths, frees memory, and invalidates all of your file handles.

int PHYSFS_delete (const char * filename)

Delete a file or directory. (filename) is specified in platform-independent notation in relation to the write dir.

A directory must be empty before this call can delete it.

Deleting a symlink will remove the link, not what it points to, regardless of whether you "permitSymLinks" or not.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Get a file listing of a search path's directory, using an application-defined callback, with errors reported. Internally, PHYSFS_enumerateFiles() just calls this function and then builds a list before returning to the application, so functionality is identical except for how the information is represented to the application.

Unlike PHYSFS_enumerateFiles(), this function does not return an array. Rather, it calls a function specified by the application once per element of the search path:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Items sent to the callback are not guaranteed to be in any order whatsoever. There is no sorting done at this level, and if you need that, you should probably use PHYSFS_enumerateFiles() instead, which guarantees alphabetical sorting. This form reports whatever is discovered in each archive before moving on to the next. Even within one archive, we can't guarantee what order it will discover data. Any sorting you find in these callbacks is just pure luck. Do not rely on it. As this walks the entire list of archives, you may receive duplicate filenames.

This API and the callbacks themselves are capable of reporting errors. Prior to this API, callbacks had to accept every enumerated item, even if they were only looking for a specific thing and wanted to stop after that, or had a serious error and couldn't alert anyone. Furthermore, if PhysicsFS itself had a problem (disk error or whatnot), it couldn't report it to the calling app, it would just have to skip items or stop enumerating outright, and the caller wouldn't know it had lost some data along the way.

Now the caller can be sure it got a complete data set, and its callback has control if it wants enumeration to stop early. See the documentation for PHYSFS_EnumerateCallback for details on how your callback should behave.

Parameters

dir Directory, in platform-independent notation, to enumerate.
c Callback function to notify about search path elements.
d Application-defined data passed to callback. Can be NULL.

Returns

non-zero on success, zero on failure. Use PHYSFS_getLastErrorCode() to obtain the specific error. If the callback returns PHYSFS_ENUM_STOP to stop early, this will be considered success. Callbacks returning PHYSFS_ENUM_ERROR will make this function return zero and set the error code to PHYSFS_ERR_APP_CALLBACK.

char ** PHYSFS_enumerateFiles (const char * dir)

Get a file listing of a search path's directory.

Warning

In PhysicsFS versions prior to 2.1, this function would return as many items as it could in the face of a failure condition (out of memory, disk i/o error, etc). Since this meant apps couldn't distinguish between complete success and partial failure, and since the function could always return NULL to report catastrophic failures anyway, in PhysicsFS 2.1 this function's policy changed: it will either return a list of complete results or it will return NULL for any failure of any kind, so we can guarantee that the enumeration ran to completion and has no gaps in its results.

Matching directories are interpolated. That is, if "C:\mydir" is in the search path and contains a directory "savegames" that contains "x.sav", "y.sav", and "z.sav", and there is also a "C:\userdir" in the search path that has a "savegames" subdirectory with "w.sav", then the following code:

char **rc = PHYSFS_enumerateFiles("savegames");

PHYSFS_freeList(rc);
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav].

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Agrega un archivo o directorio a la ruta de búsqueda. Si es un duplicado, la entrada no se agrega de nuevo, aunque la función tenga éxito. No puede agregar el mismo archivo a diferentes puntos de montaje: la verificación de duplicados se realiza contra el archivo y no contra el punto de montaje.

Cuando monta un archivo, se agrega a un sistema de archivos virtual... todos los archivos de todos los archivos se interpolan en un único árbol de archivos jerárquico. Dos archivos montados en el mismo lugar (o un archivo con archivos que se superponen a otro punto de montaje) pueden tener archivos superpuestos: en tal caso, se selecciona el archivo anterior en la ruta de búsqueda, y los otros archivos son inaccesibles para la aplicación. Esto permite que los archivos se utilicen para invalidar revisiones anteriores; puede utilizar el mecanismo de montaje para colocar archivos en un punto específico del árbol de archivos y evitar superposiciones; esto es útil para mods descargables que podrían pisotear datos de la aplicación o entre sí, por ejemplo.

El punto de montaje no necesita existir antes de montarlo, lo que es diferente de lo que pueden esperar aquellos familiarizados con el concepto de "montaje" de Unix. Además, se puede montar más de un archivo en el mismo punto de montaje, o los puntos de montaje y el contenido de los archivos pueden superponerse... el mecanismo de interpolación sigue funcionando como de costumbre.

Se permite especificar un enlace simbólico a un archivo o directorio aquí, independientemente del estado de PHYSFS_permitSymbolicLinks(). Esa función solo se ocupa de los enlaces simbólicos dentro del directorio o archivo montado.

void PHYSFS_permitSymbolicLinks (int allow)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y archivos contienen archivos que son solo punteros a otros archivos. En el sistema de archivos físico, abrir un enlace de este tipo abrirá (transparentemente) el archivo al que apunta.

Por defecto, PhysicsFS verificará si un archivo es realmente un enlace simbólico durante las llamadas de apertura y fallará si lo es. De lo contrario, el enlace podría sacarte de las rutas de escritura y búsqueda, y comprometer la seguridad.

Si deseas asumir ese riesgo, llama a esta función con un parámetro distinto de cero. Ten en cuenta que esto es más para aislar el lenguaje de scripting de un programa, en caso de que scripts no confiables intenten comprometer el sistema. En términos generales, un usuario podría tener una razón legítima para configurar un enlace simbólico, por lo que a menos que sientas que hay un peligro específico en permitirlos, deberías permitirlos.

Los enlaces simbólicos solo se verifican explícitamente cuando se trata con nombres de archivo en notación independiente de la plataforma. Es decir, al configurar tus rutas de búsqueda y escritura, etc., nunca se verifican los enlaces simbólicos.

Ten en cuenta que PHYSFS_stat() siempre verificará la ruta especificada; si esa ruta es un enlace simbólico, no se seguirá en ningún caso. Si los enlaces simbólicos no están permitidos a través de esta función, PHYSFS_stat() los ignora y trataría la consulta como si la ruta no existiera en absoluto.

El permiso de enlace simbólico se puede habilitar o deshabilitar en cualquier momento después de haber llamado a PHYSFS_init(), y está deshabilitado por defecto.

Parámetros

allow distinto de cero para permitir enlaces simbólicos, cero para denegar enlaces.

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convierte una cadena UTF-8 a una cadena Latin1. Las cadenas Latin1 son de 8 bits por carácter: una codificación popular de "alto ASCII".

Para asegurar que el búfer de destino sea lo suficientemente grande para la conversión, por favor asigna un búfer que sea el doble del tamaño del búfer de origen. UTF-8 expande los puntos de código latin1 mayores que 127 de 1 a 2 bytes, por lo que la cadena puede crecer en algunos casos.

Las cadenas que no quepan en el búfer de destino serán truncadas, pero siempre estarán terminadas en nulo y nunca tendrán una secuencia UTF-8 incompleta al final. Si la longitud del búfer es 0, esta función no hace nada.

Ten en cuenta que no proporcionamos un convertidor de UTF-8 a Latin1, ya que Latin1 no puede expresar la mayoría de los puntos de código Unicode. Es una codificación heredada; deberías estar convirtiendo lejos de ella en todo momento.

Parámetros

src Cadena de origen terminada en nulo en formato Latin1.
dst Búfer para almacenar la cadena UTF-8 convertida.
len Tamaño, en bytes, del búfer de destino.

Advertencia

Esta función no informará de un error si hay secuencias UTF-16 inválidas en la cadena de origen. Las reemplazará con un carácter '?' y continuará.

Las cadenas UTF-16 tienen 16 bits por carácter (excepto algunos caracteres, que son de 32 bits): TCHAR en Windows, al compilar con soporte Unicode. Las versiones modernas de Windows utilizan UTF-16. Las versiones de Windows anteriores a 2000 usaban TCHAR, pero solo manejaban UCS-2. UTF-16 es UCS-2, excepto por los caracteres que son de 4 bytes, los cuales de todos modos no son representables en UCS-2. Si no estás seguro, deberías estar usando UTF-16 en este momento en Windows.

Para asegurar que el búfer de destino sea lo suficientemente grande para la conversión, por favor asigna un búfer que sea el doble del tamaño del búfer de origen. UTF-8 nunca usa más de 32 bits por carácter, por lo que aunque puede reducir el tamaño de una cadena UTF-16, también puede expandirla.

Las cadenas que no quepan en el búfer de destino serán truncadas, pero siempre estarán terminadas en nulo y nunca tendrán una secuencia UTF-8 incompleta al final. Si la longitud del búfer es 0, esta función no hace nada.

int PHYSFS_utf8stricmp (const char * str1, const char * str2)

Comparación sin distinción de mayúsculas y minúsculas de dos cadenas UTF-8. Este es un reemplazo de strcasecmp/stricmp que espera que ambas cadenas estén en codificación UTF-8. Realizará "plegado de mayúsculas" para decidir si los puntos de código Unicode en las cadenas coinciden.

Si ambas cadenas son exclusivamente caracteres ASCII bajos, esto hará lo correcto, ya que también es UTF-8 válido. Si hay algún carácter ASCII alto, ¡esto no hará lo que esperas!

Informará qué cadena es "mayor que" la otra, pero ten en cuenta que esto no significa necesariamente nada: 'a' puede ser "menor que" 'b', pero un kuten japonés no tiene una relación alfabética significativa con una lambda griega, pero poder asignar un "valor" fiable hace que los algoritmos de ordenación sean posibles, aunque no del todo sensatos. La mayoría de los casos deberían tratar el valor de retorno como "igual" o "no igual".

Al igual que stricmp, esto espera que ambas cadenas estén terminadas en NULL.

Parámetros

str1 Primera cadena a comparar.
str2 Segunda cadena a comparar.

Devuelve

-1 si str1 es "menor que" str2, 1 si "mayor que", 0 si son iguales.

void PHYSFS_utf8ToUcs4 (const char * src, PHYSFS_uint32 * dst, PHYSFS_uint64 len)

Convert a UTF-8 string to a UCS-4 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UCS-4 strings are 32-bits per character. They are a superset of UTF-16, and can represent every character in Unicode. Every character is represented by exactly 32 bits.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 uses from one to four bytes per character, but UCS-4 always uses four bytes per character, so an entirely low-ASCII string will double in size! The UTF-8 characters that would take four bytes also take four bytes in UCS-4, so you don't need to allocate 4x the space just in case: double will do.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UCS-4 sequence at the end. If the buffer length is 0, this function does nothing.

Parameters

src Null-terminated source string in UTF-8 format.
dst Buffer to store converted UCS-4 string.
len Size, in bytes, of destination buffer.

PHYSFS_sint64 PHYSFS_writeBytes (PHYSFS_File * handle, const void * buffer, PHYSFS_uint64 len)

Write data to a PhysicsFS filehandle. The file must be opened for writing.

Please note that while (len) is an unsigned 64-bit integer, you are limited to 63 bits (9223372036854775807 bytes), so we can return a negative value on error. If length is greater than 0x7FFFFFFFFFFFFFFF, this function will immediately fail. For systems without a 64-bit datatype, you are limited to 31 bits (0x7FFFFFFF, or 2147483647 bytes). We trust most things won't need to do multiple gigabytes of i/o in one call anyhow, but why limit things?
