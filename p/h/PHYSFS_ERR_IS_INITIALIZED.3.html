NAME

PHYSFS_ERR_IS_INITIALIZED — La biblioteca PhysicsFS ya está inicializada.

SYNOPSIS

#include <physfs.h>

int PHYSFS_init(const char *argv0);

int PHYSFS_deinit(void);

const char * PHYSFS_getLastError(void);

DESCRIPTION

La llamada a la función PHYSFS_init devuelve PHYSFS_ERR_IS_INITIALIZED si la biblioteca PhysicsFS ya ha sido inicializada. En este caso, la biblioteca no se vuelve a inicializar ni se desinicializa, sino que se devuelve un código de error.

Para comprobar este error, se puede llamar a PHYSFS_getLastError(). Devolverá una cadena que describe el error.

La única forma de salir de este estado es llamar a PHYSFS_deinit() para desinicializar la biblioteca y luego volver a llamar a PHYSFS_init().

VALOR DE RETORNO

Cuando PHYSFS_init() devuelve PHYSFS_ERR_IS_INITIALIZED, esta función devuelve 0.

VER TAMBIÉN

PHYSFS_init(3), PHYSFS_deinit(3), PHYSFS_getLastError(3)

The version of the library you compiled against. This is determined by what header the compiler uses. Note that if you dynamically linked the library, you might have a slightly newer or older version at runtime. That version can be determined with PHYSFS_getLinkedVersion(), which, unlike PHYSFS_VERSION, is not a macro.

typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Function signature for callbacks that enumerate files.

Warning

As of PhysicsFS 2.1, Use PHYSFS_EnumerateCallback with PHYSFS_enumerate() instead; it gives you more control over the process.

These are used to report a list of directory entries to an original caller, one file/dir/symlink per callback. All strings are UTF-8 encoded. Functions should not try to modify or free any string's memory.

These callbacks are used, starting in PhysicsFS 1.1, as an alternative to functions that would return lists that need to be cleaned up with PHYSFS_freeList(). The callback means that the library doesn't need to allocate an entire list and all the strings up front.

Be aware that promised data ordering in the list versions are not necessarily so in the callback versions. Check the documentation on specific APIs, but strings may not be sorted as you expect and you might get duplicate strings.

Parameters

data User-defined data pointer, passed through from the API that eventually called the callback.
origdir A string containing the full path, in platform-independent notation, of the directory containing this file. In most cases, this is the directory on which you requested enumeration, passed in the callback for your convenience.
fname The filename that is being enumerated. It may not be in alphabetical order compared to other callbacks that have fired, and it will not contain the full path. You can recreate the fullpath with $origdir/$fname ... The file can be a subdirectory, a file, a symlink, etc.

enum PHYSFS_ErrorCode

Values that represent specific causes of failure. Most of the time, you should only concern yourself with whether a given operation failed or not, but there may be occasions where you plan to handle a specific failure case gracefully, so we provide specific error codes.

Most of these errors are a little vague, and most aren't things you can fix...if there's a permission error, for example, all you can really do is pass that information on to the user and let them figure out how to handle it. In most these cases, your program should only care that it failed to accomplish its goals, and not care specifically why.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtiene una lista de archivos de un directorio de la ruta de búsqueda, utilizando una función de devolución de llamada definida por la aplicación, con informes de errores. Internamente, PHYSFS_enumerateFiles() simplemente llama a esta función y luego construye una lista antes de devolverla a la aplicación, por lo que la funcionalidad es idéntica, excepto por cómo se representa la información a la aplicación.

A diferencia de PHYSFS_enumerateFiles(), esta función no devuelve una matriz. Más bien, llama a una función especificada por la aplicación una vez por cada elemento de la ruta de búsqueda:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

No se garantiza que los elementos enviados a la función de devolución de llamada estén en ningún orden particular. No se realiza ningún ordenamiento a este nivel, y si lo necesita, probablemente debería usar PHYSFS_enumerateFiles() en su lugar, que garantiza el ordenamiento alfabético. Esta forma informa lo que se descubre en cada archivo antes de pasar al siguiente. Incluso dentro de un archivo, no podemos garantizar el orden en que descubrirá los datos. *Cualquier ordenamiento que encuentre en estas devoluciones de llamada es pura suerte. No dependa de él.* A medida que recorre la lista completa de archivos, puede recibir nombres de archivo duplicados.

Esta API y las propias funciones de devolución de llamada son capaces de informar errores. Antes de esta API, las funciones de devolución de llamada tenían que aceptar cada elemento enumerado, incluso si solo buscaban algo específico y querían detenerse después, o si tenían un error grave y no podían alertar a nadie. Además, si PhysicsFS en sí tenía un problema (error de disco o similar), no podía informarlo a la aplicación que lo llamaba, simplemente tendría que omitir elementos o dejar de enumerar abiertamente, y el llamador no sabría que había perdido algunos datos en el camino.

Ahora, el llamador puede estar seguro de que recibió un conjunto de datos completo, y su función de devolución de llamada tiene el control si desea que la enumeración se detenga antes. Consulte la documentación de PHYSFS_EnumerateCallback para obtener detalles sobre cómo debe comportarse su función de devolución de llamada.

int PHYSFS_mount(const char *newDir, const char *mountPoint, int appendToPath)

Agrega un archivo o directorio a la ruta de búsqueda. Si es un duplicado, la entrada no se agrega de nuevo, aunque la función tenga éxito. No puede agregar el mismo archivo a dos puntos de montaje diferentes: la verificación de duplicados se realiza contra el archivo y no contra el punto de montaje.

Cuando monta un archivo, se agrega a un sistema de archivos virtual... todos los archivos en todos los archivos se interpolan en un único árbol de archivos jerárquico. Dos archivos montados en el mismo lugar (o un archivo con archivos que se superponen con otro punto de montaje) pueden tener archivos superpuestos: en tal caso, se selecciona el archivo anterior en la ruta de búsqueda, y los otros archivos son inaccesibles para la aplicación. Esto permite que los archivos se utilicen para anular revisiones anteriores; puede utilizar el mecanismo de montaje para colocar archivos en un punto específico del árbol de archivos y evitar superposiciones; esto es útil para mods descargables que podrían pisotear datos de la aplicación o entre sí, por ejemplo.

El punto de montaje no necesita existir antes de montarlo, lo que es diferente de lo que los familiarizados con el concepto de "montaje" de Unix pueden esperar. Además, se puede montar más de un archivo en el mismo punto de montaje, o los puntos de montaje y los contenidos de los archivos pueden superponerse... el mecanismo de interpolación sigue funcionando como de costumbre.

Se permite especificar un enlace simbólico a un archivo o directorio aquí, independientemente del estado de PHYSFS_permitSymbolicLinks(). Esa función solo se ocupa de los enlaces simbólicos dentro del directorio o archivo montado.

newDir directorio o archivo a agregar a la ruta, en notación dependiente de la plataforma.
mountPoint Ubicación en el árbol interpolado donde se "montará" este archivo, en notación independiente de la plataforma. NULL o "" es equivalente a "/".
appendToPath distinto de cero para agregar a la ruta de búsqueda, cero para anteponer.

Devoluciones

void PHYSFS_permitSymbolicLinks (int allow)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y archivos contienen archivos que son solo punteros a otros archivos. En el sistema de archivos físico, abrir un enlace de este tipo abrirá (de forma transparente) el archivo al que apunta.

Por defecto, PhysicsFS verificará si un archivo es realmente un enlace simbólico durante las llamadas de apertura y fallará si lo es. De lo contrario, el enlace podría sacarte de las rutas de escritura y búsqueda, y comprometer la seguridad.

Si deseas asumir ese riesgo, llama a esta función con un parámetro distinto de cero. Ten en cuenta que esto es más para poner en cuarentena el lenguaje de scripting de un programa, en caso de que scripts no confiables intenten comprometer el sistema. En términos generales, un usuario podría tener una razón legítima para configurar un enlace simbólico, por lo que a menos que sientas que hay un peligro específico en permitirlos, deberías permitirlos.

Los enlaces simbólicos solo se verifican explícitamente cuando se trata con nombres de archivo en notación independiente de la plataforma. Es decir, al configurar tus rutas de búsqueda y escritura, etc., nunca se verifican los enlaces simbólicos.

Si los enlaces simbólicos no están permitidos a través de esta función, PHYSFS_stat() los ignora y trataría la consulta como si la ruta no existiera en absoluto.

El permiso de enlaces simbólicos se puede habilitar o deshabilitar en cualquier momento después de haber llamado a PHYSFS_init(), y está deshabilitado por defecto.

Puedes cambiar la raíz de un archivo en cualquier momento, alterando el árbol de archivos interpolado (dependiendo de dónde cambien las rutas, un archivo diferente puede estar proporcionando varios archivos). Si estableces la raíz a NULL o "/", el archivo se tratará como si no se hubiera establecido ninguna raíz especial (como si el archivo se hubiera montado normalmente).

Cambiar la raíz solo afecta a las operaciones futuras en nombres de ruta; un archivo que se abrió desde una ruta que cambió debido a un setRoot no se verá afectado.

Establecer una nueva raíz no se limita a archivos en la ruta de búsqueda; también puedes establecer una en el directorio de escritura, lo que podría ser útil si tienes archivos abiertos para escritura y, por lo tanto, no puedes cambiar el directorio de escritura en este momento.

No es un error establecer un subdirectorio que no existe como raíz de un archivo; sin embargo, en este caso no se verán archivos. Si los directorios faltantes terminan creándose (un mkdir al sistema de archivos físico, etc.), esto se reflejará en el árbol interpolado.

Parámetros

archive directorio/archivo sobre el cual cambiar la raíz.
subdir nuevo subdirectorio que se convertirá en la raíz de este archivo.

Devoluciones

distinto de cero en caso de éxito, cero en caso de fallo. Usa PHYSFS_getLastErrorCode() para obtener el error específico.

Las cadenas que no quepan en el búfer de destino serán truncadas, pero siempre estarán terminadas en nulo y nunca tendrán una secuencia UCS-4 incompleta al final. Si la longitud del búfer es 0, esta función no hace nada.

NAME

PHYSFS_writeUBE16, PHYSFS_writeUBE32, PHYSFS_writeUBE64, PHYSFS_writeULE16, PHYSFS_writeULE32, PHYSFS_writeULE64 - funciones de escritura de datos binarios en un archivo PhysicsFS

LIBRARY

PhysicsFS API (libphysfs.a, libphysfs.so, physfs.dll)

SYNOPSIS

#include <physfs.h>

int PHYSFS_writeUBE16(PHYSFS_File *file, PHYSFS_uint16 val);
int PHYSFS_writeUBE32(PHYSFS_File *file, PHYSFS_uint32 val);
int PHYSFS_writeUBE64(PHYSFS_File *file, PHYSFS_uint64 val);
int PHYSFS_writeULE16(PHYSFS_File *file, PHYSFS_uint16 val);
int PHYSFS_writeULE32(PHYSFS_File *file, PHYSFS_uint32 val);
int PHYSFS_writeULE64(PHYSFS_File *file, PHYSFS_uint64 val);

DESCRIPTION

Estas funciones son utilidades para escribir valores numéricos en un archivo en un orden de bytes específico. Son convenientes porque manejan la conversión del orden de bytes nativo del sistema al orden de bytes deseado (endian grande o endian chico).

PHYSFS_writeUBE16, PHYSFS_writeUBE32, PHYSFS_writeUBE64 escriben valores de 16, 32 y 64 bits sin signo, respectivamente, en formato de orden de bytes grande (big-endian).

PHYSFS_writeULE16, PHYSFS_writeULE32, PHYSFS_writeULE64 escriben valores de 16, 32 y 64 bits sin signo, respectivamente, en formato de orden de bytes pequeño (little-endian).

Estas funciones toman un manejador de archivo PHYSFS_File* y el valor numérico a escribir. Si la escritura es exitosa, devuelven un valor distinto de cero. Si falla, devuelven cero y puedes obtener más información sobre el error llamando a PHYSFS_getLastErrorCode().

RETURN VALUES

Devuelven un valor distinto de cero en caso de éxito, y cero en caso de fallo. En caso de fallo, puedes encontrar lo que falló en PHYSFS_getLastErrorCode().
