NAME

physfs - Simple, portable, convenient library for reading data from a variety of archive types.

SYNOPSIS

#include <physfs.h>

DESCRIPTION

PhysicsFS is a library that provides a platform-independent API for reading data from a variety of archive types. It is designed to be simple to use, and to abstract away the complexities of different file systems and archive formats.

The library supports reading from plain directories, ZIP archives, and other formats that can be implemented as archivers. It also provides utilities for string conversion, byte order swapping, and file system operations.

Advertencia

Desde PhysicsFS 2.1, usa PHYSFS_EnumerateCallback con PHYSFS_enumerate() para tener más control sobre el proceso.

Estos se utilizan para reportar una lista de entradas de directorio a un llamador original, una entrada por callback. Todos los strings están codificados en UTF-8. Las funciones no deben intentar modificar o liberar la memoria de ningún string.

Estos callbacks se utilizan, a partir de PhysicsFS 1.1, como alternativa a las funciones que devuelven listas que deben ser liberadas con PHYSFS_freeList(). El callback significa que la biblioteca no necesita asignar una lista completa y todas las strings de antemano.

Ten en cuenta que la ordenación prometida en las versiones de lista no se garantiza necesariamente en las versiones de callback. Consulta la documentación de las API específicas, pero los strings pueden no estar ordenados como esperas y podrías obtener strings duplicados.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtiene una lista de archivos de un directorio de ruta de búsqueda, utilizando una devolución de llamada definida por la aplicación, con errores informados. Internamente, PHYSFS_enumerateFiles() simplemente llama a esta función y luego construye una lista antes de devolverla a la aplicación, por lo que la funcionalidad es idéntica excepto por cómo se representa la información a la aplicación.

A diferencia de PHYSFS_enumerateFiles(), esta función no devuelve una matriz. Más bien, llama a una función especificada por la aplicación una vez por elemento de la ruta de búsqueda:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Tenemos [%s] en [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // deme más datos, por favor.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

No se garantiza que los elementos enviados a la devolución de llamada estén en ningún orden específico. No se realiza ninguna clasificación a este nivel, y si la necesita, probablemente debería usar PHYSFS_enumerateFiles() en su lugar, que garantiza la clasificación alfabética. Esta forma informa lo que se descubre en cada archivo antes de pasar al siguiente. Incluso dentro de un archivo, no podemos garantizar el orden en que descubrirá los datos. Cualquier orden que encuentre en estas devoluciones de llamada es pura suerte. No dependa de ello. Dado que recorre toda la lista de archivos, es posible que reciba nombres de archivo duplicados.

Esta API y las propias devoluciones de llamada son capaces de informar errores. Antes de esta API, las devoluciones de llamada tenían que aceptar todos los elementos enumerados, incluso si solo buscaban algo específico y querían detenerse después de eso, o tenían un error grave y no podían alertar a nadie. Además, si PhysicsFS en sí tenía un problema (error de disco o similar), no podía informarlo a la aplicación que llama, solo tendría que omitir elementos o dejar de enumerar por completo, y el llamador no sabría que había perdido algunos datos en el camino.

Ahora el llamador puede estar seguro de que obtuvo un conjunto de datos completo, y su devolución de llamada tiene control si desea que la enumeración se detenga antes. Consulte la documentación de PHYSFS_EnumerateCallback para obtener detalles sobre cómo debe comportarse su devolución de llamada.

Parámetros

dir Directorio, en notación independiente de la plataforma, a enumerar.
c Función de devolución de llamada para notificar sobre elementos de la ruta de búsqueda.
d Datos definidos por la aplicación pasados ​​a la devolución de llamada. Puede ser NULL.

Retorna

Distinto de cero en caso de éxito, cero en caso de fallo. Use PHYSFS_getLastErrorCode() para obtener el error específico. Si la devolución de llamada devuelve PHYSFS_ENUM_STOP para detenerse antes, esto se considerará un éxito. Las devoluciones de llamada que devuelvan PHYSFS_ENUM_ERROR harán que esta función devuelva cero y establezca el código de error en PHYSFS_ERR_APP_CALLBACK.

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * Tenemos [%s].\n", *i);
PHYSFS_freeList(rc);

* Tenemos [z.sav].

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Agrega un archivo o directorio a la ruta de búsqueda. Si es un duplicado, la entrada no se agrega nuevamente, aunque la función tenga éxito. No puede agregar el mismo archivo a dos puntos de montaje diferentes: la verificación de duplicados se realiza contra el archivo y no contra el punto de montaje.

Cuando monta un archivo, se agrega a un sistema de archivos virtual... todos los archivos en todos los archivos se interpolan en un único árbol de archivos jerárquico. Dos archivos montados en el mismo lugar (o un archivo con archivos que se superponen a otro punto de montaje) pueden tener archivos superpuestos: en tal caso, se selecciona el archivo anterior en la ruta de búsqueda, y los otros archivos son inaccesibles para la aplicación. Esto permite que los archivos se utilicen para reemplazar revisiones anteriores; puede usar el mecanismo de montaje para colocar archivos en un punto específico del árbol de archivos y evitar superposiciones; esto es útil para mods descargables que podrían pisotear datos de aplicaciones o entre sí, por ejemplo.

El punto de montaje no necesita existir antes de montarlo, lo que es diferente de lo que los familiarizados con el concepto de "montaje" de Unix pueden esperar. Además, se pueden montar varios archivos en el mismo punto de montaje, o los puntos de montaje y el contenido de los archivos pueden superponerse... el mecanismo de interpolación aún funciona como de costumbre.

Se permite especificar un enlace simbólico a un archivo o directorio aquí, independientemente del estado de PHYSFS_permitSymbolicLinks(). Esa función solo se ocupa de los enlaces simbólicos dentro del directorio o archivo montado.

Warning

Unless you have some special, low-level need, you should be using PHYSFS_mount() instead of this.

This function operates just like PHYSFS_mount(), but takes a memory buffer instead of a pathname. This buffer contains all the data of the archive, and is used instead of a real file in the physical filesystem.

(newDir) must be a unique string to identify this archive. It is used to optimize archiver selection (if you name it XXXXX.zip, we might try the ZIP archiver first, for example, or directly choose an archiver that can only trust the data is valid by filename extension). This filename must be unique, as the system won't allow you to have two archives with the same name.

(ptr) must remain until the archive is unmounted. When the archive is unmounted, the system will call (del)(ptr), which will notify you that the system is done with the buffer, and give you a chance to free your resources. If this function fails, (del) is not called.

void PHYSfs_makepath (char *path, const char *dir1, const char *dir2, ... )

This function is deprecated. Use PHYSFS_mount() instead.

Build a path that is correctly formatted for the platform. This function is primarily useful for dealing with archives that contain other archives. For normal file access, PhysicsFS provides platform-neutral access, so you won't need to worry about path separators.

path must be a buffer large enough to hold the resulting path, including the null terminator.

dir1 is the first component of the path. If it is NULL, then no path will be created.

dir2 and subsequent arguments are optional path components. If they are NULL, the list of components is terminated.

Example:

char buf[PHYSFS_MAX_DIR_LEN];
physfs_makepath(buf, "foo", "bar", "baz", NULL);
On POSIX systems, buf will contain "/foo/bar/baz". On Windows systems, it will contain "foo\\bar\\baz".

Parameters

path A buffer to store the resulting path.
dir1 The first directory component.
dir2 The second directory component.

void PHYSFS_setErrorCode (PHYSFS_ErrorCode code)

Establece el código de error del hilo actual. Esto permite que puedas establecer el valor que se devolverá por el siguiente llamado a PHYSFS_getLastErrorCode(). Esto reemplazará cualquier código de error existente, ya sea establecido por tu aplicación o internamente por PhysicsFS.

Los códigos de error se almacenan por hilo; lo que estableces aquí no será accesible por otro hilo.

Cualquier llamada a PhysicsFS puede cambiar el código de error actual, por lo que cualquier código que estableces aquí será ligeramente frágil, y así no deberías construir un framework de reporting de errores serio sobre esta función. El objetivo principal de esta función es permitir que PHYSFS_Io implementaciones establezcan el estado de error, que generalmente será devuelto a tu aplicación cuando se haga una llamada a PHYSFS_Io que falla internamente.

Esta función no importa si el código de error es un valor conocido por PhysicsFS o no (pero PHYSFS_getErrorByCode() devolverá NULL para valores desconocidos). El valor será reportado sin interferencia por PHYSFS_getLastErrorCode().

int PHYSFS_setRoot (const char * archive, const char * subdir)

Hace que una subdirectorio de un archivo sea su directorio raíz. Esto te permite reducir los archivos accionables en un determinado archivo. Por ejemplo, si tienes x.zip con un archivo en y/z.txt montado a /a, si llamas a PHYSFS_setRoot("x.zip", "/y"), entonces la llamada a PHYSFS_openRead("/a/z.txt") será exitosa.

Puedes cambiar la raíz de un archivo en cualquier momento, alterando el árbol de archivos interpolado (dependiendo de donde se muevan las rutas, un archivo diferente podría proporcionar archivos diversos). Si estableces la raíz a NULL o "/", el archivo será tratado como si no hubiera sido establecida una raíz especial (como si el archivo se montara normally).

Cambiar la raíz solo afecta las operaciones futuras en rutas de archivos; un archivo que fue abierto desde una ruta que cambió debido a un setRoot no será afectado.

Establecer una nueva raíz no está limitado a archivos en el directorio de búsqueda; puedes establecer una en el directorio de escritura también, lo cual podría ser útil si tienes archivos abiertos para escribir y no puedes cambiar el directorio de escritura ahora.

No es un error establecer una subdirectorio que no exista como raíz de un archivo, aunque en ese caso no se verán archivos. Si los directorios faltantes terminan siendo creados (una mkdir en el sistema de archivos físico, etc), esto se reflejará en el árbol interpolado.

Parámetros

archive Directorio/archivo en el cual se cambia la raíz.
subdir Subdirectorio nuevo para ser la raíz de este archivo.

Retorno

no cero en éxito, cero en error. Usa PHYSFS_getLastErrorCode() para obtener el específico error.

int PHYSFS_setSaneConfig (const char * organization, const char * appName, const char * archiveExt, int includeCdRoms, int archivesFirst)

Configura rutas saneadas por defecto. Función de ayuda.

El directorio de escritura será establecido en el pref dir devuelto por

PHYSFS_getPrefDir(organization, appName)

, que se crea si no existe.

La información anterior es suficiente para asegurar que la carpeta de configuración de tu programa esté separada de otros desordenados, y sea independiente del sistema de operación.

El camino de búsqueda será:

  • Directorio de escritura (creado si no existe)
  • Directorio de base (PHYSFS_getBaseDir())
  • Todos los directorios de CD-ROM encontrados (opcional)

Estos directorios se buscan por extensiones (archiveExt), que, si son válidas y soportadas, también se agregan a la ruta de búsqueda. Si especificaste "PKG" para (archiveExt), y hay un archivo llamado data.PKG en la carpeta de base, se lo verificará. Las archivadas pueden ser appendidas o prepended a la ruta de búsqueda en orden alfabético, independientemente de donde las encontraron. Todos los archivados se montan en la raíz del sistema de archivos virtual ("/").

Todo lo anterior puede lograrse desde el programa, pero esta función lo hace todo por ti. Puedes agregar más a la ruta de búsqueda manualmente, también.

Parámetros

organization Nombre de tu empresa/grupo/etc para usarse como directorio, así que manténlo pequeño y sin adornos.
appName Nombre específico de tu programa, para separarlo de otros programas que usen PhysicsFS.
archiveExt Extensión usada por tu programa para especificar un archivado. Por ejemplo, Quake 3 usa "pk3", aunque sean solo archivos zip. Especifica NULL para no buscar archivados automáticamente. No especifíquela con la letra '.'; si quieres buscar archivos ZIP, especifíca "ZIP" y no ".ZIP" ... el búsqueda de archivados es insensible al caso.
includeCdRoms No cero para incluir CD-ROMs en la ruta de búsqueda, y (si (archiveExt) != NULL) buscar archivos. Esto puede causar un bloqueo significativo al acceder discos, y si no hay discos en la unidad (o incluso no montadas en sistemas Unix), no estarán disponibles. Puedes especificar cero y manejar la configuración de discos tú mismo.
archivesFirst No cero para prepending las archivadas a la ruta de búsqueda. Cero para append. Ignorado si !(archiveExt).

Retorno

no cero en éxito, cero en error. Usa PHYSFS_getLastErrorCode() para obtener el específico error.

int PHYSFS_ucs4stricmp (const PHYSFS_uint32 * str1, const PHYSFS_uint32 * str2)

Comparación insensible a mayúsculas y minúsculas de dos cadenas UCS-4. Este es un reemplazo de strcasecmp/stricmp que espera que ambas cadenas estén en codificación UCS-4 (también conocida como UTF-32). Hará un "plegado de mayúsculas" para decidir si los puntos de código Unicode en las cadenas coinciden.

Informará qué cadena es "mayor que" la otra, pero ten en cuenta que esto no significa necesariamente nada: 'a' puede ser "menor que" 'b', pero un kuten japonés no tiene una relación alfabética significativa con una lambda griega, pero poder asignar un "valor" confiable hace posibles los algoritmos de ordenación, aunque no sean del todo sensatos. La mayoría de los casos deben tratar el valor de retorno como "igual" o "no igual".

Convert a UTF-8 string to a UTF-16 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UTF-16 strings are 16-bits per character (except some chars, which are 32-bits): TCHAR on Windows, when building with Unicode support. Modern Windows releases use UTF-16. Windows releases before 2000 used TCHAR, but only handled UCS-2. UTF-16 is UCS-2, except for the characters that are 4 bytes, which aren't representable in UCS-2 at all anyhow. If you aren't sure, you should be using UTF-16 at this point on Windows.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 uses from one to four bytes per character, but UTF-16 always uses two to four, so an entirely low-ASCII string will double in size! The UTF-16 characters that would take four bytes also take four bytes in UTF-8, so you don't need to allocate 4x the space just in case: double will do.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-16 surrogate pair at the end. If the buffer length is 0, this function does nothing.

Parameters

src Null-terminated source string in UTF-8 format.
dst Buffer to store converted UTF-16 string.
len Size, in bytes, of destination buffer.
