typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Firma de función para devoluciones de llamada que enumeran archivos.

Advertencia

A partir de PhysicsFS 2.1, usa PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; te da más control sobre el proceso.

Estos se utilizan para informar una lista de entradas de directorio a un llamador original, un archivo/directorio/enlace simbólico por devolución de llamada. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de ninguna cadena.

Estas devoluciones de llamada se utilizan, a partir de PhysicsFS 1.1, como alternativa a las funciones que devolverían listas que necesitan ser liberadas con PHYSFS_freeList(). La devolución de llamada significa que la biblioteca no necesita asignar una lista completa y todas las cadenas por adelantado.

Ten en cuenta que el orden de los datos prometidos en las versiones de lista no es necesariamente el mismo en las versiones de devolución de llamada. Consulta la documentación de las API específicas, pero es posible que las cadenas no estén ordenadas como esperas y que obtengas cadenas duplicadas.

const char *PHYSFS_getPrefDir(const char *org, const char *app)

Obtener la ruta de directorio específica para archivos que se puedan escribir. Función de ayuda.

Obtener la ruta de directorio "pref". Esta es para donde los usuarios pueden escribir archivos personales (preferencias y guardar juegos, etc) específicos de su aplicación. Esta carpeta es única por usuario y por aplicación.

Esta función decide la ubicación adecuada en el sistema de archivos nativo, crea la carpeta si es necesario y devuelve una cadena en notación dependiente de plataforma, adecuada para pasar a PHYSFS_setWriteDir().

En Linux, podría ser: "/home/bob/.local/share/My Program Name"

En Mac OS X, podría ser: "/Users/bob/Library/Application Support/My Program Name"

(etc.)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

Advertencia

A menos que tenga alguna necesidad especial de bajo nivel, debería estar usando PHYSFS_mount() en lugar de esto.

¡Los archivos dentro de otros archivos pueden ser muy lentos! Si bien un PHYSFS_File puede buscar incluso cuando los datos están comprimidos, puede hacerlo rebobinando al principio y descomprimiendo todo antes del punto de búsqueda. El uso normal de archivos puede realizar muchas búsquedas en segundo plano. Como tal, es posible que encuentre que el uso normal de archivos es extremadamente doloroso si se monta de esta manera. Planifique en consecuencia: si, por ejemplo, tiene un archivo .zip que se autoextrae y desea montar algo dentro de él, comprima el contenido del archivo interno y asegúrese de que el archivo .zip externo no comprima también el archivo interno.

El uso más popular para esto es probablemente montar archivos almacenados dentro de otros archivos.

  • The Base Dir (PHYSFS_getBaseDir())
  • All found CD-ROM dirs (optionally)

These directories are then searched for files ending with the extension (archiveExt), which, if they are valid and supported archives, will also be added to the search path. If you specified "PKG" for (archiveExt), and there's a file named data.PKG in the base dir, it'll be checked. Archives can either be appended or prepended to the search path in alphabetical order, regardless of which directories they were found in. All archives are mounted in the root of the virtual file system ("/").

All of this can be accomplished from the application, but this just does it all for you. Feel free to add more to the search path manually, too.

Parameters

organization Name of your company/group/etc to be used as a dirname, so keep it small, and no-frills.
appName Program-specific name of your program, to separate it from other programs using PhysicsFS.
archiveExt File extension used by your program to specify an archive. For example, Quake 3 uses "pk3", even though they are just zipfiles. Specify NULL to not dig out archives automatically. Do not specify the '.' char; If you want to look for ZIP files, specify "ZIP" and not ".ZIP" ... the archive search is case-insensitive.
includeCdRoms Non-zero to include CD-ROMs in the search path, and (if (archiveExt) != NULL) search them for archives. This may cause a significant amount of blocking while discs are accessed, and if there are no discs in the drive (or even not mounted on Unix systems), then they may not be made available anyhow. You may want to specify zero and handle the disc setup yourself.
archivesFirst Non-zero to prepend the archives to the search path. Zero to append them. Ignored if !(archiveExt).

Returns

nonzero on success, zero on error. Use PHYSFS_getLastErrorCode() to obtain the specific error.

Detailed Description

These functions provide an interface to the archive files managed by the physfs library. They allow you to read from and write to files within the archives, as well as perform basic file operations like seeking, checking for end-of-file, and getting file lengths.

The byte-swapping functions (PHYSFS_readBE*, PHYSFS_readLE*, PHYSFS_writeBE*, PHYSFS_writeLE*) are convenience functions that handle the conversion between the platform's native byte order and the specified endianness (Big Endian or Little Endian).
