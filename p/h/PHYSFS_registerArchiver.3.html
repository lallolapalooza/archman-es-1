PHYSFS_Version


A structure that holds version information for the library.


Description
  

  This structure is used by PHYSFS_VERSION, which is a macro defined in
  the PhysicsFS header. It is used to check, at compile time, the version of the
  library you have compiled against.


Parameters
  






major The major version number.


minor The minor version number.


patch The patch version number.

PHYSFS_getLinkedVersion


Get the version of the dynamically linked library.


Returns
  

  A pointer to a PHYSFS_Version struct. Note that this is a pointer to an
  internal structure, and you should not attempt to modify it or free it.


Description
  

  This function returns the version of the PhysicsFS library that was linked
  against at runtime. This is important for dynamically linked libraries, as the
  header file you compiled against might be a different version than the library
  that is actually present on the system. This function allows you to determine
  the runtime version of the library.


It's important to note that PHYSFS_VERSION is a macro that
  provides compile-time version checking. PHYSFS_getLinkedVersion(), on
  the other hand, provides runtime version information. You might use
  PHYSFS_VERSION to ensure compatibility during compilation and
  PHYSFS_getLinkedVersion() to perform runtime checks or gather
  information about the library version.

PHYSFS_init


Initialize the PhysicsFS library.


Parameters
  






argv0 A string containing the name of the program,
    usually set to `argv[0]` from `main()`. This is used to determine the
    program's path for the default preferences directory.


errmsg A pointer to a string buffer where an error message
    can be written if initialization fails. If this is NULL, no error message
    will be generated.


maxfiles A hint for the maximum number of files that will
    be opened simultaneously. This can be used to pre-allocate resources. If set
    to zero, PhysicsFS will use a default value.




Returns
  

  1 on success, 0 on failure. If failure occurs, and
    errmsg is not NULL, the error message will be stored in the buffer
    pointed to by errmsg.


Description
  

  This function must be called before any other PhysicsFS functions are used. It
  initializes the library, sets up internal data structures, and determines the
  location of the default preferences directory.


The argv0 parameter is crucial for identifying the program's
    installation path, which is used to locate platform-specific configuration
    files and directories. Providing an accurate value for argv0 ensures
    that PhysicsFS can function correctly.


The maxfiles parameter allows you to provide a hint about
    the expected number of concurrent file operations. This can help PhysicsFS
    optimize resource allocation, although it's not a strict limit.


If initialization fails, the function returns 0, and an
    error message is optionally provided via the errmsg buffer.


See also
  






PHYSFS_deinit








PHYSFS_deinit


De-initialize the PhysicsFS library.


Description
  

  This function should be called when your application is shutting down to clean
  up any resources allocated by PhysicsFS. It closes all opened archives and
  files, frees memory, and generally restores the system to the state it was in
  before PHYSFS_init() was called.


It is important to call this function to prevent resource leaks
    and ensure a clean shutdown of the library.

int   PHYSFS_mount (const char * newDir, const char * mountPoint, int   appendToPath)


Add an archive or directory to the search path. If this is a
    duplicate, the entry is not added again, even though the function succeeds.
    You may not add the same archive to two different mount points: duplicate
    checking is done against the archive and not the mount point.


When you mount an archive, it is added to a virtual file
    system...all files in all of the archives are interpolated into a single
    hierarchical file tree. Two archives mounted at the same place (or an
    archive with files overlapping another mount point) may have overlapping
    files: in such a case, the file earliest in the search path is selected, and
    the other files are inaccessible to the application. This allows archives to
    be used to override previous revisions; you can use the mounting mechanism to
    place archives at a specific point in the file tree and prevent overlap; this
    is useful for downloadable mods that might trample over application data or
    each other, for example.


The mount point does not need to exist prior to mounting, which is
    different than those familiar with the Unix concept of "mounting"
    may expect. Also, more than one archive can be mounted to the same
    mount point, or mount points and archive contents can overlap...the
    interpolation mechanism still functions as usual.


Specifying a symbolic link to an archive or directory is allowed
    here, regardless of the state of PHYSFS_permitSymbolicLinks(). That
    function only deals with symlinks inside the mounted directory or
    archive.

void PHYSFS_permitSymbolicLinks (int allow)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y archivos contienen archivos que son solo punteros a otros archivos. En el sistema de archivos físico, abrir un enlace de este tipo abrirá (transparentemente) el archivo al que apunta.

Por defecto, PhysicsFS verificará si un archivo es realmente un enlace simbólico durante las llamadas open y fallará si lo es. De lo contrario, el enlace podría llevarte fuera de las rutas de escritura y búsqueda, y comprometer la seguridad.

Si deseas asumir ese riesgo, llama a esta función con un parámetro distinto de cero. Ten en cuenta que esto es más para aislar el lenguaje de scripting de un programa, en caso de que scripts no confiables intenten comprometer el sistema. En general, un usuario podría tener una razón legítima para configurar un enlace simbólico, por lo que a menos que sientas que hay un peligro específico al permitirlos, deberías permitirlos.

Los enlaces simbólicos solo se verifican explícitamente cuando se trata con nombres de archivo en notación independiente de la plataforma. Es decir, al configurar tus rutas de búsqueda y escritura, etc., nunca se verifican los enlaces simbólicos.

Ten en cuenta que PHYSFS_stat() siempre verificará la ruta especificada; si esa ruta es un enlace simbólico, no se seguirá en ningún caso. Si los enlaces simbólicos no están permitidos a través de esta función, PHYSFS_stat() los ignora y trataría la consulta como si la ruta no existiera en absoluto.

El permiso de enlace simbólico se puede habilitar o deshabilitar en cualquier momento después de haber llamado a PHYSFS_init(), y está deshabilitado por defecto.

Parámetros

allow distinto de cero para permitir enlaces simbólicos, cero para denegar enlaces.

PHYSFS_writeUBE16, PHYSFS_writeUBE32, PHYSFS_writeUBE64, PHYSFS_writeULE16, PHYSFS_writeULE32, PHYSFS_writeULE64 - convert and write an unsigned value in a specific endianness.

SYNOPSIS

#include <physfs.h>

int PHYSFS_writeUBE32(PHYSFS_File *file, PHYSFS_uint32 val);

Detailed Description

These functions convert a value from the platform's native byte order to the specified endianness (either big-endian or little-endian) and write it to a PHYSFS_File.

These are convenience functions. They will attempt to convert the value to the specified endianness and write it. If the platform's native byte order is already the target endianness, no conversion is performed.

On success, a non-zero value is returned. On failure, zero is returned, and you can find out what went wrong from PHYSFS_getLastErrorCode().
