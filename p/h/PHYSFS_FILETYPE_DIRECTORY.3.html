typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Signatura de funciones de callbacks que enumeran archivos.

Advertencia

Desde PhysicsFS 2.1, usa PHYSFS_EnumerateCallback con PHYSFS_enumerate() en lugar; te da más control sobre el proceso.

Estos se utilizan para reportar una lista de directorios de entrada a un llamador original, una entrada por callback. Todos los strings son codificados en UTF-8. Las funciones no deben intentar modificar o liberar la memoria de ningún string.

Estos callbacks se utilizan, desde PhysicsFS 1.1, como alternativa a funciones que devuelven listas que deben ser limpiadas con PHYSFS_freeList(). El callback significa que la librería no necesita alojar un lista completa y todas las strings de antemano.

Tienes que estar alerta de que el ordenamiento de los datos en las versiones de lista no necesariamente es así en las versiones de callback. Verifica la documentación de APIs específicas, pero los strings pueden no estar ordenados como esperas y podrías obtener duplicados.

Valores que representan causas específicas de fallo. La mayoría del tiempo, deberías prestar atención solo a si una operación falló o no, pero pueden haber ocasiones en las que planees manejar una situación específica de forma graciosas, por lo que ofrecemos códigos específicos de error.

int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 *to)

"Doblar" un punto de código Unicode a un equivalente en minúsculas. (Esto es para uso limitado y avanzado. Si no ve una necesidad inmediata, puede ignorarlo para siempre).

Convierte un punto de código Unicode en su equivalente en minúsculas. Los códigos inválidos o aquellos sin un equivalente en minúsculas se devuelven sin convertir.

Nota: ¡Puede obtener múltiples puntos de código como resultado! La letra eszeta alemana, por ejemplo, se convierte en dos puntos de código en minúsculas 's'. La teoría es que si doblas dos cadenas, una con eszeta y otra con 'SS', coincidirán.

Advertencia

Quienquiera que haya estudiado Unicode conoce el problema de la "I Turca". Esta API no lo maneja. Asume que una letra en todo Unicode se convierte de forma incorrecta. Si no conoce este tema, puede ignorar este problema para la mayoría del planeta, pero la perfección es imposible.

to El búfer donde se guardarán los valores de punto de código doblados. Debe apuntar a espacio para al menos 3 PHYSFS_uint32 ranuras.

El número de puntos de código producidos al doblar. Entre 1 y 3.

int PHYSFS_deinit (void )

Desinicializar la librería PhysicsFS. Esto cierra cualquier archivo abierto a través de PhysicsFS, limpia las rutas de búsqueda/escritura, libera memoria y invalida todos tus manejadores de archivo.

Nota: Esta llamada puede fallar si hay un archivo abierto para escritura que se niega a cerrarse (por ejemplo, el sistema operativo bajo el cual se ejecuta estaba almacenando en caché escrituras a un sistema de archivos en red, y el servidor de archivos ha caído, o un disco duro ha fallado, etc.). Generalmente es mejor cerrar todos los manejadores de escritura antes de llamar a esta función, para manejar un fallo específico de manera suave.

Una vez desinicializado correctamente, se puede volver a llamar a PHYSFS_init() para reiniciar el subsistema. Todos los estados predeterminados de la API se restauran en este punto, excepto cualquier asignador personalizado que hayas especificado, el cual sobrevive entre inicializaciones.

Retorno

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtiene una lista de archivos de un directorio de la ruta de búsqueda, usando una función de devolución de llamada definida por la aplicación, con informes de errores. Internamente, PHYSFS_enumerateFiles() simplemente llama a esta función y luego construye una lista antes de devolverla a la aplicación, por lo que la funcionalidad es idéntica excepto por cómo se representa la información a la aplicación.

A diferencia de PHYSFS_enumerateFiles(), esta función no devuelve una matriz. Más bien, llama a una función especificada por la aplicación una vez por cada elemento de la ruta de búsqueda:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Tenemos [%s] en [%s].\n", fname, origdir);
    return physFS_ENUM_OK;  // dame más datos, por favor.
}
// ...
PHYSFS_enumerate("/alguna/ruta", printDir, NULL);

No se garantiza que los elementos enviados a la función de devolución de llamada estén en ningún orden determinado. No se realiza ningún ordenamiento en este nivel, y si lo necesitas, probablemente deberías usar PHYSFS_enumerateFiles() en su lugar, que garantiza el ordenamiento alfabético. Esta forma informa lo que se descubre en cada archivo antes de pasar al siguiente. Incluso dentro de un mismo archivo, no podemos garantizar el orden en que descubrirá los datos. Cualquier ordenamiento que encuentres en estas devoluciones de llamada es pura suerte. No dependas de él. Dado que recorre toda la lista de archivos, puedes recibir nombres de archivo duplicados.

Esta API y las propias funciones de devolución de llamada son capaces de informar errores. Antes de esta API, las funciones de devolución de llamada tenían que aceptar cada elemento enumerado, incluso si solo buscaban algo específico y querían detenerse después, o tenían un error grave y no podían alertar a nadie. Además, si PhysicsFS en sí tenía un problema (error de disco o similar), no podía informarlo a la aplicación que lo llamaba, solo tendría que omitir elementos o detener la enumeración directamente, y el llamador no sabría que había perdido algunos datos en el camino.

Ahora el llamador puede estar seguro de que obtuvo un conjunto completo de datos, y su función de devolución de llamada tiene control si desea que la enumeración se detenga anticipadamente. Consulte la documentación de PHYSFS_EnumerateCallback para obtener detalles sobre cómo debe comportarse su función de devolución de llamada.

dir Directorio, en notación independiente de la plataforma, a enumerar.
c Función de devolución de llamada para notificar sobre los elementos de la ruta de búsqueda.
d Datos definidos por la aplicación pasados a la función de devolución de llamada. Puede ser NULL.

Retorna

Distinto de cero en caso de éxito, cero en caso de fallo. Utilice PHYSFS_getLastErrorCode() para obtener el error específico. Si la función de devolución de llamada devuelve PHYSFS_ENUM_STOP para detenerse anticipadamente, esto se considerará un éxito. Obtener la ruta específica del usuario y de la aplicación donde se pueden escribir archivos. Función de ayuda.

Obtener el "pref dir". Está destinado a ser donde los usuarios pueden escribir archivos personales (preferencias y partidas guardadas, etc.) que son específicos de su aplicación. Este directorio es único por usuario y por aplicación.

Esta función decidirá la ubicación apropiada en el sistema de archivos nativo, creará el directorio si es necesario y devolverá una cadena en notación dependiente de la plataforma, adecuada para pasar a PHYSFS_setWriteDir().

En Windows, esto podría parecerse a: "C:\\Users\\bob\\AppData\\Roaming\\Mi Compañía\\Nombre de Mi Programa"

En Linux, esto podría parecerse a: "/home/bob/.local/share/Nombre de Mi Programa"

En Mac OS X, esto podría parecerse a: "/Users/bob/Library/Application Support/Nombre de Mi Programa"

(etc.)

Probablemente debería usar el directorio de preferencias para su directorio de escritura, y también ponerlo cerca del principio de su ruta de búsqueda. Versiones anteriores de PhysicsFS ofrecían solo PHYSFS_getUserDir() y le dejaban a usted determinar dónde debían ir los archivos dentro de ese árbol. Esto encuentra la ubicación correcta para cualquier plataforma, que no solo cambia entre sistemas operativos, sino también entre versiones del mismo sistema operativo.

Especifica el nombre de su organización (si no es una organización real, su nombre o un dominio de Internet que posea podría servir) y el nombre de su aplicación. Estos deben ser nombres propios.

Tanto las cadenas (org) como (app) pueden convertirse en parte de un nombre de directorio, así que siga estas reglas:

  • Intente usar la misma cadena de organización (incluida la sensibilidad a mayúsculas y minúsculas) para todas sus aplicaciones que utilizan esta función.
  • Siempre use una cadena de aplicación única para cada una, y asegúrese de que nunca cambie para una aplicación una vez que haya decidido sobre ella.
  • Los caracteres Unicode son legales, siempre que estén codificados en UTF-8, pero...
  • ... solo use letras, números y espacios. Evite la puntuación como "Nombre del Juego 2: La Venganza del Chico Malo" ... "Nombre del Juego 2" es suficiente.

El puntero devuelto por esta función sigue siendo válido hasta que vuelva a llamar a esta función, o llame a PHYSFS_deinit(). Sin embargo, esta no es necesariamente una llamada rápida, por lo que debería llamarla una vez al inicio y copiar la cadena si la necesita.

Debe suponer que la ruta devuelta por esta función es el único lugar seguro para escribir archivos (y que PHYSFS_getUserDir() y PHYSFS_getBaseDir(), aunque podrían ser escribibles, o incluso padres de la ruta devuelta, no son donde debe escribir cosas).

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

newDir directory or archive to add to the path, in platform-dependent notation.
mountPoint Location in the interpolated tree that this archive will be "mounted", in platform-independent notation. NULL or "" is equivalent to "/".
appendToPath nonzero to append to search path, zero to prepend.

Returns

nonzero if added to path, zero on failure (bogus archive, dir missing, etc). Use PHYSFS_getLastErrorCode() to obtain the specific error.

int PHYSFS_mountPath (PHYSFS_File ** file, const char * newDir, const char * mountPoint, int appendToPath)

Agrega un archivo, contenido en un manejador PHYSFS_File, a la ruta de búsqueda.

Advertencia

A menos que tenga una necesidad especial de bajo nivel, debería estar usando PHYSFS_mount() en lugar de esta función.

¡Los archivos dentro de archivos pueden ser muy lentos! Mientras que un PHYSFS_File puede buscar incluso cuando los datos están comprimidos, puede hacerlo retrocediendo al inicio y descomprimiendo todo antes del punto de búsqueda. El uso normal de archivos puede realizar muchas búsquedas en segundo plano. Como tal, podría encontrar que el uso normal de archivos es extremadamente tedioso si se montan de esta manera. Planifique en consecuencia: si, por ejemplo, tiene un archivo .zip autoextraíble y desea montar algo en él, comprima el contenido del archivo interno y asegúrese de que el archivo .zip externo no comprima también el archivo interno.

Esta función opera igual que PHYSFS_mount(), pero toma un manejador PHYSFS_File en lugar de un nombre de ruta. Este manejador contiene todos los datos del archivo y se utiliza en lugar de un archivo real en el sistema de archivos físico. El PHYSFS_File puede estar respaldado por un archivo real en el sistema de archivos físico, pero no es necesariamente así. El uso más popular para esto es probablemente montar archivos almacenados dentro de otros archivos.

(newDir) debe ser una cadena única para identificar este archivo. Se utiliza para optimizar la selección del archivador (si lo nombra XXXXX.zip, podríamos intentar primero el archivador ZIP, por ejemplo, o elegir directamente un archivador que solo pueda confiar en que los datos son válidos por la extensión del nombre del archivo). No necesita referirse a un archivo real en absoluto. Si la extensión del nombre del archivo no es útil, el sistema intentará con cada archivador hasta que uno funcione o ninguno de ellos lo haga. Este nombre de archivo debe ser único, ya que el sistema no le permitirá tener dos archivos con el mismo nombre.

(file) debe permanecer hasta que el archivo se desmonte. Cuando el archivo se desmonte, el sistema llamará a PHYSFS_close(file). Si necesita que este manejador sobreviva, tendrá que envolverlo en un PHYSFS_Io y utilizar PHYSFS_mountIo() en su lugar.

Si esta función falla, no se llama a PHYSFS_close(file).

newDir Nombre de archivo que puede representar este flujo.
mountPoint Ubicación en el árbol interpolado donde se "montará" este archivo, en notación independiente de la plataforma. NULL o "" es equivalente a "/".
appendToPath distinto de cero para agregar a la ruta de búsqueda, cero para anteponer.

Retorna

Distinto de cero si se agregó a la ruta, cero en caso de fallo (archivo inválido, etc.). Use PHYSFS_getLastErrorCode() para obtener el error específico.

Convierte una cadena UTF-8 a una cadena Latin1. Las cadenas Latin1 son de 8 bits por carácter: una codificación popular de "alto ASCII".

Para asegurar que el búfer de destino sea lo suficientemente grande para la conversión, por favor, asigna un búfer que sea el doble del tamaño del búfer de origen. UTF-8 expande los puntos de código latin1 mayores que 127 de 1 a 2 bytes, por lo que la cadena puede crecer en algunos casos.

Por favor, ten en cuenta que no proporcionamos un convertidor de UTF-8 a Latin1, ya que Latin1 no puede expresar la mayoría de los puntos de código Unicode. Es una codificación heredada; deberías estar convirtiéndote lejos de ella en todo momento.

Parámetros

src Cadena de origen terminada en nulo en formato Latin1.
dst Búfer para almacenar la cadena UTF-8 convertida.

Description

These functions are convenience wrappers around PHYSFS_write(). They convert an unsigned integer from the host platform's native byte order to the specified endianness (big-endian or little-endian) and then write that value to the specified file.

Endianness is a way of storing byte sequences. Big-endian means the most significant byte is stored first (at the lowest memory address). Little-endian means the least significant byte is stored first.

Most modern systems (like x86, x86_64, ARM) are little-endian. Older architectures (like SPARC, PowerPC) were often big-endian.

Network byte order is always big-endian, so if you are writing data that will be sent over a network, you'll want to use the big-endian variants of these functions.

PHYSFS_writeUBE16() converts and writes an unsigned 16-bit big-endian value.

PHYSFS_writeUBE32() converts and writes an unsigned 32-bit big-endian value.

PHYSFS_writeUBE64() converts and writes an unsigned 64-bit big-endian value.

PHYSFS_writeULE16() converts and writes an unsigned 16-bit little-endian value.

PHYSFS_writeULE32() converts and writes an unsigned 32-bit little-endian value.

PHYSFS_writeULE64() converts and writes an unsigned 64-bit little-endian value.
