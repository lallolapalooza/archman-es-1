PHYSFS_enumerate

Esto es lo mismo que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, excepto que puede devolver un resultado de la devolución de llamada: a saber, si está buscando algo específico, una vez que lo encuentra, puede indicarle a PhysicsFS que deje de enumerar más. Esto se usa con PHYSFS_enumerate(), que esperemos que hayamos hecho bien esta vez. :)

Parámetros

data Puntero de datos definido por el usuario, pasado desde la API que finalmente llamó a la devolución de llamada.
origdir Una cadena que contiene la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio sobre el cual solicitó la enumeración, pasado en la devolución de llamada para su conveniencia.
fname El nombre del archivo que se está enumerando. Es posible que no esté en orden alfabético en comparación con otras devoluciones de llamada que se han activado, y no contendrá la ruta completa. Puede recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Firma de función para devoluciones de llamada que enumeran archivos.

Advertencia

A partir de PhysicsFS 2.1, use PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; le da más control sobre el proceso.

Estos se utilizan para informar una lista de entradas de directorio a un llamador original, un archivo/directorio/enlace simbólico por devolución de llamada. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de ninguna cadena.

Estas devoluciones de llamada se utilizan, a partir de PhysicsFS 1.1, como alternativa a las funciones que devolverían listas que deben limpiarse con PHYSFS_freeList(). La devolución de llamada significa que la biblioteca no necesita asignar una lista completa y todas las cadenas por adelantado.

Tenga en cuenta que el orden prometido de los datos en las versiones de lista no es necesariamente el mismo en las versiones de devolución de llamada. Consulte la documentación de las API específicas, pero es posible que las cadenas no estén ordenadas como espera y que reciba cadenas duplicadas.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtiene una lista de archivos de un directorio de ruta de búsqueda, utilizando una función de devolución de llamada definida por la aplicación, con informes de errores. Internamente, PHYSFS_enumerateFiles() simplemente llama a esta función y luego construye una lista antes de devolverla a la aplicación, por lo que la funcionalidad es idéntica excepto por cómo se representa la información a la aplicación.

A diferencia de PHYSFS_enumerateFiles(), esta función no devuelve una matriz. En cambio, llama a una función especificada por la aplicación una vez por elemento de la ruta de búsqueda:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

No se garantiza que los elementos enviados a la función de devolución de llamada estén en ningún orden determinado. No se realiza ningún ordenamiento en este nivel, y si lo necesita, probablemente debería usar PHYSFS_enumerateFiles() en su lugar, que garantiza la ordenación alfabética. Esta forma informa lo que se descubre en cada archivo antes de pasar al siguiente. Incluso dentro de un solo archivo, no podemos garantizar el orden en que descubrirá los datos. _Cualquier ordenamiento que encuentre en estas devoluciones de llamada es pura suerte. No confíe en él._ Como esto recorre toda la lista de archivos, puede recibir nombres de archivo duplicados.

Esta API y las propias funciones de devolución de llamada son capaces de informar errores. Antes de esta API, las funciones de devolución de llamada tenían que aceptar cada elemento enumerado, incluso si solo buscaban algo específico y querían detenerse después de eso, o tenían un error grave y no podían alertar a nadie. Además, si PhysicsFS en sí tenía un problema (error de disco o similar), no podía informarlo a la aplicación que llamaba, solo tenía que omitir elementos o dejar de enumerar directamente, y el llamador no sabría que había perdido algunos datos en el camino.

Ahora el llamador puede estar seguro de que obtuvo un conjunto de datos completo, y su función de devolución de llamada tiene control si desea que la enumeración se detenga antes. Consulte la documentación de PHYSFS_EnumerateCallback para obtener detalles sobre cómo debe comportarse su función de devolución de llamada.

Parámetros

dir Directorio, en notación independiente de la plataforma, a enumerar.
c Función de devolución de llamada para notificar sobre los elementos de la ruta de búsqueda.
d Datos definidos por la aplicación pasados a la función de devolución de llamada. Puede ser NULL.

Devoluciones

Distinto de cero en caso de éxito, cero en caso de fallo. Utilice PHYSFS_getLastErrorCode() para obtener el error específico. Si la función de devolución de llamada devuelve PHYSFS_ENUM_STOP para detenerse antes, esto se considerará un éxito. Las funciones de devolución de llamada que devuelven PHYSFS_ENUM_ERROR harán que esta función devuelva cero y establezca el código de error en PHYSFS_ERR_APP_CALLBACK.

char ** PHYSFS_enumerateFiles (const char * dir)

Obtiene una lista de archivos de un directorio de ruta de búsqueda.

Advertencia

En versiones de PhysicsFS anteriores a la 2.1, esta función devolvería tantos elementos como pudiera frente a una condición de error (falta de memoria, error de E/S de disco, etc.). Dado que esto significaba que las aplicaciones no podían distinguir entre el éxito completo y el fallo parcial, y dado que la función siempre podía devolver NULL para informar fallos catastróficos de todos modos, en PhysicsFS 2.1 la política de esta función cambió: devolverá una lista de resultados completos o devolverá NULL para cualquier fallo de cualquier tipo, para que podamos garantizar que la enumeración se completó y no tiene huecos en sus resultados.

Los directorios coincidentes se interpolan. Es decir, si "C:\mydir" está en la ruta de búsqueda y contiene un directorio "savegames" que contiene "x.sav", "y.sav", y "z.sav", y también hay un "C:\userdir" en la ruta de búsqueda que tiene un subdirectorio "savegames" con "w.sav", entonces el siguiente código:

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);
PHYSFS_freeList(rc);
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..fi

No olvide llamar a PHYSFS_freeList() con el valor de retorno de esta función cuando haya terminado con él.

PHYSFS_mount

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

This function operates exactly like PHYSFS_mount, but takes a PHYSFS_File instead of a filename. The PHYSFS_File contains all the archive data and is used in place of a physical file on the physical filesystem. int PHYSFS_registerArchiver (const PHYSFS_Archiver * archiver)

Agrega un nuevo archivador al sistema.

Advertencia

Esto es para usos avanzados y complejos. No lo necesitas a menos que realmente sepas lo que estás haciendo. La mayoría de las aplicaciones no lo necesitarán.

Si deseas proporcionar tu propio archivador (por ejemplo, un formato de archivo de archivo personalizado, o algo virtual que quieras hacer que parezca un sistema de archivos al que puedas acceder a través de las API normales de PhysicsFS), aquí es donde comienzas. Una vez que un archivador se registra correctamente, puedes usar PHYSFS_mount() para agregar archivos que tu archivador soporta a la ruta de búsqueda, o tal vez usarlo como directorio de escritura. Internamente, PhysicsFS usa esta función para registrar sus propios archivadores incorporados, como el soporte para .zip, etc.

No puedes tener dos archivadores que manejen la misma extensión. Si vas a tener un conflicto, puedes anular el registro del otro archivador (incluidos los incorporados) con PHYSFS_deregisterArchiver().

Los datos en (archiver) se copian; puedes liberar este puntero cuando esta función retorne.

Una vez que esta función retorna con éxito, PhysicsFS podrá soportar archivos de este tipo hasta que anules el registro del archivador nuevamente.

Parámetros

archiver El archivador a registrar.

Retorna

Cero en caso de error, distinto de cero en caso de éxito.

Obsoleto

int PHYSFS_setAllocator (const PHYSFS_Allocator * allocator)

Conecta tus propias rutinas de asignación a PhysicsFS. (Esto es para un uso limitado y avanzado. Si no ves inmediatamente la necesidad, probablemente puedas ignorarlo para siempre).

Por defecto, PhysicsFS usará lo que sea razonable para una plataforma para administrar memoria dinámica (generalmente malloc/realloc/free de ANSI C, pero algunas plataformas pueden usar algo más), pero en algunos casos inusuales, la aplicación podría querer más control sobre la administración de memoria de la biblioteca. Esto te permite redirigir PhysicsFS para que use tus propias rutinas de asignación en su lugar. Solo puedes llamar a esta función antes de PHYSFS_init(); si la biblioteca está inicializada, rechazará tus intentos de cambiar el asignador a mitad de camino. Puedes llamar a esta función después de PHYSFS_deinit() si estás dispuesto a cerrar la biblioteca y reiniciarla con un nuevo asignador; esta es una operación segura y compatible. El asignador permanece intacto entre las llamadas de deinit/init. Si deseas volver al asignador predeterminado de la plataforma, pasa un NULL aquí.

Si no estás seguro de qué hacer con esta función, puedes ignorarla completamente.

Parámetros

allocator Estructura que contiene los puntos de entrada de tu asignador.

Retorna

Cero en caso de fallo, distinto de cero en caso de éxito. Esta llamada solo falla cuando se usa entre llamadas a PHYSFS_init() y PHYSFS_deinit().

int PHYSFS_setBuffer (PHYSFS_File * handle, PHYSFS_uint64 bufsize)

Configura el búfer para un manejador de archivo PhysicsFS. Define un búfer de E/S para un manejador de archivo. Se asignará un bloque de memoria de (bufsize) bytes y se asociará con (handle).

void PHYSFS_setErrorCode (PHYSFS_ErrorCode code)

Establece el código de error del hilo actual. Esto permite que establezcas el valor que será devuelto por la próxima llamada a PHYSFS_getLastErrorCode(). Esto sobrescribirá cualquier código de error existente, ya sea establecido por tu aplicación o por PhysicsFS.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Establece una subcarpeta de un archivo como la carpeta raíz. Esto te permite restringir los archivos accesibles a una carpeta específica. Por ejemplo, si tienes un archivo x.zip en y/z.txt montado en /a, si llamas a PHYSFS_setRoot("x.zip", "/y"), entonces la llamada PHYSFS_openRead("/a/z.txt") será exitosa.

Puedes cambiar la carpeta raíz de un archivo en cualquier momento, alterando así el árbol de archivos interpolado (dependiendo de dónde se busquen las rutas, un archivo diferente podría proporcionar archivos distintos). Si estableces la carpeta raíz en NULL o en "/" el archivo se tratará como si no hubiera sido configurado de forma especial (como si se hubiera montado normalmente).

Cambiar la carpeta raíz solo afecta a las operaciones futuras en las rutas de archivos; un archivo que se abrió desde una ruta que cambió debido a una llamada a PHYSFS_setRoot no se verá afectado.

Establecer una nueva carpeta raíz no se limita a los archivos en el directorio de búsqueda; puedes establecerla en el directorio de escritura también, lo cual puede ser útil si tienes archivos abiertos para escribir y no puedes cambiar el directorio de escritura en ese momento.

No es un error establecer una subcarpeta que no exista como la carpeta raíz de un archivo; sin embargo, no se mostrarán archivos en este caso. Si las carpetas faltantes se crean (una mkdir en el sistema de archivos físico, etc.), esto se reflejará en el árbol interpolado.

Parámetros

archive Carpeta/archivo sobre el cual se cambiará la carpeta raíz.
subdir Carpeta subalterna nueva como carpeta raíz de este archivo.

Retorno

Distinto de cero en caso de éxito, cero en caso de error. Usa PHYSFS_getLastErrorCode() para obtener el error específico.

int PHYSFS_setSaneConfig (const char * organization, const char * appName, const char * archiveExt, int includeCdRoms, int archivesFirst)

Establece rutas por defecto razonables. Una función de ayuda.

El directorio de escritura se establecerá en el directorio de preferencias devuelto por

PHYSFS_getPrefDir(organization, appName)

, que se crea si no existe.

La explicación anterior es suficiente para asegurar que la carpeta de configuración de tu programa esté separada de otros desordenes y sea independiente del sistema operativo.

La ruta de búsqueda será:

  • Directorio de escritura (creado si no existe)
  • Directorio base (PHYSFS_getBaseDir())
  • Archivos de CD-ROM encontrados (opcional)

Estos directorios se buscan para archivos con la extensión especificada (archiveExt), que, si son válidos y soportados, también se añadirán a la ruta de búsqueda. Si especificaste "PKG" para (archiveExt), y hay un archivo llamado data.PKG en el directorio base, se verificará. Los archivos pueden añadirse al principio o al final de la ruta de búsqueda en orden alfabético, independientemente de dónde se encontraran. Todos los archivos se montan en la raíz del sistema de archivos virtual ("/").

Todo lo anterior puede realizarse manualmente, pero esta función hace todo por ti. Puedes añadir más elementos a la ruta de búsqueda manualmente también.

Parámetros

organization Nombre de tu organización/grupo/etc a usar como nombre de carpeta, así que mantenlo corto y sin añadidos.
appName Nombre específico del programa de tu aplicación, para separarlo de otros programas que usan PhysicsFS.
archiveExt Extensión utilizada por tu programa para especificar un archivo. Por ejemplo, Quake 3 usa "pk3", aunque sean simplemente archivos zip. Especifica NULL para no buscar archivos automáticamente. No especifiques el punto '.'; si quieres buscar archivos ZIP, especifica "ZIP" y no ".ZIP"... la búsqueda de archivos se realiza sin distinción de mayúsculas y minúsculas.
includeCdRoms Distinto de cero para incluir CD-ROMs en la ruta de búsqueda, y (si (archiveExt) != NULL) buscarlos para encontrar archivos. Esto puede causar una pausa significativa al acceder a los discos, y si no hay discos en la unidad (o incluso no montados en sistemas Unix), pueden no estar disponibles. Puedes especificar cero y manejar la configuración de discos tú mismo.
archivesFirst Distinto de cero para anteponer los archivos a la ruta de búsqueda. Cero para añadirlos al final. Ignorado si !(archiveExt).

Retorno

Distinto de cero en caso de éxito, cero en caso de error. Usa PHYSFS_getLastErrorCode() para obtener el error específico.

Para asegurar que el búfer de destino sea lo suficientemente grande para la conversión, por favor, asigna un búfer que sea el doble del tamaño del búfer de origen. UTF-8 expande los puntos de código latin1 mayores que 127 de 1 a 2 bytes, por lo que la cadena puede crecer en algunos casos.

Tenga en cuenta que no proporcionamos un conversor de UTF-8 a Latin1, ya que Latin1 no puede expresar la mayoría de los puntos de código Unicode. Es una codificación heredada; deberías alejarte de ella en todo momento.
