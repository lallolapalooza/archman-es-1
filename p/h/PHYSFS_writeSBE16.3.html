Define de compatibilidad con la API 1.0. PHYSFS_file es idéntico a PHYSFS_File. Este #define está aquí para compatibilidad con versiones anteriores de la API 1.0, que tenía una convención de capitalización inconsistente en este caso. PHYSFS_enumerate

Esto es lo mismo que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, excepto que puede devolver un resultado del callback: a saber: si está buscando algo específico, una vez que lo encuentra, puede indicarle a PhysicsFS que deje de enumerar más. Parámetros

data Puntero de datos definido por el usuario, pasado desde la API que finalmente llamó al callback.
origdir Una cadena que contiene la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio sobre el cual solicitó la enumeración, pasado en el callback para su conveniencia.
fname El nombre del archivo que se está enumerando. Puede que no esté en orden alfabético en comparación con otros callbacks que se han ejecutado, y no contendrá la ruta completa. Puede recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

Advertencia

A partir de PhysicsFS 2.1, use PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; le da más control sobre el proceso.

Estos se utilizan para informar una lista de entradas de directorio a un llamador original, un archivo/directorio/enlace simbólico por callback. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de ninguna cadena.

Estos callbacks se utilizan, a partir de PhysicsFS 1.1, como una alternativa a las funciones que devolverían listas que necesitan ser limpiadas con PHYSFS_freeList(). El callback significa que la biblioteca no necesita asignar una lista completa y todas las cadenas por adelantado.

int PHYSFS_deinit (void )

Inicializa la biblioteca PhysicsFS. Esto cierra todos los archivos abiertos a través de PhysicsFS, vacía las rutas de búsqueda/escritura, libera memoria e invalida todos tus manejadores de archivo.

Tenga en cuenta que esta llamada puede FALLAR si hay un archivo abierto para escritura que se niega a cerrarse (por ejemplo, el sistema operativo subyacente estaba almacenando en búfer escrituras a un sistema de archivos de red y el servidor de archivos ha fallado, o un disco duro ha fallado, etc.). Generalmente es mejor cerrar todos los manejadores de escritura usted mismo antes de llamar a esta función, para poder manejar graciosamente un fallo específico.

Una vez inicializado con éxito, se puede volver a llamar a PHYSFS_init() para reiniciar el subsistema. Todos los estados de la API por defecto se restauran en este punto, con la excepción de cualquier asignador personalizado que haya especificado, que sobrevive entre inicializaciones.

Devoluciones

distinto de cero en caso de éxito, cero en caso de error. Los detalles del error se pueden obtener de PHYSFS_getLastError(). Si falla, el estado de PhysFS es indefinido y probablemente muy dañado.

int PHYSFS_delete (const char * filename)

Elimina un archivo o directorio. (filename) se especifica en notación independiente de la plataforma en relación con el directorio de escritura.

Un directorio debe estar vacío antes de que esta llamada pueda eliminarlo.

La eliminación de un enlace simbólico eliminará el enlace, no lo que apunta, independientemente de si "permitSymLinks" está activado o no.

Por lo tanto, si tienes el directorio de escritura configurado en "C:\mygame\writedir" y llamas a PHYSFS_delete("downloads/maps/level1.map"), entonces el archivo "C:\mygame\writedir\downloads\maps\level1.map" se elimina del sistema de archivos físico, si existe y el sistema operativo permite la eliminación.

Ten en cuenta que en sistemas Unix, la eliminación de un archivo puede tener éxito, pero el archivo real no se eliminará hasta que todos los procesos que tengan un manejador de archivo abierto para él (incluido tu programa) cierren sus manejadores.

Lo más probable es que los bits que componen el archivo todavía existan, simplemente se ponen a disposición para ser sobrescritos más tarde. No consideres esto un método de seguridad ni nada parecido. :)

Parámetros

filename Nombre del archivo a eliminar.

Devoluciones

distinto de cero en caso de éxito, cero en caso de error. Usa PHYSFS_getLastErrorCode() para obtener el error específico.

DESCRIPTION

PhysicsFS keeps track of the last error that happened, and makes it available to you. This is done via two functions: PHYSFS_getLastErrorCode() and PHYSFS_getErrorByCode().

PHYSFS_getLastErrorCode() returns the last error code that occurred in *any* PhysicsFS function. It is a 32-bit unsigned integer. If no error has occurred, it will return 0.

PHYSFS_getErrorByCode() takes an error code (such as the one returned by PHYSFS_getLastErrorCode()) and returns a human-readable string that describes the error. If the code is not recognized, it will return a generic error string.

These two functions are thread-local. They are not shared between threads. This means that calling one will not reset the same thread-specific error state. Calling one will wipe out the other's data. If you need both, call PHYSFS_getLastErrorCode(), then pass that value to PHYSFS_getErrorByCode().

Generally, applications should only concern themselves with whether a given function failed; however, if you require more specifics, you can try this function to glean information, if there's some specific problem you're expecting and plan to handle. But with most things that involve file systems, the best course of action is usually to give up, report the problem to the user, and let them figure out what should be done about it. For that, you might prefer PHYSFS_getErrorByCode() instead.

Enumeration value that represents last reported error.

const char * PHYSFS_getPrefDir (const char * org, const char * app)

Get the user-and-app-specific path where files can be written. Helper function.

Get the "pref dir". This is meant to be where users can write personal files (preferences and save games, etc) that are specific to your application. This directory is unique per user, per application.

(etc.)

Older versions of PhysicsFS offered only PHYSFS_getUserDir() and left you to figure out where the files should go under that tree. This finds the correct location for whatever platform, which not only changes between operating systems, but also versions of the same operating system.

You specify the name of your organization (if it's not a real organization, your name or an Internet domain you own might do) and the name of your application. These should be proper names.

  • Try to use the same org string (including case-sensitivity) for all your applications that use this function.
  • Always use a unique app string for each one, and make sure it never changes for an app once you've decided on it.
  • Unicode characters are legal, as long as it's UTF-8 encoded, but...

Figure out where in the search path a file resides. The file is specified in platform-independent notation. The returned filename will be the element of the search path where the file was found, which may be a directory, or an archive. int PHYSFS_mount(const char *newDir, const char *mountPoint, int appendToPath)

Agregar un archivo o directorio a la ruta de búsqueda. Si es un duplicado, el registro no se añade de nuevo, incluso si la función es exitosa. No puedes agregar el mismo archivo a dos diferentes puntos de montaje: la verificación de duplicados se hace contra el archivo, no contra el punto de montaje.

Al montar un archivo, se lo añade a un sistema de archivos virtual... todos los archivos de todos los archivos montados se interpolan en una sola jerarquía de directorios. Dos archivos montados en el mismo punto (o un archivo con archivos que superponen un punto de montaje) pueden tener archivos superpuestos: en tal caso, el archivo más antiguo en la ruta de búsqueda es seleccionado, y los otros archivos no son accesibles por la aplicación. Esto permite usar los archivos para reemplazar revisiones previas; puedes usar el mecanismo de montaje para colocar archivos en un punto específico en el árbol de archivos y evitar superposiciones; es útil para modulos descargados que pueden trasplantar sobre los datos de aplicación o entre sí, por ejemplo.

El punto de montaje no necesita existir antes de montar, lo que es diferente de lo que se espera de los usuarios familiarizados con el concepto Unix de "montar". Además, más de un archivo puede montarse en el mismo punto de montaje, o los puntos de montaje y contenidos de los archivos pueden superponerse... el mecanismo de interpolación aún funciona.

La especificación de un enlace símbólico hacia un archivo o directorio es permitida aquí, independientemente del estado de PHYSFS_permitSymbolicLinks(). Esta función solo maneja enlaces símbólicos dentro del directorio o archivo montado.

void PHYSFS_permitirEnlacesSimbolicos (int permitir)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y archivos contienen archivos que son solo punteros a otros archivos. En el sistema de archivos físico, abrir un enlace de este tipo abrirá (transparente) el archivo al que apunta.

Por defecto, PhysicsFS verificará si un archivo es realmente un enlace simbólico durante las llamadas open y fallará si lo es. De lo contrario, el enlace podría llevarlo fuera de las rutas de escritura y búsqueda, y comprometer la seguridad.

Si desea asumir ese riesgo, llame a esta función con un parámetro distinto de cero. Tenga en cuenta que esto es más para aislar el lenguaje de scripting de un programa, en caso de que scripts no confiables intenten comprometer el sistema. En términos generales, un usuario podría tener una razón legítima para configurar un enlace simbólico, por lo que a menos que sienta que existe un peligro específico en permitirlo, debería permitirlos.

Los enlaces simbólicos solo se verifican explícitamente cuando se trata con nombres de archivo en notación independiente de la plataforma. Es decir, al configurar sus rutas de búsqueda y escritura, etc., nunca se verifican los enlaces simbólicos.

Tenga en cuenta que PHYSFS_stat() siempre verificará la ruta especificada; si esa ruta es un enlace simbólico, no se seguirá en ningún caso. Si los enlaces simbólicos no están permitidos a través de esta función, PHYSFS_stat() los ignora y trataría la consulta como si la ruta no existiera en absoluto.

El permiso de enlace simbólico se puede habilitar o deshabilitar en cualquier momento después de haber llamado a PHYSFS_init(), y está deshabilitado por defecto.

Parámetros

permitir distinto de cero para permitir enlaces simbólicos, cero para denegar enlaces.

Configura el almacenamiento en búfer para un identificador de archivo PhysicsFS. Define un búfer de E/S para un identificador de archivo. Se asignará un bloque de memoria de (bufsize) bytes y se asociará con (handle).

Las llamadas a PHYSFS_read() extraerán de este búfer hasta que esté vacío, y luego lo rellenarán para más lecturas. Ten en cuenta que los archivos comprimidos, como los archivos ZIP, se descomprimirán mientras se almacenan en búfer, por lo que esto puede ser útil para compensar operaciones intensivas en CPU. Los manejadores de archivos de PhysicsFS no tienen búfer por defecto.

¡Por favor, comprueba el valor de retorno de esta función! Los fallos pueden incluir no poder buscar hacia atrás en un archivo de solo lectura al eliminar el búfer, no poder asignar el búfer y no poder vaciar el búfer al disco, entre otros problemas inesperados.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Haz que un subdirectorio de un archivo sea su directorio raíz. Esto te permite delimitar los archivos accesibles en un archivo específico. Por ejemplo, si tienes x.zip con un archivo en y/z.txt, montado en /a, si llamas a PHYSFS_setRoot("x.zip", "/y"), entonces la llamada a PHYSFS_openRead("/a/z.txt") tendrá éxito.

Puedes cambiar la raíz de un archivo en cualquier momento, alterando el árbol de archivos interpolado (dependiendo de dónde cambien las rutas, un archivo diferente puede estar proporcionando varios archivos). Si estableces la raíz a NULL o "/", el archivo se tratará como si no se hubiera establecido ninguna raíz especial (como si el archivo se hubiera montado normalmente).

Cambiar la raíz solo afecta a las operaciones futuras en nombres de ruta; un archivo que se abrió desde una ruta que cambió debido a un setRoot no se verá afectado.

Establecer una nueva raíz no se limita a los archivos en la ruta de búsqueda; también puedes establecer una en el directorio de escritura, lo que podría ser útil si tienes archivos abiertos para escritura y, por lo tanto, no puedes cambiar el directorio de escritura en este momento.

No es un error establecer un subdirectorio que no existe como raíz de un archivo; sin embargo, no se verán archivos en este caso. Si los directorios faltantes terminan creándose (un mkdir al sistema de archivos físico, etc.) entonces esto se reflejará en el árbol interpolado.

Parámetros

archive directorio/archivo sobre el que cambiar la raíz.
subdir nuevo subdirectorio para convertir en la raíz de este archivo.

Devuelve

distinto de cero en caso de éxito, cero en caso de fallo. Usa PHYSFS_getLastErrorCode() para obtener el error específico.

int PHYSFS_setSaneConfig (const char * organization, const char * appName, const char * archiveExt, int includeCdRoms, int archivesFirst)

Configura rutas predeterminadas y sensatas. Función de ayuda.

El directorio de escritura se establecerá en el directorio de preferencias devuelto por

PHYSFS_getPrefDir(organization, appName)

, que se crea si no existe.

Lo anterior es suficiente para asegurar que el directorio de configuración de tu programa esté separado de otras distracciones y sea independiente de la plataforma.

La ruta de búsqueda será:

  • El Directorio de Escritura (creado si no existe)
  • El Directorio Base (PHYSFS_getBaseDir())
  • Todos los directorios de CD-ROM encontrados (opcionalmente)

Estos directorios se buscan para encontrar archivos que terminen con la extensión (archiveExt), los cuales, si son archivos válidos y compatibles, también se añadirán a la ruta de búsqueda. Si especificaste "PKG" para (archiveExt), y hay un archivo llamado data.PKG en el directorio base, se comprobará. Los archivos pueden añadirse o anteponerse a la ruta de búsqueda en orden alfabético, independientemente de los directorios en los que se encontraron. Todos los archivos se montan en la raíz del sistema de archivos virtual ("/").

Todo esto se puede lograr desde la aplicación, pero esto simplemente lo hace todo por ti. Siéntete libre de añadir más cosas a la ruta de búsqueda manualmente también.

Parámetros

organization Nombre de tu empresa/grupo/etc. para ser usado como nombre de directorio, así que mantenlo corto y sencillo.
appName Nombre específico del programa para separarlo de otros programas que usan PhysicsFS.
archiveExt Extensión de archivo utilizada por tu programa para especificar un archivo. Por ejemplo, Quake 3 usa "pk3", aunque solo sean archivos zip. Especifica NULL para no buscar archivos automáticamente. No especifiques el carácter '.'; si quieres buscar archivos ZIP, especifica "ZIP" y no ".ZIP" ... la búsqueda de archivos no distingue entre mayúsculas y minúsculas.
includeCdRoms Distinto de cero para incluir CD-ROMs en la ruta de búsqueda, y (si (archiveExt) != NULL) buscarlos para encontrar archivos. Esto puede causar una cantidad significativa de bloqueo mientras se accede a los discos, y si no hay discos en la unidad (o incluso no montados en sistemas Unix), entonces puede que no estén disponibles de todos modos. Es posible que desees especificar cero y manejar la configuración del disco tú mismo.
archivesFirst Distinto de cero para anteponer los archivos a la ruta de búsqueda. Cero para añadirlos. Ignorado si !(archiveExt).

Devuelve

distinto de cero en caso de éxito, cero en caso de error. Usa PHYSFS_getLastErrorCode() para obtener el error específico.

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convierte una cadena UTF-8 a una cadena Latin1. Las cadenas Latin1 son de 8 bits por carácter: una codificación popular de "ASCII alto".

Para garantizar que el búfer de destino sea lo suficientemente grande para la conversión, por favor, asigne un búfer que sea el doble del tamaño del búfer de origen. UTF-8 expande los puntos de código latin1 mayores a 127 de 1 a 2 bytes, por lo que la cadena puede crecer en algunos casos.

Las cadenas que no quepan en el búfer de destino se truncarán, pero siempre estarán terminadas en nulo y nunca tendrán una secuencia UTF-8 incompleta al final. Si la longitud del búfer es 0, esta función no hace nada.

Tenga en cuenta que no proporcionamos un convertidor de UTF-8 a Latin1, ya que Latin1 no puede expresar la mayoría de los puntos de código Unicode. Es una codificación heredada; deberías estar convirtiendo lejos de ella en todo momento.

Parámetros

src Cadena de origen terminada en nulo en formato Latin1.
dst Búfer para almacenar la cadena UTF-8 convertida.
len Tamaño, en bytes, del búfer de destino.

Al igual que stricmp, esto espera que ambas cadenas estén terminadas en NULL.

Warning

void PHYSFS_utf8ToUtf16 (const char * src, PHYSFS_uint16 * dst, PHYSFS_uint64 len)

Convert a UTF-8 string to a UTF-16 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UTF-16 strings are 16-bits per character (except some chars, which are 32-bits): TCHAR on Windows, when building with Unicode support. Modern Windows releases use UTF-16. Windows releases before 2000 used TCHAR, but only handled UCS-2. UTF-16 is UCS-2, except for the characters that are 4 bytes, which aren't representable in UCS-2 at all anyhow. If you aren't sure, you should be using UTF-16 at this point on Windows.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 uses from one to four bytes per character, but UTF-16 always uses two to four, so an entirely low-ASCII string will double in size! The UTF-16 characters that would take four bytes also take four bytes in UTF-8, so you don't need to allocate 4x the space just in case: double will do.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-16 surrogate pair at the end. If the buffer length is 0, this function does nothing.
