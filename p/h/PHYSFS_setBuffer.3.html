int PHYSFS_setBuffer (PHYSFS_File *handle, PHYSFS_uint64 bufsize)

Establece el tamaño del búfer para un manejador de archivo PhysicsFS.

Descripción

Llama a PHYSFS_setBuffer para establecer el tamaño del búfer para el archivo especificado por handle en bufsize bytes.

Si bufsize es 0, se desactiva el almacenamiento en búfer. Si es mayor que 0, se asigna memoria para el búfer, se vacía cualquier contenido existente y se establece el nuevo tamaño.

Si se produce un error durante la asignación de memoria o la operación de E/S, la función devuelve 0. Si tiene éxito, devuelve 1.

Para archivos abiertos para lectura, el búfer solo puede ser para lectura. Para archivos abiertos para escritura o anexión, el búfer solo puede ser para escritura. No se puede establecer un búfer para archivos abiertos en modo de lectura/escritura.

Valor de Retorno

Devuelve 1 si tiene éxito, 0 si falla.

Firma de función para callbacks que enumeran archivos.

Advertencia

A partir de PhysicsFS 2.1, usa PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; te da más control sobre el proceso.

Estos se utilizan para informar una lista de entradas de directorio a un llamador original, un archivo/directorio/enlace simbólico por callback. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de ninguna cadena.

int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

"Plegar" un punto de código Unicode a un equivalente en minúsculas. (Esto es para uso limitado y hardcore. Si no ves inmediatamente una necesidad para ello, probablemente puedas ignorarlo para siempre.)

Esto convertirá un punto de código Unicode a su equivalente en minúsculas. Los puntos de código no válidos y los puntos de código sin un equivalente en minúsculas se devolverán sin convertir.

¡Ten en cuenta que podrías obtener varios puntos de código en respuesta! El Eszett alemán, por ejemplo, se plegará en dos puntos de código 's' en minúsculas. La teoría es que si pliegas dos cadenas, una con un Eszett y otra con "SS", coincidirán.

int PHYSFS_deinit (void )

Desinicializar la biblioteca PhysicsFS. Esto cierra todos los archivos abiertos a través de PhysicsFS, vacía las rutas de búsqueda/escritura, libera memoria e invalida todos tus manejadores de archivos.

Ten en cuenta que esta llamada puede FALLAR si hay un archivo abierto para escritura que se niega a cerrarse (por ejemplo, el sistema operativo subyacente estaba almacenando en búfer escrituras en un sistema de archivos de red, y el servidor de archivos ha fallado, o ha fallado un disco duro, etc.). Generalmente es mejor cerrar todos los manejadores de escritura usted mismo antes de llamar a esta función, para poder manejar de forma elegante un fallo específico.

Una vez desinicializado con éxito, se puede llamar a PHYSFS_init() de nuevo para reiniciar el subsistema. Todos los estados predeterminados de la API se restauran en este punto, con la excepción de cualquier asignador personalizado que hayas especificado, que sobrevive entre inicializaciones.

Devuelve

distinto de cero si tiene éxito, cero si hay un error. Los detalles del error se pueden obtener de PHYSFS_getLastError(). Si falla, el estado de PhysFS no está definido y probablemente muy dañado.

int PHYSFS_getLastErrorCode (void )

Get the last error code that was reported.

Some PhysicsFS functions may fail. When this happens, they will return a specific value indicating failure. The last error code is stored in a thread-local storage slot, so this function will always report the error for the current thread, even if other threads are also experiencing errors.

The error codes are defined in physfs.h. You can pass the value returned by this function to PHYSFS_getErrorByCode() to get a human-readable string representation of the error.

Note that some functions, like PHYSFS_init() and PHYSFS_setErrorCallbacks(), do not set an error code. Also, calling a function that reports an error might overwrite the error state set by a previous call. This means you should query the error code immediately after a function returns an error code, and before calling any other PhysicsFS function.

It's important to note that the thread-local error state is reset by certain functions. For example, PHYSFS_close() will clear the error state. This means that if you call PHYSFS_close(), and then later call PHYSFS_getLastErrorCode(), you may get an unexpected error code, because the call to PHYSFS_close() reset the state. This is especially problematic if you have multiple threads calling PhysicsFS functions; if one thread calls a function that resets the error state, it will affect the error state for all other threads, even if they don't call the same function. This means that if you need to track errors across multiple threads, you should capture the error code immediately after a function fails, and store it in your own data structures. If you need both the error code and a human-readable string, you should call PHYSFS_getLastErrorCode() and then pass the returned code to PHYSFS_getErrorByCode().

Applications should generally only be concerned with whether a function failed. However, if you require more specifics, you can use this function to obtain more detailed information. This is useful if you are expecting a specific type of error and want to handle it differently. In most cases involving file systems, the best course of action is to give up, report the problem to the user, and let them decide what to do. For such cases, you might prefer to use PHYSFS_getErrorByCode().

Returns

An enumeration value representing the last reported error.

This function determines the appropriate location in the native filesystem, creates the directory if necessary, and returns a string in platform-dependent notation, suitable for passing to PHYSFS_setWriteDir().

On Windows, this might look like: "C:\\Users\\bob\\AppData\\Roaming\\My Company\\My Program Name"

On Linux, this might look like: "/home/bob/.local/share/My Program Name"

On Mac OS X, this might look like: "/Users/bob/Library/Application Support/My Program Name"

(And so on.)

You should probably use the pref dir for your write directory, and also place it near the beginning of your search path. Older versions of PhysicsFS offered only PHYSFS_getUserDir() and left you to figure out where the files should go under that tree. This function finds the correct location for any platform, which not only varies between operating systems but also between versions of the same operating system.

You specify the name of your organization (if it's not a real organization, your name or an Internet domain you own might suffice) and the name of your application. These should be proper names.

Both the (org) and (app) strings may become part of a directory name, so please follow these rules:

  • Try to use the same org string (including case sensitivity) for all your applications that use this function.
  • Always use a unique app string for each application, and ensure it never changes once decided upon.
  • Unicode characters are legal, as long as they are UTF-8 encoded, but...
  • ...only use letters, numbers, and spaces. Avoid punctuation like "Game Name 2: Bad Guy's Revenge!"... "Game Name 2" is sufficient.

The pointer returned by this function remains valid until you call this function again, or call PHYSFS_deinit(). This is not necessarily a fast call, so you should call it once at startup and copy the string if you need it.

You should assume that the path returned by this function is the only safe place to write files (and that PHYSFS_getUserDir() and PHYSFS_getBaseDir(), while they might be writable or even parents of the returned path, are not where you should be writing things).

The returned filename will be the element of the search path where the file was found, which may be a directory or an archive. PHYSFS_mount

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mount points: duplicate checking is done against the archive and not the mount point.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierarchical file tree. Two archives mounted at the same place (or an archive with files overlapping another mount point) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mount point does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mount point, or mount points and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

int PHYSFS_mountFile (PHYSFS_File * file, const char * newDir, const char * mountPoint, int appendToPath)

Agrega un archivo, contenido en un manejador PHYSFS_File, a la ruta de búsqueda.

Advertencia

A menos que tenga alguna necesidad especial de bajo nivel, debería usar PHYSFS_mount() en lugar de esto.

¡Los archivos dentro de archivos pueden ser muy lentos! Mientras que un PHYSFS_File puede buscar incluso cuando los datos están comprimidos, puede hacerlo rebobinando al principio y descomprimiendo todo antes del punto de búsqueda. El uso normal de archivos puede realizar muchas búsquedas entre bastidores. Como tal, puede encontrar que el uso normal de archivos es extremadamente doloroso si se monta de esta manera. Planifique en consecuencia: si, por ejemplo, tiene un archivo .zip autoextraíble y desea montar algo en él, comprima el contenido del archivo interno y asegúrese de que el archivo .zip externo no comprima también el archivo interno.

Esta función opera igual que PHYSFS_mount(), pero toma un manejador PHYSFS_File en lugar de una ruta de archivo. Este manejador contiene todos los datos del archivo y se utiliza en lugar de un archivo real en el sistema de archivos físico. El PHYSFS_File puede estar respaldado por un archivo real en el sistema de archivos físico, pero no es necesariamente así. El uso más popular para esto es probablemente montar archivos almacenados dentro de otros archivos.

(newDir) debe ser una cadena única para identificar este archivo. Se utiliza para optimizar la selección del archivador (si lo nombra XXXXX.zip, podríamos intentar primero el archivador ZIP, por ejemplo, o elegir directamente un archivador que solo pueda confiar en que los datos son válidos por la extensión del nombre de archivo). No necesita referirse a un archivo real en absoluto. Si la extensión del nombre de archivo no es útil, el sistema intentará con todos los archivadores hasta que uno funcione o ninguno de ellos lo haga. Este nombre de archivo debe ser único, ya que el sistema no le permitirá tener dos archivos con el mismo nombre.

(file) debe permanecer hasta que el archivo se desmonte. Cuando el archivo se desmonte, el sistema llamará a PHYSFS_close(file). Si necesita que este manejador sobreviva, tendrá que envolverlo en un PHYSFS_Io y usar PHYSFS_mountIo() en su lugar.

Si esta función falla, no se llama a PHYSFS_close(file).

void PHYSFS_permitSymbolicLinks (int allow)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y archivos contienen archivos que son solo punteros a otros archivos. En el sistema de archivos físico, abrir un enlace de este tipo abrirá (transparentemente) el archivo al que apunta.

Por defecto, PhysicsFS verificará si un archivo es realmente un enlace simbólico durante las llamadas open y fallará si lo es. De lo contrario, el enlace podría sacarte de las rutas de escritura y búsqueda, y comprometer la seguridad.

Si deseas asumir ese riesgo, llama a esta función con un parámetro distinto de cero. Ten en cuenta que esto es más para aislar el lenguaje de scripting de un programa, en caso de que scripts no confiables intenten comprometer el sistema. En términos generales, un usuario podría tener una razón legítima para configurar un enlace simbólico, por lo que a menos que sientas que hay un peligro específico en permitirlos, deberías permitirlos.

Los enlaces simbólicos solo se verifican explícitamente cuando se tratan nombres de archivo en notación independiente de la plataforma. Es decir, al configurar tus rutas de búsqueda y escritura, etc., nunca se verifican los enlaces simbólicos.

Ten en cuenta que PHYSFS_stat() siempre verificará la ruta especificada; si esa ruta es un enlace simbólico, no se seguirá en ningún caso. Si los enlaces simbólicos no están permitidos a través de esta función, PHYSFS_stat() los ignora y trataría la consulta como si la ruta no existiera en absoluto.

El permiso de enlace simbólico se puede habilitar o deshabilitar en cualquier momento después de haber llamado a PHYSFS_init(), y está deshabilitado por defecto.

Advertencia

Esto es para usuarios avanzados y experimentados. No lo necesitas a menos que sepas realmente lo que estás haciendo. La mayoría de las aplicaciones no lo necesitarán.

Una vez que esta función retorna con éxito, PhysicsFS podrá dar soporte a archivos de este tipo hasta que desregistres el archivador de nuevo.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Make a subdirectory of an archive its root directory. This lets you narrow down the accessible files in a specific archive. For example, if you have x.zip with a file in y/z.txt, mounted to /a, if you call PHYSFS_setRoot("x.zip", "/y"), then the call PHYSFS_openRead("/a/z.txt") will succeed.

You can change an archive's root at any time, altering the interpolated file tree (depending on where paths shift, a different archive may be providing various files). If you set the root to NULL or "/", the archive will be treated as if no special root was set (as if the archive was just mounted normally).

Changing the root only affects future operations on pathnames; a file that was opened from a path that changed due to a setRoot will not be affected.

Setting a new root is not limited to archives in the search path; you may set one on the write dir, too, which might be useful if you have files open for write and thus can't change the write dir at the moment.

It is not an error to set a subdirectory that does not exist to be the root of an archive; however, no files will be visible in this case. If the missing directories end up getting created (a mkdir to the physical filesystem, etc) then this will be reflected in the interpolated tree.

Parameters

archive dir/archive on which to change root.
subdir new subdirectory to make the root of this archive.

Returns

nonzero on success, zero on failure. Use PHYSFS_getLastErrorCode() to obtain the specific error.

int PHYSFS_setSaneConfig (const char * organization, const char * appName, const char * archiveExt, int includeCdRoms, int archivesFirst)

Set up sane, default paths. Helper function.

The write dir will be set to the pref dir returned by

PHYSFS_getPrefDir(organization, appName)

, which is created if it doesn't exist.

The above is sufficient to make sure your program's configuration directory is separated from other clutter, and platform-independent.

The search path will be:

  • The Write Dir (created if it doesn't exist)
  • The Base Dir (PHYSFS_getBaseDir())
  • All found CD-ROM dirs (optionally)

These directories are then searched for files ending with the extension (archiveExt), which, if they are valid and supported archives, will also be added to the search path. If you specified "PKG" for (archiveExt), and there's a file named data.PKG in the base dir, it'll be checked. Archives can either be appended or prepended to the search path in alphabetical order, regardless of which directories they were found in. All archives are mounted in the root of the virtual file system ("/").

All of this can be accomplished from the application, but this just does it all for you. Feel free to add more to the search path manually, too.

Parameters

organization Name of your company/group/etc to be used as a dirname, so keep it small, and no-frills.
appName Program-specific name of your program, to separate it from other programs using PhysicsFS.
archiveExt File extension used by your program to specify an archive. For example, Quake 3 uses "pk3", even though they are just zipfiles. Specify NULL to not dig out archives automatically. Do not specify the '.' char; If you want to look for ZIP files, specify "ZIP" and not ".ZIP" ... the archive search is case-insensitive.
includeCdRoms Non-zero to include CD-ROMs in the search path, and (if (archiveExt) != NULL) search them for archives. This may cause a significant amount of blocking while discs are accessed, and if there are no discs in the drive (or even not mounted on Unix systems), then they may not be made available anyhow. You may want to specify zero and handle the disc setup yourself.
archivesFirst Non-zero to prepend the archives to the search path. Zero to append them. Ignored if !(archiveExt).

Returns

nonzero on success, zero on error. Use PHYSFS_getLastErrorCode() to obtain the specific error.

void PHYSFS_utf8ToUcs4 (const char * src, PHYSFS_uint32 * dst, PHYSFS_uint64 len)

Convert a UTF-8 string to a UCS-4 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UCS-4 strings are 32-bits per character. The only real reason to use this function is if you are building for a platform that does not use UTF-16 (like old BeOS or macOS). UTF-16 is preferred on modern Windows systems.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 uses from one to four bytes per character, but UCS-4 always uses four, so an entirely low-ASCII string will more than double in size.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UCS-4 sequence at the end. If the buffer length is 0, this function does nothing.

Parameters

src Null-terminated source string in UTF-8 format.
dst Buffer to store converted UCS-4 string.
len Size, in bytes, of destination buffer.

int PHYSFS_writeULE64 (PHYSFS_File * archivo, PHYSFS_uint64 val)

Convierte y escribe un valor sin signo de 64 bits en formato littleendian. Función de conveniencia. Convierte un valor sin signo de 64 bits del orden de bytes nativo de la plataforma a littleendian y lo escribe en un archivo.

Parámetros

archivo Manejador de archivo PhysicsFS al que se escribirá.
val Valor a convertir y escribir.

Retorna

cero en caso de fallo, distinto de cero en caso de éxito. En caso de fallo, puedes averiguar qué salió mal con PHYSFS_getLastErrorCode().
