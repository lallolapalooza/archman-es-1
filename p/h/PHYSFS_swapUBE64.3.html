typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Firma de función para callbacks que enumeran archivos.

Advertencia

A partir de PhysicsFS 2.1, use PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; le da más control sobre el proceso.

Estos se utilizan para informar una lista de entradas de directorio a un llamador original, un archivo/directorio/enlace simbólico por callback. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de ninguna cadena.

Estos callbacks se utilizan, a partir de PhysicsFS 1.1, como una alternativa a las funciones que devolverían listas que necesitan ser limpiadas con PHYSFS_freeList(). El callback significa que la biblioteca no necesita asignar una lista completa y todas las cadenas por adelantado.

Tenga en cuenta que el orden prometido de los datos en las versiones de lista no es necesariamente el mismo en las versiones de callback. Consulte la documentación de APIs específicas, pero es posible que las cadenas no estén ordenadas como espera y que reciba cadenas duplicadas.

Parámetros

data Puntero a datos definido por el usuario, pasado desde la API que finalmente llamó al callback.
origdir Una cadena que contiene la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio sobre el que solicitó la enumeración, pasado en el callback para su conveniencia.
fname El nombre del archivo que se está enumerando. Puede que no esté en orden alfabético en comparación con otros callbacks que se hayan disparado, y no contendrá la ruta completa. Puede recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

enum PHYSFS_ErrorCode

Valores que representan causas específicas de fallo. La mayoría de las veces, solo debería preocuparse por si una operación dada falló o no, pero puede haber ocasiones en las que planee manejar un caso de fallo específico con gracia, por lo que proporcionamos códigos de error específicos.

La mayoría de estos errores son un poco vagos, y la mayoría no son cosas que pueda arreglar... si hay un error de permiso, por ejemplo, todo lo que realmente puede hacer es pasar esa información al usuario y dejar que él descubra cómo manejarlo. En la mayoría de estos casos, su programa solo debería preocuparse de que no logró alcanzar sus objetivos, y no preocuparse específicamente por qué.

A directory must be empty before this call can delete it.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtiene una lista de archivos de un directorio de la ruta de búsqueda, utilizando una función de devolución de llamada definida por la aplicación, con informes de errores. Internamente, PHYSFS_enumerateFiles() simplemente llama a esta función y luego construye una lista antes de devolverla a la aplicación, por lo que la funcionalidad es idéntica, excepto por cómo se representa la información a la aplicación.

A diferencia de PHYSFS_enumerateFiles(), esta función no devuelve una matriz. Más bien, llama a una función especificada por la aplicación una vez por cada elemento de la ruta de búsqueda:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Tenemos [%s] en [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // dame más datos, por favor.
}
// ...
PHYSFS_enumerate("/alguna/ruta", printDir, NULL);

No se garantiza que los elementos enviados a la función de devolución de llamada estén en ningún orden particular. No se realiza ninguna ordenación en este nivel, y si la necesita, probablemente debería usar PHYSFS_enumerateFiles() en su lugar, que garantiza la ordenación alfabética. Esta forma informa lo que se descubre en cada archivo antes de pasar al siguiente. Incluso dentro de un archivo, no podemos garantizar en qué orden descubrirá los datos. Cualquier ordenación que encuentre en estas devoluciones de llamada es pura suerte. No confíe en ella. Dado que recorre toda la lista de archivos, puede recibir nombres de archivo duplicados.

Esta API y las propias funciones de devolución de llamada son capaces de informar errores. Antes de esta API, las funciones de devolución de llamada tenían que aceptar cada elemento enumerado, incluso si solo buscaban algo específico y querían detenerse después, o si tenían un error grave y no podían alertar a nadie. Además, si PhysicsFS en sí tenía un problema (error de disco o similar), no podía informarlo a la aplicación que lo llamaba, solo tendría que omitir elementos o dejar de enumerar directamente, y el llamador no sabría que había perdido algunos datos en el camino.

Ahora el llamador puede estar seguro de que ha obtenido un conjunto completo de datos, y su función de devolución de llamada tiene control si desea que la enumeración se detenga anticipadamente. Consulte la documentación de PHYSFS_EnumerateCallback para obtener detalles sobre cómo debe comportarse su función de devolución de llamada.

d Datos definidos por la aplicación pasados a la función de devolución de llamada. Puede ser NULL.

Obtiene el último código de error para el hilo actual.

PhysicsFS rastrea los códigos de error por hilo, para que no se pisen unos a otros. Por ejemplo, si llama a PHYSFS_openRead() y luego a PHYSFS_read(), y ambos fallan, solo el error de PHYSFS_read() se registrará en el hilo actual. Si llama a PHYSFS_getLastErrorCode() dos veces seguidas, obtendrá el mismo estado de error específico del hilo. Llamar a uno borrará los datos del otro. Si necesita ambos, llame a PHYSFS_getLastErrorCode() y luego pase ese valor a PHYSFS_getErrorByCode().

En general, las aplicaciones solo deberían preocuparse de si una determinada función falló; sin embargo, si necesita más detalles, puede intentar usar esta función para obtener información, si hay algún problema específico que espera y planea manejar. Pero con la mayoría de las cosas que involucran sistemas de archivos, el mejor curso de acción suele ser rendirse, informar el problema al usuario y dejar que él decida qué hacer al respecto. Para eso, podría preferir PHYSFS_getErrorByCode() en su lugar.

Retorna

Valor de enumeración que representa el último error reportado.

const char * PHYSFS_getPrefDir (const char * org, const char * app)

Obtiene la ruta específica del usuario y la aplicación donde se pueden escribir archivos. Función auxiliar.

Obtiene el "directorio de preferencias". Se pretende que sea donde los usuarios puedan escribir archivos personales (preferencias y partidas guardadas, etc.) que sean específicos de su aplicación. Este directorio es único por usuario y por aplicación.

Esta función decidirá la ubicación apropiada en el sistema de archivos nativo, creará el directorio si es necesario y devolverá una cadena en notación dependiente de la plataforma, adecuada para pasar a PHYSFS_setWriteDir().

En Windows, podría verse así: "C:\\Users\\bob\\AppData\\Roaming\\Mi Compañía\\Mi Nombre de Programa"

En Linux, podría verse así: "/home/bob/.local/share/Mi Nombre de Programa"

En Mac OS X, podría verse así: "/Users/bob/Library/Application Support/Mi Nombre de Programa"

(etc.)

Probablemente debería usar el directorio de preferencias para su directorio de escritura, y también ponerlo cerca del principio de su ruta de búsqueda. Las versiones anteriores de PhysicsFS ofrecían solo PHYSFS_getUserDir() y le dejaban descubrir dónde debían ir los archivos dentro de ese árbol. Esto encuentra la ubicación correcta para cualquier plataforma, que no solo cambia entre sistemas operativos, sino también entre versiones del mismo sistema operativo.

Especifica el nombre de su organización (si no es una organización real, su nombre o un dominio de Internet que posea podría servir) y el nombre de su aplicación. Estos deben ser nombres propios.

Tanto las cadenas (org) como (app) pueden convertirse en parte de un nombre de directorio, así que siga estas reglas:

  • Intente usar la misma cadena de organización (incluida la distinción entre mayúsculas y minúsculas) para todas sus aplicaciones que utilicen esta función.
  • Siempre use una cadena de aplicación única para cada una, y asegúrese de que nunca cambie para una aplicación una vez que haya decidido sobre ella.
  • Los caracteres Unicode son legales, siempre que estén codificados en UTF-8, pero...
  • ... solo use letras, números y espacios. Evite la puntuación como "Nombre del Juego 2: La Venganza del Malo" ... "Nombre del Juego 2" es suficiente.

El puntero devuelto por esta función permanece válido hasta que vuelva a llamar a esta función, o llame a PHYSFS_deinit(). Sin embargo, esta no es necesariamente una llamada rápida, por lo que debería llamar a esto una vez al inicio y copiar la cadena si la necesita.

Debe asumir que la ruta devuelta por esta función es el único lugar seguro para escribir archivos (y que PHYSFS_getUserDir() y PHYSFS_getBaseDir(), aunque podrían ser escribibles, o incluso padres de la ruta devuelta, no son donde debería escribir cosas).

org El nombre de su organización.
app El nombre de su aplicación.

Cadena de SOLO LECTURA del directorio de usuario en notación dependiente de la plataforma. NULL si hay un problema (la creación del directorio falló, etc.).

const char * PHYSFS_getRealDir (const char * filename)

Descubre dónde reside un archivo en la ruta de búsqueda. El archivo se especifica en notación independiente de la plataforma. El nombre del archivo devuelto será el elemento de la ruta de búsqueda donde se encontró el archivo, que puede ser un directorio o un archivo. Incluso si hay múltiples coincidencias en diferentes partes de la ruta de búsqueda, solo se utiliza la primera que se encuentra, al igual que al abrir un archivo.

Si alguna parte de una coincidencia es un enlace simbólico, y no ha permitido explícitamente los enlaces simbólicos, se ignorará y la búsqueda de una coincidencia continuará.

Si especifica un directorio falso que solo existe como punto de montaje, se asociará con el primer archivo montado allí, aunque ese directorio no esté necesariamente contenido en un archivo real.

Esto devolverá NULL si no hay un directorio real asociado con (filename). Específicamente, PHYSFS_mountIo(), PHYSFS_mountMemory() y PHYSFS_mountHandle() devolverán NULL incluso si el nombre del archivo se encuentra en la ruta de búsqueda. Planifique en consecuencia.

Parámetros

filename archivo a buscar.

Cadena de SOLO LECTURA del elemento de la ruta de búsqueda que contiene el archivo en cuestión. NULL si no se encuentra.

int PHYSFS_mount(const char *newDir, const char *mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

Parameters

newDir directory or archive to add to the path, in platform-dependent notation.
mountPoint Location in the interpolated tree that this archive will be "mounted", in platform-independent notation. NULL or "" is equivalent to "/".
appendToPath nonzero to append to search path, zero to prepend.

Returns

nonzero if added to path, zero on failure (bogus archive, dir missing, etc). Use PHYSFS_getLastErrorCode() to obtain the specific error.

int PHYSFS_mount(const char *newDir, const char *mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

Parameters

newDir directory or archive to add to the path, in platform-dependent notation.
mountPoint Location in the interpolated tree that this archive will be "mounted", in platform-independent notation. NULL or "" is equivalent to "/".
appendToPath nonzero to append to search path, zero to prepend.

Returns

nonzero if added to path, zero on failure (bogus archive, dir missing, etc). Use PHYSFS_getLastErrorCode() to obtain the specific error.

Initialize the PhysicsFS library. This must be called before any other PhysicsFS function.

This should be called prior to any attempts to change your process's current working directory.

Warning

On Android, argv0 should be a non-NULL pointer to a PHYSFS_AndroidInit struct. This struct must hold a valid JNIEnv * and a JNI jobject of a Context (either the application context or the current Activity is fine). Both are cast to a void * so we don't need jni.h included wherever physfs.h is. PhysicsFS uses these objects to query some system details. PhysicsFS does not hold a reference to the JNIEnv or Context past the call to PHYSFS_init(). If you pass a NULL here, PHYSFS_init can still succeed, but PHYSFS_getBaseDir() and PHYSFS_getPrefDir() will be incorrect.

Parameters

argv0 the argv[0] string passed to your program's mainline. This may be NULL on most platforms (such as ones without a standard main() function), but you should always try to pass something in here. Many Unix-like systems need to pass argv[0] from main() in here. See warning about Android, too!

nonzero on success, zero on error. Specifics of the error can be gleaned from PHYSFS_getLastError().

int PHYSFS_mount(const char *newDir, const char *mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

Parameters

newDir directory or archive to add to the path, in platform-dependent notation.
mountPoint Location in the interpolated tree that this archive will be "mounted", in platform-independent notation. NULL or "" is equivalent to "/".
appendToPath nonzero to append to search path, zero to prepend.

Returns

nonzero if added to path, zero on failure (bogus archive, dir missing, etc). Use PHYSFS_getLastErrorCode() to obtain the specific error.

mountPoint Location in the interpolated tree that this archive will be "mounted", in platform-independent notation. NULL or "" is equivalent to "/".
appendToPath nonzero to append to search path, zero to prepend.

int PHYSFS_mount(const char *newDir, const char *mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

Parameters

newDir directory or archive to add to the path, in platform-dependent notation.
mountPoint Location in the interpolated tree that this archive will be "mounted", in platform-independent notation. NULL or "" is equivalent to "/".
appendToPath nonzero to append to search path, zero to prepend.

Returns

nonzero if added to path, zero on failure (bogus archive, dir missing, etc). Use PHYSFS_getLastErrorCode() to obtain the specific error.

int PHYSFS_mountIo (PHYSFS_Io * io, const char * newDir, const char * mountPoint, int appendToPath)

Añade un archivo, construido sobre un PHYSFS_Io, a la ruta de búsqueda.

Advertencia

A menos que tengas alguna necesidad de bajo nivel especial, deberías usar PHYSFS_mount() en su lugar.

Esta función opera exactamente como PHYSFS_mount(), pero toma un PHYSFS_Io en lugar de un camino de directorio. Internamente, PHYSFS_mount() llama a esta función con un PHYSFS_Io basado en el sistema de archivos físico.

(newDir) debe ser una cadena única para identificar este archivo. Se utiliza para optimizar la selección de archivadores (si nombras el archivo XXXXX.zip, podríamos intentar el archivador ZIP, por ejemplo, o elegir directamente un archivador que solo confíe en la extensión del nombre). No necesita referirse a un archivo físico real. Si la extensión del nombre no es útil, el sistema intentará todos los archivadores hasta que uno funcione o ninguno de ellos funcione. Este nombre debe ser único, ya que el sistema no permitirá tener dos archivos con el mismo nombre.

(io) debe permanecer válido hasta que el archivo sea desmontado. Cuando el archivo sea desmontado, el sistema llamará a (io)->destroy(io), lo que te dará la oportunidad de liberar tus recursos.

Si esta función falla, (io)->destroy(io) no se llamará.

Parámetros

void PHYSFS_permitSymbolicLinks (int allow)

Habilita o desactiva la seguridad de enlaces simbólicos. Algunos sistemas de archivos físicos y archivados contienen archivos que son simples referencias a otros archivos. Al abrir un enlace simbólico en un sistema físico, se abrirá de forma transparente el archivo al que se refiere.

Por defecto, PhysicsFS verificará si un archivo es realmente un enlace simbólico durante las llamadas de apertura y fallará si lo es. De lo contrario, el enlace podría llevarte fuera de los caminos de lectura y escritura, comprometiendo la seguridad.

Si quieres asumir ese riesgo, llama a esta función con un valor no cero. Deberás tener en cuenta que esto es más para el sandboxing de un lenguaje de scripting de un programa, en caso de que scripts no confiables intenten comprometer el sistema. Generalmente, un usuario podría tener una razón legítima para establecer un enlace simbólico, así que no deberías desactivarlo, salvo que sientas un peligro específico.

Los enlaces simbólicos solo se verifican cuando se manejan nombres de archivos en notación no independiente de la plataforma. Es decir, cuando estás configurando tus caminos de búsqueda y escritura, etc., los enlaces simbólicos nunca son verificados.

La permisión de enlaces simbólicos puede activarse o desactivarse en cualquier momento después de haber llamado PHYSFS_init(), y está desactivada por defecto.

int PHYSFS_setRoot(const char * archive, const char * subdir)

Make a subdirectory of an archive its root directory. This lets you narrow down the accessible files in a specific archive. For example, if you have x.zip with a file in y/z.txt, mounted to /a, if you call PHYSFS_setRoot("x.zip", "/y"), then the call PHYSFS_openRead("/a/z.txt") will succeed.

You can change an archive's root at any time, altering the interpolated file tree (depending on where paths shift, a different archive may be providing various files). If you set the root to NULL or "/", the archive will be treated as if no special root was set (as if the archive was just mounted normally).

Changing the root only affects future operations on pathnames; a file that was opened from a path that changed due to a setRoot will not be affected.

Setting a new root is not limited to archives in the search path; you may set one on the write dir, too, which might be useful if you have files open for write and thus can't change the write dir at the moment.

It is not an error to set a subdirectory that does not exist to be the root of an archive; however, no files will be visible in this case. If the missing directories end up getting created (a mkdir to the physical filesystem, etc) then this will be reflected in the interpolated tree.

If length is greater than 0x7FFFFFFFFFFFFFFF, this function will immediately fail. For systems without a 64-bit datatype, you are limited to 31 bits (0x7FFFFFFF, or 2147483647 bytes). We trust most things won't need to do multiple gigabytes of i/o in one call anyhow, but why limit things?

Parameters

handle retval from PHYSFS_openWrite() or PHYSFS_openAppend().
buffer buffer of (len) bytes to write to (handle).
len number of bytes being written to (handle).

Returns

number of bytes written. This may be less than (len); in the case of an error, the system may try to write as many bytes as possible, so an incomplete write might occur. PHYSFS_getLastErrorCode() can shed light on the reason this might be < (len). -1 if complete failure.
