Esto es lo mismo que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, excepto que puede devolver un resultado del callback: a saber, si estás buscando algo específico, una vez que lo encuentras, puedes decirle a PhysicsFS que deje de enumerar más. Parámetros

data Puntero de datos definido por el usuario, pasado desde la API que finalmente llamó al callback.
origdir Una cadena que contiene la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio sobre el que solicitaste la enumeración, pasado en el callback para tu conveniencia.
fname El nombre del archivo que se está enumerando. Puede que no esté en orden alfabético en comparación con otros callbacks que se hayan ejecutado, y no contendrá la ruta completa. Puedes recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Firma de función para callbacks que enumeran archivos.

Advertencia

A partir de PhysicsFS 2.1, usa PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; te da más control sobre el proceso.

Estos se utilizan para informar una lista de entradas de directorio a un llamador original, un archivo/directorio/enlace simbólico por callback. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de ninguna cadena.

Estos callbacks se utilizan, a partir de PhysicsFS 1.1, como una alternativa a las funciones que devolverían listas que necesitan ser limpiadas con PHYSFS_freeList(). El callback significa que la biblioteca no necesita asignar una lista completa y todas las cadenas por adelantado.

Ten en cuenta que el orden prometido de los datos en las versiones de lista no es necesariamente así en las versiones de callback. Consulta la documentación de las APIs específicas, pero es posible que las cadenas no estén ordenadas como esperas y podrías obtener cadenas duplicadas.

Parámetros

data Puntero de datos definido por el usuario, pasado desde la API que finalmente llamó al callback.
origdir Una cadena que contiene la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio sobre el que solicitaste la enumeración, pasado en el callback para tu conveniencia.
fname El nombre del archivo que se está enumerando. Puede que no esté en orden alfabético en comparación con otros callbacks que se hayan ejecutado, y no contendrá la ruta completa. Puedes recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

enum PHYSFS_ErrorCode

Valores que representan causas específicas de fallo. La mayoría de las veces, solo deberías preocuparte por si una operación dada falló o no, pero puede haber ocasiones en las que planees manejar un caso de fallo específico con gracia, por lo que proporcionamos códigos de error específicos.

La mayoría de estos errores son un poco vagos, y la mayoría no son cosas que puedas arreglar... si hay un error de permisos, por ejemplo, lo único que realmente puedes hacer es pasar esa información al usuario y dejar que descubra cómo manejarlo. En la mayoría de estos casos, tu programa solo debería preocuparse de que no logró cumplir sus objetivos, y no preocuparse específicamente por qué.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Get a list of files from a directory in the search path, using an application-defined callback, with errors reported. Internally, PHYSFS_enumerateFiles() simply calls this function and then builds a list before returning to the application, so the functionality is identical, but the representation of the information to the application is different.

Unlike PHYSFS_enumerateFiles(), this function does not return an array. Instead, it calls an application-specified function once for each item in the search path:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Items sent to the callback are not necessarily guaranteed in any order. No sorting is done at this level, and if you need that, you should use PHYSFS_enumerateFiles(), which guarantees alphabetical ordering. This form reports what is found in each archive before moving on to the next. Even within one archive, we can't guarantee the order in which data is discovered. Any ordering you find in these callbacks is pure luck. You should not depend on it. As this walks through the entire file listing, you may receive duplicate filenames.

This API and the callbacks themselves can report errors. Before this API, callbacks had to accept every enumerated item, even if they were only looking for a specific item and wanted to stop after finding it, or had a fatal error and couldn't notify anyone. Additionally, if PhysicsFS itself had a problem (disk error or whatever), it couldn't report it to the calling app; it would just move on to the next item or stop enumerating, and the caller wouldn't know that it had missed some data along the way.

Now the caller can be assured that they have received a complete set of data, and their callback has control over whether to stop enumeration early. See the documentation for PHYSFS_EnumerateCallback for details on how your callback should behave.

Parameters

dir Directory, in platform-independent notation, to enumerate.
c Callback function to notify about items in the path.
d Application-defined data that is passed to the callback. Can be NULL.

Returns

Non-zero on success, zero on failure. Use PHYSFS_getLastErrorCode() to get the specific error. If the callback returns PHYSFS_ENUM_STOP, this is considered success. Callbacks that return PHYSFS_ENUM_ERROR will cause this function to return zero and set the error code to PHYSFS_ERR_APP_CALLBACK.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Añade un archivo o directorio a la ruta de búsqueda. Si es un duplicado, el registro no se agrega de nuevo, incluso aunque la función éxitome. No puedes añadir el mismo archivo a dos diferentes montajes: la verificación de duplicados se hace contra el archivo, no contra el montaje.

Cuando montas un archivo, se añade a un sistema de archivos virtual... todos los archivos de todos los archivos montados se interpolan en una sola arboléctica de directorios. Dos archivos montados en el mismo lugar (o un archivo con archivos que superponen un montaje) pueden tener archivos superpuestos: en tal caso, el archivo más antiguo en la ruta de búsqueda se selecciona, y los otros archivos son inaccesibles para el aplicativo. Esto permite usar los archivos para reemplazar revisiones anteriores; puedes usar el mecanismo de montaje para colocar archivos en un punto específico en el árbol de archivos y evitar superposiciones; esto es útil para mods descargados que puedan sobreescalar los datos de aplicación o entre sí, por ejemplo.

El punto de montaje no necesita existir antes de montar, lo cual es diferente de lo que se espera en el concepto Unix de "montar" para usuarios familiarizados. Además, más de un archivo puede montarse en el mismo punto de montaje, o los puntos de montaje y contenido de los archivos pueden superponerse... la mecánica de interpolación sigue siendo funcional.

Se permite especificar un enlace simbólico a un archivo o directorio, independientemente del estado de PHYSFS_permitSymbolicLinks(). Esta función solo maneja enlaces simbólicos dentro del directorio o archivo montado.

appendToPath no cero para append a la ruta de búsqueda, cero para prepended.

void PHYSFS_permitSymbolicLinks (int allow)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y archivos contienen archivos que son solo punteros a otros archivos. En el sistema de archivos físico, abrir dicho enlace abrirá (transparenemente) el archivo al que apunta.

Por defecto, PhysicsFS comprobará si un archivo es realmente un enlace simbólico durante las llamadas a open y fallará si lo es. De lo contrario, el enlace podría sacarte de las rutas de escritura y búsqueda, y comprometer la seguridad.

Si deseas asumir ese riesgo, llama a esta función con un parámetro distinto de cero. Ten en cuenta que esto es más para aislar el lenguaje de scripting de un programa, en caso de que scripts no confiables intenten comprometer el sistema. En general, un usuario podría tener una razón legítima para configurar un enlace simbólico, por lo que a menos que sientas que hay un peligro específico en permitirlos, deberías permitirlos.

Los enlaces simbólicos solo se comprueban explícitamente cuando se trata con nombres de archivo en notación independiente de la plataforma. Es decir, al configurar tus rutas de búsqueda y escritura, etc., los enlaces simbólicos nunca se comprueban.

Ten en cuenta que PHYSFS_stat() siempre comprobará la ruta especificada; si esa ruta es un enlace simbólico, no se seguirá en ningún caso. Si los enlaces simbólicos no están permitidos a través de esta función, PHYSFS_stat() los ignora y trataría la consulta como si la ruta no existiera en absoluto.

El permiso de enlace simbólico se puede habilitar o deshabilitar en cualquier momento después de haber llamado a PHYSFS_init(), y está deshabilitado por defecto.

Parámetros

int PHYSFS_setRoot (const char * archive, const char * subdir)

Haz que un subdirectorio de un archivo sea su directorio raíz. Esto te permite limitar los archivos accesibles en un archivo específico. Por ejemplo, si tienes x.zip con un archivo en y/z.txt, montado en /a, si llamas a PHYSFS_setRoot("x.zip", "/y"), entonces la llamada PHYSFS_openRead("/a/z.txt") tendrá éxito.

Puedes cambiar la raíz de un archivo en cualquier momento, alterando el árbol de archivos interpolado (dependiendo de dónde cambien las rutas, un archivo diferente puede estar proporcionando varios archivos). int PHYSFS_setSaneConfig (const char * organization, const char * appName, const char * archiveExt, int includeCdRoms, int archivesFirst)

Configura rutas sensatas y por defecto. Función auxiliar.

El directorio de escritura se establecerá en el pref dir devuelto por

PHYSFS_getPrefDir(organization, appName)

, que se crea si no existe.

Lo anterior es suficiente para asegurar que el directorio de configuración de tu programa esté separado de otro desorden, y sea independiente de la plataforma.

La ruta de búsqueda será:

  • El Directorio de Escritura (creado si no existe)
  • El Directorio Base (PHYSFS_getBaseDir())
  • Todos los directorios de CD-ROM encontrados (opcionalmente)

Estos directorios se buscan luego para encontrar archivos que terminen con la extensión (archiveExt), que, si son archivos válidos y compatibles, también se agregarán a la ruta de búsqueda. Si especificaste "PKG" para (archiveExt), y hay un archivo llamado data.PKG en el directorio base, se verificará. Los archivos pueden agregarse o anteponerse a la ruta de búsqueda en orden alfabético, independientemente de los directorios en los que se encontraron. Todos los archivos se montan en la raíz del sistema de archivos virtual ("/")

Todo esto puede ser logrado por la aplicación, pero esto simplemente lo hace todo por ti. Siéntete libre de agregar más a la ruta de búsqueda manualmente también.

Parámetros

organization Nombre de tu empresa/grupo/etc. para ser usado como nombre de directorio, así que mantenlo corto y sin adornos.
appName Nombre específico del programa para tu programa, para separarlo de otros programas que usan PhysicsFS.
archiveExt Extensión de archivo utilizada por tu programa para especificar un archivo. Por ejemplo, Quake 3 usa "pk3", aunque solo son archivos zip. Especifica NULL para no extraer archivos automáticamente. No especifiques el carácter '.'; si quieres buscar archivos ZIP, especifica "ZIP" y no ".ZIP" ... la búsqueda de archivos no distingue entre mayúsculas y minúsculas.
includeCdRoms Distinto de cero para incluir CD-ROMs en la ruta de búsqueda, y (si (archiveExt) != NULL) buscarlos para encontrar archivos. Esto puede causar una cantidad significativa de bloqueo mientras se accede a los discos, y si no hay discos en la unidad (o incluso no montados en sistemas Unix), entonces es posible que no estén disponibles de todos modos. Puede que quieras especificar cero y manejar la configuración del disco tú mismo.
archivesFirst Distinto de cero para anteponer los archivos a la ruta de búsqueda. Cero para agregarlos. Ignorado si !(archiveExt).

distinto de cero en caso de éxito, cero en caso de error. Usa PHYSFS_getLastErrorCode() para obtener el error específico.
