#define PHYSFS_file PHYSFS_File

1.0 API compatibility define. PHYSFS_file is identical to PHYSFS_File. This #define is here for backwards compatibility with the 1.0 API, which had an inconsistent capitalization convention in this case. New code should use PHYSFS_File, as this #define may go away someday.

#define PHYSFS_VERSION( x)

Value:

    (x)->minor = PHYSFS_VER_MINOR; \
    (x)->patch = PHYSFS_VER_PATCH; \
}

Macro to determine PhysicsFS version program was compiled against. This macro fills in a PHYSFS_Version struct

ture con la versión de la biblioteca con la que compiló. Esto se determina por la cabecera que utiliza el compilador. Tenga en cuenta que si vinculó dinámicamente la biblioteca, podría tener una versión ligeramente más nueva o más antigua en tiempo de ejecución. Esa versión se puede determinar con PHYSFS_getLinkedVersion(), que, a diferencia de PHYSFS_VERSION, no es una macro.

PHYSFS_enumerate

Esto es lo mismo que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, excepto que puede devolver un resultado del callback: a saber, si estás buscando algo específico, una vez que lo encuentras, puedes decirle a PhysicsFS que deje de enumerar más. Esto se usa con PHYSFS_enumerate(), que esperemos que hayamos hecho bien esta vez. :)

Parámetros

data Puntero a datos definido por el usuario, pasado desde la API que finalmente llamó al callback.
origdir Una cadena que contiene la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio sobre el que solicitó la enumeración, pasado en el callback para su conveniencia.
fname El nombre del archivo que se está enumerando. Puede que no esté en orden alfabético en comparación con otros callbacks que se han disparado, y no contendrá la ruta completa. Puede recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

Devuelve

Un valor de PHYSFS_EnumerateCallbackResult. Todos los demás valores están (actualmente) indefinidos; no los utilice.

PHYSFS_EnumerateCallbackResult

typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Firma de función para callbacks que enumeran archivos.

Advertencia

A partir de PhysicsFS 2.1, utilice PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; le da más control sobre el proceso.

Estos se utilizan para informar a un llamador original de una lista de entradas de directorio, un archivo/directorio/enlace simbólico por callback. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de ninguna cadena.

Estos callbacks se utilizan, a partir de PhysicsFS 1.1, como una alternativa a las funciones que devolverían listas que deben limpiarse con PHYSFS_freeList(). El callback significa que la biblioteca no necesita asignar una lista completa y todas las cadenas por adelantado.

Tenga en cuenta que el orden de los datos prometidos en las versiones de lista no es necesariamente el mismo en las versiones de callback. Consulte la documentación de las API específicas, pero es posible que las cadenas no estén ordenadas como espera y podría obtener cadenas duplicadas.

Parámetros

data Puntero a datos definido por el usuario, pasado desde la API que finalmente llamó al callback.
origdir Una cadena que contiene la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio sobre el que solicitó la enumeración, pasado en el callback para su conveniencia.
fname El nombre del archivo que se está enumerando. Puede que no esté en orden alfabético en comparación con otros callbacks que se han disparado, y no contendrá la ruta completa. Puede recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

enum PHYSFS_ErrorCode

Valores que representan causas específicas de error. La mayoría de las veces, solo debería preocuparse por si una operación dada falló o no, pero puede haber ocasiones en las que planee manejar un caso de error específico con gracia, por lo que proporcionamos códigos de error específicos.

La mayoría de estos errores son un poco vagos, y la mayoría no son cosas que usted pueda arreglar... si hay un error de permisos, por ejemplo, todo lo que realmente puede hacer es pasar esa información al usuario y dejar que él decida cómo manejarlo. En la mayoría de estos casos, su programa solo debería preocuparse de que no logró sus objetivos, y no preocuparse específicamente por qué.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Get a list of files from a directory in the search path, using an application-defined callback, with errors reported. Internally, PHYSFS_enumerateFiles() simply calls this function and then builds a list before returning to the application, so the functionality is identical, save how the information is presented to the application.

Unlike PHYSFS_enumerateFiles(), this function does not return an array. Instead, it calls an application-specified function once for each item in the search path:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

The items passed to the callback are not guaranteed to be in any order. No sorting is done at this level, and if you need it, you should use PHYSFS_enumerateFiles(), which guarantees alphabetical sorting. This form reports what is discovered for each file before moving to the next. Even within one archive, we can't guarantee the order in which data is discovered. *Any sorting you find in these callbacks is just pure luck. Do not rely on it.* Since this walks through the entire file listing, you may get duplicate filenames.

This API and the callbacks themselves can report errors. Prior to this API, callbacks had to accept every enumerated item, even if they were only looking for a specific object and wanted to stop after or had a serious error and couldn't notify anyone. Also, if PhysicsFS itself had a problem (disk error or whatever), it couldn't report it to the application; it would just go on to skip items or stop entirely, and the caller would have no idea that it had lost some data along the way.

Now the caller can be assured that they got a complete set of data, and if they want to stop enumeration early, their callback has control. See the documentation for PHYSFS_EnumerateCallback for details on how your callback should behave.

Parameters

dir Directory, in system-independent notation, to enumerate.
c Callback function to notify about path items.
d Application-defined data passed to the callback. May be NULL.

Returns

non-zero on success, zero on failure. Use PHYSFS_getLastErrorCode() to get the specific error. If the callback returns PHYSFS_ENUM_STOP to stop early, this is considered success. Callbacks returning PHYSFS_ENUM_ERROR will cause this function to return zero and set the error code to PHYSFS_ERR_APP_CALLBACK.

char ** PHYSFS_enumerateFiles (const char * dir)

Get a list of files from a directory in the search path.

Warning

In versions of PhysicsFS prior to 2.1, this function would return as many items as it could in case of failure (memory error, disk i/o error, etc.). This meant that applications couldn't distinguish between complete success and partial failure, and since the function could always return NULL to report catastrophic failure, in PhysicsFS 2.1 this policy has changed: it will return a complete list of results or return NULL in case of *any* failure, so we can guarantee that the enumeration completed and there are no gaps in your results.

Directories that match will be interleaved. That is, if "C:\mydir" is in the search path and contains a directory "savegames" which contains "x.sav", "y.sav", and "z.sav", and there is also a "C:\userdir" in the search path that has a "savegames" directory with "w.sav", then the following code:

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Añadir un archivo o directorio a la ruta de búsqueda. Si es un duplicado, la entrada no se añade de nuevo, aunque la función tenga éxito. No puede añadir el mismo archivo a dos puntos de montaje diferentes: la comprobación de duplicados se realiza contra el archivo y no contra el punto de montaje.

Cuando monta un archivo, se añade a un sistema de archivos virtual... todos los archivos de todos los archivos se interpolan en un único árbol de archivos jerárquico. Dos archivos montados en el mismo lugar (o un archivo con archivos que se superponen a otro punto de montaje) pueden tener archivos superpuestos: en tal caso, se selecciona el archivo anterior en la ruta de búsqueda, y los otros archivos son inaccesibles para la aplicación. Esto permite utilizar archivos para anular revisiones anteriores; puede utilizar el mecanismo de montaje para colocar archivos en un punto específico del árbol de archivos y evitar la superposición; esto es útil para mods descargables que podrían pisotear datos de la aplicación o entre sí, por ejemplo.

El punto de montaje no necesita existir antes de montar, lo que es diferente de lo que los familiarizados con el concepto de "montaje" de Unix pueden esperar. Además, se pueden montar más de un archivo en el mismo punto de montaje, o los puntos de montaje y el contenido de los archivos pueden superponerse... el mecanismo de interpolación sigue funcionando como de costumbre.

Especificar un enlace simbólico a un archivo o directorio está permitido aquí, independientemente del estado de PHYSFS_permitSymbolicLinks(). Esa función solo se ocupa de enlaces simbólicos dentro del directorio o archivo montado.

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y archivos contienen archivos que son solo punteros a otros archivos. En el sistema de archivos físico, abrir un enlace de este tipo abrirá (transparente) el archivo al que apunta.

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convierte una cadena Latin1 a una cadena UTF-8. Las cadenas Latin1 son de 8 bits por carácter: una codificación popular de "ASCII superior".

Para asegurar que el buffer de destino sea lo suficientemente grande para la conversión, por favor, asigna un buffer que sea el doble del tamaño del buffer de origen. UTF-8 expande los puntos de código Latin1 mayores de 127 de 1 a 2 bytes, por lo que la cadena puede crecer en algunos casos.

Las cadenas que no caben en el buffer de destino se truncarán, pero siempre se terminarán con null y nunca tendrán una secuencia UTF-8 incompleta al final. Si la longitud del buffer es 0, esta función no hace nada.

Tenga en cuenta que no proporcionamos un conversor de UTF-8 a Latin1, ya que Latin1 no puede expresar la mayoría de los puntos de código Unicode. Es una codificación heredada; deberías estar convirtiendo lejos de ella en todo momento.

Parámetros

src Cadena de origen terminada en null en formato Latin1.
dst Buffer para almacenar la cadena UTF-8 convertida.
len Tamaño, en bytes, del buffer de destino.
