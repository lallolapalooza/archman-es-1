DESCRIPTION

The PhysicsFS library provides an abstraction layer over various kinds of data sources. It allows you to treat archives (like ZIP files, tarballs, etc.) and directories seamlessly as if they were directories on your filesystem. This is useful for games and other applications that need to manage large amounts of data, often bundled into archives.

The library handles byte-order swapping for different endiannesses, character encoding conversions (UTF-8, UCS-2, UCS-4, Latin1), and provides a consistent API for file I/O operations across different platforms.

Data Types

The library defines various integer types with specific sizes and signedness (e.g., PHYSFS_sint16 for a 16-bit signed integer, PHYSFS_uint32 for a 32-bit unsigned integer). It also defines opaque types like PHYSFS_File, PHYSFS_Io, PHYSFS_Allocator, PHYSFS_Archiver, PHYSFS_Stats, and PHYSFS_Version which represent internal library structures and are manipulated through the provided functions.

Callbacks are defined for enumerating files and strings, allowing the application to process results iteratively.

Initialization and Shutdown

Before using any other PhysicsFS function, you must call PHYSFS_init(). This function initializes the library and should be called only once per application. The `argv0` parameter is used for detecting the application's executable path, which can be important for finding default configuration files or archives.

To release all resources and clean up, call PHYSFS_initFree() before your application exits. This function should be called exactly once, after all other PhysicsFS functions have been called.

PHYSFS_isInit() can be used to check if the library has been successfully initialized.

Mounting and Search Path

PhysicsFS uses a search path to locate files. You can add directories or archives to this path using PHYSFS_mount(). The `mountPoint` parameter specifies where in the virtual filesystem the archive or directory will appear. If `appendToPath` is non-zero, the new mount point is added to the end of the search path; otherwise, it's added to the beginning.

PhysicsFS supports mounting archives directly from memory buffers (PHYSFS_mountMemory), from PHYSFS_Io interfaces (PHYSFS_mountIo), or from existing PHYSFS_File handles (PHYSFS_mountHandle).

You can remove items from the search path using PHYSFS_unmount().

PHYSFS_getMountPoint() can be used to find out which mount point a given directory or archive is associated with.

PHYSFS_getCdRomDirsCallback() and PHYSFS_getSearchPathCallback() allow you to iterate over CD-ROM directories and the current search path, respectively, using a provided callback function.

File Listing and Information

PHYSFS_enumerate() and PHYSFS_enumerateFilesCallback() provide ways to get a list of files within a given directory in the virtual filesystem. The former reports errors, while the latter uses a callback function for processing the results.

PHYSFS_stat() retrieves information about a file or directory, such as its size, modification time, and type (regular file, directory, etc.).

Byte Order Swapping

The functions prefixed with `swapSLE` (Swap Little-Endian Signed) and `swapULE` (Swap Little-Endian Unsigned) convert values from little-endian byte order to the platform's native byte order. Functions prefixed with `swapSBE` and `swapUBE` do the same for big-endian byte order.

These functions are useful when reading data from files or network streams that were written in a specific byte order.

Reading and Writing Values

The `PHYSFS_readS*E*` and `PHYSFS_readU*E*` functions read a value of a specified size and endianness from a PHYSFS_File handle and convert it to the platform's native byte order. The `*BE` variants read big-endian values, while the `*LE` variants read little-endian values.

Conversely, the `PHYSFS_writeS*E*` and `PHYSFS_writeU*E*` functions convert a value from the platform's native byte order to the specified endianness (big-endian `*BE`, little-endian `*LE`) and write it to the PHYSFS_File handle.

These functions are essential for handling binary data files that adhere to specific endianness conventions.

Low Level I/O

PHYSFS_readBytes() reads a specified number of raw bytes from a PHYSFS_File handle into a buffer. It returns the number of bytes actually read, which may be less than requested if end-of-file is reached or an error occurs.

PHYSFS_writeBytes() writes a specified number of raw bytes from a buffer to a PHYSFS_File handle. It returns the number of bytes actually written.

Character Encoding Conversions

PhysicsFS provides functions to convert strings between different character encodings:

  • PHYSFS_utf8FromUcs4(): Converts a UCS-4 (UTF-32) string to UTF-8.
  • PHYSFS_utf8ToUcs4(): Converts a UTF-8 string to UCS-4.
  • PHYSFS_utf8FromUcs2(): Converts a UCS-2 (UTF-16) string to UTF-8.
  • PHYSFS_utf8ToUcs2(): Converts a UTF-8 string to UCS-2.
  • PHYSFS_utf8FromUtf16(): Converts a UTF-16 string to UTF-8.
  • PHYSFS_utf8ToUtf16(): Converts a UTF-8 string to UTF-16.
  • PHYSFS_utf8FromLatin1(): Converts a Latin1 string to UTF-8.

These functions are crucial for handling international text data correctly, especially when dealing with files originating from different systems or applications.

String Comparison and Case Folding

PHYSFS_caseFold() converts a given Unicode codepoint to its lowercase equivalent. This is useful for implementing case-insensitive comparisons.

The `PHYSFS_utf*stricmp` functions provide case-insensitive string comparison for UTF-8, UTF-16, and UCS-4 encoded strings.

Error Handling

PHYSFS_getLastErrorCode() returns the last error code that occurred in the current thread. The error codes are defined in the `PHYSFS_ErrorCode` enumeration.

PHYSFS_getErrorByCode() takes an error code and returns a human-readable string describing the error.

PHYSFS_setErrorCode() allows you to manually set the error code for the current thread. This is typically used internally by PhysicsFS but can be useful for custom error reporting.

Allocator and Configuration

PHYSFS_setAllocator() allows you to provide your own memory allocation functions (malloc, realloc, free) to PhysicsFS. This can be useful for integrating with custom memory management systems.

PHYSFS_getAllocator() returns a pointer to the currently active allocator structure.

PHYSFS_symbolicLinksPermitted() checks if symbolic links are allowed by the current configuration. Symbolic links might be used by some archive formats or filesystem implementations.

PHYSFS_getPrefDir() returns a platform-specific path where user preferences or application data can be stored. The `org` and `app` arguments are used to construct this path.

Archiver Management

PhysicsFS supports various archive formats (e.g., ZIP, RAR, 7z). You can query the supported types using PHYSFS_supportedArchiveTypes().

To add support for custom archive formats, you can use PHYSFS_registerArchiver() with a pointer to a PHYSFS_Archiver structure that defines how to read and write your archive type. Correspondingly, PHYSFS_deregisterArchiver() removes an archiver.

PHYSFS_setRoot() allows you to specify a subdirectory within an archive to be treated as the root directory for that archive.

int PHYSFS_enumerate(const char *dir, PHYSFS_EnumerateCallback c, void *d)

Get a file listing of a search path's directory, using an application-defined callback, with errors reported. Internally, PHYSFS_enumerateFiles() just calls this function and then builds a list before returning to the application, so functionality is identical except for how the information is represented to the application.

Unlike PHYSFS_enumerateFiles(), this function does not return an array. Rather, it calls a function specified by the application once per element of the search path:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Items sent to the callback are not guaranteed to be in any order whatsoever. There is no sorting done at this level, and if you need that, you should probably use PHYSFS_enumerateFiles() instead, which guarantees alphabetical sorting. This form reports whatever is discovered in each archive before moving on to the next. Even within one archive, we can't guarantee what order it will discover data. Any sorting you find in these callbacks is just pure luck. Do not rely on it. As this walks the entire list of archives, you may receive duplicate filenames.

This API and the callbacks themselves are capable of reporting errors. Prior to this API, callbacks had to accept every enumerated item, even if they were only looking for a specific thing and wanted to stop after that, or had a serious error and couldn't alert anyone. Furthermore, if PhysicsFS itself had a problem (disk error or whatnot), it couldn't report it to the calling app, it would just have to skip items or stop enumerating outright, and the caller wouldn't know it had lost some data along the way.

Now the caller can be sure it got a complete data set, and its callback has control if it wants enumeration to stop early. See the documentation for PHYSFS_EnumerateCallback for details on how your callback should behave.

dir Directory, in platform-independent notation, to enumerate.
c Callback function to notify about search path elements.
d Application-defined data passed to callback. Can be NULL.

Returns

non-zero on success, zero on failure. Use PHYSFS_getLastErrorCode() to obtain the specific error. If the callback returns PHYSFS_ENUM_STOP to stop early, this will be considered success. char **PHYSFS_enumerateFiles(const char *dir)

Get a file listing of a search path's directory.

Warning

In PhysicsFS versions prior to 2.1, this function would return as many items as it could in the face of a failure condition (out of memory, disk i/o error, etc). Since this meant apps couldn't distinguish between complete success and partial failure, and since the function could always return NULL to report catastrophic failures anyway, in PhysicsFS 2.1 this function's policy changed: it will either return a list of complete results or it will return NULL for any failure of any kind, so we can guarantee that the enumeration ran to completion and has no gaps in its results.

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);
PHYSFS_freeList(rc);

Will print:

* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav].

PHYSFS_mount()

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

Añade un archivo, contenido en un manejador PHYSFS_File, a la ruta de búsqueda.

Advertencia

A menos que tengas alguna necesidad especial de bajo nivel, deberías usar PHYSFS_mount() en lugar de esta función.

¡Los archivos dentro de archivos pueden ser muy lentos! Mientras que un PHYSFS_File puede buscar incluso cuando los datos están comprimidos, puede hacerlo retrocediendo al inicio y descomprimiendo todo antes del punto de búsqueda. El uso normal de archivos puede realizar muchas búsquedas en segundo plano. Como tal, podrías encontrar que el uso normal de archivos es extremadamente doloroso si se monta de esta manera. Planifica en consecuencia: si, por ejemplo, tienes un archivo .zip autoextraíble y quieres montar algo dentro de él, comprime el contenido del archivo interior y asegúrate de que el archivo .zip exterior no comprima también el archivo interior.

Esta función opera de manera similar a PHYSFS_mount(), pero toma un manejador PHYSFS_File en lugar de una ruta de archivo. Este manejador contiene todos los datos del archivo y se utiliza en lugar de un archivo real en el sistema de archivos físico. El PHYSFS_File puede estar respaldado por un archivo real en el sistema de archivos físico, pero no es necesariamente así. El uso más popular para esto es probablemente montar archivos almacenados dentro de otros archivos.

(newDir) debe ser una cadena única para identificar este archivo. No necesita referirse a un archivo real en absoluto. Si la extensión del nombre del archivo no es útil, el sistema intentará con cada archivador hasta que uno funcione o ninguno de ellos lo haga. int PHYSFS_setRoot (const char * archivo, const char * subdirectorio)

Hace que un subdirectorio de un archivo sea su directorio raíz. Esto te permite limitar los archivos accesibles en un archivo específico. Por ejemplo, si tienes x.zip con un archivo en y/z.txt, montado en /a, si llamas PHYSFS_setRoot("x.zip", "/y"), entonces la llamada PHYSFS_openRead("/a/z.txt") tendrá éxito.

archivo directorio/archivo sobre el cual cambiar la raíz.
subdirectorio nuevo subdirectorio para hacer la raíz de este archivo.

distinto de cero en caso de éxito, cero en caso de fallo. Usa PHYSFS_getLastErrorCode() para obtener el error específico.

Comparación insensible a mayúsculas y minúsculas de dos cadenas UTF-8. Este es un reemplazo de strcasecmp/stricmp que espera que ambas cadenas estén en codificación UTF-8. Realizará "plegado de mayúsculas" para decidir si los puntos de código Unicode en las cadenas coinciden.

Si ambas cadenas son exclusivamente caracteres ASCII bajos, esto hará lo correcto, ya que también es UTF-8 válido. Si hay algún carácter ASCII alto, ¡esto no hará lo que esperas!

Informará qué cadena es "mayor que" la otra, pero ten en cuenta que esto no significa necesariamente nada: 'a' puede ser "menor que" 'b', pero un kuten japonés no tiene una relación alfabética significativa con una lambda griega, pero poder asignar un "valor" confiable hace posibles los algoritmos de ordenación, aunque no sean del todo sensatos. La mayoría de los casos deberían tratar el valor de retorno como "igual" o "no igual".

Al igual que stricmp, esto espera que ambas cadenas estén terminadas en nulo.

Parámetros

str1 Primera cadena a comparar.
str2 Segunda cadena a comparar.

Retorna

-1 si str1 es "menor que" str2, 1 si es "mayor que", 0 si son iguales.

NAME

PHYSFS_writeUBE16, PHYSFS_writeUBE32, PHYSFS_writeUBE64, PHYSFS_writeULE16, PHYSFS_writeULE32, PHYSFS_writeULE64 - write data in specific endianness.

SYNOPSIS

#include <physfs.h>

int PHYSFS_writeUBE16(PHYSFS_File *file, PHYSFS_uint16 val);
int PHYSFS_writeUBE32(PHYSFS_File *file, PHYSFS_uint32 val);

int PHYSFS_writeULE32(PHYSFS_File *file, PHYSFS_uint32 val);
int PHYSFS_writeULE64(PHYSFS_File *file, PHYSFS_uint64 val);

Description

These functions allow you to write numerical data to a PHYSFS_File in a specific byte order (endianness). They convert the data from the platform's native byte order to the specified endianness before writing it to the file.

Functions starting with writeU indicate an unsigned value.

Functions ending with BE indicate Big-Endian byte order.

Functions ending with LE indicate Little-Endian byte order.

The number indicates the number of bits in the data type (16, 32, or 64).

These are convenience functions. If you are writing a large amount of data, it is more efficient to write it directly using PHYSFS_write.
