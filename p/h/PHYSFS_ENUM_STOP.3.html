Estos valores determinan si un callback de enumeración debe continuar emitiendo o detenerse (y por qué).

PHYSFS_enumerate

Este es el mismo que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, excepto que puede devolver un resultado desde el callback: si estás buscando algo específico, una vez encontrado, puedes decirle a PhysicsFS que detenga la enumeración. Parámetros

data Puntero de datos personalizado, pasado por la API que finalmente llamó al callback.
origdir Una cadena con la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, es el directorio en el que solicitaste la enumeración, pasado en el callback para tu conveniencia.
fname El nombre del archivo que se está enumerando. Puede no estar en orden alfabético en comparación con otros callbacks que se hayan llamado, y no contendrá la ruta completa. Puedes recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

Retorna

Un valor de PHYSFS_EnumerateCallbackResult. Todos los demás valores son (actualmente) indefinidos; no los uses.

typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Firma de funciones de callback que enumeran archivos.

Advertencia

A partir de PhysicsFS 2.1, utiliza PHYSFS_EnumerateCallback con PHYSFS_enumerate(); esto te da más control sobre el proceso.

Estos se utilizan para reportar una lista de entradas de directorio a un llamador original, una entrada por callback. Todas las cadenas están en formato UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de las cadenas.

Estos callbacks se utilizan, desde PhysicsFS 1.1, como alternativa a las funciones que devuelven listas que deben ser liberadas con PHYSFS_freeList(). El callback significa que la biblioteca no necesita asignar una lista completa y todas las cadenas al principio.

Debes tener en cuenta que los órdenes prometidos en las versiones de lista no son necesariamente los mismos en las versiones de callback. Consulta la documentación de APIs específicas, pero es posible que las cadenas no estén ordenadas como esperas y podrías obtener cadenas duplicadas.

data Puntero de datos personalizado, pasado por la API que finalmente llamó al callback.
origdir Una cadena con la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, es el directorio en el que solicitaste la enumeración, pasado en el callback para tu conveniencia.
fname El nombre del archivo que se está enumerando. Puede no estar en orden alfabético en comparación con otros callbacks que se hayan llamado, y no contendrá la ruta completa. Puedes recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtiene un listado de archivos de un directorio de la ruta de búsqueda, utilizando una devolución de llamada definida por la aplicación, con informes de errores. Internamente, PHYSFS_enumerateFiles() simplemente llama a esta función y luego crea una lista antes de devolverla a la aplicación, por lo que la funcionalidad es idéntica, excepto por la forma en que la información se representa a la aplicación.

A diferencia de PHYSFS_enumerateFiles(), esta función no devuelve una matriz. En su lugar, llama a una función especificada por la aplicación una vez por cada elemento de la ruta de búsqueda:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Tenemos [%s] en [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // deme más datos, por favor.
}
// ...
PHYSFS_enumerate("/alguna/ruta", printDir, NULL);

No se garantiza que los elementos enviados a la devolución de llamada estén en ningún orden específico. No se realiza ningún tipo de ordenación en este nivel, y si lo necesita, probablemente debería usar PHYSFS_enumerateFiles() en su lugar, que garantiza la ordenación alfabética. Esta forma informa lo que se descubre en cada archivo antes de pasar al siguiente. Incluso dentro de un mismo archivo, no podemos garantizar el orden en que descubrirá los datos. *Cualquier ordenación que encuentre en estas devoluciones de llamada es pura suerte. No confíe en ella.* A medida que recorre toda la lista de archivos, puede recibir nombres de archivo duplicados.

Esta API y las propias devoluciones de llamada son capaces de informar errores. Antes de esta API, las devoluciones de llamada tenían que aceptar cada elemento enumerado, incluso si solo buscaban algo específico y querían detenerse después de eso, o si tenían un error grave y no podían alertar a nadie. Además, si PhysicsFS en sí tenía un problema (error de disco o similar), no podía informarlo a la aplicación que lo llamaba, solo tenía que omitir elementos o dejar de enumerar directamente, y el llamador no sabría que había perdido algunos datos en el camino.

Ahora el llamador puede estar seguro de que obtuvo un conjunto completo de datos, y su devolución de llamada tiene control si desea que la enumeración se detenga antes. Consulte la documentación de PHYSFS_EnumerateCallback para obtener detalles sobre cómo debe comportarse su devolución de llamada.

Parámetros

dir Directorio, en notación independiente de la plataforma, a enumerar.
c Función de devolución de llamada para notificar sobre elementos de la ruta de búsqueda.
d Datos definidos por la aplicación pasados a la devolución de llamada. Puede ser NULL.

Devuelve

Distinto de cero en caso de éxito, cero en caso de fallo. Use PHYSFS_getLastErrorCode() para obtener el error específico. Si la devolución de llamada devuelve PHYSFS_ENUM_STOP para detenerse antes, esto se considerará un éxito. Las devoluciones de llamada que devuelvan PHYSFS_ENUM_ERROR harán que esta función devuelva cero y establezca el código de error en PHYSFS_ERR_APP_CALLBACK.

const char *PHYSFS_getPrefDir (const char * org, const char * app)

Obtener la ruta de directorio específica del usuario y de la aplicación donde se pueden escribir archivos. Función de ayuda.

Obtener el "directorio de preferencias". Este es el lugar donde los usuarios pueden escribir archivos personales (preferencias y partidas guardadas, etc.) específicos de su aplicación. Esta carpeta es única por usuario y por aplicación.

Esta función determina la ubicación adecuada en el sistema de archivos nativo, crea la carpeta si no existe y devuelve una cadena en notación dependiente del sistema, adecuada para pasar a PHYSFS_setWriteDir().

En Windows, podría verse así: "C:\\Users\\bob\\AppData\\Roaming\\Mi Empresa\\Mi Nombre de Programa"

En Linux, podría verse así: "/home/bob/.local/share/Mi Nombre de Programa"

En Mac OS X, podría verse así: "/Users/bob/Library/Application Support/Mi Nombre de Programa"

(etc.)

Deberías usar el directorio de preferencias para tu ruta de escritura, y también colocarlo cerca del principio de tu lista de búsqueda. Versiones antiguas de PhysicsFS ofrecían solo PHYSFS_getUserDir() y dejaban que los usuarios determinaran dónde deberían almacenarse los archivos dentro de ese árbol. Esto encuentra la ubicación correcta para cualquier plataforma, que no solo cambia entre sistemas operativos, sino también entre versiones del mismo sistema operativo.

Especifica el nombre de tu organización (si no es una organización real, tu nombre o un dominio que poseas podría servir) y el nombre de tu aplicación. Estos deben ser nombres adecuados.

Ambas cadenas (org) y (app) pueden ser parte de un nombre de carpeta, así que por favor sigue estas reglas:

  • Usa la misma cadena de organización (incluyendo mayúsculas y minúsculas) para todas tus aplicaciones que utilicen esta función.
  • Usa una cadena de aplicación única para cada una, asegurándote de que no cambie para una aplicación una vez que la hayas decidido.
  • Los caracteres Unicode son válidos, siempre que estén codificados como UTF-8, pero...
  • ...solo usa letras, números y espacios. Evita el uso de caracteres como "Nombre del Juego 2: ¡La Venganza del Malo!" ... "Nombre del Juego 2" es suficiente.

El puntero devuelto por esta función permanece válido hasta que lo vuelvas a usar o llames a PHYSFS_deinit(). Aunque no es rápido, deberías llamarlo una vez al inicio del programa y copiar la cadena si la necesitas.

Debes asumir que la ruta devuelta por esta función es la única ubicación segura para escribir archivos (y que PHYSFS_getUserDir() y PHYSFS_getBaseDir(), aunque puedan ser escribibles o incluso padres de la ruta devuelta, no son la ubicación adecuada donde deberías escribir).

org el nombre de tu organización.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Añade un archivo y directorio a la ruta de búsqueda. Si es un duplicado, el elemento no se añade de nuevo, incluso si la función tiene éxito. No puedes añadir el mismo archivo a dos puntos de montaje diferentes: el control de duplicados se realiza contra el archivo, no contra el punto de montaje.

Cuando montas un archivo, se añade a un sistema de archivos virtual... todos los archivos de todos los archivos se interpolan en una sola jerarquía de directorios. Dos archivos montados en el mismo lugar (o un archivo con archivos que se superponen a otro punto de montaje) pueden tener archivos superpuestos: en tal caso, se selecciona el archivo más cercano en la ruta de búsqueda y los otros archivos son inaccesibles para la aplicación. Esto permite usar archivos para sobrescribir revisiones anteriores; puedes usar el mecanismo de montaje para colocar archivos en un punto específico del árbol de archivos y evitar la superposición; es útil para modificaciones descargadas que puedan pisar datos de la aplicación o entre sí, por ejemplo.

Se permite especificar un enlace simbólico a un archivo o directorio, independientemente del estado de PHYSFS_permitSymbolicLinks(). Esta función solo se enfoca en enlaces simbólicos dentro del archivo o directorio montado.

appendToPath distinto de cero para añadir al final de la ruta, cero para añadir al principio.

Planifica en consecuencia: si, por ejemplo, tienes un archivo .zip autoextraíble y quieres montar algo dentro de él, comprime el contenido del archivo interior y asegúrate de que el archivo .zip exterior no comprima el archivo interior demasiado.

void PHYSFS_permitSymbolicLinks (int allow)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y archivos contienen archivos que son solo punteros a otros archivos. En el sistema de archivos físico, abrir un enlace de este tipo abrirá (transparentemente) el archivo al que apunta.

Por defecto, PhysicsFS verificará si un archivo es realmente un enlace simbólico durante las llamadas de apertura y fallará si lo es. De lo contrario, el enlace podría sacarte de las rutas de escritura y búsqueda, y comprometer la seguridad.

Si desea asumir ese riesgo, llame a esta función con un parámetro distinto de cero. Tenga en cuenta que esto es más para aislar el lenguaje de scripting de un programa, en caso de que scripts no confiables intenten comprometer el sistema. En términos generales, un usuario podría tener una razón legítima para configurar un enlace simbólico, por lo que a menos que sienta que hay un peligro específico en permitirlos, debería permitirlos.

Los enlaces simbólicos solo se verifican explícitamente cuando se trata con nombres de archivo en notación independiente de la plataforma. Es decir, al configurar sus rutas de búsqueda y escritura, etc., nunca se verifican los enlaces simbólicos.

Tenga en cuenta que PHYSFS_stat() siempre verificará la ruta especificada; si esa ruta es un enlace simbólico, no se seguirá en ningún caso. Si los enlaces simbólicos no están permitidos a través de esta función, PHYSFS_stat() los ignora y trataría la consulta como si la ruta no existiera en absoluto.

El permiso de enlace simbólico se puede habilitar o deshabilitar en cualquier momento después de haber llamado a PHYSFS_init(), y está deshabilitado por defecto.

Parámetros

allow distinto de cero para permitir enlaces simbólicos, cero para denegarlos.

int PHYSFS_setAllocator (const PHYSFS_Allocator * allocator)

Establece tus propios algoritmos de asignación en PhysicsFS. (Esto es para uso limitado y complicado. Si no ves una necesidad inmediata para ello, puedes ignorarlo para siempre).

Por defecto, PhysicsFS utilizará lo más razonable para gestionar la memoria dinámica en un sistema de plataforma (generalmente malloc/realloc/free, aunque en algunos sistemas podría usar algo diferente), pero en casos raros, la aplicación podría querer más control sobre la gestión de memoria de la librería. Esto permite que PhysicsFS utilice tus propios algoritmos de asignación. Puedes llamar a esta función después de PHYSFS_deinit() si estás dispuesto a apagar la librería y reiniciarla con un nuevo algoritmo de asignación; esta es una operación segura y soportada. El algoritmo se mantiene intacto entre llamadas de desinicialización/inicialización. Si deseas volver a usar el algoritmo predeterminado de la plataforma, pasa NULL aquí.

Si no estás seguro de qué hacer con esta función, puedes ignorarla por completo.

Parámetros

allocator La estructura con los puntos de entrada de tu algoritmo de asignación.

Retorno

Cero en caso de fallo, distinto de cero en caso de éxito. Esta llamada falla si se utiliza entre PHYSFS_init() y PHYSFS_deinit().

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convertir una cadena Latin1 en una cadena UTF-8. Las cadenas Latin1 tienen 8 bits por carácter: una popular codificación "high ASCII".

Para asegurar que el buffer de destino sea suficientemente grande para la conversión, por favor asigna un buffer que sea el doble del tamaño del buffer de origen. El UTF-8 expande los códigos Latin1 por encima de 127 de 1 a 2 bytes, así que la cadena puede crecer en algunos casos.

Las cadenas que no quepan en el buffer de destino se truncarán, pero siempre serán terminadas en nulo y nunca tendrán una secuencia UTF-8 incompleta al final. Si la longitud del buffer es 0, esta función no hace nada.

Nota: No proporcionamos un convertidor de UTF-8 a Latin1, ya que Latin1 no puede expresar más códigos Unicode. Es un formato antiguo; deberías convertir a él a todas horas.

Parámetros

src Cadena de origen en formato Latin1 terminada en nulo.
dst Buffer de destino para la cadena UTF-8 convertida.
len Tamaño, en bytes, del buffer de destino.

void PHYSFS_utf8FromUcs2 (const PHYSFS_uint16 * src, char * dst, PHYSFS_uint64 len)

Convertir una cadena UCS-2 en una cadena UTF-8.

Advertencia

Casi con seguridad deberías usar PHYSFS_utf8FromUtf16(), que estuvo disponible en PhysicsFS 2.1, a menos que sepas lo que estás haciendo.

Esta función no reportará un error si hay valores inválidos en la cadena de origen UCS-2. Los reemplazará con '?' y continuará con la conversión.

Las cadenas UCS-2 tienen 16 bits por carácter: TCHAR en Windows cuando se compila con soporte Unicode. Ten en cuenta que las versiones modernas de Windows usan UTF-16, que es un formato extendido de UCS-2, pero no es UCS-2 en sí mismo. Casi con seguridad quieres PHYSFS_utf8FromUtf16() en su lugar.

Para asegurar que el buffer de destino sea suficientemente grande para la conversión, por favor asigna un buffer que sea el doble del tamaño del buffer de origen. El UTF-8 nunca usa más de 32 bits por carácter, así que aunque pueda reducir una cadena UCS-2, también puede expandirla.

Las cadenas que no quepan en el buffer de destino se truncarán, pero siempre serán terminadas en nulo y nunca tendrán una secuencia UTF-8 incompleta al final. Si la longitud del buffer es 0, esta función no hace nada.

Parámetros

src Cadena de origen en formato UCS-2 terminada en nulo.
dst Buffer de destino para la cadena UTF-8 convertida.

int PHYSFS_utf8stricmp (const char * str1, const char * str2)

Comparación insensible a mayúsculas y minúsculas de dos cadenas UTF-8. Este es un reemplazo para strcasecmp/stricmp que espera que ambas cadenas estén en codificación UTF-8. Realizará "case folding" para determinar si los códigos de caracteres Unicode en las cadenas son iguales.

Si ambas cadenas son exclusivamente caracteres de bajo ASCII, esto hará lo correcto, ya que también es UTF-8 válido. Si hay algún carácter de alto ASCII, ¡esto no hará lo que esperas!

Informará cuál cadena es "mayor que" la otra, pero debes tener en cuenta que esto no siempre tiene sentido: 'a' puede ser "menor que" 'b', pero un kuten japonés no tiene una relación alfabética significativa con una lambda griega, pero poder asignar un valor fiable es posible para algoritmos de ordenación, si no son totalmente racionales. La mayoría de los casos deberían tratar el valor devuelto como "igual" o "no igual".

Como stricmp, esto espera que ambas cadenas estén terminadas en nulo.

Parámetros

str1 Cadena a comparar primero.
str2 Cadena a comparar segunda.

Retorno

-1 si str1 es "menor que" str2, 1 si es "mayor que", 0 si son iguales.

void PHYSFS_utf8ToUcs4 (const char * src, PHYSFS_uint32 discriminant, PHYSFS_uint32 * dst, PHYSFS_uint64 len)

Convert a UTF-8 string to a UCS-4 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UCS-4 strings are 32-bits per character. UTF-8 strings use between one and four bytes per character. The maximum number of UCS-4 characters you can possibly store in a buffer is 1/4 of the buffer size in bytes. To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is four times the size of the source buffer. UTF-8 characters that would require four bytes will still require four bytes when converted to UCS-4, so you don't need to allocate 16x the space just in case: 4x will do.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UCS-4 sequence at the end. If the buffer length is 0, this function does nothing.

Parameters

src Null-terminated source string in UTF-8 format.
dst Buffer to store converted UCS-4 string.
len Size, in bytes, of destination buffer.
