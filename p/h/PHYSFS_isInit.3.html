1.0 API compatibility define. PHYSFS_file is identical to PHYSFS_File. This #define is here for backwards compatibility with the 1.0 API, which had an inconsistent capitalization convention in this case. New code should use PHYSFS_File, as this #define may go away someday.

PHYSFS_enumerate

Esto es lo mismo que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, excepto que puede devolver un resultado del callback: es decir, si estás buscando algo específico, una vez que lo encuentres, puedes decirle a PhysicsFS que deje de enumerar más. typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Firma de función para callbacks que enumeran archivos.

Advertencia

A partir de PhysicsFS 2.1, usa PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; te da más control sobre el proceso.

Estos se utilizan para informar una lista de entradas de directorio a un llamador original, un archivo/directorio/enlace simbólico por callback. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de ninguna cadena.

Estos callbacks se utilizan, a partir de PhysicsFS 1.1, como una alternativa a las funciones que devolverían listas que deben limpiarse con PHYSFS_freeList(). El callback significa que la biblioteca no necesita asignar una lista completa y todas las cadenas por adelantado.

Ten en cuenta que el orden de los datos prometido en las versiones de lista no es necesariamente así en las versiones de callback. Consulta la documentación de las APIs específicas, pero las cadenas pueden no estar ordenadas como esperas y podrías obtener cadenas duplicadas.

Parámetros

data Puntero de datos definido por el usuario, pasado desde la API que finalmente llamó al callback.
origdir Una cadena que contiene la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio sobre el cual solicitaste la enumeración, pasado en el callback para tu conveniencia.
fname El nombre del archivo que se está enumerando. Puede que no esté en orden alfabético en comparación con otros callbacks que se han activado, y no contendrá la ruta completa. Puedes recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

enum PHYSFS_ErrorCode

Valores que representan causas específicas de fallo. La mayoría de las veces, solo deberías preocuparte por si una operación dada falló o no, pero puede haber ocasiones en las que planees manejar un caso de fallo específico con gracia, por lo que proporcionamos códigos de error específicos.

La mayoría de estos errores son un poco vagos, y la mayoría no son cosas que puedas arreglar... si hay un error de permisos, por ejemplo, todo lo que realmente puedes hacer es pasar esa información al usuario y dejar que ellos descubran cómo manejarlo. En la mayoría de estos casos, tu programa solo debería preocuparse de que no logró sus objetivos, y no preocuparse específicamente por qué.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Get a file listing of a search path's directory, using an application-defined callback, with errors reported. Internally, PHYSFS_enumerateFiles() just calls this function and then builds a list before returning to the application, so functionality is identical except for how the information is represented to the application.

Unlike PHYSFS_enumerateFiles(), this function does not return an array. Rather, it calls a function specified by the application once per element of the search path:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Items sent to the callback are not guaranteed to be in any order whatsoever. There is no sorting done at this level, and if you need that, you should probably use PHYSFS_enumerateFiles() instead, which guarantees alphabetical sorting. This form reports whatever is discovered in each archive before moving on to the next. Even within one archive, we can't guarantee what order it will discover data. Any sorting you find in these callbacks is just pure luck. Do not rely on it. As this walks the entire list of archives, you may receive duplicate filenames.

This API and the callbacks themselves are capable of reporting errors. Prior to this API, callbacks had to accept every enumerated item, even if they were only looking for a specific thing and wanted to stop after that, or had a serious error and couldn't alert anyone. Furthermore, if PhysicsFS itself had a problem (disk error or whatnot), it couldn't report it to the calling app, it would just have to skip items or stop enumerating outright, and the caller wouldn't know it had lost some data along the way.

Now the caller can be sure it got a complete data set, and its callback has control if it wants enumeration to stop early. See the documentation for PHYSFS_EnumerateCallback for details on how your callback should behave.

Parameters

dir Directory, in platform-independent notation, to enumerate.
c Callback function to notify about search path elements.
d Application-defined data passed to callback. Can be NULL.

Returns

non-zero on success, zero on failure. Use PHYSFS_getLastErrorCode() to obtain the specific error. If the callback returns PHYSFS_ENUM_STOP to stop early, this will be considered success. Callbacks returning PHYSFS_ENUM_ERROR will make this function return zero and set the error code to PHYSFS_ERR_APP_CALLBACK.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Añadir un archivo o directorio a la ruta de búsqueda. Si es un duplicado, la entrada no se añade de nuevo, aunque la función tenga éxito. No puede añadir el mismo archivo a dos puntos de montaje diferentes: la comprobación de duplicados se realiza contra el archivo y no contra el punto de montaje.

Cuando monta un archivo, se añade a un sistema de archivos virtual... todos los archivos en todos los archivos se interpolan en un único árbol de archivos jerárquico. Dos archivos montados en el mismo lugar (o un archivo con archivos que se superponen a otro punto de montaje) pueden tener archivos superpuestos: en tal caso, se selecciona el archivo anterior en la ruta de búsqueda y los otros archivos son inaccesibles para la aplicación. Esto permite que los archivos se utilicen para reemplazar revisiones anteriores; puede utilizar el mecanismo de montaje para colocar archivos en un punto específico del árbol de archivos y evitar la superposición; esto es útil para modificaciones descargables que podrían pisotear los datos de la aplicación o entre sí, por ejemplo.

El punto de montaje no necesita existir antes del montaje, lo cual es diferente de lo que aquellos familiarizados con el concepto de "montaje" de Unix podrían esperar. Además, se pueden montar más de un archivo al mismo punto de montaje, o los puntos de montaje y el contenido de los archivos pueden superponerse... el mecanismo de interpolación todavía funciona como de costumbre.

Se permite especificar un enlace simbólico a un archivo o directorio aquí, independientemente del estado de PHYSFS_permitSymbolicLinks(). Esa función solo se ocupa de los enlaces simbólicos dentro del directorio o archivo montado.

mountPoint Ubicación en el árbol interpolado donde se "montará" este archivo, en notación independiente de la plataforma. NULL o "" es equivalente a "/".
appendToPath distinto de cero para añadir a la ruta de búsqueda, cero para preceder.

Devoluciones

void PHYSFS_permitSymbolicLinks (int allow)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y archivos contienen archivos que son solo punteros a otros archivos. En el sistema de archivos físico, abrir dicho enlace abrirá (transparentemente) el archivo al que apunta.

Por defecto, PhysicsFS verificará si un archivo es realmente un enlace simbólico durante las llamadas de apertura y fallará si lo es. De lo contrario, el enlace podría sacarte de las rutas de escritura y búsqueda, y comprometer la seguridad.

Si quieres asumir ese riesgo, llama a esta función con un parámetro distinto de cero. Ten en cuenta que esto es más para aislar el lenguaje de scripting de un programa, en caso de que scripts no confiables intenten comprometer el sistema. En términos generales, un usuario podría tener una razón legítima para configurar un enlace simbólico, por lo que a menos que sientas que hay un peligro específico en permitirlos, deberías permitirlos.

Los enlaces simbólicos solo se verifican explícitamente cuando se trata con nombres de archivo en notación independiente de la plataforma. Es decir, al configurar tus rutas de búsqueda y escritura, etc., nunca se verifican los enlaces simbólicos.

Ten en cuenta que PHYSFS_stat() siempre verificará la ruta especificada; si esa ruta es un enlace simbólico, no se seguirá en ningún caso. Si los enlaces simbólicos no están permitidos a través de esta función, PHYSFS_stat() los ignora y trataría la consulta como si la ruta no existiera en absoluto.

El permiso de enlace simbólico se puede habilitar o deshabilitar en cualquier momento después de haber llamado a PHYSFS_init(), y está deshabilitado por defecto.

Parámetros

allow distinto de cero para permitir enlaces simbólicos, cero para denegar enlaces.
