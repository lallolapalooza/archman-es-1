typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Function signature for callbacks that enumerate files.

Warning

As of PhysicsFS 2.1, Use PHYSFS_EnumerateCallback with PHYSFS_enumerate() instead; it gives you more control over the process.

These are used to report a list of directory entries to an original caller, one file/dir/symlink per callback. All strings are UTF-8 encoded. Functions should not try to modify or free any string's memory.

These callbacks are used, starting in PhysicsFS 1.1, as an alternative to functions that would return lists that need to be cleaned up with PHYSFS_freeList(). The callback means that the library doesn't need to allocate an entire list and all the strings up front.

Be aware that promised data ordering in the list versions are not necessarily so in the callback versions. Check the documentation on specific APIs, but strings may not be sorted as you expect and you might get duplicate strings.

Parameters

data User-defined data pointer, passed through from the API that eventually called the callback.
origdir A string containing the full path, in platform-independent notation, of the directory containing this file. In most cases, this is the directory on which you requested enumeration, passed in the callback for your convenience.
fname The filename that is being enumerated. It may not be in alphabetical order compared to other callbacks that have fired, and it will not contain the full path. You can recreate the fullpath with $origdir/$fname ... The file can be a subdirectory, a file, a symlink, etc.

enum PHYSFS_ErrorCode

Values that represent specific causes of failure. Most of the time, you should only concern yourself with whether a given operation failed or not, but there may be occasions where you plan to handle a specific failure case gracefully, so we provide specific error codes.

Most of these errors are a little vague, and most aren't things you can fix...if there's a permission error, for example, all you can really do is pass that information on to the user and let them figure out how to handle it. In most these cases, your program should only care that it failed to accomplish its goals, and not care specifically why.

int PHYSFS_delete (const char * filename)

Delete a file or directory. (filename) is specified in platform-independent notation in relation to the write dir.

A directory must be empty before this call can delete it.

Deleting a symlink will remove the link, not what it points to, regardless of whether you "permitSymLinks" or not.

So if you've got the write dir set to "C:\mygame\writedir" and call PHYSFS_delete("downloads/maps/level1.map") then the file "C:\mygame\writedir\downloads\maps\level1.map" is removed from the physical filesystem, if it exists and the operating system permits the deletion.

\n

Obtiene una lista de archivos de un directorio de la ruta de búsqueda, utilizando una devolución de llamada definida por la aplicación, con informes de errores. Internamente, PHYSFS_enumerateFiles() simplemente llama a esta función y luego crea una lista antes de devolverla a la aplicación, por lo que la funcionalidad es idéntica excepto por cómo se representa la información a la aplicación.

\n

A diferencia de PHYSFS_enumerateFiles(), esta función no devuelve una matriz. En su lugar, llama a una función especificada por la aplicación una vez por cada elemento de la ruta de búsqueda:

\n
static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)\n{\n    printf(\" * Tenemos [%s] en [%s].\\n\", fname, origdir);\n    return PHYSFS_ENUM_OK;  // dame más datos, por favor.\n}\n// ...\nPHYSFS_enumerate(\"/alguna/ruta\", printDir, NULL);

No se garantiza que los elementos enviados a la devolución de llamada estén en ningún orden. No se realiza ningún ordenamiento a este nivel, y si lo necesita, probablemente debería usar PHYSFS_enumerateFiles() en su lugar, que garantiza el ordenamiento alfabético. Esta forma informa lo que se descubre en cada archivo antes de pasar al siguiente. Incluso dentro de un archivo, no podemos garantizar el orden en que descubrirá los datos. Cualquier orden que encuentre en estas devoluciones de llamada es pura suerte. No confíe en ello. Dado que recorre toda la lista de archivos, es posible que reciba nombres de archivo duplicados.

Antes de esta API, las devoluciones de llamada tenían que aceptar cada elemento enumerado, incluso si solo buscaban algo específico y querían detenerse después de eso, o tenían un error grave y no podían alertar a nadie. Además, si PhysicsFS en sí tenía un problema (error de disco o similar), no podía informarlo a la aplicación que lo llamaba, solo tendría que omitir elementos o dejar de enumerar por completo, y el llamador no sabría que había perdido algunos datos en el camino.

\n

Ahora el llamador puede estar seguro de que obtuvo un conjunto de datos completo, y su devolución de llamada tiene el control si desea que la enumeración se detenga antes. Advertencia

Desde PhysicsFS 2.1, esta función ha sido quemada. Antes de PhysicsFS 2.1, era la única forma de obtener detalles de error más allá de la valoración básica de una función. Esto se usaba para un string legible humano en varios idiomas y no era útil para el parsing de aplicaciones. Era un problema, porque el desarrollador no seleccionaba el idioma en tiempo de compilación, y los mantenedores de PhysicsFS tenían que (mal) mantener un gran cantidad de trabajo de localización. La aplicación no podía parsear los strings, incluso si contaban con un idioma específico, porque algunos eran dinámicamente generados. int PHYSFS_mount(const char *newDir, const char *mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

int PHYSFS_setAllocator (const PHYSFS_Allocator * allocator)

Conecta tus propias rutinas de asignación a PhysicsFS. (Esto es para un uso limitado y especializado. Si no ves una necesidad inmediata, probablemente puedas ignorar esto para siempre).

Por defecto, PhysicsFS utilizará lo que sea razonable para una plataforma para gestionar la memoria dinámica (generalmente malloc/realloc/free de ANSI C, pero algunas plataformas pueden usar algo diferente), pero en algunos casos poco comunes, la aplicación podría querer un mayor control sobre la gestión de memoria de la biblioteca. El asignador permanece intacto entre las llamadas de deinit/init. Si quieres volver al asignador por defecto de la plataforma, pasa un NULL aquí.

int PHYSFS_setBuffer (PHYSFS_File * handle, int bufsize)

Enable or disable buffering on an open file. This is useful for performance, especially when dealing with archives.

If bufsize is non-zero, buffering is enabled, and the buffer will be at least this big. If bufsize is zero, buffering is disabled, and any existing buffer is freed.

Note that enabling buffering will try to flush the buffer to disk if the file is open for writing. If this flush fails, the function will fail.

Likewise, disabling buffering will try to flush the buffer to disk. If this flush fails, the function will fail.

You can resize an existing buffer by calling this function more than once on the same file. Setting the buffer size to zero will free an existing buffer.

PhysicsFS file handles are unbuffered by default.

Please check the return value of this function! Failures can include not being able to seek backwards in a read-only file when removing the buffer, not being able to allocate the buffer, and not being able to flush the buffer to disk, among other unexpected problems.

Parameters

handle handle returned from PHYSFS_open*().
bufsize size, in bytes, of buffer to allocate.

Returns

nonzero if successful, zero on error.

Make a subdirectory of an archive its root directory. This lets you narrow down the accessible files in a specific archive. For example, if you have x.zip with a file in y/z.txt, mounted to /a, if you call PHYSFS_setRoot("x.zip", "/y"), then the call PHYSFS_openRead("/a/z.txt") will succeed.

Convert a UTF-8 string to a Latin1 string. Latin1 strings are 8-bits per character: a popular "high ASCII" encoding.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 expands latin1 codepoints over 127 from 1 to 2 bytes, so the string may grow in some cases.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-8 sequence at the end. If the buffer length is 0, this function does nothing.

Please note that we do not supply a UTF-8 to Latin1 converter, since Latin1 can't express most Unicode codepoints. It's a legacy encoding; you should be converting away from it at all times.

Por favor, ten en cuenta que aunque (len) es un entero sin signo de 64 bits, estás limitado a 63 bits (9223372036854775807 bytes), así que podemos devolver un valor negativo en caso de error. Si la longitud es mayor que 0x7FFFFFFFFFFFFFFF, esta función fallará inmediatamente. Para sistemas sin un tipo de dato de 64 bits, estás limitado a 31 bits (0x7FFFFFFF, o 2147483647 bytes). Confiamos en que la mayoría de las cosas no necesitarán hacer múltiples gigabytes de entrada/salida en una sola llamada, ¡pero ¿por qué limitar las cosas?

Parámetros

handle valor de retorno de PHYSFS_openWrite() o PHYSFS_openAppend().
buffer búfer de (len) bytes a escribir en (handle).
len número de bytes que se escriben en (handle).

Devuelve

número de bytes escritos. Esto puede ser menor que (len); en caso de error, el sistema puede intentar escribir tantos bytes como sea posible, por lo que puede ocurrir una escritura incompleta. PHYSFS_getLastErrorCode() puede arrojar luz sobre la razón por la cual esto podría ser < (len). -1 si hay un fallo completo.
