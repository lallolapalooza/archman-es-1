#define PHYSfs_version

This macro expands to an integer that represents the version of the PhysicsFS library that you compiled against. This is determined by what header the compiler uses. Note that if you dynamically linked the library, you might have a slightly newer or older version at runtime. That version can be determined with PHYSFS_getLinkedVersion(), which, unlike PHYSFS_VERSION, is not a macro.

PHYSFS_enumerate

This is the same thing as PHYSFS_EnumFilesCallback from PhysicsFS 2.0, except it can return a result from the callback: namely: if you're looking for something specific, once you find it, you can tell PhysicsFS to stop enumerating further. This is used with PHYSFS_enumerate(), which we hopefully got right this time. :)

Parameters

data User-defined data pointer, passed through from the API that eventually called the callback.
origdir A string containing the full path, in platform-independent notation, of the directory containing this file. In most cases, this is the directory on which you requested enumeration, passed in the callback for your convenience.
fname The filename that is being enumerated. It may not be in alphabetical order compared to other callbacks that have fired, and it will not contain the full path. You can recreate the fullpath with $origdir/$fname ... The file can be a subdirectory, a file, a symlink, etc.

Returns

A value from PHYSFS_EnumerateCallbackResult. All other values are (currently) undefined; don't use them.

typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Function signature for callbacks that enumerate files.

Warning

As of PhysicsFS 2.1, Use PHYSFS_EnumerateCallback with PHYSFS_enumerate() instead; it gives you more control over the process.

These are used to report a list of directory entries to an original caller, one file/dir/symlink per callback. All strings are UTF-8 encoded. Functions should not try to modify or free any string's memory.

These callbacks are used, starting in PhysicsFS 1.1, as an alternative to functions that would return lists that need to be cleaned up with PHYSFS_freeList(). The callback means that the library doesn't need to allocate an entire list and all the strings up front.

Be aware that promised data ordering in the list versions are not necessarily so in the callback versions. Check the documentation on specific APIs, but strings may not be sorted as you expect and you might get duplicate strings.

Parameters

data User-defined data pointer, passed through from the API that eventually called the callback.
origdir A string containing the full path, in platform-independent notation, of the directory containing this file. In most cases, this is the directory on which you requested enumeration, passed in the callback for your convenience.
fname The filename that is being enumerated. It may not be in alphabetical order compared to other callbacks that have fired, and it will not contain the full path. You can recreate the fullpath with $origdir/$fname ... The file can be a subdirectory, a file, a symlink, etc.

enum PHYSFS_ErrorCode

Values that represent specific causes of failure. Most of the time, you should only concern yourself with whether a given operation failed or not, but there may be occasions where you plan to handle a specific failure case gracefully, so we provide specific error codes.

Most of these errors are a little vague, and most aren't things you can fix...if there's a permission error, for example, all you can really do is pass that information on to the user and let them figure out how to handle it. In most these cases, your program should only care that it failed to accomplish its goals, and not care specifically why.

int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

"Plegar" un punto de código Unicode a un equivalente en minúsculas. (Esto es para uso limitado y exigente. Si no ves inmediatamente una necesidad para ello, probablemente puedas ignorar esto para siempre).

Esto convertirá un punto de código Unicode en su equivalente en minúsculas. Los puntos de código falsos y aquellos sin equivalente en minúsculas se devolverán sin convertir.

¡Ten en cuenta que podrías obtener múltiples puntos de código en respuesta! El Eszett alemán, por ejemplo, se plegará en dos puntos de código latino 's' en minúsculas. La teoría es que si pliegas dos cadenas, una con un Eszett y otra con "SS", coincidirán.

Advertencia

Cualquiera que haya estudiado Unicode sabe sobre el problema de la "I turca". Esta API no lo maneja. Supón que esta única letra en todo Unicode se plegará de forma incorrecta. Si no sabes de qué se trata, probablemente puedas ignorar este problema para la mayor parte del planeta, pero la perfección es imposible.

Parámetros

from El punto de código a plegar.
to Búfer para almacenar los valores de los puntos de código plegados. Esto debe apuntar a espacio para al menos 3 ranuras de PHYSFS_uint32.

Retorna

El número de puntos de código que produjo el plegado. Entre 1 y 3.

int PHYSFS_close (PHYSFS_File * handle)

Cierra un manejador de archivo de PhysicsFS. Esta llamada puede fallar si el sistema operativo estaba almacenando en caché escrituras en el medio físico y, ahora forzado a escribir esos cambios en el medio físico, no puede almacenar los datos por alguna razón. En tal caso, el manejador de archivo permanece abierto. ¡Un programa bien escrito SIEMPRE debe verificar el valor de retorno de la llamada de cierre además de cada llamada de escritura!

Parámetros

int PHYSFS_deinit (void )

Desinicializa la biblioteca PhysicsFS. Esto cierra cualquier archivo abierto a través de PhysicsFS, borra las rutas de búsqueda/escritura, libera memoria e invalida todos tus manejadores de archivo.

Ten en cuenta que esta llamada puede FALLAR si hay un archivo abierto para escritura que se niega a cerrarse (por ejemplo, el sistema operativo subyacente estaba almacenando en caché escrituras en un sistema de archivos de red, y el servidor de archivos ha fallado, o un disco duro ha fallado, etc.). Generalmente es mejor cerrar todos los manejadores de escritura tú mismo antes de llamar a esta función, para poder manejar de forma elegante un fallo específico.

Una vez desinicializado con éxito, se puede volver a llamar a PHYSFS_init() para reiniciar el subsistema. Todos los estados de la API predeterminados se restauran en este punto, con la excepción de cualquier asignador personalizado que hayas especificado, el cual sobrevive entre inicializaciones.

Retorna

distinto de cero si tiene éxito, cero si hay error. Los detalles del error se pueden obtener de PHYSFS_getLastError(). Si falla, el estado de PhysFS no está definido y probablemente muy dañado.

const char * PHYSFS_getLastError (void )

Obtén información de error para humanos.

Obsoleto

Usa PHYSFS_getLastErrorCode() y PHYSFS_getErrorByCode() en su lugar.

Advertencia

Desde PhysicsFS 2.1, esta función ha sido reforzada. Antes de PhysicsFS 2.1, era la única manera de obtener detalles de error fuera de los valores de retorno básicos de una función. Estaba pensada como una cadena de texto legible por humanos en varios idiomas, y no era útil para el análisis de aplicaciones. Era un problema, ya que el desarrollador no elegía el idioma en tiempo de compilación, y los mantenedores de PhysicsFS tenían que (mal) mantener un gran trabajo de localización. La aplicación no podía analizar las cadenas, incluso si tenían un idioma específico, ya que algunas se generaban dinámicamente. En la versión 2.1 y posteriores, siempre devuelve una cadena estática en inglés; puedes usarla como una clave de localización personalizada si lo deseas, ya que prometemos no cambiar las cadenas existentes. Además, si tu aplicación quiere ver errores específicamente, ahora ofrecemos una mejor opción: usa PHYSFS_getLastErrorCode() en su lugar.

Obtén el último mensaje de error de PhysicsFS como una cadena legible por humanos, terminada en NULL. Devolverá NULL si no ha habido ningún error desde la última llamada a esta función. El puntero devuelto apunta a un búfer interno. Cada hilo tiene un estado de error único asociado. int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Añadir un archivo o directorio a la ruta de búsqueda. Si es un duplicado, la entrada no se añade de nuevo, a pesar de que la función tenga éxito. No puede añadir el mismo archivo a dos puntos de montaje diferentes: la comprobación de duplicados se realiza contra el archivo y no contra el punto de montaje.

Cuando monta un archivo, se añade a un sistema de archivos virtual... todos los archivos en todos los archivos se interpolan en un único árbol de archivos jerárquico. Dos archivos montados en el mismo lugar (o un archivo con archivos que se superponen con otro punto de montaje) pueden tener archivos superpuestos: en tal caso, se selecciona el archivo anterior en la ruta de búsqueda, y los otros archivos son inaccesibles para la aplicación. Esto permite que los archivos se utilicen para anular revisiones anteriores; puede utilizar el mecanismo de montaje para colocar archivos en un punto específico del árbol de archivos y evitar la superposición; esto es útil para mods descargables que podrían pisotear datos de la aplicación o entre sí, por ejemplo.

El punto de montaje no necesita existir antes de montarlo, lo que es diferente a lo que los familiarizados con el concepto Unix de "montar" pueden esperar. Además, más de un archivo puede montarse en el mismo punto de montaje, o los puntos de montaje y el contenido de los archivos pueden superponerse... el mecanismo de interpolación sigue funcionando como de costumbre.

Se permite especificar un enlace simbólico a un archivo o directorio aquí, independientemente del estado de PHYSFS_permitSymbolicLinks(). Esa función solo se ocupa de los enlaces simbólicos dentro del directorio o archivo montado.

mountPoint Ubicación en el árbol interpolado donde este archivo será "montado", en notación independiente de la plataforma. NULL o "" es equivalente a "/".
appendToPath distinto de cero para añadir a la ruta de búsqueda, cero para añadir al principio.

Advertencia

A menos que tenga alguna necesidad especial de bajo nivel, debería estar usando PHYSFS_mount() en lugar de esto.

Esta función opera igual que PHYSFS_mount(), pero toma un búfer de memoria en lugar de una ruta de archivo. Este búfer contiene todos los datos del archivo y se utiliza en lugar de un archivo real en el sistema de archivos físico.

(newDir) debe ser una cadena única para identificar este archivo. Se utiliza para optimizar la selección del archivador (si lo nombra XXXXX.zip, podríamos intentar primero el archivador ZIP, por ejemplo, o elegir directamente un archivador que solo pueda confiar en que los datos son válidos por la extensión del nombre de archivo). void PHYSFS_permitSymbolicLinks (int allow)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y archivos contienen archivos que son solo punteros a otros archivos. En el sistema de archivos físico, abrir dicho enlace abrirá (transparentemente) el archivo al que apunta.

Por defecto, PhysicsFS verificará si un archivo es realmente un enlace simbólico durante las llamadas de apertura y fallará si lo es. De lo contrario, el enlace podría sacarte de las rutas de escritura y búsqueda, y comprometer la seguridad.

Si deseas asumir ese riesgo, llama a esta función con un parámetro distinto de cero. Ten en cuenta que esto es más para aislar el lenguaje de scripting de un programa, en caso de que scripts no confiables intenten comprometer el sistema. En términos generales, un usuario podría tener una razón legítima para crear un enlace simbólico, por lo que a menos que sientas que hay un peligro específico en permitirlos, deberías permitirlos.

Los enlaces simbólicos solo se verifican explícitamente cuando se tratan nombres de archivo en notación independiente de la plataforma. Es decir, al configurar tus rutas de búsqueda y escritura, etc., nunca se verifican los enlaces simbólicos.

Ten en cuenta que PHYSFS_stat() siempre verificará la ruta especificada; si esa ruta es un enlace simbólico, no se seguirá en ningún caso. Si los enlaces simbólicos no están permitidos a través de esta función, PHYSFS_stat() los ignora y trataría la consulta como si la ruta no existiera en absoluto.

El permiso de enlace simbólico se puede habilitar o deshabilitar en cualquier momento después de haber llamado a PHYSFS_init(), y está deshabilitado por defecto.

The search path will be:

  • The Write Dir (created if it doesn't exist)
  • The Base Dir (PHYSFS_getBaseDir())
  • All found CD-ROM dirs (optionally)

These directories are then searched for files ending with the extension (archiveExt), which, if they are valid and supported archives, will also be added to the search path. If you specified "PKG" for (archiveExt), and there's a file named data.PKG in the base dir, it'll be checked. Archives can either be appended or prepended to the search path in alphabetical order, regardless of which directories they were found in. All archives are mounted in the root of the virtual file system ("/").

All of this can be accomplished from the application, but this just does it all for you. Feel free to add more to the search path manually, too.

archiveExt File extension used by your program to specify an archive. For example, Quake 3 uses "pk3", even though they are just zipfiles. Specify NULL to not dig out archives automatically. Do not specify the '.' char; If you want to look for ZIP files, specify "ZIP" and not ".ZIP" ... the archive search is case-insensitive.

nonzero on success, zero on error. Use PHYSFS_getLastErrorCode() to obtain the specific error.
