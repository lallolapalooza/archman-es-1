Compatibilidad con la API 1.0. PHYSFS_file es idéntico a PHYSFS_File. Esta #define existe por compatibilidad con la API 1.0, que tenía una convención de capitalización inconsistente en este caso. El nuevo código debe usar PHYSFS_File, ya que esta #define puede desaparecer algún día.

estructura con la versión de la biblioteca con la que compilaste. Esto se determina por el encabezado que el compilador utiliza. Esa versión se puede determinar con PHYSFS_getLinkedVersion(), que, a diferencia de PHYSFS_VERSION, no es una macro.

typedef PHYSFS_EnumerateCallbackResult(* physfs_EnumerateCallback) (void *data, const char *origdir, const char *fname)

Posibles valores de retorno de PHYSFS_EnumerateCallback. Firma de función para callbacks que enumeran y devuelven resultados.

Estos valores dictan si un callback de enumeración debe continuar ejecutándose o detenerse (y por qué se detiene).

PHYSFS_EnumerateCallback

PHYSFS_enumerate

Esto es lo mismo que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, excepto que puede devolver un resultado del callback: a saber: si estás buscando algo específico, una vez que lo encuentras, puedes indicarle a PhysicsFS que deje de enumerar más. Esto se usa con PHYSFS_enumerate(), que esperamos haber hecho bien esta vez. :)

Parámetros

data Puntero de datos definido por el usuario, pasado desde la API que finalmente llamó al callback.
origdir Una cadena que contiene la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio sobre el que solicitaste la enumeración, pasado en el callback para tu conveniencia.
fname El nombre del archivo que se está enumerando. Puede que no esté en orden alfabético en comparación con otros callbacks que se han ejecutado, y no contendrá la ruta completa. Puedes recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

Devuelve

Un valor de PHYSFS_EnumerateCallbackResult. Todos los demás valores son (actualmente) indefinidos; no los uses.

Advertencia

A partir de PhysicsFS 2.1, usa PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; te da más control sobre el proceso.

Estos se utilizan para informar una lista de entradas de directorio a un llamador original, un archivo/directorio/enlace simbólico por callback. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar o liberar la memoria de ninguna cadena.

Estos callbacks se utilizan, a partir de PhysicsFS 1.1, como una alternativa a las funciones que devolverían listas que necesitan ser limpiadas con PHYSFS_freeList(). El callback significa que la biblioteca no necesita asignar una lista completa y todas las cadenas de antemano.

Ten en cuenta que el orden de los datos prometido en las versiones de lista no es necesariamente así en las versiones de callback. Consulta la documentación de las APIs específicas, pero es posible que las cadenas no estén ordenadas como esperas y podrías recibir cadenas duplicadas.

Parámetros

data Puntero de datos definido por el usuario, pasado desde la API que finalmente llamó al callback.
origdir Una cadena que contiene la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio sobre el que solicitaste la enumeración, pasado en el callback para tu conveniencia.
fname El nombre del archivo que se está enumerando. Puede que no esté en orden alfabético en comparación con otros callbacks que se han ejecutado, y no contendrá la ruta completa. Puedes recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtiene una lista de archivos de un directorio de la ruta de búsqueda, utilizando una función de devolución de llamada definida por la aplicación, con informes de errores. Internamente, PHYSFS_enumerateFiles() simplemente llama a esta función y luego construye una lista antes de devolverla a la aplicación, por lo que la funcionalidad es idéntica, excepto por cómo se representa la información a la aplicación.

A diferencia de PHYSFS_enumerateFiles(), esta función no devuelve una matriz. En su lugar, llama a una función especificada por la aplicación una vez por cada elemento de la ruta de búsqueda:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // dame más datos, por favor.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

No se garantiza que los elementos enviados a la función de devolución de llamada estén en ningún orden particular. No se realiza ninguna ordenación a este nivel, y si la necesitas, probablemente deberías usar PHYSFS_enumerateFiles() en su lugar, que garantiza la ordenación alfabética. Esta forma informa de lo que se descubre en cada archivo antes de pasar al siguiente. Incluso dentro de un archivo, no podemos garantizar el orden en que descubrirá los datos. _Cualquier ordenación que encuentres en estas devoluciones de llamada es pura suerte. No confíes en ella._ Dado que recorre toda la lista de archivos, puedes recibir nombres de archivo duplicados.

Esta API y las propias funciones de devolución de llamada son capaces de informar de errores. Antes de esta API, las funciones de devolución de llamada tenían que aceptar cada elemento enumerado, incluso si solo buscaban algo específico y querían detenerse después de eso, o si tenían un error grave y no podían alertar a nadie. Además, si PhysicsFS en sí mismo tenía un problema (error de disco o similar), no podía informarlo a la aplicación que lo llamaba, solo tendría que omitir elementos o dejar de enumerar por completo, y el llamador no sabría que había perdido algunos datos en el camino.

Ahora el llamador puede estar seguro de que obtuvo un conjunto de datos completo, y su función de devolución de llamada tiene control si quiere que la enumeración se detenga antes. Consulte la documentación de PHYSFS_EnumerateCallback para obtener detalles sobre cómo debe comportarse su función de devolución de llamada.

Parameters

dir Directorio, en notación independiente de la plataforma, a enumerar.
c Función de devolución de llamada para notificar sobre elementos de la ruta de búsqueda.
d Datos definidos por la aplicación pasados a la función de devolución de llamada. Puede ser NULL.

Returns

Distinto de cero en caso de éxito, cero en caso de fallo. Utiliza PHYSFS_getLastErrorCode() para obtener el error específico. Si la función de devolución de llamada devuelve PHYSFS_ENUM_STOP para detenerse antes de tiempo, esto se considerará un éxito. Las funciones de devolución de llamada que devuelven PHYSFS_ENUM_ERROR harán que esta función devuelva cero y establezca el código de error en PHYSFS_ERR_APP_CALLBACK.

char ** PHYSFS_enumerateFiles (const char * dir)

Obtiene una lista de archivos de un directorio de la ruta de búsqueda.

Warning

En versiones de PhysicsFS anteriores a la 2.1, esta función devolvía tantos elementos como pudiera frente a una condición de error (falta de memoria, error de E/S de disco, etc.). Dado que esto significaba que las aplicaciones no podían distinguir entre el éxito completo y el fallo parcial, y dado que la función siempre podía devolver NULL para informar de fallos catastróficos de todos modos, en PhysicsFS 2.1 la política de esta función cambió: devolverá una lista de resultados completos o devolverá NULL para cualquier tipo de fallo, para que podamos garantizar que la enumeración se completó y no tiene lagunas en sus resultados.

Los directorios coincidentes se interpolan. Es decir, si "C:\mydir" está en la ruta de búsqueda y contiene un directorio "savegames" que contiene "x.sav", "y.sav" y "z.sav", y también hay un "C:\userdir" en la ruta de búsqueda que tiene un subdirectorio "savegames" con "w.sav", entonces el siguiente código:

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);
PHYSFS_freeList(rc);
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..fi

    devueltos siempre estarán libres de duplicados y siempre estarán ordenados
    alfabéticamente (o mejor dicho, en orden Unicode sensible a mayúsculas y
    minúsculas) para ti.
No olvides llamar a PHYSFS_freeList() con el valor de retorno de
    esta función cuando hayas terminado con él.

const char * PHYSFS_getPrefDir (const char * org, const char * app)

Obtiene la ruta específica del usuario y de la aplicación donde se pueden escribir archivos. Función auxiliar.

Obtiene el "pref dir" (directorio de preferencias). Está destinado a ser el lugar donde los usuarios pueden escribir archivos personales (preferencias y partidas guardadas, etc.) que son específicos de tu aplicación. Este directorio es único por usuario, por aplicación.

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

Parameters

newDir directory or archive to add to the path, in platform-dependent notation.
mountPoint Location in the interpolated tree that this archive will be "mounted", in platform-independent notation. NULL or "" is equivalent to "/".
appendToPath nonzero to append to search path, zero to prepend.

Returns

nonzero if added to path, zero on failure (bogus archive, dir missing, etc). Use PHYSFS_getLastErrorCode() to obtain the specific error.

Añade un archivo, contenido en un manejador de PHYSFS_File, a la ruta de búsqueda.

Advertencia

A menos que tenga alguna necesidad especial de bajo nivel, debería usar PHYSFS_mount() en lugar de esto.

¡Los archivos dentro de otros archivos pueden ser muy lentos! Mientras que un PHYSFS_File puede buscar incluso cuando los datos están comprimidos, puede hacerlo rebobinando al principio y descomprimiendo todo antes del punto de búsqueda. El uso normal de archivos puede realizar muchas búsquedas en segundo plano. Como tal, podría encontrar que el uso normal de archivos es extremadamente doloroso si se monta de esta manera. Planifique en consecuencia: si, por ejemplo, tiene un archivo .zip autoextraíble y desea montar algo dentro de él, comprima el contenido del archivo interno y asegúrese de que el archivo .zip externo no comprima también el archivo interno.

Esta función opera de manera similar a PHYSFS_mount(), pero toma un manejador de PHYSFS_File en lugar de una ruta de archivo. Este manejador contiene todos los datos del archivo y se utiliza en lugar de un archivo real en el sistema de archivos físico. El PHYSFS_File puede estar respaldado por un archivo real en el sistema de archivos físico, pero no necesariamente. El uso más popular para esto es probablemente montar archivos almacenados dentro de otros archivos.

(newDir) debe ser una cadena única para identificar este archivo. Se utiliza para optimizar la selección del archivador (si lo nombra XXXXX.zip, podríamos probar primero el archivador ZIP, por ejemplo, o elegir directamente un archivador que solo pueda confiar en que los datos son válidos por la extensión del nombre del archivo). No necesita referirse a un archivo real en absoluto. Si la extensión del nombre del archivo no es útil, el sistema intentará con cada archivador hasta que uno funcione o ninguno lo haga. Este nombre de archivo debe ser único, ya que el sistema no le permitirá tener dos archivos con el mismo nombre.

(file) debe permanecer hasta que el archivo se desmonte. Cuando el archivo se desmonte, el sistema llamará a PHYSFS_close(file). Si necesita que este manejador sobreviva, tendrá que envolverlo en un PHYSFS_Io y usar PHYSFS_mountIo() en su lugar.

Si esta función falla, no se llama a PHYSFS_close(file).

file El manejador de PHYSFS_File que contiene los datos del archivo.
newDir Nombre de archivo que puede representar este flujo.
mountPoint Ubicación en el árbol interpolado donde se "montará" este archivo, en notación independiente de la plataforma. NULL o "" es equivalente a "/".
appendToPath distinto de cero para añadir a la ruta de búsqueda, cero para anteponer.

Retorna

Distinto de cero si se añadió a la ruta, cero en caso de fallo (archivo no válido, etc.). Use PHYSFS_getLastErrorCode() para obtener el error específico.

int PHYSFS_setAllocator (const PHYSFS_Allocator * allocator)

Por defecto, PhysicsFS utilizará lo que sea razonable para la plataforma para gestionar la memoria dinámica (generalmente malloc/realloc/free de ANSI C, pero algunas plataformas podrían usar algo diferente), pero en algunos casos poco comunes, la aplicación podría querer más control sobre la gestión de memoria de la biblioteca. void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convert a Latin1 string to a UTF-8 string. Latin1 strings are 8-bits per character: a popular "high ASCII" encoding.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 expands latin1 codepoints over 127 from 1 to 2 bytes, so the string may grow in some cases.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-8 sequence at the end. If the buffer length is 0, this function does nothing.

Please note that we do not supply a UTF-8 to Latin1 converter, since Latin1 can't express most Unicode codepoints. It's a legacy encoding; you should be converting away from it at all times.

src Null-terminated source string in Latin1 format.
dst Buffer to store converted UTF-8 string.

Convierte una cadena UTF-8 a una cadena UTF-16.

Advertencia

Esta función no informará de un error si hay secuencias UTF-8 inválidas en la cadena de origen. Las reemplazará con un carácter '?' y continuará.

PHYSFS_writeUBE16, PHYSFS_writeUBE32, PHYSFS_writeUBE64, PHYSFS_writeULE16, PHYSFS_writeULE32, PHYSFS_writeULE64 - write formatted numeric data to a PHYSFS file.

SYNOPSIS

#include <physfs.h>

int PHYSFS_writeUBE16(PHYSFS_File *file, PHYSFS_uint16 val);

Detailed Description

These functions convert a numeric value from the platform's native byte order to the specified endianness, and then write the result to the specified file handle.

int PHYSFS_writeUBE16 (PHYSFS_File * file, PHYSFS_uint16 val)

Convert and write an unsigned 16-bit bigendian value. Convenience function. Convert an unsigned 16-bit value from the platform's native byte order to bigendian and write it to a file.

Parameters

file PhysicsFS file handle to which to write.
val Value to convert and write.

Returns

zero on failure, non-zero on success. On failure, you can find out what went wrong from PHYSFS_getLastErrorCode().
