typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Firma de función para callbacks que enumeran archivos.

Advertencia

A partir de PhysicsFS 2.1, usa PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; te da más control sobre el proceso.

Estos se utilizan para informar una lista de entradas de directorio a un llamador original, un archivo/directorio/enlace simbólico por callback. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de ninguna cadena.

Estos callbacks se utilizan, a partir de PhysicsFS 1.1, como una alternativa a las funciones que devolverían listas que necesitan ser limpiadas con PHYSFS_freeList(). El callback significa que la biblioteca no necesita asignar una lista completa y todas las cadenas de antemano.

Ten en cuenta que el orden de los datos prometido en las versiones de lista no es necesariamente así en las versiones de callback. Consulta la documentación de APIs específicas, pero es posible que las cadenas no estén ordenadas como esperas y podrías obtener cadenas duplicadas.

Parámetros

data Puntero de datos definido por el usuario, pasado desde la API que finalmente llamó al callback.
origdir Una cadena que contiene la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio sobre el que solicitaste la enumeración, pasado en el callback para tu conveniencia.
fname El nombre del archivo que se está enumerando. Puede que no esté en orden alfabético en comparación con otros callbacks que se hayan ejecutado, y no contendrá la ruta completa. Puedes recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Get a file listing of a search path's directory, using an application-defined callback, with errors reported. Internally, PHYSFS_enumerateFiles() just calls this function and then builds a list before returning to the application, so functionality is identical except for how the information is represented to the application.

Unlike PHYSFS_enumerateFiles(), this function does not return an array. Rather, it calls a function specified by the application once per element of the search path:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Items sent to the callback are not guaranteed to be in any order whatsoever. There is no sorting done at this level, and if you need that, you should probably use PHYSFS_enumerateFiles() instead, which guarantees alphabetical sorting. This form reports whatever is discovered in each archive before moving on to the next. Even within one archive, we can't guarantee what order it will discover data. Any sorting you find in these callbacks is just pure luck. Do not rely on it. As this walks the entire list of archives, you may receive duplicate filenames.

This API and the callbacks themselves are capable of reporting errors. Prior to this API, callbacks had to accept every enumerated item, even if they were only looking for a specific thing and wanted to stop after that, or had a serious error and couldn't alert anyone. Furthermore, if PhysicsFS itself had a problem (disk error or whatnot), it couldn't report it to the calling app, it would just have to skip items or stop enumerating outright, and the caller wouldn't know it had lost some data along the way.

Now the caller can be sure it got a complete data set, and its callback has control if it wants enumeration to stop early. See the documentation for PHYSFS_EnumerateCallback for details on how your callback should behave.

Parameters

dir Directory, in platform-independent notation, to enumerate.
c Callback function to notify about search path elements.
d Application-defined data passed to callback. Can be NULL.

Returns

non-zero on success, zero on failure. Use PHYSFS_getLastErrorCode() to obtain the specific error. If the callback returns PHYSFS_ENUM_STOP to stop early, this will be considered success. int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Añadir un archivo o directorio a la ruta de búsqueda. Si es un duplicado, la entrada no se añade de nuevo, aunque la función tenga éxito. No se puede añadir el mismo archivo a dos puntos de montaje diferentes: la comprobación de duplicados se realiza contra el archivo y no contra el punto de montaje.

Cuando montas un archivo, se añade a un sistema de archivos virtual... todos los archivos de todos los archivos se interpolan en un único árbol de archivos jerárquico. Dos archivos montados en el mismo lugar (o un archivo con archivos que se solapan con otro punto de montaje) pueden tener archivos superpuestos: en tal caso, se selecciona el archivo anterior en la ruta de búsqueda, y los otros archivos son inaccesibles para la aplicación. Esto permite que los archivos se utilicen para anular revisiones anteriores; puede usar el mecanismo de montaje para colocar archivos en un punto específico del árbol de archivos y evitar superposiciones; esto es útil para mods descargables que podrían pisotear datos de la aplicación o entre sí, por ejemplo.

El punto de montaje no necesita existir antes de montar, lo que es diferente de lo que los familiarizados con el concepto de "montaje" de Unix pueden esperar. Además, se pueden montar varios archivos en el mismo punto de montaje, o los contenidos de los puntos de montaje y archivos pueden superponerse... el mecanismo de interpolación sigue funcionando como de costumbre.

Se permite especificar un enlace simbólico a un archivo o directorio aquí, independientemente del estado de PHYSFS_permitSymbolicLinks(). Esa función solo se ocupa de los enlaces simbólicos dentro del directorio montado o archivo.

appendToPath distinto de cero para añadir a la ruta de búsqueda, cero para añadir al principio.

void PHYSFS_permitSymbolicLinks (int allow)

Permite o deniega el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y archivos contienen archivos que son solo punteros a otros archivos. En el sistema de archivos físico, la apertura de dicho enlace abrirá (transparente) el archivo al que apunta.

Por defecto, PhysicsFS verificará si un archivo es realmente un enlace simbólico durante las llamadas de apertura y fallará si lo es. De lo contrario, el enlace podría llevarte fuera de las rutas de escritura y búsqueda, y comprometer la seguridad.

Si deseas asumir ese riesgo, llama a esta función con un parámetro distinto de cero. Ten en cuenta que esto es más para aislar el lenguaje de scripting de un programa, en caso de que scripts no confiables intenten comprometer el sistema. En general, un usuario podría tener una razón legítima para configurar un enlace simbólico, por lo que a menos que sientas que existe un peligro específico al permitirlos, deberías permitirlos.

Los enlaces simbólicos solo se verifican explícitamente cuando se trata con nombres de archivo en notación independiente de la plataforma. Es decir, al configurar tus rutas de búsqueda y escritura, etc., nunca se verifican los enlaces simbólicos.

Si los enlaces simbólicos no están permitidos a través de esta función, PHYSFS_stat() los ignora y trataría la consulta como si la ruta no existiera en absoluto.

El permiso de enlaces simbólicos se puede habilitar o deshabilitar en cualquier momento después de haber llamado a PHYSFS_init(), y está deshabilitado por defecto.

int PHYSFS_setRoot(const char *archive, const char *subdir)

Hace un subdirectorio de un archivo como su directorio raíz. Esto permite que puedas acotar los archivos accesibles en un archivo específico. Por ejemplo, si tienes x.zip con un archivo en y/z.txt montado a /a, si llamás a PHYSFS_setRoot("x.zip", "/y"), entonces la llamada a PHYSFS_openRead("/a/z.txt") se satisfará.

Puedes cambiar el raíz de un archivo en cualquier momento, alterando el árbol de archivos interpolado (dependiendo de donde se muevan las rutas, puede proporcionar diferentes archivos de un archivo distinto). Si estableces el raíz a NULL o a "/", el archivo será tratado como si no hubiera raíz especial (como si el archivo hubiera sido montado normalmente).

Cambiar el raíz solo afecta las operaciones futuras en rutas de archivos; un archivo que se abrió desde una ruta que cambió debido a un setRoot no será afectado.

Establecer un nuevo raíz no está limitado a archivos en el directorio de búsqueda; puedes establecerlo en el directorio de escritura también, lo cual puede ser útil si tienes archivos abiertos para escritura y no puedes cambiar el directorio de escritura en este momento.

No es un error establecer un subdirectorio que no exista como raíz de un archivo, aunque no se mostrarán archivos en este caso. Si los directorios faltantes terminan siendo creados (una mkdir en el sistema de archivos físico, etc), esto se reflejará en el árbol interpolado.

Parámetros

archive directorio/archive sobre el cual cambiar el raíz.
subdir subdirectorio nuevo a hacer el raíz de este archivo.

Retorna

nozero en éxito, cero en fallo. Usa PHYSFS_getLastErrorCode() para obtener el error específico.

int PHYSFS_setSaneConfig(const char *organization, const char *appName, const char *archiveExt, int includeCdRoms, int archivesFirst)

Configura caminos sencillos y predeterminados. Función de ayuda.

El directorio de escritura se establecerá en el prefdir devuelto por

, que se crea si no existe.

La parte anterior es suficiente para asegurar que el directorio de configuración de tu programa esté separado de otros archivos de desorden, y sea independiente del sistema de operación.

La ruta de búsqueda será:

  • Directorio de escritura (creado si no existe)
  • Directorio base (PHYSFS_getBaseDir())
  • Todos los directorios CD-ROM encontrados (opcional)

Estos directorios se buscan por extensiones (archiveExt), que, si son válidas y soportadas, también se agregan a la ruta de búsqueda. Si especificaste "PKG" para (archiveExt) y hay un archivo llamado data.PKG en el directorio base, se verificará. Los archivos pueden ser appendidos o prependedos a la ruta de búsqueda en orden alfabético, independientemente de dónde se encontraron. Todos los archivos se montan en el raíz del sistema de archivos virtual ("/").

Todo lo anterior puede realizarse desde la aplicación, pero esto lo hace todo para ti. Puedes añadir más a la ruta de búsqueda manualmente, también.

Especifica NULL para no buscar automáticamente archivos. No especifiques la letra '.'; si quieres buscar archivos ZIP, especifícalo como "ZIP" y no como ".ZIP" ... la búsqueda de archivos es insensible a mayúsculas y minúsculas.
includeCdRoms No cero para incluir CD-ROMs en la ruta de búsqueda, y (si (archiveExt) != NULL) buscarlos por archivos. Esto puede causar un bloqueo significativo mientras se acceden discos, y si no hay discos en la unidad (o incluso no montadas en sistemas Unix), pueden no estar disponibles. Puedes especificar cero y manejar la configuración de discos tú mismo.
archivesFirst No cero para prepender los archivos a la ruta de búsqueda. Cero para appendearlos. Ignorado si !(archiveExt).

nozero en éxito, cero en error. Usa PHYSFS_getLastErrorCode() para obtener el error específico.

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convert a Latin1 string to a UTF-8 string. Latin1 strings are 8-bits per character: a popular "high ASCII" encoding.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 expands latin1 codepoints over 127 from 1 to 2 bytes, so the string may grow in some cases.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-8 sequence at the end. If the buffer length is 0, this function does nothing.

Please note that we do not supply a UTF-8 to Latin1 converter, since Latin1 can't express most Unicode codepoints. It's a legacy encoding; you should be converting away from it at all times.

Parameters

src Null-terminated source string in Latin1 format.
dst Buffer to store converted UTF-8 string.
len Size, in bytes, of destination buffer.

PHYSFS_writeUBE16, PHYSFS_writeUBE32, PHYSFS_writeUBE64, PHYSFS_writeULE16, PHYSFS_writeULE32, PHYSFS_writeULE64 - write platform-native data to a PhysicsFS file.

SYNOPSIS

#include <physfs.h>

int PHYSFS_writeUBE16(PHYSFS_File *file, PHYSFS_uint16 val);

int PHYSFS_writeUBE32(PHYSFS_File *file, PHYSFS_uint32 val);

Detailed Description

These are convenience functions that convert a value from the platform's native byte order to either big-endian or little-endian, and then write that value to a PhysicsFS file.

PHYSFS_writeUBE16 writes an unsigned 16-bit big-endian value.

PHYSFS_writeUBE32 writes an unsigned 32-bit big-endian value.

PHYSFS_writeUBE64 writes an unsigned 64-bit big-endian value.

PHYSFS_writeULE16 writes an unsigned 16-bit little-endian value.

PHYSFS_writeULE32 writes an unsigned 32-bit little-endian value.

PHYSFS_writeULE64 writes an unsigned 64-bit little-endian value.
