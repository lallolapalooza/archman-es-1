DESCRIPTION

Este archivo de cabecera principal para PhysicsFS contiene las declaraciones de las funciones de bajo nivel para acceder a los archivos y manejar la configuración de la biblioteca.

Las funciones de intercambio de bytes (por ejemplo, PHYSFS_swapSLE32) convierten valores entre el orden de bytes little-endian (el más común en las arquitecturas x86) y el orden de bytes nativo de la plataforma. Esto es útil cuando se leen o escriben datos en formatos de archivo que especifican un orden de bytes particular.

Las funciones de lectura y escritura (por ejemplo, PHYSFS_readSLE32, PHYSFS_writeSLE32) combinan la lectura o escritura de un valor desde/hacia un archivo con la conversión del orden de bytes. Estas funciones son convenientes para manejar datos numéricos en archivos.

PHYSFS_isInit se utiliza para comprobar si PhysicsFS se ha inicializado correctamente. PHYSFS_symbolicLinksPermitted comprueba si la creación y el seguimiento de enlaces simbólicos están habilitados.

PHYSFS_setAllocator permite al usuario proporcionar sus propias funciones de asignación de memoria para que PhysicsFS las utilice, lo que puede ser útil para la depuración o la integración con sistemas de gestión de memoria personalizados.

Las funciones PHYSFS_mount, PHYSFS_mountIo, PHYSFS_mountMemory y PHYSFS_mountHandle se utilizan para añadir archivos o directorios al sistema de archivos virtual de PhysicsFS. PHYSFS_getMountPoint puede ser utilizado para determinar dónde se montó un directorio específico. PHYSFS_unmount elimina un elemento de la ruta de búsqueda. Las funciones de callback como PHYSFS_getCdRomDirsCallback y PHYSFS_getSearchPathCallback permiten iterar sobre los directorios montados.

Las funciones PHYSFS_enumerateFilesCallback y PHYSFS_enumerate se utilizan para obtener listas de archivos dentro de un directorio especificado en la ruta de búsqueda de PhysicsFS.

Las funciones de conversión de codificación de caracteres (por ejemplo, PHYSFS_utf8FromUcs4, PHYSFS_utf8ToUcs2) manejan la conversión entre diferentes esquemas de codificación de caracteres, como UTF-8, UCS-2, UCS-4 y Latin1. Esto es crucial para manejar nombres de archivo y datos de texto en diferentes plataformas y locales.

PHYSFS_caseFold, PHYSFS_utf8stricmp, PHYSFS_utf16stricmp y PHYSFS_ucs4stricmp proporcionan funcionalidades para realizar comparaciones de cadenas insensibles a mayúsculas y minúsculas en varias codificaciones de caracteres.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtiene una lista de archivos de un directorio de la ruta de búsqueda, utilizando una función de devolución de llamada definida por la aplicación, con informes de errores. Internamente, PHYSFS_enumerateFiles() simplemente llama a esta función y luego construye una lista antes de devolverla a la aplicación, por lo que la funcionalidad es idéntica excepto por cómo se representa la información a la aplicación.

A diferencia de PHYSFS_enumerateFiles(), esta función no devuelve una matriz. Más bien, llama a una función especificada por la aplicación una vez por cada elemento de la ruta de búsqueda:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Tenemos [%s] en [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // deme más datos, por favor.
}
// ...
PHYSFS_enumerate("/alguna/ruta", printDir, NULL);

No se garantiza que los elementos enviados a la función de devolución de llamada estén en ningún orden de ningún tipo. No se realiza ninguna ordenación a este nivel, y si la necesita, probablemente debería usar PHYSFS_enumerateFiles() en su lugar, que garantiza la ordenación alfabética. Esta forma informa lo que se descubre en cada archivo antes de pasar al siguiente. Incluso dentro de un archivo, no podemos garantizar el orden en que descubrirá los datos. Cualquier orden que encuentre en estas llamadas es pura suerte. No confíe en ella. Dado que recorre toda la lista de archivos, puede recibir nombres de archivo duplicados.

Esta API y las propias funciones de devolución de llamada son capaces de informar errores. Antes de esta API, las funciones de devolución de llamada tenían que aceptar cada elemento enumerado, incluso si solo buscaban algo específico y querían detenerse después de eso, o tenían un error grave y no podían alertar a nadie. Además, si PhysicsFS en sí tenía un problema (error de disco o similar), no podía informarlo a la aplicación que llamaba, simplemente tendría que omitir elementos o dejar de enumerar por completo, y el llamador no sabría que había perdido algunos datos en el camino.

Ahora el llamador puede estar seguro de que obtuvo un conjunto completo de datos, y su función de devolución de llamada tiene control si desea que la enumeración se detenga antes. Consulte la documentación de PHYSFS_EnumerateCallback para obtener detalles sobre cómo debe comportarse su función de devolución de llamada.

dir Directorio, en notación independiente de la plataforma, a enumerar.
c Función de devolución de llamada para notificar sobre los elementos de la ruta de búsqueda.
d Datos definidos por la aplicación pasados a la función de devolución de llamada. Puede ser NULL.

Devuelve

Distinto de cero en caso de éxito, cero en caso de error. Utilice PHYSFS_getLastErrorCode() para obtener el error específico. Si la función de devolución de llamada devuelve PHYSFS_ENUM_STOP para detenerse antes, esto se considerará un éxito. Las funciones de devolución de llamada que devuelven PHYSFS_ENUM_ERROR harán que esta función devuelva cero y establezca el código de error en PHYSFS_ERR_APP_CALLBACK.

char ** PHYSFS_enumerateFiles (const char * dir)

Obtiene una lista de archivos de un directorio de la ruta de búsqueda.

Advertencia

En las versiones de PhysicsFS anteriores a la 2.1, esta función devolvería tantos elementos como pudiera frente a una condición de error (falta de memoria, error de E/S de disco, etc.). Dado que esto significaba que las aplicaciones no podían distinguir entre el éxito completo y el fracaso parcial, y dado que la función siempre podía devolver NULL para informar fallos catastróficos de todos modos, en PhysicsFS 2.1 la política de esta función cambió: devolverá una lista de resultados completos o devolverá NULL para cualquier tipo de error, para que podamos garantizar que la enumeración se completó y no tiene lagunas en sus resultados.

Los directorios coincidentes se interpolan. Es decir, si "C:\mydir" está en la ruta de búsqueda y contiene un directorio "savegames" que contiene "x.sav", "y.sav" y "z.sav", y también hay un "C:\userdir" en la ruta de búsqueda que tiene un subdirectorio "savegames" con "w.sav", entonces el siguiente código:

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * Tenemos [%s].\n", *i);
PHYSFS_freeList(rc);
* Tenemos [x.sav].
* Tenemos [y.sav].
* Tenemos [z.sav].
* Tenemos [w.sav]..fi
Siéntete libre de ordenar la lista como prefieras. Sin embargo, los datos devueltos siempre contendrán duplicados y siempre se ordenarán alfabéticamente (o mejor dicho, en orden Unicode sensible a mayúsculas y minúsculas) para ti.
No olvides llamar a PHYSFS_freeList() con el valor devuelto por esta función cuando hayas terminado con él.

No puede agregar el mismo archivo a dos puntos de montaje diferentes: la comprobación de duplicados se realiza contra el archivo y no contra el punto de montaje.

Cuando monta un archivo, se agrega a un sistema de archivos virtual... todos los archivos en todos los archivos se interpolan en un único árbol de archivos jerárquico. Dos archivos montados en el mismo lugar (o un archivo con archivos que se superponen a otro punto de montaje) pueden tener archivos superpuestos: en tal caso, se selecciona el archivo anterior en la ruta de búsqueda, y los otros archivos son inaccesibles para la aplicación. Esto permite que los archivos se utilicen para anular revisiones anteriores; puede usar el mecanismo de montaje para colocar archivos en un punto específico del árbol de archivos y evitar la superposición; esto es útil para mods descargables que podrían pisotear datos de la aplicación o entre sí, por ejemplo.

El punto de montaje no necesita existir antes de montarlo, lo que es diferente de lo que esperan aquellos familiarizados con el concepto de "montar" de Unix. Además, se pueden montar más de un archivo en el mismo punto de montaje, o los puntos de montaje y el contenido de los archivos pueden superponerse... el mecanismo de interpolación sigue funcionando como de costumbre.

Se permite especificar un enlace simbólico a un archivo o directorio aquí, independientemente del estado de PHYSFS_permitSymbolicLinks(). Esa función solo trata con enlaces simbólicos dentro del directorio montado o archivo.

void PHYSFS_permitSymbolicLinks(int allow)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y archivos contienen archivos que son solo punteros a otros archivos. En el sistema de archivos físico, la apertura de dicho enlace abrirá (transparentemente) el archivo al que apunta.

Por defecto, PhysicsFS verificará si un archivo es realmente un enlace simbólico durante las llamadas de apertura y fallará si lo es. De lo contrario, el enlace podría sacarte de las rutas de escritura y búsqueda, y comprometer la seguridad.

Si deseas asumir ese riesgo, llama a esta función con un parámetro distinto de cero. Ten en cuenta que esto es más para aislar el lenguaje de scripting de un programa, en caso de que scripts no confiables intenten comprometer el sistema. En términos generales, un usuario podría tener una razón legítima para configurar un enlace simbólico, por lo que a menos que sientas que existe un peligro específico al permitirlos, deberías permitirlos.

Los enlaces simbólicos solo se verifican explícitamente cuando se tratan con nombres de archivo en notación independiente de la plataforma. Es decir, al configurar tus rutas de búsqueda y escritura, etc., los enlaces simbólicos nunca se verifican.

Ten en cuenta que PHYSFS_stat() siempre verificará la ruta especificada; si esa ruta es un enlace simbólico, no se seguirá en ningún caso. Si los enlaces simbólicos no están permitidos a través de esta función, PHYSFS_stat() los ignora y trataría la consulta como si la ruta no existiera en absoluto.

El permiso de enlace simbólico se puede habilitar o deshabilitar en cualquier momento después de haber llamado a PHYSFS_init(), y está deshabilitado por defecto.

Parámetros

allow distinto de cero para permitir enlaces simbólicos, cero para denegarlos.

void PHYSFS_utf8ToUcs4 (const char * src, PHYSFS_uint32 (*dst), PHYSFS_uint64 len)

Convert a UTF-8 string to a UCS-4 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UCS-4 strings are 32-bits per character. They are the most straightforward encoding. The downside is that they take up more space than UTF-8 for simple ASCII text.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is four times the size of the source buffer. UTF-8 uses from one to four bytes per character, but UCS-4 always uses four bytes per character. If the string contains only ASCII characters, the buffer size will increase by 400%! The UTF-8 characters that would take four bytes also take four bytes in UCS-4, so you don't need to allocate 4x the space just in case: four times the size will do.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UCS-4 sequence at the end. If the buffer length is 0, this function does nothing.

Parameters

src Null-terminated source string in UTF-8 format.
dst Buffer to store converted UCS-4 string.
len Size, in bytes, of destination buffer.

Convert a UTF-8 string to a UTF-16 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UTF-16 strings are 16-bits per character (except some chars, which are 32-bits): TCHAR on Windows, when building with Unicode support. Modern Windows releases use UTF-16. Windows releases before 2000 used TCHAR, but only handled UCS-2. UTF-16 is UCS-2, except for the characters that are 4 bytes, which aren't representable in UCS-2 at all anyhow. If you aren't sure, you should be using UTF-16 at this point on Windows.

UTF-8 uses from one to four bytes per character, but UTF-16 always uses two to four, so an entirely low-ASCII string will double in size! The UTF-16 characters that would take four bytes also take four bytes in UTF-8, so you don't need to allocate 4x the space just in case: double will do.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-16 surrogate pair at the end. If the buffer length is 0, this function does nothing.

src Null-terminated source string in UTF-8 format.
dst Buffer to store converted UTF-16 string.
