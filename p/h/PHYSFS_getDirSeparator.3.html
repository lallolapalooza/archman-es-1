typedef PHYSFS_EnumerateCallbackResult(* physfs_EnumerateCallback) (void *data, const char *origdir, const char *fname)

Possible return values from PHYSFS_EnumerateCallback. Function signature for callbacks that enumerate and return results.

These values dictate if an enumeration callback should continue to fire, or stop (and why it is stopping).

See also

PHYSFS_EnumerateCallback

PHYSFS_enumerate

This is the same thing as PHYSFS_EnumFilesCallback from PhysicsFS 2.0, except it can return a result from the callback: namely: if you're looking for something specific, once you find it, you can tell PhysicsFS to stop enumerating further. This is used with PHYSFS_enumerate(), which we hopefully got right this time. :)

Parameters

data User-defined data pointer, passed through from the API that eventually called the callback.
origdir A string containing the full path, in platform-independent notation, of the directory containing this file. In most cases, this is the directory on which you requested enumeration, passed in the callback for your convenience.
fname The filename that is being enumerated. It may not be in alphabetical order compared to other callbacks that have fired, and it will not contain the full path. You can recreate the fullpath with $origdir/$fname ... The file can be a subdirectory, a file, a symlink, etc.

Returns

A value from PHYSFS_EnumerateCallbackResult. All other values are (currently) undefined; don't use them.

typedef void(* physfs_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Function signature for callbacks that enumerate files.

Warning

As of PhysicsFS 2.1, Use PHYSFS_EnumerateCallback with PHYSFS_enumerate() instead; it gives you more control over the process.

These are used to report a list of directory entries to an original caller, one file/dir/symlink per callback. All strings are UTF-8 encoded. Functions should not try to modify or free any string's memory.

These callbacks are used, starting in PhysicsFS 1.1, as an alternative to functions that would return lists that need to be cleaned up with PHYSFS_freeList(). The callback means that the library doesn't need to allocate an entire list and all the strings up front.

Be aware that promised data ordering in the list versions are not necessarily so in the callback versions. Check the documentation on specific APIs, but strings may not be sorted as you expect and you might get duplicate strings.

Parameters

data User-defined data pointer, passed through from the API that eventually called the callback.
origdir A string containing the full path, in platform-independent notation, of the directory containing this file. In most cases, this is the directory on which you requested enumeration, passed in the callback for your convenience.
fname The filename that is being enumerated. It may not be in alphabetical order compared to other callbacks that have fired, and it will not contain the full path. You can recreate the fullpath with $origdir/$fname ... The file can be a subdirectory, a file, a symlink, etc.

enum PHYSFS_ErrorCode

Values that represent specific causes of failure. Most of the time, you should only concern yourself with whether a given operation failed or not, but there may be occasions where you plan to handle a specific failure case gracefully, so we provide specific error codes.

Most of these errors are a little vague, and most aren't things you can fix...if there's a permission error, for example, all you can really do is pass that information on to the user and let them figure out how to handle it. In most these cases, your program should only care that it failed to accomplish its goals, and not care specifically why.

int PHYSFS_enumerate(const char *dir, PHYSFS_EnumerateCallback c, void *d)

Obtener una lista de archivos de una carpeta de la ruta de búsqueda, utilizando un callback definido por la aplicación, con errores reportados. Internamente, PHYSFS_enumerateFiles() solo llama a esta función y luego construye una lista antes de devolver a la aplicación, así que la funcionalidad es idéntica, excepto por cómo la información se presenta a la aplicación.

Aunque PHYSFS_enumerateFiles() no devuelve un array, esta función llama a una función especificada por la aplicación una vez por cada elemento de la ruta de búsqueda:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // dame más datos, por favor.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Los elementos enviados al callback no están garantizados para estar en ningún orden. No se realiza ninguna ordenación en este nivel, y si necesitas eso, deberías usar PHYSFS_enumerateFiles(), que garantiza la ordenación alfabética. Esta forma reporta lo que se encuentra en cada archive antes de moverse al siguiente. Incluso dentro de un archive, no podemos garantizar el orden en que se descubren los datos. Cualquier ordenación que encuentres en estos callbacks es pura suerte. No dependas de ella. Como esta función recorre toda la lista de archivos, podrías recibir nombres de archivo duplicados.

Esta API y los propios callbacks son capaces de reportar errores. Antes de esta API, los callbacks tenían que aceptar cada elemento enumerado, incluso si solo buscaban un objeto específico y querían detenerse allí, o tenían un error grave y no podían notificar a nadie. Además, si PhysicsFS tenía un problema (error de disco o lo que fuera), no podía reportarlo a la aplicación que lo llamaba; simplemente tendría que saltarse elementos o detener la enumeración por completo, y el llamador no sabría que había perdido algunos datos en el camino.

Ahora el llamador puede asegurarse de haber obtenido un conjunto completo de datos, y si quiere detener la enumeración de forma temprana, su callback tiene el control. Consulta el documento de PHYSFS_EnumerateCallback para obtener detalles sobre cómo debe comportarse tu callback.

c Función de callback para notificar sobre elementos de la ruta de búsqueda.
d Datos definidos por el usuario pasados al callback. Puede ser NULL.

Devuelve

Distinto de cero en caso de éxito, cero en caso de fallo. Usa PHYSFS_getLastErrorCode() para obtener el error específico. Si el callback devuelve PHYSFS_ENUM_STOP para detenerse de forma temprana, esto se considera un éxito. char **PHYSFS_enumerateFiles(const char *dir)

Obtener una lista de archivos de una carpeta de la ruta de búsqueda.

Nota

En versiones de PhysicsFS anteriores a la 2.1, esta función devolvería tantos elementos como fuera posible en caso de fallo (error de memoria, error de E/S de disco, etc.). Esto significaba que los programas no podían distinguir entre un éxito completo y un fallo parcial, y dado que la función podía devolver NULL para informar de un fallo catastrófico, en PhysicsFS 2.1 esta política cambió: devolverá una lista completa de resultados o devolverá NULL en caso de cualquier fallo, de modo que podamos garantizar que la enumeración se completó y no haya lagunas en sus resultados.

Las carpetas que coinciden se interpolan. Es decir, si "C:\mydir" está en la ruta de búsqueda y contiene una carpeta "savegames" que contiene "x.sav", "y.sav" y "z.sav", y también existe una "C:\userdir" en la ruta de búsqueda que contiene una subcarpeta "savegames" con "w.sav", entonces el siguiente código:

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);
PHYSFS_freeList(rc);
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..

No olvide llamar PHYSFS_freeList() con el valor devuelto por esta función cuando haya terminado con él.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Añadir un archivo o directorio a la ruta de búsqueda. Si es un duplicado, la entrada no se añade de nuevo, incluso si la función es exitosa. No puedes añadir el mismo archivo a dos puntos de montaje diferentes: la verificación de duplicados se realiza contra el archivo y no contra el punto de montaje.

Al montar un archivo, se añade a un sistema de archivos virtual... todos los archivos de todos los archivos montados se interpolan en un único árbol jerárquico. Dos archivos montados en el mismo lugar (o un archivo con archivos que se superponen a un punto de montaje) pueden tener archivos superpuestos: en ese caso, el archivo más temprano en la ruta de búsqueda es seleccionado, y los otros archivos no son accesibles por la aplicación. void PHYSFS_permitSymbolicLinks (int allow)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y archivos contienen archivos que son solo punteros a otros archivos. En el sistema de archivos físico, abrir un enlace de este tipo abrirá (transparentemente) el archivo al que apunta.

Por defecto, PhysicsFS verificará si un archivo es realmente un enlace simbólico durante las llamadas de apertura y fallará si lo es. De lo contrario, el enlace podría llevarte fuera de las rutas de escritura y búsqueda, y comprometer la seguridad.

Si quieres asumir ese riesgo, llama a esta función con un parámetro distinto de cero. Ten en cuenta que esto es más para aislar el lenguaje de scripting de un programa, en caso de que scripts no confiables intenten comprometer el sistema. En términos generales, un usuario podría tener una razón legítima para configurar un enlace simbólico, por lo que, a menos que sientas que hay un peligro específico al permitirlos, deberías permitirlos.

Los enlaces simbólicos solo se verifican explícitamente cuando se trata con nombres de archivo en notación independiente de la plataforma. Es decir, al configurar tus rutas de búsqueda y escritura, etc., nunca se verifican los enlaces simbólicos.

Ten en cuenta que PHYSFS_stat() siempre verificará la ruta especificada; si esa ruta es un enlace simbólico, no se seguirá en ningún caso. Si los enlaces simbólicos no están permitidos a través de esta función, PHYSFS_stat() los ignora y trataría la consulta como si la ruta no existiera en absoluto.

El permiso de enlace simbólico se puede habilitar o deshabilitar en cualquier momento después de haber llamado a PHYSFS_init(), y está deshabilitado por defecto.

allow distinto de cero para permitir enlaces simbólicos, cero para denegarlos.

int PHYSFS_setRoot (const char * archive, const char * subdir)

int PHYSFS_setSaneConfig (const char * organization, const char * appName, const char * archiveExt, int includeCdRoms, int archivesFirst)

Configura rutas predeterminadas y razonables. Función auxiliar.

El directorio de escritura se establecerá en el directorio de preferencias devuelto por

PHYSFS_getPrefDir(organization, appName)

, que se crea si no existe.

Lo anterior es suficiente para asegurar que el directorio de configuración de su programa esté separado de otro desorden, y sea independiente de la plataforma.

La ruta de búsqueda será:

  • El Directorio de Escritura (creado si no existe)
  • El Directorio Base (PHYSFS_getBaseDir())
  • Todos los directorios de CD-ROM encontrados (opcionalmente)

Estos directorios se buscan luego archivos que terminan con la extensión (archiveExt), que, si son archivos válidos y compatibles, también se agregarán a la ruta de búsqueda. Si especificó "PKG" para (archiveExt), y hay un archivo llamado data.PKG en el directorio base, se verificará. Los archivos pueden agregarse o anteponerse a la ruta de búsqueda en orden alfabético, independientemente de los directorios en los que se encontraron. Todos los archivos se montan en la raíz del sistema de archivos virtual ("/").

Todo esto puede ser realizado por la aplicación, pero esto simplemente lo hace todo por usted. Siéntase libre de agregar más a la ruta de búsqueda manualmente también.

Parámetros

organization Nombre de su empresa/grupo/etc. que se utilizará como nombre de directorio, así que manténgalo pequeño y sin adornos.
appName Nombre específico del programa, para separarlo de otros programas que usan PhysicsFS.
archiveExt Extensión de archivo utilizada por su programa para especificar un archivo. Por ejemplo, Quake 3 usa "pk3", aunque solo sean archivos zip. Nota: aunque (len) es un entero sin signo de 64 bits, estás limitado a 63 bits (9223372036854775807 bytes), por lo que podemos devolver un valor negativo en caso de error. Si la longitud es mayor que 0x7FFFFFFFFFFFFFFF, esta función fallará inmediatamente. Para sistemas sin tipos de 64 bits, estás limitado a 31 bits (0x7FFFFFFF, o 2147483647 bytes). Confiamos en que casi nada necesite realizar E/S de varios gigabytes en una sola llamada, ¡pero ¿por qué limitar las cosas?

Parámetros

handle Valor devuelto por PHYSFS_openWrite() o PHYSFS_openAppend().
buffer Búfer de (len) bytes a escribir (handle).
len Número de bytes a escribir (handle).

Retorna

Número de bytes escritos. Esto puede ser menor que (len); en caso de error, el sistema puede intentar escribir tantos bytes como sea posible, por lo que podría ocurrir una escritura incompleta. PHYSFS_getLastErrorCode() puede proporcionar información sobre la razón por la que este resultado es < (len). -1 si hay un fallo total.
