DESCRIPTION

The functions documented in this man page provide access to the PhysicsFS library, a library that aims to provide a platform-independent API for accessing files in a game.

PhysicsFS allows an application to treat archives (like zip files) as directories, and can merge multiple directories and archives into a single virtual filesystem.

The functions are grouped into logical sections:

  • Byte-swapping: Functions to swap byte orders between little-endian, big-endian, and the platform's native byte order. These are useful for reading and writing data files that need to be portable across different architectures.
  • Reading and writing integers: Functions to read and write integers (16, 32, and 64 bits, signed and unsigned) from and to PhysicsFS file handles, handling byte-swapping automatically.
  • Initialization and cleanup: Functions to initialize and shut down the PhysicsFS library.
  • Mounting and unmounting archives: Functions to add and remove directories and archives from PhysicsFS's search path.
  • Directory and file enumeration: Functions to list the contents of directories within the PhysicsFS search path.
  • String conversion and comparison: Functions for converting strings between different character encodings (UTF-8, UCS-2, UCS-4, Latin-1) and performing case-insensitive comparisons.
  • File handling: Low-level functions for reading and writing raw bytes to PhysicsFS file handles.
  • Error handling: Functions to retrieve error codes and their descriptions.
  • Allocator management: Functions to set and get the memory allocator used by PhysicsFS.
  • Archiver management: Functions to register and deregister custom archive types.
  • Configuration: Functions to get the preferred directory for configuration files and to control symbolic link handling.

It is essential to initialize PhysicsFS using PHYSFS_init() before calling most other functions, and to deinitialize it using PHYSFS_deinit() when your application exits.

The byte-swapping functions (e.g., PHYSFS_swapSLE32) convert values between little-endian and the platform's native byte order. If the platform is already little-endian, these functions are no-ops. Similarly, the big-endian functions (e.g., PHYSFS_swapSBE16) convert values to and from big-endian format.

The read and write functions (e.g., PHYSFS_readSLE16, PHYSFS_writeULE32) simplify the process of reading and writing numerical data from/to files, automatically handling the necessary byte swapping based on the specified endianness.

PHYSFS_mount() adds a directory or archive to the search path. The `mountPoint` argument specifies where in the virtual filesystem this new directory/archive should appear. If `mountPoint` is NULL, it's mounted at the root. If `appendToPath` is non-zero, this mount takes precedence over existing mounts at the same location.

PHYSFS_getMountPoint() returns the mount point for a given directory within the search path.

Callbacks provided by PHYSFS_getCdRomDirsCallback(), PHYSFS_getSearchPathCallback(), and PHYSFS_enumerateFilesCallback() allow applications to iterate over directories, the search path, and the contents of directories, respectively, without needing to manually manage file handles.

The UTF-8 conversion functions (PHYSFS_utf8FromUcs4, PHYSFS_utf8ToUcs4, PHYSFS_utf8FromUcs2, PHYSFS_utf8ToUcs2, PHYSFS_utf8FromLatin1, PHYSFS_utf8FromUtf16, PHYSFS_utf8ToUtf16) provide a way to translate strings between different character encodings commonly used in internationalization.

Case-insensitive string comparison functions like PHYSFS_utf8stricmp() are provided for comparing strings that may contain different casing but should be considered equivalent.

PHYSFS_readBytes() and PHYSFS_writeBytes() offer direct control over reading and writing raw data to and from a file handle.

PHYSFS_mountIo(), PHYSFS_mountMemory(), and PHYSFS_mountHandle() provide flexible ways to mount archives from various sources, including custom I/O objects, memory buffers, and existing file handles.

PHYSFS_getLastErrorCode() and PHYSFS_getErrorByCode() are crucial for diagnosing and reporting errors that occur within the PhysicsFS library.

PHYSFS_setErrorCode() allows an application to manually set the error code for the current thread.

PHYSFS_getPrefDir() is a convenient way to obtain the user-and-app-specific directory where preference files or other user data can be safely stored.

PHYSFS_registerArchiver() and PHYSFS_deregisterArchiver() allow extending PhysicsFS to support custom archive formats beyond the built-in ones.

PHYSFS_setRoot() changes the root directory for a specific archive, effectively making a subdirectory of that archive appear as the top level.

The `PHYSFS_file` macro is a compatibility define for the older `PHYSFS_File` type. New code should use `PHYSFS_File` directly.

RETURN VALUES

Most functions return an integer value. A non-zero return value typically indicates success, while a zero return value indicates failure. When a function fails, the specific error can be retrieved using PHYSFS_getLastErrorCode().

Functions that return pointers typically return NULL on failure.

Callback functions provided to PhysicsFS should return 0 to continue processing and 1 to stop.

Functions returning PHYSFS_sint64 indicate the number of bytes read or written, or -1 on error.

Firma de función para callbacks que enumeran archivos.

Advertencia

A partir de PhysicsFS 2.1, use PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; le da más control sobre el proceso.

Estos se utilizan para informar una lista de entradas de directorio a un llamador original, un archivo/directorio/enlace simbólico por callback. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de ninguna cadena.

Estos callbacks se utilizan, a partir de PhysicsFS 1.1, como una alternativa a las funciones que devolverían listas que deben limpiarse con PHYSFS_freeList(). El callback significa que la biblioteca no necesita asignar una lista completa y todas las cadenas por adelantado.

Tenga en cuenta que el orden de los datos prometido en las versiones de lista no es necesariamente así en las versiones de callback. Consulte la documentación de las API específicas, pero es posible que las cadenas no estén ordenadas como espera y que reciba cadenas duplicadas.

Deinitialize the PhysicsFS library. This closes any files opened via PhysicsFS, blanks the search/write paths, frees memory, and invalidates all of your file handles.

int PHYSFS_delete(const char *filename)

Delete a file or directory. (filename) is specified in platform-independent notation in relation to the write dir.

A directory must be empty before this call can delete it.

Deleting a symlink will remove the link, not what it points to, regardless of whether you "permitSymLinks" or not.

So if you've got the write dir set to "C:\mygame\writedir" and call PHYSFS_delete("downloads/maps/level1.map") then the file "C:\mygame\writedir\downloads\maps\level1.map" is removed from the physical filesystem, if it exists and the operating system permits the deletion.

Note that on Unix systems, deleting a file may be successful, but the actual file won't be removed until all processes that have an open filehandle to it (including your program) close their handles.

Chances are, the bits that make up the file still exist, they are just made available to be written over at a later point. Don't consider this a security method or anything. :)

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtiene una lista de archivos del directorio de una ruta de búsqueda, utilizando una devolución de llamada definida por la aplicación, con errores informados. Internamente, PHYSFS_enumerateFiles() simplemente llama a esta función y luego crea una lista antes de devolverla a la aplicación, por lo que la funcionalidad es idéntica excepto por cómo se representa la información a la aplicación.

A diferencia de PHYSFS_enumerateFiles(), esta función no devuelve una matriz. En su lugar, llama a una función especificada por la aplicación una vez por cada elemento de la ruta de búsqueda:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Tenemos [%s] en [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // dame más datos, por favor.
}
// ...
PHYSFS_enumerate("/alguna/ruta", printDir, NULL);

No se garantiza que los elementos enviados a la devolución de llamada estén en ningún orden particular. No se realiza ninguna ordenación a este nivel, y si la necesita, probablemente debería usar PHYSFS_enumerateFiles() en su lugar, que garantiza la ordenación alfabética. Esta forma informa lo que se descubre en cada archivo antes de pasar al siguiente. Incluso dentro de un archivo, no podemos garantizar el orden en que descubrirá los datos. *Cualquier ordenación que encuentre en estas devoluciones de llamada es pura suerte. No dependa de ella*. A medida que recorre toda la lista de archivos, puede recibir nombres de archivo duplicados.

Esta API y las propias devoluciones de llamada son capaces de informar errores. Antes de esta API, las devoluciones de llamada tenían que aceptar todos los elementos enumerados, incluso si solo buscaban algo específico y querían detenerse después de eso, o si tenían un error grave y no podían alertar a nadie. Además, si PhysicsFS en sí tenía un problema (error de disco o similar), no podía informarlo a la aplicación que llamaba, solo tenía que omitir elementos o dejar de enumerar por completo, y el que llamaba no sabría que había perdido algunos datos en el camino.

Ahora el que llama puede estar seguro de que obtuvo un conjunto de datos completo, y su devolución de llamada tiene control si desea que la enumeración se detenga temprano. Consulte la documentación de PHYSFS_EnumerateCallback para obtener detalles sobre cómo debe comportarse su devolución de llamada.

dir Directorio, en notación independiente de la plataforma, a enumerar.
c Función de devolución de llamada para notificar sobre los elementos de la ruta de búsqueda.
d Datos definidos por la aplicación pasados a la devolución de llamada. Puede ser NULL.

Devuelve

Distinto de cero en caso de éxito, cero en caso de fallo. Use PHYSFS_getLastErrorCode() para obtener el error específico. const char *PHYSFS_getPrefDir (const char * org, const char * app)

Obtener la ruta de directorio específica para archivos en los que se puede escribir. Función de ayuda.

Obtener el "pref dir". Este es el lugar donde los usuarios pueden escribir archivos personales (preferencias y partidas guardadas, etc.) específicos de su aplicación. Este directorio es único por usuario y por aplicación.

Esta función decide la ubicación adecuada en el sistema de archivos nativo, crea el directorio si es necesario y devuelve una cadena en notación independiente de la plataforma, adecuada para pasar a PHYSFS_setWriteDir().

En Linux, podría verse como: "/home/bob/.local/share/My Program Name"

En Mac OS X, podría verse como: "/Users/bob/Library/Application Support/My Program Name"

(etc.)

Deberías usar el pref dir para tu ruta de escritura, y también colocarlo al principio de tu lista de búsqueda. Versiones antiguas de PhysicsFS solo ofrecían PHYSFS_getUserDir() y dejaban que tu aplicación decidiera dónde colocar los archivos bajo esa carpeta. Esta encuentra la ubicación correcta para cualquier plataforma, que no solo cambia entre sistemas operativos, sino también entre versiones del mismo sistema operativo.

  • Usa la misma cadena de organización (incluido el caso sensible) para todas tus aplicaciones que utilicen esta función.
  • Usa una cadena de aplicación única para cada una, y asegúrate de que no cambie para una aplicación después de haber decidido el nombre.
  • Los caracteres Unicode son válidos, siempre que estén codificados como UTF-8, pero...
  • ... usa solo letras, números y espacios. Evita puntos como "Nombre del Juego 2: ¡La Venganza del Malo!" ... "Nombre del Juego 2" es suficiente.

El puntero devuelto por esta función permanece válido hasta que lo llames de nuevo o llames a PHYSFS_deinit(). No es necesariamente una llamada rápida, así que deberías llamarla una vez al inicio y copiar la cadena si la necesitas.

int PHYSFS_mount(const char *newDir, const char *mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

Parameters

newDir directory or archive to add to the path, in platform-dependent notation.
mountPoint Location in the interpolated tree that this archive will be "mounted", in platform-independent notation. NULL or "" is equivalent to "/".
appendToPath nonzero to append to search path, zero to prepend.

Returns

nonzero if added to path, zero on failure (bogus archive, dir missing, etc). Use PHYSFS_getLastErrorCode() to obtain the specific error.

void PHYSFS_permitSymbolicLinks (int allow)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y archivos contienen archivos que son solo punteros a otros archivos. En el sistema de archivos físico, la apertura de dicho enlace abrirá (transparentemente) el archivo al que apunta.

Por defecto, PhysicsFS comprobará si un archivo es realmente un enlace simbólico durante las llamadas de apertura y fallará si lo es. De lo contrario, el enlace podría llevarte fuera de las rutas de escritura y búsqueda, y comprometer la seguridad.

Si quieres asumir ese riesgo, llama a esta función con un parámetro distinto de cero. Ten en cuenta que esto es más para aislar el lenguaje de scripting de un programa, en caso de que scripts no confiables intenten comprometer el sistema. En términos generales, un usuario podría tener una razón legítima para configurar un enlace simbólico, por lo que a menos que sientas que hay un peligro específico al permitirlos, deberías permitirlos.

Los enlaces simbólicos solo se comprueban explícitamente cuando se trata con nombres de archivo en notación independiente de la plataforma. Es decir, al configurar tus rutas de búsqueda y escritura, etc., nunca se comprueban los enlaces simbólicos.

Por favor, ten en cuenta que PHYSFS_stat() siempre comprobará la ruta especificada; si esa ruta es un enlace simbólico, no se seguirá en ningún caso. Si los enlaces simbólicos no están permitidos a través de esta función, PHYSFS_stat() los ignora y trataría la consulta como si la ruta no existiera en absoluto.

El permiso de enlace simbólico se puede habilitar o deshabilitar en cualquier momento después de haber llamado a PHYSFS_init(), y está deshabilitado por defecto.

Parámetros

allow distinto de cero para permitir enlaces simbólicos, cero para denegar el enlace.

int PHYSFS_setSaneConfig (const char * organization, const char * appName, const char * archiveExt, int includeCdRoms, int archivesFirst)

Configura rutas predeterminadas y sensatas. Función de ayuda.

El directorio de escritura se establecerá en el directorio de preferencias devuelto por

PHYSFS_getPrefDir(organization, appName)

, que se crea si no existe.

Lo anterior es suficiente para asegurar que el directorio de configuración de su programa esté separado de otro desorden y sea independiente de la plataforma.

La ruta de búsqueda será:

  • El Directorio de Escritura (creado si no existe)
  • El Directorio Base (PHYSFS_getBaseDir())
  • Todos los directorios de CD-ROM encontrados (opcionalmente)

Si especificó "PKG" para (archiveExt), y hay un archivo llamado data.PKG en el directorio base, se verificará. Todos los archivos se montan en la raíz del sistema de archivos virtual ("/").

Todo esto se puede lograr desde la aplicación, pero esto simplemente lo hace todo por usted. Siéntase libre de agregar más a la ruta de búsqueda manualmente también.

archiveExt Extensión de archivo utilizada por su programa para especificar un archivo. Por ejemplo, Quake 3 usa "pk3", aunque son solo archivos zip. Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

If you aren't sure, you should be using UTF-16 at this point on Windows.

UTF-8 uses from one to four bytes per character, but UTF-16 always uses two to four, so an entirely low-ASCII string will double in size! The UTF-16 characters that would take four bytes also take four bytes in UTF-8, so you don't need to allocate 4x the space just in case: double will do.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-16 surrogate pair at the end. If the buffer length is 0, this function does nothing.

src Null-terminated source string in UTF-8 format.
dst Buffer to store converted UTF-16 string.
len Size, in bytes, of destination buffer.

PHYSFS_writeBytes

PHYSFS_sint64 PHYSFS_writeBytes (PHYSFS_File * handle, const void * buffer, PHYSFS_uint64 len)

Escribe datos en un manejador de archivos PhysicsFS. El archivo debe estar abierto para escritura.

Por favor, ten en cuenta que aunque (len) es un entero sin signo de 64 bits, estás limitado a 63 bits (9223372036854775807 bytes), por lo que podemos devolver un valor negativo en caso de error. Si la longitud es mayor que 0x7FFFFFFFFFFFFFFF, esta función fallará inmediatamente. Para sistemas sin un tipo de dato de 64 bits, estás limitado a 31 bits (0x7FFFFFFF, o 2147483647 bytes). Confiamos en que la mayoría de las cosas no necesitarán realizar múltiples gigabytes de E/S en una sola llamada, pero ¿por qué limitar las cosas?

Devuelve

número de bytes escritos. Esto puede ser menor que (len); en caso de error, el sistema puede intentar escribir tantos bytes como sea posible, por lo que puede ocurrir una escritura incompleta.
