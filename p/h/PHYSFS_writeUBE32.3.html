struct PHYSfs.h: PHYSFS_Version

Used to track the version of PhysicsFS that you are using.

This structure is used to store the major, minor, and patch level of the library. It is used in conjunction with the PHYSFS_VERSION macro to check that the version of the library you are using at compile time is compatible with the version of the library you compiled against. This is determined by what header the compiler uses. Note that if you dynamically linked the library, you might have a slightly newer or older version at runtime. That version can be determined with PHYSFS_getLinkedVersion(), which, unlike PHYSFS_VERSION, is not a macro.

Parameters

x A pointer to a PHYSFS_Version struct to initialize.

typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Function signature for callbacks that enumerate files.

Warning

As of PhysicsFS 2.1, Use PHYSFS_EnumerateCallback with PHYSFS_enumerate() instead; it gives you more control over the process.

These are used to report a list of directory entries to an original caller, one file/dir/symlink per callback. All strings are UTF-8 encoded. Functions should not try to modify or free any string's memory.

These callbacks are used, starting in PhysicsFS 1.1, as an alternative to functions that would return lists that need to be cleaned up with PHYSFS_freeList(). The callback means that the library doesn't need to allocate an entire list and all the strings up front.

Be aware that promised data ordering in the list versions are not necessarily so in the callback versions. Check the documentation on specific APIs, but strings may not be sorted as you expect and you might get duplicate strings.

Parameters

data User-defined data pointer, passed through from the API that eventually called the callback.
origdir A string containing the full path, in platform-independent notation, of the directory containing this file. In most cases, this is the directory on which you requested enumeration, passed in the callback for your convenience.
fname The filename that is being enumerated. It may not be in alphabetical order compared to other callbacks that have fired, and it will not contain the full path. You can recreate the fullpath with $origdir/$fname ... The file can be a subdirectory, a file, a symlink, etc.

enum PHYSFS_ErrorCode

Values that represent specific causes of failure. Most of the time, you should only concern yourself with whether a given operation failed or not, but there may be occasions where you plan to handle a specific failure case gracefully, so we provide specific error codes.

Most of these errors are a little vague, and most aren't things you can fix...if there's a permission error, for example, all you can really do is pass that information on to the user and let them figure out how to handle it. In most these cases, your program should only care that it failed to accomplish its goals, and not care specifically why.

void PHYSFS_deregisterArchiver (const char * ext)

Deregister an archiver. This means that PhysicsFS will no longer attempt to open archives with the given filename extension.

If you deregister an archiver that was handling a currently open archive, that archive will remain open, but it will not be able to handle any subsequent requests. This is generally not a problem, as PhysicsFS tries to deregister all of its own archivers automatically when it shuts down cleanly. This is mainly useful if you want to unload archivers on the fly, or if you want to prevent PhysicsFS from automatically deregistering all archivers, so you don't need to explicitly deregister yours if you otherwise shut down cleanly.

Parámetros

ext Extensión de nombre de archivo que maneja el archivador.

Retorna

Cero en caso de error, distinto de cero en caso de éxito.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtener una lista de archivos de un directorio de ruta de búsqueda, utilizando una devolución de llamada definida por la aplicación, con errores informados. Internamente, PHYSFS_enumerateFiles() simplemente llama a esta función y luego crea una lista antes de devolverla a la aplicación, por lo que la funcionalidad es idéntica excepto por cómo se representa la información a la aplicación.

A diferencia de PHYSFS_enumerateFiles(), esta función no devuelve una matriz. Más bien, llama a una función especificada por la aplicación una vez por cada elemento de la ruta de búsqueda:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Tenemos [%s] en [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // dame más datos, por favor.
}
// ...
PHYSFS_enumerate("/algun/ruta", printDir, NULL);

No se garantiza que los elementos enviados a la devolución de llamada estén en ningún orden específico. No se realiza ningún ordenamiento en este nivel, y si lo necesita, probablemente debería usar PHYSFS_enumerateFiles() en su lugar, lo que garantiza un ordenamiento alfabético. Esta forma informa lo que se descubre en cada archivo antes de pasar al siguiente. Incluso dentro de un archivo, no podemos garantizar el orden en que descubrirá los datos. *Cualquier ordenamiento que encuentre en estas devoluciones de llamada es pura suerte. No confíe en él.* A medida que recorre toda la lista de archivos, puede recibir nombres de archivo duplicados.

Esta API y las propias devoluciones de llamada son capaces de informar errores. Antes de esta API, las devoluciones de llamada tenían que aceptar cada elemento enumerado, incluso si solo buscaban algo específico y querían detenerse después de eso, o tenían un error grave y no podían alertar a nadie. Además, si PhysicsFS en sí mismo tenía un problema (error de disco o similar), no podía informarlo a la aplicación que lo llamaba, solo tendría que omitir elementos o dejar de enumerar por completo, y el llamador no sabría que había perdido algunos datos en el camino.

Ahora el llamador puede estar seguro de que obtuvo un conjunto de datos completo, y su devolución de llamada tiene control si desea que la enumeración se detenga antes. Consulte la documentación de PHYSFS_EnumerateCallback para obtener detalles sobre cómo debe comportarse su devolución de llamada.

Parámetros

dir Directorio, en notación independiente de la plataforma, a enumerar.
c Función de devolución de llamada para notificar sobre los elementos de la ruta de búsqueda.
d Datos definidos por la aplicación pasados a la devolución de llamada. Puede ser NULL.

Retorna

Distinto de cero en caso de éxito, cero en caso de fallo. Utilice PHYSFS_getLastErrorCode() para obtener el error específico. Si la devolución de llamada devuelve PHYSFS_ENUM_STOP para detenerse antes, esto se considerará un éxito. Las devoluciones de llamada que devuelvan PHYSFS_ENUM_ERROR harán que esta función devuelva cero y establezcan el código de error en PHYSFS_ERR_APP_CALLBACK.

char ** PHYSFS_enumerateFiles (const char * dir)

Obtener una lista de archivos de un directorio de ruta de búsqueda.

Advertencia

En las versiones de PhysicsFS anteriores a la 2.1, esta función devolvía tantos elementos como podía ante una condición de fallo (falta de memoria, error de E/S de disco, etc.). Dado que esto significaba que las aplicaciones no podían distinguir entre éxito completo y fallo parcial, y dado que la función siempre podía devolver NULL para informar fallos catastróficos de todos modos, en PhysicsFS 2.1 la política de esta función cambió: devolverá una lista de resultados completos o devolverá NULL para cualquier fallo de cualquier tipo, de modo que podamos garantizar que la enumeración se completó y no tiene lagunas en sus resultados.

Los directorios coincidentes se interpolan. Es decir, si "C:\mydir" está en la ruta de búsqueda y contiene un directorio "savegames" que contiene "x.sav", "y.sav" y "z.sav", y también hay un "C:\userdir" en la ruta de búsqueda que tiene un subdirectorio "savegames" con "w.sav", entonces el siguiente código:

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * Tenemos [%s].\n", *i);
PHYSFS_freeList(rc);
* Tenemos [x.sav].
* Tenemos [y.sav].
* Tenemos [z.sav].
* Tenemos [w.sav]..fi
Siéntase libre de ordenar la lista como prefiera. Sin embargo, los datos
    devueltos siempre estarán libres de duplicados y siempre estarán ordenados
    alfabéticamente (o mejor dicho: ordenados por Unicode sensible a
    mayúsculas/minúsculas) para usted.
No olvide llamar a PHYSFS_freeList() con el valor de retorno de
    esta función cuando haya terminado con él.
Parámetros
dir directorio en notación independiente de la plataforma a enumerar. 
Retorna
Matriz terminada en nulo de cadenas terminadas en nulo, o NULL para casos
    de error.

int PHYSFS_getLastErrorCode (void )

Get the last error code that was reported by any PhysicsFS function. All PhysicsFS functions set the thread-specific error code when they fail. This function returns that code.

It is important to note that the error code is per-thread. If you have multiple threads calling PhysicsFS functions, each thread will maintain its own error code. This means that if thread A calls a function that fails, and then thread B calls a function that succeeds, thread A's error code will remain unchanged.

The error code is also reset to `PHYSFS_ERR_OK` (0) when a function succeeds. This means that if you call a function that fails, and then call a function that succeeds, the error code from the second call will be `PHYSFS_ERR_OK`.

This means you should *always* check the return value of a PhysicsFS function *before* calling any other PhysicsFS function. Calling one will wipe out the other's error state. If you need both, call PHYSFS_getLastErrorCode(), then pass that value to PHYSFS_getErrorByCode().

Generally, applications should only concern themselves with whether a given function failed; however, if you require more specifics, you can try this function to glean information, if there's some specific problem you're expecting and plan to handle. But with most things that involve file systems, the best course of action is usually to give up, report the problem to the user, and let them figure out what should be done about it. For that, you might prefer PHYSFS_getErrorByCode() instead.

Enumeration value that represents the last reported error.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

Si bien un PHYSFS_File puede buscar incluso cuando los datos están comprimidos, puede hacerlo rebobinando al principio y descomprimiendo todo antes del punto de búsqueda. Agrega un archivo, construido sobre un PHYSFS_Io, a la ruta de búsqueda.

Advertencia

A menos que tenga alguna necesidad especial de bajo nivel, debería usar PHYSFS_mount() en lugar de esto.

Esta función opera igual que PHYSFS_mount(), pero toma un PHYSFS_Io en lugar de una ruta. En segundo plano, PHYSFS_mount() llama a esta función con un PHYSFS_Io basado en el sistema de archivos físico.

(newDir) debe ser una cadena única para identificar este archivo. Se utiliza para optimizar la selección del archivador (si lo nombra XXXXX.zip, podríamos intentar primero el archivador ZIP, por ejemplo, o elegir directamente un archivador que solo pueda confiar en que los datos son válidos por la extensión del nombre del archivo). No necesita referirse a un archivo real en absoluto. Si la extensión del nombre del archivo no es útil, el sistema intentará cada archivador hasta que uno funcione o ninguno lo haga. Este nombre de archivo debe ser único, ya que el sistema no le permitirá tener dos archivos con el mismo nombre.

(io) debe permanecer hasta que el archivo se desmonte. Cuando el archivo se desmonte, el sistema llamará a (io)->destroy(io), lo que le dará la oportunidad de liberar sus recursos.

Si esta función falla, no se llama a (io)->destroy(io).

Parámetros

io instancia de E/S para el archivo que se agregará a la ruta.
newDir Nombre de archivo que puede representar este flujo.
mountPoint Ubicación en el árbol interpolado donde se "montará" este archivo, en notación independiente de la plataforma. NULL o "" es equivalente a "/".
appendToPath distinto de cero para agregar a la ruta de búsqueda, cero para anteponer.

Devuelve

distinto de cero si se agregó a la ruta, cero en caso de falla (archivo no válido, problema de E/S del flujo, etc.). Use PHYSFS_getLastErrorCode() para obtener el error específico.

void PHYSFS_permitSymbolicLinks (int allow)

Enable or disable the following of symbolic links. Some physical filesystems and archives contain files that are just pointers to other files. On the physical filesystem, opening such a link will (transparently) open the file that is pointed to.

By default, PhysicsFS will check if a file is a symlink during open calls and fail if it is. Otherwise, the link could take you outside the write and search paths, and compromise security.

If you want to take that risk, call this function with a non-zero parameter. Note that this is more for sandboxing a program's scripting language, in case untrusted scripts try to compromise the system. Generally speaking, a user could very well have a legitimate reason to set up a symlink, so unless you feel there's a specific danger in allowing them, you should permit them.

Symlinks are only explicitly checked when dealing with filenames in platform-independent notation. That is, when setting up your search and write paths, etc, symlinks are never checked for.

Please note that PHYSFS_stat() will always check the path specified; if that path is a symlink, it will not be followed in any case. If symlinks aren't permitted through this function, PHYSFS_stat() ignores them, and would treat the query as if the path didn't exist at all.

Symbolic link permission can be enabled or disabled at any time after you've called PHYSFS_init(), and is disabled by default.

Parameters

allow nonzero to permit symlinks, zero to deny linking.

See also

PHYSFS_symbolicLinksPermitted

Compara dos cadenas UTF-8 de forma insensible a mayúsculas y minúsculas. Esta es una sustitución de strcasecmp/stricmp que espera que ambas cadenas estén en formato UTF-8. Realizará un "corte de mayúsculas/minúsculas" para determinar si los códigos Unicode en las cadenas son iguales.

Si ambas cadenas son solo caracteres de bajo ASCII, esto hará lo correcto, ya que también es UTF-8 válido. Si hay caracteres de alto ASCII, ¡esto no hará lo que esperas!

La mayoría de los casos debería tratar el valor devuelto como "igual" o "no igual".

Al igual que stricmp, esta función espera que ambas cadenas estén terminadas en nulo.

str1 Cadena a comparar.
str2 Cadena a comparar.

Retornar

-1 si str1 es "menor que" str2, 1 si es "mayor que", 0 si son iguales.

NAME

PHYSFS_writeUBE16, PHYSFS_writeUBE32, PHYSFS_writeUBE64, PHYSFS_writeULE16, PHYSFS_writeULE32, PHYSFS_writeULE64 - Convert and write endian specific values to a PhysicsFS archive.

SYNOPSIS

#include <physfs.h>

int PHYSFS_writeUBE16(PHYSFS_File * file, PHYSFS_uint16 val);

int PHYSFS_writeUBE32(PHYSFS_File * file, PHYSFS_uint32 val);

int PHYSFS_writeUBE64(PHYSFS_File * file, PHYSFS_uint64 val);

int PHYSFS_writeULE16(PHYSFS_File * file, PHYSFS_uint16 val);

int PHYSFS_writeULE32(PHYSFS_File * file, PHYSFS_uint32 val);

int PHYSFS_writeULE64(PHYSFS_File * file, PHYSFS_uint64 val);

Detailed Description

These functions are all convenience functions that convert a value from the platform's native byte order to the specified endianness and then write it to the given file handle.

The platform's native byte order is used for all standard I/O operations in PhysicsFS, so this is useful for writing data to files that need to be portable across different architectures.

For example, if you are writing a file format that specifies unsigned 16-bit integers in big-endian order, and your machine is little-endian, you would use PHYSFS_writeUBE16.

All of these functions are equivalent to calling PHYSFS_write with the correctly endian-swapped data.

The return value indicates success or failure. On failure, you can find out what went wrong from PHYSFS_getLastErrorCode().

Note that PHYSFS_uint64 is only 32 bits on platforms without any sort of 64-bit support.
