DESCRIPTION

The PhysicsFS library provides a platform-independent API for accessing files. It is designed to allow you to easily manage archives (like ZIP files) and other collections of files as if they were a single directory tree.

The API is divided into several categories:

  • Initialization and Shutdown
  • File Access
  • Archive Mounting
  • Directory Enumeration
  • String Conversion and Comparison
  • Allocator Hooking
  • Error Handling
  • Version Information

This header file defines the core data types and function prototypes for the PhysicsFS library.

Advertencia

A partir de PhysicsFS 2.1, use PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; le da más control sobre el proceso.

Se utilizan para informar una lista de entradas de directorio a un llamante original, un archivo/directorio/enlace simbólico por callback. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de ninguna cadena.

Estos callbacks se utilizan, a partir de PhysicsFS 1.1, como una alternativa a las funciones que devolverían listas que deben limpiarse con PHYSFS_freeList(). El callback significa que la biblioteca no necesita asignar una lista completa y todas las cadenas por adelantado.

Tenga en cuenta que el orden de los datos prometido en las versiones de lista no es necesariamente así en las versiones de callback. Consulte la documentación de las API específicas, pero es posible que las cadenas no estén ordenadas como espera y podría obtener cadenas duplicadas.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Get a list of files from a search path, using a user-supplied callback, with errors reported. Internally, PHYSFS_enumerateFiles() just calls this function and then builds a list before returning to the application, so the functionality is identical, though the information is represented differently.

Unlike PHYSFS_enumerateFiles(), this function does not return an array. Instead, it calls a user-supplied function once for each item in the search path:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Items sent to the callback are not guaranteed to be in any order. No sorting is done at this level, and if you need it, you should use PHYSFS_enumerateFiles(), which guarantees alphabetical order. This form reports what it finds in each archive file before moving on to the next path. Even within one archive, we can't guarantee the order in which data is discovered. Any sorting you find in these callbacks is just pure luck. Do not rely on it. Since this walks the entire list of archives, you may get duplicate filenames.

This API and the callbacks themselves are capable of reporting errors. Before this API, callbacks had to accept every enumerated item, even if they were only looking for a specific object and wanted to stop after that, or if there was a serious error and they couldn't notify anyone. Also, if PhysicsFS itself had a problem (disk error or whatever), it couldn't report it to the calling application, it would simply have to skip items or stop enumeration altogether, and the caller wouldn't know that it had lost some data along the way.

Now the caller can ensure they have received a complete set of data, and if they want to stop enumeration early, their callback will have control. See the documentation for PHYSFS_EnumerateCallback for details on how your callback should behave.

Parameters

dir Directory path, in platform-independent notation, to enumerate.
c Callback function to notify about search path items.
d Application-defined data to pass to the callback. May be NULL.

Returns

Non-zero on success, zero on error. Use PHYSFS_getLastErrorCode() to get the specific error. If the callback returns PHYSFS_ENUM_STOP to stop early, this will be considered success. Callbacks returning PHYSFS_ENUM_ERROR will cause this function to return zero and set the error code to PHYSFS_ERR_APP_CALLBACK.

char ** PHYSFS_enumerateFiles (const char * dir)

Get a list of files from a search path.

Warning

In versions of PhysicsFS prior to 2.1, this function would return as many items as possible in the event of an error (such as memory error, disk i/o, etc.). Since this made it impossible for applications to differentiate between complete success and partial failure, and since the function could always return NULL to report catastrophic errors, in PhysicsFS 2.1 this policy was changed: it will either return a complete list of results, or return NULL in the event of any error, thus guaranteeing that the enumeration completed and no results are missing.

Matching directories are interpolated. That is, if "C:\mydir" is in the search path and contains a directory "savegames" which contains "x.sav", "y.sav", and "z.sav", and furthermore there is a "C:\userdir" in the search path which has a subdirectory "savegames" with "w.sav", then the following code:

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);
PHYSFS_freeList(rc);
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..
Feel free to sort the list however you like. However, the returned data will always contain no duplicates, and will be always sorted in alphabetic (rather: case-sensitive Unicode) order for you.
Don't forget to call PHYSFS_freeList() with the return value from this function when you are done with it.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Añade un archivo o directorio a la ruta de búsqueda. Si es un duplicado, la entrada no se añade de nuevo, aunque la función tenga éxito. No puede añadir el mismo archivo a dos puntos de montaje diferentes: la comprobación de duplicados se realiza contra el archivo y no contra el punto de montaje.

Cuando monta un archivo, se añade a un sistema de archivos virtual... todos los archivos de todos los archivos se interpolan en un único árbol de archivos jerárquico. Dos archivos montados en el mismo lugar (o un archivo con archivos que se solapan con otro punto de montaje) pueden tener archivos superpuestos: en tal caso, se selecciona el archivo anterior en la ruta de búsqueda, y los otros archivos son inaccesibles para la aplicación. Esto permite que los archivos se utilicen para anular revisiones anteriores; puede usar el mecanismo de montaje para colocar archivos en un punto específico del árbol de archivos y evitar superposiciones; esto es útil para mods descargables que podrían pisotear datos de la aplicación o entre sí, por ejemplo.

El punto de montaje no necesita existir antes del montaje, lo que es diferente de lo que pueden esperar quienes estén familiarizados con el concepto de "montaje" de Unix. Además, se pueden montar varios archivos en el mismo punto de montaje, o los contenidos de los puntos de montaje y archivos pueden superponerse... el mecanismo de interpolación sigue funcionando como de costumbre.

Se permite especificar un enlace simbólico a un archivo o directorio aquí, independientemente del estado de PHYSFS_permitSymbolicLinks(). Esa función solo se ocupa de enlaces simbólicos dentro del directorio o archivo montado.

int PHYSFS_mountArchive (PHYSFS_File * file, const char * newDir, const char * mountPoint, int appendToPath)

Añade un archivo, contenido en un handle de PHYSFS_File, a la ruta de búsqueda.

Advertencia

A menos que tenga alguna necesidad especial de bajo nivel, debería usar PHYSFS_mount() en lugar de esto.

Los archivos dentro de archivos pueden ser muy lentos. Mientras que un PHYSFS_File puede buscar incluso cuando los datos están comprimidos, puede hacerlo rebobinando al principio y descomprimiendo todo antes del punto de búsqueda. El uso normal de archivos puede realizar muchas búsquedas en segundo plano. Como tal, puede encontrar que el uso normal de archivos es extremadamente doloroso si se monta de esta manera. Planifique en consecuencia: si, por ejemplo, tiene un archivo .zip autoextraíble y desea montar algo dentro de él, comprima el contenido del archivo interior y asegúrese de que el archivo .zip exterior no comprima también el archivo interior.

Esta función opera igual que PHYSFS_mount(), pero toma un handle de PHYSFS_File en lugar de una ruta de archivo. Este handle contiene todos los datos del archivo y se utiliza en lugar de un archivo real en el sistema de archivos físico. El PHYSFS_File puede estar respaldado por un archivo real en el sistema de archivos físico, pero no es necesariamente así. El uso más popular para esto es probablemente montar archivos almacenados dentro de otros archivos.

(newDir) debe ser una cadena única para identificar este archivo. Se utiliza para optimizar la selección del archiver (si lo nombras XXXXX.zip, podríamos intentar primero el archiver ZIP, por ejemplo, o elegir directamente un archiver que solo pueda confiar en que los datos son válidos por la extensión del nombre del archivo). No necesita referirse a un archivo real en absoluto. Si la extensión del nombre del archivo no es útil, el sistema intentará con cada archiver hasta que uno funcione o ninguno lo haga. Este nombre de archivo debe ser único, ya que el sistema no le permitirá tener dos archivos con el mismo nombre.

(file) debe permanecer hasta que el archivo se desmonte. Cuando el archivo se desmonte, el sistema llamará a PHYSFS_close(file). Si necesita que este handle sobreviva, tendrá que envolverlo en un PHYSFS_Io y usar PHYSFS_mountIo() en su lugar.

Si esta función falla, no se llama a PHYSFS_close(file).

newDir Nombre de archivo que puede representar este stream.
mountPoint Ubicación en el árbol interpolado donde se "montará" este archivo, en notación independiente de la plataforma. NULL o "" es equivalente a "/".
appendToPath distinto de cero para añadir a la ruta de búsqueda, cero para anteponer.

int PHYSFS_setBuffer (PHYSFS_File * handle, unsigned int bufsize)

Set the buffer size for an open file.

This function can be used to set the buffer size for a given file handle. If the handle is currently buffered, the existing buffer will be flushed and freed, and a new one will be allocated with the specified size.

If bufsize is zero, the buffer is freed and the file is unbuffered.

Setting the buffer size to zero for a read-only file might fail if PhysicsFS cannot seek backwards in that file (e.g. if it's a pipe). In such cases, PhysicsFS will attempt to flush the buffer to disk and then free it. If this flush fails, the function will fail.

A bufsize of zero will also fail if the file is currently open for writing, as this implicitly causes a flush... check your return values!

Seeking, etc transparently accounts for buffering.

You can resize an existing buffer by calling this function more than once on the same file. Setting the buffer size to zero will free an existing buffer.

PhysicsFS file handles are unbuffered by default.

Please check the return value of this function! Failures can include not being able to seek backwards in a read-only file when removing the buffer, not being able to allocate the buffer, and not being able to flush the buffer to disk, among other unexpected problems.

handle handle returned from PHYSFS_open*().
bufsize size, in bytes, of buffer to allocate.

Returns

nonzero if successful, zero on error.

The write dir will be set to the pref dir returned by

, which is created if it doesn't exist.

  • The Base Dir (PHYSFS_getBaseDir())
  • All found CD-ROM dirs (optionally)

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convierte una cadena Latin1 a una cadena UTF-8. Las cadenas Latin1 tienen 8 bits por carácter: una codificación popular de "ASCII alto".

Para asegurar que el búfer de destino sea lo suficientemente grande para la conversión, por favor, asigna un búfer del doble del tamaño del búfer de origen. UTF-8 expande los puntos de código latin1 mayores a 127 de 1 a 2 bytes, por lo que la cadena puede crecer en algunos casos.

Las cadenas que no quepan en el búfer de destino serán truncadas, pero siempre estarán terminadas en nulo y nunca tendrán una secuencia UTF-8 incompleta al final. Si la longitud del búfer es 0, esta función no hace nada.

Ten en cuenta que no proporcionamos un conversor de UTF-8 a Latin1, ya que Latin1 no puede expresar la mayoría de los puntos de código Unicode. Es una codificación heredada; deberías estar convirtiendo desde ella en todo momento.

Parámetros

src Cadena de origen terminada en nulo en formato Latin1.
dst Búfer para almacenar la cadena UTF-8 convertida.
len Tamaño, en bytes, del búfer de destino.

int PHYSFS_utf8stricmp (const char * str1, const char * str2)

Comparación insensible a mayúsculas y minúsculas de dos cadenas UTF-8. Este es un reemplazo de strcasecmp/stricmp que espera que ambas cadenas estén en codificación UTF-8. Realizará "plegado de mayúsculas" para decidir si los puntos de código Unicode en las cadenas coinciden.

Si ambas cadenas son exclusivamente caracteres ASCII bajos, esto hará lo correcto, ya que también es UTF-8 válido. Si hay algún carácter ASCII alto, ¡esto no hará lo que esperas!

Informará cuál cadena es "mayor que" la otra, pero ten en cuenta que esto no tiene necesariamente ningún significado: 'a' puede ser "menor que" 'b', pero un kuten japonés no tiene una relación alfabética significativa con una lambda griega, pero poder asignar un "valor" confiable hace que los algoritmos de ordenación sean posibles, aunque no del todo sensatos. La mayoría de los casos deberían tratar el valor de retorno como "igual" o "no igual".

Al igual que stricmp, esto espera que ambas cadenas estén terminadas en NULL.

Parámetros

str1 Primera cadena a comparar.
str2 Segunda cadena a comparar.

Retorna

-1 si str1 es "menor que" str2, 1 si es "mayor que", 0 si es igual.

Escribe datos en un manejador de archivo de PhysicsFS. El archivo debe estar abierto para escritura.

Tenga en cuenta que aunque (len) es un entero sin signo de 64 bits, estás limitado a 63 bits (9223372036854775807 bytes), por lo que podemos devolver un valor negativo en caso de error. Si la longitud es mayor que 0x7FFFFFFFFFFFFFFF, esta función fallará inmediatamente. Para sistemas sin un tipo de dato de 64 bits, estás limitado a 31 bits (0x7FFFFFFF, o 2147483647 bytes).
