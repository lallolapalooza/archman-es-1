typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Firma de función para callbacks que enumeran archivos.

Advertencia

A partir de PhysicsFS 2.1, usa PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; te da más control sobre el proceso.

Estos se utilizan para informar una lista de entradas de directorio a un llamador original, un archivo/directorio/enlace simbólico por callback. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de ninguna cadena.

Estos callbacks se utilizan, a partir de PhysicsFS 1.1, como una alternativa a las funciones que devolverían listas que necesitan ser limpiadas con PHYSFS_freeList(). El callback significa que la biblioteca no necesita asignar una lista completa y todas las cadenas por adelantado.

Ten en cuenta que el orden de los datos prometido en las versiones de lista no es necesariamente el mismo en las versiones de callback. Consulta la documentación de las APIs específicas, pero es posible que las cadenas no estén ordenadas como esperas y podrías obtener cadenas duplicadas.

Parámetros

data Puntero a datos definido por el usuario, pasado desde la API que finalmente llamó al callback.
origdir Una cadena que contiene la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio sobre el que solicitaste la enumeración, pasado en el callback para tu conveniencia.
fname El nombre del archivo que se está enumerando. Es posible que no esté en orden alfabético en comparación con otros callbacks que se hayan ejecutado, y no contendrá la ruta completa. Puedes recrear la ruta completa con $origdir/$fname... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

enum PHYSFS_ErrorCode

Valores que representan causas específicas de fallo. La mayoría de las veces, solo deberías preocuparte por si una operación dada falló o no, pero puede haber ocasiones en las que planees manejar un caso de fallo específico con gracia, por lo que proporcionamos códigos de error específicos.

La mayoría de estos errores son un poco vagos, y la mayoría no son cosas que puedas arreglar... si hay un error de permisos, por ejemplo, todo lo que realmente puedes hacer es pasar esa información al usuario y dejar que descubran cómo manejarlo. En la mayoría de estos casos, tu programa solo debería preocuparse de que no logró alcanzar sus objetivos, y no importarle específicamente por qué.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtiene una lista de archivos de un directorio de ruta de búsqueda, utilizando una función de devolución de llamada definida por la aplicación, con notificación de errores. Internamente, PHYSFS_enumerateFiles() simplemente llama a esta función y luego crea una lista antes de devolverla a la aplicación, por lo que la funcionalidad es idéntica excepto por cómo se representa la información a la aplicación.

A diferencia de PHYSFS_enumerateFiles(), esta función no devuelve una matriz. En cambio, llama a una función especificada por la aplicación una vez por elemento de la ruta de búsqueda:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Tenemos [%s] en [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // dame más datos, por favor.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

No se garantiza que los elementos enviados a la función de devolución de llamada estén en ningún orden. No se realiza ninguna ordenación en este nivel y, si la necesita, probablemente debería usar PHYSFS_enumerateFiles() en su lugar, que garantiza la ordenación alfabética. Esta forma informa lo que se descubre en cada archivo antes de pasar al siguiente. Incluso dentro de un solo archivo, no podemos garantizar el orden en que descubrirá los datos. Cualquier ordenación que encuentre en estas devoluciones de llamada es pura suerte. No confíe en ella. Dado que esto recorre toda la lista de archivos, puede recibir nombres de archivo duplicados.

Esta API y las propias funciones de devolución de llamada son capaces de notificar errores. Antes de esta API, las funciones de devolución de llamada tenían que aceptar cada elemento enumerado, incluso si solo buscaban algo específico y querían detenerse después de eso, o tenían un error grave y no podían alertar a nadie. Además, si PhysicsFS en sí tenía un problema (error de disco o similar), no podía informárselo a la aplicación que lo llamaba, solo tenía que omitir elementos o dejar de enumerar por completo, y el llamador no sabría que había perdido algunos datos en el camino.

Ahora el llamador puede estar seguro de que obtuvo un conjunto de datos completo, y su función de devolución de llamada tiene el control si desea que la enumeración se detenga antes. Consulte la documentación de PHYSFS_EnumerateCallback para obtener detalles sobre cómo debe comportarse su función de devolución de llamada.

Parámetros

dir Directorio, en notación independiente de la plataforma, a enumerar.
c Función de devolución de llamada para notificar los elementos de la ruta de búsqueda.
d Datos definidos por la aplicación pasados a la función de devolución de llamada. Puede ser NULL.

Devuelve

Distinto de cero en caso de éxito, cero en caso de error. Utilice PHYSFS_getLastErrorCode() para obtener el error específico. Si la función de devolución de llamada devuelve PHYSFS_ENUM_STOP para detenerse anticipadamente, esto se considerará un éxito. Las funciones de devolución de llamada que devuelven PHYSFS_ENUM_ERROR harán que esta función devuelva cero y establecerá el código de error en PHYSFS_ERR_APP_CALLBACK.

Obtiene una lista de archivos de un directorio de ruta de búsqueda.

Advertencia

En versiones de PhysicsFS anteriores a la 2.1, esta función devolvería tantos elementos como pudiera frente a una condición de error (falta de memoria, error de E/S de disco, etc.). Dado que esto significaba que las aplicaciones no podían distinguir entre éxito total y fallo parcial, y dado que la función siempre podía devolver NULL para informar fallos catastróficos de todos modos, en PhysicsFS 2.1 la política de esta función cambió: devolverá una lista de resultados completos o devolverá NULL para cualquier tipo de fallo, para que podamos garantizar que la enumeración se completó y no tiene lagunas en sus resultados.

Los directorios coincidentes se interpolan. char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * Tenemos [%s].\n", *i);
PHYSFS_freeList(rc);

* Tenemos [z.sav].
* Tenemos [w.sav]..fi

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

mountPoint Location in the interpolated tree that this archive will be "mounted", in platform-independent notation. NULL or "" is equivalent to "/".

PHYSFS_permitSymbolicLinks

Enable or disable following of symbolic links. Some physical filesystems and archives contain files that are just pointers to other files. On the physical filesystem, opening such a link will (transparently) open the file that is pointed to.

By default, PhysicsFS will check if a file is really a symlink during open calls and fail if it is. Otherwise, the link could take you outside the write and search paths, and compromise security.

If you want to take that risk, call this function with a non-zero parameter. Note that this is more for sandboxing a program's scripting language, in case untrusted scripts try to compromise the system. Generally speaking, a user could very well have a legitimate reason to set up a symlink, so unless you feel there's a specific danger in allowing them, you should permit them.

Symlinks are only explicitly checked when dealing with filenames in platform-independent notation. That is, when setting up your search and write paths, etc, symlinks are never checked for.

Please note that PHYSFS_stat() will always check the path specified; if that path is a symlink, it will not be followed in any case. If symlinks aren't permitted through this function, PHYSFS_stat() ignores them, and would treat the query as if the path didn't exist at all.

Symbolic link permission can be enabled or disabled at any time after you've called PHYSFS_init(), and is disabled by default.

Parameters

allow nonzero to permit symlinks, zero to deny linking.

void PHYSFS_utf8ToUtf16 (const char * src, PHYSFS_uint16 * dst, PHYSFS_uint64 len)

Convierte una cadena UTF-8 a una cadena UTF-16.

Advertencia

Esta función no informará de un error si hay secuencias UTF-8 inválidas en la cadena de origen. Las reemplazará con un carácter '?' y continuará.

Las cadenas UTF-16 tienen 16 bits por carácter (excepto algunos caracteres, que tienen 32 bits): TCHAR en Windows, cuando se compila con soporte Unicode. Las versiones modernas de Windows usan UTF-16. Las versiones de Windows anteriores a 2000 usaban TCHAR, pero solo manejaban UCS-2. UTF-16 *es* UCS-2, excepto por los caracteres que tienen 4 bytes, que de todos modos no son representables en UCS-2. Si no estás seguro, deberías estar usando UTF-16 en este momento en Windows.

Para asegurar que el búfer de destino sea lo suficientemente grande para la conversión, por favor asigna un búfer del doble del tamaño del búfer de origen. UTF-8 usa de uno a cuatro bytes por carácter, pero UTF-16 siempre usa de dos a cuatro, ¡así que una cadena completamente ASCII de bajo nivel duplicará su tamaño! Los caracteres UTF-16 que ocuparían cuatro bytes también ocupan cuatro bytes en UTF-8, así que no necesitas asignar 4 veces el espacio por si acaso: el doble será suficiente.

Las cadenas que no quepan en el búfer de destino serán truncadas, pero siempre estarán terminadas en nulo y nunca tendrán un par sustituto UTF-16 incompleto al final. Si la longitud del búfer es 0, esta función no hace nada.

src Cadena de origen terminada en nulo en formato UTF-8.
dst Búfer para almacenar la cadena UTF-16 convertida.
len Tamaño, en bytes, del búfer de destino.

Escribe datos en un manejador de archivo PhysicsFS. El archivo debe estar abierto para escritura.

Por favor, ten en cuenta que aunque (len) es un entero sin signo de 64 bits, estás limitado a 63 bits (9223372036854775807 bytes), por lo que podemos devolver un valor negativo en caso de error.
