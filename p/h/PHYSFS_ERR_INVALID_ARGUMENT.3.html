typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Firma de funciones de callback que enumeran archivos.

Advertencia

Desde PhysicsFS 2.1, usa PHYSFS_EnumerateCallback con PHYSFS_enumerate() para tener más control sobre el proceso.

Estos se usan para reportar una lista de entradas de directorio a un llamador original, una entrada por callback. Todos los strings son codificados en UTF-8. Las funciones no deben intentar modificar o liberar memoria de los strings.

Estos callbacks se usan, desde PhysicsFS 1.1, como alternativa a funciones que devuelven listas que deben ser limpiadas con PHYSFS_freeList(). El callback indica que la biblioteca no necesita asignar una lista completa y todos los strings.

Tenga en cuenta que la ordenación de los datos en las versiones de lista no garantiza necesariamente en las versiones de callback. Verifique la documentación de APIs específicas, pero los strings pueden no estar ordenados como lo esperaba y puede obtener strings duplicados.

Parámetros

data puntero a datos definidos por el usuario, pasado a través de la API que finalmente llamó el callback.
origdir cadena que contiene el camino completo, en notación de plataforma independiente, del directorio que contiene este archivo. En la mayoría de los casos, es el directorio en el cual solicitaste la enumeración, pasado en el callback para tu conveniencia.
fname el nombre del archivo que se está enumerando. No necesariamente estarán en orden alfabético comparado con otros callbacks que hayan sido llamados, y no contendrá el camino completo. Puedes recrear el camino completo con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

Retornar

Un valor de PHYSFS_EnumerateCallbackResult. Todos otros valores son (actualmente) indefinidos; no los use.

int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

"Plegar" un punto de código Unicode a un equivalente en minúsculas. (Esto es para uso limitado y avanzado. Si no ve una necesidad inmediata para ello, probablemente pueda ignorar esto para siempre).

Esto convertirá un punto de código Unicode en su equivalente en minúsculas. Los puntos de código inválidos y aquellos sin un equivalente en minúsculas se devolverán sin convertir.

Tenga en cuenta que ¡es posible que obtenga varios puntos de código en la respuesta! La Eszett alemana, por ejemplo, se plegará en dos puntos de código 's' en minúsculas. La teoría es que si se pliegan dos cadenas, una con una Eszett y otra con "SS", coincidirán.

Advertencia

Cualquiera que sea estudiante de Unicode conoce el problema de la "I turca". Esta API no lo maneja. Suponga que esta única letra en todo Unicode se plegará de forma incorrecta. Si no sabe de qué se trata, probablemente pueda ignorar este problema para la mayor parte del planeta, pero la perfección es imposible.

Parámetros

from El punto de código a plegar.

const char * PHYSFS_getPrefDir (const char * org, const char * app)

Obtener la ruta específica del usuario y de la aplicación donde se pueden escribir archivos. Función auxiliar.

Obtiene el "directorio de preferencias". Se pretende que sea donde los usuarios puedan escribir archivos personales (preferencias y partidas guardadas, etc.) que sean específicos de tu aplicación. Este directorio es único por usuario, por aplicación.

Esta función decidirá la ubicación apropiada en el sistema de archivos nativo, creará el directorio si es necesario y devolverá una cadena en notación dependiente de la plataforma, adecuada para pasar a PHYSFS_setWriteDir().

En Windows, podría verse así: "C:\\Users\\bob\\AppData\\Roaming\\Mi Empresa\\Mi Nombre de Programa"

En Linux, podría verse así: "/home/bob/.local/share/Mi Nombre de Programa"

En Mac OS X, podría verse así: "/Users/bob/Library/Application Support/Mi Nombre de Programa"

(etc.)

Probablemente deberías usar el directorio de preferencias para tu directorio de escritura, y también ponerlo cerca del principio de tu ruta de búsqueda. Versiones anteriores de PhysicsFS ofrecían solo PHYSFS_getUserDir() y te dejaban averiguar dónde debían ir los archivos dentro de ese árbol. Esto encuentra la ubicación correcta para cualquier plataforma, que no solo cambia entre sistemas operativos, sino también entre versiones del mismo sistema operativo.

Especificas el nombre de tu organización (si no es una organización real, tu nombre o un dominio de Internet que poseas podría servir) y el nombre de tu aplicación. Estos deben ser nombres propios.

  • Intenta usar la misma cadena de org (incluida la sensibilidad a mayúsculas y minúsculas) para todas tus aplicaciones que usen esta función.
  • Siempre usa una cadena de app única para cada una, y asegúrate de que nunca cambie para una app una vez que hayas decidido cuál será.
  • Los caracteres Unicode son legales, siempre que estén codificados en UTF-8, pero...
  • ...solo usa letras, números y espacios. Evita signos de puntuación como "Nombre del Juego 2: ¡La Venganza del Chico Malo!" ... "Nombre del Juego 2" es suficiente.

Deberías asumir que la ruta devuelta por esta función es el único lugar seguro para escribir archivos (y que PHYSFS_getUserDir() y PHYSFS_getBaseDir(), aunque podrían ser escribibles, o incluso padres de la ruta devuelta, no son donde deberías escribir cosas).

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Añadir un archivo o directorio a la ruta de búsqueda. Si es un duplicado, la entrada no se añade de nuevo, aunque la función tenga éxito. No puede añadir el mismo archivo a dos puntos de montaje diferentes: la comprobación de duplicados se realiza contra el archivo y no contra el punto de montaje.

Cuando monta un archivo, se añade a un sistema de archivos virtual... todos los archivos en todos los archivos se interpolan en un único árbol de archivos jerárquico. Dos archivos montados en el mismo lugar (o un archivo con archivos que se solapan con otro punto de montaje) pueden tener archivos que se solapan: en tal caso, se selecciona el archivo anterior en la ruta de búsqueda, y los otros archivos son inaccesibles para la aplicación. Esto permite utilizar archivos para invalidar revisiones anteriores; puede utilizar el mecanismo de montaje para colocar archivos en un punto específico del árbol de archivos y evitar solapamientos; esto es útil para mods descargables que podrían pisotear datos de la aplicación o entre sí, por ejemplo.

El punto de montaje no necesita existir antes de montarlo, lo que es diferente de lo que los familiarizados con el concepto de montaje de Unix pueden esperar. Además, se puede montar más de un archivo en el mismo punto de montaje, o los puntos de montaje y los contenidos de los archivos pueden solaparse... el mecanismo de interpolación sigue funcionando como de costumbre.

Se permite especificar un enlace simbólico a un archivo o directorio aquí, independientemente del estado de PHYSFS_permitSymbolicLinks(). Esa función solo se ocupa de los enlaces simbólicos dentro del directorio montado o archivo.

Parámetros

mountPoint Ubicación en el árbol interpolado donde este archivo será "montado", en notación independiente de la plataforma. NULL o "" es equivalente a "/".
appendToPath distinto de cero para añadir a la ruta de búsqueda, cero para añadir al principio.

Retorna

distinto de cero si se añadió a la ruta, cero en caso de fallo (archivo no válido, directorio faltante, etc.). Use PHYSFS_getLastErrorCode() para obtener el error específico.

void PHYSFS_permitSymbolicLinks (int allow)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y archivos contienen archivos que son solo punteros a otros archivos. En el sistema de archivos físico, la apertura de dicho enlace abrirá (transparente) el archivo al que apunta.

Por defecto, PhysicsFS comprobará si un archivo es realmente un enlace simbólico durante las llamadas de apertura y fallará si lo es. De lo contrario, el enlace podría sacarte de las rutas de escritura y de búsqueda, y comprometer la seguridad.

Si deseas asumir ese riesgo, llama a esta función con un parámetro distinto de cero. Ten en cuenta que esto es más para aislar el lenguaje de scripting de un programa, en caso de que scripts no confiables intenten comprometer el sistema. En términos generales, un usuario podría tener una razón legítima para configurar un enlace simbólico, por lo que, a menos que sientas que hay un peligro específico en permitirlos, deberías permitirlos.

Los enlaces simbólicos solo se comprueban explícitamente cuando se trata con nombres de archivo en notación independiente de la plataforma. Es decir, al configurar tus rutas de búsqueda y escritura, etc., nunca se comprueban los enlaces simbólicos.

El permiso de enlace simbólico se puede habilitar o deshabilitar en cualquier momento después de haber llamado a PHYSFS_init(), y está deshabilitado por defecto.

Convierte una cadena UTF-8 a una cadena UTF-16.

Advertencia

Esta función no informará de un error si hay secuencias UTF-8 inválidas en la cadena fuente. Las reemplazará con un carácter '?' y continuará.

Las cadenas UTF-16 tienen 16 bits por carácter (excepto algunos caracteres, que tienen 32 bits): TCHAR en Windows, cuando se compila con soporte Unicode. Las versiones modernas de Windows usan UTF-16. Las versiones de Windows anteriores a 2000 usaban TCHAR, pero solo manejaban UCS-2. UTF-16 *es* UCS-2, excepto por los caracteres que tienen 4 bytes, que de todos modos no son representables en UCS-2. Si no estás seguro, deberías estar usando UTF-16 en este momento en Windows.

Para asegurarte de que el búfer de destino sea lo suficientemente grande para la conversión, asigna un búfer que sea el doble del tamaño del búfer de origen. UTF-8 usa de uno a cuatro bytes por carácter, pero UTF-16 siempre usa de dos a cuatro, ¡así que una cadena completamente ASCII de bajo nivel duplicará su tamaño! Los caracteres UTF-16 que ocuparían cuatro bytes también ocupan cuatro bytes en UTF-8, por lo que no necesitas asignar 4 veces el espacio por si acaso: el doble será suficiente.

Las cadenas que no caben en el búfer de destino se truncarán, pero siempre estarán terminadas en nulo y nunca tendrán un par sustituto UTF-16 incompleto al final. Si la longitud del búfer es 0, esta función no hace nada.

Parámetros

src Cadena fuente terminada en nulo en formato UTF-8.
dst Búfer para almacenar la cadena UTF-16 convertida.
len Tamaño, en bytes, del búfer de destino.

NAME

PHYSFS_writeUBE16, PHYSFS_writeUBE32, PHYSFS_writeUBE64, PHYSFS_writeULE16, PHYSFS_writeULE32, PHYSFS_writeULE64 — convenience functions for writing integer values in different endianness.

LIBRARY

libphysfs (included in PhysFS)

SYNOPSIS

#include <physfs.h>

int PHYSFS_writeUBE32(PHYSFS_File *file, PHYSFS_uint32 val);

int physFS_writeULE32(PHYSFS_File *file, PHYSFS_uint32 val);
int physFS_writeULE64(PHYSFS_File *file, PHYSFS_uint64 val);

DESCRIPTION

These are convenience functions for writing integer values to a PhysicsFS file handle. They convert the given integer value from the platform's native byte order to the specified endianness (BE for Big Endian, LE for Little Endian) and then write the value to the file.

The functions handle the necessary byte swapping if the platform's native byte order differs from the target endianness.
