typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Firma de función para callbacks que enumeran archivos.

Advertencia

A partir de PhysicsFS 2.1, use PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; le da más control sobre el proceso.

Estos se utilizan para informar una lista de entradas de directorio a un llamador original, un archivo/directorio/enlace simbólico por callback. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de ninguna cadena.

Estos callbacks se utilizan, a partir de PhysicsFS 1.1, como una alternativa a las funciones que devolverían listas que necesitan ser liberadas con PHYSFS_freeList(). El callback significa que la biblioteca no necesita asignar una lista completa y todas las cadenas por adelantado.

Tenga en cuenta que el orden de los datos prometido en las versiones de lista no es necesariamente el mismo en las versiones de callback. Consulte la documentación de APIs específicas, pero las cadenas pueden no estar ordenadas como espera y puede recibir cadenas duplicadas.

fname El nombre del archivo que se está enumerando. Puede que no esté en orden alfabético en comparación con otros callbacks que se han activado, y no contendrá la ruta completa. int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Get a file listing of a search path's directory, using an application-defined callback, with errors reported. Internally, PHYSFS_enumerateFiles() just calls this function and then builds a list before returning to the application, so functionality is identical except for how the information is represented to the application.

Unlike PHYSFS_enumerateFiles(), this function does not return an array. Rather, it calls a function specified by the application once per element of the search path:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Items sent to the callback are not guaranteed to be in any order whatsoever. There is no sorting done at this level, and if you need that, you should probably use PHYSFS_enumerateFiles() instead, which guarantees alphabetical sorting. This form reports whatever is discovered in each archive before moving on to the next. Even within one archive, we can't guarantee what order it will discover data. Any sorting you find in these callbacks is just pure luck. Do not rely on it. As this walks the entire list of archives, you may receive duplicate filenames.

This API and the callbacks themselves are capable of reporting errors. Prior to this API, callbacks had to accept every enumerated item, even if they were only looking for a specific thing and wanted to stop after that, or had a serious error and couldn't alert anyone. Furthermore, if PhysicsFS itself had a problem (disk error or whatnot), it couldn't report it to the calling app, it would just have to skip items or stop enumerating outright, and the caller wouldn't know it had lost some data along the way.

Now the caller can be sure it got a complete data set, and its callback has control if it wants enumeration to stop early. See the documentation for PHYSFS_EnumerateCallback for details on how your callback should behave.

Parameters

dir Directory, in platform-independent notation, to enumerate.
c Callback function to notify about search path elements.
d Application-defined data passed to callback. Can be NULL.

Returns

non-zero on success, zero on failure. Use PHYSFS_getLastErrorCode() to obtain the specific error. If the callback returns PHYSFS_ENUM_STOP to stop early, this will be considered success. Callbacks returning PHYSFS_ENUM_ERROR will make this function return zero and set the error code to PHYSFS_ERR_APP_CALLBACK.

char ** PHYSFS_enumerateFiles (const char * dir)

Get a file listing of a search path's directory.

Warning

In PhysicsFS versions prior to 2.1, this function would return as many items as it could in the face of a failure condition (out of memory, disk i/o error, etc). Since this meant apps couldn't distinguish between complete success and partial failure, and since the function could always return NULL to report catastrophic failures anyway, in PhysicsFS 2.1 this function's policy changed: it will either return a list of complete results or it will return NULL for any failure of any kind, so we can guarantee that the enumeration ran to completion and has no gaps in its results.

char **rc = PHYSFS_enumerateFiles("savegames");

for (i = rc; *i != NULL; i++)

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system... all files in all of the archives are interpolated into a single hierarchical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap... the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

Parameters

newDir directory or archive to add to the path, in platform-dependent notation.
mountPoint Location in the interpolated tree that this archive will be "mounted", in platform-independent notation. NULL or "" is equivalent to "/".
appendToPath nonzero to append to search path, zero to prepend.

Returns

nonzero if added to path, zero on failure (bogus archive, dir missing, etc). Use PHYSFS_getLastErrorCode() to obtain the specific error.

void PHYSFS_permitSymbolicLinks (int allow)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y archivos contienen archivos que son solo punteros a otros archivos. En el sistema de archivos físico, la apertura de un enlace de este tipo abrirá (transparente) el archivo al que apunta.

Por defecto, PhysicsFS comprobará si un archivo es realmente un enlace simbólico durante las llamadas de apertura y fallará si lo es. De lo contrario, el enlace podría sacarte de las rutas de escritura y búsqueda, y comprometer la seguridad.

Si quieres asumir ese riesgo, llama a esta función con un parámetro distinto de cero. Ten en cuenta que esto es más para aislar el lenguaje de scripting de un programa, en caso de que scripts no confiables intenten comprometer el sistema. En general, un usuario podría tener una razón legítima para configurar un enlace simbólico, por lo que a menos que sientas que hay un peligro específico en permitirlo, deberías permitirlos.

Los enlaces simbólicos solo se comprueban explícitamente cuando se trata de nombres de archivo en notación independiente de la plataforma. Es decir, al configurar las rutas de búsqueda y escritura, etc., nunca se comprueban los enlaces simbólicos.

Ten en cuenta que PHYSFS_stat() siempre comprobará la ruta especificada; si esa ruta es un enlace simbólico, no se seguirá en ningún caso. Si los enlaces simbólicos no están permitidos a través de esta función, PHYSFS_stat() los ignora y trataría la consulta como si la ruta no existiera en absoluto.

El permiso de enlaces simbólicos se puede habilitar o deshabilitar en cualquier momento después de haber llamado a PHYSFS_init(), y está deshabilitado por defecto.

Parámetros

allow distinto de cero para permitir enlaces simbólicos, cero para denegar la vinculación.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Establece un subdirectorio de un archivo como directorio raíz. Esto te permite acotar los archivos accesibles en un archivo específico. Por ejemplo, si tienes x.zip con un archivo en y/z.txt, montado en /a, si llamas a PHYSFS_setRoot("x.zip", "/y"), entonces la llamada PHYSFS_openRead("/a/z.txt") tendrá éxito.

Puedes cambiar la raíz de un archivo en cualquier momento, alterando el árbol de archivos interpolado (dependiendo de dónde cambien las rutas, un archivo diferente puede estar proporcionando varios archivos). Establecer una nueva raíz no se limita a los archivos en la ruta de búsqueda; también puedes establecer una en el directorio de escritura, lo que podría ser útil si tienes archivos abiertos para escritura y, por lo tanto, no puedes cambiar el directorio de escritura en este momento.

No es un error establecer un subdirectorio que no existe como raíz de un archivo; sin embargo, en este caso no se verán archivos. Si los directorios faltantes terminan creándose (un mkdir al sistema de archivos físico, etc.) entonces esto se reflejará en el árbol interpolado.

archive directorio/archivo sobre el cual cambiar la raíz.

int PHYSFS_setSaneConfig (const char * organization, const char * appName, const char * archiveExt, int includeCdRoms, int archivesFirst)

Configura rutas predeterminadas y sensatas. Función auxiliar.

El directorio de escritura se establecerá en el directorio de preferencias devuelto por

PHYSFS_getPrefDir(organization, appName)

, que se crea si no existe.

Lo anterior es suficiente para asegurar que el directorio de configuración de tu programa esté separado de otro desorden, y sea independiente de la plataforma.

La ruta de búsqueda será:

  • El Directorio de Escritura (creado si no existe)
  • El Directorio Base (PHYSFS_getBaseDir())
  • Todos los directorios de CD-ROM encontrados (opcionalmente)

Estos directorios se buscan luego de archivos que terminan con la extensión (archiveExt), que, si son archivos válidos y compatibles, también se agregarán a la ruta de búsqueda. Si especificaste "PKG" para (archiveExt), y hay un archivo llamado data.PKG en el directorio base, se verificará. Los archivos pueden agregarse o anteponerse a la ruta de búsqueda en orden alfabético, independientemente de los directorios en los que se encontraron. Todos los archivos se montan en la raíz del sistema de archivos virtual ("/").

Todo esto puede ser logrado por la aplicación, pero esto lo hace todo por ti. Siéntete libre de agregar más manualmente a la ruta de búsqueda, también.

organization Nombre de tu empresa/grupo/etc. que se utilizará como nombre de directorio, así que mantenlo corto y sin adornos.
appName Nombre específico del programa para tu programa, para separarlo de otros programas que usan PhysicsFS.
archiveExt Extensión de archivo utilizada por tu programa para especificar un archivo. Por ejemplo, Quake 3 usa "pk3", aunque solo son archivos zip. Especifica NULL para no extraer archivos automáticamente. No especifiques el carácter '.'; Si quieres buscar archivos ZIP, especifica "ZIP" y no ".ZIP" ... la búsqueda de archivos no distingue entre mayúsculas y minúsculas.
includeCdRoms Distinto de cero para incluir CD-ROMs en la ruta de búsqueda, y (si (archiveExt) != NULL) buscarlos para encontrar archivos. Esto puede causar una cantidad significativa de bloqueo mientras se accede a los discos, y si no hay discos en la unidad (o incluso si no están montados en sistemas Unix), es posible que de todos modos no estén disponibles. Es posible que desees especificar cero y manejar la configuración del disco tú mismo.
archivesFirst Distinto de cero para anteponer los archivos a la ruta de búsqueda. Cero para agregarlos al final. Ignorado si !(archiveExt).

distinto de cero si tiene éxito, cero en caso de error. Usa PHYSFS_getLastErrorCode() para obtener el error específico.

file PhysicsFS file handle to which to write.
val Value to convert and write.

Returns

zero on failure, non-zero on success. On failure, you can find out what went wrong from PHYSFS_getLastErrorCode().

Warning

Remember, PHYSFS_uint64 is only 32 bits on platforms without any sort of 64-bit support.
