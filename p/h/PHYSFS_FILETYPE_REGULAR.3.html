DESCRIPTION

These functions provide abstract access to a list of archives. They are used to read files from archives, without having to deal with the internal format of the archives.

The basic idea is that you can query for files, get a file handle to a file, read from it, and then close it. All of these operations are transparently done against archives in the search path.

The search path is a list of directories and archives. PhysicsFS searches this path in order to find files.

Byte Order Conversion:

The functions starting with PHYSFS_swap convert byte orders between the specified endianness (little or big) and the platform's native byte order. The functions starting with PHYSFS_read read data from a file and convert it to the platform's native byte order. The functions starting with PHYSFS_write convert data from the platform's native byte order and write it to a file.

Character Encoding Conversion:

The functions starting with PHYSFS_utf8From convert strings from various encodings (UCS-2, UCS-4, UTF-16, Latin1) to UTF-8. The functions starting with PHYSFS_utf8To convert strings from UTF-8 to various encodings.

String Comparison:

The functions starting with PHYSFS_stricmp perform case-insensitive comparisons of strings in different encodings.

Initialization and Control:

PHYSFS_init() initializes the library. It should be called before any other PhysicsFS function. PHYSFS_deinit() cleans up any resources used by the library.

PHYSFS_mount() adds a directory or archive to the search path. PHYSFS_unmount() removes it. PHYSFS_getSearchPathCallback() can be used to iterate over the current search path.

PHYSFS_getPrefDir() returns the path to a directory where user-specific configuration files can be stored.

PHYSFS_registerArchiver() and PHYSFS_deregisterArchiver() allow for dynamic registration and deregistration of archive formats.

Error Handling:

Most functions return an integer status code: zero for success, non-zero for failure. Use PHYSFS_getLastErrorCode() to get a machine-readable error code, and PHYSFS_getErrorByCode() to get a human-readable description.

typedef void(* physfs_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Firma de función para devoluciones de llamada que enumeran archivos.

Advertencia

A partir de PhysicsFS 2.1, use PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; le da más control sobre el proceso.

Estos se utilizan para informar una lista de entradas de directorio a un llamador original, un archivo/directorio/enlace simbólico por devolución de llamada. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de ninguna cadena.

Estas devoluciones de llamada se utilizan, a partir de PhysicsFS 1.1, como alternativa a las funciones que devolverían listas que necesitan ser limpiadas con PHYSFS_freeList(). La devolución de llamada significa que la biblioteca no necesita asignar una lista completa y todas las cadenas por adelantado.

Tenga en cuenta que el orden de los datos prometido en las versiones de lista no es necesariamente así en las versiones de devolución de llamada. Consulte la documentación de APIs específicas, pero es posible que las cadenas no estén ordenadas como espera y que reciba cadenas duplicadas.

enum PHYSFS_ErrorCode

Valores que representan causas específicas de fallo. La mayoría de las veces, solo debe preocuparse por si una operación dada falló o no, pero puede haber ocasiones en las que planee manejar un caso de fallo específico graciosamente, por lo que proporcionamos códigos de error específicos.

La mayoría de estos errores son un poco vagos, y la mayoría no son cosas que pueda arreglar... si hay un error de permisos, por ejemplo, todo lo que realmente puede hacer es pasar esa información al usuario y dejar que él descubra cómo manejarlo. En la mayoría de estos casos, su programa solo debería preocuparse de que no logró sus objetivos, y no preocuparse específicamente por qué.

Deinitialize the PhysicsFS library. This closes any files opened via PhysicsFS, blanks the search/write paths, frees memory, and invalidates all of your file handles.

Deleting a symlink will remove the link, not what it points to, regardless of whether you "permitSymLinks" or not.

const char *PHYSFS_getPrefDir(const char *org, const char *app)

Obtiene la ruta específica del usuario y de la aplicación donde se pueden escribir archivos. Función auxiliar.

Obtiene el "directorio de preferencias". Esto está destinado a ser donde los usuarios pueden escribir archivos personales (preferencias y partidas guardadas, etc.) que son específicos de tu aplicación. Este directorio es único por usuario, por aplicación.

En Linux, esto podría verse así: "/home/bob/.local/share/Mi Nombre de Programa"

En Mac OS X, esto podría verse así: "/Users/bob/Library/Application Support/Mi Nombre de Programa"

(etc.)

Probablemente deberías usar el directorio de preferencias para tu directorio de escritura, y también ponerlo cerca del principio de tu ruta de búsqueda. Versiones anteriores de PhysicsFS ofrecían solo PHYSFS_getUserDir() y te dejaban averiguar dónde debían ir los archivos en ese árbol.   • Intenta usar la misma cadena de organización (incluida la sensibilidad a mayúsculas y minúsculas) para todas tus aplicaciones que utilizan esta función.
  • Siempre usa una cadena de aplicación única para cada una, y asegúrate de que nunca cambie para una aplicación una vez que hayas decidido cuál será.
  • Los caracteres Unicode son legales, siempre que estén codificados en UTF-8, pero...
  • ... solo usa letras, números y espacios. Evita la puntuación como "Nombre del Juego 2: ¡La Venganza del Chico Malo!" ... "Nombre del Juego 2" es suficiente.

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

Advertencia

A menos que tenga alguna necesidad especial de bajo nivel, debería usar PHYSFS_mount() en lugar de esto.

¡Los archivos dentro de archivos pueden ser muy lentos! Si bien un PHYSFS_File puede buscar incluso cuando los datos están comprimidos, puede hacerlo rebobinando hasta el principio y descomprimiendo todo antes del punto de búsqueda. El uso normal de archivos puede realizar muchas búsquedas en segundo plano. Como tal, puede encontrar que el uso normal de archivos es extremadamente doloroso si se monta de esta manera. Planifique en consecuencia: si, por ejemplo, tiene un archivo .zip que se autocomprime y desea montar algo dentro de él, comprima el contenido del archivo interno y asegúrese de que el archivo .zip externo no comprima el archivo interno también.

Esta función opera igual que PHYSFS_mount(), pero toma un manejador PHYSFS_File en lugar de una ruta de archivo. Este manejador contiene todos los datos del archivo y se utiliza en lugar de un archivo real en el sistema de archivos físico. El PHYSFS_File puede estar respaldado por un archivo real en el sistema de archivos físico, pero no es necesariamente así. El uso más popular para esto es probablemente montar archivos almacenados dentro de otros archivos.

(newDir) debe ser una cadena única para identificar este archivo. void PHYSFS_permitSymbolicLinks (int allow)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y archivos contienen archivos que son solo punteros a otros archivos. En el sistema de archivos físico, abrir dicho enlace abrirá (transparentemente) el archivo al que apunta.

Por defecto, PhysicsFS verificará si un archivo es realmente un enlace simbólico durante las llamadas de apertura y fallará si lo es. De lo contrario, el enlace podría sacarte de las rutas de escritura y de búsqueda, y comprometer la seguridad.

Si quieres asumir ese riesgo, llama a esta función con un parámetro distinto de cero. Ten en cuenta que esto es más para poner en cuarentena el lenguaje de scripting de un programa, en caso de que scripts no confiables intenten comprometer el sistema. En términos generales, un usuario podría tener una razón legítima para configurar un enlace simbólico, por lo que a menos que sientas que hay un peligro específico al permitirlos, deberías permitirlos.

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convierte una cadena UTF-8 a una cadena Latin1. Las cadenas Latin1 son de 8 bits por carácter: una codificación popular de "ASCII extendido".

Para asegurar que el búfer de destino sea lo suficientemente grande para la conversión, por favor, asigna un búfer que sea el doble del tamaño del búfer de origen. UTF-8 expande los puntos de código latin1 mayores que 127 de 1 a 2 bytes, por lo que la cadena puede crecer en algunos casos.

Las cadenas que no caben en el búfer de destino se truncarán, pero siempre estarán terminadas en nulo y nunca tendrán una secuencia UTF-8 incompleta al final. Si la longitud del búfer es 0, esta función no hace nada.

Por favor, ten en cuenta que no proporcionamos un conversor de UTF-8 a Latin1, ya que Latin1 no puede expresar la mayoría de los puntos de código Unicode. Es una codificación heredada; deberías estar convirtiendo desde ella en todo momento.

Parámetros

src Cadena de origen terminada en nulo en formato Latin1.
dst Búfer para almacenar la cadena UTF-8 convertida.
len Tamaño, en bytes, del búfer de destino.

Advertencia

casi con toda seguridad deberías usar PHYSFS_utf8FromUtf16(), que estuvo disponible en PhysicsFS 2.1, a menos que sepas lo que estás haciendo.

Esta función no informará de un error si hay secuencias UTF-16 inválidas en la cadena de origen. Las reemplazará con un carácter '?' y continuará.

Las cadenas UTF-16 son de 16 bits por carácter (excepto algunos caracteres, que son de 32 bits): TCHAR en Windows, al compilar con soporte Unicode. Las versiones modernas de Windows usan UTF-16. Las versiones de Windows anteriores a 2000 usaban TCHAR, pero solo manejaban UCS-2. UTF-16 *es* UCS-2, excepto por los caracteres que son de 4 bytes, que de todas formas no son representables en UCS-2. Si no estás seguro, deberías estar usando UTF-16 en este momento en Windows.

Para asegurar que el búfer de destino sea lo suficientemente grande para la conversión, por favor, asigna un búfer que sea el doble del tamaño del búfer de origen. UTF-8 nunca usa más de 32 bits por carácter, por lo que si bien puede reducir el tamaño de una cadena UTF-16, también puede expandirla.

Las cadenas que no caben en el búfer de destino se truncarán, pero siempre estarán terminadas en nulo y nunca tendrán una secuencia UTF-8 incompleta al final. Si la longitud del búfer es 0, esta función no hace nada.

int PHYSFS_utf8stricmp (const char * str1, const char * str2)

Comparación insensible a mayúsculas y minúsculas de dos cadenas UTF-8. Este es un reemplazo de strcasecmp/stricmp que espera que ambas cadenas estén en codificación UTF-8. Realizará "plegado de mayúsculas" para decidir si los puntos de código Unicode en las cadenas coinciden.

Si ambas cadenas son exclusivamente caracteres ASCII de bajo nivel, esto hará lo correcto, ya que también es UTF-8 válido. Si hay caracteres ASCII de alto nivel, ¡esto no hará lo que esperas!

Informará cuál cadena es "mayor que" la otra, pero ten en cuenta que esto no significa necesariamente nada: 'a' puede ser "menor que" 'b', pero un kuten japonés no tiene una relación alfabética significativa con una lambda griega, pero poder asignar un "valor" fiable hace posibles los algoritmos de ordenación, aunque no sean del todo sensatos. La mayoría de los casos deberían tratar el valor de retorno como "igual" o "no igual".

Al igual que stricmp, esto espera que ambas cadenas estén terminadas en NULL.

Parámetros

str1 Primera cadena a comparar.
str2 Segunda cadena a comparar.

Devuelve

-1 si str1 es "menor que" str2, 1 si es "mayor que", 0 si son iguales.

Esta función no reportará un error si hay secuencias inválidas de UTF-8 en la cadena de entrada. Reemplazará estas con un carácter '?' y continuará.

PHYSFS_sint64 PHYSFS_writeBytes (PHYSFS_File * handle, const void * buffer, PHYSFS_uint64 len)

Escribir datos a un archivo PhysicsFS. El archivo debe estar abierto para escritura.

Nota: aunque (len) es un entero de 64 bits no negativo, estás limitado a 63 bits (9223372036854775807 bytes), así que podemos devolver un valor negativo en caso de error. Si el largo es mayor que 0x7FFFFFFFFFFFFFFF, esta función fallará inmediatamente. Para sistemas sin tipo de 64 bits, estás limitado a 31 bits (0x7FFFFFFF, o 2147483647 bytes). Confiamos que casi nada necesitará realizar múltiples gigabytes de I/O en una sola llamada, pero ¿por qué limitar las cosas?

Número de bytes escritos. Esto puede ser menor que (len); en el caso de un error, el sistema podría intentar escribir tantos bytes como sea posible, así que podría haber una escritura incompleta.
