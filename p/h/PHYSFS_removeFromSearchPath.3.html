typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Firma de función para callbacks que enumeran archivos.

Advertencia

A partir de PhysicsFS 2.1, utiliza PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; te da más control sobre el proceso.

Estos se utilizan para informar una lista de entradas de directorio a un llamador original, un archivo/directorio/enlace simbólico por callback. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de ninguna cadena.

Estos callbacks se utilizan, a partir de PhysicsFS 1.1, como alternativa a las funciones que devolverían listas que necesitan ser limpiadas con PHYSFS_freeList(). El callback significa que la biblioteca no necesita asignar una lista completa ni todas las cadenas por adelantado.

Ten en cuenta que el orden de los datos prometido en las versiones de lista no es necesariamente así en las versiones de callback. Consulta la documentación de APIs específicas, pero es posible que las cadenas no estén ordenadas como esperas y podrías obtener cadenas duplicadas.

data Puntero de datos definido por el usuario, pasado desde la API que eventualmente llamó al callback.
origdir Una cadena que contiene la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio sobre el cual solicitaste la enumeración, pasado en el callback para tu conveniencia.
fname El nombre del archivo que se está enumerando. Puede que no esté en orden alfabético en comparación con otros callbacks que se hayan ejecutado, y no contendrá la ruta completa. Puedes recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

enum PHYSFS_ErrorCode

Valores que representan causas específicas de fallo. La mayoría de las veces, solo deberías preocuparte por si una operación dada falló o no, pero puede haber ocasiones en las que planees manejar un caso de fallo específico con gracia, por lo que proporcionamos códigos de error específicos.

La mayoría de estos errores son un poco vagos, y la mayoría no son cosas que puedas arreglar... si hay un error de permisos, por ejemplo, todo lo que realmente puedes hacer es pasar esa información al usuario y dejar que él decida cómo manejarlo. En la mayoría de estos casos, tu programa solo debería saber que no logró alcanzar sus objetivos, y no debería importarle específicamente por qué.

Deinitialize the PhysicsFS library. This closes any files opened via PhysicsFS, blanks the search/write paths, frees memory, and invalidates all of your file handles.

Note that this call can FAIL if there's a file open for writing that refuses to close (for example, the underlying operating system was buffering writes to network filesystem, and the fileserver has crashed, or a hard drive has failed, etc). int PHYSFS_delete(const char *filename)

Delete a file or directory. (filename) is specified in platform-independent notation in relation to the write dir.

A directory must be empty before this call can delete it.

Deleting a symlink will remove the link, not what it points to, regardless of whether you "permitSymLinks" or not.

So if you've got the write dir set to "C:\mygame\writedir" and call PHYSFS_delete("downloads/maps/level1.map") then the file "C:\mygame\writedir\downloads\maps\level1.map" is removed from the physical filesystem, if it exists and the operating system permits the deletion.

Note that on Unix systems, deleting a file may be successful, but the actual file won't be removed until all processes that have an open filehandle to it (including your program) close their handles.

Chances are, the bits that make up the file still exist, they are just made available to be written over at a later point. Don't consider this a security method or anything. :)

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtiene una lista de archivos de un directorio de la ruta de búsqueda, utilizando una función de devolución de llamada definida por la aplicación, con informes de errores. Internamente, PHYSFS_enumerateFiles() simplemente llama a esta función y luego crea una lista antes de devolverla a la aplicación, por lo que la funcionalidad es idéntica, excepto por cómo se representa la información a la aplicación.

A diferencia de PHYSFS_enumerateFiles(), esta función no devuelve una matriz. Más bien, llama a una función especificada por la aplicación una vez por elemento de la ruta de búsqueda:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Tenemos [%s] en [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // dame más datos, por favor.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

No se garantiza que los elementos enviados a la función de devolución de llamada estén en ningún orden. No se realiza ninguna ordenación en este nivel, y si la necesita, probablemente debería usar PHYSFS_enumerateFiles() en su lugar, que garantiza la ordenación alfabética. Esta forma informa lo que se descubre en cada archivo antes de pasar al siguiente. Incluso dentro de un archivo, no podemos garantizar el orden en que descubrirá los datos. _Cualquier ordenación que encuentre en estas devoluciones de llamada es pura suerte. No confíe en ella._ A medida que recorre toda la lista de archivos, es posible que reciba nombres de archivo duplicados.

Esta API y las propias devoluciones de llamada son capaces de informar errores. Antes de esta API, las devoluciones de llamada tenían que aceptar cada elemento enumerado, incluso si solo buscaban algo específico y querían detenerse después de eso, o tenían un error grave y no podían alertar a nadie. Además, si PhysicsFS mismo tenía un problema (error de disco o similar), no podía informarlo a la aplicación que lo llamaba, solo tendría que omitir elementos o dejar de enumerar directamente, y el llamador no sabría que había perdido algunos datos en el camino.

Ahora, el llamador puede estar seguro de que obtuvo un conjunto de datos completo, y su función de devolución de llamada tiene el control si desea que la enumeración se detenga anticipadamente. Consulte la documentación de PHYSFS_EnumerateCallback para obtener detalles sobre cómo debe comportarse su función de devolución de llamada.

Parámetros

dir Directorio, en notación independiente de la plataforma, a enumerar.
c Función de devolución de llamada para notificar sobre elementos de la ruta de búsqueda.
d Datos definidos por la aplicación pasados a la función de devolución de llamada. Puede ser NULL.

Devoluciones

Distinto de cero en caso de éxito, cero en caso de fallo. Utilice PHYSFS_getLastErrorCode() para obtener el error específico. Si la función de devolución de llamada devuelve PHYSFS_ENUM_STOP para detenerse anticipadamente, esto se considerará un éxito. Las funciones de devolución de llamada que devuelven PHYSFS_ENUM_ERROR harán que esta función devuelva cero y establezca el código de error en PHYSFS_ERR_APP_CALLBACK.

Obtiene la ruta específica del usuario y de la aplicación donde se pueden escribir archivos. Función de ayuda.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

newDir directory or archive to add to the path, in platform-dependent notation.
mountPoint Location in the interpolated tree that this archive will be "mounted", in platform-independent notation. NULL or "" is equivalent to "/".
appendToPath nonzero to append to search path, zero to prepend.

Returns

nonzero if added to path, zero on failure (bogus archive, dir missing, etc). Use PHYSFS_getLastErrorCode() to obtain the specific error.

Add an archive, contained in a PHYSFS_File handle, to the search path.

Warning

Unless you have some special, low-level need, you should be using PHYSFS_mount() instead of this.

Archives-in-archives may be very slow! While a PHYSFS_File can seek even when the data is compressed, it may do so by rewinding to the start and decompressing everything before the seek point. Normal archive usage may do a lot of seeking behind the scenes. As such, you might find normal archive usage extremely painful if mounted this way. Plan accordingly: if you, say, have a self-extracting .zip file, and want to mount something in it, compress the contents of the inner archive and make sure the outer .zip file doesn't compress the inner archive too.

This function operates just like PHYSFS_mount(), but takes a PHYSFS_File handle instead of a pathname. This handle contains all the data of the archive, and is used instead of a real file in the physical filesystem. The PHYSFS_File may be backed by a real file in the physical filesystem, but isn't necessarily. The most popular use for this is likely to mount archives stored inside other archives.

void PHYSFS_permitSymbolicLinks (int allow)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivo físicos y arquitecturas contienen archivos que son simplemente referencias a otros archivos. Al abrir un enlace simbólico físico, este se abrirá transparentemente en el archivo al que se refiere.

Por defecto, PhysicsFS verifica si un archivo es realmente un enlace simbólico durante las llamadas de abrir y falla si es así. De otra manera, el enlace podría llevarte fuera de los caminos de lectura y escritura, comprometiendo la seguridad.

Si quieres asumir ese riesgo, llama a esta función con un valor distinto de cero. Nota que esto es más para el sandboxing de un lenguaje de scripting de un programa, en caso de que scripts no confiables intenten comprometer el sistema. Generalmente, un usuario podría tener una razón legítima para establecer un enlace simbólico, así que no deberías deshabilitarlo a menos que percibas un riesgo específico.

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convert a Latin1 string to a UTF-8 string. Latin1 strings are 8-bits per character: a popular "high ASCII" encoding.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 expands latin1 codepoints over 127 from 1 to 2 bytes, so the string may grow in some cases.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-8 sequence at the end. If the buffer length is 0, this function does nothing.

Please note that we do not supply a UTF-8 to Latin1 converter, since Latin1 can't express most Unicode codepoints. It's a legacy encoding; you should be converting away from it at all times.
