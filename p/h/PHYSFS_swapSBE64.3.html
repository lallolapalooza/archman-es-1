DESCRIPTION

The PhysicsFS library is intended to provide a platform-independent API for accessing files. It is often used for games, to allow them to load data from archives (like ZIP files) transparently.

This header file defines the public interface to the PhysicsFS library.

Swap endianness

These functions swap the endianness of the supplied value from little-endian to the platform's native byte order, or vice-versa. For example, PHYSFS_swapSLE32 swaps a 32-bit signed integer from little-endian to native byte order.

These functions are used internally by PhysicsFS to handle files that are stored in a specific endianness (like little-endian), but the host machine might be using a different endianness (like big-endian). All data read from archives will be swapped into the host's native byte order before being returned to the application.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtenga una lista de archivos de un directorio de la ruta de búsqueda, utilizando una devolución de llamada definida por la aplicación, con errores informados. Internamente, PHYSFS_enumerateFiles() simplemente llama a esta función y luego crea una lista antes de devolverla a la aplicación, por lo que la funcionalidad es idéntica excepto por cómo se representa la información a la aplicación.

A diferencia de PHYSFS_enumerateFiles(), esta función no devuelve una matriz. Más bien, llama a una función especificada por la aplicación una vez por cada elemento de la ruta de búsqueda:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // dame más datos, por favor.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

No se garantiza que los elementos enviados a la devolución de llamada estén en ningún orden particular. No se realiza ningún ordenamiento en este nivel, y si lo necesita, probablemente debería usar PHYSFS_enumerateFiles() en su lugar, que garantiza el ordenamiento alfabético. Esta forma informa lo que se descubre en cada archivo antes de pasar al siguiente. Incluso dentro de un archivo, no podemos garantizar el orden en que descubrirá los datos. Cualquier orden que encuentre en estas devoluciones de llamada es pura suerte. No confíe en él. Dado que recorre toda la lista de archivos, puede recibir nombres de archivo duplicados.

Esta API y las devoluciones de llamada en sí mismas son capaces de informar errores. Antes de esta API, las devoluciones de llamada tenían que aceptar todos los elementos enumerados, incluso si solo buscaban algo específico y querían detenerse después de eso, o tenían un error grave y no podían alertar a nadie. Además, si PhysicsFS en sí tenía un problema (error de disco o similar), no podía informarlo a la aplicación que lo llamaba, solo tenía que omitir elementos o dejar de enumerar por completo, y el llamador no sabría que había perdido algunos datos en el camino.

Ahora el llamador puede estar seguro de que obtuvo un conjunto de datos completo, y su devolución de llamada tiene control si desea que la enumeración se detenga temprano. Consulte la documentación de PHYSFS_EnumerateCallback para obtener detalles sobre cómo debe comportarse su devolución de llamada.

int PHYSFS_mount(const char *newDir, const char *mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

Advertencia

A menos que tengas alguna necesidad especial de bajo nivel, deberías usar PHYSFS_mount() en lugar de esto.

¡Los archivos dentro de archivos pueden ser muy lentos! Mientras que un PHYSFS_File puede buscar incluso cuando los datos están comprimidos, puede hacerlo rebobinando al principio y descomprimiendo todo antes del punto de búsqueda. El uso normal de archivos puede realizar muchas búsquedas en segundo plano. Como tal, podrías encontrar que el uso normal de archivos es extremadamente doloroso si se monta de esta manera. Planifica en consecuencia: si, por ejemplo, tienes un archivo .zip autoextraíble y quieres montar algo dentro de él, comprime el contenido del archivo interno y asegúrate de que el archivo .zip externo no comprima también el archivo interno.

Esta función opera igual que PHYSFS_mount(), pero toma un manejador PHYSFS_File en lugar de una ruta de archivo. Este manejador contiene todos los datos del archivo y se utiliza en lugar de un archivo real en el sistema de archivos físico. El PHYSFS_File puede estar respaldado por un archivo real en el sistema de archivos físico, pero no es necesariamente así. El uso más popular para esto es probablemente montar archivos almacenados dentro de otros archivos.

(newDir) debe ser una cadena única para identificar este archivo. No necesita referirse a un archivo real en absoluto. Si la extensión del nombre de archivo no es útil, el sistema intentará con cada archiver hasta que uno funcione o ninguno de ellos lo haga. Este nombre de archivo debe ser único, ya que el sistema no te permitirá tener dos archivos con el mismo nombre.

Comparación insensible a mayúsculas y minúsculas de dos cadenas UTF-8. Este es un reemplazo de strcasecmp/stricmp que espera que ambas cadenas estén en codificación UTF-8. Realizará un "plegado de mayúsculas" para decidir si los puntos de código Unicode en las cadenas coinciden.

Si ambas cadenas son exclusivamente caracteres ASCII de bajo nivel, esto hará lo correcto, ya que también es UTF-8 válido. Si hay algún carácter ASCII de alto nivel, ¡esto no hará lo que esperas!

Informará de qué cadena es "mayor que" la otra, pero ten en cuenta que esto no tiene por qué significar nada: 'a' puede ser "menor que" 'b', pero un kuten japonés no tiene una relación alfabética significativa con una lambda griega, pero poder asignar un "valor" confiable hace que los algoritmos de ordenación sean posibles, aunque no del todo sensatos. La mayoría de los casos deberían tratar el valor de retorno como "igual" o "no igual".

Al igual que stricmp, esto espera que ambas cadenas estén terminadas en nulo.

Parámetros

str1 Primera cadena a comparar.
str2 Segunda cadena a comparar.

Devuelve

-1 si str1 es "menor que" str2, 1 si "mayor que", 0 si son iguales.

void PHYSFS_utf8ToUtf16 (const char * src, PHYSFS_uint16 * dst, PHYSFS_uint64 len)

Convert a UTF-8 string to a UTF-16 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UTF-16 strings are 16-bits per character (except some chars, which are 32-bits): TCHAR on Windows, when building with Unicode support. Modern Windows releases use UTF-16. Windows releases before 2000 used TCHAR, but only handled UCS-2. UTF-16 is UCS-2, except for the characters that are 4 bytes, which aren't representable in UCS-2 at all anyhow. If you aren't sure, you should be using UTF-16 at this point on Windows.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 uses from one to four bytes per character, but UTF-16 always uses two to four, so an entirely low-ASCII string will double in size! The UTF-16 characters that would take four bytes also take four bytes in UTF-8, so you don't need to allocate 4x the space just in case: double will do.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-16 surrogate pair at the end. If the buffer length is 0, this function does nothing.

Parameters

src Null-terminated source string in UTF-8 format.
dst Buffer to store converted UTF-16 string.
len Size, in bytes, of destination buffer.

PHYSFS_sint64 PHYSFS_writeBytes (PHYSFS_File * handle, const void * buffer, PHYSFS_uint64 len)

Escribe datos en un manejador de archivos PhysicsFS. El archivo debe abrirse para escritura.

Tenga en cuenta que aunque (len) es un entero sin signo de 64 bits, está limitado a 63 bits (9223372036854775807 bytes), por lo que podemos devolver un valor negativo en caso de error. Si la longitud es mayor que 0x7FFFFFFFFFFFFFFF, esta función fallará inmediatamente. Para sistemas sin un tipo de dato de 64 bits, está limitado a 31 bits (0x7FFFFFFF, o 2147483647 bytes). Confiamos en que la mayoría de las cosas no necesitarán realizar múltiples gigabytes de E/S en una sola llamada, ¡pero ¿por qué limitar las cosas?

Devuelve

número de bytes escritos. Esto puede ser menor que (len); en caso de error, el sistema puede intentar escribir tantos bytes como sea posible, por lo que puede ocurrir una escritura incompleta.
