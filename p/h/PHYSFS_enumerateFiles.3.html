typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Firma de función para callbacks que enumeran archivos.

Advertencia

A partir de PhysicsFS 2.1, use PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; le da más control sobre el proceso.

Estos se utilizan para informar una lista de entradas de directorio a un llamador original, un archivo/directorio/enlace simbólico por callback. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de ninguna cadena.

Estos callbacks se utilizan, a partir de PhysicsFS 1.1, como una alternativa a las funciones que devolverían listas que necesitan ser limpiadas con PHYSFS_freeList(). El callback significa que la biblioteca no necesita asignar una lista completa y todas las cadenas por adelantado.

Tenga en cuenta que el orden de los datos prometidos en las versiones de lista no es necesariamente el mismo en las versiones de callback. Consulte la documentación sobre APIs específicas, pero es posible que las cadenas no estén ordenadas como espera y podría obtener cadenas duplicadas.

Parámetros

data Puntero a datos definido por el usuario, pasado desde la API que finalmente llamó al callback.
origdir Una cadena que contiene la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio sobre el que solicitó la enumeración, pasado en el callback para su conveniencia.
fname El nombre del archivo que se está enumerando. Es posible que no esté en orden alfabético en comparación con otros callbacks que se han disparado, y no contendrá la ruta completa. Puede recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

enum PHYSFS_ErrorCode

Valores que representan causas específicas de fallo. La mayoría de las veces, solo debería preocuparse por si una operación dada falló o no, pero puede haber ocasiones en las que planee manejar un caso de fallo específico con gracia, por lo que proporcionamos códigos de error específicos.

La mayoría de estos errores son un poco vagos y la mayoría no son cosas que pueda arreglar... si hay un error de permisos, por ejemplo, lo único que realmente puede hacer es pasar esa información al usuario y dejar que él descubra cómo manejarlo. En la mayoría de estos casos, su programa solo debería preocuparse de que no logró sus objetivos, y no debería preocuparse específicamente por qué.

"Fold" a Unicode codepoint to a lowercase equivalent. (This is for limited, hardcore use. If you don't immediately see a need for it, you can probably ignore this forever.)

This will convert a Unicode codepoint into its lowercase equivalent. Bogus codepoints and codepoints without a lowercase equivalent will be returned unconverted.

Note that you might get multiple codepoints in return! The German Eszett, for example, will fold down to two lowercase latin 's' codepoints. The theory is that if you fold two strings, one with an Eszett and one with "SS" down, they will match.

int PHYSFS_deinit(void)

Deinitialize the PhysicsFS library. This closes any files opened via PhysicsFS, blanks the search/write paths, frees memory, and invalidates all of your file handles.

Note that this call can FAIL if there's a file open for writing that refuses to close (for example, the underlying operating system was buffering writes to network filesystem, and the fileserver has crashed, or a hard drive has failed, etc). It is usually best to close all write handles yourself before calling this function, so that you can gracefully handle a specific failure.

Once successfully deinitialized, PHYSFS_init() can be called again to restart the subsystem. All default API states are restored at this point, with the exception of any custom allocator you might have specified, which survives between initializations.

Returns

nonzero on success, zero on error. Specifics of the error can be gleaned from PHYSFS_getLastError(). If failure, state of PhysFS is undefined, and probably badly screwed up.

int PHYSFS_delete(const char *filename)

Delete a file or directory. (filename) is specified in platform-independent notation in relation to the write dir.

A directory must be empty before this call can delete it.

Deleting a symlink will remove the link, not what it points to, regardless of whether you "permitSymLinks" or not.

So if you've got the write dir set to "C:\mygame\writedir" and call PHYSFS_delete("downloads/maps/level1.map") then the file "C:\mygame\writedir\downloads\maps\level1.map" is removed from the physical filesystem, if it exists and the operating system permits the deletion.

Note that on Unix systems, deleting a file may be successful, but the actual file won't be removed until all processes that have an open filehandle to it (including your program) close their handles.

Chances are, the bits that make up the file still exist, they are just made available to be written over at a later point. Don't consider this a security method or anything. :)

Parameters

filename Filename to delete.

Returns

nonzero on success, zero on error. Use PHYSFS_getLastErrorCode() to obtain the specific error.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtiene una lista de archivos de un directorio de ruta de búsqueda, utilizando una función de devolución de llamada definida por la aplicación, con informes de errores. Internamente, PHYSFS_enumerateFiles() simplemente llama a esta función y luego construye una lista antes de devolverla a la aplicación, por lo que la funcionalidad es idéntica excepto por cómo se representan los datos a la aplicación.

A diferencia de PHYSFS_enumerateFiles(), esta función no devuelve una matriz. Más bien, llama a una función especificada por la aplicación una vez por elemento de la ruta de búsqueda:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Hemos encontrado [%s] en [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // dame más datos, por favor.
}
// ...
PHYSFS_enumerate("/alguna/ruta", printDir, NULL);

No se garantiza que los elementos enviados a la función de devolución de llamada estén en ningún orden. No se realiza ninguna ordenación en este nivel, y si la necesita, probablemente debería usar PHYSFS_enumerateFiles() en su lugar, que garantiza la ordenación alfabética. Esta forma informa lo que se descubre en cada archivo antes de pasar al siguiente. Incluso dentro de un solo archivo, no podemos garantizar el orden en que descubrirá los datos. Cualquier ordenación que encuentre en estas devoluciones de llamada es pura suerte. No confíe en ella. Dado que recorre toda la lista de archivos, puede recibir nombres de archivo duplicados.

Esta API y las propias funciones de devolución de llamada son capaces de informar errores. Antes de esta API, las funciones de devolución de llamada tenían que aceptar cada elemento enumerado, incluso si solo buscaban algo específico y querían detenerse después de eso, o tenían un error grave y no podían alertar a nadie. Además, si PhysicsFS en sí mismo tenía un problema (error de disco o similar), no podía informarlo a la aplicación que lo llamaba, solo tendría que omitir elementos o dejar de enumerar directamente, y el llamador no sabría que había perdido algunos datos en el camino.

Ahora el llamador puede estar seguro de que obtuvo un conjunto de datos completo, y su función de devolución de llamada tiene control si desea que la enumeración se detenga antes. Consulte la documentación de PHYSFS_EnumerateCallback para obtener detalles sobre cómo debe comportarse su función de devolución de llamada.

Parámetros

dir Directorio, en notación independiente de la plataforma, a enumerar.
c Función de devolución de llamada para notificar sobre elementos de la ruta de búsqueda.
d Datos definidos por la aplicación pasados a la función de devolución de llamada. Puede ser NULL.

Devuelve

Distinto de cero en caso de éxito, cero en caso de fallo. Utilice PHYSFS_getLastErrorCode() para obtener el error específico. Si la función de devolución de llamada devuelve PHYSFS_ENUM_STOP para detenerse antes, esto se considerará un éxito. Las funciones de devolución de llamada que devuelvan PHYSFS_ENUM_ERROR harán que esta función devuelva cero y establezca el código de error en PHYSFS_ERR_APP_CALLBACK.

Advertencia

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * Hemos encontrado [%s].\n", *i);
PHYSFS_freeList(rc);
* Hemos encontrado [x.sav].
* Hemos encontrado [y.sav].
* Hemos encontrado [z.sav].
* Hemos encontrado [w.sav]..fi

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Añade un archivo o directorio a la ruta de búsqueda. Si es un duplicado, la entrada no se añade de nuevo, aunque la función tenga éxito. No puedes añadir el mismo archivo a dos puntos de montaje diferentes: la comprobación de duplicados se realiza contra el archivo y no contra el punto de montaje.

Cuando montas un archivo, se añade a un sistema de archivos virtual... todos los archivos en todos los archivos se interpolan en un solo árbol de archivos jerárquico. Dos archivos montados en el mismo lugar (o un archivo con archivos que se superponen a otro punto de montaje) pueden tener archivos superpuestos: en tal caso, se selecciona el archivo anterior en la ruta de búsqueda, y los otros archivos son inaccesibles para la aplicación. Esto permite que los archivos se utilicen para anular revisiones anteriores; puedes usar el mecanismo de montaje para colocar archivos en un punto específico del árbol de archivos y prevenir la superposición; esto es útil para mods descargables que podrían pisotear datos de la aplicación o entre sí, por ejemplo.

El punto de montaje no necesita existir antes de montarlo, lo cual es diferente de lo que aquellos familiarizados con el concepto de "montaje" de Unix pueden esperar. Además, se pueden montar más de un archivo al mismo punto de montaje, o los puntos de montaje y el contenido de los archivos pueden superponerse... el mecanismo de interpolación aún funciona como de costumbre.

Especificar un enlace simbólico a un archivo o directorio está permitido aquí, independientemente del estado de PHYSFS_permitSymbolicLinks(). Esa función solo trata con enlaces simbólicos dentro del directorio o archivo montado.

Parámetros

mountPoint Ubicación en el árbol interpolado donde este archivo será "montado", en notación independiente de la plataforma. NULL o "" es equivalente a "/".
appendToPath Distinto de cero para añadir a la ruta de búsqueda, cero para anteponer.

Se utiliza para optimizar la selección del archivero (si lo nombra XXXXX.zip, podríamos intentar primero el archivero ZIP, por ejemplo, o elegir directamente un archivero que solo pueda confiar en que los datos son válidos por la extensión del nombre de archivo). No necesita referirse a un archivo real en absoluto. Si la extensión del nombre de archivo no es útil, el sistema intentará todos los archiveros hasta que uno funcione o ninguno de ellos lo haga. Este nombre de archivo debe ser único, ya que el sistema no le permitirá tener dos archivos con el mismo nombre.

(ptr) debe permanecer hasta que el archivo se desmonte. Cuando el archivo se desmonte, el sistema llamará a (del)(ptr), lo que le notificará que el sistema ha terminado con el buffer y le dará la oportunidad de liberar sus recursos. (del) puede ser NULL, en cuyo caso el sistema no intentará liberar el buffer.

Si esta función falla, no se llama a (del).

void PHYSFS_permitSymbolicLinks (int allow)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y archivos contienen archivos que son solo punteros a otros archivos. En el sistema de archivos físico, la apertura de dicho enlace abrirá (transparentemente) el archivo al que apunta.

Por defecto, PhysicsFS verificará si un archivo es realmente un enlace simbólico durante las llamadas de apertura y fallará si lo es. De lo contrario, el enlace podría llevarte fuera de las rutas de escritura y búsqueda, y comprometer la seguridad.

Si deseas asumir ese riesgo, llama a esta función con un parámetro distinto de cero. Ten en cuenta que esto es más para aislar el lenguaje de scripting de un programa, en caso de que scripts no confiables intenten comprometer el sistema. En términos generales, un usuario podría tener una razón legítima para configurar un enlace simbólico, por lo que a menos que sientas que hay un peligro específico en permitirlos, deberías permitirlos.

Los enlaces simbólicos solo se verifican explícitamente cuando se tratan nombres de archivo en notación independiente de la plataforma. Es decir, al configurar tus rutas de búsqueda y escritura, etc., nunca se verifican los enlaces simbólicos.

Ten en cuenta que PHYSFS_stat() siempre verificará la ruta especificada; si esa ruta es un enlace simbólico, no se seguirá en ningún caso. Si los enlaces simbólicos no están permitidos a través de esta función, PHYSFS_stat() los ignora y trataría la consulta como si la ruta no existiera en absoluto.

El permiso de enlace simbólico se puede habilitar o deshabilitar en cualquier momento después de haber llamado a PHYSFS_init(), y está deshabilitado por defecto.

Parámetros

allow distinto de cero para permitir enlaces simbólicos, cero para denegar enlaces.

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convert a Latin1 string to a UTF-8 string. Latin1 strings are 8-bits per character: a popular "high ASCII" encoding.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 expands latin1 codepoints over 127 from 1 to 2 bytes, so the string may grow in some cases.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-8 sequence at the end. If the buffer length is 0, this function does nothing.

Please note that we do not supply a UTF-8 to Latin1 converter, since Latin1 can't express most Unicode codepoints. It's a legacy encoding; you should be converting away from it at all times.

Parameters

src Null-terminated source string in Latin1 format.
dst Buffer to store converted UTF-8 string.
len Size, in bytes, of destination buffer.

NAME

PHYSFS_writeUBE16, PHYSFS_writeUBE32, PHYSFS_writeUBE64, PHYSFS_writeULE16, PHYSFS_writeULE32, PHYSFS_writeULE64 - Convert and write an unsigned 16/32/64-bit value in big/little endian format.

SYNOPSIS

#include <physfs.h>

int PHYSFS_writeUBE16(PHYSFS_File *file, PHYSFS_uint16 val);

int PHYSFS_writeUBE32(PHYSFS_File *file, PHYSFS_uint32 val);

int PHYSFS_writeUBE64(PHYSFS_File *file, PHYSFS_uint64 val);

int PHYSFS_writeULE16(PHYSFS_File *file, PHYSFS_uint16 val);

int PHYSFS_writeULE32(PHYSFS_File *file, PHYSFS_uint32 val);

int PHYSFS_writeULE64(PHYSFS_File *file, PHYSFS_uint64 val);

Detailed Description

These functions convert an unsigned integer from the platform's native byte order to the specified endianness (big or little) and write it to the specified file.

These are convenience functions. The platform's native byte order might be big endian or little endian. These functions handle the conversion so you don't have to worry about it.

The 64-bit versions have a potential pitfall: on platforms without any sort of 64-bit integer support, PHYSFS_uint64 may only be 32 bits wide. In such cases, the upper 32 bits of the value will be lost.
