typedef PHYSFS_EnumerateCallbackResult(* PHYSFS_EnumerateCallback) (void *data, const char *origdir, const char *fname)

Valores de retorno posibles de PHYSFS_EnumerateCallback. Firma de función para devoluciones de llamada que enumeran y devuelven resultados.

Estos valores dictan si una devolución de llamada de enumeración debe continuar ejecutándose o detenerse (y por qué se detiene).

PHYSFS_enumerate

Esto es lo mismo que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, excepto que puede devolver un resultado de la devolución de llamada: es decir, si está buscando algo específico, una vez que lo encuentra, puede indicarle a PhysicsFS que deje de enumerar más. Esto se usa con PHYSFS_enumerate(), que esperemos que hayamos hecho bien esta vez. :)

Parámetros

data Puntero de datos definido por el usuario, pasado desde la API que finalmente llamó a la devolución de llamada.
origdir Una cadena que contiene la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio sobre el que solicitó la enumeración, pasado en la devolución de llamada para su conveniencia.
fname El nombre del archivo que se está enumerando. Es posible que no esté en orden alfabético en comparación con otras devoluciones de llamada que se han activado, y no contendrá la ruta completa. Puede recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

Devoluciones

Un valor de PHYSFS_EnumerateCallbackResult. Todos los demás valores no están definidos (actualmente); no los use.

typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Firma de función para devoluciones de llamada que enumeran archivos.

Advertencia

A partir de PhysicsFS 2.1, use PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; le da más control sobre el proceso.

Estos se utilizan para informar una lista de entradas de directorio a un llamador original, un archivo/directorio/enlace simbólico por devolución de llamada. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de ninguna cadena.

Estas devoluciones de llamada se utilizan, a partir de PhysicsFS 1.1, como una alternativa a las funciones que devolverían listas que necesitan ser liberadas con PHYSFS_freeList(). La devolución de llamada significa que la biblioteca no necesita asignar una lista completa y todas las cadenas por adelantado.

Tenga en cuenta que las promesas de orden de datos en las versiones de lista no son necesariamente así en las versiones de devolución de llamada. Consulte la documentación de las API específicas, pero es posible que las cadenas no estén ordenadas como espera y que obtenga cadenas duplicadas.

data Puntero de datos definido por el usuario, pasado desde la API que finalmente llamó a la devolución de llamada.

fname El nombre del archivo que se está enumerando. Es posible que no esté en orden alfabético en comparación con otras devoluciones de llamada que se han activado, y no contendrá la ruta completa. Puede recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

typedef void(* PHYSFS_StringCallback) (void *data, const char *str)

Tenga en cuenta que las promesas de orden de datos en las versiones de lista no son necesariamente así en las versiones de devolución de llamada. Consulte la documentación de las API específicas, pero es posible que las cadenas no estén ordenadas como espera.

Deinitialize the PhysicsFS library. This closes any files opened via PhysicsFS, blanks the search/write paths, frees memory, and invalidates all of your file handles.

int PHYSFS_delete (const char * filename)

Delete a file or directory. (filename) is specified in platform-independent notation in relation to the write dir.

A directory must be empty before this call can delete it.

Deleting a symlink will remove the link, not what it points to, regardless of whether you "permitSymLinks" or not.

So if you've got the write dir set to "C:\mygame\writedir" and call PHYSFS_delete("downloads/maps/level1.map") then the file "C:\mygame\writedir\downloads\maps\level1.map" is removed from the physical filesystem, if it exists and the operating system permits the deletion.

Note that on Unix systems, deleting a file may be successful, but the actual file won't be removed until all processes that have an open filehandle to it (including your program) close their handles.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtener una lista de archivos de un directorio de ruta de búsqueda, utilizando una devolución de llamada definida por la aplicación, con informes de errores. Internamente, PHYSFS_enumerateFiles() simplemente llama a esta función y luego construye una lista antes de devolverla a la aplicación, por lo que la funcionalidad es idéntica excepto por cómo se representa la información a la aplicación.

A diferencia de PHYSFS_enumerateFiles(), esta función no devuelve una matriz. En su lugar, llama a una función especificada por la aplicación una vez por elemento de la ruta de búsqueda:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * Tenemos [%s] en [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // dame más datos, por favor.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

No se garantiza que los elementos enviados a la devolución de llamada estén en ningún orden. No se realiza ninguna ordenación en este nivel, y si la necesita, probablemente debería usar PHYSFS_enumerateFiles() en su lugar, que garantiza la ordenación alfabética. Esta forma informa lo que se descubre en cada archivo antes de pasar al siguiente. Incluso dentro de un archivo, no podemos garantizar el orden en que descubrirá los datos. Cualquier ordenación que encuentre en estas devoluciones de llamada es pura suerte. No confíe en ella. Dado que recorre toda la lista de archivos, puede recibir nombres de archivo duplicados.

Esta API y las devoluciones de llamada en sí mismas son capaces de informar errores. Antes de esta API, las devoluciones de llamada tenían que aceptar cada elemento enumerado, incluso si solo buscaban algo específico y querían detenerse después de eso, o tenían un error grave y no podían alertar a nadie. Además, si PhysicsFS en sí tenía un problema (error de disco o similar), no podía informárselo a la aplicación que llama, solo tendría que omitir elementos o dejar de enumerar por completo, y el que llama no sabría que perdió algunos datos en el camino.

Ahora, el que llama puede estar seguro de que obtuvo un conjunto de datos completo, y su devolución de llamada tiene control si desea que la enumeración se detenga antes. Consulte la documentación de PHYSFS_EnumerateCallback para obtener detalles sobre cómo debe comportarse su devolución de llamada.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

int PHYSFS_mountFile(PHYSFS_File * file, const char * newDir, const char * mountPoint, int appendToPath)

Agrega un archivo, contenido en un manejador PHYSFS_File, a la ruta de búsqueda.

Advertencia

A menos que tenga alguna necesidad especial de bajo nivel, debería usar PHYSFS_mount() en lugar de esto.

¡Los archivos dentro de otros archivos pueden ser muy lentos! Mientras que un PHYSFS_File puede buscar incluso cuando los datos están comprimidos, puede hacerlo rebobinando al principio y descomprimiendo todo antes del punto de búsqueda. El uso normal de archivos puede implicar muchas búsquedas en segundo plano. Como tal, puede encontrar que el uso normal de archivos es extremadamente doloroso si se monta de esta manera. Planifique en consecuencia: si, por ejemplo, tiene un archivo .zip autoextraíble y desea montar algo dentro de él, comprima el contenido del archivo interior y asegúrese de que el archivo .zip exterior no comprima el archivo interior también.

Esta función opera igual que PHYSFS_mount(), pero toma un manejador PHYSFS_File en lugar de una ruta de archivo. Este manejador contiene todos los datos del archivo y se utiliza en lugar de un archivo real en el sistema de archivos físico. El PHYSFS_File puede estar respaldado por un archivo real en el sistema de archivos físico, pero no es necesariamente así. El uso más popular para esto es probablemente montar archivos almacenados dentro de otros archivos.

(newDir) debe ser una cadena única para identificar este archivo. Se utiliza para optimizar la selección del archivero (si lo nombra XXXXX.zip, podríamos intentar primero el archivero ZIP, por ejemplo, o elegir directamente un archivero que solo pueda confiar en que los datos son válidos por la extensión del nombre del archivo). No necesita referirse a un archivo real en absoluto. Si la extensión del nombre del archivo no es útil, el sistema intentará con cada archivero hasta que uno funcione o ninguno de ellos lo haga. Este nombre de archivo debe ser único, ya que el sistema no le permitirá tener dos archivos con el mismo nombre.

(file) debe permanecer hasta que el archivo se desmonte. Cuando el archivo se desmonte, el sistema llamará a PHYSFS_close(file). Si necesita que este manejador sobreviva, tendrá que envolverlo en un PHYSFS_Io y usar PHYSFS_mountIo() en su lugar.

Si esta función falla, no se llama a PHYSFS_close(file).

Parámetros

file El manejador PHYSFS_File que contiene los datos del archivo.
newDir Nombre de archivo que puede representar este flujo.
mountPoint Ubicación en el árbol interpolado donde se "montará" este archivo, en notación independiente de la plataforma. NULL o "" es equivalente a "/".
appendToPath distinto de cero para agregar a la ruta de búsqueda, cero para anteponer.

Retorna

Distinto de cero si se agregó a la ruta, cero en caso de fallo (archivo no válido, etc.). Use PHYSFS_getLastErrorCode() para obtener el error específico.

void PHYSFS_permitSymbolicLinks (int allow)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y archivos contienen archivos que son solo punteros a otros archivos. En el sistema de archivos físico, abrir un enlace de este tipo abrirá (transparentemente) el archivo al que apunta.

Por defecto, PhysicsFS comprobará si un archivo es realmente un enlace simbólico durante las llamadas de apertura y fallará si lo es. De lo contrario, el enlace podría sacarte de las rutas de escritura y búsqueda, y comprometer la seguridad.

Si desea asumir ese riesgo, llame a esta función con un parámetro distinto de cero. Tenga en cuenta que esto es más para aislar el lenguaje de scripting de un programa, en caso de que scripts no confiables intenten comprometer el sistema. En general, un usuario podría tener una razón legítima para crear un enlace simbólico, por lo que a menos que sienta que existe un peligro específico al permitirlos, debería permitirlos.

Los enlaces simbólicos solo se comprueban explícitamente al tratar con nombres de archivo en notación independiente de la plataforma. Es decir, al configurar sus rutas de búsqueda y escritura, etc., nunca se comprueban los enlaces simbólicos.

Tenga en cuenta que PHYSFS_stat() siempre comprobará la ruta especificada; si esa ruta es un enlace simbólico, no se seguirá en ningún caso. Si los enlaces simbólicos no están permitidos a través de esta función, PHYSFS_stat() los ignora y trataría la consulta como si la ruta no existiera en absoluto.

El permiso de enlace simbólico se puede habilitar o deshabilitar en cualquier momento después de haber llamado a PHYSFS_init(), y está deshabilitado por defecto.

Parámetros

allow distinto de cero para permitir enlaces simbólicos, cero para denegarlos.

PHYSFS_writeUBE32, PHYSFS_writeUBE64, PHYSFS_writeULE16, PHYSFS_writeULE32, PHYSFS_writeULE64 — Convert and write an unsigned integer value in a specific endianness.

Detailed Description

These functions are convenience functions for writing unsigned integers to a file, automatically converting them from the platform's native byte order to the specified endianness (bigendian or littleendian).

PHYSFS_writeUBE16, PHYSFS_writeUBE32, PHYSFS_writeUBE64 convert an unsigned integer from the platform's native byte order to big-endian format and write it to the specified file.

PHYSFS_writeULE16, PHYSFS_writeULE32, PHYSFS_writeULE64 convert an unsigned integer from the platform's native byte order to little-endian format and write it to the specified file.
