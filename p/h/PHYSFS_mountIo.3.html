PHYSFS_EnumerateCallback

PHYSFS_enumerate

Esto es lo mismo que PHYSFS_EnumFilesCallback de PhysicsFS 2.0, excepto que puede devolver un resultado del callback: es decir, si estás buscando algo específico, una vez que lo encuentras, puedes indicarle a PhysicsFS que deje de enumerar más. Esto se usa con PHYSFS_enumerate(), que esperamos que lo hayamos hecho bien esta vez. :)

Parámetros

data Puntero de datos definido por el usuario, pasado desde la API que finalmente llamó al callback.
origdir Una cadena que contiene la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio sobre el cual solicitaste la enumeración, pasado en el callback para tu conveniencia.
fname El nombre del archivo que se está enumerando. Puede que no esté en orden alfabético en comparación con otros callbacks que se han ejecutado, y no contendrá la ruta completa. Puedes recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

Devuelve

Un valor de PHYSFS_EnumerateCallbackResult. Todos los demás valores están (actualmente) indefinidos; no los uses.

PHYSFS_EnumerateCallbackResult

typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Firma de función para callbacks que enumeran archivos.

Advertencia

A partir de PhysicsFS 2.1, utiliza PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; te da más control sobre el proceso.

Se utilizan para informar una lista de entradas de directorio a un llamador original, un archivo/directorio/enlace simbólico por callback. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de ninguna cadena.

Estos callbacks se utilizan, a partir de PhysicsFS 1.1, como una alternativa a las funciones que devolverían listas que necesitan ser limpiadas con PHYSFS_freeList(). El callback significa que la biblioteca no necesita asignar una lista completa y todas las cadenas por adelantado.

Ten en cuenta que el orden prometido de los datos en las versiones de lista no es necesariamente así en las versiones de callback. Consulta la documentación de APIs específicas, pero es posible que las cadenas no estén ordenadas como esperas y podrías obtener cadenas duplicadas.

Parámetros

data Puntero de datos definido por el usuario, pasado desde la API que finalmente llamó al callback.
origdir Una cadena que contiene la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio sobre el cual solicitaste la enumeración, pasado en el callback para tu conveniencia.
fname El nombre del archivo que se está enumerando. Puede que no esté en orden alfabético en comparación con otros callbacks que se han ejecutado, y no contendrá la ruta completa. Puedes recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

enum PHYSFS_ErrorCode

Valores que representan causas específicas de fallo. La mayoría de las veces, solo deberías preocuparte por si una operación dada falló o no, pero puede haber ocasiones en las que planees manejar un caso de fallo específico de manera elegante, por lo que proporcionamos códigos de error específicos.

La mayoría de estos errores son un poco vagos, y la mayoría no son cosas que puedas arreglar... si hay un error de permisos, por ejemplo, todo lo que realmente puedes hacer es pasar esa información al usuario y dejar que él decida cómo manejarlo. En la mayoría de estos casos, tu programa solo debería saber que no logró cumplir sus objetivos, y no importarle específicamente por qué.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Get a file listing of a search path's directory, using an application-defined callback, with errors reported. Internally, PHYSFS_enumerateFiles() just calls this function and then builds a list before returning to the application, so functionality is identical except for how the information is represented to the application.

Unlike PHYSFS_enumerateFiles(), this function does not return an array. Rather, it calls a function specified by the application once per element of the search path:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Items sent to the callback are not guaranteed to be in any order whatsoever. There is no sorting done at this level, and if you need that, you should probably use PHYSFS_enumerateFiles() instead, which guarantees alphabetical sorting. This form reports whatever is discovered in each archive before moving on to the next. Even within one archive, we can't guarantee what order it will discover data. Any sorting you find in these callbacks is just pure luck. Do not rely on it. As this walks the entire list of archives, you may receive duplicate filenames.

This API and the callbacks themselves are capable of reporting errors. Prior to this API, callbacks had to accept every enumerated item, even if they were only looking for a specific thing and wanted to stop after that, or had a serious error and couldn't alert anyone. Furthermore, if PhysicsFS itself had a problem (disk error or whatnot), it couldn't report it to the calling app, it would just have to skip items or stop enumerating outright, and the caller wouldn't know it had lost some data along the way.

Now the caller can be sure it got a complete data set, and its callback has control if it wants enumeration to stop early. See the documentation for PHYSFS_EnumerateCallback for details on how your callback should behave.

Parameters

dir Directory, in platform-independent notation, to enumerate.
c Callback function to notify about search path elements.
d Application-defined data passed to callback. Can be NULL.

Returns

non-zero on success, zero on failure. Use PHYSFS_getLastErrorCode() to obtain the specific error. If the callback returns PHYSFS_ENUM_STOP to stop early, this will be considered success. Callbacks returning PHYSFS_ENUM_ERROR will make this function return zero and set the error code to PHYSFS_ERR_APP_CALLBACK.

Gets the "pref dir". This is where the user can write files (preferences and save games, etc) specific to your application. This directory is unique per-user and per-application.

This function figures out the appropriate location on the native file system, creates the directory if necessary, and returns a string in system notation, suitable for passing to PHYSFS_setWriteDir().

On Windows, it might look like: "C:\\Users\\bob\\AppData\\Roaming\\My Company\\My Program Name"

On Linux, it might look like: "/home/bob/.local/share/My Program Name"

On Mac OS X, it might look like: "/Users/bob/Library/Application Support/My Program Name"

(etc.)

It is recommended that you use this directory path for your write directory, and also put it at the beginning of your search path. Older versions of PhysicsFS offered only PHYSFS_getUserDir() and left it up to the user to figure out where to place files under that tree. This function finds the correct location for any platform, which not only changes between operating systems, but also between versions of the same operating system.

You specify the name of your organization (if not a real org, your name or an Internet domain you own might work). The name of your application. These should be sensible names.

Both the (org) and (app) strings can become part of a directory name, so please follow these rules:

  • Try to use the same organization string (including case sensitivity) for all applications that use this function.
  • Use a unique string for each application and make sure it doesn't change for an application after you decide on it.
  • Unicode characters are valid, as long as they're encoded as UTF-8, but...
  • ...only use letters, numbers, and spaces. Avoid characters like "Game Name 2: Bad Guy's Revenge!" ... "Game Name 2" is sufficient.

The pointer returned by this function remains valid until you call it again, or call PHYSFS_deinit(). While not fast, it should be called once at startup, and the string copied if you need it.

You should assume that the path returned by this function is the only safe place to write files (and that PHYSFS_getUserDir() and PHYSFS_getBaseDir(), despite the fact that they may be writable, or even parents of the returned path, are not where you should be writing).

Parameters:

org name of your organization.
app name of your application.

Return value:

System-notation user directory string. NULL if there was a problem (directory creation failed, etc).

Determines where a file is located in the search path. The file is specified in system-agnostic notation. The name returned will be the search path element where the file was found, which may be a directory or an archive file. int PHYSFS_mount (const char *newDir, const char *mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

Parameters

newDir directory or archive to add to the path, in platform-dependent notation.
mountPoint Location in the interpolated tree that this archive will be "mounted", in platform-independent notation. NULL or "" is equivalent to "/".
appendToPath nonzero to append to search path, zero to prepend.

Returns

nonzero if added to path, zero on failure (bogus archive, dir missing, etc). Use PHYSFS_getLastErrorCode() to obtain the specific error.

int PHYSFS_mountIo (PHYSFS_File * io, const char * newDir, const char * mountPoint, int appendToPath)

Añade un archivo, contenido en un manejador PHYSFS_File, a la ruta de búsqueda.

Advertencia

A menos que tenga alguna necesidad especial de bajo nivel, debería usar PHYSFS_mount() en lugar de esta función.

¡Los archivos dentro de otros archivos pueden ser muy lentos! Mientras que un PHYSFS_File puede buscar incluso cuando los datos están comprimidos, puede hacerlo retrocediendo al inicio y descomprimiendo todo antes del punto de búsqueda. El uso normal de archivos puede realizar muchas búsquedas en segundo plano. Como tal, podría encontrar que el uso normal de archivos es extremadamente engorroso si se monta de esta manera. Planifique en consecuencia: si, por ejemplo, tiene un archivo .zip autoextraíble y desea montar algo dentro de él, comprima el contenido del archivo interno y asegúrese de que el archivo .zip externo no comprima también el archivo interno.

Esta función opera igual que PHYSFS_mount(), pero toma un manejador PHYSFS_File en lugar de una ruta de archivo. Este manejador contiene todos los datos del archivo y se utiliza en lugar de un archivo real en el sistema de archivos físico. El PHYSFS_File puede estar respaldado por un archivo real en el sistema de archivos físico, pero no necesariamente. El uso más popular para esto es probablemente montar archivos almacenados dentro de otros archivos.

(newDir) debe ser una cadena única para identificar este archivo. Se utiliza para optimizar la selección del archivero (si lo nombra XXXXX.zip, podríamos intentar primero el archivero ZIP, por ejemplo, o elegir directamente un archivero que solo pueda confiar en que los datos son válidos por la extensión del nombre del archivo). No es necesario que se refiera a un archivo real en absoluto. Si la extensión del nombre del archivo no es útil, el sistema intentará con cada archivero hasta que uno funcione o ninguno lo haga. Este nombre de archivo debe ser único, ya que el sistema no le permitirá tener dos archivos con el mismo nombre.

(file) debe permanecer hasta que el archivo se desmonte. Cuando el archivo se desmonte, el sistema llamará a PHYSFS_close(file). Si necesita que este manejador persista, tendrá que envolverlo en un PHYSFS_Io y usar PHYSFS_mountIo() en su lugar.

Si esta función falla, no se llama a PHYSFS_close(file).

newDir Nombre de archivo que puede representar este flujo.

appendToPath distinto de cero para añadir a la ruta de búsqueda, cero para anteponer.

Retorna

Distinto de cero si se añadió a la ruta, cero en caso de fallo (archivo inválido, etc.). Use PHYSFS_getLastErrorCode() para obtener el error específico.

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Para asegurar que el búfer de destino sea lo suficientemente grande para la conversión, por favor, asigna un búfer que sea el doble del tamaño del búfer de origen. UTF-8 expande los puntos de código Latin1 mayores que 127 de 1 a 2 bytes, por lo que la cadena puede crecer en algunos casos.

Ten en cuenta que no proporcionamos un conversor de UTF-8 a Latin1, ya que Latin1 no puede expresar la mayoría de los puntos de código Unicode. Es una codificación heredada; deberías estar alejándote de ella en todo momento.

void PHYSFS_utf8FromUcs2 (const PHYSFS_uint16 * src, char * dst, PHYSFS_uint64 len)

Convierte una cadena UCS-2 a una cadena UTF-8.

Advertencia

casi con toda seguridad deberías usar PHYSFS_utf8FromUtf16(), que estuvo disponible en PhysicsFS 2.1, a menos que sepas lo que estás haciendo.

Esta función no informará de un error si hay valores UCS-2 inválidos en la cadena de origen. Los reemplazará con un carácter '?' y continuará.

These functions convert a value from the platform's native byte order to the specified byte order (big-endian or little-endian), and then write it to the given file handle.

These are convenience functions. You could achieve the same effect manually using PHYSFS_write(3), but these functions handle the byte-swapping for you.
