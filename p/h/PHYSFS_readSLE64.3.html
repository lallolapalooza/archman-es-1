typedef PHYSFS_EnumerateCallbackResult(* PHYSFS_EnumerateCallback) (void *data, const char *origdir, const char *fname)

Possible return values from PHYSFS_EnumerateCallback. Function signature for callbacks that enumerate and return results.

These values dictate if an enumeration callback should continue to fire, or stop (and why it is stopping).

See also

PHYSFS_EnumerateCallback

PHYSFS_enumerate

This is the same thing as PHYSFS_EnumFilesCallback from PhysicsFS 2.0, except it can return a result from the callback: namely: if you're looking for something specific, once you find it, you can tell PhysicsFS to stop enumerating further. This is used with PHYSFS_enumerate(), which we hopefully got right this time. :)

Parameters

data User-defined data pointer, passed through from the API that eventually called the callback.
origdir A string containing the full path, in platform-independent notation, of the directory containing this file. In most cases, this is the directory on which you requested enumeration, passed in the callback for your convenience.
fname The filename that is being enumerated. It may not be in alphabetical order compared to other callbacks that have fired, and it will not contain the full path. You can recreate the fullpath with $origdir/$fname ... The file can be a subdirectory, a file, a symlink, etc.

Returns

A value from PHYSFS_EnumerateCallbackResult. All other values are (currently) undefined; don't use them.

typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Function signature for callbacks that enumerate files.

Warning

As of PhysicsFS 2.1, Use PHYSFS_EnumerateCallback with PHYSFS_enumerate() instead; it gives you more control over the process.

These are used to report a list of directory entries to an original caller, one file/dir/symlink per callback. All strings are UTF-8 encoded. Functions should not try to modify or free any string's memory.

These callbacks are used, starting in PhysicsFS 1.1, as an alternative to functions that would return lists that need to be cleaned up with PHYSFS_freeList(). The callback means that the library doesn't need to allocate an entire list and all the strings up front.

Be aware that promised data ordering in the list versions are not necessarily so in the callback versions. Check the documentation on specific APIs, but strings may not be sorted as you expect and you might get duplicate strings.

Parameters

data User-defined data pointer, passed through from the API that eventually called the callback.
origdir A string containing the full path, in platform-independent notation, of the directory containing this file. In most cases, this is the directory on which you requested enumeration, passed in the callback for your convenience.
fname The filename that is being enumerated. It may not be in alphabetical order compared to other callbacks that have fired, and it will not contain the full path. You can recreate the fullpath with $origdir/$fname ... The file can be a subdirectory, a file, a symlink, etc.

enum PHYSFS_ErrorCode

Values that represent specific causes of failure. Most of the time, you should only concern yourself with whether a given operation failed or not, but there may be occasions where you plan to handle a specific failure case gracefully, so we provide specific error codes.

Most of these errors are a little vague, and most aren't things you can fix...if there's a permission error, for example, all you can really do is pass that information on to the user and let them figure out how to handle it. In most these cases, your program should only care that it failed to accomplish its goals, and not care specifically why.

int PHYSFS_delete(const char *filename)

Delete a file or directory. (filename) is specified in platform-independent notation in relation to the write dir.

A directory must be empty before this call can delete it.

Deleting a symlink will remove the link, not what it points to, regardless of whether you "permitSymLinks" or not.

So if you've got the write dir set to "C:\mygame\writedir" and call PHYSFS_delete("downloads/maps/level1.map") then the file "C:\mygame\writedir\downloads\maps\level1.map" is removed from the physical filesystem, if it exists and the operating system permits the deletion.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Obtener una lista de archivos de un directorio de la ruta de búsqueda, utilizando una función de devolución de llamada definida por la aplicación, con informes de errores. Internamente, PHYSFS_enumerateFiles() simplemente llama a esta función y luego crea una lista antes de devolverla a la aplicación, por lo que la funcionalidad es idéntica excepto por cómo se representa la información a la aplicación.

A diferencia de PHYSFS_enumerateFiles(), esta función no devuelve una matriz. Más bien, llama a una función especificada por la aplicación una vez por elemento de la ruta de búsqueda:

{
    printf(" * Tenemos [%s] en [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // dame más datos, por favor.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

No se garantiza que los elementos enviados a la función de devolución de llamada estén en ningún orden específico. No se realiza ninguna ordenación en este nivel, y si la necesita, probablemente debería usar PHYSFS_enumerateFiles() en su lugar, que garantiza la ordenación alfabética. Esta forma informa lo que se descubre en cada archivo antes de pasar al siguiente. Incluso dentro de un archivo, no podemos garantizar el orden en que descubrirá los datos. *Cualquier ordenación que encuentre en estas llamadas de devolución es pura suerte. No confíe en ella.* Dado que recorre toda la lista de archivos, puede recibir nombres de archivo duplicados.

Esta API y las propias funciones de devolución de llamada son capaces de informar errores. Antes de esta API, las funciones de devolución de llamada tenían que aceptar cada elemento enumerado, incluso si solo buscaban algo específico y querían detenerse después de eso, o si tenían un error grave y no podían alertar a nadie. Además, si PhysicsFS en sí mismo tenía un problema (error de disco o similar), no podía informarlo a la aplicación que lo llamaba, solo tendría que omitir elementos o dejar de enumerar por completo, y el llamador no sabría que había perdido algunos datos en el camino.

Ahora el llamador puede estar seguro de que obtuvo un conjunto de datos completo, y su función de devolución de llamada tiene control si desea que la enumeración se detenga antes. Consulte la documentación de PHYSFS_EnumerateCallback para obtener detalles sobre cómo debe comportarse su función de devolución de llamada.

Get the last error code. PhysicsFS uses thread-local storage to keep track of error states. This means that if thread A calls a function that fails, and then thread B calls a function that fails, thread B will not affect thread A's error state.

However, this also means that if you need to capture an error code and then perform another PhysicsFS operation that might fail, you must call PHYSFS_getLastErrorCode() to get the error code first. Otherwise, the subsequent operation will overwrite the original error state.

This function is safe to call even if no error has occurred; it will simply return PHYSFS_ERR_OK.

Note

Calling PHYSFS_getLastErrorCode() and then PHYSFS_getErrorByCode() will reset the same thread-specific error state. Calling one will wipe out the other's data. If you need both, call PHYSFS_getLastErrorCode(), then pass that value to PHYSFS_getErrorByCode().

Generally, applications should only concern themselves with whether a given function failed; however, if you require more specifics, you can try this function to glean information, if there's some specific problem you're expecting and plan to handle. But with most things that involve file systems, the best course of action is usually to give up, report the problem to the user, and let them figure out what should be done about it. For that, you might prefer PHYSFS_getErrorByCode() instead.

PHYSFS_mount

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

Advertencia

A menos que tenga alguna necesidad especial de bajo nivel, debería usar PHYSFS_mount() en lugar de esto.

¡Los archivos dentro de archivos pueden ser muy lentos! Mientras que un PHYSFS_File puede buscar incluso cuando los datos están comprimidos, puede hacerlo retrocediendo al inicio y descomprimiendo todo antes del punto de búsqueda. El uso normal de archivos puede realizar muchas búsquedas en segundo plano. Como tal, podría encontrar que el uso normal de archivos es extremadamente doloroso si se monta de esta manera. Planifique en consecuencia: si, por ejemplo, tiene un archivo .zip que se autoextrae y desea montar algo dentro de él, comprima el contenido del archivo interno y asegúrese de que el archivo .zip externo no comprima el archivo interno también.

Esta función opera de manera similar a PHYSFS_mount(), pero toma un manejador PHYSFS_File en lugar de una ruta de archivo. Este manejador contiene todos los datos del archivo y se utiliza en lugar de un archivo real en el sistema de archivos físico. El PHYSFS_File puede estar respaldado por un archivo real en el sistema de archivos físico, pero no necesariamente lo está. El uso más popular para esto es probablemente montar archivos almacenados dentro de otros archivos.

void PHYSFS_permitSymbolicLinks (int allow)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y arquitecturas contienen archivos que son simples punteros a otros archivos. Al abrir un enlace simbólico en un sistema de archivos físico, se abre transparentemente el archivo al que apunta.

Por defecto, PhysicsFS verificará si un archivo es realmente un enlace simbólico durante las llamadas de apertura y fallará si lo es. De lo contrario, el enlace podría llevarte fuera de los caminos de lectura y escritura, comprometiendo la seguridad.

Si deseas asumir ese riesgo, llama a esta función con un valor distinto de cero. Ten en cuenta que esto es más para el sandboxing de lenguajes de script de un programa, en caso de que scripts no confiables intenten comprometer el sistema. Por lo general, un usuario podría tener una razón válida para crear un enlace simbólico, por lo que no deberías deshabilitarlo, a menos que sientas que existe un riesgo específico.

Los enlaces simbólicos solo se comprueban cuando se manejan nombres de archivo en notación independiente de la plataforma. Es decir, cuando se configuran tus rutas de búsqueda y escritura, etc., nunca se comprueban los enlaces simbólicos.

Nota: PHYSFS_stat() siempre comprueba la ruta especificada; si es un enlace simbólico, no se seguirá en ningún caso. Si los enlaces simbólicos no están permitidos a través de esta función, PHYSFS_stat() los ignorará y tratará la consulta como si la ruta no existiera.

La permisión de enlaces simbólicos puede habilitarse o deshabilitarse en cualquier momento después de haber llamado PHYSFS_init(), y está deshabilitada por defecto.

Parámetros

allow distinto de cero para permitir enlaces simbólicos, cero para deshabilitar el enlace.

void PHYSFS_setBuffer(PHYSFS_File *handle, unsigned int bufsize)

Establece el tamaño del búfer para un archivo dado. Esto es principalmente útil para controlar el rendimiento de E/S, pero puede hacer que las lecturas sean menos transparentes.

Al establecer el tamaño del búfer en un valor distinto de cero, se asigna un búfer para el archivo. Si se solicita un tamaño de búfer más grande que el búfer existente, se realocará el búfer existente. Si se solicita un tamaño de búfer más pequeño, se recortará el búfer existente y se descartarán los datos en exceso. Un tamaño de búfer de cero liberará cualquier búfer asignado al archivo.

Cuando se llama a esta función con un tamaño de búfer distinto de cero, se vaciará implícitamente el búfer existente. ¡Comprueba tus valores de retorno!

La búsqueda, etc., tiene en cuenta el búfer de forma transparente.

Puedes cambiar el tamaño de un búfer existente llamando a esta función más de una vez en el mismo archivo. Establecer el tamaño del búfer en cero liberará un búfer existente.

Los manejadores de archivos de PhysicsFS no tienen búfer por defecto.

¡Por favor, comprueba el valor de retorno de esta función! Los fallos pueden incluir la imposibilidad de buscar hacia atrás en un archivo de solo lectura al eliminar el búfer, la imposibilidad de asignar el búfer y la imposibilidad de volcar el búfer al disco, entre otros problemas inesperados.

Parámetros

handle manejador devuelto por PHYSFS_open*().
bufsize tamaño, en bytes, del búfer a asignar.

Devuelve

distinto de cero si tiene éxito, cero en caso de error.

void PHYSFS_setErrorCode(PHYSFS_ErrorCode code)

Establece el código de error del hilo actual. Esto te permite establecer el valor que devolverá la próxima llamada a PHYSFS_getLastErrorCode(). Esto reemplazará cualquier código de error existente, ya sea establecido por tu aplicación o internamente por PhysicsFS.

Los códigos de error se almacenan por hilo; lo que establezcas aquí no será accesible para otro hilo.

Cualquier llamada a PhysicsFS puede cambiar el código de error actual, por lo que cualquier código que establezcas aquí es algo frágil, y por lo tanto, no deberías construir ningún marco de reporte de errores serio sobre esta función. El objetivo principal de esta función es permitir que las implementaciones de PHYSFS_Io establezcan el estado de error, que generalmente se devolverá a tu aplicación cuando PhysicsFS realice una llamada a PHYSFS_Io que falle internamente.

A esta función no le importa si el código de error es un valor conocido por PhysicsFS o no (pero PHYSFS_getErrorByCode() devolverá NULL para valores desconocidos). El valor será reportado sin ser modificado por PHYSFS_getLastErrorCode().

Parámetros

code Código de error que se convertirá en el nuevo estado de error del hilo actual.

Puedes cambiar la raíz de un archivo en cualquier momento, alterando el árbol de archivos interpolado (dependiendo de dónde cambien las rutas, un archivo diferente puede estar proporcionando varios archivos). Si estableces la raíz en NULL o "/", el archivo se tratará como si no se hubiera establecido ninguna raíz especial (como si el archivo se hubiera montado normalmente).

Cambiar la raíz solo afecta a las operaciones futuras sobre nombres de ruta; un archivo que se abrió desde una ruta que cambió debido a un setRoot no se verá afectado.

Establecer una nueva raíz no se limita a los archivos en la ruta de búsqueda; también puedes establecer una en el directorio de escritura, lo que podría ser útil si tienes archivos abiertos para escritura y, por lo tanto, no puedes cambiar el directorio de escritura en este momento.

No es un error establecer un subdirectorio que no existe como raíz de un archivo; sin embargo, no se verán archivos en este caso. Si los directorios faltantes terminan siendo creados (un mkdir al sistema de archivos físico, etc.), esto se reflejará en el árbol interpolado.

Parámetros

archive directorio/archivo sobre el que cambiar la raíz.
subdir nuevo subdirectorio que se convertirá en la raíz de este archivo.

Devuelve

distinto de cero en caso de éxito, cero en caso de fallo. Usa PHYSFS_getLastErrorCode() para obtener el error específico.

UTF-16 *es* UCS-2, excepto por los caracteres que tienen 4 bytes, que de todas formas no son representables en UCS-2. Si no estás seguro, deberías estar usando UTF-16 en este momento en Windows.

Para asegurarte de que el búfer de destino sea lo suficientemente grande para la conversión, asigna un búfer que sea el doble del tamaño del búfer de origen. UTF-8 usa de uno a cuatro bytes por carácter, pero UTF-16 siempre usa de dos a cuatro, ¡así que una cadena completamente ASCII de bajo nivel duplicará su tamaño! Los caracteres UTF-16 que ocuparían cuatro bytes también ocupan cuatro bytes en UTF-8, por lo que no necesitas asignar 4 veces el espacio por si acaso: el doble será suficiente.

Las cadenas que no caben en el búfer de destino se truncarán, pero siempre estarán terminadas en nulo y nunca tendrán un par sustituto UTF-16 incompleto al final. Si la longitud del búfer es 0, esta función no hace nada.

Parámetros

src Cadena de origen terminada en nulo en formato UTF-8.
dst Búfer para almacenar la cadena UTF-16 convertida.
len Tamaño, en bytes, del búfer de destino.

PHYSFS_sint64 PHYSFS_writeBytes(PHYSFS_File * handle, const void * buffer, PHYSFS_uint64 len)

Escribe datos en un manejador de archivo de PhysicsFS. El archivo debe estar abierto para escritura.

Tenga en cuenta que aunque (len) es un entero sin signo de 64 bits, estás limitado a 63 bits (9223372036854775807 bytes), por lo que podemos devolver un valor negativo en caso de error. Si la longitud es mayor que 0x7FFFFFFFFFFFFFFF, esta función fallará inmediatamente. Para sistemas sin un tipo de dato de 64 bits, estás limitado a 31 bits (0x7FFFFFFF, o 2147483647 bytes). Confiamos en que la mayoría de las cosas no necesitarán realizar múltiples gigabytes de E/S en una sola llamada, ¡pero ¿por qué limitar las cosas?
