1.0 API compatibility define. PHYSFS_file is identical to PHYSFS_File. This #define is here for backwards compatibility with the 1.0 API, which had an inconsistent capitalization convention in this case. New code should use PHYSFS_File, as this #define may go away someday.

typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Firma de función para callbacks que enumeran archivos.

Advertencia

A partir de PhysicsFS 2.1, use PHYSFS_EnumerateCallback con PHYSFS_enumerate() en su lugar; le da más control sobre el proceso.

Se utilizan para informar una lista de entradas de directorio a un llamador original, un archivo/directorio/enlace simbólico por callback. Todas las cadenas están codificadas en UTF-8. Las funciones no deben intentar modificar ni liberar la memoria de ninguna cadena.

Estos callbacks se utilizan, a partir de PhysicsFS 1.1, como una alternativa a las funciones que devolverían listas que deben limpiarse con PHYSFS_freeList(). El callback significa que la biblioteca no necesita asignar una lista completa y todas las cadenas por adelantado.

Tenga en cuenta que el orden de los datos prometido en las versiones de lista no es necesariamente así en las versiones de callback. Consulte la documentación de APIs específicas, pero es posible que las cadenas no estén ordenadas como espera y que reciba cadenas duplicadas.

origdir Una cadena que contiene la ruta completa, en notación independiente de la plataforma, del directorio que contiene este archivo. En la mayoría de los casos, este es el directorio sobre el cual solicitó la enumeración, pasado en el callback para su conveniencia.
fname El nombre del archivo que se está enumerando. Es posible que no esté en orden alfabético en comparación con otros callbacks que se hayan disparado, y no contendrá la ruta completa. Puede recrear la ruta completa con $origdir/$fname ... El archivo puede ser un subdirectorio, un archivo, un enlace simbólico, etc.

enum PHYSFS_ErrorCode

Valores que representan causas específicas de falla. La mayoría de las veces, solo debe preocuparse por si una operación dada falló o no, pero puede haber ocasiones en las que planee manejar un caso de falla específico con gracia, por lo que proporcionamos códigos de error específicos.

La mayoría de estos errores son un poco vagos, y la mayoría no son cosas que pueda arreglar... si hay un error de permiso, por ejemplo, todo lo que realmente puede hacer es pasar esa información al usuario y dejar que descubran cómo manejarlo. En la mayoría de estos casos, su programa solo debería preocuparse de que no logró sus objetivos, y no preocuparse específicamente por qué.

int PHYSFS_deinit (void )

Deinitialize the PhysicsFS library. This closes any files opened via PhysicsFS, blanks the search/write paths, frees memory, and invalidates all of your file handles.

Note that this call can FAIL if there's a file open for writing that refuses to close (for example, the underlying operating system was buffering writes to network filesystem, and the fileserver has crashed, or a hard drive has failed, etc). int PHYSFS_delete (const char * filename)

Delete a file or directory. (filename) is specified in platform-independent notation in relation to the write dir.

A directory must be empty before this call can delete it.

Deleting a symlink will remove the link, not what it points to, regardless of whether you "permitSymLinks" or not.

So if you've got the write dir set to "C:\mygame\writedir" and call PHYSFS_delete("downloads/maps/level1.map") then the file "C:\mygame\writedir\downloads\maps\level1.map" is removed from the physical filesystem, if it exists and the operating system permits the deletion.

int PHYSFS_init (const char * argv0)

Inicializar la biblioteca PhysicsFS. Esto debe llamarse antes que cualquier otra función de PhysicsFS.

Esto debe llamarse antes de cualquier intento de cambiar el directorio de trabajo actual de su proceso.

Advertencia

En Android, argv0 debe ser un puntero no NULL a una estructura PHYSFS_AndroidInit. Esta estructura debe contener un JNIEnv * válido y un jobject JNI de un Context (el contexto de la aplicación o la Actividad actual están bien). Ambos se convierten a void * para que no necesitemos incluir jni.h dondequiera que se incluya physfs.h. PhysicsFS utiliza estos objetos para consultar algunos detalles del sistema. PhysicsFS no mantiene una referencia al JNIEnv o Context más allá de la llamada a PHYSFS_init(). Si pasa NULL aquí, PHYSFS_init aún puede tener éxito, pero PHYSFS_getBaseDir() y PHYSFS_getPrefDir() serán incorrectos.

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Añadir un archivo o directorio a la ruta de búsqueda. Si es un duplicado, la entrada no se añade de nuevo, aunque la función tenga éxito. No puede añadir el mismo archivo a dos puntos de montaje diferentes: la comprobación de duplicados se realiza contra el archivo y no contra el punto de montaje.

Cuando monta un archivo, se añade a un sistema de archivos virtual... todos los archivos de todos los archivos se interpolan en un único árbol de archivos jerárquico. Dos archivos montados en el mismo lugar (o un archivo con archivos que se solapan con otro punto de montaje) pueden tener archivos que se solapan: en tal caso, se selecciona el archivo anterior en la ruta de búsqueda, y los otros archivos son inaccesibles para la aplicación. Esto permite que los archivos se utilicen para anular revisiones anteriores; puede utilizar el mecanismo de montaje para colocar archivos en un punto específico del árbol de archivos y evitar solapamientos; esto es útil para mods descargables que podrían pisar datos de la aplicación o entre sí, por ejemplo.

El punto de montaje no necesita existir antes de montarlo, lo que es diferente de lo que pueden esperar aquellos familiarizados con el concepto de "montaje" de Unix. Además, se pueden montar varios archivos en el mismo punto de montaje, o los puntos de montaje y el contenido de los archivos pueden solaparse... el mecanismo de interpolación sigue funcionando como de costumbre.

Se permite especificar un enlace simbólico a un archivo o directorio aquí, independientemente del estado de PHYSFS_permitSymbolicLinks(). Esa función solo se ocupa de los enlaces simbólicos dentro del directorio o archivo montado.

appendToPath distinto de cero para añadir a la ruta de búsqueda, cero para anteponer.

void PHYSFS_permitSymbolicLinks (int allow)

Habilita o deshabilita el seguimiento de enlaces simbólicos. Algunos sistemas de archivos físicos y arquitecturas contienen archivos que son solo punteros a otros archivos. Al abrir un enlace simbólico en un sistema físico, se abrirá transparentemente el archivo al que se apunta.

Por defecto, PhysicsFS verificará si un archivo es realmente un enlace simbólico durante las llamadas de apertura y fallará si lo es. De lo contrario, el enlace podría llevarte fuera del camino de lectura y búsqueda, comprometiendo la seguridad.

Si deseas asumir ese riesgo, llama a esta función con un valor distinto de cero. Ten en cuenta que esto es más para el sandboxing de un lenguaje de scripting en caso de que scripts no confiables intenten comprometer el sistema. En general, un usuario podría tener una razón válida para crear un enlace simbólico, por lo que no deberías deshabilitarlo a menos que percibas un peligro específico.

Los enlaces simbólicos solo se verifican cuando se manejan nombres de archivos en notación independiente de la plataforma. Es decir, cuando se establecen tus rutas de búsqueda y escritura, etc., los enlaces simbólicos nunca se verifican.

Nota: PHYSFS_stat() siempre verifica la ruta especificada; si esa ruta es un enlace simbólico, se ignora en cualquier caso. Si no se permite a través de esta función, PHYSFS_stat() ignora los enlaces simbólicos y trataría la consulta como si la ruta no existiera.

La permisibilidad de enlaces simbólicos puede habilitarse o deshabilitarse después de haber llamado PHYSFS_init(), y está deshabilitada por defecto.

Parámetros

allow distinto de cero para permitir enlaces simbólicos, cero para deshabilitar el enlace.

int PHYSFS_utf8stricmp (const char * str1, const char * str2)

Comparación insensible a mayúsculas/minúsculas de dos cadenas UTF-8. Esta es una sustitución de strcasecmp/stricmp que espera que ambas cadenas estén en formato UTF-8. Realizará un "plegado de mayúsculas" para decidir si los códigos Unicode en las cadenas coinciden.

Si ambas cadenas son solo caracteres de bajo ASCII, esto hará lo correcto, ya que también es UTF-8 válido. Si hay algún carácter de alto ASCII, ¡esto no hará lo que esperas!

Estará informando cuál de las cadenas es "mayor que" la otra, pero debes tener en cuenta que esto no significa necesariamente nada: 'a' puede ser "menor que" 'b', pero una kuten japonesa no tiene una relación alfabética significativa con una lambda griega, pero ser capaz de asignar un valor fiable hace que los algoritmos de ordenación sean posibles, aunque no sean completamente racionales. La mayoría de los casos deberían tratar el valor devuelto como "igual" o "no igual".

Al igual que stricmp, espera que ambas cadenas estén terminadas en nulo.

Parámetros

str1 Cadena a comparar.
str2 Cadena a comparar.

Devuelve

-1 si str1 es "menor que" str2, 1 si "mayor que", 0 si son iguales.

PHYSFS_sint64 PHYSFS_writeBytes (PHYSFS_File * handle, const void * buffer, PHYSFS_uint64 len)

Escribe datos en un manejador de archivo PhysicsFS. El archivo debe estar abierto para escritura.

Por favor, ten en cuenta que aunque (len) es un entero sin signo de 64 bits, estás limitado a 63 bits (9223372036854775807 bytes), por lo que podemos devolver un valor negativo en caso de error. Si la longitud es mayor que 0x7FFFFFFFFFFFFFFF, esta función fallará inmediatamente. Para sistemas sin un tipo de dato de 64 bits, estás limitado a 31 bits (0x7FFFFFFF, o 2147483647 bytes).
