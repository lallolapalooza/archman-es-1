NOMBRE

Parse::RecDescent - Generar analizadores descendentes recursivos

VERSIÓN

Este documento describe la versión 1.967015 de Parse::RecDescent publicada el 4 de abril de 2017.

SINOPSIS

use Parse::RecDescent;
# Generar un analizador a partir de la especificación en $grammar:
    $parser = new Parse::RecDescent ($grammar);
# Generar un analizador a partir de la especificación en $othergrammar
    $anotherparser = new Parse::RecDescent ($othergrammar);
# Analizar $text usando la regla 'startrule' (que debe estar
# definida en $grammar):
   $parser->startrule($text);
# Analizar $text usando la regla 'otherrule' (que también debe
# estar definida en $grammar):
    $parser->otherrule($text);
# Cambiar el patrón del prefijo de token universal
# antes de construir una gramática
# (el valor predeterminado es: '\s*'):
   $Parse::RecDescent::skip = '[ \t]+';
# Reemplazar producciones de reglas existentes (o crear nuevas)
# con las producciones definidas en $newgrammar:
   $parser->Replace($newgrammar);
# Extender reglas existentes (o crear nuevas)
# añadiendo producciones adicionales definidas en $moregrammar:
   $parser->Extend($moregrammar);
# Banderas globales (útiles como argumentos de línea de comandos con -s):
   $::RD_ERRORS       # si no está indefinido, informar errores fatales
   $::RD_WARN         # si no está indefinido, también informar problemas no fatales
   $::RD_HINT         # si está definido, también sugerir soluciones
   $::RD_TRACE        # si está definido, también rastrear el comportamiento de los analizadores
   $::RD_AUTOSTUB     # si está definido, genera "stubs" para reglas indefinidas
   $::RD_AUTOACTION   # si está definido, añade la acción especificada a las producciones

DESCRIPCIÓN

Visión general

Parse::RecDescent genera incrementalmente analizadores de texto descendentes recursivos a partir de sencillas especificaciones de gramática tipo yacc. Proporciona:

  • Expresiones regulares o cadenas literales como terminales (tokens),
  • Múltiples producciones (no contiguas) para cualquier regla,
  • Subreglas repetidas y opcionales dentro de las producciones,
  • Acceso completo a Perl dentro de las acciones especificadas como parte de la gramática,
  • Informes de errores sencillos y automatizados durante la generación del analizador y el análisis,
  • La capacidad de comprometerse, retirarse o rechazar producciones particulares durante un análisis,
  • La capacidad de pasar datos hacia arriba y hacia abajo en el árbol de análisis ("hacia abajo" a través de listas de argumentos de subreglas, "hacia arriba" a través de valores de retorno de subreglas)
  • Extensión incremental de la gramática de análisis (incluso durante un análisis),
  • Precompilación de objetos analizadores,
  • Resolución de conflictos de reducción-reducción definible por el usuario a través de la "puntuación" de producciones coincidentes.

Usando "Parse::RecDescent"

Los objetos analizadores se crean llamando a "Parse::RecDescent::new", pasando una especificación de gramática (ver las siguientes subsecciones). Si la gramática es correcta, "new" devuelve una referencia bendecida que luego se puede usar para iniciar el análisis a través de cualquier regla especificada en la gramática original. Una secuencia típica se ve así:

$grammar = q {
    # ESPECIFICACIÓN DE GRAMÁTICA AQUÍ
     };
$parser = new Parse::RecDescent ($grammar) or die "¡Gramática incorrecta!\n";
# adquirir $text
defined $parser->startrule($text) or print "¡Texto incorrecto!\n";

La regla a través de la cual se inicia el análisis debe estar explícitamente definida en la gramática (es decir, para el ejemplo anterior, la gramática debe incluir una regla de la forma: "startrule: <subreglas>".

Si la regla de inicio tiene éxito, se devuelve su valor (ver más abajo). El fracaso en la generación del analizador original o el fracaso en la coincidencia de un texto se indica devolviendo "undef". Tenga en cuenta que es fácil configurar gramáticas que pueden tener éxito, pero que devuelven un valor de 0, "0" o "". Así que no se sienta tentado a escribir:

$parser->startrule($text) or print "¡Texto incorrecto!\n";

Normalmente, el analizador no tiene ningún efecto sobre el texto original. Así que en el ejemplo anterior, el valor de $text no cambiaría después de haber sido analizado.

Si, sin embargo, el texto a coincidir se pasa por referencia:

$parser->startrule(\$text)

entonces cualquier texto que se haya consumido durante la coincidencia se eliminará del principio de $text.

Reglas

En la gramática a partir de la cual se construye el analizador, las reglas se especifican dando un identificador (que debe cumplir /[A-Za-z]\w*/), seguido de dos puntos en la misma línea, seguido de una o más producciones, separadas por barras verticales simples. La disposición de las producciones es totalmente libre:

regla1:  produccion1
 |  produccion2 |
produccion3 | produccion4

En cualquier punto de la gramática, las reglas definidas previamente pueden ser extendidas con producciones adicionales. Esto se logra redeclarando la regla con las nuevas producciones. Por lo tanto:

regla1: a | b | c
regla2: d | e | f
regla1: g | h

es exactamente equivalente a:

regla1: a | b | c | g | h
regla2: d | e | f

Cada producción en una regla consta de cero o más elementos, cada uno de los cuales puede ser: el nombre de otra regla que coincidir (una "subregla"), un patrón o una cadena literal que coincidir directamente (un "token"), un bloque de código Perl que ejecutar (una "acción"), una instrucción especial para el analizador (una "directiva"), o un comentario estándar de Perl (que se ignora).

Una regla coincide con un texto si una de sus producciones coincide. Una producción coincide si cada uno de sus elementos coincide con subcadenas consecutivas del texto. Las producciones de una regla que se está analizando se prueban en el mismo orden en que aparecen en la gramática original, y la primera producción coincidente termina el intento de coincidencia (exitosamente). Si se prueban todas las producciones y ninguna coincide, el intento de coincidencia falla.

Tenga en cuenta que este comportamiento es bastante diferente del comportamiento de "preferir la coincidencia más larga" de yacc. Por ejemplo, si yacc estuviera analizando la regla:

seq : 'A' 'B'
| 'A' 'B' 'C'

al coincidir "AB" miraría hacia adelante para ver si hay una 'C' siguiente y, si es así, coincidiría con la segunda producción en lugar de la primera. En otras palabras, yacc intenta efectivamente todas las producciones de una regla de amplitud primero en paralelo, y selecciona la "mejor" coincidencia, donde "mejor" significa la más larga (tenga en cuenta que esta es una gran simplificación del comportamiento real de yacc, pero servirá para nuestros propósitos).

En contraste, "Parse::RecDescent" intenta cada producción de profundidad primero secuencialmente, y selecciona la "mejor" coincidencia, donde "mejor" significa la primera. Esta es la diferencia fundamental entre el análisis "de abajo hacia arriba" y "descendente recursivo".

Cada elemento emparejado con éxito en una producción recibe un valor, que puede ser accedido en acciones posteriores dentro de la misma producción (o, en algunos casos, como el valor de retorno de una llamada de subregla exitosa). Los elementos fallidos no tienen un valor asociado, ya que el fallo de un elemento provoca que toda la producción circundante falle inmediatamente. Las siguientes secciones describen los diversos tipos de elementos y sus valores de éxito.

Subreglas

Una subregla que aparece en una producción es una instrucción para el analizador de que intente coincidir con la regla nombrada en ese punto del texto que se está analizando. Si la subregla nombrada no está definida cuando se solicita, la producción que la contiene falla inmediatamente (a menos que se haya "autostubbed" - ver Autostubbing).

Una regla puede (recursivamente) llamarse a sí misma como subregla, pero *no* como el elemento más a la izquierda en ninguna de sus producciones (ya que tales recursiones suelen ser no terminantes).

El valor asociado con una subregla es el valor asociado con su variable $return (ver "Acciones" a continuación), o con el último elemento emparejado con éxito en la coincidencia de la subregla.

subregla(s)  # Coincidir una o más veces
subregla(s?) # Coincidir cero o más veces
subregla(N)  # Coincidir exactamente N veces para el entero N > 0
subregla(N..M)   # Coincidir entre N y M veces
subregla(..M)    # Coincidir entre 1 y M veces

# Sintaxis de la gramática de Parse::RecDescent
#
# El analizador trabaja con un conjunto de reglas. Cada regla tiene el formato:
#
#    rulename: expression
#    rulename: expression { action }
#    rulename: expression { action } expression { action }
#    rulename: expression { action } expression { action } ...
#
# donde el "expression" puede ser:
#
#    "literal"           # coincide con el literal exacto
#    /regex/              # coincide con la expresión regular
#    symbol               # coincide con el símbolo (regla) `symbol`
#    ( list )             # grupo de símbolos
#    symbol( n )          # coincide con `symbol` n veces
#    symbol( n, m )       # coincide con `symbol` entre n y m veces
#    symbol +             # coincide con `symbol` una o más veces
#    symbol *             # coincide con `symbol` cero o más veces
#    symbol ?             # coincide con `symbol` cero o una vez
#    symbol | symbol      # coincide con el primer O el segundo símbolo
#    symbol & symbol      # coincide con el primer Y el segundo símbolo
#    symbol - symbol      # coincide con el primer SINO el segundo símbolo
#    -                    # coincide con la nada
#    { action }           # ejecuta la acción Perl
#
# Los símbolos pueden ser terminales (cadenas o expresiones regulares) o no terminales
# (nombres de reglas).
#
# Las acciones son bloques de código Perl encerrados entre llaves {}.
# Pueden aparecer después de cualquier subexpresión en una producción.
#
# Las variables especiales disponibles dentro de las acciones:
#
#  @item
#      El array @item contiene los resultados de los componentes de la producción
#      actual. @item[0] es la producción completa, @item[1] es el primer componente,
#      @item[2] el segundo, y así sucesivamente. Si un componente es una acción,
#      el valor de retorno de esa acción se almacena en @item. Si el componente
#      es una regla no terminal, su valor de retorno se almacena en @item.
#      Si el componente es un literal o una expresión regular, la cadena coincidente
#      se almacena en @item.
#
#  $#item
#      El índice más alto utilizado en @item.
#
#  $item[n]
#      Alias conveniente para @item[n].
#
#  $itempos[n]
#      Referencia a un hash que contiene información de posición para el n-ésimo
#      componente de la producción actual. Véase más abajo para más detalles.
#
#  $from_num y $to_num
#      Valores enteros que indican el número de la línea de inicio y fin (respectivamente)
#      de la producción actual. Por ejemplo, si la producción coincide con el texto
#      en la línea 5, entonces $from_num es 5 y $to_num es 5.
#
#  @arg y %arg
#      El array @arg y el hash %arg almacenan cualquier argumento pasado a la regla
#      desde otra regla (ver "Listas de argumentos de subreglas"). Los cambios en
#      los elementos de cualquiera de las variables no se propagan de vuelta a la
#      regla que llama (los datos se pueden pasar de vuelta desde una subregla a través
#      de la variable $return - ver el siguiente elemento).
#
#  $return
#      Si se asigna un valor a $return dentro de una acción, ese valor se devuelve
#      si la producción que contiene el evento de acción coincide finalmente.
#      Tenga en cuenta que establecer $return *no* causa que la producción actual
#      tenga éxito. Simplemente le dice qué devolver si *tiene* éxito. Por lo tanto,
#      $return es análogo a $$ en una gramática yacc.
#
#      Si $return no se asigna dentro de una producción, el valor del último componente
#      de la producción (es decir: $item[$#item]) se devuelve si la producción tiene
#      éxito.
#
#  $commit
#      El estado actual de compromiso con la producción actual (ver "Directivas"
#      más abajo).
#
#  $skip
#      El prefijo terminal actual (ver "Directivas" más abajo).
#
#  $text
#      El texto restante (no analizado). Los cambios en $text *no* se propagan fuera
#      de las producciones fallidas, pero sí sobreviven a las producciones exitosas.
#      Por lo tanto, es posible alterar dinámicamente el texto que se está analizando,
#      por ejemplo, para proporcionar una facilidad similar a "#include":
#
#      hash_include: '#include' filename
#          { $text = ::loadfile($item[2]) . $text }
#      filename: '<' /[a-z0-9._-]+/i '>'  { $return = $item[2] }
#      | '"' /[a-z0-9._-]+/i '"'  { $return = $item[2] }
#
#  $thisline y $prevline
#      $thisline almacena el número de línea actual dentro del análisis actual
#      (comenzando desde 1). $prevline almacena el número de línea del último carácter
#      que ya se analizó con éxito (esto será diferente de $thisline al final de

#
#      Para mayor eficiencia, $thisline y $prevline son en realidad hashes enlazados,

#      crea que el número de línea actual es el valor que se está asignando. Tenga en cuenta
#      que este ajuste se reflejará en todos los cálculos posteriores de números de línea.
#
#      Modificar el valor de la variable $text (como en el ejemplo anterior de
#      "hash_include", por ejemplo) confundirá el mecanismo de conteo de líneas. Para
#      evitar esto, debe llamar a Parse::RecDescent::LineCounter::resync($thisline)
#      *inmediatamente* después de cualquier asignación a la variable $text (o, al

#
#      También vea la entrada para @itempos.

#

#      y solo recalculan el número de columna requerido cuando se utiliza el valor de la

#
#      La asignación a $thiscolumn o $prevcolumn es un error fatal.

#      También vea la entrada para @itempos.
#
#  $thisoffset y $prevoffset

#      del texto completo que se está analizando (comenzando desde 0). $prevoffset almacena
#      el desplazamiento del último carácter que se analizó con éxito. En todos los casos
#      "$prevoffset == $thisoffset-1".
#
#      Para mayor eficiencia, $thisoffset y $prevoffset son en realidad hashes enlazados,
#      y solo recalculan el desplazamiento requerido cuando se utiliza el valor de la
#      variable.
#
#      La asignación a $thisoffset o $prevoffset es un error fatal.
#
#      Modificar el valor de la variable $text *no* afectará al mecanismo de conteo
#      de desplazamiento.
#
#      También vea la entrada para @itempos.
#
#  @itempos
#      El array @itempos almacena una referencia de hash correspondiente a cada elemento de
#      @item. Los elementos del hash proporcionan lo siguiente:
#
#      $itempos[$n]{offset}{from}  # VALOR DE $thisoffset ANTES DE $item[$n]
#      $itempos[$n]{offset}{to}    # VALOR DE $prevoffset DESPUÉS DE $item[$n]
#      $itempos[$n]{line}{from}    # VALOR DE $thisline ANTES DE $item[$n]
#      $itempos[$n]{line}{to}      # VALOR DE $prevline DESPUÉS DE $item[$n]
#      $itempos[$n]{column}{from}  # VALOR DE $thiscolumn ANTES DE $item[$n]
#      $itempos[$n]{column}{to}    # VALOR DE $prevcolumn DESPUÉS DE $item[$n]
#
#      Tenga en cuenta que los diversos "$itempos[$n]...{from}" registran el valor
#      apropiado *después* de que se haya omitido cualquier prefijo de token.
#
#      Por lo tanto, en lugar del algo tedioso y propenso a errores:

#                a $itempos[3]{column}{to]" }

#      Tenga en cuenta, sin embargo, que (en la implementación actual) el uso de
#      @itempos en cualquier parte de una gramática implica que la información de

Start-up actions


Start-up actions can appear within a grammar extension or
    replacement (that is, a partial grammar installed via
    Parse::RecDescent::Extend() or
    Parse::RecDescent::Replace() - see "Incremental
    Parsing"), and will be executed before the new grammar is installed.
    Note, however, that a particular start-up action is only ever executed
  once.






Autoactions


It is sometimes desirable to be able to specify a default action
    to be taken at the end of every production (for example, in order to easily
    build a parse tree). If the variable
    $::RD_AUTOACTION is defined when
    Parse::RecDescent::new() is called, the contents of
    that variable are treated as a specification of an action which is to
    appended to each production in the corresponding grammar.


Alternatively, you can hard-code the autoaction within a grammar,
    using the "<autoaction:...>"
    directive.


So, for example, to construct a simple parse tree you could
  write:


$::RD_AUTOACTION = q { [@item] };
parser = Parse::RecDescent->new(q{
expression: and_expr '||' expression | and_expr
and_expr:   not_expr '&&' and_expr   | not_expr
not_expr:   '!' brack_expr       | brack_expr
brack_expr: '(' expression ')'       | identifier
identifier: /[a-z]+/i
});


or:


parser = Parse::RecDescent->new(q{
<autoaction: { [@item] } >
expression: and_expr '||' expression | and_expr
and_expr:   not_expr '&&' and_expr   | not_expr
not_expr:   '!' brack_expr       | brack_expr
brack_expr: '(' expression ')'       | identifier
identifier: /[a-z]+/i
});


Either of these is equivalent to:


parser = new Parse::RecDescent (q{
expression: and_expr '||' expression
    { [@item] }
  | and_expr
    { [@item] }
and_expr:   not_expr '&&' and_expr
    { [@item] }
|   not_expr
    { [@item] }
not_expr:   '!' brack_expr
    { [@item] }
|   brack_expr
    { [@item] }
brack_expr: '(' expression ')'
    { [@item] }
  | identifier
    { [@item] }
identifier: /[a-z]+/i
    { [@item] }
});


Alternatively, we could take an object-oriented approach, use
    different classes for each node (and also eliminating redundant intermediate
    nodes):


$::RD_AUTOACTION = q
  { $#item==1 ? $item[1] : "$item[0]_node"->new(@item[1..$#item]) };
parser = Parse::RecDescent->new(q{
    expression: and_expr '||' expression | and_expr
    and_expr:   not_expr '&&' and_expr   | not_expr
    not_expr:   '!' brack_expr           | brack_expr
    brack_expr: '(' expression ')'       | identifier
    identifier: /[a-z]+/i
});


or:


parser = Parse::RecDescent->new(q{
    <autoaction:
      $#item==1 ? $item[1] : "$item[0]_node"->new(@item[1..$#item])
    >
    expression: and_expr '||' expression | and_expr
    and_expr:   not_expr '&&' and_expr   | not_expr
    not_expr:   '!' brack_expr           | brack_expr
    brack_expr: '(' expression ')'       | identifier
    identifier: /[a-z]+/i
});


which are equivalent to:


parser = Parse::RecDescent->new(q{
    expression: and_expr '||' expression
        { "expression_node"->new(@item[1..3]) }
    | and_expr
    and_expr:   not_expr '&&' and_expr
        { "and_expr_node"->new(@item[1..3]) }
    |   not_expr
    not_expr:   '!' brack_expr
        { "not_expr_node"->new(@item[1..2]) }
    |   brack_expr
    brack_expr: '(' expression ')'
        { "brack_expr_node"->new(@item[1..3]) }
    | identifier
    identifier: /[a-z]+/i
        { "identifer_node"->new(@item[1]) }
});


Note that, if a production already ends in an action, no
    autoaction is appended to it. For example, in this version:


$::RD_AUTOACTION = q
  { $#item==1 ? $item[1] : "$item[0]_node"->new(@item[1..$#item]) };
parser = Parse::RecDescent->new(q{
    expression: and_expr '&&' expression | and_expr
    and_expr:   not_expr '&&' and_expr   | not_expr
    not_expr:   '!' brack_expr           | brack_expr
    brack_expr: '(' expression ')'       | identifier
    identifier: /[a-z]+/i
        { 'terminal_node'->new($item[1]) }
});


each "identifier" match produces
    a "terminal_node" object, not an
    "identifier_node" object.


A level 1 warning is issued each time an "autoaction" is
    added to some production.






Autotrees


A commonly needed autoaction is one that builds a parse-tree. It
    is moderately tricky to set up such an action (which must treat terminals
    differently from non-terminals), so Parse::RecDescent simplifies the process
    by providing the "<autotree>"
    directive.


If this directive appears at the start of grammar, it causes
    Parse::RecDescent to insert autoactions at the end of any rule except those
    which already end in an action. The action inserted depends on whether the
    production is an intermediate rule (two or more items), or a terminal of the
    grammar (i.e. a single pattern or string item).


So, for example, the following grammar:


<autotree>
file    : command(s)
command : get | set | vet
get : 'get' ident ';'
set : 'set' ident 'to' value ';'
vet : 'check' ident 'is' value ';'
ident   : /\w+/
value   : /\d+/


is equivalent to:


file    : command(s)        { bless \%item, $item[0] }
command : get       { bless \%item, $item[0] }
| set           { bless \%item, $item[0] }
| vet           { bless \%item, $item[0] }
get : 'get' ident ';'   { bless \%item, $item[0] }
set : 'set' ident 'to' value ';'    { bless \%item, $item[0] }
vet : 'check' ident 'is' value ';'  { bless \%item, $item[0] }
ident   : /\w+/  { bless {__VALUE__=>$item[1]}, $item[0] }
value   : /\d+/  { bless {__VALUE__=>$item[1]}, $item[0] }


Note that each node in the tree is blessed into a class of the
    same name as the rule itself. This makes it easy to build object-oriented
    processors for the parse-trees that the grammar produces. Note too that the
    last two rules produce special objects with the single attribute
    '__VALUE__'. This is because they consist solely of a single terminal.


This autoaction-ed grammar would then produce a parse tree in a
    data structure like this:


{
  file => {
    command => {
     [ get => {
        identifier => { __VALUE__ => 'a' },
          },
       set => {
        identifier => { __VALUE__ => 'b' },
        value      => { __VALUE__ => '7' },
          },
       vet => {
        identifier => { __VALUE__ => 'b' },
        value      => { __VALUE__ => '7' },
          },
      ],
       },
  }
}


(except, of course, that each nested hash would also be blessed
    into the appropriate class).


You can also specify a base class for the
    "<autotree>" directive. The supplied
    prefix will be prepended to the rule names when creating tree nodes. The
    following are equivalent:


<autotree:MyBase::Class>
<autotree:MyBase::Class::>


And will produce a root node blessed into the
    "MyBase::Class::file" package in the
    example above.






Autostubbing


Normally, if a subrule appears in some production, but no rule of
    that name is ever defined in the grammar, the production which refers to the
    non-existent subrule fails immediately. This typically occurs as a result of
    misspellings, and is a sufficiently common occurrence that a warning is
    generated for such situations.


However, when prototyping a grammar it is sometimes useful to be
    able to use subrules before a proper specification of them is really
    possible. For example, a grammar might include a section like:


function_call: identifier '(' arg(s?) ')'
identifier: /[a-z]\w*/i


where the possible format of an argument is sufficiently complex
    that it is not worth specifying in full until the general function call
    syntax has been debugged. In this situation it is convenient to leave the
    real rule "arg" undefined and just slip in
    a placeholder (or "stub"):


arg: 'arg'


so that the function call syntax can be tested with dummy input
    such as:


f0()
f1(arg)
f2(arg arg)
f3(arg arg arg)


et cetera.


Early in prototyping, many such "stubs" may be required,
    so "Parse::RecDescent" provides a means of
    automating their definition. If the variable
    $::RD_AUTOSTUB is defined when a parser is built, a
    subrule reference to any non-existent rule (say,
    "subrule"), will cause a "stub"
    rule to be automatically defined in the generated parser. If
    "$::RD_AUTOSTUB eq '1'" or is false, a
    stub rule of the form:


subrule: 'subrule'


will be generated. The special-case for a value of
    '1' is to allow the use of the perl -s with
    -RD_AUTOSTUB without generating "subrule:
    '1'" per below. If $::RD_AUTOSTUB is
    true, a stub rule of the form:


subrule: $::RD_AUTOSTUB


will be generated. $::RD_AUTOSTUB must
    contain a valid production item, no checking is performed. No lazy
    evaluation of $::RD_AUTOSTUB is performed, it is
    evaluated at the time the Parser is generated.


Hence, with $::RD_AUTOSTUB defined, it is
    possible to only partially specify a grammar, and then "fake"
    matches of the unspecified (sub)rules by just typing in their name, or a
    literal value that was assigned to
  $::RD_AUTOSTUB.






Look-ahead


If a subrule, token, or action is prefixed by "...",
    then it is treated as a "look-ahead" request. That means that the
    current production can (as usual) only succeed if the specified item is
    matched, but that the matching does not consume any of the text being
    parsed. This is very similar to the
    "/(?=...)/" look-ahead construct in Perl
    patterns. Thus, the rule:


inner_word: word ...word


will match whatever the subrule "word" matches, provided
    that match is followed by some more text which subrule "word"
    would also match (although this second substring is not actually consumed by
    "inner_word")

SPECIAL TOKENS


The following are keywords which may be used as terminals in
    rules, or which may be used as parts of rules. They are, for the most part,
    self-explanatory.



  
any

  
Matches any single character.

  
empty

  
Matches the empty string. Succeeds without consuming any text.

  
eof

  
Matches the end of the input text. Fails if called anywhere but the end
      of the input.

  
eoi

  
Matches the end of the input. Succeeds without consuming any text. Is
      synonymous with eof.

  
fail

  
Always fails. Is synonymous with the action undef.

  
literal

  
Matches the literal string given as its argument. For example,
      literal 'foo' matches the string foo.
      The argument may be quoted in any of the standard Perl quote-delimited
      formats.

  
lookup

  
Matches a string from a list of strings. The list is given as the
      argument. For example, lookup qw( if else while )
      matches any of the strings if,
      else, or while.

  
match

  
Matches a Perl regular expression. The expression is given as the
      argument. For example, match qr/[a-z]+/ matches
      one or more lower-case letters. The argument may be quoted in any of the
      standard Perl quote-delimited formats.

  
token

  
Matches a token previously defined using the token
      directive (see below).








PREFIX OPERATORS


The following are operators which may precede any rule, subrule,
    or token.



  
none

  
The opposite of any. Matches any single character,
      except the one given as its argument.

  
not

  
The opposite of literal, lookup,
      or match. If the argument would normally succeed,
      this operator makes it fail. If the argument would normally fail, this
      operator makes it succeed (without consuming any text). Hence, a rule
      such as:

    
identifier: ...!keyword ...!'_' /[A-Za-z_]\w*/

    
matches a string of characters which satisfies the pattern
      "/[A-Za-z_]\w*/", but only if the same
      sequence of characters would not match either subrule "keyword" or
      the literal token '_'.

    
Sequences of look-ahead prefixes accumulate, multiplying their
      positive and/or negative senses. Hence:

    
inner_word: word ...!......!word

    
is exactly equivalent to the original example above (a warning is
      issued in cases like these, since they often indicate something left out, or
      misunderstood).

    
Note that actions can also be treated as look-aheads. In such
      cases, the state of the parser text (in the local variable
      $text) after the look-ahead action is
      guaranteed to be identical to its state before the action, regardless
      of how it's changed within the action (unless you actually undefine
      $text, in which case you get the disaster you
      deserve :-).

Committing and
    uncommitting

  
The "<commit>" and
      "<uncommit>" directives permit the
      recursive descent of the parse tree to be pruned (or "cut") for
      efficiency. Within a rule, a
      "<commit>" directive instructs the
      rule to ignore subsequent productions if the current production fails. For
      example:
    
command: 'find' <commit> filename
   | 'open' <commit> filename
   | 'move' filename filename


    
Clearly, if the leading token 'find' is matched in the first
        production but that production fails for some other reason, then the
        remaining productions cannot possibly match. The presence of the
        "<commit>" causes the
        "command" rule to fail immediately if an invalid
        "find" command is found, and likewise if an invalid
        "open" command is encountered.

    
It is also possible to revoke a previous commitment. For
        example:

    
if_statement: 'if' <commit> condition
    'then' block <uncommit>
    'else' block
    | 'if' <commit> condition
    'then' block


    
In this case, a failure to find an "else" block in
        the first production shouldn't preclude trying the second production,
        but a failure to find a "condition" certainly should.

    
As a special case, any production in which the first
        item is an "<uncommit>"
        immediately revokes a preceding
        "<commit>" (even though the
        production would not otherwise have been tried). For example, in the
        rule:

    
request: 'explain' expression
       | 'explain' <commit> keyword
       | 'save'
       | 'quit'
       | <uncommit> term '?'


    
if the text being matched was "explain?", and the
        first two productions failed, then the
        "<commit>" in production two
        would cause productions three and four to be skipped, but the leading
        "<uncommit>" in the production
        five would allow that production to attempt a match.

    
Note in the preceding example, that the
        "<commit>" was only placed in
        production two. If production one had been:

    
request: 'explain' <commit> expression


    
then production two would be (inappropriately) skipped if a
        leading "explain..." was encountered.

    
Both "<commit>" and
        "<uncommit>" directives always
        succeed, and their value is always 1.

  

  
Rejecting a
    production

  
The "<reject>" directive
      immediately causes the current production to fail (it is exactly
      equivalent to, but more obvious than, the action
      "{undef}"). A
      "<reject>" is useful when it is
      desirable to get the side effects of the actions in one production,
      without prejudicing a match by some other production later in the rule.
      For example, to insert tracing code into the parse:
    
complex_rule: { print "In complex rule...\n"; } <reject>
complex_rule: simple_rule '+' 'i' '*' simple_rule
    | 'i' '*' simple_rule
    | simple_rule


    
It is also possible to specify a conditional rejection, using
        the form
        "<reject:condition>",
        which only rejects if the specified condition is true. This form of
        rejection is exactly equivalent to the action
        "{(condition)?undef:1}>".
        For example:

    
command: save_command
   | restore_command
   | <reject: defined $::tolerant> { exit }
   | <error: Unknown command. Ignored.>


    
A "<reject>" directive
        never succeeds (and hence has no associated value). A conditional
        rejection may succeed (if its condition is not satisfied), in which case
        its value is 1.

    
As an extra optimization,
        "Parse::RecDescent" ignores any
        production which begins with an unconditional
        "<reject>" directive, since any
        such production can never successfully match or have any useful
        side-effects. A level 1 warning is issued in all such cases.

    
Note that productions beginning with conditional
        "<reject:...>" directives are
        never "optimized away" in this manner, even if they are
        always guaranteed to fail (for example:
        "<reject:1>")

    
Due to the way grammars are parsed, there is a minor
        restriction on the condition of a conditional
        "<reject:...>": it cannot
        contain any raw '<' or '>' characters. For example:

    
line: cmd <reject: $thiscolumn > max> data


    
results in an error when a parser is built from this grammar
        (since the grammar parser has no way of knowing whether the first >
        is a "less than" or the end of the
        "<reject:...>".

    
To overcome this problem, put the condition inside a do{}
        block:

    
line: cmd <reject: do{$thiscolumn > max}> data


    
Note that the same problem may occur in other directives that
        take arguments. The same solution will work in all cases.

  

  
Skipping between
    terminals

  
The "<skip>" directive enables the
      terminal prefix used in a production to be changed. For example:
    
OneLiner: Command <skip:'[ \t]*'> Arg(s) /;/


    
causes only blanks and tabs to be skipped before terminals in
        the "Arg" subrule (and any of
        its subrules>, and also before the final
        "/;/" terminal. Once the production is
        complete, the previous terminal prefix is reinstated. Note that this
        implies that distinct productions of a rule must reset their terminal
        prefixes individually.

    
The "<skip>" directive
        evaluates to the previous terminal prefix, so it's easy to
        reinstate a prefix later in a production:

    
Command: <skip:","> CSV(s) <skip:$item[1]> Modifier


    
The value specified after the colon is interpolated into a
        pattern, so all of the following are equivalent (though their efficiency
        increases down the list):

    
<skip: "$colon|$comma">   # ASSUMING THE VARS HOLD THE OBVIOUS VALUES
<skip: ':|,'>
<skip: q{[:,]}>
<skip: qr/[:,]/>


    
There is no way of directly setting the prefix for an entire
        rule, except as follows:

    
Rule: <skip: '[ \t]*'> Prod1
    | <skip: '[ \t]*'> Prod2a Prod2b
    | <skip: '[ \t]*'> Prod3


    
or, better:

    
Rule: <skip: '[ \t]*'>
(
    Prod1
  | Prod2a Prod2b
  | Prod3
)


    
The skip pattern is passed down to subrules, so setting the
        skip for the top-level rule as described above actually sets the prefix
        for the entire grammar (provided that you only call the method
        corresponding to the top-level rule itself). Alternatively, or if you
        have more than one top-level rule in your grammar, you can provide a
        global "<skip>" directive prior
        to defining any rules in the grammar. These are the preferred
        alternatives to setting
        $Parse::RecDescent::skip.

    
Additiona

  





        "<skip>", de hecho, te permite
        tener un comportamiento de salto completamente dinámico. Por ejemplo:

        
Rule_with_dynamic_skip: <skip: $::skip_pattern> Rule


    
Luego puedes establecer $::skip_pattern
        antes de invocar
        "Rule_with_dynamic_skip" y hacer que
        salte lo que hayas especificado.

    
Nota: Hasta la versión 1.51 de Parse::RecDescent, se

Resincronización

  
La directiva "<resync>" proporciona
      un medio visualmente distintivo para consumir parte del texto que se está
      analizando, generalmente para omitir una entrada errónea. En su forma más
      simple, "<resync>" simplemente
      consume texto hasta e incluyendo el siguiente carácter de nueva línea
      ("\n"), teniendo éxito solo si se
      encuentra la nueva línea, en cuyo caso hace que su regla circundante
      devuelva cero en caso de éxito.
    
En otras palabras, un
        "<resync>" es exactamente equivalente
        al token "/[^\n]*\n/" seguido de la
        acción
        "{ $return = 0 }"
        (excepto que las producciones que comienzan con un
        "<resync>" se ignoran al generar
        mensajes de error). Un uso típico podría ser:

        
script : command(s)
command: save_command
   | restore_command
   | <resync> # INTENTA LA SIGUIENTE LÍNEA, SI ES POSIBLE


    
También es posible especificar explícitamente un patrón de
        resincronización, utilizando la variante
        "<resync:patrón>".
        Esta versión tiene éxito solo si el patrón especificado coincide (y
        consume) el texto analizado. En otras palabras,
        "<resync:patrón>"
        es exactamente equivalente al token
        "/patrón/"
        (seguido de una acción
        "{ $return = 0 }").
        Por ejemplo, si los comandos se terminaban con nuevas líneas o puntos y
        comas:

        
command: save_command
   | restore_command
   | <resync:[^;\n]*[;\n]>


    
El valor de una directiva "<resync>"
        (de cualquier tipo) que haya coincidido con éxito es el texto que ha
        consumido. Tenga en cuenta, sin embargo, que dado que la directiva
        también establece $return, una producción que
        consiste en un único "<resync>"
        tiene éxito pero devuelve el valor cero (que una regla de llamada puede
        encontrar útil para distinguir entre coincidencias "verdaderas" y
        coincidencias "tolerantes"). Recuerde que devolver un valor cero indica
        que la regla *tuvo éxito* (ya que solo un "undef"
        denota un fallo dentro de los analizadores de
        "Parse::RecDescent").

  

  
Manejo de errores

  
La directiva "<error>" proporciona la
      generación automática o definida por el usuario de mensajes de error
      durante un análisis. En su forma más simple,
      "<error>" prepara un mensaje de
      error basado en la discrepancia entre el último elemento esperado y el
      texto que causó el fallo. Por ejemplo, dada la regla:
        
McCoy: curse ',' name ', soy un doctor, no un' a_profession '!'
 | pronoun 'muerto,' name '!'
 | <error>


    
las siguientes cadenas producirían los siguientes
        mensajes:

  






  
"Amén, Jim"

  

    
ERROR (línea 1): McCoy inválido: Se esperaba maldición o pronombre
    no encontrado


  

  
"¡Maldición, Jim, soy un doctor, no un extraterrestre de orejas puntiagudas!"

  

    
ERROR (línea 1): McCoy inválido: Se esperaba ", I'm a doctor, not a"
    pero se encontró ", I'm a doctor!" en su lugar


  

  
"Él está muerto,\n"

  

    
ERROR (línea 2): McCoy inválido: No se encontró el nombre esperado


  

  
"Él está vivo"

  

    
ERROR (línea 1): McCoy inválido: Se esperaba 'muerto,' pero se encontró
    "vivo!" en su lugar


  

  
"¡Maldición, Jim, soy un doctor, no un extraterrestre de orejas puntiagudas!"

  

    
ERROR (línea 1): McCoy inválido: Se esperaba una profesión pero se encontró
    "extraterrestre de orejas puntiagudas!" en su lugar


  








Tenga en cuenta que, al generar automáticamente mensajes de error, todos
    los guiones bajos en los nombres de las reglas utilizados en un mensaje se
    reemplazan por espacios simples (por ejemplo, "a_production" se convierte en
    "a production"). Por lo tanto, una elección juiciosa de nombres de reglas
    puede mejorar considerablemente la legibilidad de los mensajes de error
    automáticos (así como la mantenibilidad de la gramática original).


Si el error generado automáticamente no es suficiente, es posible
    proporcionar un mensaje explícito como parte de la directiva de error. Por
    ejemplo:


Spock: "Fascinante ',' (name | 'Captain') '.'
 | "Altamente ilógico, doctor."
 | <error: ¡Nunca dijo eso!>


lo que resultaría en que *todos* los fallos al analizar una
    subregla de "Spock" imprimieran el siguiente mensaje:


ERROR (línea <N>): Spock inválido:  Nunca dijo eso!


El mensaje de error se trata como una cadena "qq{...}" y se
    interpola cuando se genera el error (¡*no* cuando se especifica la
    directiva!). Por lo tanto:


<error: Error místico cerca de "$text">


insertaría correctamente la cadena de texto ambiental que causó
    el error.


Hay otras dos formas de directiva de error:
    "<error?>" y
    "<error?: msg>". Estas se
    comportan igual que
    "<error>" y
    "<error: msg>",
    respectivamente, excepto que solo se activan si la regla está
    "confirmada" en el momento en que se encuentran. Por ejemplo:


Scotty: "Ya sabes que no puedes cambiar las Leyes de la Física," <commit> name
  | name <commit> ',' '¡se va a volar!'
  | <error?>


solo generará un error para una cadena que comience con "Ya sabes
    que no puedes cambiar las Leyes de la Física,", o un nombre válido, pero que
    aún así no coincida con la producción correspondiente. Es decir,
    "$parser->Scotty("¡Sí,
    Capitán")" fallará silenciosamente (ya que ninguna
    producción "confirmará" la regla con esa entrada), mientras que
    "$parser->Scotty("Sr.
    Spock, ¡no puedo hacerlo!")" fallará con el mensaje
    de error:


ERROR (línea 1): Scotty inválido: se esperaba '¡se va a volar!'
    pero se encontró '¡no puedo hacerlo!' en su lugar.


ya que en ese caso la segunda producción confirmaría después de
    coincidir con el nombre inicial.


Tenga en cuenta que para permitir este comportamiento, todas las
    directivas "<error>" que son el primer
    elemento de una producción anulan la confirmación de la regla el tiempo
    suficiente para permitir que se intente su producción (es decir, cuando su
    producción falla, la confirmación se restablece para que se omitan las
    producciones subsiguientes).


Para anular la confirmación de la regla *permanentemente* antes
    de un mensaje de error, es necesario colocar un
    "<uncommit>" explícito antes del
    "<error>". Por ejemplo:


line: 'Kirk:'  <commit> Kirk
| 'Spock:' <commit> Spock
| 'McCoy:' <commit> McCoy
| <uncommit> <error?> <reject>
| <resync>


Los mensajes de error generados por los diversos directivas de tipo
    "<error...>" no se muestran
    inmediatamente. En su lugar, se "enfilan" en un búfer y solo se muestran una
    vez que el análisis finalmente falla. Además, las directivas
    "<error...>" que causan que una
    producción de una regla falle se eliminan automáticamente de la cola de
    mensajes si otra producción hace que la regla completa tenga éxito
    posteriormente. Esto significa que puede colocar directivas
    "<error...>" donde sea útil el
    diagnóstico, y solo se mostrarán aquellas asociadas con fallos reales del
    analizador. Consulte también "GOTCHAS".


Como regla general, los diagnósticos más útiles se generan
    generalmente en el nivel más bajo dentro de la gramática, o en el nivel más
    alto. Una buena regla general es identificar aquellas subreglas que consisten
    principalmente (o en su totalidad) en terminales, y luego colocar una
    directiva "<error...>" al final de
    cualquier otra regla que llame a una o más de esas subreglas.


Hay otra situación en la que se suprime la salida de los diversos
    tipos de directivas de error; a saber, cuando la regla que las contiene se
    está analizando como parte de una "anticipación" (consulte "Anticipación").
    En este caso, la directiva de error aún hará que la regla falle, pero lo hará
    silenciosamente.


Una directiva "<error>"
    incondicional siempre falla (y, por lo tanto, no tiene un valor asociado).
    Esto significa que encontrar tal directiva siempre hace que la producción que
    la contiene falle. Por lo tanto, una directiva
    "<error>" será inevitablemente el
    último elemento (útil) de una regla (se emite una advertencia de nivel 3 si
    una producción contiene elementos después de una directiva
    "<error>" incondicional).


Una directiva "<error?>"
    *tendrá éxito* (es decir: no fallará :-) si la regla actual no está
    confirmada cuando se encuentra la directiva. En ese caso, el valor asociado
    de la directiva es cero. Por lo tanto, este tipo de directiva de error *puede*
    usarse antes del final de una producción. Por ejemplo:


command: 'do' <commit> something
   | 'report' <commit> something
   | <error?: Error de sintaxis> <error: Comando desconocido>


Advertencia:



El directive
    "<error?>" no
    significa "fallar siempre (pero hacerlo silenciosamente a menos que se confirme)". En realidad, significa "fallar (e informar) solo si se confirma, de lo contrario
    tener éxito". Para lograr la semántica de "fallar silenciosamente si no se confirma", es necesario usar:


regla: item <commit> item(s)
| <error?> <reject>  # FALLAR SILENCIOSAMENTE A MENOS QUE SE CONFIRME


Sin embargo, como la gente parece esperar que un directive solitario
    "<error?>" funcione así:


regla: item <commit> item(s)
| <error?: Mensaje de error si se confirma>
| <error:  Mensaje de error si no se confirma>


Parse::RecDescent agrega automáticamente un directive
    "<reject>" si el directive
    "<error?>" es el único elemento en una producción. Se emite una advertencia de nivel 2 (ver más abajo) cuando esto sucede.


El nivel de reporte de errores durante la construcción del parser y el análisis se controla por la presencia o ausencia de cuatro variables globales:
    $::RD_ERRORS, $::RD_WARN,
    $::RD_HINT, y <$::RD_TRACE>. Si
    $::RD_ERRORS está definida (y, por defecto, lo está)
    entonces se reportan errores fatales.


Siempre que $::RD_WARN esté definida, también se reportan ciertos problemas no fatales.


Las advertencias tienen un "nivel" asociado: 1, 2 o 3. Cuanto mayor sea el nivel, más seria será la advertencia. El valor de la variable global correspondiente ($::RD_WARN)
    determina el nivel más bajo de advertencia que se mostrará. Por lo tanto, para ver todas las advertencias, establezca $::RD_WARN a 1. Para ver solo las advertencias más serias, establezca $::RD_WARN a 3.
    Por defecto, $::RD_WARN se inicializa a 3, asegurando que los errores serios pero no fatales se reporten automáticamente.


También hay un directive de gramática para activar advertencias desde dentro de la gramática: "<warn>". Toma un argumento opcional, que especifica el nivel de advertencia:
    "<warn: 2>".


Consulte "DIAGNÓSTICOS" para obtener una lista de los diversos mensajes de error y advertencia que genera Parse::RecDescent cuando estas dos
    variables están definidas.


Definir cualquiera de las variables restantes (que no están definidas por defecto) aumenta aún más la cantidad de información reportada. Definir
    $::RD_HINT hace que el generador de parser ofrezca análisis y sugerencias más detalladas sobre errores y advertencias. Tenga en cuenta que establecer
    $::RD_HINT en cualquier punto establece automáticamente
    $::RD_WARN a 1. También hay un directive
    "<hint>", que se puede codificar directamente en una gramática.


Definir $::RD_TRACE hace que el generador de parser y el parser reporten su progreso a STDERR con detalles agobiantes (aunque, sin sugerencias a menos que $::RD_HINT esté definida por separado). Este detalle se puede moderar de una sola manera: si
    $::RD_TRACE tiene un valor entero (N) mayor que 1, solo los N caracteres del "contexto de análisis actual" (es decir, dónde estamos en la cadena de entrada en cualquier momento del análisis) se reportan en cada momento.


$::RD_TRACE es principalmente útil para depurar una gramática que no se comporta como se espera. Para este fin, si
    $::RD_TRACE está definida cuando se construye un parser, cualquier código de parser real que se genere también se escribe en un archivo llamado
    "RD_TRACE" en el directorio local.


Hay dos directivas asociadas con la variable
    $::RD_TRACE. Si una gramática contiene un directive
    "<trace_build>" en cualquier parte de su especificación, $::RD_TRACE se activa durante la fase de construcción del parser. Si una gramática contiene un directive
    "<trace_parse>" en cualquier parte de su especificación, $::RD_TRACE se activa durante cualquier análisis que realice el parser.


Tenga en cuenta que las cuatro variables pertenecen al paquete "main", lo que las hace más fáciles de referenciar en el código que controla el parser, y también facilita su conversión en flags de línea de comandos
    ("-RD_ERRORS", "-RD_WARN", "-RD_HINT",
    "-RD_TRACE") bajo perl -s.


Los directivas correspondientes son útiles para "hardcodear"
    las diversas características de depuración en una gramática particular (en lugar de tener que establecer y restablecer variables externas).



  
Redireccionando
    diagnósticos

  
Los diagnósticos proporcionados por el mecanismo de trazado siempre van a STDERR. Si
      necesita que vayan a otro lugar, localice y reabra STDERR antes del análisis.
    
Por ejemplo:

        
{
    local *STDERR = IO::File->new(">$filename") or die $!;
    my $result = $parser->startrule($text);
}


  

  
Verificaciones de
    consistencia

  
Cada vez que se construye un parser, Parse::RecDescent realiza una serie de
      verificaciones de consistencia (potencialmente costosas). Estas incluyen: verificar que la gramática no sea recursiva a la izquierda y que ninguna regla haya quedado sin definir.
    
Estas verificaciones son salvaguardas importantes durante el desarrollo, pero representan una sobrecarga innecesaria cuando la gramática es estable y está lista para ser desplegada. Por lo tanto, Parse::RecDescent proporciona un directive para deshabilitarlas:
        "<nocheck>".

    
Si una gramática contiene un directive
        "<nocheck>" en cualquier parte de su especificación, se omiten las verificaciones adicionales en tiempo de compilación.

  

  
Especificando
    variables locales

  
Ocasionalmente es conveniente especificar variables que son locales a una sola
      regla. Esto se puede lograr incluyendo un directive
      "<rulevar:...>" en cualquier parte de la regla. Por ejemplo:
        
markup: <rulevar: $tag>
markup: tag {($tag=$item[1]) =~ s/^<|>$//g} body[$tag]


    
El directive de ejemplo "<rulevar:
        $tag>" hace que se declare una variable "my" llamada
        $tag al inicio de la subrutina que implementa la
        regla "markup" (es decir, antes de la primera producción, independientemente de dónde se especifique dentro de la regla).

    
Específicamente, cualquier directive de la forma:
        "<rulevar:texto>"
        causa que una línea de la forma "my
        texto;"
        se agregue al principio de la subrutina de la regla, inmediatamente después
        de las definiciones de las siguientes variables locales:

        
$thisparser $commit
$thisrule   @item
$thisline   @arg
$text   %arg


    
Esto significa que los siguientes
        directivos "<rulevar>" funcionan como se espera:

        
<rulevar: $count = 0 >
<rulevar: $firstarg = $arg[0] || '' >
<rulevar: $myItems = \@item >
<rulevar: @context = ( $thisline, $text, @arg ) >
<rulevar: ($name,$age) = $arg{"name","age"} >


    
Si se requiere una variable que también sea visible para las subreglas, debe ser
        "local"izada, no
        "my"izada.
        "rulevar" por defecto es
        "my", pero si
        "local" se especifica explícitamente:

        
<rulevar: local $count = 0 >


    
entonces se declara una variable "local"izada, y estará disponible dentro de las subreglas.

    
Sin embargo, tenga en cuenta que, dado que todas estas variables son
        variables "my", sus valores no persisten entre los intentos de coincidencia en una regla dada. Para preservar los valores entre los intentos de coincidencia, los valores se pueden almacenar dentro del miembro "local" del objeto
        $thisrule:

        
countedrule: { $thisrule->{"local"}{"count"}++ }
     <reject>
   | subrule1
   | subrule2
   | <reject: $thisrule->{"local"}{"count"} == 1>
     subrule3


    
Al hacer coincidir una regla, cada directive
        "<rulevar>" se interpreta como si fuera un directive
        "<reject>" incondicional
        (es decir, causa que cualquier producción en la que aparezca falle inmediatamente la coincidencia). Por esta razón (y para mejorar la legibilidad), es habitual especificar cualquier directive
        "<rulevar>"
        en una producción separada al principio de la regla (esto tiene la ventaja adicional de permitir que
        "Parse::RecDescent" optimice y elimine
        dichas producciones, al igual que lo hace para el directive
        "<reject>").

  

  
Reglas con coincidencia
    dinámica

  
Dado que las expresiones regulares y las cadenas entre comillas dobles se interpolan, es
      relativamente fácil especificar producciones con tokens "sensibles al contexto". Por ejemplo:
        
command:  keyword  body  "end $item[1]"


    
lo que asegura que un bloque de comandos esté delimitado por un par
        "<keyword>...end <mismo keyword>".

    
Construir producciones en las que las subreglas sean sensibles al contexto también es posible, a través del directive
        "<matchrule:...>".
        Este directive se comporta de manera idéntica a un elemento de subregla, excepto que la regla que se invoca para hacer coincidirlo está determinada por la cadena especificada después de los dos puntos. Por ejemplo, podríamos reescribir la
        regla "command" de esta manera:

        
command:  keyword  <matchrule:body>  "end $item[1]"


    
Lo que aparezca después de los dos puntos en el directive se trata como una cadena interpolada (es decir, como si apareciera en el operador
        "qq{...}") y el valor de esa cadena interpolada es el nombre de la subregla que se debe hacer coincidir.

    
Por supuesto, simplemente poner una cadena constante como
        "body" en un directive
        "<matchrule:...>" tiene poco interés o beneficio. El poder del directiv

  





e se ve cuando
    usamos una cadena que se interpola a algo interesante. Por
    ejemplo:


comando:    palabra clave <regla_match:$item[1]_cuerpo> "fin $item[1]"
palabra clave:    'mientras' | 'si' | 'funcion'
cuerpo_mientras: condicion bloque
cuerpo_si:    condicion bloque ('si no' bloque)(?)
cuerpo_funcion:  lista_argumentos bloque



Ahora la regla "comando"
    selecciona cómo proceder basándose en la palabra clave que se encuentra. Es
    como si "comando" se declarara:


comando:    'mientras'    cuerpo_mientras    "fin mientras"
   |    'si'       cuerpo_si   "fin si"
   |    'funcion' funcion_cuerpo "fin funcion"



Cuando una
    directiva "<regla_match:...>" se utiliza
    como subregla repetida, la expresión del nombre de la regla se
    "enlaza tardíamente". Es decir, el nombre de la regla a llamar se
    re-evalúa *cada vez* que se intenta una coincidencia. Por lo tanto, la
    siguiente gramática:


{ $::especie = 'perros' }
par:   'dos' <regla_match:$::especie>(s)
perros:   /perros/ { $::especie = 'gatos' }
gatos:   /gatos/



coincidirá completamente con la cadena "dos perros gatos
    gatos", mientras que solo coincidirá con la cadena "dos perros perros
    perros" hasta la octava letra. Si el nombre de la regla estuviera
    "enlanzado temprano" (es decir, evaluado solo la primera vez que se
    encuentra la directiva en una producción), se esperaría el comportamiento
    inverso.


Tenga en cuenta que la directiva
    "regla_match" toma una cadena que se tratará como
    un nombre de regla, *no* como una invocación de regla. Es decir, es como una
    referencia simbólica de Perl, no un "eval". Así como
    puede decir:


$subnombre = 'foo';
# y más tarde...
&{$foo}(@args);



pero no:


$subnombre = 'foo(@args)';
# y más tarde...
&{$foo};



del mismo modo puede decir:


$nombre_regla = 'foo';
# y en la gramática...
<regla_match:$nombre_regla>[@args]



pero no:


$nombre_regla = 'foo[@args]';
# y en la gramática...
<regla_match:$nombre_regla>



Acciones
    Diferidas


La directiva "<diferir:...>" se utiliza para
    especificar una acción a realizar cuando (¡y solo si!) la producción actual
    tiene éxito finalmente.

Siempre que aparece una directiva
    "<diferir:...>", el código que especifica se
    convierte en un cierre (una referencia anónima a una subrutina) que se pone
    en cola dentro del objeto analizador activo. Tenga en cuenta que, dado que el
    código diferido se convierte en un cierre, los valores de cualquier variable
    "local" (como $texto, <@item>, etc.) se
    conservan hasta que el código diferido se ejecuta realmente.


Si el análisis finalmente tiene éxito *y* la producción en la
    que se evaluó la directiva
    "<diferir:...>" formó parte del análisis
    exitoso, entonces el código diferido se ejecuta inmediatamente antes de que el
    análisis retorne. Si, sin embargo, la producción que puso en cola una acción
    diferida falla, o una de las reglas de nivel superior que llamó a esa
    producción falla, entonces la acción diferida se elimina de la cola y, por lo
    tanto, nunca se ejecuta.


Por ejemplo, dada la gramática:


frase: sustantivo trans sustantivo
| sustantivo intrans
sustantivo:     'el perro'
    { print "$item[1]\t(sustantivo)\n" }
|     'la carne'
    { print "$item[1]\t(sustantivo)\n" }
trans:    'comió'
    { print "$item[1]\t(transitivo)\n" }
intrans:  'comió'
    { print "$item[1]\t(intransitivo)\n" }
   |  'ladró'
    { print "$item[1]\t(intransitivo)\n" }



entonces analizar la frase "el perro comió" produciría la salida:


el perro  (sustantivo)
comió  (transitivo)
el perro  (sustantivo)
comió  (intransitivo)



Esto se debe a que, aunque la primera producción de
    "frase" finalmente falla, sus subreglas
    iniciales "sustantivo" y
    "trans" coinciden y, por lo tanto, ejecutan sus
    acciones asociadas. Luego, la segunda producción de
    "frase" tiene éxito, lo que hace que las acciones de
    las subreglas "sustantivo" y
    "intrans" también se ejecuten.


Por otro lado, si las acciones se reemplazaran por directivas
    "<diferir:...>":


frase: sustantivo trans sustantivo
| sustantivo intrans
sustantivo:     'el perro'
    <diferir: print "$item[1]\t(sustantivo)\n" >
|     'la carne'
    <diferir: print "$item[1]\t(sustantivo)\n" >
trans:    'comió'
    <diferir: print "$item[1]\t(transitivo)\n" >
intrans:  'comió'
    <diferir: print "$item[1]\t(intransitivo)\n" >
   |  'ladró'
    <diferir: print "$item[1]\t(intransitivo)\n" >



la salida sería:


el perro  (sustantivo)
comió  (intransitivo)



ya que las acciones diferidas solo se ejecutan si se evaluaron en
    una producción que finalmente contribuye al análisis exitoso.


En este caso, aunque la primera producción de
    "frase" hizo que las subreglas
    "sustantivo" y
    "trans" coincidieran, esa producción falló
    finalmente y, por lo tanto, las acciones diferidas puestas en cola por esas
    subreglas se descartaron posteriormente. Luego, la segunda producción tuvo
    éxito, lo que hizo que todo el análisis tuviera éxito, y por lo tanto las
    acciones diferidas puestas en cola por la (segunda) coincidencia de la
    subregla "sustantivo" y la coincidencia posterior
    de "intrans" *se* conservan y eventualmente se
    ejecutan.


Las acciones diferidas proporcionan un medio para mejorar el
    rendimiento de un analizador, ejecutando solo aquellas acciones que forman
    parte del árbol de análisis final para los datos de entrada.


Alternativamente, las acciones diferidas pueden verse como un
    mecanismo para construir (y ejecutar) una subrutina personalizada que
    corresponde a los datos de entrada dados, de manera muy similar a cómo las
    autoacciones (ver "Autoacciones") pueden usarse para construir una estructura
    de datos personalizada para una entrada específica.


Independientemente de si la acción que especifica se ejecuta o no,
    una directiva "<diferir:...>" siempre tiene
    éxito, devolviendo el número de acciones diferidas actualmente en cola en ese
    momento.


Análisis de Perl


Parse::RecDescent proporciona soporte limitado para analizar subconjuntos de
    Perl, a saber: operadores tipo comilla, variables de Perl y bloques de
    código completos.

La directiva
    "<perl_comillalike>" puede usarse para
    analizar cualquier operador tipo comilla de Perl:
    'una cadena', "m/un patrón/",
    "tr{trans}{formación}", etc. Lo hace llamando a
    Text::Balanced::quotelike().


Si se encuentra un operador tipo comilla, se devuelve una
    referencia a una matriz de ocho elementos. Esos elementos son idénticos a los
    últimos ocho elementos devueltos por Text::Balanced::extract_quotelike()
    en contexto de matriz, a saber:








  
[0]

  
el nombre del operador tipo comilla -- 'q', 'qq', 'm', 's', 'tr' -- si el
      operador tenía nombre; de lo contrario,
      "undef",

  
[1]

  
el delimitador izquierdo del primer bloque de la operación,

  
[2]

  
el texto del primer bloque de la operación (es decir, el contenido de una
      comilla, la expresión regular de una coincidencia, o sustitución o la lista
      de destino de una traducción),

  
[3]

  
el delimitador derecho del primer bloque de la operación,

  
[4]

  
el delimitador izquierdo del segundo bloque de la operación si existe (es
      decir, si es una "s",
      "tr" o
      "y"); de lo contrario,
      "undef",

  
[5]

  
el texto del segundo bloque de la operación si existe (es decir, el
      reemplazo de una sustitución o la lista de traducción de una traducción);
      de lo contrario, "undef",

  
[6]

  
el delimitador derecho del segundo bloque de la operación (si lo hay); de
      lo contrario, "undef",

  
[7]

  
los modificadores finales en la operación (si los hay); de lo contrario,
      "undef".








Si no se encuentra una expresión tipo comilla, la directiva falla
    con el valor habitual "undef".


La directiva
    "<perl_variable>" puede usarse para analizar
    cualquier variable de Perl:
    $escalar, @array,
    %hash,
    $ref->{campo}[$indice], etc. Lo hace llamando a
    Text::Balanced::extract_variable().


Si la directiva coincide con texto que representa una especificación
    válida de variable de Perl, devuelve ese texto. De lo contrario, falla con el
    valor habitual "undef".


La directiva
    "<perl_codeblock>" puede usarse para analizar
    bloques de código Perl delimitados por llaves, como: {
    $a = 1; f() =~ m/pat/; }. Lo hace llamando a
    Text::Balanced::extract_codeblock().


Si la directiva coincide con texto que representa un bloque de código
    Perl válido, devuelve ese texto. De lo contrario, falla con el valor habitual
    "undef".


También puedes indicarle qué tipo de corchetes usar como delimitadores
    externos. Por ejemplo:


lista_argumentos: <perl_codeblock ()>


hace que una lista de argumentos coincida con un bloque de código perl
    cuyos delimitadores externos sean "(...)" (en lugar
    del predeterminado "{...}").





  
Construcción
      de tokens

  
Eventualmente, Parse::RecDescent podrá analizar entrada tokenizada, así como
      cadenas ordinarias. En preparación para este día gozoso, se ha proporcionado
      la directiva "<token:...>". Esta directiva
      crea un token que será adecuado para la entrada de un analizador
      Parse::RecDescent (cuando finalmente admita entrada tokenizada).
    
El texto del token es el valor de la inmediatamente




  elemento anterior en la producción. Una
        "<token:...>" directiva siempre
        tiene éxito con un valor de retorno que es la referencia hash que es el nuevo
        token. También establece el valor de retorno para la producción a esa referencia hash.

    
La
        "<token:...>" directiva facilita la
        creación de un analizador léxico compatible con Parse::RecDescent en
        Parse::RecDescent:

        
my $lexer = new Parse::RecDescent q
{
lex:    token(s)
token:  /a\b/          <token:INDEF>
     |  /the\b/        <token:DEF>
     |  /fly\b/        <token:NOUN,VERB>
     |  /[a-z]+/i { lc $item[1] }  <token:ALPHA>
     |  <error: Unknown token>
};


    
que eventualmente podrá ser utilizado con una gramática
        Parse::RecDescent regular:

        
my $parser = new Parse::RecDescent q
{
startrule: subrule1 subrule 2
# ETC...
};


    
ya sea con una fase de pre-análisis léxico:

        
$parser->startrule( $lexer->lex($data) );


    
o con un enfoque de análisis léxico bajo demanda:

        
$parser->startrule( sub{$lexer->token(\$data)} );


    
Pero actualmente, solo la
        "<token:...>" directiva está
        realmente implementada. El resto es vaporware.

  
  
Especificando
    operaciones

  
Uno de los requisitos más comunes al construir un analizador es especificar
      operadores binarios. Desafortunadamente, en una gramática normal, las reglas
      para tales cosas son incómodas:
        
disjunction:    conjunction ('or' conjunction)(s?)
    { $return = [ $item[1], @{$item[2]} ] }
conjunction:    atom ('and' atom)(s?)
    { $return = [ $item[1], @{$item[2]} ] }


    
o ineficientes:

        
disjunction:    conjunction 'or' disjunction
    { $return = [ $item[1], @{$item[2]} ] }
   |    conjunction
    { $return = [ $item[1] ] }
conjunction:    atom 'and' conjunction
    { $return = [ $item[1], @{$item[2]} ] }
   |    atom
    { $return = [ $item[1] ] }


    
y de cualquier manera es feo y difícil de acertar.

    
Las directivas
        "<leftop:...>" y
        "<rightop:...>" proporcionan una
        forma más fácil de especificar tales operaciones. Usando
        "<leftop:...>" los ejemplos
        anteriores se convierten en:

        
disjunction:    <leftop: conjunction 'or' conjunction>
conjunction:    <leftop: atom 'and' atom>


    
La directiva
        "<leftop:...>" especifica un
        operador binario asociativo por la izquierda. Se especifica alrededor de
        tres elementos de gramática más (típicamente subreglas o terminales),
        que coinciden con el operando izquierdo, el operador en sí y el operando
        derecho respectivamente.

    
Una directiva
        "<leftop:...>" como:

        
disjunction:    <leftop: conjunction 'or' conjunction>


    
se convierte en lo siguiente:

        
disjunction:    ( conjunction ('or' conjunction)(s?)
    { $return = [ $item[1], @{$item[2]} ] } )


    
En otras palabras, una directiva
        "<leftop:...>" coincide con el
        operando izquierdo seguido de cero o más repeticiones tanto del operador
        como del operando derecho. Luego aplana los elementos coincidentes en un
        array anónimo que se convierte en el valor (único) de toda la directiva
        "<leftop:...>".

    
Por ejemplo, una directiva
        "<leftop:...>" como:

        
output:  <leftop: ident '<<' expr >


    
dada una cadena como:

        
cout << var << "str" << 3


    
coincidiría, y $item[1] se establecería
        en:

        
[ 'cout', 'var', '"str"', '3' ]


    
En otras palabras:

        
output:  <leftop: ident '<<' expr >


    
es equivalente a un operador asociativo por la izquierda:

        
output:  ident          { $return = [$item[1]]   }
      |  ident '<<' expr        { $return = [@item[1,3]]     }
      |  ident '<<' expr '<<' expr      { $return = [@item[1,3,5]]   }
      |  ident '<<' expr '<<' expr '<<' expr    { $return = [@item[1,3,5,7]] }
      #  ...etc...


    
De manera similar, la directiva
        "<rightop:...>" toma un operando
        izquierdo, un operador y un operando derecho:

        
assign:  <rightop: var '=' expr >


    
y los convierte en:

        
assign:  ( (var '=' {$return=$item[1]})(s?) expr
    { $return = [ @{$item[1]}, $item[2] ] } )


    
que es equivalente a un operador asociativo por la derecha:

        
assign:  expr       { $return = [$item[1]]       }
      |  var '=' expr       { $return = [@item[1,3]]     }
      |  var '=' var '=' expr   { $return = [@item[1,3,5]]   }
      |  var '=' var '=' var '=' expr   { $return = [@item[1,3,5,7]] }
      #  ...etc...


    
Tenga en cuenta que para ambas directivas
        "<leftop:...>" y
        "<rightop:...>", la directiva
        normalmente no devuelve el operador en sí, solo una lista de los
        operandos involucrados. Esto es particularmente útil para especificar
      listas:

        
list: '(' <leftop: list_item ',' list_item> ')'
    { $return = $item[2] }


    
Sin embargo, hay un problema: a veces el operador es
        significativo en sí mismo. Por ejemplo, en una lista de Perl, una coma
        y un "=>" son ambos separadores
        válidos, pero el "=>" tiene
        semántica de stringificación adicional. Por lo tanto, es importante
        saber cuál se usó en cada caso.

    
Para resolver este problema, las directivas
        "<leftop:...>" y
        "<rightop:...>"
        *sí* devuelven los operadores también, bajo dos circunstancias. El primer
        caso es cuando el operador se especifica como una subregla. En ese
        instante, se devuelve lo que sea que coincida con el operador (asumiendo
        que si el operador es lo suficientemente importante como para tener su
        propia subregla, entonces es lo suficientemente importante como para
        devolverlo).

    
El segundo caso es cuando el operador se especifica como una
        expresión regular. En ese caso, si el primer subpatrón entre paréntesis
        de la expresión regular coincide, se devuelve ese valor coincidente
        (esto es análogo al comportamiento de la función Perl
        "split", excepto que solo se devuelve
        el primer subpatrón).

    
En otras palabras, dada la entrada:

        
( a=>1, b=>2 )


    
las especificaciones:

        
list:      '('  <leftop: list_item separator list_item>  ')'
separator: ',' | '=>'


    
o:

        
list:      '('  <leftop: list_item /(,|=>)/ list_item>  ')'


    
hacen que los separadores de lista se intercalen con los
        operandos en el array anónimo en $item[2]:

        
[ 'a', '=>', '1', ',', 'b', '=>', '2' ]


    
Pero la siguiente versión:

        
list:      '('  <leftop: list_item /,|=>/ list_item>  ')'


    
devuelve solo los operadores:

        
[ 'a', '1', 'b', '2' ]


    
Por supuesto, ninguna de las especificaciones anteriores maneja el
        caso de una lista vacía, ya que las directivas
        "<leftop:...>" y
        "<rightop:...>" requieren al menos
        un operando derecho o izquierdo para coincidir. Para especificar que el
        operador puede coincidir "trivialmente", es necesario agregar un
        calificador "(s?)" a la directiva:

        
list:      '('  <leftop: list_item /(,|=>)/ list_item>(s?)  ')'


    
Tenga en cuenta que en casi todos los ejemplos anteriores, el
        primer y tercer argumento de la directiva
        "<leftop:...>" eran la misma subregla.
        Esto se debe a que los
        "<leftop:...>" se utilizan
        frecuentemente para especificar listas "separadas" del mismo
        tipo de elemento. Para hacer que tales listas sean más fáciles de
        especificar, la siguiente sintaxis:

        
list:   element(s /,/)


    
es exactamente equivalente a:

        
list:   <leftop: element /,/ element>


    
Tenga en cuenta que el separador debe especificarse como un patrón
        crudo (es decir, no como una cadena o subregla).

  

  
Producciones
    con puntuación

  
Por defecto, las reglas de gramática de Parse::RecDescent siempre aceptan la
      primera producción que coincide con la entrada. Pero si dos o más
      producciones pueden coincidir potencialmente con la misma entrada, elegir
      la primera que lo haga puede no ser óptimo.
    
Por ejemplo, si estuviera analizando la oración "time flies
        like an arrow", podría usar una regla como esta:

        
sentence: verb noun preposition article noun { [@item] }
| adjective noun verb article noun   { [@item] }
| noun verb preposition article noun { [@item] }


    
Cada una de estas producciones coincide con la oración, pero la
        tercera es la interpretación más probable. Sin embargo, si la oración
        hubiera sido "fruit flies like a banana", entonces la segunda
        producción es probablemente la coincidencia correcta.

    
Para atender tales situaciones, se puede usar la
        "<score:...>". La directiva es
        equivalente a un "<reject>" incondicional,
        excepto que le permite especificar una "puntuación" para la
        producción actual. Si esa puntuación es numéricamente mayor que la mejor
        puntuación de cualquier producción anterior, la producción actual se
        almacena en caché para su posterior consideración. Si ninguna producción
        posterior coincide, la producción almacenada en caché se trata como si
        hubiera coincidido, y el valor del elemento inmediatamente anterior a su
        directiva
        "<score:...>" se devuelve como
        resultado.

    
En otras palabras, al colocar una directiva
        "<score:...>" al final de cada
        producción, puede seleccionar qué producción coincide utilizando criterios
        distintos del orden de especificación. Por ejemplo:

        
sentence: verb noun preposition article noun { [@item] } <score: sensible(@item)>
| adjective noun verb article noun   { [@item] } <score: sensible(@item)>
| noun verb preposition article noun { [@item] } <score: sensible(@item)>


    
Ahora, cuando cada producción alcanza su respectiva directiva
        "<score:...>", la subrutina
        "sensible" será llamada para evaluar
      late los elementos coincidentes (de alguna manera). Una vez que se hayan
        probado todas las producciones, la que tenga la puntuación más alta
        será la que se acepte como coincidencia para la regla. 

    
La variable $score siempre contiene
        la mejor puntuación actual de cualquier producción, y la variable
        $score_return contiene el valor de retorno
        correspondiente.

    
Como otro ejemplo, la siguiente gramática coincide con líneas
        que pueden estar separadas por comas, dos puntos o punto y coma. Esto
        puede ser complicado si una línea separada por dos puntos también contiene
        comas, o viceversa. La gramática resuelve la ambigüedad seleccionando
        la regla que da como resultado el menor número de campos:

        
line: seplist[sep=>',']  <score: -@{$item[1]}>
| seplist[sep=>':']  <score: -@{$item[1]}>
| seplist[sep=>" "]  <score: -@{$item[1]}>
seplist: <skip:""> <leftop: /[^$arg{sep}]*/ "$arg{sep}" /[^$arg{sep}]*/>


    
Note el uso de la negación dentro de la directiva
        "<score:...>" para garantizar
        que la lista separada con la mayor cantidad de elementos obtenga la
        puntuación más baja.

    
Como indican los ejemplos anteriores, a menudo ocurre que todas
        las producciones de una regla utilizan exactamente la misma directiva
        "<score:...>". Es tedioso tener
        que repetir esta directiva idéntica en cada producción, por lo que
        Parse::RecDescent también proporciona la directiva
        "<autoscore:...>".

    
Si aparece una directiva
        "<autoscore:...>" en cualquier
        producción de una regla, el código que especifica se utiliza como
        código de puntuación para todas las producciones de esa regla, excepto
        las producciones que ya terminan con una directiva explícita
        "<score:...>". Por lo tanto, las
        reglas anteriores podrían reescribirse:

        
line: <autoscore: -@{$item[1]}>
line: seplist[sep=>',']
| seplist[sep=>':']
| seplist[sep=>" "]
sentence: <autoscore: sensible(@item)>
| verb noun preposition article noun { [@item] }
| adjective noun verb article noun   { [@item] }
| noun verb preposition article noun { [@item] }


    
Tenga en cuenta que la directiva
        "<autoscore:...>" en sí misma
        actúa como un "<reject>"
        incondicional y (al igual que la directiva
        "<rulevar:...>") se poda en
        tiempo de compilación siempre que sea posible.

  

  
Prescindir de las
    comprobaciones de gramática

  
Durante la fase de compilación de la construcción del analizador, Parse::RecDescent
      realiza un pequeño número de comprobaciones en la gramática que se le
      proporciona. Específicamente, comprueba que la gramática no sea
      izquierdamente recursiva, que no haya construcciones "insaciables" de la
      forma:
        
rule: subrule(s) subrule


    
y que no falten reglas (es decir, que se haga referencia a
        ellas pero nunca se definan).

    
Estas comprobaciones son importantes durante el desarrollo, pero
        pueden ralentizar la construcción del analizador en código estable. Por
        lo tanto, Parse::RecDescent proporciona la directiva <nocheck>
        para desactivarlas. La directiva solo puede aparecer antes de la primera
        definición de regla y desactiva la comprobación en el resto de la
        gramática actual.

    
Normalmente, esta directiva se añadiría cuando un analizador
        ha sido probado a fondo y está listo para su lanzamiento.

  







Listas de argumentos de subreglas


Ocasionalmente, es útil pasar datos a una subregla que se está
    invocando. Por ejemplo, considere el siguiente fragmento de gramática:


classdecl: keyword decl
keyword:   'struct' | 'class';
decl:      # WHATEVER


La regla "decl" podría desear
    saber cuál de las dos palabras clave se utilizó (ya que puede afectar algún
    aspecto de cómo se interpreta la declaración posterior).
    "Parse::RecDescent" permite al diseñador
    de la gramática pasar datos a una regla, colocando esos datos en una
    *lista de argumentos* (es decir, entre corchetes) inmediatamente después de
    cada elemento de subregla en una producción. Por lo tanto, podríamos pasar
    la palabra clave a "decl" de la
    siguiente manera:


classdecl: keyword decl[ $item[1] ]
keyword:   'struct' | 'class';
decl:      # WHATEVER


La lista de argumentos puede constar de cualquier número (¡incluido
    cero!) de expresiones Perl separadas por comas. En otras palabras, se parece
    exactamente a una referencia a una matriz anónima de Perl. Por ejemplo,
    podríamos pasar la palabra clave, el nombre de la regla circundante y la
    cadena literal 'keyword' a "decl" así:


classdecl: keyword decl[$item[1],$item[0],'keyword']
keyword:   'struct' | 'class';
decl:      # WHATEVER


Dentro de la regla a la que se pasan los datos
    ("decl" en los ejemplos anteriores) esos
    datos están disponibles como elementos de una variable local
    @arg. Por lo tanto, "decl"
    podría informar sus intenciones de la siguiente manera:


classdecl: keyword decl[$item[1],$item[0],'keyword']
keyword:   'struct' | 'class';
decl:      { print "Declarando $arg[0] (un $arg[2])\n";
     print "(esta regla llamada por $arg[1])" }


Las listas de argumentos de subreglas también pueden interpretarse
    como hashes, simplemente usando la variable local %arg
    en lugar de @arg. Por lo tanto, podríamos reescribir
    el ejemplo anterior:


classdecl: keyword decl[keyword => $item[1],
    caller  => $item[0],
    type    => 'keyword']
keyword:   'struct' | 'class';
decl:      { print "Declarando $arg{keyword} (un $arg{type})\n";
     print "(esta regla llamada por $arg{caller})" }


Tanto @arg como %arg
    siempre están disponibles, por lo que el diseñador de la gramática puede
    elegir la convención (o combinación de convenciones) que mejor se adapte.


Las listas de argumentos de subreglas también son útiles para
    crear "plantillas de reglas" (especialmente cuando se usan junto con la
    directiva "<matchrule:...>"). Por
    ejemplo, la subregla:


list:     <matchrule:$arg{rule}> /$arg{sep}/ list[%arg]
    { $return = [ $item[1], @{$item[3]} ] }
|     <matchrule:$arg{rule}>
    { $return = [ $item[1]] }


es una plantilla útil para el problema común de hacer coincidir
    una lista separada. Por ejemplo:


function: 'func' name '(' list[rule=>'param',sep=>';'] ')'
param:    list[rule=>'name',sep=>','] ':' typename
name:     /\w+/
typename: name


Cuando una lista de argumentos de subreglas se utiliza con una
    subregla repetida, la lista de argumentos va *antes* del especificador de
    repetición:


list:   /some|many/ thing[ $item[1] ](s)


La lista de argumentos está "vinculada tardíamente". Es decir, se
    revalúa por cada repetición de la subregla repetida. Esto significa que cada
    intento de repetición para hacer coincidir la subregla puede recibir un
    conjunto de argumentos completamente diferente si el valor de la expresión
    en la lista de argumentos cambia entre intentos. Así, por ejemplo, la
    gramática:


{ $::species = 'dogs' }
pair:   'two' animal[$::species](s)
animal: /$arg[0]/ { $::species = 'cats' }


coincidirá completamente con la cadena "two dogs cats cats",
    mientras que solo coincidirá con la cadena "two dogs dogs dogs" hasta la
    octava letra. Si el valor de la lista de argumentos estuviera "vinculado
    tempranamente" (es decir, evaluado solo la primera vez que se intenta una
    coincidencia de subregla repetida), se esperaría que los comportamientos de
    coincidencia se invirtieran.


Por supuesto, es posible "vincular tempranamente" de forma efectiva
    dichas listas de argumentos pasándoles un valor que no cambie en cada
    repetición. Por ejemplo:


{ $::species = 'dogs' }
pair:   'two' { $::species } animal[$item[2]](s)
animal: /$arg[0]/ { $::species = 'cats' }


Los argumentos también se pueden pasar a la regla de inicio,
    simplemente añadiéndolos a la lista de argumentos con la que se llama a la
    regla de inicio ( *después* del parámetro "número de línea"). Por ejemplo,
  dado:


$parser = new Parse::RecDescent ( $grammar );
$parser->data($text, 1, "str", 2, \@arr);
#         ^^^^^  ^  ^^^^^^^^^^^^^^^
#       |    |     |
# TEXTO A ANALIZAR    |     |
# NÚMERO DE LÍNEA DE INICIO     |
# ELEMENTOS DE @arg QUE SE PASAN A LA REGLA data


entonces, dentro de las producciones de la regla
    "data", la matriz
    @arg contendrá
    "("str", 2, \@arr)".






Alternaciones


Las alternaciones son reglas implícitas (sin nombre) definidas como
    parte de una producción. Una alternación se define como una serie de
    producciones separadas por '|' dentro de un par de corchetes. Por ejemplo:


character: 'the' ( good | bad | ugly ) /dude/


Cada alternación define implícitamente una nueva subregla, cuyo
    nombre generado automáticamente indica su origen:
    "_alternation_<I>_of_production_<P>_of_rule<R>"
    para los valores apropiados de <I>, <P> y <R>. Se inserta
    una llamada a esta subregla implícita en lugar de los corchetes. Por lo tanto,
    el ejemplo anterior es simplemente una forma abreviada conveniente de:


character: 'the'
   _alternation_1_of_production_1_of_rule_character
   /dude/
_alternation_1_of_production_1_of_rule_character:
   good | bad | ugly


Dado que las alternaciones se analizan llamando recursivamente al
    generador de analizadores, cualquier tipo de elemento puede aparecer en una
    alternación. Por ejemplo:


character: 'the' ( 'high' "plains"  # Silencioso, con poncho
     | /no[- ]name/ # Silencioso, sin poncho
     | vengeance_seeking    # Poncho opcional
     | <error>
     ) drifter


En este caso, si ocurriera un error, el mensaje generado
    automáticamente sería:


ERROR (line <N>): Subregla implícita inválida: Se esperaba
      'high' o /no[- ]name/ o genérico,
      pero se encontró "pacifista" en su lugar


Dado que cada alternación tiene de hecho un nombre, incluso es
    posible extenderlas o reemplazarlas:


parser->Replace(
"_alternation_1_of_production_1_of_rule_character:
    'generic Eastwood'"
    );


Más importante aún, dado que las alternaciones son una forma de
    subregla, se les pueden dar especificadores de repetición:


character: 'the' ( good | bad | ugly )(?) /dude/






Análisis incremental


"Parse::RecDescent" proporciona
    dos métodos - "Extend" y
    "Replace" - que se pueden utilizar para
    alterar la gramática que coincide con un analizador. Ambos métodos toman el
    mismo argumento que "Parse::RecDescent::new", a saber de gramática
    cadena


"Parse::RecDescent::Extend"
    interpreta la especificación de la gramática y añade las producciones que encuentra al final de las reglas para las que se especifican. Por ejemplo:


$add = "nombre: 'Jimmy-Bob' | 'Bobby-Jim'\ndescripción: color /cuellos?/";
parser->Extend($add);


añade dos producciones a la regla "nombre" (creándola si es necesario) y una producción a la regla "descripción".


"Parse::RecDescent::Replace" es
    idéntico, excepto que primero restablece cada regla especificada en la gramática adicional, eliminando cualquier producción existente. Por lo tanto, después de:


$add = "nombre: 'Jimmy-Bob' | 'Bobby-Jim'\ndescripción: color /cuellos?/";
parser->Replace($add);


solo existen los "nombre" válidos y la única descripción posible.


Un uso más interesante de los métodos
    "Extend" y
    "Replace" es llamarlos dentro de la acción de un analizador en ejecución. Por ejemplo:


typedef: 'typedef' nombre_tipo identificador ';'
       { $thisparser->Extend("nombre_tipo: '$item[3]'") }
   | <error>
identificador: ...!nombre_tipo /[A-Za-z_]w*/


lo que evita automáticamente que los nombres de tipo se definan como typedef, o:


comando: 'map' nombre_clave 'a' clave_abortar
       { $thisparser->Replace("clave_abortar: '$item[2]'") }
   | 'map' nombre_clave 'a' nombre_clave
       { map_key($item[2],$item[4]) }
   | clave_abortar
       { exit if confirm("¿abortar?") }
clave_abortar: 'q'
nombre_clave: ...!clave_abortar /[A-Za-z]/


que permite al usuario cambiar el enlace de la clave de abortar, pero no desvincularlo.


El uso cuidadoso de tales construcciones hace posible reconfigurar un analizador en ejecución, eliminando la necesidad de retroalimentación semántica al proporcionar retroalimentación sintáctica en su lugar. Sin embargo, como está implementado actualmente,
    Replace() y Extend() tienen que regenerar y volver a "evaluar" todo el analizador cada vez que se llaman. Esto los hace bastante lentos para gramáticas grandes.


En tales casos, el uso juicioso de una expresión regular interpolada probablemente será mucho más eficiente:


typedef: 'typedef' nombre_tipo/ identificador ';'
       { $thisparser->{local}{nombre_tipo} .= "|$item[3]" }
   | <error>
identificador: ...!nombre_tipo /[A-Za-z_]w*/
nombre_tipo: /$thisparser->{local}{nombre_tipo}/






Precompilando   analizadores


Normalmente Parse::RecDescent construye un analizador a partir de una gramática en tiempo de ejecución. Ese enfoque simplifica el diseño e implementación del código de análisis, pero tiene la desventaja de que ralentiza el proceso de análisis: tienes que esperar a que Parse::RecDescent construya el analizador cada vez que se ejecuta el programa. Las gramáticas largas o complejas pueden ser particularmente lentas de construir, lo que provoca retrasos inaceptables al inicio.


Para superar esto, el módulo proporciona una forma de
    "precompilar" un objeto analizador y guardarlo en un módulo separado. Ese módulo puede ser utilizado luego para crear clones del analizador original.


Una gramática puede precompilarse utilizando el método de clase
    "Precompile". Por ejemplo, para precompilar una gramática almacenada en el escalar $grammar, y producir una clase llamada PreGrammar en un archivo de módulo llamado PreGrammar.pm, podría usar:


use Parse::RecDescent;
Parse::RecDescent->Precompile([$options_hashref], $grammar, "PreGrammar", ["RuntimeClass"]);


El primer argumento requerido es la cadena de la gramática, el segundo es el nombre de la clase a construir. El nombre del archivo del módulo se genera automáticamente añadiendo ".pm" al último elemento del nombre de la clase. Por lo tanto:


Parse::RecDescent->Precompile($grammar, "My::New::Parser");


produciría un archivo de módulo llamado Parser.pm.


Después del nombre de la clase, puede especificar el nombre de la
    clase de tiempo de ejecución (runtime_class) llamada por el analizador precompilado. Consulte "Tiempos de ejecución precompilados" para obtener más detalles.


Se puede proporcionar una referencia de hash opcional como primer argumento a "Precompile". Este argumento es actualmente EXPERIMENTAL y puede cambiar en una futura versión de Parse::RecDescent. La única opción admitida actualmente es
    "-standalone", consulte "Analizadores precompilados independientes".


Es algo tedioso tener que escribir un pequeño programa Perl solo para generar una clase de gramática precompilada, por lo que Parse::RecDescent tiene una magia especial que le permite hacer el trabajo directamente desde la línea de comandos.


Si su gramática se especifica en un archivo llamado grammar, puede generar una clase llamada Yet::Another::Grammar de la siguiente manera:


> perl -MParse::RecDescent - grammar Yet::Another::Grammar [Runtime::Class]


Esto produciría un archivo llamado Grammar.pm que contiene la definición completa de una clase llamada Yet::Another::Grammar. Por supuesto, para usar esa clase, necesitaría poner el archivo Grammar.pm en un directorio llamado Yet/Another, en algún lugar de su ruta de inclusión de Perl.


Habiendo creado la nueva clase, es muy fácil usarla para construir un analizador. Simplemente "use" el nuevo módulo, y luego llame a su método "new" para crear un objeto analizador. Por ejemplo:


use Yet::Another::Grammar;
my $parser = Yet::Another::Grammar->new();


El efecto de estas dos líneas es exactamente el mismo que:


use Parse::RecDescent;
open GRAMMAR_FILE, "grammar" or die;
local $/;
my $grammar = <GRAMMAR_FILE>;
my $parser = Parse::RecDescent->new($grammar);


solo que considerablemente más rápido.


Sin embargo, tenga en cuenta que los analizadores producidos por cualquiera de los enfoques son exactamente los mismos, por lo que, si bien la precompilación tiene un efecto en la velocidad de configuración, no tiene ningún efecto en la velocidad de análisis. RecDescent 2.0 abordará ese problema.


Analizadores precompilados independientes


Hasta la versión 1.967003 de Parse::RecDescent, los módulos analizadores construidos con "Precompile" dependían de Parse::RecDescent. Las futuras versiones de Parse::RecDescent con implementaciones internas diferentes romperían los analizadores precompilados preexistentes.


La versión 1.967_005 añadió la capacidad para que Parse::RecDescent se incluya en el archivo .pm resultante si pasa la opción booleana
    "-standalone" a
    "Precompile":


Parse::RecDescent->Precompile({ -standalone => 1, },
    $grammar, "My::New::Parser");


Parse::RecDescent se incluye como
    $class::_Runtime para evitar conflictos entre una versión instalada de Parse::RecDescent y otros analizadores precompilados creados con Parse::RecDescent. El nombre de esta clase se puede cambiar con la opción
    "-runtime_class" a Precompile. Este cambio de nombre es experimental y está sujeto a cambios en futuras versiones.


Los analizadores precompilados siguen dependiendo de Parse::RecDescent por defecto, ya que esta característica todavía se considera experimental. En el futuro, los analizadores independientes se convertirán en la opción predeterminada.


Tiempos de ejecución precompilados


Los analizadores precompilados independientes incluyen cada uno una copia de Parse::RecDescent. Para los usuarios que tienen una familia de analizadores precompilados relacionados, esto es muy ineficiente.
    "Precompile" ahora admite una opción experimental
    "-runtime_class". Para construir un analizador precompilado con un nombre de tiempo de ejecución diferente, llame:


Parse::RecDescent->Precompile({
        -standalone => 1,
        -runtime_class => "My::Runtime",
    },
    $grammar, "My::New::Parser");


El analizador independiente resultante contendrá una copia de
    Parse::RecDescent, renombrada a "My::Runtime".


Para construir un conjunto de analizadores que
    "use" un tiempo de ejecución con nombre personalizado, sin incluir ese tiempo de ejecución en la salida, simplemente construya esos analizadores con
    "-runtime_class" y sin
    "-standalone":


Parse::RecDescent->Precompile({
        -runtime_class => "My::Runtime",
    },
    $grammar, "My::New::Parser");


El propio tiempo de ejecución debe generarse también, para que pueda ser
    "use"d por My::New::Parser. Para generar el archivo de tiempo de ejecución, utilice una de las dos siguientes llamadas:


Parse::RecDescent->PrecompiledRuntime("My::Runtime");
Parse::RecDescent->Precompile({
        -standalone => 1,
        -runtime_class => "My::Runtime",
    },
    '', # gramática vacía
    "My::Runtime");







TRAMPAS


Esta sección describe errores comunes que los escritores de gramáticas parecen cometer habitualmente.




1.   Esperar que un error invalide siempre un análisis


Un error común al usar mensajes de error es escribir la gramática de esta manera:


archivo: línea(s)
línea: tipo_línea_1
| tipo_línea_2
| tipo_línea_3
| <error>


La expectativa parece ser que cualquier línea que no sea de tipo 1, 2 o 3 invocará la directiva
    "<error>" y, por lo tanto, provocará que el análisis falle.


Desafortunadamente, eso solo sucede si el error ocurre en la primera línea. La primera regla establece que un
    "archivo" se corresponde con una o más líneas, por lo que si incluso una sola línea tiene éxito, la primera regla se satisface por completo y el análisis en su conjunto tiene éxito. Eso significa que cualquier mensaje de error generado por fallos posteriores en la regla
    "línea" se ignora silenciosamente.


Normalmente, lo que realmente se necesita es esto:


archivo: línea(s) fin_archivo    { $return = $item[1] }
línea: tipo_línea_1
| tipo_línea_2
| tipo_línea_3
| <error>
fin_archivo: /^\Z/


La adición de la subregla "fin_archivo" a la primera producción significa que un archivo solo coincide con una serie de coincidencias de "línea" exitosas que consumen el texto de entrada completo. Si queda algún texto de entrada después de que se hayan hecho coincidir las líneas, debe haber habido un error en la última
    "línea". En ese caso, la regla
    "fin_archivo" fallará, provocando que toda la regla
    "archivo" también falle.


Tenga en cuenta también que "fin_archivo" debe coincidir con
    "/^\Z/" (fin de texto), no
    &quo
t;/^\cZ/" o
    "/^\cD/" (fin de archivo).


Y no olvides la acción al final de la producción. Si solo escribes:


file: line(s) eofile


entonces el valor devuelto por la regla
    "file" será el valor de su último
    elemento: "eofile". Dado que
    "eofile" siempre devuelve una cadena vacía
    en caso de éxito, eso hará que la regla "file"
    devuelva esa cadena vacía. Aparte de devolver el valor incorrecto, devolver
    una cadena vacía provocará fallos en código como:


$parser->file($filetext) || die;


(ya que "" es falso).


Recuerda que Parse::RecDescent devuelve undef en caso de fallo,
    por lo que la única comprobación segura de fallo es:


defined($parser->file($filetext)) || die;






2.   Usando un "return" en una acción


Una acción es como un bloque "do"
    dentro de la subrutina que implementa la regla circundante. Por lo tanto, si
    pones una instrucción "return" en una
    acción:


range: '(' start '..' end )'
    { return $item{end} }
   /\s+/ 


esa subrutina devolverá inmediatamente, sin comprobar el resto de
    los elementos de la producción actual (por ejemplo, el
    "/\s+/") y sin configurar las estructuras
    de datos necesarias para indicar al analizador que la regla ha tenido
    éxito.


La forma correcta de establecer un valor de retorno en una acción
    es establecer la variable $return:


range: '(' start '..' end )'
            { $return = $item{end} }
       /\s+/ 






2.   Estableciendo $Parse::RecDescent::skip en tiempo de análisis


Si deseas cambiar el comportamiento de omisión predeterminado (ver
    "Separadores de Terminales" y la directiva
    "<skip:...>") estableciendo
    $Parse::RecDescent::skip, debes recordar establecer
    esta variable *antes* de crear el objeto de gramática.


Por ejemplo, es posible que desees omitir todos los comentarios
    similares a Perl con esta expresión regular:


my $skip_spaces_and_comments = qr/
      (?mxs:
         \s+         # o bien espacios
         | \# .*?$   # o un guión y lo que sea hasta el final de línea
      )*             # repetido a voluntad (en cualquier orden)
   /;


Y luego:


my $parser1 = Parse::RecDescent->new($grammar);
$Parse::RecDescent::skip = $skip_spaces_and_comments;
my $parser2 = Parse::RecDescent->new($grammar);
$parser1->parse($text); # esto no maneja comentarios
$parser2->parse($text); # esto omite comentarios correctamente


Los dos analizadores se comportan de manera diferente, porque cualquier
    comportamiento de omisión especificado a través de
    $Parse::RecDescent::skip se codifica de forma rígida
    cuando se construye el objeto de gramática, no en tiempo de análisis.

"Parse::RecDescent" actualmente

  • Código Perl inválido en bloques de código (error fatal).
    •

    •

    • 
  
  • Componentes faltantes o extraños en una directiva

      "<rightop>".
    • 
  
  • Componentes irreconocibles en la especificación de la gramática (error
      fatal).
    • 
  
  • Componentes de regla "huérfanos" especificados antes de la primera

      "<error>" (advertencia de nivel
      3).
    •

      podrías proporcionarlas más tarde a través de
      Parse::RecDescent::Extend()).
    • 
  
  • Instancias donde el comportamiento de repetición codicioso probablemente

  • Múltiples especificadores de lookahead consecutivos (solo una advertencia

  • Producciones que comienzan con una directiva
      "<reject>" o
      "<rulevar:...>". Dichas
      producciones se optimizan (una advertencia de nivel 1).
    •

ASUNTOS EN CURSO Y DIRECCIONES FUTURAS



  
1.

  
Las repeticiones son "incorregiblemente codiciosas" en el sentido de
      que consumirán todo lo que puedan y no retrocederán si ese comportamiento
      causa que una producción falle innecesariamente. Por lo tanto, por ejemplo:
        
rule: subrule(s) subrule


    
*nunca* tendrá éxito, porque la repetición consumirá todas las
        subreglas que encuentre, sin dejar ninguna para que coincida con el
        segundo elemento. Tales construcciones son relativamente raras (y
        "Parse::RecDescent::new" genera una
        advertencia siempre que ocurren) por lo que esto puede no ser un problema,
        especialmente ya que el comportamiento insaciable se puede superar
        "manualmente" escribiendo:

        
rule: penultimate_subrule(s) subrule
penultimate_subrule: subrule ...subrule


    
El problema es que esta construcción es exactamente el doble de
        cara que la original, mientras que la retroceso solo añadiría 1/N
        al costo (para que coincida con N repeticiones de
        "subrule"). Agradecería comentarios sobre
        la necesidad de retroceso; particularmente sobre casos donde la falta de
        ello hace que el rendimiento del análisis sea problemático.

  

  
2.

  
Habiendo abierto esa lata de gusanos, también es necesario considerar si
      hay una necesidad de especificadores de repetición no codiciosos. De nuevo,
      es posible (con cierto costo) proporcionar la funcionalidad requerida
      manualmente:
        
rule: nongreedy_subrule(s) othersubrule
nongreedy_subrule: subrule ...!othersubrule


    
En general, el problema es si el beneficio de esta funcionalidad
        adicional supera los inconvenientes de complicar aún más la sintaxis de
        especificación de gramática (actualmente minimalista) y (peor) introducir
        más sobrecarga en los analizadores generados.

  

  
3.

  
Una directiva "<autocommit>" sería
      agradable. Es decir, sería útil poder decir:
        
command: <autocommit>
command: 'find' name
   | 'find' address
   | 'do' command 'at' time 'if' condition
   | 'do' command 'at' time
   | 'do' command
   | unusual_command


    
y que el generador dedujera que esto debería ser
        "podado" así:

        
command: 'find' name
   | 'find' <commit> address
   | 'do' <commit> command <uncommit>
    'at' time
    'if' <commit> condition
   | 'do' <commit> command <uncommit>
    'at' <commit> time
   | 'do' <commit> command
   | unusual_command


    
Hay varias cuestiones aquí. Primero, ¿debería el
        "<autocommit>" instalar
        automáticamente un "<uncommit>" al
        inicio de la última producción (en el entendido de que la regla
        "command" no sabe si un "unusual_command" podría
        comenzar con "find" o "do") o debería analizarse el
        subgrafo "unusual_command" (para ver si *podría* ser viable
        después de un "find" o "do")?

    
La segunda cuestión es cómo tratar las expresiones regulares.
        El enfoque más simple sería simplemente hacer un commit antes de ellas (en
        el entendido de que *podrían* coincidir). Se obtendría una mejor
        eficiencia analizando todos los tokens literales anteriores para
        determinar si el patrón coincidiría con ellos.

    
En general, las cuestiones son: ¿puede tal
        "poda" automatizada acercarse a una mano
