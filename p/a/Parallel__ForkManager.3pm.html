Parallel::ForkManager(3) Documentación contribuida por el usuario de Perl Parallel::ForkManager(3)

NOMBRE

Parallel::ForkManager - Un gestor simple de bifurcaciones para procesamiento paralelo

VERSIÓN

versión 2.04

SINOPSIS

use Parallel::ForkManager;
my $pm = Parallel::ForkManager->new($MAX_PROCESSES);
BUCLE_DATOS:
foreach my $data (@all_data) {
  # Bifurca y devuelve el pid del hijo:
  my $pid = $pm->start and next BUCLE_DATOS;
  ... haz algún trabajo con $data en el proceso hijo ...
  $pm->finish; # Termina el proceso hijo
}

DESCRIPCIÓN

Este módulo está destinado para su uso en operaciones que se pueden realizar en paralelo, donde el número de procesos a bifurcar debe ser limitado. El uso típico es un descargador que recuperará cientos/miles de archivos.

El código para un descargador se vería algo así:

use LWP::Simple;
use Parallel::ForkManager;
...
my @links=(
  ["http://www.foo.bar/rulez.data","rulez_data.txt"],
  ["http://new.host/more_data.doc","more_data.doc"],
  ...
);
...
# Max 30 procesos para descarga paralela
my $pm = Parallel::ForkManager->new(30);
ENLACES:
foreach my $linkarray (@links) {
  $pm->start and next ENLACES; # haz la bifurcación
  my ($link, $fn) = @$linkarray;
  warn "No se puede obtener $fn de $link"
    if getstore($link, $fn) != RC_OK;
  $pm->finish; # haz la salida en el proceso hijo
}
$pm->wait_all_children;

Primero, necesitas instanciar el Gestor de Bifurcaciones con el constructor "new". Debes especificar el número máximo de procesos a crear. Si especificas 0, entonces NO se hará ninguna bifurcación; esto es bueno para fines de depuración.

Luego, usa $pm->start para hacer la bifurcación. $pm devuelve 0 para el proceso hijo y el pid del hijo para el proceso padre (ver también "fork" en perlfunc). El "and next" omite el bucle interno en el proceso padre. NOTA: $pm->start muere si la bifurcación falla.

$pm->finish termina el proceso hijo (asumiendo que se hizo una bifurcación en "start").

NOTA: No puedes usar $pm->start si ya estás en el proceso hijo. Si quieres gestionar otro conjunto de subprocesos en el proceso hijo, ¡debes instanciar otro objeto Parallel::ForkManager!

MÉTODOS

La letra del comentario indica dónde debe ejecutarse el método. P para padre, C para hijo.

new $procesos
Instancia un nuevo objeto Parallel::ForkManager. Debes especificar el número máximo de hijos a bifurcar. Si especificas 0 (cero), entonces no se bifurcarán hijos. Esto está destinado a fines de depuración.

El segundo parámetro opcional, $tempdir, solo se usa si quieres que los hijos envíen de vuelta una referencia a algunos datos (ver RECUPERACIÓN DE ESTRUCTURAS DE DATOS abajo). Si no se proporciona, se establece mediante una llamada a File::Temp::tempdir().

El método new morirá si el directorio temporal no existe o no es un directorio.

Desde la versión 2.00, el constructor también puede ser llamado en el estilo típico Moo/Moose. Es decir,

my $fm = Parallel::ForkManager->new(
    max_proc => 4,
    tempdir => '...',
    child_role => 'Parallel::ForkManager::CustomChild',
);
child_role
Devuelve el nombre del rol consumido por el objeto ForkManager en los procesos hijos. Por defecto es Parallel::ForkManager::Child y puede ser establecido a algo más a través del constructor.
start [ $identificador_proceso ]
Este método realiza la bifurcación. Devuelve el pid del proceso hijo para el padre y 0 para el proceso hijo. Si el parámetro $procesos para el constructor es 0, entonces, asumiendo que estás en el proceso hijo, $pm->start simplemente devuelve 0.

Se puede proporcionar un $identificador_proceso opcional a este método... Se utiliza por la función de devolución de llamada "run_on_finish" (ver DEVOLUCIONES DE LLAMADA) para identificar el proceso terminado.

start_child [ $identificador_proceso, ] \&callback
Similar a "start", pero ejecutará el &callback como hijo. Si la devolución de llamada devuelve algo, se pasará como los datos a transmitir de vuelta al proceso padre a través de finish().
finish [ $codigo_salida [, $referencia_estructura_datos] ]
Cierra el proceso hijo saliendo y acepta un código de salida opcional (el código de salida por defecto es 0) que se puede recuperar en el padre a través de la devolución de llamada. Si se proporciona el segundo parámetro opcional, el hijo intenta enviar su contenido de vuelta al padre. Si usas el programa en modo depuración ($procesos == 0), este método simplemente llama a la devolución de llamada.

Si se proporciona la $referencia_estructura_datos, se serializa y se pasa al proceso padre. Ver RECUPERACIÓN DE ESTRUCTURAS DE DATOS para más información.

set_max_procs $procesos
Permite establecer un nuevo número máximo de hijos a mantener.
wait_all_children
Puedes llamar a este método para esperar a todos los procesos que se hayan bifurcado. Esta es una espera bloqueante.
reap_finished_children
Esta es una llamada no bloqueante para recoger hijos y ejecutar devoluciones de llamada independientemente de las llamadas a "start" o "wait_all_children". Úsalo en escenarios donde "start" se llama infrecuentemente pero te gustaría que las devoluciones de llamada se ejecutaran rápidamente.
is_parent
Devuelve "true" si estás dentro del padre o "false" si estás dentro del hijo.
is_child
Devuelve "true" si estás dentro del hijo o "false" si estás dentro del padre.
max_procs
Devuelve el número máximo de procesos que el objeto bifurcará.
running_procs
Devuelve los pids de los procesos bifurcados actualmente monitoreados por "Parallel::ForkManager". Ten en cuenta que los hijos todavía se informan como en ejecución hasta que el gestor de bifurcaciones los recoja, a través de la próxima llamada a "start" o "wait_all_children". 
my @pids = $pm->running_procs;
my $nbr_children = $pm->running_procs;
running_procs_with_identifiers
Devuelve una lista de pares. Las claves son los pids de los procesos bifurcados (como los devuelve "running_procs" y los valores son los identificadores dados a esos pids por "start". Si no se proporcionó ningún identificador para un proceso, el valor para ese pid no estará definido.
wait_for_available_procs( $n )
Espera hasta que $n ranuras de proceso disponibles estén disponibles. Si no se proporciona $n, el valor predeterminado es 1.
waitpid_blocking_sleep
Devuelve el período de espera, en segundos, de las llamadas pseudo-bloqueantes. El período de espera puede ser una fracción de segundo.

Devuelve 0 si está deshabilitado.

Por defecto es 1 segundo.

Ver LLAMADAS BLOQUEANTES para más detalles.

set_waitpid_blocking_sleep $segundos
Establece el período de espera, en segundos, de las llamadas pseudo-bloqueantes. Establecer a 0 para deshabilitar.

Ver LLAMADAS BLOQUEANTES para más detalles.

CALLBACKS

CALLBACKS

Puedes definir callbacks en el código, que se llaman cuando ocurran eventos como iniciar un proceso o al finalizar. Declara estos antes de la primera llamada a start().

Los callbacks pueden definirse con los siguientes métodos:

run_on_finish $code [, $pid ]
Puedes definir una subrutina que se llama cuando un proceso hijo se termina. Se llama en el proceso padre.

Los parámetros de $code son los siguientes:

- el identificador del proceso, que se termina
- código de salida del programa
- identificación del proceso (si se proporciona en el método "start")
- señal de salida (0-127: nombre de la señal)
- core dump (1 si hubo core dump al finalizar)
- referencia a la estructura de datos o indefinida (ver RETRIEVING DATASTRUCTURES)
run_on_start $code
Puedes definir una subrutina que se llama cuando se inicia un proceso hijo. Se llama después de la inicialización exitosa en el proceso padre.

Los parámetros de $code son los siguientes:

- el identificador del proceso que se ha iniciado
- identificación del proceso (si se proporciona en el método "start")
run_on_wait $code, [$period]
Puedes definir una subrutina que se llama cuando el proceso hijo necesita esperar a la inicialización. Si $period no está definido, se llama una vez por proceso hijo. Si $period está definido, $code se llama periódicamente, y el módulo espera $period segundos entre las llamadas. Nota, $period puede ser un número decimal también. El tiempo exacto de $period segundos no está garantizado, las señales pueden reducirse y el scheduler puede hacerlo más largo (en sistemas ocupados).

Los $code llamados en el método "start" y el método "wait_all_children" también.

No se pasan parámetros a $code en la llamada.

BLOCKING CALLS

Cuando se espera a que los procesos hijos se terminen, "Parallel::ForkManager" está entre un fork y un lugar duro (si te excusas el terrible pánico). La función de Perl bajo la cual el módulo se basa, "waitpid", puede bloquear hasta que se termine un proceso específico o cualquier otro proceso hijo, pero no para un grupo de procesos dado.

Esto significa que, cuando espera a que un hijo de su grupo termine, el módulo puede hacer una de dos cosas:

Solo espera a sus propios procesos hijos
Se realiza mediante un ciclo usando una llamada no bloqueante de "waitpid" y un statement de sleep. El código hace algo así: 
while(1) {
        if ( cualquiera de los P::FM proceso hijo terminó ) {
            return su PID
        }
        sleep $sleep_period
    }

Este es el comportamiento por defecto que el módulo usará. No es el más eficiente para esperar a los procesos hijos, pero es el más seguro para garantizar que "Parallel::ForkManager" no interfiera con cualquier parte del código.

El período de sleep se establece mediante el método "set_waitpid_blocking_sleep".

Bloquea hasta que cualquier proceso termine
Alternativamente, "Parallel::ForkManager" puede llamar a "waitpid" de manera que bloquee hasta que un proceso hijo termine. Si el proceso hijo no fue uno de los procesos hijos supervisados, el espera se reanudará. Este es más eficiente, pero significa que "P::FM" puede capturar (y descartar) la notificación de terminación que otro parte del código podría estar esperando.

Si este es un conflicto de tiempo que no aplica a tu código, puedes establecer el período de waitpid_blocking_sleep a 0, lo que habilitará llamadas de "waitpid" bloqueantes.

my $pm = Parallel::ForkManager->new( 4 );
$pm->set_waitpid_blocking_sleep(0);  # true blocking calls enabled
for ( 1..100 ) {
    $pm->start and next;
    ...; # hacer trabajo
    $pm->finish;
}

RETRIEVING DATASTRUCTURES from child processes

La capacidad de recuperar estructuras de datos del padre es nueva desde la versión 0.7.6.

Cada proceso hijo puede opcionalmente enviar una estructura de datos al padre. Por estructura de datos, se refiere a una referencia a una cadena, un hash o un array. Los contenidos de la estructura se escriben a archivos temporales en el disco usando el módulo Storable's store() método. La referencia es luego recuperada dentro del código que envía el callback a la función run_on_finish.

La estructura de datos puede ser cualquier estructura de datos perl que hace sentido: cadena, valor numérico o una referencia a un array, hash o objeto.

Hay dos pasos involucrados en la recuperación de estructuras de datos:

1) Una referencia a la estructura de datos que el hijo quiere enviar al padre se proporciona como el segundo argumento de la llamada finish(). Es el cargo del hijo decidir si o no enviar algo al padre.

2) La referencia a la estructura de datos se recupera usando la callback proporcionada en el método run_on_finish().

Recuerda que la recuperación de estructuras de datos no es lo mismo que devolver una estructura de datos desde una llamada a un método. No es lo que realmente ocurre. La estructura de datos referida en un proceso hijo se serializa y se escribe en un archivo por Storable. El archivo se lee de nuevo en memoria y se crea una nueva estructura de datos perteneciente al proceso padre. Por favor considera el costo de performance que implica, así que intenta mantener la estructura devuelta pequeña.

EXAMPLES

Parallel get

Este ejemplo pequeño puede usarse para obtener URLs en paralelo.

use Parallel::ForkManager;
use LWP::Simple;
my $pm = Parallel::ForkManager->new(10);
LINKS:
for my $link (@ARGV) {
  $pm->start and next LINKS;
  my ($fn) = $link =~ /^.*\/(.*?)$/;
  if (!$fn) {
    warn "Cannot determine filename from $fn\n";
  } else {
    $0 .= " " . $fn;
    print "Getting $fn from $link\n";
    my $rc = getstore($link, $fn);
    print "$link downloaded. response code: $rc\n";
  };
  $pm->finish;
};

Callbacks

Ejemplo de un programa que utiliza callbacks para obtener el código de salida de los hijos:

use strict;
use Parallel::ForkManager;
my $max_procs = 5;
my @names = qw( Fred Jim Lily Steve Jessica Bob Dave Christine Rico Sara );
# hash para resolver el PID a información específica del hijo
my $pm = Parallel::ForkManager->new($max_procs);
# Setup un callback para cuando un hijo termina
$pm->run_on_finish( sub {
    my ($pid, $exit_code, $ident) = @_;
    print "** $ident just got out of the pool " .
      "with PID $pid and exit code: $exit_code\n";
});
$pm->run_on_start( sub {
    my ($pid, $ident)=@_;
    print "** $ident started, pid: $pid\n";
});
$pm->run_on_wait( sub {
    print "** Have to wait for one children ...\n"
  },
  0.5
);
NAMES:
foreach my $child ( 0 .. $#names ) {
  my $pid = $pm->start($names[$child]) and next NAMES;
  # Este código es el proceso hijo
  print "This is $names[$child], Child number $child\n";
  sleep ( 2 * $child );
  print "$names[$child], Child $child is about to get out...\n";
  sleep 1;
  $pm->finish($child); # pasar un código de salida a finish
}
print "Waiting for Children...\n";
$pm->wait_all_children;
print "Everybody is out of the pool!\n";

Data structure retrieval

En este ejemplo simple, cada hijo envía una referencia a una cadena.

use Parallel::ForkManager 0.7.6;
use strict;
my $pm = Parallel::ForkManager->new(2, '/server/path/to/temp/dir/');
# recuperación de estructuras de datos y manejo
$pm -> run_on_finish ( # llamada antes de la primera llamada a start()
  sub {
    my ($pid, $exit_code, $ident, $exit_signal, $core_dump, $data_structure_reference) = @_;
    # recuperar la estructura de datos del hijo
    if (defined($data_structure_reference)) {  # hijos no están forzados a enviar nada
      my $string = ${$data_structure_reference};  # hijo envía una referencia a una cadena
      print "$string\n";
    }
    else {  # errores durante la almacenación o recuperación generarán un aviso
      print qq|No message received from child process $pid!\n|;
    }
  }
);
# preparar componentes aleatorios
my @foods = ('chocolate', 'ice cream', 'peanut butter', 'pickles', 'pizza', 'bacon', 'pancakes', 'spaghetti', 'cookies');
my @preferences = ('loves', q|can't stand|, 'always wants more', 'will walk 100 miles for', 'only eats', 'would starve rather than eat');
# ejecutar procesos paralelos
PERSONS:
foreach my $person (qw(Fred Wilma Ernie Bert Lucy Ethel Curly Moe Larry)) {
  $pm->start() and next PERSONS;
  # generar un enunciado aleatorio sobre preferencias de comida
  my $statement = $person . ' ' . $preferences[int(rand @preferences)] . ' ' . $foods[int(rand @foods)];
  # enviarlo al proceso padre
  $pm->finish(0, \$statement);  # notar que es un referencia a un escalar, no el escalar mismo
}
$pm->wait_all_children;

Un ejemplo de recuperación de estructuras de datos muestra cómo los hijos deciden si enviar algo, qué enviar y cómo procesar lo que se recupera.

use Parallel::ForkManager 0.7.6;

$pm->finish(0, \@array) if ($return_choice eq 'array'); $pm->finish(0, \%hash) if ($return_choice eq 'hash'); # como un hijo responsable, informa al padre que su instrucción no fue válida } else { $pm->finish(0, \qq|Instrucciones inválidas: "$instruction->{'send'}".)|; USANDO RAND() EN PROCESOS BIFURCADOS

Una advertencia que vale la pena notar es que todos los procesos bifurcados usarán la misma semilla aleatoria, por lo que potencialmente proporcionarán los mismos resultados (ver http://blogs.perl.org/users/brian_phillips/2010/06/when-rand-isnt-random.html). Si estás usando rand() y quieres que cada hijo bifurcado use una semilla diferente, puedes agregar lo siguiente a tu programa:

$pm->run_on_start(sub { srand });

EXTENSIÓN

A partir de la versión 2.0.0, "Parallel::ForkManager" usa Moo internamente. Cuando se bifurca un proceso del objeto padre, la instancia bifurcada del objeto se modificará para consumir el rol Parallel::ForkManager::Child. Todo esto hace que extender Parallel::ForkManager para implementar cualquier mecanismo de almacenamiento/recuperación o cualquier otro comportamiento sea bastante fácil.

Ejemplo: almacenar y recuperar datos a través de un servicio web

{
    package Parallel::ForkManager::Web;
    use HTTP::Tiny;
    use Moo;
    extends 'Parallel::ForkManager';
    has ua => (
        is => 'ro',
        lazy => 1,
        default => sub {
            HTTP::Tiny->new;
        }
    );
    sub store {
        my( $self, $data ) = @_;
        $self->ua->post( "http://.../store/$$", { body => $data } );
    }
    sub retrieve {
        my( $self, $kid_id ) = @_;
        $self->ua->get( "http://.../store/$kid_id" )->{content};
    }
}
my $fm = Parallel::ForkManager::Web->new(2);
$fm->run_on_finish(sub{
    my $retrieved = $_[5];
    print "obtenido ", $retrieved, "\n";
});
$fm->start_child(sub {
    return $_**2;
}) for 1..3;
$fm->wait_all_children;

Ejemplo: hacer que los procesos hijos salgan diferentemente

use Parallel::ForkManager;
package Parallel::ForkManager::Child::PosixExit {
    use Moo::Role;
    with 'Parallel::ForkManager::Child';
    sub finish  { POSIX::_exit() };
}
my $fm = Parallel::ForkManager->new(
    max_proc   => 1,
    child_role => 'Parallel::ForkManager::Child::PosixExit'
);

SEGURIDAD

Parallel::ForkManager utiliza archivos temporales cuando un proceso hijo devuelve información a su proceso padre. Los nombres de archivo se basan en los procesos del padre y del hijo, por lo que son bastante fáciles de adivinar. Por lo tanto, si la seguridad es una preocupación en su entorno, asegúrese de que el directorio utilizado por Parallel::ForkManager esté restringido solo al usuario actual (el comportamiento predeterminado es crear un directorio, a través de "tempdir" de File::Temp, lo que hace eso).

SOLUCIÓN DE PROBLEMAS

PerlIO::gzip y Parallel::ForkManager no juegan bien juntos

Si está utilizando PerlIO::gzip en sus procesos hijos, puede terminar con archivos corruptos. Esto no es realmente culpa de P::FM, sino un problema entre PerlIO::gzip y fork() (ver https://rt.cpan.org/Public/Bug/Display.html?id=114557).

Afortunadamente, parece que hay una manera fácil de solucionar el problema agregando la capa "unix"? Es decir,

open(IN, '<:unix:gzip', ...

ERRORES Y LIMITACIONES

No use Parallel::ForkManager en un entorno donde otros procesos hijos puedan afectar la ejecución del programa principal; no se recomienda usar este módulo en un entorno donde ya se usa fork() / wait().

Si desea utilizar más de una copia de Parallel::ForkManager, debe asegurarse de que todos los procesos hijos se hayan terminado, antes de utilizar el segundo objeto en el programa principal.

Eres libre de usar una nueva copia de Parallel::ForkManager en los procesos hijos, aunque no creo que tenga sentido.
