Params::Validate(3pm) Documentación de Perl aportada por el usuario Params::Validate(3pm)

NOMBRE

Params::Validate - Valida parámetros de métodos/funciones

VERSIÓN

versión 1.31

SINOPSIS

use Params::Validate qw(:all);
# acepta parámetros con nombre (hash o hashref)
sub foo {
    validate(
        @_, {
            foo => 1,    # obligatorio
            bar => 0,    # opcional
        }
    );
}
# acepta parámetros posicionales
sub bar {
    # los dos primeros son obligatorios, el tercero es opcional
    validate_pos( @_, 1, 1, 0 );
}
sub foo2 {
    validate(
        @_, {
            foo =>
                # especifica un tipo
                { type => ARRAYREF },
            bar =>
                # especifica una interfaz
                { can => [ 'print', 'flush', 'frobnicate' ] },
            baz => {
                type      => SCALAR,     # un escalar...
                                         # ...que es un entero simple...
                regex     => qr/^\d+$/,
                callbacks => {           # ...y menor que 90
                    'menor que 90' => sub { shift() < 90 },
                },
            }
        }
    );
}
sub callback_with_custom_error {
    validate(
        @_,
        {
            foo => {
                callbacks => {
                    'es un entero' => sub {
                        return 1 if $_[0] =~ /^-?[1-9][0-9]*$/;
                        die "$_[0] no es un valor entero válido";
                    },
                },
            }
        }
    );
}
sub with_defaults {
    my %p = validate(
        @_, {
            # obligatorio
            foo => 1,
            # $p{bar} será 99 si no se proporciona bar. bar ahora
            # es opcional.
            bar => { default => 99 }
        }
    );
}
sub pos_with_defaults {
    my @p = validate_pos( @_, 1, { default => 99 } );
}
sub sets_options_on_call {
    my %p = validate_with(
        params => \@_,
        spec   => { foo => { type => SCALAR, default => 2 } },
        normalize_keys => sub { $_[0] =~ s/^-//; lc $_[0] },
    );
}

DESCRIPCIÓN

Recomiendo considerar el uso de Params::ValidationCompiler en su lugar. Ese módulo, a pesar de ser Perl puro, es significativamente más rápido que este, al costo de tener que adoptar un sistema de tipos como Specio, Type::Tiny, o el que viene con Moose.

Este módulo permite validar los parámetros de llamadas a métodos o funciones a un nivel arbitrario de especificidad. En su nivel más simple, es capaz de validar que se proporcionaron los parámetros requeridos y que no se pasaron parámetros adicionales no especificados.

También es capaz de determinar que un parámetro es de un tipo específico, que es un objeto de una cierta jerarquía de clases, que posee ciertos métodos, o de aplicar callbacks de validación a los argumentos.

EXPORTACIÓN

El módulo siempre exporta las funciones validate() y validate_pos().

También tiene una función adicional disponible para exportar, "validate_with", que puede ser usada para validar cualquier tipo de parámetros, y establecer varias opciones en base a cada invocación.

Además, puede exportar las siguientes constantes, que se usan como parte de la verificación de tipos. Estas son "SCALAR", "ARRAYREF", "HASHREF", "CODEREF", "GLOB", "GLOBREF" y "SCALARREF", "UNDEF", "OBJECT", "BOOLEAN" y "HANDLE". Estas se explican en la sección sobre Validación de Tipos.

Las constantes están disponibles a través de la etiqueta de exportación ":types". También hay una etiqueta ":all" que incluye todas las constantes, así como la función validation_options().

VALIDACIÓN DE PARÁMETROS

Los mecanismos de validación proporcionados por este módulo pueden manejar tanto parámetros nombrados como posicionales. En su mayor parte, las mismas características están disponibles para cada uno. La mayor diferencia es la forma en que la especificación de validación se entrega a la subrutina relevante. La otra diferencia está en los mensajes de error producidos cuando fallan las comprobaciones de validación.

Al manejar parámetros nombrados, el módulo aceptará un hash o una referencia a hash.

Las subrutinas que esperan parámetros nombrados deben llamar a la subrutina validate() de esta manera:

validate(
    @_, {
        parametro1 => especificacion de validacion,
        parametro2 => especificacion de validacion,
        ...
    }
);

Las subrutinas que esperan parámetros posicionales deben llamar a la subrutina validate_pos() de esta manera:

validate_pos( @_, { especificacion de validacion }, { especificacion de validacion } );

Parámetros Obligatorios/Opcionales

Si solo desea especificar que algunos parámetros son obligatorios y otros opcionales, esto se puede hacer de forma muy sencilla.

Para una subrutina que espera parámetros nombrados, haría esto:

validate( @_, { foo => 1, bar => 1, baz => 0 } );

Esto indica que los parámetros "foo" y "bar" son obligatorios y que el parámetro "baz" es opcional. La presencia de cualquier otro parámetro causará un error.

Para una subrutina que espera parámetros posicionales, haría esto:

validate_pos( @_, 1, 1, 0, 0 );

Esto indica que se esperan al menos 2 y no más de 4 parámetros. Si tiene una subrutina que tiene un número mínimo de parámetros pero puede aceptar cualquier número máximo, puede hacer esto:

validate_pos( @_, 1, 1, (0) x (@_ - 2) );

Esto siempre será válido siempre que se proporcionen al menos dos parámetros. Se podría usar una construcción similar para los parámetros de validación más complejos descritos más adelante.

Tenga en cuenta que esto:

validate_pos( @_, 1, 1, 0, 1, 1 );

no tiene ningún sentido, así que no lo haga. Cualquier cero debe venir al final de la especificación de validación.

Además, si especifica que un parámetro puede tener un valor predeterminado, entonces se considera opcional.

Validación de Tipos

Este módulo soporta los siguientes tipos simples, que pueden ser exportados como constantes:

  • SCALAR

    Un escalar que no es una referencia, como 10 o 'hola'. Un parámetro que es indefinido no se trata como un escalar. Si desea permitir valores indefinidos, tendrá que especificar "SCALAR | UNDEF".

  • ARRAYREF

    Una referencia de array como "[1, 2, 3]" o "\@foo".

  • HASHREF

    Una referencia de hash como "{ a => 1, b => 2 }" o "\%bar".

  • CODEREF

    Una referencia a subrutina como "\&foo_sub" o "sub { print "hola" }".

  • GLOB

    Este es un poco complicado. Un glob sería algo como *FOO, pero no "\*FOO", que es una referencia a glob. Cabe señalar que este truco:

    my $fh = do { local *FH; };

    hace que $fh sea un glob, no una referencia a glob. Por otro lado, el valor de retorno de "Symbol::gensym" es una referencia a glob. Cualquiera de los dos puede ser usado como manejador de archivo o directorio.

  • GLOBREF

    Una referencia a glob como "\*FOO". Ver la entrada GLOB arriba para más detalles.

  • SCALARREF

    Una referencia a un escalar como "\$x".

  • UNDEF

    Un valor indefinido

  • OBJECT

    Una referencia bendecida.

  • BOOLEAN

    Esta es una opción especial, y es solo un atajo para "UNDEF | SCALAR".

  • HANDLE

    Esta opción también es especial, y es solo un atajo para "GLOB | GLOBREF". Sin embargo, parece probable que la mayoría de las personas interesadas en globs o referencias a globs estén realmente interesadas en si el parámetro en cuestión podría ser un manejo de archivo o directorio válido.

Para especificar que un parámetro debe ser de un tipo dado al usar parámetros con nombre, haga esto:

validate(
    @_, {
        foo => { type => SCALAR },
        bar => { type => HASHREF }
    }
);

Si un parámetro puede ser de más de un tipo, simplemente use el operador OR bit a bit ("|") para combinarlos.

validate( @_, { foo => { type => GLOB | GLOBREF } );

Para parámetros posicionales, esto se puede especificar de la siguiente manera:

validate_pos( @_, { type => SCALAR | ARRAYREF }, { type => CODEREF } );

Validación de interfaz

Para especificar que se espera que un parámetro tenga un cierto conjunto de métodos, podemos hacer lo siguiente:

   validate(
       @_, {
           foo =>
               # solo tiene que ser capaz de ->bar
               { can => 'bar' }
       }
   );
... o ...
   validate(
       @_, {
           foo =>
               # debe ser capaz de ->bar y ->print
               { can => [qw( bar print )] }
       }
   );

Validación de clase

Una advertencia. Al construir sus interfaces externas, probablemente sea mejor especificar qué métodos espera que tenga un objeto en lugar de de qué clase debe ser (o una hija de). Esto hará que su API sea mucho más flexible.

Dicho esto, si desea validar que un parámetro entrante pertenece a una clase (o clase hija) o clases, haga:

   validate(
       @_,
       { foo => { isa => 'My::Frobnicator' } }
   );
... o ...
   validate(
       @_,
       # debe ser ambos, no uno u otro!
       { foo => { isa => [qw( My::Frobnicator IO::Handle )] } }
   );

Validación con expresiones regulares

Si desea especificar que un parámetro dado debe coincidir con una expresión regular específica, esto se puede hacer con la clave de especificación "regex". Por ejemplo:

validate(
    @_,
    { foo => { regex => qr/^\d+$/ } }
);

El valor de la clave "regex" puede ser una cadena o una expresión regular precompilada creada a través de "qr".

Si el valor que se verifica contra una expresión regular no está definido, la expresión regular se verifica explícitamente contra la cadena vacía (''), para evitar advertencias de "Uso de valor no inicializado".

El módulo "Regexp::Common" en CPAN es una excelente fuente de expresiones regulares adecuadas para validar entradas.

Validación con callbacks

Si ninguno de los anteriores es suficiente, es posible pasar uno o más callbacks para validar el parámetro. Al callback se le dará el valor del parámetro como su primer argumento. Su segundo argumento serán todos los parámetros, como una referencia a un hash o a un array. Los callbacks se especifican como una referencia a hash. La clave es un id para el callback (usado en mensajes de error) y el valor es una referencia a una subrutina, como:

validate(
    @_,
    {
        foo => {
            callbacks => {
                'smaller than a breadbox' => sub { shift() < $breadbox },
                'green or blue'           => sub {
                    return 1 if $_[0] eq 'green' || $_[0] eq 'blue';
                    die "$_[0] is not green or blue!";
                }
            }
        }
    }
);
validate(
    @_, {
        foo => {
            callbacks => {
                'bigger than baz' => sub { $_[0] > $_[1]->{baz} }
            }
        }
    }
);

El callback debe devolver un valor verdadero si el valor es válido. Si no, puede devolver falso o morir. Si devuelve falso, "Params::Validate" lanzará un mensaje de error genérico.

Si su callback muere en su lugar, puede proporcionar un mensaje de error personalizado. Si el callback muere con una cadena simple, esta cadena se agregará a un mensaje de excepción generado por "Params::Validate". Si el callback muere con una referencia (bendecida o no), entonces esta será relanzada tal cual por "Params::Validate".

Desinfección de entrada

Si desea valores desinfectados, establezca la clave "untaint" en un hashref de especificación a un valor verdadero, así:

my %p = validate(
    @_, {
        foo => { type => SCALAR, untaint => 1 },
        bar => { type => ARRAYREF }
    }
);

Esto desinfectará el parámetro "foo" si los parámetros son válidos.

Tenga en cuenta que la desinfección solo se realiza si *todos los parámetros* son válidos. Además, solo se desinfectan los valores de retorno, no los valores originales pasados a la función de validación.

Pedir la desinfección de un valor de referencia no hará nada, ya que "Params::Validate" solo intentará desinfectar la referencia en sí misma.

Revisitar obligatorio/opcional

Si desea especificar algo como tipo o interfaz, además del hecho de que un parámetro puede ser opcional, haga esto:

validate(
    @_, {
        foo => { type => SCALAR },
        bar => { type => ARRAYREF, optional => 1 }
    }
);

o esto para parámetros posicionales:

validate_pos(
    @_,
    { type => SCALAR },
    { type => ARRAYREF, optional => 1 }
);

Por defecto, se asume que los parámetros son obligatorios a menos que se especifiquen como opcionales.

Dependencias

También es posible especificar que un parámetro opcional dado depende de la presencia de uno o más parámetros opcionales.

validate(
    @_, {
        cc_number => {
            type     => SCALAR,
            optional => 1,
            depends  => [ 'cc_expiration', 'cc_holder_name' ],
        },
        cc_expiration  => { type => SCALAR, optional => 1 },
        cc_holder_name => { type => SCALAR, optional => 1 },
    }
);

En este caso, "cc_number", "cc_expiration" y "cc_holder_name" son todos opcionales. Sin embargo, si se proporciona "cc_number", entonces también se deben proporcionar "cc_expiration" y "cc_holder_name".

Esto le permite agrupar conjuntos de parámetros que deben proporcionarse todos juntos.

La versión validate_pos() de las dependencias es ligeramente diferente, en el sentido de que solo puedes depender de un otro parámetro. Además, si, por ejemplo, el segundo parámetro depende del cuarto parámetro, entonces implica una dependencia del tercer parámetro también. Esto se debe a que si el cuarto parámetro es requerido, el usuario también debe proporcionar un tercer parámetro para que pueda haber cuatro parámetros en total.

"Params::Validate" morirá si intentas depender de un parámetro no declarado como parte de tu especificación de parámetros.

Especificar valores por defecto

Si las funciones validate() o validate_pos() se llaman en un contexto de lista, devolverán un hash o que contendrá los parámetros originales más los valores por defecto según lo indicado por la especificación de validación.

Si la función no se llama en un contexto de lista, proporcionar un valor por defecto en la especificación de validación aún indica que el parámetro es opcional.

El hash o array devuelto por la función siempre será una copia de los parámetros originales, para dejar @_ intacto para la función que llama.

Ejemplos simples de valores por defecto serían:

my %p = validate( @_, { foo => 1, bar => { default => 99 } } );
my @p = validate_pos( @_, 1, { default => 99 } );

En contexto escalar, se devolverá una referencia a hash o una referencia a array, según corresponda.

NOTAS DE USO

Fallo de validación

Por defecto, cuando la validación falla, "Params::Validate" llama a Carp::confess(). Esto se puede anular estableciendo la opción "on_fail", que se describe en la sección OPCIONES GLOBALES.

Llamadas a métodos

Al usar este módulo para validar los parámetros pasados a una llamada de método, probablemente querrá eliminar la clase/objeto de la lista de parámetros *antes* de llamar a validate() o validate_pos(). Si su método espera parámetros con nombre, esto es necesario para que la función validate() funcione realmente, de lo contrario @_ no será utilizable como un hash, porque primero tendrá su objeto (o clase) *seguido* por un conjunto de claves y valores.

Por lo tanto, el uso idiomático de validate() en una llamada de método se verá algo así:

sub method {
    my $self = shift;
    my %params = validate(
        @_, {
            foo => 1,
            bar => { type => ARRAYREF },
        }
    );
}

Acelerar la validación

En la mayoría de los casos, la especificación de validación seguirá siendo la misma para cada llamada a una subrutina. En ese caso, puede acelerar la validación definiendo la especificación de validación una sola vez, en lugar de en cada llamada a la subrutina:

my %spec = ( ... );
sub foo {
    my %params = validate( @_, \%spec );
}

También puede u

USO_DEL_ESTADO

use feature 'state'; sub foo { state $spec = { ... }; my %params = validate( @_, $spec ); }

"OPCIONES_GLOBALES" OPCIONES

Dado que la API de las funciones validate() y validate_pos() no permite especificar opciones aparte de la especificación de validación, es posible configurar algunas opciones como 'globales' pseudo. Estas permiten especificar si la validación de parámetros con nombre debe ser sensible a mayúsculas y minúsculas, por ejemplo.

Estas opciones se llaman 'globales' pseudo porque estas configuraciones **solo se aplican a las llamadas que se originan desde el paquete que estableció las** **opciones**.

En otras palabras, si estoy en el paquete "Foo" y llamo a validation_options(), esas opciones solo estarán en vigor cuando llame a validate() desde el paquete "Foo".

Si bien esto es bastante diferente de cómo operan la mayoría de los módulos, considero que es necesario para permitir que un módulo/aplicación utilice Params::Validate mientras sigue utilizando otros módulos que también lo usan, quizás con diferentes opciones establecidas.

La desventaja es que si estás escribiendo una aplicación con un estilo de llamada estándar para todas las funciones, y tu aplicación tiene diez módulos, **cada** **módulo debe incluir una llamada a** validation_options(). Por supuesto, podrías escribir un módulo que todos tus módulos utilicen y que emplee varios trucos para hacer esto al importarlo.

Opciones

  • normalize_keys => $callback

    Esta opción solo es relevante cuando se trata de parámetros con nombre.

    Esta función de retorno se utilizará para transformar las claves de hash de los parámetros y de la especificación del parámetro cuando se llamen validate() o validate_with().

    Cualquier alteración realizada por esta función de retorno se reflejará en el hash de parámetros que devuelve la función de validación. Por ejemplo:

    sub foo {
    return validate_with(
        params => \@_,
        spec   => { foo => { type => SCALAR } },
        normalize_keys =>
            sub { my $k = shift; $k =~ s/^-//; return uc $k },
    );
}
%p = foo( foo => 20 );
# $p{FOO} ahora es 20
%p = foo( -fOo => 50 );
# $p{FOO} ahora es 50

    La función de retorno debe devolver un valor definido.

    Si se proporciona una función de retorno, las opciones obsoletas "ignore_case" y "strip_leading" se ignoran.

  • allow_extra => $booleano

    Si es verdadero, la rutina de validación permitirá parámetros adicionales no especificados en la especificación de validación. En el caso de parámetros posicionales, esto permite un número ilimitado de parámetros máximos (aunque todavía se puede establecer un mínimo). El valor predeterminado es falso.

  • on_fail => $callback

    Si se proporciona, esta función de retorno se llamará cada vez que falle una comprobación de validación. Se llamará con un solo parámetro, que será una cadena que describe el fallo. Esto es útil si desea que este módulo lance excepciones como objetos en lugar de cadenas, por ejemplo.

    Se espera que esta función de retorno llame internamente a die(). Si no lo hace, la validación continuará, con resultados impredecibles.

    El valor predeterminado es simplemente usar la función confess() del módulo Carp.

  • stack_skip => $número

    Esto le dice a Params::Validate cuántos marcos de la pila saltar al encontrar un nombre de subrutina para usar en los mensajes de error. Por defecto, mira un marco hacia atrás, al llamador inmediato de validate() o validate_pos(). Si se establece esta opción, se omiten el número dado de marcos.

  • ignore_case => $booleano

    OBSOLETO

    Esto solo es relevante cuando se trata de parámetros con nombre. Si es verdadero, el código de validación ignorará las mayúsculas y minúsculas de los nombres de los parámetros. El valor predeterminado es falso.

  • strip_leading => $caracteres

    OBSOLETO

    Esto también es solo relevante cuando se trata de parámetros con nombre. Si se proporciona, se considerarán equivalentes los parámetros que comiencen con estos caracteres a los parámetros sin ellos por completo. Por ejemplo, si se especifica como '-', entonces "-foo" y "foo" se considerarían idénticos.

OPCIONES_POR_INVOCACIÓN

La función validate_with() se puede usar para establecer las opciones enumeradas anteriormente en una base por invocación. Por ejemplo:

my %p = validate_with(
    params => \@_,
    spec   => {
        foo => { type    => SCALAR },
        bar => { default => 10 }
    },
    allow_extra => 1,
);

Además de las opciones enumeradas anteriormente, también es posible establecer la opción "called", que debe ser una cadena. Esta cadena se utilizará en cualquier mensaje de error causado por un fallo al cumplir la especificación de validación.

Esta subrutina validará parámetros con nombre como un hash si el parámetro "spec" es una referencia de hash. Si es una referencia de array, se asume que los parámetros son posicionales.

my %p = validate_with(
    params => \@_,
    spec   => {
        foo => { type    => SCALAR },
        bar => { default => 10 }
    },
    allow_extra => 1,
    called      => 'El constructor de la clase Quux::Baz',
);
my @p = validate_with(
    params => \@_,
    spec   => [
        { type    => SCALAR },
        { default => 10 }
    ],
    allow_extra => 1,
    called      => 'El constructor de la clase Quux::Baz',
);

DESACTIVACIÓN_DE_LA_VALIDACIÓN

Si la variable de entorno "PERL_NO_VALIDATION" se establece en algo verdadero, la validación se desactiva. Esto puede ser útil si solo desea utilizar este módulo durante el desarrollo, pero no quiere la penalización de rendimiento en producción.

El único error que se detectará será cuando se pase un número impar de parámetros a una función/método que espera un hash.

Si desea activar y desactivar selectivamente la validación en tiempo de ejecución, puede establecer directamente la variable global $Params::Validate::NO_VALIDATION. Se **recomienda encarecidamente** que **localice** cualquier cambio en esta variable, ya que otros módulos que esté utilizando pueden esperar que la validación esté activada cuando se ejecuten. Por ejemplo:

{
    local $Params::Validate::NO_VALIDATION = 1;
    # sin error
    foo( bar => 2 );
}
# error
foo( bar => 2 );
sub foo {
    my %p = validate( @_, { foo => 1 } );
    ...;
}

Pero si quieres dispararte en el pie y simplemente desactivarla, ¡adelante!

ESPECIFICACIÓN_DE_UNA_IMPLEMENTACIÓN

Este módulo viene con dos implementaciones equivalentes, una en XS y otra en Perl puro. Por defecto, intentará cargar la versión XS y recurrirá a la implementación de Perl puro según sea necesario. Si desea solicitar una versión específica, puede establecer la variable de entorno "PARAMS_VALIDATE_IMPLEMENTATION" en "XS" o "PP". Si la implementación que solicita no se puede cargar, este módulo fallará al cargarse.

MODO_TAINT

La implementación XS de este módulo tiene algunos problemas en modo taint con versiones de Perl anteriores a 5.14. Si la validación falla, en lugar de recibir el mensaje de error esperado, recibirá un mensaje como "Insecure dependency in eval_sv". Esto se puede solucionar deshaciendo el taint de los argumentos usted mismo, utilizando la implementación de Perl puro o actualizando su Perl.

LIMITACIONES

Por el momento no hay forma (salvo una función de retorno) de especificar que algo debe ser de una de una lista de clases, o que debe poseer uno de una lista de métodos. Si esto es deseado, se puede agregar en el futuro.

Idealmente, solo habría una función de validación. Si alguien descubre cómo hacer esto, por favor hágamelo saber.
