PPI(3pm) Documentación de Perl contribuida por el usuario PPI(3pm)

NOMBRE

PPI - Analizar, Evaluar y Manipular Perl (sin usar perl)

SINOPSIS

use PPI;

# Crear un nuevo documento vacío
my $Document = PPI::Document->new;

# Crear un documento a partir de código fuente
$Document = PPI::Document->new(\'print "¡Hola Mundo!\n"');

# Cargar un Documento desde un archivo
$Document = PPI::Document->new('Module.pm');

# ¿Contiene algún POD?
if ( $Document->find_any('PPI::Token::Pod') ) {
    print "El módulo contiene POD\n";
}

# Obtener el nombre del paquete principal
$pkg = $Document->find_first('PPI::Statement::Package')->namespace;

# Eliminar toda esa desagradable documentación
$Document->prune('PPI::Token::Pod');
$Document->prune('PPI::Token::Comment');

# Guardar el archivo
$Document->save('Module.pm.stripped');

DESCRIPCIÓN

Acerca de este documento

Este es el manual de PPI. Describe su razón de ser, su estructura general, su uso, una descripción general de la API y proporciona algunas muestras de implementación.

Antecedentes

La capacidad de leer y manipular Perl (el lenguaje) programáticamente, aparte de con perl (la aplicación), fue algo que causó dificultades durante mucho tiempo.

La causa de este problema fue la gramática compleja y dinámica de Perl. Aunque normalmente no hay una gran diversidad en la gramática de la mayoría del código Perl, ciertos problemas causan grandes problemas a la hora de analizarlo.

De hecho, bastante al principio de la historia de Perl, Tom Christiansen introdujo a la comunidad Perl la cita de "Nada más que perl puede analizar Perl", o como se dice más a menudo ahora como un lugar común:

"Sólo perl puede analizar Perl"

Un ejemplo de las cosas que impiden que Perl se analice fácilmente son las firmas de funciones, como se demuestra en lo siguiente.

@result = (dothis $foo, $bar);

# ¿Con cuál de las siguientes es equivalente?
@result = (dothis($foo), $bar);
@result = dothis($foo, $bar);

La primera línea anterior puede interpretarse de dos maneras diferentes, dependiendo de si la función &dothis espera un argumento, o dos, o varios.

Un "analizador de código" (algo que analiza con fines de ejecución) como perl necesita información que no se encuentra en la vecindad inmediata de la sentencia que se está analizando.

La información podría no sólo estar en otra parte del archivo, sino que podría no estar ni siquiera en el mismo archivo. También podría no ser posible determinar esta información sin la ejecución previa de un bloque "BEGIN {}", o la carga y ejecución de uno o más módulos externos. O peor aún, la función &dothis podría ni siquiera haber sido escrita todavía.

Al analizar Perl como código, también debe ejecutarlo.

Incluso el propio perl nunca comprende completamente la estructura del código fuente después y, de hecho, **mientras** lo procesa, y en ese sentido no "analiza" el código fuente de Perl en algo remotamente parecido a un documento estructurado. Esto lo hace de poca utilidad para cualquier tarea que necesite tratar el código fuente como un documento, y hacerlo de forma fiable y robusta.

Para más información sobre por qué es imposible analizar perl, vea la respuesta seminal de Randal Schwartz a la pregunta de "¿Por qué no puedes analizar Perl?".

http://www.perlmonks.org/index.pl?node_id=44722

El propósito de PPI **no** es analizar código Perl, sino **documentos** Perl. Al tratar el problema de esta manera, podemos analizar un solo archivo que contenga código fuente Perl "aislado" de cualquier otro recurso, como las bibliotecas de las que el código pueda depender, y sin necesidad de ejecutar una instancia de perl junto o dentro del analizador.

Históricamente, el uso de un analizador perl incrustado se consideraba ampliamente la vía más probable para encontrar una solución al análisis de Perl. Se ha investigado de vez en cuando, pero los intentos generalmente han fallado o han sufrido casos extremos lo suficientemente malos como para ser abandonados.

¿Qué significa PPI?

"PPI" es un acrónimo del nombre original más largo del módulo "Parse::Perl::Isolated". Y con el espíritu de los juegos tontos de acrónimos jugados por ciertos proyectos de Código Abierto sin nombre que quizás hayas oído mencionar, también es un retroacrónimo de "I Parse Perl" (Yo Analizo Perl).

Por supuesto, podría estar mintiendo y haber inventado la segunda parte 10 minutos antes del lanzamiento de PPI 1.000. Además, **todos** los paquetes Perl geniales tienen TLAs (Acrónimos de Tres Letras). Es una regla o algo así.

¿Por qué no simplemente pensar en ello como la **Interfaz de Análisis de Perl** para simplificar.

El nombre original se acortó para evitar que el autor (y tú, los usuarios) contrajeran Lesiones por Esfuerzo Repetitivo (RSI) al tener que escribir cosas locas como "Parse::Perl::Isolated::Token::QuoteLike::Backtick" 100 veces al día.

En reconocimiento de que alguien podría algún día encontrar una solución válida para el problema de la gramática, se decidió al inicio del proyecto dejar el espacio de nombres "Parse::Perl" libre para cualquier esfuerzo de este tipo.

Desde entonces, he podido demostrarme a mí mismo que **es** verdaderamente imposible analizar con precisión Perl como código y documento a la vez. Para los académicos, el análisis de Perl sufre del "Problema de la Parada".

¿Por qué analizar Perl?

Una vez que puedas aceptar que nunca podremos analizar Perl lo suficientemente bien como para cumplir los estándares de aquello que trata a Perl como código, vale la pena reexaminar *por qué* queremos "analizar" Perl en absoluto.

¿Cuáles son las cosas para las que la gente podría querer un "analizador de Perl"?

Documentación
Analizar el contenido de un documento Perl para generar automáticamente documentación, en paralelo o como reemplazo de la documentación POD.

Permitir a un indexador localizar y procesar todos los comentarios y la documentación del código para aplicaciones de "búsqueda de texto completo".

Análisis Estructural y de Calidad
Determinar la calidad u otras métricas en un cuerpo de código, e identificar situaciones relacionadas con frases, técnicas o ubicaciones particulares.

Indexar funciones, variables y paquetes dentro del código Perl, y realizar análisis de búsqueda y de grafos (en el sentido de nodos/aristas) en bases de código grandes.

Perl::Critic, basado en PPI, es una herramienta grande y próspera para la detección de errores y el análisis de estilo del código Perl.

Refactorización
Realizar cambios estructurales, de sintaxis u otros en el código de manera automatizada, ya sea de forma independiente o con la ayuda de un editor. Esta lista de tareas incluye backporting, forward porting, evaluación parcial, "mejora" del código, o lo que sea. Todo el tipo de cosas que querrías de un Perl::Editor.
Diseño
Cambiar el diseño del código sin cambiar su significado. Esto incluye técnicas como la limpieza (como perltidy), ofuscación, compresión y "aplastamiento", o para implementar preferencias o políticas de formato.
Presentación
Esto incluye métodos para mejorar la presentación del código, sin cambiar el contenido del código. Modificar, mejorar, colorear sintácticamente, etc., la presentación de un documento Perl. Generar funciones tipo "IntelliText".

Si tratamos esto como una línea de base para el tipo de cosas en las que tendremos que construir sobre Perl, entonces se hace posible identificar un estándar de cuán bueno necesita ser un analizador de Perl.

¿Cuán bueno es Suficientemente Bueno(TM)?

PPI busca ser lo suficientemente bueno como para lograr todas las tareas anteriores, o para proporcionar una API suficientemente buena sobre la que permitir a otros implementar módulos en estas y áreas relacionadas.

NAME

PPI - A Perl code parsing module

SYNOPSIS

```perl

    use PPI;

    # Read a file
    my $doc = PPI->new()->parse_file('some_file.pl');

    # Or from a string
    my $doc = PPI->new()->parse(q{
        my $foo = 'bar';
        sub baz { return 1 }
    });

    # Now you can work with the document object
    if ($doc->defined_variables) {
        print "Found variables\n";
    }
    my @statements = $doc->statements;
    ...

DESCRIPTION

PPI is a module that provides a parsing interface to Perl code. This means that it can read Perl code, and then provide you with an object model that represents that code. This can then be used to inspect the code, modify it, or generate new code.

The primary goal of PPI is to parse Perl code as a document, rather than as executed code. This means that it attempts to store everything that is in the source file, including whitespace, comments and POD, and associated that content with the correct locations within the Perl structure of the document.

The secondary goal of PPI is to be able to "round trip" code. This means that if you parse a file, make no modifications to the document object, and then serialize it back out to a file, that the output file will be identical to the input file. This is a surprisingly difficult thing to achieve, and is the main reason why PPI has so many classes.

The third goal of PPI is to provide a clean and simple API that allows you to easily achieve the primary goals.

Perl Document Object Model

The PPI module uses a system of objects called the Perl Document Object Model, or PDOM, to represent the Perl code.

A PDOM consists of a tree of objects. Each object represents a part of the source file. The most generic of these are PPI::Element and PPI::Node. PPI::Element is the base class for all objects, and PPI::Node is the base class for objects that contain other objects.

The main classes that you will likely be working with are:

PPI::Document
Represents a complete Perl file or string.
PPI::Statement
Represents a single statement, as understood by Perl. This can be anything from a simple variable assignment to a complex block of code.
PPI::Structure
Represents a structure within a statement. This includes things like blocks of code ({ ... }), lists (( ... )), arrays ([ ... ]), hashes ({ ... }), conditions (if (...) etc).
PPI::Token
Represents a token in the source code. This is the most basic element, and includes things like words, numbers, operators, symbols, whitespace, comments, and POD.

There are a number of other classes for more specific cases, but these are the main ones you will encounter.

Limitations

PPI attempts to parse Perl code as a document, which is subtly different from parsing it as executed code. As a result, there are a few limitations:

  • Source Filters

    PPI does not currently support source filters. Any code that uses source filters (such as the FILTER pragma) will not be parsed correctly. This is because source filters change the code being parsed on the fly, and PPI cannot know what the altered code will be.

  • `use Source::Filter`

    As an extension of the above, PPI does not support code that has been modified by modules such as Acme::Bleach, or modules that implement their own source filters (such as Switch). While PPI may be able to parse some of these in the future, no guarantee is made.

    The ability to extend PPI to handle lexical additions to the language is planned for a future release.

  • CPAN Coverage

    The original goal was to parse 99% of all Perl documents on CPAN. This goal has been exceeded, with only a handful of non-Acme modules on CPAN currently not parseable by PPI. Most of these are so badly broken that they do not compile as Perl code anyway.

    Therefore, unless you are actively trying to break PPI, it should handle your code without issue.

Internationalisation

PPI provides partial support for internationalisation and localisation.

Specifically, it allows the use of characters from the Latin-1 character set to be used in quotes, comments, and POD. Primarily, this covers languages from Europe and South America.

PPI does not currently provide support for Unicode. If you need Unicode support and would like to help, contact the author. (contact details below)

Round Trip Safe

When PPI parses a file it builds everything into the model, including whitespace. This is needed in order to make the Document fully "Round Trip" safe.

The general concept behind a "Round Trip" parser is that it knows what it is parsing is somewhat uncertain, and so expects to get things wrong from time to time. In the cases where it parses code wrongly the tree will serialize back out to the same string of code that was read in, repairing the parser's mistake as it heads back out to the file.

The end result is that if you parse in a file and serialize it back out without changing the tree, you are guaranteed to get the same file you started with. PPI does this correctly and reliably for 100% of all known cases.

What goes in, will come out. Every time.

The one minor exception at this time is that if the newlines for your file are wrong (meaning not matching the platform newline format), PPI will localise them for you. (It isn't to be convenient, supporting arbitrary newlines would make some of the code more complicated)

Better control of the newline type is on the wish list though, and anyone wanting to help out is encouraged to contact the author.

IMPLEMENTATION

General Layout

PPI is built upon two primary "parsing" components, PPI::Tokenizer and PPI::Lexer, and a large tree of about 70 classes which implement the various the Perl Document Object Model (PDOM).

The PDOM is conceptually similar in style and intent to the regular DOM or other code Abstract Syntax Trees (ASTs), but contains some differences to handle perl-specific cases, and to assist in treating the code as a document. Please note that it is not an implementation of the official Document Object Model specification, only somewhat similar to it.

On top of the Tokenizer, Lexer and the classes of the PDOM, sit a number of classes intended to make life a little easier when dealing with PDOM trees.

Both the major parsing components were hand-coded from scratch with only plain Perl code and a few small utility modules. There are no grammar or patterns mini-languages, no YACC or LEX style tools and only a small number of regular expressions.

This is primarily because of the sheer volume of accumulated cruft that exists in Perl. Not even perl itself is capable of parsing Perl documents (remember, it just parses and executes it as code).

As a result, PPI needed to be cruftier than perl itself. Feel free to shudder at this point, and hope you never have to understand the Tokenizer codebase. Speaking of which...

The Tokenizer

The Tokenizer takes source code and converts it into a series of tokens. It does this using a slow but thorough character by character manual process, rather than using a pattern system or complex regexes.

Or at least it does so conceptually. If you were to actually trace the code you would find it's not truly character by character due to a number of regexps and optimisations throughout the code. This lets the Tokenizer "skip ahead" when it can find shortcuts, so it tends to jump around a line a bit wildly at times.

In practice, the number of times the Tokenizer will actually move the character cursor itself is only about 5% - 10% higher than the number of tokens contained in the file. This makes it about as optimal as it can be made without implementing it in something other than Perl.

In 2001 when PPI was started, this structure made PPI quite slow, and not really suitable for interactive tasks. This situation has improved greatly with multi-gigahertz processors, but can still be painful when working with very large files.

The target parsing rate for PPI is about 5000 lines per gigacycle. It is currently believed to be at about 1500, and the main avenue for making it to the target speed has now become PPI::XS, a drop-in XS accelerator for PPI.

Since PPI::XS has only just gotten off the ground and is currently only at proof-of-concept stage, this may take a little while. Anyone interested in helping out with PPI::XS is highly encouraged to contact the author. In fact, the design of PPI::XS means it's possible to port one function at a time safely and reliably. So every little bit will help.

The Lexer

The Lexer takes a token stream, and converts it to a lexical tree. Because we are parsing Perl documents this includes whitespace, comments, and all number of weird things that have no relevance when code is actually executed.

An instantiated PPI::Lexer consumes PPI::Tokenizer objects and produces PPI::Document objects. However you should probably never be working with the Lexer directly. You should just be able to create PPI::Document objects and work with them directly.

The Perl Document Object Model

The PDOM is a structured collection of data classes that together provide a correct and scalable model for documents that follow the standard Perl syntax.

To summarize the above layout, all PDOM objects inherit from the PPI::Element class.

Under this are PPI::Token, strings of content with a known type, and PPI::Node, syntactically significant containers that hold other Elements.

The three most important of these are the PPI::Document, the PPI::Statement and the PPI::Structure classes.

The Document, Statement and Structure

At the top of all complete PDOM trees is a PPI::Document object. It represents a complete file of Perl source code as you might find it on disk.

There are some specialised types of document, such as PPI::Document::File and PPI::Document::Normalized but for the purposes of the PDOM they are all just considered to be the same thing.

Each Document will contain a number of Statements, Structures and Tokens.

A PPI::Statement is any series of Tokens and Structures that are treated as a single contiguous statement by perl itself. You should note that a Statement is as close as PPI can get to "parsing" the code in the sense that perl-itself parses Perl code when it is building the op-tree.

Debido al aislamiento y la sintaxis de Perl, es demostrablemente imposible que PPI determine con precisión la precedencia de los operadores o qué tokens son argumentos implícitos para una llamada a subrutina.

Así que, en lugar de darte una mala suposición con una alta probabilidad de ser incorrecta, PPI no intenta determinar la precedencia o los parámetros de las subrutinas en absoluto.

En un nivel fundamental, solo sabe que esta serie de elementos representa una única Sentencia tal como Perl la ve, pero puede hacerlo con suficiente certeza como para que sea confiable.

Sin embargo, para tipos específicos de Sentencias, el PDOM puede derivar información útil adicional sobre su significado. Para el mejor, más útil y más utilizado ejemplo, consulta PPI::Statement::Include.

Una PPI::Structure es cualquier serie de tokens contenidos dentro de llaves coincidentes. Esto incluye bloques de código, condiciones, llaves de argumentos de funciones, constructores de arrays y hashes anónimos, listas, llaves de alcance y todas las demás estructuras sintácticas representadas por un par de llaves coincidentes, incluyendo (aunque al principio no parezca obvio) las llaves "<READLINE>".

Cada Structure contiene cero, uno o muchos Tokens y Structures (las reglas para esto varían para las diferentes sub-clases de Structure)

Bajo las reglas de la estructura PDOM, una Sentencia nunca puede contener directamente otra Sentencia hija, una Structure nunca puede contener directamente otra Structure hija, y un Documento nunca puede contener otro Documento en ningún lugar del árbol.

Aparte de estas tres reglas, el árbol PDOM es extremadamente flexible.

El PDOM en Acción

Para demostrar el PDOM en uso, comencemos con un ejemplo que muestra cómo podría verse el árbol para el siguiente fragmento de código Perl simple.

#!/usr/bin/perl
print( "Hola Mundo!" );
exit();

Traducido a un árbol PDOM, tendría la siguiente estructura (como se muestra a través del PPI::Dumper incluido).

PPI::Document
  PPI::Token::Comment                '#!/usr/bin/perl\n'
  PPI::Token::Whitespace             '\n'
  PPI::Statement
    PPI::Token::Word                 'print'
    PPI::Structure::List             ( ... )
      PPI::Token::Whitespace         ' '
      PPI::Statement::Expression
        PPI::Token::Quote::Double    '"Hola Mundo!"'
      PPI::Token::Whitespace         ' '
    PPI::Token::Structure            ';'
  PPI::Token::Whitespace             '\n'
  PPI::Token::Whitespace             '\n'
  PPI::Statement
    PPI::Token::Word                 'exit'
    PPI::Structure::List             ( ... )
    PPI::Token::Structure            ';'
  PPI::Token::Whitespace             '\n'

Por favor, ten en cuenta que en este ejemplo, las cadenas solo se enumeran para el PPI::Token real que contiene esa cadena. Las Structures se enumeran con el tipo de caracteres de llave que representan indicados.

El módulo PPI::Dumper puede usarse para generar árboles similares tú mismo.

Podemos hacer que ese volcado PDOM sea un poco más fácil de leer si eliminamos todo el espacio en blanco. Aquí está de nuevo, sin los espacios en blanco distractores.

PPI::Document
  PPI::Token::Comment                '#!/usr/bin/perl\n'
  PPI::Statement
    PPI::Token::Word                 'print'
    PPI::Structure::List             ( ... )
      PPI::Statement::Expression
        PPI::Token::Quote::Double    '"Hola Mundo!"'
    PPI::Token::Structure            ';'
  PPI::Statement
    PPI::Token::Word                 'exit'
    PPI::Structure::List             ( ... )
    PPI::Token::Structure            ';'

Como puedes ver, el árbol puede volverse bastante profundo a veces, especialmente cuando cada token aislado en un corchete se convierte en su propia sentencia. Esto es necesario para permitir que cualquier cosa dentro del árbol pueda crecer. También hace que los algoritmos de búsqueda y análisis sean mucho más flexibles.

Debido a la profundidad y complejidad de los árboles PDOM, se ha añadido un gran número de métodos muy fáciles de usar siempre que ha sido posible para ayudar a las personas que trabajan con árboles PDOM a realizar tareas normales de forma relativamente rápida y eficiente.

Resumen de las Clases Principales

Las principales clases de PPI, y los enlaces a su propia documentación, se enumeran aquí en orden alfabético.

PPI::Document
El objeto Document, la raíz del PDOM.
PPI::Document::Fragment
Un fragmento cohesivo de un Documento más grande. Aunque no tiene un uso real actual, es necesario para su uso en ciertos algoritmos internos de manipulación de árboles.

Por ejemplo, para hacer cosas como cortar/copiar/pegar, etc. Muy similar a un PPI::Document, pero tiene algunos métodos adicionales y no representa un límite de alcance léxico.

Un fragmento de documento tampoco es serializable, por lo que no se puede escribir en un archivo.

PPI::Dumper
Una clase simple para volcar versiones de depuración legibles de estructuras PDOM, como en la demostración anterior.
PPI::Element
La clase Element es la clase base abstracta para todos los objetos dentro del PDOM.
PPI::Find
Implementa una forma de objeto instanciable de búsqueda de árboles PDOM.
PPI::Lexer
El Lexer de PPI. Convierte flujos de Tokens en árboles PDOM.
PPI::Node
El objeto Node, la clase base abstracta para todos los objetos PDOM que pueden contener otros Elementos, como los objetos Document, Statement y Structure.
PPI::Statement
La clase base para todas las sentencias de Perl. Las sentencias genéricas de "evaluar por efectos secundarios" son de este tipo real. Otros tipos de sentencias más interesantes pertenecen a una de sus hijas.

Consulta su propia documentación para una descripción más detallada y una lista de todos los diferentes tipos de sentencias y sub-clases.

PPI::Structure
La clase base abstracta para todas las estructuras. Una Structure es una construcción del lenguaje que consiste en llaves coincidentes que contienen un conjunto de otros elementos.

Consulta la documentación de PPI::Structure para obtener una descripción y una lista de todos los diferentes tipos de estructuras y sub-clases.

PPI::Token
Un token es la unidad básica de contenido. En su nivel más básico, un Token es solo una cadena etiquetada con metadatos (su clase y algunas banderas adicionales en algunos casos).
PPI::Token::_QuoteEngine
Las clases PPI::Token::Quote y PPI::Token::QuoteLike proporcionan clases base abstractas para los muchos y variados tipos de comillas y cosas similares a comillas en Perl. Sin embargo, gran parte de la lógica real de las comillas se implementa en un motor de comillas separado, ubicado en PPI::Token::_QuoteEngine.

Las clases que heredan de PPI::Token::Quote, PPI::Token::QuoteLike y PPI::Token::Regexp generalmente son analizadas solo por el Motor de Comillas.

PPI::Tokenizer
El Tokenizador de PPI. Un Tokenizer consume un fragmento de texto y proporciona acceso a un flujo de objetos PPI::Token.

El Tokenizador es muy, muy complicado, hasta el punto de que incluso el autor camina con cuidado al trabajar con él.

La mayor parte de la complicación es el resultado de optimizaciones que han triplicado la velocidad de tokenización, a expensas de la mantenibilidad. Manejamos el espagueti comentando todo extensamente.

PPI::Transform
La API de Transformación de Documentos Perl. Proporciona una interfaz estándar y una clase base abstracta para objetos y clases que manipulan Documentos.

INSTALACIÓN

La distribución central de PPI es puro Perl y se ha mantenido lo más compacta posible y con la menor cantidad de dependencias posible.

Debería descargarse e instalarse normalmente en cualquier plataforma desde las aplicaciones CPAN y CPANPLUS, o directamente usando el archivo tar de la distribución. Si se instala manualmente, puede que necesites instalar primero algunos pequeños módulos de utilidad. Los exactos dependerán de tu versión de perl.

No hay instrucciones especiales de instalación para PPI, y se aplican las instrucciones normales de "Perl Makefile.PL", "make", "make test", "make install".

EXTENSIÓN

El propio espacio de nombres PPI está reservado para uso de PPI. Se recomienda utilizar el espacio de nombres PPIx:: para modificaciones o prototipos específicos de PPI, o Perl:: para módulos que proporcionan funciones generales relacionadas con el lenguaje Perl.

Si lo que deseas implementar parece encajar en el espacio de nombres PPIx::, deberías considerar contactar primero a los mantenedores de PPI en GitHub, ya que lo que deseas puede estar ya en progreso, o puedes considerar contribuir a PPI mismo.
