PPI::Tokenizer(3) Documentación de Perl aportada por el usuario PPI::Tokenizer(3)

NOMBRE

PPI::Tokenizer - El Tokenizador de Documentos Perl

SINOPSIS

# Crear un tokenizador para un archivo, array o cadena
$Tokenizer = PPI::Tokenizer->new( 'archivo.pl' );
$Tokenizer = PPI::Tokenizer->new( \@lineas       );
$Tokenizer = PPI::Tokenizer->new( \$fuente      );

# Devolver todos los tokens del documento
my $tokens = $Tokenizer->all_tokens;

# O podemos usarlo como un iterador
while ( my $Token = $Tokenizer->get_token ) {
      print "Token encontrado '$Token'\n";
}

# Si REALMENTE necesitamos mover el cursor manualmente,
# también puedes hacerlo (el lexer necesita esta capacidad para hacer rollbacks)
$is_incremented = $Tokenizer->increment_cursor;
$is_decremented = $Tokenizer->decrement_cursor;

DESCRIPCIÓN

PPI::Tokenizer es la clase que proporciona objetos Tokenizer para su uso en la división de cadenas de código fuente Perl en Tokens.

Para cuando lea esto, probablemente necesite saber un poco sobre la diferencia entre cómo perl analiza el "código" Perl y cómo PPI analiza los "documentos" Perl.

"perl" en sí (el intérprete) utiliza una especificación lex modificada en gran medida para especificar su lógica de análisis, mantiene varios tipos de estado a medida que avanza, y tokeniza, lexifica Y EJECUTA incrementalmente al mismo tiempo.

De hecho, es matemáticamente imposible utilizar el método de análisis de perl sin ejecutar código simultáneamente. Se ha publicado una prueba matemática formal que demuestra el método.

Aquí es de donde proviene el axioma "Solo perl puede analizar Perl".

PPI utiliza un enfoque completamente diferente al abandonar la capacidad (imposible) de analizar Perl de la misma manera que lo hace el intérprete, y en su lugar analiza la fuente como un documento, utilizando una estructura de documento derivada independientemente de la documentación Perl y aproximando la interpretación del intérprete perl tan de cerca como sea posible.

Hubo un momento de duda durante mucho tiempo sobre si podíamos acercarnos lo suficiente, pero al final resultó que se podía hacer.

En este enfoque, el tokenizador "PPI::Tokenizer" se implementa por separado del lexer PPI::Lexer.

El trabajo de "PPI::Tokenizer" es tomar código fuente puro como una cadena y dividirlo en un flujo/conjunto de tokens, y contiene la mayor parte de la "magia negra" utilizada en PPI. En comparación, el lexer implementa una estructura de árbol relativamente sencilla y tiene una implementación que no es complicada (en comparación con la locura en el tokenizador, al menos).

El Tokenizador utiliza una inmensa cantidad de heurísticas, conjeturas y código auxiliar, respaldado por una API interna muy, **MUY** flexible, pero afortunadamente fue posible encapsular en gran medida la magia negra, por lo que no hay mucho que se exponga a las personas que usan el "PPI::Tokenizer" en sí.

MÉTODOS

A pesar de la increíble complejidad, el Tokenizador en sí solo expone un número relativamente pequeño de métodos, con la mayor parte de la complejidad implementada en métodos privados.

new $archivo | \@lineas | \$fuente

El constructor principal "new" crea un nuevo objeto Tokenizer. Estos objetos no tienen parámetros de configuración y solo se pueden usar una vez, para tokenizar un único archivo de código fuente perl.

Toma como argumento una cadena escalar normal que contiene código fuente, una referencia a un escalar que contiene código fuente o una referencia a un ARRAY que contiene líneas de código fuente terminadas en nueva línea.

Devuelve un nuevo objeto "PPI::Tokenizer" en caso de éxito, o lanza una excepción PPI::Exception en caso de error.

get_token

Al usar el objeto PPI::Tokenizer como un iterador, el método "get_token" es el método principal que se utiliza. Incrementa el cursor y devuelve el siguiente Token en el array de salida.

El análisis real del archivo se realiza solo cuando es necesario, y línea por línea. Cuando "get_token" llega al final del array de tokens, hará que el analizador extraiga la siguiente línea y la analice, continuando según sea necesario hasta que haya más tokens en el array de salida que get_token pueda devolver.

Esto significa que se pueden crear varios objetos Tokenizer, y no consumirán CPU significativa hasta que realmente comience a extraer tokens de ellos.

Devuelve un objeto PPI::Token en caso de éxito, 0 si el Tokenizer había llegado al final del archivo, o "undef" en caso de error.

all_tokens

Cuando no se utiliza como iterador, el método "all_tokens" indica al Tokenizer que analice el archivo completo y devuelva todos los tokens en una sola referencia a ARRAY.

Cabe señalar que "all_tokens" NO interfiere con el uso del objeto Tokenizer como iterador (no modifica el cursor de tokens) y el uso de los dos mecanismos diferentes se puede mezclar de forma segura.

Devuelve una referencia a un ARRAY de objetos PPI::Token en caso de éxito o lanza una excepción en caso de error.

increment_cursor

Aunque expuesto como un método público, "increment_cursor" se implementa solo para uso experto, al escribir lexers u otros componentes que trabajan directamente en flujos de tokens.

Incrementa manualmente el cursor de tokens hacia adelante en el archivo, en efecto, "saltándose" el siguiente token.

Devuelve verdadero si el cursor se incrementa, 0 si ya está al final del archivo, o "undef" en caso de error.

decrement_cursor

Aunque expuesto como un método público, "decrement_cursor" se implementa solo para uso experto, al escribir lexers u otros componentes que trabajan directamente en flujos de tokens.

Decrementa manualmente el cursor de tokens hacia atrás en el archivo, en efecto, "deshaciendo" el flujo de tokens. Y de hecho, para eso está principalmente destinado, cuando el componente que consume el flujo de tokens necesita implementar algún tipo de característica de "deshacer" en su uso del flujo de tokens.

Devuelve verdadero si el cursor se decrementa, 0 si ya está al principio del archivo, o "undef" en caso de error.

NOTAS

Cómo funciona el Tokenizador

Entender el Tokenizador no es para los débiles de corazón. Es, con mucho, la pieza de perl más compleja y retorcida que jamás he escrito y que aún está construida correctamente y no es un terrible desastre espagueti. De hecho, probablemente quieras saltarte esta sección.

Pero si realmente quieres entender, bueno, allá vamos.

Entrada y Limpieza de Código Fuente

El Tokenizador comienza tomando código fuente en una variedad de formas, succionándolo todo y fusionándolo en una gran cadena, y realizando nuestra propia división interna de líneas, utilizando un "separador de líneas universal" que permite al Tokenizador tomar código fuente de cualquier plataforma (e incluso admite algunos tipos conocidos de saltos de línea rotos causados por errores de edición mixta mac/pc/*nix).

El array resultante de líneas se utiliza para alimentar al tokenizador, y también es accedido directamente por la lógica heredoc para realizar la parte orientada a líneas del soporte de here-doc.

Haciendo las cosas a la antigua

Debido a la complejidad de perl, y después de 2 intentos de análisis previamente abortados, al final el tokenizador se configuró en torno a un método línea-búfer carácter por carácter.

Es decir, el Tokenizador extrae y mantiene una línea a la vez en un búfer de línea, y

luego itera un cursor a lo largo de ella. En cada posición del cursor, se llama a un método en la clase de token en la que nos encontremos actualmente, la cual examinará el carácter en la posición actual y lo manejará.

A medida que se llaman los métodos manejadores en las diversas clases de tokens, estos construyen un array de tokens de salida para el código fuente.

Varias partes del Tokenizer utilizan la búsqueda anticipada, la búsqueda retrospectiva de distancia arbitraria (aunque actualmente el máximo son tres tokens significativos), o ambas, y varias otras suposiciones heurísticas.

Me han dicho que oficialmente se denomina un "analizador de retroceso con búsquedas anticipadas infinitas".

Variables de Estado

Además de la línea actual y el cursor de caracteres, el Tokenizer mantiene una serie de variables de estado diferentes.

Clase Actual
El Tokenizer mantiene la clase de token actual en todo momento. Gran parte del tiempo será simplemente la clase "Espacio en blanco", que es la base de un documento. A medida que el tokenizador ejecuta los diversos manejadores de caracteres, la clase cambia mucho a medida que avanza. De hecho, en algunos casos, el manejador de caracteres puede no manejar el carácter directamente, sino cambiar la "clase actual" y luego transferir el control al manejador de caracteres para la nueva clase.

Debido a esto, y a otras cosas que abordaré más adelante, el número de veces que se llaman los manejadores de caracteres no tiene, de hecho, una relación directa con el número de caracteres reales en el documento.

Zona Actual
En lugar de crear una pila de clases para permitir capas infinitamente anidadas de clases, el Tokenizer reconoce solo una única capa.

Dicho de otra manera, en varias partes del archivo, el Tokenizer reconocerá diferentes clases "base" o "sustrato". Cuando un Token como un comentario o un número es finalizado por el tokenizador, este "retrocede" al estado base.

Esto permite la tokenización adecuada de áreas especiales como los bloques __DATA__ y __END__, que también contienen cosas como comentarios y POD, sin permitir la creación de Tokens significativos dentro de estas áreas.

Para la parte principal de un documento, utilizamos PPI::Token::Whitespace para esto, con la idea de que el código está "flotando en un mar de espacios en blanco".

Token Actual
La última variable de estado principal es el "token actual". Este es el Token que está siendo construido actualmente por el Tokenizer. Para ciertos tipos, puede ser manipulado, transformado y cambiar de clase considerablemente mientras se ensambla, a medida que la comprensión del token por parte del Tokenizer sobre el contenido del token cambia.

Cuando el Tokenizer está seguro de que ha visto el final del Token, este será "finalizado", lo que lo agregará al array de tokens de salida y restablecerá la clase actual a la de la zona en la que nos encontramos actualmente.

También debo señalar en este punto que la variable "token actual" es opcional. El Tokenizer es capaz de saber a qué clase está configurado actualmente, sin haber acumulado realmente ningún carácter en el Token.

Haciéndolo más rápido

Como me imagino, llamar a varios métodos diferentes para cada carácter y ejecutar expresiones regulares y otras heurísticas complejas hizo que la primera versión completamente funcional del tokenizador fuera extremadamente lenta.

Durante las pruebas, creé una métrica para medir la velocidad de análisis llamada LPGC, o "líneas por gigaciclo". Un gigaciclo es simplemente mil millones de ciclos de CPU en una CPU típica de un solo núcleo, por lo que un Tokenizer funcionando a "1000 líneas por gigaciclo" debería generar alrededor de 1200 líneas de código tokenizado cuando se ejecuta en un procesador de 1200 MHz.

La primera versión funcional del tokenizador funcionaba a solo 350 LPGC, por lo que tokenizar un módulo grande típico como ExtUtils::MakeMaker tardaba de 10 a 15 segundos. Esta lentitud lo hacía poco práctico para muchos usos.

Por lo tanto, en el analizador actual, hay múltiples capas de optimización muy cuidadosamente integradas en la base. Esto ha llevado el tokenizador a un más razonable LPGC de 1000, a expensas de hacer el código bastante más retorcido.

Haciéndolo más rápido - Clasificación de línea completa

El primer paso en el proceso de optimización fue agregar un nuevo manejador para permitir que varias de las clases más básicas (espacios en blanco, comentarios) pudieran ser analizadas línea por línea. Al inicio de cada línea, se llama a un manejador especial opcional (solo compatible con pocas clases) para verificar si toda la línea puede ser analizada de una sola vez.

Esto se utiliza principalmente para manejar cosas como POD, comentarios, líneas vacías y algunos otros casos especiales menores.

Haciéndolo más rápido - Inlining

La segunda etapa de la optimización implicó la inlining de un pequeño número de métodos críticos que se repetían un número extremadamente alto de veces. El perfilado sugirió que había alrededor de 1.000.000 de llamadas a métodos individuales por gigaciclo, y al reducir estas en dos tercios se obtuvo una mejora significativa de la velocidad, del orden de aproximadamente un 50%.

Es posible que observe que muchos métodos en el código de "PPI::Tokenizer" parecen muy anidados y largos. Esto se debe principalmente a esta inlining.

Alrededor de este tiempo, también se eliminó algo de código de estadísticas que existía en las primeras versiones del analizador, ya que se determinó que consumía alrededor del 15% de la CPU para todo el analizador, mientras complicaba el núcleo.

Se tomó la decisión de que, dadas las dificultades probables con las futuras mejoras planificadas, y dado el costo relativamente alto involucrado, las características estadísticas se eliminarían del Tokenizer.

Haciéndolo más rápido - Motor de Comillas

Una vez que la inlining alcanzó rendimientos decrecientes, se hizo obvio a partir de los resultados del perfilado que se estaba gastando una gran cantidad de tiempo recorriendo carácter por carácter un código largo, simple y "sintácticamente aburrido", como comentarios y cadenas.

El motor de expresiones regulares existente se expandió para abarcar también comillas y otras cosas similares a comillas, y se agregó una clase base abstracta especial que proporcionaba una serie de métodos de análisis especializados que "escaneaban hacia adelante", buscando el final de una cadena y actualizando el cursor para dejarlo en una posición válida para la siguiente llamada.

Este es también el punto en el que el número de llamadas al manejador de caracteres comenzó a diferir en gran medida del número de caracteres. Pero se ha hecho de manera que permite al analizador conservar el poder de la versión original en los puntos críticos, mientras salta a través de los "trozos aburridos" según sea necesario para obtener velocidad adicional.

La adición de esta característica permitió que el tokenizador superara los 1000 LPGC por primera vez.

Haciéndolo más rápido - El Mecanismo de "Completado"

A medida que se hizo evidente que se podían obtener grandes aumentos de velocidad utilizando este mecanismo de "salto hacia adelante", se agregó un nuevo método manejador que maneja explícitamente el análisis de un token completo, donde la estructura del token es relativamente simple. Tokens como los símbolos encajan en este caso, ya que una vez que pasamos el sigilo inicial y el carácter de palabra, sabemos que podemos saltar hacia adelante y "completar" el resto del token con mucha más facilidad.

Se han agregado varios de estos para la mayoría o posiblemente todos los casos comunes, con la mayoría de estos manejadores de "completado" implementados utilizando expresiones regulares.

De hecho, se han agregado tantos que en este punto, se podría reclasificar argumentablemente el tokenizador como un "tokenizador híbrido de expresiones regulares, carácter por carácter, heurístico". Ahora se consumen más tokens en métodos de "completado" en un programa típico que los manejados por los métodos normales carácter por carácter.

Muchos de estos manejadores de completado se implementaron durante la escritura del Lexer, y esto ha permitido que el analizador completo mantenga aproximadamente 1000 LPGC a pesar del creciente peso del Lexer.

Haciéndolo más rápido - Portado a C (En progreso)

Aunque sería extraordinariamente difícil portar todo el Tokenizer a C, se ha comenzado a trabajar en un paquete de "acelerador" PPI::XS que actúa como un complemento separado y detectado automáticamente al paquete principal de PPI.

PPI::XS implementa versiones más rápidas de una variedad de funciones dispersas por toda la base de código de PPI, desde el Núcleo del Tokenizer, el Motor de Comillas y varios otros lugares, y las implementa de manera idéntica en XS/C.

En particular, los métodos de salto anticipado del Motor de Comillas parecen ser extremadamente adecuados para ser implementados en C, y varias otras funciones podrían ser seleccionadas una por una e implementadas en C.

Cada método se prueba exhaustivamente para garantizar que la funcionalidad sea idéntica, y se incluye un mecanismo de versionado para garantizar que si una función se desincroniza, PPI::XS degradará graciosamente y simplemente no reemplazará ese único método.
