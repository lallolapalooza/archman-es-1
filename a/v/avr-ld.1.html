LD(1) Herramientas de desarrollo GNU LD(1)

NOMBRE

ld - El enlazador de GNU

SINOPSIS

ld [opciones] archivo_objeto ...

DESCRIPCIÓN

ld combina un número de archivos de objetos y de archivos de biblioteca, reubica sus datos y resuelve las referencias a símbolos. Usualmente, el último paso en la compilación de un programa es ejecutar ld.

ld acepta archivos escritos en el Lenguaje de Comandos de Enlazado, que es una extensión de la sintaxis del Lenguaje de Comandos del Editor de Enlaces de AT&T, para proporcionar un control explícito y total sobre el proceso de enlazado.

Esta página del manual no describe el lenguaje de comandos; véase la entrada de ld en "info" para más detalles sobre el lenguaje de comandos y sobre otros aspectos del enlazador de GNU.

Esta versión de ld usa las bibliotecas BFD de propósito general para operar con archivos de objetos. Esto permite a ld leer, combinar y escribir archivos de objetos en muchos formatos diferentes, por ejemplo, COFF o "a.out". Diferentes formatos pueden ser enlazados juntos para producir cualquier tipo de archivo de objeto disponible.

Además de su flexibilidad, el enlazador de GNU es más útil que otros enlazadores a la hora de proporcionar información de diagnóstico. Muchos enlazadores abandonan la ejecución inmediatamente al encontrar un error; siempre que sea posible, ld continúa la ejecución, permitiéndote identificar otros errores (o, en algunos casos, obtener un archivo de salida a pesar del error).

El enlazador de GNU ld está diseñado para cubrir una amplia gama de situaciones y ser lo más compatible posible con otros enlazadores. Como resultado, tienes muchas opciones para controlar su comportamiento.

OPCIONES

El enlazador admite una gran cantidad de opciones de línea de comandos, pero en la práctica real se usan pocas en un contexto particular. Por ejemplo, un uso frecuente de ld es enlazar archivos de objetos Unix estándar en un sistema Unix estándar y compatible. En un sistema así, para enlazar un archivo "hello.o":

ld -o <salida> /lib/crt0.o hello.o -lc

Esto le dice a ld que produzca un archivo llamado salida como el resultado de enlazar el archivo "/lib/crt0.o" con "hello.o" y la biblioteca "libc.a", que vendrá de los directorios de búsqueda estándar. (Véase la discusión de la opción -l más abajo.)

Algunas de las opciones de línea de comandos de ld pueden especificarse en cualquier punto de la línea de comandos. Sin embargo, las opciones que se refieren a archivos, como -l o -T, hacen que el archivo se lea en el punto en el que aparece la opción en la línea de comandos, en relación con los archivos de objetos y otras opciones de archivo. Repetir opciones que no son de archivo con un argumento diferente no tendrá más efecto, o anulará las apariciones previas (aquellas más a la izquierda en la línea de comandos) de esa opción. Las opciones que pueden especificarse significativamente más de una vez se anotan en las descripciones más abajo.

Los argumentos que no son opciones son archivos de objetos o archivos de biblioteca que deben ser enlazados juntos. Pueden seguir, preceder o mezclarse con las opciones de la línea de comandos, excepto que un argumento de archivo de objeto no puede colocarse entre una opción y su argumento.

Usualmente, el enlazador se invoca con al menos un archivo de objeto, pero puedes especificar otras formas de archivos de entrada binarios usando -l, -Ry el lenguaje de comandos de scripts. Si no se especifican archivos de entrada binarios en absoluto, el enlazador no produce ninguna salida y emite el mensaje No hay archivos de entrada.

Si el enlazador no puede reconocer el formato de un archivo de objeto, asumirá que es un script de enlazado. Un script especificado de esta manera aumenta el script de enlazado principal utilizado para el enlazado (ya sea el script de enlazado predeterminado o el especificado usando -T). Esta característica permite al enlazador enlazar contra un archivo que parece ser un objeto o una biblioteca, pero que en realidad solo define algunos valores de símbolos, o usa "INPUT" o "GROUP" para cargar otros objetos. Especificar un script de esta manera solo aumenta el script de enlazado principal, con los comandos extra colocados después del script principal; usa la opción -T para reemplazar por completo el script de enlazado predeterminado, pero ten en cuenta el efecto del comando "INSERT" .

Para las opciones cuyos nombres son una sola letra, los argumentos de la opción deben seguir la letra de la opción sin espacio en blanco intermedio, o darse como argumentos separados inmediatamente después de la opción que los requiere.

Para las opciones cuyos nombres tienen varias letras, puede preceder al nombre de la opción un solo guion o dos; por ejemplo, -trace-symbol y --trace-symbol son equivalentes. Nótese que hay una excepción a esta regla. Las opciones de múltiples letras que comienzan con una 'o' en minúscula solo pueden ir precedidas por dos guiones. Esto es para reducir la confusión con la opción -o . Así que, por ejemplo, -omagic establece el nombre del archivo de salida a magic mientras que --omagic establece el indicador NMAGIC en la salida.

Los argumentos de las opciones de múltiples letras deben estar separados del nombre de la opción por un signo igual, o darse como argumentos separados inmediatamente después de la opción que los requiere. Por ejemplo, --trace-symbol foo y --trace-symbol=foo son equivalentes. Se aceptan abreviaturas únicas de los nombres de las opciones de múltiples letras.

Nótese que si el enlazador se invoca indirectamente, a través de un controlador de compilador (por ejemplo, gcc), entonces todas las opciones de línea de comandos del enlazador deben ir precedidas por -Wl, (o lo que sea apropiado para el controlador de compilador particular), así:

gcc -Wl,--start-group foo.o bar.o -Wl,--end-group

Esto es importante, porque de lo contrario el programa controlador del compilador puede descartar silenciosamente las opciones del enlazador, resultando en un enlazado incorrecto. También puede surgir confusión al pasar opciones que requieren valores a través de un controlador, ya que el uso de un espacio entre la opción y el argumento actúa como un separador y hace que el controlador pase solo la opción al enlazador y el argumento al compilador. En este caso, es más sencillo usar las formas unidas de las opciones de una sola y de múltiples letras, como:

gcc foo.o bar.o -Wl,-eENTRY -Wl,-Map=a.map

Las razones para permitir referencias a símbolos indefinidos en bibliotecas compartidas especificadas en el momento del enlace son que:

  • Una biblioteca compartida especificada en el momento del enlace puede no ser la misma que la que está disponible en el momento de la carga, por lo que el símbolo podría ser resoluble en el momento de la carga.

-rpath-link=directories
This option is used to provide the linker with a list of directories to search for shared libraries. When doing a non-shared, non-relocatable link, it will automatically try to locate the required shared library and include it in the link, if it is not included explicitly. In such a case, several directories are searched as described below. The -rpath-link option specifies the first set of directories to search. This option may specify a sequence of directory names either by providing a list of names separated by colons, or by appearing multiple times.

The tokens $ORIGIN and $LIB can appear in these search directories. They will be replaced by the full path to the directory containing the program or shared object in the case of $ORIGIN and either lib - for 32-bit binaries - or lib64 - for 64-bit binaries - in the case of $LIB.

The alternative form of these tokens - ${ORIGIN} and ${LIB} can also be used. The token $PLATFORM is not supported.

The --rpath-link option should be used with caution as it overrides the search path that may have been hard compiled into a shared library. In such a case it is possible to unintentionally use a different search path than the runtime linker would have used.

When additional shared libraries are required, the linker will search directories in the order listed below in order to find them. Note however that this only applies to additional libraries needed to satisfy already included shared libraries. It does not apply to libraries that are included via the -l command line option. Searches for -l libraries are only conducted in directories specified by the -L option.

1.
Any directories specified by -rpath-link options.
2.
Any directories specified by -rpath options. The difference between -rpath and -rpath-link is that directories specified by -rpath options are included in the executable and used at runtime, whereas the -rpath-link option is only effective at link time. Searching -rpath in this way is only supported by native linkers and cross linkers which have been configured with the --with-sysroot option.
3.
On an ELF system, for native linkers, if the -rpath and -rpath-link options were not used, search the contents of the environment variable "LD_RUN_PATH".
4.
On SunOS, if the -rpath option was not used, search any directories specified using -L options.
5.
For a native linker, search the contents of the environment variable "LD_LIBRARY_PATH".
6.
For a native ELF linker, the directories in "DT_RUNPATH" or "DT_RPATH" of a shared library are searched for shared libraries needed by it. The "DT_RPATH" entries are ignored if "DT_RUNPATH" entries exist.
7.
For a linker for a Linux system, if the file /etc/ld.so.conf exists, the list of directories found in that file. Note: the path to this file is prefixed with the "sysroot" value, if that is defined, and then any "prefix" string if the linker was configured with the --prefix=<path> option.
8.
For a native linker on a FreeBSD system, any directories specified by the "_PATH_ELF_HINTS" macro defined in the elf-hints.h header file.
9.
Any directories specified by a "SEARCH_DIR" command in a linker script given on the command line, including scripts specified by -T (but not -dT).
10.
The default directories, normally /lib and /usr/lib.
11.
Any directories specified by a plugin LDPT_SET_EXTRA_LIBRARY_PATH.
12.
Any directories specified by a "SEARCH_DIR" command in a default linker script.

If the required shared library is not found, the linker will issue a warning and continue with the link.

--section-ordering-file=script
This option is used to augment the current linker script with additional mapping of input sections to output sections. This file must use the same syntax for "SECTIONS" as is used in normal linker scripts, but it should not do anything other than place input sections into output sections. @pxref{SECTIONS}

A second constraint on the section ordering script is that it can only reference output sections that are already defined by whichever linker script is currently in use. (Ie the default linker script or a script specified on the command line). The benefit of the section ordering script however is that the input sections are mapped to the start of the output sections, so that they can ensure the ordering of sections in the output section. For example, imagine that the default linker script looks like this:

SECTIONS {
  .text : { *(.text.hot) ; *(.text .text.*) }
  .data : { *(.data.big) ; *(.data .data.*) }
  }

Then if a section ordering file like this is used:

.text : { *(.text.first) ; *(.text.z*) }
.data : { foo.o(.data.first) ; *(.data.small) }

This would be equivalent to a linker script like this:

SECTIONS {
  .text : { *(.text.first) ; *(.text.z*) ; *(.text.hot) ; *(.text .text.*) }
  .data : { foo.o(.data.first) ; *(.data.small) ; *(.data.big) ; *(.data .data.*) }
  }

The advantage of the section ordering file is that it can be used to order those sections that matter to the user without having to worry about any other sections, or memory regions, or anything else.

Por lo tanto, en programas grandes, a menudo es necesario utilizar múltiples valores de puntero global para poder direccionar todas las constantes posibles. Esta opción genera una advertencia siempre que ocurre este caso.

--wrap=simbolo
Utiliza una función envoltorio para simbolo. Cualquier referencia no definida a simbolo se resolverá a "__wrap_simbolo". Cualquier referencia no definida a "__real_simbolo" se resolverá a simbolo.

Esto se puede usar para proporcionar un envoltorio para una función del sistema. La función envoltorio debe llamarse "__wrap_simbolo". Si desea llamar a la función del sistema, debe llamar a "__real_simbolo".

Aquí hay un ejemplo trivial:

void *
__wrap_malloc (size_t c)
{
  printf ("malloc llamado con %zu\n", c);
  return __real_malloc (c);
}

Si enlaza otro código con este archivo usando --wrap malloc, entonces todas las llamadas a "malloc" llamarán a la función "__wrap_malloc" en su lugar. La llamada a "__real_malloc" en "__wrap_malloc" llamará a la función "malloc" real.

Es posible que desee proporcionar también una función "__real_malloc", para que los enlaces sin la opción --wrap tengan éxito. Si hace esto, no debe colocar la definición de "__real_malloc" en el mismo archivo que "__wrap_malloc"; si lo hace, el ensamblador puede resolver la llamada antes de que el enlazador tenga la oportunidad de envolverla a "malloc".

Solo las referencias no definidas son reemplazadas por el enlazador. Por lo tanto, las referencias internas de la unidad de traducción a simbolo no se resuelven a "__wrap_simbolo". En el siguiente ejemplo, la llamada a "f" en "g" no se resuelve a "__wrap_f".

int
f (void)
{
  return 123;
}

int
g (void)
{
  return f();
}

Nota: el uso de la extensión 'auto-import' también hará que los datos de solo lectura que normalmente se colocarían en la sección .rdata se coloquen en la sección .data en su lugar. Esto es para solucionar un problema con las constantes que se describe aquí: http://www.cygwin.com/ml/cygwin/2004-09/msg01101.html

Usar 'auto-import' generalmente 'funcionará sin problemas' -- pero a veces puedes ver este mensaje:

"variable '<var>' can't be auto-imported. Please read the documentation for ld's "--enable-auto-import" for details."

Este mensaje ocurre cuando alguna (sub)expresión accede a una dirección dada finalmente por la suma de dos constantes (las tablas de importación de Win32 solo permiten una). Los casos en los que esto puede ocurrir incluyen accesos a campos miembro de variables de struct importadas de una DLL, así como el uso de un índice constante en una variable de array importada de una DLL. Cualquier variable de múltiples palabras (arrays, structs, long long, etc.) puede desencadenar esta condición de error. Sin embargo, independientemente del tipo de datos exacto de la variable exportada problemática, ld siempre la detectará, emitirá la advertencia y saldrá.

Hay varias formas de abordar esta dificultad, independientemente del tipo de datos de la variable exportada:

Una forma es usar la opción --enable-runtime-pseudo-reloc. Esto deja la tarea de ajustar las referencias en tu código cliente para el entorno de ejecución, por lo que este método solo funciona cuando el entorno de ejecución admite esta característica.

Una segunda solución es forzar que una de las 'constantes' sea una variable -- es decir, desconocida y no optimizable en tiempo de compilación. Para los arrays, hay dos posibilidades: a) hacer que el índice (la dirección del array) sea una variable, o b) hacer que el índice 'constante' sea una variable. Así:

extern type extern_array[];
extern_array[1] -->
   { volatile type *t=extern_array; t[1] }

o

extern type extern_array[];
extern_array[1] -->
   { volatile int t=1; extern_array[t] }

Para los structs (y la mayoría de los otros tipos de datos de múltiples palabras), la única opción es hacer que el struct en sí (o el long long, o el ...) sea variable:

extern struct s extern_struct;
extern_struct.field -->
   { volatile struct s *t=& t->field }

o

extern long long extern_ll;
extern_ll -->
  { volatile long long * local_ll=& *local_ll }

Un tercer método para tratar con esta dificultad es abandonar 'auto-import' para el símbolo problemático y marcarlo con "__declspec(dllimport)". Sin embargo, en la práctica eso requiere usar #defines en tiempo de compilación para indicar si estás construyendo una DLL, construyendo código cliente que se enlazará con la DLL, o simplemente construyendo/enlazando con una biblioteca estática. Al elegir entre los varios métodos para resolver el problema de la 'dirección directa con desplazamiento constante', deberías considerar el uso típico del mundo real:

Original:

--foo.h
extern int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  printf("%d\n",arr[1]);
}

Solución 1:

--foo.h
extern int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  /* This workaround is for win32 and cygwin; do not "optimize" */
  volatile int *parr = arr;
  printf("%d\n",parr[1]);
}

Solución 2:

--foo.h
/* Note: auto-export is assumed (no __declspec(dllexport)) */
#if (defined(_WIN32) || defined(__CYGWIN__)) && \
  !(defined(FOO_BUILD_DLL) || defined(FOO_STATIC))
#define FOO_IMPORT __declspec(dllimport)
#else
#define FOO_IMPORT
#endif
extern FOO_IMPORT int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  printf("%d\n",arr[1]);
}

Una cuarta forma de evitar este problema es recodificar tu biblioteca para usar una interfaz funcional en lugar de una interfaz de datos para las variables problemáticas (por ejemplo, set_foo() y get_foo() funciones de acceso).

ENVIRONMENT

You can change the behaviour of ld with the environment variables "GNUTARGET", "LDEMULATION" and "COLLECT_NO_DEMANGLE".

"GNUTARGET" determines the input-file object format if you don't use -b (or its synonym --format). Its value should be one of the BFD names for an input format. If there is no "GNUTARGET" in the environment, ld uses the natural format of the target. If "GNUTARGET" is set to "default" then BFD attempts to discover the input format by examining binary input files; this method often succeeds, but there are potential ambiguities, since there is no method of ensuring that the magic number used to specify object-file formats is unique. However, the configuration procedure for BFD on each system places the conventional format for that system first in the search-list, so ambiguities are resolved in favor of convention.

"LDEMULATION" determines the default emulation if you don't use the -m option. The emulation can affect various aspects of linker behaviour, particularly the default linker script. You can list the available emulations with the --verbose or -V options. If the -m option is not used, and the "LDEMULATION" environment variable is not defined, the default emulation depends upon how the linker was configured.

Normally, the linker will default to demangling symbols. However, if "COLLECT_NO_DEMANGLE" is set in the environment, then it will default to not demangling symbols. This environment variable is used in a similar fashion by the "gcc" linker wrapper program. The default may be overridden by the --demangle and --no-demangle options.
