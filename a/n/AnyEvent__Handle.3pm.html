Pongo "undef" en la referencia de AnyEvent::Handle dentro de mi callback y aún recibo más

Eso es porque AnyEvent::Handle mantiene una referencia a sí mismo cuando manejo callbacks de lectura o escritura.

¿Por qué mi callback "on_eof" nunca se
llama?
Probablemente porque se está llamando a tu callback "on_error" en su lugar: Cuando tienes solicitudes pendientes en tu cola de lectura, un EOF se considera un error, ya que claramente esperabas algunos datos.

Para evitar esto, asegúrate de tener una cola de lectura vacía siempre que tu manejador se supone que está "inactivo" (es decir, los cierres de conexión están bien). Puedes establecer un manejador "on_read" que simplemente empuje las primeras solicitudes de lectura en la

cola.

Ver también la siguiente preg

unta, que explica esto con un
poco más de detalle.
¿Cómo puedo atender solicitudes en un
bucle?
La mayoría de los protocolos consisten en alguna fase de configuración (autenticación, por ejemplo) seguida de una fase de manejo de solicitudes, donde el servidor espera solicitudes y las atiende, en un bucle.

Hay dos variantes importantes: La primera (tradicional, mejor) variante atiende solicitudes hasta que el servidor recibe algún comando QUIT, lo que le hace cerrar la conexión primero (altamente deseable para un servidor TCP ocupado). Que un cliente corte la conexión es un error, lo que significa que esta variante puede detectar un cierre

inesperado.

Para manejar este caso, asegúrate siempre de tener una cola de lectura no vacía, empujando el manejador "read request start" en

ella: 
# asumimos que una solicitud comienza con una sola línea
my @start_request; @start_request = (line => sub {
   my ($hdl, $line) = @_;
   ... manejar solicitud
   # empujar la siguiente lectura de solicitud, posiblemente desde un callback anidado
   $hdl->push_read (@start_request);
});
# autenticación completada, ahora entrar en el bucle de manejo de solicitudes
# ahora empujar el primer @start_request
$hdl->push_read (@start_request)
;

Al tener siempre un "push_read" pendiente, el manejador siempre espera algunos datos y lanza el error "EPIPE" cuando la conexión se corta

inesperadamente.

La segunda variante es un protocolo donde el cliente puede cortar la conexión en cualquier momento. Para TCP, esto significa que la máquina del servidor puede quedarse sin sockets más fácilmente, y en general, significa que no puedes distinguir un fallo de protocolo/caída del cliente de un cierre normal de conexión. No obstante, este tipo de protocolos son comunes (y a veces incluso la mejor solución al

problema).

Tener una solicitud de lectura pendiente en todo momento es posible si ignoras los errores "EPIPE", pero esto no ayuda con cuando el cliente corta la conexión durante una solicitud, lo que seguiría siendo un

error.

Una mejor solución es empujar la lectura inicial de la solicitud en un callback "on_read". Esto evita un error, ya que cuando el servidor no espera datos (es decir, está esperando inactivamente la siguiente solicitud, un EOF no lanzará un error, sino que simplemente resultará en un callback "on_eof". También es un poco más lento y

más simple: 
# autenticación completada, ahora entrar en el bucle de manejo de solicitudes
$hdl->on_read (sub {
   my ($hdl) = @_;
   # llamado cada vez que recibimos datos pero la cola de lectura está vacía
   # simplemente comenzar a leer la solicitud
   $hdl->push_read (line => sub {
      my ($hdl, $line) = @_;
      ... manejar solicitud
      # no hacer nada especial cuando la solicitud ha sido atendida, simplemente
      # dejar que la cola de solicitudes quede vacía.
});
});
Obtengo invocaciones de callback diferentes en modo TLS/¿Por qué no puedo pausar la
lectura?
A diferencia de, digamos, TCP, las conexiones TLS no consisten en dos canales de comunicación independientes, uno para cada dirección. O dicho de otra manera, las direcciones de lectura y escritura no son independientes una de otra: no puedes escribir datos a menos que también estés preparado para leer, y viceversa.

Esto significa que, en modo TLS, podrías obtener invocaciones de callback "on_error" o "on_eof" cuando no esperas ningún dato de lectura - la razón es que AnyEvent::Handle siempre lee en modo

TLS.

Durante la conexión, tienes que asegurarte de que siempre tengas una cola de lectura no vacía, o un observador "on_read". Al final de la conexión (o cuando ya no quieras usarla) puedes llamar al método "

destr
oy".
¿Cómo leo datos hasta que el otro lado cierra la
conexión?
Si solo quieres leer tus datos en un escalar de perl, la forma más fácil de lograr esto es estableciendo un callback "on_read" que no hace nada, limpiando el callback "on_eof" y en el callback "on_error", los datos estarán en "$_[0]{rbuf}": 
$handle->on_read (sub { });
$handle->on_eof (undef);
$handle->on_error (sub {
   my $data = delete $_[0]{rbuf}
; });

Ten en cuenta que este ejemplo elimina el miembro "rbuf" del objeto manejador, lo que normalmente no está permitido por la API. Se permite expresamente en este caso solo, ya que el objeto manejador necesita ser destruido

después.

La razón para usar "on_error" es que las conexiones TCP, debido a latencias y pérdida de paquetes, podrían cerrarse de manera bastante violenta con un error, cuando de hecho todos los datos han sido

recibidos.

Usualmente es mejor usar acuses de recibo al transferir datos, para asegurarte de que el

otro lado no ha muerto simplemente y que has recibido los datos intactos. Esta es tamb
ién una razón por la que tantos protocolos de internet tienen un comando QUIT explícito.
No quiero destruir el manejador demasiado pronto - ¿cómo espero hasta que todos los datos hayan sido
escritos?
Después de escribir tus últimos bits de datos, establece el callback "on_drain" y destruye el manejador ahí - con la configuración predeterminada de "low_water_mark" esto será llamado precisamente cuando todos los datos hayan sido escritos en el socket: 
$handle->push_write (...);
$handle->on_drain (sub {
   AE::log debug => "Todos los datos enviados al kernel.";
   undef $handle;
});

Si solo quieres encolar algunos datos y luego señalizar EOF al otro lado, considera usar "->push_shutdow

n" en s
u lugar.
Quiero contactar a un servidor TLS/SSL, no me importa la
seguridad.
Si tu servidor TLS es un servidor TLS puro (por ejemplo, HTTPS) que solo habla TLS, conéctate a él y luego crea el AnyEvent::Handle con el parámetro "tls": 
tcp_connect $host, $port, sub {
   my ($fh) = @_;
   my $handle = new AnyEvent::Handle
      fh  => $fh,
      tls => "connect",
      on_error => sub { ... };
   $handle->push_write (..
.);
};
Quiero contactar a un servidor TLS/SSL, sí me importa la
seguridad.
Entonces deberías además habilitar la verificación de certificados, incluyendo la verificación del nombre del par, si el protocolo que usas lo soporta (ver AnyEvent::TLS, "verify_peername").

para HTTPS:

   my ($fh) = @_;

del par.

tls_ctx  => {

Quiero crear un servidor TLS/SSL, ¿cómo hago

Bueno, primero necesitas conseguir un certificado y clave de servidor.
