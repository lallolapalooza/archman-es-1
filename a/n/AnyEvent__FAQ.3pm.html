AnyEvent::FAQ - preguntas frecuentes

Preguntas frecuentes

La versión más reciente de este documento se puede encontrar en http://pod.tst.eu/http://cvs.schmorp.de/AnyEvent/lib/AnyEvent/FAQ.pod.

Mi programa termina antes de hacer nada, ¿qué está pasando?

A los programadores nuevos en la programación basada en eventos a menudo se les olvida que en realidad pueden hacer otras cosas mientras "esperan" a que ocurra un evento y por lo tanto olvidan esperar realmente cuando, de hecho, no tienen nada más que hacer.

Aquí hay un ejemplo:

use AnyEvent;
my $timer = AnyEvent->timer (after => 5, cb => sub { say "hi" });

La expectativa podría ser que el programa imprima "hi" después de 5 segundos y probablemente termine. Sin embargo, si ejecuta esto, su programa terminará casi instantáneamente: crear el temporizador no espera a que termine, en su lugar el "timer" método devuelve inmediatamente y perl ejecuta el resto del programa. Pero no queda nada por ejecutar, así que perl termina.

Para forzar a AnyEvent a esperar algo, use una condvar:

use AnyEvent;
my $quit_program = AnyEvent->condvar;
my $timer = AnyEvent->timer (after => 5, cb => sub { $quit_program->send });
$quit_program->recv;

Aquí el programa no termina inmediatamente, porque primero espera la condición "quit_program".

En la mayoría de los casos, su programa principal debería llamar directamente a la función "loop" de la biblioteca de eventos:

use EV;
use AnyEvent;
...
EV::loop;

¿Por qué mi callback "tcp_connect" nunca se llama?

Tricky: "tcp_connect" (y algunas otras funciones en AnyEvent::Socket) es críticamente sensible al contexto del llamador.

En contexto void, simplemente hará su trabajo y eventualmente llamará al callback. En cualquier otro contexto, sin embargo, devolverá un objeto "guard" especial: cuando se destruya (por ejemplo, cuando no lo almacene sino que lo descarte), tcp_connect ya no intentará conectarse ni llamará a ningún callback.

A menudo esto sucede cuando la "tcp_connect" llamada está al final de una función:

sub do_connect {
   tcp_connect "www.example.com", 80, sub {
      ... código extenso
   };
}

Entonces el llamador decide si hay un contexto void o no. Se pueden evitar estos casos devolviendo explícitamente nada:

sub do_connect {
   tcp_connect "www.example.com", 80, sub {
      ... código extenso
   };
   () # devolver nada
}

¿Por qué algunos backends usan mucho CPU en "AE::cv->recv"?

Muchas personas prueban este simple programa, o su equivalente:

use AnyEvent;
AnyEvent->condvar->recv;

Luego se sorprenden al ver que esto básicamente está inactivo con el backend Perl, pero usa 100% de CPU con el backend EV, que se supone que es tan eficiente.

La clave para entender esto es entender que el programa anterior es en realidad defectuoso: Nada llama a "->send" en la condvar, nunca. Peor aún, no hay observadores de eventos en absoluto. Básicamente, crea un deadlock: no hay manera de avanzar, este programa no hace nada útil, y esto no cambiará en el futuro: ya es un ex-loro.

Algunos backends reaccionan a esto congelándose, algunos inactivos, y algunos hacen un bucle de 100% CPU.

Dado que este programa no es útil (y se comporta como está documentado con todos los backends, ya que AnyEvent no hace garantías sobre el tiempo de CPU), esto no debería ser un gran problema: tan pronto como su programa realmente implemente algo, el uso de CPU será normal.

¿Por qué este FAQ no trata preguntas sobre AnyEvent::Handle?

Porque AnyEvent::Handle tiene un NONFAQ propio que ya trata problemas comunes.

¿Cómo puedo combinar aplicaciones Win32::GUI con AnyEvent?

Bueno, no en el mismo hilo del SO, eso está seguro :) Lo que puede hacer es crear otro ithread (o fork) y ejecutar AnyEvent dentro de ese hilo, o mejor aún, ejecutar todo su código GUI en un segundo ithread.

Por ejemplo, podría cargar Win32::GUI y AnyEvent::Util, luego crear un socketpair portátil para la comunicación GUI->AnyEvent.

Luego fork/crear un nuevo ithread, ahí dentro, crear una ventana y enviar el "$WINDOW->{-Handle}" al ithread de AnyEvent para que pueda "PostMessage".

La comunicación de GUI a AnyEvent podría funcionar empujando algunos datos a un Thread::Queue y escribiendo un byte en el socket. El observador de AnyEvent en el otro lado luego mirará la cola.

La comunicación de AnyEvent a GUI también puede usar un Thread::Queue, pero para despertar el hilo GUI, usaría en su lugar "Win32::GUI::PostMessage $WINDOW, 1030, 0, """, y el hilo GUI escucharía estos mensajes usando "$WINDOW->Hook (1030 (), sub { ... })".

Mi callback muere y...

No debe - parte del contrato entre AnyEvent y el código del usuario es que los callbacks no lanzan excecciones (y no hacen cosas aún más malvadas, como usar "last" fuera de un bucle :). Si su callback puede morir a veces, necesita usar "eval".

Si desea rastrear un caso así y puede reproducirlo, puede habilitar el envoltorio (llamando a "AnyEvent::Debug::wrap" o configurando "PERL_ANYEVENT_DEBUG_WRAP=1" antes de iniciar su programa). Esto envolverá cada callback en un eval y reportará cualquier excepción completa con un backtrace y algo de información sobre qué observador murió, dónde fue creado, etc.
