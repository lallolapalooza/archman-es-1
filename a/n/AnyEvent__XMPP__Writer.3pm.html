XMPP est de toute façon fondamentalement cassé. Il est censé être un sous-ensemble de XML. Mais un sous-ensemble des productions XML n'est pas du XML. À strictement parler, vous avez besoin d'un analyseur et d'un écrivain "XML" spécial pour XMPP pour

Et un analyseur devrait échouer avec une erreur. Mais XMPP ne s'en soucie pas, il se fie simplement au comportement dépendant de l'implémentation des modes d'analyse par morceaux pour l'analyse SAX. Cette fonctionnalité n'est même pas spécifiée par la recommandation XML d'aucune manière. La recommandation dit même que c'est indéfini ce qui se passe si

vous

traitez des documents XML non bien formés. Mais j'essaie d'être aussi conforme que possible au "XML" de XMPP (cela devrait être autour de 99-100%). Mais il est difficile de dire ce qui est conforme en XML, car les spécifications du "XML" de XMPP et du XML se contredisent. Par exemple, XMPP dit aussi que vous n'avez qu'à générer et accepter les encodages UTF-8 du XML, mais la recommandation XML dit que chaque analyseur doit accepter UTF-8 et UTF-16. Alors, que faites-vous ?

Utilisez-vous

un analyseur conforme au XML ou en écrivez-vous un vous-même ? J'utilise XML::Parser::Expat car expat sait comment analyser les documents "XML" cassés (alias 'partiels'), comme XMPP l'exige. Un autre argument est que si vous capturez une conversation XMPP jusqu'à la fin, et même si une balise '</stream:stream>' a été capturée, vous n'aurez pas un document XML valide. Le problème est que vous devez renvoyer une balise <stream>

après

chaque authentification TLS et SASL ! Awww... je me répète. Mais bon... AnyEvent::XMPP fait de son mieux avec expat pour

De retour au problème de la génération de "XML" : j'ai découvert que de nombreux serveurs XMPP (par ex. jabberd14 et ejabberd) ont des problèmes avec les espaces de noms XML. C'est la raison pour laquelle j'attribue manuellement les préfixes d'espace de noms : les serveurs n'acceptent tout simplement pas du XML avec des espaces de noms valides. Le

projet

3921bis indique même qu'un client DEVRAIT générer un préfixe 'stream' pour la balise <stream>. Je vous conseille de définir explicitement les espaces de noms aussi si vous générez du "XML" pour XMPP vous-même, au moins jusqu'à ce

send_presence ($id, $type, $create_cb, %attrs
)
Envía una estanza de presencia.

$create_cb tiene el mismo significado que para "send_iq". %attrs le permitirá pasar argumentos opcionales adicionales como

'to'.

$type es el tipo de la presencia, que puede ser uno de los

O undef, en caso de que desee enviar una presencia 'normal'. O algo completamente diferente si no le gusta la RFC 3921

%attrs contiene atributos adicionales para la etiqueta de presencia o puede contener una de las siguientes claves

excepcionales:

Si %attrs contiene una clave 'show': se generará una etiqueta xml secundaria con ese nombre y el valor como contenido, que debe ser uno de 'away', 'chat', 'dnd' y 'xa'. Si contiene un valor indefinido, no se generará tal etiqueta, lo que generalmente significa que se refiere a la presencia

'available'.

Si %attrs contiene una clave 'status': se generará una etiqueta xml secundaria con ese nombre y el valor como contenido. Si el valor de la clave 'status' es una referencia a un hash, las claves se interpretarán como identificadores de idioma para el atributo xml:lang de cada elemento de estado. Si alguna de estas claves es la cadena vacía '', no se generará ningún atributo xml:lang para ella. Los valores serán el contenido de caracteres de las etiquetas de

estado.

Si %attrs contiene una clave 'priority': se generará una etiqueta xml secundaria con ese nombre y el valor como contenido, que debe ser un número entre -128 y

+127.

Nota: Si $create_cb es indefinido y se proporcionaron uno de los atributos anteriores (show, status o priority), la etiqueta de presencia generada no estará

vacía.

Tenga en cuenta que todos los valores de atributos y datos de caracteres serán filtrados por "filter_xml_chars" (véase también AnyEvent::XMPP::

Util)
.
