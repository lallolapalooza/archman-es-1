DESCRIPCIÓ

N

Este módulo contiene algunas funciones auxiliares para escribir "XML" de XMPP, que en realidad no es XML en absoluto ;-( Uso XML::Writer y lo ajusto hasta que crea "XML" que es aceptado por la mayoría de los servidores probablemente (todos los servidores XMPP que probé deberían funcionar (jabberd14, jabberd2, ejabberd, googletalk)

.

Espero que la semántica de XML::Writer no cambie mucho en el futuro, pero si lo hace y encuentras problemas, ¡por favor

repórtalos!

El concepto completo de "XML" de XMPP está fundamentalmente roto de todos modos. Se supone que debe ser un subconjunto de XML. Pero un subconjunto de producciones de XML no es XML. Estrictamente hablando, necesitas un analizador y escritor de "XML" especial para XMPP para ser 100%

conforme.

Además, XMPP requiere que analices estos documentos "XML" parciales. Pero un documento XML parcial no está bien formado, ¡vaya, ni siquiera es un documento XML! Y un analizador debería abortar con un error. Pero XMPP no se preocupa, simplemente se basa en el comportamiento dependiente de la implementación de los modos de análisis por trozos para el análisis SAX. Esta funcionalidad ni siquiera está especificada por la recomendación XML de ninguna manera. La recomendación incluso dice que es indefinido qué sucede si procesas documentos XML mal

formados.

Pero intento ser lo más conforme posible con el "XML" de XMPP (debería estar alrededor del 99-100%). Pero es difícil decir qué XML es conforme, ya que las especificaciones de "XML" de XMPP y XML se contradicen. Por ejemplo, XMPP también dice que solo tienes que generar y aceptar codificaciones UTF-8 de XML, pero la recomendación XML dice que cada analizador tiene que aceptar UTF-8 y UTF-16. Entonces, ¿qué haces? ¿Usas un analizador conforme a XML o escribes el tuyo

propio?

Estoy usando XML::Parser::Expat porque expat sabe cómo analizar documentos "XML" rotos (también conocidos como 'parciales'), como lo requiere XMPP. Otro argumento es que si capturas una conversación de XMPP hasta el final, e incluso si se capturó una etiqueta '</stream:stream>', no tendrás un documento XML válido. El problema es que tienes que reenviar una etiqueta <stream> después de cada autenticación TLS y SASL. ¡Aay! Me estoy

repitiendo.

Pero bueno... AnyEvent::XMPP hace lo mejor que puede con expat para lidiar con la rotura fundamental del "XML" en

XMPP.

Volviendo al problema de la generación de "XML": He descubierto que muchos servidores XMPP (por ejemplo, jabberd14 y ejabberd) tienen problemas con los espacios de nombres XML. Esa es la razón por la que asigno los prefijos de espacio de nombres manualmente: los servidores simplemente no aceptan XML con espacios de nombres válidos. El borrador 3921bis incluso establece que un cliente DEBERÍA generar un prefijo 'stream' para la etiqueta <stream>

.

Te aconsejo que establezcas explícitamente los espacios de nombres también si generas "XML" para XMPP tú mismo, al menos hasta que todos o la mayoría de los servidores XMPP hayan sido corregidos. Lo cual podría llevar algunos años :-) Y tal vez nunca

suceda.

Y otra nota: Como XMPP requiere que todos los caracteres de entidad predefinidos se escapen en los datos de caracteres, necesitas un escritor de "XML" que escapará

todo: 
RFC 3920 - 11.1. Restricciones:
  datos de caracteres o valores de atributos que contengan caracteres sin escapar
  que correspondan a las entidades predefinidas (Sección 4.6 en ella);
  dichos caracteres DEBEN ser
escapados

Esto significa: Tienes que escapar '>' en los datos de caracteres. No sé si XML::Writer hace eso. Y sinceramente no me importa mucho esto. XMPP está roto por diseño y apenas tengo tiempo de escribir mis propios analizadores y escritores de XML para satisfacer su enfermo gusto por el "XML". (¿Me estoy repitiendo?

)

Estaría contento si finalmente dijeran (en RFC3920):

"XMPP NO ES XML. Es solo similar a XML, y algunas ut
ilidades XML te permiten procesar este tipo de XML.".

send_iq ($id, $type, $create_cb, %attrs
)
Este método envía una estanza IQ de tipo $type (para ser conforme usa solo: 'get', 'set', 'result' y 'error').

Si $create_cb es una referencia a código será llamada con una instancia de XML::Writer como primer argumento, que debe usarse para rellenar la estanza IQ. El XML::Writer está en modo NO SEGURO, por lo que puedes usar con seguridad raw() para escribir

XML.

$create_cb es una referencia a un hash el hash se usará como argumentos clave=>valor para la función "simxml" definida en AnyEvent::XMPP::Util. "simxml" se usará entonces para generar el contenido de la estanza IQ. (Esto es muy conveniente cuando quieres escribir el contenido de las estanzas en el código y no quieres construir un árbol DOM tú mismo.

..).

Si $create_cb es una referencia a un array sus elementos se interpretarán como un único argumento $create_cb (que puede ser una referencia a un hash o una referencia a código) y se ejecutarán

secuencialmente.

Si $create_cb es indefinido se generará una etiqueta

vacía.

$id es el id a dar a esta estanza IQ y es obligatorio en esta

Envía una estanza de presencia.

$create_cb tiene el mismo significado que para "send_iq". %attrs le permitirá pasar argumentos opcionales adicionales como

$type es el tipo de la presencia, que puede ser uno de los

O undef, en caso de que desee enviar una presencia 'normal'. O algo completamente diferente si no le gusta la RFC 3921

%attrs contiene atributos adicionales para la etiqueta de presencia o puede contener una de las siguientes claves

excepcionales:

Si %attrs contiene una clave 'show': se generará una etiqueta xml secundaria con ese nombre y el valor como contenido, que debe ser uno de 'away', 'chat', 'dnd' y 'xa'. Si contiene un valor indefinido, no se generará tal etiqueta, lo que generalmente significa que se refiere a la presencia

'available'.

Si %attrs contiene una clave 'status': se generará una etiqueta xml secundaria con ese nombre y el valor como contenido. Si el valor de la clave 'status' es una referencia a un hash, las claves se interpretarán como identificadores de idioma para el atributo xml:lang de cada elemento de estado. Si alguna de estas claves es la cadena vacía '', no se generará ningún atributo xml:lang para ella. Los valores serán el contenido de caracteres de las etiquetas de

estado.

Si %attrs contiene una clave 'priority': se generará una etiqueta xml secundaria con ese nombre y el valor como contenido, que debe ser un número entre -128 y

+127.

Nota: Si $create_cb es indefinido y se proporcionaron uno de los atributos anteriores (show, status o priority), la etiqueta de presencia generada no estará

vacía.

Tenga en cuenta que todos los valores de atributos y datos de caracteres serán filtrados por "filter_xml_chars" (véase también AnyEvent::XMPP::

Util)
.
