DESCRIPCIÓ

N

Este módulo de protocolo del kernel implementa el Protocolo de Resolución de Direcciones definido en RFC 826. Se utiliza para convertir entre direcciones de hardware de Capa 2 y direcciones de protocolo IPv4 en redes directamente conectadas. Normalmente, el usuario no interactúa directamente con este módulo excepto para configurarlo; en su lugar, proporciona un servicio para otros protocolos en el

kernel.

Un proceso de usuario puede recibir paquetes ARP utilizando sockets de tipo packet(7). También existe un mecanismo para gestionar la caché ARP en el espacio de usuario utilizando sockets de netlink(7). La tabla ARP también se puede controlar a través de ioctl(2) en cualquier socket AF_

INET.

El módulo ARP mantiene una caché de mapeos entre direcciones de hardware y direcciones de protocolo. La caché tiene un tamaño limitado, por lo que las entradas antiguas y menos utilizadas son recolectadas por el recolector de basura. Las entradas marcadas como permanentes nunca son eliminadas por el recolector de basura. La caché se puede manipular directamente mediante el uso de ioctls y su comportamiento se puede ajustar mediante las interfaces /proc descritas más

abajo.

Cuando no hay retroalimentación positiva para un mapeo existente después de algún tiempo (véanse las interfaces /proc más abajo), una entrada de caché de vecinos se considera obsoleta. La retroalimentación positiva se puede obtener de una capa superior; por ejemplo, de un ACK TCP exitoso. Otros protocolos pueden señalar progreso utilizando el indicador MSG_CONFIRM en sendmsg(2). Cuando no hay progreso, ARP intenta sondear de nuevo. Primero intenta preguntar a un demonio arp local app_solicit veces por una dirección MAC actualizada. Si eso falla y se conoce una dirección MAC antigua, se envía una sonda unicast ucast_solicit veces. Si eso también falla, transmitirá una nueva solicitud ARP a la red. Las solicitudes se envían solo cuando hay datos en cola para

enviar.

Linux añadirá automáticamente una entrada proxy arp no permanente cuando reciba una solicitud para una dirección hacia la que reenvía y el proxy arp esté habilitado en la interfaz receptora. Cuando existe una ruta de rechazo para el destino, no se añade ninguna entrada proxy

arp.

Ioctl

s

Hay tres ioctls disponibles en todos los sockets AF_INET. Toman un puntero a una struct arpreq como su

argumento. 


struct arpreq {
    struct sockaddr arp_pa;      /* dirección de protocolo */
    struct sockaddr arp_ha;      /* dirección de hardware */
    int             arp_flags;   /* indicadores */
    struct sockaddr arp_netmask; /* máscara de red de la dirección de protocolo */
    char            arp_dev[16];
}
;

SIOCSARP, SIOCDARP y SIOCGARP establecen, eliminan y obtienen un mapeo ARP respectivamente. Establecer y eliminar mapeos ARP son operaciones privilegiadas y solo pueden ser realizadas por un proceso con la capacidad CAP_NET_ADMIN o un UID efectivo de

0.

arp_pa debe ser una dirección AF_INET y arp_ha debe tener el mismo tipo que el dispositivo especificado en arp_dev. arp_dev es una cadena terminada en cero que nombra un

dispositivo.

Interfaces

/proc

ARP soporta un rango de interfaces /proc para configurar parámetros de forma global o por interfaz. Las interfaces se pueden acceder leyendo o escribiendo los archivos /proc/sys/net/ipv4/neigh/*/*. Cada interfaz en el sistema tiene su propio directorio en /proc/sys/net/ipv4/neigh/. La configuración en el directorio "default" se utiliza para todos los dispositivos creados. A menos que se especifique lo contrario, las interfaces relacionadas con el tiempo se especifican en

segundos.

VERSIONE

S

El struct arpreq cambió en Linux 2.0 para incluir el miembro arp_dev y los números de ioctl cambiaron al mismo tiempo. El soporte para los ioctl antiguos se eliminó en Linux 2.

2.

Se eliminó el soporte para entradas proxy arp para redes (máscara de red distinta de 0xffffffff) en Linux 2.2. Fue reemplazado por la configuración automática de proxy arp por parte del kernel para todos los hosts alcanzables en otras interfaces (cuando el reenvío y el proxy arp están habilitados para la interfaz)

.

Las interfaces neigh/* no existían

antes de
Linux 2.2.

ERRORE

S

Algunas configuraciones de temporizador se especifican en jiffies, lo que depende de la arquitectura y de la versión del kernel; véase time(

7).

No hay forma de señalar retroalimentación positiva desde el espacio de usuario. Esto significa que los protocolos orientados a la conexión implementados en el espacio de usuario generarán tráfico ARP excesivo, porque ndisc sondeará regularmente la dirección MAC. El mismo problema se aplica a algunos protocolos del kernel (por ejemplo, NFS sobre UDP)
