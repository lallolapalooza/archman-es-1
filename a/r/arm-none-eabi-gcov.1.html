DESCRIPCIÓN

gcov es un programa de cobertura de pruebas. Úsalo en conjunto con GCC para analizar tus programas y ayudar a crear código más eficiente y rápido, y para descubrir partes no probadas de tu programa. Puedes usar gcov como una herramienta de perfilado para ayudar a descubrir dónde tus esfuerzos de optimización tendrán el mayor impacto en tu código. También puedes usar gcov junto con la otra herramienta de perfilado, gprof, para evaluar qué partes de tu código utilizan la mayor cantidad de tiempo de cómputo.

Las herramientas de perfilado te ayudan a analizar el rendimiento de tu código. Usando un perfilador como gcov o gprof, puedes obtener estadísticas básicas de rendimiento, como:

  • con qué frecuencia se ejecuta cada línea de código
  • qué líneas de código se ejecutan realmente
  • cuánto tiempo de cómputo utiliza cada sección de código

Una vez que conoces estos detalles sobre cómo funciona tu código cuando se compila, puedes examinar cada módulo para ver cuáles deberían ser optimizados. gcov te ayuda a determinar en qué trabajar para la optimización.

Los desarrolladores de software también utilizan la prueba de cobertura junto con conjuntos de pruebas (testsuites) para asegurarse de que el software es realmente lo suficientemente bueno para una versión. Los conjuntos de pruebas pueden verificar que un programa funciona como se espera; un programa de cobertura verifica cuánto del programa es ejercitado por el conjunto de pruebas. Luego, los desarrolladores pueden determinar qué tipos de casos de prueba deben agregarse a los conjuntos de pruebas para crear tanto pruebas mejores como un mejor producto final.

Deberías compilar tu código sin optimización si planeas usar gcov, ya que la optimización, al combinar algunas líneas de código en una función, puede no proporcionarte tanta información como necesitas para buscar `puntos calientes' (hot spots) donde el código consume mucho tiempo de cómputo. De manera similar, dado que gcov acumula estadísticas por línea (en la resolución más baja), funciona mejor con un estilo de programación que coloca una sola sentencia por línea. Si utilizas macros complicadas que se expanden a bucles u otras estructuras de control, las estadísticas son menos útiles: solo informan sobre la línea donde aparece la llamada a la macro. Si tus macros complejas se comportan como funciones, puedes reemplazarlas con funciones en línea para resolver este problema.

gcov crea un archivo de registro llamado archivo_fuente.gcov que indica cuántas veces se ha ejecutado cada línea de un archivo fuente archivo_fuente.c. Puedes usar estos archivos de registro junto con gprof para ayudar a ajustar el rendimiento de tus programas. gprof proporciona información de tiempo que puedes usar junto con la información que obtienes de gcov.

gcov solo funciona en código compilado con GCC. No es compatible con ningún otro mecanismo de perfilado o cobertura de pruebas.

OPCIONES

-a
--all-blocks
Escribe recuentos de ejecución individuales para cada bloque básico. Normalmente, gcov genera recuentos de ejecución solo para los bloques principales de una línea. Con esta opción, puedes determinar si los bloques dentro de una sola línea no se están ejecutando.
-b
--branch-probabilities
Escribe las frecuencias de las ramas en el archivo de salida y la información resumen de las ramas en la salida estándar. Esta opción te permite ver con qué frecuencia se tomó cada rama en tu programa. Las ramas incondicionales no se mostrarán, a menos que se proporcione la opción -u.
-c
--branch-counts
Escribe las frecuencias de las ramas como el número de ramas tomadas, en lugar del porcentaje de ramas tomadas.
-g
--conditions
Escribe la cobertura de condiciones en el archivo de salida y la información resumen de condiciones en la salida estándar. Esta opción te permite ver si las condiciones en tu programa, al menos una vez, tuvieron un efecto independiente en el resultado de la expresión booleana (cobertura de condición/decisión modificada). Esto requiere que compiles el código fuente con -fcondition-coverage.
-d
--display-progress
Muestra el progreso en la salida estándar.
-f
--function-summaries
Genera resúmenes para cada función además del resumen a nivel de archivo.
-h
--help
Muestra ayuda sobre el uso de gcov (en la salida estándar) y sale sin realizar ningún procesamiento adicional.
-j
--json-format
Genera el archivo gcov en un formato intermedio JSON fácil de analizar que no requiere código fuente para su generación. El archivo JSON se comprime con el algoritmo de compresión gzip y los archivos tienen la extensión .gcov.json.gz.

    Para cada función, se imprime una línea que muestra cuántas veces se llama a la función, cuántas veces retorna y qué porcentaje de los bloques de la función se ejecutaron.

    Para cada bloque básico, se imprime una línea después de la última línea del bloque básico que describe la rama o llamada que finaliza el bloque básico. Puede haber múltiples ramas y llamadas listadas para una sola línea de código fuente si hay múltiples bloques básicos que terminan en esa línea. En este caso, a cada rama y llamada se le da un número. No hay una forma simple de mapear estas ramas y llamadas de regreso a las construcciones fuente. En general, sin embargo, la rama o llamada de menor número corresponderá a la construcción más a la izquierda en la línea de código fuente.

    Para una rama, si se ejecutó al menos una vez, se imprimirá un porcentaje que indica el número de veces que se tomó la rama dividido por el número de veces que se ejecutó la rama. De lo contrario, se imprimirá el mensaje "never executed".

    Para una llamada, si se ejecutó al menos una vez, se imprimirá un porcentaje que indica el número de veces que la llamada retornó dividido por el número de veces que se ejecutó la llamada. Esto generalmente será 100%, pero puede ser menor para funciones que llaman a "exit" o "longjmp", y por lo tanto pueden no retornar cada vez que se llaman.

    Los recuentos de ejecución son acumulativos. Si el programa de ejemplo se ejecutara nuevamente sin eliminar el archivo .gcda, el recuento del número de veces que se ejecutó cada línea en el código fuente se agregaría a los resultados de la ejecución anterior. Esto es potencialmente útil de varias maneras. Por ejemplo, podría usarse para acumular datos durante un número de ejecuciones de programas como parte de un conjunto de verificación de pruebas, o para proporcionar información a más largo plazo y más precisa durante un gran número de ejecuciones de programas.

    Los datos en los archivos .gcda se guardan inmediatamente antes de que el programa salga. Por cada

    archivo fuente compilado con -fprofile-arcs, el código de perfilado primero intenta leer un archivo .gcda existente; si el archivo no coincide con el ejecutable (número diferente de conteos de bloques básicos) ignorará el contenido del archivo. Luego añade los nuevos conteos de ejecución y finalmente escribe los datos en el

    archivo.

    Usando gcov con la optimización de

    GCC

    Si planea usar gcov para ayudar a optimizar su código, primero debe compilar su programa con una opción especial de GCC --coverage. Aparte de eso, puede usar cualquier otra opción de GCC; pero si quiere demostrar que cada línea de su programa fue ejecutada, no debe compilar con optimización al mismo tiempo. En algunas máquinas, el optimizador puede eliminar algunas líneas de código simples combinándolas con otras líneas. Por ejemplo, código como

    este: 
    if (a != b)
  c = 1;
else
  c =
    0;

    puede ser compilado en una sola instrucción en algunas máquinas. En este caso, no hay forma de que gcov calcule conteos de ejecución separados para cada línea porque no hay código separado para cada línea. Por lo tanto, la salida de gcov se ve así si compiló el programa con

    optimización: 
    100:   12:if (a != b)
100:   13:  c = 1;
100:   14:else
100:   15:  c =
    0;

    La salida muestra que este bloque de código, combinado por la optimización, se ejecutó 100 veces. En cierto sentido este resultado es correcto, porque solo había una instrucción que representaba a estas cuatro líneas. Sin embargo, la salida no indica cuántas veces el resultado fue 0 y cuántas veces el resultado fue

    1.

    Las funciones en línea pueden crear conteos de línea inesperados. Los conteos de línea se muestran para el código fuente de la función en línea, pero lo que se muestra depende de dónde se insertó la función en línea, o si no se insertó en

    absoluto.

    Si la función no se inserta en línea, el compilador debe emitir una copia fuera de línea de la función, en cualquier archivo de objeto que la necesite. Si fileA.o y fileB.o contienen ambos cuerpos fuera de línea de una función en línea particular, también contendrán ambos los conteos de cobertura para esa función. Cuando fileA.o y fileB.o se enlazan juntos, el enlazador, en muchos sistemas, seleccionará uno de esos cuerpos fuera de línea para todas las llamadas a esa función, y eliminará o ignorará el otro. Desafortunadamente, no eliminará los contadores de cobertura para el cuerpo de función no utilizado. Por lo tanto, cuando se instrumenta, todas las usos de esa función excepto uno mostrarán conteos

    cero.

    Si la función se inserta en línea en varios lugares, la estructura de bloques en cada ubicación podría no ser la misma. Por ejemplo, una condición podría ahora ser calculable en tiempo de compilación en algunas instancias. Debido a que la cobertura de todos los usos de la función en línea se mostrará para las mismas líneas de código fuente, los conteos de línea en sí mismos podrían parecer

    inconsistentes.

    Las aplicaciones de larga duración pueden usar las instalaciones "__gcov_reset" y "__gcov_dump" para restringir la recolección de perfiles a la región de interés del programa. Llamar a "__gcov_reset(void)" borrará todos los contadores de perfil en tiempo de ejecución a cero, y llamar a "__gcov_dump(void)" hará que la información de perfil recolectada en ese punto se vuelque a los archivos de salida .gcda. Las aplicaciones instrumentadas usan un destructor estático con prioridad 99 para invocar la función "__gcov_dump". Así "__gcov_dump" se ejecuta después de todos los destructores estáticos definidos por el usuario, así como los manejadores registrados con "atexit"

    .

    Si un ejecutable carga un objeto compartido dinámico a través de la funcionalidad dlopen, -Wl,--dynamic-list-data es necesario para volcar todos los datos de

    perfil.

    La biblioteca de tiempo de ejecución de perfilado reporta varios errores relacionados con la manipulación de perfiles y el guardado de perfiles. Los errores se imprimen en la salida de error estándar o en el archivo GCOV_ERROR_FILE, si se usa la variable de entorno. Para terminar inmediatamente después de que ocurra un error, establezca la variable de entorno GCOV_EXIT_AT_ERROR. Eso puede ayudar a los usuari

    os a encontrar choqu
    es de perfiles que conducen a un perfil engañoso.
