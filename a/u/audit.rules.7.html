AUDIT.RULES(7) Utilidades de Administración del Sistema AUDIT.RULES(7)

NOMBRE

audit.rules - un conjunto de reglas cargadas en el sistema de auditoría del kernel

DESCRIPCIÓN

audit.rules es un archivo que contiene reglas de auditoría que serán cargadas por el script de inicio del demonio de auditoría cada vez que se inicie el demonio. El programa auditctl es utilizado por los scripts de inicio para realizar esta operación. La sintaxis de las reglas es esencialmente la misma que al escribir un comando auditctl en un prompt de shell, excepto que no es necesario escribir el nombre del comando auditctl, ya que este se implica. Las reglas de auditoría vienen en 3 variedades: control, archivo y llamada de sistema.

Control

Los comandos de control generalmente implican la configuración del sistema de auditoría en lugar de decirle qué vigilar. Estos comandos típicamente incluyen eliminar todas las reglas, establecer el tamaño de la cola de backlogs del kernel, establecer el modo de fallo, establecer el límite de tasa de eventos o indicarle a auditctl que ignore los errores de sintaxis en las reglas y continúe cargando. Generalmente, estas reglas están en la parte superior del archivo de reglas.

Sistema de archivos

Las reglas del sistema de archivos a veces se llaman "watches" (vigilancias). Estas reglas se utilizan para auditar el acceso a archivos o directorios particulares que puedan interesarle. Si la ruta dada en una regla de vigilancia es un directorio, entonces la regla utilizada es recursiva hasta el fondo del árbol de directorios, excluyendo cualquier directorio que pueda ser puntos de montaje. La sintaxis de estas reglas de vigilancia generalmente sigue este formato:

-a always,exit -F arch=b64 -F path=ruta-al-archivo -F perm=permisos -F key=nombre-clave

donde los permisos son cualquiera de los siguientes:

r
- lectura del archivo
w
- escritura en el archivo
x
- ejecución del archivo
a
- cambio en los atributos del archivo

Para un mejor rendimiento, debe proporcionar un campo arch en la regla. Los permisos individuales causarán la selección de llamadas de sistema específicas que utilizan ese tipo de acceso. No proporcionar la arquitectura causará la selección de todas las llamadas de sistema, lo que afectará el rendimiento, ya que se evaluarán todas las llamadas de sistema.

Las vigilancias también se pueden crear utilizando el formato obsoleto -w, que permite la compatibilidad hacia atrás a expensas del rendimiento del sistema, como se explica. Usando reglas de llamadas de sistema como se muestra arriba, puede elegir entre path y dir, que son contra un inode específico o un árbol de directorios respectivamente. También cabe señalar que la vigilancia de directorios recursiva se detendrá si hay un punto de montaje debajo del directorio padre. Existe una opción para hacer que el subdirectorio montado sea equivalente usando una regla -q.

Llamada de sistema

Las reglas de llamadas de sistema se cargan en un motor de coincidencia que intercepta cada llamada de sistema que todos los programas del sistema realizan. Por lo tanto, es muy importante usar reglas de llamadas de sistema solo cuando sea necesario, ya que estas afectan el rendimiento. Cuantas más reglas, mayor será el impacto en el rendimiento. Sin embargo, puede ayudar al rendimiento combinando llamadas de sistema en una sola regla siempre que sea posible.

El kernel de Linux tiene 6 listas de coincidencia de reglas o filtros, como a veces se les llama. Son: task, exit, user, exclude, filesystem y io_uring. La lista de tareas (task) se comprueba solo durante las llamadas de sistema fork o clone. Raramente se usa en la práctica.

El filtro de salida (exit) es el lugar donde se evalúan todas las solicitudes de auditoría del sistema de archivos y de llamadas de sistema.

El filtro de usuario (user) se utiliza para filtrar (eliminar) algunos eventos que se originan en el espacio de usuario. Por defecto, se permite cualquier evento que se origine en el espacio de usuario. Por lo tanto, si hay algunos eventos que no desea ver, este es un lugar donde algunos pueden eliminarse. Consulte auditctl(8) para conocer los campos válidos.

El filtro de exclusión (exclude) se utiliza para excluir la emisión de ciertos eventos. El tipo de mensaje y varios campos de atributos del sujeto se pueden utilizar para indicar al kernel qué tipos de mensajes no desea registrar. Este filtro puede eliminar el evento en su totalidad y no es selectivo sobre ningún otro atributo. Los filtros de usuario y de salida son más adecuados para auditar selectivamente eventos. La acción se ignora para este filtro, y por defecto es "nunca".

El filtro io_uring se utiliza para vigilar las llamadas de sistema subyacentes realizadas por operaciones io_uring.

Las reglas de llamadas de sistema tienen la forma general de:

-a acción,lista -S llamada_de_sistema -F campo=valor -k nombre-clave

La opción -a le indica al motor de coincidencia de reglas del kernel que deseamos agregar una regla al final de la lista de reglas. Pero debemos especificar en qué lista de reglas va y qué acción tomar cuando se activa. Las acciones válidas son:

always
- siempre crea un evento
never
- nunca crea un evento

La acción y la lista están separadas por una coma, pero sin espacio entre ellas. Las listas válidas son: task, exit, user, exclude, filesystem y io_uring. Su significado fue explicado anteriormente.

A continuación, en la regla, normalmente estaría la opción -S. Este campo puede ser el nombre o el número de la llamada de sistema. Para mayor legibilidad, casi siempre se usa el nombre. Puede proporcionar más de una llamada de sistema en una regla especificando otra opción -S. Cuando se envían al kernel, todos los campos de llamadas de sistema se colocan en una máscara para que una sola comparación pueda determinar si la llamada de sistema es de interés. Por lo tanto, agregar múltiples llamadas de sistema en una regla es muy eficiente. Cuando especifica un nombre de llamada de sistema, auditctl buscará el nombre y obtendrá su número de llamada de sistema. Esto causa algunos problemas en máquinas bi-arquitectura. Los números de llamada de sistema de 32 y 64 bits a veces, pero no siempre, coinciden. Por lo tanto, para resolver este problema, generalmente necesitaría dividir la regla en 2, una especificando -F arch=b32 y la otra especificando -F arch=b64. Esto debe ir delante de la opción -S para que auditctl consulte la tabla de búsqueda correcta al devolver el número.

Después de especificar la llamada de sistema, normalmente tendría una o más opciones -F que afinan contra qué hacer coincidir. En lugar de enumerar todos los tipos de campos válidos aquí, el lector debería consultar la página del manual de auditctl, que tiene una lista completa de cada campo y su significado. Pero vale la pena mencionar un par de cosas.

El sistema de auditoría considera que las UID son números sin signo. El sistema de auditoría utiliza el número -1 para indicar que una loginuid no está configurada. Esto significa que cuando se imprime, parece 4294967295. Pero cuando escribe reglas, puede usar "unset", que es fácil de recordar, o -1, o 4294967295. Todos son equivalentes. Si escribe una regla para intentar obtener los usuarios válidos del sistema, necesita mirar en /etc/login.defs para ver dónde comienzan las cuentas de usuario. Por ejemplo, si UID_MIN es 1000, entonces también deberá tener en cuenta que la representación sin signo de -1 es mayor que 500. Por lo tanto, abordaría esto con la siguiente parte de una regla:

-F auid>=1000 -F auid!=unset

Estas comprobaciones individuales se combinan con un "and" y ambas deben ser verdaderas.

Lo último que debe saber sobre las reglas de llamadas de sistema es que puede agregar un campo de clave, que es una cadena de texto libre que desea insertar en el evento para ayudar a identificar su significado. Esto se discute con más detalle en la sección NOTAS.

NOTAS

El propósito de la auditoría es poder realizar una investigación periódica o siempre que ocurra un incidente. Unos pocos pasos sencillos en la planificación previa facilitarán este trabajo. El mejor consejo es usar claves tanto en las vigilancias como en las reglas de llamadas de sistema para dar un significado a la regla. Si las reglas están relacionadas o juntas cumplen un requisito específico, asígneles un nombre de clave común. Puede usar esto durante su investigación para seleccionar solo resultados con un significado específico.

Al realizar una investigación, normalmente comenzaría con la salida principal de aureport para tener una idea de lo que está sucediendo en el sistema. Este informe le informa principalmente sobre eventos que están codificados de forma rígida por el sistema de auditoría, como inicios/cierres de sesión, usos de autenticación, anomalías del sistema, cuántos usuarios han estado en la máquina y si SE Linux ha detectado algún AVC.

aureport --start esta-semana

Después de ver el informe, probablemente querrá obtener una segunda opinión sobre qué reglas cargadas se han estado activando

PROBLEMAS

Si no está recibiendo eventos en reglas de syscall que cree que debería, intente ejecutar un programa de prueba bajo strace para que pueda ver los syscalls. Existe la posibilidad de que haya identificado el syscall

incorrecto.

Si recibe una advertencia de auditctl que dice, "32/64 bit syscall mismatch in line XX, you should specify an arch". Esto significa que especificó una regla de syscall en un sistema bi-arquitectura donde el syscall tiene un número de syscall diferente para las interfaces de 32 y 64 bits. Esto significa que en una de esas interfaces probablemente esté auditando el syscall incorrecto. Para solucionar el problema, reescriba la regla como dos reglas especificando la arquitectura pretendida para cada regla. Por

ejemplo, 
-a always,exit -S openat -k
access

se reescribiría

como 
-a always,exit -F arch=b32 -S openat -k access
-a always,exit -F arch=b64 -S openat -k
access

Si recibe una advertencia que dice, "entry rules deprecated, changing to exit rule". Esto significa que tiene una regla destin

ada al filtro de entrada, pero ese filtro ya no está disponible. Auditctl movió su regla al filtro de salida para que no se pie
rda. Pero para solucionar esto y que no reciba la advertencia más, necesita cambiar la regla problemática de entrada a salida.

CONECTADOS

Si la auditoría está habilitada, entonces puede obtener cualquier evento que no sea causado por reglas de syscall o de vigilancia de archivos (porque no tiene ninguna regla cargada). Eso significa que se puede emitir cualquier evento desde 1100-1299, 1326, 1328, 1331 y superiores. La razón por la que hay una serie de eventos conectados es porque son requeridos por el cumplimiento normativo y se envían automáticamente como cortesía. (Por ejemplo, el inicio/cierre de sesión es un evento obligatorio en todas las guías de seguridad.) Si no desea esto, puede usar el filtro exclude para descartar eventos que no

desee.
