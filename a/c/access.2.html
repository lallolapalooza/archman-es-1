DESCRIPCIÓ

N

access() comprueba si el proceso que llama puede acceder al archivo path. Si path es un enlace simbólico, se

desreferencia.

El mode especifica la(s) comprobación(es) de accesibilidad a realizar, y es o bien el valor F_OK, o una máscara que consiste en la unión bit a bit de uno o más de R_OK, W_OK y X_OK. F_OK comprueba la existencia del archivo. R_OK, W_OK y X_OK comprueban si el archivo existe y otorga permisos de lectura, escritura y ejecución, respectivamente

.

La comprobación se realiza utilizando el UID real y el GID del proceso que llama, en lugar de los IDs efectivos como se hace cuando se intenta realmente una operación (por ejemplo, open(2)) en el archivo. De manera similar, para el usuario root, la comprobación utiliza el conjunto de capacidades permitidas en lugar del conjunto de capacidades efectivas; y para los usuarios no root, la comprobación utiliza un conjunto vacío de

capacidades.

Esto permite a los programas set-user-ID y a los programas dotados de capacidades determinar fácilmente la autoridad del usuario que los invoca. En otras palabras, access() no responde a la pregunta "¿puedo leer/escribir/ejecutar este archivo?". Responde a una pregunta ligeramente diferente: "(suponiendo que soy un binario setuid) ¿puede el usuario que me invocó leer/escribir/ejecutar este archivo?", lo que da a los programas set-user-ID la posibilidad de evitar que usuarios maliciosos provoquen que lean archivos que los usuarios no deberían poder

leer.

Si el proceso que llama tiene privilegios (es decir, su UID real es cero), entonces una comprobación X_OK es exitosa para un archivo regular si el permiso de ejecución está habilitado para cualquiera de los propietarios del archivo, el grupo u

otros.

VERSIONE

S

Si el proceso que llama tiene los privilegios adecuados (es decir, es superusuario), POSIX.1-2001 permite que una implementación indique éxito para una comprobación X_OK incluso si no están establecidos ninguno de los bits de permiso de ejecución del archivo. Linux no hace

esto.

Diferencias entre la biblioteca C y el

núcleo

La llamada al sistema faccessat() cruda toma solo los primeros tres argumentos. Los AT_EACCESS y AT_SYMLINK_NOFOLLOW flags son realmente implementados dentro de la función envolvente de glibc para faccessat(). Si se especifica cualquiera de estos flags, entonces la función envolvente emplea fstatat(2) para determinar los permi

sos de acceso, per

NOTA

S

Advertencia: Usar estas llamadas para verificar si un usuario está autorizado a, por ejemplo, abrir un archivo antes de hacerlo realmente usando open(2) crea un agujero de seguridad, porque el usuario podría explotar el corto intervalo de tiempo entre la verificación y la apertura del archivo para manipularlo. Por esta razón, el uso de esta llamada al sistema debe evitarse. (En el ejemplo recién descrito, una alternativa más segura sería cambiar temporalmente el ID de usuario efectivo del proceso al ID real y luego llamar a open(2).

)

access() siempre desreferencia los enlaces simbólicos. Si necesitas verificar los permisos en un enlace simbólico, usa faccessat() con el flag AT_SYMLINK_NOFOLLOW

.

Estas llamadas devuelven un error si alguno de los tipos de acceso en mode es denegado, incluso si algunos de los otros tipos de acceso en mode son

permitidos.

Un archivo es accesible solo si los permisos en cada uno de los directorios en el prefijo de ruta de path otorgan acceso de búsqueda (es decir, ejecución). Si algún directorio es inaccesible, entonces la llamada a access() falla, independientemente de los permisos del archivo en

sí.

Solo se verifican los bits de acceso, no el tipo de archivo o el contenido. Por lo tanto, si se encuentra que un directorio es escribible, probablemente significa que se pueden crear archivos en el directorio, y no que el directorio pueda ser escrito como un archivo. De manera similar, un archivo DOS puede ser reportado como ejecutable, pero la llamada a execve(2) seguirá

fallando.

Estas llamadas pueden no funcionar correctamente en sistemas de archivos NFSv2 con el mapeo de UID habilitado, porqu

e el mapeo de UID se realiza en el servidor y está oculto para el cliente, que verifica los permisos. (Las versiones
3 y superiores de NFS realizan la verificación en el servidor.) Problemas similares pueden ocurrir en montajes FUSE.

ERRORE

S

Debido a que la llamada al sistema faccessat() del núcleo Linux no soporta un argumento flags, la función envolvente faccessat() proporcionada en glibc 2.32 y versiones anteriores emula la funcionalidad requerida usando una combinación de la llamada al sistema faccessat() y fstatat(2). Sin embargo, esta emulación no tiene en cuenta los ACL. A partir de glibc 2.33, la función envolvente evita este error haciendo uso de la llamada al sistema faccessat2() donde es proporcionada por el núcleo

subyacente.

En Linux 2.4 (y anteriores) hay cierta rareza en el manejo de pruebas X_OK para el superusuario. Si todas las categorías de permiso de ejecución están deshabilitadas para un archivo que no es directorio, entonces la única prueba de access() que devuelve -1 es cuando mode es especificado como solo X_OK; si R_OK o W_OK también es especificado en mode, entonces access() devuelve 0 para tales archivos. Las primeras versiones de Linux 2.6 (hasta y incluyendo Linux 2.6.3) también se comportaban de la misma manera que Linux 2.

4.

Antes de Linux 2.6.20, estas llamadas ignoraban el efecto de la MS_NOEXEC flag si se usó para mount(2) el sistema de archivos subyacente. Desde Linux 2.6.20, la MS_NOEXEC flag

es res
petada.
