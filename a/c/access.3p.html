ACCESS(3P) Manual del Programador POSIX ACCESS(3P)

PROLOGO

Esta página del manual forma parte del Manual del Programador POSIX. La implementación de esta interfaz en Linux puede diferir (consulte la página del manual de Linux correspondiente para conocer los detalles del comportamiento en Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

access, faccessat — determinar la accesibilidad de un descriptor de archivo

SINOPSIS

#include <unistd.h>
int access(const char *path, int amode);
#include <fcntl.h>
int faccessat(int fd, const char *path, int amode, int flag);

DESCRIPCIÓN

La función access() comprueba si el archivo denominado por la ruta apuntada por el argumento path es accesible según el patrón de bits contenido en amode. Las comprobaciones de accesibilidad (incluyendo los permisos de directorio comprobados durante la resolución de la ruta) se realizarán utilizando el ID de usuario real en lugar del ID de usuario efectivo y el ID de grupo real en lugar del ID de grupo efectivo.

El valor de amode es la OR inclusiva a nivel de bits de los permisos de acceso que se van a comprobar (R_OK, W_OK, X_OK) o la prueba de existencia (F_OK).

Si se comprueban permisos de acceso, cada uno se comprobará individualmente, según se describe en el volumen de Definiciones Base de POSIX.1‐2017, Sección 4.5, Permisos de Acceso a Archivos, excepto que donde esa descripción se refiere al permiso de ejecución para un proceso con privilegios apropiados, una implementación puede indicar éxito para X_OK incluso si el permiso de ejecución no se otorga a ningún usuario.

La función faccessat(), cuando se llama con un valor de flag de cero, será equivalente a la función access(), excepto en el caso en que path especifique una ruta relativa. En este caso, el archivo cuya accesibilidad se va a determinar se localizará en relación con el directorio asociado con el descriptor de archivo fd en lugar del directorio de trabajo actual. Si el modo de acceso de la descripción del archivo abierto asociado con el descriptor de archivo no es O_SEARCH, la función comprobará si las búsquedas de directorio están permitidas utilizando los permisos actuales del directorio subyacente al descriptor de archivo. Si el modo de acceso es O_SEARCH, la función no realizará la comprobación.

Si faccessat() recibe el valor especial AT_FDCWD en el parámetro fd, se utilizará el directorio de trabajo actual y, si flag es cero, el comportamiento será idéntico a una llamada a access().

Los valores para flag se construyen mediante una OR inclusiva a nivel de bits de banderas de la siguiente lista, definidas en <fcntl.h>:

AT_EACCESS
Las comprobaciones de accesibilidad (incluidos los permisos de directorio comprobados durante la resolución de la ruta) se realizarán utilizando el ID de usuario efectivo y el ID de grupo efectivo en lugar del ID de usuario real y el ID de grupo real, como se requiere en una llamada a access().

VALOR DE RETORNO

Tras una finalización exitosa, estas funciones devolverán 0. En caso contrario, estas funciones devolverán -1 y establecerán errno para indicar el error.

ERRORES

Estas funciones fallarán si:

EACCES
Los bits de permiso del modo del archivo no permiten el acceso solicitado, o se deniega el permiso de búsqueda en un componente del prefijo de ruta.
ELOOP
Existe un bucle en los enlaces simbólicos encontrados durante la resolución del argumento path.
ENAMETOOLONG

La longitud de un componente de una ruta es mayor que {NAME_MAX}.
ENOENT
Un componente de path no nombra un archivo existente o path es una cadena vacía.
ENOTDIR
Un componente del prefijo de ruta nombra un archivo existente que no es ni un directorio ni un enlace simbólico a un directorio, o el argumento path contiene al menos un carácter que no es <barra> y termina con uno o más caracteres de <barra> finales y el último componente de la ruta nombra un archivo existente que no es ni un directorio ni un enlace simbólico a un directorio.
EROFS
Se solicita acceso de escritura a un archivo en un sistema de archivos de solo lectura.

La función faccessat() fallará si:

EACCES
El modo de acceso de la descripción del archivo abierto asociado con fd no es O_SEARCH y los permisos del directorio subyacente a fd no permiten búsquedas de directorio.
EBADF
El argumento path no especifica una ruta absoluta y el argumento fd no es AT_FDCWD ni un descriptor de archivo válido abierto para lectura o búsqueda.
ENOTDIR
El argumento path no es una ruta absoluta y fd es un descriptor de archivo asociado con un archivo que no es un directorio.

Estas funciones pueden fallar si:

EINVAL
El valor del argumento amode es inválido.
ELOOP
Se encontraron más de {SYMLOOP_MAX} enlaces simbólicos durante la resolución del argumento path.
ENAMETOOLONG

La longitud de una ruta excede {PATH_MAX}, o la resolución de ruta de un enlace simbólico produjo un resultado intermedio con una longitud que excede {PATH_MAX}.
ETXTBSY
Se solicita acceso de escritura a un archivo de procedimiento puro (texto compartido) que se está ejecutando.

La función faccessat() puede fallar si:

EINVAL
El valor del argumento flag no es válido.

Las siguientes secciones son informativas.

EJEMPLOS

Comprobando la existencia de un archivo

El siguiente ejemplo comprueba si un archivo llamado myfile existe en el directorio /tmp.

#include <unistd.h>
...
int result;
const char *pathname = "/tmp/myfile";
result = access (pathname, F_OK);

USO DE APLICACIONES

Se desaconseja el uso de estas funciones, ya que la información devuelta está desactualizada cuando se actúa sobre ella. (Es decir, actuar sobre la información siempre conduce a una condición de carrera de tiempo de comprobación a tiempo de uso). Una aplicación debería, en su lugar, intentar la acción por sí misma y manejar el error [EACCES] que ocurre si el archivo no es accesible (con un cambio de IDs de usuario y grupo efectivos antes, y quizás un cambio de vuelta después, en el caso de que se hubiera utilizado access() o faccessat() sin AT_EACCES).

Históricamente, uno de los usos de access() era en programas set-user-ID root para comprobar si el usuario que ejecutaba el programa tenía acceso a un archivo. Esto se basaba en privilegios de "superusuario" que se otorgaban basándose en que el ID de usuario efectivo fuera cero, de modo que cuando access() utilizaba el ID de usuario real para comprobar la accesibilidad, esos privilegios no se tenían en cuenta. En sistemas más recientes donde se pueden asignar privilegios que no tienen asociación con IDs de usuario o grupo, si un programa con tales privilegios llama a access(), el cambio de IDs no tiene efecto sobre los privilegios y, por lo tanto, se tienen en cuenta en las comprobaciones de accesibilidad. Por lo tanto, access() (y faccessat() con flag cero) no pueden utilizarse para este propósito histórico en tales programas. Si se utiliza un nombre de ruta relativo, no se tiene en cuenta si el directorio actual (o el directorio asociado al descriptor de archivo fd) es accesible a través de cualquier nombre de ruta absoluto. Las aplicaciones que utilizan access(), o faccessat() sin AT_EACCES, pueden por lo tanto actuar como si el archivo fuera accesible para un usuario con el ID de usuario real y el ID de grupo del proceso, cuando dicho usuario en la práctica no podría acceder al archivo porque el acceso sería denegado en algún punto por encima del directorio actual (o del directorio asociado al descriptor de archivo fd) en la jerarquía de archivos.

Si access() o faccessat() se utiliza con W_OK para comprobar el acceso de escritura a un directorio que tiene el bit S_ISVTX establecido, un valor de retorno que indica que el directorio es escribible puede ser engañoso, ya que algunas operaciones sobre los archivos del directorio no estarían permitidas basándose en la propiedad de dichos archivos (véase el volumen de Definiciones Básicas de POSIX.1‐2017, Sección 4.3, Protección de Directorios).

Se pueden considerar válidos valores adicionales de amode además del conjunto definido en la descripción; por ejemplo, si un sistema tiene controles de acceso extendidos.

El uso del valor AT_EACCESS para flag habilita funcionalidades no disponibles en access().

JUSTIFICACIÓN

En las primeras propuestas, algunas deficiencias en la función access() llevaron a la creación de una función eaccess() porque:

1.
Las implementaciones históricas de access() no prueban el acceso al archivo correctamente cuando el ID de usuario real del proceso es el de superusuario. En particular, siempre devuelven cero al probar permisos de ejecución sin tener en cuenta si el archivo es ejecutable.
2.
El superusuario tiene acceso completo a todos los archivos de un sistema. Como consecuencia, los programas iniciados por el superusuario y que cambian al ID de usuario efectivo con privilegios menores no pueden usar access() para probar sus permisos de acceso a archivos.

Sin embargo, el modelo histórico de eaccess() no resuelve el problema (1), por lo que este volumen de POSIX.1‐2017 ahora permite que access() se comporte de la manera deseada porque varias implementaciones han corregido el problema. También se argumentó que el problema (2) se resuelve más fácilmente usando open(), chdir() o una de las funciones exec según corresponda, y respondiendo al error, en lugar de crear una nueva función que no sería tan fiable. Por lo tanto, eaccess() no está incluida en este volumen de POSIX.1‐2017.

La frase sobre privilegios apropiados y bits de permiso de ejecución refleja las dos posibilidades implementadas por las implementaciones históricas al comprobar el acceso de superusuario para X_OK.

Se desaconseja a las nuevas implementaciones devolver X_OK a menos que al menos un bit de permiso de ejecución esté establecido.

El propósito de la función faccessat() es permitir la comprobación de la accesibilidad de archivos en directorios distintos del directorio de trabajo actual sin exposición a condiciones de carrera. Cualquier parte de la ruta de un archivo podría cambiarse en paralelo a una llamada a access(), resultando en un comportamiento no especificado. Al abrir un descriptor de archivo para el directorio de destino y usar la función faccessat() se puede garantizar que el archivo probado para accesibilidad está ubicado relativo al directorio deseado.
