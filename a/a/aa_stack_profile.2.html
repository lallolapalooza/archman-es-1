aa_stack_profile(2)

Paquete: apparmor

Licencias: GPL-2.0-only, LGPL-2.0-only, LGPL-2.1-only

AA_STACK_PROFILE(2) AppArmor AA_STACK_PROFILE(2)

NOMBRE

aa_stack_profile, aa_stack_onexec - combinar múltiples perfiles para confinar una tarea

SINOPSIS

#include <sys/apparmor.h>

int aa_stack_profile(const char *profile);

int aa_stack_onexec(const char *profile);

Enlazar con -lapparmor al compilar.

DESCRIPCIÓN

AppArmor admite la acumulación de dos o más perfiles al confinar una tarea. El resultado es una intersección de todos los perfiles que se acumulan. Acumular perfiles es deseable cuando se quiere asegurar que el confinamiento nunca se volverá más permisivo. Al cambiar entre dos perfiles, como se hace con aa_change_profile(2), siempre existe la posibilidad de que el nuevo perfil sea más permisivo que el perfil antiguo, pero esa posibilidad se elimina cuando se usa aa_stack_profile().

Para acumular un perfil con el contexto de confinamiento actual, una tarea puede usar la función aa_stack_profile() . El parámetro profile es una cadena terminada en NUL que indica un nombre de perfil que debe acumularse con el confinamiento actual.

Llamar a aa_stack_profile("profile_a") sin estar confinado es equivalente a llamar a aa_change_profile("profile_a") ya que la intersección de "sin confinar" y "profile_a" es "profile_a". Llamar a aa_stack_profile("profile_b") estando confinado por "profile_a" resulta en que el confinamiento de la tarea sea la intersección de "profile_a" y "profile_b". El contexto de confinamiento resultante se representará como "profile_a//&profile_b" en los mensajes del registro de auditoría, el valor de retorno de aa_getcon(2), etc.

Los programas confinados que quieran usar aa_stack_profile() necesitan tener reglas que permitan acumular el perfil nombrado. Véase apparmor.d(8) para más detalles.

Los descriptores de archivo abiertos pueden no ser remediados después de una llamada a aa_stack_profile() , por lo que el programa que llama debe close(2) los descriptores de archivo abiertos para asegurar que no estén disponibles después de llamar a aa_stack_profile().

La función aa_stack_onexec() es como la función aa_stack_profile() excepto que especifica que la acumulación debe tener lugar en la siguiente ejecución (exec) en lugar de inmediatamente. El cambio de perfil retrasado tiene prioridad sobre cualquier regla de transición de ejecución dentro del perfil de confinamiento. Retrasar el límite de acumulación tiene algunas ventajas, elimina la necesidad de perfiles de transición de relleno y el límite de ejecución es una capa de seguridad natural donde la memoria potencialmente sensible es desmapeada.

VALOR DE RETORNO

Se devuelve cero en caso de éxito. En caso de error, se devuelve -1, y errno(3) se establece adecuadamente.

ERRORES

EINVAL
AppArmor no está cargado, no se especificó ni un perfil ni un espacio de nombres, o la comunicación a través del archivo /proc/*/attr/current no se ajustó al protocolo.
ENOMEM
No había suficiente memoria disponible en el kernel.
ENOENT
El perfil especificado no existe, o no es visible desde el espacio de nombres actual.

NOTAS

Usar aa_stack_profile() y las funciones relacionadas de libapparmor son la única forma de asegurar la compatibilidad entre diferentes versiones del kernel. Sin embargo, puede haber algunas situaciones donde libapparmor no esté disponible y sea necesario interactuar directamente con el sistema de archivos de AppArmor para acumular un perfil.

Para acumular inmediatamente un perfil llamado "profile_a", como se hace con aa_stack_profile("profile_a"), se puede usar el equivalente a este comando de shell:

$ echo -n "stack profile_a" > /proc/self/attr/current

Para acumular un perfil llamado "profile_a" en la siguiente ejecución, como se hace con aa_stack_onexec("profile_a"), se puede usar el equivalente a este comando de shell:

$ echo -n "stack profile_a" > /proc/self/attr/exec

Estas operaciones crudas del sistema de archivos de AppArmor solo deben usarse cuando usar libapparmor no es una opción viable.

EJEMPLO

El siguiente ejemplo muestra un uso simple, aunque artificial, de aa_stack_profile().

#include <stdlib.h>
#include <string.h>
#include <sys/apparmor.h>
#include <sys/types.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <stdio.h>
#include <unistd.h>
static void read_passwd()
{
        int fd;
        char buf[10];
        if ((fd=open("/etc/passwd", O_RDONLY)) < 0) {
               perror("Failure opening /etc/passwd");
               _exit(1);
        }
        /* Verify that we can read /etc/passwd */
        memset(&buf, 0, 10);
        if (read(fd, &buf, 10) == -1) {
                perror("Failure reading /etc/passwd");
                _exit(1);
        }
        buf[9] = '\0';
        printf("/etc/passwd: %s\n", buf);
        close(fd);
}
int main(int argc, char * argv[])
{
        printf("Before aa_stack_profile():\n");
        read_passwd();
        /* stack the "i_cant_be_trusted_anymore" profile, which
         * should not have read access to /etc/passwd. */
        if (aa_stack_profile("i_cant_be_trusted_anymore") < 0) {
            perror("Failure changing profile -- aborting");
            _exit(1);
        }
        printf("After aa_stack_profile():\n");
        read_passwd();
        _exit(0);
}

Este ejemplo de código requiere que un perfil similar al siguiente esté cargado con apparmor_parser(8):

# Confine stack_p to be able to read /etc/passwd and aa_stack_profile()
# to the 'i_cant_be_trusted_anymore' profile.
/tmp/stack_p {
    /etc/ld.so.cache          mr,
    /lib/ld-*.so*             mrix,
    /lib/libc*.so*            mr,
    /etc/passwd               r,
    # Needed for aa_stack_profile()
    change-profile -> &i_cant_be_trusted_anymore,
    /usr/lib/libapparmor*.so* mr,
    /proc/[0-9]*/attr/current w,
}

Así como el perfil a acumular:

profile i_cant_be_trusted_anymore {
    /etc/ld.so.cache      mr,
    /lib/ld-*.so*         mrix,
    /lib/libc*.so*        mr,
}

La salida al ejecutarlo:

$ /tmp/stack_p
Before aa_stack_profile():
/etc/passwd: root:x:0:
After aa_stack_profile():
Failure opening /etc/passwd: Permission denied
$

ERRORES CONOCIDOS

No se conocen. Si encuentra alguno, por favor repórtelo en https://gitlab.com/apparmor/apparmor/-/issues. Tenga en cuenta que usar aa_stack_profile(2) sin execve(2) no proporciona barreras de memoria entre las diferentes áreas de un programa; si se requiere separación del espacio de direcciones, entonces se deben usar procesos separados.
