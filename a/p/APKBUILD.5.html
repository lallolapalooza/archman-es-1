Si no hay una dirección web disponible para el paquete, debe establecer url como una cadena vacía ("").

subpackages Especifica subpaquetes o paquetes divididos construidos con este paquete. Típicamente, esto incluirá $pkgname-de

para archivos de desarrollo

Por defecto, la función de división es el final del nombre del paquete después del último guion. Así que para $pkgname-foo y libfoo la función de división es foo y libfoo respectivamente. Se puede establecer un nombre de función de división personalizada usando foo:funcname. De manera similar a la función package , la función de división debe mover archivos desde $pkgdir (que es el directorio de trabajo actual por defecto) o $srcdir a $subpkgdir después de crear $subpkgdir.

Por defecto, arch determina si un subpaquete se considera independiente de la arquitectura o no. Esto se puede cambiar usando foo::noarch o foo:funcname:all.

Cuando se especifican múltiples subpaquetes, sus funciones de división se ejecutan en el orden en que aparecen en subpackages.

triggers

Especifica un script de disparador (trigger) utilizado por el paquete. Un script de disparador es un script de shell que se llama siempre que se modifican archivos o directorios monitoreados. Puede especificar las rutas a monitorear usando la variable triggers de la siguiente manera: 
$pkgname.trigger=/usr/share/man:/usr/local/share/man

Esto ejecutará el script de disparador del paquete siempre que se creen, modifiquen o eliminen archivos en /usr/share/man o /usr/local/share/man .

options

La options variable le permite establecer parámetros para el paquete en tiempo de compilación. Hay una serie de opciones válidas que puede establecer, y puede establecer múltiples opciones escribiendo un espacio entre cada una. Se pueden usar nombres de opciones personalizados cuando contienen exactamente un :. Las opciones se pueden establecer para (sub)paquetes específicos usando subpkgname::option (o subpkgname:option para opciones personalizadas).

!archcheck

Especifica que el paquete contiene binarios que no pueden ejecutarse en la arquitectura de destino. Esto se usa principalmente para paquetes que contienen firmware, y normalmente nunca debería ser necesario.

bigdocs

Especifica que este paquete tiene intencionalmente un subpaquete -doc grande. Con ello se suprime una advertencia que se emitiría si el subpaquete -doc supera un cierto umbral de tamaño de paquete (actualmente 2 MiB).

charset.alias

Especifica que el paquete incluye un archivo /usr/lib/charset.alias y que debe instalarse en el sistema del usuario. Casi nunca es el caso. No use esta opción.

!check

Especifica que el paquete no ejecutará una suite de pruebas. La razón para desactivar la fase de comprobación debe anotarse en un comentario.

checkroot

Especifica que la suite de pruebas de este paquete se ejecutará en fakeroot(8). Esto es necesario para algunas suites de pruebas que fallan cuando se ejecutan como no-root.

!dbg

Especifica que el paquete no debe compilarse con un paquete de información de depuración. Esto es el valor por defecto a menos que DEFAULT_DBG esté configurado en el entorno o en abuild.conf(5). Normalmente se usa en paquetes que no generan información de depuración (como paquetes de Python puros) o paquetes que no admiten paquetes de información de depuración.

!fhs

Especifica que el paquete viola el FHS e instala en una ubicación como /usr/local, /opto /srv.

ldpath-recursive

Especifica que abuild(1) debe usar el argumento --recursive para scanelf(1) al intentar encontrar las dependencias de bibliotecas compartidas (.so) del paquete.

lib64

Especifica que el paquete instala archivos bajo /lib64 o /usr/lib64 y que la prueba para esos directorios debe omitirse. Esto está desaconsejado y solo debe usarse para paquetes que proporcionan compatibilidad para la libc de GNU.

libtool

Especifica que el paquete requiere sus archivos libtool (.la). No serán eliminados automáticamente por abuild(1).

net

Especifica que el sistema de compilación del paquete requiere acceso a una red. Esto está desaconsejado y se debe presentar un problema con los autores del paquete.

!strip

Especifica que strip(1) no debe ejecutarse en ninguno de los binarios del paquete. Esto se implica automáticamente si el -dbg subpaquete está habilitado, o si está usando DEFAULT_DBG.

suid

Especifica que los binarios del paquete pueden instalarse con set-uid. Esto es un riesgo de seguridad y se recomienda encarecidamente usar capacidades o separación de procesos en lugar de set-uid donde esté disponible.

setcap

Especifica que los binarios del paquete pueden instalarse con capacidades adicionales de setcap(8). Si esta opción está habilitada, se recomienda encarecidamente que solo los usuarios root y los usuarios de un grupo específico puedan ejecutar estos binarios, no otros.

textrels

Especifica que se sabe que los binarios del paquete contienen reubicaciones contra segmentos de texto. Por defecto, abuild(1) se negará a crear un paquete así porque esto es una preocupación de seguridad.

toolchain

Especifica que el paquete es parte del conjunto base de herramientas y puede depender de paquetes como g++.

!tracedeps

Especifica que abuild(1) no debe poblar automáticamente depends con dependencias de bibliotecas compartidas (.so) o de destinos de enlaces simbólicos.

Variables Automáticas

Las siguientes variables son definidas para usted por abuild(1), pero pueden ser anuladas si es necesario.

builddir

Especifica el directorio donde se compilará el código fuente del paquete. El valor por defecto es $srcdir/$pkgname-$pkgver lo cual es apropiado para la mayoría de las distribuciones de código fuente. Si el tarball de origen no crea un directorio $pkgname-$pkgver cuando se desempaqueta, debe anular builddir.

pkgdir

Especifica el directorio donde se instalarán los archivos compilados. Normalmente, llamará a `make DESTDIR="$pkgdir" install` o similar para instalar los archivos. El valor por defecto es $startdir/pkg y no debe modificar esta variable.

srcdir

Especifica el directorio donde se descargan y desempaquetan los archivos especificados en source . El valor por defecto es $startdir/src y no debería necesitar modificar esto.

startdir

Especifica el directorio donde reside el archivo APKBUILD . Esto generalmente no debe usarse.

subpkgdir

Especifica el directorio donde deben colocarse los archivos del subpaquete. Esta variable solo está configurada dentro de las funciones de subpaquete.

depends_doc

depends_openrc

Dependencias en tiempo de ejecución del -systemd subpaquete.

Dependencias en tiempo de ejecución del -udev subpaquete.

URL del repositorio Git para usar con `abuild snapshot`. Si la rama por defecto del repositorio no es la deseada, se puede especificar una diferente agregando -b branch donde branch es la rama a comprobar (checkout).

Funciones

Las funciones especificadas aquí pueden estar presentes en cualquier archivo APKBUILD , pero con la excepción de package, no son estrictamente requeridas.

fetch

Esta función se llama para descargar los archivos remotos en source.

unpack

Esta función desempaqueta cualquier archivo en source a srcdir.

prepare

Prepara el código fuente en srcdir para ser compilado. La función prepare por defecto se asegura de que los directorios de compilación estén configurados correctamente y aplica cualquier archivo *.patch especificado en source. Debe llamar a default_prepare si escribe una función prepare personalizada.

build

Compila el código fuente en builddir. Debe implementar esta función usted mismo. Si no se requiere compilación, puede omitirla.

check

Ejecuta la suite de pruebas del paquete. Esta función debe implementarse a menos que se haya especificado !check en options.

package

Instala el paquete en pkgdir. Tenga en cuenta que pkgdir no es creado para usted; si este paquete no instala archivos (por ejemplo, un metapaquete), debe usar `mkdir -p "$pkgdir"` para omitir la fase de empaquetado.

Scripts de Instalación

Un script de instalación se ejecuta cuando apk(8) realiza una acción en un paquete. Un script de instalación debe escribirse en shell y debe tener una #!/bin/sh declaración de intérprete como la primera línea. La install variable debe contener los scripts de instalación necesarios por el paquete.

El script de instalación se ejecutará dentro del sistema de archivos raíz donde se está instalando el paquete. Se pasará un único argumento a los scripts, que es la versión del paquete que se está instalando (o desinstalando). Los scripts pre-upgrade y post-upgrade tendrán un segundo argumento adicional, que especifica la versión del paquete antes del proceso de actualización.

Las diferentes acciones para las que se pueden especificar scripts de instalación son las siguientes:

$pkgname.pre-install

Se ejecuta antes de que se instale el paquete. Si este script termina con un error (código de salida distinto de cero), apk(8) detendrá la instalación y el paquete no se instalará. Este script de instalación se usa típicamente para crear los usuarios o grupos necesarios como se describe en pkggroups y pkgusers.

$pkgname.

post-install
Se ejecuta después de que el paquete se instala. Si este script termina con un error (código de salida distinto de cero), apk(8) marcará el paquete como roto. El comando `apk fix` intentará volver a ejecutar el script post-install si esto
ocurre.

$pkgname.

pre-upgrade
Se ejecuta antes de que el paquete se actualice. Si este script termina con un error (código de salida distinto de cero), apk(8) marcará el paquete como
roto.

$pkgname.

post-upgrade
Se ejecuta después de que el paquete se actualiza. Si este script termina con un error (código de salida distinto de cero), apk(8) marcará el paquete como roto. El comando `apk fix` intentará volver a ejecutar el script post-upgrade si esto
ocurre.

$pkgname.

pre-deinstall
Se ejecuta antes de que el paquete se elimine del sistema. Si este script termina con un error (código de salida distinto de cero), apk(8) no eliminará el paquete del
sistema.

$pkgname.
