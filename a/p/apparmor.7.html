NOMBRE

AppArmor - mejora del kernel para confinar programas a un conjunto limitado de recursos.

DESCRIPCIÓN

AppArmor es una mejora del kernel para confinar programas a un conjunto limitado de recursos. El modelo de seguridad único de AppArmor es vincular atributos de control de acceso a programas en lugar de a usuarios.

El confinamiento de AppArmor se proporciona a través de perfiles cargados en el kernel mediante apparmor_parser(8), típicamente a través de la unidad systemd apparmor.service, que se utiliza de la siguiente manera:

# systemctl start apparmor
# systemctl reload apparmor

AppArmor puede operar en dos modos: enforcement (aplicación) y complain (queja o aprendizaje):

  • enforcement - Los perfiles cargados en modo de aplicación forzarán la aplicación de la política definida en el perfil, además de informar de los intentos de violación de la política a syslogd.
  • complain - Los perfiles cargados en modo "complain" no aplicarán la política. En su lugar, informarán de los intentos de violación de la política. Este modo es conveniente para desarrollar perfiles. Para gestionar el modo de queja para perfiles individuales, se pueden utilizar las utilidades aa-complain(8) y aa-enforce(8). Estas utilidades toman un nombre de programa como argumento.

Los perfiles se almacenan tradicionalmente en archivos en /etc/apparmor.d/ bajo nombres de archivo con la convención de reemplazar el / en las rutas de archivo por . (excepto el / raíz) para que los perfiles sean más fáciles de gestionar (por ejemplo, el perfil de /usr/sbin/nscd se llamaría usr.sbin.nscd).

Los perfiles se aplican a un proceso en el momento de exec(3) (como se ve a través de la llamada al sistema execve(2)): una vez que se carga un perfil para un programa, ese programa será confinado en la próxima exec(3). Si un proceso ya se está ejecutando bajo un perfil, cuando uno reemplaza ese perfil en el kernel, el perfil actualizado se aplica inmediatamente a ese proceso. Por otro lado, un proceso que ya se está ejecutando sin confinar no puede ser confinado.

AppArmor admite el sistema de archivos securityfs del kernel de Linux y pone a disposición la lista de los perfiles cargados actualmente; para montar el sistema de archivos:

# mount -tsecurityfs securityfs /sys/kernel/security
$ cat /sys/kernel/security/apparmor/profiles
/usr/bin/mutt
/usr/bin/gpg
   ...

Normalmente, el script init montará securityfs si aún no se ha hecho.

AppArmor también restringe qué operaciones privilegiadas puede ejecutar un proceso confinado, incluso si el proceso se está ejecutando como root. Un proceso confinado no puede llamar a las siguientes llamadas al sistema:

create_module(2) delete_module(2) init_module(2) ioperm(2)
iopl(2) ptrace(2) reboot(2) setdomainname(2)
sethostname(2) swapoff(2) swapon(2) sysctl(2)

Modo de queja

En lugar de denegar el acceso a recursos para los que el perfil no tiene una regla, AppArmor puede "permitir" el acceso y registrar un mensaje para la operación que lo desencadena. Esto se llama modo de queja. Es importante tener en cuenta que las reglas que están presentes en el perfil todavía se aplican, por lo que las reglas de permiso seguirán silenciando o forzando mensajes de auditoría, y las reglas de denegación seguirán resultando en denegaciones y silenciando mensajes de denegación (ver Desactivar el silenciamiento de auditoría de denegación si esto es un problema).

El modo de queja se puede utilizar para desarrollar perfiles de forma incremental a medida que se ejercita una aplicación. Los accesos registrados se pueden añadir al perfil y luego se puede ejercitar más la aplicación para descubrir adiciones adicionales que sean necesarias. Dado que AppArmor permite los accesos, la aplicación se comportará como si AppArmor no la estuviera confinando.

Advertencia el modo de queja no proporciona ninguna seguridad, solo auditoría, mientras está habilitado. No debe utilizarse en un entorno hostil, o los malos comportamientos pueden ser registrados y añadidos al perfil como si fueran accesos a recursos que la aplicación debería utilizar.

Nota el modo de queja puede ser muy ruidoso con perfiles nuevos o vacíos, pero con perfiles desarrollados podría no registrar nada si el perfil cubre bien el comportamiento de la aplicación. Ver Limitación de Tasa de Auditoría si el modo de queja está generando demasiados mensajes de registro.

Para establecer un perfil y cualquier perfil secundario o de sombrero que el perfil pueda contener en modo de queja, utilice

aa-complain /etc/apparmor.d/<la-aplicacion>

Para establecer manualmente un perfil específico en modo de queja, añada el marcador "complain" y luego recargue manualmente el perfil:

profile foo flags=(complain) { ... }

Tenga en cuenta que el marcador "complain" debe añadirse también manualmente a cualquier sombrero o perfil secundario del perfil, o seguirán utilizando el modo anterior.

Para habilitar el modo de queja globalmente, ejecute:

echo -n complain > /sys/module/apparmor/parameters/mode

o para configurarlo en el arranque, añada:

apparmor.mode=complain

como parámetro de arranque del kernel.

Advertencia Establecer el modo de queja globalmente deshabilita todas las protecciones de seguridad de apparmor. Puede ser útil durante la depuración o el desarrollo de perfiles, pero configurarlo selectivamente por perfil es más seguro.

ERRORES

Cuando un proceso confinado intenta acceder a un archivo al que no tiene permiso, el kernel informará de un mensaje a través de la auditoría, similar a:

audit(1386511672.612:238): apparmor="DENIED" operation="exec" 
  parent=7589 profile="/tmp/sh" name="/bin/uname" pid=7605 
  comm="sh" requested_mask="x" denied_mask="x" fsuid=0 ouid=0
audit(1386511672.613:239): apparmor="DENIED" operation="open" 
  parent=7589 profile="/tmp/sh" name="/bin/uname" pid=7605 
  comm="sh" requested_mask="r" denied_mask="r" fsuid=0 ouid=0
audit(1386511772.804:246): apparmor="DENIED" operation="capable"
  parent=7246 profile="/tmp/sh" pid=7589 comm="sh" pid=7589 
  comm="sh" capability=2  capname="dac_override"

Los permisos solicitados por el proceso se describen en operation= y denied_mask= (para archivos - capacidades, etc., se utiliza un formato de registro ligeramente diferente). Se informa el "nombre" y el ID de proceso del programa en ejecución, así como el nombre del perfil, incluido cualquier "sombrero" que pueda estar activo, separado por "//". ("Nombre" está entre comillas, porque el nombre del proceso se limita a 15 bytes; es el mismo que se informa a través de la contabilidad de procesos de Berkeley.)

Para procesos confinados que se ejecutan bajo un perfil que se ha cargado en modo de queja, la aplicación no tendrá lugar y los mensajes de registro informados a la auditoría tendrán el siguiente formato:

audit(1386512577.017:275): apparmor="ALLOWED" operation="open"
  parent=8012 profile="/usr/bin/du" name="/etc/apparmor.d/tunables/"
  pid=8049 comm="du" requested_mask="r" denied_mask="r" fsuid=1000 ouid=0
audit(1386512577.017:276): apparmor="ALLOWED" operation="open"
  parent=8012 profile="/usr/bin/du" name="/etc/apparmor.d/tunables/"
  pid=8049 comm="du" requested_mask="r" denied_mask="r" fsuid=1000 ouid=0

Si el demonio de auditoría (auditd) del espacio de usuario no se está ejecutando, el kernel enviará eventos de auditoría a klogd; klogd enviará los mensajes a syslog, que registrará los mensajes con la facilidad KERN. Por lo tanto, los mensajes de RECHAZO y PERMISO pueden ir a /var/log/audit/audit.log o /var/log/messages, dependiendo de la configuración local.

DEPURACIÓN

AppArmor proporciona algunas instalaciones para registrar más información, lo que puede ayudar a depurar perfiles.

Habilitar modo de depuración

Cuando el modo de depuración está habilitado, AppArmor registrará algunos mensajes adicionales en dmesg (no a través del subsistema de auditoría). Por ejemplo, los registros indicarán si se ha aplicado la limpieza del entorno.

Para habilitar el modo de depuración, ejecute:

echo 1 > /sys/module/apparmor/parameters/debug

o para configurarlo en el arranque, añada:

apparmor.debug=1

como parámetro de arranque del kernel.

Desactivar el silenciamiento de auditoría de denegación

Para desactivar el silenciamiento de auditoría de denegación, ejecute:

echo -n noquiet >/sys/module/apparmor/parameters/audit

o para establecerlo en el arranque, añada:

apparmor.audit=noquiet

como parámetro de arranque del kernel.

Forzar modo de auditoría

AppArmor puede registrar un mensaje por cada operación que active una regla configurada en la política. Esto se llama forzar modo de auditoría.

¡Advertencia! El modo de auditoría forzado puede ser extremadamente ruidoso incluso con un solo perfil, y mucho más si está habilitado globalmente.

Para establecer un perfil específico en modo de auditoría forzado, añada la marca "audit" :

profile foo flags=(audit) { ... }

Para habilitar el modo de auditoría forzado globalmente, ejecute:

echo -n all > /sys/module/apparmor/parameters/audit

o para establecerlo en el arranque, añada:

apparmor.audit=all

como parámetro de arranque del kernel.

Limitación de la tasa de auditoría

Si auditd no está en ejecución, para evitar perder demasiados de los mensajes de registro adicionales, probablemente tendrá que desactivar la limitación de la tasa haciendo:

echo 0 > /proc/sys/kernel/printk_ratelimit

Pero incluso así, el búfer de anillo del kernel puede desbordarse y podría perder mensajes.

De lo contrario, si auditd está en ejecución, consulte auditd(8) y auditd.conf(5).
