Condicionales de

Adjuntado

Los condicionales de adjuntado se usan durante los cambios de perfil para determinar si un perfil coincide con la transición de perfil propuesta. Los condicionales de adjuntado son opcionales, cómo y cuándo se aplican está determinado por las condiciones específicas

utilizadas.

Cuando se usan condicionales de adjuntado, los condicionales de adjuntado de todos los perfiles en el espacio de nombres serán evaluados. El perfil con el conjunto de adjuntos que resulte en la mejor coincidencia se convertirá en el nuevo perfil después de una operación de transición. Los adjuntos que no coincidan resultarán en que el perfil no esté disponible para la

transición.

Si no se especifican condicionales, el perfil solo se usará si una transición especifica explícitamente el nombre del

perfil.

Condicional de Adjuntado de

Ejecución

El condicional de adjuntado de ejecución gobierna qué tan bien el perfil coincide con un programa ejecutable. Este condicional solo se usa durante una operación de ejecución cuando la regla de ejecución coincidente especifica un tipo de transición px o cx (o sus derivados). El condicional de adjuntado de ejecución también será usado por tareas que están sin confinamiento ya que usan una regla de transición pix . Si no hay coincidencias de adjuntado, depende de la regla de ejecución determinar qué sucede (fallar u una opción de respaldo). Nota: ver el

perfil Nombre

para información sobre el uso del nombre del perfil como condicional de

adjuntado.

Los condicionales de adjuntado de ejecución pueden contener nombres de variables y coincidencia de patrones. Usan una heurística de coincidencia izquierda más larga para determinar el ganador en el caso de múltiples coincidencias en tiempo de ejecución. La implementación exacta de esta resolución es específica del kernel y ha mejorado con el tiempo, mientras mantiene la compatibilidad hacia atrás. Si la heurística no puede determinar un ganador entre múltiples coincidencias, la ejecución será denegada. Condicional de Adjuntado de Atributos

r - Modo de lectura
Permite al programa tener acceso de lectura al archivo o al listado del directorio. El acceso de lectura es necesario para los scripts de shell y otro contenido interpretado.
w - Modo de escritura
Permite al programa tener acceso de escritura al archivo. Los archivos y directorios deben tener este permiso si se van a desvincular (eliminar). El modo de escritura no es necesario en un directorio para renombrar o crear archivos dentro del directorio.

Este modo entra en conflicto con el modo de añadir.

a - Modo de añadir
Permite al programa tener un acceso de escritura limitado solo para añadir al archivo. El modo de añadir evitará que una aplicación abra el archivo para escritura a menos que pase el parámetro O_APPEND al abrirlo.

El modo entra en conflicto con el modo de escritura.

ux - Modo de ejecución sin confinamiento
Permite al programa ejecutar el programa sin que se le aplique ningún perfil de AppArmor.

Este modo es útil cuando un programa confinado necesita poder realizar una operación privilegiada, como reiniciar la máquina. Al colocar la sección privilegiada en otro ejecutable y conceder derechos de ejecución sin confinamiento, es posible eludir las restricciones obligatorias impuestas a todos los procesos confinados. Use este modo solo si el hijo absolutamente debe ejecutarse sin confinamiento y se debe usar LD_PRELOAD. Cualquier perfil que use este modo proporciona una seguridad insignificante. Reglas de enlace

Las reglas de enlace permiten especificar el permiso para formar un enlace duro como un par de enlace de destino. Si se especifica la condición de subconjunto, los permisos para acceder al archivo de enlace deben ser un subconjunto de los permisos del perfil para acceder al archivo de destino. Si existe una regla 'x' en el nuevo enlace, debe coincidir exactamente con el archivo original.

Por ejemplo.

/file1  r,
/file2  rwk,
/link*  rw,
link subset /link* -> /**,

La regla de enlace permite enlazar /link a /file1 o /file2 por nombre, sin embargo, como el archivo /link tiene permisos 'rw', no se le permite enlazar a /file1 porque eso otorgaría una ruta de acceso a /file1 con más permisos que los permisos 'r' que especifica el perfil.

Se permitiría un enlace de /link a /file2 porque los permisos 'rw' de /link son un subconjunto de los permisos 'rwk' de /file1.

La regla de enlace es equivalente a especificar el permiso de enlace 'l' como un permiso inicial sin otros permisos de acceso al archivo. Cuando se hace esto, se pueden especificar las opciones de la regla de enlace.

La siguiente regla de enlace es equivalente a la regla de archivo con el permiso 'l'

link /foo -> bar,
l /foo -> /bar,

Las reglas de archivo que especifican el permiso 'l' y no especifican los permisos de enlace extendido se mapean a reglas de enlace de la siguiente manera.

/foo l,
l /foo,
link subset /foo -> /**,

Reglas de red

AppArmor admite una mediación de red simple y de grano grueso. La regla de red restringe todas las operaciones basadas en socket(2) . La mediación realizada es una comprobación de grano grueso sobre si se puede crear, leer o escribir un socket de un tipo y familia dados. Las reglas de red netlink(7) solo pueden especificar el tipo 'dgram' y 'raw'.

Las reglas de red de AppArmor se acumulan de modo que los permisos de red otorgados son la unión de todos los permisos de las reglas de red enumeradas.

Las reglas de red de AppArmor son amplias y generales y se vuelven más restrictivas a medida que se especifica más información.

p. ej.

network,               # permite el acceso a todas las redes
network tcp,           # permite el acceso a tcp
network inet tcp,      # permite el acceso a tcp solo para direcciones inet4
network inet6 tcp,     # permite el acceso a tcp solo para direcciones inet6
network netlink raw,   # permite el acceso a AF_NETLINK SOCK_RAW

Permisos de red

Los permisos de la regla de red se implican cuando una regla no declara explícitamente una lista de acceso. De forma predeterminada, si una regla no tiene una lista de acceso, se implican todos los permisos que son compatibles con el conjunto especificado de condicionales locales y de pares.

Los permisos create, bind, listen, shutdown, getattr, setattr, getopt y setopt son permisos de socket local. Solo se aplican al socket local y no se pueden especificar en reglas que tengan un condicional de par. El permiso accept se aplica a la combinación de un socket local y uno remoto. Los permisos connect, send y receive son permisos de socket remoto.

Mediación de la familia inet/inet6

AppArmor admite una mediación de grano fino de las familias inet e inet6 mediante el uso de los condicionales ip y port. El condicional ip acepta tanto IPv4 como IPv6 usando la representación regular de cuatro octetos separados por '.' para IPv4 y ocho grupos de cuatro números hexadecimales separados por ':' para IPv6. Los ceros iniciales contiguos pueden reemplazarse por '::' una vez. En un socket conectado, el emisor y el receptor no necesitan ser especificados en las llamadas al sistema recvfrom y sendto. En ese caso, y con sockets sin límite, la dirección IP es none, o desconocida. Las direcciones IP desconocidas o sin asignar se representan en la política por la palabra clave 'none'. Cuando se omite el condicional ip, se permitirán todas las direcciones IP: IPv4, IPv6 y none. Si se usa INADDR_ANY o in6addr_any, el condicional ip se puede omitir o se pueden representar por:

network ip=::,         # permite in6addr_any
network ip=0.0.0.0;    # permite INADDR_ANY

Las reglas de red admiten la especificación de direcciones IP locales y remotas, puertos y rangos de puertos.

Reglas de montaje

AppArmor admite la mediación de montaje y permite especificar tipos de sistema de archivos y banderas de montaje. La sintaxis de las reglas de montaje en AppArmor se basa en la sintaxis del comando mount(8) . Las reglas de montaje deben contener una de las palabras clave mount, remount o umount, pero todas las condiciones de montaje son opcionales. Se asume que los condicionales opcionales no especificados coinciden con todas las entradas (p. ej., no especificar fstype significa que se coinciden con todos los fstype). Debido a la complejidad del comando mount y a la forma en que se pueden especificar las opciones, AppArmor permite especificar los condicionales de tres maneras diferentes:

1.
Si un condicional se especifica usando '=', la regla solo otorga permiso para los montajes que coincidan con las opciones especificadas exactamente. Por ejemplo, una política de AppArmor con la siguiente regla: 
mount options=ro /dev/foo -> /mnt/,

Coincidiría con:

$ mount -o ro /dev/foo /mnt

pero no con ninguna de estas:

$ mount -o ro,atime /dev/foo /mnt
$ mount -o rw /dev/foo /mnt
2.
Si un condicional se especifica usando 'in', la regla otorga permiso para los montajes que coincidan con cualquier combinación de las opciones especificadas. Por ejemplo, si una política de AppArmor tiene la siguiente regla: 
mount options in (ro,atime) /dev/foo -> /mnt/,

todos estos comandos de montaje coincidirían:

$ mount -o ro /dev/foo /mnt
$ mount -o ro,atime /dev/foo /mnt
$ mount -o atime /dev/foo /mnt

pero ninguno de estos:

$ mount -o ro,sync /dev/foo /mnt
$ mount -o ro,atime,sync /dev/foo /mnt
$ mount -o rw /dev/foo /mnt
$ mount -o rw,noatime /dev/foo /mnt
$ mount /dev/foo /mnt
3.
Si se especifican múltiples condicionales en una sola regla de montaje, la regla otorga permiso para cada conjunto de opciones. Esto proporciona una forma abreviada al escribir reglas de montaje que podría ayudar a dividir lógicamente un condicional. Por ejemplo, si una política de AppArmor tiene la siguiente regla: 
mount options=ro options=atime,

ambos de estos comandos de montaje coincidirían:

$ mount -o ro /dev/foo /mnt
$ mount -o atime /dev/foo /mnt

pero este no:

$ mount -o ro,atime /dev/foo /mnt

Tenga en cuenta que las reglas de montaje separadas son distintas y las opciones no se acumulan. Por ejemplo, estas reglas de montaje de AppArmor:

mount options=ro,
mount options=atime,

no son equivalentes a ninguna de estas reglas de montaje:

mount options=(ro,atime),
mount options in (ro,atime),

Para ayudar a aclarar la flexibilidad y complejidad de las reglas de montaje, aquí hay algunas reglas de ejemplo con los comandos de coincidencia correspondientes:

permite montar /dev/foo en cualquier lugar con cualquier opción. Algunos comandos de montaje que coinciden:

$ mount -t ext3 /dev/foo /mnt
$ mount -t vfat /dev/foo /mnt
$ mount -o ro,atime,noexec,nodiratime /dev/foo /srv/some/mountpoint
mount options=ro /dev/foo,
permite montar /dev/foo en cualquier lugar, como solo lectura. Algunos comandos de montaje que coinciden:

Reglas de mount

AppArmor admite la mediación de llamadas al sistema mount(2). Las reglas de AppArmor para mount se acumulan, por lo que los permisos de mount concedidos son la unión de todos los permisos de las reglas de mount listadas.

Los permisos de mount se implican cuando una regla no especifica explícitamente una lista de acceso. Por defecto, todos los permisos de mount están implícitos.

Las reglas de mount pueden ser especificadas para diferentes partes de la llamada al sistema mount(2) y para diferentes combinaciones de opciones. Las reglas se pueden especificar para el dispositivo, el punto de montaje, el tipo de sistema de archivos y las opciones de montaje.

Las reglas de mount se pueden utilizar para permitir o denegar el montaje de dispositivos, sistemas de archivos y puntos de montaje específicos. También se pueden utilizar para restringir las opciones de montaje permitidas.

A continuación, se muestran algunos ejemplos de reglas de mount:

mount /dev/foo /mnt/bar,
Permite montar /dev/foo en /mnt/bar.
mount /dev/foo /mnt/**,
Permite montar /dev/foo en cualquier directorio debajo de /mnt/. Por ejemplo, se permitirían los siguientes montajes:
$ mount /dev/foo /mnt/1
$ mount /dev/foo /mnt/subdir/2
mount /dev/foo/** /mnt/,
Permite montar cualquier dispositivo debajo de /dev/foo en /mnt/. Por ejemplo, se permitirían los siguientes montajes:
$ mount /dev/foo/a /mnt
$ mount /dev/foo/b/c /mnt
mount options=ro /dev/foo /mnt/,
Permite montar /dev/foo en /mnt/ como solo lectura.
mount options=ro /dev/foo /mnt/1 mount options=atime /dev/foo /mnt/2,
Permite montar /dev/foo en /mnt/1 como solo lectura y montar /dev/foo en /mnt/2 con la opción atime. Esto se considera como dos reglas diferentes. Coincidencias:
$ mount -o ro /dev/foo /mnt/1
$ mount -o atime /dev/foo /mnt/2
mount -> /mnt/**,
Permite montar cualquier cosa debajo de un directorio en /mnt/**. Algunos comandos de montaje coincidentes:
$ mount /dev/foo1 /mnt/1
$ mount -o ro,atime,noexec,nodiratime /dev/foo2 /mnt/deep/path/foo2
mount options=ro -> /mnt/**,
Permite montar cualquier cosa debajo de /mnt/**, como solo lectura. Algunos comandos de montaje coincidentes:
$ mount -o ro /dev/foo1 /mnt/1
$ mount -o ro /dev/foo2 /mnt/deep/path/foo2
mount fstype=ext3 options=(rw,atime) /dev/sdb1 -> /mnt/stick/,
Permite montar un sistema de archivos ext3 en /dev/sdb1 en /mnt/stick como lectura/escritura y utilizando tiempos de acceso a inodos. Solo coincide con:
$ mount -o rw,atime /dev/sdb1 /mnt/stick
mount options=(ro, atime) options in (nodev, user) /dev/foo -> /mnt/,
Permite montar /dev/foo en /mmt/ como solo lectura y utilizando tiempos de acceso a inodos, o permite montar /dev/foo en /mnt/ con alguna combinación de 'nodev' y 'user'. Solo coincide con:
$ mount -o ro,atime /dev/foo /mnt
$ mount -o nodev /dev/foo /mnt
$ mount -o user /dev/foo /mnt
$ mount -o nodev,user /dev/foo /mnt

Reglas de colas de mensajes

AppArmor admite la mediación de colas de mensajes POSIX y SYSV.

Los permisos de colas de mensajes de AppArmor se implican cuando una regla no especifica explícitamente una lista de acceso. Por defecto, se implican todos los permisos de colas de mensajes.

Los permisos de colas de mensajes de AppArmor se vuelven más restrictivos a medida que se especifica más información. La política se puede especificar determinando su modo de acceso, tipo, etiqueta y nombre de la cola de mensajes.

Con respecto a los modos de acceso, 'r' y 'read' se utilizan para leer mensajes de la cola. 'w' y 'write' se utilizan para escribir en la cola de mensajes. 'create' se utiliza para crear la cola de mensajes y 'open' se utiliza para obtener el identificador de la cola de mensajes cuando la cola ya está creada. 'delete' se utiliza para eliminar la cola de mensajes. Los modos de acceso para obtener y establecer atributos de la cola de mensajes son 'setattr' y 'getattr'.

El tipo de política puede ser 'posix' o 'sysv'. Esta información es relevante cuando no se especifica el nombre de la cola de mensajes y, cuando se especifica, se puede inferir por el nombre de la cola, ya que el nombre de las colas de mensajes para posix debe comenzar con '/', y la clave de las colas de mensajes para SYSV debe ser un entero positivo.

La etiqueta de política es la etiqueta asignada a la cola de mensajes cuando se crea.

El nombre de la cola de mensajes puede ser una cadena que comience con '/' si el tipo es POSIX, o un entero positivo si el tipo es SYSV. Si el tipo no se especifica, se inferirá por el nombre de la cola.

Ejemplos de reglas de colas de mensajes de AppArmor:

# Permite todo el acceso a colas de mensajes
mqueue,
# Permite explícitamente todo el acceso a colas de mensajes,
mqueue (create, open, delete, read, write, getattr, setattr),
# Deniega explícitamente el uso de colas de mensajes
deny mqueue,
# Permite todo el acceso para la cola POSIX de nombre /bar
mqueue type=posix /bar,
# Permite permiso de creación para una cola SYSV con etiqueta foo
mqueue create label=foo 123,

Reglas de namespaces de usuario

Los namespaces de usuario forman parte de muchas soluciones de sandboxing y contenerización. Proporcionan una forma para que un proceso root no del sistema sea root dentro del contenedor. Desafortunadamente, esto abre una superficie de ataque en el kernel y ha sido parte de varias cadenas de exploits. Como tal, AppArmor se puede utilizar para restringir la creación de namespaces de usuario a procesos seleccionados.

Los permisos de namespaces de usuario se implican cuando una regla no especifica explícitamente una lista de acceso. La regla se vuelve más restrictiva a medida que se especifica más información.

Nota: la creación de namespaces de usuario puede estar restringida para que no esté disponible para procesos no privilegiados sin restricciones. Si este es el caso, cualquier proceso que intente crear namespaces de usuario requerirá un perfil que permita los permisos necesarios.

create
Permite la creación de namespaces de usuario.

Ejemplos de reglas de userns:

# Permite todos los permisos de userns
userns,
# Permite la creación de un userns
userns create,

Reglas de IO_URing

AppArmor admite la mediación de la nueva interfaz de IO de alta velocidad de Linux. Actualmente, hay una mediación limitada a solo unos pocos permisos por el momento.

Los permisos de IO Uring se implican cuando una regla no especifica explícitamente una lista de acceso. La regla se vuelve más restrictiva a medida que se especifica más información.

Nota: el acceso a io_uring puede estar restringido para que no esté disponible para procesos no privilegiados sin restricciones. Si este es el caso, cualquier proceso que intente usar io_uring requerirá un perfil que permita los permisos de io_uring necesarios.

sqpoll
Permite que la tarea confinada por el perfil genere un hilo de sondeo de io_uring.
override_creds
Otorga a la tarea confinada por el perfil la capacidad de anular (cambiar) sus credenciales a la etiqueta especificada, al ejecutar una operación de io_uring.

Ejemplos de reglas de IO_URING:

# Permite operaciones de io_uring
io_uring,

Reglas de Pivot Root

AppArmor media el cambio del sistema de archivos raíz a través de la llamada al sistema pivot_root(2). La sintaxis de las reglas 'pivot_root' en AppArmor se basa en los parámetros de la llamada al sistema pivot_root(2), con la notable excepción de que el orden se invierte. La ruta correspondiente al parámetro put_old de pivot_root(2) se especifica opcionalmente en la regla 'pivot_root' utilizando el prefijo 'oldroot='.

Las reglas 'pivot_root' de AppArmor pueden especificar una transición de perfil que ocurra durante la llamada al sistema pivot_root(2). Tenga en cuenta que actualmente, esta característica no es compatible con ningún kernel. Cuando esta característica sea compatible, AppArmor solo transicionará el proceso que llama a pivot_root(2) al nuevo perfil.

Las rutas especificadas en las reglas 'pivot_root' deben terminar con '/' ya que son directorios.

Aquí hay algunos ejemplos de reglas de 'pivot_root':

# Permite cualquier pivote
pivot_root,
# Permite pivotar a cualquier directorio raíz nuevo y colocar el directorio raíz antiguo
# en /mnt/root/old/
pivot_root oldroot=/mnt/root/old/,
# Permite pivotar el directorio raíz a /mnt/root/
pivot_root /mnt/root/,
# Permite pivotar a /mnt/root/ y colocar el directorio raíz antiguo en
# /mnt/root/old/
pivot_root oldroot=/mnt/root/old/ /mnt/root/,
# Permite pivotar a /mnt/root/, colocar el directorio raíz antiguo en
# /mnt/root/old/ y transicionar al perfil /mnt/root/sbin/init
pivot_root oldroot=/mnt/root/old/ /mnt/root/ -> /mnt/root/sbin/init,

Reglas de PTrace

AppArmor admite la mediación de ptrace(2). Las reglas de PTrace de AppArmor se acumulan, de modo que los permisos de PTrace concedidos son la unión de todos los permisos de las reglas de PTrace listadas.

Los permisos de PTrace de AppArmor se implican cuando una regla no especifica explícitamente una lista de acceso. Por defecto, todos los permisos de PTrace están implícitos.

Los permisos trace y tracedby rigen ptrace(2), mientras que read y readby rigen ciertos accesos al sistema de archivos proc(5), kcmp(2), futexes (get_robust_list(2)) y eventos de traza perf.

Para que una operación de ptrace sea permitida, el perfil del proceso que rastrea y el perfil de la tarea objetivo deben tener ambos los permisos correctos. Por ejemplo, el perfil del proceso que se adjunta a otra tarea debe tener el permiso trace para el perfil de la tarea objetivo, y la tarea que se rastrea debe tener el permiso tracedby para el perfil del proceso que rastrea.

Ejemplos de reglas de PTrace de AppArmor:

# Permite todo el acceso PTrace
ptrace,
# Permite explícitamente todo el acceso PTrace,
ptrace (read, readby, trace, tracedby),
# Deniega explícitamente el uso de ptrace(2)
deny ptrace (trace),
# Permite que procesos sin restricciones (por ejemplo, un depurador) nos hagan ptrace
ptrace (readby, tracedby) peer=unconfined,
# Permite ptrace de un proceso que se ejecuta bajo el perfil /usr/bin/foo
ptrace (trace) peer=/usr/bin/foo,

Reglas de señal

AppArmor admite la mediación de signal(7). Las reglas de señal de AppArmor se acumulan, de modo que los permisos de señal concedidos son la unión de todos los permisos de las reglas de señal listadas.

Los permisos de señal de AppArmor se implican cuando una regla no especifica explícitamente una lista de acceso. Por defecto, todos los permisos de señal están implícitos.

Para que el envío de una señal sea permitido, el perfil del proceso que envía la señal y el perfil de la tarea objetivo deben tener ambos los permisos correctos. Por ejemplo, el perfil de un proceso que envía una señal a otra tarea debe tener el permiso send para el perfil de la tarea objetivo, y la tarea que recibe la señal debe tener un permiso receive para el perfil del proceso que envía.

Ejemplos de reglas de señal de AppArmor:

# Permite todo el acceso a señales
signal,
# Deniega explícitamente el envío de señales HUP e INT
deny signal (send) set=(hup, int),
# Permite que procesos sin restricciones nos envíen señales
signal (receive) peer=unconfined,
# Permite el envío de señales a un proceso que se ejecuta bajo el perfil /usr/bin/foo
# perfil
signal (send) peer=/usr/bin/foo,
# Permite comprobar la existencia de PID
signal (receive, send) set=("exists"),
# Permite que nos enviemos señales a nosotros mismos usando la variable integrada @{profile_name}
signal peer=@{profile_name},
# Permite dos señales en tiempo real
signal set=(rtmin+0 rtmin+32),

Reglas de DBus

AppArmor admite la mediación de DBus. La mediación se realiza en conjunción con el demonio DBus. El demonio DBus verifica que las comunicaciones a través del bus estén permitidas por la política de AppArmor.

Las reglas de DBus de AppArmor se acumulan, de modo que los permisos de DBus concedidos son la unión

de todos los permisos de reglas DBus listados.

Las reglas DBus de AppArmor son amplias y generales y se vuelven más restrictivas a medida que se especifica más información. La política puede especificarse hasta el nivel del miembro de la interfaz (nombre del método o de la señal), sin embargo, el contenido de los mensajes no se examina.

Algunos permisos DBus de AppArmor no son compatibles con todas las reglas DBus de AppArmor. El permiso 'bind' no puede usarse en reglas de mensajes. Los permisos 'send' y 'receive' no pueden usarse en reglas de servicio. El permiso 'eavesdrop' no puede usarse en reglas que contengan cualquier condicional fuera del condicional 'bus'.

'r' y 'read' son sinónimos de 'receive'. 'w' y 'write' son sinónimos de 'send'. 'rw' es un sinónimo tanto para 'send' como para 'receive'.

Se implican permisos DBus de AppArmor cuando una regla no declara explícitamente una lista de acceso. De forma predeterminada, se implican todos los permisos DBus. Solo se implican permisos de mensaje para reglas de mensaje y solo se implican permisos de servicio para reglas de servicio.

Ejemplos de reglas DBus de AppArmor:

# Permitir todo el acceso a DBus
dbus,
# Permitir explícitamente todo el acceso a DBus,
dbus (send, receive, bind),
# Denegar el acceso de envío/recepción/enlace al bus de sesión
deny dbus bus=session,
# Permitir el acceso de enlace para un nombre particular en cualquier bus
dbus bind name=com.example.ExampleName,
# Permitir el acceso de recepción para una ruta e interfaz particulares
dbus receive path=/com/example/path interface=com.example.Interface,
# Denegar el acceso de envío/recepción al bus del sistema para una interfaz particular
deny dbus bus=system interface=com.example.ExampleInterface,
# Permitir el acceso de envío para una ruta, interfaz, miembro y par de
# nombres de pares particulares:
dbus send
     bus=session
     path=/com/example/path
     interface=com.example.Interface
     member=ExampleMethod
     peer=(name=(com.example.ExampleName1|com.example.ExampleName2)),
# Permitir el acceso de recepción para todos los pares sin confinamiento
dbus receive peer=(label=unconfined),
# Permitir la interceptación en el bus del sistema
dbus eavesdrop bus=system,
# Permitir y auditar toda la interceptación
audit dbus eavesdrop,

Reglas de sockets Unix

AppArmor admite la mediación de granularidad fina de sockets abstractos y anónimos de dominio Unix. Los sockets de dominio Unix con rutas del sistema de archivos son mediados mediante reglas de acceso a archivos.

Los sockets abstractos de dominio Unix son una extensión de Linux no portable de los sockets de dominio Unix, véase unix(7) para más información.

Rutas de direcciones de sockets Unix

El componente sun_path (también conocido como la dirección del socket) de un socket de dominio Unix se especifica mediante el

condicional addr=

. Si no se especifica un condicional de dirección como parte de una regla, la regla coincide tanto con sockets abstractos como con anónimos.

En apparmor, la dirección de un socket abstracto de dominio Unix comienza con el carácter @ , de manera similar a cómo se reportan (como rutas) por netstat -x. A continuación sigue la dirección, que puede contener coincidencias de patrones y cualquier carácter, incluido el carácter nulo. En apparmor, los caracteres nulos deben especificarse usando una secuencia de escape \000 o \x00. La coincidencia de patrones es la misma que la usada por la coincidencia de rutas de archivos, por lo que * no coincidirá con / aunque no tenga un significado especial dentro de un nombre de socket abstracto. Por ejemplo.

unix addr=@*,

Los sockets de dominio Unix autobound tienen una sun_path asignada por el kernel, por lo que no es posible especificar una dirección basada en la política. El autobinding de los sockets puede controlarse especificando la palabra clave especial auto . Por ejemplo.

unix addr=auto,

Para indicar que la regla solo se aplica al autobinding de sockets de dominio Unix. Es importante notar que esto solo se aplica al permiso bind , ya que una vez que el socket está enlazado a una dirección, es indistinguible de un socket que tenga un addr enlazado con un nombre especificado. Cuando la palabra clave auto se usa con otros permisos o como parte de un peer addr será reemplazada por un patrón que pueda coincidir con un socket autobound. Por ejemplo. Para algunos kernels

unix rw addr=auto,

se transforma en

unix rw addr=@[a-f0-9][a-f0-9][a-f0-9][a-f0-9][a-f0-9],

Es importante notar que este patrón puede coincidir con sockets abstractos que no fueron autobound pero que tienen un addr que se ajuste a lo que es generado por el kernel al hacer autobinding de un socket.

Los sockets de dominio Unix anónimos no tienen una sun_path asociada con la dirección del socket, sin embargo, puede especificarse con la palabra clave especial none para indicar que la regla solo se aplica a sockets de dominio Unix anónimos. Por ejemplo.

unix addr=none,

Si no se especifica el componente de dirección de una regla, la regla se aplica a sockets autobound, abstractos y anónimos.

Permisos de sockets Unix

Las reglas de sockets de dominio Unix se acumulan de modo que los permisos de socket Unix concedidos son la unión de todos los permisos de reglas Unix listados.

Las reglas de sockets de dominio Unix son amplias y generales y se vuelven más restrictivas a medida que se especifica más información. La política puede especificarse hasta el nivel de la dirección del socket (también conocida como sun_path) y de la etiqueta. El contenido de la comunicación no se examina.

Se implican permisos de reglas de sockets Unix cuando una regla no declara explícitamente una lista de acceso. De forma predeterminada, si una regla no tiene una lista de acceso, se implican todos los permisos que sean compatibles con el conjunto especificado de condicionales locales y de pares.

Los permisos create, bind, listen, shutdown, getattr, setattr, getopt y setopt son permisos de socket locales. Solo se aplican al socket local y no pueden especificarse en reglas que tengan un componente de par. El permiso accept se aplica a la combinación de un socket local y uno de par. Los permisos connect, send y receive son permisos de socket de par.

Solo se aplicarán los permisos de socket de par a reglas que no especifiquen permisos y que contengan un componente de par.

Ejemplos de reglas de sockets de dominio Unix:

# Permitir todos los permisos a los sockets Unix
unix,
# Permitir explícitamente todos los permisos Unix
unix (create, listen, accept, connect, send, receive, getattr, setattr, setopt, getopt),
# Denegar explícitamente el acceso a sockets Unix
deny unix,
# Permitir la creación y el uso de sockets abstractos y anónimos para profile_name
unix peer=(label=@{profile_name}),
# Permitir la recepción a través de sockets Unix desde unconfined
unix (receive) peer=(label=unconfined),
# Permitir getattr y shutdown en sockets anónimos
unix (getattr, shutdown) addr=none,
# Permitir la conexión, recepción y envío SOCK_STREAM en un socket abstracto @bar
# con un par ejecutándose bajo el perfil '/foo'
unix (connect, receive, send) type=stream peer=(label=/foo,addr="@bar"),
# Permitir aceptar conexiones y recibir desde un par ejecutándose bajo
# el perfil '/bar' en el socket abstracto '@foo'
unix (accept, receive) addr=@foo peer=(label=/bar),

Autobinding de sockets de dominio Unix abstractos

Los sockets de dominio Unix abstractos pueden hacer autobinding a una dirección. La dirección de autobinding es una cadena única de 5 dígitos de números decimales, por ejemplo. @00001. No hay nada que impida a una tarea enlazar manualmente a direcciones con un patrón similar, por lo que es imposible identificar de forma fiable las direcciones de autobinding de una dirección regular.

Interacción de las reglas de red y las reglas de sockets de dominio Unix de granularidad fina

Las reglas de red de granularidad gruesa también pueden usarse para controlar los sockets de dominio Unix. Cuando está disponible la mediación de granularidad fina de los sockets de dominio Unix, la regla de red de granularidad gruesa se mapea a la regla de socket Unix equivalente.

Por ejemplo.

network unix,  =>  unix,
network unix stream,   =>  unix stream,

Sin embargo, las reglas de mediación de granularidad fina no pueden convertirse sin pérdidas de nuevo a la regla de red de granularidad gruesa; por ejemplo.

unix bind addr=@example,

No tiene una coincidencia exacta bajo las reglas de red de granularidad gruesa, la coincidencia más cercana es la regla de permiso mucho más amplia de

network unix,

Reglas change_profile

AppArmor admite transiciones de perfil autodirigidas a través de la API change_profile. Las reglas change_profile controlan qué permisos para qué perfiles puede hacer una tarea confinada. El nombre del perfil puede contener coincidencias de patrones de apparmor para especificar diferentes perfiles.

change_profile -> **,

La API change_profile permite que la transición se retrase hasta que una tarea ejecute otra aplicación. Si se especifica una transición de regla exec para la aplicación y se usa la API change_profile para hacer una transición en el momento de la ejecución, la transición especificada por la API change_profile tiene prioridad.

El permiso change_profile puede restringir a qué perfiles se puede transicionar basándose en el nombre del ejecutable especificando la condición exec.

change_profile /bin/bash -> new_profile,

La restricción del perfil de transición a un ejecutable dado en el momento de la ejecución solo es útil cuando la tarea actual tiene permitido tomar decisiones dinámicas sobre cuál debería ser el confinamiento, pero el conjunto de decisiones necesita ser controlado. Se puede usar una lista de perfiles o múltiples reglas para especificar los perfiles en el conjunto. Por ejemplo.

change_profile /bin/bash -> {new_profile1,new_profile2,new_profile3},

Se puede usar una regla exec para especificar una transición para el ejecutable, si la transición debe permitirse incluso si no se ha usado la API change_profile para seleccionar una transición para las disponibles en el conjunto de reglas change_profile. Por ejemplo.

/bin/bash Px -> new_profile1,
change_profile /bin/bash -> {new_profile1,new_profile2,new_profile3},

El modo exec dicta si se deben usar o no las rutinas unsafe_exec del kernel de Linux para limpiar el entorno, de manera similar a los programas setuid. (Véase ld.so(8) para algo de información sobre la limpieza del entorno setuid/setgid.) El modo safe configura la limpieza del entorno para que ocurra cuando se ejecuta la nueva aplicación, y el modo unsafe desactiva el requisito de AppArmor para la limpieza del entorno (el kernel y/o la libc aún pueden requerir la limpieza del entorno). Un modo exec solo puede especificarse cuando está presente una condición exec.

change_profile safe /bin/bash -> new_profile,

No todos los kernels soportan el modo safe y el analizador degradará las reglas al modo unsafe en esa situación. Si no se especifica un modo exec, el valor predeterminado es el modo safe en kernels que lo soporten.

Regla all

La regla all se usa para añadir una regla genérica para todos los tipos de reglas soportados. Esto es útil cuando la política quiere definir una lista negra en lugar de una lista blanca, pero también puede ser útil para añadir un calificador de acceso a todas las reglas.

Por ejemplo. Lista negra

allow all,
# comienzo de la lista negra
deny file,
deny unix,

Por ejemplo. Añadir un calificador de auditoría

audit access all,

Reglas rlimit

AppArmor puede establecer y controlar los límites de recursos asociados con un perfil, como se describe en la página del manual setrlimit(2).

Los controles rlimit de AppArmor permiten establecer límites, restringir sus cambios y auditar estas acciones. La aplicación de los límites establecidos es manejada por el mecanismo de aplicación del kernel estándar para rlimits y no resultará en un mensaje auditado de apparmor si el límite se aplica.

Si un perfil no tiene una regla rlimit asociada con un rlimit determinado, el rlimit se deja intacto y se permite el acceso regular, incluido el cambio del límite. Sin embargo, si el perfil establece un rlimit, se verifica el límite actual y, si es mayor que el límite especificado en la regla, se cambiará al límite especificado.

Las reglas rlimit de AppArmor controlan el límite duro de una aplicación y aseguran que si el límite duro se reduce, el límite blando no exceda el valor del límite duro.

Por ejemplo.

set rlimit data <= 100M,
set rlimit nproc <= 10,
set rlimit nice <= 5,

Notas sobre la expansión de variables y el carácter /

Es importante tener en cuenta que la forma en que AppArmor realiza la expansión de variables depende del contexto en el que se utiliza una variable. Cuando se expande una variable, puede resultar en una cadena con varios caracteres de ruta uno al lado del otro, de una manera que no es evidente al observar la política.

Por ejemplo.

Dada la siguiente definición de variable y regla

@{HOME}=/home/*/ file rw @{HOME}/*,

La expansión de la variable resulta en una regla de

file rw /home/*//*.

Cuando esto ocurre en un contexto donde se espera una ruta, AppArmor canonizará la ruta colapsando caracteres / consecutivos en uno solo. Para el ejemplo anterior, esto sería

file rw /home/*/*,

Hay una excepción a esta regla, cuando los caracteres / consecutivos están al principio de una ruta, esto indica un espacio de nombres posix y los caracteres no se colapsarán.

Por ejemplo.

@{HOME}=/home/*/ file rw /@{HOME}/*,

resultará en una expansión de

file rw //home/*//*,

que se colapsa a

file rw //home/*/*,

Nota: que el // inicial en el ejemplo anterior no se colapsa a un solo /. Sin embargo, el segundo // (que también se vio en el primer ejemplo) se colapsa.

Reglas de alias

AppArmor también proporciona reglas de alias para remapear rutas para diseños específicos del sitio. Son una forma alternativa de reescritura de rutas para usar variables y se realizan después de la resolución de variables. Las reglas de alias deben ocurrir dentro del preámbulo del perfil. Los alias a nivel de sistema se encuentran en /etc/apparmor.d/tunables/alias, que se incluye en /etc/apparmor.d/tunables/global. /etc/apparmor.d/tunables/global generalmente se incluye al principio de un perfil de AppArmor.

Globbing (AARE)

Los recursos de archivos y otros parámetros que aceptan una AARE se pueden especificar con una sintaxis de globbing similar a la utilizada por los shells populares, como csh(1), bash(1), zsh(1).

*
puede sustituir cualquier número de caracteres, excepto '/'
**
puede sustituir cualquier número de caracteres, incluido '/'
?
puede sustituir cualquier carácter individual, excepto '/'
[abc]
sustituirá el carácter individual a, b o c
[a-c]
sustituirá el carácter individual a, b o c
[^a-c]
sustituirá cualquier carácter individual que no coincida con a, b o c
{ab,cd}
se expandirá a una regla para que coincida con ab, una regla para que coincida con cd

También puede incluir variables.

@{variable}
se expandirá a todos los valores asignados a la variable dada.

Cuando AppArmor busca un directorio, la ruta que se busca terminará con una barra (por ejemplo, /var/tmp/); de lo contrario, no terminará con una barra. Solo las reglas que coincidan con una barra final coincidirán con directorios. Algunos ejemplos, ninguno de los cuales coincide con el directorio /tmp/ en sí, son:

/tmp/*
Archivos directamente en /tmp.
/tmp/*/
Directorios directamente en /tmp.
/tmp/**
Archivos y directorios en cualquier lugar debajo de /tmp.
/tmp/**/
Directorios en cualquier lugar debajo de /tmp.

Calificadores de regla

Hay varios calificadores de regla que se pueden aplicar a las reglas de permisos. Los calificadores de regla pueden modificar la regla y/o los permisos dentro de la regla.

priority
Especifica la prioridad de la regla. Actualmente, el rango permitido es de -1000 a 1000, con una prioridad predeterminada de 0. Las reglas con mayor prioridad tienen preferencia y anularán por completo los permisos de las reglas de menor prioridad donde se superponen. Cuando las reglas se superponen parcialmente, los permisos de la regla de mayor prioridad anularán por completo las reglas de menor prioridad dentro de la superposición. Dentro de un nivel de prioridad dado, las reglas que se superponen acumularán permisos de la manera estándar de apparmor.
allow
Especifica que las solicitudes de permisos que coinciden con la regla están permitidas. Este es el valor predeterminado para las reglas y no necesita especificarse. Entra en conflicto con el calificador deny.
audit
Especifica que las solicitudes de permisos que coinciden con la regla deben registrarse en el registro de auditoría.
deny
Especifica que las solicitudes de permisos que coinciden con la regla deben ser denegadas sin registrarse. Se puede combinar con 'audit' para habilitar el registro. Entra en conflicto con el calificador allow.
owner
Especifica que la tarea debe tener el mismo euid/fsuid que el objeto al que se hace referencia en la verificación de permisos.

Bloques de calificadores

Los calificadores de regla se pueden aplicar a varias reglas a la vez agrupando las reglas en un bloque de reglas.

audit {
   /foo r,
   network,
}

Mecanismo #include

AppArmor proporciona un mecanismo de abstracción sencillo para agrupar requisitos de acceso comunes; esta abstracción es una forma extremadamente flexible de otorgar derechos específicos del sitio y simplifica enormemente la escritura de nuevos perfiles de AppArmor al ensamblar los bloques de construcción necesarios para cualquier programa dado.

El uso de '#include' se basa directamente en cpp(1); su uso reemplazará la declaración '#include' con el contenido del archivo especificado. El '#' inicial es opcional y la palabra clave '#include' puede ir seguida de una opción condicional 'if exists' que especifica que la compilación del perfil debe continuar si el archivo o directorio especificado no se encuentra.

#include "/absolute/path" especifica que se debe usar /absolute/path. #include "relative/path" especifica que se debe usar relative/path, donde la ruta es relativa al directorio de trabajo actual. #include <magic/path> es el uso más común; cargará magic/path relativo a un directorio especificado a apparmor_parser(8). /etc/apparmor.d/ es el valor predeterminado de AppArmor.

Los perfiles de AppArmor proporcionados siguen varias convenciones; las abstracciones almacenadas en /etc/apparmor.d/abstractions/ son algunos clústeres grandes que se utilizan en la mayoría de los perfiles. A continuación se presentan breves descripciones de cómo se utilizan algunas de las abstracciones.

abstractions/audio
Incluye accesos a archivos de dispositivo utilizados para aplicaciones de audio.
abstractions/authentication
Incluye acceso a archivos y servicios típicamente necesarios para servicios que realizan autenticación de usuarios.
abstractions/base
Incluye archivos que deben ser legibles y escribibles en todos los perfiles.
abstractions/bash
Incluye muchos archivos utilizados por bash; útil para shells interactivos y programas que llaman a system(3).
abstractions/consoles
Incluye acceso de lectura y escritura a los archivos de dispositivo que controlan la consola virtual, sshd(8), xterm(1), etc. Esta abstracción es necesaria para muchos programas que interactúan con los usuarios.

NAME

apparmor.d - AppArmor profile syntax

DESCRIPTION

This document describes the syntax and semantics of AppArmor profiles. AppArmor profiles are stored in the /etc/apparmor.d/ directory.

Profiles are composed of rules that specify which resources a program may access and what operations it may perform on them. Rules may be granted in discrete levels of permission: read (r), write (w), execute (x), link (l), append (a), and file locking (f).

Rules may also be granted for network access: network (n), sip_bind (sbi), tcp_fastopen (tfo), tcp_syncookies (tsc), udp_csum_send (ucs), udp_init_csum (uic), udp_send_check (usc), tcp_rcv_tsval (trv), tcp_nodelay (tnd), tcp_window_scaling (tws), tcp_sack (tss), tcp_timestamps (tst), tcp_ecn (tec), tcp_congestion_control (tcc), tcp_fast_path (tfp), tcp_abort_queue_full (taq), tcp_abort_connection_reset (tar), tcp_abort_local_reset (tal), tcp_abort_remote_reset (taa), tcp_abort_undo_open (tau), tcp_abort_undo_close (tua), tcp_abort_undo_reset (tuu).

Profile rules may be granted permissions in discrete levels of file access: read (r), write (w), execute (x), link (l), append (a), and file locking (f). Profile rules may also be granted permissions in discrete levels of mount access: mount (m), mount_br (mb), mount_remount (mr), and mount_vfsv1 (mv1).

Profile rules may also be granted permissions in discrete levels of audit access: audit (A).

A rule can specify profile capabilities by adding the character `C` followed by an allowed capability. The supported profile capabilities include: capability_sys_admin (Csa), capability_sys_boot (Csbo), capability_sys_chroot (Csch), capability_sys_module (Csm), capability_sys_nice (Csn), capability_sys_pacct (Csp), capability_sys_ptrace (Cptr), capability_sys_rawio (Csri), capability_sys_resource (Csr), capability_sys_time (Cst), capability_net_admin (CnA), capability_net_bind_service (Cnbs), capability_net_broadcast (CnB), capability_net_raw (Cnr), capability_ipc_lock (Cil), capability_ipc_owner (Cio), capability_sys_tty_config (Cstc), capability_mknod (Cm), capability_lease (Cl), capability_audit_write (Cau), capability_audit_control (Cac), capability_setgid (Csg), capability_setuid (Csu), capability_setpcap (Cspc), capability_syslog (Csl), capability_chown (Cch), capability_fowner (Cf), capability_kill (Ck), capability_module (Cmo).

An explicit deny rule can be specified by prepending the rule with an exclamation mark (`!`). Deny rules are checked before allow rules.

Rules can be prefixed with `owner` to indicate that the rule applies only when the file is owned by the process requesting access. This is useful for restricting access to files in a user's home directory.

Rules can be prefixed with `relative` to indicate that the rule applies to files relative to the directory the rule is applied to. This is useful for restricting access to files within a directory tree.

Rules can be prefixed with `complain` to indicate that the rule should be run in complain mode, meaning that AppArmor will log violations but not block them. This is useful for testing new profiles or for applications that are expected to occasionally violate policy.

Rules can be prefixed with `audit` to indicate that the rule should be audited, meaning that AppArmor will log violations but not block them. This is useful for monitoring application behavior without restricting it.

Rules can be prefixed with `enforce` to indicate that the rule should be enforced, meaning that AppArmor will log violations and block them. This is the default behavior for rules that are not prefixed with `complain` or `audit`.

Rules can be prefixed with `disable` to indicate that the rule should be disabled, meaning that AppArmor will not log or block violations associated with this rule. This is useful for temporarily disabling specific rules without modifying the profile.

Rules can be prefixed with `inherit` to indicate that the rule should be inherited by child processes. This is useful for applications that create child processes that need to have the same AppArmor restrictions.

Rules can be prefixed with `unconfined` to indicate that the rule should not be confined by AppArmor. This is useful for applications that need to have full access to the system, such as shell environments.

Rules can be suffixed with a list of comma-separated flags that modify the rule's behavior. Supported flags include:

  • ux: allow unprivileged extended attributes.
  • ix: allow indirect execution.
  • px: allow privileged execution.
  • mx: allow memory execution.
  • rx: allow read execution.
  • wx: allow write execution.
  • lx: allow link execution.
  • ax: allow append execution.
  • fx: allow file lock execution.
  • nx: allow network execution.
  • sx: allow subshell execution.
  • yx: allow symlink execution.
  • zx: allow extended attribute execution.
  • ox: allow open execution.
  • vx: allow mmap execution.
  • x: allow execute.
  • X: allow indirect execute.
  • P: allow privileged execute.
  • M: allow memory execute.
  • R: allow read execute.
  • W: allow write execute.
  • L: allow link execute.
  • A: allow append execute.
  • F: allow file lock execute.
  • N: allow network execute.
  • S: allow subshell execute.
  • Y: allow symlink execute.
  • Z: allow extended attribute execute.
  • O: allow open execute.
  • V: allow mmap execute.
  • m: allow mount.
  • b: allow mount_br.
  • r: allow mount_remount.
  • v: allow mount_vfsv1.
  • k: allow kill.

A rule can also specify a target file that the process is allowed to execute. This is done by specifying the source file followed by `->` and the target file. For example, `/usr/bin/foo -> /usr/bin/bar` means that `/usr/bin/foo` can execute `/usr/bin/bar`.

A profile can include other profiles by using the `#include` directive. This allows for modularity and reuse of common rules. For example, `#include <abstractions/bash>` will include the rules defined in the `abstractions/bash` file.

A profile can also define subprofiles, which are profiles that are applied only when a specific program is executed by the main profile. This is done by using the `profile` keyword followed by the name of the subprofile. For example, `profile baz { ... }` defines a subprofile named `baz`.

A profile can also define hats, which are sets of rules that can be applied dynamically by a process. This is done by using the `hat` keyword followed by the name of the hat. For example, `hat foo { ... }` defines a hat named `foo`.

A profile can also define capabilities, which are sets of privileges that can be granted to a process. This is done by using the `capability` keyword followed by the name of the capability. For example, `capability sys_admin { ... }` grants the `sys_admin` capability to the process.

A profile can also define variables, which are named values that can be used in the profile. This is done by using the `@{VAR}` syntax. For example, `@{HOME} = /home/user/` defines a variable named `HOME` with the value `/home/user/`.

Feature ABI

The feature abi tells AppArmor which feature set the policy was developed under. This is important to ensure that kernels with a different feature set don't enforce features that the policy doesn't support, which can result in unexpected application failures.

When policy is compiled both the kernel feature abi and policy feature abi are consulted to build a policy that will work for the system's kernel.

If the kernel supports a feature not supported by the policy then policy will be built so that the kernel does NOT enforce that feature.

If the policy supports a feature not supported by the kernel the compile may downgrade the rule with the feature to something the kernel supports, drop the rule completely, or fail the compile.

If the policy abi is specified as kernel then the running kernel's abi will be used. This should never be used in shipped policy as it can cause system breakage when a new kernel is installed.

ABI compatibility with AppArmor 2.x

AppArmor 3 remains compatible with AppArmor 2.x by detecting when a profile does not have a feature ABI specified. In this case the policy compile will either apply the pinned feature ABI as specified by the config file or the command line, or if neither of those are applied by using a default feature ABI.

It is important to note that the default feature ABI does not support new features added in AppArmor 3 or later.

An example AppArmor profile:

abi <abi/3.0>,
# a variable definition in the preamble
@{HOME} = /home/*/ /root/
# a comment about foo.
/usr/bin/foo {
  /bin/mount          ux,
  /dev/{,u}random     r,
  /etc/ld.so.cache    r,
  /etc/foo.conf       r,
  /etc/foo/*          r,
  /lib/ld-*.so*       rmix,
  /lib/lib*.so*       r,
  /proc/[0-9]**       r,
  /usr/lib/**         r,
  /tmp/foo.pid        wr,
  /tmp/foo.*          lrw,
  @{HOME}/.foo_file  rw,
  /usr/bin/baz        Cx -> baz,
  # a comment about foo's hat (subprofile), bar.
  ^bar {
    /lib/ld-*.so*       rmix,
    /usr/bin/bar        rmix,
    /var/spool/*        rwl,
  }
  # a comment about foo's subprofile, baz.
  profile baz {
    #include <abstractions/bash>
    owner /proc/[0-9]*/stat r,
    /bin/bash ixr,
    /var/lib/baz/ r,
    owner /var/lib/baz/* rw,
  }
}

KNOWN BUGS

  • Mount options support the use of pattern matching but mount flags are not correctly intersected against specified patterns. Eg, 'mount options=**,' should be equivalent to 'mount,', but it is not. (LP: #965690)
  • The fstype may not be matched against when certain mount command flags are used. Specifically fstype matching currently only works when creating a new mount and not remount, bind, etc.
  • Mount rules with multiple 'options' conditionals are not applied as documented but instead merged such that 'options in (ro,nodev) options in (atime)' is equivalent to 'options in (ro,nodev,atime)'.
  • When specifying mount options with the 'in' conditional, both the positive and negative values match when specifying one or the other. Eg, 'rw' matches when 'ro' is specified and 'dev' matches when 'nodev' is specified such that 'options in (ro,nodev)' is equivalent to 'options in (rw,dev)'.
