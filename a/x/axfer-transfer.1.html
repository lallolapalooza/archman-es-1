AXFER-TRANSFER(1) Manual de Comandos Generales AXFER-TRANSFER(1)

NOMBRE

axfer-transfer - transferidor de fotogramas de datos de audio para dispositivos de sonido y nodos.

SINOPSIS

axfer transfer dirección [ opciones-comunes ] [ opciones-backend ] [ ruta-archivo ]

axfer transfer dirección [ opciones-comunes ] [ opciones-backend ] -I | --separate-channels ruta-archivo ...

dirección = capture | playback

opciones-comunes = ( leer sección OPCIONES )

opciones-backend = ( leer sección OPCIONES )

rutas-archivo = ( leer sección OPCIONES )

DESCRIPCIÓN

El subcomando transfer de axfer realiza la transmisión de fotogramas de datos de audio para los dispositivos disponibles en los backends soportados. Este programa está esencialmente diseñado para usar las APIs de alsa-lib (backend libasound) para manejar dispositivos de sonido soportados por el subsistema de sonido de Linux (ALSA).

OPCIONES

Dirección

capture
Opera para transmisión de captura.
playback
Opera para transmisión de reproducción.

Ruta-archivo

La ruta de archivo se maneja como una ruta relativa al directorio de trabajo actual en tiempo de ejecución si no es una ruta completa desde el directorio raíz.

La entrada o salida estándar se utiliza si la ruta de archivo no se especifica o se indica como '-' .

Para la transmisión de reproducción, el formato contenedor de la ruta-archivo dada se detecta automáticamente y los metadatos se usan para los parámetros de formato de muestra, canales, frecuencia, duración. Si no se detecta nada, el contenido de la ruta de archivo dada se maneja como datos crudos. En este caso, los parámetros deben indicarse como opciones.

Se permiten múltiples rutas-archivo con la opción -I | --separate-channels. En este caso, la entrada y salida estándar no están disponibles. La misma ruta-archivo no está permitida, excepto para las rutas que se enumeran a continuación:
- /dev/null
- /dev/zero
- /dev/full
- /dev/random
- /dev/urandom

Indica el número de muestras de datos de audio por fotograma. Esto es obligatorio para la transmisión de captura, o la transmisión de reproducción con archivos que incluyen datos de audio crudos. El valor debe estar entre 1 y 256. Si se omite, se utiliza 1 como valor predeterminado.
-r, --rate=#
Indica el número de fotogramas de datos de audio por segundo. Esto es obligatorio para la transmisión de captura, o la transmisión de reproducción con archivos que incluyen datos de audio crudos. Si el valor es menor que 1000, se interpreta por unidad de kHz. El valor debe estar entre 2000 y 192000. Si se omite, se utiliza 8000 como valor predeterminado.
-t, --file-type=TYPE
Indica el tipo de archivo. Esto es obligatorio para la transmisión de captura. Los tipos disponibles se enumeran a continuación:
- wav: formato Microsoft/IBM RIFF/Wave
- au, sparc: formato Sparc AU
- voc: formato Creative Tech. voice
- raw: datos crudos

Cuando no se indica nada, para la transmisión de captura, el tipo se decide según el sufijo de ruta-archivo, y se usa el tipo raw como fallback.

Indica esta opción cuando se van a manejar varios archivos. MODELO DE

PLANIFICACIÓN

En el diseño del núcleo ALSA PCM, el tiempo de ejecución del substream PCM soporta dos modos; period-wakeup y no-period-wakeup. Estos dos modos son para diferentes modelos de

planificación.

Modelo de planificación basado en

IRQ

Por defecto, se usa el modo period-wakeup. En este modo, los controladores en el kernel deben operar el hardware para generar notificaciones periódicas para la transmisión de marcos de datos de audio. El intervalo de la notificación equivale a la misma cantidad de marcos de datos de audio como un período del búfer, contra el tiempo

real.

En un manejador asignado a la notificación, se llama a una función auxiliar del núcleo ALSA PCM para actualizar una posición a la cabecera de la transmisión de hardware, luego compararla con una posición a la cabecera de la operación de la aplicación para juzgar overrun/underrun (XRUN) y despertar procesos

bloqueados.

Para este propósito, se usa típicamente la IRQ de hardware del controlador para bus de audio serie como Inter-IC sound. En este caso, el controlador genera la IRQ de acuerdo con la transmisión en el bus de audio serie. En el manejador asignado a la IRQ, se solicita la transmisión por acceso directo a medios (DMA) entre la memoria del host dedicada y la memoria del

dispositivo.

Si el hardware de destino no soporta este tipo de mecanismo, la notificación periódica debe ser emulada por cualquier temporizador; p. ej. hrtimer, temporizador del kernel. Los plugins PCM externos generados por el SDK de plugins PCM en alsa-lib también deben emular el comportamiento

anterior.

En este modo, las aplicaciones PCM se programan de acuerdo con la manera típica de operaciones de E/S. Ejecutan llamadas al sistema bloqueantes para leer/escribir marcos de datos de audio en el búfer del substream PCM, o llamadas al sistema bloqueantes para esperar hasta que algún marco de datos de audio esté disponible. En axfer , esto se llama modelo de planificación basado en IRQ y es el comportamiento por defecto. Los usuarios pueden configurar explícitamente este modo mediante el uso de la opción --sched-model con el valor

ir
q.

Modelo de planificación basado en

temporizador

El modo no-period-wakeup es un modo opcional del tiempo de ejecución del substream PCM. El modo asume una característica específica del hardware y asistencia de los controladores en el kernel y las aplicaciones PCM. En este modo, los controladores en el kernel no operan el hardware para generar notificaciones periódicas para la transmisión de marcos de datos de audio. El hardware debe continuar automáticamente la transmisión de marcos de datos de audio sin operación periódica de los controladores; p. ej. de acuerdo con transmisión DMA auto-disparada, una cadena de descriptores

registrados.

En este modo, nada despierta procesos bloqueados, por lo tanto las aplicaciones PCM deben programarse sin ninguna operación bloqueante. Por esta razón, este modo se habilita cuando las aplicaciones PCM configuran explícitamente el parámetro de hardware al tiempo de ejecución del substream PCM, para prevenir el desorden de aplicaciones existentes. Adicionalmente, nada mantiene la temporización para la transmisión de marcos de datos de audio, por lo tanto las aplicaciones PCM deben manejar voluntariamente cualquier temporizador para encolar marcos de datos de audio en el búfer del substream PCM por el transcurso del tiempo. Además, en lugar del controlador, la aplicación PCM debe llamar a una función auxiliar del núcleo ALSA PCM para actualizar una posición a la cabecera de la transmisión de hardware y verificar

XRUN.

En axfer , esto se llama modelo de planificación basado en temporizador y está disponible siempre que el hardware/controlador asista el tiempo de ejecución no-period-wakeup. Los usuarios deben establecer explícitamente este modo mediante el uso de la opción --sched-model con el valor ti

mer.

En el modelo de planificación, las aplicaciones PCM necesitan cuidar del espacio disponible en el búfer PCM por el transcurso del tiempo, típicamente cediendo el CPU y esperando la re-planificación. Para la cesión, se calcula un tiempo de es

pera para la cantidad preferible de marcos PCM a procesar. Esto es conveniente para un tipo de aplicaciones, como servidores de sonido. Cuando un hilo de E/S del servidor espera el tiempo de espera, los otros hilos pueden procesar marco
s de datos de audio para los clientes del servidor. Además, con el uso de rebobinado/avance, las aplicaciones pueden lograr baja latencia entre la posición de transmisión y la posición de manejo incluso si usan búfers PCM de gran tamaño.

Ventajas e

inconvenientes

Idealmente, el modelo de planificación basado en temporizador tiene algunas ventajas sobre el modelo de planificación basado en IRQ. En primer lugar, no se ejecuta ningún contexto de interrupción para el substream PCM. El substream PCM se maneja solo en algún contexto de proceso. No es necesario cuidar de condiciones de carrera entre los contextos de IRQ y de proceso. Esto reduce algunas preocupaciones para algunos desarrolladores de controladores y aplicaciones. En segundo lugar, el tiempo de CPU no se usa para manejadores en el contexto de interrupción. El tiempo de CPU puede dedicarse para las otras tareas. Esto es bueno en un punto de Sistema de Tiempo Compartido. En tercer lugar, el hardware no se configura para generar interrupciones. Esto es bueno en un punto de reducción del consumo total de energía

posiblemente.

En cualquiera de los modelos de planificación, el hardware debe permitir a los controladores leer el número de marcos de datos de audio transferidos entre la memoria dedicada y la memoria del dispositivo

para el bus de audio serie. Sin embargo, en el modelo de planificación basado en temporizador, la granularidad finita y la precisión del valor son importantes. En realidad el hardware realiza la transmis
ión entre la memoria dedicada y la memoria del dispositivo para un pequeño lote de marcos de datos de audio o bytes. En la vista de las aplicaciones PCM, la granularidad en la transmisión actual es reque
rida para decidir el tiempo de espera correcto para cada operación de E/S. A partir del kernel Linux v4.21, la interfaz ALSA PCM entre kernel/espacio de usuario no tiene la característica para reportarlo.

Estructura

modular

Este programa consta de tres módulos; xfer , mapper y container . Cada módulo tiene una capa de abstracción para permitir la implementación

real. 
           --------     ----------     -------------
dispositivo <-> | xfer | <-> | mapper | <-> | container | <-> archivo
                --------     ----------     -------------
                 libasound    single         wav
                 libffado     multiple       au
                                                     voc
raw

El módulo xfer realiza la transmisión real a dispositivos y nodos. El módulo puede tener varios backends de transmisión. Como backend predeterminado, el backend libasound se usa para realizar la transmisión a través de las APIs de alsa-lib. El módulo permite que cada backend analice sus propias opciones de línea de

comandos.

El módulo container realiza la lectura/escritura de tramas de datos de audio a través de un descriptor para archivos/flujos de contenedores multimedia o datos crudos. El módulo detecta automáticamente el tipo de contenedor multimedia y analiza los parámetros en sus metadatos del encabezado de datos. En la actualidad, se admiten tres tipos de contenedores multimedia; RIFF/Wave de Microsoft/IBM ( wav ), AU de Sparc ( au ) y voz de Creative Technology ( voc ). Además, se prepara un contenedor especial para datos de audio crudos ( raw )

.

El módulo mapper maneja la disposición y alineación del búfer para la transmisión de tramas de datos de audio. El módulo tiene dos implementaciones; single y multiple . El backend single usa un contenedor para construir el búfer. El backend multiple usa varios

contenedores p
ara construirlo.

Cuidado con la copia de tramas de datos de

audio

Entre el módulo xfer y el módulo mapper, se pasa un puntero al búfer que incluye tramas de datos de audio. Este búfer tiene dos formas para orden intercalado y no intercalado. Para la primera, el puntero apunta a un búfer. Para la segunda, el puntero apunta a un arreglo en el que cada elemento apunta a un búfer. Entre el módulo mapper y el módulo container, se pasa un puntero a un búfer porque los contenedores de medios admitidos, incluido el tipo raw, almacenan tramas de datos de audio en orden

intercalado.

Al pasar tramas de datos de audio entre los módulos, axfer está programado para evitar la copia entre un búfer y otro búfer tanto como sea posible. Por ejemplo, en algunos escenarios a continuación, no ocurre copia entre

módulos.


- xfer(mmap/interleaved), mapper(single), container(any)
- xfer(mmap/non-inter

leaved), mapper(multi
ple), containers(any)

unitaria
