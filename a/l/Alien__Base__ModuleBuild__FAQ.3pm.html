¿Cómo pruebo mi paquete una vez que está construido (antes de que se instale)

?

Hay muchas formas de probar módulos Alien antes (o después) de que se instalen, pero en lugar de crear el suyo propio, considere usar Test::Alien que tiene pocas dependencias y probará su módulo muy de cerca de la forma en que realmente se usará. Es decir, construyendo una extensión XS o FFI en miniatura y usándola. Incluso tiene pruebas para distribuciones Alien orientadas a herramientas (como Alien::gmake y Alien::patch). Aquí hay un breve ejemplo, hay muchos otros incluidos con la documentación de Test::

¿Cómo parcheo paquetes que necesitan alteraciones menores (o mayores)

?

Un enfoque es crear un parche de diff unificado para los cambios que desea aplicar y simplemente ejecutar patch sobre ellos. El Alien::patch y el pan class="Li">"%{patch}" el asistente se puede usar así:

# Build.PL
use Alien::Base::ModuleBuild;

Alien::Base::ModuleBuild->new(
  ...
  alien_bin_requires => {
    'Alien::patch' => 0.06, # necesario para el asistente %{patch}
  },
  alien_build_commands => [
    '%{patch} -p1 < ../../patch/mypackage.patch',
    ...
  ],
  ...
)->create_build_script;

Crea una carpeta en la raíz de tu distribución llamada "patch" y coloca el archivo "mypackage.patch" ahí dentro. Dado que el comando "patch" se ejecutará en la raíz del paquete en lugar de en la raíz de la distribución, necesitas usar una ruta relativa prefijada con "../..". Aquí usamos Alien::patch para proporcionar patch incluso en entornos donde no está proporcionado.

Un enfoque más potente para aplicar parches es escribir una subrutina de perl para modificar el código fuente después de que haya sido extraído. Una forma de hacerlo es crear un módulo en el directorio inc de tu distribución que realice el parcheo (los módulos en inc se pueden usar durante la compilación/pruebas pero no se instalarán):

# inc/My/AlienPatch.pm
package My::AlienPatch;

# añade esta sub al espacio de nombres principal
# para que no necesitemos comillas ni escapar
# nada de lo que hay debajo
sub main::alien_patch {
  # se ejecuta en la raíz del paquete,
  # haz aquí los cambios que necesites
  # en el código fuente.
}

1;

# Build.PL
use Alien::Base::ModuleBuild;

Alien::Base::ModuleBuild->new(
  ...
  alien_build_commands => [
    # %x será reemplazado por la ruta para llamar a Perl
    # desde la línea de comandos
    "%x -I../../inc -MMy::AlienPatch -e alien_patch",
    ...
  ],
  ...
)->create_build_script;

¿Cómo compilo un paquete que usa el sistema de compilación?

autoconf

Por defecto Alien::Base::ModuleBuild asume un paquete con un script "configure" de estilo autoconf. El valor por defecto es

# Build.PL
use Alien::Base::ModuleBuild;
Alien::Base::ModuleBuild->new(
  ...
  alien_build_commands => [
    '%c --prefix=%s',
    'make',
  ],
  alien_install_commands => [
    'make install',
  ],
  ...
)->create_build_script;

Hay un par de atajos aquí, %c indica el método independiente de la plataforma para ejecutar el script "configure" , más cualquier flag normal de autoconf que sea apropiado para las bibliotecas Perl Alien. El %c también le indica a Alien::Base::ModuleBuild que use Alien::MSYS en plataformas Windows y que la agregue como dependencia. El %s es un marcador de posición para la ubicación a la que se instalará el paquete. Esto normalmente está en un directorio share específico de tu distribución.

estilo autoconf

Si ves un error como este:

Unknown option "--with-pic".

Puede ser porque tu paquete proporciona un script "configure" que proporciona una interfaz de estilo autoconf, pero no es realmente autoconf. Alien::Base::ModuleBuild es agresivo en el uso de la opción "--with-pic" porque cuando es soportada por autoconf produce código independiente de posición (importante para construir extensiones XS de forma fiable), y cuando no es soportada autoconf simplemente ignora la opción. Desafortunadamente algunos scripts "configure" de estilo autoconf consideran un error cuando ven opciones que no reconocen. Puedes decirle a Alien::Base::ModuleBuild que no use la opción "--with-pic" a través de la propiedad "alien_autoconf_with_pic" :

# Build.PL
use Alien::Base::ModuleBuild;
Alien::Base::ModuleBuild->new(
  ...
  alien_autoconf_with_pic => 0,
  ...
)->create_build_script;

CMAKE

Probablemente no puedas contar con que CMake esté disponible en la mayoría de plataformas. Afortunadamente, existe la distribución alien Alien::CMake que usará el CMake proporcionado por el sistema operativo, o lo descargará e instalará por ti. Puedes usar esto desde tu "Build.PL" con la propiedad "alien_bin_requires" :

# Build.PL
use Alien::Base::ModuleBuild;
use Config;
Alien::Base::ModuleBuild->new(
  ...
  alien_bin_requires => {
    'Alien::CMake' => 0.07,
  },
  alien_build_commands => [
    # los argumentos requeridos reales pueden variar
    "cmake -G 'Unix Makefiles' -DCMAKE_MAKE_PROGRAM=$Config{make} -DCMAKE_INSTALL_PREFIX:PATH=%s",
    "$Config{make}",
  ],
  alien_install_commands => [
    "$Config{make} install",
  ],
  ...
)->create_build_script;

¿Makefiles vanilla?

Si quieres usar el mismo "make" que Perl, puedes usar Config:

# Build.PL
use Alien::Base::ModuleBuild;
use Config;
Alien::Base::ModuleBuild->new(
  ...
  alien_build_commands => [
    "$Config{make}",
  ],
  alien_install_commands => [
    "$Config{make} install",
  ],
  ...
)->create_build_script;

¿Makefiles GNU?

Algunos paquetes requieren la sintaxis única de GNU Make. Config de Perl proporciona una entrada para "gmake", pero frecuentemente es incorrecta. No dependas de ella. En su lugar puedes usar Alien::gmake para proporcionar un GNU Make real (ya sea del sistema operativo, o compilado desde el código fuente):

# Build.PL
use Alien::Base::ModuleBuild;

Alien::Base::ModuleBuild->new(
  ...
  alien_bin_requires => {
    'Alien::gmake' => 0.11, # necesario para el asistente %{gmake}
  },
  alien_build_commands => [
    "%{gmake}",
  ],
  alien_install_commands => [
    "%{gmake} install",
  ],
  ...
)->create_build_script;

Cuando depuro la compilación de mi paquete, ¡obtengo resultados diferentes!

Si obtienes resultados al ejecutar los comandos en tu shell diferentes a lo que sucede cuando tu "Alien::" distribución intenta compilar, puede ser porque tu entorno es diferente al que tu distribución está usando. Por ejemplo, si usas Alien::CMake o Alien::gmake para compilar con herramientas específicas proporcionadas por tu sistema operativo, Alien::Base::ModuleBuild ajustará la ruta antes de ejecutar los comandos de compilación e instalación.

En el directorio de compilación alien (usualmente "_alien") encontrarás archivos de entorno que puedes cargar en tu shell ("env.csh" para tcsh y "env.sh" para shells basados en bourne), que deberían proporcionar el entorno idéntico usado por el proceso de compilación para solucionar problemas de la compilación manualmente.

% source _alien/env.sh

¿Puedo/Debo escribir un módulo Alien orientado a herramientas usando "Alien::Base" que proporcione ejecutables en lugar de una biblioteca?

Ciertamente. La intención original era proporcionar bibliotecas, pero las herramientas también son bastante realizables usando el conjunto de herramientas "Alien::Base" . Un ejemplo simple de esto que es bastante fácil de replicar es Alien::m4.

En general, esto significa especificar una subclase en tu "Build.PL" y empaquetarla en tu directorio "inc" de la distribución.

"Build.PL":

...
use lib 'inc';
use My::ModuleBuild;

My::ModuleBuild->new(
  ...
)->create_build_script;

"inc/My/ModuleBuild.pm":

package My::ModuleBuild;

use strict;
use warnings;
use parent 'Alien::Base::ModuleBuild';
use Capture::Tiny qw( capture );

sub alien_check_installed_version
{
  # consulta Alien::Base::ModuleBuild#alien_check_installed_version para más detalles

  my($self) = @_;
  my($stdout, $stderr) = capture { system 'mytool', '--version' };

  # devuelve una lista vacía si la herramienta no está disponible en el sistema,
  # o no es aceptable.
  return if $! || ...;

  # analiza desde stdout o stderr
  my $version = ...;
  return $version;
}

sub alien_check_built_version
{
  # consulta Alien::Base::ModuleBuild#alien_check_built_version para más detalles

  # devuelve una lista vacía si la versión de la herramienta no se puede encontrar, o si no
  # es aceptable. Ten en cuenta que esto causará un fallo, así que "desconocido"
  # puede ser razonable si la versión de la herramienta no se puede determinar.
  return if ...;

  # determina desde la herramienta en sí, o el directorio actual.
  my $version = ...;
  return $version;
}

1;

Como de costumbre tu clase "Alien::MyTool" simplemente será una subclase de Alien::Base. Si tu herramienta está instalada en un directorio "bin" , estás listo, la implementación por defecto de "bin_dir" debería funcionar para ti. De lo contrario, puede que necesites proporcionar una implementación alternativa:

package Alien::MyTool;

use strict;
use warnings;
use parent 'Alien::Base';

sub bin_dir
{
  # consulta Alien::Base#bin_dir para más detalles
  # Solo necesitas sobreescribir la implementación por defecto si tu herramienta
  # no se instala en el directorio estándar "bin".

  my($class) = @_;

  # normalmente para instalaciones del sistema la herramienta ya debería estar en tu
  # PATH, así que devuelve una lista vacía.
  return if $class->install_type eq 'system';

  # install_type = share
  my $dist_dir = $class->dist_dir;
  return ("$dist_dir/some/bin", "$dist_dir/some/other/bin");
}

1;

Ahora, una vez que tu Alien basado en herramientas esté instalado, puedes usar el método "bin_dir" para actualizar el "PATH" según sea necesario:

use Alien::MyTool;
use Env qw( @PATH );

unshift @PATH, Alien::MyTool->bin_dir;
system 'mytool';

Para crear dists basadas en Alien::Base desde Dist::Zilla puedes usar el plugin Dist::Zilla::Plugin::Alien.

¿Cómo verifico la versión compilada si mi biblioteca no proporciona un archivo ".

pc".

La implementación predeterminada de "alien_check_built_version" utiliza varias heurísticas, pero depende en gran medida de los archivos "pkg-config" al est

ilo

".pc" [[7]], por lo que si su biblioteca o herramienta no proporciona un ".pc" [[9]], es posible que la versión no se detecte y su compilación pueda fallar. Muchas bibliotecas se empaquetan como tarballs con la versión en el nombre del directorio en el que se extraen, y el directorio actual

cuando 
"alien_check_built_version
"

es llamado es la raíz de la compilación, por lo que puede usar "File:

:chd
ir"

como una manera fácil de determinar el número de

versión:

package My::ModuleBuild; use strict; use warnings; use parent 'Alien::Base::ModuleBuild'; use File::chdir; # provides @CWD sub alien_check_built_version { my $dir_name = $CWD[-1]; if($dir_name =~ /^libfoo-([0-9\.]+)$/) { return $1; } else { # Note that this will trigger a build failure return; } }

1;
Usar File::chdir y
@CWD
es una idiomática común en Alien::Base, porque File::chdir ya es una dependencia de Alien::Base. Para paquetes que no proporcionan un número de versión en el directorio extraído, puede necesitar algo de
creatividad.
