    NAME

    alpm-sonamev1 - libalpm soname package relation format

    DESCRIPTION

    The alpm-sonamev1 format is a specialized alpm-package-relation[7] type used to specify dependencies on shared libraries identified by their SONAME. This format is a successor to the simpler alpm-soname format and aims to resolve ambiguities by also encoding the ABI compatibility tag.

    Format details

    The format is based on the SONAME[1] of a shared library, which is typically embedded in the library file itself. The SONAME usually includes a major version number indicating ABI compatibility (e.g., libexample.so.1).

    The alpm-sonamev1 format extends the basic SONAME by appending the ELF architecture format. This is done to distinguish between different architectures if necessary, although in most common cases it defaults to 64-bit.

    The general format is:

    soname=ABI-ELFARCH
    soname
    The SONAME of the shared library (e.g., libexample.so.1).
    ABI
    The ABI compatibility tag. This is typically the major version number (e.g., 1 for libexample.so.1).
    ELFARCH
    The ELF architecture format. Common values include 32 and 64. If omitted, it defaults based on the build environment, typically 64.

    Examples:

    • libexample.so.1-64: Refers to the 64-bit version of libexample.so.1.
    • libmylib.so.2-32: Refers to the 32-bit version of libmylib.so.2.

    Matching Logic

    When a package is built, the build system attempts to resolve dependencies specified in the `provides` array of a package. If a dependency is specified using the alpm-sonamev1 format:

    1. The SONAME part (e.g., libexample.so.1) is extracted.
    2. This SONAME is used to query the available packages for a provider that offers this SONAME.
    3. The ABI compatibility tag (e.g., 1) is compared against the ABI information encoded in the provided library. The ELF architecture format[2] of the ELF file is also considered.
    4. If a match is found, the provider package is considered a suitable dependency. The specific version of the provider is determined based on the full alpm-sonamev1 string, including the ABI and architecture.
    5. If a match is found using the alpm-sonamev1 format, the unversioned form (i.e., just the SONAME without the ABI tag, like libexample.so) is added to the `depend` array of the package being built, under the `alpm-package-relation` type `provision`. This ensures that the package can be correctly identified as a runtime dependency, even if the exact SONAME version is not explicitly stated in the `depends` array.

    This mechanism allows packages to declare dependencies on shared libraries based on their SONAME, ensuring compatibility while accommodating potential versioning and architecture differences.

    USAGE

    The alpm-sonamev1 format is primarily used within the PKGBUILD(5) file when declaring package dependencies or providing shared libraries.

    Providing a soname

    When a package provides a shared library, you can declare the SONAME it provides in the `provides` array of the PKGBUILD(5). The build system, specifically makepkg(8), will automatically determine the appropriate alpm-sonamev1 representation based on the library's SONAME and the target architecture.

    Example in PKGBUILD(5):

    provides=(libexample.so=1-64)

    This declaration tells the package manager that this package provides the shared library identifiable as libexample.so with ABI version 1, specifically for the 64-bit architecture.

    Depending on a soname

    When a package depends on a shared library identified by its SONAME, you specify this in the `depends` array of the PKGBUILD(5). The format is crucial for correct dependency resolution.

    Example in PKGBUILD(5):

    depends=(glibc libexample.so=1-64)

    This declaration indicates that the package requires the shared library libexample.so with ABI version 1 for the 64-bit architecture. The package manager will then look for a package that `provides` this specific SONAME.

    During the build process, if a package provides a SONAME (e.g., libexample.so=1-64), and another package declares a dependency on the base SONAME (e.g., libexample.so), makepkg(8) uses the alpm-sonamev1 format. It matches the provided SONAME against the dependency requirement. The alpm-package-relation of type `provision` in the available package data is matched against the alpm-package-relation of type `run-time dependency` in the package being built. If a match occurs (e.g., a package provides libexample.so=1-64, and the package being built depends on libexample.so), the unversioned form (i.e., libexample.so) is added to the `depend` array of the package being built.

    Consider the case where a package simply lists libexample.so as a dependency. The build system will look for packages that provide libexample.so. If a package provides libexample.so=1-64, this provides a match. The corresponding entry in the final package's PKGINFO(5) file will be depend = libexample.so=1-64.

    This mechanism ensures that the correct version and architecture of the shared library are linked at runtime. The `provides` field in the PKGBUILD(5) should ideally reflect the SONAME with its ABI version and architecture, like libexample.so=1-64, while the `depends` field can optionally be more generic (e.g., libexample.so) if the exact versioning is handled by the provider's `provides` declaration.

    The following example demonstrates how alpm-sonamev1 is used in practice.

    The PKGBUILD for the library package:

    pkgname=example
pkgver=1.0.0
pkgrel=1
# ... other metadata ...
provides=(libexample.so=1-64)
# ... build and package functions ...

    The resulting PKGINFO file for example:

    pkgname = example
pkgver = 1.0.0-1
# ... other metadata ...
provides = libexample.so=1-64

    The PKGBUILD for the application package that depends on the library:

    pkgname=application
pkgver=1.0.0
pkgrel=1
# ... other metadata ...
depends=(glibc libexample.so)
# ... build and package functions ...

    In the `package()` function of the application, the dependency is finalized. If the build system detects that the `example` package provides `libexample.so=1-64`, and the `application` package declared a dependency on `libexample.so`, the final `depend` entry in the application's PKGINFO will be:

    depend = libexample.so=1-64

    This ensures that the runtime dependency correctly points to the specific version and architecture of the library provided by the example package. The alpm-package-relation of type `provision` in the PKGINFO data of the packages available in the build environment is matched against the dependency declaration. If one matches, the unversioned form (e.g., libexample.so) instead of the basic form is added to the alpm-package-relation of type `run-time dependency` in the PKGINFO file of the package that is being built (e.g. depend = libexample.so=1-64).

    EXAMPLES

    Providing a soname

    The following example PKGBUILD for a package named example is used to build and install an upstream project, which provides a shared object named libexample.so.

    pkgname=example
pkgver=1.0.0
pkgrel=1
pkgdesc="An example library"
arch=(x86_64)
url="https://example.org/library.html"
license=(MIT)
depends=(glibc)
provides=(libexample.so=1-64)
source=("https://example.org/$pkgname-$pkgver.tar.gz")
sha256sums=(7d865e959b2466918c9863afca942d0fb89d7c9ac0c99bafc3749504ded97730)
build() {
  make -C $pkgname-$pkgver
}
package() {
  make DESTDIR="$pkgdir" install -C $pkgname-$pkgver
}

    The following SRCINFO file can be generated from the above PKGBUILD file:

    pkgbase = example
    pkgdesc = An example library
    pkgver = 1.0.0
    pkgrel = 1
    arch = x86_64
    url = https://example.org/library.html
    license = MIT
  depends = glibc
    provides = libexample.so=1-64
    source = https://example.org/example-1.0.0.tar.gz
    sha256sums = 7d865e959b2466918c9863afca942d0fb89d7c9ac0c99bafc3749504ded97730
pkgname = example

    This example assumes that the project results in installing the following files to the filesystem:

    /usr/lib/libexample.so -> libexample.so.1
/usr/lib/libexample.so.1 -> libexample.so.1.0.0
/usr/lib/libexample.so.1.0.0

    Here, the file /usr/lib/libexample.so.1.0.0 encodes the soname libexample.so.1.

    After building from source, the resulting package file for example contains the following PKGINFO file:

    pkgname = example
pkgver = 1.0.0-1
pkgdesc = An example library
url = https://example.org/library.html
builddate = 1729181726
packager = Your Name <your.name@example.org>
size = 181849963
arch = x86_64
license = MIT
provides = libexample.so=1-64
depend = glibc

    Depending on a soname

    The following PKGBUILD for a package named application is used to build an upstream project that depends on the example package from the previous example. More specifically, the resulting package depends on the shared object libexample.so which is provided by the example package.

    In the PKGBUILD the run-time dependency on the libexample.so shared object is added in the package function instead of in the global run-time dependency declaration, while the example package is declared as global build dependency. This is because multiple sonames of the same name but of different ELF architecture format may exist (consider e.g. the explicit forms libexample.so=1-32 and libexample.so=1-64). If libexample.so was exposed as global run-time dependency, a build tool may accidentally pull in the wrong package containing a libexample.so due to the existing structural overlap between alpm-sonamev1 and alpm-package-relation!

    pkgname=application
pkgver=1.0.0
pkgrel=1
pkgdesc="An example application"
arch=(x86_64)
url="https://example.org/application.html"
license=(MIT)
depends=(glibc)
makedepends=(example)
source=("https://example.org/$pkgname-$pkgver.tar.gz")
sha256sums=(b5bb9d8014a0f9b1d61e21e796d78dccdf1352f23cd32812f4850b878ae4944c)
build() {
  make -C $pkgname-$pkgver
}
package() {
  depends+=(example libexample.so)
  make DESTDIR="$pkgdir" install -C $pkgname-$pkgver
}

    The following SRCINFO file can be generated from the above PKGBUILD file:

    pkgbase = application
    pkgdesc = An example application
    pkgver = 1.0.0
    pkgrel = 1
    arch = x86_64
    url = https://example.org/application.html
    license = MIT
    depends = glibc
    depends = example
    depends = libexample.so
    makedepends = example
    source = https://example.org/application-1.0.0.tar.gz
    sha256sums = b5bb9d8014a0f9b1d61e21e796d78dccdf1352f23cd32812f4850b878ae4944c
pkgname = application

    After building from source, the resulting package file for application contains the following PKGINFO file:

    pkgname = application
pkgver = 1.0.0-1
pkgdesc = An example application
url = https://example.org/application.html
builddate = 1729181726
packager = Your Name <your@email.com>
size = 181849963
arch = x86_64
license = MIT
depend = glibc
depend = example
depend = libexample.so=1-64
