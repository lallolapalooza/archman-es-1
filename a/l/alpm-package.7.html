NAME

package - a package based on Arch Linux Package Management (ALPM) concepts.

DESCRIPTION

ALPM based packages refer to (optionally compressed) tar archives that contain package files. Package files encompass mandatory metadata files as well as optional scripts and data files.

Package files are created from package sources (i.e. PKGBUILD) using package build software (e.g. makepkg). For Arch Linux specific package build software refer to devtools and pkgctl.

Package management software (e.g. pacman) relies on metadata files and scripts for the purpose of dependency resolution and installation. Data files can be installed on compatible target systems using package management software.

FORMAT

Uncompressed ALPM based package files follow the following naming scheme:

An alpm-package-name directly followed by a ‘-’ sign, directly followed by an alpm-package-version (in the full or full with epoch form), directly followed by a ‘-’ sign, directly followed by an alpm-architecture, directly followed by the string ‘.pkg.tar’, e.g.:

  • example-1.0.0-1-any.pkg.tar
  • example-1.0.0-1-x86_64.pkg.tar

Compression

ALPM based packages may optionally be compressed using a single supported compression technology. If a package is compressed, a technology-specific suffix is appended to the file name:

  • .Z for compression based on adaptive Lempel-Ziv coding (e.g. example-1.0.0-1-x86_64.pkg.tar.Z), see the compress command
  • .bz2 for bzip2 compression (e.g. example-1.0.0-1-x86_64.pkg.tar.bz2)
  • .gz for gzip compression (e.g. example-1.0.0-1-x86_64.pkg.tar.gz)
  • .lrz for lrzip compression (e.g. example-1.0.0-1-x86_64.pkg.tar.lrz)
  • .lz4 for lz4 compression (e.g. example-1.0.0-1-x86_64.pkg.tar.lz4)
  • .lz for lzip compression (e.g. example-1.0.0-1-x86_64.pkg.tar.lz)
  • .lzo for lzop compression (e.g. example-1.0.0-1-x86_64.pkg.tar.lzo)
  • .xz for xz compression (e.g. example-1.0.0-1-x86_64.pkg.tar.xz)
  • .zst for zstd compression (e.g. example-1.0.0-1-x86_64.pkg.tar.zst)

Handling of compression technologies is specific to the package build tool. Refer to COMPRESSBZ2, COMPRESSGZ, COMPRESSLRZ, COMPRESSLZ, COMPRESSLZ4, COMPRESSLZO, COMPRESSXZ, COMPRESSZ, COMPRESSZST and PKGEXT in makepkg.conf for compression options and package extensions used in makepkg.

Digital signatures

Digital signatures can be created for package files.

Currently, only OpenPGP detached signatures over the package file are supported. Detached signatures carry the same name as the package file for which they are created, with an additional .sig suffix (e.g. example-1.0.0-1-x86_64.pkg.tar.zst.sig is the digital signature for a package file example-1.0.0-1-x86_64.pkg.tar.zst).

CONTENTS

The contents of an ALPM based package are distinguished between metadata, scripts and data files.

Metadata

The following files must be present at the root of an ALPM based package:

  • .BUILDINFO: a BUILDINFO file
  • .MTREE: an ALPM-MTREE file
  • .PKGINFO: a PKGINFO file

The above files provide relevant metadata for the installation, upgrade and uninstallation of packages on a target system (see alpm-package-relation for details on dependency resolution), as well as reproducibly building a bit-by-bit identical package from the same sources (see reproducible builds[2]).

Scripts

Optionally, an alpm-install-scriptlet named .INSTALL may be present at the root of an ALPM based package.

Data

Zero or more data files may be present in an ALPM based package (refer to alpm-meta-package for details on why packages may not contain any data files).

All existing data files of a package are extracted to the root directory[3] of a target system upon installation of the package.

No specific rules exist on which data files (and directories) are allowed as contents of a package, but it is advisable to adhere to common standards such as the systemd File Hierarchy Requirements[4] and/or the Filesystem Hierarchy Standard[5] and by default have all files and directories be owned by root. In conclusion, it is best practice to never package files in directories that contain user data (e.g. below /home).

More specific guidelines around the validation of data files in packages are subject to the implementer’s discretion (e.g. a distribution using ALPM).

EXAMPLES

The following example PKGBUILD defines the package example which only creates a single data file (plus the directories in which it is located):

pkgname=example
pkgver=1.0.0
pkgrel=1
pkgdesc="A simple package example"
arch=(any)
url="https://example.org"
license=(GPL-3.0-or-later)
package() {
  install -vdm 755 "$pkgdir/usr/share/$pkgname/"
  echo "data" > "$pkgdir/usr/share/$pkgname/data.txt"
}

Assuming makepkg is used to build a package from above PKGBUILD and is configured to use zstd for compression, the resulting package file is called example-1.0.0-1-any.pkg.tar.zst.

The package file contents can be examined as follows:

$ tar -tf example-1.0.0-1-any.pkg.tar.zst
.BUILDINFO
.MTREE
.PKGINFO
usr/
usr/share/
usr/share/example/
usr/share/example/data.txt

NOMBRE

package - un paquete basado en los conceptos de Arch Linux Package Management (ALPM).

DESCRIPCIÓN

Los paquetes basados en ALPM se refieren a archivos tar (opcionalmente comprimidos) que contienen archivos de paquete. Los archivos de paquete abarcan archivos de metadatos obligatorios, así como scripts y archivos de datos opcionales.

Los archivos de paquete se crean a partir de las fuentes del paquete (es decir, PKGBUILD) utilizando software de compilación de paquetes (por ejemplo, makepkg). Para el software de compilación de paquetes específico de Arch Linux, consulte devtools y pkgctl.

El software de gestión de paquetes (por ejemplo, pacman) depende de los archivos de metadatos y los scripts para la resolución de dependencias e instalación. Los archivos de datos se pueden instalar en sistemas de destino compatibles utilizando software de gestión de paquetes.

FORMATO

Los archivos de paquete basados en ALPM *sin comprimir* siguen el siguiente esquema de nombres:

Un nombre-del-paquete-alpm seguido directamente por un signo ‘-’, seguido directamente por una versión-del-paquete-alpm (en forma *completa* o *completa con epoch*), seguido directamente por un signo ‘-’, seguido directamente por una arquitectura-alpm, seguido directamente por la cadena ‘.pkg.tar’, por ejemplo:

  • example-1.0.0-1-any.pkg.tar
  • example-1.0.0-1-x86_64.pkg.tar

Compresión

Los paquetes basados en ALPM pueden comprimirse opcionalmente usando una única tecnología de compresión compatible. Si un paquete está comprimido, se añade un sufijo específico de la tecnología al nombre del archivo:

  • .Z para compresión basada en codificación adaptativa Lempel-Ziv (por ejemplo, example-1.0.0-1-x86_64.pkg.tar.Z), consulte el comando compress
  • .bz2 para compresión bzip2 (por ejemplo, example-1.0.0-1-x86_64.pkg.tar.bz2)
  • .gz para compresión gzip (por ejemplo, example-1.0.0-1-x86_64.pkg.tar.gz)
  • .lrz para compresión lrzip (por ejemplo, example-1.0.0-1-x86_64.pkg.tar.lrz)
  • .lz4 para compresión lz4 (por ejemplo, example-1.0.0-1-x86_64.pkg.tar.lz4)
  • .lz para compresión lzip (por ejemplo, example-1.0.0-1-x86_64.pkg.tar.lz)
  • .lzo para compresión lzop (por ejemplo, example-1.0.0-1-x86_64.pkg.tar.lzo)
  • .xz para compresión xz (por ejemplo, example-1.0.0-1-x86_64.pkg.tar.xz)
  • .zst para compresión zstd (por ejemplo, example-1.0.0-1-x86_64.pkg.tar.zst)

El manejo de las tecnologías de compresión es específico de la herramienta de compilación del paquete. Consulte COMPRESSBZ2, COMPRESSGZ, COMPRESSLRZ, COMPRESSLZ, COMPRESSLZ4, COMPRESSLZO, COMPRESSXZ, COMPRESSZ, COMPRESSZST y PKGEXT en makepkg.conf para ver las opciones de compresión y las extensiones de paquete utilizadas en makepkg.

Firmas digitales

Se pueden crear firmas digitales para los archivos de paquete.

Actualmente, solo se admiten las firmas separadas de OpenPGP sobre el archivo del paquete. Las firmas separadas tienen el mismo nombre que el archivo del paquete para el que se crean, con un sufijo adicional .sig (por ejemplo, example-1.0.0-1-x86_64.pkg.tar.zst.sig es la firma digital de un archivo de paquete example-1.0.0-1-x86_64.pkg.tar.zst).

CONTENIDOS

Los contenidos de un paquete basado en ALPM se distinguen entre archivos de metadatos, scripts y datos.

Metadatos

Los siguientes archivos deben estar presentes en la raíz de un paquete basado en ALPM:

  • .BUILDINFO: un archivo BUILDINFO
  • .MTREE: un archivo ALPM-MTREE
  • .PKGINFO: un archivo PKGINFO

Los archivos anteriores proporcionan metadatos relevantes para la instalación, actualización y desinstalación de paquetes en un sistema de destino (ver alpm-package-relation para detalles sobre la resolución de dependencias), así como para construir de forma reproducible un paquete idéntico bit a bit a partir de las mismas fuentes (ver builds reproducibles[2]).

Scripts

Opcionalmente, puede haber un scriptlet de instalación alpm llamado .INSTALL en la raíz de un paquete basado en ALPM.

Datos

Puede haber cero o más archivos de datos en un paquete basado en ALPM (consulte alpm-meta-package para obtener detalles sobre por qué los paquetes pueden no contener archivos de datos).

Todos los archivos de datos existentes de un paquete se extraen en el directorio raíz[3] de un sistema de destino al instalar el paquete.

No existen reglas específicas sobre qué archivos (y directorios) de datos están permitidos como contenido de un paquete, pero es aconsejable adherirse a estándares comunes como los Requisitos del Sistema de Jerarquía de Archivos de systemd[4] y/o el Filesystem Hierarchy Standard[5] y, por defecto, tener todos los archivos y directorios propiedad de root. En conclusión, es una buena práctica no empaquetar nunca archivos en directorios que contengan datos de usuario (por ejemplo, debajo de /home).

Directrices más específicas sobre la validación de archivos de datos en paquetes están sujetas a la discreción del implementador (por ejemplo, una distribución que utiliza ALPM).

EJEMPLOS

El siguiente ejemplo de PKGBUILD define el paquete example que solo crea un único archivo de datos (más los directorios en los que se encuentra):

pkgname=example
pkgver=1.0.0
pkgrel=1
pkgdesc="Un ejemplo de paquete simple"
arch=(any)
url="https://example.org"
license=(GPL-3.0-or-later)
package() {
  install -vdm 755 "$pkgdir/usr/share/$pkgname/"
  echo "data" > "$pkgdir/usr/share/$pkgname/data.txt"
}

Suponiendo que se utiliza makepkg para compilar un paquete a partir del PKGBUILD anterior y está configurado para usar zstd para la compresión, el archivo de paquete resultante se llama example-1.0.0-1-any.pkg.tar.zst.

El contenido del archivo del paquete se puede examinar de la siguiente manera:

$ tar -tf example-1.0.0-1-any.pkg.tar.zst
.BUILDINFO
.MTREE
.PKGINFO
usr/
usr/share/
usr/share/example/
usr/share/example/data.txt
