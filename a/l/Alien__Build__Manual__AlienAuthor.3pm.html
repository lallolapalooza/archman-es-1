DESCRIPCIÓN

Nota: Por favor, lea el documento completo antes de comenzar a escribir su propio alienfile. ¡La sección sobre bibliotecas dinámicas frente a estáticas probablemente le ahorrará muchos problemas si la lee ahora!

Este documento está destinado a enseñar a los autores de Alien cómo construir su propia distribución Alien utilizando Alien::Build y Alien::Base. Tal distribución Alien consta de tres partes esenciales:

Un alienfile
Esta es una receta para cómo 1) detectar una versión ya instalada de la biblioteca o herramienta que está convirtiendo en alien, 2) descargar y construir la biblioteca o herramienta que está convirtiendo en alien y 3) recopilar los ajustes de configuración necesarios para el uso de esa biblioteca o herramienta.
Un instalador "Makefile.PL" o "Build.PL" o un "dist.ini" si está utilizando Dist::Zilla
Esta es una capa delgada entre su receta alienfile y el instalador de Perl (ya sea ExtUtils::MakeMaker o Module::Build).
Una clase de Perl (archivo .pm) que hereda de Alien::Base
Para la mayoría de los Aliens, esto no necesita ser personalizado en absoluto, ya que Alien::Base generalmente hace lo que necesita.

Por ejemplo, si estuviera convirtiendo en alien una biblioteca llamada libfoo, podría tener estos archivos:

Alien-Libfoo-1.00/Makefile.PL
Alien-Libfoo-1.00/alienfile
Alien-Libfoo-1.00/lib/Alien/Libfoo.pm

Este documento se centrará principalmente en instruirle sobre cómo construir un alienfile, pero también cubriremos brevemente cómo hacer un simple "Makefile.PL" o "dist.ini" para acompañarlo. También abordaremos cuándo podría querer extender su subclase para agregar funcionalidad no estándar.

Uso de comandos

La mayoría de las bibliotecas y herramientas de software vendrán con instrucciones sobre cómo instalarlas en forma de comandos que usted está destinado a escribir manualmente en un shell. La forma más fácil de automatizar esas instrucciones es simplemente poner los comandos en su alienfile. Por ejemplo, supongamos que libfoo se construye utilizando autoconf y proporciona un "pkg-config" ".pc" archivo.

También discutiremos más adelante los complementos. Para sistemas de construcción comunes como autoconf o CMake, generalmente es mejor usar el complemento apropiado porque manejarán los casos especiales mejor que un simple conjunto de comandos. Vamos a echar un vistazo a los comandos primero porque es más fácil entender las diferentes fases con comandos.

(Aparte, autoconf es una serie de herramientas y macros utilizadas para configurar (generalmente) una biblioteca o herramienta de C o C++ generando cualquier número de Makefiles. Es el equivalente en C a ExtUtils::MakeMaker, si se quiere. Básicamente, si las instrucciones de su biblioteca o herramienta comienzan con './configure', es muy probable que sea una biblioteca o herramienta basada en autoconf).

(Aparte2, "pkg-config" es una forma más o menos estándar de proporcionar los indicadores de compilación y enlace necesarios para compilar y enlazar contra la biblioteca. Si su herramienta instala un ".pc" archivo, generalmente en "$PREFIX/lib/pkgconfig" entonces, su herramienta usa "pkg-config").

Aquí está el alienfile que podría tener:

use alienfile;

probe [ 'pkg-config --exists libfoo' ];

share {

  start_url 'http://www.libfoo.org/src/libfoo-1.00.tar.gz';

  download [ 'wget %{.meta.start_url}' ];

  extract [ 'tar zxf %{.install.download}' ];

  build [
    [ './configure --prefix=%{.install.prefix} --disable-shared' ],
    [ '%{make}' ],
    [ '%{make} install' ],
  ];

};

gather [
  [ 'pkg-config --modversion libfoo', \'%{.runtime.version}' ],
  [ 'pkg-config --cflags     libfoo', \'%{.runtime.cflags}'  ],
  [ 'pkg-config --libs       libfoo', \'%{.runtime.libs}'    ],
];

Hay mucho ocurriendo aquí, así que vamos a decodificarlo un poco. Un alienfile es solo algo de Perl con algo de azúcar específico de alien. La primera línea

use alienfile;

importa el azúcar en el alienfile. También es un indicador para el lector de que esto es un alienfile y no algún otro tipo de script de Perl.

La segunda línea es la directiva probe:

probe [ 'pkg-config --exists libfoo' ];

se utiliza para ver si la biblioteca ya está instalada en el sistema de destino. Si "pkg-config" está en el path, y si libfoo está instalado, esto debería salir con un éxito (0) y decirle a Alien::Build que use la biblioteca del sistema. Si "pkg-config" no está en el PATH, o si libfoo no está instalado, entonces saldrá con un no éxito (!= 0) y le dirá a Alien::Build que descargue y construya desde el código fuente.

Puede proporcionar tantas directivas probe como quiera. Esto es útil si hay diferentes formas de sondear el sistema. Alien::Build se detendrá en la primera biblioteca del sistema encontrada con éxito. Digamos que nuestra biblioteca libfoo viene con un ".pc" archivo para usar con "pkg-config" y también proporciona un "foo-config" programa para encontrar los mismos valores. Podría especificar esto en su alienfile

probe [ 'pkg-config --exists libfoo' ];
probe [ 'foo-config --version' ];

Otras directivas pueden especificarse varias veces si hay diferentes métodos que se pueden intentar para los varios pasos.

A veces es más fácil sondear una biblioteca desde Perl en lugar de con un comando. Para eso puede usar una referencia de código. Por ejemplo, otra forma de llamar a "pkg-config" sería desde Perl:

probe sub {
  my($build) = @_;  # $build es la instancia de Alien::Build.
  system 'pkg-config --exists libfoo';
  $? == 0 ? 'system' : 'share';
};

El código de Perl debería devolver 'system' si la biblioteca está instalada, y 'share' si no lo está. (Otras directivas deberían devolver un valor verdadero en éxito, y un valor falso en fallo). También puede lanzar una excepción con "die" para indicar un fallo.

La siguiente parte del alienfile es el bloque "share" que se utiliza para agrupar las directivas que se usan para descargar e instalar la biblioteca o herramienta en el caso de que no esté ya instalada.

share {
  start_url 'http://www.libfoo.org/src/libfoo-1.00.tar.gz';
  download [ 'wget %{.meta.start_url}' ];
  extract [ 'tar zxf %{.install.download}' ];
  build [
    [ './configure --prefix=%{.install.prefix} --disable-shared' ],
    [ '%{make}' ],
    [ '%{make} install' ],
  ];
};

El start_url especifica dónde encontrar el paquete que está convirtiendo en alien. Debería ser ya sea un tarball (o archivo zip, o lo que sea) o un índice HTML. La directiva download como puede imaginar especifica cómo descargar la biblioteca o herramienta. La directiva extract especifica cómo extraer el archivo una vez que se ha descargado. En el paso de extracción, puede usar la variable "%{.install.download}" como un marcador de posición para el archivo que se descargó en el paso de descarga. Esto también es accesible si usa una referencia de código desde la instancia de Alien::Build:

share {
  ...
  requires 'Archive::Extract';
  extract sub {
    my($build) = @_;
    my $tarball = $build->install_prop->{download};
    my $ae = Archive::Extract->new( archive => $tarball );
    $ae->extract;
    1;
  }
  ...
};

La directiva build especifica cómo construir la biblioteca o herramienta una vez que se ha descargado y extraído. Note que la variable especial "%{.install.prefix}" es la ubicación donde la biblioteca debería ser instalada. "%{make}" es un asistente que será reemplazado por el "make"apropiado, que puede llamarse de manera diferente en algunas plataformas (en Windows por ejemplo, frecuentemente puede llamarse "nmake" o "dmake").

La parte final del alienfile tiene una directiva gather que especifica cómo obtener los detalles sobre cómo compilar y enlazar contra la biblioteca. Para esto, una vez más usamos el comando "pkg-config" :

gather [
  [ 'pkg-config --modversion libfoo', \'%{.runtime.version}' ],
  [ 'pkg-config --cflags     libfoo', \'%{.runtime.cflags}'  ],
  [ 'pkg-config --libs       libfoo', \'%{.runtime.libs}'    ],
];

La referencia escalar como último elemento de la lista de comandos le indica a Alien::Build que la salida del comando debe almacenarse en la variable dada. Las variables de ejecución (runtime) son las que estarán disponibles en "Alien::Libfoo" una vez que esté instalado. (Las propiedades de instalación, que son las que hemos visto hasta ahora, se descartan una vez que la distribución Alien está instalada.

También puedes proporcionar un "sys" bloque para las directivas que deben usarse cuando se detecta una instalación del sistema. Normalmente solo necesitas hacer esto si el paso de recopilación (gather) es diferente entre las instalaciones compartidas (share) y del sistema. Por ejemplo, lo anterior es equivalente a:

build {
  ...
  gather [
    [ 'pkg-config --modversion libfoo', \'%{.runtime.version}' ],
    [ 'pkg-config --cflags     libfoo', \'%{.runtime.cflags}'  ],
    [ 'pkg-config --libs       libfoo', \'%{.runtime.libs}'    ],
  ];
};

sys {
  gather [
    [ 'pkg-config --modversion libfoo', \'%{.runtime.version}' ],
    [ 'pkg-config --cflags     libfoo', \'%{.runtime.cflags}'  ],
    [ 'pkg-config --libs       libfoo', \'%{.runtime.libs}'    ],
  ];
};

(A propósito, la razón por la que se llama "sys" y no "system" es para que no entre en conflicto con la función incorporada "system" )!

Uso de plugins

El primer ejemplo es una buena manera de mostrar el camino manual completo que puedes elegir, pero hay mucha repetición si estás haciendo muchos Aliens que usan autoconf y "pkg-config" (lo cual es bastante común). alienfile te permite usar plugins. Ver Alien::Build::Plugin para una lista de algunas de las categorías de plugins.

Por ahora, solo te mostraré cómo escribir el alienfile para libfoo de arriba usando Alien::Build::Plugin::Build::Autoconf, Alien::Build::Plugin::PkgConfig::Negotiate, Alien::Build::Plugin::Download::Negotiate, y Alien::Build::Plugin::Extract::Negotiate

use alienfile;

plugin 'PkgConfig' => (
  pkg_name => 'libfoo',
);

share {
  start_url 'http://www.libfoo.org/src';
  plugin 'Download' => (
    filter => qr/^libfoo-[0-9\.]+\.tar\.gz$/,
    version => qr/^libfoo-([0-9\.]+)\.tar\.gz$/,
  );
  plugin 'Extract' => 'tar.gz';
  plugin 'Build::Autoconf';
  build [
    '%{configure} --disable-shared',
    '%{make}',
    '%{make} install',
  ];
};

El primer plugin que usamos es el "pkg-config" plugin de negociación. Un plugin de negociación es uno que no hace el trabajo real, sino que selecciona el mejor de un conjunto de plugins dependiendo de tu plataforma y entorno. (En el caso de Alien::Build::Plugin::PkgConfig::Negotiate, puede optar por usar herramientas de línea de comandos, una implementación pura en Perl (PkgConfig), o libpkgconf, dependiendo de lo que esté disponible). Al usar plugins de negociación puedes omitir el "::Negotiate" sufijo. Así que como puedes ver, usar el plugin aquí es una ventaja porque es más confiable que simplemente especificar un comando que puede no estar instalado.

A continuación usamos el plugin de negociación de descarga. Esto también es mejor que la versión de arriba, porque de nuevo, "wget" puede no estar instalado en el sistema de destino. Además, puedes especificar una URL que será escaneada en busca de enlaces, y usar la versión más reciente.

Usamos el plugin de negociación de extracción (Extract) para usar herramientas de línea de comandos, o bibliotecas de Perl para extraer del archivo una vez que se ha descargado.

Finalmente usamos el plugin de Autoconf (Alien::Build::Plugin::Build::Autoconf). Esto es mucho más sofisticado y confiable que en el ejemplo anterior, por varias razones. Esta versión incluso funcionará en Windows asumiendo que la biblioteca o herramienta que estás alienizando soporta esa plataforma.

Estrictamente hablando, la directiva build no es necesaria, porque el plugin de autoconf proporciona un valor predeterminado que es razonable. La única razón por la que querrías incluirla es si necesitas proporcionar banderas adicionales al paso de configuración.

share {
  ...
  build [
    '%{configure} --enable-bar --enable-baz --disable-shared',
    '%{make}',
    '%{make} install',
  ];
};

Múltiples archivos .pc

Algunos paquetes vienen con múltiples bibliotecas emparejadas con múltiples ".pc" archivos. En este caso, quieres proporcionar a Alien::Build::Plugin::PkgConfig::Negotiate una referencia de array de nombres de paquetes.

plugin 'PkgConfig' => (
  pkg_name => [ 'foo', 'bar', 'baz' ],
);

Todos los paquetes deben ser encontrados para que la instalación "system" tenga éxito. Una vez instalado, el primer "pkg_name" será usado por defecto (en este ejemplo "foo"), y puedes recuperar cualquier otro "pkg_name" usando el método alt de Alien::Base.

Una nota sobre bibliotecas dinámicas vs. estáticas

Si estás usando tu Alien para construir un módulo XS, es importante que uses bibliotecas estáticas si es posible. Si tienes un paquete que se niega a construir una biblioteca estática, entonces puedes usar Alien::Role::Dino.

En realidad, déjame retroceder un minuto. Para una "share" instalación, es mejor usar bibliotecas estáticas para construir tu extensión XS. Esto se debe a que si tu Alien es actualizado alguna vez a una nueva versión, puede romper tus módulos XS existentes. Para una "system" instalación, las bibliotecas compartidas son generalmente las mejores porque a menudo puedes obtener parches de seguridad sin tener que reconstruir nada en el mundo de perl.

Si miraste de cerca las secciones "Usando comandos" y "Usando plugins" de arriba, puedes notar que nos esforzamos donde fue posible por decirle a Autotools que construya solo bibliotecas estáticas usando el "--disable-shared" comando. El plugin de Autoconf también hace esto por defecto.

Sin embargo, a veces tendrás un paquete que construye ambos, o tal vez quieras que tanto las bibliotecas estáticas como las dinámicas funcionen con XS y FFI. Para ese caso, está el plugin Alien::Build::Plugin::Gather::IsolateDynamic.

use alienfile;
...
plugin 'Gather::IsolateDynamic';

Lo que hace es que mueve las bibliotecas dinámicas (usualmente .so en Unix y .DLL en Windows) a un lugar donde puedan ser encontradas por FFI, y donde no serán usadas por el compilador para construir XS. Generalmente no hace ningún daño incluir este plugin, así que si estás empezando, podrías querer agregarlo de todos modos. Se puede argumentar que debería haber sido el comportamiento predeterminado desde el principio.

Si ya has publicado un Alien que no aísla sus bibliotecas dinámicas, entonces podrías obtener algunos fallos de aliens antiguos actualizados porque el directorio share no se limpia por defecto (esto es quizás un error de diseño en la forma en que funcionan los directorios share, pero es una característica de larga data). Una solución para esto es usar la "clean_install" propiedad en Alien::Build::MM, que limpiará el directorio share en la actualización, y posiblemente te ahorre mucha angustia.

Integración con MakeMaker

Una vez que tengas un alienfile que funcione, puedes escribir tu "Makefile.PL".

use ExtUtils::MakeMaker;
use Alien::Build::MM;

my $abmm = Alien::Build::MM->new;

WriteMakefile($abmm->mm_args(
  ABSTRACT           => 'Discover or download and install libfoo',
  DISTNAME           => 'Alien-Libfoo',
  NAME               => 'Alien::Libfoo',
  VERSION_FROM       => 'lib/Alien/Libfoo.pm',
  CONFIGURE_REQUIRES => {
    'Alien::Build::MM' => 0,
  },
  BUILD_REQUIRES => {
    'Alien::Build::MM' => 0,
  },
  PREREQ_PM => {
    'Alien::Base' => 0,
  },
  # If you are going to write the recommended
  # tests you will will want these:
  TEST_REQUIRES => {
    'Test::Alien' => 0,
    'Test2::V0'   => 0,
  },
));

sub MY::postamble {
  $abmm->mm_postamble;
}

El "lib/Alien/Libfoo.pm" que lo acompaña es muy simple:

package Alien::Libfoo;

use strict;
use warnings;
use parent qw( Alien::Base );

1;

¡Ya has terminado y puedes instalarlo normalmente!:

% perl Makefile.PL
% make
% make test
% make install

Configuración no estándar

Alien::Base soporta la mayoría de las cosas que tu Alien necesitará, como flags de compilación (cflags), flags de enlace (libs) y directorio de binarios (bin_dir). Tu biblioteca u herramienta puede tener otros elementos de configuración que no son soportados por defecto. Puedes almacenar los valores en el alienfile dentro de las propiedades de tiempo de ejecución (runtime):

gather [
  # estándar:
  [ 'foo-config --version libfoo', \'%{.runtime.version}' ],
  [ 'foo-config --cflags  libfoo', \'%{.runtime.cflags}'  ],
  [ 'foo-config --libs    libfoo', \'%{.runtime.libs}'    ],
  # no estándar
  [ 'foo-config --bar-baz libfoo', \'%{.runtime.bar_baz}' ],
];

luego puedes exponerlos en tu subclase de Alien::Base:

package Alien::Libfoo;

use strict;
use warnings;
use parent qw( Alien::Base );

sub bar_baz {
  my($self) = @_;
  $self->runtime_prop->{bar_baz},
};

1;

Pruebas

(opcional, pero muy recomendado)

Deberías escribir una prueba usando Test::Alien para asegurarte de que tu alien funcionará con cualquier módulo XS que vaya a usarlo:

use Test2::V0;
use Test::Alien;
use Alien::Libfoo;

alien_ok 'Alien::Libfoo';

xs_ok do { local $/; <DATA> }, with_subtest {
  is Foo::something(), 1, 'Foo::something() returns 1';
};

done_testing;

__DATA__
#include "EXTERN.h"
#include "perl.h"
#include "XSUB.h"
#include <foo.h>

MODULE = Foo PACKAGE = Foo

int something()

También puedes usar Test::Alien para probar herramientas en lugar de bibliotecas:

use Test2::V0;
use Test::Alien;
use Alien::Libfoo;

alien_ok 'Alien::Libfoo';
run_ok(['foo', '--version'])
  ->exit_is(0);

done_testing;

También puedes escribir pruebas específicas para FFI::Platypus, si tu alien va a ser usado para escribir bindings de FFI. (la prueba de abajo es el equivalente en FFI al ejemplo XS de arriba).

use Test2::V0;
use Test::Alien;
use Alien::Libfoo;

alien_ok 'Alien::Libfoo';
ffi_ok { symbols => [ 'something' ] }, with_subtest {
  # $ffi es una instancia de FFI::Platypus con la lib
  # configurada apropiadamente.
  my($ffi) = @_;
  my $something = $ffi->function( something => [] => 'int' );
  is $something->call(), 1, 'Foo::something() returns 1';
};

Si usas "ffi_ok" quieres asegurarte de que tu alien produzca bibliotecas dinámicas de manera fiable. Si no es consistente (si por ejemplo algunas plataformas tienden a no proporcionar o compilar bibliotecas dinámicas), puedes verificar que "dynamic_libs" no devuelva una lista vacía.

...
alien_ok 'Alien::Libfoo';
SKIP: {
  skip "This test requires a dynamic library"
    unless Alien::Libfoo->dynamic_libs;
  ffi_ok { symbols [ 'something' ] }, with_subtest {
    ...
  };
}

Puedes encontrar más detalles sobre las pruebas de módulos Alien en la documentación de Test::Alien.

También puedes ejecutar las pruebas que vienen con el paquete que estás alienizando, usando un bloque "test" en tu alienfile. Ten en cuenta que algunos paquetes usan herramientas de prueba u otros prerrequisitos que no estarán disponibles en las máquinas de tus usuarios cuando intenten instalar tu alien. Así que no quieres añadir ciegamente un bloque de prueba sin verificar cuáles son los prerrequisitos. Para paquetes al estilo de Autoconf típicamente pruebas un paquete usando el comando "make check" :

use alienfile;

plugin 'PkgConfig' => 'libfoo';

share {
  ... # pasos de compilación estándar.
  test [ '%{make} check' ];
};
