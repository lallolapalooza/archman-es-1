DESCRIPCIÓ

N

La función alarm() hará que el sistema genere una señal SIGALRM para el proceso después de que hayan transcurrido el número de segundos de tiempo real especificado por seconds. Los retrasos en la planificación del procesador pueden impedir que el proceso maneje la señal tan pronto como se

genera.

Si seconds es 0, una solicitud de alarma pendiente, si la hay, es

cancelada.

Las solicitudes de alarma no se acumulan; solo se puede programar una generación de SIGALRM de esta manera. Si la señal SIGALRM aún no se ha generado, la llamada resultará en la reprogramación del momento en que se genere la señal

SIGALRM.

Las interacciones entre alarm() y setitimer() no están

espe
cificadas.

USO EN

APLICACIONES

La función fork() borra las alarmas pendientes en el proceso hijo. Una nueva imagen de proceso creada por una de las funciones exec hereda el tiempo restante para una señal de alarma en la imagen del proceso

antiguo.

Los desarrolladores de aplicaciones deben tener en cuenta que el tipo del argumento seconds y el valor de retorno de alarm() es unsigned. Eso significa que una Aplicación de Interfaces de Sistema POSIX Estrictamente Conforme no puede pasar un valor mayor que el valor mínimo garantizado para {UINT_MAX}, que el estándar ISO C establece como 65535, y cualquier aplicación que pase un valor mayor está restringiendo su portabilidad. Se consideró un tipo diferente, pero las implementaciones históricas, incluidas aquellas con un tipo int de 16 bits, usan consistentemente o bien unsigned o int

.

Los desarrolladores de aplicaciones deben ser conscientes de posibles interacciones cuando el mismo proceso usa tanto la función alarm() como la función

slee
p().

JUSTIFICACIÓ

N

Muchas implementaciones históricas (incluyendo Version 7 y System V) permiten que una alarma ocurra hasta un segundo antes. Otras implementaciones permiten alarmas hasta medio segundo o un tic de reloj antes, o no permiten que ocurran antes en absoluto. Esta última se considera la más apropiada, ya que proporciona el comportamiento más predecible, especialmente dado que la señal siempre puede retrasarse por un tiempo indefinido debido a la planificación. Las aplicaciones pueden así elegir el argumento seconds como la cantidad mínima de tiempo que desean que transcurra antes de la

señal.

El término "tiempo real" aquí y en otros lugares (sleep(), times()) pretende significar tiempo de "reloj de pared" como uso común del inglés inglés, y no tiene nada que ver con "sistemas operativos de tiempo real". Está en contraste con el tiempo virtual, que podría malinterpretarse si solo se usara time

.

En algunas implementaciones, incluyendo 4.3 BSD, valores muy grandes del argumento seconds se redondean silenciosamente hacia abajo a un valor máximo específico de la implementación. Este máximo es lo suficientemente grande (del orden de varios meses) como para que el efecto no sea

notable.

Había dos opciones posibles para la generación de alarmas en aplicaciones multihilo: generación para el hilo que llama o generación para el proceso. La primera opción no habría sido particularmente útil ya que el estado de la alarma se mantiene a nivel de proceso y la alarma establecida por la última invocación de alarm() es la única que estaría

activa.

Además, permitir la generación de una señal asincrónica para un hi

lo habría introducido una excepción al modelo general de seña
les. Esto requiere una razón convincente para ser justificado.
