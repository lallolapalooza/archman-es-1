DESCRIPCIÓ

N

ALTER TABLE cambia la definición de una tabla existente. Hay varias subformas descritas a continuación. Tenga en cuenta que el nivel de bloqueo requerido puede diferir para cada subforma. Se adquiere un bloqueo ACCESS EXCLUSIVE a menos que se indique explícitamente lo contrario. Cuando se dan múltiples subcomandos, el bloqueo adquirido será el más estricto requerido por cualquier

subcomando.

ADD COLUMN [ IF NOT EXISTS

]
Esta forma añade una nueva columna a la tabla, usando la misma sintaxis que CREATE TABLE. Si se especifica IF NOT EXISTS y ya existe una columna con este nombre, no se lanza ningún
error.

DROP COLUMN [ IF EXISTS

]
Esta forma elimina una columna de una tabla. Los índices y las restricciones de tabla que involucren la columna también serán eliminados automáticamente. Las estadísticas multivariadas que referencien la columna eliminada también serán removidas si la eliminación de la columna haría que las estadísticas contengan datos de solo una sola columna. Necesitará decir CASCADE si algo fuera de la tabla depende de la columna, por ejemplo, referencias de clave externa o vistas. Si se especifica IF EXISTS y la columna no existe, no se lanza ningún error. En este caso, se emite en su lugar un
aviso.

SET DATA

TYPE
Esta forma cambia el tipo de una columna de una tabla. Los índices y las restricciones simples de tabla que involucren la columna serán convertidos automáticamente para usar el nuevo tipo de columna, reanalizando la expresión originalmente proporcionada. La cláusula opcional COLLATE especifica una ordenación para la nueva columna; si se omite, la ordenación es la predeterminada para el nuevo tipo de columna. La cláusula opcional USING especifica cómo calcular el nuevo valor de la columna a partir del antiguo; si se omite, la conversión predeterminada es la misma que una conversión de asignación del tipo de datos antiguo al nuevo. Se debe proporcionar una cláusula USING si no hay una conversión implícita o de asignación del tipo antiguo al nuevo.

Cuando se usa esta forma, las estadísticas de la columna son eliminadas, por lo que se recomienda ejecutar ANALYZE en la tabla después. Para una columna generada virtual, ANALYZE no es necesario porque tales c

Estas formas establecen o eliminan el valor predeterminado para una columna (donde la eliminación equivale a establecer el valor predeterminado a NULL). El nuevo valor predeterminado solo se aplicará en comandos INSERT o UPDATE posteriores; no causa que las filas ya existentes en la tabla
cambien.

SET/DROP NOT

NULL
Estas formas cambian si una columna está marcada para permitir valores nulos o para rechazar valores nulos.

SET NOT NULL solo se puede aplicar a una columna siempre que ninguno de los registros de la tabla contenga un valor NULL para la columna. Ordinariamente esto se verifica durante el ALTER TABLE escaneando toda la tabla, a menos que se especifique NOT VALID; sin embargo, si existe una restricción CHECK válida (y no se elimina en el mismo comando) que demuestre que no puede existir ningún NULL, entonces el escaneo de la tabla se omite. Si una columna tiene una restricción not-null inválida, SET NOT NULL la

valida.

Si esta tabla es una partición, no se puede realizar DROP NOT NULL en una columna si está marcada como NOT NULL en la tabla padre. Para eliminar la restricción NOT NULL de todas las particiones, realice

DROP NOT NULL en la tabla padre. Incluso si no hay una restricción NOT NULL en la tabla padre, una restricción de este tipo aún se puede agregar a particiones individuales, si se desea; es decir, lo
s hijos pueden rechazar nulos incluso si el padre los permite, pero no de la manera inversa. También es posible eliminar la restricción NOT NULL de SOLO la tabla padre, lo que no la elimina de los hijos.

Esta forma establece o restablece opciones por atributo. Actualmente, las únicas opciones por atributo definidas son n_distinct y n_distinct_inherited, que anulan las estimaciones del número de valores distintos realizadas por las operaciones ANALYZE posteriores. n_distinct afecta las estadísticas de la tabla en sí, mientras que n_distinct_inherited afecta las estadísticas recopiladas para la tabla más sus hijos de herencia, y para las estadísticas recopiladas para tablas particionadas. Cuando el valor especificado es un valor positivo, el planificador de consultas asumirá que la columna contiene exactamente el número especificado de valores no nulos distintos. También se pueden especificar valores fraccionarios utilizando valores por debajo de 0 y por encima o igual a -1. Esto le indica al planificador de consultas que estime el número de valores distintos multiplicando el valor absoluto del número especificado por el número estimado de filas en la tabla. Por ejemplo, un valor de -1 implica que todos los valores en la columna son distintos, mientras que un valor de -0.5 implica que cada valor aparece dos veces en promedio. Esto puede ser útil cuando el tamaño de la tabla cambia con el tiempo. SET STORAGE { PLAIN | EXTERNAL | EXTENDED | MAIN | DEFAULT

}
Esta forma establece el modo de almacenamiento para una columna. Esto controla si esta columna se mantiene en línea o en una tabla TOAST secundaria, y si los datos deben comprimirse o no. PLAIN debe usarse para valores de longitud fija como integer y está en línea, sin comprimir. MAIN es para datos en línea, comprimibles. EXTERNAL es para datos externos, sin comprimir, y EXTENDED es para datos externos, comprimidos. Escribir DEFAULT establece el modo de almacenamiento en el modo predeterminado para el tipo de datos de la columna. EXTENDED es el predeterminado para la mayoría de los tipos de datos que admiten almacenamiento que no sea PLAIN. El uso de EXTERNAL hará que las operaciones de subcadena en valores de texto y bytea muy grandes se ejecuten más rápido, a costa de un mayor espacio de almacenamiento. Tenga en cuenta que ALTER TABLE ... SET STORAGE no cambia nada en la tabla en sí; solo establece la estrategia a seguir durante las actualizaciones futuras de la tabla. Consulte la Sección 66.2 para obtener más
información.

SET COMPRESSION compression_metho

d
Esta forma establece el método de compresión para una columna, determinando cómo se comprimirán los valores insertados en el futuro (si el modo de almacenamiento permite la compresión en absoluto). Esto no hace que la tabla se reescriba, por lo que los datos existentes aún pueden estar comprimidos con otros métodos de compresión. Si la tabla se restaura con pg_restore, todos los valores se reescriben con el método de compresión configurado. Sin embargo, cuando los datos se insertan desde otra relación (por ejemplo, mediante INSERT ... SELECT), los valores de la tabla de origen no necesariamente se des-TOASTean, por lo que cualquier dato previamente comprimido puede conservar su método de compresión existente, en lugar de ser recomprimido con el método de compresión de la columna de destino. Los métodos de compresión admitidos son pglz y lz4. (lz4 solo está disponible si --with-lz4 se usó al compilar PostgreSQL.) Además, compression_method puede ser default, que selecciona el comportamiento predeterminado de consultar la configuración default_toast_compression en el momento de la inserción de datos para determinar el método a
utilizar.

ADD table_constraint [ NOT VALID

]
Esta forma agrega una nueva restricción a una tabla utilizando la misma sintaxis de restricción que CREATE TABLE, más la opción NOT VALID, que actualmente solo se permite para restricciones de clave externa, CHECK y not-null.

Normalmente, esta forma hará que se escanee la tabla para verificar que todas las filas existentes en la tabla satisfagan la nueva restricción. Pero si se usa la opción NOT VALID, este escaneo potencialmente largo se omite. La restricción aún se aplicará a las inserciones o actualizaciones posteriores (es decir, fallarán a menos que exista una fila coincidente en la tabla referenciada, en el caso de las claves externas, o fallarán a menos que la nueva fila coincida con la condición de verificación especificada). Pero la base de datos no asumirá que la restricción se cumple para todas las filas de la tabla, hasta que se valide mediante el uso de la opción VALIDATE CONSTRAINT. Consulte las Notas a continuación para obtener más información sobre el uso de la opción NOT

VALID.

Tenga en cuenta que ADD FOREIGN KEY también adquiere un bloqueo SHARE ROW EXCLUSIVE en la tabla referenciada, además del bloqueo en la tabla en la que se declara la

restricción.

Esta forma agrega una nueva restricción PRIMARY KEY o UNIQUE a una tabla basándose en un índice único existente. Todas las columnas del índice se incluirán en la restricción.

El índice no puede tener columnas de expresión ni ser un índice parcial. Además, debe ser un índice b-tree con orden de clasificación predeterminado. Estas restricciones garantizan que el índice sea equivalente a uno que sería construido por un comando regular ADD PRIMARY KEY o ADD

UNIQUE.

Si se especifica PRIMARY KEY, y las columnas del índice no están ya marcadas como NOT NULL, entonces este comando intentará realizar ALTER COLUMN SET NOT NULL contra cada una de esas columnas. Eso requiere un escaneo completo de la tabla para verificar que la(s) columna(s) no contenga(n) nulos. En todos los demás casos, esta es una operación

rápida.

Si se proporciona un nombre de restricción, el índice se renombrará para coincidir con el nombre de la restricción. De lo contrario, la restricción se nombrará igual que el

índice.

Después de que se ejecute este comando, el índice es “propiedad” de la restricción, de la misma manera que si el índice hubiera sido construido por un comando regular ADD PRIMARY KEY o ADD UNIQUE. En particular, eliminar la restricción hará que el índice también

desaparezca.

Esta forma actualmente no es compatible con las tablas

particionadas.

ATTACH PARTITION partition_name { FOR VALUES partition_bound_spec | DEFAULT

}
Esta forma adjunta una tabla existente (que a su vez puede estar particionada) como una partición de la tabla de destino. La tabla se puede adjuntar como una partición para valores específicos usando FOR VALUES o como una partición predeterminada usando DEFAULT. Para cada índice en la tabla de destino, se creará uno correspondiente en la tabla adjunta; o, si ya existe un índice equivalente, se adjuntará al índice de la tabla de destino, como si se hubiera ejecutado ALTER INDEX ATTACH PARTITION. Nótese que si la tabla existente es una tabla externa, actualmente no se permite adjuntar la tabla como una partición de la tabla de destino si hay índices UNIQUE en la tabla de destino. (Véase también CREATE FOREIGN TABLE (CREATE_FOREIGN_TABLE(7)).) Para cada disparador a nivel de fila definido por el usuario que exista en la tabla de destino, se crea uno correspondiente en la tabla adjunta.

Una partición que usa FOR VALUES utiliza la misma sintaxis para partition_bound_spec que CREATE TABLE. La especificación de límites de la partición debe corresponder a la estrategia de partición y a la clave de partición de la tabla de destino. La tabla que se va a adjuntar debe tener todas las mismas columnas que la tabla de destino y ninguna más; además, los tipos de columna deben coincidir también. Además, debe tener todas las restricciones NOT NULL y CHECK de la tabla de destino, no marcadas como NO INHERIT. Actualmente, las restricciones FOREIGN KEY no se consideran. Las restricciones UNIQUE y PRIMARY KEY de la tabla padre se crearán en la partición, si no existen

ya.

Si la nueva partición es una tabla normal, se realiza un escaneo completo de la tabla para comprobar que las filas existentes en la tabla no violan la restricción de partición. Es posible evitar este escaneo añadiendo una restricción CHECK válida a la tabla que solo permita filas que satisfagan la restricción de partición deseada antes de ejecutar este comando. La restricción CHECK se utilizará para determinar que no es necesario escanear la tabla para validar la restricción de partición. Sin embargo, esto no funciona si alguna de las claves de partición es una expresión y la partición no acepta valores NULL. Si se adjunta una partición de lista que no aceptará valores NULL, añada también una restricción NOT NULL a la columna de clave de partición, a menos que sea una

expresión.

Si la nueva partición es una tabla externa, no se hace nada para verificar que todas las filas de la tabla externa obedezcan la restricción de partición. (Véase la discusión en CREATE FOREIGN TABLE (CREATE_FOREIGN_TABLE(7)) sobre restricciones en la tabla externa.

)

Cuando una tabla tiene una partición predeterminada, definir una nueva partición cambia la restricción de partición para la partición predeterminada. La partición predeterminada no puede contener ninguna fila que necesite ser movida a la nueva partición, y se escaneará para verificar que no haya ninguna. Este escaneo, al igual que el de la nueva partición, se puede evitar si hay una restricción CHECK apropiada presente. Al igual que con el escaneo de la nueva partición, siempre se omite cuando la partición predeterminada es una tabla

externa.

Adjuntar una partición adquiere un bloqueo SHARE UPDATE EXCLUSIVE en la tabla padre, además de los bloqueos ACCESS EXCLUSIVE en la tabla que se adjunta y en la partición predeterminada (si la hay)

una tabla particionada. Del mismo modo, si la partición predeterminada es en sí misma una tabla particionada. El bl

DETACH PARTITION partition_name [ CONCURRENTLY | FINALIZE

]
Esta forma separa la partición especificada de la tabla de destino. La partición separada continúa existiendo como una tabla independiente, pero ya no tiene ningún vínculo con la tabla de la que fue separada. Cualquier índice que estuviera adjunto a los índices de la tabla de destino se separa. Cualquier disparador que fuera creado como clon de los de la tabla de destino se elimina. Se obtiene un bloqueo SHARE en cualquier tabla que referencie a esta tabla particionada en restricciones de clave externa.

Si se especifica CONCURRENTLY, se ejecuta usando un nivel de bloqueo reducido para evitar bloquear otras sesiones que puedan estar accediendo a la tabla particionada. En este modo, se usan internamente dos transacciones. Durante la primera transacción, se toma un bloqueo SHARE UPDATE EXCLUSIVE tanto en la tabla padre como en la partición, y la partición se marca como en proceso de separación; en ese punto, la transacción se confirma y se espera a todas las demás transacciones que usen la tabla particionada. Una vez que todas esas transacciones han completado, la segunda transacción adquiere SHARE UPDATE EXCLUSIVE en la tabla particionada y ACCESS EXCLUSIVE en la partición, y el proceso de separación se completa. Se añade a la partición una restricción CHECK que duplica la restricción de partición. CONCURRENTLY no se puede ejecutar en un bloque de transacción y no se permite si la tabla particionada contiene una partición

predeterminada.

Si se especifica FINALIZE, se completa una invocación previa de DETACH C

ONCURRENTLY que fue cancelada o interrumpida. Como máximo, una partición
en una tabla particionada puede estar pendiente de separación a la vez.

Todas las formas de ALTER TABLE que actúan sobre una sola tabla, excepto RENAME, SET SCHEMA, ATTACH PARTITION y DETACH PARTITION, se pueden combinar en una lista de múltiples alteraciones para aplicarse juntas. Por ejemplo, es posible añadir varias columnas y/o alterar el tipo de varias columnas en un solo comando. Esto es particularmente útil con tablas grandes, ya que solo se necesita hacer un solo recorrido sobre la

tabla.

Debe ser propietario de la tabla para usar ALTER TABLE. Para cambiar el esquema o el tablespace de una tabla, también debe tener el privilegio CREATE en el nuevo esquema o tablespace. Para añadir la tabla como un nuevo hijo de una tabla padre, también debe ser propietario de la tabla padre. Asimismo, para adjuntar una tabla como una nueva partición de la tabla, debe ser propietario de la tabla que se adjunta. Para alterar el propietario, debe poder hacer SET ROLE al nuevo rol

propietario, y ese rol debe tener el privilegio CREATE en el esquema de la tabla. (Estas restricciones garantizan que alterar el propietario no hace nada que no podría hacer eliminando y recreando la tabla. Sin embargo,
un superusuario puede alterar la propiedad de cualquier tabla de todos modos.) Para añadir una columna o alterar el tipo de una columna o usar la cláusula OF, también debe tener el privilegio USAGE en el tipo de datos.

NOTA

S

La palabra clave COLUMN es redundante y se puede

omitir.

Cuando se añade una columna con ADD COLUMN y se especifica un DEFAULT no volátil, el valor predeterminado se evalúa en el momento de la sentencia y el resultado se almacena en los metadatos de la tabla, donde se devolverá cuando se acceda a cualquier fila existente. El valor solo se aplicará cuando la tabla se reescriba, haciendo que el ALTER TABLE sea muy rápido incluso en tablas grandes. Si no se especifican restricciones de columna, se usa NULL como el DEFAULT. En ninguno de los dos casos se requiere una reescritura de la

tabla.

Añadir una columna con un DEFAULT volátil (por ejemplo, clock_timestamp()), una columna generada almacenada, una columna de identidad, o una columna con un tipo de datos de dominio que tenga restricciones causará que se reescriba la tabla completa y sus índices. Añadir una columna generada virtual nunca requiere una reescritura.rite

.

Cambiar el tipo de una columna existente normalmente provocará que se reescriba toda la tabla y sus índices. Como excepción, al cambiar el tipo de una columna existente, si la cláusula USING no cambia el contenido de la columna y el tipo antiguo es coercible binariamente al nuevo tipo o un dominio sin restricciones sobre el nuevo tipo, no se necesita una reescritura de la tabla. Sin embargo, los índices seguirán reconstruyéndose a menos que el sistema pueda verificar que el nuevo índice sería lógicamente equivalente al existente. Por ejemplo, si la colación de una columna ha sido cambiada, se requiere una reconstrucción del índice porque el nuevo orden de clasificación podría ser diferente. Sin embargo, en ausencia de un cambio de colación, una columna puede cambiarse de text a varchar (o viceversa) sin reconstruir los índices porque estos tipos de datos se ordenan de manera

idéntica.

Las reconstrucciones de tablas y/o índices pueden llevar una cantidad significativa de tiempo para una tabla grande, y temporalmente requerirán hasta el doble del espacio en

disco.

Agregar una restricción CHECK o NOT NULL requiere escanear la tabla para verificar que las filas existentes cumplen la restricción, pero no requiere una reescritura de la tabla. Si se agrega una restricción CHECK como NOT ENFORCED, no se realizará ninguna

verificación.

De manera similar, al adjuntar una nueva partición, se puede escanear para verificar que las filas existentes cumplen la restricción de la

partición.

La razón principal para proporcionar la opción de especificar múltiples cambios en un solo ALTER TABLE es que múltiples escaneos de tablas o reescrituras se puedan combinar en un solo pase sobre la

tabla.

Escanear una tabla grande para verificar nuevas restricciones de clave externa, check o not-null puede llevar mucho tiempo, y otras actualizaciones de la tabla se bloquean hasta que el comando ALTER TABLE ADD CONSTRAINT se confirme. El propósito principal de la opción de restricción NOT VALID es reducir el impacto de agregar una restricción en las actualizaciones concurrentes. Con NOT VALID, el comando ADD CONSTRAINT no escanea la tabla y puede confirmarse inmediatamente. Después de eso, se puede emitir un comando VALIDATE CONSTRAINT para verificar que las filas existentes satisfacen la restricción. El paso de validación no necesita bloquear actualizaciones concurrentes, ya que sabe que otras transacciones harán cumplir la restricción para las filas que insertan o actualizan; solo las filas preexistentes necesitan ser verificadas. Por lo tanto, la validación adquiere solo un bloqueo SHARE UPDATE EXCLUSIVE en la tabla que se está alterando. (Si la restricción es una clave externa, también se requiere un bloqueo ROW SHARE en la tabla referenciada por la restricción.) Además de mejorar la concurrencia, puede ser útil usar NOT VALID y VALIDATE CONSTRAINT en casos donde se sabe que la tabla contiene violaciones preexistentes. Una vez que la restricción está en su lugar, no se pueden insertar nuevas violaciones, y los problemas existentes pueden corregirse a su ritmo hasta que VALIDATE CONSTRAINT finalmente tenga

éxito.

La forma DROP COLUMN no elimina físicamente la columna, sino que simplemente la hace invisible para las operaciones SQL. Las operaciones posteriores de inserción y actualización en la tabla almacenarán un valor nulo para la columna. Así, eliminar una columna es rápido pero no reducirá inmediatamente el tamaño en disco de su tabla, ya que el espacio ocupado por la columna eliminada no se recupera. El espacio se recuperará con el tiempo a medida que se actualicen las filas

existentes.

Para forzar la recuperación inmediata del espacio ocupado por una columna eliminada, puede ejecutar una de las formas de ALTER TABLE que realiza una reescritura de toda la tabla. Esto resulta en la reconstrucción de cada fila con la columna eliminada reemplazada por un valor

nulo.

Las formas de reescritura de ALTER TABLE no son seguras para MVCC. Después de una reescritura de tabla, la tabla parecerá vacía para las transacciones concurrentes, si están usando una instantánea tomada antes de que ocurriera la reescritura. Vea la Sección 13.6 para más

detalles.

La opción USING de SET DATA TYPE puede en realidad especificar cualquier expresión que involucre los valores antiguos de la fila; es decir, puede referirse a otras columnas además de la que se está convirtiendo. Esto permite realizar conversiones muy generales con la sintaxis SET DATA TYPE. Debido a esta flexibilidad, la expresión USING no se aplica al valor predeterminado de la columna (si lo hay); el resultado podría no ser una expresión constante como se requiere para un valor predeterminado. Esto significa que cuando no hay una conversión implícita o de asignación del tipo antiguo al nuevo, SET DATA TYPE podría fallar al convertir el valor predeterminado aunque se proporcione una cláusula USING. En tales casos, elimine el valor predeterminado con DROP DEFAULT, realice el ALTER TYPE y luego use SET DEFAULT para agregar un nuevo valor predeterminado adecuado. Consideraciones similares se aplican a los índices y restricciones que involucran la

columna.

Si una tabla tiene tablas descendientes, no se permite agregar, renombrar o cambiar el tipo de una columna en la tabla padre sin hacer lo mismo con los descendientes. Esto asegura que los descendientes siempre tengan columnas que coincidan con el padre. De manera similar, una restricción CHECK no puede ser renombrada en el padre sin también renombrarla en todos los descendientes, de modo que las restricciones CHECK también coincidan entre el padre y sus descendientes. (Esa restricción no se aplica a las restricciones basadas en índices, sin embargo.) También, porque seleccionar del padre también selecciona de sus descendientes, una restricción en el padre no puede marcarse como válida a menos que también se marque como válida para esos descendientes. En todos estos casos, ALTER TABLE ONLY será

rechazado.

Una operación DROP COLUMN recursiva eliminará la columna de una tabla descendiente solo si el descendiente no hereda esa columna de ningún otro padre y nunca tuvo una definición independiente de la columna. Un DROP COLUMN no recursivo (es decir, ALTER TABLE ONLY ... DROP COLUMN) nunca elimina ninguna columna descendiente, sino que las marca como definidas independientemente en lugar de heredadas. Un comando DROP COLUMN no recursivo fallará para una tabla particionada, porque todas las particiones de una tabla deben tener las mismas columnas que la raíz de la

partición.

Las acciones para columnas de identidad (ADD GENERATED, SET etc., DROP IDENTITY), así como las acciones CLUSTER, OWNER y TABLESPACE nunca se propagan recursivamente a las tablas descendientes; es decir, siempre actúan como si se hubiera especificado ONLY. Las acciones que afectan los estados de los disparadores se propagan recursivamente a las particiones de las tablas particionadas (a menos que se especifique ONLY), pero nunca a los descendientes de herencia tradicional. Agregar una restricción se propaga recursivamente solo para las restricciones CHECK que no están marcadas como NO

INHERIT.

No se permite cambiar ninguna parte de una tabla de catálogo del

sistema.

COMPATIBILIDA

D

Las formas ADD [COLUMN], DROP [COLUMN], DROP IDENTITY, RESTART, SET DEFAULT, SET DATA TYPE (sin USING), SET GENERATED, y SET sequence_option se ajustan al estándar SQL. La forma ADD table_constraint se ajusta al estándar SQL cuando se omiten las cláusulas USING INDEX y NOT VALID y el tipo de restricción es uno de CHECK, UNIQUE, PRIMARY KEY, o REFERENCES. Las demás formas son extensiones de PostgreSQL del estándar SQL. Además, la capacidad de especificar más de una manipulación en un solo comando ALTER TABLE es una

extensión.

ALTER TABLE DROP COLUMN se puede usar para eliminar la única columna de una tabla, dejando una

tabla de cero columnas. Esta es una extensión de
SQL, que prohíbe las tablas de cero columnas.
