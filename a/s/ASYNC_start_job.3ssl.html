DESCRIPCIÓ

N

OpenSSL implementa capacidades asíncronas a través de un ASYNC_JOB. Esto representa código que puede iniciarse y ejecutarse hasta que ocurra algún evento. En ese punto, el código puede pausarse y el control regresa al código del usuario hasta que algún evento posterior indique que el trabajo puede reanudarse. Es la implementación específica de OpenSSL de multitarea

cooperativa.

La creación de un ASYNC_JOB es una operación relativamente costosa. Por lo tanto, por razones de eficiencia, los trabajos pueden crearse por adelantado y reutilizarse muchas veces. Se mantienen en un grupo (pool) hasta que se necesitan, momento en el que se eliminan del grupo, se usan y luego se devuelven al grupo cuando el trabajo se completa. Si la aplicación del usuario es multihilo, entonces ASYNC_init_thread() puede llamarse para cada hilo que iniciará trabajos asíncronos. Antes de que el código del usuario salga, los recursos específicos del hilo deben limpiarse. Esto normalmente ocurrirá automáticamente (ver OPENSSL_init_crypto(3)) pero puede iniciarse explícitamente usando ASYNC_cleanup_thread(). No debe haber trabajos asíncronos pendientes para el hilo cuando ASYNC_cleanup_thread() sea llamado. No asegurarse de esto resultará en fugas de

memoria.

El argumento max_size limita el número de ASYNC_JOBs que se mantendrán en el grupo. Si max_size se establece en 0, entonces no se establece ningún límite superior. Cuando se necesita un ASYNC_JOB pero no hay ninguno disponible en el grupo, se creará uno automáticamente, siempre que el total de ASYNC_JOBs gestionados por el grupo no exceda max_size. Cuando el grupo se inicializa por primera vez, se crearán inmediatamente init_size ASYNC_JOBs. Si ASYNC_init_thread() no se llama antes de que el grupo se use por primera vez, se llamará automáticamente con un max_size de 0 (sin límite superior) y un init_size de 0 (sin ASYNC_JOBs creados por adelantado)

.

Un trabajo asíncrono se inicia llamando a la función ASYNC_start_job(). Inicialmente, *job debería ser NULL. ctx debería apuntar a un objeto ASYNC_WAIT_CTX creado a través de la función ASYNC_WAIT_CTX_new(3). ret debería apuntar a una ubicación donde el valor de retorno de la función asíncrona debería almacenarse al completarse el trabajo. func representa la función que debería iniciarse de forma asíncrona. Los datos a los que apunta args y de tamaño size se copiarán y luego se pasarán como argumento a func cuando el trabajo comience. ASYNC_start_job devolverá uno de los siguientes

valores:
ASYNC_E
RR
Ocurrió un error al intentar iniciar el trabajo. Verifique la cola de errores de OpenSSL (p. ej., ver ERR_print_errors(3)) para más
detalles.
ASYNC_NO_JO
BS
No hay trabajos disponibles actualmente en el grupo. Esta llamada puede reintentarse más
tarde.
ASYNC_PAU
SE
El trabajo se inició correctamente pero fue "pausado" antes de completarse (ver ASYNC_pause_job() más abajo). Un manejador del trabajo se coloca en *job. Se puede realizar otro trabajo (si se desea) y reiniciar el trabajo más tarde. Para reiniciar un trabajo, llame a ASYNC_start_job() de nuevo pasando el manejador del trabajo en *job. Los parámetros func, args y size se ignorarán al reiniciar un trabajo. Al reiniciar un trabajo, ASYNC_start_job() debe ser llamado desde el mismo hilo desde el que el trabajo fue originalmente iniciado. ASYNC_WAIT_CTX se usa para saber cuándo un trabajo está listo para ser
reiniciado.
ASYNC_FINI
SH
El trabajo se completó. *job será NULL y el valor de retorno de func se colocará en *r
et
.

En cualquier momento puede haber un máximo de un trabajo ejecutándose activamente por hilo (puede tener muchos pausados). ASYNC_get_current_job() puede usarse para obtener un puntero al ASYNC_JOB que se está ejecutando actualmente. Si no hay ningún trabajo ejecutándose actualmente, esto devolverá

NULL.

Si se ejecuta dentro del contexto de un trabajo (es decir, habiendo sido llamado directa o indirectamente por la función "func" pasada como argumento a ASYNC_start_job()), entonces ASYNC_pause_job() devolverá inmediatamente el control a la aplicación de llamada con ASYNC_PAUSE devuelto desde la llamada a ASYNC_start_job(). Una llamada posterior a ASYNC_start_job pasando el ASYNC_JOB relevante en el parámetro *job reanudará la ejecución desde la llamada a ASYNC_pause_job(). Si ASYNC_pause_job() se llama mientras no se está dentro del contexto de un trabajo, no se realiza ninguna acción y ASYNC_pause_job() retorna

inmediatamente.

ASYNC_get_wait_ctx() puede usarse para obtener un puntero al ASYNC_WAIT_CTX para el trabajo (ver ASYNC_WAIT_CTX_new(3)). Los ASYNC_WAIT_CTXs contienen dos formas diferentes de notificar a las aplicaciones que un trabajo está listo para ser reanudado. Una es un descriptor de archivo de "espera" (wait), y el otro es un mecanismo de

"callback".

El descriptor de archivo de "espera" asociado con ASYNC_WAIT_CTX se usa para que las aplicaciones esperen a que el descriptor de archivo esté listo para "leer" usando una llamada a función del sistema como select(2) o poll(2) (estar listo para "leer" indica que el trabajo debería reanudarse). Si no se proporciona ningún descriptor de archivo, la aplicación tendrá que "sondear" periódicamente el trabajo intentando reiniciarlo para ver si está listo para

continuar.

Los ASYNC_WAIT_CTXs también tienen un mecanismo de "callback" para notificar a las aplicaciones. El callback es establecido por una aplicación, y será llamado automáticamente cuando un motor (engine) complete una operación criptográfica, de modo que la aplicación pueda reanudar el flujo de trabajo pausado sin sondear. Un motor podría escribirse para verificar si el callback ha sido establecido. Si lo ha sido, usaría el mecanismo de callback en preferencia a las notificaciones por descriptor de archivo. Si no se establece un callback, el motor puede usar notificaciones basadas en descriptor de archivo. Tenga en cuenta que no todos los motores pueden soportar el mecanismo de callback, por lo que el callback puede no usarse incluso si ha sido establecido. Ver ASYNC_WAIT_CTX_new() para más

detalles.

La función ASYNC_block_pause() evitará que el trabajo actualmente activo se pause. El bloque permanecerá hasta una llamada posterior a ASYNC_unblock_pause(). Estas funciones pueden anidarse, p. ej., si llama a ASYNC_block_pause() dos veces, debe llamar a ASYNC_unblock_pause() dos veces para volver a habilitar la pausa. Si estas funciones se llaman cuando no hay ningún trabajo activo actualmente, no tienen ningún efecto. Esta funcionalidad puede ser útil para evitar escenarios de interbloqueo (deadlock). Por ejemplo, durante la ejecución de un ASYNC_JOB, una aplicación adquiere un bloqueo (lock). Luego llama a alguna función criptográfica que invoca ASYNC_pause_job(). Esto devuelve el control al código que creó el ASYNC_JOB. Si ese código luego intenta adquirir el mismo bloqueo antes de reanudar el trabajo original, puede ocurrir un interbloqueo. Al llamar a ASYNC_block_pause() inmediatamente después de adquirir el bloqueo y ASYNC_unblock_pause() inmediatamente antes de liberarlo, esta situación no puede

ocurrir.

Algunas plataformas no pueden soportar operaciones asíncronas. La función ASYNC_is_capable() puede usarse para detectar si la plataforma actual es capaz de operaciones asíncronas.le o

no.

Se admiten funciones de asignación de memoria personalizadas para la plataforma POSIX. Las funciones de asignación de memoria personalizadas permiten métodos alternativos para asignar memoria de pila, como mmap o el uso de memoria de pila del hilo actual. El uso de un callback ASYNC_stack_alloc_fn también permite la manipulación del tamaño de la pila, que por defecto es de 32k. El tamaño de la pila se puede alterar asignando una pila de un tamaño diferente al solicitado y devolviendo el nuevo tamaño de la pila en el *num del

callb
ack.

NOTA

S

En las plataformas Windows, el encabezado <openssl/async.h> depende de algunos de los tipos que habitualmente se ponen a disposición al incluir <windows.h>. Es probable que el desarrollador de la aplicación requiera control sobre cuándo se incluye este último, comúnmente como uno de los primeros encabezados incluidos. Por lo tanto, se define como responsabilidad del desarrollador de la aplicación incluir <windows.h> antes de <openssl/

async
.h>.

EJEMPLO

S

El siguiente ejemplo demuestra cómo usar la mayoría de las API asíncronas

principales: 
#ifdef _WIN32
# include <windows.h>
#endif
#include <stdio.h>
#include <unistd.h>
#include <openssl/async.h>
#include <openssl/crypto.h>
int unique = 0;
void cleanup(ASYNC_WAIT_CTX *ctx, const void *key, OSSL_ASYNC_FD r, void *vw)
{
    OSSL_ASYNC_FD *w = (OSSL_ASYNC_FD *)vw;
    close(r);
    close(*w);
    OPENSSL_free(w);
}
int jobfunc(void *arg)
{
    ASYNC_JOB *currjob;
    unsigned char *msg;
    int pipefds[2] = {0, 0};
    OSSL_ASYNC_FD *wptr;
    char buf = 'X';
    currjob = ASYNC_get_current_job();
    if (currjob != NULL) {
        printf("Executing within a job\n");
    } else {
        printf("Not executing within a job - should not happen\n");
        return 0;
    }
    msg = (unsigned char *)arg;
    printf("Passed in message is: %s\n", msg);
    /*
     * Create a way to inform the calling thread when this job is ready
     * to resume, in this example we're using file descriptors.
     * For offloading the task to an asynchronous ENGINE it's not necessary,
     * the ENGINE should handle that internally.
     */
    if (pipe(pipefds) != 0) {
        printf("Failed to create pipe\n");
        return 0;
    }
    wptr = OPENSSL_malloc(sizeof(OSSL_ASYNC_FD));
    if (wptr == NULL) {
        printf("Failed to malloc\n");
        return 0;
    }
    *wptr = pipefds[1];
    ASYNC_WAIT_CTX_set_wait_fd(ASYNC_get_wait_ctx(currjob), &unique,
                               pipefds[0], wptr, cleanup);
    /*
     * Normally some external event (like a network read being ready,
     * disk access being finished, or some hardware offload operation
     * completing) would cause this to happen at some
     * later point - but we do it here for demo purposes, i.e.
     * immediately signalling that the job is ready to be woken up after
     * we return to main via ASYNC_pause_job().
     */
    write(pipefds[1], &buf, 1);
    /*
     * Return control back to main just before calling a blocking
     * method. The main thread will wait until pipefds[0] is ready
     * for reading before returning control to this thread.
     */
    ASYNC_pause_job();
    /* Perform the blocking call (it won't block with this example code) */
    read(pipefds[0], &buf, 1);
    printf ("Resumed the job after a pause\n");
    return 1;
}
int main(void)
{
    ASYNC_JOB *job = NULL;
    ASYNC_WAIT_CTX *ctx = NULL;
    int ret;
    OSSL_ASYNC_FD waitfd;
    fd_set waitfdset;
    size_t numfds;
    unsigned char msg[13] = "Hello world!";
    printf("Starting...\n");
    ctx = ASYNC_WAIT_CTX_new();
    if (ctx == NULL) {
        printf("Failed to create ASYNC_WAIT_CTX\n");
        abort();
    }
    for (;;) {
        switch (ASYNC_start_job(&job, ctx, &ret, jobfunc, msg, sizeof(msg))) {
        case ASYNC_ERR:
        case ASYNC_NO_JOBS:
            printf("An error occurred\n");
            goto end;
        case ASYNC_PAUSE:
            printf("Job was paused\n");
            break;
        case ASYNC_FINISH:
            printf("Job finished with return value %d\n", ret);
            goto end;
        }
        /* Get the file descriptor we can use to wait for the job
         * to be ready to be woken up
         */
        printf("Waiting for the job to be woken up\n");
        if (!ASYNC_WAIT_CTX_get_all_fds(ctx, NULL, &numfds)
                || numfds > 1) {
            printf("Unexpected number of fds\n");
            abort();
        }
        ASYNC_WAIT_CTX_get_all_fds(ctx, &waitfd, &numfds);
        FD_ZERO(&waitfdset);
        FD_SET(waitfd, &waitfdset);
        /* Wait for the job to be ready for wakeup */
        select(waitfd + 1, &waitfdset, NULL, NULL, NULL);
    }
end:
    ASYNC_WAIT_CTX_free(ctx);
    printf("Finishing\n");
    return 0;
}
