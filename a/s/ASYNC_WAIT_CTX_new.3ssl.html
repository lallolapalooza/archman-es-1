Un objeto ASYNC_WAIT_CTX representa una

"sesión

"

asíncrona, es decir, un conjunto relacionado de operaciones criptográficas. Por ejemplo, en términos de SSL, esto tendría una correspondencia uno a uno con una conexión SSL. El código de la aplicación debe crear un ASYNC_WAIT_CTX usando la función ASYNC_WAIT_CTX_new() antes de llamar a ASYNC_start_job()

(consulte

ASYNC_START_JOB(3)). Cuando se inicia el trabajo, se asocia con el ASYNC_WAIT_CTX durante la duración de ese trabajo. Un ASYNC_WAIT_CTX solo debe usarse para un ASYNC_JOB a la vez, pero puede reutilizarse después de que un ASYNC_JOB haya finalizado para un ASYNC_JOB posterior. Cuando la sesión esté completa (por ejemplo, se cierre la conexión SSL), el código de la aplicación limpia con ASYNC_WAIT_CTX_free(). Los ASYNC_WAIT_CTX pueden tener descriptores de archivo de "espera" asociados. Llamar a ASYNC_WAIT_CTX_get_all_fds() y pasar un puntero a un ASYNC

_WAIT_CTX

en el parámetro ctx devolverá los descriptores de archivo de espera asociados con ese trabajo en *fd. El número de descriptores de archivo devueltos se almacenará en *numfds. Es responsabilidad del llamador asegurarse de que se haya asignado suficiente memoria en *fd para recibir todos los descriptores de archivo. Llamar a ASYNC_WAIT_CTX_get_all_fds() con un valor fd NULL no devolverá ningún descriptor de archivo, pero aún así poblará *numfds. Por lo tanto, normalmente se espera que el código de la aplicación llame a esta función dos veces: una para obtener el número de descriptores de archivo (fds) y luego de nuevo cuando se haya asignado suficiente memoria. Si solo se está usando un motor asíncrono, normalmente esta llamada solo devolverá un fd. Si se están usando múltiples motores asíncronos, podrían devolverse más. La función ASYNC_WAIT_CTX_get_changed_fds() puede usarse para detectar si algún fd ha cambiado desde la última vez que ASYNC_start_job(

)

devolvió ASYNC_PAUSE (o desde que se creó el ASYNC_WAIT_CTX si no se ha recibido ningún resultado ASYNC_PAUSE). Los parámetros numaddfds y numdelfds se poblarán con el número de fds añadidos o eliminados respectivamente. *addfd y *delfd se poblarán con la lista de fds añadidos y eliminados respectivamente. De manera similar a ASYNC_WAIT_CTX_get_all_fds(), cualquiera de estos puede ser NULL, pero si no lo son, el llamador es responsable de asegurarse de que se asigne suficiente memoria. Se anima a los implementadores de código consciente de la asincronía (por ejemplo, motores) a devolver un fd estable durante la vida útil del ASYNC_WAIT_CTX para

reducir

el "desgaste" de los fds que cambian regularmente, aunque no se proporcionan garantías de esto a las aplicaciones. Las aplicaciones pueden esperar a que el descriptor de archivo esté listo para "leer" usando una llamada a función del sistema como select

o

poll (estar listo para "leer" indica que el trabajo debe reanudarse). Si no se proporciona ningún descriptor de archivo, la aplicación tendrá que "sondear" periódicamente el trabajo intentando reiniciarlo para ver si está listo para continuar. El código consciente de la asincronía (por ejemplo, motores) puede obtener el ASYNC_WAIT_CTX actual del trabajo a través de ASYNC_get_wait_ctx(3

)

y proporcionar un descriptor de archivo para usar en la espera llamando a ASYNC_WAIT_CTX_set_wait_fd(). Normalmente esto lo haría un motor inmediatamente antes de llamar a ASYNC_pause_job() y no por el código del usuario final. Se puede obtener una asociación existente con un descriptor de archivo usando ASYNC_WAIT_CTX_get_fd() y se puede borrar usando ASYNC_WAIT_CTX_clear_fd(). Ambas funciones requieren un valor key que sea único para el código consciente de la asincronía. Podría ser cualquier valor único, pero un buen candidato podría ser el ENGINE * del motor. El parámetro custom_data puede ser cualquier valor, y se devolverá en una llamada posterior a ASYNC_WAIT_CTX_get_fd(). La función ASYNC_WAIT_CTX_set_wait_fd() también espera un puntero a una rutina de "limpieza". Esta puede ser NULL, pero si se proporciona, se llamará automáticamente cuando se libere el ASYNC_WAIT_CTX, y le da al motor la oportunidad de cerrar el fd o cualquier otro recurso. Nota: La rutina de "limpieza" no se llama si el fd se borra directamente mediante una llamada a ASYNC_WAIT_CTX_clear_fd(). Un ejemplo de uso típico podría ser un motor capaz de asincronía. El código del usuario iniciaría o

peraciones

criptográficas. El motor iniciaría esas operaciones de forma asíncrona y luego llamaría a ASYNC_WAIT_CTX_set_wait_fd() seguido de ASYNC_pause_job() para devolver el control al código del usuario. El código del usuario puede entonces realizar otras tareas o esperar a que el trabajo esté listo llamando a "select" u otra función similar en el descriptor de archivo de espera. El motor puede señalar al código del usuario que el trabajo debe reanudarse haciendo que el descriptor de archivo de espera sea "legible". Una vez reanudado, el motor debe borrar la señal de despertar en el descriptor de archivo de espera. Además de un descriptor de archivo, el código del

usuario

también puede ser notificado a través de un callback. El callback y los punteros de datos se almacenan dentro del ASYNC_WAIT_CTX junto con un campo de estado adicional que puede usarse para la notificación de reintentos desde un motor. Este método adicional puede usarse cuando el usuario considera que un descriptor de archivo es demasiado costoso en términos de ciclos de CPU o en algún contexto donde un descriptor de archivo no es

apropiado.

ASYNC_WAIT_CTX_set_callback() establece el callback y el argumento del callback. Se llamará al callback para notificar al código del usuario cuando un motor complete una operación criptográfica. Es un requisito que la función de callback sea pequeña y no bloqueante, ya que se ejecutará en el contexto de un mecanismo de sondeo o una

interrupción.
