OSSL_HTTP_transfer(3ssl)

NOMBRE

OSSL_HTTP_open, OSSL_HTTP_bio_cb_t, OSSL_HTTP_proxy_connect, OSSL_HTTP_set1_request, OSSL_HTTP_exchange, OSSL_HTTP_get, OSSL_HTTP_transfer, OSSL_HTTP_close - Funciones de alto nivel para cliente HTTP

#include <openssl/http.h>

                                   int connect, int detail);

                            const char *proxyuser, const char *proxypass,
                            int timeout, BIO *bio_err, const char *prog);

                           const STACK_OF(CONF_VALUE) *headers,

                           size_t max_resp_len, int timeout, int keep_alive);

DESCRIPCIÓN

OSSL_HTTP_open() inicia una sesión HTTP utilizando el argumento bio si no es NULL, de lo contrario, conectándose a un servidor dado opcionalmente a través de un proxy.

Típicamente, la compilación de OpenSSL soporta sockets y el parámetro bio es NULL. En este caso, rbio debe ser NULL también y el servidor debe ser no NULL. La función crea un BIO de red internamente utilizando BIO_new_connect(3) para conectarse al servidor dado y al puerto opcionalmente dado, que por defecto es 80 para HTTP o 443 para HTTPS. Luego, este BIO interno se utiliza para establecer una conexión y para intercambiar una o más solicitudes y respuestas.

Si se proporciona bio y rbio es NULL, se utiliza este bio en su lugar. Si se proporcionan tanto bio como rbio (que pueden ser BIOs de memoria, por ejemplo), no se establece ninguna conexión explícita, sino que bio se utiliza para escribir solicitudes y rbio para leer respuestas. Tan pronto como el cliente ha vaciado bio, el servidor debe estar listo para proporcionar una respuesta o indicar una condición de espera a través de rbio.

Si se proporciona bio, es un error proporcionar argumentos proxy o no_proxy no NULL, mientras que los argumentos server y port pueden proporcionarse para admitir salida diagnóstica. Si bio es NULL, el parámetro opcional proxy puede usarse para establecer un proxy HTTP(S) a utilizar (a menos que sea anulado por la configuración de "no_proxy"). Si TLS no se usa, esto por defecto es la variable de entorno "http_proxy" si está configurada, de lo contrario "HTTP_PROXY". Si use_ssl != 0, por defecto es "https_proxy" si está configurada, de lo contrario "HTTPS_PROXY". Una cadena de proxy vacía "" prohíbe el uso de un proxy. De lo contrario, el formato es "[http[s]://][userinfo@]host[:port][/path][?query][#fragment]", donde se ignoran los userinfo, path, query y fragment proporcionados. Si la cadena de host es una dirección IPv6, debe estar encerrada entre "[" y "]". El número de puerto de proxy predeterminado es 80, o 443 en caso de que se proporcione "https:". Las funciones del cliente HTTP se conectan a través del proxy dado a menos que el servidor se encuentre en la lista opcional no_proxy de nombres de host o direcciones IP de proxy separados por "," y/o espacios en blanco (si no es NULL; por defecto es la variable de entorno "no_proxy" si está configurada, de lo contrario "NO_PROXY"). El proxy HTTP simple se admite directamente, mientras que el uso de un proxy para conexiones HTTPS requiere una función de devolución de llamada adecuada, como OSSL_HTTP_proxy_connect(), que se describe a continuación.

Si use_ssl es distinto de cero, se solicita una conexión TLS y se debe proporcionar el parámetro bio_update_fn.

El parámetro bio_update_fn, que es opcional si use_ssl es 0, puede usarse para modificar el BIO de conexión utilizado por el cliente HTTP, pero no puede usarse cuando se proporcionan tanto bio como rbio. bio_update_fn es una función de devolución de llamada de conexión/desconexión de BIO con el prototipo

BIO *(*OSSL_HTTP_bio_cb_t)(BIO *bio, void *arg, int connect, int detail)

La función de devolución de llamada puede modificar el BIO proporcionado en el argumento bio, mediante lo cual puede usar un argumento de tiempo de ejecución opcionalmente definido por el usuario arg, que puede apuntar, por ejemplo, a una estructura SSL_CTX. Durante el establecimiento de la conexión, justo después de llamar a BIO_do_connect_retry(), la función de devolución de llamada se invoca con el argumento connect siendo 1 y detail siendo 1 si use_ssl es distinto de cero (es decir, se solicita HTTPS), de lo contrario 0. En la desconexión, connect es 0 y detail es 1 si no ocurrió ningún error, de lo contrario 0. Por ejemplo, en la conexión, la devolución de llamada puede insertar un BIO SSL para implementar HTTPS; después de la desconexión, puede realizar una salida diagnóstica y extraer y liberar el BIO SSL.

La función de devolución de llamada debe devolver el BIO modificado bio o NULL para indicar un fallo, en cuyo caso no debe modificar el BIO.

Aquí hay un ejemplo simple que soporta conexiones TLS (pero no a través de un proxy):

BIO *http_tls_cb(BIO *bio, void *arg, int connect, int detail)
{
    if (connect && detail) { /* conectando con TLS */
        SSL_CTX *ctx = (SSL_CTX *)arg;
        BIO *sbio = BIO_new_ssl(ctx, 1);
        bio = sbio != NULL ? BIO_push(sbio, bio) : NULL;
    } else if (!connect) { /* desconectando */
        BIO *hbio;
        if (!detail) { /* ha ocurrido un error */
            /* opcionalmente añadir diagnósticos aquí */
        }
        BIO_ssl_shutdown(bio);
        hbio = BIO_pop(bio);
        BIO_free(bio); /* BIO SSL */
        bio = hbio;
    }
    return bio;
}

Después de la desconexión, el BIO modificado se desasignará utilizando BIO_free_all(). El argumento de devolución de llamada opcional arg no se consume, por lo que el llamante debe liberarlo cuando ya no sea necesario.

El parámetro buf_size especifica la longitud máxima de línea de la cabecera de respuesta. Un valor <= 0 significa que se utiliza OSSL_HTTP_DEFAULT_MAX_LINE_LEN (4KiB). buf_size también se utiliza como el número de bytes de contenido que se leen a la vez.

Si el parámetro overall_timeout es > 0, esto indica el número máximo de segundos que la transferencia HTTP general (es decir, la configuración de la conexión si es necesario, el envío de solicitudes y la recepción de respuestas) puede tardar hasta completarse. Un valor <= 0 permite esperar indefinidamente, es decir, sin tiempo de espera.

OSSL_HTTP_proxy_connect() puede ser utilizado por una función de devolución de llamada de conexión BIO anterior para establecer una conexión SSL/TLS a través de un proxy HTTPS. Promueve el BIO dado bio representando una conexión preestablecida con un proxy TLS usando el método HTTP CONNECT, opcionalmente usando credenciales de cliente proxy proxyuser y proxypass, para conectarse con protección TLS finalmente a server y port. Si el argumento port es NULL o una cadena vacía, por defecto es "443". Si el parámetro timeout es > 0, esto indica el número máximo de segundos que la configuración de la conexión puede tardar. Un valor <= 0 permite esperar indefinidamente, es decir, sin tiempo de espera. Dado que esta función es típicamente llamada por aplicaciones como openssl-s_client(1), utiliza los parámetros bio_err y prog (a menos que sean NULL) para imprimir información diagnóstica adicional

OSSL_HTTP_set1_request()

OSSL_HTTP_transfer()

OSSL_HTTP_close()

SINOPSIS

OSSL_HTTP_set1_request() configura en rctx la cabecera de la solicitud y los datos de contenido, así como las expectativas sobre la respuesta, utilizando los siguientes parámetros.

OSSL_HTTP_exchange() intercambia cualquier forma de solicitud y respuesta HTTP según lo especificado por rctx.

OSSL_HTTP_get() utiliza HTTP GET para obtener datos de bio si no es NULL, de lo contrario, del servidor contenido en url.

OSSL_HTTP_transfer() intercambia una solicitud y respuesta HTTP a través de una conexión gestionada por prctx.

OSSL_HTTP_close() cierra la conexión y libera rctx.

DESCRIPCIÓN

OSSL_HTTP_set1_request() configura en rctx la cabecera de la solicitud y los datos de contenido, así como las expectativas sobre la respuesta, utilizando los siguientes parámetros. Si <rctx> indica el uso de un proxy para HTTP (pero no para HTTPS), el host del servidor (y opcionalmente el puerto) debe colocarse en la cabecera; por lo tanto, debe estar presente en rctx. Para compatibilidad con versiones anteriores, el servidor (y el puerto opcional) también pueden proporcionarse en el argumento path comenzando con "http://" (dando así una URI absoluta). Si path es NULL, se utiliza por defecto "/". Si req es NULL, se utilizará el método HTTP GET para enviar la solicitud, de lo contrario, se utilizará HTTP POST con el contenido de req y el content_type opcional, donde la longitud de los datos en req no necesita determinarse de antemano: el BIO se leerá sobre la marcha mientras se envía la solicitud, lo que admite la transmisión en tiempo real. La lista opcional headers puede contener líneas de cabecera HTTP personalizadas adicionales. El parámetro max_resp_len especifica la longitud máxima permitida del contenido de la respuesta, donde el valor 0 indica que no hay límite. Para el significado de los parámetros expected_content_type, expect_asn1, timeout y keep_alive, consulte OSSL_HTTP_REQ_CTX_set_expected(3).

OSSL_HTTP_exchange() intercambia cualquier forma de solicitud y respuesta HTTP según lo especificado por rctx, que debe incluir datos de conexión y solicitud, típicamente configurados usando OSSL_HTTP_open() y OSSL_HTTP_set1_request(). Implementa el núcleo de las funciones descritas a continuación. Si el método HTTP es GET y redirection_url no es NULL, este último puntero se utiliza para proporcionar cualquier nueva ubicación que el servidor pueda devolver con el código HTTP 301 (MOVED_PERMANENTLY) o 302 (FOUND). En este caso, la función devuelve NULL y el llamante es responsable de liberar la URL con OPENSSL_free(3). Si la cabecera de respuesta contiene una o más líneas "Content-Length" y/o se espera una respuesta codificada en ASN.1, que debe incluir una longitud total, se comprueba la consistencia de las indicaciones de longitud recibidas y que no superan ninguna longitud de respuesta máxima dada. Si se espera una respuesta codificada en ASN.1, la función devuelve en caso de éxito el contenido almacenado en un BIO de memoria, que no admite la transmisión en tiempo real. De lo contrario, devuelve directamente el BIO leído que contiene el contenido de la respuesta, lo que permite una respuesta de longitud indefinida y puede admitir la transmisión en tiempo real. El llamante es responsable de liberar el puntero BIO obtenido.

OSSL_HTTP_get() utiliza HTTP GET para obtener datos de bio si no es NULL, de lo contrario, del servidor contenido en url, y lo devuelve como un BIO. Admite redirección a través de los códigos de estado HTTP 301 o 302. Está pensado para transferencias con un solo viaje de ida y vuelta, por lo que no admite conexiones persistentes. Si bio no es NULL, los componentes de host y puerto en url no se utilizan para la conexión, pero el nombre de host se utiliza, como de costumbre, para la cabecera "Host". Se ignoran los componentes de userinfo y fragmento en url. El componente de consulta se maneja como parte del componente de ruta. Si el componente de esquema de url es "https", se solicita una conexión TLS y se debe proporcionar la bio_update_fn, según se describe para OSSL_HTTP_open(). Los parámetros restantes se interpretan como se describe para OSSL_HTTP_open() y OSSL_HTTP_set1_request(), respectivamente. El llamante es responsable de liberar el puntero BIO obtenido.

OSSL_HTTP_transfer() intercambia una solicitud y respuesta HTTP a través de una conexión gestionada por prctx sin admitir redirección. Combina OSSL_HTTP_open(), OSSL_HTTP_set1_request(), OSSL_HTTP_exchange() y OSSL_HTTP_close(). Si prctx no es NULL, reutiliza cualquier conexión abierta representada por un *prctx no NULL. Mantiene la conexión abierta si se solicita o requiere una conexión persistente y esto fue concedido por el servidor, de lo contrario, cierra la conexión y asigna NULL a *prctx. Los parámetros restantes se interpretan como se describe para OSSL_HTTP_open() y OSSL_HTTP_set1_request(), respectivamente. El llamante es responsable de liberar el puntero BIO obtenido.

OSSL_HTTP_close() cierra la conexión y libera rctx. El parámetro ok se pasa a cualquier función de actualización de BIO dada durante la configuración, como se describe anteriormente para OSSL_HTTP_open(). Debe ser 1 si no ocurrió ningún error durante la transferencia HTTP y 0 en caso contrario.

NOTAS

Los nombres de las variables de entorno utilizadas por esta implementación: "http_proxy", "HTTP_PROXY", "https_proxy", "HTTPS_PROXY", "no_proxy" y "NO_PROXY", se han elegido para una máxima compatibilidad con otras implementaciones de clientes HTTP como wget, curl y git.

Cuando se compila con el seguimiento habilitado, OSSL_HTTP_transfer() y todas las funciones que la utilizan pueden rastrearse utilizando OSSL_TRACE_CATEGORY_HTTP. Consulte también OSSL_trace_enabled(3) y openssl-env(7).

VALORES DE RETORNO

OSSL_HTTP_open() devuelve un OSSL_HTTP_REQ_CTX en caso de éxito, de lo contrario NULL.

OSSL_HTTP_proxy_connect() y OSSL_HTTP_set1_request() devuelven 1 en caso de éxito, 0 en caso de error.

En caso de éxito, OSSL_HTTP_exchange(), OSSL_HTTP_get() y OSSL_HTTP_transfer() devuelven un BIO de memoria que almacena en búfer todos los datos recibidos si se espera una respuesta codificada en ASN.1, de lo contrario, un BIO que puede admitir transmisión en tiempo real. El llamante debe liberar el BIO. En caso de fallo, devuelven NULL. Las condiciones de fallo incluyen tiempo de espera de conexión/transferencia, errores de análisis, etc. El llamante es responsable de liberar el puntero BIO obtenido.

OSSL_HTTP_close() devuelve 0 si algo salió mal al desconectar, de lo contrario 1.
