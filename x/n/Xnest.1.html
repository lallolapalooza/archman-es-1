Xnest(1) Manual de Comandos Generales Xnest(1)

NOMBRE

Xnest - un servidor X anidado

SINOPSIS

Xnest [ opciones ]

DESCRIPCIÓN

Xnest es tanto un cliente X como un servidor X. Xnest es un cliente del servidor real que administra ventanas y solicitudes gráficas en su nombre. Xnest es un servidor para sus propios clientes. Xnest administra ventanas y solicitudes gráficas en su nombre. Para estos clientes, Xnest parece ser un servidor convencional.

OPCIONES

Xnest admite todas las opciones estándar de la implementación de servidor de ejemplo. Para más detalles, consulte Xserver(1). Los siguientes argumentos adicionales también son compatibles.

-display cadena
Esta opción especifica el nombre de visualización del servidor real al que Xnest intentará conectarse. Si no se proporciona en la línea de comandos, Xnest leerá la variable de entorno DISPLAY para obtener esta información.
-sync
Esta opción indica a Xnest que sincronice sus operaciones de ventana y gráficas con el servidor real. Esta es una opción útil para la depuración, pero ralentizará considerablemente el rendimiento de Xnest. No debe usarse a menos que sea absolutamente necesario.
-full
Esta opción indica a Xnest que utilice la regeneración completa de los objetos del servidor real y que reabra una nueva conexión al servidor real cada vez que el servidor anidado se regenere. La implementación del servidor de ejemplo regenera todos los objetos en el servidor cuando termina el último cliente de este servidor. Cuando esto sucede, Xnest, por defecto, mantiene la misma ventana de nivel superior y la misma conexión al servidor real en cada nueva generación. Si el usuario selecciona la regeneración completa, incluso la ventana de nivel superior y la conexión al servidor real se regenerarán para cada generación del servidor.
-class cadena
Esta opción especifica la clase visual predeterminada del servidor anidado. Es similar a la opción -cc del conjunto de opciones estándar, excepto que acepta una cadena en lugar de un número para la especificación de la clase visual. La cadena debe ser uno de los siguientes seis valores: StaticGray, GrayScale, StaticColor, PseudoColor, TrueColor o DirectColor. Si se especifican tanto las opciones -class como -cc, la última instancia de cualquiera de las opciones tiene prioridad. La clase del visual predeterminado del servidor anidado no tiene por qué ser la misma que la clase del visual predeterminado del servidor real, pero debe ser compatible con el servidor real. Utilice xdpyinfo(1) para obtener una lista de las clases visuales compatibles en el servidor real antes de iniciar Xnest. Si el usuario elige una clase estática, todos los colores del mapa de colores predeterminado se preasignarán. Si el usuario elige una clase dinámica, los colores del mapa de colores predeterminado estarán disponibles para que los clientes individuales los asignen.
-depth int
Esta opción especifica la profundidad visual predeterminada del servidor anidado. La profundidad del visual predeterminado del servidor anidado no tiene por qué ser la misma que la profundidad del visual predeterminado del servidor real, pero debe ser compatible con el servidor real. Utilice xdpyinfo(1) para obtener una lista de las profundidades visuales compatibles en el servidor real antes de iniciar Xnest.
-sss
Esta opción indica a Xnest que utilice el salvapantallas de software. Por defecto, Xnest utilizará el salvapantallas que corresponde al salvapantallas de hardware en el servidor real. Por supuesto, incluso este salvapantallas se genera por software, ya que Xnest no controla ningún hardware real. Sin embargo, se trata como un salvapantallas de hardware dentro del código del servidor de ejemplo.
-geometry AxH+X+Y
Esta opción especifica los parámetros de geometría para la ventana de nivel superior de Xnest. Consulte “ESPECIFICACIONES DE GEOMETRÍA” en X(7) para ver una discusión de la sintaxis de esta opción. Esta ventana corresponde a la ventana raíz del servidor anidado. El ancho A y la altura H especificados con esta opción serán el ancho y la altura máximos de cada ventana de nivel superior de Xnest. Xnest permitirá al usuario hacer cualquier ventana de nivel superior más pequeña, pero no cambiará realmente el tamaño de la ventana raíz del servidor anidado. Xnest aún no admite la extensión RANDR para redimensionar, rotar y reflejar la ventana raíz. Si esta opción no se especifica, Xnest elegirá A y H para que sean 3/4 de las dimensiones de la ventana raíz del servidor real.
-bw int
Esta opción especifica el ancho del borde de la ventana de nivel superior de Xnest. El parámetro entero int debe ser positivo. El ancho de borde predeterminado es 1.
-name cadena
Esta opción especifica el nombre de la ventana de nivel superior de Xnest como cadena. El valor predeterminado es el nombre del programa.
-scrns int
Esta opción especifica el número de pantallas a crear en el servidor anidado. Por cada pantalla, Xnest creará una ventana de nivel superior separada. Cada pantalla se referencia por el número después del punto en la especificación del nombre de visualización del cliente. Por ejemplo, xterm -display :1.1 abrirá un cliente xterm(1) en el servidor anidado con el número de visualización :1 en la segunda pantalla. El número de pantallas está limitado por la constante codificada en el código del servidor de ejemplo, que suele ser 3.
-install
Esta opción indica a Xnest que realice su propia instalación de mapa de colores omitiendo el administrador de ventanas real. Para que funcione correctamente, el usuario probablemente tendrá que salir temporalmente del administrador de ventanas real. Por defecto, Xnest mantendrá la ventana del cliente anidado cuyo mapa de colores debe instalarse en el servidor real en la propiedad WM_COLORMAP_WINDOWS de la ventana de nivel superior de Xnest. Si este mapa de colores es del mismo tipo visual que la ventana raíz del servidor anidado, Xnest asociará este mapa de colores a la ventana de nivel superior de Xnest también. Dado que esto no tiene por qué ser así, los administradores de ventanas deberían consultar principalmente la propiedad WM_COLORMAP_WINDOWS en lugar del mapa de colores asociado con la ventana de nivel superior de Xnest. Desafortunadamente, los administradores de ventanas no son muy buenos haciendo eso todavía, por lo que esta opción puede ser útil.
-parent id_ventana
Esta opción indica a Xnest que utilice id_ventana como la ventana raíz en lugar de crear una ventana.

DESCRIPCIÓN EXTENDIDA

Iniciar Xnest es tan simple como iniciar xclock(1) desde un emulador de terminal. Si un usuario desea ejecutar Xnest en la misma estación de trabajo que el servidor real, es importante que al servidor anidado se le asigne su propia dirección de socket de escucha. Por lo tanto, si ya hay un servidor ejecutándose en la estación de trabajo del usuario, Xnest deberá iniciarse con un nuevo número de visualización. Dado que generalmente no hay más de un servidor ejecutándose en una estación de trabajo, especificar ‘Xnest :1’ en la línea de comandos será suficiente para la mayoría de los usuarios. Por cada servidor que se ejecute en la estación de trabajo, el número de visualización deberá incrementarse en uno. Por lo tanto, si desea iniciar otro Xnest, deberá escribir ‘Xnest :2’ en la línea de comandos.

Para ejecutar clientes en el servidor anidado, a cada cliente se le debe asignar el mismo número de visualización que al servidor anidado. Por ejemplo, ‘xterm -display :1’ iniciará un proceso xterm en el primer servidor anidado y ‘xterm -display :2’ iniciará un xterm en el segundo servidor anidado del ejemplo anterior. Se pueden iniciar clientes adicionales desde estos xterm en cada servidor anidado.

Xnest como un cliente

Un aspecto importante de Xnest es que es un cliente del servidor real. Como cliente, Xnest debe proporcionar un nombre de visualización para el servidor real. Si el usuario ha iniciado Xnest en la misma estación de trabajo, la línea de comandos anterior contendrá un nombre de visualización para el servidor anidado. Si el servidor real se está ejecutando en otra máquina, el usuario debe proporcionar el nombre de esa máquina o dirección IP en la línea de comandos. Por ejemplo, “Xnest -display myhost:0.0 :1”.

En este caso, la opción “-display myhost:0.0” indica a Xnest que se conecte al servidor X que se ejecuta en la máquina denominada myhost y que se refiera a él como la visualización 0.0. La siguiente opción, “:1”, indica a Xnest que cree un nuevo servidor con el número de visualización :1.

' href='#Xnest_como_cliente'>Xnest como cliente

Xnest se comporta y se presenta ante el servidor real y otros clientes reales como otro cliente real. Sin embargo, es un cliente bastante exigente, ya que casi cualquier solicitud de ventana o gráficos de un cliente anidado dará lugar a una solicitud de ventana o gráficos de Xnest al servidor real. Por lo tanto, es deseable que Xnest y el servidor real estén en una red local, o mejor aún, en la misma máquina. Xnest asume que el servidor real soporta la extensión SHAPE. No hay forma de desactivar esta suposición dinámicamente. Xnest se puede compilar sin la extensión SHAPE integrada, en cuyo caso el servidor real no necesita soportarla. La compatibilidad con la selección dinámica de la extensión SHAPE puede considerarse en desarrollos futuros de Xnest.

Dado que Xnest no necesita usar el mismo visual predeterminado que el servidor real, la ventana de nivel superior del cliente Xnest siempre tiene su propio mapa de colores. Esto implica que los colores de otras ventanas no se mostrarán correctamente mientras el foco del teclado o del puntero esté en la ventana de Xnest, a menos que el servidor real tenga soporte para más de un mapa de colores instalado en cualquier momento. El mapa de colores asociado con la ventana superior del cliente Xnest no tiene por qué ser el mapa de colores apropiado que el servidor anidado desea instalar en el servidor real. En el caso de que un cliente anidado intente instalar un mapa de colores de un visual diferente al visual predeterminado del servidor anidado, Xnest colocará la ventana superior de este cliente anidado y todas las demás ventanas superiores de los clientes anidados que utilicen el mismo mapa de colores en la propiedad WM_COLORMAP_WINDOWS de la ventana de nivel superior de Xnest en el servidor real. Por lo tanto, es importante que el gestor de ventanas real que gestiona la ventana de nivel superior de Xnest mire la propiedad WM_COLORMAP_WINDOWS en lugar del mapa de colores asociado con la ventana de nivel superior de Xnest. Dado que la mayoría de los gestores de ventanas aún no parecen implementar esta convención correctamente, Xnest puede realizar opcionalmente la instalación directa de mapas de colores en el servidor real, eludiendo al gestor de ventanas real. Si el usuario elige esta opción, generalmente es necesario desactivar temporalmente el gestor de ventanas real, ya que interferirá con el esquema de instalación de mapas de colores de Xnest.

Los procedimientos de control de teclado y puntero del servidor anidado cambian los parámetros de control de teclado y puntero del servidor real. Por lo tanto, después de que Xnest se inicie, cambiará los controles de teclado y puntero del servidor real a sus propios valores predeterminados internos.

Xnest como servidor

Xnest como servidor se parece exactamente a un servidor real para sus propios clientes. Para los clientes, no hay forma de saber si se están ejecutando en un servidor real o anidado.

Como ya se mencionó, Xnest es un servidor muy fácil de usar en cuanto a personalización. Xnest captará una serie de argumentos de línea de comandos que pueden configurar su clase visual y profundidad predeterminadas, número de pantallas, etc.

La única aparente complejidad desde la perspectiva del usuario al usar Xnest como servidor es la selección de fuentes. Xnest gestiona las fuentes cargándolas localmente y luego pasando el nombre de la fuente al servidor real, pidiéndole que cargue esa fuente de forma remota. Este enfoque evita la sobrecarga de enviar los bits de glifos a través de la red para cada operación de texto, aunque en realidad es un error. La consecuencia de este enfoque es que el usuario tendrá que preocuparse por dos rutas de fuentes diferentes: una local para el servidor anidado y una remota para el servidor real, ya que Xnest no propaga su ruta de fuentes al servidor real. La razón de esto es que los servidores real y anidado no necesariamente se ejecutan en el mismo sistema de archivos, lo que hace que las dos rutas de fuentes sean mutuamente incompatibles. Por lo tanto, si hay una fuente en la ruta de fuentes local del servidor anidado, no hay garantía de que esta fuente exista en la ruta de fuentes remota del servidor real. El cliente xlsfonts(1), si se ejecuta en el servidor anidado, listará las fuentes en la ruta de fuentes local y, si se ejecuta en el servidor real, listará las fuentes en la ruta de fuentes remota. Antes de que una fuente pueda ser abierta con éxito por el servidor anidado, debe existir en las rutas de fuentes local y remota. Es responsabilidad del usuario asegurarse de que este sea el caso.

DIRECCIONES FUTURAS

Hacer dinámica la exigencia de la extensión SHAPE en el servidor real, en lugar de tener que recompilar Xnest para activar o desactivar esta exigencia.

Quizás debería haber una opción de línea de comandos para indicar a Xnest que herede los parámetros de control de teclado y puntero del servidor real en lugar de imponer los suyos propios.

Xnest debería leer un archivo de entrada de personalización para proporcionar aún mayor libertad y simplicidad en la selección del diseño deseado.

No hay soporte para el almacenamiento en caché (backing store) ni para los salvados inferiores (save unders), pero esto también debería considerarse.

La implementación adecuada de las fuentes debería trasladarse a la capa *os*.

ERRORES

No funciona bien en servidores que soportan diferentes profundidades visuales.

Todavía se bloquea aleatoriamente.

Probablemente tiene algunas fugas de memoria.
