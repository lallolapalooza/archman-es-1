NOMBRE

XML::SAX::Intro - Una introducción al análisis SAX con Perl

Introducción

XML::SAX es una nueva forma de trabajar con analizadores XML en Perl. En este artículo discutiremos por qué deberías usar SAX, por qué deberías usar XML::SAX, y veremos algunos de los detalles de implementación más finos. El texto a continuación asume cierta familiaridad con el análisis basado en callbacks o push, pero si no estás familiarizado con estas técnicas, un buen lugar para empezar es la excelente serie de artículos de Kip Hampton en XML.com.

Reemplazando XML::Parser

La forma de facto de analizar XML en Perl es usar XML::Parser de Larry Wall y Clark Cooper. Este módulo es una envoltura de Perl y XS para la biblioteca de análisis XML expat de James Clark. Ha sido un proyecto de gran éxito, pero sufre un par de defectos bastante importantes. Primero, es una API propietaria, diseñada antes de que se concibiera la API SAX, lo que significa que no es fácilmente reemplazable por otros analizadores de flujo. Segundo, sus callbacks son referencias a subrutinas. Esto no parece ser un gran problema, pero desafortunadamente conduce a código como:

sub handle_start {
  my ($e, $el, %attrs) = @_;
  if ($el eq 'foo') {
    $e->{inside_foo}++; # ¡MAL! $e es un objeto XML::Parser::Expat.
  }
}

Como puedes ver, estamos usando el objeto $e para almacenar nuestra información de estado, lo cual es una mala idea porque no somos dueños de ese objeto; no lo creamos. Es un objeto interno de XML::Parser que resulta ser una referencia a un hash. Podríamos sobrescribir variables de estado internas de XML::Parser fácilmente usando esto, o Clark podría cambiarlo a una referencia a un array (no es que lo haga, porque rompería mucho código, pero podría).

La única forma actual con XML::Parser de mantener el estado de forma segura es usar un cierre:

my $state = MyState->new();
$parser->setHandlers(Start => sub { handle_start($state, @_) });

Este cierre atrapa la variable $state, que ahora se pasa como primer parámetro a tu callback. Desafortunadamente, muy pocas personas usan esta técnica, ya que no está documentada en los archivos POD de XML::Parser.

Otra razón por la que podrías no querer usar XML::Parser es porque necesitas alguna característica que no proporciona (como la validación), o podrías necesitar usar una biblioteca que no usa expat, debido a que no está instalada en tu sistema, o debido a tener un ISP restrictivo. Usar SAX te permite sortear estas restricciones.

Presentando SAX

SAX significa Simple API for XML. Y simple es realmente. Construir un analizador SAX y pasar eventos a manejadores se hace tan simple como:

use XML::SAX;
use MySAXHandler;

my $parser = XML::SAX::ParserFactory->parser(
      Handler => MySAXHandler->new
);

$parser->parse_uri("foo.xml");

El concepto importante a captar aquí es que SAX usa una clase fábrica llamada XML::SAX::ParserFactory para crear una nueva instancia de analizador. La razón de esto es poder soportar otras implementaciones de analizadores subyacentes para diferentes conjuntos de características. Esto es algo que XML::Parser siempre ha carecido seriamente.

En el código anterior vemos el método parse_uri usado, pero igualmente podríamos haber llamado parse_file, parse_string, o parse(). Por favor, consulta XML::SAX::Base para ver qué parámetros toman estos métodos, pero no te dejes engañar pensando que parse_file toma un nombre de archivo. No, toma un manejador de archivo, un glob, o una subclase de IO::Handle. Ten cuidado.

SAX funciona de manera muy similar al método de callback por defecto de XML::Parser, excepto que tiene una gran diferencia: en lugar de establecer callbacks individuales, creas una nueva clase en la que recibir los callbacks. Cada callback se llama como una llamada de método en una instancia de esa clase manejadora. Un ejemplo lo demostrará mejor:

package MySAXHandler;
use base qw(XML::SAX::Base);

sub start_document {
  my ($self, $doc) = @_;
  # procesar evento de inicio de documento
}

sub start_element {
  my ($self, $el) = @_;
  # procesar evento de inicio de elemento
}

Ahora, cuando instanciamos esto como arriba, y analizamos algún XML con esto como manejador, los métodos start_document y start_element se llamarán como llamadas de método, por lo que esto sería el equivalente a llamar directamente a:

$object->start_element($el);

Observa cómo esto es diferente al estilo de llamada de XML::Parser, que llama a:

start_element($e, $name, %attribs);

Es la diferencia entre llamadas a funciones y llamadas a métodos lo que te permite crear subclases de manejadores SAX, lo que contribuye a que SAX sea una solución potente.

Como puedes ver, a diferencia de XML::Parser, tenemos que definir un nuevo paquete en el que hacer nuestro procesamiento (hay trucos que puedes hacer para que esto no sea necesario, pero dejaré que los expertos averigüen cómo hacerlos). El mayor beneficio de esto es que mantienes tu propia variable de estado ($self en el ejemplo anterior), liberándote así de las preocupaciones mencionadas anteriormente. También es una mejora en el mantenimiento: puedes colocar el código en un archivo separado si lo deseas, y tus métodos de callback siempre se llaman de la misma manera, en lugar de tener que elegir un nombre adecuado para ellos como tenías que hacer con XML::Parser. Esto es una victoria obvia.

Los analizadores SAX también son muy flexibles en cómo les pasas un manejador. Puedes usar un parámetro constructor como vimos anteriormente, o podemos pasar el manejador directamente en la llamada a uno de los métodos parse:

$parser->parse(Handler => $handler, 
               Source => { SystemId => "foo.xml" });
# o...
$parser->parse_file($fh, Handler => $handler);

Esta flexibilidad permite usar un analizador en muchos escenarios diferentes a lo largo de tu script (aunque uno no debería sentirse presionado a usar este método, ya que la construcción del analizador generalmente no es un proceso que consuma mucho tiempo).

Parámetros de Callback

Lo único que necesitas saber para entender SAX básico son la estructura de los parámetros pasados a cada uno de los callbacks. En XML::Parser, todos los parámetros se pasan como múltiples opciones a los callbacks, por lo que, por ejemplo, el callback Start se llamaría como my_start($e, $name, %attributes), y el callback PI se llamaría como my_processing_instruction($e, $target, $data). En SAX, cada callback recibe una referencia a un hash, que contiene entradas que definen nuestro "nodo". Los callbacks clave y las estructuras que reciben son:

start_element

El manejador start_element se llama cada vez que un analizador ve una etiqueta de apertura. Se le pasa una estructura de elemento que consiste en:

LocalName
El nombre del elemento menos cualquier prefijo de namespace que pudiera haber venido en el documento.
NamespaceURI
La URI del namespace asociado con este elemento, o la cadena vacía para ninguno.
Attributes
Un conjunto de atributos como se describe a continuación.
Name
El nombre del elemento tal como se vio en el documento (es decir, incluido cualquier prefijo asociado con él)
Prefix
El prefijo utilizado para calificar el namespace de este elemento, o la cadena vacía si no hay ninguno.

Los Attributes son una referencia a un hash, indexada por lo que hemos llamado notación de "James Clark". Esto significa que el nombre del atributo se ha expandido para incluir cualquier URI de namespace asociado, y se ha combinado como {ns}name, donde "ns" es la URI de namespace expandida del atributo si y solo si el atributo tenía un prefijo, y "name" es el LocalName del atributo.

El nombre del atributo menos cualquier prefijo de namespace que pudiera haber venido en el documento.

La URI del namespace asociado con este atributo. Si el atributo no tenía prefijo, entonces consiste solo en la cadena vacía.

XML::SAX::Intro - Introducción a SAX

XML::SAX::Intro - Introducción a SAX

Introduction

SAX es una API para el procesamiento de XML. A diferencia de DOM, que construye una representación en memoria del documento, SAX es un evento basado en un sistema, que le va diciendo al programa lo que está sucediendo a medida que va procesando el documento.

Este tutorial es una introducción a la API SAX tal como está implementada en Perl.

Replacing XML::Parser

Antes de SAX, la forma más fácil de procesar XML en Perl era con el módulo XML::Parser. Este módulo es un envoltorio para el parser Expat, y tiene la gran desventaja de que debes construir el DOM completo en memoria para poder trabajar con él.

En documentos XML grandes, esto puede suponer un uso de memoria enorme, y es fácil quedarse sin memoria. Con XML::Parser, además, la forma de definir el parser es un poco engorrosa.

XML::SAX fue diseñado para superar estas limitaciones.

Introducing SAX

SAX, o la Interfaz de Parser XML Simple, es una API estándar para el procesamiento de XML. En lugar de construir un árbol en memoria del documento, SAX es un sistema basado en eventos. El parser XML va leyendo el documento y, a medida que encuentra cosas, envía eventos a tu programa. Tu programa debe entonces reaccionar a estos eventos.

Para usar SAX, debes escribir una clase que implemente los manejadores de eventos SAX. Luego, creas una instancia de esta clase y se la pasas al parser XML. El parser se encargará de llamar a tus manejadores cuando sea apropiado.

Aquí hay un ejemplo simple:

    use XML::SAX::ParserFactory;

    package MyHandler;
    sub start_element {
        my ($self, $element) = @_;
        print "Starting element: ", $element->{Name}, "\n";
    }
    sub end_element {
        my ($self, $element) = @_;
        print "Ending element: ", $element->{Name}, "\n";
    }
    sub characters {
        my ($self, $element) = @_;
        print "Character data: ", $element->{Data}, "\n";
    }

    my $handler = MyHandler->new;
    my $parser = XML::SAX::ParserFactory->parser(Handler => $handler);
    $parser->parse_uri("example.xml");

Lo que hace este ejemplo es crear un parser SAX y luego pasarle un manejador de eventos llamado MyHandler. Este manejador tiene métodos para start_element, end_element y characters. El parser llamará a estos métodos a medida que procesa el archivo example.xml.

Lo bueno de SAX es que no necesitas construir el DOM en memoria. Simplemente reaccionas a los eventos y procesas los datos como necesites.

Callback Parameters

Aquí se describen los parámetros pasados a los distintos manejadores de eventos SAX.

start_element

El manejador start_element se llama cuando el parser encuentra una etiqueta de inicio. Se llama para todas las etiquetas, incluyendo las de elementos vacíos (por ejemplo, <foo/>).

El manejador recibe una referencia a un hash con la siguiente estructura:

Name
El nombre completo de la etiqueta, incluyendo el prefijo del namespace si lo hay (por ejemplo, {"ns:tag"}). Si no hay namespace, es simplemente el nombre de la etiqueta (por ejemplo, {"tag"}).
LocalName
El nombre de la etiqueta sin el prefijo del namespace (por ejemplo, {"tag"}). Siempre presente.
NamespaceURI
El URI del namespace de la etiqueta, o el string vacío si no hay namespace. El parser se encarga de resolver los namespaces, así que no tienes que preocuparte por eso.
Attributes
Una referencia a un array de hashes, donde cada hash representa un atributo. Cada hash de atributo tiene las siguientes claves:
Name
El nombre completo del atributo, incluyendo el prefijo del namespace si lo hay.
LocalName
El nombre del atributo sin el prefijo del namespace.
NamespaceURI
El URI del namespace del atributo, o el string vacío si no hay namespace.
Value
El valor del atributo.
Prefix
El prefijo del namespace utilizado para calificar el nombre de este atributo, o el string vacío si no hay ninguno.

end_element

El manejador end_element se llama ya sea cuando un parser ve una etiqueta de cierre, o después de que start_element haya sido llamado para un elemento vacío (ten en cuenta, sin embargo, que un parser puede, si lo desea, llamar a characters con un string vacío cuando ve un elemento vacío. No hay una forma sencilla en SAX de determinar si el parser realmente vio un elemento vacío, un inicio y fin de elemento sin contenido).

El manejador end_element recibe exactamente la misma estructura que start_element, menos la entrada Attributes. Sin embargo, hay que tener en cuenta que no debe ser una referencia a los mismos datos que recibe start_element, por lo que puedes cambiar los valores en start_element, pero esto no afectará a los valores que luego verá end_element.

characters

La devolución de llamada characters puede ser llamada en varias circunstancias. La más obvia es cuando se ve datos de caracteres ordinarios en el marcado. Pero también se llama para texto en una sección CDATA, y también se llama en otras situaciones. Un parser SAX no tiene que hacer ninguna garantía de cuántas veces puede llamar a characters para un tramo de texto en un documento XML; puede llamar una vez, o puede llamar una vez por cada carácter del texto. Para solucionar esto, a menudo es importante para el desarrollador SAX usar una técnica de agrupación, donde el texto se recopila y se procesa en una de las otras devoluciones de llamada. Esto no siempre es necesario, pero es una técnica que vale la pena aprender, que cubriremos en XML::SAX::Advanced (cuando llegue a escribirla).

El manejador characters se llama con una estructura muy simple: una referencia a un hash que consta de una sola entrada:

Data
Los datos de texto que se recibieron.

comment

La devolución de llamada comment se llama para texto de comentarios. A diferencia de con characters(), la devolución de llamada comment *debe* ser invocada solo una vez para toda la cadena de comentario. Recibe una única estructura simple: una referencia a un hash que contiene solo una entrada:

Data
El texto del comentario.

processing_instruction

El manejador processing_instruction se llama para todas las instrucciones de procesamiento en el documento. Ten en cuenta que estas instrucciones de procesamiento pueden aparecer antes del elemento raíz del documento, o después de él, o en cualquier lugar donde el texto y los elementos aparecerían normalmente dentro del documento, de acuerdo con la especificación XML.

Al manejador se le pasa una estructura que contiene solo dos entradas:

Target
El objetivo de la instrucción de procesamiento
Data
Los datos de texto en la instrucción de procesamiento. Puede ser un string vacío para una instrucción de procesamiento que no tiene elemento de datos. Por ejemplo, <?wiggle?> es una instrucción de procesamiento perfectamente válida.

Tip of the iceberg

Lo que hemos discutido anteriormente es realmente la punta del iceberg de SAX. Y hasta ahora parece que no hay mucho de interés en SAX más allá de lo que hemos visto con XML::Parser. Pero va mucho más allá, lo prometo.

A las personas que odian el código orientado a objetos porque sí, puede que les parezca que crear un nuevo paquete solo para procesar algo es una pérdida de tiempo cuando hasta ahora han estado procesando cosas bien con código procedural. Pero hay una razón para toda esta locura. Y esa razón son los Filtros SAX.

Como viste al principio, para que el parser sepa sobre nuestra clase, le pasamos una instancia de nuestra clase como Handler al parser. Pero ahora imagina qué pasaría si nuestra clase también pudiera aceptar una opción de Handler, y simplemente hiciera algún procesamiento y pasara nuestros datos más adelante en la línea? En pocas palabras, así es como funcionan los filtros SAX. ¡Son tuberías de Unix para el siglo XXI!

Hay dos desventajas en esto. Número 1: escribir filtros SAX puede ser complicado. Si miras al futuro y lees el tutorial avanzado que estoy escribiendo, verás que Handler puede venir en varias formas y tamaños. Por lo tanto, asegurarse de que tu filtro haga lo correcto puede ser complicado. Segundo, construir cadenas de filtros complejas puede ser difícil, y el pensamiento simple nos dice que solo tenemos una pasada por nuestro documento, cuando a menudo necesitaremos más que eso.

Afortunadamente, esas desventajas han sido solucionadas con el lanzamiento de dos módulos muy geniales. ¡Lo que es aún mejor es que no escribí ninguno de los dos!

El primer módulo es XML::SAX::Base. Este es un módulo SAX VITAL que actúa como una clase base para todos los parsers y filtros SAX. Proporciona una abstracción de la llamada a los métodos del manejador, que asegura que tu filtro o parser haga lo correcto, y lo hace RÁPIDAMENTE. Por lo tanto, si alguna vez necesitas escribir un filtro SAX, lo cual probablemente necesites si estás procesando XML -> XML, o XML -> HTML, entonces necesitas escribirlo como una subclase de XML::SAX::Base. De verdad, este es un consejo que no debes ignorar a la ligera. No entraré en los detalles de escribir un filtro SAX aquí. Kip Hampton, el autor de XML::SAX::Base, ha cubierto esto muy bien en su artículo en XML.com aquí <URI>.

Para construir pipelines SAX, Barrie Slaymaker, un hacker de Perl de toda la vida cuyos módulos probablemente hayas oído o utilizado, escribió un módulo muy inteligente llamado XML::SAX::Machines. Este combina algunos módulos de tipo filtro SAX realmente inteligentes, con un kit de herramientas de construcción para filtros que facilita la creación de pipelines. Pero antes de ver cómo lo facilita, primero veamos lo complicado que parece construir pipelines de filtros SAX complejos.

use XML::SAX::ParserFactory;
use XML::Filter::Filter1;
use XML::Filter::Filter2;
use XML::SAX::Writer;

my $output_string;
my $writer = XML::SAX::Writer->new(Output => \$output_string);
my $filter2 = XML::SAX::Filter2->new(Handler => $writer);
my $filter1 = XML::SAX::Filter1->new(Handler => $filter2);
my $parser = XML::SAX::ParserFactory->parser(Handler => $filter1);

$parser->parse_uri("foo.xml");

Esto es mucho más fácil con XML::SAX::Machines:

use XML::SAX::Machines qw(Pipeline);

my $output_string;
my $parser = Pipeline(
      XML::SAX::Filter1 => XML::SAX::Filter2 => \$output_string
      );

$parser->parse_uri("foo.xml");

Uno de los principales beneficios de XML::SAX::Machines es que los pipelines se construyen en orden natural, en lugar del orden inverso que vimos con la construcción manual de pipelines. XML::SAX::Machines se encarga de todos los detalles internos de la construcción de tuberías, proporcionándote al final solo un parser que puedes usar (y puedes reutilizar el mismo parser tantas veces como necesites).

Solo un consejo final. Si alguna vez te quedas atascado y no entiendes lo que se pasa de un filtro o parser SAX al siguiente, entonces Devel::TraceSAX vendrá a tu rescate. Este plugin de depuración de Perl te permitirá volcar el flujo de eventos SAX a medida que pasa. El uso es realmente muy simple, solo llama a tu script de Perl que usa SAX de la siguiente manera:

$ perl -d:TraceSAX <scriptname>

Y preferiblemente, redirige la salida a un paginador, como more o less. La salida es extremadamente verbosa, pero debería ayudar a aclarar algunos problemas.
