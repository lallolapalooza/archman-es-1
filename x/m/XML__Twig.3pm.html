NOMBRE

XML::Twig - Un módulo de Perl para procesar enormes documentos XML en modo árbol.

SINOPSIS

Tenga en cuenta que esta documentación está destinada como una referencia del módulo.

Documentación completa, incluyendo un tutorial, ejemplos, una versión HTML más fácil de usar, una tarjeta de referencia rápida y una sección de Preguntas Frecuentes (FAQ) están disponibles en http://www.xmltwig.org/xmltwig.

Documentos pequeños (cargados en memoria como un árbol):

my $twig=XML::Twig->new();    # crear el twig
$twig->parsefile( 'doc.xml'); # construirlo
my_process( $twig);           # usar métodos de twig para procesarlo
$twig->print;                 # mostrar el twig

Documentos enormes (procesados en modo combinado flujo/árbol):

# como máximo se cargará un div en memoria
my $twig=XML::Twig->new(
  twig_handlers =>
    { title   => sub { $_->set_tag( 'h2') }, # cambiar etiquetas title a h2
                                             # $_ es el elemento actual
      para    => sub { $_->set_tag( 'p')  }, # cambiar para a p
      hidden  => sub { $_->delete;       },  # eliminar elementos ocultos
      list    => \&my_list_process,          # procesar elementos list
      div     => sub { $_[0]->flush;     },  # mostrar y liberar memoria
    },
  pretty_print => 'indented',                # la salida tendrá un formato agradable
  empty_tags   => 'html',                    # muestra <etiqueta_vacia />
                       );
$twig->parsefile( 'my_big.xml');
sub my_list_process
  { my( $twig, $list)= @_;
    # ...
  }

Vea XML::Twig 101 para otras formas de usar el módulo, como filtro por ejemplo.

DESCRIPCIÓN

Este módulo proporciona una forma de procesar documentos XML. Está construido sobre "XML::Parser".

El módulo ofrece una interfaz de árbol para el documento, mientras le permite mostrar las partes que han sido completamente procesadas.

Permite un uso mínimo de recursos (CPU y memoria) al construir el árbol solo para las partes de los documentos que necesitan procesamiento real, a través del uso de las opciones "twig_roots " y "twig_print_outside_roots ". Los métodos "finish " y "finish_print " también ayudan a aumentar el rendimiento.

XML::Twig intenta hacer que las cosas simples sean fáciles, por lo que hace todo lo posible para hacerse cargo de muchas de las características (generalmente molestas, pero a veces necesarias) que vienen con XML y XML::Parser.

HERRAMIENTAS

XML::Twig viene con algunas utilidades de línea de comandos:

xml_pp - formateador bonito XML

Formatea XML de forma bonita usando XML::Twig.

xml_grep - busca en archivos XML elementos específicos

"xml_grep" realiza una búsqueda en archivos XML. En lugar de usar expresiones regulares, utiliza expresiones XPath (de hecho, el subconjunto de XPath soportado por XML::Twig).

xml_split - corta un archivo XML grande en trozos más pequeños

"xml_split" toma un archivo XML (presumiblemente grande) y lo divide en varios archivos más pequeños, basándose en varios criterios (nivel en el árbol, tamaño o una expresión XPath).

xml_merge - vuelve a unir archivos XML divididos con xml_split

"xml_merge" toma varios archivos xml que han sido divididos usando "xml_split" y recrea un único archivo.

xml_spellcheck - corrige la ortografía de archivos XML

"xml_spellcheck" te permite corregir la ortografía del contenido de un archivo XML. Extrae el texto (el contenido de los elementos y opcionalmente de los atributos), llama a un corrector ortográfico sobre él, y luego recrea el documento XML.

XML::Twig 101

XML::Twig puede usarse tanto en documentos XML "pequeños" (que caben en memoria) como en otros enormes procesando partes del documento y mostrándolas o descartándolas una vez procesadas.

Cargar un documento XML y procesarlo

my $t= XML::Twig->new();
$t->parse( '<d><title>título</title><para>p 1</para><para>p 2</para></d>');
my $root= $t->root;
$root->set_tag( 'html');              # cambiar doc a html
$title= $root->first_child( 'title'); # obtener el título
$title->set_tag( 'h1');               # convertirlo en h1
my @para= $root->children( 'para');   # obtener los hijos para
foreach my $para (@para)
  { $para->set_tag( 'p'); }           # convertirlos en p
$t->print;                            # mostrar el documento

Otros métodos útiles incluyen:

att: "$elt->att( 'foo')" devuelve el atributo "foo" para un elemento,

set_att: "$elt->set_att( foo => "bar")" establece el atributo "foo" al valor "bar",

next_sibling: "$elt->next_sibling" devuelve el siguiente hermano en el documento (en el ejemplo "$title->next_sibling" es el primer "para", también puedes (y de hecho deberías) usar "$elt->next_sibling( 'para')" para obtenerlo.

El documento también puede ser transformado mediante el uso de los métodos cut (cortar), copy (copiar), paste (pegar) y move (mover): "$title->cut; $title->paste( after => $p);" por ejemplo.

Y mucho más, consulta XML::Twig::Elt.

Procesar un documento XML trozo por trozo

Una de las fortalezas de XML::Twig es que te permite trabajar con archivos que no caben en memoria. Almacenar un documento XML en memoria como un árbol consume mucha memoria; el factor de expansión suele ser alrededor de 10x.

Para hacer esto, puedes definir manejadores (handlers) que se llamarán una vez que un elemento específico haya sido completamente analizado (cerrado). En estos manejadores, puedes acceder al elemento y procesarlo como consideres conveniente, utilizando la navegación y los métodos cut/copy/paste, más muchos otros convenientes como "prefix ". Una vez que el elemento se ha procesado completamente, puedes "flush " (vaciarlo), lo que muestra el elemento y libera su memoria. También puedes "purge " (purgarlo) si no necesitas mostrarlo (si solo estás extrayendo algunos datos del documento, por ejemplo). El manejador se llamará de nuevo una vez que se haya analizado el siguiente elemento relevante.

my $t= XML::Twig->new( twig_handlers =>
                        { section => \&section,
                          para   => sub { $_->set_tag( 'p'); }
                        },
                     );
$t->parsefile( 'doc.xml');
# el manejador se llama una vez que una sección se ha procesado por completo,
# es decir, cuando se encuentra la etiqueta de cierre para section,
# recibe el twig y el elemento (incluyendo todos sus sub-elementos) como argumentos
sub section
  { my( $t, $section)= @_;      # argumentos para todos los twig_handlers
    $section->set_tag( 'div');  # cambiar el nombre de la etiqueta
    # usemos el atributo nb como prefijo para el título
    my $title= $section->first_child( 'title'); # encontrar el título
    my $nb= $title->att( 'nb'); # obtener el atributo
    $title->prefix( "$nb - ");  # fácil, ¿verdad?
    $section->flush;            # muestra la sección y libera memoria
  }

Cuando se llama a un manejador, $_ contiene el elemento que coincide con el manejador.

HANDLERS

XML::Twig allows you to specify handlers that will be called for every element that matches a given expression. This allows for much more complex processing than is possible with a simple walker, or with XML::Parser.

The syntax for the expressions is a simplified XPath. The following are all valid expressions:

section
section/title
section//title
/doc/section/title
/doc//title
section[@level="1"]
section[@level="1" or @force]
section/title[@lang="en"]
section/title[@lang="en"]/sub
section[@level >= 1]
section[title]
section[title="foo"]
section[title="foo" or title="bar"]
section[title="foo" and title!="bar"]
section[title/name="foo"]
section[title/name =~ /^[A-Z]/]

You can also use:

#PCDATA
#CDATA
#COMMENT
#PI

to process PCDATA, CDATA, comments and processing instructions. You can also use the "twig_handlers " option to set handlers for specific elements.

Here is an example using more elaborate conditions. This handler matches only "title" elements that are in in "section" elements:

my $t= XML::Twig->new( twig_handlers =>
                         { 'section/title' => sub { $_->print } }
                     )
                ->parsefile( 'doc.xml');

Here "sub { $_->print }" simply prints the current element.

Handlers can also test for the presence or content of attributes:

my $t= XML::Twig->new( twig_handlers =>
                    { 'section[@level="1" or @force]' => sub { $_->print } }
                     );
                ->parsefile( 'doc.xml');

You can also use "start_tag_handlers " to process an element as soon as the start tag is found.

Processing just parts of an XML document

The twig_roots mode builds only the required sub-trees from the document. Anything outside of the twig roots is ignored:

my $t= XML::Twig->new(
     # the twig will include just the root and selected titles
         twig_roots   => { 'section/title' => \&print_n_purge,
                           'annex/title'   => \&print_n_purge
         }
                    );
$t->parsefile( 'doc.xml');
sub print_n_purge
  { my( $t, $elt)= @_;
    print $elt->text;    # print the text (including sub-element texts)
    $t->purge;           # frees the memory
  }

You can use that mode when you want to process parts of a documents but are not interested in the rest and you don't want to pay the price, either in time or memory, to build the tree for the it.

Building an XML filter

You can combine the "twig_roots" and the "twig_print_outside_roots" options to build filters, which let you modify selected elements and output the rest of the document as-is.

This would convert prices in $ to prices in Euro in a document:

my $t= XML::Twig->new(
         twig_roots   => { 'price' => \&convert, },   # process prices
         twig_print_outside_roots => 1,               # print the rest
                    );
$t->parsefile( 'doc.xml');
sub convert
  { my( $t, $price)= @_;
    my $currency=  $price->att( 'currency');          # get the currency
    if( $currency eq 'USD')
      { $usd_price= $price->text;                     # get the price
        # %rate is just a conversion table
        my $euro_price= $usd_price * $rate{usd2euro};
        $price->set_text( $euro_price);               # set the new price
        $price->set_att( currency => 'EUR');          # don't forget this!
      }
    $price->print;                                    # output the price
  }

Simplifying XML processing

Whitespaces
Whitespaces that look non-significant are discarded. This behaviour can be controlled using the "keep_spaces ", "keep_spaces_in " and "discard_spaces_in " options.
Encoding
You can specify that you want the output in the same encoding as the input (provided you have valid XML, which means you have to specify the encoding either in the document or when you create the Twig object) using the "keep_encoding " option.

You can also use "output_encoding " to convert the internal UTF-8 format to the required encoding.

Comments and Processing Instructions (PI)
Comments and PIs can be hidden from the processing, but still appear in the output (they are carried by the "real" element closer to them). Or, they can be made available to processing as "#COMMENT" and "#PI" elements.
Pretty Printing
XML::Twig can output the document pretty-printed so it is easier to read for us humans.
Surviving an untimely death
XML parsers are supposed to react violently when fed improper XML. XML::Parser just dies.

XML::Twig provides the "safe_parse " and the "safe_parsefile " methods which wraps the parse in an "eval" and returns either the parsed twig or 0 in case of failure.

Private attributes
Attributes with a name starting with # (illegal in XML!) will not be output, so you can safely use them to store temporary values during processing. Note that you can store anything in a private attribute, not just text, it's just a regular Perl variable, so a reference to an object or a huge data structure is perfectly fine.

CLASSES

XML::Twig uses a very limited number of classes. The ones you are most likely to use are "XML::Twig ", which represents a complete XML document, including the document itself (the root of the document itself is "root "), its handlers, its input or output filters... The other main class is "XML::Twig::Elt ", which models an XML element. "Element" here has a very wide definition: it can be a regular element, or text stored in a "#PCDATA" (or "#CDATA") tag, an entity (tag is "#ENT"), a Processing Instruction ("#PI"), or a comment ("#COMMENT").

XML::Twig and XML::Twig::Elt are the two commonly used classes.

You might want to look the "elt_class " option if you want to subclass "XML::Twig::Elt".

Attributes are just attached to their parent element, they are not objects per se. (Please use the provided methods "att " and "set_att " to access them, if you access them as a hash, then your code becomes implementation dependent and might break in the future.)

Other classes that are seldom used are "XML::Twig::Entity_list " and "XML::Twig::Entity ".

If you use "XML::Twig::XPath " instead of "XML::Twig", elements are then created as "XML::Twig::XPath::Elt ".

METHODS

XML::Twig

A twig is a subclass of XML::Parser, so all XML::Parser methods can be called on a twig object, including parse and parsefile. "setHandlers" on the other hand cannot be used, see "BUGS ".

new
This is a class method, the constructor for XML::Twig. Options are passed as keyword-value pairs. Recognized options are the same as XML::Parser, plus some (in fact a lot!) XML::Twig specifics.

New Options:

twig_handlers
This argument consists of a hash "{ expression =" \&handler}> where expression is a an XPath-like expression (+ some others).

XPath expressions are limited to using the child and descendant axis (indeed you can't specify an axis), and predicates cannot be nested. You can use the "string", or string(<tag>) function (except in "twig_roots" triggers).

Additionally you can use regexps (/ delimited) to match attribute and string values.

Examples:

foo
foo/bar
foo//bar
/foo/bar
/foo//bar
/foo/bar[@att1 = "val1" and @att2 = "val2"]/baz[@a >= 1]
foo[string()=~ /^duh!+/]
/foo[string(bar)=~ /\d+/]/baz[@att != 3]

#CDATA can be used to call a handler for a CDATA tag. #COMMENT can be used to call a handler for comments.

Some additional (

(no XPath) también se proporcionan para conveniencia:

instrucciones de procesamiento
'?' o '#PI' activa el manejador para cualquier instrucción de procesamiento, y '?<target>' o '#PI <target>' activa un manejador para instrucciones de procesamiento con el destino dado (ej: '#PI xml-stylesheet').
nivel(<nivel>)
Activa el manejador en cualquier elemento de ese nivel en el árbol (la raíz es el nivel 1).
_todos_
Activa el manejador para todos los elementos del árbol.
_predeterminado_
Activa el manejador para cada elemento que NO tiene ningún otro manejador.

Los manejadores se evalúan y se ponen en cola contra el documento de entrada, luego se ejecutan. Los cambios realizados por un manejador (como cambios de nombre de etiqueta, mover o envolver el elemento - incluso en manejadores de etiqueta de apertura) <no> afectan a los manejadores posteriores en cola, incluso si las modificaciones hacen que su expresión de activación ya no coincida. Hay una excepción a esto: los atributos "privados" (cuyos nombres comienzan con un '#' y solo se pueden crear durante el procesamiento, ya que no son XML válidos) se verifican contra la rama actual.

Los manejadores se activan en un orden fijo, ordenados por su tipo (expresiones xpath primero, luego expresiones regulares, luego nivel), luego por si especifican una ruta completa (comenzando en el elemento raíz) o no, luego por el número de pasos en la expresión, luego el número de predicados, luego el número de pruebas en los predicados. Los manejadores donde el último paso no especifica un paso ("foo/bar/*") se activan después de otros manejadores XPath. Finalmente, los manejadores "_todos_" se activan al final.

Importante: Una vez que un manejador ha sido activado, si devuelve 0, entonces no se llama a ningún otro manejador, excepto al manejador "_todos_", que siempre se llama.

Si un manejador devuelve un valor verdadero y se aplican otros manejadores, se llamará al siguiente manejador aplicable. Repetir, enjuagar, enjabonar...; La excepción a esa regla es cuando se establece la opción "do_not_chain_handlers ", en cuyo caso solo se llamará al primer manejador.

Es una buena idea devolver explícitamente un valor verdadero corto (como 1) de los manejadores; esto asegura que se llamen otros manejadores aplicables incluso si la última declaración del manejador resulta ser falsa. Esto también puede acelerar el código al evitar que el resultado de la última declaración del código se copie y se pase al código que administra los manejadores. Realmente vale la pena tener 1 en lugar de una cadena larga devuelta.

Cuando se analiza la etiqueta de cierre de un elemento, se llama al manejador correspondiente con dos argumentos: la rama y el "Elemento ". La rama incluye el árbol del documento que se ha construido hasta ahora, el elemento es el subárbol completo para el elemento.

Dado que los manejadores solo se llaman cuando se encuentra la etiqueta de cierre del elemento, esto significa que los manejadores de los elementos internos se llaman antes que los de los elementos externos.

$_ también se establece en el elemento, por lo que es fácil escribir manejadores en línea como:

para => sub { $_->set_tag( 'p'); }

El texto se almacena en elementos cuyo nombre de etiqueta es "#PCDATA" (debido al contenido mixto, texto y sub-elemento en un elemento, no hay forma de almacenar el texto como un simple atributo del elemento contenedor).

Advertencia: Si ha utilizado "purge" o "flush" en la rama, es posible que el elemento no esté completo: algunos de sus hijos podrían haber sido completamente descartados o purgados, y la etiqueta de apertura podría incluso haber sido impresa (por "flush") ya, por lo que cambiar su etiqueta podría no dar el resultado esperado.

raíces_rama
Este argumento te permite construir el árbol solo para los elementos que te interesan. 
Ejemplo: my $t= XML::Twig->new( twig_roots => { title => 1, subtitle => 1});
         $t->parsefile( file);
         my $t= XML::Twig->new( twig_roots => { 'section/title' => 1});
         $t->parsefile( file);

devuelve una rama que contiene un documento que incluye solo elementos "title" y "subtitle", como hijos del elemento raíz.

Puedes usar generic_attribute_condition, attribute_condition, full_path, partial_path, tag, tag_regexp, _predeterminado_ y _todos_ para activar la construcción de la rama. Las string_condition y regexp_condition no se pueden usar, ya que el contenido del elemento, y la cadena, aún no se han analizado cuando se verifica la condición.

ADVERTENCIA: Las rutas se verifican en el documento. Incluso si se utiliza la opción "twig_roots", se verificarán contra el árbol completo del documento, no contra el árbol virtual creado por XML::Twig.

ADVERTENCIA: Los elementos de twig_roots NO deben anidarse, eso confundiría irremediablemente a XML::Twig.

Nota: Puedes establecer manejadores (twig_handlers) usando twig_roots
Ejemplo: my $t= XML::Twig->new( twig_roots =>
{ title => sub { $_[1]->print;},
subtitle => \&process_subtitle
}
);
$t->parsefile( file);

Para ser utilizado junto con el argumento "twig_roots". Cuando se establece en un valor verdadero, esto imprime el documento fuera de los elementos "twig_roots". 
Ejemplo: my $t= XML::Twig->new( twig_roots => { title => \&number_title },

start_tag_handlers
Un hash "<{ expression =" \&handler}>>. Establece manejadores de elementos que se llaman cuando el elemento está abierto (al final del manejador "Start" de XML::Parser). Los manejadores se llaman con dos parámetros: la rama y el elemento. El elemento está vacío en ese punto, pero sus atributos se crean.

Puedes usar generic_attribute_condition, attribute_condition, full_path, partial_path, tag, tag_regexp, _predeterminado_ y _todos_ para activar el manejador.

string_condition y regexp_condition no se pueden usar, ya que el contenido del elemento, y la cadena, aún no se han analizado cuando se verifica la condición.

Los usos principales para los manejadores de etiquetas de apertura son cambiar el nombre de la etiqueta (podría tener que hacerlo tan pronto como encuentre la etiqueta de apertura si planea "flush" la rama en algún punto del elemento, y para crear atributos temporales que se usarán al procesar sub-elementos con "twig_handlers" regulares.

También deberías usarlo para cambiar etiquetas si usas "flush". Si cambia la etiqueta en un "twig_handler" regular, la etiqueta de apertura podría ya haber sido enviada.

Nota: Los manejadores de "start_tag" pueden llamarse fuera de "twig_roots" si se utiliza este argumento, en este caso los manejadores se llaman con los siguientes argumentos: $t (la rama), $tag (la etiqueta del elemento) y %att (un hash de los atributos del elemento).

Si el argumento "twig_print_outside_roots" también se usa, si el último manejador llamado devuelve un valor "verdadero", entonces la etiqueta de apertura se imprimirá como apareció en el documento original; si el manejador devuelve un valor "falso", entonces la etiqueta de apertura no se imprimirá (para que puedas imprimir una cadena modificada tú mismo, por ejemplo).

Ten en cuenta que puedes usar el método ignore en "start_tag_handlers" (y solo allí).

end_tag_handlers
Un hash "<{ expression =" \&handler}>>. Establece manejadores de elementos que se llaman cuando el elemento se cierra (al final del manejador "End" de XML::Parser). Los manejadores se llaman con dos parámetros: la rama y la etiqueta del elemento.

Los twig_handlers se llaman cuando un elemento se analiza completamente, ¿entonces por qué tener esta opción redundante? Solo hay un uso para "end_tag_handlers": cuando se usa la opción "twig_roots", para activar un

Un controlador para un elemento fuera de las raíces. Es, por ejemplo, muy útil para numerar títulos en un documento usando secciones anidadas:

mi @no= (0);
mi $no;
mi $t= XML::Twig->new(
        start_tag_handlers =>
         { section => sub { $no[$#no]++; $no= join '.', @no; push @no, 0; } },
        twig_roots         =>
         { title   => sub { $_[1]->prefix( $no); $_[1]->print; } },
        end_tag_handlers   => { section => sub { pop @no;  } },
        twig_print_outside_roots => 1
                    );
 $t->parsefile( $file);

Usar los "end_tag_handlers" sin "twig_roots" resultará en un error.

do_not_chain_handlers
Si esta opción se establece a un valor verdadero, entonces solo se llamará a un controlador para cada elemento, incluso si varios cumplen la condición.

Tenga en cuenta que el controlador "_all_" todavía se llama independientemente.

ignore_elts
Esta opción le permite ignorar elementos al construir la rama. Esto es útil en casos donde no puede usar "twig_roots" para ignorar elementos, por ejemplo, si el elemento a ignorar es un hermano de los elementos que le interesan.

Ejemplo:

mi $twig= XML::Twig->new( ignore_elts => { elt => 'discard' });
$twig->parsefile( 'doc.xml');

Esto construirá la rama completa para el documento, excepto que todos los elementos "elt" (y sus hijos) serán omitidos.

Las claves en el hash son disparadores, limitados al mismo subconjunto que "start_tag_handlers ". Los valores pueden ser "discard" para descartar el elemento, "print" para imprimir el elemento tal cual, "string" para almacenar el texto de los elementos ignorados, incluido el marcado, en un campo de la rama: "$t->{twig_buffered_string}" o una referencia a un escalar, en cuyo caso el texto de los elementos ignorados, incluido el marcado, se almacenará en el escalar. Cualquier otro valor se tratará como "discard".

char_handler
Una referencia a una subrutina que se llamará cada vez que se encuentre "#PCDATA".

La subrutina recibe la cadena como argumento y devuelve la cadena modificada:

# queremos todas las cadenas en mayúsculas
sub my_char_handler
  { mi( $text)= @_;
    $text= uc( $text);
    return $text;
  }
css_sel
Cuando se establece a un valor verdadero, permite selectores "tag.class" en los controladores.

El punto es un carácter válido en nombres de elementos, por ejemplo "div.header" es un nombre XML completamente válido.

Pero dado que XML::Twig se usa bastante para procesar XHTML y dialectos basados en HTML, es bastante conveniente poder usar "div.header" para activar un elemento "div" con una clase "header", en lugar del más engorroso "div[@class=~/\bheader\b/]".

Tenga en cuenta que la sintaxis "tag.class" es compatible con las expresiones de navegación, a menos que "css_sel" se establezca explícitamente a 0.

elt_class
El nombre de una clase utilizada para almacenar elementos. Esta clase debe heredar de "XML::Twig::Elt" (y por defecto es "XML::Twig::Elt"). Esta opción se utiliza para crear una subclase de la clase de elementos y extenderla con nuevos métodos.

Esta opción es necesaria porque durante el análisis del XML, los elementos son creados por "XML::Twig" sin ningún control por parte del código del usuario.

keep_atts_order
Establecer esta opción a un valor verdadero hace que el hash de atributos se vincule a un objeto "Tie::IxHash". Esto significa que "Tie::IxHash" debe estar instalado para que esta opción esté disponible. También significa que el hash mantiene su orden, por lo que obtendrá los atributos en orden. Esto permite mostrar los atributos en el mismo orden en que estaban en el documento original.
keep_encoding
Esta es una opción (ligeramente?) maliciosa: si el documento XML no está codificado en UTF-8 y desea mantenerlo así, entonces establecer keep_encoding utilizará el método original_string de "Expat" para los caracteres, manteniendo así la codificación original, así como las entidades originales en las cadenas.

Consulte el archivo de prueba "t/test6.t" para ver qué resultados puede esperar de las diversas opciones de codificación.

ADVERTENCIA: Esta opción NO se utiliza al analizar con el analizador no bloqueante (métodos "parse_start", "parse_more", parse_done), que probablemente no debería usar con XML::Twig de todos modos, ya que no están probados.

output_encoding
Esta opción genera un filtro de salida usando "Encode", "Text::Iconv", o "Unicode::Map8" y "Unicode::Strings", y establece la codificación en la declaración XML. Esta es la forma más fácil de manejar las codificaciones. Si necesita características más sofisticadas, consulte "output_filter" a continuación.
output_filter
Esta opción se utiliza para convertir la codificación de caracteres del documento de salida. Se le pasa una cadena que corresponde a un filtro predefinido o una referencia a una subrutina. El filtro se llamará cada vez que un documento o elemento sea procesado por las funciones "print" ( "print", "sprint", "flush").

Filtros predefinidos:

latin1
Utiliza "Encode", "Text::Iconv" o "Unicode::Map8" y "Unicode::String" o una expresión regular (que solo funciona con XML::Parser 2.27), en este orden, para convertir todos los caracteres a ISO-8859-15 (generalmente latin1 es sinónimo de ISO-8859-1, pero en la práctica parece que ISO-8859-15, que incluye el símbolo del euro, es más útil y probablemente lo que la mayoría de la gente quiere).
html
Realiza la misma conversión que "latin1", además de codificar entidades usando "HTML::Entities" (curiosamente, necesitará tener HTML::Entities instalado para que esté disponible). Esto solo debe usarse si las etiquetas y los nombres de los atributos están en US-ASCII, de lo contrario, se convertirán y la salida ya no será un XML válido.
safe
Convierte la salida solo a ASCII (EE. UU.) más caracteres de entidad ("&#nnn;"). Esto solo debe usarse si las etiquetas y los nombres de los atributos están en US-ASCII, de lo contrario, se convertirán y la salida ya no será un XML válido.
safe_hex
Igual que "safe" excepto que las entidades de caracteres están en hexadecimal ("&#xnnn;").
encode_convert ($encoding)
Devuelve una referencia de subrutina que se puede usar para convertir cadenas utf8 a $encoding). Utiliza "Encode". 
mi $conv = XML::Twig::encode_convert( 'latin1');
mi $t = XML::Twig->new(output_filter => $conv);
iconv_convert ($encoding)
Esta función se utiliza para crear una subrutina de filtro que se utilizará para convertir los caracteres a la codificación de destino utilizando "Text::Iconv" (que debe estar instalado, consulte la documentación del módulo y de la biblioteca "iconv" para averiguar qué codificaciones están disponibles en su sistema). 
mi $conv = XML::Twig::iconv_convert( 'latin1');
mi $t = XML::Twig->new(output_filter => $conv);
unicode_convert ($encoding)
Esta función se utiliza para crear una subrutina de filtro que se utilizará para convertir los caracteres a la codificación de destino utilizando "Unicode::Strings" y "Unicode::Map8" (que deben estar instalados, consulte la documentación de los módulos para averiguar qué codificaciones están disponibles en su sistema). 
mi $conv = XML::Twig::unicode_convert( 'latin1');
mi $t = XML::Twig->new(output_filter => $conv);

Los métodos "text" y "att" no utilizan el filtro, por lo que sus resultados siempre están en unicode.

Estos filtros predeclarados se basan en subrutinas que se pueden usar por sí solas (como "XML::Twig::foo").

html_encode ($string)
Utiliza "HTML::Entities" para codificar una cadena utf8.
safe_encode ($string)
Utiliza "Encode" para codificar caracteres no ASCII en la cadena en formato "&#<nnnn>;".
safe_encode_hex ($string)
Utiliza "Encode" para codificar caracteres no ASCII en la cadena s
regexp2latin1($string)
Utiliza una expresión regular para codificar una cadena utf8 en latin 1 (ISO-8859-1).
output_text_filter
Igual que output_filter, excepto que no se aplica a los corchetes y comillas alrededor de los valores de los atributos. Esto es útil para todos los filtros que podrían cambiar el etiquetado, básicamente cualquier cosa que no solo cambie la codificación de la salida. "html", "safe" y "safe_hex" se utilizan mejor con esta opción.
input_filter
Esta opción es similar a "output_filter" excepto que el filtro se aplica a los caracteres antes de que se almacenen en el twig, en el momento del análisis.
remove_cdata
Establecer esta opción a un valor verdadero forzará al twig a generar secciones "#CDATA" como "#PCDATA" regulares (con escape).
parse_start_tag
Si utiliza la opción "keep_encoding", entonces esta opción se puede utilizar para reemplazar la función de análisis predeterminada. Debe proporcionar un coderef (una referencia a una subrutina) como argumento. Esta subrutina toma la etiqueta original (proporcionada por el método original_string() de XML::Parser::Expat) y devuelve una etiqueta y los atributos en un hash (o en una lista nombre_atributo/valor_atributo).
no_xxe
Evita que se analicen entidades externas.

Esta es una característica de seguridad, en caso de que el XML de entrada no sea de confianza. Con esta opción establecida a un valor verdadero, la definición de entidades externas en el documento hará que el análisis falle.

Esto evita que una entidad como "<!ENTITY xxe PUBLIC "bar" "/etc/passwd">" haga que el campo de contraseña esté disponible en el documento.

expand_external_ents
Cuando se utiliza esta opción, las entidades externas (que están definidas) se expanden cuando el documento se genera utilizando funciones de "impresión" como "print ", "sprint ", "flush " y "xml_string ". Tenga en cuenta que en el twig la entidad se almacenará como un elemento con una etiqueta '"#ENT"', la entidad no se expandirá allí, por lo que es posible que desee procesar las entidades antes de generarlas.

Si una entidad externa no está disponible, el análisis fallará.

Un caso especial es cuando el valor de esta opción es -1. En ese caso, una entidad faltante no hará que el analizador falle, sino que su "name", "sysid" y "pubid" se almacenarán en el twig como "$twig->{twig_missing_system_entities}" (una referencia a un array de hashes { name => <name>, sysid => <sysid>, pubid => <pubid> }). Sí, es un poco un truco, pero es útil en algunos casos.

load_DTD
Si este argumento se establece a un valor verdadero, "parse" o "parsefile" en el twig cargarán la información DTD. Esta información se puede acceder a través del twig, en un "DTD_handler" por ejemplo. Esto cargará incluso un DTD externo.

Los valores predeterminados y fijos para los atributos también se completarán, basándose en el DTD.

Tenga en cuenta que para hacer esto, el módulo generará un archivo temporal en el directorio actual. Si esto es un problema, házmelo saber y añadiré una opción para especificar un directorio alternativo.

Ver "Manejo de DTD" para más información.

DTD_handler
Establece un manejador que se llamará una vez que se hayan cargado el doctype (y el DTD), con dos argumentos: el twig y el DTD.
no_prolog
No genera un prólogo (declaración XML y DTD).
id
Este argumento opcional da el nombre de un atributo que puede ser utilizado como un ID en el documento. Los elementos cuyo ID se conoce se pueden acceder a través del método elt_id. id tiene por defecto 'id'. Ver "BUGS ".
discard_spaces
Si este argumento opcional se establece a un valor verdadero, entonces los espacios se descartan cuando parecen no ser significativos: las cadenas que contienen solo espacios y al menos un salto de línea se descartan. Este argumento se establece a verdadero por defecto.

El algoritmo exacto para descartar espacios es: las cadenas que incluyen solo espacios (perl \s) y al menos un \n justo antes de una etiqueta de apertura o cierre se descartan.

discard_all_spaces
Si este argumento se establece a un valor verdadero, los espacios se descartan de manera más agresiva que con "discard_spaces": las cadenas que no incluyen un \n también se descartan. Esta opción es apropiada para XML orientado a datos.
keep_spaces
Si este argumento opcional se establece a un valor verdadero, entonces todos los espacios en el documento se conservan y se almacenan como "#PCDATA".

Advertencia: Agregar esta opción puede resultar en cambios en el twig generado: los espacios que antes se descartaban podrían terminar en un nuevo elemento de texto. Vea la diferencia llamando al siguiente código con 0 y 1 como argumentos:

perl -MXML::Twig -e'print XML::Twig->new( keep_spaces => shift)->parse( "<d> \n<e/></d>")->_dump'

"keep_spaces" y "discard_spaces" no pueden ser ambos establecidos.

discard_spaces_in
Este argumento establece "keep_spaces" a verdadero, pero hace que el generador de twig descarte espacios en los elementos listados.

La sintaxis para usar este argumento es:

XML::Twig->new( discard_spaces_in => [ 'elt1', 'elt2']);
keep_spaces_in
Este argumento establece "discard_spaces" a verdadero, pero hace que el generador de twig conserve espacios en los elementos listados.

La sintaxis para usar este argumento es:

XML::Twig->new( keep_spaces_in => [ 'elt1', 'elt2']);

Advertencia: Agregar esta opción puede resultar en cambios en el twig generado: los espacios que antes se descartaban podrían terminar en un nuevo elemento de texto.

pretty_print
Establece el método de impresión bonita (pretty print). Los valores son '"none"' (predeterminado), '"nsgmls"', '"nice"', '"indented"', '"indented_c"', '"indented_a"', '"indented_close_tag"', '"cvs"', '"wrapped"', '"record"' y '"record_c"'.

pretty_print formatea:

none
El documento se genera como una sola línea, sin saltos de línea excepto los que se encuentran dentro de los elementos de texto.
nsgmls
Se insertan saltos de línea en lugares seguros: es decir, dentro de las etiquetas, entre una etiqueta y un atributo, entre atributos y antes del > al final de una etiqueta.

Esto es bastante feo pero mejor que "none", y es muy seguro, el documento seguirá siendo válido (conforme a su DTD).

Así es como el analizador SGML "sgmls" divide los documentos, de ahí el nombre.

nice
Esta opción inserta saltos de línea antes de cualquier etiqueta que no contenga texto (por lo que los elementos con contenido textual no se rompen ya que el \n es significativo).

Advertencia: Esta opción deja el documento bien formado pero podría hacerlo inválido (no conforme a su DTD). Si tiene elementos declarados como:

<!ELEMENT foo (#PCDATA|bar)>

entonces un elemento "foo" que incluya uno de "bar" se imprimirá como:

<foo>
<bar>bar es solo pcdata</bar>
</foo>

Esto es inválido, ya que el analizador tomará el salto de línea después de la etiqueta "foo" como una señal de que el elemento contiene PCDATA, y luego fallará al encontrar la etiqueta "bar". ¡Esto puede ser importante para usted o no, pero tenga en cuenta!

indented
Igual que "nice" (y con la misma advertencia) pero indenta los elementos de acuerdo a su nivel.
indented_c
Igual que "indented", pero un poco más compacto: las etiquetas de cierre están en la misma línea que el texto anterior.
indented_close_tag
Igual que "indented", excepto que la etiqueta de cierre también está indentada, para alinearse con las etiquetas dentro del elemento.
indented_a
Esto formatea los archivos XML de una manera amigable para el control de versiones orientada a líneas. El formato se describe en http://tinyurl.com/2kwscq (ese es un documento de Oracle con un
(URL absurdamente larga).

Tenga en cuenta que para cumplir totalmente con la «especificación», el orden de los atributos no debe cambiarse, por lo que si no están ya en orden alfabético, deberá usar la opción "keep_atts_order".

cvs
Igual que "indented_a".
wrapped
Igual que "indented_c", pero las líneas se ajustan usando Text::Wrap::wrap. La longitud predeterminada de las líneas es la predeterminada para $Text::Wrap::columns, y se puede cambiar modificando esa variable.
record
Esta es una impresión bonita orientada a registros que muestra los datos en registros, un campo por línea (lo que se parece MUCHO a "indented").
record_c
Significa registro compacto, un registro por línea.
empty_tags
Establece el estilo de visualización de etiquetas vacías («"normal"», «"html"» o «"expand"»).

"normal" produce una etiqueta vacía '"<tag/>"', "html" añade un espacio '"<tag />"' para elementos que pueden estar vacíos en XHTML y "expand" produce '"<tag></tag>"'.

quote
Establece el carácter de comillas para los atributos («"single"» o «"double"»).
escape_gt
Por defecto, XML::Twig no escapa el carácter > en su salida, ya que no está exigido por la especificación XML. Con esta opción activada, > se reemplaza por "&gt;".
comments
Establece la forma en que se procesan los comentarios: «"drop"» (predeterminado), «"keep"» o «"process"».

Opciones de procesamiento de comentarios:

drop
Descarta los comentarios; no se leen ni se imprimen en la salida.
keep
Los comentarios se cargan y aparecerán en la salida; no son accesibles dentro de la rama (twig) y no interferirán con el procesamiento.

Nota: Los comentarios en medio de un elemento de texto como:

<p>texto <!-- comentario --> más texto --></p>

se conservan en su posición original en el texto. Usar métodos de «print» como "print" o "sprint" devolverá los comentarios en el texto. Sin embargo, usar "text" o "field" no lo hará.

Cualquier uso de "set_pcdata" en el elemento "#PCDATA" (directa o a través de otros métodos como "set_content") eliminará el(los) comentario(s).

process
Los comentarios se cargan en la rama (twig) y se tratan como elementos regulares con un valor de etiqueta de "#COMMENT". Esto puede interferir con el procesamiento si espera que "$elt->{first_child}" sea un elemento pero encuentra un comentario allí. La validación del esquema no lo protegerá de esto, ya que los comentarios pueden ocurrir en cualquier lugar. Puede usar "$elt->first_child( 'tag')" (lo cual es un buen hábito de todos modos) para obtener lo que desea.

Considere usar "process" si está generando eventos SAX de XML::Twig.

pi
Establece la forma en que se procesan las instrucciones de procesamiento: «"drop"», «"keep"» (predeterminado), o «"process"».

Tenga en cuenta que también puede establecer manejadores de PI en la opción "twig_handlers":

'?'       => \&handler
'?target' => \&handler2

Los manejadores se llamarán con dos parámetros, la rama (twig) y el elemento PI si "pi" está establecido a "process", y con tres, la rama (twig), el objetivo y los datos si "pi" está establecido a "keep". Por supuesto, no se llamarán si "pi" está establecido a "drop".

Si "pi" está establecido a "keep", el manejador debe devolver una cadena que se usará tal cual como el texto de la PI (debería parecerse a «"<?target data?" » o '' si quiere eliminar la PI).

Solo se llamará a un manejador, "?target" o "?" si no hay un manejador específico para ese objetivo disponible.

map_xmlns
Esta opción se pasa como un hashref que mapea URIs a prefijos. Los prefijos en el documento se reemplazarán por los del mapa. Los prefijos mapeados se pueden (de hecho, deben) usar para activar manejadores, o para navegar o consultar el documento.

Ejemplo:

my $t= XML::Twig->new( map_xmlns => {'http://www.w3.org/2000/svg' => "svg"},
                       twig_handlers =>
                         { 'svg:circle' => sub { $_->set_att( r => 20) } },
                       pretty_print => 'indented',
                     )
                ->parse( '<doc xmlns:gr="http://www.w3.org/2000/svg">
                            <gr:circle cx="10" cy="90" r="10"/>
                         </doc>'
                       )
                ->print;

Esto producirá:

<doc xmlns:svg="http://www.w3.org/2000/svg">
   <svg:circle cx="10" cy="90" r="20"/>
</doc>
keep_original_prefix

my $t= XML::Twig->new( map_xmlns => {'http://www.w3.org/2000/svg' => "svg"},
                       twig_handlers =>
                         { 'svg:circle' => sub { $_->set_att( r => 20) } },
                       keep_original_prefix => 1,
                       pretty_print => 'indented',
                     )

                            <gr:circle cx="10" cy="90" r="10"/>
                         </doc>'
                       )
                ->print;

Esto produce:

<doc xmlns:gr="http://www.w3.org/2000/svg">
   <gr:circle cx="10" cy="90" r="20"/>
</doc>
original_uri ($prefix)
Llamado dentro de un manejador, esto devuelve la URI vinculada al prefijo del espacio de nombres en el documento original.
index ($arrayref o $hashref)
Esta opción crea listas de elementos específicos durante el análisis del XML. Toma una referencia a una lista de expresiones de activación o a un nombre de hash => expresión, y para cada una genera la lista de elementos que coinciden con la expresión. La lista se puede acceder a través del método "index".

Ejemplo:

# usando una referencia de array
my $t= XML::Twig->new( index => [ 'div', 'table' ])
                ->parsefile( "foo.xml");
my $divs= $t->index( 'div');
my $first_div= $divs->[0];
my $last_table= $t->index( table => -1);
# usando un hashref para nombrar los índices
my $t= XML::Twig->new( index => { email => 'a[@href=~/^ \s*mailto:/]'})
                ->parsefile( "foo.xml");
my $last_emails= $t->index( email => -1);

Tenga en cuenta que el índice no se mantiene después del análisis. Si los elementos se eliminan, se renombra o se alteran de otra manera durante el procesamiento, el índice NO se actualiza. (Sin embargo, modificar el elemento id actualizará el índice).

att_accessors <lista de nombres de atributos>
Crea métodos que dan acceso directo a los atributos: 
my $t= XML::Twig->new( att_accessors => [ 'href', 'src'])
                ->parsefile( $file);
my $first_href= $t->first_elt( 'img')->src; # igual que ->att( 'src')
$t->first_elt( 'img')->src( 'new_logo.png') # cambia el valor del atributo
elt_accessors
Crea métodos que dan acceso directo al primer elemento hijo (en contexto escalar) o a la lista de elementos (en contexto de lista):

La lista de accesores a crear se puede dar de dos maneras: en un array, o en un alias de hash => expresión.

my $t=  XML::Twig->new( elt_accessors => [ 'head'])
                ->parsefile( $file);
my $title_text= $t->root->head->field( 'title');
# igual que $title_text= $t->root->first_child( 'head')->field( 'title');
my $t=  XML::Twig->new( elt_accessors => { warnings => 'p[@class="warning"]', d2 => 'div[2]'}, )
                ->parsefile( $file);
my $body= $t->first_elt( 'body');
my @warnings= $body->warnings; # igual que $body->children( 'p[@class="warning"]');
my $s2= $body->d2;             # igual que $body->first_child( 'div[2]')
field_accessors
Creamétodos que dan acceso directo al texto del primer elemento hijo: 
my $t=  XML::Twig->new( field_accessors => [ 'h1'])

my $div_title_text= $t->first_elt( 'div')->title;
# lo mismo que $title_text= $t->first_elt( 'div')->field( 'title');
use_tidy
Establece esta opción para usar HTML::Tidy en lugar de HTML::TreeBuilder para convertir HTML a XML. Para HTML, especialmente el HTML real (el "crap" real que se encuentra en la naturaleza), un módulo u otro hace un mejor trabajo en la conversión. Además, HTML::Tidy puede ser un poco difícil de instalar, por lo que XML::Twig ofrece ambas opciones. TIMTOWTDI.
output_html_doctype
Al usar HTML::TreeBuilder para convertir HTML, esta opción hace que la declaración DOCTYPE se genere, lo que puede ser importante para algunos navegadores heredados. Sin esta opción, la definición DOCTYPE NO se genera. Tampoco si la definición es completamente incorrecta (es decir, no fácilmente analizable), tampoco se genera.

Nota: Odio los nombres de argumentos similares a Java que usa la mayoría de los módulos XML. Así que, al más puro estilo TIMTOWTDI, todos los argumentos pueden escribirse como "NombreFeoEstiloJava" o como "NombreLegiblePerl": "twig_print_outside_roots" o "TwigPrintOutsideRoots" (o incluso "twigPrintOutsideRoots" { escalofrío }). XML::Twig los normaliza antes de procesarlos.

parse ( $source)
El parámetro $source debe ser una cadena que contenga el documento XML completo, o debe ser un "IO::Handle" abierto (también conocido como filehandle).

Se lanza una llamada "die" si ocurre un error de análisis. De lo contrario, devuelve el twig construido por el análisis. Usa "safe_parse" si quieres que el análisis devuelva el control incluso cuando ocurre un error.

Si se llama a este método como método de clase ("XML::Twig->parse( $algún_xml_o_html)") entonces se crea un objeto XML::Twig, usando los parámetros excepto el último (por ejemplo, "XML::Twig->parse( pretty_print => 'indented', $algún_xml_o_html)") y se le llama "xparse".

Ten en cuenta que al analizar un filehandle, este NO debe abrirse con una codificación (es decir, ábrelo con "open( my $in, '<', $nombre_archivo)"). El archivo será analizado por "expat", por lo que especificar la codificación en realidad causa problemas para el analizador (puede provocar que falle, ver https://rt.cpan.org/Ticket/Display.html?id=78877). Para analizar un archivo, en realidad se recomienda usar "parsefile" con el nombre del archivo, en lugar de <parse> en el archivo abierto.

parsestring
Igual que "parse" (por compatibilidad retroactiva).

NAME

XML::Twig::Elt - manipulate an XML document as a tree

SYNOPSIS

 use XML::Twig;
 my $twig= XML::Twig->new(
   Twig_lib_encoding => 'latin1',
   pretty_print      => 'xml',
   twig_handlers     => {
     qr{.} => sub {
       $_[0]->set_att( 'att' => 'value' );
     },
   },
 );
 $twig->parsefile( 'input.xml');
 $twig->print;

DESCRIPTION

XML::Twig is a module that parses an XML document, represents it as a tree, and provides methods to manipulate the tree. It uses the Expat parser (via XML::Parser) and therefore benefits from its speed and XML support.

The module is composed of two classes: XML::Twig and XML::Twig::Elt. The former handles the parsing and provides the main interface, while the latter represents the nodes in the XML tree.

There are three ways to use XML::Twig:

  • The simplest way is to parse a document and print it with some modifications:

        use XML::Twig;
    my $twig= XML::Twig->new()->parsefile( 'file.xml');
    # ... manipulate the tree ...
    $twig->print;

  • You can also use the event-driven approach, using handlers:

        use XML::Twig;
    my $twig= XML::Twig->new( twig_handlers => { tagname => \&sub,
                                            qr{.} => \&sub,
                                            '#comment' => \&sub,
                                          }
                             );
    $twig->parsefile( 'file.xml');

    When the parser encounters a tag named "tagname", it calls the subroutine &sub. The subroutine receives the twig object as its first argument. The method set_tag_handler can also be used.

    The tag name can be a regular expression. qr{.} matches any element. '#comment' matches comments. '#PCDATA' matches text nodes. A handler registered for '#PCDATA' will be called with the text node as the first argument, and the twig object as the second.

    A handler registered for '#text' will be called with the text node as the first argument, and the twig object as the second. This is equivalent to '#PCDATA'.

  • Finally, you can also build a tree from scratch:

        use XML::Twig;
    my $twig= XML::Twig->new();
    my $elt1= $twig->root( 'root');
    my $elt2= $elt1->append_child( 'element1');
    $elt2->set_content( 'this is element1');
    my $elt3= $elt1->append_child( 'element2');
    $elt3->set_att( 'attribute' => 'value');
    $twig->print;

subs_text ($regexp, $replace)
subs_text realiza sustituciones de texto, similar al operador " s///" de perl.

$regexp debe ser una expresión regular de perl, creada con el operador "qr".

Devuelve el elemento que llama.

$replace puede incluir "$1, $2"... de la $regexp. También se puede utilizar para crear elementos y entidades, utilizando "&elt( tag => { att => val }, text)" (sintaxis similar a "new ") y &ent( name).

Aquí hay un ejemplo bastante complejo:

$elt->subs_text( qr{(?<!do not )link to (http://([^\s,]*))},
                 'see &elt( a =>{ href => $1 }, $2)'
               );

Esto reemplaza texto como link to http://www.xmltwig.org por see <a href="www.xmltwig.org">www.xmltwig.org</a>, pero no do not link to....

Generación de entidades (aquí reemplazando espacios por &nbsp;):

$elt->subs_text( qr{ },'&ent( "&nbsp;")');

o, usando una variable:

my $ent="&nbsp;";
$elt->subs_text( qr{ }, "&ent( '$ent')");

Tenga en cuenta que la sustitución es siempre global, como si se utilizara el modificador "g" en una sustitución de perl, y que se realiza en todos los descendientes de texto del elemento.

Bug: en la $regexp, solo se pueden usar "\1", "\2"... si la expresión de reemplazo no incluye elementos o atributos. por ejemplo:

$t->subs_text( qr/((t[aiou])\2)/, '$2');             # ok, reemplaza toto, tata, titi, tutu por to, ta, ti, tu

DT

Internal DTD
El documento XML incluye una DTD interna y, posiblemente, declaraciones de entidades.

Si utiliza la opción load_DTD al crear el twig, la información de la DTD y las declaraciones de entidades serán accesibles.

La DTD y las declaraciones de entidades se "vaciarán" (o se "imprimirán") tal cual (si no han sido modificadas) o reconstruidas (mal, los comentarios se pierden, el orden no se mantiene; debido a su contenido, nadie debería ver esta DTD) si han sido modificadas. También puede modificarlas directamente cambiando el campo "$twig->{twig_doctype}->{internal}" (directamente de XML::Parser, consulte la documentación del manejador "Doctype").

DTD externa
El documento XML incluye una referencia a una DTD externa y, posiblemente, declaraciones de entidades.

Si utiliza "load_DTD" al crear el twig, la información de la DTD y las declaraciones de entidades serán accesibles. Las declaraciones de entidades se "vaciarán" (o se "imprimirán") tal cual (si no han sido modificadas) o reconstruidas (mal, los comentarios se pierden, el orden no se mantiene).

Puede cambiar la doctype a través del método "$twig->set_doctype" e imprimir la dtd a través de los métodos "$twig->dtd_text" o "$twig->dtd_print".

Si necesita modificar la lista de entidades, esta es probablemente la forma más fácil de hacerlo.

Flush

Recuerde que los manejadores de elementos se llaman cuando el elemento se CIERRA, por lo que si tiene manejadores para elementos anidados, los manejadores internos se llamarán primero. Esto hace que sea más complicado de lo que parece, por ejemplo, numerar secciones anidadas (o cláusulas, o divs), ya que los títulos de las secciones internas se manejan antes que las secciones externas.

BUGS

segfault durante el análisis
Esto ocurre al analizar documentos enormes, o muchos pequeños, con una versión de Perl anterior a la 5.16.

Esto se debe a un error en la forma en que se manejan las referencias débiles en Perl.

La solución es actualizar a Perl 5.16 o posterior ("perlbrew" es una gran herramienta para gestionar varias instalaciones de perl en la misma máquina).

Otra forma de solucionar el problema, NO RECOMENDADA, es desactivar las referencias débiles escribiendo "XML::Twig::_set_weakrefs( 0);" al principio del código. Esto no está soportado en absoluto y puede provocar otros problemas.

manejo de entidades
Debido al comportamiento de XML::Parser, las entidades no base en valores de atributos desaparecen si no se declaran en el documento: "att="val&ent;"" se convertirá en "att => val", a menos que utilice el argumento "keep_encoding" para "XML::Twig->new".
manejo de DTD
Los métodos de manejo de DTD tienen bastantes errores. Nadie los utiliza y parece muy difícil hacer que funcionen en todos los casos, incluso con varias versiones ligeramente incompatibles de XML::Parser y libexpat.

Básicamente, puede leer la DTD, sacarla de nuevo correctamente y actualizar entidades, pero poco más.

Así que utilice XML::Twig con documentos independientes, o con documentos que hagan referencia a una DTD externa, pero no espere que analice correctamente e incluso imprima la DTD.

lista de ID
La lista de ID NO se actualiza cuando se cortan o eliminan elementos.
change_gi
Este método no funcionará correctamente si hace: 
$twig->change_gi( $old1, $new);
$twig->change_gi( $old2, $new);
$twig->change_gi( $new, $even_newer);
verificación de cordura en llamadas a métodos de XML::Parser
XML::Twig debería prevenir realmente las llamadas a algunos métodos de XML::Parser, especialmente el método "setHandlers".
impresión bonita
La impresión bonita (al menos usando el estilo '"indented"') es difícil de hacer bien. Solo los elementos que pertenecen al documento se sangrarán correctamente. Imprimir elementos que no pertenecen al twig hace imposible que XML::Twig determine su profundidad y, por lo tanto, su nivel de sangría.

Además, hay un error inevitable al usar "flush" e impresión bonita para elementos con contenido mixto que comienzan con un elemento incrustado:

<elt><b>b</b>toto<b>bold</b></elt>
se imprimirá como
<elt>
  <b>b</b>toto<b>bold</b></elt>

si vacía el twig al encontrar el elemento "<b>".

Globals

Estas son las cosas que pueden causar problemas al código que llama, especialmente si es multihilo. También pueden causar problemas bajo mod_perl.

constantes exportadas
Quiéralas o no, ¡las tiene! Estas son subrutinas para usar como constantes al crear o probar elementos: 
PCDATA  devuelve '#PCDATA'
CDATA   devuelve '#CDATA'
PI      devuelve '#PI', tuve que elegir entre PROC y PI :--(
valores con ámbito de módulo: constantes
estos no deberían causar problemas: 
%base_ent= ( '>' => '&gt;',
             '<' => '&lt;',
             '&' => '&amp;',
             "'" => '&apos;',
             '"' => '&quot;',
           );
CDATA_START   = "<![CDATA[";
CDATA_END     = "]]>";
PI_START      = "<?";
PI_END        = "?>";
COMMENT_START = "<!--";
COMMENT_END   = "-->";

estilos de impresión bonita:

( $NSGMLS, $NICE, $INDENTED, $INDENTED_C, $WRAPPED, $RECORD1, $RECORD2)= (1..7);

estilo de salida de etiquetas vacías:

( $HTML, $EXPAND)= (1..2);
valores con ámbito de módulo: pueden ser cambiados
La mayoría de estos se ocupan de la impresión bonita, por lo que lo peor que puede pasar es que la salida XML no se vea bien, pero siga siendo válida y procesada de forma idéntica por los procesadores XML.

$empty_tag_style puede causar problemas en los navegadores HTML y cambiar $ID muy probablemente crearía problemas.

$pretty=0;           # estilo de impresión bonita
$quote='"';          # comillas para atributos
$INDENT= '  ';       # sangría para impresión bonita sangrada
$empty_tag_style= 0; # cómo mostrar etiquetas vacías
$ID                  # atributo utilizado como id ('id' por defecto)
valores con ámbito de módulo: definitivamente cambiados
Estas 2 variables se utilizan para reemplazar etiquetas por un índice, ahorrando así espacio al crear un twig. Si realmente le causan demasiados problemas, hágamelo saber, es probable que sea posible crear un interruptor o al menos una versión de XML::Twig que no realice esta optimización. 
%gi2index;     # etiqueta => índice
@index2gi;     # lista de etiquetas

Si necesita manipular todos estos valores, puede utilizar los siguientes métodos en el objeto XML::Twig:

global_state
Devuelve un hashref con todas las variables globales utilizadas por XML::Twig.

El hash tiene los siguientes campos: "pretty", "quote", "indent", "empty_tag_style", "keep_encoding", "expand_external_entities", "output_filter", "output_text_filter", "keep_atts_order".

set_global_state ($state)
Establece el estado global, $state es un hashref.
save_global_state
Guarda el estado global actual.
restore_global_state
Restaura el estado previamente guardado (usando "Lsave_global_state">).

Módulos Alternativos

XML::Twig no es el único módulo de procesamiento de XML disponible en CPAN (¡ni mucho menos!).

La principal alternativa que recomendaría es XML::LibXML.

Aquí hay una comparación rápida de los 2 módulos:

XML::LibXML, en realidad "libxml2" en el que se basa, se adhiere a los estándares e implementa un buen número de ellos de una manera bastante estricta: XML, XPath, DOM, RelaxNG, debo estar olvidando un par (¿XInclude?). Es rápido y bastante frugal en cuanto a memoria.

XML::Twig es más antiguo: cuando empecé a escribirlo, XML::Parser/expat era el único juego en la ciudad. Implementa XML y eso es todo (más un subconjunto de XPath, y puedes usar XML::Twig::XPath si tienes XML::XPathEngine instalado para soporte completo). Es más lento y requiere más memoria para un árbol completo que XML::LibXML. En el lado positivo (¡sí, hay un lado positivo!) te permite procesar un documento grande en fragmentos, y por lo tanto te permite abordar documentos que no podrían cargarse en memoria con XML::LibXML, y ofrece muchos (¡y quiero decir MUCHOS!) métodos de alto nivel, para todo, desde agregar estructura a XML de "bajo nivel", hasta atajos para conversiones de XHTML y más. También hace bastante DWIM (Do What I Mean), eliminando comentarios y espacios en blanco no significativos pero preservándolos en la salida, por ejemplo. Como no se adhiere a DOM, también suele resultar en un código más corto que en XML::LibXML.

Más allá de las características puras de los 2 módulos, XML::LibXML parece ser preferido por los "puristas de XML", mientras que XML::Twig parece ser más utilizado por los Hackers de Perl que tienen que lidiar con XML. Como habrás notado, XML::Twig también viene con mucha documentación, pero estoy seguro de que si pides ayuda sobre XML::LibXML aquí o en Perlmonks obtendrás respuestas.

Ten en cuenta que en realidad me resulta bastante difícil comparar los 2 módulos: por un lado, conozco XML::Twig a la perfección y puedo hacer que haga casi cualquier cosa que necesite (o lo mejoro ;-) mientras que tengo un conocimiento muy básico de XML::LibXML. Así que en cuanto a características, prefiero usar XML::Twig ;-) Por otro lado, soy dolorosamente consciente de algunas de las deficiencias, posibles errores y código francamente feo que se esconden en XML::Twig, aunque es poco probable que te afecten (a menos que, por ejemplo, necesites cambiar la DTD de un documento mediante programación), mientras que no he mirado mucho XML::LibXML, por lo que todavía me parece brillante y limpio.

Dicho esto, si necesitas procesar un documento que es demasiado grande para caber en memoria y XML::Twig es demasiado lento para ti, mi consejo a regañadientes sería usar el XML::Parser "desnudo". No será tan fácil de usar como XML::Twig: básicamente, con XML::Twig intercambias algo de velocidad (dependiendo de lo que hagas, de un factor de 3 a... ninguno) por facilidad de uso, pero será más fácil IMHO que usar SAX (aunque no sea estándar), y en este punto MUCHO más rápido (ver la última prueba en http://www.xmltwig.org/article/simple_benchmark/).
