XML::SAX::Base(3) Documentación de Perl contribuida por el usuario XML::SAX::Base(3)

NOMBRE

XML::SAX::Base - Clase base para drivers y filtros SAX

SINOPSIS

package MiFiltro;
use XML::SAX::Base;
@ISA = ('XML::SAX::Base');

DESCRIPCIÓN

Este módulo tiene una tarea muy simple: ser una clase base para drivers y filtros PerlSAX. Su comportamiento predeterminado es pasar la entrada directamente a la salida sin cambios. Puede ser útil usar este módulo como clase base para no tener que, por ejemplo, implementar la devolución de llamada characters().

Las principales ventajas que proporciona son la fácil distribución de eventos de la manera correcta (es decir, se encarga de comprobar que el manejador ha implementado ese método, o ha definido un AUTOLOAD), y la garantía de que los filtros pasarán los eventos que no están implementando a los manejadores posteriores que aún podrían estar interesados en ellos.

ESCRIBIENDO DRIVERS Y FILTROS SAX

La referencia de la API de Perl Sax está en http://perl-xml.sourceforge.net/perl-sax/.

Escribir filtros SAX es tremendamente fácil: todo lo que necesita hacer es heredar de este módulo y definir los eventos que desea manejar. Una explicación más detallada se puede encontrar en http://www.xml.com/pub/a/2001/10/10/sax-filters.html.

Escribir Drivers es igualmente sencillo. Lo único a lo que debe prestar atención es a **NO** llamar a los eventos usted mismo (esto se aplica también a los Filtros). Por ejemplo:

package MiFiltro;
use base qw(XML::SAX::Base);
sub start_element {
  my $self = shift;
  my $data = shift;
  # hacer algo
  $self->{Handler}->start_element($data); # MAL
}

El ejemplo anterior funciona bien como precisamente eso: un ejemplo. Pero tiene varios fallos: 1) no comprueba si el manejador define start_element. Quizás no quiera ver ese evento, en cuyo caso no debería lanzarlo (de lo contrario, morirá). 2) no comprueba ContentHandler y luego Handler (es decir, no comprueba que el usuario no haya solicitado eventos en un manejador específico, y si no en el predeterminado), 3) si comprobara todo eso, no solo el código sería engorroso (ver el código fuente de este módulo para hacerse una idea) sino que también probablemente tendría que comprobar un DocumentHandler (en caso de que fuera SAX1) y AUTOLOADs potencialmente definidos en todos estos paquetes. Como puede ver, eso sería bastante doloroso. En lugar de pasar por eso, simplemente recuerde usar código similar al siguiente en su lugar:

package MiFiltro;
use base qw(XML::SAX::Base);
sub start_element {
  my $self = shift;
  my $data = shift;
  # hacer algo para filtrar
  $self->SUPER::start_element($data); # BUENO (¡y fácil!)
}

De esta manera, una vez que haya hecho su trabajo, devuelve la pelota a XML::SAX::Base ¡y se encarga de todos esos problemas por usted!

Tenga en cuenta que el ejemplo anterior no se aplica solo a los filtros, los drivers se beneficiarán de la misma característica.

MÉTODOS

Se definen una serie de métodos en esta clase para fines de herencia. Algunos probablemente no necesiten ser sobrescritos (por ejemplo, parse_file) pero algunos claramente deberían serlo (por ejemplo, parse). Las opciones para estos métodos se describen en la especificación PerlSAX2 disponible en http://cvs.sourceforge.net/cgi-bin/viewcvs.cgi/~checkout~/perl-xml/libxml-perl/doc/sax-2.0.html?rev=HEAD&content-type=text/html.

  • parse

    El método parse es el punto de entrada principal para analizar documentos. Internamente, el método parse detectará qué tipo de "cosa" está analizando y llamará al método apropiado en su clase de implementación. Aquí está la tabla de mapeo de lo que hay en las opciones Source (ver la especificación Perl SAX 2.0 para el significado de estos valores):

    Source Contiene           parse() llama a
===============           =============
CharacterStream (*)       _parse_characterstream($stream, $options)
ByteStream                _parse_bytestream($stream, $options)
String                    _parse_string($string, $options)
SystemId                  _parse_systemid($string, $options)

    Sin embargo, tenga en cuenta que estos métodos pueden no ser sensatos si su clase de driver no es para analizar XML. Un ejemplo podría ser un driver DBI que genera XML/SAX a partir de una tabla de base de datos. Si es así, probablemente querrá escribir su propio método parse().

    También tenga en cuenta que Source puede contener tanto una entrada PublicId como una entrada Encoding. Para acceder a ellas, examine $options->{Source} tal como se pasa a su método.

    (*) Un CharacterStream es un manejador de archivos que no necesita ninguna traducción de codificación. Esto se implementa como un manejador de archivos normal y solo funciona en Perl 5.7.2 o superior usando PerlIO. Para obtener un solo carácter, o un número de caracteres, use la función central de Perl read(). Para obtener un solo byte (o un número de bytes), puede usar sysread(). La codificación del stream debe estar en la entrada Encoding para el Source.

  • parse_file, parse_uri, parse_string

    Todas estas son variaciones de conveniencia de parse() y, de hecho, simplemente configuran las opciones antes de llamarlo. Probablemente no necesite sobrescribir estas.

  • get_options

    Este es un método de conveniencia para obtener opciones al estilo SAX2, o de forma más genérica como hashes o como hashrefs (devuelve un hashref). Probablemente querrá usar este método en sus propias implementaciones de parse() y de new().

  • get_feature, set_feature

    Estos simplemente obtienen y establecen características, y lanzan las excepciones apropiadas definidas en la especificación si es necesario.

    Si su subclase define características no definidas en esta, entonces debería sobrescribir estos métodos de tal manera que comprueben primero sus características y luego llamen a los métodos de la clase base para las características no definidas por su clase. Un ejemplo sería:

    sub get_feature {
    my $self = shift;
    my $feat = shift;
    if (exists $MY_FEATURES{$feat}) {
        # manejar la característica de varias maneras
    }
    else {
        return $self->SUPER::get_feature($feat);
    }
}

    Actualmente, esta parte no está implementada.

  • set_handler

    Este método toma un tipo de manejador (Handler, ContentHandler, etc.) y un objeto manejador como argumentos, y cambia el manejador actual para ese tipo de manejador, encargándose de restablecer el estado interno que necesita ser restablecido. Esto permite cambiar un manejador durante el análisis sin encontrar problemas (cambiarlo directamente en el objeto analizador probablemente causará problemas).

  • set_document_handler, set_content_handler, set_dtd_handler, set_lexical_handler, set_decl_handler, set_error_handler, set_entity_resolver

    Estos son simplemente envoltorios alrededor del método anterior, y toman un objeto manejador como su argumento. Internamente, simplemente llaman a set_handler con los argumentos correctos.

  • get_handler

    El inverso de set_handler, este método toma una cadena opcional que contiene un tipo de manejador (DTDHandler, ContentHandler, etc. se usa 'Handler' si no se pasa ningún tipo). Devuelve una referencia al objeto que implementa esa clase, o undef si ese tipo de manejador no está establecido para el driver/filtro actual.

  • get_document_handler, get_content_handler, get_dtd_handler, get_lexical_handler, get_decl_handler, get_error_handler, get_entity_resolver

    Estos son simplemente envoltorios alrededor del método get_handler(), y no toman argumentos. Internamente, simplemente llaman a get_handler con el nombre del tipo de manejador correcto.

XML::SAX::Base - Perl module for writing SAX drivers and filters

NAME

XML::SAX::Base - Perl module for writing SAX drivers and filters

SYNOPSIS

  use XML::SAX::Base;

  # Subclassing XML::SAX::Base to create a driver
  package MyDriver;
  use base 'XML::SAX::Base';

  sub start_document {
    my $self = shift;
    $self->SUPER::start_document(@_);
    print "Starting document!\n";
  }

  # Subclassing XML::SAX::Base to create a filter
  package MyFilter;
  use base 'XML::SAX::Base';

  sub start_element {
    my $self = shift;
    print "Encountered element: ", $_[1]->{LocalName}, "\n";
    $self->SUPER::start_element(@_);
  }

DESCRIPTION

XML::SAX::Base is a base class that provides a convenient way to write SAX drivers and filters. It implements the standard SAX driver interface, and provides default no-op implementations of all the handler methods. This means you only need to override the methods you are interested in.

When subclassing XML::SAX::Base, you can either implement a SAX driver or a SAX filter. A SAX driver is responsible for parsing an XML document and firing SAX events. A SAX filter is responsible for intercepting SAX events from a driver or another filter, optionally modifying them, and passing them on to the next handler in the chain.

The core idea behind XML::SAX::Base is to provide a convenient way to build SAX event handler chains. You can have multiple filters stacked on top of each other, each performing a specific task, such as validating, transforming, or logging XML data.

WRITING SAX DRIVERS AND FILTERS

To write a SAX driver or filter using XML::SAX::Base, you should create a new Perl package that uses XML::SAX::Base as its base class:

All the SAX handler methods are provided with a default implementation that does nothing. You only need to override the methods that you want to act upon. Remember to call the superclass's method using $self->SUPER::method_name(@_) if you want the event to be passed on to the next handler in the chain (for filters) or to allow the default behavior to occur (for drivers).

The SAX specification defines the following handler methods:

  • start_document
  • end_document
  • start_element
  • end_element
  • start_prefix_mapping
  • end_prefix_mapping
  • characters
  • ignorable_whitespace
  • processing_instruction
  • comment
  • entity_reference
  • notation_decl
  • unparsed_entity_decl
  • element_decl
  • attlist_decl
  • doctype_decl
  • xml_decl
  • entity_decl
  • attribute_decl
  • internal_entity_decl
  • external_entity_decl
  • resolve_entity
  • start_dtd
  • end_dtd
  • start_entity
  • end_entity
  • warning
  • error
  • fatal_error

METHODS

This class provides default no-op implementations for all the SAX handler methods listed above.

The primary methods you will interact with when using this class are the SAX handler methods themselves. You will subclass this class and override the methods you need to customize.

For example, if you want to create a filter that prints the names of all elements encountered:

  package MyElementLogger;
  use base 'XML::SAX::Base';

  sub start_element {
    my $self = shift;
    my $element = shift; # The hash containing element details

    print "Element: ", $element->{LocalName}, "\n";

    # Call the superclass method to pass the event on
    $self->SUPER::start_element(@_);
  }

If you are writing a driver, you would implement the logic to parse your XML source and then call the appropriate handler methods on the SAX parser object (which is usually passed as an argument to your driver's methods or stored internally).

The parse method is often used by drivers. It takes a source and optionally a hash of options. The source can be a file name, a URL, or a file handle.

The handler methods receive arguments according to the SAX specification. For example, start_element receives a hash reference containing details about the element, such as:

  {
    'Name'        => 'QualifiedName',
    'LocalName'   => 'LocalPart',
    'NamespaceURI' => 'URI',
    'Attributes'  => { ... }, # Hash of attributes
    'BaseURI'     => 'URI',
    'XSI'         => 'http://www.w3.org/2001/XMLSchema-instance',
    'XSD'         => 'http://www.w3.org/2001/XMLSchema',
  }

Consult the SAX specification for the exact arguments passed to each handler method.
