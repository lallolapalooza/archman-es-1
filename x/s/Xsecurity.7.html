XSECURITY(7) Manual de información miscelánea XSECURITY(7)

NOMBRE

Xsecurity - control de acceso a pantalla X

DESCRIPCIÓN GENERAL

X proporciona mecanismos para implementar muchos sistemas de control de acceso. La implementación de ejemplo incluye cinco mecanismos:

    Acceso por Host	Control de acceso simple basado en host.
    MIT-MAGIC-COOKIE-1	"Cookies" compartidas en texto plano.
    XDM-AUTHORIZATION-1	Claves privadas seguras basadas en DES.
    SUN-DES-1	Basado en el sistema de RPC seguro de Sun.
    Interpretado por el Servidor	Métodos de control de acceso dependientes del servidor

No todos estos están disponibles en todas las compilaciones o implementaciones.

DESCRIPCIONES DE LOS SISTEMAS DE ACCESO

Acceso por Host
Se permite el acceso al servidor X a cualquier cliente de un host en la lista de control de acceso por host. Este sistema puede funcionar razonablemente bien en un entorno donde todos se confían mutuamente, o cuando solo una persona puede iniciar sesión en una máquina dada, y es fácil de usar cuando la lista de hosts utilizados es pequeña. Este sistema no funciona bien cuando varias personas pueden iniciar sesión en una sola máquina y no existe confianza mutua. La lista de hosts permitidos se almacena en el servidor X y se puede modificar con el comando xhost. La lista se almacena en el servidor por dirección de red, no por nombres de host, por lo que no se actualiza automáticamente si un host cambia de dirección mientras el servidor está en ejecución. Al usar los mecanismos más seguros que se enumeran a continuación, la lista de hosts normalmente se configura como la lista vacía, de modo que solo los programas autorizados puedan conectarse a la pantalla. Consulte la sección OTORGANDO ACCESO de la página del manual de Xserver para obtener detalles sobre cómo se inicializa esta lista al inicio del servidor.
MIT-MAGIC-COOKIE-1
Al usar MIT-MAGIC-COOKIE-1, el cliente envía una "cookie" de 128 bits junto con la información de configuración de la conexión. Si la cookie presentada por el cliente coincide con una que tiene el servidor X, se permite el acceso a la conexión. La cookie se elige para que sea difícil de adivinar; xdm genera dichas cookies automáticamente cuando se utiliza esta forma de control de acceso. La copia de la cookie del usuario generalmente se almacena en el archivo .Xauthority en el directorio de inicio, aunque la variable de entorno XAUTHORITY se puede usar para especificar una ubicación alternativa. Xdm pasa automáticamente una cookie al servidor por cada nueva sesión de inicio de sesión y almacena la cookie en el archivo del usuario al iniciar sesión.
La cookie se transmite por la red sin cifrar, por lo que no hay nada que impida que un espía de red obtenga los datos y los use para acceder al servidor X. Este sistema es útil en un entorno donde muchos usuarios ejecutan aplicaciones en la misma máquina y desean evitar interferencias entre sí, con la advertencia de que este control es solo tan bueno como el control de acceso a la red física. En entornos donde la escucha a nivel de red es difícil, este sistema puede funcionar razonablemente bien.
XDM-AUTHORIZATION-1
Los sitios que compilan con soporte DES pueden usar un mecanismo de control de acceso basado en DES llamado XDM-AUTHORIZATION-1. Es similar en uso a MIT-MAGIC-COOKIE-1 en el sentido de que una clave se almacena en el archivo .Xauthority y se comparte con el servidor X. Sin embargo, esta clave consta de dos partes: una clave de cifrado DES de 56 bits y 64 bits de datos aleatorios utilizados como autenticador.
Al conectarse al servidor X, la aplicación genera 192 bits de datos combinando la hora actual en segundos (desde las 00:00 del 1/1/1970 GMT) junto con 48 bits de "identificador". Para conexiones TCP/IPv4, el identificador es la dirección más el número de puerto; para conexiones locales, es el ID del proceso y 32 bits para formar un ID único (en caso de que se realicen múltiples conexiones al mismo servidor desde un solo proceso). Este paquete de 192 bits se cifra luego utilizando la clave DES y se envía al servidor X, que puede verificar si el solicitante está autorizado a conectarse descifrando con la misma clave DES y validando el autenticador y los datos adicionales. Este sistema es útil en muchos entornos donde el control de acceso basado en host es inapropiado y donde no se puede garantizar la seguridad de la red.
SUN-DES-1
Las versiones recientes de SunOS (y algunos otros sistemas) han incluido un sistema de llamadas a procedimiento remoto seguro de clave pública. Este sistema se basa en la noción de un principal de red; un par de nombre de usuario y dominio NIS. Utilizando este sistema, el servidor X puede descubrir de forma segura el nombre de usuario real del proceso solicitante. Implica cifrar datos con la clave pública del servidor X, por lo que se necesita la identidad del usuario que inició el servidor X para esto; esta identidad se almacena en el archivo .Xauthority. Al extender la semántica de "dirección de host" para incluir esta noción de principal de red, esta forma de control de acceso es muy fácil de usar.
Para permitir el acceso a un nuevo usuario, use xhost. Por ejemplo, 
    xhost keith@ ruth@mit.edu
agrega a "keith" del dominio NIS de la máquina local y a "ruth" en el dominio NIS "mit.edu". Para que keith o ruth se conecten correctamente a la pantalla, deben agregar el principal que inició el servidor a su archivo .Xauthority. Por ejemplo: 
    xauth add expo.lcs.mit.edu:0 SUN-DES-1 unix.expo.lcs.mit.edu@our.domain.edu
Este sistema solo funciona en máquinas que admiten RPC seguro y solo para usuarios que han configurado los pares de claves públicas/privadas apropiados en su sistema. Consulte la documentación de RPC seguro para obtener detalles. Para acceder a la pantalla desde un host remoto, es posible que deba realizar un keylogin en el host remoto primero.
Interpretado por el Servidor
El método Interpretado por el Servidor proporciona dos cadenas al servidor X para su entrada en la lista de control de acceso. La primera cadena representa el tipo de entrada y la segunda cadena contiene el valor de la entrada. Estas cadenas son interpretadas por el servidor y diferentes implementaciones y compilaciones pueden admitir diferentes tipos de entradas. Los tipos admitidos en la implementación de ejemplo se definen en la sección TIPOS DE ACCESO INTERPRETADOS POR EL SERVIDOR a continuación. Las entradas de este tipo se pueden manipular a través de xhost. Por ejemplo, para agregar una entrada Interpretada por el Servidor de tipo localuser con un valor de root, el comando es xhost +si:localuser:root.

EL ARCHIVO DE AUTORIZACIÓN

Excepto para el control de Acceso por Host y el control de Acceso Interpretado por el Servidor, cada uno de estos sistemas utiliza datos almacenados en el archivo .Xauthority para generar la información de autorización correcta que se pasará al servidor X al configurar la conexión. MIT-MAGIC-COOKIE-1 y XDM-AUTHORIZATION-1 almacenan datos secretos en el archivo; por lo que cualquiera que pueda leer el archivo puede acceder al servidor X. SUN-DES-1 solo almacena la identidad del principal que inició el servidor (unix.hostname@domain cuando el servidor es iniciado por xdm), por lo que no es útil para nadie que no esté autorizado a conectarse al servidor.

Cada entrada en el archivo .Xauthority coincide con una cierta familia de conexión (TCP/IP, DECnet o conexiones locales) y nombre de pantalla X (nombre del host más número de pantalla). Esto permite que múltiples entradas de autorización para diferentes pantallas compartan el mismo archivo de datos. Una familia de conexión especial (FamilyWild, valor 65535) hace que una entrada coincida con todas las pantallas, permitiendo que la entrada se use para todas las conexiones. Cada entrada contiene además el nombre de autorización y cualquier dato de autorización privado que sea necesario para ese tipo de autorización para generar la información correcta en el momento de la configuración de la conexión.

El programa xauth manipula el formato del archivo .Xauthority. Comprende la semántica de las familias de conexión y los formatos de dirección, mostrándolos en un formato fácil de entender. También comprende que SUN-DES-1 utiliza valores de cadena para los datos de autorización y los muestra de manera apropiada.

El servidor X (cuando se ejecuta en una estación de trabajo) lee la información de autorización de un nombre de archivo pasado en la línea de comandos con la opción -auth (consulte la página del manual de Xserver). Las entradas de autorización en el archivo se utilizan para controlar el acceso al servidor. En cada uno de los esquemas de autorización mencionados anteriormente, los datos necesarios para que el servidor inicialice un esquema de autorización son idénticos a los datos necesarios para que el cliente genere la información de autorización apropiada, por lo que el mismo archivo puede ser utilizado por ambos procesos. Esto es especialmente útil cuando se utiliza xinit.

NAME

Xsecurity - X Window System security mechanisms

OVERVIEW

This document describes the security mechanisms used by the X Window System, as well as the file format used for storing authorization information. Security in the X Window System is based on authorization. When a client attempts to connect to an X server, the server checks whether the client is authorized to connect. If the client is authorized, the server allows the connection and exchanges authorization information with the client. This information is used to authenticate all subsequent communication between the client and the server.

ACCESS SYSTEM DESCRIPTIONS

The X Window System supports several authorization mechanisms. The following are common examples:

MIT-MAGIC-COOKIE-1
This system uses 128 bits of data shared between the user and the X server. Any collection of bits can be used. Xdm generates these keys using a cryptographically secure pseudo random number generator, and so the key to the next session cannot be computed from the current session key.
XDM-AUTHORIZATION-1
This system uses two pieces of information. First, 64 bits of random data, second a 56 bit DES encryption key (again, random data) stored in 8 bytes, the last byte of which is ignored. Xdm generates these keys using the same random number generator as is used for MIT-MAGIC-COOKIE-1.
SUN-DES-1
This system needs a string representation of the principal which identifies the associated X server. This information is used to encrypt the client's authority information when it is sent to the X server. When xdm starts the X server, it uses the root principal for the machine on which it is running (unix.hostname@domain, e.g., "unix.expire.lcs.mit.edu@our.domain.edu"). Putting the correct principal name in the .Xauthority file causes Xlib to generate the appropriate authorization information using the secure RPC library.

SERVER INTERPRETED ACCESS TYPES

The sample implementation includes several Server Interpreted mechanisms:

    IPv6	IPv6 literal addresses
    hostname	Network host name
    localuser	Local connection user id
    localgroup	Local connection group id
IPv6
A literal IPv6 address as defined in IETF RFC 3513. This allows adding IPv6 addresses when the X server supports IPv6, but the xhost client was compiled without IPv6 support.
hostname
The value must be a hostname as defined in IETF RFC 2396. Due to Mobile IP and dynamic DNS, the name service is consulted at connection authentication time, unlike the traditional host access control list which only contains numeric addresses and does not automatically update when a host's address changes. Note that this definition of hostname does not allow use of literal IP addresses.
localuser & localgroup
On systems which can determine in a secure fashion the credentials of a client process, the "localuser" and "localgroup" authentication methods provide access based on those credentials. The format of the values provided is platform specific. For POSIX & UNIX platforms, if the value starts with the character '#', the rest of the string is treated as a decimal uid or gid, otherwise the string is defined as a user name or group name.
If your system supports this method and you use it, be warned that some programs that proxy connections and are setuid or setgid may get authenticated as the uid or gid of the proxy process. For instance, some versions of ssh will be authenticated as the user root, no matter what user is running the ssh client, so on systems with such software, adding access for localuser:root may allow wider access than intended to the X display.
