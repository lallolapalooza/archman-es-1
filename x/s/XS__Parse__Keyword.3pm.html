XS::Parse::Keyword(3pm) Documentación de Perl contribuida por el usuario XS::Parse::Keyword(3pm)

NOMBRE

"XS::Parse::Keyword" - Funciones XS para ayudar en el análisis de sintaxis de palabras clave

DESCRIPCIÓN

Este módulo proporciona algunas funciones XS para ayudar a escribir módulos de sintaxis que proporcionan nueva sintaxis visible en Perl, principalmente para autores de plugins de palabras clave que utilizan el mecanismo de hook "PL_keyword_plugin". Es poco probable que sea de mucha utilidad para otros; y muy poco probable que sea de utilidad al escribir código Perl usando estos. A menos que estés escribiendo un plugin de palabra clave usando XS, este módulo no es para ti.

Este módulo también es actualmente experimental, y el diseño todavía está evolucionando y sujeto a cambios. Las versiones posteriores pueden romper la compatibilidad de ABI, requiriendo cambios o al menos una reconstrucción de cualquier módulo que dependa de él.

FUNCIONES XS

boot_xs_parse_keyword

void boot_xs_parse_keyword(double ver);

Llama a esta función desde tu sección "BOOT" para inicializar el módulo y los hooks de análisis.

ver debe ser 0 o un número decimal para el requisito de versión del módulo; por ejemplo:

boot_xs_parse_keyword(0.14);

register_xs_parse_keyword

void register_xs_parse_keyword(const char *keyword,
  const struct XSParseKeywordHooks *hooks, void *hookdata);

Esta función instala un conjunto de hooks de análisis para asociar con la palabra clave dada. Dicha palabra clave será entonces manejada automáticamente por un analizador de palabras clave instalado por el propio "XS::Parse::Keyword".

HOOKS DE ANÁLISIS

La estructura "XSParseKeywordHooks" proporciona las siguientes etapas de hook, que se invocan en el orden dado.

flags

Las siguientes banderas están definidas:

"XPK_FLAG_EXPR"
Se espera que la función de análisis o compilación devuelva "KEYWORD_PLUGIN_EXPR".
"XPK_FLAG_STMT"
Se espera que la función de análisis o compilación devuelva "KEYWORD_PLUGIN_STMT".

Estas dos banderas son en gran medida para el beneficio de proporcionar información estática en el momento del registro para ayudar al análisis estático u otras tareas relacionadas a saber qué tipo de elemento gramatical producirá esta palabra clave.

"XPK_FLAG_AUTOSEMI"
La sintaxis forma una declaración completa, que debe ir seguida de un punto y coma separador de declaraciones (";"). Este punto y coma es opcional al final de un bloque.

El punto y coma, si está presente, se consumirá automáticamente.

"XPK_FLAG_BLOCKSCOPE"
Todo el proceso de análisis y compilación se envolverá en un par de llamadas block_start() y block_end(). Esto asegura que, por ejemplo, cualquier variable léxica recién introducida no escape del ámbito de la sintaxis creada por la palabra clave.
"XPK_FLAG_PERMIT_LEXICAL"
La palabra clave permite un prefijo "my", para que el autor indique que debe tener efecto léxico. Normalmente esto solo tendría sentido para palabras clave que declaran alguna nueva entidad nombrada, donde normalmente la entidad de esa palabra clave se nombra en la tabla de símbolos en su lugar.

En el momento del "parse" y "build", este hecho se indicará con "PL_parser->in_my" establecido en el valor "KEY_my", en lugar de su valor cero habitual.

Esta bandera se ignora silenciosamente en versiones de Perl anteriores a 5.16, porque en versiones anteriores la solución alternativa para detectar el prefijo "my" causa fallos de análisis aparentemente no relacionados en utf8.pm.

La Etapa de "permitir"

const char *permit_hintkey;
bool (*permit) (pTHX_ void *hookdata);

Invocado por el hook del analizador de palabras clave instalado, que se utiliza para manejar palabras clave registradas por "register_xs_parse_keyword".

Como atajo para el caso común, el "permit_hintkey" puede apuntar a una cadena para buscar en el hash de pistas. Si el nombre de clave dado no se encuentra en el hash de pistas, la palabra clave no está permitida. Si la clave está presente, la función "permit" se invoca como normal.

Si no es rechazada por una clave de pista que no se encontró en el hash de pistas, la parte de la función de la etapa se llama a continuación y debe inspeccionar si la palabra clave está permitida en este momento, quizás inspeccionando otras pistas léxicas, y devolver verdadero solo si la palabra clave está permitida.

Tanto la cadena como la función son opcionales. Cualquiera de las dos o ambas pueden estar presentes. Si ninguna está presente, la palabra clave siempre está permitida, lo cual probablemente no es lo que querías hacer.

La Etapa de "verificar"

void (*check)(pTHX_ void *hookdata);

Invocado una vez que la palabra clave ha sido permitida. Si está presente, esta función hook puede verificar el contexto léxico circundante, el estado u otra información y lanzar una excepción si no está satisfecha con que la palabra clave deba aplicarse en esta posición.

La Etapa de "analizar"

Esta etapa se invoca una vez que la palabra clave ha sido verificada, y realmente analiza el texto entrante en un optree. Se implementa llamando al **primer** de los siguientes punteros de función que no sea NULL. La función invocada puede opcionalmente construir un optree para representar la sintaxis analizada y colocarlo en la variable dirigida por "out". Si no lo hace, se construirá un "OP_NULL" simple en su lugar.

lex_read_space() se llama tanto antes como después de invocar esta etapa, por lo que en muchos casos simples, la función hook en sí misma no necesita preocuparse por ello.

int (*parse)(pTHX_ OP **out, void *hookdata);

Si está presente, esto debería consumir texto del búfer del analizador invocando las funciones "lex_*" o "parse_*" y eventualmente devolver un valor de resultado "KEYWORD_PLUGIN_*".

Esta es la opción más genérica y potente, pero requiere la mayor cantidad de trabajo de implementación.

int (*build)(pTHX_ OP **out, XSParseKeywordPiece *args[], size_t nargs, void *hookdata);

Si "parse" no está presente, esto se llama en su lugar después de analizar una secuencia de argumentos, de los tipos dados por el campo pieces; que debe ser una matriz terminada en cero de tipos de piezas.

Esta alternativa es algo menos genérica y potente que proporcionar "parse" usted mismo, pero implica mucho menos trabajo de análisis y es más corta y fácil de implementar.

int (*build1)(pTHX_ OP **out, XSParseKeywordPiece *arg0, void *hookdata);

Si ni "parse" ni "build" están presentes, esto se llama como una variante más simple de "build" cuando solo se requiere un único argumento. Toma su tipo del campo "piece1" en su lugar.

PIEZAS Y TIPOS DE PIEZAS

Cuando se utilizan las alternativas "build" o "build1" para la fase de "parse", la sintaxis real es analizada automáticamente por este módulo, de acuerdo con la especificación dada por el campo pieces o piece1. El resultado de ese paso de análisis se coloca en el parámetro args o arg0 para la función invocada.

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

, usando un tipo "struct" que consta de los siguientes campos:

typedef struct {
   union {
      OP *op;
      CV *cv;
      SV *sv;
      int i;
      struct {
         SV *name;
         SV *value;
      } attr;
      PADOFFSET padix;
      struct XSParseInfixInfo *infix;
   };
   int line;
} XSParseKeywordPiece;

Qué campo de la unión anónima se establece depende del tipo de la pieza. El campo line contiene el número de línea del archivo fuente donde comenzó el análisis sintáctico de esa pieza.

Algunos tipos de piezas son "atómicos", cuya definición es autocontenida. Otros son estructurales, definidos en términos de piezas internas. Juntos forman una definición completa en forma de árbol de la sintaxis que la palabra clave espera encontrar.

Los tipos atómicos generalmente proporcionan exactamente un argumento a la lista de args (con la excepción de las coincidencias literales, que no proporcionan nada). Los tipos estructurales pueden proporcionar un argumento inicial por sí mismos, seguido de una lista de los valores de cada subpieza que contenían en su interior. Por lo tanto, aunque la estructura de datos que define la forma sintáctica es un árbol, los valores de los argumentos en los que se analiza se pasan como una matriz plana a la función "build".

Algunos tipos estructurales necesitan poder determinar si la sintaxis relacionada con alguna parte opcional de ellos está presente en el texto de origen entrante o no. En este caso, las piezas relacionadas con esas partes opcionales deben admitir la "sondeo". Esta capacidad se indica también a continuación.

Muchos de los tipos de piezas atómicas tienen una variante que es opcional; si la entrada dada no se parece a la sintaxis esperada para el tipo de pieza, una versión de tipo con el sufijo "_OPT" en su lugar devolverá "NULL" en su puntero de resultado.

El tipo de cada pieza debe ser uno de los siguientes valores de macro.

XPK_BLOCK

atómico, puede sondear, emite op.

XPK_BLOCK

Se espera un bloque de código delimitado por llaves, pasado como un optree en el campo op. Esto se analizará como un bloque dentro del ámbito de la función actual.

Esto se puede sondear comprobando la presencia del carácter de llave de apertura ("{").

Tenga cuidado al definir gramáticas con esto, ya que una llave de apertura también es un carácter válido para iniciar una expresión de término, por ejemplo. Dada la elección entre "XPK_BLOCK" y "XPK_TERMEXPR", cualquiera de ellos podría intentar consumir dicho código como

{ 123, 456 }

XPK_BLOCK_VOIDCTX, XPK_BLOCK_SCALARCTX, XPK_BLOCK_LISTCTX

Variantes de "XPK_BLOCK" que envuelven un ámbito de contexto void, escalar o de lista alrededor del bloque.

XPK_PREFIXED_BLOCK

estructural, emite op.

XPK_PREFIXED_BLOCK(pieces ...)

Se esperan algunas piezas, seguidas de un bloque de código delimitado por llaves, que se pasa como un optree en el campo op. Las piezas del prefijo se analizan primero y sus resultados se pasan antes del bloque en sí.

Toda la secuencia, incluidos los elementos del prefijo, está contenida dentro de un par de llamadas a block_start() / block_end(). Esto permite que las piezas del prefijo introduzcan nuevos elementos en el ámbito léxico del bloque, por ejemplo, mediante el uso de "XPK_LEXVAR_MY".

Se realiza automáticamente una llamada a intro_my() al final de las piezas del prefijo, antes de que se analice el bloque en sí, asegurando que las nuevas variables léxicas sean ahora visibles.

Además, aquí se reconocen los siguientes tipos de piezas adicionales:

XPK_SETUP
void setup(pTHX_ void *hookdata);
XPK_SETUP(&setup)

atómico, no emite nada.

Este tipo de pieza ejecuta una función dada por puntero. Típicamente, esta función puede usarse para introducir nuevo estado léxico en el analizador sintáctico, o de alguna otra manera tener algún efecto secundario en el contexto de análisis del bloque a analizar.

XPK_PREFIXED_BLOCK_ENTERLEAVE

Una variante de "XPK_PREFIXED_BLOCK" que además envuelve toda la operación de análisis, incluyendo block_start(), block_end() y cualquier llamada a las funciones "XPK_SETUP", dentro de un par "ENTER"/"LEAVE".

Esto no debería marcar una diferencia en las piezas de análisis estándar proporcionadas aquí, pero puede ser un comportamiento útil para el código en la función de configuración, especialmente si desea modificar el estado del analizador y usar la pila guardada para asegurar que se restaure de nuevo cuando el análisis haya finalizado.

XPK_ANONSUB

atómico, emite cv.

Se espera un bloque de código delimitado por llaves, y se ensambla en el cuerpo de una nueva subrutina anónima. Esto se pasará como un CV de protosub en el campo cv.

XPK_STAGED_ANONSUB

XPK_STAGED_ANONSUB(stages ...)

estructural, emite cv.

Una variante de "XPK_ANONSUB" que acepta punteros de función adicionales para ser invocados en varios puntos durante el análisis y la compilación. Estos pueden usarse para interrumpir el análisis normal de manera similar a XS::Parse::Sublike, aunque actualmente de forma algo menos flexible.

La lista stages puede contener elementos de los siguientes tipos. No es necesario que todas las etapas estén presentes, pero las que estén presentes deben estar en el siguiente orden. Se permiten múltiples copias de cada etapa; se invocan en el orden escrito, con código de análisis sucediendo entre ellas.

XPK_ANONSUB_PREPARE
XPK_ANONSUB_PREPARE(&callback)

atómico, no emite nada.

Invoca la función de devolución de llamada antes de start_subparse().

XPK_ANONSUB_START
XPK_ANONSUB_START(&callback)

atómico, no emite nada.

Invoca la función de devolución de llamada después de block_start() pero antes de analizar el contenido real del bloque.

XPK_ANONSUB_END
OP *op_wrapper_callback(pTHX_ OP *o, void *hookdata);
XPK_ANONSUB_END(&op_wrapper_callback)

atómico, no emite nada.

Invoca la función de devolución de llamada después de analizar el contenido del bloque pero antes de llamar a block_end(). La función de devolución de llamada puede modificar el optree si es necesario y devolver uno nuevo.

XPK_ANONSUB_WRAP
XPK_ANONSUB_WRAP(&op_wrapper_callback)

atómico, no emite nada.

Invoca la función de devolución de llamada después de block_end() pero antes de pasar el optree a newATTRSUB(). La función de devolución de llamada puede modificar el optree si es necesario y devolver uno nuevo.

XPK_ARITHEXPR. XPK_ARITHEXPR_OPT

atómico, emite op.

XPK_ARITHEXPR

Se espera una expresión aritmética, analizada usando parse_arithexpr() y pasada como un optree en el campo op.

XPK_ARITHEXPR_VOIDCTX, XPK_ARITHEXPR_OPT

XPK_ARITHEXPR_SCALARCTX, XPK_ARITHEXPR_SCALARCTX_OPT

Variantes de "XPK_ARITHEXPR" que ponen la expresión en contexto void o escalar.

XPK_TERMEXPR, XPK_TERMEXPR_OPT

atómico, emite op.

XPK_TERMEXPR

Se espera una expresión de término, analizada usando parse_termexpr() y pasada como un optree en el campo op.

XPK_TERMEXPR_VOIDCTX, XPK_TERMEXPR_VOIDCTX

XPK_TERMEXPR_SCALARCTX, XPK_TERMEXPR_SCALARCTX_OPT

Variantes de "XPK_TERMEXPR" que ponen la expresión en contexto void o escalar.

XPK_LISTEXPR, XPK_LISTEXPR_OPT

atómico, emite op.

XPK_LISTEXPR

Se espera una expresión de lista, analizada usando parse_listexpr() y pasada como un optree en el campo op.

XPK_LISTEXPR_LISTCTX, XPK_LISTEXPR_LISTCTX_OPT

Variante de "XPK_LISTEXPR" que pone la expresión en contexto de lista.

XPK_PREFIXED_TERMEXPR_ENTERLEAVE, XPK_PREFIXED_LISTEXPR_ENTERLEAVE

XPK_PREFIXED_TERMEXPR_ENTERLEAVE(pieces ...)
XPK_PREFIXED_LISTEXPR_ENTERLEAVE(pieces ...)

Variantes de "XPK_TERMEXPR" o "XPK_LISTEXPR" que esperan una secuencia de piezas primero antes de analizar una expresión de término, de forma similar a cómo funciona "XPK_PREFIXED_BLOCK_ENTERLEAVE". Toda la operación está envuelta en un par "ENTER"/"LEAVE".

Estas están destinadas solo al uso de piezas "XPK_SETUP" como prefijos. Cualquier otra pieza que realmente analice entrada real probablemente causará gramáticas excesivamente complejas, sutiles o directamente ambiguas, y debe evitarse.

XPK_IDENT, XPK_IDENT_OPT

atómico, puede sondear, emite sv.

Se espera un nombre de identificador sin comillas, y se pasa como un SV que contiene un PV en el campo *sv*. No se permite que un identificador contenga un doble dos puntos ("::").

XPK_PACKAGENAME, XPK_PACKAGENAME_OPT

atómico, puede sondear, emite sv.

Se espera un nombre de paquete sin comillas, y se pasa como un SV que contiene un PV en el campo *sv*. Un nombre de paquete es similar a un identificador, excepto que permite dobles dos puntos en el medio.

XPK_LEXVARNAME

atómico, emite sv.

XPK_LEXVARNAME(kind)

Se espera un nombre de variable léxica, y se pasa como un SV que contiene un PV en el campo *sv*. El argumento "kind" especifica qué tipos de variables están permitidos, y debe ser una máscara de bits de uno o más bits de "XPK_LEXVAR_SCALAR", "XPK_LEXVAR_ARRAY" y "XPK_LEXVAR_HASH". Un atajo conveniente "XPK_LEXVAR_ANY" permite los tres.

XPK_ATTRIBUTES

atómico, emite i seguido de más argumentos.

Se espera una lista de atributos prefijados con ":", en el mismo formato que los atributos de subrutina o variable. Un ":" inicial opcional indica la presencia de atributos, y luego se analizan uno o más de ellos. Los atributos pueden separarse opcionalmente por ":" adicionales, pero esto no es obligatorio.

Se espera que cada atributo sea un nombre de identificador, seguido de un valor opcional entre paréntesis. El espacio en blanco **NO** está permitido entre el nombre y el valor, según las reglas de análisis estándar de Perl.

:attrname
:attrname(value)

El campo *i* indica cuántos atributos se encontraron. Ese número de argumentos adicionales se pasa, cada uno conteniendo dos SVs en los campos *attr.name* y *attr.value*. Este número puede ser cero.

No es un error que no haya atributos presentes, o que falte el dos puntos opcional. En este caso, *i* se establecerá en cero.

XPK_VSTRING, XPK_VSTRING_OPT

atómico, puede sondear, emite sv.

Se espera una cadena de versión, con el formato "v1.234" incluyendo el carácter "v" inicial. Se pasa como un objeto SV de versión en el campo *sv*.

XPK_LEXVAR

atómico, emite padix.

XPK_LEXVAR(kind)

Se espera un nombre de variable léxica y se busca en la almohadilla actual. El índice de almohadilla resultante se pasa en el campo *padix*. No ocurre ningún error si la variable no se encuentra; se pasa el valor "NOT_IN_PAD" en su lugar.

El argumento "kind" especifica qué tipos de variables están permitidos, según "XPK_LEXVARNAME".

XPK_LEXVAR_MY

atómico, emite padix.

XPK_LEXVAR_MY(kind)

Se espera un nombre de variable léxica, se agrega a la almohadilla actual como si se especificara en una expresión "my", y se pasa como el índice de almohadilla en el campo *padix*.

El argumento "kind" especifica qué tipos de variables están permitidos, según "XPK_LEXVARNAME".

XPK_COMMA, XPK_COLON, XPK_EQUALS

atómico, puede sondear, no emite nada.

Se espera un carácter literal (",", ":" o "="). No se pasa ningún valor de argumento.

XPK_AUTOSEMI

atómico, no emite nada.

Se espera opcionalmente un punto y coma literal (";") como terminador de sentencia. Si el siguiente token es una llave de cierre para indicar el final de un bloque, entonces no se requiere un punto y coma. Si se encuentra algo más, se generará un error.

Este tipo de pieza es lo mismo que especificar "XPK_FLAG_AUTOSEMI". Es útil colocarlo al final de una secuencia que forma parte de una elección de sintaxis, donde algunas formas indican una sentencia que termina en punto y coma, mientras que otras pueden terminar en un bloque completo que no lo necesita.

XPK_INFIX_*

atómico, puede sondear, emite infix.

Un operador infijo reconocido por XS::Parse::Infix. El puntero devuelto apunta a una estructura asignada por "XS::Parse::Infix" que describe el operador.

Se proporcionan varias versiones de la macro, cada una utilizando un filtro de selección diferente para elegir ciertos operadores infijos disponibles:

XPK_INFIX_RELATION         // cualquier operador relacional
XPK_INFIX_EQUALITY         // un operador de igualdad como `==` o `eq`
XPK_INFIX_MATCH_NOSMART    // cualquier tipo de operador "match", excepto smartmatch
XPK_INFIX_MATCH_SMART      // XPK_INFIX_MATCH_NOSMART más smartmatch

XPK_LITERAL

atómico, puede sondear, no emite nada.

XPK_LITERAL("literal")

Se espera una coincidencia de cadena literal. No se pasa ningún valor de argumento.

Esta forma generalmente debe evitarse siempre que sea posible, ya que es muy fácil de abusar para crear sintaxis que confunden tanto a los humanos como a las herramientas de código. Generalmente, se reserva solo para el primer componente de una secuencia "XPK_OPTIONAL" o "XPK_REPEATED", para proporcionar una "palabra clave secundaria" que dicho elemento repetido pueda buscar.

XPK_KEYWORD

atómico, puede sondear, no emite nada.

XPK_KEYWORD("keyword")

Se espera una coincidencia de cadena literal. No se pasa ningún valor de argumento.

Esto es similar a "XPK_LITERAL" excepto que además verifica que el carácter siguiente no sea un carácter de identificador. Esto asegura que se conserve el comportamiento deseado similar a una palabra clave. Por ejemplo, dada la entrada "keyword", la pieza XPK_LITERAL("key") coincidiría, mientras que XPK_KEYWORD("key") no lo haría debido al carácter posterior "w".

XPK_INTRO_MY

atómico, no emite nada.

Llama inmediatamente a la función central de Perl intro_my(). No se consume entrada ni se genera valor de salida. Esto es a menudo útil después de "XPK_LEXVAR_MY".

XPK_WARNING

atómico, no emite nada.

XPK_WARNING("message here")

Emite una advertencia llamando a la función central de Perl warn() sobre la cadena literal dada. Esto es equivalente a simplemente llamar a warn() desde la función de compilación, excepto que se emite inmediatamente en el momento del análisis, por lo que la numeración de líneas será más precisa. Además, al colocarlo como parte de una secuencia opcional o de elección, la advertencia solo se emitirá condicionalmente si se encuentra esa parte de la estructura gramatical.

XPK_WARNING_...

Existen varias variantes de "XPK_WARNING" que son condicionales a que se habiliten categorías de advertencia particulares. Estas son las que probablemente sean útiles en el momento del análisis:

XPK_WARNING_AMBIGUOUS
XPK_WARNING_DEPRECATED
XPK_WARNING_EXPERIMENTAL
XPK_WARNING_PRECEDENCE
XPK_WARNING_SYNTAX

XPK_SEQUENCE

estructural, podría admitir sondeo, no emite nada.

XPK_SEQUENCE(pieces ...)

Un tipo estructural que contiene una serie de piezas. Esto es normalmente equivalente a simplemente colocar las piezas en secuencia dentro de su propio contenedor, pero es útil dentro de "XPK_CHOICE" o "XPK_TAGGEDCHOICE".

"XPK_SEQUENCE" admite sondeo si su primera pieza contenida lo hace; es decir, es transparente al sondeo.

XPK_OPTIONAL

estructural, emite i.

XPK_OPTIONAL(pieces ...)

Un tipo estructural que puede esperar encontrar sus piezas contenidas, o se conforma con no encontrarlas. Esto pasará un argumento cuyo campo *i* contiene 1 o 0, dependiendo de si se encontraron los contenidos. El primer tipo de pieza dentro debe admitir sondeo.

XPK_REPEATED

estructural, emite i.

XPK_REPEATED(pieces ...)

Un tipo estructural que espera encontrar sus piezas contenidas una o más veces. Esto pasará un argumento cuyo campo *i* contiene el número de veces que se encontraron las piezas. El primer tipo de pieza dentro debe admitir sondeo.

XPK_CHOICE

estructural, emite i.

XPK_CHOICE(pieces ...)

Un tipo estructural que intenta hacer coincidir sus piezas contenidas en secuencia, pero solo tiene éxito si una de ellas coincide completamente. Se pasa un argumento cuyo campo *i* contiene el índice (basado en cero) de la opción que coincidió. Todas las piezas contenidas deben admitir sondeo.

XPK_TAGGEDCHOICE

estructural, emite i.

XPK_TAGGEDCHOICE(tag1 => pieces1, tag2 => pieces2, ...)

Similar a "XPK_CHOICE", excepto que cada opción está precedida por una etiqueta. La etiqueta se consume y se pasa en el campo *tag*. Se pasa un argumento cuyo campo *i* contiene el índice (basado en cero) de la opción que coincidió. Todas las piezas contenidas deben admitir sondeo.

XPK_END_OF_INPUT

atómico, no emite nada.

Espera el final de la entrada. Si se encuentra algo más, se genera un error.

XPK_NULL

atómico, no emite nada.

No consume ninguna entrada y no genera ningún valor. Esto puede ser útil como marcador de posición en secuencias, o para indicar un punto en el que la entrada no es necesaria.

XPK_SET_FLAG, XPK_CLEAR_FLAG

atómico, no emite nada.

XPK_SET_FLAG(flag)
XPK_CLEAR_FLAG(flag)

Establece o borra un bit de bandera en el contexto de análisis. El argumento "flag" debe ser una de las constantes "XPK_FLAG_...".

XPK_DEBUG_TRACE

atómico, no emite nada.

XPK_DEBUG_TRACE("message here")

Imprime un mensaje de depuración si el analizador se está ejecutando en modo de depuración. Esto es similar a "XPK_WARNING", pero solo aparece cuando se habilita explícitamente la depuración.

XPK_DEBUG_DUMP

atómico, no emite nada.

Activa una traza de depuración completa del estado actual del analizador. Esto puede generar una gran cantidad de salida y solo debe usarse cuando sea necesario para la depuración profunda.

XPK_REPEATED

estructural, emite i.

XPK_REPEATED(pieces ...)

Un tipo estructural que espera encontrar cero o más repeticiones de sus piezas contenidas. Esto pasará un argumento cuyo campo i contiene el número de repeticiones encontradas. El primer tipo de pieza contenido debe soportar la sonda (probe).

XPK_CHOICE

estructural, puede sondear, emite i.

XPK_CHOICE(options ...)

Un tipo estructural que espera encontrar una de varias opciones alternativas. Se proporciona una lista ordenada de tipos, todos los cuales deben soportar la sonda. Esto pasará un argumento cuyo campo i da el índice de la primera opción que fue aceptada. La primera opción toma el valor 0.

Dado que cada una de las opciones se interpreta como una alternativa, no como una secuencia, deberías usar "XPK_SEQUENCE" si una secuencia de múltiples elementos debe considerarse como una única alternativa.

No es un error si ninguna opción coincide. En ese momento, el campo i se establecerá en -1.

Si necesitas un mensaje de error en este caso, establece la última opción para que sea del tipo "XPK_FAILURE". Esto causará que se imprima un mensaje de error en su lugar.

XPK_FAILURE("cadena de mensaje")

XPK_TAGGEDCHOICE

estructural, puede sondear, emite i.

XPK_TAGGEDCHOICE(choice, tag, ...)

Un tipo estructural similar a "XPK_CHOICE", excepto que cada tipo de opción va seguido de un elemento de tipo "XPK_TAG" que proporciona un entero. Es ese valor entero, en lugar del índice posicional de la opción dentro de la lista, lo que se pasa en el campo i.

XPK_TAG(valor)

Dado que cada una de las opciones se interpreta como una alternativa, no como una secuencia, deberías usar "XPK_SEQUENCE" si una secuencia de múltiples elementos debe considerarse como una única alternativa.

XPK_COMMALIST

estructural, puede que soporte sonda, emite i.

XPK_COMMALIST(pieces ...)

Un tipo estructural que espera encontrar una o más repeticiones de sus piezas contenidas, separadas por caracteres de coma literal (","). Esto es algo similar a "XPK_REPEATED", excepto que necesita al menos una copia, necesita comas entre sus elementos, pero no requiere que la primera pieza contenida soporte la sonda (la coma en sí misma es suficiente para indicar una repetición).

"XPK_COMMALIST" soporta la sonda si su primera pieza contenida lo hace; es decir, es transparente a la sonda.

XPK_PARENS

estructural, puede sondear, no emite nada.

XPK_PARENS(pieces ...)

Un tipo estructural que espera encontrar una secuencia de piezas, todas contenidas entre paréntesis como "( ... )". Esto no pasará ningún argumento adicional.

XPK_ARGS

estructural, no emite nada.

XPK_ARGS(pieces ...)

Un tipo estructural similar a "XPK_PARENS", excepto que los paréntesis son opcionales; muy parecido al análisis de Perl de llamadas a funciones conocidas.

Si se encuentran paréntesis en la entrada, serán consumidos por esta pieza y se comportará de manera idéntica a "XPK_PARENS". Si no hay un paréntesis de apertura, esta pieza se comportará como "XPK_SEQUENCE" y consumirá todas las piezas dentro de ella, sin esperar un paréntesis de cierre.

XPK_BRACKETS

estructural, puede sondear, no emite nada.

XPK_BRACKETS(pieces ...)

Un tipo estructural que espera encontrar una secuencia de piezas, todas contenidas entre corchetes como "[ ... ]". Esto no pasará ningún argumento adicional.

XPK_BRACES

estructural, puede sondear, no emite nada.

XPK_BRACES(pieces ...)

Un tipo estructural que espera encontrar una secuencia de piezas, todas contenidas entre llaves como "{ ... }". Esto no pasará ningún argumento adicional.

Tenga en cuenta que esto no es necesario usarlo con "XPK_BLOCK" o "XPK_ANONSUB"; esos ya consumirán un conjunto de llaves. Esto está destinado a sintaxis especial restringida que no debería aceptar simplemente un bloque arbitrario.

XPK_CHEVRONS

estructural, puede sondear, no emite nada.

XPK_CHEVRONS(pieces ...)

Un tipo estructural que espera encontrar una secuencia de piezas, todas contenidas entre corchetes angulares como "< ... >". Esto no pasará ningún argumento adicional.

Recuerde que expresiones como "a > b" son expresiones de término válidas, por lo que el contenido de este ámbito no debería permitir expresiones arbitrarias o el corchete de cierre será ambiguo.

XPK_PARENS_OPT, XPK_BRACKETS_OPT, XPK_BRACES_OPT, XPK_CHEVRONS_OPT

estructural, puede sondear, emite i.

XPK_PARENS_OPT(pieces ...)
XPK_BRACKETS_OPT(pieces ...)
XPK_BRACES_OPT(pieces ...)
XPK_CHEVERONS_OPT(pieces ...)

Cada una de las cuatro macros de estructura contenida anteriores tiene una variante opcional, cuyo nombre se sufija con "_OPT". Estas pasan un argumento cuyo campo i es verdadero o falso, indicando si se encontró el ámbito, seguido de los valores del propio ámbito.

Este es un atajo conveniente para anidar el ámbito dentro de una macro "XPK_OPTIONAL".

XPK_..._pieces

XPK_SEQUENCE_pieces(ptr)
XPK_OPTIONAL_pieces(ptr)
...

Para cada una de las macros "XPK_..." que toma una lista de piezas de longitud variable, hay una variante cuyo nombre termina en "..._pieces", que toma un único argumento de puntero directamente. Este debe apuntar a un array de "const XSParseKeywordPieceType []" cuyo último elemento es el elemento cero.

Normalmente, el código escrito a mano de una gramática fija sería poco probable que usara estas formas, pero pueden ser útiles en casos generados dinámicamente.
