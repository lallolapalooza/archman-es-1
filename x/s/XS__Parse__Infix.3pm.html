XS::Parse::Infix(3pm) Documentación de Perl contribuida por el usuario XS::Parse::Infix(3pm)

NOMBRE

"XS::Parse::Infix" - Funciones XS para ayudar en el análisis de operadores infijos

DESCRIPCIÓN

Este módulo proporciona algunas funciones XS para ayudar a escribir módulos de sintaxis que proporcionan nuevos operadores infijos como sintaxis de perl, principalmente para autores de plugins de sintaxis. Es poco probable que sea de gran utilidad para nadie más; y es muy poco probable que sea de utilidad alguna al escribir código perl que los utilice. A menos que esté escribiendo un plugin de sintaxis usando XS, este módulo no es para usted.

Este módulo también es actualmente experimental, y el diseño aún está evolucionando y sujeto a cambios. Las versiones posteriores pueden romper la compatibilidad de ABI, requiriendo cambios o al menos una reconstrucción de cualquier módulo que dependa de él.

Además, los lugares donde se puede utilizar esta funcionalidad son relativamente pequeños. El soporte para operadores infijos personalizados, tal como se añadió en la versión de desarrollo de Perl "v5.37.7", y por lo tanto está presente en Perl "v5.38.0".

Además, los diversos tipos de tokens "XPK_INFIX_*" de XS::Parse::Keyword admiten consultas en este módulo, por lo que algunas sintaxis proporcionadas por otros módulos podrían ser capaces de hacer uso de estos nuevos operadores infijos.

Operadores con nombre léxico vs. con nombre global

Desde la versión 0.43, la forma en que opera este módulo ha cambiado. Desde esta versión, el método preferido de operación para los operadores infijos es que el módulo que los registra los cree con un nombre completamente cualificado (es decir, incluyendo el nombre del paquete que los implementa). Otro código que desee importar el operador puede entonces proporcionar un nombre local para él visible dentro de un alcance. Esto actúa como un alias para el nombre completamente cualificado registrado. El nombre importado no necesita ser el mismo en varios alcances; esto permite que los operadores importados se renombren en alcances específicos para evitar conflictos de nombres.

Las versiones anteriores de este módulo solo admitían operadores que tienen un nombre global que puede o no estar habilitado en alcances léxicos. Con este modelo, si bien la visibilidad de un operador se puede controlar por alcance, si es visible siempre debe tener el mismo nombre y no se puede renombrar para evitar un conflicto de nombres.

En alguna versión futura de este módulo, el método antiguo puede ser eliminado, una vez que todos los módulos existentes de CPAN se hayan actualizado al nuevo modelo.

CONSTANTES

HAVE_PL_INFIX_PLUGIN

if( XS::Parse::Infix::HAVE_PL_INFIX_PLUGIN ) { ... }

Esta constante es verdadera si se compila en un perl que admite el mecanismo de extensión "PL_infix_plugin", lo que significa que los operadores infijos personalizados registrados con este módulo serán reconocidos por el analizador de perl.

Ninguna versión de producción real de perl admite todavía esta característica, pero véase más arriba para obtener detalles de las versiones de desarrollo que sí lo hacen.

FUNCIONES PERL

apply_infix

$pkg->apply_infix( $on, $args, @infix );

Desde la versión 0.43.

Destinado a ser llamado por los métodos "import" y "unimport" de un módulo que implementa operadores infijos. Esto configura las diversas claves requeridas en el hash de pistas léxicas para crear un alias léxico para el operador (es) solicitado (s).

$on debe ser un valor verdadero para "import" o un valor falso para "unimport". $args debe ser una referencia a un array del array de argumentos, que se modificará para extraer los valores reconocidos, dejando atrás cualquier otra cosa no reconocida. @infix debe ser una lista de nombres de operadores implementados por el paquete que importa, nombrados por $pkg.

Después de invocar este método, el llamador debe inspeccionar los valores restantes en el array de argumentos, ya sea para manejarlos de alguna otra manera, o simplemente para quejarse de ellos.

package Some::Infix::Module;
sub import
{
   my $pkg = shift;
   $pkg->XS::Parse::Infix::apply_infix( 1, \@_, qw( operator names here ) );
   die "Unrecognised symbols: @_" if @_;
}

Cuando este módulo se "use"a, los operadores nombrados se aliásan de los nombres completamente cualificados.

use Some::Infix::Module qw( operator );
my $z = $x operator $y;

En este punto, el nombre "operator" se convierte en un alias léxico de "Some::Infix::Module::operator".

Cada nombre de operador importado puede ir seguido opcionalmente de opciones de importación, dadas en una referencia de hash. Actualmente, la única opción nombrada reconocida es "-as", que permite al alcance que importa proporcionar un nombre diferente para el operador importado, quizás para evitar conflictos de nombres, o por elegancia.

use Some::Infix::Module operator => { -as => "myname" };
my $z = $x myname $y;  # invoca Some::Infix::Module::operator

void boot_xs_parse_infix(double ver);

Llame a esta función desde su sección "BOOT" para inicializar el módulo y los ganchos de análisis.

ver debe ser 0 o un número decimal para el requisito de versión del módulo; por ejemplo,

parse_infix

bool parse_infix(enum XSParseInfixSelection select, struct XSParseInfixInfo **infop);

Desde la versión 0.27.

Esta función intenta analizar la sintaxis de un operador infijo desde la posición actual del analizador. Si tiene éxito, rellena la variable apuntada por infop con un puntero a la estructura de información real y devuelve "true". Si no se encuentra ningún operador adecuado, devuelve "false".

xs_parse_infix_new_op

OP *xs_parse_infix_new_op(const struct XSParseInfixInfo *info, U32 flags,
   OP *lhs, OP *rhs);

Esta función construye un nuevo fragmento de árbol de operadores para representar la invocación del operador infijo con los operandos dados. Debería usarse de manera muy similar a la función "newBINOP" del núcleo de perl.

El puntero a la estructura "info" se obtendría del campo "infix" del resultado de invocar los diversos tipos de tokens "XPK_INFIX_*" de "XS::Parse::Keyword", o llamando directamente a "parse_infix".

register_xs_parse_infix

void register_xs_parse_infix(const char *opname,
   const struct XSParseInfixHooks *hooks, void *hookdata);

Esta función instala un conjunto de ganchos de análisis que se asociarán con el nombre del operador dado. Este nuevo operador estará entonces disponible a través de XS::Parse::Keyword por los diversos tipos de tokens "XPK_INFIX_*", "parse_infix", o para el "PL_infix_plugin" del núcleo de perl si está disponible.

Estos tokens producirán una estructura de información, con los siguientes campos:

struct XSParseInfixInfo {
   const char *opname;
   OPCODE opcode;  /* para operadores integrados, o OP_CUSTOM para
                      los registrados personalizados */
   struct XSParseInfixHooks *hooks;
   void                     *hookdata;
   enum XSParseInfixClassification cls;  /* desde la versión 0.28 */
};

NAME

XSParse::Infix::Hook – defining custom infix operators

SYNOPSIS

    use XS::Parse::Infix;

    my $hook = {
        flags           => 0,
        lhs_flags       => 0,
        rhs_flags       => 0,
        cls             => XPI_CLS_UNARY,
        wrapper_func_name => undef,
        permit_hintkey  => undef,
        permit          => undef,
        new_op          => undef,
        ppaddr          => undef,
        parse           => undef,
    };

    register_infix_hooks( $hook, ... );

DESCRIPTION

This module defines the structure for custom infix operators, and provides facilities for registering them. A custom infix operator can be used to extend Perl syntax, for example to implement custom operators for object oriented programming, or for specialised numerical or symbolic computations.

Registration is done via the register_infix_hooks function, which takes one or more hash references. Each hash reference represents a single operator definition.

The hash keys correspond to the fields of the XSParseInfixHooks structure described below.

Operator Names

Operator names are specified as strings, e.g. "<=>". If the name contains characters that could be mistaken for the start of a new interface style operator name (i.e. "::") then the name must be provided in quotes. Otherwise, if the name is not quoted it is assumed to be a fully-qualified operator name in the new interface style. If not, it is presumed to be an older globally-named one.

PARSE HOOKS

The "XSParseInfixHooks" structure provides the following fields which are used at various stages of parsing.

struct XSParseInfixHooks {
   U16 flags;
   U8 lhs_flags;
   U8 rhs_flags;
   enum XSParseInfixClassification cls;
   const char *wrapper_func_name;
   const char *permit_hintkey;
   bool (*permit)(pTHX_ void *hookdata);
   OP *(*new_op)(pTHX_ U32 flags, OP *lhs, OP *rhs, SV **parsedata, void *hookdata);
   OP *(*ppaddr)(pTHX);
   /* optional */
   void (*parse)(pTHX_ U32 flags, SV **parsedata, void *hookdata);
};

Flags

The "flags" field gives details on how to handle the operator overall. It should be a bitmask of the following constants, or left as zero:

XPI_FLAG_LISTASSOC
Since version 0.40.

If set, the operator supports n-way list-associative syntax; written in the form

OPERAND op OPERAND op OPERAND op ...

In this case, the custom operator will be a LISTOP rather than a BINOP, and every operand of the entire chain will be stored as a child op of it. The op function will need to know how many operands it is working on. There are two ways this may be indicated, depending on whether it was known at compile-time.

If the number operands is known at compile-time, the "OPf_STACKED" flag is not set, and the "op_private" field indicates the number of operand expressions that were present.

If the number is not known (for example, the operator is being used as the body of a generated wrapper function), the "OPf_STACKED" flag is set. The number of arguments will be passed as the UV of an extra SV which is pushed last to the stack. The op function should pop this first to find out.

It is typical to begin a list-associative op function with code such as:

int n = (PL_op->op_flags & OPf_STACKED) ? POPu : PL_op->op_private;

If the operator is list-associative, then "lhs_flags" and "rhs_flags" must be equal.

The "lhs_flags" and "rhs_flags" fields give details on how to handle the left- and right-hand side operands, respectively.

It should be set to one of the following constants, or left as zero:

XPI_OPERAND_TERM_LIST
The operand will be foced into list context, preserving the "OP_PUSHMARK" at the beginning. This means that the ppfunc for this infix operator will have to "POPMARK" to find that.
XPI_OPERAND_LIST
The same as above.

Older versions used to provide constants named "XPI_OPERAND_ARITH" and "XPI_OPERAND_TERM" but they related to an older version of the core perl branch. These names are now aliases for zero, and can be removed from new code.

In addition the following extra bitflags are defined:

XPI_OPERAND_ONLY_LOOK
If set, the operator function promises that it will not mutate any of its passed values, nor allow leaking of direct alias pointers to them via return value or other locations.

This flag is optional; omitting it when applicable will not change any observed behaviour. Setting it may enable certain optimisations to be performed.

Currently, this flag simply enables an optimisation in the call-checker for infix operator wrapper functions that take list-shaped operands. This optimisation discards an "OP_ANONLIST" operation which would create a temporary anonymous array reference for its operand values, allowing a slight saving of memory use and CPU time. This optimisation is only safe to perform if the operator does not mutate or retain aliases of any of the arguments, as otherwise the caller might see unexpected modifications or value references to the values passed.

The Selection Stage

The "cls" field gives a "classification" of the operator, suggesting what sort of operation it provides. This is used as a filter by the various "XS::Parse::Keyword" selection macros.

The classification should be one of the "XPI_CLS_*" constants found and described further in the main XSParseInfix.h file.

The "permit" Stage

As a shortcut for the common case, the "permit_hintkey" may point to a string to look up from the hints hash. If the given key name is not found in the hints hash then the keyword is not permitted. If the key is present then the "permit" function is invoked as normal.

If not rejected by a hint key that was not found in the hints hash, the function part of the stage is called next and should inspect whether the keyword is permitted at this time perhaps by inspecting other lexical clues, and return true only if the keyword is permitted.

Both the string and the function are optional. Either or both may be present. If neither is present then the keyword is always permitted - which is likely not what you wanted to do.

The "parse" Stage

If the optional "parse" hook function is present, it is called immediately after the parser has recognised the presence of the named operator itself but before it attempts to consume the right-hand side term. This hook function can attempt further parsing, in order to implement more complex syntax such as hyper-operators.

When invoked, it is passed a pointer to an "SV *"-typed storage variable. It is free to use this variable it desires to store a result, which will then later be made available to the "new_op" function.

The Op Generation Stage

If the infix operator is going to be used, then one of the "new_op" or the "ppaddr" fields explain how to create a new optree fragment.

If "new_op" is defined then it will be used, and is expected to return an optree fragment that consumes the LHS and RHS arguments to implement the semantics of the operator. If the optional "parse" stage had been present earlier, the "SV **" pointer passed here will point to the same storage that "parse" had previously had access to, so it can retrieve the results.

If "new_op" is not present, then the "ppaddr" will be used instead to construct a new BINOP or LISTOP of the "OP_CUSTOM" type. If an earlier "parse" stage had stored additional results into the "SV *" variable these will be lost here.

The Wrapper Function

Additionally, if the "wrapper_func_name" field is set to a string, this gives the (fully-qualified) name for a function to be generated as part of registering the operator. This newly-generated function will act as a wrapper for the operator.

For operators whose RHS is a scalar, the wrapper function is assumed to take two simple scalar arguments. The result of invoking the function on those arguments will be determined by using the operator code.

$result = $lhs OP $rhs;
$result = WRAPPERFUNC( $lhs, $rhs );

For operators whose RHS is a list, the wrapper function takes at least one argument, possibly more. The first argument is the scalar on the LHS, and the remaining arguments, however many there are, form the RHS:

$result = $lhs OP @rhs;
$result = WRAPPERFUNC( $lhs, @rhs );

For operators whose LHS and RHS is a list, the wrapper function takes two arguments which must be array references containing the lists.

$result = @lhs OP @rhs;
$result = WRAPPERFUNC( \@lhs, \@rhs );

This creates a convenience for accessing the operator from perls that do not support "PL_infix_plugin".

In the case of scalar infix operators, the wrapper function also includes a call-checker which attempts to inline the operator directly into the callsite. Thus, in simple cases where the function is called directly on exactly two scalar arguments (such as in the following), no "ENTERSUB" overhead will be incurred and the generated optree will be identical to that which would have been generated by using infix operator syntax directly:

WRAPPERFUNC( $lhs, $rhs );
WRAPPERFUNC( $lhs, CONSTANT );
WRAPPERFUNC( $args[0], $args[1] );
WRAPPERFUNC( $lhs, scalar otherfunc() );

The checker is very pessimistic and will only rewrite callsites where it determines this can be done safely. It will not rewrite any of the following forms:

WRAPPERFUNC( $onearg );            # not enough args
WRAPPERFUNC( $x, $y, $z );         # too many args
WRAPPERFUNC( @args[0,1] );         # not a scalar
WRAPPERFUNC( $lhs, otherfunc() );  # not a scalar

The wrapper function for infix operators which take lists on both sides also has a call-checker which will attempt to inline the operator directly into the callsite.

XS::Parse::Infix - Perl core documentation

NAME

XS::Parse::Infix - A module for implementing custom infix operators

DESCRIPTION

This module helps you implement custom infix operators in Perl. It provides a way to define new operators and integrate them with Perl's parser and compiler, including automatic support for deparsing (converting Perl code back into source code).

The primary mechanism involves defining a C XS function that acts as a "wrapper" for your operator. This wrapper function is called when the operator is encountered in Perl code.

Operator Syntax

The general syntax for defining an infix operator using this module is:

    new_infix_operator(
        name          => 'operator_name',
        wrapper       => \&wrapper_sub,
        <...>,
    );
name
The string name of the operator (e.g., '+', '||', '->').
wrapper
A reference to a subroutine that will be called when the operator is executed. This subroutine receives the left-hand and right-hand operands as arguments.

Additional options can be passed to control the operator's behavior, such as precedence, associativity, and parser optimizations.

Parser Optimisations

This module performs several optimisations during parsing to improve efficiency and reduce the complexity of the generated optree (an internal representation of the code).

One key optimisation involves handling scalar operators. If the operator is declared as only needing to "look" at its operands (using the "XPI_OPERAND_ONLY_LOOK" flag), the callchecker can inline the array-reference operator and omit the resulting dereference behavior. This means that code like:

@lhs OP @rhs;
WRAPPERFUNC( \@lhs, \@rhs );

will emit the same optree, without needing explicit "OP_SREFGEN" or "OP_RV2AV" operations.

Note that this optimisation has a rare corner case: if one of the referenced arrays is also the backing store for a blessed object reference, and that object's class has an "@{}" overload, the overload will not be invoked.

my @arr;
package SomeClass {
   use overload '@{}' => sub { return ["values", "go", "here"]; };
}
bless \@arr, "SomeClass";
# This will not actually invoke the overload operator
WRAPPERFUNC( \@arr, [4, 5, 6] );

This corner case, related to taking duplicate references to the same blessed object's backing store variable, is unlikely to affect real-world code. Regular objects passed by reference into the wrapper function will still have their overload methods invoked as expected.

The callchecker for list operands can also optionally discard an "OP_ANONLIST" op, which is used for anonymous array reference construction:

($u, $v, $w) OP ($x, $y, $z);
WRAPPERFUNC( [$u, $v, $w], [$x, $y, $z] );

This optimisation is only performed if the operator is marked safe to do so with the "XPI_OPERAND_ONLY_LOOK" flag.

If a function with the specified name already exists when the operator is registered, it will be left untouched, and no new wrapper will be created. This allows for multiple spellings of the same infix operator, such as a Unicode version and an ASCII transliteration. The first registration creates the wrapper; subsequent identical registrations are skipped.

When generating an optree for a wrapper function call, the "new_op" hook function will be called with a "NULL" pointer for the "SV *"-typed parse data storage, as the "parse" hook will not have an opportunity to run in this scenario.

CONSTANTS

The following constants are exported by the module and can be used to control operator behavior:

XPI_OPERATOR_PRECEDENCE_MASK
XPI_OPERATOR_ASSOCIATIVITY_MASK
XPI_PRECEDENCE_MAX
XPI_LEFT_ASSOC
XPI_RIGHT_ASSOC
XPI_NON_ASSOC
XPI_OPERAND_ONLY_LOOK
This flag indicates that the operator only needs to examine its operands and does not modify them or cause side effects that the parser needs to track precisely. This enables certain optimisations.
XPI_CAN_BE_INLINED
Indicates that the operator's wrapper function can potentially be inlined into the optree, reducing function call overhead.

PERL FUNCTIONS

new_infix_operator

Registers a new infix operator.

    new_infix_operator(
        name          => 'OPERATOR_NAME',
        wrapper       => \&SUBROUTINE,
        precedence    => NUMBER,
        associativity => ASSOCIATIVITY, # XPI_LEFT_ASSOC, XPI_RIGHT_ASSOC, XPI_NON_ASSOC
        flags         => FLAGS,        # e.g., XPI_OPERAND_ONLY_LOOK
        # ... other options
    );

The arguments are:

name
The string name of the operator.
wrapper
A reference to the Perl subroutine that acts as the wrapper for the operator. This subroutine receives the left-hand and right-hand operands as arguments.
precedence
An integer representing the operator's precedence. Higher numbers indicate higher precedence.
associativity
One of the constants "XPI_LEFT_ASSOC", "XPI_RIGHT_ASSOC", or "XPI_NON_ASSOC".
flags
A bitmask of flags from the constants defined above. "XPI_OPERAND_ONLY_LOOK" is particularly important for parser optimisations.

XS FUNCTIONS

This module primarily interacts with Perl's internals via C XS functions. Developers typically don't need to call these directly but rather use the Perl API provided by the module.

PARSE HOOKS

The module allows for custom parser hooks to be defined for operators. These hooks can influence how the operator is parsed and translated into Perl's internal representation (optree).

When the parser encounters an infix operator, it may invoke a custom hook associated with that operator. The module handles the registration and invocation of these hooks.

As mentioned earlier, the "new_op" hook function is invoked with a "NULL" pointer for the parse data storage when generating an optree for a wrapper function call, as the "parse" hook doesn't run in this case.

The callchecker for list operands can optionally discard an op of the "OP_ANONLIST" type, which is used by anonymous array-ref construction:

($u, $v, $w) OP ($x, $y, $z);
WRAPPERFUNC( [$u, $v, $w], [$x, $y, $z] );

This optimisation is only performed if the operator declared it safe to do so, via the "XPI_OPERAND_ONLY_LOOK" flag.

If a function of the given name already exists at registration time it will be left undisturbed and no new wrapper will be created. This permits the same infix operator to have multiple spellings of its name; for example to allow both a real Unicode and a fallback ASCII transliteration of the same operator. The first registration will create the wrapper function; the subsequent one will skip it because it would otherwise be identical.

The following describes a specific optimisation related to inlining array references in similar circumstances. In addition to the optimisations described above for scalar operators, this checker will also inline an array-reference operator and omit the resulting dereference behaviour. Thus, the two following lines emit the same optree, without an "OP_SREFGEN" or "OP_RV2AV":

@lhs OP @rhs;
WRAPPERFUNC( \@lhs, \@rhs );

Note that technically, this optimisation isn't strictly transparent in the odd cornercase that one of the referenced arrays is also the backing store for a blessed object reference, and that object class has a "@{}" overload.

my @arr;
package SomeClass {
   use overload '@{}' => sub { return ["values", "go", "here"]; };
}
bless \@arr, "SomeClass";
# this will not actually invoke the overload operator
WRAPPERFUNC( \@arr, [4, 5, 6] );

As this cornercase relates to taking duplicate references to the same blessed object's backing store variable, it should not matter to any real code; regular objects that are passed by reference into the wrapper function will run their overload methods as normal.

The callchecker for list operands can optionally also discard an op of the "OP_ANONLIST" type, which is used by anonymous array-ref construction:

($u, $v, $w) OP ($x, $y, $z);
WRAPPERFUNC( [$u, $v, $w], [$x, $y, $z] );

This optimisation is only performed if the operator declared it safe to do so, via the "XPI_OPERAND_ONLY_LOOK" flag.

If a function of the given name already exists at registration time it will be left undisturbed and no new wrapper will be created. This permits the same infix operator to have multiple spellings of its name; for example to allow both a real Unicode and a fallback ASCII transliteration of the same operator. The first registration will create the wrapper function; the subsequent one will skip it because it would otherwise be identical.

Note that when generating an optree for a wrapper function call, the "new_op" hook function will be invoked with a "NULL" pointer for the "SV *"-typed parse data storage, as there won't be an opporunity for the "parse" hook to run in this case.

DEPARSE

This module operates with B::Deparse in order to automatically provide deparse support for infix operators. Every infix operator that is implemented as a custom op (and thus has the "ppaddr" hook field set) will have deparse logic added. This will allow it to deparse to either the named wrapper function, or to the infix operator syntax if on a "PL_infix_plugin"-enabled perl and the appropriate lexical hint is enabled at the callsite.

In order for this to work, it is important that your custom operator is not registered as a custom op using the Perl_register_custom_op() function. This registration will be performed by "XS::Parse::Infix" itself at the time the infix operator is registered.
