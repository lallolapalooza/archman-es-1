X11::Protocol::WM(3) Documentación de Perl aportada por el usuario X11::Protocol::WM(3)

NOMBRE

X11::Protocol::WM -- funciones relacionadas con el gestor de ventanas para programas cliente

SINOPSIS

use X11::Protocol::WM;

DESCRIPCIÓN

Estas son algunas funciones relacionadas con el gestor de ventanas para uso de programas cliente, según el "Manual de Convenciones de Comunicación Inter-Cliente" y algunas de las "Pistas de Ventanas Extendidas" de Net-WM.

/usr/share/doc/xorg-docs/icccm/icccm.txt.gz

http://www.freedesktop.org/wiki/Specifications/wm-spec

Propiedades Usuales

Cada ventana de cliente de nivel superior debería usualmente

  • set_wm_class() para identificarse a sí misma a otros programas (ver "WM_CLASS" abajo).
  • set_wm_name() y set_wm_icon_name() para el nombre de ventana visible por el usuario (ver "WM_NAME, WM_ICON_NAME" abajo).
  • set_wm_client_machine_from_syshostname() y set_net_wm_pid() para el proceso en ejecución (ver "WM_CLIENT_MACHINE" y "_NET_WM_PID" abajo).

Luego, opcionalmente,

  • Si tienes un icono, usa set_wm_hints() con un bitmap o una ventana (ver "WM_HINTS" abajo).
  • Si el usuario proporcionó un tamaño o posición inicial en la línea de comandos, usa set_wm_normal_hints(). Lo mismo si el programa tiene tamaños mínimos/máximos o una relación de aspecto deseada (ver "WM_NORMAL_HINTS" abajo).
  • Si se puede construir un comando para reiniciar el programa, usa set_wm_command(), y preferiblemente manténlo actualizado con cambios como el archivo abierto actualmente, etc. (ver "WM_COMMAND" abajo).

FUNCIONES

Propiedades de Texto

Las funciones de propiedad que toman cadenas de texto como set_wm_name() aceptan cadenas de bytes o cadenas de caracteres anchos (Perl 5.8 y superior). Las cadenas de bytes se presumen Latin-1 y se establecen como tipo "STRING" en las propiedades. Las cadenas de caracteres anchos se almacenan como "STRING" si son completamente Latin-1, o se codifican a "COMPOUND_TEXT" para otros caracteres (ver Encode::X11).

En el futuro, quizás las funciones de cadena puedan aceptar algún tipo de objeto de texto compuesto para representar segmentos de varias codificaciones para convertirse en "COMPOUND_TEXT", junto con manipulaciones para dicho contenido, etc. Si el texto son bytes en una de las codificaciones ICCCM, podría ahorrar trabajo representarlo directamente como segmentos de "COMPOUND_TEXT" en lugar de pasar a caracteres anchos y volver.

"set_text_property ($X, $window, $prop, $str)"
Establece la propiedad $prop dada (átomo entero) en $window (XID entero) usando "STRING" o "COMPOUND_TEXT" como se describe arriba. Si $str es "undef" entonces $prop se elimina.

$str está limitado a "$X->maximum_request_length()". En teoría, se pueden almacenar cadenas más largas por partes, pero aquí no se intenta hacer eso. El límite máximo de solicitud es de al menos 16384 bytes y el servidor puede permitir más, posiblemente mucho más.

WM_CLASS

"X11::Protocol::WM::set_wm_class ($X, $window, $instance, $class)"
Establece la propiedad "WM_CLASS" en $window (un XID).

Esta propiedad puede ser utilizada por el gestor de ventanas para buscar configuraciones y preferencias para el programa a través del sistema de Recursos X (ver "RECURSOS" en X(7)) o similar.

Usualmente, el nombre de la instancia es el comando del programa, como "xterm", y el nombre de la clase es algo como "XTerm". Algunos programas tienen opciones de línea de comandos para establecer la clase y/o la instancia, para que el usuario pueda tener diferentes configuraciones del gestor de ventanas aplicadas a una copia en ejecución particular de un programa.

X11::Protocol::WM::set_wm_class ($X, $window,
                                 "mi_programa", "MiPrograma");

$instance y $class deben ser solo ASCII o Latin-1. Las cadenas de caracteres anchos que sean Latin-1 se convierten según sea necesario.

WM_CLIENT_MACHINE

"X11::Protocol::WM::set_wm_client_machine ($X, $window, $hostname)"
Establece la propiedad "WM_CLIENT_MACHINE" en $window a $hostname (una cadena).

$hostname debería ser el nombre de la máquina cliente tal como lo ve el servidor. Si $hostname es "undef", entonces la propiedad se elimina.

Usualmente un nombre de máquina es solo ASCII, pero se acepta cualquier cosa según las "Propiedades de Texto" anteriores.

"X11::Protocol::WM::set_wm_client_machine_from_syshostname ($X, $window)"
Establece la propiedad "WM_CLIENT_MACHINE" en $window usando el módulo Sys::Hostname.

Si "Sys::Hostname" no puede determinar un nombre de host por sus varios métodos, entonces actualmente la propiedad se elimina. ¿Sería mejor dejarla sin cambios, o devolver un indicador para decir si se estableció?

Algunos de los casos de "Sys::Hostname" podrían devolver "localhost". Eso se pasa sin cambios, asumiendo que sería cuando no hay red más allá del host local, por lo que el cliente y el servidor están en la misma máquina y el nombre "localhost" es suficiente.

WM_COMMAND

"X11::Protocol::WM::set_wm_command ($X, $window, $command, $arg...)"
Establece la propiedad "WM_COMMAND" en $window (un XID).

Debería ser un nombre de programa y cadenas de argumentos que reiniciarán el cliente. $command es el nombre del programa, seguido de cualquier cadena de argumento.

X11::Protocol::WM::set_wm_command ($X, $window,
                                   'mi_programa',
                                   '--opcion',
                                   'archivo.txt');

El comando debería iniciar el cliente en su estado actual, por lo que el comando podría incluir un nombre de archivo, opciones de línea de comandos para la configuración actual, etc.

Se permiten caracteres no ASCII según las "Propiedades de Texto" anteriores. La especificación ICCCM es para que Latin-1 funcione en un sistema POSIX Latin-1, pero qué tan bien sobreviven otras cosas en un gestor de sesiones, etc., es otro asunto.

Un cliente puede establecer esto en cualquier momento, o si participa en el protocolo del gestor de sesiones "WM_SAVE_YOURSELF", entonces debería establecerlo en respuesta a un "ClientMessage" de "WM_SAVE_YOURSELF".

;WM_SAVE_YOURSELF" y cerrar, frustrando el objetivo de permitir "WM_DELETE_WINDOW" consultar al usuario y quizás no cerrar.

La solución más sencilla sería usar solo "WM_DELETE_WINDOW", mantener "WM_COMMAND" siempre actualizado y estar preparado para guardar el estado en caso de pérdida de conexión. Esto es bastante razonable de todos modos, ya que un mensaje "WM_SAVE_YOURSELF" tiene un uso bastante limitado, dado que la pérdida de conexión u otra terminación pueden ocurrir en cualquier momento, por lo que si el estado es importante, sería prudente mantenerlo guardado.

WM_ICON_SIZE

"($min_width,$min_height, $max_width,$max_height, $width_inc,$height_inc) = X11::Protocol::WM::get_wm_icon_size($X,$root)"
Devuelve los tamaños de icono recomendados por el gestor de ventanas ("WM_ICON_SIZE") (en píxeles) como un rango y un incremento sobre el mínimo. Si no existe la propiedad "WM_ICON_SIZE", devuelve una lista vacía.

$root es la ventana raíz desde la que leer. Si se omite, se lee la predeterminada de "$X->root".

Un mapa de bits de icono o una ventana en "WM_HINTS" debería ser un tamaño dentro de este rango. Muchos gestores de ventanas no establecen un tamaño de icono preferido. 32x32 podría ser típico en una pantalla pequeña o 48x48 en una pantalla más grande.

WM_HINTS

"X11::Protocol::WM::set_wm_hints ($X, $window, key=>value, ...)"
Establece la propiedad "WM_HINTS" en $window (un XID). Por ejemplo, 
X11::Protocol::WM::set_wm_hints
    ($X, $my_window,
     input         => 1,
     initial_state => 'NormalState',
     icon_pixmap   => $my_pixmap);

Los parámetros clave/valor son los siguientes.

input             entero 0 o 1
initial_state     cadena o número enumerado
icon_pixmap       mapa de bits (entero XID), profundidad 1
icon_window       ventana (entero XID)
icon_x            coordenada entera
icon_y            / coordenada entera
icon_mask         mapa de bits (entero XID)
window_group      ventana (entero XID)
urgency           booleano

"input" es 1 si el cliente quiere que el gestor de ventanas le dé el foco de entrada del teclado a $window. Esto se hará con "$X->SetInputFocus()", o si "WM_TAKE_FOCUS" está en "WM_PROTOCOLS", entonces en su lugar se hará con un "ClientMessage".

"input" es 0 si el gestor de ventanas no debe darle el foco al cliente. Esto se debe a que $window es solo de salida, o si "WM_TAKE_FOCUS" está en "WM_PROTOCOLS", entonces porque el cliente hará un SetInputFocus() a sí mismo al presionar un botón apropiado, etc.

"initial_state" es una cadena o un número. El ICCCM permite "NormalState" o "IconicState" como estados iniciales.

"NormalState"       1
"IconicState"       3

"icon_pixmap" debe ser un mapa de bits, es decir, un mapa de píxeles (XID) con profundidad 1. El gestor de ventanas lo dibujará con colores de contraste adecuados. Los píxeles "1" son el primer plano y el "0" es el fondo. El mapa de bits "icon_mask" se aplica al icono mostrado. Se puede usar para crear un icono no rectangular.

"icon_window" es una ventana que el gestor de ventanas puede mostrar cuando $window se minimiza. Esto se puede usar para un icono multicolor, ya sea mediante un fondo o mediante dibujo del cliente (en respuesta a eventos "Expose", o actualizado periódicamente para un reloj, etc.). La "icon_window" debe ser un hijo de la raíz y debe usar el visual y el mapa de colores predeterminados de la pantalla. El gestor de ventanas podría redimensionar la ventana y/o el borde.

El gestor de ventanas podría establecer una propiedad "WM_ICON_SIZE" en la ventana raíz para indicar buenos tamaños de icono. Ver "WM_ICON_SIZE" arriba.

"window_group" es el XID de una ventana que es el líder de grupo de un conjunto de ventanas de nivel superior utilizadas por el cliente. El gestor de ventanas podría proporcionar una forma de manipular el grupo en su conjunto, por ejemplo, para minimizarlo todo. Si se minimiza, se utilizan las sugerencias de icono del líder para el icono. El líder de grupo puede ser una ventana no mapeada. Puede ser conveniente usar una ventana que nunca se mapea como líder para todas las ventanas posteriores.

"urgency" verdadero significa que la ventana es importante y el gestor de ventanas debe llamar la atención del usuario de alguna manera. El cliente puede cambiar esta sugerencia en cualquier momento para cambiar la importancia actual.

"(key => $value, ...) = X11::Protocol::WM::get_wm_hints ($X, $window)"
Devuelve la propiedad "WM_HINTS" de $window. La devolución es una lista de pares clave/valor según set_wm_hints() anterior 
input => 1,
icon_pixmap => 1234,
...

Solo los campos con sus bits de bandera activados en las sugerencias se incluyen en la devolución. Si no existe ninguna "WM_HINTS" o si su campo de banderas es cero, la devolución es una lista vacía.

La devolución se puede colocar en un hash para obtener campos por nombre,

my %hints = X11::Protocol::WM::get_wm_hints ($X, $window);
if (exists $hints{'icon_pixmap'}) {
  print "icon_pixmap es ", $hints{'icon_pixmap'}, "\n";
}

"initial_state" es una cadena como "NormalState". Los mapas de bits y las ventanas son la cadena "None" si están establecidos pero son cero (lo cual es probablemente inusual). Si "$X->{'do_interp'}" está deshabilitado, entonces todos son números.

X11R2 Xlib tenía un error en su XSetWMHints() que cortaba el valor de "window_group" de las sugerencias almacenadas. El campo "window_group" se omite de la devolución si los datos leídos carecen de dicho campo.

"(key => $value, ...) = X11::Protocol::WM::change_wm_hints ($X, $window, key=>value, ...)"
Cambia algunos campos de la propiedad "WM_HINTS" en $window. Los campos clave/valor dados se cambian. Otros campos se dejan solos. Por ejemplo, 
X11::Protocol::WM::set_wm_hints ($X, $window,
                                 urgency => 1);

Un valor "undef" significa eliminar un campo,

X11::Protocol::WM::set_wm_hints ($X, $window,
                                 icon_pixmap => undef,
                                 icon_mask   => undef);

El cambio requiere un viaje de ida y vuelta al servidor para obtener los valores actuales de $window. Una aplicación podría preferir recordar sus sugerencias deseadas y enviar un completo set_wm_hints() cada vez.

"$bytes = X11::Protocol::WM::pack_wm_hints ($X, key=>value...)"
Empaqueta un conjunto de valores en una cadena de bytes con formato de "WM_HINTS". Los argumentos clave/valor son según set_wm_hints() anterior y el resultado son los bytes crudos almacenados en una propiedad "WM_HINTS".

El argumento $X no se utiliza actualmente, pero está presente en caso de que "initial_state" u otros valores puedan usar una búsqueda de "$X->num()" en el futuro.

"(key => $value, ...) = X11::Protocol::WM::unpack_wm_hints ($X, $bytes)"
Desempaqueta una cadena de bytes como una estructura "WM_HINTS". El resultado son pares clave/valor según get_wm_hints() anterior. El parámetro $X se utiliza para "do_interp". No hay comunicación con el servidor.

WM_NAME, WM_ICON_NAME

"X11::Protocol::WM::set_wm_name ($X, $window, $name)"
Establece la propiedad "WM_NAME" en $window (un XID entero) a $name (una cadena).

El gestor de ventanas podría mostrar esto como un título encima de la ventana, o en un menú de ventanas, etc. Puede ser una cadena de caracteres anchos de Perl 5.8 según "Text Properties" anterior. Un buen gestor de ventanas debería admitir títulos no ASCII o no Latin-1, pero qué tan bien se muestren puede depender de las fuentes, etc.

"X11::Protocol::WM::set_wm_icon_name ($X, $window, $name)"
Establece la propiedad "WM_ICON_NAME" en $window (un XID entero) a $name (una cadena).

El gestor de ventanas podría mostrar esto cuando $window se minimiza. Si $window no tiene un icono (en "WM_HINTS" o del propio gestor de ventanas), entonces este texto podría ser todo lo que se muestre. En cualquier caso, debería ser algo corto. Puede ser una cadena de caracteres anchos de Perl 5.8 según "Text Properties" anterior.

WM_NORMAL_HINTS

"X11::Protocol::WM::set_wm_normal_hints ($X, $window, key=>value,...)"
Establece la propiedad "WM_NORMAL_HINTS" en $window (un XID entero). Esta es una estructura "WM_SIZE_HINTS" que le dice al gestor de ventanas qué tamaños desea el cliente. Por ejemplo, 
set_wm_normal_hints ($X, $window,
                     min_width => 200,
                     min_height => 100);

Generalmente el gestor de ventanas restringe el redimensionamiento del usuario a los límites de las sugerencias. La mayoría de los gestores de ventanas utilizan estas sugerencias, pero por supuesto, solo son sugerencias y un buen programa debe estar preparado para otros tamaños, incluso si no se verá bien o no podrá hacer mucho útil cuando sea demasiado grande o demasiado pequeño, etc.

Los parámetros clave/valor son

user_position      booleano, la posición x,y de la ventana es especificada por el usuario
user_size          booleano, el ancho,alto de la ventana es especificado por el usuario
program_position   booleano, la posición x,y de la ventana es especificada por el programa
program_size       booleano, el ancho,alto de la ventana es especificado por el programa
min_width          \ enteros, tamaño mínimo en píxeles
min_height         /
max_width          \ enteros, tamaño máximo en píxeles
max_height         /
base_width         \ enteros, base del tamaño en píxeles
base_height        /
width_inc          \ enteros, incremento del tamaño en píxeles
height_inc         /
min_aspect         \ fracción 2/3 o decimal 2 o 1.5
min_aspect_num      | o entero num/den hasta 0x7FFFFFFF
min_aspect_den      |
max_aspect          |
max_aspect_num      |
max_aspect_den     /
win_gravity        Enum WinGravity "NorthEast" etc

"user_position" y "user_size" son indicadores que significan que la x,y o ancho,alto de la ventana (en el núcleo habitual de "$X->SetWindowAttributes()") fueron proporcionados por el usuario, por ejemplo, a partir de una opción de línea de comandos "-geometry". El gestor de ventanas generalmente obedecerá estos valores y omitirá cualquier auto-colocación o colocación interactiva que de otra manera podría hacer.

"program_position" y "program_size" son indicadores que significan que la x,y o ancho,alto de la ventana fueron calculados por el programa. El gestor de ventanas podría anularlos con su propia política de posicionamiento o dimensionamiento. Generalmente no hay necesidad de establecer estos campos a menos que el programa tenga una idea definida de dónde y qué tan grande debería ser. Para un tamaño, es suficiente establecer el ancho,alto de la ventana principal y dejar que el gestor de ventanas (si hay uno ejecutándose) actúe a partir de ahí.

Los elementos que se muestran agrupados arriba deben proporcionarse juntos, por lo que, por ejemplo, si se proporciona un "min_width", entonces también se debe proporcionar un "min_height".

"base_width", "base_height" y "width_inc", "height_inc" solicitan que la ventana tenga un cierto tamaño base en píxeles y luego un múltiplo de "inc" píxeles por encima de eso. Esto puede ser utilizado por cosas como "xterm" que desean un tamaño fijo para el borde o la barra de desplazamiento y luego un múltiplo del tamaño de carácter por encima de eso. Si no se proporcionan "base_width", "base_height", entonces "min_width", "min_height" es el tamaño base.

"base_width", "base_height" pueden ser menores que "min_width", "min_height". Esto significa que el tamaño aún debe ser un múltiplo de base+inc, pero el primer múltiplo de este tipo que sea al menos el tamaño mínimo. El gestor de ventanas generalmente presenta el múltiplo "inc" al usuario, de modo que, por ejemplo, en un xterm, el usuario ve un recuento de caracteres. Un tamaño mínimo puede entonces exigir, por ejemplo, un tamaño mínimo de carácter de 1x1 o 2x2.

"min_aspect", "max_aspect" solicitan que la ventana tenga una cierta relación de ancho/alto mínima o máxima. Por ejemplo, un aspecto 2/1 significa que debe ser el doble de ancho que de alto. Esto se aplica al tamaño por encima de "base_width", "base_height", o si la base no se proporciona, a todo el tamaño de la ventana.

"min_aspect_num", "min_aspect_den" y "max_aspect_num", "max_aspect_den" establecen directamente los valores del numerador y denominador (INT32, por lo que máximo 0x7FFF_FFFF). O "min_aspect" y "max_aspect" aceptan un solo valor en varias formas que se convierten en valores num/den.

2         entero
1.125     decimal, significando 1125/1000
2/3       fracción
1.5/4.5   fracción con decimales

Los valores mayores que 0x7FFFFFFF en estas formas se reducen proporcionalmente según sea necesario. Un valor de punto flotante de Perl generalmente tendrá más bits de precisión que 0x7FFFFFFF y se trunca a algo que quepa.

"win_gravity" es cómo al cliente le gustaría ser desplazado para hacer espacio para cualquier marco circundante que el gestor de ventanas pueda agregar. Por ejemplo, si el programa calculó el tamaño y la posición de la ventana para asegurar que la esquina noreste esté en una posición deseada, entonces proporcione "win_gravity => "NorthEast"" para que el gestor de ventanas mantenga la esquina noreste igual cuando aplique su marco.

"win_gravity => "Static"" significa que el marco se coloca alrededor de la ventana y la ventana no se mueve en absoluto. Por supuesto, eso podría significar que parte del marco termina fuera de la pantalla.

"$bytes = X11::Protocol::WM::pack_size_hints ($X, key=>value,...)"
Devuelve una cadena de bytes que es una estructura "WM_SIZE_HINTS" creada a partir de los parámetros clave/valor dados. "WM_SIZE_HINTS" es el tipo de estructura para "WM_NORMAL_HINTS" descrito anteriormente y los parámetros clave/valor son como se describen arriba.

El parámetro $X se utiliza para interpretar los valores enum de "win_gravity". No hay comunicación con el servidor.

"($num,$den) = X11::Protocol::WM::aspect_to_num_den ($aspect)"
Devuelve un par de enteros INT32 de 0 a 0x7FFF_FFFF para la relación de aspecto dada $aspect. Esta es la conversión que se aplica a "min_aspect" y "max_aspect" arriba. $aspect puede ser cualquiera de los enteros, decimales o fracciones descritos.

WM_PROTOCOLS

"X11::Protocol::WM::set_wm_protocols ($X, $window, $protocol,...)"
Establece la propiedad "WM_PROTOCOLS" en $window (un XID). Cada argumento es un nombre de protocolo de cadena o un ID de átomo entero. 
X11::Protocol::WM::set_wm_protocols
  ($X, $window, 'WM_DELETE_WINDOW', '_NET_WM_PING')

Por ejemplo, "WM_DELETE_WINDOW" significa que cuando el usuario hace clic en el botón de cierre, el gestor de ventanas envía un evento "ClientMessage" en lugar de hacer un KillClient(). El evento "ClientMessage" permite a un programa limpiar o preguntar al usuario sobre guardar un documento antes de salir, etc.

WM_STATE

El gestor de ventanas mantiene un estado para cada ventana cliente que gestiona,

WithdrawnState
NormalState
IconicState

"WithdrawnState" significa que la ventana no está mapeada y el gestor de ventanas no la está gestionando. Una ventana recién creada ("$X->CreateWindow()") está inicialmente en "WithdrawnState" y en el primer "$X->MapWindow()" pasa a "NormalState" (o a "IconicState" si ese es el estado inicial solicitado en "WM_HINTS").

iconify() y withdraw() a continuación pueden cambiar el estado a icónico o retirado. Una ventana puede restaurarse de icónica a normal mediante un MapWindow().

"($state, $icon_window) = X11::Protocol::WM::get_wm_state ($X, $window)"
Devuelve la propiedad "WM_STATE" de $window. Esto es establecido por el gestor de ventanas en las ventanas de aplicación de nivel superior. Si no existe tal propiedad, la devolución es una lista vacía.

$state devuelto es una cadena enum, o un valor entero si "$X->{'do_interp'}" está deshabilitado o el valor no es reconocido.

"WithdrawnState"    0      no mostrado
"NormalState"       1      ventana mostrada
"IconicState"       3      iconificado de alguna manera
"ZoomState"         2      \ ya no está en ICCCM
"InactiveState"     4      /   (zoom significaba maximizado)

$icon_window devuelto es la ventana (XID entero) utilizada por el gestor de ventanas para mostrar un icono de $window. Si no existe tal ventana, entonces $icon_window es "None" (o 0 si "$X->{'do_interp'}" está deshabilitado).

$icon_window podría ser la ventana del icono de "WM_HINTS" del cliente o podría ser una ventana creada por el gestor de ventanas. El cliente puede dibujar en ella para animaciones, etc., quizás seleccionando eventos "Expose" en ella para saber cuándo redibujar.

"WM_STATE" es establecido por el gestor de ventanas cuando una ventana de nivel superior se mapea por primera vez (o quizás antes), y luego se mantiene actualizado. Generalmente, la ausencia de la propiedad "WM_STATE" o una "WM_STATE" establecida en WithdrawnState significa que el gestor de ventanas no está gestionando la ventana, o aún no lo está haciendo. Un cliente puede seleccionar la máscara de eventos "PropertyChange" de la manera habitual para escuchar los cambios de "WM_STATE".

"($state, $icon_window) = X11::Protocol::WM::unpack_wm_state ($X, $bytes)"
Desempaqueta los bytes de una propiedad "WM_STATE" a un $state

WM_FUNCTIONS

The window manager communicates the state of a window via the "WM_STATE" property. The window manager also provides functions for controlling the state of a window.

"X11::Protocol::WM::get_wm_state ($X, $window)"
Return the value of the "WM_STATE" property on $window (an XID). This will be "undef" if the property is not set. Otherwise it will be a list of two items:

$X is used for "$X->{'do_interp'}" but there's no communication with the server.

"X11::Protocol::WM::iconify ($X, $window)"
"X11::Protocol::WM::iconify ($X, $window, $root)"
Change $window to "IconicState" by sending a "ClientMessage" to the window manager.

If the window manager does not have any iconification then it might do nothing (eg. some tiling window managers). If there's no window manager running then iconification is not possible and this message will do nothing.

$root should be the root window of $window. If not given or "undef" then it's obtained by a QueryTree() here. Any client can iconify any top level window.

If $window has other windows which are "WM_TRANSIENT_FOR" for it then generally the window manager will iconify or hide those windows too (see "WM_TRANSIENT_FOR" below).

"X11::Protocol::WM::withdraw ($X, $window)"
"X11::Protocol::WM::withdraw ($X, $window, $root)"
Change $window to "WithdrawnState" by an "$X->UnmapWindow()" and a synthetic "UnmapNotify" message to the window manager.

If there's no window manager running then the UnmapWindow() unmaps and the "UnmapNotify" message does nothing.

$root should be the root window of $window. If not given or "undef" then it's obtained by a QueryTree() here.

If other windows are "WM_TRANSIENT_FOR" this $window (eg. open dialog windows) then generally the client should withdraw them too. The window manager might make such other windows inaccessible anyway.

The ICCCM specifies an "UnmapNotify" message so the window manager is notified of the desired state change even if $window is already unmapped, such as in "IconicState" or perhaps during some window manager reparenting, etc.

$window can be changed back to NormalState or IconicState later with "$X->MapWindow()" the same as for a newly created window. (And "WM_HINTS" "initial_state" can give a desired initial iconic/normal state). But before doing so be sure the window manager has recognised the withdraw(). This will be when the window manager changes the "WM_STATE" property to "WithdrawnState", or deletes that property.

Any client can withdraw any toplevel window, but it's unusual for a client to withdraw windows which are not its own.

WM_TRANSIENT_FOR

"X11::Protocol::WM::set_wm_transient_for ($X, $window, $transient_for)"
Set the "WM_TRANSIENT_FOR" property on $window (an XID).

$transient_for is another window XID, or "undef" if $window is not transient for anything so "WM_TRANSIENT_FOR" should be deleted.

"Transient for" means $window is some sort of dialog or menu related to the given $transient_for window. The window manager will generally iconify $window together with its $transient_for, etc. See set_motif_wm_hints() below for "modal" transients.

_MOTIF_WM_HINTS

"X11::Protocol::WM::set_motif_wm_hints ($X, $window, key=>value...)"
Set the "MOTIF_WM_HINTS" property on $window (an XID).

These hints control window decorations and "modal" state. It originated in the Motif "mwm" window manager but is recognised by most other window managers. It should be set on a toplevel window before mapping. Changes made later might not affect what the window manager does.

X11::Protocol::WM::set_motif_wm_hints
  ($X, $dialog_window,
   input_mode => "full_application_modal");
$X->MapWindow ($dialog_window);

Ordinary windows generally don't need to restrict their decorations etc, but something special like a clock or gadget might benefit.

X11::Protocol::WM::set_motif_wm_hints
  ($X, $my_gadget_window,
   functions   => 4+32,   # move+close
   decorations => 1+4+8); # border+title+menu

The key/value arguments are

functions   => integer bits
decorations => integer bits
input_mode  => enum string or integer
status      => integer bits

"functions" is what actions the window manager should offer to the user in a drop-down menu or similar. It's an integer bitwise OR of the following values. If not given then the default is normally all functions.

bit    actions offered
---    ---------------
 1     all functions
 2     resize window
 4     move window
 8     minimize, to iconify
16     maximize, to full-screen (with a frame still)
32     close window

"decorations" is what visual decorations the window manager should show around the window. It's an integer bitwise OR of the following values. If not given then the default is normally all decorations.

bit       decorations displayed
---       ---------------------
 1        all decorations
 2        border around the window
 4        resizeh, handles to resize by dragging
 8        title bar, showing WM_NAME
16        menu, drop-down menu of the "functions" above
32        minimize button, to iconify
64        maximize button, to full-screen

"input_mode" allows a window to be "modal", meaning the user should interact only with $window. The window manager will generally keep it on top, not move the focus to other windows, etc. The value is one of the following strings or corresponding integer,

  string                   integer
"modeless"                    0    not modal (the default)
"primary_application_modal"   1    modal to its "transient for"
"system_modal"                2    modal to the whole display
"full_application_modal"      3    modal to the current client

"primary_application_modal" means $window is modal for the "WM_TRANSIENT_FOR" set on $window (see "WM_TRANSIENT_FOR" above), but other windows on the display can be used normally. "full_application_modal" means modal for all windows of the same client, but other clients can be used normally.

Modal behaviour is important for good user interaction and therefore ought to be implemented by a window manager, but a good program should be prepared to do something with input on other windows.

"status" field is a bitwise OR of the following bits (only one currently).

bit
 1    tearoff menu window

Tearoff menu flag is intended for tearoff menus, as the name suggests.

X11::Protocol::WM::set_motif_wm_hints
  ($X, $my_tearoff_window, status => 1);

Motif "mwm" will expand the window to make it wide enough for the "WM_NAME" in the frame title bar. Otherwise a title is generally truncated to as much as fits the window's current width. Expanding can be good for tearoffs where the title bar is some originating item name etc which the user should see. But don't be surprised if this flag is ignored by other window managers.

Perhaps in the future the individual bits above will have some symbolic names. Either constants or string values interpreted. What would a possible get_hints() return, and what might be convenient to add/subtract bits?

See /usr/include/Xm/MwmUtil.h on the hints bits, and see "mwm" sources WmWinInfo.c ProcessWmWindowTitle() for the "status" tearoff window flag.

_NET_FRAME_EXTENTS

"my ($left,$right, $top,$bottom) = X11::Protocol::WM::get_net_frame_extents ($X, $window)"
Get the "_NET_FRAME_EXTENTS" property from $window.

This is set on top-level windows by the window manager to report how many pixels of frame or decoration it has added around $window.

If there's no such property set then the return is an empty list. So for example

my ($left,$right,$top,$bottom)
      = get_net_frame_extents ($X, $window)
  or print "no frame extents";
my ($left,$right,$top,$bottom)
  = get_net_frame_extents ($X, $window);
if (! defined $left) {
  print "no frame extents";
}

A client might look at the frame size if moving a window programmatically so as not to put the title bar etc off-screen. Oldish window managers might not provide this information though.

_NET_WM_PID

"X11::Protocol::WM::set_ne
t_wm_pid ($X, $window)"
"X11::Protocol::WM::set_net_wm_pid ($X, $window, $pid)"
"X11::Protocol::WM::set_net_wm_pid ($X, $window, undef)"
Establece la propiedad "_NET_WM_PID" en $window al ID de proceso $pid dado, o al ID de proceso actual $$ si se omite. (Ver perlvar para $$.) Si $pid es "undef", entonces la propiedad se elimina.

Un gestor de ventanas o similar podría usar el PID para matar forzosamente a un cliente que no responde. Solo es útil si "WM_CLIENT_MACHINE" (arriba) también está configurado, para saber dónde se está ejecutando el cliente.

_NET_WM_STATE

Un gestor de ventanas compatible con EWMH mantiene un conjunto de banderas de estado para cada ventana cliente. Un estado es un átomo como "_NET_WM_STATE_FULLSCREEN" y cada estado puede estar presente o ausente. Los estados admitidos se enumeran en la propiedad "_NET_SUPPORTED" en la raíz (junto con otras características). Por ejemplo,

my @net_supported = X11::Protocol::Other::get_property_atoms
                     ($X, $X->root, $X->atom('_NET_SUPPORTED'));
if (grep {$_ == $X->atom('_NET_WM_STATE_FULLSCREEN')}
         @net_supported) {
  print "Tengo _NET_WM_STATE_FULLSCREEN\n";
}

Cualquier cliente puede pedir al gestor de ventanas que cambie los estados de cualquier ventana. Un cliente podría establecer estados iniciales en una nueva ventana con set_net_wm_state() abajo. Los estados posibles incluyen

_NET_WM_STATE_MODAL
La ventana es modal a su padre "WM_TRANSIENT_FOR", o si "WM_TRANSIENT_FOR" no está establecido, entonces es modal a su grupo de ventanas.

Ver "_MOTIF_WM_HINTS" para establecer modal con las sugerencias de estilo de Motif.

_NET_WM_STATE_STICKY
La ventana se mantiene en una posición fija en la pantalla cuando el escritorio se desplaza.
_NET_WM_STATE_MAXIMIZED_VERT
_NET_WM_STATE_MAXIMIZED_HORZ
La ventana tiene un tamaño máximo vertical u horizontalmente, o ambos. La ventana todavía tiene su decoración circundante y el tamaño debe obedecer los incrementos de tamaño especificados en "WM_NORMAL_HINTS".
_NET_WM_STATE_FULLSCREEN
La ventana ocupa toda la pantalla sin decoración alrededor, siendo así la pantalla completa.

El gestor de ventanas recuerda el tamaño "normal" de la ventana para que cuando se eliminen los estados maximizado o pantalla completa se restaure el tamaño anterior.

_NET_WM_STATE_SHADED
La ventana está "sombreada", lo que generalmente significa que se muestra su barra de título pero no la ventana del cliente. Esta es una alternativa a la minimización de una ventana.
_NET_WM_STATE_SKIP_TASKBAR
_NET_WM_STATE_SKIP_PAGER
No mostrar la ventana en una barra de tareas o en un paginador, respectivamente.
_NET_WM_STATE_HIDDEN (solo lectura)
Este estado es establecido por el gestor de ventanas cuando la ventana está minimizada o similar y por lo tanto no aparece en pantalla. Los clientes no pueden cambiar esto.
_NET_WM_STATE_ABOVE
_NET_WM_STATE_BELOW
La ventana se mantiene por encima o por debajo de otras ventanas de cliente. El orden de apilamiento mantenido es aproximadamente 
 arriba
+-----------------------------+
|  _NET_WM_WINDOW_TYPE_DOCK   |   Paneles "DOCK" (etc) arriba,
+-----------------------------+   excepto quizás ventanas
|     _NET_WM_STATE_ABOVE     |   FULLSCREEN encima de esos
+-----------------------------+   paneles cuando tienen foco
|            normal           |
+-----------------------------+
|     _NET_WM_STATE_BELOW     |
+-----------------------------+
| _NET_WM_WINDOW_TYPE_DESKTOP |
+-----------------------------+
 abajo
_NET_WM_STATE_DEMANDS_ATTENTION
La ventana debe ser llamada a la atención del usuario de alguna manera. Un cliente establece esto y el gestor de ventanas lo borra después de que la ventana haya recibido atención del usuario (lo que podría significar foco de teclado o similar).

Las siguientes funciones obtienen o establecen los estados.

"change_net_wm_state($X, $window, $action, $state, key=>value,...)"
Cambia una de las banderas de estado "_NET_WM_STATE" en $window enviando un mensaje al gestor de ventanas. Por ejemplo, 
change_net_wm_state ($X, $window, "toggle", "FULLSCREEN");

$window debe ser una ventana gestionada, es decir, debe haber sido mapeada inicialmente y no ser una override-redirect. Si no es así o si no hay gestor de ventanas o este no tiene EWMH, este mensaje de cambio no tendrá ningún efecto.

$action es una cadena o entero de cómo cambiar el estado,

"remove"       0
"add"          1
"toggle"       2

$state es una cadena como "FULLSCREEN" o un entero de átomo como "$X->atom("_NET_WM_STATE_FULLSCREEN")".

Los parámetros opcionales adicionales clave/valor son

state2   => cadena o átomo
source   => "none", "normal", "user", 0,1,2
root     => XID entero, o undef

Un mensaje de cambio puede actuar sobre uno o dos estados. Para dos estados, el segundo es "state2". Por ejemplo, para maximizar vertical y horizontalmente en una sola operación,

change_net_wm_state ($X, $window, "add", "MAXIMIZED_VERT",
                     state2 => "MAXIMIZED_HORZ");

"source" es de dónde provino la solicitud de cambio. El valor predeterminado es "normal", que significa una aplicación normal. "user" es para un programa de control de interfaz de usuario como un paginador. ("none"=0 es lo que daban los clientes antes de EWMH 1.2).

"root" es la ventana raíz (XID entero) de $window. Si es "undef" o no se proporciona, se busca mediante "$X->QueryTree()". Si ya conoces la raíz, proporcionarla evita esa consulta de ida y vuelta.

"@strings = get_net_wm_state ($X, $window)"
"@atoms = get_net_wm_state_atoms ($X, $window)"
Obtiene la propiedad "_NET_WM_STATE" de $window. get_net_wm_state() devuelve una lista de cadenas como "FULLSCREEN". get_net_wm_state_atoms() devuelve una lista de enteros de átomos como "$X->atom('_NET_WM_STATE_FULLSCREEN')". En ambos casos, si no existe dicha propiedad o si está vacía, devuelve una lista vacía.
"set_net_wm_state ($X, $window, $state,...)"
Establece la propiedad "_NET_WM_STATE" en $window. Cada $state puede ser 
cadena como "FULLSCREEN"
cadena como "_NET_WM_STATE_FULLSCREEN"
átomo entero de un nombre como _NET_WM_STATE_FULLSCREEN

Un cliente puede establecer "_NET_WM_STATE" en una nueva ventana para informar al gestor de ventanas de los estados iniciales deseados. Esto es solo un "debería" en la especificación EWMH, por lo que podría no ser obedecido.

# estado inicial deseado
set_net_wm_state ($X, $window,
                  "MAXIMIZED_HORZ", "MAXIMIZED_VERT");

Una vez que la ventana es gestionada por el gestor de ventanas (una vez mapeada), los clientes no deben establecer "_NET_WM_STATE", sino pedir al gestor de ventanas con el mensaje change_net_wm_state() anterior.

_NET_WM_USER_TIME

"set_net_wm_user_time ($X, $window, $time)"
Establece la propiedad "_NET_WM_USER_TIME" en $window.

$time debe ser un valor de tiempo del servidor (un entero) del último evento de pulsación de tecla, etc., del usuario en $window. O cuando se crea $window, el tiempo del evento que provocó su apertura.

En una ventana recién creada, un valor especial de $time 0 significa que la ventana no debe recibir el foco cuando se mapee -- asumiendo que el gestor de ventanas reconoce "_NET_WM_USER_TIME", por supuesto.

Si el cliente tiene la ventana activa, debe actualizar "_NET_WM_USER_TIME" para cada entrada del usuario. Generalmente, los eventos KeyPress y ButtonPress son entradas del usuario, pero normalmente KeyRelease y ButtonRelease no lo son, ya que son los eventos Press los que el usuario está haciendo activamente.

El gestor de ventanas podría usar "_NET_WM_USER_TIME" para controlar el foco y/o el orden de apilamiento para que, por ejemplo, una ventana emergente lenta no robe el foco si has ido a otra ventana para hacer otro trabajo mientras tanto.

_NET_WM_WINDOW_TYPE

"X11::Protocol::WM::set_net_wm_window_type ($X, $window, $window_type)"
Establece la propiedad "_NET_WM_WINDOW_TYPE" en $window (un XID). $window_type puede ser 
cadena como "NORMAL"
átomo entero de un nombre como _NET_WM_WINDOW_TYPE_NORMAL

Los tipos de ventana de EWMH son los siguientes.

"NORMAL"
"DIALOG"
"DESKTOP"
"DOCK"
"TOOLBAR"
"MENU"
"UTILITY"
"SPLASH"

Frame a Cliente

"$window = X11::Protocol::WM::frame_window_to_client ($X, $frame)"
Devuelve la ventana del cliente (un XID) contenida dentro de la ventana del gestor de ventanas $frame (un XID). $frame es generalmente un hijo inmediato de la ventana raíz.

Si no se encuentra ninguna ventana de cliente en $frame, devuelve "undef".

Este podría ocurrir si $frame es una ventana de icono o similar creada por el propio gestor de ventanas, o un cliente de anulación de redirección sin marco, o si no hay ningún gestor de ventanas en ejecución. En estos dos últimos casos, $frame sería ya el cliente.

La estrategia es mirar $frame y descender por el árbol de ventanas buscando una propiedad "WM_STATE" que el gestor de ventanas coloca en el nivel superior de un cliente cuando está mapeado. La profundidad de búsqueda y el número total de ventanas son limitados en caso de que el gestor de ventanas realice su decoración de alguna manera ridícula o el cliente use ventanas excesivas (que se recorrerían si no hay gestor de ventanas).

+-rootwin--------------------------+
|                                  |
|                                  |
|    +-frame-win--------+          |
|    | +-client-win---+ |          |
|    | | WM_STATE ... | |          |
|    | |              | |          |
|    | +--------------+ |          |
|    +------------------+          |
|                                  |
+----------------------------------+

Se tiene cuidado de no producir errores si algunas ventanas se destruyen durante la búsqueda. Cuando una ventana pertenece a otros clientes, podría destruirse en cualquier momento. Si $frame en sí mismo no existe, entonces el retorno es "undef".

Esta función es similar a lo que hacen "xwininfo" y programas similares para ir desde un hijo de la ventana raíz de nivel superior hasta la ventana del cliente, según dmsimple.c Select_Window() o Xlib XmuClientWindow(). (Ver también X11::Protocol::ChooseWindow.)

Raíz Virtual

Algunos gestores de ventanas utilizan una ventana de "raíz virtual" que cubre toda la pantalla. Las ventanas de aplicaciones o las ventanas de marco son entonces hijas de esa raíz virtual. Esto puede ayudar al gestor de ventanas a implementar un escritorio grande o múltiples escritorios, aunque tiende a fallar de maneras sutiles con varios programas orientados a la raíz, incluyendo, por ejemplo, xsetroot(1) o la selección al hacer clic en xwininfo(1) y xprop(1).

"$window = X11::Protocol::WM::root_to_virtual_root ($X, $root)"
Si el gestor de ventanas está utilizando una raíz virtual, devuelve ese XID de ventana. Si no, devuelve "undef".

La implementación actual busca una ventana con una propiedad "__SWM_VROOT", según los gestores de ventanas "swm", "tvtwm" y "amiwm", y como utiliza el programa "xscreensaver" y quizás algunas versiones de KDE.

Todavía no hay nada para EWMH "_NET_VIRTUAL_ROOTS". ¿Los gestores de ventanas lo utilizan? ¿Es "_NET_CURRENT_DESKTOP" un índice en esa lista de raíces virtuales?

(Ver X11::Protocol::XSetRoot para cambiar el fondo de una raíz o raíz virtual.)

EXPORTACIONES

Nada se exporta por defecto, pero las funciones pueden solicitarse en el estilo habitual de "Exporter",

use X11::Protocol::WM 'set_wm_hints';
set_wm_hints ($X, $window, input => 1, ...);

O simplemente llame con el nombre completo del paquete

use X11::Protocol::WM;
X11::Protocol::WM::set_wm_hints ($X, $window, input => 1, ...);

No hay etiqueta ":all" ya que este módulo está pensado como un conjunto de funciones y importar cosas aún desconocidas sería pedir conflictos de nombres.

ERRORES

No se presta mucha atención al texto en un sistema EBCDIC. Las cadenas de caracteres anchos probablemente funcionen, pero las cadenas de bytes pueden pasar directamente mientras deberían ser recodificadas a Latin-1. Pero lo mismo probablemente se aplica a partes del núcleo "X11::Protocol" como "$X->atom_name()" donde querría convertir Latin-1 del servidor a EBCDIC nativo.
