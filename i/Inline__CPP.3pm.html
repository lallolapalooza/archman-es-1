Eligiendo un Compilador de

C++

Inline::CPP solo analiza las firmas de subrutinas y clases dentro de tu código C++ y crea enlaces a ellas. Al igual que con Inline::C, necesitarás un compilador adecuado la primera vez que ejecutes el

script.

Si eres parte de la afortunada mayoría, aceptarás los valores predeterminados mientras instalas Inline::CPP; el compilador de C++ correcto y las bibliotecas estándar serán configurados para ti. Si eres parte de la desafortunada (y disminuyente) minoría, sigue

leyendo.

Aquí está la regla: usa un compilador de C++ que sea compatible con el compilador que construyó "perl". Por ejemplo, si "perl" fue construido con "gcc", usa "g++". Si estás en una máquina Sun o IRIX y el compilador de C del sistema "cc" construyó "perl", entonces usa el compilador de C++ del sistema, "CC"

.

Algunos compiladores en realidad compilan tanto C como C++ con el mismo compilador. El "cl.exe" de Microsoft es uno de esos compiladores -- le pasas la bandera <-TP> para convencerlo de que quieres modo C++. Se espera que esto se deduzca por defecto en el momento de la

instalación.

Si estás usando el compilador de C++ de GNU, asegúrate de tener instalado el

front-end g++ (algunas distribuciones de Linux no lo instalan por defecto,
pero lo proporcionan a través de sus utilidades de gestión de paquetes).

Usando Inline::

CPP

Inline::CPP es muy similar a Inline::C, y en la mayoría de los casos se puede usar en lugar de Inline::C sin cambiar una sola línea de código Perl o C. Si no lo has hecho ya, deberías dejar de leer ahora mismo y leer la documentación de Inline::C, incluyendo el Inline::

C-Cookbook.

Este módulo usa una gramática para analizar tu código C++ y crea enlaces a funciones o clases que son reconocidas. Si una función es reconocida, estará disponible desde el espacio de Perl. Si la firma de la función no es reconocida, no estará disponible desde Perl, pero estará disponible desde otras funciones o clases dentro del código

C++.

El siguiente ejemplo muestra cómo los fragmentos de C++ se mapean a

Perl:

Ejemplo

1: 
use Inline CPP => <<'END';
using namespace std;
int doodle() { }
class Foo {
 public:
   Foo();
   ~Foo();
   int get_data() { return data; }
   void set_data(int a) { data = a; }
 private:
   int data;
};
Foo::Foo() { cout << "creating a Foo()" << endl; }
Foo::~Foo() { cout << "deleting a Foo()" << endl; }
END

Después de ejecutar el código anterior, tu tiempo de ejecución de Perl se vería similar a como si se hubiera ejecutado el siguiente

código: 
sub main::doodle { }
package main::Foo;
sub new { print "creating a Foo()\n"; bless {}, shift }
sub DESTROY { print "deleting a Foo()\n" }
sub get_data { my $o=shift; $o->{data} }
sub set_data { my $o=shift; $o->{data} = shift
}

La diferencia, por supuesto, es que en el último, Perl hace el trabajo. En el ejemplo de Inline::CPP, todas las llamadas a funciones se envían a tu código C++. Eso significa que cosas como esta no

funcionarán: 
my $obj = new Foo;
$obj->{extrafield} =
10;

No funciona porque $obj no es un hash bendito (blessed). Es

una referencia bendi
ta a un objeto de C++.

Fase de Compilación de

C++

La primera vez que ejecutes un programa que usa Inline::CPP, el código C++ será compilado en una "_Inline/" o ".Inline/" dentro del directorio de trabajo. La primera ejecución incurrirá en una penalización de tiempo de inicio asociada con la compilación del código C++. Sin embarg

o, el código compilado se almacena en caché, y asumiendo que no se modifica, las ejecu
ciones posteriores omitirán la compilación de C++, y el tiempo de inicio será rápido.

C++

El código C++ inline puede residir casi en cualquier lugar que quieras dentro de tu código Perl. Gran parte de esto está documentado más a fondo en el POD de Inline, pero aquí hay algunos conceptos

Basando Distribuciones (CPAN) en Inline::

CPP

Llevando el concepto de reutilización de código un paso más allá, es totalmente posible empaquetar una distribución con una dependencia de Inline::CPP. Cuando el usuario instala la distribución (es decir, el módulo), el código C++ será compilado durante la construcción del módulo, y nunca más (a menos que el usuario actualice el módulo). Así que el usuario nunca verá el retraso de inicio asociado con la compilación de código

C++.

Un ejemplo y prueba de concepto para este enfoque se puede encontrar en el módulo de CPAN Math::Prime::

FastSieve.

Este enfoque implica el uso de Inline::MakeMaker, y está bien documentado en el POD de Inline bajo el encabezado Writing Modules with Inline http://search.cpan.org/perldoc?Inline#Writing_Modules_with_Inlin

e

Sin embargo, es posible que desees eliminar la dependencia de Inline::CPP por completo del código que empaquetas en una distribución. Esto se puede hacer usando InlineX::CPP2XS, que convierte el código generado por Inline::CPP a código Perl XS, apto para distribución sin la dependencia de Inline::CPP. InlineX::CPP2XS incluye un directorio example/ que realmente convierte Math::Prime::FastSieve a XS

puro.

Algunos autores de extensiones eligen implementar primero en Inline::CPP, y luego ajustar manualmente, luego copiar y pegar el archivo XS resultante en su propia distribución, con un efecto similar (y posiblemente un poco más de control de granularidad fina) que el enfoque

CPP2XS.

Espacios de nombres de

Perl

Digamos que usas Inline::CPP

así: 
package Some::Foo;
use Inline CPP => <<'END_CPP';
#include <iostream>
using namespace std;
class Foo {
  private:
    int data;
  public:
    Foo()  { cout << "creating a Foo()" << endl; }

El problema es que la clase C++, ""Foo"" se mapeará a Perl debajo del "Some::Foo" namespace, como "Some::Foo::Foo", y necesitaría ser instanciada así: "my $foo = Some::Foo::Foo->new()". Esto probablemente no es lo que el usuario pretendía. Usa la opción de configuración namespace para establecer tu espacio de nombres

base: 
use Inline CPP => config => namespace =>
'Some';

Ahora, "Foo" cae bajo la "Some" jerarquía: "Some::Foo", y puede ser instanciada como "my $foo = Some::Foo->new()". Esto probablemente es lo que el

usuari
o pret
endía.

Sobrescribe el nombre de la clase

C++.

Bajo el comportamiento predeterminado, surgirá un conflicto de nombres de clase C++ al intentar implementar las clases C++ "Foo::Bar::MyClass" y "Foo::Qux::MyClass" que dependen una de la otra de alguna manera, porque C++ ve ambas clases con el nombre solo de "MyClass". No podemos resolver este conflicto de C++ usando solo la opción de configuración "namespace", porque "namespace" solo se aplica al nombre del paquete Perl, no al nombre de la clase

C++.

En el futuro, este problema puede ser resuelto mediante el soporte de Inline::CPP para el operador nativo de C++ "namespace" y/o nombres de clases C++ que contengan el "::" token de ámbito de doble dos

puntos.

Por ahora, este problema se resuelve usando la opción de configuración "classes", que acepta ya sea una referencia a hash o una referencia a código. Cuando se proporciona una referencia a hash, cada clave del hash es un nombre de clase C++, y cada valor del hash es un nombre de clase Perl correspondiente. Esta referencia a hash sirve como un mecanismo de mapeo de nombres de clase de C++-a-Perl, y puede usarse en combinación con la opción de configuración "namespace" para ejercer control total sobre el nombrado de clases y

paquetes.

Cuando se proporciona una referencia a código, debe aceptar como su único argumento el nombre de la clase C++, y devolver un valor de cadena que contenga el nombre del paquete Perl generado. Cuando se proporciona una referencia a código para la opción de configuración "classes", el valor de la opción de configuración "namespace" es

ignorado.

La referencia a hash puede considerarse un método de mapeo manual, y la referencia a código un método de mapeo

automático.

Archivo de ejemplo "/tmp/Foo__Bar__My

Class.c": 
class MyClass {
  private:
    int a;
  public:
    MyClass() :a(10) {}
    int fetch () { return a; }
}
;

Archivo de ejemplo "/tmp/Foo__Qux__My

Class.c": 
#include "/tmp/Foo__Bar__MyClass.c"
class MyClass {
  private:
    int a;
  public:
    MyClass() :a(20) {}
    int fetch () { return a; }
    int other_fetch () { MyClass mybar; return mybar.fetch(); }
}
;

Encontramos el conflicto de nombres de clase C++

cuando 
use Inline CPP => '/tmp/Foo__Qux__MyClass.c' => namespace => 'Foo::
Qux';

El compilador C++ ve dos clases "MyClass" y da un error de

redefinición: 
_08conflict_encounter_t_9d68.xs:25:7: error: redefinition of ‘class MyClass’
 class MyClass {
       ^
In file included from _08conflict_encounter_t_9d68.xs:24:0:
/tmp/Foo__Bar__MyClass.c:1:7: error: previous definition of ‘class MyClass’

La solución es renombrar cada "MyClass" para utilizar nombres de clase únicos, como "Foo__Bar__MyClass" y "Foo__Qux__MyClass", y usar la opción de configuración

"classes".

Archivo de ejemplo actualizado "/tmp/Foo__Bar__My

Class.c": 
class Foo__Bar__MyClass {
  private:
    int a;
  public:
    Foo__Bar__MyClass() :a(10) {}
    int fetch () { return a; }
}
;

Archivo de ejemplo actualizado "/tmp/Foo__Qux__My

Class.c": 
#include "/tmp/Foo__Bar__MyClass.c"
class Foo__Qux__MyClass {
  private:
    int a;
  public:
    Foo__Qux__MyClass() :a(20) {}
    int fetch () { return a; }
    int other_fetch () { Foo__Bar__MyClass mybar; return mybar.fetch(); }
}
;

Primero, considera la siguiente llamada actualizada a Inline usando el método de referencia a hash para mapear manualmente el espacio de nombres y los nombres de clase. Este ejemplo no da ningún error de C++, y se ejecuta correctamente tanto en C++ como en

Este ejemplo automatiza el mapeo del '__' doble guion bajo al '::' doble dos puntos de

Anula el espacio de nombres base

predeterminado.

Bajo el comportamiento predeterminado, una clase C++ "Foo" creada invocando Inline::CPP desde "package Bar" resultará en que la clase C++ "Foo" sea accesible desde Perl como "Bar::Foo". Aunque este comportamiento predeterminado puede ser deseable en algunos casos, podría no serlo en otros. Un ejemplo sería crear una clase "Foo" mientras se invoca Inline::CPP desde el paquete "Foo". La clase resultante se vinculará a Perl como "Foo::Foo", que probablemente no era lo que se

pretendía.

Este comportamiento predeterminado puede ser anulado especificando un "namespace" base alternativo. Los ejemplos son probablemente la mejor manera de

explicarlo: 
package Foo;
use Inline CPP => config => namespace => 'Bar';
use Inline CPP => <<'EOCPP';
class Baz {
  private:
    int a;
  public:
    Baz() :a(20) {}
    int fetch () { return a; }
};
EOCPP
package main;
my $b = Bar::Baz->new();
print $b->fetch, "\n"; #
20.

Como se demuestra aquí, el espacio de nombres en el que reside "Baz" ahora puede ser independiente del paquete desde el cual se invocó Inline::CPP. Considera en cambio el comportamiento

predeterminado: 
package Foo;
use Inline CPP => <<'EOCPP';
class Foo {
  private:
    int a;
  public:
    Baz() :a(20) {}
    int fetch () { return a; }
};
EOCPP
package main;
my $b = Foo::Foo->new();
print $b->fetch, "\n"; #
20.

Es probable que, en este caso, no sea deseable que la clase C++ "Foo" resida en el espacio de nombres de Perl "Foo::Foo". Podemos solucionarlo añadiendo nuestra propia configuración de espacio de

nombres: 
package Foo;
use Inline CPP => config => namespace => q{};  # Disassociate from
# calling package. use Inline CPP => <<'EOCPP'; class Baz { private: int a; public: Baz(
) :a(20) {} int fetch () { return a; } }; EOCPP package main; my $b = Foo->new(); print $b->fetch, "\n"; # 20.

Enlaces

C++-Perl

Esta sección describe cómo las variables "Perl" se mapean a variables "C++" y

viceversa.

Perl usa una pila para pasar argumentos de ida y vuelta a las subrutinas. Cuando se llama a un sub, extrae todos sus argumentos de la pila; cuando termina, empuja sus valores de retorno de vuelta a la

pila.

XS (el lenguaje de Perl para crear extensiones de C o C++ para Perl) usa "mapas de tipos" para convertir SVs en tipos de C y viceversa. Esto se hace a través de varias llamadas de macros XS, conversiones de tipo y la API de Perl. XS también te permite definir tus propios

mapeos.

"Inline::CPP" usa un enfoque mucho más simple. Analiza los archivos de mapa de tipos del sistema y solo se vincula a funciones con tipos soportados. Puedes informar a "Inline::CPP" sobre archivos de mapa de tipos personalizados

también.

Si tienes estructuras de datos no triviales en C++ o Perl, probablemente deberías pasarlas como un SV* y hacer la conversión tú mismo en tu función

C++.

En C++, una estructura es una clase cuyo ámbito predeterminado es público, no privado. Inline::CPP se vincula a estructuras teniendo esto en cuenta -- los métodos get/set aún no se autogeneran (aunque esta característica podría añadirse en una próxima versión)

.

Si tienes una estructura C, puedes usar Inline::Struct para permitir a Perl acceso completo a los internos de la estructura. Puedes crear y modificar estructuras desde dentro de Perl, así como pasar estructuras a funciones C++ y devolverlas desde funciones. Ten en cuenta que Inline::Struct no entiende ninguna característica de C++, por lo que los constructores y las funciones miembro no están soportados. Consulta Inline::Struct para obtener más

detalles.

Ejemplo 5 - Elipses Revisitadas (y Sobrecarga o

Plantillas)

Este ejemplo de cómo usar elipses está adaptado de una discusión en Perl Monks. El problema era que alguien quería llamar a funciones sobrecargadas. Perl no entiende las reglas de sobrecarga de C++, y C++ no tiene idea de cómo Perl pretende llamar a las funciones aquí. Así que escribimos un envoltorio para tomar el control nosotros

mismos: 
use Inline CPP => 'DATA';
say multiadd( 1 );          # No dispatch; just return the value.
say multiadd( 1, 2 );       # Dispatch add( int, int ).
say multiadd( 1, 2, 3 );    # Dispatch add( int, int, int ).
say multiadd( 1, 2, 3, 4 ); # No dispatch; throw an exception.
__DATA__
__CPP__
#include <stdexcept>
// Inline::CPP won't create predictable bindings to overloaded functions.
int add ( int a, int b ) {
  return a + b;
}
int add ( int a, int b, int c ) {
  return a + b + c;
}
// But a function call with elipses can dispatch to overloaded functions since
// no Perl binding is required in reaching those functions.
int multiadd ( SV * a, ... ) {
  dXSARGS;  // Creates a variable 'items' that contains a paramater count.
  try{
    switch ( items ) {
      case 1:  return SvIV(ST(0));
      case 2:  return add( SvIV(ST(0)), SvIV(ST(1)) );
      case 3:  return add( SvIV(ST(0)), SvIV(ST(1)), SvIV(ST(2)) );
      default: throw std::runtime_error(
        "multiadd() - Too many args in function call"
      );
    }
  }
  catch ( std::runtime_error msg ) {
    croak( msg.what() );  // Perl likes croak for exceptions.
  }
}

Técnicamente, una de las versiones de add() se enlazará a Perl, pero es frágil usarla, ya que las reglas de cuál se enlaza no están definidas. Este ejemplo supera el problema de que Perl/XS no entiende la sobrec

arga al simplemente envolver las llamadas a funciones sobrecargadas en una función que
sí entiende. Y usamos elipses para manejar un número variable de argumentos. Este
mismo enfoque se puede aplicar a la llamada de código generado por plantillas también.

Estándar

C++11

¿Está Inline::CPP listo para el estándar C++11? La respuesta corta a esa pregunta es "Mayormente, en la medida en que tu compilador sea compatible con el estándar C++11." Hay dos problemas a considerar. Primero, qué es capaz de hacer tu compilador (y cómo habilitas esas capacidades), y segundo, qué necesita preocuparle a

Perl.

Tomando la primera pregunta primero (porque es la más fácil): Usa la opción "ccflags" mostrada arriba para pasar el flag adecuado a tu compilador para habilitar las características de C++11. La mayor parte de lo que tu compilador soportará, "Inline::CPP" se

encargará.

También podrías necesitar usar el flag "cc" para especificar una versión más nueva del compilador, si resulta que tienes más de uno instalado -- uno que maneje C++11 y uno que

no.

Ahora para la pregunta de qué necesita preocuparle a Perl: Inline::CPP no mira dentro de funciones o métodos. Ese código se trata como una caja negra que pasa directamente a tu compilador. Así que dentro de tus funciones y métodos, siéntete libre de usar cualquier característica de C++11 que

quieras.

Las áreas críticas son encabezados de funciones, definiciones de clases y código que cae fuera de funciones o clases. Tomemos Enums como

ejemplo: 
enum Colors { RED, GREEN, BLUE }
;

¿Cómo debería esto mapearse a Perl? No hay una respuesta clara. C++11 añade el concepto de ámbito a los

enums: 
enum class Colors { RED, GREEN, BLUE }
;

Cómo esto debería enlazarse a Perl se vuelve aún más difícil. La verdad es que Inline::CPP no enlazará ninguno de los dos a Perl. Y probablemente estés mejor con ese enfoque que tener de repente $Colors::RED = 0; apareciendo en tu código Perl. Ten en cuenta, sin embargo, que la construcción se pasa directamente a tu compilador C++, así que siéntete libre de usarla dentro del código C++. Simplemente no se filtrará a tus espacios de nombres de

Perl.

En este momento, la omisión más evidente de sintaxis C++11 válida en Inline::CPP es la nueva sintaxis de "tipo de retorno tardío". C++11 introdujo la siguiente sintaxis

legal: 
auto add ( int x, int y ) -> int { return x + y;
}

Esta omisión solo será un factor para funciones que quieras enlazar a Perl. Si no necesitas que la función se enlace a Perl, la sintaxis está bien; Inline::CPP simplemente ignora la función. Es importante notar que los usos más comunes de esta sintaxis involucran plantillas y lambdas. Las plantillas no tienen sentido para Inline::CPP de todos modos. Y las lambdas están bien, porque ocurren dentro de funciones, así que Inline::CPP no las ve de todos modos. Por ahora, simplemente no uses la sintaxis de tipo de retorno tardío en el encabezado de funciones que necesiten enlazarse a Perl. Esto podría arreglarse en futuras revisiones de la

gramática.

Otro problema es "constexpr"

: 
constexpr int multiply ( int x, int y ) { return x * y;
}

"constexpr" no es reconocido por Inline::CPP, así que esta función no se enlazará a Perl. No creo que las funciones "constexpr" puedan siquiera generar enlaces externos, porque se resuelven a una constante en tiempo de compilación. Realmente no tienen sentido para uso externo (el compilador no puede saber cómo las llamarás). En consecuencia, serán ignoradas por Inline::CPP (y pasarán a tu compilador, así que funcionarán dentro de tu código C++)

.

Y finalmente, Referencias de valo

r rvalue:

Inline::CPP no entiende (todavía)

esto: 
int x = 100;
int getInt ()
{
    return x;
}
int && getRvalueInt ()
{
    return std::move( x );
}

La función getInt() se enlazará a Perl, pero la sintaxis "&&" no es reconocida por Inline::CPP, y no resultará en la generación de un enlace. Así que getRvalueInt() será invisible para Perl. Sin embargo, es perfectamente legal usarla dentro de tu código C++ siempre que no necesites que se enlace a

Perl.

Aparte de eso (hasta donde yo sé), ¡estás listo para ir! Adelante y usa la nueva versión de "for( auto it: x ) {...}", o incluso..

. 
for_each( v.begin(), v.end(), [] (int val) { std::cout << val; } )
;

Plantillas: Puedes usar bibliotecas de plantillass en tu código, pero Inline::CPP no sabrá cómo analizar y enlazar definiciones de plantillas. El problema fundamental es que el compilador de C++ no tiene idea de cómo un lenguaje dinámico como Perl pretende invocar código generado por plantillas y, por lo tanto, no sabe qué código generar a partir de ellas. Mantén las plantillas encapsuladas lejos de la interfaz que se expondrá a Perl envolviendo las llamadas en funciones que le den al compilador un tipo con el que
trabajar.
Sobrecarga de
operadores
Sobrecarga de funciones -- Este es un problema similar al de las plantillas. Perl no conoce las reglas de resolución de sobrecarga de funciones de C++. Y C++ no conoce a Perl. XS nunca fue diseñado para manejar este tipo de discrepancia. Esto impide implementar el Regla de Tres para código destinado a enlazarse con Perl, pero como Perl maneja tus enlaces, probablemente no sea un
problema.
Estos tres problemas (Plantillas, Sobrecarga de Operadores y Sobrecarga de Funciones) son situaciones en las que el lenguaje C++ y el lenguaje Perl simplemente no se corresponden bien entre sí. Cuanto antes te acostumbres a esta desconexión, antes tendrás una idea de lo que funcionará y lo que no. Las plantillas son la forma en que un lenguaje estático como C++ aborda el concepto de programación genérica. Perl es un lenguaje tan dinámico que las plantillas (que se resuelven completamente en tiempo de compilación) no pueden resolverse cuando son llamadas por Perl. El concepto de paso de parámetros de Perl es tan dinámico que las firmas de función (que C++ usa para resolver sobrecargas) tampoco pueden mapearse de manera significativa. Habrá otras características de C++ que no se mapean en Perl, y viceversa. Considera los enums de C++. ¿Debería Perl tratarlos como constantes mapeándolos mediante el pragma constant? La respuesta no está clara, y el hecho es que no serán enlazados en Perl en
absoluto.
La herencia múltiple no funciona correctamente (aún)
.
Los arreglos multidimensionales como datos miembro no están implementados
(aún).
Declarar un tipo de parámetro void no está implementado. Simplemente usa "int myfunc();" en lugar de "int myfunc(void);". Esto es C++, no C. Está bien, de
verdad.
Excepciones: Aunque está bien lanzar una excepción usando 'throw', Perl no sabrá cómo recuperarse de ella y obtendrás un volcado de núcleo en lugar de una muerte a la manera de Perl. La solución es simple, croak("Mensaje"). Perl tratará eso como una llamada a "die". El quinto ejemplo de arriba demuestra cómo obtener lo mejor de ambos mundos: el manejo de excepciones rico de C++ y el "die" de
Perl.
La idea principal es esta: Atrapa tus throws. Y cualquier cosa que no pueda manejarse con elegancia, relánzala de vuelta a Perl usando "cro
ak
".
