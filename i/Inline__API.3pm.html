Paquete: perl-inline

Inline::API(3) Documentación de Perl aportada por el usuario Inline::API(3)

NOMBRE

Inline-API - Cómo vincular un lenguaje de programación a Perl usando Inline.pm

SINOPSIS

#!/usr/bin/perl
use Inline Foo;
say_it('foo');  # Usa Foo para imprimir "Hello, Foo"
__Foo__
foo-sub say_it {
    foo-my $foo = foo-shift;
    foo-print "Hello, $foo\n";
}

DESCRIPCIÓN

Así que crees que Inline C es bastante genial, pero lo que realmente necesitas es que Perl funcione con el nuevo lenguaje de programación "Foo". Pues tienes suerte. "Inline.pm" tiene soporte para añadir tu propio Módulo de Soporte de Lenguaje Inline (ILSM), como "Inline::Foo".

Inline siempre ha estado destinado a funcionar con muchos lenguajes de programación diferentes. Muchos de los detalles pueden compartirse entre implementaciones, de modo que "Inline::Java" tiene una interfaz similar a "Inline::ASM". Todo el código común está en "Inline.pm".

Los módulos específicos de un lenguaje como "Inline::Python" son subclases de "Inline.pm". Pueden heredar tanto del comportamiento común como deseen, y proporcionar comportamiento específico propio. Esto generalmente se presenta en forma de Opciones de Configuración y compilación específica del lenguaje.

El soporte de Inline C es probablemente la mejor plantilla para copiar. Desde la versión 0.30, todo el soporte de C fue aislado en el módulo "Inline::C" y la gramática de análisis se desglosa aún más en "Inline::C::grammar". Todos estos componentes vienen con la distribución de Inline.

Este POD te da todos los detalles que necesitas para implementar un ILSM. Para asistencia adicional, contacta a inline@perl.org. Ver ["VER TAMBIÉN"] más abajo.

Examinaremos el lenguaje de broma Inline::Foo que se distribuye con Inline. En realidad es un ILSM totalmente funcional. Lo uso en el arnés de pruebas de Inline para probar la funcionalidad base de Inline. Es muy corto, y puede ayudarte a comprender la API de Inline.

A UN ESQUELETO

Para el resto de este tutorial, supongamos que estamos escribiendo un ILSM para el lenguaje ficticio "Foo". Lo llamaremos "Inline::Foo". Aquí está la implementación completa (y funcional).

package Inline::Foo;
use strict;
$Inline::Foo::VERSION = '0.01';
@Inline::Foo::ISA = qw(Inline);
require Inline;
use Carp;
#===========================================================
# Registra Foo como un Módulo de Soporte de Lenguaje Inline (ILSM)
#===========================================================
sub register {
    return {
        language => 'Foo',
        aliases => ['foo'],
        type => 'interpreted',
        suffix => 'foo',
       };
}
#===========================================================
# Mensajes de error
#===========================================================
sub usage_config {
    my ($key) = @_;
    "'$key' is not a valid config option for Inline::Foo\n";
}
sub usage_config_bar {
    "Invalid value for Inline::Foo config option BAR";
}
#===========================================================
# Valida las Opciones de Configuración de Foo
#===========================================================
sub validate {
    my $o = shift;
    $o->{ILSM}{PATTERN} ||= 'foo-';
    $o->{ILSM}{BAR} ||= 0;
    while (@_) {
    my ($key, $value) = splice @_, 0, 2;
    if ($key eq 'PATTERN') {
        $o->{ILSM}{PATTERN} = $value;
        next;
    }
    if ($key eq 'BAR') {
        croak usage_config_bar
          unless $value =~ /^[01]$/;
        $o->{ILSM}{BAR} = $value;
        next;
    }
    croak usage_config($key);
    }
}
#===========================================================
# Analiza y compila el código Foo
#===========================================================
sub build {
    my $o = shift;
    my $code = $o->{API}{code};
    my $pattern = $o->{ILSM}{PATTERN};
    $code =~ s/$pattern//g;
    $code =~ s/bar-//g if $o->{ILSM}{BAR};
    sleep 1;             # imita el retraso de compilación
    {
        package Foo::Tester;
        eval $code;
    }
    croak "Foo build failed:\n$@" if $@;
    my $path = "$o->{API}{install_lib}/auto/$o->{API}{modpname}";
    my $obj = $o->{API}{location};
    $o->mkpath($path) unless -d $path;
    open FOO_OBJ, "> $obj"
      or croak "Can't open $obj for output\n$!";
    print FOO_OBJ $code;
    close \*FOO_OBJ;
}
#===========================================================
# Solo necesario para lenguajes interpretados
#===========================================================
sub load {
    my $o = shift;
    my $obj = $o->{API}{location};
    open FOO_OBJ, "< $obj"
      or croak "Can't open $obj for output\n$!";
    my $code = join '', <FOO_OBJ>;
    close \*FOO_OBJ;
    eval "package $o->{API}{pkg};\n$code";
    croak "Unable to load Foo module $obj:\n$@" if $@;
}
#===========================================================
# Devuelve un pequeño informe sobre el código Foo.
#===========================================================
sub info {
    my $o = shift;
    my $text = <<'END';
This is a small report about the Foo code. Perhaps it contains
information about the functions the parser found which will be
bound to Perl. It will get included in the text produced by the
Inline 'INFO' command.
END
    return $text;
}
1;

Excepto por load(), las subrutinas en este código son obligatorias para un ILSM. Lo que hacen se describe más abajo. Algunas cosas a tener en cuenta:

  • "Inline::Foo" debe ser una subclase de Inline. Esto se logra con: 
    @Inline::Foo::ISA = qw(Inline);
  • La línea '"require Inline;"' no es necesaria. Pero está ahí para recordarte no decir '"use Inline;"'. Esto no funcionará.
  • Recuerda, no es válido que un usuario diga: 
    use Inline::Foo;

    "Inline.pm" detectará ese uso por ti en su método "import" , que se hereda automáticamente ya que "Inline::Foo" es una subclase.

  • En la función build, normalmente necesitas analizar tu código fuente. Inline::C usa Parse::RecDescent para hacer esto. Inline::Foo simplemente usa eval. (Después de eliminar todas las apariciones de 'foo-').

    Un método de análisis alternativo que funciona bien para muchos ILSMs (como Java y Python) es usar el propio compilador del lenguaje para analizar por ti. Esto funciona siempre que se pueda hacer que el compilador devuelva información de análisis.

LA API DE INLINE

Esta sección es una especificación más formal de qué funcionalidad necesitarás proporcionar para implementar un ILSM.

Cuando Inline determina que algo "Foo" código necesita ser compilado, cargará automáticamente tu módulo ILSM. Luego llamará a varias subrutinas que necesitas proporcionar. Llamaremos a estas subrutinas "callbacks" (retrollamadas).

Necesitarás proporcionar las siguientes 5 subrutinas de callback.

El register() Callback

Esta subrutina no recibe argumentos. Devuelve una referencia a un hash de metadatos del ILSM. Inline llama a esta rutina solo cuando intenta detectar nuevos ILSMs que se han instalado en un sistema dado. Aquí hay un ejemplo de la referencia al hash que devolverías para Foo:

{
    language => 'Foo',
    aliases => ['foo'],
    type => 'interpreted',
    suffix => 'foo',
};

Los elementos de metadatos tienen los siguientes significados:

language
Este es el nombre propio del lenguaje. Generalmente se implementa como "Inline::X" para un lenguaje dado 'X'.
aliases
Esta es una referencia a un array de alias de nombres de lenguaje. El nombre propio de un lenguaje solo puede contener caracteres de palabra. A-Za-z0-9_ Un alias puede contener cualquier carácter excepto espacios en blanco y comillas. Esto es útil para nombres como 'C++' y 'C#'.
type
Debe establecerse en 'compiled' (compilado) o 'interpreted' (interpretado). Indica la categoría del lenguaje.
suffix
Esta es la extensión de archivo para el objeto en caché que serácreado. Para los lenguajes 'compilados', probablemente será 'so' o 'dll'. El valor apropiado está en "Config.pm".

Para los lenguajes interpretados, este valor puede ser lo que quieras. Python usa "pydat". Foo usa "foo".

El validate() Callback

A esta rutina se le pasan todas las opciones de configuración que no fueron manejadas previamente por el módulo base Inline. Las opciones se pasan como pares clave/valor. Depende de ti validar cada opción y almacenar su valor en el objeto Inline (que también se pasa). Si una opción en particular es inválida, debes hacer croak con un mensaje de error apropiado.

Ten en cuenta que todas las palabras clave que recibe esta rutina serán convertidas a mayúsculas por "Inline", sin importar en qué mayúsculas o minúsculas las haya dado el programa.

El build() Callback

Esta subrutina es responsable de hacer el análisis y la compilación del código fuente de Foo. El objeto Inline se pasa como único argumento. Toda la información pertinente se almacenará en este objeto. build() es necesario para crear un objeto de caché con un nombre específico, o para hacer croak con un mensaje de error apropiado.

Esta es la parte principal de tu ILSM. Dado que probablemente será bastante complicado, probablemente sea mejor que estudies un ILSM existente como "Inline::C".

El load() Callback

Este método solo necesita ser proporcionado para lenguajes interpretados. Su responsabilidad es iniciar el intérprete.

Para los lenguajes compilados, se llama a la rutina load de "Inline.pm" que usa "DynaLoader" para cargar el objeto compartido o DLL.

El info() Callback

Este método se llama cuando el usuario hace uso del "INFO" atajo. Deberías devolver una cadena que contenga un pequeño informe sobre el código Inlined.

EL OBJETO INLINE

"Inline.pm" crea un objeto Perl basado en hash para cada sección de código fuente Inlined que recibe. Este objeto contiene mucha información sobre el código, el entorno y las opciones de configuración utilizadas.

Este objeto es un hash que está dividido en varios subhashes. Los únicos dos subhashes que un ILSM debería usar en absoluto son $o->{API} y $o->{ILSM}. El primero contiene toda la información que Inline ha recopilado para ti para que puedas crear/cargar un objeto de caché de tu diseño. El segundo es un repositorio donde tu ILSM puede almacenar libremente datos que podría necesitar más adelante.

Esta sección describirá todos los atributos del objeto "API" de Inline.

El atributo code
Este es el código fuente real pasado por el usuario. Se almacena como una sola cadena larga.
El atributo language
El nombre propio del lenguaje que se está utilizando.
El atributo language_id
El nombre del lenguaje especificado por el usuario. Podría ser 'C++' en lugar de 'CPP'.
El atributo module
Este es el nombre de archivo del objeto compartido.
El atributo modfname
Este es el nombre de archivo del objeto compartido.
El atributo modpname
Esta es la extensión de la ruta de instalación del objeto compartido.
El atributo version
La versión de "Inline.pm" que se está usando.
El atributo pkg
El paquete Perl desde el cual se invocó esta llamada de Inline.
El atributo install_lib
Este es el directorio en el que escribir el objeto compartido.
El atributo build_dir
Este es el directorio bajo el cual deberías escribir todos tus archivos relacionados con la construcción.
El atributo script
Este es el nombre del script que invocó a Inline.
El atributo location
Esta es la ruta completa del objeto ejecutable en cuestión.
El atributo suffix
Este es el nombre de la extensión de la biblioteca compartida. (Normalmente 'so' o 'dll').

Método derive_minus_I

Los ILSMs pueden necesitar ejecutar subprocesos de Perl con un entorno similar al actual - particularmente @INC. Se puede llamar a este método para devolver una lista de rutas absolutas que pasar a un intérprete de Perl para recrear ese entorno. Necesitarás anteponer "-I" a cada una. Este método omite de esa lista cualquier ruta que aparezca en $ENV{PERL5LIB} o las bibliotecas predeterminadas de Perl, ya que esas estarán disponibles de todos modos.

EL ESPACIO DE NOMBRES INLINE

"Inline.pm" ha sido configurado de modo que cualquiera puede escribir sus propios módulos de soporte de lenguaje. Además permite que cualquiera escriba una implementación diferente de un lenguaje Inline existente, como C por ejemplo. Puedes distribuir ese módulo en el CPAN.

Si tienes planes de implementar y distribuir un módulo Inline, te pediría que por favor trabajes con la comunidad Inline. Podemos ser contactados en la lista de correo de Inline: inline@perl.org (Envía un correo a inline-subscribe@perl.org para suscribirte). Aquí deberías encontrar los consejos y la asistencia necesarios para hacer que tu módulo sea un éxito.

La comunidad Inline decidirá si tu implementación de COBOL se distribuirá como el oficial "Inline::COBOL" o si debería usar un espacio de nombres alternativo. En casos de disputa, yo (Ingy döt Net) retengo la autoridad final. (y espero no tener que usarla :-) En realidad modules@perl.org retiene la autoridad final.

Pero incluso si quieres trabajar solo, eres libre y bienvenido a escribir y distribuir módulos de soporte de lenguaje Inline en CPAN. Solo necesitarás distribuirlos bajo un nombre de paquete diferente.
