Inline(3) Documentación de Perl aportada por el usuario Inline(3)

NOMBRE

Inline - Escribir subrutinas de Perl en otros lenguajes de programación

VERSIÓN

Este documento describe la versión 0.87de Inline.

SINOPSIS

use Inline C;
print "9 + 16 = ", add(9, 16), "\n";
print "9 - 16 = ", subtract(9, 16), "\n";
__END__
__C__
int add(int x, int y) {
  return x + y;
}
int subtract(int x, int y) {
  return x - y;
}

DESCRIPCIÓN

El módulo Inline le permite poner código fuente de otros lenguajes de programación directamente "inline" en un script o módulo de Perl. El código se compila automáticamente según sea necesario y luego se carga para un acceso inmediato desde Perl.

Inline le ahorra la molestia de tener que escribir y compilar su propio código de enlace utilizando herramientas como XS o SWIG. Simplemente escriba el código donde lo desee y ejecute su Perl como de costumbre. Todos los detalles complicados son gestionados por usted. La compilación e instalación de sus fragmentos de código ocurren de forma transparente; todo lo que notará es el retraso de la compilación en la primera ejecución.

El código Inline solo se compila la primera vez que lo ejecuta (o cada vez que se modifica), por lo que solo sufre el impacto en el rendimiento una vez. El código que se incluye en línea en módulos distribuidos (como en el CPAN) se compilará cuando se instale el módulo, por lo que el usuario final nunca notará el tiempo de compilación.

Lo mejor de todo es que funciona igual en Unix y en Microsoft Windows. Consulte Inline-Support para obtener información sobre soporte.

¿Por qué Inline?

¿Quiere saber "¿Por qué usaría otros lenguajes en Perl?" o "¿Por qué debería usar Inline para hacerlo?"? Intentaré responder ambas.

¿Por qué usaría otros lenguajes en Perl?
La razón más obvia es el rendimiento. Para un lenguaje interpretado, Perl es muy rápido. Mucha gente dirá "Cualquier cosa que Perl pueda hacer, C puede hacerla más rápido". (Nunca mencionan el tiempo de desarrollo :-) De todos modos, es posible que pueda eliminar un cuello de botella en su código Perl usando otro lenguaje, sin tener que escribir todo el programa en ese lenguaje. Esto reduce su tiempo de desarrollo general, porque está usando Perl para todo el código no crítico.

Otra razón es acceder a funcionalidad de API existentes que usan el lenguaje. Parte de este código puede estar disponible solo en forma binaria. Pero creando pequeñas subrutinas en el lenguaje nativo, puede "pegar" bibliotecas existentes a su Perl. Como usuario del CPAN, sabe que la reutilización de código es algo bueno. Entonces, ¿por qué tirar esas bibliotecas de Fortran todavía?

Si está usando Inline con el lenguaje C, entonces puede acceder a todos los internos de Perl mismo. Esto abre las compuertas tanto al poder extremo como al peligro.

Quizás la mejor razón es "¡Porque quiero!". La diversidad mantiene interesante al mundo. ¡TMTOWTDI!

¿Por qué debería usar Inline para hacerlo?
Ya existen dos instalaciones principales para extender Perl con C. Son XS y SWIG. Ambos son similares en sus capacidades, al menos en lo que a Perl se refiere. Y ambos son bastante difíciles de aprender en comparación con Inline.

Hay una gran curva de aprendizaje involucrada en la configuración y el uso del entorno XS. Necesita familiarizarse bastante con los siguientes documentos:

  • perlxs
  • perlxstut
  • perlapi
  • perlguts
  • perlmod
  • h2xs
  • xsubpp
  • ExtUtils::MakeMaker

Con Inline puede estar listo y funcionando en minutos. Hay un Manual de Recetas de C con muchos programas cortos pero completos que puede extender a sus problemas de la vida real. No necesita aprender sobre el complicado proceso de construcción que ocurre en segundo plano. Ni siquiera necesita compilar el código usted mismo. Inline se encarga de cada último detalle excepto escribir el código C.

A los programadores de Perl no les importan cosas tontas como compilar. "Ajustar, Ejecutar, Ajustar, Ejecutar" es nuestra forma de vida. Inline hace todo el trabajo sucio por usted.

Otra ventaja de Inline es que puede usarlo directamente en un script. Incluso puede usarlo en un one-liner de Perl. Con XS y SWIG, usted siempre configura un módulo completamente separado. Incluso si solo tiene una o dos funciones. Inline hace que las cosas fáciles sean fáciles y las difíciles posibles. Al igual que Perl.

Finalmente, Inline soporta varios lenguajes de programación (no solo C y C++). En el momento de escribir esto, Inline tiene soporte para C, C++, Java, Python, Ruby, Tcl, Ensamblador, Basic, Guile, Befunge, Octave, Awk, BC, TT (Template Toolkit), WebChat e incluso PERL. Se están añadiendo regularmente nuevos Módulos de Soporte de Lenguaje Inline (ILSMs). Consulte Inline-API para detalles sobre cómo crear su propio ILSM.

USANDO EL MÓDULO INLINE.PM

Inline es un poco diferente a la mayoría de los módulos de Perl a los que está acostumbrado. No importa ninguna función en su espacio de nombres y no tiene ningún método orientado a objetos. Toda su interfaz (con dos pequeñas excepciones) se especifica a través del comando 'use Inline ...' .

Esta sección explicará todas las formas diferentes de "usar Inline". Si desea comenzar a usar C con Inline inmediatamente, consulte Inline::C-Cookbook.

Lo Básico

La forma más básica de usar Inline es:

use Inline X => "X source code";

donde 'X' es uno de los lenguajes de programación Inline soportados. El segundo parámetro identifica el código fuente que desea vincular a Perl. El código fuente se puede especificar usando cualquiera de las siguientes sintaxis:

La palabra clave DATA.
use Inline Java => 'DATA';
# Perl code goes here ...
__DATA__
__Java__
/* Java code goes here ... */

La forma más fácil y visualmente más limpia de especificar su código fuente en un programa Perl con Inline es usar la palabra clave especial "DATA" . Esto le dice a Inline que busque un marcador especial en el flujo de entrada de su manejador de archivos "DATA" . En este ejemplo, el marcador especial es "__Java__", que es el lenguaje de programación rodeado por dobles guiones bajos.

En caso de que lo haya olvidado, el archivo pseudo "DATA" está compuesto por todo el texto después de la sección "__END__" o "__DATA__" de su programa. Si está trabajando fuera del paquete "main" , es mejor usar el marcador "__DATA__" o de lo contrario Inline no encontrará su código.

Usar este esquema mantiene su código Perl arriba, y todo lo feo de Java abajo donde pertenece. Esto es visualmente limpio y hace que el código sea más mantenible. Un excelente beneficio secundario es que no tiene que escapar ningún carácter como podría hacer en una cadena de Perl. El código fuente es literal. Por estas razones, prefiero este método más que los demás.

El único problema con este estilo es que como Perl no puede leer el manejador de archivos "DATA" hasta el tiempo de ejecución, obviamente no puede vincular sus funciones hasta el tiempo de ejecución. El efecto neto de esto es que no puede usar sus funciones Inline como palabras desnudas (sin predeclararlas) porque Perl no tiene idea de que existen durante el tiempo de compilación.

Las palabras clave FILE y BELOW.
use Inline::Files;
use Inline Java => 'file';
# Perl code goes here ...
__JAVA__
/* Java code goes here ... */

Este es el método más nuevo para especificar su código fuente. Hace uso del módulo de Perl "Inline::Files" escrito por Damian Conway. El estilo básico y el significado son los mismos que para la palabra clave "DATA" , pero hay algunas peculiaridades sintácticas y semánticas.

Primero, debe decir 'use Inline::Files' antes de que 'use Inline' necesite esos archivos. El especial '"DATA"' se reemplaza por '"file"' o '"below"'. Esto permite el uso del malentendido idiomático de:

use Inline C => 'below';

Puedes omitir la "__DATA__" etiqueta ahora. Inline::Files es un filtro de código fuente que eliminará estas secciones de tu programa antes de que Perl lo compile. Luego estarán disponibles para que Inline las utilice. Y como todo esto se puede hacer en tiempo de compilación, no tienes que preocuparte por las advertencias de la palabra clave 'DATA'.

Este módulo tiene un par de pequeñas advertencias. Dado que Inline::Files solo reconoce marcadores de archivo con letras mayúsculas, debes especificar la forma mayúscula del nombre de tu lenguaje. Además, hay una penalización en el tiempo de inicio por usar un filtro de código fuente.

En este punto, Inline::Files es software alfa y su uso es experimental. La integración de este módulo por parte de Inline también es incipiente en este momento. Una de las cosas que planeo hacer con Inline::Files es obtener información de números de línea para que cuando una extensión no compile, los mensajes de error apunten al archivo fuente y número de línea correctos.

Mi mejor consejo es usar Inline::Files para pruebas (especialmente a medida que su soporte mejore), pero usa DATA para producción y código distribuido/CPAN.

Cadenas
use Inline Java => <<'END';
/* El código Java va aquí ... */
END
# El código Perl va aquí ...

También puedes especificar el código fuente como una cadena única. Una forma conveniente de escribir la cadena es usar el estilo de comillas de "aquí documento" de Perl. Esto está bien para funciones pequeñas pero puede volverse engorroso en gran escala. Por otra parte, la variante de cadena probablemente tiene la menor penalización de inicio y todas las funciones se enlazan en tiempo de compilación.

Si deseas poner la cadena en una variable escalar, ten en cuenta que la "use" sentencia es una directiva de tiempo de compilación. Como tal, todas las variables que usa también deben establecerse en tiempo de compilación, "antes" de la sentencia 'use Inline'. Aquí hay una forma de hacerlo:

my $code;
BEGIN {
    $code = <<END;
/* El código Java va aquí ... */
END
}
use Inline Java => $code;
# El código Perl va aquí ...
La bind() Función
Una alternativa al uso del método BEGIN block es especificar el código fuente en tiempo de ejecución usando el método 'Inline->bind()'. (Esta es una de las excepciones de interfaz mencionadas anteriormente) El bind() método toma los mismos argumentos que 'use Inline ...'. 
my $code = <<END;
/* El código Java va aquí ... */
END
Inline->bind(Java => $code);

Puedes pensar en bind() como una forma de eval() código en otros lenguajes de programación.

Aunque bind() es una característica poderosa, no se recomienda su uso en módulos basados en Inline. De hecho, no funcionará en absoluto para módulos instalables. Consulta las instrucciones a continuación para crear módulos con Inline.

Otros Métodos
El código fuente para Inline también se puede especificar como un nombre de archivo externo, una referencia a una subrutina que devuelve código fuente, o una referencia a un arreglo que contiene líneas de código fuente. (Ten en cuenta que si el archivo fuente externo está en el directorio actual, debe especificarse con un punto inicial.' - es decir '.file.ext' en lugar de simplemente 'file.ext'.) Estos métodos se usan con menos frecuencia pero pueden ser útiles en algunas situaciones.

Por ejemplo, para cargar tu código C++ desde un archivo con el mismo nombre que tu módulo perl con la extensión de archivo intercambiada, puedes usar:

use Inline CPP => (__FILE__ =~ s/\.pm$/.cpp/r);
Abreviatura
Si estás usando los métodos 'DATA' o 'file' descritos anteriormente y no hay parámetros adicionales, puedes omitir la palabra clave por completo. Por ejemplo: 
use Inline 'Java';
# El código Perl va aquí ...
__DATA__
__Java__
/* El código Java va aquí ... */

o

use Inline::Files;
use Inline 'Java';
# El código Perl va aquí ...
__JAVA__
/* El código Java va aquí ... */

Más sobre la Sección DATA

Si estás escribiendo un módulo, también puedes usar la sección DATA para POD y subrutinas de AutoLoader. Solo asegúrate de ponerlas antes del primer marcador de Inline. Si instalas el módulo auxiliar "Inline::Filters", incluso puedes usar POD dentro de tu código Inline. Solo tienes que especificar un filtro para eliminarlo.

También puedes especificar múltiples secciones de Inline, posiblemente en diferentes lenguajes de programación. Aquí hay otro ejemplo:

# El módulo Foo.pm
package Foo;
use AutoLoader;
use Inline C;
use Inline C => DATA => filters => 'Strip_POD';
use Inline Python;
1;
__DATA__
sub marine {
    # Esta es una subrutina cargada automáticamente
}
=head1 Subrutinas externas
=cut
__C__
/* Primera sección C */
__C__
/* Segunda sección C */
=head1 Mi Función C
Alguna documentación POD.
=cut
__Python__
"""Una Sección Python"""

Una cosa importante a recordar es que necesitas tener un "use Inline Foo=> 'DATA'" para cada "__Foo__" marcador, y deben estar en el mismo orden. Esto te permite aplicar diferentes opciones de configuración a cada sección.

Opciones de Configuración

Inline intenta hacer lo correcto siempre que sea posible. Pero a veces puede que necesites anular las acciones predeterminadas. Esto es fácil de hacer. Simplemente lista las opciones de configuración de Inline después de los parámetros regulares de Inline. Todas las opciones de configuración se especifican como pares (clave, valor).

use Inline (C => 'DATA',
            directory => './inline_dir',
            libs => '-lfoo',
            inc => '-I/foo/include',
            prefix => 'XXX_',
            warnings => 0,
           );

También puedes especificar las opciones de configuración en una llamada de Inline separada así:

use Inline (C => Config =>
            directory => './inline_dir',
            libs => '-lfoo',
            inc => '-I/foo/include',
            prefix => 'XXX_',
            warnings => 0,
           );
use Inline C => <<'END_OF_C_CODE';

La palabra clave especial 'Config' le dice a Inline que esta es una llamada solo de configuración. No se compilará ni se enlazará código fuente a Perl.

Si deseas especificar opciones de configuración globales que no se apliquen a un lenguaje en particular, simplemente deja fuera el lenguaje de la llamada. Así:

use Inline Config => warnings => 0;

Las opciones Config se heredan y son aditivas. Puedes usar tantas llamadas Config como quieras. Y puedes aplicar diferentes opciones a diferentes secciones de código. Cuando se pasa una sección de código fuente, Inline aplicará las opciones que se hayan especificado hasta ese punto. Aquí hay un ejemplo de configuración compleja:

use Inline (Config =>
            directory => './inline_dir',
           );
use Inline (C => Config =>
            libs => '-lglobal',
           );
use Inline (C => 'DATA',         # Primera Sección C
            libs => ['-llocal1', '-llocal2'],
           );
use Inline (Config =>
            warnings => 0,
           );
use Inline (Python => 'DATA',    # Primera Sección Python
            libs => '-lmypython1',
           );
use Inline (C => 'DATA',         # Segunda Sección C
            libs => [undef, '-llocal3'],
           );

El primer "Config" se aplica a todas las llamadas posteriores. El segundo "Config" se aplica a todas las secciones "C" posteriores (pero no a las secciones "Python" ). En la primera sección "C" , las bibliotecas externas "global", "local1" y "local2" se utilizan. (La mayoría de las opciones permiten la forma de cadena o de referencia de arreglo, y hacen lo correcto.) La sección "Python" no usa la biblioteca "global" , pero usa el mismo "DIRECTORY", y tiene las advertencias desactivadas. La segunda sección "C" solo usa la biblioteca "local3" . Eso se debe a que un valor de "undef" restablece el comportamiento aditivo.

Las opciones "directory" y "warnings" son opciones genéricas de Inline. Todas las demás opciones son específicas del lenguaje. Para averiguar qué hacen las opciones "C" , consulta "Inline::C".

Activar y Desactivar

Si una opción de configuración particular tiene opciones de valor 1 y 0, puedes usar los modificadores 'enable' y 'disable'. En otras palabras, esto:

use Inline Config =>
           force_build => 1,
           clean_after_build => 0;

podría reescribirse como:

use Inline Config =>
           enable => force_build =>
           disable => clean_after_build;

Jugando 'con' Otros

Inline tiene una sintaxis de configuración especial que le indica que obtenga más opciones de configuración de otros módulos Perl. Aquí hay un ejemplo:

use Inline with => 'Event';

Esto le dice a Inline que cargue el módulo "Event.pm" y le pida información de configuración. Dado que "Event" tiene una API de C propia, puede pasar a Inline toda la información que necesita para poder usar "Event" callbacks de C sin problemas.

Eso significa que no necesitas especificar los typemaps, bibliotecas compartidas, archivos de inclusión y otra información necesaria para que esto funcione.

Puedes especificar un solo módulo o una lista de ellos. Como:

use Inline with => qw(Event Foo Bar);

Actualmente, los módulos que funcionan con Inline incluyen "Event", "PDL", y aquellos que usan "Alien::Build.

Para que tu módulo funcione con Inline de esta manera, tu módulo necesita proporcionar un método de clase llamado "Inline" que reciba un lenguaje de Inline como parámetro (por ejemplo, "C"), y devuelva una referencia a un hash con información de configuración que sea aceptable para el ILSM correspondiente. Para C, ver Opciones de Configuración de C. Por ejemplo:

my $confighashref = Event->Inline('C'); # solo soporta C en 1.21
# el hashref contiene las claves INC, TYPEMAPS, MYEXTLIB, AUTO_INCLUDE, BOOT

Si tu módulo usa ExtUtils::Depends versión 0.400 o superior, tu módulo solo necesita esto:

package Module;
use autouse Module::Install::Files => qw(Inline);

Atajos de Inline

Inline te permite establecer muchas opciones de configuración desde la línea de comandos. Estas opciones se llaman 'atajos'. Pueden ser muy útiles, especialmente cuando solo quieres establecer las opciones temporalmente, digamos, para depurar.

Por ejemplo, para obtener información general sobre tu código de Inline en el script "Foo.pl", usa el comando:

perl -MInline=info Foo.pl

Si quieres forzar la compilación de tu código, incluso si ya lo está, usa:

perl -MInline=force Foo.pl

Si quieres hacer ambas cosas, usa:

perl -MInline=info -MInline=force Foo.pl

o mejor aún:

perl -MInline=info,force Foo.pl

El 'directorio' de Inline

Inline necesita un lugar para construir tu código e instalar los resultados de la compilación. Usa un único directorio llamado '.Inline/' en circunstancias normales. Si creas este directorio en tu directorio de inicio, en el directorio actual o en el directorio donde reside tu programa, Inline lo encontrará y lo usará. También puedes especificarlo en la variable de entorno "PERL_INLINE_DIRECTORY" o directamente en tu programa, usando la opción de palabra clave "directory" . Si Inline no puede encontrar el directorio en ninguno de estos lugares, creará un directorio '_Inline/' en tu directorio actual o en el directorio donde reside tu script.

Uno de los factores clave para usar Inline con éxito es entender este directorio. Al desarrollar código, generalmente es mejor crear este directorio (o dejar que Inline lo haga) en tu directorio actual. Recuerda que no hay nada sagrado sobre este directorio excepto que contiene tu código compilado. Siéntete libre de eliminarlo en cualquier momento. Inline simplemente empezará desde cero y recompilará tu código en la próxima ejecución. Si tienes varios programas que quieres forzar a recompilar, simplemente elimina tu directorio '.Inline/' .

Probablemente sea mejor tener un directorio '.Inline/' separado para cada proyecto en el que estés trabajando. Es posible que quieras mantener el código estable en el <.Inline/> en tu directorio de inicio. En sistemas multiusuario, cada usuario debe tener sus propios directorios '.Inline/' . Podría ser un riesgo de seguridad poner el directorio en un lugar compartido como "/tmp/".

Depurando Errores de Inline

Todos los programadores cometen errores. Cuando cometas un error con Inline, como escribir código C incorrecto, obtendrás un gran informe de error en tu pantalla. Este informe te dice dónde buscar para hacer la depuración. Algunos lenguajes también pueden volcar los mensajes de error generados durante la compilación.

Cuando Inline necesita compilar algo, crea un subdirectorio bajo tu directorio "DIRECTORY/build/" . Aquí es donde escribe todos los componentes que necesita para compilar tu extensión. Cosas como archivos XS, Makefiles y archivos de registro de salida.

Si todo va bien, Inline eliminará este subdirectorio. Si hay un error, Inline dejará el directorio intacto e imprimirá su ubicación. La idea es que supuestamente debas entrar en ese directorio y averiguar qué sucedió.

Lee la documentación de tu Módulo de Soporte de Lenguaje de Inline particular para más información.

El Archivo de Registro 'config'

Inline mantiene un archivo en caché de todos los metadatos de los Módulos de Soporte de Lenguaje de Inline en un archivo llamado "config". Este archivo se puede encontrar en tu directorio "directory" . Si el archivo no existe, Inline crea uno nuevo. Buscará en tu sistema cualquier módulo que comience con "Inline::". Luego llamará al método register() de ese módulo para obtener información útil para futuras invocaciones.

Cada vez que añadas un nuevo ILSM, deberías eliminar este archivo para que Inline descubra automáticamente tu módulo de lenguaje recién instalado. (Esto ya no debería ser necesario a partir de Inline-0.49.)

OPCIONES DE CONFIGURACIÓN

Esta sección lista todas las opciones de configuración genéricas de Inline. Para la configuración específica de un lenguaje, consulta la documentación de ese lenguaje.

"directory"
La opción de configuración "directory" es el directorio que Inline usa tanto para compilar como para instalar una extensión.

Normalmente, Inline buscará en un montón de lugares conocidos un directorio llamado '.Inline/'. Si no lo encuentra, creará un directorio llamado '_Inline/'

Si quieres especificar tu propio directorio, usa esta opción de configuración.

Ten en cuenta que debes crear el directorio "directory" tú mismo. Inline no lo hará por ti.

"name"
Puedes usar esta opción para establecer el nombre del módulo objeto de tu extensión de Inline. Por ejemplo: 
use Inline C => 'DATA',
           name => 'Foo::Bar';

haría que tu código C se compilara en el objeto:

lib/auto/Foo/Bar/Bar.so
lib/auto/Foo/Bar/Bar.inl

(El componente .inl contiene información de dependencia para asegurarse de que el código fuente esté sincronizado con el ejecutable)

Si no usas "name", Inline elegirá un nombre por ti basado en el nombre de tu programa o en el nombre del paquete. En este caso, Inline también habilitará la opción "autoname" , que incorpora una pequeña parte de la huella digital MD5 en tu nombre de objeto, para hacerlo único.

"autoname"
Esta opción se habilita siempre que no se especifica el parámetro "name" . Para deshabilitarla, di: 
use Inline C => 'DATA',
           disable => 'autoname';

"autoname" incorpora suficiente de la huella digital MD5 para hacer que el nombre de tu módulo sea único. Los objetos creados con "autoname" nunca serán reemplazados. Eso también significa que nunca serán limpiados automáticamente.

"autoname" es muy útil para pequeños scripts desechables. Para cosas más serias, usa siempre la opción "name" .

"version"
Especifica el número de versión del objeto de extensión de Inline. Se usa solo para módulos, y debe coincidir con la variable global $VERSION. Adicionalmente, esta opción debe usarse si (y solo si) un módulo se está configurando para ser instalado permanentemente en el árbol sitelib de Perl usando Inline::MakeMaker (NO usado por Inline::Module). Inline emitirá un error fatal si la usas de otra manera.

La presencia del parámetro "version" es la forma oficial de hacer saber a Inline que tu código es un módulo instalable/instalado. Inline nunca generará un objeto en la caché temporal (directorio"_Inline/" ) si "version" está establecido. Tampoco intentará recompilar un módulo que fue instalado en el árbol site de Perl de alguien.

Así que la regla básica es desarrollar sin "version", y entregar con "version".

"with"
"with" también puede usarse como una opción de configuración en lugar de usar la sintaxis especial 'with'. Haz esto si quieres usar diferentes secciones de código de Inline con diferentes módulos. (Probablemente un uso muy raro) 
use Event;
use Inline C => DATA => with => 'Event';

Los módulos especificados usando la forma de configuración de "with" no serán no requeridos automáticamente. Debes "use" tú mismo.

"using"
Puedes anular los módulos que son usados por los ILSMs con la opción "using" . Esto se usa típicamente para anular el analizador predeterminado para Inline::C, pero podría ser usado por cualquier ILSM para cualquier propósito. 
use Inline config => using => '::Parser::RecDescent';
use Inline C => '...';

Esto le diría a Inline::C que use Inline::C::Parser::RecDescent.

"global_load"
Esta opción es solo para lenguajes compilados. Le dice a Inline que le diga a DynaLoader que cargue un archivo objeto de tal manera que sus símbolos puedan ser resueltos dinámicamente por otros archivos objetos. Puede no funcionar en todas las plataformas. Ver el atajo "global" más abajo.
"untaint"
Puedes usar esta opción siempre que uses el interruptor "-T" de Perl, para la comprobación de contaminación (taint). Esta opción le dice a Inline que descontamine ciegamente todas las variables contaminadas. (Esto es generalmente considerado como algo inseguro y no se recomienda - pero la opción está ahí para que la uses si quieres. Por favor, considera usar algo distinto de Inline para scripts que necesiten comprobación de contaminación.) También activa "safemode" por defecto. Ver el atajo "untaint" más abajo. Verás advertencias sobre la descontaminación ciega de campos en %ENV y en objetos de Inline. Si quieres silenciar estas advertencias, establece la opción de Config ";no_untaint_warn" => 1. Puede haber algunos problemas al descontaminar scripts Inline donde versiones antiguas de Cwd, como las que se distribuían con versiones tempranas de perl-5.8 (y anteriores), están instaladas. Actualizar Cwd probablemente resolverá estos problemas.
safemode
Realiza comprobaciones de seguridad adicionales, en un intento de frustrar código malicioso. Esta opción no puede garantizar la seguridad, pero sí activa todas las comprobaciones actualmente implementadas. (Actualmente, la única "comprobación actualmente implementada" es asegurarse de que "directory" la opción también se haya utilizado.)

Hay una pequeña penalización de inicio al usar "safemode". Además, usar "untaint" activa automáticamente esta opción. Si necesita que su código arranque más rápido bajo "-T" (taint) checking, necesitará desactivar esta opción manualmente. Solo hágalo si no le preocupan los riesgos de seguridad. Vea el atajo "unsafe" a continuación.

"force_build"
Hace que Inline construya (compile) el código fuente cada vez que el programa se ejecuta. El valor predeterminado es 0. Vea el atajo "force" a continuación.
"build_noisy"
Indica a los ILSM que deben volcar los mensajes de construcción a la terminal en lugar de estar en silencio sobre todos los detalles de la construcción.
"build_timers"
Indica a los ILSM que impriman información de tiempo sobre cuánto duró cada fase de construcción. Generalmente requiere "Time::HiRes".
"clean_after_build"
Indica a Inline que limpie el área de construcción actual si la construcción fue exitosa. A veces desea "disable" esto para depurar. El valor predeterminado es 1. Vea el atajo "noclean" a continuación.
"clean_build_area"
Indica a Inline que limpie los viejos áreas de construcción dentro de todo el Inline "directory". El valor predeterminado es 0. Vea el atajo "clean" a continuación.
"print_info"
Indica a Inline que imprima varias informaciones sobre el código fuente. El valor predeterminado es 0. Vea el atajo "info" a continuación.
"print_version"
Indica a Inline que imprima información de versión sobre sí mismo. El valor predeterminado es 0. Vea el atajo "version" a continuación.
"reportbug"
Pone a Inline en modo 'reportbug', que es lo que desea si desea reportar un error.
"rewrite_config_file"
El valor predeterminado es 0, pero establecer "rewrite_config_file => 1" significará que el archivo de configuración existente en el Inline "directory" será sobrescrito. (Esto es útil si el archivo de configuración existente no está actualizado con respecto a los lenguajes soportados.)
"warnings"
Esta opción le dice a Inline si debe imprimir ciertas advertencias. El valor predeterminado es 1.

ATAJOS DE CONFIGURACIÓN DE INLINE

Esta es una lista de todas las opciones de configuración de atajo actualmente disponibles para Inline. Especifíquelas desde la línea de comandos al ejecutar scripts de Inline.

perl -MInline=noclean inline_script.pl

o

perl -MInline=info,force,noclean inline_script.pl

Puede especificar múltiples atajos separados por comas. No son sensibles a mayúsculas/minúsculas. También puede especificar atajos dentro del programa Inline así:

use Inline 'info', 'force', 'noclean';

NOTA: Si una 'use Inline' declaración se usa para establecer atajos, no puede
usarse para propósitos adicionales.

"clean"
Le dice a Inline que elimine cualquier directorio de construcción que pueda estar quedando en su área de construcción. Normalmente estos directorios se eliminan inmediatamente después de una construcción exitosa. Las excepciones son cuando la construcción falla, o cuando usa las opciones "noclean" o "reportbug" .
"force"
Fuerza la recompilación del código, incluso si todo está actualizado.
"global"
Activa la opción "global_load" .
"info"
Esta es una opción muy útil cuando quiere saber qué está pasando bajo el capó. Le dice a Inline que imprima información útil en "STDERR". Entre las cosas que se imprimen está una lista de qué funciones de Inline fueron vinculadas exitosamente a Perl.
"noclean"
Le dice a Inline que deje los archivos de construcción después de compilar.
"noisy"
Usa la opción "build_noisy" para imprimir mensajes durante una construcción.
"reportbug"
Pone a Inline en modo "reportbug" , que realiza un procesamiento especial cuando desea reportar un error. "reportbug" también fuerza automáticamente una construcción, y no limpia después. Esto es para que pueda comprimir con tar y enviarme por correo el directorio de construcción. "reportbug" imprimirá instrucciones exactas sobre qué hacer. Por favor, léalas y siga las cuidadosamente.

NOTA: "reportbug" le informa que use el comando tar. Si su sistema no
tiene tar, por favor use el comando "zip" equivalente.

"safe"
Activa "safemode" . "untaint" activará esto automáticamente. Aunque este modo realiza comprobaciones de seguridad adicionales, no garantiza la seguridad.
"site_install"
Este parámetro solía usarse para crear módulos Inline instalables. Ha sido eliminado de Inline por completo y reemplazado con un mecanismo mucho más simple y potente, "Inline::MakeMaker". Vea la sección a continuación sobre cómo crear módulos con Inline.
"_testing"
Usado internamente por Ct09parser.t y Ct10callback.t (en la suite de pruebas de Inline::C). Establecer esta opción con Inline::C significará que archivos llamados "parser_id" y "void_test" son creados en el directorio "./Inline_test" , creando ese directorio si no existe ya. Los archivos (pero no el "./Inline_test directory") son limpiados al llamar a Inline::C::_testing_cleanup(). También es usado por "t/06rewrite_config.t" para activar una advertencia.
"timers"
Activa "build_timers" para obtener información de diagnóstico adicional sobre las construcciones.
"unsafe"
Desactiva "safemode" . Úselo en combinación con "untaint" para un tiempo de inicio ligeramente más rápido bajo "-T". Úselo solo si está seguro de que el entorno es seguro.
"untaint"
Activa la opción "untaint" . Se usa con el interruptor "-T" . En términos de prácticas seguras, esta es definitivamente no una forma recomendada de lidiar con la verificación de contaminación, pero es la única opción actualmente disponible con Inline. Úsela bajo su propio riesgo.
"version"
Le dice a Inline que reporte su versión de lanzamiento.

ESCRIBIENDO MÓDULOS CON INLINE

La forma actualmente preferida de autorar módulos CPAN con Inline es usar Inline::Module (distribuido por separado). Inline se distribuye con Inline::MakeMaker, que le ayuda a configurar un Makefile.PL que invoca Inline en el momento de la instalación para compilar todo el código antes de que sea instalado, pero el módulo resultante aún depende de Inline y del módulo de soporte de lenguaje como Inline::C. Para evitar esta dependencia, lo que realmente quiere hacer es convertir su distribución a XS plano antes de subirla a CPAN. Inline::Module cumple ese rol, y también se integra bien con herramientas de autoría más modernas.

Vea Inline::Module para detalles sobre ese enfoque, o continúe leyendo a continuación para la técnica más antigua con Inline::MakeMaker.

Supongamos que quiere escribir un módulo llamado "Math::Simple". Comience usando el siguiente comando:

h2xs -PAXn Math::Simple

Esto generará un montón de archivos que forman un esqueleto de lo que necesita para un módulo distribuible. (Lea la página del manual de h2xs para averiguar qué hacen las opciones) A continuación, modifique el archivo "Simple.pm" para que se vea así:

package Math::Simple;
$VERSION = '1.23';
use base 'Exporter';
@EXPORT_OK = qw(add subtract);
use strict;
use Inline C => 'DATA',
           version => '1.23',
           name => 'Math::Simple';
# La siguiente llamada Inline->init() es opcional - vea más abajo para más información.
#Inline->init();
1;
__DATA__
=pod
=cut
__C__
int add(int x, int y) {
  return x + y;
}
int subtract(int x, int y) {
  return x - y;
}

Las cosas importantes a notar aquí son que usted debe especificar un parámetro "name" y un parámetro "version" . El "name" debe coincidir con el nombre del paquete de su módulo. El parámetro "version" debe coincidir con la variable $VERSION de su módulo y deben ser considerados válidos por "version::parse".

NOTA: Estas son las comprobaciones de cordura de Inline para asegurarse de que usted sabe lo que está haciendo
antes de subir su código a CPAN. Aseguran que una vez que el módulo haya
sido instalado en el sistema de alguien, el módulo no sería
recompilado automáticamente por ninguna razón. Esto hace que los módulos basados en Inline
funcionen exactamente de la misma manera que los basados en XS.

Finalmente, necesita modificar el Makefile.PL. Simplemente cambie:

use ExtUtils::MakeMaker;

a

use Inline::MakeMaker;

Y, para que la construcción del módulo funcione correctamente en el shell cpan, agregue la siguiente directiva al WriteMakefile()del Makefile.PL:

CONFIGURE_REQUIRES  =>  {
    'Inline::MakeMaker'     => 0.45,
    'ExtUtils::MakeMaker'   => 6.52,
},

Esta directiva "CONFIGURE_REQUIRES" asegura que el shell cpan instalará Inline en la máquina del usuario (si no lo estády presente) antes de construir su módulo basado en Inline. Especificar "ExtUtils::MakeMaker => 6.52," es opcional, y puede omitirse si lo desea. Solo asegura que no se emitan algunas advertencias inofensivas relacionadas con la "CONFIGURE_REQUIRES" directiva durante la construcción del módulo. También significa, por supuesto, que ExtUtils::Makemaker se actualizará primero en la máquina del usuario a menos que el usuario ya tenga la versión 6.52 o posterior. Si el
