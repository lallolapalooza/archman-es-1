NOMBRE

Image::ExifTool::MIE - Leer/escribir información meta MIE

SINOPSIS

Este módulo es utilizado por Image::ExifTool

DESCRIPCIÓN

Este módulo contiene las rutinas requeridas por Image::ExifTool para leer y escribir información en archivos MIE.

¿QUÉ ES MIE?

MIE significa "Meta Information Encapsulation" (Encapsulación de Información Meta). El formato MIE es un formato de información meta dedicado y extensible que soporta el almacenamiento de información meta tanto binaria como textual. MIE puede usarse para encapsular información meta de muchas fuentes y agruparla junto con cualquier tipo de archivo.

Características

A continuación se muestra una tabla de puntuación muy subjetiva que compara las características de varios formatos comunes de archivos e información meta, y los compara con MIE. Las siguientes características se puntúan para cada formato con una puntuación de 0 a 10:

 1) Extensible (puede incorporar información definida por el usuario).
 2) IDs de etiquetas significativos (pista sobre el significado de información desconocida).
 3) Capacidad de lectura/escritura secuencial (transmisible).
 4) Estructura jerárquica de información.
 5) Fácil de implementar lector/escritor/editor.
 6) Orden de la información bien definido.
 7) Soporte para longitudes de datos grandes: >64kB (+5) y >4GB (+5).
 8) Cadenas de texto localizadas.
 9) Múltiples documentos en un solo archivo.
10) Formato compacto que no desperdicia espacio en disco ni ancho de banda.
11) Soporte para información meta comprimida.
12) Elementos de datos reubicables (es decir, sin desplazamientos fijos).
13) Información meta binaria (+7) con orden de bytes variable (+3).
14) No se requieren etiquetas obligatorias (una complicación innecesaria).
15) Añadir información al final del archivo sin editar.

Por diseño, MIE ocupa el primer lugar con una ventaja significativa. Otros formatos con puntuaciones razonables son PDF, PNG y XMP, pero cada uno tiene puntos débiles significativos. Lo que puede resultar sorprendente es que TIFF, EXIF e IPTC ocupen posiciones tan bajas.

Además de puntuar alto en todas estas características, el formato MIE tiene la capacidad única de encapsular cualquier otro tipo de archivo, y proporciona un método no invasivo de añadir información meta a un archivo. La información meta está lógicamente separada de los datos originales del archivo, lo cual es extremadamente importante porque la información meta se pierde rutinariamente cuando se editan los archivos.

Además, el formato MIE soporta múltiples archivos por simple concatenación, permitiendo todo tipo de características maravillosas como bases de datos lineales, historiales de edición o actualizaciones de archivos no intrusivas. Esta capacidad también puede aprovecharse para permitir que se añadan remates (trailers) en formato MIE a algunos otros tipos de archivos.

ESPECIFICACIÓN DEL FORMATO MIE 1.1 (2007-01-21)

Estructura del archivo

Un archivo MIE consiste en una serie de elementos MIE. Un elemento MIE puede contener datos o un grupo de elementos MIE, proporcionando un formato jerárquico para almacenar datos. Cada elemento MIE se identifica por un nombre de etiqueta legible por humanos, y puede almacenar datos de cero a 2^64-1 bytes de longitud.

Firma del archivo

El primer elemento en el archivo MIE debe ser un elemento de grupo MIE sin comprimir con un nombre de etiqueta de "0MIE". Esta restricción permite que los primeros 8 bytes de un archivo MIE se usen para identificar un archivo de formato MIE. La siguiente tabla lista las dos posibles secuencias de bytes iniciales para un archivo de formato MIE (la primera para orden de bytes big-endian, y la segunda para orden de bytes little-endian):

Número de byte:      0    1    2    3    4    5    6    7
Caracteres C:     ~ \x10 \x04    ?    0    M    I    E
    o             ~ \x18 \x04    ?    0    M    I    E
Hexadecimal:     7e   10   04    ?   30   4d   49   45
    o             7e   18   04    ?   30   4d   49   45
Decimal:        126   16    4    ?   48   77   73   69
    o            126   24    4    ?   48   77   73   69

Note que el byte 1 puede tener uno de los dos valores posibles (0x10 o 0x18), y el byte 3 puede tener cualquier valor (0x00 a 0xff).

Estructura del elemento

1 byte  SyncByte = 0x7e (decimal 126, carácter '~')
1 byte  FormatCode (ver abajo)
1 byte  TagLength (T)
1 byte  DataLength (da D si DataLength < 253)
T bytes TagName (T dado por TagLength)
2 bytes DataLength2 [existe solo si DataLength == 255 (0xff)]
4 bytes DataLength4 [existe solo si DataLength == 254 (0xfe)]
8 bytes DataLength8 [existe solo si DataLength == 253 (0xfd)]
D bytes DataBlock (D dado por DataLength)

La longitud mínima del elemento es 4 bytes (para un terminador de grupo). El tamaño máximo de DataBlock es 2^64-1 bytes. TagLength y DataLength son enteros sin signo, y el orden de bytes para los campos DataLength de múltiples bytes es especificado por el elemento de grupo MIE que los contiene. El SyncByte está alineado a bytes, así que no se añade relleno para alinear en un límite de N bytes.

FormatCode

El código de formato es una máscara de bits que define el formato de los datos:

7654 3210
++++ ----  FormatType
---- +---  TypeModifier
---- -+--  Compressed
---- --++  FormatSize
FormatType (máscara de bits 0xf0):
0x00 - otros datos (o desconocidos)
0x10 - grupo MIE
0x20 - cadena de texto
0x30 - lista de cadenas de texto separadas por nulos
0x40 - entero
0x50 - racional
0x60 - punto fijo
0x70 - punto flotante
0x80 - espacio libre
TypeModifier (máscara de bits 0x08):
Modifica el significado de ciertos FormatTypes (0x00-0x60): 
0x08 - otros datos sensibles al orden de bytes del grupo MIE
0x18 - grupo MIE con orden de bytes little-endian
0x28 - cadena de texto codificada en UTF
0x38 - lista de cadenas de texto codificadas en UTF
0x48 - entero con signo
0x58 - racional con signo (el denominador siempre es sin signo)
0x68 - punto fijo con signo
Compressed (máscara de bits 0x04):
Si este bit está establecido, el bloque de datos se comprime usando Zlib deflate. Un grupo MIE completo puede comprimirse, con la excepción de los grupos a nivel de archivo.
FormatSize (máscara de bits 0x03):
Da el tamaño en bytes de cada elemento de datos: 
0x00 - 8 bits  (1 byte)
0x01 - 16 bits (2 bytes)
0x02 - 32 bits (4 bytes)
0x03 - 64 bits (8 bytes)

El número de bytes en un solo valor para este formato es dado por 2**FormatSize (o 1 << FormatSize). El número de valores es la longitud de los datos dividida por este número de bytes. Es un error si la longitud de los datos no es un múltiplo exacto del tamaño del formato en bytes.

La siguiente es una lista de todos los valores de FormatCode MIE actualmente definidos para datos sin comprimir (añada 0x04 a cada valor para datos comprimidos):

0x00 - otros datos (insensibles al orden de bytes del grupo MIE) (1)
0x01 - otros datos de 16 bits (pueden intercambiarse bytes)
0x02 - otros datos de 32 bits (pueden intercambiarse bytes)
0x03 - otros datos de 64 bits (pueden intercambiarse bytes)
0x08 - otros datos (sensibles al orden de bytes del grupo MIE) (1)
0x10 - grupo MIE con valores big-endian (1)
0x18 - grupo MIE con valores little-endian (1)
0x20 - cadena ASCII (ISO 8859-1) (2,3)
0x28 - cadena UTF-8 (2,3,4)
0x29 - cadena UTF-16 (2,3,4)
0x2a - cadena UTF-32 (2,3,4)
0x30 - lista de cadenas ASCII (ISO 8859-1) (3,5)
0x38 - lista de cadenas UTF-8 (3,4,5)
0x39 - lista de cadenas UTF-16 (3,4,5)
0x3a - lista de cadenas UTF-32 (3,4,5)
0x40 - entero sin signo de 8 bits
0x41 - entero sin signo de 16 bits
0x42 - entero sin signo de 32 bits
0x43 - entero sin signo de 64 bits (6)
0x48 - entero con signo de 8 bits
0x49 - entero con signo de 16 bits
0x4a - entero con signo de 32 bits
0x4b - entero con signo de 64 bits (6)
0x52 - racional sin signo de 32 bitsracional sin signo (16 bits de numerador y luego denominador) (7)
0x53 - racional sin signo de 64 bits (32 bits de numerador y luego denominador) (7)
0x5a - racional con signo de 32 bits (el denominador es sin signo) (7)
0x5b - racional con signo de 64 bits (el denominador es sin signo) (7)
0x61 - punto fijo sin signo de 16 bits (los 8 bits altos son la parte entera) (8)
0x62 - punto fijo sin signo de 32 bits (los 16 bits altos son la parte entera) (8)
0x69 - punto fijo con signo de 16 bits (los 8 bits altos son el entero con signo) (8)
0x6a - punto fijo con signo de 32 bits (los 16 bits altos son el entero con signo) (8)
0x72 - flotante IEEE de 32 bits (no recomendado por razones de portabilidad)
0x73 - doble IEEE de 64 bits (no recomendado por razones de portabilidad) (6)
0x80 - espacio libre (el dato de valor no contiene información útil)

Notas:

1.
El orden de bytes especificado por el TypeModifier del grupo MIE se aplica al elemento del grupo MIE así como a todos los elementos dentro del grupo. Los datos de todos los FormatCodes excepto 0x08 (otros datos, sensibles al orden de bytes) pueden ser transferidos entre grupos MIE con diferente orden de bytes mediante el intercambio de bytes de los datos sin comprimir de acuerdo con el formato de datos especificado. La siguiente lista ilustra el patrón de intercambio de bytes, basado en FormatSize, para todos los tipos de formato excepto racional (FormatType 0x50). 
  FormatSize              Cambio en la Secuencia de Bytes
--------------      -----------------------------------
0x00 (8 bits)       0 1 2 3 4 5 6 7 --> 0 1 2 3 4 5 6 7 (sin cambio)
0x01 (16 bits)      0 1 2 3 4 5 6 7 --> 1 0 3 2 5 4 7 6
0x02 (32 bits)      0 1 2 3 4 5 6 7 --> 3 2 1 0 7 6 5 4
0x03 (64 bits)      0 1 2 3 4 5 6 7 --> 7 6 5 4 3 2 1 0

Los valores racionales consisten en dos enteros, por lo que se intercambian como el FormatSize siguiente más bajo. Por ejemplo, un racional de 32 bits (FormatSize 0x02, y FormatCode 0x52 o 0x5a) se intercambia como dos valores de 16 bits (es decir, como si tuviera FormatSize 0x01).

2.
El TagName de un elemento de cadena puede tener un sufijo de 6 caracteres para indicar un locale específico. (ej. "Title-en_US", o "Keywords-de_DE").
3.
Las cadenas de texto normalmente no terminan en nulo, sin embargo pueden ser rellenadas con uno o más caracteres nulos al final del bloque de datos para permitir que las cadenas sean editadas dentro de bloques de datos de longitud fija. Los saltos de línea en el texto se indican con un solo carácter LF (0x0a).
4.
Las cadenas UTF no deben comenzar con una marca de orden de bytes (BOM) ya que el orden de bytes y el tamaño de byte son especificados por el formato MIE. Si se encuentra una BOM, debe ser tratada como un espacio sin separación de ancho cero.
5.
Una lista de cadenas de texto separadas por caracteres nulos. Estas listas no deben ser rellenadas con nulos ni terminar en nulo, ya que esto sería interpretado como cadenas adicionales de longitud cero. Para cadenas ASCII y UTF-8, el carácter nulo es un solo cero (0x00). Para cadenas UTF-16 o UTF-32, el carácter nulo es 2 o 4 ceros respectivamente.
6.
Los enteros y dobles de 64 bits están sujetos al orden de bytes especificado para tanto las palabras de 32 bits como los bytes dentro de estas palabras. Por ejemplo, el byte de orden alto es siempre el primer byte si es big-endian, y el octavo byte si es little-endian. Esto significa que siempre es necesario algún intercambio para estos valores en sistemas donde el orden de bytes difiere del orden de palabras (ej. algunos sistemas ARM), independientemente de la naturaleza big-endian o little-endian de los valores almacenados.
7.
Los valores racionales se tratan como dos enteros separados. El numerador siempre viene primero independientemente del orden de bytes. En un valor racional con signo, solo el numerador tiene signo. El denominador de todos los valores racionales es sin signo (ej. un racional con signo de 64 bits de 0x80000000/0x80000000 evalúa a -1, no a +1).
8.
Los valores de punto fijo de 32 bits se convierten a punto flotante tratándolos como un entero y dividiéndolos por un valor apropiado. ej) 
valor fijo de 16 bits = valor entero de 16 bits / 256.0
valor fijo de 32 bits = valor entero de 32 bits / 65536.0

TagLength

Da la longitud de la cadena TagName. Cualquier valor entre 0 y 255 es válido, pero un TagLength de 0 es válido solo para el terminador del grupo MIE.

DataLength

DataLength es un byte sin signo que da el número de bytes en el bloque de datos. Un valor entre 0 y 252 da la longitud de datos directamente, y los números de 253 a 255 están reservados para códigos de DataLength extendidos. Los códigos 255, 254 y 253 indican que el elemento contiene un entero sin signo adicional de 2, 4 o 8 bytes que representa la longitud de datos.

0-252      - longitud del bloque de datos
255 (0xff) - usar DataLength2
254 (0xfe) - usar DataLength4
253 (0xfd) - usar DataLength8

Un DataLength de cero es válido para cualquier elemento excepto un grupo MIE comprimido. Un DataLength de cero para un grupo MIE sin comprimir indica que la longitud del grupo es desconocida. Para otros elementos, una longitud de cero indica que no hay datos asociados. Un elemento terminador debe tener un DataLength de 0, 6 o 10, y no puede usar un DataLength extendido.

TagName

La cadena TagName tiene de 0 a 255 bytes de longitud, y está compuesta de los caracteres ASCII A-Z, a-z, 0-9 y guion bajo ('_'). También, un guion ('-') es usado para separar el código de idioma/país en el TagName de una cadena de texto localizada, y una cadena de unidades (posiblemente que contiene otros caracteres ASCII) puede aparecer entre corchetes al final del TagName. La cadena TagName NO termina en nulo. Un elemento MIE con una cadena de etiqueta de longitud cero está reservado para el terminador del grupo.

Los elementos MIE se ordenan alfabéticamente por TagName dentro de cada grupo. Se permiten múltiples elementos con el mismo TagName, incluso dentro del mismo grupo.

Los TagNames deben ser significativos. Las mayúsculas son significativas. Las palabras deben estar en minúsculas con un primer carácter en mayúscula, y los acrónimos deben estar en mayúsculas. El guion bajo ("_") está provisto para permitir la separación de dos acrónimos o dos números, pero no debería usarse a menos que sea necesario. No es necesaria ninguna separación entre un acrónimo y una palabra (ej. "ISOSetting").

Todos los TagNames deben comenzar con una letra en mayúscula. Una excepción a esta regla permite que las etiquetas comiencen con un dígito (0-9) si deben venir antes de otras etiquetas en el orden de clasificación, o con una letra en minúscula (a-z) si deben venir después. Por ejemplo, el elemento '0Type' comienza con un dígito por lo que viene antes, y el elemento 'data' comienza con una letra en minúscula para que venga después de las etiquetas de información meta en el grupo principal "0MIE".

Los nombres de etiqueta para cadenas de texto localizadas tienen un sufijo de 6 caracteres con el siguiente formato: El primer carácter es un guion ('-'), seguido de un código de idioma ISO 639-1 de 2 caracteres en minúsculas, luego un guion bajo ('_'), y terminando con un código de país ISO 3166-1 alfa 2 de 2 caracteres en mayúsculas. (ej. "-en_US", "-en_GB", "-de_DE" o "-fr_FR". Note que "GB", y no "UK" es el código para Gran Bretaña, aunque "UK" debería ser reconocido por razones de compatibilidad.) El sufijo se incluye al ordenar las etiquetas alfabéticamente, por lo que el locale por defecto (sin sufijo de nombre de etiqueta) siempre viene primero. Si el país es desconocido o no aplica, un código de país de "XX" debería ser usado.

Las etiquetas con valores numéricos pueden permitir que se especifiquen unidades de medida. La cadena de unidades se almacena entre corchetes al final del nombre de la etiqueta, y está compuesta de cero o más caracteres ASCII en el rango 0x21 a 0x7d, excluyendo los caracteres de corchete 0x28 y 0x29. (ej. "Resolution(/cm)" o "SpecificHeat(J/kg.K)".) Vea Image::ExifTool::MIEUnits para detalles. Las cadenas de unidades no están localizadas, y no pueden usarse en combinación con cadenas de texto localizadas.

Los conjuntos de etiquetas que requerirían un prefijo común deberían ser añadidos en un grupo MIE separado en lugar de añadir el prefijo a todos los nombres de etiqueta. Por ejemplo, en lugar de estos TagName's:

ExternalFlashType
ExternalFlashSerialNumber
ExternalFlashFired

uno designaría en su lugar un grupo MIE separado "ExternalFlash" para contener los siguientes elementos:

Type
SerialNumber
Fired

DataLength2/4/8

Estos campos extendidos de DataLength existen solo si DataLength es 255, 254 o 253, y son respectivamente enteros sin signo de 2, 4 o 8 bytes que dan la longitud del bloque de datos. Uno de estos valores debe ser usado si el bloque de datos es mayor de 252 bytes, pero pueden ser usados si se desea para bloques más pequeños también (aunque esto puede añadir unos pocos bytes innecesarios al elemento MIE).

DataBlock

El valor de datos para el elemento MIE. El formato de los datos es dado por el FormatCode. Para elementos de grupo MIE, los datos incluyen todos los elementos contenidos y el terminador del grupo.

Grupos MIE

Todos los elementos de datos MIE deben estar contenidos dentro de un grupo. Un grupo comienza con un elemento de grupo MIE, y termina con un terminador de grupo. Los grupos pueden estar anidados en una jerarquía a una profundidad arbitraria.

Un elemento de grupo MIE es identificado por un código de formato de 0x10 (orden de bytes big endian) o 0x18 (little endian). El terminador de grupo es distinguido por un TagLength de cero (es el único elemento permitido para tener un TagLength de cero), y tiene un FormatCode de 0x00.

Al elemento de grupo MIE se le permite tener un DataLength de cero solo si los datos no están comprimidos. Este valor especial indica que la longitud del grupo es desconocida (de lo contrario el valor mínimo para DataLength es 4, correspondiente al tamaño mínimo del grupo que incluye un terminador de al menos 4 bytes). Si DataLength es cero, todos los elementos del grupo deben ser analizados hasta que se encuentre el terminador del grupo. Si es distinto de cero, DataLength incluye la longitud de todos los elementos contenidos dentro del grupo, incluyendo el terminador del grupo. Se recomienda el uso de un DataLength distinto de cero porque permite a los lectores saltar rápidamente grupos MIE completos. Para grupos comprimidos DataLength debe ser distinto de cero, y es la longitud de los datos del grupo comprimido (que incluye el terminador del grupo comprimido).

Terminador de Grupo

El terminador de grupo tiene un FormatCode y TagLength de cero. El DataLength del terminador debe ser de 0, 6 o 10 bytes, y los códigos de DataLength extendidos no pueden ser usados. Con un DataLength de cero, la secuencia de bytes para un terminador es "7e 00 00 00" (hex). Con un DataLength de 6 o 10 bytes, el bloque de datos del terminador contiene información sobre la longitud y el orden de bytes del grupo precedente. Esta información adicional es recomendada para grupos a nivel de archivo, y es usada en archivos MIE multi-documento y en trailers MIE para permitir que el archivo sea escaneado hacia atrás desde el final. (Esto también puede permitir que algunos documentos sean recuperados si parte del archivo está corrupta.) La estructura de este bloque de datos de terminador opcional es la siguiente:

4 u 8 bytes  GroupLength (entero sin signo)
1 byte        ByteOrder (0x10 o 0x18, igual que el grupo MIE)
1 byte        GroupLengthSize (0x04 o 0x08)

Los valores ByteOrder y GroupLengthSize dan el orden de bytes y el tamaño del entero GroupLength. El valor GroupLength es la longitud total del grupo MIE completo que termina con este terminador, incluyendo el elemento de grupo MIE de apertura y el terminador en

sí.

bytes.

El formato MIE puede ser usado para información de trailer añadida a otros tipos de archivos. Cuando esto se hace, una firma debe aparecer al final del grupo MIE principal para identificar de manera única el trailer del formato MIE. Para lograr esto, una firma de trailer "zmie" es escrita como el último elemento en el grupo principal "0MIE". Este elemento tiene un FormatCode de 0, un TagLength de 4, un DataLength de 0, y un TagName de "zmie". Con esta firma, la secuencia de bytes hex "7e 00 04 00 7a 6d 69 65" aparece inmediatamente antes del terminador de grupo final, y los últimos 22 bytes del trailer corresponden a uno de los siguientes 4 patrones (donde la longitud del trailer es dada por "xx", como arriba)

: 
?? ?? ?? ?? 7e 00 04 00 7a 6d 69 65 7e 00 00 06 xx xx xx xx 10 04
?? ?? ?? ?? 7e 00 04 00 7a 6d 69 65 7e 00 00 06 xx xx xx xx 18 04
7e 00 04 00 7a 6d 69 65 7e 00 00 0a xx xx xx xx xx xx xx xx 10 08
7e 00 04 00 7a 6d 69 65 7e 00 00 0a xx xx xx xx xx xx xx xx 18
08

Tener en cuenta que el terminador con DataLength cero no puede ser usado aquí porque la longitud del trailer debe ser conocida para buscar hacia atrás desde el final del

archivo.

Múltiples trailers pueden

ser añadidos al mismo arc
hivo usando esta técnica.

Valores de Datos

MIE

Los valores de datos MIE para una etiqueta dada usualmente no están restringidos a un FormatCode específico. Cualquier valor puede ser representado en cualquier formato apropiado, incluyendo números representados en forma de cadena (ASCII o UTF)

.

Es preferible que valores estrechamente relacionados con el mismo formato sean escritos en una sola etiqueta en lugar de usar múltiples etiquetas. Esto mejora la localización de valores similares y disminuye la sobrecarga del elemento MIE. Por ejemplo, en lugar de etiquetas separadas ImageWidth y ImageHeight, se define una sola etiqueta

ImageSize.

Las etiquetas que pueden tomar un conjunto discreto de valores deben tener valores significativos si es posible. Esto mejora la extensibilidad del formato y permite una interpretación más razonable de valores no

reconocidos.

Representación

Numérica

Números enteros y de punto flotante pueden ser representados en forma binaria o de cadena. En forma de cadena, los enteros son una serie de dígitos con un signo inicial opcional (ej. "[+|-]DDDDDD"), y múltiples valores son separados por un solo carácter de espacio (ej. "23 128 -32"). Los números de punto flotante son similares pero también pueden contener un punto decimal y/o un exponente con signo con un carácter inicial 'e' (ej. "[+|-]DD[.DDDDDD][e(+|-)EEE]"). La cadena "inf" es usada para representar infinito. Una ventaja de las cadenas numéricas es que pueden tener una precisión arbitrariamente alta porque el número posible de dígitos significativos es virtualmente

ilimitado.

Tener en cuenta que los valores numéricos pueden tener unidades de medida asociadas que son especificadas en la cadena

"TagName".

Formato de

Fecha/Hora

Todas las fechas MIE son cadenas en la forma "YYYY:mm:dd HH:MM:SS.ss+HH:MM". Los segundos fraccionarios (".ss") son opcionales, y si se incluyen pueden conte

ner cualquier número de dígitos significativos (a diferencia de todos los demás campos que tienen un número fijo de dígitos y deben ser rellenados con ceros
iniciales si es necesario). La zona horaria ("+HH:MM" o "-HH:MM") es recomendada pero no requerida. Si no se da, se asume la zona horaria del sistema local.

Tipo

MIME

El tipo MIME básico para un archivo MIE es "application/x-mie", sin embargo el tipo MIME específico depende del tipo de subarchivo, y se obtiene añadiendo "x-mie-" al tipo MIME del subarchivo. Por ejemplo, con un subarchivo de tipo "image/jpeg", el tipo MI

ME del archivo MIE es "image/x-mie-jpeg". Pero tener en cuenta que el "x-" no se duplica si el tipo MIME del subarchivo ya comienza con "x-". Así que un subarchivo con tipo MIME "image/x-raw" está contenido dentro de un archivo MIE de tipo "image/x-mie-ra
w", no "image/x-mie-x-raw". En el caso de múltiples documentos en un archivo MIE, el tipo MIME se toma del primer documento. Independientemente del tipo de subarchivo, todos los archivos en formato MIE deben tener una extensión de nombre de archivo ".MIE".

Niveles de

Soporte

Aplicaciones básicas de lectura/escritura MIE pueden optar por no proporcionar soporte para algunas características avanzadas del formato MIE. Características que pueden no ser soportadas por todo el software

son:
Compresi
ón
El software que no soporta compresión debe ignorar elementos y grupos comprimidos, pero debería ser capaz de procesar la información
restante.
Longitudes de datos
grandes
Algunos software pueden limitar el tamaño máximo de un grupo o elemento MIE. Históricamente, un límite de 2GB puede ser impuesto
por algunos sistemas. Sin embargo, las longitudes de datos de 8 bytes deberían ser soportadas por todas las aplicaciones siemp
re que el valor no exceda el límite del sistema. (ej. Para sistemas con un límite de 2GB, las longitudes de datos de 8 bytes deb
erían ser soportadas si los 17 bits superiores son todos cero.) Si se encuentra una longitud de datos por encima del límite del
sistema, puede ser necesario que la aplicación detenga el procesamiento si no puede buscar el siguiente elemento en el archivo.

ExifTool.

Encapsulando Información con Datos en un Archivo

MIE

El siguiente comando encapsula cualquier archivo reconocido por ExifTool dentro de un archivo MIE, e inicializa las etiquetas MIE desde la información dentro del

archivo: 
exiftool -o new.mie -tagsfromfile FILE '-mie:all<all' \
    '-subfilename<filename' '-subfiletype<filetype' \
    '-subfilemimetype<mimetype' '-subfiledata<=FILE
'

donde "FILE" es el nombre del

archivo.

Para archivos no reconocidos, este comando puede ser

usado: 
exiftool -o new.mie -subfilename=FILE -subfiletype=TYPE \
    -subfilemimetype=MIME '-subfiledata<=FILE
'

donde "TYPE" y "MIME" representan el tipo de archivo de origen y el tipo MIME

respectivamente
.

Añadiendo un Trailer MIE a un

Archivo

El formato MIE también puede ser usado para almacenar información en un trailer añadido a otro tipo de archivo. Tener en cuenta que los trailers pueden no ser compatibles con todos los formatos de archivo, pero JPEG y TIFF son dos formatos donde la información de trailer adicional no crea ningún problema para el análisis normal del archivo. También tener en cuenta que esta técnica tiene la desventaja de que la información del trailer comúnmente se pierde si el archivo es posteriormente editado por otro

software.

Crear un trailer MIE con ExifTool es un proceso de dos pasos ya que ExifTool actualmente no puede ser usado para añadir un trailer MIE directamente. El ejemplo a continuación ilustra los pasos para añadir un trailer MIE con una imagen de vista previa pequeña ("small.jpg") a una imagen JPEG de destino ("dst.jp

g").

Paso 1) Crear un archivo MIE con un TrailerSignature que contenga la información

deseada: 
exiftool -o new.mie -trailersignature=1 -tagsfromfile small.jpg \
    '-previewimagetype<filetype' '-previewimagesize<imagesize' \
    '-previewimagename<filename' '-previewimage<=small.
jpg'

Paso 2) Adjunte la información MIE a otro archivo. En Unix, esto se puede hacer con el comando

'cat': 
cat new.mie >> dst.
jpg

Una vez añadido, ExifTool puede usa

rse para editar o eliminar un remate
MIE en una imagen JPEG o TIFF.

Múltiples Documentos MIE en un Solo

Archivo

La especificación MIE permite que múltiples documentos MIE (o remates) existan en un solo archivo. Un archivo así puede crearse simplemente concatenando documentos MIE. ExifTool puede usarse para acceder a la información en un documento específico añadiendo un número de copia al nombre del grupo MIE. Por

ejemplo: 
# escribir la etiqueta Author en el segundo documento MIE
exiftool -mie2:author=phil test.mie # eliminar el primer
documento MIE de un archivo exiftool -mie1:all= test.mie

Unidades de

Medida

Algunas etiquetas MIE permiten que los valores se especifiquen en diferentes unidades de medida. En el formato de archivo MIE estas unidades se combinan con el nombre de la etiqueta, pero al usar ExifTool se especifican entre corchetes después del

valor: 
exiftool -mie:gpsaltitude='7500(ft)' test.
mie

Si no se proporcionan unidades, se escriben las unidades

predeterminadas
.

Texto

Localizado

Los valores de texto localizado se acceden añadiendo un código de idioma/país al nombre de la etiqueta. Por

ejemplo: 
exiftool -com
ment-en_us='t
his is a comm
ent' test.mie
