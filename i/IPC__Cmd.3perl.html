$path = can_run( PROGRAM )

;

"can_run" toma solo un argumento: el nombre de un binario que deseas localizar. "can_run" funciona de manera similar al binario de unix "which" o al comando de bash "type", que escanea tu ruta, buscando el binario

solicitado.

A diferencia de "which" y "type", esta función es independiente de la plataforma y también funcionará, por ejemplo, en

Win32.

Si se llama en un contexto escalar, devolverá la ruta completa al binario que pediste si se encontró, o "undef" si no se

encontró.

Si se llama en un contexto de lista y la variable global $INSTANCES tiene un valor verdadero, devolverá una lista de las rutas completas a las instancias del binario donde se encontraron en "PATH", o una lista vací

a si no se
encontró.

$hashref = run_forked( COMMAND, { child_stdin => SCALAR, timeout => DIGIT, stdout_handler => CODEREF, stderr_handler => CODEREF} )

"run_forked" se utiliza para ejecutar algún programa o un coderef, opcionalmente alimentarlo con alguna entrada, obtener su código de retorno y salida (tanto stdout como stderr en búferes separados). Además, permite terminar el programa si tarda demasiado en

finalizar.

La característica importante y distintiva de run_forked es el tiempo de espera de ejecución, que al principio parece ser una tarea bastante simple, pero si piensas que el programa que estás generando podría generar algunos hijos propios (que a su vez podrían hacer lo mismo y así sucesivamente), resulta que no es un problema

sencillo.

"run_forked" está diseñado para sobrevivir y terminar con éxito casi cualquier tarea de larga duración, incluso una bomba de fork en caso de que tu sistema tenga los recursos para sobrevivir durante el tiempo de espera

especificado.

Esto se logra creando un proceso de vigilancia separado que genera el programa especificado en una sesión de proceso separada y lo supervisa: opcionalmente lo alimenta con entrada, almacena su código de salida, stdout y stderr, lo termina en caso de que se ejecute durante más tiempo del

especificado.

La invocación requiere que se ejecute el comando o un coderef y opcionalmente un hashref de

opciones:
"timeou
t"
Especifica en segundos cuánto tiempo debe ejecutarse el comando antes de que se le envíe SIG_KILL (9), lo que lo termina efectivamente a él y a todos sus hijos (directos o indirectos)
.
"child_stdi
n"
Especifica algún texto que se pasará a la "STDIN" del programa
ejecutado.
"stdout_handl
er"
Coderef de una subrutina a llamar cuando se recibe una porción de datos en STDOUT desde el programa en
ejecución.
"stderr_handl
er"
Coderef de una subrutina a llamar cuando se recibe una porción de datos en STDERR desde el programa en
ejecución.
"wait_loop_callba
ck"
Coderef de una subrutina a llamar dentro del bucle de espera principal (mientras "run_forked" espera a que el externo termine o falle). Es útil para detener el proceso externo antes de que termine por sí mismo, p. ej. 
my $r = run_forked("some external command", {

CÓMO

FUNCIONA

"run" intentará ejecutar tu comando utilizando la siguiente

lógica:
  • Si tienes "IPC::Run" instalado, y la variable $IPC::Cmd::USE_IPC_RUN está establecida en true (Consulte la sección "Variables Globales") úsalo para ejecutar el comando. Tendrás la salida completa disponible en los búferes, los comandos interactivos seguramente funcionarán y se garantiza que tus configuraciones de verbosidad se respetarán
    • limpiamente.
  • De lo contrario, si la variable $IPC::Cmd::USE_IPC_OPEN3 está establecida en true (Consulte la sección "Variables Globales"), intenta ejecutar el comando usando IPC::Open3. Los búferes estarán disponibles en todas las plataformas, los comandos interactivos seguirán ejecutándose limpiamente, y también tus configuraciones de verbosidad se adherirán
    • bien;
  • De lo contrario, si tienes el argumento "verbose" establecido en true, recurrimos a una simple llamada a system(). No podemos capturar ningún búfer, pero los comandos interactivos seguirán
    • funcionando.
  • De lo contrario, intentaremos redirigir temporalmente STDERR y STDOUT, hacer una llamada a system() con tu comando y luego reabrir STDERR y STDOUT. Este es el mét
    • odo de último recurso y aún te permitirá
ejecutar tus comandos limpiamente. Sin e
mbargo, no habrá búferes disponibles.

Espacios en blanco y IPC::Open3 / system
()
Al usar "IPC::Open3" o "system", si proporcionas una cadena como el argumento "command", se asume que está escapada adecuadamente. Puedes usar la constante "QUOTE" como carácter de cita portátil (ver arriba). Sin embargo, si proporcionas una referencia a un array, se aplican reglas especiales:

Si tu comando contiene caracteres especiales (< > | &), se convertirá internamente en una cadena antes de ejecutar el comando, para evitar que estos caracteres especiales sean escapados y pasados como argumentos en lugar de conservar su significado

especial.

Sin embargo, si el comando contenía argumentos que contenían espacios en blanco, convertir el comando en una cadena pierden la importancia de los espacios en blanco. Por lo tanto, "IPC::Cmd" pondrá entre comillas cualquier argumento que contenga espacios en blanco en tu c

omando si el comando se pasa como una refer
encia a un array y contiene caracteres especiales.
Espacios en blanco y IPC::
Run
Al usar "IPC::Run", si proporcionas una cadena como el argumento "command", la cadena se dividirá por espacios en blanco para determinar los elementos individuales de tu comando. Aunque esto generalmente hará lo que quieres decir, puede fallar si tienes archivos o comandos con espacios en blanco en ellos.

Si no deseas que esto ocurra, deberías proporcionar una referencia a un array, donde todas las partes de tu comando ya estén separadas. Sin embargo, ten en cuenta que, si hay espacios en blanco extra o espurios en estas partes, el analizador o el código subyacente puede no interpretarlo correctamente y causar un

error.
