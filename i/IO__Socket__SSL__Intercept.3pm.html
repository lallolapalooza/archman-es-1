SINOPSI

S 
use IO::Socket::SSL::Intercept;
# crear interceptor con certificados proxy
my $mitm = IO::Socket::SSL::Intercept->new(
    proxy_cert_file => 'proxy_cert.pem',
    proxy_key_file  => 'proxy_key.pem',
    ...
);
my $listen = IO::Socket::INET->new( LocalAddr => .., Listen => .. );
while (1) {
    # aceptar nuevo cliente TCP
    my $client = $listen->accept or next;
    # conectar SSL con el servidor
    my $server = IO::Socket::SSL->new(
        PeerAddr => ..,
        SSL_verify_mode => ...,
        ...
    ) or die "ssl connect failed: $!,$SSL_ERROR";
    # clonar certificado del servidor
    my ($cert,$key) = $mitm->clone_cert( $server->peer_certificate );
    # y actualizar el lado del cliente a SSL con el certificado clonado
    IO::Socket::SSL->start_SSL($client,
        SSL_server => 1,
        SSL_cert => $cert,
        SSL_key => $key
    ) or die "upgrade failed: $SSL_ERROR";
    # ahora transferir datos entre $client y $server y analizar
    # los datos sin cifrar
    ...
}

DESCRIPCIÓ

N

Este módulo proporciona funcionalidad para clonar certificados y firmarlos

con un certificado proxy, haciendo así fácil interceptar conexiones SSL (hom
bre en el medio). También gestiona una caché de los certificados generados.

Cómo funciona la intercepción

SSL

Interceptar conexiones SSL es útil para analizar tráfico cifrado por razones de seguridad o para pruebas. No rompe la seguridad de extremo a extremo de SSL, p. ej. un cliente correctamente escrito notará la intercepción a menos que configure explícitamente el cliente para que confíe en su interceptor. La intercepción SSL funciona de la siguiente

manera:
  • Crear un nuevo certificado CA, que se usará para firmar los certificados clonados. Este certificado CA proxy debería ser de confianza para el cliente, o (un cliente correctamente escrito) lanzará mensajes de error o denegará las conexiones porque detectó un ataque de hombre en el medio. Debido a la forma en que funciona la intercepción, no es posible soporte para certificados del lado del cliente.

    Usando openssl, un certificado CA proxy y clave privada así pueden

    crearse con: 
    openssl genrsa -out proxy_key.pem 1024
openssl req -new -x509 -extensions v3_ca -key
    proxy_key.pem -out proxy_cert.pem # exportar como PKCS12 para importar en el navegad
    • or openssl pkcs12 -export -in proxy_cert.pem -inkey proxy_key.pem -out proxy_cert.p12
  • Configurar el cliente para que se conecte usando el proxy interceptante o de algún modo redirigir las conexiones desde el cliente al proxy (p. ej. redirecciones con filtros de paquetes, suplantación ARP o DNS
    • etc).
  • Aceptar la conexión TCP desde el cliente, p. ej. no realizar ningún protocolo de enlace SSL con el cliente
    • todavía.
  • Establecer la conexión SSL con el servidor y verificar el certificado del servidor como de costumbre. Luego crear un nuevo certificado basado en el certificado original del servidor, pero firmado por su CA proxy. Este es el paso donde IO::Socket::SSL::Intercept
    • ayuda.
  • Actualizar la conexión TCP con el cliente a SSL usando el certificado clonado del servidor. Si el cliente confía en su CA proxy aceptará la actualización a
    • SSL.
  • Transferir datos entre cliente y servidor. Mient
    • ras las conexiones con cliente y servidor
están ambas cifradas con SSL, leerá/escribirá lo
s datos sin cifrar en su aplicación proxy.

serial
INTEGER|CODE
Este argumento opcional da el punto de partida para los números de serie de los certificados recién creados. Si no se establece, el número de serie se creará basado en el resumen del certificado original. Si el valor es código, se llamará con "serial(original_cert,CERT_asHash(original_cert))" y debería devolver el nuevo número de
serie.
cache HASH |
SUBROUTINE
Este argumento opcional da una forma de cachear certificados creados, para que no se vuelvan a crear en accesos futuros al mismo host. Si el argumento no se da, se usa un HASH interno.

Si el argumento es un hash, almacenará para cada certificado generado una referencia hash con "cert" y "atime" en el hash, donde "atime" es el tiempo del último acceso (para expirar entradas sin uso) y "cert" es el certificado. Tenga en cuenta que el certificado está en el formato X509 interno de Net::SSLeay y por lo tanto no se puede simplemente volcar y restaurar. La clave para el hash es un "ident" dado a "clone_cert" o generado del certificado

original.

Si el argumento es una subrutina, se llamará como "$cache->(ident,sub)". Esta llamada debería devolver un "(cert,key)" existente (en caché) o llamar a "sub" sin argumentos para crear un nuevo "(cert,key)", almacenarlo y devolverlo. Si se llama con $cache->('type') la función debería simplemente devolver 1 para señalar

que soporta el tipo actual de c
aché. Si en su lugar no devuelve nada, s
e asume la interfaz de caché má
s antigua por razones de compatibilidad.
