DESCRIPCIÓ

N

La biblioteca Image::Size está basada en el script "wwwis" escrito por Alex Knowles (alex@ed.ac.uk), una herramienta para examinar HTML y añadir los parámetros 'width' y 'height' a las etiquetas de imagen. Los tamaños se almacenan internamente en caché basándose

en el nombre del archivo, de modo que múltiples llamadas sobre el mismo nombre de archivo (
como imágenes usadas en listas con viñetas, por ejemplo) no resultan en cálculos repetidos.

SUBRUTINAS/MÉTODO

S

Image::Size proporciona tres interfaces para

importar:
imgsize(fluj
o)
Devuelve una lista de tres elementos con las dimensiones X e Y (ancho y alto, en ese orden) y el tipo de imagen de flujo. Los errores se señalan mediante valores indefinidos (undef) para los dos primeros elementos, y una cadena de error en el tercero. El tercer elemento puede ser (y usualmente es) ignorado, pero es útil al dimensionar datos cuyo tipo es
desconocido.
html_imgsize(fluj
o)
Devuelve el ancho y el alto (X e Y) de flujo preformateados como una sola cadena 'width="X" height="Y"' adecuada para añadir a etiquetas IMG HTML generadas. Si la llamada subyacente a "imgsize" falla, undef es devuelto. El formato devuelto es adecuado tanto para HTML como para
XHTML.
attr_imgsize(fluj
o)
Devuelve el ancho y el alto de flujo como parte de una lista de 4 elementos útil para rutinas que usan tablas hash para la manipulación de parámetros con nombre, como las bibliotecas Tk o CGI. Un valor de retorno típico se parece a "("-width", X, "-height", Y)". Si la llamada subyacente a "imgsize" falla, undef es
dev
uelto.

Por defecto, solo imgsize() es exportado. Cualquiera de las tres o una combinación de ellas puede ser importada explícitamente, o las tres pueden serlo con la etiqueta :al

l.

Adicionalmente, si el módulo Image::Magick está presente, los tipos de archivo soportados por él también son soportados por Image::Size. Ver también

"ADVERTENCIAS".

Al usar la interfaz "imgsize", hay un tercer valor no usado devuelto si el programador desea guardarlo y examinarlo. Este valor es la identidad del tipo de dato, expresada como una abreviatura de 2-3 letras como la listada arriba. Esto es útil cuando se opera con manejadores de archivo abiertos o datos en memoria, donde el tipo es tan desconocido como el tamaño. Las dos rutinas de soporte ignoran este tercer valor de retorno, por lo que quienes deseen usarlo deben usar la rutina base "imgsize"

.

Nótese que cuando se usa el respaldo de Image::Magick (para todos los archivos no soportados nativamente), la identidad del tipo de dato proviene directamente del parámetro 'format' reportado por Image::Magick, por lo que puede no cumplir el formato de abreviatura de 2-3 letras. Por ejemplo

, un archivo WBMP podría ser reportado como
'Wireless Bitmap (level 0) image' en este caso.

Almacenamiento en caché de información y

$NO_CACHE

Cuando se pasa un nombre de archivo a cualquiera de las rutinas de dimensionado, el comportamiento por defecto de la biblioteca es almacenar en caché la información resultante. El tiempo de modificación del archivo también se registra, para determinar si la caché debe ser purgada y actualizada. Esto fue añadido originalmente debido a que un número de aplicaciones CGI usaban esta biblioteca para generar atributos para páginas que a menudo usaban el mismo elemento gráfico muchas

veces.

Sin embargo, el almacenamiento en caché puede llevar a problemas cuando los archivos son generados dinámicamente, a una tasa que excede la resolución del valor del tiempo de modificación en el sistema de archivos. Así, la variable de control opcionalmente importable $NO_CACHE ha sido introducida. Si este valor es cualquiera que evalúe a un valor no falso (ya sea el valor 1, cualquier cadena no nula, etc.) entonces el almacenamiento en caché se deshabilita hasta tal momento en que el programa lo vuelva a habilitar estableciendo el valor a

falso.

El parámetro $NO_CACHE puede ser importado como con la rutina imgsize, y también es importado al usar la etiqueta de importación ":all". Si el programador elige no importarlo, aún es accesible por el nombre de paquete completamente calificado, $Image::Size::NO_CACHE

.

Compartiendo la Caché entre

Procesos

Si estás utilizando Image::Size en un entorno de múltiples hilos o múltiples procesos, es posible que desees habilitar el intercambio de la información en caché entre los procesos (o hilos). Image::Size no proporciona de forma nativa ninguna facilidad para esto, ya que añadiría a la lista de

dependencias.

Para hacer posible que los usuarios hagan esto por sí mismos, la tabla hash %CACHE que Image::Size usa internamente para almacenamiento puede ser importada en la declaración use. El usuario puede entonces hacer uso de paquetes como IPC::MMA (IPC::MMA) que pueden "vincular" (tie) un hash a un segmento de memoria

compartida: 
use Image::Size qw(imgsize %CACHE);

Dimensionando Imágenes

PhotoCD

Con la versión 2.95, se incluye soporte para el formato de imagen Kodak PhotoCD. Sin embargo, estos archivos de imagen no son exactamente como los demás. Un archivo es la fuente de la imagen en cualquiera de un rango de resolpredefinidas (todas con la misma relación de aspecto). Soportar esto aquí es complicado, ya que no hay nada inherente en el archivo que lo limite a una resolución

específica.

La biblioteca aborda esto utilizando un mapeo de escala, y requiriendo que el usuario (tú) especifique qué escala es preferida para la devolución. Al igual que la configuración $NO_CACHE descrita anteriormente, esta es una variable escalar importable que puede ser usada dentro de la aplicación que utiliza Image::Size. Este parámetro se llama $PCD_SCALE, y es importado con el mismo nombre. También es importado cuando se utiliza la etiqueta ":all" o puede ser referenciado como $Image::Size::PCD_SCALE

.

El parámetro debe ser establecido a uno de los siguientes

valores: 
base/16
base/4
base
base4
base16
base64

Ten en cuenta que no todos los discos PhotoCD incluirán la resolución "base64". Las resoluciones reales no se listan aquí, ya que son constantes y pueden encontrarse en cualquier documentación sobre el formato PCD. El valor de $PCD_SCALE se trata de manera insensible a mayúsculas y minúsculas, así que "base" es lo mismo que "Base" o "BaSe". La escala por defecto está establecida en "base"

.

También ten en cuenta que la biblioteca no hace ningún esfuerzo por leer suficiente del archivo PCD para verificar que la resolución solicitada está d

isponible. El propósito de esta biblioteca es leer lo menos necesario para operar de manera eficiente. Por lo tanto, la única diferencia real que se
puede encontrar es en si la orientación de la imagen es vertical u horizontal. Eso es de hecho todo lo que la biblioteca extrae del archivo de imagen.

Controlando el Comportamiento con Imágenes

GIF

Las imágenes GIF presentan una situación algo inusual cuando se trata de leer el tamaño. Debido a que los GIFs pueden ser una serie de sub-imágenes para reproducirse como una secuencia animada, ¿qué parte quiere el usuario obtener el

tamaño?

Al tratar con archivos GIF, el usuario puede controlar el comportamiento estableciendo el valor global $Image::Size::GIF_BEHAVIOR. Al igual que la configuración PCD, este puede ser importado al cargar la biblioteca. Tres valores son reconocidos por el código que maneja los

GIFs:
0
Este es el valor por defecto. Cuando se elige este valor, las dimensiones devueltas son las de la "pantalla". La "pantalla" es el área de visualización que el GIF declara en el primer bloque de datos del archivo. Ninguna sub-imagen será mayor que esto en tamaño; si lo son, la especificación dicta que deben ser recortadas para caber dentro de la caja.

Este es también el método más rápido para di

mensionar el GIF, ya que lee la men
or cantidad de datos del flujo de la imagen.
1
Si se establece este valor, entonces se devuelve el tamaño de la primera sub-imagen dentro del GIF. Para archivos GIF planos (no animados), esto sería lo mismo que la pantalla (aunque no tiene que serlo, estrictamente hablando).

Cuando se lee el primer bloque descriptor de imagen, el cód

igo devuelve inmediatamente, haciendo esto solo un
poco menos eficiente que la configuración anterior.
2
Si se elige este valor, entonces el código recorre todas las sub-imágenes del GIF animado, y devuelve las dimensiones de la más grande de ellas.

Esta opción requiere que se

lea la imagen GIF completa, p

se encuentra la más grande.

Cualquier valor fuera de este rango producirá un error en el código GIF antes de que se lea cualquier dato de

imagen.

El valor de las dimensiones distintas de

la ventana de visualización ("panta
lla") es dudoso. Sin embargo, algunos us
uarios han pedido esa funcionalidad.

Image::Size Y SERVIDORES

WEB

Hay algunos enfoques para sacar el máximo partido a Image::Size en un entorno de servidor web de múltiples procesos. Los dos más comunes son el pre-caché y el uso de memoria compartida. Estos ejemplos se centran en Apache, pero deberían ser adaptables a otros enfoques de servidores

también.

Pre-Caché de Datos de

Imagen

Un enfoque es incluir código en un script de inicio de Apache que lea la información de todas las imágenes de antemano. Un script cargado a través de "PerlRequire", por ejemplo, se convierte en parte de la memoria del servidor antes de que se creen los procesos hijos. Cuando los hijos son creados, entran en existencia con una caché pre-inicializada ya

disponible.

La desventaja de este enfoque es que tienes que planificar de antemano qué archivos de imagen necesitas poner en caché. Además, si la lista es lo suficientemente larga, puede ralentizar el tiempo de inicio del

servidor.

La ventaja es que mantiene la información centralizada en

un solo lugar y por lo tanto más fácil de gestionar
y mantener. También no requiere módulos CPAN adicionales.

Caché con Memoria

Compartida

Otro enfoque es introducir un segmento de memoria compartida al que los procesos individuales todos tienen acceso. Esto se puede hacer con cualquiera de una variedad de módulos de memoria compartida en

CPAN.

Probablemente la forma más fácil de hacer esto es usar uno de los paquetes que permiten vincular (tie) un hash a un segmento de memoria compartida. Puedes usar esto en combinación con la importación de la variable de tabla hash que es usada por Image::Size para la caché, o puedes referirte a ella explícitamente por su nombre completo de

paquete: 
use IPC::Shareable;
use Image::Size;
tie %Image::Size::CACHE, 'IPC::Shareable', 'size', { create => 1 }
;

Ese ejemplo usa IPC::Shareable (ver IPC::Shareable) y usa la opción para el comando "tie" que le dice a IPC::Shareable que cree el segmento. Una vez que el proceso inicial del servidor comienza a crear hijos, todos compartirán el manejador vinculado al segmento de

memoria.

Otro paquete que proporciona esta capacidad es IPC::MMA (ver IPC::MMA), que proporciona gestión de memoria compartida a través de la biblioteca mm de Ralf Engelschall (los detalles están disponibles en la documentación de IPC::MMA)

: 
use IPC::MMA;
use Image::Size qw(%CACHE);
my $mm = mm_create(65536, '/tmp/test_lockfile');
my $mmHash = mm_make_hash($mm);
tie %CACHE, 'IPC::MM::Hash',
$mmHash;

Como antes, esto se hace en la fase de ini

cio del servidor web. A medida que se
crean los procesos hijos, heredan el pun
tero al segmento compartido existente.

MÁS

EJEMPLOS

La interfaz attr_imgsize también es muy adecuada para usar con la extensión

Tk: 
$image = $widget->Photo(-file => $img_path, attr_imgsize($img_path))
;

Dado que las clases "Tk::Image" usan nombres de opciones con guiones como "CGI", no se necesita ninguna traducción

adicional.

Este paquete también es muy adecuado para su uso dentro de un contexto de servidor web Apache. Los tamaños de archivo se ponen en caché al leerlos (con una comprobación contra la hora de modificación del archivo, en caso de cambios), una característica útil para un entorno mod_perl en el que un proceso hijo perdura más allá de la vida útil de una sola petición. Otros aspectos del entorno mod_perl cooperan bien con este módulo, como la capacidad de usar una sub-petición para obtener la ruta completa de un archivo dentro del espacio del servidor. Esto complementa las capacidades de generación de HTML del módulo CGI, en el que "CGI::img" quiere una URL pero "attr_imgsize" necesita una ruta de

archivo: 
# Assume $Q is an object of class CGI, $r is an Apache request object.
# $imgpath is a URL for something like "/img/redball.gif".
$r->print($Q->img({ -src => $imgpath,
                    attr_imgsize($r->lookup_uri($imgpath)->filename) }))
;

La ventaja aquí, además de no tener que codificar la raíz de documentos del servidor

, es que Apache pasa la sub-petición a través del ciclo de vida de la petición habi
tual, incluyendo cualquier etapa que reescriba la URL o la modifique de otra manera.

DIAGNÓSTICO

S

La rutina base, "imgsize", devuelve undef como el primer valor en su lista cuando ha ocurrido un error. El tercer elemento contiene un mensaje de error

descriptivo.

Las otras dos rutinas simplemente devuelven undef en caso

de
error.

ADVERTENCI

AS

El caché de datos de tamaño solo se puede hacer en entradas que son nombres de archivos. Los manejadores de archivos abiertos y las referencias a escalares no pueden ser transformados de manera fiable en una clave única para la tabla de datos de caché. Los búfers podrían ser puestos en caché usando el módulo MD5, y quizás en el futuro haga eso una opción. Sin embargo, no deseo alargar la lista de dependencias con otro elemento en este

momento.

Dado que Image::Magick opera sobre nombres de archivos, no manejadores, el uso de él está restringido a los casos en los que la entrada a "imgsize" se proporciona

como nombre
de archivo.
