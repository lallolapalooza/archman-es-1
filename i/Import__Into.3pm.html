Import::Into - Im

portar paquetes

SINOPSI

S 
package My::MultiExporter;
use Import::Into;
# simple
sub import {
  Thing1->import::into(scalar caller);
}
# múltiple
sub import {
  my $target = caller;
  Thing1->import::into($target);
  Thing2->import::into($target, qw(import arguments));
}
# por nivel
sub import {
  Thing1->import::into(1);
}
# con Exporter
use base qw(Exporter);
sub import {
  shift->export_to_level(1);
  Thing1->import::into(1);
}
# sin My::MultiExporter == sin Thing1
sub unimport {
  Thing1->unimport::out_of(scalar caller);
}

Las personas que quieran reexportar su módulo también deberían estar usando Import::Into. Cualquier exportador o pragma funcionará sin

problemas.

Nota: No necesita hacer ningún cambio en Thing1 para poder llamar "import::into" en él. Este es un método global, y se puede invocar en cualquier paquet

e (y de hecho en cualquier objeto tambié
n, aunque es menos común que quiera hacerlo).

DESCRIPCIÓ

N

Escribir exportadores es una molestia. Algunos usan Exporter, algunos usan Sub::Exporter, algunos usan Moose::Exporter, algunos usan Exporter::Declare ... y algunas cosas son

pragmas.

Exportar en nombre de otra persona es más difícil. Los exportadores no proporcionan una API consistente para esto, y los pragmas necesitan que se llame directamente a su método import, ya que afectan a la unidad actual de

compilación.

"Import::Into" proporciona métodos

globales para ha
cer esto indoloro.

$package->import::into( $target, @arguments )

;

Un método global, invocable en cualquier paquete. Carga e importa el paquete dado en $target. @arguments se pasan al método import del

paquete.

$target puede ser un nombre de paquete al que exportar, un entero para el nivel del llamador al que exportar, o una referencia a hash con las siguientes

opciones:
packa
ge
El paquete destino al que
exportar.
filena
me
El nombre de archivo aparente al que exportar. Algunos módulos exportadores, como autodie o strictures, se preocupan por el nombre de archivo al que se les
importa.
li
ne
El número de línea aparente al que exportar. Para combinarse con la opción "file
name".
lev
el
El nivel del llamador al que exportar. Esto rellenará automáticamente las opciones "package", "filename", y "line", haciéndola la opción más fácil y más
consistente.
versi
on
Un número de versión para comprobar en el módulo. El equivalente a especificar el número de versión en una línea
"
use
".

;

Equivalente a "import::into", pero despacha al método "unimport" de $package en lugar de "imp

o
rt
".

POR QUÉ USAR ESTE

MÓDULO

Las APIs para los módulos exportadores no son consistentes. Las subclases de Exporter proporcionan export_to_level, pero si sobrescribieron su método import, todas las apuestas están anuladas. Sub::Exporter proporciona un parámetro into, pero averiguar que algo lo usó no es trivial. Los pragmas necesitan que se llame directamente a su método "import" ya que afectan a la unidad actual de

compilación.

Es ...

molesto.

Sin embargo, hay un enfoque que realmente funciona para todos estos

tipos. 
eval "package $target; use $thing;
"

funcionará para cualquier cosa que compruebe caller, que es todo excepto los pragmas. Pero no funciona para los pragmas - los pragmas

necesitan: 
$thing->
import;

porque están diseñados para afectar al código que se está compilando actualmente - así que dentro de un eval, ese es el ámbito del propio eval, no el módulo que acaba de "use"arle - así

que 
sub import {
  eval "use strict;"
}

no hace lo que quería,

pero 
sub import {
  strict->import;
}

aplicará strict al archivo que llama

correctamente.

Por supuesto, ahora tiene dos problemas nuevos - primero, que todavía necesita saber si algo es un pragma, y segundo, que no puede usar cualquiera de estos enfoques por sí solos en algo como Moose o Moo que es tanto un exportador como un

pragma.

Así que, una solución para eso

es: 
use Module::Runtime;
my $sub = eval "package $target; sub { use_module(shift)->import(\@_) }";
$sub->($thing, @import_args)
;

lo que significa que import se llama desde el lugar correcto para que los pragmas tengan efecto, y desde el paquete correcto para que la comprobación de caller funcione - y así se comporta correctamente para todos los tipos de exportador, para los pragmas, y para los

híbridos.

Adicionalmente, algunas rutinas de import comprueban el nombre de archivo al que se les importa. Esto se puede tratar generando una directiva #line en el eval, lo que cambiará lo que "caller" informa para el nombre de archivo cuando se llama en el importador. El nombre de archivo y el número de línea a usar en la directiva entonces necesitan ser obtenidos usando "caller"

: 
my ($target, $file, $line) = caller(1);
my $sub = eval qq{
  package $target;
#line $line "$file"
  sub { use_module(shift)->import(\@_) }
};
$sub->($thing, @import_args)
;

Y necesita alternar entre estas implementaciones dependiendo de si está apuntando a un paquete específico, o a algo en su pila de

llamadas.

Recordar todo esto, sin embargo, es excesivamente irritante. Así que escribí un módulo para no tener que hacerlo más. Cargar Import::Into crea un método global "import::into" que puede llamar en cualquier paquete para importarlo en otro paquete. Así que ahora puede simplemente

escribir: 
use Import::Into;
$thing->import::into($target, @import_args)
;

Esto funciona debido a cómo perl resuelve las llamadas a métodos - una llamada a un nombre de método simple se resuelve contra el paquete de la clase u objeto, así

que 
$thing->method_name(@args)
;

es aproximadamente equivalente

a: 
my $code_ref = $thing->can('method_name');
$code_ref->($thing, @args)
;

mientras que si se encuentra un "::", la búsqueda se hace relativa al nombre del paquete (es decir, todo antes del último "::") así

que 
$thing->Package::Name::method_name(@args)
;

es aproximadamente equivalente

a: 
my $code_ref = Package::Name->can('method_name');
$code_ref->($thing, @args)
;

Así que dado que Import::Into define un método "into" en el paquete "import", la sintaxis llama confiablemente a

ese.

Para más locura de este tipo, eche un vistazo al artículo que escribí en http://shadow.cat/blog/matt-s-trout/madness-with-methods que cubre el abuso de coderefs y la sintaxis "${\...}

".

Y eso

es
todo.
