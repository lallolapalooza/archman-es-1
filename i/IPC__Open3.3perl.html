IPC::Open3(3perl) Guía de referencia para programadores de Perl IPC::Open3(3perl)

NOMBRE

IPC::Open3 - abre un proceso para lectura, escritura y manejo de errores usando open3()

SINOPSIS

use Symbol 'gensym'; # vivifica un manejador separado para STDERR
my $pid = open3(my $chld_in, my $chld_out, my $chld_err = gensym,
                'some', 'cmd', 'and', 'args');
# o pasa el comando a través del shell
my $pid = open3(my $chld_in, my $chld_out, my $chld_err = gensym,
                'some cmd and args');
# lee desde la entrada estándar del padre
# envía STDOUT y STDERR a un manejador ya abierto
open my $outfile, '>>', 'output.txt' or die "open failed: $!";
my $pid = open3(['&', *STDIN], ['&', $outfile], undef,
                'some', 'cmd', 'and', 'args');
# escribe a la salida estándar y error estándar del padre
my $pid = open3(my $chld_in, ['&', *STDOUT], ['&', *STDERR],
                'some', 'cmd', 'and', 'args');
# recolecta el zombie y recupera el estado de salida
waitpid( $pid, 0 );
my $child_exit_status = $? >> 8;

DESCRIPCIÓN

Extremadamente similar a "open2" de IPC::Open2, "open3" inicia el comando dado y proporciona manejadores de archivo para interactuar con los flujos de E/S estándar del comando.

my $pid = open3($chld_in, $chld_out, $chld_err, @command_and_args);

Conecta $chld_in para escribir en la entrada estándar del hijo, $chld_out para leer de la salida estándar del hijo, y $chld_err para leer del flujo de error estándar del hijo. Si $chld_err es falso, o el mismo descriptor de archivo que $chld_out, entonces "STDOUT" y "STDERR" del hijo están en el mismo manejador de archivo. Esto significa que no puedes pasar una variable no inicializada para $chld_err y hacer que "open3" genere automáticamente un manejador de archivo para ti, pero gensym de Symbol se puede usar para vivificar una nueva referencia glob; véase "SINOPSIS". El manejador $chld_in tendrá autoflush activado.

Por defecto, los manejadores de archivo que pasas se usan como parámetros de salida. "open3" crea internamente tres pipes. El extremo de escritura del primer pipe y los extremos de lectura de los otros pipes se conectan a la entrada/salida/error estándar del comando, respectivamente. Los extremos de lectura y escritura correspondientes se colocan en los tres primeros argumentos de "open3".

Los argumentos del manejador de archivo pueden tomar las siguientes formas:

  • Una variable no inicializada (técnicamente, tanto "undef" como la cadena vacía funcionarán): "open3" genera un nuevo manejador de archivo y lo asigna al argumento, que debe ser una variable modificable para que esto funcione (de lo contrario, se generará una excepción).

    Esto no funciona para $chld_err, sin embargo: Si el argumento $chld_err es un valor falso, el flujo de error del hijo se redirige automáticamente a su salida estándar.

  • Un manejador existente en forma de glob de tipo como *STDIN o *FOO o una referencia a uno de ellos: "open3" coloca el manejador de archivo en la ranura "IO" del glob de tipo, lo que significa que el manejador de archivo desnudo correspondiente (como "STDIN" o "FOO") puede usarse para E/S desde/hacia el proceso hijo. (Si el manejador ya está abierto, se cierra automáticamente primero).
  • Una cadena que contiene el nombre de un manejador desnudo (como 'STDIN' o 'FOO'): Dichas cadenas se resuelven a globs de tipo en tiempo de ejecución y luego actúan como el caso descrito anteriormente.

Sin embargo, es posible hacer que "open3" use un manejador existente directamente (como argumento de entrada) y omitir la creación de un pipe. Para hacer esto, el argumento del manejador de archivo debe tener una de las siguientes dos formas:

  • Una referencia de matriz como "['&', $fh]", es decir, el primer elemento es la cadena '&' y el segundo elemento es el manejador existente que se utilizará en el proceso hijo.
  • Una cadena en la forma '<&FOO' o '>&FOO', es decir, una cadena que comienza con los dos caracteres "<&" (para entrada) o ">&" (para salida), seguidos del nombre de un manejador de archivo desnudo. (La forma de cadena no se puede usar con manejadores almacenados en variables.)

Si usa esta forma para $chld_in, el manejador de archivo se cerrará en el proceso padre.

Los manejadores de archivo también pueden ser enteros, en cuyo caso se entienden como descriptores de archivo.

"open3" devuelve el ID del proceso del proceso hijo. No devuelve en caso de error: simplemente genera una excepción que coincide con "/^open3:/". Sin embargo, los errores de "exec" en el hijo (como archivo inexistente o permiso denegado), solo se informan a $chld_err en Windows y OS/2, ya que no es posible capturarlos.

Si el proceso hijo muere por cualquier motivo, la próxima escritura a $chld_in probablemente generará una SIGPIPE en el padre, lo cual es fatal por defecto, por lo que es posible que desees manejar esta señal.

Nota: si especifica "-" como comando, de forma análoga a "open(my $fh, "-|")", el proceso hijo será simplemente el proceso Perl bifurcado en lugar de un comando externo. Esta característica aún no es compatible con las plataformas Win32.

"open3" no espera ni recolecta el proceso hijo después de que sale. Excepto para programas cortos donde es aceptable dejar que el sistema operativo se encargue de esto, debes hacerlo tú mismo. Normalmente, esto es tan simple como llamar a "waitpid $pid, 0" cuando hayas terminado con el proceso. No hacer esto puede resultar en una acumulación de procesos difuntos o "zombies". Consulte "waitpid" en perlfunc para obtener más información.

Si intentas leer desde el escritor de salida estándar del hijo y su escritor de error estándar, tendrás problemas con el bloqueo, lo que significa que querrás usar "select" o IO::Select, lo que significa que es mejor usar "sysread" en lugar de "readline" para cosas normales.

Esto es muy peligroso, ya que puedes bloquearte para siempre. "open3" asume que va a hablar con algo como bc(1), escribiéndole y leyéndole. Esto es presumiblemente seguro porque "sabes" que comandos como bc(1) leerán una línea a la vez y generarán una línea a la vez. Programas como sort(1) que leen todo su flujo de entrada primero, sin embargo, es muy probable que causen un interbloqueo.

El gran problema con este enfoque es que si no tienes control sobre el código fuente que se ejecuta en el proceso hijo, no puedes controlar lo que hace con el almacenamiento en búfer del pipe. Por lo tanto, no puedes simplemente abrir un pipe a "cat -v" y leer y escribir continuamente una línea desde él.
