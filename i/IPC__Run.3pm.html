NOMBRE

IPC::Run - system() y procesos en segundo plano con tuberías, redirecciones, ptys (Unix, Win32)

SINOPSIS

## Primero, un comando para ejecutar:
   my @cat = qw( cat );
## Usando run() en lugar de system():
   use IPC::Run qw( run timeout );
   run \@cat, \$in, \$out, \$err, timeout( 10 ) or die "cat: $?";
   # También se puede hacer I/O a refs de subrutinas y nombres de archivo:
   run \@cat, '<', "in.txt", \&out, \&err or die "cat: $?";
   run \@cat, '<', "in.txt", '>>', "out.txt", '2>>', "err.txt";
   # Redireccionando usando pseudo-terminales en lugar de tuberías.
   run \@cat, '<pty<', \$in,  '>pty>', \$out_and_err;
## Scripting de subprocesos (como Expect):
   use IPC::Run qw( start pump finish timeout );
   # Leer incrementalmente de / escribir a escalares. 
   # $in se vacía a medida que se alimenta a la entrada estándar de cat,
   # $out acumula la salida estándar de cat
   # $err acumula el error estándar de cat
   # $h es para "arnés".
   my $h = start \@cat, \$in, \$out, \$err, timeout( 10 );
   $in .= "alguna entrada\n";
   pump $h until $out =~ /input\n/g;
   $in .= "alguna entrada más\n";
   pump $h until $out =~ /\G.*more input\n/;
   $in .= "alguna entrada final\n";
   finish $h or die "cat devolvió $?";
   warn $err if $err; 
   print $out;         ## Toda la salida de cat
# Tubería entre hijos
   run \@cat, '|', \@gzip;
# Múltiples hijos simultáneamente (run() bloquea hasta que todos
# los hijos terminan, usa start() para ejecución en segundo plano):
   run \@foo1, '&', \@foo2;
# Llamar a \&set_up_child en el hijo antes de que ejecute el
# comando (solo funciona en sistemas con fork() y exec() reales)
# las excepciones lanzadas en set_up_child() se propagarán de vuelta
# al padre y se lanzarán desde run().
   run \@cat, \$in, \$out,
      init => \&set_up_child;
# Leer desde / escribir a manejadores de archivos que abres y cierras
   open IN,  '<in.txt'  or die $!;
   open OUT, '>out.txt' or die $!;
   print OUT "preámbulo\n";
   run \@cat, \*IN, \*OUT or die "cat devolvió $?";
   print OUT "postámbulo\n";
   close IN;
   close OUT;
# Crear tuberías para que tú leas / escribas (como IPC::Open2 & 3).
   $h = start
      \@cat,
         '<pipe', \*IN, # también puede ser un manejador de archivo léxico, p.ej. \my $infh
         '>pipe', \*OUT,
         '2>pipe', \*ERR 
      or die "cat devolvió $?";
   print IN "alguna entrada\n";
   close IN;
   print <OUT>, <ERR>;
   finish $h;
# Mezcla de modos de entrada y salida
   run \@cat, 'in.txt', \&catch_some_out, \*ERR_LOG;
# Otras construcciones de redirección
   run \@cat, '>&', \$out_and_err;
   run \@cat, '2>&1';
   run \@cat, '0<&3';
   run \@cat, '<&-';
   run \@cat, '3<', \$in3;
   run \@cat, '4>', \$out4;
   # etc.
# Pasar opciones:
   run \@cat, 'in.txt', debug => 1;
# Llamar al shell de este sistema, devuelve TRUE si el código de salida es 0
# ESTE ES EL SENTIDO OPUESTO DEL VALOR DE RETORNO de system()
   run "cat a b c" or die "cat devolvió $?";
# Lanzar un subproceso directamente, sin shell. No se puede hacer redirección
# con esta forma, está aquí para comportarse como system() con un
# resultado invertido.
   $r = run "cat a b c";
# Leer de un archivo a un escalar
   run io( "filename", 'r', \$recv );
   run io( \*HANDLE,   'r', \$recv );

DESCRIPCIÓN

IPC::Run permite ejecutar e interactuar con procesos hijos usando archivos, tuberías y pseudo-ttys. Se admiten tanto los usos de estilo system() como los de scripting, y pueden mezclarse. Del mismo modo, se admiten los estilos de API funcional y orientada a objetos, y también pueden mezclarse.

Se proporcionan varios operadores de redirección que recuerdan a los que se ven en las líneas de comando comunes de Unix y DOS.

INICIO RÁPIDO SIMPLE

Aquí tienes una guía rápida para el uso básico de la función run() de IPC::Run.

Capturar salida y errores de un comando externo

Supongamos que quieres ejecutar un comando en tu shell. Usaremos "ls" por simplicidad, aunque hay formas mucho mejores de obtener una lista de archivos, como la función glob() o el módulo File::Find.

La forma básica de run() tiene el comando y sus argumentos pasados como un arrayref en el primer argumento. El comando no puede ser una sola cadena.

@cmd = [ 'ls', '-a', '-l', '-r', '-t' ];    # Sí
@cmd = ( 'ls -a -l -r -t' );                # No

Después del comando, pasa una referencia escalar "\$in" para la entrada a pasar, y referencias escalares "\$out" y "\$err" para recibir el contenido de stdout y stderr.

use IPC::Run qw( run );
@cmd = qw( ls -l -a -r -t );
run( \@cmd, \$in, \$out, \$err ) or die $?;
print("\$err tiene ", length($err), " bytes de largo\n");
print($err, "\n");
print("\$out tiene ", length($out), " bytes de largo\n");
print($out, "\n");

Ejecutar esto mostrará algo como:

$err tiene 0 bytes de largo
$out tiene 1410 bytes de largo
total 392
drwxr-xr-x    3 andy  staff     96 Mar 17 11:53 .github
-rw-r--r--    1 andy  staff    158 Mar 17 11:53 .gitignore
... etc ...

Ten en cuenta que $out y $err siempre están definidos después de una llamada a run(), incluso si no reciben datos.

Pasar entrada al programa externo

Si tienes entrada para pasar, ponla en las variables $in. Por ejemplo, para usar el comando "wc" para contar líneas, palabras y caracteres en un bloque de texto:

$in = <<'CARROLL';
'Twas brillig, and the slithy toves
    Did gyre and gimble in the wabe:
All mimsy were the borogoves,
    And the mome raths outgrabe.
CARROLL
@cmd = qw( wc );
run( \@cmd, \$in, \$out, \$err ) or die $?;
print "$out";

Esto da la salida:

4      23     140

Manejar errores

Es importante comprobar el código de retorno de run() para ver si el comando se ejecutó correctamente. run() devuelve un booleano verdadero en caso de éxito y falso en caso de fallo. Ten en cuenta que esto es lo opuesto a system() de Perl, que devuelve 0 en caso de éxito y un valor distinto de cero en caso de fallos.

Para el código de error específico del subproceso, comprueba $? directamente.

@cmd = qw( tar xzvf nonexistent.tar );
if ( !run( \@cmd, \$in, \$out, \$err ) ) {
    print "\$? = $?\n";
    print "err = $err\n";
}

Ejecutar esto da:

$? = 256
err = tar: Error al abrir el archivo: No se pudo abrir 'nonexistent.tar'

Si el programa no existe, entonces run() hará "die" y no devolverá nada. Por ejemplo:

@cmd = qw( bogus-command );
my $rc = run( \@cmd, \$in, \$out, \$err );
print "run devolvió ", ($rc ? "verdadero" : "falso"), "\n";

Ejecutar esto no llega a la sentencia "print".

Comando 'bogus-command' no encontrado en [ lista de rutas ] en program.pl línea N.

Para manejar la posibilidad de un programa inexistente, llama a run() dentro de un "eval".

my $rc;
eval { $rc = run( \@cmd, \$in, \$out, \$out ); 1; };
if ( !defined($rc) ) {
    print "run murió: $@\n";
}
else {
    if ( $rc ) {
        print "run devolvió verdadero\n";
    }
    else {
        print "run devolvió falso\n";
        print "\$? = $?\n";
    }
}

Hay dos modos en los que puedes ejecutar arneses: run() funciona como un system() mejorado, y start()/pump()/finish() permiten procesos en segundo plano e interacciones programadas con

ellos.

Al usar run(), todos los datos a enviar al arnés se configuran de antemano (aunque se puede alimentar a los subprocesos con entradas desde referencias a subrutinas para sortear esta limitación). El arnés se ejecuta y se recopila toda su salida, luego se espera a todos los procesos

hijos: 
run \@cmd, \<<IN, \$out;
blah
IN
## Para precompilar arneses y ejecutarlos más tarde:
my $h = harness \@cmd, \<<IN, \$out;
blah
IN
run
$h;

La API de segundo plano y programación la proporcionan start(), pump(), y finish(): start() crea un arnés si es necesario (llamando a harness()) e inicia cualquier subproceso, pump() te permite consultarlos para ver su actividad, y finish() luego monitorea las actividades del arnés hasta que se

completen. 
## Construye el arnés, abre todas las tuberías e inicia los subprocesos
my $h = start \@cat, \$in, \$out;
$in = "first input\n";
## Ahora haz E/S.  start() no hace E/S.
pump $h while length $in;  ## Espera a que se vaya toda la entrada
## Ahora haz algo más de E/S.
$in = "second input\n";
pump $h until $out =~ /second input/;
## Limpieza
finish $h or die "cat returned $?
";

Opcionalmente puedes compilar el arnés con harness() antes de llamar a start() o run(), y puedes omitir start() entre harness() y pump(). Podrías querer hacer estas cos

as si compilas tus ar
neses por adelantado.

salida

Como se muestra en la mayoría de los ejemplos de programación, la facilidad de leer en un escalar para recopilar la salida del subcomando se usa a menudo con expresiones regulares para detectar puntos de parada. Esto se debe a que la salida del subcomando a menudo llega a trozos y gotas, a menudo solo un carácter o línea a la vez. Esta salida es entrada para el programa principal y se acumula en variables como $out y $err en nuestros

Supongamos que quieres acumular toda la salida en $out y analizarla después. Tiempos de espera y

temporizadores

Lo más probable es que no quieras que tus subprocesos se ejecuten para siempre, y a veces es bueno saber que van un poco lentos. Los tiempos de espera lanzan excepciones después de que haya transcurrido algún tiempo, los temporizadores simplemente hacen que pump() retorne después de que haya transcurrido algún tiempo. Ninguno se restablece/reinicia automáticamente

.

Los objetos de tiempo de espera se crean llamando a timeout( $interval ) y pasando el resultado a run(), start() o harness(). El período de tiempo de espera comienza a contar justo después de que todos los procesos hijos hayan sido fork()eados o spawn()eados, y se consultan para ver si han expirado en run(), pump() y finish(). Si/when expiran, se lanza una excepción. Esto es típicamente útil para evitar que un subproceso tarde

demasiado.

Si ocurre un tiempo de espera en run(), todos los procesos hijos serán terminados y todos los descriptores de archivo/tubería/ptty abiertos por run() serán cerrados. Los descriptores de archivo abiertos por el proceso padre y pasados a run() no se cierran en este

evento.

Si ocurre un tiempo de espera en pump(), pump_nb(), o finish(), depende de ti decidir si kill_kill() a todos los hijos o implementar algún mecanismo de respaldo más elegante. No se cerrará ninguna E/S en pump(), pump_nb() o finish() por tal excepción (aunque la E/S a menudo se cierra en esas rutinas durante el curso natural de los eventos)

.

A menudo una excepción es demasiado severa. timer( $interval ) crea objetos temporizadores que simplemente evitan que pump() se bloquee para siempre. Esto puede ser útil para detectar E/S estancada o imprimir un mensaje tranquilizador o "." para calmar a un usuario

ansioso.

Los tiempos de espera y los temporizadores se pueden reiniciar en cualquier momento usando el método start() del temporizador (este no es el start() que lanza subprocesos). Para reiniciar un temporizador, necesitas mantener una referencia al

temporizador: 
  ## Comienza con un tiempo de espera largo y agradable para dejar que smbclient se conecte.  Si
  ## pump o finish tardan demasiado, se lanzará una excepción.
my $h;
eval {
  $h = harness \@smbclient, \$in, \$out, \$err, ( my $t = timeout 30 );
  sleep 11;  # Sin efecto: el temporizador aún no está en marcha
  start $h;
  $in = "cd /src\n";
  pump $h until ! length $in;
  $in = "ls\n";
  ## Ahora usa un tiempo de espera corto, ya que esto debería ser más rápido
  $t->start( 5 );
  pump $h until ! length $in;
  $t->start( 10 );  ## Dale a smbclient un poco de tiempo para apagarse.
  $h->finish;
};
if ( $@ ) {
  my $x = $@;    ## Preserva $@ en caso de que ocurra otra excepción
  $h->kill_kill; ## mátalo suavemente, luego brutalmente si es necesario, o solo
                  ## brutalmente en Win32.
  die $x;
}

Los tiempos de espera y los temporizadores no se comprueban una vez que los subprocesos se han apagado; no expirarán en el intervalo entre el

último proceso válido y cuando IPC::Run recoja los
códigos de resultado de los procesos, por ejemplo.

Sincronización de lanzamiento, propagación de excepciones del

hijo

start() pausa al padre hasta que el hijo ejecute el comando o la referencia CODE y propague cualquier excepción lanzada (incluyendo fallo de exec()) de vuelta al padre. Esto tiene varios efectos agradables: cualquier excepción lanzada en el hijo, incluyendo fallo de exec(), salen volando de start() o run() como si hubieran ocurrido en el

padre.

Esto incluye excepciones lanzadas por tu código desde subrutinas init. En este

ADVERTENCIA: Los coprocesos de función ("run \&foo, ...") sufren de dos limitaciones. La primera es que es difícil cerrar todos los manejadores de archivo (filehandles) que el hijo hereda del padre, ya que no hay forma de escanear todos los FILEHANDLEs abiertos en Perl y es doloroso y un poco peligroso cerrar todos los descriptores de archivo abiertos con POSIX::close(). Doloroso porque tampoco podemos decir qué fds están abiertos a nivel POSIX, así que tendríamos que escanear todos los fds posibles y cerrar cualquiera que no queramos que esté abierto (normalmente exec() cierra cualquier no heredable pero nosotros no exec() para los procesos

&sub.

El segundo problema es que los subs DESTROY de Perl y otras limpiezas al salir se ejecutan en el proceso hijo. Si los objetos se instancian en el padre antes de que el hijo se haga fork, el DESTROY se ejecutará una vez en el padre y una vez en el hijo. Cuando los subs de coproceso salen, se llama a POSIX::_exit para solucionar esto, pero significa que los objetos que todavía están referenciados en ese momento no se limpian. Por lo tanto, establecer variables de paquete o variables de cierre para que apunten a objetos que dependen de DESTROY para afectar cosas fuera del proceso (archivos, etc.), conducirá a

errores.
