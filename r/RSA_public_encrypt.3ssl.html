RSA_public_encrypt(3ssl)

Paquete: openssl

Licencias: Apache-2.0

RSA_PUBLIC_ENCRYPT(3ssl) OpenSSL RSA_PUBLIC_ENCRYPT(3ssl)

NOMBRE

RSA_public_encrypt, RSA_private_decrypt - Criptografía de clave pública RSA

SINOPSIS

#include <openssl/rsa.h>

Las siguientes funciones han sido marcadas como obsoletas desde OpenSSL 3.0 y pueden ser completamente ocultadas definiendo OPENSSL_API_COMPAT con un valor de versión adecuado, ver openssl_user_macros(7):

int RSA_public_encrypt(int flen, const unsigned char *from,
                       unsigned char *to, RSA *rsa, int padding);
int RSA_private_decrypt(int flen, const unsigned char *from,
                        unsigned char *to, RSA *rsa, int padding);

DESCRIPCIÓN

Ambas funciones descritas en esta página están obsoletas. Las aplicaciones deberían usar en su lugar EVP_PKEY_encrypt_init_ex(3), EVP_PKEY_encrypt(3), EVP_PKEY_decrypt_init_ex(3) y EVP_PKEY_decrypt(3).

RSA_public_encrypt() cifra los flen bytes en from (normalmente una clave de sesión) usando la clave pública rsa y almacena el texto cifrado en to. to debe apuntar a RSA_size(rsa) bytes de memoria.

padding denota uno de los siguientes modos:

RSA_PKCS1_PADDING
Relleno PKCS #1 v1.5. Actualmente, este es el modo más utilizado. Sin embargo, se recomienda encarecidamente usar RSA_PKCS1_OAEP_PADDING en nuevas aplicaciones. VER ADVERTENCIA ABAJO.
RSA_PKCS1_OAEP_PADDING
EME-OAEP según se define en PKCS #1 v2.0 con SHA-1, MGF1 y un parámetro de codificación vacío. Este modo se recomienda para todas las nuevas aplicaciones.
RSA_NO_PADDING
Cifrado RSA puro. Este modo *solo* debe usarse para implementar modos de relleno criptográficamente seguros en el código de la aplicación. Cifrar datos de usuario directamente con RSA no es seguro.

Al cifrar, flen no debe ser mayor que RSA_size(rsa) - 11 para los modos de relleno basados en PKCS #1 v1.5, no mayor que RSA_size(rsa) - 42 para RSA_PKCS1_OAEP_PADDING y exactamente RSA_size(rsa) para RSA_NO_PADDING. Cuando se usa un modo de relleno distinto de RSA_NO_PADDING, RSA_public_encrypt() incluirá algunos bytes aleatorios en el texto cifrado y, por lo tanto, el texto cifrado será diferente cada vez, incluso si el texto plano y la clave pública son exactamente idénticos. El texto cifrado devuelto en to siempre se rellenará con ceros hasta exactamente RSA_size(rsa) bytes. to y from pueden superponerse.

RSA_private_decrypt() descifra los flen bytes en from usando la clave privada rsa y almacena el texto plano en to. flen debe ser igual a RSA_size(rsa) pero puede ser menor, cuando hay bytes cero iniciales en el texto cifrado. Estos no son importantes y pueden eliminarse, pero RSA_public_encrypt() no lo hace. to debe apuntar a una sección de memoria lo suficientemente grande como para contener los datos descifrados máximos posibles (que es igual a RSA_size(rsa) para RSA_NO_PADDING, RSA_size(rsa) - 11 para los modos de relleno basados en PKCS #1 v1.5 y RSA_size(rsa) - 42 para RSA_PKCS1_OAEP_PADDING). padding es el modo de relleno que se utilizó para cifrar los datos. to y from pueden superponerse.

VALORES DE RETORNO

RSA_public_encrypt() devuelve el tamaño de los datos cifrados (es decir, RSA_size(rsa)). RSA_private_decrypt() devuelve el tamaño del texto plano recuperado. Un valor de retorno de 0 no es un error y solo significa que el texto plano estaba vacío.

En caso de error, se devuelve -1; los códigos de error se pueden obtener mediante ERR_get_error(3).

ADVERTENCIAS

Los fallos de descifrado en el modo RSA_PKCS1_PADDING filtran información que potencialmente puede ser utilizada para montar un ataque de oráculo de relleno de Bleichenbacher. Esta es una debilidad inherente en el diseño del relleno PKCS #1 v1.5. Prefiera RSA_PKCS1_OAEP_PADDING.

En OpenSSL antes de la versión 3.2.0, tanto el valor de retorno como la longitud del valor devuelto podían usarse para montar el ataque de Bleichenbacher. Desde la versión 3.2.0, el proveedor predeterminado en OpenSSL no devuelve un error cuando fallan las verificaciones de relleno. En su lugar, genera un mensaje aleatorio basado en la clave privada utilizada y el texto cifrado proporcionado para que el código de la aplicación no tenga que implementar un manejo de errores seguro contra canales laterales. Las aplicaciones que desean ser seguras contra ataques de canales laterales con proveedores que no implementan rechazo implícito, aún necesitan manejar los valores devueltos utilizando código libre de canales laterales. El manejo libre de canales laterales de la pila de errores se puede realizar mediante un par de llamadas incondicionales ERR_set_mark(3) y ERR_pop_to_mark(3) o mediante la llamada a ERR_clear_error(3).

CONFORME A

SSL, PKCS #1 v2.0

VER TAMBIÉN

ERR_get_error(3), RAND_bytes(3), RSA_size(3), EVP_PKEY_decrypt(3), EVP_PKEY_encrypt(3)
