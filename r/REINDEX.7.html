NOMBRE

REINDEX - reconstruir índices

SINOPSIS

REINDEX [ ( opción [, ...] ) ] { INDEX | TABLE | SCHEMA } [ CONCURRENTLY ] nombre
REINDEX [ ( opción [, ...] ) ] { DATABASE | SYSTEM } [ CONCURRENTLY ] [ nombre ]
donde opción puede ser una de las siguientes:
    CONCURRENTLY [ booleano ]
    TABLESPACE nuevo_tablespace
    VERBOSE [ booleano ]

DESCRIPCIÓN

REINDEX reconstruye un índice utilizando los datos almacenados en la tabla del índice, reemplazando la copia antigua del índice. Hay varios escenarios en los que se puede usar REINDEX:

•Un índice se ha corrompido y ya no contiene datos válidos. Aunque en teoría esto nunca debería ocurrir, en la práctica los índices pueden corromperse debido a errores de software o fallos de hardware. REINDEX proporciona un método de recuperación.
•Un índice se ha vuelto “hinchado” (bloated), es decir, contiene muchas páginas vacías o casi vacías. Esto puede ocurrir con índices B-tree en PostgreSQL bajo ciertos patrones de acceso poco comunes. REINDEX proporciona una forma de reducir el consumo de espacio del índice escribiendo una nueva versión del índice sin las páginas muertas. Consulte la Sección 24.2 para obtener más información.
•Ha alterado un parámetro de almacenamiento (como fillfactor) para un índice y desea asegurarse de que el cambio ha surtido pleno efecto.
•Si la creación de un índice falla con la opción CONCURRENTLY, este índice queda como “inválido”. Dichos índices son inútiles pero puede ser conveniente usar REINDEX para reconstruirlos. Tenga en cuenta que solo REINDEX INDEX es capaz de realizar una creación concurrente en un índice inválido.

PARÁMETROS

INDEX

Recrea el índice especificado. Esta forma de REINDEX no puede ejecutarse dentro de un bloque de transacciones cuando se usa con un índice particionado.

TABLE

Recrea todos los índices de la tabla especificada. Si la tabla tiene una tabla secundaria “TOAST”, también se reconstruye. Esta forma de REINDEX no puede ejecutarse dentro de un bloque de transacciones cuando se usa con una tabla particionada.

SCHEMA

Recrea todos los índices del esquema especificado. Si una tabla de este esquema tiene una tabla secundaria “TOAST”, también se reconstruye. También se procesan los índices en catálogos del sistema compartidos. Esta forma de REINDEX no puede ejecutarse dentro de un bloque de transacciones.

DATABASE

Recrea todos los índices dentro de la base de datos actual, excepto los catálogos del sistema. Los índices en catálogos del sistema no se procesan. Esta forma de REINDEX no puede ejecutarse dentro de un bloque de transacciones.

SYSTEM

Recrea todos los índices en catálogos del sistema dentro de la base de datos actual. Se incluyen los índices en catálogos del sistema compartidos. Los índices en tablas de usuario no se procesan. Esta forma de REINDEX no puede ejecutarse dentro de un bloque de transacciones.

nombre

El nombre del índice, tabla o base de datos específico que se va a reconstruir. Los nombres de índices y tablas pueden estar cualificados por esquema. Actualmente, REINDEX DATABASE y REINDEX SYSTEM solo pueden reconstruir la base de datos actual. Su parámetro es opcional y debe coincidir con el nombre de la base de datos actual.

CONCURRENTLY

Cuando se utiliza esta opción, PostgreSQL reconstruirá el índice sin tomar bloqueos que impidan inserciones, actualizaciones o eliminaciones concurrentes en la tabla; mientras que una reconstrucción de índice estándar bloquea las escrituras (pero no las lecturas) en la tabla hasta que se completa. Hay varias advertencias a tener en cuenta al usar esta opción: consulte Reconstrucción de índices de forma concurrente a continuación.

Para tablas temporales, REINDEX siempre es no concurrente, ya que ninguna otra sesión puede acceder a ellas, y la reconstrucción no concurrente es más barata.

TABLESPACE

Especifica que los índices se reconstruirán en un nuevo espacio de tablas (tablespace).

VERBOSE

Imprime un informe de progreso a medida que cada índice se reconstruye en el nivel INFO.

booleano

Especifica si la opción seleccionada debe activarse o desactivarse. Puede escribir TRUE, ON o 1 para habilitar la opción, y FALSE, OFF o 0 para deshabilitarla. El valor booleano también se puede omitir, en cuyo caso se asume TRUE.

nuevo_tablespace

El espacio de tablas donde se reconstruirán los índices.

NOTAS

Si sospecha de corrupción en un índice de una tabla de usuario, simplemente puede reconstruir ese índice, o todos los índices de la tabla, usando REINDEX INDEX o REINDEX TABLE.

Las cosas son más complicadas si necesita recuperarse de la corrupción de un índice en una tabla del sistema. En este caso, es importante que el sistema no haya utilizado ninguno de los índices sospechosos. (De hecho, en este tipo de escenarios, es posible que los procesos del servidor fallen inmediatamente al iniciarse, debido a la dependencia de los índices corruptos). Para recuperarse de forma segura, el servidor debe iniciarse con la opción -P, que evita que utilice índices para las consultas al catálogo del sistema.

Una forma de hacerlo es detener el servidor e iniciar un servidor PostgreSQL de un solo usuario con la opción -P incluida en su línea de comandos. Luego, se pueden emitir REINDEX DATABASE, REINDEX SYSTEM, REINDEX TABLE o REINDEX INDEX, dependiendo de cuánto quiera reconstruir. En caso de duda, use REINDEX SYSTEM para seleccionar la reconstrucción de todos los índices del sistema en la base de datos. Luego, salga de la sesión del servidor de un solo usuario y reinicie el servidor normal. Consulte la página de referencia de postgres(1) para obtener más información sobre cómo interactuar con la interfaz del servidor de un solo usuario.

Alternativamente, se puede iniciar una sesión de servidor normal con la opción -P incluida en sus opciones de línea de comandos. El método para hacer esto varía entre clientes, pero en todos los clientes basados en libpq, es posible establecer la variable de entorno PGOPTIONS a -P antes de iniciar el cliente. Tenga en cuenta que aunque este método no requiere bloquear a otros clientes, aún podría ser prudente evitar que otros usuarios se conecten a la base de datos dañada hasta que las reparaciones se hayan completado.

REINDEX es similar a un drop y recreate del índice en que el contenido del índice se reconstruye desde cero. Sin embargo, las consideraciones de bloqueo son bastante diferentes. REINDEX bloquea las escrituras pero no las lecturas de la tabla padre del índice. También toma un bloqueo ACCESS EXCLUSIVE en el índice específico que se está procesando, lo que bloqueará las lecturas que intenten usar ese índice. En particular, el planificador de consultas intenta tomar un bloqueo ACCESS SHARE en cada índice de la tabla, independientemente de la consulta, y por lo tanto REINDEX bloquea virtualmente cualquier consulta excepto algunas consultas preparadas cuyo plan se ha almacenado en caché y que no utilizan este índice en particular. En contraste, DROP INDEX toma momentáneamente un bloqueo ACCESS EXCLUSIVE en la tabla padre, bloqueando tanto escrituras como lecturas. El subsiguiente CREATE INDEX bloquea las escrituras pero no las lecturas; dado que el índice no está presente, ninguna lectura intentará usarlo, lo que significa que no habrá bloqueo, pero las lecturas pueden verse forzadas a costosos escaneos secuenciales.

Mientras REINDEX se está ejecutando, el search_path se cambia temporalmente a pg_catalog, pg_temp.

Reconstruir un índice o tabla individual requiere tener el privilegio MAINTAIN sobre la tabla. Tenga en cuenta que mientras REINDEX en un índice o tabla particionado requiere tener el privilegio MAINTAIN sobre la tabla particionada, dichos comandos omiten las comprobaciones de privilegios al procesar las particiones individuales. Reconstruir un esquema o base de datos requiere ser el propietario de ese esquema o base de datos o tener privilegios del rol pg_maintain. Tenga en cuenta específicamente que es, por lo tanto, posible que los no superusuarios reconstruyan índices de tablas propiedad de otros usuarios. Sin embargo, como excepción especial, REINDEX DATABASE, REINDEX SCHEMA y REINDEX SYSTEM omitirán los índices en catálogos compartidos a menos que el usuario tenga el privilegio MAINTAIN sobre el catálogo.

La reconstrucción de índices particionados o tablas particionadas es compatible con REINDEX INDEX o REINDEX TABLE, respectivamente. Cada partición de la relación particionada especificada se reconstruye en una transacción separada. Dichos comandos no se pueden usar dentro de un bloque de transacciones al trabajar en una tabla o índice particionado.

REINDEX

reindex - re-create indexes, or rebuild a table or system catalog

SYNOPSIS

REINDEX [ ( [ VERBOSE ] [ ANALYZE ] [ TABLESPACE tablespace_name ] [ INDEX_SORT_BLOCK_SIZE size ] [ METADATA_ONLY ] [ CONCURRENTLY ] ) ] target ...

where target can be:

    TABLE table_name [ [, . . . ] ]
    DATABASE database_name [ [, . . . ] ]
    SYSTEM
    INDEX index_name [ [, . . . ] ]
    TABLESPACE tablespace_name [ [, . . . ] ]

DESCRIPTION

REINDEX rebuilds one or more indexes in a PostgreSQL database. It also has the ability to rebuild entire tables or system catalogs.

Rebuilding an index typically involves dropping the existing index and creating a new one. The new index is populated with the data from the table. This can be useful for several reasons:

  • A bloated index can be shrunk by reindexing. This is often beneficial after many deletions or updates of indexed columns.
  • A previously corrupted index can be repaired by reindexing.
  • When changing index storage parameters (like fillfactor), reindexing is required to apply the new parameters.
  • If an index has become inefficient due to the order of operations, reindexing can potentially improve performance.

REINDEX can also rebuild an entire table (including all indexes on it) and its associated TOAST data. This is done by re-creating the table contents, indexes, and TOAST data. This operation can be used to reclaim storage space and remove bloat from a table and its indexes. Rebuilding a table is a heavy operation that requires significant work and time.

REINDEX can also rebuild all the system catalogs. This is typically only needed if there's a suspicion that the system catalogs are corrupted. Rebuilding system catalogs is a heavy operation and should only be performed with extreme caution.

The command can also rebuild all indexes associated with a tablespace. This is useful if the tablespace itself has been reconfigured (e.g. moved to new storage).

PARAMETERS

REINDEX allows the following options:

VERBOSE
This option specifies that a detailed status message will be emitted during the execution of the command for each index or table being reindexed.
ANALYZE
This option specifies that the ANALYZE command should be run on each table after it is reindexed. This provides the query planner with updated statistics. This is the default behavior.
TABLESPACE tablespace_name
This option specifies that all indexes (or tables, if the corresponding table has tablespace set to this value) created by this command should be created in the specified tablespace. If this option is specified for an index, any existing index is dropped and a new one is created in the specified tablespace. If the option is specified for a table, all indexes on the table will be moved to the specified tablespace. If the table itself is to be moved, that requires a separate command (e.g. `ALTER TABLE ... SET TABLESPACE`). If this option is specified for a database, all indexes and tables in that database will be moved to the specified tablespace. If the option is specified for SYSTEM, all system indexes will be moved to the specified tablespace.
INDEX_SORT_BLOCK_SIZE size
This option specifies the amount of memory to use for sorting during index builds. The default is determined by the PostgreSQL server configuration parameter idx_sort_tablespace.
METADATA_ONLY
This option causes only the metadata for indexes to be rebuilt. No data is read from the table and no data is written to the index. This option is only useful for fixing inconsistencies in index metadata, for example, after an incomplete recovery. Note that the index may not be fully valid after this operation.
CONCURRENTLY
This option allows indexes to be rebuilt without taking strong locks on the table. This means that other operations (like INSERT, UPDATE, DELETE, SELECT) can continue to run on the table while the index is being rebuilt. See the section below for more details.

The target can be one of:

TABLE table_name
Rebuilds all indexes on the specified table, and also rebuilds the table itself (including any TOAST data). If the TABLESPACE option is specified, the table and its indexes will be moved to that tablespace.
DATABASE database_name
Rebuilds all indexes in the specified database. If the TABLESPACE option is specified, all tables and indexes in that database will be moved to that tablespace.
SYSTEM
Rebuilds all system catalog indexes. This should only be done if the system catalogs are suspected of being corrupt.
INDEX index_name
Rebuilds the specified index. If the TABLESPACE option is specified, the index will be moved to that tablespace.
TABLESPACE tablespace_name
Rebuilds all indexes in the specified tablespace. If the TABLESPACE option is specified, all tables in that tablespace will be moved to that tablespace.

NOTES

When REINDEX is run on a table, it will rebuild the table, all its indexes, and any associated TOAST data. If the TABLESPACE option is used, the table and its indexes will be moved to the specified tablespace. If the table has partitioned indexes, the leaf partitions are rebuilt, and the indexes on them are moved to the new tablespace if specified. All partitions attached inherit the new tablespace. On failure, it may not have moved all the indexes to the new tablespace. Re-running the command will rebuild all the leaf partitions and move previously-unprocessed indexes to the new tablespace.

If SCHEMA, DATABASE or SYSTEM is used with TABLESPACE, system relations are skipped and a single WARNING will be generated. Indexes on TOAST tables are rebuilt, but not moved to the new tablespace.

Rebuilding Indexes Concurrently

Rebuilding an index can interfere with regular operation of a database. Normally PostgreSQL locks the table whose index is rebuilt against writes and performs the entire index build with a single scan of the table. Other transactions can still read the table, but if they try to insert, update, or delete rows in the table they will block until the index rebuild is finished. This could have a severe effect if the system is a live production database. Very large tables can take many hours to be indexed, and even for smaller tables, an index rebuild can lock out writers for periods that are unacceptably long for a production system.

PostgreSQL supports rebuilding indexes with minimum locking of writes. This method is invoked by specifying the CONCURRENTLY option of REINDEX. When this option is used, PostgreSQL must perform two scans of the table for each index that needs to be rebuilt and wait for termination of all existing transactions that could potentially use the index. This method requires more total work than a standard index rebuild and takes significantly longer to complete as it needs to wait for unfinished transactions that might modify the index. However, since it allows normal operations to continue while the index is being rebuilt, this method is useful for rebuilding indexes in a production environment. Of course, the extra CPU, memory and I/O load imposed by the index rebuild may slow down other operations.

The following steps occur in a concurrent reindex. Each step is run in a separate transaction. If there are multiple indexes to be rebuilt, then each step loops through all the indexes before moving to the next step.

1.A new transient index definition is added to the catalog pg_index. This definition will be used to replace the old index. A SHARE UPDATE EXCLUSIVE lock at session level is taken on the indexes being reindexed as well as their associated tables to prevent any schema modification while processing.
2.A first pass to build the index is done for each new index. Once the index is built, its flag pg_index.indisready is switched to “true” to make it ready for inserts, making it visible to other sessions once the transaction that performed the build is finished. This step is done in a separate transaction for each index.
3.Then a second pass is performed to add tuples that were added while the first pass was running. This step is also done in a separate transaction for each index.
4.All the constraints that refer to the index are changed to refer to the new index definition, and the names of the indexes are changed. At this point, pg_index.indisvalid is switched to “true” for the new index and to “false” for the old, and a cache invalidation is done causing all sessions that referenced the old index to be invalidated.
5.The old indexes have pg_index.indisready switched to “false” to prevent any new tuple insertions, after waiting for running queries that might reference the old index to complete.
6.The old indexes are dropped. The SHARE UPDATE EXCLUSIVE session locks for the indexes and the table are released.

If a problem arises while rebuilding the indexes, such as a uniqueness violation in a unique index, the REINDEX command will fail but leave behind an “invalid” new index in addition to the pre-existing one. This index will be ignored for querying purposes because it might be incomplete; however it will still consume update overhead. The psql \d command will report such an index as INVALID:

postgres=# \d tab
       Table "public.tab"
 Column |  Type   | Modifiers
--------+---------+-----------
 col    | integer |
Indexes:
    "idx" btree (col)
    "idx_ccnew" btree (col) INVALID

If the index marked INVALID is suffixed _ccnew, then it corresponds to the transient index created during the concurrent operation, and the recommended recovery method is to drop it using DROP INDEX, then attempt REINDEX CONCURRENTLY again. If the invalid index is instead suffixed _ccold, it corresponds to the original index which could not be dropped; the recommended recovery method is to just drop said index, since the rebuild proper has been successful. A nonzero number may be appended to the suffix of the invalid index names to keep them unique, like _ccnew1, _ccold2, etc.

Regular index builds permit other regular index builds on the same table to occur simultaneously, but only one concurrent index build can occur on a table at a time. In both cases, no other types of schema modification on the table are allowed meanwhile. Another difference is that a regular REINDEX TABLE or REINDEX INDEX command can be performed within a transaction block, but REINDEX CONCURRENTLY cannot.

Like any long-running transaction, REINDEX on a table can affect which tuples can be removed by concurrent VACUUM on any other table.

REINDEX SYSTEM does not support CONCURRENTLY since system catalogs cannot be reindexed concurrently.

Furthermore, indexes for exclusion constraints cannot be reindexed concurrently. If such an index is named directly in this command, an error is raised. If a table or database with exclusion constraint indexes is reindexed concurrently, those indexes will be skipped. (It is possible to reindex such indexes without the CONCURRENTLY option.)

Each backend running REINDEX will report its progress in the pg_stat_progress_create_index view. See Section 27.4.4 for details.

EXAMPLES

Rebuild a single index:

REINDEX INDEX my_index;

Rebuild all the indexes on the table my_table:

REINDEX TABLE my_table;

Rebuild all indexes in a particular database, without trusting the system indexes to be valid already:

$ export PGOPTIONS="-P"
$ psql broken_db
...
broken_db=> REINDEX DATABASE broken_db;
broken_db=> \q

Rebuild indexes for a table, without blocking read and write operations on involved relations while reindexing is in progress:

REINDEX TABLE CONCURRENTLY my_broken_table;

COMPATIBILITY

There is no REINDEX command in the SQL standard.
