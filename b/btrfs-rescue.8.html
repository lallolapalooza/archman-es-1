NOMBRE

btrfs-rescue - recuperar un sistema de archivos btrfs dañado

SINOPSIS

btrfs rescue <subcomando> <argumentos>

DESCRIPCIÓN

Un conjunto de comandos dirigidos a solucionar un problema específico y que pueden no ser adecuados para :doc:`btrfs-check`.

SUBCOMANDO

chunk-recover [opciones] <dispositivo>
Recuperar el árbol de bloques (chunk tree) escaneando los dispositivos.

Opciones

-y
asumir una respuesta de sí a todas las preguntas.
-h
ayuda.
-v
(obsoleto) alias para la opción global -v

Nota:

Dado que chunk-recover escaneará el dispositivo completo, será muy lento, especialmente si se ejecuta en un dispositivo grande.
fix-device-size <dispositivo>
Corrige los valores del tamaño del dispositivo y los bytes totales de la superbloque que no coinciden.

El kernel 4.11 comenzó a verificar el tamaño del dispositivo de forma más estricta, y esto podría no coincidir con el valor almacenado de bytes totales. Consulte el mensaje de error exacto a continuación. Los kernels más recientes se negarán a montar el sistema de archivos donde los valores no coinciden. Este error no es fatal y puede corregirse. Este comando corregirá los valores del tamaño del dispositivo si es posible.

BTRFS error (device sdb): super_total_bytes 92017859088384 mismatch with fs_devices total_rw_bytes 92017859094528

La discrepancia también puede manifestarse como una advertencia del kernel:

WARNING: CPU: 3 PID: 439 at fs/btrfs/ctree.h:1559 btrfs_update_device+0x1c5/0x1d0 [btrfs]
fix-data-checksum <dispositivo>
Corrige selectivamente las discrepancias de checksum de datos.

Existe un problema antiguo por el cual si un programa de espacio de usuario realiza E/S directa (direct IO) y modifica el búfer antes de que la escritura finalice, puede generar discrepancias de checksum de datos.

Este problema es conocido pero no se ha corregido hasta la versión upstream v6.15 (backportado a kernels más antiguos). Por lo tanto, es posible encontrar falsas discrepancias de checksum de datos en cualquier btrfs de larga ejecución.

En ese caso, se puede utilizar este programa para reparar dicho problema.

Opciones

-r|--readonly
modo de solo lectura, solo escanea e informa sobre las discrepancias de checksum de datos, no repara.
-i|--interactive
modo interactivo, pregunta cómo reparar, ignora los errores por defecto.
-m|--mirror <num>
usa el espejo especificado para actualizar el elemento de checksum para todos los bloques corruptos.

El valor debe ser >= 1, y si el bloque corrupto tiene menos espejos que el valor, el número de espejo será num % (num_mirrors + 1).

clear-ino-cache <dispositivo>
Elimina los elementos sobrantes relacionados con la función obsoleta de caché de números de inodo.

La función habilitada por la opción de montaje inode_cache se ha eliminado por completo en el kernel 5.11.

clear-space-cache <v1|v2> <dispositivo>
Elimina por completo los datos en disco de la caché de espacio libre de la versión dada.

Especialmente para la caché de espacio libre v1, la opción de montaje clear_cache solo eliminaba la caché de los grupos de bloques actualizados, el resto no se eliminaba. Por lo tanto, este comando se proporciona para borrar manualmente la caché de espacio libre.

clear-uuid-tree <dispositivo>
Borra el árbol de UUID, para que el kernel pueda regenerarlo en el próximo montaje de lectura/escritura.

Desde el kernel v4.16 se realizan más comprobaciones de integridad, y a veces árboles no críticos como el árbol de UUID pueden causar problemas y rechazar el montaje. En tal caso, borrar el árbol de UUID puede hacer que el sistema de archivos se pueda montar de nuevo sin mucho riesgo, ya que se construye a partir de otros árboles. Consulte también la opción de montaje rescan_uuid_tree (en btrfs-man5) <btrfs-man5//#mount-option-rescan-uuid-tree>.

super-recover [opciones] <dispositivo>
Recupera superbloques dañados de copias buenas.

Opciones

-y
asumir una respuesta de sí a todas las preguntas.
-v
(obsoleto) alias para la opción global -v
zero-log <dispositivo>
Borra el árbol de registro del sistema de archivos.

Este comando borrará el árbol de registro del sistema de archivos. Esto puede solucionar un conjunto específico de problemas cuando el montaje del sistema de archivos falla durante la reproducción del registro. Consulte a continuación ejemplos de rastreos de pila que pueden aparecer en el registro del sistema.

Nota:

Borrar el registro puede provocar la pérdida de cambios que se realizaron desde la última confirmación de transacción. Esto puede ser hasta 30 segundos (período de confirmación predeterminado) o menos si la confirmación fue implícita por otra actividad del sistema de archivos.

Se puede determinar si zero-log es necesario según el rastreo de pila del kernel:

? replay_one_dir_item+0xb5/0xb5 [btrfs]
? walk_log_tree+0x9c/0x19d [btrfs]
? btrfs_read_fs_root_no_radix+0x169/0x1a1 [btrfs]
? btrfs_recover_log_trees+0x195/0x29c [btrfs]
? replay_one_dir_item+0xb5/0xb5 [btrfs]
? btree_read_extent_buffer_pages+0x76/0xbc [btrfs]
? open_ctree+0xff6/0x132c [btrfs]

Si los errores son como los anteriores, entonces se debe usar zero-log para borrar el registro y el sistema de archivos podrá montarse normalmente de nuevo. Las palabras clave a buscar son 'open_ctree', que indica que es durante el montaje, y nombres de funciones que contienen replay, recover o log_tree.

ESTADO DE SALIDA

btrfs rescue devuelve un estado de salida cero si tiene éxito. Se devuelve un valor distinto de cero en caso de fallo.

DISPONIBILIDAD

btrfs es parte de btrfs-progs. Consulte la documentación en https://btrfs.readthedocs.io.
