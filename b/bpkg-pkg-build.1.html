NOMBRE

bpkg-pkg-build - construir paquete

SINOPSIS

bpkg pkg-build|build [opciones] [--upgrade|-u | --patch|-p]
                     [var-cfg... --] esp-paq...
bpkg pkg-build|build [opciones]  --upgrade|-u | --patch|-p
                     [var-cfg... --]

esp-paq = [flags](([esquema:]paq[esp-ver]),...[@loc-rep] |
                   [@]loc-rep                          |
                   archivo                            |
                   dir/)
flags      = ?
esquema     = sys
esp-ver   = /versión | restricción-ver

DESCRIPCIÓN

El comando pkg-build construye uno o más paquetes, incluidas todas sus dependencias. Además de construir paquetes nuevos, este comando también se utiliza para actualizar o degradar paquetes que ya están presentes en la configuración. Y a menos que se especifique la opción --keep-unused|-K, pkg-build también eliminará paquetes dependientes que de otro modo ya no se usarían.

La primera forma (se especifican uno o más paquetes) construye nuevos o actualiza (por defecto o si se especifica --upgrade) o aplica parches (si se especifica --patch) a los paquetes especificados. La segunda forma (sin argumentos pero con --upgrade o --patch especificado) actualiza o aplica parches a todos los paquetes retenidos en la configuración (ver más abajo para detalles sobre paquetes retenidos).

En ambas formas, especificar la opción --immediate|-i o --recursive|-r hace que pkg-build actualice o aplique parches a las dependencias inmediatas o a todas las dependencias de los paquetes especificados (primera forma) o retenidos (segunda forma), respectivamente. Tenga en cuenta también que en la primera forma estas opciones solo se pueden especificar con un --upgrade o --patch explícito.

Cada paquete puede especificarse solo como el nombre (paq) con especificación de versión opcional (esp-ver), en cuyo caso el código fuente del paquete se obtendrá automáticamente de uno de los repositorios configurados. Consulte los comandos bpkg-rep-add(1) y bpkg-rep-fetch(1) para obtener más información sobre los repositorios de paquetes. La especificación de versión (esp-ver) puede ser la versión exacta en el formato /versión o la restricción de versión como se describe en Restricción de Versión de Paquete (#restriccion-version-paquete). Si no se especifica esp-ver, se construirá la última versión disponible. Para realizar una degradación, se debe especificar explícitamente la versión deseada. Por ejemplo:

bpkg build foo libfoo/1.2.3 "bar < 2.0.0"

Alternativamente, la ubicación del repositorio de paquetes (loc-rep) se puede especificar como parte del comando de compilación. En este caso, si no se especifica esp-ver, se construirá la última versión disponible de este repositorio. Por ejemplo:

bpkg build foo,libfoo/1.2.3@https://git.example.org/foo.git#master

Si solo se especifica la ubicación, se construirán las últimas versiones de todos los paquetes disponibles directamente desde este repositorio (tenga en cuenta que esto no incluye paquetes disponibles desde repositorios complementarios). El delimitador @ se puede omitir si la ubicación es una URL. Por ejemplo:

bpkg build https://git.example.org/foo.git#master
bpkg build @/ruta/al/repositorio/

Un nombre de paquete (paq) puede ir precedido de un esquema de paquete (esquema). Actualmente, el único esquema reconocido es sys, que instruye a pkg-build a configurar el paquete como disponible desde el sistema en lugar de construirlo desde el código fuente.

La versión del paquete del sistema (esp-ver) puede no ser una restricción de versión, sino que puede ser el valor especial '/*', que indica que la versión debe considerarse desconocida pero que satisface cualquier restricción de versión. Si no se especifica, pkg-build intentará consultar al gestor de paquetes del sistema la versión instalada, a menos que el gestor de paquetes del sistema no sea compatible o esta funcionalidad esté deshabilitada con --sys-no-query, en cuyo caso se asume el valor esp-ver '/*'. Si el gestor de paquetes del sistema es compatible, la instalación automática de un paquete disponible se puede solicitar con la opción --sys-install. Tenga en cuenta que si la versión no se especifica explícitamente, entonces al menos un paquete stub debe estar disponible desde uno de los repositorios, a menos que se especifique la opción --sys-no-stub.

Finalmente, un paquete puede especificarse como la ruta al archivo del paquete (archivo) o al directorio del paquete (dir/; tenga en cuenta que debe terminar con un separador de directorio). Consulte los comandos bpkg-pkg-fetch(1) y bpkg-pkg-unpack(1) para obtener más información sobre la semántica de especificar el paquete como archivo o directorio.

Las variables de configuración adicionales (var-cfg), si las hay, deben especificarse antes de los paquetes (esp-paq) y deben separarse con --. Dichas variables solo son efectivas al configurar y solo para los paquetes que se especificaron explícitamente en la línea de comandos (a menos que sean anulaciones globales). También se pueden especificar para que solo se apliquen a paquetes específicos utilizando el mecanismo de agrupación de argumentos discutido a continuación. Consulte bpkg-pkg-configure(1) para obtener más información sobre las variables de configuración.

Por defecto, un paquete que se especifica explícitamente en la línea de comandos se construye para mantenerse: no se considerará para eliminación automática si ya no tiene dependientes. Solo se consideran disponibles para construir para mantener las versiones de los repositorios que se agregaron a la configuración (bpkg-rep-add(1)).

Alternativamente, un paquete puede construirse (o, más comúnmente, actualizarse/degradarse) como una dependencia especificando la marca ? (flags) o la opción --dependency. Dicho paquete solo se agregará a la configuración si realmente tiene algún dependiente y, una vez que ya no se use, se eliminará automáticamente. Solo se consideran disponibles para construir como dependencia las versiones de los repositorios prerrequisito de los paquetes dependientes.

Los paquetes (tanto los construidos para mantener como las dependencias) que se especifican con una versión de paquete explícita (esp-ver) o como archivo o directorio, mantendrán sus versiones, es decir, no se actualizarán automáticamente.

Como ilustración, supongamos en el siguiente ejemplo que el repositorio estable contiene los paquetes foo 1.0.0, así como libfoo 1.0.0 y 1.1.0, mientras que testing — libfoo 2.0.0, que testing se complementa con estable, y que foo depende de libfoo >= 1.0.0:

bpkg fetch https://example.org/1/testing
bpkg build foo            # construir foo    1.0.0 para mantener
                          # construir libfoo 1.1.0 como dependencia
bpkg build ?libfoo/1.0.0  # degradar libfoo 1.0.0 como dependencia,
                          #           también mantener versión 1.0.0
bpkg build ?libfoo/2.0.0  # error: 2.0.0 no disponible en el repositorio
                          #        del dependiente (foo) (estable)
bpkg build libfoo/2.0.0   # actualizar libfoo 2.0.0 para mantener,
                          #         también mantener versión 2.0.0

Un paquete puede construirse en una de las configuraciones enlazadas en lugar de la actual (o el módulo del sistema host/build, para build-

(dependencias de tiempo) configuración especificando una de las opciones --config-* (ver bpkg-cfg-create(1) para información sobre configuraciones enlazadas). Por ejemplo:

bpkg build foo { --config-name=alt-host }+ ?bison

PKG-BUILD OPCIONES DE PAQUETE

Las siguientes opciones (así como variables de configuración adicionales) se pueden agrupar para aplicarse a un pkg-spec específico, así como especificarse globalmente, en cuyo caso se aplican a todos los paquetes especificados (ver bpkg-argument-grouping(1) para más detalles).

--upgrade|-u
Actualiza los paquetes a la última versión disponible que satisface todas las restricciones.
--patch|-p
Actualiza los paquetes a la última versión de parche disponible que satisface todas las restricciones.
--deorphan
Reemplaza los paquetes huérfanos con las versiones de paquetes disponibles que mejor coincidan y satisfagan todas las restricciones.

Puede suceder que un paquete construido ya no tenga el paquete correspondiente disponible en el repositorio de donde provino (por ejemplo, como resultado de bpkg-rep-fetch(1) o bpkg-rep-remove(1)). Dicho paquete se llama huérfano. Sin la opción --deorphan, actualizar, degradar o aplicar un parche a un huérfano lo dejará sin cambios si no hay una versión más adecuada del paquete disponible. Si se especifica la opción --deorphan, entonces un huérfano será reemplazado por uno no huérfano. En este caso, si se especifica --upgrade, --patch o la versión del paquete, la nueva versión se seleccionará en consecuencia. De lo contrario, se seleccionará la versión más cercana a la versión huérfana utilizando el siguiente orden de preferencia: (1) misma versión, revisión e iteración, (2) última iteración de la misma versión y revisión, (3) revisión posterior de la misma versión, (4) parche posterior de la misma versión, (5) versión menor posterior de la misma versión, (6) última versión disponible, incluida la anterior (ver Versión del Paquete (#package-version) para más detalles).

--immediate|-i
También actualiza, aplica parches o elimina huérfanos de dependencias inmediatas.
--recursive|-r
También actualiza, aplica parches o elimina huérfanos de todas las dependencias, recursivamente.
--upgrade-immediate
Actualiza dependencias inmediatas.
--patch-immediate
Aplica parches a dependencias inmediatas.
--deorphan-immediate
Elimina huérfanos de dependencias inmediatas.
--upgrade-recursive
Actualiza todas las dependencias, recursivamente.
--patch-recursive
Aplica parches a todas las dependencias, recursivamente.
--deorphan-recursive
Elimina huérfanos de todas las dependencias, recursivamente.
--dependency
Construye, actualiza o degrada un paquete como dependencia en lugar de mantenerlo.
--keep-out
Mantiene los directorios de salida de los paquetes externos entre actualizaciones y downgrades. Consulte bpkg-pkg-disfigure(1) para obtener más detalles.
--disfigure
Desfigura los paquetes entre actualizaciones y downgrades, causando efectivamente una reconfiguración desde cero.
--checkout-root dir
Saca los paquetes que provienen de repositorios basados en control de versiones al directorio especificado en lugar de al directorio de configuración. Consulte la opción --output-root en bpkg-pkg-checkout(1) para obtener más detalles.
--checkout-purge
Elimina los directorios de paquetes (fuente) sacados cuando los paquetes son purgados. Consulte la opción --output-purge en bpkg-pkg-checkout(1) para obtener más detalles.
--config-name name
Nombre de la configuración enlazada en la que construir este(os) paquete(s). Por defecto, el paquete se construye en la configuración actual. Repita esta opción para especificar múltiples configuraciones.
--config-id num
ID numérico de la configuración enlazada en la que construir este(os) paquete(s). Por defecto, el paquete se construye en la configuración actual. Repita esta opción para especificar múltiples configuraciones.
--config-uuid uuid
UUID de la configuración enlazada en la que construir este(os) paquete(s). Por defecto, el paquete se construye en la configuración actual. Repita esta opción para especificar múltiples configuraciones.

bpkg-pkg-build - Build a package with bpkg

SYNOPSIS

bpkg pkg-build options

DESCRIPTION

The bpkg pkg-build command is used to build a package with bpkg. It reads the build.toml configuration file and performs the necessary steps to create a package.

PKG-BUILD PACKAGE OPTIONS

--name package-name
Specify the name of the package to build. If not specified, it will be inferred from the build.toml file.
--version package-version
Specify the version of the package to build. If not specified, it will be inferred from the build.toml file.
--description package-description
Specify the description of the package. If not specified, it will be inferred from the build.toml file.
--arch architecture
Specify the architecture for which to build the package. If not specified, it will be inferred from the system.
--maintainer maintainer-name
Specify the maintainer of the package. If not specified, it will be inferred from the build.toml file.
--license license-name
Specify the license of the package. If not specified, it will be inferred from the build.toml file.
--source source-url
Specify the URL of the package source. If not specified, it will be inferred from the build.toml file.
--depends dependency-list
Specify a comma-separated list of package dependencies. If not specified, it will be inferred from the build.toml file.
--makedepends makedepends-list
Specify a comma-separated list of build-time dependencies. If not specified, it will be inferred from the build.toml file.
--checkdepends checkdepends-list
Specify a comma-separated list of check-time dependencies. If not specified, it will be inferred from the build.toml file.
--conflicts conflicts-list
Specify a comma-separated list of conflicting packages. If not specified, it will be inferred from the build.toml file.
--provides provides-list
Specify a comma-separated list of capabilities provided by the package. If not specified, it will be inferred from the build.toml file.
--replaces replaces-list
Specify a comma-separated list of packages that this package replaces. If not specified, it will be inferred from the build.toml file.
--optdepends opt-depends-list
Specify a comma-separated list of optional dependencies. If not specified, it will be inferred from the build.toml file.
--recommends recommends-list
Specify a comma-separated list of recommended packages. If not specified, it will be inferred from the build.toml file.
--suggests suggests-list
Specify a comma-separated list of suggested packages. If not specified, it will be inferred from the build.toml file.
--groups group-list
Specify a comma-separated list of package groups. If not specified, it will be inferred from the build.toml file.
--url package-url
Specify the URL of the package. If not specified, it will be inferred from the build.toml file.
--local-path local-path
Specify the local path to the package source. If not specified, it will be inferred from the build.toml file.
--build-dir build-directory
Specify the directory where the package will be built. If not specified, a temporary directory will be used.
--output-dir output-directory
Specify the directory where the built package will be placed. If not specified, the current directory will be used.
--skip-dependencies
Skip the dependency check and build the package regardless of whether dependencies are met.
--skip-build
Skip the build process and only prepare the package files.
--skip-package
Skip the packaging process and only build the package files.
--skip-install
Skip the installation process after building the package.
--clean
Clean the build directory before building the package.
--rebuild
Rebuild the package even if it already exists.
--force
Force the build process, overwriting existing files.

DEFAULT OPTIONS FILES

The bpkg pkg-build command looks for configuration files in the following order:

  1. ./build.toml
  2. ~/.config/bpkg/build.toml
  3. /etc/bpkg/build.toml
