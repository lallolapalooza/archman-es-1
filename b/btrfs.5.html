Asegura que todas las operaciones de escritura de E/S pasen por la caché del dispositivo y se almacenen permanentemente cuando el sistema de archivos está en su punto de comprobación de consistencia. Esto típicamente significa que se envía un comando de flush al dispositivo que sincronizará todos los datos pendientes y los bloques de metadatos ordinarios, luego escribe el superbloque y emite otro

Los flushes de escritura conllevan una ligera penalización y también impiden que el planificador de bloques de E/S reordene las solicitudes de manera más efectiva. antes.

Controla la compresión de datos de archivos de BTRFS. El tipo puede especificarse como zlib, lzo, zstd o no (para no comprimir, usado para remontar). Si no se especifica ningún tipo, se usa zlib. Si se especifica compress-force, entonces la compresión se intentará siempre, pero los datos pueden terminar sin comprimir si la compresión los haría más

grandes.

Tanto zlib como zstd (desde la versión 5.1) exponen el nivel de compresión como un parámetro ajustable con niveles más altos que intercambian velocidad y memoria (zstd) por mayores ratios de compresión. Esto se puede establecer añadiendo dos puntos y el nivel deseado. ZLIB acepta el rango [1, 9] y ZSTD acepta [1, 15]. Si no se establece ningún nivel, ambos actualmente usan un nivel predeterminado de 3. El valor 0 es un alias para el nivel

predeterminado.

De lo contrario, se aplican algunas heurísticas simples para detectar un archivo incompresible. Si los primeros bloques escritos en un archivo no son compresibles, todo el archivo se marca permanentemente para omitir la compresión. Dado que esto es demasiado simple, compress-force es una solución alternativa que comprimirá la mayoría de los archivos a costa de algunos ciclos de CPU desperdiciados en intentos fallidos. Desde el núcleo 4.15, un conjunto de algoritmos heurísticos ha mejorado mediante el uso de muestreo de frecuencia, detección de patrones repetidos y cálculo de entropía de Shannon para

evitarlo.

space_cache, space_cache=<version>,

(nospace_cache desde: 3.2, space_cache=v1 y space_cache=v2 desde 4.5, predeterminado: space_cache=v2)

Opciones para controlar la caché de espacio libre. La caché de espacio libre mejora enormemente el rendimiento al leer el espacio libre de los grupos de bloques en la memoria. Sin embargo, gestionar la caché de espacio consume algunos recursos, incluida una pequeña cantidad de espacio en

disco.

Hay dos implementaciones de la caché de espacio libre. La original, denominada v1, solía ser una opción predeterminada segura pero ha sido reemplazada por v2. La caché de espacio v1 puede desactivarse en el momento del montaje con nospace_cache sin

limpiarla.

En sistemas de archivos muy grandes (muchos terabytes) y ciertas cargas de trabajo, el rendimiento de la caché de espacio v1 puede degradarse drásticamente. La implementación v2, que añade un nuevo árbol B llamado árbol de espacio libre, aborda este problema. Una vez habilitada, la caché de espacio v2 se usará siempre y no podrá desactivarse a menos que se limpie. Utilice clear_cache,space_cache=v1 o clear_cache,nospace_cache para hacerlo. Si v2 está habilitada, la caché de espacio v1 se limpiará (en el primer montaje) y los núcleos sin soporte de v2 solo podrán montar el sistema de archivos en modo solo lectura. En un sistema de archivos desmontado, las cachés (ambas versiones) pueden limpiarse con "btrfs check --clear-space-ca

che".

Los comandos btrfs-check(8) <> y :doc:`mkfs.btrfs tienen soporte completo para la caché de espacio libre v2 desde la versión v4.

19.

ARCHIVOS_DE_SWAP

Los archivos de swap son la forma recomendada de añadir espacio de swap en Btrfs. Permiten crear el espacio de swap como un archivo normal en un sistema de archivos Btrfs. Este archivo puede ser copiado, enviado, clonado o copiado en la instantánea.

Sin embargo, hay algunas advertencias:

  • No se permite agujeros en el archivo de swap. Esto significa que el archivo debe ser asignado contiguamente. El comando `fallocate(1)` o el flag `nocow` (sin copy-on-write) son necesarios para asegurar esto.
  • El archivo de swap no puede ser copiado en la instantánea.
  • El archivo de swap no puede ser comprimido.
  • Los archivos de swap solo se pueden almacenar en dispositivos de un solo dispositivo.
  • Los archivos de swap no se pueden mezclar con la desduplicación.

Un archivo de swap activado se comportará de manera diferente dependiendo de si el subvolumen que lo contiene ha sido copiado en instantánea o no. Si el subvolumen ha sido copiado en instantánea, el archivo de swap se tratará como un archivo normal y no se compartirá con las instantáneas anteriores.

Si el subvolumen no ha sido copiado en instantánea, el archivo de swap se tratará como un archivo de swap y se compartirá con las instantáneas anteriores.

Una vez activado, el archivo de swap se comportará como un archivo normal para todos los fines, excepto para el de escribir datos. Esto significa que no se le aplicarán las escrituras de copiado en la instantánea y se comportará como un archivo normal en este sentido.

Sin embargo, los archivos de swap de Btrfs tienen algunas limitaciones importantes cuando se trata de operaciones de todo el sistema de archivos:

  • Las operaciones de todo el sistema de archivos que requieren que todas las extensiones de datos estén libres, como la reorganización de bloques (balance), fallarán si hay extensiones de archivos de swap activas.
  • Las operaciones de todo el sistema de archivos que intentan encoger el sistema de archivos pueden fallar si las extensiones de archivos de swap activas están fuera del rango encogido.

Cuando hay archivos de swap activos, las siguientes operaciones de todo el sistema de archivos omitirán las extensiones de archivos de swap o pueden fallar:

  • balance: se omitirán los grupos de bloques con extensiones de cualquier archivo de swap activo y se reportarán; el resto se procesará normalmente.
  • resize grow: no afectado.
  • resize shrink: funciona siempre que las extensiones de cualquier archivo de swap activo estén fuera del rango encogido.
  • device add: si los nuevos dispositivos no interfieren con ningún archivo de swap ya activo, esta operación funcionará, aunque no se podrá activar ningún archivo de swap nuevo después.
  • device delete: si el dispositivo se ha añadido como se ha indicado anteriormente, también se puede eliminar.
  • device replace: lo mismo.

Cuando no hay archivos de swap activos y se está ejecutando una operación exclusiva de todo el sistema de archivos (por ejemplo, balance, device delete, shrink), los archivos de swap no se pueden activar temporalmente. La operación debe finalizar primero.

Para crear y activar un archivo de swap, ejecute los siguientes comandos:

# truncate -s 0 swapfile
# chattr +C swapfile
# fallocate -l 2G swapfile
# chmod 0600 swapfile
# mkswap swapfile
# swapon swapfile

Desde la versión 6.1, es posible crear el archivo de swap en un solo comando (excepto la activación):

# btrfs filesystem mkswapfile --size 2G swapfile
# swapon swapfile

Tenga en cuenta que la UUID devuelta por la utilidad mkswap identifica el "sistema de archivos" de swap y, como se almacena en un archivo, generalmente no es visible ni utilizable como identificador, a diferencia de si estuviera en un dispositivo de bloque.

Una vez activado, el archivo aparecerá en /proc/swaps:

# cat /proc/swaps
Filename          Type          Size           Used      Priority
/path/swapfile    file          2097152        0         -2

El archivo de swap se puede crear como una operación única o, una vez creado correctamente, activarlo en cada arranque con el comando swapon -a (normalmente iniciado por el gestor de servicios). Añada la siguiente entrada a /etc/fstab, suponiendo que el sistema de archivos que proporciona /path ya se ha montado en este punto. También se pueden establecer opciones de montaje adicionales relevantes para el archivo de swap (como la prioridad, no las opciones de montaje de BTRFS).

/path/swapfile        none        swap        defaults      0 0

A partir de ahora, el subvolumen con el archivo de swap activo no se puede copiar en una instantánea hasta que el archivo de swap se desactive de nuevo con swapoff. Entonces, el archivo de swap es un archivo normal y el subvolumen puede volver a copiarse en una instantánea, aunque esto impediría otra activación de cualquier archivo de swap que se haya copiado en una instantánea. Se pueden crear y activar nuevos archivos de swap (no copiados en instantáneas).

De lo contrario, un archivo de swap inactivo no afecta al subvolumen que lo contiene. La activación crea un estado temporal en memoria e impide algunas operaciones de archivo, pero no se almacena de forma permanente.

HIBERNACIÓN

Un archivo de swap puede usarse para la hibernación, pero no es directo. Antes de la hibernación, se debe escribir un desplazamiento de reanudación en el archivo /sys/power/resume_offset o se debe establecer el parámetro de línea de comandos del kernel resume_offset.

El valor es el desplazamiento físico en el dispositivo. ¡Tenga en cuenta que **este no es el mismo** valor que **filefrag** imprime como desplazamiento físico!

El sistema de archivos Btrfs utiliza mapeos entre direcciones lógicas y físicas, pero aquí lo físico aún puede mapearse a una o más direcciones físicas de bloque específicas del dispositivo. Es el desplazamiento físico específico del dispositivo el que es adecuado como desplazamiento de reanudación.

Desde la versión 6.1, hay un comando btrfs inspect-internal map-swapfile <#man-inspect-map-swapfile> que imprimirá el desplazamiento físico del dispositivo y el valor ajustado para /sys/power/resume_offset. Tenga en cuenta que el valor se divide por el tamaño de página, es decir, no es el desplazamiento en sí mismo.

# btrfs filesystem mkswapfile swapfile
# btrfs inspect-internal map-swapfile swapfile
Physical start: 811511726080
Resume offset:     198122980

Para scripting y conveniencia, la opción -r imprimirá solo el desplazamiento:

# btrfs inspect-internal map-swapfile -r swapfile
198122980

El comando map-swapfile también verifica todos los requisitos, es decir, no hay agujeros, un solo dispositivo, etc.

ALGORITMOS_DE_SUMA_DE_VERIFICACIÓN

Los datos y metadatos se suman por defecto. La suma de verificación se calcula antes de escribir y se verifica después de leer los bloques de los dispositivos. El bloque de metadatos completo tiene una suma de verificación en línea almacenada en la cabecera del nodo b-tree. Cada bloque de datos tiene una suma de verificación separada almacenada en el árbol de sumas de verificación.

Nota:

Dado que la suma de verificación de datos se calcula justo antes de enviarla al dispositivo de bloques, btrfs tiene un requisito estricto de que el bloque de datos correspondiente no se modifique hasta que la escritura se haya completado.

Este requisito se cumple para una escritura en búfer, ya que btrfs tiene el control total de su caché de páginas, pero una escritura directa (O_DIRECT) omite la caché de páginas y btrfs no puede controlar el búfer de E/S directa (ya que puede estar en la memoria del espacio de usuario). Por lo tanto, es posible que un programa en el espacio de usuario modifique su búfer de escritura directa antes de que el búfer se escriba completamente, y esto puede provocar una discrepancia en la suma de verificación de datos.

Para evitar esto, el kernel a partir de la versión 6.14 forzará que una escritura directa vuelva a ser en búfer, si el inodo requiere una suma de verificación de datos. Esto implicará una pequeña penalización de rendimiento. Si requiere escrituras directas de cero copia reales, establezca la bandera NODATASUM para el inodo y asegúrese de que el búfer de E/S directa esté completamente alineado al tamaño del bloque.

Se admiten varios algoritmos de suma de verificación. El algoritmo predeterminado y compatible con versiones anteriores es crc32c. Desde el kernel 5.5, hay tres más con diferentes características y compensaciones en cuanto a velocidad y seguridad. La siguiente lista puede ayudarle a decidir cuál seleccionar.

CRC32C (resumen de 32 bits)
Predeterminado, mejor compatibilidad con versiones anteriores. Muy rápido, las CPU modernas tienen soporte a nivel de instrucción, no es resistente a colisiones pero todavía tiene buenas capacidades de detección de errores.
XXHASH (resumen de 64 bits)
Puede usarse como sucesor de CRC32C. Muy rápido, optimizado para CPU modernas que utilizan canalización de instrucciones, buena resistencia a colisiones y detección de errores.
SHA256 (resumen de 256 bits)
Hash de nivel criptográfico. Relativamente lento pero con posible aceleración de instrucciones de CPU o tarjetas de hardware especializadas. Certificado FIPS y ampliamente utilizado.
BLAKE2b (resumen de 256 bits)
Hash de nivel criptográfico. Relativamente rápido, con posible aceleración de CPU utilizando extensiones SIMD. No estandarizado pero basado en BLAKE, que fue finalista de SHA3, ampliamente utilizado. El algoritmo utilizado es BLAKE2b-256, optimizado para plataformas de 64 bits.

El tamaño del resumen afecta al tamaño total de las sumas de verificación de datos almacenadas en el sistema de archivos. Los bloques de metadatos tienen un área fija de hasta 256 bits (32 bytes), por lo que no hay aumento. Cada bloque de datos tiene una suma de verificación separada almacenada, con una sobrecarga adicional de las hojas b-tree.

Cualquier archivo que haya sido tocado por la llamada al sistema fallocate siempre quedará exceptuado de la compresión incluso si se usa la opción de montaje force-compress

La razón de esto es que una llamada exitosa a fallocate debe garantizar que las escrituras futuras al rango asignado no fallen por falta de espacio. de la compresión para todos lo

Los archivos con datos ya comprimidos o con datos que no se comprimirán bien con las restricciones de CPU y memoria de las implementaciones del núcleo utilizan una lógica de decisión simple. Si la primera porción de datos que se comprime no es más pequeña que el original, la compresión de todo el archivo se deshabilita. A menos que el sistema de archivos esté montado con compress-force en cuyo caso btrfs intentará comprimir cada bloque, recurriendo a almacenar la versión sin comprimir para cada bloque que resulte más grande después de la compresión. futuro.

montado.

HEURÍSTICAS DE

PRE-COMPRESIÓN

Las heurísticas pretenden realizar unas pocas pruebas estadísticas rápidas sobre los datos comprimidos para evitar una compresión probablemente costosa que resultaría ineficiente. Los algoritmos de compresión también podrían tener detección interna de datos incompresibles pero esto lleva a mel sobrecoste ya que la compresión se realiza en otro hilo y de todos modos tiene que escribir los datos. La heurística no requiere escritura y puede utilizar la memoria en caché.

Las pruebas realizadas se basan en: muestreo de datos, detección de patrones repetidos largos, frecuencia de bytes, entropía de Shannon.

COMPATIBILIDAD

La compresión requiere sumas de verificación de datos y COW, por lo tanto, la opción de montaje/bandera de inodo nodatasum o nodatasum resultará en ninguna compresión.

Las lecturas de IO directo de datos comprimidos siempre recurrirán a lecturas en búfer.

El comportamiento de escritura de IO directo depende de la bandera del inodo. Para inodos con suma de verificación de datos, las escrituras de IO directo siempre recurrirán a escrituras en búfer, por lo tanto, pueden generar datos comprimidos si la opción de montaje/banderas de inodo lo permite.

Para inodos sin sumas de verificación de datos, las escrituras de IO directo no poblarán la caché de páginas y, dado que el inodo no tiene sumas de verificación de datos, de todos modos no se generarán datos comprimidos.

Los algoritmos de compresión se han agregado con el tiempo, por lo que también se debe considerar la compatibilidad de versiones, junto con otras herramientas que pueden acceder a los datos comprimidos, como los cargadores de arranque.

El sistema de archivos btrfs admite el establecimiento de atributos o banderas de archivo. Tenga en cuenta que existen interfaces antiguas y nuevas, con nombres confusos. La siguiente lista debería aclarar eso:

  • atributos: utilidades chattr(1) https://man7.org/linux/man-pages/man1/chattr.1.html o lsattr(1) https://man7.org/linux/man-pages/man1/lsattr.1.html (los ioctl son FS_IOC_GETFLAGS y FS_IOC_SETFLAGS), debido a los nombres de los ioctl, los atributos también se llaman banderas.

MODO ZONIFICADO (ZONED MODE)

Desde la versión 5.12, btrfs soporta el llamado modo zonificado. Este es un formato especial en disco y una estrategia de asignación/escritura que es amigable para dispositivos zonificados. En resumen, un dispositivo se divide en zonas de tamaño fijo y cada zona se puede actualizar de forma append-only (solo añadir), o restablecer. Dado que btrfs no tiene estructuras de datos fijas, excepto las superbloques, el modo zonificado solo requiere una colocación de bloques que siga las restricciones del dispositivo. Puede aprender sobre toda la arquitectura en https://zonedstorage.io.

Los dispositivos también se denominan SMR/ZBC/ZNS, en modo de gestión por el host (host-managed). Tenga en cuenta que hay dispositivos que parecen no zonificados pero que en realidad lo son, esto es gestión por el disco (drive-managed) y el uso del modo zonificado no ayudará.

El tamaño de la zona depende del dispositivo, los tamaños típicos son 256MiB o 1GiB. En general, debe ser una potencia de dos. Los dispositivos zonificados emulados como null_blk permiten establecer varios tamaños de zona.

Requisitos, limitaciones

  • todos los dispositivos deben tener el mismo tamaño de zona.
  • el tamaño máximo de zona es 8GiB.
  • el tamaño mínimo de zona es 4MiB.
  • la mezcla de dispositivos zonificados y no zonificados es posible, las escrituras de zona se emulan, pero esto es principalmente para pruebas.
  • la superbloque se maneja de forma especial y se encuentra en ubicaciones diferentes que en un sistema de archivos no zonificado:
  • primaria: 0B (y las dos zonas siguientes)
  • secundaria: 512GiB (y las dos zonas siguientes)
  • terciaria: 4TiB (4096GiB, y las dos zonas siguientes)

Características incompatibles

La principal restricción de los dispositivos zonificados es la falta de actualización in situ de los datos. Esto es inherentemente incompatible con algunas características:

  • NODATACOW - sobrescribir in situ, no se pueden crear tales archivos.
  • fallocate - preasignación de espacio para la primera escritura in situ.
  • mixed-bg - escrituras desordenadas a datos y metadatos, corregir eso significa usar grupos de bloques de datos y metadatos separados.
  • arranque - la zona en el desplazamiento 0 contiene la superbloque, restablecer la zona destruiría los datos del cargador de arranque.

El soporte inicial carece de algunas características, pero están planeadas:

  • solo se admiten los perfiles simple (datos, metadatos) y DUP (metadatos).
  • fstrim - debido a la dependencia del caché de espacio libre v1.

Super bloque

Como se mencionó anteriormente, la superbloque se maneja de forma especial. Para que sea segura ante fallos, al menos una zona en una ubicación conocida debe contener una superbloque válida. Esto se implementa como un búfer circular en dos zonas consecutivas, comenzando desde los desplazamientos conocidos 0B, 512GiB y 4TiB.

Los valores son diferentes a los de los dispositivos no zonificados. Cada nueva superbloque se añade al final de la zona; una vez que se llena, la zona se restablece y las escrituras continúan en la siguiente

uno. Buscar el último super bloque necesita leer los desplazamientos de ambas zonas y determinar la última versión

escrita.

La cantidad de espacio reservada para el super bloque depende del tamaño de la zona. Las copias secundaria y terciaria están en desplazamientos distantes, ya que se espera que

la capacidad de los dispositivos sea grande, decenas de terabytes. El tamaño de zona máximo admitido es 8GiB, lo que significaría que, por ejemplo, el desplazamiento 0-16GiB
se reservaría solo para el super bloque en un dispositivo hipotético de ese tamaño de zona. Esto es un desperdicio, pero es necesario para garantizar la seguridad ante caídas.

Reclamación de zonas, recolección de

basura

Dado que las zonas son de solo adición, sobrescribir datos o los cambios COW en los metadatos hacen que partes de las zonas estén utilizadas pero no conectadas a las estructuras del sistema de archivos. Esto hace que el espacio sea inutilizable y crece con el tiempo. Una vez que la relación alcanza un umbral (configurable), se inicia un proceso de reclamación en segundo plano y reubica los bloques restantes en uso en una nueva zona. La antigua se restablece y puede usarse de

nuevo.

Este proceso puede llevar algún tiempo dependiendo de otros trabajos en segundo

plano o de la cantidad de nuevos datos escritos. Es posible encontrar un ENOSPC
intermitente. Algunos dispositivos también limitan el número de zonas activas.

El mecanismo COW y múltiples dispositivos bajo un mismo capó permiten un concepto interesante, llamado dispositivo de siembra: extender un sistema de archivos de solo lectura en un dispositivo con otro dispositivo que captura todas las escrituras. Por ejemplo, imagina una imagen dorada inmutable de un sistema operativo mejorada con otro dispositivo que permite usar los datos de la imagen dorada y la operación normal. Esta idea se originó en CD-ROMs con el SO base y permitiendo usarlos para sistemas en vivo, pero esto se volvió obsoleto. Hay tecnologías que proporcionan funcionalidad similar, como unionmount https://en.wikipedia.org/wiki/Union_mount, overlayfs https://en.wikipedia.org/wiki/OverlayFS o qcow2 https://en.wikipedia.org/wiki/Qcow#qcow2 imagen

snapshot.

El dispositivo de siembra comienza como un sistema de archivos normal, una vez que el contenido está listo, btrfstune -S 1 se usa para marcarlo como un dispositivo de siembra. Montar tal dispositivo no permitirá ninguna escritura, excepto añadir un nuevo dispositivo con btrfs device add. Luego el sistema de archivos puede ser remontado como de lectura-escritura

Dado que el sistema de archivos en el dispositivo de siembra siempre se reconoce como de solo lectura, se puede usar para sembrar múltiples sistemas de archivos desde un dispositivo al mismo tiempo. El UUID que normalmente está adjunto a un dispositivo se cambia automáticamente a un UUID aleatorio en cada

montaje.

RAID56

La función RAID56 proporciona striping y paridad sobre varios dispositivos, igual que el RAID5/6 tradicional. Hay algunas deficiencias de implementación y diseño que lo hacen poco confiable para algunos casos extremos y la función no debería usarse en producción, solo para evaluación o pruebas. La seguridad ante fallos de energía para metadatos con RAID56 no es

100%.

Metadato

s

No uses raid5 ni raid6 para metadatos. Usa raid1 o raid1c3 respectivamente

.

Los perfiles sustitutos proporcionan las mismas garantías contra la pérdida de 1 o 2 dispositivos, y en cierto sentido pueden ser una mejora. Recuperarse de un dispositivo faltante solo necesitará acceder a la copia restante 1ª o 2ª, que en general puede estar almacenada en algunos otros dispositivos debido a la forma en que RAID1 funciona en btrfs, a diferencia de un perfil striped (similar a raid0) que necesitaría todos los dispositivos todo el

tiempo.

El patrón de asignación y consumo de espacio es diferente (p. ej. en N dispositivos): para raid5 como ejemplo, un chunk de 1GiB se reserva en cada dispositivo, mientras que con raid1 cada chunk de 1GiB se almacena en 2 dispositivos. El consumo de cada 1GiB de metadatos usados es entonces N * 1GiB vs 2 * 1GiB. Usar raid1 es también más conveniente para balancear/convertir a otro

perfil debido al menor requisito d
e espacio de chunk disponible.

Soporte faltante/incomplet

o

Cuando RAID56 está en el mismo sistema de archivos con diferentes perfiles raid, el reporte de espacio es inexacto, p. ej. df, btrfs filesystem df o btrfs filesystem usage. Cuando hay solo un perfil por tipo de grupo de bloques (p. ej. RAID5 para datos) el reporte es

exacto.

Cuando se inicia un scrub en un sistema de archivos RAID56, se inicia en todos los dispositivos lo que degrada el rendimiento. La solución es iniciarlo en cada dispositivo por separado. Debido a eso las estadísticas del dispositivo pueden no coincidir con el estado real y algunos errores pueden reportarse múltiples

veces.

El problema del agujero de escritura. Un apagado sucio podría dejar una tira parcialmente escrita en un estado donde algunas rangos de tira y la paridad son de escrituras antiguas y algunas son nuevas. La información de cuál es cuál no se rastrea. El diario de escritura no está implementado. Alternativamente una lectura-modificación completa-write garantizaría que siempre se escriba una franja completa, evitando completamente el agujero de escritura, pero el rendimiento en ese caso resultó ser demasiado malo para su

uso.

El striping ocurre en todos los dispositivos disponibles (en el mome

nto en que se asignaron los chunks), por lo que si se agrega un nuevo

MODELO DE ALMACENAMIENTO, CONSIDERACIONES DE HARDWARE

Modelo de almacenamiento

Un modelo de almacenamiento es un modelo que captura aspectos físicos clave de la estructura de datos en un almacén de datos. Un sistema de archivos es la estructura lógica que organiza los datos sobre el dispositivo de almacenamiento.

El sistema de archivos asume varias características o limitaciones del dispositivo de almacenamiento y las utiliza o aplica medidas para garantizar la fiabilidad. BTRFS en particular se basa en un modo de escritura COW (copy on write), es decir, no actualiza los datos en el lugar, sino que escribe una nueva copia en una ubicación diferente y luego cambia atómicamente los punteros.

En un mundo ideal, el dispositivo cumple lo que promete. El sistema de archivos asume que esto puede no ser cierto, por lo que se aplican mecanismos adicionales para detectar hardware que no se comporta correctamente o para obtener datos válidos por otros medios. Los dispositivos pueden (y lo hacen) aplicar sus propios mecanismos de detección y reparación, pero no asumiremos ninguno.

Memoria

principal

Las estructuras de datos y los bloques de datos sin procesar se almacenan temporalmente en la memoria de la computadora antes de ser escritos en el dispositivo. Es crítico que la memoria sea confiable porque incluso simples inversiones de bits (bit flips) pueden tener vastas consecuencias y llevar a estructuras dañadas, no solo en el sistema de archivos sino en todo el sistema

operativo.

Basado en la experiencia en la comunidad, las inversiones de bits en la memoria son más comunes de lo que uno pensaría. Cuando ocurre, es reportado por el verificador de árboles (tree-checker) o por una discrepancia de suma de verificación después de leer bloques. Hay algunas instancias muy obvias de inversiones de bits que ocurren, por ejemplo, en una secuencia ordenada de claves en bloques de metadatos. Podemos inferir fácilmente a partir de otros datos qué valores se dañan y cómo. Sin embargo, arreglar eso no es directo y requeriría referencias cruzadas de datos de todo el sistema de archivos para ver el

alcance.

Si está disponible, la memoria ECC debería reducir las posibilidades de inversiones de bits, pero este tipo de memoria no está disponible en todos los casos. Se debería realizar una prueba de memoria en caso de que haya un patrón visible de inversiones de bits, aunque esto puede no detectar un módulo de memoria defectuoso porque la carga real del sistema podría ser el factor que haga aparecer los problemas. En los últimos años se han demostrado ataques sobre cómo operan los módulos de memoria (rowhammer) logrando que bits específicos se inviertan. Aunque estos fueron dirigidos, esto demuestra que una serie de lecturas o escrituras puede afectar partes no relacionadas de la

memoria.

Los perfiles de grupos de bloques con redundancia (como RAID1) no protegerán contra errores de memoria ya que los bloques se almacenan primero en la memoria antes de ser escritos en los dispositivos desde la misma

fuente.

Un sistema de archivos montado de solo lectura no afectará al dispositivo de bloques subyacente en casi el 100% (con excepciones altamente improbables). La excepción es un registro de árbol (tree-log) que necesita ser reproducido durante el montaje (y antes de que el montaje de solo lectura tenga lugar), se necesita memoria de trabajo para eso y esta puede ser afectada por inversiones de bits. Existe un caso teórico donde una inversión de bit cambia el estado del sistema de archivos de solo lectura a lectura/escritura

.

Discos rotacionales

(HDD)

Los HDD rotacionales típicamente fallan a nivel de sectores individuales o pequeños clústeres. Los fallos de lectura son capturados en los niveles por debajo del sistema de archivos y se devuelven al usuario como EIO - Error de entrada/salida (Input/output error). Leer los bloques repetidamente puede devolver los datos eventualmente, pero esto es mejor hecho por herramientas especializadas y el sistema de archivos toma el resultado de las capas inferiores. Reescribir los sectores puede provocar un remapeo interno, pero esto inevitablemente lleva a una pérdida de

datos.

El firmware del disco es técnicamente software pero desde la perspectiva del sistema de archivos es parte del hardware. Las solicitudes de E/S son procesadas, y se realizan almacenamiento en caché u otras various optimizaciones, lo que puede llevar a errores bajo alta carga o condiciones físicas inesperadas o casos de uso no

soportados.

Los discos están conectados por cables con dos extremos, ambos de los cuales pueden causar problemas cuando no se conectan adecuadamente. Las transferencias de datos están protegidas por sumas de verificación (checksums) y las capas inferiores se esfuerzan por transferir los datos correctamente o no transferirlos en absoluto. Los errores de cables mal conectados pueden manifestarse como una gran cantidad de solicitudes de lectura o escritura fallidas, o como ráfagas cortas de error dependiendo de las condiciones

físicas.

Unidades de estado sólido

(SSD)

El mecanismo de almacenamiento de información es diferente al de los HDD y esto afecta también al modo de fallo. Los datos se almacenan en celdas agrupadas en bloques grandes con un número limitado de reinicios y otras restricciones de escritura. El firmware intenta evitar reinicios innecesarios y realiza optimizaciones para maximizar la vida útil del medio de almacenamiento. Las técnicas conocidas son la deduplicación (bloques con la misma huella/hash se mapean al mismo bloque físico), compresión o remapeo interno y recolección de basura (garbage collection) de celdas de memoria usadas. Debido al procesamiento adicional, existen medidas para verificar los datos, por ejemplo mediante códigos

ECC.

Las observaciones de SSDs fallando muestran que toda la electrónica falla a la vez o afecta a muchos datos (por ejemplo, almacenados en un chip). Recuperar tales datos puede necesitar equipo especializado y leer los datos repetidamente no ayuda como puede ocurrir con los

HDD.

Hay varias tecnologías de celdas de memoria con diferentes características y precios. La vida útil se ve afectada directamente por el tipo y la frecuencia de los datos escritos. Escribir "demasiados" datos distintos (por ejemplo, cifrados) puede hacer que la deduplicación interna sea ineficaz y llevar a muchas reescrituras y un mayor desgaste de las celdas de

memoria.

hardware.
