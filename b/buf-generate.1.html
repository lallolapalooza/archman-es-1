NOMBRE

buf-generate - Genera código con plugins de protoc

SINOPSIS

buf generate [flags]

DESCRIPCIÓN

Este comando utiliza un archivo de plantilla con la siguiente estructura:

# buf.gen.yaml
# La versión de la plantilla de generación.
# Los valores válidos son v1beta1, v1 y v2.
# Requerido.
version: v2
# Cuando clean se establece en true, elimina los directorios, archivos zip y/o
# archivos jar especificados en el campo "out" para todos los plugins antes de
# ejecutar la generación de código. Por defecto es false.
# Opcional.
clean: true
# Los plugins a ejecutar.
# Requerido.
plugins:
    # Usa el plugin alojado en buf.build/protocolbuffers/go en la versión v1.28.1.
    # Si se omite la versión, se usa la última versión del plugin.
    # Se requiere uno de "remote", "local" y "protoc_builtin".
  - remote: buf.build/protocolbuffers/go:v1.28.1
    # El directorio de salida relativo.
    # Requerido.
    out: gen/go
    # La revisión del plugin remoto a usar, un número de secuencia que Buf
    # incrementa al reconstruir o reenpaquetar el plugin.
    revision: 4
    # Cualquier opción a proporcionar al plugin.
    # Esto puede ser una cadena única o una lista de cadenas.
    # Opcional.
    opt: paths=source_relative
    # Si generar código para archivos importados también.
    # Opcional.
    include_imports: false
    # Si generar código para los tipos bien conocidos.
    # Opcional.
    include_wkt: false
    # Incluir solo estos tipos para este plugin.
    # Opcional.
    types:
      - "foo.v1.User"
    # Excluir estos tipos para este plugin.
    # Opcional.
    exclude_types:
      - "buf.validate.oneof"
      - "buf.validate.message"
      - "buf.validate.field""
    # El nombre de un plugin local si es detectable en "${PATH}" o su ruta en el
    # sistema de archivos.
  - local: protoc-gen-es
    out: gen/es
    include_imports: true
    include_wkt: true
    # La invocación completa de un plugin local se puede especificar como una lista.
  - local: ["go", "run", "path/to/plugin.go"]
    out: gen/plugin
    # La estrategia de generación a usar. Hay dos opciones:
    #
    # 1. "directory"
    #
    #   Esto hará que buf divida los archivos de entrada por directorio y realice
    #   invocaciones de plugin separadas en paralelo. Esto es aproximadamente el
    #   equivalente concurrente de:
    #
    #     for dir in $(find . -name '*.proto' -print0 | xargs -0 -n1 dirname | sort | uniq); do
    #       protoc -I . $(find "${dir}" -name '*.proto')
    #     done
    #
    #   Casi todos los plugins de Protobuf requieren esto, o funcionan con esto,
    #   y este es el valor recomendado y predeterminado.
    #
    # 2. "all"
    #
    #   Esto hará que buf realice una única invocación de plugin con todos los
    #   archivos de entrada. Esto es aproximadamente el equivalente de:
    #
    #     protoc -I . $(find . -name '*.proto')
    #
    #   Esto es necesario para ciertos plugins que esperan que se les proporcionen
    #   todos los archivos a la vez. Esta es también la única estrategia para los
    #   plugins remotos.
    #
    # Si se omite, se usa "directory". La mayoría de los usuarios no necesitan
    # establecer esta opción.
    # Opcional.
    strategy: directory
    # "protoc_builtin" especifica un plugin que viene con protoc, sin el prefijo
    # "protoc-gen-".
  - protoc_builtin: java
    out: gen/java
    # Ruta a protoc. Si no se especifica, se utiliza la instalación de protoc en
    # "${PATH}".
    # Opcional.
    protoc_path: path/to/protoc
# Managed mode modifica las opciones de archivo y/o las opciones de campo sobre
# la marcha.
managed:
  # Habilita el modo gestionado.
  enabled: true
  # Cada regla de anulación especifica una opción, el valor para esta opción y,
  # opcionalmente, los archivos/campos para los que se aplica la anulación.
  #
  # Las opciones de archivo aceptadas son:
  #  - java_package
  #  - java_package_prefix
  #  - java_package_suffix
  #  - java_multiple_files
  #  - java_outer_classname
  #  - java_string_check_utf8
  #  - go_package
  #  - go_package_prefix
  #  - optimize_for
  #  - csharp_namespace
  #  - csharp_namespace_prefix
  #  - ruby_package
  #  - ruby_package_suffix
  #  - objc_class_prefix
  #  - php_namespace
  #  - php_metadata_namespace
  #  - php_metadata_namespace_suffix
  #  - cc_enable_arenas
  #
  # Una regla de anulación puede aplicarse a una opción de campo.
  # Las opciones de campo aceptadas son:
  #  - jstype
  #
  # Si múltiples anulaciones para la misma opción se aplican a un archivo o
  # campo, la última regla tiene efecto.
  # Opcional.
  override:
      # Establece "go_package_prefix" a "foo/bar/baz" para todos los archivos.
    - file_option: go_package_prefix
      value: foo/bar/baz
      # Establece "java_package_prefix" a "net.foo" para archivos en
      # "buf.build/foo/bar".
    - file_option: java_package_prefix
      value: net.foo
      module: buf.build/foo/bar
      # Establece "java_package_prefix" a "dev" para "file.proto".
      # Esto anula el valor "net.foo" para "file.proto" de la regla anterior.
    - file_option: java_package_prefix
      value: dev
      module: buf.build/foo/bar
      path: file.proto
      # Establece "go_package" a "x/y/z" para todos los archivos en el
      # directorio "x/y/z".
    - file_option: go_package
      value: foo/bar/baz
      path: x/y/z
      # Establece el "jstype" de un campo a "JS_NORMAL".
    - field_option: jstype
      value: JS_STRING
      field: foo.v1.Bar.baz
  # Deshabilita el modo gestionado bajo ciertas condiciones.
  # Tiene precedencia sobre "overrides".
  # Opcional.
  disable:
      # No modificar ninguna opción para archivos en este módulo.
    - module: buf.build/googleapis/googleapis
      # No modificar ninguna opción para este archivo.
    - module: buf.build/googleapis/googleapis
      path: foo/bar/file.proto
      # No modificar "java_multiple_files" para ningún archivo
    - file_option: java_multiple_files
      # No modificar "csharp_namespace" para archivos en este módulo.
    - module: buf.build/acme/weather
      file_option: csharp_namespace
# Las entradas para generar código.
# Las entradas aquí se ignoran si se especifica una entrada como argumento de
# línea de comandos.
# Cada entrada es uno de "directory", "git_repo", "module", "tarball", "zip_archive",
# "proto_file", "binary_image", "json_image", "text_image" y "yaml_image".
# Opcional.
inputs:
    # La ruta a un directorio.
  - directory: x/y/z
    # La URL de un repositorio Git.
  - git_repo: https://github.com/acme/weather.git
    # La rama a clonar.
    # Opcional.
    branch: dev
    # El subdirectorio en el repositorio a usar.
    # Opcional.
    subdir: proto
    # Profundidad del clon a realizar.
    # Opcional.
    depth: 30
    # La URL de un módulo BSR.
  - module: buf.build/acme/weather
    # Generar código solo para estos tipos.
    # Opcional.
    types:
      - "foo.v1.User"
      - "foo.v1.UserService"
    # Excluir estos tipos.
    # Opcional.
    exclude_types:
      - "buf.validate"
    # Generar código solo para archivos en estas rutas.
    # Si está vacío, incluir todas las rutas.
    paths:
      - a/b/c
      - a/b/d
    # No generar código para archivos en estas rutas.
    exclude_paths:
      - a/b/c/x.proto
      - a/b/d/y.proto
    # La URL o ruta a un archivo tar.
  - tarball: a/b/x.tar.gz
    # La ruta relativa dentro del archivo a usar como directorio base.
    # Opcional.
    subdir: proto
    # El esquema de compresión, derivado de la extensión del archivo si no se
    # especifica.
    # Las extensiones ".tgz" y ".tar.gz" usan Gzip automáticamente.
    # ".tar.zst" usa Zstandard automáticamente.
    # Opcional.
    compression: gzip
    # Lee en la ruta relativa y elimina un número determinado de componentes.
    # Opcional.
    strip_components: 2
    # La URL o ruta a un archivo zip.
  - zip_archive: https://github.com/googleapis/googleapis/archive/master.zip
    # El número de directorios a eliminar.
    # Opcional.
    strip_components: 1
    # La ruta a un archivo proto específico.
  - proto_file: foo/bar/baz.proto
    # Si generar código para archivos en el mismo paquete también, por defecto es false.
    # Opcional.
    include_package_files: true
    # Una imagen Buf en formato binario.
    # Otros formatos de imagen son "yaml_image", "text_image" y "json_image".
  - binary_image: image.binpb.gz
    # El esquema de compresión del archivo de imagen, derivado de la extensión
    # del archivo si no se especifica.
    # Opcional.
    compression: gzip

Como ejemplo, aquí hay un "buf.gen.yaml" típico para go y grpc, asumiendo que "protoc-gen-go" y "protoc-gen-go-grpc" están en su "$PATH":

# buf.gen.yaml
version: v2
plugins:
  - local: protoc-gen-go
    out: gen/go
    opt: paths=source_relative
  - local: protoc-gen-go-grpc
    out: gen/go
    opt:
      - paths=source_relative
      - require_unimplemented_servers=false

Por defecto, buf generate buscará un archivo con esta forma llamado "buf.gen.yaml" en su directorio actual. Esto puede considerarse como una plantilla para el conjunto de plugins que desea invocar.

El primer argumento es la fuente, el módulo o la imagen de la cual generar. Por defecto es "." si no se especifica ningún argumento.

Utilice buf.gen.ya

ml como plantilla, directorio actual como

entrada: 
$ buf
generate

Igual que los valores predeterminados (plantilla de "buf.gen.yaml", directorio actual como entrada)

: 
$buf generate --template buf.gen.yaml
.

La bandera --template también acepta datos YAML o JSON como entrada, por lo que se puede usar sin un

archivo: 
$buf generate --template '{"version":"v2","plugins":[{"local":"protoc-gen-go","out":"gen/go"}]}
'

Descarga el repositorio y genera stubs de código según la plantilla bar.

yaml: 
$buf generate --template bar.yaml https://github.com/foo/bar.
git

Genera en el directorio bar/, anteponiendo bar/ a las directivas out en la

plantilla: 
$buf generate --template bar.yaml -o bar https://github.com/foo/bar.
git

Las rutas en la plantilla y la bandera -o se interpretarán como relativas al directorio actual, por lo que puedes colocar tus archivos de plantilla en cualquier

lugar.

Si solo quieres generar stubs para un subconjunto de tu entrada, puedes hacerlo mediante --path. Por

ejemplo,

Generar solo para los archivos en los directorios proto/foo y

proto/bar: 
$buf generate --path proto/foo --path
proto/bar

Generar solo para los archivos proto/foo/foo.proto y proto/foo/bar.

proto: 
$buf generate --path proto/foo/foo.proto --path proto/foo/bar.
proto

Generar solo para los archivos en el directorio proto/foo de tu repositorio

git: 
$buf generate --template buf.gen.yaml https://github.com/foo/bar.git --path
proto/foo

Ten en cuenta que todas las rutas deben estar contenidas dentro del mismo módulo. Por ejemplo, si tienes un módulo en "proto", no puedes especificar "--path proto", sin embargo, "--path proto/foo" está permitido ya que "proto/foo" está contenido dentro de

"proto".

Los plugins se invocan en el orden en que se especifican en la plantilla, pero cada plugin tiene una invocación paralela por directorio, con los resultados de cada invocación combinados antes de escribir el

resultado.

Los puntos de inserción se procesa

n en el orden en que los plugins se especifican en la plantilla.
