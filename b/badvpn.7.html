NOMBRE

BadVPN - sistema VPN peer-to-peer

DESCRIPCIÓN

BadVPN es un sistema VPN peer-to-peer. Proporciona una red de nivel 2 (Ethernet) entre los pares (nodos de la red VPN). Los pares se conectan a un servidor central que actúa como servidor de chat para que establezcan conexiones directas entre sí (conexiones de datos). Estas conexiones se utilizan para transferir datos de red (tramas Ethernet).

Características

Conexiones de datos

Los pares pueden transferir datos de red ya sea mediante UDP o TCP. Para ambos existen formas de asegurar los datos (véase más abajo).

Soporte IPv6

IPv6 puede utilizarse tanto para las conexiones al servidor como para las conexiones de datos, junto con IPv4. Adicionalmente, ambos pueden combinarse para permitir una migración gradual a IPv6.

Selección de dirección

Debido a que los NAT y los cortafuegos están muy extendidos, es más difícil para los servicios peer-to-peer operar. En general, para que dos ordenadores puedan comunicarse, un ordenador debe enlazar a una de sus direcciones, y el otro ordenador debe conectarse al ordenador que enlazó (tanto para TCP como para UDP). En una red con conectividad punto a punto, el ordenador que se conecta puede conectarse a la misma dirección a la que el ordenador enlazante enlazó, por lo que es suficiente con que el ordenador enlazante envíe su dirección al ordenador que se conecta. Sin embargo, los NAT y los cortafuegos rompen la conectividad punto a punto. Cuando una red está detrás de un NAT, es, por defecto, imposible que los ordenadores externos a esa red se conecten a los ordenadores dentro de la red. Esto se debe a que los ordenadores dentro de la red no tienen una dirección IP visible externamente, y solo se comunican con el mundo exterior a través de la dirección IP externa del router NAT. Sin embargo, es posible configurar manualmente el router NAT para reenviar un número de puerto específico en su dirección IP externa a un ordenador específico dentro de la red. Esto hace posible que un ordenador externo a la red se conecte a un ordenador dentro de una red, sin embargo, debe conectarse a la dirección externa del router NAT (en lugar de la dirección a la que el ordenador interno enlazó, que es su dirección interna). Por lo tanto, debe haber alguna manera para que el par que se conecta sepa a qué dirección conectarse.

BadVPN resuelve este problema con las llamadas ámbitos de dirección. El par que enlaza debe tener una lista de direcciones externas para cada dirección a la que pueda enlazar, posiblemente ordenadas de mejor a peor. Cada dirección externa tiene su nombre de ámbito. Un nombre de ámbito representa parte de una red desde la que se puede alcanzar una dirección externa. Por otro lado, el par que se conecta debe tener una lista de ámbitos a los que puede llegar. Cuando un par enlaza a una dirección, envía al otro par una lista de direcciones externas junto con los nombres de ámbito. Ese par elige entonces la primera dirección externa cuyo ámbito reconoce e intenta conectarse a ella (si hay alguna).

BadVPN también permite que un par tenga múltiples direcciones para enlazar. Es posible especificar tanto una dirección IPv4 como una dirección IPv6 para trabajar en un entorno multiprotocolo.

Reenvío (Relaying)

BadVPN puede configurarse para permitir que pares que no pueden comunicarse directamente (es decir, debido a NATs o cortafuegos) reenvíen datos de red a través de un tercer par. El reenvío solo se intenta si ninguno de los dos pares reconoce ninguna de las direcciones externas del otro par (o no hay ninguna). Para que el reenvío funcione, para cada uno de los dos pares (P1, el otro P2) debe haber al menos un tercer par (R) a través del cual P1 tenga permitido reenviar y con el que pueda comunicarse directamente, y todos esos pares R deben poder comunicarse directamente con P2.

IGMP snooping

Los nodos de BadVPN realizan IGMP snooping para entregar tramas de multidifusión de manera eficiente. Por ejemplo, esto hace posible usar BadVPN como un túnel hacia una red IPTV de un Proveedor de Servicios de Internet para que puedas ver TV desde donde quieras (dada una calidad de enlace suficiente).

Calidad del código

BadVPN tiene un gran enfoque en la calidad y fiabilidad del código. BadVPN está escrito en el lenguaje de programación C. Es un programa de un solo hilo impulsado por eventos. Esto permite un bajo uso de recursos y tiempos de respuesta rápidos. Aunque C es un lenguaje de bajo nivel relativamente, los programas están hechos de módulos pequeños, altamente cohesivos y débilmente acoplados que se combinan en un programa completo a un alto nivel. Los módulos se acceden y se comunican a través de interfaces pequeñas, simples y directas. Utiliza un diseño basado en flujos que simplifica enormemente el procesamiento de datos y la entrada y salida de los programas.

Características de seguridad

BadVPN contiene muchas características de seguridad, todas las cuales son opcionales. Las características de seguridad incluidas se describen aquí.

TLS para conexiones cliente-servidor

Es posible que los pares se comuniquen con el servidor de chat de forma segura con TLS. Se recomienda encarecidamente que se utilice esta característica si se necesita alguna seguridad. No usarla hace que todas las demás características de seguridad sean inútiles, ya que los clientes intercambian claves sin cifrar a través del servidor. Cuando está habilitado, el servidor de chat requiere que cada cliente se identifique con un certificado.

BadVPN usa la biblioteca NSS de Mozilla para el soporte TLS. Esto significa que los certificados y claves requeridos deben estar disponibles en una base de datos NSS. La base de datos y los certificados pueden generarse con el certutil comando. Véase la sección de ejemplos sobre cómo generar y distribuir los certificados.

TLS para mensajería entre pares

Si se está usando TLS para conexiones cliente-servidor, también se usará entre cada par de pares que se comuniquen a través del servidor, encima de las conexiones TLS al servidor. Esto asegura los mensajes del propio servidor. Es importante porque los mensajes pueden incluir claves de cifrado y otros datos privados.

TLS para conexiones de datos TCP

Si se usa TCP para las conexiones de datos entre los pares, las conexiones de datos pueden asegurarse con TLS. Esto requiere usar TLS para las conexiones cliente-servidor. Los clientes necesitan confiar en los certificados de los demás para poder conectarse. Adicionalmente, cada cliente debe identificarse ante sus pares con los mismos certificados que usó para conectarse al servidor.

Cifrado para conexiones de datos UDP

Si se usa UDP para las conexiones de datos, es posible que cada par de pares cifre sus paquetes UDP con un cifrado de bloque simétrico. Nótese que las claves de cifrado se transmiten a través del servidor sin cifrar, por lo que para que esto sea útil, las conexiones al servidor deben asegurarse con TLS. El cifrado tiene como objetivo evitar que terceros vean el contenido real de los datos de red que se transfieren.

Hashes para conexiones de datos UDP

Si se usa UDP para las conexiones de datos, es posible incluir hashes en los paquetes. Nótese que los hashes solo son útiles junto con el cifrado. Si está habilitado, el hash se calcula sobre el paquete con el campo de hash a cero y luego se escribe en el campo de hash. Los hashes se calculan y se incluyen antes del cifrado (si está habilitado). Combinado con el cifrado, los hashes tienen como objetivo evitar que terceros manipulen los paquetes y los inyecten en la red.

Contraseñas de un solo uso para conexiones de datos UDP

Si se usa UDP para las conexiones de datos, es posible incluir contraseñas de un solo uso en los paquetes. Nótese que para que esto sea útil, las conexiones al servidor deben asegurarse con TLS. Las contraseñas de un solo uso se generan a partir de un valor semilla cifrando datos cero con un cifrado de bloque. La semilla contiene la clave de cifrado para el cifrado de bloque y el vector de inicialización. Solo se usa un número fijo de contraseñas de una sola semilla. Los pares intercambian semillas a través del servidor. Las contraseñas de un solo uso tienen como objetivo evitar ataques de repetición.

Control sobre la comunicación entre pares

Es posible instruir al servidor de chat para que solo permita que ciertos pares se comuniquen. Esto romperá la conectividad extremo a extremo en la red virtual. Es útil en ciertos casos para mejorar la seguridad, por ejemplo cuando la VPN se usa solo para permitir que los clientes se conecten de forma segura a un servicio central.

EJEMPLOS

Configuración de certificados

Si quieres usar TLS para las conexiones al servidor (recomendado), el servidor y todos los pares necesitarán certificados. Esta sección explica cómo generar y distribuir los certificados usando las herramientas de línea de comandos NSS.

Configuración de la Autoridad de Certificación (CA)

En el sistema que alojará la CA, crea una base de datos NSS

CONFIGURACIÓN DE CERTIFICADOS

Esta sección describe cómo crear una Autoridad de Certificación (CA) de confianza, y generar certificados para el servidor y los peers.

Configuración de la CA

En el sistema que actuará como CA, cree una base de datos NSS y genere un certificado de CA válido por 24 meses:

vpnca $ certutil -d sql:/home/vpnca/nssdb -N
vpnca $ certutil -d sql:/home/vpnca/nssdb -S -n "vpnca" -s "CN=vpnca" -t "TC,," -x -2 -v 24
> ¿Es este un certificado de CA [y/N]? y
> Introduzca la restricción de longitud de ruta, pulse Enter para omitir [<0 para ilimitada]: > -1
> ¿Es esta una extensión crítica [y/N]? n

Exporte el certificado público de la CA (este archivo es público):

vpnca $ certutil -d sql:/home/vpnca/nssdb -L -n vpnca -a > ca.pem

Configuración del certificado del servidor

En el sistema de la CA, genere un certificado para el servidor válido por 24 meses, con contexto de uso de servidor TLS:

vpnca $ certutil -d sql:/home/vpnca/nssdb -S -n "<insert_server_name>" -s "CN=<insert_server_name>" -c "vpnca" -t ",," -2 -6 -v 24
> 0
> -1
> ¿Es esta una extensión crítica [y/N]? n
> ¿Es este un certificado de CA [y/N]? n
> Introduzca la restricción de longitud de ruta, pulse Enter para omitir [<0 para ilimitada]: >
> ¿Es esta una extensión crítica [y/N]? n

Exporte el certificado del servidor a un archivo PKCS#12 (este archivo debe mantenerse en secreto):

vpnca $ pk12util -d sql:/home/vpnca/nssdb -o server.p12 -n "<insert_server_name>"

En el sistema que ejecutará el servidor, cree una base de datos NSS e importe el certificado de la CA y el certificado del servidor:

vpnserver $ certutil -d sql:/home/vpnserver/nssdb -N
vpnserver $ certutil -d sql:/home/vpnserver/nssdb -A -t "CT,," -n "vpnca" -i /path/to/ca.pem
vpnserver $ pk12util -d sql:/home/vpnserver/nssdb -i /path/to/server.p12

Configuración de certificados de peer

En el sistema de la CA, genere un certificado para el peer válido por 24 meses, con contextos de uso de cliente TLS y servidor TLS:

vpnca $ certutil -d sql:/home/vpnca/nssdb -S -n "peer-<insert_name>" -s "CN=peer-<insert_name>" -c "vpnca" -t ",," -2 -6 -v 24
> 0
> 1
> -1
> ¿Es esta una extensión crítica [y/N]? n
> ¿Es este un certificado de CA [y/N]? n
> Introduzca la restricción de longitud de ruta, pulse Enter para omitir [<0 para ilimitada]: >
> ¿Es esta una extensión crítica [y/N]? n

Exporte el certificado del peer a un archivo PKCS#12 (este archivo debe mantenerse en secreto):

vpnca $ pk12util -d sql:/home/vpnca/nssdb -o peer-<insert_name>.p12 -n "peer-<insert_name>"

En el sistema que ejecutará el cliente VPN, cree una base de datos NSS e importe el certificado de la CA y el certificado del peer:

vpnclient $ certutil -d sql:/home/vpnclient/nssdb -N
vpnclient $ certutil -d sql:/home/vpnclient/nssdb -A -t "CT,," -n "vpnca" -i /path/to/ca.pem
vpnclient $ pk12util -d sql:/home/vpnclient/nssdb -i /path/to/peer-<insert_name>.p12

Configuración de dispositivos TAP

Necesita crear y configurar dispositivos TAP en todos los ordenadores que participarán en la red virtual (es decir, ejecutarán el programa cliente). Consulte badvpn-client(8), sección `CONFIGURACIÓN DEL DISPOSITIVO TAP` para más detalles.

Ejemplo: Red IPv4 local, transporte UDP, seguridad cero

Inicio del servidor:

badvpn-server --listen-addr 0.0.0.0:7000

Inicio de los peers:

badvpn-client

--server-addr <insert_server_local_address>:7000
--transport-mode udp --encryption-mode none --hash-mode none
--scope local1
--bind-addr 0.0.0.0:8000 --num-ports 30 --ext-addr {server_reported}:8000 local1
--tapdev tap0

Ejemplo: Añadiendo seguridad TLS y UDP

Inicio del servidor (otras opciones como arriba):

badvpn-server ...

--ssl --nssdb sql:/home/vpnserver/nssdb --server-cert-name "<insert_server_name>"

Inicio de los peers (otras opciones como arriba):

badvpn-client ...

--ssl --nssdb sql:/home/vpnclient/nssdb --client-cert-name "peer-<insert_name>"
--encryption-mode blowfish --hash-mode md5 --otp blowfish 3000 2000

Ejemplo: Múltiples redes locales detrás de NATs, todas conectadas a Internet

Para cada peer en la red local existente, configure el router NAT para reenviar su rango de puertos a él (asumiendo que sus rangos de puertos no se superponen). Los clientes también necesitan conocer la dirección IP externa del router NAT. Si no tiene una estática, necesitará descubrirla antes de iniciar los clientes. Reenvíe también el puerto del servidor al servidor.

Inicio de los peers en la red local (otras opciones como arriba):

badvpn-client

...
--scope internet
...
--ext-addr <insert_NAT_routers_external_IP>:<insert_start_of_forwarded_port_range> internet
...

La opción --ext-addr se aplica a la opción --bind-addr especificada previamente y debe venir después de la primera opción --ext-addr que especifica una dirección local.

Ahora realice una configuración similar en otra red local detrás de un NAT. Sin embargo:
- No configure un nuevo servidor, en su lugar haga que los peers se conecten al servidor existente en la primera red local.
- No puede usar {server_reported} para las opciones --ext-addr de dirección local, porque el servidor informaría de la dirección externa del router NAT en lugar de la dirección interna del peer. En su lugar, cada peer tiene que conocer su dirección IP interna.
- Use un nombre de ámbito diferente para ello, por ejemplo, "local2" en lugar de "local1".

Si se configura correctamente, todos los peers podrán comunicarse: los de la misma red local se comunicarán directamente a través de direcciones locales, y los de diferentes redes locales se comunicarán a través de Internet.
