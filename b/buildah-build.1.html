DESCRIPCIÓ

N

Construye una imagen usando instrucciones de uno o más Containerfiles o Dockerfiles y un directorio de contexto de construcción especificado. Un Containerfile usa internamente la misma sintaxis que un Dockerfile. Para este documento, un archivo referido como Containerfile puede ser un archivo llamado 'Containerfile' o

'Dockerfile'.

El directorio de contexto de construcción se puede especificar como la URL http(s) de un archivo comprimido, un repositorio git o un

Containerfile.

Si no se especifica ningún directorio de contexto, Buildah asumirá el directorio de trabajo actual como contexto de construcción, que debería contener un

Containerfile.

Los Containerfiles que terminan con el sufijo ".in" serán preprocesados mediante cpp(1). Esto puede ser útil para descomponer los Containerfiles en varias partes reutilizables que pueden usarse a través de la directiva #include de CPP. Tenga en cuenta que un archivo Containerfile.in aún puede ser usado por otras herramientas al preprocesarlo manualmente mediante cpp -E. Cualquier comentario (líneas que comienzan con #) en los Containerfile(s) incluidos que no sean comandos de preprocesamiento, se imprimirán como advertencias durante las

construcciones.

Cuando la URL es un archivo comprimido, el contenido de la URL se descarga a una ubicación temporal y se extrae antes de la

ejecución.

Cuando la URL es un Containerfile, el archivo se descarga a una ubicación

temporal.

Cuando se establece un repositorio Git como la URL, el repositorio se clona localmente y luego se usa como contexto de construcción. Se puede usar una rama (o ID de commit) no predeterminada y un subdirectorio del repositorio git clonado incluyendo sus nombres al final de la URL en la forma myrepo.git#mybranch:subdir, myrepo.git#mycommit:subdir, o myrepo.git#:subdir si el subdirectorio deb

--output, -o="

"

Salida adicional (formato: type=local,

dest=path)

La opción --output (o -o) complementa el comportamiento predeterminado de construir una imagen de contenedor permitiendo a los usuarioso exportar el contenido de la imagen como archivos en el sistema de archivos local, lo que puede ser útil para generar binarios locales, generación de código, etc.

El valor para --output es una secuencia de pares clave=valor separados por comas, que definen el tipo de salida y las opciones.

Las claves admitidas son:
dest: Destino para la salida exportada. Puede establecerse en - para indicar la salida estándar, o a una ruta absoluta o relativa.

Los valores type válidos son:
local: escribe los archivos de construcción resultantes en un directorio del lado del cliente.
tar: escribe los archivos resultantes como un único archivo tarball (.tar).

Alternativamente, en lugar de una secuencia separada por comas, el valor de --output puede ser solo el destino (en el formato **dest**) (por ejemplo, --output alguna-ruta, --output -), y el type se inferirá como tar si el destino de salida es -, y local en caso contrario.

Las marcas de tiempo en el contenido de salida se establecerán para que coincidan exactamente con el valor especificado usando la opción --timestamp, o para que coincidan exactamente con el valor especificado para la opción --source-date-epoch, si alguna de ellas se especifica.

--pull

Por defecto, los volúmenes montados mediante enlace son privados. Esto significa que cualquier montaje realizado dentro del contenedor no será visible en el host y viceversa. Este comportamiento puede cambiarse especificando una propiedad de propagación del montaje del

volumen.

Cuando la política de propagación del montaje se establece en shared, cualquier montaje completado dentro del contenedor en ese volumen será visible tanto para el host como para el contenedor. Cuando la política de propagación del montaje se establece en slave, se habilita la propagación de montaje unidireccional y cualquier montaje completado en el host para ese volumen será visible solo dentro del contenedor. Para controlar la propiedad de propagación del montaje del volumen, use la opción de propagación :[r]shared, :[r]slave o :[r]private. La propiedad de propagación solo puede especificarse para volúmenes montados mediante enlace y no para volúmenes internos o volúmenes con nombre. Para que la propagación del montaje funcione en el punto de montaje de origen (el punto de montaje donde se monta el directorio de origen), este debe tener las propiedades de propagación correctas. Para volúmenes compartidos, el punto de montaje de origen debe ser compartido. Y para volúmenes esclavos, el montaje de origen debe ser compartido o esclavo. [1]

Si la utilidad findmnt no está disponible, el punto de montaje de origen puede determinarse mirando la entrada de montaje en /proc/self/mountinfo. Mire los campos opcionales y vea si se especifican algunas propiedades de propagación. shared:X significa que el montaje es compartido (shared), master:X significa que el montaje es esclavo (slave) y si no hay nada, significa que el montaje es privado (private). [1]

⟨#Footnote1⟩

Para cambiar las propiedades de propagación de un punto de montaje, use el comando mount. Por ejemplo, para montar mediante enlace el directorio de origen /foo hacer mount --bind /foo /foo y mount --make-private --make-shared /foo. Esto convertirá /foo en un punto de montaje compartido. Las propiedades de propagación del montaje de origen se pueden cambiar directamente. Por ejemplo, si / es el montaje de origen para /foo, entonces use mount --make-shared / para convertir / en un montaje compartido.

La instrucción ENV en un Containerfile se puede usar para definir valores de variables. Cuando se compila la imagen, los valores persistirán en la imagen del contenedor. A veces es más conveniente cambiar los valores en el Containerfile a través de una opción de línea de comandos en lugar de cambiar los valores dentro del propio Containerfile.

Las siguientes variables se pueden usar junto con la opción --build-arg para anular los valores correspondientes establecidos en el Containerfile usando la instrucción ENV.

  • HTTP_PROXY
  • HTTPS_PROXY
  • FTP_PROXY
  • NO_PROXY

Consulte la sección Usando variables de tiempo de compilación ⟨#using-build-time-variables⟩ de los Ejemplos.

Compilar una imagen usando una URL

Esto clonará el repositorio de GitHub especificado desde la URL y lo usará como contexto. El Containerfile o Dockerfile en la raíz del repositorio se utiliza como contexto de la compilación. Esto solo funciona si el repositorio de GitHub es un repositorio dedicado.

buildah build https://github.com/containers/PodmanHello.git

Nota: Github no admite el uso de git:// para realizar la operación de clonación debido a cambios recientes en su guía de seguridad (https://github.blog/2021-09-01-improving-git-protocol-security-github/). Use una URL https:// si el repositorio de origen está alojado en Github.

Compilar una imagen usando una URL a un contexto empaquetado en tar

Buildah obtendrá el archivo tar, lo descomprimirá y usará su contenido como contexto de compilación. El Containerfile o Dockerfile en la raíz del archivo y el resto del archivo se usarán como contexto de compilación. Si también pasa una opción -f PATH/Containerfile, el sistema buscará ese archivo dentro del contenido del archivo tar.

buildah build -f dev/Containerfile https://10.10.10.1/buildah/context.tar.gz

Nota: los formatos de compresión admitidos son 'xz', 'bzip2', 'gzip' e 'identity' (sin compresión).

ENTORNO

BUILD_REGISTRY_SOURCES

BUILD_REGISTRY_SOURCES, si está establecido, se trata como un objeto JSON que contiene listas de nombres de registros bajo las claves insecureRegistries, blockedRegistries y allowedRegistries.

Al extraer una imagen de un registro, si el nombre del registro coincide con alguno de los elementos de la lista blockedRegistries, se deniega el intento de extracción de la imagen. Si hay registros en la lista allowedRegistries y el nombre del registro no está en la lista, se deniega el intento de extracción.

TMPDIR La variable de entorno TMPDIR permite al usuario especificar dónde se almacenan los archivos temporales mientras se extraen y se envían imágenes. Por defecto es '/var/tmp'.

Archivos

.containerignore/.dockerignore

Si el archivo .containerignore/.dockerignore existe en el directorio de contexto, buildah build lee su contenido. Si ambos existen, se utiliza .containerignore. Use la bandera --ignorefile para anular la ubicación de la ruta del archivo de omisión. Buildah utiliza el contenido para excluir archivos y directorios del directorio de contexto, al ejecutar las directivas COPY y ADD en el Containerfile/Dockerfile

Los usuarios pueden especificar una serie de globales de shell Unix en un archivo .containerignore/.dockerignore para identificar archivos/directorios a excluir.

Buildah admite una cadena comodín especial ** que coincide con cualquier número de directorios (incluido cero). Por ejemplo, **/*.go excluirá todos los archivos que terminen en .go que se encuentren en todos los directorios.

Ejemplo de archivo .containerignore:

# excluir este contenido para la imagen
*/*.c
**/output*
src

*/*.c Excluye archivos y directorios cuyos nombres terminen en .c en cualquier subdirectorio de nivel superior. Por ejemplo, el archivo de origen include/rootless.c.

**/output* Excluye archivos y directorios que comiencen con output desde cualquier directorio.

src Excluye archivos llamados src y el directorio src, así como cualquier contenido en él.

Las líneas que comienzan con ! (signo de exclamación) se pueden usar para hacer excepciones a las exclusiones. El siguiente es un ejemplo de archivo .containerignore/.dockerignore que utiliza este mecanismo:

*.doc
!Help.doc

Excluir todos los archivos doc excepto Help.doc de la imagen.

Esta funcionalidad es compatible con el manejo de archivos .containerignore descrito aquí:

https://github.com/containers/common/blob/main/docs/containerignore.5.md

registries.conf (/etc/containers/registries.conf)

registries.conf es el archivo de configuración que especifica qué registros de contenedores se deben consultar al completar nombres de imágenes que no incluyen una parte de registro o dominio.

policy.json (/etc/containers/policy.json)

Archivo de política de firmas. Define la política de confianza para las imágenes de contenedor. Controla qué registros de contenedores se pueden utilizar para las imágenes y si la herramienta debe confiar en las imágenes.
