DESCRIPCIÓN

BIO_s_bio() devuelve el método para un BIO pair. Un BIO pair es un par de BIOs de origen/destino donde los datos escritos en cualquiera de las mitades del par se almacenan en búfer y pueden leerse desde la otra mitad. Normalmente, ambas mitades deben ser manejadas por el mismo hilo de la aplicación, ya que no se realiza ningún bloqueo en las estructuras de datos internas.

Dado que las cadenas de BIO típicamente terminan en un BIO de origen/destino, es posible hacer de este una mitad de un BIO pair y tener todos los datos procesados por la cadena bajo el control de la aplicación.

Un uso típico de los BIO pairs es colocar la E/S de TLS/SSL bajo el control de la aplicación; esto puede usarse cuando la aplicación desea usar un transporte no estándar para TLS/SSL o cuando las rutinas normales de socket son inapropiadas.

Las llamadas a BIO_read_ex() leerán datos del búfer o solicitarán un reintento si no hay datos disponibles.

Las llamadas a BIO_write_ex() colocarán datos en el búfer o solicitarán un reintento si el búfer está lleno.

Las llamadas estándar BIO_ctrl_pending() y BIO_ctrl_wpending() pueden usarse para determinar la cantidad de datos pendientes en el búfer de lectura o escritura.

BIO_reset() borra cualquier dato en el búfer de escritura.

BIO_make_bio_pair() une dos BIOs separados en un par conectado.

BIO_destroy_pair() destruye la asociación entre dos BIOs conectados. Liberar cualquiera de las mitades del par destruirá automáticamente la asociación.

BIO_shutdown_wr() se usa para cerrar un BIO b. Después de esta llamada no se permiten más escrituras en el BIO b (devolverán un error). Las lecturas en la otra mitad del par devolverán cualquier dato pendiente o EOF cuando se hayan leído todos los datos pendientes.

BIO_set_write_buf_size() establece el tamaño del búfer de escritura del BIO b a size. Si el tamaño no está inicializado se usa un valor por defecto. Actualmente es 17K, suficiente para un registro TLS de tamaño máximo.

BIO_get_write_buf_size() devuelve el tamaño del búfer de escritura.

BIO_new_bio_pair() combina las llamadas a BIO_new(), BIO_make_bio_pair() y BIO_set_write_buf_size() para crear un par conectado de BIOs bio1, bio2 con tamaños de búfer de escritura writebuf1 y writebuf2. Si alguno de los tamaños es cero se usa el tamaño por defecto. BIO_new_bio_pair() no comprueba si bio1 o bio2 apuntan a algún otro BIO; los valores se sobrescriben, BIO_free() no se llama.

BIO_get_write_guarantee() y BIO_ctrl_get_write_guarantee() devuelven la longitud máxima de datos que pueden escribirse actualmente en el BIO. Las escrituras mayores que este valor devolverán un valor de BIO_write_ex() menor que la cantidad solicitada o, si el búfer está lleno, solicitarán un reintento. BIO_ctrl_get_write_guarantee() es una función, mientras que BIO_get_write_guarantee() es una macro.

BIO_get_read_request() y BIO_ctrl_get_read_request() devuelven la cantidad de datos solicitados, o el tamaño del búfer si es menor, si el último intento de lectura en la otra mitad del BIO pair falló debido a un búfer vacío. Esto puede usarse para determinar cuántos datos deben escribirse en el BIO para que la siguiente lectura tenga éxito: esto es más útil en aplicaciones TLS/SSL donde la cantidad de datos leída suele ser significativa en lugar de solo un tamaño de búfer. Después de una lectura exitosa esta llamada devolverá cero. También devolverá cero una vez que se hayan escrito nuevos datos que satisfagan la solicitud de lectura o parte de ella. Ten en cuenta que BIO_get_read_request() nunca devuelve una cantidad mayor que la devuelta por BIO_get_write_guarantee().

BIO_ctrl_reset_read_request() también puede usarse para restablecer el valor devuelto por BIO_get_read_request() a cero.

NOTAS

Ambas mitades de un BIO pair deben ser liberadas. Es decir, incluso si una mitad se libera implícitamente debido a una llamada a BIO_free_all() o SSL_free() la otra mitad necesita ser liberada.

Cuando se usa en aplicaciones bidireccionales (como TLS/SSL) se debe tener cuidado de vaciar cualquier dato en el búfer de escritura. Esto puede hacerse llamando a BIO_pending() en la otra mitad del par y, si hay datos pendientes, leyéndolos y enviándolos al transporte subyacente. Esto debe hacerse antes de cualquier procesamiento normal (como llamar a select() ) debido a una solicitud y BIO_should_read() siendo verdadero.

Para ver por qué esto es importante, considera un caso donde se envía una solicitud usando BIO_write_ex() y se lee una respuesta con BIO_read_ex(), esto puede ocurrir durante un apretón de manos TLS/SSL, por ejemplo. BIO_write_ex() tendrá éxito y colocará datos en el búfer de escritura. BIO_read_ex() inicialmente fallará y BIO_should_read() será verdadero. Si la aplicación luego espera a que los datos estén disponibles en el transporte subyacente antes de vaciar el búfer de escritura, nunca tendrá éxito porque la solicitud nunca se envió.

BIO_eof() es verdadero si no hay datos en el BIO par y el BIO par ha sido cerrado.

BIO_make_bio_pair(), BIO_destroy_bio_pair(), BIO_shutdown_wr(), BIO_set_write_buf_size(), BIO_get_write_buf_size(), BIO_get_write_guarantee(), y BIO_get_read_request() están implementados como macros.

VALORES DE RETORNO

BIO_new_bio_pair() devuelve 1 en caso de éxito, con los nuevos BIOs disponibles en bio1 y bio2, o 0 en caso de fallo, con punteros NULL almacenados en las ubicaciones para bio1 y bio2. Consulta la pila de errores para más información.

EJEMPLOS

El BIO pair puede usarse para tener control total sobre el acceso a la red de una aplicación. La aplicación puede llamar a select() en el socket según sea necesario sin tener que pasar por la interfaz SSL.

BIO *internal_bio, *network_bio;
...
BIO_new_bio_pair(&internal_bio, 0, &network_bio, 0);
SSL_set_bio(ssl, internal_bio, internal_bio);
SSL_operations(); /* p. ej. SSL_read y SSL_write */
...
aplicación |   motor TLS
   |        |
   +----------> SSL_operations()
            |     /\    ||
            |     ||    \/
            |   BIO-pair (internal_bio)
            |   BIO-pair (network_bio)
            |     ||     /\
            |     \/     ||
   +-----------< BIO_operations()
   |        |
   |        |
  socket
 ...
 SSL_free(ssl);                /* libera implícitamente internal_bio */
 BIO_free(network_bio);
 ...

Dado que el BIO pair solo almacenará los datos en búfer y nunca accederá directamente a la conexión, se comporta de forma no bloqueante y retornará tan pronto como el búfer de escritura esté lleno o el búfer de lectura esté vacío. Luego la aplicación debe vaciar el búfer de escritura y/o llenar el búfer de lectura.

Usa BIO_ctrl_pending()para averiguar si hay datos almacenados en búfer en el BIO y deben transferirse a la red. Usa BIO_ctrl_get_read_request() para averiguar cuántos bytes deben escribirse en el búfer antes de que SSL_operation() pueda continuar con éxito.

ADVERTENCIAS

Dado que los datos están en búfer, SSL_operation() puede retornar con una condición ERROR_SSL_WANT_READ, pero aún hay datos en el búfer de escritura. Una aplicación no debe depender del valor de error de SSL_operation() pero debe asegurarse de que el búfer de escritura siempre se vacíe primero. De lo contrario puede ocurrir un bloqueo ya que el par podría estar esperando los datos antes de poder continuar.
