DESCRIPCIÓ

N

BorgBackup (en breve: Borg) es un programa de copias de seguridad con deduplicación. Opcionalmente, admite compresión y cifrado

autenticado.

El objetivo principal de Borg es proporcionar una forma eficiente y segura de hacer copias de seguridad de los datos. La técnica de deduplicación de datos utilizada hace que Borg sea adecuado para copias de seguridad diarias, ya que solo se almacenan los cambios. La técnica de cifrado autenticado lo hace adecuado para copias de seguridad hacia destinos no totalmente

confiables.

Borg almacena un conjunto de archivos en un archivo. Un repositorio es una colección de archivos. El formato de los repositorios es específico de Borg. Borg no distingue los archivos entre sí de ningu

na manera que no sea su nombre; no importa cuándo o dónde se
crearon los archivos (por ejemplo, en diferentes hosts).

Registr

o

Borg escribe toda la salida de registro en stderr de forma predeterminada. Pero ten en cuenta que algo que aparece en stderr no indica una condición de error solo porque esté en stderr. Por favor, comprueba los niveles de registro de los mensajes y el código de retorno de borg para determinar condiciones de error, advertencia o

éxito.

Si deseas capturar la salida de registro en un archivo, simplemente

redirígela: 
borg create
repo::arch
ive myfiles
2>> logfile

Se pueden implementar configuraciones de registro personalizadas a través de BORG_LOGGING_CONF

.

El nivel de registro de la configuración de registro integrada es WARNING de forma predeterminada. Esto se debe a que queremos que Borg sea mayormente silencioso y solo emita advertencias, errores y mensajes críticos, a menos que se haya solicitado la salida proporcionando una opción que implique salida (por ejemplo, --list o --progre

ss).

Niveles de registro: DEBUG < INFO < WARNING < ERROR <

CRITICAL

Usa --debug para establecer el nivel de registro DEBUG - para obtener salida de nivel debug, info, warning, error y

critical.

Usa --info (o -v o --verbose) para establecer el nivel de registro INFO - para obtener salida de nivel info, warning, error y

critical.

Usa --warning (predeterminado) para establecer el nivel de registro WARNING - para obtener salida de nivel warning, error y

critical.

Usa --error para establecer el nivel de registro ERROR - para obtener salida de nivel error y

critical.

Usa --critical para establecer el nivel de registro CRITICAL - para obtener salida de nivel

critical.

Aunque puedes establecer varios niveles de registro, no esperes que cada comando dé una salida diferente en diferentes niveles de registro - es solo una

posibilidad.

Variables de Entorno

BORG_SELinux_CONTEXT
Si SELinux está habilitado en tu sistema, este ajuste puede ser usado para indicarle a SELinux qué contexto de seguridad debe ser usado en los archivos y directorios que cree borg. Usa esto si tu política SELinux no es capaz de manejar el contexto de seguridad adecuado por sí misma. Debe ser un valor de contexto SELinux válido. Ejemplo: 
BORG_SELinux_CONTEXT="untrusted_home_t"
Este valor por defecto es "" (vacío).
BORG_ROLLING_HASH
Especifica el algoritmo de hash de rodadura a usar. Los valores válidos son murmur3, sha1, sha256, sha512, xxhash. El valor por defecto es murmur3.

Si no está establecido, borg usa un valor por defecto de murmur3. El hash de rodadura es usado para la deduplicación de archivos grandes. Si un valor de hash incorrecto se usa para un repositorio ya existente, puede resultar en la corrupción de este (lo que significa que los datos no se podrán recuperar). Borg se quejará si intentas cambiar el hash de rodadura para un repositorio existente. No hay razón para usar un hash que no sea murmur3, excepto si tienes problemas específicos o si quieres experimentar.

BORG_UNKNOWN_CHUNK_CHECKSUM_POLICY
Establece la política para manejar sumas de verificación de fragmentos desconocidos. Valores posibles:
ignore
Ignora las sumas de verificación desconocidas.
warn
Emite una advertencia sobre sumas de verificación desconocidas.
strict
Termina con un error si se encuentra una suma de verificación desconocida.
El valor por defecto es warn.
BORG_TEST_ENVIRONMENT
Ejecuta las pruebas internas al inicio de cada invocación de comando borg.

Se puede usar BORG_SELFTEST=disabled para desactivar las pruebas y ahorrar algo de tiempo. Desactivar no es recomendable para usuarios normales de borg, pero los proveedores de almacenamiento de borg a gran escala pueden usar esto para optimizar servidores de producción después de haber realizado al menos una prueba borg única (con selftests no desactivados) al instalar o actualizar máquinas / OS / borg.

BORG_WORKAROUNDS
Una lista de cadenas separadas por comas que activan soluciones alternativas en borg, por ejemplo, para solucionar errores en otro software.

Las cadenas actualmente conocidas son:

basesyncfile
Usa el código más simple de BaseSyncFile para evitar problemas con sync_file_range. Puede que necesites esto para ejecutar borg en WSL (Windows Subsystem for Linux) o en contenedores systemd.nspawn en algunas arquitecturas (por ejemplo, ARM). Usar esto no afecta la seguridad de los datos, pero podría resultar en un comportamiento de escritura más intermitente en el disco (no en streaming continuo al disco).
retry_erofs
Reintenta abrir un archivo sin O_NOATIME si la apertura de un archivo con O_NOATIME causó EROFS. Necesitarás esto para crear archivos a partir de copias de sombra de volumen en WSL1 (Windows Subsystem for Linux 1).
authenticated_no_key
Soluciona una contraseña o clave perdida para un repositorio en modo autenticado (estos solo están autenticados, pero no cifrados). Si la clave falta en la configuración del repositorio, añade key = anything allí.

Esta solución alternativa es solo para emergencias y solo para extraer datos de un repositorio afectado (acceso de solo lectura):

BORG_WORKAROUNDS=authenticated_no_key borg extract repo::archive

Después de haber extraído todos los datos que necesitas, DEBES eliminar el repositorio:

BORG_WORKAROUNDS=authenticated_no_key borg delete repo

Ahora puedes inicializar un nuevo repositorio. Asegúrate de no volver a usar la solución alternativa.

ignore_invalid_archive_tam
Soluciona TAMs de archivo inválidos creados por borg < 1.2.5, ver #7791.

Esta solución alternativa probablemente solo necesite usarse una vez al seguir las instrucciones de actualización para CVE-2023-36811, ver archives_tam_vuln.

En operaciones normales de producción, esta solución alternativa nunca debería usarse.

Así que por favor, prueba tus scripts interactivamente antes de hacerlos scripts no interactivos.

Directorios y archivos:
BORG_BASE_DIR
Por defecto es $HOME o ~$USER o ~ (en ese orden). Si quieres mover todas las carpetas específicas de borg a una ruta personalizada a la vez, todo lo que necesitas hacer es modificar BORG_BASE_DIR: las otras rutas para caché, configuración, etc. se adaptarán correspondientemente (asumiendo que no las has establecido a un valor personalizado diferente).
BORG_CACHE_DIR
Por defecto es $BORG_BASE_DIR/.cache/borg. Si BORG_BASE_DIR no está explícitamente establecido mientras la variable de entorno XDG https://specifications.freedesktop.org/basedir-spec/0.6/ar01s03.html
XDG_CACHE_HOME está establecida, entonces se usa $XDG_CACHE_HOME/borg en su lugar. Este directorio contiene la caché local y puede necesitar mucho espacio para manejar repositorios grandes. Asegúrate de ser consciente de los aspectos de seguridad asociados de la ubicación de la caché: cache_security
BORG_CONFIG_DIR
Por defecto es $BORG_BASE_DIR/.config/borg. Si BORG_BASE_DIR no está explícitamente establecido mientras la variable de entorno XDG https://specifications.freedesktop.org/basedir-spec/0.6/ar01s03.html
XDG_CONFIG_HOME está establecida, entonces se usa $XDG_CONFIG_HOME/borg en su lugar. Este directorio contiene todos los directorios de configuración de borg, ver el FAQ para un aviso de seguridad sobre los datos en este directorio: home_config_borg
BORG_SECURITY_DIR
Por defecto es $BORG_CONFIG_DIR/security. Este directorio contiene información que borg usa para rastrear su uso de NONCES ("números usados una vez" - usualmente en contexto de encriptación) y otros datos relevantes para la seguridad.
BORG_KEYS_DIR
Por defecto es $BORG_CONFIG_DIR/keys. Este directorio contiene las claves para repositorios cifrados.
BORG_KEY_FILE
Cuando se establece, usa la ruta dada como archivo de clave del repositorio. Por favor, ten en cuenta que esto es solo para aplicaciones bastante especiales que gestionan externamente completamente los archivos de clave:
  • esta configuración solo se aplica a los modos de archivo de clave (no a los modos de clave de repositorio).
  • se recomienda usar una ruta completa y absoluta al archivo de clave.
  • todos los directorios en la ruta dada deben existir.
  • esta configuración obliga a borg a usar el archivo de clave en la ubicación dada.
  • el archivo de clave debe existir (para la mayoría de los comandos) o será creado (borg init).
  • necesitas dar una ruta diferente para diferentes repositorios.
  • necesitas apuntar al archivo de clave correcto que coincida con el repositorio en el que operará el comando.

Aquí es donde se almacenan los archivos temporales (puede necesitar mucho espacio temporal para algunas operaciones), ver tempfile https://docs.python.org/3/library/tempfile.html#tempfile.gettempdir
para detalles.

Por favor, ten en cuenta:

  • Ten mucho cuidado al usar los "respondedores" con "sí", las advertencias con pregunta existen para tu seguridad/la seguridad de tus datos.
  • Ten también mucho cuidado al poner tu contraseña en un script, asegúrate de que tenga los permisos de archivo apropiados (por ejemplo, modo 600, root:root).

Sistemas de archivos

Recomendamos encarecidamente no usar Borg (ni ningún otro software similar a una base de datos) en sistemas de archivos no transaccionales como FAT, ya que no se puede asumir ninguna consistencia en caso de fallos de alimentación (o desconexión repentina de una unidad externa o fallos similares).

Si bien Borg utiliza un almacén de datos que es resistente a estos fallos cuando se usa en sistemas de archivos transaccionales, no es posible garantizarlo con algunos hardwares, independientemente del software utilizado. No conocemos una lista de hardware afectado.

Si sospechas que tu repositorio de Borg todavía es consistente y legible después de que ocurriera uno de los fallos mencionados anteriormente, ejecuta borg check --verify-data para asegurarte de que es consistente. Requisitos para los sistemas de archivos del repositorio de Borg

  • Nombres de archivo largos
  • Al menos tres niveles de directorio con nombres cortos
  • Típicamente, tamaños de archivo de hasta unos pocos cientos de MB. Los repositorios grandes pueden requerir archivos grandes (>2 GB).
  • Hasta 1000 archivos por directorio.
  • rename(2) / MoveFile(Ex) debería funcionar según lo especificado, es decir, en el mismo sistema de archivos debería ser una operación de movimiento (no de copia), y en caso de un directorio debería fallar si el destino existe y no es un directorio vacío, ya que esto se utiliza para el bloqueo.
  • Se necesitan enlaces duros para borg_upgrade (si no se usa la opción --inplace). También se usan enlaces duros para una actualización de archivo más segura y protegida (por ejemplo, del archivo de configuración del repositorio), pero el c
