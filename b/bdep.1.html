bdep(1) General Commands Manual bdep(1)

NOMBRE

bdep - gestor de dependencias de proyectos

SINOPSIS

bdep --help
bdep --version
bdep help [comando | tema]
bdep [opciones-comunes] comando [opciones-comando] args-comando

DESCRIPCIÓN

El gestor de dependencias de proyectos build2 se utiliza para gestionar las dependencias de un proyecto durante el desarrollo.

Para una descripción detallada de cualquier comando o tema de ayuda, use el comando help o consulte la página man correspondiente (las páginas man tienen el prefijo bdep-, por ejemplo bdep-help(1)). Tenga en cuenta también que opciones-comando y args-comando pueden especificarse en cualquier orden y opciones-comunes pueden especificarse como parte de opciones-comando.

Un proyecto bdep es un directorio, normalmente bajo un sistema de control de versiones como git(1), llamado repositorio de proyecto. Un proyecto contiene uno o más paquetes. Si contiene varios, normalmente están relacionados, por ejemplo, la biblioteca libhello y el programa hello.

Los paquetes en un proyecto pueden depender de otros paquetes fuera del proyecto. Para distinguir entre ambos, los llamamos paquetes del proyecto y paquetes de dependencia, respectivamente. Naturalmente, nuestros paquetes del proyecto pueden ser paquetes de dependencia de otra persona.

Un proyecto simple de un solo paquete contiene el paquete en la raíz del repositorio del proyecto. Por ejemplo (observe la ubicación del paquete manifest y lockfile):

hello/
|-- .git/
|-- ...
|-- lockfile
`-- manifest

Vea Manifest del Paquete (#manifest-package) para detalles sobre el archivo manifest.

Si un proyecto contiene varios paquetes o deseamos colocar el paquete en un subdirectorio, entonces la raíz del repositorio del proyecto debe contener el archivo packages.manifest que especifica las ubicaciones de los paquetes. Por ejemplo:

hello/
|-- .git/
|-- hello/
|   |-- ...
|   |-- lockfile
|   `-- manifest
|-- libhello/
|   |-- ...
|   |-- lockfile
|   `-- manifest
`-- packages.manifest

Para este proyecto, packages.manifest tendría el siguiente contenido:

: 1
location: hello/
:
location: libhello/

La raíz del repositorio del proyecto normalmente también contendrá el archivo repositories.manifest que lista los repositorios que proporcionan los paquetes de dependencia. Por ejemplo:

hello/
|-- ...
|-- manifest
`-- repositories.manifest

Si nuestro proyecto hello quisiera usar libhello como paquete de dependencia, entonces su repositories.manifest podría verse así:

: 1
summary: hello project repository
:
role: prerequisite
location: https://example.com/libhello.git

Vea Lista de Repositorios Manifiesto (#manifest-repository-list) para detalles sobre el archivo repositories.manifest.

Para el desarrollo, un proyecto bdep está asociado con una o más bpkg(1) configuraciones de construcción. Estas configuraciones se utilizan como respaldo para construir los paquetes del proyecto y sus dependencias.

La lista de configuraciones de construcción asociadas, así como la lista de paquetes del proyecto inicializados en cada configuración, se almacena en la base de datos de proyectos de bdep bajo el subdirectorio .bdep/ del directorio raíz del proyecto. Por ejemplo:

hello-gcc/     # Configuración de construcción para gcc.
hello-clang/   # Configuración de construcción para clang.
hello/
|-- .bdep/
|-- .git/
`-- ...

El núcleo de la funcionalidad de bdep es la sincronización de estado entre el proyecto y una o más configuraciones de construcción asociadas. Por ejemplo, si listamos una nueva dependencia en el archivo manifest del paquete, entonces bdep descarga y configura esta dependencia en una configuración de construcción. De manera similar, si actualizamos o degradamos una dependencia en una configuración de construcción, entonces bdep actualiza la entrada correspondiente en el lockfile del paquete.

Un flujo de trabajo típico de bdep consistiría en los siguientes pasos.

Obtener el Proyecto

Normalmente usaríamos el sistema de control de versiones para obtener el proyecto que queremos desarrollar: 
$ git clone ssh://example.com/hello.git

Alternativamente, podemos usar el comando bdep-new(1) para iniciar un nuevo proyecto (vea Nombre del Paquete (#package-name) para detalles sobre la denominación de proyectos):

$ bdep new -l c++ -t exe hello

De forma similar a las herramientas de control de versiones, normalmente ejecutamos bdep desde el directorio del proyecto o uno de sus subdirectorios:

$ cd hello

Vea bdep-projects-configs(1) para formas alternativas de especificar la ubicación del proyecto.

Inicializar el Proyecto

A continuación, usamos el comando bdep-init(1) para crear nuevas o agregar configuraciones de construcción existentes e inicializar nuestro proyecto en estas configuraciones: 
$ bdep init -C ../hello-gcc @gcc cc config.cxx=g++
$ bdep init -A ../hello-clang @clang

Si el directorio de configuración está al lado del proyecto y su nombre tiene el formato nombre-proyecto-nombre-conf, entonces se puede usar la versión abreviada de init en su lugar:

$ bdep init -C @gcc cc config.cxx=g++
$ bdep init -A @clang

Después de la inicialización, podemos usar el comando bdep-status(1) para examinar el estado de nuestro proyecto en sus configuraciones:

$ bdep status -a
in configuration @gcc:
hello configured 0.1.0-a.0.19700101000000
in configuration @clang:
hello configured 0.1.0-a.0.19700101000000

La mayoría de los comandos de bdep operan en una o más configuraciones de construcción asociadas con el proyecto. Si no especificamos una explícitamente, se utiliza la configuración por defecto (normalmente la primera agregada; gcc en nuestro caso). Alternativamente, podemos especificar las configuraciones por nombre (si se les asignó), como directorios, o con --all|-a (vea bdep-projects-configs(1) para detalles). Por ejemplo:

$ bdep status @clang @gcc      # por nombre
$ bdep status -c ../hello-gcc  # como directorio

Si un comando opera en varias configuraciones (como status -a en el ejemplo anterior), imprimirá una línea identificando cada configuración antes de imprimir el resultado del comando.

Por defecto, el directorio fuente del proyecto se configura para redirigir a la configuración de construcción por defecto. Es decir, podemos ejecutar el sistema de construcción en el directorio fuente y este automáticamente construirá en la configuración redirigida, así como enlazar los resultados de vuelta al directorio fuente usando enlaces simbólicos u otro mecanismo adecuado (vea bdep-config(1) para detalles). Por ejemplo:

$ b        # construir en gcc
<...>
$ ./hello  # ejecutar el resultado

Usar el sistema de construcción directamente en configuraciones distintas de la por defecto requiere especificar explícitamente sus rutas. Para hacer esto más conveniente, los comandos bdep-update(1), bdep-test(1), y bdep-clean(1) nos permiten referirnos a ellas por nombre, realizar la operación deseada del sistema de construcción en varias de ellas a la vez, y, en el caso de test, realizarla en dependencias inmediatas o todas, o en un proyecto. Por ejemplo:

$ bdep test @gcc @clang
in configuration @gcc:
<...>
in configuration @clang:
<...>

Para desinicializar un proyecto en una o más configuraciones de construcción podemos usar el comando bdep-deinit(1). Por ejemplo:

$ bdep deinit -a
Agregar, Eliminar o Cambiar Dependencias

Supongamos que encontramos libhello que nos gustaría usar en nuestro proyecto. Primero editamos el archivo repositories.manifest de nuestro proyecto y agregamos el repositorio de libhello como nuestro prerrequisito: 
$ cat repositories.manifest
...
role: prerequisite
location: https://example.com/libhello.git
...

A continuación, editamos nuestro archivo manifest y especificamos una dependencia en libhello:

$ cat manifest
...
depends: libhello ^1.0.0
...

Si ahora ejecutamos bdep-status(1), notaremos que una nueva iteración de nuestro proyecto

está disponible para

sincronización: 
$ bdep status
hello configured 0.1.0-a.0.19700101000000
      available  0.1.0-a.0.
19700101000000#1

Consulte Versión del paquete (#packag

e-version) para obtener detalles sobre versiones de paquetes e iteraciones.
Sincronizar el Proyecto con las
Configuraciones

Para sincronizar los cambios en la información de dependencias del proyecto con sus configuraciones de compilación, usamos el comando bdep-sync(1). Continuando con nuestro ejemplo, esto resultará en que libhello sea descargado y configurado, ya que nuestro proyecto ahora depende de él: 
$ bdep sync
synchronizing:
  build libhello/1.0.0 (required by hello)
  upgrade hello/0.1.0-a.0.19700101000000#1
$ bdep status -i
hello configured 0.1.0-a.0.19700101000000#1
  libhello ^1.0.0 configured
1.0.0

Tenga en cuenta que, de forma predeterminada, las configuraciones de compilación se sincronizan automáticamente en cada invocación del sistema de compilación (consulte bdep-config(1) para más detalles). Como resultado, rara vez necesitamos ejecutar el comando sync explícitamente, y en su lugar podemos simplemente ejecutar la operación deseada del sistema de compilación (por ejemplo, update o test) directamente. Por

ejemplo: 
$ b test
synchronizing:
  build libhello/1.0.0 (required by hello)
  upgrade hello/0.1.0-a.0.19700101000000#1
<...>

También es posible que varios proyectos compartan una configuración de compilación. En este caso, todos los proyectos se sincronizan a la vez, independientemente del proyecto de origen. Por ejemplo, si también fuéramos los autores de libhello y lo alojáramos en un repositorio de control de versiones separado (en lugar de ser un paquete en el repositorio hello ), entonces habría sido natural desarrollarlo junto con hello en las mismas

configuraciones: 
$ cd ../libhello
$ bdep init -A ..
/hello-gcc @gcc $ bdep sync # sy
nchronizes both hello and libhello
Actualizar o Retroceder
Dependencias

El comando bdep-sync(1) también se usa para actualizar o retroceder dependencias (y también se ejecuta como el último paso de init). Supongamos que nos enteramos de que se ha lanzado una nueva versión de libhello y nos gustaría probarla.

Para actualizar la lista de paquetes de dependencias disponibles, usamos el comando bdep-fetch(1) (o, como un atajo, la opción -f para statu

s): 
$ bdep fetch
$ bdep status libhello
libhello configured 1.0.0 available [1.
1.0]

Sin una versión explícita ni la opción --patch|-p , sync actualizará la dependencia especificada a la última versión

disponible: 
$ bdep sync libhello
synchronizing:
  upgrade libhello/1.1.0
  reconfigure hello/0.1.0
$ bdep status -i
hello configured 0.1.0-a.0.19700101000000#1
  libhello ^1.0.0 configured
1.1.0

Supongamos que no nos gustó la nueva versión y nos gustaría volver a usar la antigua. Para retroceder una dependencia, tenemos que especificar su versión

explícitamente: 
$ bdep status -o libhello
libhello
configured 1.1.0 available [1.0.0]
(1.1.0) $ bdep sync libhello/1.0.0 synchronizing: downgrade libhello/1.1.0 reconfigure hello/0.1.0
