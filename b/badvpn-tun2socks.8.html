NOMBRE

badvpn-tun2socks - crea un dispositivo TUN para enrutar tráfico TCP a través de un servidor SOCKS

SINOPSIS

badvpn-tun2socks
[--help]
[--version]
[--logger <stdout/syslog>]
[--syslog-facility <string>] [--syslog-ident <string>]
[--loglevel <0-5/none/error/warning/notice/info/debug>]
[--channel-loglevel <nombre-canal> <0-5/none/error/warning/notice/info/debug>] ...
[--tundev <nombre>]
--netif-ipaddr <ipaddr>
--netif-netmask <ipnetmask>
--socks-server-addr <addr>
[--udpgw-remote-server-addr <addr>]
[--udpgw-max-connections <número>]
[--udpgw-connection-buffer-size <número>]

El formato de dirección es a.b.c.d:puerto (IPv4) o [dirección]:puerto (IPv6).

DESCRIPCIÓN

badvpn-tun2socks es una utilidad de red utilizada para "socksificar" conexiones TCP a nivel de red. Implementa un dispositivo TUN que acepta todas las conexiones TCP entrantes (sin importar la IP de destino) y las reenvía a través de un servidor SOCKS. Esto permite reenviar todas las conexiones a través de SOCKS, sin necesidad de soporte por parte de las aplicaciones. Puede utilizarse, por ejemplo, para reenviar conexiones a través de un servidor SSH remoto.

EJEMPLO

Este ejemplo demuestra el uso de tun2socks en combinación con la característica de reenvío dinámico de SSH.

Conéctate al servidor SSH, pasando -D localhost:1080 al comando ssh para habilitar el reenvío dinámico. Esto hará que ssh abra un servidor SOCKS local a través del cual tun2socks reenviará las conexiones.

Primero, crea un dispositivo TUN (por ejemplo, usando openvpn):

  openvpn --mktun --dev tun0 --user <algúnusuario>

Configura la IP del nuevo dispositivo tun:

  ifconfig tun0 10.0.0.1 netmask 255.255.255.0

Ahora inicia el programa badvpn-tun2socks:

  badvpn-tun2socks --tundev tun0 --netif-ipaddr 10.0.0.2 --netif-netmask 255.255.255.0 \
                   --socks-server-addr 127.0.0.1:1080

Ten en cuenta que la dirección 10.0.0.2 no es un error tipográfico. Especifica la dirección IP del router virtual dentro del dispositivo TUN y debe ser diferente de la IP de la interfaz TUN en sí (pero en la misma subred).

Ahora deberías poder hacer ping a la IP del router virtual (10.0.0.2):

  ping -n 10.0.0.2

Todo lo que queda es enrutar las conexiones a través del dispositivo TUN en lugar de la puerta de enlace predeterminada existente. Esto se hace de la siguiente manera:

1. Añade una ruta al servidor SSH a través de tu puerta de enlace existente, con una métrica menor que la ruta predeterminada original.

2. Si tus servidores DNS están en una red que no está directamente conectada (por ejemplo, en Internet), también añade rutas para ellos (como para el servidor SSH). Esto es necesario porque tun2socks no reenvía UDP por defecto (ver más abajo).

3. Añade una ruta predeterminada a través del router virtual en el dispositivo TUN, con una métrica menor que la ruta predeterminada original, pero mayor que las rutas SSH y DNS.

Esto hará que todas las conexiones externas pasen por el dispositivo TUN, excepto la conexión SSH (de lo contrario, SSH pasaría por el dispositivo TUN, que pasaría por... SSH).

Por ejemplo (suponiendo que no hay rutas predeterminadas existentes con métrica <=6; de lo contrario, elimínalas o cambia sus métricas):

  route add <IP_del_servidor_SSH> gw <IP_de_la_puerta_de_enlace_original> metric 5
  <lo mismo para DNS>
  route add default gw 10.0.0.2 metric 6

REENVÍO UDP

tun2socks puede reenviar UDP, sin embargo, esto requiere un demonio reenviador, badvpn-udpgw, que se ejecute en el servidor SSH remoto:

  badvpn-udpgw --listen-addr 127.0.0.1:7300

Luego, indica a tun2socks que reenvíe UDP a través del reenviador:

  --udpgw-remote-server-addr 127.0.0.1:7300
