NOMBRE

bt_language - el lenguaje de datos BibTeX, tal como es reconocido por btparse

SINOPSIS

# Gramática léxica, modo 1: nivel superior
AT                    \@
NEWLINE               \n
COMMENT               \%~[\n]*\n
WHITESPACE            [\ \r\t]+
JUNK                  ~[\@\n\ \r\t]+
# Gramática léxica, modo 2: dentro de una entrada
NEWLINE               \n
COMMENT               \%~[\n]*\n
WHITESPACE            [\ \r\t]+
NUMBER                [0-9]+
NAME                  [a-z0-9\!\$\&\*\+\-\.\/\:\;\<\>\?\[\]\^\_\`\|]+
LBRACE                \{
RBRACE                \}
LPAREN                \(
RPAREN                \)
EQUALS                =
HASH                  \#
COMMA                 ,
QUOTE                 \"
# Gramática léxica, modo 3: cadenas
# (muy complicada -- ver el texto)
# Gramática sintáctica:
bibfile : ( entry )*
entry : AT NAME body
body : STRING                    # para entradas de comentario
     | ENTRY_OPEN contents ENTRY_CLOSE
contents : ( NAME | NUMBER ) COMMA fields   # para entradas regulares
         | fields                # para entradas de definición de macro
         | value                 # para entradas de preámbulo
fields : field { COMMA fields }
       | 
field : NAME EQUALS value
value : simple_value ( HASH simple_value )*
simple_value : STRING
             | NUMBER
             | NAME

DESCRIPCIÓN

Uno de los problemas de BibTeX es que no existe una especificación formal del lenguaje. Esto significa que los usuarios que exploran los rincones más oscuros del lenguaje se quedan en gran medida por su cuenta, y los programadores que implementan sus propios analizadores (parsers) se quedan completamente por su cuenta, a menos que observen el comportamiento de la implementación original.

Otros implementadores de analizadores (Nelson Beebe de "bibclean" , en particular) se han tomado la molestia de explicar el lenguaje aceptado por su analizador, y en ese espíritu se presenta lo siguiente.

Si no está familiarizado con los misterios de los lenguajes regulares y libres de contexto, no lo tendrá fácil para entender esto. Esto no es no una introducción al lenguaje BibTeX; cualquier libro de LaTeX sería más adecuado para aprender el lenguaje de datos en sí mismo.

GRAMÁTICA LÉXICA

El analizador léxico tiene tres modos distintos: nivel superior, dentro de una entrada y cadena. En términos generales, el nivel superior es el modo inicial; entramos en el modo de dentro de una entrada al ver un "@" en el nivel superior; y al ver el "}" o ")" que termina la entrada, volvemos al nivel superior. Entramos en el modo cadena al ver un " o una "{" que no delimita una entrada desde el modo de dentro de una entrada. Tenga en cuenta que el lenguaje léxico es a la vez no regular (porque las llaves deben equilibrarse) y sensible al contexto (porque "{" puede significar cosas diferentes dependiendo de su contexto sintáctico). Dicho esto, usaremos expresiones regulares para describir los elementos léxicos, porque son el punto de partida utilizado por el propio analizador léxico. El resto de la gramática léxica se explicará informalmente en el texto.

Desde el nivel superior, se reconocen los siguientes tokens de acuerdo con las expresiones regulares de la derecha:

AT                    \@
NEWLINE               \n
COMMENT               \%~[\n]*\n
WHITESPACE            [\ \r\t]+
JUNK                  ~[\@\n\ \r\t]+

(Tenga en cuenta que esta es la sintaxis de expresiones regulares de PCCTS, que debería ser bastante familiar para los usuarios de otros motores de regex. Una peculiaridad es que una clase de caracteres se niega como "~[...]" en lugar de "[^...]".)

Al ver "at" en el nivel superior, entramos en el modo de dentro de una entrada. Los espacios en blanco, la basura (junk), los saltos de línea y los comentarios se omiten todos, y los dos últimos incrementan un contador de líneas. (La basura se reconoce explícitamente para permitir el esquema de "comentario implícito" de "bibtex".)

Desde el modo de dentro de una entrada, reconocemos el salto de línea, el comentario y el espacio en blanco de la misma manera que en el modo de nivel superior. Además, se reconocen los siguientes tokens:

NUMBER                [0-9]+
NAME                  [a-z0-9\!\$\&\*\+\-\.\/\:\;\<\>\?\[\]\^\_\`\|]+
LBRACE                \{
RBRACE                \}
LPAREN                \(
RPAREN                \)
EQUALS                =
HASH                  \#
COMMA                 ,
QUOTE                 \"

En este punto, el analizador léxico empieza a sonar sospechosamente como una gramática libre de contexto, en lugar de una colección de expresiones regulares independientes. Sin embargo, es necesario mantener esta complejidad en el analizador porque ciertos caracteres ("{" y "("" en particular) tienen significados léxicos muy diferentes dependiendo de los tokens que los han precedido en el flujo de entrada.

En particular, "{" y "(" se tratan como "abridores de entrada" si siguen a un token "at" y a un token "name" , a menos que el valor del token "name" sea "comment". (Tenga en cuenta el cambio de nivel superior a dentro de una entrada entre los dos tokens.) En el caso de @comment , el delimitador se considera que inicia una cadena, y entramos en el modo cadena. De lo contrario, el delimitador se guarda, y cuando vemos un "}" o un ")" correspondiente, se considera un "cerrador de entrada". (Las llaves se equilibran automáticamente aquí porque el analizador léxico de cadenas se encarga de contar la profundidad de las llaves.)

En cualquier otro lugar, "{" se considera que inicia una cadena, y entramos en el modo cadena. " siempre inicia una cadena, independientemente del contexto. Los otros tokens ("name", "number", "equals", "hash"y "comma") se reconocen incondicionalmente.

Tenga en cuenta que "name" es un token comodín utilizado para tipos de entrada, claves de citación, nombres de campo y nombres de macro; como BibTeX tiene reglas ligeramente diferentes (y en gran medida no documentadas) para estos varios elementos, se necesita un poco de astucia para que las cosas funcionen. Como punto de partida, considere la definición de BibTeX de lo que está permitido para una clave de entrada: una secuencia de cualquier carácter excepto

" # % ' ( ) , = { }

más espacio. Hay un par de problemas con este esquema. Primero, sin especificar el conjunto de caracteres del que provienen esos "10 mágicos", es un poco difícil saber qué se permite exactamente. Segundo, permitir caracteres "@" podría llevar a una sintaxis de BibTeX confusa (no confunde a BibTeX, pero podría confundir a un lector humano). Finalmente, permitir ciertos caracteres que son especiales para TeX significa que BibTeX puede generar código TeX inválido: intente poner una barra invertida ("\") o una virgulilla ("~") en una clave de citación. (Esta última excepción es bastante específica de la aplicación de "generar código (La)TeX a partir de una base de datos BibTeX", pero dado que esa es la aplicación principal para las bases de datos BibTeX, presumiblemente será la aplicación principal para btparse, al menos inicialmente. Por lo tanto, tiene sentido prestar atención a este problema.)

En btparse, entonces, un nombre se define como cualquier secuencia de letras, dígitos, guiones bajos y los siguientes caracteres:

! $ & * + - . / : ; < > ? [ ] ^ _ ` |

Esta lista se derivó eliminando los "10 mágicos" de BibTeX del conjunto de caracteres ASCII imprimibles de 7 bits (32-126), y luego eliminando además "@", "\"y "~". Esto significa que btparse no permite algunas de las claves de entrada más extrañas que BibTeX aceptaría, como "\foo@bar", pero aún permite una cadena con dígitos iniciales. De hecho, de la definición anterior parece que btparse aceptaría una cadena de todos dígitos como un "nombre;" no es el caso, sin embargo, ya que el analizador léxico reconoce tal cadena de dígitos como un número primero. Hay dos problemas aquí: las claves de entrada de BibTeX pueden ser de hecho completamente numéricas, y los nombres de campo no pueden comenzar con un dígito. (Esas son dos de las diferencias no tan obvias en el manejo de claves y nombres de campo por parte de BibTeX.) Los trucos utilizados para lidiar con estos problemas se implementan en el analizador sintáctico (parser) en lugar del analizador léxico, por lo que están descritos en "GRAMÁTICA SINTÁCTICA" a continuación.

El analizador léxico de cadenas reconoce los tokens "lbrace", "rbrace", "lparen" y "rparen" para contar la profundidad de llaves o paréntesis. Esto es necesario para saber cuándo aceptar una cadena delimitada por llaves o paréntesis. (Nótese que una cadena delimitada por paréntesis solo se permite después de @comment; esta no es una construcción normal de BibTeX.) Además, convierte cada carácter de espacio en blanco no espacial (nueva línea, retorno de carro y tabulación) en un solo espacio. (Las secuencias de espacios en blanco no se colapsan; ese es el dominio del post-procesamiento de cadenas, que está bien alejado del escáner o del analizador.) Finalmente, acepta """ para delimitar cadenas delimitadas por comillas. Aparte de esas restricciones, el analizador léxico de cadenas acepta cualquier cosa hasta el delimitador de fin de cadena.

GRAMÁTICA SINTÁCTICA

(El lenguaje utilizado para describir la gramática aquí es la forma extendida de Backus-Naur (EBNF) utilizada por PCCTS. Los terminales se representan con cadenas en mayúsculas, los no terminales con cadenas en minúsculas; los nombres de los terminales son los mismos que los dados en la gramática léxica anterior. "( foo )*" significa cero o más repeticiones de la producción "foo", y "{ foo }" significa una "foo" opcional.)

Un archivo es solo una secuencia de cero o más entradas:

bibfile : ( entry )*

Una entrada es una arroba, un nombre (el "tipo de entrada") y el cuerpo de la entrada:

entry : AT NAME body

Un cuerpo es una cadena (esta alternativa solo se intenta si el tipo de entrada es "comment") o el contenido de la entrada:

body : STRING                    # para entradas de comentario
     | ENTRY_OPEN contents ENTRY_CLOSE

("ENTRY_OPEN" y "ENTRY_CLOSE" son "{" y "}" o "(" y ")", dependiendo de lo que se vea en la entrada para una entrada particular.)

Hay tres producciones posibles para el no terminal "contents". Solo una se aplica a cualquier entrada dada, dependiendo del meta-tipo de entrada (que a su vez depende del tipo de entrada). Actualmente, btparse soporta cuatro meta-tipos de entrada: comentario, preámbulo, definición de macro y regular. Las dos primeras corresponden a las entradas @comment y @preamble; "definición de macro" es para entradas @string; y "regular" es para todos los demás tipos de entrada. (La biblioteca se extenderá para manejar los tipos de entrada @modify y @alias, y los meta-tipos correspondientes de "modify" y "alias", cuando se lance BibTeX 1.0 y se conozca la sintaxis exacta.) El concepto de "meta-tipo" es necesario para que todos los tipos de entrada que no se reconocen específicamente caigan en el meta-tipo "regular". También es conveniente no tener que hacer "strcmp" el tipo de entrada todo el tiempo.

contents : ( NAME | NUMBER ) COMMA fields     # para entradas regulares
         | fields                # para entradas de definición de macro
         | value                 # para entradas de preámbulo

Nótese que la clave de entrada no es solo un "NAME", sino "( NAME | NUMBER)". Esto es necesario porque BibTeX permite claves de entrada totalmente numéricas, pero el analizador léxico de btparse reconoce tales cadenas de dígitos como tokens "NUMBER".

"fields" es una lista separada por comas de campos, con una coma final opcional:

fields : field { COMMA fields }
       |

Un "field" es una única asignación de "campo = valor":

field : NAME EQUALS value

Nótese que "NAME" aquí es una versión restringida del token "name" descrito en "GRAMÁTICA LÉXICA" anterior. Cualquier token "name" será aceptado por el analizador, pero se verifica inmediatamente para asegurar que no comience con un dígito; si es así, se activa un error de sintaxis artificial. (Esto es para compatibilidad con BibTeX, que no permite que los nombres de campo comiencen con un dígito.)

Un "value" es una serie de valores simples unidos por caracteres '#':

value : simple_value ( HASH simple_value )*

Un valor simple es una cadena, un número o un nombre (para invocaciones de macro):

simple_value : STRING
             | NUMBER
             | NAME
