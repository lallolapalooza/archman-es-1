BYACC(1) Comandos de Usuario BYACC(1)

NOMBRE

byacc - generador de analizadores LALR(1)

SINOPSIS

byacc [ -BdghilLPrtvVy ] [ -b prefijo_archivo ] [ -H archivo_definiciones ] [ -o archivo_salida ] [ -p prefijo_simbolo ] nombre_archivo

DESCRIPCIÓN

Byacc lee la especificación de la gramática en el archivo nombre_archivo y genera un analizador LALR(1) para ella. Los analizadores consisten en un conjunto de tablas de análisis LALR(1) y una rutina de control escrita en el lenguaje de programación C. Byacc normalmente escribe las tablas de análisis y la rutina de control en el archivo y.tab.c.

Las siguientes opciones están disponibles:

-b prefijo_archivo
La opción -b cambia el prefijo que se antepone a los nombres de los archivos de salida al texto denotado por prefijo_archivo. El prefijo predeterminado es el carácter y.
-B
crea un analizador de retroceso (configuración en tiempo de compilación para btyacc).
-d
hace que se escriba el archivo de cabecera y.tab.h. Contiene #define para los identificadores de tokens.
-h
imprime un mensaje de uso en la salida estándar.
-H archivo_definiciones
hace que los #define para los identificadores de tokens se escriban en el archivo_definiciones proporcionado en lugar del archivo y.tab.h utilizado por la opción -d.
-g
La opción -g hace que se escriba una descripción gráfica del analizador LALR(1) generado en el archivo y.dot en formato graphviz, listo para ser procesado por dot(1).
-i
La opción -i hace que se escriba un archivo de cabecera suplementario y.tab.i. Contiene declaraciones extern y #define suplementarios según sea necesario para mapear los nombres convencionales prefijados por yacc con yy a lo que la opción -p pueda especificar. El archivo de código, por ejemplo, y.tab.c se modifica para incluir este archivo así como el archivo y.tab.h, forzando un uso consistente de los símbolos definidos en esos archivos.
El archivo de cabecera suplementario facilita la separación de la compilación de archivos lex y yacc.
-l
Si la opción -l no se especifica, byacc insertará directivas #line en el código generado. Las directivas #line permiten que el compilador C relacione los errores en el código generado con el código original del usuario. Si se especifica la opción -l, byacc no insertará las directivas #line. Las directivas #line especificadas por el usuario se conservarán.
-L
habilita el procesamiento de posiciones, por ejemplo, “%locations” (configuración en tiempo de compilación para btyacc).
-o archivo_salida
especifica el nombre del archivo para el archivo del analizador. Si no se proporciona esta opción, el nombre del archivo de salida es el prefijo del archivo concatenado con el sufijo del archivo, por ejemplo, y.tab.c. Esto anula la opción -b.
-p prefijo_simbolo
La opción -p cambia el prefijo que se antepone a los símbolos generados por yacc al texto denotado por prefijo_simbolo. El prefijo predeterminado es la cadena yy.
-P
crea un analizador reentrante, por ejemplo, “%pure-parser”.
-r
La opción -r hace que byacc produzca archivos separados para el código y las tablas. El archivo de código se llama y.code.c y el archivo de tablas se llama y.tab.c. El prefijo “y.” se puede anular usando la opción -b.
-s
suprime las sentencias “#define” generadas para literales de cadena en una sentencia “%token”, para que se parezca más al comportamiento original de yacc.
Normalmente, cuando byacc ve una línea como
%token OP_ADD "ADD"
nota que el “ADD” entre comillas es un identificador C válido, y genera un #define no solo para OP_ADD, sino también para ADD, por ejemplo:
#define OP_ADD 257
#define ADD 258
El yacc original no genera el segundo “#define”. La opción -s suprime este “#define”.
POSIX (IEEE 1003.1 2004) solo documenta nombres y números para “%token”, aunque el yacc original y bison también aceptan literales de cadena.
-t
La opción -t cambia las directivas del preprocesador generadas por byacc de modo que las sentencias de depuración se incorporen al código compilado.
Byacc envía la salida de depuración a la salida estándar (compatible tanto con el yacc original como con btyacc), mientras que btyacc escribe la salida de depuración en la salida de error estándar (como bison).
-v
La opción -v hace que se escriba una descripción legible por humanos del analizador generado en el archivo y.output.
-V
imprime el número de versión en la salida estándar.
-y
byacc ignora esta opción, que bison soporta para compatibilidad aparente con POSIX.

El parámetro nombre_archivo no es opcional. Sin embargo, byacc acepta un único “-” para leer la gramática de la entrada estándar. Un marcador doble “--” denota el fin de las opciones. Se espera un único parámetro nombre_archivo después de un marcador “--”.

DIAGNÓSTICOS

Si hay reglas que nunca se reducen, el número de tales reglas se informa en la salida de error. Si hay algún conflicto LALR(1), el número de conflictos se informa en la salida de error.

EXTENSIÓNES

Byacc proporciona algunas extensiones para la compatibilidad con bison y otras implementaciones de yacc. Acepta varias opciones largas que tienen equivalentes en byacc. Las funciones %destructor y %locations solo están disponibles si byacc ha sido configurado y compilado para soportar la funcionalidad de retroceso (btyacc). El resto de las características están siempre disponibles:

%code palabra_clave { código }
Añade el código fuente indicado en un punto dado del archivo de salida. La palabra_clave opcional le dice a byacc dónde insertar el código:
top
justo después de la definición de versión en el archivo de código generado.
requires
justo después de la declaración de variables públicas del analizador. Si se proporciona la opción -d, el código se inserta al principio del archivo de definiciones.
provides
justo después de la declaración de variables privadas del analizador. Si se proporciona la opción -d, el código se inserta al final del archivo de definiciones.
Si no se proporciona ninguna palabra_clave, el código se inserta al principio de la sección de código copiada literalmente del archivo fuente. Se pueden proporcionar múltiples directivas %code; byacc las inserta en el archivo de código o definiciones correspondiente en el orden en que aparecen en el archivo fuente.
%debug
Esto tiene el mismo efecto que la opción de línea de comandos “-t”.
%destructor { código } simbolo+
define código que se invoca cuando un símbolo se descarta automáticamente durante la recuperación de errores. Este código se puede usar para reclamar dinámic
lly memoria asignada asociada con el valor semántico correspondiente para los casos en los que las acciones del usuario no pueden gestionar la memoria explícitamente.
Al encontrar un error de análisis, el analizador generado descarta símbolos de la pila y tokens de entrada hasta alcanzar un estado que permita continuar el análisis. Este enfoque de recuperación de errores resulta en una fuga de memoria si el YYSTYPE valor es, o contiene, punteros a memoria asignada dinámicamente.
El código entre corchetes código se invoca siempre que el analizador descarta uno de los símbolos. Dentro de código, “$$” o “$<tag>$” designa el valor semántico asociado con el símbolo descartado, y “@$” designa su ubicación (ver %locations directiva).
Un destructor por símbolo se define listando un símbolo de la gramática en symbol+. Un destructor por tipo se define listando una etiqueta de tipo semántico (por ejemplo, “<some_tag>”) en symbol+; en este caso, el analizador invocará código siempre que descarte cualquier símbolo de la gramática que tenga esa etiqueta de tipo semántico, a menos que ese símbolo tenga su propio destructor por símbolo.
Se admiten dos categorías de destructor predeterminado que se invocan al descartar cualquier símbolo de la gramática que no tenga destructor por símbolo ni por tipo:
  • el código para “<*>” se usa para símbolos de la gramática que tienen una etiqueta de tipo semántico declarada explícitamente (mediante “%type”);
  • el código para “<>” se usa para símbolos de la gramática que no tienen etiqueta de tipo semántico declarada.
%empty
ignorado por byacc.
%expect number
le indica a byacc el número esperado de conflictos desplazar/reducir. Eso hace que solo informe el número si difiere.
%expect-rr number
le indica a byacc el número esperado de conflictos reducir/reducir. Eso hace que solo informe el número si difiere. Esto es (a diferencia de bison) permitido en analizadores LALR.
%locations
le indica a byacc habilitar la gestión de la información de posición asociada con cada token, proporcionada por el analizador léxico en la variable global yylloc, de manera similar a la gestión de la información de valor semántico proporcionada en yylval.
Al igual que con los valores semánticos, las ubicaciones se pueden referenciar dentro de las acciones usando @$ para referirse a la ubicación del símbolo del lado izquierdo, y @N (N un entero) para referirse a la ubicación de uno de los símbolos del lado derecho. También al igual que con los valores semánticos, cuando se coincide con una regla, se usa una acción predeterminada para calcular la ubicación representada por @$ como el comienzo del primer símbolo y el final del último símbolo en el lado derecho de la regla. Este cálculo predeterminado se puede anular mediante una asignación explícita a @$ en una acción de regla.
El tipo de yylloc es YYLTYPE, que está definido por defecto como:
typedef struct YYLTYPE {
    int first_line;
    int first_column;
    int last_line;
    int last_column;
} YYLTYPE;
YYLTYPE puede ser redefinido por el usuario (YYLTYPE_IS_DEFINED debe definirse, para inhibir el predeterminado) en la sección de declaraciones del archivo de especificación. Al igual que en bison, la macro YYLLOC_DEFAULT se invoca cada vez que se coincide con una regla para calcular una posición para el lado izquierdo de la regla, antes de que se ejecute la acción asociada; esta macro puede ser redefinida por el usuario.
Esta directiva agrega un YYLTYPE parámetro a yyerror(). Si la %pure-parser directiva está presente, un YYLTYPE parámetro se agrega a las llamadas yylex() .
%lex-param { argument-declaration }
Por defecto, el analizador léxico no acepta parámetros, por ejemplo, yylex(). Use esta directiva para agregar declaraciones de parámetros para su analizador léxico personalizado.
%parse-param { argument-declaration }
Por defecto, el analizador no acepta parámetros, por ejemplo, yyparse(). Use esta directiva para agregar declaraciones de parámetros para su analizador personalizado.
%pure-parser
La mayoría de las variables (aparte de yydebug y yynerrs) se asignan en la pila dentro de yyparse, haciendo que el analizador sea razonablemente reentrante.
%token-table
Hace que los nombres de los tokens del analizador estén disponibles en el yytname array. Sin embargo, byacc no predefine “$end”, “$error” ni “$undefined” en este array.

PORTABILIDAD

Según Robert Corbett,

Berkeley Yacc es un generador de analizadores LALR(1).  Berkeley Yacc
ha sido hecho tan compatible como sea posible con AT&T Yacc.
Berkeley Yacc puede aceptar cualquier especificación de entrada que
conforme a la documentación de AT&T Yacc.  Las especificaciones
que aprovechen características no documentadas de AT&T Yacc
probablemente serán rechazadas.

La justificación en

http://pubs.opengroup.org/onlinepubs/9699919799/utilities/yacc.html

documenta algunas características de AT&T yacc que ya no son requeridas para el cumplimiento de POSIX.

Dicho esto, puede que le interese reutilizar archivos de gramática con alguna otra implementación que no sea estrictamente compatible con AT&T yacc. Por ejemplo, hay bison. Aquí hay algunas diferencias:

•
Yacc acepta un signo igual precediendo la llave izquierda de una acción (como en el archivo de gramática original ftp.y):
    |   STAT CRLF
        = {
                statcmd();
        }
  • Yacc y bison emiten el código en un orden diferente, y en particular bison hace referencia anticipada a funciones comunes como yylex, yyparse y yyerror sin proporcionar prototipos.
  • El soporte de bison para “%expect” está roto en más de una versión. Para obtener los mejores resultados usando bison, elimine esa directiva.
  • Bison no tiene equivalente para algunas de las byaccopciones de línea de comandos, dependiendo de directivas incrustadas en el archivo de gramática.
  • La opción “-y” de bison no afecta la falta de soporte de bison para características de AT&T yacc que se consideraron obsoletas.
  • Yacc acepta múltiples parámetros con %lex-param y %parse-param en dos formas
{type1 name1} {type2 name2} ...
{type1 name1,  type2 name2 ...}
Bison acepta la última (aunque no documentada), pero dependiendo de la versión puede generar código incorrecto.
•
Al igual que bison, byacc agregará parámetros especificados mediante %parse-param a yyparse, yyerror y (si está configurado para back-tracking) al destructor declarado usando %destructor. Bison pone los parámetros adicionales primero para yyparse y yyerror pero al final para los destructores. Yacc coincide con este comportamiento.
