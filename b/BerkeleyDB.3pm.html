Este módulo de Perl proporciona una interfaz para la mayoría de la funcionalidad disponible en las versiones 2, 3, 5 y 6 de Berkeley DB. En general, es seguro asumir que la interfaz proporcionada aquí es idéntica a la interfaz de Berkeley DB. Los cambios principales han sido para hacer que la API de Berkeley DB funcione de una manera idiomática en Perl. Tenga en cuenta que si está usando Berkeley DB 2.x, las nuevas funciones disponibles en Berkeley DB 3.x o posteriores no están disponibles a través de este

módulo.

Se espera que el lector esté familiarizado con la documentación de Berkeley DB. Donde la interfaz proporcionada aquí es idéntica a la biblioteca de Berkeley DB y la...

La Clase BerkeleyDB::

Env

La clase BerkeleyDB::Env proporciona una interfaz a la función de Berkeley DB db_appinit en Berkeley DB 2.x o db_env_create y DBENV->open en Berkeley DB 3.x (o posterior). Su propósito es inicializar una serie de subsistemas que luego pueden usarse de manera consistente en todas las bases de datos que utilice en el

entorno.

Si no pretende usar transacciones, bloqueo o registro (logging), entonces no debería necesitar hacer uso de BerkeleyDB:

:Env.

Tenga en cuenta que un entorno consiste en una serie de archivos que Berkeley DB gestiona en segundo plano por usted. Cuando use un entorno por primera vez, necesita ser creado explícitamente. Esto se hace incluyendo "DB_CREATE" con el parámetro "Flags", descrito a

continuación.

Almacén de Datos Concurrente de Berkeley DB

(CDS)

El Almacén de Datos Concurrente de Berkeley DB (CDS) es un mecanismo de bloqueo ligero que es útil en escenarios donde las transacciones son

excesivas.

¿Qué es

CDS?

La interfaz CDS de Berkeley DB es un mecanismo de bloqueo ligero y simple que permite un acceso concurrente seguro a las bases de datos de Berkeley DB. Su aplic

ación puede tener múltiples procesos lectores y escritores, pero Berkeley DB lo organizará de modo que solo un proceso pueda tener un bloqueo de escritura en la
base de datos a la vez, es decir, múltiples procesos pueden leer de una base de datos concurrentemente, pero todos los procesos de escritura serán serializados.

¿Debería

usarlo?

Aunque este modelo de bloqueo simple es perfectamente adecuado para algunas aplicaciones, será demasiado restrictivo para otras. Antes de decidir usar el modo CDS, debe estar seguro de que es adecuado para el comportamiento esperado de su

aplicación.

Las características clave de este modelo

son
  • Todas las operaciones de escritura están
    • serializadas.
  • Una operación de escritura s
    • e bloqueará hasta que todas l
as lecturas hayan terminado.

Hay algunos atributos de su aplicación de los que debe ser consciente antes de elegir usar

CDS.

En primer lugar, si su aplicación necesita recuperabilidad o soporte de transacciones, entonces CDS no será

adecuado.

A continuación, ¿cuál será la proporción de operaciones de lectura a operaciones de escritura que tendrá su

aplicación?

Si está realizando principalmente operaciones de lectura y muy pocas escrituras, entonces CDS puede ser

apropiado.

¿Cuál es el rendimiento esperado de lecturas/escrituras en su

aplicación?

Si su aplicación hace un 90% de escrituras y un 10% de lecturas, pero en promedio solo tiene una transacción cada 5 segundos, entonces el hecho de que todas las escrituras estén serializadas no importará, porque casi nunca habrá múltiples procesos de escritura

bloqueados.

En resumen, el modo CDS puede ser apropiado para su aplicación si realiza principalmente lecturas y muy pocas escrituras o si hay un bajo rendimiento. Además, si no necesita poder revertir una serie de operaciones de base de datos si ocurre un error, entonces CDS está

bien.

Si alguno de estos no es el caso, necesita

rá usar transacciones de Berkeley DB. Eso
está fuera del alcance de este documento.

Bloqueo

Utilizado

Berkeley DB implementa el modo CDS usando dos tipos de bloqueo por debajo del capó - a saber, bloqueos de lectura y bloqueos de escritura. Un bloqueo de lectura permite que múltiples procesos accedan a la base de datos para lectura al mismo tiempo. Un bloqueo de escritura solo obtendrá acceso a la base de datos cuando no haya bloqueos de lectura o escritura activos. El bloqueo de escritura se bloqueará hasta que el proceso que retiene el bloqueo lo

libere.

Múltiples procesos con bloqueos de lectura pueden acceder a la base de datos al mismo tiempo siempre que ningún proceso tenga un bloqueo de escritura. Un proceso con un bloqueo de escritura solo puede acceder a la base de datos si no hay otros bloqueos de lectura o escritura

activos.

La mayor parte del tiempo el modo CDS de Berkeley DB manejará todo el bloqueo sin que su aplicación tenga que hacer nada. Sin embargo, hay algunas excepciones de las que debe ser consciente - estas se discutirán en "Actualizando Registros de Forma Segura" y "Cursores Implícitos" más

abajo.

Un Cursor de Berkeley DB (creado con "$db->db_cursor") retendrá un bloqueo en la base de datos hasta que se cierre explícitamente o se destruya. Esto significa que el bloqueo tiene el potencial de ser de larga

duración.

Por defecto los cursores de Berkeley DB crean un bloqueo de lectura, pero es posible crear un cursor que retenga un bloqueo de escritura,

así 
$cursor = $db->db_cursor(DB_WRITECURSOR)
;

Mientras un cursor de lectura o escritura esté activo, bloqueará cualquier otro proceso que quiera escribir en la base de

datos.

Para evitar problemas de bloqueo, mantenga los cursores abiertos solo el tiempo que sean necesarios. Lo mismo es cierto cuando usa el método "cursor" o el método "cds_lock"

.

Para información completa sobre CDS, consulte la sección "Berkeley DB

Concurrent Data Store applications" (Aplicaciones de Almacén de Datos
Concurrente de Berkeley DB) en la Guía de Referencia de Berkeley DB.

Actualizando un Registro de Forma

Segura

Una de las principales trampas al usar CDS es si quiere actualizar un registro en una base de datos, es decir, quiere recuperar un registro de una base de datos, modificarlo de alguna manera y ponerlo de vuelta en la base de

datos.

Por ejemplo, digamos que está escribiendo una aplicación web y quiere mantener un registro del número de veces que su sitio es accedido en una base de datos de Berkeley DB. Así que su código tendrá una línea de código como esta (suponiendo, por supuesto, que %hash ha sido vinculado (tied) a una base de datos de Berkeley DB)

: 
$hash{Counter} ++
;

Eso puede parecer inofensivo, pero hay una condición de carrera escondida ahí. Si reescribo la línea de código usando la API de bajo nivel de Berkeley DB, que es lo que realmente se ejecutará, la condición de carrera puede ser más

aparente: 
$db->db_get("Counter", $value);
++ $value ;
$db->db_put("Counter", $value)
;

Considere lo que sucede por debajo del capó cuando ejecuta los comandos anteriores. Primero, el valor existente para la clave "Counter" se obtiene de la base de datos usando "db_get". Se usará un bloqueo de lectura para esta parte de la actualización. Luego el valor se incrementa, y el nuevo valor se escribe de vuelta a la base de datos usando "db_put". Esta vez se usará un bloqueo de

escritura.

Aquí está el problema - no hay nada que impida que dos (o más) procesos ejecuten la parte de lectura al mismo tiempo. Recuerde, múltiples procesos pueden retener un bloqueo de lectura en la base de datos al mismo tiempo. Así que ambos obtendrán el mismo valor, digamos 7, de la base de datos. Ambos incrementan el valor a 8 e intentan escribirlo en la base de datos. Berkeley DB asegurará que solo uno de los procesos obtenga un bloqueo de escritura, mientras el otro será bloqueado. Así que el proceso que ocurrió que obtuvo el bloqueo de escritura almacenará el valor 8 en la base de datos y liberará el bloqueo de escritura. Ahora el otro proceso será desbloqueado, y también escribirá el valor 8 en la base de datos. El resultado, en este ejemplo, es que hemos perdido un acierto en el

contador.

Para manejar este tipo de escenario, necesita hacer la actualización atómica. Un método de conveniencia, llamado "cds_lock", es suministrado con el módulo BerkeleyDB para este propósito. Usando "cds_lock", el código de actualización del contador ahora puede ser reescrito

así: re>my $lk = $dbh->cds_lock() ; $hash{Counter} ++ ; $lk->cds_unlock;

o bien esto, donde se utiliza el ámbito para limitar el tiempo de vida del objeto de

bloqueo 
{
    my $lk = $dbh->cds_lock() ;
    $hash{Counter} ++ ;
}

De manera similar, "cds_lock" puede usarse con la API nativa de Berkeley

DB 
my $lk = $dbh->cds_lock() ;
$db->db_get("Counter", $value);
++ $value ;
$db->db_put("Counter", $value);
$lk->
unlock;

El método "cds_lock" se asegurará de que el proceso actual tenga acceso exclusivo a la base de datos hasta que el bloqueo sea liberado explícitamente, mediante "$lk->cds_unlock()" o cuando el objeto de bloqueo sea

destruido.

Si le interesa, todo lo que hace "cds_lock" es abrir un cursor de "escritura". Esto tiene el efecto secundario útil de mantener un bloqueo de escritura en la base de datos hasta que el cursor sea eliminado. Así es como se crea un cursor de

escritura 
$cursor = $db->db_cursor(DB_WRITECURSOR)
;

Si ha instanciado múltiples objetos "cds_lock" para una base de datos dentro de un solo proceso, ese proceso mantendrá un bloqueo de escritura en la base de datos hasta que TODOS los objetos "cds_lock" hayan sido destruidos. Los objetos "cds_lock" han sido

destruidos.

Como con todos los cursores de escritura, debe intentar limitar el ámbito del "cds_lock" al menor tiempo posible. Recuerde que la base de datos completa est

ará bloqueada para otros procesos mien
tras el bloqueo de escritura esté activo.

No se puede escribir con un cursor de lectura mientras un cursor de escritura está

activo

Este problema es más fácil de demostrar con un ejemplo, así que considere el código siguiente. La intención del código es incrementar los valores de todos los elementos en una base de datos en

uno. 
# Assume $db is a database opened in a CDS environment.
# Create a write-lock
my $lock = $db->db_cursor(DB_WRITECURSOR);
# or
# my $lock = $db->cds_lock();
my $cursor = $db->db_cursor();
# Now loop through the database, and increment
# each value using c_put.
while ($cursor->c_get($key, $value, DB_NEXT) == 0)
{
     $cursor->c_put($key, $value+1, DB_CURRENT) == 0
         or die "$BerkeleyDB::Error\n";
}

El cursor de lectura ha deshabilitado automáticamente una operación de escritura para prevenir un bloqueo mutuo (deadlock)

Así que la regla es -- usted NO PUEDE llevar a cabo una operación de escritura usando un cursor de solo lectura (es decir, no puede usar "c_put" ni "c_del") mientras otro cursor de escritura ya está

activo.

La solución para este problema es simplemente usar "db_put" en lugar de "c_put",

así

# Create a write-lock
my $lock = $db->db_cursor(DB_WRITECURSOR);
# or
# my $lock = $db->cds_lock();
my $cursor = $db->db_cursor();
# Now loop through the database, and increment
# each value using c_put.
while ($cursor->c_get($key, $value, DB_NEXT) == 0)
{
     $db->db_put($key, $value+1) == 0
         or die "$BerkeleyDB::Error\n";

Cursores

implícitos

Todos los cursores de Berkeley DB mantendrán un bloqueo de lectura o de escritura en la base de datos durante la existencia del cursor. Para prevenir el bloqueo de otros procesos, necesita asegurarse de que no sean de larga

duración.

Hay varias instancias en las que la interfaz Perl para Berkeley DB creará un cursor internamente sin que usted sea consciente de ello. La mayoría de estos son de muy corta duración y no afectarán la ejecución de su script, pero hay algunas excepciones

notables.

Considere este fragmento de

código 
while (my ($k, $v) = each %hash)
{
    # do something
}

Para implementar la funcionalidad de "each", se creará un cursor de lectura internamente para permitirle iterar a través del hash vinculado, %hash. Mientras ese cursor siga activo, se mantendrá obviamente un bloqueo de lectura contra la base de datos. Si su aplicación tiene otros procesos de escritura, estos serán bloqueados hasta que el cursor de lectura se cierre. Eso no sucederá hasta que el bucle

termine.

Para evitar problemas de bloqueo, mantenga los cursores abiertos solo mientras sean necesarios. Lo mismo es cierto cuando usted usa el método "cursor" o el método "cds_

lock".

El comportamiento de bloqueo de las funciones "values" o "keys", mostradas a continuación, es sutilmente

diferente. 
foreach my $k (keys %hash)
{
    # do something
}
foreach my $v (values %hash)
{
    # do something
}

Al igual que en la función "each", se creará un cursor de lectura para iterar sobre la base de datos en ambos casos. Donde "keys" y "values" difieren es en el lugar donde el cursor lleva a cabo la iteración a través de la base de datos. Mientras "each" llevaba a cabo una sola iteración cada vez que era invocado, las funciones "keys" y "values" iterarán a través de la base de datos completa de una sola vez -- la base de datos completa será leída en memoria antes de la primera iteración del

bucle.

Aparte del hecho de que un bloqueo de lectura se mantendrá durante el tiempo requerido para iterar a través de la base de datos, el uso de "keys" y "values" es no recomendado porque resultará en que la

base de datos completa
sea leída en memoria.

Evitando el bloqueo mutuo (deadlock) con múltiples bases de

datos

Si su aplicación CDS usa múltiples archivos de base de datos, y necesita escribir en más de uno de ellos, necesita tener cuidado de no crear un bloqueo

mutuo.

Por ejemplo, digamos que tiene dos bases de datos, D1 y D2, y dos procesos, P1 y P2. Asuma que quiere escribir un registro en cada base de datos. Si P1 escribe los registros en las bases de datos en el orden D1, D2 mientras el proceso P2 escribe los registros en el orden D2, D1, existe el potencial de que ocurra un bloqueo

mutuo.

Este escenario puede evitarse ya sea adquiriendo siempre los bloqueos de escritura en exactamente el mismo orden en el código de su aplicación, o usando el indicador "DB_CDB_ALLDB" al abrir el entorno. Este indicador hará que un bloqueo de escritura se aplique a todas las bases de datos en el

entorno.

Un ejemplo -- el problema de la terminación

NULL.

Considere el siguiente escenario. Usted tiene una base de datos DBM que necesita compartir con una aplicación de C de terceros. La aplicación de C asume que todas las claves y valores están terminados en NULL. Desafortunadamente, cuando Perl escribe en bases de datos DBM no usa terminación NULL, así que su aplicación Perl tendrá que gestionar la terminación NULL por sí misma. Cuando usted escriba en la base de datos tendrá que usar algo como

esto: 
$hash{"$key\0"} = "$value\0"
;

De manera similar, el NULL necesita ser tenido en cuenta cuando usted está considerando la longitud de las claves/valores

existentes.

Sería mucho mejor si pudiera ignorar las terminaciones NULL problema en el código principal de la aplicación y tener un mecanismo que automáticamente añada el NULL terminante a todas las claves y valores cada vez que se escribe en la base de datos y que los elimine cuando se leen de la base de datos. Como seguro que ya has adivinado, este es un problema que los Filtros DBM pueden resolver muy

fácilmente. 
use strict ;
use BerkeleyDB ;
my %hash ;
my $filename = "filt.db" ;
unlink $filename ;
my $db = tie %hash, 'BerkeleyDB::Hash',
            -Filename   => $filename,
            -Flags      => DB_CREATE
  or die "Cannot open $filename: $!\n" ;
# Install DBM Filters
$db->filter_fetch_key  ( sub { s/\0$//    } ) ;
$db->filter_store_key  ( sub { $_ .= "\0" } ) ;
$db->filter_fetch_value( sub { s/\0$//    } ) ;
$db->filter_store_value( sub { $_ .= "\0" } ) ;
$hash{"abc"} = "def" ;
my $a = $hash{"ABC"} ;
# ...
undef $db ;
untie %hash
;

Con suerte, el contenido de cada uno de los filtros debería ser

autoexplicativo. Ambos filtros "fetch" eliminan el NULL
terminante, y ambos filtros "store" añaden un NULL terminante.

$db->filter_store_key  ( sub { $_ = pack ("i", $_) } ) ;

untie %hash
;
