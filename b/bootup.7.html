NOMBRE

bootup - Proceso de arranque del sistema

DESCRIPCIÓN

Intervienen varios componentes diferentes en el arranque de un sistema Linux. Inmediatamente después de encender la energía, el firmware del sistema realizará una inicialización mínima del hardware y cederá el control a un cargador de arranque (por ejemplo, systemd-boot(7) o GRUB[1]) almacenado en un dispositivo de almacenamiento persistente. Este cargador de arranque invocará entonces un kernel del sistema operativo desde el disco (o la red). En los sistemas que utilizan EFI u otros tipos de firmware, este firmware también puede cargar el kernel directamente.

El kernel (opcionalmente) monta un sistema de archivos en memoria, que busca el sistema de archivos raíz. En la actualidad esto se implementa como un "initramfs" — un archivo CPIO comprimido que el kernel extrae en un tmpfs. En el pasado se utilizaban sistemas de archivos normales con un dispositivo de bloque en memoria (ramdisk), y el nombre "initrd" todavía se usa para describir ambos conceptos. Es el cargador de arranque o el firmware el que carga tanto el kernel como las imágenes initrd/initramfs en la memoria, pero es el kernel el que lo interpreta como un sistema de archivos. systemd(1) puede usarse para gestionar servicios en el initrd, de manera similar al sistema real.

Después de que se encuentra y monta el sistema de archivos raíz, el initrd cede el control al gestor de sistema del host (como systemd(1)) almacenado en el sistema de archivos raíz, el cual es entonces responsable de detectar todo el hardware restante, montar todos los sistemas de archivos necesarios y lanzar todos los servicios configurados.

Al apagarse, el gestor de sistema detiene todos los servicios, desmonta todos los sistemas de archivos que no estén ocupados (desconectando las tecnologías de almacenamiento que los respaldan), y luego (opcionalmente) salta al exitrd. El exitrd está respaldado por tmpfs y desmonta/desconecta los sistemas de archivos restantes, incluyendo el raíz real. Como último paso, el sistema se apaga.

Se puede encontrar información adicional sobre el proceso de arranque del sistema en boot(7).

ARRANQUE DEL GESTOR DE SISTEMA

Al arrancar, el gestor de sistema en la imagen del SO es responsable de inicializar los sistemas de archivos, servicios y controladores necesarios para el funcionamiento del sistema. En los sistemas systemd(1) , este proceso se divide en varios pasos discretos que se exponen como unidades objetivo. (Véase systemd.target(5) para información detallada sobre las unidades objetivo.) El proceso de arranque está altamente paralelizado de modo que el orden en que se alcanzan unidades objetivo específicas no es determinista, pero aún así se adhiere a una cantidad limitada de estructura de ordenación.

Cuando systemd inicia el sistema, activará todas las unidades que son dependencias de default.target (así como recursivamente todas las dependencias de estas dependencias). Usualmente, default.target es simplemente un alias de graphical.target o multi-user.target, dependiendo de si el sistema está configurado para una interfaz gráfica o solo para una consola de texto. Para imponer un ordenación mínima entre las unidades incluidas, hay disponibles varias unidades objetivo bien conocidas, como se lista en systemd.special(7).

Las unidades objetivo que se usan comúnmente como objetivos de arranque están enfatizadas. Estas unidades son buenas opciones como objetivos finales, por ejemplo pasándolas a la opción de línea de comandos del kernel systemd.unit= (véase systemd(1)) o creando un enlace simbólico desde default.target hacia ellas.

timers.target es incluido por basic.target de forma asíncrona. Esto permite que las unidades de temporizador dependan de servicios que solo se vuelven disponibles más tarde en el arranque.

INICIO DEL GESTOR DE USUARIO

El gestor de sistema inicia la unidad user@uid.service para cada usuario, la cual lanza una instancia separada sin privilegios de systemd para cada usuario — el gestor de usuario. De manera similar al gestor de sistema, el gestor de usuario inicia unidades que son incluidas por default.target. El siguiente gráfico es una visión general estructural de las unidades de usuario bien conocidas. Para sesones no gráficas, se usa default.target. Cada vez que el usuario inicia sesión en una sesión gráfica, el gestor de inicio de sesión iniciará el objetivo graphical-session.target que se usa para incluir las unidades requeridas para la sesión gráfica. Varios objetivos (mostrados en el lado derecho) se inician cuando el hardware específico está disponible para el usuario.

ARRANQUE EN EL INITRD

Systemd también puede utilizarse en el initrd. Detecta el entorno del initrd comprobando la existencia del archivo /etc/initrd-release. El objetivo predeterminado en el initrd es initrd.target. El proceso de arranque es idéntico al del gestor del sistema hasta el objetivo basic.target. Después de eso, systemd ejecuta el objetivo especial initrd.target. Antes de que se monten los sistemas de archivos, el gestor determinará si el sistema debe reanudarse desde la hibernación o continuar con el arranque normal. Esto se logra mediante systemd-hibernate-resume.service, el cual debe finalizarse antes de local-fs-pre.target, de modo que ningún sistema de archivos pueda montarse antes de que la comprobación esté completa. Cuando el dispositivo raíz se encuentra disponible, se alcanza initrd-root-device.target. Si el dispositivo raíz puede montarse en /sysroot, la unidad sysroot.mount se vuelve activa y se alcanza initrd-root-fs.target. El servicio initrd-parse-etc.service escanea /sysroot/etc/fstab en busca de un posible punto de montaje /usr/ y entradas adicionales marcadas con la x-initrd.mount opción. Todas las entradas encontradas se montan debajo de /sysroot, y se alcanza initrd-fs.target. El servicio initrd-cleanup.service aísla hacia el initrd-switch-root.target, donde pueden ejecutarse servicios de limpieza. Como último paso, se activa initrd-switch-root.service, lo que hará que el sistema cambie su raíz a /sysroot.

Los objetivos de apagado del sistema comúnmente utilizados son enfatizados.

Tenga en cuenta que systemd-halt.service(8), systemd-reboot.service, systemd-poweroff.service y systemd-kexec.service transicionarán el sistema y el gestor del servidor (PID 1) a la segunda fase del apagado del sistema (implementada en el binario systemd-shutdown), la cual desmontará cualquier sistema de archivos restante, terminará cualquier proceso restante y liberará cualquier otro recurso restante, de una manera simple y robusta, sin tener en cuenta ya ningún concepto de servicio o unidad. En ese punto, las aplicaciones y recursos normales generalmente ya han sido terminados y liberados, por lo que la segunda fase solo opera como una red de seguridad para todo aquello que no pudo ser detenido o liberado por alguna razón durante la fase primaria de apagado basada en unidades descrita arriba.

EL EXITRD

El "exitrd" es un concepto simétrico al del initrd. Cuando el gestor del sistema se está apagando y /run/initramfs/shutdown existe, cambiará la raíz a /run/initramfs/ y ejecutará /shutdown. Este programa se ejecuta desde el tmpfs montado en /run/, por lo que puede desmontar el antiguo sistema de archivos raíz y realizar pasos adicionales, por ejemplo, desmontar almacenamiento complejo o realizar un registro adicional sobre el apagado.
