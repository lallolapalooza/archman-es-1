Operaciones con secuencias de

bytes.

Una secuencia de bytes es una estructura de datos mutable que contiene una secuencia de longitud fija de bytes. Cada byte puede ser indexado en tiempo constante para lectura o

escritura.

Dada una secuencia de bytes s de longitud l , podemos acceder a cada uno de los l bytes de s a través de su índice en la secuencia. Los índices comienzan en 0 , y llamaremos a un índice válido en s si cae dentro del rango [0...l-1] (inclusivo). Una posición es el punto entre dos bytes o al principio o al final de la secuencia. Llamamos a una posición válida en s si cae dentro del rango [0...l] (inclusivo). Tenga en cuenta que el byte en el índice n está entre las posiciones n y n+1

.

Se dice que dos parámetros start y len designan un rango válido de s si len >= 0 y start y start+len son posiciones válidas en s

.

Las secuencias de bytes pueden modificarse in situ, por ejemplo a través de las funciones set y blit descritas a continuación. Véase también cadenas (módulo String ), que son casi la misma estructura de datos, pero no pueden modificarse in

situ.

Los bytes están representados por el tipo de OCaml char

.

La versión etiquetada de este módulo puede usarse como se describe en el módulo StdLabe

ls .

Conversiones no seguras (para usuarios

avanzados)

Esta sección describe funciones de conversión no seguras y de bajo nivel entre bytes y string . No copian los datos internos; usadas incorrectamente, pueden romper el invariante de inmutabilidad de las cadenas. Están disponibles para autores de bibliotecas expertos, pero para la mayoría de los propósitos debería usar BytesLabels.to_string y BytesLabels.of_string en su

lugar.

val unsafe_to_string : bytes ->

string

Convierte inseguramente una secuencia de bytes en una

cadena.

Para razonar sobre el uso de unsafe_to_string , es conveniente considerar una disciplina de "propiedad". Un fragmento de código que manipula algunos datos "posee" esos datos; hay varios modos de propiedad disjuntos,

incluyendo:

-Propiedad única: los datos pueden ser accedidos y

mutados

-Propiedad compartida: los datos tienen varios propietarios, que solo pueden acceder a ellos, no

mutarlos.

La propiedad única es lineal: pasar los datos a otro fragmento de código significa renunciar a la propiedad (no podemos escribir los datos de nuevo). Un propietario único puede decidir hacer que los datos sean compartidos (renunciando a los derechos de mutación sobre ellos), pero los datos compartidos no pueden volver a ser de propiedad

única.

unsafe_to_string s solo puede usarse cuando el llamador posee la secuencia de bytes s -- ya sea de forma única o como datos inmutables compartidos. El llamador renuncia a la propiedad de s , y obtiene la propiedad de la cadena

devuelta.

Hay dos casos de uso válidos que respetan esta disciplina de

propiedad:

1. Crear una cadena inicializando y mutando una secuencia de bytes que nunca cambia después de que se realiza la

inicialización. 
let string_init len f : string =
  let s = Bytes.create len in
  for i = 0 to len - 1 do Bytes.set s i (f i) done;
  Bytes.unsafe_to_string
s

Esta función es segura porque la secuencia de bytes s nunca será accedida o mutada después de que se llame a unsafe_to_string . El código de string_init renuncia a la propiedad de s , y devuelve la propiedad de la cadena resultante a su

llamador.

Nótese que sería inseguro si s se pasara como un parámetro adicional a la función f ya que podría escapar de esta manera y ser mutado en el futuro -- string_init renunciaría a la propiedad de s para pasarlo a f , y no podría llamar a unsafe_to_string de forma

segura.

Hemos proporcionado las funciones String.init , String.map y String.mapi para cubrir la mayoría de los casos de construcción de nuevas cadenas. Debería preferir esas sobre to_string o unsafe_to_string siempre que sea

aplicable.

2. Dar temporalmente la propiedad de una secuencia de bytes a una función que espera una cadena de propiedad única y devuelve la propiedad, para que podamos mutar la secuencia de nuevo después de que la llamada haya

terminado. 
let bytes_length (s : bytes) =
  String.length (Bytes.unsafe_to_string
s)

En este caso de uso, no prometemos que s nunca será mutado después de la llamada a bytes_length s . La función String.length toma prestada temporalmente la propiedad única de la secuencia de bytes (y la ve como una string ), pero devuelve esta propiedad al llamador, que puede asumir que s sigue siendo una secuencia de bytes válida después de la llamada. Nótese que esto solo es correcto porque sabemos que String.length no captura su argumento -- podría escapar por un canal lateral como un combinador de

memoización.

El llamador no puede mutar s mientras la cadena está prestada (ha renunciado temporalmente a la propiedad). Esto afecta a los programas concurrentes, pero también a funciones de orden superior: si String.length devolviera un cierre para ser llamado más tarde, s no debería ser mutado hasta que este cierre sea completamente aplicado y devuelva la

propiedad.

Secuencias de bytes y seguridad de

concurrencia

Se debe tener cuidado al acceder concurrentemente a secuencias de bytes desde múltiples domi

nios: el acceso a una secuencia de bytes nunca hará que un programa se bloquee, pero los acce
sos no sincronizados pueden producir resultados sorprendentes (no consistentes secuencialmente).

Atomicida

d

Toda operación sobre secuencias de bytes que accede a más de un byte no es atómica. Esto incluye la iteración y el

escaneo.

Por ejemplo, considere el siguiente

programa: 
let size = 100_000_000
let b = Bytes.make size  ' '
let update b f ()  =
  Bytes.iteri (fun i x -> Bytes.set b i (Char.chr (f (Char.code x)))) b
let d1 = Domain.spawn (update b (fun x -> x + 1))
let d2 = Domain.spawn (update b (fun x -> 2 * x + 1))
let () = Domain.join d1; Domain.join d2
la secuencia de bytes b puede contener una mezcla no determinista de '!' , 'A' , 'B' y 'C' valores.

Después de ejecutar este código, cada byte de la secuencia b es o bien '!' , 'A' , 'B' o 'C' . Si se requiere atomicidad, entonces el usuario debe implementar su propia sincronización (por ejemplo, usando Mutex.t

)
.

Carreras de

datos

Si dos dominios solo acceden a partes disjuntas de una secuencia de bytes, entonces el comportamiento observado es equivalente a alguna intercalación secuencial de las operaciones de los dos

dominios.

Se dice que ocurre una carrera de datos cuando dos dominios acceden al mismo byte sin sincronización y al menos uno de los accesos es una escritura. En la ausencia de carreras de datos, el comportamiento observado es equivalente a alguna intercalación secuencial de las operaciones de diferentes

dominios.

Siempre que sea posible, las carreras de datos deben evitarse usando sincronización para mediar los accesos a los elementos de la

secuencia.

De hecho, en presencia de carreras de datos, los programas no se bloquearán pero el comportamiento observado puede no

ser equivalente a ninguna intercalación secuencial de operaciones de diferentes dominios. Sin embargo, incluso en prese
ncia de carreras de datos, una operación de lectura devolverá el valor de alguna escritura previa a esa ubicación.

Accesos de tamaño

mixto

Otro punto sutil es que si una carrera de datos implica escrituras y lecturas de tamaño mixto en la misma ubicación, el orden en el que esas escrituras y lecturas son observadas por los dominios no está especificado. Por ejemplo, el siguiente código escribe secuencialmente un entero de 32 bits y un char en el mismo

índice 
let b = Bytes.make 10 '\000'
let d1 = Domain.spawn (fun () -> Bytes.set_int32_ne b 0 100; b.[0] <- 'd' )

En esta situación, un dominio que observa la escritura de 'd' en b. 0 no está garantizado que también observe la escritura en los índices 1 , 2 o 3
