B4(5) Manual de formatos de archivo B4(5)

NOMBRE

B4 - Trabajar con envíos de código en un archivo public-inbox

SINOPSIS

b4 {mbox,am,shazam,pr,diff,ty,kr,prep,send,trailers} [opciones]

DESCRIPCIÓN

Esta es una utilidad auxiliar para trabajar con parches y solicitudes de fusión (pull requests) disponibles a través de un archivo public-inbox como lore.kernel.org. Está escrita para simplificar la participación en flujos de trabajo basados en parches, como los utilizados en el desarrollo del núcleo de Linux.

El nombre "b4" se eligió por su facilidad de escritura y porque B-4 fue el precursor de Lore y Data en el universo de Star Trek.

La documentación completa está disponible en https://b4.docs.kernel.org/ .

SUBCOMANDOS

Orientados al mantenedor:

  • mbox: Descargar un hilo como archivo mbox
  • am: Crear un archivo mbox listo para git-am
  • shazam: Aplicar series de parches a repositorios git
  • pr: Trabajar con solicitudes de fusión (pull requests)
  • ty: Crear respuestas plantilla para parches y solicitudes de fusión procesados
  • diff: Mostrar diferencias estilo range-diff entre versiones de parches
  • kr: (ESQUELETO) Operar con llaveros compatibles con patatt

Orientados al colaborador:

  • prep: preparar tu serie para su envío
  • trailers: recuperar y aplicar trailers de revisión de código
  • send: enviar tu serie para revisión en listas de distribución

Para ver las opciones completas y lo que hacen, por favor consulta b4 --help y b4 subcomando --help.

b4 mbox

Este comando permite recuperar hilos completos de una instancia remota de public-inbox. Puedes abrir el archivo mbox resultante con la mayoría de los clientes de correo para acciones como responder a conversaciones o revisar envíos de parches.

Puedes proporcionar el mensaje ya sea como msgid, como URL completa a un archivo public-inbox, o puedes enviarlo por stdin.

Para las opciones y sus descripciones, consulta b4 mbox --help.

Ejemplos

b4 mbox [msgid]
Descargar un hilo del servidor public-inbox predeterminado y guardarlo en el directorio actual como un archivo .mbox.
b4 mbox -m ~/Mail [msgid]
Descargar un hilo de tu carpeta ~/Mail y guardarlo en el directorio actual como un archivo .mbox.
b4 mbox -fo ~/Mail [public-inbox-url]
Descargar el hilo de este servidor public-inbox y añadirlo a tu buzón existente, filtrando cualquier duplicado que ya esté en la carpeta de tu buzón.

b4 am

Este comando permite recuperar hilos de una instancia public-inbox y prepararlos para aplicarlos a un repositorio git usando el comando "git am". Realizará automáticamente las siguientes operaciones:

  • elegir la última versión enviada de la serie (también puede buscar hilos más nuevos usando -c )
  • verificar firmas DKIM y la atestación patatt en todos los parches y mensajes de revisión de código
  • recopilar todos los trailers de revisión de código enviados (Reviewed-by, Acked-by, etc.) y ponerlos en el mensaje de confirmación
  • añadir tu propio trailer Signed-off-by (con -s)
  • rehacer la serie a partir de actualizaciones parciales (p. ej., alguien envía una v2 de un solo parche en lugar de rehacer toda la serie)
  • adivinar a dónde pertenecen los parches en el historial del árbol, si no se especifica la base de confirmación exacta (con -g)
  • preparar el árbol para una fusión de tres vías (con -3)
  • seleccionar un subconjunto de parches de una serie grande (con -P)

Nota: A menos que pretendas hacer algún trabajo preparatorio en la serie antes de aplicarla al repositorio git (p. ej., una fusión de tres vías), deberías considerar usar b4 shazam para aplicar la serie recuperada.

Para las opciones y sus descripciones, consulta b4 am --help.

Ejemplos

b4 am -sl [msgid]
Descargar un hilo del servidor public-inbox predeterminado, aplicar cualquier trailer de seguimiento, añadir tu propio trailer Signed-Off-By más un trailer Link: que indique el origen del parche, y luego guardar el archivo .mbox resultante en el directorio actual listo para ser aplicado por "git am".
b4 am -sl -P 1-3 [msgid]
Igual que el ejemplo anterior, pero seleccionar solo los parches 1,2,3 de toda la serie.
b4 am -3 [msgid]
Descargar la serie y preparar el árbol git local para una fusión de tres vías asegurándose de que todos los blobs del índice existan.
b4 am --check [msgid]
Descargar la serie y mostrar si pasa las verificaciones. Puedes especificar el comando usando la opción de configuración b4.am-perpatch-check-cmd . Para el núcleo de Linux, el valor predeterminado será el conjunto de opciones más común de checkpatch.pl .

b4 shazam

Esto es muy similar a b4 am, pero también aplicará los parches directamente al árbol git actual usando git am. Alternativamente, cuando se usa con -H, puede obtener la serie de parches en FETCH_HEAD como si fuera una solicitud de fusión, lista para revisar y fusionar. B4 usa la carta de presentación como plantilla para la confirmación de fusión.

Si quieres invocar automáticamente git-merge, puedes usar -M en lugar de -H. B4 abre automáticamente el editor permitiéndote editar el mensaje de la confirmación de fusión.

Nota: las opciones -M y -H funcionan mejor para series que tengan la información de base-commit que coincida con un objeto en tu árbol local.

Para las opciones y sus descripciones, consulta b4 shazam --help.

Ejemplos

b4 shazam -sl -M [msgid]
Descargar un hilo del servidor public-inbox predeterminado, aplicar cualquier trailer de seguimiento, añadir tu propio trailer Signed-Off-By más un trailer Link: con el origen del parche, y luego fusionar esta confirmación en el repositorio git actual usando la carta de presentación como plantilla para la confirmación de fusión.
b4 shazam -sl -M --merge-base v6.4-rc4 [msgid]
Igual que el ejemplo anterior, pero fuerza que la base de fusión sea el objeto commit-ish proporcionado en lugar del que se lista en la propia serie de parches.

b4 pr

Este comando es para trabajar con solicitudes de fusión enviadas usando git-request-pull. Proporciona los siguientes beneficios en comparación con usar git directamente:

  • puede verificar si la fusión ya está aplicada antes de realizar un git fetch
  • verifica la firma en la etiqueta o la confirmación superior especificada en la solicitud de fusión
  • puede rastrear solicitudes de fusión aplicadas y enviar respuestas a los remitentes usando b4 ty

Para las opciones y sus descripciones, consulta b4 pr --help.

Ejemplos

b4 pr [msgid]
Descargar el mensaje con la solicitud de fusión y aplicarlo al árbol git actual.

b4 ty

Si has recuperado y aplicado algunos parches a tu árbol, deberías poder activar el “auto-agradecedor”, que usa el rastreo de patch-id y el asunto de las confirmaciones para averiguar qué series de las que has recuperado ya has aplicado a tu árbol. El proceso suele ser bastante rápido y bastante preciso.

Para enviar correos directamente usando -S, deberías tener una sección [sendemail] configurada en algún lugar de tus archivos de configuración de git aplicables. De forma predeterminada, b4 ty escribe archivos .thanks en el directorio actual que puedes editar y enviar usando un comando como mutt -f thanks.file.

Para las opciones y sus descripciones, vea b4 ty --help.

Ejemplos

b4 ty -a -S
Localice cualquier serie recuperada que haya aplicado al repositorio git actual y envíe agradecimientos a todos los miembros de la conversación.
b4 ty -a -S --dry-run
Igual que lo anterior, pero en lugar de enviarlo realmente, muestre primero cómo será el mensaje.

b4 diff

El subcomando diff permite comparar dos revisiones diferentes de la misma serie de parches usando git range-diff. Tenga en cuenta que, para realizar la comparación range-diff, ambas revisiones deben aplicarse limpiamente al árbol actual, lo que no siempre es posible de lograr.

Para las opciones y sus descripciones, vea b4 diff --help.

Ejemplos

b4 diff [msgid-of-vN]
Recupera el hilo que coincide con el msgid especificado e intenta localizar automáticamente la versión anterior de la serie. Si tiene éxito, muestra la salida de git range-diff comparando las diferencias de los parches.

b4 kr

Este subcomando permite mantener un llavero local de claves de colaboradores.

Nota: esta parte de b4 está en desarrollo activo con mejoras planificadas para el futuro cercano.

Para las opciones y sus descripciones, vea b4 kr --help.

Ejemplos

b4 kr --show-keys [msgid]
Recupera el hilo especificado y muestra cualquier clave criptográfica utilizada para atestiguar los parches.

b4 prep, trailers, send

Estos comandos permiten preparar y enviar una serie de parches para su revisión en la lista de correo. La documentación completa está disponible en línea en la siguiente dirección:


https://b4.docs.kernel.org/en/latest/contributor/overview.html

Para las opciones, vea la salida de b4 prep --help, b4 trailers --help y b4 send --help.

Ejemplos

b4 prep -n my-new-feature -f v6.4-rc4
Inicie una nueva rama, bifurcándola desde la etiqueta v6.4-rc4, y prepárela para añadir más parches.
b4 prep --edit-cover
Edite la carta de presentación de la serie actual. Este paso no es necesario para la mayoría de los envíos de un solo parche.
b4 prep --auto-to-cc
Encuentre todas las direcciones que necesitan recibir una copia del envío de la serie de parches y añádalas a la carta de presentación.
b4 prep --check
Ejecute las verificaciones configuradas en su serie para identificar cualquier problema potencial. Para el kernel de Linux, esto ejecuta checkpatch.pl con el conjunto de parámetros recomendado.
b4 send -o /tmp/outdir
Genere los parches que b4 va a enviar y guárdelos en el directorio especificado. Esto le permite revisar la serie antes de enviarlos realmente.
b4 send --preview-to [addr1@example.com addr2@example.com]
Envíe una versión de "vista previa" de la serie para que alguien la revise antes de enviarla upstream.
b4 trailers -u
Recupere cualquier trailer de revisión de código proporcionado para su serie y aplíquelos a la rama actual.

CONFIGURACIÓN

La configuración de b4 se maneja mediante git-config(1), por lo que puede almacenarla en el archivo de nivel superior $HOME/.gitconfig o en un archivo .git/config por repositorio si su flujo de trabajo cambia por proyecto.

Para ver las opciones de configuración disponibles, vea la documentación en línea en
https://b4.docs.kernel.org/en/latest/config.html

PROXIMIDAD DE SOLICITUDES

Los comandos que realizan solicitudes HTTP remotas pueden configurarse para usar un proxy estableciendo la variable de entorno HTTPS_PROXY , como se describe en
https://docs.python-requests.org/en/latest/user/advanced/#proxies .
