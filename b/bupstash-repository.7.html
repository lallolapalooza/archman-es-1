La parte más importante de bupstash es el repositorio. Es donde se almacenan todos los datos en una forma mayormente cifrada. El cliente de bupstash interactúa con el repositorio a través de stdin/stdout del proceso bupstash-serve(1). Esto puede ser local, o a través de un protocolo como

ssh.

Debido a que la mayoría de los datos están cifrados, la estructura del repositorio es bastante

simple.

La estructura del árbol de

hash

Bupstash almacena flujos arbitrarios de datos en el repositorio dividiendo el flujo en fragmentos, direccionando los fragmentos con hmac, luego comprimiendo y cifrando los fragmentos con la porción de clave pública de una clave de bupstash. Cada fragmento se almacena entonces en el directorio de datos en un archivo nombrado según el hash hmac de los contenidos. A medida que generamos una secuencia de fragmentos con direcciones hmac correspondientes, podemos construir una estructura de árbol a partir de estas direcciones. Los nodos hoja del árbol son simplemente los datos cifrados. Otros nodos en el árbol son simplemente listas sin cifrar de hashes hmac, que pueden apuntar a nodos hoja cifrados u otros subárboles. La idea clave detrás del árbol de hash es que podemos convertir un flujo arbitrario de datos en una única dirección HMAC con fragmentos de tamaño aproximadamente igual. Cuando se añaden múltiples árboles de hash al repositorio, comparten estructura y permiten la

deduplicación.

Este esquema de direccionamiento y cifrado tiene algunas propiedades

importantes:
○
El propietario del repositorio no puede adivinar el contenido de los fragmentos ya que la clave HMAC es desconocida para
él.
○
El propietario del repositorio no puede descifrar las hojas del árbol de hash, ya que están
cifradas.
○
El propietario del repositorio puede iterar el árbol de hash para la recolección de
basura.
○
El propietario del repositorio puede ejecutar la recolección de basura sin recuperar los nodos hoja del almacenamiento en
frío.
○
El propietario del repositorio puede transmitir un flujo de nodos del árbol de hash a un cliente sin idas y vueltas de
red.
○
Un cliente puede enviar flujos de datos a un repositorio sin compartir la clave de
cifrado.
○
Un cliente puede recuperar y verificar un flujo de datos verificando los
hmacs.

Estas propiedades son deseables para permitir una reco

lección de basura de alto rendimiento y transmisió
n de datos con pre-carga en el lado del repositorio.

División y

deduplicación

Los datos se deduplican dividiendo un flujo de datos en pequeños fragmentos, y nunca almacenando el mismo fragmento dos veces. El rendimiento de esta deduplicación se determina así por cómo se definen los puntos de división de los fragmentos. Para lectores curiosos: bupstash usa algo conocido como 'fragmentación de

finida por contenido' para encontrar
divisiones de fragmentos eficientes.

Formatos de

fragmentos

Los fragmentos en la base de datos son de uno de los siguientes tipos; en general, conocemos el tipo de un fragmento basándonos en los metadatos del elemento y la altura del árbol de

hash.

Fragmento de datos

cifrados

Estos fragmentos forman las raíces de nuestros árboles de hash; contienen datos cifrados. Contienen un paquete de intercambio de claves, con suficiente información para que la clave maestra derive la clave de

sesión.

KEY_EXCHANGE_PACKET1_BYTES[PACKET1_SZ] || ENCRYPTED_BYTES[...

]

Después de la descifrado, el fragmento se comprime opcionalmente, por lo que son datos comprimidos, o datos con un byte de pie

nulo.

COMPRESSED_DATA[...] || DECOMPRESSED_SIZE[4] || COMPRESSION_TYPE[1

]

o

DATA[...] ||

0x00

Los tipos de compresión válidos

son:
○
1 == compresión
lz4.
○
2 == compresión
zstd.

hash

Estos fragmentos forman nodos no hoja en nuestro árbol de hash; consisten en una lista de direcciones precedida por el número total de fragmentos de datos que se encuentran debajo de ellas en el

árbol.

NUM_DATA_CHUNKS[8] ADDRESS[ADDRESS_SZ] NUM_DATA_CHUNKS[8] ADDRESS[ADDRESS_SZ] NUM_DATA_CHUNKS[8] ADDRESS[ADDRESS_SZ] NUM_DATA_CHUNKS[8] ADDRESS[ADDRESS_SZ] ..
