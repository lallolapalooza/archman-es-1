El subsistema de Berkeley Packet Filter extendido (eBPF) consiste en programas escritos en un lenguaje de pseudo-ensamblador, que luego se adjuntan a uno de los varios ganchos del kernel y se ejecutan en reacción a eventos específicos. Este framework difiere del BPF "clásico" más antiguo (o "cBPF") en varios aspectos, uno de ellos siendo la capacidad de llamar funciones especiales (o "helpers") desde dentro de un programa. Estas funciones están restringidas a una lista blanca de helpers definidos en el

kernel.

Estos helpers son usados por los programas eBPF para interactuar con el sistema, o con el contexto en el que trabajan. Por ejemplo, pueden ser usados para imprimir mensajes de depuración, para obtener el tiempo transcurrido desde que el sistema fue arrancado, para interactuar con mapas eBPF, o para manipular paquetes de red. Dado que hay varios tipos de programas eBPF, y que no se ejecutan en el mismo contexto, cada tipo de programa solo puede llamar a un subconjunto de estos

helpers.

Debido a las convenciones de eBPF, un helper no puede tener más de cinco

argumentos.

Internamente, los programas eBPF llaman directamente a las funciones auxiliares compiladas sin requerir ninguna interfaz de funciones externas. Como resultado, llamar a los helpers no introduce ninguna sobrecarga, ofreciendo así un excelente

rendimiento.

Este documento es un intento de listar y documentar los helpers disp

onibles para los desarrolladores de eBPF. Están ordenados cronológic
amente (los helpers más antiguos en el kernel en la parte superior).

long bpf_tail_call(void *ctx, struct bpf_map *prog_array_map, u32 index)
Descripción
Esta función auxiliar especial se utiliza para activar una "llamada de cola" (tail call), o en otras palabras, para saltar a otro programa eBPF. Se utiliza el mismo marco de pila (pero los valores en la pila y en los registros del llamador no son accesibles para el llamado). Este mecanismo permite la encadenación de programas, ya sea para aumentar el número máximo de instrucciones eBPF disponibles, o para ejecutar programas dados en bloques condicionales. Por razones de seguridad, existe un límite superior en el número de llamadas de cola sucesivas que se pueden realizar.

Al llamar a esta función auxiliar, el programa intenta saltar a un programa referenciado en el índice index en prog_array_map, un mapa especial de tipo BPF_MAP_TYPE_PROG_ARRAY, y pasa ctx, un puntero al contexto.

Si la llamada tiene éxito, el kernel ejecuta inmediatamente la primera instrucción del nuevo programa. Esto no es una llamada a función y nunca regresa al programa anterior. Si la llamada falla, la función auxiliar no tiene ningún efecto y el llamador continúa ejecutando sus instrucciones subsiguientes. Una llamada puede fallar si el programa de destino para el salto no existe (es decir, index es superior al número de entradas en prog_array_map), o si se ha alcanzado el número máximo de llamadas de cola para esta cadena de programas. Este límite se define en el kernel mediante la macro MAX_TAIL_CALL_CNT (no accesible al espacio de usuario), que actualmente está establecido en 33.

Retorno
0 en caso de éxito, o un error negativo en caso de fallo.

Descripción

u32 bpf_clone_redirect(struct sk_buff *skb, u32 ifindex, u64 flags)
Description
Clone the packet and redirect it to another net device of index ifindex. The original packet is not freed, so the caller must explicitly free it using bpf_clone_redirect() if it is not consumed.

Except for XDP, both ingress and egress interfaces can be used for redirection. Currently, XDP only supports redirection to the egress interface, and accepts no flag at all.

Descripción
Lee el valor de un contador de eventos de rendimiento y lo almacena en buf de tamaño buf_size. Esta ayuda se basa en un map de tipo BPF_MAP_TYPE_PERF_EVENT_ARRAY. La naturaleza del contador de eventos de rendimiento se selecciona cuando se actualiza map con descriptores de archivo de eventos de rendimiento. El map es un array cuyo tamaño es el número de CPUs disponibles, y cada celda contiene un valor relativo a una CPU. El valor a recuperar se indica mediante flags, que contiene el índice de la CPU a buscar, enmascarado con BPF_F_INDEX_MASK. Alternativamente, flags se puede establecer en BPF_F_CURRENT_CPU para indicar que se debe recuperar el valor de la CPU actual.

Esta ayuda se comporta de manera similar a la ayuda bpf_perf_event_read(), excepto que en lugar de simplemente devolver el valor observado, rellena la estructura buf. Esto permite recuperar datos adicionales: en particular, se copian los tiempos de activación y ejecución (en buf->enabled y buf->running, respectivamente). En general, se recomienda bpf_perf_event_read_value() sobre bpf_perf_event_read(), que tiene algunos problemas de ABI y ofrece menos funcionalidades.

Estos valores son interesantes, porque los contadores de PMU (Unidad de Medición de Rendimiento) de hardware son recursos limitados. Cuando hay más eventos de rendimiento basados en PMU abiertos que contadores disponibles, el kernel multiplexará estos eventos para que cada evento reciba un cierto porcentaje (pero no todos) del tiempo de PMU. En caso de que ocurra la multiplexación, el número de muestras o el valor del contador no reflejarán la situación en comparación con cuando no ocurre ninguna multiplexación. Esto dificulta la comparación entre diferentes ejecuciones. Típicamente, el valor del contador debe normalizarse antes de compararlo con otros experimentos. La normalización habitual se realiza de la siguiente manera.

contador_normalizado = contador * t_activado / t_ejecucion

Donde t_activado es el tiempo de activación del evento y t_ejecucion es el tiempo de ejecución del evento desde la última normalización. Los tiempos de activación y ejecución se acumulan desde la apertura del evento de rendimiento. Para lograr un factor de escala entre dos invocaciones de un programa eBPF, los usuarios pueden usar el id de CPU como clave (lo cual es típico para el modelo de uso de array de rendimiento) para recordar el valor anterior y realizar el cálculo dentro del programa eBPF.
