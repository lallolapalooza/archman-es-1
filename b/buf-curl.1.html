DESCRIPCIÓ

N

Este comando le ayuda a invocar puntos finales RPC HTTP en un servidor que usa gRPC o

Connect.

Por defecto, se usa la reflexión del servidor, a menos que la bandera --reflect esté establecida en false. Sin la reflexión del servidor, se debe proporcionar una bandera --schema para indicar el esquema Protobuf del método que se está

invocando.

El único argumento posicional es la URL del método RPC a invocar. El nombre del método a invocar proviene de los dos últimos componentes de la URL, que deben ser el nombre del servicio completamente calificado y el nombre del método, respectivamente

.

La URL puede usar http o https como esquema. Si se usa http se usará HTTP 1.1 a menos que la bandera --http2-prior-knowledge esté establecida. Si se usa https, se preferirá HTTP/2 durante la negociación del protocolo y se usará HTTP 1.1 solo si el servidor no soporta

HTTP/2.

El protocolo RPC predeterminado que se usará será Connect. Para usar un protocolo diferente (gRPC o gRPC-Web), use la bandera --protocol. Tenga en cuenta que el protocolo gRPC no se puede usar con HTTP 1.

1.

La solicitud de entrada se especifica mediante la bandera -d o --data. Si está ausente, se envía una solicitud vacía. Si el valor de la bandera comienza con un signo de arroba (@), el resto del valor de la bandera se interpreta como un nombre de archivo del cual leer el cuerpo de la solicitud. Si ese nombre de archivo es solo un guion (-), entonces el cuerpo de la solicitud se lee de stdin. El cuerpo de la solicitud es un documento JSON que contiene el mensaje de solicitud formateado en JSON. Si el método RPC que se está invocando es un método de streaming del lado del cliente, el cuerpo de la solicitud puede consistir en múltiples valores JSON, uno tras otro. Los múltiples documentos JSON generalmente deben separarse por espacios en blanco, aunque esto no es estrictamente requerido a menos que el tipo de mensaje de solicitud tenga una representación JSON personalizada que no sea un objeto

JSON.

Los metadatos de la solicitud (es decir, encabezados) se definen usando las banderas -H o --header . El valor de la bandera está en formato "nombre: valor". Pero si comienza con un signo de arroba (@), el resto del valor se interpreta como un nombre de archivo del cual se leen los encabezados, cada uno en una línea separada. Si el nombre de archivo es solo un guion (-), entonces los encabezados se leen de

stdin.

Si tanto los encabezados como el cuerpo de la solicitud deben leerse del mismo archivo (o ambos leídos de stdin), el archivo debe incluir primero los encabezados, luego una línea en blanco, y luego el cuerpo de la

solicitud.

Ejemplos

:

Emitir un RPC unario a un servidor gRPC de texto plano (es decir, "h2c"), donde el esquema del servicio está en un módulo Buf en el directorio actual, usando un mensaje de solicitud

vacío: 
$ buf curl --schema . --protocol grpc --http2-prior-knowledge  \
     http://localhost:20202/foo.bar.v1.FooService/DoSomethin
g

Emitir un RPC a un servidor Connect, donde el esquema proviene del Buf Schema Registry, usando una solicitud que se define como un argumento de línea de

comandos: 
$ buf curl --schema buf.build/connectrpc/eliza  \
     --data '{"name": "Bob Loblaw"}'          \
     https://demo.connectrpc.com/connectrpc.eliza.v1.ElizaService/Introduc
e

Emitir un RPC unario a un servidor que soporta reflexión, con salida

detallada: 
$ buf curl --data '{"sentence": "I am not feeling well."}' -v  \
	 https://demo.connectrpc.com/connectrpc.eliza.v1.ElizaService/Sa
y

Emitir un RPC de streaming del lado del cliente a un servidor gRPC-web que soporta reflexión, donde los encabezados personalizados y los datos de la solicitud están ambos en un

heredoc: 
$ buf curl --data @- --header @- --protocol grpcweb                              \
	 https://demo.connectrpc.com/connectrpc.eliza.v1.ElizaService/Converse  \
   <<EOM
Custom-Header-1: foo-bar-baz
Authorization: token jas8374hgnkvje9wpkerebncjqol4
{"sentence": "Hi, doc. I feel hungry."}
{"sentence": "What is the answer to life, the universe, and everything?"}
{"sentence": "If you were a fish, what of fish would you be?."}
EOM

Tenga en cuenta que la reflexión del servidor (es decir, el uso de la bandera --reflect) no funciona con HTTP 1.1 ya que el protocolo depende del streaming bidireccional. Si se usa la reflexión del servidor, la URL asumida para el servicio de reflexión es la misma que la URL dada, pero con los dos últimos elementos eliminados y reemplazados con el nombre del servicio y el método para la reflexión del

servidor.

Si ocurre un error debido a un uso incorrecto u otro error inesperado, este programa devol

verá un código de salida que es menor que 8. Si el RPC falla de otra manera, este programa
devolverá un código de salida que es el código gRPC, desplazado tres bits a la izquierda.

HTTP/3.

--reflect-header=[] Cabeceras de solicitud a incluir con las solicitudes de reflexión. Esta bandera solo se puede usar cuando --reflect también está establecido. Esta bandera se puede especificar más de una vez para indicar múltiples cabeceras. Cada valor de bandera debe tener la forma "nombre: valor". Pero se puede usar un valor especial de '*' para indicar que todas las cabeceras de solicitud normales (de las banderas --header y -H) también deben incluirse con las solicitudes de reflexión. Un valor especial de '@' significa leer cabeceras del archivo en . Si la ruta es "-" entonces las cabeceras se leen de stdin. No está permitido indicar un archivo con la misma ruta que la usada con la bandera de datos de la solicitud (--data o -d). imagen

--reflect-protocol="" El protocolo de reflexión a usar para descargar información del servidor. Esta bandera solo se puede usar cuando se usa la reflexión del servidor. Por defecto, este comando probará todos los protocolos de reflexión conocidos desde el más nuevo hasta el más antiguo. Si esto resulta en un error "Not Implemented", se usarán protocolos más antiguos. En la práctica, esto significa que "grpc-v1" se prueba primero, y "grpc-v1alpha" se usa si no funciona. Si se introducen protocolos de reflexión más nuevos, pueden preferirse en ausencia de esta bandera establecida explícitamente a un protocolo específico. Los valores válidos para esta bandera son "grpc-v1" y "grpc-v1alpha". Estos corresponden a los servicios nombrados "grpc.reflection.v1.ServerReflection" y "grpc.reflection.v1alpha.ServerReflection"

respectivamente

--schema=[] El módulo a usar para el esquema RPC. Esto es necesario si el servidor no soporta reflexión del servidor. El formato de este argumento es el mismo que para los argumentos de otros subcomandos de buf como build y generate. Puede indicar un directorio, un archivo, un módulo remoto en el Buf Schema Registry, o incluso stdin ("-") para alimentar una imagen o un conjunto de descriptores de archivo al comando en una tubería de shell. Si están presentes múltiples banderas de esquema, se consultarán en orden para resolver nombres de servicios y tipos. Establecer esta bandera implica --reflect=false a menos que una bandera de reflexión esté explícitamente presente. Si tanto las banderas de esquema como las de reflexión están en uso, se usará la reflexión primero y luego se consultarán los esquemas en orden si la reflexión falla en resolver un elemento del

esquema.

--servername="" El nombre del servidor a usar en los apretones de manos TLS (para SNI) si el esquema de la URL es https. Si no se especifica, el valor por defecto es el host de origen en la URL o el valor en una cabecera "Host" si se proporciona

una

--unix-socket="" La ruta a un socket unix que se usará en lugar de abrir un socket TCP al host y puerto indicados en la

URL

-u, --user="" Las credenciales de usuario a enviar, mediante una cabecera de autorización básica. El valor debe estar en el formato "nombre de usuario:contraseña". Si el valor no tiene dos puntos, se asume que es solo el nombre de usuario, en cuyo caso se le pedirá que ingrese una contraseña. Esto anula el uso de un archivo .netrc. Esto se ignora si se proporciona una bandera --header o -H que establece una cabecera llamada 'Authorization'

.

-A, --user-agent="" La cadena de agente de usuario a enviar. Esto se ignora si se proporciona una bandera --header o -H que establece una cabecera llamada
