CLAVES DE

CONFIGURACIÓN

Las claves de configuración en bundler tienen dos formas: la forma canónica y la forma de variable

de

entorno. Por ejemplo, pasar la opción --without a bundle install(1) bundle-install.1.html evita que Bundler instale ciertos grupos especificados en el Gemfile(5). Bundler persiste este valor en app/. bundle/config para que las llamadas a Bundler.setup no intenten encontrar gems del Gemfile que no instaló. Además, las llamadas posteriores a bundle install(1) bundle-install. 1.html recuerdan este ajuste y omiten esos grupos. La forma

canónica

de esta configuración es "without". Para convertir la forma canónica a la forma de variable de entorno, póngala en mayúsculas y anteponga BUNDLE_. La forma de variable de entorno de "without" es BUNDLE_WITHOUT. Cualquier

punto

en las claves de configuración debe reemplazarse con dos guiones bajos al establecerla mediante variables de entorno. La clave de configuración local.rack se convierte en la variable de entorno BUNDLE_LOCAL__RAC

RECORDAR

OPCIONES

Los indicadores pasados a bundle install o al entorno de ejecución de Bundler, como --path foo o --without production, se recuerdan entre comandos y se guardan en la configuración de tu aplicación local (normalmente, ./.bundle/co

nfig).

Sin embargo, esto cambiará en bundler 4, así que es mejor no depender de este comportamiento. Si estas opciones deben recordarse, es mejor establecerlas usando bundle config (por ejemplo, bundle config set --local path foo)

.

Los indicadores que se pueden configurar

son:
--b
in
Crea un directorio (por defecto ~/bin) y coloca allí los ejecutables de la gema. Estos ejecutables se ejecutan en el contexto de Bundler. Si se usa, es posible que desees añadir este directorio a la variable PATH de tu entorno. Por ejemplo, si la gema rails viene con un ejecutable rails, este indicador creará un ejecutable bin/rails que asegura que todas las dependencias referenciadas se resolverán usando las gemas del
bundle.
--deployme
nt
En modo de despliegue, Bundler 'desplegará' el bundle para su uso en producción. Por favor, comprueba cuidadosamente si quieres tener esta opción habilitada en los entornos de desarrollo o test
.
--on
ly
Una lista de grupos separada por espacios para instalar solo las gemas de los grupos especificados. Por favor, comprueba cuidadosamente si también quieres instalar gemas sin grupo, ya que se colocan dentro del grupo defaultp. Por ejemplo solo test:default instalará todas las gemas especificadas en el grupo test y sin
una.
--pa
th
La ubicación donde instalar las gemas especificadas. Por defecto es la configuración de Rubygems. Bundler comparte esta ubicación con Rubygems, gem install ... también instalará la gema ahí. Por lo tanto, las gemas instaladas sin una configuración de --path ... aparecerán al llamar a gem list. En consecuencia, las gemas instaladas en otras ubicaciones no se
listarán.
--witho
ut
Una lista separada por espacios o separada por : de grupos que referencian gemas a omitir durante la
instalación.
--wi
th
Una lista separada por espacios o separada por : de grupos opcionales que refe
rencian gemas a
incluir durante

CONSTRUCCIÓN

Puedes usar bundle config para darle a Bundler los indicadores a pasar al instalador de gemas cada vez que bundler intente instalar una gema

particular.

Un ejemplo muy común, la gema mysql, requiere que los usuarios de Snow Leopard pasen indicadores de configuración a gem install para especificar dónde encontrar el ejecutable mysql

_config. 
gem install mysql -- --with-mysql-config=/usr/local/mysql/bin/mysql_

Dado que la ubicación específica de ese ejecutable puede cambiar de una máquina a otra, puedes especificar estos indicadores de forma individual para cada

máquina. 
bundle config set --global build.mysql --with-mysql-config=/usr/local/mysql/bin/mysql_
con
fig

Después de ejecutar este comando, cada vez que bundler necesite instalar la gema mysql, pasará los ind

icadores que e
specificaste.

REPOSITORIOS GIT

LOCALES

Bundler también te permite trabajar contra un repositorio git local en lugar de usar la versión remota. Esto se puede lograr configurando una anulación

local: 
bundle config set --local local.NOMBRE_GEMA /ruta/al/repositorio/git
/lo
cal

Por ejemplo, para usar un repositorio Rack local, un desarrollador podría

llamar: 
bundle config set
--local local.rac
k ~/Work/git/rack

Ahora, en lugar de hacer checkout del repositorio git remoto, se usará la anulación local. Similar a una fuente de ruta, cada vez que el repositorio git local cambie, Bundler recogerá automáticamente los cambios. Esto significa que un commit en el repositorio git local actualizará la revisión en el Gemfile.lock a la revisión del repositorio git local. Esto requiere la misma atención que los submódulos de git. Antes de hacer push al remoto, debes asegurarte de que la anulación local haya sido subida, de lo contrario podrías apuntar a un commit que solo existe en tu máquina local. También necesitarás escapar con CGI tus nombres de usuario y

contraseñas.

Bundler realiza muchas verificaciones para asegurar que un desarrollador no trabaje con referencias inválidas. En particular, forzamos a un desarrollador a especificar una rama en el Gemfile para usar esta función. Si la rama especificada en el Gemfile y la rama actual en el repositorio git local no coinciden, Bundler abortará. Esto asegura que un desarrollador siempre esté trabajando contra las ramas correctas, y previene el bloqueo accidental a una rama

diferente.

Finalmente, Bundler también asegura que la revisión actual en el Gemfile.lock exista en el repositorio git local. Al hacer esto,

Bundler te obliga a obtener lo
s últimos cambios en los remotos.

ESPEJOS DE FUENTES DE

GEMAS

Bundler soporta anular fuentes de gemas con espejos. Esto te permite configurar rubygems.org como la fuente de gemas en tu Gemfile mientras aún usas tu espejo para obtener las

gemas. 
bundle config set
--global mirror.URL
_FUENTE URL_ESPEJO

Por ejemplo, para usar un espejo de https://rubygems.org alojado en https://examp

le.org: 
bundle config set --globa
l mirror.https://rubygem
s.org https://example.org

Cada espejo también proporciona una configuración de tiempo de espera de respaldo. Si el espejo no responde dentro del tiempo de espera de respaldo, Bundler intentará usar el servidor original en lugar del

espejo. 
bundle config set --glo
bal mirror.URL_FUENTE.
fallback_timeout TIEMPO

Por ejemplo, para volver a rubygems.org después de 3

segundos: 
bundle config set --glob
al mirror.https://rubygem
s.org.fallback_timeout 3

El tiempo de espera de respaldo predeterminado es 0.1 se

gundos, pero la configuración actualmente solo puede
aceptar segundos enteros (por ejemplo, 1, 15 o 30).

CREDENCIALES PARA FUENTES DE

GEMAS

Bundler te permite configurar credenciales para cualquier fuente de gemas, lo que te permite evitar poner secretos en tu

Gemfile. 
bundle config set --g

así: 
bundle config set --global ht
tps://github.com/rubygems/ru
bygems.git usuario:contraseña

O puedes establecer las credenciales como una variable de entorno

así: 
export BUNDLE_G
ITHUB__COM=usu

Esto es especialmente útil para repositorios privados en hosts como GitHub, donde puedes usar tokens OAuth

Ten en cuenta que cualquier credencial configurada será redactada por comandos informativos como bundle config list o bundle config get, a menos que uses el indicador --parseable. Esto es para evitar filtrar credenciales involuntariamente al copiar y pegar la salida de

bundler.

Ten en cuenta también que para garantizar una correspondencia adecuada entre nombres de variables de entorno válidos y nombres de host válidos, bundler realiza las siguientes transformaciones

:
  • Cualquier carácter - en un nombre de host se mapea a un triple subrayado (___) en la variable de entorno
    • correspondiente.
  • Cualquier carácter . en un nombre de host se mapea a un doble subrayado (__) en la variable de entorno
    • correspondiente
.

Esto significa que si tienes un servidor de gemas llamado my.gem-host.com, necesitarás usar la variable BUNDLE_MY__GEM___HOST__COM para confi

gurar credenciales para
él a través de ENV.
