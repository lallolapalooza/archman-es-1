NOMBRE

bootparam - introducción a los parámetros de tiempo de arranque del kernel de Linux

DESCRIPCIÓN

El kernel de Linux acepta ciertas 'opciones de línea de comandos' o 'parámetros de tiempo de arranque' en el momento en que se inicia. En general, esto se utiliza para proporcionar al kernel información sobre parámetros de hardware que el kernel no podría determinar por sí mismo, o para evitar/sobrescribir los valores que el kernel detectaría de otra manera.

Cuando el kernel es arrancado directamente por el BIOS, no tienes la oportunidad de especificar ningún parámetro. Por lo tanto, para aprovechar esta posibilidad, tienes que usar un cargador de arranque que sea capaz de pasar parámetros, como GRUB.

La lista de argumentos

La línea de comandos del kernel se analiza en una lista de cadenas (argumentos de arranque) separadas por espacios. La mayoría de los argumentos de arranque tienen la forma:


nombre[=valor_1][,valor_2]...[,valor_10]

donde 'nombre' es una palabra clave única que se utiliza para identificar a qué parte del kernel se le deben dar los valores asociados (si los hay). Ten en cuenta que el límite de 10 es real, ya que el código actual solo maneja 10 parámetros separados por comas por palabra clave. (Sin embargo, puedes reutilizar la misma palabra clave con hasta 10 parámetros adicionales en situaciones inusualmente complicadas, asumiendo que la función de configuración lo soporta.)

La mayor parte del análisis está codificada en el archivo fuente del kernel init/main.c. Primero, el kernel comprueba si el argumento es alguno de los argumentos especiales 'root=', 'nfsroot=', 'nfsaddrs=', 'ro', 'rw', 'debug' o 'init'. El significado de estos argumentos especiales se describe a continuación.

Luego recorre una lista de funciones de configuración para ver si la cadena de argumentos especificada (como 'foo') ha sido asociada con una función de configuración ('foo_setup()') para un dispositivo o parte específica del kernel. Si pasaste al kernel la línea foo=3,4,5,6, entonces el kernel buscaría en el array bootsetups para ver si 'foo' estaba registrado. Si lo estaba, entonces llamaría a la función de configuración asociada con 'foo' (foo_setup()) y le entregaría los argumentos 3, 4, 5 y 6 tal como se dieron en la línea de comandos del kernel.

Cualquier cosa de la forma 'foo=bar' que no sea aceptada como una función de configuración como se describió anteriormente, se interpreta entonces como una variable de entorno a establecer. Un ejemplo (¿inútil?) sería usar 'TERM=vt100' como argumento de arranque.

Cualquier argumento restante que no haya sido recogido por el kernel y que no haya sido interpretado como variable de entorno, se pasa luego al PID 1, que es usualmente el programa init(1) . El argumento más común que se pasa al proceso init es la palabra 'single', que le instruye arrancar el ordenador en modo de usuario único, y no lanzar todos los demonios habituales. Consulta la página manual para la versión de init(1) instalada en tu sistema para ver qué argumentos acepta.

Argumentos de arranque generales no específicos de dispositivos

'init=...'
Esto establece el comando inicial que será ejecutado por el kernel. Si esto no está establecido, o no se puede encontrar, el kernel intentará /sbin/init, luego /etc/init, luego /bin/init, luego /bin/sh y entrará en pánico si todo esto falla.
'nfsaddrs=...'
Esto establece la dirección de arranque NFS a la cadena dada. Esta dirección de arranque se usa en caso de un arranque por red.
'nfsroot=...'
Esto establece el nombre de la raíz NFS a la cadena dada. Si esta cadena no comienza con '/' o ',' o un dígito, se le antepone '/tftpboot/'. Este nombre de raíz se usa en caso de un arranque por red.
'root=...'
Este argumento le dice al kernel qué dispositivo debe usarse como el sistema de archivos raíz mientras arranca. El valor predeterminado de esta configuración se determina en tiempo de compilación, y usualmente es el valor del dispositivo raíz del sistema en el que se compiló el kernel. Para sobrescribir este valor y seleccionar la segunda unidad de disquete como dispositivo raíz, se usaría 'root=/dev/fd1'.
El dispositivo raíz puede especificarse simbólicamente o numéricamente. Una especificación simbólica tiene la forma /dev/XXYN, donde XX designa el tipo de dispositivo (por ejemplo, 'hd' para disco duro compatible con ST-506, con Y en 'a'–'d'; 'sd' para disco compatible con SCSI, con Y en 'a'–'e'), Y la letra o número del controlador, y N el número (en decimal) de la partición en este dispositivo.
Ten en cuenta que esto no tiene nada que ver con la designación de estos dispositivos en tu sistema de archivos. La parte '/dev/' es puramente convencional.
También se acepta la especificación numérica, más engorrosa y menos portable, de los posibles dispositivos raíz anteriores en formato mayor/menor. (Por ejemplo, /dev/sda3 es mayor 8, menor 3, así que podrías usar 'root=0x803' como alternativa.)
'rootdelay='
Este parámetro establece el retraso (en segundos) para pausar antes de intentar montar el sistema de archivos raíz.
'rootflags=...'
Este parámetro establece la cadena de opciones de montaje para el sistema de archivos raíz (véase también fstab(5)).
'rootfstype=...'
La opción 'rootfstype' le dice al kernel que monte el sistema de archivos raíz como si fuera del tipo especificado. Esto puede ser útil (por ejemplo) para montar un sistema de archivos ext3 como ext2 y luego eliminar el diario en el sistema de archivos raíz, revirtiendo de hecho su formato de ext3 a ext2 sin necesidad de arrancar el equipo desde medios alternativos.
'ro'
'rw'
La opción 'ro' le dice al kernel que monte el sistema de archivos raíz como 'solo lectura' para que los programas de verificación de consistencia del sistema de archivos (fsck) puedan hacer su trabajo en un sistema de archivos en reposo. Ningún proceso puede escribir en archivos en el sistema de archivos en cuestión hasta que sea 'remontado' como capaz de lectura/escritura, por ejemplo, con 'mount -w -n -o remount /'. (Véase también mount(8).)
La opción 'rw' le dice al kernel que monte el sistema de archivos raíz en lectura/escritura. Este es el valor predeterminado.
'resume=...'
Esto le dice al kernel la ubicación de los datos de suspensión a disco desde la que quieres que la máquina se reanude después de la hibernación. Usualmente, es la misma que tu partición o archivo de intercambio. Ejemplo:

resume=/dev/hda2

'reserve=...'
Esto se usa para proteger regiones de puertos E/S de las sondeas. La forma del comando es:

reserve=iobase,extensión[,iobase,extensión]...

En algunas máquinas puede ser necesario evitar que los controladores de dispositivos busquen dispositivos (sondeo automático) en una región específica. Esto puede deberse a hardware que reacciona mal al sondeo, o hardware que sería identificado erróneamente, o simplemente hardware que no quieres que el kernel inicialice.
El argumento de arranque reserve especifica una región de puerto E/S que no debe ser sondeada. Un controlador de dispositivos no sondeará una región reservada, a menos que otro argumento de arranque especifique explícitamente que lo haga.
Por ejemplo, la línea de arranque

reserve=0x300,32  blah=0x300

impide que todos los controladores de dispositivos excepto el controlador de 'blah' sonden 0x300-0x31f.
'panic=N'
Por defecto, el kernel no se reiniciará después de un pánico, pero esta opción hará que el kernel se reinicie después de N segundos (si N es mayor que cero). Este tiempo de espera de pánico también se puede establecer con

echo N > /proc/sys/kernel/panic

'reboot=[warm|cold][,[bios|hard]]'
Desde Linux 2.0.22, un reinicio es por defecto un reinicio en frío. Se pide el antiguo valor predeterminado con 'reboot=warm'. (Un reinicio en frío puede ser necesario para restablecer cierto hardware, pero podría destruir datos aún no escritos en una caché de disco. Un reinicio en caliente puede ser más rápido.) Por defecto, un reinicioes difícil, al pedirle al controlador del teclado que haga pulsar la línea de reinicio hacia abajo, pero hay al menos un tipo de placa base en el que eso no funciona. La opción 'reboot=bios' saltará en su lugar a través del BIOS.
'nosmp'
'maxcpus=N'
(Solo cuando __SMP__ está definido.) Una opción de línea de comandos 'nosmp' o 'maxcpus=0' desactivará la activación de SMP por completo; una opción 'maxcpus=N' limita el número máximo de CPUs activadas en modo SMP a N.

Argumentos de arranque para uso de los desarrolladores del núcleo

'debug'
Los mensajes del núcleo se pasan a un demonio (por ejemplo, klogd(8) o similar) para que puedan registrarse en disco. Los mensajes con una prioridad superior a console_loglevel también se imprimen en la consola. (Para una discusión sobre los niveles de registro, ver syslog(2).) De forma predeterminada, console_loglevel está configurado para registrar mensajes en niveles superiores a KERN_DEBUG. Este argumento de arranque hará que el núcleo también imprima mensajes registrados en el nivel KERN_DEBUG. El nivel de registro de la consola también puede establecerse en un sistema ya arrancado a través del archivo /proc/sys/kernel/printk (descrito en syslog(2)), la operación syslog(2) SYSLOG_ACTION_CONSOLE_LEVEL , o dmesg(8).
'profile=N'
Es posible habilitar una función de perfilado del núcleo, si se desea averiguar dónde está el núcleo gastando sus ciclos de CPU. El perfilado se habilita estableciendo la variable prof_shift en un valor distinto de cero. Esto se hace ya sea especificando CONFIG_PROFILE en tiempo de compilación, o dando la opción 'profile='. Ahora el valor que prof_shift obtendrá será N, cuando se indique, o CONFIG_PROFILE_SHIFT, cuando ese se indique, o 2, el valor predeterminado. La importancia de esta variable es que da la granularidad del perfilado: en cada tic de reloj, si el sistema estaba ejecutando código del núcleo, se incrementa un contador:

profile[address >> prof_shift]++;

La información de perfilado en bruto se puede leer desde /proc/profile. Probablemente querrás usar una herramienta como readprofile.c para procesarla. Escribir en /proc/profile borrará los contadores.

Argumentos de arranque para uso de ramdisk

(Solo si el núcleo fue compilado con CONFIG_BLK_DEV_RAM.) En general, es una mala idea usar un ramdisk bajo Linux; el sistema usará la memoria disponible de manera más eficiente por sí mismo. Pero mientras se arranca, a menudo es útil cargar el contenido del disquete en un ramdisk. También se podría tener un sistema en el que primero algunos módulos (para el sistema de archivos o el hardware) deban cargarse antes de que se pueda acceder al disco principal.

En Linux 1.3.48, el manejo de los ramdisks cambió drásticamente. Anteriormente, la memoria se asignaba estáticamente, y había un parámetro 'ramdisk=N' para indicar su tamaño. (Esto también podía establecerse en la imagen del núcleo en tiempo de compilación.) Hoy en día, los discos RAM usan la caché de búferes y crecen dinámicamente. Para mucha información sobre la configuración actual de los ramdisks, ver el archivo de código fuente del núcleo Documentation/blockdev/ramdisk.txt (Documentation/ramdisk.txt en núcleos más antiguos).
Hay cuatro parámetros, dos booleanos y dos enteros.
'load_ramdisk=N'
Si N=1, carga un ramdisk. Si N=0, no carga un ramdisk. (Este es el valor predeterminado.)
'prompt_ramdisk=N'
Si N=1, solicita la inserción del disquete. (Este es el valor predeterminado.) Si N=0, no solicita nada. (Por lo tanto, este parámetro nunca es necesario.)
'ramdisk_size=N' u (obsoleto) 'ramdisk=N'
Establece el tamaño máximo del(los) ramdisk(s) a N kB. El valor predeterminado es 4096 (4 MB).
'ramdisk_start=N'
Establece el número de bloque de inicio (el desplazamiento en el disquete donde el ramdisk comienza) a N. Esto es necesario en caso de que el ramdisk siga a una imagen del núcleo.
'noinitrd'
(Solo si el núcleo fue compilado con CONFIG_BLK_DEV_RAM y CONFIG_BLK_DEV_INITRD.) Hoy en día es posible compilar el núcleo para usar initrd. Cuando esta función está habilitada, el proceso de arranque cargará el núcleo y un disco RAM inicial; luego el núcleo convierte initrd en un ramdisk "normal", que se monta de lectura-escritura como dispositivo raíz; luego se ejecuta /linuxrc ; después, el sistema de archivos raíz "real" se monta, y el sistema de archivos initrd se mueve a /initrd; finalmente, se realiza la secuencia de arranque habitual (por ejemplo, la invocación de /sbin/init).
Para una descripción detallada de la función initrd, ver el archivo de código fuente del núcleo Documentation/admin-guide/initrd.rst (o Documentation/initrd.txt antes de Linux 4.10).
La opción 'noinitrd' le indica al núcleo que, aunque fue compilado para operar con initrd, no debe pasar por los pasos anteriores, sino dejar los datos de initrd bajo /dev/initrd. (Este dispositivo solo puede usarse una vez: los datos se liberan tan pronto como el último proceso que lo usó ha cerrado /dev/initrd.)

Argumentos de arranque para dispositivos SCSI

Notación general para esta sección:

iobase -- el primer puerto de E/S que ocupa el host SCSI. Se especifican en notación hexadecimal, y usualmente se encuentran en el rango desde 0x200 hasta 0x3ff.

irq -- la interrupción de hardware para la que la tarjeta está configurada para usarse. Los valores válidos dependerán de la tarjeta en cuestión, pero usualmente serán 5, 7, 9, 10, 11, 12 y 15. Los otros valores suelen usarse para periféricos comunes como discos duros IDE, disquetes, puertos serie, y así sucesivamente.

scsi-id -- el ID que el adaptador host usa para identificarse a sí mismo en el bus SCSI. Solo algunos adaptadores host le permiten cambiar este valor, ya que la mayoría lo tienen especificado permanentemente internamente. El valor predeterminado habitual es 7, pero las placas Seagate y Future Domain TMC-950 usan 6.

parity -- si el adaptador host SCSI espera que los dispositivos conectados proporcionen un valor de paridad con todos los intercambios de información. Especificar un uno indica que la comprobación de paridad está habilitada, y un cero la deshabilita. De nuevo, no todos los adaptadores soportarán la selección del comportamiento de paridad como argumento de arranque.

'max_scsi_luns=...'
Un dispositivo SCSI puede tener un número de 'subdispositivos' contenidos dentro de sí mismo. El ejemplo más común es uno de los nuevos CD-ROM SCSI que manejan más de un disco a la vez. Cada CD se direcciona como un 'Logical Unit Number' (LUN) de ese dispositivo en particular. Pero la mayoría de los dispositivos, como discos duros, unidades de cinta, y tales, son solo un dispositivo, y se les asignará el LUN cero.
Algunos dispositivos SCSI mal diseñados no pueden manejar ser sondeados por LUNs distintos de cero. Por lo tanto, si el indicador en tiempo de compilación CONFIG_SCSI_MULTI_LUN no está establecido, los núcleos más nuevos por defecto solo sondearán el LUN cero.
Para especificar el número de LUNs sondeados al arrancar, se introduce 'max_scsi_luns=n' como argumento de arranque, donde n es un número entre uno y ocho. Para evitar los problemas descritos anteriormente, se usaría n=1 para no molestar a tales dispositivos defectuosos.
Configuración de la cinta SCSI
Alguna configuración en tiempo de arranque del controlador de cinta SCSI se puede lograr usando lo siguiente:

st=buf_size[,write_threshold[,max_bufs]]

Los dos primeros números se especifican en unidades de kB. El buf_size predeterminado es 32 kB, y el tamaño máximo que se puede especificar es un ridículo 16384 kB. El write_threshold es el valor al que el búfer se envía a la cinta, con un valor predeterminado de 30 kB. El número máximo de búferes varía con el número de unidades detectadas, y tiene un valor predeterminado de dos. Un ejemplo de uso sería:

st=32,30,2

Se pueden encontrar detalles completos en el archivo Documentation/scsi/st.txt (o drivers/scsi/README.st para núcleos más antiguos) en el código fuente del núcleo de Linux.

Discos duros

Parámetros del controlador de disco/CD-ROM IDE
El controlador IDE acepta varios parámetros, que van desde especificaciones de geometría del disco, hasta soporte para chips de controlador defectuosos. Las opciones específicas de la unidad se especifican usando 'hdX=' con X en 'a'–'h'.
Las opciones no específicas de la unidad se especifican con el prefijo 'hd='. Nótese que usar un prefijo específico de la unidad para una opción no específica de la unidad seguirá funcionando, y la opción simplemente se aplicará como se espera.
Nótese también que 'hd=' puede usarse para referirse a la siguiente unidad no especificada en la secuencia (a, ..., h). Para las siguientes discusiones, se citará la opción 'hd=' por brevedad. Ver el archivo Documentation/ide/ide.txt (o Documentation/ide.txt en núcleos más antiguos, o drivers/block/README.ide en núcleos muy antiguos) en el código fuente del núcleo de Linux para más detalles.
Las opciones 'hd=cyls,heads,sects[,wpcom[,irq]]'
Estas opciones se usan para especificar la geometría física del disco. Solo se requieren los tres primeros valores. Los valores de cilindros/cabezas/sectores serán los usados por fdisk. El valor de precompensación de escritura se ignora para los discos IDE. El valor de IRQ especificado será el IRQ usado para la interfaz en la que reside la unidad, y no es realmente un parámetro específico de la unidad.
La opción 'hd=serialize'
El chip de interfaz IDE dual CMD-640 está defectuoso de fábrica de tal manera que cuando las unidades en la interfaz secundaria se usan al mismo tiempo que las unidades en la interfaz primaria, corromperá tus datos. Usar esta opción le dice al controlador que se asegure de que ambas interfaces nunca se usen al mismo tiempo.
La opción 'hd=noprobe'
No sondear esta unidad. Por ejemplo,

hdb=noprobe hdb=1166,7,17

NAME

bootparam - Parámetros de arranque del kernel de Linux

DESCRIPTION

Este documento describe los parámetros de arranque del kernel de Linux. Los parámetros de arranque se pasan al kernel al arrancar el sistema operativo. Se pueden usar para configurar el kernel o para pasar información a los programas del espacio de usuario.

Los parámetros de arranque se pueden especificar de varias maneras, incluyendo:

  • la línea de comandos del cargador de arranque
    Los cargadores de arranque como LILO y GRUB permiten especificar parámetros de arranque en sus archivos de configuración.
  • la línea de comandos del kernel
    Los parámetros de arranque se pueden pasar directamente al kernel en la línea de comandos.

Los parámetros de arranque se dividen en varias categorías, incluyendo:

Dispositivos de disco IDE y sus opciones

'hd='
Este parámetro se utiliza para pasar información sobre los discos duros IDE al kernel. La sintaxis es la siguiente:

hd=cyls,heads,sects

Donde:
  • cyls: el número de cilindros del disco.
  • heads: el número de cabezales del disco.
  • sects: el número de sectores por pista del disco.
Si hay varios discos duros instalados, el parámetro 'hd=' se puede repetir para cada disco. Por ejemplo:

hd=100,16,63 hd=200,32,63

hd=nowerr
Esta opción se utiliza para habilitar una solución alternativa para unidades de disco que tienen el bit WRERR_STAT permanentemente activado.
hd=cdrom
Esta opción le indica al controlador IDE que hay un CD-ROM compatible con ATAPI conectado en lugar de un disco duro IDE normal. En la mayoría de los casos, el CD-ROM se identifica automáticamente, pero si no es así, esta opción puede ayudar.
Opciones estándar del controlador de disco ST-506 ('hd=')
El controlador de disco estándar puede aceptar argumentos de geometría para los discos de forma similar al controlador IDE. Sin embargo, ten en cuenta que solo espera tres valores (C/H/S); cualquier cantidad mayor o menor será ignorada silenciosamente. Además, solo acepta 'hd=' como argumento, es decir, 'hda=' y similares no son válidos aquí. El formato es el siguiente:

hd=cyls,heads,sects

Si hay dos discos instalados, lo anterior se repite con los parámetros de geometría del segundo disco.

Dispositivos Ethernet

Diferentes controladores utilizan diferentes parámetros, pero todos comparten al menos una IRQ, un valor base de puerto de E/S y un nombre. En su forma más genérica, se parece a esto:


ether=irq,iobase[,param_1[,...param_8]],name

El primer argumento no numérico se toma como el nombre. Los valores param_n (si son aplicables) suelen tener significados diferentes para cada tarjeta/controlador diferente. Los valores param_n típicos se utilizan para especificar cosas como la dirección de memoria compartida, la selección de la interfaz, el canal DMA y similares.

El uso más común de este parámetro es forzar la detección de una segunda tarjeta Ethernet, ya que el valor predeterminado es detectar solo una. Esto se puede lograr con un simple:


ether=0,0,eth1

Ten en cuenta que los valores cero para la IRQ y la base de E/S en el ejemplo anterior indican a los controladores que realicen una detección automática.

El documento Ethernet-HowTo tiene una extensa documentación sobre el uso de múltiples tarjetas y sobre la implementación específica de la tarjeta/controlador de los valores param_n donde se utilizan. Los lectores interesados deben consultar la sección de ese documento sobre su tarjeta en particular.

El controlador de disquete

Hay muchas opciones para el controlador de disquete, y todas están listadas en Documentation/blockdev/floppy.txt (o Documentation/floppy.txt en kernels más antiguos, o drivers/block/README.fd para kernels muy antiguos) en el código fuente del kernel de Linux. Consulta ese archivo para obtener detalles.

El controlador de sonido

El controlador de sonido también puede aceptar argumentos de arranque para anular los valores compilados. Esto no se recomienda, ya que es bastante complejo. Se describe en el archivo del código fuente del kernel de Linux Documentation/sound/oss/README.OSS (drivers/sound/Readme.linux en versiones de kernel más antiguas). Acepta un argumento de arranque de la forma:


sound=device1[,device2[,device3...[,device10]]]

donde cada valor deviceN tiene el siguiente formato 0xTaaaId y los bytes se utilizan de la siguiente manera:

T - tipo de dispositivo: 1=FM, 2=SB, 3=PAS, 4=GUS, 5=MPU401, 6=SB16, 7=SB16-MPU401

aaa - dirección de E/S en hexadecimal.

I - línea de interrupción en hexadecimal (es decir, 10=a, 11=b, ...)

d - canal DMA.

Como puedes ver, se vuelve bastante complicado, y es mejor compilar tus propios valores personales como se recomienda. Usar un argumento de arranque 'sound=0' deshabilitará completamente el controlador de sonido.

El controlador de impresora de línea

'lp='

Sintaxis:

lp=0
lp=auto
lp=reset
lp=port[,port...]

Puedes indicar al controlador de impresora qué puertos usar y cuáles no usar. Esto último es útil si no quieres que el controlador de impresora reclame todos los puertos paralelos disponibles, para que otros controladores (por ejemplo, PLIP, PPA) puedan usarlos en su lugar.
El formato del argumento son múltiples nombres de puerto. Por ejemplo, lp=none,parport0 usará el primer puerto paralelo para lp1 y deshabilitará lp0. Para deshabilitar completamente el controlador de impresora, se puede usar lp=0.
