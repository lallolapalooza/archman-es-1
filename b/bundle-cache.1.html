BUNDLE-CACHE(1) Manual de comandos generales BUNDLE-CACHE(1)

NOMBRE

bundle-cache - Empaqueta tus archivos .gem necesarios en tu aplicación

SINOPSIS

bundle cache [OPCIONES]

alias: package, pack

DESCRIPCIÓN

Copia todos los archivos .gem necesarios para ejecutar la aplicación en el directorio vendor/cache. En el futuro, al ejecutar bundle install(1) bundle-install.1.html, se usarán los gems de la caché en lugar de los de rubygems.org.

OPCIONES

--all
Incluir todas las fuentes (incluyendo path y git).
--all-platforms
Incluir gems para todas las plataformas presentes en el lockfile, no solo la actual.
--cache-path=RUTA-CACHE
Especificar una ruta de caché diferente a la predeterminada (vendor/cache).
--gemfile=GEMFILE
Usar el gemfile especificado en lugar de Gemfile.
--no-install
No instalar los gems, solo actualizar la caché.
--no-prune
No eliminar gems obsoletos de la caché.
--path=RUTA
Especificar una ruta diferente a la predeterminada del sistema ($BUNDLE_PATH o $GEM_HOME).
--quiet
Solo mostrar advertencias y errores.
--frozen
No permitir que el Gemfile.lock se actualice después de la instalación de esta operación de bundle cache.

GEMS GIT Y DE RUTA

El comando bundle cache también puede empaquetar dependencias :git y :path además de archivos .gem. Esto debe habilitarse explícitamente con la opción --all. Una vez utilizada, la opción --all se recordará.

SOPORTE PARA MÚLTIPLES PLATAFORMAS

Al usar gems que tienen diferentes paquetes para diferentes plataformas, Bundler admite el almacenamiento en caché de gems para otras plataformas donde el Gemfile se ha resuelto (es decir, presente en el lockfile) en vendor/cache. Esto debe habilitarse con la opción --all-platforms. Esta configuración se recordará en su configuración local de bundler.

OBTENCIÓN REMOTA

Por defecto, si ejecuta bundle install(1) bundle-install.1.html después de ejecutar bundle cache(1) bundle-cache.1.html, bundler aún se conectará a rubygems.org para verificar si existe un gem específico de plataforma para alguno de los gems en vendor/cache.

Por ejemplo, considere este Gemfile(5):

source "https://rubygems.org"
gem "nokogiri"

Si ejecuta bundle cache bajo C Ruby, bundler recuperará la versión de nokogiri para la plataforma "ruby". Si despliega en JRuby y ejecuta bundle install, bundler se verá obligado a verificar si existe una versión de nokogiri para la plataforma "java".

Aunque el gem nokogiri para la plataforma Ruby es *técnicamente* aceptable en JRuby, tiene una extensión C que no se ejecuta en JRuby. Como resultado, bundler, por defecto, se conectará a rubygems.org para verificar si tiene una versión de alguno de sus gems más específica para su plataforma.

Este problema tampoco se limita a la plataforma "java". Un problema similar (común) puede ocurrir al desarrollar en Windows y desplegar en Linux, o incluso al desarrollar en OSX y desplegar en Linux.

Si está seguro de que los gems empaquetados en vendor/cache son apropiados para la plataforma en la que se encuentra, puede ejecutar bundle install --local para omitir la verificación de gems más apropiados y usar los de vendor/cache.

Una forma de asegurarse de tener las versiones de plataforma correctas de todos sus gems es ejecutar bundle cache en una máquina idéntica y subir los gems. Por ejemplo, puede ejecutar bundle cache en un staging box idéntico durante su proceso de staging, y subir los vendor/cache antes de desplegar en producción.

Por defecto, bundle cache(1) bundle-cache.1.html obtiene y también instala los gems en la ubicación predeterminada. Para empaquetar las dependencias en vendor/cache sin instalarlas en la ubicación de instalación local, puede ejecutar bundle cache --no-install.

HISTORIA

En Bundler 2.1, cache asumió las funcionalidades de package y ahora package y pack son alias de cache.
