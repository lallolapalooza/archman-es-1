buildah-commit(1) General Commands Manual buildah-commit(1)

NOMBRE

buildah-commit - Crea una imagen a partir de un contenedor de trabajo.

SINOPSIS

buildah commit [opciones] contenedor [imagen]

DESCRIPCIÓN

Escribe una nueva imagen utilizando la capa de lectura-escritura del contenedor especificado y, si se basa en una imagen, las capas de esa imagen. Si imagen no comienza con un componente de nombre de registro, se agregará localhost al nombre. Si no se proporciona imagen, la imagen no tendrá nombre. Cuando una imagen no tiene nombre, el comando buildah images mostrará <none> en las columnas REPOSITORY y TAG.

El valor imagen soporta todos los transportes de containers-transports(5). Si no se especifica ningún transporte, se utiliza el transporte containers-storage (es decir, almacenamiento local).

VALOR DE RETORNO

El ID de la imagen que se creó. En caso de error, se devuelve 1 y se devuelve errno.

OPCIONES

--add-file fuente[:destino]

Lee el contenido del archivo fuente y lo agrega a la imagen confirmada como un archivo en destino. Si no se especifica destino, se utilizará la ruta de fuente. El nuevo archivo será propiedad de UID 0, GID 0, tendrá permisos 0644 y se le dará la marca de tiempo especificada en la opción --timestamp si se especifica. Esta opción se puede especificar varias veces.

--annotation anotación[=valor]

Agrega una anotación a la imagen (por ejemplo, anotación=valor) a los metadatos de la imagen. Se puede usar varias veces. Si se nombra anotación, pero no se proporciona ni = ni valor, entonces la anotación se establece en un valor vacío.

Nota: esta información no está presente en los formatos de imagen de Docker, por lo que se descarta al escribir imágenes en formatos de Docker.

--authfile ruta

Ruta del archivo de autenticación. El valor predeterminado es ${XDG_RUNTIME_DIR}/containers/auth.json. Consulte containers-auth.json(5) para obtener más información. Este archivo se crea utilizando buildah login.

Si el estado de autorización no se encuentra allí, se verifica $HOME/.docker/config.json, que se establece utilizando docker login.

Nota: También puede anular la ruta predeterminada del archivo de autenticación estableciendo la variable de entorno REGISTRY_AUTH_FILE. export REGISTRY_AUTH_FILE=ruta

--cert-dir ruta

Utiliza certificados en ruta (*.crt, *.cert, *.key) para conectarse al registro. El directorio de certificados predeterminado es /etc/containers/certs.d.

--change, -c "INSTRUCCIÓN"

Aplica el cambio a la imagen confirmada que se habría realizado si se hubiera construido utilizando un Containerfile que incluyera la instrucción especificada. Esta opción se puede especificar varias veces.

--config nombre_archivo

Lee una versión codificada en JSON de un objeto de configuración de imagen desde el archivo especificado y fusiona sus valores con la configuración de la imagen que se está confirmando.

--annotation-created

Agrega una anotación a la imagen (ver también --annotation) a los metadatos de la imagen estableciendo "org.opencontainers.image.created" a la hora actual, o a la marca de fecha especificada en el indicador --source-date-epoch o --timestamp, si se utilizó alguno de ellos. Si es false, no habrá dicha anotación en la imagen escrita.

Nota: esta información no está presente en los formatos de imagen de Docker, por lo que se descarta al escribir imágenes en formatos de Docker.

--creds creds

El [nombre de usuario[:contraseña]] a utilizar para autenticarse con el registro si es necesario. Si no se proporcionan uno o ambos valores, aparecerá un aviso en la línea de comandos y se podrá ingresar el valor. La contraseña se ingresa sin mostrarse.

--cw opciones

Produce una imagen adecuada para ser utilizada como carga de trabajo confidencial que se ejecuta en un entorno de ejecución confiable (TEE) utilizando krun (es decir, crun compilado con la función libkrun habilitada e invocado como krun). En lugar de los contenidos convencionales, el sistema de archivos raíz de la imagen contendrá una imagen de disco cifrada e información de configuración para krun.

El valor de opciones es una lista separada por comas de pares clave=valor, que proporciona información de configuración necesaria para producir los datos adicionales que se incluirán en la imagen del contenedor.

Las claves reconocidas son:

attestation_url: La ubicación de un agente de claves / servidor de atestación. Si se especifica un valor, el ID de carga de trabajo de la nueva imagen, junto con la frase secreta utilizada para cifrar la imagen del disco, se registrarán con el servidor, y la ubicación del servidor se almacenará en la imagen del contenedor. En tiempo de ejecución, se espera que krun se ponga en contacto con el servidor para recuperar la frase secreta utilizando el ID de carga de trabajo, que también se almacena en la imagen del contenedor. Si no se especifica ningún valor, se debe especificar un valor de passphrase.

cpus: El número de CPU virtuales con los que se espera que se ejecute la imagen en tiempo de ejecución. Si no se especifica, se proporcionará un valor predeterminado.

firmware_library: La ubicación de la biblioteca compartida libkrunfw-sev. Si no se especifica, buildah verifica su presencia en una serie de ubicaciones codificadas.

memory: La cantidad de memoria con la que se espera que se ejecute la imagen en tiempo de ejecución, como número de megabytes. Si no se especifica, se proporcionará un valor predeterminado.

passphrase: La frase secreta a utilizar para cifrar la imagen del disco que se incluirá en la imagen del contenedor. Si no se especifica ningún valor, pero se especifica un valor de attestation_url, se utilizará una frase secreta generada aleatoriamente. Los autores recomiendan especificar una attestation_url pero no una passphrase.

slop: Espacio adicional a asignar para la imagen del disco en comparación con el tamaño de los contenidos de la imagen del contenedor, expresado como un porcentaje (..%) o un valor de tamaño (bytes o unidades más grandes si hay sufijos como KB o MB), o una suma de dos o más de esas especificaciones separadas por "+". Si no se especifica, buildah estima que el 25% más de espacio que los contenidos será suficiente, pero esta opción se proporciona en caso de que su estimación sea incorrecta. Si el tamaño especificado o calculado es inferior a 10 megabytes, se aumentará a 10 megabytes.

type: El tipo de entorno de ejecución confiable (TEE) para el cual debe marcarse la imagen. Los valores aceptados son "SEV" (AMD Secure Encrypted Virtualization - Estado Cifrado) y "SNP" (AMD Secure Encrypted Virtualization - Nested Paging Seguro). Si no se especifica, el valor predeterminado es "SNP".

workload_id: Un identificador de carga de trabajo que se registrará en la imagen del contenedor, para ser utilizado en tiempo de ejecución para recuperar la frase secreta utilizada para cifrar la imagen del disco. Si no se especifica, se derivará un valor semialeatorio del ID de imagen de la imagen base.

--disable-compression, -D

No comprimir las capas del sistema de archivos al crear la imagen a menos que sea requerido por la ubicación donde se está escribiendo la imagen. Esta es la configuración predeterminada, ya que las capas de imagen se comprimen automáticamente cuando se envían a los registros, y las imágenes que se escriben en almacenamiento local solo necesitarían ser descomprimidas nuevamente para almacenarse. La compresión se puede forzar en todos los casos especificando --disable-compression=false.

--encrypt-layer capa(s)

Capa(s) a cifrar: índices de capas indexados desde 0 con soporte para indexación negativa (por ejemplo, 0 es la primera capa, -1 es la última capa). Si no se define, cifrará todas las capas si se especifica el indicador de clave de cifrado.

--encryption-key clave

El [protocolo:archivo_clave] especifica el protocolo de cifrado, que puede ser JWE (RFC7516), PGP (RFC4880) y PKCS7 (RFC2315) y el material de clave necesario para el cifrado de la imagen. Por ejemplo, jwe:/ruta/a/clave.pem o pgp:admin@example.com o pkcs7:/ruta/a/archivo-x509.

--format, -f [oci | docker]

Controla el formato del manifiesto de la imagen y los datos de configuración. Los formatos reconocidos incluyen oci (OCI image-spec v1.0, el valor predeterminado) y docker (versión 2, utilizando el formato de esquema 2 para el manifiesto).

Nota: También puede anular el formato predeterminado estableciendo la variable de entorno BUILDAH_FORMAT. export BUILDAH_FORMAT=docker

EJEMPLOS

Confirmar un contenedor llamado `mycontainer` como una nueva imagen llamada `myimage`:

$ buildah commit mycontainer myimage
```

Confirmar un contenedor llamado `mycontainer` como una nueva imagen con un nombre de registro especificado:

$ buildah commit mycontainer docker://myregistry.com/myimage
```

Confirmar un contenedor llamado `mycontainer` como una nueva imagen con una etiqueta específica:

$ buildah commit mycontainer myimage:1.0
```

Confirmar un contenedor llamado `mycontainer` como una nueva imagen sin nombre:

$ buildah commit mycontainer
```

Confirmar un contenedor llamado `mycontainer` como una nueva imagen llamada `myimage` y agregar anotaciones:

$ buildah commit --annotation vendor=RedHat --annotation com.example.version=1.0 mycontainer myimage
```

Confirmar un contenedor llamado `mycontainer` como una nueva imagen llamada `myimage` y establecer la marca de tiempo de creación:

$ buildah commit --timestamp 1607120183 mycontainer myimage
```

Confirmar un contenedor llamado `mycontainer` como una nueva imagen llamada `myimage`, pero sin incluir la anotación de fecha de creación:

$ buildah commit --created-annotation=false mycontainer myimage
```

Confirmar un contenedor llamado `mycontainer` como una nueva imagen llamada `myimage`, agregando un archivo al committed image:

$ buildah commit --add-file /tmp/myfile.txt:/etc/myconfig.conf mycontainer myimage
```

Confirmar un contenedor llamado `mycontainer` como una nueva imagen llamada `myimage`, agregando un archivo al committed image y especificando la propiedad y los permisos:

$ buildah commit --add-file /tmp/myfile.txt:644:0:0:/etc/myconfig.conf mycontainer myimage
```

Confirmar un contenedor llamado `mycontainer` como una nueva imagen OCI llamada `myimage` y agregando un cambio de instrucción:

$ buildah commit --format oci -c "ENTRYPOINT ["/usr/bin/mycmd"]" mycontainer myimage
```

Confirmar un contenedor llamado `mycontainer` como una nueva imagen llamada `myimage` usando el formato Docker y especificando un archivo de configuración:

$ buildah commit --format docker --config /tmp/myconfig.json mycontainer myimage
```

Confirmar un contenedor llamado `mycontainer` como una nueva imagen llamada `myimage`, donde la imagen es cifrada usando una clave PGP:

$ buildah commit --encryption-key pgp:admin@example.com mycontainer myimage
```

Confirmar un contenedor llamado `mycontainer` como una nueva imagen llamada `myimage`, cifrando solo las capas 0 y 2:

$ buildah commit --encryption-key pgp:admin@example.com --encrypt-layer 0 --encrypt-layer 2 mycontainer myimage
```

Confirmar un contenedor llamado `mycontainer` como una nueva imagen llamada `myimage`, creando una imagen confidencial para TEE SEV:

$ buildah commit --cw "type=SEV,memory=2048,cpus=2,attestation_url=https://attest.example.com" mycontainer myimage
```

Confirmar un contenedor llamado `mycontainer` como una nueva imagen llamada `myimage`, creando una imagen confidencial para TEE SNP sin una URL de atestación, pero especificando una frase secreta:

$ buildah commit --cw "type=SNP,memory=2048,cpus=2,passphrase=mysecret" mycontainer myimage
```

OPCIONES

--identity-label valor-booleano

Añade una etiqueta io.buildah.version con su valor establecido en la versión de buildah que confirmó la imagen (por defecto true a menos que se utilice --timestamp o --source-date-epoch).

--iidfile ImageIDfile

Escribe el ID de la imagen en el archivo.

--manifest "nombreLista"

Nombre de la lista de manifiestos a la que se añadirá la imagen creada. Crea la lista de manifiestos si no existe. Esta opción es útil para crear imágenes de múltiples arquitecturas.

--omit-history valor-booleano

Omite la información del historial de construcción en la imagen creada. (por defecto false).

Esta opción es útil en los casos en que los usuarios finales deseen explícitamente establecer --omit-history para omitir el History opcional de las imágenes creadas o cuando se trabaja con imágenes creadas utilizando herramientas de construcción que no incluyen información de History en sus imágenes.

--pull

Cuando el indicador --pull está habilitado o se establece explícitamente en true (con --pull=true), intenta descargar las últimas versiones de las imágenes escáner SBOM de los registros listados en registries.conf si no existe una imagen escáner SBOM local o si la imagen en el registro es más nueva que la que está en el almacenamiento local. Genera un error si la imagen escáner SBOM no está en ningún registro listado y no está presente localmente.

Si el indicador está deshabilitado (con --pull=false), no descargues imágenes escáner SBOM de los registros, usa solo las versiones locales. Genera un error si una imagen escáner SBOM no está presente localmente.

Si el indicador de descarga se establece en always (con --pull=always), descarga las imágenes escáner SBOM de los registros listados en registries.conf. Genera un error si no se encuentra una imagen escáner SBOM en los registros, incluso si una imagen con el mismo nombre está presente localmente.

Si el indicador de descarga se establece en missing (con --pull=missing), descarga las imágenes escáner SBOM solo si no se pudieron encontrar en el almacenamiento local de contenedores. Genera un error si no se encontró ninguna imagen y la descarga falla.

Si el indicador de descarga se establece en never (con --pull=never), no descargues imágenes escáner SBOM de los registros, usa solo las versiones locales. Genera un error si la imagen no está presente localmente.

--quiet, -q

Al escribir la imagen de salida, suprime la salida del progreso.

--rewrite-timestamp

Al generar la nueva capa para la imagen, asegúrate de que ningún contenido añadido tenga una marca de tiempo posterior al valor utilizado por el indicador --source-date-epoch, si se proporcionó alguno, reemplazando cualquier marca de tiempo que sea posterior a ese valor, por ese valor.

--rm Elimina el contenedor de trabajo y su contenido después de crear la imagen. Por defecto, deja el contenedor y su contenido en su lugar.

--sbom preset

Genera SBOMs (Software Bills Of Materials) para la imagen de salida escaneando el contenedor de trabajo y los contextos de construcción utilizando la combinación nombrada de imagen escáner, comandos escáner y estrategia de fusión. Debe especificarse con uno o más de --sbom-image-output, --sbom-image-purl-output, --sbom-output y --sbom-purl-output. Presets reconocidos y el conjunto de opciones a los que equivalen:

  • "syft", "syft-cyclonedx":
    --sbom-scanner-image=ghcr.io/anchore/syft
    --sbom-scanner-command="/syft scan -q dir:{ROOTFS} --output cyclonedx-json={OUTPUT}"
    --sbom-scanner-command="/syft scan -q dir:{CONTEXT} --output cyclonedx-json={OUTPUT}"
    --sbom-merge-strategy=merge-cyclonedx-by-component-name-and-version
  • "syft-spdx":
    --sbom-scanner-image=ghcr.io/anchore/syft
    --sbom-scanner-command="/syft scan -q dir:{ROOTFS} --output spdx-json={OUTPUT}"
    --sbom-scanner-command="/syft scan -q dir:{CONTEXT} --output spdx-json={OUTPUT}"
    --sbom-merge-strategy=merge-spdx-by-package-name-and-versioninfo
  • "trivy", "trivy-cyclonedx":
    --sbom-scanner-image=ghcr.io/aquasecurity/trivy
    --sbom-scanner-command="trivy filesystem -q {ROOTFS} --format cyclonedx --output {OUTPUT}"
    --sbom-scanner-command="trivy filesystem -q {CONTEXT} --format cyclonedx --output {OUTPUT}"
    --sbom-merge-strategy=merge-cyclonedx-by-component-name-and-version
  • "trivy-spdx":
    --sbom-scanner-image=ghcr.io/aquasecurity/trivy
    --sbom-scanner-command="trivy filesystem -q {ROOTFS} --format spdx-json --output {OUTPUT}"
    --sbom-scanner-command="trivy filesystem -q {CONTEXT} --format spdx-json --output {OUTPUT}"
    --sbom-merge-strategy=merge-spdx-by-package-name-and-versioninfo

--sbom-image-output ruta

Al generar SBOMs, almacena el SBOM generado en la ruta especificada en la imagen de salida. No hay valor por defecto.

--sbom-image-purl-output ruta

Al generar SBOMs, escanea en busca de información PURL (package URL ⟨https://github.com/package-url/purl-spec/blob/master/PURL-SPECIFICATION.rst⟩), y guarda una lista de PURLs encontradas en el archivo nombrado en el sistema de archivos local. No hay valor por defecto.

--sbom-merge-strategy método

Si se está utilizando más de un valor de --sbom-scanner-command, utiliza el método especificado para fusionar la salida de los comandos posteriores con la salida de los comandos anteriores. Los valores reconocidos incluyen:

  • cat
    Concatena los archivos.
  • merge-cyclonedx-by-component-name-and-version
    Fusiona los campos "component" de los documentos JSON, ignorando los valores de
    los documentos cuando la combinación de sus valores de "name" y "version" ya está
    presente. Los documentos se procesan en el orden en que se generan, que es el orden en que se especificaron los comandos que los generan.
  • merge-spdx-by-package-name-and-versioninfo
    Fusiona los campos "package" de los documentos JSON, ignorando los valores de
    los documentos cuando la combinación de sus valores de "name" y "versionInfo" ya está
    presente. Los documentos se procesan en el orden en que se generan, que es el orden en que se especificaron los comandos que los generan.

--sbom-output archivo

Al generar SBOMs, almacena el SBOM generado en el archivo nombrado en el sistema de archivos local. No hay valor por defecto.

--sbom-purl-output archivo

Al generar SBOMs, escanea en busca de información PURL (package URL ⟨https://github.com/package-url/purl-spec/blob/master/PURL-SPECIFICATION.rst⟩), y guarda una lista de PURLs encontradas en el archivo nombrado en el sistema de archivos local. No hay valor por defecto.

--sbom-scanner-command imagen

Genera SBOMs ejecutando el comando especificado desde la imagen escáner. Si se especifican varios comandos, se ejecutan en el orden en que se especifican. Se realizan las siguientes sustituciones de texto:
- {ROOTFS}
La raíz del sistema de archivos de la imagen creada, montada como enlace.
- {CONTEXT}
El contexto de construcción y los contextos de construcción adicionales, montados como enlace.
- {OUTPUT}
El nombre de un archivo de salida temporal, para ser leído y fusionado con otros o copiado a otro lugar.

--sbom-scanner-image imagen

Genera SBOMs utilizando la imagen escáner especificada.

--sign-by huella digital

Firma la nueva imagen utilizando la clave GPG que coincide con la huella digital especificada.

--source-date-epoch segundos

Establece la marca de tiempo "created" para la imagen en este número de segundos desde la época (Unix time 0, es decir, 00:00:00 UTC del 1 de enero de 1970) para facilitar la creación de compilaciones deterministas (por defecto es $SOURCE_DATE_EPOCH si está establecido, de lo contrario se utilizará la hora actual).

La marca de tiempo "created" se escribe en la configuración y el manifiesto de la imagen cuando se confirma la imagen, por lo que confirmar el mismo contenedor de trabajo en dos momentos diferentes producirá imágenes con diferentes hashes sha256, incluso si no se realizaron otros cambios en el contenedor de trabajo entre medias.

Cuando se establece --source-date-epoch, la marca de tiempo "created" se establece siempre en la hora especificada, lo que debería permitir la confirmación de imágenes idénticas en diferentes momentos.

Entra en conflicto con el indicador similar --timestamp, que también establece su hora especificada en el contenido de las capas.

--squash

Comprime todas las capas de la nueva imagen (incluidas las heredadas de una imagen base) en una única capa nueva.

--timestamp segundos

Establece la marca de tiempo "created" para la imagen en este número de segundos desde la época (Unix time 0, es decir, 00:00:00 UTC del 1 de enero de 1970) para facilitar la creación de compilaciones deterministas (por defecto es la hora actual).

La marca de tiempo "created" se escribe en la configuración y el manifiesto de la imagen cuando se confirma la imagen, por lo que confirmar el mismo contenedor de trabajo en dos momentos diferentes producirá imágenes con diferentes hashes sha256, incluso si no se realizaron otros cambios en el contenedor de trabajo entre medias.

Cuando se establece --timestamp, la marca de tiempo "created" se establece siempre en la hora especificada, lo que debería permitir la confirmación de imágenes idénticas en diferentes momentos. Todo el contenido de la nueva capa añadida como parte de la imagen también llevará esta marca de tiempo.

Entra en conflicto con el indicador similar --source-date-epoch, que, por defecto, no afecta a las marcas de tiempo del contenido de las capas.

--tls-verify valor-booleano

Requiere HTTPS y verificación de certificados al comunicarse con registros de contenedores (por defecto es true). La verificación TLS no se puede utilizar al comunicarse con un registro inseguro.

--unsetannotation anotación

Anula la anotación de la imagen, lo que provoca que la anotación no se herede de la imagen base.

--unsetenv env

Anula las variables de entorno de la imagen final.

BUILD_REGISTRY_SOURCE

S

BUILD_REGISTRY_SOURCES, si está definida, se trata como un objeto JSON que contiene listas de nombres de registros bajo las claves insecureRegistries, blockedRegistries, y allowedRegistries

.

Al hacer commit de una imagen, si se le va a dar un nombre a la imagen, la parte del nombre que corresponde a un registro se compara con los elementos de la lista blockedRegistries, y si coincide con alguno de ellos, se deniega el intento de commit. Si hay registros en la lista allowedRegistries, y la parte del nombre que corresponde al registro no está en la lista, se deniega el intento de

commit.
