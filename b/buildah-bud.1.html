NOMBRE

buildah-build - Construye una imagen utilizando instrucciones de Containerfiles

SINOPSIS

buildah build [opciones] [contexto]

buildah bud [opciones] [contexto]

DESCRIPCIÓN

Construye una imagen utilizando instrucciones de uno o más Containerfiles o Dockerfiles y un directorio de contexto de construcción especificado. Un Containerfile utiliza la misma sintaxis que un Dockerfile internamente. Para este documento, un archivo al que se hace referencia como Containerfile puede ser un archivo llamado 'Containerfile' o 'Dockerfile'.

El directorio de contexto de construcción se puede especificar como la URL http(s) de un archivo, repositorio git o Containerfile.

Si no se especifica ningún directorio de contexto, Buildah asumirá el directorio de trabajo actual como contexto de construcción, que debería contener un Containerfile.

Los Containerfiles que terminan con el sufijo ".in" se preprocesarán a través de cpp(1). Esto puede ser útil para descomponer Containerfiles en varias partes reutilizables que se pueden usar a través de la directiva #include de CPP. Tenga en cuenta que un archivo Containerfile.in todavía puede ser utilizado por otras herramientas cuando se preprocesan manualmente a través de cpp -E. Cualquier comentario (líneas que comienzan con #) en los Containerfiles incluidos que no sean comandos de preprocesamiento, se imprimirán como advertencias durante las compilaciones.

Cuando la URL es un archivo, el contenido de la URL se descarga a una ubicación temporal y se extrae antes de la ejecución.

Cuando la URL es un Containerfile, el archivo se descarga a una ubicación temporal.

Cuando se establece un repositorio Git como URL, el repositorio se clona localmente y luego se utiliza como contexto de construcción. Una rama no predeterminada (o ID de commit) y un subdirectorio del repositorio git clonado se pueden usar incluyendo sus nombres al final de la URL en el formato myrepo.git#mybranch:subdir, myrepo.git#mycommit:subdir, o myrepo.git#:subdir si el subdirectorio debe usarse desde la rama predeterminada.

OPCIONES

--add-host=[]

Agrega un mapeo personalizado de host a IP (host:ip)

Agrega una línea a /etc/hosts. El formato es nombre de host:ip. La opción --add-host se puede establecer varias veces. Entra en conflicto con la opción --no-hosts.

En lugar de una dirección IP, se puede proporcionar la bandera especial host-gateway. Esto se resuelve en una dirección IP que el contenedor puede usar para conectarse al host. La dirección IP elegida depende de su configuración de red, por lo tanto, no hay garantía de que Buildah pueda determinar la dirección del host-gateway automáticamente, lo que hará que Buildah falle con un mensaje de error. Puede sobrescribir esta dirección IP utilizando la opción host_containers_internal_ip en containers.conf.

La dirección del host-gateway también es utilizada por Buildah para agregar automáticamente los nombres de host host.containers.internal y host.docker.internal a /etc/hosts. Puede evitar esto proporcionando la opción --no-hosts, o configurando host_containers_internal_ip="none" en containers.conf. Si no se configuró ninguna dirección de host-gateway manualmente y Buildah no puede determinar la dirección IP automáticamente, Buildah omitirá silenciosamente la adición de estos nombres de host internos a /etc/hosts. Si Buildah se está ejecutando en una máquina virtual que utiliza podman machine (esto incluye hosts Mac y Windows), Buildah omitirá silenciosamente la adición de los nombres de host internos a /etc/hosts, a menos que se haya configurado una dirección IP manualmente; los nombres de host internos se resuelven mediante el resolvedor DNS de gvproxy en su lugar.

Buildah usará el archivo /etc/hosts del host como base por defecto, es decir, cualquier nombre de host presente en este archivo también estará presente en el archivo /etc/hosts del contenedor. Se puede configurar un archivo base diferente utilizando la configuración base_hosts_file en containers.conf

--all-platforms

En lugar de construir para un conjunto de plataformas especificadas utilizando la opción --platform, inspecciona las imágenes base de la compilación y construye para todas las plataformas para las que están disponibles. Las etapas que utilizan scratch como punto de partida no se pueden inspeccionar, por lo que debe haber al menos una etapa que no sea scratch para que la detección funcione de manera útil.

--annotation anotación[=valor]

Agrega una anotación de imagen (por ejemplo, anotación=valor) a los metadatos de la imagen. Se puede usar varias veces. Si se nombra la anotación, pero no se proporciona = ni un valor, entonces la anotación se establece en un valor vacío.

Nota: esta información no está presente en los formatos de imagen Docker, por lo que se descarta al escribir imágenes en formatos Docker.

--arch="ARQUITECTURA"

Establece la ARQUITECTURA de la imagen a construir, y la de la imagen base a descargar, si la compilación utiliza una, al valor proporcionado en lugar de usar la arquitectura del host. (Ejemplos: arm, arm64, 386, amd64, ppc64le, s390x)

--authfile ruta

Ruta del archivo de autenticación. Por defecto es ${XDG_RUNTIME_DIR}/containers/auth.json. Consulte containers-auth.json(5) para obtener más información. Este archivo se crea usando buildah login.

Si el estado de autorización no se encuentra allí, se verifica $HOME/.docker/config.json, que se establece usando docker login.

Nota: También puede anular la ruta predeterminada del archivo de autenticación estableciendo la variable de entorno REGISTRY_AUTH_FILE. export REGISTRY_AUTH_FILE=ruta

--build-arg arg=valor

Especifica un argumento de compilación y su valor, que se interpolará en las instrucciones leídas de los Containerfiles de la misma manera que las variables de entorno, pero que no se agregarán a la lista de variables de entorno en la configuración de la imagen resultante.

Consulte la sección VARIABLES DE TIEMPO DE COMPILACIÓN ⟨#build-time-variables⟩ para ver la lista de variables que se pueden sobrescribir dentro del Containerfile en tiempo de ejecución.

--build-arg-file ruta

Especifica un archivo que contiene líneas de argumentos de compilación del formato arg=valor. El nombre de archivo sugerido es argfile.conf.

Las líneas de comentarios que comienzan con # se ignoran, junto con las líneas en blanco. Todas las demás deben tener el formato arg=valor pasado a --build-arg.

Si se proporcionan varios argumentos a través de las opciones --build-arg-file y --build-arg, los argumentos de compilación se fusionarán en todos los archivos proporcionados y los argumentos de línea de comandos.

Cualquier archivo proporcionado en una opción --build-arg-file se leerá antes que los argumentos suministrados a través de la opción --build-arg.

Cuando se especifica un nombre de argumento dado varias veces, la última instancia es la que se pasa a las compilaciones resultantes. Esto significa que los valores de --build-arg siempre anulan a los de un --build-arg-file.

--build-context nombre=valor

Especifica un contexto de compilación adicional utilizando su nombre corto y su ubicación. Los contextos de compilación adicionales se pueden referenciar de la misma manera que accedemos a diferentes etapas en la instrucción COPY.

Los valores válidos podrían ser: * Directorio local – por ejemplo, --build-context project2=../path/to/project2/src * URL HTTP a un archivo tar – por ejemplo, --build-context src=https://example.org/releases/src.tar * Imagen de contenedor – especificada con un prefijo container-image://, por ejemplo, --build-context alpine=container-image://alpine:3.15, (también acepta docker://, docker-image://)

En el lado del Containerfile, puede hacer referencia al contexto de compilación en todos los comandos que aceptan el parámetro “from”. Así es como podría verse:

FROM [nombre]
COPY --from=[nombre] ...
RUN --mount=from=[nombre] …

El valor de [nombre] coincide con el siguiente orden de prioridad:

  • Contexto de compilación con nombre definido con --build-context [nombre]=..
  • Etapa definida con AS [nombre] dentro de Containerfile
  • Imagen [nombre], ya sea local o en un registro remoto

--cache-from

Repositorio a utilizar como una lista potencial de fuentes de caché. Cuando se especifica, Buildah intentará buscar imágenes de caché en los repositorios especificados e intentará descargar imágenes de caché en lugar de ejecutar los pasos de compilación localmente. Buildah solo intentará descargar imágenes cacheadas previamente si se consideran coincidencias de caché válidas.

Utilice la opción --cache-to para poblar uno o más repositorios remotos con contenido de caché.

Ejemplo

# poblar una caché y también consultarla
buildah build -t test --layers --cache-to registry/myrepo/cache --cache-from registry/myrepo/cache .

--cache-to

Parámetros para la creación de caché. Buildah puede exportar imágenes de compilación y sus capas a un repositorio remoto. La opción --cache-to se puede especificar varias veces para crear múltiples salidas de caché.

La sintaxis del parámetro es type=TYPE,mode=MODE,dest=DESTINATION[,param=value...].

El parámetro type especifica el tipo de exportación de caché. Actualmente, solo se admite el tipo registry.

El parámetro mode especifica cómo se debe escribir la caché. Los modos disponibles son min (solo las capas necesarias) y max (todas las capas, lo que puede resultar en imágenes más grandes y una compilación más lenta).

El parámetro dest especifica el destino de la caché. Para el tipo registry, esto es un nombre de repositorio.

Los parámetros adicionales pueden incluir ignore=true para ignorar errores al escribir en la caché, o compression=COMPRESSION para especificar un nivel de compresión.

Cuando se utiliza la opción --cache-to, Buildah puede generar imágenes de caché que se pueden utilizar como fuentes de caché en compilaciones posteriores. Consulte la opción --cache-from.

--cert-dir ruta

Ruta de un directorio que contiene certificados TLS de confianza mutua (mTLS).

Si se especifica, Buildah utilizará los certificados en este directorio para verificar las conexiones TLS a los registros remotos.

Los certificados deben nombrarse de la siguiente manera:

  • ca.crt: Certificado de autoridad de certificación
  • ca.pem: Certificado de autoridad de certificación
  • client.crt: Certificado de cliente
  • client.pem: Certificado de cliente
  • client.key: Clave privada del cliente

--cpu-shares=0

Límite de CPU para el contenedor de compilación.

--creds usuario:contraseña

Credenciales de autenticación de usuario:contraseña para acceder a un repositorio remoto.

Esto tiene prioridad sobre las credenciales especificadas mediante la opción --authfile.

Establece el período de CPU para la compilación.

--cpu-quota=0

Establece la cuota de CPU para la compilación.

--cpu-realtime-period=0

Establece el período de tiempo real de CPU para la compilación.

--cpu-realtime-runtime=0

Establece el tiempo de ejecución de tiempo real de CPU para la compilación.

--cpuset-cpus lista-de-cpus

Establece las CPU que los procesos dentro del contenedor pueden usar. Por ejemplo: 0-3 o 0,1.

--cpuset-mems lista-de-mems

Establece la memoria que los procesos dentro del contenedor pueden usar. Por ejemplo: 0-1 o 0,1.

--debug

Habilita la salida de depuración.

--disable-content-trust

Deshabilita la verificación de firmas de contenido. Esto está habilitado por defecto en algunos registros.

--dns ip

Especifica una dirección de servidor DNS para el contenedor. Puede especificarse varias veces.

--dns-opt opción

Especifica una opción de DNS para el contenedor. Puede especificarse varias veces.

--dns-option opción

Especifica una opción de DNS para el contenedor. Puede especificarse varias veces.

--dns-search dominio

Especifica un dominio de búsqueda DNS para el contenedor. Puede especificarse varias veces.

--dockerfile ruta

El archivo a usar como Containerfile. Por defecto, es 'Containerfile' o 'Dockerfile' en el directorio raíz del contexto.

--drop capacidad

Elimina una capacidad del kernel. Por ejemplo, --drop=SYS_ADMIN.

--emulator ruta

Ruta de un binario emulador que se utiliza para ejecutar binarios de diferente arquitectura. Esto es útil cuando se construye en una arquitectura diferente a la de destino, por ejemplo, para construir binarios ARM en una máquina x86_64.

--enable característica

Habilita una característica experimental. Las características disponibles son: sbom, pull-proxy, push-proxy.

--exclude ruta

Opcionalmente, se puede especificar una lista de archivos o directorios que se excluirán del contexto de compilación. Por ejemplo, --exclude=tmp o --exclude=*.log.

--file ruta

El archivo a usar como Containerfile. Por defecto, es 'Containerfile' o 'Dockerfile' en el directorio raíz del contexto.

--force-rm

Elimina las capas intermedias después de la compilación, incluso si la compilación falla.

--format formato

El formato de imagen de salida. Los formatos válidos son docker, oci, oci-archive, docker-archive. El valor predeterminado es oci.

--from imagen

Especifica la imagen base para la compilación. Si no se especifica, se utilizará la primera imagen base definida en el Containerfile.

--gateway ip

Dirección IP del gateway predeterminado para la red del contenedor. Si no se especifica, Buildah utilizará la red predeterminada.

Especifica la URL del proxy HTTP a usar durante la compilación.

--https-proxy proxy

Especifica la URL del proxy HTTPS a usar durante la compilación.

--identity nombre

Opcionalmente, permite al usuario especificar un nombre para la imagen resultante. Esto puede ser útil para identificar compilaciones específicas o para mantener un registro de las imágenes creadas.

--iidfile ruta

Escribe el ID de la imagen en el archivo especificado.

Ruta a un archivo de caché de imagen para importar. Buildah utilizará este archivo como una fuente de caché para la compilación actual. Esto puede acelerar las compilaciones al reutilizar capas de imágenes existentes.

--isolation modo

Modo de aislamiento a usar para la compilación. Los modos válidos son chroot, copy-ளாக, overlay, ssh, userns. El valor predeterminado es chroot.

--jobs número

Número de trabajos paralelos que se ejecutarán durante la compilación. Por defecto, es 1.

Agrega una etiqueta de imagen (por ejemplo, etiqueta=valor) a los metadatos de la imagen. Se puede usar varias veces.

Guarda cada instrucción del Containerfile como una capa separada en la imagen. Esto puede hacer que las imágenes sean más pequeñas y más fáciles de gestionar.

Dirección del agente de metadatos para la compilación.

Límite de memoria para el contenedor de compilación. Por ejemplo, '1g' o '512m'.

Reserva de memoria para el contenedor de compilación. Por ejemplo, '1g' o '512m'.

Modo de red para el contenedor de compilación. Los modos válidos son bridge, host, none, container:name. El valor predeterminado es bridge.

--no-cache

No utilice la caché de capas durante la compilación.

--no-hosts

No agregue el archivo /etc/hosts predeterminado al contenedor.

--os="SO"

Establece el SO de la imagen a construir, y el de la imagen base a descargar, si la compilación utiliza una, al valor proporcionado en lugar de usar el SO del host. (Ejemplos: linux, windows)

--output ruta

Escribe la imagen resultante en la ruta especificada. Si no se especifica, la imagen se guarda en el almacén de imágenes de Buildah.

--output-oci

Formato de salida OCI. Equivalente a --format oci.

--platform plataforma

Especifica la plataforma de destino para la compilación. La plataforma debe tener el formato 'os/arquitectura[/variante]', por ejemplo, 'linux/amd64', 'linux/arm64'.

--progress-bar

Muestra una barra de progreso durante la compilación.

--pull

Intenta descargar las imágenes base especificadas en el Containerfile antes de iniciar la compilación. Si una imagen base ya existe localmente, no se descargará.

Intenta descargar las imágenes base especificadas en el Containerfile incluso si ya existen localmente.

--quiet, -q

Suprime la salida informativa de la compilación.

--registry nombre

Especifica el nombre del registro que se utilizará para descargar imágenes base y subir imágenes compiladas. Si no se especifica, se utiliza el registro predeterminado.

--remap-usr from:to

Remapea los IDs de usuario (UID) y grupo (GID) del contenedor. Esto es útil cuando se ejecutan contenedores como usuario no raíz en el host, pero se quiere que los archivos creados en el contenedor tengan propiedad de raíz. El formato es 'de:a', por ejemplo, '--remap-usr 0:1000' remapea el UID 0 (root) en el contenedor al UID 1000 en el host.

Elimina los contenedores intermedios después de la compilación.

Elimina los contenedores intermedios después de la compilación, incluso si la compilación falla.

--runtime ruta

Ruta del tiempo de ejecución del contenedor a usar. Por defecto, es 'runc'.

--security-opt opción

Opciones de seguridad para el contenedor de compilación.

--set-by-id

Establece el ID de la imagen por su ID de contenido. Útil para asegurar la reproducibilidad.

--shared-mounts

Permite que los montajes compartidos se utilicen en el contenedor de compilación.

--shell shell

El shell a usar para ejecutar comandos en el contenedor. Por defecto, es '/bin/sh'.

--signature-policy ruta

Ruta de un archivo de política de firma. Buildah utilizará este archivo para verificar las firmas de las imágenes descargadas.

--stdin

Establece la variante de la imagen a construir, y la de la imagen base a descargar, si la compilación utiliza una, al valor proporcionado en lugar de usar la variante del host. (Ejemplos: v7, v8)

EJEMPLOS

Construir una imagen desde el directorio actual y etiquetarla como 'myimage:latest':

buildah build -t myimage:latest .

Construir una imagen desde un repositorio Git y etiquetarla como 'myrepo:v1.0':

buildah build -t myrepo:v1.0 https://github.com/example/myrepo.git

Construir una imagen desde un archivo tar remoto y etiquetarla como 'webserver:latest':

buildah build -t webserver:latest https://example.com/webserver.tar.gz

Construir una imagen utilizando un Dockerfile específico en un directorio diferente y etiquetarla como 'customapp:dev':

buildah build -f ./app/Dockerfile -t customapp:dev ./app

Construir una imagen especificando argumentos de compilación:

buildah build --build-arg VERSION=1.2.3 -t myapp:1.2.3 .

Construir una imagen especificando un contexto de compilación adicional y copiando archivos desde él:

buildah build --build-context configs=../configs -t myapp:latest .
# En el Containerfile:
COPY --from=configs /app/config.yaml /etc/myapp/config.yaml

Construir una imagen sin usar la caché:

buildah build --no-cache -t myimage:latest .

Construir una imagen y guardarla como un archivo OCI:

buildah build --format oci -o /tmp/myimage.tar .

Construir una imagen para una plataforma específica:

buildah build --platform linux/arm64 -t myimage:arm64 .

Nota: La opción --cache-from de Buildah está diseñada de manera diferente a la opción --cache-from de Docker y BuildKit. El mecanismo de caché distribuida de Buildah extrae las imágenes intermedias del registro remoto por sí mismo, a diferencia de Docker y BuildKit donde la imagen intermedia se almacena en la imagen misma. El enfoque de Buildah es similar al de kaniko, el cual no infla el tamaño de la imagen original con imágenes intermedias. Además, las imágenes intermedias pueden mantenerse verdaderamente distribuidas en uno o más registros remotos usando el mecanismo de caché de Buildah.

Por defecto, los volúmenes montados vinculadamente (bind mounted) son privados. Eso significa que cualquier montaje realizado dentro del contenedor no será visible en el host y viceversa. Este comportamiento se puede cambiando especificando una propiedad de propagación del montaje del

Cuando la política de propagación del montaje se establece en shared (compartido), cualquier montaje completado dentro del contenedor en ese volumen será visible tanto para el host como para el contenedor. Cuando la política de propagación del montaje se establece en slave (esclavo), se habilita la propagación de montaje unidireccional y cualquier montaje completado en el host para ese volumen será visible solo dentro del contenedor. Para controlar la propiedad de propagación del montaje del volumen, use la bandera de propagación :[r]shared, :[r]slave o :[r]private. La propiedad de propagación solo puede especificarse para volúmenes montados vinculadamente y no para volúmenes internos o volúmenes con nombre. Para que la propagación del montaje funcione en el punto de montaje de origen (el punto de montaje donde se monta el directorio de origen), este debe tener las propiedades de propagación correctas.
