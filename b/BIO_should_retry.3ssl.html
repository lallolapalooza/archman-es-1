BIO_should_retry(3ssl)

Paquete: openssl

Licencias: Apache-2.0

BIO_SHOULD_RETRY(3ssl) OpenSSL BIO_SHOULD_RETRY(3ssl)

NOMBRE

BIO_should_read, BIO_should_write, BIO_should_io_special, BIO_retry_type, BIO_should_retry, BIO_get_retry_BIO, BIO_get_retry_reason, BIO_set_retry_reason - Funciones de reintento de BIO

SINOPSIS

#include <openssl/bio.h>
int BIO_should_read(BIO *b);
int BIO_should_write(BIO *b);
int BIO_should_io_special(iBIO *b);
int BIO_retry_type(BIO *b);
int BIO_should_retry(BIO *b);
BIO *BIO_get_retry_BIO(BIO *bio, int *reason);
int BIO_get_retry_reason(BIO *bio);
void BIO_set_retry_reason(BIO *bio, int reason);

DESCRIPCIÓN

Estas funciones determinan por qué un BIO no puede leer o escribir datos. Normalmente se llamarán después de una llamada fallida a BIO_read_ex() o BIO_write_ex() .

BIO_should_retry() es verdadera si la llamada que produjo esta condición debe reintentarse más tarde.

Si BIO_should_retry() es falsa, entonces la causa es una condición de error.

BIO_should_read() es verdadera si la causa de la condición es que el BIO no tiene suficientes datos para devolver. Compruebe la legibilidad y/o reintente la última operación.

BIO_should_write() es verdadera si la causa de la condición es que el BIO tiene datos pendientes por escribir. Compruebe la escribibilidad y/o reintente la última operación.

BIO_should_io_special() es verdadera si alguna condición "especial", es decir, una razón distinta de la lectura o la escritura, es la causa de la condición.

BIO_retry_type() devuelve una máscara de la causa de una condición de reintento que consiste en los valores BIO_FLAGS_READ, BIO_FLAGS_WRITE, BIO_FLAGS_IO_SPECIAL aunque los tipos de BIO actuales solo establecerán uno de estos.

BIO_get_retry_BIO() determina la razón precisa de la condición especial, devuelve el BIO que causó esta condición y si reason no es NULL, contiene el código de razón. El significado del código de razón y la acción que debe tomarse depende del tipo de BIO que resultó en esta condición.

BIO_get_retry_reason() devuelve la razón de una condición especial si se le pasa el BIO relevante, por ejemplo, el devuelto por BIO_get_retry_BIO().

BIO_set_retry_reason() establece la razón de reintento para una condición especial para un BIO dado. Normalmente esto solo sería llamado por implementaciones de BIO.

NOTAS

BIO_should_read(), BIO_should_write(), BIO_should_io_special(), BIO_retry_type(), y BIO_should_retry(), están implementados como macros.

Si BIO_should_retry() devuelve falso, entonces la "condición de error" precisa depende del tipo de BIO que la causó y del código de retorno de la operación del BIO. Por ejemplo, si una llamada a BIO_read_ex() en un BIO de socket devuelve 0 y BIO_should_retry() es falsa, entonces la causa será que la conexión se cerró. Una condición similar en un BIO de archivo significará que ha alcanzado EOF. Algunos tipos de BIO pueden colocar información adicional en la cola de errores. Para más detalles, consulte las páginas manuales de cada tipo de BIO.

Si la estructura de E/S subyacente está en modo bloqueante, casi todos los tipos de BIO actuales no solicitarán un reintento, porque las llamadas de E/S subyacentes no lo harán. Si la aplicación sabe que el tipo de BIO nunca señalará un reintento, entonces no necesita llamar a BIO_should_retry() después de una llamada de E/S de BIO fallida. Esto normalmente se hace con los BIO de archivo.

Los BIO de SSL son la única excepción actual a esta regla: pueden solicitar un reintento incluso si la estructura de E/S subyacente es bloqueante, si ocurre un handshake durante una llamada a BIO_read(). Una aplicación puede reintentar la llamada fallida inmediatamente o evitar esta situación estableciendo SSL_MODE_AUTO_RETRY en la estructura SSL subyacente.

Aunque una aplicación puede reintentar inmediatamente una llamada no bloqueante fallida, esto probablemente será muy ineficiente porque la llamada fallará repetidamente hasta que los datos puedan procesarse o estén disponibles. Una aplicación normalmente esperará hasta que la condición necesaria se satisfaga. Cómo se hace esto depende de la estructura de E/S subyacente.

Por ejemplo, si la causa es en última instancia un socket y BIO_should_read() es verdadera, se puede hacer una llamada a select() para esperar hasta que los datos estén disponibles y luego reintentar la operación del BIO. Al combinar las condiciones de reintento de varios BIO no bloqueantes en una sola llamada a select() es posible atender varios BIO en un solo hilo, aunque el rendimiento puede ser pobre si están presentes BIO de SSL porque pueden ocurrir largas demoras durante el proceso de handshake inicial.

Es posible que un BIO se bloquee indefinidamente si la estructura de E/S subyacente no puede procesar ni devolver ningún dato. Esto depende del comportamiento de las funciones de E/S de la plataforma. A menudo no es deseable: una solución es usar E/S no bloqueante y usar un tiempo de espera en la llamada a select() (o equivalente).

ERRORES

Las funciones ASN1 de OpenSSL no pueden manejar elegantemente la E/S no bloqueante: es decir, no pueden reintentar después de una lectura o escritura parcial. Esto generalmente se soluciona pasando solo los datos relevantes a las funciones ASN1 cuando la estructura completa puede leerse o escribirse.

VALORES DE RETORNO

BIO_should_read(), BIO_should_write(), BIO_should_io_special(), y BIO_should_retry() devuelven 1 o 0 basado en las condiciones reales del BIO.

BIO_retry_type() devuelve una combinación de banderas que presenta la causa de una condición de reintento o falso si no hay condición de reintento.

BIO_get_retry_BIO() devuelve una estructura BIO válida.

BIO_get_retry_reason() devuelve la razón de una condición especial.

VER TAMBIÉN

bio(7)

HISTORIA

Las funciones BIO_get_retry_reason() y BIO_set_retry_reason() se añadieron en OpenSSL 1.1.0.
