NOMBRE

buildah-from - Crea un nuevo contenedor de trabajo, ya sea desde cero o utilizando una imagen especificada como punto de partida.

SINOPSIS

buildah from [opciones] imagen

DESCRIPCIÓN

Crea un contenedor de trabajo basado en el nombre de imagen especificado. Si el nombre de imagen proporcionado es "scratch", se crea un nuevo contenedor vacío. Los nombres de imagen utilizan el formato "transportador":"detalles".

Se admiten múltiples transportadores:

dir:ruta
Un directorio local existente ruta que contiene el manifiesto, las archivos tar de capas y las firmas en archivos individuales. Este es un formato no estandarizado, útil principalmente para depuración o inspección no invasiva de imágenes.

docker://referencia-docker (Por defecto)
Una imagen en un registro que implementa la "API HTTP V2 del Registro de Docker". Por defecto, utiliza el estado de autorización en $XDG_RUNTIME_DIR/containers/auth.json, que se establece usando (buildah login). Consulte containers-auth.json(5) para obtener más información. Si el estado de autorización no se encuentra allí, se busca en $HOME/.docker/config.json, que se establece usando (docker login).
Si referencia-docker no incluye un nombre de registro, se consultará primero localhost, seguido de cualquier registro nombrado en la configuración de registros.

docker-archive:ruta
Una imagen se recupera como un archivo con formato de podman load.

docker-daemon:referencia-docker
Una imagen referencia-docker almacenada en el almacenamiento interno del demonio de docker. referencia-docker debe incluir una etiqueta o un digest. Alternativamente, al leer imágenes, el formato también puede ser docker-daemon:algo:digest (un ID de imagen).

oci:ruta:etiqueta**
Una etiqueta de imagen en un directorio compatible con la "Especificación de Diseño de Imágenes de Contenedores Abiertos" en ruta.

oci-archive:ruta:etiqueta
Una etiqueta de imagen etiqueta en un directorio compatible con la "Especificación de Diseño de Imágenes de Contenedores Abiertos" en ruta.

DEPENDENCIAS

Buildah resuelve la ruta al registro desde el cual extraer por medio del archivo /etc/containers/registries.conf, containers-registries.conf(5). Si el comando buildah from falla con un error de "imagen no conocida", primero verifique que el archivo registries.conf esté instalado y configurado apropiadamente.

VALOR DE RETORNO

El ID del contenedor que fue creado. En caso de error se retorna 1.

OPCIONES

--add-host=[]

Añade un mapeo personalizado de host a IP (host:ip)

Añade una línea a /etc/hosts. El formato es nombre de host:ip. La opción --add-host puede establecerse múltiples veces.

--arch="ARQUITECTURA"

Establece la ARQUITECTURA de la imagen a descargar al valor proporcionado en lugar de usar la arquitectura del host. (Ejemplos: arm, arm64, 386, amd64, ppc64le, s390x)

--authfile ruta

Ruta del archivo de autenticación. El valor por defecto es ${XDG_RUNTIME_DIR}/containers/auth.json. Consulte containers-auth.json(5) para más información. Este archivo se crea usando buildah login.

Si el estado de autorización no se encuentra allí, se busca en $HOME/.docker/config.json, que se establece usando docker login.

Nota: También puede anular la ruta por defecto del archivo de autenticación estableciendo la variable de entorno REGISTRY_AUTH_FILE. export REGISTRY_AUTH_FILE=ruta

--cap-add=CAP_xxx

Añade la capacidad especificada al conjunto por defecto de capacidades que se proporcionarán para las invocaciones posteriores de buildah run que utilicen este contenedor. Ciertas capacidades se conceden por defecto; esta opción se puede utilizar para añadir más.

--cap-drop=CAP_xxx

Elimina la capacidad especificada del conjunto por defecto de capacidades que se proporcionarán para las invocaciones posteriores de buildah run que utilicen este contenedor. Las capacidades CAP_CHOWN, CAP_DAC_OVERRIDE, CAP_FOWNER, CAP_FSETID, CAP_KILL, CAP_NET_BIND_SERVICE, CAP_SETFCAP, CAP_SETGID, CAP_SETPCAP y CAP_SETUID se conceden por defecto; esta opción se puede utilizar para eliminarlas. La lista de capacidades por defecto se gestiona en containers.conf(5).

Si una capacidad se especifica tanto para la opción --cap-add como para --cap-drop, se eliminará, independientemente del orden en que se dieron las opciones.

--cert-dir ruta

Utiliza los certificados en ruta (*.crt, *.cert, *.key) para conectarse al registro. El directorio de certificados por defecto es /etc/containers/certs.d.

--cgroup-parent=""

Ruta a los cgroups bajo los cuales se creará el cgroup para el contenedor. Si la ruta no es absoluta, la ruta se considera relativa a la ruta de cgroups del proceso init. Se crearán cgroups si no existen ya.

--cgroupns cómo

Establece la configuración para los namespaces IPC cuando el contenedor se utilice posteriormente para buildah run. El valor configurado puede ser "" (la cadena vacía) o "private" para indicar que se debe crear un nuevo namespace de cgroup, o puede ser "host" para indicar que se debe reutilizar el namespace de cgroup en el que se está ejecutando buildah.

--cidfile ArchivoIDContenedor

Escribe el ID del contenedor en el archivo.

--cpu-period=0

Limita el período CFS (Completely Fair Scheduler) de la CPU

Limita el uso de CPU del contenedor. Esta bandera le indica al kernel que restrinja el uso de CPU del contenedor al período que usted especifique.

--cpu-quota=0

Limita la cuota CFS (Completely Fair Scheduler) de la CPU

Limita el uso de CPU del contenedor. Por defecto, los contenedores se ejecutan con el recurso completo de CPU. Esta bandera le indica al kernel que restrinja el uso de CPU del contenedor a la cuota que usted especifique.

--cpu-shares, -c=0

Comparticiones de CPU (peso relativo)

Por defecto, todos los contenedores obtienen la misma proporción de ciclos de CPU. Esta proporción puede modificarse cambiando el peso de compartición de CPU del contenedor en relación con el peso de todos los demás contenedores en ejecución.

Para modificar la proporción respecto al valor por defecto de 1024, use la bandera --cpu-shares para establecer el peso a 2 o superior.

La proporción solo se aplicará cuando se estén ejecutando procesos que consuman mucha CPU. Cuando las tareas en un contenedor están inactivas, otros contenedores pueden utilizar el tiempo de CPU restante. La cantidad real de tiempo de CPU variará según el número de contenedores en ejecución en el sistema.

Por ejemplo, considere tres contenedores, uno tiene una cuota de CPU de 1024 y otros dos tienen una configuración de cuota de CPU de 512. Cuando los procesos en los tres contenedores intentan usar el 100% de la CPU, el primer contenedor recibiría el 50% del tiempo total de CPU. Si añade un cuarto contenedor con una cuota de CPU de 1024, el primer contenedor solo obtiene el 33% de la CPU. Los contenedores restantes reciben el 16.5%, 16.5% y 33% de la CPU.

En un sistema multinúcleo, las cuotas de tiempo de CPU se distribuyen entre todos los núcleos de CPU. Incluso si un contenedor está limitado a menos del 100% del tiempo de CPU, puede utilizar el 100% de cada núcleo de CPU individual.

Por ejemplo, considere un sistema con más de tres núcleos. Si inicia un contenedor {C0} con -c=512 ejecutando un proceso, y otro contenedor {C1} con -c=1024 ejecutando dos procesos, esto puede resultar en la siguiente división de cuotas de CPU:

PID    contenedor	CPU	CPU share
100    {C0}		0	100% de CPU0
101    {C1}		1	100% de CPU1
102    {C1}		2	100% de CPU2

CPUs en las que permitir la ejecución (0-3, 0,1)

--cpuset-mems=""

Nodos de memoria (MEMs) en los que permitir la ejecución (0-3, 0,1). Solo efectivo en sistemas NUMA.

Si tiene cuatro nodos de memoria en su sistema (0-3), use --cpuset-mems=0,1 entonces los procesos en su contenedor solo usarán memoria de los primeros dos nodos de memoria.
