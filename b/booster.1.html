NOMBRE

booster - generador rápido y seguro de initramfs

DESCRIPCIÓN

Booster es una herramienta para crear imágenes de initramfs necesarias en la etapa temprana del proceso de arranque de Linux. Booster está diseñado pensando en la velocidad y el caso de uso de cifrado completo de disco.

Ventajas de Booster:

  • Rápido tiempo de construcción de imágenes y rápido tiempo de arranque.
  • Soporte listo para usar para configuraciones de cifrado completo de disco basadas en LUKS.
  • Vinculación de datos estilo Clevis. El sistema de archivos cifrado se puede vincular a un chip TPM2 o a un servicio de red. Esto ayuda a desbloquear la unidad automáticamente, pero solo si el servicio TPM2/red está presente.
  • Detecta y desbloquea automáticamente el cifrado de partición de tipo systemd-cryptenroll (fido2 y tpm2).
  • Fácil de configurar.
  • Descubrimiento automático de configuración del host. Esto ayuda a crear imágenes minimalistas específicas para el host actual.

ARCHIVO DE CONFIGURACIÓN

El archivo de configuración del generador de booster se encuentra en /etc/booster.yaml. Aquí hay un archivo de configuración de ejemplo:

network:
  interfaces: enp0s31f2,2e:1d:61:30:a3:63
  dhcp: on
  # se puede usar dhcp arriba o configuración estática abajo
  ip: 10.0.2.15/24
  gateway: 10.0.2.255
  dns_servers: 192.168.1.1,8.8.8.8
universal: false
modules: -*,hid_apple,kernel/sound/usb/,kernel/fs/btrfs/btrfs.ko,kernel/lib/crc4.ko.xz
compression: zstd
mount_timeout: 5m6s
strip: true
extra_files: vim,/usr/share/vim/vim82/,fsck,fsck.ext4
vconsole: true
enable_lvm: true
enable_mdraid: true
  • El nodo network, si está presente, inicializa la red en el momento del arranque. Es necesario si el montaje de un sistema de archivos raíz requiere acceso a la red (por ejemplo, en caso de vinculación Tang). La red se puede configurar dinámicamente con DHCPv4 o estáticamente dentro de esta configuración. En el primer caso, dhcp se establece en on. En el segundo caso, la configuración permite especificar ip - la dirección IP de la máquina y su máscara de red, gateway - la puerta de enlace predeterminada, dns_servers - una lista separada por comas de servidores DNS. El nodo network también acepta la propiedad interfaces - una lista separada por comas de interfaces de red (especificadas con nombre o dirección MAC) para habilitar en el momento del arranque. Los nombres de red como enp0s31f6 se resuelven a direcciones MAC en el momento de la generación y luego se pasan a init. Si el nodo interfaces no se especifica, todas las interfaces se activan al arrancar.
  • universal es un indicador booleano que le dice a booster que genere una imagen universal. Por defecto, booster genera una imagen específica del host que incluye los módulos del kernel utilizados en el host actual. Por ejemplo, si el host no tiene un chip TPM2, se ignoran los módulos tpm. La imagen universal incluye muchos módulos del kernel y herramientas que podrían ser necesarios en una amplia gama de configuraciones de hardware.
  • modules es una lista separada por comas de módulos adicionales para agregar o eliminar de la imagen generada. Se puede usar un nombre de módulo o una ruta relativa al directorio de módulos (/usr/lib/modules/$KERNEL_VERSION). El sufijo del algoritmo de compresión (por ejemplo, ".xz", ".gz) se puede omitir del nombre del archivo del módulo. Si el elemento comienza con un signo menos (-), significa "no lo agregues a la imagen", de lo contrario, los módulos se agregan. Si la ruta termina con un símbolo de barra (/) , se considera un directorio y todos los módulos de este directorio deben agregarse recursivamente. Un símbolo especial * (asterisco) significa todos los módulos. Se puede usar, por ejemplo, para agregar todos los módulos o eliminar todos los módulos predefinidos de la imagen. Booster también tiene en cuenta las dependencias de los módulos; todas las dependencias de los módulos especificados se agregarán a la imagen.
  • modules_force_load lista de nombres de módulos que se cargan forzadamente durante el proceso de arranque antes de cambiar al espacio de usuario. Cualquier módulo en esta lista se agrega automáticamente a la imagen, por lo que no es necesario duplicarlo en la propiedad modules.
  • append_all_modaliases es un indicador booleano que instruye a booster a agregar todos los alias de módulos del host a la imagen de booster. Este indicador es útil para depurar problemas de tiempo de espera de arranque cuando faltan módulos importantes en la imagen. Establecer el indicador en true ayudará a imprimir los nombres de los módulos para los alias que fueron solicitados por el kernel pero faltaban en la imagen.
  • compression es un indicador que especifica la compresión para el archivo initramfs de salida. Actualmente, los algoritmos admitidos son "zstd", "gzip", "xz", "lz4", "none". Si no se especifica ninguna opción, se usa "zstd" como compresión predeterminada.
  • mount_timeout tiempo de espera para que aparezca el sistema de archivos raíz. El formato del campo es un número decimal y luego una unidad. Las unidades válidas son "s", "m", "h". Si no se especifica ningún valor, se usa el tiempo de espera predeterminado (3 minutos). Para deshabilitar completamente el tiempo de espera, especifique "0s".
  • strip es un indicador booleano que habilita la eliminación de archivos ELF antes de agregarlos a la imagen. Los binarios, las bibliotecas compartidas y los módulos del kernel son ejemplos de archivos ELF que se procesan con la utilidad UNIX strip.
Esta opción no es compatible con módulos firmados. Si ve un error de arranque como booster: finit(crc32,generic): la clave fue rechazada por el servicio, establezca la opción de configuración strip en false.
  • extra_files es una lista separada por comas de archivos adicionales para agregar a la imagen. Si un elemento comienza con una barra ("/"), se considera una ruta absoluta. De lo contrario, es una ruta relativa a /usr/bin. Si el elemento es un directorio, su contenido se agrega recursivamente. Hay algunos casos especiales:
  • agregar busybox a la imagen habilita un shell de emergencia en caso de pánico durante el proceso de arranque.
  • agregar fsck habilita la verificación del sistema de archivos al arrancar. También requiere que se agregue a la imagen el binario específico del sistema de archivos llamado fsck.$rootfstype. Los sistemas de archivos se corrigen automáticamente y si falla, el arranque se detiene y es responsabilidad del usuario corregir el sistema de archivos raíz.
  • vconsole es un indicador que habilita la configuración temprana de la consola del usuario. Si se establece en true, booster lee la configuración de /etc/vconsole.conf y /etc/locale.conf y agrega el mapa de teclas y las fuentes requeridas a la imagen generada. Se tienen en cuenta las siguientes propiedades de configuración: KEYMAP, KEYMAP_TOGGLE, FONT, FONT_MAP, FONT_UNIMAP. Consulte también el manual de vconsole.conf https://man.archlinux.org/man/vconsole.conf.5.en.
  • enable_lvm es un indicador que habilita el ensamblaje de volúmenes LVM en el momento del arranque. Este indicador también asegura que se agreguen todos los módulos/binarios necesarios a la imagen.
  • enable_mdraid es un indicador que habilita el ensamblaje de MdRaid en el momento del arranque. Este indicador también asegura que se agreguen todos los módulos/binarios necesarios a la imagen.
  • enable_zfs es un indicador que habilita el sistema de archivos ZFS como sistema de archivos raíz. Este indicador también asegura que se agreguen todos los módulos/binarios necesarios a la imagen. Tenga en cuenta que si ZFS está habilitado, se debe usar la opción de arranque zfs= en lugar de la opción de arranque root=.

Una vez que haya terminado de modificar su archivo de configuración y quiera regenerar las imágenes de booster en /boot, use /usr/lib/booster/regenerate_images. Es un script de conveniencia que realiza el mismo tipo de regeneración de imágenes que si hubiera instalado booster con su administrador de paquetes.

    PARÁMETROS DEL KERNEL PARA EL TIEMPO DE ARRANQUE

    Algunas partes de la funcionalidad de arranque de booster pueden modificarse con parámetros de arranque del kernel. Estos parámetros suelen establecerse a través de la configuración del cargador de arranque. Booster boot utiliza los siguientes parámetros del kernel:

    • root=$deviceref referencia al dispositivo del dispositivo raíz. Vea las notas a continuación sobre cómo especificar la referencia al dispositivo. Si root= apunta a una partición LUKS, entonces se desbloquea automáticamente como un dispositivo /dev/mapper/root y se monta como raíz. Booster también soporta el autodescubrimiento de la partición raíz https://systemd.io/DISCOVERABLE_PARTITIONS/ - si no se especifica el parámetro root= entonces booster busca particiones con un tipo GPT específico y la usa para montar como raíz.
    • rootfstype=$TIPO (p. ej. rootfstype=ext4). Por defecto, booster intenta detectar el tipo de sistema de archivos raíz. Pero si la autodetección no funciona, entonces este parámetro del kernel es útil. Por favor, también presente un ticket para que podamos mejorar el código que detecta los tipos de archivo.
    • rootflags=$OPCIONES opciones de montaje para el sistema de archivos raíz, p. ej. rootflags=user_xattr,nobarrier. En el modo de autodescubrimiento de particiones se tiene en cuenta el atributo GPT 60 ("solo lectura").
    • rd.luks.uuid=$UUID UUID de la partición LUKS donde está encerrada la partición raíz. booster intentará desbloquear este dispositivo LUKS.
    • rd.luks.name=$UUID=$NOMBRE similar al parámetro rd.luks.uuid pero también especifica el nombre utilizado para la apertura del dispositivo LUKS.
    • rd.luks.key=$UUID=$RUTA ruta absoluta a un archivo de clave en el initrd/initramfs que puede usarse para desbloquear el dispositivo identificado por UUID; si este archivo no existe o falla al desbloquearlo, se recurrirá a una solicitud de contraseña.
    • rd.luks.options=opt1,opt2 una lista separada por comas de indicadores LUKS. Las opciones soportadas son discard, same-cpu-crypt, submit-from-crypt-cpus, no-read-workqueue, no-write-workqueue. Tenga en cuenta que booster también soporta indicadores persistentes de LUKS v2 almacenados con los metadatos de la partición. Cualquier opción de línea de comandos se añade encima de los indicadores persistentes.
    • rd.modules_force_load una lista separada por comas de módulos del kernel adicionales que deben cargarse forzadamente.
    • resume=$deviceref referencia al dispositivo de suspensión en disco.
    • zfs=$pool/$dataset especifica qué conjunto de datos de ZFS debe usarse para la partición raíz. Esta opción solo se usa si la opción de configuración ZFS está habilitada. Si el sistema de archivos ZFS está habilitado, entonces el parámetro de arranque root= se ignora.
    • booster.log configura el registro de inicialización de booster. Acepta una lista separada por comas de los siguientes valores:
    Uno de los valores de nivel (de más a menos detallado) - debug, info, warning, error. Si no se especifica el nivel, se usa info por defecto.
    console - imprime los registros de inicialización de booster en la consola.
    El registro de depuración también se imprime en el búfer kmsg del kernel y está disponible para leerse con dmesg o con journalctl -b. Si el nivel de depuración está habilitado, el limitador de kmsg se desactiva automáticamente.
    • booster.debug una opción obsoleta que es equivalente a booster.log=debug,console.
    • quiet Establece la verbosidad de la inicialización de booster al mínimo. Esta opción se ignora si booster.debug o booster.log está establecido.
    • init=$RUTA ruta al binario de init de espacio de usuario. Si no se especifica, se usa el valor predeterminado /sbin/init .

    NOTAS

    Referencia al dispositivo

    La referencia al dispositivo es una forma de especificar un dispositivo o partición en los parámetros del kernel. Está etiquetada como $deviceref arriba. La referencia al dispositivo tiene uno de los siguientes valores:

    • /dev/XXX ruta a un archivo de dispositivo específico, puede ser una ruta a un dispositivo/partición real como /dev/sda1, /dev/nvme0n1 o una ruta a un dispositivo virtual dm-mapper como /dev/mapper/root o /dev/vg_mesos/lv_mesos_containers.
    • UUID=$UUID o /dev/disk/by-uuid/$UUID referencia al dispositivo por su UUID de sistema de archivos/LUKS. Vea las notas sobre las reglas de formato de UUID a continuación.
    • LABEL=$ETIQUETA o /dev/disk/by-label/$ETIQUETA referencia al dispositivo por su etiqueta de sistema de archivos/LUKS.
    • PARTUUID=$UUID o /dev/disk/by-partuuid/$UUID referencia al dispositivo por el UUID de la partición GPT.
    • PARTUUID=$UUID/PARTNROFF=$DESPLAZAMIENTO referencia al dispositivo por $DESPLAZAMIENTO desde una partición GPT especificada por $UUID, p. ej. PARTUUID=fd59d06d-ffa8-473b-94f0-6584cb2b6665/PARTNROFF=2.
    • PARTLABEL=$ETIQUETA o /dev/disk/by-partlabel/$ETIQUETA referencia al dispositivo por la etiqueta de la partición GPT.
    • HWPATH=$RUTA o /dev/disk/by-path/$RUTA referencia al dispositivo por una ruta de hardware determinista, p. ej. pci-0000:02:00.0-nvme-1-part2.
    • WWID=$ID o /dev/disk/by-id/$ID referencia al dispositivo por su wwid, p. ej. nvme-KXG6AZNV256G_TOSHIBA_40SA13GZF6B1-part3

    Parámetros UUID

    Parámetros de arranque como root=UUID=$UUID y rd.luks.uuid=$UUID le permiten especificar el dispositivo de bloqueo por su UUID. El formato del UUID es xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx donde x es un símbolo hexadecimal en minúscula o mayúscula. El parámetro UUID puede opcionalmente encerrarse con el símbolo de comillas " aunque no se recomienda. Los siguientes ejemplos muestran el formato correcto de los parámetros: root=UUID=ac8299a8-91ce-4bf6-a524-55a62844b787, root=UUID="ac8299a8-91ce-4bf6-a524-55a62844b787" (no recomendado), rd.luks.uuid=ac8299a8-91ce-4bf6-a524-55a62844b787, rd.luks.uuid="ac8299a8-91ce-4bf6-a524-55a62844b787" (no recomendado).

    Selección de módulos

    Esta es una nota para resumir el algoritmo que calcula qué módulos terminarán en la imagen de booster generada. La lista inicial de módulos para booster es defaultModulesList - un conjunto de módulos predefinidos codificados en generator.go. Estos son módulos seleccionados que probablemente cubren la mayoría de las necesidades de arranque del sistema - disco, sistema de archivos, teclado, tpm, ethernet, controladores usb.

    Si la opción de configuración universal está establecida en false (valor predeterminado) entonces se utiliza el llamado modo host. Es decir, la imagen se genera con los controladores necesarios solo para el hardware del host actual. Para lograrlo, booster obtiene todos los módulos actualmente cargados de /sys/module/ y calcula la intersección con defaultModulesList.

    Luego booster mira la opción de configuración modules , una lista separada por comas de elementos. Itera sobre todos los elementos de izquierda a derecha. La regla de filtrado del modo host no se aplica a esta lista de módulos especificados manualmente.

    Si el elemento comienza con el signo menos - entonces elimina los módulos dados de la imagen, de lo contrario los módulos se añaden a la imagen.

    Si el elemento es un nombre de módulo, entonces este módulo se añade/elimina. Tenga en cuenta que por convención el nombre de un módulo del kernel puede calcularse a partir de su nombre de archivo reemplazando todos los guiones por guiones bajos, p. ej. para el módulo hid-apple.ko.gz el nombre será hid_apple.

    Si el elemento es una ruta al archivo del módulo relativa a /usr/lib/modules/$KERNEL_VERSION entonces el módulo se añade/elimina. Tenga en cuenta que el sufijo del algoritmo de compresión puede omitirse del nombre de archivo del módulo.

    Si el elemento termina con el símbolo de barra / entonces este elemento se considera un directorio relativo a /usr/lib/modules/$KERNEL_VERSION. Booster recorre este directorio recursivamente y añade/elimina los módulos a la imagen. El signo menos puede usarse con los directorios.

    El símbolo de asterisco * es un atajo para "todos los módulos", puede usarse para añadir todos los módulos o eliminar todos los módulos de la imagen.

    A continuación, booster pasa a la opción modules_force_load que consiste en nombres de módulos para cargar en el momento del arranque. Todos estos módulos también se añaden a la imagen.

    En el paso final, booster calcula los grafos de dependencias entre módulos y todas las dependencias requeridas. Por ejemplo, si un usuario añadió manualmente ext4 y el sistema de compilación del kernel dice que el módulo ext requiere mbcache y jbd2 entonces tanto mbcache como jbd2 se añaden automáticamente a la imagen.

    Imagen de kernel unificada

    Una Imagen de kernel unificada https://uapi-group.org/specifications/specs/unified_kernel_image/ (UKI) es un binario PE que agrupa varios componentes de arranque (p. ej. kernel, initrd y un stub de arranque UEFI) como un solo ejecutable. Esto permite arrancar directamente a través del firmware (UEFI) así como autenticar todos los componentes de arranque a la vez para Secure Boot.

    Para generar UKIs en Booster, por favor instale el generador UKI de systemd (systemd-ukify) desde el gestor de paquetes de su distribución y use /usr/lib/booster/regenerate_uki. Es un script de conveniencia que realiza el mismo tipo de regeneración de imagen que si instalara booster con su gestor de paquetes, luego pasa el resultado al generador UKI de systemd (ukify) como entrada. El script solo pasa un subconjunto de componentes de arranque,

    Unified Kernel Image

    Booster can also create a Unified Kernel Image (UKI) that contains all necessary components to boot, namely the system's microcode(s), initrd, os-release file, boot splash image and kernel. Kernel command-line entries of the UKI are inherited from /etc/booster.yaml.

    Please note that to boot the UKI by default, it may be necessary to configure your system's boot loader configuration file(s) accordingly.

    DEBUGGING

    If you have a problem with booster boot tool you can enable debug mode to get more information about what is going on. Just add booster.log=debug,console kernel parameter and booster provide additional logs.

    Usar TFTP para descargar registros de dispositivos no arrancables

    In case of a boot failure, when the devices are missing, logs can still be retrieved from busybox using the network. First, set up a tftp server (port 69) on another machine/VM. For example on Archlinux, pacman -S atftp; systemctl start atftpd. Then, edit /etc/booster.yaml and add network support and busybox (extra_files: busybox). Regenerate the initramfs and reboot. Once inside busybox, get the logs and send them to the tftp server:

    $ dmesg >boot.log
$ lsmod >mods.log
$ tftp -pl boot.log <server ip>
$ tftp -pl mods.log <server ip>

    The logs will be in /srv/atftp on the server.

    Tiempo de espera de arranque

    If you got booster: Timeout waiting for root filesystem error please add append_all_modaliases config flag and rebuild the image. With this flag you'll get a list of modules that were requested by the kernel but absent in the booster image. Some of these modules might be required to boot your system.

    EJEMPLOS

    Create an initramfs file specific for the current kernel/host. The output file is booster.img:

    $ booster build booster.img

    Create an universal image with many modules (such as SATA/TPM/NVME/... drivers) included:

    $ booster build --universal booster.img

    Create an initramfs for kernel version 5.4.91-1-lts and copy it to /boot/booster-lts.img:

    $ booster build --kernel-version 5.4.91-1-lts /boot/booster-lts.img

    Here is a systemd-boot configuration stored at /boot/loader/entries/booster.conf. In this example e122d09e-87a9-4b35-83f7-2592ef40cefa is a UUID for the LUKS partition and 08684949-bcbb-47bb-1c17-089aaa59e17e is a UUID for the encrypted filesystem (e.g. ext4). Please refer to your bootloader documentation for more info about its configuration.

    title Linux with Booster
linux /vmlinuz-linux
initrd /booster-linux.img
options rd.luks.uuid=e122d09e-87a9-4b35-83f7-2592ef40cefa root=UUID=08684949-bcbb-47bb-1c17-089aaa59e17e rw

    Users of the Btrfs filesystem with a system installed on a subvolume should add rootflags corresponding to their entry in /etc/fstab. In this example 69bc4dd2-7f6c-4821-aa6b-d80d9c97d470 is a UUID for Btrfs partition, with the system installed on subvolume called root and /etc/fstab looks like this:

    UUID=69bc4dd2-7f6c-4821-aa6b-d80d9c97d470	/         	btrfs     	rw,relatime,autodefrag,compress=zstd:2,space_cache,subvol=root	0 0

    So /boot/loader/entries/booster.conf should looks like this:

    title Linux with Booster
linux /vmlinuz-linux
initrd /booster-linux.img
options root=UUID=69bc4dd2-7f6c-4821-aa6b-d80d9c97d470 rw rootflags=relatime,autodefrag,compress=zstd:2,space_cache,subvol=root

    Create a Unified Kernel Image and write the result to /boot/EFI/Linux:

    $ /usr/lib/booster/regenerate_uki build /boot/EFI/Linux
