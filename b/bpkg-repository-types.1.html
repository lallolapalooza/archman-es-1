NOMBRE

bpkg-repository-types - tipos de repositorio, estructura y URLs

DESCRIPCIÓN

Este tema de ayuda describe los tipos de repositorio reconocidos por bpkg, su estructura y el formato de sus URLs. Actualmente se soportan tres tipos de repositorios: pkg basado en archivos, dir basado en directorios y git basado en control de versiones.

La ubicación del repositorio puede especificar el tipo de repositorio como parte del componente de esquema de la URL en el formato tipo+protocolo. Por ejemplo:

git+https://example.com/foo
dir+file:///tmp/repo

Tenga en cuenta que la especificación explícita solo es necesaria cuando el tipo correcto no se puede inferir de la URL. Consulte bpkg-rep-add(1) para obtener detalles.

REPOSITORIOS PKG

Un repositorio pkg está basado en archivos. Es decir, contiene una colección de varios paquetes/versiones como archivos. Para más información sobre la estructura de los repositorios pkg, consulte el Manual del Gestor de Paquetes build2. La ubicación del repositorio pkg puede ser una ruta de directorio local o una URL http(s)://.

REPOSITORIOS DIR

Un repositorio dir está basado en directorios. Es decir, contiene una colección de varios paquetes como directorios, pero solo una versión por paquete puede estar presente en dicho repositorio. La ubicación del repositorio dir puede ser una ruta de directorio local o una URL file://.

Se espera que un repositorio dir contenga el archivo manifest o packages.manifest en el directorio raíz del repositorio. Si solo contiene manifest, entonces se asume que es un repositorio simple de un solo paquete con el archivo manifest siendo su manifiesto de paquete. De lo contrario, el archivo packages.manifest debe listar las ubicaciones de los paquetes disponibles, como se describe en Manifiesto de Lista de Paquetes para Repositorios dir (#manifest-package-list-dir).

Un repositorio dir también puede contener el archivo repositories.manifest en el directorio raíz del repositorio. Este archivo se puede usar para describir el repositorio en sí mismo, así como para especificar sus repositorios prerrequisito y complementarios. Consulte Manifiesto de Lista de Repositorios (#manifest-repository-list) para obtener detalles sobre el formato y la semántica de este archivo.

REPOSITORIOS GIT

Un repositorio git está basado en control de versiones. Es decir, normalmente contiene múltiples versiones del mismo paquete (pero también puede contener varios paquetes, generalmente relacionados, en el mismo repositorio).

Un repositorio git tiene la misma estructura y archivos de manifiesto que el repositorio dir. Consulte Manifiesto de Lista de Paquetes para Repositorios dir (#manifest-package-list-dir) y Manifiesto de Lista de Repositorios (#manifest-repository-list) para obtener detalles sobre su formato y semántica.

Teóricamente, un repositorio git puede contener tantas versiones de paquetes como commits existan. Sin embargo, en la práctica, normalmente solo estamos interesados en un pequeño subconjunto de ellos, mientras que la obtención y el procesamiento de información para todos ellos podría ser prohibitivamente costoso. Como resultado, por defecto, solo las etiquetas anunciadas en el formato refs/tags/v* donde la parte después de v también es una versión estándar válida (#module-version) se consideran fuentes de versiones de paquetes útiles. Estos commits normalmente corresponden a versiones lanzadas y se denominan el conjunto por defecto. Tenga en cuenta que solo se considera la última revisión de cada versión.

En lugar del conjunto por defecto, es posible proporcionar un conjunto personalizado de versiones disponibles especificando uno o más identificadores de commit y/o referencias y/o patrones de referencias en el fragmento de la URL del repositorio (consulte git-ls-remote(1) para obtener detalles sobre referencias anunciadas). Por ejemplo:

https://example.com/foo.git#v1.2.3
https://example.com/foo.git#master
https://example.com/foo.git#af234f56
https://example.com/foo.git#tags/releases/*
https://example.com/foo.git#HEAD,tags/v1.*.*,heads/feature-*

Además, es posible expandir (o reducir) el conjunto por defecto utilizando la notación especial de fragmento ##. Por ejemplo:

https://example.com/foo.git##HEAD     - conjunto por defecto más HEAD
https://example.com/foo.git##heads/*  - conjunto por defecto más ramas
https://example.com/foo.git##-v1.*    - conjunto por defecto menos v1.*

Un fragmento de URL de repositorio git es una lista separada por comas de filtros de referencia en el siguiente formato:

[nombre_ref][@commit]

Se debe especificar nombre_ref, commit, o ambos. Si se especifican ambos, entonces nombre_ref solo se usa para minimizar la cantidad de datos que se obtienen y se espera que commit pertenezca a su historial. Por ejemplo:

.../foo.git#master@48fba3625d65941bb85a39061bcf795d4949c778

La parte nombre_ref puede ser un identificador de commit abreviado o una referencia anunciada o un patrón de referencia bajo refs/. Mientras que commit debe ser el SHA1 completo de 40 caracteres que no necesariamente tiene que ser anunciado. Para mayor comodidad, se asume que un filtro de 40 caracteres que consiste solo en dígitos hexadecimales es commit, incluso si no está prefijado con @. En el improbable caso de que esto produzca un resultado incorrecto, se puede usar la forma @ con commit omitido. Por ejemplo:

.../foo.git#48fba3625d65941bb85a39061bcf795d4949c778   (id de commit)
.../foo.git#deadbeefdeadbeefdeadbeefdeadbeefdeadbeef@  (referencia)

La parte nombre_ref puede usar los caracteres comodín * y ? con la semántica estándar, así como la secuencia de caracteres ** que coincide en subdirectorios, recursivamente. Por ejemplo:

.../foo.git#tags/v*    - tags/v1.2.3 pero no tags/old/v0.1.0
.../foo.git#tags/v**   - tags/v1.2.3 y tags/old/v0.1.0

Una nombre_ref relativa se busca en refs/, refs/tags/ y refs/heads/, así como entre referencias simbólicas como HEAD. Para anclarla a refs/, hazla absoluta, por ejemplo:

.../foo.git#tags/v*   - refs/tags/v1.2.3 pero también refs/heads/tags/voo
.../foo.git#/tags/v*  - solo refs/tags/v1.2.3

Mientras que se permite que un patrón nombre_ref no coincida con ninguna referencia, una no-patrón que no se resuelve a una referencia es inválida.

Si un nombre_ref comienza con un guion (-), entonces se trata como un filtro de exclusión: cualquier referencia que coincida se excluye del conjunto incluido por los filtros precedentes (o el conjunto por defecto). Por ejemplo:

.../foo.git#v*,-v1.*  - excluir v1.* de v*
.../foo.git##-v1.*    - excluir v1.* del conjunto por defecto

Para admitir la especificación de un guion inicial literal, un nombre_ref que comience con un signo más (+) se trata como un filtro de inclusión. Por ejemplo:

.../foo.git#+x   - incluir x
.../foo.git#+-x  - incluir -x
.../foo.git#++x  - incluir +x

Los protocolos git actualmente soportados son git://, ssh:// (pero no la sintaxis de pseudo-URL scp), http:// y https:// para repositorios remotos y file:// para repositorios locales. Mientras que bpkg intenta minimizar la cantidad de información (historial) obtenida, no siempre es posible para algunos protocolos y/o configuraciones de servidor, como se discute a continuación.

Un repositorio git accesible a través de http(s):// puede usar el protocolo dumb o smart (consulte la documentación de git para obtener detalles). El protocolo dumb solo proporciona soporte limitado para la minimización de la obtención y, si se usa este protocolo, bpkg no tiene más opción que descargar una cantidad sustancial de historial.

El protocolo smart permite la obtención de historial mínimo para etiquetas y ramas. Si esto también es posible para (todos) los identificadores de commit depende de si el servidor está configurado para permitir la obtención de commits no anunciados. Para obtener detalles, consulte los valores de configuración de git uploadpack.allowReachableSHA1InWant y uploadpack.allowAnySHA1InWant.

Los protocolos git:// y ssh:// son similares a http:// smart en que admiten la obtención de historial mínimo para etiquetas y ramas y pueden admitir o no esto para identificadores de commit dependiendo de la configuración del servidor. Sin embargo, tenga en cuenta que, a diferencia de http(s)://, para estos protocolos bpkg no intenta detectar si se permite la obtención de commits no anunciados y siempre asume que no es así.
