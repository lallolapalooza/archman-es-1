programme du OBJ en tant que PATH. bpftool prog loadall épingle tous les programmes du OBJ sous le répertoire PATH. type est PATH. optionnel, s'il n'est pas spécifié le type de programme sera déduit des noms de sections. Par défaut bpftool créera de nouvelles maps comme déclarées dans l'objet ELF étant chargé. Le paramètre map permet la réutilisation de maps existantes. Il peut être spécifié plusieurs fois, chaque fois pour une map différente. IDX fait référence à l'index de la map à remplacer dans le fichier ELF en comptant à partir de 0, tandis que NAME permet de remplacer une map par son nom. MAP spécifie la map à utiliser, en faisant référence à elle par id ou via un fichier épinglé. Si offload_dev NAME est spécifié, le programme sera chargé sur le périphérique réseau donné (offload). Si xdpmeta_dev NAME est spécifié, le programme deviendra lié au périphérique sans offload, ce qui facilite l'accès aux métadonnées XDP. L'argument optionnel pinmaps peut être fourni pour épingler toutes les maps sous le répertoire MAP_DIR. Si autoattach est spécifié, le programme sera attaché

Si avant l'épinglage. Dans ce cas, seul le lien (représentant le programme attaché à son hook) est épinglé, pas le programme en tant que tel, donc le chemin n'apparaîtra pas dans bpftool prog show -f, mais seulement dans bpftool link show -f. De plus, cela ne fonctionne que lorsque bpftool (libbpf) est capable de déduire toutes les informations nécessaires depuis le fichier objet, en particulier, ce n'est pas pris en charge pour tous les types de programmes. Si un programme ne prend pas en charget autoattach, bpftool recurre al fijado regular para ese

programa.

La opción kernel_btf permite especificar un archivo BTF externo para reemplazar el archivo BTF vmlinux del propio sistema para las reubicaciones CO-RE. Tenga en cuenta que cualquier otra característica que dependa de BTF (como los programas fentry/fexit, struct_ops) requiere el archivo BTF para el kernel real que se está ejecutando en el host, a menudo expuesto en /sys/kernel/btf/vm

linux.

Nota: PATH debe estar ubicado en el punto de montaje bpffs. No debe contener un punto ('.'), que está reservado para futuras extensiones de bpf

f

bpftool prog attach PROG ATTACH_TYPE [MAP
]
Adjunta el programa bpf PROG (con el tipo especificado por ATTACH_TYPE). La mayoría de los ATTACH_TYPE requieren un parámetro MAP, con la excepción de flow_dissector, que se adjunta al espacio de nombres de red
actual.
bpftool prog detach PROG ATTACH_TYPE [MAP
]
Desadjunta el programa bpf PROG (con el tipo especificado por ATTACH_TYPE). La mayoría de los ATTACH_TYPE requieren un parámetro MAP, con la excepción de flow_dissector, que se desadjunta del espacio de nombres de red
actual.
bpftool prog
tracelog
Vuelca la tubería de seguimiento del sistema a la consola (stdout). Pulse <Ctrl+C> para dejar de imprimir. Los programas BPF pueden escribir en esta tubería de seguimiento en tiempo de ejecución con el auxiliar bpf_trace_printk(). Esto debe usarse solo con fines de depuración. Para transmitir datos de los programas BPF al espacio de usuario, se pueden usar eventos perf (véase también bpftool-map
(8)).
bpftool prog tracelog { stdout | stderr } PR
OG
Vuelca el flujo BPF del programa. Los programas BPF pueden escribir en estos flujos en tiempo de ejecución con la kfunc bpf_stream_vprintk(). El kernel puede escribir mensajes de error en el flujo de error estándar. Esta instalación debe usarse solo con fines de
depuración.
bpftool prog run PROG data_in FILE [data_out FILE [data_size_out L]] [ctx_in FILE [ctx_out FILE [ctx_size_out M]]] [repeat N
]
Ejecuta el programa BPF PROG en la infraestructura de pruebas del kernel para BPF, lo que significa que el programa trabaja con los datos y el contexto proporcionados por el usuario, y no con paquetes reales o funciones monitoreadas, etc. El valor de retorno y la duración de la ejecución de la prueba se imprimen en la consola.

Los datos de entrada se leen desde el FILE pasado con data_in. Si este FILE es "-", los datos de entrada se leen de la entrada estándar. El contexto de entrada, si lo hay, se lee desde el FILE pasado con ctx_in. Nuevamente, "-" puede usarse para leer de la entrada estándar, pero solo si la entrada estándar no se está usando ya para los datos de entrada. Si se pasa un FILE con data_out, los datos de salida se escriben en ese archivo. De manera similar, el contexto de salida se escribe en el FILE pasado con ctx_out. Para ambos flujos de salida, "-" puede usarse para imprimir en la salida estándar (como texto plano, o JSON si se pasó la opción correspondiente). Si se omiten las palabras clave de salida, los datos y el contexto de salida se descartan. Las palabras clave data_size_out y ctx_size_out se usan para pasar el tamaño (en bytes) de los búferes de salida al kernel, aunque el valor predeterminado de 32 kB debería ser más que suficiente para la mayoría de los

casos.

La palabra clave repeat se usa para indicar el número de ejecuciones consecutivas a realizar. Tenga en cuenta que los datos y el contexto de salida impresos en los archivos corresponden a la última de esas ejecuciones. La duración impresa al final de las ejecuciones es un promedio de todas las ejecuciones realizadas por el

comando.

No todos los tipos de programas admiten la ejecución de pruebas. Entre los que sí lo hacen, no todos pueden tomar los argumentos ctx_in/ctx_out. bpftool no realiza comp

robaciones sobre los
tipos de programas.
bpftool prog profile PROG [duration DURATION] METRI
Cs
Perfil METRICs para el programa bpf PROG durante DURATION segundos o hasta que el usuario pulse <Ctrl+C>. DURATION es opcional. Si DURATION no se especifica, el perfilado se ejecutará hasta UINT_MAX seg
undos.
