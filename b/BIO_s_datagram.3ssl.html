BIO_s_datagram(3ssl)

Paquete: openssl

Licencias: Apache-2.0

BIO_S_DATAGRAM(3ssl) OpenSSL BIO_S_DATAGRAM(3ssl)

NOMBRE

BIO_s_datagram, BIO_new_dgram, BIO_ctrl_dgram_connect, BIO_ctrl_set_connected, BIO_dgram_recv_timedout, BIO_dgram_send_timedout, BIO_dgram_get_peer, BIO_dgram_set_peer, BIO_dgram_detect_peer_addr, BIO_dgram_get_mtu_overhead - BIO de red con semántica de datagrama

SINOPSIS

#include <openssl/bio.h>
BIO_METHOD *BIO_s_datagram(void);
BIO *BIO_new_dgram(int fd, int close_flag);
int BIO_ctrl_dgram_connect(BIO *bio, const BIO_ADDR *peer);
int BIO_ctrl_set_connected(BIO *bio, const BIO_ADDR *peer);
int BIO_dgram_recv_timedout(BIO *bio);
int BIO_dgram_send_timedout(BIO *bio);
int BIO_dgram_get_peer(BIO *bio, BIO_ADDR *peer);
int BIO_dgram_set_peer(BIO *bio, const BIO_ADDR *peer);
int BIO_dgram_get_mtu_overhead(BIO *bio);
int BIO_dgram_detect_peer_addr(BIO *bio, BIO_ADDR *peer);

DESCRIPCIÓN

BIO_s_datagram() es una implementación de BIO diseñada para usarse con sockets de red que proporcionan semántica de datagrama, como los sockets UDP. Es adecuada para usarse con DTLSv1 o QUIC.

Debido a que BIO_s_datagram() tiene semántica de datagrama, una sola llamada a BIO_write() envía un solo datagrama y una sola llamada a BIO_read() recibe un solo datagrama. Si el tamaño del búfer pasado a BIO_read() es insuficiente, el datagrama se trunca silenciosamente.

Para un BIO basado en memoria que proporciona semántica de datagrama idéntica a la de BIO_s_datagram(), véase BIO_s_dgram_pair(3).

Este BIO admite las funciones BIO_sendmmsg(3) y BIO_recvmmsg(3) .

Al usar BIO_s_datagram(), es importante tener en cuenta lo siguiente:

  • Este BIO puede usarse con un socket de red conectado o no conectado. Un socket conectado es un socket de red al que se le ha llamado BIO_connect(3) o una función similar específica del sistema operativo. Un socket así solo puede recibir datagramas del par especificado. Cualquier otro socket es un socket no conectado y puede recibir datagramas de cualquier host.
  • A pesar de sus nombres, ni BIO_ctrl_dgram_connect() ni BIO_ctrl_set_connected() hacen que un socket se convierta en conectado. Estos controles se proporcionan para indicar al BIO cómo está configurado el socket subyacente y cómo debe usarse; véase más abajo.
  • El uso de BIO_s_datagram() con un socket de red no conectado es peligroso porque cualquier llamada exitosa a BIO_read() hace que la dirección del par utilizada para cualquier llamada posterior a BIO_write() se establezca en la dirección de origen del datagrama recibido por esa llamada a BIO_read(). Por lo tanto, a menos que el llamador invoque BIO_dgram_set_peer() inmediatamente antes de cada llamada a BIO_write(), o nunca llame a BIO_read(), cualquier host en la red puede hacer que los datagramas escritos en el futuro se redirijan a ese host. Por lo tanto, se recomienda que los usuarios usen BIO_s_dgram() solo con un socket conectado, o, si usan BIO_s_dgram() con un socket no conectado, usen solo los métodos BIO_sendmmsg(3) y BIO_recvmmsg(3) y renuncien al uso de BIO_read(3) y BIO_write(3). Una excepción es cuando se debe usar DTLSv1_listen(3) ; véase DTLSv1_listen(3) para una discusión más detallada.
  • A diferencia de BIO_read(3) y BIO_write(3), los métodos BIO_sendmmsg(3) y BIO_recvmmsg(3) son inmutables y no hacen que el estado interno de BIO_s_datagram() cambie.

Hay varios controles disponibles para configurar BIO_s_datagram() mediante BIO_ctrl(3):

BIO_ctrl_dgram_connect (BIO_CTRL_DGRAM_CONNECT)
Esto equivale a llamar a BIO_dgram_set_peer(3).

A pesar de su nombre, esta función no hace que el socket subyacente se convierta en conectado.

BIO_ctrl_set_connected (BIO_CTRL_SET_CONNECTED)
Esto informa a BIO_s_datagram() si el socket subyacente ha sido conectado y, por lo tanto, cómo BIO_s_datagram() debe intentar usar el socket.

Si el argumento peer no es NULL, BIO_s_datagram() asume que el socket subyacente ha sido conectado e intentará usar el socket mediante APIs del sistema operativo que no especifican direcciones de par (por ejemplo, send(3) y recv(3) o similares). El argumento peer debe especificar la dirección del par a la que está conectado el socket.

Si el argumento peer es NULL, BIO_s_datagram() asume que el socket subyacente no está conectado e intentará usar el socket mediante una API del sistema operativo que especifica direcciones de par (por ejemplo, sendto(3) y recvfrom(3)).

Este control no afecta la operación de BIO_sendmmsg(3) ni BIO_recvmmsg(3).

BIO_dgram_get_peer (BIO_CTRL_DGRAM_GET_PEER)
Esto produce un BIO_ADDR que especifica uno de los siguientes valores, el que haya ocurrido más recientemente:
  • La dirección del par pasada por última vez a BIO_dgram_set_peer(), BIO_ctrl_dgram_connect() o BIO_ctrl_set_connected().
  • La dirección del par del datagrama recibido por última vez por una llamada a BIO_read().
BIO_dgram_set_peer (BIO_CTRL_DGRAM_SET_PEER)
Establece la dirección del par que se usará para las escrituras posteriores en este BIO.

Advertencia: Cuando se usa con un socket de red no conectado, el valor establecido puede ser modificado por llamadas futuras a BIO_read(3), lo que hace que el uso de BIO_s_datagram() sea peligroso cuando se usa con sockets de red no conectados; véase más arriba.

Esto no afecta la operación de BIO_sendmmsg(3). BIO_recvmmsg(3) no afecta el valor establecido por BIO_dgram_set_peer().

BIO_dgram_detect_peer_addr (BIO_CTRL_DGRAM_DETECT_PEER_ADDR)
Esto es similar a BIO_dgram_get_peer() excepto que si la dirección del par no ha sido establecida en el objeto BIO, se intentará una llamada al sistema operativo como getpeername(2) para intentar autodetectar la dirección del par a la que está conectado el socket subyacente. Otros BIOs también pueden implementar este control si son capaces de detectar una dirección de par, sin necesidad de implementar también BIO_dgram_set_peer() y BIO_dgram_get_peer().
BIO_dgram_recv_timeout (BIO_CTRL_DGRAM_GET_RECV_TIMER_EXP)
Devuelve 1 si la última operación de E/S realizada en el BIO (por ejemplo, mediante una llamada a BIO_read(3)) pudo haber sido causada por un tiempo de espera de recepción.
BIO_dgram_send_timedout (BIO_CTRL_DGRAM_GET_SEND_TIMER_EXP)
Devuelve 1 si la última operación de E/S realizada en el BIO (por ejemplo, mediante una llamada a BIO_write(3)) pudo haber sido causada por un tiempo de espera de envío.
BIO_dgram_get_mtu_overhead (BIO_CTRL_DGRAM_GET_MTU_OVERHEAD)
Devuelve una cantidad en bytes que es una estimación aproximada del número de bytes de sobrecarga que normalmente deberían añadirse a un tamaño de carga útil de datagrama para estimar el tamaño final del paquete de Capa 3 (p. ej., IP) que contendrá el datagrama. En la mayoría de los casos, el tamaño máximo de carga útil de datagrama que puede transmitirse puede determinarse determinando el MTU del enlace en bytes y restando el valor devuelto por esta llamada.

El valor devuelto por esta llamada depende del protocolo de la capa de red que se esté usando.

El valor devuelto no es totalmente fiable porque las sobrecargas de datagrama puedenigher en configuraciones de red atípicas, por ejemplo donde se usan cabeceras de extensión IPv6 u opciones IPv4.

BIO_CTRL_DGRAM_SET_DONT_FRAG
Si num es distinto de cero, configura el socket de red subyacente para habilitar el modo Don't Fragment, en el cual los datagramas se establecerán con el bit Don't Fragment (DF) de IP activado. Si num es cero, el modo Don't Fragment se deshabilita.
BIO_CTRL_DGRAM_QUERY_MTU
Consulta al SO su evaluación de la Ruta MTU (Path MTU) para el destino al que apunta el socket de red subyacente, y devuelve esa Ruta MTU en bytes. Este control solo puede usarse con un socket conectado.

Esto no está soportado en todas las plataformas y depende de que el SO lo soporte. Devuelve 0 en caso de fallo.

BIO_CTRL_DGRAM_MTU_DISCOVER
Este control solicita que se habilite el descubrimiento de Ruta MTU (Path MTU discovery) en el socket de red subyacente.
BIO_CTRL_DGRAM_GET_FALLBACK_MTU
Devuelve el tamaño mínimo estimado de la carga útil del datagrama que siempre debería ser soportado por el BIO. Este tamaño está determinado por la MTU mínima requerida para ser soportada por la capa de red subyacente aplicable. El uso de datagramas de este tamaño puede llevar a un rendimiento subóptimo, pero deberían ser enrutables en todas las circunstancias. El valor devuelto es el tamaño de la carga útil del datagrama en bytes y no incluye el tamaño de las cabeceras de los protocolos de capa 3 o capa 4.
BIO_CTRL_DGRAM_MTU_EXCEEDED
Devuelve 1 si la última escritura intentada en el BIO falló debido a que el tamaño de la escritura intentada excedió la MTU aplicable.
BIO_CTRL_DGRAM_SET_NEXT_TIMEOUT
Acepta un puntero a un struct timeval. Si el tiempo especificado es cero, deshabilita los tiempos de espera de recepción. En caso contrario, configura el intervalo de tiempo especificado como el tiempo de espera de recepción para el socket con el propósito de futuras BIO_read(3) llamadas.
BIO_CTRL_DGRAM_SET_PEEK_MODE
Si num es distinto de cero, habilita el modo peek; en caso contrario, deshabilita el modo peek. Donde el modo peek está habilitado, las llamadas a BIO_read(3) leen datagramas del socket de red subyacente en modo peek, lo que significa que una llamada futura a BIO_read(3) producirá el mismo datagrama hasta que el modo peek sea deshabilitado.

BIO_recvmmsg(3) no se ve afectado por este control.

BIO_new_dgram() es una función auxiliar que instancia un BIO_s_datagram() y establece el BIO para usar el socket dado en fd llamando a BIO_set_fd().

VALORES DE RETORNO

BIO_s_datagram() devuelve un método BIO.

BIO_new_dgram() devuelve un BIO en caso de éxito y NULL en caso de fallo.

BIO_ctrl_dgram_connect(), BIO_ctrl_set_connected() y BIO_dgram_set_peer() devuelven 1 en caso de éxito y 0 en caso de fallo.

BIO_dgram_get_peer() y BIO_dgram_detect_peer_addr() devuelven 0 en caso de fallo y el número de bytes para la representación de la dirección emitida (un valor positivo) en caso de éxito.

BIO_dgram_recv_timedout() y BIO_dgram_send_timedout() devuelven 0 o 1 dependiendo de la circunstancia; véase la discusión anterior.

BIO_dgram_get_mtu_overhead() devuelve un valor en bytes.
