TAP::Parser(3perl) Guía de Referencia del Programador de Perl TAP::Parser(3perl)

NOMBRE

TAP::Parser - Analizar salida TAP

VERSIÓN

Versión 3.50

SINOPSIS

use TAP::Parser;
my $parser = TAP::Parser->new( { source => $source } );
while ( my $result = $parser->next ) {
    print $result->as_string;
}

DESCRIPCIÓN

"TAP::Parser" está diseñado para producir un análisis adecuado de la salida TAP. Para un ejemplo de cómo ejecutar pruebas a través de este módulo, consulte los sencillos marcos en "examples/".

Hay una wiki dedicada al Protocolo de Prueba de Cualquier Cosa (TAP):

http://testanything.org

Incluye el Cookbook de TAP::Parser:

http://testanything.org/testing-with-tap/perl/tap::parser-cookbook.html

MÉTODOS

Métodos de Clase

"new"

my $parser = TAP::Parser->new(\%args);

Devuelve un nuevo objeto "TAP::Parser".

Los argumentos deben ser un hashref con *uno* de las siguientes claves:

  • "source"

    CAMBIADO en 3.18

    Este es el método preferido para pasar la entrada al constructor.

    El "source" se utiliza para crear un TAP::Parser::Source que se pasa a "iterator_factory_class", que a su vez determina cómo manejar la fuente y crea un <TAP::Parser::Iterator> para ella. El iterador es utilizado por el analizador para leer el flujo TAP.

    Para configurar el *IteratorFactory*, use el parámetro "sources" a continuación.

    Tenga en cuenta que "source", "tap" y "exec" son *mutuamente exclusivos*.

  • "tap"

    CAMBIADO en 3.18

    El valor debe ser la salida TAP completa.

    El *tap* se utiliza para crear un TAP::Parser::Source que se pasa a "iterator_factory_class", que a su vez determina cómo manejar la fuente y crea un <TAP::Parser::Iterator> para ella. El iterador es utilizado por el analizador para leer el flujo TAP.

    Para configurar el *IteratorFactory*, use el parámetro "sources" a continuación.

    Tenga en cuenta que "source", "tap" y "exec" son *mutuamente exclusivos*.

  • "exec"

    Debe pasarse una referencia a un array.

    La referencia al array *exec* se utiliza para crear un TAP::Parser::Source que se pasa a "iterator_factory_class", que a su vez determina cómo manejar la fuente y crea un <TAP::Parser::Iterator> para ella. El iterador es utilizado por el analizador para leer el flujo TAP.

    Por defecto, la clase TAP::Parser::SourceHandler::Executable creará un objeto TAP::Parser::Iterator::Process para manejar la fuente. Esto pasa las cadenas de referencia del array como argumentos de comando a IPC::Open3::open3:

    exec => [ '/usr/bin/ruby', 't/my_test.rb' ]

    Si se dan argumentos de prueba ("test_args"), se agregarán al final de la lista de argumentos del comando.

    Para configurar el *IteratorFactory*, use el parámetro "sources" a continuación.

    Tenga en cuenta que "source", "tap" y "exec" son *mutuamente exclusivos*.

Las siguientes claves son opcionales.

  • "sources"

    NUEVO en 3.18.

    Si se establece, "sources" debe ser un hashref que contenga los nombres de los TAP::Parser::SourceHandlers a cargar y/o configurar. Los valores son un hash de configuración que estará accesible para los manejadores de origen a través de "config_for" en TAP::Parser::Source.

    Por ejemplo:

    sources => {
  Perl => { exec => '/path/to/custom/perl' },
  File => { extensions => [ '.tap', '.txt' ] },
  MyCustom => { some => 'config' },
}

    Esto hará que "TAP::Parser" pase una configuración personalizada a dos de los manejadores de origen incorporados - TAP::Parser::SourceHandler::Perl, TAP::Parser::SourceHandler::File - e intentará cargar la clase "MyCustom". Vea "load_handlers" en TAP::Parser::IteratorFactory para más detalles.

    El parámetro "sources" afecta a cómo se manejan los parámetros "source", "tap" y "exec".

    Vea TAP::Parser::IteratorFactory, TAP::Parser::SourceHandler y sus subclases para más detalles.

  • "callback"

    Si está presente, cada callback correspondiente a un tipo de resultado dado será llamado con el resultado como argumento si se usa el método "run":

    my %callbacks = (
    test    => \&test_callback,
    plan    => \&plan_callback,
    comment => \&comment_callback,
    bailout => \&bailout_callback,
    unknown => \&unknown_callback,
);
my $aggregator = TAP::Parser::Aggregator->new;
for my $file ( @test_files ) {
    my $parser = TAP::Parser->new(
        {
            source    => $file,
            callbacks => \%callbacks,
        }
    );
    $parser->run;
    $aggregator->add( $file, $parser );
}
  • "switches"

    Si se utiliza un archivo Perl como fuente, se pueden pasar interruptores opcionales que se utilizarán al invocar el ejecutable de Perl.

    my $parser = TAP::Parser->new( {
    source   => $test_file,
    switches => [ '-Ilib' ],
} );
  • "test_args"

    Se utiliza junto con la opción "source" y "exec" para proporcionar una referencia a un array de argumentos estilo @ARGV para pasar al programa de prueba.

  • "spool"

    Si se pasa un manejador de archivo, escribirá una copia de todo el TAP analizado en ese manejador.

  • "merge"

    Si es falso, STDERR no se captura (aunque se 'retransmite' para mantenerlo algo sincronizado con STDOUT.)

    Si es verdadero, STDERR y STDOUT son el mismo manejador de archivo. Esto puede causar problemas si STDERR contiene algo que se parezca al formato TAP, pero permite una sincronización exacta.

    Las sutilezas de este comportamiento pueden depender de la plataforma y pueden cambiar en el futuro.

  • "grammar_class"

    Esta opción se introdujo para permitirle personalizar fácilmente qué clase de *gramática* debe usar el analizador. Por defecto es TAP::Parser::Grammar.

    Vea también "make_grammar".

  • "result_factory_class"

    Esta opción se introdujo para permitirle personalizar fácilmente qué clase de *fábrica de resultados* debe usar el analizador. Por defecto es TAP::Parser::ResultFactory.

    Vea también "make_result".

  • "iterator_factory_class"

    CAMBIADO en 3.18

    Esta opción se introdujo para permitirle personalizar fácilmente qué clase de *fábrica de iteradores* debe usar el analizador. Por defecto es TAP::Parser::IteratorFactory.

Métodos de Instancia

"next"

NAME

TAP::Parser - parse Test Anything Protocol

SYNOPSIS

use TAP::Parser;

# from a file
my $parser = TAP::Parser->new( { source => $file } );

# from a string
my $parser = TAP::Parser->new( { source => $string } );

# from a filehandle
my $parser = TAP::Parser->new( { source => $fh } );

# from a glob
my $parser = TAP::Parser->new( { source => qr/^t\/\S+\.t$/ } );

# from a glob that doesn't contain perl
my $parser = TAP::Parser->new( { source => qr/^t\/\S+\.t$/, language => 'plain' } );

# get results one at a time
while ( my $result = $parser->next ) {
    print $result->as_string, "\n";
}

# get all results at once
my @results = $parser->all_tap;

# run the tests and bail on failure
$parser->run;

# custom grammar class
my $parser = TAP::Parser->new( {
    source        => $file,
    grammar_class => 'My::Grammar',
} );

# custom result factory
my $parser = TAP::Parser->new( {
    source              => $file,
    result_factory_class=> 'My::ResultFactory',
} );

# custom iterator factory
my $parser = TAP::Parser->new( {
    source                => $file,
    iterator_factory_class=> 'My::IteratorFactory',
} );

DESCRIPTION

This module is a parser for the Test Anything Protocol (TAP). It can parse TAP output from a file, a string, or a filehandle.

The TAP::Parser takes care of the TAP protocol details, letting you concentrate on the results of your tests.

It works by spitting out individual result objects as it parses them. You can get these one at a time using the "next" method, or all at once using the "all_tap" method.

See the TAP::Parser::Result documentation for more information on how to use the result objects.

For information on TAP itself, please refer to the TAP specification:

  • http://www.testanything.org/wiki/index.php/Spec+v12

METHODS

"new"

my $parser = TAP::Parser->new( $args );

Returns a new TAP::Parser object.

The $args argument is a hashref of options:

source
This is the most important argument. It can be a string (which will be treated as a file path), a filehandle, a glob, or a string containing TAP data. If it's a string representing a file path, the parser will open and read from that file. If it's a filehandle, it will read from that. If it's a glob (a regular expression), it will find all files matching the glob and parse them all. If it's just a string, it will be treated as the TAP data itself.
language
This option specifies the language of the TAP. It can be "perl" (the default) or "plain". This affects how the parser handles certain constructs, like pragmas.
callback
A coderef which will be called with each result object as it is parsed. Note that this is called for every result, including comments and unknown lines.
merge
A boolean value. If true, TAP::Parser will attempt to merge STDERR into STDOUT. This is useful for capturing comments that are printed to STDERR instead of STDOUT.
encoding
Specifies the character encoding of the input TAP. Defaults to UTF-8.
diagnostics
A boolean value. If true, the parser will attempt to parse diagnostic information (like YAML or basic key/value pairs) that might be associated with test failures.
grammar_class
Allows you to specify a custom grammar class. Defaults to TAP::Parser::Grammar.
result_factory_class
Allows you to specify a custom result factory class. Defaults to TAP::Parser::ResultFactory.
iterator_factory_class
Allows you to specify a custom iterator factory class. Defaults to TAP::Parser::IteratorFactory.

"next"

my $result = $parser->next;

This method returns the results of the parsing, one result at a time. Note that it is destructive. You can't rewind and examine previous results.

If callbacks are used, they will be issued before this call returns.

Each result returned is a subclass of TAP::Parser::Result. See that module and related classes for more information on how to use them.

"run"

$parser->run;

This method merely runs the parser and parses all of the TAP.

"make_grammar"

Make a new TAP::Parser::Grammar object and return it. Passes through any arguments given.

The "grammar_class" can be customized, as described in "new".

"make_result"

Make a new TAP::Parser::Result object using the parser's TAP::Parser::ResultFactory, and return it. Passes through any arguments given.

The "result_factory_class" can be customized, as described in "new".

"make_iterator_factory"

NEW to 3.18.

Make a new TAP::Parser::IteratorFactory object and return it. Passes through any arguments given.

"iterator_factory_class" can be customized, as described in "new".

INDIVIDUAL RESULTS

If you've read this far in the docs, you've seen this:

while ( my $result = $parser->next ) {
    print $result->as_string;
}

Each result returned is a TAP::Parser::Result subclass, referred to as result types.

Result types

Basically, you fetch individual results from the TAP. The six types, with examples of each, are as follows:

  • Version 
    TAP version 12
  • Plan 
    1..42
  • Pragma 
    pragma +strict
  • Test 
    ok 3 - We should start with some foobar!
  • Comment 
    # Hope we don't use up the foobar.
  • Bailout 
    Bail out!  We ran out of foobar!
  • Unknown 
    ... yo, this ain't TAP! ...

Each result fetched is a result object of a different type. There are common methods to each result object and different types may have methods unique to their type. Sometimes a type method may be overridden in a subclass, but its use is guaranteed to be identical.

Common type methods

"type"

Returns the type of result, such as "comment" or "test".

"as_string"

Prints a string representation of the token. This might not be the exact output, however. Tests will have test numbers added if not present, TODO and SKIP directives will be capitalized and, in general, things will be cleaned up. If you need the original text for the token, see the "raw" method.

"raw"

Returns the original line of text which was parsed.

"is_plan"

Indicates whether or not this is the test plan line.

"is_test"

Indicates whether or not this is a test line.

"is_comment"

Indicates whether or not this is a comment. Comments will generally only appear in the TAP stream if STDERR is merged to STDOUT. See the "merge" option.

"is_bailout"

Indicates whether or not this is bailout line.

"is_yaml"

Indicates whether or not the current item is a YAML block.

"is_unknown"

Indicates whether or not the current line could be parsed.

"is_ok"

if ( $result->is_ok ) { ... }

Reports whether or not a given result has passed. Anything which is not a test result returns true. This is merely provided as a convenient shortcut which allows you to do this:

my $parser = TAP::Parser->new( { source => $source } );
while ( my $result = $parser->next ) {
    # only print failing results
    print $result->as_string unless $result->is_ok;
}

"plan" methods

if ( $result->is_plan ) { ... }

If the above evaluates as true, the following methods will be available on the $result object.

"plan"

if ( $result->is_plan ) {
   print $result->plan;
}

This is merely a synonym for "as_string".

"directive"

my $directive = $result->directive;

If a SKIP directive is included with the plan, this method will return it.

1..0 # SKIP: why bother?

"explanation"

my $explanation = $result->explanation;

If a SKIP directive was included with the plan, this method will return the explanation, if any.

"pragma" methods

if ( $result->is_pragma ) { ... }

If the above evaluates as true, the following methods will be available on the $result object.

"pragmas"

Returns a list of pragmas each of which is a + or - followed by the pragma name.

"comment" methods

if ( $result->is_comment ) { ... }

If the above evaluates as true, the following methods will be available on the $result object.

"comment"

if ( $result->is_comment ) {
    my $comment = $result->comment;
    print "I have something to say:  $comment";
}

"bailout" methods

if ( $result->is_bailout ) { ... }

If the above evaluates as true, the following methods will be available on the $result object.

"explanation"

if ( $result->is_bailout ) {
    my $explanation = $result->explanation;
    print "We bailed out because ($explanation)";
}

If, and only if, a token is a bailout token, you can get an "explanation" via this method. The explanation is the text after the mystical "Bail out!" words which appear in the tap output.

"unknown" methods

if ( $result->is_unknown ) { ... }

There are no unique methods for unknown results.

"test" methods

if ( $result->is_test ) { ... }

If the above evaluates as true, the following methods will be available on the $result object.

"ok"

my $ok = $result->ok;

Returns the literal text of the "ok" or "not ok" status.

"number"

my $test_number = $result->number;

Returns the number of the test, even if the original TAP output did not supply that number.

"description"

my $description = $result->description;

Returns the description of the test, if any. This is the portion after the test number but before the directive.

"directive"

my $directive = $result->directive;

Returns either "TODO" or "SKIP" if either directive was present for a test line.

"explanation"

my $explanation = $result->explanation;

If a test had either a "TODO" or "SKIP" directive, this method will return the accompanying explanation, if present.

not ok 17 - 'Pigs can fly' # TODO not enough acid

For the above line, the explanation is not enough acid.

"is_ok"

if ( $result->is_ok ) { ... }

Returns a boolean value indicating whether or not the test passed. Remember that for TODO tests, the test always passes.

Note: this was formerly "passed". The latter method is deprecated and will issue a warning.

"is_actual_ok"

if ( $result->is_actual_ok ) { ... }

Returns a boolean value indicating whether or not the test passed, regardless of its TODO status.

Note: this was formerly "actual_passed". The latter method is deprecated and will issue a warning.

TAP METHODS

This module provides a large number of methods for examining the results of a test run.

Individual Test Results

"is_unplanned"

if ( $test->is_unplanned ) { ... }

If a test number is greater than the number of planned tests, this method will return true. Unplanned tests will always return false for "is_ok", regardless of whether or not the test "has_todo" (see TAP::Parser::Result::Test for more information about this).

"has_skip"

if ( $result->has_skip ) { ... }

Returns a boolean value indicating whether or not this test had a SKIP directive.

"has_todo"

if ( $result->has_todo ) { ... }

Returns a boolean value indicating whether or not this test had a TODO directive.

Note that TODO tests always pass. If you need to know whether or not they really passed, check the "is_actual_ok" method.

"in_todo"

if ( $parser->in_todo ) { ... }

True while the most recent result was a TODO. Becomes true before the TODO result is returned and stays true until just before the next non- TODO test is returned.

TOTAL RESULTS

After parsing the TAP, there are many methods available to let you dig through the results and determine what is meaningful to you.

Individual Results

These results refer to individual tests which are run.

"passed"

my @passed = $parser->passed; # the test numbers which passed
my $passed = $parser->passed; # the number of tests which passed

This method lets you know which (or how many) tests passed. If a test failed but had a TODO directive, it will be counted as a passed test.

"failed"

my @failed = $parser->failed; # the test numbers which failed
my $failed = $parser->failed; # the number of tests which failed

This method lets you know which (or how many) tests failed. If a test passed but had a TODO directive, it will NOT be counted as a failed test.

"actual_passed"

# the test numbers which actually passed
my @actual_passed = $parser->actual_passed;
# the number of tests which actually passed
my $actual_passed = $parser->actual_passed;

This method lets you know which (or how many) tests actually passed, regardless of whether or not a TODO directive was found.

"actual_ok"

This method is a synonym for "actual_passed".

"actual_failed"

# the test numbers which actually failed
my @actual_failed = $parser->actual_failed;
# the number of tests which actually failed
my $actual_failed = $parser->actual_failed;

This method lets you know which (or how many) tests actually failed, regardless of whether or not a TODO directive was found.

"todo"

my @todo = $parser->todo; # the test numbers with todo directives
my $todo = $parser->todo; # the number of tests with todo directives

This method lets you know which (or how many) tests had TODO directives.

"todo_passed"

# the test numbers which unexpectedly succeeded
my @todo_passed = $parser->todo_passed;
# the number of tests which unexpectedly succeeded
my $todo_passed = $parser->todo_passed;

This method lets you know which (or how many) tests actually passed but were declared as "TODO" tests.

"todo_failed"

# deprecated in favor of 'todo_passed'.  This method was horribly misnamed.

This was a badly misnamed method. It indicates which TODO tests unexpectedly succeeded. Will now issue a warning and call "todo_passed".

"skipped"

my @skipped = $parser->skipped; # the test numbers with SKIP directives
my $skipped = $parser->skipped; # the number of tests with SKIP directives

This method lets you know which (or how many) tests had SKIP directives.

Pragmas

"pragma"

Get or set a pragma. To get the state of a pragma:

if ( $p->pragma('strict') ) {
    # be strict
}

To set the state of a pragma:

$p->pragma('strict', 1); # enable strict mode

"pragmas"

Get a list of all the currently enabled pragmas:

my @pragmas_enabled = $p->pragmas;

Summary Results

These results are "meta" information about the total results of an individual test program.

"plan"

my $plan = $parser->plan;

Returns the test plan, if found.

"good_plan"

Deprecated. Use "is_good_plan" instead.

"is_good_plan"

if ( $parser->is_good_plan ) { ... }

Returns a boolean value indicating whether or not the number of tests planned matches the number of tests run.

Note: this was formerly "good_plan". The latter method is deprecated and will issue a warning.

And since we're on that subject ...

"tests_planned"

print $parser->tests_planned;

Returns the number of tests planned, according to the plan. For example, a plan of '1..17' will mean that 17 tests were planned.

"tests_run"

print $parser->tests_run;

Returns the number of tests which actually were run. Hopefully this will match the number of "$parser->tests_planned".

"skip_all"

Returns a true value (actually the reason for skipping) if all tests were skipped.

"start_time"

Returns the wall-clock time when the Parser was created.

"end_time"

Returns the wall-clock time when the end of TAP input was seen.

"start_times"

Returns the CPU times (like "times" in perlfunc when the Parser was created.

"end_times"

Returns the CPU times (like "times" in perlfunc when the end of TAP input was seen.

"has_problems"

if ( $parser->has_problems ) {
    ...
}

This is a 'catch-all' method which returns true if any tests have currently failed, any TODO tests unexpectedly succeeded, or any parse errors occurred.

"version"

$parser->version;

Once the parser is done, this will return the version number for the parsed TAP. Version numbers were introduced with TAP version 13 so if no version number is found version 12 is assumed.

"exit"

$parser->exit;

Once the parser is done, this will return the exit status. If the parser ran an executable, it returns the exit status of the executable.

"wait"

$parser->wait;

Once the parser is done, this will return the wait status. If the parser ran an executable, it returns the wait status of the executable. Otherwise, this merely returns the "exit" status.

"ignore_exit"

$parser->ignore_exit(1);

Tell the parser to ignore the exit status from the test when determining whether the test passed. Normally tests with non-zero exit status are considered to have failed even if all individual tests passed. In cases where it is not possible to control the exit value of the test script use this option to ignore it.

"parse_errors"

my @errors = $parser->parse_errors; # the parser errors
my $errors = $parser->parse_errors; # the number of parser_errors

Fortunately, all TAP output is perfect. In the event that it is not, this method will return parser errors. Note that a junk line which the parser does not recognize is "not" an error. This allows this parser to handle future versions of TAP. The following are all TAP errors reported by the parser:

  • Misplaced plan

    The plan (for example, '1..5'), must only come at the beginning or end of the TAP output.

  • No plan

    Gotta have a plan!

  • More than one plan 
    1..3
ok 1 - input file opened
not ok 2 - first line of the input valid # todo some data
ok 3 read the rest of the file
1..3

    Right. Very funny. Don't do that.

  • Test numbers out of sequence 
    1..3
ok 1 - input file opened
not ok 2 - first line of the input valid # todo some data
ok 2 read the rest of the file

    That last test line above should have the number '3' instead of '2'.

    Note that it's perfectly acceptable for some lines to have test numbers and others to not have them. However, when a test number is found, it must be in sequence. The following is also an error:

    1..3
ok 1 - input file opened
not ok - first line of the input valid # todo some data
ok 2 read the rest of the file

    But this is not:

    1..3
ok  - input file opened
not ok - first line of the input valid # todo some data
ok 3 read the rest of the file

NAME

TAP::Parser - parse the Test Anything Protocol

VERSION

This document describes TAP::Parser version 3.42.

SYNOPSIS

    use TAP::Parser;
    my $parser = TAP::Parser->new(file => 't/test.pl');
    while (my $next = $parser->next) {
        # $next is a TAP::Base object (e.g. TAP::YAML, TAP::Directive, TAP::Plan)
        # See TAP::Parser::Result for details.
        if ($next->isa('TAP::Parser::Result::Test')) {
            if ($next->approved) {
                print "Test #", $next->index, " passed\n";
            } else {
                print "Test #", $next->index, " failed\n";
                print $next->diag, "\n" if $next->diag;
            }
        } elsif ($next->isa('TAP::Parser::Result::Plan')) {
            print "Found plan: ", $next->max, "\n";
        } elsif ($next->isa('TAP::Parser::Result::Comment')) {
            print "Comment: ", $next->value, "\n";
        }
    }
    my $summary = $parser->summary;
    print "Total tests: ", $summary->{tests}, "\n";
    print "Ok: ", $summary->{ok}, "\n";
    print "Not ok: ", $summary->{not_ok}, "\n";

DESCRIPTION

This module provides a pure Perl parser for the Test Anything Protocol (TAP). TAP is a simple text-based protocol for reporting the results of tests. TAP::Parser reads a stream of TAP text, parses it, and returns the results as objects.

TAP::Parser works by creating a TAP::Parser::Grammar object, which does the actual parsing. TAP::Parser::Grammar is responsible for breaking down the TAP stream into individual results.

The results are represented as objects derived from TAP::Base. The most common result type is TAP::Parser::Result::Test, which represents a single test case.

See TAP::Parser::Result for a list of all result types.

METHODS

Most of the functionality of TAP::Parser is exposed through its methods. The primary method is "next", which returns the next result object from the stream.

Other important methods include:

new
Creates a new TAP::Parser object.
    my $parser = TAP::Parser->new(file => 't/test.pl');
    my $parser = TAP::Parser->new(source => \*FILEHANDLE);
    my $parser = TAP::Parser->new(string => $tap_string);

The "new" method accepts the following arguments:

  • "file": The path to a file containing TAP output.
  • "source": A filehandle (or other IO::Handle object) containing TAP output.
  • "string": A string containing TAP output.
  • "grammar_class": The name of a class to use for parsing. Defaults to TAP::Parser::Grammar. See TAP::Parser::Grammar for details.
  • "arguments": A hash reference of arguments to pass to the grammar's constructor.
next
Reads the next result from the TAP stream and returns it as an object. Returns undef if the end of the stream is reached. This is the primary method for iterating through TAP results.
all_results
Reads all remaining results from the TAP stream and returns them as a list of objects.
summary
Returns a hash reference containing a summary of the test results. The hash contains the following keys:
    tests   - total number of tests run
    ok      - number of tests that passed
    not_ok  - number of tests that failed
plan
Returns the TAP::Parser::Result::Plan object for the stream, or undef if no plan was found.
diag
Returns a hash reference containing diagnostic information. The keys are the test indices, and the values are the diagnostic strings.
has_plan
Returns true if the TAP stream contains a plan, false otherwise.
has_failed
Returns true if any tests failed, false otherwise.
make_result
This method is called by the grammar to create result objects. You can override this method in a subclass to customize the result objects that are created.
make_grammar
This method is called by "new" to create the grammar object. You can override this method in a subclass to use a custom grammar class.

INDIVIDUAL RESULTS

TAP::Parser produces a variety of result objects, all of which inherit from TAP::Base. The most common types are:

  • TAP::Parser::Result::Test: Represents a single test. Contains methods like index, approved, directive, and diag.
  • TAP::Parser::Result::Plan: Represents the test plan. Contains methods like max (the number of tests) and directive.
  • TAP::Parser::Result::Comment: Represents a comment line. Contains a value method.
  • TAP::Parser::Result::Directive: Represents a directive line (e.g., TODO or SKIP). Contains a directive method.
  • TAP::Parser::Result::Bailout: Represents a bailout message. Contains a reason method.

See TAP::Parser::Result for a full list of result types and their methods.

TOTAL RESULTS

The "summary" method provides a convenient way to get an overview of the test results. It returns a hash with keys like "tests", "ok", and "not_ok".

CALLBACKS

TAP::Parser does not currently support callbacks. If you need callback-style processing, you should iterate through the results manually using the "next" method.

TAP GRAMMAR

TAP::Parser uses TAP::Parser::Grammar to tokenize the input stream and produce results. If you need to customize the parsing behavior, you should subclass TAP::Parser::Grammar and specify your subclass using the "grammar_class" parameter when creating a TAP::Parser object.

See TAP::Parser::Grammar for more details.

BACKWARDS COMPATIBILITY

TAP::Parser aims for backward compatibility with previous versions. However, changes may be introduced in minor releases. Always check the changeset for details.

SUBCLASSING

You can subclass TAP::Parser to customize its behavior. Common reasons for subclassing include:

  • Using a custom grammar class: Override the "make_grammar" method.
  • Customizing result object creation: Override the "make_result" method.

Custom Grammar

To use a custom grammar, subclass TAP::Parser::Grammar and set the "grammar_class" parameter in "new".

Example:

    package My::Custom::Grammar;
    use base 'TAP::Parser::Grammar';
    # ... custom grammar rules ...

    package My::Custom::Parser;
    use base 'TAP::Parser';

    sub make_grammar {
        my $self = shift;
        return My::Custom::Grammar->new(@_);
    }

    # OR, if your grammar class name is predictable:
    # sub grammar_class { 'My::Custom::Grammar' }

    # ... use My::Custom::Parser ...
    my $parser = My::Custom::Parser->new(file => 't/test.pl');

Custom Result Objects

If you need to customize the objects created by the parser, you can subclass TAP::Parser and override the "make_result" method.

Grammar

TAP::Parser::Grammar is the heart of the parser. It tokenizes the TAP input stream and produces results. If you need to customize its behaviour you should probably familiarize yourself with the source first. Enough lecturing.

Subclass TAP::Parser::Grammar and customize your parser by setting the "grammar_class" parameter. See "new" for more details.

If you need to customize the objects on creation, subclass TAP::Parser and override "make_grammar"
