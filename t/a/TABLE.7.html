NOMBRE

SELECT, TABLE, WITH - recuperar filas de una tabla o vista

DESCRIPCIÓN

SELECT recupera filas de una tabla o vista. El procesamiento general de SELECT se realiza de la siguiente manera:

1. Todas las consultas en la lista de WITH se computan. Estas efectivamente actúan como tablas temporales o vistas que pueden ser referenciadas en la lista de FROM. Una consulta de WITH que se refiera más de una vez en la lista de FROM se computa solo una vez, a menos que se especifique con NOT MATERIALIZED. (Ver la Cláusula WITH.)
2. Todos los elementos en la lista de FROM se computan. (Cada elemento en la lista de FROM es una tabla real o virtual.) Si se especifican más de un elemento en la lista de FROM, se unen entre sí. (Ver la Cláusula FROM.)
3. Si se especifica el cláusula WHERE, se eliminan de la salida las filas que no satisfacen la condición. (Ver la Cláusula WHERE.)
4. Si se especifica el cláusula GROUP BY, o si hay llamadas a funciones agrupadas, la salida se combina en grupos de filas que coincidan en uno o más valores, y los resultados de funciones agrupadas se computan. Si hay una cláusula HAVING, se eliminan los grupos que no satisfagan la condición dada. (Ver la Cláusula GROUP BY y HAVING.) Aunque las columnas de salida se computan de forma nominal en el siguiente paso, pueden también referirse (por nombre o número ordinal) en la cláusula GROUP BY.
5. Las filas de salida real se computan utilizando las expresiones de SELECT para cada fila seleccionada o grupo de filas. (Ver la Lista de SELECT.)
6. SELECT DISTINCT elimina filas duplicadas del resultado. SELECT DISTINCT ON elimina las filas que coincidan en todas las expresiones especificadas. SELECT ALL (por defecto) devuelve todas las filas candidatas, incluidas duplicadas. (Ver la Cláusula DISTINCT.)
7. Usando los operadores UNION, INTERSECT y EXCEPT, se puede combinar el resultado de múltiples consultas SELECT para formar un conjunto de resultados unico. El operador UNION devuelve todas las filas que están en uno o ambos de los resultados. El operador INTERSECT devuelve todas las filas que están strictamente en ambos resultados. El operador EXCEPT devuelve las filas que están en el primer resultado pero no en el segundo. En todos los casos, se eliminan filas duplicadas, a menos que ALL sea especificado. La palabra clave "DISTINCT" puede agregarse explícitamente para eliminar filas duplicadas. Nota que "DISTINCT" es el comportamiento predeterminado aquí, aunque "ALL" sea el comportamiento predeterminado para SELECT mismo. (Ver la Cláusula UNION, INTERSECT y EXCEPT.)
8. Si se especifica el cláusula ORDER BY, las filas devueltas se ordenan en el orden especificado. Si no se especifica el cláusula ORDER BY, se devuelven las filas en cualquier orden que el sistema encuentre más rápido. (Ver la Cláusula ORDER BY.)
9. Si se especifica el cláusula LIMIT (o FETCH FIRST) o OFFSET, la consulta SELECT solo devuelve una subconjunto de las filas de resultado. (Ver la Cláusula LIMIT.)
10. Si se especifica FOR UPDATE, FOR NO KEY UPDATE, FOR SHARE o FOR KEY SHARE, la consulta SELECT bloquea las filas seleccionadas contra actualizaciones concurrentes. (Ver la Cláusula de Bloqueo.)

Debes tener el privilegio de SELECT en cada columna utilizada en una consulta SELECT. La utilización de FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE o FOR KEY SHARE requiere el privilegio de UPDATE (al menos para una columna de cada tabla seleccionada).

PARÁMETROS

Cláusula WITH

La cláusula WITH permite especificar una o más consultas subyacentes que pueden ser referenciadas por nombre en la consulta principal. Las consultas subyacentes actúan efectivamente como tablas temporales o vistas durante el tiempo de la consulta principal. Cada consulta subyacente puede ser una SELECT, TABLE, VALUES, INSERT, UPDATE, DELETE o MERGE instrucción. Cuando se escribe una instrucción de modificación de datos (INSERT, UPDATE, DELETE, o MERGE) en WITH, suele incluirse una cláusula RETURNING. Es el resultado de RETURNING, y no el tabla subyacente que la instrucción modifica, lo que forma la tabla temporal que se lee por la consulta principal. Si no se omiten RETURNING, la instrucción aún se ejecuta, pero no produce salida, por lo que no puede ser referida como una tabla por la consulta principal.

Un nombre (sin especificación de esquema) debe especificarse para cada consulta de WITH. Opcionalmente, se pueden especificar una lista de nombres de columna; si este se omite, los nombres de columna se infieren de la consulta subyacente.

Si se especifica RECURSIVE, permite a una consulta SELECT subyacente referirse a sí misma por nombre. Esta consulta subyacente debe tener la forma:

non_recursive_term UNION [ ALL | DISTINCT ] recursive_term

donde la referencia a sí mismo recursiva debe aparecer en el lado derecho de la UNION. Solo se permite una referencia a sí mismo recursiva por consulta. Las consultas de modificación de datos no son admitidas, pero se pueden utilizar los resultados de una consulta SELECT recursiva en una instrucción de modificación de datos. Ver Sección 7.8 para un ejemplo.

Otro efecto de RECURSIVE es que las consultas de WITH no tienen que estar ordenadas: una consulta puede referirse a otra que aparezca más tarde en la lista. (Sin embargo, referencias circulares, o recursión mutua, no son implementadas.) Sin RECURSIVE, las consultas de WITH pueden referirse solo a consultas de WITH que sean hermanas y que aparezcan antes en la lista de WITH.

Cuando hay múltiples consultas en la cláusula WITH, RECURSIVE debe escribirse solo una vez, inmediatamente después de WITH. Aplica a todas las consultas de la cláusula WITH, aunque no tenga efecto en las consultas que no usen recursión o referencias hacia adelante.

La cláusula opcional SEARCH calcula una columna de secuencia de búsqueda que puede usarse para ordenar los resultados de una consulta recursiva en orden de profundidad o anchura. El nombre de la lista de columnas especifica la

El nombre de la lista de columnas especifica la forma en que se determinan las columnas de búsqueda. Si el argumento BREADTH FIRST es especificado, se realiza una búsqueda en anchura. Si DEPTH FIRST es especificado, se realiza una búsqueda en profundidad. Las búsquedas por anchura primero aplanan los resultados para un nivel antes de moverse al siguiente, mientras que las búsquedas por profundidad primero exploran ramas enteras antes de pasar a la siguiente.

Si se utiliza el argumento SET, entonces se deben proporcionar los nombres de las columnas de salida. Una columna debe ser especificada para el número de secuencia de búsqueda. Una segunda columna puede ser especificada para el valor de marca del ciclo (el valor de marca del ciclo predeterminado es 1, el otro valor de marca del ciclo es el valor especificado en TO, y el valor de marca del ciclo predeterminado es NULL). Una tercera columna puede ser especificada para el valor de la ruta del ciclo.

Si se especifica el argumento CYCLE, entonces la consulta detectará ciclos en los datos. Esto se usa a menudo en conjunción con los tipos de datos de grafos. El primer nombre de columna en la lista de columnas especifica la columna de búsqueda. Las siguientes dos columnas especifican el valor de marca del ciclo y el valor de marca predeterminado. La última columna especifica la ruta del ciclo.

Si se especifica MATERIALIZED, la consulta de WITH se computa y se almacena en una tabla temporal que luego es leída. Si se especifica NOT MATERIALIZED (la predeterminación), la consulta de WITH es evaluada cada vez que se le hace referencia. La elección entre MATERIALIZED y NOT MATERIALIZED puede tener efectos importantes en el rendimiento. Si una consulta de WITH es referenciada muchas veces, MATERIALIZED puede ser más rápido. Si es referenciada solo una vez, NOT MATERIALIZED suele ser más rápido.

Lista SELECT

La lista SELECT especifica las columnas que se recuperan de la consulta. El asterisco (*) puede ser usado para recuperar todas las columnas de la consulta. Si se utilizan múltiples tablas en la lista FROM, se puede usar un nombre de tabla o alias para especificar todas las columnas de esa tabla específica, como en *. Para especificar todas las columnas de todas las tablas, se usa * sin calificativos.

Cada expression puede ser una constante, una variable, una columna o una expresión que incluya las anteriores. La expresión se evalúa para cada fila (o grupo de filas, si se agrupa) y constituye la columna de salida. Se puede usar la palabra clave AS para asignar un nombre a la columna de salida. Si se omite un nombre, el sistema infiere uno.

Se puede usar el calificador DISTINCT para eliminar filas duplicadas de la salida. DISTINCT ON ( expression [, ...]) elimina las filas duplicadas basadas en el valor de las expresiones especificadas. El DISTINCT ON debe ser seguido por una cláusula ORDER BY. La primera expresión en la cláusula ORDER BY debe coincidir con la primera expresión en la cláusula DISTINCT ON. Las filas posteriores que tengan las mismas expresiones en la cláusula DISTINCT ON se eliminan; se conserva la primera fila según la cláusula ORDER BY. Por ejemplo, SELECT DISTINCT ON (a) a, b FROM t ORDER BY a, b; devolverá la primera fila para cada valor único de 'a', elegida por el valor más pequeño de 'b'.

Cláusula FROM

La cláusula FROM especifica las fuentes de datos para la consulta. Las fuentes de datos pueden ser tablas, vistas, subconsultas o llamadas a funciones. Las fuentes de datos se pueden combinar usando un tipo de join. Los tipos de join admitidos son INNER JOIN (o simplemente JOIN), LEFT JOIN (o LEFT OUTER JOIN), RIGHT JOIN (o RIGHT OUTER JOIN), FULL JOIN (o FULL OUTER JOIN), CROSS JOIN, NATURAL JOIN y las formas de unión específicas de PostgreSQL.

Si se especifican múltiples elementos en la cláusula FROM, se unen según las condiciones especificadas en las cláusulas ON, USING o NATURAL. Si no se especifica ninguna condición de unión, se realiza un CROSS JOIN, que genera el producto cartesiano de las dos fuentes de datos.

Una tabla puede ser especificada con la palabra clave ONLY para restringir la consulta a la tabla especificada, sin incluir sus tablas descendientes. Esto se aplica solo a las tablas con herencia.

TABLESAMPLE puede usarse para especificar que se debe muestrear la tabla en lugar de usar todas las filas. El método de muestreo y los argumentos dependen del sistema de almacenamiento. REPEATABLE(seed) se puede usar para garantizar la repetibilidad del muestreo.

Las subconsultas en la cláusula FROM deben estar entre paréntesis y tener un alias. Las funciones que devuelven un conjunto de filas pueden ser llamadas en la cláusula FROM. Si la función devuelve una columna de orden ordinal, se puede usar WITH ORDINALITY para incluirla en el resultado.

LATERAL permite que una subconsulta o llamada a función en la cláusula FROM haga referencia a columnas de elementos anteriores en la cláusula FROM.

Cláusula WHERE

La cláusula WHERE filtra las filas de la consulta según una condición booleana. Solo las filas para las cuales la condición es verdadera se conservan.

Cláusula GROUP BY

La cláusula GROUP BY agrupa filas que tienen los mismos valores en una o más columnas (o expresiones) en un conjunto de filas resumido. La cláusula GROUP BY se usa a menudo con funciones de agregación (como COUNT, SUM, AVG, MAX, MIN) para realizar cálculos sobre cada grupo.

Si se usa ALL, se conservan todos los grupos, incluidos los que no coinciden con las condiciones de HAVING. Si se usa DISTINCT, se eliminan los grupos duplicados. Las formas ROLLUP, CUBE y GROUPING SETS proporcionan formas avanzadas de agrupar datos, permitiendo la generación de subtotalizaciones y totalizaciones generales.

Cláusula HAVING

La cláusula HAVING filtra los grupos creados por la cláusula GROUP BY. Solo los grupos para los cuales la condición es verdadera se conservan en el resultado.

Cláusula WINDOW

La cláusula WINDOW define ventanas para funciones de ventana. Las funciones de ventana realizan cálculos sobre un conjunto de filas de tabla que están relacionadas de alguna manera con la fila actual. La cláusula WINDOW permite definir estas particiones y órdenes de manera eficiente para su uso en la lista SELECT o en la cláusula ORDER BY.

UNION, INTERSECT, EXCEPT

Estos operadores combinan los resultados de dos o más consultas SELECT. UNION devuelve todas las filas de todas las consultas. INTERSECT devuelve solo las filas que se encuentran en todas las consultas. EXCEPT devuelve las filas que están en la primera consulta pero no en las siguientes. La versión ALL de cada operador incluye duplicados.

Cláusula ORDER BY

La cláusula ORDER BY especifica el orden en que se devuelven las filas. Se pueden ordenar las filas por una o más expresiones, en orden ascendente (ASC, predeterminado) o descendente (DESC). USING operator permite especificar un operador de ordenamiento personalizado. NULLS { FIRST | LAST } controla la posición de los valores NULL en el resultado ordenado.

Cláusula LIMIT

La cláusula LIMIT restringe el número de filas devueltas por la consulta. El valor ALL significa que no se aplica límite. OFFSET especifica el número de filas a omitir antes de comenzar a devolver filas. FETCH se puede usar como una alternativa a LIMIT y OFFSET, y permite especificar la palabra clave WITH TIES para incluir todas las filas que empatan con la última fila si se usa ORDER BY.

Cláusula de Bloqueo

FOR UPDATE, FOR NO KEY UPDATE, FOR SHARE y FOR KEY SHARE se utilizan para bloquear las filas seleccionadas y evitar que sean modificadas por otras transacciones mientras la transacción actual está en curso. FOR NO KEY UPDATE y FOR KEY SHARE bloquean solo las filas y no las filas de índice asociadas. FOR UPDATE y FOR SHARE bloquean tanto las filas como las filas de índice asociadas. NOWAIT y SKIP LOCKED se pueden usar para evitar que la transacción espere si las filas ya están bloqueadas por otra transacción.

NOTAS

La sintaxis de TABLE es una forma abreviada de SELECT * FROM table_name. Puede ser útil en conjunción con la cláusula WITH.

La cláusula WITH es evaluada y materializada (si se especifica) antes de que se aplique la cláusula FROM.

Si se especifica DISTINCT ON, la consulta debe tener una cláusula ORDER BY.

Las funciones que devuelven tipos compuestos pueden ser tratadas como tablas, por ejemplo, SELECT * FROM foo(arg1, arg2) AS alias.

La cláusula WITH RECURSIVE no permite referencias circulares, ni recursión mutua.

La cláusula de bloqueo solo se aplica a las tablas especificadas en la lista FROM. Si una tabla en la lista FROM no está incluida en la cláusula de bloqueo, puede ser modificada por otras transacciones.

Si se utiliza la cláusula WITH, el orden de procesamiento es el siguiente:

1. Computar las consultasWITH.
2. Aplicar la cláusula FROM.
3. Aplicar la cláusula WHERE.
4. Aplicar la cláusula GROUP BY.
5. Aplicar la cláusula HAVING.
6. Computar las expresiones de SELECT.
7. Aplicar DISTINCT.
8. Aplicar UNION, INTERSECT, EXCEPT.
9. Aplicar ORDER BY.
10. Aplicar LIMIT y OFFSET.
11. Aplicar cláusulas de bloqueo.

EJEMPLOS

Recuperar todas las columnas de la tabla `empleados` y ordenarlas por salario:

SELECT * FROM empleados ORDER BY salario DESC;

Recuperar nombres y salarios de empleados en el departamento 'Ventas' con salario superior a 50000:

SELECT nombre, salario FROM empleados WHERE departamento = 'Ventas' AND salario > 50000;

Contar el número de empleados en cada departamento:

SELECT departamento, COUNT(*) FROM empleados GROUP BY departamento;

Usar una subconsulta con WITH para encontrar el salario promedio de los empleados en cada departamento:

WITH dept_sal AS (
    SELECT departamento, AVG(salario) AS avg_sal
    FROM empleados
    GROUP BY departamento
)
SELECT e.nombre, ds.avg_sal
FROM empleados e
JOIN dept_sal ds ON e.departamento = ds.departamento
WHERE e.salario > ds.avg_sal;

Recuperar la fila con el salario más alto de cada departamento (usando DISTINCT ON):

SELECT DISTINCT ON (departamento) departamento, nombre, salario
FROM empleados
ORDER BY departamento, salario DESC;

Seleccionar las 10 filas con el salario más alto:

SELECT nombre, salario
FROM empleados
ORDER BY salario DESC
LIMIT 10;

Una propiedad clave de las consultas WITH es que normalmente se evalúan solo una vez por ejecución de la consulta principal, incluso si la consulta principal se refiere a ellas más de una vez. En particular, se garantiza que las sentencias de modificación de datos se ejecutarán una y solo una vez, independientemente de si la consulta principal lee toda o parte de su salida.

Sin embargo, una consulta WITH puede marcarse como NOT MATERIALIZED para eliminar esta garantía. En ese caso, la consulta WITH puede plegarse en la consulta principal como si fuera una simple subconsulta SELECT en la cláusula FROM de la consulta principal. Esto resulta en cómputos duplicados si la consulta principal se refiere a esa consulta WITH más de una vez; pero si cada uso de este tipo requiere solo unas pocas filas de la salida total de la consulta WITH, NOT MATERIALIZED puede proporcionar un ahorro neto al permitir que las consultas se optimicen conjuntamente. NOT MATERIALIZED se ignora si se adjunta a una consulta WITH que es recursiva o no es libre de efectos secundarios (es decir, no es un SELECT simple que no contenga funciones volátiles).

Por defecto, una consulta WITH libre de efectos secundarios se pliega en la consulta principal si se utiliza exactamente una vez en la cláusula FROM de la consulta principal. Esto permite la optimización conjunta de los dos niveles de consulta en situaciones donde eso debería ser semánticamente invisible. Sin embargo, dicho plegado puede evitarse marcando la consulta WITH como MATERIALIZED. Esto podría ser útil, por ejemplo, si la consulta WITH se está utilizando como una valla de optimización para evitar que el planificador elija un plan deficiente. Las versiones de PostgreSQL anteriores a la v12 nunca realizaron dicho plegado, por lo que las consultas escritas para versiones anteriores podrían depender de WITH para actuar como una valla de optimización.

Cláusula FROM

La cláusula FROM especifica una o más tablas de origen para el SELECT. Si se especifican múltiples fuentes, el resultado es el producto cartesiano (cross join) de todas las fuentes. Pero usualmente se agregan condiciones de calificación (a través de WHERE) para restringir las filas devueltas a un pequeño subconjunto del producto cartesiano.

La cláusula FROM puede contener los siguientes elementos:

nombre_tabla

El nombre (opcionalmente calificado por esquema) de una tabla o vista existente. Si se especifica ONLY antes del nombre de la tabla, solo se escanea esa tabla. Si no se especifica ONLY, se escanean la tabla y todas sus tablas descendientes (si las hay). Opcionalmente, se puede especificar * después del nombre de la tabla para indicar explícitamente que se incluyen las tablas descendientes.

alias

Un nombre sustituto para el elemento FROM que contiene el alias. Un alias se utiliza por brevedad o para eliminar ambigüedades en auto-joins (donde la misma tabla se escanea varias veces). Cuando se proporciona un alias, oculta completamente el nombre real de la tabla o función; por ejemplo, dada FROM foo AS f, el resto del SELECT debe referirse a este elemento FROM como f y no como foo. Si se escribe un alias, también se puede escribir una lista de alias de columna para proporcionar nombres sustitutos para uno o más columnas de la tabla.

TABLESAMPLE método_muestreo ( argumento [, ...] ) [ REPEATABLE ( semilla ) ]

Una cláusula TABLESAMPLE después de un nombre_tabla indica que se debe usar el método_muestreo especificado para recuperar un subconjunto de las filas de esa tabla. Este muestreo precede a la aplicación de cualquier otro filtro como cláusulas WHERE. La distribución estándar de PostgreSQL incluye dos métodos de muestreo, BERNOULLI y SYSTEM, y otros métodos de muestreo se pueden instalar en la base de datos a través de extensiones.

Los métodos de muestreo BERNOULLI y SYSTEM aceptan cada uno un único argumento que es la fracción de la tabla a muestrear, expresada como un porcentaje entre 0 y 100. Este argumento puede ser cualquier expresión de valor real. (Otros métodos de muestreo pueden aceptar más o diferentes argumentos.) Estos dos métodos devuelven una muestra seleccionada aleatoriamente de la tabla que contendrá aproximadamente el porcentaje especificado de las filas de la tabla. El método BERNOULLI escanea toda la tabla y selecciona o ignora filas individuales de forma independiente con la probabilidad especificada. El método SYSTEM realiza un muestreo a nivel de bloque, con cada bloque teniendo la probabilidad especificada de ser seleccionado; se devuelven todas las filas de cada bloque seleccionado. El método SYSTEM es significativamente más rápido que el método BERNOULLI cuando se especifican porcentajes de muestreo pequeños, pero puede devolver una muestra menos aleatoria de la tabla como resultado de efectos de agrupamiento.

La cláusula opcional REPEATABLE especifica un número o expresión de semilla para generar números aleatorios dentro del método de muestreo. El valor de la semilla puede ser cualquier valor de punto flotante no nulo. Dos consultas que especifican la misma semilla y valores de argumento seleccionarán la misma muestra de la tabla, si la tabla no ha cambiado entretanto. Pero diferentes valores de semilla generalmente producirán muestras diferentes. Si no se proporciona REPEATABLE, se selecciona una nueva muestra aleatoria para cada consulta, basándose en una semilla generada por el sistema. Tenga en cuenta que algunos métodos de muestreo adicionales no aceptan REPEATABLE y siempre producirán nuevas muestras en cada uso.

select

Una sub-SELECT puede aparecer en la cláusula FROM. Esto actúa como si su salida se creara como una tabla temporal durante la duración de este único comando SELECT. Tenga en cuenta que la sub-SELECT debe estar rodeada de paréntesis, y se puede proporcionar un alias de la misma manera que para una tabla. Un comando VALUES también se puede utilizar aquí.

nombre_consulta_with

Una consulta WITH se referencia escribiendo su nombre, como si el nombre de la consulta fuera un nombre de tabla. (De hecho, la consulta WITH oculta cualquier tabla real del mismo nombre a efectos de la consulta principal. Si es necesario, puede referirse a una tabla real del mismo nombre calificando el nombre de la tabla por esquema.) Se puede proporcionar un alias de la misma manera que para una tabla.

nombre_funcion

Las llamadas a funciones pueden aparecer en la cláusula FROM. (Esto es especialmente útil para funciones que devuelven conjuntos de resultados, pero se puede usar cualquier función.) Esto actúa como si la salida de la función se creara como una tabla temporal durante la duración de este único comando SELECT. Si el tipo de resultado de la función es compuesto (incluyendo el caso de una función con múltiples parámetros OUT), cada atributo se convierte en una columna separada en la tabla implícita.

Cuando se agrega la cláusula opcional WITH ORDINALITY a la llamada a la función, se agregará una columna adicional de tipo bigint a la(s) columna(s) de resultado de la función. Esta columna numera las filas del conjunto de resultados de la función, comenzando desde 1. Por defecto, esta columna se llama ordinality.

Se puede proporcionar un alias de la misma manera que para una tabla. Si se escribe un alias, también se puede escribir una lista de alias de columna para proporcionar nombres sustitutos para uno o más atributos del tipo de retorno compuesto de la función, incluida la columna de ordinalidad si está presente.

Se pueden combinar múltiples llamadas a funciones en un único elemento de cláusula FROM rodeándolas con ROWS FROM( ... ). La salida de dicho elemento es la concatenación de la primera fila de cada función, luego la segunda fila de cada función, etc. Si algunas de las funciones producen menos filas que otras, se sustituyen valores nulos por los datos faltantes, de modo que el número total de filas devueltas sea siempre el mismo que para la función que produjo más filas.

Si la función se ha definido como que devuelve el tipo de datos record, entonces debe estar presente un alias o la palabra clave AS, seguido de una lista de definiciones de columna en el formato ( nombre_columna tipo_datos [, ... ]). La lista de definiciones de columna debe coincidir con el número y tipos reales de columnas devueltas por la función.

Al utilizar la sintaxis ROWS FROM( ... ), si una de las funciones requiere una lista de definiciones de columna, se prefiere colocar la lista de definiciones de columna después de la llamada a la función dentro de ROWS FROM( ... ). Una lista de definiciones de columna se puede colocar después del constructo ROWS FROM( ... ) solo si hay una sola función y ninguna cláusula WITH ORDINALITY.

Para usar ORDINALITY junto con una lista de definiciones de columna, debe usar la sintaxis ROWS FROM( ... ) y colocar la lista de definiciones de columna dentro de ROWS FROM( ... ).

tipo_join

Uno de
•[ INNER ] JOIN
•LEFT [ OUTER ] JOIN
•RIGHT [ OUTER ] JOIN
•FULL [ OUTER ] JOIN

Para los tipos de join INNER y OUTER, se debe especificar una condición de join, es decir, exactamente una de ON condición_join, USING (columna_join [, ...]), o NATURAL. Ver más abajo para el significado.

Una cláusula JOIN combina dos elementos FROM, que por conveniencia nos referiremos como "tablas", aunque en realidad pueden ser cualquier tipo de elemento FROM. Use paréntesis si es necesario para determinar el orden de anidamiento. En ausencia de paréntesis, los JOINs se anidan de izquierda a derecha. En cualquier caso, JOIN se vincula más fuertemente que las comas que separan los elementos de la lista FROM. Todas las opciones JOIN son simplemente una notación

Por conveniencia, ya que no hacen nada que no puedas hacer con FROM y WHERE simples.

LEFT OUTER JOIN devuelve todas las filas del producto cartesiano calificado (es decir, todas las filas combinadas que pasan su condición de unión), más una copia de cada fila de la tabla de la izquierda para la que no hubo ninguna fila de la derecha que pasara la condición de unión. Esta fila de la izquierda se extiende al ancho completo de la tabla unida insertando valores nulos para las columnas de la derecha. Tenga en cuenta que solo la condición propia de la cláusula JOIN se considera al decidir qué filas tienen coincidencias. Las condiciones externas se aplican después.

Por el contrario, RIGHT OUTER JOIN devuelve todas las filas unidas, más una fila por cada fila de la derecha no coincidente (extendida con nulos a la izquierda). Esto es solo una conveniencia de notación, ya que podrías convertirlo en un LEFT OUTER JOIN intercambiando las tablas de la izquierda y la derecha.

FULL OUTER JOIN devuelve todas las filas unidas, más una fila por cada fila de la izquierda no coincidente (extendida con nulos a la derecha), más una fila por cada fila de la derecha no coincidente (extendida con nulos a la izquierda).

ON condicion_union

condicion_union es una expresión que resulta en un valor booleano (similar a una cláusula WHERE) que especifica qué filas en una unión se consideran coincidentes.

USING ( columna_union [, ...] ) [ COMO alias_uso_union ]

Una cláusula de la forma USING ( a, b, ... ) es una abreviatura de ON tabla_izquierda.a = tabla_derecha.a Y tabla_izquierda.b = tabla_derecha.b .... Además, USING implica que solo una de cada par de columnas equivalentes se incluirá en la salida de la unión, no ambas.

Si se especifica un nombre de alias_uso_union, proporciona un alias de tabla para las columnas de unión. Solo las columnas de unión listadas en la cláusula USING son direccionables por este nombre. A diferencia de un alias regular, esto no oculta los nombres de las tablas unidas del resto de la consulta. A diferencia de un alias regular, no puedes escribir una lista de alias de columnas; los nombres de salida de las columnas de unión son los mismos que aparecen en la lista USING.

NATURAL

NATURAL es una abreviatura de una lista USING que menciona todas las columnas en las dos tablas que tienen nombres coincidentes. Si no hay nombres de columna comunes, NATURAL es equivalente a ON TRUE.

CROSS JOIN

CROSS JOIN es equivalente a INNER JOIN ON (TRUE), es decir, no se eliminan filas por calificación. Producen un producto cartesiano simple, el mismo resultado que obtienes al listar las dos tablas en el nivel superior de FROM, pero restringido por la condición de unión (si la hay).

LATERAL

La palabra clave LATERAL puede preceder a un elemento FROM de sub-SELECT. Esto permite que el sub-SELECT haga referencia a columnas de elementos FROM que aparecen antes en la lista FROM. (Sin LATERAL, cada sub-SELECT se evalúa de forma independiente y, por lo tanto, no puede hacer referencia cruzada a ningún otro elemento FROM).

LATERAL también puede preceder a un elemento FROM de llamada a función, pero en este caso es una palabra de ruido, ya que la expresión de la función puede hacer referencia a elementos FROM anteriores en cualquier caso.

Un elemento LATERAL puede aparecer en el nivel superior de la lista FROM, o dentro de un árbol JOIN. En este último caso, también puede hacer referencia a cualquier elemento que esté en el lado izquierdo de un JOIN del cual esté en el lado derecho.

Cuando un elemento FROM contiene referencias cruzadas LATERAL, la evaluación procede de la siguiente manera: por cada fila del elemento FROM que proporciona la(s) columna(s) referenciada(s) cruzada(s), o conjunto de filas de múltiples elementos FROM que proporcionan las columnas, el elemento LATERAL se evalúa utilizando los valores de la(s) columna(s) de esa fila o conjunto de filas. Las filas resultantes se unen como de costumbre con las filas de las que se calcularon. Esto se repite para cada fila o conjunto de filas de la(s) tabla(s) fuente de columnas.

La(s) tabla(s) fuente de columnas deben estar unidas INNER o LEFT al elemento LATERAL, de lo contrario no habría un conjunto bien definido de filas a partir del cual calcular cada conjunto de filas para el elemento LATERAL. Por lo tanto, aunque una construcción como X RIGHT JOIN LATERAL Y es sintácticamente válida, en realidad no se permite que Y haga referencia a X.

Cláusula WHERE

La cláusula WHERE opcional tiene la forma general

WHERE condicion

donde condicion es cualquier expresión que se evalúa como un resultado de tipo booleano. Cualquier fila que no cumpla esta condición se eliminará de la salida. Una fila cumple la condición si devuelve verdadero cuando los valores de la fila real se sustituyen por cualquier referencia a variables.

Cláusula GROUP BY

La cláusula GROUP BY opcional tiene la forma general

GROUP BY [ ALL | DISTINCT ] elemento_agrupacion [, ...]

GROUP BY condensará en una sola fila todas las filas seleccionadas que compartan los mismos valores para las expresiones agrupadas. Una expresion utilizada dentro de un elemento_agrupacion puede ser un nombre de columna de entrada, o el nombre o número ordinal de una columna de salida (elemento de la lista SELECT), o una expresión arbitraria formada a partir de valores de columnas de entrada. En caso de ambigüedad, un nombre de GROUP BY se interpretará como un nombre de columna de entrada en lugar de un nombre de columna de salida.

Si GROUPING SETS, ROLLUP o CUBE están presentes como elementos de agrupación, entonces la cláusula GROUP BY en su conjunto define un número de conjuntos de agrupación independientes. El efecto es equivalente a construir una UNION ALL entre subconsultas con los conjuntos de agrupación individuales como sus cláusulas GROUP BY. La cláusula DISTINCT opcional elimina conjuntos duplicados antes del procesamiento; no transforma la UNION ALL en una UNION DISTINCT. Para más detalles sobre el manejo de conjuntos de agrupación, consulte la Sección 7.2.4.

Las funciones agregadas, si se utilizan, se calculan en todas las filas que componen cada grupo, produciendo un valor separado para cada grupo. (Si hay funciones agregadas pero no hay cláusula GROUP BY, la consulta se trata como si tuviera un solo grupo que comprende todas las filas seleccionadas). El conjunto de filas alimentado a cada función agregada puede ser filtrado adicionalmente adjuntando una cláusula FILTER a la llamada de la función agregada; consulte la Sección 4.2.7 para obtener más información. Cuando está presente una cláusula FILTER, solo las filas que la cumplen se incluyen en la entrada de esa función agregada.

Cuando está presente GROUP BY, o cualquier función agregada, no es válido que las expresiones de la lista SELECT hagan referencia a columnas no agrupadas excepto dentro de funciones agregadas o cuando la columna no agrupada depende funcionalmente de las columnas agrupadas, ya que de lo contrario habría más de un valor posible para devolver para una columna no agrupada. Una dependencia funcional existe si las columnas agrupadas (o un subconjunto de ellas) son la clave primaria de la tabla que contiene la columna no agrupada.

Tenga en cuenta que todas las funciones agregadas se evalúan antes de evaluar cualquier expresión "escalar" en la cláusula HAVING o en la lista SELECT. Esto significa que, por ejemplo, una expresión CASE no se puede usar para omitir la evaluación de una función agregada; consulte la Sección 4.2.14.

Actualmente, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE y FOR KEY SHARE no se pueden especificar con GROUP BY.

Cláusula HAVING

La cláusula HAVING opcional tiene la forma general

HAVING condicion

donde condicion es la misma que se especifica para la cláusula WHERE.

HAVING elimina las filas de grupo que no satisfacen la condición. HAVING es diferente de WHERE: WHERE filtra filas individuales antes de la aplicación de GROUP BY, mientras que HAVING filtra filas de grupo creadas por GROUP BY. Cada columna referenciada en condicion debe hacer referencia inequívocamente a una columna de agrupación, a menos que la referencia aparezca dentro de una función agregada o la columna no agrupada dependa funcionalmente de las columnas de agrupación.

La presencia de HAVING convierte una consulta en una consulta agrupada incluso si no hay una cláusula GROUP BY. Esto es lo mismo que sucede cuando la consulta contiene funciones agregadas pero no hay una cláusula GROUP BY. Todas las filas seleccionadas se consideran que forman un solo grupo, y la lista SELECT y la cláusula HAVING solo pueden hacer referencia a columnas de tablas dentro de funciones agregadas. Dicha consulta emitirá una sola fila si la condición HAVING es verdadera, cero filas si no es verdadera.

Actualmente, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE y FOR KEY SHARE no se pueden especificar con HAVING.

Cláusula WINDOW

La cláusula WINDOW opcional tiene la forma general

WINDOW nombre_ventana AS ( definicion_ventana ) [, ...]

donde nombre_ventana es un nombre que se puede referenciar desde cláusulas OVER o definiciones de ventana posteriores, y definicion_ventana es

[ nombre_ventana_existente ]
[ PARTITION BY expresion [, ...] ]
[ ORDER BY expresion [ ASC | DESC | USING operador ] [ NULLS { FIRST | LAST } ] [, ...] ]
[ clausula_marco ]

Si se especifica un nombre_ventana_existente, debe hacer referencia a una entrada anterior en la lista WINDOW; la nueva ventana copia su cláusula de partición de esa entrada, así como su cláusula de ordenación si la tiene. En este caso, la nueva ventana no puede especificar su propia cláusula PARTITION BY, y puede especificar ORDER BY solo si la ventana copiada no tiene una. La nueva ventana siempre usa su propia cláusula de marco; la ventana copiada no debe especificar una cláusula de marco.

Los elementos de la lista PARTITION BY se interpretan de manera muy similar a los elementos de una cláusula GROUP BY, excepto que siempre son expresiones simples y nunca el nombre o número de una columna de salida. Otra diferencia es que estas expresiones pueden contener llamadas a funciones agregadas, que no están permitidas en una cláusula GROUP BY regular. Se permiten aquí porque el anidamiento ocurre después de la agrupación y la agregación.

De manera similar, los elementos de la lista ORDER BY se interpretan de manera muy similar a los elementos de una cláusula ORDER BY a nivel de sentencia, excepto que las expresiones siempre se toman como expresiones simples y nunca como el nombre o número de una columna de salida.

La clausula_marco opcional define el marco de ventana para las funciones de ventana que dependen del marco (no todas lo hacen). El marco de ventana es un conjunto de filas relacionadas para cada fila de la consulta (llamada la fila actual). La clausula_marco puede ser una de

{ RANGE | ROWS | GROUPS } inicio_marco [ exclusiones_marco ]
{ RANGE | ROWS | GROUPS } BETWEEN inicio_marco AND fin_marco [ exclusiones_marco ]

donde inicio_marco y fin_marco pueden ser uno de

UN
BOUNDED PRECEDING
offset PRECEDING
CURRENT ROW
offset FOLLOWING
UNBOUNDED FOLLOWING

y frame_exclusion puede ser uno de

EXCLUDE CURRENT ROW
EXCLUDE GROUP
EXCLUDE TIES
EXCLUDE NO OTHERS

Si se omite frame_end, se establece por defecto en CURRENT ROW. Las restricciones son que frame_start no puede ser UNBOUNDED FOLLOWING, frame_end no puede ser UNBOUNDED PRECEDING, y la opción frame_end no puede aparecer antes en la lista anterior de opciones de frame_start y frame_end que la opción frame_start; por ejemplo, RANGE BETWEEN CURRENT ROW AND offset PRECEDING no está permitido.

La opción de marco predeterminada es RANGE UNBOUNDED PRECEDING, que es lo mismo que RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW; establece el marco para que sean todas las filas desde el inicio de la partición hasta el último elemento igual al de la fila actual (una fila que la cláusula ORDER BY de la ventana considera equivalente a la fila actual; todas las filas son iguales si no hay ORDER BY). En general, UNBOUNDED PRECEDING significa que el marco comienza con la primera fila de la partición, y de manera similar UNBOUNDED FOLLOWING significa que el marco termina con la última fila de la partición, independientemente del modo RANGE, ROWS o GROUPS. En el modo ROWS, CURRENT ROW significa que el marco comienza o termina con la fila actual; pero en el modo RANGE o GROUPS significa que el marco comienza o termina con el primer o último elemento igual al de la fila actual en el orden de ORDER BY. Las opciones offset PRECEDING y offset FOLLOWING varían en su significado dependiendo del modo de marco. En el modo ROWS, el offset es un entero que indica que el marco comienza o termina esa cantidad de filas antes o después de la fila actual. En el modo GROUPS, el offset es un entero que indica que el marco comienza o termina esa cantidad de grupos de elementos antes o después del grupo de elementos de la fila actual, donde un grupo de elementos es un conjunto de filas que son equivalentes según la cláusula ORDER BY de la ventana. En el modo RANGE, el uso de la opción offset requiere que haya exactamente una columna ORDER BY en la definición de la ventana. Entonces, el marco contiene aquellas filas cuyo valor de la columna de ordenación no es más que offset menor que (para PRECEDING) o mayor que (para FOLLOWING) el valor de la columna de ordenación de la fila actual. En estos casos, el tipo de datos de la expresión offset depende del tipo de datos de la columna de ordenación. Para columnas de ordenación numéricas, suele ser del mismo tipo que la columna de ordenación, pero para columnas de ordenación de fecha y hora, es un intervalo. En todos estos casos, el valor del offset debe ser no nulo y no negativo. Además, si bien el offset no tiene que ser una constante simple, no puede contener variables, funciones de agregación ni funciones de ventana.

La opción frame_exclusion permite que las filas alrededor de la fila actual se excluyan del marco, incluso si se incluirían según las opciones de inicio y fin del marco. EXCLUDE CURRENT ROW excluye la fila actual del marco. EXCLUDE GROUP excluye la fila actual y sus elementos iguales de ordenación del marco. EXCLUDE TIES excluye cualquier elemento igual de la fila actual del marco, pero no la fila actual en sí. EXCLUDE NO OTHERS simplemente especifica explícitamente el comportamiento predeterminado de no excluir la fila actual ni sus elementos iguales.

Tenga en cuenta que el modo ROWS puede producir resultados impredecibles si el orden de ORDER BY no ordena las filas de forma única. Los modos RANGE y GROUPS están diseñados para garantizar que las filas que son iguales en el orden de ORDER BY se traten de manera similar: todas las filas de un grupo de elementos dado estarán dentro o fuera del marco.

El propósito de una cláusula WINDOW es especificar el comportamiento de las funciones de ventana que aparecen en la lista SELECT o en la cláusula ORDER BY de la consulta. Estas funciones pueden hacer referencia a las entradas de la cláusula WINDOW por nombre en sus cláusulas OVER. Sin embargo, una entrada de la cláusula WINDOW no tiene por qué ser referenciada en ningún lugar; si no se utiliza en la consulta, simplemente se ignora. Es posible utilizar funciones de ventana sin ninguna cláusula WINDOW, ya que una llamada a una función de ventana puede especificar su definición de ventana directamente en su cláusula OVER. Sin embargo, la cláusula WINDOW ahorra escritura cuando la misma definición de ventana es necesaria para más de una función de ventana.

Actualmente, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE y FOR KEY SHARE no se pueden especificar con WINDOW.

Las funciones de ventana se describen en detalle en las secciones 3.5, 4.2.8 y 7.2.5.

Lista SELECT

La lista SELECT (entre las palabras clave SELECT y FROM) especifica las expresiones que forman las filas de salida de la sentencia SELECT. Las expresiones pueden (y usualmente lo hacen) referirse a columnas calculadas en la cláusula FROM.

Al igual que en una tabla, cada columna de salida de un SELECT tiene un nombre. En un SELECT simple, este nombre se utiliza solo para etiquetar la columna para su visualización, pero cuando el SELECT es una subconsulta de una consulta más grande, el nombre es visto por la consulta más grande como el nombre de la columna de la tabla virtual producida por la subconsulta. Para especificar el nombre a usar para una columna de salida, escriba AS output_name después de la expresión de la columna. (Puede omitir AS, pero solo si el nombre de salida deseado no coincide con ninguna palabra clave de PostgreSQL (ver Apéndice C). Para protegerse contra posibles adiciones futuras de palabras clave, se recomienda que siempre escriba AS o ponga el nombre de salida entre comillas dobles). Si no especifica un nombre de columna, PostgreSQL elige un nombre automáticamente. Si la expresión de la columna es una referencia de columna simple, el nombre elegido es el mismo que el nombre de esa columna. En casos más complejos, se puede usar el nombre de una función o tipo, o el sistema puede recurrir a un nombre generado como ?column?.

El nombre de la columna de salida se puede utilizar para referirse al valor de la columna en las cláusulas ORDER BY y GROUP BY, pero no en las cláusulas WHERE o HAVING; allí debe escribir la expresión en su lugar.

En lugar de una expresión, se puede escribir * en la lista de salida como un atajo para todas las columnas de las filas seleccionadas. Además, puede escribir table_name.* como un atajo para las columnas que provienen solo de esa tabla. En estos casos, no es posible especificar nuevos nombres con AS; los nombres de las columnas de salida serán los mismos que los nombres de las columnas de la tabla.

De acuerdo con el estándar SQL, las expresiones en la lista de salida deben ser calculadas antes de aplicar DISTINCT, ORDER BY o LIMIT. Esto es obviamente necesario cuando se usa DISTINCT, ya que de lo contrario no está claro qué valores se están haciendo distintos. Sin embargo, en muchos casos es conveniente que las expresiones de salida se calculen después de ORDER BY y LIMIT; particularmente si la lista de salida contiene alguna función volátil o costosa. Con ese comportamiento, el orden de evaluación de las funciones es más intuitivo y no habrá evaluaciones correspondientes a filas que nunca aparecen en la salida. PostgreSQL evaluará efectivamente las expresiones de salida después de ordenar y limitar, siempre que esas expresiones no se referencien en DISTINCT, ORDER BY o GROUP BY. (Como contraejemplo, SELECT f(x) FROM tab ORDER BY 1 claramente debe evaluar f(x) antes de ordenar). Las expresiones de salida que contienen funciones que devuelven conjuntos se evalúan efectivamente después de ordenar y antes de limitar, de modo que LIMIT actúe para cortar la salida de una función que devuelve conjuntos.


Nota

Las versiones de PostgreSQL anteriores a la 9.6 no ofrecían garantías sobre el momento de la evaluación de las expresiones de salida frente al ordenamiento y la limitación; dependía de la forma del plan de consulta elegido.

Cláusula DISTINCT

Si se especifica SELECT DISTINCT, se eliminan todas las filas duplicadas del conjunto de resultados (se conserva una fila de cada grupo de duplicados). SELECT ALL especifica lo contrario: se conservan todas las filas; ese es el comportamiento predeterminado.

SELECT DISTINCT ON ( expresión [, ...] ) conserva solo la primera fila de cada conjunto de filas donde las expresiones dadas se evalúan como iguales. Las expresiones DISTINCT ON se interpretan utilizando las mismas reglas que para ORDER BY (ver arriba). Tenga en cuenta que la "primera fila" de cada conjunto es impredecible a menos que se utilice ORDER BY para garantizar que la fila deseada aparezca primero. Por ejemplo:

SELECT DISTINCT ON (location) location, time, report
    FROM weather_reports
    ORDER BY location, time DESC;

recupera el informe meteorológico más reciente para cada ubicación. Pero si no hubiéramos usado ORDER BY para forzar el orden descendente de los valores de tiempo para cada ubicación, habríamos obtenido un informe de un tiempo impredecible para cada ubicación.

Las expresiones DISTINCT ON deben coincidir con las expresiones ORDER BY más a la izquierda. La cláusula ORDER BY normalmente contendrá expresiones adicionales que determinan la precedencia deseada de las filas dentro de cada grupo DISTINCT ON.

Actualmente, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE y FOR KEY SHARE no se pueden especificar con DISTINCT.

Cláusula UNION

La cláusula UNION tiene esta forma general:

select_statement UNION [ ALL | DISTINCT ] select_statement

select_statement es cualquier sentencia SELECT sin una cláusula ORDER BY, LIMIT, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE o FOR KEY SHARE. (ORDER BY y LIMIT se pueden adjuntar a una subexpresión si está encerrada en paréntesis. Sin paréntesis, estas cláusulas se aplicarán al resultado de la UNION, no a su expresión de entrada derecha).

El operador UNION calcula la unión de conjuntos de las filas devueltas por las sentencias SELECT involucradas. Una fila está en la unión de conjuntos de dos conjuntos de resultados si aparece en al menos uno de los conjuntos de resultados. Las dos sentencias SELECT que representan los operandos directos de UNION deben producir el mismo número de columnas, y las columnas correspondientes deben ser de tipos de datos compatibles.

El resultado de UNION no contiene filas duplicadas a menos que se especifique la opción ALL. ALL evita la eliminación de duplicados. (Por lo tanto, UNION ALL suele ser significativamente más rápido que UNION; use ALL cuando pueda). DISTINCT se puede escribir para especificar explícitamente el comportamiento predeterminado de eliminar filas duplicadas.

Múltiples operadores UNION en la misma sentencia SELECT se evalúan de izquierda a derecha, a menos que se indique lo contrario mediante paréntesis.

Actualmente, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE y FOR KEY SHARE no se pueden especificar ni para un resultado UNION ni para ninguna entrada de un UNION.

Cláusula INTERSECT

La cláusula INTERSECT tiene esta forma general:

select_statement INTERSECT [ ALL | DISTINCT ] select_statement

select_statement es cualquier sentencia SELECT sin una cláusula ORDER BY, LIMIT, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE o FOR KEY SHARE.

El operador INTERSECT calcula la intersección de conjuntos de las filas devueltas por las sentencias SELECT involucradas. Una fila está en la intersección de dos conjuntos de resultados si aparece en ambos conjuntos de resultados.

El resultado de INTERSECT no contiene filas duplicadas a menos que se especifique la opción ALL. Con ALL, una fila que tiene m duplicados en la tabla izquierda y n duplicados en la tabla derecha aparecerá min(m,n) veces en el conjunto de resultados. Se puede escribir DISTINCT para especificar explícitamente el comportamiento predeterminado de eliminación de filas duplicadas.

Múltiples operadores INTERSECT en la misma sentencia SELECT se evalúan de izquierda a derecha, a menos que los paréntesis dicten lo contrario. INTERSECT se vincula más fuertemente que UNION. Es decir, A UNION B INTERSECT C se leerá como A UNION (B INTERSECT C).

Actualmente, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE y FOR KEY SHARE no se pueden especificar ni para un resultado de INTERSECT ni para ninguna entrada de un INTERSECT.

Cláusula EXCEPT

La cláusula EXCEPT tiene esta forma general:

sentencia_select EXCEPT [ ALL | DISTINCT ] sentencia_select

sentencia_select es cualquier sentencia SELECT sin una cláusula ORDER BY, LIMIT, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE o FOR KEY SHARE.

El operador EXCEPT calcula el conjunto de filas que están en el resultado de la sentencia SELECT izquierda pero no en el resultado de la derecha.

El resultado de EXCEPT no contiene filas duplicadas a menos que se especifique la opción ALL. Con ALL, una fila que tiene m duplicados en la tabla izquierda y n duplicados en la tabla derecha aparecerá max(m-n,0) veces en el conjunto de resultados. Se puede escribir DISTINCT para especificar explícitamente el comportamiento predeterminado de eliminación de filas duplicadas.

Múltiples operadores EXCEPT en la misma sentencia SELECT se evalúan de izquierda a derecha, a menos que los paréntesis dicten lo contrario. EXCEPT se vincula al mismo nivel que UNION.

Actualmente, FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE y FOR KEY SHARE no se pueden especificar ni para un resultado de EXCEPT ni para ninguna entrada de un EXCEPT.

Cláusula ORDER BY

La cláusula opcional ORDER BY tiene esta forma general:

ORDER BY expresión [ ASC | DESC | USING operador ] [ NULLS { FIRST | LAST } ] [, ...]

La cláusula ORDER BY hace que las filas de resultado se ordenen según la(s) expresión(es) especificada(s). Si dos filas son iguales según la expresión más a la izquierda, se comparan según la siguiente expresión y así sucesivamente. Si son iguales según todas las expresiones especificadas, se devuelven en un orden dependiente de la implementación.

Cada expresión puede ser el nombre o el número ordinal de una columna de salida (elemento de la lista SELECT), o puede ser una expresión arbitraria formada a partir de los valores de las columnas de entrada.

El número ordinal se refiere a la posición ordinal (de izquierda a derecha) de la columna de salida. Esta característica hace posible definir un orden basado en una columna que no tiene un nombre único. Esto nunca es absolutamente necesario porque siempre es posible asignar un nombre a una columna de salida utilizando la cláusula AS.

También es posible utilizar expresiones arbitrarias en la cláusula ORDER BY, incluidas columnas que no aparecen en la lista de salida de SELECT. Por lo tanto, la siguiente sentencia es válida:

SELECT name FROM distributors ORDER BY code;

Una limitación de esta característica es que una cláusula ORDER BY que se aplica al resultado de una cláusula UNION, INTERSECT o EXCEPT solo puede especificar un nombre o número de columna de salida, no una expresión.

Si una expresión ORDER BY es un nombre simple que coincide tanto con un nombre de columna de salida como con un nombre de columna de entrada, ORDER BY lo interpretará como el nombre de la columna de salida. Esta es la opción opuesta a la que tomará GROUP BY en la misma situación. Esta inconsistencia se hace para ser compatible con el estándar SQL.

Opcionalmente, se puede agregar la palabra clave ASC (ascendente) o DESC (descendente) después de cualquier expresión en la cláusula ORDER BY. Si no se especifica, ASC se asume por defecto. Alternativamente, se puede especificar un nombre de operador de ordenamiento específico en la cláusula USING. Un operador de ordenamiento debe ser un miembro menor o mayor que de alguna familia de operadores de árbol B. ASC suele ser equivalente a USING < y DESC suele ser equivalente a USING >. (Pero el creador de un tipo de datos definido por el usuario puede definir exactamente cuál es el ordenamiento de ordenamiento predeterminado, y podría corresponder a operadores con otros nombres).

Si se especifica NULLS LAST, los valores nulos se ordenan después de todos los valores no nulos; si se especifica NULLS FIRST, los valores nulos se ordenan antes de todos los valores no nulos. Si no se especifica ninguno, el comportamiento predeterminado es NULLS LAST cuando ASC se especifica o se infiere, y NULLS FIRST cuando DESC se especifica (por lo tanto, el valor predeterminado es actuar como si los nulos fueran mayores que los no nulos). Cuando se especifica USING, el ordenamiento predeterminado de nulos depende de si el operador es un operador de menor o mayor que.

Tenga en cuenta que las opciones de ordenamiento solo se aplican a la expresión que siguen; por ejemplo, ORDER BY x, y DESC no significa lo mismo que ORDER BY x DESC, y DESC.

Los datos de tipo cadena de caracteres se ordenan según la colación que se aplica a la columna que se está ordenando. Esto se puede anular si es necesario incluyendo una cláusula COLLATE en la expresión, por ejemplo, ORDER BY mycolumn COLLATE "en_US". Para obtener más información, consulte la Sección 4.2.10 y la Sección 23.2.

Cláusula LIMIT

La cláusula LIMIT consta de dos sub-cláusulas independientes:

LIMIT { cuenta | ALL }
OFFSET inicio

El parámetro cuenta especifica el número máximo de filas a devolver, mientras que inicio especifica el número de filas a omitir antes de comenzar a devolver filas. Cuando se especifican ambos, se omiten inicio filas antes de comenzar a contar las cuenta filas a devolver.

Si la expresión cuenta se evalúa como NULL, se trata como LIMIT ALL, es decir, sin límite. Si inicio se evalúa como NULL, se trata igual que OFFSET 0.

SQL:2008 introdujo una sintaxis diferente para lograr el mismo resultado, que PostgreSQL también soporta. Es:

OFFSET inicio { ROW | ROWS }
FETCH { FIRST | NEXT } [ cuenta ] { ROW | ROWS } { ONLY | WITH TIES }

En esta sintaxis, el valor inicio o cuenta es requerido por el estándar para ser una constante literal, un parámetro o un nombre de variable; como una extensión de PostgreSQL, se permiten otras expresiones, pero generalmente necesitarán estar entre paréntesis para evitar ambigüedades. Si se omite cuenta en una cláusula FETCH, por defecto es 1. La opción WITH TIES se utiliza para devolver cualquier fila adicional que empate en el último lugar del conjunto de resultados según la cláusula ORDER BY; ORDER BY es obligatorio en este caso, y SKIP LOCKED no está permitido. ROW y ROWS, así como FIRST y NEXT, son palabras clave que no influyen en los efectos de estas cláusulas. Según el estándar, la cláusula OFFSET debe preceder a la cláusula FETCH si ambas están presentes; pero PostgreSQL es más permisivo y permite cualquier orden.

Al usar LIMIT, es una buena idea usar una cláusula ORDER BY que restrinja las filas de resultado a un orden único. De lo contrario, obtendrá un subconjunto impredecible de las filas de la consulta — podría estar pidiendo las décima a vigésima filas, ¿pero la décima a vigésima en qué orden? No sabrá el orden a menos que especifique ORDER BY.

El planificador de consultas tiene en cuenta LIMIT al generar un plan de consulta, por lo que es muy probable que obtenga planes diferentes (que produzcan diferentes órdenes de filas) dependiendo de lo que use para LIMIT y OFFSET. Por lo tanto, usar diferentes valores de LIMIT/OFFSET para seleccionar diferentes subconjuntos de un resultado de consulta dará resultados inconsistentes a menos que se imponga un orden de resultado predecible con ORDER BY. Esto no es un error; es una consecuencia inherente del hecho de que SQL no garantiza la entrega de los resultados de una consulta en ningún orden particular a menos que se utilice ORDER BY para restringir el orden.

Incluso es posible que ejecuciones repetidas de la misma consulta LIMIT devuelvan diferentes subconjuntos de las filas de una tabla, si no hay un ORDER BY para forzar la selección de un subconjunto determinista. Nuevamente, esto no es un error; el determinismo de los resultados simplemente no está garantizado en tal caso.

La Cláusula de Bloqueo

FOR UPDATE, FOR NO KEY UPDATE, FOR SHARE y FOR KEY SHARE son cláusulas de bloqueo; afectan cómo SELECT bloquea las filas a medida que se obtienen de la tabla.

La cláusula de bloqueo tiene la forma general

FOR nivel_bloqueo [ OF referencia_desde [, ...] ] [ NOWAIT | SKIP LOCKED ]

donde nivel_bloqueo puede ser uno de

UPDATE
NO KEY UPDATE
SHARE
KEY SHARE

referencia_desde debe ser un alias de tabla o un nombre de tabla no oculto referenciado en la cláusula FROM. Para obtener más información sobre cada modo de bloqueo a nivel de fila, consulte la Sección 13.3.2.

Para evitar que la operación espere a que otras transacciones confirmen, use la opción NOWAIT o SKIP LOCKED. Con NOWAIT, la sentencia informa un error, en lugar de esperar, si una fila seleccionada no se puede bloquear inmediatamente. Con SKIP LOCKED, se omiten las filas seleccionadas que no se pueden bloquear inmediatamente. Omitir filas bloqueadas proporciona una vista inconsistente de los datos, por lo que esto no es adecuado para trabajos de propósito general, pero se puede usar para evitar la contención de bloqueos con múltiples consumidores que acceden a una tabla tipo cola. Tenga en cuenta que NOWAIT y SKIP LOCKED solo se aplican a los bloqueos a nivel de fila — el bloqueo de tabla ROW SHARE requerido todavía se adquiere de la manera habitual (ver Capítulo 13). Puede usar LOCK con la opción NOWAIT primero, si necesita adquirir el bloqueo de tabla sin esperar.

Si se nombran tablas específicas en una cláusula de bloqueo, entonces solo se bloquean las filas que provienen de esas tablas; cualquier otra tabla utilizada en el SELECT se lee simplemente como de costumbre. Una cláusula de bloqueo sin una lista de tablas afecta a todas las tablas utilizadas en la sentencia. Si se aplica una cláusula de bloqueo a una vista o subconsulta, afecta a todas las tablas utilizadas en la vista o subconsulta. Sin embargo, estas cláusulas no se aplican a las consultas WITH referenciadas por la consulta principal. Si desea que el bloqueo de filas ocurra dentro de una consulta WITH, especifique una cláusula de bloqueo dentro de la consulta WITH.

Múltiples cláusulas de bloqueo pueden ser escritas

ten si es necesario especificar un comportamiento de bloqueo diferente para tablas diferentes. Si la misma tabla se menciona (o se ve afectada implícitamente) por más de una cláusula de bloqueo, entonces se procesa como si solo se hubiera especificado la más fuerte. De manera similar, una tabla se procesa como NOWAIT si eso se especifica en alguna de las cláusulas que la afectan. De lo contrario, se procesa como SKIP LOCKED si eso se especifica en alguna de las cláusulas que la afectan.

Las cláusulas de bloqueo no se pueden usar en contextos donde las filas devueltas no se puedan identificar claramente con filas de tablas individuales; por ejemplo, no se pueden usar con agregación.

Cuando una cláusula de bloqueo aparece en el nivel superior de una consulta SELECT, las filas que se bloquean son exactamente aquellas que son devueltas por la consulta; en el caso de una consulta de unión, las filas bloqueadas son aquellas que contribuyen a las filas de unión devueltas. Además, se bloquearán las filas que cumplieron las condiciones de la consulta según la instantánea de la consulta, aunque no se devolverán si se actualizaron después de la instantánea y ya no cumplen las condiciones de la consulta. Si se utiliza LIMIT, el bloqueo se detiene una vez que se han devuelto suficientes filas para cumplir con el límite (pero tenga en cuenta que las filas omitidas por OFFSET se bloquearán). De manera similar, si se usa una cláusula de bloqueo en la consulta de un cursor, solo se bloquearán las filas realmente recuperadas o saltadas por el cursor.

Cuando una cláusula de bloqueo aparece en una subconsulta SELECT, las filas bloqueadas son aquellas devueltas a la consulta externa por la subconsulta. Esto puede implicar menos filas de las que sugeriría la inspección de la subconsulta por sí sola, ya que las condiciones de la consulta externa pueden usarse para optimizar la ejecución de la subconsulta. Por ejemplo,

SELECT * FROM (SELECT * FROM mi_tabla FOR UPDATE) ss WHERE col1 = 5;

bloqueará solo las filas con col1 = 5, aunque esa condición no esté textualmente dentro de la subconsulta.

Las versiones anteriores fallaron en preservar un bloqueo que se actualiza mediante un savepoint posterior. Por ejemplo, este código:

BEGIN;
SELECT * FROM mi_tabla WHERE key = 1 FOR UPDATE;
SAVEPOINT s;
UPDATE mi_tabla SET ... WHERE key = 1;
ROLLBACK TO s;

no conservaría el bloqueo FOR UPDATE después del ROLLBACK TO. Esto se ha corregido en la versión 9.3.


Precaución

Es posible que un comando SELECT ejecutándose en el nivel de aislamiento de transacción READ COMMITTED y usando ORDER BY y una cláusula de bloqueo devuelva filas desordenadas. Esto se debe a que ORDER BY se aplica primero. El comando ordena el resultado, pero luego puede bloquearse al intentar obtener un bloqueo en una o más de las filas. Una vez que el SELECT se desbloquea, algunos de los valores de las columnas de ordenación podrían haberse modificado, lo que haría que esas filas parecieran estar desordenadas (aunque están en orden en términos de los valores de las columnas originales). Esto se puede solucionar si es necesario colocando la cláusula FOR UPDATE/SHARE en una subconsulta, por ejemplo

SELECT * FROM (SELECT * FROM mi_tabla FOR UPDATE) ss ORDER BY columna1;

Tenga en cuenta que esto bloqueará todas las filas de mi_tabla, mientras que FOR UPDATE en el nivel superior solo bloquearía las filas realmente devueltas. Esto puede suponer una diferencia significativa de rendimiento, especialmente si ORDER BY se combina con LIMIT u otras restricciones. Por lo tanto, esta técnica solo se recomienda si se esperan actualizaciones concurrentes de las columnas de ordenación y se requiere un resultado estrictamente ordenado.

En los niveles de aislamiento de transacción REPEATABLE READ o SERIALIZABLE, esto provocaría un error de serialización (con un SQLSTATE de '40001'), por lo que no hay posibilidad de recibir filas desordenadas bajo estos niveles de aislamiento.

Comando TABLE

El comando

TABLE nombre

es equivalente a

SELECT * FROM nombre

Puede usarse como comando de nivel superior o como una variante de sintaxis que ahorra espacio en partes de consultas complejas. Solo las cláusulas de bloqueo WITH, UNION, INTERSECT, EXCEPT, ORDER BY, LIMIT, OFFSET, FETCH y FOR se pueden usar con TABLE; la cláusula WHERE y cualquier forma de agregación no se pueden usar.

Este ejemplo usa WITH RECURSIVE para encontrar todos los subordinados (directos o indirectos) del empleado Mary, y su nivel de indirectez, de una tabla que muestra solo subordinados directos:

WITH RECURSIVE employee_recursive(distance, employee_name, manager_name) AS (
    SELECT 1, employee_name, manager_name
    FROM employee
    WHERE manager_name = 'Mary'
  UNION ALL
    SELECT er.distance + 1, e.employee_name, e.manager_name
    FROM employee_recursive er, employee e
    WHERE er.employee_name = e.manager_name
  )
SELECT distance, employee_name FROM employee_recursive;

Observe la forma típica de las consultas recursivas: una condición inicial, seguida de UNION, seguida de la parte recursiva de la consulta. SELECT m.name AS mname, pname
FROM manufacturers m, LATERAL get_product_names(m.id) pname;

Los fabricantes que actualmente no tienen ningún producto no aparecerían en el resultado, ya que es una unión interna. Si deseáramos incluir los nombres de dichos fabricantes en el resultado, podríamos hacer:

SELECT m.name AS mname, pname
FROM manufacturers m LEFT JOIN LATERAL get_product_names(m.id) pname ON true;

COMPATIBILIDAD

Por supuesto, la sentencia SELECT es compatible con el estándar SQL. Pero hay algunas extensiones y algunas características faltantes.

Cláusulas FROM Omitidas

PostgreSQL permite omitir la cláusula FROM. Tiene un uso directo para calcular los resultados de expresiones simples:

SELECT 2+2;
 ?column?
----------
        4

Otras bases de datos SQL no pueden hacer esto excepto introduciendo una tabla simbólica de una fila de la cual hacer el SELECT.

Listas SELECT Vacías

La lista de expresiones de salida después de SELECT puede estar vacía, produciendo una tabla de resultados de cero columnas. Esto no es sintaxis válida según el estándar SQL. PostgreSQL lo permite para ser coherente con la posibilidad de tablas de cero columnas. Sin embargo, no se permite una lista vacía cuando se usa DISTINCT.

Omisión de la Palabra Clave AS

En el estándar SQL, la palabra clave opcional AS

se puede omitir antes del nombre de una columna de salida siempre que el nuevo nombre de columna sea un nombre de columna válido (es decir, no sea el mismo que ninguna palabra clave reservada). PostgreSQL es ligeramente más restrictivo: AS es obligatorio si el nuevo nombre de columna coincide con alguna palabra clave en absoluto, reservada o no. La práctica recomendada es usar AS o comillas dobles para los nombres de las columnas de salida, para evitar cualquier posible conflicto con futuras adiciones de palabras clave.

En los elementos FROM, tanto el estándar como PostgreSQL permiten que AS se omita antes de un alias que sea una palabra clave no reservada. Pero esto es impráctico para los nombres de las columnas de salida, debido a ambigüedades sintácticas.

Omitir alias de subconsulta en FROM

Según el estándar SQL, una subconsulta SELECT en la lista FROM debe tener un alias. En PostgreSQL, este alias puede omitirse.

ONLY y herencia

El estándar SQL requiere paréntesis alrededor del nombre de la tabla al escribir ONLY, por ejemplo SELECT * FROM ONLY (tab1), ONLY (tab2) WHERE .... PostgreSQL considera que estos paréntesis son opcionales.

PostgreSQL permite escribir un * al final para especificar explícitamente el comportamiento no-ONLY de incluir tablas hijas. El estándar no permite esto.

(Estos puntos se aplican por igual a todos los comandos SQL que admiten la opción ONLY.)

Restricciones de la cláusula TABLESAMPLE

La cláusula TABLESAMPLE actualmente solo se acepta en tablas regulares y vistas materializadas. Según el estándar SQL, debería ser posible aplicarla a cualquier elemento FROM.

Llamadas a funciones en FROM

PostgreSQL permite escribir una llamada a función directamente como un miembro de la lista FROM. En el estándar SQL, sería necesario envolver dicha llamada a función en una subconsulta SELECT; es decir, la sintaxis FROM func(...) alias es aproximadamente equivalente a FROM LATERAL (SELECT func(...)) alias. Tenga en cuenta que LATERAL se considera implícito; esto se debe a que el estándar requiere semántica LATERAL para un elemento UNNEST() en FROM. PostgreSQL trata UNNEST() de la misma manera que otras funciones que devuelven conjuntos.

Espacio de nombres disponible para GROUP BY y ORDER BY

En el estándar SQL-92, una cláusula ORDER BY solo puede usar nombres o números de columna de salida, mientras que una cláusula GROUP BY solo puede usar expresiones basadas en nombres de columna de entrada. PostgreSQL extiende cada una de estas cláusulas para permitir también la otra opción (pero utiliza la interpretación del estándar si hay ambigüedad). PostgreSQL también permite que ambas cláusulas especifiquen expresiones arbitrarias. Tenga en cuenta que los nombres que aparecen en una expresión siempre se tomarán como nombres de columna de entrada, no como nombres de columna de salida.

SQL:1999 y posteriores utilizan una definición ligeramente diferente que no es totalmente compatible hacia atrás con SQL-92. En la mayoría de los casos, sin embargo, PostgreSQL interpretará una expresión ORDER BY o GROUP BY de la misma manera que lo hace SQL:1999.

Dependencias funcionales

PostgreSQL reconoce la dependencia funcional (permitiendo que las columnas se omitan de GROUP BY) solo cuando la clave principal de una tabla se incluye en la lista GROUP BY. El estándar SQL especifica condiciones adicionales que deberían ser reconocidas.

LIMIT y OFFSET

Las cláusulas LIMIT y OFFSET son sintaxis específica de PostgreSQL, también utilizada por MySQL. El estándar SQL:2008 ha introducido las cláusulas OFFSET ... FETCH {FIRST|NEXT} ... para la misma funcionalidad, como se muestra anteriormente en la Cláusula LIMIT. Esta sintaxis también es utilizada por IBM DB2. (Las aplicaciones escritas para Oracle utilizan con frecuencia una solución alternativa que involucra la columna generada automáticamente rownum, que no está disponible en PostgreSQL, para implementar los efectos de estas cláusulas).

FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE, FOR KEY SHARE

Aunque FOR UPDATE aparece en el estándar SQL, el estándar solo lo permite como una opción de DECLARE CURSOR. PostgreSQL lo permite en cualquier consulta SELECT, así como en subconsultas SELECT, pero esto es una extensión. Las variantes FOR NO KEY UPDATE, FOR SHARE y FOR KEY SHARE, así como las opciones NOWAIT y SKIP LOCKED, no aparecen en el estándar.

Sentencias de modificación de datos en WITH

PostgreSQL permite usar INSERT, UPDATE, DELETE y MERGE como consultas WITH. Esto no se encuentra en el estándar SQL.

Cláusulas no estándar

DISTINCT ON ( ... ) es una extensión del estándar SQL.

ROWS FROM( ... ) es una extensión del estándar SQL.

Las opciones MATERIALIZED y NOT MATERIALIZED de WITH son extensiones del estándar SQL.
