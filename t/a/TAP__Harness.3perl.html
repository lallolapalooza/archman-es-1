TAP::Harness(3perl) Guía de referencia del programador de Perl TAP::Harness(3perl)

NOMBRE

TAP::Harness - Ejecuta scripts de prueba con estadísticas

VERSIÓN

Versión 3.50

DESCRIPCIÓN

Este es un sencillo sistema de pruebas que permite ejecutar pruebas y agregar automáticamente los resultados y mostrarlos en STDOUT.

SINOPSIS

use TAP::Harness;
my $harness = TAP::Harness->new( \%args );
$harness->runtests(@tests);

MÉTODOS

Métodos de clase

"new"

my %args = (
   verbosity => 1,
   lib     => [ 'lib', 'blib/lib', 'blib/arch' ],
)
my $harness = TAP::Harness->new( \%args );

El constructor devuelve un nuevo objeto "TAP::Harness". Acepta un hashref opcional cuyas claves permitidas son:

  • "verbosity"

    Establece el nivel de verbosidad:

     1   verbose        Imprime los resultados individuales de las pruebas en STDOUT.
 0   normal
-1   quiet          Suprime parte de la salida de las pruebas (principalmente
                    fallos mientras se ejecutan las pruebas).
-2   really quiet   Suprime todo excepto el resumen de las pruebas.
-3   silent         Suprime todo.
  • "timer"

    Agrega el tiempo de ejecución de cada prueba a la salida. Usa Time::HiRes si está disponible.

  • "failures"

    Muestra los fallos de las pruebas (esto no tiene efecto si se selecciona "verbose").

  • "comments"

    Muestra los comentarios de las pruebas (esto no tiene efecto si se selecciona "verbose").

  • "show_count"

    Actualiza el contador de pruebas en ejecución durante la ejecución.

  • "normalize"

    Establecer a un valor verdadero para normalizar el TAP que se emite en los modos verbosos.

  • "lib"

    Acepta un valor escalar o una referencia de array de valores escalares que indican qué rutas de bibliotecas permitidas deben incluirse si se ejecutan pruebas de Perl. Naturalmente, esto solo tiene sentido en el contexto de pruebas escritas en Perl.

  • "switches"

    Acepta un valor escalar o una referencia de array de valores escalares que indican qué interruptores deben incluirse si se ejecutan pruebas de Perl. Naturalmente, esto solo tiene sentido en el contexto de pruebas escritas en Perl.

  • "test_args"

    Una referencia a un array estilo @INC de argumentos que se pasarán a cada programa de prueba.

    test_args => ['foo', 'bar'],

    si deseas pasar argumentos diferentes a cada prueba, deberías pasar un hash de arrays, indexado por el alias de cada prueba:

    test_args => {
  my_test    => ['foo', 'bar'],
  other_test => ['baz'],
}
  • "color"

    Intenta producir salida en color.

  • "exec"

    Típicamente, las pruebas de Perl se ejecutan a través de esto. Sin embargo, cualquier cosa que genere TAP está bien. Puedes usar este argumento para especificar el nombre del programa (y los interruptores opcionales) para ejecutar tus pruebas con:

    exec => ['/usr/bin/ruby', '-w']

    También puedes pasar una referencia a una subrutina para determinar y devolver el programa adecuado a ejecutar basándose en un script de prueba dado. La referencia a la subrutina debe esperar el objeto TAP::Harness en sí mismo como primer argumento, y el nombre del archivo como segundo argumento. Puede devolver una referencia de array que contenga el comando a ejecutar e incluyendo el nombre del archivo de prueba. También puede simplemente devolver "undef", en cuyo caso TAP::Harness recurrirá a la ejecución del script de prueba en Perl:

    exec => sub {
    my ( $harness, $test_file ) = @_;
    # Deja que se ejecuten las pruebas de Perl.
    return undef if $test_file =~ /[.]t$/;
    return [ qw( /usr/bin/ruby -w ), $test_file ]
      if $test_file =~ /[.]rb$/;
  }

    Si la subrutina devuelve un escalar con un salto de línea o un manejador de archivos, se interpretará como TAP en bruto o como un flujo TAP, respectivamente.

  • "merge"

    Si "merge" es verdadero, el sistema de pruebas creará analizadores que fusionarán STDOUT y STDERR para cualquier proceso que inicien.

  • "sources"

    NUEVO en 3.18.

    Si se establece, "sources" debe ser un hashref que contenga los nombres de los TAP::Parser::SourceHandlers a cargar y/o configurar. Los valores son un hash de configuración que será accesible para los manejadores de origen a través de "config_for" en TAP::Parser::Source.

    Por ejemplo:

    sources => {
  Perl => { exec => '/path/to/custom/perl' },
  File => { extensions => [ '.tap', '.txt' ] },
  MyCustom => { some => 'config' },
}

    El parámetro "sources" afecta a cómo se manejan los parámetros "source", "tap" y "exec".

    Para más detalles, ver el parámetro "sources" en "new" en TAP::Parser, TAP::Parser::Source, y TAP::Parser::IteratorFactory.

  • "aggregator_class"

    El nombre de la clase a utilizar para agregar resultados de pruebas. El valor predeterminado es TAP::Parser::Aggregator.

  • "version"

    NUEVO en 3.22.

    Asume esta versión de TAP para TAP::Parser en lugar de la versión predeterminada de TAP 12.

  • "formatter_class"

    El nombre de la clase a utilizar para formatear la salida. El valor predeterminado es TAP::Formatter::Console, o TAP::Formatter::File si la salida no es una TTY.

  • "multiplexer_class"

    El nombre de la clase a utilizar para multiplexar pruebas durante la ejecución paralela. El valor predeterminado es TAP::Parser::Multiplexer.

  • "parser_class"

    El nombre de la clase a utilizar para analizar TAP. El valor predeterminado es TAP::Parser.

  • "scheduler_class"

    El nombre de la clase a utilizar para programar la ejecución de pruebas. El valor predeterminado es TAP::Parser::Scheduler.

  • "formatter"

    Si se establece, "formatter" debe ser un objeto capaz de formatear la salida TAP. Ver TAP::Formatter::Console como ejemplo.

  • "errors"

    Si se encuentran errores de análisis en la salida TAP, se hará una nota de esto en el informe resumen. Para ver todos los errores de análisis, establece este argumento a verdadero:

    errors => 1
  • "directives"

    Si se establece a un valor verdadero, solo se mostrarán los resultados de las pruebas con directivas. Esto anula otras configuraciones como "verbose" o "failures".

  • "ignore_exit"

    Si se establece a un valor verdadero, instruye a "TAP::Parser" para ignorar el estado de salida y espera de los scripts de prueba.

  • "jobs"

    El número máximo de pruebas paralelas a ejecutar en cualquier momento. Qué pruebas se pueden ejecutar en paralelo se controla mediante "rules". El valor predeterminado es ejecutar solo una prueba a la vez.

  • "rules"

    Una referencia a un hash de reglas que controlan qué pruebas pueden ejecutarse en paralelo. Si no se declaran reglas y CPAN::Meta::YAML está disponible, "TAP::Harness" intenta cargar reglas de un archivo YAML especificado por el parámetro "rulesfile". Si no existe ningún archivo de reglas, el valor predeterminado es que todas las pruebas sean elegibles para ejecutarse en paralelo.

  • "rulesfiles"

    Esto especifica dónde encontrar un archivo YAML de reglas de programación de pruebas. Si no se proporciona, busca un archivo predeterminado para usar. Primero comprueba si hay un archivo dado en la variable de entorno "HARNESS_RULESFILE", luego comprueba testrules.yml y luego t/testrules.yml.

  • "stdout"

    Un manejador de archivos para capturar la salida estándar.

  • "trap"

    Intenta imprimir información resumida si la ejecución se interrumpe por SIGINT (Ctrl-C).

    Métodos de instancia

    "runtests"

    $harness->runtests(@tests);

    Acepta una matriz de @tests para ser ejecutada. Generalmente, estos deberían ser los nombres de los archivos de prueba, pero esto no es obligatorio. Cada elemento en @tests se pasará a TAP::Parser::new() como una "source". Consulta TAP::Parser para obtener más información.

    Es posible proporcionar alias que se mostrarán en lugar del nombre de la prueba al proporcionar la prueba como una referencia a una matriz que contiene "[ $test, $alias ]":

    $harness->runtests( [ 't/foo.t', 'Foo Una Vez' ],
                    [ 't/foo.t', 'Foo Dos Veces' ] );

    Normalmente, es un error intentar ejecutar la misma prueba dos veces. Los alias te permiten superar esta limitación al darle a cada ejecución de la prueba un nombre único.

    Las pruebas se ejecutarán en el orden en que se encuentren.

    Si la variable de entorno "PERL_TEST_HARNESS_DUMP_TAP" está definida, debería nombrar un directorio en el que se escribirá una copia del TAP sin procesar para cada prueba. El TAP se escribirá en archivos con nombre para cada prueba. Se crearán subdirectorios según sea necesario.

    Devuelve un TAP::Parser::Aggregator que contiene los resultados de la prueba.

    "summary"

    $harness->summary( $aggregator );

    Imprime el resumen de un TAP::Parser::Aggregator.

    "aggregate_tests"

    $harness->aggregate_tests( $aggregate, @tests );

    Ejecuta las pruebas nombradas y muestra un resumen del resultado. Las pruebas se ejecutarán en el orden en que se encuentren.

    Los resultados de las pruebas se añadirán al TAP::Parser::Aggregator proporcionado. Se puede llamar a "aggregate_tests" varias veces para ejecutar varios conjuntos de pruebas. Se pueden usar varias instancias de "Test::Harness" para pasar resultados a un único agregador, de modo que diferentes partes de una suite de pruebas compleja se puedan ejecutar utilizando diferentes configuraciones de "TAP::Harness". Esto es útil, por ejemplo, en el caso de que algunas pruebas deban ejecutarse en paralelo pero otras no sean adecuadas para la ejecución en paralelo.

    my $formatter   = TAP::Formatter::Console->new;
my $ser_harness = TAP::Harness->new( { formatter => $formatter } );
my $par_harness = TAP::Harness->new(
    {   formatter => $formatter,
        jobs      => 9
    }
);
my $aggregator = TAP::Parser::Aggregator->new;
$aggregator->start();
$ser_harness->aggregate_tests( $aggregator, @ser_tests );
$par_harness->aggregate_tests( $aggregator, @par_tests );
$aggregator->stop();
$formatter->summary($aggregator);

    Ten en cuenta que para requisitos de prueba más sencillos, a menudo será posible reemplazar el código anterior con una sola llamada a "runtests".

    Cada elemento de la matriz @tests es:

    • el nombre de origen de una prueba a ejecutar
    • una referencia a una matriz [ nombre de origen, nombre para mostrar ]

    En el caso de una suite de pruebas de Perl, los nombres de origen suelen ser simplemente los nombres de archivo de los scripts de prueba a ejecutar.

    Cuando proporcionas un nombre para mostrar por separado, es posible ejecutar una prueba más de una vez; el nombre para mostrar es efectivamente el alias por el que se conoce la prueba dentro del sistema de gestión. Al sistema de gestión no le importa si ejecuta la misma prueba más de una vez cuando cada invocación utiliza un nombre diferente.

    "make_scheduler"

    Llamado por el sistema de gestión cuando necesita crear un TAP::Parser::Scheduler. Anúlalo en una subclase para proporcionar un planificador alternativo. Se le pasa a "make_scheduler" la lista de pruebas que se pasó a "aggregate_tests".

    "jobs"

    Obtiene o establece el número de ejecuciones de pruebas concurrentes que está gestionando el sistema de gestión. Por defecto, este valor es 1; para pruebas paralelas, este valor debe ser mayor.

    "make_parser"

    Crea una nueva sesión de analizador y formateador de pantalla. Normalmente se utiliza y/o se anula en subclases.

    my ( $parser, $session ) = $harness->make_parser;

    "finish_parser"

    Termina el uso de un analizador. Normalmente se utiliza y/o se anula en subclases. El analizador no se destruye como resultado de esto.

    CONFIGURACIÓN

    "TAP::Harness" está diseñado para ser fácil de configurar.

    Plugins

    Los plugins de "TAP::Parser" te permiten cambiar la forma en que el TAP se *introduce* y se *emite* desde el analizador.

    Los TAP::Parser::SourceHandlers manejan la *entrada* de TAP. Puedes configurarlos y cargar manejadores personalizados utilizando el parámetro "sources" de "new".

    Los TAP::Formatters manejan la *salida* de TAP. Puedes cargar formateadores personalizados utilizando el parámetro "formatter_class" de "new". Para configurar un formateador, actualmente necesitas instanciarlo fuera de TAP::Harness y pasarlo con el parámetro "formatter" a "new". Esto *podría* abordarse añadiendo un parámetro *formatters* a "new" en el futuro.

    "Module::Build"

    Module::Build versión 0.30 admite "TAP::Harness".

    Para cargar plugins de "TAP::Harness", necesitarás usar el parámetro "tap_harness_args" de "new", típicamente desde tu "Build.PL". Por ejemplo:

    Module::Build->new(
    module_name        => 'MyApp',
    test_file_exts     => [qw(.t .tap .txt)],
    use_tap_harness    => 1,
    tap_harness_args   => {
        sources => {
            MyCustom => {},
            File => {
                extensions => ['.tap', '.txt'],
            },
        },
        formatter_class => 'TAP::Formatter::HTML',
    },
    build_requires     => {
        'Module::Build' => '0.30',
        'TAP::Harness'  => '3.18',
    },
)->create_build_script;

    Consulta "new"

    "ExtUtils::MakeMaker"

    ExtUtils::MakeMaker no admite TAP::Harness directamente.

    "prove"

    prove admite plugins de "TAP::Harness", y tiene su propio sistema de plugins. Consulta "FORMATTERS" en prove, "SOURCE HANDLERS" en prove y App::Prove para obtener más detalles.

    ESCRIBIR PLUGINS

    Si no puedes configurar "TAP::Harness" para hacer lo que quieres y no puedes encontrar un plugin existente, considera escribir uno.

    Los dos casos de uso principales admitidos por TAP::Harness para plugins son la *entrada* y la *salida*:

    Personalizar cómo el TAP entra en el analizador
    Para hacer esto, puedes extender un TAP::Parser::SourceHandler existente o escribir el tuyo propio. Es una API bastante sencilla y se pueden cargar y configurar utilizando el parámetro "sources" de "new".
    Personalizar cómo los resultados del TAP se emiten desde el analizador
    Para hacer esto, puedes extender un TAP::Formatter existente o escribir el tuyo propio. Escribir formateadores es un poco más complicado que escribir un *SourceHandler*, ya que necesitarás comprender la API de TAP::Parser. Un buen punto de partida es comprender cómo funciona "aggregate_tests".

    Los formateadores personalizados se pueden cargar y configurar utilizando el parámetro "formatter_class" de "new".

    TAP::Harness::Base - Manual de ArchWiki

    NAME

    TAP::Harness::Base - Base class for test harnesses

    VERSION

    This document describes TAP::Harness::Base version 3.44.

    DESCRIPTION

    TAP::Harness::Base is the base class for TAP::Harness. You'll generally not need to use it directly, but it provides a good structure for writing your own test harness if you wish.

    SYNOPSIS

        use TAP::Harness::Base;
                    my $harness = TAP::Harness::Base->new({ ... });
                    my $results = $harness->runtests(@tests);

    CONFIGURING

    The constructor new takes a hash reference of arguments. The most important ones are:

    "jobs"
    Set the number of jobs to run tests in parallel.
    "stdout_data"
    If true, capture STDOUT data from tests.
    "stderr_data"
    If true, capture STDERR data from tests.
    "merge"
    If true, merge STDERR into STDOUT.
    "formatter"
    The formatter to use for test output.
    "merge_formatter"
    The formatter to use for merged output.

    WRITING PLUGINS

    If you need to customize the behavior of TAP::Harness, you can write a plugin. The plugin should be a subclass of TAP::Harness::Base and should override the methods you want to change.

    SUBCLASSING

    If writing a plugin isn't an option, consider extending it. It is designed to be (mostly) easy to subclass, though the cases when sub-classing is necessary should be few and far between.

    Methods

    The following methods are ones you may wish to override if you want to subclass "TAP::Harness".

    "new"
    "runtests"
    "summary"

    REPLACING

    If you like the "prove" utility and TAP::Parser but you want your own harness, all you need to do is write one and provide "new" and "runtests" methods. Then you can use the "prove" utility like so:

    prove --harness My::Test::Harness

    Note that while "prove" accepts a list of tests (or things to be tested), "new" has a fairly rich set of arguments. You'll probably want to read over this code carefully to see how all of them are being used.
