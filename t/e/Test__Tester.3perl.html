NAME

Test::Tester - Facilita la prueba de módulos de prueba construidos con Test::Builder

SYNOPSIS

use Test::Tester tests => 6;
use Test::MyStyle;
check_test(
  sub {
    is_mystyle_eq("this", "that", "not eq");
  },
  {
    ok => 0, # esperamos que esto falle
    name => "not eq",
    diag => "Expected: 'this'\nGot: 'that'",
  }
);

o

use Test::Tester tests => 6;
use Test::MyStyle;
check_test(
  sub {
    is_mystyle_qr("this", "that", "not matching");
  },
  {
    ok => 0, # esperamos que esto falle
    name => "not matching",
    diag => qr/Expected: 'this'\s+Got: 'that'/,
  }
);

o

use Test::Tester;
use Test::More tests => 3;
use Test::MyStyle;
my ($premature, @results) = run_tests(
  sub {
    is_database_alive("dbname");
  }
);
# ahora usa Test::More::like para comprobar la salida del diagnóstico
like($results[0]->{diag}, "/^Database ping took \\d+ seconds$"/, "diag");

DESCRIPTION

Si ha escrito un módulo de prueba basado en Test::Builder, entonces Test::Tester le permite probarlo con el mínimo esfuerzo.

CÓMO USAR (LA FORMA FÁCIL)

A partir de la versión 0.08, Test::Tester ya no requiere que incluya nada especial en sus módulos de prueba. Todo lo que necesita hacer es

use Test::Tester;

en su script de prueba **antes** de cualquier otro módulo basado en Test::Builder y listo.

Se pueden utilizar otros módulos basados en Test::Builder para ayudar con las pruebas. De hecho, incluso puede usar funciones de su módulo para probar otras funciones del mismo módulo (aunque esto es posible, probablemente no sea una buena idea; si su módulo tiene errores, usarlo para probarse a sí mismo podría dar respuestas incorrectas).

La forma más fácil de probar es hacer algo como

check_test(
  sub { is_mystyle_eq("this", "that", "not eq") },
  {
    ok => 0, # esperamos que la prueba falle
    name => "not eq",
    diag => "Expected: 'this'\nGot: 'that'",
  }
);

esto ejecutará la prueba is_mystyle_eq, capturando sus resultados y comprobando que son lo que se esperaba.

Puede que necesite examinar los resultados de la prueba de una manera más flexible; por ejemplo, la salida de diagnóstico puede ser bastante larga o compleja, o puede implicar algo que no puede predecir de antemano, como una marca de tiempo. En este caso, puede obtener acceso directo a los resultados de la prueba:

my ($premature, @results) = run_tests(
  sub {
    is_database_alive("dbname");
  }
);
like($result[0]->{diag}, "/^Database ping took \\d+ seconds$"/, "diag");

o

check_test(
  sub { is_mystyle_qr("this", "that", "not matching") },
  {
    ok => 0, # esperamos que la prueba falle
    name => "not matching",
    diag => qr/Expected: 'this'\s+Got: 'that'/,
  }
);

No podemos predecir cuánto tardará el ping de la base de datos, por lo que usamos la prueba like() de Test::More para comprobar que la cadena de diagnóstico tiene la forma correcta.

CÓMO USAR (LA FORMA DIFÍCIL)

Esto está aquí solo por compatibilidad hacia atrás

Haga que su módulo utilice el objeto Test::Tester::Capture en lugar del de Test::Builder. Cómo hacer esto depende de su módulo, pero asumiendo que su módulo guarda el objeto Test::Builder en $Test y que todas sus rutinas de prueba acceden a él a través de $Test, entonces proporcionar una función como esta

sub set_builder
{
  $Test = shift;
}

debería permitir que sus scripts de prueba hagan

Test::YourModule::set_builder(Test::Tester->capture);

y después de eso, todas las pruebas dentro de su módulo serán capturadas.

RESULTADOS DE LA PRUEBA

El resultado de cada prueba se captura en un hash. Estos hashes son los mismos que los hashes devueltos por Test::Builder->details, pero con un par de campos adicionales.

Estos campos se documentan en Test::Builder en la función details()

ok
¿Pasó la prueba?
actual_ok
¿La prueba realmente pasó? Es decir, ¿el pase provino de Test::Builder->ok() o pasó porque era una prueba TODO?
name
El nombre proporcionado para la prueba.
type
¿Qué tipo de prueba? Las posibilidades incluyen skip, todo, etc. Ver Test::Builder para más detalles.
reason
La razón del skip, todo, etc. Ver Test::Builder para más detalles.

Estos campos son exclusivos de Test::Tester.

diag
Cualquier diagnóstico que se haya emitido para la prueba. Esto solo incluye diagnósticos emitidos **después** de que se declara el resultado de la prueba.

Tenga en cuenta que Test::Builder asegura que cualquier diagnóstico termine en \n y que en versiones anteriores de Test::Tester era esencial que tuviera el \n final en sus diagnósticos esperados. A partir de la versión 0.10, Test::Tester agregará el \n si lo olvidó. No agregará un \n si no espera ningún diagnóstico. Vea abajo para obtener ayuda para rastrear problemas difíciles de espacios y tabulaciones.

depth
Esto le permite comprobar que su módulo de prueba está estableciendo el valor correcto para $Test::Builder::Level y, por lo tanto, proporcionando el archivo y el número de línea correctos cuando una prueba falla. Se calcula mirando caller() y $Test::Builder::Level. Debe contar cuántas subrutinas hay antes de saltar a la función que está probando. Así, por ejemplo, en 
run_tests( sub { my_test_function("a", "b") } );

la profundidad debe ser 1 y en

sub deeper { my_test_function("a", "b") }
run_tests(sub { deeper() });

la profundidad debe ser 2, es decir, 1 por el sub {} y uno por deeper(). Esto puede parecer un poco complejo, pero si sus pruebas se ven como los ejemplos simples en este documento, entonces no necesita preocuparse, ya que la profundidad siempre será 1 y eso es lo que Test::Tester espera por defecto.

Nota: si no especifica un valor para la profundidad en check_test(), entonces lo compara automáticamente con 1; si realmente desea omitir la prueba de profundidad, pase undef.

Nota: la profundidad no se calculará correctamente para pruebas que se ejecutan desde un manejador de señales o un bloque END o cualquier otro lugar que oculte la pila de llamadas.

Algunas de las funciones de Test::Tester devuelven arreglos de estos hashes, al igual que Test::Builder->details. Es decir, el hash para la primera prueba será el elemento 1 del arreglo (no el 0). El elemento 0 no será un hash, será una cadena que contendrá cualquier salida de diagnóstico que estuvo antes del primer resultado de la prueba. Por lo general, esto debería estar vacío; si no lo está, significa que algo emitió diagnósticos antes de que aparecieran los resultados de la prueba.

ESPACIOS Y TABULACIONES

Las apariencias pueden ser engañosas, especialmente cuando se trata de vacíos. Si se rasca la cabeza intentando averiguar por qué Test::Tester dice que sus diagnósticos están mal cuando parecen perfectos, la respuesta es probablemente el espacio en blanco. A partir de la versión 0.10, Test::Tester rodea los valores de diagnóstico esperados y obtenidos con comillas simples para que sea más fácil detectar espacios en blanco finales. Así que en este ejemplo

# Got diag (5 bytes):
# 'abcd '
# Expected diag (4 bytes):
# 'abcd'

está bastante claro que hay un espacio al final de la primera cadena. Otra forma de resolver este problema es usar color y video inverso en una terminal ANSI; vea a continuación COLOUR si desea esto.

Desafortunadamente, esto a veces no es suficiente; ni el color ni las comillas le ayudarán con problemas que involucren tabulaciones, otros caracteres no imprimibles y ciertos tipos de problemas inherentes a Unicode. ESPACIOS Y TABULACIONES

Si desea ver los caracteres de espacio, tabulación y retorno de carro tal como son, puede activar un modo especial en el que estos caracteres se muestran con su código ASCII exacto. Esto hace que la salida sea más difícil de leer pero mucho más fácil para encontrar diferencias sutiles entre cadenas. Para activar este modo, llame a show_space() en su script de prueba o establezca la variable de entorno "TESTTESTERSPACE" a un valor verdadero. El ejemplo anterior se vería así:

# Got diag (5 bytes):
# abcd\x{20}
# Expected diag (4 bytes):
# abcd

COLOR

Si prefiere usar el color como medio para encontrar caracteres de espacio en blanco complicados, puede establecer la variable de entorno "TESTTESTCOLOUR" a un par de colores separados por comas, el primero para el primer plano y el segundo para el fondo. Por ejemplo, "white,red" imprimirá texto blanco sobre un fondo rojo. Esto requiere el módulo Term::ANSIColor. Puede especificar cualquier color que sea aceptable para la función Term::ANSIColor::color.

Si escribe color de forma diferente, no hay problema. La variable "TESTTESTERCOLOR" también funciona (si se establecen ambas, la ortografía británica prevalece).

FUNCIONES EXPORTADAS

($premature, @results) = run_tests(\&test_sub)

\&test_sub es una referencia a una subrutina.

run_tests ejecuta la subrutina en $test_sub y captura los resultados de cualquier prueba dentro de ella. Puede ejecutar más de 1 prueba dentro de esta subrutina si lo desea.

$premature es una cadena que contiene cualquier salida de diagnóstico de antes de la primera prueba.

@results es una matriz de hashes de resultados de pruebas.

cmp_result(\%result, \%expect, $name)

\%result es una referencia a un hash de resultados de pruebas.

\%expect es una referencia a un hash de valores esperados para el resultado de la prueba.

cmp_result compara el resultado con los valores esperados. Si se encuentran diferencias, genera diagnósticos. Puede omitir cualquier campo del resultado esperado y cmp_result no realizará la comparación de ese campo.

cmp_results(\@results, \@expects, $name)

\@results es una referencia a una matriz de resultados de pruebas.

\@expects es una referencia a una matriz de referencias a hashes.

cmp_results verifica que los resultados coincidan con los resultados esperados y, si se encuentran diferencias, genera diagnósticos. Primero verifica que el número de elementos en \@results y \@expects sea el mismo. Luego, recorre cada resultado, verificándolo contra el resultado esperado como en cmp_result() arriba.

($premature, @results) = check_tests(\&test_sub, \@expects, $name)

\&test_sub es una referencia a una subrutina.

\@expect es una referencia a una matriz de referencias a hashes que son los resultados esperados de las pruebas.

check_tests combina run_tests y cmp_tests en una sola llamada. También verifica si las pruebas fallaron en alguna etapa.

Devuelve los mismos valores que run_tests, por lo que puede examinar más a fondo los resultados de las pruebas si es necesario.

($premature, @results) = check_test(\&test_sub, \%expect, $name)

\&test_sub es una referencia a una subrutina.

\%expect es una referencia a un hash de valores esperados para el resultado de la prueba.

check_test es un envoltorio alrededor de check_tests. Combina run_tests y cmp_tests en una sola llamada, verificando si la prueba falló. Asume que solo se ejecuta una sola prueba dentro de \&test_sub e incluye una prueba para asegurarse de que esto sea cierto.

Devuelve los mismos valores que run_tests, por lo que puede examinar más a fondo los resultados de las pruebas si es necesario.

show_space()

Activa el escape de caracteres como se describe en la sección ESPACIOS Y TABULACIONES.

CÓMO FUNCIONA

Normalmente, un módulo de prueba (llamémoslo Test::MyStyle) llama a Test::Builder->new para obtener el objeto Test::Builder. Test::MyStyle llama a métodos en este objeto para registrar información sobre los resultados de las pruebas. Cuando se carga Test::Tester, reemplaza el método new() de Test::Builder con uno que devuelve un objeto Test::Tester::Delegate. La mayor parte del tiempo, este objeto se comporta como el objeto real de Test::Builder. Cualquier método que se llame se delega al objeto real de Test::Builder, por lo que todo funciona perfectamente. Sin embargo, una vez que entramos en modo de prueba, las llamadas a los métodos ya no se pasan al objeto real de Test::Builder, sino que van al objeto Test::Tester::Capture. Este objeto parece exactamente como el objeto real de Test::Builder, excepto que, en lugar de generar resultados de pruebas y diagnósticos, simplemente registra toda la información para su análisis posterior.

SALVEDADES

El soporte para llamar a Test::Builder->note es mínimo. Se implementa como un stub vacío, por lo que los módulos que lo utilizan no fallarán, pero las llamadas no se registran para fines de prueba como los demás. Se aceptan parches.

VER TAMBIÉN

Test::Builder la fuente de bondad para pruebas. Test::Builder::Tester para un enfoque alternativo al problema abordado por Test::Tester: captura las cadenas generadas por Test::Builder. Esto significa que no puede obtener acceso separado a las piezas individuales de información y debe predecir exactamente lo que generará su prueba.
