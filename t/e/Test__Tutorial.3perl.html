Nueces y tornillos de las pruebas.

Este es el programa de prueba más básico.

#!/usr/bin/perl -w
print "1..1\n";
print 1 + 1 == 2 ? "ok 1\n" : "not ok 1\n";

Como 1 + 1 es 2, imprime:

1..1
ok 1

Lo que esto dice es: 1..1 "Voy a ejecutar una prueba." [1] "ok 1" "La primera prueba pasó". Y eso es casi toda la magia que hay en las pruebas. Su unidad básica de prueba es el ok. Por cada cosa que prueba, se imprime un "ok". Simple. Test::Harness interpreta los resultados de sus pruebas para determinar si tuvo éxito o falló (más sobre eso más adelante).

Escribir todas estas sentencias `print` se vuelve tedioso rápidamente. Afortunadamente, existe Test::Simple. Tiene una función, ok().

#!/usr/bin/perl -w
use Test::Simple tests => 1;
ok( 1 + 1 == 2 );

Eso hace lo mismo que el código anterior. ok() es la columna vertebral de las pruebas de Perl, y la usaremos en lugar de hacerlo nosotros mismos a partir de ahora. Si ok() recibe un valor verdadero, la prueba pasa. Falso, falla.

#!/usr/bin/perl -w
use Test::Simple tests => 2;
ok( 1 + 1 == 2 );
ok( 2 + 2 == 5 );

De eso proviene:

1..2
ok 1
not ok 2
#     Failed test (test.pl at line 5)
# Looks like you failed 1 tests of 2.

1..2 "Voy a ejecutar dos pruebas." Este número es un plan. Ayuda a asegurar que su programa de prueba se ejecutó completamente y no murió o se saltó algunas pruebas. "ok 1" "La primera prueba pasó." "not ok 2" "La segunda prueba falló". Test::Simple imprime útilmente algunos comentarios adicionales sobre sus pruebas.

No es aterrador. Venga, tome mi mano. Vamos a dar un ejemplo de cómo probar un módulo. Para nuestro ejemplo, probaremos una biblioteca de fechas, Date::ICal. Está en CPAN, así que descargue una copia y siga el ejemplo. [2]

¿Por dónde empezar?

Esta es la parte más difícil de las pruebas, ¿por dónde empezar? La gente a menudo se siente abrumada por la aparente enormidad de la tarea de probar un módulo completo. El mejor lugar para empezar es por el principio. Date::ICal es un módulo orientado a objetos, y eso significa que se empieza creando un objeto. Pruebe new().

#!/usr/bin/perl -w
# asuma que estas dos líneas están en todos los ejemplos subsiguientes
use strict;
use warnings;
use Test::Simple tests => 2;
use Date::ICal;
my $ical = Date::ICal->new;         # crear un objeto
ok( defined $ical );                # comprobar que obtuvimos algo
ok( $ical->isa('Date::ICal') );     # y que es la clase correcta

Ejecute eso y debería obtener:

1..2
ok 1
ok 2

¡Felicidades! Ha escrito su primera prueba útil.

Nombres

Esa salida no es muy descriptiva, ¿verdad? Cuando tiene dos pruebas, puede averiguar cuál es la #2, pero ¿qué pasa si tiene 102 pruebas?

Cada prueba puede tener un pequeño nombre descriptivo como segundo argumento para ok().

use Test::Simple tests => 2;
ok( defined $ical,              'new() devolvió algo' );
ok( $ical->isa('Date::ICal'),   "  y es la clase correcta" );

Ahora verá:

1..2
ok 1 - new() devolvió algo
ok 2 -   y es la clase correcta

Probar el manual

La forma más sencilla de crear un conjunto de pruebas decente es simplemente probar lo que dice el manual que hace. [3] Extraigamos algo del "SYNOPSIS" en Date::ICal y probemos que todas sus partes funcionan.

#!/usr/bin/perl -w
use Test::Simple tests => 8;
use Date::ICal;
$ical = Date::ICal->new( year => 1964, month => 10, day => 16,
                         hour => 16,   min   => 12, sec => 47,
                         tz   => '0530' );
ok( defined $ical,            'new() devolvió algo' );
ok( $ical->isa('Date::ICal'), "  y es la clase correcta" );
ok( $ical->sec   == 47,       '  sec()'   );
ok( $ical->min   == 12,       '  min()'   );
ok( $ical->hour  == 16,       '  hour()'  );
ok( $ical->day   == 17,       '  day()'   );
ok( $ical->month == 10,       '  month()' );
ok( $ical->year  == 1964,     '  year()'  );

Ejecute eso y obtendrá:

1..8
ok 1 - new() devolvió algo
ok 2 -   y es la clase correcta
ok 3 -   sec()
ok 4 -   min()
ok 5 -   hour()
not ok 6 -   day()
#     Failed test (- at line 16)
ok 7 -   month()
ok 8 -   year()
# Looks like you failed 1 tests of 8.

¡Ups, un fallo! [4] Test::Simple nos informa útilmente en qué línea ocurrió el fallo, pero no mucho más. Se suponía que debíamos obtener 17, pero no lo hicimos. ¿Qué obtuvimos? Ni idea. Podría volver a ejecutar la prueba en el depurador o insertar algunas sentencias `print` para averiguarlo.

En cambio, cambie de Test::Simple a Test::More. Test::More hace todo lo que hace Test::Simple, ¡y más! De hecho, Test::More hace las cosas *exactamente* como las hace Test::Simple. Literalmente puede reemplazar Test::Simple y poner Test::More en su lugar. Eso es exactamente lo que vamos a hacer.

Test::More hace más que Test::Simple. La diferencia más importante en este punto es que proporciona formas más informativas de decir "ok". Aunque puede escribir casi cualquier prueba con un ok() genérico, no puede decirle qué salió mal. La función is() nos permite declarar que algo se supone que es igual a algo más:

use Test::More tests => 8;
use Date::ICal;
$ical = Date::ICal->new( year => 1964, month => 10, day => 16,
                         hour => 16,   min   => 12, sec => 47,
                         tz   => '0530' );
ok( defined $ical,            'new() devolvió algo' );
ok( $ical->isa('Date::ICal'), "  y es la clase correcta" );
is( $ical->sec,     47,       '  sec()'   );
is( $ical->min,     12,       '  min()'   );
is( $ical->hour,    16,       '  hour()'  );
is( $ical->day,     17,       '  day()'   );
is( $ical->month,   10,       '  month()' );
is( $ical->year,    1964,     '  year()'  );

"¿Es "$ical->sec" 47?" "¿Es "$ical->min" 12?" Con is() en su lugar, obtiene más información:

1..8
ok 1 - new() devolvió algo
ok 2 -   y es la clase correcta
ok 3 -   sec()
ok 4 -   min()
ok 5 -   hour()
not ok 6 -   day()
#     Failed test (- at line 16)
#          got: '16'
#     expected: '17'
ok 7 -   month()
ok 8 -   year()
# Looks like you failed 1 tests of 8.

Ajá. "$ical->day" devolvió 16, pero esperábamos 17. Una rápida comprobación muestra que el código está funcionando bien, cometimos un error al escribir las pruebas. Cámbielo a:

is( $ical->day,     16,       '  day()'   );

... y todo funciona.

En cualquier momento que esté haciendo un tipo de prueba de "esto es igual a aquello", use is(). Incluso funciona en matrices. La prueba siempre está en contexto escalar, por lo que puede probar cuántos elementos hay en una matriz de esta manera. [5]

is( @foo, 5, 'foo tiene 5 elementos' );

A veces las pruebas están mal

Esto nos lleva a una lección muy importante. El código tiene errores. Las pruebas son código. Ergo, las pruebas tienen errores. Una prueba fallida podría significar un error en el código, pero no descarte la posibilidad de que la prueba esté mal.

Probando muchos valores

Vamos a querer probar muchas fechas aquí, intentando engañar al código con muchos casos límite diferentes. ¿Funciona antes de 1970? ¿Después de 2038? ¿Antes de 1904? ¿Los años después del 10.000 le dan problemas? ¿Los años bisiestos los maneja correctamente? Podríamos seguir repitiendo el código anterior, o podríamos configurar un pequeño bucle try/expect.

use Test::More tests => 32;
use Date::ICal;
my %ICal_Dates = (
        # Una cadena ICal     Y el año, mes, día
        #                    hora, minuto y segundo que esperamos.
        '19971024T120000' =>    # de la documentación.
                            [ 1997, 10, 24, 12,  0,  0 ],
        '20390123T232832' =>    # después de la época Unix
                            [ 2039,  1, 23, 23, 28, 32 ],
        '19671225T000000' =>    # antes de la época Unix
                            [ 1967, 12, 25,  0,  0,  0 ],
        '18990505T232323' =>    # antes de la época de MacOS
                            [ 1899,  5,  5, 23, 23, 23 ],
);
while( my($ical_str, $expect) = each %ICal_Dates ) {
    my $ical = Date::ICal->new( ical => $ical_str );
    ok( defined $ical,            "new(ical => '$ical_str')" );
    ok( $ical->isa('Date::ICal'), "  y es la clase correcta" );
    is( $ical->year,    $expect->[0],     '  year()'  );
    is( $ical->month,   $expect->[1],     '  month()' );
    is( $ical->day,     $expect->[2],     '  day()'   );
    is( $ical->hour,    $expect->[3],     '  hour()'  );
    is( $ical->min,     $expect->[4],     '  min()'   );
    is( $ical->sec,     $expect->[5],     '  sec()'   );
}

Ahora podemos probar montones de fechas simplemente añadiéndolas a %ICal_Dates. Ahora que requiere menos esfuerzo probar con más fechas, te inclinarás a añadir más a medida que se te ocurran. El único problema es que cada vez que añadimos algo, tenemos que seguir ajustando la línea "use Test::More tests => ##". Eso puede volverse molesto rápidamente. Hay formas de hacer que esto funcione mejor.

Primero, podemos calcular el plan dinámicamente usando la función plan().

use Test::More;
use Date::ICal;
my %ICal_Dates = (
    ...lo mismo que antes...
);
# Por cada clave en el hash, ejecutamos 8 pruebas.
plan tests => keys(%ICal_Dates) * 8;
...y luego tus pruebas...

Para ser aún más flexible, usa "done_testing". Esto significa que solo estamos ejecutando algunas pruebas, no sabemos cuántas. [6]

use Test::More;   # en lugar de tests => 32
... # pruebas aquí
done_testing();   # llegamos al final de forma segura

Si no especificas un plan, Test::More espera ver done_testing() antes de que tu programa termine. Te advertirá si lo olvidas. Puedes darle a done_testing() un número opcional de pruebas que esperabas ejecutar, y si el número ejecutado difiere, Test::More te dará otro tipo de advertencia.

Nombres informativos

Echa un vistazo a la línea:

ok( defined $ical,            "new(ical => '$ical_str')" );

Hemos añadido más detalles sobre lo que estamos probando y la cadena ICal que estamos probando a continuación. Así obtienes resultados como:

ok 25 - new(ical => '19971024T120000')
ok 26 -   y es la clase correcta
ok 27 -   year()
ok 28 -   month()
ok 29 -   day()
ok 30 -   hour()
ok 31 -   min()
ok 32 -   sec()

Si algo falla, sabrás cuál fue y eso facilitará la localización del problema. Intenta añadir información de depuración a los nombres de las pruebas.

Describe lo que prueban las pruebas, para que sea más fácil depurar una prueba fallida para ti o para la próxima persona que ejecute tu prueba.

Omitiendo pruebas

Revisando las pruebas existentes de Date::ICal, encontré esto en t/01sanity.t [7]

#!/usr/bin/perl -w
use Test::More tests => 7;
use Date::ICal;
# Asegúrate de que el tiempo de época se maneja correctamente.
my $t1 = Date::ICal->new( epoch => 0 );
is( $t1->epoch, 0,          "Tiempo de época de 0" );
# XXX Esto solo funcionará en sistemas Unix.
is( $t1->ical, '19700101Z', "  época a ICal" );
is( $t1->year,  1970,       "  year()"  );
is( $t1->month, 1,          "  month()" );
is( $t1->day,   1,          "  day()"   );
# igual que las pruebas anteriores, pero comenzando con ical en lugar de epoch
my $t2 = Date::ICal->new( ical => '19700101Z' );
is( $t2->ical, '19700101Z', "Inicio de la época en notación ICal" );
is( $t2->epoch, 0,          "  y de vuelta a ICal" );

El inicio de la época es diferente en la mayoría de los sistemas operativos no Unix [8]. Aunque Perl suaviza las diferencias en su mayor parte, ciertos puertos lo hacen de manera diferente. MacPerl es uno que recuerdo de inmediato. [9] En lugar de poner un comentario en la prueba y esperar que alguien lea la prueba al depurar el fallo, podemos decir explícitamente que nunca va a funcionar y omitir la prueba.

use Test::More tests => 7;
use Date::ICal;
# Asegúrate de que el tiempo de época se maneja correctamente.
my $t1 = Date::ICal->new( epoch => 0 );
is( $t1->epoch, 0,          "Tiempo de época de 0" );
SKIP: {
    skip('La conversión de época a ICal no funciona en Mac OS', 6)
        if $^O eq 'MacOS';
    is( $t1->ical, '19700101Z', "  época a ICal" );
    is( $t1->year,  1970,       "  year()"  );
    is( $t1->month, 1,          "  month()" );
    is( $t1->day,   1,          "  day()"   );
    # igual que las pruebas anteriores, pero comenzando con ical en lugar de epoch
    my $t2 = Date::ICal->new( ical => '19700101Z' );
    is( $t2->ical, '19700101Z', "Inicio de la época en notación ICal" );
    is( $t2->epoch, 0,          "  y de vuelta a ICal" );
}

Aquí ocurre un poco de magia. Cuando se ejecuta en cualquier cosa que no sea MacOS, todas las pruebas se ejecutan normalmente. Pero en MacOS, skip() hace que todo el contenido del bloque SKIP se omita. Nunca se ejecuta. En su lugar, skip() imprime una salida especial que le dice a Test::Harness que las pruebas han sido omitidas.

1..7
ok 1 - Tiempo de época de 0
ok 2 # skip La conversión de época a ICal no funciona en Mac OS
ok 3 # skip La conversión de época a ICal no funciona en Mac OS
ok 4 # skip La conversión de época a ICal no funciona en Mac OS
ok 5 # skip La conversión de época a ICal no funciona en Mac OS
ok 6 # skip La conversión de época a ICal no funciona en Mac OS
ok 7 # skip La conversión de época a ICal no funciona en Mac OS

Esto significa que tus pruebas no fallarán en MacOS. Esto significa menos correos electrónicos de usuarios de MacPerl informándote sobre pruebas fallidas que sabes que nunca funcionarán. Tienes que tener cuidado con las pruebas omitidas. Estas son para pruebas que no funcionan y que *nunca funcionarán*. No es para omitir errores genuinos (llegaremos a eso en un momento).

Las pruebas se omiten total y completamente. [10] Esto funcionará.

SKIP: {
    skip("¡No quiero morir!");
    die, die, die, die, die;
}

Pruebas TODO

Mientras ojeaba la página del manual de Date::ICal, me encontré con esto:

ical
    $ical_string = $ical->ical;
Recupera, o establece, la fecha en el objeto, usando cualquier
cadena de fecha/hora ICal válida.

"Recupera o establece". Hmmm. No vi una prueba para usar ical() para establecer la fecha en la suite de pruebas de Date::ICal. Así que escribí una:

use Test::More tests => 1;
use Date::ICal;
my $ical = Date::ICal->new;
$ical->ical('20201231Z');
is( $ical->ical, '20201231Z',   'Estableciendo vía ical()' );

Ejecuta eso. Vi:

1..1
not ok 1 - Estableciendo vía ical()
#     Failed test (- at line 6)
#          got: '20010814T233649Z'
#     expected: '20201231Z'
# Parece que fallaste 1 prueba de 1.

¡Ups! Parece que no está implementado. Supón que no tienes tiempo para arreglar esto. [11] Normalmente, simplemente comentarías la prueba y pondrías una nota en una lista de tareas pendientes en algún lugar. En su lugar, indica explícitamente "esta prueba fallará" envolviéndola en un bloque "TODO":

use Test::More tests => 1;
TODO: {
    local $TODO = 'ical($ical) aún no implementado';
    my $ical = Date::ICal->new;
    $ical->ical('20201231Z');
    is( $ical->ical, '20201231Z',   'Estableciendo vía ical()' );
}

Ahora, cuando ejecutas, es un poco diferente:

1..1
not ok 1 - Estableciendo vía ical() # TODO ical($ical) aún no implementado
#          got: '20010822T201551Z'
#     expected: '20201231Z'

Test::More no dice "Parece que fallaste 1 prueba de 1". Ese '# TODO' le dice a Test::Harness "se supone que esto va a fallar" y trata un fallo como una prueba exitosa. Puedes escribir pruebas incluso antes de haber arreglado el código subyacente.

Si una prueba TODO tiene éxito, Test::Harness la informará como "ÉXITO INESPERADO". Cuando eso suceda, elimina el bloque TODO con "local $TODO" y conviértelo en una prueba real.

Probando con modo de prohibición (taint mode).

El modo de prohibición es algo curioso. Es la más global de todas las características globales. Una vez que lo activas, afecta a *todo* el código de tu programa y a *todos* los módulos utilizados (y a todos los módulos que ellos usan). Si una sola pieza de código no está limpia para la prohibición, todo explota. Con esto en mente, es muy importante asegurarse de que tu módulo funcione en modo de prohibición.

Es muy sencillo hacer que tus pruebas se ejecuten en modo de prohibición. Simplemente añade un "-T" a la línea "#!". Test::Harness leerá los interruptores en "#!" y los usará para ejecutar tus pruebas.

#!/usr/bin/perl -Tw
...prueba normalmente aquí...

Cuando digas "make test", se ejecutará con el modo de prohibición activado.

NAME

Test::Tutorial - A tutorial for writing tests

DESCRIPTION

This is a tutorial for writing tests in Perl using the Test::* modules.

It covers the basics of testing, including:

  • What tests are and why they are important.
  • How to write simple tests using Test::Simple.
  • How to use more advanced features like Test::More.
  • How to handle common testing scenarios.

This tutorial is intended for developers who are new to testing in Perl or who want to improve their testing practices.

FOOTNOTES

1.
The TODO tests are marked with a special comment # TODO. These tests are not run by default, but they can be run explicitly by setting the PERL_TEST_TODO environment variable.
2.
The SKIP tests are marked with a special comment # SKIP. These tests are skipped by default, but they can be run explicitly by setting the PERL_TEST_SKIP environment variable.
3.
The BAIL_OUT function is used to immediately exit the test suite with a non-zero exit code. This is useful for critical failures that should prevent further testing.
4.
The Test::More module provides a number of convenience functions for writing tests, such as ok, is, ne, etc. It also provides support for TODO and SKIP tests.
5.
The diag function can be used to print diagnostic messages to standard error. These messages are ignored by the test runner, but they can be helpful for debugging.
6.
