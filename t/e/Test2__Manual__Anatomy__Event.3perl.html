NOMBRE

Test2::Manual::Anatomy::Event - Los detalles internos de los eventos

DESCRIPCIÓN

Los eventos son la forma en que las herramientas afectan el estado global y transmiten información al harness (sistema de ejecución de pruebas) o al humano que ejecuta las pruebas.

HISTORIA

Antes de continuar, es importante que conozcas algo de historia sobre los eventos. Inicialmente existía una API de eventos, y un evento implementaba la API para producir un efecto. Esta API demostró ser propensa a pérdidas de información e inflexible. Recientemente, se introdujo el sistema de 'facetas' (facets), que compensa las deficiencias e inflexibilidad de la API antigua.

Todos los eventos aún deben implementar la API antigua, pero esto se puede automatizar en gran medida si utilizas el sistema de facetas de forma eficaz. De manera similar, las facetas esenciales a menudo se pueden deducir de eventos que solo implementan la API antigua, aunque su información puede ser menos completa.

EL OBJETO EVENTO

Todos los objetos de evento deben heredar de Test2::Event. Si heredas de esta clase base e implementas correctamente la API antigua, las facetas se generarán para ti de forma gratuita. Por otro lado, puedes heredar de esta clase e importar también Test2::Util::Facets2Legacy, que en cambio dependerá de tus datos de facetas y deducirá la API antigua a partir de ellos.

Todos los eventos nuevos "DEBEN" implementar ambas APIs de una forma u otra. Una forma común de hacerlo es simplemente implementar ambas APIs directamente en tu evento.

Aquí tienes una buena plantilla para un nuevo evento:

package Test2::Event::Mine;
use strict;
use warnings;
use parent 'Test2::Event';
use Test2::Util::Facets2Legacy ':ALL';
sub facet_data {
    my $self = shift;
    # Añade las facetas 'about', 'amnesty', y 'trace'
    my $out = $self->common_facet_data;
    # Añade cualquier faceta adicional al hashref de $out
    ...
    return $out;
}
1;

LA API DE FACETAS

La nueva API es un único método: facet_data(). Este método debe devolver un hashref donde cada clave es específica de un tipo de faceta, y el valor es un hashref de faceta o una matriz de hashrefs de facetas. Algunas facetas "DEBEN" ser hashrefs únicos, otras "DEBEN" ser hashrefs dentro de un arrayref.

Los tipos de facetas *estándar* son los siguientes:

assert => {details => $nombre, pass => $booleano, no_debug => $booleano, number => $quizas_entero}
Documentado en Test2::EventFacet::Assert. Un evento solo puede tener uno.

La clave 'details' es el nombre de la aserción.

La clave 'pass' indica una aserción que pasa o falla.

La clave 'no_debug' indica a cualquier harness o formateador que no se deben añadir diagnósticos automáticamente a una aserción fallida (se usa cuando hay diagnósticos personalizados en su lugar).

La clave 'number' es para uso del harness, nunca la establezcas tú mismo.

about => {details => $cadena, no_display => $booleano, package => $paquete}
Documentado en Test2::EventFacet::About. Un evento solo puede tener uno.

'details' es una cadena legible por humanos que describe el evento general.

'no_display' significa que un formateador/harness debe ocultar el evento.

'package' es el paquete del evento que describe la faceta (por ejemplo, Test2::Event::Ok)

amnesty => [{details => $cadena, tag => $cadena_corta, inherited => $booleano}]
Documentado en Test2::EventFacet::Amnesty. Un evento puede tener varios.

Este evento es cómo se implementan cosas como 'todo' (todo esto). La amnistía evita que una aserción fallida cause un fallo global de las pruebas.

'details' es una descripción legible por humanos de por qué se concede amnistía al fallo (por ejemplo, la razón de 'todo').

'tag' es una cadena corta legible por humanos, o categoría, para la amnistía. Típicamente es 'TODO' o 'SKIP'.

'inherited' es verdadero si la amnistía se aplicó en un contexto padre (verdadero si esta prueba se ejecuta en una subprueba marcada como todo).

control => {details => $cadena, global => $booleano, terminate => $quizas_entero, halt => $booleano, has_callback => $booleano, encoding => $codificación}
Documentado en Test2::EventFacet::Control. Un evento puede tener uno.

Esta faceta se usa para aplicar un comportamiento adicional cuando se procesa el evento.

'details' es una explicación legible por humanos para el comportamiento.

'global' verdadero si este evento debe ser reenviado y procesado por todos los hubs en todas partes. (bail-out usa esto)

'terminate' esto debe ser undef o un entero. Cuando está definido, esto hará que la prueba salga con el código de salida específico.

'halt' se usa para indicar a cualquier harness que no se deben ejecutar más archivos de prueba (bail-out usa esto).

'has_callback' se establece en verdadero si el evento tiene una subrutina de devolución de llamada definida.

'encoding' se usa para indicar al formateador qué codificación debe usar.

errors => [{details => $cadena, tag => $cadena_corta, fail => $booleano}]
Documentado en Test2::EventFacet::Error. Un evento puede tener varios.

'details' es una explicación legible por humanos del error.

'tag' es una categoría corta legible por humanos para el error.

'fail' es verdadero si el error debe causar un fallo en la prueba. Si esto es falso, el error es simplemente informativo, pero no fatal.

info => [{details => $cadena, tag => $cadena_corta, debug => $booleano, important => $booleano}]
Documentado en Test2::EventFacet::Info. Un evento puede tener varios.

Así es como se implementan diag y note.

'details' mensaje legible por humanos.

'tag' categoría corta para el mensaje, como 'diag' o 'note'.

'debug' es verdadero si el mensaje es de naturaleza diagnóstica, esta es la principal diferencia entre una nota y un diag.

'important' es verdadero si el mensaje no es diagnóstico, pero es importante que se muestre de todos modos. Esto se usa principalmente para comunicarse con un harness.

parent => {details => $cadena, hid => $hid, children => [...], buffered => 1}
Documentado en Test2::EventFacet::Parent. Un evento solo puede tener uno.

Esto es utilizado por las subpruebas.

'details' nombre legible por humanos de la subprueba.

'hid' id del hub de la subprueba.

'children' un arrayref que contiene instancias de facet_data de todos los eventos hijos.

'buffered' verdadero si fue una subprueba en búfer.

plan => {details => $cadena, count => $entero, skip => $booleano, none => $booleano}
Documentado en Test2::EventFacet::Plan. Un evento solo puede tener uno.

'details' es una cadena legible por humanos que describe el plan (por ejemplo, por qué se omite una prueba).

'count' es el número de aserciones esperadas (0 para omitir).

'skip' es verdadero si el plan es omitir la prueba.

'none' se usa para el plan 'no_plan' de Test::More.

trace => {details => $cadena, frame => [$paquete, $archivo, $linea, $sub], pid => $entero, tid => $entero, cid => $cid, hid => $hid, nested => $entero, buffered => $booleano}
Documentado en Test2::EventFacet::Trace. Un evento solo puede tener uno.

Esta es la forma en que se rastrea la información de depuración. Esto se toma del objeto de contexto en el momento de la creación del evento.

'details' mensaje de depuración legible por humanos (de lo contrario se genera a partir del frame)

'frame' primeros 4 campos devueltos por caller: "[$paquete, $archivo, $linea, $nombre_subrutina]".

'pid' el ID del proceso en el que se creó el evento.

'tid' el hilo en el que se creó el evento.

'cid' el ID del contexto utilizado para crear el evento.

'hid' el ID del hub al que se envió el evento.

'nest' profundidad de anidamiento de subpruebas del evento.

'buffered' es verdadero si el evento se generó dentro de una subprueba con búfer.

NAME

Test2::Manual::Anatomy::Event - The anatomy of an event.

DESCRIPTION

This document will detail the anatomy of an event object in the Test2 testing framework. Events are the primary means by which test results are communicated. They are immutable objects that are passed around between different parts of the testing harness.

All events are blessed hashes. They contain keys that are used to describe the event. These keys are standardized and form the core of the Test2 API.

The primary purpose of events is to carry data. This data is referred to as 'facets'. Facets are the key-value pairs within an event hash. These facets can be arbitrary, or they can be standard facets that have well-defined meanings.

STANDARD FACETS

There are a number of standard facets that are recognized by most Test2 tools.

$string = $event->{assert}
This facet is used to describe an assertion. The string value should be the name of the test that is being run. For example: 
    assert => "The answer is 42"
$string = $event->{plan}
This facet is used to describe the plan for the test suite. The string value should be a human-readable description of the plan. For example: 
    plan => "skip all: Tests are unavailable"
$string = $event->{diag}
This facet is used to provide diagnostic information. This is typically used for failure messages, or other information that may be useful for debugging. For example: 
    diag => "Expected 'foo' but got 'bar'"

HISTORY

This document was originally part of Test2::API.

THE EVENT OBJECT

Events are blessed hashes. This means they are ordinary Perl hashes that have had a package name associated with them. This allows them to have methods.

The core of an event is its facets. Facets are key/value pairs within the hash. Most tools will only care about a few specific keys, but you can add arbitrary keys to an event. These are known as custom facets.

$event
A blessed hash that represents an event. All events will have a package name, and will inherit from Test2::Event.

THE FACET API

The facet API is the mechanism by which Test2 allows for arbitrary data to be attached to events. This data is known as a facet.

Facets are stored in the event hash as key/value pairs. The key determines the type of facet, and the value is the data for that facet.

There are two types of facets: simple facets and list facets.

Simple Facets
A simple facet is a key/value pair where the value is a single item. For example: 
    assert => "Test passed"
List Facets
A list facet is a key/value pair where the value is an array reference. For example: 
    custom_list => [ "item1", "item2" ]

All facet types have a 'details' key that may have a string. This string should always be human readable, and should be an explanation for the facet. For an assertion this is the test name. For a plan this is the reason for the plan (such as skip reason). For info it is the human readable diagnostics message.

CUSTOM FACETS

You can write custom facet types as well, simply add a new key to the hash and populated it. The general rule is that any code looking at the facets should ignore any it does not understand.

Optionally you can also create a package to document your custom facet. The package should be proper object, and may have additional methods to help work with your facet.

package Test2::EventFacet::MyFacet;
use parent 'Test2::EventFacet';
sub facet_key { 'myfacet' }
sub is_list { 0 }
1;

Your facet package should always be under the Test2::EventFacet:: namespace if you want any tools to automatically find it. The last part of the namespace should be the non-plural name of your facet with only the first word capitalized.

$string = $facet_class->facet_key
The key for your facet should be the same as the last section of the namespace, but all lowercase. You may append 's' to the key if your facet is a list type.
$bool = $facet_class->is_list
True if an event should put these facets in a list: 
{ myfacet => [{}, {}] }

False if an event may only have one of this type of facet at a time:

{ myfacet => {} }

EXAMPLES

The assert facet is not a list type, so its implementation would look like this:

package Test2::EventFacet::Assert;
sub facet_key { 'assert' }
sub is_list { 0 }

The amnesty facet is a list type, but amnesty does not need 's' appended to make it plural:

package Test2::EventFacet::Amnesty;
sub facet_key { 'amnesty' }
sub is_list { 1 }

The error facet is a list type, and appending 's' makes error plural as errors. This means the package name is '::Error', but the key is 'errors'.

package Test2::EventFacet::Error;
sub facet_key { 'errors' }
sub is_list { 1 }

Note2: In practice most tools completely ignore the facet packages, and work with the facet data directly in its raw structure. This is by design and recommended. The facet data is intended to be serialized frequently and passed around. When facets are concerned, data is important, classes and methods are not.

THE OLD API

The old API was simply a set of methods you were required to implement:

$bool = $e->causes_fail
Returns true if this event should result in a test failure. In general this should be false.
$bool = $e->increments_count
Should be true if this event should result in a test count increment.
$e->callback($hub)
If your event needs to have extra effects on the Test2::Hub you can override this method.

This is called BEFORE your event is passed to the formatter.

$num = $e->nested
If this event is nested inside of other events, this should be the depth of nesting. (This is mainly for subtests)
$bool = $e->global
Set this to true if your event is global, that is ALL threads and processes should see it no matter when or where it is generated. This is not a common thing to want, it is used by bail-out and skip_all to end testing.
$code = $e->terminate
This is called AFTER your event has been passed to the formatter. This should normally return undef, only change this if your event should cause the test to exit immediately.

If you want this event to cause the test to exit you should return the exit code here. Exit code of 0 means exit success, any other integer means exit with failure.

This is used by Test2::Event::Plan to exit 0 when the plan is 'skip_all'. This is also used by Test2::Event:Bail to force the test to exit with a failure.

This is called after the event has been sent to the formatter in order to ensure the event is seen and understood.

$msg = $e->summary
This is intended to be a human readable summary of the event. This should ideally only be one line long, but you can use multiple lines if necessary. This is intended for human consumption. You do not need to make it easy for machines to understand.

The default is to simply return the event package name.

($count, $directive, $reason) = $e->sets_plan()
Check if this event sets the testing plan. It will return an empty list if it does not. If it does set the plan it will return a list of 1 to 3 items in order: Expected Test Count, Test Directive, Reason for directive.
$bool = $e->diagnostics
True if the event contains diagnostics info. This is useful because a non-verbose harness may choose to hide events that are not in this category. Some formatters may choose to send these to STDERR instead of STDOUT to ensure they are seen.
$bool = $e->no_display
False by default. This will return true on events that should not be displayed by formatters.
