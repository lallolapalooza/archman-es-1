NOMBRE

Test2::API - Interfaz principal para escribir herramientas de prueba basadas en Test2.

***NOTA SOBRE INTERNOS***

¡Los internos de este paquete están sujetos a cambios en cualquier momento! Los métodos públicos proporcionados no cambiarán de forma incompatible con versiones anteriores (una vez que haya una versión estable), pero los detalles de implementación subyacentes podrían hacerlo. ¡No rompa la encapsulación aquí!

Actualmente, la implementación consiste en crear una única instancia del objeto Test2::API::Instance. Todos los métodos de clase delegan a la única instancia. No hay acceso público al singleton, y eso es intencional. Los métodos de clase proporcionados por este paquete proporcionan la única funcionalidad expuesta públicamente.

Esto se hace principalmente para evitar los problemas que tuvo Test::Builder al exponer su singleton. No queremos que nadie reemplace este singleton, lo re-enlace o manipule directamente sus internos. Si necesita hacer algo y no puede debido a las restricciones aquí impuestas, por favor, repórtelo como un problema. Si es posible, crearemos una forma para que implemente su funcionalidad sin exponer cosas que no deberían exponerse.

DESCRIPCIÓN

Este paquete exporta todas las funciones necesarias para escribir y/o verificar herramientas de prueba. Usando estos bloques de construcción, puede comenzar a escribir herramientas de prueba muy rápidamente. También se le proporcionan herramientas que le ayudan a probar las herramientas que escribe.

SINOPSIS

ESCRIBIENDO UNA HERRAMIENTA

El método context() es su interfaz principal en el framework Test2.

package My::Ok;
use Test2::API qw/context/;
our @EXPORT = qw/my_ok/;
use base 'Exporter';
# Igual que ok() de Test::More
sub my_ok($;$) {
    my ($bool, $name) = @_;
    my $ctx = context(); # Obtiene un contexto
    $ctx->ok($bool, $name);
    $ctx->release; # Libera el contexto
    return $bool;
}

Ver Test2::API::Context para una lista de métodos disponibles en el objeto contexto.

PROBANDO TUS HERRAMIENTAS

La herramienta "intercept { ... }" le permite interceptar temporalmente todos los eventos generados por el sistema de prueba:

use Test2::API qw/intercept/;
use My::Ok qw/my_ok/;
my $events = intercept {
    # Estos eventos no se muestran
    my_ok(1, "pass");
    my_ok(0, "fail");
};

A partir de la versión 1.302178, esto ahora devuelve una referencia a una matriz que también es una instancia de Test2::API::InterceptResult. Ver la documentación de Test2::API::InterceptResult para detalles sobre cómo utilizarla mejor.

EXPORTACIONES PRINCIPALES DE LA API

Todas las exportaciones son opcionales. Debe especificar las subs a importar.

use Test2::API qw/context intercept run_subtest/;

Esta es la lista de exportaciones que son las más comunes. Si solo está escribiendo una herramienta, entonces esto es probablemente todo lo que necesita. Si necesita algo y no puede encontrarlo aquí, entonces también puede mirar en "OTRAS EXPORTACIONES DE LA API".

Estas exportaciones carecen del prefijo 'test2_' debido a su importancia/comunidad. Las exportaciones en la sección "OTRAS EXPORTACIONES DE LA API" tienen el prefijo 'test2_' para asegurar que destaquen.

context(...)

Uso:

$ctx = context()
$ctx = context(%params)

La función context() siempre devolverá el contexto actual. Si ya hay un contexto activo, se devolverá. Si no hay un contexto activo, se generará uno. Cuando se genera un contexto, utilizará por defecto el archivo y el número de línea desde donde se llamó a la subactual.

Por favor, consulte "DETALLES CRÍTICOS" en Test2::API::Context para reglas importantes sobre lo que puede y no puede hacer con un contexto una vez que se obtiene.

Nota Esta función lanzará una excepción si ignora el objeto contexto que devuelve.

Nota En perls 5.14+, se utiliza una verificación de profundidad para asegurar que no haya fugas de contexto. Esto no se puede hacer de forma segura en perls más antiguas debido a https://rt.perl.org/Public/Bug/Display.html?id=127774 Puede activarla forzosamente estableciendo "$ENV{T2_CHECK_DEPTH} = 1" o "$Test2::API::DO_DEPTH_CHECK = 1" ANTES de cargar Test2::API.

PARÁMETROS OPCIONALES

Todos los parámetros para "context" son opcionales.

level => $int
Si debe obtener un contexto en una sub más profunda que su punto de entrada, puede usar esto para decirle cuántos marcos de pila EXTRA debe mirar hacia atrás. Si no se proporciona esta opción, se usa el valor predeterminado de 0. 
sub third_party_tool {
    my $sub = shift;
    ... # No obtiene un contexto
    $sub->();
    ...
}
third_party_tool(sub {
    my $ctx = context(level => 1);
    ...
    $ctx->release;
});
wrapped => $int
Use esto si necesita escribir su propia herramienta que envuelva una llamada a context() con la intención de que devuelva un objeto contexto. 
sub my_context {
    my %params = ( wrapped => 0, @_ );
    $params{wrapped}++;
    my $ctx = context(%params);
    ...
    return $ctx;
}
sub my_tool {
    my $ctx = my_context();
    ...
    $ctx->release;
}

Si no hace esto, las herramientas que llame y que también busquen un contexto notarán que el contexto que obtuvieron se creó a la misma profundidad de pila, lo que activará medidas de protección que le advertirán y destruirán el contexto existente.

stack => $stack
Normalmente context() mira la pila global del hub. Si está manteniendo su propia instancia de Test2::API::Stack, puede pasarla para que se use en lugar de la global.
hub => $hub
Use este parámetro si desea obtener el contexto para un hub específico en lugar del que esté en la parte superior de la pila.
on_init => sub { ... }
Esto le permite proporcionar una sub de devolución de llamada que se llamará SOLO si su llamada a context() generó un nuevo contexto. La devolución de llamada NO se llamará si context() está devolviendo un contexto existente. El único argumento que se pasa a la devolución de llamada será el propio objeto contexto. 
sub foo {
    my $ctx = context(on_init => sub { 'will run' });
    my $inner = sub {
        # Esta devolución de llamada no se ejecuta ya que estamos obteniendo
        # el contexto existente de nuestro sub padre.
        my $ctx = context(on_init => sub { 'will NOT run' });
        $ctx->release;
    }
    $inner->();
    $ctx->release;
}
on_release => sub { ... }
Esto le permite proporcionar una sub de devolución de llamada que se llamará cuando se libere la instancia del contexto. Esta devolución de llamada se agregará al contexto devuelto, incluso si se devuelve un contexto existente. Si varias llamadas a context agregan devoluciones de llamada, todas se llamarán en orden inverso cuando el contexto finalmente se libere.

.Dd August 27, 2021 .Os .Sh NAME Test2::API \- Core API for Test2 .Sh DESCRIPTION The Test2 package is a framework for writing tests. The primary goal is to make it easier to write tests in perl, and to make it easier to write modules that help you write tests. .Pp This package exports a set of commonly used tools. These are the tools that most people will reach for. There are other tools that are exported, but they are not as commonly needed. Those are documented in Test2::API::Extra. .Sh MAIN API EXPORTS The following tools are exported by default. They are exported into the caller's namespace, and are available for direct use. .Sh TOOLS .TP .B context() .rte Usage: .rte .rte my $ctx = context(); .rte .rte Returns the current context. If no context exists, one will be created. .Pp This is the fundamental function for Test2. Most tools will require a context to be present to function. .TP .B release .rte Usage: .rte .rte release $ctx; .rte release $ctx, ...; .rte .rte This is intended as a shortcut that lets you release your context .B and return a value in one statement. This function will get your context, and an optional return value. It will release your context, then return your value. Scalar context is always assumed. .Pp .Vt sub tool { .Vt my $ctx = context(); .Vt ... .Vt return release $ctx, 1; .Vt } .Pp This tool is most useful when you want to return the value you get from calling a function that needs to see the current context: .Pp .Vt my $ctx = context(); .Vt my $out = some_tool(...); .Vt $ctx->release; .Vt return $out; .Pp We can combine the last 3 lines of the above like so: .Pp .Vt my $ctx = context(); .Vt release $ctx, some_tool(...); .TP .B context_do(&;@) .rte Usage: .rte sub my_tool { .rte context_do { .rte my $ctx = shift; .rte my (@args) = @_; .rte $ctx->ok(1, "pass"); .rte ... .rte # No need to call $ctx->release, done for you on scope exit. .rte } @_; .rte } .rte .rte Using this inside your test tool takes care of a lot of boilerplate for you. It will ensure a context is acquired. It will capture and rethrow any exception. It will ensure the context is released when you are done. It preserves the subroutine call context (list, scalar, void). .Pp This is the safest way to write a test tool. The only two downsides to this are a slight performance decrease, and some extra indentation in your source. If the indentation is a problem for you then you can take a peek at the next section. .TP .B no_context(&;$) .rte Usage: .rte no_context { ... }; .rte no_context { ... } $hid; .rte .rte sub my_tool(&) { .rte my $code = shift; .rte my $ctx = context(); .rte ... .rte no_context { .rte # Things in here will not see our current context, they get a new .rte # one. .rte $code->(); .rte }; .rte ... .rte $ctx->release; .rte }; .rte .rte This tool will hide a context for the provided block of code. This means any tools run inside the block will get a completely new context if they acquire one. The new context will be inherited by tools nested below the one that acquired it. .Pp This will normally hide the current context for the top hub. If you need to hide the context for a different hub you can pass in the optional \(lq$hid\(rq parameter. .TP .B intercept(&) .rte Usage: .rte my $events = intercept { .rte ok(1, "pass"); .rte ok(0, "fail"); .rte ... .rte }; .rte .rte This function takes a codeblock as its only argument, and it has a prototype. It will execute the codeblock, intercepting any generated events in the process. It will return an array reference with all the generated event objects. All events should be subclasses of Test2::Event. .Pp As of version 1.302178 the events array that is returned is blssed as an Test2::API::InterceptResult instance. Test2::API::InterceptResult Provides a helpful interface for filtering and/or inspecting the events list overall, or individual events within the list. .Pp This is intended to help you test your test code. This is not intended for people simply writing tests. .TP .B run_subtest(...) .rte Usage: .rte run_subtest($NAME, \&CODE, $BUFFERED, @ARGS) .rte # or .rte run_subtest($NAME, \&CODE, \%PARAMS, @ARGS) .rte .rte This will run the provided codeblock with the args in \(lq@args\(rq. This codeblock will be run as a subtest. A subtest is an isolated test state that is condensed into a single Test2::Event::Subtest event, which contains all events generated inside the subtest. .Pp .I ARGUMENTS: .TP $NAME The name of the subtest. .TP \&CODE The code to run inside the subtest. .TP $BUFFERED or \%PARAMS If this is a simple scalar then it will be treated as a boolean for the \(lqbuffered\(rq setting. If this is a hash reference then it will be used as a parameters hash. The param hash will be used for hub construction (with the specified keys removed). .RS 4 .TP Keys that are removed and used by run_subtest: .TP 'buffered' =E> $bool Toggle buffered status. .TP 'inherit_trace' =E> $bool Normally the subtest hub is pushed and the sub is allowed to generate its own root context for the hub. When this setting is turned on a root context will be created for the hub that shares the same trace as the current context. .Pp Set this to true if your tool is producing subtests without user-specified subs. .TP 'no_fork' =E> $bool Defaults to off. Normally forking inside a subtest will actually fork the subtest, resulting in 2 final subtest events. This parameter will turn off that behavior, only the original process/thread will return a final subtest event. .RE .TP @ARGS Any extra arguments you want passed into the subtest code. .Pp .I BUFFERED VS UNBUFFERED (OR STREAMED) .Pp Normally all events inside and outside a subtest are sent to the formatter immediately by the hub. Sometimes it is desirable to hold off sending events within a subtest until the subtest is complete. This usually depends on the formatter being used. .TP Things not affected by this flag .Pp In both cases events are generated and stored in an array. This array is eventually used to populate the \(lqsubevents\(rq attribute on the Test2::Event::Subtest event that is generated at the end of the subtest. This flag has no effect on this part; it always happens. .Pp At the end of the subtest, the final Test2::Event::Subtest event is sent to the formatter. .TP Things that are affected by this flag .Pp The \(lqbuffered\(rq attribute of the Test2::Event::Subtest event will be set to the value of this flag. This means any formatter, listener, etc which looks at the event will know if it was buffered. .TP Things that are formatter dependent .Pp Events within a buffered subtest may or may not be sent to the formatter as they happen. If a formatter fails to specify then the default is to **NOT SEND** the events as they are generated, instead the formatter can pull them from the \(lqsubevents\(rq attribute. .Pp A formatter can specify by implementing the \(lqhide_buffered()\(rq method. If this method returns true then events generated inside a buffered subtest will not be sent independently of the final subtest event. .Pp An example of how this is used is the Test2::Formatter::TAP formatter. For unbuffered subtests the events are rendered as they are generated. At the end of the subtest, the final subtest event is rendered, but the \(lqsubevents\(rq attribute is ignored. For buffered subtests the opposite occurs, the events are NOT rendered as they are generated, instead the \(lqsubevents\(rq attribute is used to render them all at once. This is useful when running subtests tests in parallel, since without it the output from subtests would be interleaved together. .Sh OTHER API EXPORTS .Pp Exports in this section are not commonly needed. These all have the 'test2_' prefix to help ensure they stand out. You should look at the \(lqMAIN API EXPORTS\(rq section before looking here. This section is one where \(lqGreat power comes with great responsibility\(rq. It is possible to break things badly if you are not careful with these. .Pp All exports are optional. It will return false if they have not. Init happens as late as possible. It happens as soon as a tool requests the IPC instance, the formatter, or the stack. .TP $bool = **test2_load_done()** This will simply return the boolean value of the loaded flag. If Test2 has finished loading this will be true, otherwise false. Loading is considered complete the first time a tool requests a context. .TP **test2_set_is_end()** .br test2_set_is_end($bool) This is used to toggle Test2's belief that the END phase has already started. With no arguments this will set it to true. With arguments it will set it to the first argument's value. .Pp This is used to prevent the use of \(lqcaller()\(rq in END blocks which can cause segfaults. TEST2::API

The Test2 API

VERSION

  $Id: API.pm 397 2022-09-22 14:07:11Z nubby $

SYNOPSIS

  use Test2::API qw(run_tests);

  run_tests(sub {
      ok 1;
      ok 0;
  });

DESCRIPTION

This module provides the main API for Test2. This is what you will typically use to write tests.

This module is responsible for providing the global context and the main entry points for running tests. It also provides access to the internals of the Test2 system, such as formatters, IPC, and other utilities.

***INTERNALS NOTE***

This module exports most of its functionality directly. This is done for convenience and historical reasons. In the future, this may change to a more object oriented approach.

MAIN API EXPORTS

run_tests(sub{})
This is the main entry point for running tests. It takes a coderef (sub {}) which contains the test code. This function will handle setting up the test environment, running the tests, and printing the results.
context()
Get the current test context. This is the object that holds all the state for the current test run. You can use this to manually create events, or to access other parts of the Test2 system.

OTHER API EXPORTS

These are other useful functions that you may want to use.

test2_can_fork()
Returns true if the current system supports forking. This is useful for determining if you can use parallel testing.
test2_is_child()
Returns true if the current process is a child process. This is useful for tests that use forking.
test2_ipc_set_timeout($timeout)
Get/Set the timeout value for the IPC system. This timeout is how long the IPC system will wait for child processes and threads to finish before aborting.

The default value is 30 seconds.

MANAGING FORMATTERS

These let you access, or specify, the formatters that can/should be used.

$formatter = test2_formatter
This will return the global formatter class. This is not an instance. By default the formatter is set to Test2::Formatter::TAP.

You can override this default using the "T2_FORMATTER" environment variable.

Normally 'Test2::Formatter::' is prefixed to the value in the environment variable:

$ T2_FORMATTER='TAP' perl test.t     # Use the Test2::Formatter::TAP formatter
$ T2_FORMATTER='Foo' perl test.t     # Use the Test2::Formatter::Foo formatter

If you want to specify a full module name you use the '+' prefix:

$ T2_FORMATTER='+Foo::Bar' perl test.t     # Use the Foo::Bar formatter
test2_formatter_set($class_or_instance)
Set the global formatter class. This can only be set once. Note: This will override anything specified in the 'T2_FORMATTER' environment variable.
@formatters = test2_formatters()
Get a list of all loaded formatters.
test2_formatter_add($class_or_instance)
Add a formatter to the list. Last formatter added is used at initialization. If this is called after initialization a warning will be issued.

TIME STAMPS

You can enable or disable timestamps in trace facets. They are disabled by default for compatibility and performance reasons.

test2_enable_trace_stamps()
Enable stamps in traces.
test2_disable_trace_stamps()
Disable stamps in traces.
$bool = test2_trace_stamps_enabled()
Check status of trace stamps.

OTHER EXAMPLES

See the "/Examples/" directory included in this distribution.

MAGIC

This package has an END block. This END block is responsible for setting the exit code based on the test results. This end block also calls the callbacks that can be added to this package.
