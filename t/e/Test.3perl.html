NOMBRE

Test - proporciona un marco simple para escribir scripts de prueba

SINOPSIS

use strict;
use Test;
# usa un bloque BEGIN para imprimir nuestro plan antes de que MyModule sea cargado
BEGIN { plan tests => 14, todo => [3,4] }
# carga tu módulo...
use MyModule;
# Notas útiles. Todas las líneas de nota deben comenzar con un "#".
print "# Estoy probando MyModule versión $MyModule::VERSION\n";
ok(0); # fallo
ok(1); # éxito
ok(0); # ok, fallo esperado (ver lista todo, arriba)
ok(1); # ¡sorpresa de éxito!
ok(0,1);             # fallo: '0' ne '1'
ok('broke','fixed'); # fallo: 'broke' ne 'fixed'
ok('fixed','fixed'); # éxito: 'fixed' eq 'fixed'
ok('fixed',qr/x/);   # éxito: 'fixed' =~ qr/x/
ok(sub { 1+1 }, 2);  # éxito: '2' eq '2'
ok(sub { 1+1 }, 3);  # fallo: '2' ne '3'
my @list = (0,0);
ok @list, 3, "\@list=".join(',',@list);      # notas adicionales
ok 'segmentation fault', '/(?i)success/';    # coincidencia de expresión regular
skip(
  $^O =~ m/MSWin/ ? "Saltar si es MSWin" : 0,  # si saltar
  $foo, $bar  # argumentos iguales que para ok(...)
);
skip(
  $^O =~ m/MSWin/ ? 0 : "Saltar si no es MSWin",  # si saltar
  $foo, $bar  # argumentos iguales que para ok(...)
);

DESCRIPCIÓN

Este módulo simplifica la tarea de escribir archivos de prueba para módulos Perl, de modo que su salida esté en el formato que Test::Harness espera ver.

GUÍA RÁPIDA

Para escribir una prueba para tu nuevo módulo (y probablemente aún no terminado), crea un nuevo archivo llamado t/test.t (en un nuevo directorio t). Si tienes múltiples archivos de prueba, para probar los conjuntos de características "foo", "bar" y "baz", siéntete libre de llamar a tus archivos t/foo.t, t/bar.t y t/baz.t.

Funciones

Este módulo define tres funciones públicas: plan(...), ok(...) y skip(...). Por defecto, las tres son exportadas por la declaración "use Test;".

plan(...)
BEGIN { plan %la_plan; }

Esta debería ser la primera cosa que llames en tu script de prueba. Declara tu plan de pruebas, cuántas habrá, si se permite que alguna falle, etc.

El uso típico es simplemente:

use Test;
BEGIN { plan tests => 23 }

Estas son las cosas que puedes poner en los parámetros para plan:

"tests => número"
El número de pruebas en tu script. Esto incluye todas las llamadas a ok() y skip().
"todo => [1,5,14]"
Una referencia a una lista de pruebas que se permite que fallen. Véase "PRUEBAS TODO".
"onfail => sub { ... }"
"onfail => \&some_sub"
Una referencia a una subrutina que se ejecutará al final del script de prueba, si alguna de las pruebas falla. Véase "ONFAIL".

Debes llamar a plan(...) una y solo una vez. Debes llamarla en un bloque "BEGIN {...}", así:

BEGIN { plan tests => 23 }
ok(...)
ok(1 + 1 == 2);
ok($tenemos, $esperamos);
ok($tenemos, $esperamos, $diagnóstico);

Esta función es la razón de ser de "Test". Es la función básica que se encarga de imprimir ""ok"" o ""not ok"", junto con el número de prueba actual. (Eso es lo que "Test::Harness" quiere ver).

En su uso más básico, ok(...) simplemente toma una única expresión escalar. Si su valor es verdadero, la prueba pasa; si es falso, la prueba falla. Ejemplos:

# Ejemplos de ok(escalar)
ok( 1 + 1 == 2 );           # ok si 1 + 1 == 2
ok( $foo =~ /bar/ );        # ok si $foo contiene 'bar'
ok( baz($x + $y) eq 'Armondo' );    # ok si baz($x + $y) devuelve
                                    # 'Armondo'
ok( @a == @b );             # ok si @a y @b tienen la misma
                            # longitud

La expresión se evalúa en contexto escalar. Así que lo siguiente funcionará:

ok( @stuff );                       # ok si @stuff tiene algún
                                    # elemento
ok( !grep !defined $_, @stuff );    # ok si todo en @stuff
                                    # está definido.

Un caso especial es si la expresión es una referencia a una subrutina (ya sea en sintaxis "sub {...}" o en sintaxis "\&foo"). En ese caso, se ejecuta y su valor (verdadero o falso) determina si la prueba pasa o falla. Por ejemplo,

ok( sub {   # Ver si sleep funciona al menos pasablemente
  my $start_time = time;
  sleep 5;
  time() - $start_time  >= 4
});

En su forma de dos argumentos, "ok(arg1, arg2)" compara los dos valores escalares para ver si coinciden. Coinciden si ambos no están definidos, o si arg2 es una expresión regular que coincide con arg1, o si comparan igual con "eq".

# Ejemplo de ok(escalar, escalar)
ok( "this", "that" );               # no ok, 'this' ne 'that'
ok( "", undef );                    # no ok, "" está definido

El segundo argumento se considera una expresión regular si es un objeto de expresión regular o una cadena que parece una expresión regular. Los objetos de expresión regular se construyen con el operador qr// en versiones recientes de perl. Una cadena se considera que parece una expresión regular si sus caracteres primero y último son "/", o si el primer carácter es "m" y sus caracteres segundo y último son ambos el mismo carácter no alfanumérico ni espacio en blanco. Estas expresiones regulares

Ejemplos de expresiones regulares:

ok( 'JaffO', '/Jaff/' );    # ok, 'JaffO' =~ /Jaff/
ok( 'JaffO', 'm|Jaff|' );   # ok, 'JaffO' =~ m|Jaff|
ok( 'JaffO', qr/Jaff/ );    # ok, 'JaffO' =~ qr/Jaff/;
ok( 'JaffO', '/(?i)jaff/ ); # ok, 'JaffO' =~ /jaff/i;

Si uno (¡o ambos!) son referencias a subrutinas, se ejecutan y se usan como valor para la comparación. Por ejemplo:

ok sub {
    open(OUT, '>', 'x.dat') || die $!;
    print OUT "\x{e000}";
    close OUT;
    my $bytecount = -s 'x.dat';
    unlink 'x.dat' or warn "Can't unlink : $!";
    return $bytecount;
  },
  4
;

La prueba anterior pasa dos valores a "ok(arg1, arg2)": el primero es un coderef y el segundo es el número 4. Antes de que "ok" los compare, llama al coderef y usa su valor de retorno como el valor real de este parámetro. Asumiendo que $bytecount devuelve 4, "ok" termina probando "4 eq 4". Como eso es verdadero, esta prueba pasa.

Finalmente, puedes añadir un tercer argumento opcional, en "ok(arg1,arg2, nota)", donde nota es un valor de cadena que se imprimirá si la prueba falla. Esta debería ser información útil sobre la prueba, relacionada con por qué falló, y/o una descripción de la prueba. Por ejemplo:

ok( grep($_ eq 'something unique', @stuff), 1,
    "¡Algo que debería ser único no lo es!\n".
    '@stuff = '.join ', ', @stuff
  );

Desafortunadamente, una nota no se puede usar con el estilo de un argumento de ok(). Es decir, si intentas "ok(arg1, nota)", entonces "Test" interpretará esto como "ok(arg1, arg2)", y probablemente terminará probando "

DIAGNOSTICS

The ok() and diag() routines are used to emit diagnostics. diag() is used to emit diagnostics that are always printed. ok() is used to emit diagnostics that are printed only if the test fails. By default, only one line of diagnostics is printed per failure. But if you want more, you can set the "diag_indent" variable:

    use Test;
    BEGIN { plan tests => 3, diag_indent => 1 }
    diag( "This is a diagnostic message" );
    ok( 0, "this test fails" );
    ok( 0, "this test also fails\n  with an indented message" );

This will produce:

    ok 1 - this test fails
    not ok 2 - this test also fails
    #   This is a diagnostic message
    #   with an indented message

Note that the ok() call is for the second failure, and it has an expected result and a diagnostic message. The expected result is the string "this test also fails", and the diagnostic message is "with an indented message". Both are printed, indented, after the failure.

You can force ok() to print diagnostics even if the test succeeds by passing it a true value as the first argument:

    ok( 1, 1, "this test succeeds but we want diagnostics anyway" );

This will print:

    ok 1 - this test succeeds but we want diagnostics anyway
    #   Expected: 1

Note that the diagnostic message here is the expected value. If you want to provide your own diagnostic message, you can do so:

    ok( 1, 1, 'this test succeeds', "but we want diagnostics anyway" );

Which will produce:

    ok 1 - this test succeeds
    #   Expected: 1
    #   Note: but we want diagnostics anyway

The ok() function also handles comparisons of strings and numbers, and automatically stringifies them for you:

    my $string = "1";
    my $number = 1;
    ok( $string, $number );      # ok "1" eq 1
    ok( $number, $string );      # ok 1 eq "1"

If you want a plain, old-fashioned comparison, you need to use the one-argument form:

    ok( $string eq $number );   # not ok "1" ne 1
    ok( $number == $string );  # ok 1 == "1"

The special case is when you want to compare two numbers, and one of them might be a string. In that case, you'll want to use the two-argument form:

    my $string = "1";
    my $number = 1;
    ok( $string, $number );      # ok "1" eq 1
    ok( $number, $string );      # ok 1 eq "1"

This is because ok() defaults to using eq for comparison. If you want to use ==, you need to specify it:

    ok( $string, $number, '==' ); # ok "1" == 1

Or, you can just use the one-argument form:

    ok( $string == $number );    # ok "1" == 1

This also applies to regexes. If you want to compare a string to a regex, you need to use the two-argument form and specify the comparison operator:

    ok( $string, qr/1/, '=~' );   # ok "1" =~ qr/1/

Or, again, the one-argument form:

    ok( $string =~ qr/1/ );      # ok "1" =~ qr/1/

This is all quite confusing, so here's a table summarizing the special cases:

Let's say we have:

    $arg1 = 'foo';
    $arg2 = 'bar';
    $num1 = 1;
    $num2 = '1';
    $regex = qr/foo/;

Then:

ok( $arg1, $arg2 )
This compares $arg1 and $arg2 using eq. So, ok('foo', 'bar') is not ok.
ok( $arg1, $regex )
This compares $arg1 using =~. So, ok('foo', qr/foo/) is ok.
ok( $num1, $num2 )
This compares $num1 and $num2 using eq. So, ok(1, '1') is ok.
ok( $num1, $arg1 )
This compares $num1 using ==. So, ok(1, 'foo') is not ok.
ok( $arg1, $num1 )
This compares $arg1 using eq. So, ok('foo', 1) is not ok.
ok( $num1, $num2, '==' )
Explicitly uses == for comparison. ok(1, '1', '==') is ok.
ok( $num1, $num2, '=~' )
Explicitly uses =~ for comparison. ok(1, qr/1/, '=~') is ok.
ok( $num1, $num2, '!=' )
Explicitly uses != for comparison. ok(1, '2', '!=') is ok.
ok( $num1, $num2, '!~' )
Explicitly uses !~ for comparison. ok(1, qr/2/, '!~') is ok.

All of the above special cases can occasionally cause some problems. See "BUGS and CAVEATS".

skip(skip_if_true, args...)

This is used for tests that under some conditions can be skipped. It's basically equivalent to:

    if( $skip_if_true ) {
      ok(1);
    } else {
      ok( args... );
    }

...except that the ok(1) emits not just ""ok testnum"" but actually ""ok testnum # skip_if_true_value"".

The arguments after the skip_if_true are what is fed to ok(...) if this test isn't skipped.

Example usage:

    my $if_MSWin =
      $^O =~ m/MSWin/ ? 'Skip if under MSWin' : '';
    # A test to be skipped if under MSWin (i.e., run except under
    # MSWin)
    skip($if_MSWin, thing($foo), thing($bar) );

Or, going the other way:

    my $unless_MSWin =
      $^O =~ m/MSWin/ ? '' : 'Skip unless under MSWin';
    # A test to be skipped unless under MSWin (i.e., run only under
    # MSWin)
    skip($unless_MSWin, thing($foo), thing($bar) );

The tricky thing to remember is that the first parameter is true if you want to skip the test, not run it; and it also doubles as a note about why it's being skipped. So in the first codeblock above, read the code as "skip if MSWin -- (otherwise) test whether thing($foo) is thing($bar)" or for the second case, "skip unless MSWin...".

Also, when your skip_if_reason string is true, it really should (for backwards compatibility with older Test.pm versions) start with the string "Skip", as shown in the above examples.

Note that in the above cases, thing($foo) and thing($bar) are evaluated -- but as long as the "skip_if_true" is true, then we skip(...) just tosses out their value (i.e., not bothering to treat them like values to ok(...). But if you need to not eval the arguments when skipping the test, use this format:

    skip( $unless_MSWin,
      sub {
        # This code returns true if the test passes.
        # (But it doesn't even get called if the test is skipped.)
        thing($foo) eq thing($bar)
      }
    );

or even this, which is basically equivalent:

    skip( $unless_MSWin,
      sub { thing($foo) }, sub { thing($bar) }
    );

That is, both are like this:

    if( $unless_MSWin ) {
      ok(1);  # but it actually appends "# $unless_MSWin"
              #  so that Test::Harness can tell it's a skip
    } else {
      # Not skipping, so actually call and evaluate...
      ok( sub { thing($foo) }, sub { thing($bar) } );
    }

TEST TYPES

  • NORMAL TESTS

    These tests are expected to succeed. Usually, most or all of your tests are in this category. If a normal test doesn't succeed, then that means that something is wrong.

  • SKIPPED TESTS

    The skip(...) function is for tests that might or might not be possible to run, depending on the availability of platform-specific features. The first argument should evaluate to true (think "yes, please skip") if the required feature is not available. After the first argument, skip(...) works exactly the same way as ok(...) does.

  • TODO TESTS

    TODO tests are designed for maintaining an executable TODO list. These tests are expected to fail. If a TODO test does succeed, then the feature in question shouldn't be on the TODO list, now should it?

    Packages should NOT be released with succeeding TODO tests. As soon as a TODO test starts working, it should be promoted to a normal test, and the newly working feature should be documented in the release notes or in the change log.

ONFAIL

BEGIN { plan test => 4, onfail => sub { warn "CALL 911!" } }

Although test failures should be enough, extra diagnostics can be triggered at the end of a test run. "onfail" is passed an array ref of hash refs that describe each test failure. Each hash will contain at least the following fields: "package", "repetition", and "result". (You shouldn't rely on any other fields being present.) If the test had an expected value or a diagnostic (or "note") string, these will also be included.

The optional "onfail" hook might be used simply to print out the version of your package and/or how to report problems. It might also be used to generate extremely sophisticated diagnostics for a particularly bizarre test failure. However it's not a panacea. Core dumps or other unrecoverable errors prevent the "onfail" hook from running. (It is run inside an "END" block.) Besides, "onfail" is probably over-kill in most cases. (Your test code should be simpler than the code it is testing, yes?)

BUGS and CAVEATS

  • ok(...)'s special handing of strings which look like they might be regexes can also cause unexpected behavior. An innocent: 
        ok( $fileglob, '/path/to/some/*stuff/' );

    will fail, since Test.pm considers the second argument to be a regex! The best bet is to use the one-argument form:

        ok( $fileglob eq '/path/to/some/*stuff/' );
  • ok(...)'s use of string "eq" can sometimes cause odd problems when comparing numbers, especially if you're casting a string to a number: 
        $foo = "1.0";
    ok( $foo, 1 );      # not ok, "1.0" ne 1

    Your best bet is to use the single argument form:

        ok( $foo == 1 );    # ok "1.0" == 1
  • As you may have inferred from the above documentation and examples, "ok"'s prototype is "($;$$)" (and, incidentally, "skip"'s is "($;$$$)"). This means, for example, that you can do "ok @foo, @bar" to compare the size of the two arrays. But don't be fooled into thinking that "ok @foo, @bar" means a comparison of the contents of two arrays -- you're comparing just the number of elements of each. It's so easy to make that mistake in reading "ok @foo, @bar" that you might want to be very explicit about it, and instead write ok scalar(@foo), scalar(@bar).
  • This almost definitely doesn't do what you expect: 
        ok $thingy->can('some_method');

    Why? Because "can" returns a coderef to mean "yes it can (and the method is this...)", and then "ok" sees a coderef and thinks you're passing a function that you want it to call and consider the truth of the result of! I.e., just like:

        ok $thingy->can('some_method')->();

    What you probably want instead is this:

        ok $thingy->can('some_method') && 1;

    If the "can" returns false, then that is passed to "ok". If it returns true, then the larger expression "$thingy->can('some_method') && 1" returns 1, which "ok" sees as a simple signal of success, as you would expect.

  • The syntax for "skip" is about the only way it can be, but it's still quite confusing. Just start with the above examples and you'll be okay.

    Moreover, users may expect this:

        skip $unless_mswin, foo($bar), baz($quux);

    to not evaluate foo($bar) and baz($quux) when the test is being skipped. But in reality, they are evaluated, but "skip" just won't bother comparing them if $unless_mswin is true.

    You could do this:

        skip $unless_mswin, sub{foo($bar)}, sub{baz($quux)};

    But that's not terribly pretty. You may find it simpler or clearer in the long run to just do things like this:

        if( $^O =~ m/MSWin/ ) {
      print "# Yay, we're under $^O\n";
      ok foo($bar), baz($quux);
      ok thing($whatever), baz($stuff);
      ok blorp($quux, $whatever);
      ok foo($barzbarz), thang($quux);
    } else {
      print "# Feh, we're under $^O.  Watch me skip some tests...\n";
      for(1 .. 4) { skip "Skip unless under MSWin" }
    }

    But be quite sure that "ok" is called exactly as many times in the first block as "skip" is called in the second block.

ENVIRONMENT

If "PERL_TEST_DIFF" environment variable is set, it will be used as a command for comparing unexpected multiline results. If you have GNU diff installed, you might want to set "PERL_TEST_DIFF" to "diff -u". If you don't have a suitable program, you might install the "Text::Diff" module and then set "PERL_TEST_DIFF" to be "perl -MText::Diff -e 'print diff(@ARGV)'". If

"PERL_TEST_DIFF" no está configurado pero el módulo "Algorithm::Diff" está disponible, entonces se utilizará para mostrar las diferencias en resultados multilínea.
