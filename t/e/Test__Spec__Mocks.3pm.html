NOMBRE

Test::Spec::Mocks - Plugin de Simulación de Objetos para Test::Spec

SINOPSIS

use Test::Spec;
use base qw(Test::Spec);
use My::RSS::Tool;    # esto es lo que estamos probando
use LWP::UserAgent;
describe "RSS tool" => sub {
  it "should fetch and parse an RSS feed" => sub {
    my $xml = load_rss_fixture();
    LWP::Simple->expects('get')->returns($xml);
    # llama a LWP::Simple::get, pero devuelve nuestro $xml en su lugar
    my @stories = My::RSS::Tool->run;
    is_deeply(\@stories, load_stories_fixture());
  };
};

DESCRIPCIÓN

Test::Spec::Mocks es un plugin para Test::Spec que proporciona mocking y stubbing de objetos, métodos individuales y subrutinas simples en instancias de objetos y clases. Este módulo está inspirado y toma prestado en gran medida de Mocha, una biblioteca para el lenguaje de programación Ruby. Mocha en sí está inspirado en JMock.

Los objetos simulados (mock objects) proporcionan una forma de simular el comportamiento de objetos reales, al tiempo que proporcionan resultados consistentes y repetibles. Esto es muy útil cuando necesita probar una función cuyos resultados dependen de un factor externo que normalmente no se puede controlar (como la hora del día). Los mocks también le permiten probar su código de forma aislada, un principio de las pruebas unitarias.

Hay muchas otras razones por las que los objetos simulados podrían ser útiles. Consulte el artículo sobre objetos simulados http://en.wikipedia.org/wiki/Mock_object en Wikipedia para ver muchos más ejemplos y una cobertura más profunda de la filosofía detrás de la simulación de objetos.

Ecosistema

Test::Spec::Mocks actualmente solo se puede usar dentro de pruebas creadas con el framework BDD de Test::Spec.

Terminología

Familiarícese con estos términos:

  • Objeto stub (stub object)

    Un objeto stub es un objeto creado específicamente para devolver respuestas predefinidas para un conjunto específico de métodos. Estos se crean con la función stub.

  • Objeto mock (mock object)

    Los objetos mock son similares a los objetos stub, pero están programados con respuestas preparadas y expectativas de cómo serán llamados. Si las expectativas no se cumplen, generan una excepción para indicar que la prueba falló. Los objetos mock se crean con la función mock.

  • Método stub (stubbed method)

    Los métodos stub reemplazan temporalmente los métodos existentes en una clase o instancia de objeto. Esto es útil cuando solo desea anular un subconjunto del comportamiento de un objeto o clase. Por ejemplo, es posible que desee anular el método "do" de un manejador DBI para que no realice cambios en su base de datos, pero aún necesite que el manejador responda normalmente al método "quote". Anulará métodos utilizando el método stubs.

  • Método mock (mocked method)

    Si ha estado leyendo hasta este punto, esto no será una sorpresa. Los métodos mock son como los métodos stub, pero vienen con expectativas que generarán una excepción si no se cumplen. Por ejemplo, puede simular un método "save" en un objeto para asegurarse de que es llamado por el código que está probando, al tiempo que evita que los datos se guarden realmente en el disco en su prueba. Utilice el método expects para crear métodos mock.

  • "stub", "mock"

    Dependiendo del contexto, estos pueden referirse a objetos y métodos stub, o a objetos y métodos mock, respectivamente.

Usando objetos stub (stubs anónimos)

A veces, el código que está probando requiere que le pase un objeto que cumpla con una interfaz específica. Por ejemplo, está probando una biblioteca de solicitudes de consola, pero no quiere requerir que una persona real esté presente, esperando escribir respuestas en la consola. La biblioteca requiere un objeto que devuelva una cadena cuando se llame al método "read_line".

Podría crear una clase específicamente para devolver entradas de consola de prueba. ¿Pero por qué hacerlo? Puede crear un objeto stub en una sola línea:

describe "An Asker" => sub {
  my $asker = Asker->new;
  it "returns true when a yes_or_no question is answered 'yes'" => sub {
    my $console_stub = stub(read_line => "yes");
    # $console_stub->read_line devuelve "yes"
    ok( $asker->yes_or_no($console_stub, "Am I awesome?") );
  };
  it "returns false when a yes_or_no question is answered 'no'" => sub {
    my $console_stub = stub(read_line => "no");
    ok( ! $asker->yes_or_no($console_stub, "Am I second best?") );
  };
};

Los stubs también pueden tomar referencias a subrutinas. Esto es útil cuando el comportamiento que necesita imitar es un poco más complejo.

it "keeps asking until it gets an answer" => sub {
  my @answers = (undef, "yes");
  my $console_stub = stub(read_line => sub { shift @answers });
  # cuando se llama a console_stub por primera vez, devuelve undef
  # la segunda vez devuelve "yes"
  ok( $asker->yes_or_no($console_stub, "Do I smell nice?") );
};

Usando objetos mock

Si desea llevar sus pruebas un paso más allá, puede usar objetos mock en lugar de objetos stub. Los mocks aseguran que los métodos que espera que se llamen realmente se llamen. Si no es así, el mock generará una excepción que hará que su prueba falle.

En este ejemplo, estamos probando que "read_line" se llama una vez y solo una vez (el predeterminado para los mocks).

it "returns true when a yes_or_no question is answered 'yes'" => sub {
  my $console_mock = mock();
  $console_mock->expects('read_line')
               ->returns("yes");
  # $console_mock->read_line devuelve "yes"
  ok( $asker->yes_or_no($console_mock, "Am I awesome?") );
};

Si el método "yes_or_no" de Asker no llama a "read_line" en nuestro mock exactamente una vez, la prueba fallaría con un mensaje como:

expected read_line to be called exactly 1 time, but it was called 0 times

Puede especificar cuántas veces debe llamarse su mock con "exactly":

it "keeps asking until it gets an answer" => sub {
  my @answers = (undef, "yes");
  my $console_mock = mock();
  $console_mock->expects('read_line')
               ->returns(sub { shift @answers })
               ->exactly(2);
  # cuando se llama a console_mock por primera vez, devuelve undef
  # la segunda vez devuelve "yes"
  ok( $asker->yes_or_no($console_mock, "Do I smell nice?") );
};

Si desea algo más flexible que "exactly", puede elegir entre "at_least", "at_most", "any_number" y otros. Consulte "MÉTODOS DE AJUSTE DE EXPECTATIVAS".

Anulación de métodos (Stubbing methods)

A veces desea anular solo un pequeño subconjunto del comportamiento de un objeto.

describe "The old audit system" => sub {
  my $dbh;
  before sub { $dbh = SomeExternalClass->get_dbh };
  it "executes the expected sql" => sub {
    my $sql;
    $dbh->stubs(do => sub { $sql = shift; return 1 });
    # $dbh->do("foo") ahora establece $sql a "foo"
    # $dbh->quote todavía hace lo que normalmente haría
    audit_event($dbh, "server crash, oh noes!!");
    like( $sql, qr/insert into audit_event.*'server crash, oh noes!!!'/ );
  };
};

También puede anular métodos de clase:

# 1977-05-26T14:11:55
my $event_datetime = DateTime->new(from_epoch => 0xdeafcab);
it "should tag each audit event with the current time" => sub {
  DateTime->stubs('now' => sub { $event_datetime });
  is( audit_timestamp(), '19770526.141155' );
};
