NOMBRE

Text::BibTeX::Structure - proporciona clases base para módulos de estructura de usuario

SINOPSIS

# Definir una estructura 'Foo' para bases de datos BibTeX: primero, la
# clase de estructura:
package Text::BibTeX::FooStructure;
@ISA = ('Text::BibTeX::Structure');
sub known_option 
{
   my ($self, $option) = @_;
   ...
}
sub default_option
{
   my ($self, $option) = @_;
   ...
}
sub describe_entry
{
   my $self = shift;
   $self->set_fields ($type,
                      \@required_fields,
                      \@optional_fields,
                      [$constraint_1, $constraint_2, ...]);
   ...
}
# Ahora, la clase de entrada estructurada
package Text::BibTeX::FooEntry;
@ISA = ('Text::BibTeX::StructuredEntry');
# definir los métodos que desees

DESCRIPCIÓN

El módulo "Text::BibTeX::Structure" proporciona dos clases que forman la base del sistema de "módulo de estructura" de btOOL. Este sistema es cómo se definen e imponen las estructuras de base de datos en archivos BibTeX, y proporciona una elegante síntesis de técnicas orientadas a objetos con estructuras de bases de datos al estilo BibTeX. Nada de lo descrito aquí es particularmente profundo o sutil; cualquiera familiarizado con la programación orientada a objetos debería poder seguirlo. Sin embargo, se inventa y se utiliza una buena cantidad de jerga, así que preste atención.

Una estructura de base de datos, en la jerga de btOOL, es simplemente un conjunto de tipos de entrada permitidos y las reglas para los campos en cada uno de esos tipos de entrada. Actualmente, hay tres tipos de reglas que se aplican a los campos: algunos campos son obligatorios, lo que significa que deben estar presentes en cada entrada para un tipo dado; otros son opcionales, lo que significa que pueden estar presentes y se utilizarán si lo están; otros campos son miembros de conjuntos de restricciones, que se explican en "Listas de campos y conjuntos de restricciones" más adelante.

Una estructura de btOOL se implementa con dos clases: la clase de estructura y la clase de entrada estructurada. La primera define todo lo que se aplica a la estructura en su conjunto (tipos permitidos y reglas de campos). La segunda proporciona métodos que operan sobre entradas individuales que se ajustan (o se supone que se ajustan) a la estructura. Las dos clases proporcionadas por el módulo "Text::BibTeX::Structure" son "Text::BibTeX::Structure" y "Text::BibTeX::StructuredEntry"; estas sirven como clases base para, respectivamente, todas las clases de estructura y todas las clases de entrada estructurada. Una estructura canónica se proporciona como ejemplo con btOOL: la estructura "Bib", que (a través de las clases "BibStructure" y "BibEntry") proporciona la misma funcionalidad que los archivos de estilo estándar de BibTeX 0.99. Se espera que otros programadores escriban nuevas estructuras relacionadas con la bibliografía, posiblemente derivando de la estructura "Bib", para emular parte de la funcionalidad que está disponible a través de archivos de estilo BibTeX de terceros.

El propósito de esta página del manual es describir todo el sistema de "módulo de estructura". Es principalmente para programadores que desean implementar una nueva estructura de base de datos para archivos de datos con sintaxis BibTeX; si está interesado en las reglas particulares para la estructura "Bib" que emula BibTeX, consulte Text::BibTeX::Bib.

Tenga en cuenta que el prefijo "Text::BibTeX" se omite de la mayoría de los nombres de módulos y clases en esta página del manual, excepto donde sea necesario.

CLASES DE ESTRUCTURA

Las clases de estructura tienen dos roles: definir la lista de tipos permitidos y las reglas de campos, y manejar las opciones de estructura.

Listas de campos y conjuntos de restricciones

Las listas de campos y los conjuntos de restricciones definen la estructura de la base de datos para un tipo de entrada particular: es decir, especifican las reglas que una entrada debe seguir para ajustarse a la estructura (asumiendo que la entrada es de un tipo permitido). Hay tres componentes en las reglas de campos para cada tipo de entrada: una lista de campos obligatorios, una lista de campos opcionales y restricciones de campos. Los campos obligatorios y opcionales deben ser obvios para cualquiera con experiencia en BibTeX: todos los campos obligatorios deben estar presentes, y cualquier campo opcional que esté presente tiene algún significado para la estructura. (Se podría concebir una interpretación "estricta", donde cualquier campo no mencionado en la definición oficial no está permitido; esto sería contrario al espíritu abierto de las bases de datos BibTeX, pero podría ser útil en ciertas aplicaciones donde se desea un nivel de control más estricto. Actualmente, btOOL no ofrece tal opción).

Las restricciones de campos capturan las relaciones del tipo "uno o el otro, pero no ambos" presentes para algunos tipos de entrada en los archivos de estilo estándar de BibTeX. La mayoría de la documentación de BibTeX omite la distinción entre campos mutuamente restringidos y campos obligatorios/opcionales. Por ejemplo, uno de los tipos de entrada estándar es "book", y ""author" o "editor"" se da en la lista de campos obligatorios para ese tipo. El significado de esto es que una entrada de tipo "book" debe tener *o* los campos "author" *o* "editor", pero no ambos. De manera similar, ""volume" o "number"" se enumeran bajo el encabezado "campos opcionales" para entradas "book"; sería más exacto decir que cada entrada "book" puede tener uno o el otro, o ninguno, de "volume" o "number", pero no ambos.

btOOL intenta aclarar esta situación creando una tercera categoría de campos, aquellos que están mutuamente restringidos. Por ejemplo, ni "author" ni "editor" aparecen en la lista de campos obligatorios para el tipo "inbook" según btOOL; en su lugar, se crea una restricción de campo para expresar esta relación:

[1, 1, ['author', 'editor']]

Es decir, una restricción de campo es una referencia a una lista de tres elementos. El último elemento es una referencia al conjunto de restricción, la lista de campos a los que se aplica la restricción. (Llamarlo conjunto es un poco impreciso, ya que hay condiciones en las que el orden de los campos importa — vea el método "check_field_constraints" en "MÉTODOS 2: CLASE BASE DE ENTRADA ESTRUCTURADA".) Los dos primeros elementos son el número mínimo y máximo de campos del conjunto de restricción que deben estar presentes para que una entrada se ajuste a la restricción. Esta restricción expresa así que debe haber exactamente uno (≥ 1 y ≤ 1) de los campos "author" o "editor" en una entrada "book".

La restricción "uno o ninguno, pero no ambos" que se aplica a los campos "volume" y "number" para entradas "book" se expresa de manera ligeramente diferente:

[0, 1, ['volume', 'number']]

Es decir, puede estar presente 0 o 1, pero no los 2 completos, de "volume" o "number".

Es importante notar que la comprobación y aplicación de las restricciones de campos se basa puramente en contar qué campos de un conjunto están realmente presentes; este mecanismo no puede capturar relaciones del tipo "x debe estar presente si y está presente".

Los requisitos impuestos a la clase de estructura real son simples: debe proporcionar un método "describe_entry" que configura una estructura de datos elaborada que describe los tipos de entrada permitidos y todas las reglas de campos para esos tipos. La clase "Structure" proporciona métodos (heredados por una clase de estructura particular) para ayudar a las clases de estructura particulares a crear esta estructura de datos de una manera consistente y controlada. Por ejemplo, el método "describe_structure" en la clase "BibStructure" que emula BibTeX 0.99 es bastante simple:

/p> 
sub describe_entry
{
   my $self = shift;
   # serie de 13 llamadas a $self->set_fields (una para cada tipo de
   # entrada estándar)
}

Una de esas llamadas al método "set_fields" define las reglas para las entradas de tipo "book":

$self->set_fields ('book',
                   [qw(title publisher year)],
                   [qw(series address edition month note)],
                   [1, 1, [qw(author editor)]],
                   [0, 1, [qw(volume number)]]);

La primera lista de campos es la lista de campos requeridos, y la segunda es la lista de campos opcionales. Puede haber cualquier número de restricciones de campo después de la lista de campos opcionales; en este caso, hay dos, una para cada una de las restricciones ("author"/"editor" y "volume"/"number") descritas anteriormente. En ningún momento se suministra explícitamente una lista de tipos permitidos; en cambio, cada llamada a "set_fields" añade un tipo permitido más.

Los nuevos módulos de estructura que derivan de otros existentes probablemente usarán el método "add_fields" (y posiblemente "add_constraints") para aumentar un tipo de entrada existente. La adición de nuevos tipos debe hacerse con "set_fields", sin embargo.

Opciones de estructura

La otra responsabilidad de las clases de estructura es manejar las *opciones de estructura*. Estos son valores escalares que permiten al usuario personalizar el comportamiento tanto de la clase de estructura como de la clase de entrada estructurada. Por ejemplo, se podría tener una opción para habilitar la "estructura extendida", que podría añadir un montón de nuevos tipos de entrada y nuevos campos. (En este caso, el método "describe_entry" tendría que prestar atención a esta opción y modificar su comportamiento en consecuencia.) O bien, se podrían tener opciones para controlar cómo la clase de entrada estructurada ordena o formatea las entradas (para estructuras de bibliografía como "Bib").

La forma fácil de manejar las opciones de estructura es proporcionar dos métodos, "known_option" y "default_option". Estos devuelven, respectivamente, si una opción dada es compatible y cuál es su valor predeterminado. (Si tu estructura no soporta ninguna opción, puedes simplemente heredar estos métodos de la clase "Structure". El "known_option" predeterminado devuelve falso para todas las opciones, y su compañero "default_option" falla con un error de "opción desconocida".)

Una vez que se proporcionan "known_option" y "default_option", la clase de estructura puede relajarse y heredar los métodos más visibles "set_options" y "get_options" de la clase "Structure". Estos son los métodos que se usan realmente para modificar/consultar opciones, y serán utilizados por los programas de aplicación para personalizar el comportamiento del módulo de estructura, y por el propio módulo de estructura para prestar atención a los deseos del usuario.

Las opciones generalmente deben tener valores de cadena puros, para que el método genérico set_options no tenga que analizar cadenas suministradas por el usuario en una estructura complicada. Sin embargo, "set_options" acepta cualquier valor escalar, por lo que si el módulo de estructura documenta claramente sus requisitos, el programa de aplicación podría suministrar una estructura que cumpla sus necesidades. Ten en cuenta que esto requiere cooperación entre la aplicación y el módulo de estructura; el código intermediario en "Text::BibTeX::Structure" no sabe nada sobre el formato o la sintaxis de las opciones de tu estructura, y cualquier escalar que la aplicación pase a través de "set_options" se almacenará para que tu módulo lo recupere a través de "get_options".

Como ejemplo, la estructura "Bib" soporta una serie de opciones de "etiquetado" que permiten a las aplicaciones controlar el lenguaje de etiquetado utilizado para formatear entradas bibliográficas. Estas opciones se emparejan de forma natural, ya que los comandos de formato en los lenguajes de etiquetado generalmente tienen que activarse y desactivarse. La estructura "Bib" por lo tanto espera referencias a listas de dos elementos para las opciones de etiquetado; para especificar el énfasis estilo LaTeX 2e para títulos de libros, una aplicación como "btformat" establecería la opción "btitle_mkup" de la siguiente manera:

$structure->set_options (btitle_mkup => ['\emph{', '}']);

Otras opciones para otras estructuras podrían tener una estructura más complicada, pero depende de la clase de estructura documentar y hacer cumplir esto.

CLASES DE ENTRADAS ESTRUCTURADAS

Una *clase de entrada estructurada* define el comportamiento de las entradas individuales bajo el régimen de una estructura de base de datos particular. Esta es la *razón de ser* de cualquier estructura de base de datos: la clase de estructura simplemente establece las reglas para que las entradas cumplan con la estructura, pero la clase de entrada estructurada proporciona los métodos que operan realmente sobre las entradas individuales. Dado que esto es completamente abierto, los requisitos de una clase de entrada estructurada son mucho menos rígidos que para una clase de estructura. De hecho, todos los requisitos de una clase de entrada estructurada se pueden cumplir simplemente heredando de "Text::BibTeX::StructuredEntry", la otra clase proporcionada por el módulo "Text::BibTeX::Structure". (Para que conste, esos requisitos son: una clase de entrada estructurada debe proporcionar los métodos de análisis/consulta/manipulación de entradas de la clase "Entry", y debe proporcionar los métodos "check", "coerce" y "silently_coerce" de la clase "StructuredEntry". Dado que "StructuredEntry" hereda de "Entry", ambos requisitos se cumplen "gratis" por las clases de entrada estructurada que heredan de "Text::BibTeX::StructuredEntry", ¡así que naturalmente este es el curso de acción recomendado!)

Deliberadamente no hay otros métodos requeridos de las clases de entrada estructurada. Una aplicación particular (por ejemplo, "btformat" para estructuras de bibliografía) requerirá ciertos métodos, pero depende de la aplicación y del módulo de estructura acordar los requisitos a través de la documentación.

INTERACCIONES DE CLASES

Imponer una estructura de base de datos a tus entradas desencadena una reacción en cadena de interacciones entre varias clases en la biblioteca "Text::BibTeX" que deberían ser transparentes cuando todo va bien. Podría resultar confuso si las cosas van mal y tienes que adentrarte en varios niveles de programas de aplicación, clases centrales de "Text::BibTeX" y algún módulo de estructura.

La justificación de este complicado comportamiento es que te permite escribir programas que utilizarán un módulo estructurado particular sin saber el nombre de la estructura cuando escribas el programa. Por lo tanto, el usuario puede suministrar una estructura de base de datos, y finalmente los objetos de entrada que manipules serán bendecidos en una clase suministrada por el módulo de estructura. Un breve ejemplo ilustrará esto.

Típicamente, un programa basado en "Text::BibTeX" se basa en un núcleo de código como este:

$bibfile = Text::BibTeX::File->new("foo.bib");
while ($entry = Text::BibTeX::Entry->new($bibfile))
{
   # procesar $entry
}

En este caso, no ocurre nada especial entre bastidores: el objeto $bibfile es bendecido en la clase "Text::BibTeX::File", y $entry es bendecido en "Text::BibTeX::Entry". Este es el comportamiento convencional de las clases de Perl, pero no es el único comportamiento posible. Supongamos ahora que se espera que $bibfile cumpla con una estructura de base de datos especificada por $structure (presumiblemente un valor suministrado por el usuario, y por lo tanto desconocido en tiempo de compilación):

$bibfile = Text::BibTeX::File->new("foo.bib");
$bibfile->set_structure ($structure);
while ($entry = Text::BibTeX::Entry->new($bibfile))
{
   # procesar $entry
}

Ocurren muchas cosas entre bastidores con la llamada al método "set_structure" de $bibfile. Primero, se crea un nuevo objeto de estructura a partir de $structure. El nombre de la estructura implica el nombre de un módulo de Perl —el módulo de estructura— que es cargado por el constructor "Structure". (La principal consecuencia de esto es que cualquier error en tiempo de compilación en tu módulo de estructura no se revelará hasta que una llamada a "Text::BibTeX::File::set_structure" o "Text::BibTeX::Structure::new" intente cargarlo.)

Recuerda que la primera responsabilidad de un módulo de estructura es definir una clase de estructura. El "objeto de estructura" creado por la llamada al método "set_structure" es en realidad un objeto de esta clase; este es el primer truco —el objeto de estructura (oculto entre bastidores) es bendecido en una clase cuyo nombre no se conoce hasta el tiempo de ejecución.

Ahora, el comportamiento del constructor "Text::BibTeX::Entry::new" cambia sutilmente: en lugar de devolver un objeto bendecido en la clase "Text::BibTeX::Entry" como podrías esperar del código, el objeto es bendecido en la clase de entrada estructurada asociada con $structure.

Por ejemplo, si el valor de $structure es "Foo", eso significa que el usuario ha suministrado un módulo que implementa la estructura "Foo". (Normalmente, este módulo se llamaría "Text::BibTeX::Foo", pero puedes personalizar esto.) Llamar al método "set_structure" en $bibfile hará que al

MECÁNICAS INTERNAS

El intento de crear una nueva estructura de objeto a través del constructor "Text::BibTeX::Structure", que carga el módulo de estructura "Text::BibTeX::Foo". Una vez que este módulo se carga con éxito, el nuevo objeto se "bendice" (blessed) en su clase de estructura, que presumiblemente se llamará "Text::BibTeX::FooStructure" (de nuevo, esto es personalizable). Al nuevo objeto se le proporcionan las opciones de estructura del usuario a través del método "set_options" (generalmente heredado), y luego se le pide que describa la disposición real de las entradas llamando a su método "describe_entry". Esto, a su vez, generalmente llamará al método heredado "set_fields" para cada tipo de entrada en la estructura de la base de datos. Cuando el constructor "Structure" finaliza, el nuevo objeto de estructura se almacena en el objeto "File" (recuerde, empezamos todo esto llamando a "set_structure" en un objeto "File") para referencia futura.

Luego, cuando se crea un nuevo objeto "Entry" y se analiza a partir de ese objeto "File" en particular, ocurren más trucos. Trivialmente, el objeto de estructura almacenado en el objeto "File" también se almacena en el objeto "Entry". (La idea es que las entradas podrían pertenecer a una estructura de base de datos independientemente de cualquier archivo, pero por lo general simplemente obtendrán la estructura que se asignó a su archivo de base de datos). Más importante aún, el nuevo objeto "Entry" se "bendice" (re-blessed) de nuevo en la clase de entrada estructurada proporcionada por el módulo de estructura, presumiblemente, en este caso, "Text::BibTeX::FooEntry" (también personalizable).

Una vez que toda esta prestidigitación se ha logrado, la aplicación puede tratar sus objetos de entrada como objetos de la clase de entrada estructurada para la estructura "Foo"; pueden llamar a los métodos de verificación/coerción heredados de "Text::BibTeX::StructuredEntry", y también pueden llamar a cualquier método específico de las entradas para esta estructura de base de datos en particular. Cuáles podrían ser estos métodos depende del implementador de la estructura decidir y documentar; por lo tanto, las aplicaciones pueden ser específicas de una estructura de base de datos en particular, o pueden funcionar en todas las estructuras que proporcionan ciertos métodos. La elección depende del desarrollador de la aplicación, y el rango de opciones abiertas para él depende de qué métodos proporcionan los implementadores de la estructura.

MÉTODOS 1: CLASE BASE DE ESTRUCTURA

La primera clase proporcionada por el módulo "Text::BibTeX::Structure" es "Text::BibTeX::Structure". Esta clase está destinada a proporcionar métodos que serán heredados por las clases de estructura suministradas por el usuario; tales clases no deben anular ninguno de los métodos descritos aquí (excepto "known_option" y "default_option") sin una muy buena razón. Además, anular el método "new" sería inútil, porque en general las aplicaciones no conocerán el nombre de su clase de estructura; solo pueden llamar a "Text::BibTeX::Structure::new" (generalmente a través de "Text::BibTeX::File::set_structure").

Finalmente, hay tres métodos que las clases de estructura deben implementar: "known_option", "default_option" y "describe_entry". Los dos primeros se describen en "Opciones de estructura" más arriba, el último en "Listas de campos y conjuntos de restricciones". Tenga en cuenta que "describe_entry" depende en gran medida de los métodos "set_fields", "add_fields" y "add_constraints" descritos aquí.

Constructor/métodos de consulta simples

new (ESTRUCTURA, [OPCIÓN => VALOR, ...])
Construye un nuevo objeto de estructura, *no* un objeto "Text::BibTeX::Structure", sino más bien un objeto "bendecido" (blessed) en la clase de estructura asociada con ESTRUCTURA. Más precisamente:
  • Carga (con "require") el módulo que implementa ESTRUCTURA. En ausencia de otra información, el nombre del módulo se deriva añadiendo ESTRUCTURA a "Text::BibTeX::", por lo tanto, el módulo "Text::BibTeX::Bib" implementa la estructura "Bib". Use la pseudo-opción "module" para anular este nombre de módulo. Por ejemplo, si la estructura "Foo" es implementada por el módulo "Foo": 
    $structure = Text::BibTeX::Structure->new
   ('Foo', module => 'Foo');

    Este método falla (`die`) si hay algún error al cargar/compilar el módulo de estructura.

  • Verifica que el módulo de estructura proporcione una clase de estructura y una clase de entrada estructurada. La clase de estructura se nombra añadiendo "Structure" al nombre del módulo, y la clase de entrada estructurada añadiendo "Entry". Por lo tanto, en ausencia de una opción "module", estas dos clases (para la estructura "Bib") se llamarían "Text::BibTeX::BibStructure" y "Text::BibTeX::BibEntry". Cualquiera o ambos nombres de clase predeterminados pueden ser anulados haciendo que el módulo de estructura devuelva una referencia a un hash (en contraposición al tradicional 1 devuelto por los módulos). Este hash podría entonces proporcionar un elemento "structure_class" para nombrar la clase de estructura, y un elemento "entry_class" para nombrar la clase de entrada estructurada.

    Además de garantizar que las dos clases realmente existan, "new" verifica que heredan correctamente (de "Text::BibTeX::Structure" y "Text::BibTeX::StructuredEntry" respectivamente), y que la clase de estructura proporciona los métodos requeridos "known_option", "default_option" y "describe_entry".

  • Crea el nuevo objeto de estructura y lo "bendice" (blesses) en la clase de estructura. Le proporciona opciones pasando todos los pares (OPCIÓN, VALOR) a su método "set_options". Llama a su método "describe_entry", que debería listar los requisitos de campo para todos los tipos de entrada reconocidos por esta estructura. "describe_entry" probablemente usará algunos o todos los métodos "set_fields", "add_fields" y "add_constraints", descritos a continuación, para esto.
name ()
Devuelve el nombre de la estructura descrita por el objeto.
entry_class ()
Devuelve el nombre de la clase de entrada estructurada asociada con esta estructura.

Métodos de descripción de la estructura de campos

add_constraints (TIPO, RESTRICCIÓN, ...)
Añade una o más restricciones de campo a la estructura. Una restricción de campo se especifica como una referencia a una lista de tres elementos; el último elemento es una referencia a la lista de campos afectados, y los primeros dos elementos son el número mínimo y máximo de campos del conjunto de restricciones permitidos en una entrada de tipo TIPO. Consulte "Listas de campos y conjuntos de restricciones" para una explicación completa de las restricciones de campo.
add_fields (TIPO, REQUERIDOS [, OPCIONALES [, RESTRICCIÓN, ...]])
Añade campos a las listas de requeridos/opcionales para entradas de tipo TIPO. También puede añadir restricciones de campo, pero puede hacerlo tan fácilmente usando "add_constraints" para ello.

REQUERIDOS y OPCIONALES, si se definen, deben ser referencias a listas de campos que se añadirán a las listas respectivas. Las RESTRICCIONES, si se dan, son exactamente como se describen para "add_constraints" más arriba.

set_fields (TIPO, REQUERIDOS [, OPCIONALES [, RESTRICCIONES, ...]])
Establece las listas de campos requeridos/opcionales para entradas de tipo TIPO. Idéntico a "add_fields", excepto que las listas de campos y la lista de restricciones se establecen desde cero aquí, en lugar de añadirse a las existentes.

Métodos de consulta de la estructura de campos

types ()
Devuelve la lista de tipos de entrada admitidos por la estructura.
known_type (TIPO)
Devuelve verdadero si TIPO es un tipo de entrada admitido.
known_field (TIPO, CAMPO)
Devuelve verdadero si CAMPO está en la lista requerida, lista opcional, o uno de los conjuntos de restricciones para entradas de tipo TIPO.

Métodos de opciones

known_option (OPCIÓN)
Retorna falso. Esto es principalmente para el uso de estructuras derivadas que no tienen opciones, y por lo tanto no necesitan proporcionar su propio método "known_option". Las estructuras que realmente ofrecen opciones deberían sobrescribir este método; debería retornar verdadero si OPCIÓN es una opción admitida.
default_option (OPCIÓN)
Se bloquea con un mensaje de \"opción desconocida\". De nuevo, esto es principalmente para uso por parte de clases de estructura derivadas que en realidad no ofrecen ninguna opción. Las estructuras que manejan opciones deberían sobrescribir este método; cada opción manejada por "known_option" debería tener un valor predeterminado (que podría ser simplemente "undef") que es retornado por "default_option". Tu método "default_options" debería fallar ante una opción desconocida, quizás llamando a "SUPER::default_option" (para asegurar mensajes de error consistentes). Por ejemplo: 
sub default_option
{
   my ($self, $option) = @_;
   return $default_options{$option}
      if exists $default_options{$option};
   $self->SUPER::default_option ($option);   # crash
}

El valor predeterminado para una opción es retornado por "get_options" cuando esa opción no ha sido establecida explícitamente con "set_options".

set_options (OPCIÓN => VALOR, ...)
Establece uno o más valores de opción. (Puedes suministrar tantos pares de "OPCIÓN => VALOR" como quieras, siempre y cuando haya un número par de argumentos.) Cada OPCIÓN debe ser manejada por el módulo de estructura (como se indica en el método "known_option"); de lo contrario, "set_options" fallará (`croak`). Cada VALOR puede ser cualquier valor escalar; depende del módulo de estructura validarlos.
get_options (OPCIÓN, ...)
Retorna el(los) valor(es) de una o más opciones. Cualquier OPCIÓN que no haya sido establecida por "set_options" retornará su valor predeterminado, obtenido usando el método "default_value". Si la OPCIÓN no es admitida por el módulo de estructura, entonces tu programa ya se ha bloqueado (cuando intentó establecerla con "set_option"), o se bloqueará aquí (gracias a la llamada a "default_option").

MÉTODOS 2: CLASE BASE DE ENTRADAS ESTRUCTURADAS

La otra clase proporcionada por el módulo "Structure" es "StructuredEntry", la clase base para todas las clases de entradas estructuradas. Esta clase hereda de "Entry", por lo que todos sus métodos de consulta/manipulación de entradas están disponibles. "StructuredEntry" añade métodos para verificar que una entrada se ajusta a la estructura de la base de datos definida por una clase de estructura.

Solo tiene sentido que "StructuredEntry" se utilice como clase base; nunca crearías objetos "StructuredEntry" independientes. La razón superficial de esto es que solo las clases particulares de entrada estructurada tienen una clase de estructura asociada con ellas; "StructuredEntry" por sí sola no tiene información sobre tipos permitidos, campos requeridos, restricciones de campo, etc. Para una comprensión más profunda, consulta "INTERACCIONES DE CLASES" arriba.

Dado que "StructuredEntry" deriva de "Entry", opera naturalmente sobre entradas BibTeX. Por lo tanto, las siguientes descripciones se refieren a "la entrada" — este es solo el objeto (entrada) sobre el que se opera. Ten en cuenta que estos métodos se presentan en orden ascendente, lo que significa que los métodos que es más probable que uses realmente — "check", "coerce" y "silently_coerce" — están al final. En una primera lectura, probablemente querrás saltar directamente a ellos para un resumen rápido.

structure ()
Retorna el objeto que define la estructura a la que se supone que la entrada debe ajustarse. Esta será una instancia de alguna clase de estructura, y existe principalmente para que los métodos de verificación/coerción puedan consultar la estructura sobre los tipos y campos que reconoce. Si, por alguna razón, quisieras consultar la estructura de una entrada sobre la validez del tipo "foo", podrías hacer esto: 
# asume que $entry es un objeto de alguna clase de entrada estructurada, es decir,
# hereda de Text::BibTeX::StructuredEntry
$structure = $entry->structure;
$foo_known = $structure->known_type ('foo');
check_type ([WARN])
Retorna verdadero si la entrada tiene un tipo válido según su estructura. Si WARN es verdadero, entonces un tipo inválido resulta en una advertencia impresa.
check_required_fields ([WARN [, COERCE]])
Verifica que todos los campos requeridos estén presentes en la entrada. Si WARN es verdadero, entonces se imprime una advertencia por cada campo faltante. Si COERCE es verdadero, entonces los campos faltantes se establecen a una cadena vacía.

Esto no es usado generalmente por otro código; consulta los métodos "check" y "coerce" a continuación.

check_field_constraints ([WARN [, COERCE]])
Verifica que la entrada se ajuste a todas las restricciones de campo impuestas por su estructura. Recuerda que una restricción de campo consiste en una lista de campos y un número mínimo y máximo de esos campos que deben estar presentes en una entrada. Para cada restricción, "check_field_constraints" simplemente cuenta cuántos campos del conjunto de campos de la restricción están presentes. Si este recuento cae por debajo del mínimo o por encima del máximo para esa restricción y WARN es verdadero, se emite una advertencia. En general, esta advertencia tiene el formato "entre x e y de los campos foo, bar y baz deben estar presentes". Los casos más comunes se manejan especialmente para generar mensajes de advertencia más útiles y fáciles de leer.

Si COERCE es verdadero, entonces la entrada se modifica para forzar su conformidad con todas las restricciones de campo. Cómo se hace esto depende de si la violación es una cuestión de no tener suficientes campos presentes en la entrada, o de tener demasiados campos presentes. En el primer caso, se agregan suficientes campos (como cadenas vacías) para cumplir con los requisitos de la restricción; en el segundo caso, se eliminan campos. Qué campos agregar o eliminar se controla por el orden de los campos en la lista de campos de la restricción.

Un ejemplo debería aclarar esto. Por ejemplo, una restricción de campo que especifica que exactamente uno de "author" o "editor" debe aparecer en una entrada se vería así:

[1, 1, ['author', 'editor']]

Supongamos que la siguiente entrada se analiza y se espera que se ajuste a esta estructura:

@inbook{unknown:1997a,
  title = "Un capítulo de libro no atribuido",
  booktitle = "Un libro no editado",
  publisher = "Foo, Bar \& Company",
  year = 1997
}

Si se llama a "check_field_constraints" en este método con COERCE verdadero (lo cual es hecho por cualquiera de los métodos "full_check", "coerce" y "silently_coerce"), entonces el campo "author" se establece como una cadena vacía. (Recorremos la lista de campos en el conjunto de campos de la restricción en orden — dado que "author" es el primer campo faltante, lo proporcionamos; con eso hecho, la entrada ahora se ajusta a la restricción "author"/"editor", así que hemos terminado.)

Sin embargo, si la misma estructura se aplicara a esta entrada:

@inbook{smith:1997a,
  author = "John Smith",
  editor = "Fred Jones",
  ...
}

entonces el campo "editor" sería eliminado. En este caso, permitimos el primer campo en la lista de campos de la restricción — "author". Dado que solo un campo del conjunto puede estar presente, todos los campos posteriores al primero están en violación, por lo que se eliminan.

De nuevo, este método no es usado generalmente por otro código; más bien, es llamado por "full_check" y sus amigos a continuación.

full_check ([WARN [, COERCE]])
Retorna verdadero si el tipo y los campos de una entrada son todos válidos. Es decir, llama a "check_type", "check_required_fields" y "check_field_constraints"; si todas devuelven verdadero, entonces también lo hace "full_check". WARN y COERCE simplemente se pasan a los tres métodos "check_*": el primero controla la impresión de advertencias, y el segundo decide si debemos modificar la entrada para forzar su conformidad.

NAME

Text::BibTeX::Structure - Base class for BibTeX structures

SYNOPSIS

    use Text::BibTeX::Structure;

    # Subclasses inherit methods from this class.
    #
    # For example:
    package My::BibTeX::Structure;
    use base qw(Text::BibTeX::Structure);
    # ...

DESCRIPTION

This is the base class for objects representing BibTeX structures (like Text::BibTeX::String, Text::BibTeX::Value, etc.). Subclasses should inherit from this class.

It defines methods for checking the validity of a structure against its associated database structure, and for coercing it into conformance.

STRUCTURE CLASSES

Text::BibTeX::String, Text::BibTeX::Value, Text::BibTeX::Comment, Text::BibTeX::Macro, Text::BibTeX::Braced_Literal, Text::BibTeX::Quoted_Literal.

STRUCTURED ENTRY CLASSES

Text::BibTeX::Entry, Text::BibTeX::Preamble, Text::BibTeX::String_Def, Text::BibTeX::Variable.

CLASS INTERACTIONS

The methods defined in this class are primarily intended for use by Text::BibTeX::Database and the structured entry classes.

EXAMPLE

    use Text::BibTeX::Entry;
    use Text::BibTeX::Value;
    use Text::BibTeX::Database;

    # Create a simple database with a single entry
    my $db = Text::BibTeX::Database->new;
    my $entry = Text::BibTeX::Entry->new('article', 'unique-key');
    $entry->set_field('author', 'Some One');
    $entry->set_field('title', 'An Article Title');
    $entry->set_field('year', Text::BibTeX::Value->new(1999));
    $db->add_entry($entry);

    # Check the validity of the entry
    if ($db->check) {
        print "Entry is valid.\n";
    } else {
        print "Entry is invalid.\n";
        # Use $db->errors to see details
    }

    # Coerce the entry (e.g., fix missing fields if possible)
    $db->coerce;

METHODS 1: BASE STRUCTURE CLASS

check ()
Checks the validity of the object (and its children, if any) against its associated database structure: the type must be known, all required fields must be present, and all field constraints must be met. See "check_type", "check_required_fields", and "check_field_constraints" for details.
full_check (WARN => boolean, COERCE => boolean)
Performs a full check of the object against its associated database structure. WARN (default true) enables printing of warnings for non-critical errors. COERCE (default false) attempts to coerce the object into conformance with the database structure before checking. Returns true if the object is valid, false otherwise.

METHODS 2: BASE STRUCTURED ENTRY CLASS

These methods are primarily intended for use by structured entry classes (like Text::BibTeX::Entry) which inherit from Text::BibTeX::Structure.

check ()
Checks the validity of the object and its associated fields against its associated database structure: the type must be known, all required fields must be present, and all field constraints must be met. See "check_type", "check_required_fields", and "check_field_constraints" for details.

Calling "check" is the same as calling "full_check" with WARN true and COERCE false.

coerce ()
Same as "check", except entries are coerced into conformance with the database structure---that is, it's just like "full_check" with both WARN and COERCE true.
silently_coerce ()
Same as "coerce", except warnings aren't printed---that is, it's just like "full_check" with WARN false and COERCE true.
