Test2::Tools::Process(3) Documentación de Perl contribuida por el usuario Test2::Tools::Process(3)

NOMBRE

Test2::Tools::Process - Pruebas unitarias para código que llama a exit, exec, system o qx()

VERSIÓN

version 0.07

SINOPSIS

use Test2::V0 -no_srand => 1;
use Test2::Tools::Process;

process {
  system 'foo', 'bar';
} [
  # comprobar que la primera llamada a system es
  # a un comando foo con cualquier argumento
  proc_event(system => array {
    item 'foo';
    etc;
  }, sub {
    # simular el comando foo
    my($proc, @args) = @_;
    note "comando bar simulado: @args";
    # simular una salida normal
    $proc->exit(0);
  }),
];

process {
  exit 2;
  note 'no ejecutado';
} [
  # se pueden usar todas las comprobaciones de Test2 en el estado de salida
  proc_event(exit => match qr/^[2-3]$/),
];

process {
  exit 4;
} [
  # o puedes simplemente comprobar que el estado de salida coincide numéricamente
  proc_event(exit => 4),
];

process {
  exit 5;
} [
  # o simplemente comprobar que se llamó a exit.
  proc_event('exit'),
];

process {
  exec 'foo bar';
  exec 'baz';
  note 'no ejecutado';
} [
  # emular el primer exec como fallido
  proc_event(exec => match qr/^foo\b/, sub {
    my($return, @command) = @_;
    $! = 2;
    return 0;
  }),
  # el segundo exec se emulará como exitoso
  proc_event('exec'),
];

# solo interceptar `exit`
is intercept_exit { exit 10 }, 10;

# solo interceptar `exec`
is intercept_exec { exec 'foo', 'bar', 'baz' }, ['foo','bar','baz'];

done_testing;

DESCRIPCIÓN

Este conjunto de herramientas de prueba está destinado a escribir pruebas unitarias para código que interactúa con otros procesos sin utilizar procesos reales que puedan tener efectos secundarios no deseados. También le permite probar código que termina el flujo del programa sin terminar realmente su prueba. Hasta ahora, permite probar y/o simular "exit", "exec", "system", "readpipe" y "qx//". Se añadirán otras pruebas relacionadas con procesos en el futuro.

Este módulo toma prestadas algunas ideas de Test::Exit. En particular, no utiliza excepciones para simular "exit" o "exec", por lo que puede probar libremente código que llama a estas dentro de un "eval".

FUNCIONES

process

my $ok = process { ... } \@events, $test_name;
my $ok = process { ... } \@events;
my $ok = process { ... } $test_name;
my $ok = process { ... };

Ejecuta el bloque, interceptando llamadas a "exit", "exec", "system", "readpipe" y "qx//". Las llamadas se comparan luego con "\@events" como los eventos de proceso esperados. Consulte "proc_event" a continuación para definir eventos individuales, y la sinopsis anterior para ver ejemplos.

named_signal

my $signame = named_signal $name;

Dado un nombre de señal de cadena como "KILL", esto devolverá el número de señal entero. Lanzará una excepción si el $name no es válido.

intercept_exit

my $status = intercept_exit { ... };

Intercepta cualquier llamada a c<exit> dentro del bloque y devuelve el estado de salida. Devuelve "undef" si no hubo llamadas a "exec".

intercept_exec

my $arrayref = intercept_exec { ... };

Intercepta cualquier llamada a "exec" dentro del bloque y devuelve la línea de comandos que se le pasó. Devuelve "undef" si no hubo llamadas a "exec".

COMPROBACIONES

proc_event

process { ... } [
  proc_event($type => $check, $callback),
  proc_event($type => $check),
  proc_event($type => $callback),
  proc_event($type),

  # comprobaciones de resultados adicionales para eventos `system`
  proc_event('system' => $check, \%result_check, $callback),
  proc_event('system' => \%result_check, $callback),
  proc_event('system' => $check, \%result_check),
  proc_event('system' => \%result_check),
];

La función "proc_event" crea un evento de proceso, con una comprobación y un callback opcionales. Cómo funciona $check depende de $type. Si no se proporciona $check, solo comprobará que coincida el $type. Debido a su naturaleza, los eventos "exit" y "exec" se emulan. Las llamadas "system" realizarán realmente una llamada al sistema, a menos que se proporcione un $callback.

exit
Un evento de proceso para una llamada "exit". La comprobación se realiza sobre el valor de estado pasado a "exit". Este valor siempre será un entero. Si no se pasó ningún valor de estado a "exit", se usará 0 como valor de estado.

Si no se proporciona un callback, se emulará una llamada a "exit" terminando el bloque del proceso sin ejecutar más código. El resto de la prueba continuará.

proc_event( exit => sub {
  my($proc, $status) = @_;
  $proc->terminate;
});

El callback toma un objeto $proc y un valor $status. Normalmente "exit" nunca debería devolver nada, por lo que lo que quieres hacer es llamar al método "terminate" en el objeto $proc.

exec
Un evento de proceso para una llamada "exec". La comprobación se realiza contra el comando pasado a "exec". Si "exec" se llama con un solo argumento, será una cadena, de lo contrario, será una referencia de array. De esta manera, puedes diferenciar entre los modos ESCALAR y LISTA de "exec".

Si no se proporciona un callback, se emulará una llamada a "exec" (exitosa) terminando el bloque del proceso sin ejecutar más código. El resto de la prueba continuará.

proc_event( exec => sub {
  my($proc, @command) = @_;
  ...;
});

El callback toma un objeto $proc y los argumentos pasados a "exec" como @command. Puedes emular una llamada a "exec" fallida utilizando el método "errno" en el objeto $proc:

proc_event( exec => sub {
  my($proc, @command) = @_;
  $proc->errno(2); # este es el valor de errno
});

Para emular una llamada a "exec" exitosa, quieres recordar llamar al método "terminate" en el objeto $proc.

proc_event( exec => sub {
  my($proc, @command) = @_;
  $proc->terminate;
});
system
Un evento de proceso para "system", "piperead" y "qx//". La primera comprobación (como con "exec") es contra la cadena de comandos pasada a "system". La segunda es una referencia de hash con comprobaciones de resultados.
status
Comprueba el estado de salida del comando.

Este será el mismo valor que se devuelve al llamar a system(). Si estás emulando una llamada a system() y no quieres que se ejecute ningún código real, deberás devolver algo que se parezca a un estado de salida.

# Asegúrate de que el comando 'ls' salga con estado 0
proc_event(
  system => 'ls',
  status => 0,
);

# Asegúrate de que el comando 'grep' salga con estado 1
# y que su salida sea 'bar'
proc_event(
  system => 'grep foo bar',
  status => 1,
  stdout => 'bar',
);
stdout
Comprueba la salida estándar del comando.

Solo se puede comprobar si la llamada es para "piperead" o "qx//".

stderr
Comprueba la salida de error estándar del comando.

No se puede comprobar para "system" porque el comando system no puede ser fácilmente interceptado para capturar el stderr.

CALLBACKS

Hay tres formas de especificar un callback. El primero se puede utilizar para emular casi cualquier comportamiento que necesites. Todos los callbacks se llaman con el objeto del proceso como primer argumento, y luego con los argumentos que se pasaron al comando original.

proc_event($type, $check, $callback)
Si estás intentando comprobar una llamada a "system", el callback se llama después de que se haya realizado la comprobación de la línea de comandos, y se espera que devuelva un hash de las claves de resultado que necesites (como status, stdout, stderr).
proc_event($type, $callback)
Este es el mismo que el anterior, pero asume que el callback devolverá el hash de resultados.
proc_event($type => $check, \%result_check, $callback)
Es idéntico al primer formato, pero con las comprobaciones de resultados del hash.
proc_event($type => \%result_check, $callback)
Es idéntico al segundo formato, pero con las comprobaciones de resultados del hash.

Como se mencionó anteriormente, los callbacks para "exit" y "exec" son un poco diferentes. En lugar de devolver valores, se espera que manipulen el objeto $proc para indicar un error o una salida.

Para "exit", el callback se llama con $proc y el estado de salida. El código dentro del callback es responsable de llamar a $proc->terminate para que la prueba pueda continuar.

Para "exec", el callback se llama con $proc y los argumentos de la línea de comandos. El código dentro del callback es responsable de llamar a $proc->terminate para simular una ejecución exitosa, o a $proc->errno($errno) para simular un fallo.

SUBVERTIR EL ORDEN DE LAS LLAMADAS

Este módulo se basa en la idea de que las llamadas a funciones como exit y exec son especiales. Lo que ocurre es que se sobrescriben temporalmente los modificadores globales de CORE::. Esto significa que si llamas a tu función de prueba dentro de un eval, esa llamada a exit no funcionará:

    my $status;
    eval {
        process {
            exit 2;
        } [ proc_event(exit => \$status) ];
    };
    ok($@); # Esto debería ser verdadero

No obstante, si llamas a exit dentro del bloque process, el evento de salida se capturará, y eval no capturará nada.

    my $status;
    eval {
        process {
            exit 2;
        } [ proc_event(exit => \$status) ];
    };
    ok(!$@); # Esto debería ser falso
    is($status, 2);

Test2::Tools::Process(3pm)
Test2::Tools::Process 0.07

NAME

Test2::Tools::Process - test processes.

VERSION

0.07

SYNOPSIS

use Test2::V0;
use Test2::Tools::Process;

# Execute a command and check its exit status
ok( system("ls -l") == 0, "ls exited cleanly");

# Execute a command and check its exit status, and also check stderr for content
my $check = {
    stdout => qr/some content/,
    stderr => qr/some error/,
    exit => 0,
};
ok( system("some_command") );

# Execute a command and check its exit status, and also check errno
my $check = {
    errno => 2, # Command not found
    exit => -1, # Any non-zero exit status
};
ok( system("non_existent_command") );

# Execute a command and check that it was killed by a signal
my $check = {
    signal => 9, # KILL signal
};
ok( system("some_command") );


# With a callback to simulate the command
subtest 1 => sub {
    plan tests => 1;

    my $checker = Test2::Tools::Process::Proc->new;

    my $pid = proc_event(
        system => sub {
            my ($proc, @command) = @_;
            $proc->exit(0); # Simulate a successful exit
            # $proc->signal(9); # Simulate being killed by a signal
            # $proc->errno(2); # Simulate a failed system call
        }
    );

    ok( system("ls -l") == 0 );
};

done_testing;

DESCRIPTION

This module provides tools for testing code that executes external commands using Perl's built-in "system", "exec", "qx", and "open" (with a pipe).

It works by overriding these functions in the "CORE::GLOBAL" namespace with its own versions. These versions can either execute the real command or, if a callback is provided, simulate the command's behavior.

FUNCTIONS

The module exports the following functions:

proc_event
proc_event(
    system => $check,
    [ exec => $check ],
    [ qx   => $check ],
    [ readpipe => $check ],
    [ callback => sub { ... } ],
);

This is the main function for setting up event checks. It takes a hash of checks and optional callback.

The checks can be:

system

Checks the return value of system().

exec

Checks the behavior of exec(). This is a bit different as exec does not return.

qx

Checks the return value of qx() (backticks).

readpipe

Checks the behavior of open() when used to read from a pipe.

The $check value can be a hash reference containing one of the following keys:

exit
proc_event( system => { exit => $check } );

The normal termination status. This is usually the value passed to "exit" in the program called. Typically a program that succeeded will return zero (0) and a failed on will return non-zero.

errno
proc_event( system => { errno => $check } );

The "errno" or $! value if the system call failed. Most commonly this is for bad command names, but it could be something else like running out of memory or other system resources.

signal
proc_event( system => { signal => $check } );

Set if the process was killed by a signal.

Only one check should be included because only one of these is usually valid. If you do not provide this check, then it will check that the status code is zero only.

By default the actual system call will be made, but if you provide a callback you can simulate commands, which is helpful in unit testing your script without having to call external programs which may have unwanted side effects.

proc_event( system => sub {
  my($proc, @command) = @_;
  ...
});

Like the "exec" event, @command contains the full command passed to the "system" call. You can use the $proc object to simulate one of three different results:

exit
$proc->exit($status);
$proc->exit;

Exit with the given status. A status of zero (0) will be used if not provided. If no result is specified in the callback at all then a status of zero (0) will also be used.

signal
$proc->signal($signal);

Terminate with the given signal. $signal can be either an integer value (in which case no validation that it is a real signal is done), or a string signal name like "KILL", "HUP" or any signal supported by your operating system. If you provide an invalid signal name an exception will be thrown.

proc_event( system => { signal => 9 } => sub {
  my($proc, @args) = @_;
  $proc->signal('KILL');
});

Note that when you kill one of these faux processes with a signal you will want to update the expected signal check, as in the example above.

errno
$proc->errno($errno);

Simulate a failed "system" call. Most often "system" will fail if the command is not found. The $errno passed in should be a valid "errno" value. On my system 2 is the error code for command not found. Example:

proc_event( system => { errno => number(2) } => sub {
  my($proc, @args) = @_;
  $proc->errno(2);
});
type
my $type = $proc->type;

Returns "system" or "readpipe" depending on the Perl function that triggered the system call.

CAVEATS

The "exit" emulation, doesn't call "END" callbacks or other destructors, since you aren't really terminating the process.

This module installs handlers for "exec", "exit", "system" and "readpipe", in the "CORE::GLOBAL" namespace, so if your code is also installing handlers there then things might not work.

This module is not apparently compatible with IPC::Run3. Use Capture::Tiny instead, which is better maintained in my opinion.
