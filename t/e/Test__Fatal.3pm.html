Test::Fatal(3) Documentación perl aportada por usuarios Test::Fatal(3)

NOMBRE

Test::Fatal - helpers para probar código con excepciones de forma muy sencilla

VERSIÓN

versión 0.018

SINOPSIS

use Test::More;
use Test::Fatal;
use System::Under::Test qw(might_die);
is(
  exception { might_die; },
  undef,
  "el código vivió",
);
like(
  exception { might_die; },
  qr/resulta que murió/,
  "el código murió como se esperaba",
);
isa_ok(
  exception { might_die; },
  'Exception::Whatever',
  'la excepción lanzada',
);

DESCRIPCIÓN

Test::Fatal es una alternativa a Test::Exception. Hace poco más, pero debería permitir mayor flexibilidad al probar código que lanza excepciones con el mismo nivel de tipado.

Exporta por defecto una rutina: "exception".

¡Atención! "exception" no manipula la pila de llamadas. Las rutinas de prueba escritas por el usuario que utilizan "exception" deben ser cuidadosas para evitar falsos positivos si las excepciones usan trazas de pila que muestran argumentos. Para una solución más mágica que sobrescriba globalmente "caller", vea Test::Exception.

VERSIÓN DE PERL

Esta librería debería funcionar en versiones de perl publicadas incluso hace mucho tiempo. Debería funcionar en cualquier versión de perl publicada en los últimos cinco años.

Aunque pueda funcionar en versiones antiguas de perl, no se garantiza que la versión mínima requerida no se aumente. La versión puede aumentarse por cualquier motivo, y no hay garantía de que se aceptarán parches para disminuir la versión mínima requerida de perl.

FUNCIONES

exception

my $exception = exception { ... };

"exception" toma un bloque de código sin paréntesis y devuelve la excepción lanzada por ese bloque. Si no se lanza ninguna excepción, devuelve undef.

¡Atención! Si el bloque resulta en una excepción *no calificada* (por ejemplo, 0 o la cadena vacía), Test::Fatal se detendrá. Dado que cualquiera de estos casos indica un problema serio en el sistema bajo prueba, este comportamiento se considera una *funcionalidad*. Nota que este problema solo se conoce en perls antiguas antes de 5.14.

Debes tener cuidado si estás probando estas condiciones: envolver "exception { ...} en un bloque ok() no te dará el resultado que deseas, así que asegúrate de usar is() en su lugar. También puedes usar directamente el mecanismo de manejo de excepciones de Try::Tiny, el sistema de excepciones subyacente de Test::Fatal.

Nota que no se realiza ninguna prueba TAP. En otras palabras, no se emite una línea como "ok" o "not ok". Es tu responsabilidad usar el resto de "exception" en una prueba existente como "ok", "isa_ok", "is", etc. O podrías descartar usar "dies_ok" y "lives_ok", que ofrecen salida TAP.

"exception" no altera la pila de llamadas presentada al bloque llamado, por lo que si la excepción devuelta tiene una traza de pila, incluirá algunos frames entre el código que llama a "exception" y el código que lanza la excepción. Esto se considera una *funcionalidad* porque evita el mecanismo raro de "Sub::Uplevel".

¡Atención! Esta no es una buena idea:

sub exception_like(&$;$) {
    my ($code, $pattern, $name) = @_;
    like( &exception($code), $pattern, $name );
}
exception_like(sub { }, qr/foo/, 'foo aparece en la excepción');

Si el código en el "..." va a lanzar una traza de pila con los argumentos de cada subrutina en su pila de llamadas (por ejemplo, mediante "Carp::confess", el nombre del test, y "foo aparece en la excepción" se va a matchear por la regex. En su lugar, escribe:

like( exception { ... }, qr/foo/, 'foo aparece en la excepción' );

Si realmente quieres una rutina de prueba que muestre el nombre del test, envuelve los argumentos en un arrayref para ocultar el texto literal de la pila de llamadas:

sub exception_like(&$) {
    my ($code, $args) = @_;
    my ($pattern, $name) = @$args;
    like( &exception($code), $pattern, $name );
}
exception_like(sub { }, [ qr/foo/, 'foo aparece en la excepción' ] );

Para ayudar a evitar el problema donde el patrón se ve en la excepción debido a la pila de llamadas, $Carp::MaxArgNums se establece localmente en -1 cuando se llama al bloque de código. Si no quieres que así sea, restablécelo a cualquier valor que prefieras al principio del bloque de código. Claramente, esta solución no afecta todas las formas posibles en las que los argumentos de las subrutinas en la pila de llamadas puedan "contaminar" la prueba. El propósito aquí es prevenir algunas pasadas falsas de usuarios que no leyeron la documentación. Tu castigo por leerlo es que debes considerar si quieres hacer algo al respecto.

¡Atención: Una idea final errónea:

isnt( exception { ... }, undef, "¡mi código murió!");

Aunque esto prueba que tu código terminó, deberías probar que terminó por la razón correcta. Por ejemplo, si cometes un error inútil en el bloque, como usar el desreferenciador incorrecto, tu prueba pasará incluso si el código que se está probando no se ejecuta realmente. Si estás esperando una excepción inspeccionable con un identificador o clase, prueba eso. Si estás esperando una excepción de cadena, considera usar "like".

success

try {
  should_live;
} catch {
  fail("boo, morimos");
} success {
  pass("¡hurra, vivimos!");
};

"success", exportado solo por solicitud, es un helper de Try::Tiny con semántica idéntica a "finally", pero el cuerpo del bloque solo se ejecutará si el bloque "try" se ejecuta sin errores.

Aunque casi cualquier prueba de excepción se puede realizar con "exception", los bloques de prueba de success pueden ayudar a organizar pruebas complejas.

dies_ok

lives_ok

Exportadas solo por solicitud, estas dos rutinas ejecutan un bloque de código y proporcionan salida TAP indicando si se lanzó o no una excepción. Estas ofrecen una ruta de actualización fácil para reemplazar pruebas existentes basadas en "Test::Exception".

RJBS no sugiere usar esto salvo como una conveniencia mientras se portan pruebas a la rutina "exception" de Test::Fatal.

use Test::More tests => 2;
use Test::Fatal qw(dies_ok lives_ok);
dies_ok { die "Fallé" } 'código que falla';
lives_ok { return "Estoy vivo" } 'código que no falla';
