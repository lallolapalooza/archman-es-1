NOMBRE

Test2::Manual::Anatomy::EndToEnd - Visión general de Test2 desde la carga hasta el final.

DESCRIPCIÓN

Esta es una visión general de alto nivel de todo, desde la carga de Test2 hasta el final de un script de prueba.

¿QUÉ SUCEDE CUANDO CARGO LA API?

use Test2::API qw/context/
Se crea una instancia singleton de Test2::API::Instance.
No tienes acceso a esto, es un detalle de implementación.
Se definen varias funciones de API que utilizan la instancia singleton.
Puedes importar estas funciones o usarlas directamente.
¿Y luego qué?
Espera...

La API intencionalmente hace lo menos posible. En este punto, aún algo puede cambiar el formateador, cargar Test2::IPC, u otros efectos globales que deben hacerse antes de que se cree el primer Test2::API::Context. Una vez que se crea el primer Test2::API::Context, la API finalizará la inicialización.

Ver "¿QUÉ SUCEDE CUANDO ADQUIERO UN CONTEXTO?" para más información.

¿QUÉ SUCEDE CUANDO USO UNA HERRAMIENTA?

Esta sección cubre el flujo de trabajo básico que deben seguir todas las herramientas como ok().

sub ok($$) {
    my ($bool, $name) = @_;
    my $ctx = context();
    my $event = $ctx->send_event('Ok', pass => $bool, name => $name);
    ...
    $ctx->release;
    return $bool;
}
ok(1, "1 is true");
Se ejecuta una función de herramienta.
ok(1, "1 is true");
La herramienta adquiere un objeto de contexto.
my $ctx = context();

Ver "¿QUÉ SUCEDE CUANDO ADQUIERO UN CONTEXTO?" para más información.

La herramienta utiliza el objeto de contexto para crear, enviar y devolver eventos.
Ver "¿QUÉ SUCEDE CUANDO ENVÍO UN EVENTO?" para más información. 
my $event = $ctx->send_event('Ok', pass => $bool, name => $name);
Cuando termina, la herramienta DEBE liberar el contexto.
Ver "¿QUÉ SUCEDE CUANDO LIBERO UN CONTEXTO?" para más información. 
$ctx->release();
La herramienta devuelve un valor.
return $bool;

¿QUÉ SUCEDE CUANDO ADQUIERO UN CONTEXTO?

my $ctx = context();

Estas acciones pueden no ocurrir exactamente en este orden, pero eso es un detalle de implementación. Para los fines de este documento, se utiliza este orden para ayudar al lector a comprender el flujo.

$!, $@, $? y $^E se capturan y preservan.
Test2 se asegura de preservar los valores de $!, $@, $? y $^E para que las herramientas de prueba no modifiquen estas variables inesperadamente. Se capturan al principio para poder restaurarlas más tarde.
El estado de la API se cambia a 'loaded'.
El estado 'loaded' significa que las herramientas de prueba ya han comenzado a ejecutarse. Esto es importante ya que algunos complementos deben surtir efecto antes de que se ejecuten las pruebas. Este cambio de estado solo ocurre la primera vez que se adquiere un contexto y puede activar la ejecución de algunos hooks definidos por los complementos.
Se encuentra el hub actual.
Un contexto se adjunta al Test2::Hub actual. Si no hay un hub actual, se inicializará el hub raíz. Esto también inicializará la pila de hubs si es necesario.
Los hooks de adquisición de contexto se activan.
Es posible crear hooks globales o específicos del hub que se activan cada vez que se adquiere un contexto; estos hooks se activarán ahora. Estos hooks se activan incluso si ya existe un contexto.
Se encuentra cualquier contexto existente.
Si el hub actual ya tiene un contexto, se utilizará una copia de este en lugar de un contexto completamente nuevo. Esto es importante porque permite que las herramientas anidadas hereden el contexto utilizado por las herramientas padre.
Se mide la profundidad de la pila.
Test2 se asegura de detectar errores en la forma en que se utiliza el contexto. La profundidad de la pila se utiliza para lograr esto. Si hay un contexto existente, la profundidad se verificará con el que se encuentra aquí. Si el contexto antiguo tiene la misma profundidad de pila, o una menor, significa que una herramienta se está comportando de manera incorrecta y no ha limpiado el contexto cuando terminó, en cuyo caso el contexto antiguo se limpiará y se emitirá una advertencia.
Se crea un nuevo contexto (si no se encontró un contexto existente)
Si no hay un contexto existente, se creará uno nuevo utilizando los datos recopilados hasta el momento.
Los hooks de inicialización del contexto se activan (si no se encontró un contexto existente)
Si se creó un nuevo contexto, se activarán los hooks de creación de contexto.
$!, $@, $?, y $^E se restauran.
Nos aseguramos de que $!, $@, $?, y $^E no cambien en este punto para que los cambios que hicimos no afecten nada más. Esto se hace en caso de que algo dentro de la construcción del contexto haya cambiado accidentalmente estas variables.
Se devuelve el contexto.
Tienes un objeto de contexto nuevo y brillante, o una copia del contexto existente.

¿QUÉ SUCEDE CUANDO ENVÍO UN EVENTO?

my $event = $ctx->send_event('Ok', pass => $bool, name => $name);
Se carga el módulo Test2::Event::Ok.
El método send_event() cargará automáticamente cualquier paquete de Evento necesario. Normalmente, send_event() asumirá que el primer argumento es una clase de evento sin el prefijo "Test2::Event::", que añadirá por ti. Si quieres usar una clase de evento que está en un namespace diferente, puedes añadir un prefijo de "+" a la clase para indicar a la herramienta que estás proporcionando un nombre de clase completamente calificado: 
my $event = $ctx->send_event('+Fully::Qualified::Event', pass => $bool, name => $name);
Se crea una nueva instancia de Test2::Event::Ok.
El objeto de evento se instancia utilizando los parámetros proporcionados.
El objeto de evento se envía al hub.
El hub se encarga de todo a partir de aquí.
El hub procesa el evento a través de cualquier filtro.
Los filtros pueden modificar o eliminar eventos. Los filtros se ejecutan primero, antes de que el evento pueda modificar el estado global de la prueba.
El estado global de la prueba se actualiza para reflejar el evento.
Si el evento afecta al recuento de pruebas, este se incrementará. Si el evento causa un fallo, el recuento de fallos se incrementará. Hay algunas otras formas en que el estado global puede verse afectado.
El evento se envía al formateador.
Después de que el estado se modifica, el hub enviará el evento al formateador para su representación. Aquí es donde normalmente se produce el TAP.
El evento se envía a todos los oyentes.
Puede haber cualquier número de oyentes que tomen medidas cuando se procesan los eventos; esto ocurre ahora.

¿QUÉ SUCEDE CUANDO LIBERO UN CONTEXTO?

$ctx->release;
Se libera la copia del contexto actual.
Si tu herramienta está anidada dentro de otra, entonces liberar simplemente destruirá la copia del contexto, nada más sucederá.

NAME

Test2::Manual::Anatomy::EndToEnd - The anatomy of how Test2 executes

DESCRIPTION

This document details what happens behind the scenes when you run a Test2 test script.

WHAT HAPPENS WHEN I LOAD THE API?

use Test2::API;
The root hub is created.
A hub is a scope for tests. The root hub is the scope that contains all other scopes.
The root context is created.
A context is a container for all the data needed by a test tool. This includes things like the current line number, the plan for the tests, etc.
The API version is checked.
The API version is checked to ensure that the Test2 distribution you are using is compatible with the Test::Builder distribution you might also be using.
IPC is initialized (if enabled).
If IPC is enabled, then the necessary IPC machinery will be initialized.

WHAT HAPPENS WHEN I USE A TOOL?

my $got = pass();
The current context is acquired.
A tool will first attempt to acquire the current context. If no context exists, it will create one.
The line number is updated.
The line number is updated in the context to reflect the line number where the tool was called.
The event is generated.
An event is generated based on the tool that was called. For example, pass() generates a pass event.
The event is sent to the hub.
The event is sent to the current hub. The hub is responsible for processing the event.

WHAT HAPPENS WHEN I ACQUIRE A CONTEXT?

A new context is created if none exists.
If there is no current context, a new one will be created. This new context will be linked to the canonical context.
The context is linked to the canonical context.
This ensures that all contexts are eventually linked back to the root context.
The line number is recorded.
The line number where the context was acquired is recorded. This is used for reporting purposes.

WHAT HAPPENS WHEN I SEND AN EVENT?

The event is queued.
The event is added to a queue for processing. This allows for asynchronous processing of events.
The event is processed.
The event is processed by the current hub. This may involve executing hooks, sending events to other processes, etc.

WHAT HAPPENS WHEN I RELEASE A CONTEXT?

If this was the canonical context, it will actually release
When a context is created it is considered 'canon'. Any context obtained by a nested tool will be considered a child context linked to the canonical one. Releasing child contexts does not do anything of note (but is still required).
Release hooks are called
Release hooks are the main motivation behind making the release() method, and making it a required action on the part of test tools. These are hooks that we can have called when a tool is complete. This is how plugins like Test2::Plugin::DieOnFail are implemented. If we simply had a destructor call the hooks then we would be unable to write this plugin as a "die" inside of a destructor is useless.
The context is cleared
The main context data is cleared allowing the next tool to create a new context. This is important as the next tool very likely has a new line number.
$!, $@, $?, and $^E are restored
When a Test2 tool is complete it will restore $@, $!, $? and $^E to avoid action at a distance.

WHAT HAPPENS WHEN I USE done_testing()?

done_testing();
Any pending IPC events will be culled.
If IPC is turned on, a final culling will take place.
Follow-up hooks are run
The follow-up hooks are a way to run actions when a hub is complete. This is useful for adding cleanup tasks, or final tests to the end of a test.
The final plan event is generated and processed.
The final plan event will be produced using the current test count as the number of tests planned.
The current hub is finalized.
This will mark the hub is complete, and will not allow new events to be processed.

WHAT HAPPENS WHEN A TEST SCRIPT IS DONE?

Test2 has some behaviors it runs in an "END { ... }" block after tests are done running. This end block does some final checks to warn you if something went wrong. This end block also sets the exit value of the script.

API Versions are checked.
A warning will be produced if Test::Builder is loaded, but has a different version compared to Test2::API. This situation can happen if you downgrade to an older Test-Simple distribution, and is a bad situation.
Any remaining context objects are cleaned up.
If there are leftover context objects they will need to be cleaned up. A leftover context is never a good thing, and usually requires a warning. A leftover context could also be the result of an exception being thrown which terminates the script, Test2 is fairly good at noticing this and not warning in these cases as the warning would simply be noise.
Child processes are sent a 'waiting' event.
If IPC is active, a waiting event is sent to all child processes.
The script will wait for all child processes and/or threads to complete.
This happens only when IPC is loaded, but Test::Builder is not. This behavior is useful, but would break compatibility for legacy tests.
The hub stack is cleaned up.
All hubs are finalized starting from the top. Leftover hubs are usually a bad thing, so a warning is produced if any are found.
The root hub is finalized.
This step is a no-op if done_testing() was used. If needed this will mark the root hub as finished.
Exit callbacks are called.
This is a chance for plugins to modify the final exit value of the script.
The scripts exit value ($?) is set.
If the test encountered any failures this will be set to a non-zero value. If possible this will be set to the number of failures, or 255 if the number is larger than 255 (the max value allowed).
Broken module diagnostics
Test2 is aware of many modules which were broken by Test2's release. At this point the script will check if any known-broken modules were loaded, and warn you if they were.

Note: This only happens if there were test failures. No broken module warnings are produced on a success.
