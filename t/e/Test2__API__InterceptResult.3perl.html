NOMBRE

Test2::API::InterceptResult - Representación de una lista de eventos.

DESCRIPCIÓN

Esta clase representa una lista de eventos, normalmente obtenida usando intercept() de Test2::API.

Esta clase está pensada para personas que desean verificar los resultados de las herramientas de prueba que escriben.

Esta clase proporciona métodos para normalizar, resumir o mapear la lista de eventos. La salida de estas operaciones hace que verificar sus herramientas de prueba y los eventos que generan sea significativamente más fácil. En la mayoría de los casos, esto le evita la necesidad de una comprensión profunda del modelo de eventos/facetas.

SINOPSIS

Normalmente, obtienes una instancia de esta clase cuando usas intercept() de Test2::API.

use Test2::V0;
use Test2::API qw/intercept/;
my $events = intercept {
    ok(1, "pass");
    ok(0, "fail");
    todo "broken" => sub { ok(0, "fixme") };
    plan 3;
};
# Este es típicamente el constructo más útil
# squash_info() fusiona aserciones y diagnósticos que están asociados
#   (y devuelve una nueva instancia con las modificaciones)
# flatten() condensa los datos de las facetas en los detalles clave para cada evento
#   (y devuelve esas estructuras en un arrayref)
is(
    $events->squash_info->flatten(),
    [
        {
            causes_failure => 0,
            name => 'pass',
            pass => 1,
            trace_file => 'xxx.t',
            trace_line => 5,
        },
        {
            causes_failure => 1,
            name => 'fail',
            pass => 0,
            trace_file => 'xxx.t',
            trace_line => 6,
            # Puede haber más de un mensaje de diagnóstico, por lo que este
            # es siempre un array cuando está presente.
            diag => ["Failed test 'fail'\nat xxx.t line 6."],
        },
        {
            causes_failure => 0,
            name => 'fixme',
            pass => 0,
            trace_file => 'xxx.t',
            trace_line => 7,
            # Puede haber más de un mensaje de diagnóstico o razón de 'todo',
            # por lo que estos son siempre un array cuando están presentes.
            todo => ['broken'],
            # El mensaje de diagnóstico se convirtió en una nota ya que la aserción estaba
            # TODO
            note => ["Failed test 'fixme'\nat xxx.t line 7."],
        },
        {
            causes_failure => 0,
            plan => 3,
            trace_file => 'xxx.t',
            trace_line => 8,
        },
    ],
    "Los eventos aplanados se ven como esperamos"
);

Ver Test2::API::InterceptResult::Event para una descripción completa de lo que flatten() proporciona para cada evento.

MÉTODOS

Tenga en cuenta que ningún método modifica la instancia original a menos que se le solicite que lo haga.

CONSTRUCCIÓN

$events = Test2::API::InterceptResult->new(@EVENTS)
$events = Test2::API::InterceptResult->new_from_ref(\@EVENTS)
Estos crean una nueva instancia de Test2::API::InterceptResult a partir de los eventos dados.

En la primera forma se devuelve un nuevo arrayref "bendecido". En la forma 'new_from_ref', la referencia que usted pasa es directamente "bendecida".

Ambos lanzarán una excepción si se llaman en contexto nulo. Esto es principalmente importante para los métodos de "filtrado" que se enumeran a continuación, que normalmente devuelven una nueva instancia; lanzan una excepción en tales casos, ya que probablemente significa que alguien tenía la intención de filtrar el original en el lugar.

$clone = $events->clone()
Haz una copia de los eventos originales. Tenga en cuenta que esta es una copia profunda, toda la estructura se duplica. Esto utiliza "dclone" de Storable para lograr la copia profunda.

NORMALIZACIÓN

@events = $events->event_list
Esto devuelve todos los eventos en forma de lista.
$hub = $events->hub
Esto devuelve un nuevo objeto Test2::Hub que ha procesado todos los eventos contenidos en la instancia. Esto le da una forma sencilla de inspeccionar los cambios de estado que causan sus eventos.
$state = $events->state
Esto devuelve un resumen del estado de un hub después de procesar todos los eventos. 
{
    count        => 2,      # Número de aserciones realizadas
    failed       => 1,      # Número de fallos de prueba vistos
    is_passing   => 0,      # Booleano, verdadero si la prueba estaría pasando
                            # después de procesar los eventos.
    plan         => 2,      # Plan, ya sea un número, undef, 'SKIP', o 'NO PLAN'
    follows_plan => 1,      # Verdadero si hay un plan y se siguió.
                            # Falso si el plan y las aserciones no
                            # coincidieron, undef si no había plan en la
                            # lista de eventos.
    bailed_out   => undef,  # undef a menos que haya habido un 'bail-out' en los
                            # eventos en cuyo caso esta será una cadena
                            # explicando por qué hubo un 'bail-out', si no
                            # se dio razón, simplemente se establecerá a
                            # verdadero (1).
    skip_reason  => undef,  # Si hubo un 'skip_all', esto dará la
                            # razón.
}
$new = $events->upgrade
$events->upgrade(in_place => $BOOL)
Nota: Normalmente devuelve una nueva instancia, dejando la original sin cambios. Si la llama en contexto nulo, lanzará una excepción. Si desea modificar la original, debe pasar la opción "in_place => 1". Puede llamar a esto en contexto nulo cuando solicite modificarla en el lugar. La forma en el lugar devuelve la instancia que fue modificada para que pueda encadenar métodos.

Esto creará una copia de la lista donde todos los eventos se han convertido en instancias de Test2::API::InterceptResult::Event. Esto es extremadamente útil ya que Test2::API::InterceptResult::Event proporciona una interfaz mucho mejor para trabajar con eventos. Esto le permite evitar pensar en tipos de eventos heredados.

Esto también significa que sus pruebas contra la lista no son frágiles si la herramienta que está probando cambia aleatoriamente el tipo de eventos que genera (es decir, cambiar de Test2::Event::Ok a Test2::Event::Pass, ambos realizan aserciones y ambos se normalizarán a instancias de Test2::API::InterceptResult::Event idénticas (o lo suficientemente cercanas)).

Realmente casi siempre querrá esto, la única razón por la que no se hace automáticamente es para asegurarse de que la herramienta intercept() sea retrocompatible.

$new = $events->squash_info
$events->squash_info(in_place => $BOOL)
Nota: Normalmente devuelve una nueva instancia, dejando la original sin cambios. Si la llama en contexto nulo, lanzará una excepción. Si desea modificar la original, debe pasar la opción "in_place => 1". Puede llamar a esto en contexto nulo cuando solicite modificarla en el lugar. La forma en el lugar devuelve la instancia que fue modificada para que pueda encadenar métodos.

Nota: Todos los eventos en la nueva instancia o modificada serán convertidos a instancias de Test2::API::InterceptResult::Event. No hay forma de evitar esto, la operación de aplastamiento requiere la clase de evento mejorada.

Test::More y muchas otras herramientas heredadas enviarían notas, diagnósticos y aserciones como eventos separados. Un subtest en Test::More enviaría una nota con el nombre del subtest, la aserción del subtest y, finalmente, un evento de diagnóstico si el subtest fallaba. Este método normalizará las cosas aplastando la nota y el diagnóstico en el mismo evento que el subtest (esto es diferente de ponerlos dentro del subtest, que no es lo que sucede).

FILTRADO

Nota: Normalmente devuelven nuevas instancias, dejando las originales sin cambios. Si las llama en contexto nulo, lanzarán excepciones. Si desea modificar las originales, debe pasar la opción "in_place => 1". Puede llamar a estas en contexto nulo cuando solicite modificarlas en el lugar. Las formas en el lugar devuelven la instancia que fue modificada para que pueda encadenar métodos.

NOMBRE

Test2::API::InterceptResult - Un envoltorio para una lista de eventos

DESCRIPCIÓN

Este módulo es un envoltorio para una lista de eventos de Test2. No se supone que este módulo sea usado directamente. Más bien, los métodos que se exponen aquí son para ser usados por Test2::API::Intercept.

En este contexto, los métodos expuestos aquí son para acceder a los eventos que han sido interceptados.

in_place => $BOOL
Cuando es verdadero, el método modificará la instancia en el lugar en lugar de devolver una nueva instancia.
args => \@ARGS
Si deseas pasar parámetros al método de evento que se está utilizando para el filtrado, puedes hacerlo aquí.

MÉTODOS

$events->grep($CALL, %PARAMS)
Esto es esencialmente: 
Test2::API::InterceptResult->new(
    grep { $_->$CALL( @{$PARAMS{args}} ) } $self->event_list,
);

Nota: que $CALL se llama en una versión mejorada del evento, aunque los eventos devueltos serán los originales, no los mejorados.

$CALL puede ser el nombre de un método en Test2::API::InterceptResult::Event, o un coderef.

$events->asserts(%PARAMS)
Esto es esencialmente: 
$events->grep(has_assert => @{$PARAMS{args}})

Devuelve una nueva instancia que contiene solo los eventos que realizaron aserciones.

$events->subtests(%PARAMS)
Esto es esencialmente: 
$events->grep(has_subtest => @{$PARAMS{args}})

Devuelve una nueva instancia que contiene solo los eventos que tienen subpruebas.

$events->diags(%PARAMS)
Esto es esencialmente: 
$events->grep(has_diags => @{$PARAMS{args}})

Devuelve una nueva instancia que contiene solo los eventos que tienen diagnósticos.

$events->notes(%PARAMS)
Esto es esencialmente: 
$events->grep(has_notes => @{$PARAMS{args}})

Devuelve una nueva instancia que contiene solo los eventos que tienen notas.

$events->errors(%PARAMS)
Nota: Los errores NO son aserciones fallidas. Las aserciones fallidas son algo diferente.

Esto es esencialmente:

$events->grep(has_errors => @{$PARAMS{args}})

Devuelve una nueva instancia que contiene solo los eventos que tienen errores.

$events->plans(%PARAMS)
Esto es esencialmente: 
$events->grep(has_plan => @{$PARAMS{args}})

Devuelve una nueva instancia que contiene solo los eventos que establecieron el plan.

$events->causes_fail(%PARAMS)
$events->causes_failure(%PARAMS)
Estos son esencialmente: 
$events->grep(causes_fail    => @{$PARAMS{args}})
$events->grep(causes_failure => @{$PARAMS{args}})

Nota: causes_fail() y causes_failure() son alias mutuos en los eventos, por lo que estos métodos son efectivamente alias aquí también.

Devuelve una nueva instancia que contiene solo los eventos que causan fallo.

MAPEO

Estos métodos **SIEMPRE** devuelven un arrayref.

Nota: Ningún método en Test2::API::InterceptResult::Event modifica el evento de ninguna manera.

Notas importantes sobre eventos:

Test2::API::InterceptResult::Event se diseñó a medida para ser utilizado en listas de eventos. La mayoría de los métodos que no son aplicables a un evento dado devolverán una lista vacía, por lo que normalmente no necesita preocuparse por valores "undef" no deseados o excepciones que se lancen. Mapear sobre métodos de eventos es un uso previsto, por lo que funciona bien para producir listas.

Excepciones a la regla:

Algunos métodos como "causes_fail" siempre devuelven un booleano verdadero o falso para todos los eventos. Cualquier método prefijado con "the_" transmite la intención de que el evento debe tener exactamente 1 de algo, por lo que lanzarán una excepción cuando esa condición no se cumpla.

$arrayref = $events->map($CALL, %PARAMS)
Esto es esencialmente: 
[ map { $_->$CALL(@{ $PARAMS{args} }) } $events->upgrade->event_list ];

$CALL puede ser el nombre de un método en Test2::API::InterceptResult::Event, o un coderef.

$arrayref = $events->flatten(%PARAMS)
