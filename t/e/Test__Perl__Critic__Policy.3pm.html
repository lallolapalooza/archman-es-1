NOMBRE

Test::Perl::Critic::Policy - Un framework para probar tus Policies personalizadas

SINOPSIS

use Test::Perl::Critic::Policy qw< all_policies_ok >;
# Asumiendo que los archivos .run están dentro del directorio 't'...
all_policies_ok()
# O si tus archivos .run están en un directorio diferente...
all_policies_ok( '-test-directory' => 'run' );
# Y si solo quieres ejecutar pruebas para algunas políticas...
all_policies_ok( -policies => ['Some::Policy', 'Another::Policy'] );
# Si quieres que tu programa de prueba acepte nombres cortos de Policy como
# parámetros de línea de comandos...
#
# Puedes entonces probar una sola política ejecutando
# "perl -Ilib t/policy-test.t My::Policy".
my %args = @ARGV ? ( -policies => [ @ARGV ] ) : ();
all_policies_ok(%args);

DESCRIPCIÓN

Este módulo proporciona un framework para probar funcionalmente tus módulos customizados de Perl::Critic::Policy. Las pruebas de políticas usualmente implican alimentarla con una cadena de código Perl y verificar su comportamiento. En los viejos tiempos, esas cadenas de código Perl se mezclaban directamente en el script de prueba. Eso apestaba.

SUBRUTINAS IMPORTABLES

all_policies_ok('-test-directory' => $path, -policies => \@policy_names)
Carga todos los archivos *.run debajo del "-test-directory" y ejecuta las pruebas. Si "-test-directory" no se especifica, por defecto es t/. "-policies" es una referencia opcional a un array de nombres de Políticas acortados. Si se especifica "-policies", solo se ejecutarán las pruebas para las Políticas que coincidan con uno de los "m/$POLICY_NAME/imx".

CREACIÓN DE LOS ARCHIVOS *.run

Probar una política sigue un patrón muy simple:

* Nombre de la Política
    * Nombre del subtest
    * Parámetros opcionales
    * Número de fallos esperados
    * Excepción opcional esperada
    * Nombre de archivo opcional para el código

Cada uno de los subtests para una política se recopila en un único archivo .run, con propiedades de prueba como comentarios delante de cada bloque de código que describe cómo esperamos que Perl::Critic reaccione al código. Por ejemplo, digamos que tienes una política llamada Variables::ProhibitVowels:

(En el archivo t/Variables/ProhibitVowels.run)
## name Basics
## failures 1
## cut
my $vrbl_nm = 'foo';    # Buen nombre, sin vocales
my $wango = 12;         # Mal nombre, pronunciable
## name Sometimes Y
## failures 1
## cut
my $yllw = 0;       # "y" no es una vocal aquí
my $rhythm = 12;    # Pero aquí sí lo es

Estos se llaman "subtests", y se muestran dos arriba. La belleza de incorporar múltiples subtests en un archivo es que el .run es en sí mismo un archivo Perl (mayormente) válido, y no está oculto en un HEREDOC, por lo que la codificación de colores de tu editor aún funciona, y es mucho más fácil trabajar con el código y el POD.

Si necesitas pasar algún parámetro de configuración para tu subtest, hazlo así:

## parms { allow_y => '0' }

Ten en cuenta que todos los valores en este hash deben ser cadenas de texto porque eso es lo que Perl::Critic te entregará desde un .perlcriticrc.

Si es un subtest TODO (probablemente debido a alguna esquina extraña de PPI que ejercimos y que Adam está arreglando, ¿verdad?), entonces haz una entrada "##TODO".

## TODO Debería pasar cuando salga PPI 1.xxx

Si se espera que el código active una excepción en la política, indícalo así:

## error 1

Si quieres probar el mensaje de error, márcalo con "/.../" para indicar una prueba like():

## error /No se puede cargar Foo::Bar/

Si el nombre del archivo del código es importante para la política que estás probando, puedes indicarlo así para que se use "fcritique" (ver "fcritique" para más detalles):

## filename lib/Foo/Bar.pm

El valor de "parms" se "eval"uará y se pasará a pcritique(), así que ten cuidado.

En general, un documento de subtest va desde el "## cut" que lo inicia hasta el siguiente "## name" o el final del archivo. En circunstancias muy raras, puede que necesites terminar el documento de prueba antes. Un segundo "## cut" hará esto. La única necesidad conocida para esto está en t/Miscellanea/RequireRcsKeywords.run, donde se utiliza para evitar que las palabras clave RCS en el pie de página del archivo produzcan falsos positivos o negativos en la última prueba.

Ten en cuenta que en ninguna parte del archivo .run especificas la política que estás probando. Eso está implícito en el nombre del archivo.
