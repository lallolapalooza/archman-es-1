NOMBRE

Test::Inter - framework para scripts de prueba interactivos más legibles

DESCRIPCIÓN

Este es otro framework para escribir scripts de prueba. Gran parte de la sintaxis está inspirada libremente en Test::More, y Test::Inter tiene la mayor parte de su funcionalidad, pero no es un reemplazo directo.

Test::More (y otros frameworks de prueba existentes) sufren de dos debilidades, ambas me han impedido usarlos:

Ninguno ofrece la capacidad de acceder a pruebas específicas de una manera razonablemente interactiva, principalmente con fines de depuración.
Ninguno ofrece la capacidad de escribir las pruebas en el formato que haga que las pruebas sean más legibles.

La forma en que escribo y uso scripts de prueba, los módulos Test::* existentes no son tan útiles como podrían ser.

Los scripts de prueba escritos con Test::More funcionan bien cuando se ejecutan como parte del conjunto de pruebas, pero depurar una prueba individual requiere pasos adicionales, y las pruebas en sí mismas no son tan legibles como deberían ser.

EJECUCIÓN INTERACTIVA

Un requisito que tengo de un framework de prueba es la capacidad de interactuar con él.

Hago la mayor parte de mi depuración utilizando scripts de prueba. Cuando encuentro un error, escribo un caso de prueba para él (típicamente agregándolo a un script de prueba existente) y luego lo depuro usando el script de prueba. Luego, dejo la prueba allí para asegurar que el error no regrese (con suerte).

Dado que utilizo scripts de prueba de una manera muy interactiva (a menudo en el depurador), quiero poder hacer lo siguiente trivialmente:

Acceso fácil a una prueba o pruebas específicas
Me gustaría poder ejecutar solo una prueba individual, o un subconjunto de pruebas.
Establecer puntos de interrupción fácilmente en el depurador
Establecer un punto de interrupción en el depurador para ejecutar hasta el inicio de la N-ésima prueba es una de las tareas más comunes que quiero hacer cuando depuro una prueba fallida.

Para ilustrar el primer punto, en Test::More, una serie de pruebas se pueden especificar en un script de prueba como se muestra en el siguiente ejemplo (se agregan números de línea para mayor comodidad):

...
100:  # prueba 1
101:  $result = func("manzanas","canastas");
102:  is($result, "suficiente");
103:
104:  # prueba 2
105:  $result = func("pomelos","toneladas");
106:  is($result, "suficiente");
107:
108:  # prueba 3
109:  $result = func("naranjas","cargamentos");
110:  is($result, "insuficiente");
111:
112:  # pruebas 4-6
113:  foreach my $arg (qw(peras ciruelas piña)) {
114:    $result = func($arg,"cajas");
115:    is($result, "suficiente");
116:  }
...

Supongamos que ejecutó el conjunto de pruebas y la prueba 3 falló. Para depurarla, tiene que abrir el script de prueba, encontrar la tercera prueba y establecer el punto de interrupción apropiado. En este caso, querrá detenerse en la línea 109.

Ninguno de estos pasos es imposible, por supuesto, pero llevará algún tiempo hacerlo bien. Se vuelve más difícil cuando hay muchas pruebas (imagine que quiere probar la prueba 117 en lugar de la prueba 3) o cuando las pruebas están envueltas en bucles, incrustadas en subrutinas u otras situaciones similares.

Como ejemplo, ¿qué pasa si la quinta prueba falla en el ejemplo anterior? Ahora, el punto de interrupción será condicional, por lo que debe averiguar no solo la línea, sino también la condición en el estado apropiado durante esa prueba. En este caso, necesita detenerse en la línea 114 cuando $arg sea 'ciruelas'.

¿No sería mucho mejor establecer un punto de interrupción en func cuando se alcance la N-ésima prueba? Con Test::Inter, puede hacerlo.

Entonces, para el script anterior, los comandos del depurador que usaría para depurar la tercera prueba son:

Test::More :   b 109
Test::Inter:   b func ($::TI_NUM==3)

y la quinta prueba son:

Test::More :   b 114  ($arg eq 'ciruelas')
Test::Inter:   b func ($::TI_NUM==5)

También sería bueno poder omitir las dos primeras pruebas... tal vez tarden mucho en ejecutarse, y quiero empezar directamente con la prueba 3. También puede hacer esto fácilmente configurando la variable $::TI_START.

Hay algunas otras variables que se pueden usar para especificar qué prueba o pruebas ejecutar, descritas en la sección "VARIABLES DE TEST::INTER" a continuación.

La otra cosa que quiero hacer cuando ejecuto los scripts de prueba de forma interactiva es ver más información que ayude a depurar una prueba fallida.

Esto se puede controlar con variables como TI_QUIET, TI_MODE y TI_WIDTH descritas a continuación en la sección "VARIABLES DE TEST::INTER".

PRUEBAS LEGIBLES

La otra característica que quería en un conjunto de pruebas es la capacidad de definir las pruebas en un formato que sea natural y legible PARA LAS PRUEBAS. En casi todos los casos, es mejor pensar en un script de prueba como que consta de dos partes separadas: una parte de script y una parte de prueba.

La parte del script de un script de prueba es la parte menos importante. Suele ser bastante trivial, rara vez necesita ser cambiada y no es el enfoque del script de prueba.

La parte de las pruebas del script ES la parte importante, y estas deben expresarse en un formato que sea natural para ellas, fácil de mantener, fácil de leer y fácil de modificar, y ninguna de estas debería implicar modificar la parte del script en general. Debido a que el contenido de las pruebas es la parte importante del script, el énfasis debe estar en hacerlas más legibles, incluso a expensas de la parte del script. Como regla general, si la parte del script del script de prueba oscurece las pruebas de alguna manera, ¡no está escrita correctamente!

La solución a esto se entiende bien y es común a muchos otros sistemas donde se mezclan dos "lenguajes". La tarea de especificar correctamente tanto las pruebas como el script de prueba es prácticamente idéntica a la tarea de crear un script PHP que consista en una mezcla de PHP y HTML, o la tarea de crear un archivo de plantilla utilizando algún sistema de plantillas donde el archivo consista en una mezcla de texto a mostrar y comandos de plantillas. En cada uno de estos casos se entiende bien que cuanto más se entrelazan los dos "lenguajes", menos legibles son ambos y más difícil es mantenerlos. Cuanto más puedas separarlos, más fáciles serán de leer y mantener.

Siempre que sea posible, quiero que las pruebas se escriban en algún tipo de formato de texto que se pueda ver y modificar fácilmente (generalmente como una tabla simple) sin comandos de Perl intercalados. Quiero la libertad de definir las pruebas en una sección (una cadena larga, la sección DATA o incluso en un archivo separado) que sea fácilmente legible. Esto puede introducir la necesidad de analizarla, pero hace que sea significativamente más fácil mantener las pruebas.

Esta flexibilidad hace que sea mucho más fácil leer las pruebas (en contraposición al script), que es el contenido fundamental de un script de prueba.

Mirando nuevamente el script de prueba de ejemplo, puede ver que hay demasiado Perl intercalado con las pruebas.

Es difícil leer las pruebas individualmente en este script porque hay demasiado código Perl entre ellas, y es prácticamente imposible verlas en su conjunto.

Es cierto que, al observar este ejemplo en particular, es muy simple... pero el script NO es el contenido que te interesa (y ten en cuenta que muchos scripts de prueba no son ni de lejos tan simples). El contenido REAL de este script son las pruebas, que consisten en los argumentos de la función y el resultado esperado. Aunque no es imposible ver cada uno de ellos en el script anterior, no está en un formato que favorezca el estudio de las pruebas, y especialmente no para examinar la lista de pruebas en su conjunto.

Ahora, mire una forma alternativa de especificar las pruebas utilizando este módulo:

$tests = "
  manzanas     canastas   => suficiente
  pomelos      toneladas  => suficiente
  naranjas     cargamentos => insuficiente
  peras        cajas     => suficiente
  ciruelas     cajas     => suficiente
  piña         cajas     => suficiente
";
$o->tests(tests => $tests,
          func  => \&func);

Aquí, es fácil ver la lista de pruebas, y agregar pruebas adicionales es muy sencillo.

CREACIÓN DE UNA PRUEBA

Este módulo admite una serie de métodos para definir pruebas, por lo que puede utilizar el que sea más conveniente (incluidos métodos que son idénticos a Test::More si esa es realmente la mejor opción).

Cada prueba puede tener varias piezas de información:

Una

MÉTODOS BASE

new
$o = new Test::Inter [$name] [%options];

Esto crea un nuevo framework de prueba. Hay varias opciones que pueden usarse para especificar qué pruebas se ejecutan, cómo se ejecutan y qué salida se genera.

El script de prueba completo puede nombrarse pasando en $name.

Todas las opciones pueden establecerse de cuatro maneras diferentes.

Primero, puedes pasar un hash de CLAVE = VALOR > en el método new. Así, para establecer la opción start, el hash %options) contendría:

start => VALOR

Segundo, puedes establecer una variable de entorno. Esto sobrescribirá cualquier valor pasado en el primer método. La variable de entorno se llama TI_XXX, donde XXX es la opción completamente en mayúsculas. Así:

$ENV{TI_START} = VALOR

La tercera forma, que sobrescribe las dos anteriores, es establecer una variable global. También se llama TI_XXX en el espacio de nombres principal, así para establecerla, configura:

$::TI_START = VALOR

La última forma es llamar a uno de los siguientes métodos, que sobrescribirán todos los demás métodos.

Cada una de las opciones permitidas se describe a continuación en los siguientes métodos base:

Devuelve la versión del módulo.

encoding
$o->encoding($encoding);

$encoding es cualquier valor que pueda pasarse como codificación a la función Encode::decode de Perl.

Úsala si tus cadenas de prueba contienen caracteres en otras codificaciones.

start
$o = new Test::Inter 'start' => $N;
$o->start($N)

Para definir qué prueba quieres comenzar, establece la opción start como se describe en el método new.

Cuando se define la prueba start, las pruebas con número menor que N se ignoran por completo. Si las pruebas se están ejecutando en modo silencioso (ver el método quiet), no se imprime nada para estas pruebas. De lo contrario, se imprime un mensaje de salto.

Una clase de pruebas aún se ejecuta. Las pruebas que se ejecutan con require_ok o use_ok (para probar la carga de módulos) aún se ejecutan.

Si no se usa ningún valor (o un valor de 0), las pruebas se ejecutan desde la primera.

end
$o = new Test::Inter 'end' => $M;
$o->end($M);

Para definir qué prueba quieres finalizar, establece la opción end como se describe en el método new.

Cuando se define la prueba end, las pruebas con número mayor que M se ignoran por completo. Si las pruebas se están ejecutando en modo silencioso (ver el método quiet), no se imprime nada para estas pruebas. De lo contrario, se imprime un mensaje de salto.

Si no se especifica ningún valor, se usa por defecto 0 (lo que significa que todas las pruebas restantes se ejecutan).

testnum
$o = new Test::Inter 'testnum' => $N;
$o->testnum($N);

Para ejecutar solo una prueba, establece la opción testnum como se describe en el método new.

Es equivalente a establecer tanto la prueba start como la end en $N).

plan
done_testing
$o = new Test::Inter 'plan' => $N;
$o->plan($n);
$o->done_testing();
$o->done_testing($n);

La API TAP (el lenguaje utilizado para ejecutar una secuencia de pruebas y ver cuáles fallaron y cuáles pasaron) requiere una declaración del número de pruebas esperadas a ejecutar.

Esta declaración puede aparecer al inicio del archivo de prueba, o al final.

Si sabes de antemano cuántas pruebas deberían ejecutarse en el script de prueba, puedes establecer la opción plan como se describe en el método new con el número de pruebas.

Si sabes cuántas pruebas deberán ejecutarse al final del script de prueba, puedes pasar un número entero no cero al método done_testing.

Frecuentemente, no te importa cuántas pruebas hay en el script (especialmente si se añaden pruebas nuevas regularmente). En este caso, aún necesitas incluir una declaración que diga que el número de pruebas esperadas es el número de pruebas que se ejecutaron. Para hacer esto, llama al método done_testing sin argumentos.

NOTA: si se usa el método plan, debe usarse antes de ejecutar cualquier prueba (incluyendo aquellas que prueban la carga de módulos). Si se usa el método done_testing, debe llamarse después de que todas las pruebas hayan sido ejecutadas. Debes especificar un plan o usar una declaración done_testing, pero no ambos.

No es estrictamente necesario establecer un plan si el script se ejecuta de forma interactiva, por lo que si por alguna razón este módulo se usa para scripts de prueba que no son parte de una suite de prueba estándar de Perl, los comandos plan y done_testing son opcionales. De hecho, el script se ejecutará correctamente sin ellos... pero un instalador de Perl reportará un error en la suite de prueba.

abort
$o = new Test::Inter 'abort' => 0/1/2;
$o->abort(0/1/2);

Para definir cómo se trata un fallo, establece la opción abort como se describe en el método new. La opción abort puede tomar un valor de 0, 1 o 2.

Si se establece a 1, el script de prueba se ejecutará sin modificaciones hasta que una prueba falle. En ese punto, todas las pruebas restantes se dejarán de ejecutar. Con un valor de 2, el script se ejecutará hasta que una prueba falle y luego se detendrá con un código de error 1. Con un valor de 0, los fallos de prueba se informarán, pero el script continuará.

En ambos casos, las pruebas todo no activarán el comportamiento de aborto.

quiet
$o = new Test::Inter 'quiet' => 0/1/2;
$o->quiet(0/1/2);

Para definir cómo se informan los fallos, establece la opción quiet como se describe en el método new. La opción quiet puede tomar un valor de 0, 1 o 2.

Si se establece a 0 (por defecto), se imprimirá toda la información. Si se establece a 1, se imprimirá información opcional que no se mostrará. Si se establece a 2, se imprimirá información opcional que no se mostrará.

mode
$o = new Test::Inter 'mode' => MODE;
$o->mode(MODE);

Los scripts de Test::Inter pueden ejecutarse en modo interactivo o como parte de una suite de pruebas con diferentes comportamientos. Para seleccionar el modo, establece la opción mode como se describe en el método new. La opción mode puede tomar un valor de 'inter' o 'test'.

Cuando se ejecuta en modo de prueba, se imprimen los resultados usando la sintaxis TAP (es decir, 'ok 1', 'not ok 3', etc.).

Cuando se ejecuta en modo interactivo, se imprimen los resultados en un formato más legible para humanos.

width
$o = new Test::Inter 'width' => WIDTH;
$o->width(WIDTH);

La opción width puede establecerse como se describe en el método new.

WIDTH es el ancho de la terminal (para imprimir información sobre las pruebas que fallaron). El valor por defecto es 80, pero puede establecerse a cualquier ancho (y las líneas más largas se truncan). Si WIDTH se establece a 0, las líneas no se truncan.

use_lib
$o = new Test::Inter 'use_lib' => VALOR;
$o->use_lib(VALOR);
$o->use_lib();

Por defecto, la librería incluida en la distribución del módulo se agregará a la ruta de búsqueda de módulos, por lo que una línea 'use MODULE' debería encontrar la versión almacenada en este módulo.

Si se establece VALOR a 'off', la ruta de búsqueda no se modifica automáticamente.

Puedes añadir la ruta de la librería más tarde llamando:

$o->use_lib('on');
$o->use_lib();

Nota: ambas llamadas deben usarse. La primera establece la opción, la segunda modifica realmente la ruta de búsqueda.
