NOMBRE

Template::Manual::Views - Vistas de Template Toolkit (experimental)

Descripción general

Una vista es efectivamente una colección de plantillas y/o definiciones de variables que pueden ser pasadas como una unidad autocontenida. Esto representa una interfaz o estilo de presentación particular para otros objetos o elementos de datos.

Puedes usar vistas para implementar "skins" personalizados para una aplicación o conjunto de contenido. Puedes usarlas para ayudar a simplificar la presentación de objetos o tipos de datos comunes. Incluso puedes usarlas para automatizar la presentación de estructuras de datos complejas como las generadas en un árbol de "XML::DOM" o similar. Dejas que un iterador haga el recorrido, y la vista se encarga de la presentación. Voilà - tienes un recorrido independiente de la vista, tímido ante la estructura, usando plantillas.

En general, las vistas pueden usarse de varias maneras diferentes para lograr varios objetivos. Resuelven elegantemente algunos problemas que de otra manera serían difíciles o complicados, y facilitan cosas que antes eran difíciles.

Por el momento, todavía son muy experimentales. La sintaxis de las directivas y la API subyacente probablemente cambiarán considerablemente en la próxima versión o dos. Por favor, ten mucho cuidado al construir tus soluciones de comercio electrónico de millones de dólares basándote en esta característica.

Vistas como Coleccionadores/Proveedores de Plantillas

La directiva "VIEW" inicia una definición de vista e incluye un nombre por el cual la vista puede ser referenciada. La definición de la vista continúa hasta la directiva "END" correspondiente.

[% VIEW mi_vista %]
   ...
[% END %]

El primer rol de una vista es actuar como un colector y proveedor de plantillas. El método include() puede ser llamado en una vista para hacer efectivamente lo mismo que la directiva "INCLUDE". El nombre de la plantilla se pasa como primer argumento, seguido de cualquier definición de variable local para la plantilla.

[% mi_vista.include('encabezado', titulo='El Título') %]
#   equivalente a
[% INCLUDE encabezado  titulo='El Título' %]

Las vistas aceptan una serie de opciones de configuración que pueden ser utilizadas para controlar diferentes aspectos de su comportamiento. Las opciones '"prefix"' y '"suffix"' pueden ser especificadas para añadir un prefijo y/o sufijo fijo al nombre de cada plantilla.

[% VIEW mi_vista
     prefix = 'mi/'
     suffix = '.tt2' ;
   END
%]

Ahora la llamada

[% mi_vista.include('encabezado', titulo='El Título') %]

es equivalente a

[% INCLUDE mi/encabezado.tt2  titulo='El Título' %]

Las vistas proporcionan un método "AUTOLOAD" que mapea nombres de métodos al método include(). Por lo tanto, lo siguiente es equivalente:

[% mi_vista.include('encabezado', titulo='Hola Mundo') %]
[% mi_vista.include_encabezado(titulo='Hola Mundo') %]
[% mi_vista.encabezado(titulo='Hola Mundo') %]

Definiciones locales de BLOCK

Una definición de "VIEW" puede incluir definiciones de "BLOCK" que permanecen locales a la vista. Una solicitud para una plantilla particular devolverá un "BLOCK", si está definido, con preferencia a cualquier otra plantilla del mismo nombre.

[% BLOCK foo %]
   bloque foo público
[% END %]
[% VIEW simple %]
   [% BLOCK foo %]
   bloque foo simple
   [% END %]
[% END %]
[% VIEW elegante %]
   [% BLOCK foo %]
   bloque foo elegante
   [% END %]
[% END %]
[% INCLUDE foo %]       # bloque foo público
[% simple.foo %]         # bloque foo simple
[% elegante.foo %]         # bloque foo elegante

Además de las definiciones de "BLOCK", una "VIEW" puede contener cualquier otra directiva de plantilla. El bloque completo de definición de "VIEW" se procesa para inicializar la vista, pero no se genera ninguna salida (esto puede cambiar pronto - y guardarse como elemento de '"output"', accesible posteriormente como "[% vista.output %]"). Sin embargo, las directivas que tienen efectos secundarios, como las que actualizan una variable, tendrán consecuencias notables.

Preservar el estado de variables dentro de las Vistas

Las vistas también pueden ser usadas para guardar los valores de cualquier variable existente, o para crear nuevas en el punto en que se define la vista. A diferencia de los metadatos simples de plantilla ("META") que solo pueden contener valores de cadena estáticos, el bloque de inicialización de la vista puede contener cualquier directiva de plantilla y generar cualquier tipo de salida y/o elementos de datos dinámicos.

[% VIEW mi_sitio_web %]
   [% vista.titulo   = titulo or 'Mi Sitio Web Genial' %]
   [% vista.autor  = "$abw.nombre, $abw.email" %]
   [% vista.barra_lateral = INCLUDE mi/barra_lateral.tt2 %]
[% END %]

Nota que los elementos de datos adicionales pueden ser especificados como argumentos a la directiva "VIEW". Cualquier cosa que no parezca un parámetro de configuración se asume que es un elemento de datos. Esto puede ser un poco peligroso, por supuesto, porque nunca se sabe cuándo podría añadirse un nuevo elemento de configuración que interfiera con tus datos.

[% VIEW mi_sitio_web
        # opciones de configuración
        prefix = 'mi/'
        # datos varios
        titulo   = titulo or 'Mi Sitio Web Genial'
        autor  = "$abw.nombre, $abw.email"
        barra_lateral = INCLUDE mi/barra_lateral.tt2
%]
   ...
[% END %]

Fuera de la definición de la vista puedes acceder a las variables de la vista como, por ejemplo:

[% mi_sitio_web.titulo %]

Una característica importante es la equivalencia de variables simples y plantillas. Puedes implementar el elemento de vista '"titulo"' como una variable simple, una plantilla definida en un archivo externo, posiblemente con un prefijo/sufijo añadido automáticamente, o como una definición local de "BLOCK" dentro de la definición "[% VIEW %] ... [% END %]". Si usas la sintaxis anterior, la vista hará Lo Correcto para devolver la salida apropiada.

Al final ("END") de la definición de "VIEW", la vista se "sella" para evitar que actualices accidentalmente cualquier valor de variable. Si intentas cambiar el valor de una variable después del "END" del bloque de definición de "VIEW", se lanzará un error de "view".

[% TRY;
     mi_sitio_web.titulo = 'Nuevo Título';
   CATCH;
     error;
   END
%]

El error anterior se informará como:

error de vista - no se puede actualizar elemento en vista sellada: título

Lo mismo es cierto si pasas un parámetro a una variable de vista. Esto se interpreta como un intento de actualizar la variable y generará la misma advertencia.

[% mi_sitio_web.titulo('Nuevo Título') %]    # ¡error de vista!

Puedes establecer el parámetro "silent" para que la vista ignore estos parámetros y simplemente devuelva el valor de la variable.

[% VIEW mi_sitio_web
        silent = 1
        titulo  = titulo or 'Mi Sitio Web Genial'
        # ... ;
   END
%]
[% mi_sitio_web.titulo('Bla Bla') %]   # Mi Sitio Web Genial

Alternativamente, puedes especificar que una vista no esté sellada, permitiendo que las variables existentes sean actualizadas y se definan nuevas variables.

[% VIEW mi_sitio_web
        sealed = 0
        titulo  = titulo or 'Mi Sitio Web Genial'
        # ... ;
   END
%]
[% mi_sitio_web.titulo('Bla Bla') %]   # Bla Bla
[% mi_sitio_web.titulo %]                # Bla Bla

Herencia, Delegación y Reutilización

Las vistas pueden ser heredadas de vistas definidas previamente mediante el uso del parámetro "base". Este ejemplo muestra cómo se define una vista base que aplica un prefijo "view/default/" a todos los nombres de plantilla.

[% VIEW mi.vista.default
        prefix = 'view/default/';
   END
%]

Así, la directiva:

[% mi.vista.default.encabezado(titulo='Hola Mundo') %]

es ahora equivalente a:

[% INCLUDE view/default/encabezado titulo='Hola Mundo' %]

VIEW DIRECTIVE

The VIEW directive allows you to define a view which acts as a template repository and also as a proxy for other views. This is particularly useful for creating complex templates and for managing inheritance and delegation.

A view is defined using the VIEW directive, and a block of code which defines the view's behaviour:

[% VIEW <name>
      [ PARAM list ]
   END
%]
   ... view definition code ...
[% END %]

The <name> is a reference to the view. This can be any valid Template Toolkit variable name. The view can be referred to by this name later in the template. If the name is prefixed with a package name, e.g. My::View::Fancy, then the view will be treated as a class and Perl's standard class loading mechanisms will be used to load the view.

The optional PARAM list can contain one or more parameters to be passed to the view's constructor when it is defined. These are typically used to specify configuration options.

Inheritance and Delegation

A key feature of views is the ability to inherit from or delegate to other views. This is achieved using the base parameter within the view definition.

When a view is defined with a base parameter, it inherits all the templates and variables from the specified base view. This allows for a hierarchical structure of views, where more specific views can extend or override the behaviour of more general ones.

For example, you could define a default view:

[% VIEW my.view.default
        prefix = 'view/default/';
   END
%]
[% VIEW my.view.fancy
        base   = my.view.default
        prefix = 'view/fancy/';
   END
%]

Now the directive:


[% my.view.fancy.header(title='Hello World') %]


will resolve to:


[% INCLUDE view/fancy/header title='Hello World' %]


or if that doesn't exist, it will be handled by the base view
    as:


[% INCLUDE view/default/header title='Hello World' %]


When a parent view is specified via the
    "base" parameter, the delegation of a view
    to its parent for fetching templates and accessing user defined variables is
    automatic. You can also implement your own inheritance, delegation or other
    reuse patterns by explicitly delegating to other views.


[% BLOCK foo %]
   public foo block
[% END %]
[% VIEW plain %]
   [% BLOCK foo %]
   <plain>[% PROCESS foo %]</plain>
   [% END %]
[% END %]
[% VIEW fancy %]
   [% BLOCK foo %]
   [% plain.foo | replace('plain', 'fancy') %]
   [% END %]
[% END %]
[% plain.foo %]     # <plain>public foo block</plain>
[% fancy.foo %]     # <fancy>public foo block</fancy>


Note that the regular
    "INCLUDE/PROCESS/WRAPPER" directives work
    entirely independently of views and will always get the original, unaltered
    template name rather than any local per-view definition.

Self-Reference

A reference to the view object under definition is available with the "VIEW ... END" block by its specified name and also by the special name '"view"' (similar to the "my $self = shift;" in a Perl method or the '"this"' pointer in C++, etc). The view is initially unsealed allowing any data items to be defined and updated within the "VIEW ... END" block. The view is automatically sealed at the end of the definition block, preventing any view data from being subsequently changed.

(NOTE: sealing should be optional. As well as sealing a view to prevent updates ("SEALED"), it should be possible to set an option in the view to allow external contexts to update existing variables ("UPDATE") or even create totally new view variables ("CREATE")).

[% VIEW fancy %]
   [% fancy.title  = 'My Fancy Title' %]
   [% fancy.author = 'Frank Open' %]
   [% fancy.col    = { bg => '#ffffff', bar => '#a0a0ff' } %]
[% END %]

or

[% VIEW fancy %]
   [% view.title  = 'My Fancy Title' %]
   [% view.author = 'Frank Open' %]
   [% view.col    = { bg => '#ffffff', bar => '#a0a0ff' } %]
[% END %]

It makes no real difference in this case if you refer to the view by its name, '"fancy"', or by the general name, '"view"'. Outside of the view block, however, you should always use the given name, '"fancy"':

[% fancy.title  %]
[% fancy.author %]
[% fancy.col.bg %]

The choice of given name or '"view"' is much more important when it comes to "BLOCK" definitions within a "VIEW". It is generally recommended that you use '"view"' inside a "VIEW" definition because this is guaranteed to be correctly defined at any point in the future when the block gets called. The original name of the view might have long since been changed or reused but the self-reference via '"view"' should always be intact and valid.

Take the following VIEW as an example:

[% VIEW foo %]
   [% view.title = 'Hello World' %]
   [% BLOCK header %]
   Title: [% view.title %]
   [% END %]
[% END %]

Even if we rename the view, or create a new "foo" variable, the header block still correctly accesses the "title" attribute of the view to which it belongs. Whenever a view "BLOCK" is processed, the "view" variable is always updated to contain the correct reference to the view object to which it belongs.

[% bar = foo %]
[% foo = { title => "New Foo" } %]  # no problem
[% bar.header %]                    # => Title: Hello World

Saving References to External Views

When it comes to view inheritance, it's always a good idea to take a local copy of a parent or delegate view and store it as an attribute within the view for later use. This ensures that the correct view reference is always available, even if the external name of a view has been changed.

[% VIEW plain %]
   ...
[% END %]
[% VIEW fancy %]
   [% view.plain = plain %]
   [% BLOCK foo %]
   [% view.plain.foo | replace('plain', 'fancy') %]
   [% END %]
[% END %]
[% plain.foo %]         # => <plain>public foo block</plain>
[% plain = 'blah' %]    # no problem
[% fancy.foo %]         # => <fancy>public foo block</fancy>

Views as Data Presenters

Another key role of a view is to act as a dispatcher to automatically apply the correct template to present a particular object or data item. This is handled via the print() method.

Here's an example:

[% VIEW foo %]
   [% BLOCK text %]
      Some text: [% item %]
   [% END %]
   [% BLOCK hash %]
      a hash:
      [% FOREACH key = item.keys.sort -%]
         [% key %] => [% item.$key %]
      [% END -%]
   [% END %]
   [% BLOCK list %]
      a list: [% item.sort.join(', ') %]
   [% END %]
[% END %]

We can now use the view to print text, hashes or lists. The print() method includes the right template depending on the typing of the argument (or arguments) passed.

[% some_text = 'I read the news today, oh boy.' %]
[% a_hash    = { house => 'Lords', hall => 'Albert' } %]
[% a_list    = [ 'sure', 'Nobody', 'really' ] %]
[% view.print(some_text) %]
                    # Some text: I read the news today, oh boy.
[% view.print(a_hash) %]
                    # a hash:
                         hall => Albert
                         house => Lords
[% view.print(a_list) %]
                    # a list: Nobody, really, sure

You can also provide templates to print objects of any other class. The class name is mapped to a template name with all non-word character sequences such as '"::"' converted to a single '"_"'.

[% VIEW foo %]
   [% BLOCK Foo_Bar %]
      a Foo::Bar object:
          thingies: [% view.print(item.thingies) %]
           doodahs: [% view.print(item.doodahs)  %]
   [% END %]
[% END %]
[% USE fubar = Foo::Bar(...) %]
[% foo.print(fubar) %]

Note how we use the view object to display various items within the objects ('"thingies"' and '"doodahs"'). We don't need to worry what kind of data these represent (text, list, hash, etc) because we can let the view worry about it, automatically mapping the data type to the correct template.

Views may define their own type => template map.

[% VIEW foo
     map = { TEXT  => 'plain_text',
             ARRAY => 'show_list',
             HASH  => 'show_hash',
             My::Module => 'template_name'
             default    => 'any_old_data'
           }
%]
    [% BLOCK plain_text %]
       ...
    [% END %]
    ...
[% END %]

They can also provide a "default" map entry, specified as part of the "map" hash or as a parameter by itself.

[% VIEW foo
     map     = { ... },
     default = 'whatever'
%]
   ...
[% END %]

or

[% VIEW foo %]
   [% view.map     = { ... }
      view.default = 'whatever'
   %]
   ...
[% END %]

The print() method provides one more piece of magic. If you pass it a reference to an object which provides a present() method, then the method will be called passing the view as an argument. This then gives any object a chance to determine how it should be presented via the view.

package Foo::Bar;
...
sub present {
    my ($self, $view) = @_;
    return "a Foo::Bar object:\n"
         . "thingies: " . $view->print($self->{ _THINGIES }) . "\n"
         . "doodahs: " . $view->print($self->{ _DOODAHS }) . "\n";
}

The object is free to delve deeply into its innards and mess around with its own private data, before presenting the relevant data via the view. In a more complex example, a present() method might walk part of a tree making calls back against the view to present different nodes within the tree. We may not want to expose the internal structure of the tree (because that would break encapsulation and make our presentation code dependant on it) but we want to have some way of walking the tree and presenting items found in a particular manner.

This is known as Structure Shy Traversal. Our view object doesn't require prior knowledge about the internal structure of any data set to be able to traverse it and present the data contained therein. The data items themselves, via the present() method, can implement the internal iterators to guide the view along the right path to presentation happiness.

The upshot is that you can use views to greatly simplify the display of data structures like "XML::DOM" trees. The documentation for the "Template::Plugin::XML::DOM" module contains an example of this. In essence, it looks something like this:

XML source:

<user name="Andy Wardley">
    <project id="iCan" title="iCan, but theyCan't"/>
    <project id="p45"  title="iDid, but theyDidn't"/>
</user>

TT View:

[% VIEW fancy %]
   [% BLOCK user %]
      User: [% item.name %]
            [% item.content(myview) %]
   [% END %]
   [% BLOCK project %]
        Project: [% project.id %] - [% project.name %]
   [% END %]
[% END %]

Generate view:

[% USE dom = XML.DOM %]
[% fancy.print(dom.parse(xml_source)) %]

Output:

User: Andy Wardley
  Project: iCan - iCan, but theyCan't
  Project: p45 - iDid, but th

NAME

Template::Manual::Views - Views as template collectors

Overview

A View object acts as a named container for one or more template definitions. It can be used to group related templates together under a single name, making it easier to manage and reuse them.

The View object acts as a collector of template definitions, mapping template names to template blocks. When a View object is invoked with the print() method, it iterates through the items provided as arguments and, for each item, calls the associated template defined within the view.

Views as Template Collectors/Providers

A View object can be used to collect a set of template definitions. These definitions can be provided as arguments to the VIEW directive.

[% VIEW myview %]
   [% BLOCK hello %]
      Hello, [% name %]!
   [% END %]
   [% BLOCK goodbye %]
      Goodbye, [% name %]!
   [% END %]
[% END %]

[% USE greet = myview %]
[% greet.print(name='World', template='hello') %]
   "Hello, World!"
[% greet.print(name='World', template='goodbye') %]
   "Goodbye, World!"

In this example, myview is defined as a View object which collects two template blocks: hello and goodbye. The USE greet = myview statement assigns the View object to the variable greet. The subsequent calls to greet.print() use the templates defined within myview to generate output.

Local BLOCK Definitions

Template definitions can also be defined locally within a template, and then used to construct a View object. This allows for more dynamic creation and manipulation of views.

[% WRAPPER mywrapper %]
   [% BLOCK title %]My Document Title[% END %]
   [% BLOCK body %]This is the main content.[% END %]

   [% USE view = VIEW %]
   [% view.add(BLOCK=title) %]
   [% view.add(BLOCK=body) %]

   [% view.print() %]
[% END %]

Here, a View object is created using the VIEW directive without any arguments. The template blocks title and body are then added to the view using the add() method. Finally, the view.print() method is called to render the content using the combined templates.

Preserving Variable State within Views

A key feature of View objects is their ability to preserve variable state between invocations. This means that variables defined within a view's context are maintained across multiple calls to print(), enabling the construction of complex, stateful output.

The same approach can be applied to many other areas. Here's an example from the "File"/"Directory" plugins.

[% VIEW myview %]
   [% BLOCK file %]
      - [% item.name %]
   [% END %]
   [% BLOCK directory %]
      * [% item.name %]
        [% item.content(myview) FILTER indent %]
   [% END %]
[% END %]
[% USE dir = Directory(dirpath) %]
[% myview.print(dir) %]

And here's the same approach use to convert POD documentation to any other format via template.

[%  # load Pod plugin and parse source file into Pod Object Model
    USE Pod;
    pom = Pod.parse_file(my_pod_file);
    # define view to map all Pod elements to "pod/html/xxx" templates
    VIEW pod2html
        prefix='pod/html';
    END;
    # now print document via view (i.e. as HTML)
    pod2html.print(pom)
%]

Here we simply define a template prefix for the view which causes the view to look for "pod/html/head1", "pod/html/head2", "pod/html/over" as templates to present the different sections of the parsed Pod document.

There are some examples in the Template Toolkit test suite: t/pod.t and t/view.t which may shed some more light on this. See the distribution sub-directory examples/pod/html for examples of Pod -> HTML templates.
