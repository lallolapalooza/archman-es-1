NOMBRE

Test::More - otro framework para escribir scripts de prueba

SINOPSIS

use Test::More tests => 23;
# o
use Test::More skip_all => $reason;
# o
use Test::More;   # ver done_testing()
require_ok( 'Some::Module' );
# Diversas formas de decir "ok"
ok($got eq $expected, $test_name);
is  ($got, $expected, $test_name);
isnt($got, $expected, $test_name);
# En lugar de imprimir STDERR "# aquí está lo que salió mal\n"
diag("aquí está lo que salió mal");
like  ($got, qr/expected/, $test_name);
unlike($got, qr/expected/, $test_name);
cmp_ok($got, '==', $expected, $test_name);
is_deeply($got_complex_structure, $expected_complex_structure, $test_name);
SKIP: {
    skip $why, $how_many unless $have_some_feature;
    ok( foo(),       $test_name );
    is( foo(42), 23, $test_name );
};
TODO: {
    local $TODO = $why;
    ok( foo(),       $test_name );
    is( foo(42), 23, $test_name );
};
can_ok($module, @methods);
isa_ok($object, $class);
pass($test_name);
fail($test_name);
BAIL_OUT($why);
# NO IMPLEMENTADO!!!
my @status = Test::More::status;

DESCRIPCIÓN

¡ALTO! Si recién estás comenzando a escribir pruebas, échale un vistazo a Test2::Suite primero.

Este es un reemplazo directo para Test::Simple al que puedes cambiar una vez que te familiarices con las pruebas básicas.

El propósito de este módulo es proporcionar una amplia gama de utilidades de prueba. Diversas formas de decir "ok" con mejor salida de diagnóstico, facilidades para omitir pruebas, probar características futuras y comparar estructuras de datos complejas. Si bien puedes hacer casi cualquier cosa con una simple función ok(), esta no proporciona una buena salida de diagnóstico.

Me encanta cuando un plan sale bien

Antes que nada, necesitas un plan de pruebas. Esto básicamente declara cuántas pruebas ejecutará tu script para protegerte contra fallos prematuros.

La forma preferida de hacer esto es declarar un plan cuando "use Test::More".

use Test::More tests => 23;

Hay casos en los que no sabrás de antemano cuántas pruebas ejecutará tu script. En este caso, puedes declarar tus pruebas al final.

use Test::More;
... ejecuta tus pruebas ...
done_testing( $number_of_tests_run );

NOTA done_testing() nunca debe llamarse en un bloque "END { ... }".

A veces, realmente no sabes cuántas pruebas se ejecutaron, o es demasiado difícil de calcular. En ese caso, puedes omitir $number_of_tests_run.

En algunos casos, querrás omitir completamente un script de prueba entero.

use Test::More skip_all => $skip_reason;

Tu script declarará un salto con la razón por la cual se omitió y saldrá inmediatamente con un cero (éxito). Ver Test::Harness para más detalles.

Si quieres controlar qué funciones exportará Test::More, tienes que usar la opción 'import'. Por ejemplo, para importar todo excepto 'fail', harías:

use Test::More tests => 23, import => ['!fail'];

Alternativamente, puedes usar la función plan(). Útil para cuando tienes que calcular el número de pruebas.

use Test::More;
plan tests => keys %Stuff * 3;

o para decidir entre ejecutar las pruebas o no:

use Test::More;
if( $^O eq 'MacOS' ) {
    plan skip_all => 'Prueba irrelevante en MacOS';
}
else {
    plan tests => 42;
}
done_testing
done_testing();
done_testing($number_of_tests);

Si no sabes cuántas pruebas vas a ejecutar, puedes emitir el plan cuando hayas terminado de ejecutar las pruebas.

$number_of_tests es lo mismo que plan(), es el número de pruebas que esperabas ejecutar. Puedes omitirlo, en cuyo caso el número de pruebas que ejecutaste no importa, solo el hecho de que tus pruebas se ejecutaron hasta su conclusión.

Esto es más seguro y reemplaza el plan "no_plan".

Nota: Nunca debes poner done_testing() dentro de un bloque "END { ... }". El plan está ahí para asegurar que tu prueba no salga antes de que las pruebas se completen. Si usas un bloque END, evitas por completo esta protección.

Nombres de prueba

Por convención, a cada prueba se le asigna un número en orden. Esto se hace en gran medida automáticamente por ti. Sin embargo, a menudo es muy útil asignar un nombre a cada prueba. ¿Cuál preferirías ver?

ok 4
not ok 5
ok 6

¿o?

ok 4 - exponencial básica
not ok 5 - exponencial simple
ok 6 - fuerza == masa * aceleración

El segundo te da una idea de lo que falló. También hace que sea más fácil encontrar la prueba en tu script, simplemente busca "exponencial simple".

Todas las funciones de prueba toman un argumento de nombre. Es opcional, pero se recomienda encarecidamente su uso.

Estoy bien, tú no lo estás.

El propósito básico de este módulo es imprimir "ok #" o "not ok #" dependiendo de si una prueba dada tuvo éxito o falló. Todo lo demás es solo un extra.

Todas las siguientes imprimen "ok" o "not ok" dependiendo de si la prueba tuvo éxito o falló. Todas también devuelven verdadero o falso, respectivamente.

ok
ok($got eq $expected, $test_name);

Esto simplemente evalúa cualquier expresión ("$got eq $expected" es solo un ejemplo simple) y la usa para determinar si la prueba tuvo éxito o falló. Una expresión verdadera pasa, una falsa falla. Muy simple.

Por ejemplo:

ok( $exp{9} == 81,                   'exponencial simple' );
ok( Film->can('db_Main'),            'set_db()' );
ok( $p->tests == 4,                  'visto tests' );
ok( !grep(!defined $_, @items),      'todos los items definidos' );

(Mnemotecnia: "Esto está bien.")

$test_name es una descripción muy corta de la prueba que se imprimirá. Hace que sea muy fácil encontrar una prueba en tu script cuando falla y da a otros una idea de tus intenciones. $test_name es opcional, pero muy encarecidamente recomendamos su uso.

Si un ok() falla, producirá algunos diagnósticos:

not ok 18 - suficiente mucosidad
#   Test fallido 'suficiente mucosidad'
#   en foo.t en la línea 42.

Esto es lo mismo que la rutina ok() de Test::Simple.

is
isnt
is  ( $got, $expected, $test_name );
isnt( $got, $expected, $test_name );

Similar a ok(), is() e isnt() comparan sus dos argumentos con "eq" y "ne" respectivamente y usan el resultado de eso para determinar si la prueba tuvo éxito o falló. Así que estas:

# ¿Es la respuesta definitiva 42?
is( ultimate_answer(), 42,          "Significado de la vida" );
# $foo no está vacío
isnt( $foo, '',     "Tengo algo de foo" );

son similares a estas:

ok( ultimate_answer() eq 42,        "Significado de la vida" );
ok( $foo ne '',     "Tengo algo de foo" );

"undef" solo coincidirá con "undef". Así que puedes probar un valor contra "undef" así:

is($not_defined, undef, "indefinido como se esperaba");

(Mnemotecnia: "Esto es eso." "Esto no es eso.")

¿Por qué usarlos? Producen mejores diagnósticos en caso de fallo. ok() no puede saber qué estás probando (más allá del nombre), pero is() e isnt() saben cuál era la prueba y por qué falló. Por ejemplo, esta prueba:

COMPARAJE DE REFERENCIAS COMPLEJAS

Debido a que las referencias en Perl son a menudo complejas y no son comparables usando eq o ==, necesitas una forma especial para compararlas.

is_deeply
is_deeply( $got, $expected, $test_name )

Compara dos referencias (arrays, hashes, etc.) para ver si son estructuralmente idénticas.

Por ejemplo:

my $foo = {
    bar => [ 1, 2, { baz => 42 } ],
    qux => 1,
};
my $expected = {
    bar => [ 1, 2, { baz => 42 } ],
    qux => 1,
};
is_deeply( $foo, $expected, 'deep structure matches' );

Si las estructuras no coinciden, se imprimirá la diferencia con un formato de diff.

También puede comparar un array o hash simple:

is_deeply( [1, 2, 3], [1, 2, 3], 'simple array' );
is_deeply( { a => 1 }, { a => 1 }, 'simple hash' );

Nota: is_deeply está implementado usando Devel::PPPort, que está incluido en la distribución estándar de Perl desde la versión 5.6.0.

EXPRESIONES REGULARES

like
unlike
like( $got, $pattern, $test_name );
unlike( $got, $pattern, $test_name );

Comprueba si $got coincide con la expresión regular $pattern. like pasa si coincide, unlike pasa si no coincide.

Estas son equivalentes a:

ok( $got =~ /$pattern/, $test_name );
ok( $got !~ /$pattern/, $test_name );

Sin embargo, like y unlike producen diagnósticos mucho mejores si falla. Por ejemplo, si se supone que una cadena debe coincidir con una expresión regular, pero no lo hace, el error que se imprime contendrá la cadena que no coincidió y la expresión regular con la que se probó.

(Mnemotecnia: "Parece que coincide." "Parece que no coincide.")

OTROS TESTS DE CASI ESTÁNDAR

can_ok
can_ok($module, @methods);

Prueba que un módulo puede realizar los métodos que se le indican.

Por ejemplo:

can_ok('File::Find', 'find');

esto es similar a:

ok( $module->can($method) )

pero es más fácil de escribir y produce un mejor diagnóstico si falla.

isa_ok
isa_ok( $thing, $class, $test_name );

Prueba que $thing es una instancia de $class.

Por ejemplo:

isa_ok( $file, 'File::Spec' );

esto es similar a:

ok( ref($thing) eq $class )

pero es más fácil de escribir y produce un mejor diagnóstico si falla.

pass
pass($test_name);

Simplemente imprime "ok #" con el nombre de la prueba dado. Útil cuando no hay una condición obvia que probar, pero simplemente se supone que el código que se ejecuta tiene éxito.

fail
fail($test_name);

Imprime "not ok #" con el nombre de la prueba dado. Útil para indicar que un caso de prueba esperado ha fallado.

DIAGNÓSTICOS AVANZADOS

diag
diag("here's what went wrong");

Si una prueba falla, es posible que desees proporcionar información adicional sobre el error. diag imprime sus argumentos precedidos por un #.

Por ejemplo:

not ok 1
#   Failed test 'correct output'
#   at foo.t line 12.
#     'This is not the output you were looking for'
#          vs 'This is the output you were looking for'
#     The two strings differ only by the word 'not'.
#     This is not the output you were looking for
#     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
# Have      : This is not the output you were looking for
# Want      : This is the output you were looking for
#           : ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
#                 ^^^^^
# It's not all bad.
# Test::More knows about diffs.

Si se llama a diag después de un fallo, su salida se incluirá en el informe de fallos.

SALIDA ANTICIPADA DEL PROGRAMA

BAIL_OUT
BAIL_OUT($reason);

Si algo va terriblemente mal y no puedes continuar con las pruebas, puedes llamar a BAIL_OUT. Esto imprimirá el mensaje dado y saldrá del programa con un código de salida distinto de cero. Esto se usa típicamente cuando un archivo de configuración no se encuentra o cuando se requiere una dependencia externa que no está presente.

SALTO DE PRUEBAS

A veces, querrás omitir una prueba. Esto podría ser porque una característica aún no está implementada, o porque la prueba falla en ciertas plataformas, etc.

SKIP

Se puede usar para omitir pruebas individuales o grupos de pruebas.

use Test::More tests => 4;
ok( 1, 'This test will run' );
SKIP: {
    skip 'This feature is not implemented yet', 2 unless $feature_is_ready;
    ok( foo(), 'feature foo' );
    is( bar(), 42, 'feature bar' );
};
ok( 4, 'This test will also run' );

La sintaxis es skip $why, $how_many, donde $why es la razón para omitir la prueba y $how_many es el número de pruebas que se omitirán. Si se omite $how_many, se asumirá que es 1.

El bloque SKIP: está allí solo para que la mayoría de los probadores de Perl puedan ver que la prueba se omitió.

La prueba skip se puede usar en combinación con una condición. Si la condición es falsa, la prueba no se omitirá.

TODO

A veces querrás marcar una prueba como "por hacer". Esto indica que la prueba se espera que falle actualmente, pero que esperas que funcione en el futuro. Esto es útil para registrar un error conocido sin que la suite de pruebas falle.

use Test::More tests => 3;
ok( 1, 'This test will pass' );
TODO: {
    local $TODO = 'Bug #123: This feature is broken';
    ok( foo(), 'feature foo' );
    is( bar(), 42, 'feature bar' );
};
ok( 4, 'This test will pass too' );

La prueba marcada como TODO se ejecutará, pero si pasa, se informará como un fallo TODO. Si falla, se informará como un paso TODO.

Nombre

Test::More - A simple, powerful testing framework for Perl.

Sinopsis

    use Test::More tests => 10; # Or done_testing()

    # Basic tests
    ok( $condition, $test_name );
    is( $got, $expected, $test_name );
    isnt( $got, $expected, $test_name );
    like( $got, qr/pattern/, $test_name );
    unlike( $got, qr/pattern/, $test_name );
    cmp_ok( $got, $operator, $expected, $test_name );

    # Object and module tests
    can_ok( $module, @methods );
    isa_ok( $object, $class, $object_name );
    new_ok( $class );

    # Structured tests
    subtest $name => \&code, @args;

    # Simple pass/fail
    pass($test_name);
    fail($test_name);

    # Skipping tests
    skip( $reason, $num_tests );
    skip_all( $reason );

    # Diagnosing tests
    diag( $message );
    note( $message );

Descripción

Test::More es el módulo de pruebas más utilizado en el ecosistema de Perl. Proporciona una rica colección de subrutinas para escribir pruebas para su código Perl. Si está escribiendo un módulo o una aplicación para Perl, debería usar Test::More.

El objetivo principal de Test::More es permitirle escribir pruebas de forma sencilla y concisa, al tiempo que proporciona diagnósticos útiles cuando las pruebas fallan.

Pruebas básicas

ok
ok( $condition, $test_name );

Esta es la más básica de todas las pruebas. Evalúa la expresión $condition y declara la prueba como ok si es verdadera, o not ok si es falsa. El $test_name opcional proporciona una descripción de la prueba que se mostrará si la prueba falla.

ok( 42, 'a string of numbers' );
ok( undef, 'this test should fail' );

Si $test_name no se proporciona, se generará uno por defecto.

is
is( $got, $expected, $test_name );

Compara dos valores, $got y $expected, para ver si son idénticos. Utiliza el operador eq para la comparación de cadenas y el operador == para la comparación de números. Por defecto, se trata como una comparación de cadenas. Para obtener la comparación numérica, use cmp_ok.

my $foo = 'waffle';
my $bar = 'yarblokos';
is( $foo, $bar,   'Is foo the same as bar?' );

Producirá algo como esto:

not ok 17 - Is foo the same as bar?
#   Failed test 'Is foo the same as bar?'
#   in foo.t at line 139.
#          got: 'waffle'
#     expected: 'yarblokos'

Así podrá averiguar qué salió mal sin tener que volver a ejecutar la prueba.

Se le anima a usar is() e isnt() sobre ok() siempre que sea posible, sin embargo, ¡no se sienta tentado a usarlos para averiguar si algo es verdadero o falso!

# XXX MAL!
is( exists $brooklyn{tree}, 1, 'A tree grows in Brooklyn' );

Esto no comprueba si "exists $brooklyn{tree}" es verdadero, comprueba si devuelve 1. Muy diferente. Similares advertencias existen para falso y 0. En estos casos, use ok().

ok( exists $brooklyn{tree},    'A tree grows in Brooklyn' );

Una simple llamada a isnt() normalmente no proporciona una prueba sólida, pero hay casos en los que no se puede decir mucho más sobre un valor que el hecho de que es diferente de algún otro valor:

new_ok $obj, "Foo";
my $clone = $obj->clone;
isa_ok $obj, "Foo", "Foo->clone";
isnt $obj, $clone, "clone() produces a different object";

Históricamente soportábamos una función "isn't()" como alias de isnt(), sin embargo, en Perl 5.37.9 se deprecó el uso del apóstrofe como separador de paquetes y para Perl 5.42.0 se habrá eliminado completamente. En consecuencia, el uso de "isn't()" también está obsoleto y producirá advertencias cuando se utilice, a menos que las advertencias de 'deprecated' se desactiven específicamente en el ámbito en el que se use. Se le aconseja encarecidamente que migre a usar isnt() en su lugar.

like
like( $got, qr/expected/, $test_name );

Similar a ok(), like() compara $got con la expresión regular "qr/expected/".

Así que esto:

like($got, qr/expected/, 'this is like that');

es similar a:

ok( $got =~ m/expected/, 'this is like that');

(Mnemotecnia "Esto es como eso".)

El segundo argumento es una expresión regular. Puede ser dado como una referencia de expresión regular (es decir, "qr//") o (para una mejor compatibilidad con perls más antiguos) como una cadena que parece una expresión regular (los delimitadores alternativos no son actualmente compatibles):

like( $got, '/expected/', 'this is like that' );

Las opciones de la expresión regular pueden colocarse al final ('/expected/i').

Sus ventajas sobre ok() son similares a las de is() y isnt(). Mejores diagnósticos en caso de fallo.

unlike
unlike( $got, qr/expected/, $test_name );

Funciona exactamente como like(), solo que comprueba si $got no coincide con el patrón dado.

cmp_ok
cmp_ok( $got, $op, $expected, $test_name );

A medio camino entre ok() y is() se encuentra cmp_ok(). Esto le permite comparar dos argumentos utilizando cualquier operador binario de Perl. La prueba pasa si la comparación es verdadera y falla en caso contrario.

# ok( $got eq $expected );
cmp_ok( $got, 'eq', $expected, 'this eq that' );
# ok( $got == $expected );
cmp_ok( $got, '==', $expected, 'this == that' );
# ok( $got && $expected );
cmp_ok( $got, '&&', $expected, 'this && that' );
...etc...

Su ventaja sobre ok() es que cuando la prueba falla sabrá cuáles eran $got y $expected:

not ok 1
#   Failed test in foo.t at line 12.
#     '23'
#         &&
#     undef

También es útil en aquellos casos en los que se comparan números y el uso de "eq" por parte de is() interfiera:

cmp_ok( $big_hairy_number, '==', $another_big_hairy_number );

Es especialmente útil cuando se comparan relaciones de mayor o menor que entre valores:

cmp_ok( $some_value, '<=', $upper_limit );
can_ok
can_ok($module, @methods);
can_ok($object, @methods);

Comprueba que el $module o $object pueden realizar estos @methods (funciona también con funciones).

can_ok('Foo', qw(this that whatever));

es casi exactamente lo mismo que decir:

ok( Foo->can('this') &&
    Foo->can('that') &&
    Foo->can('whatever')
  );

solo que sin escribir tanto y con una mejor interfaz. Útil para probar rápidamente una interfaz.

No importa cuántos @methods compruebes, una sola llamada a can_ok() cuenta como una prueba. Si deseas lo contrario, usa:

foreach my $meth (@methods) {
    can_ok('Foo', $meth);
}
isa_ok
isa_ok($object,   $class, $object_name);
isa_ok($subclass, $class, $object_name);
isa_ok($ref,      $type,  $ref_name);

Comprueba si el dado "$object->isa($class)". También comprueba que el objeto se definió en primer lugar. Útil para este tipo de cosas:

my $obj = Some::Module->new;
isa_ok( $obj, 'Some::Module' );

donde de lo contrario tendrías que escribir

my $obj = Some::Module->new;
ok( defined $obj && $obj->isa('Some::Module') );

para protegerte de que tu script de prueba explote.

También puedes probar una clase, para asegurarte de que tiene el ancestro correcto:

isa_ok( 'Vole', 'Rodent' );

Funciona también con referencias:

isa_ok( $array_ref, 'ARRAY' );

Los diagnósticos de esta prueba normalmente solo se refieren a 'el objeto'. Si deseas que sean más específicos, puedes proporcionar un $object_name (por ejemplo, 'Cliente de prueba').

new_ok
my $obj = new_ok( $class );
my $obj = new_ok( $class => \@args );
my $obj = new_ok( $class => \@args, $object_name );

Una función de conveniencia que combina la creación de un objeto y la llamada a isa_ok() sobre ese objeto.

Es básicamente equivalente a:

my $obj = $class->new(@args);
isa_ok $obj, $class, $object_name;

Si @args no se proporciona, se usará una lista vacía.

Esta función solo funciona en new() y asume que new() devolverá un solo objeto que sea $class.

subtest
subtest $name => \&code, @args;

subtest() ejecuta el &code como su propia pequeña prueba con su propio plan y su propio resultado. La prueba principal considera esto como una sola prueba, utilizando el resultado de toda la subprueba para determinar si está ok o no ok.

Por ejemplo...

use Test::More tests => 3;

pass("First test");
subtest 'An example subtest' => sub {
    plan tests => 2;
    pass("This is a subtest");
    pass("So is this");
};
pass("Third test");

Esto produciría.

1..3
ok 1 - First test
    # Subtest: An example subtest
    1..2
    ok 1 - This is a subtest
    ok 2 - So is this
ok 2 - An example subtest
ok 3 - Third test

Una subprueba puede llamar a "skip_all". No se ejecutarán pruebas, pero la subprueba se considera omitida.

subtest 'skippy' => sub {
    plan skip_all => 'cuz I said so';
    pass('this test will never be run');
};

Devuelve verdadero si la subprueba pasó, falso en caso contrario.

Debido a cómo funcionan las subpruebas, puedes omitir un plan si lo deseas. Esto añade un done_testing() implícito al final de tu subprueba. Las dos subpruebas siguientes son equivalentes:

subtest 'subtest with implicit done_testing()', sub {
    ok 1, 'subtests with an implicit done testing should work';
    ok 1, '... and support more than one test';
    ok 1, '... no matter how many tests are run';
};
subtest 'subtest with explicit done_testing()', sub {
    ok 1, 'subtests with an explicit done testing should work';
    ok 1, '... and support more than one test';
    ok 1, '... no matter how many tests are run';
    done_testing();
};

Los argumentos adicionales dados a "subtest" se pasan al callback. Por ejemplo:

sub my_subtest {
    my $range = shift;
    ...
}
for my $range (1, 10, 100, 1000) {
    subtest "testing range $range", \&my_subtest, $range;
}
pass
fail
pass($test_name);
fail($test_name);

A veces solo quieres decir que las pruebas han pasado. Por lo general, el caso es que tienes alguna condición complicada que es difícil de encajar en un ok(). En este caso, puedes simplemente usar pass() (para declarar la prueba como ok) o fail (para no ok). Son sinónimos de ok(1) y ok(0).

Úsalos muy, muy, muy poco.

Pruebas de módulos

A veces quieres comprobar si un módulo, o una lista de módulos, se pueden cargar correctamente. Por ejemplo, a menudo querrás una primera prueba que simplemente cargue todos los módulos de la distribución para asegurarte de que funcionan antes de continuar con pruebas más complicadas.

Carga de módulos

Para tales fines tenemos "use_ok" y "require_ok".

require_ok
require_ok($module);
require_ok($file);

Intenta "require" el dado $module o $file. Si se carga con éxito, la prueba pasará. De lo contrario, fallará y mostrará el error de carga.

"require_ok" adivinará si la entrada es un nombre de módulo o un nombre de archivo.

No se lanzará ninguna excepción si la carga falla.

# require Some::Module
require_ok "Some::Module";
# require "Some/File.pl";
require_ok "Some/File.pl";
# detén las pruebas si alguno de tus módulos no carga
for my $module (@module) {
    require_ok $module or BAIL_OUT "No se puede cargar $module";
}
use_ok
BEGIN { use_ok($module); }
BEGIN { use_ok($module, @imports); }

Similar a "require_ok", pero realizará un "use" del $module en cuestión y solo cargará módulos, no archivos.

Si solo deseas probar que un módulo se puede cargar, usa "require_ok".

Si solo deseas cargar un módulo en una prueba, recomendamos simplemente usar "use" directamente. Esto provocará que la prueba se detenga.

Se recomienda ejecutar use_ok() dentro de un bloque BEGIN para que sus funciones se exporten en tiempo de compilación y los prototipos se cumplan correctamente.

Si se proporcionan @imports, se pasan al uso. Entonces, esto:

BEGIN { use_ok('Some::Module', qw(foo bar)) }

es como hacer esto:

use Some::Module qw(foo bar);

Los números de versión se pueden verificar así:

# Igual que "use Some::Module 1.02"
BEGIN { use_ok('Some::Module', 1.02) }

No intentes hacer esto:

BEGIN {
    use_ok('Some::Module');
    ...algún código que depende del uso...
    ...ocurriendo en tiempo de compilación...
}

porque la noción de "tiempo de compilación" es relativa. En su lugar, querrás:

BEGIN { use_ok('Some::Module') }
BEGIN { ...algún código que depende del uso... }

Si deseas el equivalente a "use Foo ()", usa un módulo pero sin importar nada, usa "require_ok".

BEGIN { require_ok "Foo" }

Estructuras de datos complejas

No todo es una simple comparación de igualdad o una expresión regular. Hay momentos en los que necesitas ver si dos estructuras de datos son equivalentes. Para estas instancias, Test::More proporciona un puñado de funciones útiles.

NOTA No estoy seguro de lo que sucederá con los manejadores de archivos.

is_deeply
is_deeply( $got, $expected, $test_name );

Similar a is(), excepto que si $got y $expected son referencias, realiza una comparación profunda recorriendo cada estructura de datos para ver si son equivalentes. Si las dos estructuras son diferentes, mostrará el lugar donde comienzan a diferir.

is_deeply() compara los valores desreferenciados de las referencias, las referencias en sí mismas (excepto por su tipo) se ignoran. Esto significa que aspectos como la bendición y las ligaduras no se consideran "diferentes".

is_deeply() actualmente tiene un manejo muy limitado de referencias a funciones y globs. Simplemente verifica si tienen el mismo referente. Esto puede mejorar en el futuro.

Test::Differences y Test::Deep proporcionan una funcionalidad más profunda en esta línea.

NOTA is_deeply() tiene limitaciones cuando se trata de comparar cadenas y referencias:

my $path = path('.');
my $hash = {};
is_deeply( $path, "$path" ); # ok
is_deeply( $hash, "$hash" ); # fail

Esto sucede porque is_deeply des-sobrecargará todos los argumentos incondicionalmente. Probablemente sea mejor no usar is_deeply con sobrecarga. Por razones de legado, esto probablemente nunca se solucionará. Si deseas una herramienta mucho mejor para esto, deberías ver Test2::Suite. Específicamente, Test2::Tools::Compare tiene una función is() que funciona como "is_deeply" con muchas mejoras.

Diagnósticos

Si eliges la función de prueba correcta, generalmente obtendrás una buena idea de lo que salió mal cuando falló. Pero a veces no funciona así. Así que aquí tenemos formas para que escribas tus propios mensajes de diagnóstico que son más seguros que simplemente "print STDERR".

diag
diag(@diagnostic_message);

Imprime un mensaje de diagnóstico que se garantiza que no interferirá con la salida de la prueba. Como "print", @diagnostic_message simplemente se concatena.

Devuelve falso, para preservar el fallo.

Útil para este tipo de cosas:

ok( grep(/foo/, @users), "Hay un usuario foo" ) or
    diag("Como no hay foo, comprueba que /etc/bar esté configurado correctamente");

lo que produciría:

not ok 42 - Hay un usuario foo
#   Prueba fallida 'Hay un usuario foo'
#   en foo.t en la línea 52.
# Como no hay foo, comprueba que /etc/bar esté configurado correctamente.

Quizás recuerdes "ok() or diag()" con el mnemotécnico open() or die().

NOTA El formato exacto de la salida de diagnóstico todavía está cambiando, pero se garantiza que lo que sea que le envíes no interferirá con la prueba.

note
note(@diagnostic_message);

Similar a diag(), excepto que el mensaje no se verá cuando la prueba se ejecute en un arnés. Solo será visible en el flujo TAP detallado.

Útil para incluir notas que podrían ser útiles para depurar, pero que no indican un problema.

note("El archivo temporal es $tempfile");
explain
my @dump = explain @diagnostic_message;

Volcará el contenido de cualquier referencia en un formato legible para humanos. Generalmente querrás pasar esto a "note" o "diag".

Útil para cosas como...

is_deeply($have, $want) || diag explain $have;

o

note explain \%args;
Some::Class->method(%args);

Pruebas condicionales

A veces, ejecutar una prueba bajo ciertas condiciones hará que el script de prueba muera. Cierta función o método no está implementado (como fork() en MacOS), algún recurso no está disponible (como una conexión de red) o un módulo no está disponible. En estos casos, es necesario omitir pruebas o declarar que se supone que fallan pero que funcionarán en el futuro (una prueba todo).

Para más detalles sobre la mecánica de las pruebas skip y todo, consulta Test::Harness.

La forma en que Test::More maneja esto es con un bloque con nombre. Básicamente, un bloque de pruebas que puede omitirse o hacerse todo. Es mejor si te lo muestro...

SKIP: BLOQUE
SKIP: {
    skip $why, $how_many if $condition;
    ...el código normal de prueba va aquí...
}

Esto declara un bloque de pruebas que pueden omitirse, $how_many pruebas que hay, $why y bajo qué $condition omitirlas. Un ejemplo es la forma más fácil de ilustrar:

SKIP: {
    eval { require HTML::Lint };
    skip "HTML::Lint no instalado", 2 if $@;
    my $lint = new HTML::Lint;
    isa_ok( $lint, "HTML::Lint" );
    $lint->parse( $html );
    is( $lint->errors, 0, "No se encontraron errores en HTML" );
}

Si el usuario no tiene HTML::Lint instalado, todo el bloque de código *no se ejecutará en absoluto*. Test::More generará ok especiales que Test::Harness interpreta como pruebas omitidas, pero que pasan.

Es importante que $how_many refleje con precisión el número de pruebas en el bloque SKIP para que el número de pruebas ejecutadas coincida con tu plan. Si tu plan es "no_plan", $how_many es opcional y por defecto será 1.

Es perfectamente seguro anidar bloques SKIP. Cada bloque SKIP debe tener la etiqueta "SKIP", o Test::More no podrá hacer su magia.

No omitas pruebas que fallan porque hay un error en tu programa, o para las cuales aún no tienes código escrito. Para eso usas TODO. Sigue leyendo.

TODO: BLOQUE
TODO: {
    local $TODO = $why if $condition;
    ...el código normal de prueba va aquí...
}

Declara un bloque de pruebas que esperas que fallen y $why. Tal vez sea porque no has corregido un error o no has terminado una nueva característica:

TODO: {
    local $TODO = "URI::Geller no está terminado";
    my $card = "Ocho de tréboles";
    is( URI::Geller->your_card, $card, '¿Es ESTA tu carta?' );
    my $spoon;
    URI::Geller->bend_spoon;
    is( $spoon, 'bent',    "Doblado de cuchara, eso es original" );
}

Con un bloque todo, se espera que las pruebas internas fallen. Test::More ejecutará las pruebas normalmente, pero imprimirá indicadores especiales indicando que son "todo". Test::Harness interpretará los fallos como correctos. Si algo tiene éxito

TODO TODO: { local $TODO = 1; # tests that are expected to fail } $TODO = "some reason"; TODO: { # tests that are expected to fail for some reason } TODO: { todo_skip $why, $how_many; # tests that are expected to fail for some reason } This feature is designed for those times when you want to test something that you know is going to fail. The most common use is to use it to mark tests that you haven't written yet. For example, if you're testing a module you've just started, you might have a basic test suite, and you want to write tests for things you haven't implemented yet. You can do it like this: use Test::More tests => 10; my $todo_count = 0; ok( 1, "basic test" ); ok( 1, "another basic test" ); # Tests for features we haven't implemented yet TODO: { local $TODO = 1; ok( 0, "feature X not implemented yet" ); $todo_count++; ok( 0, "feature Y not implemented yet" ); $todo_count++; } done_testing($todo_count); This will result in a test script that passes! All of the tests inside the TODO block will be reported as "ok" (even though they might be failing). The output will look like this: ok 1 - basic test ok 2 - another basic test ok 3 - feature X not implemented yet # TODO ok 4 - feature Y not implemented yet # TODO 1..4 Looks ok, (skipped 2 tests, out of 4) The test harness will correctly report that only 4 tests were run. The TODO tests will be reported as TODO. If the TODO tests were to pass (which they shouldn't, since they are tests for code that isn't there yet!), they will be reported as TODO but successful. If you leave $TODO unset or undef, Test::More reports failures as normal. This can be useful to mark the tests as expected to fail only in certain conditions, e.g.: TODO: { local $TODO = "$^O doesn't work yet. :(" if !_os_is_supported($^O); ... } todo_skip TODO: { todo_skip $why, $how_many if $condition; ...normal testing code... } With todo tests, it's best to have the tests actually run. That way you'll know when they start passing. Sometimes this isn't possible. Often a failing test will cause the whole program to die or hang, even inside an "eval BLOCK" with and using "alarm". In these extreme cases you have no choice but to skip over the broken tests entirely. The syntax and behavior is similar to a "SKIP: BLOCK" except the tests will be marked as failing but todo. Test::Harness will interpret them as passing. When do I use SKIP vs. TODO? If it's something the user might not be able to do, use SKIP. This includes optional modules that aren't installed, running under an OS that doesn't have some feature (like fork() or symlinks), or maybe you need an Internet connection and one isn't available. If it's something the programmer hasn't done yet, use TODO. This is for any code you haven't written yet, or bugs you have yet to fix, but want to put tests in your testing script (always a good idea). Test control BAIL_OUT BAIL_OUT($reason); Indicates to the harness that things are going so badly all testing should terminate. This includes the running of any additional test scripts. This is typically used when testing cannot continue such as a critical module failing to compile or a necessary external utility not being available such as a database connection failing. The test will exit with 255. For even better control look at Test::Most. Discouraged comparison functions The use of the following functions is discouraged as they are not actually testing functions and produce no diagnostics to help figure out what went wrong. They were written before is_deeply() existed because I couldn't figure out how to display a useful diff of two arbitrary data structures. These functions are usually used inside an ok(). ok( eq_array(\@got, \@expected) ); is_deeply() can do that better and with diagnostics. is_deeply( \@got, \@expected ); They may be deprecated in future versions. eq_array my $is_eq = eq_array(\@got, \@expected); Checks if two arrays are equivalent. This is a deep check, so multi-level structures are handled correctly. eq_hash my $is_eq = eq_hash(\%got, \%expected); Determines if the two hashes contain the same keys and values. This is a deep check. eq_set my $is_eq = eq_set(\@got, \@expected); Similar to eq_array(), except the order of the elements is *not* important. This is a deep check, but the irrelevancy of order only applies to the top level. ok( eq_set(\@got, \@expected) ); Is better written: is_deeply( [sort @got], [sort @expected] ); *NOTE* By historical accident, this is not a true set comparison. While the order of elements does not matter, duplicate elements do. *NOTE* eq_set() does not know how to deal with references at the top level. The following is an example of a comparison which might not work: eq_set([\1, \2], [\2, \1]); Test::Deep contains much better set comparison functions. Extending and Embedding Test::More Sometimes the Test::More interface isn't quite enough. Fortunately, Test::More is built on top of Test::Builder which provides a single, unified backend for any test library to use. This means two test libraries which both use Test::Builder *can* be used together in the same program. If you simply want to do a little tweaking of how the tests behave, you can access the underlying Test::Builder object like so: builder my $test_builder = Test::More->builder; Returns the Test::Builder object underlying Test::More for you to play with. EXIT CODES If all your tests passed, Test::Builder will exit with zero (which is normal). If anything failed it will exit with how many failed. If you run less (or more) tests than you planned, the missing (or extras) will be considered failures. If no tests were ever run Test::Builder will throw a warning and exit with 255. If the test died, even after having successfully completed all its tests, it will still be considered a failure and will exit with 255. So the exit codes are... 0 all tests successful 255 test died or all passed but wrong # of tests run any other number how many failed (including missing or extras) If you fail more than 254 tests, it will be reported as 254. *NOTE* This behavior may go away in future versions. COMPATIBILITY Test::More works with Perls as old as 5.8.1. Thread support is not very reliable before 5.10.1, but that's because threads are not very reliable before 5.10.1. Although Test::More has been a core module in versions of Perl since 5.6.2, Test::More has evolved since then, and not all of the features you're used to will be present in the shipped version of Test::More. If you are writing a module, don't forget to indicate in your package metadata the minimum version of Test::More that you require. For instance, if you want to use done_testing() but want your test script to run on Perl 5.10.0, you will need to explicitly require Test::More > 0.88. Key feature milestones include: subtests Subtests were released in Test::More 0.94, which came with Perl 5.12.0. Subtests did not implicitly call done_testing() until 0.96; the first Perl with that fix was Perl 5.14.0 with 0.98. done_testing() This was released in Test::More 0.88, and first shipped with Perl in 5.10.1 as part of Test::More 0.92. cmp_ok() Although cmp_ok() was introduced in 0.40, 0.86 fixed an important bug to make it safe for overloaded objects; the fixed first shipped with Perl in 5.10.1 as part of Test::More 0.92. new_ok() note() and explain() These were was released in Test::More 0.82, and first shipped with Perl in 5.10.1 as part of Test::More 0.92. There is a full version history in the Changes file, and the Test::More versions included as core can be found using Module::CoreList: $ corelist -a Test::More CAVEATS and NOTES UTF-8 / "Wide character in print" If you use UTF-8 or other non-ASCII characters with Test::More you might get a "Wide character in print" warning. Using "binmode STDOUT, ":utf8"" will not fix it. Test::Builder (which powers Test::More) duplicates STDOUT and STDERR. So any changes to them, including changing their output disciplines, will not be seen by Test::More. One work around is to apply encodings to STDOUT and STDERR as early as possible and before Test::More (or any other Test module) loads. use open ':std', ':encoding(UTF-8)'; use Test::More; A more direct work around is to change the filehandles used by Test::Builder. my $builder = Test::More->builder; binmode $builder->output, ":encoding(UTF-8)"; binmode $builder->failure_output, ":encoding(UTF-8)"; binmode $builder->todo_output, ":encoding(UTF-8)"; Overloaded objects String overloaded objects are compared *as strings* (or in cmp_ok()'s case, strings or numbers as appropriate to the comparison op). This prevents Test::More from piercing an object's interface allowing better blackbox testing. So if a function starts returning overloaded objects instead of bare strings your tests won't notice the difference. This is good. However, it does mean that functions like is_deeply() cannot be used to test the internals Test::More(3pm)

NAME

Test::More - A Simple Test Suite Framework

SYNOPSIS

    use Test::More tests => 2;
    
    my $foo = 1;
    is($foo, 1, 'foo is 1');
    
    my $bar = 2;
    is($bar, 2, 'bar is 2');

or

    use Test::More qw(plan ok like unlike);
    
    plan_is_plan;
    
    ok(1, 'this is ok');
    ok(0, 'this is not ok');

DESCRIPTION

This module provides a simple, flexible, and easy-to-use testing framework for Perl. It's designed to be lightweight and minimize the amount of boilerplate code required for writing tests.

The primary goal is to make testing as painless as possible, allowing developers to focus on the logic of their code rather than the mechanics of testing.

EXIT CODES

Test::More exits with a status code of 0 if all tests pass, and non-zero otherwise. This behaviour is compatible with standard testing tools like "make test" and "prove".

COMPATIBILITY

Test::More aims for backward compatibility with older versions of Perl where possible. However, certain features or behaviours may depend on newer Perl versions. For detailed compatibility information, refer to the specific documentation or version notes.

CAVEATS and NOTES

String comparison
When comparing strings, be mindful of potential issues with locale settings or character encodings. If you encounter unexpected failures in string comparisons, consider using modules like Test::UTF8 or ensuring consistent encoding throughout your test suite.
Complex data structures
For testing complex nested data structures, such as arrays of hashes or hashes of arrays, the basic comparison functions might not be sufficient. In such cases, consider using modules like Test::Deep, which provides more flexible testing functions for intricate data structures.

Threads
Test::More will only be aware of threads if "use threads" has been done before Test::More is loaded. This is ok: 
use threads;
use Test::More;

This may cause problems:

use Test::More
use threads;

Perl versions 5.8.1 and above are supported. Anything below that has too many bugs.

HISTORY

This module is a result of convergent evolution with Joshua Pritikin's Test module. The author was largely unaware of its existence when the initial routines were written. This module exists because of the perceived difficulty in easily integrating test names into Test's interface (along with a few other issues).

The goal was to create a testing utility that is simple to learn, quick to use, and difficult to misuse, while offering more flexibility than the existing Test.pm. Consequently, the names of the most common routines are kept short, and special cases and magic side effects are minimized. The principle is WYSIWYG (What You See Is What You Get).
