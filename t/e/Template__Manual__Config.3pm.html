NOMBRE

Template::Manual::Config - Opciones de configuración

Opciones de estilo y análisis de plantillas

ENCODING

La opción "ENCODING" especifica la codificación de caracteres de los archivos de plantilla:

my $template = Template->new({
    ENCODING => 'utf8',
});

Una plantilla que comience con una marca de orden de bytes (BOM) Unicode tendrá su codificación detectada automáticamente.

START_TAG, END_TAG

Las opciones "START_TAG" y "END_TAG" se utilizan para especificar secuencias de caracteres o expresiones regulares que marcan el inicio y el final de las directivas de plantilla en línea. Los valores predeterminados para "START_TAG" y "END_TAG" son '"[%' y '"%]"', respectivamente, lo que nos da el estilo de directiva familiar:

[% example %]

Se pueden usar caracteres de expresiones regulares de Perl y, por lo tanto, deben escaparse (o usar la función "quotemeta" de Perl) si se pretende que representen caracteres literales.

my $template = Template->new({
    START_TAG => quotemeta('<+'),
    END_TAG   => quotemeta('+>'),
});

Ejemplo:

<+ INCLUDE foobar +>

La directiva "TAGS" también se puede usar para establecer los valores "START_TAG" y "END_TAG" por archivo de plantilla.

[% TAGS <+ +> %]

OUTLINE_TAG

La opción "OUTLINE_TAG" se puede usar para habilitar directivas de "esquema" de una sola línea.

my $template = Template->new({
    OUTLINE_TAG => '%%',
});

Esto le permite usar etiquetas tanto en línea como de esquema de la siguiente manera:

%% IF user
Hello [% user.name %]
%% END

La cadena (o regex) de "OUTLINE_TAG" debe aparecer al principio de una línea. La directiva continúa hasta el final de la línea. El carácter de nueva línea al final de la línea se considera el marcador invisible de fin de directiva y se elimina.

TAG_STYLE

La opción "TAG_STYLE" se puede usar para establecer tanto "START_TAG" como "END_TAG" según estilos de etiquetas predefinidos.

my $template = Template->new({
    TAG_STYLE => 'star',
});

Los estilos disponibles son:

template    [% ... %]               (predeterminado)
template1   [% ... %] o %% ... %%  (TT versión 1)
metatext    %% ... %%               (Text::MetaText)
star        [* ... *]               (TT alternativo)
php         <? ... ?>               (PHP)
asp         <% ... %>               (ASP)
mason       <% ...  >               (HTML::Mason)
html        <!-- ... -->            (Comentarios HTML)

El estilo "outline" utiliza los marcadores predeterminados para "START_TAG" y "END_TAG" ("[%' y "%]"', respectivamente) y además define "OUTLINE_TAG" como "%%".

my $template = Template->new({
    TAG_STYLE => 'outline',
});

Esto le permite usar etiquetas tanto en línea como de esquema de la siguiente manera:

%% IF user
Hello [% user.name %]
%% END

Cualquier valor especificado para "START_TAG", "END_TAG" y/o "OUTLINE_TAG" anulará los definidos por un "TAG_STYLE".

La directiva "TAGS" también puede usarse para establecer un "TAG_STYLE"

[% TAGS html %]
<!-- INCLUDE header -->

PRE_CHOMP, POST_CHOMP

Todo lo que esté fuera de las etiquetas de directiva se considera texto plano y, en general, se pasa sin cambios (pero consulte la opción INTERPOLATE). Esto incluye todos los caracteres de espacio en blanco y nueva línea que rodean las etiquetas de directiva. Las directivas que no generan ninguna salida dejarán huecos en el documento de salida.

Ejemplo:

Foo
[% a = 10 %]
Bar

Salida:

Foo
Bar

Las opciones "PRE_CHOMP" y "POST_CHOMP" pueden ayudar a limpiar parte de este espacio en blanco extralegal. Ambas están deshabilitadas por defecto.

my $template = Template->new({
    PRE_CHOMP  => 1,
    POST_CHOMP => 1,
});

Con "PRE_CHOMP" establecido en 1, se eliminará el salto de línea y el espacio en blanco previos a una directiva al principio de una línea. Esto tiene el efecto de concatenar una línea que comienza con una directiva al final de la línea anterior.

    Foo <----------.
                   |
,---(PRE_CHOMP)----'
|
`-- [% a = 10 %] --.
                   |
,---(POST_CHOMP)---'
|
`-> Bar

Con "POST_CHOMP" establecido en 1, se eliminará cualquier espacio en blanco después de una directiva hasta el salto de línea inclusive. Esto tiene el efecto de unir una línea que termina con una directiva al comienzo de la siguiente línea.

Si "PRE_CHOMP" o "POST_CHOMP" se establece en 2, todo el espacio en blanco, incluido cualquier número de saltos de línea, se eliminará y se reemplazará por un solo espacio. Esto es útil para HTML, donde (generalmente) un bloque contiguo de espacio en blanco se representa igual que un solo espacio.

Con "PRE_CHOMP" o "POST_CHOMP" establecido en 3, todo el espacio en blanco adyacente (incluidos los saltos de línea) se eliminará por completo.

Estos valores se definen como las constantes "CHOMP_NONE", "CHOMP_ONE", "CHOMP_COLLAPSE" y "CHOMP_GREEDY" en el módulo Template::Constants. "CHOMP_ALL" también se define como un alias para "CHOMP_ONE" para proporcionar compatibilidad con versiones anteriores del Toolkit de Plantillas.

Además, los modificadores de etiqueta chomp que se enumeran a continuación también se pueden utilizar para la configuración "PRE_CHOMP" y "POST_CHOMP".

my $template = Template->new({
   PRE_CHOMP  => '~',
   POST_CHOMP => '-',
});

"PRE_CHOMP" y "POST_CHOMP" se pueden activar para directivas individuales colocando un '"-"' inmediatamente al principio y/o al final de la directiva.

[% FOREACH user IN userlist %]
   [%- user -%]
[% END %]

Esto tiene el mismo efecto que "CHOMP_ONE" al eliminar todo el espacio en blanco antes o después de la directiva hasta el salto de línea inclusive. La plantilla se procesará como si estuviera escrita:

[% FOREACH user IN userlist %][% user %][% END %]

Para eliminar todo el espacio en blanco, incluidos varios saltos de línea, use en su lugar el carácter de tilde ('"~"').

[% FOREACH user IN userlist %]
   [%~ user ~%]
[% END %]

Para colapsar todo el espacio en blanco a un solo espacio, use el signo igual ('"="').

[% FOREACH user IN userlist %]
   [%= user =%]
[% END %]

Aquí la plantilla se procesa como si estuviera escrita:

[% FOREACH user IN userlist %] [% user %] [% END %]

Si tiene "PRE_CHOMP" o "POST_CHOMP" establecido como opciones de configuración, entonces puede usar el signo más ('"+"') para deshabilitar cualquier opción de chomping (es decir, dejar el espacio en blanco intacto) en una base por directiva.

[% FOREACH user IN userlist %]
User: [% user +%]
[% END %]

Directivas de Configuración de Plantillas

La siguiente es una lista de opciones que se pueden pasar al constructor Template->new() para configurar el comportamiento del procesador de plantillas.

INCLUDE_PATH

El "INCLUDE_PATH" es un parámetro que se utiliza para buscar plantillas de forma recursiva. Puede especificarse como un solo nombre de directorio, un separador de ruta de Perl (por ejemplo, ':' en Unix o ';' en Windows) o una lista de directorios.

Las rutas pueden ser absolutas o relativas al directorio de trabajo actual.

my $template = Template->new({
    INCLUDE_PATH => '/usr/local/templates/main',
});

my $template = Template->new({
    INCLUDE_PATH => 'lib/templates',
});

my $template = Template->new({
    INCLUDE_PATH => [
        '/usr/local/templates/main',
        '/usr/local/templates/lib',
        'templates',
    ],
});

Si no se especifica un "INCLUDE_PATH", el procesador de plantillas buscará en el directorio de trabajo actual.

LOAD_PATT

El "LOAD_PATT" es una expresión regular que se utiliza para identificar qué plantillas se cargan desde un archivo de entrada dado. El valor predeterminado es '^([\w\/\-]+)$', que coincide con los nombres de archivo que solo contienen caracteres alfanuméricos, barras inclinadas y guiones.

Se utiliza internamente para la carga de plantillas y no suele ser necesario modificarlo.

COMPILE_DIR

El "COMPILE_DIR" puede configurarse para especificar un directorio donde se almacenarán las plantillas compiladas. Esto permite que el procesador de plantillas reutilice las plantillas compiladas de operaciones anteriores, lo que acelera significativamente el procesamiento de plantillas. Si no se especifica, las plantillas se mantendrán en memoria.

my $template = Template->new({
    COMPILE_DIR => '/var/tmp/ttc',
});

El directorio especificado debe ser escribible por el proceso que ejecuta el script de Perl.

TMPL_SHIFT

Si se establece en un valor verdadero, el "TMPL_SHIFT" permite que el procesador de plantillas elimine el prefijo del nombre de archivo de las plantillas especificadas con "INCLUDE" o "PROCESS", y las busque en el "INCLUDE_PATH" como si el nombre del archivo estuviera predefinido por el "TMPL_SHIFT".

Por ejemplo, si "TMPL_SHIFT" está configurado como "views/", entonces una directiva [% INCLUDE views/main %] se buscaría en el "INCLUDE_PATH" como "main.tt".

Esto es útil para organizar plantillas en subdirectorios, pero tratarlas como si estuvieran en el directorio raíz del "INCLUDE_PATH".

DEFAULT

Esta opción permite especificar un nombre de plantilla predeterminado que se procesará si no se especifica ninguna plantilla (por ejemplo, si se llama a process() sin argumentos).

my $template = Template->new({
    DEFAULT => 'default_page.tt',
});

Sin embargo, si el procesador de plantillas encuentra una directiva "DEFAULT" dentro de una plantilla, entonces esa directiva prevalecerá sobre el parámetro "DEFAULT" proporcionado al constructor, y la plantilla especificada en la directiva será procesada en su lugar. Si la directiva "RAPPER" está definida, entonces la plantilla "DEFAULT" se procesará en su lugar, si está definida. Ten en cuenta que la plantilla "DEFAULT" no se utiliza cuando las plantillas se especifican con nombres de archivo absolutos o relativos, o como una referencia a un manejador de archivo de entrada o cadena de texto.

BLOCKS

La opción "BLOCKS" se puede utilizar para predefinir un conjunto predeterminado de bloques de plantillas. Estos deben especificarse como una referencia a un array hash que mapea nombres de plantilla a texto de plantilla, subrutinas u objetos Template::Document.

my $template = Template->new({
    BLOCKS => {
        header  => 'La Cabecera.  [% title %]',
        footer  => sub { return $some_output_text },
        another => Template::Document->new({ ... }),
    },
});

VIEWS

La opción VIEWS se puede utilizar para definir uno o más objetos Template::View. Se pueden especificar como una referencia a un array hash o una referencia de lista.

my $template = Template->new({
    VIEWS => {
        my_view => { prefix => 'my_templates/' },
    },
});

Ten en cuenta que los arrays hash de Perl no están ordenados, por lo que si deseas especificar múltiples vistas de las cuales una o más se basan en otras vistas, deberías usar una referencia de lista para preservar el orden de definición.

my $template = Template->new({
    VIEWS => [
        bottom => { prefix => 'bottom/' },
        middle => { prefix => 'middle/', base => 'bottom' },
        top    => { prefix => 'top/',    base => 'middle' },
    ],
});

AUTO_RESET

La opción "AUTO_RESET" está establecida por defecto y hace que la caché local de "BLOCKS" para el objeto Template::Context se reinicie en cada llamada al método process() de Template. Esto asegura que cualquier "BLOCK" definido dentro de una plantilla solo persistirá hasta que esa plantilla termine de procesarse. Esto evita que los "BLOCK"s definidos en una solicitud de procesamiento interfieran con otras solicitudes independientes procesadas posteriormente por el mismo objeto de contexto.

El elemento "BLOCKS" puede usarse para especificar un conjunto predeterminado de definiciones de bloques para el objeto Template::Context. Las definiciones posteriores de "BLOCK" en las plantillas anularán estas, pero se restablecerán en cada reinicio si "AUTO_RESET" está habilitado (por defecto), o si se llama al método reset() de Template::Context.

RECURSION

El procesador de plantillas generará una excepción de archivo si detecta recursión directa o indirecta en una plantilla. Establecer esta opción a cualquier valor verdadero permitirá que las plantillas se incluyan recursivamente entre sí.

Variables de Plantilla

VARIABLES

La opción "VARIABLES" (o "PRE_DEFINE" - son equivalentes) se puede usar para especificar un array hash de variables de plantilla que se utilizarán para preinicializar el stash cuando se cree. Estos elementos se ignoran si el elemento "STASH" está definido.

my $template = Template->new({
    VARIABLES => {
        title   => 'Una Página de Demostración',
        author  => 'Joe Hacker Aleatorio',
        version => 3.14,
    },
};

o

my $template = Template->new({
    PRE_DEFINE => {
        title   => 'Una Página de Demostración',
        author  => 'Joe Hacker Aleatorio',
        version => 3.14,
    },
};

CONSTANTS

La opción "CONSTANTS" se puede usar para especificar un array hash de variables de plantilla que son constantes en tiempo de compilación. Estas variables se resuelven una vez cuando la plantilla se compila, y por lo tanto no requieren una resolución adicional en tiempo de ejecución. Esto resulta en un procesamiento significativamente más rápido de las plantillas compiladas y se puede usar para variables que no cambian de una solicitud a la siguiente.

my $template = Template->new({
    CONSTANTS => {
        title   => 'Una Página de Demostración',
        author  => 'Joe Hacker Aleatorio',
        version => 3.14,
    },
};

CONSTANT_NAMESPACE

Las variables constantes se acceden por defecto a través del espacio de nombres "constants".

[% constants.title %]

La opción "CONSTANTS_NAMESPACE" se puede establecer para especificar un espacio de nombres alternativo.

my $template = Template->new({
    CONSTANTS => {
        title   => 'Una Página de Demostración',
        # ...etc...
    },
    CONSTANTS_NAMESPACE => 'const',
};

En este caso, las constantes se accederían como:

[% const.title %]

NAMESPACE

El mecanismo de plegado de constantes descrito anteriormente es un ejemplo de un manejador de espacios de nombres. Los manejadores de espacios de nombres se pueden definir para proporcionar mecanismos de análisis alternativos para variables en diferentes espacios de nombres.

Bajo el capó, el módulo Template convierte una configuración de constructor como:

my $template = Template->new({
    CONSTANTS => {
        title   => 'Una Página de Demostración',
        # ...etc...
    },
    CONSTANTS_NAMESPACE => 'const',
};

en una como:

my $template = Template->new({
    NAMESPACE => {
        const => Template:::Namespace::Constants->new({
            title   => 'Una Página de Demostración',
            # ...etc...
        }),
    },
};

Puede usar este mecanismo para definir múltiples espacios de nombres constantes, o para instalar sus propios manejadores personalizados.

my $template = Template->new({
    NAMESPACE => {
        site => Template:::Namespace::Constants->new({
            title   => "Widgets de Wardley",
            version => 2.718,
        }),
        author => Template:::Namespace::Constants->new({
            name  => 'Andy Wardley',
            email => 'abw@andywardley.com',
        }),
        voodoo => My::Namespace::Handler->new( ... ),
    },
};

Ahora tiene dos espacios de nombres constantes, por ejemplo:

[% site.title %]
[% author.name %]

así como su propio manejador de espacios de nombres personalizado instalado para el espacio de nombres 'voodoo'.

[% voodoo.magic %]

Vea Template::Namespace::Constants para un ejemplo de cómo se ve un manejador de espacios de nombres por dentro.

Opciones de Procesamiento de Plantillas

Las siguientes opciones se utilizan para especificar cualquier plantilla adicional que deba procesarse antes, después, alrededor o en lugar de la plantilla pasada como primer argumento al método process() de Template. Estas opciones pueden realizar varias tareas útiles, como agregar cabeceras o pies de página estándar a todas las páginas, envolver la salida de la página en otras plantillas, predefinir variables o realizar tareas de inicialización o limpieza, generar automáticamente información de resumen de página, elementos de navegación, etc.

La tarea de procesar la plantilla se delega internamente al módulo Template::Service que, como era de esperar, también tiene un método process(). Cualquier plantilla definida por la opción "PRE_PROCESS" se procesa primero y cualquier salida generada se agrega al búfer de salida. Luego se procesa la plantilla principal, o si se definen una o más plantillas "PROCESS", entonces estas se procesan en turno. En este caso, una de las plantillas "PROCESS" es responsable de procesar la plantilla principal, mediante una directiva como:

[% PROCESS $template %]

La salida del procesamiento de la plantilla principal o de las plantillas "PROCESS" se envuelve en cualquier plantilla "WRAPPER", si está definida. Las plantillas "WRAPPER" no necesitan preocuparse por procesar explícitamente la plantilla porque ya se habrá hecho por ellas. En su lugar, las plantillas "WRAPPER" acceden al contenido que están envolviendo a través de la variable "content".

wrapper before
[% content %]
wrapper after

La salida generada al procesar la plantilla principal y/o cualquier plantilla "PROCESS" o "WRAPPER" se agrega al búfer de salida. Finalmente, se procesan las plantillas "POST_PROCESS" y su salida también se agrega al búfer de salida, que luego se devuelve.

Si la plantilla principal genera una excepción durante el procesamiento, se procesarán en su lugar las plantillas relevantes definidas a través de la opción "ERROR". Si se define y se procesa con éxito, la salida de la plantilla de error se agregará al búfer de salida en lugar de la plantilla que generó el error y el procesamiento continuará, aplicando cualquier plantilla "WRAPPER" y "POST_PROCESS". Si no se define ninguna opción "ERROR" relevante, o si el error ocurre en una de las plantillas "PRE_PROCESS", "WRAPPER" o "POST_PROCESS", el proceso terminará inmediatamente y se devolverá el error.

PRE_PROCESS, POST_PROCESS

Estos valores pueden establecerse para contener el(los) nombre(s) de archivos de plantilla (relativos a "INCLUDE_PATH") que deben procesarse inmediatamente antes y/o después de cada plantilla. Estos no se agregan a las plantillas procesadas en un documento a través de directivas como "INCLUDE", "PROCESS", "WRAPPER", etc.

my $template = Template->new({
    PRE_PROCESS  => 'header',
    POST_PROCESS => 'footer',
};

OPTIONS

The Template Toolkit accepts a wide range of configuration options, which can be specified as a hash reference when creating a new Template object.

PRE_PROCESS / POST_PROCESS

The "PRE_PROCESS" and "POST_PROCESS" options may be used to specify one or more template files that should be processed before and after, respectively, the main template document.

If multiple template files are specified as a list (i.e. a reference to an array), they are processed in the order defined.

my $template = Template->new({
    PRE_PROCESS  => [ 'config', 'header' ],
    POST_PROCESS => 'footer',
};

Alternately, multiple template may be specified as a single string, delimited by '":"'. This delimiter string can be changed via the "DELIMITER" option.

my $template = Template->new({
    PRE_PROCESS  => 'config:header',
    POST_PROCESS => 'footer',
};

The "PRE_PROCESS" and "POST_PROCESS" templates are evaluated in the same variable context as the main document and may define or update variables for subsequent use.

config:

[% # set some site-wide variables
   bgcolor = '#ffffff'
   version = 2.718
%]

header:

[% DEFAULT title = 'My Funky Web Site' %]
<html>
  <head>
    <title>[% title %]</title>
  </head>
  <body bgcolor="[% bgcolor %]">

footer:

    <hr>
    Version [% version %]
  </body>
</html>

The Template::Document object representing the main template being processed is available within "PRE_PROCESS" and "POST_PROCESS" templates as the "template" variable. Metadata items defined via the "META" directive may be accessed accordingly.

$template->process('mydoc.html', $vars);

mydoc.html:

[% META title = 'My Document Title' %]
blah blah blah
...

header:

<html>
  <head>
    <title>[% template.title %]</title>
  </head>
  <body bgcolor="[% bgcolor %]">

PROCESS

The "PROCESS" option may be set to contain the name(s) of template files (relative to "INCLUDE_PATH") which should be processed instead of the main template passed to the Template process() method. This can be used to apply consistent wrappers around all templates, similar to the use of "PRE_PROCESS" and "POST_PROCESS" templates.

my $template = Template->new({
    PROCESS  => 'content',
};
# processes 'content' instead of 'foo.html'
$template->process('foo.html');

A reference to the original template is available in the "template" variable. Metadata items can be inspected and the template can be processed by specifying it as a variable reference (i.e. prefixed by "$") to an "INCLUDE", "PROCESS" or "WRAPPER" directive.

content:

<html>
  <head>
    <title>[% template.title %]</title>
  </head>
  <body>
<!-- begin content -->
[% PROCESS $template %]
<!-- end content -->
    <hr>
    &copy; Copyright [% template.copyright %]
  </body>
</html>

foo.html:

[% META
   title     = 'The Foo Page'
   author    = 'Fred Foo'
   copyright = '2000 Fred Foo'
%]
<h1>[% template.title %]</h1>
Welcome to the Foo Page, blah blah blah

output:

<html>
  <head>
    <title>The Foo Page</title>
  </head>
  <body>
<!-- begin content -->
<h1>The Foo Page</h1>
Welcome to the Foo Page, blah blah blah
<!-- end content -->
    <hr>
    &copy; Copyright 2000 Fred Foo
  </body>
</html>

WRAPPER

The "WRAPPER" option can be used to specify one or more templates which should be used to wrap around the output of the main page template. The main template is processed first (or any "PROCESS" template(s)) and the output generated is then passed as the "content" variable to the "WRAPPER" template(s) as they are processed.

my $template = Template->new({
    WRAPPER => 'wrapper',
};
# process 'foo' then wrap in 'wrapper'
$template->process('foo', { message => 'Hello World!' });

wrapper:

<wrapper>
[% content %]
</wrapper>

foo:

This is the foo file!
Message: [% message %]

The output generated from this example is:

<wrapper>
This is the foo file!
Message: Hello World!
</wrapper>

You can specify more than one "WRAPPER" template by setting the value to be a reference to a list of templates. The "WRAPPER" templates will be processed in reverse order with the output of each being passed to the next (or previous, depending on how you look at it) as the 'content' variable. It sounds complicated, but the end result is that it just "Does The Right Thing" to make wrapper templates nest in the order you specify.

my $template = Template->new({
    WRAPPER => [ 'outer', 'inner' ],
};
# process 'foo' then wrap in 'inner', then in 'outer'
$template->process('foo', { message => 'Hello World!' });

outer:

<outer>
[% content %]
</outer>

inner:

<inner>
[% content %]
</inner>

The output generated is then:

<outer>
<inner>
This is the foo file!
Message: Hello World!
</inner>
</outer>

One side-effect of the "inside-out" processing of the "WRAPPER" configuration item (and also the "WRAPPER" directive) is that any variables set in the template being wrapped will be visible to the template doing the wrapping, but not the other way around.

You can use this to good effect in allowing page templates to set pre-defined values which are then used in the wrapper templates. For example, our main page template 'foo' might look like this:

foo:

[% page = {
       title    = 'Foo Page'
       subtitle = 'Everything There is to Know About Foo'
       author   = 'Frank Oliver Octagon'
   }
%]
<p>
Welcome to the page that tells you everything about foo
blah blah blah...
</p>

The "foo" template is processed before the wrapper template meaning that the "page" data structure will be defined for use in the wrapper template.

wrapper:

<html>
  <head>
    <title>[% page.title %]</title>
  </head>
  <body>
    <h1>[% page.title %]</h1>
    <h2>[% page.subtitle %]</h1>
    <h3>by [% page.author %]</h3>
    [% content %]
  </body>
</html>

It achieves the same effect as defining "META" items which are then accessed via the "template" variable (which you are still free to use within "WRAPPER" templates), but gives you more flexibility in the type and complexity of data that you can define.

ERROR

The "ERROR" (or "ERRORS" if you prefer) configuration item can be used to name a single template or specify a hash array mapping exception types to templates which should be used for error handling. If an uncaught exception is raised from within a template then the appropriate error template will instead be processed.

If specified as a single value then that template will be processed for all uncaught exceptions.

my $template = Template->new({
    ERROR => 'error.html'
});

If the "ERROR" item is a hash reference the keys are assumed to be exception types and the relevant template for a given exception will be selected. A "default" template may be provided for the general case. Note that "ERROR" can be pluralised to "ERRORS" if you find it more appropriate in this case.

my $template = Template->new({
    ERRORS => {
        user     => 'user/index.html',
        dbi      => 'error/database',
        default  => 'error/default',
    },
});

In this example, any "user" exceptions thrown will cause the user/index.html template to be processed, "dbi" errors are handled by error/database and all others by the error/default template. Any "PRE_PROCESS" and/or "POST_PROCESS" templates will also be applied to these error templates.

Note that exception types are hierarchical and a "foo" handler will catch all "foo.*" errors (e.g. "foo.bar", "foo.bar.baz") if a more specific handler isn't defined. Be sure to quote any exception types that contain periods to prevent Perl concatenating them into a single string (i.e. "user.passwd" is parsed as 'user'.'passwd').

my $template = Template->new({
    ERROR => {
        'user.login'  => 'user/login.html',
        'user.passwd' => 'user/badpasswd.html',
        'user'        => 'user/index.html',
        'default'     => 'error/default',
    },
});

In this example, any template processed by the $template object, or other templates or code called from within, can raise a "user.login" exception and have the service redirect to the user/login.html template. Similarly, a "user.passwd" exception has a specific handling template, user/badpasswd.html, while all other "user" or "user.*" exceptions cause a redirection to the user/index.html page. All other exception types are handled by error/default.

Exceptions can be raised in a template using the "THROW" directive,

[% THROW user.login 'no user id: please login' %]

or by calling the throw() method on the current Template::Context object,

$context->throw('user.passwd', 'Incorrect Password');
$context->throw('Incorrect Password');
# tipo 'undef'

o desde código Perl llamando a die() con un objeto Template::Exception,

die (Template::Exception->new('user.denied', 'ID de usuario inválido'));

o simplemente llamando a die() con una cadena de error. Esto se captura automáticamente y se convierte en una excepción de tipo '"undef"' que luego puede ser manejada de la manera habitual.

die "Lo siento Dave, no puedo hacer eso";

Tenga en cuenta que el '"undef"' del que estamos hablando aquí es una cadena literal en lugar del "undef" de Perl utilizado para representar valores indefinidos.

Opciones de ejecución de Plantillas

EVAL_PERL

Este flag se utiliza para indicar si los bloques "PERL" y/o "RAWPERL" deben ser evaluados. Está deshabilitado por defecto y cualquier bloque "PERL" o "RAWPERL" encontrado generará excepciones de tipo '"perl"' con el mensaje '"EVAL_PERL no establecido"'. Tenga en cuenta, sin embargo, que los bloques "RAWPERL" siempre deben contener código Perl válido, independientemente del flag "EVAL_PERL". El analizador fallará al compilar plantillas que contengan código Perl inválido en bloques "RAWPERL" y lanzará una excepción de tipo '"file"'.

Al usar plantillas compiladas (ver "Opciones de Caché y Compilación"), "EVAL_PERL" tiene un efecto cuando se compila la plantilla, y de nuevo cuando la plantilla se procesa posteriormente, posiblemente en un contexto diferente al que la compiló.

Si "EVAL_PERL" se establece cuando se compila una plantilla, entonces todos los bloques "PERL" y "RAWPERL" se incluirán en la plantilla compilada. Si la opción "EVAL_PERL" no está establecida, se generará código Perl que siempre lanzará una excepción '"perl"' con el mensaje '"EVAL_PERL no establecido"' cada vez que se ejecute el código de la plantilla compilada.

Por lo tanto, debe tener "EVAL_PERL" establecido si desea que sus plantillas compiladas incluyan bloques "PERL" y "RAWPERL".

En algún momento en el futuro, al usar una invocación diferente de Template Toolkit, puede que procese una plantilla precompilada. Suponiendo que la opción "EVAL_PERL" se estableció en el momento en que se compiló la plantilla, la salida de cualquier bloque "RAWPERL" se incluirá en la plantilla compilada y se ejecutará cuando se procese la plantilla. Esto sucederá independientemente del estado de "EVAL_PERL" en tiempo de ejecución.

Sin embargo, los bloques "PERL" regulares son un poco más cautelosos. Si el flag "EVAL_PERL" no está establecido para el contexto *actual*, es decir, el que intenta procesarlo, lanzará la familiar excepción '"perl"' con el mensaje '"EVAL_PERL no establecido"'.

Así, puede compilar plantillas para incluir bloques "PERL", pero deshabilitarlos opcionalmente cuando las procese más tarde. Tenga en cuenta, sin embargo, que es posible que un bloque "PERL" contenga un bloque Perl de tipo ""BEGIN { # algún código }"" que siempre se ejecutará independientemente del estado de "EVAL_PERL" en tiempo de ejecución. Por lo tanto, si establece "EVAL_PERL" al compilar plantillas, se asume que confía en que las plantillas harán lo correcto. De lo contrario, debe aceptar el hecho de que no hay una forma infalible de evitar que cualquier código incluido hurgue en la sala de estar del entorno de ejecución, causando una verdadera molestia si realmente quiere hacerlo. Si no le gusta la idea de que invitados no deseados causen problemas, puede aceptar el valor predeterminado y mantener "EVAL_PERL" deshabilitado.

SALIDA

Ubicación o manejador de salida por defecto. Esto puede especificarse como: un nombre de archivo (relativo a "OUTPUT_PATH", si está definido, o el directorio de trabajo actual si no se especifica de forma absoluta); un manejador de archivo (por ejemplo, "GLOB" o IO::Handle) abierto para escritura; una referencia a una cadena de texto a la que se agrega la salida (la cadena no se borra); una referencia a una subrutina que se llama, pasando el texto de salida como argumento; como referencia a un array, al que se le hará push() el contenido; o como referencia a cualquier objeto que soporte el método print(). Esta última opción incluye el objeto "Apache::Request" que se pasa como argumento a los manejadores de Apache/mod_perl.

ejemplo 1 (nombre de archivo):

my $template = Template->new({
    SALIDA => "/tmp/foo",
});

ejemplo 2 (cadena de texto):

my $output   = '';
my $template = Template->new({
    SALIDA => \$output,
});

ejemplo 3 (manejador de archivo):

open (TOUT, ">", $file) || die "$file: $!\n";
my $template = Template->new({
    SALIDA => \*TOUT,
});

ejemplo 4 (subrutina):

sub output { my $out = shift; print "SALIDA: $out" }
my $template = Template->new({
    SALIDA => \&output,
});

ejemplo 5 (referencia a array):

my $template = Template->new({
    SALIDA => \@output,
})

ejemplo 6 (manejador Apache/mod_perl):

sub handler {
    my $r = shift;
    my $t = Template->new({
        SALIDA => $r,
    });
    ...
}

La ubicación de "SALIDA" por defecto puede ser anulada pasando un tercer parámetro al método process() de Template. Esto puede especificarse como cualquiera de los tipos de argumento anteriores.

$t->process($file, $vars, "/tmp/foo");
$t->process($file, $vars, \$output);
$t->process($file, $vars, \*MYGLOB);
$t->process($file, $vars, \@output);
$t->process($file, $vars, $r);  # Apache::Request
...

RUTA_DE_SALIDA

"RUTA_DE_SALIDA" permite especificar un directorio en el que se escribirán los archivos de salida. Un archivo de salida puede ser especificado por la opción "SALIDA", o pasado por nombre como tercer parámetro al método process() de Template.

my $template = Template->new({
    RUTA_INCLUSION => "/tmp/src",
    RUTA_SALIDA  => "/tmp/dest",
});
my $vars = {
    ...
};
foreach my $file ('foo.html', 'bar.html') {
    $template->process($file, $vars, $file)
        || die $template->error();
}

Este ejemplo leerá los archivos de entrada /tmp/src/foo.html y /tmp/src/bar.html y escribirá la salida procesada en /tmp/dest/foo.html y /tmp/dest/bar.html, respectivamente.

ESTRICTO

Por defecto, Template Toolkit ignorará silenciosamente el uso de variables indefinidas (una mala decisión de diseño que lamento).

Cuando la opción "ESTRICTO" está establecida, el uso de cualquier variable o valor indefinido provocará el lanzamiento de una excepción. La excepción tendrá un "tipo" de "var.undef" y un mensaje de la forma "variable indefinida: xxx".

my $template = Template->new(
    ESTRICTO => 1
);

Las siguientes opciones se pueden utilizar para habilitar y controlar la salida de mensajes de depuración de los componentes del Template Toolkit.

DEBUG
Este es un alias para la opción "DEBUG_DIRS".

El fragmento de plantilla de ejemplo:

Hola Mundo

generaría esta salida:

Como puede ver, cada línea del texto de entrada está precedida por un comentario que indica el nombre del archivo (si está disponible) y el número de línea, seguido del contenido de esa línea.

[% DEBUG template.html, 'includes/' %]

Opciones de caché y compilación

CACHE_SIZE

El módulo Template::Provider almacena en caché las plantillas compiladas para evitar la necesidad de volver a analizar archivos o bloques de plantillas cada vez que se utilizan. La opción "CACHE_SIZE" se utiliza para limitar el número de plantillas compiladas que el módulo debe almacenar en caché.

Por defecto, "CACHE_SIZE" no está definido y se almacenan en caché todas las plantillas compiladas. Cuando se establece en cualquier valor positivo, la caché se limitará a almacenar no más de ese número de plantillas compiladas. Cuando se carga y compila una nueva plantilla y la caché está llena (es decir, el número de entradas == "CACHE_SIZE"), la plantilla compilada utilizada con menos frecuencia se descarta para dar paso a la nueva.

La opción "CACHE_SIZE" se puede establecer en 0 para deshabilitar la caché por completo.

my $template = Template->new({
    CACHE_SIZE => 64,   # solo almacenar en caché 64 plantillas compiladas
});
my $template = Template->new({
    CACHE_SIZE => 0,   # no almacenar en caché ninguna plantilla compilada
});

Además de almacenar en caché las plantillas a medida que se encuentran, Template::Provider también implementa el almacenamiento en caché negativo para mantener un registro de las plantillas que *no* se encuentran. Esto permite al proveedor rechazar rápidamente una solicitud de una plantilla que no ha podido localizar previamente, ahorrando el esfuerzo de buscarla de nuevo. Esto es útil cuando una "INCLUDE_PATH" incluye varios proveedores, asegurando que la solicitud se pase a través de los proveedores lo más rápido posible.

STAT_TTL

Este valor se puede establecer para controlar cuánto tiempo conservará Template::Provider una plantilla en caché en la memoria antes de comprobar si la plantilla de origen ha cambiado.

my $provider = Template::Provider->new({
    STAT_TTL => 60,  # un minuto
});

El valor predeterminado es 1 (segundo). Probablemente querrá establecer un valor más alto si ejecuta Template Toolkit dentro de una aplicación de servidor web persistente (por ejemplo, mod_perl). Por ejemplo, establécelo en 60 y el proveedor solo buscará cambios en las plantillas una vez por minuto como máximo. Sin embargo, durante el desarrollo (o en cualquier momento en que realice cambios frecuentes en las plantillas) probablemente querrá mantenerlo en un valor bajo para no tener que esperar a que el proveedor note que sus plantillas han cambiado.

COMPILE_EXT

A partir de la versión 2, Template Toolkit tiene la capacidad de compilar plantillas a código Perl y guardarlas en disco para su uso posterior (es decir, persistencia de caché). La opción "COMPILE_EXT" se puede proporcionar para especificar una extensión de nombre de archivo para los archivos de plantilla compilada. No está definida por defecto y no se intentará leer ni escribir ningún archivo de plantilla compilada.

my $template = Template->new({
    COMPILE_EXT => '.ttc',
});

Si "COMPILE_EXT" está definida (y "COMPILE_DIR" no lo está, véase más abajo), entonces los archivos de plantilla compilada con la extensión "COMPILE_EXT" se escribirán en el mismo directorio desde el que se cargaron los archivos de plantilla de origen.

La compilación y reutilización posterior de plantillas ocurre automáticamente cada vez que se establecen las opciones "COMPILE_EXT" o "COMPILE_DIR". Template Toolkit recargará y reutilizará automáticamente los archivos compilados cuando los encuentre en el disco. Si el archivo de origen correspondiente se ha modificado desde que se escribió la versión compilada, cargará y recompilará el origen y escribirá una nueva versión compilada en el disco.

Esta forma de persistencia de caché ofrece beneficios significativos en términos de tiempo y recursos necesarios para recargar plantillas. Las plantillas compiladas pueden ser recargadas por una simple llamada a require() de Perl, dejando que Perl se encargue de todo el análisis y la compilación. Esto es algo bueno.

COMPILE_DIR

La opción "COMPILE_DIR" se utiliza para especificar un directorio raíz alternativo bajo el cual se deben guardar los archivos de plantilla compilada.

my $template = Template->new({
    COMPILE_DIR => '/tmp/ttc',
});

La opción "COMPILE_EXT" también se puede especificar para añadir una extensión de archivo consistente a estos archivos.

my $template1 = Template->new({
    COMPILE_DIR => '/tmp/ttc',
    COMPILE_EXT => '.ttc1',
});
my $template2 = Template->new({
    COMPILE_DIR => '/tmp/ttc',
    COMPILE_EXT => '.ttc2',
});

Cuando "COMPILE_EXT" no está definido, los archivos de plantilla compilada tienen el mismo nombre que los archivos de plantilla originales, pero residen en un árbol de directorios diferente.

Cada directorio en "INCLUDE_PATH" se replica completamente debajo del directorio "COMPILE_DIR". Este ejemplo:

my $template = Template->new({
    COMPILE_DIR  => '/tmp/ttc',
    INCLUDE_PATH => '/home/abw/templates:/usr/share/templates',
});

crearía la siguiente estructura de directorios:

/tmp/ttc/home/abw/templates/
/tmp/ttc/usr/share/templates/

Los archivos cargados desde diferentes directorios de "INCLUDE_PATH" tendrán sus formas compiladas guardadas en el directorio "COMPILE_DIR" relevante.

En plataformas Win32, un nombre de archivo puede ir precedido de una letra de unidad y dos puntos. Por ejemplo:

C:/My Templates/header

Los dos puntos se eliminarán silenciosamente del nombre del archivo cuando se añadan a los valores de "COMPILE_DIR" para evitar la generación de nombres de archivo ilegales. Cualquier dos puntos en los elementos de "COMPILE_DIR" se dejarán intactos. Por ejemplo:

# Solo Win32
my $template = Template->new({
    DELIMITER    => ';',
    COMPILE_DIR  => 'C:/TT2/Cache',
    INCLUDE_PATH => 'C:/TT2/Templates;D:/My Templates',
});

Esto crearía los siguientes directorios de caché:

C:/TT2/Cache/C/TT2/Templates
C:/TT2/Cache/D/My Templates

Plugins y filtros

PLUGINS

La opción "PLUGINS" se puede utilizar para proporcionar una referencia a una matriz hash que mapea nombres de plugins a nombres de módulos Perl. Se definen varios plugins estándar (por ejemplo, "table", "format", "cgi", etc.) que se mapean a sus contrapartes "Template::Plugin::*" correspondientes. Estos pueden ser redefinidos por valores en el hash "PLUGINS".

my $template = Template->new({
    PLUGINS => {
        cgi => 'MyOrg::Template::Plugin::CGI',
        foo => 'MyOrg::Template::Plugin::Foo',
        bar => 'MyOrg::Template::Plugin::Bar',
    },
});

La convención recomendada es especificar estos nombres de plugin en minúsculas. Template Toolkit primero busca una coincidencia exacta sensible a mayúsculas y minúsculas y luego intenta la conversión a minúsculas del nombre especificado.

[% USE Foo %]      # busca 'Foo' luego 'foo'

Si define todos sus "PLUGINS" con nombres en minúsculas, se localizarán independientemente de cómo el usuario especifique el nombre en la directiva USE. Si, por el contrario, define sus "PLUGINS" con nombres en mayúsculas o mixtas, el nombre especificado en la directiva "USE" debe coincidir exactamente con la mayúscula.

La directiva "USE" se utiliza para crear objetos de plugin y lo hace llamando al método plugin() en el objeto Template::Context actual. Si el nombre del plugin está definido en el hash "PLUGINS", el módulo Perl correspondiente se carga a través de require(). El contexto llama al método de clase load() que debería devolver el nombre de la clase (caso predeterminado y general) o un objeto prototipo contra el cual se puede llamar al método new() para instanciar objetos de plugin individuales.

Si el nombre del plugin no está definido en el hash "PLUGINS", entran en juego las opciones "PLUGIN_BASE" y/o "LOAD_PERL".

PLUGIN_BASE

Si un plugin no está definido en el "PLUGINS" hash, entonces Template Toolkit intenta cargar el plugin del módulo Perl predeterminado que se crea añadiendo el nombre del plugin a la cadena "PLUGIN_BASE". Si "PLUGIN_BASE" no está definido, se asume que el nombre del módulo es simplemente el nombre del plugin con el prefijo "Template::Plugin::".

my $template = Template->new({
    PLUGIN_BASE => 'MyOrg::Plugin',
});

Ahora, si un usuario escribe:

[% USE cgi %]

Entonces el kit de herramientas intentará cargar el módulo MyOrg::Plugin::CGI.

Si se especifican tanto "PLUGIN_BASE" como "PLUGINS", el hash "PLUGINS" tendrá prioridad. Esto le permite anular la carga predeterminada de módulos para nombres de plugin específicos mientras sigue utilizando las convenciones de nomenclatura predeterminadas para otros.

LOAD_PERL

Esta opción booleana (que se establece en 1 o 0) controla si el kit de herramientas debe intentar cargar módulos Perl no definidos en el hash "PLUGINS" y no especificados por "PLUGIN_BASE". Si "LOAD_PERL" se establece en 0 (que es el valor predeterminado), cualquier intento de usar un plugin no definido generará un error. Si se establece en 1, el kit de herramientas intentará cargar el módulo Perl correspondiente, buscando primero el nombre del plugin especificado y luego el nombre del plugin con el prefijo "Template::Plugin::".

my $template = Template->new({
    LOAD_PERL => 1,
});

Por ejemplo, si un usuario escribe:

[% USE MyPlugin %]

Y si "LOAD_PERL" está configurado en 1, el kit de herramientas intentará cargar el módulo MyPlugin o Template::Plugin::MyPlugin.

Esto es útil si tiene plugins personalizados que no encajan en la convención de nomenclatura Template::Plugin::* o si desea permitir el uso de cualquier módulo Perl como plugin.

FILTER_PATH

La opción "FILTER_PATH" se utiliza para especificar una lista de directorios en los que buscar módulos de filtro Perl. Los filtros son como plugins pero se utilizan para procesar el contenido de las variables o bloques de plantilla. Se invocan utilizando la directiva FILTER.

La opción "FILTER_PATH" espera una referencia a una matriz de nombres de directorios. El kit de herramientas buscará los módulos de filtro en estos directorios en el orden especificado.

my $template = Template->new({
    FILTER_PATH => [ '/home/user/lib/Template/Filters', 'lib/MyFilters' ],
});

Si un usuario escribe:

[% value FILTER string %]

El kit de herramientas buscará el módulo Template::Filter::String en el primer directorio de "FILTER_PATH", y si no se encuentra allí, buscará en el segundo directorio, y así sucesivamente. Si no se encuentra ningún módulo de filtro coincidente después de buscar en todos los directorios, se generará un error.

Si "FILTER_PATH" no está definido, el kit de herramientas utiliza la ruta de inclusión estándar para buscar módulos de filtro, que suele ser Template::Filter::*.

Customisation and Extension

PLUGINS

If a plugin is not found explicitly via the "PLUGINS" hash then the "PLUGIN_BASE" is used to attempt to construct a correct Perl module name which can be successfully loaded.

The "PLUGIN_BASE" can be specified as a reference to an array of module namespaces, or as a single value which is automatically converted to a list. The default "PLUGIN_BASE" value ("Template::Plugin") is then added to the end of this list.

example 1:

my $template = Template->new({
    PLUGIN_BASE => 'MyOrg::Template::Plugin',
});
[% USE Foo %]    # => MyOrg::Template::Plugin::Foo
                   or        Template::Plugin::Foo

example 2:

my $template = Template->new({
    PLUGIN_BASE => [   'MyOrg::Template::Plugin',
                       'YourOrg::Template::Plugin'  ],
});

template:

[% USE Foo %]    # =>   MyOrg::Template::Plugin::Foo
                   or YourOrg::Template::Plugin::Foo
                   or          Template::Plugin::Foo

If you don't want the default "Template::Plugin" namespace added to the end of the "PLUGIN_BASE", then set the $Template::Plugins::PLUGIN_BASE variable to a false value before calling the new() Template#new() constructor method. This is shown in the example below where the "Foo" plugin is located as "My::Plugin::Foo" or "Your::Plugin::Foo" but not as "Template::Plugin::Foo".

example 3:

use Template::Plugins;
$Template::Plugins::PLUGIN_BASE = '';
my $template = Template->new({
    PLUGIN_BASE => [   'My::Plugin',
                       'Your::Plugin'  ],
});

template:

[% USE Foo %]    # =>   My::Plugin::Foo
                   or Your::Plugin::Foo

LOAD_PERL

If a plugin cannot be loaded using the "PLUGINS" or "PLUGIN_BASE" approaches then the provider can make a final attempt to load the module without prepending any prefix to the module path. This allows regular Perl modules (i.e. those that don't reside in the Template::Plugin or some other such namespace) to be loaded and used as plugins.

By default, the "LOAD_PERL" option is set to 0 and no attempt will be made to load any Perl modules that aren't named explicitly in the "PLUGINS" hash or reside in a package as named by one of the "PLUGIN_BASE" components.

Plugins loaded using the "PLUGINS" or "PLUGIN_BASE" receive a reference to the current context object as the first argument to the new() constructor. Modules loaded using "LOAD_PERL" are assumed to not conform to the plugin interface. They must provide a new() class method for instantiating objects but it will not receive a reference to the context as the first argument.

Plugin modules should provide a load() class method (or inherit the default one from the Template::Plugin base class) which is called the first time the plugin is loaded. Regular Perl modules need not. In all other respects, regular Perl objects and Template Toolkit plugins are identical.

If a particular Perl module does not conform to the common, but not unilateral, new() constructor convention then a simple plugin wrapper can be written to interface to it.

FILTERS

The "FILTERS" option can be used to specify custom filters which can then be used with the "FILTER" directive like any other. These are added to the standard filters which are available by default. Filters specified via this option will mask any standard filters of the same name.

The "FILTERS" option should be specified as a reference to a hash array in which each key represents the name of a filter. The corresponding value should contain a reference to an array containing a subroutine reference and a flag which indicates if the filter is static (0) or dynamic (1). A filter may also be specified as a solitary subroutine reference and is assumed to be static.

$template = Template->new({
    FILTERS => {
        'sfilt1' =>   \&static_filter,      # static
        'sfilt2' => [ \&static_filter, 0 ], # same as above
        'dfilt1' => [ \&dyanamic_filter_factory, 1 ],
    },
});

Additional filters can be specified at any time by calling the define_filter() method on the current Template::Context object. The method accepts a filter name, a reference to a filter subroutine and an optional flag to indicate if the filter is dynamic.

my $context = $template->context();
$context->define_filter('new_html', \&new_html);
$context->define_filter('new_repeat', \&new_repeat, 1);

Static filters are those where a single subroutine reference is used for all invocations of a particular filter. Filters that don't accept any configuration parameters (e.g. "html") can be implemented statically. The subroutine reference is simply returned when that particular filter is requested. The subroutine is called to filter the output of a template block which is passed as the only argument. The subroutine should return the modified text.

sub static_filter {
    my $text = shift;
    # do something to modify $text...
    return $text;
}

The following template fragment:

[% FILTER sfilt1 %]
Blah blah blah.
[% END %]

is approximately equivalent to:

&static_filter("\nBlah blah blah.\n");

Filters that can accept parameters (e.g. "truncate") should be implemented dynamically. In this case, the subroutine is taken to be a filter 'factory' that is called to create a unique filter subroutine each time one is requested. A reference to the current Template::Context object is passed as the first parameter, followed by any additional parameters specified. The subroutine should return another subroutine reference (usually a closure) which implements the filter.

sub dynamic_filter_factory {
    my ($context, @args) = @_;
    return sub {
        my $text = shift;
        # do something to modify $text...
        return $text;
    }
}

The following template fragment:

[% FILTER dfilt1(123, 456) %]
Blah blah blah
[% END %]

is approximately equivalent to:

my $filter = &dynamic_filter_factory($context, 123, 456);
&$filter("\nBlah blah blah.\n");

See the "FILTER" directive for further examples.

LOAD_TEMPLATES

The "LOAD_TEMPLATES" option can be used to provide a reference to a list of Template::Provider objects or sub-classes thereof which will take responsibility for loading and compiling templates.

my $template = Template->new({
    LOAD_TEMPLATES => [
        MyOrg::Template::Provider->new({ ... }),
        Template::Provider->new({ ... }),
    ],
});

When a "PROCESS", "INCLUDE" or "WRAPPER" directive is encountered, the named template may refer to a locally defined "BLOCK" or a file relative to the "INCLUDE_PATH" (or an absolute or relative path if the appropriate "ABSOLUTE" or "RELATIVE" options are set). If a "BLOCK" definition can't be found (see the Template::Context template() method for a discussion of "BLOCK" locality) then each of the "LOAD_TEMPLATES" provider objects is queried in turn via the fetch() method to see if it can supply the required template.

Each provider can return a compiled template, an error, or decline to service the request in which case the responsibility is passed to the next provider. If none of the providers can service the request then a 'not found' error is returned. The same basic provider mechanism is also used for the "INSERT" directive but it bypasses any "BLOCK" definitions and doesn't attempt is to parse or process the contents of the template file.

If "LOAD_TEMPLATES" is undefined, a single default provider will be instantiated using the current configuration parameters. For example, the Template::Provider "INCLUDE_PATH" option can be specified in the Template configuration and will be correctly passed to the provider's constructor method.

my $template = Template->new({
    INCLUDE_PATH => '/here:/there',
});

LOAD_PLUGINS

The "LOAD_PLUGINS" options can be used to specify a list of provider objects (i.e. they implement the fetch() method) which are responsible for loading and instantiating template plugin objects. The Template::Context plugin() method queries each provider in turn in a "Chain of Responsibility" as per the template() and filter() methods.

my $template = Template->new({
    LOAD_PLUGINS => [
        MyOrg::Template::Plugins->new({ ... }),
        Template::Plugins->new({ ... }),
    ],
});

my $template = Template->new({

TOLERANT

El flag "TOLERANT" se usa para controlar el comportamiento de los módulos de proveedores de Template Toolkit (Template::Provider, Template::Plugins, Template::Filters) cuando se producen errores. Por defecto, cualquier error se reporta como tal, y la solicitud por el recurso específico ("template", "plugin", "filter") se rechaza y se lanza una excepción.

Cuando el flag "TOLERANT" está establecido a valores verdaderos, los errores se ignoran silenciosamente y el proveedor devuelve "STATUS_DECLINED". Esto permite que un proveedor siguiente asume la responsabilidad de proporcionar el recurso, en lugar de rechazar la solicitud de inmediato. Si todos los proveedores rechazan servir la solicitud, se lanzará una excepción "<resource> not found" por medio de fallos tolerados o por una desición genuina de no cumplir.

Una referencia a un objeto Template::Service o su subclase, a la cual debe delegar el módulo Template. Si no se especifica, se crea automáticamente un objeto Template::Service utilizando la configuración actual.

Ejemplo:

my $template = Template->new({

Una referencia a un objeto Template::Context que define un entorno específico en el que se procesan las plantillas.
