NOMBRE

Test::Warnings - Testear alertas y la falta de ellas

VERSIÓN

versión 0.038

SINOPSIS

use Test::More;
use Test::Warnings;
pass('yay!');
done_testing;

emite TAP:

ok 1 - yay!
ok 2 - no (inesperado) alertas (vía done_testing)
1..2

y:

use Test::More tests => 3;
use Test::Warnings 0.005 ':all';
pass('yay!');
like(warning { warn "oh noes!" }, qr/^oh noes/, 'we warned');

emite TAP:

ok 1 - yay!
ok 2 - we warned
ok 3 - no (inesperado) alertas (vía bloque END)
1..3

DESCRIPCIÓN

Si has intentado usar Test::NoWarnings para confirmar que no se generan alertas en tus tests, combinado con la comodidad de "done_testing" para no tener que declarar un número de prueba, habrás descubierto que estos dos elementos no funcionan bien juntos, ya que el número de prueba se calculará antes de que se ejecute la prueba de alertas, resultando en un error de TAP. (Ver "ejemplos/test_nowarnings.pl" en esta distribución para una demostración.)

Este módulo está destinado a ser utilizado como sustituto de Test::NoWarnings: también añade una prueba adicional, pero la ejecuta antes de "done_testing" calcula el número de prueba, en lugar de después. Lo hace alhookear "done_testing" así como mediante un "END" block. Puedes declarar un plan, o no, y todo seguirá funcionando.

Es realmente equivalente a:

use Test::NoWarnings 1.04 ':early';

aunque las alertas siguen siendo impresas normally cuando ocurren. Estás seguro/a y encantado/a de realizar una búsqueda-global-replace de lo anterior con "use Test::Warnings;", ya sea que tus tests tengan un plan o no.

También puede usarse como sustituto de Test::Warn, si deseas testear el contenido de las alertas esperadas; lee más sobre cómo.

FUNCIONES

Las siguientes funciones están disponibles para importar (no incluidas por defecto; puedes también obtener todas ellas mediante la etiqueta ":all"):

allow_warnings([bool]) - EXPERIMENTAL - PUEDE SER ELIMINADO

Cuando se le pasa un valor verdadero, o no se le pasa ningún valor, las alertas siguientes no generarán un fallo de prueba; cuando se le pasa un valor falso, las alertas siguientes sí generarán un fallo de prueba. El valor inicial es "false".

Cuando se permiten alertas, cualquier alerta se emitirá mediante "Test::Builder::note".

"allowing_warnings" - EXPERIMENTAL - PUEDE SER ELIMINADO

Devuelve si estamos actualmente permitiendo alertas (como se describe con "allow_warnings").

"had_no_warnings()"

Prueba si hay alguna alerta previa a un llamado a "allowing_warnings". Se ejecuta automáticamente al final de todas las pruebas, pero también puede llamarse manualmente en cualquier momento, con lo cual se puede hacer lo que se quiera.

"warnings({ código })"

Dado un bloque de código, ejecuta el bloque y devuelve una lista de todas las alertas (no previamente permitidas mediante "allow_warnings") emitidas dentro. Esto te permite testear la presencia de alertas que no solo se permitirían, sino que deben ser emitidas. No se proporcionan funciones de testing; puedes testear estas mismas con tus propias funciones de testing, como Test::More::is o Test::Deep::cmp_deeply).

Puedes usar este constructo como sustituto de Test::Warn::warnings_are:

is_deeply(
    [ warnings { ... } ],
    [
        'mensaje de alerta 1',
        'mensaje de alerta 2',
    ],
    'se esperan alertas',
);

o, para sustituir Test::Warn::warnings_like:

cmp_deeply(
    [ warnings { ... } ],
    bag(    # orden de mensajes no importa
        re(qr/ mensaje de alerta 1 /),
        re(qr/ mensaje de alerta 2 /),
    ),
    'se esperan alertas (en cualquier orden)',
);

Las alertas generadas por este bloque de código no se propagan más allá. Sin embargo, ya que se devuelven desde esta función con su nombre de archivo y número de línea intactos, puedes re-emitirlas inmediatamente después de llamar a warnings(...), si lo deseas.

Nota: "use Test::Warnings 'warnings'" te dará una subrutina "warnings" en tu espacio de nombres (más probablemente "main", si estás escribiendo un test), por lo que no podrás posteriormente hacer "warnings->import" — será un error: "Not enough arguments for Test::Warnings::warnings at ... near "warnings->import"". Para evitarlo, either usa la forma completa ("Test::warnings") o haz tus llamadas a la subrutina "warnings" primero.

"warning({ código })"

Es lo mismo que "warnings( { code } )", excepto que devuelve un escalar siempre (el único warning producido, si hubo uno, o un arrayref de lo contrario), lo que puede ser más cómodo que warnings() si esperas exactamente una alerta.

Sin embargo, te recomendamos capturar el resultado de warning() en una variable temporal para poder imprimir su valor si no contiene lo que esperas. Por ejemplo, con esta prueba:

like(
    warning { foo() },
    qr/^esta es una alerta/,
    'se esperó una alerta de foo()',
);

si gets dos warnings (o ninguno) en lugar de uno, obtendrás un arrayref, lo que resultará en un mensaje de prueba no útil como:

#   Failed test 'se esperó una alerta de foo()'
#   at t/mytest.t line 10.
#                   'ARRAY(0xdeadbeef)'
#     no match '(?^:^esta es una alerta)'

Por lo tanto, cambia tu prueba a:

my $warning = warning { foo() };
like(
    $warning,
    qr/^esta es una alerta/,
    'se esperó una alerta de foo()',
) or diag 'se obtuvieron alertas (o ninguna): ', explain($warning);

permite_patterns

allow_patterns(qr/ siempre permitir esta alerta /);
{
  my $temp = allow_patterns(qr/ solo permitir en este ámbito /, qr/ otra alerta temporal /);
  ... cosas ...
}

Dado una o más expresiones regulares, en "qr/.../", añade las mismas a la lista de permisos (las alertas se emitirán con "note" en lugar de activar el gestor de alertas). Si el valor devuelto se guarda en una variable local, la exención de alerta se aplicará solo en ese ámbito (la adición se revierte al final del ámbito); de lo contrario, el efecto será global.

desactiva_patterns

Dado una o más expresiones regulares, en "qr/.../", elimina la alerta de la lista de permisos. La expresión debe exactamente coincidir con una expresión previamente proporcionada a "allow_patterns".

OPCIONES DE IMPORTACIÓN

":all"

Importa todas las funciones mencionadas anteriormente

":early"

Esto es principalmente para Test::NoWarnings compatibilidad. Añade una prueba antes de done_testing se llama, haciendo que las pruebas se puedan ejecutar sin un plan declarando el número de pruebas.

":nowarnings"

Esto es también para compatibilidad con Test::NoWarnings. Añade una prueba que comprueba que no se han producido alertas, y la ejecuta al final. El nombre de la prueba es "no (inesperadas) alertas".

NAME

Test::Warnings - Make sure your tests do not generate warnings

VERSION

This document describes Test::Warnings version 0.038.

SYNOPSIS

    use Test::More tests => 1;
    use Test::Warnings;

    # This test will fail if the code block generates a warning:
    ok_or_pass( sub {
        # some code here
    });

    # Or use the END block:
    BEGIN {
        $ENV{PERL_TEST_DIAGNOSTIC} = 1;
    }
    use Test::More tests => 1;
    use Test::Warnings;
    # ... code that generates warnings ...
    done_testing(); # or END {}

DESCRIPTION

This module is designed to help testers write tests that do not generate warnings. It does this by intercepting warnings generated by Perl code, and then checking to see if any warnings were generated when the test finishes.

In particular, this module is designed to be used in conjunction with modules like Test::More, and to provide a simple way to ensure that your modules do not emit warnings in normal use.

While it is generally a good idea to ensure that your tests do not generate warnings, there are certain situations where it is desirable to do so. For example, you may want to allow warnings to be generated in certain situations, such as when a deprecated feature is being used. In such cases, you can use the ":fail_on_warning" import option to control the behavior of the module.

FUNCTIONS

The module exports one function: ok_or_pass.

ok_or_pass takes a code reference as its argument. It executes the code reference, and if any warnings are generated during the execution of the code, the test will fail. If no warnings are generated, the test will pass.

If you do not want to use the ok_or_pass function, you can use the "END" or "done_testing" blocks to check for warnings. In this case, the module will check for warnings when the test program exits, and if any warnings are generated, the test will fail.

IMPORT OPTIONS

This module recognizes the following import options:

":no_end_test"

Disables the addition of a "had_no_warnings" test via "END" or "done_testing"

":fail_on_warning"

When used, fail immediately when an unexempted warning is generated (as opposed to waiting until "had_no_warnings" or "done_testing" is called).

I recommend you only turn this option on when debugging a test, to see where a surprise warning is coming from, and rely on the end-of-tests check otherwise.

":report_warnings"

When used, had_no_warnings() will print all the unexempted warning content, in case it had been suppressed earlier by other captures (such as "stderr_like" in Test::Output or "capture" in Capture::Tiny).

OTHER OPTIONS

You can temporarily turn off the failure behaviour of this module, swapping it out for reporting (see ":report_warnings" above) with:

$ENV{PERL_TEST_WARNINGS_ONLY_REPORT_WARNINGS} = 1;

This can be useful for working around problematic modules that have warnings in newer Perl versions.

CAVEATS

Sometimes new warnings can appear in Perl that should not block installation -- for example, smartmatch was recently deprecated in perl 5.17.11, so now any distribution that uses smartmatch and also tests for warnings cannot be installed under 5.18.0. You might want to consider only making warnings fail tests in an author environment -- you can do this with the if pragma:

use if $ENV{AUTHOR_TESTING} || $ENV{RELEASE_TESTING}, 'Test::Warnings';

In future versions of this module, when interfaces are added to test the content of warnings, there will likely be additional sugar available to indicate that warnings should be checked only in author tests (or TODO when not in author testing), but will still provide exported subs. Comments are enthusiastically solicited - drop me an email, write up an RT ticket, or come by "#perl-qa" on irc!

Achtung! This is not a great idea:

sub warning_like(&#36;_;$) {
    my ($code, $pattern, $name) = @_;
    like( &#36;warning($code), $pattern, $name );
}

warning_like( { ... }, qr/foo/, 'foo appears in the warning' );

If the code in the "{ ... }" is going to warn with a stack trace with the arguments to each subroutine in its call stack (for example via "Carp::cluck"), the test name, "foo appears in the warning" will itself be matched by the regex (see examples/warning_like.t). Instead, write this:

like( warning { ... }, qr/foo/, 'foo appears in the warning' );

CAVEATS

If you are using another module that sets its own warning handler (for example Devel::Confess or diagnostics) your results may be mixed, as those handlers will interfere with this module's ability to properly detect and capture warnings in their original form.
