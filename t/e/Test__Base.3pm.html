NOMBRE

Test::Base - Un Framework de Pruebas Basado en Datos

SINOPSIS

Un nuevo módulo de pruebas:

# lib/MyProject/Test.pm
package MyProject::Test;
use Test::Base -Base;
use MyProject;
package MyProject::Test::Filter;
use Test::Base::Filter -base;
sub my_filter {
    return MyProject->do_something(shift);
}

Una prueba de ejemplo:

# t/sample.t
use MyProject::Test;
plan tests => 1 * blocks;
run_is input => 'expected';
sub local_filter {
    s/my/your/;
}
__END__
=== Prueba uno (el nombre de la prueba)
--- input my_filter local_filter
my
input
lines
--- expected
expected
output
=== Prueba dos
Esta es una descripción opcional
de esta prueba en particular.
--- input my_filter
other
input
lines
--- expected
other expected
output

DESCRIPCIÓN

Probar suele ser la parte fea de la autoría de módulos Perl. Perl te da una forma estándar de ejecutar pruebas con Test::Harness, y primitivas de prueba básicas con Test::More. Después de eso, estás prácticamente solo para desarrollar un marco y una filosofía de pruebas. Test::More te anima a crear tu propio marco de pruebas heredando de Test::Builder, pero eso no es trivial.

Test::Base te da una forma de escribir tu propia clase base de marco de pruebas que *es* trivial. De hecho, es tan simple como dos líneas:

package MyTestFramework;
use Test::Base -Base;

Un módulo llamado "MyTestFramework.pm" que contenga esas dos líneas, dará todo el poder de Test::More y todo el poder de Test::Base a cada archivo de prueba que lo utilice. A medida que aumentes las capacidades de "MyTestFramework", tus pruebas tendrán todo ese poder también.

"MyTestFramework" se convierte en un lugar para que pongas todos tus fragmentos de prueba reutilizables. A medida que escribas pruebas, verás patrones y duplicación, y puedes "subirlos" a "MyTestFramework". Por supuesto, no tienes que heredar de Test::Base en absoluto. Puedes usarlo directamente en muchas aplicaciones, incluyendo todos los lugares donde usarías Test::More.

Test::Base se concentra en ofrecer patrones reutilizables basados en datos, para que puedas escribir pruebas con un mínimo de código. En el corazón de todas las pruebas tienes entradas, procesos y salidas esperadas. Test::Base proporciona algunas formas limpias para que expreses tus datos de entrada y salida esperada, para que puedas dedicar tu

tiempo a centrarte en eso en lugar de en la estructura de tu código.

FUNCIONES EXPORTADAS

Test::Base extiende Test::More y exporta todas sus funciones. Así que básicamente puedes escribir tus pruebas igual que con Test::More. Test::Base también exporta muchas funciones propias:

"is(actual, esperado, [nombre-de-prueba])"
Este es el equivalente a la función "is" de Test::More con un giro interesante. Si tus resultados actuales y esperados difieren y la salida tiene varias líneas, esta función te mostrará un formato de diferencia unificada de la salida. ¡Considera el beneficio al buscar el único carácter que es diferente en cientos de líneas de salida!

La salida de diferencias requiere el módulo opcional "Text::Diff" de CPAN. Si no tienes este módulo, la función is() simplemente te dará la salida normal de Test::More. Para deshabilitar las diferencias por completo, establece la variable de entorno "TEST_SHOW_NO_DIFFS" (o $ENV{TEST_SHOW_NO_DIFFS}) a un valor verdadero. También puedes llamar a la función "no_diff" como atajo.

bloques( [nombre-de-sección-de-datos] )
La función más importante es "bloques". En contexto de lista, devuelve una lista de objetos "Test::Base::Block" que se generan a partir de la especificación de pruebas en la sección "DATA" de tu archivo de prueba. En contexto escalar, devuelve el número de objetos. Esto es útil para calcular tu plan de Test::More.

Cada objeto Test::Base::Block tiene métodos que corresponden a los nombres de las secciones de datos de ese objeto. También hay un método "name" y un método "description" para acceder a esas partes del bloque si se especificaron.

La función "bloques" puede tomar un único argumento opcional, que indica que solo devuelva los bloques que contienen una sección de datos con un nombre particular. De lo contrario, "bloques" devuelve todos los bloques.

my @todos_mis_bloques = bloques;
my @solo_los_bloques_foo = bloques('foo');
siguiente_bloque()
Puedes usar la función next_block para iterar sobre todos los bloques. 
while (my $bloque = next_block) {
    ...
}

Devuelve undef después de que todos los bloques han sido iterados. Luego puede ser llamada de nuevo para reiterar.

primer_bloque()
Devuelve el primer bloque o undef si no hay ninguno. Reinicia el iterador para la función "siguiente_bloque".
ejecutar(&subrutina)
Hay muchas maneras de escribir tus pruebas. Puedes referenciar cada bloque individualmente o puedes iterar sobre todos los bloques y realizar una operación común. La función "ejecutar" hace la iteración por ti, así que todo lo que necesitas hacer es pasarle un bloque de código para que se ejecute para cada bloque.

La función "ejecutar" toma una subrutina como argumento, y llama a la sub una vez por cada bloque en la especificación. Le pasa el objeto de bloque actual a la subrutina.

ejecutar {
    my $bloque = shift;
    is(process($bloque->foo), $bloque->bar, $bloque->name);
};
"ejecutar_es([nombre_dato1, nombre_dato2])"
Muchas veces simplemente quieres ver si dos secciones de datos son equivalentes en cada bloque, probablemente después de haber sido procesadas a través de uno o más filtros. Con la función "ejecutar_es", simplemente puedes pasar los nombres de dos secciones de datos que existen en cada bloque, y iterará sobre cada bloque comparando las dos secciones. 
ejecutar_es 'foo', 'bar';

Si no se proporcionan secciones de datos, "ejecutar_es" intentará detectarlas automáticamente.

NOTA: Test::Base ignorará silenciosamente cualquier bloque que no contenga
ambas secciones.

"es_profundo($dato1, $dato2, $nombre_prueba)"
Como "is_deeply" de Test::More pero usa el módulo más correcto Test::Deep.
"ejecutar_es_profundamente([nombre_dato1, nombre_dato2])"
Como "run_is_deeply" pero usa "es_profundo" que usa el más correcto Test::Deep.
"ejecutar_es_profundamente([nombre_dato1, nombre_dato2])"
Como "ejecutar_es" pero usa "is_deeply" para la comparación de estructuras de datos complejas.
"ejecutar_es_profundamente([nombre_dato1, nombre_dato2])"
Como "ejecutar_es_profundamente" pero usa "es_profundo" que usa el más correcto Test::Deep.
"ejecutar_como([nombre_dato, patron_regular | nombre_dato]);"
La función "ejecutar_como" es similar a "ejecutar_es" excepto que el segundo argumento es una expresión regular. El patrón puede ser un objeto "qr{}" o una sección de datos que ha sido filtrada a una expresión regular. 
ejecutar_como 'foo', qr{<html.*};
ejecutar_como 'foo', 'coincidencia';
"ejecutar_sin_coincidir([nombre_dato, patron_regular | nombre_dato]);"
La función "ejecutar_sin_coincidir" es similar a "ejecutar_como", excepto que es lo opuesto. 
ejecutar_sin_coincidir 'foo', qr{<html.*};
ejecutar_sin_coincidir 'foo', 'sin_coincidencia';
"comparar_ejecucion(nombre_dato1, nombre_dato2)"
La función "comparar_ejecucion" es como las funciones "ejecutar_es", "ejecutar_es_profundamente" y "ejecutar_como" al
l rolled into one. It loops over each relevant block and determines what type of comparison to do.

NOTE: If you do not specify either a plan, or run any tests, the
"run_compare" function will automatically be run.

"delimiters($block_delimiter, $data_delimiter)"
Override the default delimiters of "===" and "---".
spec_file($file_name)
By default, Test::Base reads its input from the DATA section. This function tells it to get the spec from a file instead.
spec_string($test_data)
By default, Test::Base reads its input from the DATA section. This function tells it to get the spec from a string that has been prepared somehow.
"filters( @filters_list or $filters_hashref )"
Specify a list of additional filters to be applied to all blocks. See "FILTERS" below.

You can also specify a hash ref that maps data section names to an array ref of filters for that data type.

filters {
        xxx => [qw(chomp lines)],
        yyy => ['yaml'],
        zzz => 'eval',
    };

If a filters list has only one element, the array ref is optional.

"filters_delay( [1 | 0] );"
By default Test::Base::Block objects are have all their filters run ahead of time. There are testing situations in which it is advantageous to delay the filtering. Calling this function with no arguments or a true value, causes the filtering to be delayed. 
use Test::Base;
    filters_delay;
    plan tests => 1 * blocks;
    for my $block (blocks) {
        ...
        $block->run_filters;
        ok($block->is_filtered);
        ...
    }

In the code above, the filters are called manually, using the "run_filters" method of Test::Base::Block. In functions like "run_is", where the tests are run automatically, filtering is delayed until right before the test.

filter_arguments()
Return the arguments after the equals sign on a filter. 
sub my_filter {
        my $args = filter_arguments;
        # is($args, 'whazzup');
        ...
    }
    __DATA__
    === A test
    --- data my_filter=whazzup
tie_output()
You can capture STDOUT and STDERR for operations with this function: 
my $out = '';
    tie_output(*STDOUT, $out);
    print "Hey!\n";
    print "Che!\n";
    untie *STDOUT;
    is($out, "Hey!\nChe!\n");
no_diff()
Turn off diff support for is() in a test file.
default_object()
Returns the default Test::Base object. This is useful if you feel the need to do an OO operation in otherwise functional test code. See OO below.
"WWW() XXX() YYY() ZZZ()"
These debugging functions are exported from the Spiffy.pm module. See Spiffy for more info.
"croak() carp() cluck() confess()"
You can use the functions from the Carp module without needing to import them. Test::Base does it for you by default.

ESPECIFICACIÓN DE PRUEBAS

Test::Base te permite especificar tus datos de prueba en un archivo externo, la sección DATA de tu programa o desde una variable escalar que contenga toda la entrada de texto.

Una especificación de prueba es una serie de líneas de texto. Cada prueba (o bloque) está separada por una línea que contiene el delimitador de bloque y un nombre de prueba opcional. Cada bloque se subdivide además en secciones nombradas con una línea que contiene el delimitador de datos y el nombre de la sección de datos. Una "descripción" de la prueba puede ir en líneas después del delimitador de bloque pero antes de la primera sección de datos.

Aquí está la disposición básica de una especificación:

=== <nombre del bloque 1>
<líneas de descripción opcionales del bloque>
--- <nombre de la sección de datos 1> <filtro-1> <filtro-2> <filtro-n>
<líneas de datos de prueba>
--- <nombre de la sección de datos 2> <filtro-1> <filtro-2> <filtro-n>
<líneas de datos de prueba>
--- <nombre de la sección de datos n> <filtro-1> <filtro-2> <filtro-n>
<líneas de datos de prueba>
=== <nombre del bloque 2>
<líneas de descripción opcionales del bloque>
--- <nombre de la sección de datos 1> <filtro-1> <filtro-2> <filtro-n>
<líneas de datos de prueba>
--- <nombre de la sección de datos 2> <filtro-1> <filtro-2> <filtro-n>
<líneas de datos de prueba>
--- <nombre de la sección de datos n> <filtro-1> <filtro-2> <filtro-n>
<líneas de datos de prueba>

Aquí hay un ejemplo de código:

use Test::Base;
delimiters qw(### :::);
# código de prueba aquí
__END__
### Test One
We want to see if foo and bar
are really the same...
::: foo
a foo line
another foo line
::: bar
a bar line
another bar line
### Test Two
::: foo
some foo line
some other foo line
::: bar
some bar line
some other bar line
::: baz
some baz line
some other baz line

Este ejemplo especifica dos bloques. Ambos tienen secciones de datos foo y bar. El segundo bloque tiene un componente baz. El delimitador de bloque es "###" y el delimitador de datos es ":::".

El delimitador de bloque predeterminado es "===" y el delimitador de datos predeterminado es "--- ".

Hay algunos nombres de sección de datos especiales que se utilizan con fines de control:

--- SKIP
--- ONLY
--- LAST

Un bloque con una sección SKIP hace que esa prueba se ignore. Esto es útil para deshabilitar una prueba temporalmente.

Un bloque con una sección ONLY hace que solo ese bloque se utilice. Esto es útil cuando te concentras en que una sola prueba pase. Si hay más de un bloque con ONLY, se elegirá el primero.

Dado que ONLY es muy útil para depurar y a veces olvidas eliminar la bandera ONLY antes de confirmar en el VCS o subir a CPAN, Test::Base te muestra por defecto un mensaje de diagnóstico que dice Encontré ONLY ... ¿tal vez estás depurando?. Si no te gusta, usa "no_diag_on_only".

Un bloque con una sección LAST hace que ese bloque sea el último en la especificación. Todos los bloques siguientes serán ignorados.

FILTROS

El poder real al escribir pruebas con Test::Base proviene de sus capacidades de filtrado. Test::Base viene con un conjunto cada vez mayor de filtros genéricos útiles que puedes secuenciar y aplicar a varios bloques de prueba. Eso significa que puedes especificar la serialización del bloque en el formato más legible que puedas encontrar, y dejar que los filtros lo traduzcan a lo que realmente necesitas para una prueba. También es fácil escribir tus propios filtros.

Test::Base te permite especificar una lista de filtros para cada sección de datos de cada bloque. Los filtros predeterminados son "norm" y "trim". Estos filtros se aplicarán (en orden) a los datos después de que se hayan analizado desde la especificación y antes de que se establezcan en su objeto Test::Base::Block.

Puedes agregar a la lista de filtros predeterminados con la función "filters". Puedes especificar filtros adicionales a un bloque específico listándolos después del nombre de la sección en una línea del delimitador de la sección de datos.

Ejemplo:

use Test::Base;
filters qw(foo bar);
filters { perl => 'strict' };
sub upper { uc(shift) }
__END__
=== Test one
--- foo trim chomp upper
...
--- bar -norm
...
--- perl eval dumper
my @foo = map {
    - $_;
} 1..10;
\ @foo;

Poner un "-" antes de un filtro en una línea delimitadora, deshabilita ese filtro.

Escalar vs Lista

Cada filtro puede tomar una lista escalar o una lista como entrada, y devolverá una lista escalar o una lista. Dado que los filtros se encadenan, es importante aprender qué filtros esperan qué tipo de entrada y devuelven qué tipo de salida.

Por ejemplo, considera la siguiente lista de filtros:

norm trim lines chomp array dumper eval

Los datos siempre comienzan como una única cadena escalar. "norm" toma un escalar y devuelve un escalar. "trim" toma una lista y devuelve una lista, pero un escalar es una lista válida. "lines" toma un escalar y devuelve una lista. "chomp" toma una lista y devuelve una lista. "array" toma una lista y devuelve un escalar (una referencia de matriz anónima que contiene los elementos de la lista). "dumper" toma una lista y devuelve un escalar. "eval" toma un escalar y crea una lista.

Una lista de exactamente un elemento funciona bien como entrada para un filtro que requiere un escalar, pero cualquier otra lista causará una excepción. Un escalar en contexto de lista se considera una lista de un elemento.

Los métodos accesores de datos para bloques devolverán una lista de valores cuando se usen en contexto de lista, y el primer elemento de la lista en contexto escalar. Esto suele ser "lo correcto", pero tenlo en cuenta.

Los Filtros de Stock

Test::Base viene con un gran conjunto de filtros de stock. Están en el módulo "Test::Base::Filter". Ve a Test::Base::Filter para obtener una lista y descripción de estos filtros.

Creando tus Propios Filtros

Crear extensiones de filtro es muy simple. Puedes escribir una función en el espacio de nombres "main", o un método en el espacio de nombres "Test::Base::Filter" o una subclase de él. En cualquier caso, el texto y los argumentos adicionales se pasan y tú devuelves lo que quieras que sea el nuevo valor.

Aquí tienes un ejemplo autoexplicativo:

use Test::Base;
filters 'foo', 'bar=xyz';
sub foo {
    transform(shift);
}
sub Test::Base::Filter::bar {
    my $self = shift;       # El objeto Test::Base::Filter
    my $data = shift;
    my $args = $self->current_arguments;
    my $current_blo
ck_object = $self->block; # transformar $data de forma rudimentaria return $data; }

Si usas la interfaz de método para un filtro, puedes acceder a los detalles internos del bloque llamando al método "block" en el objeto filtro.

Normalmente probablemente solo usarás la interfaz funcional, aunque todos los filtros incorporados son métodos.

Ten en cuenta que los filtros definidos en el espacio de nombres "main" pueden verse así:

sub filter9 {
    s/foo/bar/;
}

ya que Test::Base automáticamente manipula la cadena de entrada en la variable $ _ y comprueba el valor de retorno de la función para ver si parece un número. Si debes definir un filtro que devuelva solo un número, hazlo en un espacio de nombres diferente como un método. Estos filtros no permiten la manipulación simplista de $ _.

OO

Test::Base tiene una interfaz funcional agradable para uso simple. Bajo el capó, todo es orientado a objetos. Se crea un objeto Test::Base por defecto y todas las funciones son en realidad llamadas a métodos sobre él.

Esto significa que si necesitas hacer cosas sofisticadas, también puedes usar todas las cosas orientadas a objetos. Simplemente crea nuevos objetos Test::Base y usa las funciones como métodos.

use Test::Base;
my $blocks1 = Test::Base->new;
my $blocks2 = Test::Base->new;
$blocks1->delimiters(qw(!!! @@@))->spec_file('test1.txt');
$blocks2->delimiters(qw(### $$$))->spec_string($test_data);
plan tests => $blocks1->blocks + $blocks2->blocks;
# ... etc

LA CLASE "TEST::BASE::BLOCK"

En Test::Base, los bloques se exponen como objetos Test::Base::Block. Esta sección enumera los métodos que se pueden llamar en un objeto Test::Base::Block. Por supuesto, cada nombre de sección de datos también está disponible como un método.

name()
Esta es la descripción corta opcional de un bloque, que se especifica en la línea separadora del bloque.
description()
Esta es una descripción larga opcional del bloque. Es el texto tomado de entre el separador de bloque y la primera sección de datos.
seq_num()
Devuelve un número de secuencia para este bloque. Los números de secuencia comienzan con 1.
blocks_object()
Devuelve el objeto Test::Base que posee este bloque.
run_filters()
Ejecuta los filtros en las secciones de datos de los bloques. No necesitas usar este método a menos que también hayas usado la función "filters_delay".
is_filtered()
Devuelve verdadero si los filtros ya se han ejecutado para este bloque.
original_values()
Devuelve un hash de los valores originales y sin filtrar de cada sección de datos.

SUBCLASIFICACIÓN

Una de las mejores cosas de Test::Base es que es fácil de subclasificar. Esto es muy importante, porque en tu proyecto personal, probablemente querrás extender Test::Base con tus propios filtros y otras piezas reutilizables de tu marco de pruebas.

Aquí tienes un ejemplo de una subclase:

package MyTestStuff;
use Test::Base -Base;
our @EXPORT = qw(some_func);
sub some_func {
    (my ($self), @_) = find_my_self(@_);
    ...
}
package MyTestStuff::Block;
use base 'Test::Base::Block';
sub desc {
    $self->description(@_);
}
package MyTestStuff::Filter;
use base 'Test::Base::Filter';
sub upper {
    $self->assert_scalar(@_);
    uc(shift);
}

Ten en cuenta que no tienes que re-exportar todas las funciones de Test::Base. Eso sucede automáticamente, debido al poder de Spiffy.

La primera línea en "some_func" permite que se llame como una función o como un método en el código de prueba.

SOPORTE DE DISTRIBUCIÓN

Podrías pensar que no quieres usar Test::Base en tus módulos, porque añade una dependencia de instalación. No temas. Module::Install::TestBase se encarga de eso.

Simplemente escribe un Makefile.PL que se parezca a esto:

use inc::Module::Install;
name            'Foo';
all_from        'lib/Foo.pm';
use_test_base;
WriteAll;

La línea con "use_test_base" empaquetará automáticamente todo el código que el usuario necesita para ejecutar pruebas basadas en Test::Base.

OTRAS CARACTERÍSTICAS GENIALES

Test::Base añade automáticamente:

use strict;
use warnings;

a todos tus scripts de prueba y subclases de Test::Base. Una característica de Spiffy, de hecho.

HISTORIAL

Este módulo comenzó su vida con el horrible y ridículo nombre "Test::Chunks". Fue renombrado a "Test::Base" con la esperanza de que fuera visto como el módulo muy útil que se ha convertido. Si estás cambiando de "Test::Chunks" a "Test::Base", simplemente sustituye el concepto y el uso de "chunks" por "blocks".
