Test2::Event(3perl) Guía de referencia del programador de Perl Test2::Event(3perl)

NOMBRE

Test2::Event - Clase base para eventos

DESCRIPCIÓN

Clase base para todos los objetos de evento que se pasan a través de Test2.

SINOPSIS

package Test2::Event::MiEvento;
use strict;
use warnings;
# Esto hará que nuestra clase sea una subclase de evento (requerido)
use base 'Test2::Event';
# Añadir algunos accesores (opcional)
# No está obligado a usar HashBase, puede usar cualquier herramienta de objetos que
# desee, o crear sus propios accesores.
use Test2::Util::HashBase qw/foo bar baz/;
# Úselo si desea que la API heredada se escriba para usted, para que esto
# funcione, deberá implementar un método facet_data().
use Test2::Util::Facets2Legacy;
# Oportunidad de inicializar algunos valores predeterminados
sub init {
    my $self = shift;
    # no otros argumentos en @_
    $self->set_foo('xxx') unless defined $self->foo;
    ...
}
# Esta es la nueva forma para que los eventos transmitan datos al sistema Test2
sub facet_data {
    my $self = shift;
    # Obtener facetas comunes como 'about', 'trace' 'amnesty' y 'meta'
    my $facet_data = $self->common_facet_data();
    # ¿Está haciendo una aserción?
    $facet_data->{assert} = {pass => 1, details => 'mi aserción'};
    ...
    return $facet_data;
}
1;

MÉTODOS

GENERALES

$trace = $e->trace
Obtiene una instantánea de Test2::EventFacet::Trace tal como estaba cuando se generó este evento.
$bool_o_undef = $e->related($e2)
Verifica si 2 eventos están relacionados. En este caso, relacionado significa que sus rastros comparten una firma, lo que significa que fueron creados con el mismo contexto (o al menos por contextos que comparten un id, que es lo mismo, a menos que alguien esté haciendo algo muy malo).

Esto se puede usar para vincular de manera confiable múltiples eventos creados por la misma herramienta. Por ejemplo, una prueba fallida como "ok(0, "fallo"" generará 2 eventos, uno siendo un Test2::Event::Ok y el otro un Test2::Event::Diag. Ambos eventos están relacionados, habiendo sido creados bajo el mismo contexto y por la misma herramienta inicial (aunque múltiples herramientas pueden haber estado anidadas bajo la inicial).

Esto devolverá "undef" si la relación no se puede verificar, lo que sucede si alguno de los eventos tiene un rastro incompleto o faltante. Esto devolverá 0 si los rastros están completos, pero no coinciden. Se devolverá 1 si hay una coincidencia.

$e->add_amnesty({tag => $TAG, details => $DETAILS});
Esto se puede usar para agregar amnistía a este evento. La amnistía solo afecta a las aserciones fallidas en la mayoría de los casos, pero algunos formateadores pueden mostrarlas para aserciones exitosas, o incluso para no-aserciones también.

La amnistía evitará que una aserción fallida cause que la prueba general falle. En otras palabras, marca un fallo como esperado y permitido.

Nota: Así es como se implementa 'TODO' internamente. TODO es esencialmente amnistía con la etiqueta 'TODO'. Los detalles son la razón del TODO.

$uuid = $e->uuid
Si la etiqueta UUID está habilitada (Ver Test::API), cualquier evento que haya pasado por un hub será etiquetado con un UUID. Un evento recién creado aún no estará etiquetado en la mayoría de los casos.
$class = $e->load_facet($name)
Este método se utiliza para cargar una faceta por nombre (o clave). Intentará cargar la clase de la faceta; si tiene éxito, devolverá la clase que cargó. Si falla, devolverá "undef". Esto almacena en caché el resultado a nivel de clase para que las llamadas futuras sean más rápidas.

La variable $name debe ser la clave utilizada para acceder a la faceta en un hashref de facetas. Por ejemplo, la faceta de aserción tiene la clave 'assert', la faceta de información tiene la clave 'info' y la faceta de error tiene la clave 'errors'. Puede incluir u omitir la 's' al final del nombre; el método es lo suficientemente inteligente como para intentar ambas formas (con 's' y sin 's'), verificará lo que proporcionó primero y, si no lo encuentra, agregará o eliminará la 's' y lo intentará de nuevo.

@classes = $e->FACET_TYPES()
@classes = Test2::Event->FACET_TYPES()
Esto devuelve una lista de todas las facetas que se han cargado usando el método load_facet(). Esto no devolverá ninguna clase que no se haya cargado, o que se haya cargado directamente sin una llamada a load_facet().

Nota: Los tipos de facetas principales se cargan y se rellenan automáticamente en esta lista.

NUEVA API

$hashref = $e->common_facet_data();
Esto puede ser utilizado por las subclases para generar un hashref de datos de faceta inicial. Esto rellenará el hashref con las facetas de rastreo, metadatos, amnistía y acerca de. Estas facetas se producen casi siempre de la misma manera para todos los eventos.
$hashref = $e->facet_data()
Si no anula esto, la implementación predeterminada intentará generar facetas a partir de la API heredada. Esta generación se limita a lo que la API heredada puede proporcionar. Se recomienda anular este método y escribir explícitamente los datos de las facetas.
$hashref = $e->facets()
Esto toma el hashref de facet_data() y bendice cada faceta en la subclase "Test2::EventFacet::*" adecuada. Si no se puede encontrar una clase para ninguna faceta, se pasará sin cambios.
@errors = $e->validate_facet_data();
@errors = $e->validate_facet_data(%params);
@errors = $e->validate_facet_data(\%facets, %params);
@errors = Test2::Event->validate_facet_data(%params);
@errors = Test2::Event->validate_facet_data(\%facets, %params);
Este método validará los datos de la faceta y devolverá una lista de errores. Si no se encuentran errores, devolverá una lista vacía.

Esto se puede llamar como un método de objeto sin argumentos, en cuyo caso se llamará al método facet_data() para obtener los datos de la faceta que se validarán.

Cuando se utiliza como un método de objeto, el argumento "\%facet_data" puede omitirse.

Cuando se utiliza como un método de clase, el argumento "\%facet_data" es requerido.

Los argumentos restantes se agruparán en un hash %params.

Actualmente, solo se define 1 parámetro:

require_facet_class => $BOOL
Cuando se establece en verdadero (el valor predeterminado es falso), esto rechazará cualquier faceta para la que no se pueda encontrar una clase de faceta. Normalmente, las facetas sin clases se asumen personalizadas y se ignoran.

¿QUÉ SON LAS FACETAS?

Las facetas son cómo los eventos transmiten su propósito a los internos de Test2 y a los formateadores. Un evento sin facetas no tendrá ningún efecto intencional en el estado general de la prueba, y la mayoría de los formateadores no lo mostrarán en absoluto, excepto quizás para decir que se vio un evento de tipo desconocido.

Las facetas son producidas por la subrutina facet_data(), que casi siempre deberías anular. Se espera que facet_data() devuelva un hashref donde cada clave es el tipo de faceta y el valor es un hashref con los datos de esa faceta, o una matriz de hashrefs. Algunas facetas deben definirse como hashrefs individuales, otras deben definirse como una matriz de hashrefs. Ninguna faceta permite ambos.

facet_data() NO DEBE bendecir los datos que devuelve; el hashref principal y los hashrefs de facetas anidados DEBEN estar vacíos, aunque los elementos contenidos dentro de cada faceta pueden estar bendecidos. Los datos devueltos por este método deberían ser también copias de los datos internos para evitar modificaciones accidentales del estado.

facets() toma los datos de facet_data() y los bendice en los paquetes "Test2::EventFacet::*". Sin embargo, esto rara vez se usa; los paquetes EventFacet son principalmente para conveniencia y documentación. Las clases EventFacet no se utilizan en absoluto internamente, sino que se utilizan los datos sin procesar.

Mantén toda la estructura del archivo.

Nota: Cada tipo único de faceta tiene el campo 'details'. Este campo siempre está destinado para consumo humano y, cuando se proporciona, debe explicar el "por qué" de la faceta. Todos los otros campos son específicos de la faceta.

about => {...}
Test2::EventFacet::About

Esta contiene información sobre el evento en sí, como el nombre del paquete del evento. El campo "details" para esta faceta es un resumen general del evento.

assert => {...}
Test2::EventFacet::Assert

Esta faceta se utiliza si se realizó una aserción. El campo "details" de esta faceta es la descripción de la aserción.

control => {...}
Test2::EventFacet::Control

Esta faceta se utiliza para informar a Test2::Event::Hub sobre acciones especiales que el evento causa. Cosas como detener todas las pruebas, terminar la prueba actual, etc. En esta faceta, el campo "details" explica por qué se tomó cualquier acción especial.

Nota: Así es como se implementa el bail-out.

meta => {...}
Test2::EventFacet::Meta

La faceta meta contiene todos los metadatos adjuntos al evento. En este caso, el campo "details" no tiene un significado especial, pero puede estar presente si algo establece el campo 'details' en el evento.

parent => {...}
Test2::EventFacet::Parent

Esta faceta contiene eventos anidados y detalles similares para subpruebas. En esta faceta, el campo "details" será típicamente el nombre de la subprueba.

plan => {...}
Test2::EventFacet::Plan

Esta faceta informa al sistema que se ha establecido un plan. El campo "details" de esta es normalmente vacío, pero cuando está presente, explica por qué el plan es así; esto es más útil si el plan es para saltar todas las pruebas.

trace => {...}
Test2::EventFacet::Trace

Esta faceta contiene información relacionada con cuándo y dónde se generó el evento. Así es como se conoce el archivo de prueba y el número de línea de un fallo. Esta faceta también puede ayudarte a saber si las pruebas están relacionadas.

En esta faceta, el campo "details" anula el mensaje "failed at test_file.t line 42." proporcionado en un fallo de aserción.

amnesty => [{...}, ...]
Test2::EventFacet::Amnesty

La faceta amnesty es una lista en lugar de un único elemento; esto es importante ya que la amnistía puede provenir de múltiples fuentes a la vez.

Para cada instancia de amnistía, el campo "details" explica por qué se concedió la amnistía.

Nota: Fuera de los formateadores, la amnistía solo actúa para perdonar una aserción fallida.

errors => [{...}, ...]
Test2::EventFacet::Error

La faceta errors es una lista en lugar de un único elemento; se puede listar cualquier número de errores. En esta faceta, el campo "details" describe el error, o puede contener el mensaje de error en sí (como una excepción). En Perl, las excepciones pueden ser objetos serializados, por lo que los datos de esta faceta pueden contener elementos anidados que son serializados.

No todos los errores se consideran catastróficos; hay un campo "fail" que debe establecerse para que un error cause el fallo de la prueba.

Nota: Esta faceta es única en que el nombre del campo es 'errors' mientras que el paquete es 'Error'. Esto se debe a que es el único tipo de faceta que es a la vez una lista y tiene un nombre donde el plural no es el mismo que el singular. Esto puede causar cierta confusión, pero me parece menos confuso que la alternativa.

info => [{...}, ...]
Test2::EventFacet::Info

La faceta info es una lista en lugar de un único elemento; se puede adjuntar cualquier cantidad de información adicional a un evento. Algunas informaciones pueden ser diagnósticos críticos, otras pueden ser simplemente comentarios; esto se determina por el flag "debug".

Para esta faceta, el campo "details" es el info en sí. Este info puede ser una cadena o una estructura de datos para mostrar. Este es uno de los pocos tipos de facetas que pueden contener elementos serializados.

API LEGACY

$bool = $e->causes_fail
Devuelve verdadero si este evento debe resultar en un fallo de prueba. En general, esto debería ser falso.
$bool = $e->increments_count
Debería ser verdadero si este evento debe incrementar el contador de pruebas.
$e->callback($hub)
Si tu evento necesita tener efectos adicionales sobre el Test2::Hub puedes sobrescribir este método.

Esto se llama **ANTES** de que tu evento se envíe al formateador.

$num = $e->nested
Si este evento está anidado en otros eventos, esta debería ser la profundidad del anidamiento. (Esto es principalmente para subpruebas)
$bool = $e->global
Establece esto a verdadero si tu evento es global, es decir, todos los hilos y procesos deben verlo independientemente de cuándo o dónde se genere. Esto no es algo común, se usa para bail-out y skip_all para terminar la prueba.
$code = $e->terminate
Esto se llama **DESPUÉS** de que tu evento se haya enviado al formateador. Normalmente debería devolver undef, solo cambia si tu evento debería causar la salida inmediata de la prueba.

Si quieres que tu evento cause la salida de la prueba, debes devolver el código de salida aquí. El código de salida 0 significa éxito, cualquier otro número significa fallo.

Esto es utilizado por Test2::Event::Plan para salir con 0 cuando el plan es 'skip_all'. También es utilizado por Test2::Event:Bail para forzar la salida de la prueba con un fallo.

Esto se llama después de que el evento ha sido enviado al formateador para asegurar que el evento sea visto y entendido.

$msg = $e->summary
Se espera que esto sea un resumen legible por humanos del evento. Idealmente debería ser una sola línea, pero puedes usar múltiples líneas si es necesario. Esto es para consumo humano. No necesitas hacerlo fácil para las máquinas.

El valor por defecto es simplemente devolver el nombre del paquete del evento.

($count, $directive, $reason) = $e->sets_plan()
Comprueba si este evento establece el plan de prueba. Devuelve una lista vacía si no lo hace. Si lo hace, devuelve una lista de 1 a 3 elementos en orden: contador de pruebas esperado, directiva de prueba, razón de la directiva.
$bool = $e->diagnostics
Verdadero si el evento contiene información de diagnóstico. Esto es útil porque un harness no verboso puede optar por ocultar los eventos que no están en esta categoría. Algunos formateadores pueden optar por enviar estos a STDERR en lugar de STDOUT para asegurarse de que sean vistos.
$bool = $e->no_display
Falso por defecto. Esto devolverá verdadero para los eventos que no deben ser mostrados por los formateadores.
$id = $e->in_subtest
Si el evento está dentro de una subprueba, debería tener el ID de la subprueba.
$id = $e->subtest_id
Si el evento es un evento final de subprueba, debería contener el ID de la subprueba.

Test2::Event

NAME

Test2::Event - Eventos para la interfaz Test2

SYNOPSIS


use Test2::Event;

my $event = Test2::Event::pass( message => "Esto es una prueba" );
my $event = Test2::Event::fail( message => "Esto falla" );
my $event = Test2::Event::skip( message => "Esto se salta" );
my $event = Test2::Event::bail( message => "Esto detiene" );
my $event = Test2::Event::error( message => "Esto es un error" );
my $event = Test2::Event::diag( message => "Esto es un diagnóstico" );
my $event = Test2::Event::explain( message => "Esto es una explicación" );
my $event = Test2::Event::todo( message => "Esto está en TODO" );
my $event = Test2::Event::ok(
    bool => 1,
    name => "Prueba OK",
    diag => "Este es un diagnóstico",
);
my $event = Test2::Event::is(
    got => [ 1, 2, 3 ],
    want => [ 1, 2, 3 ],
    name => "Comprobación de igualdad",
);
my $event = Test2::Event::cmp_ok(
    got => 5,
    op => "==",
    want => 5,
    name => "Comparación numérica",
);
my $event = Test2::Event::JSON::from_json(
    got => { a => 1 },
    want => { a => 1 },
    name => "Comprobación de JSON",
);
my $event = Test2::Event::YAML::from_yaml(
    got => { a => 1 },
    want => { a => 1 },
    name => "Comprobación de YAML",
);
my $event = Test2::Event::Subtest::new(
    plan => Test2::API::plan(subtest => 5),
    name => "Subprueba",
);
my $event = Test2::Event::done;

# Para deserializar un evento
my $event = Test2::Event::from_json($json_string);

DESCRIPTION

Esta clase proporciona los eventos para la interfaz Test2.

Los eventos son objetos que se utilizan para comunicar resultados de pruebas.

Cada evento tiene un tipo y puede contener datos adicionales.
