NOMBRE

Test::Spec - Escribir pruebas en un estilo de especificación declarativa

SINOPSIS

use Test::Spec; # activa automáticamente strict y warnings
describe "Una fecha" => sub {
  my $date;
  describe "en un año bisiesto" => sub {
    before each => sub {
      $date = DateTime->new(year => 2000, month => 2, day => 28);
    };
    it "debería saber que está en un año bisiesto" => sub {
      ok($date->is_leap_year);
    };
    it "debería reconocer el 29 de febrero" => sub {
      is($date->add(days => 1)->day, 29);
    };
  };
  describe "no en un año bisiesto" => sub {
    before each => sub {
      $date = DateTime->new(year => 2001, month => 2, day => 28);
    };
    it "debería saber que NO está en un año bisiesto" => sub {
      ok(!$date->is_leap_year);
    };
    it "NO debería reconocer el 29 de febrero" => sub {
      is($date->add(days => 1)->day, 1);
    };
  };
};
runtests unless caller;
# Genera la siguiente salida:
# ok 1 - Una fecha en un año bisiesto debería saber que está en un año bisiesto
# ok 2 - Una fecha en un año bisiesto debería reconocer el 29 de febrero
# ok 3 - Una fecha no en un año bisiesto debería saber que NO está en un año bisiesto
# ok 4 - Una fecha no en un año bisiesto NO debería reconocer el 29 de febrero
# 1..4

DESCRIPCION

Este es un sistema de pruebas de estilo de especificación declarativa para el desarrollo guiado por comportamiento (BDD) en Perl. Las pruebas (también conocidas como ejemplos) se nombran con cadenas en lugar de nombres de subrutinas, por lo que sus dedos sufrirán menos fatiga por el uso excesivo de guiones bajos, con el beneficio adicional de que los informes de pruebas son más legibles.

Este módulo está inspirado y toma prestado en gran medida de RSpec http://rspec.info/documentation, una herramienta BDD para el lenguaje de programación Ruby.

EXPORTA

Cuando se le da ninguna lista (es decir, "use Test::Spec;"), esta clase exportará:

  • Funciones de definición de especificaciones

    Estas son las funciones que utilizará para definir comportamientos y ejecutar sus especificaciones: "describe", "it", "they", "before", "after", "runtests", "share", "shared_examples_for", "it_should_behave_like" y "spec_helper".

  • Las funciones de stub/mock en Test::Spec::Mocks.
  • Todo lo que Test::More exporta normalmente

    Esto incluye "ok", "is" y similares. Los usará para asegurar el comportamiento correcto.

  • Todo lo que Test::Deep exporta normalmente

    Más aserciones incluyendo "cmp_deeply".

  • Todo lo que "Test::Trap" exporta normalmente

    La función trap(), que le permite probar comportamientos que llaman a exit() y otras cosas difíciles como esa. "Un eval de bloque con esteroides".

Si especifica una lista de importación, solo las funciones directamente de "Test::Spec" (las documentadas a continuación) están disponibles.

FUNCIONES

runtests
runtests(@patrones)
Ejecuta todos los ejemplos cuyas descripciones coinciden con una de las expresiones regulares (no sensibles a mayúsculas y minúsculas) en @patrones. Si @patrones no se proporciona, ejecuta *todos* los ejemplos. La variable de entorno "SPEC" se utilizará como patrón predeterminado si está presente.

Si se llama como una función (es decir, *no* como una llamada a método con "->"), "runtests" autodetectará el paquete desde el cual se llama y ejecutará los ejemplos de ese paquete. Un modismo útil es:

runtests unless caller;

que ejecutará los ejemplos cuando el archivo se cargue como un script (por ejemplo, ejecutándolo desde la línea de comandos), pero no cuando se cargue como un módulo (con "require" o "use").

describe DESCRIPCION => CODE
describe CODE
Define un contexto de especificación bajo el cual se pueden definir ejemplos y más descripciones. Todos los ejemplos *deben* estar dentro de un bloque "describe".
Los bloques de "describe" se pueden anidar para reducir la duplicación en sus especificaciones.
Para especificaciones grandes, los bloques "describe" pueden ahorrarle mucha duplicación: 
describe "Un objeto User" => sub {
  my $user;
  before sub {
    $user = User->new;
  };
  describe "desde un formulario web" => sub {
    before sub {
      $user->init_from_tree({ username => "bbill", ... });
    };
    it "debería leer sus atributos del formulario";
    describe "al guardar" => sub {
      it "debería requerir un nombre de usuario único";
      it "debería requerir una contraseña";
    };
  };
};

El trabajo de configuración realizado en cada bloque "before" se propaga de un nivel al siguiente, por lo que no tiene que llamar manualmente a alguna función de inicialización en cada prueba. Se hace automáticamente según el contexto.

Usar bloques describe mejora la legibilidad sin requerir más escritura.
El nombre del contexto se incluirá por defecto en el informe de éxito/fallo generado por los métodos de prueba basados en Test::Builder (por ejemplo, la función ok() de Test::More). Para un caso como este: 
describe "Una golondrina sin carga" => sub {
  it "tiene una velocidad de 11 metros por segundo" => sub {
    is($swallow->airspeed, "11m/s");
  };
};

La salida generada es:

ok 1 - Una golondrina sin carga tiene una velocidad de 11 metros por segundo

Compare esto con el siguiente caso de prueba para generar la misma salida:

sub unladen_swallow_airspeed : Test {
  is($swallow->airspeed, "11m/s",
     "Una golondrina sin carga tiene una velocidad de 11 metros por segundo");
}

Los bloques "describe" se ejecutan en el orden en que se definen. Se permiten múltiples bloques "describe" con el mismo nombre. No se reemplazan mutuamente, sino que los bloques "describe" posteriores extienden el existente del mismo nombre.

before CÓDIGO
\n
Define el código que se ejecutará antes de que se ejecuten las pruebas en el bloque describe actual. Si se especifica \"cada\", el CÓDIGO se re-ejecutará para cada prueba en el contexto. Si se especifica \"todos\", el CÓDIGO solo se ejecutará antes de la primera prueba.\n

\n El valor predeterminado es \"cada\", debido a esta lógica presentada en la documentación de RSpec:\n

\n

\n "Es muy tentador usar before(:all) y after(:all) para situaciones en las que no es apropiado. before(:all) comparte algo de estado (no todo) entre múltiples ejemplos. Esto significa que los ejemplos se vinculan, lo cual es un absoluto no-no en las pruebas. Realmente solo deberías usar before(:all) para configurar colaboradores globales pero no las cosas que estás describiendo en los ejemplos."\n

\n

\n Los casos más comunes de abuso son el acceso a bases de datos y/o la configuración de fixtures. Cada ejemplo que accede a la base de datos debe comenzar con una pizarra limpia, de lo contrario, los ejemplos se vuelven frágiles y pierden su valor con falsos negativos y, lo que es peor, falsos positivos."\n

\n

(http://rspec.info/documentation/before_and_after.html)\n

\n
Afirma que lo que se está probando actualmente pasa todas las pruebas del grupo de ejemplos identificado por DESCRIPCIÓN (habiendo sido previamente definido con un bloque "shared_examples_for"). share %HASH
\n
Registra %HASH para compartir datos entre pruebas y grupos de ejemplos. Esto te permite compartir variables con código en diferentes ámbitos léxicos sin recurrir al uso de variables de paquete (es decir, globales) o pasar por otros trucos para eludir problemas de ámbito.\n

Cada hash que se "share"d se refiere a los mismos datos. Compartir un hash hará que su contenido existente sea inaccesible, porque después contendrá los mismos datos que todos los demás hashes compartidos. El resultado es que obtienes un hash con semántica global pero con ámbito léxico (asumiendo que %HASH es una variable léxica).\n

\n

Hay varios beneficios de usar "share" sobre el uso de un hash global \"regular\". Primero, no tienes que decidir a qué paquete pertenecerá el hash, lo cual es molesto cuando tienes especificaciones en varios paquetes que hacen referencia a los mismos ejemplos compartidos. Tampoco tienes que abarrotar tus ejemplos con dos puntos para nombres completamente calificados. Por ejemplo, en mi empresa nuestras especificaciones van en la jerarquía \"ICA::TestCase\", y \"$ICA::TestCase::Some::Package::variable\" agota tanto la vista como las manos. Por último, usar "share" permite que "Test::Spec" proporcione esta funcionalidad sin decidir el nombre de la variable por ti (y, por lo tanto, potencialmente sobrescribir una de tus variables).\n

\n 
share %vars;      # %vars ahora se refiere al share global\nshare my %vars;   # declara y comparte %vars en un solo paso\n
\n
\n
spec_helper\n FILESPEC
\n
Carga el código fuente de Perl en "FILESPEC" en el paquete de la especificación actual. Si "FILESPEC" es relativo (sin barra inicial), se trata como relativo al archivo de especificación (es decir, no al script que se está ejecutando actualmente). Esto te permite mantener scripts de ayuda cerca de las especificaciones que utilizan sin ejercitar tus habilidades de File::Spec en tus especificaciones.\n 
# en foo/spec.t\nspec_helper \"helper.pl\";          # carga foo/helper.pl\nspec_helper \"helpers/helper.pl\";  # carga foo/helpers/helper.pl\nspec_helper \"/path/to/helper.pl\"; # carga /path/to/helper.pl\n

NAME

Test::Spec - A Ruby-inspired specification framework for Perl

SYNOPSIS

use Test::Spec;
describe "Array" => sub {
  before each => sub {
    @array = (1, 2, 3);
  };
  it "should have 3 elements" => sub {
    # $browser is available here from the top level
    # it can also be shared via share()
    is(@array, 3);
  };
  it "should contain 3" => sub {
    ok @array ~~ [3];
  };
  after each => sub {
    # clean up if necessary
  };
};
describe "String" => sub {
  # you can define examples that can be shared across multiple
  # descriptions
  it_should_behave_like "all browsers";
  it "should have a length" => sub {
    is(length("foo"), 3);
  };
};
# In another file, say, all_browsers.pl
shared_examples_for "all browsers" => sub {
  # no need to declare share my %vars here
  # it's available from the calling scope
  it "should open a url" => sub {
    ok $browser->open("http://www.example.com/");
  };
};

DESCRIPTION

Test::Spec is a testing framework for Perl that allows you to write tests in a descriptive, human-readable format inspired by RSpec.

Test::Spec allows you to define tests in a nested structure and provides helpful methods like describe, context, it, before, after, and share.

Sharing examples and variables

Sometimes you want to define a set of tests that can be reused across multiple test files. This is where shared_examples_for and it_should_behave_like come in.

The $browser variable in the example above is a lexical variable that is in scope for all the examples. But once those examples are split into multiple files, you would have to use either package global variables or worse, come up with some other hack. This is where "share" and "spec_helper" come in.

# safari.t
package Testcase::Safari;
use Test::Spec;
spec_helper 'all_browsers.pl';
describe "Safari" => sub {
  share my %vars;
  before all => sub { $vars{browser} = Safari->new };
  it_should_behave_like "all browsers";
  it "should have safari features";
};
# firefox.t
package Testcase::Firefox;
use Test::Spec;
spec_helper 'all_browsers.pl';
describe "Firefox" => sub {
  share my %vars;
  before all => sub { $vars{browser} = Firefox->new };
  it_should_behave_like "all browsers";
  it "should have firefox features";
};
# in all_browsers.pl
shared_examples_for "all browsers" => sub {
  # doesn't have to be the same name!
  share my %t;
  it "should open a URL" => sub {
    ok $t{browser}->open("http://www.google.com/");
  };
  ...
};

Order of execution

This example, shamelessly adapted from the RSpec website, gives an overview of the order in which examples run, with particular attention to "before" and "after".

describe Thing => sub {
  before all => sub {
    # This is run once and only once, before all of the examples
    # and before any before("each") blocks.
  };
  before each => sub {
    # This is run before each example.
  };
  before sub {
    # "each" is the default, so this is the same as before("each")
  };
  it "should do stuff" => sub {
    ...
  };
  it "should do more stuff" => sub {
    ...
  };
  after each => sub {
    # this is run after each example
  };
  after sub {
    # "each" is the default, so this is the same as after("each")
  };
  after all => sub {
    # this is run once and only once after all of the examples
    # and after any after("each") blocks
  };
};
