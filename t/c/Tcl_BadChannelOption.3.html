ARGUMENTOS

const Tcl_ChannelType *typePtr (en)
Punta a una estructura que contiene las direcciones de los procedimientos que pueden ser llamados para realizar E/S y otras funciones en el canal.

El nombre de este canal, como file3; no debe estar en uso por ningún otro canal. Puede ser NULL, en cuyo caso el canal se crea sin nombre. Si el canal creado se asigna a uno de los canales estándar (stdin, stdout o stderr), el nombre del canal asignado será el nombre del canal estándar.
ClientData instanceData (en)
Valor arbitrario de una palabra para asociar con este canal. Este valor se pasa a los procedimientos en typePtr cuando se invocan.

Combinación OR de TCL_READABLE y TCL_WRITABLE para indicar si un canal es legible y escribible.
Tcl_Channel channel (en)
El canal sobre el que operar.
int direction (en)
TCL_READABLE significa que se desea el manejador de entrada; TCL_WRITABLE significa que se desea el manejador de salida.
ClientData *handlePtr (salida)
Punta a la ubicación donde se debe almacenar el manejador específico del sistema operativo.
int size (en)
El tamaño, en bytes, de los búferes a asignar en este canal.
int mask (en)
Una combinación OR de TCL_READABLE, TCL_WRITABLE y TCL_EXCEPTION que indica los eventos que han ocurrido en este canal.

Intérprete actual. (puede ser NULL)
const char *optionName (en)
Nombre de la opción inválida.

Lista de opciones específicas (palabras separadas por espacios, sin “-”) para añadir a la lista de opciones genéricas estándar. Puede ser NULL para mostrar solo el mensaje de error de opciones genéricas.

DESCRIPCIÓN

Tcl utiliza una arquitectura de canales de dos capas. Proporciona una capa superior genérica para permitir que los programas C y Tcl realicen entrada y salida utilizando las mismas API para una variedad de archivos, dispositivos, sockets, etc. Las API C genéricas se describen en la entrada del manual para Tcl_OpenFileChannel.

La capa inferior proporciona controladores de canal específicos del tipo para cada tipo de dispositivo soportado en cada plataforma. Esta entrada del manual describe las API C utilizadas para comunicarse entre la capa genérica y los controladores de canal específicos del tipo. También explica cómo se pueden añadir nuevos tipos de canales proporcionando nuevos controladores de canal.

Los controladores de canal consisten en una serie de componentes: Primero, cada controlador de canal proporciona una estructura Tcl_ChannelType que contiene punteros a funciones que implementan las diversas operaciones utilizadas por la capa genérica para comunicarse con el controlador de canal. La estructura Tcl_ChannelType y las funciones a las que se hace referencia en ella se describen en la sección TCL_CHANNELTYPE, más abajo.

Segundo, los controladores de canal suelen proporcionar un comando Tcl para crear instancias de ese tipo de canal. Por ejemplo, el comando Tcl open crea canales que utilizan los controladores de canal de archivo y comando, y el comando Tcl socket crea canales que utilizan sockets TCP para la comunicación de red.

Tercero, un controlador de canal proporciona opcionalmente una función C para abrir instancias de canal de ese tipo. Por ejemplo, Tcl_OpenFileChannel abre un canal que utiliza el controlador de canal de archivo, y Tcl_OpenTcpClient abre un canal que utiliza el protocolo de red TCP. Estas funciones de creación suelen utilizar Tcl_CreateChannel internamente para abrir el canal.

Para añadir un nuevo tipo de canal, debe implementar una API C o un comando Tcl que abra un canal invocando Tcl_CreateChannel. Cuando su controlador llame a Tcl_CreateChannel, pasará una estructura Tcl_ChannelType que describe los procedimientos de E/S del controlador. La capa genérica invocará entonces las funciones referenciadas en esa estructura para realizar operaciones en el canal.

Tcl_CreateChannel abre un nuevo canal y asocia los typePtr e instanceData proporcionados con él. El canal se abre en el modo indicado por mask. Para una discusión de los controladores de canal, sus operaciones y la estructura Tcl_ChannelType, consulte la sección TCL_CHANNELTYPE, más abajo.

Tcl_CreateChannel interactúa con el código que gestiona los canales estándar. Una vez que un canal estándar se inicializó a través de una llamada a Tcl_GetStdChannel o una llamada a Tcl_SetStdChannel, cerrar este canal estándar hará que la siguiente llamada a Tcl_CreateChannel también establezca el nuevo canal como el nuevo canal estándar. Consulte Tcl_StandardChannels para un tratado general sobre los canales estándar y el comportamiento de la biblioteca Tcl con respecto a ellos.

Tcl_GetChannelInstanceData devuelve los datos de instancia asociados con el canal en channel. Esto es lo mismo que el argumento instanceData en la llamada a Tcl_CreateChannel que creó este canal.

Tcl_GetChannelType devuelve un puntero a la estructura Tcl_ChannelType utilizada por el canal en el argumento channel. Esto es lo mismo que el argumento typePtr en la llamada a Tcl_CreateChannel que creó este canal.

Tcl_GetChannelName devuelve una cadena que contiene el nombre asociado con el canal, o NULL si el argumento channelName de Tcl_CreateChannel era NULL.

Tcl_GetChannelHandle coloca el manejador de dispositivo específico del sistema operativo asociado con channel para la dirección dada direction en

de la ubicación especificada por handlePtr y devuelve TCL_OK. Si el canal no tiene un manejador de dispositivo para la dirección especificada, entonces se devuelve TCL_ERROR. Diferentes controladores de canal devolverán diferentes tipos de manejadores. Consulte las entradas del manual para cada controlador para determinar qué tipo de manejador se devuelve.

Tcl_GetChannelThread devuelve el ID del hilo que actualmente gestiona el channel especificado. Esto permite a los controladores de canal enviar sus eventos de archivo a la cola de eventos correcta incluso para un núcleo multihilo.

Tcl_GetChannelMode devuelve una combinación OR de TCL_READABLE y TCL_WRITABLE, indicando si el canal está abierto para entrada y salida.

Tcl_GetChannelBufferSize devuelve el tamaño, en bytes, de los búferes asignados para almacenar entrada o salida en el channel. Si el valor no fue establecido por una llamada anterior a Tcl_SetChannelBufferSize, descrito a continuación, se devuelve el valor predeterminado de 4096.

Tcl_SetChannelBufferSize establece el tamaño, en bytes, de los búferes que se asignarán en operaciones posteriores en el canal para almacenar entrada o salida. El argumento size debe estar entre uno y un millón, permitiendo búferes de un byte a un millón de bytes. Si size está fuera de este rango, Tcl_SetChannelBufferSize establece el tamaño del búfer en 4096.

Tcl_NotifyChannel es llamada por un controlador de canal para indicar a la capa genérica que los eventos especificados por mask han ocurrido en el canal. Los controladores de canal son responsables de invocar esta función cada vez que los manejadores de canal necesiten ser llamados para el canal (o se deban realizar otras tareas pendientes, como un vaciado de escritura). Consulte WATCHPROC a continuación para obtener más detalles.

Tcl_BadChannelOption es llamada desde el setOptionProc o getOptionProc específico del controlador para generar un mensaje de error completo.

Tcl_ChannelBuffered devuelve el número de bytes de entrada actualmente almacenados en el búfer interno (área de retroceso) del propio canal. No informa sobre los datos en los búferes generales de la pila de canales de la que forma parte el canal suministrado.

Tcl_IsChannelShared comprueba el contador de referencias del channel especificado y devuelve si el channel fue compartido entre múltiples intérpretes (resultado == 1) o no (resultado == 0).

Tcl_IsChannelRegistered comprueba si el channel especificado está registrado en el interpretador dado (resultado == 1) o no (resultado == 0).

Tcl_IsChannelExisting comprueba si un canal con el nombre especificado está registrado en la lista global de todos los canales (del hilo) (resultado == 1) o no (resultado == 0).

Tcl_CutChannel elimina el channel especificado de la lista global (del hilo) de todos los canales (del hilo actual). No se permite la aplicación a un canal todavía registrado en algún intérprete. También notifica al controlador si la versión de Tcl_ChannelType es TCL_CHANNEL_VERSION_4 (o superior), y Tcl_DriverThreadActionProc está definida para él.

Tcl_SpliceChannel agrega el channel especificado a la lista global (del hilo) de todos los canales (del hilo actual). No se permite la aplicación a un canal registrado en algún intérprete. También notifica al controlador si la versión de Tcl_ChannelType es TCL_CHANNEL_VERSION_4 (o superior), y Tcl_DriverThreadActionProc está definida para él.

Tcl_ClearChannelHandlers elimina todos los manejadores de canal y los scripts de eventos asociados con el channel especificado, cerrando así todo el procesamiento de eventos para este canal.

TCL_CHANNELTYPE

Un controlador de canal proporciona una estructura Tcl_ChannelType que contiene punteros a funciones que implementan las diversas operaciones en un canal; estas operaciones se invocan según sea necesario por la capa genérica. La estructura fue versionada a partir de Tcl 8.3.2/8.4 para corregir un problema con los controladores de canal apilados. Consulte la sección TIPOS DE CANAL ANTIGUOS a continuación para obtener detalles sobre la estructura antigua.

La estructura Tcl_ChannelType contiene los siguientes campos:

typedef struct Tcl_ChannelType {
        const char *typeName;
        Tcl_ChannelTypeVersion version;
        Tcl_DriverCloseProc *closeProc;
        Tcl_DriverInputProc *inputProc;
        Tcl_DriverOutputProc *outputProc;
        Tcl_DriverSeekProc *seekProc;
        Tcl_DriverSetOptionProc *setOptionProc;
        Tcl_DriverGetOptionProc *getOptionProc;
        Tcl_DriverWatchProc *watchProc;
        Tcl_DriverGetHandleProc *getHandleProc;
        Tcl_DriverClose2Proc *close2Proc;
        Tcl_DriverBlockModeProc *blockModeProc;
        Tcl_DriverFlushProc *flushProc;
        Tcl_DriverHandlerProc *handlerProc;
        Tcl_DriverWideSeekProc *wideSeekProc;
        Tcl_DriverThreadActionProc *threadActionProc;
        Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

No es necesario proporcionar implementaciones para todas las operaciones del canal. Aquellas que no sean necesarias pueden establecerse en NULL en la estructura: blockModeProc, seekProc, setOptionProc, getOptionProc, getHandleProc y close2Proc, además de flushProc, handlerProc, threadActionProc y truncateProc. Otras funciones que no se pueden implementar de forma significativa deben devolver EINVAL cuando se llamen, para indicar que las operaciones que representan no están disponibles. Tenga en cuenta también que wideSeekProc puede ser NULL si seekProc lo es.

El usuario solo debe usar la estructura anterior para la instanciación de Tcl_ChannelType. Al hacer referencia a campos en una estructura Tcl_ChannelType, se deben utilizar las siguientes funciones para obtener los valores: Tcl_ChannelName, Tcl_ChannelVersion, Tcl_ChannelBlockModeProc, Tcl_ChannelCloseProc, Tcl_ChannelClose2Proc, Tcl_ChannelInputProc, Tcl_ChannelOutputProc, Tcl_ChannelSeekProc, Tcl_ChannelWideSeekProc, Tcl_ChannelThreadActionProc, Tcl_ChannelTruncateProc, Tcl_ChannelSetOptionProc, Tcl_ChannelGetOptionProc, Tcl_ChannelWatchProc, Tcl_ChannelGetHandleProc, Tcl_ChannelFlushProc o Tcl_ChannelHandlerProc.

El cambio en las estructuras se realizó de tal manera que los tipos de canal estándar son compatibles binariamente. Sin embargo, los tipos de canal que utilizan canales apilados (es decir, TLS, Trf) tienen nuevas versiones para corresponder con el cambio anterior, ya que el código anterior para canales apilados tenía problemas.

TYPENAME

El campo typeName contiene una cadena terminada en nulo que identifica el tipo de dispositivo implementado por este controlador, por ejemplo, file o socket.

Este valor se puede recuperar con Tcl_ChannelName, que devuelve un puntero a la cadena.

VERSION

El campo version debe establecerse en la versión de la estructura que requiere. TCL_CHANNEL_VERSION_2 es el mínimo recomendado. TCL_CHANNEL_VERSION_3 debe establecerse para especificar el miembro wideSeekProc. TCL_CHANNEL_VERSION_4 debe establecerse para especificar el miembro threadActionProc (incluye wideSeekProc). TCL_CHANNEL_VERSION_5 debe establecerse para especificar los miembros truncateProc (incluye wideSeekProc y threadActionProc). Si no se establece en ninguno de estos, se asume que este Tcl_ChannelType tiene la estructura original. Consulte TIPOS DE CANAL ANTIGUOS para obtener más detalles. Si bien Tcl reconocerá y funcionará con ambas estructuras, los canales apilados deben ser como mínimo de TCL_CHANNEL_VERSION_2 para funcionar correctamente.

Este valor se puede recuperar con Tcl_ChannelVersion, que devuelve uno de TCL_CHANNEL_VERSION_5, TCL_CHANNEL_VERSION_4, TCL_CHANNEL_VERSION_3, TCL_CHANNEL_VERSION_2 o TCL_CHANNEL_VERSION_1.

BLOCKMODEPROC

El campo blockModeProc contiene la dirección de una función llamada por la capa genérica para establecer el modo bloqueante y no bloqueante en el dispositivo. BlockModeProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverBlockModeProc(
        ClientData instanceData,
        int mode);

El instanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando se creó este canal. El argumento mode es TCL_MODE_BLOCKING o TCL_MODE_NONBLOCKING para establecer el dispositivo en modo bloqueante o no bloqueante. La función debe devolver cero si la operación fue exitosa, o un código de error POSIX distinto de cero si la operación falló.

Si la operación es exitosa, la función puede modificar el instanceData proporcionado para registrar que el canal entró en modo bloqueante o no bloqueante y para implementar el comportamiento bloqueante o no bloqueante. Para algunos tipos de dispositivos, el comportamiento bloqueante y no bloqueante puede ser implementado por el sistema operativo subyacente; para otros tipos de dispositivos, el comportamiento debe ser emulado en el controlador de canal.

Este valor se puede recuperar con Tcl_ChannelBlockModeProc, que devuelve un puntero a la función.

Un controlador de canal que no proporciona un blockModeProc debe ser muy, muy cuidadoso. Debe indicar a la capa genérica exactamente qué modo bloqueante es aceptable para él, y también debe documentar esto para el usuario para que el modo bloqueante del canal no se cambie a un valor inaceptable. Cualquier confusión aquí puede llevar al intérprete a un interbloqueo (falso y difícil de encontrar).

CLOSEPROC Y CLOSE2PROC

El campo closeProc contiene la dirección de una función llamada por la capa genérica para limpiar la información relacionada con el controlador cuando se cierra el canal. CloseProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverCloseProc(
        ClientData instanceData,
        Tcl_Interp *interp);

El argumento instanceData es el mismo que el valor proporcionado a Tcl_CreateChannel cuando se creó el canal. La función debe liberar cualquier almacenamiento mantenido por el controlador de canal para este canal, y cerrar los dispositivos de entrada y salida encapsulados por este canal. Todo el resultado en cola se habrá vaciado al dispositivo antes de que se llame a esta función, y no se invocarán más operaciones del controlador en esta instancia después de llamar a closeProc. Si la operación de cierre es exitosa, el procedimiento

debería devolver cero; de lo contrario, debería devolver un código de error POSIX distinto de cero. Además, si ocurre un error y interp no es NULL, el procedimiento debería almacenar un mensaje de error en el resultado del intérprete.

Alternativamente, los canales que admiten el cierre de los lados de lectura y escritura de forma independiente pueden establecer closeProc en TCL_CLOSE2PROC y establecer close2Proc en la dirección de una función que coincida con el siguiente prototipo:

typedef int Tcl_DriverClose2Proc(
        ClientData instanceData,
        Tcl_Interp *interp,
        int flags);

Se llamará a close2Proc con flags establecido en una combinación OR de TCL_CLOSE_READ o TCL_CLOSE_WRITE para indicar que el controlador debe cerrar el lado de lectura y/o escritura del canal. Se puede invocar al controlador del canal para realizar operaciones adicionales en el canal después de que se llame a close2Proc para cerrar uno o ambos lados del canal. Si flags es 0 (cero), el controlador debe cerrar el canal de la manera descrita anteriormente para closeProc. No se invocarán más operaciones en esta instancia después de que se llame a close2Proc con todas las banderas borradas. En todos los casos, la función close2Proc debería devolver cero si la operación de cierre fue exitosa; de lo contrario, debería devolver un código de error POSIX distinto de cero. Además, si ocurre un error y interp no es NULL, el procedimiento debería almacenar un mensaje de error en el resultado del intérprete.

Los valores closeProc y close2Proc se pueden recuperar con Tcl_ChannelCloseProc o Tcl_ChannelClose2Proc, que devuelven un puntero a la función respectiva.

INPUTPROC

El campo inputProc contiene la dirección de una función llamada por la capa genérica para leer datos del archivo o dispositivo y almacenarlos en un búfer interno. InputProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverInputProc(
        ClientData instanceData,
        char *buf,
        int bufSize,
        int *errorCodePtr);

InstanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando se creó el canal. El argumento buf apunta a una matriz de bytes en la que se almacenará la entrada del dispositivo, y el argumento bufSize indica cuántos bytes están disponibles en buf.

El argumento errorCodePtr apunta a una variable entera proporcionada por la capa genérica. Si ocurre un error, la función debe establecer la variable en un código de error POSIX que identifique el error que ocurrió.

La función debe leer datos del dispositivo de entrada encapsulado por el canal y almacenarlos en buf. En caso de éxito, la función debe devolver un entero no negativo que indique cuántos bytes se leyeron del dispositivo de entrada y se almacenaron en buf. En caso de error, la función debe devolver -1. Si ocurre un error después de que se hayan leído algunos datos del dispositivo, esos datos se pierden.

Si inputProc puede determinar que el dispositivo de entrada tiene algunos datos disponibles pero menos de los solicitados por el argumento bufSize, la función solo debe intentar leer tantos datos como estén disponibles y devolver sin bloquear. Si el dispositivo de entrada no tiene ningún dato disponible en absoluto y el canal está en modo no bloqueante, la función debe devolver un error EAGAIN. Si el dispositivo de entrada no tiene ningún dato disponible y el canal está en modo bloqueante, la función debe bloquearse durante el menor tiempo posible hasta que se pueda leer al menos un byte de datos del dispositivo; luego, debe devolver tantos datos como pueda leer sin bloquear.

Este valor se puede recuperar con Tcl_ChannelInputProc, que devuelve un puntero a la función.

OUTPUTPROC

El campo outputProc contiene la dirección de una función llamada por la capa genérica para transferir datos de un búfer interno al dispositivo de salida. OutputProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverOutputProc(
        ClientData instanceData,
        const char *buf,
        int toWrite,
        int *errorCodePtr);

InstanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando se creó el canal. El argumento buf contiene una matriz de bytes que se escribirán en el dispositivo, y el argumento toWrite indica cuántos bytes se escribirán desde el argumento buf.

El argumento errorCodePtr apunta a una variable entera proporcionada por la capa genérica. Si ocurre un error, la función debe establecer esta variable en un código de error POSIX que identifique el error.

La función debe escribir los datos en buf en el dispositivo de salida encapsulado por el canal. En caso de éxito, la función debe devolver un entero no negativo que indique cuántos bytes se escribieron en el dispositivo de salida. El valor de retorno es normalmente el mismo que toWrite, pero puede ser menor en algunos casos, como si la operación de salida se interrumpe por una señal. Si ocurre un error, la función debe devolver -1. En caso de error, es posible que se hayan escrito algunos datos en el dispositivo.

Si el canal no está bloqueado y el dispositivo de salida no puede absorber ningún dato en absoluto, la función debe devolver -1 con un error EAGAIN sin escribir ningún dato.

Este valor se puede recuperar con Tcl_ChannelOutputProc, que devuelve un puntero a la función.

SEEKPROC Y WIDESEEKPROC

El campo seekProc contiene la dirección de una función llamada por la capa genérica para mover el punto de acceso en el que se aplicarán las operaciones de entrada o salida posteriores. SeekProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverSeekProc(
        ClientData instanceData,
        long offset,
        int seekMode,
        int *errorCodePtr);

El argumento instanceData es el mismo que el valor dado a Tcl_CreateChannel cuando se creó este canal. Offset y seekMode tienen el mismo significado que para el procedimiento Tcl_Seek (descrito en la entrada del manual de Tcl_OpenFileChannel).

El argumento errorCodePtr apunta a una variable entera proporcionada por la capa genérica para devolver valores errno de la función. La función debe establecer esta variable en un código de error POSIX si ocurre un error. La función debe almacenar un código de error EINVAL si el tipo de canal no implementa el desplazamiento.

El valor de retorno es el nuevo punto de acceso o -1 en caso de error. Si ocurrió un error, la función no debe mover el punto de acceso.

Si hay un campo seekProc no NULL, el campo wideSeekProc puede contener la dirección de una función alternativa a utilizar que maneje desplazamientos anchos (es decir, mayores de 32 bits), lo que permite desplazamientos dentro de archivos de más de 2 GB. Se llamará a wideSeekProc en preferencia a seekProc, pero ambos deben definirse si se define wideSeekProc. WideSeekProc debe coincidir con el siguiente prototipo:

typedef Tcl_WideInt Tcl_DriverWideSeekProc(
        ClientData instanceData,
        Tcl_WideInt offset,
        int seekMode,
        int *errorCodePtr);

Los argumentos y valores de retorno significan lo mismo que con seekProc arriba, excepto que el tipo de desplazamientos y el tipo de retorno son diferentes.

El valor seekProc se puede recuperar con Tcl_ChannelSeekProc, que devuelve un puntero a la función, y de manera similar, wideSeekProc se puede recuperar con Tcl_ChannelWideSeekProc.

SETOPTIONPROC

El campo setOptionProc contiene la dirección de una función llamada por la capa genérica para establecer una opción específica del tipo de canal en un canal. setOptionProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverSetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        const char *newValue);

optionName es el nombre de una opción a establecer, y newValue es el nuevo valor para esa opción, como una cadena. instanceData es el mismo que el valor dado a Tcl_CreateChannel cuando se creó este canal. La función debe realizar cualquier acción específica del tipo de canal que sea necesaria para implementar el nuevo valor de la opción.

Algunas opciones son manejadas por el código genérico y esta función nunca se llama para establecerlas, por ejemplo, -blockmode. Otras opciones son específicas de cada tipo de canal y se llamará al procedimiento setOptionProc del controlador del canal para implementarlas. El campo setOptionProc puede ser NULL, lo que indica que este tipo de canal no admite opciones específicas del tipo.

Si el valor de la opción se modifica correctamente al nuevo valor, la función devuelve TCL_OK. Debe llamar a Tcl_BadChannelOption, que a su vez devuelve TCL_ERROR si el optionName no se reconoce. Si newValue especifica un valor para la opción que no es compatible o si ocurre un error de llamada al sistema, la función debe dejar un mensaje de error en el resultado de interp si interp no es NULL. La función también debe llamar a Tcl_SetErrno para almacenar un código de error POSIX apropiado.

Este valor se puede recuperar con Tcl_ChannelSetOptionProc, que devuelve un puntero a la función.

GETOPTIONPROC

El campo getOptionProc contiene la dirección de una función llamada por la capa genérica para obtener el valor de una opción específica del tipo de canal en un canal. getOptionProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverGetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        Tcl_DString *optionValue);

OptionName es el nombre de una opción admitida por este tipo de canal. Si el nombre de la opción no es NULL, la función almacena su valor actual, como una cadena, en la cadena dinámica de Tcl optionValue. Si optionName es NULL, la función almacena en optionValue una lista alterna de todas las opciones admitidas y sus valores actuales. En caso de éxito, la función devuelve TCL_OK. Debe llamar a Tcl_BadChannelOption, que a su vez devuelve TCL_ERROR si el option

Tcl_ChannelType

Un Tcl_ChannelType estructura define un tipo de canal. Esta estructura se pasa a la rutina Tcl_CreateChannel para registrar un nuevo tipo de canal con el sistema de canales Tcl.

La estructura Tcl_ChannelType tiene los siguientes campos:

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
    Tcl_DriverFlushProc *flushProc;
    Tcl_DriverHandlerProc *handlerProc;
    Tcl_DriverThreadActionProc *threadActionProc;
    Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;
typeName
El nombre del tipo de canal, por ejemplo, "file" o "socket". Este nombre se utiliza para registrar el tipo de canal con el sistema de canales Tcl.
blockModeProc
Un puntero a la función Tcl_DriverBlockModeProc. Esta función se llama cuando el modo de bloqueo de un canal cambia. Debe devolver el modo de bloqueo anterior. Si el modo de bloqueo no se puede establecer en el valor deseado, la función debe dejar un mensaje de error en el resultado de interp si interp no es NULL. La función también debe llamar a Tcl_SetErrno para almacenar un código de error POSIX apropiado.
closeProc
Un puntero a la función Tcl_DriverCloseProc. Esta función se llama cuando se cierra un canal. Debe liberar cualquier recurso asociado con el canal.
inputProc
Un puntero a la función Tcl_DriverInputProc. Esta función se llama para leer datos de un canal. Debe devolver el número de bytes leídos o -1 en caso de error.
outputProc
Un puntero a la función Tcl_DriverOutputProc. Esta función se llama para escribir datos en un canal. Debe devolver el número de bytes escritos o -1 en caso de error.
seekProc
Un puntero a la función Tcl_DriverSeekProc. Esta función se llama para buscar una posición en un canal. Debe devolver la nueva posición en el canal o -1 en caso de error.
setOptionProc
Un puntero a la función Tcl_DriverSetOptionProc. Esta función se llama para establecer una opción en un canal. Debe devolver TCL_OK si la opción se estableció correctamente, o TCL_ERROR en caso de error. Si ocurre un error del sistema, la función debe dejar un mensaje de error en el resultado de interp si interp no es NULL. La función también debe llamar a Tcl_SetErrno para almacenar un código de error POSIX apropiado.
getOptionProc
Un puntero a la función Tcl_DriverGetOptionProc. Esta función se llama para obtener el valor de una opción de un canal. Debe devolver TCL_OK si la opción se obtuvo correctamente, o TCL_ERROR en caso de error. Si ocurre un error del sistema, la función debe dejar un mensaje de error en el resultado de interp si interp no es NULL. La función también debe llamar a Tcl_SetErrno para almacenar un código de error POSIX apropiado.
watchProc
Un puntero a la función Tcl_DriverWatchProc. Esta función se llama para inicializar el mecanismo de notificación de eventos para un canal. Debe llamar a Tcl_NotifyChannel cuando ocurra un evento en el canal.
getHandleProc
Un puntero a la función Tcl_DriverGetHandleProc. Esta función se llama para obtener el identificador específico del dispositivo para un canal. Debe devolver TCL_OK si el identificador se obtuvo correctamente, o TCL_ERROR en caso de error.
close2Proc
Un puntero a la función Tcl_DriverClose2Proc. Esta función se llama cuando se cierra un canal. Es similar a closeProc, pero también toma un argumento skip que indica si se deben omitir los datos pendientes en el canal.
flushProc
Actualmente reservado para uso futuro. Debe establecerse en NULL.
handlerProc
Un puntero a la función Tcl_DriverHandlerProc. Esta función se llama para notificar al canal que ha ocurrido un evento. Se define para controladores de canales apilados que desean ser notificados de eventos que ocurren en el canal subyacente (apilado).
threadActionProc
Un puntero a la función Tcl_DriverThreadActionProc. Esta función se llama cuando un canal se crea, se cierra o se va a mover a un hilo diferente. Se utiliza para inicializar o actualizar el estado específico del hilo para un canal.
truncateProc
Un puntero a la función Tcl_DriverTruncateProc. Esta función se llama cuando un canal se trunca a una longitud determinada. Debe devolver 0 en caso de éxito o un código errno en caso de error.

Algunas opciones son manejadas por el código genérico y esta función nunca se llama para recuperar su valor, por ejemplo, -blockmode. Otras opciones son específicas de cada tipo de canal y la rutina getOptionProc del controlador del canal se llamará para implementarlas. El campo getOptionProc puede ser NULL, lo que indica que este tipo de canal no admite opciones específicas del tipo.

Este valor puede recuperarse con Tcl_ChannelGetOptionProc, que devuelve un puntero a la función.

WATCHPROC

El campo watchProc contiene la dirección de una función llamada por la capa genérica para inicializar el mecanismo de notificación de eventos para detectar eventos de interés en este canal. WatchProc debe coincidir con el siguiente prototipo:

typedef void Tcl_DriverWatchProc(
        ClientData instanceData,
        int mask);

El instanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó este canal. El argumento mask es una combinación OR de TCL_READABLE, TCL_WRITABLE y TCL_EXCEPTION; indica los eventos que el llamador está interesado en detectar en este canal.

La función debe inicializar mecanismos específicos del tipo de dispositivo para detectar cuándo hay un evento de interés presente en el canal. Cuando ocurre uno o más de los eventos designados en el canal, el controlador del canal es responsable de llamar a Tcl_NotifyChannel para informar al módulo genérico de canales. El controlador debe tener cuidado de no dejar morir a otros controladores de canales o fuentes de devoluciones de llamadas invocando Tcl_NotifyChannel con demasiada frecuencia. La equidad se puede garantizar utilizando la cola de eventos de Tcl para permitir que el evento del canal se programe en secuencia con otros eventos. Consulte la descripción de Tcl_QueueEvent para obtener detalles sobre cómo poner en cola un evento.

Este valor puede recuperarse con Tcl_ChannelWatchProc, que devuelve un puntero a la función.

GETHANDLEPROC

El campo getHandleProc contiene la dirección de una función llamada por la capa genérica para recuperar un identificador específico del dispositivo del canal. GetHandleProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverGetHandleProc(
        ClientData instanceData,
        int direction,
        ClientData *handlePtr);

InstanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó este canal. El argumento direction es TCL_READABLE para recuperar el identificador utilizado para la entrada, o TCL_WRITABLE para recuperar el identificador utilizado para la salida.

Si la implementación del canal tiene identificadores específicos del dispositivo, la función debe recuperar el identificador apropiado asociado con el canal, según el argumento direction. El identificador debe almacenarse en la ubicación a la que apunta handlePtr, y se debe devolver TCL_OK. Si el canal no está abierto para la dirección especificada, o si la implementación del canal no utiliza identificadores de dispositivo, la función debe devolver TCL_ERROR.

Este valor puede recuperarse con Tcl_ChannelGetHandleProc, que devuelve un puntero a la función.

FLUSHPROC

El campo flushProc está actualmente reservado para uso futuro. Debe establecerse en NULL. FlushProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverFlushProc(
        ClientData instanceData);

Este valor puede recuperarse con Tcl_ChannelFlushProc, que devuelve un puntero a la función.

HANDLERPROC

El campo handlerProc contiene la dirección de una función llamada por la capa genérica para notificar al canal que ha ocurrido un evento. Debe definirse para los controladores de canales apilados que deseen ser notificados de eventos que ocurren en el canal subyacente (apilado). HandlerProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverHandlerProc(
        ClientData instanceData,
        int interestMask);

InstanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó este canal. El interestMask es una combinación OR de TCL_READABLE o TCL_WRITABLE; indica qué tipo de evento ocurrió en este canal.

Este valor puede recuperarse con Tcl_ChannelHandlerProc, que devuelve un puntero a la función.

THREADACTIONPROC

El campo threadActionProc contiene la dirección de la función llamada por la capa genérica cuando se crea, se cierra o se va a mover a un hilo diferente un canal, es decir, cada vez que el estado específico del hilo del controlador pueda tener que inicializarse o actualizarse. Puede ser NULL. La acción TCL_CHANNEL_THREAD_REMOVE se utiliza para notificar al controlador que debe actualizar o eliminar cualquier dato específico del hilo que pueda estar manteniendo para el canal.

La acción TCL_CHANNEL_THREAD_INSERT se utiliza para notificar al controlador que debe actualizar o inicializar cualquier dato específico del hilo que pueda estar manteniendo utilizando el hilo que realiza la llamada como asociado. Consulte Tcl_CutChannel y Tcl_SpliceChannel para obtener más detalles.

typedef void Tcl_DriverThreadActionProc(
        ClientData instanceData,
        int action);

InstanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó este canal.

Estos valores pueden recuperarse con Tcl_ChannelThreadActionProc, que devuelve un puntero a la función.

TRUNCATEPROC

El campo truncateProc contiene la dirección de la función llamada por la capa genérica cuando un canal se trunca a cierta longitud. Puede ser NULL.

typedef int Tcl_DriverTruncateProc(
        ClientData instanceData,
        Tcl_WideInt length);

InstanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó este canal, y length es la nueva longitud del archivo subyacente, que no debe ser negativa. El resultado debe ser 0 en caso de éxito o un código errno (adecuado para su uso con Tcl_SetErrno) en caso de fallo.

Estos valores pueden recuperarse con Tcl_ChannelTruncateProc, que devuelve un puntero a la función.

TCL_BADCHANNELOPTION

Este procedimiento genera un mensaje de error de "opción no válida" en un intérprete (opcional). Se utiliza por los controladores de canales cuando se solicita una opción Set/Get inválida. Su propósito es concatenar la lista genérica de opciones a las específicas y factorizar el mensaje de error de las opciones genéricas.

Siempre devuelve TCL_ERROR

Se genera un mensaje de error en el valor de resultado de interp para indicar que se invocó un comando con una opción incorrecta. El mensaje tiene el formato

    opción incorrecta "blah": debería ser una de
    <...opciones genéricas...>+<...opciones específicas...>
por lo que obtiene, por ejemplo: 
    opción incorrecta "-blah": debería ser una de -blocking,
    -buffering, -buffersize, -eofchar, -translation,
    -peername, o -sockname
cuando se llama con optionList igual a "peername sockname"

"blah" es el argumento optionName y "<opciones específicas>" es una lista separada por espacios de palabras de opciones específicas. La función se encarga de insertar signos menos antes de cada opción, comas después y un "o" antes de la última opción.

TIPOS DE CANALES ANTIGUOS

La estructura original (8.3.1 y anteriores) Tcl_ChannelType contiene los siguientes campos:

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
} Tcl_ChannelType;

Todavía es posible crear canales con la estructura anterior. El código interno de canales determinará la versión. Es imperativo utilizar la nueva estructura Tcl_ChannelType si está creando un controlador de canales apilado, debido a problemas con la implementación anterior de canales apilados (en 8.2.0 a 8.3.1).

Antes de 8.4.0 (es decir, durante las últimas versiones de 8.3 y la parte inicial del ciclo de desarrollo de 8.4), la estructura Tcl_ChannelType contenía los siguientes campos:

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_ChannelTypeVersion version;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverFlushProc *flushProc;
    Tcl_DriverHandlerProc *handlerProc;
    Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

Cuando la estructura anterior se registra como un tipo de canal, el campo version siempre debe ser TCL_CHANNEL_VERSION_2.

NAME

Tcl_BadChannelOption - handle unknown channel options

SYNOPSIS

#include <tcl.h>

int
Tcl_BadChannelOption(interp, channel, optionName, opt, mask)

ARGUMENTS

<code>Tcl_Interp *interp</code> (in)
Interpreter to use for reporting errors.
<code>Tcl_Channel channel</code> (in)
The channel for which an unknown option was seen. This argument is used to check if the channel is valid; otherwise, it may be NULL.
<code>const char *optionName</code> (in)
The name of the option that was not recognized.
<code>const char *opt</code> (in)
The specific channel option string (e.g., "-myoption") that was not recognized. This is used to generate a more specific error message.
<code>int mask</code> (in)
A bitmask indicating which options are valid for the given channel. This is used to generate a more specific error message.

DESCRIPTION

This procedure is a utility function to be used by channel drivers when processing channel options. It is called when a channel driver encounters an option that it does not recognize. The function will generate a standard Tcl error message reporting the unknown option and return TCL_ERROR.

The error message will be of the form:

bad option "-<optionName>" for channel "<channelName>"; must be one of ...

where <channelName> is the name of the channel and <optionName> is the value of the <code>opt</code> argument. The "must be one of ..." part is generated by using the <code>mask</code> argument.

TCL_CHANNELTYPE

The <code>mask</code> argument is a bitmask where each bit corresponds to a specific channel option. Tcl provides several standard masks that can be used:

<code>TCL_CHANNEL_READABLE</code>
Indicates the channel can be read from.
<code>TCL_CHANNEL_WRITABLE</code>
Indicates the channel can be written to.
<code>TCL_CHANNEL_APPEND</code>
Indicates the channel supports append mode.
<code>TCL_CHANNEL_BLOCKING</code>
Indicates the channel supports blocking/nonblocking modes.
<code>TCL_CHANNEL_EOF</code>
Indicates the channel supports EOF events.
<code>TCL_CHANNEL_TRANSLATION</code>
Indicates the channel supports translation modes.
<code>TCL_CHANNEL_START_LINE</code>
Indicates the channel supports START_LINE mode.
<code>TCL_CHANNEL_END_LINE</code>
Indicates the channel supports END_LINE mode.
<code>TCL_CHANNEL_DELETE_SO</code>
Indicates the channel supports DELETE_SO mode.
<code>TCL_CHANNEL_BINARY</code>
Indicates the channel supports binary mode.
<code>TCL_CHANNEL_UXSPECIAL</code>
Indicates the channel supports special Unix-like options.

Channel drivers can combine these masks using the bitwise OR operator. For example, a channel driver that supports reading and writing and blocking/nonblocking modes would use <code>TCL_CHANNEL_READABLE | TCL_CHANNEL_WRITABLE | TCL_CHANNEL_BLOCKING</code>.

TCL_BADCHANNELOPTION

This procedure is a utility function to be used by channel drivers when processing channel options. It is called when a channel driver encounters an option that it does not recognize. The function will generate a standard Tcl error message reporting the unknown option and return TCL_ERROR.

The error message will be of the form:

bad option "-<optionName>" for channel "<channelName>"; must be one of ...

where <channelName> is the name of the channel and <optionName> is the value of the <code>opt</code> argument. The "must be one of ..." part is generated by using the <code>mask</code> argument.

OLD CHANNEL TYPES

This function supersedes the older Tcl_GetChannelOption and Tcl_SetChannelOption functions. It is recommended to use this function when dealing with channel options.
