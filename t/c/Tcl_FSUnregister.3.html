DESCRIPTION

There are several reasons for calling the Tcl_FS API functions (e.g. Tcl_FSAccess and Tcl_FSStat) rather than calling system level functions like access and stat directly. First, they will work cross-platform, so an extension which calls them should work unmodified on Unix and Windows. Second, the Windows implementation of some of these functions fixes some bugs in the system level calls. Third, these function calls deal with any “Utf to platform-native” path conversions which may be required (and may cache the results of such conversions for greater efficiency on subsequent calls). Fourth, and perhaps most importantly, all of these functions are “virtual filesystem aware”. Any virtual filesystem (VFS for short) which has been registered (through Tcl_FSRegister) may reroute file access to alternative media or access methods. This means that all of these functions (and therefore the corresponding file, glob, pwd, cd, open, etc. Tcl commands) may be operate on “files” which are not native files in the native filesystem. This also means that any Tcl extension which accesses the filesystem (FS for short) through this API is automatically “virtual filesystem aware”. Of course, if an extension accesses the native filesystem directly (through platform-specific APIs, for example), then Tcl cannot intercept such calls.

If appropriate VFSes have been registered, the “files” may, to give two examples, be remote (e.g. situated on a remote ftp server) or archived (e.g. lying inside a .zip archive). Such registered filesystems provide a lookup table of functions to implement all or some of the functionality listed here. Finally, the Tcl_FSStat and Tcl_FSLstat calls abstract away from what the “struct stat” buffer is actually declared to be, allowing the same code to be used both on systems with and systems without support for files larger than 2GB in size.

The Tcl_FS API is Tcl_Obj-ified and may cache internal representations and other path-related strings (e.g. the current working directory). One side-effect of this is that one must not pass in values with a reference count of zero to any of these functions. If such calls were handled, they might result in memory leaks (under some circumstances, the filesystem code may wish to retain a reference to the passed in value, and so one must not assume that after any of these calls return, the value still has a reference count of zero - it may have been incremented) or in a direct segmentation fault (or other memory access error) due to the value being freed part way through the complex value manipulation required to ensure that the path is fully normalized and absolute for filesystem determination. The practical lesson to learn from this is that

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

is wrong, and may cause memory errors. The path must have its reference count incremented before passing it in, or decrementing it. For this reason, values with a reference count of zero are considered not to be valid filesystem paths and calling any Tcl_FS API function with such a value will result in no action being taken.

FS API FUNCTIONS

Tcl_FSCopyFile attempts to copy the file given by srcPathPtr to the path name given by destPathPtr. If the two paths given lie in the same filesystem (according to Tcl_FSGetFileSystemForPath) then that filesystem's “copy file” function is called (if it is non-NULL). Otherwise the function returns -1 and sets the errno global C variable to the “EXDEV” POSIX error code (which signifies a “cross-domain link”).

Tcl_FSCopyDirectory attempts to copy the directory given by srcPathPtr to the path name given by destPathPtr. If the two paths given lie in the same filesystem (according to Tcl_FSGetFileSystemForPath) then that filesystem's “copy file” function is called (if it is non-NULL). Otherwise the function returns -1 and sets the errno global C variable to the “EXDEV” POSIX error code (which signifies a “cross-domain link”).

Tcl_FSCreateDirectory attempts to create the directory given by pathPtr by calling the owning filesystem's “create directory” function.

Tcl_FSDeleteFile attempts to delete the file given by pathPtr by calling the owning filesystem's “delete file” function.

Tcl_FSRemoveDirectory attempts to remove the directory given by pathPtr by calling the owning filesystem's “remove directory” function.

Tcl_FSRenameFile attempts to rename the file or directory given by srcPathPtr to the path name given by destPathPtr. If the two paths given lie in the same filesystem (according to Tcl_FSGetFileSystemForPath) then that filesystem's “rename file” function is called (if it is non-NULL). Otherwise the function returns -1 and sets the errno global C variable to the “EXDEV” POSIX error code (which signifies a “cross-domain link”).

Tcl_FSListVolumes calls each filesystem which has a non-NULL “list volumes” function and asks them to return their list of root volumes. It accumulates the return values in a list which is returned to the caller (with a reference count of 0).

Tcl_FSEvalFileEx reads the file given by pathPtr using the encoding identified by encodingName and evaluates its contents as a Tcl script. It returns the same information as Tcl_EvalObjEx. If encodingName is NULL, the system encoding is used for reading the file contents. If the file could not be read then a Tcl error is returned to describe why the file could not be read. The eofchar for files is “\x1A” (^Z) for all platforms. If you require a “^Z” in code for string comparison, you can use “\x1A”, which will be safely substituted by the Tcl interpreter into “^Z”. Tcl_FSEvalFile is a simpler version of Tcl_FSEvalFileEx that always uses the system encoding when reading the file.

Tcl_FSLoadFile dynamically loads a binary code file into memory and returns the addresses of two procedures within that file, if they are defined. The appropriate function for the filesystem to which pathPtr belongs will be called. If that filesystem does not implement this function (most virtual filesystems will not, because of OS limitations in dynamically loading binary code), Tcl will attempt to copy the file to a temporary directory and load that temporary file. Tcl_FSUnloadFile reverses the operation, asking for the library indicated by the loadHandle to be removed from the process. Note that, unlike with the unload command, this does not give the library any opportunity to clean up.

Both the above functions return a standard Tcl completion code. If an error occurs, an error message is left in the interp's result.

The token provided via the variable indicated by loadHandlePtr may be used with Tcl_FindSymbol.

Tcl_FSMatchInDirectory is used by the globbing code to search a directory for all files which match a given pattern. The appropriate function for the filesystem to which pathPtr belongs will be called.

The return value is a standard Tcl result indicating whether an error occurred in globbing. Error messages are placed in interp (unless interp is NULL, which is allowed), but good results are placed in the resultPtr given.

Note that the glob code implements recursive patterns internally, so this function will only ever be passed simple patterns, which can be matched using the logic of string match. To handle recursion, Tcl will call this function frequently asking only for directories to be returned. A special case of being called with a NULL pattern indicates that the path needs to be checked only for the correct type.

Tcl_FSLink replaces the library version of readlink, and extends it to support the creation of links. The appropriate function for the filesystem to which linkNamePtr belongs will be called.

If the toPtr is NULL, a “read link” action is performed. The result is a Tcl_Obj specifying the contents of the symbolic link given by linkNamePtr, or NULL if the link could not be read. The result is owned by the caller, which should call Tcl_DecrRefCount when the result is no longer needed. If the toPtr is not NULL, Tcl should create a link of one of the types passed in in the linkAction flag. This flag is an OR'ed combination of TCL_CREATE_SYMBOLIC_LINK and TCL_CREATE_HARD_LINK. Where a choice exists (i.e. more than one flag is passed in), the Tcl convention is to prefer symbolic links. When a link is successfully created, the return value should be toPtr (which is therefore already owned by the caller). If unsuccessful, NULL is returned.

Tcl_FSLstat fills the Tcl_StatBuf structure statPtr with information about the specified file. You do not need any access rights to the file to get this information but you need search rights to all directories named in the path leading to the file. The Tcl_StatBuf structure includes info regarding device, inode (always 0 on Windows), privilege mode, nlink (always 1 on Windows), user id (always 0 on Windows), group id (always 0 on Windows), rdev (same as device on Windows), size, last acce

ss time, hora de última modificación y última hora de cambio de metadatos. Consulte la **API PORTABLE STAT RESULT** para obtener una descripción de cómo escribir código portable para asignar y acceder a la estructura Tcl_StatBuf.

Si path existe, Tcl_FSLstat devuelve 0 y la estructura stat se rellena con datos. De lo contrario, se devuelve -1 y no se proporciona información stat.

Tcl_FSUtime reemplaza la versión de biblioteca de utime.

Devuelve 0 en caso de éxito y -1 en caso de error (según la documentación de **utime**). Si tiene éxito, la función actualizará los valores "atime" y "mtime" del archivo proporcionado.

Tcl_FSFileAttrsGet implementa el acceso de lectura para el subcomando **file** **attributes**, que se puede enganchar. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

Si el resultado es TCL_OK, entonces se colocó un valor en objPtrRef, que solo será válido temporalmente (a menos que se llame a Tcl_IncrRefCount).

Tcl_FSFileAttrsSet implementa el acceso de escritura para el subcomando **file** **attributes**, que se puede enganchar. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

Tcl_FSFileAttrStrings implementa parte del subcomando **file** **attributes**, que se puede enganchar. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

El procedimiento llamado puede devolver una matriz de cadenas o, en su lugar, devolver NULL y colocar una lista de Tcl en objPtrRef. Tcl tomará esa lista y primero incrementará su recuento de referencias antes de usarla. Al finalizar ese uso, Tcl decrementará su recuento de referencias. Por lo tanto, si Tcl debe desechar la lista cuando termine, debe tener un recuento de referencias de cero, y si la lista no debe desecharse, el sistema de archivos debe asegurarse de retener un recuento de referencias al valor.

Tcl_FSAccess verifica si al proceso se le permitiría leer, escribir o probar la existencia del archivo (u otro objeto del sistema de archivos) cuyo nombre es pathname. Si pathname es un enlace simbólico en Unix, se prueban los permisos del archivo al que se refiere este enlace simbólico.

En caso de éxito (todos los permisos solicitados concedidos), se devuelve cero. En caso de error (al menos un bit en el modo solicitó un permiso denegado, o ocurrió algún otro error), se devuelve -1.

Tcl_FSStat rellena la estructura Tcl_StatBuf statPtr con información sobre el archivo especificado. No necesita ningún derecho de acceso al archivo para obtener esta información, pero necesita derechos de búsqueda para todos los directorios nombrados en la ruta que conduce al archivo. La estructura Tcl_StatBuf incluye información sobre el dispositivo, inodo (siempre 0 en Windows), modo de privilegios, nlink (siempre 1 en Windows), id de usuario (siempre 0 en Windows), id de grupo (siempre 0 en Windows), rdev (igual que el dispositivo en Windows), tamaño, hora del último acceso, hora de la última modificación y hora del último cambio de metadatos. Consulte la **API PORTABLE STAT RESULT** para obtener una descripción de cómo escribir código portable para asignar y acceder a la estructura Tcl_StatBuf.

Si path existe, Tcl_FSStat devuelve 0 y la estructura stat se rellena con datos. De lo contrario, se devuelve -1 y no se proporciona información stat.

Tcl_FSOpenFileChannel abre un archivo especificado por pathPtr y devuelve un manejador de canal que se puede utilizar para realizar entrada y salida en el archivo. Esta API está modelada según el procedimiento **fopen** de la biblioteca de E/S estándar de Unix. La sintaxis y el significado de todos los argumentos son similares a los dados en el comando Tcl **open** al abrir un archivo. Si ocurre un error al abrir el canal, Tcl_FSOpenFileChannel devuelve NULL y registra un código de error POSIX que se puede recuperar con Tcl_GetErrno. Además, si interp no es NULL, Tcl_FSOpenFileChannel deja un mensaje de error en el resultado de interp después de cualquier error.

El canal recién creado no está registrado en el intérprete proporcionado; para registrarlo, use Tcl_RegisterChannel. Si uno de los canales estándar, **stdin**, **stdout** o **stderr**, se cerró previamente, el acto de crear el nuevo canal también lo asigna como reemplazo del canal estándar.

Tcl_FSGetCwd reemplaza la versión de biblioteca de **getcwd**.

Devuelve el directorio de trabajo actual de la biblioteca Tcl. Este puede ser diferente al directorio de trabajo de la plataforma nativa, lo que ocurre cuando el directorio de trabajo actual no está en el sistema de archivos nativo.

El resultado es un puntero a un Tcl_Obj que especifica el directorio actual, o NULL si no se pudo determinar el directorio actual. Si se devuelve NULL, se deja un mensaje de error en el resultado de interp.

El resultado ya tiene su recuento de referencias incrementado para el llamador. Cuando ya no sea necesario, se debe decrementar ese recuento de referencias. Esto es necesario por razones de seguridad de subprocesos, para permitir que varios subprocesos accedan a esta y funciones relacionadas, al tiempo que se garantiza que los resultados sean siempre válidos.

Tcl_FSChdir reemplaza la versión de biblioteca de **chdir**. La ruta se normaliza y luego se pasa al sistema de archivos que la reclama. Si ese sistema de archivos no implementa esta función, Tcl recurrirá a una combinación de **stat** y **access** para verificar si el directorio existe y tiene los permisos adecuados.

Para obtener resultados, consulte la documentación de **chdir**. Si tiene éxito, mantenemos un registro de la ruta exitosa en cwdPathPtr para llamadas posteriores a **Tcl_FSGetCwd**.

Tcl_FSPathSeparator devuelve el carácter separador que se utilizará para el elemento más específico de la ruta especificada por pathPtr (es decir, la última parte de la ruta).

El separador se devuelve como un Tcl_Obj que contiene una cadena de longitud 1. Si la ruta no es válida, se devuelve NULL.

Tcl_FSJoinPath toma el Tcl_Obj dado, que debe ser una lista válida (a la que se le permite tener un recuento de referencias de cero), y devuelve el valor de ruta dado considerando los primeros elementos como segmentos de ruta válidos (cada segmento de ruta puede ser una ruta completa, una ruta parcial o simplemente un solo directorio o nombre de archivo posible). Si algún segmento de ruta es realmente una ruta absoluta, se descartan todos los segmentos de ruta anteriores. Si elementos es menor que 0, usamos toda la lista.

Es posible que el valor devuelto sea en realidad un elemento de la lista dada, por lo que el llamador debe tener cuidado de incrementar el recuento de referencias del resultado antes de liberar la lista.

El valor devuelto, típicamente con un recuento de referencias de cero (pero podría compartirse bajo algunas condiciones), contiene la ruta unida. El llamador debe agregar un recuento de referencias al valor antes de usarlo. En particular, el valor devuelto podría ser un elemento de la lista dada, por lo que liberar la lista podría liberar el valor prematuramente si no se ha tomado un recuento de referencias. Si el número de elementos es cero, el valor devuelto será un Tcl_Obj de cadena vacía.

Tcl_FSSplitPath toma el Tcl_Obj dado, que debería ser una ruta válida, y devuelve un valor de lista Tcl que contiene cada segmento de esa ruta como un elemento. Devuelve un valor de lista con un recuento de referencias de cero. Si el lenPtr proporcionado no es NULL, la variable a la que apunta se actualizará para contener el número de elementos en la lista devuelta.

Tcl_FSEqualPaths prueba si las dos rutas dadas representan el mismo objeto del sistema de archivos. Devuelve 1 si las rutas son iguales y 0 si son diferentes. Si alguna ruta es NULL, siempre se devuelve 0.

Tcl_FSGetNormalizedPath intenta extraer del Tcl_Obj dado una representación de ruta normalizada única, cuyo valor de cadena se puede utilizar como identificador único del archivo.

Devuelve el valor de ruta normalizada, propiedad de Tcl, o NULL si la ruta no era válida o no se pudo convertir correctamente. La extracción de rutas absolutas y normalizadas es muy eficiente (porque el sistema de archivos opera sobre estas representaciones internamente), aunque el resultado cuando el sistema de archivos contiene numerosos enlaces simbólicos puede no ser la versión más amigable de una ruta. El valor de retorno es propiedad de Tcl y tiene una vida útil equivalente a la de pathPtr pasado (a menos que sea una ruta relativa, en cuyo caso el valor de ruta normalizada puede liberarse en cualquier momento que cambie el cwd); el llamador puede, por supuesto, incrementar el recuento de referencias si desea mantener una copia por más tiempo.

Tcl_FSJoinToPath toma el valor dado, que normalmente debería ser una ruta válida o NULL, y une a él la matriz de segmentos de ruta dados.

Devuelve un valor, típicamente con un recuento de referencias de cero (pero podría compartirse bajo algunas condiciones), que contiene la ruta unida. El llamador debe agregar un recuento de referencias al valor antes de usarlo. Si alguno de los valores pasados a esta función (pathPtr o elementos de path) tiene un recuento de referencias de cero, se liberarán cuando esta función devuelva.

Tcl_FSConvertToPathType intenta convertir el Tcl_Obj dado a un tipo de ruta Tcl válido, teniendo en cuenta que el cwd puede haber cambiado incluso si este valor supuestamente ya es del tipo correcto. El nombre de archivo puede comenzar con "~" (para indicar el directorio de inicio del usuario actual) o "~" (para indicar el directorio de inicio de cualquier usuario).

Si la conversión tiene éxito (es decir, el valor es una ruta válida en uno de los sistemas de archivos actuales), se devuelve **TCL_OK**. De lo contrario, se devuelve **TCL_ERROR**, y se puede dejar un mensaje de error en el intérprete.

Tcl_FSGetInternalRep extrae la representación interna de un valor de ruta dado, en el sistema de archivos dado. Si el valor de ruta pertenece a un sistema de archivos diferente, devolvemos NULL. Si la representación interna es actualmente NULL, intentamos generarla, llamando a **Tcl_FSCreateInternalRepProc** del sistema de archivos.

Devuelve NULL o una representación de ruta interna válida. Esta representación interna se almacena en caché, de modo que las llamadas repetidas a esta función no requerirán conversiones adicionales.

Tcl_FSGetTranslatedPath intenta extraer la ruta traducida del Tcl_Obj dado.

Si la traducción tiene éxito (es decir, el valor es una ruta válida), se devuelve. De lo contrario, se devolverá NULL y se puede dejar un mensaje de error en el intérprete. Una ruta "traducida" es aquella que no contiene secuencias "~" o "~usuario" (estas se han expandido a su representación actual en el sistema de archivos). El valor devuelto es propiedad del llamador, que debe almacenarlo o llamar a **Tcl_DecrRefCount** para garantizar que la memoria se libere. Esta función tiene poca utilidad práctica, y **Tcl_FSGetNormalizedPath** o **Tcl_FSGetNativePath** son funciones generalmente mejores para usar en la mayoría de los propósitos.

Tcl_FSGetTranslatedStringPath hace lo mismo que Tcl_FSGetTranslatedPath, pero devuelve una cadena de caracteres o NULL. La cadena devuelta se asigna dinámicamente.

It also provides support for virtual file systems. THE Tcl OBJECT PATH API The Tcl object path API provides functions for creating and manipulating Tcl path objects. Path objects are used to represent file paths in Tcl. Tcl_FSNewNativePath creates a new path object from a native path string. The native path string is in the encoding native to the host operating system. The caller is responsible for freeing the returned object. The caller also owns the memory pointed to by nativePath and must store it or call ckfree to ensure it is freed. Again, Tcl_FSGetNormalizedPath or Tcl_FSGetNativePath are usually better functions to use for most purposes. Tcl_FSNewNativePath performs something like the reverse of the usual obj->path->nativerep conversions. If some code retrieves a path in native form (from, e.g. readlink or a native dialog), and that path is to be used at the Tcl level, then calling this function is an efficient way of creating the appropriate path value type. The resulting value is a pure "path" value, which will only receive a UTF-8 string representation if that is required by some Tcl code. Tcl_FSGetNativePath is for use by the Win/Unix native filesystems, so that they can easily retrieve the native (char* or TCHAR*) representation of a path. This function is a convenience wrapper around Tcl_FSGetInternalRep. It may be desirable in the future to have non-string-based native representations (for example, on macOS, a representation using a fileSpec of FSRef structure would probably be more efficient). On Windows a full Unicode representation would allow for paths of unlimited length. Currently the representation is simply a character string which may contain either the relative path or a complete, absolute normalized path in the native encoding (complex conditions dictate which of these will be provided, so neither can be relied upon, unless the path is known to be absolute). If you need a native path which must be absolute, then you should ask for the native version of a normalized path. If for some reason a non-absolute, non-normalized version of the path is needed, that must be constructed separately (e.g. using Tcl_FSGetTranslatedPath). The native representation is cached so that repeated calls to this function will not require additional conversions. The return value is owned by Tcl and has a lifetime equivalent to that of the pathPtr passed in (unless that is a relative path, in which case the native representation may be freed any time the cwd changes). Tcl_FSFileSystemInfo returns a list of two elements. The first element is the name of the filesystem (e.g. "native", "vfs", "zip", or "prowrap", perhaps), and the second is the particular type of the given path within that filesystem (which is filesystem dependent). The second element may be empty if the filesystem does not provide a further categorization of files. A valid list value is returned, unless the path value is not recognized, when NULL will be returned. Tcl_FSGetFileSystemForPath returns a pointer to the Tcl_Filesystem which accepts this path as valid. If no filesystem will accept the path, NULL is returned. Tcl_FSGetPathType determines whether the given path is relative to the current directory, relative to the current volume, or absolute. On calling this function, Tcl will attach the filesystem to the list of known filesystems, and it will become fully functional immediately. OPERACIONES DEL SISTEMA DE ARCHIVOS

Los campos de esta sección de la estructura contienen direcciones de funciones que se llaman para llevar a cabo las operaciones básicas del sistema de archivos. Un sistema de archivos que se espera que se utilice con el conjunto completo de comandos estándar de Tcl debe implementar todas estas. Si algunas de ellas no se implementan, entonces ciertos comandos de Tcl pueden fallar al operar en rutas dentro de ese sistema de archivos. Sin embargo, en algunas instancias esto puede ser deseable (por ejemplo, un sistema de archivos de solo lectura no debería implementar las últimas cuatro funciones, y un sistema de archivos que no soporta enlaces simbólicos no necesita implementar la función readlink, etc. El núcleo de Tcl espera que los sistemas de archivos se comporten de esta manera).

El "tipo" se utiliza solo a efectos informativos y debe devolverse como la representación de cadena del Tcl_Obj devuelto. Un valor típico de retorno podría ser "networked", "zip" o "ftp". Función para procesar una llamada a Tcl_FSStat. Debe ser implementada para cualquier sistema de archivos razonable, ya que muchos comandos a nivel de Tcl dependen crucialmente de ella (por ejemplo, file atime, file isdirectory, file size, glob).

        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

El Tcl_FSStatProc rellena la estructura stat statPtr con información sobre el archivo especificado. No necesita ningún derecho de acceso al archivo para obtener esta información, pero necesita derechos de búsqueda para todos los directorios mencionados en la ruta que conduce al archivo. La estructura stat incluye información sobre el dispositivo, el inodo (siempre 0 en Windows), el modo de privilegios, nlink (siempre 1 en Windows), id de usuario (siempre 0 en Windows), id de grupo (siempre 0 en Windows), rdev (igual que el dispositivo en Windows), tamaño, tiempo del último acceso, tiempo de la última modificación y tiempo del último cambio de metadatos.

Si el archivo representado por pathPtr existe, Tcl_FSStatProc devuelve 0 y la estructura stat se rellena con datos. De lo contrario, se devuelve -1 y no se proporciona información stat.

Función para procesar una llamada a Tcl_FSOpenFileChannel. Debe implementarse para cualquier sistema de archivos razonable, ya que todas las operaciones que requieren abrir o acceder al contenido de un archivo la utilizarán (por ejemplo, open, encoding y muchos comandos de Tk).

        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

El Tcl_FSOpenFileChannelProc abre un archivo especificado por pathPtr y devuelve un manejador de canal que se puede utilizar para realizar operaciones de entrada y salida en el archivo. Esta API está modelada a partir del procedimiento fopen de la biblioteca estándar de E/S de Unix. La sintaxis y el significado de todos los argumentos son similares a los dados en el comando open de Tcl al abrir un archivo, donde el argumento mode es una combinación de las banderas POSIX O_RDONLY, O_WRONLY, etc. Si ocurre un error al abrir el canal, Tcl_FSOpenFileChannelProc devuelve NULL y registra un código de error POSIX que se puede recuperar con Tcl_GetErrno. Además, si interp no es NULL, Tcl_FSOpenFileChannelProc deja un mensaje de error en el resultado de interp después de cualquier error.

El canal recién creado no debe registrarse en el intérprete proporcionado por un Tcl_FSOpenFileChannelProc; esa tarea corresponde al llamador de Tcl_FSOpenFileChannel (si es necesario). Si uno de los canales estándar, stdin, stdout o stderr se cerró previamente, el acto de crear el nuevo canal también lo asigna como reemplazo para el canal estándar.

MATCHINDIRECTORYPROC

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La función debe devolver todos los archivos o directorios (u otros objetos del sistema de archivos) que coincidan con el patrón dado y concuerden con la especificación de types proporcionada. Hay dos formas en que se puede llamar a esta función. Si pattern es NULL, entonces pathPtr es una especificación de ruta completa de un solo archivo o directorio que debe verificarse en cuanto a existencia y tipo correcto. De lo contrario, pathPtr es un directorio, cuyo contenido la función debe buscar archivos o directorios que tengan el tipo correcto. En cualquier caso, se puede suponer que pathPtr no es NULL y no está vacío. Actualmente no está documentado si pathPtr tendrá un separador de archivos al final o no, por lo que el código debe ser flexible para ambas posibilidades.

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso de coincidencia. Los mensajes de error se colocan en interp, a menos que interp sea NULL, en cuyo caso no es necesario generar ningún mensaje de error; en un resultado TCL_OK, los resultados deben agregarse al valor de resultPtr dado (que se puede suponer que es una lista válida y no compartida de Tcl). Las coincidencias agregadas a resultPtr deben incluir cualquier prefijo de ruta dado en pathPtr (esto generalmente significa que serán especificaciones de ruta absolutas). Tenga en cuenta que si no se encuentran coincidencias, eso simplemente conduce a un resultado vacío; los errores solo se señalan para problemas reales del archivo o del sistema de archivos que puedan ocurrir durante el proceso de coincidencia.

La estructura Tcl_GlobTypeData que se pasa en el parámetro types contiene los siguientes campos:

typedef struct Tcl_GlobTypeData {
    /* Corresponde a bcdpfls como en 'find -t' */
    int type;
    /* Corresponde a los permisos de archivo */
    int perm;
    /* Tipo de Mac aceptable */
    Tcl_Obj *macType;
    /* Creador de Mac aceptable */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Hay dos casos específicos que es importante manejar correctamente, ambos cuando types no es NULL. Los dos casos son cuando types->types & TCL_GLOB_TYPE_DIR o types->types & TCL_GLOB_TYPE_MOUNT son verdaderos (y en particular cuando las otras banderas son falsas). En el primero de estos casos, la función debe listar los directorios contenidos. Tcl utiliza esto para implementar globbing recursivo, por lo que es fundamental que los sistemas de archivos implementen la coincidencia de directorios correctamente. En el segundo de estos casos, con TCL_GLOB_TYPE_MOUNT, el sistema de archivos debe listar los puntos de montaje que se encuentran dentro del pathPtr dado (y en este caso, pathPtr no tiene por qué estar dentro del mismo sistema de archivos, a diferencia de todos los demás casos en los que se llama a esta función). El soporte para esto es crítico si Tcl quiere tener transiciones fluidas entre un sistema de archivos y otro.

LINKPROC

En este caso, el resultado no es propiedad del llamador (es decir, no se necesitan manipulaciones de recuento de referencias en ninguno de los extremos). LISTVOLUMESPROC

Función para listar los volúmenes del sistema de archivos agregados por este sistema de archivos. Solo debe implementarse si el sistema de archivos agrega volúmenes al principio del sistema de archivos, para que puedan ser devueltos por file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

El resultado debe ser una lista de volúmenes agregados por este sistema de archivos, o NULL (o una lista vacía) si no se proporcionan volúmenes. El valor del resultado se considera propiedad del sistema de archivos (no del núcleo de Tcl), pero se le debe dar un contador de referencias para Tcl. Tcl utilizará el contenido de la lista y luego disminuirá ese contador de referencias. Esto permite a los sistemas de archivos elegir si realmente desean retener una lista "global" de volúmenes o no (si no, generan la lista sobre la marcha y la pasan a Tcl con un contador de referencias de 1 y luego se olvidan de la lista; si sí, simplemente incrementan el contador de referencias de su lista global y se la pasan a Tcl, que copiará el contenido y luego disminuirá el contador de nuevo a donde estaba).

Por lo tanto, Tcl considera que los valores de retorno de este proc son de solo lectura.

FILEATTRSTRINGSPROC

Función para listar todas las cadenas de atributos que son válidas para este sistema de archivos. Si no se implementa, el sistema de archivos no admitirá el comando file attributes. Esto permite adjuntar información adicional arbitraria a los archivos en el sistema de archivos. Si no se implementa, no es necesario implementar los métodos get y set.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

La función llamada puede devolver una matriz de cadenas o puede devolver NULL y colocar una lista de Tcl en el objPtrRef proporcionado. Tcl tomará esa lista y primero incrementará su contador de referencias antes de usarla. Al finalizar ese uso, Tcl disminuirá su contador de referencias. Por lo tanto, si la lista debe ser eliminada por Tcl cuando termine, debe tener un contador de referencias de cero, y si la lista no debe ser eliminada, el sistema de archivos debe asegurarse de devolver un valor con un contador de referencias de al menos uno.

FILEATTRSGETPROC

Función para procesar una llamada a Tcl_FSFileAttrsGet, utilizada por file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

Devuelve un código de retorno estándar de Tcl. El valor del atributo recuperado, que corresponde al elemento con índice index en la lista devuelta por Tcl_FSFileAttrStringsProc, es un Tcl_Obj colocado en objPtrRef (si se devolvió TCL_OK) y es probable que tenga un contador de referencias de cero. En cualquier caso, debemos almacenarlo en algún lugar (por ejemplo, el resultado de Tcl) o incrementar/disminuir su contador de referencias para garantizar que se libere correctamente.

FILEATTRSSETPROC

Función para procesar una llamada a Tcl_FSFileAttrsSet, utilizada por file attributes. Si el sistema de archivos es de solo lectura, no es necesario implementarlo.

typedef int Tcl_FSFileAttrsSetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj *objPtr);

El valor del atributo del elemento con índice index en la lista devuelta por Tcl_FSFileAttrStringsProc debe establecerse en el objPtr proporcionado.

CREATEDIRECTORYPROC

Función para procesar una llamada a Tcl_FSCreateDirectory. Debe implementarse, a menos que el sistema de archivos sea solo-lectura.

typedef int Tcl_FSCreateDirectoryProc(
            Tcl_Obj *pathPtr);

El valor de retorno es un resultado estándar de Tcl indicando si se produjo un error durante el proceso. Si se realiza correctamente, debería haberse creado una nueva carpeta en el lugar especificado por pathPtr.

REMOVEDIRECTORYPROC

Función para procesar una llamada a Tcl_FSRemoveDirectory. Debe implementarse, a menos que el sistema de archivos sea solo-lectura.

typedef int Tcl_FSRemoveDirectoryProc(
            Tcl_Obj *pathPtr,
            int recursive,
            Tcl_Obj **errorPtr);

El valor de retorno es un resultado estándar de Tcl indicando si se produjo un error durante el proceso. Si se realiza correctamente, la carpeta especificada por pathPtr debería haber sido eliminada del sistema de archivos. Si el flag recursive está dado, una carpeta no vacía debería ser eliminada sin error. Si el flag no está dado, y la carpeta es no vacía, se debe emitir un error POSIX "EEXIST". Si se produce un error, el nombre del archivo o carpeta que causó el error debería estar en errorPtr.

DELETEFILEPROC

Función para procesar una llamada a Tcl_FSDeleteFile. Debe implementarse, a menos que el sistema de archivos sea solo-lectura.

typedef int Tcl_FSDeleteFileProc(
            Tcl_Obj *pathPtr);

El valor de retorno es un resultado estándar de Tcl indicando si se produjo un error durante el proceso. Si se realiza correctamente, el archivo especificado por pathPtr debería haber sido eliminado del sistema de archivos. Debe tener en cuenta que, si el sistema de archivos soporta enlaces simbólicos, Tcl llamará esta función y no Tcl_FSRemoveDirectoryProc cuando sea necesario para eliminarlos (incluso si son enlaces simbólicos a directorios).

EFICIENCIA DEL SISTEMA DE ARCHIVOS

Estas funciones no deben implementarse para un sistema de archivos particular, ya que el núcleo tiene una implementación de respaldo disponible. Vea cada descripción individual para las consecuencias de dejar los campos NULL.

LSTATPROC

Función para procesar una llamada a Tcl_FSLstat. Si no se implementa, Tcl intentará usar la statProc definida previamente. Por lo tanto, solo debe implementarse si el sistema de archivos puede diferenciar entre las llamadas stat y lstat.

typedef int Tcl_FSLstatProc(
                Tcl_Obj *pathPtr,
                Tcl_StatBuf *statPtr);

El comportamiento de esta función es muy similar al de la Tcl_FSStatProc definida previamente, a menos que se aplique a un enlace simbólico, en cuyo caso devuelve información sobre el enlace, no sobre el archivo objetivo.

COPYFILEPROC

Función para procesar una llamada a Tcl_FSCopyFile. Si no se implementa, Tcl recurrirá al modo open-r, open-w y fcopy como mecanismo de copia. Por lo tanto, solo debe implementarse si el sistema de archivos puede realizar esa acción con mayor eficiencia.

typedef int Tcl_FSCopyFileProc(
                Tcl_Obj *srcPathPtr,
                Tcl_Obj *destPathPtr);

El valor de retorno es un resultado estándar de Tcl indicando si se produjo un error durante el proceso de copia. Tenga en cuenta que destPathPtr es el nombre del archivo que debería convertirse en la copia de srcPathPtr. Nunca será el nombre de un directorio en el que se pueda copiar srcPathPtr (es decir, el funcionamiento es mucho más simple que el subcomando file copy del nivel Tcl). Tenga en cuenta que, si el sistema de archivos soporta enlaces simbólicos, Tcl llamará esta función y no copyDirectoryProc cuando sea necesario para copiarlos (incluso si son enlaces simbólicos a directorios). Finalmente, si el sistema de archivos determina que no puede soportar la acción de copia de archivos, llamando Tcl_SetErrno(EXDEV) y devolviendo un resultado no TCL_OK indicará a Tcl el uso de sus mecanismos de respaldo estándar.

RENAMEFILEPROC

Función para procesar una llamada a Tcl_FSRenameFile. Si no se implementa, Tcl recurrirá a un mecanismo de copia y eliminación. Por lo tanto, solo debe implementarse si el sistema de archivos puede realizar esa acción con mayor eficiencia.

typedef int Tcl_FSRenameFileProc(
                Tcl_Obj *srcPathPtr,
                Tcl_Obj *destPathPtr);

El valor de retorno es un resultado estándar de Tcl indicando si se produjo un error durante el proceso de renombrado. Si el sistema de archivos determina que no puede soportar la acción de file rename, llamando Tcl_SetErrno(EXDEV) y devolviendo un resultado no TCL_OK indicará a Tcl el uso de sus mecanismos de respaldo estándar.

COPYDIRECTORYPROC

Función para procesar una llamada a Tcl_FSCopyDirectory. Si no se implementa, Tcl recurrirá a un mecanismo recursivo de file mkdir, file copy. Por lo tanto, solo debe implementarse si el sistema de archivos puede realizar esa acción con mayor eficiencia.

typedef int Tcl_FSCopyDirectoryProc(
                Tcl_Obj *srcPathPtr,
                Tcl_Obj *destPathPtr,
                Tcl_Obj **errorPtr);

El valor de retorno es un resultado estándar de Tcl indicando si se produjo un error durante el proceso de copia. Si se produce un error, el nombre del archivo o directorio que causó el error debe estar en errorPtr. Tenga en cuenta que destPathPtr es el nombre del directorio que debería convertirse en la imagen del archivo srcPathPtr. No es el nombre de un directorio en el que srcPathPtr se puede copiar (es decir, el funcionamiento es mucho más simple que el subcomando file copy del nivel Tcl). Finalmente, si el sistema de archivos determina que no puede soportar la acción de copia de directorios, llamando Tcl_SetErrno(EXDEV) y devolviendo un resultado no TCL_OK indicará a Tcl el uso de sus mecanismos de respaldo estándar.

LOADFILEPROC

Función para procesar una llamada a Tcl_FSLoadFile. Si no se implementa, Tcl recurrirá a un mecanismo de copia a un archivo temporal, seguido de una llamada a Tcl_FSLoadFile en ese archivo temporal. Por lo tanto, solo debe implementarse si el sistema de archivos puede cargar código directamente, o puede implementarse simplemente para devolver TCL_ERROR para deshabilitar la funcionalidad de carga en este sistema de archivos.

typedef int Tcl_FSLoadFileProc(
                Tcl_Interp *interp,
                Tcl_Obj *pathPtr,
                Tcl_LoadHandle *handlePtr,
                Tcl_FSUnloadFileProc *unloadProcPtr);

Devuelve un código de finalización estándar de Tcl. Si ocurre un error, un mensaje de error se deja en el resultado del interp. La función carga dinámicamente un archivo binario en memoria. Si se realiza correctamente, handlePtr debe llenarse con un token para el archivo cargado dinámicamente, y unloadProcPtr debe llenarse con la dirección de un procedimiento. El procedimiento de descarga será llamado con el Tcl_LoadHandle dado como único parámetro cuando Tcl necesite descargar el archivo. Por ejemplo, para el sistema de archivos nativo, el Tcl_LoadHandle devuelto es actualmente un token que se puede usar en TclpFindSymbol privada para acceder a funciones en el nuevo código. Cada sistema de archivos puede definir el Tcl_LoadHandle como lo requiera. Finalmente, si el sistema de archivos determina que no puede soportar la acción de carga de archivos, llamando Tcl_SetErrno(EXDEV) y devolviendo un resultado no TCL_OK indicará a Tcl el uso de sus mecanismos de respaldo estándar.

UNLOADFILEPROC

Función para descargar un archivo que fue previamente cargado con éxito. Si la carga fue implementada, esta también debe implementarse, si es necesario realizar alguna acción de limpieza.

typedef void Tcl_FSUnloadFileProc(
                Tcl_LoadHandle loadHandle);

GETCWDPROC

Función para procesar una llamada a Tcl_FSGetCwd. La mayoría de los sistemas de archivos no necesitan implementar esta. Suele llamarse una vez, si getcwd se llama antes de chdir. Puede ser NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
                Tcl_Interp *interp);

Si el sistema de archivos soporta una noción nativa de directorio de trabajo actual (que podría cambiar independientemente de Tcl), esta función debería devolver ese cwd como resultado, o NULL si el directorio de trabajo actual no puede ser determinado (por ejemplo, el usuario no tiene permisos adecuados en el directorio de trabajo). Si se devuelve NULL, se deja un mensaje de error en el resultado del interp

CHDIRPROC

Función para procesar una llamada a Tcl_FSChdir. Si los sistemas de archivos no implementan esta, se emulará mediante una serie de comprobaciones de acceso a directorios. De lo contrario, los sistemas de archivos virtuales que lo implementan solo deben devolver un resultado positivo si pathPtr es un directorio válido y accesible en su sistema de archivos. No deben recordar el resultado, ya que ese será recordado automáticamente por Tcl_FSGetCwd. Los sistemas de archivos reales deben realizar la acción correcta (es decir, llamar a la API adecuada de chdir del sistema).

typedef int Tcl_FSChdirProc(
                Tcl_Obj *pathPtr);

La Tcl_FSChdirProc cambia el directorio de trabajo actual de la aplicación al valor especificado en pathPtr. La función devuelve -1 en caso de error o 0 en caso de éxito.
