DESCRIPCIÓN

Tcl utiliza una arquitectura de canales de dos capas. Proporciona una capa superior genérica para permitir que los programas C y Tcl realicen entrada y salida utilizando las mismas API para una variedad de archivos, dispositivos, sockets, etc. Las API C genéricas se describen en la entrada del manual para Tcl_OpenFileChannel.

La capa inferior proporciona controladores de canal específicos de tipo para cada tipo de dispositivo soportado en cada plataforma. Esta entrada del manual describe las API C utilizadas para comunicarse entre la capa genérica y los controladores de canal específicos de tipo. También explica cómo se pueden añadir nuevos tipos de canales proporcionando nuevos controladores de canal.

Los controladores de canal consisten en varios componentes: Primero, cada controlador de canal proporciona una estructura Tcl_ChannelType que contiene punteros a funciones que implementan las diversas operaciones utilizadas por la capa genérica para comunicarse con el controlador de canal. La estructura Tcl_ChannelType y las funciones referenciadas por ella se describen en la sección TCL_CHANNELTYPE, más abajo.

Segundo, los controladores de canal suelen proporcionar un comando Tcl para crear instancias de ese tipo de canal. Por ejemplo, el comando Tcl open crea canales que utilizan los controladores de canal de archivo y de comando, y el comando Tcl socket crea canales que utilizan sockets TCP para la comunicación de red.

Tercero, un controlador de canal opcionalmente proporciona una función C para abrir instancias de canal de ese tipo. Por ejemplo, Tcl_OpenFileChannel abre un canal que utiliza el controlador de canal de archivo, y Tcl_OpenTcpClient abre un canal que utiliza el protocolo de red TCP. Estas funciones de creación típicamente utilizan Tcl_CreateChannel internamente para abrir el canal.

Para añadir un nuevo tipo de canal, debes implementar una API C o un comando Tcl que abra un canal invocando Tcl_CreateChannel. Cuando tu controlador llama a Tcl_CreateChannel, pasa una estructura Tcl_ChannelType que describe los procedimientos de E/S del controlador. La capa genérica invocará entonces las funciones referenciadas en esa estructura para realizar operaciones en el canal.

Tcl_CreateChannel abre un nuevo canal y asocia los typePtr e instanceData proporcionados con él. El canal se abre en el modo indicado por mask. Para una discusión de los controladores de canal, sus operaciones y la estructura Tcl_ChannelType, ver la sección TCL_CHANNELTYPE, más abajo.

Tcl_CreateChannel interactúa con el código que gestiona los canales estándar. Una vez que un canal estándar se inicializó a través de una llamada a Tcl_GetStdChannel o una llamada a Tcl_SetStdChannel, el cierre de este canal estándar provocará que la siguiente llamada a Tcl_CreateChannel convierta el nuevo canal en el nuevo canal estándar también. Ver Tcl_StandardChannels para un tratado general sobre los canales estándar y el comportamiento de la biblioteca Tcl con respecto a ellos.

Tcl_GetChannelInstanceData devuelve los datos de instancia asociados con el canal en channel. Esto es lo mismo que el argumento instanceData en la llamada a Tcl_CreateChannel que creó este canal.

Tcl_GetChannelType devuelve un puntero a la estructura Tcl_ChannelType utilizada por el canal en el argumento channel. Esto es lo mismo que el argumento typePtr en la llamada a Tcl_CreateChannel que creó este canal.

Tcl_GetChannelName devuelve una cadena que contiene el nombre asociado con el canal, o NULL si el argumento channelName de Tcl_CreateChannel era NULL.

VERBOSITY

El valor de verbosidad para el canal especificado por handlePtr se devuelve en el argumento levelPtr. Si el canal no tiene un identificador de dispositivo para la dirección especificada, se devuelve TCL_ERROR.

Tcl_GetChannelInstanceData devuelve los datos de instancia para el canal especificado por handlePtr. Los datos de instancia son los mismos que los pasados a Tcl_CreateChannel cuando se creó este canal.

Tcl_GetChannelHandle devuelve el identificador del dispositivo para la dirección especificada por handlePtr y devuelve TCL_OK. Si el canal no tiene un identificador de dispositivo para la dirección especificada, se devuelve TCL_ERROR en su lugar. Los controladores de canal diferentes devolverán diferentes tipos de identificador. Consulte las entradas del manual para cada controlador para determinar qué tipo de identificador se devuelve.

Tcl_GetChannelThread devuelve el id del hilo que actualmente gestiona el channel especificado. Esto permite a los controladores de canal enviar sus eventos de archivo a la cola de eventos correcta incluso para un núcleo multihilo.

Tcl_GetChannelMode devuelve una combinación OR de TCL_READABLE y TCL_WRITABLE, que indica si el canal está abierto para entrada y salida.

Tcl_GetChannelBufferSize devuelve el tamaño, en bytes, de los búferes asignados para almacenar la entrada o salida en channel. Si el valor no fue establecido por una llamada anterior a Tcl_SetChannelBufferSize, descrita a continuación, entonces se devuelve el valor predeterminado de 4096.

Tcl_SetChannelBufferSize establece el tamaño, en bytes, de los búferes que se asignarán en operaciones posteriores en el canal para almacenar entrada o salida. El argumento size debe estar entre uno y un millón, permitiendo búferes de un byte a un millón de bytes. Si size está fuera de este rango, Tcl_SetChannelBufferSize establece el tamaño del búfer en 4096.

Tcl_NotifyChannel es llamada por un controlador de canal para indicar a la capa genérica que los eventos especificados por mask han ocurrido en el canal. Los controladores de canal son responsables de invocar esta función siempre que los manejadores de canal deban ser llamados para el canal (o se deban realizar otras tareas pendientes como un vaciado de escritura). Consulte WATCHPROC a continuación para obtener más detalles.

Tcl_BadChannelOption es llamada desde el setOptionProc o getOptionProc específico del controlador para generar un mensaje de error completo.

Tcl_ChannelBuffered devuelve el número de bytes de entrada actualmente almacenados en el búfer interno (área de retroceso) del propio canal. No informa sobre los datos en los búferes generales de la pila de canales de la que forma parte el canal suministrado.

Tcl_IsChannelShared comprueba el contador de referencias del channel especificado y devuelve si el channel fue compartido entre múltiples intérpretes (resultado == 1) o no (resultado == 0).

Tcl_IsChannelRegistered comprueba si el channel especificado está registrado en el interpretador dado (resultado == 1) o no (resultado == 0).

Tcl_IsChannelExisting comprueba si un canal con el nombre especificado está registrado en la lista global (de hilos) de todos los canales (resultado == 1) o no (resultado == 0).

Tcl_CutChannel elimina el channel especificado de la lista global (de hilos) de todos los canales (del hilo actual). No se permite la aplicación a un canal aún registrado en algún intérprete. También notifica al controlador si la versión de Tcl_ChannelType es TCL_CHANNEL_VERSION_4 (o superior), y Tcl_DriverThreadActionProc está definida para él.

Tcl_SpliceChannel añade el channel especificado a la lista global (de hilos) de todos los canales (del hilo actual). No se permite la aplicación a un canal registrado en algún intérprete. También notifica al controlador si la versión de Tcl_ChannelType es TCL_CHANNEL_VERSION_4 (o superior), y Tcl_DriverThreadActionProc está definida para él.

Tcl_ClearChannelHandlers elimina todos los manejadores de canal y scripts de eventos asociados con el channel especificado, cerrando así todo el procesamiento de eventos para este canal.

TCL_CHANNELTYPE

Un controlador de canal proporciona una estructura Tcl_ChannelType que contiene punteros a funciones que implementan las diversas operaciones en un canal; estas operaciones se invocan según sea necesario desde la capa genérica. La estructura fue versionada a partir de Tcl 8.3.2/8.4 para corregir un problema con los controladores de canal apilados. Consulte la sección OLD CHANNEL TYPES a continuación para obtener detalles sobre la estructura antigua.

La estructura Tcl_ChannelType contiene los siguientes campos:

typedef struct Tcl_ChannelType {
        const char *typeName;
        Tcl_ChannelTypeVersion version;
        Tcl_DriverCloseProc *closeProc;
        Tcl_DriverInputProc *inputProc;
        Tcl_DriverOutputProc *outputProc;
        Tcl_DriverSeekProc *seekProc;
        Tcl_DriverSetOptionProc *setOptionProc;
        Tcl_DriverGetOptionProc *getOptionProc;
        Tcl_DriverWatchProc *watchProc;
        Tcl_DriverGetHandleProc *getHandleProc;
        Tcl_DriverClose2Proc *close2Proc;
        Tcl_DriverBlockModeProc *blockModeProc;
        Tcl_DriverFlushProc *flushProc;
        Tcl_DriverHandlerProc *handlerProc;
        Tcl_DriverWideSeekProc *wideSeekProc;
        Tcl_DriverThreadActionProc *threadActionProc;
        Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

No es necesario proporcionar implementaciones para todas las operaciones de canal. Aquellas que no sean necesarias pueden establecerse en NULL en la estructura: blockModeProc, seekProc, setOptionProc, getOptionProc, getHandleProc y close2Proc, además de flushProc, handlerProc, threadActionProc y truncateProc. Otras funciones que no se pueden implementar de manera significativa deben devolver EINVAL cuando se llamen, para indicar que las operaciones que representan no están disponibles. Tenga en cuenta también que wideSeekProc puede ser NULL si seekProc lo es.

El usuario solo debe usar la estructura anterior para la instanciación de Tcl_ChannelType. Al hacer referencia a los campos en una estructura Tcl_ChannelType, se deben utilizar las siguientes funciones para obtener los valores: Tcl_ChannelName, Tcl_ChannelVersion, Tcl_ChannelBlockModeProc, Tcl_ChannelCloseProc, Tcl_ChannelClose2Proc, Tcl_ChannelInputProc, Tcl_ChannelOutputProc, Tcl_ChannelSeekProc, Tcl_ChannelWideSeekProc, Tcl_ChannelThreadActionProc, Tcl_ChannelTruncateProc, Tcl_ChannelSetOptionProc, Tcl_ChannelGetOptionProc, Tcl_ChannelWatchProc, Tcl_ChannelGetHandleProc, Tcl_ChannelFlushProc o Tcl_ChannelHandlerProc.

El cambio en las estructuras se realizó de tal manera que los tipos de canal estándar son binariamente compatibles. Sin embargo, los tipos de canal que utilizan canales apilados (es decir, TLS, Trf) tienen nuevas versiones para corresponder al cambio anterior, ya que el código anterior para canales apilados tenía problemas.

TYPENAME

El campo typeName contiene una cadena terminada en nulo que identifica el tipo del dispositivo implementado por este controlador, por ejemplo, file o socket.

Este valor se puede recuperar con Tcl_ChannelName, que devuelve un puntero a la cadena.

VERSION

El campo version debe establecerse en la versión de la estructura que necesita. TCL_CHANNEL_VERSION_2 es el mínimo recomendado. TCL_CHANNEL_VERSION_3 debe establecerse para especificar el miembro wideSeekProc. TCL_CHANNEL_VERSION_4 debe establecerse para especificar el miembro threadActionProc (incluye wideSeekProc). TCL_CHANNEL_VERSION_5 debe establecerse para especificar los miembros truncateProc (incluye wideSeekProc y threadActionProc). Si no se establece en ninguno de estos, entonces se asume que este Tcl_ChannelType tiene la estructura original. Consulte OLD CHANNEL TYPES para obtener más detalles. Si bien Tcl reconocerá y funcionará con ambas estructuras, los canales apilados deben ser de al menos TCL_CHANNEL_VERSION_2 para funcionar correctamente.

Este valor se puede recuperar con Tcl_ChannelVersion, que devuelve una de las siguientes opciones: TCL_CHANNEL_VERSION_5, TCL_CHANNEL_VERSION_4, TCL_CHANNEL_VERSION_3, TCL_CHANNEL_VERSION_2 o TCL_CHANNEL_VERSION_1.

BLOCKMODEPROC

El campo blockModeProc contiene la dirección de una función llamada por la capa genérica para establecer el modo de bloqueo y no bloqueo en el dispositivo. BlockModeProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverBlockModeProc(
        ClientData instanceData,
        int mode);

El instanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando se creó este canal. El argumento mode es TCL_MODE_BLOCKING o TCL_MODE_NONBLOCKING para establecer el dispositivo en modo de bloqueo o no bloqueo. La función debe devolver cero si la operación fue exitosa, o un código de error POSIX distinto de cero si la operación falló.

Si la operación es exitosa, la función puede modificar el instanceData suministrado para registrar que el canal entró en modo de bloqueo o no bloqueo y para implementar el comportamiento de bloqueo o no bloqueo. Para algunos tipos de dispositivo, el comportamiento de bloqueo y no bloqueo puede ser implementado por el sistema operativo subyacente; para otros tipos de dispositivo, el comportamiento debe ser emulado en el controlador de canal.

Este valor se puede recuperar con Tcl_ChannelBlockModeProc, que devuelve un puntero a la función.

Un controlador de canal que no suministra un blockModeProc debe tener mucho, mucho cuidado. Debe indicar a la capa genérica exactamente qué modo de bloqueo le es aceptable, y también debe documentar esto para el usuario para que el modo de bloqueo del canal no se cambie a un valor inaceptable. Cualquier confusión aquí puede llevar al intérprete a un punto muerto (falso y difícil de encontrar).

CLOSEPROC

The closeProc field contains the address of a function called by the generic layer to close a channel. closeProc must match the following prototype:

typedef int Tcl_DriverCloseProc(
        ClientData instanceData,
        Tcl_Interp *interp);

InstanceData is the same as the value passed to Tcl_CreateChannel when the channel was created. The function should perform any channel-type-specific actions needed to close the channel, such as releasing file descriptors or memory. If the close operation is successful, the function should return zero; otherwise it should return a nonzero POSIX error code. In addition, if an error occurs and interp is not NULL, the procedure should store an error message in the interpreter's result.

Alternatively, channels that support closing the read and write sides independently may set closeProc to TCL_CLOSE2PROC and set close2Proc to the address of a function that matches the following prototype:

typedef int Tcl_DriverClose2Proc(
        ClientData instanceData,
        Tcl_Interp *interp,
        int flags);

The close2Proc will be called with flags set to an OR'ed combination of TCL_CLOSE_READ or TCL_CLOSE_WRITE to indicate that the driver should close the read and/or write side of the channel. The channel driver may be invoked to perform additional operations on the channel after close2Proc is called to close one or both sides of the channel. If flags is 0 (zero), the driver should close the channel in the manner described above for closeProc. No further operations will be invoked on this instance after close2Proc is called with all flags cleared. In all cases, the close2Proc function should return zero if the close operation was successful; otherwise it should return a nonzero POSIX error code. In addition, if an error occurs and interp is not NULL, the procedure should store an error message in the interpreter's result.

The closeProc and close2Proc values can be retrieved with Tcl_ChannelCloseProc or Tcl_ChannelClose2Proc, which return a pointer to the respective function.

INPUTPROC

The inputProc field contains the address of a function called by the generic layer to read data from the file or device and store it in an internal buffer. InputProc must match the following prototype:

typedef int Tcl_DriverInputProc(
        ClientData instanceData,
        char *buf,
        int bufSize,
        int *errorCodePtr);

InstanceData is the same as the value passed to Tcl_CreateChannel when the channel was created. The buf argument points to an array of bytes in which to store input from the device, and the bufSize argument indicates how many bytes are available at buf.

The errorCodePtr argument points to an integer variable provided by the generic layer. If an error occurs, the function should set the variable to a POSIX error code that identifies the error that occurred.

The function should read data from the input device encapsulated by the channel and store it at buf. On success, the function should return a nonnegative integer indicating how many bytes were read from the input device and stored at buf. On error, the function should return -1. If an error occurs after some data has been read from the device, that data is lost.

If inputProc can determine that the input device has some data available but less than requested by the bufSize argument, the function should only attempt to read as much data as is available and return without blocking. If the input device has no data available whatsoever and the channel is in nonblocking mode, the function should return an EAGAIN error. If the input device has no data available whatsoever and the channel is in blocking mode, the function should block for the shortest possible time until at least one byte of data can be read from the device; then, it should return as much data as it can read without blocking.

This value can be retrieved with Tcl_ChannelInputProc, which returns a pointer to the function.

OUTPUTPROC

The outputProc field contains the address of a function called by the generic layer to transfer data from an internal buffer to the output device. OutputProc must match the following prototype:

typedef int Tcl_DriverOutputProc(
        ClientData instanceData,
        const char *buf,
        int toWrite,
        int *errorCodePtr);

InstanceData is the same as the value passed to Tcl_CreateChannel when the channel was created. The buf argument contains an array of bytes to be written to the device, and the toWrite argument indicates how many bytes are to be written from the buf argument.

The errorCodePtr argument points to an integer variable provided by the generic layer. If an error occurs, the function should set this variable to a POSIX error code that identifies the error.

The function should write the data at buf to the output device encapsulated by the channel. On success, the function should return a nonnegative integer indicating how many bytes were written to the output device. The return value is normally the same as toWrite, but may be less in some cases such as if the output operation is interrupted by a signal. If an error occurs the function should return -1. In case of error, some data may have been written to the device.

If the channel is nonblocking and the output device is unable to absorb any data whatsoever, the function should return -1 with an EAGAIN error without writing any data.

This value can be retrieved with Tcl_ChannelOutputProc, which returns a pointer to the function.

SEEKPROC AND WIDESEEKPROC

The seekProc field contains the address of a function called by the generic layer to move the access point at which subsequent input or output operations will be applied. SeekProc must match the following prototype:

typedef int Tcl_DriverSeekProc(
        ClientData instanceData,
        long offset,
        int seekMode,
        int *errorCodePtr);

The instanceData argument is the same as the value given to Tcl_CreateChannel when this channel was created. Offset and seekMode have the same meaning as for the Tcl_Seek procedure (described in the manual entry for Tcl_OpenFileChannel).

The errorCodePtr argument points to an integer variable provided by the generic layer for returning errno values from the function. The function should set this variable to a POSIX error code if an error occurs. The function should store an EINVAL error code if the channel type does not implement seeking.

The return value is the new access point or -1 in case of error. If an error occurred, the function should not move the access point.

If there is a non-NULL seekProc field, the wideSeekProc field may contain the address of an alternative function to use which handles wide (i.e. larger than 32-bit) offsets, so allowing seeks within files larger than 2GB. The wideSeekProc will be called in preference to the seekProc, but both must be defined if the wideSeekProc is defined. WideSeekProc must match the following prototype:

typedef Tcl_WideInt Tcl_DriverWideSeekProc(
        ClientData instanceData,
        Tcl_WideInt offset,
        int seekMode,
        int *errorCodePtr);

The arguments and return values mean the same thing as with seekProc above, except that the type of offsets and the return type are different.

The seekProc value can be retrieved with Tcl_ChannelSeekProc, which returns a pointer to the function, and similarly the wideSeekProc can be retrieved with Tcl_ChannelWideSeekProc.

SETOPTIONPROC

The setOptionProc field contains the address of a function called by the generic layer to set a channel type specific option on a channel. setOptionProc must match the following prototype:

typedef int Tcl_DriverSetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        const char *newValue);

optionName is the name of an option to set, and newValue is the new value for that option, as a string. The instanceData is the same as the value given to Tcl_CreateChannel when this channel was created. The function should do whatever channel type specific action is required to implement the new value of the option.

Some options are handled by the generic code and this function is never called to set them, e.g. -blockmode. Other options are specific to each channel type and the setOptionProc procedure of the channel driver will get called to implement them. The setOptionProc field can be NULL, which indicates that this channel type supports no type specific options.

If the option value is successfully modified to the new value, the function returns TCL_OK. It should call Tcl_BadChannelOption which itself returns TCL_ERROR if the optionName is unrecognized. If newValue specifies a value for the option that is not supported or if a system call error occurs, the function should leave an error message in the result of interp if interp is not NULL. The function should also call Tcl_SetErrno to store an appropriate POSIX error code.

This value can be retrieved with Tcl_ChannelSetOptionProc, which returns a pointer to the function.
