DESCRIPCIÓN

Tcl utiliza una arquitectura de canales de dos capas. Proporciona una capa superior genérica para permitir que los programas C y Tcl realicen entrada y salida utilizando las mismas API para una variedad de archivos, dispositivos, sockets, etc. Las API genéricas de C se describen en la entrada del manual para Tcl_OpenFileChannel.

La capa inferior proporciona controladores de canales específicos de tipo para cada tipo de dispositivo soportado en cada plataforma. Esta entrada del manual describe las API de C utilizadas para comunicarse entre la capa genérica y los controladores de canales específicos de tipo. También explica cómo se pueden añadir nuevos tipos de canales proporcionando nuevos controladores de canales.

Los controladores de canales consisten en varios componentes: Primero, cada controlador de canales proporciona una estructura Tcl_ChannelType que contiene punteros a funciones que implementan las diversas operaciones utilizadas por la capa genérica para comunicarse con el controlador de canales. La estructura Tcl_ChannelType y las funciones referenciadas por ella se describen en la sección TCL_CHANNELTYPE, más abajo.

Segundo, los controladores de canales suelen proporcionar un comando Tcl para crear instancias de ese tipo de canal. Por ejemplo, el comando Tcl open crea canales que utilizan los controladores de canales de archivo y comando, y el comando Tcl socket crea canales que utilizan sockets TCP para la comunicación de red.

Tercero, un controlador de canales proporciona opcionalmente una función C para abrir instancias de canal de ese tipo. Por ejemplo, Tcl_OpenFileChannel abre un canal que utiliza el controlador de canales de archivo, y Tcl_OpenTcpClient abre un canal que utiliza el protocolo de red TCP. Estas funciones de creación utilizan típicamente Tcl_CreateChannel internamente para abrir el canal.

Para añadir un nuevo tipo de canal, debe implementar una API C o un comando Tcl que abra un canal invocando Tcl_CreateChannel. Cuando su controlador llama a Tcl_CreateChannel, pasa una estructura Tcl_ChannelType que describe los procedimientos de E/S del controlador. La capa genérica invocará entonces las funciones referenciadas en esa estructura para realizar operaciones en el canal.

Tcl_CreateChannel abre un nuevo canal y asocia los typePtr y instanceData suministrados con él. El canal se abre en el modo indicado por mask. Para una discusión de los controladores de canales, sus operaciones y la estructura Tcl_ChannelType, véase la sección TCL_CHANNELTYPE, más abajo.

Tcl_CreateChannel interactúa con el código que gestiona los canales estándar. Una vez que un canal estándar se inicializó a través de una llamada a Tcl_GetStdChannel o una llamada a Tcl_SetStdChannel, el cierre de este canal estándar hará que la siguiente llamada a Tcl_CreateChannel convierta el nuevo canal en el nuevo canal estándar también. Véase Tcl_StandardChannels para un tratado general sobre los canales estándar y el comportamiento de la biblioteca Tcl con respecto a ellos.

Tcl_GetChannelInstanceData devuelve los datos de instancia asociados con el canal en channel. Esto es lo mismo que el argumento instanceData en la llamada a Tcl_CreateChannel que creó este canal.

Tcl_GetChannelType devuelve un puntero a la estructura Tcl_ChannelType utilizada por el canal en el argumento channel. Esto es lo mismo que el argumento typePtr en la llamada a Tcl_CreateChannel que creó este canal.

Tcl_GetChannelName devuelve una cadena que contiene el nombre asociado con el canal, o NULL si el argumento channelName de Tcl_CreateChannel era NULL.

FUNCIONES DEL CONTROLADOR DE CANAL

Estas funciones son utilizadas por el nivel genérico de Tcl para interactuar con los controladores de canal específicos del dispositivo.

Tcl_GetChannelHandle retorna un puntero a un manejador para el canal en la ubicación especificada por handlePtr y retorna TCL_OK. Si el canal no tiene un manejador de dispositivo para la dirección especificada, entonces se retorna TCL_ERROR. Diferentes controladores de canal retornarán diferentes tipos de manejador. Consulte las entradas del manual para cada controlador para determinar qué tipo de manejador se retorna.

Tcl_GetChannelThread retorna el id del hilo que actualmente está gestionando el channel especificado. Esto permite a los controladores de canal enviar sus eventos de archivo a la cola de eventos correcta incluso para un núcleo multi-hilo.

Tcl_GetChannelMode retorna una combinación OR de TCL_READABLE y TCL_WRITABLE, indicando si el canal está abierto para entrada y salida.

Tcl_GetChannelBufferSize retorna el tamaño, en bytes, de los búferes asignados para almacenar entrada o salida en el channel. Si el valor no fue establecido por una llamada anterior a Tcl_SetChannelBufferSize, descrita a continuación, entonces se retorna el valor predeterminado de 4096.

Tcl_SetChannelBufferSize establece el tamaño, en bytes, de los búferes que se asignarán en operaciones posteriores en el canal para almacenar entrada o salida. El argumento size debe estar entre uno y un millón, permitiendo búferes de un byte a un millón de bytes. Si size está fuera de este rango, Tcl_SetChannelBufferSize establece el tamaño del búfer a 4096.

Tcl_NotifyChannel es llamada por un controlador de canal para indicar a la capa genérica que los eventos especificados por mask han ocurrido en el canal. Los controladores de canal son responsables de invocar esta función siempre que los manejadores de canal necesiten ser llamados para el canal (o se deban realizar otras tareas pendientes como un vaciado de escritura). Consulte WATCHPROC a continuación para más detalles.

Tcl_BadChannelOption es llamada desde el setOptionProc o getOptionProc específico del controlador para generar un mensaje de error completo.

Tcl_ChannelBuffered retorna el número de bytes de entrada actualmente almacenados en el búfer interno (área de retroceso) del propio canal. No informa sobre los datos en los búferes generales para la pila de canales de la que forma parte el canal suministrado.

Tcl_IsChannelShared comprueba el contador de referencias del channel especificado y retorna si el channel fue compartido entre múltiples intérpretes (resultado == 1) o no (resultado == 0).

Tcl_IsChannelRegistered comprueba si el channel especificado está registrado en el intérprete dado (resultado == 1) o no (resultado == 0).

Tcl_IsChannelExisting comprueba si un canal con el nombre especificado está registrado en la lista global (del hilo) de todos los canales (resultado == 1) o no (resultado == 0).

Tcl_CutChannel elimina el channel especificado de la lista global (del hilo) de todos los canales (del hilo actual). No se permite la aplicación a un canal todavía registrado en algún intérprete. También notifica al controlador si la versión de Tcl_ChannelType es TCL_CHANNEL_VERSION_4 (o superior) y si Tcl_DriverThreadActionProc está definido para él.

Tcl_SpliceChannel añade el channel especificado a la lista global (del hilo) de todos los canales (del hilo actual). No se permite la aplicación a un canal registrado en algún intérprete. También notifica al controlador si la versión de Tcl_ChannelType es TCL_CHANNEL_VERSION_4 (o superior) y si Tcl_DriverThreadActionProc está definido para él.

Tcl_ClearChannelHandlers elimina todos los manejadores de canal y scripts de eventos asociados con el channel especificado, interrumpiendo así todo el procesamiento de eventos para este canal.

TCL_CHANNELTYPE

Un controlador de canal proporciona una estructura Tcl_ChannelType que contiene punteros a funciones que implementan las diversas operaciones en un canal; estas operaciones se invocan según sea necesario por la capa genérica. La estructura fue versionada a partir de Tcl 8.3.2/8.4 para corregir un problema con los controladores de canal apilados. Consulte la sección OLD CHANNEL TYPES a continuación para obtener detalles sobre la estructura antigua.

La estructura Tcl_ChannelType contiene los siguientes campos:

typedef struct Tcl_ChannelType {
        const char *typeName;
        Tcl_ChannelTypeVersion version;
        Tcl_DriverCloseProc *closeProc;
        Tcl_DriverInputProc *inputProc;
        Tcl_DriverOutputProc *outputProc;
        Tcl_DriverSeekProc *seekProc;
        Tcl_DriverSetOptionProc *setOptionProc;
        Tcl_DriverGetOptionProc *getOptionProc;
        Tcl_DriverWatchProc *watchProc;
        Tcl_DriverGetHandleProc *getHandleProc;
        Tcl_DriverClose2Proc *close2Proc;
        Tcl_DriverBlockModeProc *blockModeProc;
        Tcl_DriverFlushProc *flushProc;
        Tcl_DriverHandlerProc *handlerProc;
        Tcl_DriverWideSeekProc *wideSeekProc;
        Tcl_DriverThreadActionProc *threadActionProc;
        Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

No es necesario proporcionar implementaciones para todas las operaciones del canal. Aquellas que no sean necesarias pueden establecerse en NULL en la estructura: blockModeProc, seekProc, setOptionProc, getOptionProc, getHandleProc y close2Proc, además de flushProc, handlerProc, threadActionProc y truncateProc. Otras funciones que no pueden implementarse de manera significativa deben retornar EINVAL cuando se llamen, para indicar que las operaciones que representan no están disponibles. También tenga en cuenta que wideSeekProc puede ser NULL si seekProc lo es.

El usuario solo debe usar la estructura anterior para la instanciación de Tcl_ChannelType. Al hacer referencia a los campos en una estructura Tcl_ChannelType, se deben utilizar las siguientes funciones para obtener los valores: Tcl_ChannelName, Tcl_ChannelVersion, Tcl_ChannelBlockModeProc, Tcl_ChannelCloseProc, Tcl_ChannelClose2Proc, Tcl_ChannelInputProc, Tcl_ChannelOutputProc, Tcl_ChannelSeekProc, Tcl_ChannelWideSeekProc, Tcl_ChannelThreadActionProc, Tcl_ChannelTruncateProc, Tcl_ChannelSetOptionProc, Tcl_ChannelGetOptionProc, Tcl_ChannelWatchProc, Tcl_ChannelGetHandleProc, Tcl_ChannelFlushProc o Tcl_ChannelHandlerProc.

El cambio en las estructuras se hizo de tal manera que los tipos de canal estándar son binariamente compatibles. Sin embargo, los tipos de canal que utilizan canales apilados (es decir, TLS, Trf) tienen nuevas versiones para corresponder al cambio anterior, ya que el código anterior para canales apilados tenía problemas.

TYPENAME

El campo typeName contiene una cadena terminada en nulo que identifica el tipo del dispositivo implementado por este controlador, por ejemplo, file o socket.

Este valor se puede recuperar con Tcl_ChannelName, que retorna un puntero a la cadena.

VERSION

El campo version debe establecerse en la versión de la estructura que requiere. TCL_CHANNEL_VERSION_2 es el mínimo recomendado. TCL_CHANNEL_VERSION_3 debe establecerse para especificar el miembro wideSeekProc. TCL_CHANNEL_VERSION_4 debe establecerse para especificar el miembro threadActionProc (incluye wideSeekProc). TCL_CHANNEL_VERSION_5 debe establecerse para especificar los miembros truncateProc (incluye wideSeekProc y threadActionProc). Si no se establece en ninguno de estos, se asume que este Tcl_ChannelType tiene la estructura original. Consulte OLD CHANNEL TYPES para más detalles. Si bien Tcl reconocerá y funcionará con ambas estructuras, los canales apilados deben ser de al menos TCL_CHANNEL_VERSION_2 para funcionar correctamente.

Este valor se puede recuperar con Tcl_ChannelVersion, que retorna uno de TCL_CHANNEL_VERSION_5, TCL_CHANNEL_VERSION_4, TCL_CHANNEL_VERSION_3, TCL_CHANNEL_VERSION_2 o TCL_CHANNEL_VERSION_1.

BLOCKMODEPROC

El campo blockModeProc contiene la dirección de una función llamada por la capa genérica para establecer el modo de bloqueo y no bloqueo en el dispositivo. BlockModeProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverBlockModeProc(
        ClientData instanceData,
        int mode);

El instanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando se creó este canal. El argumento mode es ya sea TCL_MODE_BLOCKING o TCL_MODE_NONBLOCKING para establecer el dispositivo en modo de bloqueo o no bloqueo. La función debe retornar cero si la operación fue exitosa, o un código de error POSIX distinto de cero si la operación falló.

Si la operación es exitosa, la función puede modificar el instanceData suministrado para registrar que el canal entró en modo de bloqueo o no bloqueo y para implementar el comportamiento de bloqueo o no bloqueo. Para algunos tipos de dispositivos, el comportamiento de bloqueo y no bloqueo puede ser implementado por el sistema operativo subyacente; para otros tipos de dispositivos, el comportamiento debe ser emulado en el controlador de canal.

Este valor se puede recuperar con Tcl_ChannelBlockModeProc, que retorna un puntero a la función.

Un controlador de canal que **no** suministra un blockModeProc debe tener mucho, mucho cuidado. Debe decirle a la capa genérica exactamente qué modo de bloqueo es aceptable para él, y esto también debería documentarse para el usuario, de modo que el modo de bloqueo del canal no se cambie a un valor inaceptable. Cualquier confusión aquí puede llevar al intérprete a un punto muerto (falso y difícil de encontrar).

CLOSEPROC

El campo closeProc contiene la dirección de una función que es llamada por la capa genérica cuando un canal se cierra. closeProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverCloseProc(
        ClientData instanceData,
        Tcl_Interp *interp);

instanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó el canal. La función debe realizar todas las operaciones de limpieza necesarias para el canal, como liberar recursos y cerrar los descriptores de archivo subyacentes. El canal no debe ser invocado para más operaciones después de que se llame a closeProc. Si la operación de cierre es exitosa, la función debe devolver cero; de lo contrario, debe devolver un código de error POSIX distinto de cero. Adicionalmente, si ocurre un error y interp no es NULL, el procedimiento debe almacenar un mensaje de error en el resultado del intérprete.

Alternativamente, los canales que admiten el cierre de los lados de lectura y escritura de forma independiente pueden establecer closeProc en TCL_CLOSE2PROC y close2Proc en la dirección de una función que coincida con el siguiente prototipo:

typedef int Tcl_DriverClose2Proc(
        ClientData instanceData,
        Tcl_Interp *interp,
        int flags);

Se llamará a close2Proc con flags establecido en una combinación OR de TCL_CLOSE_READ o TCL_CLOSE_WRITE para indicar que el controlador debe cerrar el lado de lectura y/o escritura del canal. Al controlador del canal se le puede invocar para realizar operaciones adicionales en el canal después de que se llame a close2Proc para cerrar uno o ambos lados del canal. Si flags es 0 (cero), el controlador debe cerrar el canal de la manera descrita anteriormente para closeProc. No se invocarán más operaciones en esta instancia después de que se llame a close2Proc con todas las banderas despejadas. En todos los casos, la función close2Proc debe devolver cero si la operación de cierre fue exitosa; de lo contrario, debe devolver un código de error POSIX distinto de cero. Adicionalmente, si ocurre un error y interp no es NULL, el procedimiento debe almacenar un mensaje de error en el resultado del intérprete.

Los valores closeProc y close2Proc se pueden recuperar con Tcl_ChannelCloseProc o Tcl_ChannelClose2Proc, que devuelven un puntero a la función respectiva.

INPUTPROC

El campo inputProc contiene la dirección de una función que es llamada por la capa genérica para leer datos del archivo o dispositivo y almacenarlos en un búfer interno. InputProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverInputProc(
        ClientData instanceData,
        char *buf,
        int bufSize,
        int *errorCodePtr);

instanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando se creó el canal. El argumento buf apunta a una matriz de bytes en la que se almacenará la entrada del dispositivo, y el argumento bufSize indica cuántos bytes están disponibles en buf.

El argumento errorCodePtr apunta a una variable entera proporcionada por la capa genérica. Si ocurre un error, la función debe establecer la variable a un código de error POSIX que identifique el error que ocurrió.

La función debe leer datos del dispositivo de entrada encapsulado por el canal y almacenarlos en buf. En caso de éxito, la función debe devolver un entero no negativo que indique cuántos bytes se leyeron del dispositivo de entrada y se almacenaron en buf. En caso de error, la función debe devolver -1. Si ocurre un error después de que se hayan leído algunos datos del dispositivo, esos datos se pierden.

Si inputProc puede determinar que el dispositivo de entrada tiene algunos datos disponibles pero menos de los solicitados por el argumento bufSize, la función solo debe intentar leer tantos datos como estén disponibles y devolver sin bloquear. Si no hay datos disponibles en absoluto en el dispositivo de entrada y el canal está en modo no bloqueante, la función debe devolver un error EAGAIN. Si no hay datos disponibles en absoluto en el dispositivo de entrada y el canal está en modo bloqueante, la función debe bloquearse durante el menor tiempo posible hasta que se puedan leer al menos un byte de datos del dispositivo; luego, debe devolver tantos datos como pueda leer sin bloquear.

Este valor se puede recuperar con Tcl_ChannelInputProc, que devuelve un puntero a la función.

OUTPUTPROC

El campo outputProc contiene la dirección de una función que es llamada por la capa genérica para transferir datos de un búfer interno al dispositivo de salida. OutputProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverOutputProc(
        ClientData instanceData,
        const char *buf,
        int toWrite,
        int *errorCodePtr);

instanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando se creó el canal. El argumento buf contiene una matriz de bytes que se escribirán en el dispositivo, y el argumento toWrite indica cuántos bytes se escribirán desde el argumento buf.

El argumento errorCodePtr apunta a una variable entera proporcionada por la capa genérica. Si ocurre un error, la función debe establecer esta variable a un código de error POSIX que identifique el error.

La función debe escribir los datos en buf en el dispositivo de salida encapsulado por el canal. En caso de éxito, la función debe devolver un entero no negativo que indique cuántos bytes se escribieron en el dispositivo de salida. El valor de retorno es normalmente el mismo que toWrite, pero puede ser menor en algunos casos, como si la operación de salida es interrumpida por una señal. Si ocurre un error, la función debe devolver -1. En caso de error, es posible que se hayan escrito algunos datos en el dispositivo.

Si el canal no está bloqueado y el dispositivo de salida no puede absorber ningún dato, la función debe devolver -1 con un error EAGAIN sin escribir ningún dato.

Este valor se puede recuperar con Tcl_ChannelOutputProc, que devuelve un puntero a la función.

SEEKPROC Y WIDESEEKPROC

El campo seekProc contiene la dirección de una función que es llamada por la capa genérica para mover el punto de acceso en el que se aplicarán las operaciones posteriores de entrada o salida. SeekProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverSeekProc(
        ClientData instanceData,
        long offset,
        int seekMode,
        int *errorCodePtr);

El argumento instanceData es el mismo que el valor dado a Tcl_CreateChannel cuando se creó este canal. Offset y seekMode tienen el mismo significado que para el procedimiento Tcl_Seek (descrito en la entrada del manual para Tcl_OpenFileChannel).

El argumento errorCodePtr apunta a una variable entera proporcionada por la capa genérica para devolver valores errno de la función. La función debe establecer esta variable a un código de error POSIX si ocurre un error. La función debe almacenar un código de error EINVAL si el tipo de canal no implementa el desplazamiento.

El valor de retorno es el nuevo punto de acceso o -1 en caso de error. Si ocurrió un error, la función no debe mover el punto de acceso.

Si hay un campo seekProc no NULL, el campo wideSeekProc puede contener la dirección de una función alternativa a utilizar que maneja desplazamientos amplios (es decir, mayores de 32 bits), permitiendo así los desplazamientos dentro de archivos mayores a 2GB. Se llamará a wideSeekProc con preferencia sobre seekProc, pero ambos deben estar definidos si se define wideSeekProc. WideSeekProc debe coincidir con el siguiente prototipo:

typedef Tcl_WideInt Tcl_DriverWideSeekProc(
        ClientData instanceData,
        Tcl_WideInt offset,
        int seekMode,
        int *errorCodePtr);

Los argumentos y los valores de retorno significan lo mismo que con seekProc arriba, excepto que el tipo de los desplazamientos y el tipo de retorno son diferentes.

El valor seekProc se puede recuperar con Tcl_ChannelSeekProc, que devuelve un puntero a la función, y de manera similar se puede recuperar wideSeekProc con Tcl_ChannelWideSeekProc.

SETOPTIONPROC

El campo setOptionProc contiene la dirección de una función que es llamada por la capa genérica para establecer una opción específica del tipo de canal en un canal. setOptionProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverSetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        const char *newValue);

optionName es el nombre de una opción a establecer, y newValue es el nuevo valor para esa opción, como una cadena. instanceData es el mismo que el valor dado a Tcl_CreateChannel cuando se creó este canal. La función debe realizar cualquier acción específica del tipo de canal necesaria para implementar el nuevo valor de la opción.

Algunas opciones son manejadas por el código genérico y esta función nunca es llamada para establecerlas, por ejemplo, -blockmode. Otras opciones son específicas de cada tipo de canal y se llamará al procedimiento setOptionProc del controlador del canal para implementarlas. El campo setOptionProc puede ser NULL, lo que indica que este tipo de canal no admite opciones específicas del tipo.

Si el valor de la opción se modifica con éxito al nuevo valor, la función devuelve TCL_OK. Debe llamar a Tcl_BadChannelOption, que a su vez devuelve TCL_ERROR si optionName no es reconocido. Si newValue especifica un valor para la opción que no es compatible o si ocurre un error de llamada al sistema, la función debe dejar un mensaje de error en el resultado de interp si interp no es NULL. La función también debe llamar a Tcl_SetErrno para almacenar un código de error POSIX apropiado.

Este valor se puede recuperar con Tcl_ChannelSetOptionProc, que devuelve un puntero a la función.

typedef int Tcl_DriverGetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        Tcl_DString *optionValue);
