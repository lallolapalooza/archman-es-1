DESCRIPCIÓN

Hay varias razones para llamar a las funciones de la API Tcl_FS (por ejemplo, Tcl_FSAccess y Tcl_FSStat) en lugar de llamar directamente a funciones de nivel de sistema como access y stat. Primero, funcionan multiplataforma, por lo que una extensión que las llama debería funcionar sin modificaciones en Unix y Windows. Segundo, la implementación de Windows de algunas de estas funciones corrige algunos errores en las llamadas de nivel de sistema. Tercero, estas llamadas a funciones manejan cualquier conversión de ruta “Utf a nativo de plataforma” que pueda ser requerida (y pueden almacenar en caché los resultados de dichas conversiones para una mayor eficiencia en llamadas posteriores). Cuarto, y quizás lo más importante, todas estas funciones son “conscientes del sistema de archivos virtual”. Cualquier sistema de archivos virtual (VFS) que se haya registrado (a través de Tcl_FSRegister) puede redirigir el acceso a archivos a medios o métodos de acceso alternativos. Esto significa que todas estas funciones (y, por lo tanto, los comandos file, glob, pwd, cd, open, etc. de Tcl correspondientes) pueden operar en “archivos” que no son archivos nativos en el sistema de archivos nativo. Esto también significa que cualquier extensión de Tcl que acceda al sistema de archivos (FS para abreviar) a través de esta API es automáticamente “consciente del sistema de archivos virtual”. Por supuesto, si una extensión accede directamente al sistema de archivos nativo (a través de APIs específicas de la plataforma, por ejemplo), Tcl no puede interceptar tales llamadas.

Si se han registrado VFS apropiados, los “archivos” pueden ser, para dar dos ejemplos, remotos (por ejemplo, situados en un servidor ftp remoto) o archivados (por ejemplo, dentro de un archivo .zip). Dichos sistemas de archivos registrados proporcionan una tabla de búsqueda de funciones para implementar toda o parte de la funcionalidad enumerada aquí. Finalmente, las llamadas Tcl_FSStat y Tcl_FSLstat abstraen del contenido del búfer “struct stat”, lo que permite utilizar el mismo código tanto en sistemas con como sin soporte para archivos de más de 2 GB de tamaño.

La API Tcl_FS está **Tcl_Obj**-ificada y puede almacenar en caché representaciones internas y otras cadenas relacionadas con rutas (por ejemplo, el directorio de trabajo actual). Un efecto secundario de esto es que no se deben pasar valores con un recuento de referencias de cero a ninguna de estas funciones. Si se manejaran tales llamadas, podrían resultar en fugas de memoria (en algunas circunstancias, el código del sistema de archivos puede desear retener una referencia al valor pasado, y por lo tanto, no se debe suponer que después de que alguna de estas llamadas regrese, el valor aún tenga un recuento de referencias de cero, podría haber sido incrementado) o en una falla de segmentación directa (u otro error de acceso a memoria) debido a que el valor se libera a mitad de la manipulación compleja de valores requerida para garantizar que la ruta esté completamente normalizada y sea absoluta para la determinación del sistema de archivos. La lección práctica a aprender de esto es que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

es incorrecto y puede causar errores de memoria. El path debe tener su recuento de referencias incrementado antes de pasarlo, o decrementarlo. Por esta razón, los valores con un recuento de referencias de cero se consideran rutas de sistema de archivos no válidas y llamar a cualquier función de la API de Tcl_FS con dicho valor no tendrá ningún efecto.

FUNCIONES DE LA API FS

Tcl_FSCopyFile intenta copiar el archivo dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas se encuentran en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), se llama a la función “copiar archivo” de ese sistema de archivos (si no es NULL). De lo contrario, la función devuelve -1 y establece la variable global C errno al código de error POSIX “EXDEV” (que significa un “enlace entre dominios”).

Tcl_FSCopyDirectory intenta copiar el directorio dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas se encuentran en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), se llama a la función “copiar archivo” de ese sistema de archivos (si no es NULL). De lo contrario, la función devuelve -1 y establece la variable global C errno al código de error POSIX “EXDEV” (que significa un “enlace entre dominios”).

Tcl_FSCreateDirectory intenta crear el directorio dado por pathPtr llamando a la función “crear directorio” del sistema de archivos propietario.

Tcl_FSDeleteFile intenta eliminar el archivo dado por pathPtr llamando a la función “eliminar archivo” del sistema de archivos propietario.

Tcl_FSRemoveDirectory intenta eliminar el directorio dado por pathPtr llamando a la función “eliminar directorio” del sistema de archivos propietario.

Tcl_FSRenameFile intenta renombrar el archivo o directorio dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas se encuentran en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), se llama a la función “renombrar archivo” de ese sistema de archivos (si no es NULL). De lo contrario, la función devuelve -1 y establece la variable global C errno al código de error POSIX “EXDEV” (que significa un “enlace entre dominios”).

Tcl_FSListVolumes llama a cada sistema de archivos que tiene una función “listar volúmenes” no NULL y les pide que devuelvan su lista de volúmenes raíz. Acumula los valores de retorno en una lista que se devuelve al llamador (con un recuento de referencias de 0).

Tcl_FSEvalFileEx lee el archivo dado por pathPtr utilizando la codificación identificada por encodingName y evalúa su contenido como un script de Tcl. Devuelve la misma información que Tcl_EvalObjEx. Si encodingName es NULL, se utiliza la codificación del sistema para leer el contenido del archivo. Si el archivo no se pudo leer, se devuelve un error de Tcl para describir por qué no se pudo leer el archivo. El carácter de fin de archivo para los archivos es “\x1A” (^Z) para todas las plataformas. Si requiere un “^Z” en el código para la comparación de cadenas, puede usar “\x1A”, que será sustituido de forma segura por el intérprete de Tcl por “^Z”. Tcl_FSEvalFile es una versión más simple de Tcl_FSEvalFileEx que siempre utiliza la codificación del sistema al leer el archivo.

Tcl_FSLoadFile carga dinámicamente un archivo de código binario en memoria y devuelve las direcciones de dos procedimientos dentro de ese archivo, si están definidos. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr. Si ese sistema de archivos no implementa esta función (la mayoría de los sistemas de archivos virtuales no lo harán, debido a limitaciones del sistema operativo en la carga dinámica de código binario), Tcl intentará copiar el archivo a un directorio temporal y cargar ese archivo temporal. Tcl_FSUnloadFile revierte la operación, solicitando que se elimine la biblioteca indicada por loadHandle del proceso. Tenga en cuenta que, a diferencia del comando unload, esto no da a la biblioteca ninguna oportunidad de limpiar.

Ambas funciones anteriores devuelven un código de finalización estándar de Tcl. Si ocurre un error, se deja un mensaje de error en el resultado del interp.

El token proporcionado a través de la variable indicada por loadHandlePtr se puede usar con Tcl_FindSymbol.

Tcl_FSMatchInDirectory es utilizado por el código de globbing para buscar en un directorio todos los archivos que coinciden con un patrón dado. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el globbing. Los mensajes de error se colocan en interp (a menos que interp sea NULL, lo cual está permitido), pero los buenos resultados se colocan en resultPtr dado.

Tenga en cuenta que el código glob implementa patrones recursivos internamente, por lo que esta función solo recibirá patrones simples, que se pueden comparar utilizando la lógica de string match. Para manejar la recursión, Tcl llamará a esta función con frecuencia solicitando solo directorios que se devuelvan. Un caso especial de ser llamado con un patrón NULL indica que la ruta solo necesita ser verificada para el tipo correcto.

Tcl_FSLink reemplaza la versión de biblioteca de readlink y la extiende para admitir la creación de enlaces. Se llamará a la función apropiada para el sistema de archivos al que pertenece linkNamePtr.

Si toPtr es NULL, se realiza una acción de “leer enlace”. El resultado es un Tcl_Obj que especifica el contenido del enlace simbólico dado por linkNamePtr, o NULL si no se pudo leer el enlace. El resultado es propiedad del llamador, que debe llamar a Tcl_DecrRefCount cuando el resultado ya no sea necesario. Si toPtr no es NULL, Tcl debe crear un enlace de uno de los tipos pasados en la bandera linkAction. Esta bandera es una combinación OR de TCL_CREATE_SYMBOLIC_LINK y TCL_CREATE_HARD_LINK. Donde existe una opción (es decir, se pasa más de una bandera), la convención de Tcl es preferir los enlaces simbólicos. Cuando se crea un enlace con éxito, el valor de retorno debe ser toPtr (que, por lo tanto, ya es propiedad del llamador). Si no tiene éxito, se devuelve NULL.

Tcl_FSLstat llena la estructura Tcl_StatBuf statPtr con información sobre el archivo especificado. No necesita ningún derecho de acceso al archivo para obtener esta información, pero necesita derechos de búsqueda a todos los directorios nombrados en la ruta que conduce al archivo. La estructura Tcl_StatBuf incluye información sobre el dispositivo, inodo (siempre 0 en Windows), modo de privilegios, nlink (siempre 1 en Windows), id de usuario (siempre 0 en Windows), id de grupo (siempre 0 en Windows), rdev (igual que el dispositivo en Windows), tamaño, último

tiempo de acceso, tiempo de última modificación y tiempo de último cambio de metadatos. Consulte la API PORTABLE STAT RESULT para obtener una descripción de cómo escribir código portable para asignar y acceder a la estructura Tcl_StatBuf.

Si path existe, Tcl_FSLstat devuelve 0 y la estructura stat se rellena con datos. De lo contrario, se devuelve -1 y no se proporciona información stat.

Tcl_FSUtime reemplaza la versión de biblioteca de utime.

Esto devuelve 0 en caso de éxito y -1 en caso de error (según la documentación de utime). Si tiene éxito, la función actualizará los valores "atime" y "mtime" del archivo proporcionado.

Tcl_FSFileAttrsGet implementa el acceso de lectura para el subcomando file attributes enganchable. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

Si el resultado es TCL_OK, se colocó un valor en objPtrRef, que solo será válido temporalmente (a menos que se llame a Tcl_IncrRefCount).

Tcl_FSFileAttrsSet implementa el acceso de escritura para el subcomando file attributes enganchable. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

Tcl_FSFileAttrStrings implementa parte del subcomando file attributes enganchable. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

El procedimiento llamado puede devolver una matriz de cadenas o puede devolver NULL y colocar una lista de Tcl en objPtrRef dado. Tcl tomará esa lista y primero incrementará su recuento de referencias antes de usarla. Al finalizar ese uso, Tcl disminuirá su recuento de referencias. Por lo tanto, si Tcl debe desechar la lista cuando termine, debe tener un recuento de referencias de cero, y si Tcl no debe desechar la lista, el sistema de archivos debe asegurarse de retener un recuento de referencias para el valor.

Tcl_FSAccess comprueba si al proceso se le permitiría leer, escribir o probar la existencia del archivo (u otro objeto del sistema de archivos) cuyo nombre es pathname. Si pathname es un enlace simbólico en Unix, se probarán los permisos del archivo al que se refiere este enlace simbólico.

En caso de éxito (todos los permisos solicitados concedidos), se devuelve cero. En caso de error (al menos un bit en el modo solicitado un permiso denegado, o se produjo algún otro error), se devuelve -1.

Tcl_FSStat rellena la estructura Tcl_StatBuf statPtr con información sobre el archivo especificado. No necesita ningún derecho de acceso al archivo para obtener esta información, pero necesita derechos de búsqueda en todos los directorios mencionados en la ruta que conduce al archivo. La estructura Tcl_StatBuf incluye información sobre el dispositivo, inode (siempre 0 en Windows), modo de privilegios, nlink (siempre 1 en Windows), id de usuario (siempre 0 en Windows), id de grupo (siempre 0 en Windows), rdev (igual que el dispositivo en Windows), tamaño, tiempo de último acceso, tiempo de última modificación y tiempo de último cambio de metadatos. Consulte la API PORTABLE STAT RESULT para obtener una descripción de cómo escribir código portable para asignar y acceder a la estructura Tcl_StatBuf.

Si path existe, Tcl_FSStat devuelve 0 y la estructura stat se rellena con datos. De lo contrario, se devuelve -1 y no se proporciona información stat.

Tcl_FSOpenFileChannel abre un archivo especificado por pathPtr y devuelve un manejador de canal que se puede utilizar para realizar operaciones de entrada y salida en el archivo. Esta API se basa en el procedimiento fopen de la biblioteca estándar de E/S de Unix. La sintaxis y el significado de todos los argumentos son similares a los dados en el comando open de Tcl al abrir un archivo. Si se produce un error al abrir el canal, Tcl_FSOpenFileChannel devuelve NULL y registra un código de error POSIX que se puede recuperar con Tcl_GetErrno. Además, si interp no es NULL, Tcl_FSOpenFileChannel deja un mensaje de error en el resultado de interp después de cualquier error.

El canal recién creado no está registrado en el intérprete proporcionado; para registrarlo, use Tcl_RegisterChannel. Si uno de los canales estándar, stdin, stdout o stderr se cerró previamente, la creación del nuevo canal también lo asigna como reemplazo del canal estándar.

Tcl_FSGetCwd reemplaza la versión de biblioteca de getcwd.

Devuelve el directorio de trabajo actual de la biblioteca de Tcl. Este puede ser diferente al directorio de trabajo de la plataforma nativa, lo que ocurre cuando el directorio de trabajo actual no está en el sistema de archivos nativo.

El resultado es un puntero a un Tcl_Obj que especifica el directorio actual, o NULL si no se pudo determinar el directorio actual. Si se devuelve NULL, se deja un mensaje de error en el resultado de interp.

El resultado ya tiene su recuento de referencias incrementado para el llamador. Cuando ya no sea necesario, se debe disminuir ese recuento de referencias. Esto es necesario por razones de seguridad de hilos, para permitir que varios hilos accedan a esta y funciones relacionadas, garantizando al mismo tiempo que los resultados sean siempre válidos.

Tcl_FSChdir reemplaza la versión de biblioteca de chdir. La ruta se normaliza y luego se pasa al sistema de archivos que la reclama. Si ese sistema de archivos no implementa esta función, Tcl recurrirá a una combinación de stat y access para verificar si el directorio existe y tiene los permisos apropiados.

Para los resultados, consulte la documentación de chdir. Si tiene éxito, mantenemos un registro de la ruta exitosa en cwdPathPtr para llamadas posteriores a Tcl_FSGetCwd.

Tcl_FSPathSeparator devuelve el carácter separador que se utilizará para el elemento más específico de la ruta especificada por pathPtr (es decir, la última parte de la ruta).

El separador se devuelve como un Tcl_Obj que contiene una cadena de longitud 1. Si la ruta no es válida, se devuelve NULL.

Tcl_FSJoinPath toma el Tcl_Obj dado, que debe ser una lista válida (a la que se le permite tener un recuento de referencias de cero), y devuelve el valor de ruta dado considerando los primeros elementos elementos como segmentos de ruta válidos (cada segmento de ruta puede ser una ruta completa, una ruta parcial o simplemente un solo directorio o nombre de archivo posible). Si algún segmento de ruta es en realidad una ruta absoluta, se descartan todos los segmentos de ruta anteriores. Si elements es menor que 0, usamos toda la lista.

Es posible que el valor devuelto sea en realidad un elemento de la lista dada, por lo que el llamador debe tener cuidado de incrementar el recuento de referencias del resultado antes de liberar la lista.

El valor devuelto, típicamente con un recuento de referencias de cero (pero podría compartirse bajo algunas condiciones), contiene la ruta unida. El llamador debe agregar un recuento de referencias al valor antes de usarlo. En particular, el valor devuelto podría ser un elemento de la lista dada, por lo que liberar la lista podría liberar el valor prematuramente si no se ha tomado ningún recuento de referencias. Si el número de elementos es cero, el valor devuelto será un Tcl_Obj de cadena vacía.

Tcl_FSSplitPath toma el Tcl_Obj dado, que debería ser una ruta válida, y devuelve un valor de lista de Tcl que contiene cada segmento de esa ruta como un elemento. Devuelve un valor de lista con un recuento de referencias de cero. Si el lenPtr pasado no es NULL, la variable a la que apunta se actualizará para contener el número de elementos en la lista devuelta.

Tcl_FSEqualPaths prueba si las dos rutas dadas representan el mismo objeto del sistema de archivos. Devuelve 1 si las rutas son iguales y 0 si son diferentes. Si alguna ruta es NULL, siempre se devuelve 0.

Tcl_FSGetNormalizedPath intenta extraer del Tcl_Obj dado una representación de ruta normalizada única, cuyo valor de cadena se puede utilizar como identificador único del archivo.

Devuelve el valor de ruta normalizado, propiedad de Tcl, o NULL si la ruta no era válida o no se pudo convertir correctamente. La extracción de rutas absolutas y normalizadas es muy eficiente (porque el sistema de archivos opera internamente con estas representaciones), aunque el resultado cuando el sistema de archivos contiene numerosos enlaces simbólicos puede no ser la versión más amigable de una ruta. El valor devuelto es propiedad de Tcl y tiene una vida útil equivalente a la de pathPtr pasado (a menos que sea una ruta relativa, en cuyo caso el valor de ruta normalizado puede liberarse en cualquier momento en que cambie la cwd): el llamador puede, por supuesto, incrementar el recuento de referencias si desea mantener una copia por más tiempo.

Tcl_FSJoinToPath toma el valor dado, que normalmente debería ser una ruta válida o NULL, y le une la matriz de segmentos de ruta proporcionados.

Devuelve un valor, típicamente con un recuento de referencias de cero (pero podría compartirse bajo algunas condiciones), que contiene la ruta unida. El llamador debe agregar un recuento de referencias al valor antes de usarlo. Si alguno de los valores pasados a esta función (pathPtr o elementos de path) tiene un recuento de referencias de cero, se liberarán cuando esta función regrese.

Tcl_FSConvertToPathType intenta convertir el Tcl_Obj dado a un tipo de ruta de Tcl válido, teniendo en cuenta que la cwd puede haber cambiado incluso si este valor supuestamente ya es del tipo correcto. El nombre del archivo puede comenzar con "~" (para indicar el directorio de inicio del usuario actual) o "~" (para indicar el directorio de inicio de cualquier usuario).

Si la conversión tiene éxito (es decir, el valor es una ruta válida en uno de los sistemas de archivos actuales), se devuelve TCL_OK. De lo contrario, se devuelve TCL_ERROR, y se puede dejar un mensaje de error en el intérprete.

Tcl_FSGetInternalRep extrae la representación interna de un valor de ruta dado, en el sistema de archivos dado. Si el valor de ruta pertenece a un sistema de archivos diferente, devolvemos NULL. Si la representación interna es actualmente NULL, intentamos generarla, llamando a Tcl_FSCreateInternalRepProc del sistema de archivos.

Devuelve NULL o una representación de ruta interna válida. Esta representación interna se almacena en caché, de modo que las llamadas repetidas a esta función no requerirán conversiones adicionales.

Tcl_FSGetTranslatedPath intenta extraer la ruta traducida del Tcl_Obj dado.

Si la traducción tiene éxito (es decir, el valor es una ruta válida), se devuelve. De lo contrario, se devuelve NULL, y se puede dejar un mensaje de error en el intérprete. Una ruta "traducida" es aquella que no contiene secuencias "~" o "~usuario" (estas se han expandido a su representación actual en el sistema de archivos). El valor devuelto es propiedad del llamador, que debe almacenarlo o llamar a Tcl_DecrRefCount para garantizar que la memoria se libere. Esta función tiene poco uso práctico, y Tcl_FSGetNormalizedPath o Tcl_FSGetNativePath suelen ser funciones mejores para la mayoría de los propósitos.

Tcl_FSGetTranslatedStringPath hace lo mismo que Tcl_FSGetTranslatedPath, pero devuelve una cadena de caracteres o NULL. La cadena devuelta es dinámicamente alocada

pagado y propiedad del llamante, que debe almacenarlo o llamar a ckfree para asegurarse de que se libere. De nuevo, Tcl_FSGetNormalizedPath o Tcl_FSGetNativePath son funciones generalmente mejores para usar en la mayoría de los propósitos.

Tcl_FSNewNativePath realiza algo así como lo inverso de las conversiones habituales obj->ruta->representación nativa. Si algún código recupera una ruta en forma nativa (de, por ejemplo, readlink o un diálogo nativo), y esa ruta se va a utilizar a nivel de Tcl, entonces llamar a esta función es una forma eficiente de crear el tipo de valor de ruta apropiado.

El valor resultante es un valor de “ruta” puro, que solo recibirá una representación de cadena UTF-8 si es requerido por algún código Tcl.

Tcl_FSGetNativePath es para uso de los sistemas de archivos nativos Win/Unix, para que puedan recuperar fácilmente la representación nativa (char* o TCHAR*) de una ruta. Esta función es un envoltorio de conveniencia alrededor de Tcl_FSGetInternalRep. Puede ser deseable en el futuro tener representaciones nativas no basadas en cadenas (por ejemplo, en macOS, una representación que use una estructura fileSpec de FSRef sería probablemente más eficiente). En Windows, una representación Unicode completa permitiría rutas de longitud ilimitada. Actualmente, la representación es simplemente una cadena de caracteres que puede contener la ruta relativa o una ruta completa, absoluta y normalizada en la codificación nativa (condiciones complejas dictan cuál de estas se proporcionará, por lo que ninguna puede ser confiable, a menos que se sepa que la ruta es absoluta). Si necesita una ruta nativa que deba ser absoluta, entonces debe solicitar la versión nativa de una ruta normalizada. Si por alguna razón se necesita una versión no absoluta y no normalizada de la ruta, esta debe construirse por separado (por ejemplo, usando Tcl_FSGetTranslatedPath).

La representación nativa se almacena en caché para que las llamadas repetidas a esta función no requieran conversiones adicionales. El valor de retorno es propiedad de Tcl y tiene una vida útil equivalente a la del pathPtr pasado (a menos que sea una ruta relativa, en cuyo caso la representación nativa puede liberarse en cualquier momento en que cambie el directorio de trabajo actual).

Tcl_FSFileSystemInfo devuelve una lista de dos elementos. El primer elemento es el nombre del sistema de archivos (por ejemplo, “native”, “vfs”, “zip”, o “prowrap”, quizás), y el segundo es el tipo particular de la ruta dada dentro de ese sistema de archivos (que depende del sistema de archivos). El segundo elemento puede estar vacío si el sistema de archivos no proporciona una categorización adicional de archivos.

Se devuelve una lista válida, a menos que el valor de la ruta no sea reconocido, en cuyo caso se devolverá NULL.

Tcl_FSGetFileSystemForPath devuelve un puntero al Tcl_Filesystem que acepta esta ruta como válida.

Si ningún sistema de archivos acepta la ruta, se devuelve NULL.

Tcl_FSGetPathType determina si la ruta dada es relativa al directorio actual, relativa al volumen actual o absoluta.

Devuelve uno de TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE o TCL_PATH_VOLUME_RELATIVE

LA API DEL SISTEMA DE ARCHIVOS VIRTUAL

Un sistema de archivos proporciona una estructura Tcl_Filesystem que contiene punteros a funciones que implementan las diversas operaciones en un sistema de archivos; estas operaciones se invocan según sea necesario por la capa genérica, lo que generalmente ocurre a través de las funciones enumeradas anteriormente.

Las estructuras Tcl_Filesystem se manipulan utilizando los siguientes métodos.

Tcl_FSRegister toma un puntero a una estructura de sistema de archivos y un dato opcional para asociar con ese sistema de archivos. Al llamar a esta función, Tcl adjuntará el sistema de archivos a la lista de sistemas de archivos conocidos y se volverá completamente funcional inmediatamente. Tcl no comprueba si el mismo sistema de archivos se registra múltiples veces (y en general, eso no es algo bueno de hacer). Se devolverá TCL_OK.

Tcl_FSUnregister elimina la estructura de sistema de archivos dada de la lista de sistemas de archivos conocidos, si es conocida, y devuelve TCL_OK. Si el sistema de archivos no está registrado actualmente, se devuelve TCL_ERROR.

Tcl_FSData devolverá el clientData asociado con el sistema de archivos dado, si ese sistema de archivos está registrado. De lo contrario, devolverá NULL.

Tcl_FSMountsChanged se utiliza para informar al núcleo de Tcl que el conjunto de puntos de montaje para el sistema de archivos dado (ya registrado) ha cambiado, y que las representaciones de archivos en caché, por lo tanto, pueden no ser correctas.

Las muchas funciones en esta estructura se dividen en tres categorías: funciones de infraestructura (casi todas las cuales deben implementarse), funciones operativas (que deben implementarse si se proporciona un sistema de archivos completo) y funciones de eficiencia (que solo necesitan implementarse si se pueden hacer de manera eficiente, o si tienen efectos secundarios que son requeridos por el sistema de archivos; Tcl tiene emulaciones menos eficientes a las que puede recurrir). Es importante tener en cuenta que, en la versión actual de Tcl, la mayoría de estas sustituciones solo se utilizan para manejar comandos iniciados en Tcl, no en C. Lo que esto significa es que, si se emite un comando file rename en Tcl, y los sistemas de archivos relevantes no implementan su Tcl_FSRenameFileProc, el núcleo de Tcl recurrirá a una combinación de otras funciones del sistema de archivos (utilizará Tcl_FSCopyFileProc seguido de Tcl_FSDeleteFileProc, y si Tcl_FSCopyFileProc no está implementado, hay una sustitución adicional). Sin embargo, si se emite un comando Tcl_FSRenameFileProc a nivel de C, no ocurren tales sustituciones. Esto es cierto excepto para las últimas cuatro entradas en la tabla del sistema de archivos (lstat, load, getcwd y chdir) para las cuales sí ocurren sustituciones a nivel de C.

Cualquier función que tome nombres de ruta en forma Tcl_Obj los toma en forma UTF-8. La API de infraestructura del sistema de archivos está diseñada para admitir la conversión eficiente y en caché de estas rutas UTF-8 a otras representaciones nativas.

FILESYSTEM INFRASTRUCTURE

These fields contain basic information about the filesystem structure and addresses of functions which are used to associate a particular filesystem with a file path, and deal with the internal handling of path representations, for example copying and freeing such representations.

TYPENAME

The typeName field contains a null-terminated string that identifies the type of the filesystem implemented, e.g. "native", "zip" or "vfs".

STRUCTURE LENGTH

The structureLength field is generally implemented as sizeof(Tcl_Filesystem), and is there to allow easier binary backwards compatibility if the size of the structure changes in a future Tcl release.

VERSION

The version field should be set to TCL_FILESYSTEM_VERSION_1.

PATHINFILESYSTEMPROC

The pathInFilesystemProc field contains the address of a function which is called to determine whether a given path value belongs to this filesystem or not. Tcl will only call the rest of the filesystem functions with a path for which this function has returned TCL_OK. If the path does not belong, -1 should be returned (the behavior of Tcl for any other return value is not defined). If TCL_OK is returned, then the optional clientDataPtr output parameter can be used to return an internal (filesystem specific) representation of the path, which will be cached inside the path value, and may be retrieved efficiently by the other filesystem functions. Tcl will simultaneously cache the fact that this path belongs to this filesystem. Such caches are invalidated when filesystem structures are added or removed from Tcl's internal list of known filesystems.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

Function to normalize a path. Should be implemented for all filesystems which can have multiple string representations for the same path value. In Tcl, every "path" must have a single unique "normalized" string representation. Depending on the filesystem, there may be more than one unnormalized string representation which refers to that path (e.g., a relative path, a path with different character case if the filesystem is case insensitive, a path containing a reference to a home directory such as "~", a path containing symbolic links, etc). If the very last component in the path is a symbolic link, it should not be converted into the value it points to (but its case or other aspects should be made unique). All other path components should be converted from symbolic links. This one exception is required to agree with Tcl's semantics with file delete, file rename, file copy operating on symbolic links. This function may be called with nextCheckpoint either at the beginning of the path (i.e., zero), at the end of the path, or at any intermediate file separator in the path. It will never point to any other arbitrary position in the path. In the last of the three valid cases, the implementation can assume that the path up to and including the file separator is known and normalized.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

FILESYSTEM OPERATIONS

The fields in this section of the structure contain addresses of functions which are called to carry out the basic filesystem operations. A filesystem which expects to be used with the complete standard Tcl command set must implement all of these. If some of them are not implemented, then certain Tcl commands may fail when operating on paths within that filesystem. However, in some instances this may be desirable (for example, a read-only filesystem should not implement the last four functions, and a filesystem which does not support symbolic links need not implement the readlink function, etc. The Tcl core expects filesystems to behave in this way).

FILESYSTEMPATHTYPEPROC

Function to determine the type of a path in this filesystem. May be NULL, in which case no type information will be available to users of the filesystem. The "type" is used only for informational purposes, and should be returned as the string representation of the Tcl_Obj which is returned. A typical return value might be "networked", "zip" or "ftp". The Tcl_Obj result is owned by the filesystem and so Tcl will increment the reference count of that value if it wishes to retain a reference to it.

typedef Tcl_Obj *Tcl_FSFilesystemPathTypeProc(
        Tcl_Obj *pathPtr);

FILESYSTEMSEPARATORPROC

Function to return the separator character(s) for this filesystem. This need only be implemented if the filesystem wishes to use a different separator than the standard string "/". Amongst other uses, it is returned by the file separator command. The return value should be a value with reference count of zero.

typedef Tcl_Obj *Tcl_FSFilesystemSeparatorProc(
        Tcl_Obj *pathPtr);

STATPROC

Function to process a Tcl_FSStat call. Must be implemented for any reasonable filesystem, since many Tcl level commands depend crucially upon it (e.g., file atime, file isdirectory, file size, glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

The Tcl_FSStatProc fills the stat structure statPtr with information about the specified file. You do not need any access rights to the file to get this information but you need search rights to all directories named in the path leading to the file. The stat structure includes info regarding device, inode (always 0 on Windows), privilege mode, nlink (always 1 on Windows), user id (always 0 on Windows), group id (always 0 on Windows), rdev (same as device on Windows), size, last access time, last modification time, and last metadata change time.

If the file represented by pathPtr exists, the Tcl_FSStatProc returns 0 and the stat structure is filled with data. Otherwise, -1 is returned, and no stat info is given.

ACCESSPROC

Function to process a Tcl_FSAccess call. Must be implemented for any reasonable filesystem, since many Tcl level commands depend crucially upon it (e.g., file exists, file readable).

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

The Tcl_FSAccessProc checks whether the process would be allowed to read, write or test for existence of the file (or other filesystem object) whose name is in pathPtr. If the pathname refers to a symbolic link, then the permissions of the file referred by this symbolic link should be tested.

On success (all requested permissions granted), zero is returned. On error (at least one bit in mode asked for a permission that is denied, or some other error occurred), -1 is returned.

OPENFILECHANNELPROC

Function to process a Tcl_FSOpenFileChannel call. Must be implemented for any filesystem that supports opening files. This is used by commands like open and read.

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_Obj *chanPtr,
        const char *mode);

This function opens the file specified by pathPtr in the mode specified by mode and returns a Tcl channel. If the file cannot be opened, it returns NULL and leaves an error message in the interpreter.

OPENFILECHANNELPROC

Función para procesar una llamada a Tcl_FSOpenFileChannel. Debe ser implementada para cualquier sistema de archivos razonable, ya que las operaciones que requieren abrir o acceder al contenido de un archivo la utilizarán (p. ej., open, encoding y muchos comandos de Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

El Tcl_FSOpenFileChannelProc abre un archivo especificado por pathPtr y devuelve un manejador de canal que se puede utilizar para realizar entrada y salida en el archivo. Esta API está modelada según el procedimiento fopen de la biblioteca de E/S estándar de Unix. La sintaxis y el significado de todos los argumentos son similares a los dados en el comando open de Tcl al abrir un archivo, donde el argumento mode es una combinación de las banderas POSIX O_RDONLY, O_WRONLY, etc. Si ocurre un error al abrir el canal, el Tcl_FSOpenFileChannelProc devuelve NULL y registra un código de error POSIX que se puede recuperar con Tcl_GetErrno. Además, si interp no es NULL, el Tcl_FSOpenFileChannelProc deja un mensaje de error en el resultado de interp después de cualquier error.

El canal recién creado no debe ser registrado en el intérprete proporcionado por un Tcl_FSOpenFileChannelProc; esa tarea corresponde al que llama a Tcl_FSOpenFileChannel (si es necesario). Si uno de los canales estándar, stdin, stdout o stderr fue cerrado previamente, el acto de crear el nuevo canal también lo asigna como reemplazo del canal estándar.

MATCHINDIRECTORYPROC

Función para procesar una llamada a Tcl_FSMatchInDirectory. Si no se implementa, la funcionalidad de globbing y copia recursiva faltará en el sistema de archivos (y esto puede afectar a comandos como encoding names que utilizan funcionalidad de globbing internamente).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La función debe devolver todos los archivos o directorios (u otros objetos del sistema de archivos) que coincidan con el patrón dado y se ajusten a la especificación de types. Hay dos formas en las que esta función puede ser llamada. Si pattern es NULL, entonces pathPtr es una especificación de ruta completa de un solo archivo o directorio que debe ser verificado por existencia y tipo correcto. De lo contrario, pathPtr es un directorio, cuyo contenido la función debe buscar archivos o directorios que tengan el tipo correcto. En cualquier caso, se puede asumir que pathPtr no es NULL ni está vacío. Actualmente no está documentado si pathPtr tendrá o no un separador de archivos al final, por lo que el código debe ser flexible a ambas posibilidades.

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso de coincidencia. Los mensajes de error se colocan en interp, a menos que interp sea NULL, en cuyo caso no es necesario generar ningún mensaje de error; en un resultado TCL_OK, los resultados deben añadirse al valor dado resultPtr (que se puede asumir que es una lista válida no compartida de Tcl). Las coincidencias añadidas a resultPtr deben incluir cualquier prefijo de ruta dado en pathPtr (esto generalmente significa que serán especificaciones de ruta absoluta). Tenga en cuenta que si no se encuentran coincidencias, eso simplemente conduce a un resultado vacío; los errores solo se señalan para problemas reales de archivos o del sistema de archivos que puedan ocurrir durante el proceso de coincidencia.

La estructura Tcl_GlobTypeData pasada en el parámetro types contiene los siguientes campos:

typedef struct Tcl_GlobTypeData {
    /* Corresponde a bcdpfls como en 'find -t' */
    int type;
    /* Corresponde a los permisos del archivo */
    int perm;
    /* Tipo de Mac aceptable */
    Tcl_Obj *macType;
    /* Creador de Mac aceptable */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Hay dos casos específicos que es importante manejar correctamente, ambos cuando types no es NULL. Los dos casos son cuando types->types & TCL_GLOB_TYPE_DIR o types->types & TCL_GLOB_TYPE_MOUNT son verdaderos (y en particular cuando las otras banderas son falsas). En el primer caso, la función debe listar los directorios contenidos. Tcl utiliza esto para implementar el globbing recursivo, por lo que es crucial que los sistemas de archivos implementen la coincidencia de directorios correctamente. En el segundo caso, con TCL_GLOB_TYPE_MOUNT, el sistema de archivos debe listar los puntos de montaje que se encuentran dentro del pathPtr dado (y en este caso, pathPtr no necesita estar dentro del mismo sistema de archivos, a diferencia de todos los demás casos en los que se llama a esta función). El soporte para esto es crucial si Tcl va a tener transiciones fluidas entre un sistema de archivos y otro.

UTIMEPROC

Función para procesar una llamada a Tcl_FSUtime. Requerida para permitir la configuración (no la lectura) de tiempos con file mtime, file atime y la implementación open-r/open-w/fcopy de file copy.

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

Los tiempos de acceso y modificación del archivo especificado por pathPtr deben ser cambiados a los valores dados en la estructura tval.

El valor de retorno debe ser 0 en caso de éxito y -1 en caso de error, como con el utime del sistema.

LINKPROC

Función para procesar una llamada a Tcl_FSLink. Solo debe implementarse si el sistema de archivos admite enlaces, y de lo contrario puede ser NULL.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

Si toPtr es NULL, se le pide a la función que lea el contenido de un enlace. El resultado es un Tcl_Obj que especifica el contenido del enlace dado por linkNamePtr, o NULL si el enlace no pudo ser leído. El resultado es propiedad del que llama (y por lo tanto su contador de referencias debe ser incrementado antes de ser devuelto). Cualquier que llame debe llamar a Tcl_DecrRefCount en este resultado cuando ya no sea necesario. Si toPtr no es NULL, la función debe intentar crear un enlace. El resultado en este caso debe ser toPtr si el enlace fue exitoso y NULL en caso contrario. En este caso, el resultado no es propiedad del que llama (es decir, no se necesitan manipulaciones del contador de referencias en ninguno de los extremos). Consulte la documentación de Tcl_FSLink para la correcta interpretación de las banderas de linkAction.

LISTVOLUMESPROC

Función para listar cualquier volumen de sistema de archivos añadido por este sistema de archivos. Solo debe implementarse si el sistema de archivos agrega volúmenes al principio del sistema de archivos, para que puedan ser devueltos por file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

El resultado debe ser una lista de volúmenes añadidos por este sistema de archivos, o NULL (o una lista vacía) si no se proporcionan volúmenes. Se considera que el valor del resultado es propiedad del sistema de archivos (no del núcleo de Tcl), pero se le debe dar un contador de referencias para Tcl. Tcl utilizará el contenido de la lista e incrementará ese contador de referencias. Esto permite a los sistemas de archivos elegir si realmente desean conservar una lista "global" de volúmenes o no (si no, generan la lista sobre la marcha y se la pasan a Tcl con un contador de referencias de 1 y luego se olvidan de la lista; si sí, simplemente incrementan el contador de referencias de su lista global y se la pasan a Tcl, que copiará el contenido y luego decrementará el contador de vuelta a donde estaba).

Por lo tanto, Tcl considera que los valores de retorno de este proc son de solo lectura.

FILEATTRSTRINGSPROC

Función para listar todas las cadenas de atributos que son válidas para este sistema de archivos. Si no se implementa, el sistema de archivos no admitirá el comando file attributes. Esto permite adjuntar información adicional arbitraria a los archivos en el sistema de archivos. Si no se implementa, no hay necesidad de implementar los métodos get y set.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

La función llamada puede devolver una matriz de cadenas o puede devolver NULL y colocar una lista de Tcl en objPtrRef. Tcl tomará esa lista e incrementará primero su contador de referencias antes de usarla. Al completar ese uso, Tcl decrementará su contador de referencias. Por lo tanto, si la lista debe ser eliminada por Tcl cuando termine, debe tener un contador de referencias de cero, y si la lista no debe ser eliminada, el sistema de archivos debe asegurarse de devolver un valor con un contador de referencias de al menos uno.

FILEATTRSGETPROC

Función para procesar una llamada a Tcl_FSFileAttrsGet, utilizada por file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

Devuelve un código de retorno estándar de Tcl. El valor del atributo recuperado, que corresponde al elemento del índice index en la lista devuelta por Tcl_FSFileAttrStringsProc, es un Tcl_Obj colocado en objPtrRef (si se devolvió TCL_OK) y es probable que tenga un contador de referencias de cero. De cualquier manera, debemos almacenarlo en algún lugar (por ejemplo, el resultado de Tcl), o incrementar/decrementar su contador de referencias para asegurar que se libere correctamente.

FILEATTRSSETPROC

Función para procesar una llamada a Tcl_FSFileAttrsSet, utilizada por file attributes. Si el sistema de archivos es de solo lectura, no es necesario implementarlo.

typedef int Tcl_FSFileAttrsSetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj *objPtr);

El valor del atributo del elemento del índice index en la lista devuelta por Tcl_FSFileAttrStringsProc debe establecerse en el objPtr dado.

CREATEDIRECTORYPROC

FILESYSTEM OPERATIONS

The following are functions used to implement Tcl's filesystem interface. They are used by the Tcl core and are intended to be implemented by Tcl packages that introduce new virtual filesystems.

CREATEDIRECTORYPROC

Function to process a Tcl_FSCreateDirectory call. Should be implemented unless the FS is read-only.

typedef int Tcl_FSCreateDirectoryProc(
        Tcl_Obj *pathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, a new directory should have been added to the filesystem in the location specified by pathPtr.

REMOVEDIRECTORYPROC

Function to process a Tcl_FSRemoveDirectory call. Should be implemented unless the FS is read-only.

typedef int Tcl_FSRemoveDirectoryProc(
        Tcl_Obj *pathPtr,
        int recursive,
        Tcl_Obj **errorPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, the directory specified by pathPtr should have been removed from the filesystem. If the recursive flag is given, then a non-empty directory should be deleted without error. If this flag is not given, then and the directory is non-empty a POSIX “EEXIST” error should be signaled. If an error does occur, the name of the file or directory which caused the error should be placed in errorPtr.

DELETEFILEPROC

Function to process a Tcl_FSDeleteFile call. Should be implemented unless the FS is read-only.

typedef int Tcl_FSDeleteFileProc(
        Tcl_Obj *pathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, the file specified by pathPtr should have been removed from the filesystem. Note that, if the filesystem supports symbolic links, Tcl will always call this function and not Tcl_FSRemoveDirectoryProc when needed to delete them (even if they are symbolic links to directories).

FILESYSTEM EFFICIENCY

These functions need not be implemented for a particular filesystem because the core has a fallback implementation available. See each individual description for the consequences of leaving the field NULL.

LSTATPROC

Function to process a Tcl_FSLstat call. If not implemented, Tcl will attempt to use the statProc defined above instead. Therefore it need only be implemented if a filesystem can differentiate between stat and lstat calls.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

The behavior of this function is very similar to that of the Tcl_FSStatProc defined above, except that if it is applied to a symbolic link, it returns information about the link, not about the target file.

COPYFILEPROC

Function to process a Tcl_FSCopyFile call. If not implemented Tcl will fall back on open-r, open-w and fcopy as a copying mechanism. Therefore it need only be implemented if the filesystem can perform that action more efficiently.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the copying process. Note that, destPathPtr is the name of the file which should become the copy of srcPathPtr. It is never the name of a directory into which srcPathPtr could be copied (i.e. the function is much simpler than the Tcl level file copy subcommand). Note that, if the filesystem supports symbolic links, Tcl will always call this function and not copyDirectoryProc when needed to copy them (even if they are symbolic links to directories). Finally, if the filesystem determines it cannot support the file copy action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

RENAMEFILEPROC

Function to process a Tcl_FSRenameFile call. If not implemented, Tcl will fall back on a copy and delete mechanism. Therefore it need only be implemented if the filesystem can perform that action more efficiently.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the renaming process. If the filesystem determines it cannot support the file rename action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

COPYDIRECTORYPROC

Function to process a Tcl_FSCopyDirectory call. If not implemented, Tcl will fall back on a recursive file mkdir, file copy mechanism. Therefore it need only be implemented if the filesystem can perform that action more efficiently.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

The return value is a standard Tcl result indicating whether an error occurred in the copying process. If an error does occur, the name of the file or directory which caused the error should be placed in errorPtr. Note that, destPathPtr is the name of the directory-name which should become the mirror-image of srcPathPtr. It is not the name of a directory into which srcPathPtr should be copied (i.e. the function is much simpler than the Tcl level file copy subcommand). Finally, if the filesystem determines it cannot support the directory copy action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

LOADFILEPROC

Function to process a Tcl_FSLoadFile call. If not implemented, Tcl will fall back on a copy to native-temp followed by a Tcl_FSLoadFile on that temporary copy. Therefore it need only be implemented if the filesystem can load code directly, or it can be implemented simply to return TCL_ERROR to disable load functionality in this filesystem entirely.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Returns a standard Tcl completion code. If an error occurs, an error message is left in the interp's result. The function dynamically loads a binary code file into memory. On a successful load, the handlePtr should be filled with a token for the dynamically loaded file, and the unloadProcPtr should be filled in with the address of a procedure. The unload procedure will be called with the given Tcl_LoadHandle as its only parameter when Tcl needs to unload the file. For example, for the native filesystem, the Tcl_LoadHandle returned is currently a token which can be used in the private TclpFindSymbol to access functions in the new code. Each filesystem is free to define the Tcl_LoadHandle as it requires. Finally, if the filesystem determines it cannot support the file load action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

UNLOADFILEPROC

Function to unload a previously successfully loaded file. If load was implemented, then this should also be implemented, if there is any cleanup action required.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

Function to process a Tcl_FSGetCwd call. Most filesystems need not implement this. It will usually only be called once, if getcwd is called before chdir. May be NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

If the filesystem supports a native notion of a current working directory (which might perhaps change independent of Tcl), this function should return that cwd as the result, or NULL if the current directory could not be determined (e.g. the user does not have appropriate permissions on the cwd directory). If NULL is returned, an error message is left in the interp's result.

CHDIRPROC

Function to process a Tcl_FSChdir call. If filesystems do not implement this, it will be emulated by a series of directory access checks. Otherwise, virtual filesystems which do implement it need only respond with a positive return result if the pathPtr is a valid, accessible directory in their filesystem. They need not remember the result, since that will be automatically remembered for use by Tcl_FSGetCwd. Real filesystems should carry out the correct action (i.e. call the correct system chdir API).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

The Tcl_FSChdirProc changes the applications current working directory to the value specified in pathPtr. The function returns -1 on error or 0 on success.
