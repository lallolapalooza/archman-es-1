ARGUMENTOS

const Tcl_ChannelType *typePtr (in)
Se refiere a una estructura que contiene los puntos de procedimiento que se pueden invocar para realizar operaciones de entrada y salida en el canal.
const char *channelName (in)
El nombre del canal, como file3; no debe estar en uso por ningún otro canal. Puede ser NULL, en cuyo caso el canal se crea sin nombre. Si el canal creado se asigna a uno de los canales estándar (stdin, stdout o stderr), el nombre asignado será el nombre del canal estándar.
ClientData instanceData (in)
Valor arbitrario de un byte para asociar con este canal. Este valor se pasa a las funciones de los procedimientos en typePtr cuando se invocan.
int mask (in)
Una combinación OR de TCL_READABLE y TCL_WRITABLE que indique si el canal es lectible y escribible.
Tcl_Channel channel (in)
El canal a operar en.
int direction (in)
TCL_READABLE significa que se quiere el handle de entrada; TCL_WRITABLE significa que se quiere el handle de salida.
ClientData *handlePtr (out)
El punto de ubicación donde se debe almacenar el handle deseado del sistema operativo.
int size (in)
La cantidad, en bytes, de búfferos a asignar en este canal.
int mask (in)
Una combinación OR de TCL_READABLE, TCL_WRITABLE y TCL_EXCEPTION que indica los eventos que han ocurrido en este canal.
Tcl_Interp *interp (in)
Interprete actual. (Puede ser NULL)
const char *optionName (in)
Nombre del opción no válida.
const char *optionList (in)
Lista de opciones específicas (palabras separadas por espacios, sin el símbolo -), que se añaden a la lista de opciones estándar. Puede ser NULL para un mensaje de error estándar.

DESCRIPCIÓN

Tcl utiliza una arquitectura de canales de dos capas. Proporciona una capa superior genérica para que los programas C y Tcl puedan realizar entrada y salida usando los mismos APIs para diversos archivos, dispositivos, sockets etc. Las APIs de C genéricas se describen en el manual de entrada Tcl_OpenFileChannel.

La capa inferior proporciona drivers de canal específicos para cada tipo de dispositivo que se soporta en cada plataforma. Este manual describe las APIs C que se comunican entre la capa genérica y los drivers de canal específicos. También explica cómo se pueden agregar nuevos tipos de canales proporcionando nuevos drivers de canal.

Los drivers de canal consisten en varios componentes: Primero, cada driver de canal proporciona un Tcl_ChannelType estructura que contiene punteros a funciones implementadas para realizar las diversas operaciones utilizadas por la capa genérica para comunicarse con el driver de canal. La estructura Tcl_ChannelType y las funciones referenciadas por ella se describen en el apartado TCL_CHANNELTYPE.

Segundo, los drivers de canal suelen proporcionar un comando Tcl para crear instancias de ese tipo de canal. Por ejemplo, el comando Tcl open crea canales que usan los drivers de canal de archivo y comandos, y el comando Tcl socket crea canales que usan sockets TCP para comunicación de red.

Tercero, un driver de canal opcionalmente proporciona una función C para abrir instancias de ese tipo de canal. Por ejemplo, Tcl_OpenFileChannel abre un canal que usa el driver de canal de archivo, y Tcl_OpenTcpClient abre un canal que usa el protocolo TCP de red. Estas funciones de creación generalmente utilizan Tcl_CreateChannel internamente para abrir el canal.

Para agregar un nuevo tipo de canal, debe implementar una API C o un comando Tcl que abra un canal invocando Tcl_CreateChannel. Cuando su driver llama a Tcl_CreateChannel, pasa un Tcl_ChannelType estructura que describa las procedimientos de I/O de su driver. La capa genérica luego invocará las funciones referenciadas en esa estructura para realizar operaciones en el canal.

Tcl_CreateChannel abre un nuevo canal y asociia el typePtr y instanceData con él. El canal se abre en el modo indicado por mask. Para una discusión sobre los drivers de canal, sus operaciones y la estructura Tcl_ChannelType, véase el apartado TCL_CHANNELTYPE.

Tcl_CreateChannel interactúa con el código que gestiona los canales estándar. Una vez que un canal estándar fue inicializado mediante una llamada a Tcl_GetStdChannel o una llamada a Tcl_SetStdChannel, el cierre de este canal provocará que el próximo llamado a Tcl_CreateChannel lo convierta en el nuevo canal estándar. Consulte Tcl_StandardChannels para una trama general sobre canales estándar y el comportamiento de la biblioteca Tcl con respecto a ellos.

Tcl_GetChannelInstanceData devuelve el datos de instancia asociados al canal en channel. Esto es el mismo que el argumento instanceData en la llamada a Tcl_CreateChannel que creó este canal.

Tcl_GetChannelType devuelve un puntero a la estructura Tcl_ChannelType utilizada por el canal en el argumento channel. Esto es el mismo que el argumento typePtr en la llamada a Tcl_CreateChannel que creó este canal.

Tcl_GetChannelName devuelve una cadena con el nombre asociado al canal, o NULL si el argumento channelName de Tcl_CreateChannel era NULL.

Tcl_GetChannelHandle coloca el handle del dispositivo operativo asociado a channel para el dado direction en el handlePtr.

TCL_CHANNELTYPE

Un controlador de canal proporciona una estructura Tcl_ChannelType que contiene punteros a funciones que implementan las diversas operaciones en un canal; estas operaciones son invocadas según sea necesario por la capa genérica. La estructura fue versionada desde Tcl 8.3.2/8.4 para corregir un problema en los controladores de canal congelados. Consulte la sección OLD CHANNEL TYPES para más detalles sobre la antigua estructura.

La estructura Tcl_ChannelType contiene los siguientes campos:

typedef struct Tcl_ChannelType {
        const char *typeName;
        Tcl_ChannelTypeVersion version;
        Tcl_DriverCloseProc *closeProc;
        Tcl_DriverInputProc *inputProc;
        Tcl_DriverOutputProc *outputProc;
        Tcl_DriverSeekProc *seekProc;
        Tcl_DriverSetOptionProc *setOptionProc;
        Tcl_DriverGetOptionProc *getOptionProc;
        Tcl_DriverWatchProc *watchProc;
        Tcl_DriverGetHandleProc *getHandleProc;
        Tcl_DriverClose2Proc *close2Proc;
        Tcl_DriverBlockModeProc *blockModeProc;
        Tcl_DriverFlushProc *flushProc;
        Tcl_DriverHandlerProc *handlerProc;
        Tcl_DriverWideSeekProc *wideSeekProc;
        Tcl_DriverThreadActionProc *threadActionProc;
        Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

No es necesario proporcionar implementaciones para todas las operaciones del canal. Las que no sean necesarias pueden establecerse a NULL en la estructura: blockModeProc, seekProc, setOptionProc, getOptionProc, getHandleProc y close2Proc, además de flushProc, handlerProc, threadActionProc y truncateProc. Las funciones que no se puedan implementar de forma significativa deben devolver EINVAL cuando se llamen, indicando que las operaciones representadas no están disponibles. También se debe tener en cuenta que wideSeekProc puede ser NULL si seekProc lo es.

El usuario debe utilizar la estructura anterior solo para la instanciación de Tcl_ChannelType. Cuando se refieran a campos de una estructura Tcl_ChannelType, se deben utilizar las siguientes funciones para obtener los valores: Tcl_ChannelName, Tcl_ChannelVersion, Tcl_ChannelBlockModeProc, Tcl_ChannelCloseProc, Tcl_ChannelClose2Proc, Tcl_ChannelInputProc, Tcl_ChannelOutputProc, Tcl_ChannelSeekProc, Tcl_ChannelWideSeekProc, Tcl_ChannelThreadActionProc, Tcl_ChannelTruncateProc, Tcl_ChannelSetOptionProc, Tcl_ChannelGetOptionProc, Tcl_ChannelWatchProc, Tcl_ChannelGetHandleProc, Tcl_ChannelFlushProc o Tcl_ChannelHandlerProc.

El cambio en las estructuras se realizó de tal manera que los tipos de canal estándar sean binariamente compatibles. Sin embargo, los tipos de canal que utilizan canales congelados (es decir, TLS, Trf) tienen nuevas versiones para corresponder con el cambio anterior, ya que el código anterior para canales congelados tenía problemas.

TYPENAME

El campo typeName contiene una cadena terminada en NULL que identifica el tipo de dispositivo implementado por este controlador, por ejemplo, file o socket.

Este valor puede obtenerse con Tcl_ChannelName, que devuelve un puntero a la cadena.

VERSION

El campo version debe establecerse a la versión de la estructura que requiere. TCL_CHANNEL_VERSION_2 es la mínima recomendada. TCL_CHANNEL_VERSION_3 debe establecerse para especificar el miembro wideSeekProc. TCL_CHANNEL_VERSION_4 debe establecerse para especificar el miembro threadActionProc (incluye wideSeekProc). TCL_CHANNEL_VERSION_5 debe establecerse para especificar los miembros truncateProc (incluye wideSeekProc y threadActionProc). Si no se establece a ninguno de estos, se asume que el Tcl_ChannelType tiene la estructura original. Consulte OLD CHANNEL TYPES para más detalles. Aunque Tcl reconocerá y funcionará con cualquiera de estas estructuras, los canales congelados deben ser de al menos TCL_CHANNEL_VERSION_2 para funcionar correctamente.

Este valor puede obtenerse con Tcl_ChannelVersion, que devuelve uno de TCL_CHANNEL_VERSION_5, TCL_CHANNEL_VERSION_4, TCL_CHANNEL_VERSION_3, TCL_CHANNEL_VERSION_2 o TCL_CHANNEL_VERSION_1.

BLOCKMODEPROC

El campo blockModeProc contiene la dirección de una función llamada por la capa genérica para establecer el modo bloqueante y no bloqueante del dispositivo. blockModeProc debe corresponder al siguiente prototipo:

typedef int Tcl_DriverBlockModeProc(
        ClientData instanceData,
        int mode);

El instanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando este canal fue creado. El argumento mode es either TCL_MODE_BLOCKING o TCL_MODE_NONBLOCKING para establecer el dispositivo en modo bloqueante o no bloqueante. La función debe devolver cero si la operación fue exitosa, o un código de error POSIX no cero si la operación falló.

Si la operación es exitosa, la función puede modificar el instanceData proporcionado para registrar que el canal entró en modo bloqueante o no bloqueante y implementar el comportamiento bloqueante o no bloqueante. Para algunos tipos de dispositivo, el comportamiento bloqueante y no bloqueante puede ser implementado por el sistema operativo subyacente; para otros tipos de dispositivo, el comportamiento debe emularse en el controlador de canal.

Este valor puede obtenerse con Tcl_ChannelBlockModeProc, que devuelve un puntero a la función.

Un controlador de canal que no proporcione un blockModeProc debe ser muy cuidadoso. Debe decirle a la capa genérica exactamente qué modo bloqueante es aceptable para él, y debería documentar esto para el usuario de manera que el modo bloqueante del canal no se cambie a un valor inaceptable. Cualquier confusión aquí podría llevar a un (espurio y difícil de encontrar) bloqueo del intérprete.

CLOSEPROC AND CLOSE2PROC

El campo closeProc contiene la dirección de una función llamada por la capa genérica para limpiar la información relacionada con el controlador cuando el canal es cerrado. closeProc debe corresponder al siguiente prototipo:

typedef int Tcl_DriverCloseProc(
        ClientData instanceData,
        Tcl_Interp *interp);

El argumento instanceData es el mismo que el valor proporcionado a Tcl_CreateChannel cuando el canal fue creado. La función debe liberar cualquier almacenamiento mantenido por el controlador de canal para este canal, y cerrar los dispositivos de entrada y salida encapsulados por este canal. Antes de llamar a esta función, cualquier salida acumulada se habrá limpiado en el dispositivo. No se invocarán más operaciones del controlador después de llamar a closeProc. Si la operación de cierre es exitosa, el procedimiento

debería devolver cero; de lo contrario, debería devolver un código de error POSIX distinto de cero. Además, si ocurre un error y interp no es NULL, el procedimiento debería almacenar un mensaje de error en el resultado del intérprete.

Alternativamente, los canales que admiten el cierre de los lados de lectura y escritura de forma independiente pueden establecer closeProc en TCL_CLOSE2PROC y establecer close2Proc en la dirección de una función que coincida con el siguiente prototipo:

typedef int Tcl_DriverClose2Proc(
        ClientData instanceData,
        Tcl_Interp *interp,
        int flags);

Se llamará a close2Proc con flags establecido en una combinación OR'ed de TCL_CLOSE_READ o TCL_CLOSE_WRITE para indicar que el controlador del canal debe cerrar el lado de lectura y/o escritura del canal. Se puede invocar al controlador del canal para realizar operaciones adicionales en el canal después de que se llame a close2Proc para cerrar uno o ambos lados del canal. Si flags es 0 (cero), el controlador debe cerrar el canal de la manera descrita anteriormente para closeProc. No se invocarán más operaciones en esta instancia después de que se llame a close2Proc con todas las banderas despejadas. En todos los casos, la función close2Proc debería devolver cero si la operación de cierre fue exitosa; de lo contrario, debería devolver un código de error POSIX distinto de cero. Además, si ocurre un error y interp no es NULL, el procedimiento debería almacenar un mensaje de error en el resultado del intérprete.

Los valores closeProc y close2Proc se pueden recuperar con Tcl_ChannelCloseProc o Tcl_ChannelClose2Proc, que devuelven un puntero a la función respectiva.

INPUTPROC

El campo inputProc contiene la dirección de una función llamada por la capa genérica para leer datos del archivo o dispositivo y almacenarlos en un búfer interno. InputProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverInputProc(
        ClientData instanceData,
        char *buf,
        int bufSize,
        int *errorCodePtr);

InstanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando se creó el canal. El argumento buf apunta a una matriz de bytes en la que se almacenará la entrada del dispositivo, y el argumento bufSize indica cuántos bytes están disponibles en buf.

El argumento errorCodePtr apunta a una variable entera proporcionada por la capa genérica. Si ocurre un error, la función debería establecer la variable a un código de error POSIX que identifique el error que ocurrió.

La función debe leer datos del dispositivo de entrada encapsulado por el canal y almacenarlos en buf. En caso de éxito, la función debe devolver un entero no negativo que indique cuántos bytes se leyeron del dispositivo de entrada y se almacenaron en buf. En caso de error, la función debe devolver -1. Si ocurre un error después de que se hayan leído algunos datos del dispositivo, esos datos se pierden.

Si inputProc puede determinar que el dispositivo de entrada tiene algunos datos disponibles pero menos de los solicitados por el argumento bufSize, la función solo debe intentar leer tantos datos como estén disponibles y devolver sin bloquear. Si el dispositivo de entrada no tiene datos disponibles en absoluto y el canal está en modo no bloqueante, la función debe devolver un error EAGAIN. Si el dispositivo de entrada no tiene datos disponibles en absoluto y el canal está en modo bloqueante, la función debe bloquearse durante el menor tiempo posible hasta que se pueda leer al menos un byte de datos del dispositivo; luego, debe devolver tantos datos como pueda leer sin bloquear.

Este valor se puede recuperar con Tcl_ChannelInputProc, que devuelve un puntero a la función.

OUTPUTPROC

El campo outputProc contiene la dirección de una función llamada por la capa genérica para transferir datos de un búfer interno al dispositivo de salida. OutputProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverOutputProc(
        ClientData instanceData,
        const char *buf,
        int toWrite,
        int *errorCodePtr);

InstanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando se creó el canal. El argumento buf contiene una matriz de bytes que se escribirán en el dispositivo, y el argumento toWrite indica cuántos bytes se escribirán desde el argumento buf.

El argumento errorCodePtr apunta a una variable entera proporcionada por la capa genérica. Si ocurre un error, la función debe establecer esta variable a un código de error POSIX que identifique el error.

La función debe escribir los datos en buf en el dispositivo de salida encapsulado por el canal. En caso de éxito, la función debe devolver un entero no negativo que indique cuántos bytes se escribieron en el dispositivo de salida. El valor de retorno es normalmente el mismo que toWrite, pero puede ser menor en algunos casos, como si la operación de salida se interrumpe por una señal. Si ocurre un error, la función debe devolver -1. En caso de error, es posible que se hayan escrito algunos datos en el dispositivo.

Si el canal no está bloqueante y el dispositivo de salida no puede absorber datos alguno, la función debe devolver -1 con un error EAGAIN sin escribir ningún dato.

Este valor se puede recuperar con Tcl_ChannelOutputProc, que devuelve un puntero a la función.

SEEKPROC Y WIDESEEKPROC

El campo seekProc contiene la dirección de una función llamada por la capa genérica para mover el punto de acceso en el que se aplicarán las operaciones posteriores de entrada o salida. SeekProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverSeekProc(
        ClientData instanceData,
        long offset,
        int seekMode,
        int *errorCodePtr);

El argumento instanceData es el mismo que el valor dado a Tcl_CreateChannel cuando se creó este canal. Offset y seekMode tienen el mismo significado que para el procedimiento Tcl_Seek (descrito en la entrada del manual para Tcl_OpenFileChannel).

El argumento errorCodePtr apunta a una variable entera proporcionada por la capa genérica para devolver los valores errno de la función. La función debe establecer esta variable en un código de error POSIX si ocurre un error. La función debe almacenar un código de error EINVAL si el tipo de canal no implementa la búsqueda.

El valor de retorno es el nuevo punto de acceso o -1 en caso de error. Si ocurrió un error, la función no debe mover el punto de acceso.

Si hay un campo seekProc no NULL, el campo wideSeekProc puede contener la dirección de una función alternativa a utilizar que maneja desplazamientos amplios (es decir, mayores de 32 bits), permitiendo así búsquedas dentro de archivos de más de 2 GB. Se llamará a wideSeekProc con preferencia a seekProc, pero ambos deben definirse si se define wideSeekProc. WideSeekProc debe coincidir con el siguiente prototipo:

typedef Tcl_WideInt Tcl_DriverWideSeekProc(
        ClientData instanceData,
        Tcl_WideInt offset,
        int seekMode,
        int *errorCodePtr);

Los argumentos y valores de retorno significan lo mismo que con seekProc anteriormente, excepto que el tipo de desplazamientos y el tipo de retorno son diferentes.

El valor seekProc se puede recuperar con Tcl_ChannelSeekProc, que devuelve un puntero a la función, y de manera similar, wideSeekProc se puede recuperar con Tcl_ChannelWideSeekProc.

SETOPTIONPROC

El campo setOptionProc contiene la dirección de una función llamada por la capa genérica para establecer una opción específica del tipo de canal en un canal. setOptionProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverSetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        const char *newValue);

optionName es el nombre de una opción a establecer, y newValue es el nuevo valor para esa opción, como una cadena. El instanceData es el mismo que el valor dado a Tcl_CreateChannel cuando se creó este canal. La función debe realizar cualquier acción específica del tipo de canal que sea necesaria para implementar el nuevo valor de la opción.

Algunas opciones son manejadas por el código genérico y esta función nunca es llamada para establecerlas, por ejemplo, -blockmode. Otras opciones son específicas de cada tipo de canal y se llamará al procedimiento setOptionProc del controlador del canal para implementarlas. El campo setOptionProc puede ser NULL, lo que indica que este tipo de canal no admite opciones específicas del tipo.

Si el valor de la opción se modifica exitosamente al nuevo valor, la función devuelve TCL_OK. Debe llamar a Tcl_BadChannelOption que a su vez devuelve TCL_ERROR si el optionName no se reconoce. Si newValue especifica un valor para la opción que no es compatible o si ocurre un error de llamada al sistema, la función debe dejar un mensaje de error en el resultado de interp si interp no es NULL. La función también debe llamar a Tcl_SetErrno para almacenar un código de error POSIX apropiado.

Este valor se puede recuperar con Tcl_ChannelSetOptionProc, que devuelve un puntero a la función.

GETOPTIONPROC

El campo getOptionProc contiene la dirección de una función llamada por la capa genérica para obtener el valor de una opción específica del tipo de canal en un canal. getOptionProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverGetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        Tcl_DString *optionValue);

OptionName es el nombre de una opción admitida por este tipo de canal. Si el nombre de la opción no es NULL, la función almacena su valor actual, como una cadena, en la cadena dinámica de Tcl optionValue. Si optionName es NULL, la función almacena en optionValue una lista alternada de todas las opciones admitidas y sus valores actuales. En caso de éxito, la función devuelve TCL_OK. NAME

Tcl_DriverSetOptionProc, Tcl_DriverGetOptionProc, Tcl_DriverWatchProc, Tcl_DriverGetHandleProc, Tcl_DriverFlushProc, Tcl_DriverHandlerProc, Tcl_DriverThreadActionProc, Tcl_DriverTruncateProc - channel driver procedures

SYNOPSIS

#include <tcl.h>

typedef int Tcl_DriverSetOptionProc(
ClientData instanceData,
const char *optionName,
Tcl_Interp *interp);
typedef int Tcl_DriverGetOptionProc(
ClientData instanceData,
Tcl_Interp *interp);
typedef void Tcl_DriverWatchProc(
ClientData instanceData,
int mask);
typedef int Tcl_DriverGetHandleProc(
ClientData instanceData,
int direction,
ClientData *handlePtr);
typedef int Tcl_DriverFlushProc(
ClientData instanceData);
typedef int Tcl_DriverHandlerProc(
ClientData instanceData,
int interestMask);
typedef void Tcl_DriverThreadActionProc(
ClientData instanceData,
int action);
typedef int Tcl_DriverTruncateProc(
ClientData instanceData,
Tcl_WideInt length);

DESCRIPTION

Tcl channel drivers are responsible for implementing channel primitives. The Tcl channel API relies on the channel drivers to perform channel operations such as reading, writing, flushing, watching for events, getting the underlying device handle, etc. The structure Tcl_ChannelType is used to register a channel driver with the Tcl runtime. The fields of this structure are pointers to procedures that the generic channel code will call to perform operations on the channel.

SETOPTIONPROC

The setOptionProc field contains the address of a procedure that is called by the generic layer to set an option on the channel. SetOptionProc should match the following prototype:

typedef int Tcl_DriverSetOptionProc(
        ClientData instanceData,
        const char *optionName,
        Tcl_Interp *interp);

InstanceData is the same as the value passed to Tcl_CreateChannel when this channel was created. The optionName is the name of the option to set, and interp is the interpreter in which the channel was created. If the option is not supported, the procedure should return TCL_ERROR after setting an error message in interp. Otherwise, it should return TCL_OK.

This value can be retrieved with Tcl_ChannelSetOptionProc, which returns a pointer to the function.

GETOPTIONPROC

The getOptionProc field contains the address of a procedure that is called by the generic layer to get the value of an option for the channel. GetOptionProc should match the following prototype:

typedef int Tcl_DriverGetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp);

InstanceData is the same as the value passed to Tcl_CreateChannel when this channel was created. The procedure should set the value of the option in interp's result and return TCL_OK. If an option name is unrecognized, the procedure should set an error message in interp and return TCL_ERROR.

If a system call error occurs, the function should leave an error message in the result of interp if interp is not NULL. The function should also call Tcl_SetErrno to store an appropriate POSIX error code.

Some options are handled by the generic code and this function is never called to retrieve their value, e.g. -blockmode. Other options are specific to each channel type and the getOptionProc procedure of the channel driver will get called to implement them. The getOptionProc field can be NULL, which indicates that this channel type supports no type specific options.

This value can be retrieved with Tcl_ChannelGetOptionProc, which returns a pointer to the function.

WATCHPROC

The watchProc field contains the address of a function called by the generic layer to initialize the event notification mechanism to notice events of interest on this channel. WatchProc should match the following prototype:

typedef void Tcl_DriverWatchProc(
        ClientData instanceData,
        int mask);

The instanceData is the same as the value passed to Tcl_CreateChannel when this channel was created. The mask argument is an OR-ed combination of TCL_READABLE, TCL_WRITABLE and TCL_EXCEPTION; it indicates events the caller is interested in noticing on this channel.

The function should initialize device type specific mechanisms to notice when an event of interest is present on the channel. When one or more of the designated events occurs on the channel, the channel driver is responsible for calling Tcl_NotifyChannel to inform the generic channel module. The driver should take care not to starve other channel drivers or sources of callbacks by invoking Tcl_NotifyChannel too frequently. Fairness can be insured by using the Tcl event queue to allow the channel event to be scheduled in sequence with other events. See the description of Tcl_QueueEvent for details on how to queue an event.

This value can be retrieved with Tcl_ChannelWatchProc, which returns a pointer to the function.

GETHANDLEPROC

The getHandleProc field contains the address of a function called by the generic layer to retrieve a device-specific handle from the channel. GetHandleProc should match the following prototype:

typedef int Tcl_DriverGetHandleProc(
        ClientData instanceData,
        int direction,
        ClientData *handlePtr);

InstanceData is the same as the value passed to Tcl_CreateChannel when this channel was created. The direction argument is either TCL_READABLE to retrieve the handle used for input, or TCL_WRITABLE to retrieve the handle used for output.

If the channel implementation has device-specific handles, the function should retrieve the appropriate handle associated with the channel, according the direction argument. The handle should be stored in the location referred to by handlePtr, and TCL_OK should be returned. If the channel is not open for the specified direction, or if the channel implementation does not use device handles, the function should return TCL_ERROR.

This value can be retrieved with Tcl_ChannelGetHandleProc, which returns a pointer to the function.

FLUSHPROC

The flushProc field is currently reserved for future use. It should be set to NULL. FlushProc should match the following prototype:

typedef int Tcl_DriverFlushProc(
        ClientData instanceData);

This value can be retrieved with Tcl_ChannelFlushProc, which returns a pointer to the function.

HANDLERPROC

The handlerProc field contains the address of a function called by the generic layer to notify the channel that an event occurred. It should be defined for stacked channel drivers that wish to be notified of events that occur on the underlying (stacked) channel. HandlerProc should match the following prototype:

typedef int Tcl_DriverHandlerProc(
        ClientData instanceData,
        int interestMask);

InstanceData is the same as the value passed to Tcl_CreateChannel when this channel was created. The interestMask is an OR-ed combination of TCL_READABLE or TCL_WRITABLE; it indicates what type of event occurred on this channel.

This value can be retrieved with Tcl_ChannelHandlerProc, which returns a pointer to the function.

THREADACTIONPROC

The threadActionProc field contains the address of the function called by the generic layer when a channel is created, closed, or going to move to a different thread, i.e. whenever thread-specific driver state might have to initialized or updated. It can be NULL. The action TCL_CHANNEL_THREAD_REMOVE is used to notify the driver that it should update or remove any thread-specific data it might be maintaining for the channel.

The action TCL_CHANNEL_THREAD_INSERT is used to notify the driver that it should update or initialize any thread-specific data it might be maintaining using the calling thread as the associate. See Tcl_CutChannel and Tcl_SpliceChannel for more detail.

typedef void Tcl_DriverThreadActionProc(
        ClientData instanceData,
        int action);

InstanceData is the same as the value passed to Tcl_CreateChannel when this channel was created.

These values can be retrieved with Tcl_ChannelThreadActionProc, which returns a pointer to the function.

TRUNCATEPROC

The truncateProc field contains the address of the function called by the generic layer when a channel is truncated to some length. It can be NULL.

typedef int Tcl_DriverTruncateProc(
        ClientData instanceData,
        Tcl_WideInt length);

InstanceData is the same as the value passed to Tcl_CreateChannel when this channel was created, and length is the new length of the underlying file, which should not be negative. The result should be 0 on success or an errno code (suitable for use with Tcl_SetErrno) on failure.

These values can be retrieved with Tcl_ChannelTruncateProc, which returns a pointer to the function.

TCL_BADCHANNELOPTION

This procedure generates a “bad option” error message in an (optional) interpreter. It is used by channel drivers when an invalid Set/Get option is requested. Its purpose is to concatenate the generic options list to the specific ones and factorize the generic options error message string.

It always returns TCL_ERROR

An error message is generated in interp's result value to indicate that a command was invoked with a bad option. The message has the form

    bad option "blah": should be one of
    <...generic options...>+<...specific options...>
so you get for instance: 
    bad option "-blah": should be one of -blocking,
    -buffering, -buffersize, -eofchar, -translation,
    -peername, or -sockname
when called with optionList equal to “peername sockname”

“blah” is the optionName argument and “<specific options>” is a space separated list of specific option words. The function takes good care of inserting minus signs before each option, commas after, and an “or” before the last option.

OLD CHANNEL TYPES

The original (8.3.1 and below) Tcl_ChannelType structure contains the following fields:

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
} Tcl_ChannelType;

It is still possible to create channel with the above structure. The internal channel code will determine the version. It is imperative to use the new Tcl_ChannelType structure if you are creating a stacked channel driver, due to problems with the earlier stacked channel implementation (in 8.2.0 to 8.3.1).

Prior to 8.4.0 (i.e. during the later releases of 8.3 and early part of the 8.4 development cycle) the Tcl_ChannelType structure contained the following fields:

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_ChannelTypeVersion version;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverFlushProc *flushProc;
    Tcl_DriverHandlerProc *handlerProc;
    Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

When the above structure is registered as a channel type, the version field should always be TCL_CHANNEL_VERSION_2.

NAME

Tcl_ChannelWatchProc - channel event handler registration

SYNOPSIS

#include <tcl.h>

typedef void Tcl_ChannelWatchProc(
    ClientData clientData,
    int mask);

ARGUMENTS

ClientData clientData
The value passed as the clientData argument when the channel was created (or last modified with Tcl_WatchChannel).
int mask
A bitmask indicating which events are ready. This mask will have bits set for TCL_READABLE, TCL_WRITABLE, and/or TCL_EXCEPTION.

DESCRIPTION

Tcl_ChannelWatchProc is the type of the procedure that is called by Tcl whenever a channel for which an event handler has been registered becomes ready for I/O. The handler is registered using Tcl_WatchChannel.

TCL_CHANNELTYPE

The Tcl_ChannelType structure used to register a channel type contains a watchProc field. This field points to a procedure of type Tcl_ChannelWatchProc. This procedure is called by Tcl whenever the channel becomes ready for I/O.

TCL_BADCHANNELOPTION

The watchProc is called by Tcl with TCL_READABLE, TCL_WRITABLE, and/or TCL_EXCEPTION set in the mask. The watchProc should examine the mask and call the appropriate procedure to handle the event. For example, if the TCL_READABLE bit is set, the watchProc might call Tcl_Read to read data from the channel.

OLD CHANNEL TYPES

In older versions of Tcl, the watchProc was used to register the channel with the Tcl event loop. This is now handled by Tcl_WatchChannel.
