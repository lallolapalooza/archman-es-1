ARGUMENTOS

const Tcl_ChannelType *typePtr (entrada)
Punta a una estructura que contiene las direcciones de los procedimientos que se pueden llamar para realizar E/S y otras funciones en el canal.
const char *channelName (entrada)
El nombre de este canal, como file3; no debe estar en uso por ningún otro canal. Puede ser NULL, en cuyo caso el canal se crea sin nombre. Si el canal creado se asigna a uno de los canales estándar (stdin, stdout o stderr), el nombre del canal asignado será el nombre del canal estándar.
ClientData instanceData (entrada)
Valor arbitrario de una palabra para asociar con este canal. Este valor se pasa a los procedimientos en typePtr cuando se invocan.
int mask (entrada)
Combinación OR de TCL_READABLE y TCL_WRITABLE para indicar si un canal es legible y escribible.
Tcl_Channel channel (entrada)
El canal a operar.
int direction (entrada)
TCL_READABLE significa que se desea el manejador de entrada; TCL_WRITABLE significa que se desea el manejador de salida.
ClientData *handlePtr (salida)
Punta a la ubicación donde se debe almacenar el manejador específico del sistema operativo.
int size (entrada)
El tamaño, en bytes, de los búferes a asignar en este canal.
int mask (entrada)
Una combinación OR de TCL_READABLE, TCL_WRITABLE y TCL_EXCEPTION que indica los eventos que han ocurrido en este canal.
Tcl_Interp *interp (entrada)
Intérprete actual. (puede ser NULL)
const char *optionName (entrada)
Nombre de la opción inválida.
const char *optionList (entrada)
Lista de opciones específicas (palabras separadas por espacios, sin “-”) para añadir a la lista de opciones genéricas estándar. Puede ser NULL solo para el mensaje de error de opciones genéricas.

DESCRIPCIÓN

Tcl utiliza una arquitectura de canales de dos capas. Proporciona una capa superior genérica para permitir que los programas C y Tcl realicen entradas y salidas utilizando las mismas API para una variedad de archivos, dispositivos, sockets, etc. Las API C genéricas se describen en la entrada del manual para Tcl_OpenFileChannel.

La capa inferior proporciona controladores de canales específicos de tipo para cada tipo de dispositivo soportado en cada plataforma. Esta entrada del manual describe las API C utilizadas para comunicarse entre la capa genérica y los controladores de canales específicos de tipo. También explica cómo se pueden añadir nuevos tipos de canales proporcionando nuevos controladores de canales.

Los controladores de canales consisten en varios componentes: Primero, cada controlador de canales proporciona una estructura Tcl_ChannelType que contiene punteros a funciones que implementan las diversas operaciones utilizadas por la capa genérica para comunicarse con el controlador de canales. La estructura Tcl_ChannelType y las funciones a las que hace referencia se describen en la sección TCL_CHANNELTYPE, más abajo.

Segundo, los controladores de canales suelen proporcionar un comando Tcl para crear instancias de ese tipo de canal. Por ejemplo, el comando Tcl open crea canales que utilizan los controladores de canales de archivo y comando, y el comando Tcl socket crea canales que utilizan sockets TCP para la comunicación de red.

Tercero, un controlador de canales opcionalmente proporciona una función C para abrir instancias de canal de ese tipo. Por ejemplo, Tcl_OpenFileChannel abre un canal que utiliza el controlador de canales de archivo, y Tcl_OpenTcpClient abre un canal que utiliza el protocolo de red TCP. Estas funciones de creación suelen utilizar Tcl_CreateChannel internamente para abrir el canal.

Para añadir un nuevo tipo de canal, debe implementar una API C o un comando Tcl que abra un canal invocando Tcl_CreateChannel. Cuando su controlador llame a Tcl_CreateChannel, pasará una estructura Tcl_ChannelType que describe los procedimientos de E/S del controlador. La capa genérica invocará entonces las funciones referenciadas en esa estructura para realizar operaciones en el canal.

Tcl_CreateChannel abre un nuevo canal y asocia los typePtr y instanceData proporcionados con él. El canal se abre en el modo indicado por mask. Para una discusión de los controladores de canales, sus operaciones y la estructura Tcl_ChannelType, véase la sección TCL_CHANNELTYPE, más abajo.

Tcl_CreateChannel interactúa con el código que gestiona los canales estándar. Una vez que un canal estándar fue inicializado ya sea a través de una llamada a Tcl_GetStdChannel o una llamada a Tcl_SetStdChannel, el cierre de este canal estándar causará que la próxima llamada a Tcl_CreateChannel haga que el nuevo canal sea también el nuevo canal estándar. Vea Tcl_StandardChannels para un tratado general sobre los canales estándar y el comportamiento de la biblioteca Tcl con respecto a ellos.

Tcl_GetChannelInstanceData devuelve los datos de instancia asociados con el canal en channel. Esto es lo mismo que el argumento instanceData en la llamada a Tcl_CreateChannel que creó este canal.

Tcl_GetChannelType devuelve un puntero a la estructura Tcl_ChannelType utilizada por el canal en el argumento channel. Esto es lo mismo que el argumento typePtr en la llamada a Tcl_CreateChannel que creó este canal.

Tcl_GetChannelName devuelve una cadena que contiene el nombre asociado con el canal, o NULL si el argumento channelName de Tcl_CreateChannel era NULL.

Tcl_GetChannelHandle coloca el manejador de dispositivo específico del sistema operativo asociado con channel para la direction dada en la

ubicación especificada por handlePtr y devuelve TCL_OK. Si el canal no tiene un manejador de dispositivo para la dirección especificada, entonces se devuelve TCL_ERROR. Diferentes controladores de canal devolverán diferentes tipos de manejadores. Consulte las entradas del manual de cada controlador para determinar qué tipo de manejador se devuelve.

Tcl_GetChannelThread devuelve el identificador del hilo que está gestionando actualmente el canal especificado. Esto permite a los controladores de canal enviar sus eventos de archivo a la cola de eventos correcta incluso para un núcleo multihilo.

Tcl_GetChannelMode devuelve una combinación OR de TCL_READABLE y TCL_WRITABLE, indicando si el canal está abierto para entrada y salida.

Tcl_GetChannelBufferSize devuelve el tamaño, en bytes, de los búferes asignados para almacenar la entrada o salida en el canal. Si el valor no fue establecido por una llamada anterior a Tcl_SetChannelBufferSize, descrita a continuación, entonces se devuelve el valor predeterminado de 4096.

Tcl_SetChannelBufferSize establece el tamaño, en bytes, de los búferes que se asignarán en operaciones posteriores en el canal para almacenar la entrada o salida. El argumento size debe estar entre uno y un millón, permitiendo búferes de un byte a un millón de bytes. Si size está fuera de este rango, Tcl_SetChannelBufferSize establece el tamaño del búfer en 4096.

Tcl_NotifyChannel es llamado por un controlador de canal para indicar a la capa genérica que los eventos especificados por mask han ocurrido en el canal. Los controladores de canal son responsables de invocar esta función siempre que los manejadores de canal necesiten ser llamados para el canal (o se deban realizar otras tareas pendientes como un vaciado de escritura). Consulte WATCHPROC a continuación para más detalles.

Tcl_BadChannelOption es llamado desde el setOptionProc o getOptionProc específico del controlador para generar un mensaje de error completo.

Tcl_ChannelBuffered devuelve el número de bytes de entrada actualmente almacenados en el búfer interno (área de devolución) del propio canal. No informa sobre los datos en los búferes generales para la pila de canales de la que forma parte el canal suministrado.

Tcl_IsChannelShared verifica el contador de referencias del canal especificado y devuelve si el canal fue compartido entre múltiples intérpretes (resultado == 1) o no (resultado == 0).

Tcl_IsChannelRegistered verifica si el canal especificado está registrado en el intérprete dado (resultado == 1) o no (resultado == 0).

Tcl_IsChannelExisting verifica si un canal con el nombre especificado está registrado en la lista global (del hilo) de todos los canales (resultado == 1) o no (resultado == 0).

Tcl_CutChannel elimina el canal especificado de la lista global (del hilo) de todos los canales (del hilo actual). No se permite la aplicación a un canal que todavía esté registrado en algún intérprete. También notifica al controlador si la versión de Tcl_ChannelType es TCL_CHANNEL_VERSION_4 (o superior), y Tcl_DriverThreadActionProc está definida para él.

Tcl_SpliceChannel agrega el canal especificado a la lista global (del hilo) de todos los canales (del hilo actual). No se permite la aplicación a un canal registrado en algún intérprete. También notifica al controlador si la versión de Tcl_ChannelType es TCL_CHANNEL_VERSION_4 (o superior), y Tcl_DriverThreadActionProc está definida para él.

Tcl_ClearChannelHandlers elimina todos los manejadores de canal y scripts de eventos asociados con el canal especificado, interrumpiendo así todo el procesamiento de eventos para este canal.

TCL_CHANNELTYPE

Un controlador de canal proporciona una estructura Tcl_ChannelType que contiene punteros a funciones que implementan las diversas operaciones en un canal; estas operaciones se invocan según sea necesario por la capa genérica. La estructura se versionó a partir de Tcl 8.3.2/8.4 para corregir un problema con los controladores de canal apilados. Consulte la sección OLD CHANNEL TYPES a continuación para obtener detalles sobre la estructura antigua.

La estructura Tcl_ChannelType contiene los siguientes campos:

typedef struct Tcl_ChannelType {
        const char *typeName;
        Tcl_ChannelTypeVersion version;
        Tcl_DriverCloseProc *closeProc;
        Tcl_DriverInputProc *inputProc;
        Tcl_DriverOutputProc *outputProc;
        Tcl_DriverSeekProc *seekProc;
        Tcl_DriverSetOptionProc *setOptionProc;
        Tcl_DriverGetOptionProc *getOptionProc;
        Tcl_DriverWatchProc *watchProc;
        Tcl_DriverGetHandleProc *getHandleProc;
        Tcl_DriverClose2Proc *close2Proc;
        Tcl_DriverBlockModeProc *blockModeProc;
        Tcl_DriverFlushProc *flushProc;
        Tcl_DriverHandlerProc *handlerProc;
        Tcl_DriverWideSeekProc *wideSeekProc;
        Tcl_DriverThreadActionProc *threadActionProc;
        Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

No es necesario proporcionar implementaciones para todas las operaciones del canal. Aquellas que no sean necesarias pueden establecerse a NULL en la estructura: blockModeProc, seekProc, setOptionProc, getOptionProc, getHandleProc y close2Proc, además de flushProc, handlerProc, threadActionProc y truncateProc. Otras funciones que no se pueden implementar de manera significativa deben devolver EINVAL cuando se llamen, para indicar que las operaciones que representan no están disponibles. Tenga en cuenta también que wideSeekProc puede ser NULL si seekProc lo es.

El usuario solo debe utilizar la estructura anterior para la instanciación de Tcl_ChannelType. Al hacer referencia a los campos de una estructura Tcl_ChannelType, se deben utilizar las siguientes funciones para obtener los valores: Tcl_ChannelName, Tcl_ChannelVersion, Tcl_ChannelBlockModeProc, Tcl_ChannelCloseProc, Tcl_ChannelClose2Proc, Tcl_ChannelInputProc, Tcl_ChannelOutputProc, Tcl_ChannelSeekProc, Tcl_ChannelWideSeekProc, Tcl_ChannelThreadActionProc, Tcl_ChannelTruncateProc, Tcl_ChannelSetOptionProc, Tcl_ChannelGetOptionProc, Tcl_ChannelWatchProc, Tcl_ChannelGetHandleProc, Tcl_ChannelFlushProc o Tcl_ChannelHandlerProc.

El cambio en las estructuras se realizó de tal manera que los tipos de canal estándar son compatibles binariamente. Sin embargo, los tipos de canal que utilizan canales apilados (es decir, TLS, Trf) tienen nuevas versiones para corresponder al cambio anterior, ya que el código anterior para canales apilados tenía problemas.

TYPENAME

El campo typeName contiene una cadena terminada en nulo que identifica el tipo de dispositivo implementado por este controlador, por ejemplo, file o socket.

Este valor se puede recuperar con Tcl_ChannelName, que devuelve un puntero a la cadena.

VERSION

El campo version debe establecerse en la versión de la estructura que necesita. TCL_CHANNEL_VERSION_2 es el mínimo recomendado. TCL_CHANNEL_VERSION_3 debe establecerse para especificar el miembro wideSeekProc. TCL_CHANNEL_VERSION_4 debe establecerse para especificar el miembro threadActionProc (incluye wideSeekProc). TCL_CHANNEL_VERSION_5 debe establecerse para especificar los miembros truncateProc (incluye wideSeekProc y threadActionProc). Si no se establece en ninguno de estos, entonces se asume que este Tcl_ChannelType tiene la estructura original. Consulte OLD CHANNEL TYPES para más detalles. Si bien Tcl reconocerá y funcionará con ambas estructuras, los canales apilados deben ser de al menos TCL_CHANNEL_VERSION_2 para funcionar correctamente.

Este valor se puede recuperar con Tcl_ChannelVersion, que devuelve uno de TCL_CHANNEL_VERSION_5, TCL_CHANNEL_VERSION_4, TCL_CHANNEL_VERSION_3, TCL_CHANNEL_VERSION_2 o TCL_CHANNEL_VERSION_1.

BLOCKMODEPROC

El campo blockModeProc contiene la dirección de una función llamada por la capa genérica para establecer el modo de bloqueo y sin bloqueo en el dispositivo. BlockModeProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverBlockModeProc(
        ClientData instanceData,
        int mode);

instanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando se creó este canal. El argumento mode es TCL_MODE_BLOCKING o TCL_MODE_NONBLOCKING para establecer el dispositivo en modo de bloqueo o sin bloqueo. La función debe devolver cero si la operación fue exitosa, o un código de error POSIX distinto de cero si la operación falló.

Si la operación es exitosa, la función puede modificar el instanceData suministrado para registrar que el canal entró en modo de bloqueo o sin bloqueo y para implementar el comportamiento de bloqueo o sin bloqueo. Para algunos tipos de dispositivos, el comportamiento de bloqueo y sin bloqueo puede ser implementado por el sistema operativo subyacente; para otros tipos de dispositivos, el comportamiento debe ser emulado en el controlador de canal.

Este valor se puede recuperar con Tcl_ChannelBlockModeProc, que devuelve un puntero a la función.

Un controlador de canal que no suministra un blockModeProc debe ser muy, muy cuidadoso. Debe indicar a la capa genérica exactamente qué modo de bloqueo le es aceptable, y esto también debe documentarse para el usuario para que el modo de bloqueo del canal no se cambie a un valor inaceptable. Cualquier confusión aquí puede llevar al intérprete a un interbloqueo (falso y difícil de encontrar).

CLOSEPROC Y CLOSE2PROC

El campo closeProc contiene la dirección de una función llamada por la capa genérica para limpiar la información relacionada con el controlador cuando se cierra el canal. CloseProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverCloseProc(
        ClientData instanceData,
        Tcl_Interp *interp);

El argumento instanceData es el mismo que el valor proporcionado a Tcl_CreateChannel cuando se creó el canal. La función debe liberar cualquier almacenamiento mantenido por el controlador de canal para este canal, y cerrar los dispositivos de entrada y salida encapsulados por este canal. Toda la salida en cola se habrá vaciado al dispositivo antes de que se llame a esta función, y no se invocarán más operaciones del controlador en esta instancia después de llamar a closeProc. Si la operación de cierre es exitosa, el procedimiento

debería devolver cero; de lo contrario, debería devolver un código de error POSIX distinto de cero. Además, si ocurre un error y interp no es NULL, el procedimiento debería almacenar un mensaje de error en el resultado del intérprete.

Alternativamente, los canales que admiten el cierre de los lados de lectura y escritura de forma independiente pueden establecer closeProc en TCL_CLOSE2PROC y establecer close2Proc en la dirección de una función que coincida con el siguiente prototipo:

typedef int Tcl_DriverClose2Proc(
        ClientData instanceData,
        Tcl_Interp *interp,
        int flags);

Se llamará a close2Proc con flags establecido en una combinación OR de TCL_CLOSE_READ o TCL_CLOSE_WRITE para indicar que el controlador debe cerrar el lado de lectura y/o escritura del canal. Se puede invocar al controlador del canal para realizar operaciones adicionales en el canal después de que se llame a close2Proc para cerrar uno o ambos lados del canal. Si flags es 0 (cero), el controlador debe cerrar el canal de la manera descrita anteriormente para closeProc. No se invocarán más operaciones en esta instancia después de que se llame a close2Proc con todas las banderas despejadas. En todos los casos, la función close2Proc debe devolver cero si la operación de cierre fue exitosa; de lo contrario, debe devolver un código de error POSIX distinto de cero. Además, si ocurre un error y interp no es NULL, el procedimiento debería almacenar un mensaje de error en el resultado del intérprete.

Los valores closeProc y close2Proc se pueden recuperar con Tcl_ChannelCloseProc o Tcl_ChannelClose2Proc, que devuelven un puntero a la función respectiva.

INPUTPROC

El campo inputProc contiene la dirección de una función a la que llama la capa genérica para leer datos del archivo o dispositivo y almacenarlos en un búfer interno. InputProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverInputProc(
        ClientData instanceData,
        char *buf,
        int bufSize,
        int *errorCodePtr);

InstanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando se creó el canal. El argumento buf apunta a una matriz de bytes en la que se almacenarán las entradas del dispositivo, y el argumento bufSize indica cuántos bytes están disponibles en buf.

El argumento errorCodePtr apunta a una variable entera proporcionada por la capa genérica. Si ocurre un error, la función debe establecer la variable en un código de error POSIX que identifique el error que ocurrió.

La función debe leer datos del dispositivo de entrada encapsulado por el canal y almacenarlos en buf. En caso de éxito, la función debe devolver un entero no negativo que indique cuántos bytes se leyeron del dispositivo de entrada y se almacenaron en buf. En caso de error, la función debe devolver -1. Si ocurre un error después de que se hayan leído algunos datos del dispositivo, esos datos se pierden.

Si inputProc puede determinar que el dispositivo de entrada tiene algunos datos disponibles pero menos de los solicitados por el argumento bufSize, la función solo debe intentar leer tantos datos como estén disponibles y devolver sin bloquearse. Si el dispositivo de entrada no tiene datos disponibles en absoluto y el canal está en modo no bloqueante, la función debe devolver un error EAGAIN. Si el dispositivo de entrada no tiene datos disponibles en absoluto y el canal está en modo bloqueante, la función debe bloquearse durante el menor tiempo posible hasta que se pueda leer al menos un byte de datos del dispositivo; luego, debe devolver tantos datos como pueda leer sin bloquearse.

Este valor se puede recuperar con Tcl_ChannelInputProc, que devuelve un puntero a la función.

OUTPUTPROC

El campo outputProc contiene la dirección de una función a la que llama la capa genérica para transferir datos de un búfer interno al dispositivo de salida. OutputProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverOutputProc(
        ClientData instanceData,
        const char *buf,
        int toWrite,
        int *errorCodePtr);

InstanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando se creó el canal. El argumento buf contiene una matriz de bytes que se escribirán en el dispositivo, y el argumento toWrite indica cuántos bytes se escribirán desde el argumento buf.

El argumento errorCodePtr apunta a una variable entera proporcionada por la capa genérica. Si ocurre un error, la función debe establecer esta variable en un código de error POSIX que identifique el error.

La función debe escribir los datos en buf en el dispositivo de salida encapsulado por el canal. En caso de éxito, la función debe devolver un entero no negativo que indique cuántos bytes se escribieron en el dispositivo de salida. El valor de retorno es normalmente el mismo que toWrite, pero puede ser menor en algunos casos, como si la operación de salida es interrumpida por una señal. Si ocurre un error, la función debe devolver -1. En caso de error, es posible que algunos datos se hayan escrito en el dispositivo.

Si el canal no está bloqueando y el dispositivo de salida no puede absorber ningún dato, la función debe devolver -1 con un error EAGAIN sin escribir ningún dato.

Este valor se puede recuperar con Tcl_ChannelOutputProc, que devuelve un puntero a la función.

SEEKPROC Y WIDESEEKPROC

El campo seekProc contiene la dirección de una función a la que llama la capa genérica para mover el punto de acceso en el que se aplicarán las operaciones de entrada o salida posteriores. SeekProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverSeekProc(
        ClientData instanceData,
        long offset,
        int seekMode,
        int *errorCodePtr);

El argumento instanceData es el mismo que el valor dado a Tcl_CreateChannel cuando se creó este canal. Offset y seekMode tienen el mismo significado que para el procedimiento Tcl_Seek (descrito en la entrada del manual para Tcl_OpenFileChannel).

El argumento errorCodePtr apunta a una variable entera proporcionada por la capa genérica para devolver valores errno de la función. La función debe establecer esta variable en un código de error POSIX si ocurre un error. La función debe almacenar un código de error EINVAL si el tipo de canal no implementa la búsqueda.

El valor de retorno es el nuevo punto de acceso o -1 en caso de error. Si ocurrió un error, la función no debe mover el punto de acceso.

Si hay un campo seekProc no NULL, el campo wideSeekProc puede contener la dirección de una función alternativa a utilizar que maneje desplazamientos amplios (es decir, mayores de 32 bits), lo que permite buscar dentro de archivos mayores de 2 GB. Se llamará a wideSeekProc con preferencia a seekProc, pero ambos deben definirse si se define wideSeekProc. WideSeekProc debe coincidir con el siguiente prototipo:

typedef Tcl_WideInt Tcl_DriverWideSeekProc(
        ClientData instanceData,
        Tcl_WideInt offset,
        int seekMode,
        int *errorCodePtr);

Los argumentos y valores de retorno significan lo mismo que con seekProc arriba, excepto que el tipo de desplazamientos y el tipo de retorno son diferentes.

El valor seekProc se puede recuperar con Tcl_ChannelSeekProc, que devuelve un puntero a la función, y de manera similar, wideSeekProc se puede recuperar con Tcl_ChannelWideSeekProc.

SETOPTIONPROC

El campo setOptionProc contiene la dirección de una función a la que llama la capa genérica para establecer una opción específica del tipo de canal en un canal. setOptionProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverSetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        const char *newValue);

optionName es el nombre de una opción a establecer, y newValue es el nuevo valor para esa opción, como una cadena. instanceData es el mismo que el valor dado a Tcl_CreateChannel cuando se creó este canal. La función debe realizar cualquier acción específica del tipo de canal requerida para implementar el nuevo valor de la opción.

Algunas opciones son manejadas por el código genérico y esta función nunca se llama para establecerlas, por ejemplo, -blockmode. Otras opciones son específicas de cada tipo de canal y se llamará al procedimiento setOptionProc del controlador del canal para implementarlas. El campo setOptionProc puede ser NULL, lo que indica que este tipo de canal no admite opciones específicas del tipo.

Si el valor de la opción se modifica exitosamente al nuevo valor, la función devuelve TCL_OK. Debe llamar a Tcl_BadChannelOption que a su vez devuelve TCL_ERROR si optionName no es reconocido. Si newValue especifica un valor para la opción que no se admite o si ocurre un error de llamada al sistema, la función debe dejar un mensaje de error en el resultado de interp si interp no es NULL. La función también debe llamar a Tcl_SetErrno para almacenar un código de error POSIX apropiado.

Este valor se puede recuperar con Tcl_ChannelSetOptionProc, que devuelve un puntero a la función.

typedef int Tcl_DriverGetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        Tcl_DString *optionValue);
