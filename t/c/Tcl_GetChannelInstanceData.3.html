DESCRIPCIÓN

Tcl utiliza una arquitectura de canales de dos capas. Proporciona una capa superior genérica para permitir que los programas C y Tcl realicen entrada y salida utilizando las mismas API para una variedad de archivos, dispositivos, sockets, etc. Las API C genéricas se describen en la entrada del manual de Tcl_OpenFileChannel.

La capa inferior proporciona controladores de canales específicos de tipo para cada tipo de dispositivo admitido en cada plataforma. Esta entrada del manual describe las API C utilizadas para comunicarse entre la capa genérica y los controladores de canales específicos de tipo. También explica cómo se pueden agregar nuevos tipos de canales proporcionando nuevos controladores de canales.

Los controladores de canales consisten en una serie de componentes: Primero, cada controlador de canales proporciona una estructura Tcl_ChannelType que contiene punteros a funciones que implementan las diversas operaciones utilizadas por la capa genérica para comunicarse con el controlador de canales. La estructura Tcl_ChannelType y las funciones a las que hace referencia se describen en la sección TCL_CHANNELTYPE, a continuación.

Segundo, los controladores de canales suelen proporcionar un comando Tcl para crear instancias de ese tipo de canal. Por ejemplo, el comando Tcl open crea canales que utilizan los controladores de canales de archivo y de comando, y el comando Tcl socket crea canales que utilizan sockets TCP para la comunicación de red.

Tercero, un controlador de canales opcionalmente proporciona una función C para abrir instancias de canal de ese tipo. Por ejemplo, Tcl_OpenFileChannel abre un canal que utiliza el controlador de canales de archivo, y Tcl_OpenTcpClient abre un canal que utiliza el protocolo de red TCP. Estas funciones de creación suelen utilizar Tcl_CreateChannel internamente para abrir el canal.

Para agregar un nuevo tipo de canal, debe implementar una API C o un comando Tcl que abra un canal invocando Tcl_CreateChannel. Cuando su controlador llama a Tcl_CreateChannel, pasa una estructura Tcl_ChannelType que describe los procedimientos de E/S del controlador. Luego, la capa genérica invocará las funciones a las que hace referencia esa estructura para realizar operaciones en el canal.

Tcl_CreateChannel abre un nuevo canal y asocia los typePtr y instanceData proporcionados con él. El canal se abre en el modo indicado por mask. Para una discusión sobre los controladores de canales, sus operaciones y la estructura Tcl_ChannelType, consulte la sección TCL_CHANNELTYPE, a continuación.

Tcl_CreateChannel interactúa con el código que administra los canales estándar. Una vez que un canal estándar fue inicializado a través de una llamada a Tcl_GetStdChannel o una llamada a Tcl_SetStdChannel, el cierre de este canal estándar hará que la próxima llamada a Tcl_CreateChannel convierta el nuevo canal en el nuevo canal estándar también. Vea Tcl_StandardChannels para un tratado general sobre los canales estándar y el comportamiento de la biblioteca Tcl con respecto a ellos.

Tcl_GetChannelInstanceData devuelve los datos de instancia asociados con el canal en channel. Este es el mismo que el argumento instanceData en la llamada a Tcl_CreateChannel que creó este canal.

Tcl_GetChannelType devuelve un puntero a la estructura Tcl_ChannelType utilizada por el canal en el argumento channel. Este es el mismo que el argumento typePtr en la llamada a Tcl_CreateChannel que creó este canal.

Tcl_GetChannelName devuelve una cadena que contiene el nombre asociado con el canal, o NULL si el argumento channelName de Tcl_CreateChannel era NULL.

--- title: Channel Drivers synopsis: | This chapter describes the facilities for implementing channel drivers, which allow Tcl to perform I/O on devices other than standard files and sockets. description: | This chapter describes the facilities for implementing channel drivers, which allow Tcl to perform I/O on devices other than standard files and sockets. Channel drivers are usually implemented as C procedures that are dynamically loaded into the Tcl interpreter. They allow Tcl scripts to read and write data to and from devices such as serial ports, pipes, printers, and arbitrary memory buffers. sections: - title: Channel Management Functions content: |

The Tcl channel driver interface provides several functions that are useful for implementing channel drivers. These are:

Tcl_GetChannel
Returns a pointer to the internal channel structure associated with chanName. If chanName is not a valid channel name or if the channel has been closed, then NULL is returned.
Tcl_GetChannelInstanceData
Returns the instanceData that was passed to Tcl_CreateChannel when the channel was created. This is the same data that is passed to the driver's procedures.
Tcl_GetChannelName
Returns the name of the channel associated with the channel structure chanPtr.
Tcl_GetChannelType
Returns a pointer to the Tcl_ChannelType structure associated with the channel chanPtr.
Tcl_OpenTcpClient
Opens a TCP connection to the specified host and port and returns a channel name for the connection. If an error occurs, an error message is left in interp and NULL is returned. The channel is created with blocking semantics and the buffer size is set to the default.
Tcl_OpenTcpServer
Opens a TCP server socket on the specified port and returns a channel name for the listening socket. If an error occurs, an error message is left in interp and NULL is returned. The server socket is created with blocking semantics.
Tcl_GetChannelHandle
Returns a pointer to the device handle for the channel chanPtr in the specified direction direction. If the channel does not have a device handle for the specified direction, then NULL is returned. The direction should be one of TCL_READABLE or TCL_WRITABLE. Tcl may return different types of handles; refer to the manual entries for each driver to determine what type of handle is returned.
Tcl_SetChannelHandle
Associates the file descriptor specified by handlePtr with the channel chanPtr for the specified direction direction. If the channel already has a device handle for the specified direction, it will be replaced. The direction should be one of TCL_READABLE or TCL_WRITABLE. The function returns TCL_OK if the association was successful, and TCL_ERROR otherwise.
Tcl_GetChannelThread
Returns the id of the thread currently managing the specified channel. This allows channel drivers to send their file events to the correct event queue even for a multi-threaded core.
Tcl_GetChannelMode
Returns an OR-ed combination of TCL_READABLE and TCL_WRITABLE, indicating whether the channel is open for input and output.
Tcl_GetChannelBufferSize
Returns the size, in bytes, of buffers allocated to store input or output in channel. If the value was not set by a previous call to Tcl_SetChannelBufferSize, described below, then the default value of 4096 is returned.
Tcl_SetChannelBufferSize
Sets the size, in bytes, of buffers that will be allocated in subsequent operations on the channel to store input or output. The size argument should be between one and one million, allowing buffers of one byte to one million bytes. If size is outside this range, Tcl_SetChannelBufferSize sets the buffer size to 4096.
Tcl_NotifyChannel
Is called by a channel driver to indicate to the generic layer that the events specified by mask have occurred on the channel. Channel drivers are responsible for invoking this function whenever the channel handlers need to be called for the channel (or other pending tasks like a write flush should be performed). See WATCHPROC below for more details.
Tcl_BadChannelOption
Is called from driver specific setOptionProc or getOptionProc to generate a complete error message.
Tcl_ChannelBuffered
Returns the number of bytes of input currently buffered in the internal buffer (push back area) of the channel itself. It does not report about the data in the overall buffers for the stack of channels the supplied channel is part of.
Tcl_IsChannelShared
Checks the refcount of the specified channel and returns whether the channel was shared among multiple interpreters (result == 1) or not (result == 0).
Tcl_IsChannelRegistered
Checks whether the specified channel is registered in the given interpreter (result == 1) or not (result == 0).
Tcl_IsChannelExisting
Checks whether a channel with the specified name is registered in the (thread)-global list of all channels (result == 1) or not (result == 0).
Tcl_CutChannel
Removes the specified channel from the (thread)global list of all channels (of the current thread). Application to a channel still registered in some interpreter is not allowed. Also notifies the driver if the Tcl_ChannelType version is TCL_CHANNEL_VERSION_4 (or higher), and Tcl_DriverThreadActionProc is defined for it.
Tcl_SpliceChannel
Adds the specified channel to the (thread)global list of all channels (of the current thread). Application to a channel registered in some interpreter is not allowed. Also notifies the driver if the Tcl_ChannelType version is TCL_CHANNEL_VERSION_4 (or higher), and Tcl_DriverThreadActionProc is defined for it.
Tcl_ClearChannelHandlers
Removes all channel handlers and event scripts associated with the specified channel, thus shutting down all event processing for this channel.
- title: TCL_CHANNELTYPE content: |

A channel driver provides a Tcl_ChannelType structure that contains pointers to functions that implement the various operations on a channel; these operations are invoked as needed by the generic layer. The structure was versioned starting in Tcl 8.3.2/8.4 to correct a problem with stacked channel drivers. See the OLD CHANNEL TYPES section below for details about the old structure.

The Tcl_ChannelType structure contains the following fields:

typedef struct Tcl_ChannelType {
              const char *typeName;
              Tcl_ChannelTypeVersion version;
              Tcl_DriverCloseProc *closeProc;
              Tcl_DriverInputProc *inputProc;
              Tcl_DriverOutputProc *outputProc;
              Tcl_DriverSeekProc *seekProc;
              Tcl_DriverSetOptionProc *setOptionProc;
              Tcl_DriverGetOptionProc *getOptionProc;
              Tcl_DriverWatchProc *watchProc;
              Tcl_DriverGetHandleProc *getHandleProc;
              Tcl_DriverClose2Proc *close2Proc;
              Tcl_DriverBlockModeProc *blockModeProc;
              Tcl_DriverFlushProc *flushProc;
              Tcl_DriverHandlerProc *handlerProc;
              Tcl_DriverWideSeekProc *wideSeekProc;
              Tcl_DriverThreadActionProc *threadActionProc;
              Tcl_DriverTruncateProc *truncateProc;
      } Tcl_ChannelType;

It is not necessary to provide implementations for all channel operations. Those which are not necessary may be set to NULL in the struct: blockModeProc, seekProc, setOptionProc, getOptionProc, getHandleProc, and close2Proc, in addition to flushProc, handlerProc, threadActionProc, and truncateProc. Other functions that cannot be implemented in a meaningful way should return EINVAL when called, to indicate that the operations they represent are not available. Also note that wideSeekProc can be NULL if seekProc is.

The user should only use the above structure for Tcl_ChannelType instantiation. When referencing fields in a Tcl_ChannelType structure, the following functions should be used to obtain the values: Tcl_ChannelName, Tcl_ChannelVersion, Tcl_ChannelBlockModeProc, Tcl_ChannelCloseProc, Tcl_ChannelClose2Proc, Tcl_ChannelInputProc, Tcl_ChannelOutputProc, Tcl_ChannelSeekProc, Tcl_ChannelWideSeekProc, Tcl_ChannelThreadActionProc, Tcl_ChannelTruncateProc, Tcl_ChannelSetOptionProc, Tcl_ChannelGetOptionProc, Tcl_ChannelWatchProc, Tcl_ChannelGetHandleProc, Tcl_ChannelFlushProc, or Tcl_ChannelHandlerProc.

The change to the structures was made in such a way that standard channel types are binary compatible. However, channel types that use stacked channels (i.e. TLS, Trf) have new versions to correspond to the above change since the previous code for stacked channels had problems.

- title: TYPENAME content: |

The typeName field contains a null-terminated string that identifies the type of the device implemented by this driver, e.g. file or socket.

This value can be retrieved with Tcl_ChannelName, which returns a pointer to the string.

- title: VERSION content: |

The version field should be set to the version of the structure that you require. TCL_CHANNEL_VERSION_2 is the minimum recommended. TCL_CHANNEL_VERSION_3 must be set to specify the wideSeekProc member. TCL_CHANNEL_VERSION_4 must be set to specify the threadActionProc member (includes wideSeekProc). TCL_CHANNEL_VERSION_5 must be set to specify the truncateProc members (includes wideSeekProc and threadActionProc). If it is not set to any of these, then this Tcl_ChannelType is assumed to have the original structure. See OLD CHANNEL TYPES for more details. While Tcl will recognize and function with either structures, stacked channels must be of at least TCL_CHANNEL_VERSION_2 to function correctly.

This value can be retrieved with Tcl_ChannelVersion, which returns one of TCL_CHANNEL_VERSION_5, TCL_CHANNEL_VERSION_4, TCL_CHANNEL_VERSION_3, TCL_CHANNEL_VERSION_2 or TCL_CHANNEL_VERSION_1.

- title: BLOCKMODEPROC content: |

The blockModeProc field contains the address of a function called by the generic layer to set blocking and nonblocking mode on the device. BlockModeProc should match the following prototype:

typedef int Tcl_DriverBlockModeProc(
                  ClientData instanceData,
                  int mode);

The instanceData is the same as the value passed to Tcl_CreateChannel when this channel was created. The mode argument is either TCL_MODE_BLOCKING or TCL_MODE_NONBLOCKING to set the device into blocking or nonblocking mode. The function should return zero if the operation was successful, or a nonzero POSIX error code if the operation failed.

If the operation is successful, the function can modify the supplied instanceData to record that the channel entered blocking or nonblocking mode and to implement the blocking or nonblocking behavior. For some device types, the blocking and nonblocking behavior can be implemented by the underlying operating system; for other device types, the behavior must be emulated in the channel driver.

This value can be retrieved with Tcl_ChannelBlockModeProc, which returns a pointer to the function.

A channel driver not supplying a blockModeProc has to be very, very careful. It has to tell the generic layer exactly which blocking mode is acceptable to it, and should this also document for the user so that the blocking mode of the channel is not changed to an unacceptable value. Any confusion here may lead the interpreter into a (spurious and difficult to find) deadlock.

- title: CLOSEPROC AND CLOSE2PROC content: |

The closeProc field contains the address of a function called by the generic layer to clean up driver-related information when the channel is closed. CloseProc must match the following prototype:

typedef int Tcl_DriverCloseProc(
                  ClientData instanceData,
                  Tcl_Interp *interp);

The instanceData argument is the same as the value provided to Tcl_CreateChannel when the channel was created. The function should release any storage maintained by the channel driver for this channel, and close the input and output devices encapsulated by this channel. All queued output will have been flushed to the device before this function is called, and no further driver operations will be invoked on this instance after calling the closeProc. If the close operation is successful, the procdevolver cero; de lo contrario, debería devolver un código de error POSIX distinto de cero. Además, si ocurre un error y interp no es NULL, el procedimiento debería almacenar un mensaje de error en el resultado del intérprete.

Alternativamente, los canales que admiten el cierre independiente de los lados de lectura y escritura pueden establecer closeProc en TCL_CLOSE2PROC y establecer close2Proc en la dirección de una función que coincida con el siguiente prototipo:

typedef int Tcl_DriverClose2Proc(
        ClientData instanceData,
        Tcl_Interp *interp,
        int flags);

Se llamará a close2Proc con flags establecido en una combinación OR de TCL_CLOSE_READ o TCL_CLOSE_WRITE para indicar que el controlador debe cerrar el lado de lectura y/o escritura del canal. Se puede invocar al controlador del canal para realizar operaciones adicionales en el canal después de que se llame a close2Proc para cerrar uno o ambos lados del canal. Si flags es 0 (cero), el controlador debe cerrar el canal de la manera descrita anteriormente para closeProc. No se invocarán más operaciones en esta instancia después de que se llame a close2Proc con todas las banderas despejadas. En todos los casos, la función close2Proc debe devolver cero si la operación de cierre fue exitosa; de lo contrario, debe devolver un código de error POSIX distinto de cero. Además, si ocurre un error y interp no es NULL, el procedimiento debe almacenar un mensaje de error en el resultado del intérprete.

Los valores closeProc y close2Proc se pueden recuperar con Tcl_ChannelCloseProc o Tcl_ChannelClose2Proc, que devuelven un puntero a la función respectiva.

INPUTPROC

El campo inputProc contiene la dirección de una función llamada por la capa genérica para leer datos del archivo o dispositivo y almacenarlos en un búfer interno. InputProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverInputProc(
        ClientData instanceData,
        char *buf,
        int bufSize,
        int *errorCodePtr);

InstanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando se creó el canal. El argumento buf apunta a una matriz de bytes donde almacenar la entrada del dispositivo, y el argumento bufSize indica cuántos bytes están disponibles en buf.

El argumento errorCodePtr apunta a una variable entera proporcionada por la capa genérica. Si ocurre un error, la función debe establecer la variable en un código de error POSIX que identifique el error que ocurrió.

La función debe leer datos del dispositivo de entrada encapsulado por el canal y almacenarlos en buf. En caso de éxito, la función debe devolver un entero no negativo que indique cuántos bytes se leyeron del dispositivo de entrada y se almacenaron en buf. En caso de error, la función debe devolver -1. Si ocurre un error después de que se hayan leído algunos datos del dispositivo, esos datos se pierden.

Si inputProc puede determinar que el dispositivo de entrada tiene algunos datos disponibles pero menos de los solicitados por el argumento bufSize, la función solo debe intentar leer tantos datos como estén disponibles y devolver sin bloquear. Si el dispositivo de entrada no tiene datos disponibles en absoluto y el canal está en modo no bloqueante, la función debe devolver un error EAGAIN. Si el dispositivo de entrada no tiene datos disponibles en absoluto y el canal está en modo bloqueante, la función debe bloquearse durante el menor tiempo posible hasta que se pueda leer al menos un byte de datos del dispositivo; luego, debe devolver tantos datos como pueda leer sin bloquear.

Este valor se puede recuperar con Tcl_ChannelInputProc, que devuelve un puntero a la función.

OUTPUTPROC

El campo outputProc contiene la dirección de una función llamada por la capa genérica para transferir datos de un búfer interno al dispositivo de salida. OutputProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverOutputProc(
        ClientData instanceData,
        const char *buf,
        int toWrite,
        int *errorCodePtr);

InstanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando se creó el canal. El argumento buf contiene una matriz de bytes para escribir en el dispositivo, y el argumento toWrite indica cuántos bytes se escribirán desde el argumento buf.

El argumento errorCodePtr apunta a una variable entera proporcionada por la capa genérica. Si ocurre un error, la función debe establecer esta variable en un código de error POSIX que identifique el error.

La función debe escribir los datos en buf en el dispositivo de salida encapsulado por el canal. En caso de éxito, la función debe devolver un entero no negativo que indique cuántos bytes se escribieron en el dispositivo de salida. El valor de retorno es normalmente el mismo que toWrite, pero puede ser menor en algunos casos, como si la operación de salida se interrumpe por una señal. Si ocurre un error, la función debe devolver -1. En caso de error, es posible que se hayan escrito algunos datos en el dispositivo.

Si el canal no está bloqueando y el dispositivo de salida no puede absorber ningún dato, la función debe devolver -1 con un error EAGAIN sin escribir ningún dato.

Este valor se puede recuperar con Tcl_ChannelOutputProc, que devuelve un puntero a la función.

SEEKPROC Y WIDESEEKPROC

El campo seekProc contiene la dirección de una función llamada por la capa genérica para mover el punto de acceso en el que se aplicarán las operaciones de entrada o salida posteriores. SeekProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverSeekProc(
        ClientData instanceData,
        long offset,
        int seekMode,
        int *errorCodePtr);

El argumento instanceData es el mismo que el valor dado a Tcl_CreateChannel cuando se creó este canal. Offset y seekMode tienen el mismo significado que para el procedimiento Tcl_Seek (descrito en la entrada del manual para Tcl_OpenFileChannel).

El argumento errorCodePtr apunta a una variable entera proporcionada por la capa genérica para devolver valores errno de la función. La función debe establecer esta variable en un código de error POSIX si ocurre un error. La función debe almacenar un código de error EINVAL si el tipo de canal no implementa la búsqueda.

El valor de retorno es el nuevo punto de acceso o -1 en caso de error. Si ocurrió un error, la función no debe mover el punto de acceso.

Si hay un campo seekProc no NULL, el campo wideSeekProc puede contener la dirección de una función alternativa a utilizar que maneja desplazamientos amplios (es decir, mayores de 32 bits), permitiendo así búsquedas dentro de archivos de más de 2 GB. Se llamará a wideSeekProc preferentemente a seekProc, pero ambos deben definirse si se define wideSeekProc. WideSeekProc debe coincidir con el siguiente prototipo:

typedef Tcl_WideInt Tcl_DriverWideSeekProc(
        ClientData instanceData,
        Tcl_WideInt offset,
        int seekMode,
        int *errorCodePtr);

Los argumentos y valores de retorno significan lo mismo que con seekProc anteriormente, excepto que el tipo de desplazamientos y el tipo de retorno son diferentes.

El valor seekProc se puede recuperar con Tcl_ChannelSeekProc, que devuelve un puntero a la función, y de manera similar el wideSeekProc se puede recuperar con Tcl_ChannelWideSeekProc.

SETOPTIONPROC

El campo setOptionProc contiene la dirección de una función llamada por la capa genérica para establecer una opción específica del tipo de canal en un canal. setOptionProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverSetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        const char *newValue);

optionName es el nombre de una opción a establecer, y newValue es el nuevo valor para esa opción, como una cadena. El instanceData es el mismo que el valor dado a Tcl_CreateChannel cuando se creó este canal. La función debe realizar cualquier acción específica del tipo de canal requerida para implementar el nuevo valor de la opción.

Algunas opciones son manejadas por el código genérico y esta función nunca se llama para establecerlas, por ejemplo, -blockmode. Otras opciones son específicas de cada tipo de canal y se llamará al procedimiento setOptionProc del controlador del canal para implementarlas. El campo setOptionProc puede ser NULL, lo que indica que este tipo de canal no admite opciones específicas del tipo.

Si el valor de la opción se modifica con éxito al nuevo valor, la función devuelve TCL_OK. Debe llamar a Tcl_BadChannelOption que a su vez devuelve TCL_ERROR si el optionName no es reconocido. Si newValue especifica un valor para la opción que no es compatible o si ocurre un error de llamada al sistema, la función debe dejar un mensaje de error en el resultado de interp si interp no es NULL. La función también debe llamar a Tcl_SetErrno para almacenar un código de error POSIX apropiado.

Este valor se puede recuperar con Tcl_ChannelSetOptionProc, que devuelve un puntero a la función.

GETOPTIONPROC

El campo getOptionProc contiene la dirección de una función llamada por la capa genérica para obtener el valor de una opción específica del tipo de canal en un canal. getOptionProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverGetOptionProc(

OptionName es el nombre de una opción admitida por este tipo de canal. Si optionName es NULL, la función almacena en optionValue una lista alternada de todas las opciones admitidas y sus valores actuales. En caso de éxito, la función devuelve TCL_OK. Este procedimiento genera un mensaje de error de “opción inválida” en un intérprete (opcional). Se utiliza por los controladores de canal cuando se solicita una opción de Configurar/Obtener inválida. Su propósito es concatenar la lista genérica de opciones a las específicas y factorizar el mensaje de error de las opciones genéricas.

Siempre devuelve TCL_ERROR.

Se genera un mensaje de error en el valor de resultado de interp para indicar que un comando se invocó con una opción inválida. El mensaje tiene el formato

    opción inválida “blah”: debería ser
    <...opciones genéricas...>+<...opciones específicas...>
así que obtienes por ejemplo:

    -buffering, -buffersize, -eofchar, -translation,

cuando se llama con optionList igual a “peername sockname”

“blah” es el argumento optionName y “<opciones específicas>” es una lista separada por espacios de palabras de opción específicas. La función se encarga de insertar signos menos antes de cada opción, comas después y un “o” antes de la última opción.

Tcl_DriverCloseProc

El campo closeProc contiene la dirección de una función llamada por la capa genérica para cerrar un canal. CloseProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverCloseProc(
        ClientData instanceData,
        Tcl_Interp *interp);

InstanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó este canal. El campo closeProc debe liberar cualquier memoria o recurso asociado con el canal y devolver 0 en caso de éxito o un código de error POSIX (apropiado para usar con Tcl_SetErrno) en caso de fallo.

Este valor puede ser recuperado con Tcl_ChannelCloseProc, que devuelve un puntero a la función.

Tcl_DriverBlockModeProc

El campo blockModeProc contiene la dirección de una función llamada por la capa genérica para establecer el modo de bloqueo de un canal. BlockModeProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverBlockModeProc(
        ClientData instanceData,
        int mode);

InstanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó este canal. El argumento mode es TCL_BLOCKING o TCL_NONBLOCKING. La función debe establecer el canal en el modo especificado y devolver 0 en caso de éxito o un código de error POSIX en caso de fallo. Si el controlador de canal no implementa esta funcionalidad, el campo puede ser NULL.

Este valor puede ser recuperado con Tcl_ChannelBlockModeProc, que devuelve un puntero a la función.

Tcl_DriverInputProc

El campo inputProc contiene la dirección de una función llamada por la capa genérica para leer datos de un canal. InputProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverInputProc(
        ClientData instanceData,
        char *buf,
        int bufSize,
        int *errorCodePtr);

InstanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó este canal. Los argumentos buf y bufSize especifican un búfer en el que se deben leer los datos. La función debe leer como máximo bufSize bytes en el búfer y devolver el número de bytes leídos. Si se produce un error, la función debe almacenar un código de error POSIX adecuado en *errorCodePtr y devolver -1. Si se alcanza el final del archivo, la función debe devolver 0.

Este valor puede ser recuperado con Tcl_ChannelInputProc, que devuelve un puntero a la función.

typedef int Tcl_DriverOutputProc(
        ClientData instanceData,
        const char *buf,
        int toWrite,
        int *errorCodePtr);

InstanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó este canal. Los argumentos buf y toWrite especifican los datos que se van a escribir. La función debe escribir como máximo toWrite bytes del búfer y devolver el número de bytes escritos. Si se produce un error, la función debe almacenar un código de error POSIX adecuado en *errorCodePtr y devolver -1.

Este valor puede ser recuperado con Tcl_ChannelOutputProc, que devuelve un puntero a la función.

Tcl_DriverSeekProc

El campo seekProc contiene la dirección de una función llamada por la capa genérica para reposicionar el puntero de lectura/escritura de un canal. SeekProc debe coincidir con el siguiente prototipo:

typedef Tcl_WideInt Tcl_DriverSeekProc(
        ClientData instanceData,
        Tcl_WideInt offset,
        int seekMode);

InstanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó este canal. El argumento offset es el número de bytes a desplazar y seekMode es uno de SEEK_SET, SEEK_CUR o SEEK_END. La función debe reposicionar el puntero de lectura/escritura y devolver la nueva posición en bytes desde el principio del archivo. Si se produce un error, la función debe devolver -1.

Este valor puede ser recuperado con Tcl_ChannelSeekProc, que devuelve un puntero a la función.

Tcl_DriverSetOptionProc

El campo setOptionProc contiene la dirección de una función llamada por la capa genérica para establecer una opción específica del controlador de canal. SetOptionProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverSetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        const Tcl_Obj *valuePtr);

InstanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó este canal. OptionName es el nombre de la opción que se va a establecer y valuePtr es el valor de la opción como un Tcl_Obj. La función debe procesar la opción si es específica del controlador y devolver TCL_OK en caso de éxito o TCL_ERROR en caso de fallo. Si la opción no es reconocida, la función debe dejar un mensaje de error en el resultado de interp si interp no es NULL. La función también debe llamar a Tcl_SetErrno para almacenar un código de error POSIX apropiado.

Algunas opciones son manejadas por el código genérico y esta función nunca es llamada para recuperar su valor, por ejemplo, -blockmode. Otras opciones son específicas de cada tipo de canal y el procedimiento setOptionProc del controlador de canal será llamado para implementarlas. El campo setOptionProc puede ser NULL, lo que indica que este tipo de canal no admite opciones específicas del tipo.

Este valor puede ser recuperado con Tcl_ChannelSetOptionProc, que devuelve un puntero a la función.

Tcl_DriverGetOptionProc

El campo getOptionProc contiene la dirección de una función llamada por la capa genérica para obtener el valor de una opción específica del controlador de canal. GetOptionProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverGetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName);

InstanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó este canal. OptionName es el nombre de la opción cuyo valor se va a obtener. La función debe recuperar el valor de la opción si es específica del controlador y establecer el resultado de interp con el valor de la opción como un Tcl_Obj. Debe devolver TCL_OK en caso de éxito o TCL_ERROR en caso de fallo. Si la opción no es reconocida, la función debe dejar un mensaje de error en el resultado de interp si interp no es NULL. La función también debe llamar a Tcl_SetErrno para almacenar un código de error POSIX apropiado.

Algunas opciones son manejadas por el código genérico y esta función nunca es llamada para recuperar su valor, por ejemplo, -blockmode. Otras opciones son específicas de cada tipo de canal y el procedimiento getOptionProc del controlador de canal será llamado para implementarlas. El campo getOptionProc puede ser NULL, lo que indica que este tipo de canal no admite opciones específicas del tipo.

Este valor puede ser recuperado con Tcl_ChannelGetOptionProc, que devuelve un puntero a la función.

WATCHPROC

El campo watchProc contiene la dirección de una función llamada por la capa genérica para inicializar el mecanismo de notificación de eventos para detectar eventos de interés en este canal. WatchProc debe coincidir con el siguiente prototipo:

typedef void Tcl_DriverWatchProc(
        ClientData instanceData,
        int mask);

InstanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó este canal. El argumento mask es una combinación OR de TCL_READABLE, TCL_WRITABLE y TCL_EXCEPTION; indica los eventos que el llamante está interesado en detectar en este canal.

La función debe inicializar mecanismos específicos del tipo de dispositivo para detectar cuándo hay un evento de interés en el canal. Cuando ocurre uno o más de los eventos designados en el canal, el controlador del canal es responsable de llamar a Tcl_NotifyChannel para informar al módulo genérico del canal. El controlador debe tener cuidado de no dejar sin atención a otros controladores de canal o fuentes de devoluciones de llamada invocando Tcl_NotifyChannel con demasiada frecuencia. La equidad puede asegurarse utilizando la cola de eventos de Tcl para permitir que el evento del canal se programe en secuencia con otros eventos. Consulte la descripción de Tcl_QueueEvent para obtener detalles sobre cómo poner en cola un evento.

Este valor puede ser recuperado con Tcl_ChannelWatchProc, que devuelve un puntero a la función.

GETHANDLEPROC

El campo getHandleProc contiene la dirección de una función llamada por la capa genérica para recuperar un manejador específico del dispositivo del canal. GetHandleProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverGetHandleProc(
        ClientData instanceData,
        int direction,
        ClientData *handlePtr);

InstanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó este canal. El argumento direction es TCL_READABLE para recuperar el manejador utilizado para la entrada, o TCL_WRITABLE para recuperar el manejador utilizado para la salida.

Si la implementación del canal tiene manejadores específicos del dispositivo, la función debe recuperar el manejador apropiado asociado con el canal, según el argumento direction. El manejador debe almacenarse en la ubicación a la que apunta handlePtr y se debe devolver TCL_OK. Si el canal no está abierto para la dirección especificada, o si la implementación del canal no utiliza manejadores de dispositivo, la función debe devolver TCL_ERROR.

Este valor puede ser recuperado con Tcl_ChannelGetHandleProc, que devuelve un puntero a la función.

TIPOS DE CANAL ANTIGUOS

La estructura original (8.3.1 y anteriores) Tcl_ChannelType contiene los siguientes campos:

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
} Tcl_ChannelType;

Todavía es posible crear canales con la estructura anterior. El código interno del canal determinará la versión. Es imperativo utilizar la nueva estructura Tcl_ChannelType si se está creando un controlador de canal apilado, debido a problemas con la implementación anterior de canales apilados (en 8.2.0 a 8.3.1).

Antes de 8.4.0 (es decir, durante las últimas versiones de 8.3 y la primera parte del ciclo de desarrollo de 8.4) la estructura Tcl_ChannelType contenía los siguientes campos:

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_ChannelTypeVersion version;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverFlushProc *flushProc;
    Tcl_DriverHandlerProc *handlerProc;
    Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

Cuando la estructura anterior se registra como un tipo de canal, el campo version siempre debe ser TCL_CHANNEL_VERSION_2.
