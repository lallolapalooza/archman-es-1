DESCRIPCIÓN

Hay varias razones para llamar a las funciones de la API Tcl_FS (por ejemplo, Tcl_FSAccess y Tcl_FSStat) en lugar de llamar directamente a funciones de nivel de sistema como access y stat. En primer lugar, funcionan multiplataforma, por lo que una extensión que las llame debería funcionar sin modificaciones tanto en Unix como en Windows. En segundo lugar, la implementación de Windows de algunas de estas funciones corrige algunos errores en las llamadas de nivel de sistema. En tercer lugar, estas llamadas a funciones manejan cualquier conversión de ruta de “Utf a nativa de plataforma” que pueda ser requerida (y pueden almacenar en caché los resultados de dichas conversiones para una mayor eficiencia en llamadas posteriores). Cuarto, y quizás lo más importante, todas estas funciones son “conscientes del sistema de archivos virtual”. Cualquier sistema de archivos virtual (VFS, por sus siglas en inglés) que se haya registrado (a través de Tcl_FSRegister) puede redirigir el acceso a archivos a medios o métodos de acceso alternativos. Esto significa que todas estas funciones (y por lo tanto los comandos file, glob, pwd, cd, open, etc. de Tcl correspondientes) pueden operar sobre “archivos” que no son archivos nativos en el sistema de archivos nativo. Esto también significa que cualquier extensión Tcl que acceda al sistema de archivos (FS, por sus siglas en inglés) a través de esta API es automáticamente “consciente del sistema de archivos virtual”. Por supuesto, si una extensión accede al sistema de archivos nativo directamente (a través de APIs específicas de la plataforma, por ejemplo), Tcl no puede interceptar tales llamadas.

Si se han registrado VFS apropiados, los “archivos” pueden ser, para dar dos ejemplos, remotos (por ejemplo, situados en un servidor ftp remoto) o archivados (por ejemplo, dentro de un archivo .zip). Tales sistemas de archivos registrados proporcionan una tabla de búsqueda de funciones para implementar toda o parte de la funcionalidad enumerada aquí. Finalmente, las llamadas Tcl_FSStat y Tcl_FSLstat abstraen lo que el búfer “struct stat” está declarado para ser, permitiendo que el mismo código se utilice tanto en sistemas con como sin soporte para archivos de más de 2 GB de tamaño.

La API de Tcl_FS está **Tcl_Obj**-ificada y puede almacenar en caché representaciones internas y otras cadenas relacionadas con rutas (por ejemplo, el directorio de trabajo actual). Un efecto secundario de esto es que no se deben pasar valores con un recuento de referencias de cero a ninguna de estas funciones. Si tales llamadas se manejaran, podrían resultar en fugas de memoria (en algunas circunstancias, el código del sistema de archivos puede desear retener una referencia al valor pasado, y por lo tanto no se debe asumir que después de que cualquiera de estas llamadas regrese, el valor todavía tiene un recuento de referencias de cero; puede haber sido incrementado) o en una falla de segmentación directa (u otro error de acceso a memoria) debido a que el valor se libera a mitad de la manipulación compleja del valor requerida para garantizar que la ruta esté completamente normalizada y sea absoluta para la determinación del sistema de archivos. La lección práctica a aprender de esto es que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

es incorrecto y puede causar errores de memoria. El recuento de referencias de path debe incrementarse antes de pasarlo, o decrementar lo. Por esta razón, los valores con un recuento de referencias de cero se consideran rutas de sistema de archivos no válidas y llamar a cualquier función de la API de Tcl_FS con un valor así no tendrá ningún efecto.

FUNCIONES DE LA API FS

Tcl_FSCopyFile intenta copiar el archivo dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas se encuentran en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), se llama a la función de “copiar archivo” de ese sistema de archivos (si no es NULL). De lo contrario, la función devuelve -1 y establece la variable global de C **errno** al código de error POSIX “EXDEV” (que significa “enlace entre dominios”).

Tcl_FSCopyDirectory intenta copiar el directorio dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas se encuentran en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), se llama a la función de “copiar archivo” de ese sistema de archivos (si no es NULL). De lo contrario, la función devuelve -1 y establece la variable global de C **errno** al código de error POSIX “EXDEV” (que significa “enlace entre dominios”).

Tcl_FSCreateDirectory intenta crear el directorio dado por pathPtr llamando a la función de “crear directorio” del sistema de archivos propietario.

Tcl_FSDeleteFile intenta eliminar el archivo dado por pathPtr llamando a la función de “eliminar archivo” del sistema de archivos propietario.

Tcl_FSRemoveDirectory intenta eliminar el directorio dado por pathPtr llamando a la función de “eliminar directorio” del sistema de archivos propietario.

Tcl_FSRenameFile intenta renombrar el archivo o directorio dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas se encuentran en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), se llama a la función de “renombrar archivo” de ese sistema de archivos (si no es NULL). De lo contrario, la función devuelve -1 y establece la variable global de C **errno** al código de error POSIX “EXDEV” (que significa “enlace entre dominios”).

Tcl_FSListVolumes llama a cada sistema de archivos que tiene una función de “listar volúmenes” no NULL y les pide que devuelvan su lista de volúmenes raíz. Acumula los valores de retorno en una lista que se devuelve al llamador (con un recuento de referencias de 0).

Tcl_FSEvalFileEx lee el archivo dado por pathPtr utilizando la codificación identificada por encodingName y evalúa su contenido como un script de Tcl. Devuelve la misma información que Tcl_EvalObjEx. Si encodingName es NULL, se utiliza la codificación del sistema para leer el contenido del archivo. Si el archivo no se pudo leer, se devuelve un error de Tcl para describir por qué no se pudo leer el archivo. El carácter de fin de archivo (eofchar) para los archivos es “\x1A” (^Z) para todas las plataformas. Si requiere un “^Z” en código para comparación de cadenas, puede usar “\x1A”, que será sustituido de forma segura por el intérprete de Tcl en “^Z”. Tcl_FSEvalFile es una versión más simple de Tcl_FSEvalFileEx que siempre utiliza la codificación del sistema al leer el archivo.

Tcl_FSLoadFile carga dinámicamente un archivo de código binario en memoria y devuelve las direcciones de dos procedimientos dentro de ese archivo, si están definidos. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr. Si ese sistema de archivos no implementa esta función (la mayoría de los sistemas de archivos virtuales no lo harán, debido a limitaciones del sistema operativo en la carga dinámica de código binario), Tcl intentará copiar el archivo a un directorio temporal y cargar ese archivo temporal. Tcl_FSUnloadFile invierte la operación, solicitando que la biblioteca indicada por loadHandle se elimine del proceso. Tenga en cuenta que, a diferencia del comando **unload**, esto no da a la biblioteca ninguna oportunidad de limpieza.

Ambas funciones anteriores devuelven un código de finalización estándar de Tcl. Si ocurre un error, se deja un mensaje de error en el resultado del interp.

El token proporcionado a través de la variable indicada por loadHandlePtr puede usarse con Tcl_FindSymbol.

Tcl_FSMatchInDirectory es utilizado por el código de globbing para buscar en un directorio todos los archivos que coinciden con un patrón dado. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el globbing. Los mensajes de error se colocan en interp (a menos que interp sea NULL, lo cual está permitido), pero los buenos resultados se colocan en resultPtr proporcionado.

Tenga en cuenta que el código de **glob** implementa patrones recursivos internamente, por lo que esta función solo recibirá patrones simples, que pueden coincidir utilizando la lógica de **string match**. Para manejar la recursión, Tcl llamará a esta función con frecuencia solicitando solo que se devuelvan directorios. Un caso especial de ser llamado con un patrón NULL indica que la ruta solo debe verificarse para el tipo correcto.

Tcl_FSLink reemplaza la versión de biblioteca de **readlink**, y la extiende para soportar la creación de enlaces. Se llamará a la función apropiada para el sistema de archivos al que pertenece linkNamePtr.

Si toPtr es NULL, se realiza una acción de “leer enlace”. El resultado es un Tcl_Obj que especifica el contenido del enlace simbólico dado por linkNamePtr, o NULL si el enlace no se pudo leer. El resultado es propiedad del llamador, que debe llamar a Tcl_DecrRefCount cuando el resultado ya no sea necesario. Si toPtr no es NULL, Tcl debe crear un enlace de uno de los tipos pasados en la bandera linkAction. Esta bandera es una combinación OR de TCL_CREATE_SYMBOLIC_LINK y TCL_CREATE_HARD_LINK. Cuando existe una opción (es decir, se pasa más de una bandera), la convención de Tcl es preferir enlaces simbólicos. Cuando se crea un enlace con éxito, el valor de retorno debe ser toPtr (que por lo tanto ya es propiedad del llamador). Si no tiene éxito, se devuelve NULL.

Tcl_FSLstat rellena la estructura Tcl_StatBuf statPtr con información sobre el archivo especificado. No necesita ningún derecho de acceso al archivo para obtener esta información, pero necesita derechos de búsqueda en todos los directorios nombrados en la ruta que conduce al archivo. La estructura Tcl_StatBuf incluye información sobre el dispositivo, inodo (siempre 0 en Windows), modo de privilegios, nlink (siempre 1 en Windows), id de usuario (siempre 0 en Windows), id de grupo (siempre 0 en Windows), rdev (igual que el dispositivo en Windows), tamaño, último a

Acceso al tiempo de acceso, tiempo de modificación y tiempo de cambio de metadatos más reciente. Consulte **PORTABLE STAT RESULT API** para una descripción de cómo escribir código portátil para asignar y acceder a la estructura *Tcl_StatBuf*. Si el *path* existe, **Tcl_FSLstat** devuelve 0 y la estructura *statPtr* se llena con datos. De lo contrario, devuelve -1 y no se proporciona información de estadísticas. **Tcl_FSUtime** reemplaza la versión de la librería de *utime*. Esta función devuelve 0 en caso de éxito y -1 en caso de error (según la documentación de **utime**). Si es exitosa, actualiza los valores de **atime** y **mtime** del archivo dado. **Tcl_FSFileAttrsGet** implementa el acceso a las propiedades del subcomando **file** **attributes** para el hookable. La función adecuada para el sistema de archivos al cual pertenece *pathPtr* se llama. Si el resultado es **TCL_OK**, un valor se coloca en *objPtrRef*, que será válidamente temporal (a menos que se llame a **Tcl_IncrRefCount**). **Tcl_FSFileAttrsSet** implementa el acceso de escritura para el subcomando **file** **attributes** para el hookable. La función adecuada para el sistema de archivos al cual pertenece *pathPtr* se llama. **Tcl_FSFileAttrStrings** implementa parte del subcomando **file** **attributes** para el hookable. La función adecuada para el sistema de archivos al cual pertenece *pathPtr* se llama. El procedimiento llamado puede devolver un arreglo de strings o, en su lugar, devolver NULL y colocar una lista Tcl en *objPtrRef*. Tcl tomará esa lista y primero incrementará su cuenta de referencia antes de usarla. Después de completar el uso, Tcl decrementará su cuenta de referencia. Por lo tanto, si la lista debe ser liberada por Tcl cuando se termine, debe tener una cuenta de referencia de cero, y si no debe ser liberada, el sistema de archivos debe asegurarse de mantener una cuenta de referencia a ese valor. **Tcl_FSAccess** verifica si el proceso sería permitido leer, escribir o testear la existencia de un archivo (u otro objeto de sistema de archivos) cuyo nombre es *pathname*. Si *pathname* es un enlace simbólico en Unix, se evalúan los permisos del archivo referido por este enlace simbólico. En caso de éxito (todos los permisos solicitados), se devuelve 0. En caso de error (al menos un bit en el modo solicitado es denegado o ocurrió otro error), se devuelve -1. **Tcl_FSStat** llena la estructura *Tcl_StatBuf* con información sobre el archivo especificado. No se requieren derechos de acceso al archivo para obtener esta información, pero sí se requieren derechos de búsqueda en todos los directorios mencionados en el camino hacia el archivo. La estructura *Tcl_StatBuf* incluye información sobre el dispositivo, el inodo (0 en Windows), el modo de privilegio, el número de enlaces (1 en Windows), el ID de usuario (0 en Windows), el ID de grupo (0 en Windows), el rdev (igual que el dispositivo en Windows), el tamaño, el tiempo de acceso más reciente, el tiempo de modificación más reciente y el tiempo de cambio de metadatos más reciente. Consulte **PORTABLE STAT RESULT API** para una descripción de cómo escribir código portable para asignar y acceder a la estructura *Tcl_StatBuf*. Si *path* existe, **Tcl_FSStat** devuelve 0 y la estructura *statPtr* se llena con datos. De lo contrario, devuelve -1 y no se proporciona información de estadísticas. **Tcl_FSOpenFileChannel** abre un archivo especificado por *pathPtr* y devuelve un manejador de canal que se puede usar para leer y escribir en el archivo. Esta API se modela después de la función **fopen** de la biblioteca de entrada/salida estándar de Unix. La sintaxis y el significado de todos los argumentos son similares a los dados en el comando **open** de Tcl cuando se abre un archivo. Si ocurre un error al abrir el canal, **Tcl_FSOpenFileChannel** devuelve NULL y registra un código de error POSIX que se puede recuperar con **Tcl_GetErrno**. Además, si *interp* no es nulo, **Tcl_FSOpenFileChannel** deja un mensaje de error en el resultado de *interp* después de cualquier error. El nuevo canal no está registrado en el intérprete proporcionado; para registrarlo, use **Tcl_RegisterChannel**. Si uno de los canales estándar, **stdin**, **stdout** o **stderr**, fue previamente cerrado, la acción de crear el nuevo canal también lo asigna como sustituto de los canales estándar. **Tcl_FSGetCwd** reemplaza la versión de la función **getcwd** de la librería. Devuelve el directorio actual de la librería Tcl. Esto puede ser diferente al directorio de trabajo nativo, cuando el directorio actual no está en el sistema de archivos nativo. El resultado es un puntero a un *Tcl_Obj* que especifica el directorio actual, o NULL si el directorio no puede ser determinado. Si se devuelve NULL, se deja un mensaje de error en el resultado de *interp*. El resultado ya tiene su cuenta de referencia incrementada para el llamador. Cuando ya no se necesita, esa cuenta debe ser decrementada. Esto es necesario para la seguridad en multi-hilo, para permitir que múltiples hilos accedan a esta y a funciones relacionadas, asegurando que los resultados siempre sean válidos. **Tcl_FSChdir** reemplaza la versión de la función **chdir** de la librería. El camino se normaliza y luego se pasa al sistema de archivos que lo reclama. Si ese sistema de archivos no implementa esta función, Tcl recurre a una combinación de **stat** y **access** para verificar si el directorio existe y tiene permisos adecuados. Para ver los resultados, consulte la documentación de **chdir**. Si es exitosa, se mantiene un registro de la ruta exitosa en *cwdPathPtr* para uso posterior en **Tcl_FSGetCwd**. **Tcl_FSPathSeparator** devuelve el carácter separador utilizado para el elemento más específico de la ruta especificada por *pathPtr* (es decir, la última parte de la ruta). El separador se devuelve como un *Tcl_Obj* que contiene una cadena de longitud 1. Si la ruta es inválida, devuelve NULL. **Tcl_FSJoinPath** toma el *Tcl_Obj* dado, que debe ser una lista válida (que permite tener una cuenta de referencia cero), y devuelve el valor de ruta considerando los primeros *elements* elementos como segmentos válidos de ruta (cada segmento puede ser una ruta completa, una ruta parcial o un solo nombre posible de directorio o archivo). Si algún segmento es realmente una ruta absoluta, todos los segmentos anteriores son descartados. Si *elements* es menor que 0, usamos toda la lista. Es posible que el valor devuelto sea realmente un elemento de la lista dada, por lo que el llamador debe tener cuidado al incrementar la cuenta de referencia del resultado antes de liberar la lista. El valor devuelto, típicamente con una cuenta de referencia de cero (pero podría compartirse en ciertas condiciones), contiene la ruta unida. El llamador debe añadir una cuenta de referencia al valor antes de usarlo. En particular, el valor devuelto podría ser un elemento de la lista dada, por lo que liberar la lista podría liberar el valor prematuramente si no se ha tomado una cuenta de referencia. Si el número de elementos es cero, el valor devuelto será un objeto Tcl con valor vacío ("").y el llamante, que debe almacenarlo o llamar a ckfree para asegurarse de que se libera. Nuevamente, Tcl_FSGetNormalizedPath o Tcl_FSGetNativePath suelen ser funciones mejores para la mayoría de los propósitos.

Tcl_FSNewNativePath realiza algo así como lo inverso de las conversiones habituales obj->path->nativerep. Si algún código recupera una ruta en formato nativo (de, por ejemplo, readlink o un diálogo nativo), y esa ruta se va a utilizar a nivel de Tcl, entonces llamar a esta función es una forma eficiente de crear el tipo de valor de ruta apropiado.

El valor resultante es un valor de “ruta” puro, que solo recibirá una representación de cadena UTF-8 si así lo requiere algún código Tcl.

Tcl_FSGetNativePath es para uso de los sistemas de archivos nativos Win/Unix, de modo que puedan recuperar fácilmente la representación nativa (char* o TCHAR*) de una ruta. Esta función es un envoltorio de conveniencia alrededor de Tcl_FSGetInternalRep. Puede ser deseable en el futuro tener representaciones nativas no basadas en cadenas (por ejemplo, en macOS, una representación que use una estructura FSRef de fileSpec probablemente sería más eficiente). En Windows, una representación Unicode completa permitiría rutas de longitud ilimitada. Actualmente, la representación es simplemente una cadena de caracteres que puede contener la ruta relativa o una ruta completa, absoluta y normalizada en la codificación nativa (condiciones complejas dictan cuál de estas se proporcionará, por lo que ninguna puede confiarse, a menos que se sepa que la ruta es absoluta). Si necesita una ruta nativa que deba ser absoluta, entonces debe solicitar la versión nativa de una ruta normalizada. Si por alguna razón se necesita una versión no absoluta y no normalizada de la ruta, esta debe construirse por separado (por ejemplo, usando Tcl_FSGetTranslatedPath).

La representación nativa se almacena en caché para que las llamadas repetidas a esta función no requieran conversiones adicionales. El valor de retorno es propiedad de Tcl y tiene una vida útil equivalente a la del pathPtr pasado (a menos que sea una ruta relativa, en cuyo caso la representación nativa puede liberarse en cualquier momento en que cambie el cwd).

Tcl_FSFileSystemInfo devuelve una lista de dos elementos. El primer elemento es el nombre del sistema de archivos (por ejemplo, “native”, “vfs”, “zip”, o “prowrap”, quizás), y el segundo es el tipo particular de la ruta dada dentro de ese sistema de archivos (que depende del sistema de archivos). El segundo elemento puede estar vacío si el sistema de archivos no proporciona una categorización adicional de los archivos.

Se devuelve un valor de lista válido, a menos que el valor de la ruta no sea reconocido, en cuyo caso se devolverá NULL.

Tcl_FSGetFileSystemForPath devuelve un puntero al Tcl_Filesystem que acepta esta ruta como válida.

Si ningún sistema de archivos acepta la ruta, se devuelve NULL.

Tcl_FSGetPathType determina si la ruta dada es relativa al directorio actual, relativa al volumen actual o absoluta.

Devuelve uno de TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE o TCL_PATH_VOLUME_RELATIVE

LA API DEL SISTEMA DE ARCHIVOS VIRTUAL

Un sistema de archivos proporciona una estructura Tcl_Filesystem que contiene punteros a funciones que implementan las diversas operaciones en un sistema de archivos; estas operaciones se invocan según sea necesario por la capa genérica, lo que generalmente ocurre a través de las funciones enumeradas anteriormente.

Las estructuras Tcl_Filesystem se manipulan utilizando los siguientes métodos.

Tcl_FSRegister toma un puntero a una estructura de sistema de archivos y un dato opcional para asociar con ese sistema de archivos. Al llamar a esta función, Tcl adjuntará el sistema de archivos a la lista de sistemas de archivos conocidos, y se volverá completamente funcional de inmediato. Tcl no verifica si el mismo sistema de archivos está registrado múltiples veces (y en general, eso no es algo bueno de hacer). Se devolverá TCL_OK.

Tcl_FSUnregister elimina la estructura del sistema de archivos dada de la lista de sistemas de archivos conocidos, si es que se conoce, y devuelve TCL_OK. Si el sistema de archivos no está actualmente registrado, se devuelve TCL_ERROR.

Tcl_FSData devolverá el clientData asociado con el sistema de archivos dado, si ese sistema de archivos está registrado. De lo contrario, devolverá NULL.

Tcl_FSMountsChanged se utiliza para informar al núcleo de Tcl que el conjunto de puntos de montaje para el sistema de archivos dado (ya registrado) ha cambiado, y que las representaciones de archivos en caché pueden, por lo tanto, ya no ser correctas.

Las muchas funciones en esta estructura se dividen en tres categorías: funciones de infraestructura (casi todas las cuales deben implementarse), funciones operativas (que deben implementarse si se proporciona un sistema de archivos completo) y funciones de eficiencia (que solo deben implementarse si se pueden hacer de manera eficiente, o si tienen efectos secundarios que son requeridos por el sistema de archivos; Tcl tiene emulaciones menos eficientes a las que puede recurrir). Es importante notar que, en la versión actual de Tcl, la mayoría de estas soluciones alternativas solo se utilizan para manejar comandos iniciados en Tcl, no en C. Lo que esto significa es que, si se emite un comando file rename en Tcl, y los sistemas de archivos relevantes no implementan su Tcl_FSRenameFileProc, el núcleo de Tcl recurrirá a una combinación de otras funciones del sistema de archivos (utilizará Tcl_FSCopyFileProc seguido de Tcl_FSDeleteFileProc, y si Tcl_FSCopyFileProc no está implementado, hay una solución alternativa adicional). Sin embargo, si se emite un comando Tcl_FSRenameFileProc a nivel de C, no ocurren tales soluciones alternativas. Esto es cierto excepto para las últimas cuatro entradas en la tabla del sistema de archivos (lstat, load, getcwd y chdir) para las cuales sí ocurren soluciones alternativas a nivel de C.

Cualquier función que tome nombres de ruta en forma Tcl_Obj toma esos nombres en forma UTF-8. La API de infraestructura del sistema de archivos está diseñada para soportar la conversión eficiente y en caché de estas rutas UTF-8 a otras representaciones nativas.

MATCHINDIRECTORYPROC


Función para procesar una llamada a Tcl_FSMatchInDirectory.
    Si no se implementa, la funcionalidad de glob y copia recursiva faltará en el
    sistema de archivos (y esto puede afectar a comandos como encoding
    names que utilizan la funcionalidad de glob internamente).




typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);




La función debe devolver todos los archivos o directorios (u otros
    objetos del sistema de archivos) que coincidan con el patrón dado y concuerden
    con la especificación de types proporcionada. Hay dos formas en que se
    puede llamar a esta función. Si pattern es NULL, entonces pathPtr
    es una especificación de ruta completa de un solo archivo o directorio que
    debe verificarse en cuanto a existencia y tipo correcto. De lo contrario,
    pathPtr es un directorio, cuyo contenido la función debe buscar
    archivos o directorios que tengan el tipo correcto. En cualquier caso, se puede
    suponer que pathPtr no es NULL ni está vacío. Actualmente no está
    documentado si pathPtr tendrá o no un separador de archivos al final,
    por lo que el código debe ser flexible a ambas posibilidades.


El valor de retorno es un resultado estándar de Tcl que indica si
    ocurrió un error en el proceso de coincidencia. Los mensajes de error se
    colocan en interp, a menos que interp sea NULL, en cuyo caso no
    es necesario generar ningún mensaje de error; en un resultado TCL_OK,
    los resultados deben agregarse al valor de resultPtr dado (que se
    puede suponer que es una lista de Tcl válida y no compartida). Las coincidencias
    agregadas a resultPtr deben incluir cualquier prefijo de ruta dado en
    pathPtr (esto generalmente significa que serán especificaciones de
    ruta absoluta). Tenga en cuenta que si no se encuentran coincidencias, eso
    simplemente conduce a un resultado vacío; los errores solo se señalan para
    problemas reales de archivo o sistema de archivos que puedan ocurrir durante el
    proceso de coincidencia.


La estructura Tcl_GlobTypeData pasada en el parámetro
    types contiene los siguientes campos:




typedef struct Tcl_GlobTypeData {
    /* Corresponde a bcdpfls como en 'find -t' */
    int type;
    /* Corresponde a los permisos de archivo */
    int perm;
    /* Tipo mac aceptable */
    Tcl_Obj *macType;
    /* Creador mac aceptable */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;




Hay dos casos específicos que es importante manejar correctamente,
    ambos cuando types no es NULL. Los dos casos son cuando
    types->types & TCL_GLOB_TYPE_DIR o
    types->types & TCL_GLOB_TYPE_MOUNT son verdaderos (y en particular
    cuando las otras banderas son falsas). En el primero de estos casos, la
    función debe listar los directorios contenidos. Tcl utiliza esto para
    implementar globbing recursivo, por lo que es fundamental que los sistemas de
    archivos implementen la coincidencia de directorios correctamente. En el
    segundo de estos casos, con TCL_GLOB_TYPE_MOUNT, el sistema de
    archivos debe listar los puntos de montaje que se encuentran dentro del
    pathPtr dado (y en este caso, pathPtr no tiene por qué estar
    dentro del mismo sistema de archivos, a diferencia de todos los demás casos en
    los que se llama a esta función). El soporte para esto es crítico si Tcl
    quiere tener transiciones fluidas entre un sistema de archivos y otro.






UTIMEPROC


Función para procesar una llamada a Tcl_FSUtime. Se requiere
    para permitir el establecimiento (no la lectura) de tiempos con file
    mtime, file atime y la implementación de open-r/open-w/fcopy de
    file copy.




typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);




Los tiempos de acceso y modificación del archivo especificado por
    pathPtr deben cambiarse a los valores dados en la estructura
    tval.


El valor de retorno debe ser 0 en caso de éxito y -1 en caso de error,
    igual que con el utime del sistema.






LINKPROC


Función para procesar una llamada a Tcl_FSLink. Solo debe
    implementarse si el sistema de archivos admite enlaces, y de lo contrario puede
    ser NULL.




typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);




Si toPtr es NULL, se le está pidiendo a la función que lea el
    contenido de un enlace. El resultado es un Tcl_Obj que especifica el contenido
    del enlace dado por linkNamePtr, o NULL si no se pudo leer el enlace.
    El resultado es propiedad del llamador (y, por lo tanto, se debe incrementar
    su contador de referencias antes de devolverlo). Todos los llamadores deben
    llamar a Tcl_DecrRefCount en este resultado cuando ya no sea
    necesario. Si toPtr no es NULL, la función debe intentar crear un
    enlace. El resultado en este caso debe ser toPtr si el enlace fue
    exitoso y NULL en caso contrario. En este caso, el resultado no es propiedad
    del llamador (es decir, no se necesitan manipulaciones de recuento de
    referencias en ningún extremo). Consulte la documentación de
    Tcl_FSLink para la interpretación correcta de las banderas
    linkAction.






LISTVOLUMESPROC


Función para listar cualquier volumen de sistema de archivos agregado
    por este sistema de archivos. Solo debe implementarse si el sistema de
    archivos agrega volúmenes al principio del sistema de archivos, para que
    puedan ser devueltos por file volumes.




typedef Tcl_Obj *Tcl_FSListVolumesProc(void);




El resultado debe ser una lista de volúmenes agregados por este
    sistema de archivos, o NULL (o una lista vacía) si no se proporcionan
    volúmenes. Se considera que el valor de resultado es propiedad del sistema de
    archivos (no del núcleo de Tcl), pero se le debe dar un recuento de
    referencias para Tcl. Tcl utilizará el contenido de la lista y luego
    disminuirá ese recuento de referencias. Esto permite que los sistemas de
    archivos elijan si realmente desean retener una lista "global" de volúmenes
    o no (si no, generan la lista sobre la marcha y se la pasan a Tcl con un
    recuento de referencias de 1 y luego se olvidan de la lista; si sí, simplemente
    incrementan el recuento de referencias de su lista global y se la pasan a Tcl,
    que copiará el contenido y luego disminuirá el recuento de nuevo a donde
    estaba).


Por lo tanto, Tcl considera que los valores de retorno de este proc
    son de solo lectura.






FILEATTRSTRINGSPROC


Función para listar todas las cadenas de atributos que son válidas
    para este sistema de archivos. Si no se implementa, el sistema de archivos
    no admitirá el comando file attributes. Esto permite adjuntar
    información adicional arbitraria a los archivos en el sistema de archivos. Si
    no se implementa, no es necesario implementar los métodos get y
    set.




typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);




La función llamada puede devolver una matriz de cadenas o puede
    devolver NULL y colocar una lista de Tcl en objPtrRef. Tcl tomará
    esa lista y primero incrementará su recuento de referencias antes de usarla.
    Al finalizar ese uso, Tcl disminuirá su recuento de referencias. Por lo tanto,
    si la lista debe ser eliminada por Tcl cuando termine, debe tener un recuento
    de referencias de cero, y si la lista no debe ser eliminada, el sistema de
    archivos debe asegurarse de devolver un valor con un recuento de referencias
    de al menos uno.






FILEATTRSGETPROC


Función para procesar una llamada a Tcl_FSFileAttrsGet,
    utilizada por file attributes.




typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);




Devuelve un código de retorno estándar de Tcl. El valor del atributo
    recuperado, que corresponde al elemento de índice index en la lista
    devuelta por Tcl_FSFileAttrStringsProc, es un Tcl_Obj colocado en
    objPtrRef (si se devolvió TCL_OK) y es probable que tenga un
    recuento de referencias de cero. De cualquier manera, debemos almacenarlo en
    algún lugar (por ejemplo, el resultado de Tcl) o incrementar/decrementar su
    recuento de referencias para garantizar que se libere correctamente.






FILEATTRSSETPROC


Función para procesar una llamada a Tcl_FSFileAttrsSet,
    utilizada por file attributes. Si el sistema de archivos es de solo
    lectura, no es necesario implementarla.




typedef int Tcl_FSFileAttrsSetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj *objPtr);




El valor del atributo del elemento de índice index en la
    lista devuelta por Tcl_FSFileAttrStringsProc debe establecerse en el
    objPtr dado.
