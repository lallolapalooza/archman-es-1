DESCRIPCIÓN

Hay varias razones para llamar a las funciones de la API Tcl_FS (por ejemplo, Tcl_FSAccess y Tcl_FSStat) en lugar de llamar a funciones del nivel de sistema como access y stat directamente. Primero, estas funciones trabajarán de forma cross-platform, así que cualquier extensión que llame a estas funciones debería funcionar sin modificaciones en Unix y Windows. Segundo, la implementación de algunos de estos funciones en Windows corrige algunos errores en las llamadas del nivel de sistema. Tercero, estas llamadas de funciones tratan cualquier conversión de rutas de tipo "Utf a plataforma nativa" que pueda ser necesaria (y puede cachear los resultados de dichas conversiones para mayor eficiencia en llamadas posteriores). Cuarto, y tal vez más importante, todas estas funciones son "conscientes de sistema virtual". Cualquier sistema virtual (VFS por sus siglas) registrado (a través de Tcl_FSRegister) puede redirigir el acceso a archivos a medios o métodos alternativos. Esto significa que todas estas funciones (y por tanto, los correspondientes comandos file, glob, pwd, cd, open, etc. de Tcl) pueden operar sobre archivos que no son archivos nativos en el sistema de archivos nativo. Esto también significa que cualquier extensión de Tcl que acceda al sistema de archivos (FS por sus siglas) a través de esta API es automáticamente "consciente de sistema virtual". Claramente, si una extensión accede directamente al sistema de archivos nativo (a través de las APIs platform-specificas, por ejemplo), entonces Tcl no puede interceptar tales llamadas.

Si se han registrado adecuadamente los VFS, los "archivos" pueden, por ejemplo, ser remotos (por ejemplo, situados en un servidor FTP remoto) o archivados (por ejemplo, ubicados dentro de un archivo ZIP). Estos sistemas de archivos registrados proporcionan una tabla de funciones para implementar parte o todas las funciones mencionadas aquí. Finalmente, las llamadas a Tcl_FSStat y Tcl_FSLstat abstractan de lo que es realmente declarado el buffer struct stat, permitiendo que el mismo código se use tanto en sistemas con y sin soporte para archivos mayores de 2 GB.

La API Tcl_FS está Tcl_Obj-ificada y puede cachear representaciones internas y otros strings relacionados con rutas (por ejemplo, el directorio actual). Una consecuencia de esto es que no debe pasar valores con un contador de referencias cero a ninguna de estas funciones. Si se hubieran tratado tales llamadas, podría haber errores de memoria (en algunos casos, el código de sistema podría desechar una referencia al valor pasado y, por lo tanto, no asumir que después de cualquier de estas llamadas el valor tenga un contador de referencias cero - podría haber sido incrementado). O bien, podría haber un error de segmentación directo (o otro error de acceso a memoria) debido a que el valor se haya liberado durante el proceso complejo de manipulación del valor para garantizar que la ruta esté normalizada y absoluta para el sistema de archivos. La lección práctica a aprender es que:

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

es incorrecta y podría causar errores de memoria. El path debe tener su contador de referencias incrementado antes de pasarlo, o decrementado. Por esta razón, valores con un contador de referencias cero se consideran no válidos como rutas de sistema de archivos y llamar a cualquier función de API Tcl_FS con tales valores resultará en ninguna acción.

FUNCIONES DE API DE FS

Tcl_FSCopyFile intenta copiar el archivo dado por srcPathPtr a la ruta dada por destPathPtr. Si ambos caminos están en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), se llama al función de copiar archivo del sistema de archivos. De lo contrario, la función devuelve -1 y establece el valor global errno a EXDEV (código POSIX que indica una vinculación cruzada).

Tcl_FSCopyDirectory intenta copiar el directorio dado por srcPathPtr a la ruta dada por destPathPtr. Si ambos caminos están en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), se llama al función de copiar archivo del sistema de archivos. De lo contrario, la función devuelve -1 y establece el valor global errno a EXDEV (código POSIX que indica una vinculación cruzada).

Tcl_FSCreateDirectory intenta crear el directorio dado por pathPtr llamando al función de crear directorio del sistema de archivos que lo posee.

Tcl_FSDeleteFile intenta eliminar el archivo dado por pathPtr llamando al función de eliminar archivo del sistema de archivos que lo posee.

Tcl_FSRemoveDirectory intenta eliminar el directorio dado por pathPtr llamando al función de eliminar directorio del sistema de archivos que lo posee.

Tcl_FSRenameFile intenta renombrar el archivo o directorio dado por srcPathPtr a la ruta dada por destPathPtr. Si ambos caminos están en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), se llama al función de renombrar archivo del sistema de archivos. De lo contrario, la función devuelve -1 y establece el valor global errno a EXDEV (código POSIX que indica una vinculación cruzada).

Tcl_FSListVolumes llama a cada sistema de archivos que tenga un función de listar volúmenes no nulo y le pide a estos sistemas de archivos que devuelvan su lista de volúmenes raíz. Acaba acumulando los valores devueltos en una lista que se devuelve al llamador (con un contador de referencias de 0).

Tcl_FSEvalFileEx lee el archivo dado por pathPtr usando el código de codificación identificado por encodingName y evalúa su contenido como un script Tcl. Devuelve la misma información que Tcl_EvalObjEx. Si encodingName es NULL, se usa el código de codificación del sistema para leer el contenido del archivo. Si el archivo no se puede leer, se devuelve un mensaje de error de Tcl describiendo por qué el archivo no se pudo leer. El carácter de fin de archivo para los archivos es \x1A (^Z) para todos los sistemas. Si quieres usar \x1A en código para comparaciones de strings, puedes usarlo, que se substituirá de forma segura por el interprete Tcl en \x1A. Tcl_FSEvalFile es una versión más simple de Tcl_FSEvalFileEx que siempre usa el código de codificación del sistema al leer el archivo.

Tcl_FSLoadFile carga dinámicamente un archivo binario en memoria y devuelve las direcciones de dos procedimientos dentro de ese archivo, si están definidos. La función adecuada para el sistema de archivos al cual pertenece pathPtr se llama. Si ese sistema de archivos no implementa esta función (por ejemplo, los sistemas virtuales más comunes no la implementan debido a limitaciones del sistema operativo en la carga de código binario), Tcl intentará copiar el archivo a un directorio temporal y cargar ese archivo temporal. Tcl_FSUnloadFile inversa esta operación, pidiendo que el proceso elimine la biblioteca indicada por loadHandle de la ejecución. Debe recordarse que, a diferencia de la orden unload, esta no da oportunidad a la biblioteca de limpiar.

Ambas funciones anteriores devuelven un código de completación estándar de Tcl. Si ocurre un error, un mensaje de error se deja en el interp's result.

El token proporcionado por la variable indicada por loadHandlePtr puede usarse con Tcl_FindSymbol.

Tcl_FSMatchInDirectory se utiliza por el código de globbing para buscar todos los archivos que coincidan con un patrón dado en un directorio. La función adecuada para el sistema de archivos al cual pertenece pathPtr se llama.

El valor devuelto es un código de resultado estándar de Tcl indicando si hubo un error durante el globing. Los mensajes de error se colocan en interp (a menos que interp sea NULL, lo cual está permitido), pero los resultados buenos se colocan en el resultPtr dado.

Nota: el código de globbing implementa patrones recursivos internamente, por lo que esta función se pasará solo patrones simples, que se pueden comparar con la lógica de "string match". Para manejar la recursión, Tcl llama a esta función frecuentemente pidiendo solo directorios para devolver. Un caso especial de ser llamado con un patrón nulo indica que el camino debe ser verificado solo para el tipo correcto.

Tcl_FSLink reemplaza la versión del librero de readlink y lo extiende para soportar la creación de enlaces. La función adecuada para el sistema de archivos al cual pertenece linkNamePtr se llama.

Si el toPtr es NULL, se realiza una acción de "leer enlace". El resultado es un objeto Tcl_Obj que especifica el contenido del enlace dado por linkNamePtr, o NULL si el enlace no se puede leer. El resultado es todos los derechos de la llamada del usuario, que debería llamar Tcl_DecrRefCount cuando el resultado ya no es necesario. Si el toPtr no es NULL, Tcl debería crear un enlace de uno de los tipos que se pasen en el linkAction. Este flag es una combinación OR de TCL_CREATE_SYMBOLIC_LINK y TCL_CREATE_HARD_LINK. Si hay una elección (es decir, se pasan más de un flag), la convención Tcl es preferir enlaces simbólicos. Cuando se crea un enlace correctamente, el valor devuelto debería ser toPtr (que por lo tanto ya está propiedad de la llamada del usuario). Si no se puede crear, se devuelve NULL.

Tcl_FSLstat llena el estructura Tcl_StatBuf con información sobre el archivo especificado por statPtr. No se necesita ningún tipo de permisos sobre el archivo para obtener esta información, pero sí se necesita permisos de búsqueda sobre todos los directorios mencionados en la ruta hacia el archivo. La estructura Tcl_StatBuf incluye información sobre el dispositivo, el inodo (siempre 0 en Windows), el modo de privilegio, el número de referencias (siempre 1 en Windows), el usuario id (siempre 0 en Windows), el grupo id (siempre 0 en Windows), rdev (igual que el dispositivo en Windows), el tamaño,

Tiempo de acceso más reciente, tiempo de modificación más reciente y tiempo de cambio de metadatos más reciente. Consulta PORTABLE STAT RESULT API para una descripción de cómo escribir código portable para reservar y acceder a la estructura Tcl_StatBuf. Si path existe, Tcl_FSLstat devuelve 0 y la estructura statPtr se llena con datos. De lo contrario, devuelve -1 y no se proporciona ninguna información de estadísticas. Tcl_FSUtime reemplaza la versión del librero utime. Esta función devuelve 0 en éxito y -1 en error (como según la documentación de utime). Si es exitosa, actualiza los valores de atime y mtime de un archivo dado. Tcl_FSFileAttrsGet implementa el acceso lectura para el subcomando file attributes del hookable. La función correspondiente del sistema de archivos a quién pertenece pathPtr se llamará. Si el resultado es TCL_OK, se colocará un valor en objPtrRef, que será válidamente temporal (a menos que se llame Tcl_IncrRefCount). Tcl_FSFileAttrsSet implementa el acceso de escritura para el subcomando file attributes del hookable. La función correspondiente del sistema de archivos a quién pertenece pathPtr se llamará. Tcl_FSFileAttrStrings implementa parte del subcomando file attributes del hookable. La función correspondiente del sistema de archivos a quién pertenece pathPtr se llamará. El procedimiento llamado puede devolver una lista de strings o, en su lugar, devolver NULL y colocar un Tcl list en objPtrRef. Tcl tomará ese list y incrementará su contador de referencias antes de usarlo. Al finalizar su uso, Tcl decrementará su contador. Por lo tanto, si el list debe ser destruido por Tcl cuando termine, debe tener un contador de referencias igual a cero, y si no debe ser destruido, el sistema de archivos debe asegurar que mantenga un contador de referencias al valor. Tcl_FSAccess comprueba si el proceso sería permitido a leer, escribir o testear la existencia de un archivo (o otro objeto del sistema de archivos) cuyo nombre es pathname. Si pathname es un enlace simbólico en Unix, se testan las permiss de archivo referido por este enlace simbólico. En éxito (todas las permisos solicitadas), se devuelve 0. En error (al menos un bit en el modo solicitado es denegado o ocurre otro error), se devuelve -1. Tcl_FSStat llena la estructura Tcl_StatBuf con información sobre el archivo especificado. No se requiere acceso a este archivo para obtener la información, pero sí se requieren derechos de búsqueda en todos los directorios mencionados en la ruta. La estructura Tcl_StatBuf incluye información sobre el dispositivo, el inode (0 en Windows), el modo de privilegios, el nlink (1 en Windows), el UID (0 en Windows), el GID (0 en Windows), el rdev (igual que el dispositivo en Windows), el tamaño, el tiempo de acceso más reciente, el tiempo de modificación más reciente y el tiempo de cambio de metadatos más reciente. Consulta PORTABLE STAT RESULT API para una descripción de cómo escribir código portable para reservar y acceder a la estructura Tcl_StatBuf. Si path existe, Tcl_FSStat devuelve 0 y la estructura statPtr se llena con datos. De lo contrario, devuelve -1 y no se proporciona ninguna información de estadísticas. Tcl_FSOpenFileChannel abre un archivo especificado por pathPtr y devuelve un handle de canal que puede usarse para operaciones de lectura y escritura en el archivo. Esta API se modela después de la función fopen de la biblioteca de entrada/salida estándar de Unix. El sintaxis y significado de los argumentos son similares a los de la comanda open de Tcl cuando se abre un archivo. Si ocurre un error al abrir el canal, Tcl_FSOpenFileChannel devuelve NULL y registra un código de error POSIX que se puede recuperar con Tcl_GetErrno. Además, si interp no es NULL, Tcl_FSOpenFileChannel deja un mensaje de error en interp's resultado después de cualquier error. El canal recién creado no se registra en el interprete proporcionado; para registrarlo, use Tcl_RegisterChannel. Si uno de los canales estándar, stdin, stdout o stderr fue previamente cerrado, la acción de crear el nuevo canal también lo asigna como sustituto del canal estándar correspondiente. Tcl_FSGetCwd reemplaza la versión del librero getcwd. Devuelve el directorio de trabajo actual del librero Tcl. Este puede ser diferente al directorio de trabajo nativo, que se establece cuando el directorio de trabajo actual no está en el sistema de archivos nativo. El resultado es un puntero a un objeto Tcl Tcl_Obj que especifica el directorio actual, o NULL si no se pudo determinar el directorio. Si se devuelve NULL, se deja un mensaje de error en el resultado de interp. El resultado ya tiene su contador de referencias incrementado para el llamador. Cuando no se necesita más, ese contador debe decrementarse. Este es necesario para la seguridad en multi-threading, para permitir múltiples hilos acceder a esta y funciones relacionadas, asegurando que los resultados siempre sean válidos. Tcl_FSChdir reemplaza la versión del librero chdir. El camino se normaliza y luego se pasa al sistema de archivos que lo claim. Si ese sistema de archivos no implementa esta función, Tcl se fija a una combinación de stat y access para verificar si el directorio existe y tiene permisos adecuados. Para los resultados, consulta chdir documentación. Si es exitosa, se mantiene un registro de la ruta exitosa en cwdPathPtr para llamadas posteriores a Tcl_FSGetCwd. Tcl_FSPathSeparator devuelve el carácter separador que se usará para el elemento más específico de la ruta especificada por pathPtr (es decir, el último parte de la ruta). El separador se devuelve como un objeto Tcl con una cadena de longitud 1. Si la ruta es inválida, se devuelve NULL. Tcl_FSJoinPath toma el objeto Tcl dado, que debe ser un lista válido (permite tener un contador de referencias igual a cero), y devuelve el valor de la ruta considerando los primeros elements elementos como segmentos válidos de ruta (cada segmento puede ser una ruta completa, una ruta parcial o solo un nombre de directorio o archivo). Si cualquier segmento es realmente una ruta absoluta, todos los segmentos anteriores son descartados. Si elements es menor que 0, se usa el todo el list. Es posible que el valor devuelto sea realmente un elemento de la lista dada, por lo que el llamador debe incrementar el contador de referencias del valor antes de liberar el list. El valor devuelto, típicamente con un contador de referencias igual a cero (pero podría compartirse en ciertas condiciones), contiene la ruta unida. El llamador debe incrementar el contador de referencias antes de usarlo. En particular, el valor devuelto podría ser un elemento de la lista dada, por lo que liberar el list podría liberar el valor prematuramente si no se ha tomado ninguna referencia. Si el número de elementos es cero, el valor devuelto será un objeto Tcl Tcl_Obj con valor vacío. Tcl_FSSplitPath toma el objeto Tcl dado, que debería ser una ruta válida, y devuelve un valor de lista con cada segmento de la ruta como elemento. Devuelve un valor de lista con un contador de referencias igual a cero. Si el lenPtr es no NULL, el variable que apunta a él se actualiza con el número de elementos en el valor devuelto. Tcl_FSEqualPaths prueba si las dos rutas dadas representan el mismo objeto del sistema de archivos. Devuelve 1 si son iguales, 0 si son diferentes. Si alguno de las rutas es NULL, se devuelve 0 siempre. Tcl_FSGetNormalizedPath intenta extraer de la ruta dada una representación normalizada única, cuyo valor de cadena puede usarse como identificador único para el archivo. Devuelve la ruta normalizada, propiedad de Tcl, o NULL si la ruta no es válida o no puede ser convertida con éxito. La extracción de rutas absolutas y normalizadas es muy eficiente (porque el sistema de archivos opera internamente en estas representaciones), aunque el resultado cuando el sistema de archivos contiene muchos enlaces simbólicos no es necesariamente la versión más amigable de una ruta. El valor devuelto es propiedad de Tcl y tiene una vida útil equivalente a la del pathPtr pasado (a menos que ese sea un camino relativo, en el cual el valor normalizado puede ser liberado cualquier momento que cambie el cwd) - el llamador puede incrementar el contador de referencias si lo desea para mantener una copia más tiempo. Tcl_FSJoinToPath toma el valor dado, que generalmente debería ser una ruta válida o NULL, y une el array de segmentos de rutas dado. Devuelve un valor, típicamente con un contador de referencias igual a cero (pero podría compartirse en ciertas condiciones), con la ruta unida. El llamador debe incrementar el contador de referencias antes de usarlo. Si cualquier valor de los pasados a esta función (pathPtr o path elementos) tiene un contador de referencias igual a cero, se liberará cuando se devuelva esta función. Tcl_FSConvertToPathType intenta convertir el objeto Tcl dado a un tipo válido de ruta, considerando que el cwd puede haber cambiado incluso si este valor ya se supone de tipo correcto. El nombre de archivo puede comenzar con ~ (para indicar el directorio de usuario actual) o ~ (para indicar el directorio de cualquier usuario). Si la conversión es exitosa (es decir, el valor es una ruta válida en uno de los sistemas de archivos actuales), se devuelve TCL_OK. De lo contrario, se devuelve TCL_ERROR, y puede dejar un mensaje de error en el interprete. Tcl_FSGetInternalRep extrae la representación interna de un valor de ruta dado en el sistema de archivos dado. Si el valor de ruta pertenece a un sistema de archivos diferente, se devuelve NULL. Si la representación interna es actualmente NULL, se intenta generarla llamando a Tcl_FSCreateInternalRepProc del sistema de archivos. Devuelve NULL o una representación válida de la ruta interna. Esta representación interna se cachea, por lo que las llamadas repetidas a esta función no requieren convertir de nuevo. Tcl_FSGetTranslatedPath intenta extraer la ruta traducida del objeto Tcl dado. Si la traducción es exitosa (es decir, el valor es una ruta válida), se devuelve el valor. De lo contrario, se devuelve NULL, y puede dejar un mensaje de error en el interprete. Una ruta traducida es una que no contiene secuencias como ~ o ~user (estas se han expandido a su representación actual en el sistema de archivos). El valor devuelto es propiedad del llamador, que debe almacenarlo o llamar a Tcl_DecrRefCount para asegurar que se libere la memoria. Esta función es de poca utilidad práctica, y Tcl_FSGetNormalizedPath o Tcl_FSGetNativePath son generalmente funciones mejores para usar en mayoría de los casos. Tcl_FSGetTranslatedStringPath realiza lo mismo que Tcl_FSGetTranslatedPath, pero devuelve un string o NULL. El string devuelto es dinámicamente alojado.ubicado y propiedad del llamador, que debe almacenarlo o llamar a ckfree para asegurarse de que se libere. Nuevamente, Tcl_FSGetNormalizedPath o Tcl_FSGetNativePath son generalmente mejores funciones para usar en la mayoría de los propósitos.

Tcl_FSNewNativePath realiza algo parecido a la inversa de las conversiones habituales obj->path->nativerep. Si algún código recupera una ruta en formato nativo (desde, por ejemplo, readlink o un cuadro de diálogo nativo) y esa ruta se va a usar a nivel de Tcl, llamar a esta función es una forma eficiente de crear el tipo de valor de ruta apropiado.

El valor resultante es un valor de tipo "ruta" puro, que solo recibirá una representación de cadena UTF-8 si es requerido por algún código de Tcl.

Tcl_FSGetNativePath es para uso de los sistemas de archivos nativos Win/Unix, para que puedan recuperar fácilmente la representación nativa (char* o TCHAR*) de una ruta. Esta función es un envoltorio de conveniencia alrededor de Tcl_FSGetInternalRep. Puede ser deseable en el futuro tener representaciones nativas no basadas en cadenas (por ejemplo, en macOS, una representación que use una estructura FSRef de fileSpec sería probablemente más eficiente). En Windows, una representación Unicode completa permitiría rutas de longitud ilimitada. Actualmente, la representación es simplemente una cadena de caracteres que puede contener la ruta relativa o una ruta completa, absoluta y normalizada en la codificación nativa (condiciones complejas dictan cuál de estas se proporcionará, por lo que no se puede confiar en ninguna de ellas, a menos que se sepa que la ruta es absoluta). Si necesita una ruta nativa que deba ser absoluta, entonces debe solicitar la versión nativa de una ruta normalizada. Si por alguna razón se necesita una versión de la ruta no absoluta y no normalizada, esta debe construirse por separado (por ejemplo, usando Tcl_FSGetTranslatedPath).

La representación nativa se almacena en caché para que las llamadas repetidas a esta función no requieran conversiones adicionales. El valor de retorno es propiedad de Tcl y tiene una vida útil equivalente a la del pathPtr pasado (a menos que sea una ruta relativa, en cuyo caso la representación nativa puede liberarse en cualquier momento que cambie el cwd).

Tcl_FSFileSystemInfo devuelve una lista de dos elementos. El primer elemento es el nombre del sistema de archivos (por ejemplo, "native", "vfs", "zip" o "prowrap", quizás), y el segundo es el tipo particular de la ruta dada dentro de ese sistema de archivos (que depende del sistema de archivos). El segundo elemento puede estar vacío si el sistema de archivos no proporciona una categorización adicional de los archivos.

Se devuelve un valor de lista válido, a menos que el valor de la ruta no sea reconocido, en cuyo caso se devolverá NULL.

Tcl_FSGetFileSystemForPath devuelve un puntero al Tcl_Filesystem que acepta esta ruta como válida.

Si ningún sistema de archivos acepta la ruta, se devuelve NULL.

Tcl_FSGetPathType determina si la ruta dada es relativa al directorio actual, relativa al volumen actual o absoluta.

Devuelve uno de TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE o TCL_PATH_VOLUME_RELATIVE

LA API DEL SISTEMA DE ARCHIVOS VIRTUAL

Un sistema de archivos proporciona una estructura Tcl_Filesystem que contiene punteros a funciones que implementan las diversas operaciones en un sistema de archivos; estas operaciones se invocan según sea necesario por la capa genérica, lo que generalmente ocurre a través de las funciones listadas anteriormente.

Las estructuras Tcl_Filesystem se manipulan utilizando los siguientes métodos.

Tcl_FSRegister toma un puntero a una estructura de sistema de archivos y un dato opcional para asociar con ese sistema de archivos. Al llamar a esta función, Tcl adjuntará el sistema de archivos a la lista de sistemas de archivos conocidos y se volverá completamente funcional inmediatamente. Tcl no verifica si el mismo sistema de archivos se registra múltiples veces (y en general, eso no es algo bueno de hacer). Se devolverá TCL_OK.

Tcl_FSUnregister elimina la estructura de sistema de archivos dada de la lista de sistemas de archivos conocidos, si se conoce, y devuelve TCL_OK. Si el sistema de archivos no está registrado actualmente, se devuelve TCL_ERROR.

Tcl_FSData devolverá el clientData asociado con el sistema de archivos dado, si ese sistema de archivos está registrado. De lo contrario, devolverá NULL.

Tcl_FSMountsChanged se utiliza para informar al núcleo de Tcl que el conjunto de puntos de montaje para el sistema de archivos dado (ya registrado) ha cambiado, y que, por lo tanto, las representaciones de archivos en caché pueden ya no ser correctas.

Las muchas funciones en esta estructura se dividen en tres categorías: funciones de infraestructura (casi todas las cuales deben implementarse), funciones operativas (que deben implementarse si se proporciona un sistema de archivos completo) y funciones de eficiencia (que solo necesitan implementarse si se pueden hacer de manera eficiente, o si tienen efectos secundarios que son requeridos por el sistema de archivos; Tcl tiene emulaciones menos eficientes a las que puede recurrir). Es importante notar que, en la versión actual de Tcl, la mayoría de estas soluciones alternativas solo se utilizan para manejar comandos iniciados en Tcl, no en C. Lo que esto significa es que, si se emite un comando file rename en Tcl, y los sistemas de archivos relevantes no implementan su Tcl_FSRenameFileProc, el núcleo de Tcl recurrirá a una combinación de otras funciones del sistema de archivos (utilizará Tcl_FSCopyFileProc seguido de Tcl_FSDeleteFileProc, y si Tcl_FSCopyFileProc no está implementado, hay una solución alternativa adicional). Sin embargo, si se emite un comando Tcl_FSRenameFileProc a nivel de C, no ocurren tales soluciones alternativas. Esto es cierto excepto por las últimas cuatro entradas en la tabla del sistema de archivos (lstat, load, getcwd y chdir) para las cuales efectivamente ocurren soluciones alternativas a nivel de C.

Cualquier función que tome nombres de ruta en forma Tcl_Obj toma esos nombres en forma UTF-8. La API de infraestructura del sistema de archivos está diseñada para admitir la conversión eficiente y en caché de estas rutas UTF-8 a otras representaciones nativas.

INFRAESTRUCTURA DEL SISTEMA DE ARCHIVOS

Estos campos contienen información básica sobre la estructura del sistema de archivos y direcciones de funciones que se utilizan para asociar un sistema de archivos particular con una ruta de archivo, y para manejar el manejo interno de representaciones de rutas, por ejemplo, copiar y liberar dichas representaciones.

TYPENAME

El campo typeName contiene una cadena terminada en nulo que identifica el tipo de sistema de archivos implementado, por ejemplo, "nativo", "zip" o "vfs".

STRUCTURE LENGTH

El campo structureLength generalmente se implementa como sizeof(Tcl_Filesystem), y está ahí para permitir una mayor compatibilidad binaria hacia atrás si el tamaño de la estructura cambia en una futura versión de Tcl.

VERSION

El campo version debe establecerse en TCL_FILESYSTEM_VERSION_1.

PATHINFILESYSTEMPROC

El campo pathInFilesystemProc contiene la dirección de una función que se llama para determinar si un valor de ruta dado pertenece o no a este sistema de archivos. Tcl solo llamará al resto de las funciones del sistema de archivos con una ruta para la cual esta función ha devuelto TCL_OK. Si la ruta no pertenece, se debe devolver -1 (el comportamiento de Tcl para cualquier otro valor de retorno no está definido). Si se devuelve TCL_OK, entonces el parámetro de salida opcional clientDataPtr se puede usar para devolver una representación interna (específica del sistema de archivos) de la ruta, que se almacenará en caché dentro del valor de la ruta y podrá ser recuperada eficientemente por las otras funciones del sistema de archivos. Tcl almacenará simultáneamente en caché el hecho de que esta ruta pertenece a este sistema de archivos. Dichas cachés se invalidan cuando se agregan o eliminan estructuras de sistema de archivos de la lista interna de sistemas de archivos conocidos de Tcl.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

        ClientData clientData);

Función para convertir la representación interna a una ruta normalizada. Solo se requiere si el sistema de archivos crea valores de ruta puros sin representación de cadena/ruta. El valor de retorno es un valor de Tcl cuya representación de cadena es la ruta normalizada.

        Tcl_Obj *pathPtr);

NORMALIZEPATHPROC

Función para normalizar una ruta. Debe implementarse para todos los sistemas de archivos que puedan tener múltiples representaciones de cadena para el mismo valor de ruta. En Tcl, cada "ruta" debe tener una única representación de cadena "normalizada". Dependiendo del sistema de archivos, puede haber más de una representación de cadena no normalizada que se refiera a esa ruta (por ejemplo, una ruta relativa, una ruta con mayúsculas y minúsculas diferentes si el sistema de archivos no distingue entre mayúsculas y minúsculas, una ruta que contenga una referencia a un directorio de inicio como "~", una ruta que contenga enlaces simbólicos, etc.). Si el último componente de la ruta es un enlace simbólico, no debe convertirse en el valor al que apunta (pero su capitalización u otros aspectos deben hacerse únicos). Todos los demás componentes de la ruta deben convertirse de enlaces simbólicos. Esta única excepción es necesaria para coincidir con la semántica de Tcl con file delete, file rename, file copy que operan sobre enlaces simbólicos. Esta función puede llamarse con nextCheckpoint al principio de la ruta (es decir, cero), al final de la ruta o en cualquier separador de archivo intermedio en la ruta. Nunca apuntará a ninguna otra posición arbitraria en la ruta. En el último de los tres casos válidos, la implementación puede asumir que la ruta hasta e incluyendo el separador de archivos se conoce y está normalizada.

    int perm;
    /* Tipo aceptado de mac */
    Tcl_Obj *macType;
    /* Creador aceptado de mac */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Hay dos casos específicos que es importante manejar correctamente, ambos cuando types no es nulo. Los dos casos son cuando types->types & TCL_GLOB_TYPE_DIR o types->types & TCL_GLOB_TYPE_MOUNT son verdaderos (y en particular cuando otros flags son falsos). En el primero de estos casos, la función debe listar los directorios contenidos. Tcl usa esto para implementar la globbing recursiva, así que es crucial que los sistemas de archivos implementen correctamente la coincidencia de directorios. En el segundo de estos casos, con TCL_GLOB_TYPE_MOUNT, el sistema de archivos debe listar los puntos de montaje que se encuentren dentro del pathPtr dado (y en este caso, pathPtr no necesariamente debe estar en el mismo sistema de archivos - diferente a todos los demás casos en los cuales esta función se llama). El soporte para esto es crítico si Tcl quiere tener transiciones suaves entre diferentes sistemas de archivos.

UTIMEPROC

Función para procesar una llamada a Tcl_FSUtime. Es requerida para permitir la configuración (no lectura) de las fechas de última modificación y de última acceso de archivos, así como la implementación de la operación de copia de archivos file copy (open-r, open-w, fcopy).

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

Los tiempos de acceso y modificación del archivo especificado por pathPtr deben cambiarse a los valores dados en la estructura tval.

El valor de retorno debe ser 0 en caso de éxito y -1 en caso de error, como con el sistema utime.

LINKPROC

Función para procesar una llamada a Tcl_FSLink. Debe implementarse solo si el sistema de archivos soporta enlaces, y puede ser nulo en otros casos.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

Si toPtr es NULL, la función se está preguntando por el contenido de un enlace. El resultado es un Tcl_Obj que especifica el contenido del enlace dado por linkNamePtr, o NULL si el enlace no puede ser leído. El resultado es propiedad del llamador (y por lo tanto debe incrementar su contador de referencias antes de ser devuelto). Cualquier llamador debe llamar a Tcl_DecrRefCount sobre este resultado cuando ya no lo necesite. Si toPtr no es NULL, la función debe intentar crear un enlace. En este caso, el resultado debe ser toPtr si el enlace fue exitoso y NULL de lo contrario. En este caso, el resultado no es propiedad del llamador (es decir, no hay manipulaciones de contadores de referencias en ambos lados). Véase la documentación para Tcl_FSLink para interpretar correctamente los flags de linkAction.

LISTVOLUMESPROC

Función para listar cualquier volumen de sistema de archivos agregado por este sistema de archivos. Debe implementarse solo si el sistema de archivos agrega volúmenes al inicio del sistema de archivos, así puedan ser devueltos por file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

El resultado debe ser una lista de volúmenes agregados por este sistema de archivos, o NULL (o una lista vacía) si no se proporcionan volúmenes. El valor de retorno se considera propiedad del sistema de archivos (no del núcleo de Tcl), pero debe proporcionarse un contador de referencias para Tcl. Tcl usará el contenido de la lista y luego decrementará ese contador. Esto permite a los sistemas de archivos elegir si realmente quieren mantener una "lista global" de volúmenes o no (si no, generan la lista sobre la marcha y la pasan a Tcl con un contador de referencias de 1 y luego olvidan la lista; si sí, simplemente incrementan el contador de referencias de su lista global y la pasan a Tcl que copiará el contenido y luego decrementará el contador de vuelta a donde estaba).

Por lo tanto, Tcl considera los valores de retorno de esta proc como lectores.

FILEATTRSTRINGSPROC

Función para listar todas las cadenas de atributos válidas para este sistema de archivos. Si no se implementa, el sistema de archivos no soportará la funcionalidad file attributes. Esto permite agregar información arbitraria a archivos en el sistema de archivos. Si no se implementa, no es necesario implementar los métodos get y set.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

La función llamada puede devolver un arreglo de strings o, en cambio, puede devolver NULL y colocar un listado Tcl en el objPtrRef. Tcl tomará ese listado y primero incrementará su contador de referencias antes de usarlo. Al finalizar el uso, Tcl decrementará su contador de referencias. Por lo tanto, si el listado debe ser destruido por Tcl cuando esté terminado, debe tener un contador de referencias de cero, y si no debe ser destruido, el sistema de archivos debe asegurar que devuelva un valor con un contador de referencias de al menos uno.

FILEATTRSGETPROC

Función para procesar una llamada a Tcl_FSFileAttrsGet, utilizada por file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

Devuelve un código de retorno estándar de Tcl. El valor del atributo obtenido, que corresponde al elemento index-ésimo en la lista devuelta por Tcl_FSFileAttrStringsProc, se coloca en objPtrRef (si se devolvió TCL_OK), y es probable que tenga un contador de referencias de cero. De cualquier manera, debemos almacenar este valor en algún lugar (por ejemplo, en el resultado de Tcl) o incrementar/decrementar su contador de referencias para asegurar que se destruya correctamente.

FILEATTRSSETPROC

Función para procesar una llamada a Tcl_FSFileAttrsSet, utilizada por file attributes. Si el sistema de archivos es solo lectura, no es necesario implementar esta.

typedef int Tcl_FSFileAttrsSetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj *objPtr);

El valor del atributo del elemento index-ésimo en la lista devuelta por Tcl_FSFileAttrStringsProc debe ser establecido en el objPtr dado.

EFICIENCIA DEL SISTEMA DE ARCHIVOS

Estas funciones no necesitan ser implementadas para un sistema de archivos particular, ya que el núcleo tiene una implementación de respaldo disponible. Consulte cada descripción individual para conocer las consecuencias de dejar el campo NULL.

LSTATPROC

Función para procesar una llamada a Tcl_FSLstat. Si no se implementa, Tcl intentará usar el statProc definido anteriormente en su lugar. Por lo tanto, solo necesita ser implementado si un sistema de archivos puede diferenciar entre las llamadas stat y lstat.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

El comportamiento de esta función es muy similar al de Tcl_FSStatProc definido anteriormente, excepto que si se aplica a un enlace simbólico, devuelve información sobre el enlace, no sobre el archivo de destino.

COPYFILEPROC

Función para procesar una llamada a Tcl_FSCopyFile. Si no se implementa, Tcl recurrirá a open-r, open-w y fcopy como mecanismo de copia. Por lo tanto, solo necesita ser implementado si el sistema de archivos puede realizar esa acción de manera más eficiente.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso de copia. Tenga en cuenta que destPathPtr es el nombre del archivo que se convertirá en la copia de srcPathPtr. Nunca es el nombre de un directorio en el que se pueda copiar srcPathPtr (es decir, la función es mucho más simple que el subcomando file copy a nivel de Tcl). Tenga en cuenta que, si el sistema de archivos admite enlaces simbólicos, Tcl siempre llamará a esta función y no a copyDirectoryProc cuando sea necesario copiarlos (incluso si son enlaces simbólicos a directorios). Finalmente, si el sistema de archivos determina que no puede admitir la acción file copy, llamar a Tcl_SetErrno(EXDEV) y devolver un resultado no TCL_OK le indicará a Tcl que utilice sus mecanismos de respaldo estándar.

RENAMEFILEPROC

Función para procesar una llamada a Tcl_FSRenameFile. Si no se implementa, Tcl recurrirá a un mecanismo de copia y eliminación. Por lo tanto, solo necesita ser implementado si el sistema de archivos puede realizar esa acción de manera más eficiente.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso de renombrado. Si el sistema de archivos determina que no puede admitir la acción file rename, llamar a Tcl_SetErrno(EXDEV) y devolver un resultado no TCL_OK le indicará a Tcl que utilice sus mecanismos de respaldo estándar.

COPYDIRECTORYPROC

Función para procesar una llamada a Tcl_FSCopyDirectory. Si no se implementa, Tcl recurrirá a un mecanismo recursivo de file mkdir, file copy. Por lo tanto, solo necesita ser implementado si el sistema de archivos puede realizar esa acción de manera más eficiente.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso de copia. Si ocurre un error, el nombre del archivo o directorio que causó el error debe colocarse en errorPtr. Tenga en cuenta que destPathPtr es el nombre del directorio que se convertirá en la imagen especular de srcPathPtr. No es el nombre de un directorio en el que se pueda copiar srcPathPtr (es decir, la función es mucho más simple que el subcomando file copy a nivel de Tcl). Finalmente, si el sistema de archivos determina que no puede admitir la acción de copia de directorios, llamar a Tcl_SetErrno(EXDEV) y devolver un resultado no TCL_OK le indicará a Tcl que utilice sus mecanismos de respaldo estándar.

LOADFILEPROC

Función para procesar una llamada a Tcl_FSLoadFile. Si no se implementa, Tcl recurrirá a una copia a un archivo temporal nativo seguido de un Tcl_FSLoadFile en esa copia temporal. Por lo tanto, solo necesita ser implementado si el sistema de archivos puede cargar código directamente, o puede ser implementado simplemente para devolver TCL_ERROR para deshabilitar completamente la funcionalidad de carga en este sistema de archivos.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Devuelve un código de finalización estándar de Tcl. Si ocurre un error, se deja un mensaje de error en el resultado del interp. La función carga dinámicamente un archivo de código binario en la memoria. En una carga exitosa, handlePtr debe llenarse con un token para el archivo cargado dinámicamente, y unloadProcPtr debe llenarse con la dirección de un procedimiento. El procedimiento de descarga se llamará con el Tcl_LoadHandle dado como su único parámetro cuando Tcl necesite descargar el archivo. Por ejemplo, para el sistema de archivos nativo, el Tcl_LoadHandle devuelto es actualmente un token que se puede usar en el TclpFindSymbol privado para acceder a funciones en el nuevo código. Cada sistema de archivos es libre de definir el Tcl_LoadHandle según lo requiera. Finalmente, si el sistema de archivos determina que no puede admitir la acción de carga de archivos, llamar a Tcl_SetErrno(EXDEV) y devolver un resultado no TCL_OK le indicará a Tcl que utilice sus mecanismos de respaldo estándar.

UNLOADFILEPROC

Función para descargar un archivo cargado previamente con éxito. Si la carga fue implementada, entonces esta también debería ser implementada, si hay alguna acción de limpieza requerida.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

Función para procesar una llamada a Tcl_FSGetCwd. La mayoría de los sistemas de archivos no necesitan implementar esto. Generalmente solo se llamará una vez, si getcwd se llama antes que chdir. Puede ser NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

Si el sistema de archivos admite una noción nativa de directorio de trabajo actual (que podría cambiar independientemente de Tcl), esta función debe devolver ese cwd como resultado, o NULL si no se pudo determinar el directorio actual (por ejemplo, el usuario no tiene permisos apropiados en el directorio cwd). Si se devuelve NULL, se deja un mensaje de error en el resultado del interp.

CHDIRPROC

Función para procesar una llamada a Tcl_FSChdir. Si los sistemas de archivos no implementan esto, se emulará mediante una serie de verificaciones de acceso al directorio. De lo contrario, los sistemas de archivos virtuales que lo implementen solo necesitan responder con un resultado positivo si pathPtr es un directorio válido y accesible en su sistema de archivos. No necesitan recordar el resultado, ya que se recordará automáticamente para su uso por Tcl_FSGetCwd. Los sistemas de archivos reales deben llevar a cabo la acción correcta (es decir, llamar a la API de sistema chdir correcta).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

El Tcl_FSChdirProc cambia el directorio de trabajo actual de la aplicación al valor especificado en pathPtr. La función devuelve -1 en caso de error o 0 en caso de éxito.
