ARGUMENTOS

const Tcl_ChannelType *typePtr (entrada)
Punta a una estructura que contiene las direcciones de los procedimientos que se pueden llamar para realizar E/S y otras funciones en el canal.
const char *channelName (entrada)
El nombre de este canal, como por ejemplo file3; no debe estar siendo utilizado por ningún otro canal. Puede ser NULL, en cuyo caso el canal se crea sin nombre. Si al canal creado se le asigna uno de los canales estándar (stdin, stdout o stderr), el nombre del canal asignado será el nombre del canal estándar.
ClientData instanceData (entrada)
Valor arbitrario de una palabra para asociar con este canal. Este valor se pasa a los procedimientos en typePtr cuando se invocan.
int mask (entrada)
Combinación OR de TCL_READABLE y TCL_WRITABLE para indicar si un canal es legible y escribible.
Tcl_Channel channel (entrada)
El canal sobre el que operar.
int direction (entrada)
TCL_READABLE significa que se desea el descriptor de entrada; TCL_WRITABLE significa que se desea el descriptor de salida.
ClientData *handlePtr (salida)
Punta a la ubicación donde se debe almacenar el descriptor específico del sistema operativo.
int size (entrada)
El tamaño, en bytes, de los búferes a asignar en este canal.
int mask (entrada)
Una combinación OR de TCL_READABLE, TCL_WRITABLE y TCL_EXCEPTION que indica los eventos que han ocurrido en este canal.

Intérprete actual. (puede ser NULL)

Nombre de la opción inválida.

Opciones específicas (palabras separadas por espacios, sin el carácter “-”) para añadir a la lista de opciones genéricas estándar. Puede ser NULL solo para el mensaje de error de opciones genéricas.

DESCRIPCIÓN

Tcl utiliza una arquitectura de canales de dos capas. Proporciona una capa superior genérica para permitir que los programas C y Tcl realicen entradas y salidas utilizando las mismas API para una variedad de archivos, dispositivos, sockets, etc. Las API genéricas de C se describen en la entrada del manual para Tcl_OpenFileChannel.

La capa inferior proporciona controladores de canales específicos del tipo para cada tipo de dispositivo soportado en cada plataforma. Esta entrada del manual describe las API de C utilizadas para la comunicación entre la capa genérica y los controladores de canales específicos del tipo. También explica cómo se pueden añadir nuevos tipos de canales proporcionando nuevos controladores de canales.

Los controladores de canales constan de varios componentes: Primero, cada controlador de canales proporciona una estructura Tcl_ChannelType que contiene punteros a funciones que implementan las diversas operaciones utilizadas por la capa genérica para comunicarse con el controlador de canales. La estructura Tcl_ChannelType y las funciones a las que hace referencia se describen en la sección TCL_CHANNELTYPE, más abajo.

Segundo, los controladores de canales suelen proporcionar un comando Tcl para crear instancias de ese tipo de canal. Por ejemplo, el comando Tcl open crea canales que utilizan los controladores de canales de archivo y comando, y el comando Tcl socket crea canales que utilizan sockets TCP para la comunicación de red.

Tercero, un controlador de canales proporciona opcionalmente una función C para abrir instancias de canal de ese tipo. Por ejemplo, Tcl_OpenFileChannel abre un canal que utiliza el controlador de canales de archivo, y Tcl_OpenTcpClient abre un canal que utiliza el protocolo de red TCP. Estas funciones de creación suelen utilizar Tcl_CreateChannel internamente para abrir el canal.

Para añadir un nuevo tipo de canal, debe implementar una API C o un comando Tcl que abra un canal invocando Tcl_CreateChannel. Cuando su controlador llama a Tcl_CreateChannel, pasa una estructura Tcl_ChannelType que describe los procedimientos de E/S del controlador. La capa genérica invocará entonces las funciones referenciadas en esa estructura para realizar operaciones en el canal.

Tcl_CreateChannel abre un nuevo canal y asocia los typePtr y instanceData proporcionados con él. El canal se abre en el modo indicado por mask. Para una discusión sobre los controladores de canales, sus operaciones y la estructura Tcl_ChannelType, consulte la sección TCL_CHANNELTYPE, más abajo.

Tcl_CreateChannel interactúa con el código que gestiona los canales estándar. Una vez que un canal estándar se inicializó a través de una llamada a Tcl_GetStdChannel o una llamada a Tcl_SetStdChannel, el cierre de este canal estándar hará que la siguiente llamada a Tcl_CreateChannel convierta también el nuevo canal en el nuevo canal estándar. Consulte Tcl_StandardChannels para un tratado general sobre los canales estándar y el comportamiento de la biblioteca Tcl con respecto a ellos.

Tcl_GetChannelInstanceData devuelve los datos de instancia asociados con el canal en channel. Esto es lo mismo que el argumento instanceData en la llamada a Tcl_CreateChannel que creó este canal.

Tcl_GetChannelType devuelve un puntero a la estructura Tcl_ChannelType utilizada por el canal en el argumento channel. Esto es lo mismo que el argumento typePtr en la llamada a Tcl_CreateChannel que creó este canal.

Tcl_GetChannelName devuelve una cadena que contiene el nombre asociado con el canal, o NULL si el argumento channelName de Tcl_CreateChannel era NULL.

TCL_GETCHANNELOPTIONS

Este conjunto de funciones proporciona acceso a varias piezas de información sobre un canal Tcl y su controlador de canal.

Tcl_GetChannelOption recupera el valor de una opción especificada para un canal. La opción se especifica mediante una cadena que puede ser una de las opciones estándar de canal o una opción específica del controlador del canal. La cadena recuperada se almacena en el búfer especificado por valueTcl_ObjPtr, y se devuelve TCL_OK. Si la opción no se encuentra o si se produce un error, se devuelve TCL_ERROR.

Tcl_GetChannelHandle devuelve un puntero a la información del controlador de dispositivo para el canal dado y la dirección especificada (TCL_READABLE o TCL_WRITABLE). El controlador de canal almacenará la información de este manejador en la ubicación especificada por handlePtr y devolverá TCL_OK. Si el canal no tiene un manejador de dispositivo para la dirección especificada, entonces se devolverá TCL_ERROR. Los diferentes controladores de canal devolverán diferentes tipos de manejadores. Consulte las entradas del manual para cada controlador para determinar qué tipo de manejador se devuelve.

Tcl_GetChannelThread devuelve el id del hilo que gestiona actualmente el channel especificado. Esto permite a los controladores de canal enviar sus eventos de archivo a la cola de eventos correcta incluso para un núcleo multihilo.

Tcl_GetChannelMode devuelve una combinación OR de TCL_READABLE y TCL_WRITABLE, que indica si el canal está abierto para entrada y salida.

Tcl_GetChannelBufferSize devuelve el tamaño, en bytes, de los búferes asignados para almacenar la entrada o salida en el channel. Si el valor no fue establecido por una llamada anterior a Tcl_SetChannelBufferSize, descrita a continuación, entonces se devuelve el valor predeterminado de 4096.

Tcl_SetChannelBufferSize establece el tamaño, en bytes, de los búferes que se asignarán en operaciones posteriores en el canal para almacenar entrada o salida. El argumento size debe estar entre uno y un millón, permitiendo búferes de un byte a un millón de bytes. Si size está fuera de este rango, Tcl_SetChannelBufferSize establece el tamaño del búfer en 4096.

Tcl_NotifyChannel es llamada por un controlador de canal para indicar a la capa genérica que los eventos especificados por mask han ocurrido en el canal. Los controladores de canal son responsables de invocar esta función siempre que los manejadores de canal necesiten ser llamados para el canal (o se deban realizar otras tareas pendientes como el vaciado de escritura). Consulte WATCHPROC a continuación para más detalles.

Tcl_BadChannelOption es llamada desde setOptionProc o getOptionProc específicos del controlador para generar un mensaje de error completo.

Tcl_ChannelBuffered devuelve el número de bytes de entrada actualmente en búfer en el búfer interno (área de retroceso) del propio canal. No informa sobre los datos en los búferes generales de la pila de canales de la que forma parte el canal proporcionado.

Tcl_IsChannelShared comprueba el contador de referencias del channel especificado y devuelve si el channel fue compartido entre múltiples intérpretes (resultado == 1) o no (resultado == 0).

Tcl_IsChannelRegistered comprueba si el channel especificado está registrado en el interp de intérprete dado (resultado == 1) o no (resultado == 0).

Tcl_IsChannelExisting comprueba si un canal con el nombre especificado está registrado en la lista global (de hilos) de todos los canales (resultado == 1) o no (resultado == 0).

Tcl_CutChannel elimina el channel especificado de la lista global (de hilos) de todos los canales (del hilo actual). No se permite la aplicación a un canal todavía registrado en algún intérprete. También notifica al controlador si la versión de Tcl_ChannelType es TCL_CHANNEL_VERSION_4 (o superior), y Tcl_DriverThreadActionProc está definida para él.

Tcl_SpliceChannel añade el channel especificado a la lista global (de hilos) de todos los canales (del hilo actual). No se permite la aplicación a un canal registrado en algún intérprete. También notifica al controlador si la versión de Tcl_ChannelType es TCL_CHANNEL_VERSION_4 (o superior), y Tcl_DriverThreadActionProc está definida para él.

Tcl_ClearChannelHandlers elimina todos los manejadores de canal y scripts de eventos asociados con el channel especificado, cerrando así todo el procesamiento de eventos para este canal.

TCL_CHANNELTYPE

Un controlador de canal proporciona una estructura Tcl_ChannelType que contiene punteros a funciones que implementan las diversas operaciones en un canal; estas operaciones se invocan según sea necesario por la capa genérica. La estructura se versionó a partir de Tcl 8.3.2/8.4 para corregir un problema con los controladores de canal apilados. Consulte la sección OLD CHANNEL TYPES a continuación para obtener detalles sobre la estructura antigua.

La estructura Tcl_ChannelType contiene los siguientes campos:

typedef struct Tcl_ChannelType {
        const char *typeName;
        Tcl_ChannelTypeVersion version;
        Tcl_DriverCloseProc *closeProc;
        Tcl_DriverInputProc *inputProc;
        Tcl_DriverOutputProc *outputProc;
        Tcl_DriverSeekProc *seekProc;
        Tcl_DriverSetOptionProc *setOptionProc;
        Tcl_DriverGetOptionProc *getOptionProc;
        Tcl_DriverWatchProc *watchProc;
        Tcl_DriverGetHandleProc *getHandleProc;
        Tcl_DriverClose2Proc *close2Proc;
        Tcl_DriverBlockModeProc *blockModeProc;
        Tcl_DriverFlushProc *flushProc;
        Tcl_DriverHandlerProc *handlerProc;
        Tcl_DriverWideSeekProc *wideSeekProc;
        Tcl_DriverThreadActionProc *threadActionProc;
        Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

No es necesario proporcionar implementaciones para todas las operaciones del canal. Las que no sean necesarias pueden establecerse en NULL en la estructura: blockModeProc, seekProc, setOptionProc, getOptionProc, getHandleProc y close2Proc, además de flushProc, handlerProc, threadActionProc y truncateProc. Otras funciones que no se pueden implementar de forma significativa deben devolver EINVAL al ser llamadas, para indicar que las operaciones que representan no están disponibles. Tenga en cuenta también que wideSeekProc puede ser NULL si seekProc lo es.

El usuario solo debe utilizar la estructura anterior para la instanciación de Tcl_ChannelType. Al hacer referencia a campos en una estructura Tcl_ChannelType, se deben utilizar las siguientes funciones para obtener los valores: Tcl_ChannelName, Tcl_ChannelVersion, Tcl_ChannelBlockModeProc, Tcl_ChannelCloseProc, Tcl_ChannelClose2Proc, Tcl_ChannelInputProc, Tcl_ChannelOutputProc, Tcl_ChannelSeekProc, Tcl_ChannelWideSeekProc, Tcl_ChannelThreadActionProc, Tcl_ChannelTruncateProc, Tcl_ChannelSetOptionProc, Tcl_ChannelGetOptionProc, Tcl_ChannelWatchProc, Tcl_ChannelGetHandleProc, Tcl_ChannelFlushProc o Tcl_ChannelHandlerProc.

El cambio en las estructuras se realizó de tal manera que los tipos de canal estándar son binariamente compatibles. Sin embargo, los tipos de canal que utilizan canales apilados (es decir, TLS, Trf) tienen nuevas versiones para corresponder al cambio anterior, ya que el código anterior para canales apilados tenía problemas.

TYPENAME

El campo typeName contiene una cadena terminada en nulo que identifica el tipo de dispositivo implementado por este controlador, por ejemplo, file o socket.

Este valor se puede recuperar con Tcl_ChannelName, que devuelve un puntero a la cadena.

VERSION

El campo version debe establecerse en la versión de la estructura que necesita. TCL_CHANNEL_VERSION_2 es el mínimo recomendado. TCL_CHANNEL_VERSION_3 debe establecerse para especificar el miembro wideSeekProc. TCL_CHANNEL_VERSION_4 debe establecerse para especificar el miembro threadActionProc (incluye wideSeekProc). TCL_CHANNEL_VERSION_5 debe establecerse para especificar los miembros truncateProc (incluye wideSeekProc y threadActionProc). Si no se establece en ninguno de estos, se asume que este Tcl_ChannelType tiene la estructura original. Consulte OLD CHANNEL TYPES para más detalles. Si bien Tcl reconocerá y funcionará con ambas estructuras, los canales apilados deben ser de al menos TCL_CHANNEL_VERSION_2 para funcionar correctamente.

Este valor se puede recuperar con Tcl_ChannelVersion, que devuelve uno de TCL_CHANNEL_VERSION_5, TCL_CHANNEL_VERSION_4, TCL_CHANNEL_VERSION_3, TCL_CHANNEL_VERSION_2 o TCL_CHANNEL_VERSION_1.

BLOCKMODEPROC

El campo blockModeProc contiene la dirección de una función llamada por la capa genérica para establecer el modo de bloqueo y no bloqueo en el dispositivo. BlockModeProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverBlockModeProc(
        ClientData instanceData,
        int mode);

instanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó este canal. El argumento mode es TCL_MODE_BLOCKING o TCL_MODE_NONBLOCKING para establecer el dispositivo en modo de bloqueo o no bloqueo. La función debe devolver cero si la operación fue exitosa, o un código de error POSIX distinto de cero si la operación falló.

Si la operación es exitosa, la función puede modificar el instanceData proporcionado para registrar que el canal entró en modo de bloqueo o no bloqueo y para implementar el comportamiento de bloqueo o no bloqueo. Para algunos tipos de dispositivos, el comportamiento de bloqueo y no bloqueo puede ser implementado por el sistema operativo subyacente; para otros tipos de dispositivos, el comportamiento debe ser emulado en el controlador de canal.

Este valor se puede recuperar con Tcl_ChannelBlockModeProc, que devuelve un puntero a la función.

Un controlador de canal que no proporciona un blockModeProc debe ser muy, muy cuidadoso. Debe decirle a la capa genérica exactamente qué modo de bloqueo es aceptable para él, y también debe documentar esto para el usuario para que el modo de bloqueo del canal no se cambie a un valor inaceptable. Cualquier confusión aquí puede llevar al intérprete a un interbloqueo (falso y difícil de encontrar).

CLOSEPROC Y CLOSE2PROC

El campo closeProc contiene la dirección de una función llamada por la capa genérica para limpiar la información relacionada con el controlador cuando se cierra el canal. CloseProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverCloseProc(
        ClientData instanceData,
        Tcl_Interp *interp);

El argumento instanceData es el mismo que el valor proporcionado a Tcl_CreateChannel cuando se creó el canal. La función debe liberar cualquier almacenamiento mantenido por el controlador de canal para este canal y cerrar los dispositivos de entrada y salida encapsulados por este canal. Toda la salida en cola se habrá vaciado al dispositivo antes de llamar a esta función, y no se invocarán más operaciones del controlador en esta instancia después de llamar a closeProc. Si la operación de cierre es exitosa, el procedimiento sh

ould return zero; otherwise it should return a nonzero POSIX error code. In addition, if an error occurs and interp is not NULL, the procedure should store an error message in the interpreter's result.

Alternatively, channels that support closing the read and write sides independently may set closeProc to TCL_CLOSE2PROC and set close2Proc to the address of a function that matches the following prototype:

typedef int Tcl_DriverClose2Proc(
        ClientData instanceData,
        Tcl_Interp *interp,
        int flags);

The close2Proc will be called with flags set to an OR'ed combination of TCL_CLOSE_READ or TCL_CLOSE_WRITE to indicate that the driver should close the read and/or write side of the channel. The channel driver may be invoked to perform additional operations on the channel after close2Proc is called to close one or both sides of the channel. If flags is 0 (zero), the driver should close the channel in the manner described above for closeProc. No further operations will be invoked on this instance after close2Proc is called with all flags cleared. In all cases, the close2Proc function should return zero if the close operation was successful; otherwise it should return a nonzero POSIX error code. In addition, if an error occurs and interp is not NULL, the procedure should store an error message in the interpreter's result.

The closeProc and close2Proc values can be retrieved with Tcl_ChannelCloseProc or Tcl_ChannelClose2Proc, which return a pointer to the respective function.

PROCEDIMIENTO DE ENTRADA

El campo inputProc contiene la dirección de una función llamada por la capa genérica para leer datos del archivo o dispositivo y almacenarlos en un búfer interno. InputProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverInputProc(
        ClientData instanceData,
        char *buf,
        int bufSize,
        int *errorCodePtr);

InstanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó el canal. El argumento buf apunta a una matriz de bytes en la que se almacenarán los datos de entrada del dispositivo, y el argumento bufSize indica cuántos bytes están disponibles en buf.

El argumento errorCodePtr apunta a una variable entera proporcionada por la capa genérica. Si ocurre un error, la función debe establecer la variable a un código de error POSIX que identifique el error que ocurrió.

La función debe leer datos del dispositivo de entrada encapsulado por el canal y almacenarlos en buf. En caso de éxito, la función debe devolver un entero no negativo que indique cuántos bytes se leyeron del dispositivo de entrada y se almacenaron en buf. En caso de error, la función debe devolver -1. Si ocurre un error después de que se hayan leído algunos datos del dispositivo, esos datos se pierden.

Si inputProc puede determinar que el dispositivo de entrada tiene algunos datos disponibles pero menos de los solicitados por el argumento bufSize, la función solo debe intentar leer tantos datos como estén disponibles y devolver sin bloquear. Si no hay datos disponibles en absoluto en el dispositivo de entrada y el canal está en modo no bloqueante, la función debe devolver un error EAGAIN. Si no hay datos disponibles en absoluto en el dispositivo de entrada y el canal está en modo bloqueante, la función debe bloquearse durante el menor tiempo posible hasta que se pueda leer al menos un byte de datos del dispositivo; luego, debe devolver tantos datos como pueda leer sin bloquear.

Este valor se puede recuperar con Tcl_ChannelInputProc, que devuelve un puntero a la función.

PROCEDIMIENTO DE SALIDA

El campo outputProc contiene la dirección de una función llamada por la capa genérica para transferir datos de un búfer interno al dispositivo de salida. OutputProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverOutputProc(
        ClientData instanceData,
        const char *buf,
        int toWrite,
        int *errorCodePtr);

InstanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó el canal. El argumento buf contiene una matriz de bytes que se escribirán en el dispositivo, y el argumento toWrite indica cuántos bytes se escribirán desde el argumento buf.

El argumento errorCodePtr apunta a una variable entera proporcionada por la capa genérica. Si ocurre un error, la función debe establecer esta variable a un código de error POSIX que identifique el error.

La función debe escribir los datos en buf en el dispositivo de salida encapsulado por el canal. En caso de éxito, la función debe devolver un entero no negativo que indique cuántos bytes se escribieron en el dispositivo de salida. El valor de retorno es normalmente el mismo que toWrite, pero puede ser menor en algunos casos, como si la operación de salida se interrumpe por una señal. Si ocurre un error, la función debe devolver -1. En caso de error, es posible que se hayan escrito algunos datos en el dispositivo.

Si el canal no está bloqueando y el dispositivo de salida no puede absorber ningún dato, la función debe devolver -1 con un error EAGAIN sin escribir ningún dato.

Este valor se puede recuperar con Tcl_ChannelOutputProc, que devuelve un puntero a la función.

SEEKPROC Y WIDESEEKPROC

El campo seekProc contiene la dirección de una función llamada por la capa genérica para mover el punto de acceso en el que se aplicarán las operaciones de entrada o salida posteriores. SeekProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverSeekProc(
        ClientData instanceData,
        long offset,
        int seekMode,
        int *errorCodePtr);

El argumento instanceData es el mismo que el valor dado a Tcl_CreateChannel cuando se creó este canal. Offset y seekMode tienen el mismo significado que para el procedimiento Tcl_Seek (descrito en la entrada del manual para Tcl_OpenFileChannel).

El argumento errorCodePtr apunta a una variable entera proporcionada por la capa genérica para devolver los valores de errno de la función. La función debe establecer esta variable a un código de error POSIX si ocurre un error. La función debe almacenar un código de error EINVAL si el tipo de canal no implementa la búsqueda.

El valor de retorno es el nuevo punto de acceso o -1 en caso de error. Si ocurrió un error, la función no debe mover el punto de acceso.

Si hay un campo seekProc no NULL, el campo wideSeekProc puede contener la dirección de una función alternativa a utilizar que maneje desplazamientos amplios (es decir, mayores de 32 bits), permitiendo así búsquedas dentro de archivos de más de 2 GB. Se llamará a wideSeekProc con preferencia sobre seekProc, pero ambos deben definirse si se define wideSeekProc. WideSeekProc debe coincidir con el siguiente prototipo:

typedef Tcl_WideInt Tcl_DriverWideSeekProc(
        ClientData instanceData,
        Tcl_WideInt offset,
        int seekMode,
        int *errorCodePtr);

Los argumentos y los valores de retorno significan lo mismo que con seekProc arriba, excepto que el tipo de los desplazamientos y el tipo de retorno son diferentes.

El valor seekProc se puede recuperar con Tcl_ChannelSeekProc, que devuelve un puntero a la función, y de manera similar, wideSeekProc se puede recuperar con Tcl_ChannelWideSeekProc.

SETOPTIONPROC

El campo setOptionProc contiene la dirección de una función llamada por la capa genérica para establecer una opción específica del tipo de canal en un canal. setOptionProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverSetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        const char *newValue);

optionName es el nombre de una opción a establecer, y newValue es el nuevo valor para esa opción, como una cadena de texto. InstanceData es el mismo valor que se dio a Tcl_CreateChannel cuando se creó este canal. La función debe realizar cualquier acción específica del tipo de canal necesaria para implementar el nuevo valor de la opción.

Algunas opciones son manejadas por el código genérico y esta función nunca se llama para establecerlas, por ejemplo, -blockmode. Otras opciones son específicas de cada tipo de canal y se llamará al procedimiento setOptionProc del controlador del canal para implementarlas. El campo setOptionProc puede ser NULL, lo que indica que este tipo de canal no admite opciones específicas del tipo.

Si el valor de la opción se modifica correctamente al nuevo valor, la función devuelve TCL_OK. Debe llamar a Tcl_BadChannelOption, que a su vez devuelve TCL_ERROR si el optionName no se reconoce. Si newValue especifica un valor para la opción que no se soporta o si ocurre un error de llamada al sistema, la función debe dejar un mensaje de error en el resultado de interp si interp no es NULL. La función también debe llamar a Tcl_SetErrno para almacenar un código de error POSIX apropiado.

Este valor se puede recuperar con Tcl_ChannelSetOptionProc, que devuelve un puntero a la función.

El campo getOptionProc contiene la dirección de una función llamada por la capa genérica para obtener el valor de una opción específica del tipo de canal en un canal. getOptionProc debe coincidir con el siguiente prototipo:

DESCRIPTION

Tcl channels provide a mechanism for interacting with I/O devices such as files, pipes, sockets, and devices. The channel driver interface is used to integrate new channel types into Tcl. This section describes the structure Tcl_ChannelType which defines the behavior of a channel type, and the Tcl commands and C functions used to create, manage, and access channels.

The Tcl_ChannelType structure is defined as:

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
    Tcl_DriverFlushProc *flushProc;
    Tcl_DriverHandlerProc *handlerProc;
    Tcl_DriverThreadActionProc *threadActionProc;
    Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

The fields of the structure are described below:

TYPENAME

The name of the channel type, used to identify the type in Tcl commands like Tcl_GetChannelType.

BLOCKMODEPROC

The blockModeProc field contains the address of a function that is called to set the blocking mode for the channel. It should match the following prototype:

typedef int Tcl_DriverBlockModeProc(
        ClientData instanceData,
        int mode);

InstanceData is the value passed to Tcl_CreateChannel when this channel was created. Mode is non-zero to set blocking mode and zero for non-blocking mode. The function should return 0 on success, or an error code (suitable for use with Tcl_SetErrno) on failure.

This value can be retrieved with Tcl_ChannelBlockMode, which returns the current blocking mode.

CLOSEPROC

The closeProc field contains the address of a function that is called to close the channel. It should match the following prototype:

typedef int Tcl_DriverCloseProc(
        ClientData instanceData,
        Tcl_Interp *interp);

InstanceData is the value passed to Tcl_CreateChannel when this channel was created. The function should release any resources associated with the channel and return 0 on success or an error code (suitable for use with Tcl_SetErrno) on failure. If an error occurs and interp is not NULL, an error message should be set in interp.

This value can be retrieved with Tcl_ChannelCloseProc, which returns a pointer to the function.

INPUTPROC

The inputProc field contains the address of a function that is called to read data from the channel. It should match the following prototype:

typedef int Tcl_DriverInputProc(
        ClientData instanceData,
        char *buf,
        int toRead,
        int *errorCodePtr);

InstanceData is the value passed to Tcl_CreateChannel when this channel was created. Buf is a buffer to store the input data. toRead is the maximum number of bytes to read. The function should return the number of bytes actually read, or -1 on error. If an error occurs, the appropriate POSIX error code should be stored in *errorCodePtr.

This value can be retrieved with Tcl_ChannelInputProc, which returns a pointer to the function.

OUTPUTPROC

The outputProc field contains the address of a function that is called to write data to the channel. It should match the following prototype:

typedef int Tcl_DriverOutputProc(
        ClientData instanceData,
        const char *buf,
        int toWrite,
        int *errorCodePtr);

InstanceData is the value passed to Tcl_CreateChannel when this channel was created. Buf is a buffer containing the data to write. toWrite is the number of bytes to write. The function should return the number of bytes actually written, or -1 on error. If an error occurs, the appropriate POSIX error code should be stored in *errorCodePtr.

This value can be retrieved with Tcl_ChannelOutputProc, which returns a pointer to the function.

SEEKPROC

The seekProc field contains the address of a function that is called to seek on the channel. It should match the following prototype:

typedef int Tcl_DriverSeekProc(
        ClientData instanceData,
        Tcl_WideInt offset,
        int mode);

InstanceData is the value passed to Tcl_CreateChannel when this channel was created. Offset and mode are the same as the arguments to the Tcl command seek. The function should return the new current position after the seek, or -1 on error. If an error occurs, the appropriate POSIX error code should be set using Tcl_SetErrno.

This value can be retrieved with Tcl_ChannelSeekProc, which returns a pointer to the function.

SETOPTIONPROC

The setOptionProc field contains the address of a function that is called to set channel options. It should match the following prototype:

typedef int Tcl_DriverSetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        const char *value);

InstanceData is the value passed to Tcl_CreateChannel when this channel was created. OptionName and value are the name and value of the option to set. The function should return 0 on success, or TCL_ERROR on failure. If an error occurs and interp is not NULL, an error message should be set in interp.

Note that some options are handled by the generic channel code. The setOptionProc procedure will only be called for type-specific options.

This value can be retrieved with Tcl_ChannelSetOptionProc, which returns a pointer to the function.

GETOPTIONPROC

The getOptionProc field contains the address of a function that is called to get channel options. It should match the following prototype:

typedef int Tcl_DriverGetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        Tcl_DString *valuePtr);

InstanceData is the value passed to Tcl_CreateChannel when this channel was created. OptionName is the name of the option to retrieve. The value of the option should be appended to the valuePtr Tcl_DString. The function should return 0 on success, or TCL_ERROR on failure. If an error occurs and interp is not NULL, an error message should be set in interp. If the option is not supported by the channel driver, the function should return TCL_ERROR without setting an error message.

Some options are handled by the generic code and this function is never called to retrieve their value, e.g. -blockmode. Other options are specific to each channel type and the getOptionProc procedure of the channel driver will get called to implement them. The getOptionProc field can be NULL, which indicates that this channel type supports no type specific options.

This value can be retrieved with Tcl_ChannelGetOptionProc, which returns a pointer to the function.

WATCHPROC

The watchProc field contains the address of a function called by the generic layer to initialize the event notification mechanism to notice events of interest on this channel. WatchProc should match the following prototype:

typedef void Tcl_DriverWatchProc(
        ClientData instanceData,
        int mask);

The instanceData is the same as the value passed to Tcl_CreateChannel when this channel was created. The mask argument is an OR-ed combination of TCL_READABLE, TCL_WRITABLE and TCL_EXCEPTION; it indicates events the caller is interested in noticing on this channel.

The function should initialize device type specific mechanisms to notice when an event of interest is present on the channel. When one or more of the designated events occurs on the channel, the channel driver is responsible for calling Tcl_NotifyChannel to inform the generic channel module. The driver should take care not to starve other channel drivers or sources of callbacks by invoking Tcl_NotifyChannel too frequently. Fairness can be insured by using the Tcl event queue to allow the channel event to be scheduled in sequence with other events. See the description of Tcl_QueueEvent for details on how to queue an event.

This value can be retrieved with Tcl_ChannelWatchProc, which returns a pointer to the function.

GETHANDLEPROC

The getHandleProc field contains the address of a function called by the generic layer to retrieve a device-specific handle from the channel. GetHandleProc should match the following prototype:

typedef int Tcl_DriverGetHandleProc(
        ClientData instanceData,
        int direction,
        ClientData *handlePtr);

InstanceData is the same as the value passed to Tcl_CreateChannel when this channel was created. The direction argument is either TCL_READABLE to retrieve the handle used for input, or TCL_WRITABLE to retrieve the handle used for output.

If the channel implementation has device-specific handles, the function should retrieve the appropriate handle associated with the channel, according the direction argument. The handle should be stored in the location referred to by handlePtr, and TCL_OK should be returned. If the channel is not open for the specified direction, or if the channel implementation does not use device handles, the function should return TCL_ERROR.

This value can be retrieved with Tcl_ChannelGetHandleProc, which returns a pointer to the function.

FLUSHPROC

The flushProc field is currently reserved for future use. It should be set to NULL. FlushProc should match the following prototype:

typedef int Tcl_DriverFlushProc(
        ClientData instanceData);

This value can be retrieved with Tcl_ChannelFlushProc, which returns a pointer to the function.

HANDLERPROC

The handlerProc field contains the address of a function called by the generic layer to notify the channel that an event occurred. It should be defined for stacked channel drivers that wish to be notified of events that occur on the underlying (stacked) channel. HandlerProc should match the following prototype:

typedef int Tcl_DriverHandlerProc(
        ClientData instanceData,
        int interestMask);

InstanceData is the same as the value passed to Tcl_CreateChannel when this channel was created. The interestMask is an OR-ed combination of TCL_READABLE or TCL_WRITABLE; it indicates what type of event occurred on this channel.

This value can be retrieved with Tcl_ChannelHandlerProc, which returns a pointer to the function.

THREADACTIONPROC

The threadActionProc field contains the address of the function called by the generic layer when a channel is created, closed, or going to move to a different thread, i.e. whenever thread-specific driver state might have to initialized or updated. It can be NULL. The action TCL_CHANNEL_THREAD_REMOVE is used to notify the driver that it should update or remove any thread-specific data it might be maintaining for the channel.

The action TCL_CHANNEL_THREAD_INSERT is used to notify the driver that it should update or initialize any thread-specific data it might be maintaining using the calling thread as the associate. See Tcl_CutChannel and Tcl_SpliceChannel for more detail.

typedef void Tcl_DriverThreadActionProc(
        ClientData instanceData,
        int action);

InstanceData is the same as the value passed to Tcl_CreateChannel when this channel was created.

These values can be retrieved with Tcl_ChannelThreadActionProc, which returns a pointer to the function.

TRUNCATEPROC

The truncateProc field contains the address of the function called by the generic layer when a channel is truncated to some length. It can be NULL.

typedef int Tcl_DriverTruncateProc(
        ClientData instanceData,
        Tcl_WideInt length);

InstanceData is the same as the value passed to Tcl_CreateChannel when this channel was created, and length is the new length of the underlying file, which should not be negative. The result should be 0 on success or an errno code (suitable for use with Tcl_SetErrno) on failure.

These values can be retrieved with Tcl_ChannelTruncateProc, which returns a pointer to the function.

TCL_BADCHANNELOPTION

This procedure generates a “bad option” error message in an (optional) interpreter. It is used by channel drivers when an invalid Set/Get option is requested. Its purpose is to concatenate the generic options list to the specific ones and factorize the generic options error message string.

It always returns TCL_ERROR

An error message is generated in interp's result value to indicate that a command was invoked with a bad option. The message has the form

    bad option "blah": should be one of
    <...generic options...>+<...specific options...>
so you get for instance: 
    bad option "-blah": should be one of -blocking,
    -buffering, -buffersize, -eofchar, -translation,
    -peername, or -sockname
when called with optionList equal to “peername sockname”

“blah” is the optionName argument and “<specific options>” is a space separated list of specific option words. The function takes good care of inserting minus signs before each option, commas after, and an “or” before the last option.

OLD CHANNEL TYPES

The original (8.3.1 and below) Tcl_ChannelType structure contains the following fields:

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
} Tcl_ChannelType;

It is still possible to create channel with the above structure. The internal channel code will determine the version. It is imperative to use the new Tcl_ChannelType structure if you are creating a stacked channel driver, due to problems with the earlier stacked channel implementation (in 8.2.0 to 8.3.1).

Prior to 8.4.0 (i.e. during the later releases of 8.3 and early part of the 8.4 development cycle) the Tcl_ChannelType structure contained the following fields:

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_ChannelTypeVersion version;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverFlushProc *flushProc;
    Tcl_DriverHandlerProc *handlerProc;
    Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

When the above structure is registered as a channel type, the version field should always be TCL_CHANNEL_VERSION_2.
