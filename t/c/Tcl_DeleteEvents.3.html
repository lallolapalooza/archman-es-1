ARGUMENTOS

Tcl_EventSetupProc *setupProc (entrada)
Procedimiento a invocar para preparar la espera de eventos en Tcl_DoOneEvent.
Tcl_EventCheckProc *checkProc (entrada)
Procedimiento que Tcl_DoOneEvent invocará después de esperar eventos. Comprueba si han ocurrido eventos y, si es así, los pone en cola.
ClientData clientData (entrada)
Valor arbitrario de una palabra para pasar a setupProc, checkProc, o deleteProc.
const Tcl_Time *timePtr (entrada)
Indica la cantidad máxima de tiempo a esperar por un evento. Esto se especifica como un intervalo (cuánto tiempo esperar), no como un tiempo absoluto (cuándo despertar). Si el puntero pasado a Tcl_WaitForEvent es NULL, significa que no hay tiempo máximo de espera: esperar para siempre si es necesario.
Tcl_Event *evPtr (entrada)
Un evento para añadir a la cola de eventos. El almacenamiento para el evento debe haber sido asignado por el llamador usando Tcl_Alloc o ckalloc.
Tcl_QueuePosition position (entrada)
Dónde añadir el nuevo evento en la cola: TCL_QUEUE_TAIL, TCL_QUEUE_HEAD, o TCL_QUEUE_MARK.
Tcl_ThreadId threadId (entrada)
Un identificador único para un hilo.
Tcl_EventDeleteProc *deleteProc (entrada)
Procedimiento a invocar para cada evento en cola en Tcl_DeleteEvents.

Estructura de punteros de función que describe los procedimientos de notificador que reemplazarán a los instalados en el ejecutable. Ver REEMPLAZANDO EL NOTIFICADOR para más detalles.

INTRODUCCIÓN

Las interfaces descritas aquí se utilizan para personalizar el bucle de eventos de Tcl. Las dos personalizaciones más comunes son añadir nuevas fuentes de eventos y fusionar el bucle de eventos de Tcl con algún otro bucle de eventos, como uno proporcionado por una aplicación en la que Tcl está incrustado. Cada una de estas tareas se describe en una sección separada a continuación.

Los procedimientos de esta entrada del manual son los bloques de construcción con los que se construye el notificador de eventos de Tcl. El notificador de eventos es la capa más baja en el mecanismo de eventos de Tcl. Consta de tres cosas:

[1]
Fuentes de eventos: estas representan las formas en que se pueden generar eventos. Por ejemplo, existe una fuente de eventos de temporizador que implementa el procedimiento Tcl_CreateTimerHandler y el comando after, y existe una fuente de eventos de archivo que implementa el procedimiento Tcl_CreateFileHandler en sistemas Unix. Una fuente de eventos debe funcionar con el notificador para detectar eventos en los momentos adecuados, registrarlos en la cola de eventos y, finalmente, notificar al software de nivel superior que han ocurrido. Los procedimientos Tcl_CreateEventSource, Tcl_DeleteEventSource, y Tcl_SetMaxBlockTime, Tcl_QueueEvent, y Tcl_DeleteEvents son utilizados principalmente por las fuentes de eventos.
[2]
La cola de eventos: para aplicaciones no multihilo, hay una única cola para toda la aplicación, que contiene eventos que han sido detectados pero aún no procesados. Las fuentes de eventos colocan eventos en la cola para que puedan ser procesados en orden en momentos apropiados durante el bucle de eventos. La cola de eventos garantiza una disciplina justa de manejo de eventos, de modo que ninguna fuente de eventos pueda dejar sin servicio a las otras. También permite que los eventos se guarden para ser procesados en un momento futuro. Las aplicaciones multihilo funcionan de manera similar, excepto que hay una cola de eventos separada para cada hilo que contiene un intérprete de Tcl. Tcl_QueueEvent se utiliza (principalmente por las fuentes de eventos) para añadir eventos a la cola de eventos y Tcl_DeleteEvents se utiliza para eliminar eventos de la cola sin procesarlos. En una aplicación multihilo, Tcl_QueueEvent añade un evento a la cola del hilo actual, y Tcl_ThreadQueueEvent añade un evento a una cola en un hilo específico.
[3]
El bucle de eventos: para detectar y procesar eventos, la aplicación entra en un bucle que espera a que ocurran eventos, los coloca en la cola de eventos y luego los procesa. La mayoría de las aplicaciones lo harán llamando al procedimiento Tcl_DoOneEvent, que se describe en una entrada separada del manual.

La mayoría de las aplicaciones Tcl no necesitan preocuparse por los detalles internos del notificador de Tcl. Sin embargo, el notificador ahora tiene suficiente flexibilidad para ser redirigido ya sea a una nueva plataforma o para usar un bucle de eventos externo (como el bucle de eventos de Motif, cuando Tcl está incrustado en una aplicación de Motif). Los procedimientos Tcl_WaitForEvent y Tcl_SetTimer son implementados normalmente por Tcl, pero pueden ser reemplazados por nuevas versiones para redirigir el notificador (los procedimientos Tcl_Sleep, Tcl_CreateFileHandler, y Tcl_DeleteFileHandler también deben ser reemplazados; ver CREANDO UN NUEVO NOTIFICADOR a continuación para más detalles). Los procedimientos Tcl_ServiceAll, Tcl_ServiceEvent, Tcl_GetServiceMode, y Tcl_SetServiceMode se proporcionan para ayudar a conectar el bucle de eventos de Tcl a un bucle de eventos externo como el de Motif.

BASES DEL NOTIFICADOR

La forma más fácil de entender cómo funciona el notificador es considerar lo que sucede cuando se llama a Tcl_DoOneEvent. Tcl_DoOneEvent recibe un argumento flags que indica qué tipo de eventos se pueden procesar y si se debe bloquear si no hay eventos listos. Tcl_DoOneEvent realiza las siguientes acciones:

[1]
Comprueba la cola de eventos para ver si contiene algún evento que pueda ser procesado. Si es así, procesa el primer evento posible, lo elimina de la cola y retorna. Lo hace llamando a Tcl_ServiceEvent y pasándole el argumento flags.
[2]
Se prepara para bloquear esperando un evento. Para hacer esto, Tcl_DoOneEvent invoca un procedimiento setup en cada fuente de eventos. La fuente de eventos realizará la inicialización específica de la fuente de eventos y posiblemente llamará a Tcl_SetMaxBlockTime para limitar cuánto tiempo bloqueará Tcl_WaitForEvent si no ocurren nuevos eventos.
[3]
Llama a Tcl_WaitForEvent. Este procedimiento se implementa de manera diferente en distintas plataformas; espera a que ocurra un evento, basándose en la información proporcionada por las fuentes de eventos. Puede hacer que la aplicación se bloquee si timePtr especifica un intervalo distinto de 0. Tcl_WaitForEvent retorna cuando algo ha sucedido, como un archivo que se ha vuelto legible o la expiración del intervalo dado por timePtr. Si no hay eventos para que Tcl_WaitForEvent espere, de modo que bloquearía para siempre, entonces retorna inmediatamente y Tcl_DoOneEvent retorna 0.
[4]
Llama a un procedimiento check en cada fuente de eventos. El procedimiento check determina si ocurrieron eventos de interés para esta fuente. Si es así, los eventos se añaden a la cola de eventos.
[5]
Comprueba la cola de eventos de nuevo para ver si ahora contiene eventos que pueden ser servidos. Si es así, llama a Tcl_ServiceEvent para servir el primer evento posible, lo elimina de la cola y retorna.

EVENT QUEUE

The event queue is a list of events that are pending servicing. The events are organized as a linked list, with the newest events at the head of the list.

The following steps show how the event queue is processed:

[1]
If there are no events in the queue, return 0.
[2]
Determine the maximum time to wait for events. If the caller requested blocking, this is the shortest time specified by any event source's setup procedure using Tcl_SetMaxBlockTime. Otherwise, it is zero.
[3]
Wait until an event occurs or the maximum time determined in step [2] has expired. If an event occurs, go to step [5]. If the time expires without an event, go to step [6].
[4]
For each event source, invoke its check procedure (see below). The check procedure should add any events that are ready to the event queue.
[5]
Examine the event queue to see if it contains any events that can be serviced. If so, service the first possible event, remove it from the queue, and return.
[6]
See if there are idle callbacks pending. If so, invoke all of them and return.
[7]
Either return 0 to indicate that no events were ready, or go back to step [2] if blocking was requested by the caller.

CREACIÓN DE UNA NUEVA FUENTE DE EVENTOS

Una fuente de eventos consiste en tres procedimientos invocados por el notificador, además de procedimientos C adicionales que son invocados por código de nivel superior para organizar callbacks dirigidos por eventos. Los tres procedimientos llamados por el notificador consisten en los procedimientos de configuración y verificación descritos anteriormente, más un procedimiento adicional que se invoca cuando un evento se elimina de la cola de eventos para su servicio.

El procedimiento Tcl_CreateEventSource crea una nueva fuente de eventos. Sus argumentos especifican el procedimiento de configuración y el procedimiento de verificación para la fuente de eventos. SetupProc debe coincidir con el siguiente prototipo:

typedef void Tcl_EventSetupProc(
        ClientData clientData,
        int flags);

El argumento clientData será el mismo que el argumento clientData para Tcl_CreateEventSource; típicamente se utiliza para apuntar a información privada gestionada por la fuente de eventos. El argumento flags será el mismo que el argumento flags pasado a Tcl_DoOneEvent, excepto que nunca será 0 (Tcl_DoOneEvent reemplaza 0 con TCL_ALL_EVENTS). Flags indica qué tipos de eventos deben considerarse; si el bit correspondiente a esta fuente de eventos no está establecido, la fuente de eventos debe regresar inmediatamente sin hacer nada. Por ejemplo, la fuente de eventos de archivo verifica el bit TCL_FILE_EVENTS.

El trabajo de SetupProc es asegurarse de que la aplicación despierte cuando ocurran eventos del tipo deseado. Esto se hace típicamente de forma dependiente de la plataforma. Por ejemplo, en Unix una fuente de eventos podría llamar a Tcl_CreateFileHandler; en Windows podría solicitar notificación con un evento de Windows. Para fuentes de eventos impulsadas por temporizadores, como eventos de temporizador o cualquier evento sondeado, la fuente de eventos puede llamar a Tcl_SetMaxBlockTime para forzar a la aplicación a despertar después de un tiempo especificado, incluso si no han ocurrido eventos. Si ninguna fuente de eventos llama a Tcl_SetMaxBlockTime, entonces Tcl_WaitForEvent esperará el tiempo necesario para que ocurra un evento; de lo contrario, solo esperará tanto como el intervalo más corto pasado a Tcl_SetMaxBlockTime por una de las fuentes de eventos. Si una fuente de eventos sabe que ya tiene eventos listos para reportar, puede solicitar un tiempo de bloqueo máximo de cero. Por ejemplo, el procedimiento de configuración para la fuente de eventos X comprueba si ya hay eventos en cola. Si los hay, llama a Tcl_SetMaxBlockTime con un tiempo de bloqueo de 0 para que Tcl_WaitForEvent no se bloquee si no hay datos nuevos en la conexión X. El argumento timePtr para Tcl_WaitForEvent apunta a una estructura que describe un intervalo de tiempo en segundos y microsegundos:

typedef struct Tcl_Time {
    long sec;
    long usec;
} Tcl_Time;

El campo usec debe ser menor que 1000000.

La información proporcionada a Tcl_SetMaxBlockTime solo se utiliza para la próxima llamada a Tcl_WaitForEvent; se descarta después de que Tcl_WaitForEvent regresa. La próxima vez que se realice una espera de eventos, se llamará a los procedimientos de configuración de cada una de las fuentes de eventos, y estas podrán especificar nueva información para esa espera de eventos.

Si la aplicación utiliza un bucle de eventos externo en lugar de Tcl_DoOneEvent, las fuentes de eventos pueden necesitar llamar a Tcl_SetMaxBlockTime en otros momentos. Por ejemplo, si se registra un nuevo manejador de eventos que necesita sondear eventos, la fuente de eventos puede llamar a Tcl_SetMaxBlockTime para establecer el tiempo de bloqueo a cero para forzar al bucle de eventos externo a llamar a Tcl. En este caso, Tcl_SetMaxBlockTime invoca a Tcl_SetTimer con el intervalo más corto visto desde la última llamada a Tcl_DoOneEvent o Tcl_ServiceAll.

Además del procedimiento genérico Tcl_SetMaxBlockTime, otros procedimientos específicos de la plataforma también pueden estar disponibles para setupProc, si hay información adicional necesaria para Tcl_WaitForEvent en esa plataforma. Por ejemplo, en sistemas Unix se puede utilizar la interfaz Tcl_CreateFileHandler para esperar eventos de archivo.

El segundo procedimiento proporcionado por cada fuente de eventos es su procedimiento de verificación, indicado por el argumento checkProc para Tcl_CreateEventSource. CheckProc debe coincidir con el siguiente prototipo:

typedef void Tcl_EventCheckProc(
        ClientData clientData,
        int flags);

Los argumentos para este procedimiento son los mismos que los de setupProc. CheckProc es invocado por Tcl_DoOneEvent después de que ha esperado eventos. Presumiblemente, al menos una fuente de eventos está ahora preparada para poner en cola un evento. Tcl_DoOneEvent llama a cada una de las fuentes de eventos por turno, para que todas tengan la oportunidad de poner en cola los eventos que estén listos. El procedimiento de verificación hace dos cosas. Primero, debe ver si algún evento se ha activado. Diferentes fuentes de eventos hacen esto de diferentes maneras.

Si el procedimiento de verificación de una fuente de eventos detecta un evento interesante, debe agregar el evento a la cola de eventos de Tcl. Para hacer esto, la fuente de eventos llama a Tcl_QueueEvent. El argumento evPtr es un puntero a una estructura asignada dinámicamente que contiene el evento (ver más abajo para más información sobre problemas de gestión de memoria). Cada fuente de eventos puede definir su propia estructura de evento con la información que sea relevante para esa fuente de eventos. Sin embargo, el primer elemento de la estructura debe ser una estructura de tipo Tcl_Event, y la dirección de esta estructura se utiliza al comunicarse entre la fuente de eventos y el resto del notificador. Un Tcl_Event tiene la siguiente definición:

typedef struct {
    Tcl_EventProc *proc;
    struct Tcl_Event *nextPtr;
} Tcl_Event;

La fuente de eventos debe completar el campo proc del evento antes de llamar a Tcl_QueueEvent. El campo nextPtr se utiliza para enlazar los eventos en la cola y no debe ser modificado por la fuente de eventos.

Se puede agregar un evento a la cola en cualquiera de las tres posiciones, dependiendo del argumento position para Tcl_QueueEvent:

TCL_QUEUE_TAIL
Agrega el evento al final de la cola, de modo que todos los demás eventos pendientes se atiendan primero. Este es casi siempre el lugar correcto para los eventos nuevos.
TCL_QUEUE_HEAD
Agrega el evento al principio de la cola, de modo que se atienda antes que todos los demás eventos en cola.
TCL_QUEUE_MARK
Agrega el evento al principio de la cola, a menos que haya otros eventos al principio cuya posición sea TCL_QUEUE_MARK; en caso afirmativo, agrega el nuevo evento justo después de todos los demás eventos TCL_QUEUE_MARK. Este valor de position se utiliza para insertar una secuencia ordenada de eventos al principio de la cola, como una serie de eventos Enter y Leave sintetizados durante una operación de grab o ungrab en Tk.

Cuando llega el momento de manejar un evento de la cola (pasos 1 y 4 anteriores), Tcl_ServiceEvent invocará el proc especificado en la primera estructura Tcl_Event en cola. Proc debe coincidir con el siguiente prototipo:

typedef int Tcl_EventProc(
        Tcl_Event *evPtr,
        int flags);

El primer argumento para proc es un puntero al evento, que será el mismo que el primer argumento de la llamada Tcl_QueueEvent que agregó el evento a la cola. El segundo argumento para proc es el argumento flags para la llamada actual a Tcl_ServiceEvent; esto es utilizado por la fuente de eventos para regresar inmediatamente si sus eventos no son relevantes.

Corresponde a proc manejar el evento, típicamente invocando uno o más comandos Tcl o callbacks a nivel C. Una vez que la fuente de eventos ha terminado de manejar el evento, regresa 1 para indicar que el evento puede ser eliminado de la cola. Si por alguna razón la fuente de eventos decide que el evento no puede ser manejado en este momento, puede regresar 0 para indicar que el evento debe ser pospuesto para su procesamiento posterior; en este caso Tcl_ServiceEvent continuará con el siguiente evento en la cola e intentará servirlo. Hay varias razones por las que una fuente de eventos podría posponer un evento. Una posibilidad es que los eventos de este tipo estén excluidos por el argumento flags. Por ejemplo, la fuente de eventos de archivo siempre regresará 0 si el bit TCL_FILE_EVENTS no está establecido en flags. Otro ejemplo de posposición de eventos ocurre en Tk si se ha invocado Tk_RestrictEvents para posponer ciertos tipos de eventos de ventana.

Cuando proc regresa 1, Tcl_ServiceEvent eliminará el evento de la cola de eventos y liberará su almacenamiento. Tenga en cuenta que el almacenamiento para un evento debe ser asignado por la fuente de eventos (usando Tcl_Alloc o la macro Tcl ckalloc) antes de llamar a Tcl_QueueEvent, pero será liberado por Tcl_ServiceEvent, no por la fuente de eventos.

Las aplicaciones multihilo funcionan de manera similar, excepto que hay una cola de eventos separada para cada hilo que contiene un intérprete Tcl. Llamar a Tcl_QueueEvent en una aplicación multihilo agrega un evento a la cola del hilo actual. Para agregar un evento a la cola de otro hilo, use Tcl_ThreadQueueEvent. Tcl_ThreadQueueEvent acepta como argumento un argumento Tcl_ThreadId, que identifica de forma única un hilo en una aplicación Tcl. Para obtener el Tcl_ThreadId del hilo actual, use el procedimiento Tcl_GetCurrentThread. (Un hilo necesitaría entonces pasar este identificador a otros hilos para que estos puedan agregar eventos a su cola). Después de agregar un evento a la cola de otro hilo, normalmente necesitará llamar a Tcl_ThreadAlert para "despertar" al notificador de ese hilo para alertarlo sobre el nuevo evento.

Tcl_DeleteEvents se puede utilizar para eliminar explícitamente uno o más eventos de la cola de eventos. Tcl_DeleteEvents llama a proc para cada evento en la cola, eliminando aquellos para los que el procedimiento regresa 1. Los eventos para los que el procedimiento regresa 0 permanecen en la cola. Proc debe coincidir con el siguiente prototipo:

typedef int Tcl_EventDeleteProc(
        Tcl_Event *evPtr,
        ClientData clientData);

El argumento clientData será el mismo que el argumento clientData para Tcl_DeleteEven

CREAR UN NOTIFICADOR

El notificador consta de todos los procedimientos descritos en este manual, más Tcl_DoOneEvent y Tcl_Sleep, que están disponibles en todas las plataformas, y Tcl_CreateFileHandler y Tcl_DeleteFileHandler, que son específicos de Unix. La mayoría de estos procedimientos son generales, ya que son los mismos para todos los notificadores. Sin embargo, ninguno de ellos es dependiente del notificador: Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_SetTimer, Tcl_Sleep, Tcl_WaitForEvent, Tcl_CreateFileHandler, Tcl_DeleteFileHandler y Tcl_ServiceModeHook. Para soportar un nuevo sistema operativo o integrar Tcl con un bucle de eventos específico de un programa, debes escribir nuevas versiones de estos procedimientos.

Tcl_InitNotifier inicializa el estado del notificador y devuelve un handle al estado del notificador. Tcl llama a este procedimiento cuando se inicializa un intérprete Tcl. De manera similar, Tcl_FinalizeNotifier finaliza el notificador y es llamado por Tcl_Finalize cuando se cierra un intérprete Tcl.

Tcl_WaitForEvent es el procedimiento más bajo del notificador; es responsable de esperar por un evento "interesante" o por un tiempo dado. Antes de que Tcl_WaitForEvent se ejecute, cada procedimiento de configuración de los fuentes de eventos se habrá invocado. El argumento timePtr de Tcl_WaitForEvent da el máximo tiempo que se puede bloquear esperando por un evento, basado en las llamadas a Tcl_SetMaxBlockTime realizadas por los procedimientos de configuración y en otros información (como el bit TCL_DONT_WAIT en flags).

Idealmente, Tcl_WaitForEvent debería esperar por un evento antes de procesarlo. Más tarde, los notificadores procesarán los eventos raw y crearán Tcl_Events en la cola de eventos en sus procedimientos checkProc. Sin embargo, en algunos sistemas operativos (como Windows), esto no es posible; los eventos pueden ser procesados en Tcl_WaitForEvent, incluyendo la cola de Tcl_Events y más (por ejemplo, las callbacks de widgets nativos pueden ser invocadas). El valor devuelto de Tcl_WaitForEvent debe ser 0, 1 o -1. En plataformas como Windows, donde los eventos se procesan en Tcl_WaitForEvent, un valor devuelto de 1 indica que hay eventos pendientes que no han sido procesados. Esto es un aviso para el llamador de que debe llamar a Tcl_WaitForEvent de nuevo para procesar todos los eventos pendientes. Un valor devuelto de 0 indica que llamar a Tcl_WaitForEvent de nuevo no tendrá efecto: podría ser un sistema operativo donde Tcl_WaitForEvent solo espera sin procesar ningún evento, o Tcl_WaitForEvent sabe con seguridad que no hay más eventos pendientes (por ejemplo, el tiempo se agotó). Finalmente, un valor devuelto de -1 indica que el bucle de eventos no está más operativo y el programa debería despedirse. En Windows, esto ocurre cuando se recibe un mensaje WM_QUIT; en Unix, cuando Tcl_WaitForEvent espera eternamente debido a que no hay fuentes de eventos activas y el tiempo de espera es infinito).

Tcl_AlertNotifier se usa en aplicaciones multihilo para permitir a cualquier hilo "despertar" al notificador para alertarlo de nuevos eventos en su cola. Tcl_AlertNotifier requiere como argumento el handle del notificador devuelto por Tcl_InitNotifier.

Si el notificador se usará con un bucle de eventos externo, debe también soportar la interfaz de Tcl_SetTimer. Tcl_SetTimer se invoca por Tcl_SetMaxBlockTime cuando se ha reducido el tiempo de bloqueo máximo. Tcl_SetTimer debe organizar para que el bucle de eventos externo invocar a Tcl_ServiceAll después del intervalo especificado, incluso si no ha ocurrido ningún evento. Esta interfaz es necesaria porque Tcl_WaitForEvent no se invoca cuando hay un bucle de eventos externo. Si el notificador se usará solo desde Tcl_DoOneEvent, Tcl_SetTimer no debe hacer nada.

Tcl_ServiceModeHook se llama por parte del componente independiente del notificador cuando el código del cliente llama a Tcl_SetServiceMode. Esta hook se proporciona para soportar sistemas operativos que requieren un manejo especial de eventos cuando la aplicación está en un bucle de eventos modal (por ejemplo, el notificador Windows usa esta hook para crear una ventana de comunicación).

En sistemas Unix, el fuente de eventos de archivos también necesita soporte del notificador. El fuente de eventos de archivos consta de los procedimientos Tcl_CreateFileHandler y Tcl_DeleteFileHandler, que se describen en la página de man de Tcl_CreateFileHandler.

Los interfaces de Tcl_Sleep y Tcl_DoOneEvent se describen en sus respectivas páginas de man.

La forma más fácil de crear un nuevo notificador es revisar el código de un notificador existente, como en los archivos unix/tclUnixNotfy.c o win/tclWinNotify.c en la distribución de código de Tcl.

REEMPLAZAR EL NOTIFICADOR

Un notificador que ha sido escrito según las convenciones anteriores también puede instalarse en un proceso en ejecución en lugar del notificador estándar. Esta mecánica se usa para que un solo ejecutable pueda ser usado (con el notificador estándar) como un programa independiente y reutilizado (con un notificador reemplazado en una extensión cargaable) como una extensión de otro programa, como un plugin de navegador web.

Para hacer esto, la extensión llama a Tcl_SetNotifier, pasando un puntero a un estructura de Tcl_NotifierProcs. La estructura tiene el siguiente layout:

typedef struct Tcl_NotifierProcs {
    Tcl_SetTimerProc *setTimerProc;
    Tcl_WaitForEventProc *waitForEventProc;
    Tcl_CreateFileHandlerProc *createFileHandlerProc;
    Tcl_DeleteFileHandlerProc *deleteFileHandlerProc;
    Tcl_InitNotifierProc *initNotifierProc;
    Tcl_FinalizeNotifierProc *finalizeNotifierProc;
    Tcl_AlertNotifierProc *alertNotifierProc;
    Tcl_ServiceModeHookProc *serviceModeHookProc;
} Tcl_NotifierProcs;

Después de la llamada a Tcl_SetNotifier, los punteros dados en la estructura Tcl_NotifierProcs reemplazan a cualquier notificador que haya sido instalado en el proceso.

Es extraordinariamente inadvisable reemplazar un notificador en ejecución. Normalmente, Tcl_SetNotifier debe llamarse antes de la primera llamada a Tcl_InitNotifier.

BUCLES DE EVENTOS EXTERNOS

Las interfaces del notificador están diseñadas para que Tcl pueda estar embedida en aplicaciones que tienen sus propios bucles de eventos privados. En este caso, la aplicación no llama a Tcl_DoOneEvent excepto en el caso de bucles de eventos recursivos como llamadas a las comandos Tcl update o vwait. La mayoría del tiempo se pasa en el bucle de eventos externo de la aplicación. En este caso, el notificador debe organizar para que el bucle de eventos externo llame de nuevo a Tcl cuando ocurra un evento en los diversos fuentes de eventos Tcl. Estas callbacks deben organizar para colocar eventos adecuados en la cola de eventos Tcl.

Dado que el bucle de eventos externo no llama a Tcl_DoOneEvent de manera regular, es el notificador quien debe organizar para llamar a Tcl_ServiceEvent cada vez que haya eventos pendientes en la cola de eventos Tcl. La forma más fácil de hacer esto es invocar Tcl_ServiceAll al final de cada callback del bucle de eventos externo. Esto garantizará que todos los fuentes de eventos se listen, que los eventos cola se atiendan y que los handlers idles pendientes se procesen antes de devolver el control al programa. Además, los fuentes de eventos que necesiten ser listados para eventos pueden invocar Tcl_SetMaxBlockTime para forzar al bucle de eventos externo a llamar a Tcl incluso si no hay eventos en la cola de eventos del sistema.

Como efecto secundario de procesar eventos detectados en el bucle de eventos externo principal, Tcl puede invocar Tcl_DoOneEvent para iniciar un bucle de eventos recursivo en comandos como vwait. Tcl_DoOneEvent invocará al bucle de eventos externo, lo que resultará en callbacks como se describió anteriormente, que a su vez resultarán en llamadas a Tcl_ServiceAll. Sin embargo, en estos casos se desprecia el servicio de eventos en Tcl_ServiceAll. El servicio de eventos allí es innecesario porque el control se devuelve inmediatamente al bucle de eventos externo y por lo tanto a Tcl_DoOneEvent, que puede servir los eventos por sí mismo. Además, Tcl_DoOneEvent es supuesto para servir solo un evento, mientras que Tcl_ServiceAll normalmente sirve todos los eventos pendientes. Para manejar este situación, Tcl_DoOneEvent establece un flag para Tcl_ServiceAll que hace que éste devuelva sin servir ninguno de los eventos. Este flag se llama el modo de servicio; Tcl_DoOneEvent lo restaura a su valor anterior antes de devolverse.

En algunos casos, aunque sea necesario para Tcl_ServiceAll servir eventos incluso cuando se haya invocado desde Tcl_DoOneEvent. Esto ocurre cuando haya otro bucle de eventos recursivo invocado mediante un evento handler llamado por Tcl_DoOneEvent (como uno que forma parte de una widget nativa). En este caso, Tcl_DoOneEvent puede no tener la oportunidad de servir eventos, por lo que Tcl_ServiceAll debe servir todos los eventos. Cualquier bucle de eventos recursivo que llame a un bucle de eventos externo en lugar de Tcl_DoOneEvent debe resetear el modo de servicio para que todos los eventos sean procesados en Tcl_ServiceAll. Esto se hace invocando el procedimiento Tcl_SetServiceMode. Si Tcl_SetServiceMode se pasa TCL_SERVICE_NONE, entonces las llamadas a Tcl_ServiceAll devolverán inmediatamente sin procesar ningún evento. Si Tcl_SetServiceMode se pasa TCL_SERVICE_ALL, entonces las llamadas a Tcl_ServiceAll se comportarán normalmente. Tcl_SetServiceMode devuelve el valor anterior del modo de servicio, que debe ser restaurado cuando el bucle de eventos recursivo finalice. Tcl_GetServiceMode devuelve el valor actual del modo de servicio.

INTRODUCTION

Tcl proporciona un sistema de notificación y manejo de eventos sofisticado que permite a las aplicaciones responder a diversos tipos de eventos, como eventos de E/S, eventos de temporizador y eventos inactivos. El sistema de eventos se basa en una cola de eventos y un mecanismo de notificación que gestiona la espera y el procesamiento de eventos.

NOTIFIER BASICS

El componente central del sistema de eventos es el notifier. El notifier es responsable de esperar y señalar la disponibilidad de eventos. Tcl proporciona una implementación de notifier predeterminada, pero las aplicaciones pueden registrar su propio notifier personalizado utilizando la función Tcl_SetNotifier.

La estructura Tcl_NotifierProcs define la interfaz para un notifier. Contiene punteros a funciones para las siguientes operaciones:

  • discardEventProc: Descarta un evento de la cola.
  • processEventProc: Procesa un evento de la cola.
  • setupNextPollProc: Configura el mecanismo de espera para el próximo evento.
  • appendEventProc: Añade un evento a la cola de eventos.
  • alertNotifierProc: Se llama cuando ocurre un evento que requiere atención inmediata.
  • serviceQueueProc: Procesa todos los eventos pendientes en la cola.

La función Tcl_GetNotifier recupera el notifier actual registrado, y Tcl_AlertNotifier se puede usar para señalar al notifier que hay un evento pendiente.

La función Tcl_ServiceQueue procesa todos los eventos pendientes en la cola de eventos. Generalmente se llama dentro del bucle de eventos principal.

CREATING A NEW EVENT SOURCE

Las fuentes de eventos representan orígenes de eventos que no sean los eventos estándar de Tcl (como entrada/salida o temporizadores). Puede crear una nueva fuente de eventos utilizando la función Tcl_CreateEventSource. Esta función toma un puntero al intérprete, funciones de devolución de llamada para la preparación, la limpieza y los datos del cliente. La función readyProc se llama cuando la fuente de eventos está lista para su procesamiento, y la función setupProc se usa para configurar la espera de eventos para la fuente. Tcl_DeleteEventSource se usa para eliminar una fuente de eventos.

CREATING A NEW NOTIFIER

Para crear un nuevo notifier, debe definir una estructura Tcl_NotifierProcs con sus implementaciones de funciones personalizadas. Luego, llame a Tcl_SetNotifier para registrar su nuevo notifier. Esto permite un control total sobre cómo Tcl maneja la espera y el procesamiento de eventos.

REPLACING THE NOTIFIER

Puede reemplazar el notifier predeterminado de Tcl llamando a Tcl_SetNotifier con un puntero a su propia estructura Tcl_NotifierProcs. Esto es útil para integrar Tcl con sistemas de manejo de eventos existentes o para implementar un comportamiento de notificación personalizado.

EXTERNAL EVENT LOOPS

Tcl permite el uso de bucles de eventos externos. Puede establecer una función de bucle de eventos personalizada utilizando Tcl_SetEventLoopProc. La función Tcl_EventLoop ejecuta el bucle de eventos, y Tcl_MakeEventLoop inicializa el bucle de eventos para un intérprete determinado.

Las funciones relacionadas con hilos, como Tcl_CreateThread, Tcl_ExitThread, Tcl_JoinThread, Tcl_IsMainThread, Tcl_SetMainThread, Tcl_GetThreadData, Tcl_SetThreadData, Tcl_ThreadId y Tcl_FreeThreadData, proporcionan soporte para la programación multihilo dentro de las aplicaciones Tcl.
