DESCRIPCIÓN

Hay varias razones por las cuales se llaman las funciones de la API Tcl_FS (por ejemplo, Tcl_FSAccess y Tcl_FSStat) en lugar de llamar funciones de nivel sistema como access y stat directamente. Primero, estas funciones funcionarán de forma multiplataforma, así que una extensión que llame a ellas debería funcionar sin modificaciones en Unix y Windows. Segundo, la implementación de algunas de estas funciones en Windows corrige algunos errores en las llamadas de nivel sistema. Tercero, estas llamadas a funciones manejan cualquier conversión de rutas de tipo "UTF a nativa" que pueda ser requerida (y puede cachear los resultados de estas conversiones para mayor eficiencia en llamadas posteriores). Cuarto, y quizás lo más importante, todas estas funciones son "conscientes de sistemas virtuales" (VFS por sus siglas). Cualquier VFS registrado (a través de Tcl_FSRegister) puede redirigir el acceso a archivos a medios o métodos alternativos. Esto significa que todas estas funciones (y, por lo tanto, los comandos Tcl correspondientes file, glob, pwd, cd, open, etc.) pueden operar sobre "archivos" que no son archivos nativos en el sistema de archivos nativo. Esto también significa que cualquier extensión Tcl que acceda al sistema de archivos (FS por sus siglas) a través de esta API está automáticamente "consciente de sistemas virtuales". Obviamente, si una extensión accede al sistema de archivos nativo directamente (a través de APIs específicas del sistema, por ejemplo), entonces Tcl no puede interceptar tales llamadas.

Si los VFS se han registrado adecuadamente, los "archivos" pueden, como ejemplos, ser remotos (por ejemplo, situados en un servidor ftp remoto) o archivados (por ejemplo, situados dentro de un archivo .zip). Estos sistemas de archivos registrados proporcionan una tabla de funciones de búsqueda para implementar toda o parte de la funcionalidad mencionada aquí. Finalmente, las llamadas a Tcl_FSStat y Tcl_FSLstat abstraen lo que el buffer struct stat realmente es, permitiendo que el mismo código se utilice tanto en sistemas con como sin soporte para archivos de más de 2 GB.

La API Tcl_FS está "tipificada" como Tcl_Obj y puede cachear representaciones internas y otras cadenas relacionadas con rutas (por ejemplo, el directorio actual). Un efecto secundario de esto es que no se deben pasar valores con un contador de referencias cero a ninguna función de esta. Si se hubieran tratado así, podría haber errores de memoria (en ciertos casos, el código del sistema de archivos podría desechar una referencia al valor pasado y, por lo tanto, se debe notar que no se puede asumir que después de cualquier llamada a estas funciones el valor tenga un contador de referencias cero; podría haber sido incrementado). O bien, podría haber un fallo de segmentación (o error de acceso a memoria) debido a que el valor fue liberado durante el complejo proceso de manipulación del valor para garantizar que la ruta esté normalizada y sea absoluta para el sistema de archivos. La lección práctica a aprender es que:

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

es incorrecto y puede causar errores de memoria. El path debe incrementar su contador de referencias antes de pasarlo, o disminuirlo. Por esta razón, los valores con un contador de referencias cero se consideran no válidos como rutas de sistema de archivos y cualquier llamada a una función de la API Tcl_FS con dicho valor no produce ninguna acción.

FUNCIONES DE LA API Tcl_FS

Tcl_FSCopyFile intenta copiar el archivo dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas están en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), se llama a la función de copia de archivos del sistema de archivos. En otro caso, la función devuelve -1 y establece el valor global errno como el código POSIX EXDEV (que indica un enlace cruzado).

Tcl_FSCopyDirectory intenta copiar el directorio dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas están en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), se llama a la función de copia de directorios del sistema de archivos. En otro caso, la función devuelve -1 y establece el valor global errno como el código POSIX EXDEV (que indica un enlace cruzado).

Tcl_FSCreateDirectory intenta crear el directorio dado por pathPtr llamando a la función de crear directorios del sistema de archivos que le pertenece.

Tcl_FSDeleteFile intenta eliminar el archivo dado por pathPtr llamando a la función de eliminar archivos del sistema de archivos que le pertenece.

Tcl_FSRemoveDirectory intenta eliminar el directorio dado por pathPtr llamando a la función de eliminar directorios del sistema de archivos que le pertenece.

Tcl_FSRenameFile intenta renombrar el archivo o directorio dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas están en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), se llama a la función de renombrar archivos del sistema de archivos. En otro caso, la función devuelve -1 y establece el valor global errno como el código POSIX EXDEV (que indica un enlace cruzado).

Tcl_FSListVolumes llama a cada sistema de archivos que tenga una función list volumes no nula y le pide que devuelva su lista de volúmenes raíz. Acumula los valores devueltos en una lista que se devuelve al llamador (con un contador de referencias cero).

Tcl_FSEvalFileEx lee el archivo dado por pathPtr usando la codificación identificada por encodingName y evalúa su contenido como un script Tcl. Devuelve la misma información que Tcl_EvalObjEx. Si encodingName es NULL, se usa la codificación del sistema para leer el contenido del archivo. Si el archivo no puede ser leído, se devuelve un mensaje de error Tcl que describe por qué no se puede leer el archivo. El carácter EOF para los archivos es \x1A (^Z) para todos los sistemas. Si deseas usar \x1A en código para comparaciones de cadena, puedes usarlo, que será sustituido seguramente por el intérprete Tcl como \x1A. Tcl_FSEvalFile es una versión más simple de Tcl_FSEvalFileEx que siempre usa la codificación del sistema al leer el archivo.

Tcl_FSLoadFile carga dinámicamente un archivo binario en memoria y devuelve las direcciones de dos procedimientos dentro del archivo, si están definidos. Se llama a la función adecuada para el sistema de archivos al que pertenece pathPtr. Si dicho sistema de archivos no implementa esta función (la mayoría de sistemas de archivos virtuales no lo harán debido a limitaciones en la carga dinámica de código), Tcl intentará copiar el archivo a un directorio temporal y cargar ese archivo temporal. Tcl_FSUnloadFile revierte esta operación, solicitando que la biblioteca indicada por loadHandle sea eliminada del proceso. Nota que, a diferencia de con el comando unload, esto no da ninguna oportunidad a la biblioteca para limpiar.

Ambas funciones anteriores devuelven un código de finalización estándar de Tcl. Si ocurre un error, se deja un mensaje de error en el resultado del interp.

El token proporcionado por la variable indicada por loadHandlePtr puede usarse con Tcl_FindSymbol.

Tcl_FSMatchInDirectory es utilizada por el código de globbing para buscar todos los archivos que coincidan con un patrón dado en una carpeta. Se llama a la función adecuada para el sistema de archivos al que pertenece pathPtr.

El valor devuelto es un código de resultado estándar que indica si se produjo un error durante el globbing. Los mensajes de error se colocan en el interp (excepto si interp es NULL, lo cual está permitido), pero los resultados buenos se colocan en el resultPtr dado.

Nota que el código de glob implementa patrones recursivos internamente, por lo que esta función solo será llamada con patrones simples, que se pueden comparar con la lógica de string match. Para manejar la recursión, Tcl llama a esta función frecuentemente solicitando solo directorios para devolver. Un caso especial de ser llamada con un patrón nulo indica que la ruta necesita ser verificada solo por el tipo correcto.

Tcl_FSLink reemplaza la versión de readlink del sistema de bibliotecas y la extiende para soportar la creación de enlaces. Se llama a la función adecuada para el sistema de archivos al que pertenece linkNamePtr.

Si toPtr es NULL, se realiza una acción de "leer enlace". El resultado es un objeto Tcl que especifica el contenido del enlace dado por linkNamePtr, o NULL si el enlace no puede ser leído. El resultado es propiedad exclusiva del llamador, quien debe llamar a Tcl_DecrRefCount cuando el resultado ya no sea necesario. Si toPtr no es NULL, Tcl debería crear un enlace de uno de los tipos especificados en el bit linkAction. Este bit es una combinación OR de TCL_CREATE_SYMBOLIC_LINK y TCL_CREATE_HARD_LINK. Cuando hay una elección (es decir, se pasa más de un bit), la convención de Tcl es preferir enlaces simbólicos. Cuando un enlace se crea con éxito, el valor devuelto debe ser toPtr (que ya es propiedad del llamador). Si no se logra, se devuelve NULL.

Tcl_FSLstat llena la estructura Tcl_StatBuf con información sobre el archivo especificado. No se requiere ningún permiso para el archivo para obtener esta información, pero sí se requiere permiso de búsqueda para todos los directorios en la ruta que conduce al archivo. La estructura Tcl_StatBuf incluye información sobre el dispositivo, el inodo (siempre 0 en Windows), el modo de permisos, nlink (siempre 1 en Windows), uid (siempre 0 en Windows), gid (siempre 0 en Windows), rdev (igual que el dispositivo en Windows), tamaño, última modificación...

tiempo, tiempo de última modificación y tiempo de último cambio de metadatos. Consulte la API PORTABLE STAT RESULT para obtener una descripción de cómo escribir código portable para asignar y acceder a la estructura Tcl_StatBuf.

Si path existe, Tcl_FSLstat devuelve 0 y la estructura de estadísticas se rellena con datos. De lo contrario, se devuelve -1 y no se proporciona información de estadísticas.

Tcl_FSUtime reemplaza la versión de biblioteca de utime.

Esto devuelve 0 en caso de éxito y -1 en caso de error (según la documentación de utime). Si tiene éxito, la función actualizará los valores de "atime" y "mtime" del archivo proporcionado.

Tcl_FSFileAttrsGet implementa el acceso de lectura para el subcomando file attributes que se puede enganchar. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

Si el resultado es TCL_OK, entonces se colocó un valor en objPtrRef, que solo será válido temporalmente (a menos que se llame a Tcl_IncrRefCount).

Tcl_FSFileAttrsSet implementa el acceso de escritura para el subcomando file attributes que se puede enganchar. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

Tcl_FSFileAttrStrings implementa parte del subcomando file attributes que se puede enganchar. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

El procedimiento llamado puede devolver una matriz de cadenas o puede devolver NULL y colocar una lista Tcl en objPtrRef. Tcl tomará esa lista y primero incrementará su recuento de referencias antes de usarla. Al completar ese uso, Tcl disminuirá su recuento de referencias. Por lo tanto, si Tcl debe desechar la lista cuando termine, debería tener un recuento de referencias de cero, y si Tcl no debe desechar la lista, el sistema de archivos debe asegurarse de retener un recuento de referencias del valor.

Tcl_FSAccess verifica si al proceso se le permitiría leer, escribir o probar la existencia del archivo (u otro objeto del sistema de archivos) cuyo nombre es pathname. Si pathname es un enlace simbólico en Unix, entonces se prueban los permisos del archivo al que se refiere este enlace simbólico.

En caso de éxito (se otorgan todos los permisos solicitados), se devuelve cero. En caso de error (al menos un bit en el modo solicitó un permiso que se deniega, o ocurrió algún otro error), se devuelve -1.

Tcl_FSStat rellena la estructura Tcl_StatBuf statPtr con información sobre el archivo especificado. No necesita ningún derecho de acceso al archivo para obtener esta información, pero necesita derechos de búsqueda para todos los directorios nombrados en la ruta que conduce al archivo. La estructura Tcl_StatBuf incluye información sobre el dispositivo, el inodo (siempre 0 en Windows), el modo de privilegio, nlink (siempre 1 en Windows), el ID de usuario (siempre 0 en Windows), el ID de grupo (siempre 0 en Windows), rdev (igual que el dispositivo en Windows), el tamaño, el tiempo del último acceso, el tiempo de la última modificación y el tiempo del último cambio de metadatos. Consulte la API PORTABLE STAT RESULT para obtener una descripción de cómo escribir código portable para asignar y acceder a la estructura Tcl_StatBuf.

Si path existe, Tcl_FSStat devuelve 0 y la estructura de estadísticas se rellena con datos. De lo contrario, se devuelve -1 y no se proporciona información de estadísticas.

Tcl_FSOpenFileChannel abre un archivo especificado por pathPtr y devuelve un manejador de canal que se puede usar para realizar entrada y salida en el archivo. Esta API se basa en el procedimiento fopen de la biblioteca de E/S estándar de Unix. La sintaxis y el significado de todos los argumentos son similares a los dados en el comando open de Tcl al abrir un archivo. Si ocurre un error al abrir el canal, Tcl_FSOpenFileChannel devuelve NULL y registra un código de error POSIX que se puede recuperar con Tcl_GetErrno. Además, si interp no es NULL, Tcl_FSOpenFileChannel deja un mensaje de error en el resultado de interp después de cualquier error.

El canal recién creado no está registrado en el intérprete proporcionado; para registrarlo, use Tcl_RegisterChannel. Si uno de los canales estándar, stdin, stdout o stderr se cerró previamente, el acto de crear el nuevo canal también lo asigna como un reemplazo para el canal estándar.

Tcl_FSGetCwd reemplaza la versión de biblioteca de getcwd.

Devuelve el directorio de trabajo actual de la biblioteca Tcl. Este puede ser diferente al directorio de trabajo de la plataforma nativa, lo que ocurre cuando el directorio de trabajo actual no está en el sistema de archivos nativo.

El resultado es un puntero a un Tcl_Obj que especifica el directorio actual, o NULL si no se pudo determinar el directorio actual. Si se devuelve NULL, se deja un mensaje de error en el resultado de interp.

El resultado ya tiene incrementado su recuento de referencias para el llamador. Cuando ya no sea necesario, ese recuento de referencias debe disminuirse. Esto es necesario por motivos de seguridad de subprocesos, para permitir que varios subprocesos accedan a esta y funciones relacionadas, al tiempo que se garantiza que los resultados sean siempre válidos.

Tcl_FSChdir reemplaza la versión de biblioteca de chdir. La ruta se normaliza y luego se pasa al sistema de archivos que la reclama. Si ese sistema de archivos no implementa esta función, Tcl recurrirá a una combinación de stat y access para verificar si el directorio existe y tiene los permisos apropiados.

Para los resultados, consulte la documentación de chdir. Si tiene éxito, mantenemos un registro de la ruta exitosa en cwdPathPtr para llamadas posteriores a Tcl_FSGetCwd.

Tcl_FSPathSeparator devuelve el carácter separador que se utilizará para el elemento más específico de la ruta especificada por pathPtr (es decir, la última parte de la ruta).

El separador se devuelve como un Tcl_Obj que contiene una cadena de longitud 1. Si la ruta no es válida, se devuelve NULL.

Tcl_FSJoinPath toma el Tcl_Obj dado, que debe ser una lista válida (a la que se permite tener un recuento de referencias de cero), y devuelve el valor de la ruta dado al considerar los primeros elementos elementos como segmentos de ruta válidos (cada segmento de ruta puede ser una ruta completa, una ruta parcial o solo un solo directorio o nombre de archivo posible). Si algún segmento de ruta es en realidad una ruta absoluta, todos los segmentos de ruta anteriores se descartan. Si elementos es menor que 0, usamos toda la lista.

Es posible que el valor devuelto sea en realidad un elemento de la lista dada, por lo que el llamador debe tener cuidado de incrementar el recuento de referencias del resultado antes de liberar la lista.

El valor devuelto, típicamente con un recuento de referencias de cero (pero podría compartirse bajo algunas condiciones), contiene la ruta unida. El llamador debe agregar un recuento de referencias al valor antes de usarlo. En particular, el valor devuelto podría ser un elemento de la lista dada, por lo que liberar la lista podría liberar el valor prematuramente si no se ha tomado ningún recuento de referencias. Si el número de elementos es cero, entonces el valor devuelto será un Tcl_Obj de cadena vacía.

Tcl_FSSplitPath toma el Tcl_Obj dado, que debe ser una ruta válida, y devuelve un valor de lista Tcl que contiene cada segmento de esa ruta como un elemento. Devuelve un valor de lista con un recuento de referencias de cero. Si el lenPtr pasado no es NULL, la variable a la que apunta se actualizará para contener el número de elementos en la lista devuelta.

Tcl_FSEqualPaths prueba si las dos rutas dadas representan el mismo objeto del sistema de archivos. Devuelve 1 si las rutas son iguales y 0 si son diferentes. Si alguna ruta es NULL, siempre se devuelve 0.

Tcl_FSGetNormalizedPath intenta extraer del Tcl_Obj dado una representación de ruta normalizada única, cuyo valor de cadena se puede usar como identificador único del archivo.

Devuelve el valor de ruta normalizada, propiedad de Tcl, o NULL si la ruta no era válida o no se pudo convertir correctamente. La extracción de rutas absolutas y normalizadas es muy eficiente (porque el sistema de archivos opera en estas representaciones internamente), aunque el resultado cuando el sistema de archivos contiene numerosos enlaces simbólicos puede no ser la versión más fácil de usar de una ruta. El valor de retorno es propiedad de Tcl y tiene una vida útil equivalente a la de pathPtr pasado (a menos que sea una ruta relativa, en cuyo caso el valor de ruta normalizada puede liberarse en cualquier momento en que cambie la cwd): el llamador, por supuesto, puede incrementar el recuento de referencias si desea mantener una copia por más tiempo.

Tcl_FSJoinToPath toma el valor dado, que generalmente debería ser una ruta válida o NULL, y une a ella la matriz de segmentos de ruta proporcionados.

Devuelve un valor, típicamente con un recuento de referencias de cero (pero podría compartirse bajo algunas condiciones), que contiene la ruta unida. El llamador debe agregar un recuento de referencias al valor antes de usarlo. Si alguno de los valores pasados a esta función (pathPtr o elementos de path) tiene un recuento de referencias de cero, se liberarán cuando esta función regrese.

Tcl_FSConvertToPathType intenta convertir el Tcl_Obj dado a un tipo de ruta Tcl válido, teniendo en cuenta el hecho de que la cwd puede haber cambiado incluso si este valor ya es supuestamente del tipo correcto. El nombre de archivo puede comenzar con "~" (para indicar el directorio de inicio del usuario actual) o "~<usuario>" (para indicar el directorio de inicio de cualquier usuario).

Si la conversión tiene éxito (es decir, el valor es una ruta válida en uno de los sistemas de archivos actuales), entonces se devuelve TCL_OK. De lo contrario, se devuelve TCL_ERROR, y se puede dejar un mensaje de error en el intérprete.

Tcl_FSGetInternalRep extrae la representación interna de un valor de ruta dado, en el sistema de archivos dado. Si el valor de ruta pertenece a un sistema de archivos diferente, devolvemos NULL. Si la representación interna es actualmente NULL, intentamos generarla, llamando a Tcl_FSCreateInternalRepProc del sistema de archivos.

Devuelve NULL o una representación de ruta interna válida. Esta representación interna se almacena en caché, de modo que las llamadas repetidas a esta función no requerirán conversiones adicionales.

Tcl_FSGetTranslatedPath intenta extraer la ruta traducida del Tcl_Obj dado.

Si la traducción tiene éxito (es decir, el valor es una ruta válida), entonces se devuelve. De lo contrario, se devolverá NULL, y se puede dejar un mensaje de error en el intérprete. Una ruta "traducida" es aquella que no contiene secuencias "~" o "~usuario" (estas se han expandido a su representación actual en el sistema de archivos). El valor devuelto es propiedad del llamador, que debe almacenarlo o llamar a Tcl_DecrRefCount para garantizar que la memoria se libere. Esta función tiene poco uso práctico, y Tcl_FSGetNormalizedPath o Tcl_FSGetNativePath son generalmente funciones mejores para usar en la mayoría de los propósitos.

Tcl_FSGetTranslatedStringPath hace lo mismo que Tcl_FSGetTranslatedPath, pero devuelve una cadena de caracteres o NULL. La cadena devuelta está asignada dinámicamente

y que es propiedad del llamador, el cual debe almacenarlo o llamar a ckfree para asegurar que sea liberado. Nuevamente, Tcl_FSGetNormalizedPath o Tcl_FSGetNativePath son generalmente funciones mejores para usar en la mayoría de los propósitos.

Tcl_FSNewNativePath realiza algo así como la operación inversa de las conversiones habituales obj->path->nativerep. Si algún código recupera una ruta en formato nativo (desde, por ejemplo, readlink o un diálogo nativo), y esa ruta va a ser utilizada a nivel de Tcl, entonces llamar a esta función es una forma eficiente de crear el tipo de valor de ruta apropiado.

El valor resultante es un valor de tipo "ruta" puro, que solo recibirá una representación de cadena UTF-8 si así lo requiere algún código Tcl.

Tcl_FSGetNativePath es para uso de los sistemas de archivos nativos Win/Unix, para que puedan recuperar fácilmente la representación nativa (char* o TCHAR*) de una ruta. Esta función es un envoltorio de conveniencia alrededor de Tcl_FSGetInternalRep. Podría ser deseable en el futuro tener representaciones nativas no basadas en cadenas (por ejemplo, en macOS, una representación que use una estructura FSRef de fileSpec probablemente sería más eficiente). En Windows, una representación Unicode completa permitiría rutas de longitud ilimitada. Actualmente, la representación es simplemente una cadena de caracteres que puede contener la ruta relativa o una ruta completa, normalizada y absoluta en la codificación nativa (condiciones complejas dictan cuál de estas se proporcionará, por lo que no se puede confiar en ninguna de ellas, a menos que se sepa que la ruta es absoluta). Si necesita una ruta nativa que deba ser absoluta, entonces debe solicitar la versión nativa de una ruta normalizada. Si por alguna razón se necesita una versión no absoluta y no normalizada de la ruta, esta debe construirse por separado (por ejemplo, usando Tcl_FSGetTranslatedPath).

La representación nativa se almacena en caché para que las llamadas repetidas a esta función no requieran conversiones adicionales. El valor de retorno es propiedad de Tcl y tiene una vida útil equivalente a la del pathPtr pasado (a menos que sea una ruta relativa, en cuyo caso la representación nativa puede liberarse en cualquier momento que cambie el cwd).

Tcl_FSFileSystemInfo devuelve una lista de dos elementos. El primer elemento es el nombre del sistema de archivos (por ejemplo, "native", "vfs", "zip", o "prowrap", quizás), y el segundo es el tipo particular de la ruta dada dentro de ese sistema de archivos (que depende del sistema de archivos). El segundo elemento puede estar vacío si el sistema de archivos no proporciona una categorización adicional de los archivos.

Se devuelve un valor de lista válido, a menos que el valor de la ruta no sea reconocido, en cuyo caso se devolverá NULL.

Tcl_FSGetFileSystemForPath devuelve un puntero al Tcl_Filesystem que acepta esta ruta como válida.

Si ningún sistema de archivos acepta la ruta, se devuelve NULL.

Tcl_FSGetPathType determina si la ruta dada es relativa al directorio actual, relativa al volumen actual o absoluta.

Devuelve uno de TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE, o TCL_PATH_VOLUME_RELATIVE

LA API DEL SISTEMA DE ARCHIVOS VIRTUAL

Un sistema de archivos proporciona una estructura Tcl_Filesystem que contiene punteros a funciones que implementan las diversas operaciones en un sistema de archivos; estas operaciones se invocan según sea necesario por la capa genérica, lo que generalmente ocurre a través de las funciones listadas anteriormente.

Las estructuras Tcl_Filesystem se manipulan utilizando los siguientes métodos.

Tcl_FSRegister toma un puntero a una estructura de sistema de archivos y un dato opcional para asociarlo con ese sistema de archivos. Al llamar a esta función, Tcl adjuntará el sistema de archivos a la lista de sistemas de archivos conocidos, y se volverá completamente funcional inmediatamente. Tcl no verifica si el mismo sistema de archivos se registra múltiples veces (y en general, eso no es algo bueno de hacer). Se devolverá TCL_OK.

Tcl_FSUnregister elimina la estructura del sistema de archivos dada de la lista de sistemas de archivos conocidos, si está registrada, y devuelve TCL_OK. Si el sistema de archivos no está actualmente registrado, se devuelve TCL_ERROR.

Tcl_FSData devolverá el clientData asociado con el sistema de archivos dado, si ese sistema de archivos está registrado. De lo contrario, devolverá NULL.

Tcl_FSMountsChanged se utiliza para informar al núcleo de Tcl que el conjunto de puntos de montaje para el sistema de archivos dado (ya registrado) ha cambiado, y que, por lo tanto, las representaciones de archivos almacenadas en caché pueden ya no ser correctas.

Las muchas funciones en esta estructura se dividen en tres categorías: funciones de infraestructura (casi todas las cuales deben implementarse), funciones operativas (que deben implementarse si se proporciona un sistema de archivos completo) y funciones de eficiencia (que solo necesitan implementarse si se pueden hacer de manera eficiente, o si tienen efectos secundarios que son requeridos por el sistema de archivos; Tcl tiene emulaciones menos eficientes a las que puede recurrir). Es importante tener en cuenta que, en la versión actual de Tcl, la mayoría de estas sustituciones solo se utilizan para manejar comandos iniciados en Tcl, no en C. Lo que esto significa es que, si se emite un comando file rename en Tcl, y el(los) sistema(s) de archivos relevantes no implementan su Tcl_FSRenameFileProc, el núcleo de Tcl recurrirá a una combinación de otras funciones del sistema de archivos (utilizará Tcl_FSCopyFileProc seguido de Tcl_FSDeleteFileProc, y si Tcl_FSCopyFileProc no está implementado, hay una sustitución adicional). Sin embargo, si se emite un comando Tcl_FSRenameFileProc a nivel de C, no ocurren tales sustituciones. Esto es cierto excepto para las últimas cuatro entradas en la tabla del sistema de archivos (lstat, load, getcwd y chdir) para las cuales sí ocurren sustituciones a nivel de C.

Cualquier función que tome nombres de ruta en forma de Tcl_Obj toma esos nombres en forma UTF-8. La API de infraestructura del sistema de archivos está diseñada para admitir la conversión eficiente y en caché de estas rutas UTF-8 a otras representaciones nativas.

Función para procesar una llamada a Tcl_FSOpenFileChannel. Debe ser implementada para cualquier sistema de archivos razonable, ya que cualquier operación que requiera abrir o acceder al contenido de un archivo la utilizará (por ejemplo, open, encoding y muchos comandos de Tk).

        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

Tcl_FSOpenFileChannelProc abre un archivo especificado por pathPtr y devuelve un manejador de canal que puede ser utilizado para realizar entrada y salida en el archivo. Esta API está modelada después del procedimiento fopen de la biblioteca estándar de E/S de Unix. La sintaxis y el significado de todos los argumentos son similares a los dados en el comando open de Tcl al abrir un archivo, donde el argumento mode es una combinación de las banderas POSIX O_RDONLY, O_WRONLY, etc. Si ocurre un error al abrir el canal, Tcl_FSOpenFileChannelProc devuelve NULL y registra un código de error POSIX que puede ser recuperado con Tcl_GetErrno. Además, si interp no es NULL, Tcl_FSOpenFileChannelProc deja un mensaje de error en el resultado de interp después de cualquier error.

El canal recién creado no debe ser registrado en el intérprete proporcionado por Tcl_FSOpenFileChannelProc; esa tarea corresponde al llamador de Tcl_FSOpenFileChannel (si es necesario). Si uno de los canales estándar, stdin, stdout o stderr fue cerrado previamente, la acción de crear el nuevo canal también lo asigna como reemplazo del canal estándar.

        const char *pattern,
        Tcl_GlobTypeData *types);

La función debe devolver todos los archivos o directorios (u otros objetos del sistema de archivos) que coincidan con el patrón dado y que se ajusten a la especificación de types. Hay dos maneras en que esta función puede ser llamada. Si pattern es NULL, entonces pathPtr es una especificación de ruta completa de un solo archivo o directorio que debe ser verificado en cuanto a existencia y tipo correcto. De lo contrario, pathPtr es un directorio, cuyo contenido la función debe buscar archivos o directorios que tengan el tipo correcto. En cualquier caso, se puede asumir que pathPtr no es NULL y no está vacío. Actualmente no está documentado si pathPtr tendrá un separador de archivo al final o no, por lo que el código debe ser flexible a ambas posibilidades.

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso de coincidencia. Los mensajes de error se colocan en interp, a menos que interp sea NULL, en cuyo caso no es necesario generar ningún mensaje de error; en un resultado TCL_OK, los resultados deben agregarse al valor dado de resultPtr (que se puede asumir que es una lista válida y no compartida de Tcl). Las coincidencias agregadas a resultPtr deben incluir cualquier prefijo de ruta dado en pathPtr (esto generalmente significa que serán especificaciones de ruta absoluta). Tenga en cuenta que si no se encuentran coincidencias, eso simplemente conduce a un resultado vacío; los errores solo se señalan por problemas reales de archivos o del sistema de archivos que puedan ocurrir durante el proceso de coincidencia.

La estructura Tcl_GlobTypeData pasada en el parámetro types contiene los siguientes campos:

typedef struct Tcl_GlobTypeData {
    /* Corresponde a bcdpfls como en 'find -t' */
    int type;
    /* Corresponde a permisos de archivo */
    int perm;
    /* Tipo Mac aceptable */
    Tcl_Obj *macType;
    /* Creador Mac aceptable */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Hay dos casos específicos que es importante manejar correctamente, ambos cuando types no es NULL. Los dos casos son cuando types->types & TCL_GLOB_TYPE_DIR o types->types & TCL_GLOB_TYPE_MOUNT son verdaderos (y en particular cuando las otras banderas son falsas). En el primero de estos casos, la función debe listar los directorios contenidos. Tcl utiliza esto para implementar el globbing recursivo, por lo que es crítico que los sistemas de archivos implementen la coincidencia de directorios correctamente. En el segundo de estos casos, con TCL_GLOB_TYPE_MOUNT, el sistema de archivos debe listar los puntos de montaje que se encuentran dentro del pathPtr dado (y en este caso, pathPtr no necesariamente debe estar dentro del mismo sistema de archivos; diferente a todos los demás casos en los que se llama a esta función). El soporte para esto es crítico si Tcl quiere tener transiciones fluidas de un sistema de archivos a otro.

UTIMEPROC

Función para procesar una llamada a Tcl_FSUtime. Requerida para permitir el establecimiento (no la lectura) de tiempos con file mtime, file atime y la implementación open-r/open-w/fcopy de file copy.

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

Los tiempos de acceso y modificación del archivo especificado por pathPtr deben ser cambiados a los valores dados en la estructura tval.

El valor de retorno debe ser 0 en caso de éxito y -1 en caso de error, al igual que con la llamada del sistema utime.

LINKPROC

Función para procesar una llamada a Tcl_FSLink. Debe ser implementada solo si el sistema de archivos soporta enlaces, y de lo contrario puede ser NULL.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

Si toPtr es NULL, se le está pidiendo a la función que lea el contenido de un enlace. El resultado es un Tcl_Obj que especifica el contenido del enlace dado por linkNamePtr, o NULL si el enlace no pudo ser leído. El resultado es propiedad del llamador (y por lo tanto, su contador de referencias debe ser incrementado antes de ser devuelto). Cualquier llamador debe llamar a Tcl_DecrRefCount en este resultado cuando ya no sea necesario. Si toPtr no es NULL, la función debe intentar crear un enlace. El resultado en este caso debe ser toPtr si el enlace fue exitoso y NULL en caso contrario. En este caso, el resultado no es propiedad del llamador (es decir, no se necesitan manipulaciones del contador de referencias en ninguno de los extremos). Consulte la documentación de Tcl_FSLink para la interpretación correcta de las banderas de linkAction.

LISTVOLUMESPROC

Función para listar cualquier volumen de sistema de archivos agregado por este sistema de archivos. Debe ser implementada solo si el sistema de archivos agrega volúmenes al principio del sistema de archivos, para que puedan ser devueltos por file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

El resultado debe ser una lista de volúmenes agregados por este sistema de archivos, o NULL (o una lista vacía) si no se proporcionan volúmenes. Se considera que el valor de resultado es propiedad del sistema de archivos (no del núcleo de Tcl), pero se le debe dar un contador de referencias para Tcl. Tcl utilizará el contenido de la lista y luego decrementará ese contador de referencias. Esto permite a los sistemas de archivos elegir si realmente desean conservar una lista "global" de volúmenes o no (si no, generan la lista sobre la marcha y la pasan a Tcl con un contador de referencias de 1 y luego se olvidan de la lista; si sí, simplemente incrementan el contador de referencias de su lista global y la pasan a Tcl, que copiará el contenido y luego decrementará el contador de vuelta a donde estaba).

Por lo tanto, Tcl considera que los valores de retorno de este proc son de solo lectura.

FILEATTRSTRINGSPROC

Función para listar todas las cadenas de atributos que son válidas para este sistema de archivos. Si no se implementa, el sistema de archivos no admitirá el comando file attributes. Esto permite adjuntar información adicional arbitraria a los archivos en el sistema de archivos. Si no se implementa, no es necesario implementar los métodos de get y set.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

La función llamada puede devolver una matriz de cadenas o puede devolver NULL y colocar una lista de Tcl en objPtrRef. Tcl tomará esa lista y primero incrementará su contador de referencias antes de usarla. Al finalizar ese uso, Tcl decrementará su contador de referencias. Por lo tanto, si la lista debe ser eliminada por Tcl cuando termine, debe tener un contador de referencias de cero, y si la lista no debe ser eliminada, el sistema de archivos debe asegurarse de devolver un valor con un contador de referencias de al menos uno.

FILEATTRSGETPROC

Función para procesar una llamada a Tcl_FSFileAttrsGet, utilizada por file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

Devuelve un código de retorno estándar de Tcl. El valor del atributo recuperado, que corresponde al elemento index de la lista devuelta por Tcl_FSFileAttrStringsProc, es un Tcl_Obj colocado en objPtrRef (si se devolvió TCL_OK) y es probable que tenga un contador de referencias de cero. En cualquier caso, debemos almacenarlo en algún lugar (por ejemplo, el resultado de Tcl) o incrementar/decrementar su contador de referencias para asegurar que se libere correctamente.

FILEATTRSSETPROC

Función para procesar una llamada a Tcl_FSFileAttrsSet, utilizada por file attributes. Si el sistema de archivos es de solo lectura, no es necesario implementar esto.

typedef int Tcl_FSFileAttrsSetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj *objPtr);

El valor del atributo del elemento index en la lista devuelta por Tcl_FSFileAttrStringsProc debe establecerse en el objPtr dado.

REMOVEDIRECTORYPROC

Función para procesar una llamada a Tcl_FSRemoveDirectory. Debe implementarse a menos que el sistema de archivos sea de solo lectura.

typedef int Tcl_FSRemoveDirectoryProc(
        Tcl_Obj *pathPtr,
        int recursive,
        Tcl_Obj **errorPtr);

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso. Si tiene éxito, el directorio especificado por pathPtr debe haber sido eliminado del sistema de archivos. Si se proporciona la bandera recursive, entonces un directorio no vacío debe ser eliminado sin error. Si esta bandera no se proporciona, y el directorio está no vacío, se debe señalar un error POSIX "EEXIST". Si ocurre un error, el nombre del archivo o directorio que causó el error debe colocarse en errorPtr.

DELETEFILEPROC

Función para procesar una llamada a Tcl_FSDeleteFile. Debe implementarse a menos que el sistema de archivos sea de solo lectura.

typedef int Tcl_FSDeleteFileProc(
        Tcl_Obj *pathPtr);

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso. Si tiene éxito, el archivo especificado por pathPtr debe haber sido eliminado del sistema de archivos. Tenga en cuenta que, si el sistema de archivos admite enlaces simbólicos, Tcl siempre llamará a esta función y no a Tcl_FSRemoveDirectoryProc cuando sea necesario eliminarlos (incluso si son enlaces simbólicos a directorios).

EFICIENCIA DEL SISTEMA DE ARCHIVOS

Estas funciones no necesitan ser implementadas para un sistema de archivos particular porque el núcleo tiene una implementación de respaldo disponible. Consulte la descripción individual de cada una para conocer las consecuencias de dejar el campo NULL.

LSTATPROC

Función para procesar una llamada a Tcl_FSLstat. Si no se implementa, Tcl intentará usar la statProc definida anteriormente en su lugar. Por lo tanto, solo necesita ser implementada si un sistema de archivos puede diferenciar entre las llamadas stat y lstat.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

El comportamiento de esta función es muy similar al de Tcl_FSStatProc definido anteriormente, excepto que si se aplica a un enlace simbólico, devuelve información sobre el enlace, no sobre el archivo de destino.

COPYFILEPROC

Función para procesar una llamada a Tcl_FSCopyFile. Si no se implementa, Tcl recurrirá a open-r, open-w y fcopy como mecanismo de copia. Por lo tanto, solo necesita ser implementada si el sistema de archivos puede realizar esa acción de manera más eficiente.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso de copia. Tenga en cuenta que destPathPtr es el nombre del archivo que se convertirá en la copia de srcPathPtr. Nunca es el nombre de un directorio en el que se pueda copiar srcPathPtr (es decir, la función es mucho más simple que el subcomando file copy a nivel de Tcl). Tenga en cuenta que, si el sistema de archivos admite enlaces simbólicos, Tcl siempre llamará a esta función y no a copyDirectoryProc cuando sea necesario copiarlos (incluso si son enlaces simbólicos a directorios). Finalmente, si el sistema de archivos determina que no puede admitir la acción file copy, llamar a Tcl_SetErrno(EXDEV) y devolver un resultado que no sea TCL_OK le indicará a Tcl que utilice sus mecanismos de respaldo estándar.

RENAMEFILEPROC

Función para procesar una llamada a Tcl_FSRenameFile. Si no se implementa, Tcl recurrirá a un mecanismo de copia y eliminación. Por lo tanto, solo necesita ser implementada si el sistema de archivos puede realizar esa acción de manera más eficiente.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso de renombrado. Si el sistema de archivos determina que no puede admitir la acción file rename, llamar a Tcl_SetErrno(EXDEV) y devolver un resultado que no sea TCL_OK le indicará a Tcl que utilice sus mecanismos de respaldo estándar.

COPYDIRECTORYPROC

Función para procesar una llamada a Tcl_FSCopyDirectory. Si no se implementa, Tcl recurrirá a un mecanismo recursivo de file mkdir y file copy. Por lo tanto, solo necesita ser implementada si el sistema de archivos puede realizar esa acción de manera más eficiente.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso de copia. Si ocurre un error, el nombre del archivo o directorio que causó el error debe colocarse en errorPtr. Tenga en cuenta que destPathPtr es el nombre del directorio que se convertirá en la imagen especular de srcPathPtr. No es el nombre de un directorio en el que se pueda copiar srcPathPtr (es decir, la función es mucho más simple que el subcomando file copy a nivel de Tcl). Finalmente, si el sistema de archivos determina que no puede admitir la acción de copia de directorios, llamar a Tcl_SetErrno(EXDEV) y devolver un resultado que no sea TCL_OK le indicará a Tcl que utilice sus mecanismos de respaldo estándar.

LOADFILEPROC

Función para procesar una llamada a Tcl_FSLoadFile. Si no se implementa, Tcl recurrirá a copiar a un archivo temporal nativo y luego a un Tcl_FSLoadFile en esa copia temporal. Por lo tanto, solo necesita ser implementada si el sistema de archivos puede cargar código directamente, o puede ser implementada simplemente para devolver TCL_ERROR para deshabilitar la funcionalidad de carga en este sistema de archivos por completo.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Devuelve un código de finalización estándar de Tcl. Si ocurre un error, se deja un mensaje de error en el resultado del interp. La función carga dinámicamente un archivo de código binario en memoria. En una carga exitosa, handlePtr debe llenarse con un token para el archivo cargado dinámicamente, y unloadProcPtr debe llenarse con la dirección de un procedimiento. El procedimiento de descarga se llamará con el Tcl_LoadHandle dado como su único parámetro cuando Tcl necesite descargar el archivo. Por ejemplo, para el sistema de archivos nativo, el Tcl_LoadHandle devuelto es actualmente un token que se puede usar en el TclpFindSymbol privado para acceder a funciones en el nuevo código. Cada sistema de archivos es libre de definir el Tcl_LoadHandle como lo requiera. Finalmente, si el sistema de archivos determina que no puede admitir la acción de carga de archivos, llamar a Tcl_SetErrno(EXDEV) y devolver un resultado que no sea TCL_OK le indicará a Tcl que utilice sus mecanismos de respaldo estándar.

UNLOADFILEPROC

Función para descargar un archivo previamente cargado con éxito. Si se implementó la carga, entonces esto también debe implementarse, si hay alguna acción de limpieza requerida.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

Función para procesar una llamada a Tcl_FSGetCwd. La mayoría de los sistemas de archivos no necesitan implementar esto. Generalmente solo se llamará una vez, si getcwd se llama antes que chdir. Puede ser NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

Si el sistema de archivos admite una noción nativa de directorio de trabajo actual (que quizás podría cambiar independientemente de Tcl), esta función debe devolver ese directorio de trabajo actual como resultado, o NULL si el directorio actual no se pudo determinar (por ejemplo, el usuario no tiene los permisos apropiados en el directorio actual). Si se devuelve NULL, se deja un mensaje de error en el resultado del interp.

CHDIRPROC

Función para procesar una llamada a Tcl_FSChdir. Si los sistemas de archivos no implementan esto, se emulará mediante una serie de verificaciones de acceso a directorios. De lo contrario, los sistemas de archivos virtuales que sí lo implementan solo necesitan responder con un resultado positivo si pathPtr es un directorio válido y accesible en su sistema de archivos. No necesitan recordar el resultado, ya que se recordará automáticamente para su uso por Tcl_FSGetCwd. Los sistemas de archivos reales deben llevar a cabo la acción correcta (es decir, llamar a la API de sistema chdir correcta).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

El Tcl_FSChdirProc cambia el directorio de trabajo actual de la aplicación al valor especificado en pathPtr. La función devuelve -1 en caso de error o 0 en caso de éxito.
