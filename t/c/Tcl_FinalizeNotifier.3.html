Tcl_EventSetupProc *setupProc (entrada)
Procedimiento a invocar para preparar la espera de eventos en Tcl_DoOneEvent.
Tcl_EventCheckProc *checkProc (entrada)
Procedimiento para que Tcl_DoOneEvent lo invoque después de esperar eventos. Comprueba si se han producido eventos y, en caso afirmativo, los pone en cola.
ClientData clientData (entrada)
Valor arbitrario de una palabra para pasar a setupProc, checkProc o deleteProc.
const Tcl_Time *timePtr (entrada)
Indica la cantidad máxima de tiempo de espera para un evento. Se especifica como un intervalo (cuánto tiempo esperar), no como una hora absoluta (cuándo despertar). Si el puntero pasado a Tcl_WaitForEvent es NULL, significa que no hay un tiempo máximo de espera: esperar indefinidamente si es necesario.
Tcl_Event *evPtr (entrada)
Un evento para añadir a la cola de eventos. El espacio para el evento debe haber sido asignado por el llamador usando Tcl_Alloc o ckalloc.
Tcl_QueuePosition position (entrada)
Dónde añadir el nuevo evento en la cola: TCL_QUEUE_TAIL, TCL_QUEUE_HEAD, o TCL_QUEUE_MARK.
Tcl_ThreadId threadId (entrada)
Un identificador único para un hilo.
Tcl_EventDeleteProc *deleteProc (entrada)
Procedimiento a invocar para cada evento en cola en Tcl_DeleteEvents.

Qué tipos de eventos deben ser atendidos. Estas banderas son las mismas que las pasadas a Tcl_DoOneEvent.
int mode (entrada)
Indica si los eventos deben ser atendidos por Tcl_ServiceAll. Debe ser uno de TCL_SERVICE_NONE o TCL_SERVICE_ALL.

Estructura de punteros de función que describe los procedimientos del notificador que van a reemplazar a los instalados en el ejecutable. Consulte **REEMPLAZANDO EL NOTIFICADOR** para más detalles.

INTRODUCCIÓN

Las interfaces descritas aquí se utilizan para personalizar el bucle de eventos de Tcl. Las dos personalizaciones más comunes son añadir nuevas fuentes de eventos y fusionar el bucle de eventos de Tcl con otro bucle de eventos, como uno proporcionado por una aplicación en la que Tcl está incrustado. Cada una de estas tareas se describe en una sección separada a continuación.

Los procedimientos de esta entrada del manual son los bloques de construcción de los que está hecho el notificador de eventos de Tcl. El notificador de eventos es la capa más baja en el mecanismo de eventos de Tcl. Consta de tres partes:

[1]
Fuentes de eventos: estas representan las formas en que se pueden generar eventos. Por ejemplo, hay una fuente de eventos de temporizador que implementa el procedimiento Tcl_CreateTimerHandler y el comando after, y hay una fuente de eventos de archivo que implementa el procedimiento Tcl_CreateFileHandler en sistemas Unix. Una fuente de eventos debe trabajar con el notificador para detectar eventos en los momentos adecuados, registrarlos en la cola de eventos y, finalmente, notificar al software de nivel superior que han ocurrido. Los procedimientos Tcl_CreateEventSource, Tcl_DeleteEventSource, Tcl_SetMaxBlockTime, Tcl_QueueEvent y Tcl_DeleteEvents son utilizados principalmente por las fuentes de eventos.
[2]
La cola de eventos: para aplicaciones no multihilo, hay una única cola para toda la aplicación, que contiene eventos que han sido detectados pero no aún atendidos. Las fuentes de eventos colocan eventos en la cola para que puedan ser procesados en orden en momentos apropiados durante el bucle de eventos. La cola de eventos garantiza una disciplina justa de manejo de eventos, de modo que ninguna fuente de eventos pueda dejar a las otras sin atención. También permite guardar eventos para ser atendidos en un futuro. Las aplicaciones multihilo funcionan de manera similar, excepto que hay una cola de eventos separada para cada hilo que contiene un intérprete Tcl. Tcl_QueueEvent se utiliza (principalmente por las fuentes de eventos) para añadir eventos a la cola de eventos y Tcl_DeleteEvents se usa para eliminar eventos de la cola sin procesarlos. En una aplicación multihilo, Tcl_QueueEvent añade un evento a la cola del hilo actual, y Tcl_ThreadQueueEvent añade un evento a la cola de un hilo específico.
[3]
El bucle de eventos: para detectar y procesar eventos, la aplicación entra en un bucle que espera a que ocurran los eventos, los coloca en la cola de eventos y luego los procesa. La mayoría de las aplicaciones lo harán llamando al procedimiento Tcl_DoOneEvent, que se describe en una entrada de manual separada.

La mayoría de las aplicaciones Tcl no necesitan preocuparse por los detalles internos del notificador de Tcl. Sin embargo, el notificador ahora tiene suficiente flexibilidad para ser reorientado bien para una nueva plataforma o para usar un bucle de eventos externo (como el bucle de eventos de Motif, cuando Tcl está incrustado en una aplicación de Motif). Los procedimientos Tcl_WaitForEvent y Tcl_SetTimer son normalmente implementados por Tcl, pero pueden ser reemplazados con nuevas versiones para reorientar el notificador (los procedimientos Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_Sleep, Tcl_CreateFileHandler y Tcl_DeleteFileHandler también deben ser reemplazados; consulte CREANDO UN NUEVO NOTIFICADOR a continuación para más detalles). Los procedimientos Tcl_ServiceAll, Tcl_ServiceEvent, Tcl_GetServiceMode y Tcl_SetServiceMode se proporcionan para ayudar a conectar el bucle de eventos de Tcl con un bucle de eventos externo como el de Motif.

CONCEPTOS BÁSICOS DEL NOTIFICADOR

La forma más sencilla de entender cómo funciona el notificador es considerar lo que sucede cuando se llama a Tcl_DoOneEvent. A Tcl_DoOneEvent se le pasa un argumento de flags que indica qué tipo de eventos está permitido procesar y si debe bloquearse o no si no hay eventos listos. Tcl_DoOneEvent realiza las siguientes acciones:

[1]
Comprueba la cola de eventos para ver si contiene algún evento que pueda ser atendido. Si es así, atiende el primer evento posible, lo elimina de la cola y regresa. Lo hace llamando a Tcl_ServiceEvent y pasando el argumento flags.
[2]
Se prepara para bloquear esperando un evento. Para hacer esto, Tcl_DoOneEvent invoca un procedimiento de configuración en cada fuente de eventos. La fuente de eventos realizará la inicialización específica de la fuente de eventos y posiblemente llamará a Tcl_SetMaxBlockTime para limitar cuánto tiempo bloqueará Tcl_WaitForEvent si no ocurren nuevos eventos.
[3]
Llama a Tcl_WaitForEvent. Este procedimiento se implementa de forma diferente en distintas plataformas; espera a que ocurra un evento, basándose en la información proporcionada por las fuentes de eventos. Puede hacer que la aplicación se bloquee si timePtr especifica un intervalo distinto de 0. Tcl_WaitForEvent regresa cuando algo ha sucedido, como que un archivo se vuelve legible o que el intervalo dado por timePtr expira. Si no hay eventos para que Tcl_WaitForEvent espere, de modo que se bloquearía indefinidamente, entonces regresa inmediatamente y Tcl_DoOneEvent retorna 0.
[4]
Llama a un procedimiento de verificación en cada fuente de eventos. El procedimiento de verificación determina si ocurrieron eventos de interés para esta fuente. Si es así, los eventos se añaden a la cola de eventos.
[5]

EL BUCLE DE EVENTOS

El núcleo de la notificación de eventos de Tcl es un bucle que revisa continuamente la cola de eventos para ver si contiene eventos que puedan ser atendidos. Si es así, atiende el primer evento posible, lo elimina de la cola y regresa.

[2]
Verifica si hay manejadores de entrada o salida pendientes. Si es así, atiende el primero y regresa.
[3]
Si se solicitó esperar un evento, llama a Tcl_WaitForEvent para esperar hasta que ocurra un evento o expire el tiempo de espera máximo.
[4]
Verifica si hay eventos en la cola de eventos. Si hay, atiende el primer evento posible y lo elimina de la cola.
[5]
Revisa la cola de eventos para ver si contiene eventos que puedan ser atendidos. Si es así, atiende el primer evento posible, lo elimina de la cola y regresa.
[6]
Verifica si hay callbacks inactivos pendientes. Si es así, invoca todos ellos y regresa.
[7]
O regresa 0 para indicar que no había eventos listos, o regresa al paso [2] si se solicitó bloqueo por parte del llamador.

CREANDO UNA NUEVA FUENTE DE EVENTOS

Una fuente de eventos consiste en tres procedimientos invocados por el notificador, además de procedimientos C adicionales que son invocados por el código de nivel superior para organizar callbacks basados en eventos.

Los tres procedimientos llamados por el notificador consisten en los procedimientos de configuración y verificación descritos anteriormente, más un procedimiento adicional que se invoca cuando un evento se elimina de la cola de eventos para su atención.

El procedimiento Tcl_CreateEventSource crea una nueva fuente de eventos. Sus argumentos especifican el procedimiento de configuración y el procedimiento de verificación para la fuente de eventos. SetupProc debe coincidir con el siguiente prototipo:

typedef void Tcl_EventSetupProc(
        ClientData clientData,
        int flags);

El argumento clientData será el mismo que el argumento clientData para Tcl_CreateEventSource; típicamente se utiliza para apuntar a información privada gestionada por la fuente de eventos. El argumento flags será el mismo que el argumento flags pasado a Tcl_DoOneEvent, excepto que nunca será 0 (Tcl_DoOneEvent reemplaza 0 con TCL_ALL_EVENTS). Flags indica qué tipos de eventos deben ser considerados; si el bit correspondiente a esta fuente de eventos no está establecido, la fuente de eventos debe regresar inmediatamente sin hacer nada. Por ejemplo, la fuente de eventos de archivo verifica el bit TCL_FILE_EVENTS.

El trabajo de SetupProc es asegurarse de que la aplicación se despierte cuando ocurran eventos del tipo deseado. Esto se hace típicamente de forma dependiente de la plataforma. Por ejemplo, bajo Unix una fuente de eventos podría llamar a Tcl_CreateFileHandler; bajo Windows podría solicitar notificación con un evento de Windows. Para fuentes de eventos controladas por temporizador, como eventos de temporizador o cualquier evento sondeado, la fuente de eventos puede llamar a Tcl_SetMaxBlockTime para forzar que la aplicación se despierte después de un tiempo especificado, incluso si no han ocurrido eventos. Si ninguna fuente de eventos llama a Tcl_SetMaxBlockTime, entonces Tcl_WaitForEvent esperará el tiempo necesario para que ocurra un evento; de lo contrario, solo esperará el tiempo más corto pasado a Tcl_SetMaxBlockTime por una de las fuentes de eventos. Si una fuente de eventos sabe que ya tiene eventos listos para reportar, puede solicitar un tiempo de bloqueo máximo de cero. Por ejemplo, el procedimiento de configuración para la fuente de eventos X busca si ya hay eventos en cola. Si los hay, llama a Tcl_SetMaxBlockTime con un tiempo de bloqueo de 0 para que Tcl_WaitForEvent no se bloquee si no hay datos nuevos en la conexión X. El argumento timePtr para Tcl_WaitForEvent apunta a una estructura que describe un intervalo de tiempo en segundos y microsegundos:

typedef struct Tcl_Time {
        long sec;
        long usec;
} Tcl_Time;

El campo usec debe ser menor que 1000000.

La información proporcionada a Tcl_SetMaxBlockTime solo se utiliza para la próxima llamada a Tcl_WaitForEvent; se descarta después de que Tcl_WaitForEvent regresa. La próxima vez que se realice una espera de eventos, se llamará a los procedimientos de configuración de cada una de las fuentes de eventos, y podrán especificar nueva información para esa espera de eventos.

Si la aplicación utiliza un bucle de eventos externo en lugar de Tcl_DoOneEvent, las fuentes de eventos pueden necesitar llamar a Tcl_SetMaxBlockTime en otros momentos. Por ejemplo, si se registra un nuevo manejador de eventos que necesita sondear eventos, la fuente de eventos puede llamar a Tcl_SetMaxBlockTime para establecer el tiempo de bloqueo a cero y forzar que el bucle de eventos externo llame a Tcl. En este caso, Tcl_SetMaxBlockTime invoca Tcl_SetTimer con el intervalo más corto visto desde la última llamada a Tcl_DoOneEvent o Tcl_ServiceAll.

Además del procedimiento genérico Tcl_SetMaxBlockTime, pueden estar disponibles otros procedimientos específicos de plataforma para setupProc, si hay información adicional necesaria para Tcl_WaitForEvent en esa plataforma. Por ejemplo, en sistemas Unix se puede utilizar la interfaz Tcl_CreateFileHandler para esperar eventos de archivo.

El segundo procedimiento proporcionado por cada fuente de eventos es su procedimiento de verificación, indicado por el argumento checkProc para Tcl_CreateEventSource. CheckProc debe coincidir con el siguiente prototipo:

typedef void Tcl_EventCheckProc(
        ClientData clientData,
        int flags);

Los argumentos para este procedimiento son los mismos que los de setupProc. CheckProc es invocado por Tcl_DoOneEvent después de que ha esperado eventos. Presumiblemente, al menos una fuente de eventos está ahora preparada para poner un evento en cola. Tcl_DoOneEvent llama a cada una de las fuentes de eventos en turno, por lo que todas tienen la oportunidad de poner en cola cualquier evento que esté listo. El procedimiento de verificación hace dos cosas. Primero, debe verificar si algún evento se ha disparado. Las diferentes fuentes de eventos hacen esto de diferentes maneras.

Si el procedimiento de verificación de una fuente de eventos detecta un evento interesante, debe agregar el evento a la cola de eventos de Tcl. Para hacer esto, la fuente de eventos llama a Tcl_QueueEvent. El argumento evPtr es un puntero a una estructura asignada dinámicamente que contiene el evento (ver más abajo para más información sobre problemas de gestión de memoria). Cada fuente de eventos puede definir su propia estructura de evento con la información relevante para esa fuente de eventos. Sin embargo, el primer elemento de la estructura debe ser una estructura de tipo Tcl_Event, y la dirección de esta estructura se utiliza al comunicarse entre la fuente de eventos y el resto del notificador. Un Tcl_Event tiene la siguiente definición:

typedef struct {
        Tcl_EventProc *proc;
        struct Tcl_Event *nextPtr;
} Tcl_Event;

La fuente de eventos debe rellenar el campo proc del evento antes de llamar a Tcl_QueueEvent. El campo nextPtr se utiliza para enlazar los eventos en la cola y no debe ser modificado por la fuente de eventos.

Un evento puede ser agregado a la cola en cualquiera de las tres posiciones, dependiendo del argumento position para Tcl_QueueEvent:

TCL_QUEUE_TAIL
Agrega el evento al final de la cola, de modo que todos los demás eventos pendientes sean atendidos primero. Este es casi siempre el lugar correcto para eventos nuevos.
TCL_QUEUE_HEAD
Agrega el evento al principio de la cola, de modo que sea atendido antes que todos los demás eventos en cola.
TCL_QUEUE_MARK
Agrega el evento al principio de la cola, a menos que haya otros eventos al principio cuya posición sea TCL_QUEUE_MARK; en ese caso, agrega el nuevo evento justo después de todos los demás eventos TCL_QUEUE_MARK. Este valor de position se utiliza para insertar una secuencia ordenada de eventos al principio de la cola, como una serie de eventos Enter y Leave sintetizados durante una operación de grab o ungrab en Tk.

Cuando es hora de manejar un evento de la cola (pasos 1 y 4 anteriormente), Tcl_ServiceEvent invocará el proc especificado en la primera estructura Tcl_Event en cola. Proc debe coincidir con el siguiente prototipo:

typedef int Tcl_EventProc(
        Tcl_Event *evPtr,
        int flags);

El primer argumento para proc es un puntero al evento, que será el mismo que el primer argumento de la llamada a Tcl_QueueEvent que agregó el evento a la cola. El segundo argumento para proc es el argumento flags para la llamada actual a Tcl_ServiceEvent; esto es utilizado por la fuente de eventos para regresar inmediatamente si sus eventos no son relevantes.

Es responsabilidad de proc manejar el evento, típicamente invocando uno o más comandos de Tcl o callbacks a nivel de C. Una vez que la fuente de eventos ha terminado de manejar el evento, regresa 1 para indicar que el evento puede ser eliminado de la cola. Si por alguna razón la fuente de eventos decide que el evento no puede ser manejado en este momento, puede regresar 0 para indicar que el evento debe ser pospuesto para su procesamiento posterior; en este caso Tcl_ServiceEvent continuará con el siguiente evento en la cola e intentará atenderlo. Hay varias razones por las que una fuente de eventos podría posponer un evento. Una posibilidad es que los eventos de este tipo estén excluidos por el argumento flags. Por ejemplo, la fuente de eventos de archivo siempre regresará 0 si el bit TCL_FILE_EVENTS no está establecido en flags. Otro ejemplo de posposición de eventos ocurre en Tk si se ha invocado Tk_RestrictEvents para posponer ciertos tipos de eventos de ventana.

Cuando proc regresa 1, Tcl_ServiceEvent eliminará el evento de la cola de eventos y liberará su almacenamiento. Tenga en cuenta que el almacenamiento para un evento debe ser asignado por la fuente de eventos (usando Tcl_Alloc o la macro Tcl ckalloc) antes de llamar a Tcl_QueueEvent, pero será liberado por Tcl_ServiceEvent, no por la fuente de eventos.

Las aplicaciones multihilo funcionan de manera similar, excepto que hay una cola de eventos separada para cada hilo que contiene un intérprete Tcl. Llamar a Tcl_QueueEvent en una aplicación multihilo agrega un evento a la cola del hilo actual. Para agregar un evento a la cola de otro hilo, use Tcl_ThreadQueueEvent. Tcl_ThreadQueueEvent acepta como argumento un argumento Tcl_ThreadId, que identifica de forma única un hilo en una aplicación Tcl. Para obtener el Tcl_ThreadId del hilo actual, use el procedimiento Tcl_GetCurrentThread. (Un hilo necesitaría luego pasar esta identificación a otros hilos para que estos puedan agregar eventos a su cola.) Después de agregar un evento a la cola de otro hilo, generalmente necesita llamar a Tcl_ThreadAlert para "despertar" al notificador de ese hilo para alertarlo sobre el nuevo evento.

Tcl_DeleteEvents se puede usar para eliminar explícitamente uno o más eventos de la cola de eventos. Tcl_DeleteEvents llama a proc para cada evento en la cola, eliminando aquellos para los cuales el procedimiento regresa 1. Los eventos para los cuales el procedimiento regresa 0 permanecen en la cola. Proc debe coincidir con el siguiente prototipo:

typedef int Tcl_EventDeleteProc(
        Tcl_Event *evPtr,
        ClientData clientData);

DESCRIPCIÓN

The notifier is a collection of procedures that manage the Tcl event queue. It provides a way for Tcl to wait for events from various sources, such as file descriptors, timers, or internal events. The notifier is also responsible for invoking the Tcl event loop, which processes events from the queue.

Tcl_CreateEventSource registers a new event source with the notifier. An event source is a mechanism for generating events. The setupProc is called by the notifier whenever it needs to poll for events from this source. The checkProc is called whenever an event from this source may be ready to be processed. The clientData argument is passed to both procedures. The setupProc should initialize any data structures needed for the event source and set the maximum time that the notifier should block waiting for an event from this source. The checkProc should check if any events are ready and, if so, queue them on the Tcl event queue by calling Tcl_QueueEvent. The event source's data structures should be freed by the checkProc after the events have been queued. If the checkProc returns a non-NULL value, it points to the next event in the queue.

Tcl_DeleteEventSource deletes an event source. The setupProc, checkProc, and clientData arguments must exactly match those provided to the Tcl_CreateEventSource for the event source to be deleted. If no such source exists, Tcl_DeleteEventSource has no effect.

CREACIÓN DE UN NUEVO NOTIFICADOR

The notifier consists of all the procedures described in this manual entry, plus Tcl_DoOneEvent and Tcl_Sleep, which are available on all platforms, and Tcl_CreateFileHandler and Tcl_DeleteFileHandler, which are Unix-specific. Most of these procedures are generic, in that they are the same for all notifiers. However, none of the procedures are notifier-dependent: Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_SetTimer, Tcl_Sleep, Tcl_WaitForEvent, Tcl_CreateFileHandler, Tcl_DeleteFileHandler and Tcl_ServiceModeHook. To support a new platform or to integrate Tcl with an application-specific event loop, you must write new versions of these procedures.

Tcl_InitNotifier initializes the notifier state and returns a handle to the notifier state. Tcl calls this procedure when initializing a Tcl interpreter. Similarly, Tcl_FinalizeNotifier shuts down the notifier, and is called by Tcl_Finalize when shutting down a Tcl interpreter.

Tcl_WaitForEvent is the lowest-level procedure in the notifier; it is responsible for waiting for an “interesting” event to occur or for a given time to elapse. Before Tcl_WaitForEvent is invoked, each of the event sources' setup procedure will have been invoked. The timePtr argument to Tcl_WaitForEvent gives the maximum time to block for an event, based on calls to Tcl_SetMaxBlockTime made by setup procedures and on other information (such as the TCL_DONT_WAIT bit in flags).

Ideally, Tcl_WaitForEvent should only wait for an event to occur; it should not actually process the event in any way. Later on, the event sources will process the raw events and create Tcl_Events on the event queue in their checkProc procedures. However, on some platforms (such as Windows) this is not possible; events may be processed in Tcl_WaitForEvent, including queuing Tcl_Events and more (for example, callbacks for native widgets may be invoked). The return value from Tcl_WaitForEvent must be either 0, 1, or -1. On platforms such as Windows where events get processed in Tcl_WaitForEvent, a return value of 1 means that there may be more events still pending that have not been processed. This is a sign to the caller that it must call Tcl_WaitForEvent again if it wants all pending events to be processed. A 0 return value means that calling Tcl_WaitForEvent again will not have any effect: either this is a platform where Tcl_WaitForEvent only waits without doing any event processing, or Tcl_WaitForEvent knows for sure that there are no additional events to process (e.g. it returned because the time elapsed). Finally, a return value of -1 means that the event loop is no longer operational and the application should probably unwind and terminate. Under Windows this happens when a WM_QUIT message is received; under Unix it happens when Tcl_WaitForEvent would have waited forever because there were no active event sources and the timeout was infinite.

Tcl_AlertNotifier is used in multithreaded applications to allow any thread to “wake up” the notifier to alert it to new events on its queue. Tcl_AlertNotifier requires as an argument the notifier handle returned by Tcl_InitNotifier.

If the notifier will be used with an external event loop, then it must also support the Tcl_SetTimer interface. Tcl_SetTimer is invoked by Tcl_SetMaxBlockTime whenever the maximum blocking time has been reduced. Tcl_SetTimer should arrange for the external event loop to invoke Tcl_ServiceAll after the specified interval even if no events have occurred. This interface is needed because Tcl_WaitForEvent is not invoked when there is an external event loop. If the notifier will only be used from Tcl_DoOneEvent, then Tcl_SetTimer need not do anything.

Tcl_ServiceModeHook is called by the platform-independent portion of the notifier when client code makes a call to Tcl_SetServiceMode. This hook is provided to support operating systems that require special event handling when the application is in a modal loop (the Windows notifier, for instance, uses this hook to create a communication window).

On Unix systems, the file event source also needs support from the notifier. The file event source consists of the Tcl_CreateFileHandler and Tcl_DeleteFileHandler procedures, which are described in the Tcl_CreateFileHandler manual page.

The Tcl_Sleep and Tcl_DoOneEvent interfaces are described in their respective manual pages.

The easiest way to create a new notifier is to look at the code for an existing notifier, such as the files unix/tclUnixNotfy.c or win/tclWinNotify.c in the Tcl source distribution.

REEMPLAZO DEL NOTIFICADOR

A notifier that has been written according to the conventions above can also be installed in a running process in place of the standard notifier. This mechanism is used so that a single executable can be used (with the standard notifier) as a stand-alone program and reused (with a replacement notifier in a loadable extension) as an extension to another program, such as a Web browser plugin.

To do this, the extension makes a call to Tcl_SetNotifier passing a pointer to a Tcl_NotifierProcs data structure. The structure has the following layout:

typedef struct Tcl_NotifierProcs {
    Tcl_SetTimerProc *setTimerProc;
    Tcl_WaitForEventProc *waitForEventProc;
    Tcl_CreateFileHandlerProc *createFileHandlerProc;
    Tcl_DeleteFileHandlerProc *deleteFileHandlerProc;
    Tcl_InitNotifierProc *initNotifierProc;
    Tcl_FinalizeNotifierProc *finalizeNotifierProc;
    Tcl_AlertNotifierProc *alertNotifierProc;
    Tcl_ServiceModeHookProc *serviceModeHookProc;
} Tcl_NotifierProcs;

Following the call to Tcl_SetNotifier, the pointers given in the Tcl_NotifierProcs structure replace whatever notifier had been installed in the process.

It is extraordinarily unwise to replace a running notifier. Normally, Tcl_SetNotifier should be called at process initialization time before the first call to Tcl_InitNotifier.

BUCLES DE EVENTOS EXTERNOS

The notifier interfaces are designed so that Tcl can be embedded into applications that have their own private event loops. In this case, the application does not call Tcl_DoOneEvent except in the case of recursive event loops such as calls to the Tcl commands update or vwait. Most of the time is spent in the external event loop of the application. In this case the notifier must arrange for the external event loop to call back into Tcl when something happens on the various Tcl event sources. These callbacks should arrange for appropriate Tcl events to be placed on the Tcl event queue.

Because the external event loop is not calling Tcl_DoOneEvent on a regular basis, it is up to the notifier to arrange for Tcl_ServiceEvent to be called whenever events are pending on the Tcl event queue. The easiest way to do this is to invoke Tcl_ServiceAll at the end of each callback from the external event loop. This will ensure that all of the event sources are polled, any queued events are serviced, and any pending idle handlers are processed before returning control to the application. In addition, event sources that need to poll for events can call Tcl_SetMaxBlockTime to force the external event loop to call Tcl even if no events are available on the system event queue.

As a side effect of processing events detected in the main external event loop, Tcl may invoke Tcl_DoOneEvent to start a recursive event loop in commands like vwait. Tcl_DoOneEvent will invoke the external event loop, which will result in callbacks as described in the preceding paragraph, which will result in calls to Tcl_ServiceAll. However, in these cases it is undesirable to service events in Tcl_ServiceAll. Servicing events there is unnecessary because control will immediately return to the external event loop and hence to Tcl_DoOneEvent, which can service the events itself. Furthermore, Tcl_DoOneEvent is supposed to service only a single event, whereas Tcl_ServiceAll normally services all pending events. To handle this situation, Tcl_DoOneEvent sets a flag for Tcl_ServiceAll that causes it to return without servicing any events. This flag is called the service mode; Tcl_DoOneEvent restores it to its previous value before it returns.

In some cases, however, it may be necessary for Tcl_ServiceAll to service events even when it has been invoked from Tcl_DoOneEvent. This happens when there is yet another recursive event loop invoked via an event handler called by Tcl_DoOneEvent (such as one that is part of a native widget). In this case, Tcl_DoOneEvent may not have a chance to service events so Tcl_ServiceAll must service them all. Any recursive event loop that calls an external event loop rather than Tcl_DoOneEvent must reset the service mode so that all events get processed in Tcl_ServiceAll. This is done by invoking the Tcl_SetServiceMode procedure. If Tcl_SetServiceMode is passed TCL_SERVICE_NONE, then calls to Tcl_ServiceAll will return immediately without processing any events. If Tcl_SetServiceMode is passed TCL_SERVICE_ALL, then calls to Tcl_ServiceAll will behave normally. Tcl_SetServiceMode returns the previous value of the service mode, which should be restored when the recursive loop exits. Tcl_GetServiceMode returns the current value of the service mode.

INTRODUCTION

The Tcl event loop is responsible for dispatching events to the appropriate handlers. The notifier is a central part of the event loop, responsible for waiting for events and dispatching them. Tcl provides a default notifier that handles standard Tcl events, but it is also possible to replace the default notifier with a custom one.

NOTIFIER BASICS

The notifier is a procedure that is called by the Tcl event loop when there are no events to process. The notifier is responsible for waiting for events and dispatching them. The default Tcl notifier handles file events, timer events, idle events, and service mode events. It also handles threads.

CREATING A NEW EVENT SOURCE

To create a new event source, you need to define a new event source structure and register it with the Tcl event loop. The event source structure contains information about the event source, such as its type, its file descriptor (if any), and a procedure to be called when an event occurs.

CREATING A NEW NOTIFIER

To create a new notifier, you need to define a new notifier procedure. The notifier procedure should be a function that takes no arguments and returns void. The notifier procedure should be responsible for waiting for events and dispatching them. The Tcl_InitNotifier function can be used to register a new notifier.

REPLACING THE NOTIFIER

To replace the default Tcl notifier with a custom one, you can use the Tcl_SetNotifier function. This function takes a pointer to the new notifier procedure as an argument. The Tcl_FinalizeNotifier function can be used to restore the default Tcl notifier.

EXTERNAL EVENT_LOOPS

Tcl can be embedded in an external event loop. In this case, Tcl will not initialize its own event loop, but will instead rely on the external event loop to dispatch events. The Tcl_SetNotifier function can be used to specify a notifier procedure that will be called by the external event loop.
