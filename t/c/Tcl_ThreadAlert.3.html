ARGUMENTOS

Tcl_EventSetupProc *setupProc (entrada)
Procedimiento a invocar para preparar la espera de eventos en Tcl_DoOneEvent.
Tcl_EventCheckProc *checkProc (entrada)
Procedimiento para que Tcl_DoOneEvent lo invoque después de esperar eventos. Comprueba si han ocurrido eventos y, si es así, los pone en cola.
ClientData clientData (entrada)
Valor arbitrario de una palabra para pasar a setupProc, checkProc o deleteProc.
const Tcl_Time *timePtr (entrada)
Indica la cantidad máxima de tiempo a esperar por un evento. Esto se especifica como un intervalo (cuánto esperar), no como un tiempo absoluto (cuándo despertar). Si el puntero pasado a Tcl_WaitForEvent es NULL, significa que no hay un tiempo máximo de espera: esperar para siempre si es necesario.
Tcl_Event *evPtr (entrada)
Un evento a añadir a la cola de eventos. El espacio para el evento debe haber sido asignado por el llamador usando Tcl_Alloc o ckalloc.
Tcl_QueuePosition position (entrada)
Dónde añadir el nuevo evento en la cola: TCL_QUEUE_TAIL, TCL_QUEUE_HEAD, o TCL_QUEUE_MARK.
Tcl_ThreadId threadId (entrada)
Un identificador único para un hilo.
Tcl_EventDeleteProc *deleteProc (entrada)
Procedimiento a invocar para cada evento en cola en Tcl_DeleteEvents.
int flags (entrada)
Qué tipos de eventos procesar. Estas banderas son las mismas que se pasan a Tcl_DoOneEvent.
int mode (entrada)
Indica si los eventos deben ser procesados por Tcl_ServiceAll. Debe ser uno de TCL_SERVICE_NONE o TCL_SERVICE_ALL.
Tcl_NotifierProcs* notifierProcPtr (entrada)
Estructura de punteros de función que describe los procedimientos del notificador que reemplazarán a los instalados en el ejecutable. Véase REEMPLAZO DEL NOTIFICADOR para más detalles.

INTRODUCCIÓN

Las interfaces descritas aquí se utilizan para personalizar el bucle de eventos de Tcl. Las dos personalizaciones más comunes son añadir nuevas fuentes de eventos y fusionar el bucle de eventos de Tcl con algún otro bucle de eventos, como uno proporcionado por una aplicación en la que Tcl está incrustado. Cada una de estas tareas se describe en una sección separada a continuación.

Los procedimientos de esta entrada del manual son los bloques de construcción con los que se construye el notificador de eventos de Tcl. El notificador de eventos es la capa más baja en el mecanismo de eventos de Tcl. Consiste en tres cosas:

[1]
Fuentes de eventos: estas representan las formas en que se pueden generar eventos. Por ejemplo, hay una fuente de eventos de temporizador que implementa el procedimiento Tcl_CreateTimerHandler y el comando after, y hay una fuente de eventos de archivo que implementa el procedimiento Tcl_CreateFileHandler en sistemas Unix. Una fuente de eventos debe trabajar con el notificador para detectar eventos en los momentos adecuados, registrarlos en la cola de eventos y, finalmente, notificar al software de nivel superior que han ocurrido. Los procedimientos Tcl_CreateEventSource, Tcl_DeleteEventSource, Tcl_SetMaxBlockTime, Tcl_QueueEvent y Tcl_DeleteEvents son utilizados principalmente por las fuentes de eventos.
[2]
La cola de eventos: para aplicaciones no multihilo, hay una única cola para toda la aplicación, que contiene eventos que han sido detectados pero aún no procesados. Las fuentes de eventos colocan eventos en la cola para que puedan ser procesados en orden en momentos apropiados durante el bucle de eventos. La cola de eventos garantiza una disciplina justa de manejo de eventos, de modo que ninguna fuente de eventos pueda privar a las otras. También permite que los eventos se guarden para ser procesados en un momento futuro. Las aplicaciones multihilo funcionan de manera similar, excepto que hay una cola de eventos separada para cada hilo que contiene un intérprete de Tcl. Tcl_QueueEvent se utiliza (principalmente por las fuentes de eventos) para añadir eventos a la cola de eventos y Tcl_DeleteEvents se utiliza para eliminar eventos de la cola sin procesarlos. En una aplicación multihilo, Tcl_QueueEvent añade un evento a la cola del hilo actual, y Tcl_ThreadQueueEvent añade un evento a una cola en un hilo específico.
[3]
El bucle de eventos: para detectar y procesar eventos, la aplicación entra en un bucle que espera a que ocurran eventos, los coloca en la cola de eventos y luego los procesa. La mayoría de las aplicaciones harán esto llamando al procedimiento Tcl_DoOneEvent, que se describe en una entrada de manual separada.

La mayoría de las aplicaciones Tcl no necesitan preocuparse por los detalles internos del notificador Tcl. Sin embargo, el notificador ahora tiene suficiente flexibilidad para ser reorientado para una nueva plataforma o para utilizar un bucle de eventos externo (como el bucle de eventos Motif, cuando Tcl está incrustado en una aplicación Motif). Los procedimientos Tcl_WaitForEvent y Tcl_SetTimer son normalmente implementados por Tcl, pero pueden ser reemplazados con nuevas versiones para reorientar el notificador (los procedimientos Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_Sleep, Tcl_CreateFileHandler y Tcl_DeleteFileHandler también deben ser reemplazados; véase CREACIÓN DE UN NUEVO NOTIFICADOR más abajo para más detalles). Los procedimientos Tcl_ServiceAll, Tcl_ServiceEvent, Tcl_GetServiceMode y Tcl_SetServiceMode se proporcionan para ayudar a conectar el bucle de eventos de Tcl con un bucle de eventos externo como el de Motif.

BASES DEL NOTIFICADOR

La forma más fácil de entender cómo funciona el notificador es considerar lo que sucede cuando se llama a Tcl_DoOneEvent. A Tcl_DoOneEvent se le pasa un argumento flags que indica qué tipo de eventos se pueden procesar y si se debe bloquear si no hay eventos listos. Tcl_DoOneEvent hace lo siguiente:

[1]
Comprueba la cola de eventos para ver si contiene algún evento que pueda ser atendido. Si es así, atiende el primer evento posible, lo elimina de la cola y retorna. Hace esto llamando a Tcl_ServiceEvent y pasando el argumento flags.
[2]
Prepara para bloquear por un evento. Para hacer esto, Tcl_DoOneEvent invoca un procedimiento setup en cada fuente de eventos. La fuente de eventos realizará la inicialización específica de la fuente de eventos y posiblemente llamará a Tcl_SetMaxBlockTime para limitar cuánto tiempo bloqueará Tcl_WaitForEvent si no ocurren nuevos eventos.
[3]
Llama a Tcl_WaitForEvent. Este procedimiento se implementa de manera diferente en diferentes plataformas; espera a que ocurra un evento, basándose en la información proporcionada por las fuentes de eventos. Puede hacer que la aplicación se bloquee si timePtr especifica un intervalo distinto de 0. Tcl_WaitForEvent retorna cuando algo ha sucedido, como que un archivo se vuelve legible o el intervalo dado por timePtr expira. Si no hay eventos para que Tcl_WaitForEvent espere, de modo que bloquearía para siempre, entonces retorna inmediatamente y Tcl_DoOneEvent retorna 0.
[4]
Llama a un procedimiento check en cada fuente de eventos. El procedimiento check determina si ocurrieron eventos de interés para esta fuente. Si es así, los eventos se añaden a la cola de eventos.

CONTROL FLOW

The main loop of a Tcl application is typically structured as follows:

[1]
Process any Tcl commands that are ready to be executed (e.g., those generated by button presses or other events).
[2]
Call Tcl_DoOneEvent to service pending events. If blocking is requested by the caller (i.e., the flags argument to Tcl_DoOneEvent is non-zero), then Tcl_DoOneEvent will block until at least one event is ready. Otherwise, it will return immediately after checking for events. The steps performed by Tcl_DoOneEvent are described below.
[3]
If the application is finished, exit the loop.
[4]
Go back to step [1].

The steps performed by Tcl_DoOneEvent are as follows:

[1]
If the flags argument is 0, return immediately without doing anything.
[2]
Call the setup procedure for each event source, passing it the flags argument. The setup procedures are responsible for ensuring that the application will wake up if events of the desired type occur. This is typically done by calling platform-specific procedures such as Tcl_CreateFileHandler or Tcl_SetMaxBlockTime.
[3]
If the flags argument is non-zero, call Tcl_WaitForEvent to wait for events to occur. Tcl_WaitForEvent will block until at least one event is ready or until the shortest interval specified by the event sources' setup procedures expires. If flags is 0, Tcl_WaitForEvent returns immediately.
[4]
Call the check procedure for each event source, passing it the flags argument. The check procedures are responsible for detecting any events that have occurred since the last check and for queuing them using Tcl_QueueEvent.
[5]
Check the event queue to see if it contains any events that can be serviced. If so, service the first possible event, remove it from the queue, and return.
[6]
See if there are idle callbacks pending. If so, invoke all of them and return.
[7]
Either return 0 to indicate that no events were ready, or go back to step [2] if blocking was requested by the caller.

CREATING A NEW EVENT SOURCE

An event source consists of three procedures invoked by the notifier, plus additional C procedures that are invoked by higher-level code to arrange for event-driven callbacks. The three procedures called by the notifier consist of the setup and check procedures described above, plus an additional procedure that is invoked when an event is removed from the event queue for servicing.

The procedure Tcl_CreateEventSource creates a new event source. Its arguments specify the setup procedure and check procedure for the event source. SetupProc should match the following prototype:

typedef void Tcl_EventSetupProc(
        ClientData clientData,
        int flags);

The clientData argument will be the same as the clientData argument to Tcl_CreateEventSource; it is typically used to point to private information managed by the event source. The flags argument will be the same as the flags argument passed to Tcl_DoOneEvent except that it will never be 0 (Tcl_DoOneEvent replaces 0 with TCL_ALL_EVENTS). Flags indicates what kinds of events should be considered; if the bit corresponding to this event source is not set, the event source should return immediately without doing anything. For example, the file event source checks for the TCL_FILE_EVENTS bit.

SetupProc's job is to make sure that the application wakes up when events of the desired type occur. This is typically done in a platform-dependent fashion. For example, under Unix an event source might call Tcl_CreateFileHandler; under Windows it might request notification with a Windows event. For timer-driven event sources such as timer events or any polled event, the event source can call Tcl_SetMaxBlockTime to force the application to wake up after a specified time even if no events have occurred. If no event source calls Tcl_SetMaxBlockTime then Tcl_WaitForEvent will wait as long as necessary for an event to occur; otherwise, it will only wait as long as the shortest interval passed to Tcl_SetMaxBlockTime by one of the event sources. If an event source knows that it already has events ready to report, it can request a zero maximum block time. For example, the setup procedure for the X event source looks to see if there are events already queued. If there are, it calls Tcl_SetMaxBlockTime with a 0 block time so that Tcl_WaitForEvent does not block if there is no new data on the X connection. The timePtr argument to Tcl_WaitForEvent points to a structure that describes a time interval in seconds and microseconds:

typedef struct Tcl_Time {
    long sec;
    long usec;
} Tcl_Time;

The usec field should be less than 1000000.

Information provided to Tcl_SetMaxBlockTime is only used for the next call to Tcl_WaitForEvent; it is discarded after Tcl_WaitForEvent returns. The next time an event wait is done each of the event sources' setup procedures will be called again, and they can specify new information for that event wait.

If the application uses an external event loop rather than Tcl_DoOneEvent, the event sources may need to call Tcl_SetMaxBlockTime at other times. For example, if a new event handler is registered that needs to poll for events, the event source may call Tcl_SetMaxBlockTime to set the block time to zero to force the external event loop to call Tcl. In this case, Tcl_SetMaxBlockTime invokes Tcl_SetTimer with the shortest interval seen since the last call to Tcl_DoOneEvent or Tcl_ServiceAll.

In addition to the generic procedure Tcl_SetMaxBlockTime, other platform-specific procedures may also be available for setupProc, if there is additional information needed by Tcl_WaitForEvent on that platform. For example, on Unix systems the Tcl_CreateFileHandler interface can be used to wait for file events.

The second procedure provided by each event source is its check procedure, indicated by the checkProc argument to Tcl_CreateEventSource. CheckProc must match the following prototype:

typedef void Tcl_EventCheckProc(
        ClientData clientData,
        int flags);

The arguments to this procedure are the same as those for setupProc. CheckProc is invoked by Tcl_DoOneEvent after it has waited for events. Presumably at least one event source is now prepared to queue an event. Tcl_DoOneEvent calls each of the event sources in turn, so they all have a chance to queue any events that are ready. The check procedure does two things. First, it must see if any events have triggered. Different event sources do this in different ways.

If an event source's check procedure detects an interesting event, it must add the event to Tcl's event queue. To do this, the event source calls Tcl_QueueEvent. The evPtr argument is a pointer to a dynamically allocated structure containing the event (see below for more information on memory management issues). Each event source can define its own event structure with whatever information is relevant to that event source. However, the first element of the structure must be a structure of type Tcl_Event, and the address of this structure is used when communicating between the event source and the rest of the notifier. A Tcl_Event has the following definition:

typedef struct {
    Tcl_EventProc *proc;
    struct Tcl_Event *nextPtr;
} Tcl_Event;

The event source must fill in the proc field of the event before calling Tcl_QueueEvent. The nextPtr is used to link together the events in the queue and should not be modified by the event source.

An event may be added to the queue at any of three positions, depending on the position argument to Tcl_QueueEvent:

TCL_QUEUE_TAIL
Add the event at the back of the queue, so that all other pending events will be serviced first. This is almost always the right place for new events.
TCL_QUEUE_HEAD
Add the event at the front of the queue, so that it will be serviced before all other queued events.
TCL_QUEUE_MARK
Add the event at the front of the queue, unless there are other events at the front whose position is TCL_QUEUE_MARK; if so, add the new event just after all other TCL_QUEUE_MARK events. This value of position is used to insert an ordered sequence of events at the front of the queue, such as a series of Enter and Leave events synthesized during a grab or ungrab operation in Tk.

When it is time to handle an event from the queue (steps 1 and 4 above) Tcl_ServiceEvent will invoke the proc specified in the first queued Tcl_Event structure. Proc must match the following prototype:

typedef int Tcl_EventProc(
        Tcl_Event *evPtr,
        int flags);

The first argument to proc is a pointer to the event, which will be the same as the first argument to the Tcl_QueueEvent call that added the event to the queue. The second argument to proc is the flags argument for the current call to Tcl_ServiceEvent; this is used by the event source to return immediately if its events are not relevant.

It is up to proc to handle the event, typically by invoking one or more Tcl commands or C-level callbacks. Once the event source has finished handling the event it returns 1 to indicate that the event can be removed from the queue. If for some reason the event source decides that the event cannot be handled at this time, it may return 0 to indicate that the event should be deferred for processing later; in this case Tcl_ServiceEvent will go on to the next event in the queue and attempt to service it. There are several reasons why an event source might defer an event. One possibility is that events of this type are excluded by the flags argument. For example, the file event source will always return 0 if the TCL_FILE_EVENTS bit is not set in flags. Another example of deferring events happens in Tk if Tk_RestrictEvents has been invoked to defer certain kinds of window events.

When proc returns 1, Tcl_ServiceEvent will remove the event from the event queue and free its storage. Note that the storage for an event must be allocated by the event source (using Tcl_Alloc or the Tcl macro ckalloc) before calling Tcl_QueueEvent, but it will be freed by Tcl_ServiceEvent, not by the event source.

Threaded applications work in a similar manner, except that there is a separate event queue for each thread containing a Tcl interpreter. Calling Tcl_QueueEvent in a multithreaded application adds an event to the current thread's queue. To add an event to another thread's queue, use Tcl_ThreadQueueEvent. Tcl_ThreadQueueEvent accepts as an argument a Tcl_ThreadId argument, which uniquely identifies a thread in a Tcl application. To obtain the Tcl_ThreadId for the current thread, use the Tcl_GetCurrentThread procedure. (A thread would then need to pass this identifier to other threads for those threads to be able to add events to its queue.) After adding an event to another thread's queue, you then typically need to call Tcl_ThreadAlert to “wake up” that thread's notifier to alert it to the new event.

Tcl_DeleteEvents can be used to explicitly remove one or more events from the event queue. Tcl_DeleteEvents calls proc for each event in the queue, deleting those for with the procedure returns 1. Events for which the procedure returns 0 are left in the queue. Proc should match the following prototype:

typedef int Tcl_EventDeleteProc(
        Tcl_Event *evPtr,
        ClientData clientData);

The clientData argument will be the same as the clientData argument to Tcl_DeleteEvent

s; se usa típicamente para apuntar a información privada gestionada por la fuente del evento. El evPtr apuntará al siguiente evento en la cola.

Tcl_DeleteEventSource elimina una fuente de eventos. Los argumentos setupProc, checkProc y clientData deben coincidir exactamente con los proporcionados a Tcl_CreateEventSource para que la fuente de eventos sea eliminada. Si no existe tal fuente, Tcl_DeleteEventSource no tiene ningún efecto.

CREACIÓN DE UN NUEVO NOTIFICADOR

El notificador consta de todos los procedimientos descritos en esta entrada del manual, además de Tcl_DoOneEvent y Tcl_Sleep, que están disponibles en todas las plataformas, y Tcl_CreateFileHandler y Tcl_DeleteFileHandler, que son específicos de Unix. La mayoría de estos procedimientos son genéricos, en el sentido de que son los mismos para todos los notificadores. Sin embargo, ninguno de los procedimientos depende del notificador: Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_SetTimer, Tcl_Sleep, Tcl_WaitForEvent, Tcl_CreateFileHandler, Tcl_DeleteFileHandler y Tcl_ServiceModeHook. Para soportar una nueva plataforma o para integrar Tcl con un bucle de eventos específico de la aplicación, debe escribir nuevas versiones de estos procedimientos.

Tcl_InitNotifier inicializa el estado del notificador y devuelve un manejador al estado del notificador. Tcl llama a este procedimiento al inicializar un intérprete de Tcl. De manera similar, Tcl_FinalizeNotifier cierra el notificador y es llamado por Tcl_Finalize al cerrar un intérprete de Tcl.

Tcl_WaitForEvent es el procedimiento de más bajo nivel en el notificador; es responsable de esperar a que ocurra un evento "interesante" o a que transcurra un tiempo determinado. Antes de que se invoque Tcl_WaitForEvent, se habrá invocado el procedimiento de configuración de cada una de las fuentes de eventos. El argumento timePtr a Tcl_WaitForEvent proporciona el tiempo máximo de espera de un evento, basado en las llamadas a Tcl_SetMaxBlockTime realizadas por los procedimientos de configuración y en otra información (como el bit TCL_DONT_WAIT en flags).

Idealmente, Tcl_WaitForEvent solo debería esperar a que ocurra un evento; no debería procesar el evento de ninguna manera. Más adelante, las fuentes de eventos procesarán los eventos brutos y crearán Tcl_Events en la cola de eventos en sus procedimientos checkProc. Sin embargo, en algunas plataformas (como Windows) esto no es posible; los eventos pueden ser procesados en Tcl_WaitForEvent, incluyendo la cola de Tcl_Events y más (por ejemplo, se pueden invocar callbacks para widgets nativos). El valor de retorno de Tcl_WaitForEvent debe ser 0, 1 o -1. En plataformas como Windows donde los eventos se procesan en Tcl_WaitForEvent, un valor de retorno de 1 significa que puede haber más eventos pendientes que no han sido procesados. Esto es una señal para el llamador de que debe llamar a Tcl_WaitForEvent nuevamente si desea que se procesen todos los eventos pendientes. Un valor de retorno de 0 significa que llamar a Tcl_WaitForEvent nuevamente no tendrá ningún efecto: o bien es una plataforma donde Tcl_WaitForEvent solo espera sin hacer ningún procesamiento de eventos, o bien Tcl_WaitForEvent sabe con certeza que no hay eventos adicionales que procesar (por ejemplo, devolvió porque el tiempo expiró). Finalmente, un valor de retorno de -1 significa que el bucle de eventos ya no es operativo y la aplicación probablemente debería desenrollarse y terminar. En Windows, esto ocurre cuando se recibe un mensaje WM_QUIT; en Unix, ocurre cuando Tcl_WaitForEvent habría esperado eternamente porque no había fuentes de eventos activas y el tiempo de espera era infinito.

Tcl_AlertNotifier se utiliza en aplicaciones multihilo para permitir que cualquier hilo "despierte" al notificador para alertarlo sobre nuevos eventos en su cola. Tcl_AlertNotifier requiere como argumento el manejador del notificador devuelto por Tcl_InitNotifier.

Si el notificador se va a utilizar con un bucle de eventos externo, entonces también debe soportar la interfaz Tcl_SetTimer. Tcl_SetTimer es invocado por Tcl_SetMaxBlockTime cada vez que se ha reducido el tiempo máximo de bloqueo. Tcl_SetTimer debe organizar que el bucle de eventos externo invoque Tcl_ServiceAll después del intervalo especificado, incluso si no han ocurrido eventos. Esta interfaz es necesaria porque Tcl_WaitForEvent no se invoca cuando hay un bucle de eventos externo. Si el notificador solo se va a utilizar desde Tcl_DoOneEvent, entonces Tcl_SetTimer no necesita hacer nada.

Tcl_ServiceModeHook es llamado por la parte independiente de la plataforma del notificador cuando el código del cliente realiza una llamada a Tcl_SetServiceMode. Este hook se proporciona para soportar sistemas operativos que requieren un manejo especial de eventos cuando la aplicación está en un bucle modal (el notificador de Windows, por ejemplo, utiliza este hook para crear una ventana de comunicación).

En sistemas Unix, la fuente de eventos de archivo también necesita soporte del notificador. La fuente de eventos de archivo consta de los procedimientos Tcl_CreateFileHandler y Tcl_DeleteFileHandler, que se describen en la página del manual de Tcl_CreateFileHandler.

Las interfaces Tcl_Sleep y Tcl_DoOneEvent se describen en sus respectivas páginas del manual.

La forma más sencilla de crear un nuevo notificador es examinar el código de un notificador existente, como los archivos unix/tclUnixNotfy.c o win/tclWinNotify.c en la distribución fuente de Tcl.

REEMPLAZO DEL NOTIFICADOR

Un notificador que ha sido escrito de acuerdo con las convenciones anteriores también puede instalarse en un proceso en ejecución en lugar del notificador estándar. Este mecanismo se utiliza para que un solo ejecutable pueda ser utilizado (con el notificador estándar) como un programa independiente y reutilizado (con un notificador de reemplazo en una extensión cargable) como una extensión para otro programa, como un plugin de navegador web.

Para hacer esto, la extensión realiza una llamada a Tcl_SetNotifier pasando un puntero a una estructura de datos Tcl_NotifierProcs. La estructura tiene el siguiente diseño:

typedef struct Tcl_NotifierProcs {
    Tcl_SetTimerProc *setTimerProc;
    Tcl_WaitForEventProc *waitForEventProc;
    Tcl_CreateFileHandlerProc *createFileHandlerProc;
    Tcl_DeleteFileHandlerProc *deleteFileHandlerProc;
    Tcl_InitNotifierProc *initNotifierProc;
    Tcl_FinalizeNotifierProc *finalizeNotifierProc;
    Tcl_AlertNotifierProc *alertNotifierProc;
    Tcl_ServiceModeHookProc *serviceModeHookProc;
} Tcl_NotifierProcs;

Después de la llamada a Tcl_SetNotifier, los punteros proporcionados en la estructura Tcl_NotifierProcs reemplazan cualquier notificador que se haya instalado en el proceso.

Es extraordinariamente imprudente reemplazar un notificador en ejecución. Normalmente, Tcl_SetNotifier debe llamarse en el momento de la inicialización del proceso antes de la primera llamada a Tcl_InitNotifier.

BUCLES DE EVENTOS EXTERNOS

Las interfaces del notificador están diseñadas para que Tcl pueda incrustarse en aplicaciones que tengan sus propios bucles de eventos privados. En este caso, la aplicación no llama a Tcl_DoOneEvent excepto en el caso de bucles de eventos recursivos, como las llamadas a los comandos de Tcl update o vwait. La mayor parte del tiempo se pasa en el bucle de eventos externo de la aplicación. En este caso, el notificador debe organizar que el bucle de eventos externo llame de vuelta a Tcl cuando ocurra algo en las diversas fuentes de eventos de Tcl. Estas llamadas de retorno deben organizar que se coloquen los eventos de Tcl apropiados en la cola de eventos de Tcl.

Dado que el bucle de eventos externo no llama a Tcl_DoOneEvent de forma regular, depende del notificador organizar que se llame a Tcl_ServiceEvent siempre que haya eventos pendientes en la cola de eventos de Tcl. La forma más sencilla de hacerlo es invocar Tcl_ServiceAll al final de cada llamada de retorno del bucle de eventos externo. Esto garantizará que todas las fuentes de eventos se consulten, que se atiendan todos los eventos en cola y que se procesen todos los manejadores ociosos pendientes antes de devolver el control a la aplicación. Además, las fuentes de eventos que necesitan consultar eventos pueden llamar a Tcl_SetMaxBlockTime para forzar al bucle de eventos externo a llamar a Tcl, incluso si no hay eventos disponibles en la cola de eventos del sistema.

Como efecto secundario del procesamiento de eventos detectados en el bucle de eventos externo principal, Tcl puede invocar Tcl_DoOneEvent para iniciar un bucle de eventos recursivo en comandos como vwait. Tcl_DoOneEvent invocará el bucle de eventos externo, lo que resultará en llamadas de retorno como se describe en el párrafo anterior, lo que a su vez resultará en llamadas a Tcl_ServiceAll. Sin embargo, en estos casos, es indeseable atender eventos en Tcl_ServiceAll. Atender eventos allí es innecesario porque el control volverá inmediatamente al bucle de eventos externo y, por lo tanto, a Tcl_DoOneEvent, que puede atender los eventos por sí mismo. Además, Tcl_DoOneEvent debe atender solo un evento, mientras que Tcl_ServiceAll normalmente atiende todos los eventos pendientes. Para manejar esta situación, Tcl_DoOneEvent establece una bandera para Tcl_ServiceAll que hace que esta devuelva sin atender ningún evento. Esta bandera se llama "modo de servicio"; Tcl_DoOneEvent la restaura a su valor anterior antes de devolver.

En algunos casos, sin embargo, puede ser necesario que Tcl_ServiceAll atienda eventos incluso cuando ha sido invocado desde Tcl_DoOneEvent. Esto ocurre cuando hay otro bucle de eventos recursivo invocado a través de un manejador de eventos llamado por Tcl_DoOneEvent (como uno que forma parte de un widget nativo). En este caso, Tcl_DoOneEvent puede no tener la oportunidad de atender eventos, por lo que Tcl_ServiceAll debe atenderlos todos. Cualquier bucle de eventos recursivo que llame a un bucle de eventos externo en lugar de a Tcl_DoOneEvent debe restablecer el modo de servicio para que todos los eventos se procesen en Tcl_ServiceAll. Esto se hace invocando el procedimiento Tcl_SetServiceMode. Si a Tcl_SetServiceMode se le pasa TCL_SERVICE_NONE, entonces las llamadas a Tcl_ServiceAll devolverán inmediatamente sin procesar ningún evento. Si a Tcl_SetServiceMode se le pasa TCL_SERVICE_ALL, entonces las llamadas a Tcl_ServiceAll se comportarán normalmente. Tcl_SetServiceMode devuelve el valor anterior del modo de servicio, que debe restaurarse cuando salga el bucle recursivo. Tcl_GetServiceMode devuelve el valor actual del modo de servicio.

INTRODUCTION

The Tcl event loop is the heart of any Tcl application. It is responsible for waiting for events to occur and dispatching them to the appropriate handlers. The event loop is implemented by a notifier, which is a set of functions that Tcl calls to interact with the underlying operating system's event mechanism. This document describes the Tcl notifier mechanism and related event handling functions.

NOTIFIER BASICS

A notifier is responsible for the following:

  • Initialization and finalization: Tcl_InitNotifier and Tcl_FinalizeNotifier are called when Tcl is initialized and finalized, respectively.
  • Setting and getting the notifier: Tcl_SetNotifier and Tcl_GetNotifier allow you to replace the default notifier with a custom one.
  • Event sources: Event sources are objects that represent a source of events, such as a file descriptor, a timer, or an idle event. Tcl_CreateEventSource, Tcl_DeleteEventSource, and Tcl_GetEventSource are used to manage event sources.
  • Event queue: The event queue is a list of events that are waiting to be processed. Tcl_QueueEvent and Tcl_ThreadQueueEvent are used to add events to the queue.
  • Notifying the event loop: Tcl_AlertNotifier and Tcl_ThreadAlert are used to signal the event loop that there are new events to process.
  • Servicing events: Tcl_ServiceAll and Tcl_ServiceIdle are used to process events from the queue.

CREATING A NEW EVENT SOURCE

To create a new event source, you need to provide a Tcl_EventProc function that will be called when an event occurs, and optionally a Tcl_EventDeleteProc function that will be called when the event source is deleted.

```c
Tcl_EventSource *Tcl_CreateEventSource(Tcl_EventProc *proc, Tcl_EventDeleteProc *deleteProc, ClientData clientData);
```

The `clientData` argument is a pointer to the data associated with the event source.

CREATING A NEW NOTIFIER

To create a new notifier, you need to define a structure that conforms to the Tcl_Notifier structure and provides implementations for the required functions.

```c
typedef struct Tcl_Notifier {
Tcl_NotifierType type;
Tcl_InitNotifierProc *initNotifier;
Tcl_FinalizeNotifierProc *finalizeNotifier;
Tcl_SetNotifierProc *setNotifier;
Tcl_GetNotifierProc *getNotifier;
Tcl_CreateEventSourceProc *createEventSource;
Tcl_DeleteEventSourceProc *deleteEventSource;
Tcl_GetEventSourceProc *getEventSource;
Tcl_QueueEventProc *queueEvent;
Tcl_DeleteQueueBindingProc *deleteQueueBinding;
Tcl_AlertNotifierProc *alertNotifier;
Tcl_ServiceModeProc *serviceMode;
Tcl_ServiceAllProc *serviceAll;
Tcl_ServiceIdleProc *serviceIdle;
Tcl_ThreadQueueEventProc *threadQueueEvent;
Tcl_ThreadAlertProc *threadAlert;
} Tcl_Notifier;
```

Then, you can register your notifier using `Tcl_SetNotifier`.

REPLACING THE NOTIFIER

You can replace the default Tcl notifier with your own custom notifier by calling `Tcl_SetNotifier` with a pointer to your notifier structure. The previous notifier will be returned.

```c
Tcl_Notifier *oldNotifierPtr = Tcl_SetNotifier(myNotifierPtr);
```

EXTERNAL EVENT LOOPS

Tcl can be integrated into an external event loop. In this case, Tcl will not manage the event loop itself, but will instead rely on the external loop to dispatch events. To achieve this, you need to:

  • Create a notifier that does not block when waiting for events.
  • Call `Tcl_ServiceAll` or `Tcl_ServiceIdle` when appropriate from your external event loop.
  • Use `Tcl_AlertNotifier` to signal Tcl that there are events to process.
