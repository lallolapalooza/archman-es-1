DESCRIPCIÓN

Tcl utiliza una arquitectura de canales de dos capas. Proporciona una capa superior genérica para permitir que los programas C y Tcl realicen entrada y salida utilizando las mismas API para una variedad de archivos, dispositivos, sockets, etc. Las API C genéricas se describen en la entrada del manual para Tcl_OpenFileChannel.

La capa inferior proporciona controladores de canales específicos del tipo para cada tipo de dispositivo compatible en cada plataforma. Esta entrada del manual describe las API C utilizadas para comunicarse entre la capa genérica y los controladores de canales específicos del tipo. También explica cómo se pueden agregar nuevos tipos de canales proporcionando nuevos controladores de canales.

Los controladores de canales consisten en varios componentes: Primero, cada controlador de canales proporciona una estructura Tcl_ChannelType que contiene punteros a funciones que implementan las diversas operaciones utilizadas por la capa genérica para comunicarse con el controlador de canales. La estructura Tcl_ChannelType y las funciones a las que hace referencia se describen en la sección TCL_CHANNELTYPE, más abajo.

Segundo, los controladores de canales suelen proporcionar un comando Tcl para crear instancias de ese tipo de canal. Por ejemplo, el comando Tcl open crea canales que utilizan los controladores de canales de archivo y comando, y el comando Tcl socket crea canales que utilizan sockets TCP para la comunicación de red.

Tercero, un controlador de canales proporciona opcionalmente una función C para abrir instancias de canal de ese tipo. Por ejemplo, Tcl_OpenFileChannel abre un canal que utiliza el controlador de canales de archivo, y Tcl_OpenTcpClient abre un canal que utiliza el protocolo de red TCP. Estas funciones de creación suelen utilizar Tcl_CreateChannel internamente para abrir el canal.

Para agregar un nuevo tipo de canal, debe implementar una API C o un comando Tcl que abra un canal invocando Tcl_CreateChannel. Cuando su controlador llama a Tcl_CreateChannel, pasa una estructura Tcl_ChannelType que describe los procedimientos de E/S del controlador. Luego, la capa genérica invocará las funciones referenciadas en esa estructura para realizar operaciones en el canal.

Tcl_CreateChannel abre un nuevo canal y asocia los suministrados typePtr y instanceData con él. El canal se abre en el modo indicado por mask. Para una discusión de los controladores de canales, sus operaciones y la estructura Tcl_ChannelType, vea la sección TCL_CHANNELTYPE, más abajo.

Tcl_CreateChannel interactúa con el código que administra los canales estándar. Una vez que se inicializó un canal estándar ya sea a través de una llamada a Tcl_GetStdChannel o a Tcl_SetStdChannel, cerrar este canal estándar hará que la próxima llamada a Tcl_CreateChannel convierta también el nuevo canal en el nuevo canal estándar. Ver Tcl_StandardChannels para un tratado general sobre los canales estándar y el comportamiento de la biblioteca Tcl con respecto a ellos.

Tcl_GetChannelInstanceData devuelve los datos de instancia asociados con el canal en channel. Esto es lo mismo que el argumento instanceData en la llamada a Tcl_CreateChannel que creó este canal.

Tcl_GetChannelType devuelve un puntero a la estructura Tcl_ChannelType utilizada por el canal en el argumento channel. Esto es lo mismo que el argumento typePtr en la llamada a Tcl_CreateChannel que creó este canal.

Tcl_GetChannelName devuelve una cadena que contiene el nombre asociado con el canal, o NULL si el argumento channelName de Tcl_CreateChannel era NULL.

TCL_CHANNELTYPE

Un driver de canal proporciona una estructura Tcl_ChannelType que contiene punteros a funciones que implementan las diversas operaciones en un canal; estas operaciones se invocan según sea necesario por la capa genérica. La estructura fue versionada desde Tcl 8.3.2/8.4 para corregir un problema con los drivers de canal estacados. Consulte la sección OLD CHANNEL TYPES para detalles sobre la estructura antigua.

La estructura Tcl_ChannelType contiene los siguientes campos:

typedef struct Tcl_ChannelType {
        const char *typeName;
        Tcl_ChannelTypeVersion version;
        Tcl_DriverCloseProc *closeProc;
        Tcl_DriverInputProc *inputProc;
        Tcl_DriverOutputProc *outputProc;
        Tcl_DriverSeekProc *seekProc;
        Tcl_DriverSetOptionProc *setOptionProc;
        Tcl_DriverGetOptionProc *getOptionProc;
        Tcl_DriverWatchProc *watchProc;
        Tcl_DriverGetHandleProc *getHandleProc;
        Tcl_DriverClose2Proc *close2Proc;
        Tcl_DriverBlockModeProc *blockModeProc;
        Tcl_DriverFlushProc *flushProc;
        Tcl_DriverHandlerProc *handlerProc;
        Tcl_DriverWideSeekProc *wideSeekProc;
        Tcl_DriverThreadActionProc *threadActionProc;
        Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

No es necesario proporcionar implementaciones para todas las operaciones de canal. Los que no sean necesarios pueden ser establecidos a NULL en la estructura: blockModeProc, seekProc, setOptionProc, getOptionProc, getHandleProc, y close2Proc, además de flushProc, handlerProc, threadActionProc, y truncateProc. Otros funciones que no puedan implementarse de forma significativa deben devolver EINVAL cuando se llamen, para indicar que las operaciones que representan no están disponibles. También es importante notar que wideSeekProc puede ser NULL si seekProc es.

El usuario debe usar solo esta estructura para la instanciación de Tcl_ChannelType. Cuando se refieran a campos de una estructura Tcl_ChannelType, deben usar las siguientes funciones para obtener los valores: Tcl_ChannelName, Tcl_ChannelVersion, Tcl_ChannelBlockModeProc, Tcl_ChannelCloseProc, Tcl_ChannelClose2Proc, Tcl_ChannelInputProc, Tcl_ChannelOutputProc, Tcl_ChannelSeekProc, Tcl_ChannelWideSeekProc, Tcl_ChannelThreadActionProc, Tcl_ChannelTruncateProc, Tcl_ChannelSetOptionProc, Tcl_ChannelGetOptionProc, Tcl_ChannelWatchProc, Tcl_ChannelGetHandleProc, y Tcl_ChannelFlushProc, o Tcl_ChannelHandlerProc.

El cambio en las estructuras fue hecho de manera que los tipos de canal estándar sean compatibles binariamente. Sin embargo, los tipos de canal que utilizan canales estacados (es decir, TLS, Trf) tienen nuevas versiones para corresponder a este cambio, ya que el código anterior de los canales estacados tenia problemas.

TYPENAME

El campo typeName contiene una cadena de caracteres nula que identifica el tipo de dispositivo implementado por este driver, por ejemplo, file o socket.

Este valor se puede obtener con Tcl_ChannelName, que devuelve un puntero a la cadena.

VERSION

El campo version debe ser establecido a la versión del estructura que requieres. TCL_CHANNEL_VERSION_2 es el mínimo recomendado. TCL_CHANNEL_VERSION_3 debe ser establecido para especificar el campo wideSeekProc. TCL_CHANNEL_VERSION_4 debe ser establecido para especificar el campo threadActionProc (incluye wideSeekProc). TCL_CHANNEL_VERSION_5 debe ser establecido para especificar los campos truncateProc (incluye wideSeekProc y threadActionProc). Si no es establecido a ninguno de estos, se asume que esta Tcl_ChannelType tiene la estructura original. Consulte OLD CHANNEL TYPES para más detalles. Mientras que Tcl reconocerá y funcionará con cualquiera de estas estructuras, los canales estacados deben ser de al menos TCL_CHANNEL_VERSION_2 para funcionar correctamente.

Este valor se puede obtener con Tcl_ChannelVersion, que devuelve uno de TCL_CHANNEL_VERSION_5, TCL_CHANNEL_VERSION_4, TCL_CHANNEL_VERSION_3, TCL_CHANNEL_VERSION_2 o TCL_CHANNEL_VERSION_1.

BLOCKMODEPROC

El campo blockModeProc contiene el dirección de una función llamada por la capa genérica para establecer el modo bloqueante y no bloqueante en el dispositivo. BlockModeProc debe corresponder al siguiente prototipo:

typedef int Tcl_DriverBlockModeProc(
        ClientData instanceData,
        int mode);

El instanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando este canal fue creado. El mode es el mismo que TCL_MODE_BLOCKING o TCL_MODE_NONBLOCKING para establecer el dispositivo en modo bloqueante o no bloqueante. La función debe devolver cero si la operación fue exitosa, o un código de error POSIX no cero si la operación falló.

Si la operación es exitosa, la función puede modificar el instanceData proporcionado para registrar que el canal entró en modo bloqueante o no bloqueante y implementar el comportamiento bloqueante o no bloqueante. Para algunos tipos de dispositivos, el comportamiento bloqueante y no bloqueante puede ser implementado por el sistema operativo bajo el dispositivo; para otros tipos de dispositivos, el comportamiento debe emularse en el driver de canal.

Este valor se puede obtener con Tcl_ChannelBlockModeProc, que devuelve un puntero a la función.

Un driver de canal que no proporciona un blockModeProc debe ser muy cuidadoso. Debe indicar exactamente qué modo bloqueante es aceptable para él, y debe documentar esto para el usuario de manera que el modo bloqueante del canal no se cambie a un valor inaceptable. Cualquier confusión aquí puede provocar un (spurious y difícil de encontrar) deadlock en el intérprete.

CLOSEPROC AND CLOSE2PROC

El campo closeProc contiene el dirección de una función llamada por la capa genérica para limpiar información relacionada con el driver cuando el canal es cerrado. CloseProc debe corresponder al siguiente prototipo:

typedef int Tcl_DriverCloseProc(
        ClientData instanceData,
        Tcl_Interp *interp);

El instanceData es el mismo que el valor proporcionado a Tcl_CreateChannel cuando el canal fue creado. La función debe liberar cualquier almacenamiento mantenido por el driver de canal para este canal y cerrar los dispositivos de entrada y salida encapsulados por este canal. Antes de llamarse esta función, todos los datos de salida acumulados se han vaciado en el dispositivo. No se invocarán más operaciones del driver después de llamar a closeProc. Si la operación de cierre es exitosa, la función puede devolver cero; de lo contrario, debe devolver un código de error POSIX no cero.

La función close2Proc es una versión más nueva de closeProc que puede ser utilizada para manejar el cierre de canales estacados. El prototipo es:

typedef int Tcl_DriverClose2Proc(
        ClientData instanceData,
        int option,
        Tcl_Interp *interp);

Si se proporciona close2Proc, entonces closeProc debe ser NULL. El campo option puede ser TCL_CLOSE_READ o TCL_CLOSE_WRITE para cerrar solo el canal de lectura o escritura, respectivamente, o TCL_CLOSE_CHANNEL para cerrar ambos canales. El valor de retorno es el mismo que closeProc.

Estos valores se pueden obtener con Tcl_ChannelCloseProc y Tcl_ChannelClose2Proc, que devuelven punteros a las funciones.

Alternativamente, los canales que admiten el cierre de los lados de lectura y escritura de forma independiente pueden establecer closeProc en TCL_CLOSE2PROC y close2Proc en la dirección de una función que coincida con el siguiente prototipo:

typedef int Tcl_DriverClose2Proc(
        ClientData instanceData,
        Tcl_Interp *interp,

Se llamará a close2Proc con flags establecido en una combinación OR de TCL_CLOSE_READ o TCL_CLOSE_WRITE para indicar que el controlador debe cerrar el lado de lectura y/o escritura del canal. Se puede invocar al controlador del canal para realizar operaciones adicionales en el canal después de que se llame a close2Proc para cerrar uno o ambos lados del canal. Si flags es 0 (cero), el controlador debería cerrar el canal de la manera descrita anteriormente para closeProc. No se invocarán más operaciones en esta instancia después de que se llame a close2Proc con todos los flags borrados. En todos los casos, la función close2Proc debería devolver cero si la operación de cierre fue exitosa; de lo contrario, debería devolver un código de error POSIX distinto de cero. Además, si ocurre un error y interp no es NULL, el procedimiento debería almacenar un mensaje de error en el resultado del intérprete.

Los valores closeProc y close2Proc se pueden recuperar con Tcl_ChannelCloseProc o Tcl_ChannelClose2Proc, que devuelven un puntero a la función respectiva.

INPUTPROC

El campo inputProc contiene la dirección de una función llamada por la capa genérica para leer datos del archivo o dispositivo y almacenarlos en un búfer interno. InputProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverInputProc(
        ClientData instanceData,
        char *buf,
        int bufSize,
        int *errorCodePtr);

InstanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando se creó el canal. El argumento buf apunta a una matriz de bytes donde se almacenará la entrada del dispositivo, y el argumento bufSize indica cuántos bytes están disponibles en buf.

El argumento errorCodePtr apunta a una variable entera proporcionada por la capa genérica. Si ocurre un error, la función debe establecer la variable en un código de error POSIX que identifique el error ocurrido.

La función debe leer datos del dispositivo de entrada encapsulado por el canal y almacenarlos en buf. En caso de éxito, la función debe devolver un entero no negativo que indique cuántos bytes se leyeron del dispositivo de entrada y se almacenaron en buf. En caso de error, la función debe devolver -1. Si ocurre un error después de que se hayan leído algunos datos del dispositivo, esos datos se pierden.

Si inputProc puede determinar que el dispositivo de entrada tiene algunos datos disponibles pero menos de los solicitados por el argumento bufSize, la función solo debe intentar leer tantos datos como estén disponibles y devolver sin bloquear. Si el dispositivo de entrada no tiene datos disponibles en absoluto y el canal está en modo no bloqueante, la función debe devolver un error EAGAIN. Si el dispositivo de entrada no tiene datos disponibles en absoluto y el canal está en modo bloqueante, la función debe bloquearse durante el menor tiempo posible hasta que se pueda leer al menos un byte de datos del dispositivo; luego, debe devolver tantos datos como pueda leer sin bloquear.

Este valor se puede recuperar con Tcl_ChannelInputProc, que devuelve un puntero a la función.

OUTPUTPROC

El campo outputProc contiene la dirección de una función llamada por la capa genérica para transferir datos de un búfer interno al dispositivo de salida. OutputProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverOutputProc(
        ClientData instanceData,
        const char *buf,
        int toWrite,
        int *errorCodePtr);

InstanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando se creó el canal. El argumento buf contiene una matriz de bytes que se escribirán en el dispositivo, y el argumento toWrite indica cuántos bytes se escribirán desde el argumento buf.

El argumento errorCodePtr apunta a una variable entera proporcionada por la capa genérica. Si ocurre un error, la función debe establecer esta variable en un código de error POSIX que identifique el error.

La función debe escribir los datos en buf en el dispositivo de salida encapsulado por el canal. En caso de éxito, la función debe devolver un entero no negativo que indique cuántos bytes se escribieron en el dispositivo de salida. El valor de retorno es normalmente el mismo que toWrite, pero puede ser menor en algunos casos, como si la operación de salida se interrumpe por una señal. Si ocurre un error, la función debe devolver -1. En caso de error, es posible que algunos datos se hayan escrito en el dispositivo.

Si el canal no está bloqueado y el dispositivo de salida no puede absorber ningún dato, la función debe devolver -1 con un error EAGAIN sin escribir ningún dato.

Este valor se puede recuperar con Tcl_ChannelOutputProc, que devuelve un puntero a la función.

SEEKPROC Y WIDESEEKPROC

El campo seekProc contiene la dirección de una función llamada por la capa genérica para mover el punto de acceso en el que se aplicarán las operaciones de entrada o salida subsiguientes. SeekProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverSeekProc(
        ClientData instanceData,
        long offset,
        int seekMode,
        int *errorCodePtr);

El argumento instanceData es el mismo que el valor dado a Tcl_CreateChannel cuando se creó este canal. Offset y seekMode tienen el mismo significado que para el procedimiento Tcl_Seek (descrito en la entrada del manual de Tcl_OpenFileChannel).

El argumento errorCodePtr apunta a una variable entera proporcionada por la capa genérica para devolver valores errno de la función. La función debe establecer esta variable en un código de error POSIX si ocurre un error. La función debe almacenar un código de error EINVAL si el tipo de canal no implementa la búsqueda.

El valor de retorno es el nuevo punto de acceso o -1 en caso de error. Si ocurrió un error, la función no debe mover el punto de acceso.

Si hay un campo seekProc no NULL, el campo wideSeekProc puede contener la dirección de una función alternativa que se utilizará, la cual maneja offsets amplios (es decir, mayores de 32 bits), permitiendo así búsquedas dentro de archivos de más de 2 GB. Se llamará a wideSeekProc con preferencia sobre seekProc, pero ambos deben estar definidos si se define wideSeekProc. WideSeekProc debe coincidir con el siguiente prototipo:

typedef Tcl_WideInt Tcl_DriverWideSeekProc(
        ClientData instanceData,
        Tcl_WideInt offset,
        int seekMode,
        int *errorCodePtr);

Los argumentos y valores de retorno significan lo mismo que con seekProc arriba, excepto que el tipo de offsets y el tipo de retorno son diferentes.

El valor seekProc se puede recuperar con Tcl_ChannelSeekProc, que devuelve un puntero a la función, y de manera similar, wideSeekProc se puede recuperar con Tcl_ChannelWideSeekProc.

SETOPTIONPROC

El campo setOptionProc contiene la dirección de una función llamada por la capa genérica para establecer una opción específica del tipo de canal en un canal. setOptionProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverSetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        const char *newValue);

optionName es el nombre de una opción a establecer, y newValue es el nuevo valor para esa opción, como una cadena. InstanceData es el mismo que el valor dado a Tcl_CreateChannel cuando se creó este canal. La función debe realizar cualquier acción específica del tipo de canal que sea necesaria para implementar el nuevo valor de la opción.

Algunas opciones son manejadas por el código genérico y esta función nunca se llama para establecerlas, por ejemplo, -blockmode. Otras opciones son específicas de cada tipo de canal y se llamará al procedimiento setOptionProc del controlador del canal para implementarlas. El campo setOptionProc puede ser NULL, lo que indica que este tipo de canal no admite opciones específicas del tipo.

Si el valor de la opción se modifica correctamente al nuevo valor, la función devuelve TCL_OK. Debe llamar a Tcl_BadChannelOption, que a su vez devuelve TCL_ERROR si optionName no se reconoce. Si newValue especifica un valor para la opción que no es compatible o si ocurre un error de llamada al sistema, la función debe dejar un mensaje de error en el resultado de interp si interp no es NULL. La función también debe llamar a Tcl_SetErrno para almacenar un código de error POSIX apropiado.

Este valor se puede recuperar con Tcl_ChannelSetOptionProc, que devuelve un puntero a la función.

GETOPTIONPROC

El campo getOptionProc contiene la dirección de una función llamada por la capa genérica para obtener el valor de una opción específica del tipo de canal en un canal. getOptionProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverGetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        Tcl_DString *optionValue);

OptionName es el nombre de una opción compatible con este tipo de canal. Si el nombre de la opción no es NULL, la función almacena su valor actual, como una cadena, en la cadena dinámica de Tcl optionValue. Si optionName es NULL, la función almacena en optionValue una lista alterna de todas las opciones compatibles y sus valores actuales. En caso de éxito, la función devuelve TCL_OK. NAME

Tcl_ChannelWideSeekProc - procedure to seek to a specific position in a channel

SYNOPSIS

#include <tcl.h>

int
Tcl_ChannelWideSeekProc(
    Tcl_Channel channel,
    Tcl_WideInt offset,
    int seekMode)

ARGUMENTS

Tcl_Channel channel
The channel to seek in.
Tcl_WideInt offset
The offset to seek to, in bytes. This is a 64-bit integer.
int seekMode
Specifies how the offset is interpreted. Should be one of
  • SEEK_SET: The offset is from the beginning of the file.
  • SEEK_CUR: The offset is from the current position.
  • SEEK_END: The offset is from the end of the file.
These constants are defined in Tcl's internal header files, but not exported to user code. For 32-bit Tcl versions, they are defined as 0, 1, and 2 respectively. For 64-bit Tcl versions, they are defined as 0, 1, and 2 respectively.

DESCRIPTION

This procedure is used by channel drivers to implement seeking on channels. It is called by Tcl_Seek, and should be used by channel drivers for seeking operations. It handles interaction with the channel's underlying implementation and updates the channel's internal state.

The procedure seeks to a position specified by offset relative to the beginning of the channel, the current position, or the end of the channel, depending on the value of seekMode. The offset is a 64-bit integer, allowing seeking in very large files (larger than 2GB).

Upon successful completion, the procedure returns the new current position of the channel, in bytes, from the beginning of the channel. If an error occurs, it returns -1 and sets a Tcl error.

TCL_CHANNELTYPE

Channel drivers that support seeking should implement a Tcl_ChannelType structure containing a non-NULL seekProc field pointing to a procedure with the signature of Tcl_ChannelWideSeekProc. This procedure should perform the actual seek operation on the underlying channel representation (e.g., by calling fseeko or lseek).

TCL_BADCHANNELOPTION

If the channel does not support seeking (i.e., its Tcl_ChannelType has a NULL seekProc), then Tcl_Seek will return -1 and set an error indicating that the channel is not seekable.

OLD CHANNEL TYPES

Older versions of Tcl used a 32-bit seek function and offset. This function replaces that, providing 64-bit seek capability. Channels registered with older channel types will continue to use the 32-bit seek mechanism.
