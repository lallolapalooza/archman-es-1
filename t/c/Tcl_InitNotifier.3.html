ARGUMENTOS

Tcl_EventSetupProc *setupProc (entrada)
Procedimiento a invocar para preparar la espera de eventos en Tcl_DoOneEvent.
Tcl_EventCheckProc *checkProc (entrada)
Procedimiento para que Tcl_DoOneEvent lo invoque después de esperar eventos. Comprueba si han ocurrido eventos y, si es así, los pone en cola.
ClientData clientData (entrada)
Valor arbitrario de una palabra para pasar a setupProc, checkProc, o deleteProc.
const Tcl_Time *timePtr (entrada)
Indica la cantidad máxima de tiempo a esperar por un evento. Se especifica como un intervalo (cuánto esperar), no como una hora absoluta (cuándo despertarse). Si el puntero pasado a Tcl_WaitForEvent es NULL, significa que no hay tiempo máximo de espera: esperar indefinidamente si es necesario.
Tcl_Event *evPtr (entrada)
Un evento para añadir a la cola de eventos. El almacenamiento para el evento debe haber sido asignado por el llamador usando Tcl_Alloc o ckalloc.
Tcl_QueuePosition position (entrada)
Dónde añadir el nuevo evento en la cola: TCL_QUEUE_TAIL, TCL_QUEUE_HEAD, o TCL_QUEUE_MARK.
Tcl_ThreadId threadId (entrada)
Un identificador único para un hilo.
Tcl_EventDeleteProc *deleteProc (entrada)
Procedimiento a invocar para cada evento en cola en Tcl_DeleteEvents.
int flags (entrada)
Qué tipos de eventos deben ser atendidos. Estas banderas son las mismas que las pasadas a Tcl_DoOneEvent.
int mode (entrada)
Indica si los eventos deben ser atendidos por Tcl_ServiceAll. Debe ser uno de TCL_SERVICE_NONE o TCL_SERVICE_ALL.
Tcl_NotifierProcs* notifierProcPtr (entrada)
Estructura de punteros de función que describe los procedimientos del notificador que van a reemplazar a los instalados en el ejecutable. Ver REEMPLAZANDO EL NOTIFICADOR para más detalles.

INTRODUCCIÓN

Las interfaces descritas aquí se utilizan para personalizar el bucle de eventos de Tcl. Las dos personalizaciones más comunes son añadir nuevas fuentes de eventos y fusionar el bucle de eventos de Tcl con algún otro bucle de eventos, como uno proporcionado por una aplicación en la que Tcl está embebido. Cada una de estas tareas se describe en una sección separada a continuación.

Los procedimientos de esta entrada del manual son los bloques de construcción con los que se construye el notificador de eventos de Tcl. El notificador de eventos es la capa más baja en el mecanismo de eventos de Tcl. Consta de tres cosas:

[1]
Fuentes de eventos: representan las formas en que se pueden generar eventos. Por ejemplo, existe una fuente de eventos de temporizador que implementa el procedimiento Tcl_CreateTimerHandler y el comando after, y existe una fuente de eventos de archivo que implementa el procedimiento Tcl_CreateFileHandler en sistemas Unix. Una fuente de eventos debe trabajar con el notificador para detectar eventos en los momentos adecuados, registrarlos en la cola de eventos y, finalmente, notificar al software de nivel superior que han ocurrido. Los procedimientos Tcl_CreateEventSource, Tcl_DeleteEventSource, Tcl_SetMaxBlockTime, Tcl_QueueEvent y Tcl_DeleteEvents son utilizados principalmente por las fuentes de eventos.
[2]
La cola de eventos: para aplicaciones sin hilos, hay una única cola para toda la aplicación, que contiene eventos que han sido detectados pero aún no atendidos. Las fuentes de eventos colocan eventos en la cola para que puedan ser procesados en orden en momentos apropiados durante el bucle de eventos. La cola de eventos garantiza una disciplina justa de manejo de eventos, de modo que ninguna fuente de eventos pueda dejar a las otras sin servicio. También permite guardar eventos para ser atendidos en un momento futuro. Las aplicaciones con hilos funcionan de manera similar, excepto que hay una cola de eventos separada para cada hilo que contiene un intérprete de Tcl. Tcl_QueueEvent se utiliza (principalmente por las fuentes de eventos) para añadir eventos a la cola de eventos y Tcl_DeleteEvents se utiliza para eliminar eventos de la cola sin procesarlos. En una aplicación con hilos, Tcl_QueueEvent añade un evento a la cola del hilo actual, y Tcl_ThreadQueueEvent añade un evento a una cola en un hilo específico.
[3]
El bucle de eventos: para detectar y procesar eventos, la aplicación entra en un bucle que espera a que ocurran eventos, los coloca en la cola de eventos y luego los procesa. La mayoría de las aplicaciones lo harán llamando al procedimiento Tcl_DoOneEvent, que se describe en una entrada de manual separada.

La mayoría de las aplicaciones Tcl no necesitan preocuparse por ninguno de los detalles internos del notificador de Tcl. Sin embargo, el notificador ahora tiene suficiente flexibilidad para ser reorientado ya sea para una nueva plataforma o para utilizar un bucle de eventos externo (como el bucle de eventos de Motif, cuando Tcl está incrustado en una aplicación de Motif). Los procedimientos Tcl_WaitForEvent y Tcl_SetTimer normalmente son implementados por Tcl, pero pueden ser reemplazados con nuevas versiones para reorientar el notificador (los procedimientos Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_Sleep, Tcl_CreateFileHandler y Tcl_DeleteFileHandler también deben ser reemplazados; ver CREANDO UN NUEVO NOTIFICADOR abajo para más detalles). Los procedimientos Tcl_ServiceAll, Tcl_ServiceEvent, Tcl_GetServiceMode y Tcl_SetServiceMode se proporcionan para ayudar a conectar el bucle de eventos de Tcl a un bucle de eventos externo como el de Motif.

FUNDAMENTOS DEL NOTIFICADOR

La forma más sencilla de entender cómo funciona el notificador es considerar lo que sucede cuando se llama a Tcl_DoOneEvent. A Tcl_DoOneEvent se le pasa un argumento flags que indica qué tipo de eventos está bien procesar y también si debe bloquearse o no si no hay eventos listos. Tcl_DoOneEvent realiza las siguientes acciones:

[1]
Comprueba la cola de eventos para ver si contiene algún evento que pueda ser atendido. Si es así, atiende el primer evento posible, lo elimina de la cola y retorna. Lo hace llamando a Tcl_ServiceEvent y pasando el argumento flags.
[2]
Prepara para bloquear por un evento. Para hacer esto, Tcl_DoOneEvent invoca un procedimiento de configuración en cada fuente de eventos. La fuente de eventos realizará la inicialización específica de la fuente de eventos y posiblemente llamará a Tcl_SetMaxBlockTime para limitar cuánto tiempo bloqueará Tcl_WaitForEvent si no ocurren nuevos eventos.
[3]
Llama a Tcl_WaitForEvent. Este procedimiento se implementa de manera diferente en distintas plataformas; espera a que ocurra un evento, basándose en la información proporcionada por las fuentes de eventos. Puede hacer que la aplicación se bloquee si timePtr especifica un intervalo distinto de 0. Tcl_WaitForEvent retorna cuando ha sucedido algo, como que un archivo esté listo para ser leído o que haya expirado el intervalo dado por timePtr. Si no hay eventos para que Tcl_WaitForEvent espere, por lo que se bloquearía indefinidamente, entonces retorna inmediatamente y Tcl_DoOneEvent retorna 0.
[4]
Llama a un procedimiento de comprobación en cada fuente de eventos. El procedimiento de comprobación determina si ocurrieron eventos de interés para esta fuente. Si es así, los eventos se añaden a la cola de eventos.

ALGORITMO DEL BUCLE DE EVENTOS

El bucle de eventos Tcl es una máquina de estados simple. Para cada llamada a Tcl_DoOneEvent, el bucle realiza las siguientes acciones:

[1]
Si hay eventos en cola cuya etapa de procesamiento es 0 (es decir, eventos que ya están listos para ser atendidos), atiende el primero de ellos, lo elimina de la cola y regresa.
[2]
Llama al procedimiento de configuración para cada fuente de eventos, pasándole el indicador flags que se pasó a Tcl_DoOneEvent. Cada procedimiento de configuración es responsable de asegurarse de que su fuente de eventos esté lista para informar de eventos del tipo deseado. Esto generalmente implica llamar a Tcl_SetMaxBlockTime para indicar cuánto tiempo debe esperar el bucle de eventos antes de volver a comprobar si hay eventos. Si una fuente de eventos tiene eventos listos para ser informados, puede llamar a Tcl_SetMaxBlockTime con un tiempo de bloqueo de cero segundos para asegurarse de que el bucle no espere innecesariamente.
[3]
Si no se solicitaron eventos de bloqueo y el bucle ya ha comprobado todas las fuentes de eventos, entonces el bucle regresará 0 para indicar que no se pudieron encontrar eventos.
[4]
Si se solicitaron eventos de bloqueo, llama a Tcl_WaitForEvent para esperar a que ocurra un evento. Tcl_WaitForEvent determinará el tiempo máximo de espera a partir de la información proporcionada por los procedimientos de configuración de las fuentes de eventos. Si ninguna fuente de eventos ha establecido un tiempo máximo de espera, el tiempo de espera será infinito; de lo contrario, será el tiempo mínimo especificado por cualquiera de las fuentes de eventos.
[5]
Una vez que Tcl_WaitForEvent regresa, el bucle vuelve a iterar sobre la cola de eventos para ver si contiene algún evento que pueda ser atendido. Si es así, atiende el primer evento posible, lo elimina de la cola y regresa.
[6]
Comprueba si hay callbacks inactivos pendientes. Si es así, invócalos a todos y regresa.
[7]
O bien devuelve 0 para indicar que no había eventos listos, o bien vuelve al paso [2] si el llamador solicitó bloqueo.

CREACIÓN DE UNA NUEVA FUENTE DE EVENTOS

Una fuente de eventos consta de tres procedimientos invocados por el notificador, más procedimientos C adicionales que son invocados por código de nivel superior para organizar callbacks basados en eventos. Los tres procedimientos llamados por el notificador consisten en los procedimientos de configuración y comprobación descritos anteriormente, más un procedimiento adicional que se invoca cuando se elimina un evento de la cola de eventos para su servicio.

El procedimiento Tcl_CreateEventSource crea una nueva fuente de eventos. Sus argumentos especifican el procedimiento de configuración y el procedimiento de comprobación para la fuente de eventos. SetupProc debe coincidir con el siguiente prototipo:

typedef void Tcl_EventSetupProc(
        ClientData clientData,
        int flags);

El argumento clientData será el mismo que el argumento clientData a Tcl_CreateEventSource; típicamente se usa para apuntar a información privada gestionada por la fuente de eventos. El argumento flags será el mismo que el argumento flags pasado a Tcl_DoOneEvent excepto que nunca será 0 (Tcl_DoOneEvent reemplaza 0 con TCL_ALL_EVENTS). Flags indica qué tipos de eventos deben considerarse; si el bit correspondiente a esta fuente de eventos no está establecido, la fuente de eventos debe regresar inmediatamente sin hacer nada. Por ejemplo, la fuente de eventos de archivo comprueba el bit TCL_FILE_EVENTS.

El trabajo de SetupProc es asegurarse de que la aplicación se active cuando ocurran eventos del tipo deseado. Esto se hace típicamente de una manera dependiente de la plataforma. Por ejemplo, bajo Unix, una fuente de eventos podría llamar a Tcl_CreateFileHandler; bajo Windows, podría solicitar notificación con un evento de Windows. Para fuentes de eventos impulsadas por temporizadores, como eventos de temporizador o cualquier evento sondeado, la fuente de eventos puede llamar a Tcl_SetMaxBlockTime para forzar a la aplicación a activarse después de un tiempo especificado, incluso si no han ocurrido eventos. Si ninguna fuente de eventos llama a Tcl_SetMaxBlockTime, entonces Tcl_WaitForEvent esperará tanto como sea necesario para que ocurra un evento; de lo contrario, solo esperará tanto como el intervalo más corto pasado a Tcl_SetMaxBlockTime por una de las fuentes de eventos. Si una fuente de eventos sabe que ya tiene eventos listos para informar, puede solicitar un tiempo de bloqueo máximo de cero. Por ejemplo, el procedimiento de configuración para la fuente de eventos X comprueba si ya hay eventos en cola. Si los hay, llama a Tcl_SetMaxBlockTime con un tiempo de bloqueo de 0 para que Tcl_WaitForEvent no se bloquee si no hay nuevos datos en la conexión X. El argumento timePtr a Tcl_WaitForEvent apunta a una estructura que describe un intervalo de tiempo en segundos y microsegundos:

typedef struct Tcl_Time {
    long sec;
    long usec;
} Tcl_Time;

El campo usec debe ser menor que 1000000.

La información proporcionada a Tcl_SetMaxBlockTime solo se usa para la próxima llamada a Tcl_WaitForEvent; se descarta después de que Tcl_WaitForEvent regresa. La próxima vez que se realice una espera de eventos, se llamará nuevamente a los procedimientos de configuración de cada una de las fuentes de eventos, y podrán especificar nueva información para esa espera de eventos.

Si la aplicación utiliza un bucle de eventos externo en lugar de Tcl_DoOneEvent, las fuentes de eventos pueden necesitar llamar a Tcl_SetMaxBlockTime en otros momentos. Por ejemplo, si se registra un nuevo manejador de eventos que necesita sondear eventos, la fuente de eventos puede llamar a Tcl_SetMaxBlockTime para establecer el tiempo de bloqueo a cero para forzar al bucle de eventos externo a llamar a Tcl. En este caso, Tcl_SetMaxBlockTime invoca Tcl_SetTimer con el intervalo más corto visto desde la última llamada a Tcl_DoOneEvent o Tcl_ServiceAll.

Además del procedimiento genérico Tcl_SetMaxBlockTime, pueden estar disponibles otros procedimientos específicos de la plataforma para setupProc, si hay información adicional necesaria para Tcl_WaitForEvent en esa plataforma. Por ejemplo, en sistemas Unix se puede usar la interfaz Tcl_CreateFileHandler para esperar eventos de archivo.

El segundo procedimiento proporcionado por cada fuente de eventos es su procedimiento de comprobación, indicado por el argumento checkProc a Tcl_CreateEventSource. CheckProc debe coincidir con el siguiente prototipo:

typedef void Tcl_EventCheckProc(
        ClientData clientData,
        int flags);

Los argumentos de este procedimiento son los mismos que los de setupProc. CheckProc es invocado por Tcl_DoOneEvent después de haber esperado eventos. Presumiblemente, al menos una fuente de eventos está ahora preparada para poner en cola un evento. Tcl_DoOneEvent llama a cada una de las fuentes de eventos por turno, para que todas tengan la oportunidad de poner en cola cualquier evento que esté listo. El procedimiento de comprobación hace dos cosas. Primero, debe ver si algún evento se ha activado. Diferentes fuentes de eventos hacen esto de diferentes maneras.

Si el procedimiento de comprobación de una fuente de eventos detecta un evento interesante, debe añadir el evento a la cola de eventos de Tcl. Para hacer esto, la fuente de eventos llama a Tcl_QueueEvent. El argumento evPtr es un puntero a una estructura asignada dinámicamente que contiene el evento (ver más abajo para más información sobre problemas de gestión de memoria). Cada fuente de eventos puede definir su propia estructura de eventos con la información que sea relevante para esa fuente de eventos. Sin embargo, el primer elemento de la estructura debe ser una estructura de tipo Tcl_Event, y la dirección de esta estructura se utiliza al comunicarse entre la fuente de eventos y el resto del notificador. Un Tcl_Event tiene la siguiente definición:

typedef struct {
    Tcl_EventProc *proc;
    struct Tcl_Event *nextPtr;
} Tcl_Event;

La fuente de eventos debe rellenar el campo proc del evento antes de llamar a Tcl_QueueEvent. El campo nextPtr se utiliza para enlazar los eventos en la cola y no debe ser modificado por la fuente de eventos.

Un evento puede añadirse a la cola en una de tres posiciones, dependiendo del argumento position a Tcl_QueueEvent:

TCL_QUEUE_TAIL
Añade el evento al final de la cola, de modo que todos los demás eventos pendientes se atiendan primero. Este es casi siempre el lugar correcto para los eventos nuevos.
TCL_QUEUE_HEAD
Añade el evento al principio de la cola, de modo que se atienda antes que todos los demás eventos en cola.
TCL_QUEUE_MARK
Añade el evento al principio de la cola, a menos que haya otros eventos al principio cuya posición sea TCL_QUEUE_MARK; en ese caso, añade el nuevo evento justo después de todos los demás eventos TCL_QUEUE_MARK. Este valor de position se utiliza para insertar una secuencia ordenada de eventos al principio de la cola, como una serie de eventos Enter y Leave sintetizados durante una operación de agarre o liberación en Tk.

Cuando llega el momento de manejar un evento de la cola (pasos 1 y 4 anteriores), Tcl_ServiceEvent invocará el proc especificado en la primera estructura Tcl_Event en cola. Proc debe coincidir con el siguiente prototipo:

typedef int Tcl_EventProc(
        Tcl_Event *evPtr,
        int flags);

El primer argumento a proc es un puntero al evento, que será el mismo que el primer argumento a la llamada Tcl_QueueEvent que añadió el evento a la cola. El segundo argumento a proc es el argumento flags para la llamada actual a Tcl_ServiceEvent; esto es usado por la fuente de eventos para regresar inmediatamente si sus eventos no son relevantes.

Corresponde a proc manejar el evento, típicamente invocando uno o más comandos Tcl o callbacks a nivel C. Una vez que la fuente de eventos ha terminado de manejar el evento, devuelve 1 para indicar que el evento puede ser eliminado de la cola. Si por alguna razón la fuente de eventos decide que el evento no puede ser manejado en este momento, puede devolver 0 para indicar que el evento debe ser pospuesto para su procesamiento posterior; en este caso, Tcl_ServiceEvent continuará con el siguiente evento en la cola e intentará atenderlo. Hay varias razones por las que una fuente de eventos podría posponer un evento. Una posibilidad es que los eventos de este tipo sean excluidos por el argumento flags. Por ejemplo, la fuente de eventos de archivo siempre devolverá 0 si el bit TCL_FILE_EVENTS no está establecido en flags. Otro ejemplo de posposición de eventos ocurre en Tk si se ha invocado Tk_RestrictEvents para posponer ciertos tipos de eventos de ventana.

Cuando proc devuelve 1, Tcl_ServiceEvent eliminará el evento de la cola de eventos y liberará su almacenamiento. Tenga en cuenta que el almacenamiento de un evento debe ser asignado por la fuente de eventos (usando Tcl_Alloc o la macro Tcl ckalloc) antes de llamar a Tcl_QueueEvent, pero será liberado por Tcl_ServiceEvent, no por la fuente de eventos.

Las aplicaciones multihilo funcionan de manera similar, excepto que hay una cola de eventos separada para cada hilo que contiene un intérprete Tcl. Llamar a Tcl_QueueEvent en una aplicación multihilo añade un evento a la cola del hilo actual. Para añadir un evento a la cola de otro hilo, use Tcl_ThreadQueueEvent. Tcl_ThreadQueueEvent acepta como argumento un argumento Tcl_ThreadId, que identifica de forma única un hilo en una aplicación Tcl. Para obtener el Tcl_ThreadId del hilo actual, use el procedimiento Tcl_GetCurrentThread. (Un hilo necesitaría entonces pasar este identificador a otros hilos para que estos puedan añadir eventos a su cola). Después de añadir un evento a la cola de otro hilo, normalmente necesita llamar a Tcl_ThreadAlert para "despertar" al notificador de ese hilo para alertarlo sobre el nuevo evento.

Tcl_DeleteEvents puede usarse para eliminar explícitamente uno o más eventos de la cola de eventos. Tcl_DeleteEvents llama a proc para cada evento en la cola, eliminando aquellos para los que el procedimiento devuelve 1. Los eventos para los que el procedimiento devuelve 0 permanecen en la cola. Proc debe coincidir con el siguiente prototipo:

typedef int Tcl_EventDeleteProc(
        Tcl_Event *evPtr,
        ClientData clientData);

El argumento clientData será el mismo que el argumento clientData a Tcl_DeleteEven

ts; se usa típicamente para apuntar a información privada gestionada por la fuente de eventos. El evPtr apuntará al siguiente evento en la cola.

Tcl_DeleteEventSource elimina una fuente de eventos. Los argumentos setupProc, checkProc y clientData deben coincidir exactamente con los proporcionados a Tcl_CreateEventSource para que la fuente de eventos sea eliminada. Si no existe dicha fuente, Tcl_DeleteEventSource no tendrá ningún efecto.

CREACIÓN DE UN NUEVO NOTIFICADOR

El notificador consta de todos los procedimientos descritos en esta entrada del manual, además de Tcl_DoOneEvent y Tcl_Sleep, que están disponibles en todas las plataformas, y Tcl_CreateFileHandler y Tcl_DeleteFileHandler, que son específicos de Unix. La mayoría de estos procedimientos son genéricos, en el sentido de que son los mismos para todos los notificadores. Sin embargo, ninguno de los procedimientos depende del notificador: Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_SetTimer, Tcl_Sleep, Tcl_WaitForEvent, Tcl_CreateFileHandler, Tcl_DeleteFileHandler y Tcl_ServiceModeHook. Para dar soporte a una nueva plataforma o para integrar Tcl con un bucle de eventos específico de la aplicación, debe escribir nuevas versiones de estos procedimientos.

Tcl_InitNotifier inicializa el estado del notificador y devuelve un manejador para el estado del notificador. Tcl llama a este procedimiento al inicializar un intérprete Tcl. De manera similar, Tcl_FinalizeNotifier cierra el notificador y es llamado por Tcl_Finalize al cerrar un intérprete Tcl.

Tcl_WaitForEvent es el procedimiento de nivel más bajo en el notificador; es responsable de esperar a que ocurra un evento “interesante” o a que transcurra un tiempo determinado. Antes de invocar Tcl_WaitForEvent, se habrá invocado el procedimiento de configuración de cada una de las fuentes de eventos. El argumento timePtr a Tcl_WaitForEvent indica el tiempo máximo de espera para un evento, basado en las llamadas a Tcl_SetMaxBlockTime realizadas por los procedimientos de configuración y en otra información (como el bit TCL_DONT_WAIT en flags).

Idealmente, Tcl_WaitForEvent solo debería esperar a que ocurra un evento; no debería procesar el evento de ninguna manera. Más tarde, las fuentes de eventos procesarán los eventos brutos y crearán Tcl_Events en la cola de eventos en sus procedimientos checkProc. Sin embargo, en algunas plataformas (como Windows) esto no es posible; los eventos pueden procesarse en Tcl_WaitForEvent, incluyendo la puesta en cola de Tcl_Events y más (por ejemplo, pueden invocarse devoluciones de llamada para widgets nativos). El valor de retorno de Tcl_WaitForEvent debe ser 0, 1 o -1. En plataformas como Windows, donde los eventos se procesan en Tcl_WaitForEvent, un valor de retorno de 1 significa que puede haber más eventos pendientes que aún no se han procesado. Esto es una señal para el llamador de que debe volver a llamar a Tcl_WaitForEvent si desea que se procesen todos los eventos pendientes. Un valor de retorno de 0 significa que volver a llamar a Tcl_WaitForEvent no tendrá ningún efecto: ya sea que sea una plataforma donde Tcl_WaitForEvent solo espera sin hacer ningún procesamiento de eventos, o Tcl_WaitForEvent sabe con certeza que no hay eventos adicionales que procesar (por ejemplo, devolvió porque el tiempo expiró). Finalmente, un valor de retorno de -1 significa que el bucle de eventos ya no es operativo y la aplicación probablemente debería deshacer y terminar. En Windows, esto ocurre cuando se recibe un mensaje WM_QUIT; en Unix, ocurre cuando Tcl_WaitForEvent habría esperado para siempre porque no había fuentes de eventos activas y el tiempo de espera era infinito.

Tcl_AlertNotifier se utiliza en aplicaciones multihilo para permitir que cualquier hilo “despierte” al notificador para alertarlo sobre nuevos eventos en su cola. Tcl_AlertNotifier requiere como argumento el manejador del notificador devuelto por Tcl_InitNotifier.

Si el notificador se va a utilizar con un bucle de eventos externo, entonces también debe admitir la interfaz Tcl_SetTimer. Tcl_SetTimer es invocado por Tcl_SetMaxBlockTime siempre que se ha reducido el tiempo máximo de bloqueo. Tcl_SetTimer debe organizar que el bucle de eventos externo invoque Tcl_ServiceAll después del intervalo especificado, incluso si no han ocurrido eventos. Esta interfaz es necesaria porque Tcl_WaitForEvent no se invoca cuando hay un bucle de eventos externo. Si el notificador solo se utilizará desde Tcl_DoOneEvent, entonces Tcl_SetTimer no necesita hacer nada.

Tcl_ServiceModeHook es llamado por la parte independiente de la plataforma del notificador cuando el código cliente realiza una llamada a Tcl_SetServiceMode. Este hook se proporciona para admitir sistemas operativos que requieren un manejo especial de eventos cuando la aplicación está en un bucle modal (el notificador de Windows, por ejemplo, utiliza este hook para crear una ventana de comunicación).

En sistemas Unix, la fuente de eventos de archivo también necesita soporte del notificador. La fuente de eventos de archivo consta de los procedimientos Tcl_CreateFileHandler y Tcl_DeleteFileHandler, que se describen en la página del manual de Tcl_CreateFileHandler.

Las interfaces Tcl_Sleep y Tcl_DoOneEvent se describen en sus respectivas páginas del manual.

La forma más fácil de crear un nuevo notificador es observar el código de un notificador existente, como los archivos unix/tclUnixNotfy.c o win/tclWinNotify.c en la distribución fuente de Tcl.

REEMPLAZO DEL NOTIFICADOR

Un notificador que se ha escrito de acuerdo con las convenciones anteriores también puede instalarse en un proceso en ejecución en lugar del notificador estándar. Este mecanismo se utiliza para que un solo ejecutable pueda ser utilizado (con el notificador estándar) como un programa autónomo y reutilizado (con un notificador de reemplazo en una extensión cargable) como una extensión para otro programa, como un plugin de navegador web.

Para hacer esto, la extensión realiza una llamada a Tcl_SetNotifier pasando un puntero a una estructura de datos Tcl_NotifierProcs. La estructura tiene la siguiente disposición:

typedef struct Tcl_NotifierProcs {
    Tcl_SetTimerProc *setTimerProc;
    Tcl_WaitForEventProc *waitForEventProc;
    Tcl_CreateFileHandlerProc *createFileHandlerProc;
    Tcl_DeleteFileHandlerProc *deleteFileHandlerProc;
    Tcl_InitNotifierProc *initNotifierProc;
    Tcl_FinalizeNotifierProc *finalizeNotifierProc;
    Tcl_AlertNotifierProc *alertNotifierProc;
    Tcl_ServiceModeHookProc *serviceModeHookProc;
} Tcl_NotifierProcs;

Después de la llamada a Tcl_SetNotifier, los punteros proporcionados en la estructura Tcl_NotifierProcs reemplazan cualquier notificador que se hubiera instalado en el proceso.

Es extraordinariamente imprudente reemplazar un notificador en ejecución. Normalmente, Tcl_SetNotifier debe llamarse en el momento de la inicialización del proceso antes de la primera llamada a Tcl_InitNotifier.

BUCLES DE EVENTOS EXTERNOS

Las interfaces del notificador están diseñadas para que Tcl pueda incrustarse en aplicaciones que tienen sus propios bucles de eventos privados. En este caso, la aplicación no llama a Tcl_DoOneEvent, excepto en el caso de bucles de eventos recursivos como las llamadas a los comandos Tcl update o vwait. La mayor parte del tiempo se invierte en el bucle de eventos externo de la aplicación. En este caso, el notificador debe asegurarse de que el bucle de eventos externo llame de vuelta a Tcl cuando ocurra algo en las diversas fuentes de eventos de Tcl. Estas devoluciones de llamada deben organizar que se coloquen eventos Tcl apropiados en la cola de eventos Tcl.

Debido a que el bucle de eventos externo no llama a Tcl_DoOneEvent de forma regular, depende del notificador organizar la llamada a Tcl_ServiceEvent siempre que haya eventos pendientes en la cola de eventos Tcl. La forma más fácil de hacerlo es invocar Tcl_ServiceAll al final de cada devolución de llamada del bucle de eventos externo. Esto asegurará que todas las fuentes de eventos se interroguen, que se atiendan todos los eventos en cola y que se procesen todos los manejadores inactivos pendientes antes de devolver el control a la aplicación. Además, las fuentes de eventos que necesiten consultar eventos pueden llamar a Tcl_SetMaxBlockTime para forzar que el bucle de eventos externo llame a Tcl incluso si no hay eventos disponibles en la cola de eventos del sistema.

Como efecto secundario del procesamiento de eventos detectados en el bucle de eventos externo principal, Tcl puede invocar Tcl_DoOneEvent para iniciar un bucle de eventos recursivo en comandos como vwait. Tcl_DoOneEvent invocará el bucle de eventos externo, lo que provocará devoluciones de llamada como se describe en el párrafo anterior, lo que provocará llamadas a Tcl_ServiceAll. Sin embargo, en estos casos, es indeseable procesar eventos en Tcl_ServiceAll. El procesamiento de eventos allí es innecesario porque el control volverá inmediatamente al bucle de eventos externo y, por lo tanto, a Tcl_DoOneEvent, que puede procesar los eventos por sí mismo. Además, se supone que Tcl_DoOneEvent solo procesa un único evento, mientras que Tcl_ServiceAll normalmente procesa todos los eventos pendientes. Para manejar esta situación, Tcl_DoOneEvent establece una bandera para Tcl_ServiceAll que hace que devuelva sin procesar ningún evento. Esta bandera se llama modo de servicio; Tcl_DoOneEvent la restaura a su valor anterior antes de devolver.

En algunos casos, sin embargo, puede ser necesario que Tcl_ServiceAll procese eventos incluso cuando ha sido invocado desde Tcl_DoOneEvent. Esto ocurre cuando hay otro bucle de eventos recursivo invocado a través de un manejador de eventos llamado por Tcl_DoOneEvent (como uno que forma parte de un widget nativo). En este caso, Tcl_DoOneEvent puede no tener la oportunidad de procesar eventos, por lo que Tcl_ServiceAll debe procesarlos todos. Cualquier bucle de eventos recursivo que llame a un bucle de eventos externo en lugar de Tcl_DoOneEvent debe restablecer el modo de servicio para que todos los eventos se procesen en Tcl_ServiceAll. Esto se hace invocando el procedimiento Tcl_SetServiceMode. Si a Tcl_SetServiceMode se le pasa TCL_SERVICE_NONE, entonces las llamadas a Tcl_ServiceAll devolverán inmediatamente sin procesar ningún evento. Si a Tcl_SetServiceMode se le pasa TCL_SERVICE_ALL, entonces las llamadas a Tcl_ServiceAll se comportarán normalmente. Tcl_SetServiceMode devuelve el valor anterior del modo de servicio, que debe restaurarse cuando salga el bucle recursivo. Tcl_GetServiceMode devuelve el valor actual del modo de servicio.

INTRODUCTION

Tcl provides an event-driven programming model. The core of this model is the Tcl event loop, which waits for events to occur and then dispatches them to the appropriate handlers. The event loop is implemented by a set of procedures that manage event sources, queues, and handlers.

The event loop is responsible for:

  • Waiting for events to occur.
  • Queuing events when they occur.
  • Dispatching events to their handlers.

The event loop can be extended with new event sources and handlers. This is done by implementing the Tcl_NotifierProcs structure and registering it with the Tcl interpreter.

NOTIFIER BASICS

The Tcl_NotifierProcs structure defines the interface between the Tcl event loop and the underlying event mechanism. It contains pointers to procedures that handle the following tasks:

  • Initializing the event loop.
  • Setting and getting the notifier.
  • Alerting the notifier of new events.
  • Managing service modes.
  • Queuing and freeing events.
  • Setting and deleting timers.
  • Creating and deleting file handlers.
  • Creating and deleting thread event sources.
  • Creating and deleting idle handlers.

The Tcl_InitNotifier function initializes the Tcl event loop with the default notifier. The Tcl_GetNotifier and Tcl_SetNotifier functions allow you to get and set the current notifier, respectively. The Tcl_AlertNotifier function alerts the notifier of new events.

CREATING A NEW EVENT SOURCE

You can create new event sources by implementing the necessary procedures and registering them with the Tcl interpreter. The following procedures are used to manage event sources:

  • Tcl_QueueEvent: Queues an event for processing.
  • Tcl_MakeEventStruct: Allocates memory for an event structure.
  • Tcl_FreeEventStruct: Frees memory allocated for an event structure.
  • Tcl_SetTimer: Sets a timer to trigger an event after a specified delay.
  • Tcl_DeleteTimer: Deletes a timer.
  • Tcl_TimerIsSet: Checks if a timer is set.
  • Tcl_CreateFileHandler: Creates a file handler to monitor a file descriptor for read, write, or exception events.
  • Tcl_DeleteFileHandler: Deletes a file handler.
  • Tcl_FileHandlerIsSet: Checks if a file handler is set for a given file descriptor.
  • Tcl_CreateThreadEventSource: Creates a thread event source to monitor for events from other threads.
  • Tcl_DeleteThreadEventSource: Deletes a thread event source.
  • Tcl_ThreadEventSourceIsSet: Checks if a thread event source is set for a given thread ID.
  • Tcl_CreateIdleHandler: Creates an idle handler that is called when the event loop is idle.
  • Tcl_DeleteIdleHandler: Deletes an idle handler.
  • Tcl_IdleHandlerIsSet: Checks if an idle handler is set.

CREATING A NEW NOTIFIER

To create a new notifier, you need to implement the Tcl_NotifierProcs structure with your custom event handling logic. Then, you can register your notifier with the Tcl interpreter using Tcl_SetNotifier.

REPLACING THE NOTIFIER

You can replace the default Tcl notifier with your own custom notifier by calling Tcl_SetNotifier. This allows you to integrate Tcl's event loop with other event-driven systems or to implement custom event handling behavior.

EXTERNAL EVENT_LOOPS

Tcl's event loop can be integrated with external event loops. This is useful when you need to combine Tcl's event handling with other event-driven frameworks, such as GUI toolkits or network servers. The Tcl_SetNotifier function plays a crucial role in this integration by allowing you to replace Tcl's default event loop with your own.
