DESCRIPTION

There are several reasons for calling the Tcl_FS API functions (e.g. Tcl_FSAccess and Tcl_FSStat) rather than calling system level functions like access and stat directly. First, they will work cross-platform, so an extension which calls them should work unmodified on Unix and Windows. Second, the Windows implementation of some of these functions fixes some bugs in the system level calls. Third, these function calls deal with any “Utf to platform-native” path conversions which may be required (and may cache the results of such conversions for greater efficiency on subsequent calls). Fourth, and perhaps most importantly, all of these functions are “virtual filesystem aware”. Any virtual filesystem (VFS for short) which has been registered (through Tcl_FSRegister) may reroute file access to alternative media or access methods. This means that all of these functions (and therefore the corresponding file, glob, pwd, cd, open, etc. Tcl commands) may be operate on “files” which are not native files in the native filesystem. This also means that any Tcl extension which accesses the filesystem (FS for short) through this API is automatically “virtual filesystem aware”. Of course, if an extension accesses the native filesystem directly (through platform-specific APIs, for example), then Tcl cannot intercept such calls.

If appropriate VFSes have been registered, the “files” may, to give two examples, be remote (e.g. situated on a remote ftp server) or archived (e.g. lying inside a .zip archive). Such registered filesystems provide a lookup table of functions to implement all or some of the functionality listed here. Finally, the Tcl_FSStat and Tcl_FSLstat calls abstract away from what the “struct stat” buffer is actually declared to be, allowing the same code to be used both on systems with and systems without support for files larger than 2GB in size.

The Tcl_FS API is Tcl_Obj-ified and may cache internal representations and other path-related strings (e.g. the current working directory). One side-effect of this is that one must not pass in values with a reference count of zero to any of these functions. If such calls were handled, they might result in memory leaks (under some circumstances, the filesystem code may wish to retain a reference to the passed in value, and so one must not assume that after any of these calls return, the value still has a reference count of zero - it may have been incremented) or in a direct segmentation fault (or other memory access error) due to the value being freed part way through the complex value manipulation required to ensure that the path is fully normalized and absolute for filesystem determination. The practical lesson to learn from this is that

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

is wrong, and may cause memory errors. The path must have its reference count incremented before passing it in, or decrementing it. For this reason, values with a reference count of zero are considered not to be valid filesystem paths and calling any Tcl_FS API function with such a value will result in no action being taken.

FS API FUNCTIONS

Tcl_FSCopyFile attempts to copy the file given by srcPathPtr to the path name given by destPathPtr. If the two paths given lie in the same filesystem (according to Tcl_FSGetFileSystemForPath) then that filesystem's “copy file” function is called (if it is non-NULL). Otherwise the function returns -1 and sets the errno global C variable to the “EXDEV” POSIX error code (which signifies a “cross-domain link”).

Tcl_FSCopyDirectory attempts to copy the directory given by srcPathPtr to the path name given by destPathPtr. If the two paths given lie in the same filesystem (according to Tcl_FSGetFileSystemForPath) then that filesystem's “copy file” function is called (if it is non-NULL). Otherwise the function returns -1 and sets the errno global C variable to the “EXDEV” POSIX error code (which signifies a “cross-domain link”).

Tcl_FSCreateDirectory attempts to create the directory given by pathPtr by calling the owning filesystem's “create directory” function.

Tcl_FSDeleteFile attempts to delete the file given by pathPtr by calling the owning filesystem's “delete file” function.

Tcl_FSRemoveDirectory attempts to remove the directory given by pathPtr by calling the owning filesystem's “remove directory” function.

Tcl_FSRenameFile attempts to rename the file or directory given by srcPathPtr to the path name given by destPathPtr. If the two paths given lie in the same filesystem (according to Tcl_FSGetFileSystemForPath) then that filesystem's “rename file” function is called (if it is non-NULL). Otherwise the function returns -1 and sets the errno global C variable to the “EXDEV” POSIX error code (which signifies a “cross-domain link”).

Tcl_FSListVolumes calls each filesystem which has a non-NULL “list volumes” function and asks them to return their list of root volumes. It accumulates the return values in a list which is returned to the caller (with a reference count of 0).

Tcl_FSEvalFileEx reads the file given by pathPtr using the encoding identified by encodingName and evaluates its contents as a Tcl script. It returns the same information as Tcl_EvalObjEx. If encodingName is NULL, the system encoding is used for reading the file contents. If the file could not be read then a Tcl error is returned to describe why the file could not be read. The eofchar for files is “\x1A” (^Z) for all platforms. If you require a “^Z” in code for string comparison, you can use “\x1A”, which will be safely substituted by the Tcl interpreter into “^Z”. Tcl_FSEvalFile is a simpler version of Tcl_FSEvalFileEx that always uses the system encoding when reading the file.

Tcl_FSLoadFile dynamically loads a binary code file into memory and returns the addresses of two procedures within that file, if they are defined. The appropriate function for the filesystem to which pathPtr belongs will be called. If that filesystem does not implement this function (most virtual filesystems will not, because of OS limitations in dynamically loading binary code), Tcl will attempt to copy the file to a temporary directory and load that temporary file. Tcl_FSUnloadFile reverses the operation, asking for the library indicated by the loadHandle to be removed from the process. Note that, unlike with the unload command, this does not give the library any opportunity to clean up.

Both the above functions return a standard Tcl completion code. If an error occurs, an error message is left in the interp's result.

The token provided via the variable indicated by loadHandlePtr may be used with Tcl_FindSymbol.

Tcl_FSMatchInDirectory is used by the globbing code to search a directory for all files which match a given pattern. The appropriate function for the filesystem to which pathPtr belongs will be called.

The return value is a standard Tcl result indicating whether an error occurred in globbing. Error messages are placed in interp (unless interp is NULL, which is allowed), but good results are placed in the resultPtr given.

Note that the glob code implements recursive patterns internally, so this function will only ever be passed simple patterns, which can be matched using the logic of string match. To handle recursion, Tcl will call this function frequently asking only for directories to be returned. A special case of being called with a NULL pattern indicates that the path needs to be checked only for the correct type.

Tcl_FSLink replaces the library version of readlink, and extends it to support the creation of links. The appropriate function for the filesystem to which linkNamePtr belongs will be called.

If the toPtr is NULL, a “read link” action is performed. The result is a Tcl_Obj specifying the contents of the symbolic link given by linkNamePtr, or NULL if the link could not be read. The result is owned by the caller, which should call Tcl_DecrRefCount when the result is no longer needed. If the toPtr is not NULL, Tcl should create a link of one of the types passed in in the linkAction flag. This flag is an OR'ed combination of TCL_CREATE_SYMBOLIC_LINK and TCL_CREATE_HARD_LINK. Where a choice exists (i.e. more than one flag is passed in), the Tcl convention is to prefer symbolic links. When a link is successfully created, the return value should be toPtr (which is therefore already owned by the caller). If unsuccessful, NULL is returned.

Tcl_FSLstat fills the Tcl_StatBuf structure statPtr with information about the specified file. You do not need any access rights to the file to get this information but you need search rights to all directories named in the path leading to the file. The Tcl_StatBuf structure includes info regarding device, inode (always 0 on Windows), privilege mode, nlink (always 1 on Windows), user id (always 0 on Windows), group id (always 0 on Windows), rdev (same as device on Windows), size, last access ti

me, hora de última modificación y hora de último cambio de metadatos. Consulte la API DE RESULTADOS DE STAT PORTÁTIL para obtener una descripción de cómo escribir código portátil para asignar y acceder a la estructura Tcl_StatBuf.

Si *path* existe, Tcl_FSLstat devuelve 0 y la estructura stat se rellena con datos. De lo contrario, se devuelve -1 y no se proporciona información stat.

Tcl_FSUtime reemplaza la versión de biblioteca de utime.

Esto devuelve 0 en caso de éxito y -1 en caso de error (según la documentación de utime). Si tiene éxito, la función actualizará los valores de "atime" y "mtime" del archivo proporcionado.

Tcl_FSFileAttrsGet implementa el acceso de lectura para el subcomando file attributes que se puede conectar. Se llamará a la función apropiada para el sistema de archivos al que pertenece *pathPtr*.

Si el resultado es TCL_OK, entonces se colocó un valor en *objPtrRef*, que solo será válido temporalmente (a menos que se llame a Tcl_IncrRefCount).

Tcl_FSFileAttrsSet implementa el acceso de escritura para el subcomando file attributes que se puede conectar. Se llamará a la función apropiada para el sistema de archivos al que pertenece *pathPtr*.

Tcl_FSFileAttrStrings implementa parte del subcomando file attributes que se puede conectar. Se llamará a la función apropiada para el sistema de archivos al que pertenece *pathPtr*.

El procedimiento llamado puede devolver una matriz de cadenas o puede devolver NULL y colocar una lista de Tcl en *objPtrRef*. Tcl tomará esa lista e incrementará primero su recuento de referencias antes de usarla. Al completar ese uso, Tcl disminuirá su recuento de referencias. Por lo tanto, si Tcl debe desechar la lista cuando termine, debería tener un recuento de referencias de cero, y si Tcl no debe desechar la lista, el sistema de archivos debe asegurarse de conservar un recuento de referencias del valor.

Tcl_FSAccess comprueba si se permitiría al proceso leer, escribir o probar la existencia del archivo (u otro objeto del sistema de archivos) cuyo nombre es *pathname*. Si *pathname* es un enlace simbólico en Unix, se prueban los permisos del archivo al que se refiere este enlace simbólico.

En caso de éxito (todos los permisos solicitados concedidos), se devuelve cero. En caso de error (al menos un bit en el modo solicitó un permiso que se deniega, o ocurrió algún otro error), se devuelve -1.

Tcl_FSStat rellena la estructura *Tcl_StatBuf* *statPtr* con información sobre el archivo especificado. No necesita ningún derecho de acceso al archivo para obtener esta información, pero necesita derechos de búsqueda en todos los directorios que se nombran en la ruta que conduce al archivo. La estructura *Tcl_StatBuf* incluye información sobre el dispositivo, el inodo (siempre 0 en Windows), el modo de privilegio, nlink (siempre 1 en Windows), id de usuario (siempre 0 en Windows), id de grupo (siempre 0 en Windows), rdev (igual que el dispositivo en Windows), tamaño, hora del último acceso, hora de la última modificación y hora del último cambio de metadatos. Consulte la API DE RESULTADOS DE STAT PORTÁTIL para obtener una descripción de cómo escribir código portátil para asignar y acceder a la estructura *Tcl_StatBuf*.

Si *path* existe, Tcl_FSStat devuelve 0 y la estructura stat se rellena con datos. De lo contrario, se devuelve -1 y no se proporciona información stat.

Tcl_FSOpenFileChannel abre un archivo especificado por *pathPtr* y devuelve un identificador de canal que se puede utilizar para realizar operaciones de entrada y salida en el archivo. Esta API se basa en el procedimiento fopen de la biblioteca estándar de E/S de Unix. La sintaxis y el significado de todos los argumentos son similares a los proporcionados en el comando Tcl open al abrir un archivo. Si ocurre un error al abrir el canal, Tcl_FSOpenFileChannel devuelve NULL y registra un código de error POSIX que se puede recuperar con Tcl_GetErrno. Además, si *interp* no es NULL, Tcl_FSOpenFileChannel deja un mensaje de error en el resultado de *interp* después de cualquier error.

El canal recién creado no está registrado en el intérprete suministrado; para registrarlo, utilice Tcl_RegisterChannel. Si uno de los canales estándar, stdin, stdout o stderr se cerró previamente, el acto de crear el nuevo canal también lo asigna como un reemplazo para el canal estándar.

Tcl_FSGetCwd reemplaza la versión de biblioteca de getcwd.

Devuelve el directorio de trabajo actual de la biblioteca Tcl. Este puede ser diferente al directorio de trabajo de la plataforma nativa, lo que ocurre cuando el directorio de trabajo actual no está en el sistema de archivos nativo.

El resultado es un puntero a un Tcl_Obj que especifica el directorio actual, o NULL si no se pudo determinar el directorio actual. Si se devuelve NULL, se deja un mensaje de error en el resultado de *interp*.

El resultado ya tiene su recuento de referencias incrementado para el llamador. Cuando ya no sea necesario, se debe disminuir ese recuento de referencias. Esto es necesario por motivos de seguridad de hilos, para permitir que múltiples hilos accedan a esta y funciones relacionadas, al tiempo que se garantizan que los resultados sean siempre válidos.

Tcl_FSChdir reemplaza la versión de biblioteca de chdir. La ruta se normaliza y luego se pasa al sistema de archivos que la reclama. Si ese sistema de archivos no implementa esta función, Tcl recurrirá a una combinación de stat y access para comprobar si el directorio existe y tiene los permisos adecuados.

Para obtener resultados, consulte la documentación de chdir. Si tiene éxito, conservamos un registro de la ruta exitosa en *cwdPathPtr* para llamadas posteriores a Tcl_FSGetCwd.

Tcl_FSPathSeparator devuelve el carácter separador que se utilizará para el elemento más específico de la ruta especificada por *pathPtr* (es decir, la última parte de la ruta).

El separador se devuelve como un Tcl_Obj que contiene una cadena de longitud 1. Si la ruta no es válida, se devuelve NULL.

Tcl_FSJoinPath toma el Tcl_Obj dado, que debe ser una lista válida (que puede tener un recuento de referencias de cero), y devuelve el valor de la ruta dado al considerar los primeros *elementos* como segmentos de ruta válidos (cada segmento de ruta puede ser una ruta completa, una ruta parcial o simplemente un solo directorio o nombre de archivo posible). Si algún segmento de ruta es en realidad una ruta absoluta, se descartan todos los segmentos de ruta anteriores. Si *elementos* es menor que 0, usamos la lista entera.

Es posible que el valor devuelto sea en realidad un elemento de la lista dada, por lo que el llamador debe tener cuidado de incrementar el recuento de referencias del resultado antes de liberar la lista.

El valor devuelto, típicamente con un recuento de referencias de cero (pero podría compartirse bajo algunas condiciones), contiene la ruta unida. El llamador debe agregar un recuento de referencias al valor antes de usarlo. En particular, el valor devuelto podría ser un elemento de la lista dada, por lo que liberar la lista podría liberar el valor prematuramente si no se ha tomado ningún recuento de referencias. Si el número de elementos es cero, el valor devuelto será un Tcl_Obj de cadena vacía.

Tcl_FSSplitPath toma el Tcl_Obj dado, que debería ser una ruta válida, y devuelve un valor de lista Tcl que contiene cada segmento de esa ruta como un elemento. Devuelve un valor de lista con un recuento de referencias de cero. Si el *lenPtr* proporcionado no es NULL, la variable a la que apunta se actualizará para contener el número de elementos en la lista devuelta.

Tcl_FSEqualPaths comprueba si las dos rutas dadas representan el mismo objeto del sistema de archivos. Devuelve 1 si las rutas son iguales y 0 si son diferentes. Si alguna ruta es NULL, siempre se devuelve 0.

Tcl_FSGetNormalizedPath intenta extraer del Tcl_Obj dado una representación de ruta normalizada única, cuyo valor de cadena se puede utilizar como identificador único del archivo.

Devuelve el valor de ruta normalizado, propiedad de Tcl, o NULL si la ruta no era válida o no se pudo convertir correctamente. La extracción de rutas absolutas y normalizadas es muy eficiente (porque el sistema de archivos opera internamente con estas representaciones), aunque el resultado cuando el sistema de archivos contiene numerosos enlaces simbólicos puede no ser la versión más amigable para el usuario de una ruta. El valor de retorno es propiedad de Tcl y tiene una vida útil equivalente a la de *pathPtr* proporcionado (a menos que sea una ruta relativa, en cuyo caso el valor de ruta normalizado puede liberarse en cualquier momento en que cambie la cwd): el llamador, por supuesto, puede incrementar el recuento de referencias si desea mantener una copia por más tiempo.

Tcl_FSJoinToPath toma el valor dado, que generalmente debería ser una ruta válida o NULL, y le une la matriz de segmentos de ruta proporcionados.

Devuelve un valor, típicamente con un recuento de referencias de cero (pero podría compartirse bajo algunas condiciones), que contiene la ruta unida. El llamador debe agregar un recuento de referencias al valor antes de usarlo. Si alguno de los valores pasados a esta función (*pathPtr* o elementos de *path*) tiene un recuento de referencias de cero, se liberarán cuando esta función devuelva.

Tcl_FSConvertToPathType intenta convertir el Tcl_Obj dado a un tipo de ruta Tcl válido, teniendo en cuenta que la cwd puede haber cambiado incluso si este valor supuestamente ya es del tipo correcto. El nombre del archivo puede comenzar con "~" (para indicar el directorio de inicio del usuario actual) o "~<usuario>" (para indicar el directorio de inicio de cualquier usuario).

Si la conversión tiene éxito (es decir, el valor es una ruta válida en uno de los sistemas de archivos actuales), se devuelve TCL_OK. De lo contrario, se devuelve TCL_ERROR y es posible que se deje un mensaje de error en el intérprete.

Tcl_FSGetInternalRep extrae la representación interna de un valor de ruta dado, en el sistema de archivos dado. Si el valor de ruta pertenece a un sistema de archivos diferente, devolvemos NULL. Si la representación interna es actualmente NULL, intentamos generarla llamando a la Tcl_FSCreateInternalRepProc del sistema de archivos.

Devuelve NULL o una representación de ruta interna válida. Esta representación interna se almacena en caché, de modo que las llamadas repetidas a esta función no requerirán conversiones adicionales.

Tcl_FSGetTranslatedPath intenta extraer la ruta traducida del Tcl_Obj dado.

Si la traducción tiene éxito (es decir, el valor es una ruta válida), se devuelve. De lo contrario, se devolverá NULL y es posible que se deje un mensaje de error en el intérprete. Una ruta "traducida" es aquella que no contiene secuencias "~" o "~usuario" (estas se han expandido a su representación actual en el sistema de archivos). El valor devuelto es propiedad del llamador, que debe almacenarlo o llamar a Tcl_DecrRefCount para garantizar que se libere la memoria. Esta función tiene poco uso práctico, y Tcl_FSGetNormalizedPath o Tcl_FSGetNativePath son funciones generalmente mejores para la mayoría de los propósitos.

Tcl_FSGetTranslatedStringPath hace lo mismo que Tcl_FSGetTranslatedPath, pero devuelve una cadena de caracteres o NULL. La cadena devuelta se asigna dinámicamente y es propiedad del

por el llamador, el cual debe almacenarlo o llamar a ckfree para asegurarse de que se libera. Nuevamente, Tcl_FSGetNormalizedPath o Tcl_FSGetNativePath son generalmente mejores funciones para usar en la mayoría de los propósitos.

Tcl_FSNewNativePath realiza algo así como lo inverso de las conversiones habituales obj->path->nativerep. Si algún código recupera una ruta en formato nativo (desde, por ejemplo, readlink o un diálogo nativo), y esa ruta se va a utilizar a nivel de Tcl, entonces llamar a esta función es una forma eficiente de crear el tipo de valor de ruta apropiado.

El valor resultante es un valor de “ruta” puro, que solo recibirá una representación de cadena UTF-8 si eso es requerido por algún código Tcl.

Tcl_FSGetNativePath es para uso de los sistemas de archivos nativos Win/Unix, para que puedan recuperar fácilmente la representación nativa (char* o TCHAR*) de una ruta. Esta función es un envoltorio de conveniencia alrededor de Tcl_FSGetInternalRep. Puede ser deseable en el futuro tener representaciones nativas no basadas en cadenas (por ejemplo, en macOS, una representación que use un fileSpec de la estructura FSRef probablemente sería más eficiente). En Windows, una representación completa Unicode permitiría rutas de longitud ilimitada. Actualmente, la representación es simplemente una cadena de caracteres que puede contener la ruta relativa o una ruta nativa completa y absoluta normalizada en la codificación nativa (condiciones complejas dictan cuál de estas se proporcionará, por lo que ninguna puede ser garantizada, a menos que se sepa que la ruta es absoluta). Si necesita una ruta nativa que deba ser absoluta, entonces debe solicitar la versión nativa de una ruta normalizada. Si por alguna razón se necesita una versión no absoluta y no normalizada de la ruta, esa debe construirse por separado (por ejemplo, usando Tcl_FSGetTranslatedPath).

La representación nativa se almacena en caché para que las llamadas repetidas a esta función no requieran conversiones adicionales. El valor de retorno es propiedad de Tcl y tiene una vida útil equivalente a la del pathPtr pasado (a menos que sea una ruta relativa, en cuyo caso la representación nativa puede liberarse en cualquier momento que cambie el cwd).

Tcl_FSFileSystemInfo devuelve una lista de dos elementos. El primer elemento es el nombre del sistema de archivos (por ejemplo, “native”, “vfs”, “zip”, o “prowrap”, quizás), y el segundo es el tipo particular de la ruta dada dentro de ese sistema de archivos (que depende del sistema de archivos). El segundo elemento puede estar vacío si el sistema de archivos no proporciona una categorización adicional de archivos.

Se devuelve una lista válida, a menos que el valor de la ruta no sea reconocido, en cuyo caso se devolverá NULL.

Tcl_FSGetFileSystemForPath devuelve un puntero al Tcl_Filesystem que acepta esta ruta como válida.

Si ningún sistema de archivos acepta la ruta, se devuelve NULL.

Tcl_FSGetPathType determina si la ruta dada es relativa al directorio actual, relativa al volumen actual o absoluta.

Devuelve uno de TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE o TCL_PATH_VOLUME_RELATIVE

LA API DEL SISTEMA DE ARCHIVOS VIRTUAL

Un sistema de archivos proporciona una estructura Tcl_Filesystem que contiene punteros a funciones que implementan las diversas operaciones en un sistema de archivos; estas operaciones se invocan según sea necesario por la capa genérica, lo que generalmente ocurre a través de las funciones enumeradas anteriormente.

Las estructuras Tcl_Filesystem se manipulan utilizando los siguientes métodos.

Tcl_FSRegister toma un puntero a una estructura de sistema de archivos y un dato opcional para asociar con ese sistema de archivos. Al llamar a esta función, Tcl adjuntará el sistema de archivos a la lista de sistemas de archivos conocidos, y se volverá completamente funcional de inmediato. Tcl no verifica si el mismo sistema de archivos está registrado múltiples veces (y en general, eso no es algo bueno de hacer). Se devolverá TCL_OK.

Tcl_FSUnregister elimina la estructura del sistema de archivos dada de la lista de sistemas de archivos conocidos, si se conoce, y devuelve TCL_OK. Si el sistema de archivos no está registrado actualmente, se devuelve TCL_ERROR.

Tcl_FSData devolverá el clientData asociado con el sistema de archivos dado, si ese sistema de archivos está registrado. De lo contrario, devolverá NULL.

Tcl_FSMountsChanged se utiliza para informar al núcleo de Tcl que el conjunto de puntos de montaje para el sistema de archivos dado (ya registrado) ha cambiado, y por lo tanto, las representaciones de archivos en caché pueden ya no ser correctas.

Excepto por los tres primeros campos de esta estructura que contienen elementos de datos simples, todas las entradas contienen direcciones de funciones llamadas por la capa genérica del sistema de archivos para realizar el rango completo de acciones relacionadas con el sistema de archivos.

Las muchas funciones en esta estructura se dividen en tres categorías: funciones de infraestructura (casi todas las cuales deben ser implementadas), funciones operativas (que deben ser implementadas si se proporciona un sistema de archivos completo), y funciones de eficiencia (que solo necesitan ser implementadas si se pueden hacer de manera eficiente, o si tienen efectos secundarios que son requeridos por el sistema de archivos; Tcl tiene emulaciones menos eficientes a las que puede recurrir). Es importante tener en cuenta que, en la versión actual de Tcl, la mayoría de estos recursos de respaldo solo se utilizan para manejar comandos iniciados en Tcl, no en C. Lo que esto significa es que, si se emite un comando file rename en Tcl, y el(los) sistema(s) de archivos relevantes no implementan su Tcl_FSRenameFileProc, el núcleo de Tcl recurrirá en su lugar a una combinación de otras funciones del sistema de archivos (utilizará Tcl_FSCopyFileProc seguido de Tcl_FSDeleteFileProc, y si Tcl_FSCopyFileProc no está implementado, hay un recurso adicional). Sin embargo, si se emite un comando Tcl_FSRenameFileProc a nivel de C, no ocurren tales recursos de respaldo. Esto es cierto excepto para las últimas cuatro entradas en la tabla del sistema de archivos (lstat, load, getcwd y chdir) para las cuales los recursos de respaldo ocurren realmente a nivel de C.

Cualquier función que tome nombres de ruta en forma de Tcl_Obj toma esos nombres en forma UTF-8. La API de infraestructura del sistema de archivos está diseñada para soportar la conversión eficiente y en caché de estas rutas UTF-8 a otras representaciones nativas.

INFRAESTRUCTURA DEL SISTEMA DE ARCHIVOS

Estos campos contienen información básica sobre la estructura del sistema de archivos y las direcciones de las funciones que se utilizan para asociar un sistema de archivos particular con una ruta de archivo, y para manejar el procesamiento interno de las representaciones de ruta, por ejemplo, copiar y liberar dichas representaciones.

NOMBRE DEL TIPO

El campo typeName contiene una cadena terminada en nulo que identifica el tipo de sistema de archivos implementado, por ejemplo, "nativo", "zip" o "vfs".

LONGITUD ESTRUCTURA

El campo structureLength se implementa generalmente como sizeof(Tcl_Filesystem), y está ahí para permitir una mayor compatibilidad binaria hacia atrás si el tamaño de la estructura cambia en un lanzamiento futuro de Tcl.

VERSIÓN

El campo version debe establecerse en TCL_FILESYSTEM_VERSION_1.

PROC_RUTA_EN_SISTEMA_ARCHIVOS

El campo pathInFilesystemProc contiene la dirección de una función que se llama para determinar si un valor de ruta dado pertenece o no a este sistema de archivos. Tcl solo llamará al resto de las funciones del sistema de archivos con una ruta para la cual esta función ha devuelto TCL_OK. Si la ruta no pertenece, se debe devolver -1 (el comportamiento de Tcl para cualquier otro valor de retorno no está definido). Si se devuelve TCL_OK, el parámetro de salida opcional clientDataPtr se puede utilizar para devolver una representación interna (específica del sistema de archivos) de la ruta, que se almacenará en caché dentro del valor de la ruta y podrá ser recuperada de manera eficiente por las otras funciones del sistema de archivos. Tcl almacenará simultáneamente en caché el hecho de que esta ruta pertenece a este sistema de archivos. Dichas cachés se invalidan cuando se agregan o eliminan estructuras del sistema de archivos de la lista interna de Tcl de sistemas de archivos conocidos.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

PROC_DUPLICAR_REPRESENTACION_INTERNA

Esta función crea una copia de la representación interna de una ruta y se llama cuando Tcl necesita duplicar un valor de ruta. Si es NULL, Tcl simplemente no copiará la representación interna, que luego puede necesitar ser regenerada más tarde.

typedef ClientData Tcl_FSDupInternalRepProc(
        ClientData clientData);

PROC_LIBERAR_REPRESENTACION_INTERNA

Libera la representación interna. Esto debe implementarse si las representaciones internas necesitan ser liberadas (es decir, si se asigna memoria cuando se genera una representación interna), pero de lo contrario puede ser NULL.

typedef void Tcl_FSFreeInternalRepProc(
        ClientData clientData);

PROC_INTERNA_A_NORMALIZADA

Función para convertir la representación interna a una ruta normalizada. Solo se requiere si el sistema de archivos crea valores de ruta puros sin representación de cadena/ruta. El valor de retorno es un valor de Tcl cuya representación de cadena es la ruta normalizada.

typedef Tcl_Obj *Tcl_FSInternalToNormalizedProc(
        ClientData clientData);

PROC_CREAR_REPRESENTACION_INTERNA

Función para tomar un valor de ruta, calcular una representación interna para él y almacenar esa representación nativa en el valor. Puede ser NULL si las rutas no tienen representación interna, o si Tcl_FSPathInFilesystemProc para este sistema de archivos siempre crea inmediatamente una representación interna para las rutas que acepta.

typedef ClientData Tcl_FSCreateInternalRepProc(
        Tcl_Obj *pathPtr);

PROC_NORMALIZAR_RUTA

Función para normalizar una ruta. Debe implementarse para todos los sistemas de archivos que puedan tener múltiples representaciones de cadena para el mismo valor de ruta. En Tcl, cada "ruta" debe tener una única representación de cadena "normalizada". Dependiendo del sistema de archivos, puede haber más de una representación de cadena no normalizada que se refiera a esa ruta (por ejemplo, una ruta relativa, una ruta con diferentes mayúsculas/minúsculas si el sistema de archivos no distingue entre mayúsculas y minúsculas, una ruta que contenga una referencia a un directorio de inicio como "~", una ruta que contenga enlaces simbólicos, etc.). Si el último componente de la ruta es un enlace simbólico, no debe convertirse en el valor al que apunta (pero su mayúscula u otros aspectos deben hacerse únicos). Todos los demás componentes de la ruta deben convertirse desde enlaces simbólicos. Esta única excepción es necesaria para estar de acuerdo con la semántica de Tcl con file delete, file rename, file copy operando en enlaces simbólicos. Esta función puede ser llamada con nextCheckpoint ya sea al principio de la ruta (es decir, cero), al final de la ruta, o en cualquier separador de archivo intermedio en la ruta. Nunca apuntará a ninguna otra posición arbitraria en la ruta. En el último de los tres casos válidos, la implementación puede suponer que la ruta hasta incluir el separador de archivo es conocida y normalizada.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

OPERACIONES DEL SISTEMA DE ARCHIVOS

Los campos en esta sección de la estructura contienen las direcciones de las funciones que se llaman para realizar las operaciones básicas del sistema de archivos. Un sistema de archivos que se espera que se use con el conjunto completo de comandos estándar de Tcl debe implementar todas estas. Si no se implementan algunas de ellas, ciertos comandos de Tcl pueden fallar al operar en rutas dentro de ese sistema de archivos. Sin embargo, en algunos casos esto puede ser deseable (por ejemplo, un sistema de archivos de solo lectura no debería implementar las últimas cuatro funciones, y un sistema de archivos que no admite enlaces simbólicos no necesita implementar la función readlink, etc. El núcleo de Tcl espera que los sistemas de archivos se comporten de esta manera).

PROC_TIPO_RUTA_SISTEMA_ARCHIVOS

Función para determinar el tipo de una ruta en este sistema de archivos. Puede ser NULL, en cuyo caso no habrá información de tipo disponible para los usuarios del sistema de archivos. El "tipo" se utiliza solo a efectos informativos y debe devolverse como la representación de cadena del Tcl_Obj que se devuelve. Un valor de retorno típico podría ser "networked", "zip" o "ftp". El resultado de Tcl_Obj es propiedad del sistema de archivos y, por lo tanto, Tcl incrementará el contador de referencias de ese valor si desea conservar una referencia a él.

typedef Tcl_Obj *Tcl_FSFilesystemPathTypeProc(
        Tcl_Obj *pathPtr);

PROC_SEPARADOR_SISTEMA_ARCHIVOS

Función para devolver el (los) carácter(es) separador(es) para este sistema de archivos. Esto solo necesita implementarse si el sistema de archivos desea usar un separador diferente de la cadena estándar "/". Entre otros usos, lo devuelve el comando file separator. El valor de retorno debe ser un valor con un contador de referencias de cero.

typedef Tcl_Obj *Tcl_FSFilesystemSeparatorProc(
        Tcl_Obj *pathPtr);

PROC_STAT

Función para procesar una llamada Tcl_FSStat. Debe implementarse para cualquier sistema de archivos razonable, ya que muchos comandos de nivel Tcl dependen crucialmente de él (por ejemplo, file atime, file isdirectory, file size, glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

La Tcl_FSStatProc rellena la estructura stat statPtr con información sobre el archivo especificado. No necesita ningún derecho de acceso al archivo para obtener esta información, pero necesita derechos de búsqueda en todos los directorios nombrados en la ruta que conduce al archivo. La estructura stat incluye información sobre el dispositivo, inodo (siempre 0 en Windows), modo de privilegios, nlink (siempre 1 en Windows), id de usuario (siempre 0 en Windows), id de grupo (siempre 0 en Windows), rdev (el mismo que el dispositivo en Windows), tamaño, hora del último acceso, hora de la última modificación y hora del último cambio de metadatos.

Si el archivo representado por pathPtr existe, la Tcl_FSStatProc devuelve 0 y la estructura stat se rellena con datos. De lo contrario, se devuelve -1 y no se proporciona información stat.

PROC_ACCESO

Función para procesar una llamada Tcl_FSAccess. Debe implementarse para cualquier sistema de archivos razonable, ya que muchos comandos de nivel Tcl dependen crucialmente de él (por ejemplo, file exists, file readable).

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

La Tcl_FSAccessProc comprueba si al proceso se le permitiría leer, escribir o comprobar la existencia del archivo (u otro objeto del sistema de archivos) cuyo nombre está en pathPtr. Si el nombre de ruta se refiere a un enlace simbólico, se deben probar los permisos del archivo al que se refiere este enlace simbólico.

En caso de éxito (todos los permisos solicitados concedidos), se devuelve cero. En caso de error (al menos un bit en mode solicitó un permiso que se deniega, o ocurrió algún otro error), se devuelve -1.

PROC_ABRIR_CANAL_ARCHIVO

ILECHANNELPROC

Función para procesar una llamada a Tcl_FSOpenFileChannel. Debe implementarse para cualquier sistema de archivos razonable, ya que cualquier operación que requiera abrir o acceder al contenido de un archivo la utilizará (por ejemplo, open, encoding y muchos comandos de Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

El Tcl_FSOpenFileChannelProc abre un archivo especificado por pathPtr y devuelve un manejador de canal que se puede utilizar para realizar entrada y salida en el archivo. Esta API está modelada a partir del procedimiento fopen de la biblioteca de E/S estándar de Unix. La sintaxis y el significado de todos los argumentos son similares a los dados en el comando open de Tcl al abrir un archivo, donde el argumento mode es una combinación de las banderas POSIX O_RDONLY, O_WRONLY, etc. Si ocurre un error al abrir el canal, Tcl_FSOpenFileChannelProc devuelve NULL y registra un código de error POSIX que se puede recuperar con Tcl_GetErrno. Además, si interp no es NULL, Tcl_FSOpenFileChannelProc deja un mensaje de error en el resultado de interp después de cualquier error.

El canal recién creado no debe registrarse en el intérprete suministrado por un Tcl_FSOpenFileChannelProc; esa tarea corresponde al llamador de Tcl_FSOpenFileChannel (si es necesario). Si uno de los canales estándar, stdin, stdout o stderr se cerró previamente, la creación del nuevo canal también lo asigna como reemplazo del canal estándar.

MATCHINDIRECTORYPROC

Función para procesar una llamada a Tcl_FSMatchInDirectory. Si no se implementa, la funcionalidad de glob y copia recursiva faltará en el sistema de archivos (y esto puede afectar a comandos como encoding names, que utilizan funcionalidad de glob internamente).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La función debe devolver todos los archivos o directorios (u otros objetos del sistema de archivos) que coincidan con el patrón dado y cumplan con la especificación types dada. Hay dos formas en las que esta función puede ser llamada. Si pattern es NULL, entonces pathPtr es una especificación de ruta completa de un solo archivo o directorio que debe verificarse en cuanto a existencia y tipo correcto. De lo contrario, pathPtr es un directorio, cuyo contenido la función debe buscar archivos o directorios que tengan el tipo correcto. En cualquier caso, se puede asumir que pathPtr no es NULL y no está vacío. Actualmente no está documentado si pathPtr tendrá o no un separador de archivos al final, por lo que el código debe ser flexible a ambas posibilidades.

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso de coincidencia. Los mensajes de error se colocan en interp, a menos que interp sea NULL, en cuyo caso no es necesario generar ningún mensaje de error; con un resultado TCL_OK, los resultados deben agregarse al valor de resultPtr dado (que se puede suponer que es una lista válida y no compartida de Tcl). Las coincidencias agregadas a resultPtr deben incluir cualquier prefijo de ruta dado en pathPtr (esto generalmente significa que serán especificaciones de ruta absolutas). Tenga en cuenta que si no se encuentran coincidencias, eso simplemente conduce a un resultado vacío; los errores solo se señalan para problemas reales de archivos o del sistema de archivos que puedan ocurrir durante el proceso de coincidencia.

La estructura Tcl_GlobTypeData pasada en el parámetro types contiene los siguientes campos:

typedef struct Tcl_GlobTypeData {
    /* Corresponde a bcdpfls como en 'find -t' */
    int type;
    /* Corresponde a permisos de archivo */
    int perm;
    /* Tipo de mac aceptable */
    Tcl_Obj *macType;
    /* Creador de mac aceptable */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Hay dos casos específicos que es importante manejar correctamente, ambos cuando types no es NULL. Los dos casos son cuando types->types & TCL_GLOB_TYPE_DIR o types->types & TCL_GLOB_TYPE_MOUNT son verdaderos (y en particular cuando las otras banderas son falsas). En el primero de estos casos, la función debe listar los directorios contenidos. Tcl utiliza esto para implementar globbing recursivo, por lo que es fundamental que los sistemas de archivos implementen la coincidencia de directorios correctamente. En el segundo de estos casos, con TCL_GLOB_TYPE_MOUNT, el sistema de archivos debe listar los puntos de montaje que se encuentran dentro del pathPtr dado (y en este caso, pathPtr no necesita estar dentro del mismo sistema de archivos, a diferencia de todos los demás casos en los que se llama a esta función). El soporte para esto es fundamental si Tcl quiere tener transiciones fluidas entre un sistema de archivos y otro.

UTIMEPROC

Función para procesar una llamada a Tcl_FSUtime. Requerida para permitir el establecimiento (no la lectura) de tiempos con file mtime, file atime y la implementación open-r/open-w/fcopy de file copy.

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

Los tiempos de acceso y modificación del archivo especificado por pathPtr deben cambiarse a los valores dados en la estructura tval.

El valor de retorno debe ser 0 en caso de éxito y -1 en caso de error, al igual que con la llamada al sistema utime.

LINKPROC

Función para procesar una llamada a Tcl_FSLink. Debe implementarse solo si el sistema de archivos admite enlaces y, de lo contrario, puede ser NULL.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

Si toPtr es NULL, se le pide a la función que lea el contenido de un enlace. El resultado es un Tcl_Obj que especifica el contenido del enlace dado por linkNamePtr, o NULL si el enlace no se pudo leer. El resultado es propiedad del llamador (y, por lo tanto, su contador de referencias debe incrementarse antes de devolverlo). Cualquier llamador debe llamar a Tcl_DecrRefCount en este resultado cuando ya no se necesite. Si toPtr no es NULL, la función debe intentar crear un enlace. El resultado en este caso debe ser toPtr si el enlace tuvo éxito y NULL en caso contrario. En este caso, el resultado no es propiedad del llamador (es decir, no se necesitan manipulaciones de recuento de referencias en ninguno de los extremos). Consulte la documentación de Tcl_FSLink para la interpretación correcta de las banderas linkAction.

LISTVOLUMESPROC

Función para listar los volúmenes de sistemas de archivos agregados por este sistema de archivos. Debe implementarse solo si el sistema de archivos agrega volúmenes al principio del sistema de archivos, para que puedan ser devueltos por file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

El resultado debe ser una lista de volúmenes agregados por este sistema de archivos, o NULL (o una lista vacía) si no se proporcionan volúmenes. Se considera que el valor de resultado es propiedad del sistema de archivos (no del núcleo de Tcl), pero se le debe dar un recuento de referencias para Tcl. Tcl utilizará el contenido de la lista y luego disminuirá ese recuento de referencias. Esto permite a los sistemas de archivos elegir si realmente desean conservar una lista "global" de volúmenes o no (si no, generan la lista sobre la marcha y la pasan a Tcl con un recuento de referencias de 1 y luego se olvidan de la lista; si sí, entonces simplemente incrementan el recuento de referencias de su lista global y la pasan a Tcl, que copiará el contenido y luego disminuirá el recuento de nuevo a donde estaba).

Por lo tanto, Tcl considera que los valores de retorno de este proc son de solo lectura.

FILEATTRSTRINGSPROC

Función para listar todas las cadenas de atributos que son válidas para este sistema de archivos. Si no se implementa, el sistema de archivos no admitirá el comando file attributes. Esto permite adjuntar información adicional arbitraria a los archivos en el sistema de archivos. Si no se implementa, no hay necesidad de implementar los métodos get y set.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

La función llamada puede devolver una matriz de cadenas o puede devolver NULL y colocar una lista de Tcl en objPtrRef. Tcl tomará esa lista y primero incrementará su recuento de referencias antes de usarla. Al finalizar ese uso, Tcl disminuirá su recuento de referencias. Por lo tanto, si la lista debe ser eliminada por Tcl cuando termine, debe tener un recuento de referencias de cero, y si la lista no debe ser eliminada, el sistema de archivos debe asegurarse de devolver un valor con un recuento de referencias de al menos uno.

FILEATTRSGETPROC

Función para procesar una llamada a Tcl_FSFileAttrsGet, utilizada por file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

Devuelve un código de retorno estándar de Tcl. El valor del atributo recuperado, que corresponde al elemento index de la lista devuelta por Tcl_FSFileAttrStringsProc, es un Tcl_Obj colocado en objPtrRef (si se devolvió TCL_OK) y es probable que tenga un recuento de referencias de cero. De cualquier manera, debemos almacenarlo en algún lugar (por ejemplo, el resultado de Tcl), o Incrementar/Decrementar su recuento de referencias para asegurar que se libere correctamente.

FILEATTRSSETPROC

Función para procesar una llamada a Tcl_FSFileAttrsSet, utilizada por file attributes. Si el sistema de archivos es de solo lectura, no hay necesidad de implementar esto.

typedef int Tcl_FSFileAttrsSetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj *objPtr);

El valor del atributo del elemento index en la lista devuelta por Tcl_FSFileAttrStringsProc debe establecerse en el objPtr dado.

Tcl_FSCreateDirectoryProc

typedef int Tcl_FSCreateDirectoryProc(

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso. Si tiene éxito, se debería haber añadido un nuevo directorio al sistema de archivos en la ubicación especificada por pathPtr.

REMOVEDIRECTORYPROC

Función para procesar una llamada a Tcl_FSRemoveDirectory. Debe ser implementada a menos que el sistema de archivos sea de solo lectura.

typedef int Tcl_FSRemoveDirectoryProc(
        Tcl_Obj *pathPtr,
        int recursive,
        Tcl_Obj **errorPtr);

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso. Si tiene éxito, el directorio especificado por pathPtr debería haber sido eliminado del sistema de archivos. Si se proporciona la bandera recursive, entonces un directorio no vacío debe ser eliminado sin error. typedef int Tcl_FSDeleteFileProc(

Si tiene éxito, el archivo especificado por pathPtr debería haber sido eliminado del sistema de archivos. Tenga en cuenta que, si el sistema de archivos admite enlaces simbólicos, Tcl siempre llamará a esta función y no a Tcl_FSRemoveDirectoryProc cuando sea necesario eliminarlos (incluso si son enlaces simbólicos a directorios).

EFICIENCIA DEL SISTEMA DE ARCHIVOS

Estas funciones no necesitan ser implementadas para un sistema de archivos particular, ya que el núcleo tiene una implementación de respaldo disponible. Consulte la descripción individual para conocer las consecuencias de dejar el campo como NULL.

LSTATPROC

Función para procesar una llamada a Tcl_FSLstat. Si no se implementa, Tcl intentará usar la statProc definida anteriormente en su lugar. Por lo tanto, solo necesita ser implementada si un sistema de archivos puede diferenciar entre las llamadas stat y lstat.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

El comportamiento de esta función es muy similar al de Tcl_FSStatProc definido anteriormente, excepto que si se aplica a un enlace simbólico, devuelve información sobre el enlace, no sobre el archivo de destino.

COPYFILEPROC

Función para procesar una llamada a Tcl_FSCopyFile. Si no se implementa, Tcl recurrirá a open-r, open-w y fcopy como mecanismo de copia. Por lo tanto, solo necesita ser implementada si el sistema de archivos puede realizar esa acción de manera más eficiente.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso de copia. Tenga en cuenta que destPathPtr es el nombre del archivo que se convertirá en la copia de srcPathPtr. Nunca es el nombre de un directorio en el que se pueda copiar srcPathPtr (es decir, la función es mucho más simple que el subcomando file copy a nivel de Tcl). Tenga en cuenta que, si el sistema de archivos admite enlaces simbólicos, Tcl siempre llamará a esta función y no a copyDirectoryProc cuando sea necesario copiarlos (incluso si son enlaces simbólicos a directorios). Finalmente, si el sistema de archivos determina que no puede admitir la acción de file copy, llamar a Tcl_SetErrno(EXDEV) y devolver un resultado que no sea TCL_OK le indicará a Tcl que utilice sus mecanismos de respaldo estándar.

RENAMEFILEPROC

Función para procesar una llamada a Tcl_FSRenameFile. Si no se implementa, Tcl recurrirá a un mecanismo de copia y eliminación. Por lo tanto, solo necesita ser implementada si el sistema de archivos puede realizar esa acción de manera más eficiente.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso de renombrado. Si el sistema de archivos determina que no puede admitir la acción de file rename, llamar a Tcl_SetErrno(EXDEV) y devolver un resultado que no sea TCL_OK le indicará a Tcl que utilice sus mecanismos de respaldo estándar.

COPYDIRECTORYPROC

Función para procesar una llamada a Tcl_FSCopyDirectory. Si no se implementa, Tcl recurrirá a un mecanismo recursivo de file mkdir, file copy. Por lo tanto, solo necesita ser implementada si el sistema de archivos puede realizar esa acción de manera más eficiente.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso de copia. Si ocurre un error, el nombre del archivo o directorio que causó el error debe colocarse en errorPtr. Tenga en cuenta que destPathPtr es el nombre del directorio que se convertirá en la imagen especular de srcPathPtr. No es el nombre de un directorio en el que se pueda copiar srcPathPtr (es decir, la función es mucho más simple que el subcomando file copy a nivel de Tcl). Finalmente, si el sistema de archivos determina que no puede admitir la acción de copia de directorios, llamar a Tcl_SetErrno(EXDEV) y devolver un resultado que no sea TCL_OK le indicará a Tcl que utilice sus mecanismos de respaldo estándar.

LOADFILEPROC

Función para procesar una llamada a Tcl_FSLoadFile. Si no se implementa, Tcl recurrirá a una copia en un archivo temporal nativo seguido de un Tcl_FSLoadFile en esa copia temporal. Por lo tanto, solo necesita ser implementada si el sistema de archivos puede cargar código directamente, o puede implementarse simplemente para devolver TCL_ERROR para deshabilitar la funcionalidad de carga en este sistema de archivos por completo.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Devuelve un código de finalización estándar de Tcl. Si ocurre un error, se deja un mensaje de error en el resultado del interp. La función carga dinámicamente un archivo de código binario en la memoria. En una carga exitosa, handlePtr debe llenarse con un token para el archivo cargado dinámicamente, y unloadProcPtr debe llenarse con la dirección de un procedimiento. El procedimiento de descarga se llamará con el Tcl_LoadHandle dado como su único parámetro cuando Tcl necesite descargar el archivo. Por ejemplo, para el sistema de archivos nativo, el Tcl_LoadHandle devuelto es actualmente un token que se puede usar en el privado TclpFindSymbol para acceder a funciones en el nuevo código. Cada sistema de archivos es libre de definir Tcl_LoadHandle según lo requiera. Finalmente, si el sistema de archivos determina que no puede admitir la acción de carga de archivos, llamar a Tcl_SetErrno(EXDEV) y devolver un resultado que no sea TCL_OK le indicará a Tcl que utilice sus mecanismos de respaldo estándar.

UNLOADFILEPROC

Función para descargar un archivo previamente cargado con éxito. Si se implementó la carga, entonces esto también debería implementarse, si hay alguna acción de limpieza requerida.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

Función para procesar una llamada a Tcl_FSGetCwd. La mayoría de los sistemas de archivos no necesitan implementar esto. Por lo general, solo se llamará una vez, si se llama a getcwd antes que a chdir. Puede ser NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

Si el sistema de archivos admite una noción nativa de directorio de trabajo actual (que quizás podría cambiar independientemente de Tcl), esta función debería devolver ese cwd como resultado, o NULL si no se pudo determinar el directorio actual (por ejemplo, el usuario no tiene los permisos apropiados en el directorio cwd). Si se devuelve NULL, se deja un mensaje de error en el resultado del interp.

CHDIRPROC

Función para procesar una llamada a Tcl_FSChdir. Si los sistemas de archivos no implementan esto, se emulará mediante una serie de verificaciones de acceso a directorios. De lo contrario, los sistemas de archivos virtuales que lo implementen solo necesitan responder con un resultado positivo si pathPtr es un directorio válido y accesible en su sistema de archivos. No necesitan recordar el resultado, ya que se recordará automáticamente para su uso por Tcl_FSGetCwd. Los sistemas de archivos reales deben llevar a cabo la acción correcta (es decir, llamar a la API chdir del sistema correspondiente).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

El Tcl_FSChdirProc cambia el directorio de trabajo actual de la aplicación al valor especificado en pathPtr. La función devuelve -1 en caso de error o 0 en caso de éxito.
