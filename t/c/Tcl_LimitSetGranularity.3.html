ARGUMENTOS

Tcl_Interp *interp (entrada)
Intérprete al que se aplica el límite que se está gestionando o cuyos límites se van a comprobar.
int type (entrada)
El tipo de límite al que se refiere la operación. Debe ser TCL_LIMIT_COMMANDS o TCL_LIMIT_TIME.
int commandLimit (entrada)
El número máximo de comandos (según lo informado por info cmdcount) que pueden ejecutarse en el intérprete.
Tcl_Time *timeLimitPtr (entrada/salida)
Un puntero a una estructura de la que se leerá el nuevo límite de tiempo (Tcl_LimitSetTime) o se escribirá el límite de tiempo actual (Tcl_LimitGetTime).
int granularity (entrada)
Divisor que indica con qué frecuencia se debe comprobar realmente un límite particular. Debe ser al menos 1.
Tcl_LimitHandlerProc *handlerProc (entrada)
Función a llamar cuando se supera un límite determinado. Si el handlerProc elimina o eleva el límite durante su procesamiento, se permitirá que el intérprete limitado continúe procesando después de que el manejador devuelva el control. Se pueden adjuntar muchos manejadores al mismo límite de intérprete; su orden de ejecución no está definido, y deben identificarse por handlerProc y clientData cuando se eliminan.
ClientData clientData (entrada)
Palabra arbitraria del tamaño de un puntero utilizada para pasar algún contexto a la función handlerProc.
Tcl_LimitHandlerDeleteProc *deleteProc (entrada)
Función a llamar siempre que se elimine un manejador. Puede ser NULL si el clientData no requiere eliminación.

DESCRIPCIÓN

El subsistema de límites de recursos del intérprete de Tcl permite un control estricto sobre la cantidad de tiempo de cálculo que puede utilizar un script, y es útil para casos en los que un programa se divide en múltiples piezas donde algunas partes son más confiables que otras (por ejemplo, servidores de aplicaciones web).

Cada intérprete puede tener un límite en el tiempo de reloj para la ejecución y un límite en el número de comandos que el intérprete puede ejecutar. Dado que la comprobación de estos límites puede ser costosa (especialmente el límite de tiempo), cada límite también tiene una granularidad de comprobación, que es un divisor de un recuento interno de los puntos del núcleo donde se puede realizar una comprobación (que es inmediatamente antes de ejecutar un comando y con una frecuencia no especificada entre la ejecución de comandos, lo que puede ocurrir en bucles while con cuerpo vacío).

El componente final del motor de límites es un esquema de devolución de llamada que permite notificaciones sobre cuándo se ha superado un límite. Estas devoluciones de llamada pueden simplemente proporcionar registro o asignar más recursos al intérprete para permitirle continuar procesando durante más tiempo.

Cuando se supera un límite (y se han ejecutado las devoluciones de llamada; el orden de ejecución de las devoluciones de llamada no está especificado), la ejecución en el intérprete limitado se detiene generando un error y estableciendo una bandera que impide que el comando catch en ese intérprete capture ese error. Depende del contexto que inició la ejecución en ese intérprete (típicamente el intérprete principal) manejar el error.

API DE COMPROBACIÓN DE LÍMITES

Para comprobar los límites de recursos de un intérprete, llame a Tcl_LimitCheck, que devuelve TCL_OK si el límite no se superó (después de procesar las devoluciones de llamada) y TCL_ERROR si el límite se superó (en cuyo caso también se coloca un mensaje de error en el resultado del intérprete). Esa función solo debe llamarse cuando Tcl_LimitReady devuelve un valor distinto de cero para que se aplique la política de granularidad. Esta API está diseñada para ser similar en uso a Tcl_AsyncReady y Tcl_AsyncInvoke.

Al escribir código que puede comportarse como catch en relación con los errores, solo debe capturar un error si Tcl_LimitExceeded devuelve cero. Si devuelve un valor distinto de cero, el intérprete está en un estado de límite superado y los errores deben permitirse que se propaguen al contexto de llamada. También puede comprobar si un tipo particular de límite se ha superado utilizando Tcl_LimitTypeExceeded.

CONFIGURACIÓN DE LÍMITES

Para comprobar si se ha establecido un límite (pero no si realmente se ha superado) en un intérprete, llame a Tcl_LimitTypeEnabled con el tipo de límite que desea comprobar. Para habilitar un límite particular, llame a Tcl_LimitTypeSet, y para deshabilitar un límite, llame a Tcl_LimitTypeReset.

El nivel de un límite de comandos puede establecerse utilizando Tcl_LimitSetCommands y recuperarse utilizando Tcl_LimitGetCommands. De manera similar para un límite de tiempo con Tcl_LimitSetTime y Tcl_LimitGetTime respectivamente, pero con esa API el límite de tiempo se copia desde y hacia la estructura Tcl_Time a la que apunta el argumento timeLimitPtr.

La granularidad de comprobación para un límite particular puede establecerse utilizando Tcl_LimitSetGranularity y recuperarse utilizando Tcl_LimitGetGranularity. Tenga en cuenta que las granularidades siempre deben ser positivas.

DEVOLUCIONES DE LLAMADA DE LÍMITES

Para agregar una devolución de llamada de manejador que se invocará cuando se supere un límite, llame a Tcl_LimitAddHandler. El argumento handlerProc describe la función que se llamará realmente; debe tener el siguiente prototipo:

typedef void Tcl_LimitHandlerProc(
        ClientData clientData,
        Tcl_Interp *interp);

El argumento clientData para el manejador será lo que se pase al argumento clientData de Tcl_LimitAddHandler, y interp es el intérprete cuyo límite se superó.

El argumento deleteProc de Tcl_LimitAddHandler es una función que se llamará para eliminar el valor clientData. Puede ser TCL_STATIC o NULL si no es necesaria ninguna acción de eliminación, o TCL_DYNAMIC si todo lo necesario es liberar la estructura con Tcl_Free. De lo contrario, debe referirse a una función con el siguiente prototipo:

typedef void Tcl_LimitHandlerDeleteProc(
        ClientData clientData);

Se puede eliminar un manejador de límites utilizando Tcl_LimitRemoveHandler; el manejador que se eliminará será el primero que se encuentre (de los manejadores agregados con Tcl_LimitAddHandler) con argumentos type, handlerProc y clientData exactamente coincidentes. Esta función siempre invoca el deleteProc en el clientData (a menos que el deleteProc fuera NULL o TCL_STATIC).
