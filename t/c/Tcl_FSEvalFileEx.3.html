DESCRIPCIÓN

Hay varias razones para llamar a las funciones de la API Tcl_FS (por ejemplo, Tcl_FSAccess y Tcl_FSStat) en lugar de llamar directamente a funciones de nivel de sistema como access y stat. En primer lugar, funcionarán multiplataforma, por lo que una extensión que las llame debería funcionar sin modificaciones en Unix y Windows. En segundo lugar, la implementación de Windows de algunas de estas funciones corrige algunos errores en las llamadas a nivel de sistema. En tercer lugar, estas llamadas a funciones manejan cualquier conversión de ruta de “Utf a nativo de plataforma” que pueda ser necesaria (y pueden almacenar en caché los resultados de dichas conversiones para una mayor eficiencia en llamadas posteriores). En cuarto lugar, y quizás lo más importante, todas estas funciones “conocen los sistemas de archivos virtuales”. Cualquier sistema de archivos virtual (VFS, por sus siglas en inglés) que se haya registrado (a través de Tcl_FSRegister) puede redirigir el acceso a archivos a medios o métodos de acceso alternativos. Esto significa que todas estas funciones (y, por lo tanto, los comandos de Tcl correspondientes file, glob, pwd, cd, open, etc.) pueden operar en “archivos” que no son archivos nativos en el sistema de archivos nativo. Esto también significa que cualquier extensión de Tcl que acceda al sistema de archivos (FS, por sus siglas en inglés) a través de esta API es automáticamente “consciente de los sistemas de archivos virtuales”. Por supuesto, si una extensión accede directamente al sistema de archivos nativo (a través de APIs específicas de la plataforma, por ejemplo), Tcl no puede interceptar dichas llamadas.

Si se han registrado VFS apropiados, los “archivos” pueden ser, para dar dos ejemplos, remotos (por ejemplo, situados en un servidor ftp remoto) o archivados (por ejemplo, dentro de un archivo .zip). Dichos sistemas de archivos registrados proporcionan una tabla de búsqueda de funciones para implementar toda o parte de la funcionalidad aquí enumerada. Finalmente, las llamadas Tcl_FSStat y Tcl_FSLstat abstraen lo que es realmente el búfer “struct stat”, lo que permite usar el mismo código tanto en sistemas con soporte para archivos mayores de 2 GB como en sistemas sin él.

La API Tcl_FS está **Tcl_Obj**-ificada y puede almacenar en caché representaciones internas y otras cadenas relacionadas con rutas (por ejemplo, el directorio de trabajo actual). Un efecto secundario de esto es que no se deben pasar valores con un recuento de referencias de cero a ninguna de estas funciones. Si tales llamadas se manejaran, podrían resultar en fugas de memoria (en algunas circunstancias, el código del sistema de archivos puede desear retener una referencia al valor pasado, y por lo tanto no se puede suponer que después de que cualquiera de estas llamadas regrese, el valor todavía tenga un recuento de referencias de cero; podría haber sido incrementado) o en una falla de segmentación directa (u otro error de acceso a memoria) debido a que el valor se libera a mitad de camino de la manipulación compleja de valores requerida para garantizar que la ruta esté completamente normalizada y sea absoluta para la determinación del sistema de archivos. La lección práctica a aprender de esto es que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

es incorrecto y puede causar errores de memoria. El path debe tener su recuento de referencias incrementado antes de pasarlo, o decrementar lo. Por esta razón, los valores con un recuento de referencias de cero se consideran no válidos como rutas de sistema de archivos y llamar a cualquier función de la API de Tcl_FS con dicho valor no tendrá ningún efecto.

FUNCIONES DE LA API FS

Tcl_FSCopyFile intenta copiar el archivo dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas se encuentran en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), se llama a la función de “copiar archivo” de ese sistema de archivos (si no es NULL). De lo contrario, la función devuelve -1 y establece la variable global C errno al código de error POSIX “EXDEV” (que significa un “enlace entre dominios”).

Tcl_FSCopyDirectory intenta copiar el directorio dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas se encuentran en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), se llama a la función de “copiar archivo” de ese sistema de archivos (si no es NULL). De lo contrario, la función devuelve -1 y establece la variable global C errno al código de error POSIX “EXDEV” (que significa un “enlace entre dominios”).

Tcl_FSCreateDirectory intenta crear el directorio dado por pathPtr llamando a la función de “crear directorio” del sistema de archivos propietario.

Tcl_FSDeleteFile intenta eliminar el archivo dado por pathPtr llamando a la función de “eliminar archivo” del sistema de archivos propietario.

Tcl_FSRemoveDirectory intenta eliminar el directorio dado por pathPtr llamando a la función de “eliminar directorio” del sistema de archivos propietario.

Tcl_FSRenameFile intenta renombrar el archivo o directorio dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas se encuentran en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), se llama a la función de “renombrar archivo” de ese sistema de archivos (si no es NULL). De lo contrario, la función devuelve -1 y establece la variable global C errno al código de error POSIX “EXDEV” (que significa un “enlace entre dominios”).

Tcl_FSListVolumes llama a cada sistema de archivos que tiene una función de “listar volúmenes” no NULL y les pide que devuelvan su lista de volúmenes raíz. Acumula los valores de retorno en una lista que se devuelve al llamador (con un recuento de referencias de 0).

Tcl_FSEvalFileEx lee el archivo dado por pathPtr usando la codificación identificada por encodingName y evalúa su contenido como un script de Tcl. Devuelve la misma información que Tcl_EvalObjEx. Si encodingName es NULL, se utiliza la codificación del sistema para leer el contenido del archivo. Si el archivo no se pudo leer, se devuelve un error de Tcl para describir por qué no se pudo leer el archivo. El carácter de fin de archivo (eofchar) para los archivos es “\x1A” (^Z) para todas las plataformas. Si necesita un “^Z” en el código para comparación de cadenas, puede usar “\x1A”, que será sustituido de forma segura por el intérprete de Tcl en “^Z”. Tcl_FSEvalFile es una versión más simple de Tcl_FSEvalFileEx que siempre usa la codificación del sistema al leer el archivo.

Tcl_FSLoadFile carga dinámicamente un archivo de código binario en memoria y devuelve las direcciones de dos procedimientos dentro de ese archivo, si están definidos. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr. Si ese sistema de archivos no implementa esta función (la mayoría de los sistemas de archivos virtuales no lo harán, debido a limitaciones del sistema operativo en la carga dinámica de código binario), Tcl intentará copiar el archivo a un directorio temporal y cargar ese archivo temporal. Tcl_FSUnloadFile revierte la operación, solicitando que la biblioteca indicada por loadHandle se elimine del proceso. Tenga en cuenta que, a diferencia del comando unload, esto no brinda a la biblioteca ninguna oportunidad de limpieza.

Ambas funciones anteriores devuelven un código de finalización de Tcl estándar. Si ocurre un error, se deja un mensaje de error en el resultado del interp.

El token proporcionado a través de la variable indicada por loadHandlePtr puede usarse con Tcl_FindSymbol.

Tcl_FSMatchInDirectory es utilizada por el código de globbing para buscar en un directorio todos los archivos que coincidan con un patrón dado. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el globbing. Los mensajes de error se colocan en interp (a menos que interp sea NULL, lo cual está permitido), pero los buenos resultados se colocan en resultPtr proporcionado.

Tenga en cuenta que el código glob implementa patrones recursivos internamente, por lo que esta función solo recibirá patrones simples, que pueden coincidir usando la lógica de string match. Para manejar la recursión, Tcl llamará a esta función con frecuencia solicitando solo directorios. Un caso especial de ser llamado con un patrón NULL indica que la ruta solo debe verificarse para el tipo correcto.

Tcl_FSLink reemplaza la versión de biblioteca de readlink y la extiende para admitir la creación de enlaces. Se llamará a la función apropiada para el sistema de archivos al que pertenece linkNamePtr.

Si toPtr es NULL, se realiza una acción de “leer enlace”. El resultado es un Tcl_Obj que especifica el contenido del enlace simbólico dado por linkNamePtr, o NULL si el enlace no se pudo leer. El resultado es propiedad del llamador, que debe llamar a Tcl_DecrRefCount cuando el resultado ya no sea necesario. Si toPtr no es NULL, Tcl debe crear un enlace de uno de los tipos pasados en el indicador linkAction. Este indicador es una combinación OR de TCL_CREATE_SYMBOLIC_LINK y TCL_CREATE_HARD_LINK. Cuando hay una opción (es decir, se pasa más de un indicador), la convención de Tcl es preferir los enlaces simbólicos. Cuando se crea un enlace con éxito, el valor de retorno debe ser toPtr (que, por lo tanto, ya es propiedad del llamador). Si no tiene éxito, se devuelve NULL.

Tcl_FSLstat rellena la estructura Tcl_StatBuf statPtr con información sobre el archivo especificado. No necesita ningún derecho de acceso al archivo para obtener esta información, pero necesita derechos de búsqueda a todos los directorios nombrados en la ruta que conduce al archivo. La estructura Tcl_StatBuf incluye información sobre el dispositivo, el inodo (siempre 0 en Windows), el modo de privilegios, nlink (siempre 1 en Windows), el ID de usuario (siempre 0 en Windows), el ID de grupo (siempre 0 en Windows), rdev (lo mismo que el dispositivo en Windows), tamaño, último acceso

ss time, last modification time, and last metadata change time. See PORTABLE STAT RESULT API for a description of how to write portable code to allocate and access the Tcl_StatBuf structure.

If path exists, Tcl_FSLstat returns 0 and the stat structure is filled with data. Otherwise, -1 is returned, and no stat info is given.

Tcl_FSUtime replaces the library version of utime.

This returns 0 on success and -1 on error (as per the utime documentation). If successful, the function will update the “atime” and “mtime” values of the file given.

Tcl_FSFileAttrsGet implements read access for the hookable file attributes subcommand. The appropriate function for the filesystem to which pathPtr belongs will be called.

If the result is TCL_OK, then a value was placed in objPtrRef, which will only be temporarily valid (unless Tcl_IncrRefCount is called).

Tcl_FSFileAttrsSet implements write access for the hookable file attributes subcommand. The appropriate function for the filesystem to which pathPtr belongs will be called.

Tcl_FSFileAttrStrings implements part of the hookable file attributes subcommand. The appropriate function for the filesystem to which pathPtr belongs will be called.

The called procedure may either return an array of strings, or may instead return NULL and place a Tcl list into the given objPtrRef. Tcl will take that list and first increment its reference count before using it. On completion of that use, Tcl will decrement its reference count. Hence if the list should be disposed of by Tcl when done, it should have a reference count of zero, and if the list should not be disposed of, the filesystem should ensure it retains a reference count to the value.

Tcl_FSAccess checks whether the process would be allowed to read, write or test for existence of the file (or other filesystem object) whose name is pathname. If pathname is a symbolic link on Unix, then permissions of the file referred by this symbolic link are tested.

On success (all requested permissions granted), zero is returned. On error (at least one bit in mode asked for a permission that is denied, or some other error occurred), -1 is returned.

Tcl_FSStat fills the Tcl_StatBuf structure statPtr with information about the specified file. You do not need any access rights to the file to get this information but you need search rights to all directories named in the path leading to the file. The Tcl_StatBuf structure includes info regarding device, inode (always 0 on Windows), privilege mode, nlink (always 1 on Windows), user id (always 0 on Windows), group id (always 0 on Windows), rdev (same as device on Windows), size, last access time, last modification time, and last metadata change time. See PORTABLE STAT RESULT API for a description of how to write portable code to allocate and access the Tcl_StatBuf structure.

If path exists, Tcl_FSStat returns 0 and the stat structure is filled with data. Otherwise, -1 is returned, and no stat info is given.

Tcl_FSOpenFileChannel opens a file specified by pathPtr and returns a channel handle that can be used to perform input and output on the file. This API is modeled after the fopen procedure of the Unix standard I/O library. The syntax and meaning of all arguments is similar to those given in the Tcl open command when opening a file. If an error occurs while opening the channel, Tcl_FSOpenFileChannel returns NULL and records a POSIX error code that can be retrieved with Tcl_GetErrno. In addition, if interp is non-NULL, Tcl_FSOpenFileChannel leaves an error message in interp's result after any error.

The newly created channel is not registered in the supplied interpreter; to register it, use Tcl_RegisterChannel. If one of the standard channels, stdin, stdout or stderr was previously closed, the act of creating the new channel also assigns it as a replacement for the standard channel.

Tcl_FSGetCwd replaces the library version of getcwd.

It returns the Tcl library's current working directory. This may be different to the native platform's working directory, which happens when the current working directory is not in the native filesystem.

The result is a pointer to a Tcl_Obj specifying the current directory, or NULL if the current directory could not be determined. If NULL is returned, an error message is left in the interp's result.

The result already has its reference count incremented for the caller. When it is no longer needed, that reference count should be decremented. This is needed for thread-safety purposes, to allow multiple threads to access this and related functions, while ensuring the results are always valid.

Tcl_FSChdir replaces the library version of chdir. The path is normalized and then passed to the filesystem which claims it. If that filesystem does not implement this function, Tcl will fallback to a combination of stat and access to check whether the directory exists and has appropriate permissions.

For results, see chdir documentation. If successful, we keep a record of the successful path in cwdPathPtr for subsequent calls to Tcl_FSGetCwd.

Tcl_FSPathSeparator returns the separator character to be used for most specific element of the path specified by pathPtr (i.e. the last part of the path).

The separator is returned as a Tcl_Obj containing a string of length 1. If the path is invalid, NULL is returned.

Tcl_FSJoinPath takes the given Tcl_Obj, which must be a valid list (which is allowed to have a reference count of zero), and returns the path value given by considering the first elements elements as valid path segments (each path segment may be a complete path, a partial path or just a single possible directory or file name). If any path segment is actually an absolute path, then all prior path segments are discarded. If elements is less than 0, we use the entire list.

It is possible that the returned value is actually an element of the given list, so the caller should be careful to increment the reference count of the result before freeing the list.

The returned value, typically with a reference count of zero (but it could be shared under some conditions), contains the joined path. The caller must add a reference count to the value before using it. In particular, the returned value could be an element of the given list, so freeing the list might free the value prematurely if no reference count has been taken. If the number of elements is zero, then the returned value will be an empty-string Tcl_Obj.

Tcl_FSSplitPath takes the given Tcl_Obj, which should be a valid path, and returns a Tcl list value containing each segment of that path as an element. It returns a list value with a reference count of zero. If the passed in lenPtr is non-NULL, the variable it points to will be updated to contain the number of elements in the returned list.

Tcl_FSEqualPaths tests whether the two paths given represent the same filesystem object. It returns 1 if the paths are equal, and 0 if they are different. If either path is NULL, 0 is always returned.

Tcl_FSGetNormalizedPath attempts to extract from the given Tcl_Obj a unique normalized path representation, whose string value can be used as a unique identifier for the file.

It returns the normalized path value, owned by Tcl, or NULL if the path was invalid or could otherwise not be successfully converted. Extraction of absolute, normalized paths is very efficient (because the filesystem operates on these representations internally), although the result when the filesystem contains numerous symbolic links may not be the most user-friendly version of a path. The return value is owned by Tcl and has a lifetime equivalent to that of the pathPtr passed in (unless that is a relative path, in which case the normalized path value may be freed any time the cwd changes) - the caller can of course increment the reference count if it wishes to maintain a copy for longer.

Tcl_FSJoinToPath takes the given value, which should usually be a valid path or NULL, and joins onto it the array of paths segments given.

Returns a value, typically with reference count of zero (but it could be shared under some conditions), containing the joined path. The caller must add a reference count to the value before using it. If any of the values passed into this function (pathPtr or path elements) have a reference count of zero, they will be freed when this function returns.

Tcl_FSConvertToPathType tries to convert the given Tcl_Obj to a valid Tcl path type, taking account of the fact that the cwd may have changed even if this value is already supposedly of the correct type. The filename may begin with "~" (to indicate current user's home directory) or "~<user>" (to indicate any user's home directory).

If the conversion succeeds (i.e. the value is a valid path in one of the current filesystems), then TCL_OK is returned. Otherwise TCL_ERROR is returned, and an error message may be left in the interpreter.

Tcl_FSGetInternalRep extracts the internal representation of a given path value, in the given filesystem. If the path value belongs to a different filesystem, we return NULL. If the internal representation is currently NULL, we attempt to generate it, by calling the filesystem's Tcl_FSCreateInternalRepProc.

Returns NULL or a valid internal path representation. This internal representation is cached, so that repeated calls to this function will not require additional conversions.

Tcl_FSGetTranslatedPath attempts to extract the translated path from the given Tcl_Obj.

If the translation succeeds (i.e. the value is a valid path), then it is returned. Otherwise NULL will be returned, and an error message may be left in the interpreter. A "translated" path is one which contains no "~" or "~user" sequences (these have been expanded to their current representation in the filesystem). The value returned is owned by the caller, which must store it or call Tcl_DecrRefCount to ensure memory is freed. This function is of little practical use, and Tcl_FSGetNormalizedPath or Tcl_FSGetNativePath are usually better functions to use for most purposes.

FILESYSTEM FUNCTIONS

These functions provide a high-level API for interacting with the Tcl filesystem abstraction layer. They are used to query path types, translate paths between native and normalized forms, and to obtain information about files.

PATH TRANSLATION AND QUERYING

Tcl_FSGetNormalizedPath returns a new normalized path value from the given path value. If the path value is already normalized, it is returned unchanged. Otherwise, the path is normalized according to the rules of the filesystem that owns the path value, and a new path value is returned. The new path value is owned by the caller and must be freed using Tcl_FSFreePath.

Tcl_FSGetTranslatedPath returns a new path value which is the translation of the given path value into the filesystem specified by filesystemName. If the path value is already in that filesystem, it is returned unchanged. Otherwise, the path is translated by the appropriate filesystem drivers, and a new path value is returned. The new path value is owned by the caller and must be freed using Tcl_FSFreePath.

Tcl_FSGetInternalRep returns a pointer to the internal representation of the path value. This is primarily for use by filesystem drivers, to allow them to retrieve the native representation of a path without needing to convert it from a UTF-8 string.

Tcl_FSGetPath returns a pointer to the normalized path string representation of the given path value. The string is guaranteed to be valid as long as the path value is valid.

Tcl_FSNewNativePath creates a new normalized path value from a native path string. This is useful when dealing with paths obtained from the operating system that are not in Tcl's internal UTF-8 format. The new path value is owned by the caller and must be freed using Tcl_FSFreePath. This function is intended for use by filesystem drivers that need to create Tcl path values from native paths.

Tcl_FSNewNativePath performs something like the reverse of the usual obj->path->nativerep conversions. If some code retrieves a path in native form (from, e.g. readlink or a native dialog), and that path is to be used at the Tcl level, then calling this function is an efficient way of creating the appropriate path value type.

The resulting value is a pure “path” value, which will only receive a UTF-8 string representation if that is required by some Tcl code.

Tcl_FSGetNativePath is for use by the Win/Unix native filesystems, so that they can easily retrieve the native (char* or TCHAR*) representation of a path. This function is a convenience wrapper around Tcl_FSGetInternalRep. It may be desirable in the future to have non-string-based native representations (for example, on macOS, a representation using a fileSpec of FSRef structure would probably be more efficient). On Windows a full Unicode representation would allow for paths of unlimited length. Currently the representation is simply a character string which may contain either the relative path or a complete, absolute normalized path in the native encoding (complex conditions dictate which of these will be provided, so neither can be relied upon, unless the path is known to be absolute). If you need a native path which must be absolute, then you should ask for the native version of a normalized path. If for some reason a non-absolute, non-normalized version of the path is needed, that must be constructed separately (e.g. using Tcl_FSGetTranslatedPath).

The native representation is cached so that repeated calls to this function will not require additional conversions. The return value is owned by Tcl and has a lifetime equivalent to that of the pathPtr passed in (unless that is a relative path, in which case the native representation may be freed any time the cwd changes).

Tcl_FSFileSystemInfo returns a list of two elements. The first element is the name of the filesystem (e.g. “native”, “vfs”, “zip”, or “prowrap”, perhaps), and the second is the particular type of the given path within that filesystem (which is filesystem dependent). The second element may be empty if the filesystem does not provide a further categorization of files.

A valid list value is returned, unless the path value is not recognized, when NULL will be returned.

Tcl_FSGetFileSystemForPath returns a pointer to the Tcl_Filesystem which accepts this path as valid.

If no filesystem will accept the path, NULL is returned.

Tcl_FSGetPathType determines whether the given path is relative to the current directory, relative to the current volume, or absolute.

It returns one of TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE, or TCL_PATH_VOLUME_RELATIVE

THE VIRTUAL FILESYSTEM API

A filesystem provides a Tcl_Filesystem structure that contains pointers to functions that implement the various operations on a filesystem; these operations are invoked as needed by the generic layer, which generally occurs through the functions listed above.

The Tcl_Filesystem structures are manipulated using the following methods.

Tcl_FSRegister takes a pointer to a filesystem structure and an optional piece of data to associated with that filesystem. On calling this function, Tcl will attach the filesystem to the list of known filesystems, and it will become fully functional immediately. Tcl does not check if the same filesystem is registered multiple times (and in general that is not a good thing to do). TCL_OK will be returned.

Tcl_FSUnregister removes the given filesystem structure from the list of known filesystems, if it is known, and returns TCL_OK. If the filesystem is not currently registered, TCL_ERROR is returned.

Tcl_FSData will return the clientData associated with the given filesystem, if that filesystem is registered. Otherwise it will return NULL.

Tcl_FSMountsChanged is used to inform the Tcl's core that the set of mount points for the given (already registered) filesystem have changed, and that cached file representations may therefore no longer be correct.

Except for the first three fields in this structure which contain simple data elements, all entries contain addresses of functions called by the generic filesystem layer to perform the complete range of filesystem related actions.

The many functions in this structure are broken down into three categories: infrastructure functions (almost all of which must be implemented), operational functions (which must be implemented if a complete filesystem is provided), and efficiency functions (which need only be implemented if they can be done so efficiently, or if they have side-effects which are required by the filesystem; Tcl has less efficient emulations it can fall back on). It is important to note that, in the current version of Tcl, most of these fallbacks are only used to handle commands initiated in Tcl, not in C. What this means is, that if a file rename command is issued in Tcl, and the relevant filesystem(s) do not implement their Tcl_FSRenameFileProc, Tcl's core will instead fallback on a combination of other filesystem functions (it will use Tcl_FSCopyFileProc followed by Tcl_FSDeleteFileProc, and if Tcl_FSCopyFileProc is not implemented there is a further fallback). However, if a Tcl_FSRenameFileProc command is issued at the C level, no such fallbacks occur. This is true except for the last four entries in the filesystem table (lstat, load, getcwd and chdir) for which fallbacks do in fact occur at the C level.

Any functions which take path names in Tcl_Obj form take those names in UTF-8 form. The filesystem infrastructure API is designed to support efficient, cached conversion of these UTF-8 paths to other native representations.

INFRAESTRUCTURA DE SISTEMA DE ARCHIVOS

Estos campos contienen información básica sobre la estructura del sistema de archivos y las direcciones de las funciones que se utilizan para asociar un sistema de archivos particular con una ruta de acceso a archivo, y para gestionar el manejo interno de las representaciones de rutas, por ejemplo, copiar y liberar dichas representaciones.

NOMBRE TIPO

El campo typeName contiene una cadena terminada en nulo que identifica el tipo de sistema de archivos implementado, por ejemplo, "nativo", "zip" o "vfs".

LONGITUD ESTRUCTURA

El campo structureLength se implementa generalmente como sizeof(Tcl_Filesystem), y está ahí para permitir una compatibilidad binaria retroactiva más fácil si el tamaño de la estructura cambia en una futura versión de Tcl.

VERSIÓN

El campo version debe establecerse en TCL_FILESYSTEM_VERSION_1.

RUTA EN PROCEDIMIENTO SISTEMA ARCHIVOS

El campo pathInFilesystemProc contiene la dirección de una función que se llama para determinar si un valor de ruta dado pertenece a este sistema de archivos o no. Tcl solo llamará al resto de las funciones del sistema de archivos con una ruta para la que esta función haya devuelto TCL_OK. Si la ruta no pertenece, se debe devolver -1 (el comportamiento de Tcl para cualquier otro valor de retorno no está definido). Si se devuelve TCL_OK, entonces el parámetro de salida opcional clientDataPtr se puede usar para devolver una representación interna (específica del sistema de archivos) de la ruta, que se almacenará en caché dentro del valor de la ruta y puede ser recuperada eficientemente por las otras funciones del sistema de archivos. Tcl almacenará en caché simultáneamente el hecho de que esta ruta pertenece a este sistema de archivos. Dichas cachés se invalidan cuando se agregan o eliminan estructuras del sistema de archivos de la lista interna de Tcl de sistemas de archivos conocidos.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

PROCEDIMIENTO NORMALIZAR RUTA

Función para normalizar una ruta. Debe implementarse para todos los sistemas de archivos que pueden tener múltiples representaciones de cadena para el mismo valor de ruta. En Tcl, cada "ruta" debe tener una única representación de cadena "normalizada". Dependiendo del sistema de archivos, puede haber más de una representación de cadena no normalizada que se refiera a esa ruta (por ejemplo, una ruta relativa, una ruta con mayúsculas y minúsculas diferentes si el sistema de archivos no distingue entre mayúsculas y minúsculas, una ruta que contenga una referencia a un directorio de inicio como "~", una ruta que contenga enlaces simbólicos, etc.). Si el último componente de la ruta es un enlace simbólico, no debe convertirse al valor al que apunta (pero su mayúsculas/minúsculas u otros aspectos deben ser únicos). Todos los demás componentes de la ruta deben convertirse desde enlaces simbólicos. Esta única excepción es necesaria para coincidir con la semántica de Tcl con file delete, file rename, file copy que operan sobre enlaces simbólicos. Esta función puede ser llamada con nextCheckpoint ya sea al principio de la ruta (es decir, cero), al final de la ruta, o en cualquier separador de archivo intermedio en la ruta. Nunca apuntará a ninguna otra posición arbitraria en la ruta. En el último de los tres casos válidos, la implementación puede asumir que la ruta hasta e incluyendo el separador de archivo es conocida y normalizada.

        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

El Tcl_FSOpenFileChannelProc abre un archivo especificado por pathPtr y devuelve un manejador de canal que puede ser utilizado para realizar operaciones de entrada y salida en el archivo. Esta API está modelada a partir del procedimiento fopen de la biblioteca estándar de E/S de Unix. La sintaxis y el significado de todos los argumentos son similares a los dados en el comando open de Tcl al abrir un archivo, donde el argumento mode es una combinación de las banderas POSIX O_RDONLY, O_WRONLY, etc. Si ocurre un error al abrir el canal, Tcl_FSOpenFileChannelProc devuelve NULL y registra un código de error POSIX que puede ser recuperado con Tcl_GetErrno. Además, si interp no es NULL, Tcl_FSOpenFileChannelProc deja un mensaje de error en el resultado de interp después de cualquier error.

El canal recién creado no debe ser registrado en el intérprete proporcionado por un Tcl_FSOpenFileChannelProc; esa tarea corresponde al llamador de Tcl_FSOpenFileChannel (si es necesario). Si uno de los canales estándar, stdin, stdout o stderr fue cerrado previamente, el acto de crear el nuevo canal también lo asigna como reemplazo del canal estándar.

MATCHINDIRECTORYPROC

Función para procesar una llamada a Tcl_FSMatchInDirectory. Si no se implementa, la funcionalidad de glob y copia recursiva faltará en el sistema de archivos (y esto puede afectar a comandos como encoding names que utilizan la funcionalidad de glob internamente).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La función debe devolver todos los archivos o directorios (u otros objetos del sistema de archivos) que coincidan con el patrón dado y concuerden con la especificación de types proporcionada. Hay dos maneras en las que esta función puede ser llamada. Si pattern es NULL, entonces pathPtr es una especificación de ruta completa de un solo archivo o directorio que debe ser verificado en cuanto a existencia y tipo correcto. De lo contrario, pathPtr es un directorio, cuyo contenido la función debe buscar para encontrar archivos o directorios que tengan el tipo correcto. En cualquier caso, se puede asumir que pathPtr no es NULL ni vacío. Actualmente no está documentado si pathPtr tendrá o no un separador de archivo al final, por lo que el código debe ser flexible a ambas posibilidades.

El valor de retorno es un resultado Tcl estándar que indica si ocurrió un error en el proceso de coincidencia. Los mensajes de error se colocan en interp, a menos que interp sea NULL, en cuyo caso no es necesario generar ningún mensaje de error; en un resultado TCL_OK, los resultados deben agregarse al valor de resultPtr proporcionado (que se puede asumir que es una lista Tcl válida y no compartida). Las coincidencias añadidas a resultPtr deben incluir cualquier prefijo de ruta dado en pathPtr (esto generalmente significa que serán especificaciones de ruta absolutas). Tenga en cuenta que si no se encuentran coincidencias, eso simplemente conduce a un resultado vacío; los errores solo se señalan para problemas reales de archivo o sistema de archivos que puedan ocurrir durante el proceso de coincidencia.

La estructura Tcl_GlobTypeData pasada en el parámetro types contiene los siguientes campos:

typedef struct Tcl_GlobTypeData {
    /* Corresponde a bcdpfls como en 'find -t' */
    int type;
    /* Corresponde a los permisos del archivo */
    int perm;
    /* Tipo de Mac aceptable */
    Tcl_Obj *macType;
    /* Creador de Mac aceptable */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Hay dos casos específicos que es importante manejar correctamente, ambos cuando types no es NULL. Los dos casos son cuando types->types & TCL_GLOB_TYPE_DIR o types->types & TCL_GLOB_TYPE_MOUNT son verdaderos (y en particular cuando las otras banderas son falsas). En el primero de estos casos, la función debe listar los directorios contenidos. Tcl utiliza esto para implementar el globbing recursivo, por lo que es fundamental que los sistemas de archivos implementen la coincidencia de directorios correctamente. En el segundo de estos casos, con TCL_GLOB_TYPE_MOUNT, el sistema de archivos debe listar los puntos de montaje que se encuentran dentro del pathPtr dado (y en este caso, pathPtr no necesita estar dentro del mismo sistema de archivos, a diferencia de todos los demás casos en los que se llama a esta función). El soporte para esto es crítico si Tcl quiere tener transiciones fluidas de un sistema de archivos a otro.

UTIMEPROC

Función para procesar una llamada a Tcl_FSUtime. Requerida para permitir el establecimiento (no la lectura) de tiempos con file mtime, file atime y la implementación open-r/open-w/fcopy de file copy.

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

Los tiempos de acceso y modificación del archivo especificado por pathPtr deben cambiarse a los valores dados en la estructura tval.

El valor de retorno debe ser 0 en caso de éxito y -1 en caso de error, al igual que con la llamada de sistema utime.

LINKPROC

Función para procesar una llamada a Tcl_FSLink. Solo debe implementarse si el sistema de archivos soporta enlaces, y de lo contrario puede ser NULL.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

Si toPtr es NULL, se le está pidiendo a la función que lea el contenido de un enlace. El resultado es un Tcl_Obj que especifica el contenido del enlace dado por linkNamePtr, o NULL si el enlace no pudo ser leído. El resultado es propiedad del llamador (y por lo tanto, su contador de referencias debe ser incrementado antes de ser devuelto). Cualquier llamador debe llamar a Tcl_DecrRefCount en este resultado cuando ya no sea necesario. Si toPtr no es NULL, la función debe intentar crear un enlace. El resultado en este caso debe ser toPtr si el enlace fue exitoso y NULL en caso contrario. En este caso, el resultado no es propiedad del llamador (es decir, no se necesitan manipulaciones del contador de referencias en ninguno de los extremos). Consulte la documentación de Tcl_FSLink para la interpretación correcta de las banderas linkAction.

LISTVOLUMESPROC

Función para listar cualquier volumen del sistema de archivos agregado por este sistema de archivos. Solo debe implementarse si el sistema de archivos agrega volúmenes al principio del sistema de archivos, para que puedan ser devueltos por file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

El resultado debe ser una lista de volúmenes agregados por este sistema de archivos, o NULL (o una lista vacía) si no se proporcionan volúmenes. El valor del resultado se considera propiedad del sistema de archivos (no del núcleo de Tcl), pero se le debe dar un contador de referencias para Tcl. Tcl usará el contenido de la lista y luego decrementará ese contador de referencias. Esto permite a los sistemas de archivos elegir si realmente quieren retener una lista "global" de volúmenes o no (si no, generan la lista sobre la marcha y la pasan a Tcl con un contador de referencias de 1 y luego se olvidan de la lista; si sí, simplemente incrementan el contador de referencias de su lista global y la pasan a Tcl, que copiará el contenido y luego decrementará el contador de vuelta a donde estaba).

Por lo tanto, Tcl considera que los valores de retorno de este proc son de solo lectura.

FILEATTRSTRINGSPROC

Función para listar todas las cadenas de atributos que son válidas para este sistema de archivos. Si no se implementa, el sistema de archivos no soportará el comando file attributes. Esto permite adjuntar información adicional arbitraria a los archivos en el sistema de archivos. Si no se implementa, no es necesario implementar los métodos get y set.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

La función llamada puede devolver un array de cadenas o puede devolver NULL y colocar una lista Tcl en objPtrRef. Tcl tomará esa lista e incrementará su contador de referencias antes de usarla. Al completar ese uso, Tcl decrementará su contador de referencias. Por lo tanto, si la lista debe ser descartada por Tcl cuando termine, debe tener un contador de referencias de cero, y si la lista no debe ser descartada, el sistema de archivos debe asegurarse de devolver un valor con un contador de referencias de al menos uno.

FILEATTRSGETPROC

Función para procesar una llamada a Tcl_FSFileAttrsGet, utilizada por file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

Devuelve un código de retorno estándar de Tcl. El valor del atributo recuperado, que corresponde al elemento de índice index en la lista devuelta por Tcl_FSFileAttrStringsProc, es un Tcl_Obj colocado en objPtrRef (si se devolvió TCL_OK) y es probable que tenga un contador de referencias de cero. En cualquier caso, debemos almacenarlo en algún lugar (por ejemplo, el resultado de Tcl) o incrementar/decrementar su contador de referencias para asegurar que se libere correctamente.

FILEATTRSSETPROC

Función para procesar una llamada a Tcl_FSFileAttrsSet, utilizada por file attributes. Si el sistema de archivos es de solo lectura, no es necesario implementarlo.

typedef int Tcl_FSFileAttrsSetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj *objPtr);

El valor del atributo del elemento de índice index en la lista devuelta por Tcl_FSFileAttrStringsProc debe establecerse en el objPtr proporcionado.

CREARDIRECTORIOPROC

Función para procesar una llamada a Tcl_FSCreateDirectory. Debe implementarse a menos que el sistema de archivos sea de solo lectura.

typedef int Tcl_FSCreateDirectoryProc(
        Tcl_Obj *pathPtr);

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso. Si tiene éxito, se debería haber agregado un nuevo directorio al sistema de archivos en la ubicación especificada por pathPtr.

REMOVEDIRECTORYPROC

Función para procesar una llamada a Tcl_FSRemoveDirectory. Debe implementarse a menos que el sistema de archivos sea de solo lectura.

typedef int Tcl_FSRemoveDirectoryProc(
        Tcl_Obj *pathPtr,
        int recursive,
        Tcl_Obj **errorPtr);

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso. Si tiene éxito, el directorio especificado por pathPtr debería haber sido eliminado del sistema de archivos. Si se proporciona el indicador recursive, entonces un directorio no vacío debe ser eliminado sin error. Si este indicador no se proporciona, y el directorio está no vacío, se debe señalar un error POSIX "EEXIST". Si ocurre un error, el nombre del archivo o directorio que causó el error debe colocarse en errorPtr.

DELETEFILEPROC

Función para procesar una llamada a Tcl_FSDeleteFile. Debe implementarse a menos que el sistema de archivos sea de solo lectura.

typedef int Tcl_FSDeleteFileProc(
        Tcl_Obj *pathPtr);

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso. Si tiene éxito, el archivo especificado por pathPtr debería haber sido eliminado del sistema de archivos. Tenga en cuenta que, si el sistema de archivos admite enlaces simbólicos, Tcl siempre llamará a esta función y no a Tcl_FSRemoveDirectoryProc cuando sea necesario eliminarlos (incluso si son enlaces simbólicos a directorios).

EFICIENCIA DEL SISTEMA DE ARCHIVOS

Estas funciones no necesitan ser implementadas para un sistema de archivos particular, ya que el núcleo tiene una implementación de respaldo disponible. Consulte la descripción individual para conocer las consecuencias de dejar el campo en NULL.

LSTATPROC

Función para procesar una llamada a Tcl_FSLstat. Si no se implementa, Tcl intentará usar el statProc definido anteriormente. Por lo tanto, solo necesita implementarse si un sistema de archivos puede diferenciar entre las llamadas stat y lstat.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

El comportamiento de esta función es muy similar al de Tcl_FSStatProc definido anteriormente, excepto que si se aplica a un enlace simbólico, devuelve información sobre el enlace, no sobre el archivo de destino.

COPYFILEPROC

Función para procesar una llamada a Tcl_FSCopyFile. Si no se implementa, Tcl recurrirá a open-r, open-w y fcopy como mecanismo de copia. Por lo tanto, solo necesita implementarse si el sistema de archivos puede realizar esa acción de manera más eficiente.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso de copia. Tenga en cuenta que destPathPtr es el nombre del archivo que se convertirá en la copia de srcPathPtr. Nunca es el nombre de un directorio en el que se pueda copiar srcPathPtr (es decir, la función es mucho más simple que el subcomando file copy a nivel de Tcl). Tenga en cuenta que, si el sistema de archivos admite enlaces simbólicos, Tcl siempre llamará a esta función y no a copyDirectoryProc cuando sea necesario copiarlos (incluso si son enlaces simbólicos a directorios). Finalmente, si el sistema de archivos determina que no puede admitir la acción file copy, llamar a Tcl_SetErrno(EXDEV) y devolver un resultado que no sea TCL_OK le indicará a Tcl que utilice sus mecanismos de respaldo estándar.

RENAMEFILEPROC

Función para procesar una llamada a Tcl_FSRenameFile. Si no se implementa, Tcl recurrirá a un mecanismo de copia y eliminación. Por lo tanto, solo necesita implementarse si el sistema de archivos puede realizar esa acción de manera más eficiente.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso de renombramiento. Si el sistema de archivos determina que no puede admitir la acción file rename, llamar a Tcl_SetErrno(EXDEV) y devolver un resultado que no sea TCL_OK le indicará a Tcl que utilice sus mecanismos de respaldo estándar.

COPYDIRECTORYPROC

Función para procesar una llamada a Tcl_FSCopyDirectory. Si no se implementa, Tcl recurrirá a un mecanismo recursivo de file mkdir, file copy. Por lo tanto, solo necesita implementarse si el sistema de archivos puede realizar esa acción de manera más eficiente.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso de copia. Si ocurre un error, el nombre del archivo o directorio que causó el error debe colocarse en errorPtr. Tenga en cuenta que destPathPtr es el nombre del directorio que se convertirá en la imagen especular de srcPathPtr. No es el nombre de un directorio en el que se pueda copiar srcPathPtr (es decir, la función es mucho más simple que el subcomando file copy a nivel de Tcl). Finalmente, si el sistema de archivos determina que no puede admitir la acción de copia de directorios, llamar a Tcl_SetErrno(EXDEV) y devolver un resultado que no sea TCL_OK le indicará a Tcl que utilice sus mecanismos de respaldo estándar.

LOADFILEPROC

Función para procesar una llamada a Tcl_FSLoadFile. Si no se implementa, Tcl recurrirá a una copia a un archivo temporal nativo seguida de un Tcl_FSLoadFile en esa copia temporal. Por lo tanto, solo necesita implementarse si el sistema de archivos puede cargar código directamente, o si se puede implementar simplemente para devolver TCL_ERROR para deshabilitar la funcionalidad de carga en este sistema de archivos por completo.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Devuelve un código de finalización estándar de Tcl. Si ocurre un error, se deja un mensaje de error en el resultado del interp. La función carga dinámicamente un archivo de código binario en memoria. En una carga exitosa, handlePtr se debe completar con un token para el archivo cargado dinámicamente, y unloadProcPtr se debe completar con la dirección de un procedimiento. El procedimiento de descarga se llamará con el Tcl_LoadHandle dado como su único parámetro cuando Tcl necesite descargar el archivo. Por ejemplo, para el sistema de archivos nativo, el Tcl_LoadHandle devuelto es actualmente un token que se puede usar en el TclpFindSymbol privado para acceder a funciones en el nuevo código. Cada sistema de archivos es libre de definir el Tcl_LoadHandle según lo requiera. Finalmente, si el sistema de archivos determina que no puede admitir la acción de carga de archivos, llamar a Tcl_SetErrno(EXDEV) y devolver un resultado que no sea TCL_OK le indicará a Tcl que utilice sus mecanismos de respaldo estándar.

UNLOADFILEPROC

Función para descargar un archivo previamente cargado con éxito. Si se implementó la carga, entonces esta también debería implementarse, si hay alguna acción de limpieza requerida.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

Función para procesar una llamada a Tcl_FSGetCwd. La mayoría de los sistemas de archivos no necesitan implementar esto. Generalmente solo se llamará una vez, si se llama a getcwd antes de chdir. Puede ser NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

Si el sistema de archivos admite una noción nativa de directorio de trabajo actual (que podría cambiar independientemente de Tcl), esta función debería devolver ese directorio de trabajo actual como resultado, o NULL si no se pudo determinar el directorio actual (por ejemplo, el usuario no tiene los permisos apropiados en el directorio actual). Si se devuelve NULL, se deja un mensaje de error en el resultado del interp.

CHDIRPROC

Función para procesar una llamada a Tcl_FSChdir. Si los sistemas de archivos no implementan esto, se emulará mediante una serie de comprobaciones de acceso a directorios. De lo contrario, los sistemas de archivos virtuales que lo implementen solo necesitan responder con un resultado de retorno positivo si pathPtr es un directorio válido y accesible en su sistema de archivos. No necesitan recordar el resultado, ya que este se recordará automáticamente para su uso por Tcl_FSGetCwd. Los sistemas de archivos reales deben llevar a cabo la acción correcta (es decir, llamar a la API de sistema chdir correcta).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

El Tcl_FSChdirProc cambia el directorio de trabajo actual de la aplicación al valor especificado en pathPtr. La función devuelve -1 si hay un error o 0 si tiene éxito.
