ARGUMENTOS

Tcl_EventSetupProc *setupProc (entrada)
Procedimiento a invocar para preparar la espera de eventos en Tcl_DoOneEvent.
Tcl_EventCheckProc *checkProc (entrada)
Procedimiento para que Tcl_DoOneEvent lo invoque después de esperar eventos. Comprueba si se han producido eventos y, si es así, los pone en cola.
ClientData clientData (entrada)
Valor arbitrario de una palabra para pasar a setupProc, checkProc o deleteProc.
const Tcl_Time *timePtr (entrada)
Indica la cantidad máxima de tiempo a esperar por un evento. Esto se especifica como un intervalo (cuánto esperar), no como un tiempo absoluto (cuándo despertar). Si el puntero pasado a Tcl_WaitForEvent es NULL, significa que no hay tiempo máximo de espera: esperar para siempre si es necesario.
Tcl_Event *evPtr (entrada)
Un evento para añadir a la cola de eventos. El espacio para el evento debe haber sido asignado por el llamante usando Tcl_Alloc o ckalloc.
Tcl_QueuePosition position (entrada)
Dónde añadir el nuevo evento en la cola: TCL_QUEUE_TAIL, TCL_QUEUE_HEAD o TCL_QUEUE_MARK.
Tcl_ThreadId threadId (entrada)
Un identificador único para un hilo.
Tcl_EventDeleteProc *deleteProc (entrada)
Procedimiento a invocar para cada evento en cola en Tcl_DeleteEvents.
int flags (entrada)
Qué tipos de eventos atender. Estas banderas son las mismas que las pasadas a Tcl_DoOneEvent.
int mode (entrada)
Indica si los eventos deben ser atendidos por Tcl_ServiceAll. Debe ser uno de TCL_SERVICE_NONE o TCL_SERVICE_ALL.
Tcl_NotifierProcs* notifierProcPtr (entrada)
Estructura de punteros de función que describe los procedimientos del notificador que se van a reemplazar por los instalados en el ejecutable. Consulte REEMPLAZO DEL NOTIFICADOR para obtener más detalles.

INTRODUCCIÓN

Las interfaces descritas aquí se utilizan para personalizar el bucle de eventos de Tcl. Las dos personalizaciones más comunes son añadir nuevas fuentes de eventos y fusionar el bucle de eventos de Tcl con algún otro bucle de eventos, como uno proporcionado por una aplicación en la que Tcl está incrustado. Cada una de estas tareas se describe en una sección separada a continuación.

Los procedimientos de esta entrada del manual son los bloques de construcción con los que se construye el notificador de eventos de Tcl. El notificador de eventos es la capa más baja en el mecanismo de eventos de Tcl. Consta de tres cosas:

[1]
Fuentes de eventos: estas representan las formas en que se pueden generar eventos. Por ejemplo, existe una fuente de eventos de temporizador que implementa el procedimiento Tcl_CreateTimerHandler y el comando after, y existe una fuente de eventos de archivo que implementa el procedimiento Tcl_CreateFileHandler en sistemas Unix. Una fuente de eventos debe trabajar con el notificador para detectar eventos en los momentos adecuados, registrarlos en la cola de eventos y, finalmente, notificar al software de nivel superior que han ocurrido. Los procedimientos Tcl_CreateEventSource, Tcl_DeleteEventSource y Tcl_SetMaxBlockTime, Tcl_QueueEvent, y Tcl_DeleteEvents son utilizados principalmente por las fuentes de eventos.
[2]
La cola de eventos: para aplicaciones sin hilos, existe una única cola para toda la aplicación, que contiene eventos que han sido detectados pero aún no atendidos. Las fuentes de eventos colocan eventos en la cola para que puedan procesarse en orden en momentos apropiados durante el bucle de eventos. La cola de eventos garantiza una disciplina justa de manejo de eventos, de modo que ninguna fuente de eventos pueda dejar en ayunas a las demás. También permite que los eventos se guarden para ser atendidos en un momento futuro. Las aplicaciones con hilos funcionan de manera similar, excepto que existe una cola de eventos separada para cada hilo que contiene un intérprete de Tcl. Tcl_QueueEvent se utiliza (principalmente por las fuentes de eventos) para añadir eventos a la cola de eventos y Tcl_DeleteEvents se utiliza para eliminar eventos de la cola sin procesarlos. En una aplicación con hilos, Tcl_QueueEvent añade un evento a la cola del hilo actual, y Tcl_ThreadQueueEvent añade un evento a una cola en un hilo específico.
[3]
El bucle de eventos: para detectar y procesar eventos, la aplicación entra en un bucle que espera a que ocurran eventos, los coloca en la cola de eventos y luego los procesa. La mayoría de las aplicaciones harán esto llamando al procedimiento Tcl_DoOneEvent, que se describe en una entrada de manual separada.

La mayoría de las aplicaciones de Tcl no necesitan preocuparse por ninguno de los detalles internos del notificador de Tcl. Sin embargo, el notificador ahora tiene suficiente flexibilidad para ser redirigido ya sea para una nueva plataforma o para usar un bucle de eventos externo (como el bucle de eventos de Motif, cuando Tcl está incrustado en una aplicación de Motif). Los procedimientos Tcl_WaitForEvent y Tcl_SetTimer son normalmente implementados por Tcl, pero pueden ser reemplazados con nuevas versiones para redirigir el notificador (los procedimientos Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_Sleep, Tcl_CreateFileHandler, y Tcl_DeleteFileHandler también deben ser reemplazados; consulte CREACIÓN DE UN NUEVO NOTIFICADOR a continuación para obtener detalles). Los procedimientos Tcl_ServiceAll, Tcl_ServiceEvent, Tcl_GetServiceMode, y Tcl_SetServiceMode se proporcionan para ayudar a conectar el bucle de eventos de Tcl con un bucle de eventos externo como el de Motif.

BASES DEL NOTIFICADOR

La forma más fácil de entender cómo funciona el notificador es considerar lo que sucede cuando se llama a Tcl_DoOneEvent. A Tcl_DoOneEvent se le pasa un argumento flags que indica qué tipo de eventos están permitidos procesar y también si debe bloquearse o no si no hay eventos listos. Tcl_DoOneEvent realiza las siguientes acciones:

[1]
Comprueba la cola de eventos para ver si contiene algún evento que pueda ser atendido. Si es así, atiende el primer evento posible, lo elimina de la cola y regresa. Hace esto llamando a Tcl_ServiceEvent y pasándole el argumento flags.
[2]
Prepara para bloquear por un evento. Para hacer esto, Tcl_DoOneEvent invoca un procedimiento setup en cada fuente de eventos. La fuente de eventos realizará inicializaciones específicas de la fuente de eventos y posiblemente llamará a Tcl_SetMaxBlockTime para limitar cuánto tiempo bloqueará Tcl_WaitForEvent si no ocurren nuevos eventos.
[3]
Llama a Tcl_WaitForEvent. Este procedimiento se implementa de manera diferente en diferentes plataformas; espera a que ocurra un evento, basado en la información proporcionada por las fuentes de eventos. Puede hacer que la aplicación se bloquee si timePtr especifica un intervalo distinto de 0. Tcl_WaitForEvent regresa cuando algo ha sucedido, como que un archivo se vuelva legible o que el intervalo dado por timePtr expire. Si no hay eventos para que Tcl_WaitForEvent espere, de modo que se bloquearía para siempre, entonces regresa inmediatamente y Tcl_DoOneEvent regresa 0.
[4]
Llama a un procedimiento check en cada fuente de eventos. El procedimiento check determina si ocurrieron eventos de interés para esta fuente. Si es así, los eventos se añaden a la cola de eventos.

Tcl_DeleteEventSource elimina una fuente de eventos. Los argumentos setupProc, checkProc y clientData deben coincidir exactamente con aquellos proporcionados por Tcl_CreateEventSource para que la fuente de eventos sea eliminada. Si dicha fuente no existe, Tcl_DeleteEventSource no tendrá ningún efecto.

Tcl_InitNotifier inicializa el estado del notificador y devuelve un identificador al estado del notificador. Tcl llama a este procedimiento al inicializar un intérprete Tcl. De manera similar, Tcl_FinalizeNotifier desactiva el notificador, y es llamado por Tcl_Finalize cuando se finaliza un intérprete Tcl.

Tcl_WaitForEvent es el procedimiento de nivel más bajo del notificador; es responsable de esperar un "evento interesante" o el paso de un tiempo determinado. Antes de que se invoque Tcl_WaitForEvent, cada uno de los procedimientos de fuentes de eventos habrá sido invocado. El argumento timePtr de Tcl_WaitForEvent indica el tiempo máximo de bloqueo para un evento, basado en las llamadas a Tcl_SetMaxBlockTime realizadas por los procedimientos de configuración y otra información (como el bit TCL_DONT_WAIT en flags).

Idealmente, Tcl_WaitForEvent solo debería esperar un evento; no debería procesar el evento de ninguna manera. Luego, las fuentes de eventos procesarán los eventos brutos y crearán Tcl_Events en la cola de eventos en sus procedimientos checkProc. Sin embargo, en algunos sistemas (como Windows), esto no es posible; los eventos pueden procesarse en Tcl_WaitForEvent, incluida la cola de Tcl_Events y más (por ejemplo, se pueden invocar callbacks para widgets nativos). El valor de retorno de Tcl_WaitForEvent debe ser 0, 1 o -1. En sistemas como Windows donde los eventos se procesan en Tcl_WaitForEvent, un valor de retorno de 1 significa que podría haber más eventos pendientes sin procesar. Esto es un indicador para el llamador de que debe llamar a Tcl_WaitForEvent nuevamente para procesar todos los eventos pendientes. Un retorno de 0 significa que llamar a Tcl_WaitForEvent nuevamente no tendrá ningún efecto: puede ser un sistema donde Tcl_WaitForEvent solo espera y no procesa eventos, o Tcl_WaitForEvent sabe con certeza que no hay más eventos pendientes (por ejemplo, el tiempo ha pasado). Finalmente, un retorno de -1 significa que el bucle de eventos ya no es operativo y la aplicación debería detenerse. En Windows, esto ocurre cuando se recibe un mensaje WM_QUIT; en Unix, cuando Tcl_WaitForEvent esperaría indefinidamente porque no había fuentes de eventos activas y el tiempo de espera era infinito).

Tcl_AlertNotifier se utiliza en aplicaciones multihilo para permitir que cualquier hilo "despierte" al notificador para alertarlo sobre nuevos eventos en su cola. Tcl_AlertNotifier requiere como argumento el identificador del notificador devuelto por Tcl_InitNotifier.

Si el notificador se utilizará con una fuente de eventos externa, también debe admitir la interfaz de Tcl_SetTimer. Tcl_SetTimer es invocado por Tcl_SetMaxBlockTime cuando se ha reducido el tiempo máximo de bloqueo. Tcl_SetTimer debe organizar que el bucle de eventos externo invoque Tcl_ServiceAll después del intervalo especificado, incluso si no ha ocurrido ningún evento. Esta interfaz es necesaria porque Tcl_WaitForEvent no se invoca cuando hay un bucle de eventos externo. Si el notificador solo se utilizará desde Tcl_DoOneEvent, Tcl_SetTimer no debe hacer nada.

Tcl_ServiceModeHook es llamado por la parte independiente del notificador cuando el código del cliente llama a Tcl_SetServiceMode. Esta pista se proporciona para admitir sistemas operativos que requieren un manejo especial de eventos cuando la aplicación está en un bucle modal (el notificador de Windows, por ejemplo, usa esta pista para crear una ventana de comunicación).

En sistemas Unix, la fuente de eventos de archivo también necesita soporte del notificador. La fuente de eventos de archivo consta de los procedimientos Tcl_CreateFileHandler y Tcl_DeleteFileHandler, que se describen en la página del manual de Tcl_CreateFileHandler.

Las interfaces de Tcl_Sleep y Tcl_DoOneEvent se describen en sus respectivas páginas del manual.

La forma más fácil de crear un nuevo notificador es observar el código de un notificador existente, como en los archivos unix/tclUnixNotfy.c o win/tclWinNotify.c en la distribución del código fuente de Tcl.

REEMPLAZANDO EL NOTIFICADOR

Un notificador escrito según las convenciones anteriores también puede instalarse en un proceso en ejecución en lugar del notificador estándar. Esta mecánica se utiliza para que un único ejecutable se utilice (con el notificador estándar) como un programa independiente y se recuerde (con un notificador reemplazado en una extensión cargable) como una extensión de otro programa, como un plugin de navegador web.

Para hacer esto, la extensión llama a Tcl_SetNotifier pasando un puntero a una estructura de datos Tcl_NotifierProcs. La estructura tiene la siguiente disposición:

typedef struct Tcl_NotifierProcs {
    Tcl_SetTimerProc *setTimerProc;
    Tcl_WaitForEventProc *waitForEventProc;
    Tcl_CreateFileHandlerProc *createFileHandlerProc;
    Tcl_DeleteFileHandlerProc *deleteFileHandlerProc;
    Tcl_InitNotifierProc *initNotifierProc;
    Tcl_FinalizeNotifierProc *finalizeNotifierProc;
    Tcl_AlertNotifierProc *alertNotifierProc;
    Tcl_ServiceModeHookProc *serviceModeHookProc;
} Tcl_NotifierProcs;

Después de la llamada a Tcl_SetNotifier, los puntos de conexión dados en la estructura Tcl_NotifierProcs reemplazan lo que se había instalado previamente en el proceso.

Es extraordinariamente inadecuado reemplazar un notificador en ejecución. Normalmente, Tcl_SetNotifier debe llamarse antes de la primera llamada a Tcl_InitNotifier.

BUCLES DE EVENTOS EXTERNOS

Las interfaces del notificador están diseñadas para que Tcl pueda integrarse en aplicaciones que tengan sus propios bucles de eventos privados. En este caso, la aplicación no llama a Tcl_DoOneEvent excepto en casos de bucles de eventos recursivos, como llamadas a comandos de Tcl como update o vwait. La mayor parte del tiempo se dedica al bucle de eventos externo de la aplicación. En este caso, el notificador debe organizar que el bucle de eventos externo llame de nuevo a Tcl cuando ocurra un evento en las diversas fuentes de eventos de Tcl. Estas callbacks deben organizar que los eventos de Tcl apropiados se coloquen en la cola de eventos de Tcl.

Dado que el bucle de eventos externo no llama a Tcl_DoOneEvent de manera regular, es responsabilidad del notificador organizar la invocación de Tcl_ServiceEvent cada vez que haya eventos pendientes en la cola de eventos de Tcl. La forma más fácil de hacer esto es invocar Tcl_ServiceAll al final de cada callback del bucle de eventos externo. Esto asegurará que todas las fuentes de eventos se consulten, que los eventos en cola se atiendan y que los manejadores inactivos pendientes se procesen antes de devolver el control a la aplicación. Además, las fuentes de eventos que necesitan consultar eventos pueden invocar Tcl_SetMaxBlockTime para forzar al bucle de eventos externo a invocar Tcl incluso si no hay eventos disponibles en la cola de eventos del sistema.

Como consecuencia de procesar eventos detectados en el bucle de eventos externo principal, Tcl puede invocar Tcl_DoOneEvent para iniciar un bucle de eventos recursivo en comandos como vwait. Tcl_DoOneEvent invocará el bucle de eventos externo, lo que resultará en callbacks como se describe en el párrafo anterior, lo que a su vez resultará en llamadas a Tcl_ServiceAll. Sin embargo, en estos casos, es deseable no servir eventos en Tcl_ServiceAll. Servir eventos allí es innecesario porque el control se devolverá inmediatamente al bucle de eventos externo y, por lo tanto, a Tcl_DoOneEvent, que puede servir los eventos por sí mismo. Además, Tcl_DoOneEvent está diseñado para servir solo un evento, mientras que Tcl_ServiceAll normalmente servirá todos los eventos pendientes. Para manejar esta situación, Tcl_DoOneEvent establece una bandera para Tcl_ServiceAll que hace que devuelva sin servir ningún evento. Esta bandera se llama el modo de servicio; Tcl_DoOneEvent la restaura a su valor anterior antes de devolver el control. Por el contrario, si el notificador se va a utilizar desde una aplicación incrustada, Tcl_DoOneEvent establecerá el modo de servicio en TCL_SERVICE_ALL para que Tcl_ServiceAll realmente sirva eventos.

Sin embargo, en algunos casos, puede ser necesario que Tcl_ServiceAll sirva eventos incluso cuando se ha invocado directamente por Tcl_DoOneEvent. Esto ocurre cuando se invoca otro bucle de eventos recursivo a través de un manejador de eventos llamado por Tcl_DoOneEvent (como uno que forma parte de un widget nativo). En este caso, Tcl_DoOneEvent podría no tener la oportunidad de servir eventos, por lo que Tcl_ServiceAll debe servirlos todos. Cualquier bucle de eventos recursivo que llame a un bucle de eventos externo en lugar de Tcl_DoOneEvent debe restablecer el modo de servicio para que todos los eventos se procesen en Tcl_ServiceAll. Esto se logra invocando la función Tcl_SetServiceMode. Si se pasa TCL_SERVICE_NONE a Tcl_SetServiceMode, las llamadas a Tcl_ServiceAll devolverán inmediatamente sin procesar ningún evento. Si se pasa TCL_SERVICE_ALL a Tcl_SetServiceMode, las llamadas a Tcl_ServiceAll actuarán normalmente. Tcl_SetServiceMode devuelve el valor anterior del modo de servicio, que debe restaurarse al salir del bucle de eventos recursivo. Tcl_GetServiceMode devuelve el valor actual del modo de servicio.

INTRODUCTION

El bucle de eventos de Tcl puede ser configurado para invocar procedimientos de callback después de un cierto período de tiempo. Esto se implementa a través de temporizadores. Los temporizadores son una forma de gestionar el tiempo en Tcl, similar a cómo Tcl puede gestionar eventos de entrada/salida y eventos de "idle" (inactividad).

NOTIFIER BASICS

El sistema de notificación de Tcl es responsable de gestionar los diferentes tipos de eventos que pueden ocurrir en una aplicación Tcl. Estos eventos incluyen:

  • Eventos de entrada/salida de archivos (lectura, escritura, error en un canal).
  • Eventos de temporizador (un cierto tiempo ha transcurrido).
  • Eventos de inactividad (la aplicación no tiene nada que hacer actualmente).
  • Eventos de modo de servicio (utilizados internamente por Tcl).

Estos eventos son puestos en una cola de eventos y procesados por el bucle de eventos principal de Tcl. El sistema de notificación permite a los desarrolladores registrar sus propios manejadores para estos eventos, o incluso añadir nuevas fuentes de eventos.

CREATING A NEW EVENT SOURCE

Se pueden añadir nuevas fuentes de eventos al sistema de notificación de Tcl. Esto permite que la aplicación reaccione a eventos que no son gestionados directamente por Tcl, como eventos de red personalizados o eventos de hardware. Esto generalmente implica la creación de un nuevo objeto que se integra con el sistema de notificación.

CREATING A NEW NOTIFIER

El "notifier" es el componente central del bucle de eventos de Tcl. Es responsable de esperar los eventos y despacharlos a los manejadores apropiados. Tcl proporciona un notifier por defecto, pero es posible reemplazarlo con una implementación personalizada si se necesitan funcionalidades específicas o una integración con un bucle de eventos existente.

REPLACING THE NOTIFIER

Para reemplazar el notifier por defecto, se debe proporcionar una nueva implementación que cumpla con la interfaz requerida por Tcl. Esto permite un control más fino sobre cómo Tcl maneja los eventos y puede ser útil en entornos integrados o cuando se utilizan bibliotecas de terceros con sus propios bucles de eventos.

EXTERNAL EVENT LOOPS

Tcl puede integrarse con bucles de eventos externos. En lugar de que Tcl ejecute su propio bucle de eventos principal, puede interactuar con un bucle de eventos existente (por ejemplo, de una GUI toolkit como Tk, o una biblioteca de red). Esto permite que la lógica de Tcl se ejecute dentro de un contexto de evento más amplio.
