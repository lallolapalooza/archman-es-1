DESCRIPTION

There are several reasons for calling the Tcl_FS API functions (e.g. Tcl_FSAccess and Tcl_FSStat) rather than calling system level functions like access and stat directly. First, they will work cross-platform, so an extension which calls them should work unmodified on Unix and Windows. Second, the Windows implementation of some of these functions fixes some bugs in the system level calls. Third, these function calls deal with any “Utf to platform-native” path conversions which may be required (and may cache the results of such conversions for greater efficiency on subsequent calls). Fourth, and perhaps most importantly, all of these functions are “virtual filesystem aware”. Any virtual filesystem (VFS for short) which has been registered (through Tcl_FSRegister) may reroute file access to alternative media or access methods. This means that all of these functions (and therefore the corresponding file, glob, pwd, cd, open, etc. Tcl commands) may be operate on “files” which are not native files in the native filesystem. This also means that any Tcl extension which accesses the filesystem (FS for short) through this API is automatically “virtual filesystem aware”. Of course, if an extension accesses the native filesystem directly (through platform-specific APIs, for example), then Tcl cannot intercept such calls.

If appropriate VFSes have been registered, the “files” may, to give two examples, be remote (e.g. situated on a remote ftp server) or archived (e.g. lying inside a .zip archive). Such registered filesystems provide a lookup table of functions to implement all or some of the functionality listed here. Finally, the Tcl_FSStat and Tcl_FSLstat calls abstract away from what the “struct stat” buffer is actually declared to be, allowing the same code to be used both on systems with and systems without support for files larger than 2GB in size.

The Tcl_FS API is Tcl_Obj-ified and may cache internal representations and other path-related strings (e.g. the current working directory). One side-effect of this is that one must not pass in values with a reference count of zero to any of these functions. If such calls were handled, they might result in memory leaks (under some circumstances, the filesystem code may wish to retain a reference to the passed in value, and so one must not assume that after any of these calls return, the value still has a reference count of zero - it may have been incremented) or in a direct segmentation fault (or other memory access error) due to the value being freed part way through the complex value manipulation required to ensure that the path is fully normalized and absolute for filesystem determination. The practical lesson to learn from this is that

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

is wrong, and may cause memory errors. The path must have its reference count incremented before passing it in, or decrementing it. For this reason, values with a reference count of zero are considered not to be valid filesystem paths and calling any Tcl_FS API function with such a value will result in no action being taken.

FS API FUNCTIONS

Tcl_FSCopyFile attempts to copy the file given by srcPathPtr to the path name given by destPathPtr. If the two paths given lie in the same filesystem (according to Tcl_FSGetFileSystemForPath) then that filesystem's “copy file” function is called (if it is non-NULL). Otherwise the function returns -1 and sets the errno global C variable to the “EXDEV” POSIX error code (which signifies a “cross-domain link”).

Tcl_FSCopyDirectory attempts to copy the directory given by srcPathPtr to the path name given by destPathPtr. If the two paths given lie in the same filesystem (according to Tcl_FSGetFileSystemForPath) then that filesystem's “copy file” function is called (if it is non-NULL). Otherwise the function returns -1 and sets the errno global C variable to the “EXDEV” POSIX error code (which signifies a “cross-domain link”).

Tcl_FSCreateDirectory attempts to create the directory given by pathPtr by calling the owning filesystem's “create directory” function.

Tcl_FSDeleteFile attempts to delete the file given by pathPtr by calling the owning filesystem's “delete file” function.

Tcl_FSRemoveDirectory attempts to remove the directory given by pathPtr by calling the owning filesystem's “remove directory” function.

Tcl_FSRenameFile attempts to rename the file or directory given by srcPathPtr to the path name given by destPathPtr. If the two paths given lie in the same filesystem (according to Tcl_FSGetFileSystemForPath) then that filesystem's “rename file” function is called (if it is non-NULL). Otherwise the function returns -1 and sets the errno global C variable to the “EXDEV” POSIX error code (which signifies a “cross-domain link”).

Tcl_FSListVolumes calls each filesystem which has a non-NULL “list volumes” function and asks them to return their list of root volumes. It accumulates the return values in a list which is returned to the caller (with a reference count of 0).

Tcl_FSEvalFileEx reads the file given by pathPtr using the encoding identified by encodingName and evaluates its contents as a Tcl script. It returns the same information as Tcl_EvalObjEx. If encodingName is NULL, the system encoding is used for reading the file contents. If the file could not be read then a Tcl error is returned to describe why the file could not be read. The eofchar for files is “\x1A” (^Z) for all platforms. If you require a “^Z” in code for string comparison, you can use “\x1A”, which will be safely substituted by the Tcl interpreter into “^Z”. Tcl_FSEvalFile is a simpler version of Tcl_FSEvalFileEx that always uses the system encoding when reading the file.

Tcl_FSLoadFile dynamically loads a binary code file into memory and returns the addresses of two procedures within that file, if they are defined. The appropriate function for the filesystem to which pathPtr belongs will be called. If that filesystem does not implement this function (most virtual filesystems will not, because of OS limitations in dynamically loading binary code), Tcl will attempt to copy the file to a temporary directory and load that temporary file. Tcl_FSUnloadFile reverses the operation, asking for the library indicated by the loadHandle to be removed from the process. Note that, unlike with the unload command, this does not give the library any opportunity to clean up.

Both the above functions return a standard Tcl completion code. If an error occurs, an error message is left in the interp's result.

The token provided via the variable indicated by loadHandlePtr may be used with Tcl_FindSymbol.

Tcl_FSMatchInDirectory is used by the globbing code to search a directory for all files which match a given pattern. The appropriate function for the filesystem to which pathPtr belongs will be called.

The return value is a standard Tcl result indicating whether an error occurred in globbing. Error messages are placed in interp (unless interp is NULL, which is allowed), but good results are placed in the resultPtr given.

Note that the glob code implements recursive patterns internally, so this function will only ever be passed simple patterns, which can be matched using the logic of string match. To handle recursion, Tcl will call this function frequently asking only for directories to be returned. A special case of being called with a NULL pattern indicates that the path needs to be checked only for the correct type.

Tcl_FSLink replaces the library version of readlink, and extends it to support the creation of links. The appropriate function for the filesystem to which linkNamePtr belongs will be called.

If the toPtr is NULL, a “read link” action is performed. The result is a Tcl_Obj specifying the contents of the symbolic link given by linkNamePtr, or NULL if the link could not be read. The result is owned by the caller, which should call Tcl_DecrRefCount when the result is no longer needed. If the toPtr is not NULL, Tcl should create a link of one of the types passed in in the linkAction flag. This flag is an OR'ed combination of TCL_CREATE_SYMBOLIC_LINK and TCL_CREATE_HARD_LINK. Where a choice exists (i.e. more than one flag is passed in), the Tcl convention is to prefer symbolic links. When a link is successfully created, the return value should be toPtr (which is therefore already owned by the caller). If unsuccessful, NULL is returned.

Tcl_FSLstat fills the Tcl_StatBuf structure statPtr with information about the specified file. You do not need any access rights to the file to get this information but you need search rights to all directories named in the path leading to the file. The Tcl_StatBuf structure includes info regarding device, inode (always 0 on Windows), privilege mode, nlink (always 1 on Windows), user id (always 0 on Windows), group id (always 0 on Windows), rdev (same as device on Windows), size, last acce

ss time, hora de última modificación y hora de último cambio de metadatos. Consulte la API PORTABLE STAT RESULT para obtener una descripción sobre cómo escribir código portable para asignar y acceder a la estructura Tcl_StatBuf.

Si path existe, Tcl_FSLstat devuelve 0 y la estructura stat se rellena con datos. De lo contrario, se devuelve -1 y no se proporciona información de stat.

Tcl_FSUtime reemplaza la versión de biblioteca de utime.

Esto devuelve 0 en caso de éxito y -1 en caso de error (según la documentación de utime). Si tiene éxito, la función actualizará los valores de "atime" y "mtime" del archivo proporcionado.

Tcl_FSFileAttrsGet implementa el acceso de lectura para el subcomando file attributes que se puede enganchar. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

Si el resultado es TCL_OK, entonces se colocó un valor en objPtrRef, que solo será válido temporalmente (a menos que se llame a Tcl_IncrRefCount).

Tcl_FSFileAttrsSet implementa el acceso de escritura para el subcomando file attributes que se puede enganchar. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

Tcl_FSFileAttrStrings implementa parte del subcomando file attributes que se puede enganchar. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

El procedimiento llamado puede devolver una matriz de cadenas o puede devolver NULL y colocar una lista de Tcl en objPtrRef. Tcl tomará esa lista y primero incrementará su recuento de referencias antes de usarla. Al finalizar ese uso, Tcl decrementará su recuento de referencias. Por lo tanto, si la lista debe ser desechada por Tcl cuando termine, debería tener un recuento de referencias de cero, y si la lista no debe ser desechada, el sistema de archivos debe asegurarse de retener un recuento de referencias del valor.

Tcl_FSAccess comprueba si se permitiría al proceso leer, escribir o comprobar la existencia del archivo (u otro objeto del sistema de archivos) cuyo nombre es pathname. Si pathname es un enlace simbólico en Unix, se prueban los permisos del archivo al que se refiere este enlace simbólico.

En caso de éxito (todos los permisos solicitados concedidos), se devuelve cero. En caso de error (al menos un bit en mode solicitó un permiso denegado, o ocurrió algún otro error), se devuelve -1.

Tcl_FSStat rellena la estructura Tcl_StatBuf statPtr con información sobre el archivo especificado. No necesita derechos de acceso al archivo para obtener esta información, pero necesita derechos de búsqueda en todos los directorios nombrados en la ruta que conduce al archivo. La estructura Tcl_StatBuf incluye información sobre el dispositivo, inodo (siempre 0 en Windows), modo de privilegio, nlink (siempre 1 en Windows), id de usuario (siempre 0 en Windows), id de grupo (siempre 0 en Windows), rdev (igual que el dispositivo en Windows), tamaño, hora del último acceso, hora de la última modificación y hora del último cambio de metadatos. Consulte la API PORTABLE STAT RESULT para obtener una descripción sobre cómo escribir código portable para asignar y acceder a la estructura Tcl_StatBuf.

Si path existe, Tcl_FSStat devuelve 0 y la estructura stat se rellena con datos. De lo contrario, se devuelve -1 y no se proporciona información de stat.

Tcl_FSOpenFileChannel abre un archivo especificado por pathPtr y devuelve un manejador de canal que se puede usar para realizar entrada y salida en el archivo. Esta API está modelada según el procedimiento fopen de la biblioteca estándar de E/S de Unix. La sintaxis y el significado de todos los argumentos son similares a los proporcionados en el comando open de Tcl al abrir un archivo. Si ocurre un error al abrir el canal, Tcl_FSOpenFileChannel devuelve NULL y registra un código de error POSIX que se puede recuperar con Tcl_GetErrno. Además, si interp no es NULL, Tcl_FSOpenFileChannel deja un mensaje de error en el resultado de interp después de cualquier error.

El canal recién creado no se registra en el intérprete suministrado; para registrarlo, use Tcl_RegisterChannel. Si uno de los canales estándar, stdin, stdout o stderr se cerró previamente, la acción de crear el nuevo canal también lo asigna como un reemplazo del canal estándar.

Tcl_FSGetCwd reemplaza la versión de biblioteca de getcwd.

Devuelve el directorio de trabajo actual de la biblioteca de Tcl. Este puede ser diferente al directorio de trabajo de la plataforma nativa, lo que ocurre cuando el directorio de trabajo actual no está en el sistema de archivos nativo.

El resultado es un puntero a un Tcl_Obj que especifica el directorio actual, o NULL si no se pudo determinar el directorio actual. Si se devuelve NULL, se deja un mensaje de error en el resultado de interp.

El resultado ya tiene su recuento de referencias incrementado para el llamador. Cuando ya no sea necesario, se debe decrementar ese recuento de referencias. Esto es necesario por motivos de seguridad de hilos, para permitir que varios hilos accedan a esta y funciones relacionadas, al tiempo que se garantiza que los resultados sean siempre válidos.

Tcl_FSChdir reemplaza la versión de biblioteca de chdir. La ruta se normaliza y luego se pasa al sistema de archivos que la reclama. Si ese sistema de archivos no implementa esta función, Tcl recurrirá a una combinación de stat y access para verificar si el directorio existe y tiene los permisos apropiados.

Para ver los resultados, consulte la documentación de chdir. Si tiene éxito, guardamos un registro de la ruta exitosa en cwdPathPtr para llamadas posteriores a Tcl_FSGetCwd.

Tcl_FSPathSeparator devuelve el carácter separador que se utilizará para el elemento más específico de la ruta especificada por pathPtr (es decir, la última parte de la ruta).

El separador se devuelve como un Tcl_Obj que contiene una cadena de longitud 1. Si la ruta no es válida, se devuelve NULL.

Tcl_FSJoinPath toma el Tcl_Obj dado, que debe ser una lista válida (que puede tener un recuento de referencias de cero), y devuelve el valor de ruta dado al considerar los primeros elements elementos como segmentos de ruta válidos (cada segmento de ruta puede ser una ruta completa, una ruta parcial o simplemente un solo directorio o nombre de archivo posible). Si algún segmento de ruta es realmente una ruta absoluta, entonces todos los segmentos de ruta anteriores se descartan. Si elements es menor que 0, usamos toda la lista.

Es posible que el valor devuelto sea en realidad un elemento de la lista dada, por lo que el llamador debe tener cuidado de incrementar el recuento de referencias del resultado antes de liberar la lista.

El valor devuelto, normalmente con un recuento de referencias de cero (pero podría compartirse bajo ciertas condiciones), contiene la ruta unida. El llamador debe agregar un recuento de referencias al valor antes de usarlo. En particular, el valor devuelto podría ser un elemento de la lista dada, por lo que liberar la lista podría liberar el valor prematuramente si no se ha tomado un recuento de referencias. Si el número de elementos es cero, entonces el valor devuelto será un Tcl_Obj de cadena vacía.

Tcl_FSSplitPath toma el Tcl_Obj dado, que debería ser una ruta válida, y devuelve un valor de lista de Tcl que contiene cada segmento de esa ruta como un elemento. Devuelve un valor de lista con un recuento de referencias de cero. Si lenPtr pasado no es NULL, la variable a la que apunta se actualizará para contener el número de elementos en la lista devuelta.

Tcl_FSEqualPaths prueba si las dos rutas dadas representan el mismo objeto del sistema de archivos. Devuelve 1 si las rutas son iguales y 0 si son diferentes. Si alguna ruta es NULL, siempre se devuelve 0.

Tcl_FSGetNormalizedPath intenta extraer del Tcl_Obj dado una representación de ruta normalizada única, cuyo valor de cadena se puede utilizar como identificador único del archivo.

Devuelve el valor de la ruta normalizada, propiedad de Tcl, o NULL si la ruta no era válida o no se pudo convertir correctamente. La extracción de rutas absolutas y normalizadas es muy eficiente (porque el sistema de archivos opera internamente con estas representaciones), aunque el resultado cuando el sistema de archivos contiene numerosos enlaces simbólicos puede no ser la versión de una ruta más amigable para el usuario. El valor de retorno es propiedad de Tcl y tiene una vida útil equivalente a la de pathPtr pasado (a menos que sea una ruta relativa, en cuyo caso el valor de ruta normalizada puede liberarse en cualquier momento en que cambie el cwd): el llamador, por supuesto, puede incrementar el recuento de referencias si desea mantener una copia por más tiempo.

Tcl_FSJoinToPath toma el valor dado, que normalmente debería ser una ruta válida o NULL, y le une la matriz de segmentos de ruta dados.

Devuelve un valor, normalmente con un recuento de referencias de cero (pero podría compartirse bajo ciertas condiciones), que contiene la ruta unida. El llamador debe agregar un recuento de referencias al valor antes de usarlo. Si alguno de los valores pasados a esta función (pathPtr o elementos de path) tiene un recuento de referencias de cero, se liberarán cuando esta función regrese.

Tcl_FSConvertToPathType intenta convertir el Tcl_Obj dado a un tipo de ruta Tcl válido, teniendo en cuenta el hecho de que el cwd puede haber cambiado incluso si este valor ya se supone que es del tipo correcto. El nombre de archivo puede comenzar con "~" (para indicar el directorio personal del usuario actual) o "~" (para indicar el directorio personal de cualquier usuario).

Si la conversión tiene éxito (es decir, el valor es una ruta válida en uno de los sistemas de archivos actuales), se devuelve TCL_OK. De lo contrario, se devuelve TCL_ERROR y se puede dejar un mensaje de error en el intérprete.

Tcl_FSGetInternalRep extrae la representación interna de un valor de ruta dado, en el sistema de archivos dado. Si el valor de ruta pertenece a un sistema de archivos diferente, devolvemos NULL. Si la representación interna es actualmente NULL, intentamos generarla, llamando a Tcl_FSCreateInternalRepProc del sistema de archivos.

Devuelve NULL o una representación de ruta interna válida. Esta representación interna está en caché, de modo que las llamadas repetidas a esta función no requerirán conversiones adicionales.

Tcl_FSGetTranslatedPath intenta extraer la ruta traducida del Tcl_Obj dado.

Si la traducción tiene éxito (es decir, el valor es una ruta válida), se devuelve. De lo contrario, se devolverá NULL y se puede dejar un mensaje de error en el intérprete. Una ruta "traducida" es aquella que no contiene secuencias "~" o "~usuario" (estas se han expandido a su representación actual en el sistema de archivos). El valor devuelto es propiedad del llamador, que debe almacenarlo o llamar a Tcl_DecrRefCount para garantizar la liberación de memoria. Esta función tiene poco uso práctico, y Tcl_FSGetNormalizedPath o Tcl_FSGetNativePath suelen ser mejores funciones para usar en la mayoría de los casos.

Tcl_FSGetTranslatedStringPath hace lo mismo que Tcl_FSGetTranslatedPath, pero devuelve una cadena de caracteres o NULL. La cadena devuelta está asignada dinámicamentend propiedad del llamante, que debe almacenarla o llamar a ckfree para asegurarse de que se libere. De nuevo, Tcl_FSGetNormalizedPath o Tcl_FSGetNativePath son funciones generalmente mejores para la mayoría de los propósitos.

Tcl_FSNewNativePath realiza algo parecido a la inversa de las conversiones habituales obj->path->nativerep. Si algún código recupera una ruta en formato nativo (desde, por ejemplo, readlink o un diálogo nativo), y esa ruta se va a utilizar a nivel de Tcl, entonces llamar a esta función es una forma eficiente de crear el tipo de valor de ruta apropiado.

El valor resultante es un valor de “ruta” puro, que solo recibirá una representación de cadena UTF-8 si así lo requiere algún código Tcl.

Tcl_FSGetNativePath es para uso de los sistemas de archivos nativos Win/Unix, para que puedan recuperar fácilmente la representación nativa (char* o TCHAR*) de una ruta. Esta función es un envoltorio de conveniencia alrededor de Tcl_FSGetInternalRep. Puede ser deseable en el futuro tener representaciones nativas no basadas en cadenas (por ejemplo, en macOS, una representación que use una estructura FSRef de fileSpec probablemente sería más eficiente). En Windows, una representación Unicode completa permitiría rutas de longitud ilimitada. Actualmente, la representación es simplemente una cadena de caracteres que puede contener la ruta relativa o una ruta completa, absoluta y normalizada en la codificación nativa (condiciones complejas dictan cuál de estas se proporcionará, por lo que ninguna puede confiarse, a menos que se sepa que la ruta es absoluta). Si necesita una ruta nativa que deba ser absoluta, entonces debe solicitar la versión nativa de una ruta normalizada. Si por alguna razón se necesita una versión no absoluta, no normalizada de la ruta, esta debe construirse por separado (por ejemplo, usando Tcl_FSGetTranslatedPath).

La representación nativa se almacena en caché para que las llamadas repetidas a esta función no requieran conversiones adicionales. El valor de retorno es propiedad de Tcl y tiene una vida útil equivalente a la del pathPtr pasado (a menos que sea una ruta relativa, en cuyo caso la representación nativa puede liberarse en cualquier momento en que cambie el cwd).

Tcl_FSFileSystemInfo devuelve una lista de dos elementos. El primer elemento es el nombre del sistema de archivos (por ejemplo, "native", "vfs", "zip", o "prowrap", quizás), y el segundo es el tipo particular de la ruta dada dentro de ese sistema de archivos (que depende del sistema de archivos). El segundo elemento puede estar vacío si el sistema de archivos no proporciona una categorización adicional de los archivos.

Se devuelve un valor de lista válido, a menos que el valor de la ruta no sea reconocido, en cuyo caso se devolverá NULL.

Tcl_FSGetFileSystemForPath devuelve un puntero al Tcl_Filesystem que acepta esta ruta como válida.

Si ningún sistema de archivos acepta la ruta, se devuelve NULL.

Tcl_FSGetPathType determina si la ruta dada es relativa al directorio actual, relativa al volumen actual o absoluta.

Devuelve uno de TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE o TCL_PATH_VOLUME_RELATIVE

LA API DE SISTEMAS DE ARCHIVOS VIRTUALES

Un sistema de archivos proporciona una estructura Tcl_Filesystem que contiene punteros a funciones que implementan las diversas operaciones en un sistema de archivos; estas operaciones se invocan según sea necesario por la capa genérica, lo que generalmente ocurre a través de las funciones enumeradas anteriormente.

Las estructuras Tcl_Filesystem se manipulan utilizando los siguientes métodos.

Tcl_FSRegister toma un puntero a una estructura de sistema de archivos y un dato opcional para asociar con ese sistema de archivos. Al llamar a esta función, Tcl adjuntará el sistema de archivos a la lista de sistemas de archivos conocidos, y se volverá completamente funcional inmediatamente. Tcl no verifica si el mismo sistema de archivos está registrado varias veces (y en general, eso no es algo bueno de hacer). Se devolverá TCL_OK.

Tcl_FSUnregister elimina la estructura del sistema de archivos dada de la lista de sistemas de archivos conocidos, si se conoce, y devuelve TCL_OK. Si el sistema de archivos no está registrado actualmente, se devuelve TCL_ERROR.

Tcl_FSData devolverá el clientData asociado con el sistema de archivos dado, si ese sistema de archivos está registrado. De lo contrario, devolverá NULL.

Tcl_FSMountsChanged se utiliza para informar al núcleo de Tcl que el conjunto de puntos de montaje para el sistema de archivos dado (ya registrado) ha cambiado, y que las representaciones de archivos en caché por lo tanto ya no pueden ser correctas.

Las muchas funciones en esta estructura se dividen en tres categorías: funciones de infraestructura (casi todas las cuales deben implementarse), funciones operativas (que deben implementarse si se proporciona un sistema de archivos completo) y funciones de eficiencia (que solo necesitan implementarse si se pueden hacer de manera eficiente, o si tienen efectos secundarios que son requeridos por el sistema de archivos; Tcl tiene emulaciones menos eficientes a las que puede recurrir). Es importante tener en cuenta que, en la versión actual de Tcl, la mayoría de estas alternativas solo se utilizan para manejar comandos iniciados en Tcl, no en C. Lo que esto significa es que, si se emite un comando file rename en Tcl, y los sistemas de archivos relevantes no implementan su Tcl_FSRenameFileProc, el núcleo de Tcl recurrirá a una combinación de otras funciones del sistema de archivos (utilizará Tcl_FSCopyFileProc seguido de Tcl_FSDeleteFileProc, y si Tcl_FSCopyFileProc no está implementado, hay otra alternativa). Sin embargo, si se emite un comando Tcl_FSRenameFileProc a nivel de C, no ocurren tales alternativas. Esto es cierto excepto para las últimas cuatro entradas en la tabla del sistema de archivos (lstat, load, getcwd y chdir) para las cuales las alternativas realmente ocurren a nivel de C.

Cualquier función que tome nombres de ruta en forma de Tcl_Obj toma esos nombres en forma UTF-8. La API de infraestructura del sistema de archivos está diseñada para admitir la conversión eficiente y en caché de estas rutas UTF-8 a otras representaciones nativas.

OPENFILECHANNELPROC

Función para procesar una llamada a Tcl_FSOpenFileChannel. Debe ser implementada para cualquier sistema de archivos razonable, ya que las operaciones que requieran abrir o acceder al contenido de un archivo la utilizarán (p. ej., open, encoding y muchos comandos de Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

La función Tcl_FSOpenFileChannelProc abre un archivo especificado por pathPtr y devuelve un manejador de canal que puede ser utilizado para realizar entrada y salida en el archivo. Esta API está modelada según el procedimiento fopen de la biblioteca estándar de entrada/salida de Unix. La sintaxis y el significado de todos los argumentos son similares a los dados en el comando open de Tcl al abrir un archivo, donde el argumento mode es una combinación de las banderas POSIX O_RDONLY, O_WRONLY, etc. Si ocurre un error al abrir el canal, Tcl_FSOpenFileChannelProc devuelve NULL y registra un código de error POSIX que puede ser recuperado con Tcl_GetErrno. Además, si interp no es NULL, Tcl_FSOpenFileChannelProc deja un mensaje de error en el resultado de interp después de cualquier error.

El canal recién creado no debe ser registrado en el intérprete suministrado por Tcl_FSOpenFileChannelProc; esa tarea le corresponde al llamante de Tcl_FSOpenFileChannel (si es necesario). Si uno de los canales estándar, stdin, stdout o stderr fue cerrado previamente, el acto de crear el nuevo canal también lo asigna como un reemplazo para el canal estándar.

MATCHINDIRECTORYPROC

Función para procesar una llamada a Tcl_FSMatchInDirectory. Si no se implementa, la funcionalidad de glob y copia recursiva carecerá en el sistema de archivos (y esto puede afectar a comandos como encoding names que utilizan internamente la funcionalidad de glob).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La función debe devolver todos los archivos o directorios (u otros objetos del sistema de archivos) que coincidan con el patrón dado y se acuerden con la especificación types proporcionada. Hay dos formas en las que se puede llamar a esta función. Si pattern es NULL, entonces pathPtr es una especificación de ruta completa de un solo archivo o directorio que debe ser verificado en cuanto a existencia y tipo correcto. De lo contrario, pathPtr es un directorio, cuyo contenido la función debe buscar archivos o directorios que tengan el tipo correcto. En cualquier caso, se puede asumir que pathPtr no es NULL y no está vacío. No está documentado actualmente si pathPtr tendrá un separador de archivo al final o no, por lo que el código debe ser flexible a ambas posibilidades.

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso de coincidencia. Los mensajes de error se colocan en interp, a menos que interp sea NULL, en cuyo caso no es necesario generar ningún mensaje de error; en un resultado TCL_OK, los resultados deben agregarse al valor dado resultPtr (que se puede asumir que es una lista válida y no compartida de Tcl). Las coincidencias agregadas a resultPtr deben incluir cualquier prefijo de ruta dado en pathPtr (esto generalmente significa que serán especificaciones de ruta absoluta). Tenga en cuenta que si no se encuentran coincidencias, eso simplemente conduce a un resultado vacío; los errores solo se señalan para problemas reales del archivo o del sistema de archivos que puedan ocurrir durante el proceso de coincidencia.

La estructura Tcl_GlobTypeData pasada en el parámetro types contiene los siguientes campos:

typedef struct Tcl_GlobTypeData {
    /* Corresponde a bcdpfls como en 'find -t' */
    int type;
    /* Corresponde a los permisos de archivo */
    int perm;
    /* Tipo de Mac aceptable */
    Tcl_Obj *macType;
    /* Creador de Mac aceptable */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Hay dos casos específicos que es importante manejar correctamente, ambos cuando types no es NULL. Los dos casos son cuando types->types & TCL_GLOB_TYPE_DIR o types->types & TCL_GLOB_TYPE_MOUNT son verdaderos (y en particular cuando los otros flags son falsos). En el primer caso, la función debe listar los directorios contenidos. Tcl utiliza esto para implementar el globbing recursivo, por lo que es fundamental que los sistemas de archivos implementen correctamente la coincidencia de directorios. En el segundo caso, con TCL_GLOB_TYPE_MOUNT, el sistema de archivos debe listar los puntos de montaje que se encuentran dentro del pathPtr dado (y en este caso, pathPtr no necesita estar dentro del mismo sistema de archivos; diferente a todos los otros casos en los que se llama a esta función). El soporte para esto es crítico si Tcl quiere tener transiciones fluidas de un sistema de archivos a otro.

UTIMEPROC

Función para procesar una llamada a Tcl_FSUtime. Requerida para permitir el establecimiento (no la lectura) de tiempos con file mtime, file atime y la implementación de apertura/cierre de lectura/escritura de file copy.

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

Los tiempos de acceso y modificación del archivo especificado por pathPtr deben ser cambiados a los valores dados en la estructura tval.

El valor de retorno debe ser 0 en caso de éxito y -1 en caso de error, al igual que con el utime del sistema.

LINKPROC

Función para procesar una llamada a Tcl_FSLink. Solo debe ser implementada si el sistema de archivos soporta enlaces, y de lo contrario puede ser NULL.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

Si toPtr es NULL, se le está pidiendo a la función que lea el contenido de un enlace. El resultado es un Tcl_Obj que especifica el contenido del enlace dado por linkNamePtr, o NULL si el enlace no pudo ser leído. El resultado es propiedad del llamante (y por lo tanto su contador de referencia debe ser incrementado antes de ser devuelto). Cualquier llamante debe llamar a Tcl_DecrRefCount en este resultado cuando ya no sea necesario. Si toPtr no es NULL, la función debe intentar crear un enlace. El resultado en este caso debe ser toPtr si el enlace fue exitoso y NULL en caso contrario. En este caso, el resultado no es propiedad del llamante (es decir, no se necesitan manipulaciones de contador de referencia en ninguno de los extremos). Vea la documentación de Tcl_FSLink para la interpretación correcta de las banderas linkAction.

LISTVOLUMESPROC

Función para listar cualquier volumen de sistema de archivos añadido por este sistema de archivos. Solo debe ser implementada si el sistema de archivos añade volúmenes al principio del sistema de archivos, para que puedan ser devueltos por file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

El resultado debe ser una lista de volúmenes añadidos por este sistema de archivos, o NULL (o una lista vacía) si no se proporcionan volúmenes. Se considera que el valor de resultado es propiedad del sistema de archivos (no del núcleo de Tcl), pero se le debe dar un contador de referencia para Tcl. Tcl utilizará el contenido de la lista e luego decrementará ese contador de referencia. Esto permite a los sistemas de archivos elegir si realmente quieren retener una lista "global" de volúmenes o no (si no, generan la lista sobre la marcha y la pasan a Tcl con un contador de referencia de 1 y luego se olvidan de la lista; si sí, simplemente incrementan el contador de referencia de su lista global y la pasan a Tcl, que copiará el contenido y luego decrementará el contador de vuelta a donde estaba).

Por lo tanto, Tcl considera que los valores de retorno de este proc son de solo lectura.

FILEATTRSTRINGSPROC

Función para listar todas las cadenas de atributos que son válidas para este sistema de archivos. Si no se implementa, el sistema de archivos no admitirá el comando file attributes. Esto permite adjuntar información adicional arbitraria a los archivos en el sistema de archivos. Si no se implementa, no hay necesidad de implementar los métodos get y set.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

La función llamada puede devolver un array de cadenas o puede devolver NULL y colocar una lista de Tcl en objPtrRef. Tcl tomará esa lista y primero incrementará su contador de referencia antes de usarla. Al finalizar ese uso, Tcl decrementará su contador de referencia. Por lo tanto, si la lista debe ser descartada por Tcl cuando termine, debe tener un contador de referencia de cero, y si la lista no debe ser descartada, el sistema de archivos debe asegurarse de devolver un valor con un contador de referencia de al menos uno.

FILEATTRSGETPROC

Función para procesar una llamada a Tcl_FSFileAttrsGet, utilizada por file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

Devuelve un código de retorno estándar de Tcl. El valor del atributo recuperado, que corresponde al elemento con índice index en la lista devuelta por Tcl_FSFileAttrStringsProc, es un Tcl_Obj colocado en objPtrRef (si se devolvió TCL_OK) y es probable que tenga un contador de referencia de cero. De cualquier manera, debemos almacenarlo en algún lugar (p. ej., el resultado de Tcl) o incrementar/decrementar su contador de referencia para asegurar que se libere correctamente.

FILEATTRSSETPROC

Función para procesar una llamada a Tcl_FSFileAttrsSet, utilizada por file attributes. Si el sistema de archivos es de solo lectura, no hay necesidad de implementar esto.

typedef int Tcl_FSFileAttrsSetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj *objPtr);

El valor del atributo del elemento con índice index en la lista devuelta por Tcl_FSFileAttrStringsProc debe establecerse en el objPtr proporcionado.

CREATE DIRECTORY PROC

Function to process a Tcl_FSCreateDirectory call. Should be implemented unless the FS is read-only.

typedef int Tcl_FSCreateDirectoryProc(
        Tcl_Obj *pathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, a new directory should have been added to the filesystem in the location specified by pathPtr.

REMOVE DIRECTORY PROC

Function to process a Tcl_FSRemoveDirectory call. Should be implemented unless the FS is read-only.

typedef int Tcl_FSRemoveDirectoryProc(
        Tcl_Obj *pathPtr,
        int recursive,
        Tcl_Obj **errorPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, the directory specified by pathPtr should have been removed from the filesystem. If the recursive flag is given, then a non-empty directory should be deleted without error. If this flag is not given, then and the directory is non-empty a POSIX “EEXIST” error should be signaled. If an error does occur, the name of the file or directory which caused the error should be placed in errorPtr.

DELETE FILE PROC

Function to process a Tcl_FSDeleteFile call. Should be implemented unless the FS is read-only.

typedef int Tcl_FSDeleteFileProc(
        Tcl_Obj *pathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, the file specified by pathPtr should have been removed from the filesystem. Note that, if the filesystem supports symbolic links, Tcl will always call this function and not Tcl_FSRemoveDirectoryProc when needed to delete them (even if they are symbolic links to directories).

FILESYSTEM EFFICIENCY

These functions need not be implemented for a particular filesystem because the core has a fallback implementation available. See each individual description for the consequences of leaving the field NULL.

LSTAT PROC

Function to process a Tcl_FSLstat call. If not implemented, Tcl will attempt to use the statProc defined above instead. Therefore it need only be implemented if a filesystem can differentiate between stat and lstat calls.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

The behavior of this function is very similar to that of the Tcl_FSStatProc defined above, except that if it is applied to a symbolic link, it returns information about the link, not about the target file.

COPY FILE PROC

Function to process a Tcl_FSCopyFile call. If not implemented Tcl will fall back on open-r, open-w and fcopy as a copying mechanism. Therefore it need only be implemented if the filesystem can perform that action more efficiently.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the copying process. Note that, destPathPtr is the name of the file which should become the copy of srcPathPtr. It is never the name of a directory into which srcPathPtr could be copied (i.e. the function is much simpler than the Tcl level file copy subcommand). Note that, if the filesystem supports symbolic links, Tcl will always call this function and not copyDirectoryProc when needed to copy them (even if they are symbolic links to directories). Finally, if the filesystem determines it cannot support the file copy action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

RENAME FILE PROC

Function to process a Tcl_FSRenameFile call. If not implemented, Tcl will fall back on a copy and delete mechanism. Therefore it need only be implemented if the filesystem can perform that action more efficiently.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the renaming process. If the filesystem determines it cannot support the file rename action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

COPY DIRECTORY PROC

Function to process a Tcl_FSCopyDirectory call. If not implemented, Tcl will fall back on a recursive file mkdir, file copy mechanism. Therefore it need only be implemented if the filesystem can perform that action more efficiently.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

The return value is a standard Tcl result indicating whether an error occurred in the copying process. If an error does occur, the name of the file or directory which caused the error should be placed in errorPtr. Note that, destPathPtr is the name of the directory-name which should become the mirror-image of srcPathPtr. It is not the name of a directory into which srcPathPtr should be copied (i.e. the function is much simpler than the Tcl level file copy subcommand). Finally, if the filesystem determines it cannot support the directory copy action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

LOAD FILE PROC

Function to process a Tcl_FSLoadFile call. If not implemented, Tcl will fall back on a copy to native-temp followed by a Tcl_FSLoadFile on that temporary copy. Therefore it need only be implemented if the filesystem can load code directly, or it can be implemented simply to return TCL_ERROR to disable load functionality in this filesystem entirely.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Returns a standard Tcl completion code. If an error occurs, an error message is left in the interp's result. The function dynamically loads a binary code file into memory. On a successful load, the handlePtr should be filled with a token for the dynamically loaded file, and the unloadProcPtr should be filled in with the address of a procedure. The unload procedure will be called with the given Tcl_LoadHandle as its only parameter when Tcl needs to unload the file. For example, for the native filesystem, the Tcl_LoadHandle returned is currently a token which can be used in the private TclpFindSymbol to access functions in the new code. Each filesystem is free to define the Tcl_LoadHandle as it requires. Finally, if the filesystem determines it cannot support the file load action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

UNLOAD FILE PROC

Function to unload a previously successfully loaded file. If load was implemented, then this should also be implemented, if there is any cleanup action required.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GET CWD PROC

Function to process a Tcl_FSGetCwd call. Most filesystems need not implement this. It will usually only be called once, if getcwd is called before chdir. May be NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

If the filesystem supports a native notion of a current working directory (which might perhaps change independent of Tcl), this function should return that cwd as the result, or NULL if the current directory could not be determined (e.g. the user does not have appropriate permissions on the cwd directory). If NULL is returned, an error message is left in the interp's result.

CHDIR PROC

Function to process a Tcl_FSChdir call. If filesystems do not implement this, it will be emulated by a series of directory access checks. Otherwise, virtual filesystems which do implement it need only respond with a positive return result if the pathPtr is a valid, accessible directory in their filesystem. They need not remember the result, since that will be automatically remembered for use by Tcl_FSGetCwd. Real filesystems should carry out the correct action (i.e. call the correct system chdir API).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

The Tcl_FSChdirProc changes the applications current working directory to the value specified in pathPtr. The function returns -1 on error or 0 on success.
