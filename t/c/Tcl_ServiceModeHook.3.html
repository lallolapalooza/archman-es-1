ARGUMENTOS

Procedimiento a invocar para preparar la espera de eventos en Tcl_DoOneEvent.
Tcl_EventCheckProc *checkProc (entrada)
Procedimiento que Tcl_DoOneEvent invocará después de esperar eventos. Verifica si han ocurrido eventos y, de ser así, los pone en cola.

Valor arbitrario de una palabra que se pasará a setupProc, checkProc o deleteProc.
const Tcl_Time *timePtr (entrada)
Indica la cantidad máxima de tiempo a esperar por un evento. Esto se especifica como un intervalo (cuánto esperar), no como un tiempo absoluto (cuándo despertar). Si el puntero pasado a Tcl_WaitForEvent es NULL, significa que no hay un tiempo máximo de espera: esperar indefinidamente si es necesario.

Un evento para añadir a la cola de eventos. El espacio para el evento debe haber sido asignado por el llamador usando Tcl_Alloc o ckalloc.

Dónde añadir el nuevo evento en la cola: TCL_QUEUE_TAIL, TCL_QUEUE_HEAD, o TCL_QUEUE_MARK.

Un identificador único para un hilo.
Tcl_EventDeleteProc *deleteProc (entrada)
Procedimiento a invocar para cada evento en cola en Tcl_DeleteEvents.

INTRODUCCIÓN

Las interfaces descritas aquí se utilizan para personalizar el bucle de eventos de Tcl. Las dos personalizaciones más comunes son añadir nuevas fuentes de eventos y fusionar el bucle de eventos de Tcl con algún otro bucle de eventos, como uno proporcionado por una aplicación en la que Tcl está incrustado. Cada una de estas tareas se describe en una sección separada a continuación.

Los procedimientos de esta entrada de manual son los bloques de construcción con los que se construye el notificador de eventos de Tcl. El notificador de eventos es la capa más baja en el mecanismo de eventos de Tcl. Consta de tres cosas:

[1]
Fuentes de eventos: estas representan las formas en que se pueden generar eventos. Por ejemplo, existe una fuente de eventos de temporizador que implementa el procedimiento Tcl_CreateTimerHandler y el comando after, y existe una fuente de eventos de archivo que implementa el procedimiento Tcl_CreateFileHandler en sistemas Unix. Una fuente de eventos debe trabajar con el notificador para detectar eventos en los momentos adecuados, registrarlos en la cola de eventos y, eventualmente, notificar al software de nivel superior que han ocurrido. Los procedimientos Tcl_CreateEventSource, Tcl_DeleteEventSource, y Tcl_SetMaxBlockTime, Tcl_QueueEvent, y Tcl_DeleteEvents son utilizados principalmente por las fuentes de eventos.
[2]
La cola de eventos: para aplicaciones no multihilo, hay una única cola para toda la aplicación, que contiene eventos que han sido detectados pero aún no atendidos. Las fuentes de eventos colocan eventos en la cola para que puedan ser procesados en orden en momentos apropiados durante el bucle de eventos. La cola de eventos garantiza una disciplina justa de manejo de eventos, de modo que ninguna fuente de eventos pueda dejar hambrientas a las demás. También permite que los eventos se guarden para ser atendidos en un momento futuro. Las aplicaciones multihilo funcionan de manera similar, excepto que hay una cola de eventos separada para cada hilo que contiene un intérprete de Tcl. Tcl_QueueEvent se utiliza (principalmente por las fuentes de eventos) para añadir eventos a la cola de eventos y Tcl_DeleteEvents se utiliza para eliminar eventos de la cola sin procesarlos. En una aplicación multihilo, Tcl_QueueEvent añade un evento a la cola del hilo actual, y Tcl_ThreadQueueEvent añade un evento a una cola en un hilo específico.
[3]
El bucle de eventos: para detectar y procesar eventos, la aplicación entra en un bucle que espera a que ocurran eventos, los coloca en la cola de eventos y luego los procesa. La mayoría de las aplicaciones harán esto llamando al procedimiento Tcl_DoOneEvent, que se describe en una entrada de manual separada.

La mayoría de las aplicaciones Tcl no necesitan preocuparse por ninguno de los internos del notificador Tcl. Sin embargo, el notificador ahora tiene suficiente flexibilidad para ser reorientado, ya sea para una nueva plataforma o para usar un bucle de eventos externo (como el bucle de eventos de Motif, cuando Tcl está incrustado en una aplicación de Motif). Los procedimientos Tcl_WaitForEvent y Tcl_SetTimer son implementados normalmente por Tcl, pero pueden ser reemplazados con nuevas versiones para reorientar el notificador (los procedimientos Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_Sleep, Tcl_CreateFileHandler, y Tcl_DeleteFileHandler también deben ser reemplazados; ver CREANDO UN NUEVO NOTIFICADOR a continuación para más detalles). Los procedimientos Tcl_ServiceAll, Tcl_ServiceEvent, Tcl_GetServiceMode, y Tcl_SetServiceMode se proporcionan para ayudar a conectar el bucle de eventos de Tcl con un bucle de eventos externo como el de Motif.

BASES DEL NOTIFICADOR

La forma más fácil de entender cómo funciona el notificador es considerar lo que sucede cuando se llama a Tcl_DoOneEvent. Tcl_DoOneEvent recibe un argumento flags que indica qué tipo de eventos se pueden procesar y también si debe bloquearse o no si no hay eventos listos. Tcl_DoOneEvent realiza las siguientes acciones:

[1]
Verifica la cola de eventos para ver si contiene algún evento que pueda ser atendido. Si es así, atiende el primer evento posible, lo elimina de la cola y regresa. Hace esto llamando a Tcl_ServiceEvent y pasando el argumento flags.
[2]
Se prepara para bloquear por un evento. Para hacer esto, Tcl_DoOneEvent invoca un procedimiento de configuración en cada fuente de eventos. La fuente de eventos realizará una inicialización específica de la fuente de eventos y posiblemente llamará a Tcl_SetMaxBlockTime para limitar cuánto tiempo bloqueará Tcl_WaitForEvent si no ocurren nuevos eventos.
[3]
Llama a Tcl_WaitForEvent. Este procedimiento se implementa de manera diferente en diferentes plataformas; espera a que ocurra un evento, basándose en la información proporcionada por las fuentes de eventos. Puede hacer que la aplicación se bloquee si timePtr especifica un intervalo distinto de 0. Tcl_WaitForEvent regresa cuando algo ha sucedido, como que un archivo se vuelva legible o que expire el intervalo dado por timePtr. Si no hay eventos para que Tcl_WaitForEvent espere, por lo que se bloquearía indefinidamente, entonces regresa inmediatamente y Tcl_DoOneEvent regresa 0.
[4]
Llama a un procedimiento de verificación en cada fuente de eventos. El procedimiento de verificación determina si ocurrieron eventos de interés para esta fuente. Si es así, los eventos se agregan a la cola de eventos.
[5]

EL BUCLE DE EVENTOS

El bucle de eventos es una secuencia de pasos que se repiten continuamente. El objetivo de este bucle es atender los eventos que se han producido y que están pendientes de ser procesados. Los pasos son los siguientes:

[1]
Verificar si hay eventos en la cola de eventos que puedan ser atendidos. Si los hay, atender el primer evento posible, eliminarlo de la cola y retornar.
[2]
Determinar si se deben buscar nuevos eventos. Si se debe buscar, llamar a los procedimientos de configuración de cada fuente de eventos y, a continuación, llamar a Tcl_WaitForEvent para esperar a que ocurran nuevos eventos. Tcl_WaitForEvent se bloqueará hasta que ocurra un evento o hasta que expire el tiempo de espera máximo especificado por una de las fuentes de eventos.
[3]
Después de que Tcl_WaitForEvent retorne, llamar a los procedimientos de verificación de cada fuente de eventos. Estos procedimientos examinarán si hay eventos que se hayan producido y los añadirán a la cola de eventos si es necesario.
[4]
Verificar si hay eventos en la cola de eventos que puedan ser atendidos. Si los hay, atender el primer evento posible, eliminarlo de la cola y retornar.
[5]
Repetir el paso [4] hasta que no haya más eventos en la cola que puedan ser atendidos.
[6]
Verificar si hay devoluciones de llamada inactivas pendientes. Si las hay, invocarlas todas y retornar.
[7]
Retornar 0 para indicar que no hay eventos listos, o volver al paso [2] si el llamante solicitó bloqueo.

CREACIÓN DE UNA NUEVA FUENTE DE EVENTOS

Una fuente de eventos consta de tres procedimientos invocados por el notificador, además de procedimientos C adicionales que son invocados por código de nivel superior para organizar devoluciones de llamada basadas en eventos. Los tres procedimientos llamados por el notificador consisten en los procedimientos de configuración y verificación descritos anteriormente, más un procedimiento adicional que se invoca cuando un evento se elimina de la cola de eventos para su atención.

El procedimiento Tcl_CreateEventSource crea una nueva fuente de eventos. Sus argumentos especifican el procedimiento de configuración y el procedimiento de verificación para la fuente de eventos. SetupProc debe coincidir con el siguiente prototipo:

typedef void Tcl_EventSetupProc(
        ClientData clientData,
        int flags);

El argumento clientData será el mismo que el argumento clientData para Tcl_CreateEventSource; típicamente se utiliza para apuntar a información privada administrada por la fuente de eventos. El argumento flags será el mismo que el argumento flags pasado a Tcl_DoOneEvent, excepto que nunca será 0 (Tcl_DoOneEvent reemplaza 0 con TCL_ALL_EVENTS). Flags indica qué tipos de eventos deben considerarse; si el bit correspondiente a esta fuente de eventos no está establecido, la fuente de eventos debe retornar inmediatamente sin hacer nada. Por ejemplo, la fuente de eventos de archivo verifica el bit TCL_FILE_EVENTS.

El trabajo de SetupProc es asegurarse de que la aplicación se despierte cuando ocurran eventos del tipo deseado. Esto generalmente se hace de forma dependiente de la plataforma. Por ejemplo, en Unix una fuente de eventos podría llamar a Tcl_CreateFileHandler; en Windows podría solicitar notificación con un evento de Windows. Para fuentes de eventos impulsadas por temporizadores, como eventos de temporizador o cualquier evento sondeado, la fuente de eventos puede llamar a Tcl_SetMaxBlockTime para forzar que la aplicación se despierte después de un tiempo especificado, incluso si no han ocurrido eventos. Si ninguna fuente de eventos llama a Tcl_SetMaxBlockTime, Tcl_WaitForEvent esperará el tiempo necesario para que ocurra un evento; de lo contrario, solo esperará tanto como el intervalo más corto pasado a Tcl_SetMaxBlockTime por una de las fuentes de eventos. Si una fuente de eventos sabe que ya tiene eventos listos para reportar, puede solicitar un tiempo de bloqueo máximo de cero. Por ejemplo, el procedimiento de configuración de la fuente de eventos X busca ver si ya hay eventos en cola. Si los hay, llama a Tcl_SetMaxBlockTime con un tiempo de bloqueo de 0 para que Tcl_WaitForEvent no se bloquee si no hay datos nuevos en la conexión X. El argumento timePtr para Tcl_WaitForEvent apunta a una estructura que describe un intervalo de tiempo en segundos y microsegundos:

typedef struct Tcl_Time {
    long sec;
    long usec;
} Tcl_Time;

El campo usec debe ser menor que 1000000.

La información proporcionada a Tcl_SetMaxBlockTime solo se utiliza para la próxima llamada a Tcl_WaitForEvent; se descarta después de que Tcl_WaitForEvent retorne. La próxima vez que se realice una espera de eventos, se llamará a los procedimientos de configuración de cada una de las fuentes de eventos, y podrán especificar nueva información para esa espera de eventos.

Si la aplicación utiliza un bucle de eventos externo en lugar de Tcl_DoOneEvent, las fuentes de eventos pueden necesitar llamar a Tcl_SetMaxBlockTime en otros momentos. Por ejemplo, si se registra un nuevo manejador de eventos que necesita sondear eventos, la fuente de eventos puede llamar a Tcl_SetMaxBlockTime para establecer el tiempo de bloqueo a cero y forzar al bucle de eventos externo a llamar a Tcl. En este caso, Tcl_SetMaxBlockTime invoca Tcl_SetTimer con el intervalo más corto visto desde la última llamada a Tcl_DoOneEvent o Tcl_ServiceAll.

Además del procedimiento genérico Tcl_SetMaxBlockTime, otros procedimientos específicos de la plataforma también pueden estar disponibles para setupProc, si hay información adicional necesaria para Tcl_WaitForEvent en esa plataforma. Por ejemplo, en sistemas Unix la interfaz Tcl_CreateFileHandler se puede utilizar para esperar eventos de archivo.

El segundo procedimiento proporcionado por cada fuente de eventos es su procedimiento de verificación, indicado por el argumento checkProc para Tcl_CreateEventSource. CheckProc debe coincidir con el siguiente prototipo:

typedef void Tcl_EventCheckProc(
        ClientData clientData,
        int flags);

Los argumentos de este procedimiento son los mismos que los de setupProc. CheckProc es invocado por Tcl_DoOneEvent después de haber esperado eventos. Presumiblemente, al menos una fuente de eventos ahora está preparada para encolar un evento. Tcl_DoOneEvent llama a cada una de las fuentes de eventos por turno, para que todas tengan la oportunidad de encolar cualquier evento que esté listo. El procedimiento de verificación hace dos cosas. Primero, debe ver si algún evento se ha disparado. Diferentes fuentes de eventos hacen esto de diferentes maneras.

Si el procedimiento de verificación de una fuente de eventos detecta un evento interesante, debe añadir el evento a la cola de eventos de Tcl. Para hacer esto, la fuente de eventos llama a Tcl_QueueEvent. El argumento evPtr es un puntero a una estructura asignada dinámicamente que contiene el evento (ver más abajo para más información sobre cuestiones de gestión de memoria). Cada fuente de eventos puede definir su propia estructura de evento con la información que sea relevante para esa fuente de eventos. Sin embargo, el primer elemento de la estructura debe ser una estructura de tipo Tcl_Event, y la dirección de esta estructura se utiliza al comunicarse entre la fuente de eventos y el resto del notificador. Un Tcl_Event tiene la siguiente definición:

typedef struct {
    Tcl_EventProc *proc;
    struct Tcl_Event *nextPtr;
} Tcl_Event;

La fuente de eventos debe completar el campo proc del evento antes de llamar a Tcl_QueueEvent. nextPtr se utiliza para enlazar los eventos en la cola y no debe ser modificado por la fuente de eventos.

Un evento puede añadirse a la cola en cualquiera de las tres posiciones, dependiendo del argumento position de Tcl_QueueEvent:

TCL_QUEUE_TAIL
Añade el evento al final de la cola, de modo que todos los demás eventos pendientes se atiendan primero. Este es casi siempre el lugar correcto para los nuevos eventos.
TCL_QUEUE_HEAD
Añade el evento al principio de la cola, de modo que se atienda antes que todos los demás eventos en cola.
TCL_QUEUE_MARK
Añade el evento al principio de la cola, a menos que haya otros eventos al principio cuya posición sea TCL_QUEUE_MARK; en ese caso, añade el nuevo evento justo después de todos los demás eventos TCL_QUEUE_MARK. Este valor de position se utiliza para insertar una secuencia ordenada de eventos al principio de la cola, como una serie de eventos Enter y Leave sintetizados durante una operación de captura o liberación en Tk.

Cuando es el momento de manejar un evento de la cola (pasos 1 y 4 anteriores), Tcl_ServiceEvent invocará el proc especificado en la primera estructura Tcl_Event encolada. Proc debe coincidir con el siguiente prototipo:

typedef int Tcl_EventProc(
        Tcl_Event *evPtr,
        int flags);

El primer argumento de proc es un puntero al evento, que será el mismo que el primer argumento de la llamada Tcl_QueueEvent que añadió el evento a la cola. El segundo argumento de proc es el argumento flags para la llamada actual a Tcl_ServiceEvent; esto es utilizado por la fuente de eventos para retornar inmediatamente si sus eventos no son relevantes.

Depende de proc manejar el evento, típicamente invocando uno o más comandos Tcl o devoluciones de llamada a nivel C. Una vez que la fuente de eventos ha terminado de manejar el evento, retorna 1 para indicar que el evento puede ser eliminado de la cola. Si por alguna razón la fuente de eventos decide que el evento no puede ser manejado en este momento, puede retornar 0 para indicar que el evento debe ser diferido para su procesamiento posterior; en este caso, Tcl_ServiceEvent pasará al siguiente evento en la cola e intentará atenderlo. Hay varias razones por las que una fuente de eventos podría diferir un evento. Una posibilidad es que los eventos de este tipo estén excluidos por el argumento flags. Por ejemplo, la fuente de eventos de archivo siempre retornará 0 si el bit TCL_FILE_EVENTS no está establecido en flags. Otro ejemplo de diferimiento de eventos ocurre en Tk si se ha invocado Tk_RestrictEvents para diferir ciertos tipos de eventos de ventana.

Cuando proc retorna 1, Tcl_ServiceEvent eliminará el evento de la cola de eventos y liberará su almacenamiento. Tenga en cuenta que el almacenamiento de un evento debe ser asignado por la fuente de eventos (usando Tcl_Alloc o la macro Tcl ckalloc) antes de llamar a Tcl_QueueEvent, pero será liberado por Tcl_ServiceEvent, no por la fuente de eventos.

Las aplicaciones multihilo funcionan de manera similar, excepto que hay una cola de eventos separada para cada hilo que contiene un intérprete Tcl. Llamar a Tcl_QueueEvent en una aplicación multihilo añade un evento a la cola del hilo actual. Para añadir un evento a la cola de otro hilo, utilice Tcl_ThreadQueueEvent. Tcl_ThreadQueueEvent acepta como argumento un argumento Tcl_ThreadId, que identifica de forma única un hilo en una aplicación Tcl. Para obtener el Tcl_ThreadId del hilo actual, utilice el procedimiento Tcl_GetCurrentThread. (Un hilo necesitaría entonces pasar este identificador a otros hilos para que estos puedan añadir eventos a su cola). Después de añadir un evento a la cola de otro hilo, generalmente debe llamar a Tcl_ThreadAlert para "despertar" al notificador de ese hilo y alertarlo del nuevo evento.

Tcl_DeleteEvents se puede utilizar para eliminar explícitamente uno o más eventos de la cola de eventos. Tcl_DeleteEvents llama a proc para cada evento en la cola, eliminando aquellos para los que el procedimiento retorna 1. Los eventos para los cuales el procedimiento retorna 0 se dejan en la cola. Proc debe coincidir con el siguiente prototipo:

        Tcl_Event *evPtr,
        ClientData clientData);

NAME

Tcl_ServiceModeHook, Tcl_SetServiceMode - hook into Tcl's event loop

SYNOPSIS

#include <tcl.h>

int

    Tcl_Interp *interp,
    Tcl_ServiceModeHookProc *hookProc,
    ClientData clientData)

Tcl_ServiceModeHookProc *
Tcl_SetServiceMode(
    Tcl_Interp *interp,
    Tcl_ServiceModeHookProc *hookProc,
    ClientData clientData)

ARGUMENTS

Tcl_Interp *interp
Interpreter to act in.
Tcl_ServiceModeHookProc *hookProc
A pointer to the service mode hook procedure.
ClientData clientData
Arbitrary one-word value to be passed to the hook procedure.

INTRODUCTION

The Tcl event loop is responsible for processing events from various sources, such as I/O readiness on file descriptors, timers expiring, and idle time. When the Tcl interpreter has no events to process, it can block until an event occurs. This is done by calling the underlying operating system's event multiplexing mechanism (e.g. select, poll, epoll). In some cases, it may be desirable to perform additional work or checks before Tcl blocks, or to prevent Tcl from blocking altogether. This can be achieved by installing a service mode hook.

NOTIFIER BASICS

The notifier is the core component of the Tcl event loop. It is responsible for managing event sources and dispatching events. The notifier provides a mechanism for installing and removing event sources, as well as for processing events. The notifier also handles the blocking behavior of the event loop, by calling the underlying operating system's event multiplexing mechanism.

The default notifier implementation in Tcl is based on the select system call. It supports file events, timer events, and idle events. It also provides a service mode hook mechanism that allows users to hook into the event loop and perform custom actions.

CREATING A NEW EVENT SOURCE

To create a new event source, you need to implement a procedure that can be called by the Tcl event loop to check for events and process them. This procedure will be registered with the Tcl notifier using the Tcl_CreateFileHandler, Tcl_CreateTimerHandler, or Tcl_CreateIdleHandler functions. These functions take a file descriptor, a procedure to call when the file descriptor is ready, and client data to pass to the procedure. The procedure should return an integer value indicating whether the event source is still valid.

CREATING A NEW NOTIFIER

To create a new notifier, you need to implement a set of procedures that conform to the Tcl notifier interface. These procedures will be responsible for managing event sources, processing events, and handling the blocking behavior of the event loop. The notifier interface consists of the following procedures:

  • Tcl_CreateFileHandler: Creates a new file event source.
  • Tcl_DeleteFileHandler: Deletes a file event source.
  • Tcl_CreateTimerHandler: Creates a new timer event source.
  • Tcl_DeleteTimerHandler: Deletes a timer event source.
  • Tcl_CreateIdleHandler: Creates a new idle event source.
  • Tcl_DeleteIdleHandler: Deletes an idle event source.
  • Tcl_DoOneEvent: Processes a single event.
  • Tcl_ServiceModeHook: Installs a service mode hook.
  • Tcl_SetServiceMode: Sets the service mode for the notifier.

Once you have implemented the notifier procedures, you can register your notifier with the Tcl interpreter using the Tcl_SetNotifier function.

REPLACING THE NOTIFIER

The default Tcl notifier can be replaced by a custom notifier by calling the Tcl_SetNotifier function. This function takes a pointer to a Tcl_NotifierProcs structure, which contains pointers to the procedures that implement the notifier interface. By replacing the default notifier, you can customize the behavior of the Tcl event loop, for example, to support new types of event sources or to integrate with existing event processing mechanisms.

EXTERNAL EVENT LOOPS

Tcl can be integrated into an external event loop by calling the Tcl_DoOneEvent function. This function processes a single event from the Tcl event queue. By calling Tcl_DoOneEvent repeatedly, you can allow Tcl to process events within an existing event loop. This is useful when Tcl is embedded in an application that already has its own event processing mechanism, such as a GUI toolkit or a network server.

The Tcl_ServiceModeHook and Tcl_SetServiceMode functions can be used to control the blocking behavior of the event loop. By installing a service mode hook, you can perform custom actions before Tcl blocks or to prevent Tcl from blocking altogether. This allows for more flexible integration of Tcl into external event loops.
