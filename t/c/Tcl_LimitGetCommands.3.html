ARGUMENTOS

Tcl_Interp *interp (entrada)
Intérprete al que se aplica el límite que se está administrando o cuyos límites se verificarán.
int type (entrada)
El tipo de límite al que se refiere la operación. Debe ser TCL_LIMIT_COMMANDS o TCL_LIMIT_TIME.
int commandLimit (entrada)
El número máximo de comandos (según lo informado por info cmdcount) que pueden ejecutarse en el intérprete.
Tcl_Time *timeLimitPtr (entrada/salida)
Un puntero a una estructura desde la que se leerá el nuevo límite de tiempo (Tcl_LimitSetTime) o al que se escribirá el límite de tiempo actual (Tcl_LimitGetTime).
int granularity (entrada)
Divisor que indica con qué frecuencia se debe verificar realmente un límite determinado. Debe ser al menos 1.
Tcl_LimitHandlerProc *handlerProc (entrada)
Función a llamar cuando se excede un límite determinado. Si el handlerProc elimina o aumenta el límite durante su procesamiento, se permitirá que el intérprete limitado continúe procesando después de que el manejador regrese. Se pueden adjuntar muchos manejadores al mismo límite del intérprete; su orden de ejecución no está definido y deben ser identificados por handlerProc y clientData cuando se eliminan.
ClientData clientData (entrada)
Palabra arbitraria de tamaño de puntero utilizada para pasar algún contexto a la función handlerProc.
Tcl_LimitHandlerDeleteProc *deleteProc (entrada)
Función a llamar cada vez que se elimina un manejador. Puede ser NULL si el clientData no requiere eliminación.

DESCRIPCION

El subsistema de límites de recursos del intérprete de Tcl permite un control estricto sobre la cantidad de tiempo de cálculo que un script puede utilizar, y es útil para casos en los que un programa se divide en varias partes, donde algunas partes son más confiables que otras (por ejemplo, servidores de aplicaciones web).

Cada intérprete puede tener un límite en el tiempo real de ejecución y un límite en el número de comandos que el intérprete puede ejecutar. Dado que la verificación de estos límites puede ser costosa (especialmente el límite de tiempo), cada límite también tiene una granularidad de verificación, que es un divisor de un recuento interno del número de puntos en el núcleo donde se puede realizar una verificación (que es inmediatamente antes de ejecutar un comando y con una frecuencia no especificada entre la ejecución de comandos, que puede ocurrir en bucles while con cuerpo vacío).

El componente final del motor de límites es un esquema de llamadas de retorno que permite notificaciones sobre cuándo se ha excedido un límite. Estas llamadas de retorno solo pueden proporcionar registro o pueden asignar más recursos al intérprete para permitirle continuar procesando por más tiempo.

Cuando se excede un límite (y las llamadas de retorno se han ejecutado; el orden de ejecución de las llamadas de retorno no está especificado), la ejecución en el intérprete limitado se detiene generando un error y estableciendo una bandera que impide que el comando catch en ese intérprete atrape ese error. Depende del contexto que inició la ejecución en ese intérprete (típicamente el intérprete principal) manejar el error.

API DE VERIFICACIÓN DE LÍMITES

Para verificar los límites de recursos de un intérprete, llame a Tcl_LimitCheck, que devuelve TCL_OK si el límite no se excedió (después de procesar las llamadas de retorno) y TCL_ERROR si el límite se excedió (en cuyo caso también se coloca un mensaje de error en el resultado del intérprete). Esa función solo debe llamarse cuando Tcl_LimitReady devuelve un valor distinto de cero para que se respete la política de granularidad. Esta API está diseñada para ser similar en uso a Tcl_AsyncReady y Tcl_AsyncInvoke.

Al escribir código que puede comportarse como catch con respecto a los errores, solo debe atrapar un error si Tcl_LimitExceeded devuelve cero. Si devuelve un valor distinto de cero, el intérprete se encuentra en un estado de límite excedido y los errores deben permitirse que se propaguen al contexto de llamada. También puede verificar si un tipo particular de límite se ha excedido utilizando Tcl_LimitTypeExceeded.

CONFIGURACIÓN DE LÍMITES

Para verificar si se ha establecido un límite (pero no si realmente se ha excedido) en un intérprete, llame a Tcl_LimitTypeEnabled con el tipo de límite que desea verificar. Para habilitar un límite particular, llame a Tcl_LimitTypeSet y para deshabilitar un límite, llame a Tcl_LimitTypeReset.

El nivel de un límite de comandos se puede establecer usando Tcl_LimitSetCommands y recuperar usando Tcl_LimitGetCommands. De manera similar para un límite de tiempo con Tcl_LimitSetTime y Tcl_LimitGetTime respectivamente, pero con esa API el límite de tiempo se copia desde y hacia la estructura Tcl_Time a la que apunta el argumento timeLimitPtr.

La granularidad de verificación para un límite particular se puede establecer usando Tcl_LimitSetGranularity y recuperar usando Tcl_LimitGetGranularity. Tenga en cuenta que las granularidades deben ser siempre positivas.

LLAMADAS DE RETORNO DE LÍMITES

Para agregar una llamada de retorno de manejador que se invocará cuando se exceda un límite, llame a Tcl_LimitAddHandler. El argumento handlerProc describe la función que realmente se llamará; debe tener el siguiente prototipo:

typedef void Tcl_LimitHandlerProc(
        ClientData clientData,
        Tcl_Interp *interp);

El argumento clientData del manejador será lo que se pase al argumento clientData de Tcl_LimitAddHandler, y interp es el intérprete cuyo límite se excedió.

El argumento deleteProc de Tcl_LimitAddHandler es una función a llamar para eliminar el valor clientData. Puede ser TCL_STATIC o NULL si no se necesita ninguna acción de eliminación, o TCL_DYNAMIC si todo lo que se necesita es liberar la estructura con Tcl_Free. De lo contrario, debe hacer referencia a una función con el siguiente prototipo:

typedef void Tcl_LimitHandlerDeleteProc(
        ClientData clientData);

Un manejador de límites puede eliminarse usando Tcl_LimitRemoveHandler; el manejador eliminado será el primero que se encuentre (entre los manejadores agregados con Tcl_LimitAddHandler) con los argumentos type, handlerProc y clientData que coincidan exactamente. Esta función siempre invoca el deleteProc en el clientData (a menos que el deleteProc sea NULL o TCL_STATIC).
