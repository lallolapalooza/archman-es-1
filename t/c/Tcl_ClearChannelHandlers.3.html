ARGUMENTOS

const Tcl_ChannelType *typePtr (in)
Punta a una estructura que contiene las direcciones de los procedimientos que se pueden llamar para realizar E/S y otras funciones en el canal.
const char *channelName (in)
El nombre de este canal, como file3; no debe estar en uso por ningún otro canal. Puede ser NULL, en cuyo caso el canal se crea sin nombre. Si al canal creado se le asigna uno de los canales estándar (stdin, stdout o stderr), el nombre del canal asignado será el nombre del canal estándar.
ClientData instanceData (in)
Valor arbitrario de una palabra para asociar con este canal. Este valor se pasa a los procedimientos en typePtr cuando se invocan.
int mask (in)
Combinación OR de TCL_READABLE y TCL_WRITABLE para indicar si un canal es legible y escribible.
Tcl_Channel channel (in)
El canal a operar.
int direction (in)
TCL_READABLE significa que se desea el manejador de entrada; TCL_WRITABLE significa que se desea el manejador de salida.
ClientData *handlePtr (out)
Punta a la ubicación donde se debe almacenar el manejador específico del sistema operativo.
int size (in)
El tamaño, en bytes, de los búferes a asignar en este canal.
int mask (in)
Una combinación OR de TCL_READABLE, TCL_WRITABLE y TCL_EXCEPTION que indica los eventos que han ocurrido en este canal.
Tcl_Interp *interp (in)
Intérprete actual. (puede ser NULL)
const char *optionName (in)
Nombre de la opción inválida.
const char *optionList (in)
Lista de opciones específicas (palabras separadas por espacios, sin el carácter “-”) para añadir a la lista estándar de opciones genéricas. Puede ser NULL para un mensaje de error solo de opciones genéricas.

DESCRIPCIÓN

Tcl utiliza una arquitectura de canales de dos capas. Proporciona una capa superior genérica para permitir que los programas C y Tcl realicen entrada y salida utilizando las mismas APIs para una variedad de archivos, dispositivos, sockets, etc. Las APIs genéricas de C se describen en la entrada del manual para Tcl_OpenFileChannel.

La capa inferior proporciona controladores de canales específicos del tipo para cada tipo de dispositivo soportado en cada plataforma. Esta entrada del manual describe las APIs de C utilizadas para comunicarse entre la capa genérica y los controladores de canales específicos del tipo. También explica cómo se pueden añadir nuevos tipos de canales proporcionando nuevos controladores de canales.

Los controladores de canales consisten en varios componentes: Primero, cada controlador de canales proporciona una estructura Tcl_ChannelType que contiene punteros a funciones que implementan las diversas operaciones utilizadas por la capa genérica para comunicarse con el controlador de canales. La estructura Tcl_ChannelType y las funciones referenciadas por ella se describen en la sección TCL_CHANNELTYPE, más abajo.

Segundo, los controladores de canales suelen proporcionar un comando Tcl para crear instancias de ese tipo de canal. Por ejemplo, el comando Tcl open crea canales que utilizan los controladores de canales de archivo y de comando, y el comando Tcl socket crea canales que utilizan sockets TCP para la comunicación en red.

Tercero, un controlador de canales proporciona opcionalmente una función C para abrir instancias de canales de ese tipo. Por ejemplo, Tcl_OpenFileChannel abre un canal que utiliza el controlador de canales de archivo, y Tcl_OpenTcpClient abre un canal que utiliza el protocolo de red TCP. Estas funciones de creación suelen utilizar Tcl_CreateChannel internamente para abrir el canal.

Para añadir un nuevo tipo de canal, debe implementar una API de C o un comando Tcl que abra un canal invocando Tcl_CreateChannel. Cuando su controlador llama a Tcl_CreateChannel, le pasa una estructura Tcl_ChannelType que describe los procedimientos de E/S del controlador. La capa genérica invocará entonces las funciones referenciadas en esa estructura para realizar operaciones en el canal.

Tcl_CreateChannel abre un nuevo canal y asocia los argumentos typePtr e instanceData proporcionados con él. El canal se abre en el modo indicado por mask. Para una discusión sobre los controladores de canales, sus operaciones y la estructura Tcl_ChannelType, véase la sección TCL_CHANNELTYPE, más abajo.

Tcl_CreateChannel interactúa con el código que gestiona los canales estándar. Una vez que se inicializó un canal estándar a través de una llamada a Tcl_GetStdChannel o una llamada a Tcl_SetStdChannel, cerrar este canal estándar provocará que la siguiente llamada a Tcl_CreateChannel convierta el nuevo canal en el nuevo canal estándar también. Véase Tcl_StandardChannels para un tratado general sobre canales estándar y el comportamiento de la biblioteca Tcl con respecto a ellos.

Tcl_GetChannelInstanceData devuelve los datos de instancia asociados con el canal en channel. Esto es lo mismo que el argumento instanceData en la llamada a Tcl_CreateChannel que creó este canal.

Tcl_GetChannelType devuelve un puntero a la estructura Tcl_ChannelType utilizada por el canal en el argumento channel. Esto es lo mismo que el argumento typePtr en la llamada a Tcl_CreateChannel que creó este canal.

Tcl_GetChannelName devuelve una cadena que contiene el nombre asociado con el canal, o NULL si el argumento channelName de Tcl_CreateChannel era NULL.

CLOSEPROC AND CLOSE2PROC

El campo closeProc contiene la dirección de una función que se llama para cerrar un canal. Los canales que no pueden cerrar sus lados de lectura y escritura de forma independiente deben establecer closeProc en la dirección de una función que coincida con el siguiente prototipo:

typedef int Tcl_DriverCloseProc(
        ClientData instanceData,
        Tcl_Interp *interp);

El argumento instanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando se creó el canal. La función debe realizar cualquier acción específica del tipo de canal necesaria para cerrar el canal. Debe devolver cero si la operación de cierre se realizó correctamente; de lo contrario, debe devolver un código de error POSIX distinto de cero. Además, si se produce un error y interp no es NULL, el procedimiento debe almacenar un mensaje de error en el resultado del intérprete.

Alternativamente, los canales que admiten el cierre de los lados de lectura y escritura de forma independiente pueden establecer closeProc en TCL_CLOSE2PROC y establecer close2Proc en la dirección de una función que coincida con el siguiente prototipo:

typedef int Tcl_DriverClose2Proc(
        ClientData instanceData,
        Tcl_Interp *interp,
        int flags);

Se llamará a close2Proc con flags establecido en una combinación OR de TCL_CLOSE_READ o TCL_CLOSE_WRITE para indicar que el controlador debe cerrar el lado de lectura y/o escritura del canal. Es posible que se invoque al controlador del canal para realizar operaciones adicionales en el canal después de que se llame a close2Proc para cerrar uno o ambos lados del canal. Si flags es 0 (cero), el controlador debe cerrar el canal de la manera descrita anteriormente para closeProc. No se invocarán más operaciones en esta instancia después de que se llame a close2Proc con todas las banderas borradas. En todos los casos, la función close2Proc debe devolver cero si la operación de cierre fue exitosa; de lo contrario, debe devolver un código de error POSIX distinto de cero. Además, si ocurre un error y interp no es NULL, el procedimiento debe almacenar un mensaje de error en el resultado del intérprete.

Los valores closeProc y close2Proc se pueden recuperar con Tcl_ChannelCloseProc o Tcl_ChannelClose2Proc, que devuelven un puntero a la función respectiva.

INPUTPROC

El campo inputProc contiene la dirección de una función que la capa genérica llama para leer datos del archivo o dispositivo y almacenarlos en un búfer interno. InputProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverInputProc(
        ClientData instanceData,
        char *buf,
        int bufSize,
        int *errorCodePtr);

InstanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando se creó el canal. El argumento buf apunta a una matriz de bytes en la que se almacenará la entrada del dispositivo, y el argumento bufSize indica cuántos bytes están disponibles en buf.

El argumento errorCodePtr apunta a una variable entera proporcionada por la capa genérica. Si se produce un error, la función debe establecer la variable en un código de error POSIX que identifique el error que ocurrió.

La función debe leer datos del dispositivo de entrada encapsulado por el canal y almacenarlos en buf. En caso de éxito, la función debe devolver un entero no negativo que indique cuántos bytes se leyeron del dispositivo de entrada y se almacenaron en buf. En caso de error, la función debe devolver -1. Si se produce un error después de que se hayan leído algunos datos del dispositivo, esos datos se pierden.

Si inputProc puede determinar que el dispositivo de entrada tiene algunos datos disponibles pero menos de los solicitados por el argumento bufSize, la función solo debe intentar leer tantos datos como estén disponibles y devolver sin bloquear. Si no hay datos disponibles en absoluto en el dispositivo de entrada y el canal está en modo no bloqueante, la función debe devolver un error EAGAIN. Si no hay datos disponibles en absoluto en el dispositivo de entrada y el canal está en modo bloqueante, la función debe bloquearse durante el menor tiempo posible hasta que se puedan leer al menos un byte de datos del dispositivo; luego, debe devolver tantos datos como pueda leer sin bloquear.

Este valor se puede recuperar con Tcl_ChannelInputProc, que devuelve un puntero a la función.

OUTPUTPROC

El campo outputProc contiene la dirección de una función que la capa genérica llama para transferir datos de un búfer interno al dispositivo de salida. OutputProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverOutputProc(
        ClientData instanceData,
        const char *buf,
        int toWrite,
        int *errorCodePtr);

InstanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando se creó el canal. El argumento buf contiene una matriz de bytes que se escribirán en el dispositivo, y el argumento toWrite indica cuántos bytes se escribirán desde el argumento buf.

El argumento errorCodePtr apunta a una variable entera proporcionada por la capa genérica. Si se produce un error, la función debe establecer esta variable en un código de error POSIX que identifique el error.

La función debe escribir los datos en buf en el dispositivo de salida encapsulado por el canal. En caso de éxito, la función debe devolver un entero no negativo que indique cuántos bytes se escribieron en el dispositivo de salida. El valor de retorno es normalmente el mismo que toWrite, pero puede ser menor en algunos casos, como si la operación de salida se interrumpe por una señal. Si se produce un error, la función debe devolver -1. En caso de error, es posible que se hayan escrito algunos datos en el dispositivo.

Si el canal no está bloqueado y el dispositivo de salida no puede absorber ningún dato, la función debe devolver -1 con un error EAGAIN sin escribir ningún dato.

Este valor se puede recuperar con Tcl_ChannelOutputProc, que devuelve un puntero a la función.

SEEKPROC Y WIDESEEKPROC

El campo seekProc contiene la dirección de una función que la capa genérica llama para mover el punto de acceso en el que se aplicarán las operaciones de entrada o salida posteriores. SeekProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverSeekProc(
        ClientData instanceData,
        long offset,
        int seekMode,
        int *errorCodePtr);

El argumento instanceData es el mismo que el valor dado a Tcl_CreateChannel cuando se creó este canal. Offset y seekMode tienen el mismo significado que para el procedimiento Tcl_Seek (descrito en la entrada del manual de Tcl_OpenFileChannel).

El argumento errorCodePtr apunta a una variable entera proporcionada por la capa genérica para devolver valores errno de la función. La función debe establecer esta variable en un código de error POSIX si se produce un error. La función debe almacenar un código de error EINVAL si el tipo de canal no implementa la búsqueda.

El valor de retorno es el nuevo punto de acceso o -1 en caso de error. Si se produjo un error, la función no debe mover el punto de acceso.

Si hay un campo seekProc no NULL, el campo wideSeekProc puede contener la dirección de una función alternativa a utilizar que maneje desplazamientos amplios (es decir, mayores de 32 bits), lo que permite búsquedas dentro de archivos de más de 2 GB. Se llamará a wideSeekProc con preferencia a seekProc, pero ambos deben definirse si se define wideSeekProc. WideSeekProc debe coincidir con el siguiente prototipo:

typedef Tcl_WideInt Tcl_DriverWideSeekProc(
        ClientData instanceData,
        Tcl_WideInt offset,
        int seekMode,
        int *errorCodePtr);

Los argumentos y los valores de retorno significan lo mismo que con seekProc anteriormente, excepto que el tipo de desplazamiento y el tipo de retorno son diferentes.

El valor seekProc se puede recuperar con Tcl_ChannelSeekProc, que devuelve un puntero a la función, y de manera similar, wideSeekProc se puede recuperar con Tcl_ChannelWideSeekProc.

SETOPTIONPROC

El campo setOptionProc contiene la dirección de una función que la capa genérica llama para establecer una opción específica del tipo de canal en un canal. setOptionProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverSetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        const char *newValue);

optionName es el nombre de una opción a establecer y newValue es el nuevo valor de esa opción, como una cadena. instanceData es el mismo que el valor dado a Tcl_CreateChannel cuando se creó este canal. La función debe realizar cualquier acción específica del tipo de canal requerida para implementar el nuevo valor de la opción.

Algunas opciones son manejadas por el código genérico y esta función nunca se llama para establecerlas, por ejemplo, -blockmode. Otras opciones son específicas de cada tipo de canal y se llamará al procedimiento setOptionProc del controlador del canal para implementarlas. El campo setOptionProc puede ser NULL, lo que indica que este tipo de canal no admite opciones específicas del tipo.

Si el valor de la opción se modifica correctamente al nuevo valor, la función devuelve TCL_OK. Debe llamar a Tcl_BadChannelOption, que a su vez devuelve TCL_ERROR si optionName no se reconoce. Si newValue especifica un valor para la opción que no es compatible o si se produce un error en una llamada al sistema, la función debe dejar un mensaje de error en el resultado de interp si interp no es NULL. La función también debe llamar a Tcl_SetErrno para almacenar un código de error POSIX apropiado.

Este valor se puede recuperar con Tcl_ChannelSetOptionProc, que devuelve un puntero a la función.

GETOPTIONPROC

El campo getOptionProc contiene la dirección de una función que la capa genérica llama para obtener el valor de una opción específica del tipo de canal en un canal. getOptionProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverGetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        Tcl_DString *optionValue);

OptionName es el nombre de una opción admitida por este tipo de canal. Si el nombre de la opción no es NULL, la función almacena su valor actual, como una cadena, en la cadena dinámica de Tcl optionValue. Si optionName es NULL, la función almacena en optionValue una lista alterna de todas las opciones admitidas y sus valores actuales. En caso de éxito, la función devuelve TCL_OK. Debe llamar a Tcl_BadChannelOption, que a su vez devuelve TCL_ERROR si el op tionName no es reconocido. Si ocurre un error de llamada al sistema, la función debe dejar un mensaje de error en el resultado de interp si interp no es NULL. La función también debe llamar a Tcl_SetErrno para almacenar un código de error POSIX apropiado.

Algunas opciones son manejadas por el código genérico y esta función nunca se llama para recuperar su valor, por ejemplo, -blockmode. Otras opciones son específicas de cada tipo de canal y se llamará al procedimiento getOptionProc del controlador del canal para implementarlas. El campo getOptionProc puede ser NULL, lo que indica que este tipo de canal no admite opciones específicas del tipo.

Este valor puede recuperarse con Tcl_ChannelGetOptionProc, que devuelve un puntero a la función.

WATCHPROC

El campo watchProc contiene la dirección de una función llamada por la capa genérica para inicializar el mecanismo de notificación de eventos para detectar eventos de interés en este canal. WatchProc debe coincidir con el siguiente prototipo:

typedef void Tcl_DriverWatchProc(
        ClientData instanceData,
        int mask);

InstanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando se creó este canal. El argumento mask es una combinación OR de TCL_READABLE, TCL_WRITABLE y TCL_EXCEPTION; indica los eventos que el llamador está interesado en detectar en este canal.

La función debe inicializar mecanismos específicos del tipo de dispositivo para detectar cuándo hay un evento de interés presente en el canal. Cuando ocurre uno o más de los eventos designados en el canal, el controlador del canal es responsable de llamar a Tcl_NotifyChannel para informar al módulo genérico de canales. El controlador debe tener cuidado de no dejar sin atender a otros controladores de canales o fuentes de callbacks invocando Tcl_NotifyChannel con demasiada frecuencia. La equidad puede asegurarse utilizando la cola de eventos de Tcl para permitir que el evento del canal se programe en secuencia con otros eventos. Consulte la descripción de Tcl_QueueEvent para obtener detalles sobre cómo poner en cola un evento.

Este valor puede recuperarse con Tcl_ChannelWatchProc, que devuelve un puntero a la función.

GETHANDLEPROC

El campo getHandleProc contiene la dirección de una función llamada por la capa genérica para recuperar un manejador específico del dispositivo del canal. GetHandleProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverGetHandleProc(
        ClientData instanceData,
        int direction,
        ClientData *handlePtr);

InstanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando se creó este canal. El argumento direction es TCL_READABLE para recuperar el manejador utilizado para la entrada, o TCL_WRITABLE para recuperar el manejador utilizado para la salida.

Si la implementación del canal tiene manejadores específicos del dispositivo, la función debe recuperar el manejador apropiado asociado con el canal, según el argumento direction. El manejador debe almacenarse en la ubicación a la que apunta handlePtr, y se debe devolver TCL_OK. Si el canal no está abierto para la dirección especificada, o si la implementación del canal no utiliza manejadores de dispositivo, la función debe devolver TCL_ERROR.

Este valor puede recuperarse con Tcl_ChannelGetHandleProc, que devuelve un puntero a la función.

FLUSHPROC

El campo flushProc está actualmente reservado para uso futuro. Debe establecerse en NULL. FlushProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverFlushProc(
        ClientData instanceData);

Este valor puede recuperarse con Tcl_ChannelFlushProc, que devuelve un puntero a la función.

HANDLERPROC

El campo handlerProc contiene la dirección de una función llamada por la capa genérica para notificar al canal que ocurrió un evento. Debe definirse para controladores de canales apilados que deseen ser notificados de eventos que ocurren en el canal subyacente (apilado). HandlerProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverHandlerProc(
        ClientData instanceData,
        int interestMask);

InstanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando se creó este canal. interestMask es una combinación OR de TCL_READABLE o TCL_WRITABLE; indica qué tipo de evento ocurrió en este canal.

Este valor puede recuperarse con Tcl_ChannelHandlerProc, que devuelve un puntero a la función.

THREADACTIONPROC

El campo threadActionProc contiene la dirección de la función llamada por la capa genérica cuando se crea, cierra o va a moverse un canal a un hilo diferente, es decir, siempre que el estado del controlador específico del hilo deba inicializarse o actualizarse. Puede ser NULL. La acción TCL_CHANNEL_THREAD_REMOVE se utiliza para notificar al controlador que debe actualizar o eliminar cualquier dato específico del hilo que pueda estar manteniendo para el canal.

La acción TCL_CHANNEL_THREAD_INSERT se utiliza para notificar al controlador que debe actualizar o inicializar cualquier dato específico del hilo que pueda estar manteniendo utilizando el hilo que llama como asociado. Consulte Tcl_CutChannel y Tcl_SpliceChannel para obtener más detalles.

typedef void Tcl_DriverThreadActionProc(
        ClientData instanceData,
        int action);

InstanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando se creó este canal.

Estos valores pueden recuperarse con Tcl_ChannelThreadActionProc, que devuelve un puntero a la función.

TRUNCATEPROC

El campo truncateProc contiene la dirección de la función llamada por la capa genérica cuando se trunca un canal a cierta longitud. Puede ser NULL.

typedef int Tcl_DriverTruncateProc(
        ClientData instanceData,
        Tcl_WideInt length);

InstanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando se creó este canal, y length es la nueva longitud del archivo subyacente, que no debe ser negativa. El resultado debe ser 0 en caso de éxito o un código errno (adecuado para usar con Tcl_SetErrno) en caso de fallo.

Estos valores pueden recuperarse con Tcl_ChannelTruncateProc, que devuelve un puntero a la función.

TCL_BADCHANNELOPTION

Este procedimiento genera un mensaje de error de "opción no válida" en un intérprete (opcional). Lo utilizan los controladores de canales cuando se solicita una opción de Establecer/Obtener no válida. Su propósito es concatenar la lista de opciones genéricas a las específicas y factorizar el mensaje de error de las opciones genéricas.

Siempre devuelve TCL_ERROR.

Se genera un mensaje de error en el valor de resultado de interp para indicar que se invocó un comando con una opción incorrecta. El mensaje tiene el formato

    opción incorrecta "blah": debería ser una de
    <...opciones genéricas...>+<...opciones específicas...>
por lo que se obtiene, por ejemplo: 
    opción incorrecta "-blah": debería ser una de -blocking,
    -buffering, -buffersize, -eofchar, -translation,
    -peername, o -sockname
cuando se llama con optionList igual a “peername sockname”

“blah” es el argumento optionName y “<opciones específicas>” es una lista separada por espacios de palabras de opción específicas. La función se encarga de insertar signos menos antes de cada opción, comas después y un “o” antes de la última opción.

TIPOS DE CANAL ANTIGUOS

La estructura original (8.3.1 y anteriores) Tcl_ChannelType contiene los siguientes campos:

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
} Tcl_ChannelType;

Todavía es posible crear canales con la estructura anterior. El código interno del canal determinará la versión. Es imperativo utilizar la nueva estructura Tcl_ChannelType si está creando un controlador de canal apilado, debido a problemas con la implementación anterior de canales apilados (en 8.2.0 a 8.3.1).

Antes de 8.4.0 (es decir, durante los últimos lanzamientos de 8.3 y la parte inicial del ciclo de desarrollo de 8.4), la estructura Tcl_ChannelType contenía los siguientes campos:

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_ChannelTypeVersion version;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverFlushProc *flushProc;
    Tcl_DriverHandlerProc *handlerProc;
    Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

Cuando la estructura anterior se registra como un tipo de canal, el campo version siempre debe ser TCL_CHANNEL_VERSION_2.
