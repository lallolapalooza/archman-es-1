DESCRIPCIÓN

Tcl usa una arquitectura de canales de dos capas. Proporciona una capa superior genérica para que programas C y Tcl puedan realizar entrada y salida usando los mismos APIs para diversos archivos, dispositivos, sockets etc. Las APIs de C genéricas se describen en el manual de entrada Tcl_OpenFileChannel.

La capa inferior proporciona drivers de canal específicos para cada tipo de dispositivo soportado en cada plataforma. Este manual describe las APIs C que comunican entre la capa genérica y los drivers de canal específicos. También explica cómo se pueden añadir nuevos tipos de canales proporcionando nuevos drivers de canal.

Los drivers de canal consisten en varios componentes: Primero, cada driver de canal proporciona un Tcl_CanalTipo estructura que contiene punteros a funciones implementando las operaciones diferentes utilizadas por la capa genérica para comunicarse con el driver de canal. El Tcl_CanalTipo estructura y las funciones referenciadas por ella se describen en la sección TCL_CANALTIPO, a continuación.

Segundo, los drivers de canal suelen proporcionar una commande Tcl para crear instancias de ese tipo de canal. Por ejemplo, el comando Tcl open crea canales que usan los drivers de canal de archivo y comandos, y el comando Tcl socket crea canales que usan protocolos de sockets TCP para comunicaciones de red.

Tercero, un driver de canal opcionalmente proporciona una función C para abrir instancias de ese tipo de canal. Por ejemplo, Tcl_OpenFileChannel abre un canal que usa el driver de canal de archivo, y Tcl_OpenTcpClient abre un canal que usa el protocolo de red TCP. Estas funciones de creación generalmente usan Tcl_CrearCanal internamente para abrir el canal.

Para añadir un nuevo tipo de canal, debe implementar una API C o una commande Tcl que abra un canal invocando Tcl_CrearCanal. Cuando su driver llama a Tcl_CrearCanal, pasa un Tcl_CanalTipo estructura describiendo las procedimientos de entrada/salida de su driver. La capa genérica luego invoca las funciones referenciadas en esa estructura para realizar operaciones en el canal.

Tcl_CrearCanal abre un nuevo canal y asociará el tipoPtr y datosCanal con él. El canal se abre en el modo indicado por mascara. Para una discusión sobre los drivers de canal, sus operaciones y la estructura Tcl_CanalTipo, vea la sección TCL_CANALTIPO, a continuación.

Tcl_CrearCanal interactúa con el código que gestiona los canales estándar. Una vez que un canal estándar fue inicializado mediante una llamada a Tcl_GetStdChannel o una llamada a Tcl_SetStdChannel, el cierre de este canal causará que la próxima llamada a Tcl_CrearCanal haga del nuevo canal el nuevo canal estándar también. Vea Tcl_StandardsChannels para una discusión general sobre canales estándar y el comportamiento de la biblioteca Tcl con respecto a ellos.

Tcl_GetCanalDatos devuelve el datosCanal asociado con el canal en canal. Esto es el mismo que el datosCanal argumento en la llamada a Tcl_CrearCanal que creó este canal.

Tcl_GetCanalTipo devuelve un puntero al Tcl_CanalTipo estructura utilizado por el canal en el canal argumento. Esto es el mismo que el tipoPtr argumento en la llamada a Tcl_CrearCanal que creó este canal.

Tcl_GetCanalNombre devuelve una cadena con el nombre asociado con el canal, o NULL si el argumento canalNombre de Tcl_CrearCanal fue NULL.

Tcl_GetCanalTrea devuelve el ID del hilo que posee el canal canal. Si el canal no es propiedad de ningún hilo (por ejemplo, si se creó antes de que el intérprete se asociara con un hilo), Tcl_TreaIdReturns NULL.

Tcl_GetCanalHandle coloca el handle de sistema operativo asociado con canal para el dado dirección en el lugar handlePtr.

Tcl_GetCanalModo devuelve el modo actual del canal canal.

Tcl_GetCanalTamañoBuffer devuelve el tamaño en bytes del búffer de entrada/salida para el canal canal.

Tcl_SetCanalTamañoBuffer establece el tamaño en bytes del búffer de entrada/salida para el canal canal.

Tcl_NotificarCanal se invoca cuando ocurre un evento en el canal canal, y la mascara contiene información sobre qué tipo de evento ocurrió (por ejemplo, si el canal está listo para ser leído, escrito, o si ha ocurrido un error).

Tcl_ErrorsCanal genera un mensaje de error estándar para la opción opciónNombre, incluyendo el texto de la opción en listaOpciones, si está presente. La opción opciónNombre debe ser una de las opciones que Tcl entiende para canales de entrada/salida genéricos. Si opciónNombre no es reconocida, Tcl la trata como una opción genérica del driver de canal.

Tcl_IsCanalCompartido devuelve verdadero si el canal canal es compartido entre múltiples intérpretes Tcl.

Tcl_IsCanalRegistrado devuelve verdadero si el canal canal está registrado en el intérprete interprete.

Tcl_IsCanalExistente devuelve verdadero si existe un canal con el nombre nombreCanal en el intérprete actual.

Tcl_CutCanal remueve el canal canal de la tabla de canales del intérprete, pero no lo cierra ni libera sus recursos. Esto es útil para mover un canal a otro intérprete o para asociarlo con un nombre diferente.

Tcl_SpliceCanal hace lo opuesto a Tcl_CutCanal: reinserta un canal previamente cortado en la tabla de canales del intérprete.

Tcl_ClearCanalHandlers remueve todos los manejadores de eventos del canal canal.

Las siguientes funciones se utilizan para consultar información sobre una estructura Tcl_CanalTipo:

Tcl_GetCanalNombre devuelve el nombre del driver de canal asociado con tipoPtr.

Tcl_GetCanalVersión devuelve la versión de la estructura Tcl_CanalTipo.

Tcl_CanalBloquearModoProc devuelve el procedimiento de bloqueo de modo del driver.

Tcl_CanalCerrarProc devuelve el procedimiento de cierre del driver.

Tcl_CanalCerrar2Proc devuelve el procedimiento de cierre2 del driver.

Tcl_CanalEntradaProc devuelve el procedimiento de entrada del driver.

Tcl_CanalSalidaProc devuelve el procedimiento de salida del driver.

Tcl_CanalPausaProc devuelve el procedimiento de pausa del driver.

Tcl_CanalTruncarProc devuelve el procedimiento de truncamiento del driver.

Tcl_CanalSetOpciónProc devuelve el procedimiento de establecimiento de opciones del driver.

Tcl_CanalGetOpciónProc devuelve el procedimiento de obtención de opciones del driver.

Tcl_CanalVerificarProc devuelve el procedimiento de verificación del driver.

Tcl_CanalObtenerHandleProc devuelve el procedimiento de obtención de handle del driver.

Tcl_CanalLimpiarProc devuelve el procedimiento de limpieza del driver.

Tcl_CanalHandlerProc devuelve el procedimiento de manejador del driver.

Tcl_GetChannelThread devuelve el id del hilo que está gestionando actualmente el canal especificado. Esto permite a los drivers de canal enviar sus eventos de archivo a la cola de eventos correcta, incluso para un núcleo multi-hilo.

El argumento size debe estar entre uno y un millón, permitiendo búferes de un byte a un millón de bytes. Si size está fuera de este rango, Tcl_SetChannelBufferSize establece el tamaño del búfer a 4096.

Los drivers de canal son responsables de invocar esta función cada vez que los manejadores de canal necesiten ser llamados para el canal (o se deban realizar otras tareas pendientes como un vaciado de escritura). Consulte WATCHPROC a continuación para más detalles.

Tcl_BadChannelOption es llamada desde el setOptionProc o getOptionProc específico del driver para generar un mensaje de error completo.

Tcl_IsChannelRegistered comprueba si el canal especificado está registrado en el intérprete (hilo) dado (resultado == 1) o no (resultado == 0).

Tcl_IsChannelExisting comprueba si un canal con el nombre especificado está registrado en la lista global (de hilo) de todos los canales (resultado == 1) o no (resultado == 0).

No se permite la aplicación a un canal que todavía está registrado en algún intérprete. Tcl_SpliceChannel agrega el canal especificado a la lista global (de hilo) de todos los canales (del hilo actual). No se permite la aplicación a un canal registrado en algún intérprete. También notifica al driver si la versión de Tcl_ChannelType es TCL_CHANNEL_VERSION_4 (o superior), y Tcl_DriverThreadActionProc está definida para él.

Tcl_ClearChannelHandlers elimina todos los manejadores de canal y scripts de eventos asociados con el canal especificado, cerrando así todo el procesamiento de eventos para este canal.

TCL_CHANNELTYPE

Un driver de canal proporciona una estructura Tcl_ChannelType que contiene punteros a funciones que implementan las diversas operaciones en un canal; estas operaciones se invocan según sea necesario por la capa genérica. La estructura fue versionada a partir de Tcl 8.3.2/8.4 para corregir un problema con los canales apilados. Consulte la sección OLD CHANNEL TYPES a continuación para más detalles sobre la estructura antigua.

La estructura Tcl_ChannelType contiene los siguientes campos:

typedef struct Tcl_ChannelType {
        const char *typeName;
        Tcl_ChannelTypeVersion version;
        Tcl_DriverCloseProc *closeProc;
        Tcl_DriverInputProc *inputProc;
        Tcl_DriverOutputProc *outputProc;
        Tcl_DriverSeekProc *seekProc;
        Tcl_DriverSetOptionProc *setOptionProc;
        Tcl_DriverGetOptionProc *getOptionProc;
        Tcl_DriverWatchProc *watchProc;
        Tcl_DriverGetHandleProc *getHandleProc;
        Tcl_DriverClose2Proc *close2Proc;
        Tcl_DriverBlockModeProc *blockModeProc;
        Tcl_DriverFlushProc *flushProc;
        Tcl_DriverHandlerProc *handlerProc;
        Tcl_DriverWideSeekProc *wideSeekProc;
        Tcl_DriverThreadActionProc *threadActionProc;
        Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

No es necesario proporcionar implementaciones para todas las operaciones de canal. Aquellas que no son necesarias pueden establecerse a NULL en la estructura: blockModeProc, seekProc, setOptionProc, getOptionProc, getHandleProc y close2Proc, además de flushProc, handlerProc, threadActionProc y truncateProc. Otras funciones que no se pueden implementar de forma significativa deben devolver EINVAL cuando se llaman, para indicar que las operaciones que representan no están disponibles. Tenga en cuenta también que wideSeekProc puede ser NULL si seekProc lo es.

El usuario solo debe usar la estructura anterior para la instanciación de Tcl_ChannelType. Al referenciar campos en una estructura Tcl_ChannelType, se deben usar las siguientes funciones para obtener los valores: Tcl_ChannelName, Tcl_ChannelVersion, Tcl_ChannelBlockModeProc, Tcl_ChannelCloseProc, Tcl_ChannelClose2Proc, Tcl_ChannelInputProc, Tcl_ChannelOutputProc, Tcl_ChannelSeekProc, Tcl_ChannelWideSeekProc, Tcl_ChannelThreadActionProc, Tcl_ChannelTruncateProc, Tcl_ChannelSetOptionProc, Tcl_ChannelGetOptionProc, Tcl_ChannelWatchProc, Tcl_ChannelGetHandleProc, Tcl_ChannelFlushProc o Tcl_ChannelHandlerProc.

El cambio en las estructuras se realizó de tal manera que los tipos de canal estándar son binariamente compatibles. Sin embargo, los tipos de canal que utilizan canales apilados (es decir, TLS, Trf) tienen nuevas versiones para corresponder al cambio anterior, ya que el código anterior para canales apilados tenía problemas.

TYPENAME

El campo typeName contiene una cadena terminada en nulo que identifica el tipo de dispositivo implementado por este driver, por ejemplo, file o socket.

Este valor se puede recuperar con Tcl_ChannelName, que devuelve un puntero a la cadena.

VERSION

El campo version debe establecerse a la versión de la estructura que necesita. TCL_CHANNEL_VERSION_2 es el mínimo recomendado. TCL_CHANNEL_VERSION_3 debe establecerse para especificar el miembro wideSeekProc. TCL_CHANNEL_VERSION_4 debe establecerse para especificar el miembro threadActionProc (incluye wideSeekProc). TCL_CHANNEL_VERSION_5 debe establecerse para especificar los miembros truncateProc (incluye wideSeekProc y threadActionProc). Si no se establece en ninguna de estas, entonces se asume que este Tcl_ChannelType tiene la estructura original. Consulte OLD CHANNEL TYPES para más detalles. Mientras Tcl reconocerá y funcionará con ambas estructuras, los canales apilados deben ser de al menos TCL_CHANNEL_VERSION_2 para funcionar correctamente.

Este valor se puede recuperar con Tcl_ChannelVersion, que devuelve uno de TCL_CHANNEL_VERSION_5, TCL_CHANNEL_VERSION_4, TCL_CHANNEL_VERSION_3, TCL_CHANNEL_VERSION_2 o TCL_CHANNEL_VERSION_1.

BLOCKMODEPROC

El campo blockModeProc contiene la dirección de una función llamada por la capa genérica para establecer el modo de bloqueo y no bloqueo en el dispositivo. BlockModeProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverBlockModeProc(
        ClientData instanceData,
        int mode);

El instanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando se creó este canal. El argumento mode es TCL_MODE_BLOCKING o TCL_MODE_NONBLOCKING para establecer el dispositivo en modo de bloqueo o no bloqueo. La función debe devolver cero si la operación fue exitosa, o un código de error POSIX distinto de cero si la operación falló.

Si la operación es exitosa, la función puede modificar el instanceData proporcionado para registrar que el canal entró en modo de bloqueo o no bloqueo y para implementar el comportamiento de bloqueo o no bloqueo. Para algunos tipos de dispositivo, el comportamiento de bloqueo y no bloqueo puede ser implementado por el sistema operativo subyacente; para otros tipos de dispositivo, el comportamiento debe ser emulado en el driver del canal.

Este valor se puede recuperar con Tcl_ChannelBlockModeProc, que devuelve un puntero a la función.

Un driver de canal que **no** proporciona un blockModeProc debe ser muy, muy cuidadoso. Debe informar a la capa genérica exactamente qué modo de bloqueo es aceptable para él, y también debe documentar esto para el usuario, de modo que el modo de bloqueo del canal no se cambie a un valor inaceptable. Cualquier confusión aquí puede llevar al intérprete a un punto muerto (falso y difícil de encontrar).

CLOSEPROC Y CLOSE2PROC

El campo closeProc contiene la dirección de una función llamada por la capa genérica para limpiar la información relacionada con el driver cuando el canal se cierra. CloseProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverCloseProc(
        ClientData instanceData,
        Tcl_Interp *interp);

El argumento instanceData es el mismo que el valor proporcionado a Tcl_CreateChannel cuando se creó el canal. La función debe liberar cualquier almacenamiento mantenido por el driver del canal para este canal, y cerrar los dispositivos de entrada y salida encapsulados por este canal. Toda la salida en cola se habrá vaciado al dispositivo antes de que se llame a esta función, y no se invocarán más operaciones del driver en esta instancia después de llamar a closeProc. Si la operación de cierre es exitosa, el procedimiento debe

return zero; de lo contrario, debería devolver un código de error POSIX distinto de cero. Además, si ocurre un error y interp no es NULL, el procedimiento debe almacenar un mensaje de error en el resultado del intérprete.

Alternativamente, los canales que admiten el cierre de los lados de lectura y escritura de forma independiente pueden establecer closeProc en TCL_CLOSE2PROC y close2Proc a la dirección de una función que coincida con el siguiente prototipo:

typedef int Tcl_DriverClose2Proc(
        ClientData instanceData,
        Tcl_Interp *interp,
        int flags);

Se llamará a close2Proc con flags establecido en una combinación OR de TCL_CLOSE_READ o TCL_CLOSE_WRITE para indicar que el controlador debe cerrar el lado de lectura y/o escritura del canal. Se puede invocar al controlador del canal para realizar operaciones adicionales en el canal después de que se llame a close2Proc para cerrar uno o ambos lados del canal. Si flags es 0 (cero), el controlador debe cerrar el canal de la manera descrita anteriormente para closeProc. No se invocarán más operaciones en esta instancia después de que se llame a close2Proc con todas las banderas despejadas. En todos los casos, la función close2Proc debe devolver cero si la operación de cierre fue exitosa; de lo contrario, debe devolver un código de error POSIX distinto de cero. Además, si ocurre un error y interp no es NULL, el procedimiento debe almacenar un mensaje de error en el resultado del intérprete.

Los valores closeProc y close2Proc se pueden recuperar con Tcl_ChannelCloseProc o Tcl_ChannelClose2Proc, que devuelven un puntero a la función respectiva.

INPUTPROC

El campo inputProc contiene la dirección de una función llamada por la capa genérica para leer datos del archivo o dispositivo y almacenarlos en un búfer interno. InputProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverInputProc(
        ClientData instanceData,
        char *buf,
        int bufSize,
        int *errorCodePtr);

InstanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando se creó el canal. El argumento buf apunta a una matriz de bytes en la que se almacenará la entrada del dispositivo, y el argumento bufSize indica cuántos bytes están disponibles en buf.

El argumento errorCodePtr apunta a una variable entera proporcionada por la capa genérica. Si ocurre un error, la función debe establecer la variable en un código de error POSIX que identifique el error ocurrido.

La función debe leer datos del dispositivo de entrada encapsulado por el canal y almacenarlos en buf. En caso de éxito, la función debe devolver un entero no negativo que indique cuántos bytes se leyeron del dispositivo de entrada y se almacenaron en buf. En caso de error, la función debe devolver -1. Si ocurre un error después de que se hayan leído algunos datos del dispositivo, esos datos se pierden.

Si inputProc puede determinar que el dispositivo de entrada tiene algunos datos disponibles pero menos de lo solicitado por el argumento bufSize, la función solo debe intentar leer tantos datos como estén disponibles y devolverlos sin bloquear. Si el dispositivo de entrada no tiene datos disponibles en absoluto y el canal está en modo de no bloqueo, la función debe devolver un error EAGAIN. Si el dispositivo de entrada no tiene datos disponibles en absoluto y el canal está en modo de bloqueo, la función debe bloquearse durante el menor tiempo posible hasta que se pueda leer al menos un byte de datos del dispositivo; luego, debe devolver tantos datos como pueda leer sin bloquear.

Este valor se puede recuperar con Tcl_ChannelInputProc, que devuelve un puntero a la función.

OUTPUTPROC

El campo outputProc contiene la dirección de una función llamada por la capa genérica para transferir datos de un búfer interno al dispositivo de salida. OutputProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverOutputProc(
        ClientData instanceData,
        const char *buf,
        int toWrite,
        int *errorCodePtr);

InstanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando se creó el canal. El argumento buf contiene una matriz de bytes que se escribirán en el dispositivo, y el argumento toWrite indica cuántos bytes se escribirán desde el argumento buf.

El argumento errorCodePtr apunta a una variable entera proporcionada por la capa genérica. Si ocurre un error, la función debe establecer esta variable en un código de error POSIX que identifique el error.

La función debe escribir los datos en buf en el dispositivo de salida encapsulado por el canal. En caso de éxito, la función debe devolver un entero no negativo que indique cuántos bytes se escribieron en el dispositivo de salida. El valor de retorno es normalmente el mismo que toWrite, pero puede ser menor en algunos casos, como si la operación de salida se interrumpe por una señal. Si ocurre un error, la función debe devolver -1. En caso de error, es posible que se hayan escrito algunos datos en el dispositivo.

Si el canal está en modo de no bloqueo y el dispositivo de salida no puede absorber ningún dato en absoluto, la función debe devolver -1 con un error EAGAIN sin escribir ningún dato.

Este valor se puede recuperar con Tcl_ChannelOutputProc, que devuelve un puntero a la función.

SEEKPROC Y WIDESEEKPROC

El campo seekProc contiene la dirección de una función llamada por la capa genérica para mover el punto de acceso en el que se aplicarán las operaciones de entrada o salida posteriores. SeekProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverSeekProc(
        ClientData instanceData,
        long offset,
        int seekMode,
        int *errorCodePtr);

El argumento instanceData es el mismo que el valor dado a Tcl_CreateChannel cuando se creó este canal. Offset y seekMode tienen el mismo significado que para el procedimiento Tcl_Seek (descrito en la entrada del manual de Tcl_OpenFileChannel).

El argumento errorCodePtr apunta a una variable entera proporcionada por la capa genérica para devolver valores errno de la función. La función debe establecer esta variable en un código de error POSIX si ocurre un error. La función debe almacenar un código de error EINVAL si el tipo de canal no implementa la búsqueda.

El valor de retorno es el nuevo punto de acceso o -1 en caso de error. Si ocurrió un error, la función no debe mover el punto de acceso.

Si hay un campo seekProc no NULL, el campo wideSeekProc puede contener la dirección de una función alternativa a utilizar que maneja desplazamientos anchos (es decir, mayores de 32 bits), permitiendo así búsquedas dentro de archivos de más de 2 GB. Se llamará a wideSeekProc con preferencia a seekProc, pero ambos deben definirse si se define wideSeekProc. WideSeekProc debe coincidir con el siguiente prototipo:

typedef Tcl_WideInt Tcl_DriverWideSeekProc(
        ClientData instanceData,
        Tcl_WideInt offset,
        int seekMode,
        int *errorCodePtr);

Los argumentos y los valores de retorno significan lo mismo que con seekProc arriba, excepto que el tipo de los desplazamientos y el tipo de retorno son diferentes.

El valor seekProc se puede recuperar con Tcl_ChannelSeekProc, que devuelve un puntero a la función, y de manera similar el wideSeekProc se puede recuperar con Tcl_ChannelWideSeekProc.

SETOPTIONPROC

El campo setOptionProc contiene la dirección de una función llamada por la capa genérica para establecer una opción específica del tipo de canal en un canal. setOptionProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverSetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        const char *newValue);

optionName es el nombre de una opción a establecer, y newValue es el nuevo valor para esa opción, como una cadena. El instanceData es el mismo que el valor dado a Tcl_CreateChannel cuando se creó este canal. La función debe realizar cualquier acción específica del tipo de canal requerida para implementar el nuevo valor de la opción.

Algunas opciones son manejadas por el código genérico y esta función nunca se llama para establecerlas, por ejemplo, -blockmode. Otras opciones son específicas de cada tipo de canal y se llamará al procedimiento setOptionProc del controlador del canal para implementarlas. El campo setOptionProc puede ser NULL, lo que indica que este tipo de canal no admite opciones específicas del tipo.

Si el valor de la opción se modifica correctamente al nuevo valor, la función devuelve TCL_OK. Debe llamar a Tcl_BadChannelOption, que a su vez devuelve TCL_ERROR si optionName no se reconoce. Si newValue especifica un valor para la opción que no se admite o si ocurre un error de llamada al sistema, la función debe dejar un mensaje de error en el resultado de interp si interp no es NULL. La función también debe llamar a Tcl_SetErrno para almacenar un código de error POSIX apropiado.

Este valor se puede recuperar con Tcl_ChannelSetOptionProc, que devuelve un puntero a la función.

GETOPTIONPROC

El campo getOptionProc contiene la dirección de una función llamada por la capa genérica para obtener el valor de una opción específica del tipo de canal en un canal. getOptionProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverGetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        Tcl_DString *optionValue);

OptionName es el nombre de una opción compatible con este tipo de canal. Si el nombre de la opción no es NULL, la función almacena su valor actual, como una cadena, en la cadena dinámica Tcl optionValue. Si optionName es NULL, la función almacena en optionValue una lista alterna de todas las opciones compatibles y sus valores actuales. En caso de éxito, la función devuelve TCL_OK. Debe llamar a Tcl_BadChannelOption, que a su vez devuelve TCL_ERROR si el optionName no es reconocido. Si ocurre un error del sistema, la función debe dejar un mensaje de error en el resultado de interp si interp no es NULL. La función también debe llamar a Tcl_SetErrno para almacenar un código de error POSIX apropiado.

Algunas opciones son manejadas por el código genérico y esta función nunca es llamada para recuperar su valor, por ejemplo, -blockmode. Otras opciones son específicas para cada tipo de canal y se llamará al procedimiento getOptionProc del controlador del canal para implementarlas. El campo getOptionProc puede ser NULL, lo que indica que este tipo de canal no soporta opciones específicas del tipo.

Este valor puede recuperarse con Tcl_ChannelGetOptionProc, que devuelve un puntero a la función.

WATCHPROC

El campo watchProc contiene la dirección de una función llamada por la capa genérica para inicializar el mecanismo de notificación de eventos para detectar eventos de interés en este canal. WatchProc debe coincidir con el siguiente prototipo:

typedef void Tcl_DriverWatchProc(
        ClientData instanceData,
        int mask);

InstanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó este canal. El argumento mask es una combinación OR de TCL_READABLE, TCL_WRITABLE y TCL_EXCEPTION; indica los eventos que el llamador está interesado en detectar en este canal.

La función debe inicializar mecanismos específicos del tipo de dispositivo para detectar cuándo ocurre un evento de interés en el canal. Cuando ocurre uno o más de los eventos designados en el canal, el controlador del canal es responsable de llamar a Tcl_NotifyChannel para informar al módulo genérico del canal. El controlador debe tener cuidado de no agotar otros controladores de canal o fuentes de devoluciones de llamada invocando Tcl_NotifyChannel con demasiada frecuencia. La justicia se puede asegurar utilizando la cola de eventos de Tcl para permitir que el evento del canal se programe en secuencia con otros eventos. Vea la descripción de Tcl_QueueEvent para obtener detalles sobre cómo poner en cola un evento.

Este valor puede recuperarse con Tcl_ChannelWatchProc, que devuelve un puntero a la función.

GETHANDLEPROC

El campo getHandleProc contiene la dirección de una función llamada por la capa genérica para recuperar un manejador específico del dispositivo del canal. GetHandleProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverGetHandleProc(
        ClientData instanceData,
        int direction,
        ClientData *handlePtr);

InstanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó este canal. El argumento direction es TCL_READABLE para recuperar el manejador utilizado para la entrada, o TCL_WRITABLE para recuperar el manejador utilizado para la salida.

Si la implementación del canal tiene manejadores específicos del dispositivo, la función debe recuperar el manejador apropiado asociado con el canal, según el argumento direction. El manejador debe almacenarse en la ubicación a la que apunta handlePtr, y se debe devolver TCL_OK. Si el canal no está abierto para la dirección especificada, o si la implementación del canal no utiliza manejadores de dispositivo, la función debe devolver TCL_ERROR.

Este valor puede recuperarse con Tcl_ChannelGetHandleProc, que devuelve un puntero a la función.

FLUSHPROC

El campo flushProc está actualmente reservado para uso futuro. Debe establecerse en NULL. FlushProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverFlushProc(
        ClientData instanceData);

Este valor puede recuperarse con Tcl_ChannelFlushProc, que devuelve un puntero a la función.

HANDLERPROC

El campo handlerProc contiene la dirección de una función llamada por la capa genérica para notificar al canal que ocurrió un evento. Debe definirse para controladores de canal apilados que deseen ser notificados de eventos que ocurren en el canal subyacente (apilado). HandlerProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverHandlerProc(
        ClientData instanceData,
        int interestMask);

InstanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó este canal. El interestMask es una combinación OR de TCL_READABLE o TCL_WRITABLE; indica qué tipo de evento ocurrió en este canal.

Este valor puede recuperarse con Tcl_ChannelHandlerProc, que devuelve un puntero a la función.

THREADACTIONPROC

El campo threadActionProc contiene la dirección de la función llamada por la capa genérica cuando se crea, se cierra o se va a mover un canal a un hilo diferente, es decir, cada vez que el estado específico del controlador del hilo pueda tener que inicializarse o actualizarse. Puede ser NULL. La acción TCL_CHANNEL_THREAD_REMOVE se utiliza para notificar al controlador que debe actualizar o eliminar cualquier dato específico del hilo que pueda estar manteniendo para el canal.

La acción TCL_CHANNEL_THREAD_INSERT se utiliza para notificar al controlador que debe actualizar o inicializar cualquier dato específico del hilo que pueda estar manteniendo utilizando el hilo llamador como asociado. Consulte Tcl_CutChannel y Tcl_SpliceChannel para obtener más detalles.

typedef void Tcl_DriverThreadActionProc(
        ClientData instanceData,
        int action);

InstanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó este canal.

Estos valores pueden recuperarse con Tcl_ChannelThreadActionProc, que devuelve un puntero a la función.

TRUNCATEPROC

El campo truncateProc contiene la dirección de la función llamada por la capa genérica cuando un canal se trunca a cierta longitud. Puede ser NULL.

typedef int Tcl_DriverTruncateProc(
        ClientData instanceData,
        Tcl_WideInt length);

InstanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó este canal, y length es la nueva longitud del archivo subyacente, que no debe ser negativa. El resultado debe ser 0 en caso de éxito o un código errno (adecuado para su uso con Tcl_SetErrno) en caso de fallo.

Estos valores pueden recuperarse con Tcl_ChannelTruncateProc, que devuelve un puntero a la función.

TCL_BADCHANNELOPTION

Este procedimiento genera un mensaje de error de "opción inválida" en un intérprete (opcional). Es utilizado por los controladores de canal cuando se solicita una opción de configuración/obtención inválida. Su propósito es concatenar la lista genérica de opciones a las específicas y factorizar la cadena de mensaje de error de opciones genéricas.

Siempre devuelve TCL_ERROR

Se genera un mensaje de error en el valor de resultado de interp para indicar que se invocó un comando con una opción inválida. El mensaje tiene la forma

    opción inválida "blah": debería ser una de
    <...opciones genéricas...>+<...opciones específicas...>
así se obtiene, por ejemplo: 
    opción inválida "-blah": debería ser una de -blocking,
    -buffering, -buffersize, -eofchar, -translation,
    -peername, o -sockname
cuando se llama con optionList igual a “peername sockname”

“blah” es el argumento optionName y “<opciones específicas>” es una lista separada por espacios de palabras de opción específicas. La función se encarga de insertar signos menos antes de cada opción, comas después, y un “o” antes de la última opción.

OLD CHANNEL TYPES

La estructura original (8.3.1 y anteriores) Tcl_ChannelType contiene los siguientes campos:

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
} Tcl_ChannelType;

Todavía es posible crear canales con la estructura anterior. El código interno del canal determinará la versión. Es imperativo utilizar la nueva estructura Tcl_ChannelType si está creando un controlador de canal apilado, debido a problemas con la implementación anterior de canales apilados (en 8.2.0 a 8.3.1).

Antes de 8.4.0 (es decir, durante los últimos lanzamientos de 8.3 y la primera parte del ciclo de desarrollo de 8.4) la estructura Tcl_ChannelType contenía los siguientes campos:

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_ChannelTypeVersion version;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverFlushProc *flushProc;
    Tcl_DriverHandlerProc *handlerProc;
    Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

Cuando la estructura anterior se registra como un tipo de canal, el campo version siempre debe ser TCL_CHANNEL_VERSION_2.
