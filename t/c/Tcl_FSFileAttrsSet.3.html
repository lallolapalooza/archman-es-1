DESCRIPCIÓN

Existen varias razones para llamar a las funciones de la API Tcl_FS (por ejemplo, Tcl_FSAccess y Tcl_FSStat) en lugar de llamar directamente a funciones de nivel de sistema como access y stat. Primero, funcionarán multiplataforma, por lo que una extensión que las llame debería funcionar sin modificaciones tanto en Unix como en Windows. Segundo, la implementación de Windows de algunas de estas funciones corrige algunos errores en las llamadas de nivel de sistema. Tercero, estas llamadas de función se encargan de cualquier conversión de ruta de "Utf a nativo de plataforma" que pueda ser necesaria (y pueden almacenar en caché los resultados de dichas conversiones para una mayor eficiencia en llamadas posteriores). Cuarto, y quizás lo más importante, todas estas funciones son "conscientes del sistema de archivos virtual" (VFS, por sus siglas en inglés). Cualquier sistema de archivos virtual (VFS) que se haya registrado (a través de Tcl_FSRegister) puede redirigir el acceso a archivos a medios o métodos de acceso alternativos. Esto significa que todas estas funciones (y, por lo tanto, los comandos de Tcl correspondientes file, glob, pwd, cd, open, etc.) pueden operar sobre "archivos" que no son archivos nativos en el sistema de archivos nativo. Esto también significa que cualquier extensión de Tcl que acceda al sistema de archivos (FS, por sus siglas en inglés) a través de esta API es automáticamente "consciente del sistema de archivos virtual". Por supuesto, si una extensión accede al sistema de archivos nativo directamente (a través de API específicas de la plataforma, por ejemplo), Tcl no puede interceptar tales llamadas.

Si se han registrado VFS apropiados, los "archivos" pueden ser, por poner dos ejemplos, remotos (por ejemplo, situados en un servidor ftp remoto) o archivados (por ejemplo, dentro de un archivo .zip). Dichos sistemas de archivos registrados proporcionan una tabla de búsqueda de funciones para implementar toda o parte de la funcionalidad que se enumera aquí. Finalmente, las llamadas Tcl_FSStat y Tcl_FSLstat abstraen lo que es en realidad el búfer "struct stat", permitiendo que el mismo código se utilice tanto en sistemas con como sin soporte para archivos de más de 2 GB de tamaño.

La API Tcl_FS está "Tcl_Obj"-ificada y puede almacenar en caché representaciones internas y otras cadenas relacionadas con rutas (por ejemplo, el directorio de trabajo actual). Un efecto secundario de esto es que no se deben pasar valores con un contador de referencias de cero a ninguna de estas funciones. Si tales llamadas se manejaran, podrían resultar en fugas de memoria (en algunas circunstancias, el código del sistema de archivos puede desear retener una referencia al valor pasado, y por lo tanto no se debe asumir que después de que cualquiera de estas llamadas regrese, el valor todavía tiene un contador de referencias de cero; puede haber sido incrementado) o en una falla de segmentación directa (u otro error de acceso a la memoria) debido a que el valor se libera a mitad de la manipulación compleja de valores requerida para garantizar que la ruta sea completamente normalizada y absoluta para la determinación del sistema de archivos. La lección práctica que se debe aprender de esto es que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

es incorrecto y puede causar errores de memoria. El contador de referencias de path debe incrementarse antes de pasarlo, o decrementarlo después. Por esta razón, los valores con un contador de referencias de cero se consideran rutas de sistema de archivos no válidas y llamar a cualquier función de la API Tcl_FS con tal valor no tendrá ningún efecto.

FUNCIONES DE LA API FS

Tcl_FSCopyFile intenta copiar el archivo dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas se encuentran en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), se llama a la función "copiar archivo" de ese sistema de archivos (si no es NULL). De lo contrario, la función devuelve -1 y establece la variable global C errno al código de error POSIX "EXDEV" (que significa "enlace de dominio cruzado").

Tcl_FSCopyDirectory intenta copiar el directorio dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas se encuentran en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), se llama a la función "copiar archivo" de ese sistema de archivos (si no es NULL). De lo contrario, la función devuelve -1 y establece la variable global C errno al código de error POSIX "EXDEV" (que significa "enlace de dominio cruzado").

Tcl_FSCreateDirectory intenta crear el directorio dado por pathPtr llamando a la función "crear directorio" del sistema de archivos propietario.

Tcl_FSDeleteFile intenta eliminar el archivo dado por pathPtr llamando a la función "eliminar archivo" del sistema de archivos propietario.

Tcl_FSRemoveDirectory intenta eliminar el directorio dado por pathPtr llamando a la función "eliminar directorio" del sistema de archivos propietario.

Tcl_FSRenameFile intenta renombrar el archivo o directorio dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas se encuentran en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), se llama a la función "renombrar archivo" de ese sistema de archivos (si no es NULL). De lo contrario, la función devuelve -1 y establece la variable global C errno al código de error POSIX "EXDEV" (que significa "enlace de dominio cruzado").

Tcl_FSListVolumes llama a cada sistema de archivos que tiene una función "listar volúmenes" no NULL y les pide que devuelvan su lista de volúmenes raíz. Acumula los valores de retorno en una lista que se devuelve al llamador (con un contador de referencias de 0).

Tcl_FSEvalFileEx lee el archivo dado por pathPtr utilizando la codificación identificada por encodingName y evalúa su contenido como un script de Tcl. Devuelve la misma información que Tcl_EvalObjEx. Si encodingName es NULL, se utiliza la codificación del sistema para leer el contenido del archivo. Si el archivo no se pudo leer, se devuelve un error de Tcl para describir por qué no se pudo leer el archivo. El carácter de fin de archivo (eofchar) para archivos es "\x1A" (^Z) para todas las plataformas. Si necesita un "^Z" en el código para comparación de cadenas, puede usar "\x1A", que será sustituido de forma segura por el intérprete de Tcl en "^Z". Tcl_FSEvalFile es una versión más simple de Tcl_FSEvalFileEx que siempre utiliza la codificación del sistema al leer el archivo.

Tcl_FSLoadFile carga dinámicamente un archivo de código binario en memoria y devuelve las direcciones de dos procedimientos dentro de ese archivo, si están definidos. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr. Si ese sistema de archivos no implementa esta función (la mayoría de los sistemas de archivos virtuales no lo harán, debido a limitaciones del sistema operativo en la carga dinámica de código binario), Tcl intentará copiar el archivo a un directorio temporal y cargar ese archivo temporal. Tcl_FSUnloadFile revierte la operación, solicitando que la biblioteca indicada por loadHandle se elimine del proceso. Tenga en cuenta que, a diferencia del comando unload, esto no da a la biblioteca ninguna oportunidad de limpiar.

Ambas funciones anteriores devuelven un código de finalización de Tcl estándar. Si ocurre un error, se deja un mensaje de error en el resultado del interp.

El token proporcionado a través de la variable indicada por loadHandlePtr puede utilizarse con Tcl_FindSymbol.

Tcl_FSMatchInDirectory es utilizado por el código de globbing para buscar en un directorio todos los archivos que coincidan con un patrón dado. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el globbing. Los mensajes de error se colocan en interp (a menos que interp sea NULL, lo cual está permitido), pero los buenos resultados se colocan en resultPtr proporcionado.

Tenga en cuenta que el código glob implementa patrones recursivos internamente, por lo que esta función solo recibirá patrones simples, que se pueden hacer coincidir utilizando la lógica de string match. Para manejar la recursión, Tcl llamará a esta función con frecuencia solicitando solo directorios. Un caso especial de ser llamado con un patrón NULL indica que la ruta solo necesita ser verificada por el tipo correcto.

Tcl_FSLink reemplaza la versión de biblioteca de readlink y la extiende para admitir la creación de enlaces. Se llamará a la función apropiada para el sistema de archivos al que pertenece linkNamePtr.

Si toPtr es NULL, se realiza una acción de "leer enlace". El resultado es un Tcl_Obj que especifica el contenido del enlace simbólico dado por linkNamePtr, o NULL si el enlace no pudo ser leído. El resultado es propiedad del llamador, que debería llamar a Tcl_DecrRefCount cuando el resultado ya no sea necesario. Si toPtr no es NULL, Tcl debería crear un enlace de uno de los tipos pasados en el indicador linkAction. Este indicador es una combinación OR de TCL_CREATE_SYMBOLIC_LINK y TCL_CREATE_HARD_LINK. Donde exista una opción (es decir, se pasa más de un indicador), la convención de Tcl es preferir los enlaces simbólicos. Cuando se crea un enlace con éxito, el valor de retorno debe ser toPtr (que, por lo tanto, ya es propiedad del llamador). Si no tiene éxito, se devuelve NULL.

Tcl_FSLstat llena la estructura Tcl_StatBuf statPtr con información sobre el archivo especificado. No necesita ningún derecho de acceso al archivo para obtener esta información, pero necesita derechos de búsqueda en todos los directorios nombrados en la ruta que conduce al archivo. La estructura Tcl_StatBuf incluye información sobre el dispositivo, inodo (siempre 0 en Windows), modo de privilegios, nlink (siempre 1 en Windows), id de usuario (siempre 0 en Windows), id de grupo (siempre 0 en Windows), rdev (igual que el dispositivo en Windows), tamaño, última ac

tiempo de acceso, tiempo de última modificación y tiempo de último cambio de metadatos. Consulte la PORTABLE STAT RESULT API para obtener una descripción de cómo escribir código portable para asignar y acceder a la estructura Tcl_StatBuf.

Si path existe, Tcl_FSLstat devuelve 0 y la estructura stat se rellena con datos. De lo contrario, se devuelve -1 y no se proporciona información de stat.

Tcl_FSUtime reemplaza la versión de la biblioteca de utime.

Esto devuelve 0 en caso de éxito y -1 en caso de error (según la documentación de utime). Si tiene éxito, la función actualizará los valores de "atime" y "mtime" del archivo proporcionado.

Tcl_FSFileAttrsGet implementa el acceso de lectura para el subcomando file attributes que se puede enganchar. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

Si el resultado es TCL_OK, entonces se colocó un valor en objPtrRef, que solo será válido temporalmente (a menos que se llame a Tcl_IncrRefCount).

Tcl_FSFileAttrsSet implementa el acceso de escritura para el subcomando file attributes que se puede enganchar. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

Tcl_FSFileAttrStrings implementa parte del subcomando file attributes que se puede enganchar. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

El procedimiento llamado puede devolver una matriz de cadenas o puede devolver NULL y colocar una lista de Tcl en objPtrRef. Tcl tomará esa lista y primero incrementará su recuento de referencias antes de usarla. Al finalizar ese uso, Tcl disminuirá su recuento de referencias. Por lo tanto, si Tcl debe desechar la lista cuando termine, debe tener un recuento de referencias de cero, y si la lista no debe desecharse, el sistema de archivos debe asegurarse de mantener un recuento de referencias del valor.

Tcl_FSAccess comprueba si al proceso se le permitiría leer, escribir o probar la existencia del archivo (u otro objeto del sistema de archivos) cuyo nombre es pathname. Si pathname es un enlace simbólico en Unix, se prueban los permisos del archivo al que se refiere este enlace simbólico.

En caso de éxito (se conceden todos los permisos solicitados), se devuelve cero. En caso de error (al menos un bit en el modo solicitado deniega un permiso, o se produce algún otro error), se devuelve -1.

Tcl_FSStat rellena la estructura Tcl_StatBuf statPtr con información sobre el archivo especificado. No necesita ningún derecho de acceso al archivo para obtener esta información, pero necesita derechos de búsqueda a todos los directorios mencionados en la ruta que conduce al archivo. La estructura Tcl_StatBuf incluye información sobre el dispositivo, el inodo (siempre 0 en Windows), el modo de privilegio, nlink (siempre 1 en Windows), el id de usuario (siempre 0 en Windows), el id de grupo (siempre 0 en Windows), rdev (igual que el dispositivo en Windows), el tamaño, el tiempo de último acceso, el tiempo de última modificación y el tiempo de último cambio de metadatos. Consulte la PORTABLE STAT RESULT API para obtener una descripción de cómo escribir código portable para asignar y acceder a la estructura Tcl_StatBuf.

Si path existe, Tcl_FSStat devuelve 0 y la estructura stat se rellena con datos. De lo contrario, se devuelve -1 y no se proporciona información de stat.

Tcl_FSOpenFileChannel abre un archivo especificado por pathPtr y devuelve un manejador de canal que se puede utilizar para realizar operaciones de entrada y salida en el archivo. Esta API se basa en el procedimiento fopen de la biblioteca estándar de E/S de Unix. La sintaxis y el significado de todos los argumentos son similares a los dados en el comando open de Tcl al abrir un archivo. Si se produce un error al abrir el canal, Tcl_FSOpenFileChannel devuelve NULL y registra un código de error POSIX que se puede recuperar con Tcl_GetErrno. Además, si interp no es NULL, Tcl_FSOpenFileChannel deja un mensaje de error en el resultado de interp después de cualquier error.

El canal recién creado no está registrado en el intérprete proporcionado; para registrarlo, utilice Tcl_RegisterChannel. Si uno de los canales estándar, stdin, stdout o stderr se cerró previamente, el acto de crear el nuevo canal también lo asigna como reemplazo del canal estándar.

Tcl_FSGetCwd reemplaza la versión de la biblioteca de getcwd.

Devuelve el directorio de trabajo actual de la biblioteca Tcl. Este puede ser diferente al directorio de trabajo de la plataforma nativa, lo que sucede cuando el directorio de trabajo actual no está en el sistema de archivos nativo.

El resultado es un puntero a un Tcl_Obj que especifica el directorio actual, o NULL si no se pudo determinar el directorio actual. Si se devuelve NULL, se deja un mensaje de error en el resultado de interp.

El resultado ya tiene su recuento de referencias incrementado para el llamador. Cuando ya no sea necesario, se debe disminuir ese recuento de referencias. MATCHINDIRECTORYPROC

Función para procesar una llamada a Tcl_FSMatchInDirectory. Si no se implementa, la funcionalidad de glob y copia recursiva faltará en el sistema de archivos (y esto puede afectar a comandos como encoding names que utilizan funcionalidad de glob internamente).

        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La función debe devolver todos los archivos o directorios (u otros objetos del sistema de archivos) que coincidan con el patrón dado y cumplan con la especificación de types proporcionada. Hay dos formas en que esta función puede ser llamada. Si pattern es NULL, entonces pathPtr es una especificación de ruta completa de un único archivo o directorio que debe ser verificado por existencia y tipo correcto. De lo contrario, pathPtr es un directorio, cuyo contenido la función debe buscar para archivos o directorios que tengan el tipo correcto. En cualquier caso, se puede asumir que pathPtr no es NULL ni está vacío. Actualmente no está documentado si pathPtr tendrá un separador de archivo al final o no, por lo que el código debe ser flexible a ambas posibilidades.

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso de coincidencia. Los mensajes de error se colocan en interp, a menos que interp sea NULL, en cuyo caso no es necesario generar ningún mensaje de error; en un resultado TCL_OK, los resultados deben agregarse al valor de resultPtr proporcionado (que se puede asumir que es una lista válida y no compartida de Tcl). Las coincidencias agregadas a resultPtr deben incluir cualquier prefijo de ruta dado en pathPtr (esto generalmente significa que serán especificaciones de ruta absolutas). Tenga en cuenta que si no se encuentran coincidencias, eso simplemente conduce a un resultado vacío; los errores solo se señalan para problemas reales de archivos o del sistema de archivos que puedan ocurrir durante el proceso de coincidencia.

La estructura Tcl_GlobTypeData pasada en el parámetro types contiene los siguientes campos:

En el primero de estos casos, la función debe listar los directorios contenidos. Tcl utiliza esto para implementar el globbing recursivo, por lo que es fundamental que los sistemas de archivos implementen la coincidencia de directorios correctamente. En el segundo de estos casos, con TCL_GLOB_TYPE_MOUNT, el sistema de archivos debe listar los puntos de montaje que se encuentran dentro del pathPtr dado (y en este caso, pathPtr no necesita estar dentro del mismo sistema de archivos, a diferencia de todos los demás casos en los que se llama a esta función). El soporte para esto es fundamental si Tcl quiere tener transiciones fluidas entre un sistema de archivos y otro.
