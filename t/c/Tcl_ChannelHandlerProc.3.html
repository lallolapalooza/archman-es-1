DESCRIPCIÓN

Tcl utiliza una arquitectura de canales de dos capas. Proporciona una capa superior genérica para permitir que los programas C y Tcl realicen entrada y salida utilizando las mismas API para una variedad de archivos, dispositivos, sockets, etc. Las API C genéricas se describen en la entrada del manual de Tcl_OpenFileChannel.

La capa inferior proporciona controladores de canales específicos del tipo para cada tipo de dispositivo compatible en cada plataforma. Esta entrada del manual describe las API C utilizadas para comunicarse entre la capa genérica y los controladores de canales específicos del tipo. También explica cómo se pueden agregar nuevos tipos de canales proporcionando nuevos controladores de canales.

Los controladores de canales constan de varios componentes: Primero, cada controlador de canales proporciona una estructura Tcl_ChannelType que contiene punteros a las funciones que implementan las diversas operaciones utilizadas por la capa genérica para comunicarse con el controlador de canales. La estructura Tcl_ChannelType y las funciones a las que hace referencia se describen en la sección TCL_CHANNELTYPE, a continuación.

Segundo, los controladores de canales suelen proporcionar un comando Tcl para crear instancias de ese tipo de canal. Por ejemplo, el comando Tcl open crea canales que utilizan los controladores de canales de archivo y de comando, y el comando Tcl socket crea canales que utilizan sockets TCP para la comunicación de red.

Tercero, un controlador de canales opcionalmente proporciona una función C para abrir instancias de canal de ese tipo. Por ejemplo, Tcl_OpenFileChannel abre un canal que utiliza el controlador de canales de archivo, y Tcl_OpenTcpClient abre un canal que utiliza el protocolo de red TCP. Estas funciones de creación suelen utilizar internamente Tcl_CreateChannel para abrir el canal.

Para agregar un nuevo tipo de canal, debe implementar una API C o un comando Tcl que abra un canal invocando Tcl_CreateChannel. Cuando su controlador llama a Tcl_CreateChannel, le pasa una estructura Tcl_ChannelType que describe los procedimientos de E/S del controlador. La capa genérica invocará entonces las funciones a las que se hace referencia en esa estructura para realizar operaciones en el canal.

Tcl_CreateChannel abre un nuevo canal y asocia los typePtr y instanceData proporcionados con él. El canal se abre en el modo indicado por mask. Para una discusión sobre los controladores de canales, sus operaciones y la estructura Tcl_ChannelType, consulte la sección TCL_CHANNELTYPE, a continuación.

Tcl_CreateChannel interactúa con el código que administra los canales estándar. Una vez que un canal estándar se inicializó a través de una llamada a Tcl_GetStdChannel o una llamada a Tcl_SetStdChannel, cerrar este canal estándar provocará que la próxima llamada a Tcl_CreateChannel también convierta el nuevo canal en el nuevo canal estándar. Consulte Tcl_StandardChannels para un tratado general sobre los canales estándar y el comportamiento de la biblioteca Tcl con respecto a ellos.

Tcl_GetChannelInstanceData devuelve los datos de instancia asociados con el canal en channel. Esto es lo mismo que el argumento instanceData en la llamada a Tcl_CreateChannel que creó este canal.

Tcl_GetChannelType devuelve un puntero a la estructura Tcl_ChannelType utilizada por el canal en el argumento channel. Esto es lo mismo que el argumento typePtr en la llamada a Tcl_CreateChannel que creó este canal.

Tcl_GetChannelName devuelve una cadena que contiene el nombre asociado con el canal, o NULL si el argumento channelName a Tcl_CreateChannel era NULL.

Tcl_GetChannelHandle coloca el manejador de dispositivo específico del sistema operativo asociado con channel para la direction dada en el

specified by handlePtr and returns TCL_OK. If the channel does not have a device handle for the specified direction, then TCL_ERROR is returned instead. Different channel drivers will return different types of handle. Refer to the manual entries for each driver to determine what type of handle is returned.

Tcl_GetChannelThread returns the id of the thread currently managing the specified channel. This allows channel drivers to send their file events to the correct event queue even for a multi-threaded core.

Tcl_GetChannelMode returns an OR-ed combination of TCL_READABLE and TCL_WRITABLE, indicating whether the channel is open for input and output.

Tcl_GetChannelBufferSize returns the size, in bytes, of buffers allocated to store input or output in channel. If the value was not set by a previous call to Tcl_SetChannelBufferSize, described below, then the default value of 4096 is returned.

Tcl_SetChannelBufferSize sets the size, in bytes, of buffers that will be allocated in subsequent operations on the channel to store input or output. The size argument should be between one and one million, allowing buffers of one byte to one million bytes. If size is outside this range, Tcl_SetChannelBufferSize sets the buffer size to 4096.

Tcl_NotifyChannel is called by a channel driver to indicate to the generic layer that the events specified by mask have occurred on the channel. Channel drivers are responsible for invoking this function whenever the channel handlers need to be called for the channel (or other pending tasks like a write flush should be performed). See WATCHPROC below for more details.

Tcl_BadChannelOption is called from driver specific setOptionProc or getOptionProc to generate a complete error message.

Tcl_ChannelBuffered returns the number of bytes of input currently buffered in the internal buffer (push back area) of the channel itself. It does not report about the data in the overall buffers for the stack of channels the supplied channel is part of.

Tcl_IsChannelShared checks the refcount of the specified channel and returns whether the channel was shared among multiple interpreters (result == 1) or not (result == 0).

Tcl_IsChannelRegistered checks whether the specified channel is registered in the given interpreter (result == 1) or not (result == 0).

Tcl_IsChannelExisting checks whether a channel with the specified name is registered in the (thread)-global list of all channels (result == 1) or not (result == 0).

Tcl_CutChannel removes the specified channel from the (thread)global list of all channels (of the current thread). Application to a channel still registered in some interpreter is not allowed. Also notifies the driver if the Tcl_ChannelType version is TCL_CHANNEL_VERSION_4 (or higher), and Tcl_DriverThreadActionProc is defined for it.

Tcl_SpliceChannel adds the specified channel to the (thread)global list of all channels (of the current thread). Application to a channel registered in some interpreter is not allowed. Also notifies the driver if the Tcl_ChannelType version is TCL_CHANNEL_VERSION_4 (or higher), and Tcl_DriverThreadActionProc is defined for it.

Tcl_ClearChannelHandlers removes all channel handlers and event scripts associated with the specified channel, thus shutting down all event processing for this channel.

TCL_CHANNELTYPE

Un controlador de canal proporciona una estructura Tcl_ChannelType que contiene punteros a funciones que implementan las diversas operaciones en un canal; estas operaciones se invocan según sea necesario por la capa genérica. La estructura fue versionada a partir de Tcl 8.3.2/8.4 para corregir un problema con los controladores de canales apilados. Consulte la sección OLD CHANNEL TYPES a continuación para obtener detalles sobre la estructura antigua.

La estructura Tcl_ChannelType contiene los siguientes campos:

typedef struct Tcl_ChannelType {
        const char *typeName;
        Tcl_ChannelTypeVersion version;
        Tcl_DriverCloseProc *closeProc;
        Tcl_DriverInputProc *inputProc;
        Tcl_DriverOutputProc *outputProc;
        Tcl_DriverSeekProc *seekProc;
        Tcl_DriverSetOptionProc *setOptionProc;
        Tcl_DriverGetOptionProc *getOptionProc;
        Tcl_DriverWatchProc *watchProc;
        Tcl_DriverGetHandleProc *getHandleProc;
        Tcl_DriverClose2Proc *close2Proc;
        Tcl_DriverBlockModeProc *blockModeProc;
        Tcl_DriverFlushProc *flushProc;
        Tcl_DriverHandlerProc *handlerProc;
        Tcl_DriverWideSeekProc *wideSeekProc;
        Tcl_DriverThreadActionProc *threadActionProc;
        Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

No es necesario proporcionar implementaciones para todas las operaciones del canal. Aquellas que no sean necesarias se pueden establecer en NULL en la estructura: blockModeProc, seekProc, setOptionProc, getOptionProc, getHandleProc y close2Proc, además de flushProc, handlerProc, threadActionProc y truncateProc. Otras funciones que no se pueden implementar de manera significativa deben devolver EINVAL cuando se llaman, para indicar que las operaciones que representan no están disponibles. Tenga en cuenta también que wideSeekProc puede ser NULL si seekProc lo es.

El usuario solo debe usar la estructura anterior para la instanciación de Tcl_ChannelType. Al hacer referencia a los campos en una estructura Tcl_ChannelType, se deben usar las siguientes funciones para obtener los valores: Tcl_ChannelName, Tcl_ChannelVersion, Tcl_ChannelBlockModeProc, Tcl_ChannelCloseProc, Tcl_ChannelClose2Proc, Tcl_ChannelInputProc, Tcl_ChannelOutputProc, Tcl_ChannelSeekProc, Tcl_ChannelWideSeekProc, Tcl_ChannelThreadActionProc, Tcl_ChannelTruncateProc, Tcl_ChannelSetOptionProc, Tcl_ChannelGetOptionProc, Tcl_ChannelWatchProc, Tcl_ChannelGetHandleProc, Tcl_ChannelFlushProc o Tcl_ChannelHandlerProc.

El cambio en las estructuras se realizó de tal manera que los tipos de canal estándar son binariamente compatibles. Sin embargo, los tipos de canal que utilizan canales apilados (es decir, TLS, Trf) tienen nuevas versiones para corresponder al cambio anterior, ya que el código anterior para canales apilados tenía problemas.

TYPENAME

El campo typeName contiene una cadena terminada en nulo que identifica el tipo de dispositivo implementado por este controlador, por ejemplo, file o socket.

Este valor se puede recuperar con Tcl_ChannelName, que devuelve un puntero a la cadena.

VERSION

El campo version debe establecerse en la versión de la estructura que necesita. TCL_CHANNEL_VERSION_2 es el mínimo recomendado. Se debe establecer TCL_CHANNEL_VERSION_3 para especificar el miembro wideSeekProc. Se debe establecer TCL_CHANNEL_VERSION_4 para especificar el miembro threadActionProc (incluye wideSeekProc). Se debe establecer TCL_CHANNEL_VERSION_5 para especificar los miembros truncateProc (incluye wideSeekProc y threadActionProc). Si no se establece en ninguna de estas, se asume que esta Tcl_ChannelType tiene la estructura original. Consulte OLD CHANNEL TYPES para obtener más detalles. Si bien Tcl reconocerá y funcionará con ambas estructuras, los canales apilados deben ser al menos de TCL_CHANNEL_VERSION_2 para funcionar correctamente.

Este valor se puede recuperar con Tcl_ChannelVersion, que devuelve una de las siguientes opciones: TCL_CHANNEL_VERSION_5, TCL_CHANNEL_VERSION_4, TCL_CHANNEL_VERSION_3, TCL_CHANNEL_VERSION_2 o TCL_CHANNEL_VERSION_1.

BLOCKMODEPROC

El campo blockModeProc contiene la dirección de una función llamada por la capa genérica para establecer el modo de bloqueo y no bloqueo en el dispositivo. BlockModeProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverBlockModeProc(
        ClientData instanceData,
        int mode);

El instanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando se creó este canal. El argumento mode es TCL_MODE_BLOCKING o TCL_MODE_NONBLOCKING para establecer el dispositivo en modo de bloqueo o no bloqueo. La función debe devolver cero si la operación fue exitosa, o un código de error POSIX distinto de cero si la operación falló.

Si la operación es exitosa, la función puede modificar el instanceData proporcionado para registrar que el canal entró en modo de bloqueo o no bloqueo y para implementar el comportamiento de bloqueo o no bloqueo. Para algunos tipos de dispositivos, el comportamiento de bloqueo y no bloqueo puede ser implementado por el sistema operativo subyacente; para otros tipos de dispositivos, el comportamiento debe ser emulado en el controlador del canal.

Este valor se puede recuperar con Tcl_ChannelBlockModeProc, que devuelve un puntero a la función.

Un controlador de canal que **no** proporciona un blockModeProc debe tener mucho, mucho cuidado. Debe informar a la capa genérica exactamente qué modo de bloqueo es aceptable para él, y esto también debe documentarse para el usuario, de modo que el modo de bloqueo del canal no se cambie a un valor inaceptable. Cualquier confusión aquí puede llevar al intérprete a un punto muerto (falso y difícil de encontrar).

WATCHPROC

El campo watchProc contiene la dirección de una función llamada por la capa genérica para inicializar el mecanismo de notificación de eventos para detectar eventos de interés en este canal. WatchProc debe coincidir con el siguiente prototipo:

typedef void Tcl_DriverWatchProc(
        ClientData instanceData,
        int mask);

InstanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó este canal. El argumento mask es una combinación OR de TCL_READABLE, TCL_WRITABLE y TCL_EXCEPTION; indica los eventos sobre los que el llamador está interesado en ser notificado en este canal.

La función debe inicializar mecanismos específicos del tipo de dispositivo para detectar cuándo ocurre un evento de interés en el canal. Cuando ocurre uno o más de los eventos designados en el canal, el controlador del canal es responsable de llamar a Tcl_NotifyChannel para informar al módulo genérico de canales. El controlador debe tener cuidado de no desatender a otros controladores de canales o fuentes de callbacks invocando Tcl_NotifyChannel con demasiada frecuencia. La equidad puede asegurarse utilizando la cola de eventos de Tcl para permitir que el evento del canal se agende en secuencia con otros eventos. Consulte la descripción de Tcl_QueueEvent para obtener detalles sobre cómo encolar un evento.

Este valor puede ser recuperado con Tcl_ChannelWatchProc, que devuelve un puntero a la función.

GETHANDLEPROC

El campo getHandleProc contiene la dirección de una función llamada por la capa genérica para recuperar un manejador específico del dispositivo del canal. GetHandleProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverGetHandleProc(
        ClientData instanceData,
        int direction,
        ClientData *handlePtr);

InstanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó este canal. El argumento direction es TCL_READABLE para recuperar el manejador utilizado para la entrada, o TCL_WRITABLE para recuperar el manejador utilizado para la salida.

Si la implementación del canal tiene manejadores específicos del dispositivo, la función debe recuperar el manejador apropiado asociado con el canal, según el argumento direction. El manejador debe almacenarse en la ubicación a la que apunta handlePtr, y se debe devolver TCL_OK. Si el canal no está abierto para la dirección especificada, o si la implementación del canal no utiliza manejadores de dispositivos, la función debe devolver TCL_ERROR.

Este valor puede ser recuperado con Tcl_ChannelGetHandleProc, que devuelve un puntero a la función.

FLUSHPROC

El campo flushProc está actualmente reservado para uso futuro. Debe establecerse en NULL. FlushProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverFlushProc(
        ClientData instanceData);

Este valor puede ser recuperado con Tcl_ChannelFlushProc, que devuelve un puntero a la función.

HANDLERPROC

El campo handlerProc contiene la dirección de la función llamada por la capa genérica para notificar al canal que ocurrió un evento. Debe definirse para controladores de canales apilados que deseen ser notificados de eventos que ocurren en el canal subyacente (apilado). HandlerProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverHandlerProc(
        ClientData instanceData,
        int interestMask);

InstanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó este canal. interestMask es una combinación OR de TCL_READABLE o TCL_WRITABLE; indica qué tipo de evento ocurrió en este canal.

Este valor puede ser recuperado con Tcl_ChannelHandlerProc, que devuelve un puntero a la función.

THREADACTIONPROC

El campo threadActionProc contiene la dirección de la función llamada por la capa genérica cuando se crea, cierra o va a mover un canal a otro hilo, es decir, siempre que el estado del controlador específico del hilo pueda tener que ser inicializado o actualizado. Puede ser NULL. La acción TCL_CHANNEL_THREAD_REMOVE se utiliza para notificar al controlador que debe actualizar o eliminar cualquier dato específico del hilo que pueda estar manteniendo para el canal.

La acción TCL_CHANNEL_THREAD_INSERT se utiliza para notificar al controlador que debe actualizar o inicializar cualquier dato específico del hilo que pueda estar manteniendo utilizando el hilo que llama como asociado. Consulte Tcl_CutChannel y Tcl_SpliceChannel para obtener más detalles.

typedef void Tcl_DriverThreadActionProc(
        ClientData instanceData,
        int action);

InstanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó este canal.

Estos valores pueden ser recuperados con Tcl_ChannelThreadActionProc, que devuelve un puntero a la función.

TRUNCATEPROC

El campo truncateProc contiene la dirección de la función llamada por la capa genérica cuando un canal se trunca a una cierta longitud. Puede ser NULL.

typedef int Tcl_DriverTruncateProc(
        ClientData instanceData,
        Tcl_WideInt length);

InstanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó este canal, y length es la nueva longitud del archivo subyacente, que no debe ser negativa. El resultado debe ser 0 en caso de éxito o un código errno (adecuado para usar con Tcl_SetErrno) en caso de fallo.

Estos valores pueden ser recuperados con Tcl_ChannelTruncateProc, que devuelve un puntero a la función.

TCL_BADCHANNELOPTION

Este procedimiento genera un mensaje de error de "opción no válida" en un intérprete (opcional). Lo utilizan los controladores de canales cuando se solicita una opción de Establecer/Obtener no válida. Su propósito es concatenar la lista de opciones genéricas con las específicas y factorizar el mensaje de error de las opciones genéricas.

Siempre devuelve TCL_ERROR

Se genera un mensaje de error en el resultado del interp para indicar que se invocó un comando con una opción no válida. El mensaje tiene el formato

    opción no válida "blah": debería ser una de
    <...opciones genéricas...>+<...opciones específicas...>
por lo que se obtiene, por ejemplo: 
    opción no válida "-blah": debería ser una de -blocking,
    -buffering, -buffersize, -eofchar, -translation,
    -peername, o -sockname
cuando se llama con optionList igual a “peername sockname”

“blah” es el argumento optionName y “<opciones específicas>” es una lista separada por espacios de palabras de opciones específicas. La función se encarga de insertar signos menos antes de cada opción, comas después y un “o” antes de la última opción.

TIPOS DE CANAL ANTIGUOS

La estructura original (8.3.1 y anteriores) Tcl_ChannelType contiene los siguientes campos:

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
} Tcl_ChannelType;

Todavía es posible crear canales con la estructura anterior. El código interno de canales determinará la versión. Es imperativo utilizar la nueva estructura Tcl_ChannelType si está creando un controlador de canal apilado, debido a problemas con la implementación anterior de canales apilados (en 8.2.0 a 8.3.1).

Antes de la versión 8.4.0 (es decir, durante los últimos lanzamientos de 8.3 y la primera parte del ciclo de desarrollo de 8.4), la estructura Tcl_ChannelType contenía los siguientes campos:

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_ChannelTypeVersion version;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverFlushProc *flushProc;
    Tcl_DriverHandlerProc *handlerProc;
    Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

Cuando la estructura anterior se registra como un tipo de canal, el campo version siempre debe ser TCL_CHANNEL_VERSION_2.
