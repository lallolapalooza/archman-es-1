DESCRIPCIÓN

Hay varias razones para llamar a las funciones de la API Tcl_FS (por ejemplo, Tcl_FSAccess y Tcl_FSStat) en lugar de llamar directamente a funciones de nivel de sistema como access y stat. Primero, funcionarán multiplataforma, por lo que una extensión que las llame debería funcionar sin modificaciones tanto en Unix como en Windows. Segundo, la implementación de Windows de algunas de estas funciones corrige algunos errores en las llamadas de nivel de sistema. Tercero, estas llamadas a funciones manejan cualquier conversión de ruta "Utf a nativa de plataforma" que pueda ser necesaria (y pueden almacenar en caché los resultados de dichas conversiones para una mayor eficiencia en llamadas posteriores). Cuarto, y quizás lo más importante, todas estas funciones "entienden el sistema de archivos virtual" (VFS por sus siglas en inglés). Cualquier sistema de archivos virtual (VFS) que se haya registrado (a través de Tcl_FSRegister) puede redirigir el acceso a archivos a medios o métodos de acceso alternativos. Esto significa que todas estas funciones (y, por lo tanto, los comandos Tcl correspondientes de file, glob, pwd, cd, open, etc.) pueden operar sobre "archivos" que no son archivos nativos en el sistema de archivos nativo. Esto también significa que cualquier extensión de Tcl que acceda al sistema de archivos (FS por sus siglas en inglés) a través de esta API "entiende el sistema de archivos virtual" automáticamente. Por supuesto, si una extensión accede al sistema de archivos nativo directamente (a través de APIs específicas de la plataforma, por ejemplo), Tcl no puede interceptar dichas llamadas.

Si se han registrado VFS apropiados, los "archivos" pueden ser, por dar dos ejemplos, remotos (por ejemplo, situados en un servidor ftp remoto) o archivados (por ejemplo, dentro de un archivo .zip). Dichos sistemas de archivos registrados proporcionan una tabla de búsqueda de funciones para implementar toda o parte de la funcionalidad que se enumera aquí. Finalmente, las llamadas Tcl_FSStat y Tcl_FSLstat abstraen el búfer "struct stat", permitiendo que el mismo código se utilice tanto en sistemas con como sin soporte para archivos mayores de 2 GB.

La API Tcl_FS utiliza Tcl_Obj y puede almacenar en caché representaciones internas y otras cadenas relacionadas con rutas (por ejemplo, el directorio de trabajo actual). Un efecto secundario de esto es que no se deben pasar valores con un recuento de referencias de cero a ninguna de estas funciones. Si se manejaran tales llamadas, podrían resultar en fugas de memoria (en algunas circunstancias, el código del sistema de archivos puede desear retener una referencia al valor pasado, por lo que no se debe asumir que después de que alguna de estas llamadas regrese, el valor todavía tiene un recuento de referencias de cero; puede haber sido incrementado) o en una segmentación directa (u otro error de acceso a memoria) debido a que el valor se libera a mitad de la manipulación compleja de valores necesaria para garantizar que la ruta se normalice completamente y sea absoluta para la determinación del sistema de archivos. La lección práctica que se debe aprender de esto es que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

es incorrecto y puede causar errores de memoria. El recuento de referencias de path debe incrementarse antes de pasarlo, o decrementarse después. Por esta razón, los valores con un recuento de referencias de cero se consideran rutas de sistema de archivos no válidas y llamar a cualquier función de la API Tcl_FS con un valor de este tipo no tendrá ningún efecto.

FUNCIONES API FS

Tcl_FSCopyFile intenta copiar el archivo dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas se encuentran en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), se llama a la función "copiar archivo" de ese sistema de archivos (si no es NULL). De lo contrario, la función devuelve -1 y establece la variable global C errno al código de error POSIX "EXDEV" (que significa "enlace entre dominios").

Tcl_FSCopyDirectory intenta copiar el directorio dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas se encuentran en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), se llama a la función "copiar archivo" de ese sistema de archivos (si no es NULL). De lo contrario, la función devuelve -1 y establece la variable global C errno al código de error POSIX "EXDEV" (que significa "enlace entre dominios").

Tcl_FSCreateDirectory intenta crear el directorio dado por pathPtr llamando a la función "crear directorio" del sistema de archivos propietario.

Tcl_FSDeleteFile intenta eliminar el archivo dado por pathPtr llamando a la función "eliminar archivo" del sistema de archivos propietario.

Tcl_FSRemoveDirectory intenta eliminar el directorio dado por pathPtr llamando a la función "eliminar directorio" del sistema de archivos propietario.

Tcl_FSRenameFile intenta renombrar el archivo o directorio dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas se encuentran en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), se llama a la función "renombrar archivo" de ese sistema de archivos (si no es NULL). De lo contrario, la función devuelve -1 y establece la variable global C errno al código de error POSIX "EXDEV" (que significa "enlace entre dominios").

Tcl_FSListVolumes llama a cada sistema de archivos que tiene una función "listar volúmenes" no NULL y les pide que devuelvan su lista de volúmenes raíz. Acumula los valores de retorno en una lista que se devuelve al llamador (con un recuento de referencias de 0).

Tcl_FSEvalFileEx lee el archivo dado por pathPtr utilizando la codificación identificada por encodingName y evalúa su contenido como un script de Tcl. Devuelve la misma información que Tcl_EvalObjEx. Si encodingName es NULL, se utiliza la codificación del sistema para leer el contenido del archivo. Si el archivo no se pudo leer, se devuelve un error de Tcl para describir por qué no se pudo leer. El carácter de fin de archivo (eofchar) para los archivos es "\x1A" (^Z) para todas las plataformas. Si necesita un "^Z" en código para comparación de cadenas, puede usar "\x1A", que será sustituido de forma segura por el intérprete de Tcl por "^Z". Tcl_FSEvalFile es una versión más simple de Tcl_FSEvalFileEx que siempre utiliza la codificación del sistema al leer el archivo.

Tcl_FSLoadFile carga dinámicamente un archivo de código binario en memoria y devuelve las direcciones de dos procedimientos dentro de ese archivo, si están definidos. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr. Si ese sistema de archivos no implementa esta función (la mayoría de los sistemas de archivos virtuales no lo harán, debido a limitaciones del sistema operativo en la carga dinámica de código binario), Tcl intentará copiar el archivo a un directorio temporal y cargar ese archivo temporal. Tcl_FSUnloadFile revierte la operación, solicitando que se elimine la biblioteca indicada por loadHandle del proceso. Tenga en cuenta que, a diferencia del comando unload, esto no da a la biblioteca ninguna oportunidad de limpiar.

Ambas funciones anteriores devuelven un código de finalización estándar de Tcl. Si ocurre un error, se deja un mensaje de error en el resultado del interp.

El token proporcionado a través de la variable indicada por loadHandlePtr puede usarse con Tcl_FindSymbol.

Tcl_FSMatchInDirectory es utilizado por el código de globbing para buscar en un directorio todos los archivos que coinciden con un patrón dado. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

El valor de retorno es un resultado estándar de Tcl que indica si se produjo un error en el globbing. Los mensajes de error se colocan en interp (a menos que interp sea NULL, lo cual está permitido), pero los resultados buenos se colocan en resultPtr proporcionado.

Tenga en cuenta que el código glob implementa patrones recursivos internamente, por lo que esta función solo recibirá patrones simples, que se pueden hacer coincidir utilizando la lógica de string match. Para manejar la recursión, Tcl llamará a esta función con frecuencia pidiendo solo que se devuelvan directorios. Un caso especial de ser llamado con un patrón NULL indica que la ruta solo necesita ser verificada por el tipo correcto.

Tcl_FSLink reemplaza la versión de biblioteca de readlink y la amplía para admitir la creación de enlaces. Se llamará a la función apropiada para el sistema de archivos al que pertenece linkNamePtr.

Si toPtr es NULL, se realiza una acción de "leer enlace". El resultado es un Tcl_Obj que especifica el contenido del enlace simbólico dado por linkNamePtr, o NULL si el enlace no se pudo leer. El resultado es propiedad del llamador, que debería llamar a Tcl_DecrRefCount cuando el resultado ya no sea necesario. Si toPtr no es NULL, Tcl debería crear un enlace de uno de los tipos pasados en el indicador linkAction. Este indicador es una combinación OR de TCL_CREATE_SYMBOLIC_LINK y TCL_CREATE_HARD_LINK. Cuando existe una elección (es decir, se pasa más de un indicador), la convención de Tcl es preferir los enlaces simbólicos. Cuando se crea un enlace con éxito, el valor de retorno debería ser toPtr (que, por lo tanto, ya es propiedad del llamador). Si no tiene éxito, se devuelve NULL.

Tcl_FSLstat rellena la estructura Tcl_StatBuf statPtr con información sobre el archivo especificado. No necesita ningún derecho de acceso al archivo para obtener esta información, pero necesita derechos de búsqueda a todos los directorios nombrados en la ruta que lleva al archivo. La estructura Tcl_StatBuf incluye información sobre el dispositivo, inodo (siempre 0 en Windows), modo de privilegios, nlink (siempre 1 en Windows), id de usuario (siempre 0 en Windows), id de grupo (siempre 0 en Windows), rdev (igual que el dispositivo en Windows), tamaño, último acceso

tiempo, hora de última modificación y hora de último cambio de metadatos. Consulte la **API de resultados de stat portátiles** para obtener una descripción de cómo escribir código portátil para asignar y acceder a la estructura Tcl_StatBuf.

Si path existe, Tcl_FSLstat devuelve 0 y la estructura stat se rellena con datos. De lo contrario, se devuelve -1 y no se proporciona información de stat.

Tcl_FSUtime reemplaza la versión de biblioteca de utime.

Esto devuelve 0 en caso de éxito y -1 en caso de error (según la documentación de utime). Si tiene éxito, la función actualizará los valores de "atime" y "mtime" del archivo proporcionado.

Tcl_FSFileAttrsGet implementa el acceso de lectura para el subcomando file attributes que se puede enganchar. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

Si el resultado es TCL_OK, entonces se colocó un valor en objPtrRef, que solo será válido temporalmente (a menos que se llame a Tcl_IncrRefCount).

Tcl_FSFileAttrsSet implementa el acceso de escritura para el subcomando file attributes que se puede enganchar. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

Tcl_FSFileAttrStrings implementa parte del subcomando file attributes que se puede enganchar. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

El procedimiento llamado puede devolver una matriz de cadenas o puede devolver NULL y colocar una lista de Tcl en objPtrRef. Tcl tomará esa lista y primero incrementará su recuento de referencias antes de usarla. Al finalizar ese uso, Tcl disminuirá su recuento de referencias. Por lo tanto, si Tcl debe desechar la lista cuando termine, debería tener un recuento de referencias de cero, y si Tcl no debe desechar la lista, el sistema de archivos debe asegurarse de retener un recuento de referencias del valor.

Tcl_FSAccess comprueba si se permitiría al proceso leer, escribir o probar la existencia del archivo (u otro objeto del sistema de archivos) cuyo nombre es pathname. Si pathname es un enlace simbólico en Unix, entonces se prueban los permisos del archivo al que se refiere este enlace simbólico.

En caso de éxito (se otorgan todos los permisos solicitados), se devuelve cero. En caso de error (al menos un bit en el modo solicitado un permiso denegado, o ocurrió algún otro error), se devuelve -1.

Tcl_FSStat rellena la estructura Tcl_StatBuf statPtr con información sobre el archivo especificado. No necesita ningún derecho de acceso al archivo para obtener esta información, pero necesita derechos de búsqueda en todos los directorios nombrados en la ruta que conduce al archivo. La estructura Tcl_StatBuf incluye información sobre el dispositivo, inodo (siempre 0 en Windows), modo de privilegio, nlink (siempre 1 en Windows), id de usuario (siempre 0 en Windows), id de grupo (siempre 0 en Windows), rdev (igual que el dispositivo en Windows), tamaño, hora de último acceso, hora de última modificación y hora de último cambio de metadatos. Consulte la **API de resultados de stat portátiles** para obtener una descripción de cómo escribir código portátil para asignar y acceder a la estructura Tcl_StatBuf.

Si path existe, Tcl_FSStat devuelve 0 y la estructura stat se rellena con datos. De lo contrario, se devuelve -1 y no se proporciona información de stat.

Tcl_FSOpenFileChannel abre un archivo especificado por pathPtr y devuelve un manejador de canal que se puede utilizar para realizar operaciones de entrada y salida en el archivo. Esta API está modelada a partir del procedimiento fopen de la biblioteca estándar de E/S de Unix. La sintaxis y el significado de todos los argumentos son similares a los dados en el comando open de Tcl al abrir un archivo. Si ocurre un error al abrir el canal, Tcl_FSOpenFileChannel devuelve NULL y registra un código de error POSIX que se puede recuperar con Tcl_GetErrno. Además, si interp no es NULL, Tcl_FSOpenFileChannel deja un mensaje de error en el resultado de interp después de cualquier error.

El canal recién creado no se registra en el intérprete suministrado; para registrarlo, utilice Tcl_RegisterChannel. Si uno de los canales estándar, stdin, stdout o stderr se cerró previamente, el acto de crear el nuevo canal también lo asigna como reemplazo del canal estándar.

Tcl_FSGetCwd reemplaza la versión de biblioteca de getcwd.

Devuelve el directorio de trabajo actual de la biblioteca de Tcl. Este puede ser diferente del directorio de trabajo de la plataforma nativa, lo que ocurre cuando el directorio de trabajo actual no está en el sistema de archivos nativo.

El resultado es un puntero a un Tcl_Obj que especifica el directorio actual, o NULL si no se pudo determinar el directorio actual. Si se devuelve NULL, se deja un mensaje de error en el resultado de interp.

El resultado ya tiene incrementado su recuento de referencias para el llamador. Cuando ya no sea necesario, se debe disminuir ese recuento de referencias. Esto es necesario por motivos de seguridad de hilos, para permitir que varios hilos accedan a esta y a funciones relacionadas, al tiempo que se garantiza que los resultados sean siempre válidos.

Tcl_FSChdir reemplaza la versión de biblioteca de chdir. La ruta se normaliza y luego se pasa al sistema de archivos que la reclama. ESTRUCTURA DEL SISTEMA DE ARCHIVOS

Estos campos contienen información básica sobre la estructura del sistema de archivos y las direcciones de las funciones que se utilizan para asociar un sistema de archivos particular con una ruta de archivo, y para manejar el manejo interno de las representaciones de rutas, por ejemplo, copiarlas y liberarlas.

NOMBRE DEL TIPO

El campo typeName contiene una cadena terminada en nulo que identifica el tipo del sistema de archivos implementado, por ejemplo, "nativo", "zip" o "vfs".

LONGITUD DE LA ESTRUCTURA

El campo structureLength generalmente se implementa como sizeof(Tcl_Filesystem), y está ahí para permitir una mayor compatibilidad binaria hacia atrás si el tamaño de la estructura cambia en una futura versión de Tcl.

VERSIÓN

El campo version debe establecerse en TCL_FILESYSTEM_VERSION_1.

PROCEDIMIENTO DE RUTA EN SISTEMA DE ARCHIVOS

El campo pathInFilesystemProc contiene la dirección de una función que se llama para determinar si un valor de ruta dado pertenece o no a este sistema de archivos. Tcl solo llamará al resto de las funciones del sistema de archivos con una ruta para la cual esta función ha devuelto TCL_OK. Si la ruta no pertenece, se debe devolver -1 (el comportamiento de Tcl para cualquier otro valor de retorno no está definido). Si se devuelve TCL_OK, entonces el parámetro de salida opcional clientDataPtr se puede usar para devolver una representación interna (específica del sistema de archivos) de la ruta, que se almacenará en caché dentro del valor de la ruta y podrá ser recuperada eficientemente por las otras funciones del sistema de archivos. Tcl almacenará en caché simultáneamente el hecho de que esta ruta pertenece a este sistema de archivos. Dichas cachés se invalidan cuando se agregan o eliminan estructuras del sistema de archivos de la lista interna de sistemas de archivos conocidos de Tcl.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

Función para procesar una llamada a Tcl_FSStat. Debe implementarse para cualquier sistema de archivos razonable, ya que muchos comandos a nivel de Tcl dependen crucialmente de él (por ejemplo, file atime, file isdirectory, file size, glob).

El Tcl_FSStatProc llena la estructura stat statPtr con información sobre el archivo especificado. Tcl POSIX commands

NAME

Tcl POSIX commands
filesystem procedures - filesystem interface procedures

SYNOPSIS

package require Tcl

These procedures are part of the Tcl Support Library which allows the Tcl kernel to interact with arbitrary filesystems.

DESCRIPTION

The Tcl kernel supports the notion of virtual filesystems. This allows Tcl scripts to interact with things other than the native operating system filesystem. Examples include Zip archives, FTP sites, or even memory-based virtual filesystems.

This document describes the procedures that Tcl filesystems must implement in order to register themselves with the Tcl kernel. These procedures are collected together in a structure of type Tcl_Filesystem.

The procedures described below are grouped into two classes:

  • Procedures that must be implemented for writeable filesystems.

  • Procedures that need not be implemented because the core has a fallback implementation available.

The following structures are used throughout this document:

Tcl_Obj
Tcl's internal object representation. Used here to represent paths.
Tcl_StatBuf
A structure used to hold file status information, analogous to the structure returned by the POSIX stat system call. See Tcl_FSStatProc.
Tcl_LoadHandle
A filesystem-specific token returned by Tcl_FSLoadFileProc which identifies a loaded file.
Tcl_FSUnloadFileProc
A pointer to a function that unloads a file previously loaded by Tcl_FSLoadFileProc.

STANDARD FILESYSTEM PROCEDURES

These are the procedures that Tcl calls out to for filesystem operations. They are invoked implicitly by Tcl commands such as open, stat, cd, etc.

OPENFILEPROC

Function to process a Tcl_FSOpenFile call. Must be implemented by all filesystems.

typedef Tcl_Channel Tcl_FSOpenFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int openFlags);

The function is responsible for opening the file specified by pathPtr according to the flags specified in openFlags. openFlags is a bitmask containing the same flags as the POSIX open(2) system call (e.g., O_RDONLY, O_WRONLY, O_RDWR, O_CREAT, O_TRUNC, O_APPEND). The function should return a Tcl_Channel handle representing the opened file, or NULL if an error occurred. If NULL is returned, an error message should be left in the interp's result.

GETNATIVEPATHPROC

Function to process a Tcl_FSGetNativePath call. Must be implemented by all filesystems.

typedef Tcl_Obj *Tcl_FSGetNativePathProc(
        Tcl_Obj *pathPtr);

This function is used to translate a Tcl path into a path that is native to the underlying filesystem. For most filesystems, this will just be the path itself. However, for virtual filesystems, it may be necessary to perform some translation. For example, a virtual filesystem might use a different path separator than Tcl's native '/' character. The function should return a new Tcl_Obj representing the native path, or NULL if the translation fails.

STATPROC

Function to process a Tcl_FSStat call. Must be implemented by all filesystems.

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

The function should fill the statPtr structure with status information about the file specified by pathPtr. It should return TCL_OK on success and TCL_ERROR on failure. If an error occurs, an error message should be left in the interp's result.

LISTFILESPROC

Function to process a Tcl_FSListFiles call. Must be implemented by all filesystems.

typedef Tcl_Obj *Tcl_FSListFilesProc(
        Tcl_Obj *pathPtr);

The function should return a Tcl list of Tcl_Obj pointers, where each pointer represents the name of a file or directory within the directory specified by pathPtr. If an error occurs, NULL should be returned and an error message should be left in the interp's result.

GETREADFILEPROC

Function to process a Tcl_FSReadFile call. Must be implemented by all filesystems.

typedef Tcl_Obj *Tcl_FSReadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr);

The function should read the entire contents of the file specified by pathPtr and return it as a Tcl string object. If an error occurs, NULL should be returned and an error message should be left in the interp's result.

GETWRITEREMOVEFILEPROC

Function to process a Tcl_FSWriteFile call. Must be implemented by all filesystems.

typedef int Tcl_FSWriteFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_Obj *contentPtr);

The function should write the contents of the Tcl string object contentPtr to the file specified by pathPtr. If the file already exists, its previous contents should be truncated. The function should return TCL_OK on success and TCL_ERROR on failure. If an error occurs, an error message should be left in the interp's result.

CREATENEWDIRPROC

Function to process a Tcl_FSCreateDirectory call. Should be implemented unless the FS is read-only.

typedef int Tcl_FSCreateDirectoryProc(
        Tcl_Obj *pathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, a new directory should have been added to the filesystem in the location specified by pathPtr.

REMOVEDIRECTORYPROC

Function to process a Tcl_FSRemoveDirectory call. Should be implemented unless the FS is read-only.

typedef int Tcl_FSRemoveDirectoryProc(
        Tcl_Obj *pathPtr,
        int recursive,
        Tcl_Obj **errorPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, the directory specified by pathPtr should have been removed from the filesystem. If the recursive flag is given, then a non-empty directory should be deleted without error. If this flag is not given, then and the directory is non-empty a POSIX “EEXIST” error should be signaled. If an error does occur, the name of the file or directory which caused the error should be placed in errorPtr.

DELETEFILEPROC

Function to process a Tcl_FSDeleteFile call. Should be implemented unless the FS is read-only.

typedef int Tcl_FSDeleteFileProc(
        Tcl_Obj *pathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, the file specified by pathPtr should have been removed from the filesystem. Note that, if the filesystem supports symbolic links, Tcl will always call this function and not Tcl_FSRemoveDirectoryProc when needed to delete them (even if they are symbolic links to directories).

FILESYSTEM EFFICIENCY

These functions need not be implemented for a particular filesystem because the core has a fallback implementation available. See each individual description for the consequences of leaving the field NULL.

LSTATPROC

Function to process a Tcl_FSLstat call. If not implemented, Tcl will attempt to use the statProc defined above instead. Therefore it need only be implemented if a filesystem can differentiate between stat and lstat calls.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

The behavior of this function is very similar to that of the Tcl_FSStatProc defined above, except that if it is applied to a symbolic link, it returns information about the link, not about the target file.

COPYFILEPROC

Function to process a Tcl_FSCopyFile call. If not implemented Tcl will fall back on open-r, open-w and fcopy as a copying mechanism. Therefore it need only be implemented if the filesystem can perform that action more efficiently.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the copying process. Note that, destPathPtr is the name of the file which should become the copy of srcPathPtr. It is never the name of a directory into which srcPathPtr could be copied (i.e. the function is much simpler than the Tcl level file copy subcommand). Note that, if the filesystem supports symbolic links, Tcl will always call this function and not copyDirectoryProc when needed to copy them (even if they are symbolic links to directories). Finally, if the filesystem determines it cannot support the file copy action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

RENAMEFILEPROC

Function to process a Tcl_FSRenameFile call. If not implemented, Tcl will fall back on a copy and delete mechanism. Therefore it need only be implemented if the filesystem can perform that action more efficiently.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the renaming process. If the filesystem determines it cannot support the file rename action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

COPYDIRECTORYPROC

Function to process a Tcl_FSCopyDirectory call. If not implemented, Tcl will fall back on a recursive file mkdir, file copy mechanism. Therefore it need only be implemented if the filesystem can perform that action more efficiently.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

The return value is a standard Tcl result indicating whether an error occurred in the copying process. If an error does occur, the name of the file or directory which caused the error should be placed in errorPtr. Note that, destPathPtr is the name of the directory-name which should become the mirror-image of srcPathPtr. It is not the name of a directory into which srcPathPtr should be copied (i.e. the function is much simpler than the Tcl level file copy subcommand). Finally, if the filesystem determines it cannot support the directory copy action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

LOADFILEPROC

Function to process a Tcl_FSLoadFile call. If not implemented, Tcl will fall back on a copy to native-temp followed by a Tcl_FSLoadFile on that temporary copy. Therefore it need only be implemented if the filesystem can load code directly, or it can be implemented simply to return TCL_ERROR to disable load functionality in this filesystem entirely.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Returns a standard Tcl completion code. If an error occurs, an error message is left in the interp's result. The function dynamically loads a binary code file into memory. On a successful load, the handlePtr should be filled with a token for the dynamically loaded file, and the unloadProcPtr should be filled in with the address of a procedure. The unload procedure will be called with the given Tcl_LoadHandle as its only parameter when Tcl needs to unload the file. For example, for the native filesystem, the Tcl_LoadHandle returned is currently a token which can be used in the private TclpFindSymbol to access functions in the new code. Each filesystem is free to define the Tcl_LoadHandle as it requires. Finally, if the filesystem determines it cannot support the file load action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

UNLOADFILEPROC

Function to unload a previously successfully loaded file. If load was implemented, then this should also be implemented, if there is any cleanup action required.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

Function to process a Tcl_FSGetCwd call. Most filesystems need not implement this. It will usually only be called once, if getcwd is called before chdir. May be NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

If the filesystem supports a native notion of a current working directory (which might perhaps change independent of Tcl), this function should return that cwd as the result, or NULL if the current directory could not be determined (e.g. the user does not have appropriate permissions on the cwd directory). If NULL is returned, an error message is left in the interp's result.

CHDIRPROC

Function to process a Tcl_FSChdir call. If filesystems do not implement this, it will be emulated by a series of directory access checks. Otherwise, virtual filesystems which do implement it need only respond with a positive return result if the pathPtr is a valid, accessible directory in their filesystem. They need not remember the result, since that will be automatically remembered for use by Tcl_FSGetCwd. Real filesystems should carry out the correct action (i.e. call the correct system chdir API).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

The Tcl_FSChdirProc changes the applications current working directory to the value specified in pathPtr. The function returns -1 on error or 0 on success.
