ARGUMENTOS

Tcl_EventSetupProc *setupProc (entrada)
Procedimiento a invocar para preparar la espera de eventos en Tcl_DoOneEvent.
Tcl_EventCheckProc *checkProc (entrada)
Procedimiento para que Tcl_DoOneEvent lo invoque después de esperar eventos. Comprueba si han ocurrido eventos y, si es así, los pone en cola.
ClientData clientData (entrada)
Valor arbitrario de una palabra para pasar a setupProc, checkProc, o deleteProc.
const Tcl_Time *timePtr (entrada)
Indica la cantidad máxima de tiempo a esperar por un evento. Esto se especifica como un intervalo (cuánto tiempo esperar), no como un tiempo absoluto (cuándo despertarse). Si el puntero pasado a Tcl_WaitForEvent es NULL, significa que no hay tiempo máximo de espera: esperar para siempre si es necesario.
Tcl_Event *evPtr (entrada)
Un evento para añadir a la cola de eventos. El espacio para el evento debe haber sido asignado por el llamador usando Tcl_Alloc o ckalloc.
Tcl_QueuePosition position (entrada)
Dónde añadir el nuevo evento en la cola: TCL_QUEUE_TAIL, TCL_QUEUE_HEAD, o TCL_QUEUE_MARK.
Tcl_ThreadId threadId (entrada)
Un identificador único para un hilo.
Tcl_EventDeleteProc *deleteProc (entrada)
Procedimiento a invocar para cada evento en cola en Tcl_DeleteEvents.
int flags (entrada)
Qué tipos de eventos procesar. Estas banderas son las mismas que las pasadas a Tcl_DoOneEvent.
int mode (entrada)
Indica si los eventos deben ser procesados por Tcl_ServiceAll. Debe ser uno de TCL_SERVICE_NONE o TCL_SERVICE_ALL.
Tcl_NotifierProcs* notifierProcPtr (entrada)
Estructura de punteros de función que describe los procedimientos de notificador que reemplazarán a los instalados en el ejecutable. Ver REEMPLAZANDO EL NOTIFICADOR para más detalles.

INTRODUCCIÓN

Las interfaces descritas aquí se utilizan para personalizar el bucle de eventos de Tcl. Las dos personalizaciones más comunes son añadir nuevas fuentes de eventos y fusionar el bucle de eventos de Tcl con algún otro bucle de eventos, como uno proporcionado por una aplicación en la que Tcl esté incrustado. Cada una de estas tareas se describe en una sección separada a continuación.

Los procedimientos de esta entrada del manual son los bloques de construcción con los que se construye el notificador de eventos de Tcl. El notificador de eventos es la capa más baja en el mecanismo de eventos de Tcl. Consta de tres cosas:

[1]
Fuentes de eventos: estas representan las formas en que se pueden generar eventos. Por ejemplo, hay una fuente de eventos de temporizador que implementa el procedimiento Tcl_CreateTimerHandler y el comando after, y hay una fuente de eventos de archivo que implementa el procedimiento Tcl_CreateFileHandler en sistemas Unix. Una fuente de eventos debe trabajar con el notificador para detectar eventos en los momentos adecuados, registrarlos en la cola de eventos y, eventualmente, notificar al software de nivel superior que han ocurrido. Los procedimientos Tcl_CreateEventSource, Tcl_DeleteEventSource y Tcl_SetMaxBlockTime, Tcl_QueueEvent, y Tcl_DeleteEvents se utilizan principalmente por las fuentes de eventos.
[2]
La cola de eventos: para aplicaciones sin hilos, hay una única cola para toda la aplicación, que contiene eventos que han sido detectados pero aún no han sido procesados. Las fuentes de eventos colocan eventos en la cola para que puedan ser procesados en orden en momentos apropiados durante el bucle de eventos. La cola de eventos garantiza una disciplina justa de manejo de eventos, de modo que ninguna fuente de eventos pueda dejar a las otras sin atención. También permite que los eventos se guarden para ser procesados en un momento futuro. Las aplicaciones con hilos funcionan de manera similar, excepto que hay una cola de eventos separada para cada hilo que contiene un intérprete Tcl. Tcl_QueueEvent se utiliza (principalmente por las fuentes de eventos) para añadir eventos a la cola de eventos y Tcl_DeleteEvents se utiliza para eliminar eventos de la cola sin procesarlos. En una aplicación con hilos, Tcl_QueueEvent añade un evento a la cola del hilo actual, y Tcl_ThreadQueueEvent añade un evento a una cola en un hilo específico.
[3]
El bucle de eventos: para detectar y procesar eventos, la aplicación entra en un bucle que espera a que ocurran eventos, los coloca en la cola de eventos y luego los procesa. La mayoría de las aplicaciones harán esto llamando al procedimiento Tcl_DoOneEvent, que se describe en una entrada de manual separada.

La mayoría de las aplicaciones Tcl no necesitan preocuparse por ninguno de los internos del notificador de Tcl. Sin embargo, el notificador ahora tiene suficiente flexibilidad para ser redirigido bien para una nueva plataforma o para usar un bucle de eventos externo (como el bucle de eventos de Motif, cuando Tcl está incrustado en una aplicación de Motif). Los procedimientos Tcl_WaitForEvent y Tcl_SetTimer son normalmente implementados por Tcl, pero pueden ser reemplazados con nuevas versiones para redirigir el notificador (Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_Sleep, Tcl_CreateFileHandler, y Tcl_DeleteFileHandler también deben ser reemplazados; ver CREANDO UN NUEVO NOTIFICADOR más abajo para detalles). Los procedimientos Tcl_ServiceAll, Tcl_ServiceEvent, Tcl_GetServiceMode, y Tcl_SetServiceMode se proporcionan para ayudar a conectar el bucle de eventos de Tcl a un bucle de eventos externo como el de Motif.

CONCEPTOS BÁSICOS DEL NOTIFICADOR

La forma más sencilla de entender cómo funciona el notificador es considerar lo que ocurre cuando se llama a Tcl_DoOneEvent. A Tcl_DoOneEvent se le pasa un argumento flags que indica qué tipo de eventos está permitido procesar y también si debe bloquearse o no si no hay eventos listos. Tcl_DoOneEvent realiza las siguientes acciones:

[1]
Comprueba la cola de eventos para ver si contiene algún evento que pueda ser procesado. Si es así, procesa el primer evento posible, lo elimina de la cola y devuelve. Lo hace llamando a Tcl_ServiceEvent y pasando el argumento flags.
[2]
Se prepara para bloquear por un evento. Para ello, Tcl_DoOneEvent invoca un procedimiento setup en cada fuente de eventos. La fuente de eventos realizará la inicialización específica de la fuente de eventos y posiblemente llamará a Tcl_SetMaxBlockTime para limitar cuánto tiempo bloqueará Tcl_WaitForEvent si no ocurren nuevos eventos.
[3]
Llama a Tcl_WaitForEvent. Este procedimiento se implementa de forma diferente en distintas plataformas; espera a que ocurra un evento, basándose en la información proporcionada por las fuentes de eventos. Puede hacer que la aplicación se bloquee si timePtr especifica un intervalo distinto de 0. Tcl_WaitForEvent devuelve cuando algo ha ocurrido, como que un archivo se ha vuelto legible o el intervalo dado por timePtr ha expirado. Si no hay eventos para que Tcl_WaitForEvent espere, de modo que se bloquearía indefinidamente, entonces devuelve inmediatamente y Tcl_DoOneEvent devuelve 0.
[4]
Llama a un procedimiento check en cada fuente de eventos. El procedimiento check determina si ocurrieron eventos de interés para esta fuente. Si es así, los eventos se añaden a la cola de eventos.

CREACIÓN DE UNA NUEVA FUENTE DE EVENTOS

Una fuente de eventos consta de tres procedimientos invocados por el notificador, además de procedimientos C adicionales que son invocados por código de nivel superior para organizar callbacks basados en eventos. Los tres procedimientos llamados por el notificador consisten en los procedimientos de configuración y verificación descritos anteriormente, más un procedimiento adicional que se invoca cuando un evento se elimina de la cola de eventos para su atención.

El procedimiento Tcl_CreateEventSource crea una nueva fuente de eventos. Sus argumentos especifican el procedimiento de configuración y el procedimiento de verificación para la fuente de eventos. SetupProc debe coincidir con el siguiente prototipo:

typedef void Tcl_EventSetupProc(
        ClientData clientData,
        int flags);

El argumento clientData será el mismo que el argumento clientData para Tcl_CreateEventSource; típicamente se usa para apuntar a información privada administrada por la fuente de eventos. El argumento flags será el mismo que el argumento flags pasado a Tcl_DoOneEvent excepto que nunca será 0 (Tcl_DoOneEvent reemplaza 0 con TCL_ALL_EVENTS). Flags indica qué tipos de eventos deben considerarse; si el bit correspondiente a esta fuente de eventos no está establecido, la fuente de eventos debe regresar inmediatamente sin hacer nada. Por ejemplo, la fuente de eventos de archivo verifica el bit TCL_FILE_EVENTS.

El trabajo de SetupProc es asegurarse de que la aplicación despierte cuando ocurran eventos del tipo deseado. Esto se hace típicamente de forma dependiente de la plataforma. Por ejemplo, en Unix, una fuente de eventos podría llamar a Tcl_CreateFileHandler; en Windows, podría solicitar notificación con un evento de Windows. Para fuentes de eventos impulsadas por temporizador, como eventos de temporizador o cualquier evento sondado, la fuente de eventos puede llamar a Tcl_SetMaxBlockTime para forzar a la aplicación a despertar después de un tiempo especificado, incluso si no han ocurrido eventos. Si ninguna fuente de eventos llama a Tcl_SetMaxBlockTime, entonces Tcl_WaitForEvent esperará el tiempo necesario para que ocurra un evento; de lo contrario, solo esperará el tiempo más corto pasado a Tcl_SetMaxBlockTime por una de las fuentes de eventos. Si una fuente de eventos sabe que ya tiene eventos listos para reportar, puede solicitar un tiempo de bloqueo máximo de cero. Por ejemplo, el procedimiento de configuración para la fuente de eventos X verifica si ya hay eventos en cola. Si los hay, llama a Tcl_SetMaxBlockTime con un tiempo de bloqueo de 0 para que Tcl_WaitForEvent no se bloquee si no hay nuevos datos en la conexión X. El argumento timePtr para Tcl_WaitForEvent apunta a una estructura que describe un intervalo de tiempo en segundos y microsegundos:

typedef struct Tcl_Time {
    long sec;
    long usec;
} Tcl_Time;

El campo usec debe ser menor que 1000000.

La información proporcionada a Tcl_SetMaxBlockTime solo se utiliza para la próxima llamada a Tcl_WaitForEvent; se descarta después de que Tcl_WaitForEvent regresa. La próxima vez que se realice una espera de eventos, se llamará a los procedimientos de configuración de cada una de las fuentes de eventos, y podrán especificar nueva información para esa espera de eventos.

Si la aplicación utiliza un bucle de eventos externo en lugar de Tcl_DoOneEvent, las fuentes de eventos pueden necesitar llamar a Tcl_SetMaxBlockTime en otros momentos. Por ejemplo, si se registra un nuevo manejador de eventos que necesita sondear eventos, la fuente de eventos puede llamar a Tcl_SetMaxBlockTime para establecer el tiempo de bloqueo a cero para forzar al bucle de eventos externo a llamar a Tcl. En este caso, Tcl_SetMaxBlockTime invoca Tcl_SetTimer con el intervalo más corto visto desde la última llamada a Tcl_DoOneEvent o Tcl_ServiceAll.

Además del procedimiento genérico Tcl_SetMaxBlockTime, otros procedimientos específicos de la plataforma también pueden estar disponibles para setupProc, si hay información adicional necesaria para Tcl_WaitForEvent en esa plataforma. Por ejemplo, en sistemas Unix se puede usar la interfaz Tcl_CreateFileHandler para esperar eventos de archivo.

El segundo procedimiento proporcionado por cada fuente de eventos es su procedimiento de verificación, indicado por el argumento checkProc para Tcl_CreateEventSource. CheckProc debe coincidir con el siguiente prototipo:

typedef void Tcl_EventCheckProc(
        ClientData clientData,
        int flags);

Los argumentos para este procedimiento son los mismos que los de setupProc. CheckProc es invocado por Tcl_DoOneEvent después de que ha esperado eventos. Presumiblemente, al menos una fuente de eventos está ahora preparada para poner un evento en cola. Tcl_DoOneEvent llama a cada una de las fuentes de eventos en turno, para que todas tengan la oportunidad de poner en cola cualquier evento que esté listo. El procedimiento de verificación hace dos cosas. Primero, debe verificar si algún evento se ha disparado. Diferentes fuentes de eventos hacen esto de diferentes maneras.

Si el procedimiento de verificación de una fuente de eventos detecta un evento interesante, debe agregar el evento a la cola de eventos de Tcl. Para hacer esto, la fuente de eventos llama a Tcl_QueueEvent. El argumento evPtr es un puntero a una estructura asignada dinámicamente que contiene el evento (ver más abajo para más información sobre problemas de gestión de memoria). Cada fuente de eventos puede definir su propia estructura de eventos con la información que sea relevante para esa fuente de eventos. Sin embargo, el primer elemento de la estructura debe ser una estructura de tipo Tcl_Event, y la dirección de esta estructura se utiliza al comunicarse entre la fuente de eventos y el resto del notificador. Un Tcl_Event tiene la siguiente definición:

typedef struct {
    Tcl_EventProc *proc;
    struct Tcl_Event *nextPtr;
} Tcl_Event;

La fuente de eventos debe completar el campo proc del evento antes de llamar a Tcl_QueueEvent. El nextPtr se utiliza para enlazar los eventos en la cola y no debe ser modificado por la fuente de eventos.

Un evento puede agregarse a la cola en cualquiera de las tres posiciones, dependiendo del argumento position para Tcl_QueueEvent:

TCL_QUEUE_TAIL
Agrega el evento al final de la cola, de modo que todos los demás eventos pendientes sean atendidos primero. Este es casi siempre el lugar correcto para nuevos eventos.
TCL_QUEUE_HEAD
Agrega el evento al principio de la cola, de modo que sea atendido antes que todos los demás eventos en cola.
TCL_QUEUE_MARK
Agrega el evento al principio de la cola, a menos que haya otros eventos al principio cuya posición sea TCL_QUEUE_MARK; en caso afirmativo, agrega el nuevo evento justo después de todos los demás eventos TCL_QUEUE_MARK. Este valor de position se utiliza para insertar una secuencia ordenada de eventos al principio de la cola, como una serie de eventos Enter y Leave sintetizados durante una operación de grab o ungrab en Tk.

Cuando es hora de manejar un evento de la cola (pasos 1 y 4 anteriores), Tcl_ServiceEvent invocará el proc especificado en la primera estructura Tcl_Event en cola. Proc debe coincidir con el siguiente prototipo:

typedef int Tcl_EventProc(
        Tcl_Event *evPtr,
        int flags);

El primer argumento para proc es un puntero al evento, que será el mismo que el primer argumento de la llamada a Tcl_QueueEvent que agregó el evento a la cola. El segundo argumento para proc es el argumento flags para la llamada actual a Tcl_ServiceEvent; esto lo utiliza la fuente de eventos para regresar inmediatamente si sus eventos no son relevantes.

Es responsabilidad de proc manejar el evento, típicamente invocando uno o más comandos Tcl o callbacks a nivel C. Una vez que la fuente de eventos ha terminado de manejar el evento, regresa 1 para indicar que el evento puede ser eliminado de la cola. Si por alguna razón la fuente de eventos decide que el evento no puede ser manejado en este momento, puede regresar 0 para indicar que el evento debe ser diferido para procesamiento posterior; en este caso Tcl_ServiceEvent continuará con el siguiente evento en la cola e intentará atenderlo. Hay varias razones por las que una fuente de eventos podría diferir un evento. Una posibilidad es que los eventos de este tipo estén excluidos por el argumento flags. Por ejemplo, la fuente de eventos de archivo siempre regresará 0 si el bit TCL_FILE_EVENTS no está establecido en flags. Otro ejemplo de diferimiento de eventos ocurre en Tk si se ha invocado Tk_RestrictEvents para diferir ciertos tipos de eventos de ventana.

Cuando proc regresa 1, Tcl_ServiceEvent eliminará el evento de la cola de eventos y liberará su almacenamiento. Tenga en cuenta que el almacenamiento de un evento debe ser asignado por la fuente de eventos (usando Tcl_Alloc o la macro Tcl ckalloc) antes de llamar a Tcl_QueueEvent, pero será liberado por Tcl_ServiceEvent, no por la fuente de eventos.

Las aplicaciones multihilo funcionan de manera similar, excepto que hay una cola de eventos separada para cada hilo que contiene un intérprete Tcl. Llamar a Tcl_QueueEvent en una aplicación multihilo agrega un evento a la cola del hilo actual. Para agregar un evento a la cola de otro hilo, use Tcl_ThreadQueueEvent. Tcl_ThreadQueueEvent acepta como argumento un argumento Tcl_ThreadId, que identifica de forma única un hilo en una aplicación Tcl. Para obtener el Tcl_ThreadId del hilo actual, use el procedimiento Tcl_GetCurrentThread. (Un hilo necesitaría entonces pasar este identificador a otros hilos para que esos hilos puedan agregar eventos a su cola). Después de agregar un evento a la cola de otro hilo, generalmente necesita llamar a Tcl_ThreadAlert para "despertar" al notificador de ese hilo para alertarlo sobre el nuevo evento.

Tcl_DeleteEvents se puede utilizar para eliminar explícitamente uno o más eventos de la cola de eventos. Tcl_DeleteEvents llama a proc para cada evento en la cola, eliminando aquellos para los que el procedimiento regresa 1. Los eventos para los que el procedimiento regresa 0 permanecen en la cola. Proc debe coincidir con el siguiente prototipo:

typedef int Tcl_EventDeleteProc(
        Tcl_Event *evPtr,
        ClientData clientData);

INTRODUCTION

The Tcl event loop is the core mechanism for handling asynchronous events in Tcl. It allows Tcl applications to respond to various events, such as user input, file I/O, timers, and idle processing, without blocking the main thread of execution. The event loop relies on a notification mechanism to manage and dispatch these events.

NOTIFIER BASICS

The Tcl notifier is responsible for managing the event loop. It provides an interface for creating and registering different types of event sources, such as file descriptors, timers, and idle events. When an event occurs, the notifier dispatches it to the appropriate handler procedure.

The default notifier in Tcl is implemented using the underlying operating system's event notification facilities (e.g., `select` on Unix-like systems, `WaitForMultipleObjects` on Windows). However, Tcl's event loop can be extended or replaced with custom notifiers to support different event sources or integration with other event loops.

CREATING A NEW EVENT SOURCE

To create a new event source, you need to define a structure that conforms to the `Tcl_Event` structure and implement a source procedure. The source procedure is responsible for checking the event source and queueing new events when they occur.

You can register a new event source with the Tcl interpreter using the `Tcl_EventSource` function. This function takes the interpreter, the source procedure, and client data as arguments.

CREATING A NEW NOTIFIER

A custom notifier can be created by defining a structure that conforms to the `Tcl_Notifier` structure. This structure contains function pointers to handle different event types, such as initialization, event queuing, event source management, and event dispatching.

The `Tcl_InitNotifier` function is called during interpreter initialization to set up the default notifier. You can replace the default notifier with your custom notifier using the `Tcl_SetDefaultNotifier` function.

REPLACING THE NOTIFIER

Replacing the Tcl notifier can be useful in scenarios where you need to integrate Tcl's event loop with an existing event loop or provide support for custom event sources not covered by the default notifier. This allows Tcl to participate in a broader event-driven system.

EXTERNAL EVENT LOOPS

Tcl can be integrated with external event loops by replacing its default notifier. This allows Tcl applications to run within a larger event-driven framework, such as those found in GUI toolkits or asynchronous I/O libraries. The Tcl interpreter's event loop will then be driven by the external loop.
