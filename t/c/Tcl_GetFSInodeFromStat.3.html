DESCRIPCIÓN

Hay varias razones para llamar a las funciones de la API Tcl_FS (por ejemplo, Tcl_FSAccess y Tcl_FSStat) en lugar de llamar directamente a funciones de nivel de sistema como access y stat. Primero, funcionarán multiplataforma, por lo que una extensión que las llame debería funcionar sin modificaciones en Unix y Windows. Segundo, la implementación de Windows de algunas de estas funciones corrige algunos errores en las llamadas de nivel de sistema. Tercero, estas llamadas a funciones manejan cualquier conversión de ruta de “Utf a nativa de plataforma” que pueda ser requerida (y pueden almacenar en caché los resultados de dichas conversiones para una mayor eficiencia en llamadas posteriores). Cuarto, y quizás lo más importante, todas estas funciones son “conscientes del sistema de archivos virtual”. Cualquier sistema de archivos virtual (VFS para acortar) que se haya registrado (a través de Tcl_FSRegister) puede redirigir el acceso a archivos a medios o métodos de acceso alternativos. Esto significa que todas estas funciones (y, por lo tanto, los comandos de Tcl correspondientes file, glob, pwd, cd, open, etc.) pueden operar sobre “archivos” que no son archivos nativos en el sistema de archivos nativo. Esto también significa que cualquier extensión de Tcl que acceda al sistema de archivos (FS para acortar) a través de esta API es automáticamente “consciente del sistema de archivos virtual”. Por supuesto, si una extensión accede directamente al sistema de archivos nativo (a través de APIs específicas de la plataforma, por ejemplo), Tcl no puede interceptar dichas llamadas.

Si se han registrado VFS apropiados, los “archivos” pueden ser, para dar dos ejemplos, remotos (por ejemplo, situados en un servidor ftp remoto) o archivados (por ejemplo, dentro de un archivo .zip). Dichos sistemas de archivos registrados proporcionan una tabla de consulta de funciones para implementar toda o parte de la funcionalidad enumerada aquí. Finalmente, las llamadas Tcl_FSStat y Tcl_FSLstat abstraen el búfer “struct stat”, permitiendo que el mismo código se utilice tanto en sistemas con como sin soporte para archivos mayores de 2 GB.

La API Tcl_FS está “Tcl_Obj”-ificada y puede almacenar en caché representaciones internas y otras cadenas relacionadas con rutas (por ejemplo, el directorio de trabajo actual). Un efecto secundario de esto es que no se deben pasar valores con un recuento de referencias de cero a ninguna de estas funciones. Si tales llamadas se manejaran, podrían resultar en fugas de memoria (en algunas circunstancias, el código del sistema de archivos puede desear retener una referencia al valor pasado, y por lo tanto, no se debe asumir que después de que cualquiera de estas llamadas retorne, el valor aún tenga un recuento de referencias de cero; puede haber sido incrementado) o en una falla de segmentación directa (u otro error de acceso a la memoria) debido a que el valor se libera a mitad de la manipulación compleja del valor requerida para asegurar que la ruta esté completamente normalizada y sea absoluta para la determinación del sistema de archivos. La lección práctica que se debe aprender de esto es que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

es incorrecto y puede causar errores de memoria. El path debe tener su recuento de referencias incrementado antes de pasarlo, o decrementarlo. Por esta razón, los valores con un recuento de referencias de cero no se consideran rutas de sistema de archivos válidas y llamar a cualquier función de la API Tcl_FS con dicho valor no tendrá ningún efecto.

FUNCIONES DE LA API FS

Tcl_FSCopyFile intenta copiar el archivo dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas se encuentran en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), entonces se llama a la función de “copiar archivo” de ese sistema de archivos (si no es NULL). De lo contrario, la función devuelve -1 y establece la variable global C **errno** al código de error POSIX “EXDEV” (que significa un “enlace entre dominios”).

Tcl_FSCopyDirectory intenta copiar el directorio dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas se encuentran en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), entonces se llama a la función de “copiar directorio” de ese sistema de archivos (si no es NULL). De lo contrario, la función devuelve -1 y establece la variable global C **errno** al código de error POSIX “EXDEV” (que significa un “enlace entre dominios”).

Tcl_FSCreateDirectory intenta crear el directorio dado por pathPtr llamando a la función de “crear directorio” del sistema de archivos propietario.

Tcl_FSDeleteFile intenta eliminar el archivo dado por pathPtr llamando a la función de “eliminar archivo” del sistema de archivos propietario.

Tcl_FSRemoveDirectory intenta eliminar el directorio dado por pathPtr llamando a la función de “eliminar directorio” del sistema de archivos propietario.

Tcl_FSRenameFile intenta renombrar el archivo o directorio dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas se encuentran en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), entonces se llama a la función de “renombrar archivo” de ese sistema de archivos (si no es NULL). De lo contrario, la función devuelve -1 y establece la variable global C **errno** al código de error POSIX “EXDEV” (que significa un “enlace entre dominios”).

Tcl_FSListVolumes llama a cada sistema de archivos que tiene una función de “listar volúmenes” no NULL y les pide que devuelvan su lista de volúmenes raíz. Acumula los valores de retorno en una lista que se devuelve al llamador (con un recuento de referencias de 0).

Tcl_FSEvalFileEx lee el archivo dado por pathPtr utilizando la codificación identificada por encodingName y evalúa su contenido como un script de Tcl. Devuelve la misma información que Tcl_EvalObjEx. Si encodingName es NULL, se utiliza la codificación del sistema para leer el contenido del archivo. Si el archivo no se pudo leer, se devuelve un error de Tcl para describir por qué no se pudo leer. El carácter de fin de archivo (eofchar) para los archivos es “\x1A” (^Z) para todas las plataformas. Si requiere un “^Z” en el código para comparación de cadenas, puede usar “\x1A”, que será sustituido de forma segura por el intérprete de Tcl en “^Z”. Tcl_FSEvalFile es una versión más simple de Tcl_FSEvalFileEx que siempre utiliza la codificación del sistema al leer el archivo.

Tcl_FSLoadFile carga dinámicamente un archivo de código binario en memoria y devuelve las direcciones de dos procedimientos dentro de ese archivo, si están definidos. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr. Si ese sistema de archivos no implementa esta función (la mayoría de los sistemas de archivos virtuales no lo harán, debido a limitaciones del SO en la carga dinámica de código binario), Tcl intentará copiar el archivo a un directorio temporal y cargar ese archivo temporal. Tcl_FSUnloadFile revierte la operación, pidiendo que la biblioteca indicada por loadHandle sea eliminada del proceso. Tenga en cuenta que, a diferencia del comando unload, esto no le da a la biblioteca ninguna oportunidad de limpieza.

Ambas funciones anteriores devuelven un código de finalización estándar de Tcl. Si ocurre un error, se deja un mensaje de error en el resultado del interp.

El token proporcionado a través de la variable indicada por loadHandlePtr puede usarse con Tcl_FindSymbol.

Tcl_FSMatchInDirectory es utilizada por el código de globbing para buscar en un directorio todos los archivos que coincidan con un patrón dado. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el globbing. Los mensajes de error se colocan en interp (a menos que interp sea NULL, lo cual está permitido), pero los resultados buenos se colocan en el resultPtr proporcionado.

Tenga en cuenta que el código de glob implementa patrones recursivos internamente, por lo que esta función solo recibirá patrones simples, que se pueden hacer coincidir utilizando la lógica de string match. Para manejar la recursión, Tcl llamará a esta función con frecuencia pidiendo solo que se devuelvan directorios. Un caso especial de ser llamado con un patrón NULL indica que la ruta solo debe ser verificada por el tipo correcto.

Tcl_FSLink reemplaza la versión de biblioteca de readlink y la extiende para soportar la creación de enlaces. Se llamará a la función apropiada para el sistema de archivos al que pertenece linkNamePtr.

Si toPtr es NULL, se realiza una acción de “leer enlace”. El resultado es un Tcl_Obj que especifica el contenido del enlace simbólico dado por linkNamePtr, o NULL si el enlace no se pudo leer. El resultado es propiedad del llamador, que debe llamar a Tcl_DecrRefCount cuando el resultado ya no sea necesario. Si toPtr no es NULL, Tcl debe crear un enlace de uno de los tipos pasados en el flag linkAction. Este flag es una combinación OR de TCL_CREATE_SYMBOLIC_LINK y TCL_CREATE_HARD_LINK. Donde exista una opción (es decir, se pasa más de un flag), la convención de Tcl es preferir los enlaces simbólicos. Cuando se crea un enlace exitosamente, el valor de retorno debe ser toPtr (que por lo tanto ya es propiedad del llamador). Si no tiene éxito, se devuelve NULL.

Tcl_FSLstat llena la estructura Tcl_StatBuf statPtr con información sobre el archivo especificado. No necesita ningún derecho de acceso al archivo para obtener esta información, pero necesita derechos de búsqueda en todos los directorios nombrados en la ruta que conduce al archivo. La estructura Tcl_StatBuf incluye información sobre el dispositivo, el inodo (siempre 0 en Windows), el modo de privilegios, nlink (siempre 1 en Windows), el ID de usuario (siempre 0 en Windows), el ID de grupo (siempre 0 en Windows), rdev (igual que el dispositivo en Windows), tamaño, última

acceder al tiempo de acceso, tiempo de última modificación y tiempo de último cambio de metadatos. Consulte API DE RESULTADO DE STAT PORTÁTIL para obtener una descripción de cómo escribir código portátil para asignar y acceder a la estructura Tcl_StatBuf.

Si path existe, Tcl_FSLstat devuelve 0 y la estructura stat se rellena con datos. De lo contrario, se devuelve -1 y no se proporciona información de stat.

Tcl_FSUtime reemplaza la versión de biblioteca de utime.

Esto devuelve 0 en caso de éxito y -1 en caso de error (según la documentación de utime). Si tiene éxito, la función actualizará los valores de “atime” y “mtime” del archivo proporcionado.

Tcl_FSFileAttrsGet implementa el acceso de lectura para el subcomando file attributes enlazable. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

Si el resultado es TCL_OK, se colocó un valor en objPtrRef, que solo será válido temporalmente (a menos que se llame a Tcl_IncrRefCount).

Tcl_FSFileAttrsSet implementa el acceso de escritura para el subcomando file attributes enlazable. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

Tcl_FSFileAttrStrings implementa parte del subcomando file attributes enlazable. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

El procedimiento llamado puede devolver una matriz de cadenas o puede devolver NULL y colocar una lista de Tcl en objPtrRef. Tcl tomará esa lista y primero incrementará su recuento de referencias antes de usarla. Al finalizar su uso, Tcl decrementará su recuento de referencias. Por lo tanto, si la lista debe ser eliminada por Tcl cuando termine, debería tener un recuento de referencias de cero, y si la lista no debe ser eliminada, el sistema de archivos debe asegurarse de retener un recuento de referencias del valor.

Tcl_FSAccess comprueba si al proceso se le permitiría leer, escribir o probar la existencia del archivo (u otro objeto del sistema de archivos) cuyo nombre es pathname. Si pathname es un enlace simbólico en Unix, se prueban los permisos del archivo al que se refiere este enlace simbólico.

En caso de éxito (todos los permisos solicitados concedidos), se devuelve cero. En caso de error (al menos un bit en el modo solicitó un permiso denegado, o ocurrió algún otro error), se devuelve -1.

Tcl_FSStat rellena la estructura Tcl_StatBuf statPtr con información sobre el archivo especificado. No necesita ningún derecho de acceso al archivo para obtener esta información, pero necesita derechos de búsqueda a todos los directorios nombrados en la ruta que conduce al archivo. La estructura Tcl_StatBuf incluye información sobre el dispositivo, inodo (siempre 0 en Windows), modo de privilegios, nlink (siempre 1 en Windows), id de usuario (siempre 0 en Windows), id de grupo (siempre 0 en Windows), rdev (igual que el dispositivo en Windows), tamaño, tiempo del último acceso, tiempo de la última modificación y tiempo del último cambio de metadatos. Consulte API DE RESULTADO DE STAT PORTÁTIL para obtener una descripción de cómo escribir código portátil para asignar y acceder a la estructura Tcl_StatBuf.

Si path existe, Tcl_FSStat devuelve 0 y la estructura stat se rellena con datos. De lo contrario, se devuelve -1 y no se proporciona información de stat.

Tcl_FSOpenFileChannel abre un archivo especificado por pathPtr y devuelve un manejador de canal que se puede utilizar para realizar operaciones de entrada y salida en el archivo. Esta API se basa en el procedimiento fopen de la biblioteca estándar de E/S de Unix. La sintaxis y el significado de todos los argumentos son similares a los proporcionados en el comando open de Tcl al abrir un archivo. Si ocurre un error al abrir el canal, Tcl_FSOpenFileChannel devuelve NULL y registra un código de error POSIX que se puede recuperar con Tcl_GetErrno. Además, si interp no es NULL, Tcl_FSOpenFileChannel deja un mensaje de error en el resultado de interp después de cualquier error.

El canal recién creado no se registra en el intérprete suministrado; para registrarlo, utilice Tcl_RegisterChannel. Si uno de los canales estándar, stdin, stdout o stderr se cerró previamente, la creación del nuevo canal también lo asigna como reemplazo del canal estándar.

Tcl_FSGetCwd reemplaza la versión de biblioteca de getcwd.

Devuelve el directorio de trabajo actual de la biblioteca de Tcl. Este puede ser diferente al directorio de trabajo de la plataforma nativa, lo que ocurre cuando el directorio de trabajo actual no está en el sistema de archivos nativo.

El resultado es un puntero a un Tcl_Obj que especifica el directorio actual, o NULL si no se pudo determinar el directorio actual. Si se devuelve NULL, se deja un mensaje de error en el resultado de interp.

El resultado ya tiene su recuento de referencias incrementado para el llamador. Cuando ya no sea necesario, se debe decrementar ese recuento de referencias. Esto es necesario para la seguridad de los hilos, para permitir que múltiples hilos accedan a esta y funciones relacionadas, al tiempo que se garantiza que los resultados sean siempre válidos.

Tcl_FSChdir reemplaza la versión de biblioteca de chdir. La ruta se normaliza y luego se pasa al sistema de archivos que la reclama. Si ese sistema de archivos no implementa esta función, Tcl recurrirá a una combinación de stat y access para verificar si el directorio existe y tiene los permisos adecuados.

Para obtener resultados, consulte la documentación de chdir. Si tiene éxito, mantenemos un registro de la ruta exitosa en cwdPathPtr para llamadas posteriores a Tcl_FSGetCwd.

Tcl_FSPathSeparator devuelve el carácter separador que se utilizará para el elemento más específico de la ruta especificada por pathPtr (es decir, la última parte de la ruta).

El separador se devuelve como un Tcl_Obj que contiene una cadena de longitud 1. Si la ruta no es válida, se devuelve NULL.

Tcl_FSJoinPath toma el Tcl_Obj dado, que debe ser una lista válida (a la que se le permite tener un recuento de referencias de cero), y devuelve el valor de la ruta dado considerando los primeros elements elementos como segmentos de ruta válidos (cada segmento de ruta puede ser una ruta completa, una ruta parcial o simplemente un solo directorio o nombre de archivo posible). Si algún segmento de ruta es en realidad una ruta absoluta, todos los segmentos de ruta anteriores se descartan. Si elements es menor que 0, usamos la lista completa.

Es posible que el valor devuelto sea en realidad un elemento de la lista dada, por lo que el llamador debe tener cuidado de incrementar el recuento de referencias del resultado antes de liberar la lista.

El valor devuelto, típicamente con un recuento de referencias de cero (pero podría compartirse bajo algunas condiciones), contiene la ruta unida. El llamador debe agregar un recuento de referencias al valor antes de usarlo. En particular, el valor devuelto podría ser un elemento de la lista dada, por lo que liberar la lista podría liberar el valor prematuramente si no se ha tomado ninguna referencia. Si el número de elementos es cero, el valor devuelto será un Tcl_Obj de cadena vacía.

Tcl_FSSplitPath toma el Tcl_Obj dado, que debe ser una ruta válida, y devuelve un valor de lista de Tcl que contiene cada segmento de esa ruta como un elemento. Devuelve un valor de lista con un recuento de referencias de cero. Si lenPtr proporcionado no es NULL, la variable a la que apunta se actualizará para contener el número de elementos en la lista devuelta.

Tcl_FSEqualPaths prueba si las dos rutas dadas representan el mismo objeto del sistema de archivos. Devuelve 1 si las rutas son iguales y 0 si son diferentes. Si alguna ruta es NULL, siempre se devuelve 0.

Tcl_FSGetNormalizedPath intenta extraer del Tcl_Obj dado una representación de ruta normalizada única, cuyo valor de cadena se puede utilizar como identificador único del archivo.

Devuelve el valor de la ruta normalizada, propiedad de Tcl, o NULL si la ruta no era válida o no se pudo convertir correctamente. La extracción de rutas absolutas y normalizadas es muy eficiente (porque el sistema de archivos opera internamente sobre estas representaciones), aunque el resultado cuando el sistema de archivos contiene numerosos enlaces simbólicos puede no ser la versión más amigable para el usuario de una ruta. El valor devuelto es propiedad de Tcl y tiene una vida útil equivalente a la de pathPtr proporcionado (a menos que sea una ruta relativa, en cuyo caso el valor de la ruta normalizada puede liberarse en cualquier momento que cambie el cwd); el llamador, por supuesto, puede incrementar el recuento de referencias si desea mantener una copia por más tiempo.

Tcl_FSJoinToPath toma el valor dado, que normalmente debería ser una ruta válida o NULL, y une a ella la matriz de segmentos de ruta proporcionados.

Devuelve un valor, típicamente con un recuento de referencias de cero (pero podría compartirse bajo algunas condiciones), que contiene la ruta unida. El llamador debe agregar un recuento de referencias al valor antes de usarlo. Si alguno de los valores pasados a esta función (pathPtr o elementos de path) tiene un recuento de referencias de cero, se liberarán cuando esta función devuelva.

Tcl_FSConvertToPathType intenta convertir el Tcl_Obj dado a un tipo de ruta Tcl válido, teniendo en cuenta que el cwd puede haber cambiado incluso si este valor supuestamente ya es del tipo correcto. El nombre de archivo puede comenzar con “~” (para indicar el directorio de inicio del usuario actual) o “~<usuario>” (para indicar el directorio de inicio de cualquier usuario).

Si la conversión tiene éxito (es decir, el valor es una ruta válida en uno de los sistemas de archivos actuales), se devuelve TCL_OK. De lo contrario, se devuelve TCL_ERROR y se puede dejar un mensaje de error en el intérprete.

Tcl_FSGetInternalRep extrae la representación interna de un valor de ruta dado, en el sistema de archivos dado. Si el valor de la ruta pertenece a un sistema de archivos diferente, devolvemos NULL. Si la representación interna es actualmente NULL, intentamos generarla, llamando a Tcl_FSCreateInternalRepProc del sistema de archivos.

Devuelve NULL o una representación de ruta interna válida. Esta representación interna se almacena en caché, de modo que las llamadas repetidas a esta función no requerirán conversiones adicionales.

Tcl_FSGetTranslatedPath intenta extraer la ruta traducida del Tcl_Obj dado.

Si la traducción tiene éxito (es decir, el valor es una ruta válida), se devuelve. De lo contrario, se devolverá NULL y se puede dejar un mensaje de error en el intérprete. Una ruta “traducida” es aquella que no contiene secuencias “~” o “~usuario” (estas se han expandido a su representación actual en el sistema de archivos). El valor devuelto es propiedad del llamador, que debe almacenarlo o llamar a Tcl_DecrRefCount para garantizar que la memoria se libere. Esta función tiene poco uso práctico, y Tcl_FSGetNormalizedPath o Tcl_FSGetNativePath suelen ser mejores funciones para la mayoría de los propósitos.

Tcl_FSGetTranslatedStringPath hace lo mismo que Tcl_FSGetTranslatedPath, pero devuelve una cadena de caracteres o NULL. La cadena devuelta está asignada dinámicamente

y y propiedad del llamador, el cual debe almacenarlo o llamar a ckfree para asegurarse de que se libera. De nuevo, Tcl_FSGetNormalizedPath o Tcl_FSGetNativePath suelen ser funciones mejores para la mayoría de los propósitos.

Tcl_FSNewNativePath realiza algo parecido a la operación inversa de las conversiones habituales obj->ruta->representación nativa. Si algún código recupera una ruta en formato nativo (de, por ejemplo, readlink o un diálogo nativo), y esa ruta se va a utilizar a nivel de Tcl, llamar a esta función es una forma eficiente de crear el tipo de valor de ruta apropiado.

El valor resultante es un valor de "ruta" puro, que solo recibirá una representación de cadena UTF-8 si así lo requiere algún código Tcl.

Tcl_FSGetNativePath es para uso de los sistemas de archivos nativos Win/Unix, de modo que puedan recuperar fácilmente la representación nativa (char* o TCHAR*) de una ruta. Esta función es un envoltorio de conveniencia alrededor de Tcl_FSGetInternalRep. Podría ser deseable en el futuro tener representaciones nativas no basadas en cadenas (por ejemplo, en macOS, una representación que utilice una estructura FSRef de fileSpec probablemente sería más eficiente). En Windows, una representación Unicode completa permitiría rutas de longitud ilimitada. Actualmente, la representación es simplemente una cadena de caracteres que puede contener la ruta relativa o una ruta completa, absoluta y normalizada en la codificación nativa (condiciones complejas dictan cuál de estas se proporcionará, por lo que no se puede confiar en ninguna, a menos que se sepa que la ruta es absoluta). Si necesita una ruta nativa que deba ser absoluta, debería solicitar la versión nativa de una ruta normalizada. Si por alguna razón se necesita una versión no absoluta y no normalizada de la ruta, esta debe construirse por separado (por ejemplo, usando Tcl_FSGetTranslatedPath).

La representación nativa se almacena en caché para que las llamadas repetidas a esta función no requieran conversiones adicionales. El valor de retorno es propiedad de Tcl y tiene una vida útil equivalente a la del pathPtr pasado (a menos que sea una ruta relativa, en cuyo caso la representación nativa puede liberarse en cualquier momento en que cambie el CWD).

Tcl_FSFileSystemInfo devuelve una lista de dos elementos. El primer elemento es el nombre del sistema de archivos (por ejemplo, "native", "vfs", "zip", o "prowrap", quizás), y el segundo es el tipo particular de la ruta dada dentro de ese sistema de archivos (que depende del sistema de archivos). El segundo elemento puede estar vacío si el sistema de archivos no proporciona una categorización adicional de archivos.

Se devuelve un valor de lista válido, a menos que el valor de la ruta no sea reconocido, en cuyo caso se devolverá NULL.

Tcl_FSGetFileSystemForPath devuelve un puntero al Tcl_Filesystem que acepta esta ruta como válida.

Si ningún sistema de archivos acepta la ruta, se devuelve NULL.

Tcl_FSGetPathType determina si la ruta dada es relativa al directorio actual, relativa al volumen actual o absoluta.

Devuelve uno de TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE o TCL_PATH_VOLUME_RELATIVE.

LA API DEL SISTEMA DE ARCHIVOS VIRTUAL

Un sistema de archivos proporciona una estructura Tcl_Filesystem que contiene punteros a funciones que implementan las diversas operaciones en un sistema de archivos; estas operaciones se invocan según sea necesario por la capa genérica, lo que generalmente ocurre a través de las funciones listadas anteriormente.

Las estructuras Tcl_Filesystem se manipulan utilizando los siguientes métodos.

Tcl_FSRegister toma un puntero a una estructura de sistema de archivos y un dato opcional para asociar con ese sistema de archivos. Al llamar a esta función, Tcl adjuntará el sistema de archivos a la lista de sistemas de archivos conocidos, y se volverá completamente funcional de inmediato. Tcl no comprueba si el mismo sistema de archivos está registrado varias veces (y en general eso no es algo bueno de hacer). Se devolverá TCL_OK.

Tcl_FSUnregister elimina la estructura del sistema de archivos dada de la lista de sistemas de archivos conocidos, si se conoce, y devuelve TCL_OK. Si el sistema de archivos no está registrado actualmente, se devuelve TCL_ERROR.

Tcl_FSData devolverá el clientData asociado con el sistema de archivos dado, si ese sistema de archivos está registrado. De lo contrario, devolverá NULL.

Tcl_FSMountsChanged se utiliza para informar al núcleo de Tcl que el conjunto de puntos de montaje para el sistema de archivos dado (ya registrado) ha cambiado, y que, por lo tanto, las representaciones de archivos almacenadas en caché pueden ya no ser correctas.

Las muchas funciones de esta estructura se dividen en tres categorías: funciones de infraestructura (casi todas las cuales deben implementarse), funciones operacionales (que deben implementarse si se proporciona un sistema de archivos completo) y funciones de eficiencia (que solo necesitan implementarse si se pueden hacer de manera eficiente, o si tienen efectos secundarios que son requeridos por el sistema de archivos; Tcl tiene emulaciones menos eficientes a las que puede recurrir). Es importante tener en cuenta que, en la versión actual de Tcl, la mayoría de estos recursos de reserva solo se utilizan para manejar comandos iniciados en Tcl, no en C. Lo que esto significa es que, si se emite un comando file rename en Tcl, y el o los sistemas de archivos relevantes no implementan su Tcl_FSRenameFileProc, el núcleo de Tcl recurrirá a una combinación de otras funciones del sistema de archivos (usará Tcl_FSCopyFileProc seguido de Tcl_FSDeleteFileProc, y si Tcl_FSCopyFileProc no está implementado, hay un recurso de reserva adicional). Sin embargo, si se emite un comando Tcl_FSRenameFileProc a nivel de C, no se producen tales recursos de reserva. Esto es cierto excepto para las últimas cuatro entradas en la tabla del sistema de archivos (lstat, load, getcwd y chdir) para las cuales sí ocurren recursos de reserva a nivel de C.

Cualquier función que tome nombres de ruta en forma de Tcl_Obj toma esos nombres en forma UTF-8. La API de infraestructura del sistema de archivos está diseñada para admitir la conversión eficiente y en caché de estas rutas UTF-8 a otras representaciones nativas.

INFRAESTRUCTURA DEL SISTEMA DE ARCHIVOS

Estos campos contienen información básica sobre la estructura del sistema de archivos y las direcciones de las funciones que se utilizan para asociar un sistema de archivos particular con una ruta de archivo, y para manejar internamente las representaciones de rutas, por ejemplo, copiar y liberar dichas representaciones.

TYPENAME

El campo typeName contiene una cadena terminada en nulo que identifica el tipo del sistema de archivos implementado, por ejemplo, “native”, “zip” o “vfs”.

STRUCTURE_LENGTH

El campo structureLength se implementa generalmente como sizeof(Tcl_Filesystem), y está ahí para permitir una mayor compatibilidad binaria hacia atrás si el tamaño de la estructura cambia en una futura versión de Tcl.

VERSION

El campo version debe establecerse en TCL_FILESYSTEM_VERSION_1.

PATHINFILESYSTEMPROC

El campo pathInFilesystemProc contiene la dirección de una función que se llama para determinar si un valor de ruta dado pertenece o no a este sistema de archivos. Tcl solo llamará al resto de las funciones del sistema de archivos con una ruta para la cual esta función haya devuelto TCL_OK. Si la ruta no pertenece, se debe devolver -1 (el comportamiento de Tcl para cualquier otro valor de retorno no está definido). Si se devuelve TCL_OK, el parámetro de salida opcional clientDataPtr se puede usar para devolver una representación interna (específica del sistema de archivos) de la ruta, que se almacenará en caché dentro del valor de la ruta y podrá ser recuperada eficientemente por las otras funciones del sistema de archivos. Tcl almacenará simultáneamente en caché el hecho de que esta ruta pertenece a este sistema de archivos. Dichas cachés se invalidan cuando se agregan o eliminan estructuras del sistema de archivos de la lista interna de Tcl de sistemas de archivos conocidos.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

DUPINTERNALREPPROC

Esta función crea una copia de la representación interna de una ruta y se llama cuando Tcl necesita duplicar un valor de ruta. Si es NULL, Tcl simplemente no copiará la representación interna, que puede necesitar ser regenerada más tarde.

typedef ClientData Tcl_FSDupInternalRepProc(
        ClientData clientData);

FREEINTERNALREPPROC

Libera la representación interna. Esto debe implementarse si las representaciones internas necesitan ser liberadas (es decir, si se asigna memoria cuando se genera una representación interna), pero de lo contrario puede ser NULL.

typedef void Tcl_FSFreeInternalRepProc(
        ClientData clientData);

INTERNALTONORMALIZEDPROC

Función para convertir la representación interna a una ruta normalizada. Solo se requiere si el sistema de archivos crea valores de ruta puros sin representación de cadena/ruta. El valor de retorno es un valor de Tcl cuya representación de cadena es la ruta normalizada.

typedef Tcl_Obj *Tcl_FSInternalToNormalizedProc(
        ClientData clientData);

CREATEINTERNALREPPROC

Función para tomar un valor de ruta y calcular una representación interna para él, y almacenar esa representación nativa en el valor. Puede ser NULL si las rutas no tienen representación interna, o si el Tcl_FSPathInFilesystemProc para este sistema de archivos siempre crea inmediatamente una representación interna para las rutas que acepta.

typedef ClientData Tcl_FSCreateInternalRepProc(
        Tcl_Obj *pathPtr);

NORMALIZEPATHPROC

Función para normalizar una ruta. Debe implementarse para todos los sistemas de archivos que pueden tener múltiples representaciones de cadena para el mismo valor de ruta. En Tcl, cada "ruta" debe tener una única representación de cadena "normalizada". Dependiendo del sistema de archivos, puede haber más de una representación de cadena no normalizada que se refiera a esa ruta (por ejemplo, una ruta relativa, una ruta con mayúsculas y minúsculas diferentes si el sistema de archivos no distingue entre mayúsculas y minúsculas, una ruta que contenga una referencia a un directorio personal como "~", una ruta que contenga enlaces simbólicos, etc.). Si el último componente de la ruta es un enlace simbólico, no debe convertirse en el valor al que apunta (pero su mayúscula u otros aspectos deben hacerse únicos). Todos los demás componentes de la ruta deben convertirse de enlaces simbólicos. Esta única excepción es necesaria para concordar con la semántica de Tcl con file delete, file rename, file copy al operar sobre enlaces simbólicos. Esta función puede ser llamada con nextCheckpoint ya sea al principio de la ruta (es decir, cero), al final de la ruta, o en cualquier separador de archivos intermedio en la ruta. Nunca apuntará a ninguna otra posición arbitraria en la ruta. En el último de los tres casos válidos, la implementación puede asumir que la ruta hasta e incluyendo el separador de archivos se conoce y se ha normalizado.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

OPERACIONES DEL SISTEMA DE ARCHIVOS

Los campos de esta sección de la estructura contienen las direcciones de las funciones que se llaman para realizar las operaciones básicas del sistema de archivos. Un sistema de archivos que se espera que se utilice con el conjunto completo de comandos estándar de Tcl debe implementar todas estas. Si algunas de ellas no se implementan, ciertos comandos de Tcl pueden fallar al operar en rutas dentro de ese sistema de archivos. Sin embargo, en algunos casos esto puede ser deseable (por ejemplo, un sistema de archivos de solo lectura no debe implementar las últimas cuatro funciones, y un sistema de archivos que no admite enlaces simbólicos no necesita implementar la función readlink, etc. El núcleo de Tcl espera que los sistemas de archivos se comporten de esta manera).

FILESYSTEMPATHTYPEPROC

Función para determinar el tipo de una ruta en este sistema de archivos. Puede ser NULL, en cuyo caso no habrá información de tipo disponible para los usuarios del sistema de archivos. El "tipo" se usa solo con fines informativos y debe devolverse como la representación de cadena del Tcl_Obj que se devuelve. Un valor de retorno típico podría ser “networked”, “zip” o “ftp”. El objeto Tcl resultante es propiedad del sistema de archivos y, por lo tanto, Tcl incrementará el recuento de referencias de ese valor si desea retener una referencia a él.

typedef Tcl_Obj *Tcl_FSFilesystemPathTypeProc(
        Tcl_Obj *pathPtr);

FILESYSTEMSEPARATORPROC

Función para devolver el(los) carácter(es) separador(es) para este sistema de archivos. Esto solo necesita implementarse si el sistema de archivos desea usar un separador diferente al de la cadena estándar “/”. Entre otros usos, se devuelve mediante el comando file separator. El valor de retorno debe ser un valor con recuento de referencias cero.

typedef Tcl_Obj *Tcl_FSFilesystemSeparatorProc(
        Tcl_Obj *pathPtr);

STATPROC

Función para procesar una llamada Tcl_FSStat. Debe implementarse para cualquier sistema de archivos razonable, ya que muchos comandos a nivel de Tcl dependen crucialmente de él (por ejemplo, file atime, file isdirectory, file size, glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

El Tcl_FSStatProc llena la estructura stat statPtr con información sobre el archivo especificado. No necesita ningún derecho de acceso al archivo para obtener esta información, pero necesita derechos de búsqueda a todos los directorios mencionados en la ruta que conduce al archivo. La estructura stat incluye información sobre el dispositivo, inodo (siempre 0 en Windows), modo de privilegios, nlink (siempre 1 en Windows), id de usuario (siempre 0 en Windows), id de grupo (siempre 0 en Windows), rdev (igual que el dispositivo en Windows), tamaño, tiempo del último acceso, tiempo de la última modificación y tiempo del último cambio de metadatos.

Si el archivo representado por pathPtr existe, el Tcl_FSStatProc devuelve 0 y la estructura stat se llena con datos. De lo contrario, se devuelve -1 y no se proporciona información de stat.

ACCESSPROC

Función para procesar una llamada Tcl_FSAccess. Debe implementarse para cualquier sistema de archivos razonable, ya que muchos comandos a nivel de Tcl dependen crucialmente de él (por ejemplo, file exists, file readable).

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

El Tcl_FSAccessProc verifica si se permitiría al proceso leer, escribir o probar la existencia del archivo (u otro objeto del sistema de archivos) cuyo nombre está en pathPtr. Si la ruta se refiere a un enlace simbólico, entonces se deben probar los permisos del archivo al que hace referencia este enlace simbólico.

En caso de éxito (todos los permisos solicitados concedidos), se devuelve cero. En caso de error (al menos un bit en el modo solicitó un permiso que se deniega, o ocurrió algún otro error), se devuelve -1.

OPENFILECHANNELPROC

Función para procesar una llamada Tcl_FSOpenFileChannel. Debe implementarse para cualquier sistema de archivos que admita la apertura de canales de archivos (por ejemplo, para leer o escribir en archivos). Los comandos de Tcl como open, puts y gets dependen de esta función.

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        const char *mode,
        int permissions);

Esta función abre un canal para el archivo especificado por pathPtr en el modo especificado por mode. El argumento permissions se utiliza para especificar los permisos del archivo cuando se crea un archivo nuevo (por ejemplo, "w" o "a" en el modo).

En caso de éxito, se devuelve un descriptor de canal Tcl válido. En caso de error, se devuelve NULL y se establece un mensaje de error en el intérprete interp.

READFILECHANNELPROC

Función para procesar una llamada Tcl_FSReadFileChannel. Solo es necesario implementarla si la función openFileChannelProc puede devolver canales que permiten la lectura. Por ejemplo, el comando gets depende de esto.

typedef int Tcl_FSReadFileChannelProc(
        ClientData instanceData,
        char *buf,
        int bufSize,
        Tcl_Obj **errorPtr);

WRITEFILECHANNELPROC

Función para procesar una llamada Tcl_FSWriteFileChannel. Solo es necesario implementarla si la función openFileChannelProc puede devolver canales que permiten la escritura. Por ejemplo, los comandos puts y puts -nonewline dependen de esto.

typedef int Tcl_FSWriteFileChannelProc(
        ClientData instanceData,
        const char *buf,
        int bufSize,
        Tcl_Obj **errorPtr);

Si la función es NULL, entonces los canales devueltos por openFileChannelProc no tendrán un nombre asociado y las operaciones que requieran el nombre fallarán.

typedef Tcl_Obj *Tcl_FSGetFileChannelNameProc(
        ClientData instanceData);

typedef int Tcl_FSCloseFileChannelProc(
        ClientData instanceData);

COPYPROC

Función para copiar un archivo o directorio de una ubicación a otra. Esto es necesario para comandos como file copy.

typedef int Tcl_FSCopyProc(

Copia el archivo o directorio en sourcePtr a la ubicación en destPtr. La bandera copyFlags se usa para controlar el comportamiento de la copia (por ejemplo, si se debe sobrescribir un archivo existente). Devuelve 0 si tiene éxito, o -1 si falla.

LSTATPROC

Función para procesar una llamada Tcl_FSLstat. Esto es similar a statProc, pero si la ruta se refiere a un enlace simbólico, debe devolver información sobre el enlace simbólico en sí, en lugar de la información sobre el archivo al que apunta el enlace.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

Si la ruta existe, devuelve 0 y rellena statPtr con información. De lo contrario, devuelve -1.

LINKPROC

typedef int Tcl_FSLinkProc(

FILESYSTEM INTERFACE

Filesystem code lives in a separate DLL or library from the Tcl core. The filesystem code is responsible for implementing a set of procedures that Tcl calls to perform operations on files. The Tcl core uses these procedures to handle all filesystem operations. This allows Tcl to support multiple filesystem types, such as native filesystems, virtual filesystems, and remote filesystems. A filesystem is registered with Tcl by calling Tcl_FSCreate.

The following are the procedures that Tcl may call on a filesystem:

OPENFILECHANNELPROC

Función para procesar una llamada a Tcl_FSOpenFileChannel. Debe ser implementada para cualquier sistema de archivos razonable, ya que cualquier operación que requiera abrir o acceder al contenido de un archivo la utilizará (por ejemplo, open, encoding y muchos comandos de Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

La Tcl_FSOpenFileChannelProc abre un archivo especificado por pathPtr y devuelve un manejador de canal que puede ser usado para realizar entrada y salida en el archivo. Esta API está modelada después del procedimiento fopen de la biblioteca estándar de E/S de Unix. La sintaxis y el significado de todos los argumentos son similares a los proporcionados en el comando open de Tcl al abrir un archivo, donde el argumento mode es una combinación de las banderas POSIX O_RDONLY, O_WRONLY, etc. Si ocurre un error al abrir el canal, la Tcl_FSOpenFileChannelProc devuelve NULL y registra un código de error POSIX que puede ser recuperado con Tcl_GetErrno. Además, si interp no es NULL, la Tcl_FSOpenFileChannelProc deja un mensaje de error en el resultado de interp después de cualquier error.

El canal recién creado no debe ser registrado en el intérprete suministrado por una Tcl_FSOpenFileChannelProc; esa tarea le corresponde al llamador de Tcl_FSOpenFileChannel (si es necesario). Si uno de los canales estándar, stdin, stdout o stderr, fue cerrado previamente, el acto de crear el nuevo canal también lo asigna como reemplazo del canal estándar.

MATCHINDIRECTORYPROC

Función para procesar una llamada a Tcl_FSMatchInDirectory. Si no se implementa, entonces la funcionalidad de globbing y copia recursiva faltará en el sistema de archivos (y esto puede afectar a comandos como encoding names que utilizan la funcionalidad de globbing internamente).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La función debe devolver todos los archivos o directorios (u otros objetos del sistema de archivos) que coincidan con el patrón dado y que concuerden con la especificación de types proporcionada. Hay dos maneras en las que esta función puede ser llamada. Si pattern es NULL, entonces pathPtr es una especificación de ruta completa de un único archivo o directorio que debe ser verificado en cuanto a existencia y tipo correcto. De lo contrario, pathPtr es un directorio, cuyo contenido la función debe buscar archivos o directorios que tengan el tipo correcto. En cualquier caso, se puede asumir que pathPtr no es NULL ni vacío. Actualmente no está documentado si pathPtr tendrá o no un separador de archivo al final, por lo que el código debe ser flexible a ambas posibilidades.

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso de coincidencia. Los mensajes de error se colocan en interp, a menos que interp sea NULL, en cuyo caso no es necesario generar ningún mensaje de error; en un resultado TCL_OK, los resultados deben añadirse al valor dado de resultPtr (que se puede asumir que es una lista válida y no compartida de Tcl). Las coincidencias añadidas a resultPtr deben incluir cualquier prefijo de ruta dado en pathPtr (esto generalmente significa que serán especificaciones de ruta absoluta). Tenga en cuenta que si no se encuentran coincidencias, eso simplemente conduce a un resultado vacío; los errores solo se señalan para problemas reales de archivos o del sistema de archivos que puedan ocurrir durante el proceso de coincidencia.

La estructura Tcl_GlobTypeData pasada en el parámetro types contiene los siguientes campos:

typedef struct Tcl_GlobTypeData {
    /* Corresponde a bcdpfls como en 'find -t' */
    int type;
    /* Corresponde a los permisos del archivo */
    int perm;
    /* Tipo de Mac aceptable */
    Tcl_Obj *macType;
    /* Creador de Mac aceptable */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Hay dos casos específicos que es importante manejar correctamente, ambos cuando types no es NULL. Los dos casos son cuando types->types & TCL_GLOB_TYPE_DIR o types->types & TCL_GLOB_TYPE_MOUNT son verdaderos (y en particular cuando las otras banderas son falsas). En el primero de estos casos, la función debe listar los directorios contenidos. Tcl utiliza esto para implementar el globbing recursivo, por lo que es crucial que los sistemas de archivos implementen la coincidencia de directorios correctamente. En el segundo de estos casos, con TCL_GLOB_TYPE_MOUNT, el sistema de archivos debe listar los puntos de montaje que se encuentran dentro del directorio dado pathPtr (y en este caso, pathPtr no necesita estar dentro del mismo sistema de archivos, a diferencia de todos los demás casos en los que se llama a esta función). El soporte para esto es crucial si Tcl va a tener transiciones fluidas entre un sistema de archivos y otro.

UTIMEPROC

Función para procesar una llamada a Tcl_FSUtime. Requerida para permitir el establecimiento (no la lectura) de tiempos con file mtime, file atime y la implementación open-r/open-w/fcopy de file copy.

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

Los tiempos de acceso y modificación del archivo especificado por pathPtr deben cambiarse a los valores dados en la estructura tval.

El valor de retorno debe ser 0 en caso de éxito y -1 en caso de error, al igual que con la función del sistema utime.

LINKPROC

Función para procesar una llamada a Tcl_FSLink. Solo debe ser implementada si el sistema de archivos soporta enlaces, y de lo contrario puede ser NULL.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

Si toPtr es NULL, se le está pidiendo a la función que lea el contenido de un enlace. El resultado es un Tcl_Obj que especifica el contenido del enlace dado por linkNamePtr, o NULL si el enlace no pudo ser leído. El resultado es propiedad del llamador (y por lo tanto su contador de referencias debe ser incrementado antes de ser devuelto). Cualquier llamador debe llamar a Tcl_DecrRefCount sobre este resultado cuando ya no sea necesario. Si toPtr no es NULL, la función debe intentar crear un enlace. El resultado en este caso debe ser toPtr si el enlace tuvo éxito y NULL en caso contrario. En este caso, el resultado no es propiedad del llamador (es decir, no se necesitan manipulaciones de contador de referencias en ninguno de los extremos). Consulte la documentación de Tcl_FSLink para la interpretación correcta de las banderas de linkAction.

LISTVOLUMESPROC

Función para listar cualquier volumen del sistema de archivos añadido por este sistema de archivos. Solo debe ser implementada si el sistema de archivos añade volúmenes al principio del sistema de archivos, para que puedan ser devueltos por file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

El resultado debe ser una lista de volúmenes añadidos por este sistema de archivos, o NULL (o una lista vacía) si no se proporcionan volúmenes. El valor del resultado se considera propiedad del sistema de archivos (no del núcleo de Tcl), pero se le debe dar un contador de referencias para Tcl. Tcl utilizará el contenido de la lista y luego disminuirá ese contador de referencias. Esto permite a los sistemas de archivos elegir si realmente quieren retener una lista "global" de volúmenes o no (si no, generan la lista sobre la marcha y se la pasan a Tcl con un contador de referencias de 1 y luego se olvidan de la lista; si sí, simplemente incrementan el contador de referencias de su lista global y se la pasan a Tcl, que copiará el contenido y luego disminuirá el contador de vuelta a donde estaba).

Por lo tanto, Tcl considera que los valores de retorno de este procedimiento son de solo lectura.

FILEATTRSTRINGSPROC

Función para listar todas las cadenas de atributos que son válidas para este sistema de archivos. Si no se implementa, el sistema de archivos no soportará el comando file attributes. Esto permite adjuntar información adicional arbitraria a los archivos en el sistema de archivos. Si no se implementa, no es necesario implementar los métodos get y set.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

La función llamada puede devolver un array de cadenas o puede devolver NULL y colocar una lista de Tcl en el objPtrRef dado. Tcl tomará esa lista e incrementará primero su contador de referencias antes de usarla. Al finalizar ese uso, Tcl disminuirá su contador de referencias. Por lo tanto, si la lista debe ser liberada por Tcl cuando termine, debe tener un contador de referencias de cero, y si la lista no debe ser liberada, el sistema de archivos debe asegurarse de devolver un valor con un contador de referencias de al menos uno.

FILEATTRSGETPROC

Función para procesar una llamada a Tcl_FSFileAttrsGet, utilizada por file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

Devuelve un código de retorno estándar de Tcl. El valor del atributo recuperado, que corresponde al elemento de índice index en la lista devuelta por Tcl_FSFileAttrStringsProc, es un Tcl_Obj colocado en objPtrRef (si se devolvió TCL_OK) y es probable que tenga un contador de referencias de cero. En cualquier caso, debemos almacenarlo en algún lugar (por ejemplo, el resultado de Tcl), o incrementar/decrementar su contador de referencias para asegurar que sea liberado correctamente.

FILEATTRSSETPROC

TCL_FILESYSTEM_FUNCTIONS

As of Tcl 8.4, Tcl has the ability to incorporate foreign file systems into its own. These are typically implemented as loadable modules, but they may also be compiled directly into an application. The details of how to implement a foreign filesystem are beyond the scope of this document; rather, this document describes the functions that Tcl provides for manipulating filesystems and the functions that a foreign filesystem must provide for Tcl to use it.

These functions are encapsulated in the Tcl_Filesystem structure. See the Tcl_CreateFilesystem documentation for a description of this structure. The structure and the functions it refers to are declared in the tcl.h header file.

The filesystem functions are broken into two groups: those that Tcl uses for its own internal operations (like file access, I/O, etc.), and those that Tcl uses to implement Tcl commands like file, load, and open. These functions are described below.

ACCESSPROC

Function to process a Tcl_FSAccess call. If this function is NULL, then Tcl will fall back to using the filesystem's statProc and checking the result. Therefore, this function need only be implemented if the filesystem can check access permissions more efficiently than a stat call.

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

The return value is a standard Tcl result indicating whether an error occurred in the process. The mode argument is the bitwise OR of the POSIX access bits: R_OK, W_OK, X_OK, F_OK. If the file exists and the requested access mode is permitted, the function should return TCL_OK. Otherwise, it should return TCL_ERROR and leave an error message in the interpreter's result.

CHMODPROC

Function to process a Tcl_FSChmod call. This function must be implemented unless the filesystem is read-only.

typedef int Tcl_FSChmodProc(
        Tcl_Obj *pathPtr,
        int mode);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, the mode of the file specified by pathPtr is changed to mode.

CHOWNPROC

Function to process a Tcl_FSChown call. This function must be implemented unless the filesystem is read-only.

typedef int Tcl_FSChownProc(
        Tcl_Obj *pathPtr,
        uid_t owner,
        gid_t group);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, the owner and group of the file specified by pathPtr are changed to owner and group respectively. If owner or group is specified as -1, the corresponding change is not made.

STATPROC

Function to process a Tcl_FSStat call. This function must be implemented unless the filesystem is read-only.

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, the statPtr argument is filled with information about the file specified by pathPtr.

LISTFILESPRROC

Function to process a Tcl_FSListFiles call. This function must be implemented unless the filesystem is read-only.

typedef int Tcl_FSListFilesProc(
        Tcl_Obj *pathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, the list of files in the directory specified by pathPtr should be returned as the result for the interpreter.

CREATEDIRECTORYPROC

Function to process a Tcl_FSCreateDirectory call. Should be implemented unless the FS is read-only.

typedef int Tcl_FSCreateDirectoryProc(
        Tcl_Obj *pathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, a new directory should have been added to the filesystem in the location specified by pathPtr.

REMOVEDIRECTORYPROC

Function to process a Tcl_FSRemoveDirectory call. Should be implemented unless the FS is read-only.

typedef int Tcl_FSRemoveDirectoryProc(
        Tcl_Obj *pathPtr,
        int recursive,
        Tcl_Obj **errorPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, the directory specified by pathPtr should have been removed from the filesystem. If the recursive flag is given, then a non-empty directory should be deleted without error. If this flag is not given, then and the directory is non-empty a POSIX “EEXIST” error should be signaled. If an error does occur, the name of the file or directory which caused the error should be placed in errorPtr.

DELETEFILEPROC

Function to process a Tcl_FSDeleteFile call. Should be implemented unless the FS is read-only.

typedef int Tcl_FSDeleteFileProc(
        Tcl_Obj *pathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, the file specified by pathPtr should have been removed from the filesystem. Note that, if the filesystem supports symbolic links, Tcl will always call this function and not Tcl_FSRemoveDirectoryProc when needed to delete them (even if they are symbolic links to directories).

FILESYSTEM EFFICIENCY

These functions need not be implemented for a particular filesystem because the core has a fallback implementation available. See each individual description for the consequences of leaving the field NULL.

LSTATPROC

Function to process a Tcl_FSLstat call. If not implemented, Tcl will attempt to use the statProc defined above instead. Therefore it need only be implemented if a filesystem can differentiate between stat and lstat calls.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

The behavior of this function is very similar to that of the Tcl_FSStatProc defined above, except that if it is applied to a symbolic link, it returns information about the link, not about the target file.

COPYFILEPROC

Function to process a Tcl_FSCopyFile call. If not implemented Tcl will fall back on open-r, open-w and fcopy as a copying mechanism. Therefore it need only be implemented if the filesystem can perform that action more efficiently.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the copying process. Note that, destPathPtr is the name of the file which should become the copy of srcPathPtr. It is never the name of a directory into which srcPathPtr could be copied (i.e. the function is much simpler than the Tcl level file copy subcommand). Note that, if the filesystem supports symbolic links, Tcl will always call this function and not copyDirectoryProc when needed to copy them (even if they are symbolic links to directories). Finally, if the filesystem determines it cannot support the file copy action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

RENAMEFILEPROC

Function to process a Tcl_FSRenameFile call. If not implemented, Tcl will fall back on a copy and delete mechanism. Therefore it need only be implemented if the filesystem can perform that action more efficiently.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the renaming process. If the filesystem determines it cannot support the file rename action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

COPYDIRECTORYPROC

Function to process a Tcl_FSCopyDirectory call. If not implemented, Tcl will fall back on a recursive file mkdir, file copy mechanism. Therefore it need only be implemented if the filesystem can perform that action more efficiently.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

The return value is a standard Tcl result indicating whether an error occurred in the copying process. If an error does occur, the name of the file or directory which caused the error should be placed in errorPtr. Note that, destPathPtr is the name of the directory-name which should become the mirror-image of srcPathPtr. It is not the name of a directory into which srcPathPtr should be copied (i.e. the function is much simpler than the Tcl level file copy subcommand). Finally, if the filesystem determines it cannot support the directory copy action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

LOADFILEPROC

Function to process a Tcl_FSLoadFile call. If not implemented, Tcl will fall back on a copy to native-temp followed by a Tcl_FSLoadFile on that temporary copy. Therefore it need only be implemented if the filesystem can load code directly, or it can be implemented simply to return TCL_ERROR to disable load functionality in this filesystem entirely.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Returns a standard Tcl completion code. If an error occurs, an error message is left in the interp's result. The function dynamically loads a binary code file into memory. On a successful load, the handlePtr should be filled with a token for the dynamically loaded file, and the unloadProcPtr should be filled in with the address of a procedure. The unload procedure will be called with the given Tcl_LoadHandle as its only parameter when Tcl needs to unload the file. For example, for the native filesystem, the Tcl_LoadHandle returned is currently a token which can be used in the private TclpFindSymbol to access functions in the new code. Each filesystem is free to define the Tcl_LoadHandle as it requires. Finally, if the filesystem determines it cannot support the file load action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

UNLOADFILEPROC

Function to unload a previously successfully loaded file. If load was implemented, then this should also be implemented, if there is any cleanup action required.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

Function to process a Tcl_FSGetCwd call. Most filesystems need not implement this. It will usually only be called once, if getcwd is called before chdir. May be NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

If the filesystem supports a native notion of a current working directory (which might perhaps change independent of Tcl), this function should return that cwd as the result, or NULL if the current directory could not be determined (e.g. the user does not have appropriate permissions on the cwd directory). If NULL is returned, an error message is left in the interp's result.

CHDIRPROC

Function to process a Tcl_FSChdir call. If filesystems do not implement this, it will be emulated by a series of directory access checks. Otherwise, virtual filesystems which do implement it need only respond with a positive return result if the pathPtr is a valid, accessible directory in their filesystem. They need not remember the result, since that will be automatically remembered for use by Tcl_FSGetCwd. Real filesystems should carry out the correct action (i.e. call the correct system chdir API).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

The Tcl_FSChdirProc changes the applications current working directory to the value specified in pathPtr. The function returns -1 on error or 0 on success.

FUNCIONES DEL SISTEMA DE ARCHIVOS TCL

A partir de Tcl 8.4, Tcl tiene la capacidad de incorporar sistemas de archivos externos en los suyos. Estos se implementan típicamente como módulos cargables, pero también pueden compilarse directamente en una aplicación. Los detalles de cómo implementar un sistema de archivos externo están fuera del alcance de este documento; más bien, este documento describe las funciones que Tcl proporciona para manipular sistemas de archivos y las funciones que un sistema de archivos externo debe proporcionar para que Tcl lo utilice.

Estas funciones se encapsulan en la estructura Tcl_Filesystem. Consulte la documentación de Tcl_CreateFilesystem para obtener una descripción de esta estructura. La estructura y las funciones a las que hace referencia se declaran en el archivo de encabezado tcl.h.

Las funciones del sistema de archivos se dividen en dos grupos: aquellas que Tcl utiliza para sus propias operaciones internas (como acceso a archivos, E/S, etc.) y aquellas que Tcl utiliza para implementar comandos de Tcl como file, load y open. Estas funciones se describen a continuación.

ACCESSPROC

Función para procesar una llamada Tcl_FSAccess. Si esta función es NULL, Tcl recurrirá a utilizar el statProc del sistema de archivos y verificará el resultado. Por lo tanto, esta función solo necesita implementarse si el sistema de archivos puede verificar los permisos de acceso de manera más eficiente que una llamada stat.

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

El valor de retorno es un resultado estándar de Tcl que indica si se produjo un error en el proceso. El argumento mode es el OR a nivel de bits de los bits de acceso POSIX: R_OK, W_OK, X_OK, F_OK. Si el archivo existe y el modo de acceso solicitado está permitido, la función debe devolver TCL_OK. De lo contrario, debe devolver TCL_ERROR y dejar un mensaje de error en el resultado del intérprete.

CHMODPROC

Función para procesar una llamada Tcl_FSChmod. Esta función debe implementarse a menos que el sistema de archivos sea de solo lectura.

typedef int Tcl_FSChmodProc(
        Tcl_Obj *pathPtr,
        int mode);

El valor de retorno es un resultado estándar de Tcl que indica si se produjo un error en el proceso. Si tiene éxito, el modo del archivo especificado por pathPtr se cambia a mode.

CHOWNPROC

Función para procesar una llamada Tcl_FSChown. Esta función debe implementarse a menos que el sistema de archivos sea de solo lectura.

typedef int Tcl_FSChownProc(
        Tcl_Obj *pathPtr,
        uid_t owner,
        gid_t group);

El valor de retorno es un resultado estándar de Tcl que indica si se produjo un error en el proceso. Si tiene éxito, el propietario y el grupo del archivo especificado por pathPtr se cambian a owner y group respectivamente. Si el propietario o el grupo se especifican como -1, no se realiza el cambio correspondiente.

STATPROC

Función para procesar una llamada Tcl_FSStat. Esta función debe implementarse a menos que el sistema de archivos sea de solo lectura.

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

El valor de retorno es un resultado estándar de Tcl que indica si se produjo un error en el proceso. Si tiene éxito, el argumento statPtr se completa con información sobre el archivo especificado por pathPtr.

LISTFILESPRROC

Función para procesar una llamada Tcl_FSListFiles. Esta función debe implementarse a menos que el sistema de archivos sea de solo lectura.

typedef int Tcl_FSListFilesProc(
        Tcl_Obj *pathPtr);

El valor de retorno es un resultado estándar de Tcl que indica si se produjo un error en el proceso. Si tiene éxito, la lista de archivos en el directorio especificado por pathPtr debe devolverse como el resultado para el intérprete.

CREATEDIRECTORYPROC

Función para procesar una llamada Tcl_FSCreateDirectory. Debe implementarse a menos que el FS sea de solo lectura.

typedef int Tcl_FSCreateDirectoryProc(
        Tcl_Obj *pathPtr);

El valor de retorno es un resultado estándar de Tcl que indica si se produjo un error en el proceso. Si tiene éxito, se debe haber agregado un nuevo directorio al sistema de archivos en la ubicación especificada por pathPtr.

REMOVEDIRECTORYPROC

Función para procesar una llamada Tcl_FSRemoveDirectory. Debe implementarse a menos que el FS sea de solo lectura.

typedef int Tcl_FSRemoveDirectoryProc(
        Tcl_Obj *pathPtr,
        int recursive,
        Tcl_Obj **errorPtr);

El valor de retorno es un resultado estándar de Tcl que indica si se produjo un error en el proceso. Si tiene éxito, el directorio especificado por pathPtr debe haberse eliminado del sistema de archivos. Si se da la bandera recursive, entonces se debe eliminar un directorio no vacío sin error. Si no se da esta bandera, y el directorio no está vacío, se debe señalar un error POSIX "EEXIST". Si ocurre un error, el nombre del archivo o directorio que causó el error debe colocarse en errorPtr.

DELETEFILEPROC

Función para procesar una llamada Tcl_FSDeleteFile. Debe implementarse a menos que el FS sea de solo lectura.

typedef int Tcl_FSDeleteFileProc(
        Tcl_Obj *pathPtr);

El valor de retorno es un resultado estándar de Tcl que indica si se produjo un error en el proceso. Si tiene éxito, el archivo especificado por pathPtr debe haberse eliminado del sistema de archivos. Tenga en cuenta que, si el sistema de archivos admite enlaces simbólicos, Tcl siempre llamará a esta función y no a Tcl_FSRemoveDirectoryProc cuando sea necesario eliminarlos (incluso si son enlaces simbólicos a directorios).

EFICIENCIA DEL SISTEMA DE ARCHIVOS

Estas funciones no necesitan ser implementadas para un sistema de archivos en particular porque el núcleo tiene una implementación de respaldo disponible. Consulte la descripción individual de cada una para conocer las consecuencias de dejar el campo en NULL.

LSTATPROC

Función para procesar una llamada Tcl_FSLstat. Si no se implementa, Tcl intentará utilizar el statProc definido anteriormente en su lugar. Por lo tanto, solo necesita implementarse si un sistema de archivos puede diferenciar entre las llamadas stat y lstat.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

El comportamiento de esta función es muy similar al de Tcl_FSStatProc definido anteriormente, excepto que si se aplica a un enlace simbólico, devuelve información sobre el enlace, no sobre el archivo destino.

COPYFILEPROC

Función para procesar una llamada Tcl_FSCopyFile. Si no se implementa, Tcl recurrirá a open-r, open-w y fcopy como mecanismo de copia. Por lo tanto, solo necesita implementarse si el sistema de archivos puede realizar esa acción de manera más eficiente.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

El valor de retorno es un resultado estándar de Tcl que indica si se produjo un error en el proceso de copia. Tenga en cuenta que destPathPtr es el nombre del archivo que se convertirá en la copia de srcPathPtr. Nunca es el nombre de un directorio en el que srcPathPtr podría copiarse (es decir, la función es mucho más simple que el subcomando file copy a nivel de Tcl). Tenga en cuenta que, si el sistema de archivos admite enlaces simbólicos, Tcl siempre llamará a esta función y no a copyDirectoryProc cuando sea necesario copiarlos (incluso si son enlaces simbólicos a directorios). Finalmente, si el sistema de archivos determina que no puede admitir la acción file copy, llamar a Tcl_SetErrno(EXDEV) y devolver un resultado que no sea TCL_OK le indicará a Tcl que utilice sus mecanismos de respaldo estándar.

RENAMEFILEPROC

Función para procesar una llamada Tcl_FSRenameFile. Si no se implementa, Tcl recurrirá a un mecanismo de copia y eliminación. Por lo tanto, solo necesita implementarse si el sistema de archivos puede realizar esa acción de manera más eficiente.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

El valor de retorno es un resultado estándar de Tcl que indica si se produjo un error en el proceso de renombrado. Si el sistema de archivos determina que no puede admitir la acción file rename, llamar a Tcl_SetErrno(EXDEV) y devolver un resultado que no sea TCL_OK le indicará a Tcl que utilice sus mecanismos de respaldo estándar.

COPYDIRECTORYPROC

Función para procesar una llamada Tcl_FSCopyDirectory. Si no se implementa, Tcl recurrirá a un mecanismo recursivo de file mkdir, file copy. Por lo tanto, solo necesita implementarse si el sistema de archivos puede realizar esa acción de manera más eficiente.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

El valor de retorno es un resultado estándar de Tcl que indica si se produjo un error en el proceso de copia. Si ocurre un error, el nombre del archivo o directorio que causó el error debe colocarse en errorPtr. Tenga en cuenta que destPathPtr es el nombre del directorio que se convertirá en la imagen especular de srcPathPtr. No es el nombre de un directorio en el que srcPathPtr podría copiarse (es decir, la función es mucho más simple que el subcomando file copy a nivel de Tcl). Finalmente, si el sistema de archivos determina que no puede admitir la acción de copia de directorios, llamar a Tcl_SetErrno(EXDEV) y devolver un resultado que no sea TCL_OK le indicará a Tcl que utilice sus mecanismos de respaldo estándar.

LOADFILEPROC

Función para procesar una llamada Tcl_FSLoadFile. Si no se implementa, Tcl recurrirá a una copia a un archivo temporal nativo seguida de un Tcl_FSLoadFile en esa copia temporal. Por lo tanto, solo necesita implementarse si el sistema de archivos puede cargar código directamente, o puede implementarse simplemente para devolver TCL_ERROR para deshabilitar completamente la funcionalidad de carga en este sistema de archivos.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Devuelve un código de finalización estándar de Tcl. Si ocurre un error, se deja un mensaje de error en el resultado del interp. La función carga dinámicamente un archivo de código binario en memoria. En una carga exitosa, handlePtr se completará con un token para el archivo cargado dinámicamente, y unloadProcPtr se completará con la dirección de un procedimiento. El procedimiento de descarga se llamará con Tcl_LoadHandle dado como su único parámetro cuando Tcl necesite descargar el archivo. Por ejemplo, para el sistema de archivos nativo, el Tcl_LoadHandle devuelto es actualmente un token que se puede utilizar en el TclpFindSymbol privado para acceder a funciones del nuevo código. Cada sistema de archivos es libre de definir Tcl_LoadHandle según sus necesidades. Finalmente, si el sistema de archivos determina que no puede admitir la acción de carga de archivos, llamar a Tcl_SetErrno(EXDEV) y devolver un resultado que no sea TCL_OK le indicará a Tcl que utilice sus mecanismos de respaldo estándar.

UNLOADFILEPROC

Función para descargar un archivo previamente cargado con éxito. Si se implementó la carga, entonces esto también debe implementarse, si hay alguna acción de limpieza requerida.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

Función para procesar una llamada Tcl_FSGetCwd. La mayoría de los sistemas de archivos no necesitan implementar esto. Por lo general, solo se llamará una vez, si se llama a getcwd antes de chdir. Puede ser NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

Si el sistema de archivos admite una noción nativa de un directorio de trabajo actual (que podría cambiar independientemente de Tcl), esta función debe devolver ese cwd como resultado, o NULL si no se pudo determinar el directorio actual (por ejemplo, el usuario no tiene los permisos apropiados en el directorio actual). Si se devuelve NULL, se deja un mensaje de error en el resultado del interp.

CHDIRPROC

Función para procesar una llamada Tcl_FSChdir. Si los sistemas de archivos no implementan esto, se emulará mediante una serie de verificaciones de acceso al directorio. De lo contrario, los sistemas de archivos virtuales que lo implementan solo necesitan responder con un resultado positivo si pathPtr es un directorio válido y accesible en su sistema de archivos. No necesitan recordar el resultado, ya que se recordará automáticamente para su uso por Tcl_FSGetCwd. Los sistemas de archivos reales deben realizar la acción correcta (es decir, llamar a la API correcta del sistema chdir).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

El Tcl_FSChdirProc cambia el directorio de trabajo actual de la aplicación al valor especificado en pathPtr. La función devuelve -1 en caso de error o 0 en caso de éxito.
