DESCRIPCIÓN

Hay varias razones para llamar a las funciones de la API Tcl_FS (por ejemplo, Tcl_FSAccess y Tcl_FSStat) en lugar de llamar directamente a funciones de nivel de sistema como access y stat. Primero, funcionarán multiplataforma, por lo que una extensión que las llame debería funcionar sin modificaciones tanto en Unix como en Windows. Segundo, la implementación de Windows de algunas de estas funciones corrige algunos errores en las llamadas de nivel de sistema. Tercero, estas llamadas a funciones manejan cualquier conversión de ruta de “Utf a nativo de la plataforma” que pueda ser necesaria (y pueden almacenar en caché los resultados de dichas conversiones para una mayor eficiencia en llamadas posteriores). Cuarto, y quizás lo más importante, todas estas funciones son “conscientes del sistema de archivos virtual”. Cualquier sistema de archivos virtual (VFS, por sus siglas en inglés) que se haya registrado (a través de Tcl_FSRegister) puede redirigir el acceso a archivos a medios o métodos de acceso alternativos. Esto significa que todas estas funciones (y, por lo tanto, los comandos de Tcl correspondientes file, glob, pwd, cd, open, etc.) pueden operar sobre “archivos” que no son archivos nativos en el sistema de archivos nativo. Esto también significa que cualquier extensión de Tcl que acceda al sistema de archivos (FS, por sus siglas en inglés) a través de esta API es automáticamente “consciente del sistema de archivos virtual”. Por supuesto, si una extensión accede al sistema de archivos nativo directamente (a través de APIs específicas de la plataforma, por ejemplo), Tcl no puede interceptar tales llamadas.

Si se han registrado VFS apropiados, los “archivos” pueden ser, para dar dos ejemplos, remotos (por ejemplo, situados en un servidor ftp remoto) o archivados (por ejemplo, dentro de un archivo .zip). Dichos sistemas de archivos registrados proporcionan una tabla de búsqueda de funciones para implementar toda o parte de la funcionalidad enumerada aquí. Finalmente, las llamadas Tcl_FSStat y Tcl_FSLstat abstraen el contenido del búfer “struct stat”, lo que permite utilizar el mismo código tanto en sistemas con como sin soporte para archivos de más de 2 GB de tamaño.

La API Tcl_FS está optimizada para Tcl_Obj y puede almacenar en caché representaciones internas y otras cadenas relacionadas con rutas (por ejemplo, el directorio de trabajo actual). Un efecto secundario de esto es que no se deben pasar valores con un recuento de referencias de cero a ninguna de estas funciones. Si se manejaran tales llamadas, podrían resultar en pérdidas de memoria (en algunas circunstancias, el código del sistema de archivos puede desear retener una referencia al valor pasado, y por lo tanto, no se debe asumir que después de que cualquiera de estas llamadas regrese, el valor todavía tiene un recuento de referencias de cero, puede haber sido incrementado) o en una falla de segmentación directa (u otro error de acceso a memoria) debido a que el valor se libera a mitad de la manipulación compleja del valor requerida para garantizar que la ruta esté completamente normalizada y sea absoluta para la determinación del sistema de archivos. La lección práctica a aprender de esto es que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

es incorrecto y puede causar errores de memoria. El path debe tener su recuento de referencias incrementado antes de pasarlo, o decrementarlo. Por esta razón, los valores con un recuento de referencias de cero no se consideran rutas de sistema de archivos válidas y llamar a cualquier función de la API de Tcl_FS con dicho valor no tendrá ningún efecto.

FUNCIONES DE LA API FS

Tcl_FSCopyFile intenta copiar el archivo dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas se encuentran en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), entonces se llama a la función de “copiar archivo” de ese sistema de archivos (si no es NULL). De lo contrario, la función devuelve -1 y establece la variable global C errno al código de error POSIX “EXDEV” (que significa un “enlace entre dominios”).

Tcl_FSCopyDirectory intenta copiar el directorio dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas se encuentran en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), entonces se llama a la función de “copiar archivo” de ese sistema de archivos (si no es NULL). De lo contrario, la función devuelve -1 y establece la variable global C errno al código de error POSIX “EXDEV” (que significa un “enlace entre dominios”).

Tcl_FSCreateDirectory intenta crear el directorio dado por pathPtr llamando a la función de “crear directorio” del sistema de archivos propietario.

Tcl_FSDeleteFile intenta eliminar el archivo dado por pathPtr llamando a la función de “eliminar archivo” del sistema de archivos propietario.

Tcl_FSRemoveDirectory intenta eliminar el directorio dado por pathPtr llamando a la función de “eliminar directorio” del sistema de archivos propietario.

Tcl_FSRenameFile intenta renombrar el archivo o directorio dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas se encuentran en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), entonces se llama a la función de “renombrar archivo” de ese sistema de archivos (si no es NULL). De lo contrario, la función devuelve -1 y establece la variable global C errno al código de error POSIX “EXDEV” (que significa un “enlace entre dominios”).

Tcl_FSListVolumes llama a cada sistema de archivos que tiene una función de “listar volúmenes” no NULL y les pide que devuelvan su lista de volúmenes raíz. Acumula los valores de retorno en una lista que se devuelve al llamador (con un recuento de referencias de 0).

Tcl_FSEvalFileEx lee el archivo dado por pathPtr utilizando la codificación identificada por encodingName y evalúa su contenido como un script de Tcl. Devuelve la misma información que Tcl_EvalObjEx. Si encodingName es NULL, se utiliza la codificación del sistema para leer el contenido del archivo. Si el archivo no se pudo leer, se devuelve un error de Tcl para describir por qué no se pudo leer el archivo. El carácter de fin de archivo (eofchar) para archivos es “\x1A” (^Z) para todas las plataformas. Si necesita un “^Z” en código para comparación de cadenas, puede usar “\x1A”, que será sustituido de forma segura por el intérprete de Tcl por “^Z”. Tcl_FSEvalFile es una versión más simple de Tcl_FSEvalFileEx que siempre utiliza la codificación del sistema al leer el archivo.

Tcl_FSLoadFile carga dinámicamente un archivo de código binario en memoria y devuelve las direcciones de dos procedimientos dentro de ese archivo, si están definidos. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr. Si ese sistema de archivos no implementa esta función (la mayoría de los sistemas de archivos virtuales no lo harán, debido a limitaciones del sistema operativo en la carga dinámica de código binario), Tcl intentará copiar el archivo a un directorio temporal y cargar ese archivo temporal. Tcl_FSUnloadFile revierte la operación, pidiendo que la biblioteca indicada por loadHandle sea eliminada del proceso. Tenga en cuenta que, a diferencia del comando unload, esto no da a la biblioteca ninguna oportunidad de limpieza.

Ambas funciones anteriores devuelven un código de finalización de Tcl estándar. Si ocurre un error, se deja un mensaje de error en el resultado del interp.

El token proporcionado a través de la variable indicada por loadHandlePtr se puede utilizar con Tcl_FindSymbol.

Tcl_FSMatchInDirectory es utilizado por el código de globbing para buscar en un directorio todos los archivos que coincidan con un patrón dado. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

El valor de retorno es un resultado estándar de Tcl que indica si se produjo un error en el globbing. Los mensajes de error se colocan en interp (a menos que interp sea NULL, lo cual está permitido), pero los buenos resultados se colocan en resultPtr dado.

Tenga en cuenta que el código de glob implementa patrones recursivos internamente, por lo que esta función solo recibirá patrones simples, que se pueden hacer coincidir utilizando la lógica de string match. Para manejar la recursión, Tcl llamará a esta función con frecuencia solicitando solo que se devuelvan directorios. Un caso especial de ser llamado con un patrón NULL indica que la ruta solo necesita ser verificada para el tipo correcto.

Tcl_FSLink reemplaza la versión de biblioteca de readlink, y la extiende para soportar la creación de enlaces. Se llamará a la función apropiada para el sistema de archivos al que pertenece linkNamePtr.

Si toPtr es NULL, se realiza una acción de “leer enlace”. El resultado es un Tcl_Obj que especifica el contenido del enlace simbólico dado por linkNamePtr, o NULL si el enlace no se pudo leer. El resultado es propiedad del llamador, que debería llamar a Tcl_DecrRefCount cuando el resultado ya no sea necesario. Si toPtr no es NULL, Tcl debería crear un enlace de uno de los tipos pasados en el flag linkAction. Este flag es una combinación OR de TCL_CREATE_SYMBOLIC_LINK y TCL_CREATE_HARD_LINK. Donde exista una elección (es decir, se pasa más de un flag), la convención de Tcl es preferir los enlaces simbólicos. Cuando se crea un enlace con éxito, el valor de retorno debe ser toPtr (que por lo tanto ya es propiedad del llamador). Si no tiene éxito, se devuelve NULL.

Tcl_FSLstat rellena la estructura Tcl_StatBuf statPtr con información sobre el archivo especificado. No necesita ningún derecho de acceso al archivo para obtener esta información, pero necesita derechos de búsqueda para todos los directorios nombrados en la ruta que conduce al archivo. La estructura Tcl_StatBuf incluye información sobre el dispositivo, el inodo (siempre 0 en Windows), el modo de privilegios, nlink (siempre 1 en Windows), el ID de usuario (siempre 0 en Windows), el ID de grupo (siempre 0 en Windows), rdev (igual que el dispositivo en Windows), el tamaño, la última

tiempo de acceso, tiempo de última modificación y tiempo de último cambio de metadatos. Consulte API DE RESULTADO STAT PORTÁTIL para obtener una descripción de cómo escribir código portátil para asignar y acceder a la estructura Tcl_StatBuf.

Si path existe, Tcl_FSLstat devuelve 0 y la estructura stat se rellena con datos. De lo contrario, se devuelve -1 y no se proporciona información stat.

Tcl_FSUtime reemplaza la versión de biblioteca de utime.

Esto devuelve 0 en caso de éxito y -1 en caso de error (según la documentación de utime). Si tiene éxito, la función actualizará los valores "atime" y "mtime" del archivo proporcionado.

Tcl_FSFileAttrsGet implementa el acceso de lectura para el subcomando file attributes personalizable. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

Si el resultado es TCL_OK, entonces se colocó un valor en objPtrRef, que solo será válido temporalmente (a menos que se llame a Tcl_IncrRefCount).

Tcl_FSFileAttrsSet implementa el acceso de escritura para el subcomando file attributes personalizable. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

Tcl_FSFileAttrStrings implementa parte del subcomando file attributes personalizable. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

El procedimiento llamado puede devolver una matriz de cadenas o puede devolver NULL y colocar una lista Tcl en objPtrRef. Tcl tomará esa lista y primero incrementará su recuento de referencias antes de usarla. Al finalizar ese uso, Tcl disminuirá su recuento de referencias. Por lo tanto, si Tcl debe desechar la lista cuando termine, debe tener un recuento de referencias de cero, y si Tcl no debe desechar la lista, el sistema de archivos debe asegurarse de retener un recuento de referencias al valor.

Tcl_FSAccess comprueba si al proceso se le permitiría leer, escribir o probar la existencia del archivo (u otro objeto del sistema de archivos) cuyo nombre es pathname. Si pathname es un enlace simbólico en Unix, se prueban los permisos del archivo al que hace referencia este enlace simbólico.

En caso de éxito (todos los permisos solicitados concedidos), se devuelve cero. En caso de error (al menos un bit en mode solicitó un permiso que se deniega, o se produjo algún otro error), se devuelve -1.

Tcl_FSStat rellena la estructura Tcl_StatBuf statPtr con información sobre el archivo especificado. No necesita ningún derecho de acceso al archivo para obtener esta información, pero necesita derechos de búsqueda a todos los directorios nombrados en la ruta que conduce al archivo. La estructura Tcl_StatBuf incluye información sobre el dispositivo, inodo (siempre 0 en Windows), modo de privilegio, nlink (siempre 1 en Windows), id de usuario (siempre 0 en Windows), id de grupo (siempre 0 en Windows), rdev (igual que el dispositivo en Windows), tamaño, tiempo de último acceso, tiempo de última modificación y tiempo de último cambio de metadatos. Consulte API DE RESULTADO STAT PORTÁTIL para obtener una descripción de cómo escribir código portátil para asignar y acceder a la estructura Tcl_StatBuf.

Si path existe, Tcl_FSStat devuelve 0 y la estructura stat se rellena con datos. De lo contrario, se devuelve -1 y no se proporciona información stat.

Tcl_FSOpenFileChannel abre un archivo especificado por pathPtr y devuelve un manejador de canal que se puede utilizar para realizar operaciones de entrada y salida en el archivo. Esta API se basa en el procedimiento fopen de la biblioteca estándar de E/S de Unix. La sintaxis y el significado de todos los argumentos son similares a los dados en el comando Tcl open al abrir un archivo. Si ocurre un error al abrir el canal, Tcl_FSOpenFileChannel devuelve NULL y registra un código de error POSIX que se puede recuperar con Tcl_GetErrno. Además, si interp no es NULL, Tcl_FSOpenFileChannel deja un mensaje de error en el resultado de interp después de cualquier error.

El canal recién creado no se registra en el intérprete proporcionado; para registrarlo, use Tcl_RegisterChannel. Si uno de los canales estándar, stdin, stdout o stderr se cerró previamente, el acto de crear el nuevo canal también lo asigna como reemplazo del canal estándar.

Tcl_FSGetCwd reemplaza la versión de biblioteca de getcwd.

Devuelve el directorio de trabajo actual de la biblioteca Tcl. Este puede ser diferente al directorio de trabajo de la plataforma nativa, lo que ocurre cuando el directorio de trabajo actual no está en el sistema de archivos nativo.

El resultado es un puntero a un Tcl_Obj que especifica el directorio actual, o NULL si no se pudo determinar el directorio actual. Si se devuelve NULL, se deja un mensaje de error en el resultado de interp.

El resultado ya tiene incrementado su recuento de referencias para el llamador. Cuando ya no se necesite, se debe disminuir ese recuento de referencias. Esto es necesario por motivos de seguridad de hilos, para permitir que varios hilos accedan a esta y otras funciones relacionadas, al tiempo que se garantiza que los resultados sean siempre válidos.

Tcl_FSChdir reemplaza la versión de biblioteca de chdir. La ruta se normaliza y luego se pasa al sistema de archivos que la reclama. Si ese sistema de archivos no implementa esta función, Tcl recurrirá a una combinación de stat y access para comprobar si el directorio existe y tiene los permisos adecuados.

Para ver los resultados, consulte la documentación de chdir. Si tiene éxito, guardamos un registro de la ruta exitosa en cwdPathPtr para llamadas posteriores a Tcl_FSGetCwd.

Tcl_FSPathSeparator devuelve el carácter separador que se utilizará para el elemento más específico de la ruta especificada por pathPtr (es decir, la última parte de la ruta).

El separador se devuelve como un Tcl_Obj que contiene una cadena de longitud 1. Si la ruta no es válida, se devuelve NULL.

Tcl_FSJoinPath toma el Tcl_Obj dado, que debe ser una lista válida (a la que se le permite tener un recuento de referencias de cero), y devuelve el valor de ruta dado considerando los primeros elements elementos como segmentos de ruta válidos (cada segmento de ruta puede ser una ruta completa, una ruta parcial o simplemente un solo directorio o nombre de archivo posible). Si algún segmento de ruta es en realidad una ruta absoluta, entonces se descartan todos los segmentos de ruta anteriores. Si elements es menor que 0, usamos toda la lista.

Es posible que el valor devuelto sea en realidad un elemento de la lista dada, por lo que el llamador debe tener cuidado de incrementar el recuento de referencias del resultado antes de liberar la lista.

El valor devuelto, que típicamente tiene un recuento de referencias de cero (pero podría compartirse bajo ciertas condiciones), contiene la ruta unida. El llamador debe agregar un recuento de referencias al valor antes de usarlo. En particular, el valor devuelto podría ser un elemento de la lista dada, por lo que liberar la lista podría liberar el valor prematuramente si no se ha tomado ninguna referencia. Si el número de elementos es cero, entonces el valor devuelto será un Tcl_Obj de cadena vacía.

Tcl_FSSplitPath toma el Tcl_Obj dado, que debe ser una ruta válida, y devuelve un valor de lista Tcl que contiene cada segmento de esa ruta como un elemento. Devuelve un valor de lista con un recuento de referencias de cero. Si el lenPtr proporcionado no es NULL, la variable a la que apunta se actualizará para contener el número de elementos en la lista devuelta.

Tcl_FSEqualPaths prueba si las dos rutas dadas representan el mismo objeto del sistema de archivos. Devuelve 1 si las rutas son iguales y 0 si son diferentes. Si alguna de las rutas es NULL, siempre se devuelve 0.

Tcl_FSGetNormalizedPath intenta extraer del Tcl_Obj dado una representación de ruta normalizada única, cuyo valor de cadena se puede utilizar como un identificador único para el archivo.

Devuelve el valor de ruta normalizada, propiedad de Tcl, o NULL si la ruta no era válida o no se pudo convertir con éxito. La extracción de rutas absolutas y normalizadas es muy eficiente (porque el sistema de archivos opera internamente sobre estas representaciones), aunque el resultado cuando el sistema de archivos contiene numerosos enlaces simbólicos puede no ser la versión más amigable de una ruta. El valor devuelto es propiedad de Tcl y tiene una vida útil equivalente a la de pathPtr pasado (a menos que sea una ruta relativa, en cuyo caso el valor de ruta normalizada puede liberarse en cualquier momento que cambie el cwd): el llamador, por supuesto, puede incrementar el recuento de referencias si desea mantener una copia por más tiempo.

Tcl_FSJoinToPath toma el valor dado, que generalmente debería ser una ruta válida o NULL, y le une la matriz de segmentos de ruta proporcionados.

Devuelve un valor, típicamente con un recuento de referencias de cero (pero podría compartirse bajo ciertas condiciones), que contiene la ruta unida. El llamador debe agregar un recuento de referencias al valor antes de usarlo. Si alguno de los valores pasados a esta función (pathPtr o los elementos de path) tienen un recuento de referencias de cero, se liberarán cuando esta función devuelva.

Tcl_FSConvertToPathType intenta convertir el Tcl_Obj dado a un tipo de ruta Tcl válido, teniendo en cuenta el hecho de que el cwd puede haber cambiado incluso si este valor ya se supone que es del tipo correcto. El nombre de archivo puede comenzar con "~" (para indicar el directorio de inicio del usuario actual) o "~<usuario>" (para indicar el directorio de inicio de cualquier usuario).

Si la conversión tiene éxito (es decir, el valor es una ruta válida en uno de los sistemas de archivos actuales), entonces se devuelve TCL_OK. De lo contrario, se devuelve TCL_ERROR, y se puede dejar un mensaje de error en el intérprete.

Tcl_FSGetInternalRep extrae la representación interna de un valor de ruta dado, en el sistema de archivos dado. Si el valor de ruta pertenece a un sistema de archivos diferente, devolvemos NULL. Si la representación interna es actualmente NULL, intentamos generarla, llamando a Tcl_FSCreateInternalRepProc del sistema de archivos.

Devuelve NULL o una representación de ruta interna válida. Esta representación interna se almacena en caché, de modo que las llamadas repetidas a esta función no requerirán conversiones adicionales.

Tcl_FSGetTranslatedPath intenta extraer la ruta traducida del Tcl_Obj dado.

Si la traducción tiene éxito (es decir, el valor es una ruta válida), entonces se devuelve. De lo contrario, se devolverá NULL, y se puede dejar un mensaje de error en el intérprete. Una ruta "traducida" es aquella que no contiene secuencias "~" o "~usuario" (estas se han expandido a su representación actual en el sistema de archivos). El valor devuelto es propiedad del llamador, que debe almacenarlo o llamar a Tcl_DecrRefCount para asegurarse de que se libere la memoria. Esta función tiene poca utilidad práctica, y Tcl_FSGetNormalizedPath o Tcl_FSGetNativePath son funciones generalmente mejores para la mayoría de los propósitos.

Tcl_FSGetTranslatedStringPath hace lo mismo que Tcl_FSGetTranslatedPath, pero devuelve una cadena de caracteres o NULL. La cadena devuelta se aloca dinámicamente

poseído y propiedad del llamante, el cual debe almacenarlo o llamar a ckfree para asegurarse de que se libere. Nuevamente, Tcl_FSGetNormalizedPath o Tcl_FSGetNativePath son funciones generalmente mejores para usar en la mayoría de los casos.

Tcl_FSNewNativePath realiza algo así como lo inverso de las conversiones habituales obj->path->nativerep. Si algún código recupera una ruta en formato nativo (de, por ejemplo, readlink o un diálogo nativo), y esa ruta se va a usar a nivel de Tcl, entonces llamar a esta función es una forma eficiente de crear el tipo de valor de ruta apropiado.

El valor resultante es un valor de “ruta” puro, que solo recibirá una representación de cadena UTF-8 si es requerido por algún código Tcl.

Tcl_FSGetNativePath es para uso de los sistemas de archivos nativos Win/Unix, para que puedan recuperar fácilmente la representación nativa (char* o TCHAR*) de una ruta. Esta función es un envoltorio de conveniencia alrededor de Tcl_FSGetInternalRep. Puede ser deseable en el futuro tener representaciones nativas no basadas en cadenas (por ejemplo, en macOS, una representación que use una estructura FSRef de fileSpec probablemente sería más eficiente). En Windows, una representación Unicode completa permitiría rutas de longitud ilimitada. Actualmente, la representación es simplemente una cadena de caracteres que puede contener la ruta relativa o una ruta completa, absoluta y normalizada en la codificación nativa (condiciones complejas dictan cuál de estas se proporcionará, por lo que no se puede confiar en ninguna, a menos que se sepa que la ruta es absoluta). Si necesita una ruta nativa que deba ser absoluta, entonces debe solicitar la versión nativa de una ruta normalizada. Si por alguna razón se necesita una versión no absoluta y no normalizada de la ruta, esa debe construirse por separado (por ejemplo, usando Tcl_FSGetTranslatedPath).

La representación nativa se almacena en caché para que las llamadas repetidas a esta función no requieran conversiones adicionales. El valor de retorno es propiedad de Tcl y tiene una vida útil equivalente a la del pathPtr pasado (a menos que sea una ruta relativa, en cuyo caso la representación nativa puede liberarse en cualquier momento en que cambie el cwd).

Tcl_FSFileSystemInfo devuelve una lista de dos elementos. El primer elemento es el nombre del sistema de archivos (por ejemplo, “native”, “vfs”, “zip”, o “prowrap”, quizás), y el segundo es el tipo particular de la ruta dada dentro de ese sistema de archivos (que depende del sistema de archivos). El segundo elemento puede estar vacío si el sistema de archivos no proporciona una categorización adicional de archivos.

Se devuelve un valor de lista válido, a menos que el valor de la ruta no sea reconocido, en cuyo caso se devolverá NULL.

Tcl_FSGetFileSystemForPath devuelve un puntero al Tcl_Filesystem que acepta esta ruta como válida.

Si ningún sistema de archivos acepta la ruta, se devuelve NULL.

Tcl_FSGetPathType determina si la ruta dada es relativa al directorio actual, relativa al volumen actual o absoluta.

Devuelve uno de TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE o TCL_PATH_VOLUME_RELATIVE

LA API DEL SISTEMA DE ARCHIVOS VIRTUAL

Un sistema de archivos proporciona una estructura Tcl_Filesystem que contiene punteros a funciones que implementan las diversas operaciones en un sistema de archivos; estas operaciones se invocan según sea necesario por la capa genérica, lo que generalmente ocurre a través de las funciones enumeradas anteriormente.

Las estructuras Tcl_Filesystem se manipulan utilizando los siguientes métodos.

Tcl_FSRegister toma un puntero a una estructura de sistema de archivos y un dato opcional para asociar con ese sistema de archivos. Al llamar a esta función, Tcl adjuntará el sistema de archivos a la lista de sistemas de archivos conocidos, y se volverá completamente funcional de inmediato. Tcl no verifica si el mismo sistema de archivos se registra múltiples veces (y en general, eso no es algo bueno de hacer). Se devolverá TCL_OK.

Tcl_FSUnregister elimina la estructura del sistema de archivos dada de la lista de sistemas de archivos conocidos, si se conoce, y devuelve TCL_OK. Si el sistema de archivos no está registrado actualmente, se devuelve TCL_ERROR.

Tcl_FSData devolverá el clientData asociado con el sistema de archivos dado, si ese sistema de archivos está registrado. De lo contrario, devolverá NULL.

Tcl_FSMountsChanged se utiliza para informar al núcleo de Tcl que el conjunto de puntos de montaje para el sistema de archivos dado (ya registrado) ha cambiado, y que, por lo tanto, las representaciones de archivos cacheadas pueden no ser correctas.

Excepto por los tres primeros campos de esta estructura que contienen elementos de datos simples, todas las entradas contienen direcciones de funciones llamadas por la capa genérica del sistema de archivos para realizar la gama completa de acciones relacionadas con el sistema de archivos.

Las muchas funciones en esta estructura se dividen en tres categorías: funciones de infraestructura (casi todas las cuales deben implementarse), funciones operacionales (que deben implementarse si se proporciona un sistema de archivos completo) y funciones de eficiencia (que solo necesitan implementarse si se pueden hacer de manera eficiente, o si tienen efectos secundarios que son requeridos por el sistema de archivos; Tcl tiene emulaciones menos eficientes a las que puede recurrir). Es importante tener en cuenta que, en la versión actual de Tcl, la mayoría de estos recursos de respaldo solo se utilizan para manejar comandos iniciados en Tcl, no en C. Lo que esto significa es que, si se emite un comando file rename en Tcl, y el (los) sistema(s) de archivos relevantes no implementan su Tcl_FSRenameFileProc, el núcleo de Tcl recurrirá a una combinación de otras funciones del sistema de archivos (utilizará Tcl_FSCopyFileProc seguido de Tcl_FSDeleteFileProc, y si Tcl_FSCopyFileProc no está implementado, hay un recurso de respaldo adicional). Sin embargo, si se emite un comando Tcl_FSRenameFileProc a nivel de C, no ocurren tales recursos de respaldo. Esto es cierto excepto para las últimas cuatro entradas en la tabla del sistema de archivos (lstat, load, getcwd y chdir) para las cuales en realidad ocurren recursos de respaldo a nivel de C.

Cualquier función que tome nombres de ruta en forma Tcl_Obj toma esos nombres en forma UTF-8. La API de infraestructura del sistema de archivos está diseñada para admitir la conversión eficiente y en caché de estas rutas UTF-8 a otras representaciones nativas.

OPENFILECHANNELPROC

Función para procesar una llamada Tcl_FSOpenFileChannel. Debe implementarse para cualquier sistema de archivos razonable, ya que cualquier operación que requiera abrir o acceder al contenido de un archivo la utilizará (por ejemplo, open, encoding y muchos comandos Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

Tcl_FSOpenFileChannelProc abre un archivo especificado por pathPtr y devuelve un manejador de canal que se puede utilizar para realizar operaciones de entrada y salida en el archivo. Esta API está modelada según el procedimiento fopen de la biblioteca de E/S estándar de Unix. La sintaxis y el significado de todos los argumentos son similares a los dados en el comando open de Tcl al abrir un archivo, donde el argumento mode es una combinación de las banderas POSIX O_RDONLY, O_WRONLY, etc. Si ocurre un error al abrir el canal, Tcl_FSOpenFileChannelProc devuelve NULL y registra un código de error POSIX que se puede recuperar con Tcl_GetErrno. Además, si interp no es NULL, Tcl_FSOpenFileChannelProc deja un mensaje de error en el resultado de interp después de cualquier error.

El canal recién creado no debe registrarse en el intérprete proporcionado por un Tcl_FSOpenFileChannelProc; esa tarea corresponde al llamador de Tcl_FSOpenFileChannel (si es necesario). Si alguno de los canales estándar, stdin, stdout o stderr se cerró previamente, la creación del nuevo canal también lo asigna como reemplazo del canal estándar.

MATCHINDIRECTORYPROC

Función para procesar una llamada Tcl_FSMatchInDirectory. Si no se implementa, la funcionalidad de globbing y copia recursiva faltará en el sistema de archivos (y esto puede afectar a comandos como encoding names que utilizan internamente la funcionalidad de globbing).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La función debe devolver todos los archivos o directorios (u otros objetos del sistema de archivos) que coincidan con el patrón dado y que cumplan con la especificación de types. Hay dos formas en las que se puede llamar a esta función. Si pattern es NULL, entonces pathPtr es una especificación de ruta completa de un solo archivo o directorio que debe verificarse en cuanto a existencia y tipo correcto. De lo contrario, pathPtr es un directorio, cuyo contenido la función debe buscar archivos o directorios que tengan el tipo correcto. En cualquier caso, se puede asumir que pathPtr no es NULL ni está vacío. Actualmente no está documentado si pathPtr tendrá o no un separador de archivos al final, por lo que el código debe ser flexible a ambas posibilidades.

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso de coincidencia. Los mensajes de error se colocan en interp, a menos que interp sea NULL, en cuyo caso no es necesario generar ningún mensaje de error; en un resultado TCL_OK, los resultados deben agregarse al valor resultPtr dado (que se puede asumir que es una lista válida no compartida de Tcl). Las coincidencias agregadas a resultPtr deben incluir cualquier prefijo de ruta dado en pathPtr (esto generalmente significa que serán especificaciones de ruta absolutas). Tenga en cuenta que si no se encuentran coincidencias, eso simplemente conduce a un resultado vacío; los errores solo se señalan para problemas reales de archivo o sistema de archivos que puedan ocurrir durante el proceso de coincidencia.

La estructura Tcl_GlobTypeData pasada en el parámetro types contiene los siguientes campos:

typedef struct Tcl_GlobTypeData {
    /* Corresponde a bcdpfls como en 'find -t' */
    int type;
    /* Corresponde a permisos de archivo */
    int perm;
    /* Tipo Mac aceptable */
    Tcl_Obj *macType;
    /* Creador Mac aceptable */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Hay dos casos específicos que es importante manejar correctamente, ambos cuando types no es NULL. Los dos casos son cuando types->types & TCL_GLOB_TYPE_DIR o types->types & TCL_GLOB_TYPE_MOUNT son verdaderos (y en particular cuando las otras banderas son falsas). En el primero de estos casos, la función debe listar los directorios contenidos. Tcl utiliza esto para implementar el globbing recursivo, por lo que es fundamental que los sistemas de archivos implementen la coincidencia de directorios correctamente. En el segundo de estos casos, con TCL_GLOB_TYPE_MOUNT, el sistema de archivos debe listar los puntos de montaje que se encuentran dentro del pathPtr dado (y en este caso, pathPtr no necesita estar dentro del mismo sistema de archivos, a diferencia de todos los demás casos en los que se llama a esta función). El soporte para esto es fundamental si Tcl quiere tener transiciones fluidas entre un sistema de archivos y otro.

UTIMEPROC

Función para procesar una llamada Tcl_FSUtime. Necesaria para permitir el establecimiento (no la lectura) de tiempos con file mtime, file atime y la implementación open-r/open-w/fcopy de file copy.

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

Los tiempos de acceso y modificación del archivo especificado por pathPtr deben cambiarse a los valores dados en la estructura tval.

El valor de retorno debe ser 0 en caso de éxito y -1 en caso de error, al igual que con el utime del sistema.

LINKPROC

Función para procesar una llamada Tcl_FSLink. Solo debe implementarse si el sistema de archivos admite enlaces, y de lo contrario puede ser NULL.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

Si toPtr es NULL, se está pidiendo a la función que lea el contenido de un enlace. El resultado es un Tcl_Obj que especifica el contenido del enlace dado por linkNamePtr, o NULL si el enlace no pudo ser leído. El resultado es propiedad del llamador (y, por lo tanto, se debe incrementar su contador de referencias antes de devolverlo). Cualquier llamador debe llamar a Tcl_DecrRefCount en este resultado cuando ya no sea necesario. Si toPtr no es NULL, la función debe intentar crear un enlace. El resultado en este caso debe ser toPtr si el enlace fue exitoso y NULL en caso contrario. En este caso, el resultado no es propiedad del llamador (es decir, no se necesitan manipulaciones del contador de referencias en ninguno de los extremos). Consulte la documentación de Tcl_FSLink para la interpretación correcta de las banderas linkAction.

LISTVOLUMESPROC

Función para listar cualquier volumen de sistema de archivos agregado por este sistema de archivos. Solo debe implementarse si el sistema de archivos agrega volúmenes al principio del sistema de archivos, para que puedan ser devueltos por file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

El resultado debe ser una lista de volúmenes agregados por este sistema de archivos, o NULL (o una lista vacía) si no se proporcionan volúmenes. El valor del resultado se considera propiedad del sistema de archivos (no del núcleo de Tcl), pero se le debe asignar un contador de referencias para Tcl. Tcl utilizará el contenido de la lista e luego decrementará ese contador de referencias. Esto permite a los sistemas de archivos elegir si realmente desean retener una lista "global" de volúmenes o no (si no es así, generan la lista sobre la marcha y la pasan a Tcl con un contador de referencias de 1 y luego se olvidan de la lista; si es así, simplemente incrementan el contador de referencias de su lista global y la pasan a Tcl, que copiará el contenido y luego decrementará el contador hasta donde estaba).

Por lo tanto, Tcl considera que los valores de retorno de este proc son de solo lectura.

FILEATTRSTRINGSPROC

Función para listar todas las cadenas de atributos que son válidas para este sistema de archivos. Si no se implementa, el sistema de archivos no admitirá el comando file attributes. Esto permite adjuntar información adicional arbitraria a los archivos en el sistema de archivos. Si no se implementa, no es necesario implementar los métodos get y set.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

La función llamada puede devolver una matriz de cadenas o puede devolver NULL y colocar una lista de Tcl en el objPtrRef proporcionado. Tcl tomará esa lista y primero incrementará su contador de referencias antes de usarla. Al finalizar ese uso, Tcl decrementará su contador de referencias. Por lo tanto, si la lista debe ser eliminada por Tcl cuando termine, debe tener un contador de referencias de cero, y si la lista no debe ser eliminada, el sistema de archivos debe asegurarse de devolver un valor con un contador de referencias de al menos uno.

FILEATTRSGETPROC

Función para procesar una llamada Tcl_FSFileAttrsGet, utilizada por file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

Devuelve un código de retorno estándar de Tcl. El valor del atributo recuperado, que corresponde al elemento de índice index en la lista devuelta por Tcl_FSFileAttrStringsProc, es un Tcl_Obj colocado en objPtrRef (si se devolvió TCL_OK) y es probable que tenga un contador de referencias de cero. En cualquier caso, debemos almacenarlo en algún lugar (por ejemplo, el resultado de Tcl), o incrementar/decrementar su contador de referencias para garantizar que se libere correctamente.

FILEATTRSSETPROC

Función para procesar una llamada Tcl_FSFileAttrsSet, utilizada por file attributes. Si el sistema de archivos es de solo lectura, no es necesario implementarlo.

typedef int Tcl_FSFileAttrsSetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj *objPtr);

El valor del atributo del elemento de índice index en la lista devuelta por Tcl_FSFileAttrStringsProc debe establecerse en el objPtr proporcionado.
