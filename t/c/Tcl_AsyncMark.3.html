Tcl_AsyncCreate(3) Procedimientos de la biblioteca Tcl Tcl_AsyncCreate(3)

NOMBRE

Tcl_AsyncCreate, Tcl_AsyncMark, Tcl_AsyncInvoke, Tcl_AsyncDelete, Tcl_AsyncReady - manejar eventos asíncronos

SINOPSIS

#include <tcl.h>

Tcl_AsyncHandler
Tcl_AsyncCreate(proc, clientData)

void
Tcl_AsyncMark(async)

int
Tcl_AsyncInvoke(interp, code)

void
Tcl_AsyncDelete(async)

int
Tcl_AsyncReady()

ARGUMENTOS

Tcl_AsyncProc *proc (entrada)
Procedimiento a invocar para manejar un evento asíncrono.
ClientData clientData (entrada)
Valor de una palabra para pasar a proc.
Tcl_AsyncHandler async (entrada)
Token para el manejador de eventos asíncronos.
Tcl_Interp *interp (entrada)
Intérprete Tcl en el que se estaba evaluando el comando cuando se invocó el manejador, o NULL si el manejador se invocó cuando no había ningún intérprete activo.
int code (entrada)
Código de finalización del comando que acaba de completarse en interp, o 0 si interp es NULL.

DESCRIPCIÓN

Estos procedimientos proporcionan un mecanismo seguro para tratar eventos asíncronos como señales. Si un evento como una señal ocurre mientras se está evaluando un script de Tcl, no es seguro tomar ninguna acción sustantiva para procesar el evento. Por ejemplo, no es seguro evaluar un script de Tcl ya que el intérprete podría estar en medio de la evaluación de un script; incluso podría no ser seguro asignar memoria, ya que una asignación de memoria podría estar en progreso cuando ocurrió el evento. El único enfoque seguro es establecer una bandera indicando que el evento ocurrió, y luego manejar el evento más tarde, cuando el mundo haya vuelto a un estado limpio, como después de que el comando Tcl actual se complete.

Tcl_AsyncCreate, Tcl_AsyncDelete y Tcl_AsyncReady son sensibles a hilos. Acceden y/o establecen una estructura de datos específica del hilo en caso de un núcleo construido con --enable-threads. El token creado por Tcl_AsyncCreate contiene la información del hilo necesaria para la cual se llamó, de modo que llamar a Tcl_AsyncMark(token) solo producirá el hilo de origen en el manejador asíncrono.

Tcl_AsyncCreate crea un manejador asíncrono y devuelve un token para él. El manejador asíncrono debe crearse antes de que ocurran las ocurrencias del evento asíncrono que pretende manejar (no es seguro crear un manejador en el momento de un evento). Cuando ocurre un evento asíncrono, el código que detecta el evento (como un manejador de señales) debe llamar a Tcl_AsyncMark con el token para el manejador. Tcl_AsyncMark marcará el manejador como listo para ejecutarse, pero no invocará al manejador inmediatamente. Tcl llamará al proc asociado con el manejador más tarde, cuando el mundo esté en un estado seguro, y proc podrá llevar a cabo las acciones asociadas con el evento asíncrono. Proc debe tener argumentos y resultados que coincidan con el tipo Tcl_AsyncProc:

typedef int Tcl_AsyncProc(
        ClientData clientData,
        Tcl_Interp *interp,
        int code);

El clientData será el mismo que el argumento clientData pasado a Tcl_AsyncCreate cuando se creó el manejador. Si se invoca proc justo después de que un comando haya completado su ejecución en un intérprete, entonces interp identificará el intérprete en el que se evaluó el comando y code será el código de finalización devuelto por ese comando. El resultado del comando estará presente en el resultado del intérprete. Cuando proc retorna, lo que sea que deje en el resultado del intérprete se devolverá como resultado del comando y el valor entero devuelto por proc se usará como el nuevo código de finalización del comando.

También es posible que se invoque proc cuando no hay ningún intérprete activo. Esto puede ocurrir, por ejemplo, si un evento asíncrono ocurre mientras la aplicación está esperando entrada interactiva o un evento X. En este caso, interp será NULL y code será 0, y el valor de retorno de proc se ignorará.

El procedimiento Tcl_AsyncInvoke se llama para invocar a todos los manejadores que están listos. El procedimiento Tcl_AsyncReady devolverá un valor distinto de cero siempre que haya manejadores asíncronos listos; se puede comprobar para evitar llamadas a Tcl_AsyncInvoke cuando no hay manejadores listos. Tcl llama a Tcl_AsyncReady después de que cada comando se evalúa y llama a Tcl_AsyncInvoke si es necesario. Las aplicaciones también pueden llamar a Tcl_AsyncInvoke en momentos interesantes para esa aplicación. Por ejemplo, el manejador de eventos de Tcl llama a Tcl_AsyncReady después de cada evento y llama a Tcl_AsyncInvoke si es necesario. Los argumentos interp y code para Tcl_AsyncInvoke tienen el mismo significado que para proc: identifican el intérprete activo, si lo hay, y el código de finalización del comando que acaba de completarse.

Tcl_AsyncDelete elimina un manejador asíncrono para que su proc nunca más sea invocado. Un manejador puede ser eliminado incluso cuando está listo, y aún así no será invocado.

Si varios manejadores se vuelven activos al mismo tiempo, los manejadores se invocan en el orden en que fueron creados (el manejador más antiguo primero). El code y el resultado del intérprete para los manejadores posteriores reflejan los valores devueltos por los manejadores anteriores, de modo que el manejador creado más recientemente tiene la última palabra sobre el resultado y el código de finalización del intérprete. Si surgen nuevos manejadores mientras los manejadores se están ejecutando, Tcl_AsyncInvoke los invocará a todos; en cada punto invoca al manejador listo de mayor prioridad (más antiguo), repitiendo esto una y otra vez hasta que ya no haya manejadores listos.

ADVERTENCIA

Casi siempre es una mala idea que un manejador de eventos asíncronos modifique el resultado del intérprete o devuelva un código diferente de su argumento code. Este tipo de comportamiento puede interrumpir la ejecución de scripts de maneras sutiles y resultar en errores extremadamente difíciles de rastrear. Si un manejador de eventos asíncronos necesita evaluar scripts de Tcl, primero debe guardar el estado del intérprete llamando a Tcl_SaveInterpState, pasando el argumento code. Cuando el manejador asíncrono termine, debe restaurar el estado del intérprete llamando a Tcl_RestoreInterpState y luego devolviendo el argumento code.
