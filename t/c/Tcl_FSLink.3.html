DESCRIPCIÓN

Hay varias razones para llamar a las funciones de la API Tcl_FS (por ejemplo, Tcl_FSAccess y Tcl_FSStat) en lugar de llamar directamente a funciones de nivel de sistema como access y stat. En primer lugar, funcionan en múltiples plataformas, por lo que una extensión que las llama debería funcionar sin modificaciones tanto en Unix como en Windows. En segundo lugar, la implementación de Windows de algunas de estas funciones corrige algunos errores en las llamadas a nivel de sistema. En tercer lugar, estas llamadas a funciones manejan cualquier conversión de ruta de “Utf a nativo de la plataforma” que pueda ser necesaria (y pueden almacenar en caché los resultados de dichas conversiones para una mayor eficiencia en llamadas posteriores). En cuarto lugar, y quizás lo más importante, todas estas funciones tienen en cuenta el “sistema de archivos virtual”. Cualquier sistema de archivos virtual (VFS, por sus siglas en inglés) que se haya registrado (a través de Tcl_FSRegister) puede redirigir el acceso a archivos a medios o métodos de acceso alternativos. Esto significa que todas estas funciones (y por lo tanto, los comandos de Tcl correspondientes file, glob, pwd, cd, open, etc.) pueden operar sobre “archivos” que no son archivos nativos en el sistema de archivos nativo. Esto también significa que cualquier extensión de Tcl que acceda al sistema de archivos (FS, por sus siglas en inglés) a través de esta API tiene automáticamente en cuenta el “sistema de archivos virtual”. Por supuesto, si una extensión accede al sistema de archivos nativo directamente (a través de API específicas de la plataforma, por ejemplo), Tcl no puede interceptar tales llamadas.

Si se han registrado VFS apropiados, los “archivos” pueden ser, para dar dos ejemplos, remotos (por ejemplo, situados en un servidor ftp remoto) o archivados (por ejemplo, dentro de un archivo .zip). Dichos sistemas de archivos registrados proporcionan una tabla de búsqueda de funciones para implementar toda o parte de la funcionalidad enumerada aquí. Finalmente, las llamadas Tcl_FSStat y Tcl_FSLstat abstraen el contenido del búfer “struct stat”, permitiendo que el mismo código se utilice tanto en sistemas con soporte para archivos mayores de 2 GB como en sistemas sin él.

La API de Tcl_FS está basada en Tcl_Obj y puede almacenar en caché representaciones internas y otras cadenas relacionadas con rutas (por ejemplo, el directorio de trabajo actual). Un efecto secundario de esto es que no se deben pasar valores con un recuento de referencias de cero a ninguna de estas funciones. Si tales llamadas se manejaran, podrían resultar en fugas de memoria (bajo ciertas circunstancias, el código del sistema de archivos puede desear retener una referencia al valor pasado, y por lo tanto, no se debe asumir que después de que cualquiera de estas llamadas regrese, el valor todavía tiene un recuento de referencias de cero - puede haber sido incrementado) o en una falla de segmentación directa (u otro error de acceso a memoria) debido a que el valor se libera a mitad de la manipulación compleja del valor requerida para asegurar que la ruta esté completamente normalizada y sea absoluta para la determinación del sistema de archivos. La lección práctica que se debe aprender de esto es que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

es incorrecto y puede causar errores de memoria. El recuento de referencias de path debe incrementarse antes de pasarlo, o decrementarlo. Por esta razón, los valores con un recuento de referencias de cero se consideran rutas de sistema de archivos no válidas y llamar a cualquier función de la API de Tcl_FS con un valor de este tipo no producirá ninguna acción.

FUNCIONES DE LA API FS

Tcl_FSCopyFile intenta copiar el archivo dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas residen en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), entonces se llama a la función “copiar archivo” de ese sistema de archivos (si no es NULL). De lo contrario, la función devuelve -1 y establece la variable global C errno al código de error POSIX “EXDEV” (que significa un “enlace entre dominios”).

Tcl_FSCopyDirectory intenta copiar el directorio dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas residen en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), entonces se llama a la función “copiar archivo” de ese sistema de archivos (si no es NULL). De lo contrario, la función devuelve -1 y establece la variable global C errno al código de error POSIX “EXDEV” (que significa un “enlace entre dominios”).

Tcl_FSCreateDirectory intenta crear el directorio dado por pathPtr llamando a la función “crear directorio” del sistema de archivos propietario.

Tcl_FSDeleteFile intenta eliminar el archivo dado por pathPtr llamando a la función “eliminar archivo” del sistema de archivos propietario.

Tcl_FSRemoveDirectory intenta eliminar el directorio dado por pathPtr llamando a la función “eliminar directorio” del sistema de archivos propietario.

Tcl_FSRenameFile intenta renombrar el archivo o directorio dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas residen en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), entonces se llama a la función “renombrar archivo” de ese sistema de archivos (si no es NULL). De lo contrario, la función devuelve -1 y establece la variable global C errno al código de error POSIX “EXDEV” (que significa un “enlace entre dominios”).

Tcl_FSListVolumes llama a cada sistema de archivos que tiene una función no NULL de “listar volúmenes” y les pide que devuelvan su lista de volúmenes raíz. Acumula los valores de retorno en una lista que se devuelve al llamador (con un recuento de referencias de 0).

Tcl_FSEvalFileEx lee el archivo dado por pathPtr utilizando la codificación identificada por encodingName y evalúa su contenido como un script de Tcl. Devuelve la misma información que Tcl_EvalObjEx. Si encodingName es NULL, se utiliza la codificación del sistema para leer el contenido del archivo. Si el archivo no se pudo leer, se devuelve un error de Tcl para describir por qué no se pudo leer. El carácter de fin de archivo (eofchar) para los archivos es “\x1A” (^Z) para todas las plataformas. Si requiere un “^Z” en código para comparación de cadenas, puede usar “\x1A”, que será sustituido de forma segura por el intérprete de Tcl en “^Z”. Tcl_FSEvalFile es una versión más simple de Tcl_FSEvalFileEx que siempre utiliza la codificación del sistema al leer el archivo.

Tcl_FSLoadFile carga dinámicamente un archivo de código binario en memoria y devuelve las direcciones de dos procedimientos dentro de ese archivo, si están definidos. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr. Si ese sistema de archivos no implementa esta función (la mayoría de los sistemas de archivos virtuales no lo harán, debido a limitaciones del SO en la carga dinámica de código binario), Tcl intentará copiar el archivo a un directorio temporal y cargar ese archivo temporal. Tcl_FSUnloadFile revierte la operación, solicitando que la biblioteca indicada por loadHandle sea eliminada del proceso. Tenga en cuenta que, a diferencia del comando unload, esto no da a la biblioteca ninguna oportunidad de limpieza.

Ambas funciones anteriores devuelven un código de finalización estándar de Tcl. Si ocurre un error, se deja un mensaje de error en el resultado del interp.

El token proporcionado a través de la variable indicada por loadHandlePtr se puede utilizar con Tcl_FindSymbol.

Tcl_FSMatchInDirectory es utilizada por el código de globbing para buscar en un directorio todos los archivos que coincidan con un patrón dado. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el globbing. Los mensajes de error se colocan en interp (a menos que interp sea NULL, lo cual está permitido), pero los resultados buenos se colocan en resultPtr proporcionado.

Tenga en cuenta que el código de glob implementa patrones recursivos internamente, por lo que esta función solo recibirá patrones simples, que se pueden hacer coincidir utilizando la lógica de string match. Para manejar la recursión, Tcl llamará a esta función con frecuencia pidiendo solo que se devuelvan directorios. Un caso especial de ser llamado con un patrón NULL indica que la ruta solo necesita ser verificada para el tipo correcto.

Tcl_FSLink reemplaza la versión de biblioteca de readlink y la extiende para admitir la creación de enlaces. Se llamará a la función apropiada para el sistema de archivos al que pertenece linkNamePtr.

Si toPtr es NULL, se realiza una acción de “leer enlace”. El resultado es un Tcl_Obj que especifica el contenido del enlace simbólico dado por linkNamePtr, o NULL si el enlace no pudo ser leído. El resultado es propiedad del llamador, que debe llamar a Tcl_DecrRefCount cuando el resultado ya no sea necesario. Si toPtr no es NULL, Tcl debería crear un enlace de uno de los tipos pasados en el indicador linkAction. Este indicador es una combinación OR de TCL_CREATE_SYMBOLIC_LINK y TCL_CREATE_HARD_LINK. Donde existe una opción (es decir, se pasa más de un indicador), la convención de Tcl es preferir los enlaces simbólicos. Cuando se crea un enlace con éxito, el valor de retorno debe ser toPtr (que por lo tanto ya es propiedad del llamador). Si no tiene éxito, se devuelve NULL.

Tcl_FSLstat rellena la estructura Tcl_StatBuf statPtr con información sobre el archivo especificado. No necesita ningún derecho de acceso al archivo para obtener esta información, pero necesita derechos de búsqueda para todos los directorios nombrados en la ruta que conduce al archivo. La estructura Tcl_StatBuf incluye información sobre el dispositivo, inodo (siempre 0 en Windows), modo de privilegios, nlink (siempre 1 en Windows), id de usuario (siempre 0 en Windows), id de grupo (siempre 0 en Windows), rdev (igual que el dispositivo en Windows), tamaño, último acceso ti

e, hora de última modificación y hora de último cambio de metadatos. Consulte la API DE RESULTADOS DE STAT PORTÁTIL para obtener una descripción de cómo escribir código portátil para asignar y acceder a la estructura Tcl_StatBuf.

Si path existe, Tcl_FSLstat devuelve 0 y la estructura stat se rellena con datos. De lo contrario, se devuelve -1 y no se proporciona información de stat.

Tcl_FSUtime reemplaza la versión de biblioteca de utime.

Esto devuelve 0 en caso de éxito y -1 en caso de error (según la documentación de utime). Si tiene éxito, la función actualizará los valores "atime" y "mtime" del archivo proporcionado.

Tcl_FSFileAttrsGet implementa el acceso de lectura para el subcomando file attributes, que puede ser enganchado. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

Si el resultado es TCL_OK, entonces se colocó un valor en objPtrRef, que solo será válido temporalmente (a menos que se llame a Tcl_IncrRefCount).

Tcl_FSFileAttrsSet implementa el acceso de escritura para el subcomando file attributes, que puede ser enganchado. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

Tcl_FSFileAttrStrings implementa parte del subcomando file attributes, que puede ser enganchado. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

El procedimiento llamado puede devolver una matriz de cadenas o, en su lugar, puede devolver NULL y colocar una lista de Tcl en objPtrRef. Tcl tomará esa lista y primero incrementará su recuento de referencias antes de usarla. Al finalizar ese uso, Tcl decrementará su recuento de referencias. Por lo tanto, si Tcl debe desechar la lista cuando termine, debería tener un recuento de referencias de cero, y si la lista no debe desecharse, el sistema de archivos debe asegurarse de conservar un recuento de referencias del valor.

Tcl_FSAccess verifica si se permitiría al proceso leer, escribir o probar la existencia del archivo (u otro objeto del sistema de archivos) cuyo nombre es pathname. Si pathname es un enlace simbólico en Unix, se prueban los permisos del archivo al que se refiere este enlace simbólico.

En caso de éxito (todos los permisos solicitados concedidos), se devuelve cero. En caso de error (al menos un bit en el modo solicitado para un permiso denegado, o ocurrió algún otro error), se devuelve -1.

Tcl_FSStat rellena la estructura Tcl_StatBuf statPtr con información sobre el archivo especificado. No necesita ningún derecho de acceso al archivo para obtener esta información, pero necesita derechos de búsqueda para todos los directorios nombrados en la ruta que conduce al archivo. La estructura Tcl_StatBuf incluye información sobre el dispositivo, el inodo (siempre 0 en Windows), el modo de privilegios, nlink (siempre 1 en Windows), el id de usuario (siempre 0 en Windows), el id de grupo (siempre 0 en Windows), rdev (igual que el dispositivo en Windows), tamaño, hora del último acceso, hora de la última modificación y hora del último cambio de metadatos. Consulte la API DE RESULTADOS DE STAT PORTÁTIL para obtener una descripción de cómo escribir código portátil para asignar y acceder a la estructura Tcl_StatBuf.

Si path existe, Tcl_FSStat devuelve 0 y la estructura stat se rellena con datos. De lo contrario, se devuelve -1 y no se proporciona información de stat.

Tcl_FSOpenFileChannel abre un archivo especificado por pathPtr y devuelve un manejador de canal que se puede utilizar para realizar operaciones de entrada y salida en el archivo. Esta API está modelada según el procedimiento fopen de la biblioteca estándar de E/S de Unix. La sintaxis y el significado de todos los argumentos son similares a los proporcionados en el comando open de Tcl al abrir un archivo. Si ocurre un error al abrir el canal, Tcl_FSOpenFileChannel devuelve NULL y registra un código de error POSIX que se puede recuperar con Tcl_GetErrno. Además, si interp no es NULL, Tcl_FSOpenFileChannel deja un mensaje de error en el resultado de interp después de cualquier error.

El canal recién creado no se registra en el intérprete proporcionado; para registrarlo, use Tcl_RegisterChannel. Si uno de los canales estándar, stdin, stdout o stderr se cerró previamente, la creación del nuevo canal también lo asigna como reemplazo del canal estándar.

Tcl_FSGetCwd reemplaza la versión de biblioteca de getcwd.

Devuelve el directorio de trabajo actual de la biblioteca de Tcl. Este puede ser diferente del directorio de trabajo de la plataforma nativa, lo que ocurre cuando el directorio de trabajo actual no está en el sistema de archivos nativo.

El resultado es un puntero a un Tcl_Obj que especifica el directorio actual, o NULL si no se pudo determinar el directorio actual. Si se devuelve NULL, se deja un mensaje de error en el resultado de interp.

El resultado ya tiene su recuento de referencias incrementado para el llamador. Cuando ya no sea necesario, se debe decrementar ese recuento de referencias. Esto es necesario por motivos de seguridad de hilos, para permitir que varios hilos accedan a esta y funciones relacionadas, al tiempo que se garantiza que los resultados sean siempre válidos.

Tcl_FSChdir reemplaza la versión de biblioteca de chdir. La ruta se normaliza y luego se pasa al sistema de archivos que la reclama. Si ese sistema de archivos no implementa esta función, Tcl recurrirá a una combinación de stat y access para verificar si el directorio existe y tiene los permisos apropiados.

Para ver los resultados, consulte la documentación de chdir. Si tiene éxito, conservamos un registro de la ruta exitosa en cwdPathPtr para llamadas posteriores a Tcl_FSGetCwd.

Tcl_FSPathSeparator devuelve el carácter separador que se utilizará para el elemento más específico de la ruta especificada por pathPtr (es decir, la última parte de la ruta).

El separador se devuelve como un Tcl_Obj que contiene una cadena de longitud 1. Si la ruta no es válida, se devuelve NULL.

Tcl_FSJoinPath toma el Tcl_Obj dado, que debe ser una lista válida (a la que se le permite tener un recuento de referencias de cero), y devuelve el valor de la ruta dado considerando los primeros elements elementos como segmentos de ruta válidos (cada segmento de ruta puede ser una ruta completa, una ruta parcial o simplemente un único directorio o nombre de archivo posible). Si algún segmento de ruta es en realidad una ruta absoluta, todos los segmentos de ruta anteriores se descartan. Si elements es menor que 0, usamos la lista completa.

Es posible que el valor devuelto sea en realidad un elemento de la lista dada, por lo que el llamador debe tener cuidado de incrementar el recuento de referencias del resultado antes de liberar la lista.

El valor devuelto, típicamente con un recuento de referencias de cero (pero podría compartirse en algunas condiciones), contiene la ruta unida. El llamador debe agregar un recuento de referencias al valor antes de usarlo. En particular, el valor devuelto podría ser un elemento de la lista dada, por lo que liberar la lista podría liberar el valor prematuramente si no se ha tomado ningún recuento de referencias. Si el número de elementos es cero, el valor devuelto será un Tcl_Obj de cadena vacía.

Tcl_FSSplitPath toma el Tcl_Obj dado, que debe ser una ruta válida, y devuelve un valor de lista Tcl que contiene cada segmento de esa ruta como un elemento. Devuelve un valor de lista con un recuento de referencias de cero. Si lenPtr no es NULL, la variable a la que apunta se actualizará para contener el número de elementos en la lista devuelta.

Tcl_FSEqualPaths prueba si las dos rutas dadas representan el mismo objeto del sistema de archivos. Devuelve 1 si las rutas son iguales y 0 si son diferentes. Si alguna de las rutas es NULL, siempre se devuelve 0.

Tcl_FSGetNormalizedPath intenta extraer del Tcl_Obj dado una representación de ruta normalizada única, cuyo valor de cadena se puede utilizar como identificador único del archivo.

Devuelve el valor de ruta normalizado, propiedad de Tcl, o NULL si la ruta no era válida o no se pudo convertir correctamente. La extracción de rutas absolutas y normalizadas es muy eficiente (porque el sistema de archivos opera internamente sobre estas representaciones), aunque el resultado cuando el sistema de archivos contiene numerosos enlaces simbólicos puede no ser la versión más amigable de una ruta. El valor de retorno es propiedad de Tcl y tiene una vida útil equivalente a la de pathPtr proporcionado (a menos que sea una ruta relativa, en cuyo caso el valor de ruta normalizado puede liberarse en cualquier momento en que cambie el cwd); el llamador, por supuesto, puede incrementar el recuento de referencias si desea mantener una copia por más tiempo.

Tcl_FSJoinToPath toma el valor dado, que normalmente debería ser una ruta válida o NULL, y le une la matriz de segmentos de ruta proporcionados.

Devuelve un valor, típicamente con un recuento de referencias de cero (pero podría compartirse en algunas condiciones), que contiene la ruta unida. El llamador debe agregar un recuento de referencias al valor antes de usarlo. Si alguno de los valores pasados a esta función (pathPtr o los elementos de path) tiene un recuento de referencias de cero, se liberarán cuando esta función devuelva.

Tcl_FSConvertToPathType intenta convertir el Tcl_Obj dado a un tipo de ruta Tcl válido, teniendo en cuenta que el cwd puede haber cambiado incluso si este valor ya es supuestamente del tipo correcto. El nombre de archivo puede comenzar con "~" (para indicar el directorio principal del usuario actual) o "~<usuario>" (para indicar el directorio principal de cualquier usuario).

Si la conversión tiene éxito (es decir, el valor es una ruta válida en uno de los sistemas de archivos actuales), se devuelve TCL_OK. De lo contrario, se devuelve TCL_ERROR, y se puede dejar un mensaje de error en el intérprete.

Tcl_FSGetInternalRep extrae la representación interna de un valor de ruta dado, en el sistema de archivos dado. Si el valor de ruta pertenece a un sistema de archivos diferente, devolvemos NULL. Si la representación interna es actualmente NULL, intentamos generarla, llamando a Tcl_FSCreateInternalRepProc del sistema de archivos.

Devuelve NULL o una representación de ruta interna válida. Esta representación interna está en caché, de modo que las llamadas repetidas a esta función no requerirán conversiones adicionales.

Tcl_FSGetTranslatedPath intenta extraer la ruta traducida del Tcl_Obj dado.

Si la traducción tiene éxito (es decir, el valor es una ruta válida), se devuelve. De lo contrario, se devolverá NULL, y se puede dejar un mensaje de error en el intérprete. Una ruta "traducida" es aquella que no contiene secuencias "~" o "~usuario" (estas se han expandido a su representación actual en el sistema de archivos). El valor devuelto es propiedad del llamador, que debe almacenarlo o llamar a Tcl_DecrRefCount para asegurar que la memoria se libere. Esta función tiene poco uso práctico, y Tcl_FSGetNormalizedPath o Tcl_FSGetNativePath son funciones que generalmente se usan mejor para la mayoría de los propósitos.

Tcl_FSGetTranslatedStringPath hace lo mismo que Tcl_FSGetTranslatedPath, pero devuelve una cadena de caracteres o NULL. La cadena devuelta se asigna dinámicamente y es propiedad

Tcl_FSGetNormalizedPath o Tcl_FSGetNativePath suelen ser funciones mejores para la mayoría de los propósitos.

Tcl_FSNewNativePath realiza algo parecido a lo inverso de las conversiones habituales obj->path->nativerep. Si algún código recupera una ruta en formato nativo (de, por ejemplo, `readlink` o un diálogo nativo), y esa ruta se va a utilizar a nivel de Tcl, llamar a esta función es una forma eficiente de crear el tipo de valor de ruta adecuado.

El valor resultante es un valor de "ruta" puro, que solo recibirá una representación de cadena UTF-8 si así lo requiere algún código de Tcl.

Tcl_FSGetNativePath es para uso de los sistemas de archivos nativos Win/Unix, de modo que puedan recuperar fácilmente la representación nativa (char* o TCHAR*) de una ruta. Esta función es un envoltorio de conveniencia alrededor de Tcl_FSGetInternalRep. Puede ser deseable en el futuro tener representaciones nativas no basadas en cadenas (por ejemplo, en macOS, una representación que use un FSRef struct de fileSpec sería probablemente más eficiente). En Windows, una representación Unicode completa permitiría rutas de longitud ilimitada. Actualmente, la representación es simplemente una cadena de caracteres que puede contener la ruta relativa o una ruta completa, absoluta y normalizada en la codificación nativa (condiciones complejas dictan cuál de estas se proporcionará, por lo que no se puede confiar en ninguna de ellas, a menos que se sepa que la ruta es absoluta). Si necesita una ruta nativa que deba ser absoluta, entonces debe solicitar la versión nativa de una ruta normalizada. Si por alguna razón se necesita una versión de la ruta que no sea absoluta y no normalizada, esta debe construirse por separado (por ejemplo, utilizando Tcl_FSGetTranslatedPath).

La representación nativa se almacena en caché para que las llamadas repetidas a esta función no requieran conversiones adicionales. El valor de retorno es propiedad de Tcl y tiene una vida útil equivalente a la del pathPtr pasado (a menos que sea una ruta relativa, en cuyo caso la representación nativa puede liberarse en cualquier momento que cambie el cwd).

Tcl_FSFileSystemInfo devuelve una lista de dos elementos. El primer elemento es el nombre del sistema de archivos (por ejemplo, "native", "vfs", "zip", o "prowrap", quizás), y el segundo es el tipo particular de la ruta dada dentro de ese sistema de archivos (que depende del sistema de archivos). El segundo elemento puede estar vacío si el sistema de archivos no proporciona una categorización adicional de archivos.

Se devuelve un valor de lista válido, a menos que el valor de la ruta no sea reconocido, en cuyo caso se devolverá NULL.

Tcl_FSGetFileSystemForPath devuelve un puntero al Tcl_Filesystem que acepta esta ruta como válida.

Si ningún sistema de archivos acepta la ruta, se devuelve NULL.

Tcl_FSGetPathType determina si la ruta dada es relativa al directorio actual, relativa al volumen actual o absoluta.

Devuelve uno de TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE, o TCL_PATH_VOLUME_RELATIVE

LA API DEL SISTEMA DE ARCHIVOS VIRTUAL

Un sistema de archivos proporciona una estructura Tcl_Filesystem que contiene punteros a funciones que implementan las diversas operaciones en un sistema de archivos; estas operaciones se invocan según sea necesario por la capa genérica, lo que generalmente ocurre a través de las funciones enumeradas anteriormente.

Las estructuras Tcl_Filesystem se manipulan utilizando los siguientes métodos.

Tcl_FSRegister toma un puntero a una estructura de sistema de archivos y un dato opcional para asociar con ese sistema de archivos. Al llamar a esta función, Tcl adjuntará el sistema de archivos a la lista de sistemas de archivos conocidos, y se volverá completamente funcional inmediatamente. Tcl no verifica si el mismo sistema de archivos se registra múltiples veces (y en general eso no es algo bueno de hacer). Se devolverá TCL_OK.

Tcl_FSUnregister elimina la estructura de sistema de archivos dada de la lista de sistemas de archivos conocidos, si es que se conoce, y devuelve TCL_OK. Si el sistema de archivos no está actualmente registrado, se devuelve TCL_ERROR.

Tcl_FSData devolverá el clientData asociado con el sistema de archivos dado, si ese sistema de archivos está registrado. De lo contrario, devolverá NULL.

Tcl_FSMountsChanged se utiliza para informar al núcleo de Tcl que el conjunto de puntos de montaje para el sistema de archivos dado (ya registrado) ha cambiado, y que, por lo tanto, las representaciones de archivos almacenadas en caché pueden no ser correctas.

Excepto por los tres primeros campos de esta estructura que contienen elementos de datos simples, todas las entradas contienen direcciones de funciones llamadas por la capa genérica del sistema de archivos para realizar la gama completa de acciones relacionadas con el sistema de archivos.

Las muchas funciones en esta estructura se dividen en tres categorías: funciones de infraestructura (casi todas las cuales deben implementarse), funciones operativas (que deben implementarse si se proporciona un sistema de archivos completo) y funciones de eficiencia (que solo necesitan implementarse si se pueden hacer de manera eficiente, o si tienen efectos secundarios que son requeridos por el sistema de archivos; Tcl tiene emulaciones menos eficientes a las que puede recurrir). Es importante tener en cuenta que, en la versión actual de Tcl, la mayoría de estas dependencias solo se utilizan para manejar comandos iniciados en Tcl, no en C. Lo que esto significa es que, si se emite un comando de `file rename` en Tcl, y el(los) sistema(s) de archivos relevantes no implementan su Tcl_FSRenameFileProc, el núcleo de Tcl recurrirá a una combinación de otras funciones del sistema de archivos (utilizará Tcl_FSCopyFileProc seguido de Tcl_FSDeleteFileProc, y si Tcl_FSCopyFileProc no se implementa, hay una dependencia adicional). Sin embargo, si se emite un comando Tcl_FSRenameFileProc a nivel de C, no ocurre ninguna de estas dependencias. Esto es cierto excepto para las últimas cuatro entradas en la tabla del sistema de archivos (lstat, load, getcwd y chdir) para las cuales sí ocurren dependencias a nivel de C.

Cualquier función que tome nombres de ruta en formato Tcl_Obj toma esos nombres en formato UTF-8. La API de infraestructura del sistema de archivos está diseñada para soportar la conversión eficiente y en caché de estas rutas UTF-8 a otras representaciones nativas.

INFRAESTRUCTURA DEL SISTEMA DE ARCHIVOS

Estos campos contienen información básica sobre la estructura del sistema de archivos y las direcciones de funciones que se utilizan para asociar un sistema de archivos particular con una ruta de archivo y para manejar internamente las representaciones de rutas, por ejemplo, al copiar y liberar dichas representaciones.

NOMBRE_TIPO

El campo typeName contiene una cadena terminada en nulo que identifica el tipo del sistema de archivos implementado, por ejemplo, "nativo", "zip" o "vfs".

LONGITUD_ESTRUCTURA

El campo structureLength generalmente se implementa como sizeof(Tcl_Filesystem), y está ahí para permitir una compatibilidad básica hacia atrás más fácil en binario si el tamaño de la estructura cambia en una versión futura de Tcl.

VERSIÓN

El campo version debe establecerse en TCL_FILESYSTEM_VERSION_1.

PROC_RUTA_EN_SISTEMA_ARCHIVOS

El campo pathInFilesystemProc contiene la dirección de una función que se llama para determinar si un valor de ruta dado pertenece o no a este sistema de archivos. Tcl solo llamará al resto de las funciones del sistema de archivos con una ruta para la cual esta función ha devuelto TCL_OK. Si la ruta no pertenece, se debe devolver -1 (el comportamiento de Tcl para cualquier otro valor de retorno no está definido). Si se devuelve TCL_OK, el parámetro de salida opcional clientDataPtr se puede usar para devolver una representación interna (específica del sistema de archivos) de la ruta, que se almacenará en caché dentro del valor de la ruta y puede ser recuperada eficientemente por las otras funciones del sistema de archivos. Tcl almacenará en caché simultáneamente el hecho de que esta ruta pertenece a este sistema de archivos. Dichas cachés se invalidan cuando se agregan o eliminan estructuras del sistema de archivos de la lista interna de sistemas de archivos conocidos de Tcl.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

PROC_DUPLICAR_REP_INTERNA

Esta función crea una copia de la representación interna de una ruta y se llama cuando Tcl necesita duplicar un valor de ruta. Si es NULL, Tcl simplemente no copiará la representación interna, que luego puede ser necesario regenerar más tarde.

typedef ClientData Tcl_FSDupInternalRepProc(
        ClientData clientData);

PROC_LIBERAR_REP_INTERNA

Libera la representación interna. Esto debe implementarse si las representaciones internas necesitan ser liberadas (es decir, si se asigna memoria cuando se genera una representación interna), pero de lo contrario puede ser NULL.

typedef void Tcl_FSFreeInternalRepProc(
        ClientData clientData);

PROC_INTERNO_A_NORMALIZADO

Función para convertir la representación interna a una ruta normalizada. Solo se requiere si el sistema de archivos crea valores de ruta puros sin representación de cadena/ruta. El valor de retorno es un valor de Tcl cuya representación de cadena es la ruta normalizada.

typedef Tcl_Obj *Tcl_FSInternalToNormalizedProc(
        ClientData clientData);

PROC_CREAR_REP_INTERNA

Función para tomar un valor de ruta, calcular una representación interna para él y almacenar esa representación nativa en el valor. Puede ser NULL si las rutas no tienen representación interna, o si Tcl_FSPathInFilesystemProc para este sistema de archivos siempre crea inmediatamente una representación interna para las rutas que acepta.

typedef ClientData Tcl_FSCreateInternalRepProc(
        Tcl_Obj *pathPtr);

PROC_NORMALIZAR_RUTA

Función para normalizar una ruta. Debe implementarse para todos los sistemas de archivos que puedan tener múltiples representaciones de cadena para el mismo valor de ruta. En Tcl, cada "ruta" debe tener una única representación de cadena "normalizada". Dependiendo del sistema de archivos, puede haber más de una representación de cadena no normalizada que se refiera a esa ruta (por ejemplo, una ruta relativa, una ruta con mayúsculas y minúsculas diferentes si el sistema de archivos no distingue entre mayúsculas y minúsculas, una ruta que contenga una referencia a un directorio de inicio como "~", una ruta que contenga enlaces simbólicos, etc.). Si el último componente de la ruta es un enlace simbólico, no debe convertirse en el valor al que apunta (pero su mayúscula u otros aspectos deben hacerse únicos). Todos los demás componentes de la ruta deben convertirse desde enlaces simbólicos. Esta única excepción es necesaria para coincidir con la semántica de Tcl con file delete, file rename, file copy operando sobre enlaces simbólicos. Esta función puede ser llamada con nextCheckpoint al principio de la ruta (es decir, cero), al final de la ruta o en cualquier separador de archivo intermedio en la ruta. Nunca apuntará a ninguna otra posición arbitraria en la ruta. En el último de los tres casos válidos, la implementación puede asumir que la ruta hasta e incluyendo el separador de archivo se conoce y se normaliza.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

OPERACIONES DEL SISTEMA DE ARCHIVOS

Los campos de esta sección de la estructura contienen las direcciones de las funciones que se llaman para realizar las operaciones básicas del sistema de archivos. Un sistema de archivos que se espera que se use con el conjunto completo de comandos estándar de Tcl debe implementar todas estas. Si algunas de ellas no se implementan, ciertos comandos de Tcl pueden fallar al operar en rutas dentro de ese sistema de archivos. Sin embargo, en algunos casos esto puede ser deseable (por ejemplo, un sistema de archivos de solo lectura no debería implementar las últimas cuatro funciones, y un sistema de archivos que no admite enlaces simbólicos no necesita implementar la función readlink, etc. El núcleo de Tcl espera que los sistemas de archivos se comporten de esta manera).

PROC_TIPO_RUTA_SISTEMA_ARCHIVOS

Función para determinar el tipo de una ruta en este sistema de archivos. Puede ser NULL, en cuyo caso no habrá información de tipo disponible para los usuarios del sistema de archivos. El "tipo" se usa solo con fines informativos y debe devolverse como la representación de cadena del Tcl_Obj que se devuelve. Un valor de retorno típico podría ser "networked", "zip" o "ftp". El resultado Tcl_Obj pertenece al sistema de archivos, por lo que Tcl incrementará el recuento de referencias de ese valor si desea conservar una referencia a él.

typedef Tcl_Obj *Tcl_FSFilesystemPathTypeProc(
        Tcl_Obj *pathPtr);

PROC_SEPARADOR_SISTEMA_ARCHIVOS

Función para devolver los caracteres separadores de este sistema de archivos. Esto solo debe implementarse si el sistema de archivos desea usar un separador diferente al de la cadena estándar "/". Entre otros usos, es devuelto por el comando file separator. El valor de retorno debe ser un valor con recuento de referencias cero.

typedef Tcl_Obj *Tcl_FSFilesystemSeparatorProc(
        Tcl_Obj *pathPtr);

PROC_STAT

Función para procesar una llamada Tcl_FSStat. Debe implementarse para cualquier sistema de archivos razonable, ya que muchos comandos a nivel de Tcl dependen crucialmente de él (por ejemplo, file atime, file isdirectory, file size, glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

El Tcl_FSStatProc llena la estructura stat statPtr con información sobre el archivo especificado. No necesita ningún derecho de acceso al archivo para obtener esta información, pero necesita derechos de búsqueda a todos los directorios nombrados en la ruta que conduce al archivo. La estructura stat incluye información sobre el dispositivo, inodo (siempre 0 en Windows), modo de privilegios, nlink (siempre 1 en Windows), id de usuario (siempre 0 en Windows), id de grupo (siempre 0 en Windows), rdev (igual que el dispositivo en Windows), tamaño, tiempo del último acceso, tiempo de la última modificación y tiempo del último cambio de metadatos.

Si el archivo representado por pathPtr existe, el Tcl_FSStatProc devuelve 0 y la estructura stat se llena con datos. De lo contrario, se devuelve -1 y no se proporciona información de stat.

PROC_ACCESO

Función para procesar una llamada Tcl_FSAccess. Debe implementarse para cualquier sistema de archivos razonable, ya que muchos comandos a nivel de Tcl dependen crucialmente de él (por ejemplo, file exists, file readable).

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

LECHANNELPROC

Función para procesar una llamada a Tcl_FSOpenFileChannel. Debe ser implementada para cualquier sistema de archivos razonable, ya que cualquier operación que requiera abrir o acceder al contenido de un archivo la utilizará (por ejemplo, open, encoding y muchos comandos de Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

Tcl_FSOpenFileChannelProc abre un archivo especificado por pathPtr y devuelve un manejador de canal que se puede utilizar para realizar operaciones de entrada y salida en el archivo. Esta API está modelada a partir del procedimiento fopen de la biblioteca estándar de E/S de Unix. La sintaxis y el significado de todos los argumentos son similares a los proporcionados en el comando open de Tcl al abrir un archivo, donde el argumento mode es una combinación de las banderas POSIX O_RDONLY, O_WRONLY, etc. Si ocurre un error al abrir el canal, Tcl_FSOpenFileChannelProc devuelve NULL y registra un código de error POSIX que se puede recuperar con Tcl_GetErrno. Además, si interp no es NULL, Tcl_FSOpenFileChannelProc deja un mensaje de error en el resultado de interp después de cualquier error.

El nuevo canal creado no debe ser registrado en el intérprete proporcionado por un Tcl_FSOpenFileChannelProc; esa tarea corresponde al llamador de Tcl_FSOpenFileChannel (si es necesario). Si uno de los canales estándar, stdin, stdout o stderr se cerró previamente, el acto de crear el nuevo canal también lo asigna como reemplazo del canal estándar.

MATCHINDIRECTORYPROC

Función para procesar una llamada a Tcl_FSMatchInDirectory. Si no se implementa, la funcionalidad de glob y copia recursiva faltará en el sistema de archivos (y esto puede afectar a comandos como encoding names que utilizan la funcionalidad de glob internamente).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La función debe devolver todos los archivos o directorios (u otros objetos del sistema de archivos) que coincidan con el patrón dado y concuerden con la especificación de types proporcionada. Hay dos formas en las que esta función puede ser llamada. Si pattern es NULL, entonces pathPtr es una especificación de ruta completa de un solo archivo o directorio que debe ser verificado en cuanto a su existencia y tipo correcto. De lo contrario, pathPtr es un directorio, cuyo contenido la función debe buscar archivos o directorios del tipo correcto. En cualquier caso, se puede asumir que pathPtr no es NULL y no está vacío. Actualmente no está documentado si pathPtr tendrá o no un separador de archivo al final, por lo que el código debe ser flexible a ambas posibilidades.

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso de coincidencia. Los mensajes de error se colocan en interp, a menos que interp sea NULL, en cuyo caso no es necesario generar ningún mensaje de error; en un resultado TCL_OK, los resultados deben agregarse al valor resultPtr proporcionado (que se puede asumir que es una lista Tcl válida y no compartida). Las coincidencias agregadas a resultPtr deben incluir cualquier prefijo de ruta dado en pathPtr (esto generalmente significa que serán especificaciones de ruta absoluta). Tenga en cuenta que si no se encuentran coincidencias, eso simplemente conduce a un resultado vacío; los errores solo se señalan para problemas reales del archivo o del sistema de archivos que puedan ocurrir durante el proceso de coincidencia.

La estructura Tcl_GlobTypeData pasada en el parámetro types contiene los siguientes campos:

typedef struct Tcl_GlobTypeData {
    /* Corresponde a bcdpfls como en 'find -t' */
    int type;
    /* Corresponde a los permisos de archivo */
    int perm;
    /* Tipo de Mac aceptable */
    Tcl_Obj *macType;
    /* Creador de Mac aceptable */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Hay dos casos específicos que es importante manejar correctamente, ambos cuando types no es NULL. Los dos casos son cuando types->types & TCL_GLOB_TYPE_DIR o types->types & TCL_GLOB_TYPE_MOUNT son verdaderos (y en particular cuando las otras banderas son falsas). En el primero de estos casos, la función debe listar los directorios contenidos. Tcl utiliza esto para implementar el globbing recursivo, por lo que es fundamental que los sistemas de archivos implementen la coincidencia de directorios correctamente. En el segundo de estos casos, con TCL_GLOB_TYPE_MOUNT, el sistema de archivos debe listar los puntos de montaje que se encuentran dentro del pathPtr dado (y en este caso, pathPtr no tiene por qué estar dentro del mismo sistema de archivos, a diferencia de todos los demás casos en los que se llama a esta función). El soporte para esto es fundamental si Tcl quiere tener transiciones fluidas de un sistema de archivos a otro.

UTIMEPROC

Función para procesar una llamada a Tcl_FSUtime. Requerida para permitir el establecimiento (no la lectura) de tiempos con file mtime, file atime y la implementación open-r/open-w/fcopy de file copy.

        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

Los tiempos de acceso y modificación del archivo especificado por pathPtr deben cambiarse a los valores dados en la estructura tval.

El valor de retorno debe ser 0 en caso de éxito y -1 en caso de error, al igual que con la llamada al sistema utime.

LINKPROC

Función para procesar una llamada a Tcl_FSLink. Debe implementarse solo si el sistema de archivos admite enlaces, y de lo contrario puede ser NULL.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

Si toPtr es NULL, se le pide a la función que lea el contenido de un enlace. El resultado es un Tcl_Obj que especifica el contenido del enlace dado por linkNamePtr, o NULL si el enlace no pudo ser leído. El resultado es propiedad del llamador (y por lo tanto, su contador de referencias debe ser incrementado antes de ser devuelto). Cualquier llamador debe llamar a Tcl_DecrRefCount en este resultado cuando ya no sea necesario. Si toPtr no es NULL, la función debe intentar crear un enlace. El resultado en este caso debe ser toPtr si el enlace fue exitoso y NULL en caso contrario. En este caso, el resultado no es propiedad del llamador (es decir, no se necesitan manipulaciones de contador de referencias en ninguno de los extremos). Consulte la documentación de Tcl_FSLink para la interpretación correcta de las banderas linkAction.

LISTVOLUMESPROC

Función para listar los volúmenes del sistema de archivos agregados por este sistema de archivos. Debe implementarse solo si el sistema de archivos agrega volúmenes al principio del sistema de archivos, para que puedan ser devueltos por file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

El resultado debe ser una lista de volúmenes agregados por este sistema de archivos, o NULL (o una lista vacía) si no se proporcionan volúmenes. Se considera que el valor de resultado es propiedad del sistema de archivos (no del núcleo de Tcl), pero se le debe dar un contador de referencias para Tcl. Tcl utilizará el contenido de la lista y luego decrementará ese contador de referencias. Esto permite a los sistemas de archivos elegir si realmente desean conservar una lista "global" de volúmenes o no (si no, generan la lista sobre la marcha y se la pasan a Tcl con un contador de referencias de 1 y luego olvidan la lista; si sí, simplemente incrementan el contador de referencias de su lista global y se la pasan a Tcl, que copiará el contenido y luego decrementará el contador a su valor anterior).

Por lo tanto, Tcl considera que los valores de retorno de este proc son de solo lectura.

        Tcl_Obj **objPtrRef);

La función llamada puede devolver un array de cadenas o puede devolver NULL y colocar una lista Tcl en objPtrRef. Tcl tomará esa lista y primero incrementará su contador de referencias antes de usarla. Al finalizar ese uso, Tcl decrementará su contador de referencias. Por lo tanto, si la lista debe ser eliminada por Tcl cuando termine, debe tener un contador de referencias de cero, y si la lista no debe ser eliminada, el sistema de archivos debe asegurarse de devolver un valor con un contador de referencias de al menos uno.

FILEATTRSGETPROC

Función para procesar una llamada a Tcl_FSFileAttrsGet, utilizada por file attributes.

        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

Devuelve un código de retorno estándar de Tcl. El valor del atributo recuperado, que corresponde al elemento con el índice index en la lista devuelta por Tcl_FSFileAttrStringsProc, es un Tcl_Obj colocado en objPtrRef (si se devolvió TCL_OK) y es probable que tenga un contador de referencias de cero. En cualquier caso, debemos almacenarlo en algún lugar (por ejemplo, el resultado de Tcl) o incrementar/decrementar su contador de referencias para asegurar que se libere correctamente.

FILEATTRSSETPROC

Función para procesar una llamada a Tcl_FSFileAttrsSet, utilizada por file attributes. Si el sistema de archivos es de solo lectura, no es necesario implementarlo.

        Tcl_Obj *objPtr);

El valor del atributo del elemento con el índice index en la lista devuelta por Tcl_FSFileAttrStringsProc debe establecerse en el objPtr proporcionado.

DESCRIPTION

The Tcl filesystem interface provides a mechanism for managing filesystems that are not native to the operating system. This is useful for implementing things like zip archive access, or other virtual filesystems. This documentation describes the required and optional callback procedures that may be implemented by a filesystem package.

FILESYSTEM OPERATIONS

These functions are the core filesystem operations. Most filesystems will need to implement all of these.

STATPROC

Function to process a Tcl_FSStat call. If not implemented, Tcl will signal an error like "permission denied".

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

The behavior of this function is very similar to that of the standard Unix stat system call. It fills the structure pointed to by statPtr with information about the file or directory specified by pathPtr. It returns a standard Tcl result indicating success or failure.

OPENDIRPROC

Function to process a Tcl_FSOpenDir call. If not implemented, Tcl will signal an error like "permission denied".

typedef Tcl_DirHandle *
Tcl_FSOpenDirProc(
        Tcl_Obj *pathPtr,
        Tcl_Interp *interp);

This function should open the directory specified by pathPtr and return a pointer to a Tcl_DirHandle structure that can be used in subsequent calls to Tcl_FSDirNext and Tcl_FSCloseDir. If an error occurs, it should leave an error message in the interpreter's result and return NULL.

DIRENTRYPROC

Function to process a Tcl_FSDirNext call. If not implemented, Tcl will signal an error like "permission denied".

typedef Tcl_Obj *
Tcl_FSDirEntryProc(
        Tcl_DirHandle *dirHandle,
        Tcl_Interp *interp);

This function should return the next entry in the directory stream represented by dirHandle, or NULL if there are no more entries. The entry should be returned as a new Tcl object.

CLOSEDIRPROC

Function to process a Tcl_FSCloseDir call. If not implemented, Tcl will signal an error like "permission denied".

typedef int
Tcl_FSCloseDirProc(
        Tcl_DirHandle *dirHandle,
        Tcl_Interp *interp);

This function should close the directory stream represented by dirHandle and free any associated resources. It should return a standard Tcl result indicating success or failure.

CREATEDIRECTORYPROC

Function to process a Tcl_FSCreateDirectory call. Should be implemented unless the FS is read-only.

typedef int Tcl_FSCreateDirectoryProc(
        Tcl_Obj *pathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, a new directory should have been added to the filesystem in the location specified by pathPtr.

REMOVEDIRECTORYPROC

Function to process a Tcl_FSRemoveDirectory call. Should be implemented unless the FS is read-only.

typedef int Tcl_FSRemoveDirectoryProc(
        Tcl_Obj *pathPtr,
        int recursive,
        Tcl_Obj **errorPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, the directory specified by pathPtr should have been removed from the filesystem. If the recursive flag is given, then a non-empty directory should be deleted without error. If this flag is not given, then and the directory is non-empty a POSIX “EEXIST” error should be signaled. If an error does occur, the name of the file or directory which caused the error should be placed in errorPtr.

DELETEFILEPROC

Function to process a Tcl_FSDeleteFile call. Should be implemented unless the FS is read-only.

typedef int Tcl_FSDeleteFileProc(
        Tcl_Obj *pathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, the file specified by pathPtr should have been removed from the filesystem. Note that, if the filesystem supports symbolic links, Tcl will always call this function and not Tcl_FSRemoveDirectoryProc when needed to delete them (even if they are symbolic links to directories).

FILESYSTEM EFFICIENCY

These functions need not be implemented for a particular filesystem because the core has a fallback implementation available. See each individual description for the consequences of leaving the field NULL.

LSTATPROC

Function to process a Tcl_FSLstat call. If not implemented, Tcl will attempt to use the statProc defined above instead. Therefore it need only be implemented if a filesystem can differentiate between stat and lstat calls.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

The behavior of this function is very similar to that of the Tcl_FSStatProc defined above, except that if it is applied to a symbolic link, it returns information about the link, not about the target file.

COPYFILEPROC

Function to process a Tcl_FSCopyFile call. If not implemented Tcl will fall back on open-r, open-w and fcopy as a copying mechanism. Therefore it need only be implemented if the filesystem can perform that action more efficiently.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the copying process. Note that, destPathPtr is the name of the file which should become the copy of srcPathPtr. It is never the name of a directory into which srcPathPtr could be copied (i.e. the function is much simpler than the Tcl level file copy subcommand). Note that, if the filesystem supports symbolic links, Tcl will always call this function and not copyDirectoryProc when needed to copy them (even if they are symbolic links to directories). Finally, if the filesystem determines it cannot support the file copy action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

RENAMEFILEPROC

Function to process a Tcl_FSRenameFile call. If not implemented, Tcl will fall back on a copy and delete mechanism. Therefore it need only be implemented if the filesystem can perform that action more efficiently.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the renaming process. If the filesystem determines it cannot support the file rename action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

COPYDIRECTORYPROC

Function to process a Tcl_FSCopyDirectory call. If not implemented, Tcl will fall back on a recursive file mkdir, file copy mechanism. Therefore it need only be implemented if the filesystem can perform that action more efficiently.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

The return value is a standard Tcl result indicating whether an error occurred in the copying process. If an error does occur, the name of the file or directory which caused the error should be placed in errorPtr. Note that, destPathPtr is the name of the directory-name which should become the mirror-image of srcPathPtr. It is not the name of a directory into which srcPathPtr should be copied (i.e. the function is much simpler than the Tcl level file copy subcommand). Finally, if the filesystem determines it cannot support the directory copy action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

LOADFILEPROC

Function to process a Tcl_FSLoadFile call. If not implemented, Tcl will fall back on a copy to native-temp followed by a Tcl_FSLoadFile on that temporary copy. Therefore it need only be implemented if the filesystem can load code directly, or it can be implemented simply to return TCL_ERROR to disable load functionality in this filesystem entirely.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Returns a standard Tcl completion code. If an error occurs, an error message is left in the interp's result. The function dynamically loads a binary code file into memory. On a successful load, the handlePtr should be filled with a token for the dynamically loaded file, and the unloadProcPtr should be filled in with the address of a procedure. The unload procedure will be called with the given Tcl_LoadHandle as its only parameter when Tcl needs to unload the file. For example, for the native filesystem, the Tcl_LoadHandle returned is currently a token which can be used in the private TclpFindSymbol to access functions in the new code. Each filesystem is free to define the Tcl_LoadHandle as it requires. Finally, if the filesystem determines it cannot support the file load action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

UNLOADFILEPROC

Function to unload a previously successfully loaded file. If load was implemented, then this should also be implemented, if there is any cleanup action required.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

Function to process a Tcl_FSGetCwd call. Most filesystems need not implement this. It will usually only be called once, if getcwd is called before chdir. May be NULL.

typedef Tcl_Obj *
Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

If the filesystem supports a native notion of a current working directory (which might perhaps change independent of Tcl), this function should return that cwd as the result, or NULL if the current directory could not be determined (e.g. the user does not have appropriate permissions on the cwd directory). If NULL is returned, an error message is left in the interp's result.

CHDIRPROC

Function to process a Tcl_FSChdir call. If filesystems do not implement this, it will be emulated by a series of directory access checks. Otherwise, virtual filesystems which do implement it need only respond with a positive return result if the pathPtr is a valid, accessible directory in their filesystem. They need not remember the result, since that will be automatically remembered for use by Tcl_FSGetCwd. Real filesystems should carry out the correct action (i.e. call the correct system chdir API).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

The Tcl_FSChdirProc changes the applications current working directory to the value specified in pathPtr. The function returns -1 on error or 0 on success.
