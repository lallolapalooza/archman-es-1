ARGUMENTOS

Tcl_EventSetupProc *setupProc (in)
Procedimiento a invocar para preparar la espera de eventos en Tcl_DoOneEvent.
Tcl_EventCheckProc *checkProc (in)
Procedimiento que Tcl_DoOneEvent invocará después de esperar eventos. Comprueba si han ocurrido eventos y, si es así, los pone en cola.
ClientData clientData (in)
Valor arbitrario de una palabra que se pasará a setupProc, checkProc, o deleteProc.
const Tcl_Time *timePtr (in)
Indica la cantidad máxima de tiempo a esperar por un evento. Se especifica como un intervalo (cuánto esperar), no como un tiempo absoluto (cuándo despertar). Si el puntero pasado a Tcl_WaitForEvent es NULL, significa que no hay tiempo máximo de espera: esperar para siempre si es necesario.
Tcl_Event *evPtr (in)
Un evento a añadir a la cola de eventos. El almacenamiento para el evento debe haber sido asignado por el llamador usando Tcl_Alloc o ckalloc.
Tcl_QueuePosition position (in)
Dónde añadir el nuevo evento en la cola: TCL_QUEUE_TAIL, TCL_QUEUE_HEAD, o TCL_QUEUE_MARK.
Tcl_ThreadId threadId (in)
Un identificador único para un hilo.
Tcl_EventDeleteProc *deleteProc (in)
Procedimiento a invocar para cada evento en cola en Tcl_DeleteEvents.
int flags (in)
Qué tipos de eventos deben ser atendidos. Estas banderas son las mismas que las pasadas a Tcl_DoOneEvent.
int mode (in)
Indica si los eventos deben ser atendidos por Tcl_ServiceAll. Debe ser uno de TCL_SERVICE_NONE o TCL_SERVICE_ALL.
Tcl_NotifierProcs* notifierProcPtr (in)
Estructura de punteros a funciones que describen procedimientos de notificación que reemplazarán a los instalados en el ejecutable. Ver REEMPLAZANDO EL NOTIFICADOR para más detalles.

INTRODUCCIÓN

Las interfaces descritas aquí se utilizan para personalizar el bucle de eventos de Tcl. Las dos personalizaciones más comunes son añadir nuevas fuentes de eventos y fusionar el bucle de eventos de Tcl con algún otro bucle de eventos, como uno proporcionado por una aplicación en la que Tcl está incrustado. Cada una de estas tareas se describe en una sección separada a continuación.

Los procedimientos de esta entrada del manual son los bloques de construcción con los que se construye el notificador de eventos de Tcl. El notificador de eventos es la capa más baja en el mecanismo de eventos de Tcl. Consta de tres cosas:

[1]
Fuentes de eventos: estas representan las formas en que se pueden generar eventos. Por ejemplo, hay una fuente de eventos de temporizador que implementa el procedimiento Tcl_CreateTimerHandler y el comando after, y hay una fuente de eventos de archivo que implementa el procedimiento Tcl_CreateFileHandler en sistemas Unix. Una fuente de eventos debe trabajar con el notificador para detectar eventos en los momentos adecuados, registrarlos en la cola de eventos y, eventualmente, notificar al software de nivel superior que han ocurrido. Los procedimientos Tcl_CreateEventSource, Tcl_DeleteEventSource, Tcl_SetMaxBlockTime, Tcl_QueueEvent y Tcl_DeleteEvents son utilizados principalmente por las fuentes de eventos.
[2]
La cola de eventos: para aplicaciones sin hilos, hay una única cola para toda la aplicación, que contiene eventos que han sido detectados pero aún no atendidos. Las fuentes de eventos colocan eventos en la cola para que puedan procesarse en orden en momentos apropiados durante el bucle de eventos. La cola de eventos garantiza una disciplina justa de manejo de eventos, de modo que ninguna fuente de eventos pueda dejar sin servicio a las demás. También permite que los eventos se guarden para ser atendidos en un momento futuro. Las aplicaciones con hilos funcionan de manera similar, excepto que hay una cola de eventos separada para cada hilo que contiene un intérprete de Tcl. Tcl_QueueEvent se utiliza (principalmente por las fuentes de eventos) para añadir eventos a la cola de eventos y Tcl_DeleteEvents se utiliza para eliminar eventos de la cola sin procesarlos. En una aplicación con hilos, Tcl_QueueEvent añade un evento a la cola del hilo actual, y Tcl_ThreadQueueEvent añade un evento a una cola en un hilo específico.
[3]
El bucle de eventos: para detectar y procesar eventos, la aplicación entra en un bucle que espera a que ocurran eventos, los coloca en la cola de eventos y luego los procesa. La mayoría de las aplicaciones harán esto llamando al procedimiento Tcl_DoOneEvent, que se describe en una entrada de manual separada.

La mayoría de las aplicaciones de Tcl no necesitan preocuparse por ninguno de los detalles internos del notificador de Tcl. Sin embargo, el notificador ahora tiene suficiente flexibilidad para ser reorientado ya sea para una nueva plataforma o para utilizar un bucle de eventos externo (como el bucle de eventos de Motif, cuando Tcl está incrustado en una aplicación de Motif). Los procedimientos Tcl_WaitForEvent y Tcl_SetTimer son normalmente implementados por Tcl, pero pueden ser reemplazados por nuevas versiones para reorientar el notificador (los procedimientos Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_Sleep, Tcl_CreateFileHandler y Tcl_DeleteFileHandler también deben ser reemplazados; ver CREANDO UN NUEVO NOTIFICADOR a continuación para más detalles). Los procedimientos Tcl_ServiceAll, Tcl_ServiceEvent, Tcl_GetServiceMode y Tcl_SetServiceMode se proporcionan para ayudar a conectar el bucle de eventos de Tcl con un bucle de eventos externo como el de Motif.

BÁSICOS DEL NOTIFICADOR

La forma más fácil de entender cómo funciona el notificador es considerar lo que sucede cuando se llama a Tcl_DoOneEvent. Tcl_DoOneEvent recibe un argumento flags que indica qué tipo de eventos están permitidos procesar y también si debe bloquearse o no si no hay eventos listos. Tcl_DoOneEvent realiza las siguientes acciones:

[1]
Comprueba la cola de eventos para ver si contiene algún evento que pueda ser atendido. Si es así, atiende el primer evento posible, lo elimina de la cola y regresa. Lo hace llamando a Tcl_ServiceEvent y pasando el argumento flags.
[2]
Se prepara para bloquear por un evento. Para ello, Tcl_DoOneEvent invoca un procedimiento de configuración en cada fuente de eventos. La fuente de eventos realizará inicializaciones específicas de la fuente de eventos y posiblemente llamará a Tcl_SetMaxBlockTime para limitar cuánto tiempo bloqueará Tcl_WaitForEvent si no ocurren nuevos eventos.
[3]
Llama a Tcl_WaitForEvent. Este procedimiento se implementa de forma diferente en distintas plataformas; espera a que ocurra un evento, basándose en la información proporcionada por las fuentes de eventos. Puede hacer que la aplicación se bloquee si timePtr especifica un intervalo distinto de 0. Tcl_WaitForEvent regresa cuando algo ha sucedido, como que un archivo se ha vuelto legible o el intervalo dado por timePtr ha expirado. Si no hay eventos para que Tcl_WaitForEvent espere, por lo que se bloquearía para siempre, entonces regresa inmediatamente y Tcl_DoOneEvent regresa 0.
[4]
Llama a un procedimiento de verificación en cada fuente de eventos. El procedimiento de verificación determina si ocurrieron eventos de interés para esta fuente. Si es así, los eventos se añaden a la cola de eventos.
[5]

TAREA DE LA FUENTE DE EVENTOS

Un origen de eventos tiene tres procedimientos que son invocados por el notificador, más procedimientos C adicionales que son invocados por código de nivel superior para organizar callbacks dirigidos por eventos. Los tres procedimientos llamados por el notificador consisten en los procedimientos de configuración y comprobación descritos anteriormente, más un procedimiento adicional que se invoca cuando un evento se elimina de la cola de eventos para su servicio.

El procedimiento Tcl_CreateEventSource crea un nuevo origen de eventos. Sus argumentos especifican el procedimiento de configuración y el procedimiento de comprobación para el origen de eventos. SetupProc debe coincidir con el siguiente prototipo:

typedef void Tcl_EventSetupProc(
        ClientData clientData,
        int flags);

El argumento clientData será el mismo que el argumento clientData para Tcl_CreateEventSource; típicamente se usa para apuntar a información privada gestionada por el origen de eventos. El argumento flags será el mismo que el argumento flags pasado a Tcl_DoOneEvent excepto que nunca será 0 (Tcl_DoOneEvent reemplaza 0 con TCL_ALL_EVENTS). Flags indica qué tipos de eventos deben considerarse; si el bit correspondiente a este origen de eventos no está establecido, el origen de eventos debe devolver inmediatamente sin hacer nada. Por ejemplo, el origen de eventos de archivo comprueba el bit TCL_FILE_EVENTS.

La tarea de SetupProc es asegurarse de que la aplicación se despierte cuando ocurran eventos del tipo deseado. Esto se hace típicamente de una manera dependiente de la plataforma. Por ejemplo, en Unix un origen de eventos podría llamar a Tcl_CreateFileHandler; en Windows podría solicitar notificación con un evento de Windows. Para orígenes de eventos impulsados por temporizadores, como eventos de temporizador o cualquier evento sondeado, el origen de eventos puede llamar a Tcl_SetMaxBlockTime para forzar a la aplicación a despertarse después de un tiempo especificado incluso si no han ocurrido eventos. Si ningún origen de eventos llama a Tcl_SetMaxBlockTime entonces Tcl_WaitForEvent esperará tanto como sea necesario para que ocurra un evento; de lo contrario, solo esperará durante el intervalo más corto pasado a Tcl_SetMaxBlockTime por uno de los orígenes de eventos. Si un origen de eventos sabe que ya tiene eventos listos para informar, puede solicitar un tiempo de bloqueo máximo de cero. Por ejemplo, el procedimiento de configuración para el origen de eventos X busca para ver si ya hay eventos en cola. Si los hay, llama a Tcl_SetMaxBlockTime con un tiempo de bloqueo de 0 para que Tcl_WaitForEvent no se bloquee si no hay nuevos datos en la conexión X. El argumento timePtr a Tcl_WaitForEvent apunta a una estructura que describe un intervalo de tiempo en segundos y microsegundos:

typedef struct Tcl_Time {
    long sec;
    long usec;
} Tcl_Time;

El campo usec debe ser menor que 1000000.

La información proporcionada a Tcl_SetMaxBlockTime solo se utiliza para la próxima llamada a Tcl_WaitForEvent; se descarta después de que Tcl_WaitForEvent regrese. La próxima vez que se realice una espera de eventos, se llamará a los procedimientos de configuración de cada uno de los orígenes de eventos, y estos podrán especificar nueva información para esa espera de eventos.

Si la aplicación utiliza un bucle de eventos externo en lugar de Tcl_DoOneEvent, los orígenes de eventos pueden necesitar llamar a Tcl_SetMaxBlockTime en otros momentos. Por ejemplo, si se registra un nuevo manejador de eventos que necesita sondear eventos, el origen de eventos puede llamar a Tcl_SetMaxBlockTime para establecer el tiempo de bloqueo en cero para forzar al bucle de eventos externo a llamar a Tcl. En este caso, Tcl_SetMaxBlockTime invoca Tcl_SetTimer con el intervalo más corto visto desde la última llamada a Tcl_DoOneEvent o Tcl_ServiceAll.

Además del procedimiento genérico Tcl_SetMaxBlockTime, pueden estar disponibles otros procedimientos específicos de la plataforma para setupProc, si hay información adicional necesaria para Tcl_WaitForEvent en esa plataforma. Por ejemplo, en sistemas Unix se puede utilizar la interfaz Tcl_CreateFileHandler para esperar eventos de archivo.

El segundo procedimiento proporcionado por cada origen de eventos es su procedimiento de comprobación, indicado por el argumento checkProc a Tcl_CreateEventSource. CheckProc debe coincidir con el siguiente prototipo:

typedef void Tcl_EventCheckProc(
        ClientData clientData,
        int flags);

Los argumentos para este procedimiento son los mismos que los de setupProc. CheckProc es invocado por Tcl_DoOneEvent después de haber esperado eventos. Presumiblemente al menos un origen de eventos está ahora preparado para poner un evento en cola. Tcl_DoOneEvent llama a cada uno de los orígenes de eventos en turno, para que todos tengan la oportunidad de poner en cola los eventos que estén listos. El procedimiento de comprobación hace dos cosas. Primero, debe ver si algún evento se ha activado. Diferentes orígenes de eventos hacen esto de diferentes maneras.

Si el procedimiento de comprobación de un origen de eventos detecta un evento interesante, debe añadir el evento a la cola de eventos de Tcl. Para hacer esto, el origen de eventos llama a Tcl_QueueEvent. El argumento evPtr es un puntero a una estructura asignada dinámicamente que contiene el evento (ver más abajo para más información sobre problemas de gestión de memoria). Cada origen de eventos puede definir su propia estructura de eventos con la información que sea relevante para ese origen de eventos. Sin embargo, el primer elemento de la estructura debe ser una estructura de tipo Tcl_Event, y la dirección de esta estructura se utiliza al comunicarse entre el origen de eventos y el resto del notificador. Un Tcl_Event tiene la siguiente definición:

typedef struct {
    Tcl_EventProc *proc;
    struct Tcl_Event *nextPtr;
} Tcl_Event;

El origen de eventos debe rellenar el campo proc del evento antes de llamar a Tcl_QueueEvent. El nextPtr se utiliza para enlazar los eventos en la cola y no debe ser modificado por el origen de eventos.

Se puede añadir un evento a la cola en cualquiera de tres posiciones, dependiendo del argumento position de Tcl_QueueEvent:

TCL_QUEUE_TAIL
Añadir el evento al final de la cola, para que todos los demás eventos pendientes se atiendan primero. Este es casi siempre el lugar correcto para eventos nuevos.
TCL_QUEUE_HEAD
Añadir el evento al principio de la cola, para que se atienda antes que todos los demás eventos en cola.
TCL_QUEUE_MARK
Añadir el evento al principio de la cola, a menos que haya otros eventos al principio cuya posición sea TCL_QUEUE_MARK; en caso afirmativo, añadir el nuevo evento justo después de todos los demás eventos TCL_QUEUE_MARK. Este valor de position se utiliza para insertar una secuencia ordenada de eventos al principio de la cola, como una serie de eventos Enter y Leave sintetizados durante una operación de agarre o desagarre en Tk.

Cuando sea el momento de manejar un evento de la cola (pasos 1 y 4 anteriormente) Tcl_ServiceEvent invocará el proc especificado en la primera estructura Tcl_Event en cola. Proc debe coincidir con el siguiente prototipo:

typedef int Tcl_EventProc(
        Tcl_Event *evPtr,
        int flags);

El primer argumento a proc es un puntero al evento, que será el mismo que el primer argumento a la llamada Tcl_QueueEvent que añadió el evento a la cola. El segundo argumento a proc es el argumento flags para la llamada actual a Tcl_ServiceEvent; esto es usado por el origen de eventos para devolver inmediatamente si sus eventos no son relevantes.

Le corresponde a proc manejar el evento, típicamente invocando uno o más comandos de Tcl o callbacks a nivel C. Una vez que el origen de eventos ha terminado de manejar el evento, devuelve 1 para indicar que el evento puede ser eliminado de la cola. Si por alguna razón el origen de eventos decide que el evento no puede ser manejado en este momento, puede devolver 0 para indicar que el evento debe ser diferido para su procesamiento posterior; en este caso Tcl_ServiceEvent pasará al siguiente evento en la cola e intentará atenderlo. Hay varias razones por las que un origen de eventos podría diferir un evento. Una posibilidad es que los eventos de este tipo estén excluidos por el argumento flags. Por ejemplo, el origen de eventos de archivo siempre devolverá 0 si el bit TCL_FILE_EVENTS no está establecido en flags. Otro ejemplo de diferimiento de eventos ocurre en Tk si se ha invocado Tk_RestrictEvents para diferir ciertos tipos de eventos de ventana.

Cuando proc devuelve 1, Tcl_ServiceEvent eliminará el evento de la cola de eventos y liberará su almacenamiento. Tenga en cuenta que el almacenamiento para un evento debe ser asignado por el origen de eventos (usando Tcl_Alloc o la macro Tcl ckalloc) antes de llamar a Tcl_QueueEvent, pero será liberado por Tcl_ServiceEvent, no por el origen de eventos.

Las aplicaciones multihilo funcionan de manera similar, excepto que hay una cola de eventos separada para cada hilo que contiene un intérprete de Tcl. Llamar a Tcl_QueueEvent en una aplicación multihilo añade un evento a la cola del hilo actual. Para añadir un evento a la cola de otro hilo, use Tcl_ThreadQueueEvent. Tcl_ThreadQueueEvent acepta como argumento un argumento Tcl_ThreadId, que identifica de forma única un hilo en una aplicación Tcl. Para obtener el Tcl_ThreadId del hilo actual, use el procedimiento Tcl_GetCurrentThread. (Un hilo necesitaría luego pasar este identificador a otros hilos para que esos hilos puedan añadir eventos a su cola.) Después de añadir un evento a la cola de otro hilo, normalmente necesita llamar a Tcl_ThreadAlert para "despertar" al notificador de ese hilo y alertarlo del nuevo evento.

Tcl_DeleteEvents se puede utilizar para eliminar explícitamente uno o más eventos de la cola de eventos. Tcl_DeleteEvents llama a proc para cada evento en la cola, eliminando aquellos para los que el procedimiento devuelve 1. Los eventos para los que el procedimiento devuelve 0 permanecen en la cola. Proc debe coincidir con el siguiente prototipo:

typedef int Tcl_EventDeleteProc(
        Tcl_Event *evPtr,
        ClientData clientData);

El argumento clientData será el mismo que el argumento clientData para Tcl_Delete

An event source is a mechanism for Tcl to detect and process external events, such as input arriving on a network socket, a timer expiring, or a child process terminating. Tcl supports several built-in event sources, such as file events and timers, but applications can also register their own custom event sources using .BR Tcl_CreateEventSource . .PP .BR Tcl_CreateEventSource registers a new event source with the Tcl notifier. The notifier is the lowest-level mechanism in Tcl for handling events. It is responsible for waiting for events to occur and dispatching them to the appropriate handlers. The .I setupProc argument is a pointer to a procedure that Tcl will call to set up the event source. This procedure should initialize any necessary data structures, register any file handlers or timers required by the event source, and set the maximum time that Tcl should block while waiting for an event. The .I checkProc argument is a pointer to a procedure that Tcl will call to check for events from the source. This procedure should check if any events have occurred for the source and, if so, queue them on the Tcl event queue by calling .BR Tcl_QueueEvent . The .I clientData argument is a pointer to arbitrary data that will be passed to both .I setupProc and .I checkProc . This data can be used to associate state with the event source. .PP The .I setupProc should have the following signature: .TS IM Tcl_SetupProc \* { ClientData clientData; int *blockPtr; } .TE .PP The .I checkProc should have the following signature: .TS IM Tcl_EventProc \* { ClientData clientData; int flags; } .TE .PP When .I setupProc is called, .I clientData is passed to it, along with a pointer .I blockPtr . The .I setupProc should set .I \*blockPtr to the maximum number of seconds Tcl should block waiting for an event from this source. If the source does not need to block, it should set .I \*blockPtr to 0. If the source never needs to block (e.g., it is always ready), it can set .I \*blockPtr to -1. The .I setupProc should also register any file handlers or timers needed by the event source. .PP When .I checkProc is called, .I clientData is passed to it, along with a .I flags argument. The .I flags argument can be used to control the behavior of the check. For example, .BR TCL_DONT_WAIT (value 1) means that the check procedure should not block. The .I checkProc should check for any events associated with .I clientData . If any events are found, they should be placed on the Tcl event queue using .BR Tcl_QueueEvent . If .I checkProc discovers that an event source is no longer valid (e.g., a file descriptor has been closed), it should return a value of 0. Otherwise, it should return a non-zero value. The .I evPtr argument is a pointer to an .BR Tcl_Event . It will point to the next event in the queue. .PP .BR Tcl_DeleteEventSource deletes an event source. The .I setupProc , .I checkProc , and .I clientData arguments must exactly match those provided to .BR Tcl_CreateEventSource for the event source to be deleted. If no such source exists, .BR Tcl_DeleteEventSource has no effect. .SH CREATING A NEW NOTIFIER .PP The notifier consists of all the procedures described in this manual entry, plus .BR Tcl_DoOneEvent and .BR Tcl_Sleep , which are available on all platforms, and .BR Tcl_CreateFileHandler and .BR Tcl_DeleteFileHandler , which are Unix-specific. Most of these procedures are generic, in that they are the same for all notifiers. However, none of the procedures are notifier-dependent: .BR Tcl_InitNotifier , .BR Tcl_AlertNotifier , .BR Tcl_FinalizeNotifier , .BR Tcl_SetTimer , .BR Tcl_Sleep , .BR Tcl_WaitForEvent , .BR Tcl_CreateFileHandler , .BR Tcl_DeleteFileHandler and .BR Tcl_ServiceModeHook . To support a new platform or to integrate Tcl with an application-specific event loop, you must write new versions of these procedures. .PP .BR Tcl_InitNotifier initializes the notifier state and returns a handle to the notifier state. Tcl calls this procedure when initializing a Tcl interpreter. Similarly, .BR Tcl_FinalizeNotifier shuts down the notifier, and is called by .BR Tcl_Finalize when shutting down a Tcl interpreter. .PP .BR Tcl_WaitForEvent is the lowest-level procedure in the notifier; it is responsible for waiting for an “interesting” event to occur or for a given time to elapse. Before .BR Tcl_WaitForEvent is invoked, each of the event sources' setup procedure will have been invoked. The .I timePtr argument to .BR Tcl_WaitForEvent gives the maximum time to block for an event, based on calls to .BR Tcl_SetMaxBlockTime made by setup procedures and on other information (such as the .B TCL_DONT_WAIT bit in .I flags ). .PP Ideally, .BR Tcl_WaitForEvent should only wait for an event to occur; it should not actually process the event in any way. Later on, the event sources will process the raw events and create Tcl_Events on the event queue in their .I checkProc procedures. However, on some platforms (such as Windows) this is not possible; events may be processed in .BR Tcl_WaitForEvent , including queuing Tcl_Events and more (for example, callbacks for native widgets may be invoked). The return value from .BR Tcl_WaitForEvent must be either 0, 1, or -1. On platforms such as Windows where events get processed in .BR Tcl_WaitForEvent , a return value of 1 means that there may be more events still pending that have not been processed. This is a sign to the caller that it must call .BR Tcl_WaitForEvent again if it wants all pending events to be processed. A 0 return value means that calling .BR Tcl_WaitForEvent again will not have any effect: either this is a platform where .BR Tcl_WaitForEvent only waits without doing any event processing, or .BR Tcl_WaitForEvent knows for sure that there are no additional events to process (e.g. it returned because the time elapsed). Finally, a return value of -1 means that the event loop is no longer operational and the application should probably unwind and terminate. Under Windows this happens when a WM_QUIT message is received; under Unix it happens when .BR Tcl_WaitForEvent would have waited forever because there were no active event sources and the timeout was infinite. .PP .BR Tcl_AlertNotifier is used in multithreaded applications to allow any thread to “wake up” the notifier to alert it to new events on its queue. .BR Tcl_AlertNotifier requires as an argument the notifier handle returned by .BR Tcl_InitNotifier . .PP If the notifier will be used with an external event loop, then it must also support the .BR Tcl_SetTimer interface. .BR Tcl_SetTimer is invoked by .BR Tcl_SetMaxBlockTime whenever the maximum blocking time has been reduced. .BR Tcl_SetTimer should arrange for the external event loop to invoke .BR Tcl_ServiceAll after the specified interval even if no events have occurred. This interface is needed because .BR Tcl_WaitForEvent is not invoked when there is an external event loop. If the notifier will only be used from .BR Tcl_DoOneEvent , then .BR Tcl_SetTimer need not do anything. .PP .BR Tcl_ServiceModeHook is called by the platform-independent portion of the notifier when client code makes a call to .BR Tcl_SetServiceMode . This hook is provided to support operating systems that require special event handling when the application is in a modal loop (the Windows notifier, for instance, uses this hook to create a communication window). .PP On Unix systems, the file event source also needs support from the notifier. The file event source consists of the .BR Tcl_CreateFileHandler and .BR Tcl_DeleteFileHandler procedures, which are described in the .BR Tcl_CreateFileHandler manual page. .PP The .BR Tcl_Sleep and .BR Tcl_DoOneEvent interfaces are described in their respective manual pages. .PP The easiest way to create a new notifier is to look at the code for an existing notifier, such as the files .B unix/tclUnixNotfy.c or .B win/tclWinNotify.c in the Tcl source distribution. .SH REPLACING THE NOTIFIER .PP A notifier that has been written according to the conventions above can also be installed in a running process in place of the standard notifier. This mechanism is used so that a single executable can be used (with the standard notifier) as a stand-alone program and reused (with a replacement notifier in a loadable extension) as an extension to another program, such as a Web browser plugin. .PP To do this, the extension makes a call to .BR Tcl_SetNotifier passing a pointer to a .B Tcl_NotifierProcs data structure. The structure has the following layout: .Bd -literalindent .nf typedef struct Tcl_NotifierProcs { Tcl_SetTimerProc *setTimerProc; Tcl_WaitForEventProc *waitForEventProc; Tcl_CreateFileHandlerProc *createFileHandlerProc; Tcl_DeleteFileHandlerProc *deleteFileHandlerProc; Tcl_InitNotifierProc *initNotifierProc; Tcl_FinalizeNotifierProc *finalizeNotifierProc; Tcl_AlertNotifierProc *alertNotifierProc; Tcl_ServiceModeHookProc *serviceModeHookProc; } Tcl_NotifierProcs; .fi .Ed .PP Following the call to .BR Tcl_SetNotifier , the pointers given in the .B Tcl_NotifierProcs structure replace whatever notifier had been installed in the process. .PP It is extraordinarily unwise to replace a running notifier. Normally, .BR Tcl_SetNotifier should be called at process initialization time before the first call to .BR Tcl_InitNotifier . .SH EXTERNAL EVENT LOOPS .PP The notifier interfaces are designed so that Tcl can be embedded into applications that have their own private event loops. In this case, the application does not call .BR Tcl_DoOneEvent except in the case of recursive event loops such as calls to the Tcl commands .B update or .B vwait . Most of the time is spent in the external event loop of the application. In this case the notifier must arrange for the external event loop to call back into Tcl when something happens on the various Tcl event sources. These callbacks should arrange for appropriate Tcl events to be placed on the Tcl event queue. .PP Because the external event loop is not calling .BR Tcl_DoOneEvent on a regular basis, it is up to the notifier to arrange for .BR Tcl_ServiceEvent to be called whenever events are pending on the Tcl event queue. The easiest way to do this is to invoke .BR Tcl_ServiceAll at the end of each callback from the external event loop. This will ensure that all of the event sources are polled, any queued events are serviced, and any pending idle handlers are processed before returning control to the application. In addition, event sources that need to poll for events can call .BR Tcl_SetMaxBlockTime to force the external event loop to call Tcl even if no events are available on the system event queue. .PP As a side effect of processing events detected in the main external event loop, Tcl may invoke .BR Tcl_DoOneEvent to start a recursive event loop in commands like .B vwait . .BR Tcl_DoOneEvent will invoke the external event loop, which will result in callbacks as described in the preceding paragraph, which will result in calls to .BR Tcl_ServiceAll . However, in these cases it is undesirable to service events in .BR Tcl_ServiceAll . Servicing events there is unnecessary because control will immediately return to the external event loop and hence to .BR Tcl_DoOneEvent , which can service the events itself. Furthermore, .BR Tcl_DoOneEvent is supposed to service only a single event, whereas .BR Tcl_ServiceAll normally services all pending events. To handle this situation, .BR Tcl_DoOneEvent sets a flag for .BR Tcl_ServiceAll that causes it to return without servicing any events. This flag is called the .I service mode ; .BR Tcl_DoOneEvent restores it to its previous value before it returns. .PP In some cases, however, it may be necessary for .BR Tcl_ServiceAll to service events even when it has been invoked from .BR Tcl_DoOneEvent . This happens when there is yet another recursive event loop invoked via an event handler called by .BR Tcl_DoOneEvent (such as one that is part of a native widget). In this case, .BR Tcl_DoOneEvent may not have a chance to service events so .BR Tcl_ServiceAll must service them all. Any recursive event loop that calls an external event loop rather than .BR Tcl_DoOneEvent must reset the service mode so that all events get processed in .BR Tcl_ServiceAll . This is done by invoking the .BR Tcl_SetServiceMode procedure. If .BR Tcl_SetServiceMode is passed .B TCL_SERVICE_NONE , then calls to .BR Tcl_ServiceAll will return immediately without processing any events. If .BR Tcl_SetServiceMode is passed .B TCL_SERVICE_ALL , then calls to .BR Tcl_ServiceAll will behave normally. .BR Tcl_SetServiceMode returns the previous value of the service mode, which should be restored when the recursive loop exits. .BR Tcl_GetServiceMode returns the current value of the service mode. .SH SEE ALSO Tcl_CreateFileHandler(3), Tcl_DeleteFileHandler(3), Tcl_Sleep(3), Tcl_DoOneEvent(3), Thread(3) .SH KEYWORDS event source, notifier, event loop, callback .SH "COPYRIGHT" .sp .if n .ti 0 .if n .sk 2 .if n .ls 1 .if n .br .if n .ad Copyright © 1993 The Regents of the University of California. .if n .ad .if n .ls 0 .if n .sk 0 .if n .ti 0 Copyright © 1994-1998 Sun Microsystems, Inc. .if n .ad .if n .ls 0 .if n .sk 0 .if n .ti 0 Copyright © 2000-2001 Qualcomm Incorporated. .if n .ad .if n .ls 0 .if n .sk 0 .if n .ti 0 Copyright © 2001-2003 Microsoft Corporation. .if n .ad .if n .ls 0 .if n .sk 0 .if n .ti 0 Copyright © 2007-2008 ActiveState Software Inc. .if n .ad .if n .ls 0 .if n .sk 0 .if n .ti 0 Copyright © 2010-2011 Cesnet. .if n .ad .if n .ls 0 .if n .sk 0 .if n .ti 0 Copyright © 2012-2015 Red Hat, Inc. .if n .ad .if n .ls 0 .if n .sk 0 .if n .ti 0 Copyright © 2017-2020 Tcl Core Team. .if n .ad .if n .ls 0 .if n .sk 0 .if n .ti 0 .if n .br This is a manual page for the Tcl C API.
