DESCRIPCIÓN

The Tcl scripting language has a virtual filesystem interface that is used by the built-in Tcl commands that deal with files, directories, and volumes. The interface allows for different filesystem implementations to be plugged into Tcl. This manual page describes the Tcl filesystem interface procedures.

Tcl handles filesystem operations through a hierarchical system of filesystem objects. Each filesystem object has a file system type, which determines how the filesystem object operates. For example, the native filesystem on Unix is an instance of the “unix” filesystem type, and the native filesystem on Windows is an instance of the “windows” filesystem type. These filesystem types are implemented as C structures containing pointers to functions that perform the filesystem operations. The procedures on this manual page are the Tcl interface to these operations.

The Tcl filesystem interface provides a mechanism for applications to register new filesystem types. An application can also register existing filesystem types that may be implemented in shared libraries.

The filesystem procedures are grouped into the following categories:

Filesystem Management

Tcl_FSRegister, Tcl_FSUnregister, Tcl_FSData, Tcl_FSMountsChanged.

These procedures are used to register and unregister filesystem types, and to query and manage filesystem mounts.

Path Type Determination

Tcl_FSGetFileSystemForPath, Tcl_FSGetPathType, Tcl_FSConvertToPathType.

These procedures are used to determine the type and properties of a given path.

File Operations

Tcl_FSCopyFile, Tcl_FSDeleteFile, Tcl_FSRenameFile, Tcl_FSStat, Tcl_FSLstat, Tcl_FSAccess, Tcl_FSOpenFileChannel, Tcl_FSUtime, Tcl_FSLink.

These procedures perform standard file operations such as copying, deleting, renaming, and retrieving file status.

Directory Operations

Tcl_FSCopyDirectory, Tcl_FSCreateDirectory, Tcl_FSRemoveDirectory, Tcl_FSGetCwd, Tcl_FSChdir, Tcl_FSMatchInDirectory.

These procedures perform standard directory operations such as creating, removing, and listing directory contents.

Volume Operations

Tcl_FSListVolumes.

This procedure lists the available volumes in the system.

File Evaluation and Loading

Tcl_FSEvalFile, Tcl_FSEvalFileEx, Tcl_FSLoadFile, Tcl_FSUnloadFile.

These procedures are used to evaluate Tcl script files and load compiled Tcl code.

Path Manipulation

Tcl_FSPathSeparator, Tcl_FSJoinPath, Tcl_FSSplitPath, Tcl_FSEqualPaths, Tcl_FSGetNormalizedPath, Tcl_FSJoinToPath.

These procedures provide utilities for manipulating path names, such as joining and splitting path components, and comparing paths.

Attribute Access

Tcl_FSFileAttrsGet, Tcl_FSFileAttrsSet, Tcl_FSFileAttrStrings.

These procedures allow access to and modification of file attributes.

Native Path Representation

Tcl_FSNewNativePath, Tcl_FSGetNativePath, Tcl_FSGetTranslatedPath, Tcl_FSGetTranslatedStringPath, Tcl_FSGetInternalRep.

These procedures deal with the native representation of paths for different operating systems and filesystems.

Stat Buffer Access

Tcl_AllocStatBuf, Tcl_GetAccessTimeFromStat, Tcl_GetBlockSizeFromStat, Tcl_GetBlocksFromStat, Tcl_GetChangeTimeFromStat, Tcl_GetDeviceTypeFromStat, Tcl_GetFSDeviceFromStat, Tcl_GetFSInodeFromStat, Tcl_GetGroupIdFromStat, Tcl_GetLinkCountFromStat, Tcl_GetModeFromStat, Tcl_GetModificationTimeFromStat, Tcl_GetSizeFromStat, Tcl_GetUserIdFromStat.

These procedures provide access to the fields of a stat buffer, which is returned by Tcl_FSStat and Tcl_FSLstat.

The filesystem procedures typically return a Tcl status code. TCL_OK indicates success. Any other return value indicates an error, and the interpreter's result will contain an error message.

The path arguments to these procedures are Tcl_Obj pointers. These objects should have a filesystem path representation. If they do not, Tcl will attempt to convert them to one.

The `statPtr` argument to Tcl_FSStat and Tcl_FSLstat should be a pointer to a Tcl_StatBuf structure. This structure is compatible with the stat structure defined in POSIX. Tcl_AllocStatBuf can be used to allocate a Tcl_StatBuf structure.

The `modeString` argument to Tcl_FSOpenFileChannel is a string that specifies how the file should be opened, similar to the mode argument to the Tcl open command. For example, it can be "r" for read, "w" for write, "a" for append, etc. It can also include options like "b" for binary mode.

The `permissions` argument to Tcl_FSOpenFileChannel specifies the file permissions to be used if a new file is created. This is typically an octal value like 0644.

The `linkAction` argument to Tcl_FSLink specifies the type of link to create. It can be TCL_LINK (hard link) or TCL_SYMLINK (symbolic link).

The `types` argument to Tcl_FSMatchInDirectory is a pointer to a Tcl_GlobTypeData structure, which specifies the types of files to match. This can be used to filter results based on file type.

The `errorPtr` argument to Tcl_FSCopyDirectory and Tcl_FSRemoveDirectory is a pointer to a Tcl_Obj pointer. If an error occurs during the operation, this pointer will be filled with a Tcl_Obj containing the name of the file or directory that caused the error.

The `objPtrRef` argument to Tcl_FSFileAttrsGet and Tcl_FSFileAttrStrings is a pointer to a Tcl_Obj pointer. If the operation is successful, this pointer will be filled with a Tcl_Obj containing the requested file attributes.

The `clientData` argument to Tcl_FSNewNativePath is a void pointer that represents the native representation of the path. The exact type and meaning of this data depends on the filesystem type.

The `loadHandlePtr` argument to Tcl_FSLoadFile is a pointer to a Tcl_LoadHandle. This handle is an opaque token that represents the loaded file and is used by Tcl_FSUnloadFile to unload the file.

The `unloadProcPtr` argument to Tcl_FSLoadFile is a pointer to a Tcl_FSUnloadFileProc. This is a function pointer to the procedure that should be called to unload the loaded file.

The `proc1Ptr` and `proc2Ptr` arguments to Tcl_FSLoadFile are pointers to Tcl_PackageInitProc. These are function pointers to the entry points of the loaded code, used for initialization and safe initialization, respectively.

The `sym1` and `sym2` arguments to Tcl_FSLoadFile are strings that specify the names of procedures to look up in the loaded file's symbol table.

The `tval` argument to Tcl_FSUtime is a pointer to a utimbuf structure, which contains the desired access and modification times for the file.

The `lenPtr` argument to Tcl_FSSplitPath is a pointer to an integer. If not NULL, this integer will be filled with the number of path components returned.

The `objc` and `objv` arguments to Tcl_FSJoinToPath are the count and array of Tcl objects representing path elements to join to the base path.

DESCRIPTION

There are several reasons for calling the Tcl_FS API functions (e.g. Tcl_FSAccess and Tcl_FSStat) rather than calling system level functions like access and stat directly. First, they will work cross-platform, so an extension which calls them should work unmodified on Unix and Windows. Second, the Windows implementation of some of these functions fixes some bugs in the system level calls. Third, these function calls deal with any “Utf to platform-native” path conversions which may be required (and may cache the results of such conversions for greater efficiency on subsequent calls). Fourth, and perhaps most importantly, all of these functions are “virtual filesystem aware”. Any virtual filesystem (VFS for short) which has been registered (through Tcl_FSRegister) may reroute file access to alternative media or access methods. This means that all of these functions (and therefore the corresponding file, glob, pwd, cd, open, etc. Tcl commands) may be operate on “files” which are not native files in the native filesystem. This also means that any Tcl extension which accesses the filesystem (FS for short) through this API is automatically “virtual filesystem aware”. Of course, if an extension accesses the native filesystem directly (through platform-specific APIs, for example), then Tcl cannot intercept such calls.

If appropriate VFSes have been registered, the “files” may, to give two examples, be remote (e.g. situated on a remote ftp server) or archived (e.g. lying inside a .zip archive). Such registered filesystems provide a lookup table of functions to implement all or some of the functionality listed here. Finally, the Tcl_FSStat and Tcl_FSLstat calls abstract away from what the “struct stat” buffer is actually declared to be, allowing the same code to be used both on systems with and systems without support for files larger than 2GB in size.

The Tcl_FS API is Tcl_Obj-ified and may cache internal representations and other path-related strings (e.g. the current working directory). One side-effect of this is that one must not pass in values with a reference count of zero to any of these functions. If such calls were handled, they might result in memory leaks (under some circumstances, the filesystem code may wish to retain a reference to the passed in value, and so one must not assume that after any of these calls return, the value still has a reference count of zero - it may have been incremented) or in a direct segmentation fault (or other memory access error) due to the value being freed part way through the complex value manipulation required to ensure that the path is fully normalized and absolute for filesystem determination. The practical lesson to learn from this is that

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

is wrong, and may cause memory errors. The path must have its reference count incremented before passing it in, or decrementing it. For this reason, values with a reference count of zero are considered not to be valid filesystem paths and calling any Tcl_FS API function with such a value will result in no action being taken.

FS API FUNCTIONS

Tcl_FSCopyFile attempts to copy the file given by srcPathPtr to the path name given by destPathPtr. If the two paths given lie in the same filesystem (according to Tcl_FSGetFileSystemForPath) then that filesystem's “copy file” function is called (if it is non-NULL). Otherwise the function returns -1 and sets the errno global C variable to the “EXDEV” POSIX error code (which signifies a “cross-domain link”).

Tcl_FScopyDirectory attempts to copy the directory given by srcPathPtr to the path name given by destPathPtr. If the two paths given lie in the same filesystem (according to Tcl_FSGetFileSystemForPath) then that filesystem's “copy file” function is called (if it is non-NULL). Otherwise the function returns -1 and sets the errno global C variable to the “EXDEV” POSIX error code (which signifies a “cross-domain link”).

Tcl_FSCreateDirectory attempts to create the directory given by pathPtr by calling the owning filesystem's “create directory” function.

Tcl_FSDeleteFile attempts to delete the file given by pathPtr by calling the owning filesystem's “delete file” function.

Tcl_FSRemoveDirectory attempts to remove the directory given by pathPtr by calling the owning filesystem's “remove directory” function.

Tcl_FSRenameFile attempts to rename the file or directory given by srcPathPtr to the path name given by destPathPtr. If the two paths given lie in the same filesystem (according to Tcl_FSGetFileSystemForPath) then that filesystem's “rename file” function is called (if it is non-NULL). Otherwise the function returns -1 and sets the errno global C variable to the “EXDEV” POSIX error code (which signifies a “cross-domain link”).

Tcl_FSListVolumes calls each filesystem which has a non-NULL “list volumes” function and asks them to return their list of root volumes. It accumulates the return values in a list which is returned to the caller (with a reference count of 0).

Tcl_FSEvalFileEx reads the file given by pathPtr using the encoding identified by encodingName and evaluates its contents as a Tcl script. It returns the same information as Tcl_EvalObjEx. If encodingName is NULL, the system encoding is used for reading the file contents. If the file could not be read then a Tcl error is returned to describe why the file could not be read. The eofchar for files is “\x1A” (^Z) for all platforms. If you require a “^Z” in code for string comparison, you can use “\x1A”, which will be safely substituted by the Tcl interpreter into “^Z”. Tcl_FSEvalFile is a simpler version of Tcl_FSEvalFileEx that always uses the system encoding when reading the file.

Tcl_FSLoadFile dynamically loads a binary code file into memory and returns the addresses of two procedures within that file, if they are defined. The appropriate function for the filesystem to which pathPtr belongs will be called. If that filesystem does not implement this function (most virtual filesystems will not, because of OS limitations in dynamically loading binary code), Tcl will attempt to copy the file to a temporary directory and load that temporary file. Tcl_FSUnloadFile reverses the operation, asking for the library indicated by the loadHandle to be removed from the process. Note that, unlike with the unload command, this does not give the library any opportunity to clean up.

Both the above functions return a standard Tcl completion code. If an error occurs, an error message is left in the interp's result.

The token provided via the variable indicated by loadHandlePtr may be used with Tcl_FindSymbol.

Tcl_FSMatchInDirectory is used by the globbing code to search a directory for all files which match a given pattern. The appropriate function for the filesystem to which pathPtr belongs will be called.

The return value is a standard Tcl result indicating whether an error occurred in globbing. Error messages are placed in interp (unless interp is NULL, which is allowed), but good results are placed in the resultPtr given.

Note that the glob code implements recursive patterns internally, so this function will only ever be passed simple patterns, which can be matched using the logic of string match. To handle recursion, Tcl will call this function frequently asking only for directories to be returned. A special case of being called with a NULL pattern indicates that the path needs to be checked only for the correct type.

Tcl_FSLink replaces the library version of readlink, and extends it to support the creation of links. The appropriate function for the filesystem to which linkNamePtr belongs will be called.

If the toPtr is NULL, a “read link” action is performed. The result is a Tcl_Obj specifying the contents of the symbolic link given by linkNamePtr, or NULL if the link could not be read. The result is owned by the caller, which should call Tcl_DecrRefCount when the result is no longer needed. If the toPtr is not NULL, Tcl should create a link of one of the types passed in in the linkAction flag. This flag is an OR'ed combination of TCL_CREATE_SYMBOLIC_LINK and TCL_CREATE_HARD_LINK. Where a choice exists (i.e. more than one flag is passed in), the Tcl convention is to prefer symbolic links. When a link is successfully created, the return value should be toPtr (which is therefore already owned by the caller). If unsuccessful, NULL is returned.

Tcl_FSLstat fills the Tcl_StatBuf structure statPtr with information about the specified file. You do not need any access rights to the file to get this information but you need search rights to all directories named in the path leading to the file. The Tcl_StatBuf structure includes info regarding device, inode (always 0 on Windows), privilege mode, nlink (always 1 on Windows), user id (always 0 on Windows), group id (always 0 on Windows), rdev (same as device on Windows), size, last access time, last modification time, and last status change time. The time values are returned as the number of seconds since 00:00:00 GMT, January 1, 1970 (UTC). Tcl_FSStat is identical to Tcl_FSLstat.

Tcl_FSPathType determines the type of the file specified by pathPtr. It returns one of the following values: TCL_PATH_UNSPECIFIED, TCL_PATH_RELATIVE, TCL_PATH_ABSOLUTE, TCL_PATH_ABSOLUTE_STAR, TCL_PATH_DEVICE, TCL_PATH_VOLUME, TCL_PATH_DIRNAME, TCL_PATH_INTERP, TCL_PATH_INTERP_RELATIVE, TCL_PATH_INTERP_ABSOLUTE, TCL_PATH_INTERP_ABSOLUTE_STAR, TCL_PATH_INTERP_DEVICE, TCL_PATH_INTERP_VOLUME, TCL_PATH_INTERP_DIRNAME.

Tcl_FSNewPath creates a new path object from a list of components. It joins the components to form an absolute path, normalizes it, and returns a pointer to the new Tcl_Obj.

Tcl_FSJoinPath joins a list of path components to an optional base path. It returns a pointer to a new Tcl_Obj representing the joined path.

Tcl_FSGetFileSystemForPath returns a pointer to the Tcl_FSProviderType structure for the file system that manages the given path.

Tcl_FSGetRegisteredFileSystems returns a Tcl list of all registered file system names.

Tcl_FSRegister registers a new file system with the given name and provider procedures.

Tcl_FSUnregister unregisters a previously registered file system.

Tcl_FSData returns a pointer to the Tcl_FSData structure associated with the given path. This structure contains file system specific data.

Tcl_FSClose closes the given file channel.

Tcl_FSConfigure configures a file system object with the given option and value.

Tcl_FSGetPath returns the canonical path for the given path object.

Tcl_FSIsSameFile checks if two path objects refer to the same file.

Tcl_FSStatBuf returns a pointer to the Tcl_StatBuf structure.

LA API DEL SISTEMA DE ARCHIVOS VIRTUAL

Un sistema de archivos proporciona una estructura Tcl_Filesystem que contiene punteros a funciones que implementan las diversas operaciones en un sistema de archivos; estas operaciones se invocan según sea necesario por la capa genérica, lo que generalmente ocurre a través de las funciones enumeradas anteriormente.

Las estructuras Tcl_Filesystem se manipulan usando los siguientes métodos.

Tcl_FSRegister toma un puntero a una estructura de sistema de archivos y un dato opcional para asociar con ese sistema de archivos. Al llamar a esta función, Tcl adjuntará el sistema de archivos a la lista de sistemas de archivos conocidos y se volverá completamente funcional inmediatamente. Tcl no verifica si el mismo sistema de archivos está registrado múltiples veces (y en general, eso no es bueno). Se devolverá TCL_OK.

Tcl_FSUnregister elimina la estructura de sistema de archivos dada de la lista de sistemas de archivos conocidos, si es que es conocida, y devuelve TCL_OK. Si el sistema de archivos no está registrado actualmente, se devuelve TCL_ERROR.

Tcl_FSData devolverá el clientData asociado con el sistema de archivos dado, si ese sistema de archivos está registrado. De lo contrario, devolverá NULL.

Tcl_FSMountsChanged se utiliza para informar al núcleo de Tcl que el conjunto de puntos de montaje para el sistema de archivos dado (ya registrado) ha cambiado, y que por lo tanto las representaciones de archivos almacenadas en caché pueden ya no ser correctas.

    Tcl_FSFilesystemSeparatorProc *filesystemSeparatorProc;
    Tcl_FSStatProc *statProc;
    Tcl_FSAccessProc *accessProc;
    Tcl_FSOpenFileChannelProc *openFileChannelProc;
    Tcl_FSMatchInDirectoryProc *matchInDirectoryProc;
    Tcl_FSUtimeProc *utimeProc;
    Tcl_FSLinkProc *linkProc;
    Tcl_FSListVolumesProc *listVolumesProc;
    Tcl_FSFileAttrStringsProc *fileAttrStringsProc;
    Tcl_FSFileAttrsGetProc *fileAttrsGetProc;
    Tcl_FSFileAttrsSetProc *fileAttrsSetProc;
    Tcl_FSCreateDirectoryProc *createDirectoryProc;

Excepto por los tres primeros campos de esta estructura que contienen elementos de datos simples, todas las entradas contienen direcciones de funciones llamadas por la capa genérica del sistema de archivos para realizar el rango completo de acciones relacionadas con el sistema de archivos.

Las muchas funciones en esta estructura se dividen en tres categorías: funciones de infraestructura (casi todas deben implementarse), funciones operativas (que deben implementarse si se proporciona un sistema de archivos completo) y funciones de eficiencia (que solo necesitan implementarse si se pueden hacer de manera eficiente, o si tienen efectos secundarios requeridos por el sistema de archivos; Tcl tiene emulaciones menos eficientes a las que puede recurrir). Es importante notar que, en la versión actual de Tcl, la mayoría de estas sustituciones solo se usan para manejar comandos iniciados en Tcl, no en C. Lo que esto significa es que, si se emite un comando file rename en Tcl, y el(los) sistema(s) de archivos relevantes no implementan su Tcl_FSRenameFileProc, el núcleo de Tcl recurrirá a una combinación de otras funciones del sistema de archivos (usará Tcl_FSCopyFileProc seguido de Tcl_FSDeleteFileProc, y si Tcl_FSCopyFileProc no está implementada, hay una sustitución adicional). Sin embargo, si se emite un comando Tcl_FSRenameFileProc a nivel de C, no ocurren dichas sustituciones. Esto es cierto excepto para las últimas cuatro entradas en la tabla del sistema de archivos (lstat, load, getcwd y chdir) para las cuales sí ocurren sustituciones a nivel de C.

Cualquier función que tome nombres de ruta en forma de Tcl_Obj toma esos nombres en forma UTF-8. La API de infraestructura del sistema de archivos está diseñada para admitir la conversión eficiente y almacenada en caché de estas rutas UTF-8 a otras representaciones nativas.

TIPOS DE OBJETOS DEL SISTEMA DE ARCHIVOS

Cada sistema de archivos se implementa mediante una estructura de tipo opaco, Tcl_FSInfo. Esta estructura se devuelve mediante la función Tcl_FSGetFileSystemForPath, y puede usarse para obtener información sobre el sistema de archivos.

Una Tcl_FSInfo contendrá un puntero a una estructura Tcl_FSProcs, que contendrá punteros a funciones que pueden usarse para realizar operaciones en el sistema de archivos. Las funciones específicas disponibles dependen de las capacidades del sistema de archivos.

OPENFILECHANNELPROC

Función para procesar una llamada a Tcl_FSOpenFileChannel. Debe implementarse para cualquier sistema de archivos razonable, ya que cualquier operación que requiera abrir o acceder al contenido de un archivo la usará (p. ej., open, encoding y muchos comandos Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

El Tcl_FSOpenFileChannelProc abre un archivo especificado por pathPtr y devuelve un identificador de canal que puede usarse para realizar operaciones de entrada y salida en el archivo. Esta API está modelada según el procedimiento fopen de la biblioteca de E/S estándar de Unix. La sintaxis y el significado de todos los argumentos son similares a los dados en el comando open de Tcl al abrir un archivo, donde el argumento mode es una combinación de las banderas POSIX O_RDONLY, O_WRONLY, etc. Si ocurre un error al abrir el canal, el Tcl_FSOpenFileChannelProc devuelve NULL y registra un código de error POSIX que se puede recuperar con Tcl_GetErrno. Además, si interp no es NULL, el Tcl_FSOpenFileChannelProc deja un mensaje de error en el resultado de interp después de cualquier error.

El nuevo canal creado no debe ser registrado en el intérprete suministrado por un Tcl_FSOpenFileChannelProc; esa tarea es del llamador de Tcl_FSOpenFileChannel (si es necesario). Si uno de los canales estándar, stdin, stdout o stderr se cerró previamente, el acto de crear el nuevo canal también lo asigna como reemplazo del canal estándar.

MATCHINDIRECTORYPROC

Función para procesar una llamada a Tcl_FSMatchInDirectory. Si no se implementa, la funcionalidad de globbing y copia recursiva faltará en el sistema de archivos (y esto puede afectar a comandos como encoding names que utilizan la funcionalidad de globbing internamente).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La función debe devolver todos los archivos o directorios (u otros objetos del sistema de archivos) que coincidan con el patrón dado y de acuerdo con la especificación de types. Hay dos formas en que esta función puede ser llamada. Si pattern es NULL, entonces pathPtr es una especificación de ruta completa de un solo archivo o directorio que debe verificarse en cuanto a existencia y tipo correcto. De lo contrario, pathPtr es un directorio, cuyo contenido la función debe buscar archivos o directorios que tengan el tipo correcto. En cualquier caso, se puede asumir que pathPtr no es NULL y no está vacío. Actualmente no está documentado si pathPtr tendrá o no un separador de archivos al final, por lo que el código debe ser flexible a ambas posibilidades.

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso de coincidencia. Los mensajes de error se colocan en interp, a menos que interp sea NULL, en cuyo caso no es necesario generar ningún mensaje de error; en un resultado TCL_OK, los resultados deben agregarse al valor resultPtr dado (que se puede suponer que es una lista válida de Tcl no compartida). Las coincidencias agregadas a resultPtr deben incluir cualquier prefijo de ruta dado en pathPtr (esto generalmente significa que serán especificaciones de ruta absoluta). Tenga en cuenta que si no se encuentran coincidencias, eso simplemente conduce a un resultado vacío; los errores solo se señalan para problemas reales de archivos o del sistema de archivos que puedan ocurrir durante el proceso de coincidencia.

La estructura Tcl_GlobTypeData pasada en el parámetro types contiene los siguientes campos:

typedef struct Tcl_GlobTypeData {
    /* Corresponde a bcdpfls como en 'find -t' */
    int type;
    /* Corresponde a los permisos del archivo */
    int perm;
    /* Tipo mac aceptable */
    Tcl_Obj *macType;
    /* Creador mac aceptable */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Hay dos casos específicos que es importante manejar correctamente, ambos cuando types no es NULL. Los dos casos son cuando types->types & TCL_GLOB_TYPE_DIR o types->types & TCL_GLOB_TYPE_MOUNT son verdaderos (y en particular cuando las otras banderas son falsas). En el primer caso, la función debe listar los directorios contenidos. Tcl utiliza esto para implementar el globbing recursivo, por lo que es fundamental que los sistemas de archivos implementen la coincidencia de directorios correctamente. En el segundo de estos casos, con TCL_GLOB_TYPE_MOUNT, el sistema de archivos debe listar los puntos de montaje que se encuentran dentro del pathPtr dado (y en este caso, pathPtr no tiene por qué estar dentro del mismo sistema de archivos; a diferencia de todos los demás casos en los que se llama a esta función). El soporte para esto es fundamental si Tcl quiere tener transiciones fluidas entre un sistema de archivos y otro.

Función para procesar una llamada a Tcl_FSLink. Solo debe implementarse si el sistema de archivos admite enlaces, y de lo contrario puede ser NULL.

        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,

Si toPtr es NULL, se le está pidiendo a la función que lea el contenido de un enlace. Función para listar los volúmenes del sistema de archivos agregados por este sistema de archivos. Solo debe implementarse si el sistema de archivos agrega volúmenes al principio del sistema de archivos, para que puedan ser devueltos por file volumes.

El resultado debe ser una lista de volúmenes agregados por este sistema de archivos, o NULL (o una lista vacía) si no se proporcionan volúmenes. Tcl usará el contenido de la lista y luego disminuirá ese recuento de referencias. Esto permite a los sistemas de archivos elegir si realmente quieren conservar una lista "global" de volúmenes o no (si no, generan la lista sobre la marcha y se la pasan a Tcl con un recuento de referencias de 1 y luego se olvidan de la lista; si sí, simplemente incrementan el recuento de referencias de su lista global y se la pasan a Tcl, que copiará el contenido y luego disminuirá el recuento de nuevo a donde estaba).

Nota que, si el sistema de archivos soporta enlaces simbólicos, Tcl siempre llamará esta función y no copyDirectoryProc cuando sea necesario para copiarlos (even if they are symbolic links to directories). Finalmente, si el sistema de archivos determina que no puede soportar la acción de file copy, llamar a Tcl_SetErrno(EXDEV) y devolver un resultado no TCL_OK le informará a Tcl de usar sus mecanismos de reemplazo estándar.

RENAMEFILEPROC

Función para procesar una llamada a Tcl_FSRenameFile. Si no se implementa, Tcl caerá en un mecanismo de copia y eliminación. Por lo tanto, solo debe implementarse si el sistema de archivos puede realizar esta acción más eficientemente.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

El valor de retorno es un resultado estándar de Tcl indicando si se produjo un error durante el proceso de renombrado. Si el sistema de archivos determina que no puede soportar la acción de file rename, llamar a Tcl_SetErrno(EXDEV) y devolver un resultado no TCL_OK le informará a Tcl de usar sus mecanismos de reemplazo estándar.

COPYDIRECTORYPROC

Función para procesar una llamada a Tcl_FSCopyDirectory. Si no se implementa, Tcl caerá en un mecanismo de recursivo file mkdir, file copy como mecanismo de copia. Por lo tanto, solo debe implementarse si el sistema de archivos puede realizar esta acción más eficientemente.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

El valor de retorno es un resultado estándar de Tcl indicando si se produjo un error durante el proceso de copia. Si ocurre un error, el nombre del archivo o carpeta que causó el error debe estar en errorPtr. Nota que, destPathPtr es el nombre de la carpeta que debería convertirse en el espejo de srcPathPtr. No es nunca el nombre de un directorio en el cual se pueda copiar srcPathPtr (es decir, la función es mucho más sencilla que la subcomando file copy del nivel Tcl). Finalmente, si el sistema de archivos determina que no puede soportar la acción de copiar directorios, llamar a Tcl_SetErrno(EXDEV) y devolver un resultado no TCL_OK le informará a Tcl de usar sus mecanismos de reemplazo estándar.

LOADFILEPROC

Función para procesar una llamada a Tcl_FSLoadFile. Si no se implementa, Tcl caerá en una copia a un archivo temporal y luego en Tcl_FSLoadFile en ese archivo temporal. Por lo tanto, solo debe implementarse si el sistema de archivos puede cargar código directamente, o si puede ser implementado simplemente para retornar TCL_ERROR para desactivar la funcionalidad de carga en este sistema de archivos.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Devuelve un código de completación estándar de Tcl. Si ocurre un error, un mensaje de error se deja en el interp's result. La función dinámicamente carga un archivo binario en memoria. En caso de éxito, el handlePtr debe ser llenado con un token para el archivo dinámicamente cargado, y el unloadProcPtr debe ser llenado con la dirección de una procedimiento. El procedimiento de desenchufado se llama con el Tcl_LoadHandle dado como su único parámetro cuando Tcl necesita desenchufar el archivo. Por ejemplo, para el sistema de archivos nativo, el Tcl_LoadHandle devuelto es actualmente un token que puede usarse en el TclpFindSymbol privado para acceder a funciones en el nuevo código. Cada sistema de archivos puede definir el Tcl_LoadHandle como lo requiera. Finalmente, si el sistema de archivos determina que no puede soportar la acción de cargar archivos, llamar a Tcl_SetErrno(EXDEV) y devolver un resultado no TCL_OK le informará a Tcl de usar sus mecanismos de reemplazo estándar.

UNLOADFILEPROC

Función para desenchufar un archivo que se ha cargado previamente. Si se implementó el carga, esta debe también ser implementada, si hay algún procedimiento de limpieza necesario.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

Función para procesar una llamada a Tcl_FSGetCwd. Múltiples sistemas de archivos no necesitan implementar esta. Suele ser llamado una vez, si getcwd es llamado antes de chdir. Puede ser NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

Si el sistema de archivos soporta un concepto nativo de directorio de trabajo actual (que podría cambiar independientemente de Tcl), esta función debería devolver ese cwd como el resultado, o NULL si el directorio de trabajo actual no puede ser determinado (por ejemplo, el usuario no tiene permisos adecuados en el directorio de cwd). Si se devuelve NULL, se deja un mensaje de error en el interp's result.

CHDIRPROC

Función para procesar una llamada a Tcl_FSChdir. Si los sistemas de archivos no implementan esta, se emulará mediante una serie de comprobaciones de acceso a directorios. De otro modo, los sistemas de archivos que implementan esta deben responder con un resultado positivo si pathPtr es un directorio válido y accesible en su sistema de archivos. No deben recordar el resultado, ya que el resultado se recordará automáticamente por Tcl_FSGetCwd. Los sistemas de archivos reales deben realizar la acción correcta (es decir, llamar al API adecuado de chdir del sistema).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

La función Tcl_FSChdirProc cambia el directorio de trabajo actual del aplicativo a la valor especificada en pathPtr. La función devuelve -1 en caso de error o 0 en caso de éxito.
