ARGUMENTOS

Tcl_EventSetupProc *setupProc (entrada)
Procedimiento a invocar para preparar la espera de eventos en Tcl_DoOneEvent.
Tcl_EventCheckProc *checkProc (entrada)
Procedimiento que Tcl_DoOneEvent invocará después de esperar eventos. Comprueba si ha ocurrido algún evento y, en caso afirmativo, lo pone en cola.
ClientData clientData (entrada)
Valor arbitrario de una palabra a pasar a setupProc, checkProc o deleteProc.
const Tcl_Time *timePtr (entrada)
Indica la cantidad máxima de tiempo a esperar por un evento. Esto se especifica como un intervalo (cuánto tiempo esperar), no como un tiempo absoluto (cuándo despertar). Si el puntero pasado a Tcl_WaitForEvent es NULL, significa que no hay tiempo máximo de espera: esperar para siempre si es necesario.
Tcl_Event *evPtr (entrada)
Un evento para añadir a la cola de eventos. El espacio para el evento debe haber sido asignado por el llamador usando Tcl_Alloc o ckalloc.
Tcl_QueuePosition position (entrada)
Dónde añadir el nuevo evento en la cola: TCL_QUEUE_TAIL, TCL_QUEUE_HEAD, o TCL_QUEUE_MARK.
Tcl_ThreadId threadId (entrada)
Un identificador único para un hilo.
Tcl_EventDeleteProc *deleteProc (entrada)
Procedimiento a invocar para cada evento en cola en Tcl_DeleteEvents.
int flags (entrada)
Qué tipos de eventos procesar. Estas banderas son las mismas que las pasadas a Tcl_DoOneEvent.
int mode (entrada)
Indica si los eventos deben ser procesados por Tcl_ServiceAll. Debe ser uno de TCL_SERVICE_NONE o TCL_SERVICE_ALL.
Tcl_NotifierProcs* notifierProcPtr (entrada)
Estructura de punteros de función que describe procedimientos notificadores que se van a reemplazar por los instalados en el ejecutable. Ver REEMPLAZANDO EL NOTIFICADOR para más detalles.

INTRODUCCIÓN

Las interfaces descritas aquí se utilizan para personalizar el bucle de eventos de Tcl. Las dos personalizaciones más comunes son añadir nuevas fuentes de eventos y fusionar el bucle de eventos de Tcl con algún otro bucle de eventos, como uno proporcionado por una aplicación en la que Tcl esté incrustado. Cada una de estas tareas se describe en una sección separada a continuación.

Los procedimientos de esta entrada del manual son los bloques de construcción con los que se construye el notificador de eventos de Tcl. El notificador de eventos es la capa más baja en el mecanismo de eventos de Tcl. Consiste en tres cosas:

[1]
Fuentes de eventos: estas representan las formas en que se pueden generar eventos. Por ejemplo, existe una fuente de eventos de temporizador que implementa el procedimiento Tcl_CreateTimerHandler y el comando after, y existe una fuente de eventos de archivo que implementa el procedimiento Tcl_CreateFileHandler en sistemas Unix. Una fuente de eventos debe trabajar con el notificador para detectar eventos en los momentos adecuados, registrarlos en la cola de eventos y, finalmente, notificar al software de nivel superior que han ocurrido. Los procedimientos Tcl_CreateEventSource, Tcl_DeleteEventSource, y Tcl_SetMaxBlockTime, Tcl_QueueEvent, y Tcl_DeleteEvents se utilizan principalmente por las fuentes de eventos.
[2]
La cola de eventos: para aplicaciones sin hilos, existe una única cola para toda la aplicación, que contiene eventos que han sido detectados pero aún no procesados. Las fuentes de eventos colocan eventos en la cola para que puedan ser procesados en orden en momentos apropiados durante el bucle de eventos. La cola de eventos garantiza una disciplina justa de manejo de eventos, de modo que ninguna fuente de eventos pueda dejar a las demás sin atender. También permite que los eventos se guarden para ser procesados en un momento futuro. Las aplicaciones con hilos funcionan de manera similar, excepto que existe una cola de eventos separada para cada hilo que contiene un intérprete de Tcl. Tcl_QueueEvent se utiliza (principalmente por las fuentes de eventos) para añadir eventos a la cola de eventos y Tcl_DeleteEvents se utiliza para eliminar eventos de la cola sin procesarlos. En una aplicación con hilos, Tcl_QueueEvent añade un evento a la cola del hilo actual, y Tcl_ThreadQueueEvent añade un evento a una cola en un hilo específico.
[3]
El bucle de eventos: para detectar y procesar eventos, la aplicación entra en un bucle que espera a que ocurran eventos, los coloca en la cola de eventos y luego los procesa. La mayoría de las aplicaciones lo harán llamando al procedimiento Tcl_DoOneEvent, que se describe en una entrada de manual separada.

La mayoría de las aplicaciones Tcl no necesitan preocuparse por los detalles internos del notificador de Tcl. Sin embargo, el notificador ahora tiene suficiente flexibilidad para ser redirigido, ya sea para una nueva plataforma o para usar un bucle de eventos externo (como el bucle de eventos de Motif, cuando Tcl está incrustado en una aplicación de Motif). Los procedimientos Tcl_WaitForEvent y Tcl_SetTimer son normalmente implementados por Tcl, pero pueden ser reemplazados por nuevas versiones para redirigir el notificador (Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_Sleep, Tcl_CreateFileHandler, y Tcl_DeleteFileHandler también deben ser reemplazados; ver CREANDO UN NUEVO NOTIFICADOR a continuación para más detalles). Los procedimientos Tcl_ServiceAll, Tcl_ServiceEvent, Tcl_GetServiceMode, y Tcl_SetServiceMode se proporcionan para ayudar a conectar el bucle de eventos de Tcl con un bucle de eventos externo como el de Motif.

BASES DEL NOTIFICADOR

La forma más fácil de entender cómo funciona el notificador es considerar lo que sucede cuando se llama a Tcl_DoOneEvent. Tcl_DoOneEvent recibe un argumento flags que indica qué tipo de eventos está bien procesar y también si debe bloquearse o no si no hay eventos listos. Tcl_DoOneEvent hace lo siguiente:

[1]
Comprueba la cola de eventos para ver si contiene algún evento que pueda ser atendido. Si es así, atiende el primer evento posible, lo elimina de la cola y regresa. Lo hace llamando a Tcl_ServiceEvent y pasando el argumento flags.
[2]
Prepara para bloquear por un evento. Para hacer esto, Tcl_DoOneEvent invoca un procedimiento de configuración en cada fuente de eventos. La fuente de eventos realizará la inicialización específica de la fuente de eventos y posiblemente llamará a Tcl_SetMaxBlockTime para limitar cuánto tiempo bloqueará Tcl_WaitForEvent si no ocurren nuevos eventos.
[3]
Llama a Tcl_WaitForEvent. Este procedimiento se implementa de manera diferente en diferentes plataformas; espera a que ocurra un evento, basándose en la información proporcionada por las fuentes de eventos. Puede hacer que la aplicación se bloquee si timePtr especifica un intervalo distinto de 0. Tcl_WaitForEvent regresa cuando algo ha sucedido, como que un archivo se ha vuelto legible o el intervalo dado por timePtr ha expirado. Si no hay eventos para que Tcl_WaitForEvent espere, por lo que se bloquearía para siempre, entonces regresa inmediatamente y Tcl_DoOneEvent regresa 0.
[4]
Llama a un procedimiento de comprobación en cada fuente de eventos. El procedimiento de comprobación determina si ocurrieron eventos de interés para esta fuente. Si es así, los eventos se añaden a la cola de eventos.

PROCESO DEL BUCLE DE EVENTOS

Cuando se llama a Tcl_DoOneEvent, ejecuta un ciclo de los siguientes pasos:

[1]
Si se solicitó un bloqueo y no hay eventos en la cola, llama a Tcl_WaitForEvent para esperar a que ocurran eventos. Si hay eventos pendientes, o si Tcl_WaitForEvent tiene éxito, llama a Tcl_ServiceEvent para procesar el evento más antiguo de la cola.
[2]
Itinerario a través de todos los orígenes de eventos registrados y llama a su procedimiento de configuración. Cada procedimiento de configuración debería hacer lo necesario para garantizar que la aplicación se active cuando ocurran los eventos para los que está configurado. Por ejemplo, el origen de eventos de archivo podría registrar manejadores de archivos, mientras que el origen de eventos de temporizador podría establecer un temporizador para que se active en un momento determinado.
[3]
Itinerario a través de todos los orígenes de eventos registrados y llama a su procedimiento de comprobación. Cada procedimiento de comprobación debe determinar si hay algún evento de su tipo que esté listo para ser procesado. Si hay eventos listos, el procedimiento de comprobación los pone en cola llamando a Tcl_QueueEvent.
[4]
See if there are any events in the event queue. If so, service the first event in the queue by invoking its associated event handler procedure. Remove the event from the queue and return.
[5]
Verifica la cola de eventos para ver si contiene algún evento que pueda ser atendido. Si es así, atiende el primer evento posible, lo elimina de la cola y regresa.
[6]
Verifica si hay callbacks inactivos pendientes. Si es así, invócalos a todos y regresa.
[7]
Devuelve 0 para indicar que no había eventos listos, o vuelve al paso [2] si el llamador solicitó bloqueo.

CREACIÓN DE UN NUEVO ORIGEN DE EVENTOS

Un origen de eventos consta de tres procedimientos invocados por el notificador, además de procedimientos C adicionales que son invocados por código de nivel superior para organizar callbacks dirigidos por eventos. Los tres procedimientos llamados por el notificador consisten en los procedimientos de configuración y comprobación descritos anteriormente, más un procedimiento adicional que se invoca cuando se elimina un evento de la cola de eventos para su atención.

El procedimiento Tcl_CreateEventSource crea un nuevo origen de eventos. Sus argumentos especifican el procedimiento de configuración y el procedimiento de comprobación para el origen de eventos. SetupProc debe coincidir con el siguiente prototipo:

typedef void Tcl_EventSetupProc(
        ClientData clientData,
        int flags);

El argumento clientData será el mismo que el argumento clientData para Tcl_CreateEventSource; típicamente se utiliza para apuntar a información privada gestionada por el origen de eventos. El argumento flags será el mismo que el argumento flags pasado a Tcl_DoOneEvent, excepto que nunca será 0 (Tcl_DoOneEvent reemplaza 0 con TCL_ALL_EVENTS). Flags indica qué tipos de eventos deben considerarse; si el bit correspondiente a este origen de eventos no está establecido, el origen de eventos debe regresar inmediatamente sin hacer nada. Por ejemplo, el origen de eventos de archivo comprueba el bit TCL_FILE_EVENTS.

El trabajo de SetupProc es asegurarse de que la aplicación se active cuando ocurran eventos del tipo deseado. Esto se hace típicamente de manera dependiente de la plataforma. Por ejemplo, en Unix un origen de eventos podría llamar a Tcl_CreateFileHandler; en Windows podría solicitar notificación con un evento de Windows. Para orígenes de eventos dirigidos por temporizadores, como eventos de temporizador o cualquier evento sondeado, el origen de eventos puede llamar a Tcl_SetMaxBlockTime para forzar que la aplicación se active después de un tiempo especificado, incluso si no han ocurrido eventos. Si ningún origen de eventos llama a Tcl_SetMaxBlockTime, entonces Tcl_WaitForEvent esperará el tiempo necesario para que ocurra un evento; de lo contrario, solo esperará tanto como el intervalo más corto pasado a Tcl_SetMaxBlockTime por uno de los orígenes de eventos. Si un origen de eventos sabe que ya tiene eventos listos para informar, puede solicitar un tiempo de bloqueo cero. Por ejemplo, el procedimiento de configuración para el origen de eventos X busca si ya hay eventos en cola. Si los hay, llama a Tcl_SetMaxBlockTime con un tiempo de bloqueo de 0 para que Tcl_WaitForEvent no se bloquee si no hay datos nuevos en la conexión X. El argumento timePtr para Tcl_WaitForEvent apunta a una estructura que describe un intervalo de tiempo en segundos y microsegundos:

typedef struct Tcl_Time {
    long sec;
    long usec;
} Tcl_Time;

El campo usec debe ser menor que 1000000.

La información proporcionada a Tcl_SetMaxBlockTime solo se utiliza para la próxima llamada a Tcl_WaitForEvent; se descarta después de que Tcl_WaitForEvent regresa. La próxima vez que se realice una espera de eventos, se llamará a los procedimientos de configuración de cada uno de los orígenes de eventos, y estos podrán especificar nueva información para esa espera de eventos.

Si la aplicación utiliza un bucle de eventos externo en lugar de Tcl_DoOneEvent, los orígenes de eventos pueden necesitar llamar a Tcl_SetMaxBlockTime en otros momentos. Por ejemplo, si se registra un nuevo manejador de eventos que necesita sondear eventos, el origen de eventos puede llamar a Tcl_SetMaxBlockTime para establecer el tiempo de bloqueo a cero para forzar que el bucle de eventos externo llame a Tcl. En este caso, Tcl_SetMaxBlockTime invoca Tcl_SetTimer con el intervalo más corto visto desde la última llamada a Tcl_DoOneEvent o Tcl_ServiceAll.

Además del procedimiento genérico Tcl_SetMaxBlockTime, otros procedimientos específicos de la plataforma también pueden estar disponibles para setupProc, si hay información adicional necesaria para Tcl_WaitForEvent en esa plataforma. Por ejemplo, en sistemas Unix se puede usar la interfaz Tcl_CreateFileHandler para esperar eventos de archivo.

El segundo procedimiento proporcionado por cada origen de eventos es su procedimiento de comprobación, indicado por el argumento checkProc a Tcl_CreateEventSource. CheckProc debe coincidir con el siguiente prototipo:

typedef void Tcl_EventCheckProc(
        ClientData clientData,
        int flags);

Los argumentos para este procedimiento son los mismos que los de setupProc. CheckProc es invocado por Tcl_DoOneEvent después de haber esperado eventos. Presumiblemente, al menos un origen de eventos está ahora preparado para poner en cola un evento. Tcl_DoOneEvent llama a cada uno de los orígenes de eventos en turno, dándoles a todos la oportunidad de poner en cola cualquier evento que esté listo. El procedimiento de comprobación hace dos cosas. Primero, debe ver si algún evento se ha activado. Diferentes orígenes de eventos hacen esto de maneras diferentes.

Si el procedimiento de comprobación de un origen de eventos detecta un evento interesante, debe agregarlo a la cola de eventos de Tcl. Para hacer esto, el origen de eventos llama a Tcl_QueueEvent. El argumento evPtr es un puntero a una estructura asignada dinámicamente que contiene el evento (ver más abajo para más información sobre problemas de gestión de memoria). Cada origen de eventos puede definir su propia estructura de eventos con la información que sea relevante para ese origen de eventos. Sin embargo, el primer elemento de la estructura debe ser una estructura de tipo Tcl_Event, y la dirección de esta estructura se usa al comunicarse entre el origen de eventos y el resto del notificador. Un Tcl_Event tiene la siguiente definición:

typedef struct {
    Tcl_EventProc *proc;
    struct Tcl_Event *nextPtr;
} Tcl_Event;

El origen de eventos debe rellenar el campo proc del evento antes de llamar a Tcl_QueueEvent. El campo nextPtr se utiliza para enlazar los eventos en la cola y no debe ser modificado por el origen de eventos.

Un evento puede agregarse a la cola en cualquiera de las tres posiciones, dependiendo del argumento position a Tcl_QueueEvent:

TCL_QUEUE_TAIL
Agrega el evento al final de la cola, para que todos los demás eventos pendientes sean atendidos primero. Este es casi siempre el lugar correcto para los eventos nuevos.
TCL_QUEUE_HEAD
Agrega el evento al principio de la cola, para que sea atendido antes que todos los demás eventos en cola.
TCL_QUEUE_MARK
Agrega el evento al principio de la cola, a menos que haya otros eventos al principio cuya posición sea TCL_QUEUE_MARK; en caso afirmativo, agrega el nuevo evento justo después de todos los demás eventos TCL_QUEUE_MARK. Este valor de position se utiliza para insertar una secuencia ordenada de eventos al principio de la cola, como una serie de eventos Enter y Leave sintetizados durante una operación de grab o ungrab en Tk.

Cuando es el momento de manejar un evento de la cola (pasos 1 y 4 anteriores), Tcl_ServiceEvent invocará el proc especificado en la primera estructura Tcl_Event en cola. Proc debe coincidir con el siguiente prototipo:

typedef int Tcl_EventProc(
        Tcl_Event *evPtr,
        int flags);

El primer argumento de proc es un puntero al evento, que será el mismo que el primer argumento de la llamada a Tcl_QueueEvent que agregó el evento a la cola. El segundo argumento de proc es el argumento flags para la llamada actual a Tcl_ServiceEvent; esto es utilizado por el origen de eventos para regresar inmediatamente si sus eventos no son relevantes.

Depende de proc manejar el evento, típicamente invocando uno o más comandos Tcl o callbacks a nivel C. Una vez que el origen de eventos ha terminado de manejar el evento, devuelve 1 para indicar que el evento puede ser eliminado de la cola. Si por alguna razón el origen de eventos decide que el evento no puede ser atendido en este momento, puede devolver 0 para indicar que el evento debe ser diferido para su procesamiento posterior; en este caso Tcl_ServiceEvent continuará con el siguiente evento en la cola e intentará atenderlo. Hay varias razones por las que un origen de eventos podría diferir un evento. Una posibilidad es que los eventos de este tipo sean excluidos por el argumento flags. Por ejemplo, el origen de eventos de archivo siempre devolverá 0 si el bit TCL_FILE_EVENTS no está establecido en flags. Otro ejemplo de diferir eventos ocurre en Tk si se ha invocado Tk_RestrictEvents para diferir ciertos tipos de eventos de ventana.

Cuando proc devuelve 1, Tcl_ServiceEvent eliminará el evento de la cola de eventos y liberará su almacenamiento. Tenga en cuenta que el almacenamiento de un evento debe ser asignado por el origen de eventos (usando Tcl_Alloc o la macro Tcl ckalloc) antes de llamar a Tcl_QueueEvent, pero será liberado por Tcl_ServiceEvent, no por el origen de eventos.

Las aplicaciones multihilo funcionan de manera similar, excepto que hay una cola de eventos separada para cada hilo que contiene un intérprete de Tcl. Llamar a Tcl_QueueEvent en una aplicación multihilo agrega un evento a la cola del hilo actual. Para agregar un evento a la cola de otro hilo, use Tcl_ThreadQueueEvent. Tcl_ThreadQueueEvent acepta como argumento un argumento Tcl_ThreadId, que identifica de forma única un hilo en una aplicación Tcl. Para obtener el Tcl_ThreadId del hilo actual, use el procedimiento Tcl_GetCurrentThread. (Un hilo necesitaría pasar este identificador a otros hilos para que estos puedan agregar eventos a su cola). Después de agregar un evento a la cola de otro hilo, típicamente necesita llamar a Tcl_ThreadAlert para "despertar" al notificador de ese hilo y alertarlo sobre el nuevo evento.

Tcl_DeleteEvents se puede usar para eliminar explícitamente uno o más eventos de la cola de eventos. Tcl_DeleteEvents llama a proc para cada evento en la cola, eliminando aquellos para los que el procedimiento devuelve 1. Los eventos para los que el procedimiento devuelve 0 se dejan en la cola. Proc debe coincidir con el siguiente prototipo:

typedef int Tcl_EventDeleteProc(
        Tcl_Event *evPtr,
        ClientData clientData);

El argumento clientData será el mismo que el argumento clientData a Tcl_DeleteEvent

s; se usa típicamente para señalar información privada gestionada por la fuente de eventos. El *evPtr* apuntará al siguiente evento en la cola.

Tcl_DeleteEventSource elimina una fuente de eventos. Los argumentos *setupProc*, *checkProc* y *clientData* deben coincidir exactamente con los proporcionados a Tcl_CreateEventSource para que la fuente de eventos sea eliminada. Si no existe dicha fuente, Tcl_DeleteEventSource no tiene ningún efecto.

CREACIÓN DE UN NUEVO NOTIFICADOR

El notificador consiste en todos los procedimientos descritos en esta entrada del manual, más Tcl_DoOneEvent y Tcl_Sleep, que están disponibles en todas las plataformas, y Tcl_CreateFileHandler y Tcl_DeleteFileHandler, que son específicos de Unix. La mayoría de estos procedimientos son genéricos, en el sentido de que son los mismos para todos los notificadores. Sin embargo, ninguno de los procedimientos depende del notificador: Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_SetTimer, Tcl_Sleep, Tcl_WaitForEvent, Tcl_CreateFileHandler, Tcl_DeleteFileHandler y Tcl_ServiceModeHook. Para dar soporte a una nueva plataforma o para integrar Tcl con un bucle de eventos específico de la aplicación, debe escribir nuevas versiones de estos procedimientos.

Tcl_InitNotifier inicializa el estado del notificador y devuelve un manejador para el estado del notificador. Tcl llama a este procedimiento al inicializar un intérprete de Tcl. De manera similar, Tcl_FinalizeNotifier cierra el notificador y es llamado por Tcl_Finalize al cerrar un intérprete de Tcl.

Tcl_WaitForEvent es el procedimiento de nivel más bajo en el notificador; es responsable de esperar a que ocurra un evento “interesante” o a que transcurra un tiempo determinado. Antes de invocar Tcl_WaitForEvent, se habrá invocado el procedimiento de configuración de cada una de las fuentes de eventos. El argumento *timePtr* a Tcl_WaitForEvent proporciona el tiempo máximo para bloquearse a la espera de un evento, basándose en las llamadas a Tcl_SetMaxBlockTime realizadas por los procedimientos de configuración y en otra información (como el bit TCL_DONT_WAIT en *flags*).

Idealmente, Tcl_WaitForEvent solo debería esperar a que ocurra un evento; no debería procesar el evento de ninguna manera. Más adelante, las fuentes de eventos procesarán los eventos brutos y crearán Tcl_Events en la cola de eventos en sus procedimientos *checkProc*. Sin embargo, en algunas plataformas (como Windows) esto no es posible; los eventos pueden ser procesados en Tcl_WaitForEvent, incluyendo la puesta en cola de Tcl_Events y más (por ejemplo, se pueden invocar llamadas de retorno para widgets nativos). El valor de retorno de Tcl_WaitForEvent debe ser 0, 1 o -1. En plataformas como Windows, donde los eventos se procesan en Tcl_WaitForEvent, un valor de retorno de 1 significa que puede haber más eventos pendientes que aún no han sido procesados. Esto es una señal para el llamador de que debe llamar a Tcl_WaitForEvent nuevamente si desea que todos los eventos pendientes sean procesados. Un valor de retorno de 0 significa que llamar a Tcl_WaitForEvent nuevamente no tendrá ningún efecto: o bien es una plataforma donde Tcl_WaitForEvent solo espera sin hacer ningún procesamiento de eventos, o bien Tcl_WaitForEvent sabe con certeza que no hay eventos adicionales que procesar (por ejemplo, devolvió porque el tiempo transcurrió). Finalmente, un valor de retorno de -1 significa que el bucle de eventos ya no es operativo y la aplicación probablemente debería desenrollarse y terminar. Bajo Windows, esto ocurre cuando se recibe un mensaje WM_QUIT; bajo Unix, ocurre cuando Tcl_WaitForEvent habría esperado para siempre porque no había fuentes de eventos activas y el tiempo de espera era infinito.

Tcl_AlertNotifier se utiliza en aplicaciones multihilo para permitir que cualquier hilo “despierte” al notificador para alertarlo sobre nuevos eventos en su cola. Tcl_AlertNotifier requiere como argumento el manejador del notificador devuelto por Tcl_InitNotifier.

Si el notificador se va a utilizar con un bucle de eventos externo, entonces también debe soportar la interfaz Tcl_SetTimer. Tcl_SetTimer es invocado por Tcl_SetMaxBlockTime cada vez que el tiempo máximo de bloqueo se ha reducido. Tcl_SetTimer debe organizar que el bucle de eventos externo invoque Tcl_ServiceAll después del intervalo especificado, incluso si no han ocurrido eventos. Esta interfaz es necesaria porque Tcl_WaitForEvent no es invocado cuando hay un bucle de eventos externo. Si el notificador solo se va a usar desde Tcl_DoOneEvent, entonces Tcl_SetTimer no necesita hacer nada.

Tcl_ServiceModeHook es llamado por la parte independiente de la plataforma del notificador cuando el código cliente realiza una llamada a Tcl_SetServiceMode. Este hook se proporciona para soportar sistemas operativos que requieren un manejo especial de eventos cuando la aplicación está en un bucle modal (el notificador de Windows, por ejemplo, usa este hook para crear una ventana de comunicación).

En sistemas Unix, la fuente de eventos de archivo también necesita soporte del notificador. La fuente de eventos de archivo consiste en los procedimientos Tcl_CreateFileHandler y Tcl_DeleteFileHandler, que se describen en la página de manual de Tcl_CreateFileHandler.

Las interfaces Tcl_Sleep y Tcl_DoOneEvent se describen en sus respectivas páginas de manual.

La forma más fácil de crear un nuevo notificador es mirar el código de un notificador existente, como los archivos unix/tclUnixNotfy.c o win/tclWinNotify.c en la distribución fuente de Tcl.

REEMPLAZO DEL NOTIFICADOR

Un notificador que ha sido escrito de acuerdo con las convenciones anteriores también puede ser instalado en un proceso en ejecución en lugar del notificador estándar. Este mecanismo se utiliza para que un único ejecutable pueda ser utilizado (con el notificador estándar) como un programa autónomo y reutilizado (con un notificador de reemplazo en una extensión cargable) como una extensión a otro programa, como un plugin de navegador Web.

Para hacer esto, la extensión realiza una llamada a Tcl_SetNotifier pasando un puntero a una estructura de datos Tcl_NotifierProcs. La estructura tiene el siguiente diseño:

typedef struct Tcl_NotifierProcs {
    Tcl_SetTimerProc *setTimerProc;
    Tcl_WaitForEventProc *waitForEventProc;
    Tcl_CreateFileHandlerProc *createFileHandlerProc;
    Tcl_DeleteFileHandlerProc *deleteFileHandlerProc;
    Tcl_InitNotifierProc *initNotifierProc;
    Tcl_FinalizeNotifierProc *finalizeNotifierProc;
    Tcl_AlertNotifierProc *alertNotifierProc;
    Tcl_ServiceModeHookProc *serviceModeHookProc;
} Tcl_NotifierProcs;

Después de la llamada a Tcl_SetNotifier, los punteros proporcionados en la estructura Tcl_NotifierProcs reemplazan cualquier notificador que se hubiera instalado en el proceso.

Es extraordinariamente poco aconsejable reemplazar un notificador en ejecución. Normalmente, Tcl_SetNotifier debe ser llamado en el momento de la inicialización del proceso antes de la primera llamada a Tcl_InitNotifier.

BUCLES DE EVENTOS EXTERNOS

Las interfaces del notificador están diseñadas para que Tcl pueda ser incrustado en aplicaciones que tienen sus propios bucles de eventos privados. En este caso, la aplicación no llama a Tcl_DoOneEvent excepto en el caso de bucles de eventos recursivos como llamadas a los comandos Tcl update o vwait. La mayor parte del tiempo se pasa en el bucle de eventos externo de la aplicación. En este caso, el notificador debe organizar que el bucle de eventos externo llame de vuelta a Tcl cuando algo sucede en las diversas fuentes de eventos de Tcl. Estas llamadas de retorno deben organizar que se coloquen eventos de Tcl apropiados en la cola de eventos de Tcl.

Debido a que el bucle de eventos externo no llama a Tcl_DoOneEvent de forma regular, depende del notificador organizar que Tcl_ServiceEvent sea llamado cada vez que haya eventos pendientes en la cola de eventos de Tcl. La forma más fácil de hacerlo es invocar Tcl_ServiceAll al final de cada llamada de retorno desde el bucle de eventos externo. Esto asegurará que todas las fuentes de eventos sean encuestadas, que se atiendan todos los eventos en cola y que se procesen los manejadores inactivos pendientes antes de devolver el control a la aplicación. Además, las fuentes de eventos que necesitan encuestar eventos pueden llamar a Tcl_SetMaxBlockTime para forzar al bucle de eventos externo a llamar a Tcl incluso si no hay eventos disponibles en la cola de eventos del sistema.

Como efecto secundario del procesamiento de eventos detectados en el bucle de eventos externo principal, Tcl puede invocar Tcl_DoOneEvent para iniciar un bucle de eventos recursivo en comandos como vwait. Tcl_DoOneEvent invocará el bucle de eventos externo, lo que resultará en llamadas de retorno como se describe en el párrafo anterior, lo que resultará en llamadas a Tcl_ServiceAll. Sin embargo, en estos casos, es indeseable procesar eventos en Tcl_ServiceAll. Procesar eventos allí es innecesario porque el control volverá inmediatamente al bucle de eventos externo y, por lo tanto, a Tcl_DoOneEvent, que puede procesar los eventos por sí mismo. Además, Tcl_DoOneEvent se supone que procesa solo un evento, mientras que Tcl_ServiceAll normalmente procesa todos los eventos pendientes. Para manejar esta situación, Tcl_DoOneEvent establece una bandera para Tcl_ServiceAll que hace que devuelva sin procesar ningún evento. Esta bandera se llama *modo de servicio*; Tcl_DoOneEvent la restaura a su valor anterior antes de devolverla.

En algunos casos, sin embargo, puede ser necesario que Tcl_ServiceAll procese eventos incluso cuando ha sido invocado desde Tcl_DoOneEvent. Esto ocurre cuando hay otro bucle de eventos recursivo invocado a través de un manejador de eventos llamado por Tcl_DoOneEvent (como uno que es parte de un widget nativo). En este caso, Tcl_DoOneEvent puede no tener la oportunidad de procesar eventos, por lo que Tcl_ServiceAll debe procesarlos todos. Cualquier bucle de eventos recursivo que llame a un bucle de eventos externo en lugar de Tcl_DoOneEvent debe restablecer el modo de servicio para que todos los eventos se procesen en Tcl_ServiceAll. Esto se hace invocando el procedimiento Tcl_SetServiceMode. Si a Tcl_SetServiceMode se le pasa TCL_SERVICE_NONE, entonces las llamadas a Tcl_ServiceAll devolverán inmediatamente sin procesar ningún evento. Si a Tcl_SetServiceMode se le pasa TCL_SERVICE_ALL, entonces las llamadas a Tcl_ServiceAll se comportarán normalmente. Tcl_SetServiceMode devuelve el valor anterior del modo de servicio, que debe restaurarse cuando salga el bucle recursivo. Tcl_GetServiceMode devuelve el valor actual del modo de servicio.

NAME

Tcl_SetNotifier, Tcl_GetNotifier - Await events from a set of file descriptors and timers

SYNOPSIS

#include <tcl.h>

void
Tcl_SetNotifier(
    Tcl_NotifierProcs *notifierPtr
);

Tcl_NotifierProcs *
Tcl_GetNotifier(
    void
);

ARGUMENTS

Tcl_NotifierProcs *notifierPtr
Specifies the new notifier procedures to use.

INTRODUCTION

The Tcl event loop is responsible for processing events that occur in the Tcl application. Events can come from various sources, such as file descriptors (e.g., sockets, pipes), timers, and idle events. The event loop waits for these events to occur and then dispatches them to the appropriate handlers.

The Tcl event loop uses a notifier to interact with the underlying operating system to wait for events. The notifier is a set of procedures that Tcl calls to register event sources, wait for events, and process them. By default, Tcl uses a standard notifier that supports file events, timer events, and idle events.

NOTIFIER BASICS

The notifier is implemented as a structure of function pointers, Tcl_NotifierProcs. This structure allows Tcl to be independent of the specific event waiting mechanism used by the operating system. The structure is defined as follows:

typedef struct Tcl_NotifierProcs {
    Tcl_SetTimerProc *setTimerProc;
    Tcl_DoOneEventProc *doOneEventProc;
    Tcl_WaitEvtProc *waitEvtProc;
    Tcl_CreateFileHandlerProc *createFileHandlerProc;
    Tcl_DeleteFileHandlerProc *deleteFileHandlerProc;
    Tcl_AlertNotifierProc *alertNotifierProc;
    Tcl_ServiceModeHookProc *serviceModeHookProc;
} Tcl_NotifierProcs;

Each of these function pointers points to a procedure that performs a specific task related to event notification. Tcl_SetNotifier allows you to replace the default notifier with a custom one. Tcl_GetNotifier returns a pointer to the current notifier procedures.

CREATING A NEW EVENT SOURCE

To create a new event source, you need to implement the necessary procedures in your custom notifier. For example, if you want to add support for a new type of event, you would need to modify the event loop to handle it. This typically involves:

  1. Adding a new event type identifier.
  2. Modifying the event queue to store events of the new type.
  3. Implementing a way to generate events of the new type.
  4. Integrating the new event source with the notifier so that the event loop can wait for and process these events.

CREATING A NEW NOTIFIER

To create a new notifier, you need to define a Tcl_NotifierProcs structure and fill in the function pointers with your custom procedures. These procedures will be responsible for handling event notification and processing. For example, you might want to implement a custom notifier for a specific platform or for a specialized application that requires a different event handling mechanism.

The custom notifier procedures should adhere to the Tcl API and interact correctly with the Tcl event loop. This includes registering and unregistering event sources, waiting for events, and dispatching them to the appropriate handlers.

REPLACING THE NOTIFIER

You can replace the default Tcl notifier with your custom notifier by calling the Tcl_SetNotifier function with a pointer to your Tcl_NotifierProcs structure. This should be done early in the Tcl application's initialization process, before the event loop starts processing events.

// Example of replacing the notifier
Tcl_NotifierProcs myNotifier;
// ... initialize myNotifier with custom procedures ...
Tcl_SetNotifier(&myNotifier);

Note that replacing the notifier can have significant implications on the behavior of the Tcl event loop. Ensure that your custom notifier is fully compatible with Tcl's event handling mechanisms.

EXTERNAL EVENT LOOPS

Tcl can also be integrated with external event loops. In such cases, the Tcl event loop might not be directly responsible for waiting for events. Instead, the external event loop handles the waiting, and Tcl is notified when events are ready to be processed. The Tcl_NotifierProcs structure provides hooks for this type of integration, allowing Tcl to adapt to different event loop implementations.
