ARGUMENTOS

Tcl_EventSetupProc *setupProc (entrada)
Procedimiento a invocar para preparar la espera de eventos en Tcl_DoOneEvent.
Tcl_EventCheckProc *checkProc (entrada)
Procedimiento para que Tcl_DoOneEvent lo invoque después de esperar eventos. Comprueba si han ocurrido eventos y, si es así, los pone en cola.
ClientData clientData (entrada)
Valor arbitrario de una palabra a pasar a setupProc, checkProc, o deleteProc.
const Tcl_Time *timePtr (entrada)
Indica la cantidad máxima de tiempo a esperar un evento. Se especifica como un intervalo (cuánto esperar), no como una hora absoluta (cuándo despertar). Si el puntero pasado a Tcl_WaitForEvent es NULL, significa que no hay un tiempo máximo de espera: esperar indefinidamente si es necesario.
Tcl_Event *evPtr (entrada)
Un evento a añadir a la cola de eventos. El espacio para el evento debe haber sido asignado por el llamante usando Tcl_Alloc o ckalloc.
Tcl_QueuePosition position (entrada)
Dónde añadir el nuevo evento en la cola: TCL_QUEUE_TAIL, TCL_QUEUE_HEAD, o TCL_QUEUE_MARK.
Tcl_ThreadId threadId (entrada)
Un identificador único para un hilo.
Tcl_EventDeleteProc *deleteProc (entrada)
Procedimiento a invocar para cada evento en cola en Tcl_DeleteEvents.
int flags (entrada)
Qué tipos de eventos deben ser atendidos. Estas banderas son las mismas que las pasadas a Tcl_DoOneEvent.
int mode (entrada)
Indica si los eventos deben ser atendidos por Tcl_ServiceAll. Debe ser uno de TCL_SERVICE_NONE o TCL_SERVICE_ALL.
Tcl_NotifierProcs* notifierProcPtr (entrada)
Estructura de punteros de función que describe procedimientos de notificador que van a reemplazar a los instalados en el ejecutable. Consulte REEMPLAZO DEL NOTIFICADOR para obtener más detalles.

INTRODUCCIÓN

Las interfaces descritas aquí se utilizan para personalizar el bucle de eventos de Tcl. Las dos personalizaciones más comunes son añadir nuevas fuentes de eventos y fusionar el bucle de eventos de Tcl con algún otro bucle de eventos, como uno proporcionado por una aplicación en la que Tcl está incrustado. Cada una de estas tareas se describe en una sección separada a continuación.

Los procedimientos de esta entrada del manual son los bloques de construcción con los que se construye el notificador de eventos de Tcl. El notificador de eventos es la capa más baja en el mecanismo de eventos de Tcl. Consiste en tres cosas:

[1]
Fuentes de eventos: estas representan las formas en que se pueden generar eventos. Por ejemplo, existe una fuente de eventos de temporizador que implementa el procedimiento Tcl_CreateTimerHandler y el comando after, y existe una fuente de eventos de archivo que implementa el procedimiento Tcl_CreateFileHandler en sistemas Unix. Una fuente de eventos debe trabajar con el notificador para detectar eventos en los momentos adecuados, registrarlos en la cola de eventos y, finalmente, notificar al software de nivel superior que han ocurrido. Los procedimientos Tcl_CreateEventSource, Tcl_DeleteEventSource, y Tcl_SetMaxBlockTime, Tcl_QueueEvent, y Tcl_DeleteEvents se utilizan principalmente por las fuentes de eventos.
[2]
La cola de eventos: para aplicaciones sin hilos, existe una única cola para toda la aplicación, que contiene eventos que han sido detectados pero aún no atendidos. Las fuentes de eventos colocan eventos en la cola para que puedan ser procesados en orden en momentos apropiados durante el bucle de eventos. La cola de eventos garantiza una disciplina justa de manejo de eventos, de modo que ninguna fuente de eventos pueda dejar a las otras hambrientas. También permite guardar eventos para ser atendidos en un momento futuro. Las aplicaciones con hilos funcionan de manera similar, excepto que existe una cola de eventos separada para cada hilo que contiene un intérprete Tcl. Tcl_QueueEvent se utiliza (principalmente por las fuentes de eventos) para añadir eventos a la cola de eventos y Tcl_DeleteEvents se usa para eliminar eventos de la cola sin procesarlos. En una aplicación con hilos, Tcl_QueueEvent añade un evento a la cola del hilo actual, y Tcl_ThreadQueueEvent añade un evento a una cola en un hilo específico.
[3]
El bucle de eventos: para detectar y procesar eventos, la aplicación entra en un bucle que espera a que ocurran eventos, los coloca en la cola de eventos y luego los procesa. La mayoría de las aplicaciones lo harán llamando al procedimiento Tcl_DoOneEvent, que se describe en una entrada del manual separada.

La mayoría de las aplicaciones Tcl no necesitan preocuparse por ninguno de los detalles internos del notificador de Tcl. Sin embargo, el notificador ahora tiene suficiente flexibilidad para ser redirigido, ya sea a una nueva plataforma o para usar un bucle de eventos externo (como el bucle de eventos de Motif, cuando Tcl está incrustado en una aplicación de Motif). Los procedimientos Tcl_WaitForEvent y Tcl_SetTimer son implementados normalmente por Tcl, pero pueden ser reemplazados con nuevas versiones para redirigir el notificador (los procedimientos Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_Sleep, Tcl_CreateFileHandler, y Tcl_DeleteFileHandler también deben ser reemplazados; ver CREACIÓN DE UN NUEVO NOTIFICADOR abajo para más detalles). Los procedimientos Tcl_ServiceAll, Tcl_ServiceEvent, Tcl_GetServiceMode, y Tcl_SetServiceMode se proporcionan para ayudar a conectar el bucle de eventos de Tcl a un bucle de eventos externo como el de Motif.

BASES DEL NOTIFICADOR

La forma más fácil de entender cómo funciona el notificador es considerar lo que sucede cuando se llama a Tcl_DoOneEvent. Tcl_DoOneEvent recibe un argumento de flags que indica qué tipo de eventos está bien procesar y también si debe bloquearse o no si no hay eventos listos. Tcl_DoOneEvent hace lo siguiente:

[1]
Comprueba la cola de eventos para ver si contiene algún evento que pueda ser atendido. Si es así, atiende el primer evento posible, lo elimina de la cola y devuelve. Lo hace llamando a Tcl_ServiceEvent y pasando el argumento flags.
[2]
Se prepara para bloquear en espera de un evento. Para hacer esto, Tcl_DoOneEvent invoca un procedimiento setup en cada fuente de eventos. La fuente de eventos realizará una inicialización específica de la fuente de eventos y posiblemente llamará a Tcl_SetMaxBlockTime para limitar cuánto tiempo se bloqueará Tcl_WaitForEvent si no ocurren nuevos eventos.
[3]
Llama a Tcl_WaitForEvent. Este procedimiento se implementa de manera diferente en diferentes plataformas; espera a que ocurra un evento, basándose en la información proporcionada por las fuentes de eventos. Puede hacer que la aplicación se bloquee si timePtr especifica un intervalo distinto de 0. Tcl_WaitForEvent regresa cuando algo ha sucedido, como que un archivo se vuelve legible o expira el intervalo dado por timePtr. Si no hay eventos para que Tcl_WaitForEvent espere, por lo que se bloquearía indefinidamente, entonces regresa inmediatamente y Tcl_DoOneEvent devuelve 0.
[4]
Llama a un procedimiento check en cada fuente de eventos. El procedimiento check determina si ocurrieron eventos de interés para esta fuente. Si es así, los eventos se añaden a la cola de eventos.
[5]
Comprueba

CREACIÓN DE UNA NUEVA FUENTE DE EVENTOS

Una fuente de eventos consta de tres procedimientos invocados por el notificador, más procedimientos C adicionales que se invocan por código superior para organizar callbacks de eventos asincrónicos. Los tres procedimientos invocados por el notificador incluyen los procedimientos de configuración y verificación descritos anteriormente, más un procedimiento adicional que se invoca cuando un evento se elimina de la cola de eventos para ser procesado.

El procedimiento Tcl_CreateEventSource crea una nueva fuente de eventos. Sus argumentos especifican el procedimiento de configuración y verificación del evento. SetupProc debe coincidir con el siguiente prototipo:

typedef void Tcl_EventSetupProc(
        ClientData clientData,
        int flags);

El argumento clientData será el mismo que el argumento clientData de Tcl_CreateEventSource; suele usarse para apuntar a información privada gestionada por la fuente de eventos. El argumento flags será el mismo que el argumento flags pasado a Tcl_DoOneEvent, excepto que nunca será 0 (Tcl_DoOneEvent reemplaza 0 con TCL_ALL_EVENTS). Flags indica qué tipos de eventos deben considerarse; si el bit correspondiente a esta fuente de eventos no está activo, la fuente de eventos debe devolver inmediatamente sin realizar nada. Por ejemplo, la fuente de eventos de archivo verifica el bit TCL_FILE_EVENTS.

El SetupProc tiene el objetivo de asegurar que la aplicación se despierte cuando ocurran eventos del tipo deseado. Esto se suele realizar de forma dependiente de la plataforma. Por ejemplo, bajo Unix, una fuente de eventos podría llamar a Tcl_CreateFileHandler; bajo Windows, podría solicitar notificación con un evento de Windows. Para fuentes de eventos basadas en temporizadores, como eventos temporales o cualquier evento polleado, la fuente de eventos puede llamar a Tcl_SetMaxBlockTime para forzar a la aplicación a despertarse incluso si no han ocurrido eventos. Si ninguna fuente de eventos llama a Tcl_SetMaxBlockTime, Tcl_WaitForEvent esperará lo suficiente para que ocurra un evento; de lo contrario, solo esperará el tiempo más corto especificado por una de las fuentes de eventos. Si una fuente de eventos sabe que ya tiene eventos listos para reportar, puede solicitar un tiempo de bloqueo máximo de cero. Por ejemplo, el procedimiento de configuración de la fuente de eventos X busca si ya hay eventos en cola. Si los hay, llama a Tcl_SetMaxBlockTime con un tiempo de bloqueo de cero para que Tcl_WaitForEvent no se bloquee si no hay nuevos datos en la conexión X. El argumento timePtr de Tcl_WaitForEvent apunta a una estructura que describe un intervalo de tiempo en segundos y microsegundos:

typedef struct Tcl_Time {
    long sec;
    long usec;
} Tcl_Time;

El campo usec debe ser menor que 1000000.

La información proporcionada a Tcl_SetMaxBlockTime solo se usa para la siguiente llamada a Tcl_WaitForEvent; se descarta después de que Tcl_WaitForEvent retorne. La próxima vez que se realice una espera de evento, cada procedimiento de configuración de las fuentes de eventos se llamará de nuevo, y pueden especificar información nueva para esa espera de evento.

Si la aplicación usa un bucle de eventos externo en lugar de Tcl_DoOneEvent, las fuentes de eventos pueden necesitar llamar a Tcl_SetMaxBlockTime en otros momentos. Por ejemplo, si se registra un nuevo manejador de eventos que necesita esperar por eventos, la fuente de eventos puede llamar a Tcl_SetMaxBlockTime para establecer un tiempo de bloqueo de cero, forzando al bucle de eventos externo a llamar a Tcl. En este caso, Tcl_SetMaxBlockTime invoca Tcl_SetTimer con el intervalo más corto visto desde la última llamada a Tcl_DoOneEvent o Tcl_ServiceAll.

Además de la procedura genérica Tcl_SetMaxBlockTime, otras proceduras específicas de plataforma pueden estar disponibles para el setupProc, si es necesario proporcionar información adicional para Tcl_WaitForEvent en esa plataforma. Por ejemplo, en sistemas Unix se puede utilizar la interfaz Tcl_CreateFileHandler para esperar eventos de archivos.

El segundo procedimiento proporcionado por cada fuente de eventos es su procedimiento de verificación, indicado por el argumento checkProc de Tcl_CreateEventSource. CheckProc debe coincidir con el siguiente prototipo:

typedef void Tcl_EventCheckProc(
        ClientData clientData,
        int flags);

Los argumentos de este procedimiento son los mismos que los de setupProc. CheckProc es invocado por Tcl_DoOneEvent después de haber esperado eventos. Presumiblemente, al menos una fuente de eventos está ahora preparada para agregar un evento. Tcl_DoOneEvent llama a cada fuente de eventos por orden, por lo que todas tienen la oportunidad de agregar cualquier evento que esté listo. El procedimiento de verificación hace dos cosas. Primero, debe ver si hay eventos que se hayan activado. Diferentes fuentes de eventos lo hacen de manera diferente.

Si una fuente de eventos detecta un evento interesante, debe agregar el evento a la cola de eventos de Tcl. Para hacer esto, la fuente de eventos llama a Tcl_QueueEvent. El argumento evPtr es un puntero a una estructura asignada dinámicamente que contiene el evento (ver más abajo sobre problemas de gestión de memoria). Cada fuente de eventos puede definir su propia estructura de evento con información relevante para esa fuente de eventos. Sin embargo, el primer elemento de la estructura debe ser una estructura de tipo Tcl_Event, y el puntero a esta estructura se usa cuando se comunica entre la fuente de eventos y el resto del notificador. Una Tcl_Event tiene la siguiente definición:

typedef struct {
    Tcl_EventProc *proc;
    struct Tcl_Event *nextPtr;
} Tcl_Event;

La fuente de eventos debe llenar el campo proc de la estructura antes de llamar a Tcl_QueueEvent. El nextPtr se usa para enlazar los eventos en la cola y no debe ser modificado por la fuente de eventos.

Un evento puede ser agregado a la cola en una de tres posiciones, según el argumento position de Tcl_QueueEvent:

TCL_QUEUE_TAIL
Agregar el evento al final de la cola, así que todos los demás eventos pendientes serán procesados primero. Este es casi siempre el lugar correcto para nuevos eventos.
TCL_QUEUE_HEAD
Agregar el evento al frente de la cola, así que será procesado antes que todos los demás eventos en la cola.
TCL_QUEUE_MARK
Agregar el evento al frente de la cola, a menos que haya otros eventos al frente cuya posición sea TCL_QUEUE_MARK. Si es así, agregará el nuevo evento justo después de todos los demás eventos TCL_QUEUE_MARK. Este valor de position se utiliza para insertar una secuencia ordenada de eventos al frente de la cola, como una serie de eventos Enter y Leave generados durante una operación de arrastrar y soltar o de toma y suelta en Tk.

Cuando sea el momento de procesar un evento de la cola (pasos 1 y 4 arriba), Tcl_ServiceEvent invocará el proc especificado en la primera estructura Tcl_Event que se haya colocado en la cola. Proc debe coincidir con el siguiente prototipo:

typedef int Tcl_EventProc(
        Tcl_Event *evPtr,
        int flags);

El primer argumento de proc es un puntero al evento, que será el mismo que el primer argumento de la llamada a Tcl_QueueEvent que añadió el evento a la cola. El segundo argumento de proc es el flags de la llamada actual a Tcl_ServiceEvent; este se utiliza por la fuente de eventos para devolver inmediatamente si sus eventos no son relevantes.

Es responsabilidad de proc manejar el evento, generalmente invocando uno o más comandos Tcl o callbacks de nivel C. Una vez que la fuente de eventos ha terminado de manejar el evento, devuelve 1 para indicar que el evento puede ser eliminado de la cola. Si por alguna razón la fuente de eventos decide que el evento no puede ser manejado en este momento, puede devolver 0 para indicar que el evento debe ser pospuesto para ser procesado más tarde; en este caso, Tcl_ServiceEvent continuará con el siguiente evento en la cola e intentará procesarlo. Hay varias razones por las que una fuente de eventos podría posponer un evento. Una posibilidad es que los eventos de este tipo estén excluidos por el argumento flags. Por ejemplo, la fuente de eventos de archivo siempre devuelve 0 si el bit TCL_FILE_EVENTS no está activo en flags. Otro ejemplo de posposición de eventos ocurre en Tk si se ha llamado a Tk_RestrictEvents para posponer ciertos tipos de eventos de ventana.

Cuando proc devuelve 1, Tcl_ServiceEvent eliminará el evento de la cola y liberará su memoria. Se debe tener en cuenta que la memoria del evento debe ser asignada por la fuente de eventos (usando Tcl_Alloc o la macro Tcl ckalloc) antes de llamar a Tcl_QueueEvent, pero será liberada por Tcl_ServiceEvent, no por la fuente de eventos.

Las aplicaciones multihilo funcionan de manera similar, excepto que hay una cola de eventos separada para cada hilo que contiene un intérprete Tcl. Llamar a Tcl_QueueEvent en una aplicación multihilo agrega un evento a la cola del hilo actual. Para agregar un evento a la cola de otro hilo, use Tcl_ThreadQueueEvent. Tcl_ThreadQueueEvent acepta como argumento un Tcl_ThreadId, que identifica de forma única un hilo en una aplicación Tcl. Para obtener el Tcl_ThreadId del hilo actual, use el procedimiento Tcl_GetCurrentThread. (Un hilo entonces necesitaría pasar este identificador a otros hilos para que estos puedan agregar eventos a su cola.) Después de agregar un evento a la cola de otro hilo, típicamente necesitará llamar a Tcl_ThreadAlert para "despertar" a ese hilo y notificar al notificador de un nuevo evento.

Tcl_DeleteEvents puede usarse explícitamente para eliminar uno o más eventos de la cola de eventos. Tcl_DeleteEvents llama al proc para cada evento en la cola, eliminando aquellos que devuelven 1. Los eventos para los cuales el procedimiento devuelve 0 se mantienen en la cola. Proc debe coincidir con el siguiente prototipo:

typedef int Tcl_EventDeleteProc(
        Tcl_Event *evPtr,
        ClientData clientData);

El argumento clientData será el mismo que el argumento clientData de Tcl_Delete.

The structure has the following layout: .IS \fITcl_NotifierProcs\fR .DSS "Bd-indent" .TS HB 3in line Tcl_SetTimerProc *setTimerProc; Tcl_WaitForEventProc *waitForEventProc; Tcl_CreateFileHandlerProc *createFileHandlerProc; Tcl_DeleteFileHandlerProc *deleteFileHandlerProc; Tcl_InitNotifierProc *initNotifierProc; Tcl_FinalizeNotifierProc *finalizeNotifierProc; Tcl_AlertNotifierProc *alertNotifierProc; Tcl_ServiceModeHookProc *serviceModeHookProc; .TE .DE .PP Following the call to Tcl_SetNotifier, the pointers given in the Tcl_NotifierProcs structure replace whatever notifier had been installed in the process. .PP It is extraordinarily unwise to replace a running notifier. Normally, Tcl_SetNotifier should be called at process initialization time before the first call to Tcl_InitNotifier. .SH "EXTERNAL EVENT LOOPS" .PP The notifier interfaces are designed so that Tcl can be embedded into applications that have their own private event loops. In this case, the application does not call Tcl_DoOneEvent except in the case of recursive event loops such as calls to the Tcl commands update or vwait. Most of the time is spent in the external event loop of the application. In this case the notifier must arrange for the external event loop to call back into Tcl when something happens on the various Tcl event sources. These callbacks should arrange for appropriate Tcl events to be placed on the Tcl event queue. .PP Because the external event loop is not calling Tcl_DoOneEvent on a regular basis, it is up to the notifier to arrange for Tcl_ServiceEvent to be called whenever events are pending on the Tcl event queue. The easiest way to do this is to invoke Tcl_ServiceAll at the end of each callback from the external event loop. This will ensure that all of the event sources are polled, any queued events are serviced, and any pending idle handlers are processed before returning control to the application. In addition, event sources that need to poll for events can call Tcl_SetMaxBlockTime to force the external event loop to call Tcl even if no events are available on the system event queue. .PP As a side effect of processing events detected in the main external event loop, Tcl may invoke Tcl_DoOneEvent to start a recursive event loop in commands like vwait. Tcl_DoOneEvent will invoke the external event loop, which will result in callbacks as described in the preceding paragraph, which will result in calls to Tcl_ServiceAll. However, in these cases it is undesirable to service events in Tcl_ServiceAll. Servicing events there is unnecessary because control will immediately return to the external event loop and hence to Tcl_DoOneEvent, which can service the events itself. Furthermore, Tcl_DoOneEvent is supposed to service only a single event, whereas Tcl_ServiceAll normally services all pending events. To handle this situation, Tcl_DoOneEvent sets a flag for Tcl_ServiceAll that causes it to return without servicing any events. This flag is called the service mode; Tcl_DoOneEvent restores it to its previous value before it returns. .PP In some cases, however, it may be necessary for Tcl_ServiceAll to service events even when it has been invoked from Tcl_DoOneEvent. This happens when there is yet another recursive event loop invoked via an event handler called by Tcl_DoOneEvent (such as one that is part of a native widget). In this case, Tcl_DoOneEvent may not have a chance to service events so Tcl_ServiceAll must service them all. Any recursive event loop that calls an external event loop rather than Tcl_DoOneEvent must reset the service mode so that all events get processed in Tcl_ServiceAll. This is done by invoking the Tcl_SetServiceMode procedure. If Tcl_SetServiceMode is passed TCL_SERVICE_NONE, then calls to Tcl_ServiceAll will return immediately without processing any events. If Tcl_SetServiceMode is passed TCL_SERVICE_ALL, then calls to Tcl_ServiceAll will behave normally. Tcl_SetServiceMode returns the previous value of the service mode, which should be restored when the recursive loop exits. Tcl_GetServiceMode returns the current value of the service mode. .SH "SEE ALSO" Tcl_CreateFileHandler(3), Tcl_DeleteFileHandler(3), Tcl_Sleep(3), Tcl_DoOneEvent(3), Thread(3) .SH "KEYWORDS" Tcl_GetCurrentThread(3) - Arch manual pages

NAME

Tcl_GetCurrentThread - return the current thread identifier

SYNOPSIS

#include <tcl.h>

Tcl_ThreadId

);

ARGUMENTS

None.

INTRODUCTION

The Tcl event loop mechanism is designed to be used with multiple threads. In order to allow Tcl commands and C code to manage events for specific threads, Tcl provides a thread identification mechanism. The Tcl_GetCurrentThread function returns the identifier for the current thread.

NOTIFIER BASICS

A notifier is a data structure that manages the event loop for a Tcl thread. It is responsible for monitoring event sources and dispatching events to the appropriate handlers. The Tcl notifier provides basic mechanisms for event handling, including:

  • Event Queue: A queue that stores pending events.

  • Event Sources: Mechanisms for detecting events from various sources, such as file descriptors, timers, and interpreter events.

  • Timer Events: Events that are triggered after a specified time interval.

  • Idle Events: Events that are triggered when the event loop is idle.

  • Service Mode: A mode that allows the event loop to process events periodically even when no explicit events are pending.

  • Threads: The underlying threading model that Tcl uses to manage concurrent event loops.

CREATING A NEW EVENT SOURCE

You can create a new event source by registering a callback function with the Tcl notifier. This callback function will be invoked when an event occurs on the associated source.

CREATING A NEW NOTIFIER

You can create a new notifier for a thread by calling Tcl_CreateNotifier. This function initializes a new notifier structure and associates it with the current thread.

REPLACING THE NOTIFIER

In some cases, you may need to replace the default Tcl notifier with a custom implementation. This can be done by calling Tcl_SetNotifier with a pointer to your custom notifier structure.

EXTERNAL EVENT LOOPS

Tcl allows you to integrate its event loop with external event loops, such as those provided by GUI toolkits. This is typically achieved by using functions like Tcl_CreateFileHandler and Tcl_DoOneEvent to interact with the Tcl event system from your external loop.
