Especifica la disposición de los manejadores stdio en la canalización: combinación OR de TCL_STDIN, TCL_STDOUT, TCL_STDERR y TCL_ENFORCE_MODE. Si TCL_ENFORCE_MODE no está establecido, la canalización puede redirigir los manejadores stdio para anular los manejadores stdio para los cuales se han establecido TCL_STDIN, TCL_STDOUT y TCL_STDERR. DESCRIPCIÓN

El mecanismo de canales Tcl proporciona un mecanismo independiente de dispositivos y de plataforma para realizar operaciones de entrada y salida con búfer en una variedad de tipos de archivos, sockets y dispositivos. El mecanismo de canales es extensible a nuevos tipos de canales, proporcionando un controlador de canal de bajo nivel para el nuevo tipo; la interfaz del controlador de canal se describe en la entrada del manual de Tcl_CreateChannel. El mecanismo de canales proporciona un esquema de búfer modelado según la E/S estándar de Unix, y también permite E/S no bloqueantes en los canales.

Los procedimientos descritos en esta entrada del manual comprenden la capa genérica de la arquitectura de canales de las APIs de C. Para obtener una descripción de la arquitectura del controlador de canales y cómo implementar controladores de canales para nuevos tipos de canales, consulte la entrada del manual de Tcl_CreateChannel.

TCL_OPENFILECHANNEL

Tcl_OpenFileChannel abre un archivo especificado por fileName y devuelve un manejador de canal que puede ser utilizado para realizar entrada y salida en el archivo. Esta API está modelada después del procedimiento fopen de la biblioteca estándar de E/S de Unix. La sintaxis y el significado de todos los argumentos son similares a los dados en el comando open de Tcl al abrir un archivo. Si ocurre un error al abrir el canal, Tcl_OpenFileChannel devuelve NULL y registra un código de error POSIX que puede ser recuperado con Tcl_GetErrno. Además, si interp no es NULL, Tcl_OpenFileChannel deja un mensaje de error en el resultado de interp después de cualquier error. A partir de Tcl 8.4, la API basada en valores Tcl_FSOpenFileChannel debe usarse en lugar de Tcl_OpenFileChannel siempre que sea posible.

El canal recién creado no se registra en el intérprete suministrado; para registrarlo, use Tcl_RegisterChannel, descrito a continuación. Si uno de los canales estándar, stdin, stdout o stderr se cerró previamente, el acto de crear el nuevo canal también lo asigna como reemplazo del canal estándar.

TCL_OPENCOMMANDCHANNEL

Tcl_OpenCommandChannel proporciona una interfaz de nivel C a las funciones de los comandos exec y open. Crea una secuencia de subprocesos especificados por los argumentos argv y argc y devuelve un canal que puede ser utilizado para comunicarse con estos subprocesos. El argumento flags indica qué tipo de comunicación existirá con la tubería de comandos.

Si el flag TCL_STDIN está establecido, entonces la entrada estándar del primer subproceso estará vinculada al canal: escribir en el canal proporcionará entrada al subproceso. Si TCL_STDIN no está establecido, entonces la entrada estándar para el primer subproceso será la misma que la entrada estándar de esta aplicación. Si TCL_STDOUT está establecido, entonces la salida estándar del último subproceso se puede leer del canal; de lo contrario, va a la salida estándar de esta aplicación. Si TCL_STDERR está establecido, la salida de error estándar para todos los subprocesos se devuelve al canal y resulta en un error cuando se cierra el canal; de lo contrario, va al error estándar de esta aplicación. Si TCL_ENFORCE_MODE no está establecido, entonces argc y argv pueden redirigir los manejadores de stdio para anular TCL_STDIN, TCL_STDOUT y TCL_STDERR; si está establecido, entonces es un error que argc y argv anulen los canales de stdio para los cuales se han establecido TCL_STDIN, TCL_STDOUT y TCL_STDERR.

Si ocurre un error al abrir el canal, Tcl_OpenCommandChannel devuelve NULL y registra un código de error POSIX que puede ser recuperado con Tcl_GetErrno. Además, Tcl_OpenCommandChannel deja un mensaje de error en el resultado del intérprete. interp no puede ser NULL.

El canal recién creado no se registra en el intérprete suministrado; para registrarlo, use Tcl_RegisterChannel, descrito a continuación. Si uno de los canales estándar, stdin, stdout o stderr se cerró previamente, el acto de crear el nuevo canal también lo asigna como reemplazo del canal estándar.

TCL_MAKEFILECHANNEL

Tcl_MakeFileChannel crea un Tcl_Channel a partir de un manejador de archivo existente, específico de la plataforma. El canal recién creado no se registra en el intérprete suministrado; para registrarlo, use Tcl_RegisterChannel, descrito a continuación. Si uno de los canales estándar, stdin, stdout o stderr se cerró previamente, el acto de crear el nuevo canal también lo asigna como reemplazo del canal estándar.

TCL_GETCHANNEL

Tcl_GetChannel devuelve un canal dado el channelName utilizado para crearlo con Tcl_CreateChannel y un puntero a un intérprete de Tcl en interp. Si no se registra un canal con ese nombre en ese intérprete, el procedimiento devuelve NULL. Si el argumento modePtr no es NULL, apunta a una variable entera que recibirá una combinación OR de TCL_READABLE y TCL_WRITABLE describiendo si el canal está abierto para lectura y escritura.

Tcl_GetChannelNames y Tcl_GetChannelNamesEx escriben los nombres de los canales registrados en el resultado del intérprete como un valor de lista. Tcl_GetChannelNamesEx filtrará estos nombres de acuerdo con el pattern. Si pattern es NULL, entonces no hará ningún filtrado. El valor de retorno es TCL_OK si no ocurrieron errores al escribir en el resultado, de lo contrario es TCL_ERROR, y el mensaje de error se deja en el resultado del intérprete.

TCL_REGISTERCHANNEL

Tcl_RegisterChannel agrega un canal al conjunto de canales accesibles en interp. Después de esta llamada, los programas de Tcl que se ejecutan en ese intérprete pueden referirse al canal en operaciones de entrada o salida utilizando el nombre dado en la llamada a Tcl_CreateChannel. Después de esta llamada, el canal se convierte en propiedad del intérprete, y el llamador no debe llamar a Tcl_Close para el canal; el canal se cerrará automáticamente cuando se desregistre del intérprete.

El código que se ejecuta fuera de cualquier intérprete de Tcl puede llamar a Tcl_RegisterChannel con interp como NULL, para indicar que desea mantener una referencia a este canal. Posteriormente, el canal puede registrarse en un intérprete de Tcl y solo se cerrará cuando el número correspondiente de llamadas a Tcl_UnregisterChannel se haya realizado. Esto permite que el código que se ejecuta fuera de cualquier intérprete mantenga de forma segura una referencia a un canal que también está registrado en un intérprete de Tcl.

Este procedimiento interactúa con el código que administra los canales estándar. Si no se inicializaron canales estándar antes de la primera llamada a Tcl_RegisterChannel, se inicializarán con esa llamada. Ver Tcl_StandardChannels para un tratado general sobre los canales estándar y el comportamiento de la biblioteca Tcl con respecto a ellos.

TCL_UNREGISTERCHANNEL

Tcl_UnregisterChannel elimina un canal del conjunto de canales accesibles en interp. Después de esta llamada, los programas de Tcl ya no podrán usar el nombre del canal para referirse al canal en ese intérprete. Si esta operación eliminó el último registro del canal en cualquier intérprete, el canal también se cierra y destruye.

El código que no está asociado con un intérprete de Tcl puede llamar a Tcl_UnregisterChannel con interp como NULL, para indicar a Tcl que ya no tiene una referencia a ese canal. Si esta es la última referencia al canal, ahora se cerrará. Tcl_UnregisterChannel es muy similar a Tcl_DetachChannel, excepto que también cerrará el canal si no existen más referencias a él.

TCL_DETACHCHANNEL

Tcl_DetachChannel elimina un canal del conjunto de canales accesibles en interp. Después de esta llamada, los programas de Tcl ya no podrán usar el nombre del canal para referirse al canal en ese intérprete. Más allá de eso, este comando no tiene ningún efecto adicional. No se puede utilizar en los canales estándar (stdout, stderr, stdin) y devolverá TCL_ERROR si se le pasa uno de esos canales.

El código no asociado con un intérprete de Tcl puede llamar a Tcl_DetachChannel con interp como NULL, para indicar a Tcl que ya no tiene una referencia a ese canal. Si esta es la última referencia al canal, a diferencia de Tcl_UnregisterChannel, no se cerrará.

TCL_ISSTANDARDCHANNEL

Tcl_IsStandardChannel prueba si un canal es uno de los tres canales estándar, stdin, stdout o stderr. Si es así, devuelve 1, de lo contrario 0.

No se hace ningún intento de verificar si el canal dado o los canales estándar están inicializados o son válidos de otra manera.

TCL_CLOSE

Tcl_Close destruye el canal channel, que debe denotar un canal actualmente abierto. El canal no debe estar registrado en ningún intérprete cuando se llama a Tcl_Close. La salida en búfer se vacía en el dispositivo de salida del canal antes de destruir el canal, y la entrada en búfer se descarta. Si este es un canal de bloqueo, la llamada no regresa hasta que todos los datos en búfer se envían exitosamente al dispositivo de salida del canal. Si este es un canal sin bloqueo y hay salida en búfer que no se puede escribir sin bloquear, la llamada regresa inmediatamente; la salida se vacía en segundo plano y el canal se cerrará una vez que todos los datos en búfer se hayan enviado. En este caso, los errores durante el vaciado no se informan.

Si el canal se cerró correctamente, Tcl_Close devuelve TCL_OK. Si ocurre un error, Tcl_Close devuelve TCL_ERROR y registra un código de error POSIX que puede ser recuperado con Tcl_GetErrno. Si el canal se está cerrando sincrónicamente y ocurre un error durante el cierre del canal y interp no es NULL, se deja un mensaje de error en el resultado del intérprete.

Nota: no es seguro llamar a Tcl_Close en un canal que ha sido registrado usando Tcl_RegisterChannel; vea la documentación para Tcl_RegisterChannel, arriba, para más detalles. Si el canal se ha pasado alguna vez como argumento chan en una llamada a Tcl_RegisterChannel, debería usar en su lugar Tcl_UnregisterChannel, que llamará internamente a Tcl_Close cuando todas las llamadas a Tcl_RegisterChannel hayan sido emparejadas con las llamadas correspondientes a Tcl_UnregisterChannel.

TCL_READCHARS Y TCL_READ

Tcl_ReadChars consume bytes del channel, convirtiendo los bytes a UTF-8 basándose en la codificación del canal y almacenando los datos producidos en la representación de cadena de readObjPtr. El valor de retorno de Tcl_ReadChars es el número de caracteres, hasta charsToRead, que se almacenaron en readObjPtr. Si ocurre un error al leer, el valor de retorno es -1 y Tcl_ReadChars registra un código de error POSIX que puede ser recuperado con Tcl_GetErrno.

Establecer chars

TCL_READOBJECTS, TCL_READCHARS, TCL_READ, AND TCL_READRAW

Tcl_ReadChars reads up to bytesToRead bytes from channel into the buffer pointed to by readObjPtr. The bytes are converted to UTF-8 according to the channel's encoding and stored in readObjPtr's internal representation. The return value is the number of bytes actually read. If bytesToRead is specified as -1, the command will read all characters currently available (non-blocking) or everything until EOF (blocking mode).

The return value may be smaller than the value to read, indicating that less data than requested was available. This is called a short read. In blocking mode, this can only happen on an end-of-file. In nonblocking mode, a short read can also occur if there is not enough input currently available: Tcl_ReadChars returns a short count rather than waiting for more data.

If the channel is in blocking mode, a return value of zero indicates an end-of-file condition. If the channel is in nonblocking mode, a return value of zero indicates either that no input is currently available or an end-of-file condition. Use Tcl_Eof and Tcl_InputBlocked to tell which of these conditions actually occurred.

Tcl_ReadChars translates the various end-of-line representations into the canonical \n internal representation according to the current end-of-line recognition mode. End-of-line recognition and the various platform-specific modes are described in the manual entry for the Tcl fconfigure command.

As a performance optimization, when reading from a channel with the encoding binary, the bytes are not converted to UTF-8 as they are read. Instead, they are stored in readObjPtr's internal representation as a byte-array value. The string representation of this value will only be constructed if it is needed (e.g., because of a call to Tcl_GetStringFromObj). In this way, byte-oriented data can be read from a channel, manipulated by calling Tcl_GetByteArrayFromObj and related functions, and then written to a channel without the expense of ever converting to or from UTF-8.

Tcl_Read is similar to Tcl_ReadChars, except that it does not do encoding conversions, regardless of the channel's encoding. It is deprecated and exists for backwards compatibility with non-internationalized Tcl extensions. It consumes bytes from channel and stores them in readBuf, performing end-of-line translations on the way. The return value of Tcl_Read is the number of bytes, up to bytesToRead, written in readBuf. The buffer produced by Tcl_Read is not null-terminated. Its contents are valid from the zeroth position up to and excluding the position indicated by the return value.

Tcl_ReadRaw is the same as Tcl_Read but does not compensate for stacking. While Tcl_Read (and the other functions in the API) always get their data from the topmost channel in the stack the supplied channel is part of, Tcl_ReadRaw does not. Thus this function is only usable for transformational channel drivers, i.e. drivers used in the middle of a stack of channels, to move data from the channel below into the transformation.

TCL_GETSOBJ AND TCL_GETS

Tcl_GetsObj consumes bytes from channel, converting the bytes to UTF-8 based on the channel's encoding, until a full line of input has been seen. If the channel's encoding is binary, each byte read from the channel is treated as an individual Unicode character. All of the characters of the line except for the terminating end-of-line character(s) are appended to lineObjPtr's string representation. The end-of-line character(s) are read and discarded.

If a line was successfully read, the return value is greater than or equal to zero and indicates the number of bytes stored in lineObjPtr. If an error occurs, Tcl_GetsObj returns -1 and records a POSIX error code that can be retrieved with Tcl_GetErrno. Tcl_GetsObj also returns -1 if the end of the file is reached; the Tcl_Eof procedure can be used to distinguish an error from an end-of-file condition.

If the channel is in nonblocking mode, the return value can also be -1 if no data was available or the data that was available did not contain an end-of-line character. When -1 is returned, the Tcl_InputBlocked procedure may be invoked to determine if the channel is blocked because of input unavailability.

Tcl_Gets is the same as Tcl_GetsObj except the resulting characters are appended to the dynamic string given by lineRead rather than a Tcl value.

TCL_UNGETS

Tcl_Ungets is used to add data to the input queue of a channel, at either the head or tail of the queue. The pointer input points to the data that is to be added. The length of the input to add is given by inputLen. A non-zero value of addAtEnd indicates that the data is to be added at the end of queue; otherwise it will be added at the head of the queue. If channel has a “sticky” EOF set, no data will be added to the input queue. Tcl_Ungets returns inputLen or -1 if an error occurs.

TCL_WRITECHARS, TCL_WRITEOBJ, AND TCL_WRITE

Tcl_WriteChars accepts bytesToWrite bytes of character data at charBuf. The UTF-8 characters in the buffer are converted to the channel's encoding and queued for output to channel. If bytesToWrite is negative, Tcl_WriteChars expects charBuf to be null-terminated and it outputs everything up to the null.

Data queued for output may not appear on the output device immediately, due to internal buffering. If the data should appear immediately, call Tcl_Flush after the call to Tcl_WriteChars, or set the -buffering option on the channel to none. If you wish the data to appear as soon as a complete line is accepted for output, set the -buffering option on the channel to line mode.

The return value of Tcl_WriteChars is a count of how many bytes were accepted for output to the channel. This is either greater than zero to indicate success or -1 to indicate that an error occurred. If an error occurs, Tcl_WriteChars records a POSIX error code that may be retrieved with Tcl_GetErrno.

Newline characters in the output data are translated to platform-specific end-of-line sequences according to the -translation option for the channel. This is done even if the channel has no encoding.

Tcl_WriteObj is similar to Tcl_WriteChars except it accepts a Tcl value whose contents will be output to the channel. The UTF-8 characters in writeObjPtr's string representation are converted to the channel's encoding and queued for output to channel. As a performance optimization, when writing to a channel with the encoding binary, UTF-8 characters are not converted as they are written. Instead, the bytes in writeObjPtr's internal representation as a byte-array value are written to the channel. The byte-array representation of the value will be constructed if it is needed. In this way, byte-oriented data can be read from a channel, manipulated by calling Tcl_GetByteArrayFromObj and related functions, and then written to a channel without the expense of ever converting to or from UTF-8.

Tcl_Write is similar to Tcl_WriteChars except that it does not do encoding conversions, regardless of the channel's encoding. It is deprecated and exists for backwards compatibility with non-internationalized Tcl extensions. It accepts bytesToWrite bytes of data at byteBuf and queues them for output to channel. If bytesToWrite is negative, Tcl_Write expects byteBuf to be null-terminated and it outputs everything up to the null.

Tcl_WriteRaw is the same as Tcl_Write but does not compensate for stacking. While Tcl_Write (and the other functions in the API) always feed their input to the topmost channel in the stack the supplied channel is part of, Tcl_WriteRaw does not. Thus this function is only usable for transformational channel drivers, i.e. drivers used in the middle of a stack of channels, to move data from the transformation into the channel below it.

TCL_FLUSH

Tcl_Flush causes all of the buffered output data for channel to be written to its underlying file or device as soon as possible. If the channel is in blocking mode, the call does not return until all the buffered data has been sent to the channel or some error occurred. The call returns immediately if the channel is nonblocking; it starts a background flush that will write the buffered data to the channel eventually, as fast as the channel is able to absorb it.

The return value is normally TCL_OK. If an error occurs, Tcl_Flush returns TCL_ERROR and records a POSIX error code that can be retrieved with Tcl_GetErrno.

TCL_SEEK

Tcl_Seek moves the access point in channel where subsequent data will be read or written. Buffered output is flushed to the channel and buffered input is discarded, prior to the seek operation.

Tcl_Seek normally returns the new access point. If an error occurs, Tcl_Seek returns -1 and records a POSIX error code that can be retrieved with Tcl_GetErrno. After an error, the access point may or may not have been moved.

TCL_TELL

Tcl_Tell returns the current access point for a channel. The returned value is -1 if the channel does not support seeking.

TCL_TRUNCATECHANNEL

Tcl_TruncateChannel truncates the file underlying channel to a given length of bytes. It returns TCL_OK if the operation succeeded, and TCL_ERROR otherwise.

TCL_GETCHANNELOPTION

Tcl_GetChannelOption retrieves, in optionValue, the value of one of the options currently in effect for a channel, or a list of all options and their values. The channel argument identifies the channel for which to query an option or retrieve all options and their values. If optionName is not NULL, it is the name of the option to query; the option's value is copied to the Tcl dynamic string denoted by optionValue. TCL_OUTPUTBUFFERED

Tcl_OutputBuffered devuelve el número de bytes de salida actualmente almacenados en búfer en los búferes internos para un canal. Si el canal no está abierto para escritura, esta función siempre devuelve cero.

PROBLEMAS DE PLATAFORMA

Los manejadores devueltos por Tcl_GetChannelHandle dependen de la plataforma y del tipo de canal. En plataformas Unix, el manejador es siempre un descriptor de archivo Unix tal como lo devuelve la llamada al sistema open. En plataformas Windows, el manejador es un HANDLE de archivo cuando el canal se creó con Tcl_OpenFileChannel, Tcl_OpenCommandChannel o Tcl_MakeFileChannel. Otros tipos de canal pueden devolver un tipo diferente de manejador en plataformas Windows.
