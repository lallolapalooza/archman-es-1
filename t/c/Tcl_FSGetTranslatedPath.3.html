DESCRIPCIÓN

Hay varias razones para llamar a las funciones de la API de Tcl_FS (por ejemplo, Tcl_FSAccess y Tcl_FSStat) en lugar de llamar directamente a funciones de nivel de sistema como access y stat. Primero, funcionarán multiplataforma, por lo que una extensión que las llame debería funcionar sin modificaciones en Unix y Windows. Segundo, la implementación de Windows de algunas de estas funciones corrige algunos errores en las llamadas a nivel de sistema. Tercero, estas llamadas a funciones manejan cualquier conversión de ruta de “Utf a nativa de la plataforma” que pueda ser necesaria (y puede almacenar en caché los resultados de dichas conversiones para una mayor eficiencia en llamadas posteriores). Cuarto, y quizás lo más importante, todas estas funciones son “conscientes del sistema de archivos virtual”. Cualquier sistema de archivos virtual (VFS) que se haya registrado (a través de Tcl_FSRegister) puede redirigir el acceso a archivos a medios o métodos de acceso alternativos. Esto significa que todas estas funciones (y, por lo tanto, los comandos de Tcl correspondientes como file, glob, pwd, cd, open, etc.) pueden operar en “archivos” que no son archivos nativos en el sistema de archivos nativo. Esto también significa que cualquier extensión de Tcl que acceda al sistema de archivos (FS para abreviar) a través de esta API es automáticamente “consciente del sistema de archivos virtual”. Por supuesto, si una extensión accede al sistema de archivos nativo directamente (a través de APIs específicas de la plataforma, por ejemplo), Tcl no puede interceptar tales llamadas.

Si se han registrado VFS apropiados, los “archivos” pueden ser, para dar dos ejemplos, remotos (por ejemplo, situados en un servidor ftp remoto) o archivados (por ejemplo, dentro de un archivo .zip). Dichos sistemas de archivos registrados proporcionan una tabla de búsqueda de funciones para implementar toda o parte de la funcionalidad enumerada aquí. Finalmente, las llamadas Tcl_FSStat y Tcl_FSLstat abstraen el búfer “struct stat” de cómo se declara realmente, permitiendo que el mismo código se utilice tanto en sistemas con como sin soporte para archivos mayores de 2 GB de tamaño.

La API de Tcl_FS está orientada a Tcl_Obj y puede almacenar en caché representaciones internas y otras cadenas relacionadas con rutas (por ejemplo, el directorio de trabajo actual). Un efecto secundario de esto es que no se deben pasar valores con un recuento de referencias de cero a ninguna de estas funciones. Si tales llamadas se manejaran, podrían resultar en fugas de memoria (en algunas circunstancias, el código del sistema de archivos puede desear retener una referencia al valor pasado, y por lo tanto no se debe asumir que después de que cualquiera de estas llamadas regrese, el valor todavía tiene un recuento de referencias de cero; puede haber sido incrementado) o en una falla de segmentación directa (u otro error de acceso a la memoria) debido a que el valor se libera a mitad de camino de la manipulación compleja de valores requerida para garantizar que la ruta esté completamente normalizada y sea absoluta para la determinación del sistema de archivos. La lección práctica que se aprende de esto es que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

es incorrecto y puede causar errores de memoria. El recuento de referencias de path debe incrementarse antes de pasarlo, o decrementarse. Por esta razón, los valores con un recuento de referencias de cero se consideran rutas de sistema de archivos no válidas y llamar a cualquier función de la API de Tcl_FS con dicho valor no tendrá ningún efecto.

FUNCIONES DE LA API FS

Tcl_FSCopyFile intenta copiar el archivo dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas están en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), se llama a la función “copiar archivo” de ese sistema de archivos (si no es NULL). De lo contrario, la función devuelve -1 y establece la variable global C errno al código de error POSIX “EXDEV” (que significa un “enlace entre dominios”).

Tcl_FSCopyDirectory intenta copiar el directorio dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas están en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), se llama a la función “copiar archivo” de ese sistema de archivos (si no es NULL). De lo contrario, la función devuelve -1 y establece la variable global C errno al código de error POSIX “EXDEV” (que significa un “enlace entre dominios”).

Tcl_FSCreateDirectory intenta crear el directorio dado por pathPtr llamando a la función “crear directorio” del sistema de archivos propietario.

Tcl_FSDeleteFile intenta eliminar el archivo dado por pathPtr llamando a la función “eliminar archivo” del sistema de archivos propietario.

Tcl_FSRemoveDirectory intenta eliminar el directorio dado por pathPtr llamando a la función “eliminar directorio” del sistema de archivos propietario.

Tcl_FSRenameFile intenta renombrar el archivo o directorio dado por srcPathPtr a la ruta dada por destPathPtr. Si las dos rutas dadas están en el mismo sistema de archivos (según Tcl_FSGetFileSystemForPath), se llama a la función “renombrar archivo” de ese sistema de archivos (si no es NULL). De lo contrario, la función devuelve -1 y establece la variable global C errno al código de error POSIX “EXDEV” (que significa un “enlace entre dominios”).

Tcl_FSListVolumes llama a cada sistema de archivos que tiene una función “listar volúmenes” no NULL y les pide que devuelvan su lista de volúmenes raíz. Acumula los valores de retorno en una lista que se devuelve al llamador (con un recuento de referencias de 0).

Tcl_FSEvalFileEx lee el archivo dado por pathPtr utilizando la codificación identificada por encodingName y evalúa su contenido como un script de Tcl. Devuelve la misma información que Tcl_EvalObjEx. Si encodingName es NULL, se utiliza la codificación del sistema para leer el contenido del archivo. Si el archivo no se pudo leer, se devuelve un error de Tcl para describir por qué no se pudo leer. El carácter de fin de archivo para los archivos es “\x1A” (^Z) para todas las plataformas. Si necesita un “^Z” en el código para la comparación de cadenas, puede usar “\x1A”, que será sustituido de forma segura por el intérprete de Tcl en “^Z”. Tcl_FSEvalFile es una versión más simple de Tcl_FSEvalFileEx que siempre utiliza la codificación del sistema al leer el archivo.

Tcl_FSLoadFile carga dinámicamente un archivo de código binario en memoria y devuelve las direcciones de dos procedimientos dentro de ese archivo, si están definidos. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr. Si ese sistema de archivos no implementa esta función (la mayoría de los sistemas de archivos virtuales no lo harán, debido a limitaciones del sistema operativo en la carga dinámica de código binario), Tcl intentará copiar el archivo a un directorio temporal y cargar ese archivo temporal. Tcl_FSUnloadFile revierte la operación, solicitando que la biblioteca indicada por loadHandle se elimine del proceso. Tenga en cuenta que, a diferencia del comando unload, esto no da a la biblioteca ninguna oportunidad de limpieza.

Ambas funciones anteriores devuelven un código de finalización de Tcl estándar. Si ocurre un error, se deja un mensaje de error en el resultado del interp.

El token proporcionado a través de la variable indicada por loadHandlePtr se puede usar con Tcl_FindSymbol.

Tcl_FSMatchInDirectory es utilizado por el código de globbing para buscar en un directorio todos los archivos que coinciden con un patrón dado. Se llamará a la función apropiada para el sistema de archivos al que pertenece pathPtr.

El valor de retorno es un resultado estándar de Tcl que indica si se produjo un error en el globbing. Los mensajes de error se colocan en interp (a menos que interp sea NULL, lo cual está permitido), pero los buenos resultados se colocan en resultPtr proporcionado.

Tenga en cuenta que el código de glob implementa patrones recursivos internamente, por lo que esta función solo se llamará con patrones simples, que se pueden hacer coincidir utilizando la lógica de string match. Para manejar la recursión, Tcl llamará a esta función con frecuencia solicitando solo directorios. Un caso especial de ser llamado con un patrón NULL indica que la ruta solo necesita ser verificada por el tipo correcto.

Tcl_FSLink reemplaza la versión de biblioteca de readlink, y la extiende para admitir la creación de enlaces. Se llamará a la función apropiada para el sistema de archivos al que pertenece linkNamePtr.

Si toPtr es NULL, se realiza una acción de “leer enlace”. El resultado es un Tcl_Obj que especifica el contenido del enlace simbólico dado por linkNamePtr, o NULL si el enlace no se pudo leer. El llamador es propietario del resultado, que debería llamar a Tcl_DecrRefCount cuando el resultado ya no sea necesario. Si toPtr no es NULL, Tcl debe crear un enlace de uno de los tipos pasados en el indicador linkAction. Este indicador es una combinación OR de TCL_CREATE_SYMBOLIC_LINK y TCL_CREATE_HARD_LINK. Cuando existe una opción (es decir, se pasa más de un indicador), la convención de Tcl es preferir los enlaces simbólicos. Cuando se crea un enlace con éxito, el valor de retorno debe ser toPtr (que, por lo tanto, ya es propiedad del llamador). Si no tiene éxito, se devuelve NULL.

Tcl_FSUtime reemplaza la versión de la librería de utime. Esta función devuelve 0 en caso de éxito y -1 en caso de error (como se describe en la documentación de utime). Si se realiza correctamente, la función actualizará los valores de atime y mtime del archivo dado. Tcl_FSFileAttrsGet implementa el acceso de lectura para el subcomando file attributes de la subrutina hookable. La función adecuada para el sistema de archivos al que pertenece el pathPtr se llama. Si el resultado es TCL_OK, se coloca un valor en objPtrRef, que será válido solo temporalmente (a menos que se llame Tcl_IncrRefCount). Tcl_FSFileAttrsSet implementa el acceso de escritura para el subcomando file attributes de la subrutina hookable. La función adecuada para el sistema de archivos al que pertenece el pathPtr se llama. Tcl_FSFileAttrStrings implementa parte de la subrutina hookable file attributes del subcomando. La función adecuada para el sistema de archivos al que pertenece el pathPtr se llama. La llamada al procedimiento puede devolver un array de strings o, en su lugar, devolver NULL y colocar una lista Tcl en objPtrRef. Tcl tomará esa lista e incrementará primero su recuento de referencias antes de usarla. Al finalizar su uso, Tcl decrementará su recuento de referencias. Por lo tanto, si la lista debe ser destruida por Tcl, debe tener un recuento de referencias de cero, y si no debe ser destruida, el sistema de archivos debe asegurarse de mantener un recuento de referencias al valor. Tcl_FSAccess verifica si el proceso podría leer, escribir o probar la existencia de un archivo (o otro objeto del sistema de archivos) cuyo nombre es pathname. Si pathname es un enlace simbólico en Unix, se prueban los permisos del archivo al que apunta este enlace simbólico. En caso de éxito (todos los permisos solicitados), se devuelve 0. En caso de error (al menos un bit en el modo solicitado es denegado u ocurrió otro error), se devuelve -1. Tcl_FSStat rellena la estructura Tcl_StatBuf con información sobre el archivo especificado. No se requieren derechos de acceso al archivo para obtener esta información, pero sí se requieren derechos de búsqueda en todos los directorios que aparecen en la ruta hacia el archivo. La estructura Tcl_StatBuf incluye información sobre el dispositivo, el inodo (0 en Windows), el modo de privilegio, el número de enlaces (1 en Windows), el UID (0 en Windows), el GID (0 en Windows), el rdev (igual que el dispositivo en Windows), el tamaño, el tiempo de acceso, el tiempo de modificación y el tiempo de cambio de metadatos. Véase PORTABLE STAT RESULT API para una descripción de cómo escribir código portátil para reservar y acceder a la estructura Tcl_StatBuf. Si path existe, Tcl_FSStat devuelve 0 y la estructura statPtr está rellena con datos. De lo contrario, devuelve -1 y no se dan datos de estadísticas. Tcl_FSOpenFileChannel abre un archivo especificado por pathPtr y devuelve un manejador de canal que puede utilizarse para realizar entrada y salida en el archivo. Esta API se modela después de la función fopen de la librería de entrada/salida estándar Unix. La sintaxis y el significado de todos los argumentos son similares a los dados en el comando open de Tcl cuando se abre un archivo. Si ocurre un error al abrir el canal, Tcl_FSOpenFileChannel devuelve NULL y registra un código de error POSIX que puede recuperarse con Tcl_GetErrno. Además, si interp no es NULL, Tcl_FSOpenFileChannel deja un mensaje de error en el resultado de interp después de cualquier error. El canal recién creado no se registra en el intérprete proporcionado; para registrarlo, use Tcl_RegisterChannel. Si uno de los canales estándar, stdin, stdout o stderr fue previamente cerrado, la acción de crear el nuevo canal también lo asigna como reemplazo de los canales estándar. Tcl_FSGetCwd reemplaza la versión de la librería de getcwd. Devuelve el directorio de trabajo de la biblioteca Tcl. Este puede ser diferente al directorio de trabajo nativo, que se establece cuando el directorio de trabajo actual no está en el sistema de archivos nativo. El resultado es un puntero a un Tcl_Obj especificando el directorio actual, o NULL si no se puede determinar el directorio actual. Si se devuelve NULL, se deja un mensaje de error en el resultado de interp. El resultado ya tiene su recuento de referencias incrementado para el llamador. Cuando ya no se necesita, se debe decrementar el recuento de referencias. Esto es necesario para la seguridad multi-hilo, para que múltiples hilos puedan acceder a esta y funciones relacionadas, mientras aseguran que los resultados siempre sean válidos. Tcl_FSChdir reemplaza la versión de la librería de chdir. La ruta se normaliza y luego se pasa al sistema de archivos que la reclama. Si ese sistema de archivos no implementa esta función, Tcl recurre a una combinación de stat y access para verificar si el directorio existe y tiene permisos adecuados. Para los resultados, véase la documentación de chdir. Si se realiza correctamente, se registra un registro de la ruta exitosa en cwdPathPtr para llamadas posteriores a Tcl_FSGetCwd. Tcl_FSPathSeparator devuelve el carácter separador usado para el elemento más específico de la ruta especificada por pathPtr (es decir, la última parte de la ruta). El separador se devuelve como un Tcl_Obj conteniendo una cadena de longitud 1. Si la ruta es inválida, se devuelve NULL. Tcl_FSJoinPath toma el objeto Tcl dado, que debe ser una lista válida (que permite tener un contador de referencias cero), y devuelve el valor de ruta dado considerando los primeros elements elementos como segmentos válidos de ruta (cada segmento puede ser una ruta completa, una ruta parcial o solo un nombre de directorio o archivo). Si cualquier segmento es una ruta absoluta, se eliminan todos los segmentos anteriores. Si elements es menor que 0, se usa la lista completa. Es posible que el valor devuelto sea realmente un elemento de la lista dada, por lo que el llamador debe ser cauteloso al incrementar el recuento de referencias del valor antes de liberar la lista. El valor devuelto, típicamente con un recuento de referencias de cero (pero podría compartir bajo ciertas condiciones), contiene la ruta concatenada. El llamador debe incrementar un recuento de referencias al valor antes de usarlo. En particular, el valor devuelto podría ser un elemento de la lista dada, por lo que liberar la lista podría liberar el valor prematuramente si no se ha tomado un recuento de referencias. Si el número de elementos es cero, el valor devuelto será un objeto Tcl_Obj de cadena vacía. Tcl_FSSplitPath toma el objeto Tcl dado, que debe ser una ruta válida, y devuelve un valor de lista que contiene cada segmento de esa ruta como elemento. Devuelve un valor de lista con un recuento de referencias de cero. Si lenPtr no es NULL, la variable a la que apunta contiene el número de elementos en el valor devuelto. Tcl_FSEqualPaths prueba si las dos rutas dadas representan el mismo objeto del sistema de archivos. Devuelve 1 si las rutas son iguales, 0 si son diferentes. Si alguna de las rutas es NULL, se devuelve 0 siempre. Tcl_FSGetNormalizedPath intenta extraer una representación normalizada única de la ruta dada, cuyo valor de cadena puede usarse como identificador único para el archivo. Devuelve la ruta normalizada, propiedad de Tcl, o NULL si la ruta fue inválida o no pudo ser convertida correctamente. La extracción de rutas absolutas y normalizadas es muy eficiente (porque el sistema de archivos opera internamente con estas representaciones), aunque el resultado cuando el sistema de archivos contiene múltiples enlaces simbólicos no será la versión más amigable de una ruta. El valor devuelto es propiedad de Tcl y tiene una duración equivalente a la del pathPtr ingresado (a menos que sea un camino relativo, en cuyo caso el valor normalizado puede ser liberado cualquier vez que cambie el cwd) - el llamador puede incrementar el recuento de referencias si lo desea para mantener una copia por más tiempo. Tcl_FSJoinToPath toma el valor dado, que suele ser una ruta válida o NULL, y junta las rutas de segmentos dados. Devuelve un valor, típicamente con un recuento de referencias de cero (pero podría compartir bajo ciertas condiciones), que contiene la ruta juntada. El llamador debe incrementar un recuento de referencias al valor antes de usarlo. Si cualquiera de los valores pasados a esta función (pathPtr o elementos de path) tiene un recuento de referencias de cero, se liberará cuando esta función retorne. Tcl_FSConvertToPathType intenta convertir el objeto Tcl dado a un tipo válido de ruta, considerando que el cwd puede haber cambiado incluso si este valor ya es de tipo correcto. El nombre del archivo puede comenzar con ~ (para indicar el directorio de usuario actual) o ~ (para indicar cualquier directorio de usuario). Si la conversión es exitosa (es decir, el valor es una ruta válida en uno de los sistemas de archivos actuales), se devuelve TCL_OK. De lo contrario, se devuelve TCL_ERROR, y puede haber un mensaje de error en el intérprete. Tcl_FSGetInternalRep extrae la representación interna de un valor de ruta dado en el sistema de archivos especificado. Si el valor pertenece a un sistema de archivos diferente, se devuelve NULL. Si la representación interna es actualmente NULL, se intenta generarla llamando a Tcl_FSCreateInternalRepProc del sistema de archivos. Devuelve NULL o una representación válida de la ruta interna. Esta representación interna está cacheada, por lo que las llamadas repetidas a esta función no requieren conversiones adicionales. Tcl_FSGetTranslatedPath intenta extraer la ruta traducida a partir del objeto Tcl dado. Si la traducción es exitosa (es decir, el valor es una ruta válida), se devuelve el valor. De lo contrario, se devuelve NULL, y puede haber un mensaje de error en el intérprete. Una ruta traducida es una que no contiene ~ o ~user (estas se han expandido a su representación actual en el sistema de archivos). El valor devuelto es propiedad del llamador, que debe almacenarlo o llamar a Tcl_DecrRefCount para asegurar que se libera la memoria. Esta función no es de uso práctico, y Tcl_FSGetNormalizedPath o Tcl_FSGetNativePath son a menudo funciones más adecuadas para los fines. Tcl_FSGetTranslatedStringPath realiza lo mismo que Tcl_FSGetTranslatedPath, pero devuelve una cadena o NULL. El string devuelto es dinámicamente asignado.cated y propiedad del llamador, que debe almacenarlo o llamar a ckfree para asegurarse de que se libera. De nuevo, Tcl_FSGetNormalizedPath o Tcl_FSGetNativePath son generalmente mejores funciones para usar en la mayoría de los propósitos.

Tcl_FSNewNativePath realiza algo así como la inversa de las conversiones habituales de obj->path->nativerep. Si algún código recupera una ruta en formato nativo (de, por ejemplo, readlink o un diálogo nativo), y esa ruta se va a utilizar a nivel de Tcl, entonces llamar a esta función es una forma eficiente de crear el tipo de valor de ruta apropiado.

El valor resultante es un valor de tipo "ruta" puro, que solo recibirá una representación de cadena UTF-8 si así lo requiere algún código Tcl.

Tcl_FSGetNativePath es para uso de los sistemas de archivos nativos Win/Unix, de modo que puedan recuperar fácilmente la representación nativa (char* o TCHAR*) de una ruta. Esta función es un envoltorio de conveniencia alrededor de Tcl_FSGetInternalRep. Puede ser deseable en el futuro tener representaciones nativas no basadas en cadenas (por ejemplo, en macOS, una representación que use una estructura FSRef de fileSpec sería probablemente más eficiente). En Windows, una representación Unicode completa permitiría rutas de longitud ilimitada. Actualmente, la representación es simplemente una cadena de caracteres que puede contener la ruta relativa o una ruta completa, absoluta y normalizada en la codificación nativa (condiciones complejas dictan cuál de estas se proporcionará, por lo que ninguna puede confiarse, a menos que se sepa que la ruta es absoluta). Si necesita una ruta nativa que deba ser absoluta, entonces debe solicitar la versión nativa de una ruta normalizada. Si por alguna razón se necesita una versión no absoluta, no normalizada de la ruta, esta debe construirse por separado (por ejemplo, usando Tcl_FSGetTranslatedPath).

La representación nativa se almacena en caché para que las llamadas repetidas a esta función no requieran conversiones adicionales. El valor de retorno es propiedad de Tcl y tiene una vida útil equivalente a la del pathPtr pasado (a menos que sea una ruta relativa, en cuyo caso la representación nativa puede liberarse en cualquier momento en que cambie el cwd).

Tcl_FSFileSystemInfo devuelve una lista de dos elementos. El primer elemento es el nombre del sistema de archivos (por ejemplo, "native", "vfs", "zip" o "prowrap", quizás), y el segundo es el tipo particular de la ruta dada dentro de ese sistema de archivos (que depende del sistema de archivos). El segundo elemento puede estar vacío si el sistema de archivos no proporciona una categorización adicional de archivos.

Se devuelve un valor de lista válido, a menos que el valor de la ruta no sea reconocido, en cuyo caso se devolverá NULL.

Tcl_FSGetFileSystemForPath devuelve un puntero al Tcl_Filesystem que acepta esta ruta como válida.

Si ningún sistema de archivos acepta la ruta, se devuelve NULL.

Tcl_FSGetPathType determina si la ruta dada es relativa al directorio actual, relativa al volumen actual o absoluta.

Devuelve uno de TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE o TCL_PATH_VOLUME_RELATIVE

LA API DEL SISTEMA DE ARCHIVOS VIRTUAL

Un sistema de archivos proporciona una estructura Tcl_Filesystem que contiene punteros a funciones que implementan las diversas operaciones en un sistema de archivos; estas operaciones se invocan según sea necesario por la capa genérica, lo que generalmente ocurre a través de las funciones enumeradas anteriormente.

Las estructuras Tcl_Filesystem se manipulan usando los siguientes métodos.

Tcl_FSRegister toma un puntero a una estructura de sistema de archivos y una pieza opcional de datos para asociar con ese sistema de archivos. Al llamar a esta función, Tcl adjuntará el sistema de archivos a la lista de sistemas de archivos conocidos, y será completamente funcional inmediatamente. Tcl no verifica si el mismo sistema de archivos está registrado múltiples veces (y en general, eso no es bueno). Se devolverá TCL_OK.

Tcl_FSUnregister elimina la estructura del sistema de archivos dada de la lista de sistemas de archivos conocidos, si es conocida, y devuelve TCL_OK. Si el sistema de archivos no está registrado actualmente, se devuelve TCL_ERROR.

Tcl_FSData devolverá el clientData asociado con el sistema de archivos dado, si ese sistema de archivos está registrado. De lo contrario, devolverá NULL.

Tcl_FSMountsChanged se utiliza para informar al núcleo de Tcl que el conjunto de puntos de montaje para el sistema de archivos dado (ya registrado) ha cambiado, y que las representaciones de archivos en caché, por lo tanto, ya no pueden ser correctas.

Excepto por los tres primeros campos de esta estructura que contienen elementos de datos simples, todas las entradas contienen direcciones de funciones llamadas por la capa genérica del sistema de archivos para realizar la gama completa de acciones relacionadas con el sistema de archivos.

Las muchas funciones en esta estructura se dividen en tres categorías: funciones de infraestructura (casi todas las cuales deben implementarse), funciones operativas (que deben implementarse si se proporciona un sistema de archivos completo) y funciones de eficiencia (que solo necesitan implementarse si se pueden hacer de manera eficiente, o si tienen efectos secundarios que son requeridos por el sistema de archivos; Tcl tiene emulaciones menos eficientes a las que puede recurrir). Es importante tener en cuenta que, en la versión actual de Tcl, la mayoría de estas soluciones alternativas solo se utilizan para manejar comandos iniciados en Tcl, no en C. Lo que esto significa es que, si se emite un comando de renombrar archivo en Tcl, y los sistemas de archivos relevantes no implementan sus Tcl_FSRenameFileProc, el núcleo de Tcl recurrirá a una combinación de otras funciones del sistema de archivos (utilizará Tcl_FSCopyFileProc seguido de Tcl_FSDeleteFileProc, y si Tcl_FSCopyFileProc no está implementado, hay una solución alternativa adicional). Sin embargo, si se emite un comando Tcl_FSRenameFileProc a nivel de C, no ocurren tales soluciones alternativas. Esto es cierto excepto por las últimas cuatro entradas en la tabla del sistema de archivos (lstat, load, getcwd y chdir) para las cuales sí ocurren soluciones alternativas a nivel de C.

Cualquier función que tome nombres de ruta en forma de Tcl_Obj toma esos nombres en forma UTF-8. La API de infraestructura del sistema de archivos está diseñada para soportar la conversión eficiente y en caché de estas rutas UTF-8 a otras representaciones nativas.

ESTRUCTURA DEL SISTEMA DE ARCHIVOS

Estos campos contienen información básica sobre la estructura del sistema de archivos y las direcciones de las funciones que se utilizan para asociar un tipo específico de sistema de archivos con una ruta de archivo, y para gestionar la representación interna de las rutas de archivo, por ejemplo, para copiar y liberar dichas representaciones.

TYPENAME

El campo typeName contiene una cadena terminada en NULL que identifica el tipo de sistema de archivos implementado (por ejemplo, native, zip o vfs).

STRUCTURE LENGTH

El campo structureLength se implementa generalmente como sizeof(Tcl_Filesystem), y está allí para permitir una compatibilidad binaria más sencilla en futuras versiones de Tcl si el tamaño de la estructura cambia.

VERSION

El campo version debe establecerse como TCL_FILESYSTEM_VERSION_1.

PATHINFILESYSTEMPROC

El campo pathInFilesystemProc contiene la dirección de una función que se llama para determinar si un valor de ruta dado pertenece a este sistema de archivos o no. Tcl solo llamará a las funciones restantes del sistema de archivos con un valor de ruta para el cual esta función ha devuelto TCL_OK. Si la ruta no pertenece, se devolverá -1 (el comportamiento de Tcl para cualquier otro valor de retorno no está definido). Si se devuelve TCL_OK, el parámetro opcional clientDataPtr puede usarse para devolver una representación interna (específica del sistema de archivos) de la ruta, que se almacenará dentro del valor de la ruta y podrá ser recuperada eficientemente por otras funciones del sistema de archivos. Tcl almacenará simultáneamente la información de que esta ruta pertenece a este sistema de archivos. Dichas cachés se invalidan cuando se añaden o se quitan de la lista interna de sistemas de archivos conocidos de Tcl.

        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

Esta función crea una copia de la representación interna de una ruta y se llama cuando Tcl necesita duplicar un valor de ruta. Si es NULL, Tcl simplemente no copiará la representación interna, lo cual puede ser necesario más tarde.

typedef ClientData Tcl_FSDupInternalRepProc(
        ClientData clientData);

Libera la representación interna. Debe implementarse si es necesario liberar la representación interna (es decir, si se asignó memoria al generar la representación interna), pero puede ser NULL de lo contrario.

typedef void Tcl_FSFreeInternalRepProc(
        ClientData clientData);

Función para convertir una representación interna en una ruta normalizada. Solo se requiere si el sistema de archivos crea valores de ruta puros sin representación de cadena. El valor devuelto es un valor Tcl cuya representación de cadena es la ruta normalizada.

typedef Tcl_Obj *Tcl_FSInternalToNormalizedProc(
        ClientData clientData);

CREATEINTERNALREPPROC

Función para generar una representación interna a partir de un valor de ruta y almacenarla en el valor. Podría ser NULL si las rutas no tienen representación interna, o si el Tcl_FSPathInFilesystemProc del sistema de archivos siempre crea una representación interna inmediatamente para las rutas que acepta.

typedef ClientData Tcl_FSCreateInternalRepProc(
        Tcl_Obj *pathPtr);

NORMALIZEPATHPROC

Función para normalizar una ruta. Debe implementarse para todos los sistemas de archivos que tienen múltiples representaciones de cadena para el mismo valor de ruta. En Tcl, cada path debe tener una única representación normalizada única. Dependiendo del sistema de archivos, puede haber más de una representación no normalizada que apunte a ese camino (por ejemplo, una ruta relativa, una ruta con diferente mayúscula si el sistema de archivos no distingue mayúsculas y minúsculas, una ruta que contenga un enlace simbólico como ~, una ruta que contenga enlaces simbólicos, etc.). Si el último componente de la ruta es un enlace simbólico, no debe convertirse en su valor, pero su caso u otros aspectos deben hacerse únicos. Todos los demás componentes de la ruta deben convertirse desde enlaces simbólicos. Esta excepción es necesaria para que coincida con el comportamiento de Tcl con file delete, file rename, file copy operando sobre enlaces simbólicos. Esta función puede ser llamada con nextCheckpoint al principio de la ruta (es decir, cero), al final de la ruta o en cualquier separador de archivos intermedio en la ruta. Nunca se dirigirá a ninguna otra posición arbitraria en la ruta. En el último de los tres casos válidos, el implementador puede asumir que la ruta hasta e incluyendo el separador es conocida y normalizada.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

OPERACIONES DEL SISTEMA DE ARCHIVOS

Los campos de esta sección de la estructura contienen las direcciones de las funciones que se llaman para realizar las operaciones básicas del sistema de archivos. Un sistema de archivos que se espera utilizar con el conjunto completo de comandos de Tcl debe implementar todas estas funciones. Si alguna de ellas no está implementada, ciertos comandos de Tcl podrían fallar al operar con rutas dentro de ese sistema de archivos. Sin embargo, en algunos casos esto puede ser deseable (por ejemplo, un sistema de archivos de solo lectura no debería implementar las últimas cuatro funciones, y un sistema de archivos que no admite enlaces simbólicos no debería implementar la función readlink, etc.). El núcleo de Tcl espera que los sistemas de archivos se comporten de esta manera.

FILESYSTEMPATHTYPEPROC

Función para determinar el tipo de una ruta en este sistema de archivos. Puede ser NULL, en cuyo caso no se proporcionará información de tipo a los usuarios del sistema de archivos. El type se usa solo para información y debe devolverse como la representación de cadena del Tcl_Obj devuelto. Un valor de retorno típico podría ser networked, zip o ftp. El Tcl_Obj resultante es propiedad del sistema de archivos y, por lo tanto, Tcl incrementará el recuento de referencias del valor si desea mantener una referencia a él.

typedef Tcl_Obj *Tcl_FSFilesystemPathTypeProc(
        Tcl_Obj *pathPtr);

FILESYSTEMSEPARATORPROC

Función para devolver el carácter separador para este sistema de archivos. Solo debe implementarse si el sistema de archivos desea utilizar un separador diferente al estándar /. Entre otros usos, es devuelto por el comando file separator. El valor devuelto debe tener un recuento de referencias cero.

typedef Tcl_Obj *Tcl_FSFilesystemSeparatorProc(
        Tcl_Obj *pathPtr);

STATPROC

Función para procesar una llamada Tcl_FSStat. Debe implementarse para cualquier sistema de archivos razonable, ya que muchos comandos de Tcl dependen crucialmente de ella (por ejemplo, file atime, file isdirectory, file size, glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

La función Tcl_FSStatProc rellena la estructura de estadísticas statPtr con información sobre el archivo especificado. No necesitas derechos de acceso al archivo para obtener esta información, pero necesitas derechos de búsqueda en todos los directorios que se encuentran en la ruta que apunta al archivo. La estructura de estadísticas incluye información sobre el dispositivo, el inodo (siempre 0 en Windows), el modo de permisos, el número de enlaces (siempre 1 en Windows), el ID de usuario (siempre 0 en Windows), el ID de grupo (siempre 0 en Windows), el rdev (igual que el dispositivo en Windows), el tamaño, la última fecha de acceso, la última fecha de modificación y la última fecha de cambio de metadatos.

Si el archivo representado por pathPtr existe, Tcl_FSStatProc devuelve 0 y la estructura de estadísticas se rellena con datos. De lo contrario, se devuelve -1 y no se proporciona ninguna información de estadísticas.

ACCESSPROC

Función para procesar una llamada Tcl_FSAccess. Debe implementarse para cualquier sistema de archivos razonable, ya que muchos comandos de Tcl dependen crucialmente de ella (por ejemplo, file exists, file readable).

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

La función Tcl_FSAccessProc comprueba si al proceso se le permitiría leer, escribir o verificar la existencia del archivo (u otro objeto del sistema de archivos) cuyo nombre está en pathPtr. Si el nombre de la ruta se refiere a un enlace simbólico, se deben verificar los permisos del archivo al que se refiere ese enlace simbólico.

En caso de éxito (todos los permisos solicitados son concedidos), se devuelve 0. En caso de error (al menos un bit en el modo solicitado indica un permiso denegado, o se produce otro error), se devuelve -1.

OPENFILECHANNELPROC

Función para procesar una llamada a Tcl_FSOpenFileChannel. Debe ser implementada para cualquier sistema de archivos razonable, ya que todas las operaciones que requieren abrir o acceder al contenido de un archivo la utilizarán (por ejemplo, open, encoding y muchos comandos de Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

El Tcl_FSOpenFileChannelProc abre un archivo especificado por pathPtr y devuelve un identificador de canal que se puede utilizar para realizar operaciones de entrada y salida en el archivo. Esta API está modelada después del procedimiento fopen de la biblioteca estándar de E/S de Unix. La sintaxis y el significado de todos los argumentos son similares a los proporcionados en el comando open de Tcl al abrir un archivo, donde el argumento mode es una combinación de las banderas POSIX O_RDONLY, O_WRONLY, etc. Si ocurre un error al abrir el canal, Tcl_FSOpenFileChannelProc devuelve NULL y registra un código de error POSIX que se puede recuperar con Tcl_GetErrno. Además, si interp no es NULL, Tcl_FSOpenFileChannelProc deja un mensaje de error en el resultado de interp después de cualquier error.

El canal recién creado no debe ser registrado en el intérprete proporcionado por un Tcl_FSOpenFileChannelProc; esa tarea corresponde al llamador de Tcl_FSOpenFileChannel (si es necesario). Si uno de los canales estándar, stdin, stdout o stderr fue previamente cerrado, el acto de crear el nuevo canal también lo asigna como reemplazo del canal estándar.

MATCHINDIRECTORYPROC

Función para procesar una llamada a Tcl_FSMatchInDirectory. Si no se implementa, la funcionalidad de globbing y copia recursiva faltará en el sistema de archivos (y esto puede afectar a comandos como encoding names que utilizan internamente la funcionalidad de globbing).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La función debe devolver todos los archivos o directorios (u otros objetos del sistema de archivos) que coincidan con el patrón dado y que cumplan con la especificación types proporcionada. Hay dos formas en que esta función puede ser llamada. Si pattern es NULL, entonces pathPtr es una especificación de ruta completa de un solo archivo o directorio que debe ser verificado en cuanto a su existencia y tipo correcto. De lo contrario, pathPtr es un directorio, cuyo contenido la función debe buscar archivos o directorios que tengan el tipo correcto. En cualquier caso, se puede asumir que pathPtr no es NULL y no está vacío. Actualmente no está documentado si pathPtr tendrá o no un separador de archivos al final, por lo que el código debe ser flexible a ambas posibilidades.

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso de coincidencia. Los mensajes de error se colocan en interp, a menos que interp sea NULL, en cuyo caso no es necesario generar ningún mensaje de error; en un resultado TCL_OK, los resultados deben añadirse al valor de resultPtr proporcionado (que se puede asumir que es una lista válida y no compartida de Tcl). Las coincidencias añadidas a resultPtr deben incluir cualquier prefijo de ruta dado en pathPtr (esto generalmente significa que serán especificaciones de ruta absoluta). Tenga en cuenta que si no se encuentran coincidencias, eso simplemente conduce a una lista vacía; los errores solo se señalan para problemas reales de archivos o del sistema de archivos que puedan ocurrir durante el proceso de coincidencia.

La estructura Tcl_GlobTypeData pasada en el parámetro types contiene los siguientes campos:

typedef struct Tcl_GlobTypeData {
    /* Corresponde a bcdpfls como en 'find -t' */
    int type;
    /* Corresponde a los permisos de archivo */
    int perm;
    /* Tipo de Mac aceptable */
    Tcl_Obj *macType;
    /* Creador de Mac aceptable */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Hay dos casos específicos que es importante manejar correctamente, ambos cuando types no es NULL. Los dos casos son cuando types->types & TCL_GLOB_TYPE_DIR o types->types & TCL_GLOB_TYPE_MOUNT son verdaderos (y en particular cuando las otras banderas son falsas). En el primer caso, la función debe listar los directorios contenidos. Tcl utiliza esto para implementar la globbing recursiva, por lo que es fundamental que los sistemas de archivos implementen la coincidencia de directorios correctamente. En el segundo caso, con TCL_GLOB_TYPE_MOUNT, el sistema de archivos debe listar los puntos de montaje que se encuentran dentro del pathPtr dado (y en este caso, pathPtr no necesita estar dentro del mismo sistema de archivos, a diferencia de todos los demás casos en los que se llama a esta función). El soporte para esto es fundamental si Tcl quiere tener transiciones fluidas entre un sistema de archivos y otro.

UTIMEPROC

Función para procesar una llamada a Tcl_FSUtime. Necesaria para permitir establecer (no leer) tiempos con file mtime, file atime y la implementación de apertura/lectura y apertura/escritura/copia de archivos de file copy.

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

Los tiempos de acceso y modificación del archivo especificado por pathPtr deben cambiarse a los valores dados en la estructura tval.

El valor de retorno debe ser 0 en caso de éxito y -1 en caso de error, al igual que con el utime del sistema.

LINKPROC

Función para procesar una llamada a Tcl_FSLink. Solo debe implementarse si el sistema de archivos admite enlaces, y de lo contrario puede ser NULL.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

Si toPtr es NULL, se le está pidiendo a la función que lea el contenido de un enlace. El resultado es un Tcl_Obj que especifica el contenido del enlace dado por linkNamePtr, o NULL si el enlace no pudo ser leído. El resultado es propiedad del llamador (y por lo tanto, su contador de referencias debe ser incrementado antes de ser devuelto). Cualquier llamador debe llamar a Tcl_DecrRefCount en este resultado cuando ya no sea necesario. Si toPtr no es NULL, la función debe intentar crear un enlace. El resultado en este caso debe ser toPtr si el enlace tuvo éxito y NULL en caso contrario. En este caso, el resultado no es propiedad del llamador (es decir, no se necesitan manipulaciones de contador de referencias en ninguno de los extremos). Consulte la documentación de Tcl_FSLink para la interpretación correcta de las banderas de linkAction.

LISTVOLUMESPROC

Función para listar los volúmenes del sistema de archivos añadidos por este sistema de archivos. Solo debe implementarse si el sistema de archivos añade volúmenes al principio del sistema de archivos, para que puedan ser devueltos por file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

El resultado debe ser una lista de volúmenes añadidos por este sistema de archivos, o NULL (o una lista vacía) si no se proporcionan volúmenes. El valor del resultado se considera propiedad del sistema de archivos (no del núcleo de Tcl), pero se le debe dar un contador de referencias para Tcl. Tcl utilizará el contenido de la lista y luego decrementará ese contador de referencias. Esto permite a los sistemas de archivos elegir si realmente desean conservar una lista "global" de volúmenes o no (si no, generan la lista sobre la marcha y la pasan a Tcl con un contador de referencias de 1 y luego se olvidan de la lista; si sí, simplemente incrementan el contador de referencias de su lista global y la pasan a Tcl, que copiará el contenido y luego decrementará el contador de vuelta a donde estaba).

Por lo tanto, Tcl considera que los valores de retorno de este proc son de solo lectura.

FILEATTRSTRINGSPROC

Función para listar todas las cadenas de atributos que son válidas para este sistema de archivos. Si no se implementa, el sistema de archivos no admitirá el comando file attributes. Esto permite adjuntar información adicional arbitraria a los archivos en el sistema de archivos. Si no se implementa, no hay necesidad de implementar los métodos get y set.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

La función llamada puede devolver una matriz de cadenas o puede devolver NULL y colocar una lista de Tcl en objPtrRef. Tcl tomará esa lista y primero incrementará su contador de referencias antes de usarla. Al finalizar ese uso, Tcl decrementará su contador de referencias. Por lo tanto, si la lista debe ser eliminada por Tcl cuando termine, debe tener un contador de referencias de cero, y si la lista no debe ser eliminada, el sistema de archivos debe asegurarse de devolver un valor con un contador de referencias de al menos uno.

FILEATTRSGETPROC

Función para procesar una llamada a Tcl_FSFileAttrsGet, utilizada por file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

Devuelve un código de retorno estándar de Tcl. El valor del atributo recuperado, que corresponde al elemento index de la lista devuelta por Tcl_FSFileAttrStringsProc, es un Tcl_Obj colocado en objPtrRef (si se devolvió TCL_OK) y es probable que tenga un contador de referencias de cero. En cualquier caso, debemos almacenarlo en algún lugar (por ejemplo, el resultado de Tcl), o incrementar/decrementar su contador de referencias para asegurar que se libere correctamente.

FILEATTRSSETPROC

Función para procesar una llamada a Tcl_FSFileAttrsSet, utilizada por file attributes. Si el sistema de archivos es de solo lectura, no hay necesidad de implementar esto.

typedef int Tcl_FSFileAttrsSetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj *objPtr);

El valor del atributo del elemento index en la lista devuelta por Tcl_FSFileAttrStringsProc debe establecerse en el objPtr proporcionado.

CREATEDIRECTORYPROC

FILESYSTEM OPERATIONS

These functions are part of the interface for filesystem virtualization. They are called by Tcl to perform operations on files and directories. Filesystem implementations must implement at least one function from each of the groups listed below.

OPENFILEPROC

Function to process a Tcl_FSOpenFile call. Must be implemented for any filesystem that supports file operations.

typedef Tcl_Channel Tcl_FSOpenFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_OpenMode mode);

The return value is a standard Tcl channel handle for the opened file, or NULL if an error occurs. An error message is left in the interp's result.

READFILEPROC

Function to process a Tcl_FSReadFile call. Must be implemented for any filesystem that supports reading from files.

typedef int Tcl_FSReadFileProc(
        Tcl_Channel chan,
        char *buf,
        int toRead,
        Tcl_Obj **errorPtr);

The return value is the number of bytes read, or -1 if an error occurs. If an error does occur, the name of the file or directory which caused the error should be placed in errorPtr.

WRITEFILEPROC

Function to process a Tcl_FSWriteFile call. Must be implemented for any filesystem that supports writing to files.

typedef int Tcl_FSWriteFileProc(
        Tcl_Channel chan,
        char *buf,
        int toWrite,
        Tcl_Obj **errorPtr);

The return value is the number of bytes written, or -1 if an error occurs. If an error does occur, the name of the file or directory which caused the error should be placed in errorPtr.

CLOSEFILEPROC

Function to process a Tcl_FSCloseFile call. Must be implemented for any filesystem that supports file operations.

typedef int Tcl_FSCloseFileProc(
        Tcl_Channel chan,
        Tcl_Obj **errorPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If an error does occur, the name of the file or directory which caused the error should be placed in errorPtr.

SEEKFILEPROC

Function to process a Tcl_FSSeekFile call. Should be implemented for any filesystem that supports seeking within files.

typedef long Tcl_FSSeekFileProc(
        Tcl_Channel chan,
        long offset,
        int seekMode,
        Tcl_Obj **errorPtr);

The return value is the new offset within the file, or -1 if an error occurs. If an error does occur, the name of the file or directory which caused the error should be placed in errorPtr.

TRUNCATEFILEPROC

Function to process a Tcl_FSTruncateFile call. Should be implemented for any filesystem that supports truncating files.

typedef int Tcl_FSTruncateFileProc(
        Tcl_Channel chan,
        long length,
        Tcl_Obj **errorPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If an error does occur, the name of the file or directory which caused the error should be placed in errorPtr.

STATPROC

Function to process a Tcl_FSStat call. Must be implemented for any filesystem that supports file metadata operations.

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, information about the file or directory specified by pathPtr should be placed in statPtr.

CREATEDIRECTORYPROC

Function to process a Tcl_FSCreateDirectory call. Should be implemented unless the FS is read-only.

typedef int Tcl_FSCreateDirectoryProc(
        Tcl_Obj *pathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, a new directory should have been added to the filesystem in the location specified by pathPtr.

REMOVEDIRECTORYPROC

Function to process a Tcl_FSRemoveDirectory call. Should be implemented unless the FS is read-only.

typedef int Tcl_FSRemoveDirectoryProc(
        Tcl_Obj *pathPtr,
        int recursive,
        Tcl_Obj **errorPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, the directory specified by pathPtr should have been removed from the filesystem. If the recursive flag is given, then a non-empty directory should be deleted without error. If this flag is not given, then and the directory is non-empty a POSIX “EEXIST” error should be signaled. If an error does occur, the name of the file or directory which caused the error should be placed in errorPtr.

DELETEFILEPROC

Function to process a Tcl_FSDeleteFile call. Should be implemented unless the FS is read-only.

typedef int Tcl_FSDeleteFileProc(
        Tcl_Obj *pathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the process. If successful, the file specified by pathPtr should have been removed from the filesystem. Note that, if the filesystem supports symbolic links, Tcl will always call this function and not Tcl_FSRemoveDirectoryProc when needed to delete them (even if they are symbolic links to directories).

FILESYSTEM EFFICIENCY

These functions need not be implemented for a particular filesystem because the core has a fallback implementation available. See each individual description for the consequences of leaving the field NULL.

LSTATPROC

Function to process a Tcl_FSLstat call. If not implemented, Tcl will attempt to use the statProc defined above instead. Therefore it need only be implemented if a filesystem can differentiate between stat and lstat calls.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

The behavior of this function is very similar to that of the Tcl_FSStatProc defined above, except that if it is applied to a symbolic link, it returns information about the link, not about the target file.

COPYFILEPROC

Function to process a Tcl_FSCopyFile call. If not implemented Tcl will fall back on open-r, open-w and fcopy as a copying mechanism. Therefore it need only be implemented if the filesystem can perform that action more efficiently.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the copying process. Note that, destPathPtr is the name of the file which should become the copy of srcPathPtr. It is never the name of a directory into which srcPathPtr could be copied (i.e. the function is much simpler than the Tcl level file copy subcommand). Note that, if the filesystem supports symbolic links, Tcl will always call this function and not copyDirectoryProc when needed to copy them (even if they are symbolic links to directories). Finally, if the filesystem determines it cannot support the file copy action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

RENAMEFILEPROC

Function to process a Tcl_FSRenameFile call. If not implemented, Tcl will fall back on a copy and delete mechanism. Therefore it need only be implemented if the filesystem can perform that action more efficiently.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

The return value is a standard Tcl result indicating whether an error occurred in the renaming process. If the filesystem determines it cannot support the file rename action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

COPYDIRECTORYPROC

Function to process a Tcl_FSCopyDirectory call. If not implemented, Tcl will fall back on a recursive file mkdir, file copy mechanism. Therefore it need only be implemented if the filesystem can perform that action more efficiently.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

The return value is a standard Tcl result indicating whether an error occurred in the copying process. If an error does occur, the name of the file or directory which caused the error should be placed in errorPtr. Note that, destPathPtr is the name of the directory-name which should become the mirror-image of srcPathPtr. It is not the name of a directory into which srcPathPtr should be copied (i.e. the function is much simpler than the Tcl level file copy subcommand). Finally, if the filesystem determines it cannot support the directory copy action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

LOADFILEPROC

Function to process a Tcl_FSLoadFile call. If not implemented, Tcl will fall back on a copy to native-temp followed by a Tcl_FSLoadFile on that temporary copy. Therefore it need only be implemented if the filesystem can load code directly, or it can be implemented simply to return TCL_ERROR to disable load functionality in this filesystem entirely.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Returns a standard Tcl completion code. If an error occurs, an error message is left in the interp's result. The function dynamically loads a binary code file into memory. On a successful load, the handlePtr should be filled with a token for the dynamically loaded file, and the unloadProcPtr should be filled in with the address of a procedure. The unload procedure will be called with the given Tcl_LoadHandle as its only parameter when Tcl needs to unload the file. For example, for the native filesystem, the Tcl_LoadHandle returned is currently a token which can be used in the private TclpFindSymbol to access functions in the new code. Each filesystem is free to define the Tcl_LoadHandle as it requires. Finally, if the filesystem determines it cannot support the file load action, calling Tcl_SetErrno(EXDEV) and returning a non-TCL_OK result will tell Tcl to use its standard fallback mechanisms.

UNLOADFILEPROC

Function to unload a previously successfully loaded file. If load was implemented, then this should also be implemented, if there is any cleanup action required.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

Function to process a Tcl_FSGetCwd call. Most filesystems need not implement this. It will usually only be called once, if getcwd is called before chdir. May be NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

If the filesystem supports a native notion of a current working directory (which might perhaps change independent of Tcl), this function should return that cwd as the result, or NULL if the current directory could not be determined (e.g. the user does not have appropriate permissions on the cwd directory). If NULL is returned, an error message is left in the interp's result.

CHDIRPROC

Function to process a Tcl_FSChdir call. If filesystems do not implement this, it will be emulated by a series of directory access checks. Otherwise, virtual filesystems which do implement it need only respond with a positive return result if the pathPtr is a valid, accessible directory in their filesystem. They need not remember the result, since that will be automatically remembered for use by Tcl_FSGetCwd. Real filesystems should carry out the correct action (i.e. call the correct system chdir API).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

The Tcl_FSChdirProc changes the applications current working directory to the value specified in pathPtr. The function returns -1 on error or 0 on success.
