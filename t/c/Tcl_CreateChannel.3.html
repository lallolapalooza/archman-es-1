ARGUMENTOS

const Tcl_ChannelType *typePtr (entrada)
Punta a una estructura que contiene las direcciones de los procedimientos que se pueden llamar para realizar E/S y otras funciones en el canal.

El nombre de este canal, como file3; no debe estar en uso por ningún otro canal. Puede ser NULL, en cuyo caso el canal se crea sin nombre. Si al canal creado se le asignan los canales estándar (stdin, stdout o stderr), el nombre del canal asignado será el nombre del canal estándar.

Valor arbitrario de una palabra para asociar con este canal. Este valor se pasa a los procedimientos en typePtr cuando se invocan.

TCL_READABLE significa que se solicita el manejador de entrada; TCL_WRITABLE significa que se solicita el manejador de salida.

Punta a la ubicación donde se debe almacenar el manejador específico del sistema operativo.
int size (entrada)
El tamaño, en bytes, de los búferes a asignar en este canal.
int mask (entrada)
Una combinación OR de TCL_READABLE, TCL_WRITABLE y TCL_EXCEPTION que indica los eventos que han ocurrido en este canal.

DESCRIPCIÓN

Tcl utiliza una arquitectura de canales de dos capas. Proporciona una capa genérica superior para permitir que los programas C y Tcl realicen entrada y salida utilizando las mismas API para una variedad de archivos, dispositivos, sockets, etc. Las API C genéricas se describen en la entrada del manual para Tcl_OpenFileChannel.

La capa inferior proporciona controladores de canales específicos del tipo para cada tipo de dispositivo admitido en cada plataforma. Esta entrada del manual describe las API C utilizadas para comunicarse entre la capa genérica y los controladores de canales específicos del tipo. También explica cómo se pueden agregar nuevos tipos de canales proporcionando nuevos controladores de canales.

Los controladores de canales constan de varios componentes: Primero, cada controlador de canales proporciona una estructura Tcl_ChannelType que contiene punteros a funciones que implementan las diversas operaciones utilizadas por la capa genérica para comunicarse con el controlador de canales. La estructura Tcl_ChannelType y las funciones referenciadas por ella se describen en la sección TCL_CHANNELTYPE, a continuación.

Segundo, los controladores de canales suelen proporcionar un comando Tcl para crear instancias de ese tipo de canal. Por ejemplo, el comando Tcl open crea canales que utilizan los controladores de canales de archivos y comandos, y el comando Tcl socket crea canales que utilizan sockets TCP para la comunicación de red.

Tercero, un controlador de canales opcionalmente proporciona una función C para abrir instancias de canal de ese tipo. Por ejemplo, Tcl_OpenFileChannel abre un canal que utiliza el controlador de canales de archivos, y Tcl_OpenTcpClient abre un canal que utiliza el protocolo de red TCP. Estas funciones de creación suelen utilizar Tcl_CreateChannel internamente para abrir el canal.

Para agregar un nuevo tipo de canal, debe implementar una API C o un comando Tcl que abra un canal invocando Tcl_CreateChannel. Cuando su controlador llama a Tcl_CreateChannel, le pasa una estructura Tcl_ChannelType que describe los procedimientos de E/S del controlador. La capa genérica invocará entonces las funciones referenciadas en esa estructura para realizar operaciones en el canal.

Tcl_CreateChannel abre un nuevo canal y asocia los typePtr y instanceData proporcionados con él. El canal se abre en el modo indicado por mask. Para una discusión de los controladores de canales, sus operaciones y la estructura Tcl_ChannelType, consulte la sección TCL_CHANNELTYPE, a continuación.

Tcl_CreateChannel interactúa con el código que gestiona los canales estándar. Una vez que se inicializó un canal estándar, ya sea a través de una llamada a Tcl_GetStdChannel o una llamada a Tcl_SetStdChannel, el cierre de este canal estándar hará que la próxima llamada a Tcl_CreateChannel convierta el nuevo canal en el nuevo canal estándar también. Consulte Tcl_StandardChannels para obtener un tratado general sobre los canales estándar y el comportamiento de la biblioteca Tcl con respecto a ellos.

Tcl_GetChannelInstanceData devuelve los datos de instancia asociados con el canal en channel. Esto es lo mismo que el argumento instanceData en la llamada a Tcl_CreateChannel que creó este canal.

Tcl_GetChannelType devuelve un puntero a la estructura Tcl_ChannelType utilizada por el canal en el argumento channel. Esto es lo mismo que el argumento typePtr en la llamada a Tcl_CreateChannel que creó este canal.

Tcl_GetChannelName devuelve una cadena que contiene el nombre asociado con el canal, o NULL si el argumento channelName a Tcl_CreateChannel era NULL.

TCL_CHANNELTYPE

Un controlador de canal proporciona una estructura Tcl_ChannelType que contiene punteros a funciones que implementan las diversas operaciones en un canal; estas operaciones son invocadas según sea necesario por el nivel superior. La estructura fue versionada a partir de Tcl 8.3.2/8.4 para corregir un problema con los controladores de canal bloqueados. Consulte la sección OLD CHANNEL TYPES para obtener detalles sobre la estructura antigua.

La estructura Tcl_ChannelType contiene los siguientes campos:

typedef struct Tcl_ChannelType {
        const char *typeName;
        Tcl_ChannelTypeVersion version;
        Tcl_DriverCloseProc *closeProc;
        Tcl_DriverInputProc *inputProc;
        Tcl_DriverOutputProc *outputProc;
        Tcl_DriverSeekProc *seekProc;
        Tcl_DriverSetOptionProc *setOptionProc;
        Tcl_DriverGetOptionProc *getOptionProc;
        Tcl_DriverWatchProc *watchProc;
        Tcl_DriverGetHandleProc *getHandleProc;
        Tcl_DriverClose2Proc *close2Proc;
        Tcl_DriverBlockModeProc *blockModeProc;
        Tcl_DriverFlushProc *flushProc;
        Tcl_DriverHandlerProc *handlerProc;
        Tcl_DriverWideSeekProc *wideSeekProc;
        Tcl_DriverThreadActionProc *threadActionProc;
        Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

No es necesario proporcionar implementaciones para todas las operaciones de canal. Las que no sean necesarias se pueden establecer en NULL en la estructura: blockModeProc, seekProc, setOptionProc, getOptionProc, getHandleProc y close2Proc, además de flushProc, handlerProc, threadActionProc y truncateProc. Las funciones que no se pueden implementar de manera significativa deben devolver EINVAL cuando se llamen, indicando que las operaciones que representan no están disponibles. También se debe tener en cuenta que wideSeekProc puede ser NULL si seekProc no lo es.

El usuario solo debe utilizar esta estructura para la instanciación de Tcl_ChannelType. Cuando se refieran a los campos de una estructura Tcl_ChannelType, se deben utilizar las siguientes funciones para obtener los valores: Tcl_ChannelName, Tcl_ChannelVersion, Tcl_ChannelBlockModeProc, Tcl_ChannelCloseProc, Tcl_ChannelClose2Proc, Tcl_ChannelInputProc, Tcl_ChannelOutputProc, Tcl_ChannelSeekProc, Tcl_ChannelWideSeekProc, Tcl_ChannelThreadActionProc, Tcl_ChannelTruncateProc, Tcl_ChannelSetOptionProc, Tcl_ChannelGetOptionProc, Tcl_ChannelWatchProc, Tcl_ChannelGetHandleProc, Tcl_ChannelFlushProc o Tcl_ChannelHandlerProc.

El cambio en la estructura se hizo de tal manera que los tipos de canal estándar son binariamente compatibles. Sin embargo, los tipos de canal que utilizan canales bloqueados (es decir, TLS, Trf) tienen nuevas versiones para corresponder al cambio anterior, ya que el código anterior para canales bloqueados tenía problemas.

TYPENAME

El campo typeName contiene una cadena terminada en nulo que identifica el tipo de dispositivo implementado por este controlador, por ejemplo, file o socket.

Este valor se puede obtener con Tcl_ChannelName, que devuelve un puntero a la cadena.

VERSION

El campo version debe establecerse en la versión de la estructura que se requiere. TCL_CHANNEL_VERSION_2 es la mínima recomendada. TCL_CHANNEL_VERSION_3 debe establecerse para especificar el miembro wideSeekProc. TCL_CHANNEL_VERSION_4 debe establecerse para especificar el miembro threadActionProc (incluye wideSeekProc). TCL_CHANNEL_VERSION_5 debe establecerse para especificar los miembros truncateProc (incluye wideSeekProc y threadActionProc). Si no se establece ninguno de estos, se asume que la estructura Tcl_ChannelType tiene la estructura original. Consulte OLD CHANNEL TYPES para más detalles. Aunque Tcl reconocerá y funcionará con cualquiera de estas estructuras, los canales bloqueados deben ser de al menos TCL_CHANNEL_VERSION_2 para funcionar correctamente.

Este valor se puede obtener con Tcl_ChannelVersion, que devuelve uno de TCL_CHANNEL_VERSION_5, TCL_CHANNEL_VERSION_4, TCL_CHANNEL_VERSION_3, TCL_CHANNEL_VERSION_2 o TCL_CHANNEL_VERSION_1.

BLOCKMODEPROC

El campo blockModeProc contiene la dirección de una función llamada por el nivel superior para establecer el modo bloqueante y no bloqueante del dispositivo. BlockModeProc debe corresponder al siguiente prototipo:

typedef int Tcl_DriverBlockModeProc(
        ClientData instanceData,
        int mode);

El instanceData es el mismo que el valor proporcionado a Tcl_CreateChannel cuando se creó este canal. El argumento mode es either TCL_MODE_BLOCKING o TCL_MODE_NONBLOCKING para establecer el dispositivo en modo bloqueante o no bloqueante. La función debe devolver cero si la operación fue exitosa, o un código de error POSIX distinto de cero si la operación falló.

Si la operación es exitosa, la función puede modificar el instanceData proporcionado para registrar que el canal entró en modo bloqueante o no bloqueante e implementar el comportamiento bloqueante o no bloqueante. Para algunos tipos de dispositivos, el comportamiento bloqueante y no bloqueante puede implementarse mediante el sistema operativo subyacente; para otros tipos de dispositivos, el comportamiento debe emularse en el controlador de canal.

Este valor se puede obtener con Tcl_ChannelBlockModeProc, que devuelve un puntero a la función.

Un controlador de canal que no proporciona un blockModeProc debe ser muy, muy cuidadoso. Debe decir al nivel superior exactamente qué modo bloqueante es aceptable para él, y también debe documentarlo para el usuario para que el modo bloqueante del canal no se cambie a un valor inaceptable. Cualquier confusión aquí puede llevar al intérprete a una colisión (falsa y difícil de encontrar).

CLOSEPROC Y CLOSE2PROC

El campo closeProc contiene la dirección de una función llamada por el nivel superior para limpiar la información relacionada con el controlador cuando se cierra el canal. CloseProc debe corresponder al siguiente prototipo:

typedef int Tcl_DriverCloseProc(
        ClientData instanceData,
        Tcl_Interp *interp);

El instanceData es el mismo que el valor proporcionado a Tcl_CreateChannel cuando se creó este canal. La función debe liberar cualquier almacenamiento mantenido por el controlador de canal para este canal y cerrar los dispositivos de entrada y salida encapsulados por este canal. Todos los datos de salida en cola se han limpiado antes de que se llame a esta función, y ninguna operación del controlador se invocará después de llamar a closeProc. Si la operación de cierre es exitosa, se ejecutará el procedimiento.

uld return zero; otherwise it should return a nonzero POSIX error code. In addition, if an error occurs and interp is not NULL, the procedure should store an error message in the interpreter's result.

Alternatively, channels that support closing the read and write sides independently may set closeProc to TCL_CLOSE2PROC and set close2Proc to the address of a function that matches the following prototype:

typedef int Tcl_DriverClose2Proc(
        ClientData instanceData,
        Tcl_Interp *interp,
        int flags);

The close2Proc will be called with flags set to an OR'ed combination of TCL_CLOSE_READ or TCL_CLOSE_WRITE to indicate that the driver should close the read and/or write side of the channel. The channel driver may be invoked to perform additional operations on the channel after close2Proc is called to close one or both sides of the channel. If flags is 0 (zero), the driver should close the channel in the manner described above for closeProc. No further operations will be invoked on this instance after close2Proc is called with all flags cleared. In all cases, the close2Proc function should return zero if the close operation was successful; otherwise it should return a nonzero POSIX error code. In addition, if an error occurs and interp is not NULL, the procedure should store an error message in the interpreter's result.

The closeProc and close2Proc values can be retrieved with Tcl_ChannelCloseProc or Tcl_ChannelClose2Proc, which return a pointer to the respective function.

PROCEDIMIENTO DE ENTRADA

El campo inputProc contiene la dirección de una función llamada por la capa genérica para leer datos del archivo o dispositivo y almacenarlos en un búfer interno. InputProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverInputProc(
        ClientData instanceData,
        char *buf,
        int bufSize,
        int *errorCodePtr);

InstanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando se creó el canal. El argumento buf apunta a una matriz de bytes en la que se almacenará la entrada del dispositivo, y el argumento bufSize indica cuántos bytes están disponibles en buf.

El argumento errorCodePtr apunta a una variable entera proporcionada por la capa genérica. Si ocurre un error, la función debe establecer la variable en un código de error POSIX que identifique el error que ocurrió.

La función debe leer datos del dispositivo de entrada encapsulado por el canal y almacenarlos en buf. En caso de éxito, la función debe devolver un entero no negativo que indique cuántos bytes se leyeron del dispositivo de entrada y se almacenaron en buf. En caso de error, la función debe devolver -1. Si ocurre un error después de que se hayan leído algunos datos del dispositivo, esos datos se pierden.

Si inputProc puede determinar que el dispositivo de entrada tiene algunos datos disponibles pero menos de los solicitados por el argumento bufSize, la función solo debe intentar leer tantos datos como estén disponibles y regresar sin bloquear. Si no hay datos disponibles en absoluto en el dispositivo de entrada y el canal está en modo no bloqueante, la función debe devolver un error EAGAIN. Si no hay datos disponibles en absoluto en el dispositivo de entrada y el canal está en modo bloqueante, la función debe bloquearse durante el menor tiempo posible hasta que se pueda leer al menos un byte de datos del dispositivo; luego, debe devolver tantos datos como pueda leer sin bloquear.

Este valor se puede recuperar con Tcl_ChannelInputProc, que devuelve un puntero a la función.

PROCEDIMIENTO DE SALIDA

El campo outputProc contiene la dirección de una función llamada por la capa genérica para transferir datos de un búfer interno al dispositivo de salida. OutputProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverOutputProc(
        ClientData instanceData,
        const char *buf,
        int toWrite,
        int *errorCodePtr);

InstanceData es el mismo que el valor pasado a Tcl_CreateChannel cuando se creó el canal. El argumento buf contiene una matriz de bytes que se escribirán en el dispositivo, y el argumento toWrite indica cuántos bytes se escribirán desde el argumento buf.

El argumento errorCodePtr apunta a una variable entera proporcionada por la capa genérica. Si ocurre un error, la función debe establecer esta variable en un código de error POSIX que identifique el error.

La función debe escribir los datos en buf en el dispositivo de salida encapsulado por el canal. En caso de éxito, la función debe devolver un entero no negativo que indique cuántos bytes se escribieron en el dispositivo de salida. El valor de retorno es normalmente el mismo que toWrite, pero puede ser menor en algunos casos, como si la operación de salida se interrumpe por una señal. Si ocurre un error, la función debe devolver -1. En caso de error, es posible que se hayan escrito algunos datos en el dispositivo.

Si el canal no está bloqueado y el dispositivo de salida no puede absorber ningún dato, la función debe devolver -1 con un error EAGAIN sin escribir ningún dato.

Este valor se puede recuperar con Tcl_ChannelOutputProc, que devuelve un puntero a la función.

SEEKPROC Y WIDESEEKPROC

El campo seekProc contiene la dirección de una función llamada por la capa genérica para mover el punto de acceso en el que se aplicarán las operaciones de entrada o salida posteriores. SeekProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverSeekProc(
        ClientData instanceData,
        long offset,
        int seekMode,
        int *errorCodePtr);

El argumento instanceData es el mismo que el valor dado a Tcl_CreateChannel cuando se creó este canal. Offset y seekMode tienen el mismo significado que para el procedimiento Tcl_Seek (descrito en la entrada del manual para Tcl_OpenFileChannel).

El argumento errorCodePtr apunta a una variable entera proporcionada por la capa genérica para devolver valores errno de la función. La función debe establecer esta variable en un código de error POSIX si ocurre un error. La función debe almacenar un código de error EINVAL si el tipo de canal no implementa la búsqueda.

El valor de retorno es el nuevo punto de acceso o -1 en caso de error. Si ocurrió un error, la función no debe mover el punto de acceso.

Si hay un campo seekProc no nulo, el campo wideSeekProc puede contener la dirección de una función alternativa a utilizar que maneja desplazamientos amplios (es decir, mayores de 32 bits), permitiendo así buscar dentro de archivos de más de 2 GB. Se llamará a wideSeekProc con preferencia a seekProc, pero ambos deben estar definidos si se define wideSeekProc. WideSeekProc debe coincidir con el siguiente prototipo:

typedef Tcl_WideInt Tcl_DriverWideSeekProc(
        ClientData instanceData,
        Tcl_WideInt offset,
        int seekMode,
        int *errorCodePtr);

Los argumentos y los valores de retorno significan lo mismo que con seekProc anteriormente, excepto que el tipo de los desplazamientos y el tipo de retorno son diferentes.

El valor seekProc se puede recuperar con Tcl_ChannelSeekProc, que devuelve un puntero a la función, y de forma similar, el wideSeekProc se puede recuperar con Tcl_ChannelWideSeekProc.

SETOPTIONPROC

El campo setOptionProc contiene la dirección de una función llamada por la capa genérica para establecer una opción específica del tipo de canal en un canal. setOptionProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverSetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        const char *newValue);

optionName es el nombre de una opción a establecer, y newValue es el nuevo valor para esa opción, como una cadena. instanceData es el mismo que el valor dado a Tcl_CreateChannel cuando se creó este canal. La función debe realizar cualquier acción específica del tipo de canal requerida para implementar el nuevo valor de la opción.

Algunas opciones son manejadas por el código genérico y esta función nunca se llama para establecerlas, por ejemplo, -blockmode. Otras opciones son específicas de cada tipo de canal y se llamará al procedimiento setOptionProc del controlador del canal para implementarlas. El campo setOptionProc puede ser NULL, lo que indica que este tipo de canal no admite opciones específicas.

Si el valor de la opción se modifica correctamente al nuevo valor, la función devuelve TCL_OK. Debe llamar a Tcl_BadChannelOption, que a su vez devuelve TCL_ERROR si optionName no se reconoce. Si newValue especifica un valor para la opción que no es compatible o si ocurre un error de llamada al sistema, la función debe dejar un mensaje de error en el resultado de interp si interp no es NULL. La función también debe llamar a Tcl_SetErrno para almacenar un código de error POSIX apropiado.

Este valor se puede recuperar con Tcl_ChannelSetOptionProc, que devuelve un puntero a la función.

GETOPTIONPROC

El campo getOptionProc contiene la dirección de una función llamada por la capa genérica para obtener el valor de una opción específica del tipo de canal en un canal. getOptionProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverGetOptionProc(
        ClientData instanceData,
        Tcl_Interp *interp,
        const char *optionName,
        Tcl_DString *optionValue);

OptionName es el nombre de una opción admitida por este tipo de canal. Si el nombre de la opción no es NULL, la función almacena su valor actual, como una cadena, en la cadena dinámica de Tcl optionValue. Si optionName es NULL, la función almacena en optionValue una lista alternante de todas las opciones admitidas y sus valores actuales. En caso de éxito, la función devuelve TCL_OK. Debe llamar a Tcl_BadChannelOption, que a su vez devuelve TCL_ERROR si optionName no es reconocido. Si ocurre un error de llamada al sistema, la función debe dejar un mensaje de error en el resultado de interp si interp no es NULL. La función también debe llamar a Tcl_SetErrno para almacenar un código de error POSIX apropiado.

Algunas opciones son manejadas por el código genérico y esta función nunca se llama para recuperar su valor, por ejemplo, -blockmode. Otras opciones son específicas de cada tipo de canal y se llamará al procedimiento getOptionProc del controlador de canal para implementarlas. El campo getOptionProc puede ser NULL, lo que indica que este tipo de canal no admite opciones específicas del tipo.

Este valor se puede recuperar con Tcl_ChannelGetOptionProc, que devuelve un puntero a la función.

WATCHPROC

El campo watchProc contiene la dirección de una función llamada por la capa genérica para inicializar el mecanismo de notificación de eventos para detectar eventos de interés en este canal. WatchProc debe coincidir con el siguiente prototipo:

typedef void Tcl_DriverWatchProc(
        ClientData instanceData,
        int mask);

InstanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó este canal. El argumento mask es una combinación OR de TCL_READABLE, TCL_WRITABLE y TCL_EXCEPTION; indica los eventos que el llamador está interesado en detectar en este canal.

La función debe inicializar mecanismos específicos del tipo de dispositivo para detectar cuándo ocurre un evento de interés en el canal. Cuando ocurre uno o más de los eventos designados en el canal, el controlador del canal es responsable de llamar a Tcl_NotifyChannel para informar al módulo genérico de canales. El controlador debe tener cuidado de no privar a otros controladores de canales o fuentes de devoluciones de llamada invocando Tcl_NotifyChannel con demasiada frecuencia. La equidad se puede asegurar utilizando la cola de eventos de Tcl para permitir que el evento del canal se programe en secuencia con otros eventos. Consulte la descripción de Tcl_QueueEvent para obtener detalles sobre cómo poner en cola un evento.

Este valor se puede recuperar con Tcl_ChannelWatchProc, que devuelve un puntero a la función.

GETHANDLEPROC

El campo getHandleProc contiene la dirección de una función llamada por la capa genérica para recuperar un manejador específico del dispositivo del canal. GetHandleProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverGetHandleProc(
        ClientData instanceData,
        int direction,
        ClientData *handlePtr);

InstanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó este canal. El argumento direction es TCL_READABLE para recuperar el manejador utilizado para la entrada, o TCL_WRITABLE para recuperar el manejador utilizado para la salida.

Si la implementación del canal tiene manejadores específicos del dispositivo, la función debe recuperar el manejador apropiado asociado con el canal, según el argumento direction. El manejador debe almacenarse en la ubicación a la que apunta handlePtr, y se debe devolver TCL_OK. Si el canal no está abierto para la dirección especificada, o si la implementación del canal no utiliza manejadores de dispositivo, la función debe devolver TCL_ERROR.

Este valor se puede recuperar con Tcl_ChannelGetHandleProc, que devuelve un puntero a la función.

FLUSHPROC

El campo flushProc está actualmente reservado para uso futuro. Debe establecerse en NULL. FlushProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverFlushProc(
        ClientData instanceData);

Este valor se puede recuperar con Tcl_ChannelFlushProc, que devuelve un puntero a la función.

HANDLERPROC

El campo handlerProc contiene la dirección de una función llamada por la capa genérica para notificar al canal que ocurrió un evento. Debe definirse para controladores de canales apilados que deseen ser notificados de eventos que ocurran en el canal subyacente (apilado). HandlerProc debe coincidir con el siguiente prototipo:

typedef int Tcl_DriverHandlerProc(
        ClientData instanceData,
        int interestMask);

InstanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó este canal. El interestMask es una combinación OR de TCL_READABLE o TCL_WRITABLE; indica qué tipo de evento ocurrió en este canal.

Este valor se puede recuperar con Tcl_ChannelHandlerProc, que devuelve un puntero a la función.

THREADACTIONPROC

El campo threadActionProc contiene la dirección de la función llamada por la capa genérica cuando se crea, cierra o se va a mover un canal a un hilo diferente, es decir, siempre que el estado del controlador específico del hilo pueda tener que inicializarse o actualizarse. Puede ser NULL. La acción TCL_CHANNEL_THREAD_REMOVE se utiliza para notificar al controlador que debe actualizar o eliminar cualquier dato específico del hilo que pueda estar manteniendo para el canal.

La acción TCL_CHANNEL_THREAD_INSERT se utiliza para notificar al controlador que debe actualizar o inicializar cualquier dato específico del hilo que pueda estar manteniendo utilizando el hilo que llama como el asociado. Consulte Tcl_CutChannel y Tcl_SpliceChannel para obtener más detalles.

typedef void Tcl_DriverThreadActionProc(
        ClientData instanceData,
        int action);

InstanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó este canal.

Estos valores se pueden recuperar con Tcl_ChannelThreadActionProc, que devuelve un puntero a la función.

TRUNCATEPROC

El campo truncateProc contiene la dirección de la función llamada por la capa genérica cuando un canal se trunca a una longitud determinada. Puede ser NULL.

typedef int Tcl_DriverTruncateProc(
        ClientData instanceData,
        Tcl_WideInt length);

InstanceData es el mismo valor que se pasó a Tcl_CreateChannel cuando se creó este canal, y length es la nueva longitud del archivo subyacente, que no debe ser negativa. El resultado debe ser 0 en caso de éxito o un código errno (adecuado para usar con Tcl_SetErrno) en caso de fallo.

Estos valores se pueden recuperar con Tcl_ChannelTruncateProc, que devuelve un puntero a la función.

TCL_BADCHANNELOPTION

Este procedimiento genera un mensaje de error de “opción inválida” en un intérprete (opcional). Se utiliza por los controladores de canales cuando se solicita una opción de Establecer/Obtener inválida. Su propósito es concatenar la lista de opciones genéricas a las específicas y factorizar la cadena del mensaje de error de opciones genéricas.

Siempre devuelve TCL_ERROR.

Se genera un mensaje de error en el valor de resultado de interp para indicar que se invocó un comando con una opción incorrecta. El mensaje tiene la forma

    bad option "blah": should be one of
    <...generic options...>+<...specific options...>
así que obtienes, por ejemplo: 
    bad option "-blah": should be one of -blocking,
    -buffering, -buffersize, -eofchar, -translation,
    -peername, or -sockname
cuando se llama con optionList igual a “peername sockname”.

“blah” es el argumento optionName y “<specific options>” es una lista separada por espacios de palabras de opciones específicas. La función se encarga de insertar signos de menos antes de cada opción, comas después y un “o” antes de la última opción.

TIPOS DE CANALES ANTIGUOS

La estructura original (8.3.1 y anteriores) Tcl_ChannelType contiene los siguientes campos:

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
} Tcl_ChannelType;

Todavía es posible crear canales con la estructura anterior. El código interno del canal determinará la versión. Es imperativo usar la nueva estructura Tcl_ChannelType si está creando un controlador de canal apilado, debido a problemas con la implementación anterior de canales apilados (en 8.2.0 a 8.3.1).

Antes de 8.4.0 (es decir, durante los últimos lanzamientos de 8.3 y la parte inicial del ciclo de desarrollo de 8.4), la estructura Tcl_ChannelType contenía los siguientes campos:

typedef struct Tcl_ChannelType {
    const char *typeName;
    Tcl_ChannelTypeVersion version;
    Tcl_DriverCloseProc *closeProc;
    Tcl_DriverInputProc *inputProc;
    Tcl_DriverOutputProc *outputProc;
    Tcl_DriverSeekProc *seekProc;
    Tcl_DriverSetOptionProc *setOptionProc;
    Tcl_DriverGetOptionProc *getOptionProc;
    Tcl_DriverWatchProc *watchProc;
    Tcl_DriverGetHandleProc *getHandleProc;
    Tcl_DriverClose2Proc *close2Proc;
    Tcl_DriverBlockModeProc *blockModeProc;
    Tcl_DriverFlushProc *flushProc;
    Tcl_DriverHandlerProc *handlerProc;
    Tcl_DriverTruncateProc *truncateProc;
} Tcl_ChannelType;

Cuando la estructura anterior se registra como un tipo de canal, el campo version siempre debe ser TCL_CHANNEL_VERSION_2.
