DESCRIPTION

There are several reasons for calling the Tcl_FS API functions (e.g. Tcl_FSAccess and Tcl_FSStat) rather than calling system level functions like access and stat directly. First, they will work cross-platform, so an extension which calls them should work unmodified on Unix and Windows. Second, the Windows implementation of some of these functions fixes some bugs in the system level calls. Third, these function calls deal with any “Utf to platform-native” path conversions which may be required (and may cache the results of such conversions for greater efficiency on subsequent calls). Fourth, and perhaps most importantly, all of these functions are “virtual filesystem aware”. Any virtual filesystem (VFS for short) which has been registered (through Tcl_FSRegister) may reroute file access to alternative media or access methods. This means that all of these functions (and therefore the corresponding file, glob, pwd, cd, open, etc. Tcl commands) may be operate on “files” which are not native files in the native filesystem. This also means that any Tcl extension which accesses the filesystem (FS for short) through this API is automatically “virtual filesystem aware”. Of course, if an extension accesses the native filesystem directly (through platform-specific APIs, for example), then Tcl cannot intercept such calls.

If appropriate VFSes have been registered, the “files” may, to give two examples, be remote (e.g. situated on a remote ftp server) or archived (e.g. lying inside a .zip archive). Such registered filesystems provide a lookup table of functions to implement all or some of the functionality listed here. Finally, the Tcl_FSStat and Tcl_FSLstat calls abstract away from what the “struct stat” buffer is actually declared to be, allowing the same code to be used both on systems with and systems without support for files larger than 2GB in size.

The Tcl_FS API is Tcl_Obj-ified and may cache internal representations and other path-related strings (e.g. the current working directory). One side-effect of this is that one must not pass in values with a reference count of zero to any of these functions. If such calls were handled, they might result in memory leaks (under some circumstances, the filesystem code may wish to retain a reference to the passed in value, and so one must not assume that after any of these calls return, the value still has a reference count of zero - it may have been incremented) or in a direct segmentation fault (or other memory access error) due to the value being freed part way through the complex value manipulation required to ensure that the path is fully normalized and absolute for filesystem determination. The practical lesson to learn from this is that

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

is wrong, and may cause memory errors. The path must have its reference count incremented before passing it in, or decrementing it. For this reason, values with a reference count of zero are considered not to be valid filesystem paths and calling any Tcl_FS API function with such a value will result in no action being taken.

FS API FUNCTIONS

Tcl_FSCopyFile attempts to copy the file given by srcPathPtr to the path name given by destPathPtr. If the two paths given lie in the same filesystem (according to Tcl_FSGetFileSystemForPath) then that filesystem's “copy file” function is called (if it is non-NULL). Otherwise the function returns -1 and sets the errno global C variable to the “EXDEV” POSIX error code (which signifies a “cross-domain link”).

Tcl_FSCopyDirectory attempts to copy the directory given by srcPathPtr to the path name given by destPathPtr. If the two paths given lie in the same filesystem (according to Tcl_FSGetFileSystemForPath) then that filesystem's “copy file” function is called (if it is non-NULL). Otherwise the function returns -1 and sets the errno global C variable to the “EXDEV” POSIX error code (which signifies a “cross-domain link”).

Tcl_FSCreateDirectory attempts to create the directory given by pathPtr by calling the owning filesystem's “create directory” function.

Tcl_FSDeleteFile attempts to delete the file given by pathPtr by calling the owning filesystem's “delete file” function.

Tcl_FSRemoveDirectory attempts to remove the directory given by pathPtr by calling the owning filesystem's “remove directory” function.

Tcl_FSRenameFile attempts to rename the file or directory given by srcPathPtr to the path name given by destPathPtr. If the two paths given lie in the same filesystem (according to Tcl_FSGetFileSystemForPath) then that filesystem's “rename file” function is called (if it is non-NULL). Otherwise the function returns -1 and sets the errno global C variable to the “EXDEV” POSIX error code (which signifies a “cross-domain link”).

Tcl_FSListVolumes calls each filesystem which has a non-NULL “list volumes” function and asks them to return their list of root volumes. It accumulates the return values in a list which is returned to the caller (with a reference count of 0).

Tcl_FSEvalFileEx reads the file given by pathPtr using the encoding identified by encodingName and evaluates its contents as a Tcl script. It returns the same information as Tcl_EvalObjEx. If encodingName is NULL, the system encoding is used for reading the file contents. If the file could not be read then a Tcl error is returned to describe why the file could not be read. The eofchar for files is “\x1A” (^Z) for all platforms. If you require a “^Z” in code for string comparison, you can use “\x1A”, which will be safely substituted by the Tcl interpreter into “^Z”. Tcl_FSEvalFile is a simpler version of Tcl_FSEvalFileEx that always uses the system encoding when reading the file.

Tcl_FSLoadFile dynamically loads a binary code file into memory and returns the addresses of two procedures within that file, if they are defined. The appropriate function for the filesystem to which pathPtr belongs will be called. If that filesystem does not implement this function (most virtual filesystems will not, because of OS limitations in dynamically loading binary code), Tcl will attempt to copy the file to a temporary directory and load that temporary file. Tcl_FSUnloadFile reverses the operation, asking for the library indicated by the loadHandle to be removed from the process. Note that, unlike with the unload command, this does not give the library any opportunity to clean up.

Both the above functions return a standard Tcl completion code. If an error occurs, an error message is left in the interp's result.

The token provided via the variable indicated by loadHandlePtr may be used with Tcl_FindSymbol.

Tcl_FSMatchInDirectory is used by the globbing code to search a directory for all files which match a given pattern. The appropriate function for the filesystem to which pathPtr belongs will be called.

The return value is a standard Tcl result indicating whether an error occurred in globbing. Error messages are placed in interp (unless interp is NULL, which is allowed), but good results are placed in the resultPtr given.

Note that the glob code implements recursive patterns internally, so this function will only ever be passed simple patterns, which can be matched using the logic of string match. To handle recursion, Tcl will call this function frequently asking only for directories to be returned. A special case of being called with a NULL pattern indicates that the path needs to be checked only for the correct type.

Tcl_FSLink replaces the library version of readlink, and extends it to support the creation of links. The appropriate function for the filesystem to which linkNamePtr belongs will be called.

If the toPtr is NULL, a “read link” action is performed. The result is a Tcl_Obj specifying the contents of the symbolic link given by linkNamePtr, or NULL if the link could not be read. The result is owned by the caller, which should call Tcl_DecrRefCount when the result is no longer needed. If the toPtr is not NULL, Tcl should create a link of one of the types passed in in the linkAction flag. This flag is an OR'ed combination of TCL_CREATE_SYMBOLIC_LINK and TCL_CREATE_HARD_LINK. Where a choice exists (i.e. more than one flag is passed in), the Tcl convention is to prefer symbolic links. When a link is successfully created, the return value should be toPtr (which is therefore already owned by the caller). If unsuccessful, NULL is returned.

Tcl_FSLstat fills the Tcl_StatBuf structure statPtr with information about the specified file. You do not need any access rights to the file to get this information but you need search rights to all directories named in the path leading to the file. El resultado es un puntero a un *Tcl_Obj* que especifica el directorio actual, o NULL si no se puede determinar el directorio. Si se devuelve NULL, se deja un mensaje de error en el resultado de *interp*. El resultado ya tiene su contador de referencias incrementado para el llamador. Cuando ya no se necesite, ese contador de referencias debe decrementarse. Esto es necesario para la seguridad de hilos, para que múltiples hilos puedan acceder a esta y a funciones relacionadas, garantizando al mismo tiempo que los resultados siempre sean válidos. **Tcl_FSChdir** reemplaza la versión de biblioteca de **chdir**. La ruta se normaliza y luego se pasa al sistema de archivos que la reclama. Si ese sistema de archivos no implementa esta función, Tcl recurrirá a una combinación de **stat** y **access** para comprobar si el directorio existe y tiene permisos adecuados. Para los resultados, consulte la documentación de **chdir**. Si tiene éxito, mantenemos un registro de la ruta exitosa en *cwdPathPtr* para futuras llamadas a **Tcl_FSGetCwd**. **Tcl_FSPathSeparator** devuelve el carácter separador que se utilizará para el elemento más específico de la ruta especificada por *pathPtr* (es decir, la última parte de la ruta). El separador se devuelve como un *Tcl_Obj* que contiene una cadena de longitud 1. Si la ruta es inválida, se devuelve NULL. **Tcl_FSJoinPath** toma el *Tcl_Obj* dado, que debe ser una lista válida (que permite tener un contador de referencias de cero), y devuelve el valor de la ruta considerando los primeros *elements* elementos como segmentos de ruta válidos (cada segmento puede ser una ruta completa, una ruta parcial o solo un nombre de directorio o archivo). Si algún segmento es realmente una ruta absoluta, todos los segmentos anteriores se descartan. Si *elements* es menor que 0, usamos toda la lista. Es posible que el valor devuelto sea realmente un elemento de la lista dada, por lo que el llamador debe tener cuidado al incrementar el contador de referencias del resultado antes de liberar la lista. El valor devuelto, típicamente con un contador de referencias de cero (pero podría ser compartido en ciertos casos), contiene la ruta unida. El llamador debe agregar un contador de referencias al valor antes de usarlo. En particular, el valor devuelto podría ser un elemento de la lista dada, por lo que liberar la lista podría liberar el valor prematuramente si no se ha tomado un contador de referencias. Si el número de elementos es cero, el valor devuelto será una cadena vacía *Tcl_Obj*. **Tcl_FSSplitPath** toma el *Tcl_Obj* dado, que debe ser una ruta válida, y devuelve un valor de lista que contiene cada segmento de esa ruta como elemento. Devuelve un valor de lista con un contador de referencias de cero. Si el *lenPtr* proporcionado no es NULL, la variable a la que apunta se actualiza para contener el número de elementos en el valor de lista devuelto. **Tcl_FSEqualPaths** prueba si dos rutas dadas representan el mismo objeto del sistema de archivos. Devuelve 1 si las rutas son iguales, 0 si son diferentes. Si alguna de las rutas es NULL, siempre se devuelve 0. **Tcl_FSGetNormalizedPath** intenta extraer de un *Tcl_Obj* dado una representación normalizada única, cuyo valor de cadena puede usarse como identificador único para el archivo. Devuelve la representación normalizada de la ruta, propiedad de Tcl, o NULL si la ruta fue inválida o no se pudo convertir correctamente. La extracción de rutas absolutas y normalizadas es muy eficiente (porque el sistema de archivos opera sobre estas representaciones internamente), aunque el resultado cuando el sistema de archivos contenga muchos enlaces simbólicos no sea la versión más amigable de una ruta. El valor de retorno es propiedad de Tcl y tiene una vida útil equivalente a la del *pathPtr* proporcionado (a menos que sea una ruta relativa, en cuyo caso el valor normalizado puede liberarse en cualquier momento que cambie el cwd) - el llamador puede incrementar el contador de referencias si lo desea para mantener una copia por más tiempo. **Tcl_FSJoinToPath** toma el valor dado, que suele ser una ruta válida o NULL, y une los segmentos de ruta dados. Devuelve un valor, típicamente con un contador de referencias de cero (pero podría ser compartido en ciertos casos), que contiene la ruta unida. El llamador debe incrementar el contador de referencias antes de usarlo. Si algún valor pasado a esta función (*pathPtr* o elementos de *path*) tiene un contador de referencias de cero, estos se liberarán cuando esta función devuelva. **Tcl_FSConvertToPathType** intenta convertir el *Tcl_Obj* dado a un tipo de ruta válido, teniendo en cuenta que el cwd podría haber cambiado incluso si este valor ya se supone que es del tipo correcto. El nombre de archivo puede comenzar con ~ (para indicar el directorio del usuario actual) o ~ (para indicar el directorio de cualquier usuario). Si la conversión es exitosa (es decir, el valor es una ruta válida en uno de los sistemas de archivos actuales), se devuelve **TCL_OK**. De lo contrario, se devuelve **TCL_ERROR**, y puede dejar un mensaje de error en el intérprete. **Tcl_FSGetInternalRep** extrae la representación interna de un valor de ruta dado en el sistema de archivos dado. Si el valor de ruta pertenece a un sistema de archivos diferente, devolvemos NULL. Si la representación interna es actualmente NULL, intentamos generarla llamando a **Tcl_FSCreateInternalRepProc** del sistema de archivos. Devuelve NULL o una representación válida de la ruta interna. Esta representación interna está en caché, por lo que las llamadas repetidas a esta función no requieren conversiones adicionales. **Tcl_FSGetTranslatedPath** intenta extraer la ruta traducida a partir del *Tcl_Obj* dado. Si la traducción es exitosa (es decir, el valor es una ruta válida), se devuelve el valor. De lo contrario, se devuelve NULL, y puede dejar un mensaje de error en el intérprete. Una ruta traducida es aquella que no contiene ~ ni ~usuario (estas se han expandido a su representación actual en el sistema de archivos). El valor devuelto es propiedad del llamador, quien debe almacenarlo o llamar a **Tcl_DecrRefCount** para garantizar la liberación de memoria. Esta función tiene poca utilidad práctica, y **Tcl_FSGetNormalizedPath** o **Tcl_FSGetNativePath** son generalmente funciones más adecuadas para los fines. **Tcl_FSGetTranslatedStringPath** hace lo mismo que **Tcl_FSGetTranslatedPath**, pero devuelve una cadena o NULL. La cadena devuelta es dinámicamente todao es propiedad del llamador, quien debe almacenarlo o llamar a ckfree para asegurarse de que se libere. Nuevamente, Tcl_FSGetNormalizedPath o Tcl_FSGetNativePath son funciones que generalmente son mejores para usar en la mayoría de los propósitos.

Tcl_FSNewNativePath realiza algo así como lo inverso de las conversiones habituales obj->path->nativerep. Si algún código recupera una ruta en formato nativo (de, por ejemplo, readlink o un diálogo nativo) y esa ruta se va a utilizar a nivel de Tcl, entonces llamar a esta función es una forma eficiente de crear el tipo de valor de ruta apropiado.

El valor resultante es un valor de "ruta" puro, que solo recibirá una representación de cadena UTF-8 si es requerido por algún código de Tcl.

Tcl_FSGetNativePath es para uso de los sistemas de archivos nativos Win/Unix, de modo que puedan recuperar fácilmente la representación nativa (char* o TCHAR*) de una ruta. Esta función es un envoltorio de conveniencia alrededor de Tcl_FSGetInternalRep. Puede ser deseable en el futuro tener representaciones nativas no basadas en cadenas (por ejemplo, en macOS, una representación que use una estructura fileSpec de FSRef sería probablemente más eficiente). En Windows, una representación Unicode completa permitiría rutas de longitud ilimitada. Actualmente, la representación es simplemente una cadena de caracteres que puede contener la ruta relativa o una ruta completa, absoluta y normalizada en la codificación nativa (condiciones complejas dictan cuál de estas se proporcionará, por lo que no se puede confiar en ninguna, a menos que se sepa que la ruta es absoluta). Si necesita una ruta nativa que deba ser absoluta, entonces debe solicitar la versión nativa de una ruta normalizada. Si por alguna razón se necesita una versión no absoluta y no normalizada de la ruta, esta debe construirse por separado (por ejemplo, usando Tcl_FSGetTranslatedPath).

La representación nativa se almacena en caché para que las llamadas repetidas a esta función no requieran conversiones adicionales. El valor de retorno es propiedad de Tcl y tiene una vida útil equivalente a la del pathPtr pasado (a menos que sea una ruta relativa, en cuyo caso la representación nativa puede liberarse en cualquier momento en que cambie el cwd).

Tcl_FSFileSystemInfo devuelve una lista de dos elementos. El primer elemento es el nombre del sistema de archivos (por ejemplo, "native", "vfs", "zip" o "prowrap", quizás), y el segundo es el tipo particular de la ruta dada dentro de ese sistema de archivos (que depende del sistema de archivos). El segundo elemento puede estar vacío si el sistema de archivos no proporciona una categorización adicional de archivos.

Se devuelve un valor de lista válido, a menos que el valor de la ruta no se reconozca, en cuyo caso se devolverá NULL.

Tcl_FSGetFileSystemForPath devuelve un puntero al Tcl_Filesystem que acepta esta ruta como válida.

Si ningún sistema de archivos acepta la ruta, se devuelve NULL.

Tcl_FSGetPathType determina si la ruta dada es relativa al directorio actual, relativa al volumen actual o absoluta.

Devuelve uno de TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE o TCL_PATH_VOLUME_RELATIVE

LA API DEL SISTEMA DE ARCHIVOS VIRTUAL

Un sistema de archivos proporciona una estructura Tcl_Filesystem que contiene punteros a funciones que implementan las diversas operaciones de un sistema de archivos; estas operaciones se invocan según sea necesario por la capa genérica, lo que generalmente ocurre a través de las funciones enumeradas anteriormente.

Las estructuras Tcl_Filesystem se manipulan utilizando los siguientes métodos.

Tcl_FSRegister toma un puntero a una estructura de sistema de archivos y una pieza opcional de datos para asociar con ese sistema de archivos. Al llamar a esta función, Tcl adjuntará el sistema de archivos a la lista de sistemas de archivos conocidos y será completamente funcional inmediatamente. Tcl no verifica si el mismo sistema de archivos se registra múltiples veces (y en general, eso no es algo bueno de hacer). Se devolverá TCL_OK.

Tcl_FSUnregister elimina la estructura del sistema de archivos dada de la lista de sistemas de archivos conocidos, si se conoce, y devuelve TCL_OK. Si el sistema de archivos no está registrado actualmente, se devuelve TCL_ERROR.

Tcl_FSData devolverá el clientData asociado con el sistema de archivos dado, si ese sistema de archivos está registrado. De lo contrario, devolverá NULL.

Tcl_FSMountsChanged se utiliza para informar al núcleo de Tcl que el conjunto de puntos de montaje para el sistema de archivos dado (ya registrado) ha cambiado, y que las representaciones de archivos almacenadas en caché pueden, por lo tanto, ya no ser correctas.

Las muchas funciones en esta estructura se dividen en tres categorías: funciones de infraestructura (casi todas las cuales deben ser implementadas), funciones operativas (que deben ser implementadas si se proporciona un sistema de archivos completo) y funciones de eficiencia (que solo necesitan ser implementadas si se pueden hacer de manera eficiente, o si tienen efectos secundarios que son requeridos por el sistema de archivos; Tcl tiene emulaciones menos eficientes a las que puede recurrir). Es importante tener en cuenta que, en la versión actual de Tcl, la mayoría de estos recursos de respaldo solo se utilizan para manejar comandos iniciados en Tcl, no en C. Lo que esto significa es que, si se emite un comando file rename en Tcl, y los sistemas de archivos relevantes no implementan su Tcl_FSRenameFileProc, el núcleo de Tcl recurrirá a una combinación de otras funciones del sistema de archivos (utilizará Tcl_FSCopyFileProc seguido de Tcl_FSDeleteFileProc, y si Tcl_FSCopyFileProc no está implementado, hay un recurso de respaldo adicional). Sin embargo, si se emite un comando Tcl_FSRenameFileProc a nivel de C, no ocurren tales recursos de respaldo. Esto es cierto excepto para las últimas cuatro entradas en la tabla del sistema de archivos (lstat, load, getcwd y chdir) para las cuales sí ocurren recursos de respaldo a nivel de C.

Cualquier función que tome nombres de ruta en forma Tcl_Obj toma esos nombres en forma UTF-8. La API de infraestructura del sistema de archivos está diseñada para admitir la conversión eficiente y en caché de estas rutas UTF-8 a otras representaciones nativas.

The pathInFilesystemProc field contains the address
    of a function which is called to determine whether a given path value belongs

    cached inside the path value, and may be retrieved efficiently by the other

Function to normalize a path. Should be implemented for all
    filesystems which can have multiple string representations for the same path
    value. In Tcl, every “path” must have a single unique
    “normalized” string representation. Depending on the
    filesystem, there may be more than one unnormalized string representation
    which refers to that path (e.g. a relative path, a path with different
    character case if the filesystem is case insensitive, a path containing a
    reference to a home directory such as “~”, a path containing
    symbolic links, etc). If the very last component in the path is a symbolic
    link, it should not be converted into the value it points to (but its case or
    other aspects should be made unique). All other path components should be
    converted from symbolic links. This one exception is required to agree with
    Tcl's semantics with file delete, file rename, file
    copy operating on symbolic links. This function may be called with
    nextCheckpoint either at the beginning of the path (i.e. zero), at the
    end of the path, or at any intermediate file separator in the path. It will
    never point to any other arbitrary position in the path. In the last of the
    three valid cases, the implementation can assume that the path up to and
    including the file separator is known and normalized.

        int nextCheckpoint);

    filesystem. However, in some instances this may be desirable (for example, a
    read-only filesystem should not implement the last four functions, and a
    filesystem which does not support symbolic links need not implement the
    readlink function, etc. The Tcl core expects filesystems to behave in
    this way).

typedef Tcl_Obj *Tcl_FSFilesystemPathTypeProc(

typedef Tcl_Obj *Tcl_FSFilesystemSeparatorProc(

STATPROC


Function to process a Tcl_FSStat call. Must be implemented
    for any reasonable filesystem, since many Tcl level commands depend crucially
    upon it (e.g. file atime, file isdirectory, file size,
    glob).




typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);




The Tcl_FSStatProc fills the stat structure statPtr
    with information about the specified file. You do not need any access rights
    to the file to get this information but you need search rights to all
    directories named in the path leading to the file. The stat structure
    includes info regarding device, inode (always 0 on Windows), privilege mode,
    nlink (always 1 on Windows), user id (always 0 on Windows), group id (always
    0 on Windows), rdev (same as device on Windows), size, last access time,
    last modification time, and last metadata change time.


If the file represented by pathPtr exists, the
    Tcl_FSStatProc returns 0 and the stat structure is filled with data.
    Otherwise, -1 is returned, and no stat info is given.






ACCESSPROC


Function to process a Tcl_FSAccess call. Must be implemented
    for any reasonable filesystem, since many Tcl level commands depend crucially
    upon it (e.g. file exists, file readable).




typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);




The Tcl_FSAccessProc checks whether the process would be
    allowed to read, write or test for existence of the file (or other
    filesystem object) whose name is in pathPtr. If the pathname refers
    to a symbolic link, then the permissions of the file referred by this
    symbolic link should be tested.


On success (all requested permissions granted), zero is returned.
    On error (at least one bit in mode asked for a permission that is denied, or
    some other error occurred), -1 is returned.

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(

The function should return a valid Tcl_Channel handle on success,

OPENFILECHANNELPROC


Función para procesar una llamada a Tcl_FSOpenFileChannel. Debe implementarse para cualquier sistema de archivos razonable, ya que cualquier operación que requiera abrir o acceder al contenido de un archivo la utilizará (por ejemplo, open, encoding y muchos comandos de Tk).




typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);




El Tcl_FSOpenFileChannelProc abre un archivo especificado por pathPtr y devuelve un manejador de canal que se puede usar para realizar entradas y salidas en el archivo. Esta API está modelada según el procedimiento fopen de la biblioteca estándar de E/S de Unix. La sintaxis y el significado de todos los argumentos son similares a los dados en el comando open de Tcl al abrir un archivo, donde el argumento mode es una combinación de las banderas POSIX O_RDONLY, O_WRONLY, etc. Si ocurre un error al abrir el canal, Tcl_FSOpenFileChannelProc devuelve NULL y registra un código de error POSIX que se puede recuperar con Tcl_GetErrno. Además, si interp no es NULL, Tcl_FSOpenFileChannelProc deja un mensaje de error en el resultado de interp después de cualquier error.


El canal recién creado no debe registrarse en el intérprete proporcionado por un Tcl_FSOpenFileChannelProc; esa tarea corresponde al llamador de Tcl_FSOpenFileChannel (si es necesario). Si uno de los canales estándar, stdin, stdout o stderr se cerró previamente, el acto de crear el nuevo canal también lo asigna como reemplazo del canal estándar.

MATCHINDIRECTORYPROC

Función para procesar una llamada a Tcl_FSMatchInDirectory. Si no se implementa, la funcionalidad de glob y copia recursiva faltará en el sistema de archivos (y esto puede afectar a comandos como encoding names que utilizan la funcionalidad de glob internamente).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

La función debe devolver todos los archivos o directorios (u otros objetos del sistema de archivos) que coincidan con el patrón dado y que concuerden con la especificación de types. Hay dos formas en que se puede llamar a esta función. Si pattern es NULL, entonces pathPtr es una especificación de ruta completa de un solo archivo o directorio que debe verificarse en cuanto a existencia y tipo correcto. De lo contrario, pathPtr es un directorio, cuyo contenido la función debe buscar archivos o directorios que tengan el tipo correcto. En cualquier caso, se puede asumir que pathPtr no es NULL ni está vacío. Actualmente no está documentado si pathPtr tendrá un separador de archivo al final o no, por lo que el código debe ser flexible a ambas posibilidades.

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso de coincidencia. Los mensajes de error se colocan en interp, a menos que interp sea NULL, en cuyo caso no es necesario generar ningún mensaje de error; en un resultado TCL_OK, los resultados deben agregarse al valor resultPtr proporcionado (que se puede asumir que es una lista válida no compartida de Tcl). Las coincidencias agregadas a resultPtr deben incluir cualquier prefijo de ruta dado en pathPtr (esto generalmente significa que serán especificaciones de ruta absoluta). Tenga en cuenta que si no se encuentran coincidencias, eso simplemente conduce a un resultado vacío; los errores solo se señalan para problemas reales de archivo o sistema de archivos que pueden ocurrir durante el proceso de coincidencia.

La estructura Tcl_GlobTypeData pasada en el parámetro types contiene los siguientes campos:

typedef struct Tcl_GlobTypeData {
    /* Corresponde a bcdpfls como en 'find -t' */
    int type;
    /* Corresponde a permisos de archivo */
    int perm;
    /* Tipo de Mac aceptable */
    Tcl_Obj *macType;
    /* Creador de Mac aceptable */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

Hay dos casos específicos que es importante manejar correctamente, ambos cuando types no es NULL. Los dos casos son cuando types->types & TCL_GLOB_TYPE_DIR o types->types & TCL_GLOB_TYPE_MOUNT son verdaderos (y en particular cuando las otras banderas son falsas). En el primer caso, la función debe listar los directorios contenidos. Tcl utiliza esto para implementar el globbing recursivo, por lo que es fundamental que los sistemas de archivos implementen la coincidencia de directorios correctamente. En el segundo caso, con TCL_GLOB_TYPE_MOUNT, el sistema de archivos debe listar los puntos de montaje que se encuentran dentro del pathPtr dado (y en este caso, pathPtr no tiene por qué estar dentro del mismo sistema de archivos, a diferencia de todos los demás casos en los que se llama a esta función). El soporte para esto es fundamental si Tcl quiere tener transiciones fluidas entre un sistema de archivos y otro.

UTIMEPROC

Función para procesar una llamada a Tcl_FSUtime. Requerida para permitir el establecimiento (no la lectura) de tiempos con file mtime, file atime y la implementación open-r/open-w/fcopy de file copy.

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

Los tiempos de acceso y modificación del archivo especificado por pathPtr deben cambiarse a los valores dados en la estructura tval.

El valor de retorno debe ser 0 en caso de éxito y -1 en caso de error, al igual que con la llamada al sistema utime.

LINKPROC

Función para procesar una llamada a Tcl_FSLink. Solo debe implementarse si el sistema de archivos admite enlaces, y de lo contrario puede ser NULL.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

Si toPtr es NULL, se le está pidiendo a la función que lea el contenido de un enlace. El resultado es un Tcl_Obj que especifica el contenido del enlace dado por linkNamePtr, o NULL si el enlace no se pudo leer. El llamador es el propietario del resultado (y, por lo tanto, se debe incrementar su recuento de referencias antes de devolverlo). Cualquier llamador debe llamar a Tcl_DecrRefCount en este resultado cuando ya no sea necesario. Si toPtr no es NULL, la función debe intentar crear un enlace. El resultado en este caso debe ser toPtr si el enlace tuvo éxito y NULL en caso contrario. En este caso, el resultado no es propiedad del llamador (es decir, no se necesitan manipulaciones de recuento de referencias en ningún extremo). Consulte la documentación de Tcl_FSLink para la interpretación correcta de las banderas linkAction.

LISTVOLUMESPROC

Función para listar cualquier volumen del sistema de archivos agregado por este sistema de archivos. Solo debe implementarse si el sistema de archivos agrega volúmenes al principio del sistema de archivos, para que puedan ser devueltos por file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

El resultado debe ser una lista de volúmenes agregados por este sistema de archivos, o NULL (o una lista vacía) si no se proporcionan volúmenes. Se considera que el valor de resultado es propiedad del sistema de archivos (no del núcleo de Tcl), pero se le debe dar un recuento de referencias para Tcl. Tcl utilizará el contenido de la lista y luego disminuirá ese recuento de referencias. Esto permite a los sistemas de archivos elegir si realmente quieren conservar una lista "global" de volúmenes o no (si no, generan la lista sobre la marcha y se la pasan a Tcl con un recuento de referencias de 1 y luego olvidan la lista; si sí, simplemente incrementan el recuento de referencias de su lista global y se la pasan a Tcl, que copiará el contenido y luego disminuirá el recuento de nuevo a donde estaba).

Por lo tanto, Tcl considera que los valores de retorno de este proc son de solo lectura.

FILEATTRSTRINGSPROC

Función para listar todas las cadenas de atributos que son válidas para este sistema de archivos. Si no se implementa, el sistema de archivos no admitirá el comando file attributes. Esto permite adjuntar información adicional arbitraria a los archivos en el sistema de archivos. Si no se implementa, no es necesario implementar los métodos get y set.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

La función llamada puede devolver una matriz de cadenas o puede devolver NULL y colocar una lista de Tcl en objPtrRef. Tcl tomará esa lista y primero incrementará su recuento de referencias antes de usarla. Al finalizar ese uso, Tcl disminuirá su recuento de referencias. Por lo tanto, si Tcl debe desechar la lista cuando termine, debe tener un recuento de referencias de cero, y si la lista no debe desecharse, el sistema de archivos debe asegurarse de devolver un valor con un recuento de referencias de al menos uno.

FILEATTRSGETPROC

Función para procesar una llamada a Tcl_FSFileAttrsGet, utilizada por file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

Devuelve un código de retorno estándar de Tcl. El valor del atributo recuperado, que corresponde al elemento index en la lista devuelta por Tcl_FSFileAttrStringsProc, es un Tcl_Obj colocado en objPtrRef (si se devolvió TCL_OK) y es probable que tenga un recuento de referencias de cero. De cualquier manera, debemos almacenarlo en algún lugar (por ejemplo, el resultado de Tcl) o incrementar/decrementar su recuento de referencias para garantizar que se libere correctamente.

FILEATTRSSETPROC

Función para procesar una llamada a Tcl_FSFileAttrsSet, utilizada por file attributes. Si el sistema de archivos es de solo lectura, no es necesario implementarlo.

typedef int Tcl_FSFileAttrsSetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj *objPtr);

El valor del atributo del elemento index en la lista devuelta por Tcl_FSFileAttrStringsProc debe establecerse en el objPtr proporcionado.

CREATEDIRECTORYPROC

Función para procesar una llamada a Tcl_FSCreateDirectory. Debe ser implementada a menos que el sistema de archivos sea de solo lectura.

typedef int Tcl_FSCreateDirectoryProc(
        Tcl_Obj *pathPtr);

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso. Si tiene éxito, se debería haber añadido un nuevo directorio al sistema de archivos en la ubicación especificada por pathPtr.

REMOVEDIRECTORYPROC

Función para procesar una llamada a Tcl_FSRemoveDirectory. Debe ser implementada a menos que el sistema de archivos sea de solo lectura.

typedef int Tcl_FSRemoveDirectoryProc(
        Tcl_Obj *pathPtr,
        int recursive,
        Tcl_Obj **errorPtr);

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso. Si tiene éxito, el directorio especificado por pathPtr debería haber sido eliminado del sistema de archivos. Si se proporciona la bandera recursive, entonces un directorio no vacío debería ser eliminado sin error. Si esta bandera no se proporciona, y el directorio no está vacío, se debería señalar un error POSIX "EEXIST". DELETEFILEPROC

Función para procesar una llamada a Tcl_FSDeleteFile. Debe ser implementada a menos que el sistema de archivos sea de solo lectura.

typedef int Tcl_FSDeleteFileProc(
        Tcl_Obj *pathPtr);

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso. Si tiene éxito, el archivo especificado por pathPtr debería haber sido eliminado del sistema de archivos. Tenga en cuenta que, si el sistema de archivos soporta enlaces simbólicos, Tcl siempre llamará a esta función y no a Tcl_FSRemoveDirectoryProc cuando sea necesario eliminarlos (incluso si son enlaces simbólicos a directorios).

EFICIENCIA DEL SISTEMA DE ARCHIVOS

Estas funciones no necesitan ser implementadas para un sistema de archivos particular porque el núcleo tiene una implementación de respaldo disponible. Consulte cada descripción individual para conocer las consecuencias de dejar el campo NULL.

LSTATPROC

Función para procesar una llamada a Tcl_FSLstat. Si no se implementa, Tcl intentará usar statProc definido anteriormente en su lugar. Por lo tanto, solo necesita ser implementada si un sistema de archivos puede diferenciar entre las llamadas stat y lstat.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

El comportamiento de esta función es muy similar al de Tcl_FSStatProc definido anteriormente, excepto que si se aplica a un enlace simbólico, devuelve información sobre el enlace, no sobre el archivo de destino.

COPYFILEPROC

Función para procesar una llamada a Tcl_FSCopyFile. Si no se implementa, Tcl recurrirá a open-r, open-w y fcopy como mecanismo de copia. Por lo tanto, solo necesita ser implementada si el sistema de archivos puede realizar esa acción de manera más eficiente.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso de copia. Tenga en cuenta que destPathPtr es el nombre del archivo que se convertirá en la copia de srcPathPtr. Nunca es el nombre de un directorio en el que srcPathPtr podría copiarse (es decir, la función es mucho más simple que el subcomando file copy a nivel de Tcl). Tenga en cuenta que, si el sistema de archivos soporta enlaces simbólicos, Tcl siempre llamará a esta función y no a copyDirectoryProc cuando sea necesario copiarlos (incluso si son enlaces simbólicos a directorios). Finalmente, si el sistema de archivos determina que no puede soportar la acción file copy, llamar a Tcl_SetErrno(EXDEV) y devolver un resultado no TCL_OK le dirá a Tcl que use sus mecanismos de respaldo estándar.

RENAMEFILEPROC

Función para procesar una llamada a Tcl_FSRenameFile. Si no se implementa, Tcl recurrirá a un mecanismo de copia y eliminación. Por lo tanto, solo necesita ser implementada si el sistema de archivos puede realizar esa acción de manera más eficiente.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso de renombrado. Si el sistema de archivos determina que no puede soportar la acción file rename, llamar a Tcl_SetErrno(EXDEV) y devolver un resultado no TCL_OK le dirá a Tcl que use sus mecanismos de respaldo estándar.

COPYDIRECTORYPROC

Función para procesar una llamada a Tcl_FSCopyDirectory. Si no se implementa, Tcl recurrirá a un mecanismo recursivo de file mkdir, file copy. Por lo tanto, solo necesita ser implementada si el sistema de archivos puede realizar esa acción de manera más eficiente.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

El valor de retorno es un resultado estándar de Tcl que indica si ocurrió un error en el proceso de copia. Si ocurre un error, el nombre del archivo o directorio que causó el error debería colocarse en errorPtr. Tenga en cuenta que destPathPtr es el nombre del directorio que se convertirá en la imagen especular de srcPathPtr. No es el nombre de un directorio en el que srcPathPtr debería copiarse (es decir, la función es mucho más simple que el subcomando file copy a nivel de Tcl). Finalmente, si el sistema de archivos determina que no puede soportar la acción de copia de directorio, llamar a Tcl_SetErrno(EXDEV) y devolver un resultado no TCL_OK le dirá a Tcl que use sus mecanismos de respaldo estándar.

LOADFILEPROC

Función para procesar una llamada a Tcl_FSLoadFile. Si no se implementa, Tcl recurrirá a una copia a un archivo temporal nativo seguido de un Tcl_FSLoadFile en esa copia temporal. Por lo tanto, solo necesita ser implementada si el sistema de archivos puede cargar código directamente, o si se puede implementar simplemente para devolver TCL_ERROR para deshabilitar la funcionalidad de carga en este sistema de archivos por completo.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Devuelve un código de finalización estándar de Tcl. Si ocurre un error, se deja un mensaje de error en el resultado del interp. La función carga dinámicamente un archivo de código binario en memoria. En una carga exitosa, handlePtr se llenará con un token para el archivo cargado dinámicamente, y unloadProcPtr se llenará con la dirección de un procedimiento. El procedimiento de descarga se llamará con el Tcl_LoadHandle dado como su único parámetro cuando Tcl necesite descargar el archivo. Por ejemplo, para el sistema de archivos nativo, el Tcl_LoadHandle devuelto es actualmente un token que se puede usar en el TclpFindSymbol privado para acceder a funciones en el nuevo código. Cada sistema de archivos es libre de definir Tcl_LoadHandle según lo requiera. Finalmente, si el sistema de archivos determina que no puede soportar la acción de carga de archivos, llamar a Tcl_SetErrno(EXDEV) y devolver un resultado no TCL_OK le dirá a Tcl que use sus mecanismos de respaldo estándar.

UNLOADFILEPROC

Función para descargar un archivo previamente cargado con éxito. Si se implementó la carga, entonces esta también debería implementarse, si hay alguna acción de limpieza requerida.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

Función para procesar una llamada a Tcl_FSGetCwd. La mayoría de los sistemas de archivos no necesitan implementar esto. Por lo general, solo se llamará una vez, si se llama getcwd antes de chdir. Puede ser NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

Si el sistema de archivos admite una noción nativa de directorio de trabajo actual (que quizás pueda cambiar independientemente de Tcl), esta función debería devolver ese cwd como resultado, o NULL si no se pudo determinar el directorio actual (por ejemplo, el usuario no tiene los permisos apropiados en el directorio actual). Si se devuelve NULL, se deja un mensaje de error en el resultado del interp.

CHDIRPROC

Función para procesar una llamada a Tcl_FSChdir. Si los sistemas de archivos no implementan esto, se emulará mediante una serie de comprobaciones de acceso a directorios. De lo contrario, los sistemas de archivos virtuales que lo implementan solo necesitan responder con un resultado positivo si pathPtr es un directorio válido y accesible en su sistema de archivos. No necesitan recordar el resultado, ya que este se recordará automáticamente para su uso por Tcl_FSGetCwd. Los sistemas de archivos reales deberían llevar a cabo la acción correcta (es decir, llamar a la API chdir del sistema correcta).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

El Tcl_FSChdirProc cambia el directorio de trabajo actual de la aplicación al valor especificado en pathPtr. La función devuelve -1 en caso de error o 0 en caso de éxito.
