ARGUMENTS

Tcl_EventSetupProc *setupProc (in)
Procedure to invoke to prepare for event wait in Tcl_DoOneEvent.
Tcl_EventCheckProc *checkProc (in)
Procedure for Tcl_DoOneEvent to invoke after waiting for events. Checks to see if any events have occurred and, if so, queues them.
ClientData clientData (in)
Arbitrary one-word value to pass to setupProc, checkProc, or deleteProc.
const Tcl_Time *timePtr (in)
Indicates the maximum amount of time to wait for an event. This is specified as an interval (how long to wait), not an absolute time (when to wakeup). If the pointer passed to Tcl_WaitForEvent is NULL, it means there is no maximum wait time: wait forever if necessary.
Tcl_Event *evPtr (in)
An event to add to the event queue. The storage for the event must have been allocated by the caller using Tcl_Alloc or ckalloc.
Tcl_QueuePosition position (in)
Where to add the new event in the queue: TCL_QUEUE_TAIL, TCL_QUEUE_HEAD, or TCL_QUEUE_MARK.
Tcl_ThreadId threadId (in)
A unique identifier for a thread.
Tcl_EventDeleteProc *deleteProc (in)
Procedure to invoke for each queued event in Tcl_DeleteEvents.
int flags (in)
What types of events to service. These flags are the same as those passed to Tcl_DoOneEvent.
int mode (in)
Indicates whether events should be serviced by Tcl_ServiceAll. Must be one of TCL_SERVICE_NONE or TCL_SERVICE_ALL.
Tcl_NotifierProcs* notifierProcPtr (in)
Structure of function pointers describing notifier procedures that are to replace the ones installed in the executable. See REPLACING THE NOTIFIER for details.

INTRODUCTION

The interfaces described here are used to customize the Tcl event loop. The two most common customizations are to add new sources of events and to merge Tcl's event loop with some other event loop, such as one provided by an application in which Tcl is embedded. Each of these tasks is described in a separate section below.

The procedures in this manual entry are the building blocks out of which the Tcl event notifier is constructed. The event notifier is the lowest layer in the Tcl event mechanism. It consists of three things:

[1]
Event sources: these represent the ways in which events can be generated. For example, there is a timer event source that implements the Tcl_CreateTimerHandler procedure and the after command, and there is a file event source that implements the Tcl_CreateFileHandler procedure on Unix systems. An event source must work with the notifier to detect events at the right times, record them on the event queue, and eventually notify higher-level software that they have occurred. The procedures Tcl_CreateEventSource, Tcl_DeleteEventSource, and Tcl_SetMaxBlockTime, Tcl_QueueEvent, and Tcl_DeleteEvents are used primarily by event sources.
[2]
The event queue: for non-threaded applications, there is a single queue for the whole application, containing events that have been detected but not yet serviced. Event sources place events onto the queue so that they may be processed in order at appropriate times during the event loop. The event queue guarantees a fair discipline of event handling, so that no event source can starve the others. It also allows events to be saved for servicing at a future time. Threaded applications work in a similar manner, except that there is a separate event queue for each thread containing a Tcl interpreter. Tcl_QueueEvent is used (primarily by event sources) to add events to the event queue and Tcl_DeleteEvents is used to remove events from the queue without processing them. In a threaded application, Tcl_QueueEvent adds an event to the current thread's queue, and Tcl_ThreadQueueEvent adds an event to a queue in a specific thread.
[3]
The event loop: in order to detect and process events, the application enters a loop that waits for events to occur, places them on the event queue, and then processes them. Most applications will do this by calling the procedure Tcl_DoOneEvent, which is described in a separate manual entry.

Most Tcl applications need not worry about any of the internals of the Tcl notifier. However, the notifier now has enough flexibility to be retargeted either for a new platform or to use an external event loop (such as the Motif event loop, when Tcl is embedded in a Motif application). The procedures Tcl_WaitForEvent and Tcl_SetTimer are normally implemented by Tcl, but may be replaced with new versions to retarget the notifier (the Tcl_InitNotifier, Tcl_AlertNotifier, Tcl_FinalizeNotifier, Tcl_Sleep, Tcl_CreateFileHandler, and Tcl_DeleteFileHandler must also be replaced; see CREATING A NEW NOTIFIER below for details). The procedures Tcl_ServiceAll, Tcl_ServiceEvent, Tcl_GetServiceMode, and Tcl_SetServiceMode are provided to help connect Tcl's event loop to an external event loop such as Motif's.

NOTIFIER BASICS

The easiest way to understand how the notifier works is to consider what happens when Tcl_DoOneEvent is called. Tcl_DoOneEvent is passed a flags argument that indicates what sort of events it is OK to process and also whether or not to block if no events are ready. Tcl_DoOneEvent does the following things:

[1]
Check the event queue to see if it contains any events that can be serviced. If so, service the first possible event, remove it from the queue, and return. It does this by calling Tcl_ServiceEvent and passing in the flags argument.
[2]
Prepare to block for an event. To do this, Tcl_DoOneEvent invokes a setup procedure in each event source. The event source will perform event-source specific initialization and possibly call Tcl_SetMaxBlockTime to limit how long Tcl_WaitForEvent will block if no new events occur.
[3]
Call Tcl_WaitForEvent. This procedure is implemented differently on different platforms; it waits for an event to occur, based on the information provided by the event sources. It may cause the application to block if timePtr specifies an interval other than 0. Tcl_WaitForEvent returns when something has happened, such as a file becoming readable or the interval given by timePtr expiring. If there are no events for Tcl_WaitForEvent to wait for, so that it would block forever, then it returns immediately and Tcl_DoOneEvent returns 0.
[4]
Call a check procedure in each event source. The check procedure determines whether any events of interest to this source occurred. If so, the events are added to the event queue.

FUNCIONAMIENTO DEL BUCLE DE EVENTOS

El corazón de Tcl's manejo de eventos es el procedimiento Tcl_DoOneEvent. Cada vez que Tcl necesita hacer alguna obra, llama a este procedimiento. Típicamente, esto ocurre cuando Tcl está inactivo y esperando eventos de entrada, pero también puede ser llamado por código Tcl o C explícitamente para procesar eventos pendientes.

Tcl_DoOneEvent opera en los siguientes pasos:

1
Si el argumento flags para Tcl_DoOneEvent tiene el bit TCL_IDLE_EVENTS deshabilitado, llama a los procedimientos de preparación para todas las fuentes de eventos y luego regresa. Esto permite que las aplicaciones que no necesitan un comportamiento especial cuando están inactivas lo hagan.
2
Comprueba si hay algún evento listo para ser procesado en la cola de eventos. Si lo hay, ve al paso [5].
3
Si no hay eventos listos, llama a los procedimientos de preparación para todas las fuentes de eventos. Cada procedimiento de preparación tiene la oportunidad de actualizar el tiempo de espera máximo por defecto, si lo desea. Si algún procedimiento de preparación llama a Tcl_SetMaxBlockTime, el tiempo de espera máximo se ajusta al tiempo más corto especificado por cualquiera de los procedimientos de preparación. Si ningún procedimiento de preparación cambia el tiempo de espera máximo, Tcl_WaitForEvent esperará indefinidamente hasta que ocurra un evento. Si el tiempo de espera máximo es cero, entonces Tcl_WaitForEvent no esperará en absoluto y regresará inmediatamente.
4
Llama a Tcl_WaitForEvent con el tiempo de espera máximo calculado en el paso [3]. Tcl_WaitForEvent esperará hasta que ocurra un evento o se supere el tiempo de espera máximo. Si ocurre un evento o el tiempo de espera expira, llama a los procedimientos de comprobación para todas las fuentes de eventos, dando a cada una la oportunidad de añadir eventos a la cola si están listos. Luego, regresa.
5
Comprueba la cola de eventos para ver si contiene algún evento que pueda ser atendido. Si es así, atiende el primer evento posible, lo elimina de la cola y regresa.
6
Comprueba si hay callbacks inactivos pendientes. Si los hay, invócalos a todos y regresa.
7
Regresa 0 para indicar que no había eventos listos, o vuelve al paso [2] si el bloqueo fue solicitado por el llamador.

CREANDO UNA NUEVA FUENTE DE EVENTOS

Una fuente de eventos consta de tres procedimientos invocados por el notificador, además de procedimientos C adicionales que son invocados por código de nivel superior para organizar callbacks dirigidos por eventos.

Los tres procedimientos llamados por el notificador consisten en los procedimientos de configuración y comprobación descritos anteriormente, más un procedimiento adicional que se invoca cuando un evento se elimina de la cola de eventos para su servicio.

El procedimiento Tcl_CreateEventSource crea una nueva fuente de eventos. Sus argumentos especifican el procedimiento de configuración y el procedimiento de comprobación para la fuente de eventos. SetupProc debe coincidir con el siguiente prototipo:

typedef void Tcl_EventSetupProc(
        ClientData clientData,
        int flags);

El argumento clientData será el mismo que el argumento clientData para Tcl_CreateEventSource; se utiliza típicamente para apuntar a información privada gestionada por la fuente de eventos. El argumento flags será el mismo que el argumento flags pasado a Tcl_DoOneEvent excepto que nunca será 0 (Tcl_DoOneEvent reemplaza 0 con TCL_ALL_EVENTS). Flags indica qué tipos de eventos deben considerarse; si el bit correspondiente a esta fuente de eventos no está establecido, la fuente de eventos debe regresar inmediatamente sin hacer nada. Por ejemplo, la fuente de eventos de archivo comprueba el bit TCL_FILE_EVENTS.

El trabajo de SetupProc es asegurarse de que la aplicación despierte cuando ocurran eventos del tipo deseado. Esto se hace típicamente de forma dependiente de la plataforma. Por ejemplo, en Unix, una fuente de eventos podría llamar a Tcl_CreateFileHandler; en Windows podría solicitar notificación con un evento de Windows. Para fuentes de eventos impulsadas por temporizadores, como eventos de temporizador o cualquier evento sondeado, la fuente de eventos puede llamar a Tcl_SetMaxBlockTime para forzar a la aplicación a despertar después de un tiempo especificado, incluso si no han ocurrido eventos. Si ninguna fuente de eventos llama a Tcl_SetMaxBlockTime, entonces Tcl_WaitForEvent esperará tanto como sea necesario para que ocurra un evento; de lo contrario, solo esperará tanto como el intervalo más corto pasado a Tcl_SetMaxBlockTime por una de las fuentes de eventos. Si una fuente de eventos sabe que ya tiene eventos listos para reportar, puede solicitar un tiempo de bloqueo máximo de cero. Por ejemplo, el procedimiento de configuración para la fuente de eventos X comprueba si ya hay eventos en cola. Si los hay, llama a Tcl_SetMaxBlockTime con un tiempo de bloqueo de 0 para que Tcl_WaitForEvent no se bloquee si no hay nuevos datos en la conexión X. El argumento timePtr para Tcl_WaitForEvent apunta a una estructura que describe un intervalo de tiempo en segundos y microsegundos:

typedef struct Tcl_Time {
    long sec;
    long usec;
} Tcl_Time;

El campo usec debe ser menor que 1000000.

La información proporcionada a Tcl_SetMaxBlockTime solo se utiliza para la próxima llamada a Tcl_WaitForEvent; se descarta después de que Tcl_WaitForEvent regrese. La próxima vez que se realice una espera de eventos, se llamará a los procedimientos de configuración de cada fuente de eventos, y podrán especificar nueva información para esa espera de eventos.

Si la aplicación utiliza un bucle de eventos externo en lugar de Tcl_DoOneEvent, las fuentes de eventos pueden necesitar llamar a Tcl_SetMaxBlockTime en otros momentos. Por ejemplo, si se registra un nuevo manejador de eventos que necesita sondear eventos, la fuente de eventos puede llamar a Tcl_SetMaxBlockTime para establecer el tiempo de bloqueo a cero para forzar al bucle de eventos externo a llamar a Tcl. En este caso, Tcl_SetMaxBlockTime invoca Tcl_SetTimer con el intervalo más corto visto desde la última llamada a Tcl_DoOneEvent o Tcl_ServiceAll.

Además del procedimiento genérico Tcl_SetMaxBlockTime, otros procedimientos específicos de plataforma también pueden estar disponibles para setupProc, si hay información adicional necesaria para Tcl_WaitForEvent en esa plataforma. Por ejemplo, en sistemas Unix, la interfaz Tcl_CreateFileHandler puede usarse para esperar eventos de archivo.

El segundo procedimiento proporcionado por cada fuente de eventos es su procedimiento de comprobación, indicado por el argumento checkProc a Tcl_CreateEventSource. CheckProc debe coincidir con el siguiente prototipo:

typedef void Tcl_EventCheckProc(
        ClientData clientData,
        int flags);

Los argumentos de este procedimiento son los mismos que los de setupProc. CheckProc es invocado por Tcl_DoOneEvent después de haber esperado eventos. Presumiblemente, al menos una fuente de eventos está ahora preparada para poner un evento en cola. Tcl_DoOneEvent llama a cada una de las fuentes de eventos por turno, por lo que todas tienen la oportunidad de poner en cola cualquier evento que esté listo. El procedimiento de comprobación hace dos cosas. Primero, debe comprobar si algún evento se ha activado. Las diferentes fuentes de eventos lo hacen de diferentes maneras.

Si el procedimiento de comprobación de una fuente de eventos detecta un evento interesante, debe añadir el evento a la cola de eventos de Tcl. Para hacerlo, la fuente de eventos llama a Tcl_QueueEvent. El argumento evPtr es un puntero a una estructura asignada dinámicamente que contiene el evento (ver más abajo para más información sobre problemas de gestión de memoria). Cada fuente de eventos puede definir su propia estructura de evento con la información que sea relevante para esa fuente de eventos. Sin embargo, el primer elemento de la estructura debe ser una estructura de tipo Tcl_Event, y la dirección de esta estructura se utiliza al comunicarse entre la fuente de eventos y el resto del notificador. Un Tcl_Event tiene la siguiente definición:

typedef struct {
    Tcl_EventProc *proc;
    struct Tcl_Event *nextPtr;
} Tcl_Event;

La fuente de eventos debe rellenar el campo proc del evento antes de llamar a Tcl_QueueEvent. El campo nextPtr se utiliza para enlazar los eventos en la cola y no debe ser modificado por la fuente de eventos.

Un evento puede añadirse a la cola en cualquiera de las tres posiciones, dependiendo del argumento position de Tcl_QueueEvent:

TCL_QUEUE_TAIL
Añade el evento al final de la cola, de modo que todos los demás eventos pendientes se atiendan primero. Este es casi siempre el lugar correcto para eventos nuevos.
TCL_QUEUE_HEAD
Añade el evento al principio de la cola, de modo que se atienda antes que todos los demás eventos en cola.
TCL_QUEUE_MARK
Añade el evento al principio de la cola, a menos que haya otros eventos al principio cuya posición sea TCL_QUEUE_MARK; en caso afirmativo, añade el nuevo evento justo después de todos los demás eventos TCL_QUEUE_MARK. Este valor de position se utiliza para insertar una secuencia ordenada de eventos al principio de la cola, como una serie de eventos Enter y Leave sintetizados durante una operación de grab o ungrab en Tk.

Cuando llega el momento de manejar un evento de la cola (pasos 1 y 4 anteriores), Tcl_ServiceEvent invocará el proc especificado en la primera estructura Tcl_Event en cola. Proc debe coincidir con el siguiente prototipo:

typedef int Tcl_EventProc(
        Tcl_Event *evPtr,
        int flags);

El primer argumento de proc es un puntero al evento, que será el mismo que el primer argumento de la llamada a Tcl_QueueEvent que añadió el evento a la cola. El segundo argumento de proc es el argumento flags para la llamada actual a Tcl_ServiceEvent; esto es usado por la fuente de eventos para regresar inmediatamente si sus eventos no son relevantes.

Corresponde a proc manejar el evento, típicamente invocando uno o más comandos Tcl o callbacks a nivel C. Una vez que la fuente de eventos ha terminado de manejar el evento, regresa 1 para indicar que el evento puede ser eliminado de la cola. Si por alguna razón la fuente de eventos decide que el evento no puede ser manejado en este momento, puede regresar 0 para indicar que el evento debe ser aplazado para procesamiento posterior; en este caso Tcl_ServiceEvent continuará con el siguiente evento en la cola e intentará atenderlo. Hay varias razones por las que una fuente de eventos podría aplazar un evento. Una posibilidad es que los eventos de este tipo estén excluidos por el argumento flags. Por ejemplo, la fuente de eventos de archivo siempre regresará 0 si el bit TCL_FILE_EVENTS no está establecido en flags. Otro ejemplo de aplazamiento de eventos ocurre en Tk si se ha invocado Tk_RestrictEvents para aplazar ciertos tipos de eventos de ventana.

Cuando proc regresa 1, Tcl_ServiceEvent eliminará el evento de la cola de eventos y liberará su almacenamiento. Tenga en cuenta que el almacenamiento para un evento debe ser asignado por la fuente de eventos (usando Tcl_Alloc o la macro Tcl ckalloc) antes de llamar a Tcl_QueueEvent, pero será liberado por Tcl_ServiceEvent, no por la fuente de eventos.

Las aplicaciones multihilo funcionan de manera similar, excepto que hay una cola de eventos separada para cada hilo que contiene un intérprete de Tcl. Llamar a Tcl_QueueEvent en una aplicación multihilo añade un evento a la cola del hilo actual. Para añadir un evento a la cola de otro hilo, use Tcl_ThreadQueueEvent. Tcl_ThreadQueueEvent acepta como argumento un argumento Tcl_ThreadId, que identifica de forma única un hilo en una aplicación Tcl. Para obtener el Tcl_ThreadId del hilo actual, use el procedimiento Tcl_GetCurrentThread. (Un hilo necesitaría entonces pasar este identificador a otros hilos para que estos puedan añadir eventos a su cola.) Después de añadir un evento a la cola de otro hilo, normalmente necesitará llamar a Tcl_ThreadAlert para "despertar" al notificador de ese hilo para alertarlo del nuevo evento.

Tcl_DeleteEvents se puede utilizar para eliminar explícitamente uno o más eventos de la cola de eventos. Tcl_DeleteEvents llama a proc para cada evento en la cola, eliminando aquellos para los que el procedimiento regresa 1. Los eventos para los que el procedimiento regresa 0 permanecen en la cola. Proc debe coincidir con el siguiente prototipo:

typedef int Tcl_EventDeleteProc(
        Tcl_Event *evPtr,
        ClientData clientData);
