Type::Tiny::Manual::UsingWithMoo - uso básico de Type::Tiny con Moo

MANUAL

Restricciones de tipo

Considera la siguiente clase Moo básica:

package Horse {
  use Moo;
  use namespace::autoclean;

  has name       => ( is => 'ro' );
  has gender     => ( is => 'ro' );
  has age        => ( is => 'rw' );
  has children   => ( is => 'ro', default => sub { [] } );
}

Código como este parece bastante simple:

my $br = Horse->new(name => "Bold Ruler", gender => 'm', age => 16);
push @{ $br->children },
  Horse->new(name => 'Secretariat', gender => 'm', age => 0);

Sin embargo, una vez que te alejas del uso muy simple de la clase, las cosas pueden empezar a salir mal. Cuando insertamos un nuevo caballo en "@{ $br->children }", asumimos que "$br->children" devolvió un arrayref.

¿Qué pasa si el código que creó el caballo $br lo instanció de esta manera?

my $br = Horse->new(name => "Bold Ruler", children => 'no');

Es por esta razón que es útil que la clase Horse realice algunas comprobaciones básicas de cordura en sus propios atributos.

package Horse {
  use Moo;
  use Types::Standard qw( Str Num ArrayRef );
  use namespace::autoclean;

  has name       => ( is => 'ro', isa => Str );
  has gender     => ( is => 'ro', isa => Str );
  has age        => ( is => 'rw', isa => Num );
  has children   => (
    is      => 'ro',
    isa     => ArrayRef,
    default => sub { return  [] },
  );
}

Ahora, si instanciaras un caballo de esta manera, lanzará un error:

my $br = Horse->new(name => "Bold Ruler", children => 'no');

La primera restricción de tipo que usamos aquí fue Str. Esta es una restricción de tipo que requiere que los valores sean cadenas de texto.

Ten en cuenta que aunque "undef" no es una cadena de texto, la cadena de texto vacía sigue siendo una cadena de texto y a menudo querrás comprobar que una cadena de texto no esté vacía. Podríamos haber hecho esto:

use Types::Common::String qw( NonEmptyStr );
has name => ( is => 'ro', isa => NonEmptyStr );

Mientras que la mayoría de las restricciones de tipo que usaremos en este manual se definen en Types::Standard, la biblioteca de tipos Types::Common::String también define muchas restricciones de tipo útiles.

Hemos requerido que la edad del caballo sea un número. Esta es también una restricción de tipo común y útil. Si queremos asegurarnos de que sea un número entero, podríamos usar:

use Types::Standard qw( Int );
has age => ( is => 'rw', isa => Int );

O, dado que los números negativos tienen poco sentido como edad:

use Types::Common::Numeric qw( PositiveOrZeroInt );
has age => ( is => 'rw', isa => PositiveOrZeroInt );

La biblioteca Types::Common::Numeric define muchos subtipos útiles de Int y Num, como PositiveInt y PositiveOrZeroInt.

La última restricción de tipo que hemos usado en este ejemplo es ArrayRef. Esto requiere que el valor sea una referencia a un array.

Types::Standard también proporciona las restricciones de tipo HashRef y CodeRef. Un ejemplo de uso de esta última:

package Task {
  use Moo;
  use Types::Standard qw( CodeRef Bool );
  has on_success => ( is => 'ro', isa => CodeRef );
  has on_failure => ( is => 'ro', isa => CodeRef );
  has finished   => ( is => 'ro', isa => Bool, default => 0 );
  ...;
}

my $task = Task->new(
  on_success => sub { ... },
  on_failure => sub { ... },
  ...,
);

La restricción de tipo Bool acepta "1" como valor verdadero y "0", "" o undef como valores falsos. No se aceptan otros valores.

Existe una restricción de tipo Object que acepta cualquier objeto bendecido.

package Horse {
  use Moo;
  use Types::Standard qw( Object );
  use namespace::autoclean;

  ...;  # name, gender, age, children
  has father => ( is => 'ro', isa => Object );
  has mother => ( is => 'ro', isa => Object );
}

Finalmente, otra restricción de tipo útil a tener en cuenta es Any:

use Types::Standard qw( Any );
has stuff => ( is => 'rw', isa => Any );

Esta restricción de tipo permite cualquier valor; es esencialmente lo mismo que no hacer ninguna comprobación de tipo, pero aclara tu intención. Siempre que sea posible, Type::Tiny optimizará esta comprobación de tipo, por lo que debería tener poco (si es que alguno) impacto en el rendimiento.

Tipos paramétricos

Imaginemos que queremos llevar la cuenta de las victorias de carreras de nuestro caballo:

package Horse {
  use Moo;
  use Types::Standard qw( Str Num ArrayRef );
  use namespace::autoclean;

  ...;  # name, gender, age, children
  has wins => (
    is      => 'ro',
    isa     => ArrayRef,
    default => sub { return [] },
  );
}

Podemos crear un caballo así:

my $br = Horse->new(
  name    => "Bold Ruler",
  gender  => 'm',
  age     => 4,
  wins    => ["Futurity Stakes 1956", "Juvenile Stakes 1956"],
);

La lista de victorias es un arrayref de cadenas. La restricción de tipo ArrayRef evita que se establezca como un hashref, por ejemplo, pero no asegura que todo en el arrayref sea una cadena. Para hacer eso, necesitamos parametrizar la restricción de tipo:

has wins => (
  is      => 'ro',
  isa     => ArrayRef[Str],
  default => sub { return [] },
);

Gracias al tipo paramétrico ArrayRef[Str], el constructor lanzará un error si el arrayref que le pasas contiene algo que no sea una cadena.

Una forma alternativa de escribir esto es:

has wins => (
  is      => 'ro',
  isa     => ArrayRef->of(Str),
  default => sub { return [] },
);

Qué forma elijas es en gran medida una preferencia de estilo. ¡TIMTOWTDI! (Hay más de una manera de hacerlo).

Ten en cuenta que aunque el constructor y cualquier método setter/accessor realizarán comprobaciones de tipo, es posible eludirlas usando:

push @{ $br->wins }, $not_a_string;

Aquí no se llama al constructor, y aunque sí se llama al accessor, se llama como lector, no como escritor, por lo que nunca tiene la oportunidad de inspeccionar el valor que se está añadiendo. (Es posible usar "tie" para resolver esto, pero eso se cubrirá más adelante).

Y, por supuesto, si manipulas directamente el hashref subyacente del objeto, todas las apuestas están perdidas:

$br->{wins} = $not_an_arrayref;

Así que las restricciones de tipo tienen limitaciones. Un diseño de API cuidadoso (y no eludir la API adecuada) puede ayudar.

La restricción de tipo HashRef también se puede parametrizar:

package Design {
  use Moo;
  use Types::Standard qw( HashRef Str );
  has colours => ( is => 'ro', isa => HashRef[Str] );
}

my $eiffel65 = Design->new(
  colours => { house => "blue", little_window => "blue" },
);

La restricción de tipo HashRef[Str] asegura que los *valores* del hashref sean cadenas; no comprueba las claves del hashref porque las claves en los hashes de Perl ¡siempre son cadenas!

Si necesitas restringir las claves, es posible usar una restricción paramétrica Map:

use Types::Common::String qw( NonEmptyStr );
use Types::Standard qw( Map );
has colours => ( is => 'ro', isa => Map[NonEmptyStr, NonEmptyStr] );

Map toma dos parámetros; el primero es un tipo para comprobar las claves y el segundo es un tipo para comprobar los valores.

Otra restricción de tipo útil es la restricción de tipo Tuple.

use Types::Standard qw( ArrayRef Tuple );
use Types::Common::Numeric qw( PositiveInt );
use Types::Common::String qw( NonEmptyStr );

has wins => (
  is      => 'ro',
  isa     => ArrayRef[ Tuple[PositiveInt, NonEmptyStr] ],
  default => sub { return [] },
);

La restricción de tipo Tuple[PositiveInt, NonEmptyStr] comprueba que un valor sea un arrayref de dos elementos donde el primer elemento sea un entero positivo y el segundo elemento sea una cadena no vacía. Por ejemplo:

my $br = Horse->new(
  name    => "Bold Ruler",
  wins    => [
    [ 1956, "Futurity Stakes" ],
    [ 1956, "Juvenile Stakes" ],
  ],
);

Como puedes ver, las restricciones de tipo paramétricas pueden anidarse hasta cualquier profundidad, aunque por supuesto, cuanto más detalladas sean tus comprobaciones, más lentas serán.

Type Constraints

Type constraints are used to specify what kind of value an attribute can hold. They are defined using the isa parameter when defining an attribute.

package Horse {
  use Moo;
  use Types::Standard qw( Str Num );
  use namespace::autoclean;

  has name => ( is => 'ro', isa => Str );
  has age  => ( is => 'rw', isa => Num );
}

This defines two attributes:

  • name: Must be a string. This is a read-only attribute.

  • age: Must be a number (integer or float). This is a read-write attribute.

If you try to assign a value of the wrong type, you'll get an error:

my $h = Horse->new( name => "Secretariat", age => 3 );
$h->age( "3 years old" ); # dies with error

There are many predefined types in modules like "Types::Standard", "Types::Common::Numeric", and "Types::Common::String".

Some types are parameterizable, meaning you can pass arguments to them to further refine the constraint. For example, "ArrayRef" can be parameterized to specify what kind of elements the arrayref should contain:

use Types::Standard qw( ArrayRef Num );
has prices => (
  is => 'ro',
  isa => ArrayRef[ Num ],
  default => sub { [] },
);

This means that the prices attribute must be an arrayref, and *every* element within that arrayref must be a number. Attempting to assign [1, 2, "three"] would fail.

Tuple is another parameterizable type that allows you to specify the types of elements in a fixed-size array:

use Types::Standard qw( Tuple );
use Types::Common::Numeric qw( PositiveInt );
use Types::Common::String qw( NonEmptyStr );

has wins => (
  is      => 'ro',
  isa     => ArrayRef[
    Tuple[ PositiveInt, NonEmptyStr ]
  ],
  default => sub { [] },
);

This defines wins as an arrayref of tuples. Each tuple must contain exactly two elements: a positive integer followed by a non-empty string. This is useful for representing data like (year, race name).

We can make elements optional:

use Types::Standard qw( ArrayRef Tuple Optional );
use Types::Common::Numeric qw( PositiveInt );
use Types::Common::String qw( NonEmptyStr );

has wins => (
  is      => 'ro',
  isa     => ArrayRef[
    Tuple[ PositiveInt, NonEmptyStr, Optional[NonEmptyStr] ]
  ],
  default => sub { [] },
);

The third element will be checked if it is present, but forgiven if it is absent.

Or we could just allow tuples to contain an arbitrary list of strings after the year and race name:

use Types::Standard qw( ArrayRef Tuple Str Slurpy );
use Types::Common::Numeric qw( PositiveInt );
use Types::Common::String qw( NonEmptyStr );

has wins => (
  is      => 'ro',
  isa     => ArrayRef[
    Tuple[ PositiveInt, NonEmptyStr, Slurpy[ ArrayRef[Str] ] ]
  ],
  default => sub { [] },
);

The Slurpy[ ArrayRef[Str] ] type will "slurp" all the remaining items in the tuple into an arrayref and check it against ArrayRef[Str].

It's even possible to do this:

use Types::Standard qw( ArrayRef Tuple Any Slurpy );
use Types::Common::Numeric qw( PositiveInt );
use Types::Common::String qw( NonEmptyStr );

has wins => (
  is      => 'ro',
  isa     => ArrayRef[
    Tuple[ PositiveInt, NonEmptyStr, Slurpy[Any] ]
  ],
  default => sub { [] },
);

With this type constraint, any elements after the first two will be slurped into an arrayref and we don't check that arrayref at all. (In fact, the implementation of the Tuple type is smart enough to not bother creating the temporary arrayref to check.)

Dict is the equivalent of Tuple for checking values of hashrefs.

use Types::Standard qw( ArrayRef Dict Optional );
use Types::Common::Numeric qw( PositiveInt );
use Types::Common::String qw( NonEmptyStr );

has wins => (
  is      => 'ro',
  isa     => ArrayRef[
    Dict[
      year    => PositiveInt,
      race    => NonEmptyStr,
      jockey  => Optional[NonEmptyStr],
    ],
  ],
  default => sub { [] },
);

An example of using it:

my $br = Horse->new(
  name    => "Bold Ruler",
  wins    => [
    { year => 1956, race => "Futurity Stakes", jockey => "Eddie" },
    { year => 1956, race => "Juvenile Stakes" },
  ],
);

The Slurpy type does work for Dict too:

Dict[
  year    => PositiveInt,
  race    => NonEmptyStr,
  jockey  => Optional[NonEmptyStr],
  ()      => Slurpy[ HashRef[Str] ],  # other Str values allowed
]

And "Slurpy[Any]" means what you probably think it means:

Dict[
  year    => PositiveInt,
  race    => NonEmptyStr,
  jockey  => Optional[NonEmptyStr],
  ()      => Slurpy[Any], # allow hashref to contain absolutely anything else
]

Going back to our first example, there's an opportunity to refine our ArrayRef constraint:

package Horse {
  use Moo;
  use Types::Standard qw( Str Num ArrayRef );
  use namespace::autoclean;

  has name       => ( is => 'ro', isa => Str );
  has gender     => ( is => 'ro', isa => Str );
  has age        => ( is => 'rw', isa => Num );
  has children   => (
    is      => 'ro',
    isa     => ArrayRef[ InstanceOf["Horse"] ],
    default => sub { return [] },
  );
}

The InstanceOf["Horse"] type constraint checks that a value is a blessed object in the Horse class. So the horse's children should be an arrayref of other Horse objects.

Internally it just checks "$_->isa("Horse")" on each item in the arrayref.

It is sometimes useful to instead check "$_->DOES($role)" or "$_->can($method)" on an object. For example:

package MyAPI::Client {
  use Moo;
  use Types::Standard qw( HasMethods );

  has ua => (is => 'ro', isa => HasMethods["get", "post"] );
}

The ConsumerOf and HasMethods parameterizable types allow you to easily check roles and methods of objects.

The Enum parameterizable type allows you to accept a more limited set of string values. For example:

use Types::Standard qw( Enum );
has gender => ( is => 'ro', isa => Enum["m","f"] );

Or if you want a little more flexibility, you can use StrMatch which allows you to test strings against a regular expression:

use Types::Standard qw( StrMatch );
has gender => ( is => 'ro', isa => StrMatch[qr/^[MF]/i] );

Or StrLength to check the maximum and minimum length of a string:

use Types::Common::String qw( StrLength );
has name => ( is => 'ro', isa => StrLength[3, 100] );

The maximum can be omitted.

Similarly, the maximum and minimum values for a numeric type can be expressed using IntRange and NumRange:

use Types::Common::Numeric qw( IntRange );
# values over 200 are probably an input error
has age => ( is => 'ro', isa => IntRange[0, 200] );

Parameterized type constraints are one of the most powerful features of Type::Tiny, allowing a small set of constraints to be combined in useful ways.

Type Coercions

It is often good practice to be liberal in what you accept.

package Horse {
  use Moo;
  use Types::Standard qw( Str Num ArrayRef Bool );
  use namespace::autoclean;

  ...;  # name, gender, age, children, wins
  has is_alive => ( is => 'rw', isa => Bool, coerce => 1 );
}

The "coerce" option indicates that if a value is given which *does not* pass the Bool type constraint, then it should be coerced (converted) into something that does.

The definition of Bool says that to convert a non-boolean to a bool, you just do "!! $non_bool". So all of the following will be living horses:

Horse->new(is_alive => 42)
Horse->new(is_alive => [])
Horse->new(is_alive => "false") # in Perl, string "false" is true!

Bool is the only type constraint in Types::Standard that has a coercion defined for it. The NumericCode, UpperCaseStr, LowerCaseStr, UpperCaseSimpleStr, and LowerCaseSimpleStr types from Types::Common::String also have conversions defined.

The other built-in constraints do not define any coercions because it would be hard to agree on what it means to coerce from, say, a HashRef to an ArrayRef. Do we keep the keys? The values? Both?

But it is pretty simple to add your own coercions!

use Types::Standard qw( ArrayRef HashRef Str );
has things => (
  is     => 'rw',
  isa    => ArrayRef->plus_coercions(
    HashRef,     sub { [ values %$_ ] },
    Str,         sub { [ split /;/, $_ ] },
  ),
  coerce => 1,
);

(Don't ever forget the "coerce => 1"!)

If a hashref is provided, the values will be used, and if a string is provided, it will be split on the semicolon. Of course, if an arrayref if provided, it already passes the type constraint, so no conversion is necessary.

The coercions should be pairs of "from types" and code to coerce the value. The code can be a coderef (as above) or just string of Perl code (as below). Strings of Perl code can usually be optimized better by Type::Tiny's internals, so are generally preferred. Thanks to Perl's "q{...}" operator, they can look just as clean and pretty as coderefs.

use Types::Standard qw( ArrayRef HashRef Str );
has things => (
  is     => 'rw',
  isa    => ArrayRef->plus_coercions(
    HashRef,     q{ [ values %$_ ] },
    Str,         q{ [ split /;/, $_ ] },
  ),
  coerce => 1,
);

Coercions are deeply applied automatically, so the following will do what you expect.

has inputs => (
  is     => 'ro',
  isa    => ArrayRef->of(Bool),
  coerce => 1
);

I am, of course, assuming you expect something like:

my $coerced = [ map { !!$_ } @$orig ];

If you were assuming that, congratulations! We are on the same wavelength.

And of course you can still add more coercions to the inherited ones...

has inputs => (
  is     => 'ro',
  isa    => ArrayRef->of(Bool)->plus_coercions(Str, sub {...}),
  coerce => 1
);

Type Defaults

A previous example included:

has children => (
  is      => 'ro',
  isa     => ArrayRef,
  default => sub { return [] },
);

It's actually pretty common that you'll want an arrayref attribute to default to being an empty arrayref, a numeric attribute to default to zero, etc. Type::Tiny provides a method for that:

has children => (
  is      => 'ro',
  isa     => ArrayRef,
  default => ArrayRef->type_default,
);

Many of the types in Types::Standard have sensible type defaults defined.

Method Parameters

So far we have just concentrated on the definition of object attributes, but type constraints are also useful to validate method parameters.

Let's remember our attribute for keeping track of a horse's race wins:

use Types::Standard qw( ArrayRef Tuple Optional );
use Types::Common::Numeric qw( PositiveInt );
use Types::Common::String qw( NonEmptyStr );

has wins => (
  is      => 'ro',
  isa     => ArrayRef[
    Tuple[ PositiveInt, NonEmptyStr, Optional[NonEmptyStr] ]
  ],
  default => sub { [] },
);

Because we don't trust outside code to push new entries onto this array, let's define a method in our class to do it.

package Horse {
  ...;

  sub add_win ( $self, $year, $race, $jockey ) {
    my $win = [
      $year,
      $race,
      $jockey ? $jockey : (),
    ];
    push $self->wins->@*, $win;
    return $self;
  }
}
