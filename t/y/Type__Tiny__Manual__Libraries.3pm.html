NOMBRE

Type::Tiny::Manual::Libraries - definir tus propias librerías de tipos

MANUAL

Definir un Tipo

Un tipo es un objeto y puedes crear uno nuevo usando el constructor:

use Type::Tiny;

my $type = Type::Tiny->new(%args);

Una lista completa de los argumentos disponibles se puede encontrar en la documentación de Type::Tiny, pero los más importantes para empezar son:

"name"
El nombre de tu nuevo tipo. Type::Tiny usa una convención de nombres UpperCamelCase para las restricciones de tipo. El nombre del tipo también puede comenzar con uno o dos guiones bajos iniciales para indicar un tipo destinado solo a uso interno. Los tipos que usan caracteres no ASCII pueden causar problemas en versiones antiguas de Perl (anteriores a la 5.8).

Aunque esto es opcional y los tipos pueden ser anónimos, se requiere un nombre para que una restricción de tipo se agregue a una librería de tipos.

"constraint"
Una referencia de código que verifica $_ y devuelve un booleano. Alternativamente, se puede proporcionar una cadena de código Perl.

Si has estado prestando atención, probablemente puedas adivinar que la cadena de código Perl puede resultar en comprobaciones de tipo más eficientes.

"parent"
Una restricción de tipo existente de la que heredar. Un valor deberá pasar la restricción padre antes de que se llame a su propia restricción. 
my $Even = Type::Tiny->new(
  name       => 'EvenNumber',
  parent     => Types::Standard::Int,
  constraint => sub {
    # en esta sub no necesitamos comprobar que $_ es un Int
    # ¡porque el padre se encargará de eso!

    $_ % 2 == 0
  },
);

Aunque el "parent" es opcional, tiene sentido siempre que sea posible heredar de una restricción de tipo existente para beneficiarse de cualquier optimización o implementación XS que puedan proporcionar.

Definir una Librería

Una librería es un módulo Perl que exporta restricciones de tipo como subs. Types::Standard, Types::Common::Numeric y Types::Common::String son librerías de tipos que vienen incluidas con Type::Tiny.

Para crear una librería de tipos, crea un paquete que herede de Type::Library.

package MyTypes {
  use Type::Library -base;

  ...; # tus definiciones de tipos van aquí
}

El flag "-base" es solo un atajo para:

package MyTypes {
  use Type::Library;
  our @ISA = 'Type::Library';
}

Puedes agregar tipos así:

package MyTypes {
  use Type::Library -base;

  my $Even = Type::Tiny->new(
    name       => 'EvenNumber',
    parent     => Types::Standard::Int,
    constraint => sub {
      # en esta sub no necesitamos comprobar que $_ es un Int
      # ¡porque el padre se encargará de eso!

      $_ % 2 == 0
    },
  );

  __PACKAGE__->add_type($Even);
}

Hay un atajo para agregar tipos si van a ser objetos bendecidos por Type::Tiny y no, por ejemplo, una subclase de Type::Tiny. Simplemente puedes pasar %args directamente a "add_type".

package MyTypes {
  use Type::Library -base;

  __PACKAGE__->add_type(
    name       => 'EvenNumber',
    parent     => Types::Standard::Int,
    constraint => sub {
      # en esta sub no necesitamos comprobar que $_ es un Int
      # ¡porque el padre se encargará de eso!

      $_ % 2 == 0
    },
  );
}

El método "add_type" devuelve el tipo que acaba de agregar, por lo que puede almacenarse en una variable.

my $Even = __PACKAGE__->add_type(...);

Esto puede ser útil si deseas usar $Even como tipo padre para algún otro tipo que vayas a definir más tarde.

Aquí hay un ejemplo más grande:

package Example::Types {
  use Type::Library -base;
  use Types::Standard -types;
  use DateTime;

  # Type::Tiny::Class es una subclase de Type::Tiny para crear
  # tipos similares a InstanceOf. Es un poco mejor porque
  # hace cosas geniales como pasar $type->new(%args)
  # al constructor de la clase.
  #
  my $dt = __PACKAGE__->add_type(
    Type::Tiny::Class->new(
      name    => 'Datetime',
      class   => 'DateTime',
    )
  );

  my $dth = __PACKAGE__->add_type(
    name    => 'DatetimeHash',
    parent  => Dict[
      year       => Int,
      month      => Optional[ Int ],
      day        => Optional[ Int ],
      hour       => Optional[ Int ],
      minute     => Optional[ Int ],
      second     => Optional[ Int ],
      nanosecond => Optional[ Int ],
      time_zone  => Optional[ Str ],
    ],
  );

  my $eph = __PACKAGE__->add_type(
    name    => 'EpochHash',
    parent  => Dict[ epoch => Int ],
  );

  # No podemos simplemente usar el método "plus_coercions" porque eso crea
  # un nuevo tipo hijo anónimo para agregarle las coerciones. Queremos
  # agregarlas al tipo que existe en esta librería.
  #
  $dt->coercion->add_type_coercions(
    Int,    q{ DateTime->from_epoch(epoch => $_) },
    Undef,  q{ DateTime->now() },
    $dth,   q{ DateTime->new(%$_) },
    $eph,   q{ DateTime->from_epoch(%$_) },
  );

  __PACKAGE__->make_immutable;
}

"make_immutable" congela las coerciones de todos los tipos del paquete, de modo que ningún código externo pueda manipular las coerciones, y permite a Type::Tiny realizar optimizaciones en las coerciones, sabiendo que no se alterarán más adelante. Siempre debes hacer esto al final.

La librería exportará los tipos Datetime, DatetimeHash y EpochHash. El tipo Datetime tendrá coerciones desde Int, Undef, DatetimeHash y EpochHash.

Extender Librerías

Type::Utils proporciona una función útil "extends".

package My::Types {
  use Type::Library -base;
  use Type::Utils qw( extends );

  BEGIN { extends("Types::Standard") };

  # define tus propios tipos aquí
}

La función "extends" (que normalmente deberías usar en un bloque "BEGIN { }", no solo carga otra librería de tipos, sino que también agrega todos los tipos de ella a tu librería.

Esto significa que el código que usa My::Types anterior no necesita hacer:

use Types::Standard qw( Str );
use My::Types qw( Something );

Solo puede hacer:

use My::Types qw( Str Something );

Porque todos los tipos de Types::Standard se han copiado a My::Types y también están disponibles allí.

"extends" puede recibir una lista de librerías; puedes heredar de múltiples librerías existentes. También puede reconocer e importar tipos de librerías MooseX::Types, MouseX::Types y Specio::Exporter.

Desde Type::Library 1.012, ha habido un atajo para "extends".

package My::Types {
  use Type::Library -extends => [ 'Types::Standard' ];

  # define tus propios tipos aquí
}

El flag "-extends" toma una referencia de array de librerías de tipos para extender. Implica automáticamente "-base", por lo que no necesitas usar ambos.

Mensajes de Error Personalizados

Una restricción de tipo puede tener mensajes de error personalizados. Es bastante simple:

Type::Tiny->new(
  name       => 'EvenNumber',
  parent     => Types::Standard::Int,
  constraint => sub {
    # en esta sub no necesitamos comprobar que $_ es un Int
    # ¡porque el padre se encargará de eso!

    $_ % 2 == 0
  },
  message   => sub {
    sprintf '%s no es un número par', Type::Tiny::_dd($_);
  },
);

La referencia de código del mensaje solo toma un valor en $_ y devuelve una cadena. Puede usar Type::Tiny::_dd() como una forma de imprimir bonitamente un valor. (No te desanimes por el guion bajo en el nombre de la función. _dd() es una parte oficialmente compatible de la API de Type::Tiny ahora).

NAME

Type::Tiny::Manual::Libraries - How to create your own Type::Tiny type libraries

MANUAL

This manual page is a tutorial on how to create your own type libraries.

For more information on how to use the existing type constraints, see Type::Tiny::Manual::Usage.

Base Types

Most of the time you'll be extending existing types. For example, if you want to define a type that's an integer which is greater than zero, you'd probably want to use Types::Standard::Int as a parent:

use Type::Library -base,
  -requires => qw( Int );

__PACKAGE__->add_type(
  name       => 'PositiveInt',
  parent     => Int,
  constraint => sub { $_ > 0 },
);

This is the most basic way to create a new type. You give it a name, a parent type (or types), and a constraint.

The constraint can be a coderef, or a string of Perl code.

__PACKAGE__->add_type(
  name       => 'PositiveInt',
  parent     => Int,
  constraint => '$_ > 0',
);

You can also give a type a description:

__PACKAGE__->add_type(
  name        => 'PositiveInt',
  parent      => Int,
  constraint  => '$_ > 0',
  description => 'An integer greater than zero',
);

For more complex relationships, you can specify multiple parents. If you do this, then the value must satisfy the constraints of all parent types.

__PACKAGE__->add_type(
  name       => 'PositiveOddInt',
  parent     => [Int, OddInt], # OddInt would need to be defined elsewhere
  constraint => '$_ > 0',
);

Note that the constraint parameter is used to specify constraints that are applied *in addition* to the parent's constraints. The example above actually defines a PositiveOddInt that is greater than 0. A more sensible definition would be:

__PACKAGE__->add_type(
  name       => 'PositiveOddInt',
  parent     => OddInt,
  constraint => '$_ > 0',
);

Or maybe this:

__PACKAGE__->add_type(
  name       => 'PositiveOddInt',
  parent     => Int,
  constraint => sub { $_ > 0 and $_ % 2 }
);

The use of constraint and parent is designed such that you can define a type in terms of existing types. This avoids duplication and means that you can take advantage of any optimisations that have been made to the parent types. For example, if Int has been optimised to use a coderef, then PositiveInt will automatically get the benefit of that.

However, this is not always as efficient as it could be. Perl's subroutine calls are relatively expensive. If you were to define PositiveInt as:

use Types::Standard qw( Int );
use Type::Tiny;

my $Int = Types::Standard::Int;
my $PositiveInt = Type::Tiny->new(
  name       => 'PositiveInt',
  parent     => $Int,
  constraint => sub { $_ > 0 },
);

Then to check if a value is a PositiveInt, Type::Tiny would have to:

  1. Call the coderef for PositiveInt.

  2. If that returned true, call the coderef for Int.

This is wasteful. Fortunately, Type::Tiny can often combine these checks for you. If you provide the constraint as a string:

use Types::Standard qw( Int );
use Type::Tiny;

my $Int = Types::Standard::Int;
my $PositiveInt = Type::Tiny->new(
  name       => 'PositiveInt',
  parent     => $Int,
  constraint => '$_ > 0',
);

Then Type::Tiny can transform this into a single coderef that does both checks.

To make things even simpler, you can get Type::Tiny to automatically generate the parent checks for you. If you provide a constraint parameter, Type::Tiny assumes that the value must also satisfy the parent's constraint. This means that you don't need to explicitly include the parent's constraint check in your own constraint.

In this case, the default sub should be reasonable.

Inlining

In Perl, sub calls are relatively expensive in terms of memory and CPU use. The PositiveInt type inherits from Int which inherits from Num which inherits from Str which inherits from Defined which inherits from Item which inherits from Any.

So you might think that to check of $value is a PositiveInt, it needs to be checked all the way up the inheritance chain. But this is where one of Type::Tiny's big optimizations happens. Type::Tiny can glue together a bunch of checks with a stringy eval, and get a single coderef that can do all the checks in one go.

This is why when Type::Tiny gives you a choice of using a coderef or a string of Perl code, you should usually choose the string of Perl code. A single coderef can "break the chain".

But these automatically generated strings of Perl code are not always as efficient as they could be. For example, imagine that HashRef is defined as:

my $Defined = Type::Tiny->new(
  name       => 'Defined',
  constraint => 'defined($_)',
);
my $Ref = Type::Tiny->new(
  name       => 'Ref',
  parent     => $Defined,
  constraint => 'ref($_)',
);
my $HashRef = Type::Tiny->new(
  name       => 'HashRef',
  parent     => $Ref,
  constraint => 'ref($_) eq "HASH"',
);

Then the combined check is:

defined($_) and ref($_) and ref($_) eq "HASH"

Actually in practice it's even more complicated, because Type::Tiny needs to localize and set $_ first.

But in practice, the following should be a sufficient check:

ref($_) eq "HASH"

It is possible for the HashRef type to have more control over the string of code generated.

my $HashRef = Type::Tiny->new(
  name       => 'HashRef',
  parent     => $Ref,
  constraint => 'ref($_) eq "HASH"',
  inlined    => sub {
    my $varname = pop;
    sprintf 'ref(%s) eq "HASH"', $varname;
  },
);

The inlined coderef gets passed the name of a variable to check. This could be '$_' or '$var' or "$some{deep}{thing}[0]". Because it is passed the name of a variable to check, instead of always checking $_, this enables very efficient checking for parameterized types.

Although in this case, the inlining coderef is just returning a string, technically it returns a list of strings. If there's multiple strings, Type::Tiny will join them together in a big "&&" statement.

As a special case, if the first item in the returned list of strings is undef, then Type::Tiny will substitute the parent type constraint's inlined string in its place. So an inlieing coderef for even numbers might be:

Type::Tiny->new(
  name       => 'EvenNumber',
  parent     => Types::Standard::Int,
  constraint => sub { $_ % 2 == 0 },
  inlined    => sub {
    my $varname = pop;
    return (undef, "$varname % 2 == 0");
  },
);

Even if you provide a coderef as a string, an inlining coderef has the potential to generate more efficient code, so you should consider providing one.

Pre-Declaring Types

use Type::Library -base,
  -declare => qw( Foo Bar Baz );

This declares types Foo, Bar, and Baz at compile time so they can safely be used as barewords in your type library.

This also allows recursively defined types to (mostly) work!

use Type::Library -base,
  -declare => qw( NumericArrayRef );
use Types::Standard qw( Num ArrayRef );

__PACKAGE__->add_type(
  name     => NumericArrayRef,
  parent   => ArrayRef->of( Num | NumericArrayRef ),
);

(Support for recursive type definitions added in Type::Library 1.009_000.)

Parameterizable Types

This is probably the most "meta" concept that is going to be covered. Building your own type constraint that can be parameterized like ArrayRef or HasMethods.

The type constraint we'll build will be MultipleOf[$i] which checks that an integer is a multiple of $i.

__PACKAGE__->add_type(
  name       => 'MultipleOf',
  parent     => Int,

  # This coderef gets passed the contents of the square brackets.
  constraint_generator => sub ( $i ) {
    assert_Int $i;
    # needs to return a coderef to use as a constraint for the
    # parameterized type
    return sub { $_ % $i == 0 };
  },

  # optional but recommended
  inline_generator => sub ( $i ) {
    return sub {
      my $varname = pop;
      return (undef, "$varname % $i == 0");
    };
  },

  # probably the most complex bit
  coercion_generator => sub ( $parent_type, $child_type, $i ) {
    require Type::Coercion;
    return Type::Coercion->new(
      type_coercion_map => [
        Num, qq{ int($i * int(\$_/$i)) }
      ],
    );
  },
);

Now we can define an even number like this:

__PACKAGE__->add_type(
  name     => 'EvenNumber',
  parent   => __PACKAGE__->get_type('MultipleOf')->of(2),
  coercion => 1,  # inherit from parent
);

Note that it is possible for a type constraint to have a "constraint" and a "constraint_generator".

BaseType          # uses the constraint
BaseType[]        # constraint_generator with no arguments
BaseType[$x]      # constraint_generator with an argument

In the MultipleOf example above, MultipleOf[] with no number would throw an error because of assert_Int(shift) not finding an integer.

But it is certainly possible for BaseType[] to be meaningful and distinct from "BaseType".

For example, Tuple is just the same as ArrayRef and accepts any arrayref as being valid. But Tuple[] will only accept arrayrefs with zero elements in them. (Just like Tuple[Any,Any] will only accept arrayrefs with two elements.)
