Type::Tiny::Manual::Params(3) Documentación de Contribución de Usuarios de Perl Type::Tiny::Manual::Params(3)

NOMBRE

Type::Tiny::Manual::Params - información avanzada sobre Type::Params

MANUAL

Para empezar con Type::Params, por favor lee Type::Tiny::Manual::UsingWithMoo, que cubrirá muchos de los conceptos básicos, incluso si no estás usando Moo.

"multiple"

La opción "multiple" te permite especificar múltiples formas de llamar a una subrutina.

signature_for repeat_string => (
  multiple => [
    { positional => [ Str, Int ] },
    { named => [ string => Str, count => Int ], named_to_list => true },
  ],
);

sub repeat_string ( $string, $count ) {
  return $string x $count;
}

repeat_string(            "Hello",          42  );    # funciona
repeat_string(  string => "Hello", count => 42  );    # funciona
repeat_string({ string => "Hello", count => 42 });    # funciona
repeat_string( qr/hiya/ );                            # falla

Combina múltiples verificaciones y prueba cada una hasta que una funcione.

"list_to_named"

En muchos casos, las múltiples convenciones de llamada ofrecidas por "multiple" se pueden implementar más fácilmente usando "list_to_named".

signature_for repeat_string => (
  list_to_named => true,
  named         => [ string => Str, count => Int ],
  named_to_list => true,
);

sub repeat_string ( $string, $count ) {
  return $string x $count;
}

# Formas estándar de llamar a la función:
repeat_string(  string => "Hello", count => 42  );
repeat_string({ string => "Hello", count => 42 });

# Estas también deberían funcionar:
repeat_string( "Hello", count => 42 );
repeat_string( "Hello", { count => 42 } );
repeat_string( 42, string => "Hello" );
repeat_string( 42, { string => "Hello" } );
repeat_string( "Hello", 42 );

# Esto actualmente no funcionará, porque "42" aparece primero, así que se
# toma como la cadena, ¡pero "Hello" no es un entero válido!
repeat_string( 42, "Hello" );

La opción "list_to_named" funciona en tres etapas. Al buscar el hash o hashref de parámetros con nombre, si hay otros parámetros antes, estos se guardan a un lado en una lista de parámetros posicionales "sigilosos".

Más tarde, al validar los parámetros con nombre, si alguno parece faltar, se examina la lista de parámetros posicionales sigilosos y, si es posible, el parámetro se toma de allí.

Finalmente, después de que se hayan procesado todos los parámetros con nombre, si todavía quedan parámetros posicionales que no se necesitaban, se lanza un error.

"signature"

"signature" permite definir la firma dentro de la propia subrutina, potencialmente sobre la marcha, lo cual es útil ocasionalmente.

En lugar de esto:

signature_for foobar => (
  positional => [ Int, Str ],
);

sub foobar ( $foo, $bar ) {
  ...;
}

Haces esto:

sub foobar {
  my $check = signature( positional => [ Int, Str ] );
  my ( $foo, $bar ) = $check->( @_ );
  ...;
}

O usa "state $check" si sabes que la verificación será la misma cada vez.

Funciones versus Métodos

Para subrutinas destinadas a ser llamadas como funciones:

signature_for my_sub => ( method => false, ... );

signature_for my_sub => ( ... ); # esto es el predeterminado de todos modos

Para subrutinas destinadas a ser llamadas como métodos en un objeto bendecido:

signature_for my_method => ( method => Object, ... );

Y para subrutinas destinadas a ser llamadas como métodos en una clase:

signature_for my_method => ( method => ClassName, ... );

signature_for my_method => ( method => Str, ... );  # más rápido, menos legible

Los siguientes también están permitidos, lo que indica que la subrutina está destinada a ser llamada como un método, pero no quieres hacer verificaciones de tipo en el invocante:

signature_for my_method => ( method => builtin::true, ... );

signature_for my_method => ( method => 1, ... );

Hay atajos disponibles:

use Type::Params qw( signature_for_func signature_for_method );

signature_for_func my_function => ( ... );

signature_for_method my_method => ( ... );

Parámetros Mixtos con Nombre y Posicionales

Las opciones "head" y "tail" permiten parámetros posicionales obligatorios al principio o al final de una lista de parámetros con nombre:

signature_for my_func => (
  head  => [ Int ],
  named => [
    foo => Int,
    bar => Optional[Int],
    baz => Optional[Int],
  ],
);

my_func( 42, foo => 21 );                 # ok
my_func( 42, foo => 21, bar  => 84 );     # ok
my_func( 42, foo => 21, bar  => 10.5 );   # no ok
my_func( 42, foo => 21, quux => 84 );     # no ok

Alternativamente, "list_to_named" (ver arriba) puede ser útil.

Firmas Adecuadas

¿No desearías que tus subrutinas pudieran verse así?

sub set_name ( Object $self, Str $name ) {
  $self->{name} = $name;
}

Bueno, aquí tienes algunas soluciones para firmas de subrutinas que funcionan con Type::Tiny...

Zydeco

Zydeco es un kit de herramientas de sintaxis OO de Perl con soporte integrado para Type::Tiny en todas partes.

package MyApp {
  use Zydeco;

  class Person {
    has name ( type => Str );

    method rename ( Str $new_name ) {
      printf( "%s ahora se llamará %s\n", $self->name, $new_name );
      $self->name( $new_name );
    }

    coerce from Str via {
      $class->new( name => $_ )
    }
  }

  class Company {
    has owner ( type => 'Person' );
  }
}

my $acme = MyApp->new_company( owner => "Robert" );
$acme->owner->rename( "Bob" );

Kavorka

Kavorka es una implementación de firmas de subrutinas escrita para utilizar de forma nativa "dwim_type" de Type::Utils para las restricciones de tipo, y aprovechar las características de Type::Tiny como la incrustación y las coerciones.

method set_name ( Str $name ) {
  $self->{name} = $name;
}

Las firmas de Kavorka proporcionan mucha más flexibilidad y una velocidad ligeramente mayor que Type::Params. (La velocidad proviene de la incrustación de casi todas las verificaciones de tipo en el cuerpo de la subrutina que se está declarando.)

Kavorka también incluye soporte para la verificación de tipo del valor devuelto.

Kavorka también puede usarse como parte de Moops, un marco más grande para la programación orientada a objetos en Perl.

Function::Parameters

Function::Parameters ofrece soporte para Type::Tiny y MooseX::Types.

use Types::Standard qw( Str );
use Function::Parameters;

method set_name ( Str $name ) {
    $self->{name} = $name;
}

Attribute::Contract

Tanto Kavorka como Function::Parameters requieren una versión de Perl relativamente reciente. Attribute::Contract soporta versiones más antiguas utilizando mucha menos magia.

Necesitas Attribute::Contract 0.03 o superior.

use Attribute::Contract -types => [qw/Object Str/];

sub set_name :ContractRequires(Object, Str) {
    my ($self, $name) = @_;
    $self->{name} = $name;
}

Attribute::Contract también incluye soporte para la verificación de tipo del valor devuelto.

Type::Params no es realmente un reemplazo directo para Params::Validate; la API difiere demasiado como para afirmarlo. Sin embargo, realiza una tarea similar, por lo que tiene sentido compararlos.

Type::Tiny::Manual::Params(3pm)

NAME

Type::Tiny::Manual::Params - Parameter validation

MANUAL

This manual page is part of the Type::Tiny documentation.

Type::Params is a module that uses Type::Tiny type constraints to perform parameter validation.

It's designed to be a more powerful and more flexible alternative to modules like Params::Validate.

WHY USE TYPE::PARAMS?

There are a number of reasons why you might want to use Type::Params:

  • Type::Params uses Type::Tiny type constraints, which are generally more powerful and flexible than the type validation constants provided by Params::Validate.
  • Type::Params provides a more natural way of validating a mix of positional and named parameters.
  • Type::Params allows you to coerce parameters. For example, if you expect a "Path::Tiny" object, you could coerce it from a string.
  • If you are primarily writing object-oriented code, using Moose or similar, and you are using Type::Tiny type constraints for your attributes, then using Type::Params allows you to use the same constraints for method calls.
  • Type::Params comes bundled with Types::Standard, which provides a much richer vocabulary of types than the type validation constants that come with Params::Validate. For example, Types::Standard provides constraints like "ArrayRef[Int]" (an arrayref of integers), while the closest from Params::Validate is "ARRAYREF", which you'd need to supplement with additional callbacks if you wanted to check that the arrayref contained integers.

    Whatsmore, Type::Params doesn't just work with Types::Standard, but also any other Type::Tiny type constraints.

Params::ValidationCompiler

Params::ValidationCompiler does basically the same thing as Type::Params.

  • Params::ValidationCompiler and Type::Params are likely to perform fairly similarly. In most cases, recent versions of Type::Params seem to be slightly faster, but except in very trivial cases, you're unlikely to notice the speed difference. Speed probably shouldn't be a factor when choosing between them.
  • Type::Params's syntax is more compact: 
    state $check = signature(
  pos => [
    Object,
    Optional[Int],
    Slurpy[ArrayRef],
  ],
);

    Versus:

    state $check = validation_for(
  params => [
    { type => Object },
    { type => Int,      optional => 1 },
    { type => ArrayRef, slurpy => 1 },
  ],
);
  • Params::ValidationCompiler probably has slightly better exceptions.
