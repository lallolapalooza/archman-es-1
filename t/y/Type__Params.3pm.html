NOMBRE

Type::Params - validación de firmas de subrutinas usando restricciones y coerciones de tipos de Type::Tiny

SINOPSIS

use v5.36;
use builtin qw( true false );

package Horse {
  use Moo;
  use Types::Standard qw( Object );
  use Type::Params -sigs;
  use namespace::autoclean;

  ...;   # define atributos, etc

  signature_for add_child => (
    method     => true,
    positional => [ Object ],
  );

  sub add_child ( $self, $child ) {
    push $self->children->@*, $child;
    return $self;
  }
}

package main;

my $boldruler = Horse->new;

$boldruler->add_child( Horse->new );

$boldruler->add_child( 123 );   # muere (¡123 no es un Object!)

ESTADO

Este módulo está cubierto por la política de estabilidad de Type-Tiny.

DESCRIPCIÓN

Esto documenta los detalles del paquete Type::Params. Type::Tiny::Manual es un mejor punto de partida si eres nuevo.

Type::Params utiliza restricciones de Type::Tiny para validar los parámetros de una subrutina. Adopta el enfoque ligeramente poco ortodoxo de separar la validación en dos etapas:

1.
Compilar la especificación de parámetros en una referencia a código; luego
2.
Usar la referencia a código para validar los parámetros.

La primera etapa es lenta (puede tardar un par de milisegundos), pero solo necesita hacerse la primera vez que se llama a la subrutina. La segunda etapa es rápida; según mis benchmarks, incluso más rápida que la versión XS de Params::Validate.

Con la API moderna, rara vez necesitas preocuparte de que las dos etapas estén internamente separadas.

Tenga en cuenta que la mayoría de los ejemplos en esta documentación usan características modernas de Perl como firmas de subrutinas, desreferencia postfija y las palabras clave "true" y "false" de builtin. En Perl versión 5.36+, puedes habilitar todas estas características usando:

use v5.36;
use experimental 'builtin';
use builtin 'true', 'false';

Type::Params admite versiones anteriores de Perl (hasta la 5.8), pero es posible que necesites ajustar la sintaxis para algunos ejemplos.

API MODERNA

La API moderna se puede exportar usando:

use Type::Params -sigs;

O:

use Type::Params -v2;

O solicitando funciones por nombre:

use Type::Params qw( signature signature_for );

Dos atajos opcionales pueden ser exportados:

use Type::Params qw( signature_for_func signature_for_method );

O:

use Type::Params -sigplus;

"signature_for $nombre_de_función => ( %especificación )"

Envuelve una función existente en código adicional que implementa todos los aspectos de la firma de la subrutina, incluyendo desempaquetar argumentos de @_, aplicar valores predeterminados, coercionar y validar valores.

"signature_for( \@funciones, %opts )" es un atajo útil si tienes múltiples funciones con la misma firma.

signature_for [ 'add_nums', 'subtract_nums' ] => (
  positional => [ Num, Num ],
);

Aunque normalmente se usa en contexto void, "signature_for" devuelve un valor.

my $meta = signature_for add_nums => (
  positional => [ Num, Num ],
);

sub add_nums ( $x, $y ) {
  return $x + $y;
}

O cuando se usa con múltiples funciones:

my @metas = signature_for [ 'add_nums', 'subtract_nums' ] => (...);

Esto es un objeto Type::Params::Signature bendecido que proporciona algunas posibilidades de introspección. Inspeccionar "$meta->coderef->code" puede ser útil para ver lo que la firma está haciendo internamente.

Opciones de Especificación de Firma

La especificación de la firma es un hash que debe contener una clave "positional", "named" o "multiple" que indica si tu función acepta parámetros posicionales, nombrados o soporta múltiples convenciones de llamada, pero también puede incluir otras opciones.

"positional" ArrayRef

Esto es conceptualmente una lista de restricciones de tipos, una para cada parámetro posicional. Por ejemplo, una firma para una función que acepta dos enteros:

signature_for myfunc => ( positional => [ Int, Int ] );

Sin embargo, cada restricción de tipo va opcionalmente seguida por un hashref de opciones que afectan a ese parámetro. Por ejemplo:

signature_for myfunc => ( positional => [
  Int, { default => 40 },
  Int, { default =>  2 },
] );

Las restricciones de tipo pueden darse en su lugar como cadenas, que se buscarán usando "dwim_type" de Type::Utils.

signature_for myfunc => ( positional => [
  'Int', { default => 40 },
  'Int', { default =>  2 },
] );

Ver la sección a continuación para más información sobre las opciones de parámetros.

Los parámetros opcionales deben seguir a los parámetros requeridos, y pueden especificarse usando la restricción de tipo parametrizable Optional, la opción de parámetro "optional", o proporcionando un valor predeterminado.

# Los tres parámetros son efectivamente opcionales.
signature_for myfunc => ( positional => [
  Optional[Int],
  Int, { optional => true },
  Int, { default  => 42 },
] );

Se puede proporcionar un único parámetro "slurpy" (que agrupa el resto de argumentos) al final, usando la restricción de tipo parametrizable Slurpy, o la opción de parámetro "slurpy":

signature_for myfunc => ( positional => [
  Int,
  Slurpy[ ArrayRef[Int] ],
] );
signature_for myfunc => ( positional => [
  Int,
  ArrayRef[Int], { slurpy => true },
] );

La opción "positional" también puede abreviarse como "pos".

Así, "signature_for myfunc => ( pos => [...] )" puede usarse en lugar de la más larga "signature_for myfunc => ( positional => [...] )".

signature_for add_numbers => ( pos => [ Num, Num ] );

sub add_numbers ( $num1, $num2 ) {
  return $num1 + $num2;
}

say add_numbers( 2, 3 );   # dice 5

"named" ArrayRef

Esto es conceptualmente una lista de pares de nombres y restricciones de tipos, un par nombre+tipo para cada parámetro nombrado. Por ejemplo, una firma para una función que acepta dos enteros:

signature_for myfunc => ( named => [ foo => Int, bar => Int ] )

Sin embargo, cada restricción de tipo va opcionalmente seguida por un hashref de opciones que afectan a ese parámetro. Por ejemplo:

signature_for myfunc => ( named => [
  foo => Int, { default => 40 },
  bar => Int, { default =>  2 },
] );

Las restricciones de tipo pueden darse en su lugar como cadenas, que se buscarán usando "dwim_type" de Type::Utils.

signature_for myfunc => ( named => [
  foo => 'Int', { default => 40 },
  bar => 'Int', { default =>  2 },
] );

Se permiten parámetros opcionales y "slurpy", pero a diferencia de los parámetros posicionales, no necesitan estar al final.

Ver la sección a continuación para más información sobre las opciones de parámetros.

Si una firma usa parámetros nombrados, los valores se suministran a la función como un único objeto de parámetro:

signature_for add_numbers => ( named => [ num1 => Num, num2 => Num ] );

sub add_numbers ( $arg ) {
  return $arg->num1 + $arg->num2;
}

say add_numbers(   num1 => 2, num2 => 3   );   # dice 5
say add_numbers( { num1 => 2, num2 => 3 } );   # también dice 5

"named_to_list" ArrayRef|Bool

La opción "named_to_list" se ignora para las firmas que usan parámetros posicionales, pero para las firmas que usan parámetros nombrados, les permite ser suministrados a la función como una lista de valores en lugar de como un único objeto:

signature_for add_numbers => (
  named         => [ num1 => Num, num2 => Num ],
  named_to_list => true,
);

sub add_numbers ( $num1, $num2 ) {
  return $num1 + $num2;
}

say add_numbers(   num1 => 2, num2 => 3   );   # dice 5
say add_num
signature_for add_numbers => ( named => [ num1 => Num, num2 => Num ], ); sub add_numbers ( $arg ) { return $arg->num1 + $arg->num2; } say add_numbers( num1 => 2, num2 => 3 ); # dice 5 say add_numbers( { num1 => 2, num2 => 3 } ); # también dice 5 ```

Puedes pensar en "add_numbers" arriba como una función que toma parámetros nombrados desde el exterior, pero recibe parámetros posicionales en el interior.

Puedes usar una referencia de array para controlar el orden en que se suministrarán los parámetros. (Por defecto se devuelven en el orden en que se definieron.)

signature_for add_numbers => (
  named         => [ num1 => Num, num2 => Num ],
  named_to_list => [ qw( num2 num1 ) ],
);

sub add_numbers ( $num2, $num1 ) {
  return $num1 + $num2;
}

say add_numbers(   num1 => 2, num2 => 3   );   # dice 5
say add_numbers( { num1 => 2, num2 => 3 } );   # también dice 5

"list_to_named" Bool

Para una función que acepta parámetros nombrados, permite que se suministren alternativamente como una lista de una manera que esperamos que funcione como se espera.

signature_for add_numbers => (
  named         => [ num1 => Num, num2 => Num ],
  list_to_named => true,
);

sub add_numbers ( $arg ) {
  return $arg->num1 + $arg->num2;
}

say add_numbers( num1 => 5, num2 => 10 );      # dice 15
say add_numbers( { num1 => 5, num2 => 10 } );  # también dice 15
say add_numbers( 5, num2 => 10 );              # dice 15 otra vez
say add_numbers( 5, { num2 => 10 } );          # ¿adivina qué? dice 15
say add_numbers( 10, num1 => 5 );              # 14. ¡es broma! 15
say add_numbers( 10, { num1 => 5 } );          # otro 15
say add_numbers( 5, 10 );                      # sorpresa, dice 15

# MAL: el argumento list_to_named no puede estar al final.
say add_numbers( { num1 => 5 }, 10 );

# MAL: argumento list_to_named duplicado.
say add_numbers( 5, 10, { num1 => 5 } );

Donde se espera un hash o hashref de parámetros nombrados, cualquier parámetro que no parezca encajar en ese patrón se tratará como un parámetro posicional "sigiloso", y se intentará la primera vez que parezca que falta un parámetro nombrado.

Esta característica normalmente solo se aplica a los parámetros obligatorios. Se puede controlar manualmente parámetro a parámetro usando la opción "in_list".

Type::Params intenta ser inteligente al deducir en qué orden se dieron los parámetros posicionales sigilosos.

signature_for add_to_ref => (
  named         => [ ref => ScalarRef[Num], add => Num ],
  list_to_named => true,
);

sub add_to_ref ( $arg ) {
  $arg->ref->$* += $arg->num;
}

my $sum = 0;
add_to_ref( ref => \$sum, add => 1 );
add_to_ref( \$sum, add => 2 );
add_to_ref( \$sum, 3 );
add_to_ref( 4, \$sum );
add_to_ref( 5, sum => \$sum );
add_to_ref( add => 5, sum => \$sum );
say $sum; # 21

Este enfoque es algo más lento, pero tiene el potencial de funciones muy intuitivas.

Tenga en cuenta que "list_to_named" y "named_to_list" se pueden usar ambos en la misma firma, ya que sus significados no son contradictorios.

signature_for add_to_ref => (
  named         => [ ref => ScalarRef[Num], add => Num ],
  list_to_named => true,
  named_to_list => true,
);

sub add_to_ref ( $ref, $num ) {
  $ref->$* += $num;
}

"head" Int|ArrayRef

"head" proporciona una lista adicional de parámetros posicionales no opcionales al principio de @_. Esto se usa a menudo para llamadas a métodos. Por ejemplo, si desea definir una firma para:

$object->my_method( foo => 123, bar => 456 );

Podrías escribirlo así:

signature_for my_method => (
  head    => [ Object ],
  named   => [ foo => Optional[Int], bar => Optional[Int] ],
);

sub my_method ( $self, $arg ) {
  ...;
}

Si "head" se establece como un número en lugar de como un arrayref, es el número de argumentos adicionales al principio:

signature_for stash_foobar = (
  head    => 2,
  named   => [ foo => Optional[Int], bar => Optional[Int] ],
);

sub stash_foobar ( $self, $ctx, $arg ) {
  $ctx->stash->{foo} = $arg->foo if $arg->has_foo;
  $ctx->stash->{bar} = $arg->bar if $arg->has_bar;
  return $self;
}

...;

$app->stash_foobar( $context, foo => 123 );

En este caso, no se realiza ninguna comprobación de tipos en esos argumentos adicionales; solo se comprueba que existan.

"tail" Int|ArrayRef

Una "tail" es como una "head" excepto que es para argumentos al *final* de @_.

signature_for my_method => (
  head    => [ Object ],
  named   => [ foo => Optional[Int], bar => Optional[Int] ],
  tail    => [ CodeRef ],
);

sub my_method ( $self, $arg, $callback ) {
  ...;
}

$object->my_method( foo => 123, bar => 456, sub { ... } );

"method" Bool|TypeTiny

Mientras que "head" se puede usar para firmas de métodos, una forma más declarativa es establecer "method => true".

Si desea especificar que se trata de un método de objeto, destinado a ser llamado solo en objetos bendecidos, entonces puede usar "method => Object", usando el tipo Object de Types::Standard. Si desea especificar que es un método de clase, entonces use "method => Str", usando el tipo Str de Types::Standard. ("method => ClassName" quizás sea más claro, pero es una comprobación más lenta.)

signature_for my_method => (
  method  => true,
  named   => [ foo => Optional[Int], bar => Optional[Int] ],
);

sub my_method ( $self, $arg ) {
  ...;
}

La opción "method" tiene algunas otras diferencias sutiles con "head". Cualquier valor predeterminado de parámetro que sean coderefs se llamarán como métodos en el invocante en lugar de ser llamados sin argumentos. La opción "package" se interpretará de forma ligeramente diferente.

Es posible usar tanto "method" como "head" en la misma firma. El invocante se interpreta como que está *antes* de la "head".

Se proporciona un atajo para "method => true", aunque también habilita un par de otras opciones.

use Type::Params qw( signature_for_method );

signature_for_method my_method => (
  named => [ foo => Optional[Int], bar => Optional[Int] ],
);

sub my_method ( $self, $arg ) {
  ...;
}

"description" Str

Esta es la descripción del coderef que aparecerá en los rastreos de pila. Por defecto es "validación de parámetros para X", donde X es el nombre de la subrutina. Normalmente, el valor predeterminado estará bien.

"package" Str

Esto te permite añadir firmas a subrutinas en otros paquetes:

signature_for foo => ( package "Some::Package", ... );

Si "method" es verdadero y Some::Package no contiene una subrutina llamada "foo", entonces Type::Params recorrerá la jerarquía de herencia, buscando "foo".

Si se especifican restricciones de tipo como cadenas, Type::Params buscará tipos importados por este paquete.

# Espera que el tipo MyInt sea conocido por Some::Package.
signature_for foo => ( package "Some::Package", pos => [ 'MyInt' ] );

Esto también es compatible:

signature_for "Some::Package::foo" => ( ... );

"fallback" CodeRef|Bool

Si la subrutina que se está envolviendo no se encuentra, "signature_for" generalmente lanzará un error. Si quieres que "todavía funcione" en esta situación, usa la opción "fallback". "fallback => \&alternative_coderef_to_wrap" envolverá en su lugar un coderef diferente si el original no se encuentra. "fallback => true" es un atajo para "fallback => sub {}". Un ejemplo donde esto podría ser útil es si estás añadiendo firmas a métodos heredados de una clase padre, pero no estás 100% seguro de que existirán (quizás dependiendo de la versión de la clase padre).

signature_for add_nums => (
  positional => [ Num, Num ],
  fallback   => sub { $_[0] + $_[1] },
);

"on_die" Maybe[CodeRef]

Normalmente, cuando la verificación de la firma encuentra un error, lanzará una excepción, que es un objeto Error::TypeTiny bendecido.

Si proporcionas un coderef "on_die", en su lugar, el objeto Error::TypeTiny se le pasará.

signature_for add_numbers => (
  positional => [ Num, Num ],
  on_die     => sub {
    my $error = shift;
    print "Crisis existencial: $error\n";
    exit( 1 );
  },
);

sub add_numbers ( $num1, $num2 ) {
  return $num1 + $num2;
}

say add_numbers();   # tiene una crisis existencial

Si tu coderef "on_die" no sale o lanza una excepción, en su lugar puede devolver una lista que se usará como parámetros para tu función.

signature_for add_numbers => (
  positional => [ Num, Num ],
  on_die     => sub { return ( 40, 2 ) },
);

sub add_numbers ( $num1, $num2 ) {
  return $num1 + $num2;
}

say add_numbers();   # 42

Esto probablemente no sea muy útil.

"strictness" Bool|Str

Si estableces "strictness" a falso, entonces ciertas verificaciones de firma simplemente nunca se harán. Se pueden omitir la verificación inicial de que hay el número correcto de parámetros, más las verificaciones de tipo en parámetros que no se coercionan.

Si lo estableces a verdadero o no lo estableces en absoluto, entonces estas verificaciones siempre se realizarán.

Alternativamente, se puede establecer en el nombre completamente calificado entre comillas de una variable global de Perl o una constante, y eso se compilará en el coderef como una condición para habilitar las verificaciones estrictas.

signature_for my_func => (
  strictness => '$::CHECK_TYPES',
  positional => [ Int, ArrayRef ],
);

sub my_func ( $int, $aref ) {
  ...;
}

# Se omiten las comprobaciones de tipo
{
  local $::CHECK_TYPES = false;
  my ( $number, $list ) = my_func( {}, {} );
}

# Se realizan las comprobaciones de tipo
{
  local $::CHECK_TYPES = true;
  my ( $number, $list ) = my_func( {}, {} );
}

Un uso recomendado de "strictness" es con Devel::StrictMode.

use Devel::Stri
ctMode qw( STRICT );

state $signature = signature(
  strictness => STRICT,
  positional => [ Int, ArrayRef ],
);
```



  "multiple" ArrayRef|HashRef




  Esta opción permite que tu firma admita múltiples convenciones de llamada. Cada entrada en la matriz es una firma alternativa, como un hashref:



signature_for my_func => (
  multiple => [
    {
      positional    => [ ArrayRef, Int ],
    },
    {
      named         => [ array => ArrayRef, index => Int ],
      named_to_list => true,
    },
  ],
);

sub my_func ( $aref, $int ) {
  ...;
}



  Esa firma permitirá que tu función sea llamada como:



your_function( $arr, $ix );
your_function( array => $arr, index => $ix );
your_function( { array => $arr, index => $ix } );



  A veces, las alternativas devolverán los parámetros en órdenes diferentes:



signature_for my_func => (
  multiple => [
    { positional => [ ArrayRef, Int ] },
    { positional => [ Int, ArrayRef ] },
  ],
);



  Entonces, ¿cómo sabe tu subrutina cómo ha sido llamada? Una opción es usar la variable global "${^_TYPE_PARAMS_MULTISIG}", que se establecerá en el índice de la firma que se utilizó:



sub my_func {
  my ( $arr, $ix ) = ${^_TYPE_PARAMS_MULTISIG} == 1 ? reverse( @_ ) : @_;
  ...;
}



  Si prefieres usar nombres identificativos en lugar de un índice numérico, puedes especificarlos usando "ID":



signature_for my_func => (
  multiple => [
    { ID => 'one', positional => [ ArrayRef, Int ] },
    { ID => 'two', positional => [ Int, ArrayRef ] },
  ],
);



  O usando un hashref:



signature_for my_func => (
  multiple => {
    one => { positional => [ ArrayRef, Int ] },
    two => { positional => [ Int, ArrayRef ] },
  },
);



  Una solución más limpia es usar una referencia de código "next" para reordenar los resultados de firmas alternativas en tu orden preferido:



signature_for my_func => (
  multiple => [
    { positional => [ ArrayRef, Int ] },
    { positional => [ Int, ArrayRef ], next => sub { reverse @_ } },
  ],
);

sub my_func ( $arr, $ix ) {
  ...;
}



  Aunque conceptualmente "multiple" es un arrayref de hashrefs, también es posible usar arrayrefs dentro del arrayref.



multiple => [
  [ ArrayRef, Int ],
  [ Int, ArrayRef ],
]



  Cuando se usa un arrayref de esa manera, es un atajo para una firma posicional.




  Las referencias de código también pueden usarse adicionalmente:



signature_for my_func => (
  multiple => [
    [ ArrayRef, Int ],
    { positional => [ Int, ArrayRef ], next => sub { reverse @_ } },
    sub { ... },
    sub { ... },
  ],
);



  Las referencias de código deben ser subs que devuelvan una lista de parámetros si tienen éxito y lancen una excepción si fallan.




  Las siguientes firmas son equivalentes:



signature_for my_func => (
  multiple => [
    { method => true, positional => [ ArrayRef, Int ] },
    { method => true, positional => [ Int, ArrayRef ] },
  ],
);

signature_for my_func => (
  method   => true,
  multiple => [
    { positional => [ ArrayRef, Int ] },
    { positional => [ Int, ArrayRef ] },
  ],
);



  La opción "multiple" también puede abreviarse a "multi". Por lo tanto, "signature( multi => [...] )" se puede usar en lugar de la versión más larga "signature( multiple => [...] )". ¡Tres caracteres completos ahorrados!




  (Nota: en versiones anteriores de Type::Params, "${^_TYPE_PARAMS_MULTISIG}" se llamaba "${^TYPE_PARAMS_MULTISIG}". El último nombre ya no es compatible.)




  "message" Str




  Solo se usa por las firmas de "multiple". El mensaje de error a lanzar cuando ninguna firma coincide.




  "bless" Bool|ClassName, "class" ClassName|ArrayRef, y "constructor" Str




  Los parámetros con nombre generalmente se devuelven como un objeto bendecido:



signature_for add_numbers => ( named => [ num1 => Num, num2 => Num ] );

sub add_numbers ( $arg ) {
  return $arg->num1 + $arg->num2;
}



  La clase en la que se bendicen es una creada sobre la marcha por Type::Params. Sin embargo, estas tres opciones de firma te permiten un mayor control sobre ese proceso.




  Primero, si estableces "bless => false" y no estableces "class" o "constructor", entonces $arg será solo un hashref no bendecido.



signature_for add_numbers => (
  named        => [ num1 => Num, num2 => Num ],
  bless        => false,
);

sub add_numbers ( $arg ) {
  return $arg->{num1} + $arg->{num2};
}



  Esto es una buena mejora de velocidad, pero tener métodos adecuados para cada parámetro con nombre es una forma útil de detectar nombres mal escritos.




  Si deseas crear manualmente una clase en lugar de depender de que Type::Params genere una sobre la marcha, puedes hacerlo:



package Params::For::AddNumbers {
  sub num1 ( $self ) {
    return $self->{num1};
  }
  sub num2 ( $self ) {
    return $self->{num2};
  }
  sub sum ( $self ) {
    return $self->num1 + $self->num2;
  }
}

signature_for add_numbers => (
  named        => [ num1 => Num, num2 => Num ],
  bless        => 'Params::For::AddNumbers',
);

sub add_numbers ( $arg ) {
  return $arg->sum;
}



  Ten en cuenta que "Params::For::AddNumbers" aquí no incluye un método "new" porque Type::Params hará directamente "bless( $arg, $opts{bless} )".




  Si quieres que Type::Params use un constructor adecuado, deberías usar la opción "class" en su lugar:



package Params::For::AddNumbers {
  use Moo;
  has [ 'num1', 'num2' ] => ( is => 'ro' );
  sub sum {
    my $self = shift;
    return $self->num1 + $self->num2;
  }
}

signature_for add_numbers => (
  named        => [ num1 => Num, num2 => Num ],
  class        => 'Params::For::AddNumbers',
);

sub add_numbers ( $arg ) {
  return $arg->sum;
}



  Si deseas usar un constructor llamado de forma diferente a "new", usa:



signature_for add_numbers => (
  named        => [ num1 => Num, num2 => Num ],
  class        => 'Params::For::AddNumbers',
  constructor  => 'new_from_hashref',
);



  O como atajo:



signature_for add_numbers => (
  named        => [ num1 => Num, num2 => Num ],
  class        => [ 'Params::For::AddNumbers' => 'new_from_hashref' ],
);



  Es dudoso que quieras usar alguna de estas opciones, excepto "bless => false".




  "returns" TypeTiny, "returns_scalar" TypeTiny, y "returns_list" TypeTiny




  Estos se pueden usar para especificar el tipo devuelto por tu función.



signature_for round_number => (
  pos          => [ Num ],
  returns      => Int,
);

sub round_number ( $num ) {
  return int( $num );
}



  Si tu función devuelve diferentes tipos en contexto escalar y de lista, puedes usar "returns_scalar" y "returns_list" para indicar tipos de retorno separados en diferentes contextos.



signature_for my_func => (
  pos             => [ Int, Int ],
  returns_scalar  => Int,
  returns_list    => Tuple[ Int, Int, Int ],
);



  La restricción "returns_list" se define usando una restricción de tipo similar a ArrayRef o HashRef, aunque devuelva una lista, no una sola referencia.




  Si tu función se llama en contexto void, entonces su valor de retorno no es importante y no debe ser verificado por tipo.




  "allow_dash" Bool




  Para cualquier parámetro con nombre "similar a palabra" o alias, crea automáticamente un alias con un guion inicial.



signature_for withdraw_funds => (
  named      => [ amount => Num, account => Str ],
  allow_dash => true,
);

sub withdraw_funds ( $arg ) {
  ...;
}

withdraw_funds(  amount => 11.99,  account => 'ABC123' );
withdraw_funds( -amount => 11.99,  account => 'ABC123' );
withdraw_funds(  amount => 11.99, -account => 'ABC123' );
withdraw_funds( -amount => 11.99, -account => 'ABC123' );



  No tiene efecto en nombres que no son similares a palabras. Los nombres similares a palabras son aquellos que coinciden con "/\A[^\W0-9]\w*\z/"; esencialmente cualquier cosa que Perl permita como un nombre de variable normal no calificado.




  Opciones de Parámetros




  En las listas de parámetros para las opciones de firma "positional" y "named", cada parámetro puede ir seguido de un hashref de opciones específicas para ese parámetro:



signature_for my_func => (
  positional => [
    Int, \%options_for_first_parameter,
    Int, \%options_for_other_parameter,
  ],
  %more_options_for_signature,
);
signature_for my_func => (
  named => [
    foo => Int, \%options_for_foo,
    bar => Int, \%options_for_bar,
  ],
  %more_options_for_signature,
);



  Las siguientes opciones son compatibles para parámetros.




  "optional" Bool




  ¡Una opción llamada opcional!




  Esto hace que un parámetro sea opcional:



signature_for add_nums => (
  positional => [
    Int,
    Int,
    Bool, { optional => true },
  ],
);

sub add_nums ( $num1, $num2, $debug ) {
  my $sum = $num1 + $num2;
  warn "$sum = $num1 + $num2" if $debug;
  return $sum;
}

add_nums( 2, 3, 1 );   # imprime advertencia
add_nums( 2, 3, 0 );   # sin advertencia
add_nums( 2, 3    );   # sin advertencia



  Types::Standard también proporciona un tipo parametrizable Optional que puede ser una forma más limpia de hacer esto:



signature_for add_nums => ( pos => [ Int, Int, Optional[Bool] ] );



  En firmas con parámetros posicionales, cualquier parámetro opcional debe definirse *después* de los parámetros no opcionales. La opción "tail" proporciona una solución alternativa para parámetros requeridos al final de @_.




  En firmas con parámetros con nombre, el orden de los parámetros opcionales y no opcionales no es importante.




  "slurpy" Bool




  Una firma puede contener un solo parámetro slurpy, que recoge cualquier



"signature_for"


Esta función es la base de toda la decoración de métodos y subs con firmas de tipo. Crea y devuelve una subrutina que, cuando se llama, comprueba si la llamada está bien formada, y luego la llama a la subrutina original.


signature_for add_nums => (
  positional => [ Num, Num ],
);

sub add_nums ( $a, $b ) {
  return $a + $b;
}

say add_nums( 1, 2 ); # says 3


La llamada al ejemplo anterior es internamente equivalente a:


my $sig = signature_for add_nums => (
  positional => [ Num, Num ],
);

sub add_nums ( $a, $b ) {
  return $a + $b;
}

# This is what actually happens when you call add_nums
#
# sub &add_nums ( $a, $b ) {
#   my $checked_args = $sig->($%_);
#   return CORE::add_nums( @$checked_args );
# }
#
# 


La subrutina devuelta toma un único argumento: un hash de parámetros. Este hash puede contener:




"positional"

Un arrayref de especificaciones de parámetros posicionales.


"named"

Un arrayref de especificaciones de parámetros con nombre.


"method" Bool

Si es verdadero, la primera línea de argumentos se trata como el invocador. El primer parámetro posicional o el primer nombre de parámetro de la lista se tratará como el invocador.


"strictness" Bool|Str

Por defecto es falso. Si es verdadero, los parámetros no definidos causarán un error fatal. Si se establece en la cadena "warn", se emitirá una advertencia en su lugar.


"allow_dash" Bool

Por defecto es falso. Si es verdadero, los nombres de los parámetros con nombre pueden contener guiones (por ejemplo, "first-name" en lugar de "first_name"). Si el nombre del parámetro no contiene guiones, se permite el uso de guiones de forma nativa.


"list_to_named" Bool

Por defecto es falso. Si es verdadero, los parámetros posicionales pueden ser proporcionados como argumentos con nombre si el parámetro tiene un nombre o un alias.


"inline_list_to_named" Bool

Por defecto es falso. Si es verdadero, los parámetros posicionales pueden ser proporcionados como argumentos con nombre si el parámetro tiene un nombre o un alias. Esto es similar a "list_to_named", pero también permite que los parámetros con nombre se reordenen.


"validate" Bool

Por defecto es verdadero. Si es falso, no se realiza ninguna comprobación de tipos ni de argumentos.


"builder" CodeRef

Una subrutina que recibe el arrayref de argumentos y el hashref de parámetros con nombre, y se espera que devuelva un nuevo arrayref que contenga los argumentos validados y posiblemente modificados.


"on_error" CodeRef

Una subrutina que recibe el argumento original y el mensaje de error, y se espera que devuelva un valor. Por defecto, esto lanzará una excepción.




Cada especificación de parámetro posicional o con nombre es un arrayref. El primer elemento es el tipo de la restricción de tipo. Los elementos posteriores son opcionales y se pasan como argumentos a la función "signature_for" para configurar el comportamiento de ese parámetro específico.


En el caso de los parámetros con nombre, el primer elemento del arrayref es el nombre del parámetro (una cadena), y el segundo es el tipo. Los elementos posteriores son opciones para ese parámetro con nombre.




"slurpy"


Los parámetros que consumen el resto de los argumentos (parámetros "slurpy") se especifican con la opción "slurpy => true". Estos parámetros sólo pueden ser un tipo de referencia de array o de hash.


En firmas con parámetros posicionales, los parámetros slurpy deben tener siempre algún tipo de restricción de tipo ArrayRef o HashRef, deben aparecer siempre al *final* de la lista de parámetros posicionales, y funcionan así:


signature_for add_nums => (
  positional => [
    Num,
    ArrayRef[Num], { slurpy => true },
  ],
);

sub add_nums ( $first_num, $other_nums ) {
  my $sum = $first_num;
  for my $other ( $other_nums->@* ) {
    $sum += $other;
  }
  return $sum;
}

say add_nums( 1 );            # dice 1
say add_nums( 1, 2 );         # dice 3
say add_nums( 1, 2, 3 );      # dice 6
say add_nums( 1, 2, 3, 4 );   # dice 10


En firmas con parámetros con nombre, los parámetros slurpy deben tener siempre algún tipo de restricción de tipo HashRef, y funcionan así:


use builtin qw( true false );

signature_for process_data => (
  method => true,
  named  => [
    input   => FileHandle,
    output  => FileHandle,
    flags   => HashRef[Bool], { slurpy => true },
  ],
);

sub process_data ( $self, $arg ) {
  warn "Beginning data processing" if $arg->flags->{debug};
  ...;
}

$widget->process_data(
  input  => \*STDIN,
  output => \*STDOUT,
  debug  => true,
);


Se puede utilizar la restricción de tipo Slurpy de Types::Standard como atajo para especificar parámetros slurpy:


signature_for add_nums => (
  positional => [ Num, Slurpy[ ArrayRef[Num] ] ],
)


El tipo Slurpy[Any] se maneja especialmente y se trata como un ArrayRef slurpy en firmas con parámetros posicionales, y un HashRef slurpy en firmas con parámetros con nombre, pero tiene algunas optimizaciones adicionales para la velocidad.


"default"
    CodeRef|ScalarRef|Ref|Str|Undef


Se puede proporcionar un valor predeterminado para un parámetro.


signature_for my_func => (
  positional => [
    Int,
    Int, { default => "666" },
    Int, { default => "999" },
  ],
);


Los valores predeterminados admitidos son cualquier cadena (incluidas las numéricas), "undef", y hashrefs y arrayrefs vacíos. Los hashrefs y arrayrefs no vacíos *no están permitidos como valores predeterminados*.


Alternativamente, puede proporcionar una coderef para generar un valor predeterminado:


signature_for my_func => (
  positional => [
    Int,
    Int, { default => sub { 6 * 111 } },
    Int, { default => sub { 9 * 111 } },
  ]
);


Esa coderef puede generar cualquier valor, incluidos arrayrefs no vacíos y hashrefs no vacíos. Para undef, cadenas simples, números y estructuras vacías, evitar usar una coderef hará que el procesamiento de sus parámetros sea más rápido.


En lugar de una coderef, puede usar una referencia a una cadena de código fuente de Perl:


signature_for my_func => (
  positional => [
    Int,
    Int, { default => \ '6 * 111' },
    Int, { default => \ '9 * 111' },
  ],
);


Los valores predeterminados *serán* validados contra la restricción de tipo y potencialmente forzados.


Cualquier parámetro con un valor predeterminado será automáticamente opcional, ya que no tiene sentido proporcionar un valor predeterminado para parámetros requeridos.


Tenga en cuenta que tener *cualquier* valor predeterminado en una firma (incluso si nunca se utilizan) puede ralentizarla, ya que Type::Params necesitará construir un nuevo array en lugar de simplemente devolver @_.


"default_on_undef"
    Bool


Normalmente, los valores predeterminados solo se aplican cuando un parámetro está *ausente* (piense en "exists" para hashes o que el array es demasiado corto). Establecer "default_on_undef" en verdadero también activará el valor predeterminado si se proporciona un parámetro pero está indefinido.


Si el llamador realmente quiere proporcionar undef como valor, no se recomienda usar esto.


"coerce" Bool


Hablando de forzar la conversión, la opción "coerce" te permite indicar que un valor debe ser forzado al tipo correcto:


signature_for my_func => (
  positional => [
    Int,
    Int,
    Bool, { coerce => true },
  ],
);


Establecer "coerce" en falso deshabilitará la conversión forzada.


Si no se especifica "coerce", es decir, no es ni verdadero ni falso, entonces la conversión forzada se habilitará si la restricción de tipo tiene una conversión, y se deshabilitará en caso contrario.


Tenga en cuenta que tener *cualquier* conversión forzada en una firma (incluso si nunca se utiliza) puede ralentizarla, ya que Type::Params necesitará construir un nuevo array en lugar de simplemente devolver @_.


"clone" Bool


Si esto se establece en verdadero, clonará profundamente los valores entrantes a través de "dclone" de Storable (un módulo principal desde Perl 5.7.3).


En el siguiente ejemplo, $arr es una referencia a un *clon de* @numbers, por lo que agregar números adicionales a él deja @numbers sin cambios.


signature_for foo => (
  positional => [ ArrayRef, { clone => true } ],
);

sub foo ( $arr ) {
  push @$arr, 4, 5, 6;
}

my @numbers = ( 1, 2, 3 );
foo( \@numbers );
print "@numbers\n";  ## 1 2 3


Tenga en cuenta que la clonación ralentizará significativamente su firma.


"name" Str


Esto anula el nombre de un parámetro con nombre. No sé por qué querría hacer eso.


La siguiente firma tiene dos parámetros: "foo" y "bar". El nombre "fool" se ignora por completo.


signature_for my_func => (
  named => [
    fool   => Int, { name => 'foo' },
    bar    => Int,
  ],
);


Sin embargo, también puede nombrar parámetros posicionales, que normalmente no tienen nombres.


signature_for my_func => (
  positional => [
    Int, { name => 'foo' },
    Int, { name => 'bar' },
  ],
);


Los nombres de los parámetros posicionales en realidad no se *usan* para nada en este momento, pero pueden incorporarse a mensajes de error o similares en el futuro.


"getter" Str


Para firmas con parámetros con nombre, especifica el nombre del método utilizado para recuperar el valor de este parámetro del objeto $arg.


signature_for process_data => (
  method => true,
  named  => [
    input   => FileHandle,    { getter => 'in' },
    output  => FileHandle,    { getter => 'out' },
    flags   => HashRef[Bool], { slurpy => true },
  ],
);

sub process_data ( $self, $arg ) {
  warn "Beginning data processing" if $arg->flags->{debug};

  my ( $in, $out ) = ( $arg->in, $arg->out );
  ...;
}

$widget->process_data(
  input  => \*STDIN,
  output => \*STDOUT,
  debug  => true,
);


Ignorado por firmas con parámetros posicionales.


"predicate" Str


El objeto $arg proporcionado por firmas con parámetros con nombre también incluirá métodos "has" para cualquier argumento opcional. Por ejemplo:


signature_for process_data => (
  method => true,
  named  => [
    input   => Optional[ FileHandle ],
    output  => Optional[ FileHandle ],
    flags   => Slurpy[ HashRef[Bool] ],
  ],
);

sub process_data ( $self, $arg ) {

  if ( $self->has_input and $self->has_output ) {
    ...;
  }

  ...;
}


Establecer una opción "predicate" te permite elegir un nombre diferente para este método en lugar de "has_*".


También es posible establecer un "predicate" para parámetros no opcionales, que normalmente no obtienen un método "has".


Ignorado por firmas con parámetros posicionales.


"alias"
    Str|ArrayRef[Str]


Una lista de nombres alternativos para el parámetro, o un único nombre alternativo.


signature_for add_numbers => (
  named => [
    first_number   => Int, { alias => [ 'x' ] },
    second_number  => Int, { alias =>   'y'   },
  ],
);

sub add_numbers ( $arg ) {
  return $arg->first_number + $arg->second_number;
}

say add_numbers( first_number => 40, second_number => 2 );  # 42
say add_numbers( x            => 40, y             => 2 );  # 42
say add_numbers( first_number => 40, y             => 2 );  # 42
say add_numbers( first_number => 40, x => 1, y => 2 );      # muere!


Ignorado por firmas con parámetros posicionales.


"in_list" Bool


En conjunción con "list_to_named", determina si este parámetro puede ser proporcionado como parte de la lista de parámetros posicionales "sigilosos". Si no se está utilizando "list_to_named", "in_list" se ignora.


Por defecto es falso si el parámetro es opcional o tiene un valor predeterminado. Por defecto es verdadero si el parámetro es requerido.


"strictness" Bool|Str


Anula la opción de firma "strictness" a nivel de parámetro individual.






"signature_for_func   $function_name => ( %spec )"


Al igual que "signature_for" y por defecto a "method => false".


Si la firma tiene parámetros con nombre, además establecerá por defecto "list_to_named" y "allow_dash" a verdadero.


signature_for_func add_to_ref => (
  named         => [ ref => ScalarRef[Num], add => Num ],
  named_to_list => true,
);

sub add_to_ref ( $ref, $add ) {
  $ref->$* += $add;
}

my $sum = 0;
add_to_ref( ref => \$sum, add => 1 );
add_to_ref( \$sum, 2 );
add_to_ref( 3, \$sum );
add_to_ref( 4, { -ref => \$sum } );
say $sum; # 10


El comportamiento exacto de "signature_for_func" es inestable y puede cambiar en futuras versiones de Type::Params.






"signature_for_method   $function_name => ( %spec )"


Al igual que "signature_for" pero establecerá por defecto &qu
ot;method => true".


Si la firma tiene parámetros con nombre, también será por defecto
    "list_to_named" y
    "allow_dash" a true.


package Calculator {
  use Types::Standard qw( Num ScalarRef );
  use Type::Params qw( signature_for_method );

  ...;

  signature_for_method add_to_ref => (
    named         => [ ref => ScalarRef[Num], add => Num ],
    named_to_list => true,
  );

  sub add_to_ref ( $self, $ref, $add ) {
    $ref->$* += $add;
  }
}

my $calc = Calculator->new;
my $sum = 0;
$calc->add_to_ref( ref => \$sum, add => 1 );
$calc->add_to_ref( \$sum, 2 );
$calc->add_to_ref( 3, \$sum );
$calc->add_to_ref( 4, { -ref => \$sum } );
say $sum; # 10


El comportamiento exacto de
    "signature_for_method" es inestable y puede
    cambiar en futuras versiones de Type::Params.






signature(   %spec )


La función "signature" permite un
    control más detallado sobre las firmas. En lugar de envolver automáticamente
    tu función, devuelve un coderef al que puedes pasarle @_.


Lo siguiente es aproximadamente equivalente:


signature_for add_nums => ( pos => [ Num, Num ] );

sub add_nums ( $x, $y ) {
  return $x + $y;
}


Y:


sub add_nums {
  state $signature = signature( pos => [ Num, Num ] );
  my ( $x, $y ) = $signature->( @_ );

  return $x + $y;
}


Perl permite una forma un poco arcaica de llamar a coderefs sin usar
    paréntesis, lo que puede ser un poco más rápido a costa de ser más oscuro:


sub add_nums {
  state $signature = signature( pos => [ Num, Num ] );
  my ( $x, $y ) = &$signature; # importante: ¡sin paréntesis!

  return $x + $y;
}


Si necesitas soportar Perl 5.8, que no tenía la palabra clave
    "state":


my $__add_nums_sig;
sub add_nums {
  $__add_nums_sig ||= signature( pos => [ Num, Num ] );
  my ( $x, $y ) = &$__add_nums_sig;

  ...;
}


Esto te da más control sobre cómo y cuándo se construye y usa la
    firma, y qué se hace con los valores que desempaqueta.


En particular, ten en cuenta que si tu función nunca se llama, la
    firma ni siquiera se construye, lo que significa que para las funciones que
    usas raramente, hay menos costo por tener la firma.


A partir de 2025, probablemente querrás usar
    "signature_for" en lugar de
    "signature" en la mayoría de los casos.


Opciones Adicionales de Especificación de Firma


Hay ciertas opciones que no tienen sentido para
    "signature_for" y solo son útiles para
    "signature". Otras pueden comportarse de forma
    ligeramente diferente. Estas se anotan aquí.


"returns" TypeTiny,
    "returns_scalar" TypeTiny, y
    "returns_list" TypeTiny


Dado que "signature" no es capaz
    de envolver completamente tu función, las opciones
    "returns", "returns_scalar",
    y "returns_list" no pueden hacer nada.
    Deberías considerarlas solo como documentación.


"subname" Str


El nombre del sub cuya firma se supone que debemos verificar. Esto
    es útil en trazas de pila, etc. Por defecto es el llamador.


"package" Str


Funciona igual que en
    "signature_for", pero vale la pena mencionarlo
    de nuevo ya que está estrechamente relacionado con
    "subname".


"caller_level" Int


Si estás envolviendo "signature"
    para poder verificar firmas en nombre de otro paquete, entonces establecer
    "caller_level" a 1 (¡o más, dependiendo del
    nivel de envoltura!) puede ser una alternativa a establecer manualmente el
    "package" y
    "subname".


"next" Bool|CodeLike


Esto se puede usar para encadenar coderefs. Si entiendes
    "on_die", esto actúa como un
    "on_live".


sub add_numbers {
  state $sig = signature(
    positional => [ Num, Num ],
    next => sub {
      my ( $num1, $num2 ) = @_;

      return $num1 + $num2;
    },
  );

  my $sum = $sig->( @_ );
  return $sum;
}

say add_numbers( 2, 3 );   # dice 5


Si se establece a true en lugar de a un coderef, tiene un
    comportamiento ligeramente diferente:


sub add_numbers {
  state $sig = signature(
    positional => [ Num, Num ],
    next       => true,
  );

  my $sum = $sig->(
    sub { return $_[0] + $_[1] },
    @_,
  );
  return $sum;
}

say add_numbers( 2, 3 );   # dice 5


Esto parece extraño. ¿Por qué sería útil? Bueno, funciona bien con
    la palabra clave "around" de Moose.


sub add_numbers {
  return $_[1] + $_[2];
}

around add_numbers => signature(
  method     => true,
  positional => [ Num, Num ],
  next       => true,
  package    => __PACKAGE__,
  subname    => 'add_numbers',
);

say __PACKAGE__->add_numbers( 2, 3 );   # dice 5


Ten en cuenta la forma en que
    "around" funciona en Moose, que espera un
    coderef envolvente como su argumento final. Ese coderef envolvente luego
    espera recibir una referencia a la función original como su primer parámetro.


Esto puede permitir, por ejemplo, que un rol proporcione una
    firma que envuelva un método definido en una clase.


Esto es un poco complejo y es poco probable que lo uses, pero ha
    demostrado ser útil para herramientas que integran Type::Params con modificadores
    de métodos tipo Moose.


Ten en cuenta que "next" es el
    mecanismo que "signature_for" utiliza internamente
    para conectar la firma con el sub envuelto, por lo que usar
    "next" con
    "signature_for" es una buena receta para
    dolores de cabeza.


Si se usan firmas "multiple",
    "next" es útil para que cada firma
    "interna" ajuste los parámetros al orden correcto. Este uso de
    "next" *sí* está soportado para
    "signature_for".


La opción "goto_next" se soporta como
    un alias histórico para "next".


"want_source" Bool


En lugar de devolver un coderef, devuelve una cadena de código
    fuente de Perl. Útil para depuración.


"want_details" Bool


En lugar de devolver un coderef, devuelve un hashref con información
    incluyendo el coderef. Esto es principalmente para personas que extienden
    Type::Params y no entraré en demasiados detalles sobre lo que más contiene
    este hashref.


"want_object" Bool


En lugar de devolver un coderef, devuelve un objeto
    Type::Params::Signature. Esta es la versión más moderna de
    "want_details".








API LEGADO


Las siguientes funciones eran la API anterior a Type::Params v2.
    Todavía se soportan, pero su uso ahora está desaconsejado.


Si no proporcionas ninguna lista de importación, importarás
    "compile" y
    "compile_named":


use Type::Params;


Esto hace lo mismo:


use Type::Params -v1;


Lo siguiente importa "compile",
    "compile_named" y
    "compile_named_oo":


use Type::Params -compile;


Lo siguiente importa
    "wrap_subs" y
    "wrap_methods":


use Type::Params -wrap;




compile(   @pos_params )


Equivalente a "signature( positional =>
    \@pos_params )".


"compile( \%spec, @pos_params )"
    es equivalente a "signature( %spec, positional =>
    \@pos_params )".






compile_named(   @named_params )


Equivalente a "signature( bless => 0,
    named => \@named_params )".


"compile_named( \%spec, @named_params
    )" es equivalente a "signature( bless
    => false, %spec, named => \@named_params )".






compile_named_oo(   @named_params )


Equivalente a "signature( bless => true,
    named => \@named_params )".


"compile_named_oo( \%spec, @named_params
    )" es equivalente a "signature( bless
    => true, %spec, named => \@named_params )".






"validate(   \@args, @pos_params )"


Equivalente a "signature( positional =>
    \@pos_params )->( @args )".


La función "validate" nunca

NAME


Type::Params - A framework for writing function signatures in Perl






SYNOPSIS


    use Type::Params qw( compile signature_for );
    use Types::Standard qw( ArrayRef Int );

    signature_for my_sub => (
      positional => [ ArrayRef, Int ],
      named      => {
        foo => Undef | Str,
        bar => compile( Bool ),
      },
      optionals  => { baz => Int },
      defaults   => { baz => 0 },
    );

    sub my_sub ($arr, $ix, %args) {
      # ...
    }






STATUS


This module is stable and feature-complete. It is the successor
    to Type::Tiny::Signature and is part of the
    Type::Tiny ecosystem.


It is still actively maintained.






DESCRIPTION


This module provides a framework for defining function signatures,
    and checking function arguments against those signatures.


It is designed to be used with Type::Tiny
    compatible type libraries.


The primary way to use this module is via the
    "signature_for" function, which is a
    sub-expression that wraps a subroutine or method definition.


    signature_for $subref => ( ... );
    sub my_sub ( signature_for( ... ) ) { ... }


The arguments supplied to "signature_for"
    define the function's signature. The second argument is a hash reference that
    maps parameter names (or special keywords) to their type constraints.


Supported parameter types are:



  
"positional"

  
An array reference of type constraints for positional arguments.
      These arguments are consumed strictly in order.

  
"named"

  
A hash reference mapping parameter names to their type constraints.
      These arguments are consumed by name.

  
"optionals"

  
A hash reference mapping parameter names to their type constraints.
      These arguments are optional.

  
"defaults"

  
A hash reference mapping parameter names to their default values.
      These arguments are optional and have default values.

  
"method"

  
A boolean value. If true, the first argument is treated as the invocant
      (class or object).

  
"multiple"

  
An array reference of signature specifications. This allows for
      multiple possible signatures (e.g. overloaded functions).




The type constraints are typically provided by a compatible type
    library such as Type::Tiny or
    Types::Standard.


You will need to import the types you use, e.g.:


    use Types::Standard qw( ArrayRef Int Str );


The compile function is used to wrap
    type constraints that may have been generated by other functions in this
    module (e.g. wrap_subs).


    use Type::Params qw( compile signature_for );
    use Types::Standard qw( ArrayRef Int );

    signature_for my_sub => (
      positional => [
        compile( [ ArrayRef, Int ] ),
      ],
    );


When a function defined with "signature_for"
    is called, its arguments are checked against the specified signature. If the
    check fails, an exception is thrown.


If the check succeeds, the function body is executed. If the
    function is a method, the first argument (the invocant) is automatically
    bound to the first parameter (if method => 1 is
    specified).


If you need to pass arguments into a subroutine whose signature
    you don't control, you can use Type::Params::apply.






MODERN API




signature(   %spec )


Returns a type constraint that matches arguments that conform to
    the specified signature specification. This is useful for validating data
    structures that are supposed to represent arguments.


    use Type::Params qw( signature );
    use Types::Standard qw( ArrayRef Int );

    my $arg_checker = signature(
      positional => [ ArrayRef, Int ]
    );

    my $valid_args = [ [ 1, 2 ], 3 ];
    my $invalid_args = [ 1, 2, 3 ];

    if ( $arg_checker->check($valid_args)->ok ) {
      print "Valid arguments\n";
    }

    if ( !$arg_checker->check($invalid_args)->ok ) {
      print "Invalid arguments: ", $arg_checker->check($invalid_args)->error, "\n";
    }






compile(   %spec )


Takes a signature specification and returns a type constraint
    suitable for use with signature_for or
    signature.


    use Type::Params qw( compile signature_for );
    use Types::Standard qw( ArrayRef Int );

    signature_for my_sub => (
      positional => [ compile( [ ArrayRef, Int ] ) ]
    );






apply(   $sub, %spec )


Returns a subroutine that wraps $sub,
    checking its arguments against %spec before calling
    it.


    use Type::Params qw( apply );
    use Types::Standard qw( ArrayRef Int );

    sub check_args ($arr, $ix) {
      return $arr->[ $ix ];
    }

    my $checked_sub = apply(
      \&check_args,
      positional => [ ArrayRef, Int ],
    );

    $checked_sub->( [1, 2], 3 ); # OK
    # $checked_sub->( 1, 2 );   # Throws exception






"signature_for($sub, %spec)"


This is a subexpression that can be used directly in a subroutine
    or method definition. It defines the signature for that subroutine or
    method.


    use Type::Params qw( signature_for );
    use Types::Standard qw( Int );

    signature_for my_method => (
      method => 1,
      positional => [ Int ],
    );
    sub my_method ( $self, $x ) { ... }


You can also use it inline:


    use Type::Params qw( signature_for );
    use Types::Standard qw( Int );

    sub my_method ( signature_for( method => 1, positional => [ Int ] ) ) {
      my ($self, $x) = @_;
      # ...
    }






"compile_named(%spec)"


This is a convenience function for compiling a named parameter
    specification.


    use Type::Params qw( compile_named signature_for );
    use Types::Standard qw( Str );

    signature_for my_sub => (
      named => compile_named( foo => Str )
    );






"compile_positional(%spec)"


This is a convenience function for compiling a positional parameter
    specification.


    use Type::Params qw( compile_positional signature_for );
    use Types::Standard qw( Int );

    signature_for my_sub => (
      positional => compile_positional( Int )
    );








LEGACY API


The following functions were present in older versions of this
    module. They are still supported for backwards compatibility, but their use
    is not recommended.




"wrap_subs( func1 => \@params1, func2 => \@params2, ... )"


Equivalent to:


signature_for func1 => ( positional => \@params1 );
signature_for func2 => ( positional => \@params2 );


One slight difference is that instead of arrayrefs, you can
    provide the output of one of the "compile"
    functions:


wrap_subs( func1 => compile_named( @params1 ) );


"wrap_subs" is not exported
    unless requested by name.






"wrap_methods( func1 => \@params1, func2 => \@params2, ... )"


Equivalent to:


signature_for func1 => ( method => 1, positional => \@params1 );
signature_for func2 => ( method => 1, positional => \@params2 );


One slight difference is that instead of arrayrefs, you can
    provide the output of one of the "compile"
    functions:


wrap_methods( func1 => compile_named( @params1 ) );


"wrap_methods" is not exported
    unless requested by name.






multisig( @alternatives )


Equivalent to:


signature( multiple => \@alternatives )


"multisig( \%spec, @alternatives )" is equivalent to "signature( %spec, multiple => \@alternatives )".








TYPE CONSTRAINTS


Although Type::Params is not a real type library, it exports two
    type constraints. Their use is no longer recommended.




Invocant


Type::Params exports a type Invocant on request. This gives
    you a type constraint which accepts classnames and blessed
  objects.


use Type::Params qw( compile Invocant );

signature_for my_method => (
  method     => Invocant,
  positional => [ ArrayRef, Int ],
);

sub my_method ($self_or_class, $arr, $ix) {
  return $arr->[ $ix ];
}


"Invocant" is not exported
    unless requested by name.


Recommendation: use Defined from Types::Standard
  instead.






ArgsObject


Type::Params exports a parameterizable type constraint
    ArgsObject. It accepts the kinds of objects returned by signature
    checks for named parameters.


use v5.36;

package Foo {
  use Moo;
  use Type::Params 'ArgsObject';

  has args => (
    is  => 'ro',
    isa => ArgsObject['Bar::bar'],
  );
}

package Bar {
  use Types::Standard -types;
  use Type::Params 'signature_for';

  signature_for bar => ( named => [ xxx => Int, yyy => ArrayRef ] );

  sub bar ( $got ) {
    return 'Foo'->new( args => $got );
  }
}

Bar::bar( xxx => 42, yyy => [] );


The parameter "Bar::bar" refers to the caller when the
    check is compiled, rather than when the parameters are checked.


"ArgsObject" is not exported
    unless requested by name.


Recommendation: use Object from Types::Standard
  instead.








ENVIRONMENT



  
"PERL_TYPE_PARAMS_XS"

  
Affects the building of accessors for $arg
      objects. If set to true, will use Class::XSAccessor. If set to false, will
      use pure Perl. If this environment variable does not exist, will use
      Class::XSAccessor.
    
If Class::XSAccessor is not installed or is too old, pure Perl
        will always be used as a fallback.
