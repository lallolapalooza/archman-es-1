Tk_CreateErrorHandler(3) Procedimientos de la biblioteca Tk Tk_CreateErrorHandler(3)

NOMBRE

Tk_CreateErrorHandler, Tk_DeleteErrorHandler - manejar errores del protocolo X

SINOPSIS

#include <tk.h>

Tk_ErrorHandler
Tk_CreateErrorHandler(display, error, request, minor, proc, clientData)

Tk_DeleteErrorHandler(handler)

ARGUMENTOS

Display *display (entrada)
Pantalla cuyos errores se van a manejar.
int error (entrada)
Coincidir solo con eventos de error con este valor en el campo error_code. Si es -1, entonces coincidirá con cualquier valor de error_code.
int request (entrada)
Coincidir solo con eventos de error con este valor en el campo request_code. Si es -1, entonces coincidirá con cualquier valor de request_code.
int minor (entrada)
Coincidir solo con eventos de error con este valor en el campo minor_code. Si es -1, entonces coincidirá con cualquier valor de minor_code.
Tk_ErrorProc *proc (entrada)
Procedimiento a invocar cada vez que se reciba un evento de error para display y coincida con error, request y minor. NULL significa ignorar cualquier error coincidente.
ClientData clientData (entrada)
Valor arbitrario de una palabra para pasar a proc.
Tk_ErrorHandler handler (entrada)
Token para el manejador de errores a eliminar (valor de retorno de una llamada anterior a Tk_CreateErrorHandler).

DESCRIPCION

Tk_CreateErrorHandler organiza que un procedimiento en particular (proc) sea llamado cada vez que ocurran ciertos errores de protocolo en una pantalla en particular (display). Los errores de protocolo ocurren cuando el protocolo X se usa incorrectamente, como intentar mapear una ventana que no existe. Consulte la documentación de Xlib para XSetErrorHandler para obtener más información sobre los tipos de errores que pueden ocurrir. Para que proc sea invocado para manejar un error particular, deben ocurrir cinco cosas:

[1]
El error debe pertenecer a display.
[2]
Ya sea que el argumento error a Tk_CreateErrorHandler haya sido -1, o que el argumento error coincida con el campo error_code del evento de error.
[3]
Ya sea que el argumento request a Tk_CreateErrorHandler haya sido -1, o que el argumento request coincida con el campo request_code del evento de error.
[4]
Ya sea que el argumento minor a Tk_CreateErrorHandler haya sido -1, o que el argumento minor coincida con el campo minor_code del evento de error.
[5]
La solicitud de protocolo a la que se refiere el error debe haber sido realizada cuando el manejador estaba activo (ver más abajo para más información).

Proc debe tener argumentos y un resultado que coincidan con el siguiente tipo:

typedef int Tk_ErrorProc(
        ClientData clientData,
        XErrorEvent *errEventPtr);
El parámetro clientData de proc es una copia del parámetro clientData dado a Tcl_CreateErrorHandler cuando se creó la llamada de retorno. Típicamente, clientData apunta a una estructura de datos que contiene información específica de la aplicación que es necesaria para tratar el error. ErrEventPtr es un puntero al evento de error X. El procedimiento proc debe devolver un valor entero. Si devuelve 0, significa que proc manejó el error por completo y no es necesario tomar ninguna otra acción para el error. Si devuelve un valor distinto de cero, significa que proc no pudo manejar el error.

Si se especifica NULL para proc, todos los errores coincidentes se ignorarán: esto producirá el mismo resultado que si se hubiera especificado un procedimiento que siempre devuelve 0.

Si más de un manejador coincide con un error en particular, entonces se invocarán en orden. Los manejadores se invocarán en orden inverso de creación: el manejador declarado más recientemente primero. Si algún manejador devuelve 0, entonces los manejadores subsiguientes (más antiguos) no se invocarán. Si ningún manejador devuelve 0, entonces Tk invoca al manejador de errores predeterminado de X, que imprime un mensaje de error y aborta el programa. Si desea tener un manejador predeterminado que maneje los errores que ningún otro manejador puede manejar, declárelo primero.

La documentación de X establece que "el manejador de errores no debe llamar a ninguna función (directa o indirectamente) en la pantalla que genere solicitudes de protocolo o que busque eventos de entrada". Esta restricción se aplica a los manejadores declarados por Tk_CreateErrorHandler; desobedézcala bajo su propio riesgo.

Se puede llamar a Tk_DeleteErrorHandler para eliminar un manejador de errores creado previamente. El argumento handler identifica el manejador de errores y debe ser un valor devuelto por una llamada anterior a Tk_CreateEventHandler.

Un manejador de errores en particular se aplica a los errores que resultan de las solicitudes de protocolo generadas entre la llamada a Tk_CreateErrorHandler y la llamada a Tk_DeleteErrorHandler. Sin embargo, la llamada de retorno real a proc puede no ocurrir hasta después de la llamada a Tk_DeleteErrorHandler, debido al almacenamiento en búfer en el cliente y el servidor. Si un evento de error pertenece a una solicitud de protocolo realizada justo antes de llamar a Tk_DeleteErrorHandler, entonces el evento de error puede no haber sido procesado antes de la llamada a Tk_DeleteErrorHandler. Cuando surge esta situación, Tk guarda información sobre el manejador e invoca al procedimiento proc del manejador más tarde cuando llega el evento de error. Si una aplicación desea eliminar un manejador de errores y saber con certeza que todos los errores relevantes han sido procesados, primero debe llamar a Tk_DeleteErrorHandler y luego llamar a XSync; esto eliminará cualquier solicitud y error en búfer, pero resultará en una penalización de rendimiento porque requiere comunicación hacia y desde el servidor X. Después de la llamada a XSync, se garantiza que Tk no llamará a ningún manejador de errores eliminado antes de la llamada a XSync.

Para que el mecanismo de manejo de errores de Tk funcione correctamente, es esencial que el código de la aplicación nunca llame directamente a XSetErrorHandler; las aplicaciones solo deben usar Tk_CreateErrorHandler.
