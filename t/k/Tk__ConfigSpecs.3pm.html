NOMBRE

Tk::ConfigSpecs - Definición del comportamiento de 'configure' para widgets compuestos.

SINOPSIS

sub Populate
{
 my ($composite,$args) = @_;
 ...
 $composite->ConfigSpecs('-atributo' => [ donde,nombreBD,claseBD,predeterminado ]);
 $composite->ConfigSpecs('-alias' => '-otroatributo');
 $composite->ConfigSpecs('PREDETERMINADO' => [ donde ]);
 $composite->ConfigSpecs($subwidget->ConfigSpecs);
 ...
}
$composite->configure(-atributo => valor);

DESCRIPCIÓN

El objetivo es hacer que el método configure del widget compuesto se parezca lo más posible al configure de un widget regular de Tk. (Ver Tk::options para una descripción de este comportamiento.) Para habilitar esto, se deben definir los atributos que el compuesto acepta en su conjunto.

Definición de los ConfigSpecs para una clase.

Típicamente, un widget tendrá una o más llamadas como la siguiente

$composite->ConfigSpecs(-atributo => [donde,nombreBD,claseBD,predeterminado]);

en su método Populate. Cuando se llama a ConfigSpecs de esta manera (con argumentos), los argumentos se utilizan para construir o aumentar/reemplazar una tabla hash para el widget. (Se puede especificar más de un par de -opcion=>valor en una sola llamada).

nombreBD, claseBD y predeterminado solo son utilizados por ConfigDefault descrito a continuación, o para responder a comandos configure de 'consulta'.

Puede ser uno de los valores a continuación, o una lista de dichos valores encerrados entre [].

Los valores actualmente permitidos para donde son:

'ADVERTISED'
Aplicar configure a subwidgets *anunciados*.
'DESCENDANTS'
Aplicar configure recursivamente a todos los descendientes.
'CALLBACK'
Al establecer el atributo, se llama "Tk::Callback->new($valor)" antes de almacenar en "$composite->{Configure}{-atributo}". Esto es apropiado para atributos "-command => ..." que son manejados por el compuesto y no se reenvían a un subwidget. (Por ejemplo, Tk::Tiler tiene "-yscrollcommand" para permitirle tener una barra de desplazamiento adjunta).

Esta puede ser la primera de varias palabras clave de 'validación' (por ejemplo, font, cursor, anchor, etc.) que el núcleo de Tk trata especialmente para el código C.

'CHILDREN'
Aplicar configure a todos los hijos. (Los hijos son los descendientes inmediatos de un widget).
'METHOD'
Llamar "$cw->atributo(valor)"

Este es el caso más general. Simplemente tenga un método de la clase compuesta con el mismo nombre que el atributo. El método puede hacer cualquier validación y tener los efectos secundarios que desee. (Probablemente valga la pena 'poner en cola' usando afterIdle para efectos secundarios más complejos).

'PASSIVE'
Simplemente almacena el valor en "$composite->{Configure}{-atributo}".

Esta forma también es un marcador útil para atributos que actualmente solo maneja en tiempo de creación.

'SELF'
Aplicar configure al widget principal (por ejemplo, Frame) que es la base del compuesto. (Este es el comportamiento predeterminado para la mayoría de los atributos, lo que hace que un simple Frame se comporte como se esperaría). Tenga en cuenta que una vez que haya especificado ConfigSpecs para un atributo, debe incluir explícitamente 'SELF' en la lista si desea que el atributo se aplique al compuesto mismo (esto evita problemas de recursión infinita difíciles).
$referencia (bendecida)
Llamar $referencia->configure(-atributo => valor)

Un caso común es donde $referencia es un subwidget.

$referencia también puede ser el resultado de

Tk::Config->new(metodoSet,metodoGet,args,...);

La clase Tk::Config se utiliza para implementar todos los tipos de palabra clave anteriores. La clase tiene métodos "configure" y "cget", por lo que permite al código de nivel superior llamar *siempre* a uno de esos métodos en un *objeto* de algún tipo.

referencia hash
Definición: 
$cw->ConfigSpecs(
        ...
        -opcion => [ { -opcionX=>$w1, -opcionY=>[$w2, $w3] },
                        nombrebd clasebd predeterminado ],
        ...
        );

Entonces, "$cw->configure(-opcion => valor)" realmente hace:

$w1->configure(-opcionX => valor);
$w2->configure(-opcionY => valor);
$w3->configure(-opcionY => valor);
'otraCadena'
Llamar 
$composite->Subwidget('otraCadena')->configure( -atributo => valor );

Aunque esto está aquí por compatibilidad con versiones anteriores de Tk-b5, probablemente sea mejor usar directamente la referencia del subwidget. El único caso para conservar esta forma es permitir una capa adicional de abstracción: tal vez tener un subwidget 'actual'; esto no está probado.

Alias
"ConfigSpecs( -alias => '-otroAtributo' )" se utiliza para hacer que "-alias" sea equivalente a "-otroAtributo". Por ejemplo, los alias 
-fg => '-foreground',
-bg => '-background'

se proporcionan automáticamente (si no se especifican ya).

Delegación de todas las opciones de una clase de widget a un subwidget

$composite->ConfigSpecs($subwidget->ConfigSpecs);

Lo anterior genera una lista de argumentos de ConfigSpecs del *compuesto*, uno por cada opción válida en la clase de $subwidget, y delega dicha opción a $subwidget. Ver Tk::Widget y los ConfigSpecs del método *widget*. Duplicar las claves de ConfigSpecs del *compuesto* y del *widget* dará como resultado un comportamiento indefinido.

Valores predeterminados

Cuando el método Populate regresa, se llama a ConfigDefault.

$composite->ConfigSpecs;

(sin argumentos) para devolver una referencia a un hash. Las entradas en el hash tienen el formato:

'-atributo' => [ donde, nombreBD, claseBD, predeterminado ]

ConfigDefault ignora completamente 'donde' (y también la entrada PREDETERMINADO) y verifica la base de datos de 'opciones' en nombre del widget, y si hay una entrada que coincida con nombreBD/claseBD

-atributo => valor

se agrega a la lista de opciones que new aplicará eventualmente al widget. De manera similar, si no hay una coincidencia y se define un predeterminado, se agregará este valor predeterminado.

Las entradas de alias en el hash se utilizan para convertir los valores especificados por el usuario para el alias en valores para el atributo real.

Configure en tiempo de New()

Una vez que el control regresa a new, la lista de opciones suministradas por el usuario, aumentadas por las de ConfigDefault, se aplican al widget utilizando el método configure a continuación.

Los widgets son más flexibles y más parecidos a Tk si manejan la mayoría de sus atributos de esta manera.

Configuración de compuestos

Una vez que ocurren los pasos anteriores, las llamadas de la forma:

$composite->configure( -atributo => valor );

deberían comportarse como cualquier otro widget en lo que respecta al código del usuario final. configure será manejado por Tk::Derived::configure de la siguiente manera:

$composite->ConfigSpecs;

se llama (sin argumentos) para devolver una referencia a un hash. Se busca -atributo en este hash, si -atributo no está presente en el hash, entonces se busca 'PREDETERMINADO' en su lugar. (También se prueban los alias y provocan la redirección al atributo aliased). El resultado debería ser una referencia a una lista como:

[ donde, nombreBD, claseBD, predefa

DESCRIPTION

This is the mechanism by which composite widgets configure their children. It consists of a list of specifications, where each specification is a list of options, and the name of the child widget to which these options should be passed.

The first element of a ConfigSpec can be a list of option names, or the special keyword "where". The second element is the child widget name (or names).

The options specified are mapped to the child widget(s). If the child widget is specified as a list of names, then the options are mapped to all of them. This is handled by Tk::Derived::configure.

If "where" is specified, then it maps to a list of object references, to which the options will be passed. This is intended for use with the "Tix" composite widgets, in particular.

Configuring children

$child->configure( -attribute => value );

is called for each child, where "child" is an element of the list of object references found for "where", and "attribute => value" are the options specified in the ConfigSpec.

Inquiring attributes of composites

$composite->cget( '-attribute' );

This is handled by Tk::Derived::cget in a similar manner to configure. At present if "where" is a list of more than one object it is ignored completely and the "cached" value in

$composite->{Configure}{-attribute}.

is returned.

CAVEATS

The "-background" and "-foreground" option values are automatically propagated down to all composite widget's children. This may be sometimes not desirable, especially if some subwidgets should use own color schemes, either by using explicit options or by option database definitions. If this is the case, then just add

-foreground => 'SELF',
-background => 'SELF',

to "ConfigSpecs".

It is the author's intention to port as many of the "Tix" composite widgets as make sense. The mechanism described above may have to evolve in order to make this possible, although now aliases are handled I think the above is sufficient.
