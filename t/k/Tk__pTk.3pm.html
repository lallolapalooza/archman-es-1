NOMBRE

Tk2portableTk - cómo hacer que tu código fuente de Tk sea portable a otros lenguajes interpretados.

Autor

Ilya Zakharevich <ilya@math.ohio-state.edu> ha contribuido con la mayor parte de este documento. Muchas gracias.

DESCRIPCIÓN

PortableTk es un intento de hacer que Tk sea útil desde otros lenguajes. Actualmente tk4.0 se ejecuta en Perl usando este enfoque. A continuación, Lang es la notación para un lenguaje externo al que PortableTk enlaza el código Tk.

El principal problema al usar código desarrollado para TCL con diferentes lenguajes es la ausencia de tipos de datos: casi todo es "char*". Esto hace que la traducción automática sea inútil. Sin embargo, si "typedef" varios símbolos nuevos como "char*", aún puedes usar tu código en TCL, *y* hará posible la traducción automática.

Otro problema con el enfoque de que "todo es una cadena" es la imposibilidad de tener un resultado que diga "No Aplicable" sin generar un error. Por lo tanto, diferentes comandos de Tk devuelven diferentes valores de cadena que significan "ocurrió un error", como "", " " o "??". Otros lenguajes pueden ser más flexibles, por lo que en portableTk debes informar al compilador qué quieres que signifique el retorno como "error" (ver "Establecimiento de variables").

Actualmente, PortableTk utiliza varios enfoques diferentes para simplificar la traducción: algunas funciones de TCL que son especialmente peligrosas de usar están indefinidas, por lo que puedes encontrar fácilmente lugares que necesiten ser actualizados para usar funciones independientes del lenguaje basadas en advertencias del compilador. Eventualmente, también se proporcionará una forma de usar estas funciones independientes del lenguaje bajo el TCL adecuado. El final de este documento proporciona un punto de partida para dicho proyecto.

Estructura de pTk, portando tu código

pTk, que es un port de Tk, es muy especial con respecto a la portabilidad de otro código a portableTk. El problema es que actualmente hay muy poca esperanza de fusionar las modificaciones de nuevo en Tk, por lo que se necesita una estrategia especial para mantener este port. No utilices esta estrategia para portar tu propio código.

pTk se produce a partir de Tk a través de un proceso de dos pasos: primero, una edición manual (el resultado está en el subdirectorio "mTk"), y segundo, conversión automática por el script "munge" (escrito en Perl). Por lo tanto, el subdirectorio "pTk/mTk" contiene código con la mínima diferencia posible con el código virgen de Tk, por lo que es más fácil fusionar(1) las diferencias entre versiones de Tk en el código modificado.

Parece que la estrategia para un código portable debería ser exactamente la opuesta: comenzando desde código basado en TCL, aplicar "munge", y luego editar manualmente el código resultante. Probablemente también sea posible apuntar tu código a portableTk desde cero, ya que esto permitirá ejecutarlo en una gran cantidad de Languajes.

La única razón por la que alguien querría mirar el contenido del directorio "pTk/mTk" es para averiguar qué construcciones no son compatibles con "munge". Por otro lado, el directorio "pTk" contiene código que cumple con portableTk, por lo que puedes mirar allí para encontrar código de ejemplo.

"munge" es el script que convierte las construcciones más comunes de Tk a su equivalente "portableTk". Para que tu código califique, debes seguir las convenciones de Tk en indentación y nombres de variables, en particular, el array de argumentos para el "...CmdProc" debe llamarse "argv".

Para más detalles sobre lo que "munge" puede hacer, consulta "Traducción de algunas funciones de TCL".

API de PortableTk

Verificando bajo qué se está ejecutando

PortableTk proporciona un símbolo "????". Si este símbolo está definido, tu fuente se compila con él.

Nuevos tipos de opciones de configuración

PortableTk define varios tipos nuevos de opciones de configuración:

TK_CONFIG_CALLBACK
TK_CONFIG_LANGARG
TK_CONFIG_SCALARVAR
TK_CONFIG_HASHVAR
TK_CONFIG_ARRAYVAR
TK_CONFIG_IMAGE

Debes usarlos en lugar de TK_CONFIG_STRING siempre que sea apropiado. Esto permite que tu aplicación reciba una representación directa del recurso correspondiente en lugar de la representación de cadena, si esto es posible en el lenguaje dado.

???? Parece que "TK_CONFIG_IMAGE" y "TK_CONFIG_SCALARVAR" establecen variables de tipo "char*".

Datos del lenguaje

Se definen los siguientes tipos de datos:

"Tcl_Obj *"
es el tipo de dato principal del lenguaje. Este es un tipo al que tu función C recibe punteros para los argumentos cuando se llama a la función de Lang correspondiente. El tipo de configuración correspondiente es "TK_CONFIG_LANGARG".

Este también es un tipo que guarda información sobre el contenido de la variable de Lang.

"Var"
es un sustituto de un "char *" que contiene el nombre de una variable. En Lang es un objeto que contiene una referencia a otra variable de Lang.
"LangResultSave"
????
"LangCallback"
"LangCallback*" un sustituto de un "char *" que contiene el comando a llamar. El tipo de configuración correspondiente es "TK_CONFIG_CALLBACK".
"LangFreeProc"
Es el tipo que establece "Lang_SplitList". Antes de llamarlo, declara 
Args *args;
LangFreeProc *freeProc = NULL;
...
code = Lang_SplitList(interp, value,
    &argc, &args, &freeProc);

Después de usar los valores divididos, llama

if (args != NULL && freeProc) (*freeProc)(argc,args);

No se garantiza que los "args" puedan sobrevivir a la eliminación de "value".

Conversión

Las siguientes macros y funciones se utilizan para la conversión entre cadenas y los tipos adicionales:

LangCallback * LangMakeCallback(Tcl_Obj *)
Tcl_Obj * LangCallbackArg(LangCallback *)
char * LangString(Tcl_Obj *)

Después de usar el resultado de LangCallbackArg(), debes liberarlo con "freeProc" "LANG_DYNAMIC" (no se garantiza que cualquier cambio de "Tcl_Obj *" no se refleje en <LangCallback>, por lo que no puedes hacer LangSet...() en medio, y debes restablecerlo a "NULL" si quieres hacer asignaciones adicionales a este "Tcl_Obj *").

La siguiente función devuelve el "Tcl_Obj *" que es una referencia a "Var":

Tcl_Obj * LangVarArg(Var)

???? Es muy poco intuitivo, espero que el nombre cambie.

int LangCmpCallback(LangCallback *a,Tcl_Obj * b)

(actualmente solo una rutina de prueba), y, por último,

LangCallback * LangCopyCallback(LangCallback *)

NAME

pTk - API for producing Tcl_Obj*'s.

Author

Jan.Peter.Loh.Jr. <jploh@yahoo.com>

DESCRIPTION

This API produces Tcl_Obj*'s. In TCL, these are references to the value of a variable, or to the value produced by an expression. In other languages, these are pointers to objects which hold values. This API is designed for the case where the language does not support any built-in arbitrary precision arithmetic, and requires that the caller pass to the subroutine a reference to the variable which it should modify. E.g. it is assumed that if you call a function like someFunc(arg), then you have already passed the reference to the variable, and the function is supposed to set the value.

Structure of pTk, porting your code

The API is structured in a manner that is intended to be independent of the language that is producing the Tcl_Obj *s. That is, for the most part, TCL code can be translated directly to C, C++, or any other language, without change. The only exception to this rule is the value of the results. In TCL, the value of a variable is a Tcl_Obj *. In other languages, this may be different.

The API presented below is a set of functions that can be used to create and manage these objects. You should only use these functions, and not the underlying Tcl API directly.

void ListFactoryFinish(ListFactory *)
void ListFactoryFree(ListFactory *)

ListFactory * ListFactoryNewLevel(ListFactory *)
ListFactory * ListFactoryEndLevel(ListFactory *)
void ListFactoryResult(Tcl_Interp *, ListFactory *)

The difference is that a call to "ListFactoryFinish" should precede the actual usage of the value of "ListFactory", and there are two different ways to append an "Tcl_Obj *" to a "ListFactory": ListFactoryAppendCopy() guarantees that the value of "arg" is copied to the list, but ListFactoryAppend() may append to the list a reference to the current value of "arg". If you are not going to change the value of "arg" after appending, the call to ListFactoryAppend may be quicker.

As in TCL, the call to ListFactoryFree() does not free the "ListFactory", only the objects it references.

The functions ListFactoryNewLevel() and ListFactoryEndLevel() return a pointer to a "ListFactory" to fill. The argument of ListFactoryEndLevel() cannot be used after a call to this function.

DStrings

Production of strings are still supported in portableTk.

Accessing "Tcl_Obj *"s

The following functions for getting a value of an "Tcl_Obj *" may be provided:

double LangDouble(Tcl_Obj *)
int LangInt(Tcl_Obj *)
long LangLong(Tcl_Obj *)
int LangIsList(Tcl_Obj * arg)

The function LangIsList() is supported only partially under TCL, since there is no data types. It checks whether there is a space inside the string "arg".

Assigning numbers to "Tcl_Obj *"s

While LangSetDouble() and LangSetInt() are supported ways to assign numbers to assign an integer value to a variable, for the sake of efficiency under TCL it is supposed that the destination of these commands was massaged before the call so it contains a long enough string to sprintf() the numbers inside it. If you are going to immediately use the resulting "Tcl_Obj *", the best way to do this is to declare a buffer in the beginning of a block by

dArgBuffer;

and assign this buffer to the "Tcl_Obj *" by

void LangSetDefaultBuffer(Tcl_Obj * *)

You can also create the buffer(s) manually and assign them using

void LangSetBuffer(Tcl_Obj * *, char *)

This is the only choice if you need to assign numeric values to several "Tcl_Obj *"s simultaneously. The advantage of the first approach is that the above declarations can be made "nop"s in different languages.

Note that if you apply "LangSetDefaultBuffer" to an "Tcl_Obj *" that contains some value, you can create a leak if you do not free that "Tcl_Obj *" first. This is a non-problem in real languages, but can be a trouble in "TCL", unless you use only the above API.

Creating new "Tcl_Obj *"s

The API for creating a new "Tcl_Obj *" is

void LangNewArg(Tcl_Obj * *, LangFreeProc *)

The API for creating a new "Tcl_Obj *" is absent. Just initialize "Tcl_Obj *" to be "NULL", and apply one of "LangSet..." methods.

After you use this "Tcl_Obj *", it should be freed thusly:

"LangFreeArg(arg, freeProc)".

Evaluating a list

Use

int LangArgEval(Tcl_Interp *, Tcl_Obj * arg)

Here "arg" should be a list to evaluate, in particular, the first element should be a "LangCallback" massaged to be an "Tcl_Obj *". The arguments can be send to the subroutine by reference or by value in different languages.

Getting result as "Tcl_Obj *"

Use "Tcl_ArgResult". It is not guaranteed that result survives this operation, so the "Tcl_Obj *" you get should be the only mean to access the data from this moment on. After you use this "Tcl_Obj *", you should free it with "freeProc" "LANG_DYNAMIC" (you can do LangSet...() in between).
