NOMBRE

Tk::bind - Organizar la invocación de callbacks mediante eventos X

SINOPSIS

Recuperar enlaces:

    $widget->bind

    $widget->bind(tag)

    $widget->bind(sequence)

    $widget->bind(tag,sequence)

Asociar y destruir enlaces:

    $widget->bind(sequence,callback)

    $widget->bind(tag,sequence,callback)

DESCRIPCIÓN

El método bind asocia callbacks con eventos X. Si se especifica callback, bind organizará la evaluación de callback siempre que ocurran los eventos dados por sequence en la(s) ventana(s) identificada(s) por $widget o tag. Si callback es una cadena vacía, entonces se destruye el enlace actual para sequence, dejando sequence sin enlazar. En todos los casos en que se proporciona un argumento callback, bind devuelve una cadena vacía.

Si se especifica sequence sin un callback, entonces se devuelve el callback actualmente enlazado a sequence, o se devuelve undef si no hay un enlace para sequence. Si no se especifica ni sequence ni callback, entonces el valor de retorno es una lista cuyos elementos son todas las secuencias para las cuales existen enlaces para tag.

Si no se especifica ningún tag, entonces bind se refiere a $widget. Si se especifica tag, entonces normalmente es un nombre de clase y el bind se refiere a todas las instancias de la clase en la MainWindow asociada con $widget. (Es posible que tag sea otro "objeto widget", pero esta práctica está obsoleta). La función ref de Perl ($object) puede usarse para obtener el nombre de la clase de cualquier objeto. Cada ventana tiene una lista asociada de etiquetas, y un enlace se aplica a una ventana particular si su etiqueta está entre las especificadas para la ventana. Aunque el método bindtags puede usarse para asignar un conjunto arbitrario de etiquetas de enlace a una ventana, las etiquetas de enlace predeterminadas proporcionan el siguiente comportamiento:

Si una etiqueta es el nombre de una ventana interna, el enlace se aplica a esa ventana.

Si la etiqueta es el nombre de una ventana principal (toplevel), el enlace se aplica a la ventana principal y a todas sus ventanas internas.

Si la etiqueta es el nombre de una clase de widgets, como Tk::Button, el enlace se aplica a todos los widgets de esa clase;

Si tag tiene el valor all, el enlace se aplica a todas las ventanas descendientes de la MainWindow de la aplicación.

PATRONES DE EVENTOS

El argumento sequence especifica una secuencia de uno o más patrones de eventos, con espacios opcionales entre los patrones. Cada patrón de evento puede tener una de tres formas. En el caso más simple, es un solo carácter ASCII imprimible, como a o [. El carácter no puede ser un espacio en blanco o el carácter <. Esta forma de patrón coincide con un evento KeyPress para el carácter particular. La segunda forma de patrón es más larga pero más general. Tiene la siguiente sintaxis:

    '<modificador-modificador-tipo-detalle>'

Todo el patrón de evento está rodeado por corchetes angulares y normalmente necesita ser citado, ya que los corchetes angulares son especiales para perl. Dentro de los corchetes angulares hay cero o más modificadores, un tipo de evento y una información adicional (detalle) que identifica un botón o keysym particular. Cualquiera de los campos puede omitirse, siempre que esté presente al menos uno de tipo y detalle. Los campos deben separarse por espacios en blanco o guiones.

La tercera forma de patrón se utiliza para especificar un evento virtual con nombre, definido por el usuario; ver Tk::event para más detalles. Tiene la siguiente sintaxis:

    '<<nombre>>'

Todo el patrón de evento virtual está rodeado por corchetes angulares dobles. Dentro de los corchetes angulares está el nombre definido por el usuario del evento virtual. Los modificadores, como Shift o Control, no se pueden combinar con un evento virtual para modificarlo. Los enlaces en un evento virtual se pueden crear antes de que el evento virtual se defina, y si la definición de un evento virtual cambia dinámicamente, todas las ventanas enlazadas a ese evento virtual responderán inmediatamente a la nueva definición.

MODIFICADORES

Los modificadores consisten en cualquiera de los siguientes valores:

Control        Mod2, M2
Shift          Mod3, M3
Lock           Mod4, M4
Button1, B1    Mod5, M5
Button2, B2    Meta, M
Button3, B3    Alt
Button4, B4    Double
Button5, B5    Triple

Donde aparece más de un valor, separados por comas, los valores son equivalentes. La mayoría de los modificadores tienen los significados obvios de X. Por ejemplo, Button1 requiere que el botón 1 esté presionado cuando ocurre el evento. Para que un enlace coincida con un evento dado, los modificadores en el evento deben incluir todos los especificados en el patrón del evento. Un evento también puede contener modificadores adicionales no especificados en el enlace. Por ejemplo, si el botón 1 se presiona mientras las teclas shift y control están presionadas, el patrón <Control-Button-1> coincidirá con el evento, pero <Mod1-Button-1> no. Si no se especifican modificadores, entonces puede haber cualquier combinación de modificadores en el evento.

Meta y M se refieren a cualquiera de los modificadores M1 a M5 que esté asociado con las teclas meta en el teclado (keysyms Meta_R y Meta_L). Si no hay teclas meta, o si no están asociadas con ningún modificador, entonces Meta y M no coincidirán con ningún evento. De manera similar, el modificador Alt se refiere a cualquier modificador asociado con las teclas alt en el teclado (keysyms Alt_L y Alt_R).

Los modificadores Double, Triple y Quadruple son una conveniencia para especificar dobles clics del ratón y otros eventos repetidos. Causan que un patrón de evento particular se repita 2, 3 o 4 veces, y también imponen un requisito de tiempo y espacio en la secuencia: para que una secuencia de eventos coincida con un patrón Double, Triple o Quadruple, todos los eventos deben ocurrir cerca en el tiempo y sin un movimiento sustancial del ratón entre ellos. Por ejemplo, <Double-Button-1> es equivalente a <Button-1><Button-1> con el requisito adicional de tiempo y espacio.

EVENT PROCESSING DETAILS

When an event occurs, the event specification is checked against the list of bindings associated with the widget. The first binding specification that matches the event is executed. If the binding specification is for a specific widget, its tag list is searched (in order). If a match is found, the associated callback is executed. If no match is found in the widget's tag list, the next specification in the binding list is tried. This continues until a match is found or the list of bindings is exhausted.

The detail field of an event is used in matching. The exact meaning of detail depends on the event type. For example, for a ButtonPress event, detail is the button number that was pressed. For KeyPress and KeyRelease events, detail is the keysym of the key that was pressed or released. For Enter and Leave events, detail indicates why the crossing occurred (e.g., `NotifyNormal`, `NotifyWhileGrabbed`).

It's important to note that the event specification syntax allows for a great deal of flexibility. You can specify events based on their type, modifier keys, button numbers, keysyms, and even the detail field. This allows you to create very specific bindings for different user interactions.

For example, you can bind a callback to the event of pressing the Control key and the 'c' key simultaneously. You can also bind to the release of the left mouse button when the pointer is over a specific widget.

There are also special event types, such as FocusIn and FocusOut, which are triggered when a widget gains or loses keyboard focus. These events are particularly useful for managing widget state and user input validation. However, there are no useful percent substitutions you would make when binding to these events.

MouseWheel

Some mice on the Windows platform support a mouse wheel which is used for scrolling documents without using the scrollbars. By rolling the wheel, the system will generate MouseWheel events that the application can use to scroll. Like Key events the event is always routed to the window that currently has focus. When the event is received you can use the %D substitution to get the delta field for the event which is a integer value of motion that the mouse wheel has moved. The smallest value for which the system will report is defined by the OS. On Windows 95 & 98 machines this value is at least 120 before it is reported. However, higher resolution devices may be available in the future. The sign of the value determines which direction your widget should scroll. Positive values should scroll up and negative values should scroll down.

The last part of a long event specification is detail. In the case of a ButtonPress or ButtonRelease event, it is the number of a button (1-5). If a button number is given, then only an event on that particular button will match; if no button number is given, then an event on any button will match. Note: giving a specific button number is different than specifying a button modifier; in the first case, it refers to a button being pressed or released, while in the second it refers to some other button that is already depressed when the matching event occurs. If a button number is given then type may be omitted: if will default to ButtonPress. For example, the specifier <1> is equivalent to <ButtonPress-1>.

If the event type is KeyPress or KeyRelease, then detail may be specified in the form of an X keysym. Keysyms are textual specifications for particular keys on the keyboard; they include all the alphanumeric ASCII characters (e.g. ``a'' is the keysym for the ASCII character ``a''), plus descriptions for non-alphanumeric characters (``comma'' is the keysym for the comma character), plus descriptions for all the non-ASCII keys on the keyboard (``Shift_L'' is the keysm for the left shift key, and ``F1'' is the keysym for the F1 function key, if it exists). The complete list of keysyms is not presented here; it is available in other X documentation and may vary from system to system. If necessary, you can use the 'K' notation described below to print out the keysym name for a particular key. If a keysym detail is given, then the type field may be omitted; it will default to KeyPress. For example, <Control-comma> is equivalent to <Control-KeyPress-comma>.

BINDING CALLBACKS AND SUBSTITUTIONS

The callback argument to bind is a perl/Tk callback. which will be executed whenever the given event sequence occurs. (See Tk::callbacks for description of the possible forms.) Callback will be associated with the same MainWindow that is associated with the $widget that was used to invoke the bind method, and it will run as though called from MainLoop. If callback contains any Ev(%) calls, then each "nested" Ev(%) "callback" will be evaluated when the event occurs to form arguments to be passed to the main callback. The replacement depends on the character %, as defined in the list below. Unless otherwise indicated, the replacement string is the numeric (decimal) value of the given field from the current event. Perl/Tk has enhanced this mechanism slightly compared to the comparable Tcl/Tk mechanism. The enhancements are not yet all reflected in the list below. Some of the substitutions are only valid for certain types of events; if they are used for other types of events the value substituted is undefined (not the same as undef!).

'#'
The number of the last client request processed by the server (the serial field from the event). Valid for all event types.
'a'
The above field from the event, formatted as a hexadecimal number. Valid only for Configure events.
'b'
The number of the button that was pressed or released. Valid only for ButtonPress and ButtonRelease events.
'c'
The count field from the event. Valid only for Expose events.
'd'
The detail field from the event. The 'd' is replaced by a string identifying the detail. For Enter, Leave, FocusIn, and FocusOut events, the string will be one of the following: 
NotifyAncestor          NotifyNonlinearVirtual
NotifyDetailNone        NotifyPointer
NotifyInferior          NotifyPointerRoot
NotifyNonlinear         NotifyVirtual

For ConfigureRequest events, the string will be one of:

Above                   Opposite
Below                   None
BottomIf                TopIf

For events other than these, the substituted string is undefined. (Note that this is not the same as Detail part of sequence use to specify the event.)

'f'
The focus field from the event (0 or 1). Valid only for Enter and Leave events.
'h'
The height field from the event. Valid only for Configure, ConfigureRequest, Create, Expose, and ResizeRequest events.
'i'
The window field from the event, represented as a hexadecimal integer.
'k'
The keycode field from the event. Valid only for KeyPress and KeyRelease events.
'm'
The mode field from the event. The substituted string is one of NotifyNormal, NotifyGrab, NotifyUngrab, or NotifyWhileGrabbed. Valid only for Enter, FocusIn, FocusOut, and Leave events.
'o'
The override_redirect field from the event. Valid only for Map, Reparent, and Configure events.
'p'
The place field from the event, substituted as one of the strings PlaceOnTop or PlaceOnBottom. Valid only for Circulate and CirculateRequest events.
's'
The state field from the event. For ButtonPress, ButtonRelease, Enter, KeyPress, KeyRelease, Leave, and Motion events, a decimal string is substituted. For Visibility, one of the strings VisibilityUnobscured, VisibilityPartiallyObscured, and VisibilityFullyObscured is substituted.
't'
The time field from the event. Valid only for events that contain a time field.
'w'
The width field from the event. Valid only for Configure, ConfigueRequest, Create, Expose, and ResizeREquest events.
'x'
The x field from the event. Valid only for events containing an x field.
'y'
The y field from the event. Valid only for events containing a y field.
'@'
The string "@x,y" where x and y are as above. Valid only for events containing x and y fields. This format is used my methods of Tk::Text and similar widgets.
'A'
Substitutes the UNICODE character corresponding to the event, or the empty string if the event doesn't correspond to a UNICODE character (e.g. the shift key was pressed). XmbLookupString does all the work of translating from the event to a UNICODE character. Valid only for KeyPress and KeyRelease events.
'B'
The border_width field from the event. Valid only for Configure, ConfigureRequest and Create events.
'D'
This reports the delta value of a MouseWheel event. The delta value represents the rotation units the mouse wheel has been moved. On Windows 95 & 98 systems the smallest value for the delta is 120. Future systems may support higher resolution values for the delta. The sign of the value represents the direction the mouse wheel was scrolled.
'E'
The send_event field from the event. Valid for all event types.
'K'
The keysym corresponding to the event, substituted as a textual string. Valid only for KeyPress and KeyRelease events.
'N'
The keysym corresponding to the event, substituted as a decimal number. Valid only for KeyPress and KeyRelease events.
'R'
The root window identifier from the event. Valid only for events containing a root field.
'S'
The subwindow window identifier from the event, as an object if it is one otherwise as a hexadecimal number. Valid only for events containing a subwindow field.
'T'
The type field from the event. Valid for all event types.
'W'
The window to which the event was reported (the $widget field from the event) - as an perl/Tk object. Valid for all event types.
'X'
The x_root field from the event. If a virtual-root window manager is being used then the substituted value is the corresponding x-coordinate in the virtual root. Valid only for ButtonPress, ButtonRelease, KeyPress, KeyRelease, and Motion events.
'Y'
The y_root field from the event. If a virtual-root window manager is being used then the substituted value is the corresponding y-coordinate in the virtual root. Valid only for ButtonPress, ButtonRelease, KeyPress, KeyRelease, and Motion events.

MULTIPLE MATCHES

It is possible for several bindings to match a given X event. If the bindings are associated with different tag's, then each of the bindings will be executed, in order. By default, a class binding will be executed first, followed by a binding for the widget, a binding for its toplevel, and an all binding. The bindtags method may be used to change this order for a particular window or to associate additional binding tags with the window.

return and Tk->break may be used inside a callback to stop further processing of the event. This is particularly useful when you have multiple bindings that could potentially match an event, and you only want one of them to be executed.

Tk::bind(3pm)

NAME

Tk::bind - Bind callbacks to events

SYNOPSIS

    $widget->bind(
        PATTERN,
        CALLBACK,
        ...
    );
    $widget->bind(
        PATTERN,
        undef,
        ...
    );

DESCRIPTION

The bind method associates a Perl callback (a subroutine reference or a string containing Perl code) with an event pattern. When an event matching the pattern occurs for the widget, the callback is invoked. This is the primary mechanism for handling user interactions with Tk widgets. The PATTERN specifies the event, and the CALLBACK is the code to execute when the event occurs. You can have multiple PATTERN/CALLBACK pairs in a single call to bind. If CALLBACK is undef, then any existing bindings for PATTERN are removed.

The PATTERN syntax is described in the Tk::event manpage (see “EVENT PATTERNS”). Bindings are inherited from parent widgets. If a widget does not have a binding for a particular event, Tk will search up the widget hierarchy. This means that you can define bindings on the main window, and they will apply to all widgets within it unless overridden by a widget-specific binding.

The CALLBACK is a subroutine reference or a string containing Perl code. The callback will be invoked with the event information. If the callback is a string, it will be evaluated in the context of the widget. The callback receives the event object as its argument. The event object is a blessed array reference, whose elements can be accessed using array indexing. The callback may also be invoked with named arguments. See “BINDING CALLBACKS AND SUBSTITUTIONS” for more details.

A widget can have multiple bindings for the same event pattern. When an event occurs, Tk will search through the bindings associated with the widget's tags (including the widget itself). The most specific matching binding will be chosen and its callback invoked. If multiple bindings have the same specificity, the most recently registered binding will be chosen.

EVENT PATTERNS

An event pattern is a string that describes a sequence of events. The simplest pattern is a single event, such as <Button-1> (mouse button 1 click) or <KeyPress-a> (the 'a' key is pressed). More complex patterns can describe sequences of events, such as <Double-ButtonPress-1> (button 1 pressed twice quickly) or <a <Shift-b>> (press 'a', then press Shift-b). See Tk::event for a full description of event patterns.

MODIFIERS

Event patterns can include modifiers such as Shift-, Control-, and Alt-. For example, <Shift-KeyPress-a> matches pressing the 'a' key while the Shift key is held down. A modifier can be any of the following: Shift, Lock, Control, Alt, Meta, Super, Hyper.

EVENT TYPES

The main event types are:

ButtonPress
A mouse button is pressed.
ButtonRelease
A mouse button is released.
Motion
The mouse pointer moves.
KeyPress
A keyboard key is pressed.
KeyRelease
A keyboard key is released.
Enter
The mouse pointer enters the widget.
Leave
The mouse pointer leaves the widget.
Virtual
A virtual event (e.g., <<Paste>>).

These can be combined with button numbers (1, 2, 3, etc.) and key symbols (e.g., a, Return, Escape).

BINDING CALLBACKS AND SUBSTITUTIONS

When a callback is invoked, it receives the event object as its first argument. This object is a blessed array reference containing event- specific information. In addition, certain substitutions are performed on the callback string before it is evaluated. These substitutions are similar to those used in Tk's message command.

    %W    Widget name
    %w    Widget path name
    %X    X coordinate of the event
    %Y    Y coordinate of the event
    %x    X coordinate relative to the widget
    %y    Y coordinate relative to the widget
    %t    Event type (e.g., "ButtonPress")
    %T    Event detail (e.g., "1" for ButtonPress-1)
    %k    Keysym for KeyPress/KeyRelease
    %K    Keycode for KeyPress/KeyRelease
    %%    A literal "%"

If the callback is a subroutine reference, it is called directly, and no substitutions are performed. The event object is passed as the first argument to the subroutine.

Example:

    $button->bind('<ButtonPress-1>', sub {
        my ($event) = @_;
        print "Button 1 pressed at $event->{x}, $event->{y}\n";
    });
    $button->bind('<KeyPress-a>', q{
        print "Key 'a' pressed in widget %W\n";
    });

MULTIPLE MATCHES

If multiple bindings match an event, Tk processes them in a specific order. Bindings are associated with the widget's tags. Tk searches for the most specific matching tag sequence. The order of tag lookup is: virtual events, then the widget itself, then its parent tags, and so on, up to the toplevel window.

Within a single tag, if multiple event patterns match, the most specific pattern is chosen. Specificity is determined by the following criteria, in order:

  1. A pattern specifying a specific button or key is more specific than one that doesn't.
  2. A longer event sequence is more specific than a shorter one.
  3. If the modifiers in one pattern are a subset of the modifiers in another, the pattern with more modifiers is more specific.
  4. A virtual event pattern is less specific than a physical event pattern that matches the same sequence.

If these criteria do not determine a unique winner, the most recently registered binding is chosen.

If a callback is invoked, and it executes return, then the current callback is terminated, but Tk will continue processing callbacks associated with other tags. If Tk->break is invoked within a callback, then that callback terminates, and no other callbacks will be invoked for the event. (Tk->break is implemented using Perl's die with a special value that is caught by the Perl/Tk "glue" code.)

If more than one binding matches a particular event and they have the same tag, then the most specific binding is chosen and its callback is evaluated. The following tests are applied, in order, to determine which of several matching sequences is more specific: (a) an event pattern that specifies a specific button or key is more specific than one that doesn't; (b) a longer sequence (in terms of number of events matched) is more specific than a shorter sequence; (c) if the modifiers specified in one pattern are a subset of the modifiers in another pattern, then the pattern with more modifiers is more specific. (d) a virtual event whose physical pattern matches the sequence is less specific than the same physical pattern that is not associated with a virtual event. (e) given a sequence that matches two or more virtual events, one of the virtual events will be chosen, but the order is undefined.

If the matching sequences contain more than one event, then tests (c)-(e) are applied in order from the most recent event to the least recent event in the sequences. If these tests fail to determine a winner, then the most recently registered sequence is the winner.

If there are two (or more) virtual events that are both triggered by the same sequence, and both of those virtual events are bound to the same window tag, then only one of the virtual events will be triggered, and it will be picked at random:

$widget->eventAdd('<<Paste>>' => '<Control-y>');
$widget->eventAdd('<<Paste>>' => '<Button-2>');
$widget->eventAdd('<<Scroll>>' => '<Button-2>');
$widget->bind('Tk::Entry','<<Paste>>',sub { print 'Paste'});
$widget->bind('Tk::Entry','<<Scroll>>', sub {print 'Scroll'});

If the user types Control-y, the <<Paste>> binding will be invoked, but if the user presses button 2 then one of either the <<Paste>> or the <<Scroll>> bindings will be invoked, but exactly which one gets invoked is undefined.

If an X event does not match any of the existing bindings, then the event is ignored. An unbound event is not considered to be an error.

MULTI-EVENT SEQUENCES AND IGNORED EVENTS

When a sequence specified in a bind method contains more than one event pattern, then its callback is executed whenever the recent events (leading up to and including the current event) match the given sequence. This means, for example, that if button 1 is clicked repeatedly the sequence <Double-ButtonPress-1> will match each button press but the first. If extraneous events that would prevent a match occur in the middle of an event sequence then the extraneous events are ignored unless they are KeyPress or ButtonPress events. For example, <Double-ButtonPress-1> will match a sequence of presses of button 1, even though there will be ButtonRelease events (and possibly Motion events) between the ButtonPress events. Furthermore, a KeyPress event may be preceded by any number of other KeyPress events for modifier keys without the modifier keys preventing a match. For example, the event sequence aB will match a press of the a key, a release of the a key, a press of the Shift key, and a press of the b key: the press of Shift is ignored because it is a modifier key. Finally, if several Motion events occur in a row, only the last one is used for purposes of matching binding sequences.

ERRORS

If an error occurs in executing the callback for a binding then the Tk::Error mechanism is used to report the error. The Tk::Error mechanism will be executed at same call level, and associated with the same MainWindow as as the callback was invoked.

CAVEATS

Note that for the Canvas widget, the call to bind has to be fully qualified. This is because there is already a bind method for the Canvas widget, which binds individual canvas tags.

    $canvas->Tk::bind
