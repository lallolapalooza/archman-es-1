NOMBRE

Tk::send - Ejecutar un comando en una aplicación diferente

SINOPSIS

    $resultado = $widget->send(?opciones,?app=>cmd?arg arg ...?)

DESCRIPCIÓN

Este método organiza la ejecución de cmd (y args) para ser 'enviado' a la aplicación nombrada por app. Devuelve el resultado o un error (por lo tanto, lo anterior debería ser 'envuelto' en eval{} y se debería probar $@). App puede ser el nombre de cualquier aplicación cuya ventana principal esté en la pantalla que contiene la ventana principal del remitente; no necesita estar dentro del mismo proceso. Si no hay argumentos arg presentes, la cadena a enviar está contenida enteramente dentro del argumento cmd. Si hay uno o más args presentes, se concatenan separados por espacios en blanco para formar la cadena a enviar.

Si los argumentos iniciales de la llamada comienzan con `-' se tratan como opciones. Actualmente se definen las siguientes opciones:

-async
Solicita invocación asíncrona. En este caso, el comando send se completará inmediatamente sin esperar a que cmd se complete en la aplicación de destino; no habrá resultado disponible y se ignorarán los errores en el comando enviado. Si la aplicación de destino está en el mismo proceso que la aplicación remitente, la opción -async se ignora.
--
No tiene ningún propósito más que terminar la lista de opciones. Esta opción solo es necesaria si app podría contener un carácter `-' inicial.

NOMBRES DE APLICACIONES

El nombre de una aplicación se establece inicialmente a partir del nombre del programa o script que creó la aplicación. Puede consultar y cambiar el nombre de una aplicación con el método appname.

¿QUÉ ES UN ENVÍO?

El mecanismo send fue diseñado para permitir que las aplicaciones Tcl/Tk se enviaran Scripts Tcl entre sí. Esto no se mapea muy bien a perl/Tk. Perl/Tk "envía" una cadena a app; lo que sucede como resultado de esto depende de la aplicación receptora. Si la otra aplicación es una aplicación Tcl/Tk4.*, se tratará como un Script Tcl. Si la aplicación "otra" es una aplicación perl/Tk (incluyendo envíos a sí misma), la cadena se pasa como argumento a una llamada de método de la siguiente forma:

$ventanamain->Receive(cadena);

Existe un Tk::Receive predeterminado (AutoLoaded) que devuelve un error a la aplicación remitente. Una aplicación en particular puede definir su propio método Receive en cualquier clase del árbol de herencia de MainWindow para hacer lo que considere conveniente. Por ejemplo, podría eval la cadena, posiblemente en un "compartimento" Safe.

Si una aplicación Tcl/Tk "envía" algo a una aplicación perl/Tk, la aplicación perl/Tk tendría que intentar interpretar la cadena entrante como un script Tcl. Casos simples no deberían ser demasiado difíciles de emular (dividir por espacios en blanco y tratar el primer elemento como "comando" y los otros elementos como argumentos).

SEGURIDAD

El comando send es potencialmente una grave falla de seguridad, ya que cualquier aplicación que pueda conectarse a su servidor X puede enviar scripts a sus aplicaciones. Por lo tanto, el comportamiento predeterminado descrito anteriormente. (Con la disponibilidad de Safe, podría tener sentido relajar un poco el comportamiento predeterminado).

El eval sin supervisión de estos "scripts" entrantes puede hacer que perl lea y escriba archivos e invoque subprocesos en su nombre. El control de acceso basado en host, como el proporcionado por xhost, es particularmente inseguro, ya que permite que cualquier persona con una cuenta en hosts específicos se conecte a su servidor, y si se deshabilita, permite que cualquiera desde cualquier lugar se conecte a su servidor. Para proporcionar al menos una pequeña cantidad de seguridad, Tk central verifica el control de acceso que está utilizando el servidor y rechaza los envíos entrantes a menos que (a) el control de acceso tipo xhost esté habilitado (es decir, solo ciertos hosts pueden establecer conexiones) y (b) la lista de hosts habilitados esté vacía. Esto significa que las aplicaciones no pueden conectarse a su servidor a menos que utilicen alguna otra forma de autorización, como la proporcionada por xauth.

VEA TAMBIÉN

"eval" en perlfunc, Safe, pautas de seguridad corporativa/del administrador del sistema, etc.
