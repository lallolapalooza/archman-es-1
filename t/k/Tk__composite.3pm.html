Tk::composite - Definición de una nueva clase de widget compuesto

SINOPSIS

 package Tk::MiNuevoWidget;
 use Tk::widgets qw/ lista de widgets Tk /;
 use base qw/ Tk::Frame /;    # o Tk::Toplevel
 Construct Tk::Widget 'MiNuevoWidget';
 sub ClassInit {
     my( $class, $mw ) = @_;
     #... p.ej., enlaces de clase aquí ...
     $class->SUPER::ClassInit( $mw );
 }
 sub Populate {
     my( $self, $args ) = @_;
     my $flag = delete $args->{-flag};
     if( defined $flag ) {
         # manejar -flag => xxx que solo se puede hacer al crear
         # el tiempo de delete arriba asegura que new() no intente
         # y haga $self->configure( -flag => xxx );
     }
     $self->SUPER::Populate( $args );
     $self = $self->Component( ... );
     $self->Delegates( ... );
     $self->ConfigSpecs(
         '-cursor'    => [ SELF, 'cursor', 'Cursor',   undef ],
         '-something' => [ METHOD, dbName,  dbClass, default ],
         '-text'      => [ $label, dbName,  dbClass, default ],
         '-heading'   => [ {-text => $head},
                             heading, Heading,  'Mi Encabezado' ],
    );
}
sub something {
    my( $self, $value) = @_;
    if ( @_ > 1 ) {
       # establecerlo
    }
    return # valor actual
}
1;

DESCRIPCIÓN

La intención detrás de un compuesto es crear un widget de nivel superior, a veces llamado "super-widget" o "mega-widget". La mayoría de las veces, un compuesto se construirá sobre otros widgets usándolos, en lugar de especializarse en ellos. Por ejemplo, el widget compuesto suministrado LabEntry está *hecho de* un Entry y un Label; no es *un tipo de* Label ni *un tipo de* Entry.

La mayor parte del trabajo de un widget compuesto consiste en crear sub-widgets, organizar el despacho de opciones de configuración a los sub-widgets adecuados y administrar las opciones de configuración específicas del compuesto.

DETALLES DE GLORIA

Dependiendo de tu conocimiento de Perl/Tk, esta sección puede ser iluminadora o confusa.

Widget Compuesto

Dado que Perl/Tk utiliza en gran medida un enfoque orientado a objetos, no es de extrañar que la creación de un compuesto pase por un método new(). Sin embargo, el compuesto normalmente no define un método new() en sí mismo: normalmente es suficiente con heredar de Tk::Widget.

Esto es lo que sucede cuando el compuesto usa

use base qw/ Tk::Frame /;  # o Tk::Toplevel

para especificar su cadena de herencia. Para completar la inicialización del widget, debe llamar al método Construct de la clase Widget. Ese método acepta el nombre de la nueva clase a crear, es decir, el nombre del paquete de su widget compuesto:

Construct Tk::Widget 'MiNuevoWidget';

Aquí, MiNuevoWidget es el nombre del paquete (también conocido como la clase del widget). Esto definirá un método constructor para MiNuevoWidget, que normalmente se llama como la clase del widget. Instanciar ese compuesto en el código del cliente se vería así:

$mw = MainWindow->new;       # crea una ventana principal de nivel superior
$self = $mw->MiNuevoWidget();  # crea una instancia del
                             # widget compuesto MiNuevoWidget

Cada vez que se instancia un compuesto en el código del cliente, se invocará Tk::Widget::new() a través del constructor de clase del widget. Ese método new llamará a

$self->Populate(\%args);

donde %args son los argumentos pasados al constructor del widget. Ten en cuenta que Populate recibe una referencia al array hash que contiene todos los argumentos.

Populate generalmente se define en la clase (paquete) compuesta, que crea los sub-widgets característicos de la clase.

Creación de Sub-widgets

La creación de sub-widgets suele ocurrir en Populate(). El compuesto suele llamar al método constructor del sub-widget directamente, para sub-widgets "privados", o indirectamente a través del método Component para sub-widgets que deben ser publicitados a los clientes.

Populate puede llamar a Delegates para dirigir las llamadas a los métodos de sub-widgets elegidos. Para compuestos simples, típicamente la mayoría, si no todos los métodos, se dirigen a un único sub-widget: por ejemplo, ScrListbox dirige todos los métodos al Listbox principal, de modo que las llamadas a $composite->get(...) realicen $listbox->get(...).

Definición de opciones de mega-widget

Populate también debe llamar a ConfigSpecs() para especificar la forma en que se deben manejar las opciones similares a configure en el compuesto. Una vez que Populate retorna, el método Tk::Frame::ConfigDefault recorre las entradas de ConfigSpecs y rellena el hash %$args con los valores predeterminados para las opciones de los recursos X (.Xdefaults, etc.).

Cuando Populate retorna a Tk::Widget::new(), se realiza una llamada a $self->configure(%$args), que establece *todas* las opciones.
