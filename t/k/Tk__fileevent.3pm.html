fileevent(3) Documentación de Perl aportada por el usuario fileevent(3)

NOMBRE

Tk::fileevent - Ejecutar una llamada de retorno cuando un manejador de archivos esté listo para leer o escribir

SINOPSIS

$widget->fileevent(fileHandle,readable?,callback?)

$widget->fileevent(fileHandle,writable?,callback?)

DESCRIPCIÓN

Este comando se utiliza para crear manejadores de eventos de archivo. Un manejador de eventos de archivo es una vinculación entre un manejador de archivos y una llamada de retorno, de modo que la llamada de retorno se evalúa cada vez que el manejador de archivos está listo para leer o escribir. Los manejadores de eventos de archivo se utilizan comúnmente para permitir que los datos se reciban de otro proceso de forma basada en eventos, de modo que el receptor pueda continuar interactuando con el usuario mientras espera que lleguen los datos. Si una aplicación invoca "<>", "sysread" o "read" en un manejador de archivos bloqueante cuando no hay datos de entrada disponibles, el proceso se bloqueará; hasta que lleguen los datos de entrada, no podrá atender otros eventos, por lo que parecerá que el usuario se ``congeló''. Con fileevent, el proceso puede saber cuándo hay datos disponibles e invocar gets o read solo cuando no se bloquearán.

El argumento fileHandle para fileevent se refiere a un manejador de archivos abierto, como el valor de retorno de un comando open o socket anterior. Si se especifica el argumento callback, entonces fileevent crea un nuevo manejador de eventos: callback se evaluará cada vez que el manejador de archivos esté listo para leer o escribir (dependiendo del argumento de fileevent). En este caso, fileevent devuelve una cadena vacía. Los manejadores de eventos readable y writable para un archivo son independientes y pueden crearse y eliminarse por separado. Sin embargo, puede haber como máximo un manejador readable y uno writable para un archivo en un momento dado en un intérprete determinado. Si se llama a fileevent cuando el manejador especificado ya existe en el intérprete invocador, la nueva llamada de retorno reemplaza a la antigua.

Si no se especifica el argumento callback, fileevent devuelve la llamada de retorno actual para fileHandle, o una cadena vacía si no hay ninguna. Si el argumento callback se especifica como una cadena vacía, el manejador de eventos se elimina, de modo que no se invocará ninguna llamada de retorno. Un manejador de eventos de archivo también se elimina automáticamente cada vez que se cierra su manejador de archivos o se elimina su intérprete.

Un manejador de archivos se considera legible si hay datos sin leer disponibles en el dispositivo subyacente. Un manejador de archivos también se considera legible si hay una condición de fin de archivo o error en el archivo o dispositivo subyacente. Es importante que callback verifique estas condiciones y las maneje adecuadamente; por ejemplo, si no hay una verificación especial para el fin de archivo, puede ocurrir un bucle infinito en el que callback no lee datos, regresa y se invoca nuevamente de inmediato.

Un manejador de archivos se considera escribible si se puede escribir al menos un byte de datos en el archivo o dispositivo subyacente sin bloquear, o si hay una condición de error en el archivo o dispositivo subyacente.

La E/S basada en eventos funciona mejor para manejadores de archivos que se han puesto en modo no bloqueante. En modo bloqueante, un comando "print" puede bloquearse si le das más datos de los que el archivo o dispositivo subyacente puede aceptar, y un comando "<>", "sysread" o "read" se bloqueará si intentas leer más datos de los que están listos; no se procesarán eventos mientras los comandos se bloquean. En modo no bloqueante, "print", "<>", "sysread" y "read" nunca se bloquean. Consulte la documentación de los comandos individuales para obtener información sobre cómo manejan los manejadores de archivos bloqueantes y no bloqueantes.

La llamada de retorno para un evento de archivo se ejecuta en el contexto de $widget con el que se invocó fileevent. Si ocurre un error al ejecutar la llamada de retorno, se utiliza el mecanismo de error de Tk::Error para informar el error. Además, el manejador de eventos de archivo se elimina si alguna vez devuelve un error; esto se hace para evitar bucles infinitos debido a manejadores defectuosos.

ERRORES

En las plataformas de Windows, fileevent está limitado en los tipos de manejadores de archivos que se comportan correctamente. La puesta de los manejadores de archivos en modo no bloqueante solo se implementa en un subconjunto de plataformas UNIX (ver Tk::IO).

CRÉDITOS

fileevent se basa en el comando addinput creado por Mark Diekhans.
