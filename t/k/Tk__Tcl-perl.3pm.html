Tcl-perl(3) Documentación de Perl contribuida por el usuario Tcl-perl(3)

NOMBRE

Tcl vs perl - documentación sospechosa muy antigua sobre la portabilidad.

DESCRIPCIÓN

Esto no es realmente un .pod todavía, ni es Tcl vs perl, es una copia de la comparación de John del puerto original de perl/Tk de Malcolm con el actual. También está desactualizado en algunos lugares.

De: john@WPI.EDU (John Stoffel )
Aquí hay algunas reflexiones sobre la nueva extensión Tk y cómo creo que se
organizan los comandos. En su mayoría, estoy contento con ella, hace algunas
cosas más organizadas y más consistentes con tcl/tk, pero dado que el
lenguaje subyacente es tan diferente, no creo que necesitemos seguir
exactamente el modelo de tcl/tk para llamar al lenguaje.
La estructura básica del programa Tk es:
    require Tk;
    $top = MainWindow->new();
    #
    # crear widgets
    #
    Tk::MainLoop;
    sub method1 {
    }
    sub methodN {
    }
Esto es bastante similar a tkperl5a5, con algunos cambios cosméticos de
nomenclatura y algunos cambios más útiles en el nombre y uso del comando.
Una comparación rápida en ningún orden particular sigue:
tkperl5a5                             Tk
-------------------------------       -----------------------------------
$top=tkinit(name,display,sync);       $top=MainWindow->new();
tkpack $w, ... ;              $w->pack(...)
$w = Class::new($top, ...);   $w = $top->Class(...);
tkmainloop;                   Tk::MainLoop;
tkbind($w,"<key>",sub);               $w->bind("<key>",sub);
tkdelete($w, ...);            $w->delete(...);
$w->scanmark(...);            $w->scan("mark", ...);
$w->scandragto(...);          $w->scan("dragto", ...);
$w->tkselect();                       $w->Select();
$w->selectadjust(...);                $w->selection("adjust", ...);
$w->selectto(...);            $w->selection("to", ...);
$w->selectfrom(...);          $w->selection("from", ...);
$w->tkindex(...);             $w->index(...);
tclcmd("xxx",...);              &Tk::xxx(...)    # todos los comandos Tk, pero nada de Tcl
tclcmd("winfo", xxx, $w, ...);  $w->xxx(...);
                              $w->mark(...);
                              $w->tag(...);
$w->grabstatus();             $w->grab("status");
$w->grabrelease(...);         $w->grab("release", ...);
focus($w);                    $w->focus;
update();                     Tk->update();
idletasks();                  Tk->update("idletasks");
wm("cmd",$w, ...);            $w->cmd(...);
destroy($w);                  $w->destroy();
                              Tk::option(...);
                                $w->OptionGet(name,Class)
                              $w->place(...)
                              Tk::property(...);
$w = Entry::new($parent,...)
es ahora
$w = $parent->Entry(...)
Como esto permite que new se herede de una clase Window.
  -method=>x,-slave=>y
es ahora
  -command => [x,y]
el primer elemento de la lista se trata como "method" si y es una referencia de objeto.
(También puedes tener -command => [a,b,c,d,e]; b..e se pasan como argumentos).
Las referencias a objetos son ahora hashes en lugar de escalares y
solo hay uno de esos por ventana. Tcl_CmdInfo y PathName son entradas
en el hash.
(Esto permite que las clases derivadas
re-bendigan el hash y guarden sus propias cosas en él también).
El "Tcl_Interp" de Tk es de hecho una referencia a la ventana "." .
Puedes encontrar todas las ventanas de Tk descendientes de él a medida que se
añaden sus referencias de objeto (por PathName) a este hash.
$w->MainWindow devuelve este hash desde cualquier ventana.
Creo que debería extenderse a múltiples tkinits / Tk->news
con diferentes Displays, si el código Tk lo hace.
Finalmente, "bind" pasa la ventana como argumento "extra" (o único).
Por lo tanto:
Tk::Button->bind(<Any-Enter>,"Enter");
Vincula los eventos Enter a Tk::Button::Enter por defecto
pero se llama como $w->Enter para que la clase derivada de Button pueda simplemente
definir su propio método Enter. Ya no se necesitan &EvWref ni los globales
asociados ni las condiciones de carrera.
Una cosa a tener en cuenta: los comandos vinculados a eventos con $widget->bind
siguen el mismo patrón, pero reciben argumentos adicionales:
$widget->bind(<Any-1>,[sub {print shift}, $one, $two ]);
Cuando se llama a sub, tiene:
   $widget $one $two
pasados.
El primer argumento extra es una referencia al hash por widget que sirve como el
objeto perl para el widget.
Cada vez que un XEvent, una referencia a una clase especial se coloca
en el hash del widget. Se puede recuperar mediante el método $w->XEvent.
Los métodos de la clase XEvent son los
caracteres especiales % de Tcl/Tk.
Así:
$widget->bind(<Any-KeyPress>,
              sub {
               my $w = shift;
               my $e = $w->XEvent;
               print $w->PathName," ",$e->A," presionado ,$e->xy,"\n");
              });
XEvent->xy es un caso especial que devuelve "@" . $e->x . "," . $e->y
que es común en el paquete Text.
Debido a que se pasa un hash de widget bendecido a las subs "bound", estas pueden ser
vinculadas a métodos (posiblemente heredados) de la clase del widget:
Class->bind(<Any-Down>,Down);
sub Class::Down
{
 my $w = shift;
 # manejar la flecha hacia abajo
}
Además:
-command y similares pueden tomar una lista cuyo primer elemento puede ser una referencia a
una subrutina o un nombre de método. Los elementos restantes se pasan como argumentos a la
subrutina en el momento de la "invocación". Por lo tanto:
$b= $w->Button(blah blah, '-command' => [sub{print shift} , $fred ]);
Debería funcionar, siempre que $fred esté definido en el momento de la creación del botón.
Por lo tanto, el primer elemento de la lista es equivalente al -method de Malcolm y el segundo
sería su -slave. Cualquier elemento adicional es una ventaja y evita tener que
pasar una referencia a un array/hash como esclavo.
