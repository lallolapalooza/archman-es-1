Paquete: tk

Tk_CreateErrorHandler(3) Procedimientos de la biblioteca Tk Tk_CreateErrorHandler(3)

NOMBRE

Tk_CreateErrorHandler, Tk_DeleteErrorHandler - manejar errores del protocolo X

SINOPSIS

#include <tk.h>

Tk_ErrorHandler
Tk_CreateErrorHandler(display, error, request, minor, proc, clientData)

Tk_DeleteErrorHandler(handler)

ARGUMENTOS

Display *display (entrada)
Pantalla cuyos errores deben ser manejados.
int error (entrada)
Coincidir solo eventos de error con este valor en el campo error_code. Si es -1, entonces coincidir con cualquier valor de error_code.
int request (entrada)
Coincidir solo eventos de error con este valor en el campo request_code. Si es -1, entonces coincidir con cualquier valor de request_code.
int minor (entrada)
Coincidir solo eventos de error con este valor en el campo minor_code. Si es -1, entonces coincidir con cualquier valor de minor_code.
Tk_ErrorProc *proc (entrada)
Procedimiento a invocar cada vez que se reciba un evento de error para display y que coincida con error, request y minor. NULL significa ignorar cualquier error coincidente.
ClientData clientData (entrada)
Valor arbitrario de una palabra para pasar a proc.
Tk_ErrorHandler handler (entrada)
Token para el manejador de errores a eliminar (valor de retorno de una llamada previa a Tk_CreateErrorHandler).

DESCRIPCIÓN

Tk_CreateErrorHandler organiza que un procedimiento particular (proc) sea llamado cada vez que ocurran ciertos errores de protocolo en una pantalla particular (display). Los errores de protocolo ocurren cuando el protocolo X se usa incorrectamente, como intentar mapear una ventana que no existe. Consulte la documentación de Xlib para XSetErrorHandler para obtener más información sobre los tipos de errores que pueden ocurrir. Para que proc sea invocado para manejar un error particular, deben ocurrir cinco cosas:

[1]
El error debe referirse a display.
[2]
Ya sea que el argumento error a Tk_CreateErrorHandler haya sido -1, o que el argumento error coincida con el campo error_code del evento de error.
[3]
Ya sea que el argumento request a Tk_CreateErrorHandler haya sido -1, o que el argumento request coincida con el campo request_code del evento de error.
[4]
Ya sea que el argumento minor a Tk_CreateErrorHandler haya sido -1, o que el argumento minor coincida con el campo minor_code del evento de error.
[5]
La solicitud de protocolo a la que se refiere el error debe haberse realizado cuando el manejador estaba activo (consulte más abajo para obtener más información).

Proc debe tener argumentos y un resultado que coincidan con el siguiente tipo:

typedef int Tk_ErrorProc(
        ClientData clientData,
        XErrorEvent *errEventPtr);
El parámetro clientData de proc es una copia del parámetro clientData dado a Tcl_CreateErrorHandler cuando se creó la llamada de retorno. Típicamente, clientData apunta a una estructura de datos que contiene información específica de la aplicación que es necesaria para lidiar con el error. ErrEventPtr es un puntero al evento de error X. El procedimiento proc debe devolver un valor entero. Si devuelve 0, significa que proc manejó el error completamente y no es necesario tomar ninguna otra acción para el error. Si devuelve un valor distinto de cero, significa que proc no pudo manejar el error.

Si se especifica un valor NULL para proc, se ignorarán todos los errores coincidentes: esto producirá el mismo resultado que si se hubiera especificado un procedimiento que siempre devuelve 0.

Si más de un manejador coincide con un error particular, se invocan en orden. Los manejadores se invocarán en orden inverso de creación: el manejador declarado más recientemente primero. Si algún manejador devuelve 0, los manejadores subsiguientes (más antiguos) no se invocarán. Si ningún manejador devuelve 0, Tk invoca el manejador de errores predeterminado de X, que imprime un mensaje de error y aborta el programa. Si desea tener un manejador predeterminado que se ocupe de los errores que ningún otro manejador puede resolver, declárelo primero.

La documentación de X establece que "el manejador de errores no debe llamar a ninguna función (directa o indirectamente) en la pantalla que genere solicitudes de protocolo o que busque eventos de entrada". Esta restricción se aplica a los manejadores declarados por Tk_CreateErrorHandler; desobedézcala bajo su propio riesgo.

Se puede llamar a Tk_DeleteErrorHandler para eliminar un manejador de errores creado previamente. El argumento handler identifica el manejador de errores y debe ser un valor devuelto por una llamada previa a Tk_CreateEventHandler.

Un manejador de errores particular se aplica a los errores que resultan de las solicitudes de protocolo generadas entre la llamada a Tk_CreateErrorHandler y la llamada a Tk_DeleteErrorHandler. Sin embargo, la llamada de retorno real a proc puede no ocurrir hasta después de la llamada a Tk_DeleteErrorHandler, debido al almacenamiento en búfer en el cliente y el servidor. Si un evento de error se refiere a una solicitud de protocolo realizada justo antes de llamar a Tk_DeleteErrorHandler, es posible que el evento de error no se haya procesado antes de la llamada a Tk_DeleteErrorHandler. Cuando surge esta situación, Tk guardará información sobre el manejador e invocará el proc del manejador más tarde, cuando finalmente llegue el evento de error. Si una aplicación desea eliminar un manejador de errores y saber con certeza que todos los errores relevantes han sido procesados, primero debe llamar a Tk_DeleteErrorHandler y luego llamar a XSync; esto limpiará cualquier solicitud y error en búfer, pero resultará en una penalización de rendimiento porque requiere comunicación hacia y desde el servidor X. Después de la llamada a XSync, se garantiza que Tk no llamará a ningún manejador de errores eliminado antes de la llamada a XSync.

Para que el mecanismo de manejo de errores de Tk funcione correctamente, es esencial que el código de la aplicación nunca llame directamente a XSetErrorHandler; las aplicaciones solo deben usar Tk_CreateErrorHandler.
