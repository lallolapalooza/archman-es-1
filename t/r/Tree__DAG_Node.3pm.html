NOMBRE

Tree::DAG_Node - Un árbol N-ario

SINOPSIS

Usando como clase base

package Game::Tree::Node;
use parent 'Tree::DAG_Node';
# Ahora añade tus propios métodos que sobrescriban o extiendan los métodos en C<Tree::DAG_Node>...

Usando como clase por sí sola

use Tree::DAG_Node;
my($root) = Tree::DAG_Node -> new({name => 'root', attributes => {uid => 0} });
$root -> add_daughter(Tree::DAG_Node -> new({name => 'one', attributes => {uid => 1} }) );
$root -> add_daughter(Tree::DAG_Node -> new({name => 'two', attributes => {} }) );
$root -> add_daughter(Tree::DAG_Node -> new({name => 'three'}) ); # Los atributos por defecto son {}.

O:

my($count) = 0;
my($tree)  = Tree::DAG_Node -> new({name => 'Root', attributes => {'uid' => $count} });

O:

my $root = Tree::DAG_Node -> new();
$root -> name("Soy la cima");
$root -> attributes({uid => 0});
my $new_daughter = $root -> new_daughter;
$new_daughter -> name('Otro nodo');
$new_daughter -> attributes({uid => 1});
...

Por último, para envoltorios sofisticados - llamados _add_daughter() - alrededor de new(), mira estos módulos: Marpa::Demo::StringParser y GraphViz2::Marpa. Ambos módulos usan Moo.

Ver scripts/*.pl para otras muestras.

Usando con datos utf-8

read_tree($file_name) funciona con datos utf-8. Ver t/read.tree.t y t/tree.utf8.attributes.txt. Tal archivo puede ser creado redirigiendo la salida de tree2string() a un archivo de tipo utf-8.

Ver la documentación de Encode para la diferencia entre utf8 y utf-8. En resumen, usa utf-8.

Ver también scripts/write_tree.pl y scripts/read.tree.pl y scripts/read.tree.log.

DESCRIPCIÓN

Esta clase encapsula/crea/manipula objetos que representan nodos en una estructura de árbol. La estructura del árbol no es un objeto en sí, sino que es emergente de los enlaces que creas entre los nodos. Esta clase proporciona los métodos para crear enlaces que pueden ser usados para construir un árbol, mientras se te previene de crear cualquier tipo de enlace que no esté permitido en un árbol (tal como tener un nodo ser su propia madre o ancestro, o tener un nodo tener dos madres).

Esto es lo que quiero decir con una "estructura de árbol", dicho un poco redundantemente:

o Un árbol es un caso especial de un grafo dirigido acíclico
o Un árbol es una red de nodos donde hay exactamente un nodo raíz
Además, la única relación primaria entre nodos es la relación madre-hija.
o Ningún nodo puede ser su propia madre, o la madre de su madre, etc.
o Cada nodo en el árbol tiene exactamente un padre
Excepto la raíz, por supuesto, que no tiene padre.
o Cada nodo puede tener cualquier número (0 .. N) de nodos hijos
Los nodos hijos de un nodo dado constituyen una lista *ordenada*.

Sin embargo, eres libre de considerar este orden irrelevante. Algunas aplicaciones necesitan que los hijos estén ordenados, así que elegí considerar este el caso general.

o Un nodo puede aparecer solo en un árbol, y solo una vez en ese árbol
Notablemente (notable porque no se deriva de los dos puntos anteriores), un nodo no puede aparecer dos veces en la lista de hijas de su madre.
o Hay una idea de arriba versus abajo
Arriba significa hacia la raíz, y abajo significa lejos de la raíz (y hacia las hojas).
o Hay una idea de izquierda versus derecha
Izquierda es hacia el inicio (índice 0) de la lista de hijas de un nodo dado, y derecha es hacia el final de la lista de hijas de un nodo dado.

Los árboles como se describen arriba tienen varias aplicaciones, entre ellas: representar la constitución sintáctica, en lingüística formal; representar contingencias en un árbol de juego; representar sintaxis abstracta en el análisis de cualquier lenguaje informático -- ya sea en árboles de expresión para lenguajes de programación, o en la constitución del análisis de un documento de lenguaje de marcado. (Algunos de estos podrían no usar el hecho de que las hijas están ordenadas.)

(Nota: Los B-Trees son un caso muy especial de los tipos de árboles anteriores, y es mejor tratarlos con su propia clase. Consulta CPAN para módulos que encapsulan B-Trees; o si realmente quieres una base de datos, y por alguna razón terminaste mirando aquí, ve a mirar AnyDBM_File.)

Muchas clases base no son utilizables excepto como tales -- pero "Tree::DAG_Node" puede ser usado como una clase normal. Puedes ir y decir:

use Tree::DAG_Node;
my $root = Tree::DAG_Node->new();
$root->name("Soy la cima");
$new_daughter = Tree::DAG_Node->new();
$new_daughter->name("Más");
$root->add_daughter($new_daughter);

y así sucesivamente, construyendo y enlazando objetos de "Tree::DAG_Node" y haciendo estructuras de árbol útiles con ellos.

UNA NOTA PARA EL LECTOR

Esta clase es grande y proporciona muchos métodos. Si tu problema es simple (digamos, solo representar un árbol de análisis simple), esta clase podría parecer como usar un martillo atómico para aplastar una mosca. Pero la complejidad de las campanas y silbatos de este módulo no debería restarle eficiencia al usar esta clase para un propósito simple. De hecho, me sorprendería mucho si algún usuario alguna vez tuviera uso para más de un tercio de los métodos de esta clase. Y recuerda: un martillo atómico *matará* a esa mosca.

CONTENIDO DEL OBJETO

Implementacionalmente, cada nodo en un árbol es un objeto, en el sentido de ser una estructura de datos arbitrariamente compleja que pertenece a una clase (presumiblemente "Tree::DAG_Node", o derivadas de ella) que proporciona métodos.

Los atributos de un objeto nodo son:

o madre -- la madre de este nodo. undef si es una raíz
o hijas -- la lista (posiblemente vacía) de las hijas de este nodo
o nombre -- el nombre para este nodo
No necesita ser único, o incluso imprimible. Se imprime en algunos de los diversos métodos volcadores (dumper), pero depende de ti si no pones nada significativo o imprimible aquí.
o atributos -- lo que el usuario quiera usarlo
Presumiblemente un hashref a cualquier otro atributo que el usuario quiera almacenar sin riesgo de colisión con los atributos reales del objeto. (Uso de ejemplo: atributos para una etiqueta SGML -- definitivamente no querrías que la existencia de un par "mother=foo" en tal etiqueta colisionara con el atributo 'mother' del objeto nodo.)

Aparte de (por defecto) inicializarlo a {}, y tener el método de acceso llamado "attributes" (descrito más abajo), no hago nada con los "atributos" en este módulo. Básicamente lo pretendí para que los usuarios que no quieren/necesitan molestarse en derivar una clase de "Tree::DAG_Node", pudieran todavía adjuntar cualquier dato que quisieran en un nodo.

"madre" e "hijas" son atributos que se relacionan con el enlace -- nunca se escriben directamente, sino que se cambian según corresponda por los "métodos de enlace", discutidos más abajo.

Los otros dos (y cualesquiera otros que puedas añadir en clases derivadas) son simplemente accedidos a través de los métodos del mismo nombre, discutidos más abajo.

MÉTODOS

#
#

add_daughter(LISTA)

#

Un sinónimo exacto de "add_daughters(LISTA)".

#
#
#

add_daughters(LISTA)

#

Este método agrega los objetos nodo en LISTA al final (derecho) de la lista de hijas de $madre. Hacer que un nodo N1 sea hija de otro nodo N2 también significa que el atributo madre de N1 se establece "automáticamente" a N2; también significa que N1 deja de ser hija de cualquier otra persona al convertirse en hija de N2.

#

Si intenta hacer que un nodo sea su propia madre, se produce un error fatal. Si intenta tomar a uno de los ancestros de un nodo N1 y hacerlo también hija de N1, se produce un error fatal. Se produce un error fatal si algo en LISTA no es un objeto nodo.

#

Si intenta hacer N1 hija de N2, pero ya es hija de N2, entonces esto no hace nada; no mueve dichos nodos al final de la lista ni nada; simplemente omite hacer algo con ellos.

#
#
#

add_daughter_left(LISTA)

#

Un sinónimo exacto de "add_daughters_left(LISTA)".

#
#
#

add_daughters_left(LISTA)

#

Este método es igual que "add_daughters(LISTA)", excepto que agrega los objetos nodo en LISTA al principio (izquierdo) de la lista de hijas de $madre, en lugar del final (derecho).

#
#
#

add_left_sister(LISTA)

#

Un sinónimo exacto de "add_left_sisters(LISTA)".

#
#
#

add_left_sisters(LISTA)

#

Esto agrega los elementos en LISTA (en ese orden) como hermanas izquierdas inmediatas de $nodo. En otras palabras, dado que la lista de hijas de la madre de B es (A,B,C,D), llamar a B->add_left_sisters(X,Y) convierte la lista de hijas de la madre de B en (A,X,Y,B,C,D).

#

Si LISTA está vacía, esto no hace nada y devuelve una lista vacía.

#

Esto se implementa básicamente como una llamada a # $nodo->replace_with(LISTA, # $nodo), y por lo tanto todas las limitaciones y advertencias de replace_with se aplican.

#

El valor de retorno de # $nodo->add_left_sisters(LISTA) son los elementos de # LISTA que se agregaron, tal como los devuelve replace_with -- menos las copias de # $nodo que obtendrías de una llamada directa a # $nodo->replace_with(LISTA, # $nodo).

#
#
#

add_right_sister(LISTA)

#

Un sinónimo exacto de "add_right_sisters(LISTA)".

#
#

add_right_sisters(LISTA)

#

Al igual que add_left_sisters (que ver), excepto que los elementos en LISTA (en ese orden) son hermanas derechas inmediatas de # $nodo;

#

En otras palabras, dado que la lista de hijas de la madre de B es # (A,B,C,D), llamar a B->add_right_sisters(X,Y) hace que la lista de hijas de la madre de B sea (A,B,X,Y,C,D).

address()

#
#
#

address(DIRECCIÓN)

#

Con la primera sintaxis, devuelve la dirección de # $nodo dentro de su árbol, basándose en su posición dentro # del árbol. Una dirección se forma anotando la ruta entre la raíz y # $nodo, y concatenando los índices de hija de los # nodos por los que pasa (comenzando con 0 para la raíz, y terminando con # $nodo).

#

Por ejemplo, si para ir del nodo RAÍZ al nodo # $nodo, se pasa por RAÍZ, A, B y # $nodo, entonces la dirección se determina como:

#
#
o el índice de hija de RAÍZ es # 0
#
#
o el índice de A es, # supongamos, 2
#
A es el índice 2 en la lista de hijas de RAÍZ.
#
o el índice de B es, # supongamos, 0
#
B es el índice 0 en la lista de hijas de A.
#
o el índice de $nodo # es, supongamos, 4
#
$nodo es el índice 4 en la lista de hijas de B.
#
#

La dirección del $nodo descrito anteriormente # es, por lo tanto, "0:2:0:4".

#

(Como un caso algo especial, la dirección de la raíz es siempre # "0"; y dado que las direcciones comienzan desde la raíz, todas las direcciones comienzan con un "0".)

#

La segunda sintaxis, donde se proporciona una dirección, comienza desde la raíz del árbol al que pertenece $cualquiernodo y devuelve el nodo correspondiente a esa dirección. Devuelve undef si ningún nodo corresponde a esa dirección. Tenga en cuenta que esta rutina puede ser algo liberal en su interpretación de lo que puede constituir una dirección; es decir, acepta "0.2.0.4", además de "0:2:0:4".

#

También tenga en cuenta que la dirección de un nodo en un árbol solo es significativa en ese árbol tal como está estructurado actualmente.

#

(Considere cómo ($address1 cmp $address2) puede ser mágicamente significativo para usted, si quiso averiguar qué nodos están a la derecha de qué otros nodos.)

common(LIST)

Devuelve el nodo más bajo en el árbol que sea padre o propio de los nodos $node y LIST.

Si los nodos están bastante lejos entre sí en el árbol, el resultado es solo el raíz.

Si los nodos no están todos en el mismo árbol, el resultado es undefined.

Como caso degenerado, si LIST es vacío, devuelve $node.

common_ancestor(LIST)

Devuelve el nodo más bajo que sea padre de todos los nodos dados (en los nodos $node y LIST). En otras palabras, responde a la pregunta: "¿Cuál es el nodo en el árbol, lo más bajo posible, que sea padre de los nodos dados ($node y LIST)?"

Si los nodos están bastante lejos entre sí, el resultado es solo el raíz, excepto si alguno de los nodos es el raíz mismo, en cuyo caso el resultado es undefined (ya que el raíz no tiene padre).

Si los nodos no están todos en el mismo árbol, el resultado es undefined.

Como caso degenerado, si LIST es vacío, devuelve el madre de $node; esto será undefined si $node es el raíz.

copy($option)

copy($option)

Devuelve una copia del nodo actual (el invocante). Por ejemplo: my($copy) = $node -> copy;

El $option es un hashref de opciones con estos pares clave-valor:

o no_attribute_copy => $Boolean
Si se establece a 1, no se copia las propiedades del nodo.

Si no se especifica, el valor por defecto es 0, que copia las propiedades.

copy_at_and_under()

copy_at_and_under($options)

Devuelve una copia del árbol formado por el nodo $node y todo lo que lo sigue.

Si no se especifican opciones, copy_at_and_under se comporta como si se hubiera pasado {}.

Este funciona recorriendo la nueva arbolía desde las hojas, duplicando los nodos usando $orig_node->copy($options_ref) y luego los conecta en una nueva arbolía de la misma forma.

Las opciones que especifiques se pasan a las llamadas a $node->copy.

copy_tree()

copy_tree($options)

Devuelve la raíz de una copia del árbol que $node es miembro de. Si no se especifican opciones, copy_tree se comporta como si se hubiera pasado {}.

Este método se implementa actualmente como una llamada a $this->root->copy_at_and_under($options), pero se puede añadir en el futuro.

Las opciones que especifiques se pasan a las llamadas a $node->copy.

daughters()

Devuelve la (posiblemente vacía) lista de hijas de $node.

decode_lol($lol)

Devuelve un arrayref con la estructura profundamente anidada $lol decodificada.

$lol será la salida de either tree_to_lol() o tree_to_simple_lol().

Ver scripts/read.tree.pl y su archivo de salida scripts/read.tree.log.

delete_tree()

Destruye el árbol completo que $node es miembro de (desde la raíz), nullificando las propiedades de cada nodo-objeto (incluyendo, especialmente, sus atributos de vinculación - espero que esto sea suficiente para eliminar la circularidad en la estructura de datos), y luego lo mueve a la clase DEADNODE.

Usa este cuando ya tienes terminado con el árbol en cuestión y quieres liberar su memoria. (Si no lo haces, se liberará aún cuando tu programa acabe.)

Si intentas llamar métodos a cualquier objeto de nodo en el árbol que has destruido, obtendrás un error como:

Can't locate object method "leaves_under"
  via package "DEADNODE".

Así que si ves eso, es lo que has hecho mal. (En realidad, la clase DEADNODE proporciona una método: un método de tipo no-op "delete_tree". Por lo tanto, si quieres eliminar un árbol, pero crees que ya lo has eliminado, es seguro llamar $node->delete_tree sobre él (de nuevo).)

El método "delete_tree" es necesario porque el recolector de lodos de Perl no verá nunca que es tiempo de liberar la memoria del árbol, hasta que llames $node->delete_tree o hasta que el programa termine (en el momento de la destrucción global, cuando todo está desalineado).

Advertencia: hay mejores formas de recolectar la memoria de un árbol, formas que no requieren explicitamente llamar un método como "delete_tree" - estas involucran clases dummy, como explicado en http://mox.perl.com/misc/circle-destroy.pod).

Sin embargo, introducir una clase dummy en "Tree::DAG_Node" sería más bien un distracción. Si quieres hacer esto con tus clases derivadas, mediante un DESTROY en una clase dummy (o en una clase de metainformación del árbol), entonces hazlo.

La única situación en la que puedo imaginar que "delete_tree" no eliminará completamente el árbol es si uses el hashref en el atributo "attributes" para almacenar (presumiblemente entre otras cosas) referencias a atributos de otros nodos - lo cual 1) puede parecer un poco extraño y 2) es tu problema, porque es la estructura de tus hashes lo que es circular, no la estructura del árbol. Aunque así, considera:

# null out all my "attributes" hashes
$anywhere->root->walk_down({
  'callback' => sub {
    $hr = $_[0]->attributes; %$hr = (); return 1;
  }
});
# And then:
$anywhere->delete_tree;

(Supongo que "delete_tree" es un destructor, o como lo más cercano que puedas significar para una estructura de datos circular en Perl.)

Ver también "WHEN AND HOW TO DESTROY THE TREE".

depth_under()

Devuelve un número entero que represente la cantidad de ramas entre este $node y la hoja más lejana bajo él. (En otras palabras, devuelve la ply del árbol que comienza en $node). Considera scalar($it->ancestors) si quieres la ply de un nodo dentro del árbol completo.)

descendants()

Devuelve una lista con todos los descendientes de $node. Devuelve una lista vacía si $node es un nodo terminal.

(Nota: se escribe "descendants", no "descendents".)

draw_ascii_tree([$options])

Aquí, los [] se refieren a un parámetro opcional.

Devuelve un arrayref de líneas adecuado para imprimir.

Dibuja una representación ASCII-art del arbol estructurado.

El arbol se ve así:

             |
          <Root>
   /-------+-----+---+---\
   |       |     |   |   |
  <I>     <H>   <D> <E> <B>
 /---\   /---\   |   |   |
 |   |   |   |  <F> <F> <C>
<J> <J> <J> <J>  |   |
 |   |   |   |  <G> <G>
<K> <L> <K> <L>
     |       |
    <M>     <M>
     |       |
    <N>     <N>
     |       |
    <O>     <O>

Ver scripts/cut.and.paste.subtrees.pl.

Uso de ejemplo:

print map("$_\n", @{$tree->draw_ascii_tree});

generation()

Devuelve una lista de todos los nodos (de izquierda a derecha) que están en la generación de $node, es decir, que están a la misma distancia del nodo raíz. La generación de $root es solo $root.

Por supuesto, $node siempre está en su propia generación.

generation_under($node)

Similar a "generation()", pero devuelve solo los nodos de la generación de $node que también son descendientes de $node; en otras palabras,

@nos = $nodo->generation_under( $nodo->madre->madre );

son todos los primos de $nodo (tomando prestada más terminología de parentesco), asumiendo que $nodo tiene efectivamente una abuela. En realidad, "primos" no es una palabra adecuada, porque @nos termina incluyendo a los hermanos de $nodo y a $nodo.

De hecho, "generation_under($nodo)" es solo un alias para "generation()", pero creo que esto:

@nos = $nodo->generation_under($camino_arriba);

es un poco más legible que esto:

@nos = $nodo->generation($camino_arriba);

Pero depende de ti.

$nodo->generation_under($nodo) devuelve solo $nodo.

Si llamas a $nodo->generation_under($nodo), pero NODO2 no es $nodo ni un ancestro de $nodo, se comporta como si hubieras llamado solo a $nodo->generation().

lol_to_tree($lol)

Esto debe llamarse como un método de clase.

Convierte algo como la notación de corchetes para "árboles de Chomsky" (o, más bien, lo más cercano que se puede llegar con listas de listas de Perl (de listas (de listas))) en una estructura de árbol. Devuelve la raíz del árbol convertido.

Las reglas de conversión son: 1) si el último (posiblemente el único) elemento de una lista dada es un escalar, entonces ese se usa como atributo de "nombre" para el nodo basado en esta lista. 2) Todos los demás elementos de la lista representan nodos hija del nodo actual, recursivamente si son referencias de lista; de lo contrario, los escalares (no terminales) se consideran que denotan nodos con ese nombre. Así, ['Foo', 'Bar', 'N'] es una forma alternativa de representar [['Foo'], ['Bar'], 'N'].

Un ejemplo ilustrará:

use Tree::DAG_Node;
$lol =
  [
    [
      [ [ 'Det:The' ],
        [ [ 'dog' ], 'N'], 'NP'],
      [ '/with rabies\\', 'PP'],
      'NP'
    ],
    [ 'died', 'VP'],
    'S'
  ];
 $arbol = Tree::DAG_Node->lol_to_tree($lol);
 $diagrama = $arbol->draw_ascii_tree;
 print map "$_\n", @$diagrama;

...devuelve este árbol:

                  |
                 <S>
                  |
               /------------------\
               |                  |
             <NP>                <VP>
               |                  |
       /---------------\        <died>
       |               |
     <NP>            <PP>
       |               |
    /-------\   </with rabies\>
    |       |
<Det:The>  <N>
            |
          <dog>

Por cierto (y esto sigue de las reglas anteriores), al denotar un árbol de LoL que consiste en un solo nodo, esto:

$arbol = Tree::DAG_Node->lol_to_tree( 'Solitario' );

está bien, aunque probablemente se te ocurra denotarlo solo como:

$arbol = Tree::DAG_Node->lol_to_tree( ['Solitario'] );

lo cual, por supuesto, también está bien.

random_network($options)

Este método se puede llamar como método de clase o como método de objeto.

En el primer caso, construye una red dispuesta aleatoriamente bajo un nuevo nodo y devuelve el nodo raíz de ese árbol. En el último caso, construye la red bajo $node.

Actualmente, esto está implementado de forma un poco tibia y mediocre. Básicamente, tuve que inventar redes de aspecto aleatorio para estresar las pruebas de los diversos métodos de volcado de árboles, y así lo escribí. Si realmente quieres confiar en esto para alguna aplicación más seria que esa, te sugiero que examines el código fuente y veas si esto hace realmente lo que necesitas (por ejemplo, en cuanto a la fiabilidad de la aleatoriedad); y siéntete totalmente libre de sugerirme cambios (especialmente en forma de "Reescribí "random_network($options)", aquí está el código...")

Toma cuatro opciones:

o max_node_count -- número máximo de nodos que este árbol podrá tener (contando la raíz)
Predeterminado: 25.
o min_depth -- profundidad mínima del árbol
Las hojas solo se pueden generar después de alcanzar esta profundidad, por lo que el árbol será al menos tan profundo, a menos que se alcance max_node_count primero.

Predeterminado: 2.

o max_depth -- profundidad máxima del árbol
El árbol no será más profundo que esto.

Predeterminado: 3 más min_depth.

o max_children -- número máximo de hijos que cualquier madre en el árbol puede tener.
Predeterminado: 4.

remove_daughter(LIST)

Un sinónimo exacto de "remove_daughters(LIST)".

remove_daughters(LIST)

Esto elimina los nodos listados en LIST de la lista de hijas de $mother. Esto es una operación nula si LIST está vacío. Si hay elementos en LIST que no son hijas actuales de $mother, se ignoran.

No confundir con "clear_daughters()".

replace_with(LIST)

Esto reemplaza $node en la lista de hijas de su madre, desvinculando $node y reemplazándolo por los elementos en LIST. Esto devuelve una lista que consta de $node seguido de LIST, es decir, los nodos que lo reemplazaron.

LIST puede incluir $node mismo (presumiblemente a lo sumo una vez). LIST también puede ser la lista vacía. Sin embargo, si algún elemento en LIST es hermano de $node, se ignora, y no está en la copia de LIST pasada como valor de retorno.

Como podrías esperar para cualquier operación de enlace, los elementos en LIST no pueden ser la madre de $node, ni ningún ancestro de ella; y los elementos en LIST, por supuesto, se desvinculan de sus madres (si tienen alguna) a medida que se enlazan a la madre de $node.

(En el caso especial (y extraño) en que $node es la raíz, esto simplemente llama a $this->unlink_from_mother en todos los elementos de LIST, convirtiéndolos en raíces de sus propios árboles.)

Ten en cuenta que la lista de hijas de $node no necesariamente se ve afectada; ni las listas de hijas de los elementos en LIST. Menciono esto en caso de que pienses que replace_with cambia un nodo por otro, con respecto a la lista de su madre y a su lista de hijas, dejando el resto del árbol sin cambios. Si eso es lo que quieres, reemplazando $Old por $New, entonces quieres:

$New->set_daughters($Old->clear_daughters);
$Old->replace_with($New);

(No puedo decir que las listas de hijas de $node y de los elementos de LIST se vean afectadas nunca por replace_with, pueden verse afectadas en este caso:

$N1 = ($node->daughters)[0]; # primera hija de $node
$N2 = ($N1->daughters)[0];   # primera hija de $N1;
$N3 = Tree::DAG_Node->random_network; # o lo que sea
$node->replace_with($N1, $N2, $N3);

Como efecto secundario de adjuntar $N1 y $N2 a la madre de $node, se desvinculan de sus padres (nodos, y $N1, respectivamente). Pero la lista de hijas de N3 no se ve afectada.

En otras palabras, este método hace lo que tiene que hacer, como esperarías.

replace_with_daughters()

Esto reemplaza $node en la lista de hijas de su madre, desvinculando $node y reemplazándolo por sus hijas. En otras palabras, $node se queda sin madre y sin hijas a medida que sus hijas ascienden y ocupan su lugar. Esto devuelve una lista que consta de $node seguido de los nodos que eran sus hijas.

En el caso especial (y extraño) en que $node es la raíz, simplemente desvincula sus hijas de él, convirtiéndolas en raíces de sus propios árboles.

Efectivamente lo mismo que $node->replace_with($node->daughters), pero más eficiente, ya que se realizan menos comprobaciones. (Y también creo que $node->replace_with_daughters es una operación más común en la manipulación de árboles que $node->replace_with(LIST), por lo que merece un nombre de método propio, pero eso es solo mi opinión.)

Ten en cuenta que si cambias radicalmente la contabilidad de 'madre'/'hijas', puede que tengas que cambiar esta rutina, ya que es uno de los lugares que escribe directamente en 'daughters' y 'mother'.

simple_lol_to_tree($simple_lol)

walk_down($options)

Realiza un recorrido en profundidad de la estructura en y debajo de $node. Lo que hace en cada nodo depende del valor del hashref de opciones, que debe proporcionar. Hay tres opciones, "callback" y "callbackback" (al menos una de las cuales debe definirse, como una referencia a una subrutina), y "_depth".

Esto es lo que hace walk_down(), en forma de pseudocódigo:

o Punto de partida
Comienza en el $node dado.
o Callback
Si hay un callback, llámalo con $node como primer argumento, y el hashref de opciones como segundo argumento (que contiene el potencialmente útil _depth, recuerda). Esta función debe devolver verdadero o falso; si es falso, bloqueará el siguiente paso:
o Hijas
Si $node tiene nodos hijos, incrementa _depth y llama a $daughter->walk_down($options) para cada hija (en orden, por supuesto), donde options_hashref es el mismo hashref con el que se llamó. Cuando esto retorna, decrementa _depth.
Callbackback
Si hay un callbackback, llámalo solo a él como con callback (pero descartando el valor de retorno). Tenga en cuenta que si callback devuelve falso, bloquea el recorrido debajo de $node, pero no bloquea la llamada a callbackback para $node. (Por cierto, en el caso poco probable de que $node haya dejado de ser un objeto nodo, callbackback no se llamará).
o Retorno

$node->walk_down($options) es la forma de hacer recursivamente cosas en un árbol (si comienzas en la raíz) o en una parte de un árbol; si lo que estás haciendo se hace mejor vi

a pre-pre orden de recorrido, usa callback; si lo que estás haciendo se hace mejor con un recorrido post-orden, usa callbackback. walk_down() es incluso la base para muchos de los métodos de esta clase. Ver el código fuente para ejemplos tanto simples como horribles.

Ten en cuenta que si no especificas _depth, se inicializa a 0. Deberías establecerlo a scalar($node->ancestors) si quieres que _depth refleje la profundidad real en el árbol para los nodos llamados, en lugar de solo la profundidad debajo de $node. (Si $node es la raíz, no hay diferencia, por supuesto).

Y, a propósito, es una mala idea modificar el árbol desde el callback. Pueden ocurrir cosas impredecibles. Sugiero en su lugar que tu callback agregue a una pila de cosas que necesitan ser cambiadas, y luego, una vez que walk_down() haya terminado, cambies esos nodos desde esa pila.

Ten en cuenta que la existencia de walk_down() no significa que no puedas escribir tus propios recorridos de uso especial.

CUÁNDO Y CÓMO DESTRUIR EL ÁRBOL

Debería quedarte claro que si has construido un árbol de análisis grande o algo similar, y luego has terminado con él, deberías llamar a $some_node->delete_tree sobre él si quieres recuperar la memoria.

Pero considera este caso: tienes este árbol:

   A
 / | \
B  C  D
|     | \
E     X  Y

Supongamos que decides que no quieres D ni ninguno de sus descendientes en el árbol, así que llamas a D->unlink_from_mother. Esto NO destruye automáticamente el árbol D-X-Y. En cambio, simplemente divide el árbol en dos:

  A                        D
 / \                      / \
B   C                    X   Y
|
E

Para destruir D y su pequeño árbol, debes llamar explícitamente a delete_tree sobre él.

Ten en cuenta, sin embargo, que si llamas a C->unlink_from_mother, y si no tienes ningún enlace a C en ninguna parte, entonces C sí desaparece mágicamente. Esto se debe a que nada enlaza a C; mientras que con el árbol D-X-Y, D enlaza a X e Y, y X e Y enlazan a D. Ten en cuenta que llamar a C->delete_tree es inofensivo; después de todo, un árbol de un solo nodo sigue siendo un árbol.

Por lo tanto, esta es una forma segura de deshacerse de todos los hijos de $node y liberar la memoria asociada con ellos y sus descendientes:

foreach my $it ($node->clear_daughters) { $it->delete_tree }

Solo asegúrate de no hacer esto:

foreach my $it ($node->daughters) { $it->delete_tree }
$node->clear_daughters;

Eso está mal; la primera llamada a $_->delete_tree subirá a la raíz del árbol de $node, y aniquilará todo el árbol, no solo las partes debajo de $node. Podrías haber llamado simplemente a $node->delete_tree. (Además, una vez que $node esté muerto, no puedes llamar a clear_daughters sobre él, por lo que obtendrás un error allí).

DIVAGACIONES

Este módulo utiliza "strict", pero nunca lo escribí teniendo en cuenta las advertencias de -w; así que si usas -w, no te sorprendas si ves quejas de las entrañas de DAG_Node. Mientras no haya forma de desactivar -w para un módulo dado (en lugar de tener que hacerlo en cada subrutina con un "local $^W"), no voy a cambiar esto. Sin embargo, a veces tengo ráfagas de ambición, e intento corregir el código en DAG_Node que genera advertencias, a medida que las encuentro, lo que solo ocurre ocasionalmente. Siéntete libre de enviarme por correo electrónico cualquier parche para tales correcciones que se te ocurran, aunque sea.

Actualmente no asumo (ni aplico) nada sobre la pertenencia de clase de los nodos que se manipulan, excepto probando si cada uno proporciona un método "is_node()", como:

die "Not a node!!!" unless UNIVERSAL::can($node, "is_node");

Por lo tanto, hasta donde yo sé, los nodos de un árbol dado son libres de pertenecer a diferentes clases, siempre y cuando proporcionen/hereden "is_node()", los pocos métodos en los que esta clase se basa para navegar por el árbol, y tengan la misma estructura de objeto interna, o un superconjunto de ella. Presumiblemente, este sería el caso de cualquier objeto que pertenezca a una clase derivada de "Tree::DAG_Node", o que pertenezca a "Tree::DAG_Node" misma.

Cuando las rutinas de esta clase acceden al atributo "mother" de un nodo, o a su atributo "daughters", lo hacen (generalmente) directamente (a través de $node->{'mother'}, etc.), por eficiencia. Pero las clases derivadas de esta clase probablemente deberían hacerlo a través de un método (a través de $node->mother, etc.), por portabilidad, abstracción y bondad general.

Sin embargo, ninguna rutina de esta clase (aparte de, necesariamente, _init(), _init_name(), y "name()") accede directamente al atributo "name"; las rutinas (como los diversos métodos de dibujo/volcado del árbol) obtienen el valor "name" a través de una llamada a $obj->name(). Así que si quieres que el nombre del objeto no sea un atributo real, sino que se derive dinámicamente de alguna característica del objeto (por ejemplo, basándose en algunos de sus otros atributos, o basándose en su dirección), puedes anular el método "name()", sin causar problemas. (Asegúrate de considerar el caso de $obj->name como método de escritura, ya que se utiliza en /lol_to_tree($lol) y "random_network($options)").

PREGUNTAS FRECUENTES

¿Cuál es el mejor módulo de procesamiento de árboles?

"Tree::DAG_Node", casualmente. Más detalles: "VER TAMBIÉN".

¿Cómo procesar cada nodo en un árbol?

Ver "walk_down($options)". $options normalmente se ve así, asumiendo que deseamos pasar un arrayref como pila:

my(@stack);
$tree -> walk_down
({
        callback =>
        sub
        {
                my(@node, $options) = @_;
                # Procesa $node, usando $options...
                push @{$$options{stack} }, $node -> name;
                return 1; # Sigue caminando.
        },
        _depth => 0,
        stack  => \@stack,
});
# Procesa @stack...

¿Cómo cambio de Tree a Tree::DAG_Node?

o El nombre del nodo
En "Tree" usas $node -> value y en "Tree::DAG_Node" es $node -> name.
o Los atributos del nodo
En "Tree" usas $node -> meta y en "Tree::DAG_Node" es $node -> attributes.

¿Existen técnicas para procesar listas de nodos?

o Copia la lista de hijas y cámbiala
@them    = $mother->daughters;
@removed = splice(@them, 0, 2, @new_nodes);
$mother->set_daughters(@them);
o Selecciona un subconjunto de nodos
$mother->set_daughters
(
        grep($_->name =~ /wanted/, $mother->daughters)
);
