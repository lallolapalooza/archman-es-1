Win::Hivex::Regedit(3) Documentación de Perl aportada por el usuario Win::Hivex::Regedit(3)

NOMBRE

Win::Hivex::Regedit - Ayuda para leer y escribir archivos en formato regedit

SINOPSIS

use Win::Hivex;
use Win::Hivex::Regedit qw(reg_import reg_export);
$h = Win::Hivex->open ('SOFTWARE', write => 1);
open FILE, "updates.reg";
reg_import (\*FILE, $h);
$h->commit (undef);
reg_export ($h, "\\Microsoft\\Windows NT\\CurrentVersion", \*OUTFILE,
   prefix => "HKEY_LOCAL_MACHINE\\SOFTWARE");

DESCRIPCIÓN

Win::Hivex::Regedit es una biblioteca auxiliar para leer y escribir el formato de archivo regedit (o ".REG") de Windows. Este es el formato textual que se usa comúnmente en Windows para distribuir grupos de cambios en el Registro de Windows, y este formato es leído y escrito por los programas propietarios "reg.exe" y "regedit.exe" suministrados con Windows. *No* es lo mismo que el formato binario "hive" que la propia biblioteca hivex puede leer y escribir. Tenga en cuenta que el formato regedit no está bien especificado y, por lo tanto, pueden ocurrir desviaciones entre lo que el programa de Windows puede leer/escribir y lo que nosotros podemos leer/escribir. (Por favor, informe de errores para cualquier desviación encontrada).

Win::Hivex::Regedit es la biblioteca Perl de bajo nivel. También hay una herramienta de línea de comandos para combinar archivos hive y archivos reg (hivexregedit(1)). Si tiene una máquina virtual de Windows en la que necesita fusionar cambios en formato regedit, utilice la herramienta de alto nivel virt-win-reg(1) (parte de las herramientas de libguestfs).

FUNCIONES

reg_import

reg_import ($fh, ($h|$map), [encoding => "UTF-16LE"]);

Esta función importa las claves del registro desde el manejador de archivo $fh ya sea en el hive $h o a través de una función de mapeo.

El manejador de hive $h debe haber sido abierto para escritura, es decir, usando el flag "write => 1" para "Win::Hivex->open".

En el archivo hive binario, la primera parte del nombre de la clave (por ejemplo, "HKEY_LOCAL_MACHINE\SOFTWARE") no se almacena. Simplemente tiene que saber (de alguna manera) que esto se mapea al hive "SOFTWARE". Por lo tanto, si se le da un archivo que contiene una mezcla de claves que deben agregarse a diferentes hives, debe tener una forma de mapearlas a los manejadores de hive. Esto está fuera del alcance de la biblioteca hivex, pero si el segundo argumento es un CODEREF (es decir, una referencia a una función), entonces esta función $map se llama en cada nombre de clave:

map ($keyname)
==> ($h, $keyname)

Como se muestra, la función debe devolver un par, el manejador de hive y el nombre real de la clave (con el prefijo eliminado). Por ejemplo:

sub map {
  if ($_[0] =~ /^HKEY_LOCAL_MACHINE\\SOFTWARE(.*)/i) {
    return ($software_h, $1);
  } else ...
}

"encoding" es la codificación utilizada por defecto para las cadenas. Si no se especifica, por defecto es "UTF-16LE", sin embargo, le recomendamos encarecidamente que la especifique. Consulte "CADENAS CODIFICADAS" a continuación.

Al igual que con el programa regedit, fusionamos las nuevas claves del registro con las existentes, y los nuevos valores de nodos con los antiguos. Puede usar el carácter "-" (menos) para eliminar claves y valores individuales. Esto se explica en detalle en la página de Wikipedia sobre el Registro de Windows.

Recuerde que debe llamar a "$h->commit (undef)" en el manejador hivex antes de que se escriban los cambios en el archivo hive. Consulte "ESCRITURA EN ARCHIVOS HIVE" en hivex(3).

reg_export

reg_export ($h, $key, $fh,
            [prefix => $prefix],
            [unsafe_printable_strings => 1]);

Esta función exporta las claves del registro comenzando desde la raíz $key y recursivamente hacia abajo en el manejador de archivo $fh.

$key es una ruta insensible a mayúsculas y minúsculas del nodo desde el cual comenzar, relativa a la raíz del hive. Es un error si esta ruta no existe. Los elementos de la ruta deben estar separados por caracteres de barra invertida.

$prefix se antepone a cada nombre de clave. El uso habitual para esto es hacer que los nombres de clave aparezcan como lo harían en Windows. Por ejemplo, la clave "\Foo" en el Registro SOFTWARE, con $prefix "HKEY_LOCAL_MACHINE\SOFTWARE", se escribiría como:

[HKEY_LOCAL_MACHINE\SOFTWARE\Foo]
"Clave 1"=...
"Clave 2"=...

Si "unsafe_printable_strings" no se proporciona o es falso, la salida se escribe como ASCII puro de 7 bits, con finales de línea que son los predeterminados para el host local. Las cadenas siempre se codifican como bytes hexadecimales. Esto es seguro porque preserva el contenido y la codificación originales de las cadenas. Consulte "CADENAS CODIFICADAS" a continuación.

Si "unsafe_printable_strings" es verdadero, se asume que las cadenas son UTF-16LE y se convierten a UTF-8 para la salida. El punto de código cero final en la cadena se elimina si existe uno. Esto no es seguro porque no preserva la fidelidad de las cadenas en el Registro y porque el tipo de contenido de las cadenas no siempre es UTF-16LE. Sin embargo, es útil si solo desea mostrar cadenas para una rápida manipulación y depuración.

Puede que necesite convertir la codificación del archivo usando iconv(1) y los finales de línea usando unix2dos(1) si se envía a un usuario de Windows.

Los nodos y las claves se ordenan alfabéticamente en la salida.

Esta función *no* imprime una cabecera. El programa regedit real imprimirá una cabecera como:

Windows Registry Editor Version 5.00

seguido de una línea en blanco. (Otras cabeceras son posibles, consulte la página de Wikipedia sobre el Registro de Windows). Si desea una cabecera, debe escribirla usted mismo.

reg_export_node

reg_export_node ($h, $node, $fh, ...);

Esto es exactamente lo mismo que "reg_export" excepto que en lugar de especificar la ruta a una clave como una cadena, se pasa un manejador de biblioteca $node de hivex.

CADENAS CODIFICADAS

La situación con las cadenas codificadas en el Registro de Windows es muy confusa. Hay dos codificaciones principales que encontraría en el archivo binario (hive), ASCII de 7 bits y UTF-16LE. (Otras codificaciones son posibles, también es posible tener datos binarios arbitrarios marcados incorrectamente con un tipo de cadena).

El propio archivo hive no contiene ninguna indicación de la codificación de la cadena. Windows probablemente adivina la codificación.

Creemos que regedit probablemente adivina qué codificación usar basándose en la codificación del archivo, o tiene diferentes valores predeterminados para diferentes versiones de Windows. Ninguna de las dos opciones es apropiada para una herramienta utilizada en un sistema operativo real.

Al usar "reg_import", debe especificar la codificación predeterminada para las cadenas utilizando el parámetro "encoding". Si no se especifica, por defecto es UTF-16LE.

El archivo en sí que se importa debe estar en la codificación local para archivos (generalmente UTF-8 en sistemas Linux modernos). Esto significa que si recibe un archivo regedit de un sistema Windows, es posible que a veces tenga que recodificarlo:

iconv -f utf-16le -t utf-8 < input.reg | dos2unix > output.reg

Al escribir archivos regedit ("reg_export") evitamos toda esta locura. *Todas* las cadenas (incluso las ASCII puras) se escriben como bytes hexadecimales, por lo que no hay duda sobre cómo deben codificarse cuando se lean.
