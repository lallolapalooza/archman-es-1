NOMBRE

VACUUM - recolecta basura y opcionalmente analiza una base de datos

SINOPSIS

VACUUM [ ( opción [, ...] ) ] [ tabla_y_columnas [, ...] ]
donde opción puede ser una de las siguientes:
    FULL [ booleano ]
    FREEZE [ booleano ]
    VERBOSE [ booleano ]
    ANALYZE [ booleano ]
    DISABLE_PAGE_SKIPPING [ booleano ]
    SKIP_LOCKED [ booleano ]
    INDEX_CLEANUP { AUTO | ON | OFF }
    PROCESS_MAIN [ booleano ]
    PROCESS_TOAST [ booleano ]
    TRUNCATE [ booleano ]
    PARALLEL entero
    SKIP_DATABASE_STATS [ booleano ]
    ONLY_DATABASE_STATS [ booleano ]
    BUFFER_USAGE_LIMIT tamaño
y tabla_y_columnas es:
    [ ONLY ] nombre_tabla [ * ] [ ( nombre_columna [, ...] ) ]

DESCRIPCIÓN

VACUUM recupera el espacio ocupado por tuplas muertas. En la operación normal de PostgreSQL, las tuplas que se eliminan u obsoletan por una actualización no se eliminan físicamente de su tabla; permanecen presentes hasta que se realiza un VACUUM. Por lo tanto, es necesario ejecutar VACUUM periódicamente, especialmente en tablas actualizadas frecuentemente.

Sin una lista de tabla_y_columnas, VACUUM procesa cada tabla y vista materializada en la base de datos actual que el usuario actual tiene permiso para hacer vacuum. Con una lista, VACUUM procesa solo esas tablas.

VACUUM ANALYZE realiza un VACUUM y luego un ANALYZE para cada tabla seleccionada. Esta es una forma combinada práctica para scripts de mantenimiento de rutina. Consulte ANALYZE(7) para más detalles sobre su procesamiento.

Un simple VACUUM (sin FULL) simplemente recupera espacio y lo pone a disposición para su reutilización. Esta forma del comando puede operar en paralelo con la lectura y escritura normales de la tabla, ya que no se obtiene un bloqueo exclusivo. Sin embargo, el espacio adicional no se devuelve al sistema operativo (en la mayoría de los casos); simplemente se mantiene disponible para su reutilización dentro de la misma tabla. También nos permite aprovechar múltiples CPU para procesar índices. Esta característica se conoce como vacuum paralelo. Para deshabilitar esta característica, se puede usar la opción PARALLEL y especificar los trabajadores paralelos como cero. VACUUM FULL reescribe todo el contenido de la tabla en un nuevo archivo de disco sin espacio adicional, permitiendo que el espacio no utilizado se devuelva al sistema operativo. Esta forma es mucho más lenta y requiere un bloqueo ACCESS EXCLUSIVE en cada tabla mientras se está procesando.

PARÁMETROS

FULL

Selecciona el vacuum "completo", que puede recuperar más espacio, pero tarda mucho más y bloquea la tabla de forma exclusiva. Este método también requiere espacio en disco adicional, ya que escribe una nueva copia de la tabla y no libera la copia antigua hasta que la operación se completa. Normalmente, solo debe usarse cuando se necesita recuperar una cantidad significativa de espacio de dentro de la tabla.

FREEZE

Selecciona el "congelamiento" agresivo de tuplas. Especificar FREEZE es equivalente a realizar VACUUM con los parámetros vacuum_freeze_min_age y vacuum_freeze_table_age establecidos en cero. El congelamiento agresivo siempre se realiza cuando la tabla se reescribe, por lo que esta opción es redundante cuando se especifica FULL.

VERBOSE

Imprime un informe detallado de la actividad de vacuum para cada tabla a nivel INFO.

ANALYZE

Actualiza las estadísticas utilizadas por el planificador para determinar la forma más eficiente de ejecutar una consulta.

DISABLE_PAGE_SKIPPING

Normalmente, VACUUM omitirá páginas basándose en el mapa de visibilidad. Las páginas donde todas las tuplas se conocen como congeladas siempre se pueden omitir, y aquellas donde todas las tuplas se conocen como visibles para todas las transacciones pueden omitirse excepto cuando se realiza un vacuum agresivo. Además, excepto cuando se realiza un vacuum agresivo, algunas páginas pueden omitirse para evitar esperar a que otras sesiones terminen de usarlas. Esta opción deshabilita todo el comportamiento de omisión de páginas, y está destinada a ser utilizada solo cuando el contenido del mapa de visibilidad es sospechoso, lo que solo debería ocurrir si hay un problema de hardware o software que cause corrupción de la base de datos.

SKIP_LOCKED

Especifica que VACUUM no debe esperar a que se liberen bloqueos conflictivos al comenzar a trabajar en una relación: si una relación no puede bloquearse inmediatamente sin esperar, se omite la relación. Tenga en cuenta que incluso con esta opción, VACUUM aún puede bloquearse al abrir los índices de la relación. Además, VACUUM ANALYZE aún puede bloquearse al adquirir filas de muestra de particiones, hijos de herencia de tablas y algunos tipos de tablas externas. También, mientras que VACUUM normalmente procesa todas las particiones de tablas particionadas especificadas, esta opción hará que VACUUM omita todas las particiones si hay un bloqueo conflictivo en la tabla particionada.

INDEX_CLEANUP

Normalmente, VACUUM omitirá la limpieza de índices cuando hay muy pocas tuplas muertas en la tabla. Se espera que el costo de procesar todos los índices de la tabla supere con creces el beneficio de eliminar tuplas de índice muertas cuando esto ocurre. Esta opción se puede usar para forzar a VACUUM a procesar índices cuando hay más de cero tuplas muertas. El valor predeterminado es AUTO, que permite a VACUUM omitir la limpieza de índices cuando sea apropiado. Si INDEX_CLEANUP se establece en ON, VACUUM eliminará conservadoramente todas las tuplas muertas de los índices. Esto puede ser útil para la compatibilidad con versiones anteriores de PostgreSQL, donde este era el comportamiento estándar.

INDEX_CLEANUP también se puede establecer en OFF para forzar a VACUUM a omitir *siempre* la limpieza de índices, incluso cuando hay muchas tuplas muertas en la tabla. Esto puede ser útil cuando es necesario que VACUUM se ejecute lo más rápido posible para evitar el desbordamiento inminente del ID de transacción (consulte la Sección 24.1.5). Sin embargo, el mecanismo de seguridad contra el desbordamiento controlado por vacuum_failsafe_age se activará automáticamente para evitar el fallo por desbordamiento del ID de transacción, y debe preferirse. Si la limpieza de índices no se realiza regularmente, el rendimiento puede verse afectado, ya que a medida que la tabla se modifica, los índices acumularán tuplas muertas y la tabla en sí acumulará punteros de línea muertas que no se pueden eliminar hasta que se complete la limpieza de índices.

Esta opción no tiene efecto en tablas que no tienen índice y se ignora si se utiliza la opción FULL. Tampoco tiene efecto en el mecanismo de seguridad contra el desbordamiento del ID de transacción. Cuando se activa, omitirá la limpieza de índices, incluso cuando INDEX_CLEANUP esté establecido en ON.

PROCESS_MAIN

Especifica que VACUUM debe intentar procesar la relación principal. Este es generalmente el comportamiento deseado y es el predeterminado. Establecer esta opción en falso puede ser útil cuando solo es necesario hacer vacuum a la tabla TOAST correspondiente de una relación.

PROCESS_TOAST

Especifica que VACUUM debe intentar procesar la tabla TOAST correspondiente para cada relación, si existe. Este es generalmente el comportamiento deseado y es el predeterminado. Establecer esta opción en falso puede ser útil cuando solo es necesario hacer vacuum a la relación principal. Esta opción es necesaria cuando se utiliza la opción FULL.

TRUNCATE

Especifica que VACUUM debe intentar truncar las páginas vacías al final de la tabla y permitir que el espacio en disco de las páginas truncadas se devuelva al sistema operativo. Este es normalmente el comportamiento deseado y es el predeterminado a menos que vacuum_truncate se establezca en falso o la opción vacuum_truncate se haya establecido en falso para la tabla a la que se está haciendo vacuum. Establecer esta opción en falso puede ser útil para evitar el bloqueo ACCESS EXCLUSIVE en la tabla que requiere el truncamiento. Esta opción se ignora si se utiliza la opción FULL.

PARALLEL

Realiza las fases de vacuum de índice y limpieza de índice de VACUUM en paralelo utilizando entero trabajadores en segundo plano (para los detalles de cada fase de vacuum, consulte la Tabla 27.46). El número de trabajadores utilizados para realizar la operación es igual al número de índices en la relación que admiten vacuum paralelo, que está limitado por el número de trabajadores especificados con la opción PARALLEL, si los hay, que a su vez está limitado por max_parallel_maintenance_workers. Un índice puede participar en vacuum paralelo si y solo si el tamaño del índice es superior a min_parallel_index_scan_size. Tenga en cuenta que no se garantiza que se utilice el número de trabajadores paralelos especificados en entero durante la ejecución. Es posible que un vacuum se ejecute con menos trabajadores de los especificados, o incluso sin trabajadores. Solo se puede usar un trabajador por índice. VACUUM(7) — PostgreSQL Manual

NAME

VACUUM — reclaim storage and analyze database state

SYNOPSIS

VACUUM [ option ... ] [ table_and_columns ... ] [ ANALYZE [ option ... ] [ table_and_columns ... ] ]
VACUUM [ option ... ] [ ONLY ] table_name [ * ] [ ANALYZE [ option ... ] [ table_name ... ] [ * ] ]
VACUUM [ option ... ] [ ONLY ] table_name [ * ] [ WITH ( storage_parameter [= value] [, ...] ) ] [ ANALYZE [ option ... ] [ table_name ... ] [ * ] ] [ WITH ( storage_parameter [= value] [, ...] ) ]
VACUUM [ option ... ] [ ONLY ] table_name [ * ] [ TO tablespace_name ] [ ANALYZE [ option ... ] [ table_name ... ] [ * ] ] [ TO tablespace_name ]
VACUUM [ option ... ] [ ONLY ] table_name [ * ] [ TO tablespace_name ] [ WITH ( storage_parameter [= value] [, ...] ) ] [ ANALYZE [ option ... ] [ table_name ... ] [ * ] ] [ TO tablespace_name ] [ WITH ( storage_parameter [= value] [, ...] ) ]

DESCRIPTION

VACUUM is a PostgreSQL utility that reclaims storage occupied by dead rows. It performs several maintenance tasks: it can mark old row versions as expired, and it can delete them. It also collects statistics about the contents of tables, which the query planner uses to determine the most efficient way to execute a SQL query. Finally, it can lock tables to prevent access during maintenance.

The standard VACUUM command processes tables in the current database. When run as a standalone command, it processes all tables in the database, or a specified list of tables. When run as part of a larger command (like a transaction), it processes tables as specified by the command.

VACUUM can be run in several modes:

  • Normal VACUUM: This is the default mode. It scans tables, marks dead rows as reusable, and optionally collects statistics. It does not reclaim disk space.
  • VACUUM FULL: This mode rewrites the entire table, reclaiming all disk space occupied by dead rows. This can be slower and more resource-intensive than a normal VACUUM, and it requires an exclusive lock on the table.
  • VACUUM (VERBOSE): This option provides more detailed output about the vacuuming process, including statistics about tables and rows.
  • VACUUM (ANALYZE): This option collects statistics about the contents of tables. These statistics are used by the query planner to determine the most efficient way to execute SQL queries.
  • VACUUM (FREEZE): This option freezes all row versions, making them inaccessible to older transactions. This can prevent transaction ID wraparound issues.
  • VACUUM (PARALLEL): This option allows vacuuming to be performed in parallel using multiple worker processes. This can significantly speed up vacuuming on multi-core systems.

The VACUUM command can also be used to move tables to a different tablespace or to alter their storage parameters.

PARAMETERS

Specifies a vacuuming option. The options are:

Specifies that VACUUM should run in FULL mode. This rewrites the entire table, reclaiming all disk space occupied by dead rows. This operation requires an exclusive lock on the table, and it can be significantly slower than a standard VACUUM. It also requires more disk space during the operation.

This option can't be used with the option.

Specifies that VACUUM should attempt to freeze all row versions. Freezing makes row versions invisible to older transactions, which can help prevent transaction ID wraparound problems. This option can also be specified as a cost delay value, in which case it is used to limit the I/O cost of vacuuming. The default value is from vacuum_freeze_min_delay_is_active. Setting it to 0 disables the cost delay.

Specifies that VACUUM should print detailed information about its actions.

Specifies that VACUUM should also run ANALYZE after it finishes processing each table.

Specifies that VACUUM should run in parallel. This option can take an integer argument to specify the maximum number of worker processes that can be used. The default value is the number of CPU cores available.

This option can't be used with the option.

Specifies that VACUUM should not reclaim storage. This option is useful when you only want to collect statistics about table contents.

Specifies that VACUUM should not update table statistics. This option is useful when you want to reclaim storage but do not need to update statistics. This option can't be used with the FULL option.

Specifies that VACUUM should do nothing except update the database-wide statistics about oldest unfrozen XIDs. When this option is specified, the table_and_columns list must be empty, and no other option may be enabled except VERBOSE.

Specifies the Buffer Access Strategy ring buffer size for VACUUM. This size is used to calculate the number of shared buffers which will be reused as part of this strategy. 0 disables use of a Buffer Access Strategy. If ANALYZE is also specified, the BUFFER_USAGE_LIMIT value is used for both the vacuum and analyze stages. This option can't be used with the FULL option except if ANALYZE is also specified. When this option is not specified, VACUUM uses the value from vacuum_buffer_usage_limit. Higher settings can allow VACUUM to run more quickly, but having too large a setting may cause too many other useful pages to be evicted from shared buffers. The minimum value is 128 kB and the maximum value is 16 GB.

boolean

Specifies whether the selected option should be turned on or off. You can write TRUE, ON, or 1 to enable the option, and FALSE, OFF, or 0 to disable it. The boolean value can also be omitted, in which case TRUE is assumed.

integer

Specifies a non-negative integer value passed to the selected option.

size

Specifies an amount of memory in kilobytes. Sizes may also be specified as a string containing the numerical size followed by any one of the following memory units: B (bytes), kB (kilobytes), MB (megabytes), GB (gigabytes), or TB (terabytes).

table_name

The name (optionally schema-qualified) of a specific table or materialized view to vacuum. If ONLY is specified before the table name, only that table is vacuumed. If ONLY is not specified, the table and all of its inheritance child tables or partitions (if any) are also vacuumed. Optionally, * can be specified after the table name to explicitly indicate that inheritance child tables (or partitions) are to be vacuumed.

column_name

The name of a specific column to analyze. Defaults to all columns. If a column list is specified, ANALYZE must also be specified.

OUTPUTS

When VERBOSE is specified, VACUUM emits progress messages to indicate which table is currently being processed. Various statistics about the tables are printed as well.

NOTES

To vacuum a table, one must ordinarily have the MAINTAIN privilege on the table. However, database owners are allowed to vacuum all tables in their databases, except shared catalogs. VACUUM will skip over any tables that the calling user does not have permission to vacuum.

While VACUUM is running, the search_path is temporarily changed to pg_catalog, pg_temp.

VACUUM cannot be executed inside a transaction block.

For tables with GIN indexes, VACUUM (in any form) also completes any pending index insertions, by moving pending index entries to the appropriate places in the main GIN index structure. See Section 65.4.4.1 for details.

We recommend that all databases be vacuumed regularly in order to remove dead rows. PostgreSQL includes an “autovacuum” facility which can automate routine vacuum maintenance. For more information about automatic and manual vacuuming, see Section 24.1.

The FULL option is not recommended for routine use, but might be useful in special cases. An example is when you have deleted or updated most of the rows in a table and would like the table to physically shrink to occupy less disk space and allow faster table scans. VACUUM FULL will usually shrink the table more than a plain VACUUM would.

The PARALLEL option is used only for vacuum purposes. If this option is specified with the ANALYZE option, it does not affect ANALYZE.

VACUUM causes a substantial increase in I/O traffic, which might cause poor performance for other active sessions. Therefore, it is sometimes advisable to use the cost-based vacuum delay feature. For parallel vacuum, each worker sleeps in proportion to the work done by that worker. See Section 19.10.2 for details.

Each backend running VACUUM without the FULL option will report its progress in the pg_stat_progress_vacuum view. Backends running VACUUM FULL will instead report their progress in the pg_stat_progress_cluster view. See Section 27.4.5 and Section 27.4.2 for details.

EXAMPLES

To clean a single table onek, analyze it for the optimizer and print a detailed vacuum activity report:

VACUUM (VERBOSE, ANALYZE) onek;

COMPATIBILITY

There is no VACUUM statement in the SQL standard.

The following syntax was used before PostgreSQL version 9.0 and is still supported:

VACUUM [ FULL ] [ FREEZE ] [ VERBOSE ] [ ANALYZE ] [ table_and_columns [, ...] ]

Note that in this syntax, the options must be specified in exactly the order shown.
