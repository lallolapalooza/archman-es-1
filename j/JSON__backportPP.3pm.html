JSON::backportPP(3) Documentación de Perl aportada por el usuario JSON::backportPP(3)

NOMBRE

JSON::PP - Módulo puramente en Perl compatible con JSON::XS.

SINOPSIS

use JSON::PP;
# funciones exportadas, fallan en caso de error
# y esperan/generan UTF-8
$texto_json_codificado_utf8 = encode_json $referencia_hash_o_array_perl;
$referencia_hash_o_array_perl  = decode_json $texto_json_codificado_utf8;
# Interfaz OO
$json = JSON::PP->new->ascii->pretty->allow_nonref;

$texto_json_con_formato = $json->encode( $escalar_perl );
$escalar_perl = $json->decode( $texto_json );

# Nota que JSON versión 2.0 y superior usarán automáticamente
# JSON::XS o JSON::PP, así que deberías poder simplemente:

use JSON;

DESCRIPCIÓN

JSON::PP es un decodificador/codificador JSON puramente en Perl y (casi) compatible con JSON::XS, mucho más rápido, escrito en C por Marc Lehmann. JSON::PP funciona como un módulo de respaldo cuando usas el módulo JSON sin tener instalado JSON::XS.

Debido a esta característica de respaldo de JSON.pm, JSON::PP intenta no ser más amigable con JavaScript que JSON::XS (es decir, no escapar caracteres adicionales como U+2028 y U+2029, etc.), para que no pierdas silenciosamente esa amigabilidad con JavaScript cuando usas JSON.pm e instalas JSON::XS por velocidad o por accidente. Si necesitas un módulo puramente en Perl compatible con RFC7159 y amigable con JavaScript, prueba JSON::Tiny, que deriva del framework web Mojolicious y es también más pequeño y rápido que JSON::PP.

JSON::PP ha sido incluido en el núcleo de Perl desde Perl 5.14, principalmente para que los módulos de la toolchain de CPAN puedan parsear META.json.

INTERFAZ FUNCIONAL

Esta sección se toma casi textualmente de JSON::XS. "encode_json" y "decode_json" se exportan por defecto.

encode_json

$texto_json = encode_json $escalar_perl

Convierte la estructura de datos Perl dada a una cadena binaria codificada en UTF-8 (es decir, la cadena solo contiene octetos). Falla en caso de error.

Esta llamada a función es funcionalmente idéntica a:

$texto_json = JSON::PP->new->utf8->encode($escalar_perl)

Excepto por ser más rápida.

decode_json

$escalar_perl = decode_json $texto_json

Lo opuesto a "encode_json": espera una cadena UTF-8 (binaria) y trata de parsear esa cadena como texto JSON codificado en UTF-8, devolviendo la referencia resultante. Falla en caso de error.

Esta llamada a función es funcionalmente idéntica a:

$escalar_perl = JSON::PP->new->utf8->decode($texto_json)

Excepto por ser más rápida.

JSON::PP::is_bool

$es_booleano = JSON::PP::is_bool($escalar)

Devuelve verdadero si el escalar pasado representa JSON::PP::true o JSON::PP::false, dos constantes que actúan como 1 y 0 respectivamente y que también se usan para representar "true" y "false" de JSON en cadenas de Perl.

En perl 5.36 y versiones posteriores, también devolverá verdadero al recibir uno de los valores booleanos estándar de perl, como el resultado de una comparación.

Ver MAPPING, más abajo, para más información sobre cómo se mapean los valores JSON a Perl.

INTERFAZ ORIENTADA A OBJETOS

Esta sección también se toma de JSON::XS.

La interfaz orientada a objetos te permite configurar tu propio estilo de codificación o decodificación, dentro de los límites de los formatos soportados.

new

$json = JSON::PP->new

Crea un nuevo objeto JSON::PP que puede ser usado para de/codificar cadenas JSON. Todos los flags booleanos descritos a continuación están desactivados por defecto (con la excepción de "allow_nonref", que está activado por defecto desde la versión 4.0).

Los mutadores de flags devuelven el objeto JSON::PP nuevamente y, por lo tanto, las llamadas pueden encadenarse:

my $json = JSON::PP->new->utf8->space_after->encode({a => [1,2]})
=> {"a": [1, 2]}

ascii

$json = $json->ascii([$habilitar])

$habilitado = $json->get_ascii

Si $habilitar es verdadero (o no se proporciona), entonces el método "encode" no generará caracteres fuera del rango de código 0..127 (que es ASCII). Cualquier carácter Unicode fuera de ese rango se escapará usando \uXXXX (caracteres BMP) o una secuencia de escape doble \uHHHH\uLLLLL, según RFC4627. La cadena JSON codificada resultante puede tratarse como una cadena Unicode nativa, una cadena codificada en ASCII, en latin1 o en UTF-8, o cualquier otro superconjunto de ASCII.

Si $habilitar es falso, entonces el método "encode" no escapará caracteres Unicode a menos que sea requerido por la sintaxis JSON u otros flags. Esto resulta en un formato más rápido y compacto.

Ver también la sección NOTAS SOBRE FLAGS DE CODIFICACIÓN/JUEGOS DE CARACTERES más adelante en este documento.

El uso principal de este flag es producir textos JSON que puedan ser transmitidos a través de un canal de 7 bits, ya que los textos JSON codificados no contendrán caracteres de 8 bits.

JSON::PP->new->ascii(1)->encode([chr 0x10401])
=> ["\ud801\udc01"]

latin1

$json = $json->latin1([$habilitar])

$habilitado = $json->get_latin1

Si $habilitar es verdadero (o no se proporciona), entonces el método "encode" codificará el texto JSON resultante como latin1 (o iso-8859-1), escapando cualquier carácter fuera del rango de código 0..255. La cadena resultante puede tratarse como un texto JSON codificado en latin1 o una cadena Unicode nativa. El método "decode" no se verá afectado de ninguna manera por este flag, ya que "decode", por defecto, espera Unicode, que es un superconjunto estricto de latin1.

Si $habilitar es falso, entonces el método "encode" no escapará caracteres Unicode a menos que sea requerido por la sintaxis JSON u otros flags.

Ver también la sección NOTAS SOBRE FLAGS DE CODIFICACIÓN/JUEGOS DE CARACTERES más adelante en este documento.

El uso principal de este flag es codificar eficientemente datos binarios como texto JSON, ya que la mayoría de los octetos no se escaparán, resultando en un tamaño codificado más pequeño. La desventaja es que el texto JSON resultante está codificado en latin1 (y debe tratarse correctamente como tal al almacenar y transferir), una codificación rara para JSON. Por lo tanto, es más útil cuando deseas almacenar estructuras de datos que sabes que contienen datos binarios de manera eficiente en archivos o bases de datos, no cuando interactúas con otros codificadores/decodificadores JSON.

JSON::PP->new->latin1->encode (["\x{89}\x{abc}"]
=> ["\x{89}\\u0abc"]    # (sintaxis de perl, U+abc escapado, U+89 no)

utf8

$json = $json->utf8([$habilitar])

$habilitado = $json->get_utf8

Si $habilitar es verdadero (o no se proporciona), entonces el método "encode" codificará el resultado JSON en UTF-8, como lo requieren muchos protocolos, mientras que el método "decode" espera recibir una cadena codificada en UTF-8. Ten en cuenta que las cadenas codificadas en UTF-8 no contienen caracteres fuera del rango 0..255, por lo que son útiles para E/S byte a byte/binaria. En versiones futuras, habilitar esta opción podría habilitar la autodetección de las familias de codificación UTF-16 y UTF-32, como se describe en RFC4627.

Si $habilitar es falso, entonces el método "encode" devolverá la cadena JSON como una cadena Unicode (no codificada), mientras que "decode" espera una cadena Unicode. Cualquier decodificación o codificación (por ejemplo, a UTF-8 o UTF-16) debe ser realizada por ti, por ejemplo, usando el módulo Encode.

Ver también la sección NOTAS SOBRE FLAGS DE CODIFICACIÓN/JUEGOS DE CARACTERES más adelante en este documento.

allow_tags

$json = $json->allow_tags([$enable])
$enabled = $json->get_allow_tags

Ver "SERIALIZACIÓN DE OBJETOS" para detalles.

Si $enable es true (o se omite), entonces "encode", al detectar un objeto bendecido, verificará la existencia de la metodología "FREEZE" en la clase del objeto. Si está disponible, se utilizará para serializar el objeto en un valor JSON no estándar (que no puede ser decodificado por decodificadores JSON).

También causa que "decode" parseé valores JSON etiquetados y los deserialice llamando a la metodología "THAW".

Si $enable es false (el valor por defecto), entonces "encode" no considerará esta clase de conversión, y los valores JSON etiquetados causarán un error de parseo en "decode", como si las etiquetas no fueran parte de la gramática.

boolean_values

$json->boolean_values([$false, $true])
($false, $true) = $json->get_boolean_values

Por defecto, los valores booleanos JSON se decodificarán como los objetos $JSON::PP::false y $JSON::PP::true.

Con este método puedes especificar tus propios valores booleanos para la decodificación - al decodificar, JSON "false" se decodificará como una copia de $false, y JSON "true" como $true ("copia" es lo mismo que asignar un valor a otra variable, es decir, "$copy = $false").

Esto es útil cuando quieras pasar una estructura de datos decodificada directamente a otros serializadores como YAML, Data::MessagePack y otros.

Ten en cuenta que esto solo funciona al llamar a "decode". Puedes establecer objetos booleanos incompatibles (como boolean), pero al serializar una estructura de datos con tales objetos booleanos, aún necesitas activar "convert_blessed" (y agregar una metodología "TO_JSON" si es necesario).

Llamar a este método sin argumentos reseteará los valores booleanos a sus valores por defecto.

"get_boolean_values" devolverá ambos valores $false y $true, o una lista vacía si están por defecto.

core_bools

$json->core_bools([$enable]);

Si $enable es true (o se omite), entonces "decode" producirá valores booleanos estándar de Perl. Equivale a llamar:

$json->boolean_values(!!1, !!0)

"get_core_bools" devolverá true si esto se ha establecido. En perl 5.36, también devolverá true si los valores booleanos se han establecido a los booleanos del núcleo de Perl mediante la metodología "boolean_values".

Los métodos "unblessed_bool" y "get_unblessed_bool" se proporcionan como alias para compatibilidad con Cpanel::JSON::XS.

filter_json_object

$json = $json->filter_json_object([$coderef])

Cuando se especifica $coderef, se llamará desde "decode" cada vez que se decodifique un objeto JSON. El único argumento es una referencia al nuevo hash creado. Si el código devuelve un único escalar (que no es necesariamente una referencia), este valor (o una copia de él) se insertará en la estructura deserializada. Si devuelve una lista vacía (NOTA: no "undef", que es un escalar válido), se insertará el hash deserializado original. Este ajuste puede ralentizar la deserialización.

Cuando $coderef se omite o no se define, se eliminará cualquier callback existente y "decode" no modificará la estructura deserializada de ninguna manera.

Ejemplo, convierte todos los objetos JSON en el valor 5:

my $js = JSON::PP->new->filter_json_object(sub { 5 });
# devuelve [5]
$js->decode('[{}]');
# devuelve 5
$js->decode('{"a":1, "b":2}');

filter_json_single_key_object

$json = $json->filter_json_single_key_object($key [=> $coderef])

Funciona de forma muy similar a "filter_json_object", pero solo se llama para objetos JSON con una única clave llamada $key.

Este $coderef se llama antes que el especificado por "filter_json_object", si existe. Se le pasa el único valor del objeto JSON. Si devuelve un único valor, se insertará en la estructura. Si no devuelve nada (no "undef" sino una lista vacía), se llamará a la siguiente callback de "filter_json_object", como si no hubiera callback para clave única.

Si $coderef se omite o no se define, se desactiva la callback correspondiente. Solo puede haber una callback por clave.

Como esta callback se llama con menos frecuencia que "filter_json_object", el tiempo de deserialización no suele verse tan afectado. Por lo tanto, los objetos de clave única son excelentes objetivos para serializar objetos Perl, especialmente como objetos JSON de clave única, que son tan cercanos a la idea de valor etiquetado de JSON (es básicamente un par ID/VALOR). Sin embargo, JSON no los soporta de ninguna manera, así que debes asegurarte de que tus datos nunca parezcan un hash serializado.

Nombres típicos para la clave única son "__class_whatever__", o "$__dollars_are_rarely_used__$" o "}ugly_brace_placement", o incluso cosas como "__class_md5sum(classname)__" para reducir el riesgo de colisiones con hashes reales.

Ejemplo, decodifica objetos JSON de la forma "{"__widget__": <id> }" en el objeto correspondiente $WIDGET{<id>}:

# devuelve lo que está en $WIDGET{5}:
JSON::PP
   ->new
   ->filter_json_single_key_object (__widget__ => sub {
         $WIDGET{ $_[0] }
      })
   ->decode ('{"__widget__": 5')
# puede usarse con una metodología TO_JSON en alguna clase "widget" para serialización a JSON:
sub WidgetBase::TO_JSON {
   my ($self) = @_;
   unless ($self->{id}) {
      $self->{id} = ..get..some..id..;
      $WIDGET{$self->{id}} = $self;
   }
   { __widget__ => $self->{id} }
}

shrink

$json = $json->shrink([$enable])

$enabled = $json->get_shrink

Si $enable es true (o se omite), el texto devuelto por "encode" se reducirá (es decir, se compactará si es posible).

La definición real de lo que hace "shrink" puede cambiar en futuras versiones, pero siempre intentará ahorrar espacio a costa de tiempo.

Si $enable es false, entonces JSON::PP no hace nada.

max_depth

$json = $json->max_depth([$maximum_nesting_depth])

$max_depth = $json->get_max_depth

Establece el nivel máximo de profundidad (por defecto 512) aceptado mientras se codifica o decodifica. Si se detecta un nivel de profundidad más alto en texto JSON o en una estructura de Perl, el codificador y decodificador se detendrán y lanzarán un error en ese punto.

El nivel de profundidad se define por el número de referencias a hash o array que el codificador necesita recorrer para alcanzar un punto dado, o por el número de caracteres "{" o "[" sin su cierre correspondiente que se cruzan para alcanzar un carácter dado en una cadena.

Establecer el máximo a 1 deshabilita cualquier nivel de profundidad, asegurando que el objeto sea solo un único hash/objeto/array.

Si no se especifica un argumento, se utilizará el máximo posible, lo cual rara vez es útil.

Ver "CONSIDERACIONES DE SEGURIDAD" en JSON::XS para más información sobre por qué esto es útil.

max_size

$json = $json->max_size([$maximum_string_size])

$max_size = $json->get_max_size

Establece la longitud máxima (en bytes) del texto JSON que se intentará decodificar. El valor por defecto es 0, lo que significa sin límite. Cuando se llama a "decode" sobre una cadena más larga que este número de bytes, no intentará decodificar la cadena sino que lanzará una excepción. Esta configuración no afecta a "encode" (todavía).

Si no se especifica un argumento, se desactiva la verificación de límite (lo mismo que cuando se especifica 0).

INCREMENTAL

Esta sección también está tomada de JSON::

XS.

En algunos casos, es necesario el análisis incremental de textos JSON. Aunque este módulo siempre tiene que mantener tanto el texto JSON como la estructura de datos Perl resultante en memoria al mismo tiempo, te permite analizar un flujo JSON de forma incremental. Lo hace acumulando texto hasta tener un objeto JSON completo, que luego puede decodificar. Este proceso es similar a usar "decode_prefix" para ver si hay un objeto JSON completo disponible, pero es mucho más eficiente (y puede implementarse con un mínimo de llamadas a métodos)

.

JSON::PP solo intentará analizar el texto JSON cuando esté seguro de tener suficiente texto para obtener un resultado decisivo, usando un analizador muy simple pero verdaderamente incremental. Esto significa que a veces no se detendrá tan pronto como el analizador completo, por ejemplo, no detecta paréntesis no coincidentes. Lo único que garantiza es que comienza a decodificar tan pronto como se ha visto un texto JSON sintácticamente válido. Esto significa que necesitas establecer límites de recursos (por ejemplo, "max_size") para asegurar que el analizador se detenga en presencia de errores de

sintaxis.

Los siguientes métodos implementan este analizador

incremental.

e 
$json->incr_parse( [$string] ) # void context

$obj_or_undef = $json->incr_parse( [$string] ) # scalar context

@obj_or_empty = $json->incr_parse( [$string] ) # list context


INCREMENTAL PARSING


This section describes the incremental parser that allows you to
    parse JSON fragments and to incrementally build up JSON text.




new


my $json = JSON::PP->new


Creates a new JSON::PP object. You can pass arguments to specify
    how the JSON should be parsed and encoded. See JSON::PP->new for
    details.






incr_parse


$obj = $json->incr_parse ($string)


This is the central parsing function. It can both append new text
    and extract objects from the stream accumulated so far (both of these
    functions are optional).


If $string is given, then this string is
    appended to the already existing JSON fragment stored in the
    $json object.


After that, if the function is called in void context, it will
    simply return without doing anything further. This can be used to add more
    text in as many chunks as you want.


If the method is called in scalar context, then it will try to
    extract exactly one JSON object. If that is successful, it will
    return this object, otherwise it will return
    "undef". If there is a parse error, this
    method will croak just as "decode" would
    do (one can then use "incr_skip" to skip
    the erroneous part). This is the most common way of using the method.


And finally, in list context, it will try to extract as many
    objects from the stream as it can find and return them, or the empty list
    otherwise. For this to work, there must be no separators (other than
    whitespace) between the JSON objects or arrays, instead they must be
    concatenated back-to-back. If an error occurs, an exception will be raised
    as in the scalar context case. Note that in this case, any previously-parsed
    JSON texts will be lost.


Example: Parse some JSON arrays/objects in a given string and
    return them.


my @objs = JSON::PP->new->incr_parse ("[5][7][1,2]");






incr_text


$lvalue_string = $json->incr_text


This method returns the currently stored JSON fragment as an
    lvalue, that is, you can manipulate it. This only works when a
    preceding call to "incr_parse" in
    scalar context successfully returned an object. Under all other
    circumstances you must not call this function (I mean it. although in simple
    tests it might actually work, it will fail under real world
    conditions). As a special exception, you can also call this method before
    having parsed anything.


That means you can only use this function to look at or manipulate
    text before or after complete JSON objects, not while the parser is in the
    middle of parsing a JSON object.


This function is useful in two cases: a) finding the trailing text
    after a JSON object or b) parsing multiple JSON objects separated by
    non-JSON text (such as commas).






incr_skip


$json->incr_skip


This will reset the state of the incremental parser and will
    remove the parsed text from the input buffer so far. This is useful after
    "incr_parse" died, in which case the input
    buffer and incremental parser state is left unchanged, to skip the text
    parsed so far and to reset the parse state.


The difference to "incr_reset"
    is that only text until the parse error occurred is removed.






incr_reset


$json->incr_reset


This completely resets the incremental parser, that is, after this
    call, it will be as if the parser had never parsed anything.


This is useful if you want to repeatedly parse JSON objects and
    want to ignore any trailing data, which means you have to reset the parser
    after each successful decode.








MAPPING


Most of this section is also taken from JSON::XS.


This section describes how JSON::PP maps Perl values to JSON
    values and vice versa. These mappings are designed to "do the right
    thing" in most circumstances automatically, preserving round-tripping
    characteristics (what you put in comes out as something equivalent).


For the more enlightened: note that in the following descriptions,
    lowercase perl refers to the Perl interpreter, while uppercase
    Perl refers to the abstract Perl language itself.




JSON ->   PERL



  
object

  
A JSON object becomes a reference to a hash in Perl. No ordering of object
      keys is preserved (JSON does not preserve object key ordering
    itself).

  
array

  
A JSON array becomes a reference to an array in Perl.

  
string

  
A JSON string becomes a string scalar in Perl - Unicode codepoints in JSON
      are represented by the same codepoints in the Perl string, so no manual
      decoding is necessary.

  
number

  
A JSON number becomes either an integer, numeric (floating point) or
      string scalar in perl, depending on its range and any fractional parts. On
      the Perl level, there is no difference between those as Perl handles all
      the conversion details, but an integer may take slightly less memory and
      might represent more values exactly than floating point numbers.
    
If the number consists of digits only, JSON::PP will try to
        represent it as an integer value. If that fails, it will try to
        represent it as a numeric (floating point) value if that is possible
        without loss of precision. Otherwise it will preserve the number as a
        string value (in which case you lose roundtripping ability, as the JSON
        number will be re-encoded to a JSON string).

    
Numbers containing a fractional or exponential part will
        always be represented as numeric (floating point) values, possibly at a
        loss of precision (in which case you might lose perfect roundtripping
        ability, but the JSON number will still be re-encoded as a JSON
      number).

    
Note that precision is not accuracy - binary floating point
        values cannot represent most decimal fractions exactly, and when
        converting from and to floating point, JSON::PP only guarantees
        precision up to but not including the least significant bit.

    
When "allow_bignum" is
        enabled, big integer values and any numeric values will be converted
        into Math::BigInt and Math::BigFloat objects respectively, without
        becoming string scalars or losing precision.

  

  
true, false

  
These JSON atoms become "JSON::PP::true"
      and "JSON::PP::false", respectively.
      They are overloaded to act almost exactly like the numbers
      1 and 0. You can check
      whether a scalar is a JSON boolean by using the
      "JSON::PP::is_bool" function.

  
null

  
A JSON null atom becomes "undef" in
      Perl.

  
shell-style
    comments ("# text")

  
As a nonstandard extension to the JSON syntax that is enabled by the
      "relaxed" setting, shell-style comments
      are allowed. They can start anywhere outside strings and go till the end
      of the line.

  
tagged values
    ("(tag)value").

  
Another nonstandard extension to the JSON syntax, enabled with the
      "allow_tags" setting, are tagged values.
      In this implementation, the tag must be a perl package/class name
      encoded as a JSON string, and the value must be a JSON array
      encoding optional constructor arguments.
    
See "OBJECT SERIALISATION", below, for details.

    is a truly typeless language, so we can only guess which JSON type is meant
    by a Perl value.

Esta sección está tomada de JSON::

XS.

El lector interesado puede haber visto un número de banderas que significan codificaciones o juegos de caracteres - "utf8", "latin1" y "ascii". Parece haber algo de confusión sobre lo que hacen, así que aquí hay una breve

comparación:

"utf8" controla si el texto JSON creado por "encode" (y esperado por "decode") está codificado en UTF-8 o no, mientras que "latin1" y "ascii" solo controlan si "encode" escapa valores de caracteres fuera del rango de su respectivo juego de caracteres. Ninguna de estas banderas entra en conflicto entre sí, aunque algunas combinaciones tienen menos sentido que

otras.

Se ha tenido cuidado de hacer que todas las banderas sean simétricas con respecto a "encode" y "decode", es decir, los textos codificados con cualquier combinación de estos valores de bandera se decodificarán correctamente cuando se usen las mismas banderas - en general, si usas ajustes de bandera diferentes mientras codificas vs. cuando decodificas, probablemente tienes un error en algún

lugar.

A continuación viene una discusión detallada de estas banderas. Ten en cuenta que un "juego de caracteres" es simplemente un conjunto abstracto de pares carácter-código de punto, mientras que una codificación toma esos números de código de punto y los codifica, en nuestro caso en octetos. Unicode es (entre otras cosas) un juego de caracteres, UTF-8 es una codificación, e ISO-8859-1 (= latin 1) y ASCII son ambos juegos de caracteres y codificaciones al mismo tiempo, lo cual puede ser

confuso.
Banderas "utf8"
deshabilitadas
Cuando "utf8" está deshabilitado (el valor por defecto), entonces "encode"/"decode" generan y esperan cadenas Unicode, es decir, los caracteres con valores ordinales Unicode altos (> 255) se codificarán como tales caracteres, y del mismo modo tales caracteres se decodifican tal cual, no se les harán cambios, excepto "(re-)interpretarlos" como puntos de código Unicode o caracteres Unicode, respectivamente (para Perl, estas son la misma cosa en cadenas a menos que hagas cosas graciosas/raras/tontas).

Esto es útil cuando quieres hacer la codificación tú mismo (por ejemplo, cuando quieres tener textos JSON codificados en UTF-16) o cuando alguna otra capa hace la codificación JSON::backportPP(3pm)

NAME

JSON::backportPP - JSON::XS compatible JSON::PP implementation

SYNOPSIS

 use JSON::backportPP;
 my $json = JSON::backportPP->new( 'pretty' => 1, 'indent' => 4 );
 my $string = $json->encode( { foo => [1, 2, "bar"] } );
 print $string;
 # {
 #     "foo": [
 #         1,
 #         2,
 #         "bar"
 #     ]
 # }

 my $perl_native = $json->decode( $string );

 # or functional interface
 use JSON::backportPP qw( encode_json decode_json to_json from_json );
 my $string = encode_json( { foo => [1, 2, "bar"] } );
 my $perl_native = decode_json( $string );

DESCRIPTION

This module implements the JSON::XS API and API of JSON (from backpan) as JSON::PP. It is meant to be used for systems that don't have JSON::XS installed, but need it.

It is slower than JSON::XS and JSON::Cpanel, but should be mostly compatible.

This module implements the same API as JSON::XS and JSON, and is intended as a fallback for environments where JSON::XS might not be available or installable.

FUNCTIONAL INTERFACE

The functional interface is provided via the exported subroutines encode_json, decode_json, to_json, and from_json.

encode_json
Takes a Perl data structure and returns a JSON string. See JSON::backportPP->new for available options.
decode_json
Takes a JSON string and returns the corresponding Perl data structure. See JSON::backportPP->new for available options.
to_json
Same as encode_json.
from_json
Same as decode_json.

OBJECT-ORIENTED INTERFACE

The object oriented interface is provided via the JSON::backportPP class.

new
Creates a new JSON::backportPP object. The constructor accepts an optional hash of options. These options are mostly identical to those of JSON::XS:

The following options are available:

allow_nonref
Allows encoding of non-references (like numbers, strings, etc.). By default this is disabled.
allow_blessed
Allows encoding of blessed references (objects). By default this is disabled. If enabled, it tries to call the TO_JSON method on the object and encodes its return value.
allow_unknown
Allows encoding of types that are not explicitly JSON-enabled. This is disabled by default. If enabled, unknown types will be stringified.
canonical
If true, the keys of objects are sorted. This is useful for comparing JSON data.
croak_pretty
Deprecated. Use pretty instead.
pretty
If true, the output will be pretty-printed. Defaults to false.
indent
String to use for indentation if pretty is true. Defaults to " " (a single space).
space_before_colon
If true, a space will be added before the colon in key-value pairs. Defaults to false.
space_after_colon
If true, a space will be added after the colon in key-value pairs. Defaults to true.
space_before_comma
If true, a space will be added before the comma between elements. Defaults to false.
space_after_comma
If true, a space will be added after the comma between elements. Defaults to true.
check_circular
If true, circular references will be detected and croaked upon. Defaults to true.
utf8
If true, the input strings are expected to be UTF-8 encoded and the output will be UTF-8 encoded binary string. Defaults to false (Unicode strings).
latin1
If true, characters with ordinal values greater than 255 will be escaped. Default to false.
ascii
If true, characters with ordinal values greater than 127 will be escaped. Default to false.
bytes
If true, the input is treated as a binary string. This is the same as utf8 => 1.
encoder
Specifies the fallback encoder to use if the default Perl encoder fails. This is usually not needed.
decoder
Specifies the fallback decoder to use if the default Perl decoder fails. This is usually not needed.
filter_json_cref
If true, then references are not encoded as JSON arrays/objects, but as JSON null. This is useful for filtering specific references from JSON output, like C.
encode
Encodes a Perl data structure into a JSON string according to the object's configuration.
decode
Decodes a JSON string into a Perl data structure according to the object's configuration.

FLAGS FOR JSON::PP ONLY

The following flags are only available in JSON::PP and not in JSON::XS or JSON:

allow_tags
Allows encoding of blessed references using the TAGS mechanism. This is mostly for internal use.
tag_filter
A callback sub used to filter tags when allow_tags is enabled.

INCREMENTAL PARSING

JSON::backportPP supports incremental parsing via the incr_parse method. This is useful for parsing large JSON documents that do not fit into memory.

incr_parse
Takes a callback subroutine as an argument. The callback will be called with the decoded Perl data structure whenever a complete JSON object, array, or value is parsed.
 my $json = JSON::backportPP->new();
 $json->incr_parse(sub {
     my ($data) = @_;
     # Process $data
 });
 $json->parse( $chunk1 );
 $json->parse( $chunk2 );

ENCODING/CODESET FLAG NOTES

The utf8, latin1, and ascii flags control how strings are encoded and decoded.

"utf8" flag enabled
If the "utf8"-flag is enabled, "encode"/"decode" will encode all characters using the corresponding UTF-8 multi-byte sequence, and will expect your input strings to be encoded as UTF-8, that is, no "character" of the input string must have any value > 255, as UTF-8 does not allow that.

The "utf8" flag therefore switches between two modes: disabled means you will get a Unicode string in Perl, enabled means you get an UTF-8 encoded octet/binary string in Perl.

"latin1" or "ascii" flags enabled
With "latin1" (or "ascii") enabled, "encode" will escape characters with ordinal values > 255 (> 127 with "ascii") and encode the remaining characters as specified by the "utf8" flag.

If "utf8" is disabled, then the result is also correctly encoded in those character sets (as both are proper subsets of Unicode, meaning that a Unicode string with all character values < 256 is the same thing as a ISO-8859-1 string, and a Unicode string with all character values < 128 is the same thing as an ASCII string in Perl).

If "utf8" is enabled, you still get a correct UTF-8-encoded string, regardless of these flags, just some more characters will be escaped using "\uXXXX" then before.

Note that ISO-8859-1-encoded strings are not compatible with UTF-8 encoding, while ASCII-encoded strings are. That is because the ISO-8859-1 encoding is NOT a subset of UTF-8 (despite the ISO-8859-1 codeset being a subset of Unicode), while ASCII is.

Surprisingly, "decode" will ignore these flags and so treat all input values as governed by the "utf8" flag. If it is disabled, this allows you to decode ISO-8859-1- and ASCII-encoded strings, as both strict subsets of Unicode. If it is enabled, you can correctly decode UTF-8 encoded strings.

So neither "latin1" nor "ascii" are incompatible with the "utf8" flag - they only govern when the JSON output engine escapes a character or not.

The main use for "latin1" is to relatively efficiently store binary data as JSON, at the expense of breaking compatibility with most JSON decoders.

The main use for "ascii" is to force the output to not contain characters with values > 127, which means you can interpret the resulting string as UTF-8, ISO-8859-1, ASCII, KOI8-R or most about any character set and 8-bit-encoding, and still get the same data structure back. This is useful when your channel for JSON transfer is not 8-bit clean or the encoding might be mangled in between (e.g. in mail), and works because ASCII is a proper subset of most 8-bit and multibyte encodings in use in the world.
