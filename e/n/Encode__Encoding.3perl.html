Como se menciona en Encode, las codificaciones son (al menos en la implementación actual) definidas como objetos. ¿Por qué demonios la API de Encode es

diferente?

Debe notarse que el $check comportamiento es diferente de la API pública externa. La lógica es que el caso "sin verificar" es útil cuando la codificación es parte de un flujo que puede estar reportando errores (por ejemplo, STDERR). En tales casos, es deseable que todo pase de alguna manera sin causar errores adicionales que oscurezcan el original. Además, la codificación está mejor posicionada para saber cuál es el carácter de reemplazo correcto, así que si ese es el comportamiento deseado, dejar que el código de bajo nivel lo haga es lo más

eficiente.

Por el contrario, si $check es verdadero, el esquema anterior permite a la codificación hacer todo lo que pueda y decirle a la capa superior cuánto fue eso. Lo que falta actualmente es un mecanismo para reportar qué salió mal. La interfaz más probable será una llamada de método adicional al objeto, o quizás (para evitar forzar objetos por flujo en codificaciones de otro modo sin estado) un parámetro

adicional.

También es altamente deseable que las clases de codificación hereden de "Encode::Encoding" como clase base. Esto permite que esa clase defina comportamiento adicional para todos los objetos de

codificación. 
package Encode::MyEncoding;
use parent qw(Encode::Encoding);
__PACKAGE__->Define(qw(myCanonical myAlias))
;

para crear un objeto con "bless {Name => ...}, $class", y llamar a define_encoding. Heredan su método "name" de "Encode::Enco

ding".
