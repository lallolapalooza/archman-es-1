encoding(3perl) Guía de referencia del programador de Perl encoding(3perl)

NOMBRE

encoding - permite escribir tu script en codificaciones no ASCII ni UTF-8

ADVERTENCIA

Este módulo ha sido desaprobado desde perl v5.18. Ver "DESCRIPCIÓN" y "ERRORES".

SINOPSIS

use encoding "greek";  # ¿Le gusta Perl el griego?
use encoding "euc-jp"; # ¡Jperl!
# o incluso puedes hacer esto si tu shell soporta tu codificación nativa
perl -Mencoding=latin2 -e'...' # ¿Se siente centroeuropeo?
perl -Mencoding=euc-kr -e'...' # ¿O coreano?
# más control
# Un simple convertidor euc-cn => utf-8
use encoding "euc-cn", STDOUT => "utf8";  while(<>){print};
# "no encoding;" soportado
no encoding;
# una forma alternativa, Filtro
use encoding "euc-jp", Filter=>1;
# ahora puedes usar identificadores kanji -- ¡en euc-jp!
# codificar basado en la configuración regional actual - sólo para propósitos especializados;
# ¡¡lleno de peligros!!
use encoding ':locale';

DESCRIPCIÓN

Este pragmática se utiliza para permitir que un script de Perl se escriba en codificaciones que no son estrictamente ASCII ni UTF-8. Traduce todo o partes del script del programa Perl de una codificación dada a UTF-8, y cambia las capas de PerlIO de "STDIN" y "STDOUT" a la codificación especificada.

Este pragmática data de los días en que los editores con soporte UTF-8 eran poco comunes. Pero eso fue hace mucho tiempo, y la necesidad de ello ha disminuido considerablemente. Eso, junto con el hecho de que no funciona con hilos, junto con otros problemas (ver "ERRORES"), ha llevado a su desaprobación. Está previsto eliminar este pragmática en una futura versión de Perl. El código nuevo debe escribirse en UTF-8, y usar el pragmática "use utf8" en su lugar (ver perluniintro y utf8 para detalles). El código antiguo debe convertirse a UTF-8, a través de algo como la receta en la "SINOPSIS" (aunque este enfoque simple puede requerir ajustes manuales posteriores).

Si UTF-8 no es una opción, se recomienda usar un filtro de origen simple, como el proporcionado por Filter::Encoding en CPAN o la propia opción "Filter" de este pragmática (ver abajo).

El único uso legítimo de este pragmática es casi con seguridad uno por archivo, cerca de la parte superior, con ámbito de archivo, ya que es probable que el archivo solo se escriba en una codificación. Se aplican restricciones adicionales en Perls anteriores a v5.22 (ver "Antes de Perl v5.22").

Hay dos modos básicos de operación (más apagarlo):

"use encoding ['ENCNAME'] ;"
Tenga en cuenta: Este modo de operación ya no es compatible a partir de Perl v5.26.

Esta es la operación normal. Traduce varios literales encontrados en el archivo fuente de Perl de la codificación ENCNAME a UTF-8, y de manera similar convierte los puntos de código de caracteres. Esto se usa cuando el script es una combinación de ASCII (para los nombres de variables y la puntuación, etc.), pero los datos literales están en la codificación especificada.

ENCNAME es opcional. Si se omite, se utiliza la codificación especificada en la variable de entorno "PERL_ENCODING". Si no está establecida, o la codificación resuelta no es conocida por "Encode", se lanzará el error "Unknown encoding 'ENCNAME'".

A partir de Perl v5.8.6 ("Encode" versión 2.0.1), ENCNAME puede ser el nombre ":locale". Esto es para aplicaciones muy especializadas y se documenta en "El subpragmática ":locale"" abajo.

Los literales que se convierten son "q//, qq//, qr//, qw///, qx//", y a partir de v5.8.1, "tr///". Las operaciones que realizan conversiones incluyen "chr", "ord", "utf8::upgrade" (pero no "utf8::downgrade"), y "chomp".

También a partir de v5.8.1, el pseudo-manejador de archivo "DATA" se traduce de la codificación a UTF-8.

Por ejemplo, puedes escribir código en EUC-JP de la siguiente manera:

my $Rakuda = "\xF1\xD1\xF1\xCC"; # Camello en Kanji
             #<-caracter-><-caracter->   # 4 octetos
s/\bCamel\b/$Rakuda/;

Y con "use encoding "euc-jp"" en efecto, es lo mismo que ese código en UTF-8:

my $Rakuda = "\x{99F1}\x{99DD}"; # dos caracteres Unicode
s/\bCamel\b/$Rakuda/;

Ver "EJEMPLO" abajo para un ejemplo más completo.

A menos que "${^UNICODE}" (disponible a partir de v5.8.2) exista y sea distinto de cero, las capas de PerlIO de "STDIN" y "STDOUT" se establecen a ":encoding(ENCNAME)". Por lo tanto,

use encoding "euc-jp";
my $message = "Camel es el símbolo de perl.\n";
my $Rakuda = "\xF1\xD1\xF1\xCC"; # Camello en Kanji
$message =~ s/\bCamel\b/$Rakuda/;
print $message;

imprimirá

"\xF1\xD1\xF1\xCC es el símbolo de perl.\n"

no

"\x{99F1}\x{99DD} es el símbolo de perl.\n"

Puedes anular esto dando argumentos adicionales; ver abajo.

Ten en cuenta que "STDERR" NO se cambiará, independientemente.

También ten en cuenta que los manejadores de archivo no estándar permanecen sin afectar. Usa "use open" o "binmode" para cambiar las capas de esos.

"use encoding ENCNAME, Filter=>1;"
Esto opera como arriba, pero el argumento "Filter" con un valor distinto de cero hace que todo el script, y no solo los literales, se traduzca de la codificación a UTF-8. Esto permite que los identificadores en el origen también estén en esa codificación. (Pueden ocurrir problemas si la codificación no es un superconjunto de ASCII; imagina que todos tus puntos y comas se traducen a algo diferente). Se puede usar esta forma para hacer que 
${"\x{4eba}"}++

funcione. (Esto es equivalente a "$humano++", donde humano es un solo ideograma Han).

Esto efectivamente significa que tu código fuente se comporta como si estuviera escrito en UTF-8 con "'use utf8"' en efecto. Así que incluso si tu editor solo soporta Shift_JIS, por ejemplo, aún puedes probar ejemplos del Capítulo 15 de "Programming Perl, 3rd Ed.".

Esta opción es significativamente más lenta que la otra.

"no encoding;"
Anula la codificación del script. Las capas de "STDIN" y "STDOUT" se restablecen a "":raw"" (el flujo crudo sin procesar por defecto de bytes).

OPCIONES

Establecer "STDIN" y/o "STDOUT" individualmente

Las codificaciones de "STDIN" y "STDOUT" se pueden establecer individualmente mediante parámetros al pragmática:

use encoding 'euc-tw', STDIN => 'greek'  ...;

En este caso, no puedes omitir el primer ENCNAME. "STDIN => undef" desactiva completamente la transcodificación de E/S para ese manejador de archivo.

El sub-pragma ":

locale"

A partir de la versión v5.8.6, el nombre de la codificación puede ser ":locale". Esto significa que la codificación se toma de la configuración regional actual, y no está codificada de forma fija por el pragma. Dado que un script realmente solo puede estar codificado en exactamente una codificación, esta opción es peligrosa. Solo tiene sentido si el script mismo está escrito en ASCII, y todas las configuraciones regionales posibles que estén en uso cuando se ejecute el script son superconjuntos de ASCII. Eso significa que el script mismo no se modifica, pero a los manejadores de E/S se les añade la codificación especificada, y las operaciones como "chr" y "ord" usan esa

codificación.

La lógica para encontrar qué configuración regional usa ":locale" es la

siguiente:
1
.
Si la plataforma soporta la interfaz langinfo(CODESET), se usa el codeset devuelto como codificación predeterminada para el pragma
open.
2
.
Si 1. no funcionó pero estamos bajo el pragma locale, las variables de entorno "LC_ALL" y "LANG" (en ese orden) se buscan codificaciones (la parte después del ".", si existe), y si se encuentra alguna, se usa como codificación predeterminada para el pragma
open.
3
.
Si 1. y 2. no funcionaron, las variables de entorno "LC_ALL" y "LANG" (en ese orden) se buscan algo que parezca UTF-8, y si se encuentra alguno, ":utf8" se usa como codificación pred
eterminada pa
ra el pragma open.

Si sus variables de entorno de configuración regional ("LC_ALL", "LC_CTYPE", "LANG") contienen las cadenas 'UTF-8' o 'UTF8' (coincidencia sin distinguir mayúsculas de minúsculas), la codificación predeterminada de su "STDIN", "STDOUT" y "STDERR", y de cualquier apertura de

archivo
posterior, es UTF-8.

CODIFICACIONES

Observe que solo se ven afectados los literales (cadena o expresión regular) que tienen solo puntos de código heredados: si mezcla datos

como 
\x{100}\xDF
\xDF\x{100}

se asume que los datos están en (Latin 1 y) Unicode, no en su codificación nativa. En otras palabras, esto coincidirá en

"greek": 
"\xDF" =~ /\x{3af}
/

pero esto

no 
"\xDF\x{100}" =~ /\x{3af}\x{100}
/

ya que el "\xDF" (ISO 8859-7 GREEK SMALL LETTER IOTA WITH TONOS) de la izquierda no se actualizará a "\x{3af}" (Unicode GREEK SMALL LETTER IOTA WITH TONOS) debido al "\x{100}" de la izquierda. No debe mezclar sus datos heredados y Unicode en la misma

cadena.

Este pragma también afecta la codificación del rango de puntos de código 0x80..0xFF: normalmente los caracteres en ese rango se dejan como bytes de ocho bits (a menos que se combinen con caracteres con puntos de código 0x100 o mayores, en cuyo caso todos los caracteres necesitan convertirse en UTF-8 codificado), pero si el pragma "encoding" está presente, incluso el rango 0x80..0xFF siempre se codifica en

UTF-8.

Después de todo, lo mejor de este pragma es que no tiene que recurrir a \x{....}

solo para escribir su nombre en una codificación nativa. Así que siéntase libr
e de poner sus cadenas en su codificación entre comillas y en expresiones regulares.
