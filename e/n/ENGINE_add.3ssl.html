DESCRIPCIÓN

Todas las funciones descritas en esta página están obsoletas. Las aplicaciones deberían usar en su lugar las API de proveedores.

Estas funciones crean, manipulan y usan módulos criptográficos en forma de objetos ENGINE . Estos objetos actúan como contenedores para implementaciones de algoritmos criptográficos, y admiten un mecanismo de conteo de referencias que permite cargarlos y descargarlos dinámicamente de la aplicación en ejecución.

La funcionalidad criptográfica que puede proporcionar una implementación ENGINE incluye las siguientes abstracciones;

RSA_METHOD - para proporcionar implementaciones alternativas de RSA
DSA_METHOD, DH_METHOD, RAND_METHOD, ECDH_METHOD, ECDSA_METHOD,
      - de forma similar para otras API de OpenSSL
EVP_CIPHER - potencialmente múltiples algoritmos de cifrado (indexados por 'nid')
EVP_DIGEST - potencialmente múltiples algoritmos hash (indexados por 'nid')
carga de claves - carga de claves EVP_PKEY públicas y/o privadas

Conteo de referencias y manejadores

Debido a la naturaleza modular de la API ENGINE, los punteros a ENGINEs deben tratarse como manejadores - es decir, no solo como punteros, sino también como referencias al objeto ENGINE subyacente. Es decir, uno debería obtener una nueva referencia al hacer copias de un puntero a ENGINE si las copias se van a usar (y liberar) de forma independiente.

Los objetos ENGINE tienen dos niveles de conteo de referencias para corresponder a la forma en que se usan los objetos. En el nivel más básico, cada puntero a ENGINE es inherentemente una referencia estructural - se requiere una referencia estructural para usar el valor del puntero en absoluto, ya que este tipo de referencia es una garantía de que la estructura no puede ser desasignada hasta que la referencia sea liberada.

Sin embargo, una referencia estructural no proporciona ninguna garantía de que el ENGINE esté inicializado y sea capaz de usar cualquiera de sus implementaciones criptográficas. De hecho, es bastante posible que la mayoría de los ENGINEs no se inicialicen en absoluto en entornos típicos, ya que los ENGINEs suelen estar diseñadospara soportar hardware especializado. Para usar la funcionalidad de un ENGINE, necesitas una referencia funcional . Este tipo de referencia puede considerarse una forma especializada de referencia estructural, porque cada referencia funcional implícitamente contiene también una referencia estructural; sin embargo, para evitar errores de programación difíciles de encontrar, se recomienda tratar los dos tipos de referencia de forma independiente. Si tienes una referencia funcional a un ENGINE, tienes la garantía de que el ENGINE ha sido inicializado y está listo para realizar operaciones criptográficas, y permanecerá inicializado hasta después de que hayas liberado tu referencia.

Referencias estructurales

Este tipo básico de referencia se utiliza para instanciar nuevos ENGINEs, iterar sobre la lista enlazada interna de OpenSSL de ENGINEs cargados, leer información sobre un ENGINE, etc. Esencialmente, una referencia estructural es suficiente si solo necesitas consultar o manipular los datos de una implementación de ENGINE en lugar de usar su funcionalidad.

La ENGINE_new() función devuelve una referencia estructural a un objeto ENGINE nuevo (vacío). Hay otras funciones de la API de ENGINE que devuelven referencias estructurales, tales como; ENGINE_by_id(), ENGINE_get_first(), ENGINE_get_last(), ENGINE_get_next(), ENGINE_get_prev(). Todas las referencias estructurales deben liberarse mediante una llamada correspondiente a la ENGINE_free() función; el objeto ENGINE en sí solo se limpiará y desasignará realmente cuando se libere la última referencia estructural. Si el argumento de ENGINE_free() es NULL, no se hace nada.

También debe tenerse en cuenta que muchas llamadas a funciones de la API de ENGINE que aceptan una referencia estructural obtendrán internamente otra referencia; típicamente esto ocurre siempre que el ENGINE proporcionado sea necesario por OpenSSL después de que la función haya devuelto. Por ejemplo, la función para añadir un nuevo ENGINE a la lista interna de OpenSSL es ENGINE_add() ; si esta función devuelve éxito, entonces OpenSSL habrá almacenado internamente una nueva referencia estructural, por lo que el llamante sigue siendo responsable de liberar su propia referencia con ENGINE_free() cuando haya terminado con ella. De una manera similar, algunas funciones liberarán automáticamente la referencia estructural que se les pasa si parte del trabajo de la función es hacerlo. Por ejemplo, las ENGINE_get_next() y ENGINE_get_prev() funciones se utilizan para iterar sobre la lista interna de ENGINEs; devolverán una nueva referencia estructural al ENGINE siguiente (o anterior) en la lista o NULL si están al final (o al principio) de la lista, pero en cualquier caso la referencia estructural pasada a la función se libera en nombre del llamante.

Para aclarar el manejo de referencias de una función en particular, uno siempre debe consultar la página de documentación "man" de esa función, o en su defecto, el <openssl/engine.h> archivo de cabecera incluye algunas pistas.

Referencias funcionales

Como se mencionó, las referencias funcionales existen cuando se requiere que la funcionalidad criptográfica de un ENGINE esté disponible. Una referencia funcional se puede obtener de dos maneras; a partir de una referencia estructural existente al ENGINE requerido, o pidiendo a OpenSSL el ENGINE operativo predeterminado para un propósito criptográfico dado.

Para obtener una referencia funcional a partir de una referencia estructural existente, llama a la ENGINE_init() función. Devuelve cero si el ENGINE no estaba ya operativo y no pudo inicializarse correctamente (por ejemplo, falta de controladores del sistema, no hay hardware especial conectado, etc.), de lo contrario devolverá un valor distinto de cero para indicar que el ENGINE está ahora operativo y habrá asignado una nueva referencia funcional al ENGINE. Todas las referencias funcionales se liberan llamando a ENGINE_finish() (que elimina también la referencia estructural implícita).

La segunda manera de obtener una referencia funcional es pidiendo a OpenSSL una implementación predeterminada para una tarea dada, por ejemplo, mediante ENGINE_get_default_RSA(), ENGINE_get_default_cipher_engine(), etc. Estas se discuten en la siguiente sección, aunque normalmente no son requeridas por los programadores de aplicaciones ya que se usan automáticamente al crear y usar los tipos específicos de algoritmo relevantes en OpenSSL, tales como RSA, DSA, EVP_CIPHER_CTX, etc.

Implementaciones predeterminadas

Para cada abstracción soportada, el código de ENGINE mantiene una tabla interna de estado para controlar qué implementaciones están disponibles para una abstracción dada y cuáles deberían usarse por defecto. Estas implementaciones se registran en las tablas y se indexan por un valor 'nid', porque abstracciones como EVP_CIPHER y EVP_DIGEST soportan muchos algoritmos y modos distintos, y los ENGINEs pueden soportar arbitrariamente muchos de ellos. En el caso de otras abstracciones como RSA, DSA, etc., solo hay un "algoritmo", por lo que todas las implementaciones se registran implícitamente usando el mismo índice 'nid'.

Cuando se solicita un ENGINE predeterminado para una abstracción/algoritmo/modo dado (por ejemplo, al llamar a RSA_new_method(NULL)), se hará una llamada "get_default" al subsistema de ENGINE para procesar la tabla de estado correspondiente y devolver una referencia funcional a un ENGINE inicializado cuya implementación debería usarse. Si ningún ENGINE debería (o puede) usarse, devolverá NULL y el llamante operará con un manejador de ENGINE NULL; esto usualmente equivale a usar la implementación de software convencional. En este último caso, OpenSSL se comportará desde entonces de la manera en que lo hacía antes de que existiera la API de ENGINE.

Cada tabla de estado tiene un indicador para anotar si ha procesado esta consulta "get_default" desde que la tabla fue modificada por última vez, porque para procesar esta pregunta debe iterar sobre todos los ENGINEs registrados en la tabla intentando inicializar cada uno de ellos a su vez, por si uno de ellos está operativo. Si devuelve una referencia funcional a un ENGINE, también almacenará en caché otra referencia para acelerar el procesamiento de consultas futuras (sin necesidad de iterar sobre la tabla). Del mismo modo, almacenará en caché una respuesta NULL si no había ningún ENGINE disponible para que las consultas futuras no repitan la misma iteración a menos que la tabla de estado cambie. Este comportamiento también puede modificarse; si se establece el indicador ENGINE_TABLE_FLAG_NOINIT (usando ENGINE_set_table_flags()), no se realizarán intentos de inicialización; en su lugar, la única manera de que la tabla de estado devuelva un ENGINE distinto de NULL a la consulta "get_default" será si uno se establece expresamente en la tabla. Por ejemplo, ENGINE_set_default_RSA() hace el mismo trabajo que ENGINE_register_RSA() excepto que también establece la respuesta en caché de la tabla de estado para la consulta "get_default". En el caso de abstracciones como EVP_CIPHER, donde las implementaciones se indexan por 'nid', estos indicadores y respuestas en caché son distintos para cada valor de 'nid'.

Requisitos de la aplicación

Esta sección explicará las cosas básicas que un programador de aplicaciones debería soportar para hacer disponibles al usuario los elementos más útiles de la funcionalidad de ENGINE. Lo primero que hay que considerar es si el programador desea hacer disponibles módulos de ENGINE alternativos a la aplicación y al usuario. OpenSSL mantiene una lista enlazada interna de ENGINEs "visibles" desde la cual debe operar; al inicio, esta lista está vacía y de hecho, si una aplicación no llama a ninguna función de la API de ENGINE y usa enlace estático contra openssl, entonces el binario de la aplicación resultante no contendrá ningún código de ENGINE alternativo en absoluto. Así que la primera consideración es si alguna/todas las implementaciones de ENGINE disponibles deberían hacerse visibles a OpenSSL; esto se controla llamando a las varias funciones de "carga".

El hecho de que los ENGINEs se hagan visibles a OpenSSL (y por lo tanto se enlacen en el programa y se carguen en memoria en tiempo de ejecución) no significa que estén "registrados" o que OpenSSL los llame para usarlos automáticamente ; ese comportamiento es algo que la aplicación debe controlar. Algunas aplicaciones querrán permitir al usuario especificar exactamente qué ENGINE quiere usar, si es que se va a usar alguno. Otras pueden preferir cargar todo el soporte y hacer que OpenSSL use automáticamente en tiempo de ejecución cualquier ENGINE que sea capaz de inicializarse correctamente; es decir, asumir que esto corresponde a hardware de aceleración conectado a la máquina o algo por el estilo. Probablemente hay numerosas otras formas en que las aplicaciones pueden preferir manejar las cosas, así que simplemente ilustraremos las consecuencias tal como se aplican a un par de casos simples y dejaremos a los desarrolladores que consideren estos y el código fuente de las utilidades integradas de openssl como guías.

Si no se llaman a funciones de la API de ENGINE dentro de una aplicación, entonces OpenSSL no asignará ningún recurso interno. Sin embargo, antes de OpenSSL 1.1.0, si se cargaban algunos ENGINEs, incluso si no se registraban o usaban, era necesario llamar a ENGINE_cleanup() antes de que el programa terminara.

Uso de una implementación de ENGINE específica

Aquí asumiremos que una aplicación ha sido configurada por su usuario o administrador para querer usar el ENGINE "ACME" si está disponible en la versión de OpenSSL con la que se compiló la aplicación. Si está disponible, debería usarse por defecto para todas las operaciones de RSA, DSA y cifrado simétrico; de lo contrario, OpenSSL debería usar su software integrado como de costumbre. El siguiente código ilustra cómo abordar esto;

ENGINE *e;
const char *engine_id = "ACME";
ENGINE_load_builtin_engines();
e = ENGINE_by_id(engine_id);
if (!e)
    /* el motor no está disponible */
    return;
if (!ENGINE_init(e)) {
    /* el motor no pudo inicializarse, libera 'e' */
    ENGINE_free(e);
    return;
}
if (!ENGINE_set_default_RSA(e))
    /*
     * Esto solo debería ocurrir cuando 'e' no puede inicializarse, pero la
     * sentencia anterior sugiere que sí lo hizo.
     */
    abort();
ENGINE_set_default_DSA(e);
ENGINE_set_default_ciphers(e);
/* Libera la referencia funcional de ENGINE_init() */
ENGINE_finish(e);
/* Libera la referencia estructural de ENGINE_by_id() */
ENGINE_free(e);

Uso automático de implementaciones de ENGINE integradas

Aquí asumiremos que queremos cargar y registrar todas las implementaciones de ENGINE incluidas con OpenSSL, de modo que para cualquier algoritmo criptográfico requerido por OpenSSL, si hay un ENGINE que lo implementa y puede inicializarse, debería usarse. El siguiente código ilustra cómo esto puede funcionar;

/* Carga todos los ENGINEs incluidos en la memoria y los hace visibles */
ENGINE_load_builtin_engines();
/* Registra todos ellos para cada algoritmo que colectivamente implementan */
ENGINE_register_all_complete();

Eso es todo lo que se requiere. Por ejemplo, la próxima vez que OpenSSL intente configurar una clave RSA, cualquier ENGINE incluido que implemente RSA_METHOD será pasado a ENGINE_init() y si alguno de ellos tiene éxito, ese ENGINE será establecido como el predeterminado para el uso de RSA a partir de entonces.

Soporte de configuración avanzada

Existe un mecanismo soportado por el marco de trabajo ENGINE que permite a cada implementación de ENGINE definir un conjunto arbitrario de "comandos" de configuración y exponerlos a OpenSSL y a cualquier aplicación basada en OpenSSL. Este mecanismo se basa completamente en el uso de pares nombre-valor y asume entrada ASCII (¡no unicode ni UTF por ahora!), por lo que es ideal si las aplicaciones quieren proporcionar una manera transparente para que los usuarios proporcionen "directivas" de configuración arbitrarias directamente a dichos ENGINEs. También es posible para la aplicación interrogar dinámicamente a las implementaciones de ENGINE cargadas sobre los nombres, descripciones y indicadores de entrada de sus "comandos de control" disponibles, proporcionando un esquema de configuración más flexible. Sin embargo, si se espera que el usuario sepa qué dispositivo ENGINE está utilizando (en el caso de hardware especializado, esto va de suyo), entonces las aplicaciones pueden no necesitar preocuparse por descubrir los comandos de control soportados y simplemente preferir pasar ajustes a los ENGINEs exactamente como son proporcionados por el usuario.

Antes de ilustrar cómo funcionan los comandos de control, vale la pena mencionar para qué se usan típicamente. En términos generales, hay dos usos para los comandos de control; el primero es proporcionar los detalles necesarios a la implementación (que puede no saber nada específico sobre el sistema anfitrión) para que pueda ser inicializada para su uso. Esto podría incluir la ruta a cualquier archivo de controlador o de configuración que necesite cargar, direcciones de red requeridas, identificadores de tarjetas inteligentes, contraseñas para inicializar dispositivos protegidos, información de registro, etc. Esta clase de comandos típicamente necesita ser pasada a un ENGINE antes de intentar inicializarlo, es decir, antes de llamar a ENGINE_init(). La otra clase de comandos consiste en ajustes u operaciones que modifican cierto comportamiento o causan que ciertas operaciones se lleven a cabo, y estos comandos pueden funcionar tanto antes como después de ENGINE_init(), o en algunos casos en ambos. Las implementaciones de ENGINE deben proporcionar indicaciones de esto en las descripciones adjuntas a los comandos de control integrados y/o en la documentación externa del producto.

Emitiendo comandos de control a un ENGINE

Ilustremos con un ejemplo; una función para la cual el llamador proporciona el nombre del ENGINE que desea usar, una tabla de pares de cadenas para usar antes de la inicialización, y otra tabla para usar después de la inicialización. Tenga en cuenta que los pares de cadenas usados para los comandos de control consisten en un "nombre" de comando seguido del "parámetro" del comando - el parámetro podría ser NULL en algunos casos pero el nombre no puede serlo. Esta función debe inicializar el ENGINE (emitiendo los comandos "pre" de antemano y los comandos "post" después) y establecerlo como el predeterminado para todo excepto RAND y luego devolver un éxito booleano o un fallo.

int generic_load_engine_fn(const char *engine_id,
                           const char **pre_cmds, int pre_num,
                           const char **post_cmds, int post_num)
{
    ENGINE *e = ENGINE_by_id(engine_id);
    if (!e) return 0;
    while (pre_num--) {
        if (!ENGINE_ctrl_cmd_string(e, pre_cmds[0], pre_cmds[1], 0)) {
            fprintf(stderr, "Failed command (%s - %s:%s)\n", engine_id,
                    pre_cmds[0], pre_cmds[1] ? pre_cmds[1] : "(NULL)");
            ENGINE_free(e);
            return 0;
        }
        pre_cmds += 2;
    }
    if (!ENGINE_init(e)) {
        fprintf(stderr, "Failed initialisation\n");
        ENGINE_free(e);
        return 0;
    }
    /*
     * ENGINE_init() returned a functional reference, so free the structural
     * reference from ENGINE_by_id().
     */
    ENGINE_free(e);
    while (post_num--) {
        if (!ENGINE_ctrl_cmd_string(e, post_cmds[0], post_cmds[1], 0)) {
            fprintf(stderr, "Failed command (%s - %s:%s)\n", engine_id,
                    post_cmds[0], post_cmds[1] ? post_cmds[1] : "(NULL)");
            ENGINE_finish(e);
            return 0;
        }
        post_cmds += 2;
    }
    ENGINE_set_default(e, ENGINE_METHOD_ALL & ~ENGINE_METHOD_RAND);
    /* Success */
    return 1;
}

Tenga en cuenta que ENGINE_ctrl_cmd_string() acepta un argumento booleano que puede relajar la semántica de la función - si se establece en un valor distinto de cero, solo devolverá fallo si el ENGINE soportaba el nombre de comando dado pero falló al ejecutarlo; si el ENGINE no soporta el nombre del comando, simplemente devolverá éxito sin hacer nada. En este caso asumimos que el usuario solo está proporcionando comandos específicos para el ENGINE dado, por lo que lo establecemos en FALSE.

Descubriendo los comandos de control soportados

Es posible descubrir en tiempo de ejecución los nombres, identificadores numéricos, descripciones y parámetros de entrada de los comandos de control soportados por un ENGINE usando una referencia estructural. Tenga en cuenta que algunos comandos de control son definidos por el propio OpenSSL y este interceptará y manejará estos comandos de control en nombre del ENGINE, es decir, el manejador ctrl() del ENGINE no se usa para el comando de control. <openssl/engine.h> define un índice, ENGINE_CMD_BASE, desde el cual deben numerarse todos los comandos de control implementados por los ENGINEs. Cualquier valor de comando inferior a este símbolo se considera un comando "genérico" y es manejado directamente por las rutinas centrales de OpenSSL.

Es usando estos comandos de control "centrales" que se puede descubrir los comandos implementados por un ENGINE dado, específicamente los comandos:

ENGINE_HAS_CTRL_FUNCTION
ENGINE_CTRL_GET_FIRST_CMD_TYPE
ENGINE_CTRL_GET_NEXT_CMD_TYPE
ENGINE_CTRL_GET_CMD_FROM_NAME
ENGINE_CTRL_GET_NAME_LEN_FROM_CMD
ENGINE_CTRL_GET_NAME_FROM_CMD
ENGINE_CTRL_GET_DESC_LEN_FROM_CMD
ENGINE_CTRL_GET_DESC_FROM_CMD
ENGINE_CTRL_GET_CMD_FLAGS

Aunque estos comandos son procesados automáticamente por el código del marco de trabajo de OpenSSL, usan varias propiedades expuestas por cada ENGINE para procesar estas consultas. Un ENGINE tiene 3 propiedades que expone que pueden afectar a cómo se comporta esto; puede proporcionar un ctrl() manejador, puede especificar ENGINE_FLAGS_MANUAL_CMD_CTRL en los indicadores del ENGINE, y puede exponer un array de descripciones de comandos de control. Si un ENGINE especifica el indicador ENGINE_FLAGS_MANUAL_CMD_CTRL, entonces simplemente pasará todos estos comandos de control "centrales" directamente al manejador ctrl() del ENGINE (y por lo tanto, debe haber proporcionado uno), así que depende del ENGINE responder a estos comandos de "descubrimiento" por sí mismo. Si ese indicador no está establecido, entonces el código del marco de trabajo de OpenSSL funcionará con las siguientes reglas:

si no se proporcionó un manejador ctrl();
    ENGINE_HAS_CTRL_FUNCTION devuelve FALSE (cero),
    todos los demás comandos fallan.
si se proporcionó un manejador ctrl() pero no un array de comandos de control;
    ENGINE_HAS_CTRL_FUNCTION devuelve TRUE,
    todos los demás comandos fallan.
si se proporcionó un manejador ctrl() y un array de comandos de control;
    ENGINE_HAS_CTRL_FUNCTION devuelve TRUE,
    todos los demás comandos proceden al procesamiento ...

Si el array de comandos de control del ENGINE está vacío, entonces todos los demás comandos fallarán, de lo contrario; ENGINE_CTRL_GET_FIRST_CMD_TYPE devuelve el identificador del primer comando soportado por el ENGINE, ENGINE_GET_NEXT_CMD_TYPE toma el identificador de un comando soportado por el ENGINE y devuelve el siguiente identificador de comando o falla si no hay más, ENGINE_CMD_FROM_NAME toma un nombre de cadena para un comando y devuelve el identificador correspondiente o falla si no existe tal nombre de comando, y los comandos restantes toman un identificador de comando y devuelven las propiedades de los comandos correspondientes. Todos excepto ENGINE_CTRL_GET_FLAGS devuelven la longitud de cadena de un nombre o descripción de comando, o rellenan un búfer de caracteres proporcionado con una copia del nombre o descripción del comando. ENGINE_CTRL_GET_FLAGS devuelve una máscara combinada por OR de bits de los siguientes valores posibles:

ENGINE_CMD_FLAG_NUMERIC
ENGINE_CMD_FLAG_STRING
ENGINE_CMD_FLAG_NO_INPUT
ENGINE_CMD_FLAG_INTERNAL

Si el indicador ENGINE_CMD_FLAG_INTERNAL está establecido, entonces cualquier otro indicador es puramente informativo para el llamador - este indicador evitará que el comando sea utilizable para cualquier función de ENGINE de nivel superior como ENGINE_ctrl_cmd_string(). Los comandos "INTERNAL" no están destinados a ser expuestos a la configuración basada en texto por aplicaciones, administraciones, usuarios, etc. Estos pueden soportar operaciones arbitrarias a través de ENGINE_ctrl(), incluyendo el paso hacia y/o desde los comandos de control de datos de cualquier tipo arbitrario. Estos comandos se soportan en los mecanismos de descubrimiento simplemente para permitir a las aplicaciones determinar si un ENGINE soporta ciertos comandos específicos que podría querer usar (por ejemplo, la aplicación "foo" podría consultar varios ENGINEs para ver si implementan "FOO_GET_VENDOR_LOGO_GIF" - y el ENGINE podría por lo tanto decidir si soporta o no esta extensión específica de "foo").

VALORES DE RETORNO

ENGINE_get_first(), ENGINE_get_last(), ENGINE_get_next() y ENGINE_get_prev() devuelven una estructura ENGINE válida o NULL si ocurrió un error.

ENGINE_add() y ENGINE_remove() devuelven 1 en éxito o 0 en error.

ENGINE_by_id() devuelve una estructura ENGINE válida o NULL si ocurrió un error.

ENGINE_init() y ENGINE_finish() devuelven 1 en éxito o 0 en error.

Todas las funciones ENGINE_get_default_TYPE() , ENGINE_get_cipher_engine() y ENGINE_get_digest_engine() devuelven una estructura ENGINE válida en éxito o NULL si ocurrió un error.

Todas las funciones ENGINE_set_default_TYPE() devuelven 1 en éxito o 0 en error.

ENGINE_set_default() devuelve 1 en éxito o 0 en error.

ENGINE_get_table_flags() devuelve un valor entero sin signo que representa los indicadores de tabla globales que se usan para controlar el comportamiento de registro de las implementaciones ENGINE .

Todas las funciones ENGINE_register_TYPE() devuelven 1 en éxito o 0 en error.

ENGINE_register_complete() y ENGINE_register_all_complete() siempre devuelven 1.

ENGINE_ctrl() devuelve un valor positivo en éxito u otros en error.

ENGINE_cmd_is_executable() devuelve 1 si cmd es ejecutable o 0 en caso contrario.

ENGINE_ctrl_cmd() y ENGINE_ctrl_cmd_string() devuelven 1 en éxito o 0 en error.

ENGINE_new() devuelve una estructura ENGINE válida en éxito o NULL si ocurrió un error.

ENGINE_free() siempre devuelve 1.

ENGINE_up_ref() devuelve 1 en éxito o 0 en error.

ENGINE_set_id() y ENGINE_set_name() devuelven 1 en éxito o 0 en error.

Todas las demás funciones ENGINE_set_* las funciones devuelven 1 en caso de éxito o 0 en caso de error.

ENGINE_get_id() y ENGINE_get_name() devuelven una cadena que representa el identificador y el nombre del ENGINE e respectivamente.

ENGINE_get_RSA(), ENGINE_get_DSA(), ENGINE_get_DH() y ENGINE_get_RAND() devuelven las estructuras de método correspondientes para cada algoritmo.

ENGINE_get_destroy_function(), ENGINE_get_init_function(), ENGINE_get_finish_function(), ENGINE_get_ctrl_function(), ENGINE_get_load_privkey_function(), ENGINE_get_load_pubkey_function(), ENGINE_get_ciphers() y ENGINE_get_digests() devuelven los punteros a función correspondientes de las funciones de retorno.

ENGINE_get_cipher() devuelve una estructura EVP_CIPHER válida en caso de éxito o NULL si ocurrió un error.

ENGINE_get_digest() devuelve una estructura EVP_MD válida en caso de éxito o NULL si ocurrió un error.

ENGINE_get_flags() devuelve un entero que representa los indicadores del ENGINE que se utilizan para controlar varios comportamientos de un ENGINE.

ENGINE_get_cmd_defns() devuelve una estructura ENGINE_CMD_DEFN o NULL si no está establecida.

ENGINE_load_private_key() y ENGINE_load_public_key() devuelven una estructura EVP_PKEY válida en caso de éxito o NULL si ocurrió un error.
