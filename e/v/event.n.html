DESCRIPCIÓ

N

El comando event proporciona varias instalaciones para tratar con eventos del sistema de ventanas, como definir eventos virtuales y sintetizar eventos. El comando tiene varias formas diferentes, determinadas por el primer argumento. Actualmente se admiten las siguientes

formas:
event add <<virtual>> sequence ?sequence
...?
Asocia el evento virtual virtual con la(s) secuencia(s) de eventos físicos dada(s) por los argumentos sequence, de modo que el evento virtual se activará cuando ocurra cualquiera de las secuencias. Virtual puede ser cualquier valor de cadena y sequence puede tener cualquiera de los valores permitidos para el argumento sequence del comando bind. Si virtual ya está definido, las nuevas secuencias de eventos físicos se añaden a las secuencias existentes del
evento.
event delete <<virtual>> ?sequence sequence
...?
Elimina cada una de las secuencias de las asociadas con el evento virtual dado por virtual. Virtual puede ser cualquier valor de cadena y sequence puede tener cualquiera de los valores permitidos para el argumento sequence del comando bind. Cualquier secuencia no asociada actualmente con virtual se ignora. Si no se proporciona ningún argumento sequence, se eliminan todas las secuencias de eventos físicos para virtual, de modo que el evento virtual no se activará
más.
event generate window event ?opción valor opción valor .
..?
Genera un evento de ventana y lo organiza para que se procese como si hubiera provenido del sistema de ventanas. Window da el nombre de la ruta de la ventana para la que se generará el evento; también puede ser un identificador (como el devuelto por winfo id) siempre que sea para una ventana de la aplicación actual. Event proporciona una descripción básica del evento, como <Shift-Button-2> o <<Paste>>. Si Window está vacío, se refiere a toda la pantalla y las coordenadas son relativas a la pantalla. Event puede tener cualquiera de las formas permitidas para el argumento sequence del comando bind, excepto que debe consistir en un único patrón de evento, no en una secuencia. Los pares opción-valor pueden usarse para especificar atributos adicionales del evento, como la posición x e y del ratón; ver CAMPOS DE EVENTO más abajo. Si no se especifica la opción -when, el evento se procesa inmediatamente: todos los manejadores para el evento se completarán antes de que el comando event generate regrese. Si se especifica la opción -when, entonces determina cuándo se procesa el evento. Ciertos eventos, como los eventos de tecla, requieren que la ventana tenga el foco para recibir el evento
correctamente.

PREDEFINIDOS

Tk define los siguientes eventos virtuales para los fines de

notificación:
<<AltUnderlined>
>
Esto se envía a un widget para notificarle que la letra que tiene subrayada (como un indicador de acelerador) con la opción -underline ha sido presionada en combinación con la tecla Alt. La respuesta habitual a esto es enfocar el widget (o algún widget relacionado) o invocar el
widget.
<<Invoke>
>
Esto puede enviarse a algunos widgets (por ejemplo, button, listbox, menu) como una alternativa a <space>
.
<<ListboxSelect>
>
Esto se envía a un listbox cuando el conjunto de elementos seleccionados en el listbox es
actualizado.
<<MenuSelect>
>
Esto se envía a un menú cuando el elemento seleccionado actualmente en el menú cambia. Está destinado para su uso con sistemas de ayuda sensibles al
contexto.
<<Modified>
>
Esto se envía a un widget de texto cuando los contenidos del widget son
modificados.
<<Selection>
>
Esto se envía a un widget de texto cuando la selección en el widget es
cambiada.
<<ThemeChanged>
>
Esto se envía a todos los widgets cuando el tema ttk cambia. Los widgets ttk escuchan este evento y se redibujan a sí mismos cuando se activa. Los widgets legacy ignoran este
evento.
<<TkWorldChanged>
>
Este evento se envía a todos los widgets cuando una fuente es cambiada, por ejemplo, por el uso de [font configure]. El campo user_data (%d) tendrá el valor "FontChanged". Para otros cambios a nivel de sistema, este evento será enviado a todos los widgets, y el campo user_data indicará la causa del cambio. NOTA: todos los widgets tk y ttk ya manejan este evento
internamente.
<<TraverseIn>
>
Esto se envía a un widget cuando el foco entra al widget debido a una acción de "tab al widget" dirigida por el
usuario.
<<TraverseOut>
>
Esto se envía a un widget cuando el foco sale del widget debido a una acción de "tab al widget" dirigida por el
usuario.
<<UndoStack>
>
Esto se envía a un widget de texto cuando su pila de deshacer o pila de rehacer se vuelve vacía o no
vacía.
<<WidgetViewSync>
>
Esto se envía a un widget de texto cuando sus datos internos se vuelven obsoletos, y de nuevo cuan
do estos datos internos están de nuevo en sincronía con la vista del widget. El campo detail (sust
itución %d) es o bien true (cuando el widget está en sincronía) o false (cuando no lo está).

ASOCIACIÓN DE TECLAS A EVENTOS

VIRTUALES

Para que una asociación de evento virtual se active, deben ocurrir dos cosas. Primero, el evento virtual debe definirse con el comando event add . Segundo, debe crearse una asociación para el evento virtual con el comando bind. Considere las siguientes definiciones de eventos

virtuales: 
event add <<Paste>> <Control-y>
event add <<Paste>> <Button-2>
event add <<Save>> <Control-X><Control-S>
event add <<Save>> <Shift-F12>
if {[tk windowingsystem] eq "aqua"} {
    event add <<Save>> <Command-s>
}

En el comando bind, un evento virtual puede asociarse como cualquier otro tipo de evento incorporado de la siguiente

manera: 
bind Entry <<Pas
te>> {%W insert
[selection get]}

Los corchetes angulares dobles se utilizan para especificar que se está asociando un evento virtual. Si el usuario escribe Control-y o presiona el botón 2, o si se sintetiza un evento virtual <<Paste>> con el comando event generate, entonces se invocará la asociación <<Paste>>

.

Si una asociación virtual tiene exactamente la misma secuencia que una asociación física separada, la asociación física tendrá prioridad. Considere el siguiente

ejemplo: 
event add <<Paste>> <Control-y> <Meta-Control-y>
bind Entry <
Control-y> {puts Control-y} bin
d Entry <<Paste>> {puts Paste}

Cuando el usuario escribe Control-y se invocará la asociación <Control-y>, porque un evento físico se considera más específico que un evento virtual, todas las demás cosas siendo iguales. Sin embargo, cuando el usuario escribe Meta-Control-y se invocará la asociación <<Paste>>, porque el modificador Meta en el patrón físico asociado con la asociación virtual es más específico que la secuencia <Control-y> para el evento

físico.

Las asociaciones sobre un evento virtual pueden crearse antes de que el evento virtual exista. De hecho, el evento virtual nunca realmente necesita definirse, por ejemplo, en plataformas donde el evento virtual específico sería sin sentido o no

generable.

Cuando una definición de un evento virtual cambia en tiempo de ejecución, todas las ventanas responderán inmediatamente a la nueva definición. Partiendo del ejemplo anterior, si se ejecuta el siguiente

código: 
bind Entry <Control-y> {}
event add <<Pa
ste>> <
Key-F6>

el comportamiento cambiará de dos maneras. Primero, la asociación <<Paste>> oculta emergerá. Escribir Control-y ya no invocará la asociación <Control-y>, sino que invocará el evento virtual <<Paste>>. Segundo, presionar la tecla F6 ahora también invocará la asociación <<Paste>

>

MOVER EL PUNTERO DEL

RATÓN

A veces es útil poder mover realmente el puntero del ratón. Por ejemplo, si tiene algún software que sea capaz de demostrar directamente al usuario cómo usar el programa. Para hacer esto, necesita "teletransportar" el ratón usando el comando event generate,

así: 
for {set xy 0} {$xy < 200} {incr xy} {
    event generate . <Motion> -x $xy -y
$xy -warp 1 upd
ate after 50 }

Tenga en cuenta que normalmente se considera mala práctica mover el pu

ntero del ratón por el usuario porque le quita el control. Por lo
tanto, esta técnica debe usarse con precaución. Tenga en cuenta
también que no se garantiza que funcione en todas las plataformas.
