DESCRIPCIÓ

N

El método RAND predeterminado de OpenSSL se basa en las clases EVP_RAND para proporcionar entradas no deterministas a otros algoritmos

criptográficos.

Mientras que la API RAND es la 'interfaz frontal' destinada a ser utilizada por los desarrolladores de aplicaciones para obtener bytes aleatorios, la API EVP_RAND sirve como 'interfaz trasera', conectando la anterior con las fuentes de entropía del sistema operativo y proporcionando acceso a generadores de bits aleatorios deterministas (DRBG) y sus parámetros de configuración. Un DRBG es un tipo de generador de números pseudoaleatorios criptográficamente seguro (CSPRNG), que se describe en [NIST SP 800-90A Rev. 1]

.

Aviso

legal

A menos que tenga requisitos muy específicos para su generador aleatorio, en general no es necesario utilizar la API EVP_RAND directamente. La forma habitual de obtener bytes aleatorios es usar RAND_bytes(3) o RAND_priv_bytes(3), véase también RAND

(7
).

típicos

    • .

Encadenamiento de

EVP_RAND

Una instancia de EVP_RAND puede usarse como la fuente de entropía de otra instancia de EVP_RAND, siempre que ella misma tenga acceso a una fuente de entropía válida. La instancia de EVP_RAND que actúa como fuente de entropía se denomina padre, y la otra instancia el hijo. Típicamente, el hijo será un DRBG porque no tiene sentido que el hijo sea una fuente de

entropía.

Esto se llama encadenamiento. Una instancia de EVP_RAND encadenada se crea pasando un puntero al EVP_RAND_CTX padre como argumento a la llamada EVP_RAND_CTX_new(). Es posible crear cadenas de más de dos DRBG seguidos. También es posible usar cualquier clase de

EVP_RAND_CTX como el padre, sin embargo, solo una fuent
e de entropía activa puede ignorar y no usar a su padre.

LAS TRES INSTANCIAS COMPARTIDAS DE

DRBG

Actualmente, existen tres instancias compartidas de DRBG: el DRBG <primario>, <público> y <privado>. Mientras que el DRBG <primario> es una única instancia global, los DRBG <público> y <privado> se crean por hilo y se acceden a través del almacenamiento local del

hilo.

Por defecto, las funciones RAND_bytes(3) y RAND_priv_bytes(3) usan las instancias de DRBG <público> y <privado> locales al hilo, respectivamente

.

La instancia de DRBG

<primario>

El DRBG <primario> no es usado directamente por la aplicación, solo para resembrar las otras dos instancias de DRBG. Se resiembra a sí mismo obteniendo aleatoriedad de fuentes de entropía del sistema operativo o consumiendo aleatoriedad que fue añadida previamente por RAND_a

dd(
3).

La instancia de DRBG

<público>

Esta instancia es usada por defecto por RAND_by

tes
(3).

La instancia de DRBG

<privado>

Esta instancia es usada por defecto por RAND_priv_bytes

(
3
)

BLOQUE

O

El DRBG <primario> está destinado a ser accedido concurrentemente para resembrado por sus instancias hijas de DRBG. El bloqueo necesario se realiza internamente. No es seguro para hilos acceder al DRBG <primario> directamente a través de la interfaz EVP_RAND. Los DRBG <público> y <privado> son locales al hilo, es decir, hay una instancia de cada uno por hilo. Por lo tanto, pueden accederse de forma segura sin bloqueo a través de la interfaz

EVP_RAND.

Se pueden obtener punteros a estas instancias de DRBG usando RAND_get0_primary(), RAND_get0_public() y RAND_get0_private(), respectivamente. Tenga en cuenta que no está permitido almacenar un puntero a una de las instancias de DRBG locales al hilo en una variable u otra ubicación de memoria donde será accedido y usado por múltiples

hilos.

Todas las demás instancias de DRBG creadas por una aplicación no soportan bloqueo, porque están destinadas a ser usadas por un solo hilo. En lugar de acceder a una sola insta

ncia de DRBG concurrentemente desde diferentes hilos, se recomienda instanciar una instancia de DRBG separada por hilo. Usar el DRBG <primario> como fuente de entropía para m
últiples instancias de DRBG en diferentes hilos es seguro para hilos, porque la instancia de DRBG bloqueará el DRBG <primario> automáticamente para obtener entrada aleatoria.

RESEMILLAD

O

Una instancia de DRBG se siembra automáticamente, extrayendo entrada aleatoria de su fuente de entropía. La fuente de entropía puede ser una fuente de entropía confiable del sistema operativo, u otro DRBG con acceso a una fuente de este

tipo.

El resellado automático ocurre después de un número predefinido de solicitudes de generación. La selección de las fuentes de entropía confiables se configura en tiempo de compilación usando la opción --with-rand-seed. Las siguientes secciones explican el proceso de resellado en más

detalle.

Resellado

automático

Antes de satisfacer una solicitud de generación (EVP_RAND_generate(3)), el DRBG se resiembra automáticamente, si se cumple una de las siguientes

condiciones:

- el DRBG no fue instanciado (=sembrado) todavía o ha sido

desinstanciado.

- el número de solicitudes de generación desde el último resellado excede un cierto umbral, el llamado reseed_interval. Este comportamiento puede ser deshabilitado configurando el reseed_interval a

0.

- el tiempo transcurrido desde el último resellado excede un cierto intervalo de tiempo, el llamado reseed_time_interval. Esto puede ser disabled by setting the reseed_time_interval to

0.

- the DRBG is in an error

state.

Note: An error state is entered if the entropy source fails while the DRBG is seeding or reseeding. The last case

ensures that the DRBG automatically recovers from the
error as soon as the entropy source is available again.

Manual

Reseeding

In addition to automatic reseeding, the caller can request an immediate reseeding of the DRBG with fresh entropy by setting the prediction resistance parameter to 1 when calling EVP_RAND_gener

ate(3).

The document [NIST SP 800-90C] describes prediction resistance requests in detail and imposes strict conditions on the entropy sources that are approved for providing prediction resistance. A request for prediction resistance can only be satisfied by pulling fresh entropy from a live entropy source (section 5.5.2 of [NIST SP 800-90C]). It is up to the user to ensure that a live entropy source is configured and is being

used.

For the three shared DRBGs (and only for these) there is another way to reseed them manually: If RAND_add(3) is called with a positive randomness argument (or RAND_seed(3)), then this will immediately reseed the <primary> DRBG. The <public> and <private> DRBG will detect this on their next generate call and reseed, pulling randomness from <primary>

.

The last feature has been added to support the common practice used with previous OpenSSL versions to call RAND_add() before calling RAND_b

ytes
().

Entropy Input and Additional

Data

The DRBG distinguishes two different types of random input: entropy, which comes from a trusted source, and additional input', which can optionally be added by the user and is considered untrusted. It is possible to add additional input not only during resee

ding, but also for ev
ery generate request.

Configuring the Random Seed

Source

In most cases OpenSSL will automatically choose a suitable seed source for automatically seeding and reseeding its <primary> DRBG. The default seed source can be configured when OpenSSL is compiled by setting -DOPENSSL_DEFAULT_SEED_SRC=SEED-SRC. If not set then "SEED-SRC" is used. One can specify a third-party provider seed-source, or -DOPENSSL_DEFAULT_SEED_SRC=JITTER if

available.

In some cases however, it will be necessary to explicitly specify a seed source used by "SEED-SRC" during configuration, using the --with-rand-seed option. For more information, see the INSTALL instructions. There are also operating systems where no seed source is available and automatic reseeding is disabled by

default.

The following two sections describe the reseeding

process of the primary DRBG, depending on w
hether automatic reseeding is available or not.

Reseeding the primary DRBG with automatic seeding

enabled

Calling RAND_poll() or RAND_add() is not necessary, because the DRBG pulls the necessary entropy from its source automatically. However, both calls are permitted, and do reseed the

RNG.

RAND_add() can be used to add both kinds of random input, depending on the value of the randomness ar

gument:
randomness ==
0:
The random bytes are mixed as additional input into the current state of the DRBG. Mixing in additional input is not considered a full reseeding, hence the reseed counter is not
reset.
randomness >
0:
The random bytes are used as entropy input for a full reseeding (resp. reinstantiation) if the DRBG is instantiated (resp. uninstantiated or in an error state
). The number of random bits required for reseeding is determined by the security strength of the DRBG. Currently it defaults to 256 bits (32 bytes). It is pos
sible to provide less randomness than required. In this case the missing randomness will be obtained by pulling random input from the trusted entropy sources.

NOTE: Manual reseeding is *not allowed* in FIPS mode, because [NIST SP-800-90Ar1] mandates that entropy *shall not* be provided by the consuming application for instantiation (Section 9.1) or reseeding (Section 9.2). For that reason, the randomness argument is ignored and the random bytes provided by the RAND_add(3) and RAND_seed(3) calls are

treated as ad
ditional data.

Reseeding the primary DRBG with automatic seeding

disabled

Calling RAND_poll() will always

fail.

RAND_add() needs to be called for initial seeding and periodic reseeding. At least 48 bytes (384 bits) of randomness have to be provided, otherwise the (re-)seeding of the DRBG will fail. This corresponds to one and a half times the security strength of the DRBG. The extra half is used for the nonce during

instantiation.

More precisely, the number of bytes needed for seeding depend on the security strength of the D

RBG, which i
s set to 256
by default.
