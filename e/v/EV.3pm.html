ANTES DE EMPEZAR A USAR ESTE

MÓDULO

Si solo necesitas observadores de temporizador, E/S, señal, hijo e inactividad y no la funcionalidad avanzada de este módulo, considera usar AnyEvent en su lugar, específicamente la API simplificada descrita en

AE.

Cuando se usa con EV como backend, la API AE es tan rápida

como la API nativa de EV, pero tus programas/módulos s
eguirán funcionando con muchos otros bucles de eventos.

DESCRIPCIÓ

N

Este módulo proporciona una interfaz para libev (http://software.schmorp.de/pkg/libev.html). Aunque la documentación a continuación es exhaustiva, también se puede consultar la documentación de libev en sí misma (http://pod.tst.eu/http://cvs.schmorp.de/libev/ev.pod o perldoc EV::libev) para detalles más sutiles sobre la semántica de los observadores o alguna discusión sobre los backends disponibles, o cómo forzar un backend específico con "LIBEV_FLAGS", o simplemente en cualquier caso porque tiene información mucho más

detallada.

Este módulo es muy rápido y escalable. Es tan rápido que puedes usarlo a través del módulo AnyEvent, mantener la portabilidad a otros bucles de eventos (si no dependes de ningún tipo de observador no disponible a través de él) y aún ser más rápido que con cualquier otro bucle de eventos actualmente soportado en

Perl.

BUCLES DE

EVENTOS

EV soporta múltiples bucles de eventos: Hay un "bucle de eventos por defecto" único que puede manejar todo, incluyendo señales y observadores de hijos, y cualquier número de "bucles de eventos dinámicos" que pueden usar diferentes backends (con varias limitaciones), pero sin observadores de hijos y

señales.

No tienes que hacer nada para crear el bucle de eventos por defecto: Cuando se carga el módulo se selecciona un backend adecuado con la premisa de seleccionar un backend que funcione (lo que, por ejemplo, descarta kqueue en la mayoría de los BSD). Los módulos, a menos que tengan "necesidades especiales", siempre deben usar el bucle por defecto, ya que es el más rápido (en términos de perl), el mejor soportado por otros módulos (por ejemplo, AnyEvent o Coro) y el bucle de eventos más

portable.

Para programas específicos puedes crear bucles de eventos adicionales

dinámicamente.

Si quieres aprovechar kqueue (que a menudo funciona correctamente solo para sockets) aunque el bucle por defecto no lo habilite, puedes incrustar un bucle de kqueue en el bucle por defecto: ejecutar el bucle por defecto también servirá el bucle de kqueue hasta cierto punto. Consulta el ejemplo en la sección sobre observadores incrustados para ver cómo lograr

eso.

our @snmp_watcher;
our $snmp_prepare = EV::prepare sub {
   # no hacer nada a menos que esté activo

      or return;

   ... no mostrado
   # crear un watcher de I/O para cada socket

      (map { EV::io $_, EV::READ, sub { } }

   ... no mostrado
};

SEÑALES DE

PERL

Aunque el manejo de señales de Perl (%SIG) no es afectado por EV, el comportamiento con EV es el mismo que con cualquier otra biblioteca C: las señales de Perl solo se manejarán cuando Perl se ejecute, lo que significa que tu manejador de señales podría ser invocado solo la próxima vez que se invoque un callback de

evento.

La solución es usar watchers de señal de EV (ver "EV::signal"), lo que garantizará un funcionamiento correcto con respecto a otros watchers de

eventos.

Si no puedes hacer esto por cualquier razón, también puedes forzar a un watcher a ser llamado en cada iteración del bucle de eventos instalando un watcher "EV::

check": 
my $async_check = EV::check sub { }
;

Esto asegura que perl obtenga el control por un corto ti

empo para manejar cualquier señal pendiente, y tambié
n asegura (ligeramente) una operación general más lenta.

ITHREAD

S

Los Ithreads no están soportados por este módulo de ninguna manera. Los pseudo-hilo

s de Perl son cosas malvadas y deben morir. Los hilos reales proporcionados por Cor

FOR

La mayoría de los mecanismos "mejorados" de entrega de eventos de los sistemas operativos modernos tienen bastantes problemas con fork(2) (para decirlo claramente: no está soportado y usualmente es destructivo). Libev hace posible sortear esto al tener una función que recrea el estado del kernel después del fork en el

hijo.

En plataformas no-win32, este módulo requiere la funcionalidad pthread_atfork para hacer esto automáticamente por ti. Esta función es bastante defectuosa en la mayoría de los BSD, sin embargo, así que YMMV. La sobrecarga para esto es bastante despreciable, porque todo lo que la función actualmente hace es establecer una bandera que se verifica solo cuando el bucle de eventos se usa la próxima vez, así que cuando haces fork pero no usas EV, la sobrecarga es

mínima.
