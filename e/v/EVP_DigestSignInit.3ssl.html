DESCRIPCIÓ

N

Las rutinas de firma EVP son una interfaz de alto nivel para firmas digitales. Los datos de entrada se procesan primero (digest) antes de que se realice la

firma.

EVP_DigestSignInit_ex() configura el contexto de firma ctx para usar un resumen (digest) con el nombre mdname y la clave privada pkey. El nombre del resumen a usar se pasa al proveedor del algoritmo de firma en uso. Cómo ese proveedor interpreta el nombre del resumen es específico del proveedor. El proveedor puede implementar ese resumen directamente él mismo o puede (opcionalmente) optar por obtenerlo (lo que podría resultar en la selección de un resumen de un proveedor diferente). Si el proveedor soporta la obtención del resumen, entonces puede usar el argumento props para las propiedades a usar durante la obtención. Finalmente, los parámetros pasados params, si no son NULL, se establecen en el contexto antes de

devolver.

El algoritmo pkey se usa para obtener un EVP_SIGNATURE método implícitamente, para ser usado para la firma real. Véase "Implicit fetch" en provider(7) para más información sobre las obtenciones

implícitas.

Los proveedores por defecto y legacy de OpenSSL soportan la obtención de resúmenes y pueden obtener esos resúmenes de cualquier proveedor disponible. El proveedor FIPS de OpenSSL también soporta la obtención de resúmenes pero solo obtendrá resúmenes que estén implementados dentro del proveedor

FIPS.

ctx debe ser creado con EVP_MD_CTX_new() antes de llamar a esta función. Si pctx no es NULL, el EVP_PKEY_CTX de la operación de firma se escribirá en *pctx: esto puede usarse para establecer opciones de firma alternativas. Nótese que cualquier valor existente en *pctx es sobrescrito. El valor EVP_PKEY_CTX devuelto no debe ser liberado directamente por la aplicación si ctx no se le asigna un valor EVP_PKEY_CTX antes de ser pasado a EVP_DigestSignInit_ex() (lo que significa que el EVP_PKEY_CTX es creado dentro de EVP_DigestSignInit_ex() y será liberado automáticamente cuando el EVP_MD_CTX sea liberado). Si el EVP_PKEY_CTX a usar es creado por EVP_DigestSignInit_ex entonces usará el OSSL_LIB_CTX especificado en libctx y la cadena de consulta de propiedades especificada en props

.

El resumen mdname puede ser NULL si el algoritmo de firma lo soporta. El argumento props siempre puede ser

NULL.

No EVP_PKEY_CTX será creado por EVP_DigestSignInit_ex() si el ctx pasado ya ha sido asignado uno vía EVP_MD_CTX_set_pkey_ctx(3). Véase también SM2(7

).

Solo los tipos EVP_PKEY que soportan firma pueden usarse con estas funciones. Esto incluye algoritmos MAC donde la generación del MAC se considera como una forma de "firma". Los tipos EVP_PKEY integrados soportados por estas funciones son CMAC, Poly1305, DSA, ECDSA, HMAC, RSA, SipHash, Ed25519 y

Ed448.

NOTA

S

La interfaz EVP para firmas digitales debe usarse casi siempre en preferencia a las interfaces de bajo nivel. Esto se debe a que el código se vuelve transparente al algoritmo usado y mucho más

flexible.

EVP_DigestSign() es una operación de un solo disparo (one shot) que firma un solo bloque de datos en una función. Para algoritmos que soportan streaming es equivalente a llamar a EVP_DigestSignUpdate() y EVP_DigestSignFinal(). Para algoritmos que no soportan streaming (ej. PureEdDSA) es la única forma de firmar

datos.

En versiones anteriores de OpenSSL había un enlace entre los tipos de resumen de mensaje y los algoritmos de clave pública. Esto significaba que los resúmenes "clon" como EVP_dss1() necesitaban usarse para firmar usando SHA1 y DSA. Esto ya no es necesario y el uso de resúmenes clon ahora está

desalentado.

Para algunos tipos de clave y parámetros el generador de números aleatorios debe ser sembrado. Si el sembrado automático o el re-sembrado del CSPRNG de OpenSSL falla debido a circunstancias externas (véase RAND(7)), la operación

fallará.

La llamada a EVP_DigestSignFinal() finaliza internamente una copia del contexto de resumen. Esto significa que las llamadas a EVP_DigestSignUpdate() y EVP_DigestSignFinal() pueden ser llamadas más tarde para resumir y firmar datos adicionales. Las aplicaciones pueden deshabilitar este comportamiento estableciendo el flag de contexto EVP_MD_CTX_FLAG_FINALISE vía EVP_MD_CTX_set_f

lags(3).

Nótese que no todos los proveedores soportan la continuación, en caso de que el proveedor seleccionado no permita duplicar contextos EVP_DigestSignFinal() finalizará el contexto de resumen y el intento de procesar datos adicionales vía EVP_DigestSignUpdate() resultará en un

error.

EVP_DigestSignInit() y EVP_DigestSignInit_ex() Las funciones se pueden llamar varias veces en un contexto y los parámetros establecidos por llamadas anteriores se conservan si el parámetro pkey es NULL. La llamada simplemente restablece el estado del ctx

.

EVP_DigestSign() no se puede volver a llamar, una vez que se ha generado una firma (al pasar sig como no NULL), a menos que el EVP_MD_CTX se reinicialice llamando a EVP_DigestSignIn

it_ex().

Ignorar los códigos de retorno de error de las funciones EVP_DigestSignInit() y EVP_DigestSignInit_ex() puede conducir a un comportamiento indefinido posterior al llamar a EVP_DigestSignUpdate(), EVP_DigestSignFinal() o EVP_DigestS

ign().

El uso de EVP_PKEY_get_size() con estas funciones se desaconseja porque algunas operaciones de firma pueden tener una longitud de firma que depende de los parámetros establecidos. Como resultado, EVP_PKEY_get_size() tendría que devolver un valor que indique

la firma máxima posible para cu
alquier conjunto de parámetros.
