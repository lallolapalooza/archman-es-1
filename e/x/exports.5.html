exports(5) Manual de Formatos de Archivo exports(5)

NOMBRE

exports - tabla de exportaciones del servidor NFS

DESCRIPCIÓN

El archivo /etc/exports contiene una tabla de sistemas de archivos físicos locales en un servidor NFS que son accesibles para los clientes NFS. El contenido del archivo es mantenido por el administrador del sistema del servidor.

Cada sistema de archivos en esta tabla tiene una lista de opciones y una lista de control de acceso. La tabla es utilizada por exportfs(8) para dar información a mountd(8).

El formato del archivo es similar al archivo exports de SunOS. Cada línea contiene un punto de exportación y una lista de clientes separados por espacios en blanco que tienen permitido montar el sistema de archivos en ese punto. Cada cliente listado puede ir seguido inmediatamente por una lista de opciones de exportación entre paréntesis y separada por comas para ese cliente. No se permite espacio en blanco entre un cliente y su lista de opciones.

Además, cada línea puede tener una o más especificaciones para opciones predeterminadas después del nombre de la ruta, en la forma de un guion ("-") seguido de una lista de opciones. La lista de opciones se utiliza para todas las exportaciones posteriores en esa línea únicamente.

Las líneas en blanco se ignoran. Un signo de número ("#") introduce un comentario hasta el final de la línea. Las entradas pueden continuar a través de saltos de línea usando una barra invertida. Si un nombre de exportación contiene espacios, debe estar entrecomillado usando comillas dobles. También puede especificar espacios u otros caracteres inusuales en el nombre de la exportación usando una barra invertida seguida del código del carácter como tres dígitos octales.

Para aplicar cambios a este archivo, ejecute exportfs -ra o reinicie el servidor NFS.

Formatos de Nombres de Máquina

Los clientes NFS pueden especificarse de varias maneras:

un solo host
Puede especificar un host ya sea por un nombre abreviado reconocido por el resolutor, el nombre de dominio completamente calificado, una dirección IPv4, o una dirección IPv6. Las direcciones IPv6 no deben estar dentro de corchetes en /etc/exports para no confundirlas con coincidencias de comodín de clases de caracteres.
redes IP
También puede exportar directorios a todos los hosts en una (sub)red IP simultáneamente. Esto se hace especificando un par de dirección IP y máscara de red como dirección/máscara donde la máscara de red puede especificarse en formato decimal con puntos, o como una longitud de máscara contigua. Por ejemplo, ya sea `/255.255.252.0' o `/22' añadido a la dirección IPv4 base de la red resulta en subredes idénticas con 10 bits de host. Las direcciones IPv6 deben usar una longitud de máscara contigua y no deben estar dentro de corchetes para evitar confusión con comodines de clases de caracteres. Los caracteres comodín generalmente no funcionan en direcciones IP, aunque pueden funcionar por accidente cuando las búsquedas DNS inversas fallan.
comodines
Los nombres de máquina pueden contener los caracteres comodín * y ?, o pueden contener listas de clases de caracteres dentro de [corchetes]. Esto puede usarse para hacer el archivo exports más compacto; por ejemplo, *.cs.foo.edu coincide con todos los hosts en el dominio cs.foo.edu. Como estos caracteres también coinciden con los puntos en un nombre de dominio, el patrón dado también coincidirá con todos los hosts dentro de cualquier subdominio de cs.foo.edu.
grupos de red
Los grupos de red NIS pueden darse como @grupo. Solo la parte del host de cada miembro del grupo de red se considera al verificar la membresía. Las partes del host vacías o aquellas que contengan un solo guion (-) se ignoran.
anónimo
Esto se especifica con un solo carácter * (no confundir con la entrada comodín de arriba) y coincidirá con todos los clientes.

Si un cliente coincide con más de una de las especificaciones anteriores, entonces la primera coincidencia del orden de la lista anterior tiene prioridad, independientemente del orden en que aparezcan en la línea de exportación. Sin embargo, si un cliente coincide con más de una especificación del mismo tipo (por ejemplo, dos grupos de red), entonces la primera coincidencia del orden en que aparecen en la línea de exportación tiene prioridad.

seguridad RPCSEC_GSS

Puede usar las cadenas especiales "gss/krb5", "gss/krb5i", o "gss/krb5p" para restringir el acceso a clientes que usen seguridad rpcsec_gss. Sin embargo, esta sintaxis está obsoleta; en kernels de Linux desde la versión 2.6.23, debe usar en su lugar la opción de exportación "sec=":

sec=
La opción sec=, seguida de una lista de sabores de seguridad delimitada por dos puntos, restringe la exportación a clientes que usen esos sabores. Los sabores de seguridad disponibles incluyen sys (el predeterminado—sin seguridad criptográfica), krb5 (solo autenticación), krb5i (protección de integridad), y krb5p (protección de privacidad). Para los fines de la negociación de sabores de seguridad, el orden cuenta: los sabores preferidos deben listarse primero. El orden de la opción sec= con respecto a las otras opciones no importa, a menos que desee que algunas opciones se apliquen de manera diferente dependiendo del sabor. En ese caso puede incluir múltiples opciones sec=, y las opciones siguientes se aplicarán solo para el acceso usando los sabores listados en la opción sec= inmediatamente anterior. Las únicas opciones que se permite que varíen de esta manera son ro, rw, no_root_squash, root_squash, y all_squash.

seguridad de capa de transporte

El servidor NFS de Linux permite el uso de RPC-with-TLS (RFC 9289) para proteger el tráfico RPC entre él y sus clientes. Alternativamente, los administradores pueden asegurar el tráfico NFS usando una VPN, o un túnel ssh o un mecanismo similar, de una manera que es transparente para el servidor.

Para habilitar el uso de RPC-with-TLS, el administrador del servidor debe instalar y configurar tlshd para manejar las solicitudes de intercambio de claves de seguridad de capa de transporte del kernel local. Los clientes pueden entonces elegir usar RPC-with-TLS o pueden continuar operando sin él.

Los administradores pueden requerir el uso de RPC-with-TLS para proteger el acceso a exportaciones individuales. Esto es particularmente útil cuando se usan sabores de seguridad no criptográficos como sec=sys. La opción xprtsec= seguida de una lista de políticas de seguridad desordenada delimitada por dos puntos, puede restringir el acceso a la exportación solo a clientes que hayan negociado seguridad de capa de transporte. Las políticas de seguridad de capa de transporte actualmente soportadas incluyen:

none
El servidor permite a los clientes acceder a la exportación sin el uso de seguridad de capa de transporte.
tls
El servidor permite a los clientes que hayan negociado una sesión RPC-with-TLS sin autenticación de par (solo confidencialidad) acceder a la exportación. No se requiere que los clientes ofrezcan un certificado x.509 al establecer una sesión de seguridad de capa de transporte.
mtls
El servidor permite a los clientes que hayan negociado una sesión RPC-with-TLS con autenticación de par acceder a la exportación. El servidor requiere que los clientes ofrezcan un certificado x.509 al establecer una sesión de seguridad de capa de transporte.

Si RPC-with-TLS está configurado y habilitado y la opción xprtsec= no se especifica, la configuración predeterminada para una exportación es xprtsec=none:tls:mtls. Con esta configuración, el servidor permite a los clientes usar cualquier mecanismo de seguridad de capa de transporte o ninguno en absoluto para acceder a la exportación.

Opciones Generales

exportfs entiende las siguientes opciones de exportación:

secure
Esta opción requiere que las solicitudes que no usan gss se originen en un puerto de Internet menor que IPPORT_RESERVED (1024). Esta opción está activada por defecto. Para desactivarla, especifique insecure. (NOTA: los kernels antiguos (antes de la versión upstream del kernel 4.17) también aplicaban este requisito a las solicitudes gss.)
rw
Permite tanto solicitudes de lectura como de escritura en este volumen NFS. El predeterminado es desallowir cualquier solicitud que cambie el sistema de archivos. Esto también puede hacerse explícito usando la opción ro .
async</a>
Esta opción permite que el servidor NFS viole el protocolo NFS y responda a las peticiones antes de que cualquier cambio realizado por esa petición se haya confirmado en el almacenamiento estable (p. ej., unidad de disco).

Usar esta opción generalmente mejora el rendimiento, pero a costa de que un reinicio sucio del servidor (es decir, un fallo) pueda causar que se pierdan o corrompan datos.

sync
Responder a las peticiones solo después de que los cambios se hayan confirmado en el almacenamiento estable (véase async arriba).

En las versiones de nfs-utils hasta la 1.0.0 inclusive, la opción async era la predeterminada. En todas las versiones posteriores a la 1.0.0, sync es la predeterminada, y async debe solicitarse explícitamente si es necesario.

no_wdelay
Esta opción no tiene efecto si async también está establecido. El servidor NFS normalmente retrasará ligeramente la confirmación de una petición de escritura en el disco si sospecha que otra petición de escritura relacionada puede estar en curso o puede llegar pronto. Esto permite que múltiples peticiones de escritura se confirmen en el disco con una sola operación, lo que puede mejorar el rendimiento. Si un servidor NFS recibiera principalmente peticiones pequeñas no relacionadas, este comportamiento podría en realidad reducir el rendimiento, por lo que no_wdelay está disponible para desactivarlo. El comportamiento predeterminado puede solicitarse explícitamente con la opción wdelay .
nohide
Esta opción se basa en la opción del mismo nombre proporcionada en IRIX NFS. Normalmente, si un servidor exporta dos sistemas de archivos, uno de los cuales está montado sobre el otro, el cliente tendrá que montar ambos sistemas de archivos explícitamente para acceder a ellos. Si solo monta el padre, verá un directorio vacío en el lugar donde está montado el otro sistema de archivos. Ese sistema de archivos está "oculto".

Establecer la opción nohide en un sistema de archivos hace que este no esté oculto, y un cliente debidamente autorizado podrá moverse del padre a ese sistema de archivos sin notar el cambio.

Sin embargo, algunos clientes NFS no manejan bien esta situación ya que, por ejemplo, es posible que dos archivos en el mismo sistema de archivos aparente tengan el mismo número de inodo.

La opción nohide actualmente solo es efectiva en exportaciones de un solo host . No funciona de manera fiable con exportaciones de grupos de red, subred o comodín.

Esta opción puede ser muy útil en algunas situaciones, pero debe usarse con la debida precaución, y solo después de confirmar que el sistema cliente maneja la situación de manera efectiva.

La opción puede deshabilitarse explícitamente para NFSv2 y NFSv3 con hide.

Esta opción no es relevante cuando se usa NFSv4. NFSv4 nunca oculta los sistemas de archivos subordinados. Cualquier sistema de archivos que se exporte será visible donde se espera cuando se use NFSv4.

crossmnt
Esta opción es similar a nohide pero hace posible que los clientes accedan a todos los sistemas de archivos montados en un sistema de archivos marcado con crossmnt. Así que cuando un sistema de archivos hijo "B" está montado en un padre "A", establecer crossmnt en "A" tiene un efecto similar a establecer "nohide" en B.

Con nohide el sistema de archivos hijo debe exportarse explícitamente. Con crossmnt no es necesario. Si un hijo de un archivo crossmnt no se exporta explícitamente, entonces se exportará implícitamente con las mismas opciones de exportación que el padre, excepto fsid=. Esto hace imposible no exportar un hijo de un sistema de archivos crossmnt . Si algunos pero no todos los sistemas de archivos subordinados de un padre deben exportarse, entonces deben exportarse explícitamente y el padre no debe tener crossmnt establecido.

La opción nocrossmnt puede deshabilitar explícitamente crossmnt si se estableció previamente. Esto rara vez es útil.

subtree_check
Esta opción habilita la verificación de subárbol, que puede tener beneficios de seguridad leves, pero puede disminuir la fiabilidad en algunas circunstancias.

Si se exporta un subdirectorio de un sistema de archivos, pero no el sistema de archivos completo, entonces cada vez que llega una petición NFS, el servidor debe verificar no solo que el archivo accedido está en el sistema de archivos apropiado (lo cual es fácil) sino también que está en el árbol exportado (lo cual es más difícil). Esta verificación se llama subtree_check.

Para realizar esta verificación, el servidor debe incluir alguna información sobre la ubicación del archivo en el "filehandle" que se le da al cliente. Esto puede causar problemas al acceder a archivos que se renombran mientras un cliente los tiene abiertos (aunque en muchos casos simples seguirá funcionando).

La verificación de subárbol también se usa para asegurar que los archivos dentro de directorios a los que solo root tiene acceso solo puedan ser accedidos si el sistema de archivos se exporta con no_root_squash (véase abajo), incluso si el archivo en sí permite un acceso más general.

Para más información sobre las implicaciones de seguridad, refiérase a la sección de Exportaciones de Subdirectorios.

Como guía general, un sistema de archivos de directorio de inicio, que normalmente se exporta en la raíz y puede ver muchos renombramientos de archivos, debería exportarse con la verificación de subárbol deshabilitada. Un sistema de archivos que es mayormente de solo lectura, y al menos no ve muchos renombramientos de archivos (p. ej. /usr o /var) y para el cual pueden exportarse subdirectorios, probablemente debería exportarse con las verificaciones de subárbol habilitadas.

El comportamiento predeterminado de tener las verificaciones de subárbol deshabilitadas puede solicitarse explícitamente con no_subtree_check.

Antes de la versión 1.1.0 de nfs-utils, el predeterminado era subtree_check. Desde la versión 1.1.0, el predeterminado es no_subtree_check ya que la verificación de subárbol tiende a causar más problemas de los que vale. Si realmente requiere la verificación de subárbol, debe poner esa opción explícitamente en el archivo exports . Si no pone ninguna de las opciones, exportfs le advertirá que el cambio ha ocurrido.

insecure_locks
no_auth_nlm
Esta opción (los dos nombres son sinónimos) le dice al servidor NFS no requerir autenticación de las peticiones de bloqueo (es decir, peticiones que usan el protocolo NLM). Normalmente el servidor NFS requerirá que una petición de bloqueo posea las credenciales de un usuario que tenga acceso de lectura al archivo. Con esta opción no se realizarán comprobaciones de acceso.

Las primeras implementaciones de clientes NFS no enviaban credenciales con las peticiones de bloqueo, y aún existen muchos clientes NFS actuales basados en las implementaciones antiguas. Use esta opción si encuentra que solo puede bloquear archivos que son legibles por todos.

El comportamiento predeterminado de requerir autenticación para las peticiones NLM puede solicitarse explícitamente con cualquiera de los sinónimos auth_nlm, o secure_locks.

mountpoint=path
mp
Esta opción hace posible exportar un directorio solo si ha sido montado exitosamente. Si no se da una ruta (p. ej. mountpoint o mp) entonces el punto de exportación también debe ser un punto de montaje. Si no lo es, entonces el punto de exportación no se exporta. Esto le permite estar seguro de que el directorio debajo de un punto de montaje nunca se exportará por accidente si, por ejemplo, el sistema de archivos falló al montarse debido a un error de disco.

Si se da una ruta (p. ej. mountpoint=/path o mp=/path) entonces la ruta nominada debe ser un punto de montaje para que el punto de exportación sea exportado.

fsid=num|root|uuid
NFS necesita poder identificar cada sistema de archivos que exporta. Normalmente usará un UUID para el sistema de archivos (si el sistema de archivos tiene uno) o el número de dispositivo del dispositivo que contiene el sistema de archivos (si el sistema de archivos está almacenado en el dispositivo).

Como no todos los sistemas de archivos están almacenados en dispositivos, y no todos los sistemas de archivos tienen UUIDs, a veces es necesario decirle explícitamente a NFS cómo identificar un sistema de archivos. Esto se hace con la opción fsid= .

Para NFSv4, hay un sistema de archivos distinguido que es la raíz de todos los sistemas de archivos exportados. Esto se especifica con fsid=root o fsid=0 ambos significan exactamente lo mismo.

Otros sistemas de archivos pueden identificarse con un pequeño entero, o un UUID que debe contener 32 dígitos hexadecimales y puntuación arbitraria.

Los kernels de Linux versión 2.6.20 y anteriores no entienden la configuración UUID, por lo que debe usarse un pequeño entero si se necesita establecer una opción fsid para tales kernels. Establecer tanto un número pequeño como un UUID es compatible, por lo que la misma configuración puede hacerse funcionar en kernels antiguos y nuevos por igual.

nordirplus
Esta opción deshabilitará el manejo de peticiones READDIRPLUS. Cuando está establecida, las peticiones READDIRPLUS de clientes NFS devuelven NFS3ERR_NOTSUPP, y los clientes recurren a READDIR. Esta opción afecta solo a los clientes NFSv3.
refer=path@host[+host][:path@host[+host]]
Un cliente que referencie el punto de exportación será dirigido a elegir de la lista dada una ubicación alternativa para el sistema de archivos. (Tenga en cuenta que el servidor debe tener un punto de montaje aquí, aunque no se requiere un sistema de archivos diferente; así que, por ejemplo, mount --bind /path /path es suficiente.)

Esta opción afecta solo a los clientes NFSv4. Otros clientes ignorarán todas las partes "refer=".

replicas=path@host[+host][:path@host[+host]]
Si el cliente pide ubicaciones alternativas para el punto de exportación, se le dará esta lista de alternativas. (Tenga en cuenta que la replicación real del sistema de archivos debe manejarse en otro lugar.)
pnfs
Esta opción habilita el uso de la extensión pNFS si el nivel de protocolo es NFSv4.1 o superior, y el sistema de archivos soporta exportaciones pNFS. Con pNFS los clientes pueden evadir el servidor y realizar E/S directamente a los dispositivos de almacenamiento. El comportamiento predeterminado puede solicitarse explícitamente con la opción no_pnfs .
security_label
Con esta opción establecida, los clientes que usen NFSv4.2 o superior podrán establecer y recuperar etiquetas de seguridad (como las usadas por SELinux). Esto solo funcionará si todos los clientes usan una política de seguridad consistente. Tenga en cuenta que

NOMBRE

exports – tabla de exportación NFS

DESCRIPCIÓN

El archivo /etc/exports se utiliza para configurar el sistema de archivos que el servidor NFS exportará a los clientes.

Cada línea de la tabla de exportación define una exportación y contiene los siguientes campos:

path
La ruta de montaje del directorio o sistema de archivos que se va a exportar.
host
Una lista de hosts o grupos de hosts separados por espacios. Si se utiliza un asterisco (*) o un signo de interrogación (?) en el nombre del host, se expandirá para que coincida con una lista de hosts. El nombre de host puede ser un nombre de dominio completo, una dirección IP o un nombre de host corto. Los grupos de hosts se especifican con el prefijo @ y se resuelven utilizando el archivo /etc/netgroup. Los hosts se pueden especificar en forma de subredes IPv4 o rangos de direcciones IPv6.
options
Opciones separadas por comas que controlan el acceso a la exportación. Las opciones se aplican a la exportación de la línea en la que se especifican.

Opciones de Exportación

sync o async
Controla si las escrituras deben confirmarse en el disco antes de que se devuelva la confirmación al cliente. sync es más seguro pero más lento, mientras que async es más rápido pero menos seguro. El valor predeterminado es async.
rw o ro
Especifica si la exportación se montará como solo lectura (ro) o de lectura/escritura (rw). El valor predeterminado es ro.
root_squash
Mapea las solicitudes del usuario root del cliente a un UID anónimo en el servidor. Esto ayuda a prevenir ataques de seguridad al evitar que el root del cliente tenga acceso de root a los archivos del servidor. Esta es la opción predeterminada.
no_root_squash
Desactiva el mapeo del root del cliente a un UID anónimo. Útil para clientes sin disco donde el root del cliente debe ser el mismo que el root del servidor.
all_squash
Mapea todos los UIDs y GIDs del cliente a un UID y GID anónimos en el servidor. Útil para directorios públicos como FTP o news.
no_all_squash
Desactiva el mapeo de todos los UIDs y GIDs a un UID anónimo. Esta es la opción predeterminada.
anonuid y anongid
Especifica el UID y GID anónimos que se utilizarán cuando se apliquen las opciones root_squash o all_squash.
secure_port
Solo permite que los clientes se conecten desde puertos privilegiados (menores de 1024). Este es el comportamiento predeterminado.
insecure_port
Permite que los clientes se conecten desde cualquier puerto. Útil para clientes que no pueden usar puertos privilegiados, como algunos clientes PC-NFS.
subtree_check
Habilita la comprobación de subárboles. Esto garantiza que solo se exporten los archivos dentro del subárbol especificado. Puede mejorar la seguridad, pero puede tener un impacto en el rendimiento y causar problemas si los archivos se mueven dentro del subárbol.
no_subtree_check
Deshabilita la comprobación de subárboles. Esta es la opción predeterminada.
crossmnt
Permite que se exporten los puntos de montaje dentro de un sistema de archivos exportado. Sin esta opción, las exportaciones de subdirectorios solo se permitirán si el subdirectorio también es un punto de montaje.
fsid=num | uuid
Asigna un identificador numérico o UUID al sistema de archivos exportado. Esto es necesario para las exportaciones de subdirectorios cuando se utiliza la opción crossmnt.
security_label
Permite que el servidor NFS aplique etiquetas de seguridad a los archivos exportados. Esto es útil en entornos con políticas de seguridad obligatorias. Los kernels antiguos no admitían esta opción y habilitaban las etiquetas de seguridad de forma predeterminada.
reexport=auto-fsidnum|predefined-fsidnum
Esta opción ayuda cuando se reexporta una compartición NFS. Dado que el servidor NFS necesita un identificador único para cada sistema de archivos exportado y una compartición NFS no puede proporcionar uno, normalmente se necesita un fsid manual. Tan pronto como se utiliza crossmnt, la asignación manual de fsid ya no funcionará. Aquí es donde esta opción resulta útil. Asignará automáticamente un fsid numérico a las comparticiones NFS exportadas. Las relaciones fsid y ruta se almacenan en una base de datos SQLite. Si se selecciona auto-fsidnum, el fsid también se asigna automáticamente. predefined-fsidnum asume números de fsid preasignados y simplemente los buscará. Esta opción también depende del kernel; necesitará al menos la versión del kernel 5.19. Dado que reexport= puede asignar y asignar automáticamente fsids numéricos, ya no es posible tener fsids numéricos en otras exportaciones tan pronto como se utiliza esta opción en al menos una entrada de exportación.

La asociación entre los números de fsid y las rutas se almacena en una base de datos SQLite. No edite ni elimine la base de datos a menos que sepa exactamente lo que está haciendo. predefined-fsidnum es útil cuando ha utilizado auto-fsidnum anteriormente y no desea que se almacenen más entradas.

Mapeo de ID de Usuario

nfsd basa su control de acceso a archivos en la máquina del servidor en el uid y gid proporcionados en cada solicitud RPC de NFS. El comportamiento normal que esperaría un usuario es poder acceder a sus archivos en el servidor tal como lo haría en un sistema de archivos normal. Esto requiere que se utilicen los mismos uids y gids en la máquina cliente y en la máquina del servidor. Esto no siempre es cierto, ni siempre es deseable.

Muy a menudo, no es deseable que el usuario root en una máquina cliente también sea tratado como root al acceder a archivos en el servidor NFS. Con este fin, el uid 0 generalmente se mapea a un ID diferente: el llamado uid anónimo o de nobody. Este modo de operación (llamado `root squashing') es el predeterminado y se puede desactivar con no_root_squash.

De forma predeterminada, exportfs elige un uid y gid de 65534 para el acceso aplastado. Estos valores también se pueden anular con las opciones anonuid y anongid. Finalmente, puede mapear todas las solicitudes de usuario al uid anónimo especificando la opción all_squash.

Aquí está la lista completa de opciones de mapeo:

root_squash
Mapea las solicitudes de uid/gid 0 al uid/gid anónimo. Tenga en cuenta que esto no se aplica a ningún otro uid o gid que pueda ser igualmente sensible, como el usuario bin o el grupo staff.
no_root_squash
Desactiva el root squashing. Esta opción es principalmente útil para clientes sin disco.
all_squash
Mapea todos los uids y gids al usuario anónimo. Útil para directorios FTP públicos exportados por NFS, directorios de spool de noticias, etc. La opción opuesta es no_all_squash, que es la configuración predeterminada.
anonuid y anongid
Estas opciones establecen explícitamente el uid y gid de la cuenta anónima. Esta opción es principalmente útil para clientes PC/NFS, donde es posible que desee que todas las solicitudes parezcan provenir de un solo usuario. Como ejemplo, considere la entrada de exportación para /home/joe en la sección de ejemplo a continuación, que mapea todas las solicitudes al uid 150 (que supuestamente es el del usuario joe).

Exportaciones de Subdirectorios

Normalmente, solo debe exportar la raíz de un sistema de archivos. El servidor NFS también le permitirá exportar un subdirectorio de un sistema de archivos, sin embargo, esto tiene inconvenientes:

En primer lugar, es posible que un usuario malintencionado pueda acceder a archivos en el sistema de archivos fuera del subdirectorio exportado, adivinando los filehandles de esos otros archivos. En algunos casos, un usuario malintencionado también puede acceder a archivos en otros sistemas de archivos que no han sido exportados reemplazando el subdirectorio exportado con un enlace simbólico a cualquier otro directorio. La única forma de evitar esto es utilizando la opción subtree_check, que puede causar otros problemas.

En segundo lugar, es posible que las opciones de exportación no se apliquen de la manera que esperaría. Por ejemplo, la opción security_label no funcionará en las exportaciones de subdirectorios, y si las exportaciones de subdirectorios anidados cambian las opciones de security_label o sec=, los clientes NFSv4 normalmente verán solo las opciones de la exportación principal. Además, cuando las opciones de seguridad difieran, un cliente malintencionado puede utilizar ataques de adivinación de filehandles para acceder a los archivos de un subdirectorio utilizando las opciones de otro.

Tablas de Exportación Adicionales

Después de leer /etc/exports, exportfs lee archivos en el directorio /etc/exports.d como tablas de exportación adicionales. Solo se consideran los archivos que terminan en .exports. Los archivos que comienzan con un punto se ignoran. El formato para las tablas de exportación adicionales es el mismo que /etc/exports.

EJEMPLO

# archivo /etc/exports de muestra
/               master(rw) trusty(rw,no_root_squash)
/projects       proj*.local.domain(rw)
/usr            *.local.domain(ro) @trusted(rw)
/home/joe       pc001(rw,all_squash,anonuid=150,anongid=100)
/pub            *(ro,insecure,all_squash)
/srv/www        -sync,rw server @trusted @external(ro)
/foo            2001:db8:9:e54::/64(rw) 192.0.2.0/24(rw)
/build          buildhost[0-9].local.domain(rw)

La primera línea exporta todo el sistema de archivos a las máquinas master y trusty. Además del acceso de escritura, se desactiva todo el aplastamiento de uid para el host trusty. La segunda y tercera entrada muestran ejemplos de nombres de host comodín y netgroups (esta es la entrada `@trusted'). La cuarta línea muestra la entrada para el cliente PC/NFS discutido anteriormente. La línea 5 exporta el directorio público de FTP a todos los hosts del mundo, ejecutando todas las solicitudes bajo la cuenta de nadie. La opción insecure en esta entrada también permite a los clientes con implementaciones NFS que no utilizan un puerto reservado para NFS. La sexta línea exporta un directorio de lectura/escritura a la máquina 'server', así como al netgroup `@trusted', y los tres montajes con la opción `sync' habilitada. La séptima línea exporta un directorio a una subred IPv6 y una IPv4. La octava línea demuestra una coincidencia de comodín de clase de caracteres.
