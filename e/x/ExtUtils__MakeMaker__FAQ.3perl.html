Filosofía e Historia

¿Por qué no usar simplemente <inserta aquí otra herramienta de configuración de compilación>?
¿Por qué MakeMaker reinventó la rueda de la configuración de compilación? ¿Por qué no usar simplemente autoconf o automake o ppm o Ant o ...?

Hay muchas razones, pero la principal es la compatibilidad entre plataformas.

Perl es uno de los programas más portados que existen. Funciona en sistemas operativos que ni siquiera he oído nombrar (consulta perlport para más detalles). Necesita una herramienta de compilación que pueda funcionar en todas esas plataformas y con cualquier compilador y enlazador C extravagante que puedan tener.

No existe tal herramienta de compilación. Incluso make en sí mismo tiene dialectos muy diferentes. Así que tenemos que construir la nuestra.

¿Qué es Module::Build y cómo se relaciona con MakeMaker?
Module::Build es un proyecto de Ken Williams para reemplazar a MakeMaker. Sus principales ventajas son:
  • puro perl. sin make, sin comandos de shell
  • más fácil de personalizar
  • interiores más limpios
  • menos relleno

Module::Build fue durante mucho tiempo el sucesor oficial designado de MakeMaker. Sin embargo, la velocidad tanto de su desarrollo como de su adopción se ha ralentizado en los últimos años, y no está claro qué depara el futuro para él. Dicho esto, Module::Build sentó las bases para algo se convirtiera en el sucesor de MakeMaker. Los mantenedores de MakeMaker han dicho durante mucho tiempo que es un callejón sin salida y que debe mantenerse funcionando, mientras se tiene cuidado de extenderlo con nuevas funciones.

Escritura de Módulos

¿Cómo mantengo mi $VERSION actualizado sin tener que restablecerlo manualmente?
A menudo quieres establecer manualmente el $VERSION en la distribución del módulo principal porque esta es la versión que todos ven en CPAN y quizás quieras personalizarla un poco. Pero para todos los demás módulos en tu distribución, $VERSION es realmente solo contabilidad y todo lo importante es que suba cada vez que el módulo se cambia. Hacer esto a mano es una molestia y a menudo se olvida.

Probablemente la forma más fácil de hacer esto es usando perl-reversion en Perl::Version:

perl-reversion -bump

Si tu sistema de control de versiones admite números de revisión (git no lo hace fácilmente), la forma más sencilla de hacerlo automáticamente es usar su número de revisión (¿estás usando control de versiones, verdad?).

En CVS, RCS y SVN usas $Revision$ (consulta la documentación de tu sistema de control de versiones para más detalles). Cada vez que el archivo se registra, el $Revision$ se actualizará, actualizando tu $VERSION.

SVN usa un entero simple para $Revision$, así que puedes adaptarlo para tu $VERSION así:

($VERSION) = q$Revision$ =~ /(\d+)/;

En CVS y RCS la versión 1.9 va seguida de 1.10. Dado que CPAN compara los números de versión numéricamente, usamos un sprintf() para convertir 1.9 a 1.009 y 1.10 a 1.010, que se comparan correctamente.

$VERSION = sprintf "%d.%03d", q$Revision$ =~ /(\d+)\.(\d+)/g;

Si están involucradas ramas (es decir, $Revision: 1.5.3.4$) es un poco más complicado.

# debe estar todo en una sola línea o MakeMaker se confundirá.
$VERSION = do { my @r = (q$Revision$ =~ /\d+/g); sprintf "%d."."%03d" x $#r, @r };

En SVN, $Revision$ debería ser el mismo para cada archivo del proyecto, por lo que todos tendrían la misma $VERSION. CVS y RCS tienen un $Revision$ diferente por archivo, así que cada archivo tendrá un $VERSIONdiferente. Los sistemas de control de versiones distribuidos, como SVK, pueden tener un $Revision$ diferente basado en quién saca el archivo, lo que lleva a un $VERSION diferente en cada máquina. Finalmente, algunos sistemas de control de versiones distribuidos, como darcs, no tienen ningún concepto de número de revisión.

¿Qué es esto de META.yml y cómo llegó a mi MANIFEST?!
META.yml es un archivo de metadatos de módulo iniciado por Module::Build y generado automáticamente como parte del objetivo 'distdir' (y por lo tanto 'dist'). Consulta "Module Meta-Data" en ExtUtils::MakeMaker.

Para desactivar su generación, pasa el "NO_META" flag a WriteMakefile().

¿Cómo elimino todo lo que no está en mi MANIFEST?
Algunas personas se sorprenden de que "make distclean" no elimine todo lo que no esté listado en su MANIFEST (haciendo así una distribución limpia), sino que solo les diga lo que necesitan eliminar. Esto se hace porque se considera demasiado peligroso. Mientras desarrollas tu módulo podrías escribir un archivo nuevo, no añadirlo al MANIFEST, ejecutar un "distclean" y estar triste porque tu nuevo trabajo fue eliminado.

Si realmente quieres hacer esto, puedes usar ExtUtils::Manifest::manifind() para leer el MANIFEST y File::Find para eliminar los archivos. Pero tienes que tener cuidado. Aquí tienes un script para hacer eso. Úsalo bajo tu propio riesgo. Diviértete haciendo agujeros en tu pie.

#!/usr/bin/perl -w
use strict;
use File::Spec;
use File::Find;
use ExtUtils::Manifest qw(maniread);
my %manifest = map  {( $_ => 1 )}
               grep { File::Spec->canonpath($_) }
                    keys %{ maniread() };
if( !keys %manifest ) {
    print "No files found in MANIFEST.  Stopping.\n";
    exit;
}
find({
      wanted   => sub {
          my $path = File::Spec->canonpath($_);
          return unless -f $path;
          return if exists $manifest{ $path };
          print "unlink $path\n";
          unlink $path;
      },
      no_chdir => 1
     },
     "."
);

XS

¿Cómo evito los errores "object version X.XX does not match bootstrap parameter Y.YY"?
El código XS es muy sensible al número de versión del módulo y se quejará si el número de versión en tu módulo Perl no coincide. Si cambias el número de versión de tu módulo sin volver a ejecutar Makefile.PL, el número de versión antiguo permanecerá en el Makefile, haciendo que el código XS se compile con el número incorrecto.

Para evitar esto, puedes forzar que el Makefile se reconstruya cada vez que cambies el módulo que contiene el número de versión añadiendo esto a tus WriteMakefile() argumentos.

depend => { '$(FIRST_MAKEFILE)' => '$(VERSION_FROM)' }
¿Cómo hago que dos o más archivos XS coexistan en el mismo directorio?
A veces necesitas tener dos o más archivos XS en el mismo paquete. Hay tres formas: "XSMULTI", directorios separados, y arrancar un XS desde otro.
XSMULTI
Estructura tus módulos de modo que todos estén ubicados bajo lib, de modo que "Foo::Bar" esté en lib/Foo/Bar.pm y lib/Foo/Bar.xs, etc. Haz que tu "WriteMakefile" de nivel superior establezca la variable "XSMULTI" a un valor verdadero.

Eh, eso es todo.

Directorios separados
Pon cada archivo XS en directorios separados, cada uno con su propio Makefile.PL. Asegúrate de que cada uno de esos Makefile.PLs tenga los correctos "CFLAGS", "INC", "LIBS" etc. Necesitarás asegurarte de que el nivel superior Makefile.PL se refiera a cada uno de estos usando "DIR".
Arranque
Asumamos que tenemos un paquete "Cool::Foo", que incluye los módulos "Cool::Foo" y "Cool::Bar" cada uno con un archivo XS separado. Primero usamos el siguiente Makefile.PL: 
use ExtUtils::MakeMaker;
WriteMakefile(
    NAME              => 'Cool::Foo',
    VERSION_FROM      => 'Foo.pm',
    OBJECT              => q/$(O_FILES)/,
    # ... otros atributos ...
);

Observa el "OBJECT" atributo. MakeMaker genera las siguientes variables en el Makefile:

# Handy lists of source code files:
XS_FILES= Bar.xs \
      Foo.xs
C_FILES = Bar.c \
      Foo.c
O_FILES = Bar.o \
      Foo.o

Por lo tanto podemos usar la variable "O_FILES" para decirle a MakeMaker que use estos objetos en la biblioteca compartida.

Eso es bastante todo. Ahora escribe Foo.pm y Foo.xs, Bar.pm y Bar.xs, donde Foo.pm arranca la biblioteca compartida y Bar.pm simplemente carga Foo.pm.

El único asunto que queda es cómo arrancar Bar.xs. Esto se hace desde Foo.xs:

MODULE = Cool::Foo PACKAGE = Cool::Foo
BOOT:
# boot the second XS file
boot_Cool__Bar(aTHX_ cv);

Si tienes más de dos archivos, este es el lugar desde donde deberías arrancar los archivos XS adicionales.

Los siguientes cuatro archivos resumen todos los detalles discutidos hasta ahora.

Foo.pm:
-------
package Cool::Foo;
require DynaLoader;
our @ISA = qw(DynaLoader);
our $VERSION = '0.01';

1;

-------
package Cool::Bar;

1;

-------
#include "EXTERN.h"
#include "perl.h"
