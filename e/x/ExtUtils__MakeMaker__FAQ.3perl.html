NAME

ExtUtils::MakeMaker::FAQ - Preguntas frecuentes sobre MakeMaker

DESCRIPTION

Preguntas frecuentes, trucos y consejos para ExtUtils::MakeMaker.

Instalación del módulo

¿Cómo instalo un módulo en mi directorio de hogar?
Si no eres el administrador de Perl, probablemente no tengas permiso para instalar un módulo en su ubicación predeterminada. Hay formas de manejar esto con un muchísimo menos esfuerzo manual por tu parte mediante perlbrew y local::lib.

De lo contrario, puedes instalarlo para tu propio uso en tu directorio de hogar de la siguiente manera:

# Para usuarios no de Unix, reemplaza ~ con /ruta/a/tu/directorio/de/hogar
perl Makefile.PL INSTALL_BASE=~

Esto colocará los módulos en ~/lib/perl5, las páginas de manuales en ~/man y los programas en ~/bin.

Para asegurar que tus programas en Perl puedan ver estos nuevos módulos instalados, configura tu variable de entorno "PERL5LIB" en ~/lib/perl5 o instruye a cada uno de tus programas para que busque en ese directorio con lo siguiente:

use lib "$ENV{HOME}/lib/perl5";

o si $ENV{HOME} no está configurado y no quieres configurarlo por alguna razón, hazlo de la manera larga.

use lib "/ruta/a/tu/directorio/de/hogar/lib/perl5";
¿Cómo hago que MakeMaker y Module::Build se instalen en el mismo lugar?
Module::Build, a partir de la versión 0.28, soporta dos formas de instalar en la misma ubicación que MakeMaker.

Recomendamos encarecidamente el método install_base, ya que es el más simple y se aproxima más al comportamiento esperado de un prefijo de instalación.

1) Usa INSTALL_BASE / "--install_base"

MakeMaker (a partir de 6.31) y Module::Build (a partir de 0.28) pueden instalar en las mismas ubicaciones utilizando el concepto "install_base". Consulta "INSTALL_BASE" en ExtUtils::MakeMaker para más detalles. Para que MM y MB se instalen en la misma ubicación, simplemente establece INSTALL_BASE en MM y "--install_base" en MB en la misma ubicación.

perl Makefile.PL INSTALL_BASE=/whatever
perl Build.PL    --install_base /whatever

Esto funciona de manera más similar al comportamiento de otros lenguajes cuando especificas un prefijo. Recomendamos este método.

2) Usa PREFIX / "--prefix"

Module::Build 0.28 agregó soporte para "--prefix", que funciona como el PREFIX de MakeMaker.

perl Makefile.PL PREFIX=/whatever
perl Build.PL    --prefix /whatever

Desaconsejamos encarecidamente este método. Solo debe usarse si sabes lo que haces y específicamente necesitas el comportamiento de PREFIX. El algoritmo de PREFIX es complicado y está centrado en coincidir con la instalación del sistema.

¿Cómo evito la instalación de páginas de manuales?
Las versiones recientes de MakeMaker instalarán páginas de manuales por defecto solo en sistemas operativos basados en Unix. Para generar páginas de manuales en sistemas operativos no basados en Unix, haz el objetivo "manifypods".

Para un módulo individual:

perl Makefile.PL INSTALLMAN1DIR=none INSTALLMAN3DIR=none

Si quieres suprimir la instalación de páginas de manuales para todos los módulos que tienes, debes recompilar Perl y decirle 'none' donde pregunta dónde instalar las páginas de manuales.

¿Cómo uso un módulo sin instalarlo?
Hay dos formas. Una es construir el módulo normalmente... 
perl Makefile.PL
make
make test

...y luego usar blib para indicar a Perl el módulo construido pero no instalado:

perl -Mblib script.pl
perl -Mblib -e '...'

La otra es instalar el módulo en una ubicación temporal.

perl Makefile.PL INSTALL_BASE=~/tmp
make
make test
make install

Y luego establecer PERL5LIB en ~/tmp/lib/perl5. Esto funciona bien cuando tienes múltiples módulos con los que trabajar. También asegura que el módulo pase por todo su proceso de instalación, lo cual puede modificarlo. De nuevo, local::lib puede ayudarte aquí.

¿Cómo organizo las pruebas en subdirectorios y las hago ejecutar?
Tomemos la siguiente estructura de directorio de pruebas: 
t/foo/sometest.t
t/bar/othertest.t
t/bar/baz/anothertest.t

Ahora, dentro de la función WriteMakefile() en tu Makefile.PL, especifica dónde se encuentran tus pruebas con la directiva "test":

test => {TESTS => 't/*.t t/*/*.t t/*/*/*.t'}

La primera entrada en la cadena ejecutará todas las pruebas en el directorio principal t/. La segunda ejecutará todos los archivos de prueba ubicados en cualquier subdirectorio bajo t/. La tercera ejecutará todos los archivos de prueba dentro de cualquier subdirectorio dentro de cualquier otro subdirectorio ubicado bajo t/.

Ten en cuenta que no tienes que usar comodines. Puedes especificar explícitamente qué subdirectorios ejecutar las pruebas:

test => {TESTS => 't/*.t t/foo/*.t t/bar/baz/*.t'}
PREFIX vs INSTALL_BASE desde Module::Build::Cookbook
El comportamiento de PREFIX es complicado y depende estrechamente de cómo esté configurado tu Perl. Las ubicaciones de instalación resultantes varían de una máquina a otra y también entre diferentes instalaciones de Perl en la misma máquina. Debido a esto, es difícil documentar dónde PREFIX colocará tus módulos.

En contraste, INSTALL_BASE tiene ubicaciones de instalación predecibles y fáciles de explicar. Ahora que tanto Module::Build como MakeMaker tienen INSTALL_BASE, hay poca razón para usar PREFIX salvo para preservar tus ubicaciones de instalación existentes. Si estás comenzando una instalación de Perl nueva, te recomendamos usar INSTALL_BASE. Si tienes una instalación existente instalada mediante PREFIX, considera moverla a una estructura de instalación que coincida con INSTALL_BASE y usar esa en su lugar.

Generar archivos *.pm con sustituciones de ejemplo de $VERSION
Si quieres configurar tus archivos de módulo para condiciones locales, o para insertar automáticamente un número de versión, puedes usar la capacidad "PL_FILES" de EUMM, donde ejecutará automáticamente cada *.PL que encuentre para generar su nombre base. Por ejemplo: 
# Makefile.PL:
require 'common.pl';
my $version = get_version();
my @pms = qw(Foo.pm);
WriteMakefile(
  NAME => 'Foo',
  VERSION => $version,
  PM => { map { ($_ => "\$(INST_LIB)/$_") } @pms },
  clean => { FILES => join ' ', @pms },
);
# common.pl:
sub get_version { '0.04' }
sub process { my $v = get_version(); s/__VERSION__/$v/g; }
1;
# Foo.pm.PL:
require 'common.pl';
$_ = join '', <DATA>;
process();
my $file = shift;
open my $fh, '>', $file or die "$file: $!";
print $fh $_;
__DATA__
package Foo;
our $VERSION = '__VERSION__';
1;

Puedes notar que "PL_FILES" no se especifica arriba, ya que el predeterminado de mapear cada archivo .PL a su nombre base funciona bien.

Si el módulo generado fuera específico de la arquitectura, podrías reemplazar "$(INST_LIB)" arriba con "$(INST_ARCHLIB)", aunque si localizas los módulos bajo lib, eso implicaría asegurar que cualquier "lib/" delante de la ubicación del módulo se eliminara.

Errores y problemas comunes

"No rule to make target `/usr/lib/perl5/CORE/config.h', needed by `Makefile'"
Justo lo que dice, te falta ese archivo. MakeMaker lo usa para determinar si Perl se ha reconstruido desde que se creó el Makefile. Es un poco un error que detenga la instalación.

Algunos sistemas operativos no incluyen el directorio CORE con su instalación base de Perl. Para resolver el problema, probablemente necesites instalar un paquete de desarrollo de Perl, como perl-devel (CentOS, Fedora y otros sistemas Redhat) o perl (Ubuntu y otros sistemas Debian).

Filosofía e Historia

¿Por qué no usar simplemente <inserta aquí otra herramienta de configuración de compilación>?
¿Por qué MakeMaker reinventó la rueda de la configuración de compilación? ¿Por qué no usar simplemente autoconf o automake o ppm o Ant o ...?

Hay muchas razones, pero la principal es la compatibilidad entre plataformas.

Perl es uno de los programas más portados que existen. Funciona en sistemas operativos que ni siquiera he oído nombrar (consulta perlport para más detalles). Necesita una herramienta de compilación que pueda funcionar en todas esas plataformas y con cualquier compilador y enlazador C extravagante que puedan tener.

No existe tal herramienta de compilación. Incluso make en sí mismo tiene dialectos muy diferentes. Así que tenemos que construir la nuestra.

¿Qué es Module::Build y cómo se relaciona con MakeMaker?
Module::Build es un proyecto de Ken Williams para reemplazar a MakeMaker. Sus principales ventajas son:
  • puro perl. sin make, sin comandos de shell
  • más fácil de personalizar
  • interiores más limpios
  • menos relleno

Module::Build fue durante mucho tiempo el sucesor oficial designado de MakeMaker. Sin embargo, la velocidad tanto de su desarrollo como de su adopción se ha ralentizado en los últimos años, y no está claro qué depara el futuro para él. Dicho esto, Module::Build sentó las bases para algo se convirtiera en el sucesor de MakeMaker. Los mantenedores de MakeMaker han dicho durante mucho tiempo que es un callejón sin salida y que debe mantenerse funcionando, mientras se tiene cuidado de extenderlo con nuevas funciones.

Escritura de Módulos

¿Cómo mantengo mi $VERSION actualizado sin tener que restablecerlo manualmente?
A menudo quieres establecer manualmente el $VERSION en la distribución del módulo principal porque esta es la versión que todos ven en CPAN y quizás quieras personalizarla un poco. Pero para todos los demás módulos en tu distribución, $VERSION es realmente solo contabilidad y todo lo importante es que suba cada vez que el módulo se cambia. Hacer esto a mano es una molestia y a menudo se olvida.

Probablemente la forma más fácil de hacer esto es usando perl-reversion en Perl::Version:

perl-reversion -bump

Si tu sistema de control de versiones admite números de revisión (git no lo hace fácilmente), la forma más sencilla de hacerlo automáticamente es usar su número de revisión (¿estás usando control de versiones, verdad?).

En CVS, RCS y SVN usas $Revision$ (consulta la documentación de tu sistema de control de versiones para más detalles). Cada vez que el archivo se registra, el $Revision$ se actualizará, actualizando tu $VERSION.

SVN usa un entero simple para $Revision$, así que puedes adaptarlo para tu $VERSION así:

($VERSION) = q$Revision$ =~ /(\d+)/;

En CVS y RCS la versión 1.9 va seguida de 1.10. Dado que CPAN compara los números de versión numéricamente, usamos un sprintf() para convertir 1.9 a 1.009 y 1.10 a 1.010, que se comparan correctamente.

$VERSION = sprintf "%d.%03d", q$Revision$ =~ /(\d+)\.(\d+)/g;

Si están involucradas ramas (es decir, $Revision: 1.5.3.4$) es un poco más complicado.

# debe estar todo en una sola línea o MakeMaker se confundirá.
$VERSION = do { my @r = (q$Revision$ =~ /\d+/g); sprintf "%d."."%03d" x $#r, @r };

En SVN, $Revision$ debería ser el mismo para cada archivo del proyecto, por lo que todos tendrían la misma $VERSION. CVS y RCS tienen un $Revision$ diferente por archivo, así que cada archivo tendrá un $VERSIONdiferente. Los sistemas de control de versiones distribuidos, como SVK, pueden tener un $Revision$ diferente basado en quién saca el archivo, lo que lleva a un $VERSION diferente en cada máquina. Finalmente, algunos sistemas de control de versiones distribuidos, como darcs, no tienen ningún concepto de número de revisión.

¿Qué es esto de META.yml y cómo llegó a mi MANIFEST?!
META.yml es un archivo de metadatos de módulo iniciado por Module::Build y generado automáticamente como parte del objetivo 'distdir' (y por lo tanto 'dist'). Consulta "Module Meta-Data" en ExtUtils::MakeMaker.

Para desactivar su generación, pasa el "NO_META" flag a WriteMakefile().

¿Cómo elimino todo lo que no está en mi MANIFEST?
Algunas personas se sorprenden de que "make distclean" no elimine todo lo que no esté listado en su MANIFEST (haciendo así una distribución limpia), sino que solo les diga lo que necesitan eliminar. Esto se hace porque se considera demasiado peligroso. Mientras desarrollas tu módulo podrías escribir un archivo nuevo, no añadirlo al MANIFEST, ejecutar un "distclean" y estar triste porque tu nuevo trabajo fue eliminado.

Si realmente quieres hacer esto, puedes usar ExtUtils::Manifest::manifind() para leer el MANIFEST y File::Find para eliminar los archivos. Pero tienes que tener cuidado. Aquí tienes un script para hacer eso. Úsalo bajo tu propio riesgo. Diviértete haciendo agujeros en tu pie.

#!/usr/bin/perl -w
use strict;
use File::Spec;
use File::Find;
use ExtUtils::Manifest qw(maniread);
my %manifest = map  {( $_ => 1 )}
               grep { File::Spec->canonpath($_) }
                    keys %{ maniread() };
if( !keys %manifest ) {
    print "No files found in MANIFEST.  Stopping.\n";
    exit;
}
find({
      wanted   => sub {
          my $path = File::Spec->canonpath($_);
          return unless -f $path;
          return if exists $manifest{ $path };
          print "unlink $path\n";
          unlink $path;
      },
      no_chdir => 1
     },
     "."
);

XS

¿Cómo evito los errores "object version X.XX does not match bootstrap parameter Y.YY"?
El código XS es muy sensible al número de versión del módulo y se quejará si el número de versión en tu módulo Perl no coincide. Si cambias el número de versión de tu módulo sin volver a ejecutar Makefile.PL, el número de versión antiguo permanecerá en el Makefile, haciendo que el código XS se compile con el número incorrecto.

Para evitar esto, puedes forzar que el Makefile se reconstruya cada vez que cambies el módulo que contiene el número de versión añadiendo esto a tus WriteMakefile() argumentos.

depend => { '$(FIRST_MAKEFILE)' => '$(VERSION_FROM)' }
¿Cómo hago que dos o más archivos XS coexistan en el mismo directorio?
A veces necesitas tener dos o más archivos XS en el mismo paquete. Hay tres formas: "XSMULTI", directorios separados, y arrancar un XS desde otro.
XSMULTI
Estructura tus módulos de modo que todos estén ubicados bajo lib, de modo que "Foo::Bar" esté en lib/Foo/Bar.pm y lib/Foo/Bar.xs, etc. Haz que tu "WriteMakefile" de nivel superior establezca la variable "XSMULTI" a un valor verdadero.

Eh, eso es todo.

Directorios separados
Pon cada archivo XS en directorios separados, cada uno con su propio Makefile.PL. Asegúrate de que cada uno de esos Makefile.PLs tenga los correctos "CFLAGS", "INC", "LIBS" etc. Necesitarás asegurarte de que el nivel superior Makefile.PL se refiera a cada uno de estos usando "DIR".
Arranque
Asumamos que tenemos un paquete "Cool::Foo", que incluye los módulos "Cool::Foo" y "Cool::Bar" cada uno con un archivo XS separado. Primero usamos el siguiente Makefile.PL: 
use ExtUtils::MakeMaker;
WriteMakefile(
    NAME              => 'Cool::Foo',
    VERSION_FROM      => 'Foo.pm',
    OBJECT              => q/$(O_FILES)/,
    # ... otros atributos ...
);

Observa el "OBJECT" atributo. MakeMaker genera las siguientes variables en el Makefile:

# Handy lists of source code files:
XS_FILES= Bar.xs \
      Foo.xs
C_FILES = Bar.c \
      Foo.c
O_FILES = Bar.o \
      Foo.o

Por lo tanto podemos usar la variable "O_FILES" para decirle a MakeMaker que use estos objetos en la biblioteca compartida.

Eso es bastante todo. Ahora escribe Foo.pm y Foo.xs, Bar.pm y Bar.xs, donde Foo.pm arranca la biblioteca compartida y Bar.pm simplemente carga Foo.pm.

El único asunto que queda es cómo arrancar Bar.xs. Esto se hace desde Foo.xs:

MODULE = Cool::Foo PACKAGE = Cool::Foo
BOOT:
# boot the second XS file
boot_Cool__Bar(aTHX_ cv);

Si tienes más de dos archivos, este es el lugar desde donde deberías arrancar los archivos XS adicionales.

Los siguientes cuatro archivos resumen todos los detalles discutidos hasta ahora.

Foo.pm:
-------
package Cool::Foo;
require DynaLoader;
our @ISA = qw(DynaLoader);
our $VERSION = '0.01';
bootstrap Cool::Foo $VERSION;
1;
Bar.pm:
-------
package Cool::Bar;
use Cool::Foo; # bootstraps Bar.xs
1;
Foo.xs:
-------
#include "EXTERN.h"
#include "perl.h"
#include "XSUB.h"
MODULE = Cool::Foo  PACKAGE = Cool::Foo
BOOT:
# boot the second archivo XS
boot_Cool__Bar(aTHX_ cv);
MÓDULO = Cool::Foo  PAQUETE = Cool::Foo  PREFIJO = cool_foo_
void
cool_foo_perl_rules()
    CÓDIGO:
    fprintf(stderr, "Cool::Foo dice: Perl Rules\n");
Bar.xs:
-------
#include "EXTERN.h"
#include "perl.h"
#include "XSUB.h"
MÓDULO = Cool::Bar  PAQUETE = Cool::Bar PREFIJO = cool_bar_
void
cool_bar_perl_rules()
    CÓDIGO:
    fprintf(stderr, "Cool::Bar dice: Perl Rules\n");

Y por supuesto, una prueba muy básica:

t/cool.t:
--------
use Test::More tests => 1;
use Cool::Foo;
use Cool::Bar;
Cool::Foo::perl_rules();
Cool::Bar::perl_rules();
ok 1;

DISEÑO

Jerarquía de objetos de MakeMaker (simplificada)

Lo que la mayoría de la gente necesita saber (las superclases están arriba.)

ExtUtils::MM_Any
        |
ExtUtils::MM_Unix
        |
ExtUtils::MM_{Sistema Operativo Actual}
        |
ExtUtils::MakeMaker
        |
       MY

El objeto realmente utilizado es de la clase MY, lo que le permite anular partes de MakeMaker dentro de su Makefile.PL declarando MY::foo() métodos.

Jerarquía de objetos de MakeMaker (real)

Así es como funciona realmente:

                                ExtUtils::MM_Any
                                        |
                                ExtUtils::MM_Unix
                                        |
ExtUtils::Liblist::Kid          ExtUtils::MM_{Sistema Operativo Actual} (si es necesario)
      |                                          |
ExtUtils::Liblist     ExtUtils::MakeMaker        |
                |     |                          |   
                |     |   |-----------------------
               ExtUtils::MM
               |          |
    ExtUtils::MY         MM (creado por ExtUtils::MM)
    |                                   |
    MY (creado por ExtUtils::MY)        |
                .                       |
             (mixin)                    |
                .                       |
           PACK### (creado en cada llamada a ExtUtils::MakeMaker->new)

NOTA: Sí, esto es un desastre. Vea http://archive.develooper.com/makemaker@perl.org/msg00134.html para algo de historia.

NOTA: Cuando se carga ExtUtils::MM, elige una superclase para MM de entre los módulos ExtUtils::MM_* basándose en el sistema operativo actual.

NOTA: ExtUtils::MM_{Sistema Operativo Actual} representa uno de los módulos ExtUtils::MM_* excepto ExtUtils::MM_Any, elegido basándose en su sistema operativo.

NOTA: El objeto principal utilizado por MakeMaker es un objeto PACK###, *no* ExtUtils::MakeMaker. Es, efectivamente, una subclase de MY, ExtUtils::MakeMaker, ExtUtils::Liblist y ExtUtils::MM_{Sistema Operativo Actual}

NOTA: Los métodos en MY se copian simplemente en PACK### en lugar de que MY sea una superclase de PACK###. No recuerdo la razón.

NOTA: ExtUtils::Liblist debería eliminarse de la jerarquía de herencia y simplemente llamarse como funciones.

NOTA: Se han omitido módulos como File::Spec y Exporter por claridad.

La jerarquía de MM_*

                               MM_Win95   MM_NW5
                                    \      /
MM_BeOS  MM_Cygwin  MM_OS2  MM_VMS  MM_Win32  MM_DOS  MM_UWIN
      \        |      |         |        /      /      /
       ------------------------------------------------
                          |       |
                       MM_Unix    |
                             |    |

NOTA: Cada subclase directa de MM_Unix también es una subclase de MM_Any. Esto es un truco temporal porque MM_Unix anula algunos métodos de MM_Any con código específico de Unix. Permite que los módulos no Unix vean las implementaciones originales de MM_Any.
