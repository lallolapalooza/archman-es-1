    FORMAT { TEXT | XML | JSON | YAML } DESCRIPCIÓN Este comando muestra el plan de ejecución que el planificador de
    PostgreSQL genera para la sentencia proporcionada. El plan de ejecución
    muestra cómo se escanearán las tablas referenciadas por la sentencia —
    mediante un escaneo secuencial simple, un escaneo de índice, etc. — y, si
    se referencian múltiples tablas, qué algoritmos de unión se usarán para
    reunir las filas requeridas de cada tabla de entrada. La parte más crítica de la visualización es el costo estimado de
    ejecución de la sentencia, que es la suposición del planificador sobre
    cuánto tiempo tomará ejecutar la sentencia (medido en unidades de costo que
    son arbitrarias, pero convencionalmente significan obtenciones de páginas
    de disco). En realidad se muestran dos números: el costo de arranque antes
    de que se pueda devolver la primera fila, y el costo total para devolver
    todas las filas. Para la mayoría de las consultas, lo que importa es el
    costo total, pero en contextos como una subconsulta en EXISTS, el
    planificador elegirá el costo de arranque más pequeño en lugar del costo
    total más pequeño (ya que el ejecutor se detendrá después de obtener una
    fila, de todos modos). Además, si limita el número de filas a devolver con
    una cláusula LIMIT, el planificador hace una interpolación apropiada entre
    los costos de los extremos para estimar qué plan es realmente el más
    barato. La opción ANALYZE hace que la sentencia se ejecute realmente, no
    solo se planifique. Luego, las estadísticas reales de tiempo de ejecución
    se agregan a la visualización, incluyendo el tiempo total transcurrido
    dentro de cada nodo del plan (en milisegundos) y el número total de filas
    que realmente devolvió. Esto es útil para ver si las estimaciones del
    planificador están cerca de la realidad. Importante Tenga en cuenta que la sentencia se ejecuta realmente cuando se
    usa la opción ANALYZE. Aunque EXPLAIN descartará cualquier salida que
    un SELECT devolvería, otros efectos secundarios de la sentencia
    ocurrirán como de costumbre. Si desea usar EXPLAIN ANALYZE en una sentencia INSERT , UPD

SALIDAS

El resultado del comando es una descripción textual del plan seleccionado para la sentencia, opcionalmente anotado con estadísticas de ejecución. La Sección 14.1 describe la información proporcionada.

NOTAS

Para permitir que el planificador de consultas de PostgreSQL tome decisiones razonablemente informadas al optimizar consultas, los datos de pg_statistic deberían estar actualizados para todas las tablas utilizadas en la consulta. Normalmente, el demonio autovacuum se encargará de eso automáticamente. Pero si una tabla ha tenido recientemente cambios sustanciales en su contenido, es posible que necesite hacer un ANALYZE manual en lugar de esperar a que autovacuum ponga al día los cambios.

Para medir el costo de tiempo de ejecución de cada nodo en el plan de ejecución, la implementación actual de EXPLAIN ANALYZE añade sobrecarga de perfilado a la ejecución de la consulta. Como resultado, ejecutar EXPLAIN ANALYZE en una consulta a veces puede tardar significativamente más que ejecutar la consulta normalmente. La cantidad de sobrecarga depende de la naturaleza de la consulta, así como de la plataforma utilizada. El peor caso ocurre para nodos de plan que en sí mismos requieren muy poco tiempo por ejecución, y en máquinas que tienen llamadas al sistema operativo relativamente lentas para obtener la hora del día.

EJEMPLOS

Para mostrar el plan de una consulta simple en una tabla con una sola columna entera y 10000 filas:

EXPLAIN SELECT * FROM foo;
                       PLAN DE CONSULTA
---------------------------------------------------------
 Seq Scan on foo  (cost=0.00..155.00 rows=10000 width=4)
(1 fila)

Aquí está la misma consulta, con formato de salida JSON:

EXPLAIN (FORMAT JSON) SELECT * FROM foo;
           PLAN DE CONSULTA
--------------------------------
 [                             +
   {                           +
     "Plan": {                 +
       "Node Type": "Seq Scan",+
       "Relation Name": "foo", +
       "Alias": "foo",         +
       "Startup Cost": 0.00,   +
       "Total Cost": 155.00,   +
       "Plan Rows": 10000,     +
       "Plan Width": 4         +
     }                         +
   }                           +
 ]
(1 fila)

Si hay un índice y usamos una consulta con una condición WHERE indexable, EXPLAIN podría mostrar un plan diferente:

EXPLAIN SELECT * FROM foo WHERE i = 4;
                         PLAN DE CONSULTA
--------------------------------------------------------------
 Index Scan using fi on foo  (cost=0.00..5.98 rows=1 width=4)
   Index Cond: (i = 4)
(2 filas)

Aquí está la misma consulta, pero en formato YAML:

EXPLAIN (FORMAT YAML) SELECT * FROM foo WHERE i='4';
          PLAN DE CONSULTA
-------------------------------
 - Plan:                      +
     Node Type: "Index Scan"  +
     Scan Direction: "Forward"+
     Index Name: "fi"         +
     Relation Name: "foo"     +
     Alias: "foo"             +
     Startup Cost: 0.00       +
     Total Cost: 5.98         +
     Plan Rows: 1             +
     Plan Width: 4            +
     Index Cond: "(i = 4)"
(1 fila)

El formato XML se deja como ejercicio para el lector.

Aquí está el mismo plan con las estimaciones de costo suprimidas:

EXPLAIN (COSTS FALSE) SELECT * FROM foo WHERE i = 4;
        PLAN DE CONSULTA
----------------------------
 Index Scan using fi on foo
   Index Cond: (i = 4)
(2 filas)

Aquí hay un ejemplo de un plan de consulta para una consulta que usa una función de agregación:

EXPLAIN SELECT sum(i) FROM foo WHERE i < 10;
                             PLAN DE CONSULTA
---------------------------------------------------------------------
 Aggregate  (cost=23.93..23.93 rows=1 width=4)
   ->  Index Scan using fi on foo  (cost=0.00..23.92 rows=6 width=4)
         Index Cond: (i < 10)
(3 filas)

Aquí hay un ejemplo de uso de EXPLAIN EXECUTE para mostrar el plan de ejecución de una consulta preparada:

PREPARE query(int, int) AS SELECT sum(bar) FROM test
    WHERE id > $1 AND id < $2
    GROUP BY foo;
EXPLAIN ANALYZE EXECUTE query(100, 200);
                                                       PLAN DE CONSULTA
-------------------------------------------------------------------------------------------------------------------------
 HashAggregate  (cost=10.77..10.87 rows=10 width=12) (actual time=0.043..0.044 rows=10.00 loops=1)
   Group Key: foo
   Batches: 1  Memory Usage: 24kB
   Buffers: shared hit=4
   ->  Index Scan using test_pkey on test  (cost=0.29..10.27 rows=99 width=8) (actual time=0.009..0.025 rows=99.00 loops=1)
         Index Cond: ((id > 100) AND (id < 200))
         Index Searches: 1
         Buffers: shared hit=4
 Planning Time: 0.244 ms
 Execution Time: 0.073 ms
(10 filas)

Por supuesto, los números específicos mostrados aquí dependen del contenido real de las tablas involucradas. Nótese también que los números, e incluso la estrategia de consulta seleccionada, podrían variar entre versiones de PostgreSQL debido a mejoras en el planificador. Además, el comando ANALYZE usa muestreo aleatorio para estimar estadísticas de datos; por lo tanto, es posible que las estimaciones de costo cambien después de una nueva ejecución de ANALYZE, incluso si la distribución real de datos en la tabla no ha cambiado.

Nótese que el ejemplo anterior mostró un plan “personalizado” para los valores de parámetros específicos dados en EXECUTE. También podríamos desear ver el plan genérico para una consulta parametrizada, lo cual puede hacerse con GENERIC_PLAN:

EXPLAIN (GENERIC_PLAN)
  SELECT sum(bar) FROM test
    WHERE id > $1 AND id < $2
    GROUP BY foo;
                                  PLAN DE CONSULTA
-------------------------------------------------------------------------------
 HashAggregate  (cost=26.79..26.89 rows=10 width=12)
   Group Key: foo
   ->  Index Scan using test_pkey on test  (cost=0.29..24.29 rows=500 width=8)
         Index Cond: ((id > $1) AND (id < $2))
(4 filas)

En este caso, el analizador inferió correctamente que $1 y $2 deberían tener el mismo tipo de datos que id, por lo que la falta de información de tipo de parámetro de PREPARE no fue un problema. En otros casos podría ser necesario especificar explícitamente los tipos para los símbolos de parámetro, lo cual puede hacerse convirtiéndolos, por ejemplo:

EXPLAIN (GENERIC_PLAN)
  SELECT sum(bar) FROM test
    WHERE id > $1::integer AND id < $2::integer
    GROUP BY foo;

COMPATIBILIDAD

No hay ninguna sentencia EXPLAIN definida en el estándar SQL.

La siguiente sintaxis se usaba antes de la versión 9.0 de PostgreSQL y sigue siendo soportada:

EXPLAIN [ ANALYZE ] [ VERBOSE ] sentencia

Nótese que en esta sintaxis, las opciones deben especificarse en exactamente el orden mostrado.
