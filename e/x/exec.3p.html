EXEC(3P) Manual del Programador POSIX EXEC(3P)

PRÓLOGO

Esta página del manual forma parte del Manual del Programador POSIX. La implementación en Linux de esta interfaz puede diferir (consulte la página del manual de Linux correspondiente para detalles del comportamiento en Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

environ, execl, execle, execlp, execv, execve, execvp, fexecve — ejecutar un archivo

SINOPSIS

#include <unistd.h>
extern char **environ;
int execl(const char *path, const char *arg0, ... /*, (char *)0 */);
int execle(const char *path, const char *arg0, ... /*,
    (char *)0, char *const envp[]*/);
int execlp(const char *file, const char *arg0, ... /*, (char *)0 */);
int execv(const char *path, char *const argv[]);
int execve(const char *path, char *const argv[], char *const envp[]);
int execvp(const char *file, char *const argv[]);
int fexecve(int fd, char *const argv[], char *const envp[]);

DESCRIPCIÓN

La familia de funciones exec debe reemplazar la imagen del proceso actual con una nueva imagen de proceso. La nueva imagen debe construirse a partir de un archivo ejecutable regular llamado el archivo de imagen del nuevo proceso. No debe haber retorno de un execexitoso, porque la imagen del proceso que llama es superpuesta por la nueva imagen del proceso.

La función fexecve() debe ser equivalente a la función execve() excepto que el archivo a ejecutar se determina por el descriptor de archivo fd en lugar de por una ruta de acceso. El desplazamiento del archivo de fd se ignora.

Cuando un programa en lenguaje C se ejecuta como resultado de una llamada a una de las funciones de la familia exec , debe ser entrado como una llamada a función en lenguaje C de la siguiente manera:

int main (int argc, char *argv[]);

donde argc es el número de argumentos y argv es un array de punteros a caracteres a los propios argumentos. Además, la siguiente variable, que debe ser declarada por el usuario si se va a usar directamente:

extern char **environ;

se inicializa como un puntero a un array de punteros a caracteres a las cadenas de entorno. Los arrays argv y environ son terminados cada uno por un puntero nulo. El puntero nulo que termina el array argv no se cuenta en argc.

Las aplicaciones pueden cambiar todo el entorno en una sola operación asignando a la variable environ para que apunte a un array de punteros a caracteres a las nuevas cadenas de entorno. Después de asignar un nuevo valor a environ, las aplicaciones no deben confiar en que las nuevas cadenas de entorno permanezcan como parte del entorno, ya que una llamada a getenv(), putenv(), setenv(), unsetenv(), o cualquier función que dependa de una variable de entorno, puede, al notar que environ ha cambiado, copiar las cadenas de entorno a un nuevo array y asignar environ para que apunte a él.

Cualquier aplicación que modifique directamente los punteros a los que apunta la variable environ tiene un comportamiento indefinido.

Las aplicaciones multiproceso conformes no deben usar la variable environ para acceder o modificar ninguna variable de entorno mientras cualquier otro hilo esté modificando concurrentemente alguna variable de entorno. Una llamada a cualquier función que dependa de alguna variable de entorno debe considerarse un uso de la variable environ para acceder a esa variable de entorno.

Los argumentos especificados por un programa con una de las funciones exec deben pasarse a la nueva imagen del proceso en los argumentos correspondientes de main().

El argumento path apunta a una ruta de acceso que identifica al archivo de imagen del nuevo proceso.

El argumento file se usa para construir una ruta de acceso que identifica al archivo de imagen del nuevo proceso. Si el argumento file contiene un carácter <slash>, el argumento file debe usarse como la ruta de acceso para este archivo. De lo contrario, el prefijo de ruta para este archivo se obtiene mediante una búsqueda de los directorios pasados como la variable de entorno PATH (véase el volumen de Definiciones Básicas de POSIX.1‐2017, Capítulo 8, Variables de Entorno). Si esta variable de entorno no está presente, los resultados de la búsqueda son definidos por la implementación.

Hay dos formas distintas en las que el contenido del archivo de imagen del proceso puede hacer que la ejecución falle, distinguidas por la configuración de errno a [ENOEXEC] o [EINVAL] (véase la sección ERRORES). En los casos en los que los otros miembros de la familia de funciones exec fallarían y configurarían errno a [ENOEXEC], las funciones execlp() y execvp() deben ejecutar un intérprete de comandos y el entorno del comando ejecutado debe ser como si el proceso hubiera invocado la utilidad sh usando execl() de la siguiente manera:

execl(<shell path>, arg0, file, arg1, ..., (char *)0);

donde <ruta del shell> es una ruta de acceso no especificada para la utilidad sh , file es el archivo de imagen del proceso, y para execvp(), donde arg0, arg1, y así sucesivamente corresponden a los valores pasados a execvp() en argv[0], argv[1], y así sucesivamente.

Los argumentos representados por arg0,... son punteros a cadenas de caracteres terminadas en nulo. Estas cadenas deben constituir la lista de argumentos disponible para la nueva imagen del proceso. La lista es terminada por un puntero nulo. El argumento arg0 debe apuntar a una cadena de nombre de archivo que esté asociada con el proceso que se inicia por una de las funciones exec .

El argumento argv es un array de punteros a caracteres a cadenas terminadas en nulo. La aplicación debe asegurarse de que el último miembro de este array sea un puntero nulo. Estas cadenas deben constituir la lista de argumentos disponible para la nueva imagen del proceso. El valor en argv[0] debe apuntar a una cadena de nombre de archivo que esté asociada con el proceso que se inicia por una de las funciones exec .

El argumento envp es un array de punteros a caracteres a cadenas terminadas en nulo. Estas cadenas deben constituir el entorno para la nueva imagen del proceso. El array envp es terminado por un puntero nulo.

Para aquellas formas que no contienen un puntero envp (execl(), execv(), execlp(), y execvp()), el entorno para la nueva imagen del proceso debe tomarse de la variable externa environ en el proceso que llama.

El número de bytes disponibles para las listas combinadas de argumentos y entorno del nuevo proceso es {ARG_MAX}. Es definido por la implementación si los terminadores nulo, los punteros y/o cualquier byte de alineación están incluidos en este total.

Los descriptores de archivo abiertos en la imagen del proceso que llama deben permanecer abiertos en la nueva imagen del proceso, excepto aquellos cuyo indicador de cierre alejecutar FD_CLOEXEC esté establecido. Para aquellos descriptores de archivo que permanecen abiertos, todos los atributos de la descripción del archivo abierto permanecen sin cambios. Para cualquier descriptor de archivo que se cierre por esta razón, los bloqueos de archivo se eliminan como resultado del cierre como se describe en close(). Los bloqueos que no se eliminan por el cierre de descriptores de archivo permanecen sin cambios.

Si el descriptor de archivo 0, 1, o 2 se cerraría de otro modo después de una llamada exitosa a una de las funciones de la familia exec , las implementaciones pueden abrir un archivo no especificado para el descriptor de archivo en la nueva imagen del proceso. Si se ejecuta una utilidad estándar o una aplicación conforme con el descriptor de archivo 0 no abierto para lectura o con el descriptor de archivo 1 o 2 no abierto para escritura, el entorno en el que se ejecuta la utilidad o la aplicación debe considerarse no conforme, y en consecuencia la utilidad o la aplicación podría no comportarse como se describe en este estándar.

Los flujos de directorio abiertos en la imagen del proceso que llama deben cerrarse en la nueva imagen del proceso.

El estado del entorno de punto flotante en el hilo inicial de la nueva imagen del proceso debe establecerse al valor predeterminado.

El estado de los descriptores de conversión y los descriptores de catálogo de mensajes en la nueva imagen del proceso es indefinido.

Para la nueva imagen del proceso, lo equivalente a:

setlocale(LC_ALL, "C")

debe ejecutarse en el arranque.

Las señales establecidas a la acción predeterminada (SIG_DFL) en la imagen del proceso que llama deben establecerse a la acción predeterminada en la nueva imagen del proceso. Excepto para SIGCHLD, las señales establecidas para ser ignoradas (SIG_IGN) por la imagen del proceso que llama deben establecerse para ser ignoradas por la nueva imagen del proceso. Las señales establecidas para ser capturadas por la imagen del proceso que llama deben establecerse a la acción predeterminada en la nueva imagen del proceso. (véase <signal.h>).

Si la señal SIGCHLD está configurada para ser ignorada por la imagen de proceso que llama, no se especifica si la señal SIGCHLD se establece para ser ignorada o para la acción predeterminada en la nueva imagen de proceso.

Después de una llamada exitosa a cualquiera de las exec funciones, las pilas de señales alternativas no se conservan y la bandera SA_ONSTACK se borrará para todas las señales.

Después de una llamada exitosa a cualquiera de las exec funciones, cualquier función previamente registrada por las atexit() o pthread_atfork() funciones ya no está registrada.

Si el bit ST_NOSUID está establecido para el sistema de archivos que contiene el archivo de nueva imagen de proceso, entonces el ID de usuario efectivo, el ID de grupo efectivo, el ID de usuario de conjunto guardado y el ID de grupo de conjunto guardado permanecen sin cambios en la nueva imagen de proceso. De lo contrario, si el bit de modo de ID de usuario de conjunto del archivo de nueva imagen de proceso está establecido, el ID de usuario efectivo de la nueva imagen de proceso se establecerá al ID de usuario del archivo de nueva imagen de proceso. De manera similar, si el bit de modo de ID de grupo de conjunto del archivo de nueva imagen de proceso está establecido, el ID de grupo efectivo de la nueva imagen de proceso se establecerá al ID de grupo del archivo de nueva imagen de proceso. El ID de usuario real, el ID de grupo real y los IDs de grupo suplementarios de la nueva imagen de proceso permanecerán iguales a los de la imagen de proceso que llama. El ID de usuario efectivo y el ID de grupo efectivo de la nueva imagen de proceso se guardarán (como el ID de usuario de conjunto guardado y el ID de grupo de conjunto guardado) para su uso por setuid().

Cualquier segmento de memoria compartida adjunto a la imagen de proceso que llama no se adjuntará a la nueva imagen de proceso.

Cualquier semáforo con nombre abierto en el proceso que llama se cerrará como si se realizaran llamadas apropiadas a sem_close().

Cualquier bloque de memoria de tipado que estuviera mapeado en el proceso que llama se desmapeará, como si munmap() se hubiera llamado implícitamente para desmapearlos.

Los bloqueos de memoria establecidos por el proceso que llama mediante llamadas a mlockall() o mlock() se eliminarán. Si las páginas bloqueadas en el espacio de direcciones del proceso que llama también están mapeadas en los espacios de direcciones de otros procesos y están bloqueadas por esos procesos, los bloqueos establecidos por los otros procesos no se verán afectados por la llamada de este proceso a la exec función. Si la exec función falla, el efecto sobre los bloqueos de memoria no está especificado.

Los mapeos de memoria creados en el proceso se desmapean antes de que el espacio de direcciones se reconstruya para la nueva imagen de proceso.

Cuando la imagen de proceso que llama no utiliza las políticas de planificación SCHED_FIFO, SCHED_RR o SCHED_SPORADIC, la política de planificación y los parámetros de la nueva imagen de proceso y del hilo inicial en esa nueva imagen de proceso están definidos por la implementación.

Cuando la imagen de proceso que llama utiliza las políticas de planificación SCHED_FIFO, SCHED_RR o SCHED_SPORADIC, la política del proceso y la configuración de los parámetros de planificación no se cambiarán por una llamada a una exec función. El hilo inicial en la nueva imagen de proceso heredará la política de planificación del proceso y los parámetros. Tendrá el ámbito de contención predeterminado del sistema, pero heredará su dominio de asignación de la imagen de proceso que llama.

Los temporizadores por proceso creados por el proceso que llama se eliminarán antes de reemplazar la imagen de proceso actual con la nueva imagen de proceso.

Todos los descriptores de cola de mensajes abiertos en el proceso que llama se cerrarán, como se describe en mq_close().

Cualquier operación de E/S asíncrona pendiente puede ser cancelada. Aquellas operaciones de E/S asíncrona que no sean canceladas se completarán como si la exec función aún no hubiera ocurrido, pero cualquier notificación de señal asociada será suprimida. No está especificado si la exec función misma se bloquea esperando la finalización de dicha E/S. Sin embargo, en ningún caso, la nueva imagen de proceso creada por la exec función se verá afectada por la presencia de operaciones de E/S asíncrona pendientes en el momento en que la exec función es llamada. Si alguna E/S es cancelada, y cuál E/S puede ser cancelada al exec, está definido por la implementación.

La nueva imagen de proceso heredará el reloj de tiempo de CPU de la imagen de proceso que llama. Esta herencia significa que el reloj de tiempo de CPU del proceso del proceso que está siendo exec-ado no será reinicializado ni alterado como resultado de la exec función que no sea para reflejar el tiempo que el proceso pasó ejecutando la exec función misma.

El valor inicial del reloj de tiempo de CPU del hilo inicial de la nueva imagen de proceso se establecerá en cero.

Si el proceso que llama está siendo rastreado, la nueva imagen de proceso continuará siendo rastreada en el mismo flujo de rastreo que la imagen de proceso original, pero la nueva imagen de proceso no heredará el mapeo de nombres de eventos de rastreo a identificadores de tipo de eventos de rastreo que fue definido por llamadas a las posix_trace_eventid_open() o las posix_trace_trid_eventid_open() funciones en la imagen de proceso que llama.

Si el proceso que llama es un proceso controlador de rastreo, cualquier flujo de rastreo que haya sido creado por el proceso que llama se cerrará como se describe en la posix_trace_shutdown() función.

El ID del hilo del hilo inicial en la nueva imagen de proceso es no especificado.

El tamaño y la ubicación de la pila en la que el hilo inicial en la nueva imagen de proceso se ejecuta no está especificado.

El hilo inicial en la nueva imagen de proceso tendrá su tipo de cancelación establecido a PTHREAD_CANCEL_DEFERRED y su estado de cancelación establecido a PTHREAD_CANCEL_ENABLED.

El hilo inicial en la nueva imagen de proceso tendrá todos los valores de datos específicos de hilo establecidos a NULL y todas las claves de datos específicos de hilo serán eliminadas por la llamada a exec sin ejecutar destructores.

El hilo inicial en la nueva imagen de proceso será unible, como si se hubiera creado con el detachstate atributo establecido a PTHREAD_CREATE_JOINABLE.

Todos los demás atributos de proceso definidos en este volumen de POSIX.1‐2017 se heredarán en la nueva imagen de proceso desde la antigua imagen de proceso. Todos los demás atributos de hilo definidos en este volumen de POSIX.1‐2017 se heredarán en el hilo inicial en la nueva imagen de proceso desde el hilo que llama en la antigua imagen de proceso. La herencia de atributos de proceso o de hilo no definidos por este volumen de POSIX.1‐2017 está definida por la implementación.

Una llamada a cualquier exec función desde un proceso con más de un hilo resultará en que todos los hilos sean terminados y la nueva imagen ejecutable sea cargada y ejecutada. No se llamará a ninguna función destructora ni a ningún manejador de limpieza.

Tras la finalización exitosa, las exec funciones marcarán para su actualización la última marca de tiempo de acceso a datos del archivo. Si una exec función falló pero pudo localizar el archivo de imagen de proceso, si la última marca de tiempo de acceso a datos se marca para su actualización no está especificado. Si la exec función tiene éxito, el archivo de imagen de proceso se considerará que ha sido abierto con open(). El close() correspondiente se considerará que ocurre en un tiempo después de esta apertura, pero antes de la terminación del proceso o la finalización exitosa de una llamada posterior a una de las exec funciones, posix_spawn(), o posix_spawnp(). Los argv[] y envp[] arreglos de punteros y las cadenas a las que esos arreglos apuntan no serán modificados por una llamada a una de las exec funciones, excepto como consecuencia del reemplazo de la imagen de proceso.

Los límites de recursos guardados en la nueva imagen de proceso se establecen para ser una copia de los límites duros y blandos correspondientes del proceso.

VALOR DE RETORNO

Si una de las exec funciones retorna a la imagen de proceso que llama, ha ocurrido un error; el valor de retorno será -1, y errno se establecerá para indicar el error.

ERRORES

Las exec funciones fallarán si:

E2BIG
El número de bytes usados por la lista de argumentos y la lista de entorno de la nueva imagen de proceso es mayor que el límite impuesto por el sistema de {ARG_MAX} bytes.
EACCES
El archivo de nueva imagen de proceso no es un archivo regular y la implementación no soporta la ejecución de archivos de su tipo.
EINVAL
El archivo de nueva imagen de proceso tiene privilegios apropiados y tiene un formato de binario ejecutable reconocido, pero el sistema no soporta la ejecución de un archivo con este formato.

Las exec funciones, excepto fexecve(), fallarán si:

EACCES
Se deniega el permiso de búsqueda para un directorio listado en el prefijo de ruta del archivo de nueva imagen de proceso, o el archivo de nueva imagen de proceso deniega el permiso de ejecución.
ELOOP
Existe un bucle en enlaces simbólicos encontrados durante la resolución del path o file argumento.
ENAMETOOLONG

La longitud de un componente de una ruta de acceso es mayor que {NAME_MAX}.
ENOENT
Un componente de path o file nonombre de un archivo existente o ruta o archivo es una cadena vacía.
ENOTDIR
Un componente del prefijo de ruta del archivo de imagen del nuevo proceso nombra un archivo existente que no es un directorio ni un enlace simbólico a un directorio, o la ruta de nombre de archivo del archivo de imagen del nuevo proceso contiene al menos un carácter que no sea <barra invertida> y termina con uno o más caracteres de barra invertida finales, y el componente de nombre de archivo final nombra un archivo existente que no es un directorio ni un enlace simbólico a un directorio.

Las funciones exec , excepto execlp() y execvp(), fallarán si:

ENOEXEC
El archivo de imagen del nuevo proceso tiene el permiso de acceso apropiado pero tiene un formato no reconocido.

La función fexecve() fallará si:

EBADF
El argumento fd no es un descriptor de archivo válido abierto para ejecución.

Las funciones exec pueden fallar si:

ENOMEM
La nueva imagen de proceso requiere más memoria de la permitida por las restricciones de gestión de memoria impuestas por el hardware o el sistema.

Las funciones exec , excepto fexecve(), pueden fallar si:

ELOOP
Se encontraron más de {SYMLOOP_MAX} enlaces simbólicos durante la resolución del argumento ruta o argumento archivo .
ENAMETOOLONG

La longitud del argumento ruta o la longitud de la ruta de nombre de archivo construida a partir del argumento archivo excede {PATH_MAX}, o la resolución de la ruta de nombre de archivo de un enlace simbólico produjo un resultado intermedio con una longitud que excede {PATH_MAX}.
ETXTBSY
El archivo de imagen del nuevo proceso es un archivo de procedimiento puro (texto compartido) que está actualmente abierto para escritura por algún proceso.

Las siguientes secciones son informativas.

EJEMPLOS

Uso de execl()

El siguiente ejemplo ejecuta el comando ls , especificando la ruta de nombre de archivo del ejecutable (/bin/ls) y usando argumentos proporcionados directamente al comando para producir una salida de una sola columna.

#include <unistd.h>
int ret;
...
ret = execl ("/bin/ls", "ls", "-1", (char *)0);

Uso de execle()

El siguiente ejemplo es similar a Uso de execl(). Además, especifica el entorno para la nueva imagen de proceso usando el argumento env .

#include <unistd.h>
int ret;
char *env[] = { "HOME=/usr/home", "LOGNAME=home", (char *)0 };
...
ret = execle ("/bin/ls", "ls", "-l", (char *)0, env);

Uso de execlp()

El siguiente ejemplo busca la ubicación del comando ls entre los directorios especificados por la variable de entorno PATH .

#include <unistd.h>
int ret;
...
ret = execlp ("ls", "ls", "-l", (char *)0);

Uso de execv()

El siguiente ejemplo pasa argumentos al comando ls en el array cmd .

#include <unistd.h>
int ret;
char *cmd[] = { "ls", "-l", (char *)0 };
...
ret = execv ("/bin/ls", cmd);

Uso de execve()

El siguiente ejemplo pasa argumentos al comando ls en el array cmd , y especifica el entorno para la nueva imagen de proceso usando el argumento env .

#include <unistd.h>
int ret;
char *cmd[] = { "ls", "-l", (char *)0 };
char *env[] = { "HOME=/usr/home", "LOGNAME=home", (char *)0 };
...
ret = execve ("/bin/ls", cmd, env);

Uso de execvp()

El siguiente ejemplo busca la ubicación del comando ls entre los directorios especificados por la variable de entorno PATH , y pasa argumentos al comando ls en el array cmd .

#include <unistd.h>
int ret;
char *cmd[] = { "ls", "-l", (char *)0 };
...
ret = execvp ("ls", cmd);

USO EN APLICACIONES

Dado que el estado de los descriptores de conversión y los descriptores de catálogos de mensajes en la nueva imagen de proceso es indefinido, las aplicaciones conformes no deberían depender de su uso y deberían cerrarlos antes de llamar a una de las funciones exec .

Las aplicaciones que requieran una configuración regional POSIX distinta de la predeterminada como la configuración regional global en la nueva imagen de proceso deberían llamar a setlocale() con los parámetros apropiados.

Al asignar un nuevo valor a la variable environ , las aplicaciones deberían asegurarse de que el entorno al que apuntará contenga al menos lo siguiente:

1.
Cualquier variable definida por la implementación requerida por la implementación para proporcionar un entorno conforme. Véase la entrada _CS_V7_ENV en <unistd.h> y confstr() para más detalles.
2.
Un valor para PATH que encuentre versiones conformes de todas las utilidades estándar antes que cualquier otra versión.

La misma restricción se aplica al array envp pasado a execle() o execve(), para asegurar que la nueva imagen de proceso se invoque en un entorno conforme.

Las aplicaciones no deberían ejecutar programas con el descriptor de archivo 0 no abierto para lectura o con el descriptor de archivo 1 o 2 no abierto para escritura, ya que esto podría hacer que el programa ejecutado se comporte de manera incorrecta. Para no pasar estos descriptores de archivo a un programa ejecutado, las aplicaciones no deberían simplemente cerrarlos, sino volver a abrirlos en, por ejemplo, /dev/null. Algunas implementaciones pueden volver a abrirlos automáticamente, pero las aplicaciones no deberían depender de que esto se haga.

Si una aplicación desea realizar una prueba de suma de verificación del archivo que se está ejecutando antes de ejecutarlo, el archivo deberá abrirse con permiso de lectura para realizar la prueba de suma de verificación.

Dado que el permiso de ejecución es verificado por fexecve(), la descripción de archivo fd no necesariamente debe haberse abierto con la bandera O_EXEC. Sin embargo, si el archivo a ejecutar deniega el permiso de lectura y escritura para el proceso que se prepara para hacer el exec, la única manera de proporcionar el fd a fexecve() será usar la bandera O_EXEC al abrir el fd. En este caso, la aplicación no podrá realizar una prueba de suma de verificación ya que no podrá leer el contenido del archivo.

NAME

execve - execute a file (LEGACY, REFER TO execve())

SYNOPSIS

#include <unistd.h>

int execve(const char *path, char *const argv[], char *const envp[]);

DESCRIPTION

The execve() function shall replace the current process image with a new process image that is the interpreter program named by path. The new process image is constructed from a regular file that is currently executable and owned by the user ID specified in the effective user ID of the calling process.

The arguments shall be interpreted as follows:

path
The pathname of the file to be executed. The application shall ensure that the path is a valid pathname.
argv
A null-terminated array of character pointers to the values that will be the new process's argument list. By convention, the first element of this array points to a string that is the name of the file associated with the process image being executed. The value of argv[0] should be the name of the command being invoked. If argv is a null pointer, the list of arguments shall be considered to be empty, and the environment passed to the new process image shall be the same as the environment of the calling process.
envp
A null-terminated array of character pointers to strings that will form the new process's environment. Each string is of the form "name=value". If envp is a null pointer, the environment passed to the new process image shall be the same as the environment of the calling process. For a description of the environment list, see execle().

The execve() function shall not return on success. On failure, it shall return the value -1 and set the global variable errno to indicate the error.

The argument list and environment provided by execve() are not the same as those provided by execv(). The execve() function is intended to be used to execute binary files, whereas execv() is intended to be used to execute shell scripts. The execve() function is also intended to be used to execute files that are not shell scripts.

If the file specified by path is a text file that starts with the characters #!, the remainder of the first line of the file is interpreted as the arguments for an interpreter. A new process is created by calling the interpreter with the text file as its first argument and the arguments specified by argv as subsequent arguments. The interpreter shall be the file specified by the interpreter directive.

The interpreter directive is processed as follows: The first token on the line is the name of the interpreter file. The remaining tokens on the line are passed as arguments to the interpreter. The first argument to the interpreter is the name of the file being executed (the file specified by path). The subsequent arguments to the interpreter are the arguments specified by argv.

If the file specified by path does not start with #!, it is assumed to be an executable binary file. In this case, the file is executed directly. The arguments specified by argv are passed to the new process.

If the file specified by path does not start with #!, and the file is not an executable binary file, then the execve() function shall return an error. This includes the case where the file is a script that starts with a #! directive but does not contain a valid interpreter path.

The execve() function shall create a new process image. The new process image is created by the calling process. The new process image has the same process ID as the calling process. The calling process's text, data, BSS, and stack segments are replaced by those of the new process image.

The signal-handling settings of the calling process are preserved in the new process image. The set of pending signals for the calling process is cleared in the new process image.

All open file descriptors of the calling process remain open in the new process image. For each file descriptor, the close-on-exec flag is examined. If set, the file descriptor is closed in the new process image. Otherwise, it remains open.
