DESCRIPCIÓ

N

Exim es un agente de transferencia de correo (MTA) desarrollado en la Universidad de Cambridge. Es un programa grande con muy muchas funcionalidades. Para una especificación completa, consulte el manual de referencia. Esta página del manual contiene solo una descripción de las opciones de la línea de comandos. Ha sido generada automáticamente a partir del código fuente del manual de referencia, esperamos que sin demasiadas

alteraciones.

Como otros MTAs, Exim reemplaza a Sendmail, y normalmente es llamado por agentes de usuario (MUAs) utilizando la ruta /usr/sbin/sendmail cuando envían mensajes para su entrega (algunos sistemas operativos usan /usr/lib/sendmail). Esta ruta normalmente se configura como un enlace simbólico al binario de Exim. También puede ser usada por scripts de arranque para ini

ciar el demonio de Exim. Muchas de las opciones de la línea de comandos de Exim
son compatibles con Sendmail para que pueda actuar como un reemplazo directo.

-C <lista_archivos>
Esta opción hace que Exim encuentre el archivo de configuración en tiempo de ejecución a partir de la lista dada en lugar de la lista especificada por la configuración en tiempo de compilación CONFIGURE_FILE. Normalmente, la lista consistirá en un único nombre de archivo, pero puede ser una lista de nombres separados por dos puntos. En este caso, se utiliza el primer archivo que exista. El fallo al abrir un archivo existente detiene Exim y se genera un error.

Cuando esta opción es utilizada por un llamador que no sea root, y la lista es diferente de la lista compilada, Exim renuncia a sus privilegios de root inmediatamente, y se ejecuta con el uid y gid real y efectivo establecidos a los del llamador. Sin embargo, si se define un archivo TRUSTED_CONFIG_LIST en Local/Makefile, ese archivo contiene una lista de rutas completas, una por línea, para archivos de configuración que son de confianza. Los privilegios de root se conservan para cualquier archivo de configuración que se liste, siempre que el llamador sea el usuario de Exim (o el usuario especificado en la opción CONFIGURE_OWNER, si lo hay), y siempre que el archivo de configuración no sea escribible por usuarios o grupos inapropiados.

Dejar TRUSTED_CONFIG_LIST sin definir impide la posibilidad de probar una configuración utilizando -C hasta la recepción y entrega del mensaje, incluso si el llamador es root. La recepción funciona, pero en ese momento, Exim se ejecuta como el usuario de Exim, por lo que cuando se vuelve a ejecutar para recuperar privilegios para la entrega, el uso de -C provoca la pérdida de privilegios. Sin embargo, root puede probar la recepción y la entrega utilizando dos comandos separados (uno para poner un mensaje en la cola, usando -odq, y otro para hacer la entrega, usando -M).

Si ALT_CONFIG_PREFIX está definido en Local/Makefile, especifica una cadena de prefijo con la que debe comenzar cualquier archivo nombrado en una opción de línea de comandos -C. Además, el nombre del archivo no debe contener la secuencia /../. Sin embargo, si el valor de la opción -C es idéntico al valor de CONFIGURE_FILE en Local/Makefile, Exim ignora -C y procede como de costumbre. No hay una configuración predeterminada para ALT_CONFIG_PREFIX; cuando no está definida, se puede usar cualquier nombre de archivo con -C.

ALT_CONFIG_PREFIX se puede utilizar para confinar archivos de configuración alternativos a un directorio al que solo root tenga acceso. Esto evita que alguien que haya irrumpido en la cuenta de Exim ejecute un Exim privilegiado con un archivo de configuración arbitrario.

La utilidad -C es útil para garantizar que los archivos de configuración sean sintácticamente correctos, pero no se puede utilizar para entregas de prueba, a menos que el llamador tenga privilegios, o a menos que se trate de una configuración exótica que no requiera privilegios. No se realiza ninguna comprobación sobre el propietario o grupo de los archivos especificados por esta opción.

-D<macro>=<valor>
Esta opción se puede utilizar para anular las definiciones de macros en el archivo de configuración. Sin embargo, al igual que -C, si la utiliza un llamador sin privilegios, hace que Exim renuncie a sus privilegios de root. Si se define DISABLE_D_OPTION en Local/Makefile, el uso de -D se deshabilita completamente, y su uso provoca una salida de error inmediata.

Si WHITELIST_D_MACROS está definido en Local/Makefile, entonces debe ser una lista de macros separadas por dos puntos que se consideren seguras y, si -D solo proporciona macros de esta lista, y los valores son aceptables, entonces Exim no renunciará a los privilegios de root si el llamador es root, el usuario de tiempo de ejecución de Exim, o el CONFIGURE_OWNER, si está establecido. -q
Esta opción normalmente está restringida a usuarios administradores. Sin embargo, hay una opción de configuración llamada prod_requires_admin que se puede establecer en falso para relajar esta restricción (y también el mismo requisito para las opciones -M, -R y -S).

Si otras opciones de línea de comandos no especifican una acción, la opción -q inicia un proceso de ejecución de colas. Este escanea la cola de mensajes en espera y ejecuta un proceso de entrega para cada uno de ellos por turno. Espera a que cada proceso de entrega termine antes de iniciar el siguiente. Un proceso de entrega puede que no realice ninguna entrega si aún no se han alcanzado los tiempos de reintento para las direcciones. Utilice -qf (ver más abajo) si desea anular esto.

Si el proceso de entrega genera otros procesos para entregar otros mensajes a través de conexiones SMTP pasadas, el ejecutor de colas espera a que estos terminen antes de continuar.

Cuando se han considerado todos los mensajes en cola, el proceso original de ejecución de colas termina. En otras palabras, se realiza un solo paso por el correo en espera, un mensaje a la vez. Utilice -q con un tiempo (ver más abajo) si desea que esto se repita periódicamente.

Exim procesa los mensajes en espera en un orden impredecible. No es muy aleatorio, pero es probable que sea diferente cada vez, que es todo lo que importa. Si un mensaje en particular causa problemas a un MTA remoto, otros mensajes al mismo MTA tienen la oportunidad de pasar si se intentan primero.

Es posible hacer que los mensajes se procesen en orden de ID de mensaje léxico, que es esencialmente el orden en que llegaron, estableciendo la opción queue_run_in_order, pero esto no se recomienda para uso normal.

-q<qflags>
Realiza una ejecución de cola. La opción -q puede ir seguida de una o más letras de bandera que cambian su comportamiento. Todas son opcionales, pero si hay más de una presente, deben aparecer en el orden correcto. Cada bandera se describe en un elemento separado más abajo.
-qq...
Una opción que comienza con -qq solicita una ejecución de cola en dos etapas. En la primera etapa, la cola se escanea como si la opción queue_smtp_domains coincidiera con todos los dominios. Se enrutan las direcciones, se realizan las entregas locales, pero no se ejecutan los transportes remotos.

El rendimiento será óptimo si la opción queue_run_in_order es falsa. Si es así y la opción queue_fast_ramp es verdadera y hay disponible un socket de notificación de demonio, entonces en la primera fase de la ejecución, una vez que un número umbral de mensajes se enruta para un dominio determinado, se crea un proceso de entrega en paralelo con el resto del escaneo.

Se actualiza la base de datos de pistas que recuerda qué mensajes están esperando a dominios específicos, como si la entrega a esos dominios se hubiera aplazado.

Una vez completado el primer escaneo de cola, se realiza un segundo escaneo de cola normal, con enrutamiento y entrega realizados normalmente. Los mensajes que se enrutan al mismo dominio deberían entregarse en su mayoría a través de una sola conexión SMTP debido a las pistas que se establecieron durante el primer escaneo de cola.

Las ejecuciones de cola en dos fases deben usarse en sistemas que, incluso de forma intermitente, tienen una cola grande (como los operadores de listas de correo). También pueden ser útiles para dominios que se conectan a Internet de forma intermitente.

-q[q]i...
Si está presente la bandera *i*, el ejecutor de colas solo ejecuta procesos de entrega para aquellos mensajes que no se han intentado previamente. (*i* significa "entrega inicial"). Esto puede ser útil si está colocando mensajes en la cola usando -odq y desea que un ejecutor de colas solo procese los mensajes nuevos.
-q[q][i]f...
Si está presente una bandera *f*, se fuerza un intento de entrega para cada mensaje no congelado, mientras que sin *f* solo se intentan aquellas direcciones no congeladas que han pasado sus tiempos de reintento.
-q[q][i]ff...
Si está presente *ff*, se fuerza un intento de entrega para cada mensaje, ya esté congelado o no.
-q[q][i][f[f]]l
La bandera *l* (la letra "ele") especifica que solo se deben realizar entregas locales. Si un mensaje requiere alguna entrega remota, permanece en la cola para su entrega posterior.
-q[q][i][f[f]][l][G<name>[/<time>]]]
Si está presente la bandera *G* y un nombre, el ejecutor de colas opera en la cola con el nombre dado en lugar de la cola predeterminada. El nombre no debe contener un carácter */*. Para una ejecución de cola periódica (ver más abajo), añada al nombre una barra inclinada y un valor de tiempo.

Si otras opciones de línea de comandos especifican una acción, una opción *-qG<name>* especificará una cola sobre la que operar. Por ejemplo:


exim -bp -qGquarantine
mailq -qGquarantine
exim -qGoffpeak -Rf @special.domain.example

-q<qflags> <id de inicio> <id de fin>
Al escanear la cola, se puede hacer que Exim omita los mensajes cuyos IDs sean léxicamente menores que un valor dado, siguiendo la opción -q con un ID de mensaje de inicio. Por ejemplo:


exim -q 0t5C6f-0000c8-00

Los mensajes que llegaron antes de 0t5C6f-0000c8-00 no se inspeccionan. Si se proporciona un segundo ID de mensaje, también se omiten los mensajes cuyos IDs sean léxicamente mayores que él. Si se proporciona el mismo ID dos veces, por ejemplo,


exim -q 0t5C6f-0000c8-00 0t5C6f-0000c8-00

solo se inicia un proceso de entrega para ese mensaje. Esto difiere de -M en que se respetan los datos de reintento, y también difiere de -Mc en que cuenta como una entrega de una ejecución de cola. Tenga en cuenta que el mecanismo de selección no afecta el orden en que se escanean los mensajes. También hay otras formas de seleccionar conjuntos específicos de mensajes para su entrega en una ejecución de cola; consulte -R y -S.

-q<qflags><tiempo>
Cuando está presente un valor de tiempo, la opción -q hace que Exim se ejecute como un demonio, iniciando un proceso de ejecución de colas a intervalos especificados por el valor de tiempo dado. Esta forma de la opción -q se combina comúnmente con la opción -bd, en cuyo caso un único proceso demonio maneja ambas funciones. Una forma común de iniciar un demonio combinado al arrancar el sistema es usar un comando como


/usr/exim/bin/exim -bd -q30m

Dicho demonio escucha las llamadas SMTP entrantes y también inicia un proceso de ejecución de colas cada 30 minutos.

Es posible configurar ejecutores para múltiples colas con nombre dentro de un solo demonio. Por ejemplo:


exim -qGhipri/2m -q10m -qqGmailinglist/1h

Cuando un demonio es iniciado por -q con un valor de tiempo, pero sin -bd, no se escribe ningún archivo pid a menos que se solicite explícitamente mediante la opción -oP.

Once a message is selected for delivery by this mechanism, all its addresses are processed. For the first selected message, Exim overrides any retry information and forces a delivery attempt for each undelivered address. This means that if delivery of any address in the first message is successful, any existing retry information is deleted, and so delivery attempts for that address in subsequently selected messages (which are processed without forcing) will run. However, if delivery of any address does not succeed, the retry information is updated, and in subsequently selected messages, the failing address will be

skipped.

If the <rsflags> contain f or ff, the delivery forcing applies to all selected messages, not just the first; frozen messages are included when ff is

present.

t
When Exim is receiving a locally-generated, non-SMTP message on its standard input, the -t option causes the recipients of the message to be obtained from the To:, Cc:, and Bcc: header lines in the message instead of from the command arguments. The addresses are extracted before any rewriting takes place and the Bcc: header line, if present, is then removed.

If the command has any arguments, they specify addresses to which the message is not to be delivered. That is, the argument addresses are removed from the recipients list obtained from the headers. This is compatible with Smail 3 and in accordance with the documented behaviour of several versions of Sendmail, as described in man pages on a number of operating systems (e.g. Solaris 8, IRIX 6.5, HP-UX 11). However, some versions of Sendmail add argument addresses to those obtained from the headers, and the O'Reilly Sendmail book documents it that way. Exim can be made to add argument addresses instead of subtracting them by setting the option extract_addresses_remove_ar

guments false.

If there are any Resent- header lines in the message, Exim extracts recipients from all Resent-To:, Resent-Cc:, and Resent-Bcc: header lines instead of from To:, Cc:, and Bcc:. This is for compatibility with Sendmail and other MTAs. (Prior to release 4.20, Exim gave an error if -t was used in conjunction with Resent- header

lines.)

RFC 2822 [https://www.rfc-editor.org/rfc/rfc2822] talks about different sets of Resent- header lines (for when a message is resent several times). The RFC also specifies that they should be added at the front of the message, and separated by Received: lines. It is not at all clear how -t should operate in the present of multiple sets, nor indeed exactly what constitutes a "set". In practice, it seems that MUAs do not follow the RFC. The Resent- lines are often added at the end of the header, and if a message is resent more than once, it is common for the original set of Resent- headers to be renamed as X-Resent- when a new set is adde

d. This removes any
possible ambiguity.
