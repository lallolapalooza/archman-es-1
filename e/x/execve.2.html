DESCRIPCIÓ

N

execve() ejecuta el programa al que hace referencia path. Esto hace que el programa que está siendo ejecutado actualmente por el proceso llamador sea reemplazado por un nuevo programa, con una pila, un montón y segmentos de datos (inicializados y no inicializados) recién

inicializados.

path debe ser un ejecutable binario, o un script que comience con una línea de la

forma:


ete nal
#!intérpr 
[argumento-o
pcio
]

Para más detalles sobre el último caso, véase "Scripts de intérprete" más

abajo.

argv es un array de punteros a cadenas que se pasan al nuevo programa como sus argumentos de línea de comandos. Por convención, la primera de estas cadenas (es decir, argv[0]) debe contener el nombre de archivo asociado con el archivo que se está ejecutando. El array argv debe ser terminado por un puntero nulo. (Por lo tanto, en el nuevo programa, argv[argc] será un puntero nulo.

)

envp es un array de punteros a cadenas, convencionalmente de la forma clave=valor, que se pasan como el entorno del nuevo programa. El array envp debe ser terminado por un puntero

nulo.

Esta página de manual describe la llamada al sistema de Linux en detalle; para una visión general de la nomenclatura y las muchas, a menudo preferibles, variantes estandarizadas de esta función proporcionadas por libc, incluyendo aquellas que buscan la variable de entorno PATH, véase exec(

3).

El vector de argumentos y el entorno pueden ser accedidos por la función principal del nuevo programa, cuando se define

como: 


int main(int argc, char *argv[], char *envp[]
)

Nótese, sin embargo, que el uso de un tercer argumento en la función principal no está especificado en POSIX.1; de acuerdo con POSIX.1, el entorno debe ser accedido a través de la variable externa environ

(7).

execve() no retorna en caso de éxito, y el texto, los datos inicializados, los datos no inicializados (bss) y la pila del proceso llamador son sobrescritos de acuerdo con el contenido del programa recién

cargado.

Si el programa actual está siendo rastreado con ptrace, una señal SIGTRAP es enviada a él después de un execve() e

xitoso.

Si el bit set-user-ID está establecido en el archivo del programa al que hace referencia path, entonces el ID de usuario efectivo del proceso llamador es cambiado al del propietario del archivo del programa. De manera similar, si el bit set-group-ID está establecido en el archivo del programa, entonces el ID de grupo efectivo del proceso llamador es establecido al grupo del archivo del

programa.

Las transformaciones mencionadas anteriormente de los IDs efectivos no se realizan (es decir, los bits set-user-ID y set-group-ID son ignorados) si alguna de las siguientes condiciones es

verdadera:
•
el atributo no_new_privs está establecido para el hilo llamador (véase prctl(2
));
•
el sistema de archivos subyacente está montado con nosuid (el indicador MS_NOSUID para mount(2));
o
•
el proceso llamado
r está siendo ras
treado con ptrace.

Las capacidades del archivo del programa (véase capabilities(7)) también son ignoradas si alguna de las condiciones anteriores es

verdadera.

El ID de usuario efectivo del proceso es copiado al ID de usuario set-user-ID guardado; de manera similar, el ID de grupo efectivo es copiado al ID de grupo set-group-ID guardado. Esta copia tiene lugar después de cualquier cambio de ID efectivo que ocurra debido a los bits de modo set-user-ID y

set-group-ID.

El UID real y el GID real del proceso, así como sus IDs de grupo suplementarios, no son cambiados por una llamada a execve

().

Si el ejecutable es un ejecutable binario a.out vinculado dinámicamente que contiene stubs de biblioteca compartida, el enlazador dinámico de Linux ld.so(8) es llamado al inicio de la ejecución para traer los objetos compartidos necesarios a la memoria y enlazar el ejecutable con

ellos.

Si el ejecutable es un ejecutable ELF vinculado dinámicamente, el intérprete nombrado en el segmento PT_INTERP es usado para cargar los objetos compartidos necesarios. Este intérprete es típicamente /lib/ld-linux.so.2 para binarios enlazados con glibc (véase ld-linux.so(8))

Cualquier pila de señales alternativa no se preserva (sigaltstack

•
Los mapeos de memoria no se preservan (mmap(2

•
Los segmentos de memoria compartida de System V adjuntos son desprendidos (shmat(2

•
Las regiones de memoria compartida POSIX son desmapeadas (shm_open(
3)).
•
Los descriptores de cola de mensajes POSIX abiertos son cerrados (mq_overview

•
Cualquier semáforo con nombre POSIX abierto es cerrado (sem_overvie

•
Los temporizadores POSIX no se preservan (timer_creat

•
Cualquier flujo de directorio abierto es cerrado (opendir(

•
Los bloqueos de memoria no se preservan (mlock(2), mlockall(

•
Los manejadores de salida no se preservan (atexit(3), on_exit(

•
El entorno de coma flotante es restablecido al predeterminado (véase fenv

Los atributos del proceso en la lista anterior están todos especificados en POSIX.1. Los siguientes atributos del proceso específicos de Linux también se preservan durante un execve

():
•
El atributo "dumpable" del proceso es establecido al valor 1, a menos que se esté ejecutando un programa set-user-ID, un programa set-group-ID, o un programa con capacidades, en cuyo caso el indicador dumpable puede ser restablecido en su lugar al valor en /proc/sys/fs/suid_dumpable, en las circunstancias descritas bajo PR_SET_DUMPABLE en prctl(2). Nótese que los cambios al atributo "dumpable" pueden causar que la propiedad de los archivos en el directorio /proc/pid del proceso cambie a root:root, como se describe en proc(

•
El prctl(2) indicador PR_SET_KEEPCAPS es
borrado.
•
(Desde Linux 2.4.36 / 2.6.23) Si se está ejecutando un programa set-user-ID o set-group-ID, entonces la señal de muerte del padre establecida por prctl(2) el indicador PR_SET_PDEATHSIG es
borrada.
•
El nombre del proceso, establecido por prctl(2) PR_SET_NAME (y mostrado por ps -o comm), es restablecido al nombre del nuevo archivo

•

Nótese los siguientes puntos

adicionales:
•
Todos los hilos distintos del hilo que llama son destruidos durante un execve(). Los mutexes, las variables de condición y otros objetos de pthreads no se

•

POSIX.1 especifica que las disposiciones de cualquier señal que se ignore o se establezca por defecto se dejan sin cambios. POSIX.1 especifica una excepción: si SIGCHLD se está ignorando, entonces una implementación puede dejar la disposición sin cambios o restablecerla a la predeterminada; Linux hace lo

•
Se cancelan todas las operaciones de E/S asíncrona pendientes (aio_read(3), aio_write

•
Para el manejo de capacidades durante execve(), véase capabilitie

Por defecto, los descriptores de archivo permanecen abiertos a través de un execve(). Los descriptores de archivo marcados como close-on-exec se cierran; véase la descripción de FD_CLOEXEC en fcntl(2). (Si se cierra un descriptor de archivo, esto provocará la liberación de todos los bloqueos de registro obtenidos sobre el archivo subyacente por este proceso. Véase fcntl(2) para más detalles.) POSIX.1 dice que si los descriptores de archivo 0, 1 y 2 se cerrarían de otro modo después de un exitoso execve(), y el proceso obtendría privilegios porque el bit de modo set-user-ID o set-group-ID estaba establecido en el archivo ejecutado, entonces el sistema puede abrir un archivo no especificado para cada uno de estos descriptores de archivo. Como principio general, ningún programa portátil, ya sea privilegiado o no, puede asumir que estos tres descriptores de archivo permanecerán cerrados a través de un exec

Límites en el tamaño de los argumentos y el

entorno

La mayoría de las implementaciones de UNIX imponen algún límite al tamaño total de las cadenas de argumentos de la línea de comandos (argv) y del entorno (envp) que pueden pasarse a un nuevo programa. POSIX.1 permite que una implementación anuncie este límite usando la constante ARG_MAX (ya sea definida en <limits.h> o disponible en tiempo de ejecución usando la llamada sysconf(_SC_ARG_MAX))

.

Antes de Linux 2.6.23, la memoria utilizada para almacenar las cadenas de entorno y argumentos estaba limitada a 32 páginas (definidas por la constante del núcleo MAX_ARG_PAGES). En arquitecturas con un tamaño de página de 4 kB, esto produce un tamaño máximo de 128

kB.

En Linux 2.6.23 y posteriores, la mayoría de las arquitecturas admiten un límite de tamaño derivado del límite de recursos blando RLIMIT_STACK (véase getrlimit(2)) que está en vigor en el momento de la llamada a execve(). (Las arquitecturas sin unidad de gestión de memoria están exceptuadas: mantienen el límite que estaba en efecto antes de Linux 2.6.23.) Este cambio permite que los programas tengan una lista de argumentos y/o entorno mucho más grande. Para estas arquitecturas, el tamaño total está limitado a 1/4 del tamaño de pila permitido. (Imponer el límite de 1/4 asegura que el nuevo programa siempre tenga algo de espacio de pila.) Además, el tamaño total está limitado a 3/4 del valor de la constante del núcleo _STK_LIM (8 MiB). Desde Linux 2.6.25, el núcleo también establece un mínimo de 32 páginas para este límite de tamaño, de modo que, incluso cuando RLIMIT_STACK se establezca muy bajo, se garantiza que las aplicaciones tengan al menos tanto espacio para argumentos y entorno como el que proporcionaba Linux 2.6.22 y anteriores. (Esta garantía no se proporcionó en Linux 2.6.23 y 2.6.24.) Además, el límite por cadena es de 32 páginas (la constante del núcleo MAX_ARG_STRLEN), y el nú

En Linux, argv y envp pueden especificarse como NULL. En ambos casos, esto tiene el mismo efecto que especificar el argumento como un puntero a una lista que contiene un único puntero nulo. ¡No aproveche esta característica defectuosa no estándar y no portable!
