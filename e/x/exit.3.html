exit(3) Manual de Funciones de Biblioteca exit(3)

NOMBRE

exit - provoca la terminación normal del proceso

BIBLIOTECA

Biblioteca C Estándar (libc,-lc)

SINOPSIS

#include <stdlib.h>
[[noreturn]] void exit(int status);

DESCRIPCIÓN

La función exit() provoca la terminación normal del proceso y el byte menos significativo de status (es decir, status & 0xFF) se devuelve al proceso padre (véase wait(2)).

Se llaman a todas las funciones registradas con atexit(3) y on_exit(3) en el orden inverso a su registro. (Es posible que una de estas funciones use atexit(3) o on_exit(3) para registrar una función adicional que se ejecutará durante el procesamiento de salida; el nuevo registro se añade al principio de la lista de funciones que quedan por llamar.) Si una de estas funciones no devuelve (por ejemplo, llama a _exit(2), o se mata a sí misma con una señal), entonces no se llama a ninguna de las funciones restantes, y se abandona el procesamiento de salida posterior (en particular, el vaciado de los flujos de stdio(3) ). Si una función ha sido registrada múltiples veces usando atexit(3) o on_exit(3), entonces se llama tantas veces como fue registrada.

Todos los flujos de stdio(3) abiertos se vacían y se cierran. Los archivos creados por tmpfile(3) se eliminan.

El estándar C especifica dos constantes, EXIT_SUCCESS y EXIT_FAILURE, que pueden pasarse a exit() para indicar terminación exitosa o fallida, respectivamente.

VALOR DE RETORNO

La función exit() no retorna.

ATRIBUTOS

Para una explicación de los términos usados en esta sección, véase attributes(7).

Interfaz Atributo Valor
exit () Seguridad de hilos MT-Unsafe race:exit

La función exit() usa una variable global que no está protegida, por lo que no es segura para hilos.

ESTÁNDARES

C11, POSIX.1-2008.

HISTORIA

C89, POSIX.1-2001, SVr4, 4.3BSD.

NOTAS

El comportamiento es indefinido si una de las funciones registradas usando atexit(3) y on_exit(3) llama a exit() o a longjmp(3). Nótese que una llamada a execve(2) elimina los registros creados usando atexit(3) y on_exit(3).

El uso de EXIT_SUCCESS y EXIT_FAILURE es ligeramente más portable (a entornos no UNIX) que el uso de 0 y algún valor distinto de cero como 1 o -1. En particular, VMS usa una convención diferente.

BSD ha intentado estandarizar los códigos de salida (que algunas bibliotecas C como la Biblioteca C de GNU también han adoptado); véase el archivo <sysexits.h>.

Después de exit(), el estado de salida debe transmitirse al proceso padre. Hay tres casos:

•
Si el padre ha establecido SA_NOCLDWAIT, o ha establecido el manejador de SIGCHLD a SIG_IGN, el estado se descarta y el hijo muere inmediatamente.
•
Si el padre estaba esperando al hijo, se le notifica el estado de salida y el hijo muere inmediatamente.
•
De lo contrario, el hijo se convierte en un proceso "zombi": la mayoría de los recursos del proceso se reciclan, pero se retiene en la tabla de procesos una ranura que contiene información mínima sobre el proceso hijo (estado de terminación, estadísticas de uso de recursos). Esto permite al padre usar posteriormente waitpid(2) (o similar) para conocer el estado de terminación del hijo; en ese punto se libera la ranura del proceso zombi.

Si la implementación soporta la señal SIGCHLD , esta señal se envía al padre. Si el padre ha establecido SA_NOCLDWAIT, es indefinido si se envía una señal SIGCHLD .

Señales enviadas a otros procesos

Si el proceso que sale es el líder de sesión y su terminal de control es la terminal de control de la sesión, entonces a cada proceso en el grupo de procesos en primer plano de esta terminal de control se le envía una señal SIGHUP , y la terminal se desasocia de esta sesión, permitiendo que sea adquirida por un nuevo proceso de control.

Si la salida del proceso causa que un grupo de procesos se vuelva huérfano, y si algún miembro del grupo de procesos huérfano recién creado está detenido, entonces una señal SIGHUP seguida de una señal SIGCONT se enviará a cada proceso en este grupo de procesos. Véase setpgid(2) para una explicación de los grupos de procesos huérfanos.

Excepto en los casos anteriores, donde los procesos señalados pueden ser hijos del proceso que termina, la terminación de un proceso no no causa en general que se envíe una señal a los hijos de ese proceso. Sin embargo, un proceso puede usar la operación prctl(2) PR_SET_PDEATHSIG para disponer que reciba una señal si su padre termina.
