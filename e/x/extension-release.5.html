DESCRIPCIÓ

N

Los archivos /etc/os-release y /usr/lib/os-release contienen datos de identificación del sistema

operativo.

El formato de os-release es una lista de asignaciones de variables compatibles con el shell, separadas por saltos de línea, similares a las variables de entorno. Es posible importar la configuración desde scripts de shell Bourne; sin embargo, más allá de las simples asignaciones de variables, no se admiten características del shell (esto significa que la expansión de variables no es compatible explícitamente), lo que permite a las aplicaciones leer el archivo sin implementar un motor de ejecución compatible con el shell. Los valores de las asignaciones de variables deben estar entrecomillados con comillas dobles o simples si incluyen espacios, punto y coma u otros caracteres especiales fuera de A–Z, a–z, 0–9. (Las asignaciones que no incluyen estos caracteres especiales también pueden estar entrecomilladas, pero esto es opcional.) Los caracteres especiales del shell ("$", comillas, barra invertida, acento grave) deben escaparse con barras invertidas, siguiendo el estilo del shell. Todas las cadenas deben estar en codificación UTF-8, y no deben usarse caracteres no imprimibles. No se admite la concatenación de múltiples cadenas individualmente entrecomilladas. Las líneas que comienzan con "#" se tratan como comentarios. Se permiten e ignoran las líneas en

blanco.

El archivo /etc/os-release tiene prioridad sobre /usr/lib/os-release. Las aplicaciones deben buscar el primero y usar exclusivamente sus datos si existe, y solo recurrir a /usr/lib/os-release si falta. Las aplicaciones no deben combinar los datos de ambos archivos. /usr/lib/os-release es el lugar recomendado para almacenar la información de la versión del SO como parte de los árboles de proveedores. /etc/os-release debe ser un enlace simbólico relativo a /usr/lib/os-release, para proporcionar compatibilidad con aplicaciones que solo buscan en /etc/. Es necesario un enlace simbólico relativo en lugar de uno absoluto para evitar romper el enlace en un entorno chroot o

initrd.

os-release contiene datos que son definidos por el proveedor del sistema operativo y generalmente no deben ser modificados por el

administrador.

Dado que este archivo solo codifica nombres e identificadores, no debe ser

localizado.

Los archivos /etc/os-release y /usr/lib/os-release pueden ser enlaces simbólicos a otros archivos, pero es importante que el archivo esté disponible desde el arranque más temprano posible y, por lo tanto, debe ubicarse en el sistema de archivos

raíz.

os-release no debe contener claves repetidas. Sin embargo, los lectores deben elegir las entradas posteriores en el archivo en caso de repeticiones, de manera similar a como lo haría un shell que importa el archivo. Un lector puede advertir sobre entradas

repetidas.

Para una explicación más detallada de os-release, consulte el Anuncio de /etc/os-r

elease[1].

/etc/initrd-releas

e

En el initrd[2] y exitrd, /etc/initrd-release desempeña el mismo papel que os-release en el sistema principal. Además, la presencia de ese archivo significa que el sistema está en la fase de initrd/exitrd. /etc/os-release debe ser un enlace simbólico a /etc/initrd-release (o viceversa), para que los programas que solo buscan /etc/os-release (como se describió anteriormente) funcionen

correctamente.

/usr/lib/extension-release.d/extension-release.IMAG

E

/usr/lib/extension-release.d/extension-release.IMAGE desempeña el mismo papel para las imágenes de extensión que os-release para el sistema principal, y sigue la sintaxis y las reglas descritas en la página de Servicios Portables[3]. El propósito de este archivo es identificar la extensión y permitir que el sistema operativo verifique que la imagen de la extensión coincida con el SO base. Esto generalmente se implementa comprobando que la opción ID= de la extensión coincida con la opción ID= del host o esté incluida en la opción ID_LIKE= del host, y que o bien SYSEXT_LEVEL= existe y también coincide, o si no está presente, que VERSION_ID= existe y coincide. Esto asegura la compatibilidad ABI/API entre las capas e impide la fusión de una imagen incompatible en un

overlay.

Para identificar la propia imagen de la extensión, los mismos campos definidos a continuación pueden agregarse al archivo extension-release con un prefijo SYSEXT_ (para desambiguar de los campos utilizados para hacer coincidir la imagen base). Por ejemplo: SYSEXT_ID=myext, SYSEXT_VERSION_I

D=1.2.3.

En el nombre de archivo extension-release.IMAGE, la parte IMAGE debe coincidir exactamente con el nombre de archivo de la imagen que la contiene, con el sufijo eliminado. En caso de que no sea posible garantizar que el nombre de archivo de una imagen sea estable y no cambie entre las fases de compilación y despliegue, es posible relajar esta comprobación: si está presente exactamente un archivo cuyo nombre coincida con "extension-release.*" en este directorio, y el archivo esté etiquetado con un user.extension-release.strict xattr(7) establecido en la cadena "0", se usará en su

lugar.

RELEASE_TYPE

=
Una cadena en minúsculas (sin espacios ni otros caracteres fuera de 0-9, a-z, ".", "_", y "-"), que describe qué tipo de lanzamiento es esta versión del SO. Los valores conocidos son los siguientes:
•"stable" es para lanzamientos normales del sistema, adecuados para uso en producción. Generalmente, los lanzamientos estables alcanzan el fin de vida poco después de que salga el siguiente lanzamiento estable principal, aunque esto podría no ser el caso si, por ejemplo, una distribución adopta un modelo de lanzamiento continuo y aún está lista para producción. Los ejemplos incluyen Fedora 40, Ubuntu 23.10, OpenSUSE Tumbleweed y Arch
Linux.
•"lts" es para lanzamientos de soporte a largo plazo del sistema, adecuados para uso en producción y soportados durante un período de tiempo extendido. Generalmente, los lanzamientos LTS continúan recibiendo soporte incluso si están disponibles lanzamientos principales más recientes de la distribución. Los ejemplos incluyen Ubuntu 24.04, Debian 12 Bookworm y RHEL 9.
4.
•"development" es para versiones inestables del sistema, no adecuadas para uso en producción, como versiones alfa, beta o lanzamientos continuos inestables. Los ejemplos incluyen Fedora Rawhide, Debian Testing, Fedora 40 Beta y GNOME OS
Nightly.
•"experiment" es para compilaciones experimentales del sistema, creadas específicamente para probar alguna funcionalidad en desarrollo. Está destinado a usarse en combinación con EXPERIMENT=
.

Si no está establecido, o tiene un valor desconocido, asumir que el lanzamiento es

"stable".

Ejemplos: "RELEASE_TYPE=development", "RELEASE_TYPE=lts"

HOME_URL=, DOCUMENTATION_URL=, SUPPORT_URL=, BUG_REPORT_URL=, PRIVACY_POLICY_URL

=
Enlaces a recursos en Internet relacionados con el sistema operativo. HOME_URL= debe referirse a la página principal del sistema operativo, o alternativamente a alguna página principal de la versión específica del sistema operativo. DOCUMENTATION_URL= debe referirse a la página de documentación principal de este sistema operativo. SUPPORT_URL= debe referirse a la página de soporte principal del sistema operativo, si existe. Esto está destinado principalmente a los sistemas operativos para los que los proveedores ofrecen soporte. BUG_REPORT_URL= debe referirse a la página principal de informe de errores del sistema operativo, si existe. Esto está destinado principalmente a los sistemas operativos que dependen de la QA de la comunidad. PRIVACY_POLICY_URL= debe referirse a la página de política de privacidad principal del sistema operativo, si existe. Estos ajustes son opcionales, y es común proporcionar solo algunos de ellos. Estas URL están destinadas a exponerse en las interfaces de usuario "Acerca de este sistema" detrás de enlaces con leyendas como "Acerca de este Sistema Operativo", "Obtener Soporte", "Informar de un Error" o "Política de Privacidad". Los valores deben estar en formato RFC3986[5], y deben ser URL "http:" o "https:", y posiblemente "mailto:" o "tel:". Solo se debe listar una URL en cada ajuste. Si se necesitan referenciar múltiples recursos, se recomienda proporcionar una página de destino en línea que enlace todos los recursos disponibles.

Ejemplos: "HOME_URL="https://fedoraproject.org/"", "BUG_REPORT_URL="https://bugzilla

.redhat
.com/"".

=

Por ejemplo, "SUPPORT_END=2001-01-01" significa que el sistema fue soportado hasta el final del último día del milenio

anterior.

DEFAULT_HOSTNAME

=
Una cadena que especifica el nombre de host si hostname(5) no está presente y ninguna otra fuente de configuración especifica el nombre de host. Debe ser una sola etiqueta DNS (una cadena compuesta por caracteres ASCII de 7 bits en minúsculas y sin espacios ni puntos, limitada al formato permitido para las etiquetas de nombres de dominio DNS), o una secuencia de tales etiquetas separadas por puntos simples que forme un FQDN DNS válido. El nombre de host debe tener como máximo 64 caracteres, lo cual es una limitación de Linux (DNS permite nombres más largos).

Si el carácter de signo de interrogación "?" aparece en el nombre de host, se sustituye automáticamente por un carácter hexadecimal derivado del machine-id(5) cuando se aplica, de forma segura y determinista mediante hashing criptográfico. Ejemplo: "foobar-????-????" se expandirá automáticamente a "foobar-92a9-061c" o similar, dependiendo del ID de máquina

local.

Consulte org.freedesktop.hostname1(5) para una descripción de cómo systemd-hostnamed.service(8) determina el nombre de host de

reserva.

def read_os_release():
    try:
        filename = '/etc/os-release'
        f = open(filename)
    except FileNotFoundError:
        filename = '/usr/lib/os-release'
        f = open(filename)
    for line_number, line in enumerate(f, start=1):
        line = line.rstrip()
        if not line or line.startswith('#'):
            continue
        m = re.match(r'([A-Z][A-Z_0-9]+)=(.*)', line)
        if m:
            name, val = m.groups()
            if val and val[0] in '"\'':
                val = ast.literal_eval(val)
            yield name, val
        else:
            print(f'{filename}:{line_number}: bad line {line!r}',
                  file=sys.stderr)
