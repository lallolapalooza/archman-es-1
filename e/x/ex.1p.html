DESCRIPCIÓ

N

La utilidad ex es un editor de texto orientado a líneas. Hay otros dos modos del editor—abierto y visual—en los que está disponible la edición orientada a pantalla. Esto se describe con más detalle por los comandos ex open y visual y en vi

.

Si un operando es '-', los resultados no están

especificados.

Esta sección utiliza el término búfer de edición para describir el texto de trabajo actual. Este término no implica ninguna implementación específica. Todos los cambios de edición se realizan en el búfer de edición, y no se realizarán cambios en él que afecten a ningún archivo hasta que un comando del editor escriba el

archivo.

Ciertas terminales no tienen todas las capacidades necesarias para soportar la definición completa de ex, como los comandos de edición a pantalla completa (modo visual o modo abierto). Cuando estos comandos no puedan soportarse en tales terminales, esta condición no debe producir un mensaje de error como ``no es un comando del editor'' ni reportar un error de sintaxis. La implementación puede tanto acep

tar los comandos y producir resultados en la pantalla que sean el resultado de un intento fallido de cumplir los re
quisitos de este volumen de POSIX.1‐2017 como reportar un error describiendo la deficiencia relacionada con la terminal.

Si no hay caracteres insertados antes de los caracteres de palabra y no de palabra o <ESC> que activaron la comprobación, el conjunto de caracteres será el carácter de palabra.

Si el carácter insertado antes de los caracteres de palabra y no de palabra o <ESC> que activaron la comprobación es un carácter de palabra, el conjunto de caracteres consistirá en los caracteres insertados inmediatamente antes de los caracteres desencadenantes que son caracteres de palabra, más el carácter de palabra desencadenante.

General Information

This section describes historical differences between implementations of vi and ex, and how POSIX.1‐2008 addresses them. The goal is to provide a portable subset of the historical functionality.

Command Line Arguments

Historically, the empty edit buffer presented for editing when a file was not specified by the user was unnamed. This is permitted by POSIX.1‐2008; however, implementations are encouraged to provide users a temporary filename for this buffer because it permits them the use of ex commands that use the current pathname during temporary edit sessions.

Historically, the file specified using the -t option was not part of the current argument list. This practice is permitted by POSIX.1‐2008; however, implementations are encouraged to include its name in the current argument list for consistency.

Historically, the -c command was generally not executed until a file that already exists was edited. POSIX.1‐2008 requires conformance to this historical practice. Commands that could cause the -c command to be executed include the ex commands edit, next, recover, rewind, and tag, and the vi commands <control>‐^ and <control>‐]. Historically, reading a file into an edit buffer did not cause the -c command to be executed (even though it might set the current pathname) with the exception that it did cause the -c command to be executed if: the editor was in ex mode, the edit buffer had no current pathname, the edit buffer was empty, and no read commands had yet been attempted. For consistency and simplicity of specification, POSIX.1‐2008 does not permit this behavior.

Historically, the -r option was the same as a normal edit session if there was no recovery information available for the file. This allowed users to enter:

vi -r *.c

and recover whatever files were recoverable. In some implementations, recovery was attempted only on the first file named, and the file was not entered into the argument list; in others, recovery was attempted for each file named. In addition, some historical implementations ignored -r if -t was specified or did not support command line file arguments with the -t option. For consistency and simplicity of specification, POSIX.1‐2008 disallows these special cases, and requires that recovery be attempted the first time each file is edited.

Historically, vi initialized the ` and ' marks, but ex did not. This meant that if the first command in ex mode was visual or if an ex command was executed first (for example, vi +10 file), vi was entered without the marks being initialized. Because the standard developers believed the marks to be generally useful, and for consistency and simplicity of specification, POSIX.1‐2008 requires that they always be initialized if in open or visual mode, or if in ex mode and the edit buffer is not empty. Not initializing it in ex mode if the edit buffer is empty is historical practice; however, it has always been possible to set (and use) marks in empty edit buffers in open and visual mode edit sessions.

Addressing

Historically, ex and vi accepted the additional addressing forms '\/' and '\?'. They were equivalent to "//" and "??", respectively. They are not required by POSIX.1‐2008, mostly because nobody can remember whether they ever did anything different historically.

Historically, ex and vi permitted an address of zero for several commands, and permitted the % address in empty files for others. For consistency, POSIX.1‐2008 requires support for the former in the few commands where it makes sense, and disallows it otherwise. In addition, because POSIX.1‐2008 requires that % be logically equivalent to "1,$", it is also supported where it makes sense and disallowed otherwise.

Historically, the % address could not be followed by further addresses. For consistency and simplicity of specification, POSIX.1‐2008 requires that additional addresses be supported.

All of the following are valid addresses:

+++
Three lines after the current line.
/re/-
One line before the next occurrence of re.
-2
Two lines before the current line.
3 ---- 2
Line one (note intermediate negative address).
1 2 3
Line six.

Any number of addresses can be provided to commands taking addresses; for example, "1,2,3,4,5p" prints lines 4 and 5, because two is the greatest valid number of addresses accepted by the print command. This, in combination with the <semicolon> delimiter, permits users to create commands based on ordered patterns in the file. For example, the command 3;/foo/;+2print will display the first line after line 3 that contains the pattern foo, plus the next two lines. Note that the address 3; must be evaluated before being discarded because the search origin for the /foo/ command depends on this.

Historically, values could be added to addresses by including them after one or more <blank> characters; for example, 3 - 5p wrote the seventh line of the file, and /foo/ 5 was the same as /foo/+5. However, only absolute values could be added; for example, 5 /foo/ was an error. POSIX.1‐2008 requires conformance to historical practice. Address offsets are separately specified from addresses because they could historically be provided to visual mode search commands.

Historically, any missing addresses defaulted to the current line. This was true for leading and trailing <comma>-delimited addresses, and for trailing <semicolon>-delimited addresses. For consistency, POSIX.1‐2008 requires it for leading <semicolon> addresses as well.

Historically, ex and vi accepted the '^' character as both an address and as a flag offset for commands. In both cases it was identical to the '-' character. POSIX.1‐2008 does not require or prohibit this behavior.

Historically, the enhancements to basic regular expressions could be used in addressing; for example, '~', '\<', and '\>'. POSIX.1‐2008 requires conformance to historical practice; that is, that regular expression usage be consistent, and that regular expression enhancements be supported wherever regular expressions are used.

Command Line Parsing in ex

Historical ex command parsing was even more complex than that described here. POSIX.1‐2008 requires the subset of the command parsing that the standard developers believed was documented and that users could reasonably be expected to use in a portable fashion, and that was historically consistent between implementations. (The discarded functionality is obscure, at best.) Historical implementations will require changes in order to comply with POSIX.1‐2008; however, users are not expected to notice any of these changes. Most of the complexity in ex parsing is to handle three special termination cases:

1.
The !, global, v, and the filter versions of the read and write commands are delimited by <newline> characters (they can contain <vertical-line> characters that are usually shell pipes).
2.
The ex, edit, next, and visual in open and visual mode commands all take ex commands, optionally containing <vertical-line> characters, as their first arguments.
3.
The s command takes a regular expression as its first argument, and uses the delimiting characters to delimit the command.

Historically, <vertical-line> characters in the +command argument of the ex, edit, next, vi, and visual commands, and in the pattern and replacement parts of the s command, did not delimit the command, and in the filter cases for read and write, and the !, global, and v commands, they did not delimit the command at all. For example, the following commands are all valid:

:edit +25 | s/abc/ABC/ file.c
:s/ | /PIPE/
:read !spell % | columnate
:global/pattern/p | l
:s/a/b/ | s/c/d | set

Historically, empty or <blank> filled lines in .exrc files and sourced files (as well as EXINIT variables and ex command scripts) were treated as default commands; that is, print commands. POSIX.1‐2008 specifically requires that they be ignored when encountered in .exrc and sourced files to eliminate a common source of new user error.

Historically, ex commands with multiple adjacent (or <blank>-separated) vertical lines were handled oddly when executed from ex mode. For example, the command ||| <carriage-return>, when the cursor was on line 1, displayed lines 2, 3, and 5 of the file. In addition, the command | would only display the line after the next line, instead of the next two lines. The former worked more logically when executed from vi mode, and displayed lines 2, 3, and 4. POSIX.1‐2008 requires the vi behavior; that is, a single default command and line number increment for each command separator, and trailing <newline> characters after <vertical-line> separators are discarded.

Historically, ex permitted a single extra <colon> as a leading command character; for example, :g/pattern/:p was a valid command. POSIX.1‐2008 generalizes this to require that any number of leading <colon> characters be stripped.

Historically, any prefix of the delete command could be followed without intervening <blank> characters by a flag character because in the command d p, p is interpreted as the buffer p. POSIX.1‐2008 requires conformance to historical practice.

Historically, the k command could be followed by the mark name without intervening <blank> characters. POSIX.1‐2008 requires conformance to historical practice.

Historically, the s command could be immediately followed by flag and option characters; for example, s/e/E/|s|sgc3p was a valid command. However, flag characters could not stand alone; for example, the commands sp and s l would fail, while the command sgp and s gl would succeed. (Obviously, the '#' flag character was used as a delimiter character if it followed the

comando.) Otro problema era que los caracteres de opción tenían que preceder a los caracteres de indicador incluso cuando el comando estaba completamente especificado; por ejemplo, el comando s/e/E/pg fallaría, mientras que el comando s/e/E/gp tendría éxito. POSIX.1‐2008 requiere la conformidad con la práctica

histórica.

Históricamente, el primer nombre de comando que tenía un prefijo que coincidía con la entrada del usuario era el comando que se ejecutaba; por ejemplo, ve, ver, y vers ejecutaban todos el comando version. Sin embargo, los comandos estaban en un orden específico, de modo que a coincidía con append, no con abbreviate. POSIX.1‐2008 requiere la conformidad con la práctica histórica. La restricción en el orden de búsqueda de comandos para implementaciones con extensiones es para evitar la adición de comandos que hagan que los prefijos históricos dejen de funcionar de forma

portable.

Las implementaciones históricas de ex y vi no manejaban correctamente múltiples comandos ex, separados por caracteres <vertical-line>, que entraban o salían del modo visual o del editor. Sin embargo, porque existen implementaciones de vi que no exhiben este modo de fallo, POSIX.1‐2008 no lo

permite.

El requisito de que los nombres de comando alfabéticos consten de todos los caracteres alfabéticos siguientes hasta el siguiente carácter no alfabético significa que los nombres de comando alfabéticos deben separarse de sus argumentos por uno o más caracteres no alfabéticos, normalmente un <blank> o un carácter '!', excepto como se especifica para las excepciones, los comandos delete, k, y s

Históricamente, la ejecución repetida de los comandos de impresión predeterminados de ex (<control>‐D, eof, <newline>, <carriage-return>) borraba cualquier carácter de indicación y mostraba las siguientes líneas sin desplazar la terminal; es decir, inmediatamente debajo de cualquier línea mostrada previamente. Esto proporcionaba una presentación más limpia de las líneas del archivo para el usuario. POSIX.1‐2008 no requiere este comportamiento porque puede ser imposible en algunas situaciones; sin embargo, se anima encarecidamente a las implementaciones a proporcionar esta semántica si es

posible.

El comillado de comandos ex requerido por POSIX.1‐2008 es un superconjunto del comillado en las implementaciones históricas del editor. POSIX.1‐2008 extiende la práctica histórica, requiriendo que el comportamiento de comillado se haga consistente en todos los comandos ex, excepto para los map, unmap, abbreviate, y comandos unabbreviate, que históricamente usaban <control>‐V en lugar de caracteres <backslash> para el comillado. El comillado con backslash en ex es contraintuitivo. Las secuencias <backslash>-escape se ignoran a menos que escapen un carácter especial; por ejemplo, al realizar la expansión de argumentos de archivo, la cadena "\\%" es equivalente a '\%', no a "\<nombre de ruta actual>". Esto puede ser confuso para los usuarios porque <backslash> es usualmente uno de los caracteres que provoca que se realice la expansión del shell, y por lo tanto las reglas de comillado del shell deben tenerse en consideración. Generalmente, los caracteres de comillado solo se consideran si escapan un carácter especial, y se debe proporcionar un carácter de comillado para cada capa de análisis para la cual el carácter es especial. Como otro ejemplo, solo es necesario un único <backslash> para la secuencia '\l' en los patrones de reemplazo de sustitución, porque el carácter 'l' no es especial para ninguna capa de análisis

superior.

El comillado con <control>‐V en ex es ligeramente diferente del comillado con backslash. histórica.

Descripciones de Comandos en ex

Históricamente, varios comandos (por ejemplo, global, v, visual, s, write, wq, yank, !, <, >, & y ~) eran ejecutables en archivos vacíos (es decir, la(s) dirección(es) por defecto eran 0), o permitían direcciones explícitas de 0 (por ejemplo, 0 era una dirección válida, o 0,0 era un rango válido). Las direcciones de 0, o la ejecución de comandos en un archivo vacío, sólo tienen sentido para comandos que añaden nuevo texto al buffer de edición o comandos de escritura (porque los usuarios pueden desear escribir archivos vacíos). POSIX.1‐2008 requiere este comportamiento para tales comandos y lo prohíbe en caso contrario, para la consistencia y simplicidad de la especificación.

Un contador para un comando ex se ha corregido históricamente para que no sea mayor que la última línea de un archivo; por ejemplo, en un archivo de cinco líneas, el comando 1,6print fallaría, pero el comando 1print300 tendría éxito. POSIX.1‐2008 requiere la conformidad con la práctica histórica.

Históricamente, el uso de indicadores en los comandos ex podía ser oscuro. La práctica histórica general era la descrita por POSIX.1‐2008, pero había algunos casos especiales. Por ejemplo, los comandos list, number y print ignoraban los desplazamientos de dirección finales; por ejemplo, 3p +++# mostraría la línea 3, y 3 sería la línea actual después de la ejecución del comando. Los comandos open y visual ignoraban tanto los desplazamientos finales como los indicadores finales. Además, los indicadores especificados para los comandos open y visual interactuaban mal con la opción de edición list, y establecerla y luego desestablecerla durante la sesión de open/visual haría que vi dejara de mostrar líneas en el formato especificado. Para consistencia y simplicidad de especificación, POSIX.1‐2008 no permite ninguna de estas excepciones a la regla general.

POSIX.1‐2008 utiliza la palabra *copiar* en varios lugares al discutir buffers. Esto no pretende implicar una implementación.

Históricamente, los usuarios de ex no podían especificar buffers numéricos debido a la ambigüedad que esto causaría; por ejemplo, en el comando 3 delete 2, no está claro si 2 es un nombre de buffer o un *contador*. POSIX.1‐2008 requiere la conformidad con la práctica histórica por defecto, pero no excluye extensiones.

Históricamente, el contenido del buffer sin nombre se descartaba frecuentemente después de comandos que no lo afectaban explícitamente; por ejemplo, al usar el comando edit para cambiar de archivo. Para consistencia y simplicidad de especificación, POSIX.1‐2008 no permite este comportamiento.

La utilidad ex históricamente no tenía acceso a los buffers numéricos y, además, eliminar líneas en ex no modificaba su contenido. Por ejemplo, si después de hacer un borrado en vi, el usuario cambiaba a ex, hacía otro borrado y luego volvía a vi, el contenido de los buffers numéricos no habría cambiado. POSIX.1‐2008 requiere la conformidad con la práctica histórica. Los buffers numéricos se describen en la utilidad ex para confinar la descripción de los buffers a una sola ubicación en POSIX.1‐2008.

Los metacaracteres que activan la expansión del shell en argumentos de *file* coinciden con la práctica histórica, al igual que el método para realizar la expansión del shell. Se anima a las implementaciones que deseen proporcionar a los usuarios la flexibilidad de alterar el conjunto de metacaracteres a proporcionar una opción de edición de cadena shellmeta.

Históricamente, los comandos ex ejecutados desde vi actualizaban la pantalla cuando no era estrictamente necesario hacerlo; por ejemplo, :!date > /dev/null no requiere una actualización de pantalla porque la salida del comando date de UNIX requiere sólo una sola línea de la pantalla. Abreviar

La práctica histórica era que los caracteres que se introducían como parte de un reemplazo de abreviatura estaban sujetos a las expansiones de map, la opción de edición showmatch, expansiones de abreviatura adicionales, y así sucesivamente; es decir, se insertaban lógicamente en la cola de entrada del terminal, y no eran un simple reemplazo. POSIX.1‐2008 requiere la conformidad con la práctica histórica. La práctica histórica era que cada vez que se introducía un carácter no de palabra (que no había sido escapado por un <control>‐V) después de un carácter de palabra, vi comprobaba las abreviaturas. La comprobación se basaba en el tipo del carácter introducido antes del carácter de palabra del par palabra/no palabra que activaba la comprobación. El carácter de palabra del par palabra/no palabra que activaba la comprobación y todos los caracteres introducidos antes del par activador que fueran de ese tipo se incluían en la comprobación, con la excepción de los caracteres <espacio>, que siempre delimitaban la abreviatura.

Esto significa que, para que la abreviatura funcione, el *lhs* debe terminar con un carácter de palabra, no puede haber transiciones de palabra a caracteres no de palabra (o viceversa) excepto entre el último y el penúltimo carácter del *lhs*, y no puede haber caracteres <espacio> en el *lhs*. Además, debido a las reglas históricas de escapado, era imposible introducir un <control>‐V literal en el *lhs*. POSIX.1‐2008 requiere la conformidad con la práctica histórica. Las implementaciones históricas no informaban a los usuarios cuando se introducían abreviaturas que nunca podrían usarse; se anima encarecidamente a las implementaciones a hacerlo.

Por ejemplo, las siguientes abreviaturas funcionarán:

:ab (p  REEMPLAZAR
:ab p   REEMPLAZAR
:ab ((p REEMPLAZAR

Las siguientes abreviaturas no funcionarán:

:ab (   REEMPLAZAR
:ab (pp REEMPLAZAR

La práctica histórica es que las palabras en la línea de comandos de dos puntos de vi estaban sujetas a expansión de abreviatura, incluidos los argumentos para el comando abbrev (y, más interesante, el comando unabbrev). Dado que existen implementaciones que no realizan la expansión de abreviaturas para el primer argumento de esos comandos, esto está permitido, pero no es obligatorio, por POSIX.1‐2008. Sin embargo, la siguiente secuencia:

:ab foo bar
:ab foo baz

dio como resultado la adición de una abreviatura de "baz" para la cadena "bar" en ex/vi históricos, y la secuencia:

:ab foo1 bar
:ab foo2 bar
:unabbreviate foo2

eliminó la abreviatura "foo1", no "foo2". Estos comportamientos no están permitidos por POSIX.1‐2008 porque violan claramente las expectativas del usuario.

Era práctica histórica que <control>‐V, no <barra invertida>, se interpretara como un escapado de los caracteres siguientes en el comando abbreviate. POSIX.1‐2008 requiere la conformidad con la práctica histórica; sin embargo, debe notarse que una abreviatura que contenga un <espacio> nunca funcionará.
