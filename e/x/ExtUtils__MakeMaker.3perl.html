Atributos PREFIX y LIB

PREFIX y LIB se pueden usar para establecer varios atributos INSTALL* de una sola vez. Aquí hay un ejemplo para instalar en su directorio personal.

# Los usuarios de Unix, PREFIX=~ funciona bien
perl Makefile.PL PREFIX=/ruta/a/su/directorio/personal

Esto instalará todos los archivos del módulo en su directorio personal, con las páginas de manual y las bibliotecas yendo a un lugar apropiado (usualmente ~/man y ~/lib). Cómo se determina la ubicación exacta es complicado y depende de cómo se configuró su Perl. INSTALL_BASE funciona más como lo que otros sistemas de construcción llaman "prefix" que PREFIX y le recomendamos que use eso en su lugar.

Otra forma de especificar muchos directorios INSTALL con un solo parámetro es LIB.

perl Makefile.PL LIB=~/lib

Esto instalará los archivos independientes de la arquitectura del módulo en ~/lib, y los archivos dependientes de la arquitectura en ~/lib/$archname.

Note que, en ambos casos, la expansión de la tilde (~) es realizada por MakeMaker, no por perl por defecto, ni por make.

Los conflictos entre los parámetros LIB, PREFIX y los diversos argumentos INSTALL* se resuelven de modo que:

  • establecer LIB anula cualquier configuración de INSTALLPRIVLIB, INSTALLARCHLIB, INSTALLSITELIB, INSTALLSITEARCH (y no son afectados por PREFIX);
  • sin LIB, establecer PREFIX reemplaza la parte inicial $Config{prefix} de esos argumentos INSTALL*, incluso si estos últimos están explícitamente establecidos (pero se establecen para que aún comiencen con $Config{prefix}).

Si el usuario tiene privilegios de superusuario y no está trabajando en AFS o parientes, entonces los valores predeterminados para INSTALLPRIVLIB, INSTALLARCHLIB, INSTALLSCRIPT, etc. serán apropiados, y esta invocación será la mejor:

perl Makefile.PL;
make;
make test
make install

make install por defecto escribe alguna documentación de lo que se ha hecho en el archivo "$(INSTALLARCHLIB)/perllocal.pod". Esta característica se puede evitar llamando a make pure_install.

Enlace Estático de un Nuevo Binario Perl

Una extensión que se construye con los pasos anteriores está lista para usarse en sistemas que soportan carga dinámica. En sistemas que no soportan carga dinámica, cualquier extensión recién creada tiene que ser enlazada junto con los recursos disponibles. MakeMaker soporta el proceso de enlace creando objetivos apropiados en el Makefile cada vez que se construye una extensión. Puede invocar la sección correspondiente del makefile con

make perl

Eso produce un nuevo binario perl en el directorio actual con todas las extensiones enlazadas que se puedan encontrar en INST_ARCHLIB, SITELIBEXP y PERL_ARCHLIB. Para hacer eso, MakeMaker escribe un nuevo Makefile, en UNIX, esto se llama Makefile.aperl (puede depender del sistema). Si desea forzar la creación de un nuevo perl, se recomienda que elimine este Makefile.aperl, de modo que los directorios se busquen de nuevo en busca de bibliotecas enlazables.

El binario se puede instalar en el directorio donde perl normalmente reside en su máquina con

make inst_perl

Para producir un binario perl con un nombre diferente a "perl", simplemente diga

perl Makefile.PL MAP_TARGET=myperl
make myperl
make inst_perl

o diga

perl Makefile.PL
make myperl MAP_TARGET=myperl
make inst_perl MAP_TARGET=myperl

En cualquier caso, se le pedirá la invocación correcta del objetivo "inst_perl" que instala el nuevo binario en INSTALLBIN.

make inst_perl por defecto escribe alguna documentación de lo que se ha hecho en el archivo "$(INSTALLARCHLIB)/perllocal.pod". Esto se puede evitar llamando a make pure_inst_perl.

Advertencia: el objetivo inst_perl: muy probablemente sobrescribirá su binario perl existente. ¡Úselo con cuidado!

A veces es posible que desee construir un perl enlazado estáticamente aunque su sistema soporte carga dinámica. En este caso, puede establecer explícitamente el tipo de enlace (linktype) con la invocación del Makefile.PL o make:

perl Makefile.PL LINKTYPE=static    # recomendado

o

make LINKTYPE=static                # funciona en la mayoría de los sistemas

Determinación de las Ubicaciones de la Biblioteca Perl y de la Instalación

MakeMaker necesita saber, o adivinar, dónde están ubicadas ciertas cosas. Especialmente INST_LIB y INST_ARCHLIB (dónde poner los archivos durante la ejecución de make(1) ), PERL_LIB y PERL_ARCHLIB (dónde leer los módulos existentes), y PERL_INC (archivos de cabecera y "libperl*.*").

Las extensiones pueden construirse ya sea usando el contenido del árbol de directorios del código fuente de perl o desde la biblioteca perl instalada. La forma recomendada es construir extensiones después de haber ejecutado 'make install' en perl mismo. Puede hacerlo en cualquier directorio en su disco duro que no esté debajo del árbol de código fuente de perl. El soporte para extensiones debajo del directorio ext de la distribución de perl es solo bueno para las extensiones estándar que vienen con perl.

Si una extensión se está construyendo debajo del directorio "ext/" del código fuente de perl, entonces MakeMaker establecerá PERL_SRC automáticamente (por ejemplo, "../.."). Si PERL_SRC está definido y la extensión es reconocida como una extensión estándar, entonces otras variables tienen los siguientes valores predeterminados:

PERL_INC     = PERL_SRC
PERL_LIB     = PERL_SRC/lib
PERL_ARCHLIB = PERL_SRC/lib
INST_LIB     = PERL_LIB
INST_ARCHLIB = PERL_ARCHLIB

Si una extensión se está construyendo lejos del código fuente de perl, entonces MakeMaker dejará PERL_SRC sin definir y usará por defecto la copia instalada de la biblioteca perl. Las otras variables tienen los siguientes valores predeterminados:

PERL_INC     = $archlibexp/CORE
PERL_LIB     = $privlibexp
PERL_ARCHLIB = $archlibexp
INST_LIB     = ./blib/lib
INST_ARCHLIB = ./blib/arch

Si perl aún no ha sido instalado, entonces PERL_SRC se puede definir en la línea de comandos como se mostró en la sección anterior.

¿Qué directorio dependiente de la arquitectura?

Si no desea mantener los valores predeterminados para las macros INSTALL*, MakeMaker le ayuda a minimizar la escritura necesaria: la relación habitual entre INSTALLPRIVLIB y INSTALLARCHLIB es determinada por Configure en el tiempo de compilación de perl. MakeMaker soporta al usuario que establece INSTALLPRIVLIB. Si INSTALLPRIVLIB está establecido, pero INSTALLARCHLIB no, entonces MakeMaker establece por defecto el último para que sea el mismo subdirectorio de INSTALLPRIVLIB que Configure decidió para sus contrapartes en %Config, de lo contrario se establece por defecto a INSTALLPRIVLIB. La misma relación se mantiene para INSTALLSITELIB y INSTALLSITEARCH.

MakeMaker le da mucha más libertad de la necesaria para configurar variables internas y obtener diferentes resultados. Vale la pena mencionar que make(1) también le permite configurar la mayoría de las variables que se usan en el Makefile. Pero en la mayoría de las situaciones esto no será necesario, y solo se debe hacer si el autor de un paquete lo recomienda (o si sabe lo que está haciendo).

$VERSION o "package Name VERSION" será usada. Las siguientes líneas se analizarán correctamente:

Sobrescribir Métodos de MakeMaker

Si no puedes lograr el comportamiento deseado del Makefile especificando atributos, puedes definir subrutinas privadas en el Makefile.PL. Cada subrutina devuelve el texto que desea que se escriba en el Makefile. Para sobrescribir una sección del Makefile puedes decir:

sub MY::c_o { "new literal text" }

o puedes editar el valor por defecto diciendo algo como:

package MY; # para que "SUPER" funcione correctamente
sub c_o {
    my $inherited = shift->SUPER::c_o(@_);
    $inherited =~ s/old text/new text/;
    $inherited;
}

Si estás realizando experimentos con la incrustación de perl como una biblioteca en otras aplicaciones, podrías encontrar que MakeMaker no es suficiente. Es mejor que eches un vistazo a ExtUtils::Embed, que es una colección de utilidades para la incrustación.

Si aún necesitas una solución diferente, intenta desarrollar otra subrutina que se ajuste a tus necesidades y envía los diffs a "makemaker@perl.org"

Para una descripción completa de todos los métodos de MakeMaker, ver ExtUtils::MM_Unix.

Aquí hay un ejemplo simple de cómo añadir un nuevo objetivo al Makefile generado:

sub MY::postamble {
    return <<'MAKE_FRAG';
$(MYEXTLIB): sdbm/Makefile
        cd sdbm && $(MAKE) all
MAKE_FRAG
}

El Fin de la Programación de Culto a la Carga

WriteMakefile() ahora realiza algunas verificaciones básicas de sanidad en sus parámetros para proteger contra errores tipográficos y valores mal formateados. Esto significa que algunas cosas que solían funcionar en el pasado ahora generarán advertencias y posiblemente producirán errores internos.

Algunos de los errores más comunes:

"MAN3PODS => ' '"
Esto se usa comúnmente para suprimir la creación de páginas de manual. MAN3PODS toma un hash ref, no una cadena, pero lo anterior funcionó por accidente en versiones antiguas de MakeMaker.

El código correcto es "MAN3PODS => { }".

Soporte de Archivos de Pistas

MakeMaker.pm usa la información específica de la arquitectura de Config.pm. Además, evalúa archivos de pistas específicos de la arquitectura en un directorio "hints/" . Se espera que los archivos de pistas se llamen como sus contrapartes en "PERL_SRC/hints&quot;, pero con una extensión de nombre de archivo ".pl" (por ejemplo, "next_3_2.pl"). Simplemente son "eval"uados por MakeMaker dentro de la subrutina WriteMakefile() , y pueden usarse para ejecutar comandos así como para incluir variables especiales. Las reglas para elegir el archivo de pistas (hintsfile) son las mismas que en Configure.

El archivo de pistas (hintsfile) es eval()uado inmediatamente después de que los argumentos dados a WriteMakefile se insertan en una referencia a hash $self pero antes de que esta referencia sea bendecida (blessed). Así que si quieres hacer el equivalente para sobrescribir o crear un atributo, dirías algo como

$self->{LIBS} = ['-ldbm -lucb -lc'];

Soporte de Distribución

Para los autores de extensiones, MakeMaker proporciona varios objetivos de Makefile. La mayor parte del soporte proviene del módulo ExtUtils::Manifest, donde se puede encontrar documentación adicional.

make distcheck
informa qué archivos están debajo del directorio de compilación pero no en el archivo MANIFEST y viceversa. (Ver "fullcheck" en ExtUtils::Manifest para detalles)
make skipcheck
informa qué archivos se omiten debido a las entradas en el archivo "MANIFEST.SKIP" (Ver "skipcheck" en ExtUtils::Manifest para detalles)
make distclean
hace un realclean primero y luego el distcheck. Ten en cuenta que esto no es necesario para construir una nueva distribución siempre que estés seguro de que el archivo MANIFEST está bien.
make veryclean
hace un realclean primero y luego elimina archivos de respaldo como "*~", "*.bak", "*.old" y "*.orig"
make manifest
reescribe el archivo MANIFEST, añadiendo todos los archivos restantes encontrados (Ver "mkmanifest" en ExtUtils::Manifest para detalles)
make distdir
Copia todos los archivos que están en el archivo MANIFEST a un directorio recién creado con el nombre "$(DISTNAME)-$(VERSION)". Si ese directorio existe, será eliminado primero.

Además, creará los archivos de metadatos de módulo META.yml y META.json en el distdir y los añadirá al MANIFEST del distdir. Puedes desactivar este comportamiento con el flag NO_META.

make disttest
Hace un distdir primero, y ejecuta un "perl Makefile.PL", un make, y un make test en ese directorio.
make tardist
Primero hace un distdir. Luego un comando $(PREOP) que por defecto es un comando nulo, seguido de $(TO_UNIX), que por defecto es un comando nulo bajo UNIX, y de lo contrario convertirá los archivos en el directorio de distribución al formato UNIX. A continuación, ejecuta "tar" en ese directorio en un archivo tar y elimina el directorio. Termina con un comando $(POSTOP) que por defecto es un comando nulo.
make dist
Por defecto es $(DIST_DEFAULT), que a su vez por defecto es tardist.
make uutardist
Ejecuta un tardist primero y uuencodea el archivo tar.
make shdist
Primero hace un distdir. Luego un comando $(PREOP) que por defecto es un comando nulo. A continuación, ejecuta "shar" en ese directorio en un archivo shar y elimina el directorio intermedio de nuevo. Termina con un comando $(POSTOP) que por defecto es un comando nulo. Nota: Para que shdist funcione correctamente, es obligatorio un programa "shar" que pueda manejar directorios.
make zipdist
Primero hace un distdir. Luego un comando $(PREOP) que por defecto es un comando nulo. Ejecuta "$(ZIP) $(ZIPFLAGS)" en ese directorio en un archivo zip. Luego elimina ese directorio. Termina con un comando $(POSTOP) que por defecto es un comando nulo.
make ci
Hace un $(CI) y un $(RCS_LABEL) en todos los archivos del archivo MANIFEST.

La personalización de los objetivos dist se puede hacer especificando una referencia a hash al atributo dist de la llamada a WriteMakefile. Se reconocen los siguientes parámetros:

CI           ('ci -u')
COMPRESS     ('gzip --best')
POSTOP       ('@ :')
PREOP        ('@ :')
TO_UNIX      (depende del sistema)
RCS_LABEL    ('rcs -q -Nv$(VERSION_SYM):')
SHAR         ('shar')
SUFFIX       ('.gz')
TAR          ('tar')
TARFLAGS     ('cvf')
ZIP          ('zip')
ZIPFLAGS     ('-r')

Un ejemplo:

WriteMakefile(
    ...otras opciones...
    dist => {
        COMPRESS => "bzip2",
        SUFFIX   => ".bz2"
    }
);

Metadatos del Módulo (META y MYMETA)

Durante mucho tiempo, ha atormentado a los usuarios de módulos basados en MakeMaker el problema de obtener información básica sobre el módulo a partir de las fuentes sin ejecutar el Makefile.PL y hacer un montón de heurísticas desordenadas sobre el Makefileresultante. Con el tiempo, se ha convertido en estándar mantener esta información en uno o más archivos CPAN Meta distribuidos con cada distribución.

El formato original de los archivos CPAN Meta era YAML y el archivo correspondiente se llamaba META.yml. En 2010, se lanzó la versión 2 de la especificación CPAN::Meta, que exige el formato JSON para los metadatos con el fin de superar ciertos problemas de compatibilidad entre serializadores YAML y para evitar romper clientes antiguos que no pueden manejar una nueva versión de la especificación. La biblioteca CPAN::Meta es ahora estándar para acceder a archivos Meta de estilo antiguo y nuevo.

Si CPAN::Meta está instalado, MakeMaker generará automáticamente los archivos META.json y META.yml para ti y los añadirá a tu MANIFEST como parte del objetivo 'distdir' (y por lo tanto del objetivo 'dist'). Esto tiene como objetivo poblar CPAN de manera transparente y rápida con metadatos de módulos. Si deseas desactivar esta función, establece el flag "NO_META" de WriteMakefile() en verdadero.

En el QA Hackathon de 2008 en Oslo, los mantenedores de la cadena de herramientas de módulos Perl acordaron usar el formato CPAN Meta para comunicar los requisitos posteriores a la configuración entre los componentes de la cadena de herramientas. Estos archivos, MYMETA.json y MYMETA.yml, se generan cuando Makefile.PL genera un Makefile (si CPAN::Meta está instalado). Clientes como CPAN o CPANPLUS leerán estos archivos para ver qué prerrequisitos deben cumplirse antes de compilar o probar la distribución. Si deseas desactivar esta función, establece el flag "NO_MYMETA" de WriteMakefile() en verdadero.

Deshabilitando una extensión

Si algunos eventos detectados en Makefile.PL implican que no hay forma de crear el Módulo, pero este es un estado normal de las cosas, entonces puedes crear un Makefile que no hace nada, pero tiene éxito en todos los objetivos de compilación "habituales". Para hacerlo, usa

use ExtUtils::MakeMaker qw(WriteEmptyMakefile);
WriteEmptyMakefile();

en lugar de WriteMakefile().

Esto puede ser útil si otros módulos esperan que este módulo se compile correctamente, a diferencia de funcione correctamente (digamos, este módulo dependiente del sistema se compila en un subdirectorio de alguna otra distribución, o está listado como una dependencia en un CPAN::Bundle, pero la funcionalidad está soportada por medios diferentes en la arquitectura actual).

Otras Funciones Útiles

prompt
my $value = prompt($message);
my $value = prompt($message, $default);

La función prompt() proporciona una manera fácil de solicitar la entrada del usuario usada para escribir un makefile. Muestra el $message como una petición de entrada. Si se proporciona un $default se usará como valor por defecto. La función devuelve el $value seleccionado por el usuario.

Si prompt() detecta que no se está ejecutando de forma interactiva y no hay nada en STDIN, o si la variable de entorno PERL_MM_USE_DEFAULT está establecida en verdadero, el $default se usará sin hacer preguntas. Esto evita que los procesos automatizados se bloqueen esperando la entrada del usuario.

Si no se proporciona un $default se usará una cadena vacía en su lugar.

os_unsupported
os_unsupported();
os_unsupported if $^O eq 'MSWin32';

La función os_unsupported() proporciona una manera de salir correctamente de tu "Makefile.PL" antes de llamar a "WriteMakefile". Es esencialmente un "die" con el mensaje "OS unsupported".
