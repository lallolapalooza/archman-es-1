epoll_ctl(2) Manual de Llamadas al Sistema epoll_ctl(2)

NOMBRE

epoll_ctl - interfaz de control para un descriptor de archivo epoll

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <sys/epoll.h>
int epoll_ctl(int epfd, int op, int fd,
              struct epoll_event *_Nullable event);

DESCRIPCIÓN

Esta llamada al sistema se utiliza para añadir, modificar o eliminar entradas en la lista de intereses de la instancia epoll(7) referida por el descriptor de archivo epfd. Solicita que la operación op se realice para el descriptor de archivo de destino, fd.

Los valores válidos para el argumento op son:

EPOLL_CTL_ADD
Añade una entrada a la lista de intereses del descriptor de archivo epoll, epfd. La entrada incluye el descriptor de archivo, fd, una referencia a la descripción de archivo abierta correspondiente (véase epoll(7) y open(2)), y la configuración especificada en event.
EPOLL_CTL_MOD
Cambia la configuración asociada a fd en la lista de intereses a la nueva configuración especificada en event.
EPOLL_CTL_DEL
Elimina (desregistra) el descriptor de archivo de destino fd de la lista de intereses. El argumento event se ignora y puede ser NULL (pero véase ERRORES más abajo).

El argumento event describe el objeto enlazado al descriptor de archivo fd. La estructura struct epoll_event se describe en epoll_event(3type).

El miembro data de la estructura epoll_event especifica los datos que el kernel debe guardar y luego devolver (a través de epoll_wait(2)) cuando este descriptor de archivo esté listo.

El miembro events de la estructura epoll_event es una máscara de bits compuesta mediante OR de cero o más tipos de eventos, devueltos por epoll_wait(2), y banderas de entrada, que afectan su comportamiento, pero no se devuelven. Los tipos de eventos disponibles son:

EPOLLIN
El archivo asociado está disponible para operaciones de read(2).
EPOLLOUT
El archivo asociado está disponible para operaciones de write(2).
EPOLLRDHUP (desde Linux 2.6.17)
El par del socket de flujo cerró la conexión, o cerró la mitad de escritura de la conexión. (Esta bandera es especialmente útil para escribir código sencillo para detectar el cierre del par al usar monitorización con disparador de flanco.)
EPOLLPRI
Hay una condición excepcional en el descriptor de archivo. Véase la discusión de POLLPRI en poll(2).
EPOLLERR
Se produjo una condición de error en el descriptor de archivo asociado. Este evento también se informa para el extremo de escritura de una tubería cuando se ha cerrado el extremo de lectura.
epoll_wait(2) siempre informará de este evento; no es necesario establecerlo en events al llamar a epoll_ctl().
EPOLLHUP
Se produjo una desconexión en el descriptor de archivo asociado.
epoll_wait(2) siempre esperará este evento; no es necesario establecerlo en events al llamar a epoll_ctl().
Tenga en cuenta que al leer de un canal como una tubería o un socket de flujo, este evento simplemente indica que el par cerró su extremo del canal. Las lecturas posteriores del canal devolverán 0 (fin de archivo) solo después de que se hayan consumido todos los datos pendientes en el canal.

Y las banderas de entrada disponibles son:

EPOLLET
Solicita notificación con disparador de flanco para el descriptor de archivo asociado. El comportamiento por defecto para epoll es disparador de nivel. Véase epoll(7) para obtener información más detallada sobre la notificación con disparador de flanco y de nivel.
EPOLLONESHOT (desde Linux 2.6.2)
Solicita notificación de un solo disparo para el descriptor de archivo asociado. Esto significa que después de un evento notificado para el descriptor de archivo por epoll_wait(2), el descriptor de archivo se deshabilita en la lista de intereses y no se informarán otros eventos a través de la interfaz epoll. El usuario debe llamar a epoll_ctl() con EPOLL_CTL_MOD para reactivar el descriptor de archivo con una nueva máscara de eventos.
EPOLLWAKEUP (desde Linux 3.5)
Si EPOLLONESHOT y EPOLLET están desmarcados y el proceso tiene la capacidad CAP_BLOCK_SUSPEND, asegúrese de que el sistema no entre en estado de "suspensión" o "hibernación" mientras este evento esté pendiente o en proceso de serlo. El evento se considera "en proceso" desde el momento en que es devuelto por una llamada a epoll_wait(2) hasta la siguiente llamada a epoll_wait(2) en el mismo descriptor de archivo epoll(7), el cierre de ese descriptor de archivo, la eliminación del descriptor de archivo de evento con EPOLL_CTL_DEL, o la anulación de la selección de EPOLLWAKEUP para el descriptor de archivo de evento con EPOLL_CTL_MOD. Véase también ERRORES.
EPOLLEXCLUSIVE (desde Linux 4.5)
Establece un modo de despertar exclusivo para el descriptor de archivo epoll que se está adjuntando al descriptor de archivo de destino, fd. Cuando ocurre un evento de despertar y múltiples descriptores de archivo epoll están adjuntos al mismo destino de archivo usando EPOLLEXCLUSIVE, uno o más de los descriptores de archivo epoll recibirán un evento con epoll_wait(2). El comportamiento por defecto en este escenario (cuando EPOLLEXCLUSIVE no está establecido) es que todos los descriptores de archivo epoll reciban un evento. Por lo tanto, EPOLLEXCLUSIVE es útil para evitar problemas de "manada retumbante" en ciertos escenarios.
Si el mismo descriptor de archivo está en múltiples instancias epoll, algunas con la bandera EPOLLEXCLUSIVE y otras sin ella, entonces los eventos se proporcionarán a todas las instancias epoll que no especificaron EPOLLEXCLUSIVE, y al menos una de las instancias epoll que sí especificaron EPOLLEXCLUSIVE.
Los siguientes valores pueden especificarse junto con EPOLLEXCLUSIVE: EPOLLIN, EPOLLOUT, EPOLLWAKEUP y EPOLLET. EPOLLHUP y EPOLLERR también pueden especificarse, pero esto no es necesario: como de costumbre, estos eventos siempre se informan si ocurren, independientemente de si están especificados en events. Los intentos de especificar otros valores en events generan el error EINVAL.
EPOLLEXCLUSIVE solo puede usarse en una operación EPOLL_CTL_ADD; los intentos de emplearlo con EPOLL_CTL_MOD generan un error. Si EPOLLEXCLUSIVE se ha establecido usando epoll_ctl(), entonces una posterior EPOLL_CTL_MOD en el mismo par epfd, fd genera un error. Una llamada a epoll_ctl() que especifica EPOLLEXCLUSIVE en events y especifica el descriptor de archivo de destino fd como una instancia epoll también fallará. El error en todos estos casos es EINVAL.

VALOR DE RETORNO

Cuando tiene éxito, epoll_ctl() devuelve cero. Cuando ocurre un error, epoll_ctl() devuelve -1 y errno se establece para indicar el error.

Antes de Linux 2.6.9, la operación EPOLL_CTL_DEL requería un puntero no nulo en event, aunque este argumento se ignora. Desde Linux 2.6.9, event puede especificarse como NULL al usar EPOLL_CTL_DEL. Las aplicaciones que necesiten ser portables a kernels anteriores a Linux 2.6.9 deben especificar un puntero no nulo en event

.

Si EPOLLWAKEUP se especifica en flags, pero el llamador no tiene la capacidad CAP_BLOCK_SUSPEND, entonces el indicador EPOLLWAKEUP se ignora silenciosamente. Este comportamiento desafortunado es necesario porque no se realizaron comprobaciones de validez sobre el argumento flags en la implementación original, y la adición de la EPOLLWAKEUP con una comprobación que hacía fallar la llamada si el llamador no tenía la capacidad CAP_BLOCK_SUSPEND causó una rotura en al menos una aplicación de espacio de usuario existente que aleatoriamente (e inútilmente) especificaba este bit. Una aplicación robusta debe por lo tanto comprobar doblemente que tiene la capacidad CAP_BLOCK_SUSPEND si intenta usar el indicador E
