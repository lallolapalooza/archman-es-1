Módulos CMake Extra (ECM) proporciona varios módulos que ofrecen funciones útiles para scripts de CMake. ECM proporciona en realidad tres tipos de módulos que pueden usarse desde scripts de CMake: aquellos que extienden la funcionalidad del comando find_package se documentan en ecm-find-modules(7) <#manual:ecm-find-modules(7)>; aquellos que proporcionan configuraciones estándar para software producido por la comunidad KDE se documentan en ecm-kde-modules(7) <#manual:ecm-kde-modules(7)>. El resto proporcionan macros y funciones para uso general por scripts de CMake y se documentan

aquí.

Para usar estos módulos, necesitas decirle a CMake que encuentre el paquete ECM, y luego añadir ya sea ${ECM_MODULE_PATH} o ${ECM_MODULE_DIR} a la variable CMAKE_MODULE_PATH

:

QUIRED NO_MODULE) s
et(CMAKE_MODULE_PATH
${ECM_MODULE_DIR})

Usar ${ECM_MODULE_PATH} también hará que los módulos de búsqueda y los módulos KDE estén

disponibles.

Ten en cuenta que también hay módulos de toolchain, documentados en ecm-toolchains(7) <#manual:ecm-toolchains(7)>, pero estos son usados por usuarios

que compilan el software en lugar de desarro
lladores que escriben scripts de CMake.

ECMAddQch

Este módulo proporciona la función ecm_add_qch para generar archivos de documentación de API en formato QCH, y la función ecm_install_qch_export para generar e instalar objetivos de CMake exportados para dichos archivos QCH generados, con el fin de permitir la compilación de otro software con generación de QCH para crear enlaces a los archivos QCH dados.

ecm_add_qch(<nombre_objetivo>
    NOMBRE <nombre>
    VERSION <version>
    QCH_INSTALL_DESTINATION <ruta_instalacion_archivo_qch>
    TAGFILE_INSTALL_DESTINATION <ruta_instalacion_archivo_tags>
    [COMPONENT <componente>]
    [BASE_NAME <nombrebase>]
    [SOURCE_DIRS <dir> [<dir2> [...]]]
    [SOURCES <archivo> [<archivo2> [...]]]
    |MD_MAINPAGE <archivo_md>]
    [INCLUDE_DIRS <dir_inclusión> [<dir_inclusión2> [...]]]
    [IMAGE_DIRS <dir_imagen> [<dir_imagen2> [...]]]
    [EXAMPLE_DIRS <dir_ejemplo> [<dir_ejemplo2> [...]]]
    [ORG_DOMAIN <dominio>]
    [NAMESPACE <espacio_nombres>]
    [LINK_QCHS <qch> [<qch2> [...]]]
    [PREDEFINED_MACROS <macro[=contenido]> [<macro2[=contenido]> [...]]]
    [BLANK_MACROS <macro> [<macro2> [...]]]
    [CONFIG_TEMPLATE <archivo_plantilla_configuración>]
    [VERBOSE]
)

Esta macro agrega un objetivo llamado <nombre_objetivo> para la creación de un manual de documentación de API en formato QCH a partir de las fuentes dadas. Actualmente utiliza doxygen, las versiones futuras podrían permitir opcionalmente otras herramientas. Junto al archivo QCH, el objetivo generará un archivo de etiquetas de doxygen correspondiente, que permite crear enlaces desde otras documentaciones al archivo QCH generado.

Se recomienda hacer opcional el uso de esta macro, dependiendo la llamada a ecm_add_qch de una opción de CMake establecida, con un nombre como BUILD_QCH y siendo TRUE por defecto. Esto permitirá a los desarrolladores ahorrar recursos en los ciclos de desarrollo de código fuente normales estableciendo esta opción a FALSE.

La macro establecerá las propiedades del objetivo DOXYGEN_TAGFILE, QHP_NAMESPACE, QHP_NAMESPACE_VERSIONED, QHP_VIRTUALFOLDER y LINK_QCHS a los valores respectivos, para permitir que otro código acceda a ellos, por ejemplo, la macro ecm_install_qch_export. Para permitir el uso del objetivo <nombre_objetivo> como elemento para LINK_QCHS en posteriores llamadas a ecm_add_qch en la compilación actual, además se establece una propiedad de objetivo DOXYGEN_TAGFILE_BUILD, con la ruta del archivo de etiquetas de doxygen creado en el directorio de compilación. Si existe, ecm_add_qch utilizará esta propiedad en lugar de DOXYGEN_TAGFILE para acceder al archivo de etiquetas.

NOMBRE especifica el nombre de la documentación generada.

VERSION especifica la versión de la biblioteca para la cual se crea la documentación.

BASE_NAME especifica el nombre base para los archivos generados. El nombre base predeterminado es <nombre>.

SOURCE_DIRS especifica los directorios (incl. subdirectorios) con los archivos fuente para los que se debe generar la documentación de la API. Los directorios pueden ser relativos al directorio fuente actual. Las dependencias de los archivos en los directorios no se rastrean actualmente, aparte del argumento SOURCES. Por lo tanto, no lo use para fuentes generadas durante la compilación. Debe usarse cuando SOURCES o CONFIG_TEMPLATE no se utilizan.

SOURCES especifica los archivos fuente para los que se debe generar la documentación de la API. Debe usarse cuando SOURCE_DIRS o CONFIG_TEMPLATE no se utilizan.

MD_MAINPAGE especifica un archivo en formato Markdown que se utilizará como página principal. Esta página anulará cualquier comando \mainpage en las fuentes incluidas.

INCLUDE_DIRS especifica los directorios que se buscarán para cabeceras incluidas. Los directorios pueden ser relativos al directorio fuente actual. Desde 5.63.

IMAGE_DIRS especifica los directorios que contienen imágenes que se incluyen en la documentación. Los directorios pueden ser relativos al directorio fuente actual.

EXAMPLE_DIRS especifica los directorios que contienen ejemplos que se incluyen en la documentación. Los directorios pueden ser relativos al directorio fuente actual.

QCH_INSTALL_DESTINATION especifica dónde se instalará el archivo QCH generado.

TAGFILE_INSTALL_DESTINATION especifica dónde se instalará el archivo de etiquetas generado.

COMPONENT especifica el nombre del componente de instalación con el que se asocian las reglas de instalación para el archivo QCH y el archivo de etiquetas generados.

NAMESPACE se puede utilizar para establecer un espacio de nombres personalizado <espacio_nombres> del archivo QCH generado. El espacio de nombres se utiliza como ID único de QHelpEngine (cmp. https://doc.qt.io/qt-5/qthelpproject.html#namespace). El espacio de nombres predeterminado es <dominio>.<nombre>. Debe usarse cuando ORG_DOMAIN no se utiliza.

ORG_DOMAIN se puede utilizar para definir el prefijo del dominio de la organización para el espacio de nombres predeterminado del archivo QCH generado. Debe usarse cuando NAMESPACE no se utiliza.

LINK_QCHS especifica una lista de otros objetivos QCH que se utilizarán para crear referencias a la documentación de API del código en bibliotecas externas. Para cada objetivo <qch> en la lista, se espera que se definan las siguientes propiedades del objetivo: DOXYGEN_TAGFILE, QHP_NAMESPACE y QHP_VIRTUALFOLDER. Si alguna de estas no existe, se ignorará <qch>. Utilice la macro ecm_install_qch_export para exportar un objetivo con estas propiedades con la configuración de CMake de una biblioteca. Cualquier objetivo <qch> también puede ser uno creado anteriormente en el mismo sistema de compilación por otra llamada a ecm_add_qch.

PREDEFINED_MACROS especifica una lista de macros C/C++ que deben ser tratadas según lo dado por la herramienta de generación de documentación de API. Ejemplos son macros definidas solo en archivos generados, por lo que su definición podría no estar disponible para la herramienta.

BLANK_MACROS especifica una lista de nombres de macros C/C++ que deben ser ignorados por la herramienta de generación de documentación de API y tratadas como si se resolvieran a cadenas vacías. Ejemplos son macros de exportación definidas solo en archivos generados, por lo que su definición podría no estar disponible para la herramienta.

CONFIG_TEMPLATE especifica un archivo de plantilla de cmake personalizado para el archivo de configuración que se crea para controlar la ejecución de la herramienta de generación de documentación de API. Las siguientes variables de CMake deben utilizarse: - ECM_QCH_DOXYGEN_QHELPGENERATOR_EXECUTABLE - ECM_QCH_DOXYGEN_FILEPATH, ECM_QCH_DOXYGEN_TAGFILE Las siguientes variables de CMake se pueden utilizar: - ECM_QCH_DOXYGEN_PROJECTNAME - ECM_QCH_DOXYGEN_PROJECTVERSION - ECM_QCH_DOXYGEN_VIRTUALFOLDER - ECM_QCH_DOXYGEN_FULLNAMESPACE - ECM_QCH_DOXYGEN_TAGFILES - ECM_QCH_DOXYGEN_WARN_LOGFILE - ECM_QCH_DOXYGEN_QUIET No hay garantía de que las otras variables de CMake utilizadas actualmente en la plantilla de archivo predeterminada también estén presentes con la misma semántica en versiones futuras de esta macro.

VERBOSE indica a la herramienta de generación de documentación de API que sea más detallada sobre su actividad.

El archivo de configuración predeterminado para la herramienta de generación de documentación de API, es decir, el que se utiliza cuando no se usa CONFIG_TEMPLATE, permite al código manejar el caso de ser procesado por la herramienta definiendo la macro preprocesador C/C++ K_DOXYGEN cuando se ejecuta (desde v5.67.0). Para compatibilidad con versiones anteriores, también se establece la definición DOXYGEN_SHOULD_SKIP_THIS, pero su uso está obsoleto.

Ejemplo de uso:

ecm_add_qch(
    MyLib_QCH
    NAME MyLib
    VERSION "0.42.0"
    ORG_DOMAIN org.myorg
    SOURCE_DIRS
        src
    LINK_QCHS
        Qt5Core_QCH
        Qt5Xml_QCH
        Qt5Gui_QCH
        Qt5Widgets_QCH
    BLANK_MACROS
        MyLib_EXPORT
        MyLib_DEPRECATED
    TAGFILE_INSTALL_DESTINATION ${CMAKE_INSTALL_PREFIX}/share/docs/tags
    QCH_INSTALL_DESTINATION ${CMAKE_INSTALL_PREFIX}/share/docs/qch
    COMPONENT Devel
)

ecm_install_qch_export(
    TARGETS [<nombre> [<nombre2> [...]]]
    FILE <archivo>
    DESTINATION <destino>
    [COMPONENT <componente>]
)

Esta macro crea e instala un archivo CMake <archivo> que exporta los objetivos QCH dados <nombre>, etc., para que puedan ser recogidos por compilaciones basadas en CMake de otro software que también genere archivos QCH (usando ecm_add_qch) y que deba incluir enlaces a los archivos QCH creados por los objetivos dados. Se espera que el archivo CMake instalado <archivo> sea incluido por el archivo de configuración de CMake creado para el software que los archivos QCH relacionados documentan.

TARGETS especifica los objetivos QCH que deben ser exportados. Si un objetivo no existe o no tiene todas las propiedades necesarias, se generará una advertencia y el objetivo se omitirá. Este comportamiento podría cambiar en versiones futuras para resultar en un error en su lugar.

FILE especifica el nombre del archivo CMake creado, típicamente con una extensión .cmake.

DESTINATION especifica el directorio en el disco al que se instalará el archivo. Normalmente es el mismo que donde se instalan los archivos de configuración de CMake para este software.

COMPONENT especifica el nombre del componente de instalación con el que se asocia la regla de instalación.

Ejemplo de uso:

ecm_install_qch_export(
    TARGETS MyLib_QCH
    FILE MyLibQCHTargets.cmake
    DESTINATION "${CMAKE_INSTALL_PREFIX}/lib/cmake/MyLib"
    COMPONENT Devel
)

Este módulo proporciona las macros ecm_add_version_tools y ecm_add_version_files.

La macro ecm_add_version_tools genera un objetivo de compilación que crea un archivo de versión (`version.h`) para el proyecto.

ecm_qt_3d_quick(<nombre_objetivo>
    [SOURCE_DIRS <dirs> [...]]
    [INSTALL_DIR <ruta_instalacion>]
    [COMPONENT <componente>]
)

La macro crea un objetivo de compilación llamado <nombre_objetivo> que instala los archivos necesarios para Qt 3D Quick.

SOURCE_DIRS son los directorios que contienen los archivos fuente de Qt 3D Quick. Por defecto, es `src`.

INSTALL_DIR es el directorio donde se instalarán los archivos. Por defecto, es `${CMAKE_INSTALL_LIBDIR}/qt5/3dquick`.

COMPONENT es el nombre del componente de instalación asociado.

Ejemplo de uso:

ecm_qt_3d_quick(
    qt_3d_quick_install
    SOURCE_DIRS src/3dquick
    INSTALL_DIR ${CMAKE_INSTALL_LIBDIR}/qt5/3dquick
    COMPONENT Runtime
)

NAME

ecm-modules — modules for Extra CMake Modules

INTRODUCTION

Extra CMake Modules (ECM) is a collection of CMake modules that simplify the process of writing CMake build scripts for KDE/Qt projects.

This document describes the modules that are typically included.

ALL MODULES

ECMAddDerivedTarget

Add a target that derives from another target.

This module is used for adding derived targets like data, docs, etc.

ecm_add_derived_target(<name> <target>
                       TYPE <type> [DEPENDS <dep> ...]
                       [COMMAND <command> ...]
                       [INSTALL_DESTINATION <dir>]
                       [INCLUDES_SUBDIR <dir>])

This macro is intended to add a target to your project that derives from an already existing target (e.g. a library or an executable). The target is added to the destination directory specified by INSTALL_DESTINATION.

The TYPE can be one of the following:

data
Adds a target that installs data files. The files in <target> are installed into ${CMAKE_INSTALL_DATADIR}/<name>.
docs
Adds a target that installs documentation files. The files in <target> are installed into ${CMAKE_INSTALL_DOCDIR}/<name>.
autostart
Adds a target that installs Freedesktop autostart files. The files in <target> are installed into ${CMAKE_INSTALL_AUTOSARTDIR}/<name>.
icons
Adds a target that installs icon files. The files in <target> are installed into ${CMAKE_INSTALL_ICONDIR}/<name>.
desktop
Adds a target that installs Freedesktop desktop files. The files in <target> are installed into ${CMAKE_INSTALL_DESKTOPDIR}/<name>.

The DEPENDS keyword adds dependencies to the new target. The COMMAND keyword can be used to specify commands that are executed when the target is built.

The INCLUDES_SUBDIR keyword is used to specify a subdirectory that will be included by the installation target. This is useful for installing sets of files that are expected to be included by other components.

Example:

add_library(myplugin plugin.cpp)
ecm_add_derived_target(myplugin_data myplugin TYPE data
                       INSTALL_DESTINATION share/myplugin
                       INCLUDES_SUBDIR share/myplugin)

The check is performed by looking for common version control system directories (like .git, .svn) in the source tree.

Example:

find_package(ECM REQUIRED)
if(ECM_SOURCE_UNDER_VERSION_CONTROL)
  message(STATUS "Source is under version control.")
else()
  message(STATUS "Source is NOT under version control.")
endif()

ECMUninstallTarget

Add an uninstall target.

By including this module, an uninstall target will be added to your CMake project. This will remove all files installed (or updated) by a previous invocation of the install target. It will not remove files created or modified by an install(SCRIPT) or install(CODE) command; you should create a custom uninstallation target for these and use add_dependency to make the uninstall target depend on it:

include(ECMUninstallTarget)
install(SCRIPT install-foo.cmake)
add_custom_target(uninstall_foo COMMAND ${CMAKE_COMMAND} -P uninstall-foo.cmake)
add_dependency(uninstall uninstall_foo)

The target will fail if the install target has not yet been run (so it is not possible to run CMake on the project and then immediately run the uninstall target).

Warning:

CMake deliberately does not provide an uninstall target by default on the basis that such a target has the potential to remove important files from a user’s computer. Use with caution.

Since 1.7.0.

ECMUseFindModules

Selectively use some of the find modules provided by extra-cmake-modules.

This module is automatically available once extra-cmake-modules has been found, so it is not necessary to include(ECMUseFindModules) explicitly.

ecm_use_find_modules(DIR <dir>
                     MODULES module1.cmake [module2.cmake [...]]
                     [NO_OVERRIDE])

This allows selective use of the find modules provided by ECM, including deferring to CMake’s versions of those modules if it has them. Rather than adding ${ECM_FIND_MODULE_DIR} to CMAKE_MODULE_PATH, you use ecm_use_find_modules() to copy the modules you want to a local (build) directory, and add that to CMAKE_MODULE_PATH.

The find modules given to MODULES will be copied to the directory given by DIR (which should be located in ${CMAKE_BINARY_DIR} and added to CMAKE_MODULE_PATH). If NO_OVERRIDE is given, only modules not also provided by CMake will be copied.

Example:

find_package(ECM REQUIRED)
ecm_use_find_modules(
    DIR ${CMAKE_BINARY_DIR}/cmake
    MODULES FindEGL.cmake
    NO_OVERRIDE
)
set(CMAKE_MODULE_PATH ${CMAKE_BINARY_DIR}/cmake)

This example will make FindEGL.cmake available in your project, but only as long as it is not yet part of CMake. Calls to find_package(EGL) will then make use of this copied module (or the CMake module if it exists).

Another possible use for this macro is to take copies of find modules that can be installed along with config files if they are required as a dependency (for example, if targets provided by the find module are in the link interface of a library).

Since pre-1.0.0.

ECMWinResolveSymlinks

Resolve pseudo-symlinks created by git when cloning on Windows.

ecm_win_resolve_symlinks(<dir>)

When git checks out a repository with UNIX symlinks on Windows machine, it creates a text file for each symlink, containing a relative path to the real file. This function would recursively walk over specified directory and replace pseudo-symlinks with corresponding real file’s contents. It would then run git update-index --assume-unchanged on them to trick git.

This is useful for projects like “breeze-icons” that contain many identical icons implemented as symlinks.

Since 5.28

QtVersionOption

Adds a build option to select the major Qt version if necessary, that is, if the major Qt version has not yet been determined otherwise (e.g. by a corresponding find_package() call). This module is typically included by other modules requiring knowledge about the major Qt version.

If the ECM version passed to find_package was at least 5.240.0 Qt6 is picked by default. Otherwise Qt5 is picked.

QT_MAJOR_VERSION is defined to either be “5” or “6”.
