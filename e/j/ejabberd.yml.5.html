NOMBRE

ejabberd.yml - archivo de configuración principal de ejabberd.

SINOPSIS

ejabberd.yml

DESCRIPCIÓN

El archivo de configuración está escrito en lenguaje YAML.


Advertencia

YAML es sensible a la indentación, así que asegúrate de respetarla, o de lo contrario obtendrás errores de configuración bastante crípticos.

Lógicamente, las opciones de configuración se dividen en 3 categorías principales: Módulos, Listeners y todo lo demás llamado opciones de Nivel Superior. Por lo tanto, este documento se divide en 3 capítulos principales que describen cada categoría por separado. Así, el contenido de ejabberd.yml típicamente se verá así:

hosts:
  - example.com
  - domain.tld
loglevel: info
...
listen:
  -
    port: 5222
    module: ejabberd_c2s
  ...
modules:
  mod_roster: {}
  ...

Cualquier error de configuración (como error de sintaxis, opción desconocida o valor de opción inválido) es fatal en el sentido de que ejabberd se negará a cargar todo el archivo de configuración y no se iniciará o abortará la recarga de configuración.

Todas las opciones se pueden cambiar en tiempo de ejecución ejecutando el comando ejabberdctl reload-config. La recarga de configuración es atómica: o todas las opciones son aceptadas y aplicadas simultáneamente o la nueva configuración es rechazada sin ningún impacto en la configuración actualmente en ejecución.

Algunas opciones se pueden especificar solo para host(s) virtual(es) particular(es) usando las opciones host_config o append_host_config. Dichas opciones se llaman locales. Los ejemplos son modules, auth_method y default_db. Las opciones que no se pueden definir por host virtual se llaman globales. Los ejemplos son loglevel, certfiles y listen. Es un error de configuración poner opciones globales bajo la sección host_config o append_host_config; ejabberd se negará a cargar dicha configuración.

No se recomienda escribir ejabberd.yml desde cero. En su lugar, es mejor comenzar con el archivo de configuración "predeterminado" disponible en https://github.com/processone/ejabberd/blob/25.10/ejabberd.yml.example. Una vez que tengas ejabberd funcionando, puedes comenzar a cambiar las opciones de configuración para cumplir tus requisitos.

Ten en cuenta que este documento tiene como objetivo proporcionar una descripción completa de todas las opciones de configuración que se pueden consultar para comprender el significado de una opción particular, su formato y sus posibles valores. Será bastante difícil entender cómo configurar ejabberd leyendo solo este documento; para ello, se recomienda al lector que consulte la Guía de Configuración en línea disponible en https://docs.ejabberd.im/admin/configuration.

OPCIONES DE NIVEL SUPERIOR

Esta sección describe las opciones de nivel superior de ejabberd 25.10. Las opciones que cambiaron en esta versión están marcadas con 🟤.

access_rules: {NombreAcceso: {allow|deny: NombreACL|DefinicionACL}}

Esta opción define las reglas de acceso. A cada regla de acceso se le asigna un nombre que se puede referenciar desde otras partes del archivo de configuración (principalmente desde las opciones access de los módulos de ejabberd). Cada definición de regla puede contener un número arbitrario de secciones allow o deny, y cada sección puede contener cualquier número de reglas ACL (ver la opción acl). No hay reglas de acceso definidas por defecto.

Ejemplo:

access_rules:
  configure:
    allow: admin
  something:
    deny: someone
    allow: all
  s2s_banned:
    deny: problematic_hosts
    deny: banned_forever
    deny:
      ip: 222.111.222.111/32
    deny:
      ip: 111.222.111.222/32
    allow: all
  xmlrpc_access:
    allow:
      user: peter@example.com
    allow:
      user: ivone@example.com
    allow:
      user: bot@example.com
      ip: 10.0.0.0/24

acl: {NombreACL: {TipoACL: ValorACL}}

Esta opción define las listas de control de acceso: conjuntos de reglas con nombre que se utilizan para hacer coincidir diferentes objetivos (como un JID o una dirección IP). Cada conjunto de reglas tiene un nombre NombreACL: puede ser cualquier cadena excepto all o none (esos son nombres predefinidos para las reglas que coinciden con todo o nada respectivamente). El nombre NombreACL puede ser referenciado desde otras partes del archivo de configuración, por ejemplo, en la opción access_rules. Las reglas de NombreACL se representan mediante un mapeo {TipoACL: ValorACL}. Estos pueden ser uno de los siguientes:

ip: Network

La regla coincide con cualquier dirección IP de la Network.

node_glob: Pattern

Igual que node_regexp, pero la coincidencia se realiza en un Pattern especificado según las reglas utilizadas por el shell de Unix.

node_regexp: user_regexp@server_regexp

La regla coincide con cualquier JID cuya parte de nodo coincida con la expresión regular user_regexp y cuya parte de servidor coincida con la expresión regular server_regexp.

resource: Resource

La regla coincide con cualquier JID que tenga un recurso Resource.

resource_glob: Pattern

Igual que resource_regexp, pero la coincidencia se realiza en un Pattern especificado según las reglas utilizadas por el shell de Unix.

resource_regexp: Regexp

La regla coincide con cualquier JID cuyo recurso coincida con la expresión regular Regexp.

server: Server

La regla coincide con cualquier JID del servidor Server. El valor de Server debe ser un nombre de host válido o una dirección IP.

server_glob: Pattern

Igual que server_regexp, pero la coincidencia se realiza en un Pattern especificado según las reglas utilizadas por el shell de Unix.

server_regexp: Regexp

La regla coincide con cualquier JID del servidor que coincida con la expresión regular Regexp.

user: Username

Si Username tiene el formato "user@server", la regla coincide con un JID contra este valor. De lo contrario, si Username tiene el formato "user", la regla coincide con cualquier JID que tenga Username en la parte del nodo, siempre que la parte del servidor de este JID sea cualquiera de los hosts virtuales servidos por ejabberd.

user_glob: Pattern

Igual que user_regexp, pero la coincidencia se realiza en un Pattern especificado según las reglas utilizadas por el shell de Unix.

user_regexp: Regexp

Si Regexp tiene el formato "regexp@server", la regla coincide con cualquier JID cuya parte de nodo coincida con la expresión regular "regexp" siempre que la parte del servidor de este JID sea igual a "server". Si Regexp tiene el formato "regexp", la regla coincide con cualquier JID cuya parte de nodo coincida con la expresión regular "regexp" siempre que la parte del servidor de este JID sea cualquiera de los hosts virtuales servidos por ejabberd.

acme: Opciones

Configuración de ACME, para obtener automáticamente certificados SSL para los dominios servidos por ejabberd, lo que significa que las solicitudes y renovaciones de certificados se realizan a algún servidor CA (también conocido como "servidor ACME") de forma totalmente automática. Las Opciones son:

auto: true | false

Indica si se deben solicitar automáticamente certificados para todos los dominios configurados (que aún no tienen certificado) al arrancar el servidor o al recargar la configuración. El valor predeterminado es true.

ca_url: URL

La URL del directorio ACME que se utiliza como punto de entrada para el servidor ACME. El valor predeterminado es https://acme-v02.api.letsencrypt.org/directory, la URL del directorio de la autoridad Let’s Encrypt.

cert_type: rsa | ec

Un tipo de clave de certificado. Los valores disponibles son ec y rsa para certificados EC y RSA respectivamente. Es mejor tener certificados RSA para la compatibilidad con clientes y servidores antiguos, por lo que el valor predeterminado es rsa.

certfiles: [Path, ...]

The option accepts a list of file paths (optionally with wildcards) containing either PEM certificates or PEM private keys. At startup or configuration reload, ejabberd reads all certificates from these files, sorts them, removes duplicates, finds matching private keys and then rebuilds full certificate chains for the use in TLS connections. Use this option when TLS is enabled in either of ejabberd listeners: ejabberd_c2s, ejabberd_http and so on. NOTE: if you modify the certificate files or change the value of the option, run ejabberdctl reload-config in order to rebuild and reload the certificate chains.

Examples:

If you use Let’s Encrypt certificates for your domain "domain.tld", the configuration will look like this:

certfiles:
  - /etc/letsencrypt/live/domain.tld/fullchain.pem
  - /etc/letsencrypt/live/domain.tld/privkey.pem

disable_sasl_mechanisms: [Mechanism, ...]

Specify a list of SASL mechanisms (such as DIGEST-MD5 or SCRAM-SHA1) that should not be offered to the client. For convenience, the value of Mechanism is case-insensitive. The default value is an empty list, i.e. no mechanisms are disabled by default.

disable_sasl_scram_downgrade_protection: true | false

Allows to disable sending data required by XEP-0474: SASL SCRAM Downgrade Protection. There are known buggy clients (like those that use strophejs 1.6.2) which will not be able to authenticatate when servers sends data from that specification. This options allows server to disable it to allow even buggy clients connects, but in exchange decrease MITM protection. The default value of this option is false which enables this extension.

mod_antispam

Nota sobre esta opción: añadida en 25.07.

Filtra mensajes de spam y solicitudes de suscripción recibidas de servidores remotos basándose en listas de bloqueo en tiempo real (RTBL), listas de JIDs de spammers conocidos y/o URLs mencionadas en mensajes de spam. Regla de acceso que controla qué cuentas pueden recibir mensajes de spam. Si la regla devuelve allow para un destinatario dado, los mensajes de spam no se rechazan para ese destinatario. mod_muc

Este módulo proporciona soporte para XEP-0045: Multi-User Chat. Los usuarios pueden descubrir salas existentes, unirse o crearlas. Los ocupantes de una sala pueden chatear públicamente o tener chats privados.

El servicio MUC permite que cualquier ID de Jabber registre un apodo, de modo que nadie más pueda usar ese apodo en ninguna sala del servicio MUC. Para registrar un apodo, abre Service Discovery en tu cliente XMPP y regístrate en el servicio MUC.

También es posible registrar un apodo en una sala, de modo que nadie más pueda usar ese apodo en esa sala. Si un apodo está registrado en el servicio MUC, ese apodo no puede ser registrado en ninguna sala, y viceversa: un apodo registrado en una sala no puede ser registrado en el servicio MUC.

Este módulo soporta clustering y balanceo de carga. Se puede iniciar un módulo por nodo del clúster. Las salas se distribuyen en el momento de la creación a todas las instancias disponibles del módulo MUC. El módulo de chat multiusuario está en clúster, pero las salas en sí no están en clúster ni son tolerantes a fallos: si el nodo que gestiona un conjunto de salas deja de funcionar, las salas desaparecen y se recrearán en un nodo disponible al primer intento de conexión.

Los administradores pueden enviar un mensaje de chat grupal al JID de una sala activa, y el mensaje se mostrará en la sala como un mensaje del servicio.

mod_stream_mgmt

Este módulo añade soporte para XEP-0198: Stream Management. Este protocolo permite la gestión activa de un stream XML entre dos entidades XMPP, incluyendo características para acuses de recibo de stanza y reanudación de stream.

Opciones disponibles:

ack_timeout: timeout()

Tiempo de espera para los acuses de recibo de stanza. Establecerlo a infinity deshabilita efectivamente el tiempo de espera. El valor por defecto es 1 minuto.

cache_life_time: timeout()

Igual que la opción de nivel superior cache_life_time, pero aplicada solo a este módulo. El valor por defecto es 48 horas.

cache_size: pos_integer() | infinity

Igual que la opción de nivel superior cache_size, pero aplicada solo a este módulo.

max_ack_queue: Size

Esta opción especifica el número máximo de stanzas no acusadas en cola para posible retransmisión. Cuando se excede el límite, la sesión del cliente se termina. Los valores permitidos son enteros positivos e infinity. Debes tener cuidado al establecer este valor, ya que no debe ser demasiado bajo, de lo contrario, podrías terminar sesiones en un bucle, antes de que tengan la oportunidad de finalizar la iniciación correcta de la sesión. Definitivamente debería establecerse más alto que el tamaño de la cola offline (por ejemplo, al menos 3 veces el valor de la cola offline máxima y nunca menor que 1000). El valor por defecto es 5000.

max_resume_timeout: timeout()

Un cliente puede especificar el período de tiempo hasta que una sesión expire si se pierde la conexión. Durante este período de tiempo, el cliente puede reanudar su sesión. Esta opción limita el período de tiempo que se permite solicitar al cliente. Debe establecerse a un tiempo de espera igual o mayor que el resume_timeout por defecto. Por defecto, se establece al mismo valor que la opción resume_timeout.

queue_type: ram | file

Igual que la opción de nivel superior queue_type, pero aplicada solo a este módulo.

resend_on_timeout: true | false | if_offline

Si esta opción se establece en true, cualquier stanza de mensaje que no haya sido acusada por el cliente será reenviada al expirar la sesión. Este comportamiento podría ser deseable a menudo, pero podría tener resultados inesperados bajo ciertas circunstancias. Por ejemplo, un mensaje enviado a dos recursos podría ser reenviado a uno de ellos si el otro expiró. Por lo tanto, el valor por defecto para esta opción es false, que indica a ejabberd que genere un mensaje de error en su lugar. Alternativamente, la opción puede establecerse en if_offline. En este caso, los mensajes no acusados se reenviarán solo si ningún otro recurso está en línea cuando expira la sesión. De lo contrario, se generarán mensajes de error.

resume_timeout: timeout()

Esta opción configura el período de tiempo (por defecto) hasta que una sesión expire si se pierde la conexión. Durante este período de tiempo, un cliente puede reanudar su sesión. Ten en cuenta que el cliente puede solicitar un valor de tiempo de espera diferente, consulta la opción max_resume_timeout. Establecerlo a 0 deshabilita efectivamente la reanudación de sesión. El valor por defecto es 5 minutos.

mod_stun_disco

Nota sobre esta opción: añadida en 20.04.

Este módulo permite a los clientes XMPP descubrir servicios STUN/TURN y obtener credenciales temporales para usarlos según XEP-0215: External Service Discovery.

Opciones disponibles:

access: AccessName

Esta opción define qué regla de acceso se utilizará para controlar quién tiene permitido descubrir servicios STUN/TURN y solicitar credenciales temporales. El valor por defecto es local.

credentials_lifetime: timeout()

La vida útil de las credenciales temporales ofrecidas a los clientes. Si se utiliza el servicio TURN integrado de ejabberd, los relés TURN asignados usando credenciales temporales se terminarán poco después de que expiren las credenciales. El valor por defecto es 12 horas. Ten en cuenta que reiniciar el nodo ejabberd invalida cualquier credencial temporal ofrecida antes del reinicio a menos que se especifique un secret (ver abajo).

offer_local_services: true | false

Esta opción especifica si los servicios STUN/TURN locales configurados como listeners de ejabberd se anunciarán automáticamente. Ten en cuenta que esto no incluirá servicios habilitados para TLS, que deben configurarse manualmente usando la opción services (ver abajo). Para servicios TURN no anónimos, se ofrecerán credenciales temporales al cliente. El valor por defecto es true.

secret: Text

El secreto utilizado para generar credenciales temporales. Si esta opción no se especifica, se generará un secreto automáticamente. Sin embargo, se debe especificar explícitamente un secreto si se configuran servicios TURN no anónimos en otros nodos ejabberd y/o servicios TURN externos. Ten también en cuenta que los secretos generados automáticamente se pierden cuando se reinicia el nodo, lo que invalida cualquier credencial ofrecida antes del reinicio. Por lo tanto, se recomienda especificar explícitamente un secreto si los clientes almacenan en caché las credenciales recuperadas (para uso posterior) a través de reinicios del servicio.

services: [Service, ...]

La lista de servicios ofrecidos a los clientes. Esta lista puede incluir servicios STUN/TURN que se ejecutan en cualquier nodo ejabberd y/o servicios externos. Sin embargo, si algún servicio TURN listado que no se ejecuta en el nodo ejabberd local requiere autenticación, se debe especificar explícitamente un secret, y debe ser compartido con ese servicio. Esto solo funcionará con el servidor STUN/TURN integrado de ejabberd y con servidores externos que admitan la misma API REST para Acceso a Servicios TURN. A menos que offer_local_services se establezca en false, los servicios listados explícitamente se ofrecerán además de los anunciados automáticamente.

host: Host

El nombre de host o dirección IP en la que el servicio STUN/TURN está escuchando. Para servicios que no son TLS, se recomienda especificar una dirección IP (para evitar latencia adicional de búsqueda DNS en el lado del cliente). Para servicios TLS, el nombre de host (o dirección IP) debe coincidir con el certificado. Especificar la opción host es obligatorio.

port: 1..65535

El número de puerto en el que el servicio STUN/TURN está escuchando. El número de puerto por defecto es 3478 para servicios que no son TLS y 5349 para servicios TLS.

restricted: true | false

Esta opción determina si se ofrecen credenciales temporales para acceder al servicio. El valor por defecto es false para servicios STUN/STUNS y true para servicios TURN/TURNS.

transport: tcp | udp

El protocolo de transporte admitido por el servicio. El valor por defecto es udp para servicios que no son TLS y tcp para servicios TLS.

type: stun | turn | stuns | turns

El tipo de servicio. Debe ser stun o turn para servicios que no son TLS, stuns o turns para servicios TLS. El tipo por defecto es stun.

Example:

  -
    host: 203.0.113.3
    port: 3478

    transport: udp
    restricted: false
  -
    host: 203.0.113.3
    port: 3478
    type: turn
    transport: udp
    restricted: true
  -
    host: 2001:db8::3
    port: 3478
    type: stun
    transport: udp
    restricted: false
  -
    host: 2001:db8::3
    port: 3478
    type: turn
    transport: udp
    restricted: true
  -
    host: server.example.com
    port: 5349
    type: turns
    transport: tcp

mod_vcard_xupdat

e

El cliente del usuario puede almacenar un avatar en el vCard del usuario. El protocolo de Avatares basados en vCard (XEP-0153) proporciona un método para que los clientes informen a los contactos cuál es el valor hash del avatar. Sin embargo, clientes simples o pequeños pueden no implementar ese

protocolo.

Si este módulo está habilitado, todas las estanzas de presencia salientes del cliente obtienen automáticamente el hash del avatar en nombre del cliente. Así, los contactos reciben las estanzas de presencia con el Update Data descrito en XEP-0153 como si el cliente lo hubiera insertado él mismo. Si el cliente ya había incluido dicho elemento en la estanza de presencia, es reemplazado con el elemento generado por

ejabberd.

Al habilitar este módulo, cada modificación de vCard produce un recálculo del hash, y cada presencia enviada por un cliente produce la recuperación del hash y la reescritura de la estanza de presencia. Por esta razón, habilitar este módulo introducirá una sobrecarga computacional en servidores con clientes que cambian frecuentemente su presencia. Sin embargo, la sobrecarga se reduce significativamente con el uso de caché, así que probablemente no quieras establecer use_cache a false
