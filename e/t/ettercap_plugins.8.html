DESCRIPCIÓ

N

Ettercap(8) soporta módulos cargables en tiempo de ejecución. Se llaman plugins y vienen incluidos en el tarball de código fuente. Se compilan automáticamente si tu sistema los soporta o hasta que especifiques la opción -DENABLE_PLUGINS=OFF al script de configuración de cmake.
Algunos de los plugins más antiguos de ettercap (roper, banshee, etc.) no han sido portados a la nueva versión. Por cierto, puedes lograr los mismos resultados usando el nuevo motor de filtrado.
Si usas el modo interactivo, la mayoría de los plugins necesitan "Start Sniff" antes de

usarlos.
Para obtener una lista de los plugins instalados en tu sistema, ejecuta este
comando:

ette

rcap
-P
list

La siguiente es una lista de los plugins

disponibles:

chk_pois
on

Realiza una comprobación para ver si el módulo de envenenamiento arp de ettercap tuvo éxito. Envía paquetes ICMP echo falsificados a todas las víctimas del envenenamiento, haciéndose pasar por cada uno de los otros objetivos. Si podemos capturar una respuesta ICMP con nuestra dirección MAC como destino, significa que el envenenamiento entre esos dos objetivos es exitoso. Comprueba ambos sentidos de cada comunicación. Este plugin solo tiene sentido donde el envenenamiento tiene sentido. La prueba falla si especificas solo un objetivo en modo silencioso. No puedes ejecutar este plugin desde la línea de comandos porque el proceso de envenenamiento aún no ha comenzado. Debes lanzarlo desde el

menú
adecuado.
dns_spo
of

Este plugin intercepta consultas DNS y responde con una respuesta falsificada. Puedes elegir a qué direcciones debe responder el plugin, y el tiempo de expiración en segundos (TTL) modificando el archivo etter.dns. El plugin intercepta solicitudes A, AAAA, PTR, MX, WINS, SRV y TXT. Si era una solicitud A, el nombre se busca en el archivo y se devuelve la dirección IP (puedes usar comodines en el nombre).
Lo mismo aplica si era una solicitud

AAAA.

TTL es un campo opcional que se especifica como la última opción en una entrada del archivo etter.dns. El TTL se especifica en un número de segundos de 0 a 2^31-1 (ver RFC 2181). El TTL se especifica por host. Si el TTL no se especifica para un host en particular, el valor por defecto es 3600 segundos (1

hora).

Si era una solicitud PTR, la dirección IP se busca en el archivo y se devuelve el nombre (excepto para aquellos nombres que contengan un comodín). Para solicitudes PTR, se soportan direcciones IPv4 o

IPv6.

En caso de una solicitud MX, se crea una respuesta especial. El host se resuelve con un host falso 'mail.host' y el registro adicional contiene la dirección IP de 'mail.host'. Se devuelve la primera dirección que coincida, así que ten cuidado con el orden. La dirección IP para solicitudes MX puede ser una dirección IPv4 o una

IPv6.

Si la solicitud era una solicitud WINS, el nombre se busca en el archivo y se devuelve la dirección

IP.

En caso de una solicitud SRV, se crea una respuesta especial. El host se resuelve con un host falso 'srv.host' y el registro adicional contiene la dirección IP de 'srv.host'. La dirección IP para solicitudes SRV puede ser una dirección IPv4 o una

IPv6.

En caso de una solicitud TXT, se devuelve la cadena definida. La cadena debe estar entre comillas dobles. También se pueden usar comodines para el nombre

solicitado.

Se puede falsificar una respuesta especial para solicitudes A o AAAA, si se especifica la 'dirección indefinida' como la dirección IP en el archivo. Entonces el cliente recibe una respuesta que detiene el procesamiento de resolución inmediatamente. De esta manera se puede controlar qué familia de direcciones se está usando para acceder a un host

dual-stack.

En el caso de una solicitud ANY, se devuelven en la respuesta todos los resultados coincidentes de tipo A, AAAA, MX y TXT. Si la 'dirección indefinida' para registros A o AAAA está definida, no se devuelve nada para estos tipos, ya sea que el nombre

coincida o
no.
mdns_spo
of

Este plugin hace lo mismo que el plugin dns_spoof descrito arriba, a pesar de que escucha consultas mDNS (Multicast DNS) en el puerto UDP 5353. Para elegir a qué dirección debe responder el plugin, tienes que modificar un archivo diferente llamado etter.mdns. Debido a la naturaleza de mDNS, el plugin intercepta solo solicitudes A, AAAA, PTR

y SRV.

La forma en que el plugin mdns_spoof interpreta el archivo etter.mdns y las reglas que aplican son las mismas que con el plugin dns_spoof, aunque actualmente el plugin mdns_spoof carece de soporte para TTL personalizado. El TTL para todas las respuestas mDNS falsificadas es de 3600

segundos (1 hora)
.
dos_atta
ck

Este plugin ejecuta un ataque d.o.s. contra una dirección IP víctima. Primero "escanea" a la víctima para encontrar puertos abiertos, luego comienza a inundar estos puertos con paquetes SYN, usando una dirección "fantasma" como IP de origen. Luego usa respuestas ARP falsas para interceptar paquetes destinados al host fantasma. Cuando recibe un SYN-ACK de la víctima, responde con un paquete ACK creando una conexión ESTABLISHED. Tienes que usar una dirección IP libre en tu subred para crear el host "fantasma" (puedes usar find_ip para este propósito). No puedes ejecutar este plugin en modo unoffensive.
Este plugin está basado en el ataque DoS original Naptha (http://razor.bindview.com/publish/advisor

ies/adv_NAPTHA.html)

-TQP do

gre_rel
ay

Este plugin se puede usar para rastrear tráfico remoto redirigido por GRE. La idea básica es crear un túnel GRE que envíe todo el tráfico de una interfaz de enrutador a la máquina ettercap. El plugin enviará de vuelta los paquetes GRE al enrutador, después de la "manipulación" de ettercap (puedes usar plugins "activos" como smb_down, descifrado ssh, filtros, etc... en el tráfico redirigido). Necesita un host "falso" al que redirigir el tráfico (para evitar las respuestas del kernel). La IP "falsa" será el punto final del túnel. El plugin gre_relay se hará pasar por el host "falso". Para encontrar una dirección IP no utilizada para el host "falso" puedes usar el plugin find_ip. Basado en la técnica original Tunnelx de Anthony C. Zboralski (http://www.phrack.org/ar

chives/issues
/56/10.txt).

repoison_a

Solicita paquetes de envenenamiento después de solicitudes ARP de broadcast (o respuestas) de un host envenenado. Por ejemplo: estamos envenenando Grupo1 haciéndonos pasar por Host2. Si Host2 hace una solicitud ARP de broadcast para Host3, es posible que Grupo1 almacene en caché la dirección MAC correcta para Host2 contenida en el paquete ARP. Este plugin vuelve a envenenar la caché de Grupo1 inmediatamente después de una solicitud ARP de broadcast (o respuesta) legítima.
Este plugin es efectivo solo durante una sesión de envenenamiento arp.
En conjunto con el plugin reply_arp, repoison_arp es un buen soporte para el método estándar de mitm por envenenamiento

arp.

scan_poison
er

Verifica si alguien está envenenando entre algunos hosts de la lista y nosotros. Primero de todo verifica si dos hosts en la lista tienen la misma dirección mac. Podría significar que uno de ellos nos está envenenando pretendiendo ser el otro. Podría generar muchos falsos positivos en un entorno proxy-arp. Tienes que construir la lista de hosts para realizar esta verificación. Después, envía paquetes icmp echo a cada host en la lista y verifica si la dirección mac de origen de la respuesta difiere de la dirección que tenemos almacenada en la lista para esa ip. Podría significar que alguien está envenenando ese host pretendiendo tener nuestra dirección ip y reenvía los paquetes interceptados a nosotros. No puedes realizar esta prueba activa en modo no

ofensivo.

ejemplo

:

ettercap -
