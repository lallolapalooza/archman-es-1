NOMBRE

Mail::Message::Construct::Rebuild - modificar un Mail::Message

SINOPSIS

my $cleanup = $msg->rebuild;

DESCRIPCIÓN

Modificar mensajes existentes es una molestia, ciertamente si esto tiene que hacerse de forma automatizada. Los problemas se presentan especialmente cuando hay que crear o eliminar partes múltiples. El método rebuild() intenta simplificar esta tarea y añadir algunas características estándar.

MÉTODOS

Construcción de un mensaje

$obj->rebuild(%opciones)
Reconstruye un mensaje existente en algo nuevo. Devuelve un nuevo mensaje si se realizaron modificaciones, "undef" si el mensaje no tiene cuerpo restante, o el mensaje original si no hubo que realizar modificaciones.

Ejemplos de uso: tienes un mensaje que solo contiene html, y quieres traducirlo a un multiparte que contenga el html original y su traducción textual. O, tienes un mensaje con partes marcadas para ser eliminadas, y quieres que esos cambios se incorporen a la estructura de memoria. Otra posibilidad: limpiar todos los grupos de reenvío (ver Mail::Message::Head::ResentGroup) de la cabecera, antes de que sea escrito a un archivo.

La reconstrucción es una tarea peligrosa, donde intervienen multipartes de varios niveles y mensajes anidados. El método rebuild intenta simplificar el manejo de estos mensajes por ti.

El conjunto estándar de reglas, que es el valor por defecto para la opción "rules", es una configuración moderada. En lugar de copiar esa lista en un conjunto completo de reglas propio, también puedes especificar solo algunas reglas adicionales que se antepondrán al conjunto de reglas por defecto.

Se respeta el orden de las reglas, lo que significa que no siempre necesitas reescribir la regla completa (ver opción "rule"). Por ejemplo, la regla adicional de "removeDeletedParts" devuelve un "undef", lo que significa que cancela el efecto de la regla por defecto "replaceDeletedParts".

keep_message_id => BOOLEAN
El message-id es una identificación única del mensaje: no deben existir dos mensajes con contenido diferente en ninguna parte. Sin embargo, en la práctica, cuando un mensaje se modifica durante la transmisión, el id a menudo no se cambia incorrectamente. Esto puede llevar a complicaciones en aplicaciones que ven ambos mensajes con el mismo id.
rules => ARRAY
El ARRAY es una lista de reglas, cada una de las cuales describe una acción que se llamará en cada parte encontrada en el mensaje. La mayoría de las reglas probablemente no coincidirán, pero algunas traerán cambios al contenido. Las reglas se pueden especificar como nombres de método o como referencias de código. Las reglas son nombres de métodos que se pueden llamar en objetos de mensaje y partes de mensaje. El ARRAY también puede listar referencias de código que se pueden llamar. En cualquier caso, cada regla se llamará de la misma manera: 
$code->(MENSAJE, PARTE)

El retorno puede ser "undef" o cualquier constructo complejo basado en un Mail::Message::Part o coercible en una parte de este tipo. Para cada parte, todas las reglas se llaman en secuencia. Cuando una regla devuelve un objeto modificado, las reglas comenzarán de nuevo, sin embargo "undef" lo detendrá inmediatamente.

DETALLES

Reconstrucción de un mensaje

Modificar un mensaje existente es un trabajo complicado. No solo necesitas saber qué estás dispuesto a cambiar, sino que debes tener en cuenta los multipartes (posiblemente anidados en varios niveles), los mensajes encapsulados rfc822, la consistencia de los campos de cabecera, etc. El método rebuild() te permite centrarte en la tarea y se encarga del resto.

El método rebuild() utiliza reglas para transformar un mensaje en otro. Si una o más de las reglas se aplican, se devolverá un nuevo mensaje. Una simple comparación numérica indica si el mensaje ha cambiado. Por ejemplo

print "Sin cambios"
   if $message == $message->rebuild;

La transformación se realiza con un conjunto de reglas. Cada regla realiza solo un pequeño paso, lo que la hace fácilmente configurable. Las reglas están ordenadas, y cuando una realiza un cambio en el resultado, el resultado se pasará a todas las reglas nuevamente hasta que ninguna regla realice más cambios en la parte. Una regla también puede devolver "undef", en cuyo caso la parte será eliminada del mensaje (resultante).

Reglas generales

Esta sección describe las reglas de configuración generales: todas transformaciones bastante sencillas en la estructura del mensaje. Las reglas marcadas con (*) se utilizan por defecto.

  • descendMultiparts (*)

    Aplica las reglas a las partes de los multipartes (posiblemente anidados), no solo al mensaje de nivel superior.

  • descendNested (*)

    Aplica las reglas también al mensaje encapsulado "message/rfc822".

  • flattenEmptyMultiparts (*)

    Los mensajes multiparte que ya no tienen partes se reemplazan por una sola parte que contiene el preámbulo, el epílogo y una breve explicación.

  • flattenMultiparts (*)

    Cuando un multiparte contiene solo una parte, esa parte reemplazará al multiparte: se elimina un nivel de anidamiento. De esta manera, se pierden el preámbulo y el epílogo del multiparte (que oficialmente no tienen significado).

  • flattenNesting

    Elimina la encapsulación "message/rfc822". Solo se conservan las líneas relacionadas con el contenido del cuerpo encapsulado un nivel más arriba. Se perderá otra información, lo cual a menudo no es tan malo.

  • removeDeletedParts

    Todas las partes marcadas para eliminación se eliminan del mensaje sin dejar rastro. Si se encuentra un mensaje anidado cuyo contenido encapsulado está marcado para eliminación, se eliminará en su totalidad.

  • removeEmptyMultiparts

    Los mensajes multiparte que ya no tienen partes se eliminan. Se pierde la información en el preámbulo y el epílogo.

  • removeEmptyBodies

    Los cuerpos de mensaje simples que no contienen ninguna línea de contenido se eliminan. Esto hará perder la información que se almacena en las cabeceras de estos cuerpos.

NAME

Mail::Message::Construct::Rebuild - rebuild message structure

SYNOPSIS

  my $rebuilt_message = $message->rebuild(
      rules => [ 'rule1', 'rule2' ],
      extra_rules => [ \&my_rule, 'rule3' ],
      %options
  );

DESCRIPTION

The rebuild() method is used to transform a message structure. It can be used to simplify the structure, to remove parts of the message, or to add new parts.

The rebuild() method takes a list of rules. These rules are applied in the order they are given. Each rule is a subroutine that takes the message and a part as arguments, and returns a new part, or undef to remove the part.

The default rules are:

  • flattenMultiparts: remove multipart wrappers. A multipart/alternative is replaced by its preferred part. A multipart/mixed is replaced by its parts, which are then processed individually.
  • removeHtmlAlternativeToText: when a multipart alternative is encountered, which contains both a plain text and an html part, then the html part is deleted. Especially useful in combination with the "flattenMultiparts" rule.
  • textAlternativeForHtml: any "text/html" part which is not accompanied by an alternative plain text part will have one added. You must have a working Mail::Message::Convert::HtmlFormatText, which means that HTML::TreeBuilder and HTML::FormatText must be installed on your system.
  • removeExtraAlternativeText: when a multipart alternative is encountered, deletes all its parts except for the last part (the preferred part in accordance with RFC2046). In practice, this normally results in the alternative plain text part being deleted of an html message. Useful in combination with the "flattenMultiparts" rule.

You can specify a selection of these rules with rebuild(rules) and rebuild(extra_rules).

METHODS

rebuild()

Transform the message structure. This method takes the following arguments:

rules
An array reference of rule names (strings) to be applied. The order is important.
extra_rules
An array reference of rule names (strings) or subroutines (references to subroutines) to be applied. These are applied after the rules.

The default rules are:

  • flattenMultiparts: This rule recursively unpacks multipart messages. A multipart/mixed is replaced by its components, which are then processed recursively. A multipart/alternative is replaced by its most preferred part, which is then processed recursively.

The following rules are available:

  • removeHtmlAlternativeToText

    When a multipart alternative is encountered, which contains both a plain text and an html part, then the html part is deleted. Especially useful in combination with the "flattenMultiparts" rule.

  • textAlternativeForHtml

    Any "text/html" part which is not accompanied by an alternative plain text part will have one added. You must have a working Mail::Message::Convert::HtmlFormatText, which means that HTML::TreeBuilder and HTML::FormatText must be installed on your system.

    When you are planning to create an automatic html to plain text filter for your email, then have a look at https://github.com/logological/mimestrip

» Example: using parameter with "textAlternativeForHtml"

my $result = $msg->rebuild(
  extra_rules => [ 'textAlternativeForHtml' ],
  textAlternativeForHtml => { leftmargin => 0 },
);

In practice, this normally results in the alternative plain text part being deleted of an html message. Useful in combination with the "flattenMultiparts" rule.

Adding your own rules

If you have designed your own rule, please consider contributing this to Mail::Box; it may be useful for other people as well.

Each rule is called

my $new = $code->($message, $part, %options)

where the %options are defined by the rebuild() method internals. At least the "rules" option is passed, which is a full expansion of all the rules which will be applied.

Your subroutine shall return $part if no changes are needed, "undef" if the part should be removed, and any newly constructed "Mail::Message::Part" when a change is required. It is easiest to start looking at the source code of this package, and copy from a comparible routine.

When you have your own routine, you simply call:

my $rebuild_message = $message->rebuild(
  extra_rules => [ \&my_own_rule, 'other_rule' ],
);

DETAILS

The rebuild() method traverses the message structure recursively. For each part, it checks if a rule is defined for that part's content type or disposition. If a rule is found, it is applied. If the rule returns a new part, that part replaces the original part. If the rule returns undef, the part is deleted.

The following rules are built-in:

flattenMultiparts
This rule is applied to all multipart parts. It unpacks the multipart wrapper and recursively applies the rules to the contained parts. For multipart/alternative, it selects the most preferred part (usually plain text over HTML) and applies the rules to that part. For multipart/mixed, it applies the rules to each part individually and then reassembles them into a new multipart/mixed part.
removeHtmlAlternativeToText
This rule is applied to multipart/alternative parts. If the part contains both a text/plain and a text/html part, the text/html part is removed. This is useful for ensuring that only plain text versions of messages are processed further.
textAlternativeForHtml
This rule is applied to text/html parts. If a text/html part does not have an accompanying text/plain part within the same multipart/alternative, this rule will attempt to generate one. This requires the installation of HTML::TreeBuilder and HTML::FormatText, and a working Mail::Message::Convert::HtmlFormatText module. Additional options can be passed to the conversion routine via the rebuild() method. For example: 
        my $rebuilt = $msg->rebuild(
            extra_rules => [ 'textAlternativeForHtml' ],
            textAlternativeForHtml => { wrap => 72 },
        );
This would generate a plain text alternative with a line width of 72 characters.
removeExtraAlternativeText
[2.110] This rule is applied to multipart/alternative parts. It removes all parts except for the last one, which is considered the most preferred part according to RFC2046. In most cases, this effectively removes the plain text alternative, leaving only the HTML part. This can be useful in scenarios where you specifically want to work with the HTML content.

You can combine these rules and add your own custom rules to achieve complex message transformations. The order in which the rules are applied is crucial.

Adding your own rules

To add your own rule, you need to define a subroutine that accepts three arguments: the message object, the current part object, and a hash of options. The subroutine should return:

  • The original part object if no changes are needed.
  • undef if the part should be deleted.
  • A new Mail::Message::Part object if the part has been modified or replaced.

Here's an example of how to add a custom rule:

  sub my_custom_rule {
    my ($message, $part, %options) = @_;

    if ($part->contentType eq 'text/plain' && $part->content =~ /unsubscribe/i) {
      # Part contains an unsubscribe link, let's remove it
      return undef;
    }

    # No changes needed for other parts
    return $part;
  }

  my $rebuilt_message = $original_message->rebuild(
    extra_rules => [ \&my_custom_rule, 'flattenMultiparts' ],
  );

In this example, my_custom_rule is defined to remove any plain text part that contains the word "unsubscribe". It's then used in conjunction with the built-in flattenMultiparts rule.

DIAGNOSTICS

Error: No rebuild rule $name defined.
This error is raised by the rebuild() method when you specify a rule name that is not recognized (i.e., not a built-in rule and not a provided subroutine reference).
