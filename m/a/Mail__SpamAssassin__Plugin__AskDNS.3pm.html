NOMBRE

AskDNS - forma una consulta DNS utilizando valores de etiquetas, y consulta las listas DNSxL

SINOPSIS

loadplugin  Mail::SpamAssassin::Plugin::AskDNS
askdns D_IN_DWL _DKIMDOMAIN_._vouch.dwl.spamhaus.org TXT /\b(transaction|list|all)\b/

DESCRIPCIÓN

Utilizando una plantilla de consulta DNS según lo especificado en un parámetro de una regla askdns, el plugin reemplaza los nombres de etiquetas que se encuentran en la plantilla con sus valores y lanza consultas DNS tan pronto como los valores de las etiquetas estén disponibles. Cuando las respuestas DNS llegan gradualmente, las filtra de acuerdo con el tipo de registro de recurso DNS solicitado y una expresión de filtrado de subregla opcional, produciendo un acierto de regla si una respuesta cumple con las condiciones de filtrado.

DEFINICIONES DE REGLAS Y CONFIGURACIONES PRIVILEGIADAS

askdns NOMBRE_DE_LA_REGLA plantilla_de_consulta [tipo_rr [filtro_subconsulta]]
Una plantilla de consulta es una cadena que se expandirá para producir un nombre de dominio que se utilizará en una consulta DNS. La plantilla puede incluir nombres de etiquetas de SpamAssassin, que se reemplazarán por sus valores para formar un dominio de consulta final.

El dominio de consulta final debe cumplir con las reglas que rigen los dominios DNS, es decir, debe constar de campos de hasta 63 caracteres de longitud, delimitados por puntos, sin exceder los 255 caracteres. Se permiten nombres de dominio internacionales (en UTF-8) y se codificarán a codificación compatible con ASCII (ACE) según las reglas de IDN. Las consultas sintácticamente inválidas resultantes serán descartadas por el código del resolvedor DNS (con algunas advertencias informativas).

Puede haber un punto final al final, pero es redundante / no tiene semántica, ya que SpamAssassin utiliza un método Net::DSN::Resolver::send para consultar DNS, que ignora las opciones de resolución DNS de 'búsqueda' o 'dominio'. Los nombres de dominio en las consultas DNS no distinguen entre mayúsculas y minúsculas.

Un nombre de etiqueta es una cadena de letras mayúsculas, precedida y seguida por un carácter de guion bajo. Esta sintaxis refleja la configuración add_header, excepto que las etiquetas no pueden tener parámetros entre paréntesis cuando se usan en plantillas askdns (excepciones que se encuentran a continuación). Los nombres de etiquetas pueden aparecer en cualquier lugar de la plantilla; cada zona DNS consultada prescribe cómo se debe formar una consulta.

La etiqueta especial compatible HEADER() se puede usar para consultar cualquier contenido de encabezado, utilizando los mismos nombres/modificadores de encabezado que admiten las reglas de encabezado. Por ejemplo, _HEADER(Reply-To:addr:domain)_ se puede usar para consultar la parte de dominio recortada de la dirección Reply-To. Consulte la documentación de Mail::SpamAssassin::Conf sobre las reglas de encabezado.

Una plantilla de consulta puede contener cualquier número de nombres de etiquetas, incluido ninguno, aunque en el escenario previsto más común aparecería exactamente un nombre de etiqueta en cada regla askdns. Los nombres de etiquetas especificados se consideran dependencias. Las reglas Askdns con dependencias en el mismo conjunto de etiquetas se agrupan, y todas las consultas en un grupo se lanzan tan pronto como todas sus dependencias se cumplan, es decir, cuando el último de los valores de etiqueta esperados esté disponible mediante una llamada a set_tag() desde algún otro plugin o en otro lugar del código de SpamAssassin.

Las consultas lanzadas de todas las reglas askdns también se agrupan según un par de: tipo de consulta y un nombre de dominio de consulta expandido. Incluso si hay varias reglas que producen el mismo par tipo/dominio, solo se lanza una consulta DNS, y una respuesta a dicha consulta contribuye a todas las reglas constituyentes.

Una etiqueta puede producir ningún valor, un valor o varios valores. Las reglas Askdns que esperan una etiqueta que nunca recibe su valor nunca resultan en una consulta DNS. Las etiquetas que producen varios valores darán lugar a múltiples consultas lanzadas, cada una con una plantilla expandida que utiliza uno de los valores de la etiqueta. Un ejemplo es una etiqueta DKIMDOMAIN que produce una lista de dominios de firma, uno por cada firma válida en un mensaje firmado.

Cuando aparece más de un nombre de etiqueta distinto en una plantilla, cada uno potencialmente dando lugar a múltiples valores, se forma un producto cartesiano, y cada tupla resulta en el lanzamiento de una consulta DNS (se excluyen los duplicados). Por ejemplo, una plantilla de consulta _A_._B_.example._A_.com donde A es una lista (11,22) y B es (xx,yy,zz), dará lugar a las consultas: 11.xx.example.11.com, 22.xx.example.22.com, 11.yy.example.11.com, 22.yy.example.22.com, 11.zz.example.11.com, 22.zz.example.22.com.

Un parámetro de tipo_rr que sigue a la plantilla de consulta es una lista separada por comas de los tipos de registro de recursos DNS (RR) esperados. La ausencia del parámetro tipo_rr implica 'A'. Una respuesta DNS puede traer registros de recursos de varios tipos, pero solo se consideran los registros de recursos de un tipo que se encuentra en la lista del parámetro tipo_rr; otros registros de recursos encontrados en la sección de respuesta de una respuesta DNS se ignoran para esta regla. Un valor ANY en el parámetro tipo_rr coincide con cualquier tipo de registro de recurso. Una sección de respuesta DNS vacía no coincide con ANY.

El parámetro tipo_rr no solo proporciona un filtro para los tipos de RR encontrados en la respuesta DNS, sino que también determina el tipo de consulta DNS. Si solo se especifica un tipo de RR en el parámetro (por ejemplo, TXT), entonces este es también el tipo de RR de una consulta. Cuando se especifican varios tipos de RR (por ejemplo, A, AAAA, TXT) o si se especifica ANY, el tipo de consulta DNS será ANY y el parámetro tipo_rr solo actuará como filtro en una respuesta.

Actualmente, los tipos de RR reconocidos en el parámetro tipo_rr son: ANY, A, AAAA, MX, TXT, PTR, NAPTR, NS, SOA, CERT, CNAME, DNAME, DHCID, HINFO, MINFO, RP, HIP, IPSECKEY, KX, LOC, GPOS, SRV, OPENPGPKEY, SSHFP, SPF, TLSA, URI, CAA, CSYNC.

El último parámetro opcional de una regla es una expresión de filtrado, también conocida como subregla. Su función es muy parecida a la subregla en las reglas URIDNSBL, o en las reglas eval check_rbl. La principal diferencia es que con las reglas askdns no es necesario agrupar manualmente las reglas según su zona consultada, ya que la agrupación es automática y las consultas duplicadas se eliminan implícitamente.

El parámetro de filtrado de subregla puede ser: una cadena simple, una expresión regular, un solo valor numérico o un par de valores numéricos, o una lista de códigos rcodes (códigos de estado DNS de una respuesta). La ausencia del parámetro de filtrado implica ningún filtrado, es decir, cualquier respuesta DNS positiva (rcode=NOERROR) del tipo de RR solicitado resultará en un acierto de regla, independientemente del valor RR devuelto con la respuesta.

Cuando se utiliza una cadena simple como filtro, debe ir entre comillas simples o dobles. Para que la regla tenga éxito, la respuesta debe coincidir exactamente con la cadena de filtrado, y el tipo de RR de una respuesta debe coincidir con el tipo de consulta. El uso típico es una cadena de texto exacta para consultas TXT, o una dirección IPv4 cuádruple exacta. En el caso de un registro TXT o SPF que puede devolver varias cadenas de caracteres (como se define en la Sección 3.3 de [RFC1035]), estas cadenas se concatenan sin delimitadores antes de comparar el resultado con la cadena de filtrado. Esto sigue los requisitos de varios documentos, como RFC 5518, RFC 7208, RFC 4871, RFC 5617. Ejemplos de un parámetro de filtrado de texto simple: "127.0.0.1", "transaction", 'list' .

Una expresión regular sigue una sintaxis perl familiar como /.../ o m{...} seguida opcionalmente por banderas de regexp (como 'i' para insensibilidad a mayúsculas y minúsculas). Si una respuesta DNS coincide con el tipo de RR solicitado y la expresión regular, la regla tiene éxito. Ejemplos: /^127\.0\.0\.\d+$/, m{\bdial up\b}i.

Un solo valor numérico puede ser un número decimal, o un número hexadecimal prefijado por 0x. Dicha expresión de filtrado numérico se utiliza típicamente con consultas DNS de tipo RR A. El valor devuelto (una dirección IPv4) se enmascara con un valor de filtrado especificado y se prueba para que caiga dentro de un rango de red 127.0.0.0/8: la regla tiene éxito si el resultado no es cero: ((r & n) != 0) && ((r & 0xff000000) == 0x7f000000). Un ejemplo: 0x10.

Un par de valores numéricos (cada uno decimal, hexadecimal o cuádruple) delimitados por un '-' especifica un rango de direcciones IPv4, y un par de valores delimitados por un '/' especifica una dirección IPv4 seguida de una máscara de bits. Nuevamente, este tipo de expresión de filtrado está destinado principalmente a consultas DNS de tipo RR A. Mail::SpamAssassin::Plugin::AskDNS(3pm)

NAME

Mail::SpamAssassin::Plugin::AskDNS – SpamAssassin Mail Filter Plugin

SYNOPSIS

 use Mail::SpamAssassin::Plugin::AskDNS;

A simplified example:

 plugin: AskDNS
 askdns_test txt _ example.com

DESCRIPTION

The AskDNS plugin allows you to query DNS records for arbitrary names (A, AAAA, MX, TXT, etc.). This can be useful for checking DNS records that might indicate spam or not.

A typical use case is to check if a reverse DNS lookup matches the forward lookup of an IP address.

Here are some examples:

# Check if example.com has a TXT record containing "v=spf1"
plugin: AskDNS
askdns_test txt _ example.com @v=spf1

# Check if the IP address of the sender has a PTR record pointing to
# the hostname provided by the client. This checks the rDNS.
# Note: this rule requires the IP address to be specified in the
# rule, or implicitly using <REMOTE_ADDR>.
#
# AskDNS will default to the client IP if <REMOTE_ADDR> is not
# explicitly specified.
askdns_test ptr <REMOTE_ADDR>
# The following rule is equivalent:
# askdns_test ptr <REMOTE_ADDR>

# Check if the IP address of the sender resolves to a hostname in the
# example.com domain.
askdns_test ptr <REMOTE_ADDR> example.com

# Check if the IP address of the sender resolves to a hostname in the
# example.com domain, and if that hostname has an A record for the
# IP address.
askdns_test ptr <REMOTE_ADDR> example.com \
    && askdns_test a example.com <REMOTE_ADDR>

# Check if example.com has an MX record pointing to mail.example.com
askdns_test mx example.com mail.example.com

# Check if example.com has an A record pointing to 1.2.3.4
askdns_test a example.com 1.2.3.4

# Check if a hostname has a TXT record containing the string "some string"
# Note: The string can be a perl regex.
askdns_test txt _ hostname.example.com @some string

The askdns_test directive takes the following arguments:

Type

The DNS record type to query (e.g., A, AAAA, MX, TXT, PTR, SPF, etc.).

Name

The name to query. This can be a literal name, or a placeholder enclosed in < >. Currently supported placeholders are:

<REMOTE_ADDR>
The IP address of the client that connected to the mail server.
<SENDER_IP>
The IP address of the sender.
<REMOTE_ADDR_NAME>
The hostname resolved from the client IP address (via PTR lookup).
<SENDER_IP_NAME>
The hostname resolved from the sender IP address (via PTR lookup).

Value

The expected value of the DNS record. This can be a literal string, a regular expression (prefixed with @), or a placeholder. If omitted, any value will match.

Rcode

An optional DNS response code (rcode) to check for. This can be a numeric value or a name (e.g., NOERROR, NXDOMAIN, SERVFAIL). If specified, the test only succeeds if the DNS query returns the specified rcode. If omitted, the test only succeeds if the DNS query returns NOERROR.

Options

Optional arguments that modify the behavior of the test. Currently supported options are:

mask
Requires a numeric IP address for the Value argument. The result of the DNS query is compared against the specified Value using a bitmask. For example, 127.0.1.0/255.255.0.0 will match any IP address in the 127.0.1.x range.
norecurse
Disables recursive lookups. The DNS server will not perform recursive lookups if this option is set.
nolimit
Disables the default DNS query limit. By default, AskDNS will perform at most 3 DNS queries per rule.
no_rrsigs
Do not request DNSSEC RRSIG records. This can speed up queries on systems that do not have DNSSEC validation enabled.
ipv4
Force IPv4 DNS queries.
ipv6
Force IPv6 DNS queries.

The AskDNS plugin supports numeric filtering parameters. These can be specified as a single IP address, a range of IP addresses, or a network address with a subnet mask. The format is either IP1-IP2 for a range, or IP/MASK for a network address with a subnet mask.

When a mask is specified, the comparison is done using a bitmask: (r & m) == (n & m).

As a shorthand notation, a single quad-dotted value is equivalent to a n-n form, i.e. it must match the returned value exactly with all its bits.

Some typical examples of a numeric filtering parameter are: 127.0.1.2, 127.0.1.20-127.0.1.39, 127.0.1.0/255.255.255.0, 0.0.0.16/0.0.0.16, 0x10/0x10, 16, 0x10.

Lastly, the filtering parameter can be a comma-separated list of DNS status codes (rcode), enclosed in square brackets. Rcodes can be represented either by their numeric decimal values (0=NOERROR, 3=NXDOMAIN, ...), or their names. See https://www.iana.org/assignments/dns-parameters for the list of names. When testing for a rcode where rcode is nonzero, a RR type parameter is ignored as a filter, as there is typically no answer section in a DNS reply when rcode indicates an error. Example: [NXDOMAIN], or [FormErr,ServFail,4,5].

NOTES

DNS timeout can be set with "rbl_timeout" option. See the "Mail::SpamAssassin::Conf" POD for details on "rbl_timeout".
