NOMBRE

Module::Build::Cookbook - Ejemplos de uso de Module::Build

DESCRIPCIÓN

"Module::Build" no es conceptualmente muy complicado, pero los ejemplos siempre son útiles. Las siguientes recetas deberían ayudar a los desarrolladores y/o instaladores a juntar las piezas de otras partes de la documentación.

RECETAS BÁSICAS

Instalar módulos que usan Module::Build

En la mayoría de los casos, puedes simplemente ejecutar los siguientes comandos:

perl Build.PL
./Build
./Build test
./Build install

No hay nada complicado aquí: primero ejecutas un script llamado Build.PL, luego ejecutas un script (recién generado) llamado Build y le pasas varios argumentos.

Los comandos exactos pueden variar un poco dependiendo de cómo invoques los scripts de perl en tu sistema. Por ejemplo, si tienes varias versiones de perl instaladas, puedes instalar en los directorios de bibliotecas de una versión particular de perl así:

/usr/bin/perl5.8.1 Build.PL
./Build
./Build test
./Build install

En Windows, donde el directorio actual siempre se busca primero para los scripts, probablemente harás algo como esto:

perl Build.PL
Build
Build test
Build install

En el antiguo Mac OS (versión 9 o inferior) usando MacPerl, puedes hacer doble clic en el script Build.PL para crear el script Build, luego hacer doble clic en el script Build para ejecutar sus acciones de "build", "test" y "install".

El script Build sabe qué perl se usó para ejecutar Build.PL, por lo que no necesitas volver a invocar el script Build con la ruta completa de perl cada vez. Si lo invocas con la ruta de perl *incorrecta*, obtendrás una advertencia o un error fatal.

Modificar valores de Config.pm

"Module::Build" depende en gran medida de varios valores de "Config.pm" de perl para hacer su trabajo. Por ejemplo, las rutas de instalación predeterminadas se dan en "installsitelib" y "installvendorman3dir" y amigos, la configuración del enlazador y compilador de C se dan en "ld", "lddlflags", "cc", "ccflags", etc. *Si estás bastante seguro* de que sabes lo que estás haciendo*, puedes decirle a "Module::Build" que finja que hay valores diferentes en Config.pm de los que realmente hay, pasando argumentos para el parámetro "--config" en la línea de comandos:

perl Build.PL --config cc=gcc --config ld=gcc

Dentro del script "Build.PL", se puede lograr lo mismo pasando valores para el parámetro "config" a new():

my $build = Module::Build->new
  (
   ...
   config => { cc => 'gcc', ld => 'gcc' },
   ...
  );

En código de compilación personalizado, se puede lograr lo mismo llamando al método `config` en Module::Build:

$build->config( cc => 'gcc' );     # Establecer
$build->config( ld => 'gcc' );     # Establecer
...
my $linker = $build->config('ld'); # Obtener

Instalar módulos usando la interfaz programática

Si necesitas compilar, probar y/o instalar módulos desde dentro de otro código perl (en lugar de que el usuario escriba comandos de instalación en la shell), puedes usar la interfaz programática. Crea un objeto Module::Build (o un objeto de una subclase personalizada de Module::Build) y luego invoca su método dispatch() para ejecutar varias acciones.

my $build = Module::Build->new
  (
   module_name => 'Foo::Bar',
   license     => 'perl',
   requires    => { 'Some::Module'   => '1.23' },
  );
$build->dispatch('build');
$build->dispatch('test', verbose => 1);
$build->dispatch('install');

El primer argumento de dispatch() es el nombre de la acción, y los argumentos siguientes son parámetros con nombre.

Esta es la interfaz que usamos para probar Module::Build en sí en las pruebas de regresión.

Instalar en un directorio temporal

Para crear paquetes para administradores de paquetes como "rpm" de RedHat o "deb" de Debian, puede que necesites instalar primero en un directorio temporal y luego crear el paquete desde esa instalación temporal. Para hacer esto, especifica el parámetro "destdir" a la acción "install":

./Build install --destdir /tmp/mi-paquete-1.003

Esto esencialmente simplemente antepone todos los directorios de instalación con el directorio /tmp/mi-paquete-1.003.

Instalar en un directorio no estándar

Para instalar en un directorio no estándar (por ejemplo, si no tienes permiso para instalar en los directorios del sistema), puedes usar los parámetros "install_base" o "prefix":

./Build install --install_base /foo/bar

Consulta "RUTAS DE INSTALACIÓN" en Module::Build para una discusión mucho más completa de cómo se determinan las rutas de instalación.

Instalar en la misma ubicación que ExtUtils::MakeMaker

Con la introducción de "--prefix" en Module::Build 0.28 y "INSTALL_BASE" en "ExtUtils::MakeMaker" 6.31 es fácil hacer que ambos instalen en las mismas ubicaciones.

Primero, asegúrate de tener al menos la versión 0.28 de Module::Build instalada y la 6.31 de "ExtUtils::MakeMaker". Versiones anteriores tienen comportamientos de instalación diferentes (y en algunos casos bastante extraños).

Las siguientes banderas de instalación son equivalentes entre "ExtUtils::MakeMaker" y "Module::Build".

MakeMaker             Module::Build
PREFIX=...            --prefix ...
INSTALL_BASE=...      --install_base ...
DESTDIR=...           --destdir ...
LIB=...               --install_path lib=...
INSTALLDIRS=...       --installdirs ...
INSTALLDIRS=perl      --installdirs core
UNINST=...            --uninst ...
INC=...               --extra_compiler_flags ...
POLLUTE=1             --extra_compiler_flags -DPERL_POLLUTE

Por ejemplo, si actualmente estás instalando módulos de "MakeMaker" con este comando:

perl Makefile.PL PREFIX=~
make test
make install UNINST=1

Puedes instalar en la misma ubicación con Module::Build usando esto:

perl Build.PL --prefix ~
./Build test
./Build install --uninst 1

"prefix" vs "install_base"

El comportamiento de "prefix" es complicado y depende de cómo esté configurado tu Perl. Las ubicaciones de instalación resultantes variarán de una máquina a otra e incluso de diferentes instalaciones de Perl en la misma máquina. Debido a esto, es difícil documentar dónde "prefix" colocará tus módulos.

En contraste, "install_base" tiene ubicaciones de instalación predecibles y fáciles de explicar. Ahora que "Module::Build" y "MakeMaker" tienen ambos "install_base", hay pocas razones para usar "prefix" excepto para preservar tu configuración existente.

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

instalación. Si estás comenzando con una instalación nueva de Perl, te animamos a usar "install_base". Si ya tienes una instalación existente instalada a través de "prefix", considera moverla a una estructura de instalación que coincida con "install_base" y usar esa en su lugar.

Ejecutando un único archivo de prueba

"Module::Build" soporta la ejecución de una única prueba, lo que te permite depurar errores más rápidamente. Usa el siguiente formato:

./Build test --test_files t/mytest.t

Además, es posible que quieras ejecutar la prueba en modo detallado para obtener una salida más informativa:

./Build test --test_files t/mytest.t --verbose 1

Ejecuto esto tan frecuentemente que defino el siguiente alias de shell:

alias t './Build test --verbose 1 --test_files'

Así entonces puedo simplemente ejecutar "t t/mytest.t" para ejecutar una única prueba.

RECETAS AVANZADAS

Creando una distribución compatible con CPAN.pm

Las nuevas versiones de CPAN.pm entienden cómo usar un script Build.PL, pero las versiones antiguas no. Si los autores quieren ayudar a los usuarios con versiones antiguas, se debe proporcionar alguna forma de Makefile.PL. La forma más fácil de lograr esto es usar el parámetro "create_makefile_pl" para "Module::Build->new()" en el script "Build.PL", que puede crear varios tipos de Makefile.PL durante la acción "dist".

Como buena práctica, recomendamos usar el estilo "tradicional" de Makefile.PL a menos que tu distribución tenga necesidades que no se puedan cumplir de esa manera.

El módulo "Module::Build::Compat", que forma parte de la distribución de "Module::Build", es el responsable de crear estos Makefile.PL. Por favor, consulta Module::Build::Compat para obtener detalles.

Cambiando el orden del proceso de compilación

La propiedad "build_elements" especifica los pasos que "Module::Build" tomará al compilar una distribución. Para cambiar el orden de compilación, cambia el orden de las entradas en esa propiedad:

# Procesa los archivos pod primero
my @e = @{$build->build_elements};
my ($i) = grep {$e[$_] eq 'pod'} 0..$#e;
unshift @e, splice @e, $i, 1;

Actualmente, "build_elements" tiene el siguiente valor predeterminado:

[qw( PL support pm xs pod script )]

Ten cuidado al alterar esta propiedad, ya que puede haber dependencias de orden no obvias (¡y no documentadas!) en el código de "Module::Build".

Agregando nuevos tipos de archivos al proceso de compilación

A veces, es posible que tengas tipos de archivos adicionales que quieras instalar junto con los tipos estándar como los archivos .pm y .pod. Por ejemplo, podrías tener un archivo Bar.dat que contenga algunos datos relacionados con el módulo "Foo::Bar" y te gustaría que terminara como Foo/Bar.dat en algún lugar de la ruta @INC de perl para que "Foo::Bar" pueda acceder a él fácilmente en tiempo de ejecución. El siguiente código de un archivo de ejemplo "Build.PL" demuestra cómo lograr esto:

use Module::Build;
my $build = Module::Build->new
  (
   module_name => 'Foo::Bar',
   ...otro contenido aquí...
  );
$build->add_build_element('dat');
$build->create_build_script;

Esto encontrará todos los archivos .dat en el directorio lib/, los copiará al directorio blib/lib/ durante la acción "build", y los instalará durante la acción "install".

Si tus archivos adicionales no están ubicados en el directorio "lib/" en tu distribución, puedes especificar explícitamente dónde están, tal como lo harías con los archivos .pm o .pod:

use Module::Build;
my $build = new Module::Build
  (
   module_name => 'Foo::Bar',
   dat_files => {'some/dir/Bar.dat' => 'lib/Foo/Bar.dat'},
   ...otro contenido aquí...
  );
$build->add_build_element('dat');
$build->create_build_script;

Si tus archivos adicionales realmente necesitan ser creados en la máquina del usuario, o si necesitan algún otro tipo de procesamiento especial, probablemente querrás crear una subclase de "Module::Build" y crear un método especial para procesarlos, llamado "process_${kind}_files()":

use Module::Build;
my $class = Module::Build->subclass(code => <<'EOF');
  sub process_dat_files {
    my $self = shift;
    ... localizar y procesar archivos *.dat,
    ... y crear algo en blib/lib/
  }
EOF
my $build = $class->new
  (
   module_name => 'Foo::Bar',
   ...otro contenido aquí...
  );
$build->add_build_element('dat');
$build->create_build_script;

Si tus archivos adicionales no van a lib/ sino a otro lugar, consulta "Agregando nuevos elementos al proceso de instalación" para ver cómo hacer que se instalen.

Ten en cuenta que estos ejemplos utilizan algunas capacidades de Module::Build que aparecieron por primera vez en la versión 0.26. Antes de eso, todavía se podía hacer, pero los casos simples requerían un poco más de trabajo.

Agregando nuevos elementos al proceso de instalación

Por defecto, Module::Build crea siete subdirectorios del directorio blib durante el proceso de compilación: lib, arch, bin, script, bindoc, libdoc, y html (algunos de estos pueden faltar o estar vacíos si no hay nada que poner en ellos). Cualquier cosa copiada a estos directorios durante la compilación se instalará eventualmente durante la acción "install" (ver "RUTAS DE INSTALACIÓN" en Module::Build.

Si necesitas crear un nuevo tipo de elemento instalable personalizado, por ejemplo "conf", entonces necesitas decirle a Module::Build dónde se deben instalar las cosas en blib/conf/. Para hacer esto, usa el parámetro "install_path" del método new():

my $build = Module::Build->new
  (
   ...otro contenido aquí...
   install_path => { conf => $ruta_de_instalación }
  );

O puedes llamar al método install_path() más tarde:

$build->install_path(conf => $ruta_de_instalación);

El usuario también puede especificar la ruta en la línea de comandos:

perl Build.PL --install_path conf=/ruta/del/path/etc

Lo importante, sin embargo, es que de alguna manera la ruta de instalación debe establecerse, o nada en el directorio blib/conf/ se instalará, y se producirá un error en tiempo de ejecución durante la acción "install".

Consulta también "Agregando nuevos tipos de archivos al proceso de compilación" para ver cómo crear el contenido en blib/conf/ en primer lugar.

EJEMPLOS EN CPAN

Varias distribuciones en CPAN están haciendo un buen uso de varias características de Module::Build. Pueden servir como ejemplos del mundo real para otros.

SVN-Notify-Mirror

http://search.cpan.org/~jpeacock/SVN-Notify-Mirror/

John Peacock, autor de la distribución "SVN-Notify-Mirror", dice:

1. Usando "auto_features", verifico si dos módulos opcionales están disponibles: SVN::Notify::Config y Net::SSH;
2. Si el módulo S::N::Config está cargado, genero automáticamente archivos de prueba para él durante Build (usando la propiedad "PL_files").
3. Si la "ssh_feature" está disponible, pregunto si el usuario desea realizar las pruebas ssh (ya que requiere una pequeña configuración preliminar);
4. Solo si el usuario tiene "ssh_feature" y responde sí a las pruebas, genero un archivo de prueba.
Estoy seguro de que no podría haber manejado esta complejidad con EU::MM, pero fue muy fácil hacerlo con M::B.

Modificando una acción

A veces podrías necesitar que una acción, digamos "./Build install", haga algo inusual. Por ejemplo, podrías necesitar cambiar la propiedad de un archivo o hacer algo peculiar para tu aplicación.

Puedes crear una subclase de "Module::Build" sobre la marcha usando el método subclass() y reemplazar los métodos que realizan las acciones. Es posible que necesites leer "Module::Build::Authoring" y "Module::Build::API" para encontrar los métodos que deseas reemplazar. Todos los métodos de "acción" se implementan mediante un método llamado "ACTION_" seguido del nombre de la acción, por lo que aquí tienes un ejemplo de cómo funcionaría para la acción "install":

# Build.PL
use Module::Build;
my $class = Module::Build->subclass(
    class => "Module::Build::Custom",
    code => <<'SUBCLASS' );
sub ACTION_install {
    my $self = shift;
    # TU CÓDIGO AQUÍ
    $self->SUPER::ACTION_install;
}
SUBCLASS
$class->new(
    module_name => 'Your::Module',
    # resto de los parámetros habituales de Module::Build
)->create_build_script;

Agregando una acción

Puedes agregar una nueva acción "./Build" simplemente escribiendo el método para ella en tu subclase. Usa "depends_on" para declarar que otra acción debe haberse ejecutado antes que tu acción.

Por ejemplo, digamos que

quería poder escribir "./Build commit" para probar tu código y enviarlo a Subversion.

# Build.PL
use Module::Build;
my $class = Module::Build->subclass(
    class => "Module::Build::Custom",
    code => <<'SUBCLASS' );
sub ACTION_commit {
    my $self = shift;
    $self->depends_on("test");
    $self->do_system(qw(svn commit));
}
SUBCLASS

Empaquetado de Module::Build

Nota: Esta sección probablemente necesita una actualización a medida que la tecnología mejora (ver contrib/bundle.pl en la distribución).

Supongamos que deseas usar algunas características nuevas de Module::Build, por ejemplo, más nuevas que la versión de Module::Build que tus usuarios probablemente ya tengan instalada en sus sistemas. Lo primero que debes hacer es establecer "configure_requires" a tu versión mínima de Module::Build. Ver Module::Build::Authoring.

Pero no todos los sistemas de compilación respetan "configure_requires" todavía. Aquí te explicamos cómo puedes enviar una copia de Module::Build, pero aún así usar una versión instalada más nueva para aprovechar las correcciones de errores y las actualizaciones.

Primero, instala Module::Build en Tu-Proyecto/inc/Module-Build. CPAN no indexará nada en el directorio inc, por lo que esta copia no aparecerá en las búsquedas de CPAN.

cd Module-Build
perl Build.PL --install_base /ruta/a/Tu-Proyecto/inc/Module-Build
./Build test
./Build install

Ahora deberías tener todos los archivos .pm de Module::Build en Tu-Proyecto/inc/Module-Build/lib/perl5.

A continuación, añade esto al principio de tu Build.PL.

my $Bundled_MB = 0.30;  # o la versión que sea.
# Averigua qué versión de Module::Build está instalada o falla silenciosamente.
# Esto debería ser multiplataforma.
my $Installed_MB =
    `$^X -e "eval q{require Module::Build; print Module::Build->VERSION} or exit 1"`;
# algunos sistemas operativos añaden una nueva línea al final de cada impresión.
chomp $Installed_MB;
$Installed_MB = 0 if $?;
# Usa nuestra copia empaquetada de Module::Build si es más nueva que la instalada.
unshift @INC, "inc/Module-Build/lib/perl5" if $Bundled_MB > $Installed_MB;
require Module::Build;

Y escribe el resto de tu Build.PL normalmente. Module::Build recordará tu cambio en @INC y lo usará cuando ejecutes ./Build.

En el futuro, esperamos proporcionar una solución más automatizada para este escenario; ver "inc/latest.pm" en la distribución de Module::Build para una indicación de la dirección en la que nos movemos.
