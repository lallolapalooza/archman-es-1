Module::Build(3pm) Documentación del Contribuido por el Usuario Perl Module::Build(3pm)

NOMBRE

Module::Build - Construye e instala módulos Perl

SINOPSIS

Proceso estándar para construir e instalar módulos:

perl Build.PL
./Build
./Build test
./Build install

O, si estás en una plataforma (como DOS o Windows) que no requiere la notación "./", puedes hacer esto:

perl Build.PL
Build
Build test
Build install

DESCRIPCIÓN

"Module::Build" es un sistema para construir, probar e instalar módulos Perl. Está pensado como una alternativa a "ExtUtils::MakeMaker". Los desarrolladores pueden alterar el comportamiento del módulo mediante la subclase. Tampoco requiere un "make" en tu sistema: la mayor parte del código de "Module::Build" es Perl puro y está escrito de manera muy multiplataforma.

Consulta "COMPARACIÓN" para más comparaciones entre "Module::Build" y otras herramientas de instalación.

Para instalar "Module::Build", y cualquier otro módulo que use "Module::Build" para su proceso de instalación, haz lo siguiente:

perl Build.PL       # El script 'Build.PL' crea el script 'Build'
./Build             # Necesario ./ para asegurar que usamos este script "Build"
./Build test        # y no otro que esté en el PATH
./Build install

Esto ilustra la configuración inicial y la ejecución de tres 'acciones'. En este caso, las acciones ejecutadas son 'build' (la acción por defecto), 'test' e 'install'. Otras acciones definidas hasta ahora incluyen:

build                          manifest
clean                          manifest_skip
code                           manpages
config_data                    pardist
diff                           ppd
dist                           ppmdist
distcheck                      prereq_data
distclean                      prereq_report
distdir                        pure_install
distinstall                    realclean
distmeta                       retest
distsign                       skipcheck
disttest                       test
docs                           testall
fakeinstall                    testcover
help                           testdb
html                           testpod
install                        testpodcoverage
installdeps                    versioninstall

Puedes ejecutar la acción 'help' para obtener una lista completa de acciones.

ACCIONES

Hay algunos principios generales en juego aquí. Primero, cada tarea al construir un módulo se llama "acción". Estas acciones están listadas arriba; corresponden a las tareas de construcción, prueba, instalación, empaquetado, etc.

Segundo, los argumentos se procesan de manera muy sistemática. Los argumentos son siempre pares clave=valor. Pueden especificarse en el momento de "perl Build.PL" (es decir, "perl Build.PL destdir=/mi/lugar/secreto"), en cuyo caso sus valores duran para toda la vida del script "Build". También pueden especificarse al ejecutar una acción particular (es decir, "Build test verbose=1"), en cuyo caso sus valores duran solo para la vida útil de ese comando. Los parámetros de línea de comandos por acción tienen precedencia sobre los parámetros especificados en el momento de "perl Build.PL".

El proceso de construcción también depende en gran medida del módulo "Config.pm". Si el usuario desea anular alguno de los valores en "Config.pm", puede especificarlos así:

perl Build.PL --config cc=gcc --config ld=gcc

Las siguientes acciones de construcción se proporcionan por defecto.

build
[versión 0.01]

Si ejecutas el script "Build" sin ningún argumento, ejecuta la acción "build", que a su vez ejecuta las acciones "code" y "docs".

Esto es análogo al objetivo make all de "MakeMaker".

clean
[versión 0.01]

Esta acción limpiará cualquier archivo que el proceso de construcción haya podido crear, incluido el directorio "blib/" (pero sin incluir el directorio "_build/" ni el propio script "Build").

code
[versión 0.20]

Esta acción construye tu base de código.

Por defecto, simplemente crea un directorio "blib/" y copia cualquier archivo ".pm" y ".pod" de tu directorio "lib/" al directorio "blib/". También compila cualquier archivo ".xs" de "lib/" y los coloca en "blib/". Por supuesto, necesitas un compilador C funcional (probablemente el mismo que construyó Perl) para que la compilación funcione correctamente.

La acción "code" también ejecuta cualquier archivo ".PL" en tu directorio lib/. Típicamente estos crean otros archivos, con el mismo nombre pero sin la terminación ".PL". Por ejemplo, un archivo lib/Foo/Bar.pm.PL podría crear el archivo lib/Foo/Bar.pm. Los archivos ".PL" se procesan primero, para que cualquier archivo ".pm" (u otros tipos que manejamos) se copie correctamente.

config_data
[versión 0.26]

...

diff
[versión 0.14]

Esta acción comparará los archivos que están a punto de ser instalados con sus contrapartes instaladas. Para archivos .pm y .pod, se mostrará una diferencia (esto actualmente requiere un programa 'diff' en tu PATH). Para otros archivos como archivos binarios compilados, simplemente informamos si difieren.

Se puede pasar un parámetro "flags" a la acción, que se pasará al programa 'diff'. Consulta la documentación de tu 'diff' para ver los parámetros que acepta; uno bueno es "-u":

./Build diff flags=-u
dist
[versión 0.02]

Esta acción es útil para los autores de módulos que desean empaquetar su módulo para distribución fuente a través de un medio como CPAN. Creará un archivo tarball de los archivos listados en

y comprime el archivo tar.gz utilizando compresión GZIP.

Por defecto, esta acción utilizará el módulo "Archive::Tar". Sin embargo, puedes forzar que utilice binarios "tar" y "gzip" especificados mediante un parámetro explícito "tar" (y opcional "gzip"): 

./Build dist --tar C:\path\to\tar.exe --gzip C:\path\to\zip.exe
distcheck
[versión 0.05]

Muestra qué archivos están en la carpeta de construcción pero no en el archivo MANIFEST, y viceversa. (Ver detalles en "manifest").

distclean
[versión 0.05]

Ejecuta el acción 'realclean' y luego la acción 'distcheck'.

distdir
[versión 0.05]

Crea una carpeta de distribución llamada "$dist_name-$dist_version" (si ya existe, se eliminará primero), luego copia todos los archivos mencionados en el archivo MANIFEST a esa carpeta. Esta carpeta es la que se crea para el tarball de distribución.

distinstall
[versión 0.37]

Ejecuta el acción 'distdir', luego se cambia a esa carpeta y ejecuta "perl Build.PL", seguido de las acciones 'build' y 'install' en esa carpeta. Usa PERL_MB_OPT o .modulebuildrc para establecer opciones que se aplicarán durante los subprocessos.

distmeta
[versión 0.21]

Crea el archivo META.yml que describe la distribución.

META.yml es un archivo que contiene diversos bits de metadata sobre la distribución. La metadata incluye el nombre de la distribución, la versión, el resumen, las dependencias, la licencia y otros datos sobre la distribución. Este archivo se crea como META.yml en un formato simplificado de YAML.

META.yml también debe estar lista en MANIFEST - si no lo está, se emitirá un aviso.

La versión actual del META.yml se puede encontrar en CPAN como CPAN::Meta::Spec.

distsign
[versión 0.16]

Usa "Module::Signature" para crear un archivo SIGNATURE para tu distribución, y lo agrega a la carpeta de distribución MANIFEST.

disttest
[versión 0.05]

Ejecuta el acción 'distdir', luego se cambia a esa carpeta y ejecuta "perl Build.PL", seguido de las acciones 'build' y 'test' en esa carpeta. Usa PERL_MB_OPT o .modulebuildrc para establecer opciones que se aplicarán durante los subprocessos.

docs
[versión 0.20]

Genera documentación (por ejemplo, man pages y documentos HTML) para cualquier elemento instalable bajo blib/ que contenga POD. Si no hay targets de instalación especificados para "bindoc" o "libdoc" (como es el caso en sistemas que no soportan man pages Unix), no se realiza ninguna acción para man pages. Si no hay targets de instalación especificados para "binhtml" o "libhtml", tampoco se realiza ninguna acción para documentos HTML.

fakeinstall
[versión 0.02]

Esto es solo como la acción "install", pero no realice realmente nada; simplemente reporta qué haría si realmente hubiera ejecutado la acción "install".

help
[versión 0.03]

Esta acción imprimirá un mensaje que ayudará a usar el proceso de construcción. Mostrará una lista de acciones de construcción disponibles.

Con un argumento opcional especificando el nombre de la acción (por ejemplo, "Build help" test"), la acción 'help' mostrará la documentación POD encontrada para esa acción.

html
[versión 0.26]

Genera documentación HTML para cualquier archivo binario o librería bajo blib/ que contenga POD. La documentación HTML solo se instalará si los caminos de instalación pueden ser determinados a partir de los valores en "Config.pm". También puedes especificar o reemplazar los caminos de instalación en la línea de comandos mediante los parámetros "install_path" para los targets de instalación "binhtml" y "libhtml".

Con un argumento opcional "html_links" establecido a un valor falso, puedes evitar la búsqueda de otras documentaciones para vincular, ya que esto puede gastar un gran tiempo si no hay enlaces para generar:

./Build html --html_links 0
install
[versión 0.01]

Esta acción utilizará "ExtUtils::Install" para instalar los archivos de "blib/" en el sistema. Ver detalles sobre cómo Module::Build determina el camino de instalación y cómo influir en este proceso.

Si quieres que el proceso de instalación busque otras versiones de los archivos que estás instalando en @INC y las elimine, puedes usar el parámetro "uninst", que indica a "ExtUtils::Install" que hacer así:

./Build install uninst=1

Este puede ser una buena idea, ya que ayuda a prevenir que múltiples versiones de un módulo estén presentes en tu sistema, lo que puede ser una situación confusa.

installdeps
[versión 0.36]

Esta acción utilizará el parámetro "cpan_client" como un comando para instalar dependencias necesarias. Tú serás preguntado si deseas instalar dependencias opcionales.

El parámetro "cpan_client" se comporta por defecto como 'cpan', pero puede ser especificado como opción o en .modulebuildrc. Debe ser un comando de shell que tome una lista de módulos a instalar como argumentos (por ejemplo, 'cpanp -i' para CPANPLUS). Si el parte del programa es un camino relativo (por ejemplo, 'cpan' o 'cpanp'), se localizará relativamente al programa de Perl que ejecutó Build.PL.

/opt/perl/5.8.9/bin/perl Build.PL
./Build installdeps --cpan_client 'cpanp -i'
# instala a 5.8.9
manifest
[versión 0.05]

Esta acción está destinada a usar por parte de autores de módulos, no a usuarios que instalan módulos. Actualiza el archivo MANIFEST con los archivos actualmente presentes en la distribución. Puedes usar un archivo MANIFEST.SKIP para excluir ciertos archivos o directorios de la inclusión en MANIFEST. MANIFEST.SKIP debe contener una serie de expresiones regulares, una por línea. Si un archivo en el directorio de la distribución coincide con alguna de las expresiones regulares, no será incluido en MANIFEST.

El siguiente es un punto de partida razonable para un MANIFEST.SKIP, puedes añadir tu propio contenido a él:

^_build
^Build$
^blib
~$
\.bak$
^MANIFEST\.SKIP$
CVS

Si quieres saber qué haría la acción "manifest" sin ejecutar realmente nada, consulta las acciones "distcheck" y "skipcheck".

manifest_skip
[versión 0.3608]

Esta acción está destinada a usar por parte de autores de módulos, no a usuarios que instalan módulos. Genera un archivo de boilerplate MANIFEST.SKIP si no existe uno.

manpages
[versión 0.28]

Genera man pages para cualquier archivo binario o librería bajo blib/ que contenga POD. Las man pages se instalarán solo si los caminos de instalación pueden ser determinados a partir de los valores en "Config.pm". También puedes especificar o reemplazar los caminos de instalación mediante valores en la línea de comandos con los targets de instalación "bindoc" y "libdoc".

pardist
[versión 0.2806]

Genera un distribución en formato PAR para usar con PAR o PAR::Dist.

Requiere que la librería PAR::Dist (versión 0.17 y superior) esté instalada en tu sistema.

ppd
[versión 0.20]

Construye un archivo PPD para tu distribución.

Esta acción toma un argumento opcional "codebase" que se usa en el archivo PPD generado para especificar el (generalmente relativo) URL de la distribución. Por defecto, este valor es el nombre de la distribución sin información de ruta.

Ejemplo:

./Build ppd --codebase "MSWin32-x86-multi-thread/Module-Build-0.21.tar.gz"
ppmdist
[versión 0.23]

Genera una distribución en formato PPM y un archivo PPD de descripción. Esta acción también invoca la acción "ppd", por lo que puede aceptar el mismo argumento "codebase" descrito bajo esa acción.

Usa la misma mecanismación que la acción "dist" para tar y zipar su salida, así que puedes proporcionar "tar" y/o "gzip" parámetros para afectar el resultado.

OPTIONS

[version 0.22]

You can pass options to Module::Build actions either on the command line or in a .modulebuildrc file. The options are passed to the relevant action as you would expect. The exceptions are noted below.

build_base
Specifies the directory where Module::Build should create its build directory. The default is "Build".
build_dir
Same as build_base.
chroot
[version 0.38]

Use this option to specify a directory to chroot into before running build commands. This is useful for testing the build process in a clean environment.

clean_install_base
[version 0.40]

If true, this option will remove the contents of the installation base directory before installing new files. This is useful for ensuring a clean installation, especially when dealing with multiple versions or configurations of a module.

configure_args
[version 0.34]

Arguments to be passed to the configure script (if any). This is useful for modules that rely on external libraries or systems that need specific configuration flags. For example:

perl Build.PL --configure_args "--with-openssl=/opt/openssl"
config_cache
[version 0.34]

A file to store the results of the configure step. This can speed up subsequent builds by avoiding the need to re-run configuration checks. For example:

perl Build.PL --config_cache=config.cache
create_packlist
If true (the default), a packlist file will be created. This file lists all files installed by the distribution, and is used by CPAN clients to keep track of installed files.
extra_compiler_flags
[version 0.38]

Additional flags to pass to the C compiler. This is useful for fine-tuning compilation settings, such as optimization levels or warning flags. For example:

perl Build.PL --extra_compiler_flags "-O3 -Wall"
extra_linker_flags
[version 0.38]

Additional flags to pass to the linker. This is useful for linking against specific libraries or specifying search paths. For example:

perl Build.PL --extra_linker_flags "-L/usr/local/lib"
foreign_perl
[version 0.36]

If true, this option indicates that the distribution is intended for use with a foreign Perl interpreter (e.g., another Perl installation on the system). This can affect how certain build steps are performed, such as compiler and linker searches.

ignore_build_script_diffs
[version 0.3601]

If true, Module::Build will not warn if the Build.PL script has been modified since the distribution was built. The Build script is generated from Build.PL, and a mismatch between them can indicate potential problems. By default, Module::Build checks if the Build script is the same version that was initially invoked when building the distribution (i.e. when the "Build.PL" script was first run). As of 0.3601, a mismatch results in a warning instead of a fatal error, so this option effectively just suppresses the warning.

debug
Prints Module::Build debugging information to STDOUT, such as a trace of executed build actions.

Default Options File (.modulebuildrc)

[version 0.28]

When Module::Build starts up, it will look first for a file, $ENV{HOME}/.modulebuildrc. If it's not found there, it will look in the .modulebuildrc file in the directories referred to by the environment variables "HOMEDRIVE" + "HOMEDIR", "USERPROFILE", "APPDATA", "WINDIR", "SYS$LOGIN". If the file exists, the options specified there will be used as defaults, as if they were typed on the command line. The defaults can be overridden by specifying new values on the command line.

The action name must come at the beginning of the line, followed by any amount of whitespace and then the options. Options are given the same as they would be on the command line. They can be separated by any amount of whitespace, including newlines, as long there is whitespace at the beginning of each continued line. Anything following a hash mark ("#") is considered a comment, and is stripped before parsing. If more than one line begins with the same action name, those lines are merged into one set of options.

Besides the regular actions, there are two special pseudo-actions: the key "*" (asterisk) denotes any global options that should be applied to all actions, and the key 'Build_PL' specifies options to be applied when you invoke "perl Build.PL".

*           verbose=1   # global options
diff        flags=-u
install     --install_base /home/ken
            --install_path html=/home/ken/docs/html
installdeps --cpan_client 'cpanp -i'

If you wish to locate your resource file in a different location, you can set the environment variable "MODULEBUILDRC" to the complete absolute path of the file containing your options.

Environment variables

MODULEBUILDRC
[version 0.28]

Specifies an alternate location for a default options file as described above.

PERL_MB_OPT
[version 0.36]

Command line options that are applied to Build.PL or any Build action. The string is split as the shell would (e.g. whitespace) and the result is prepended to any actual command-line arguments.

INSTALL PATHS

[version 0.19]

When you invoke Module::Build's "build" action, it needs to figure out where to install things. The nutshell version of how this works is that default installation locations are determined from Config.pm, and they may be overridden by using the "install_path" parameter. An "install_base" parameter lets you specify an alternative installation root like /home/foo, and a "destdir" lets you specify a temporary installation directory like /tmp/install in case you want to create bundled-up installable packages.

Natively, Module::Build provides default installation locations for the following types of installable items:

lib
Usually pure-Perl module files ending in .pm.
arch
"Architecture-dependent" module files, usually produced by compiling XS, Inline, or similar code.
script
Programs written in pure Perl. In order to improve reuse, try to make these as small as possible - put the code into modules whenever possible.
bin
"Architecture-dependent" executable programs, i.e. compiled C code or something. Pretty rare to see this in a perl distribution, but it happens.
bindoc
Documentation for the stuff in "script" and "bin". Usually generated from the POD in those files. Under Unix, these are manual pages belonging to the 'man1' category.
libdoc
Documentation for the stuff in "lib" and "arch". This is usually generated from the POD in .pm files. Under Unix, these are manual pages belonging to the 'man3' category.
binhtml
This is the same as "bindoc" above, but applies to HTML documents.
libhtml
This is the same as "libdoc" above, but applies to HTML documents.

Four other parameters let you control various aspects of how installation paths are determined:

installdirs
The default destinations for these installable things come from entries in your system's "Config.pm". You can select from three different sets of default locations by setting the "installdirs" parameter as follows: 
                        'installdirs' set to:
                 core          site                vendor
            uses the following defaults from Config.pm:
lib     => installprivlib  installsitelib      installvendorlib
arch    => installarchlib  installsitearch     installvendorarch
script  => installscript   installsitescript   installvendorscript
bin     => installbin      installsitebin      installvendorbin
bindoc  => installman1dir  installsiteman1dir  installvendorman1dir
libdoc  => installman3dir  installsiteman3dir  installvendorman3dir
binhtml => installhtml1dir installsitehtml1dir installvendorhtml1dir [*]
libhtml => installhtml3dir installsitehtml3dir installvendorhtml3dir [*]
* Under some OS (eg. MSWin32) the destination for HTML documents is
  determined by the C<Config.pm> entry C<installhtmldir>.

The default value of "installdirs" is "site". If you're creating vendor distributions of module packages, you may want to do something like this:

perl Build.PL --installdirs vendor

or

./Build install --installdirs vendor

If you're installing an updated version of a module that was included with perl itself (i.e. a "core module"), then you may set "installdirs" to "core" to overwrite the module in its present location.

(Note that the 'script' line is different from "MakeMaker" - unfortunately there's no such thing as "installsitescript" or "installvendorscript" entry in "Config.pm", so we use the "installsitebin" and "installvendorbin" entries to at least get the general location right. In the future, if "Config.pm" adds some more appropriate entries, we'll start using those.)

install_path
Once the defaults have been set, you can override them.

On the command line, that would look like this:

perl Build.PL --install_path lib=/foo/lib --install_path arch=/foo/lib/arch

or this:

./Build install --install_path lib=/foo/lib --install_path arch=/foo/lib/arch
install_base
You can also set the whole bunch of installation paths by supplying the "install_base" parameter to point to a directory on your system. For instance, if you set "install_base" to "/home/ken" on a Linux system, you'll install as follows: 
lib     => /home/ken/lib/perl5
arch    => /home/ken/lib/perl5/i386-linux
script  => /home/ken/bin
bin     => /home/ken/bin
bindoc  => /home/ken/man/man1
libdoc  => /home/ken/man/man3
binhtml => /home/ken/html
libhtml => /home/ken/html

Note that this is different from how "MakeMaker"'s "PREFIX" parameter works. "install_base" just gives you a default layout under the directory you specify, which may have little to do with the "installdirs=site" layout.

The exact layout under the directory you specify may vary by system - we try to do the "sensible" thing on each platform.

destdir
If you want to install everything into a temporary directory first (for instance, if you want to create a directory tree that a package manager like "rpm" or "dpkg" could create a package from), you can use the "destdir" parameter: 
perl Build.PL --destdir /tmp/foo

or

./Build install --destdir /tmp/foo

This will effectively install to "/tmp/foo/$sitelib", "/tmp/foo/$sitearch", and the like, except that it will use "File::Spec" to make the pathnames work correctly on whatever platform you're installing on.

prefix
[version 0.42]

This is an alias for install_base. It is provided for compatibility with "MakeMaker".

INSTALL PATHS

--prefix <path>
Proporcionado para compatibilidad con el argumento PREFIX de "ExtUtils::MakeMaker". Se debe usar "prefix" cuando desee que Module::Build instale sus módulos, documentación y scripts en el mismo lugar que el mecanismo PREFIX de "ExtUtils::MakeMaker".

Lo siguiente es equivalente.

perl Build.PL --prefix /tmp/foo
perl Makefile.PL PREFIX=/tmp/foo

Debido a la compleja naturaleza de la lógica de prefijación, el comportamiento de PREFIX en "MakeMaker" ha cambiado sutilmente con el tiempo. La lógica de prefijo de --prefix de Module::Build es equivalente a la lógica de PREFIX que se encuentra en "ExtUtils::MakeMaker" 6.30.

Los mantenedores de "MakeMaker" comprenden los problemas con el mecanismo de PREFIX y agregaron soporte para INSTALL_BASE en la versión 6.31 de "MakeMaker", que fue lanzada en 2006.

Si no necesita mantener la compatibilidad con versiones antiguas (anteriores a la 6.31) de "ExtUtils::MakeMaker" o está iniciando una instalación nueva de Perl, le recomendamos que use "install_base" en su lugar (y "INSTALL_BASE" en "ExtUtils::MakeMaker"). Consulte "Installing in the same location as ExtUtils::MakeMaker" en Module::Build::Cookbook para obtener más información.

COMPARACIÓN

Una comparación entre "Module::Build" y otros instaladores de distribuciones CPAN.

  • ExtUtils::MakeMaker requiere "make" y el uso de un Makefile. "Module::Build" no lo hace, ni tampoco otros instaladores puramente perl que siguen la especificación Build.PL como Module::Build::Tiny. En la práctica, esto generalmente no es un problema para el usuario final, ya que "make" ya es necesario para instalar la mayoría de los módulos CPAN, incluso en Windows.
  • ExtUtils::MakeMaker ha sido un módulo principal en todas las versiones de Perl 5 y debe mantener la compatibilidad para instalar la mayoría de los módulos CPAN. "Module::Build" se agregó al núcleo en Perl 5.10 y se eliminó del núcleo en Perl 5.20, y (al igual que ExtUtils::MakeMaker) solo se actualiza para corregir problemas críticos y mantener la compatibilidad. "Module::Build" y otros instaladores no centrales como Module::Build::Tiny se instalan desde CPAN declarándose como una dependencia de la fase de "configure", y de esta manera, cualquier instalador puede usarse en lugar de ExtUtils::MakeMaker.
  • Personalizar el proceso de compilación con ExtUtils::MakeMaker implica anular ciertos métodos que forman el Makefile definiendo las subrutinas en el espacio de nombres "MY::", lo que requiere un conocimiento profundo de Makefile, pero permite la personalización específica de toda la compilación. Personalizar "Module::Build" implica crear una subclase de "Module::Build", agregando o anulando métodos puramente perl que representan acciones de compilación, las cuales se invocan como argumentos pasados al script generado "./Build". Este es un concepto más sencillo, pero requiere redefinir las acciones de compilación estándar para invocar sus personalizaciones. Module::Build::Tiny no permite la personalización.
  • "Module::Build" proporciona más funcionalidades y una mejor experiencia para los autores de distribuciones que ExtUtils::MakeMaker. Sin embargo, las herramientas diseñadas específicamente para la autoría, como Dist::Zilla y sus derivados Dist::Milla y Minilla, proporcionan estas y más funcionalidades, y generan un script de configuración (Makefile.PL/Build.PL) que utilizará cualquiera de los diversos instaladores por separado del lado del usuario final. App::ModuleBuildTiny es una herramienta de autoría independiente alternativa para distribuciones que usan Module::Build::Tiny, la cual requiere solo un simple Build.PL de dos líneas.

POR HACER

El método actual de depender de las marcas de tiempo para determinar si un archivo derivado está desactualizado probablemente no sea escalable, ya que requiere rastrear todas las dependencias hacia atrás, tropieza con problemas en NFS y es, en general, frágil. Sería mejor usar una firma MD5 o similar, si está disponible. Consulte "cons" para ver un ejemplo.
