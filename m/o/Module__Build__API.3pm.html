NAME

Module::Build::API - Referencia de API para desarrolladores de módulos

DESCRIPCION

A continuación se indican algunas de las funciones más importantes de Module::Build. Normalmente no necesitarás interactuar con estas funciones, a menos que quieras heredar de Module::Build. Sin embargo, una de las razones por las que crea este módulo fue para permitir la herencia (y hacerla fácil), por lo que seguramente escribiré más documentación como el interfaz se estabilice.

CONSTRUCTORES

current()
[versión 0.20]

Este método devuelve una copia razonable del objeto Module::Build actual que representa el proceso de construcción en curso. Puedes usar este objeto para consultar su método notes(), investigar sobre módulos instalados, y así sucesivamente. Este es un excelente modo de compartir información entre diferentes partes de tu proceso de construcción. Por ejemplo, puedes preguntar a un usuario un dato durante perl Build.PL, luego uses su respuesta durante una prueba de regresión:

# En Build.PL:
my $color = $build->prompt("What is your favorite color?");
$build->notes(color => $color);
# En t/colortest.t:
use Module::Build;
my $build = Module::Build->current;
my $color = $build->notes('color');
...

El modo actual de implementación del método current() podría tener diferencias menores entre el objeto $build en Build.PL y el en t/colortest.t. Nuestro objetivo es minimizar estas diferencias en futuras versiones de Module::Build, por lo que por favor reporte cualquier anomalía que encuentre.

Una importante excepción: en su implementación actual, current() no funcionará correctamente si has cambiado el directorio desde el cual se invocó Module::Build.

new()
[versión 0.03]

Crea un objeto Module::Build. Los argumentos de la metodología new() se listan a continuación. La mayoría de los argumentos son opcionales, pero debes proporcionar tanto module_name como dist_name, o uno de dist_version o dist_version_from. En otras palabras, debes proporcionar suficiente información para determinar tanto el nombre como la versión de la distribución.

add_to_cleanup
[versión 0.19]

Un array de archivos a eliminar cuando se ejecute el acción clean. Véase también el método add_to_cleanup().

allow_pureperl
[versión 0.4005]

Un booleano que indica si el módulo aún funciona sin sus partes XS. Cuando se construye un módulo XS con --pureperl_only, fallará de otra forma.

auto_configure_requires
[versión 0.34]

Este parámetro determina si Module::Build agregará automáticamente a configure_requires (y build_requires) si no está ya presente. El número de versión requerido será el último 'mayor' release, como se define por el número de versión decimal truncado a dos decimales (por ejemplo, 0.34, en lugar de 0.3402). El valor predeterminado es verdadero.

auto_features
[versión 0.26]

Este parámetro permite establecer características (ver "feature($name)") automáticamente según un conjunto de dependencias previas. Por ejemplo, para un módulo que puede usar opcionalmente bases de datos MySQL o PostgreSQL, podrías usar "auto_features" de esta manera:

my $build = Module::Build->new
  (
   ... otros parámetros aquí...
   auto_features => {
     pg_support    => {
                       description => "Interfaz con bases de datos Postgres",
                       requires    => { 'DBD::Pg' => 23.3,
                                        'DateTime::Format::Pg' => 0 },
                      },
     mysql_support => {
                       description => "Interfaz con bases de datos MySQL",
                       requires    => { 'DBD::mysql' => 17.9,
                                        'DateTime::Format::MySQL' => 0 },
                      },
   }
  );

Para cada característica nombrada, se verificarán los requisitos necesarios. Si no hay fallos, la característica se habilitará (se establecerá a 1). De lo contrario, se mostrarán los fallos y la característica se deshabilitará (se establecerá a 0).

Ve la documentación para "requires" para detalles sobre cómo especificar los requisitos.

autosplit
[versión 0.04]

Un argumento opcional "autosplit" especifica un archivo que se debe ejecutar con la función AutoSplit::autosplit(). Si varios archivos deben ser divididos, el argumento puede ser dado como un array de archivos a dividir.

Generalmente no considero el autosplit como una buena idea, ya que no siempre es claro que autosplit obtiene los beneficios de rendimiento que se esperan. Puede incluso dañar el rendimiento en entornos como mod_perl, donde gran parte del código de un módulo debe cargar durante el arranque.

build_class
[versión 0.28]

La clase Module::Build a usar en el script de construcción. Por defecto es "Module::Build" o la clase nombre pasada o creada por un llamado a "subclass()". Esta propiedad es útil si estás escribiendo un subclass personalizado de Module::Build y tienes un problema de arranque—es decir, tu subclass requiere módulos que no están instalados cuando se ejecuta "perl Build.PL", pero has listado en "build_requires" para que estén disponibles cuando se ejecute "./Build".

build_requires
[versión 0.07]

Módulos listados en esta sección son necesarios para construir y instalar el módulo dado, pero no son necesarios para su uso regular. Esta distinción es importante—permite un control más preciso sobre el cuerpo de módulos instalados y facilita la verificación de dependencias en distribuciones binarias/packagadas del módulo.

Ver la documentación para "PREREQUISITES" en Module::Build::Authoring para detalles sobre cómo especificar los requisitos.

configure_requires
[versión 0.30]

Módulos listados en esta sección deben instalarse antes de configurar este distribución (es decir, antes de ejecutar el script "Build.PL"). Esto podría ser una versión mínima específica de "Module::Build" o cualquier otro módulo que "Build.PL" necesita para hacer su trabajo. Los clientes como "CPAN.pm" o "CPANPLUS" esperan que seleccionen "configure_requires" de "META.yml" y instalen estos elementos antes de ejecutar "Build.PL".

Module::Build puede automáticamente agregar a "configure_requires". Véase "auto_configure_requires" para detalles.

Ver la documentación para "PREREQUISITES" en Module::Build::Authoring para detalles sobre cómo especificar los requisitos.

test_requires
[versión 0.4004]

Módulos listados en esta sección deben instalarse antes de probar la distribución.

Ver la documentación para "PREREQUISITES" en Module::Build::Authoring para detalles sobre cómo especificar los requisitos.

create_packlist

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

[version 0.28]

Si es verdadero, este parámetro indica a Module::Build que cree un archivo .packlist durante la acción "install", así como lo hace "ExtUtils::MakeMaker". El archivo se crea en un subdirectorio de la ubicación de instalación de "arch". Es usado por otras herramientas (CPAN, CPANPLUS, etc.) para determinar qué archivos son parte de una instalación.

El valor por defecto es verdadero. Este parámetro fue introducido en Module::Build versión 0.2609; previamente no se creaban archivos .packlist por Module::Build.

c_source
[version 0.04]

Un argumento opcional "c_source" especifica una carpeta o una referencia a un array de directorios que contengan fuentes de C de las que el resto del proceso de construcción pueda depender. Cualquier archivo ".c" en la carpeta se compilará a archivos objeto. El directorio se agregará a la ruta de búsqueda durante las etapas de compilación y vinculación de cualquier archivo C o XS.

[version 0.3604]

Una lista de directorios puede especificarse utilizando una referencia de array anónimo de strings.

conflicts
[version 0.07]

Los módulos listados en esta sección entran en conflicto serio con el módulo dado. "Module::Build" (o alguna otra herramienta de alto nivel) se negará a instalar el módulo dado si este módulo/versión también está instalado.

Vea la documentación sobre "PREREQUISITES" en Module::Build::Authoring para detalles sobre cómo especificar requisitos.

create_license
[version 0.31]

Este parámetro indica a Module::Build que cree automáticamente un archivo LICENSE en el nivel superior de su distribución, que contenga el texto completo de la licencia elegida por el autor. Esto requiere "Software::License" en la máquina del autor, y también requiere que el parámetro "license" especifique una licencia que el programa conozca.

create_makefile_pl
[version 0.19]

Este parámetro permite usar "Module::Build::Compat" durante la acción "distdir" (o "dist") para crear automáticamente un archivo Makefile.PL para compatibilidad con "ExtUtils::MakeMaker". El valor del parámetro debe ser uno de los estilos mencionados en la documentación de Module::Build::Compat.

Se desaconseja el uso de este parámetro.

create_readme
[version 0.22]

Este parámetro indica a Module::Build que cree automáticamente un archivo README en el nivel superior de su distribución. Actualmente, simplemente utiliza "Pod::Text" (o "Pod::Readme" si está instalado) en el archivo indicado por "dist_version_from" y lo coloca en el archivo README. Este no es el único estilo recomendado para escribir un README, pero parece ser uno común en CPAN.

Si genera un README de esta manera, probablemente sea buena idea crear un archivo INSTALL separado si la información no está en el archivo generado README.

dist_abstract
[version 0.20]

Esta debería ser una breve descripción de la distribución. Se usa cuando se genera metadato para META.yml y PPD. Si no se especifica, "Module::Build" busca el número de versión de la distribución en la sección POD del módulo desde el cual obtiene la versión. Si encuentra una sección POD marcada con "=head1 NAME", busca la primera línea que coincida con "\s+-\s+(.+)" y usa el texto capturado como resumen.

dist_author
[version 0.20]

Esto debería ser algo como "John Doe <jdoe@example.com>", o si hay múltiples autores, se puede especificar una referencia anónima de strings. Se usa cuando se genera metadato para META.yml y PPD. Si no se especifica, "Module::Build" busca el número de versión de la distribución en el módulo desde el cual obtiene la versión. Si encuentra una sección POD marcada con "=head1 AUTHOR", usa el contenido de esa sección.

dist_name
[version 0.11]

Especifica el nombre de esta distribución. Los autores casi nunca tendrán que establecerlo directamente; pueden usar "module_name" para establecer "dist_name" a un valor predeterminado razonable. Sin embargo, algunas distribuciones aglutinadoras como "libwww-perl" o "bioperl" tienen nombres que no corresponden directamente a un nombre de módulo, así que "dist_name" puede establecerse de forma independiente.

dist_suffix
[version 0.37]

Especifica un sufijo opcional a incluir después del número de versión en el nombre de la carpeta (y el archivo tar) de la distribución. El único sufijo actualmente reconocido por PAUSE es 'TRIAL', que indica que la distribución no debe ser indexada. Ejemplo:

Foo-Bar-1.23-TRIAL.tar.gz

Esto hará lo correcto automáticamente según "dist_version" y "release_status". Cuando "dist_version" no tenga un guion y "release_status" no sea 'stable', el valor predeterminado de "dist_suffix" será 'TRIAL'. De lo contrario, se usarán los valores predeterminados, que desactivan el sufijo.

En general, los autores solo deberían establecer esto si por un propósito específico necesitan anular el comportamiento predeterminado.

dist_version
[version 0.11]

Especifica un número de versión para la distribución. Vea "module_name" o "dist_version_from" para formas de establecerlo automáticamente a partir de una variable $VERSION en un módulo. De alguna manera u otra, se necesita establecer un número de versión.

dist_version_from
[version 0.11]

Especifica un archivo para buscar la versión de la distribución. Los autores casi nunca tendrán que establecerlo directamente; pueden usar "module_name" para establecerlo a un valor predeterminado razonable.

La versión se extrae de este archivo según las mismas reglas que ExtUtils::MakeMaker y "CPAN.pm". Implica encontrar la primera línea que coincida con el patrón regular:

/([\$*])(([\w\:\']*)\bVERSION)\b.*\=/

eval() esa línea, luego verificando el valor de la variable $VERSION. Tan feo como es, pero todos los módulos en CPAN dependen de este proceso, así que no hay posibilidad real de cambiar a algo mejor.

Si el archivo de destino de "dist_version_from" contiene más de una declaración de paquete, la versión devuelta será la que corresponda al módulo configurado "module_name".

dynamic_config
[version 0.07]

Un indicador booleano que indica si Build.PL debe ejecutarse para determinar los requisitos o si pueden ser determinados consultando solo su archivo de metadatos. La razón principal para establecer esto a verdadero es que tu módulo agrega o elimina requisitos dinámicamente en Build.PL. Si el indicador no se omite, se considerará verdadero, ya que es un modo más seguro de comportamiento.

Actualmente "Module::Build" no hace nada con este indicador; es el trabajo de herramientas de alto nivel como "CPAN.pm" lo que lo hace útil. También puede ser muy útil para análisis estático. Vea "dynamic_config" en CPAN::Meta::Spec para detalles sobre el campo de metadatos.

extra_compiler_flags
extra_linker_flags
[version 0.19]

Estos parámetros pueden contener referencias a arrays (o strings, en los cuales se dividirán en arrays) para pasar a través de los pasos de compilación y vinculación de código C. Por ejemplo, para indicar al compilador que tu código es C++, podrías hacer:

my $build = Module::Build->new
  (
   module_name          => 'Foo::Bar',
   extra_compiler_flags => ['-x', 'c++'],
  );

Para vincular tu código XS con glib podrías escribir algo así:

my $build = Module::Build->new
  (
   module_name          => 'Foo::Bar',
   dynamic_config       => 1,
   extra_compiler_flags => scalar `glib-config --cflags`,
   extra_linker_flags   => scalar `glib-config --libs`,
  );
extra_manify_args
[version 0.4006]

Cualquier argumento adicional a pasar a "Pod::Man->new()" durante la construcción de páginas man. Una elección común podría ser "utf8 => 1" para obtener soporte para Unicode.

get_options
[version 0.26]

Puedes pasar opciones de línea de comandos arbitrarias a Build.PL o a Build, y estas se almacenarán en el objeto Module::Build y podrán ser accedidas mediante el método args(). Sin embargo, a veces quieres más flexibilidad en el procesamiento de argumentos de la que permite. En tales casos, usa el parámetro "get_options" para pasar un mapa de argumentos.

especificaciones, y la lista de argumentos para Build.PL o Build se procesará de acuerdo con esas especificaciones antes de pasarlos al propio procesamiento de argumentos de "Module::Build".

Las claves admitidas para la especificación de opciones son:

type
El tipo de opción. Los tipos son los admitidos por Getopt::Long; consulta su documentación para una lista completa. Los tipos típicos son "=s" para cadenas, "+" para opciones aditivas y "!" para opciones que se pueden negar. Si el tipo no se especifica, se considerará un booleano, es decir, no se tomará ningún argumento y se asignará un valor de 1 cuando se encuentre la opción.
store
Una referencia a un escalar en el que almacenar el valor pasado a la opción. Si no se especifica, el valor se almacenará bajo el nombre de la opción en el hash devuelto por el método args().
default
Un valor predeterminado para la opción. Si no se especifica ningún valor predeterminado y no se pasa ninguna opción, la clave de la opción no existirá en el hash devuelto por args().

Puede combinar referencias a sus propias variables o subrutinas con especificaciones sin referencia, para las cuales el resultado también se almacenará en el hash devuelto por args(). Por ejemplo:

my $loud = 0;
my $build = Module::Build->new
  (
   module_name => 'Foo::Bar',
   get_options => {
                   Loud =>     { store => \$loud },
                   Dbd  =>     { type  => '=s'   },
                   Quantity => { type  => '+'    },
                  }
  );
print STDERR "HEY, ARE YOU LISTENING??\n" if $loud;
print "We'll use the ", $build->args('Dbd'), " DBI driver\n";
print "Are you sure you want that many?\n"
  if $build->args('Quantity') > 2;

Los argumentos para dicha especificación se pueden llamar así:

perl Build.PL --Loud --Dbd=DBD::pg --Quantity --Quantity --Quantity

ADVERTENCIA: Cualquier especificación de opción que entre en conflicto con las propias opciones de Module::Build (definidas por sus propiedades) generará una excepción. Utilice nombres de opción en mayúsculas para evitar conflictos no deseados con futuras opciones de Module::Build.

Consulte la documentación de Getopt::Long para obtener detalles sobre su uso.

Especifica cualquier directorio adicional en el que buscar archivos de encabezado de C. Puede proporcionarse como una cadena que indica un único directorio, o como una referencia a una lista que indica varios directorios.

meta_add
[versión 0.28]

Un hash de pares clave/valor que deben añadirse al archivo META.yml durante la acción "distmeta". Cualquier entrada existente con los mismos nombres se sobrescribirá.

Consulte la sección "MODULE METADATA" para obtener detalles.

meta_merge
[versión 0.28]

Un hash de pares clave/valor que deben fusionarse en el archivo META.yml durante la acción "distmeta". Cualquier entrada existente con los mismos nombres se sobrescribirá.

La única diferencia entre "meta_add" y "meta_merge" es su comportamiento en entradas con valores de hash y de array: "meta_add" eliminará por completo el valor de hash o array existente, pero "meta_merge" fusionará los datos suministrados en el valor de hash o array existente.

Consulte la sección "MODULE METADATA" para obtener detalles.

module_name
[versión 0.03]

El "module_name" es un atajo para establecer valores predeterminados de "dist_name" y "dist_version_from", reflejando el hecho de que la mayoría de las distribuciones de CPAN se centran en un único módulo "principal". Por ejemplo, si establece "module_name" a "Foo::Bar", entonces "dist_name" se establecerá predeterminadamente a "Foo-Bar" y "dist_version_from" se establecerá predeterminadamente a "lib/Foo/Bar.pm". "dist_version_from" se utilizará a su vez para establecer "dist_version".

Establecer "module_name" no anulará un parámetro "dist_*" que especifique explícitamente.

PL_files
\n
[versión 0.06]\n

Un parámetro opcional que especifica un conjunto de archivos \".PL\" en tu distribución. Estos se ejecutarán como scripts Perl antes de procesar el resto de los archivos de tu distribución con el nombre del archivo que están generando como argumento. Generalmente se utilizan como plantillas para crear dinámicamente otros archivos, de modo que un archivo como \"lib/Foo/Bar.pm.PL\" podría crear el archivo \"lib/Foo/Bar.pm\".

\n

Los archivos se especifican con los archivos \".PL\" como claves de hash y los archivos que generan como valores de hash, así:

\n 
my $build = Module::Build->new\n  (\n   module_name => 'Foo::Bar',\n   ...\n   PL_files => { 'lib/Foo/Bar.pm.PL' => 'lib/Foo/Bar.pm' },\n  );\n
\n

Ten en cuenta que las especificaciones de ruta se dan *siempre* en formato tipo Unix, no en el estilo del sistema local.

\n

Si tus scripts \".PL\" no crean ningún archivo, o si crean archivos con nombres inesperados, o incluso si crean varios archivos, puedes indicarlo para que Module::Build pueda manejar correctamente estos archivos creados:

\n 
PL_files => {\n             'lib/Foo/Bar.pm.PL' => 'lib/Foo/Bar.pm',\n             'lib/something.PL'  => ['/lib/something', '/lib/else'],\n             'lib/funny.PL'      => [],\n            }\n
\n

Aquí tienes un ejemplo de un archivo PL simple.

\n 
my $output_file = shift;\nopen my $fh, \">\", $output_file or die \"Can't open $output_file: $!\" ;\nprint $fh <<'END';\n#!/usr/bin/perl\nprint \"Hello, world!\\n\";\nEND\n
\n

Los archivos PL no se instalan por defecto, por lo que es seguro colocarlos en lib/ y bin/.

pm_files
\n
[versión 0.19]\n

Un parámetro opcional que especifica el conjunto de archivos \".pm\" en esta distribución, especificado como una referencia de hash cuyas claves son las ubicaciones de los archivos en las distribuciones, y cuyos valores son sus ubicaciones lógicas basadas en el nombre de su paquete, es decir, dónde se encontrarían en una distribución \"normal\" estilo Module::Build. Este parámetro está diseñado principalmente para soportar diseños alternativos de archivos.

\n

Por ejemplo, si tienes una distribución antigua estilo \"MakeMaker\" para un módulo llamado \"Foo::Bar\" y un archivo Bar.pm en el nivel superior de la distribución, podrías especificar tu diseño en tu \"Build.PL\" así:

\n

Adds a property to a "Module::Build" class. Properties are those attributes of a "Module::Build" object that can be passed into the constructor and have accessors for getting and setting. All of the core properties, such as "module_name" and "license", are defined using this method.

The first argument to add_property() is always the name of the property. The second argument can be a default value for the property, or a list of key/value pairs. Supported keys are:

"default"
The default value. May optionally be specified as a coderef, in which case the return value from executing the coderef will be used. If you need the default value to be a coderef, just use a coderef to return it, e.g.: 
default => sub { sub { ... } },
"check"
A coderef that verifies that the specified value for the property is valid. During execution of the coderef, the new value will be in the $_ variable. If the value is okay, the "check" coderef should return true. If the value is not okay, it should issue an error message via "property_error() and return false.

print $build->pedantic, $/;

print "stuff{foo} is: ", $build->stuff( 'foo' ), $/;
$build->stuff( foo => 'bar' );
print $build->stuff( 'foo' ), $/; # Outputs "bar"

You can also set the entire hashref of key/value pairs directly:

$build->stuff( { foo => 'bar', baz => 'yo' } );

In either case, if a "check" has been specified for the property, it will be applied to the entire hash. Thus, the check coderef should look something like this:

check => sub {

      return 0;

check_installed_status($module, $version)
[version 0.11]

Este método devuelve una referencia a un hash que indica si se satisface una dependencia de versión en un módulo determinado. El argumento $module se proporciona como una cadena como "Data::Dumper" o "perl", y el argumento $version puede tomar cualquiera de las formas descritas en "requires" anteriormente. Esto permite una verificación de versiones muy detallada.

La referencia al hash devuelta tiene la siguiente estructura:

{
 ok => $si_la_dependencia_se_satisface,
 have => $version_ya_instalada,
 need => $version_solicitada, # Igual que el argumento entrante $version
 message => $mensaje_de_error_informativo,
}

check_installed_version($module, $version)
[version 0.05]

Al igual que check_installed_status(), pero simplemente devuelve verdadero o falso dependiendo de si el módulo $module satisface la dependencia $version.

Si la verificación tiene éxito, el valor de retorno es la versión real de $module instalada en el sistema. Esto le permite hacer lo siguiente:

my $installed = $build->check_installed_version('DBI', '1.15');

  print "Felicitaciones, la versión $installed de DBI está instalada.\n";
} else {
  die "Lo siento, debes instalar DBI.\n";
}

Si la verificación falla, devolvemos falso y establecemos $@ a un mensaje de error informativo.

En general, es posible que prefiera usar "check_installed_status" si necesita información detallada, o este método si solo necesita una respuesta de sí/no.

[versión 0.36]

Este método devuelve una referencia a un hash de metadatos que puede usarse para crear un flujo de datos YAML. Se proporciona para que los autores puedan anular o personalizar los campos de META.yml. Por ejemplo:

package My::Builder;  
use base 'Module::Build';  
sub get_metadata {  
  my $self, @args = @_;  
  my $data = $self->SUPER::get_metadata(@args);  
  $data->{custom_field} = 'foo';  
  return $data;  
}

Los argumentos válidos incluyen:

  • "fatal": indica si la ausencia de campos de metadatos requeridos debe ser un error fatal o no. Para la creación de META, generalmente debería serlo, pero para la creación de MYMETA para usuarios finales, no debería ser fatal.

prereq_failures()
[versión 0.11]

Devuelve una estructura de datos que contiene información sobre cualquier prerrequisito fallido (de cualquiera de los tipos descritos anteriormente), o "undef" si todos los prerrequisitos se cumplen.

La estructura de datos devuelta es una referencia a un hash. Las claves de nivel superior son el tipo de prerrequisito fallido, uno de "requires", "build_requires", "conflicts", o "recommends". Los valores asociados son referencias a hash cuyas claves son los nombres de los módulos requeridos (o conflictivos). Los valores asociados de estos son referencias a hash que indican alguna información sobre el fallo. Por ejemplo:

{  
 have => '0.42',  
 need => '0.59',  
 message => 'Se instaló la versión 0.42, pero necesitamos la versión 0.59',  
}
>

o

{
 tengo => '<ninguno>',
 necesito => '0.59',
 mensaje => 'La dependencia Foo no está instalada',
}

Este hash tiene la misma estructura que el hash devuelto por el método check_installed_status(), excepto que en el caso de dependencias de "conflictos" cambiamos la clave "need" por "conflicts" y construimos un mensaje adecuado.

# Comprobar una dependencia requerida de Foo::Bar
si ( $build->prereq_failures->{requires}{Foo::Bar} ) { ...
# Comprobar si hubo algún fallo
si ( $build->prereq_failures ) { ...
# Mostrar mensajes para todos los fallos
mi $failures = $build->prereq_failures;
mientras (mi ($type, $list) = each %$failures) {
  mientras (mi ($name, $hash) = each %$list) {
    imprimir "Fallo para $name: $hash->{message}\n";
  }
}

prompt($message, $default)
[versión 0.12]

Hace una pregunta al usuario y devuelve su respuesta como una cadena. El primer argumento especifica el mensaje a mostrar al usuario (por ejemplo, "¿Dónde guardas tu dinero?"). rscan_dir($dir, $pattern)
[versión 0.28]

Utiliza "File::Find" para recorrer el directorio $dir, devolviendo una referencia a un array de entradas que coinciden con $pattern. $pattern puede ser una expresión regular (usando "qr//" o simplemente una cadena de texto), o una referencia a una subrutina que devolverá verdadero para las entradas deseadas. # Todos los archivos *.pm en lib/

# Todos los archivos en t/
$m->rscan_dir('t');
