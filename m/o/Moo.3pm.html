NOMBRE

Moo - Orientación a objetos minimalista (con compatibilidad con Moose)

SINOPSIS

package Cat::Food;
use Moo;
use strictures 2;
use namespace::clean;
sub feed_lion {
  my $self = shift;
  my $amount = shift || 1;
  $self->pounds( $self->pounds - $amount );
}
has taste => (
  is => 'ro',
);
has brand => (
  is  => 'ro',
  isa => sub {
    die "Solo SWEET-TREATZ soportado!" unless $_[0] eq 'SWEET-TREATZ'
  },
);
has pounds => (
  is  => 'rw',
  isa => sub { die "$_[0] es demasiado comida de gato!" unless $_[0] < 15 },
);
1;

Y en otro lugar:

my $full = Cat::Food->new(
    taste  => 'DELICIOUS.',
    brand  => 'SWEET-TREATZ',
    pounds => 10,
);
$full->feed_lion;
say $full->pounds;

DESCRIPCIÓN

"Moo" es un sistema de orientación a objetos extremadamente ligero. Permite definir objetos y roles de forma concisa con una sintaxis conveniente que evita los detalles del sistema de objetos de Perl. "Moo" contiene un subconjunto de Moose y está optimizado para una rápida inicialización.

"Moo" evita depender de módulos XS para permitir implementaciones simples. El nombre "Moo" se basa en el concepto de que proporciona casi, pero no exactamente, dos tercios de Moose. Por lo tanto, Moose::Manual puede servir como una guía efectiva para "Moo" aparte de los capítulos MOP y Types.

A diferencia de Mouse, este módulo no busca compatibilidad total con la sintaxis superficial de Moose, sino que prefiere la interoperabilidad total mediante las capacidades de inflación de metaclasses descritas en "MOO Y MOOSE".

Para una lista completa de las diferencias menores entre Moose y la sintaxis superficial de Moose, ve "INCOMPATIBILIDAD CON MOOSE".

¿POR QUÉ EXISTE MOO?

Si deseas un sistema de orientación a objetos con un rico Metaprotocolo, Moose ya es admirable.

Pero si no quieres usar Moose, tal vez no quieras tener un «metaprotocolo menos» como Mouse ofrece, pero probablemente quieras no tener un «metaprotocolo» en absoluto, lo que es lo que Moo proporciona.

  • Un script de línea de comandos o un script CGI donde es esencial una rápida inicialización
  • Código diseñado para ser desplegado como un único archivo mediante App::FatPacker
  • Un módulo CPAN que pueda ser utilizado por otros en las situaciones mencionadas anteriormente

"Moo" mantiene compatibilidad transparente con Moose, así que si instalas y cargas Moose, puedes usar clases y roles de Moo en el código de Moose sin modificaciones.

Moo — Orientación a objetos minimalista — busca facilitar la actualización a Moose cuando necesites más de las características mínimas ofrecidas por Moo.

MOO Y MOOSE

Si Moo detecta que Moose está cargado, registrará automáticamente metaclasses para tus paquetes Moo y Moo::Role, así que deberías poder usarlos en el código de Moose sin modificaciones.

Moo también creará restricciones de tipo para clases y roles de Moo, así que en clases de Moose "isa => 'MyMooClass'" y "isa => 'MyMooRole'" funcionarán de la misma manera que en clases de Moose y roles.

La herencia de una clase de Moose o el consumo de un Moose::Role también funcionarán.

La herencia de una clase de Mouse o el consumo de un Mouse::Role también funcionarán. Sin embargo, ten en cuenta que no proporcionamos metaclasses o metaroles de Mouse, por lo que el otro sentido no funciona. Esta característica existe para los usuarios de Any::Moose que se migran a Moo; permitir que los usuarios de Mouse usen clases de Moo no es una prioridad para nosotros.

Esto significa que no se necesita nada como Any::Moose para el código de Moo — los códigos de Moo y Moose deberían interactuar sin problemas. Para manejar el código de Mouse, probablemente necesitarás una clase o rol vacío de Moo o extender o consumir el código de Mouse, ya que no registra metaclasses reales de Moose como hace Moo.

Si necesitas deshabilitar la creación de metaclasses, añade:

no Moo::sification;

a tu código antes de cargar Moose, pero ten en cuenta que este interruptor es global y desactiva completamente el mecanismo, así que no lo colocarás en código de librería.

MOO Y CLASS::XSACCESSOR

Si una versión nueva de Class::XSAccessor está disponible, se utilizará para generar accesores simples, lectores y escritores para un mejor rendimiento. Los accesores simples son aquellos que no tienen valores predeterminados diferidos, validaciones de tipo o coerciones, o disparadores. Los lectores simples son aquellos que no tienen valores predeterminados diferidos. Los accesores y lectores generados por Class::XSAccessor se comportarán de manera ligeramente diferente: rechazarán intentos de llamarlos con el número incorrecto de parámetros.

MOO VS ANY::MOOSE

Any::Moose cargará Mouse normalmente, y Moose en un programa usando Moose — teóricamente permite obtener el tiempo de inicialización de Mouse sin desventaja para los usuarios de Moose.

Sin embargo, esto no funciona completamente, ya que la selección depende del orden de carga — el sistema de inflación de metaclasses explicado anteriormente en "MOO Y MOOSE" es significativamente más confiable.

Por lo tanto, si quieres escribir un módulo CPAN que cargue rápido o tenga solo dependencias puras de Perl pero también sea completamente utilizable por los usuarios de Moose, debes estar utilizando Moo.

Para una explicación completa, ve el artículo https://shadow.cat/blog/matt-s-trout/moo-versus-any-moose, que explica estrategias diferentes de manera más detallada y proporciona un ejemplo directo donde Moo es exitoso y Any::Moose falla.

MÉTODOS PÚBLICOS

Moo proporciona varios métodos para cualquier clase que lo use.

new

Foo::Bar->new( attr1 => 3 );

o

Foo::Bar->new({ attr1 => 3 });

El constructor de la clase. Por defecto, acepta atributos como un mapa clave-valor, o como una lista de pares clave-valor. Puedes personalizarlo con el método BUILDARGS.

does

if ($foo->does('Some::Role1')) {
  ...
}

Devuelve verdadero si el objeto compone el rol pasado.

DOES

if ($foo->DOES('Some::Role1') || $foo->DOES('Some::Class1')) {
  ...
}

Similar a "does", pero también devuelve verdadero para roles compuestos y superclases.

meta

my $meta = Foo::Bar->meta;
my @methods = $meta->get_method_list;

Devuelve un objeto que se comportará como si fuera un objeto de metaclass de Moose para la clase. Si se llama a cualquier método aparte de "make_immutable", el objeto se actualizará transparentemente a un instanciador real de Moose::Meta::Class, cargando Moose si es necesario. "make_immutable" en sí mismo es un NOP, ya que generamos metaclasses que ya son inmutables, y los usuarios que se pasan de Moose tenían una tendencia desfavorable de cargar Moose accidentalmente al llamarlo.

MÉTODOS DE CICLO DE VIDA

Hay varios métodos que puedes definir en tu clase para controlar la creación y destrucción de objetos. Deben usarse en lugar de intentar modificar "new" o "DESTROY" por ti mismo.

BUILDARGS

around BUILDARGS => sub {
  my ( $orig, $class, @args ) = @_;
  return { attr1 => $args[0] }
    if @args == 1 && !ref $args[0];
  return $class->$orig(@args);
};
Foo::Bar->new( 3 );

Este método de clase se usa para transformar los argumentos en "new" en un mapa de valores de atributo.

La implementación por defecto transforma los argumentos en un mapa de valores de atributo.

SUBRUTINAS IMPORTADAS

extends

extends 'Clase::Padre';

Declara una clase base. Se pueden pasar múltiples superclases para herencia múltiple, pero por favor considera usar roles en su lugar. La clase será cargada, pero no se generarán errores si la clase no se puede encontrar y ya existen subs en la clase.

Llamar a extends más de una vez REEMPLAZARÁ tus superclases, no las añadirá como lo haría use base.

with

with 'Rol::Alguno';

o

with 'Rol::Alguno', 'Rol::AlgunoDos';

Compone uno o más roles de Moo::Role (o Role::Tiny) en la clase actual. Se generará un error si estos roles no se pueden componer debido a definiciones de métodos conflictivas. Los roles se cargarán utilizando el mismo mecanismo que utiliza "extends".

has

has attr => (
  is => 'ro',
);

Declara un atributo para la clase.

package Foo;
use Moo;
has 'attr' => (
  is => 'ro'
);
package Bar;
use Moo;
extends 'Foo';
has '+attr' => (
  default => sub { "blah" },
);

Usando la notación "+", es posible anular un atributo.

has [qw(attr1 attr2 attr3)] => (
  is => 'ro',
);

Usando un arrayref con múltiples nombres de atributos, es posible declarar múltiples atributos con las mismas opciones.

Las opciones para "has" son las siguientes:

"is"
requerido, puede ser "ro", "lazy", "rwp" o "rw".

"ro" significa "solo lectura" y genera un accesor que muere si intentas escribir en él - es decir, solo un getter - estableciendo "reader" por defecto al nombre del atributo.

"lazy" genera un lector como "ro", pero también establece "lazy" a 1 y "builder" a "_build_${nombre_atributo}" para permitir atributos generados bajo demanda. Esta característica fue mi intento de arreglar mi incompetencia al diseñar originalmente "lazy_build", y también es implementada por MooseX::AttributeShortcuts. Sin embargo, no hay nada que te impida usar "lazy" y "builder" tú mismo con "rwp" o "rw" - es solo que generalmente no es una buena idea, así que no proporcionamos un atajo para ello.

"rwp" significa "lectura-escritura protegida" y genera un lector como "ro", pero también establece "writer" a "_set_${nombre_atributo}" para atributos que están diseñados para ser escritos desde dentro de la clase, pero de solo lectura desde fuera. Esta característica proviene de MooseX::AttributeShortcuts.

"rw" significa "lectura-escritura" y genera un getter/setter normal estableciendo "accessor" por defecto al nombre del atributo especificado.

"isa"
Toma un coderef que se utiliza para validar el atributo. A diferencia de Moose, Moo no incluye un sistema de tipos básico, por lo que en lugar de hacer "isa => 'Num'", uno debería hacer 
use Scalar::Util qw(looks_like_number);
...
isa => sub {
  die "$_[0] no es un número!" unless looks_like_number $_[0]
},

Nota que el valor de retorno para "isa" se descarta. Solo si el sub muere, la validación de tipo falla.

Consciente de Sub::Quote

Dado que Moo no ejecuta la verificación "isa" antes de "coerce" si se ha proporcionado una subrutina de coerción, las verificaciones de "isa" no son estructurales para tu código y pueden, si se desea, omitirse en compilaciones de depuración (aunque si esto resulta en un error no capturado que rompe tu programa, los autores de Moo no garantizan nada más que que te quedas con ambas mitades).

Si deseas tipos con nombres compatibles con Moose o estilo MooseX::Types, mira Type::Tiny.

Para hacer que tus entradas de "isa" se mapeen automáticamente a objetos Moose::Meta::TypeConstraint nombrados (en lugar del comportamiento por defecto de crear un tipo anónimo), establece:

$Moo::HandleMoose::TYPE_MAP{$isa_coderef} = sub {
  require MooseX::Types::Something;
  return MooseX::Types::Something::TypeName();
};

Ten en cuenta que este ejemplo es puramente ilustrativo; cualquier cosa que devuelva un objeto Moose::Meta::TypeConstraint o algo lo suficientemente similar como para que Moose esté contento está bien.

"coerce"
Toma un coderef que se supone que debeで coerción para el atributo. La idea básica es hacer algo como lo siguiente: 
coerce => sub {
  $_[0] % 2 ? $_[0] : $_[0] + 1
},

Nota que Moo siempre ejecutará tu coerción: esto es para permitir que las entradas "isa" se utilicen puramente para atrapar errores, mientras que las coerciones son siempre estructurales para tu código. Sin embargo, aplicamos cualquier verificación "isa" proporcionada después de que la coerción se haya ejecutado para asegurar que devolvió un valor válido.

Consciente de Sub::Quote

Si la opción "isa" es un objeto bendecido que proporciona un método "coerce" o "coercion", entonces la opción "coerce" puede establecerse simplemente a 1.

"handles"
Toma una cadena 
handles => 'RolRobot'

Donde "RolRobot" es un rol que define una interfaz que se convierte en la lista de métodos a manejar.

Toma una lista de métodos

handles => [ qw( uno dos ) ]

Toma un hashref

handles => {
  un => 'uno',
}
"trigger"
Toma un coderef que se llamará cada vez que se establezca el atributo. Esto incluye el constructor, pero no los valores por defecto o construidos. El coderef se invocará contra el objeto con el nuevo valor como argumento.

Si estableces esto a solo 1, genera un trigger que llama al método "_trigger_${nombre_attr}" en $self. Esta característica proviene de MooseX::AttributeShortcuts.

Ten en cuenta que Moose también pasa el valor anterior, si lo hay; esta característica aún no es compatible.

Consciente de Sub::Quote

"default"
Toma un coderef que se llamará con $self como su único argumento para poblar un atributo si no se proporcionó ningún valor para ese atributo al constructor. Alternativamente, si el atributo es perezoso, "default" se ejecuta cuando el atributo se recupera por primera vez si aún no se ha proporcionado ningún valor.

Si se proporciona un escalar simple, se insertará como una cadena. Cualquier referencia que no sea un código (hash, array) resultará en un error; para ese caso, usa en su lugar una referencia de código que devuelva el valor deseado.

Ten en cuenta que si tu valor por defecto se activa durante new(), no hay garantía de que otros atributos ya se hayan poblado, por lo que no debes confiar en su existencia.

NAME

Moo - modern object framework

SYNOPSIS

 package MyClass;
 use Moo;
 has 'foo';
 has 'bar' => (
     is       => 'ro',
     isa      => 'Int',
     required => 1,
 );

DESCRIPTION

Moo is a modern object framework. It implements a number of useful features from Moose, but without the overhead of a full metaprotocol. It is intended for use in situations where performance is a concern, but you still want a sensible object system.

Moo provides a simple, clean object system that will feel familiar to users of Moose. It supports attributes, roles, and method overrides.

WHY MOO EXISTS

Moo exists to provide a faster, lighter object system than Moose. Moose is a very powerful and extensible object system, but it carries a significant amount of overhead. Moo aims to provide the most commonly used features of Moose, but in a way that is much more performant.

Moo is not a replacement for Moose. If you need the full power and extensibility of Moose, then you should continue to use Moose. Moo is for those who need a simpler, faster object system.

MOO AND MOOSE

Moo is largely compatible with Moose. Most Moose code can be run under Moo with little or no modification. The main differences are:

Metaprotocol
Moo does not have a metaprotocol. This means that Moo objects cannot be introspected or modified at runtime in the same way that Moose objects can. This is the primary reason for Moo's improved performance.
Extensions
Some Moose extensions may not work with Moo. This is because many extensions rely on the Moose metaprotocol. If you need an extension that does not work with Moo, you may need to use Moose instead.

However, for many common use cases, Moo provides a perfectly adequate replacement for Moose. If you are writing new code and do not need the full power of Moose, Moo is often a good choice.

MOO AND CLASS::XSACCESSOR

Moo has similar goals to Class::XSAccessor, in that it aims to provide fast attribute access. Moo achieves this by using optimised C code where possible, and by using Perl's built-in fast subroutines where not. However, Moo is a more complete object system than Class::XSAccessor, providing features such as roles, method overrides, and attribute constraints.

MOO VERSUS ANY::MOOSE

Moo and Any::Moose are both attempts to provide a lighter alternative to Moose. However, they take different approaches:

Moo
Moo aims to provide a subset of Moose's features, but with a focus on performance. It achieves this by not implementing a full metaprotocol.
Any::Moose
Any::Moose is a compatibility layer that tries to provide a Moose-like API, but can fall back to other object systems (such as Moo or Moose itself) if necessary. This makes it very flexible, but it can be slower than Moo.

If you need the absolute fastest object system possible, Moo is likely the better choice. If you need maximum flexibility and compatibility, Any::Moose may be more suitable.

PUBLIC METHODS

Moo provides the following public methods:

new
Creates a new instance of the class.
does
Checks if the object or class does a given role.
meta
Returns the metaclass object for the class or object.

LIFECYCLE METHODS

Moo provides the following lifecycle methods:

BUILDARGS
Called by new to process constructor arguments.
BUILD
Called after the object has been created and attributes have been set.
DEMOLISH
Called just before the object is destroyed.

IMPORTED SUBROUTINES

When you use Moo, the following subroutines are imported into your package's namespace:

has
Declares an attribute.
coerce
Coerces a value to a given type.
does
Checks if a class or object does a given role.
enum
Creates an enumeration type.
inline_all_lvalue_subs
inline_constructor
inline_has_methods
inline_maybe_lvalue_subs
inline_only_lvalue_subs
inline_required_methods
inline_subtype_methods
inline_typed_lvalue_subs
inline_type_methods
inline_unsafe_lvalue_subs
inline_xs_accessor
inline_xs_constructor
inline_xs_methods
inline_xs_required_methods
inline_xs_subtype_methods
inline_xs_type_methods
make_immutable
Makes the class immutable. This is done automatically by Moo the first time new is called.
override
Overrides a method from a parent class or role.
role
Declares a role.
with
Applies roles to a class.

SUB QUOTE AWARE

Subroutines imported by Moo are quote-aware. This means that they will correctly handle quoted strings and barewords.

CLEANING UP IMPORTS

If you wish to avoid importing any of these subroutines into your package's namespace, you can do so using the :all tag:

 package MyClass;
 use Moo ':all';

This will import all of the subroutines into your namespace. If you want to import only a subset of the subroutines, you can specify them individually:

 package MyClass;
 use Moo 'has', 'override';

INCOMPATIBILITIES WITH MOOSE

The biggest incompatibility between Moo and Moose is the lack of a metaprotocol in Moo. This means that some features that rely on the Moose metaprotocol will not work with Moo. These include:

  • Meta-programming features that rely on the Moose metaprotocol.
  • Some Moose extensions that rely on the Moose metaprotocol.

In addition, Moo does not support some of the more advanced features of Moose, such as:

  • Chained constructors.
  • Advanced attribute composition.

However, for most common use cases, Moo is a drop-in replacement for Moose. If you are writing new code and do not need the full power of Moose, Moo is often a good choice.

The nearest Moose invocation would be:

package MyClass;
use Moose;
use warnings FATAL => "all";
use MooseX::AttributeShortcuts;

or, if you're inheriting from a non-Moose class,

package MyClass;
use Moose;
use MooseX::NonMoose;
use warnings FATAL => "all";
use MooseX::AttributeShortcuts;

META OBJECT

There is no meta object. If you need this level of complexity you need Moose - Moo is small because it explicitly does not provide a metaprotocol. However, if you load Moose, then

Class::MOP::class_of($moo_class_or_role)

will return an appropriate metaclass pre-populated by Moo.

IMMUTABILITY

Finally, Moose requires you to call

__PACKAGE__->meta->make_immutable;

at the end of your class to get an inlined (i.e. not horribly slow) constructor. Moo does it automatically the first time ->new is called on your class. ("make_immutable" is a no-op in Moo to ease migration.)

An extension MooX::late exists to ease translating Moose packages to Moo by providing a more Moose-like interface.

COMPATIBILITY WITH OLDER PERL VERSIONS

Moo is compatible with perl versions back to 5.6. When running on older versions, additional prerequisites will be required. If you are packaging a script with its dependencies, such as with App::FatPacker, you will need to be certain that the extra prerequisites are included.

MRO::Compat
Required on perl versions prior to 5.10.0.
Devel::GlobalDestruction
Required on perl versions prior to 5.14.0.
