Module::Build::Authoring(3pm) Documentación aportada por el usuario de Perl Module::Build::Authoring(3pm)

NOMBRE

Module::Build::Authoring - Creación de módulos Module::Build

DESCRIPCIÓN

Al crear un script "Build.PL" para un módulo, normalmente se utilizará un código similar al siguiente:

use Module::Build;
my $build = Module::Build->new
  (
   module_name => 'Foo::Bar',
   license  => 'perl',
   requires => {
                'perl'          => '5.6.1',
                'Some::Module'  => '1.23',
                'Other::Module' => '>= 1.2, != 1.5, < 2.0',
               },
  );
$build->create_build_script;

Un módulo simple podría arreglárselas con algo tan corto como esto para su script "Build.PL":

use Module::Build;
Module::Build->new(
  module_name => 'Foo::Bar',
  license     => 'perl',
)->create_build_script;

El modelo utilizado por "Module::Build" es muy parecido a la metáfora de "MakeMaker", con las siguientes correspondencias:

 En Module::Build                 En ExtUtils::MakeMaker
---------------------------      ------------------------
 Build.PL (script inicial)        Makefile.PL (script inicial)
 Build (un script perl corto)     Makefile (un Makefile largo)
 _build/ (información de estado   varios textos de configuración en el Makefile
 guardada)

Cualquier personalización se puede hacer simplemente creando una subclase de "Module::Build" y añadiendo un método llamado (por ejemplo) "ACTION_test", sobrescribiendo la acción 'test' por defecto. También podrías añadir un método llamado "ACTION_whatever", y luego podrías ejecutar la acción "Build whatever".

Para obtener información sobre cómo proporcionar compatibilidad con "ExtUtils::MakeMaker", consulta Module::Build::Compat y http://www.makemaker.org/wiki/index.cgi?ModuleBuildConversionGuide.

ESTRUCTURA

Module::Build crea una jerarquía de clases propicia para la personalización. Aquí está la jerarquía de clases padre-hijo en arte ASCII elegante:

/--------------------\
|   Your::Parent     |  (Si creas una subclase de Module::Build)
\--------------------/
         |
         |
/--------------------\  (No define ninguna funcionalidad
|   Module::Build    |   propia - solo averigua qué
\--------------------/   otros módulos cargar.)
         |
         |
/-----------------------------------\  (Algunos valores de $^O pueden
|   Module::Build::Platform::$^O    |   definir funcionalidad especializada.
\-----------------------------------/   De lo contrario es ...::Default,
         |                              una clase de paso.)
         |
/--------------------------\
|   Module::Build::Base    |  (La mayor parte de la funcionalidad de
\--------------------------/   Module::Build se define aquí.)

CREACIÓN DE SUBCLASES

Por ahora, hay dos formas de crear subclases de Module::Build. La primera forma es crear un módulo regular (en un archivo ".pm") que herede de Module::Build, y usar la clase de ese módulo en lugar de usar Module::Build directamente:

------ en Build.PL: ----------
#!/usr/bin/perl
use lib q(/ruta/de/libreria/no/estandar);
use My::Builder;  # O como quieras llamarlo
my $build = My::Builder->new
  (
   module_name => 'Foo::Bar',  # Todos los argumentos normales...
   license     => 'perl',
   dist_author => 'Un Tal Otro <yo@aqui.net.au>',
   requires    => { Carp => 0 }
  );
$build->create_build_script;

Esto es relativamente sencillo, y es la mejor manera de hacer las cosas si tu clase My::Builder contiene mucho código. El método create_build_script() asegurará que el valor actual de @INC (incluyendo la "/ruta/de/libreria/no/estandar") se propague al script de Build, para que My::Builder pueda ser encontrado al ejecutar acciones de compilación. Si descubres que necesitas "chdir" a directorios diferentes en tus métodos o acciones de subclase, asegúrate de regresar siempre al directorio original (disponible a través del método base_dir()) antes de devolver el control a la clase padre. Esto es importante para evitar problemas de serialización de datos.

Para adiciones muy pequeñas, Module::Build proporciona un método subclass() que te permite crear subclases de Module::Build de forma más conveniente, sin crear un archivo separado para tu módulo:

------ en Build.PL: ----------
#!/usr/bin/perl
use Module::Build;
my $class = Module::Build->subclass
  (
   class => 'My::Builder',
   code => q{
     sub ACTION_foo {
       print "¡Estoy haciendo foo hasta la muerte!\n";
     }
   },
  );
my $build = $class->new
  (
   module_name => 'Foo::Bar',  # Todos los argumentos normales...
   license     => 'perl',
   dist_author => 'Un Tal Otro <yo@aqui.net.au>',
   requires    => { Carp => 0 }
  );
$build->create_build_script;

Detrás de escena, esto en realidad crea un archivo ".pm", ya que el código que proporcionas debe persistir después de que se ejecute Build.PL si es que va a ser muy útil.

Consulta también la documentación del método "subclass()" en Module::Build::API.

PRERREQUISITOS

Tipos de prerrequisitos

Para especificar qué versiones de otros módulos son utilizados por esta distribución, se pueden definir varios tipos de prerrequisitos con los siguientes parámetros:

configure_requires
Elementos que deben estar instalados antes de configurar esta distribución (es decir, antes de ejecutar el script Build.PL). Esto podría ser una versión mínima específica de "Module::Build" o cualquier otro módulo que el Build.PL necesite para hacer su trabajo. Se espera que clientes como "CPAN.pm" o "CPANPLUS" extraigan "configure_requires" del archivo META.yml e instalen estos elementos antes de ejecutar el script "Build.PL".

Si no se especifica configure_requires, la versión actual de Module::Build se añade automáticamente a configure_requires.

build_requires
Elementos que son necesarios para construir y probar esta distribución, pero que no son necesarios después de la instalación. Esto puede ayudar a los usuarios que solo quieren instalar estos elementos temporalmente. También ayuda a reducir el tamaño del grafo de dependencias de CPAN si no todo se aplasta en "requires".
requires
Elementos que son necesarios para el funcionamiento básico.
recommends
Elementos que se recomiendan para una funcionalidad mejorada, pero hay maneras de usar esta distribución sin tenerlos instalados. También podrías pensar en esto como "puede usar" o "es consciente de" o "cambia el comportamiento en presencia de".
test_requires
Elementos que son necesarios para las pruebas.
conflicts
Elementos que pueden causar problemas con esta distribución cuando se instalan. Esto es bastante raro.

Formato de los prerrequisitos

Los prerrequisitos se proporcionan en una referencia de hash, donde las claves son los nombres de los módulos y los valores son especificadores de versión:

requires => {
             Foo::Module => '2.4',
             Bar::Module => 0,
             Ken::Module => '>= 1.2, != 1.5, < 2.0',
             perl => '5.6.0'
            },

Los cuatro especificadores de versión anteriores tienen efectos diferentes. El valor '2.4' significa que debe estar instalada **al menos** la versión 2.4 de "Foo::Module". El valor 0 significa que **cualquier** versión de "Bar::Module" es aceptable, incluso si "Bar::Module" d

NOMBRE

Module::Build

DESCRIPCIÓN

Module::Build es un sistema de construcción de módulos Perl que permite la creación de módulos con un enfoque de construcción modular. Este sistema ofrece una interfaz para automatizar la construcción, prueba e instalación de módulos, y también permite la creación de módulos personalizados con una estructura de construcción flexible.

ESTRUCTURA

Module::Build está estructurado en varios componentes principales, incluyendo:

  • "Build": el núcleo de la herramienta que gestiona la construcción, prueba e instalación de módulos.
  • "ConfigData": un módulo que permite guardar y acceder a datos de configuración de módulos.
  • "Cookbook": una guía de construcción que contiene ejemplos y explicaciones de cómo usar Module::Build.
  • "API": una interfaz de programación que permite llamar a métodos de construcción desde el código.
  • "ExtUtils::MakeMaker": una extensión que permite usar el sistema de construcción de Makefile.

SUBCLASES

Module::Build permite crear clases personalizadas para representar módulos de construcción. Estas clases pueden heredar de la clase base "Module::Build" y pueden tener sus propios métodos de construcción, prueba e instalación.

PRERREQUISITOS

Para usar Module::Build, se requieren:

  • Perl
  • Un entorno de desarrollo
  • Un módulo de construcción (como ExtUtils::MakeMaker)

GUARDADO DE INFORMACIÓN DE CONFIGURACIÓN

Module::Build proporciona una forma conveniente de guardar información de configuración a la que tu instalación de módulos (o tus pruebas de regresión) puedan acceder. Si tu proceso de construcción llama a los métodos "feature()" o "config_data()", se creará automáticamente un módulo "Foo::Bar::ConfigData", donde "Foo::Bar" es el nombre del módulo de configuración como se pasa a la función "new()". Este módulo proporciona acceso a los datos guardados por estos métodos y permite actualizar los valores. También hay un script de utilidad llamado "config_data" distribuido con Module::Build que ofrece una interfaz de línea de comandos para esta misma funcionalidad. Consulta también la documentación generada del módulo "Foo::Bar::ConfigData" y el documento del script "config_data" para más información.

INICIO DEL DESARROLLO DE MÓDULOS

Cuando comienzas a desarrollar un nuevo módulo, suele ser poco práctico crear una carpeta con todos los archivos manualmente. Algunos auto-creadores de módulos están disponibles: el más antiguo es "h2xs", que ha venido con Perl desde hace tiempo. Su nombre refleja la idea de que los módulos eran originalmente concebidos como una forma de envolver una biblioteca C en extensiones de Perl (por lo tanto, el "h" en el nombre) en una extensión de Perl (por lo tanto, el "xs" en el nombre).

Actualmente, "h2xs" ha sido ampliamente reemplazado por módulos como "ExtUtils::ModuleMaker" y "Module::Starter". Estos últimos tienen variaciones en su apoyo para "Module::Build".

AUTOMATIZACIÓN

Una ventaja de Module::Build es que, ya que se implementa como métodos de Perl, puedes invocar estos métodos directamente si quieres instalar un módulo de forma no interactiva. Por ejemplo, el siguiente script Perl invocará el proceso completo de construcción e instalación:

my $build = Module::Build->new(module_name => 'MyModule');
$build->dispatch('build');
$build->dispatch('test');
$build->dispatch('install');

Si algún paso de este proceso encuentra un error, lanzará una excepción de tipo fatal.

También puedes pasar argumentos como parte del proceso de construcción:

my $build = Module::Build->new(module_name => 'MyModule');
$build->dispatch('build');
$build->dispatch('test', verbose => 1);
$build->dispatch('install', sitelib => '/my/secret/place/');

La construcción e instalación de módulos en este modo evita la creación del archivo "Build".

MIGRACIÓN

Nota: si deseas proporcionar tanto "Makefile.PL" como "Build.PL" para tu distribución, probablemente debas agregar lo siguiente a "WriteMakefile" en tu "Makefile.PL" para que "MakeMaker" no intente ejecutar tu "Build.PL" como un archivo ".PL" normal:

PL_FILES => {},

También podrías estar interesado en ver la documentación de "Module::Build::Compat", que puede automáticamente crear varias capas de compatibilidad de "Makefile.PL" diferentes.
