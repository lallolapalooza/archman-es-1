NOMBRE

MIME-tools - módulos para analizar (¡y crear!) entidades MIME

SINOPSIS

Aquí hay un código bastante básico para analizar un mensaje MIME, y generar sus componentes decodificados en un directorio dado:

use MIME::Parser;
### Crear analizador y establecer algunas opciones de análisis:
my $parser = new MIME::Parser;
$parser->output_under("$ENV{HOME}/mimemail");
### Analizar entrada:
$entity = $parser->parse(\*STDIN) or die "parse failed\n";
### Echar un vistazo a la entidad de nivel superior (y a las partes que tenga):
$entity->dump_skeleton;

Aquí hay un código que compone y envía un mensaje MIME que contiene tres partes: un archivo de texto, un GIF adjunto y algo más de texto:

use MIME::Entity;
### Crear el nivel superior y configurar las cabeceras del correo:
$top = MIME::Entity->build(Type    =>"multipart/mixed",
                           From    => "me\@myhost.com",
                           To      => "you\@yourhost.com",
                           Subject => "¡Hola, enfermera!");
### Parte #1: un simple documento de texto:
$top->attach(Path=>"./testin/short.txt");
### Parte #2: un archivo GIF:
$top->attach(Path        => "./docs/mime-sm.gif",
             Type        => "image/gif",
             Encoding    => "base64");
### Parte #3: texto literal:
$top->attach(Data=>$message);
### Enviarlo:
open MAIL, "| /usr/lib/sendmail -t -oi -oem" or die "open: $!";
$top->print(\*MAIL);
close MAIL;

Para más ejemplos, mira los scripts en el directorio examples de la distribución MIME-tools.

DESCRIPCIÓN

MIME-tools es una colección de módulos Perl5 MIME:: para analizar, decodificar, y generar mensajes MIME simples o multipart (incluso multipart anidados). (Sí, niños, eso significa que pueden enviar mensajes con archivos GIF adjuntos).

REQUISITOS

Necesitarás lo siguiente instalado en tu sistema:

File::Path

IPC::Open2              (opcional)

MIME::QuotedPrint
Net::SMTP
Mail::Internet, ...     de la distribución MailTools.

Consulta el Makefile.PL en tu distribución para obtener la lista más completa de módulos prerrequisito y sus números de versión.

Para ilustrar, el análisis funciona de esta manera:

  • El "analizador" analiza el flujo MIME. Un analizador es una instancia de "MIME::Parser". Le entregas un flujo de entrada (como un manejador de archivo) para analizar un mensaje: si el análisis es exitoso, el resultado es una "entidad".
  • Un mensaje analizado se representa mediante una "entidad". Una entidad es una instancia de "MIME::Entity" (una subclase de "Mail::Internet"). Si el mensaje tenía "partes" (por ejemplo, archivos adjuntos), entonces esas partes también son "entidades", contenidas dentro de la entidad de nivel superior. Cada entidad tiene una "cabecera" y un "cuerpo".
  • La "cabecera" de la entidad contiene información sobre el mensaje. Una "cabecera" es una instancia de "MIME::Head" (una subclase de "Mail::Header"). Contiene información de la cabecera del mensaje: tipo de contenido, remitente, línea de asunto, etc.
  • El "cuerpo" de la entidad sabe dónde están los datos del mensaje. Puedes solicitar "abrir" esta fuente de datos para lectura o escritura, y obtendrás un "manejador de E/S".
  • Puedes abrir() un "cuerpo" y obtener un "manejador de E/S" para leer/escribir datos del mensaje. Este manejador es un objeto que básicamente es como un IO::Handle... puede ser de cualquier clase, siempre que cumpla un conjunto pequeño y estándar de métodos para leer o escribir en la fuente de datos subyacente.

Un mensaje multipart típico que contiene dos partes — un saludo textual y un archivo GIF "adjunto" — sería un árbol de objetos MIME::Entity, cada uno de los cuales tendría su propia MIME::Head. Así:

.--------.
| MIME:: | Content-type: multipart/mixed
| Entity | Subject: ¡Feliz Samhain!
`--------'
     |
     `----.
    parts |
          |   .--------.
          |---| MIME:: | Content-type: text/plain; charset=us-ascii
          |   | Entity | Content-transfer-encoding: 7bit
          |   `--------'
          |   .--------.
          |---| MIME:: | Content-type: image/gif
              | Entity | Content-transfer-encoding: base64
              `--------' Content-disposition: inline;
                           filename="hs.gif"

Análisis de mensajes

Normalmente comienzas creando una instancia de MIME::Parser y configurando ciertos parámetros de análisis: a qué directorio guardar los archivos extraídos, cómo nombrar los archivos, etc.

Luego, le das a esa instancia un manejador de archivo legible en el que espera un mensaje MIME. Si todo va bien, obtendrás un objeto MIME::Entity (una subclase de Mail::Internet), que consiste en...

  • Una MIME::Head (una subclase de Mail::Header) que contiene los datos de la cabecera MIME.
  • Un MIME::Body, que es un objeto que sabe dónde están los datos del cuerpo. Le pides a este objeto que se "abra" para lectura, y te entregará un "manejador de E/S" para leer los datos: podría ser de cualquier clase, siempre que cumpla con un subconjunto de la interfaz IO::Handle.

Si el mensaje original era un documento multipart, el objeto MIME::Entity tendrá una lista no vacía de "partes", cada una de las cuales es a su vez una MIME::Entity (que podría ser también una entidad multipart, etc., etc...).

Internamente, el analizador (en MIME::Parser) solicita instancias de MIME::Decoder cada vez que necesita decodificar un archivo codificado. MIME::Decoder tiene un mapeo de codificaciones soportadas (por ejemplo, 'base64') a clases cuyas instancias pueden decodificarlas. Puedes añadir a este mapeo para probar codificaciones nuevas/experimentales. También puedes usar MIME::Decoder por sí solo.

Composición de mensajes

Toda la composición de mensajes se realiza a través de la clase MIME::Entity. Para mensajes de una sola parte, puedes usar el constructor MIME::Entity/build para crear entidades MIME muy fácilmente.

Para mensajes multipart, puedes comenzar creando una entidad "multipart" de nivel superior con MIME::Entity::build(), y luego usar el método similar MIME::Entity::attach() para adjuntar partes a ese mensaje. Por favor, ten en cuenta: lo que la mayoría de la gente piensa como "un mensaje de texto con un archivo GIF adjunto" es en realidad un mensaje multipart con 2 partes: la primera es el mensaje de texto, y la segunda es el archivo GIF.

Sending email

Since MIME::Entity inherits directly from Mail::Internet, you can use the normal Mail::Internet mechanisms to send email. For example,

$entity->smtpsend;

Encoding/decoding support

The MIME::Decoder class can be used to encode as well; this is done when printing MIME entities. All the standard encodings are supported (see "A MIME PRIMER" below for details):

Encoding:        | Normally used when message contents are:
-------------------------------------------------------------------
7bit             | 7-bit data with under 1000 chars/line, or multipart.
8bit             | 8-bit data with under 1000 chars/line.
binary           | 8-bit data with some long lines (or no line breaks).
quoted-printable | Text files with some 8-bit chars (e.g., Latin-1 text).
base64           | Binary files.

Which encoding you choose for a given document depends largely on (1) what you know about the document's contents (text vs binary), and (2) whether you need the resulting message to have a reliable encoding for 7-bit Internet email transport.

In general, only "quoted-printable" and "base64" guarantee reliable transport of all data; the other three "no-encoding" encodings simply pass the data through, and are only reliable if that data is 7bit ASCII with under 1000 characters per line, and has no conflicts with the multipart boundaries.

I've considered making it so that the content-type and encoding can be automatically inferred from the file's path, but that seems to be asking for trouble... or at least, for Mail::Cap...

Message-logging

MIME-tools is a large and complex toolkit which tries to deal with a wide variety of external input. It's sometimes helpful to see what's really going on behind the scenes. There are several kinds of messages logged by the toolkit itself:

Debug messages
These are printed directly to the STDERR, with a prefix of "MIME-tools: debug".

Debug message are only logged if you have turned "debugging" on in the MIME::Tools configuration.

Warning messages
These are logged by the standard Perl warn() mechanism to indicate an unusual situation. They all have a prefix of "MIME-tools: warning".

Warning messages are only logged if $^W is set true and MIME::Tools is not configured to be "quiet".

Error messages
These are logged by the standard Perl warn() mechanism to indicate that something actually failed. They all have a prefix of "MIME-tools: error".

Error messages are only logged if $^W is set true and MIME::Tools is not configured to be "quiet".

Usage messages
Unlike "typical" warnings above, which warn about problems processing data, usage-warnings are for alerting developers of deprecated methods and suspicious invocations.

Usage messages are currently only logged if $^W is set true and MIME::Tools is not configured to be "quiet".

When a MIME::Parser (or one of its internal helper classes) wants to report a message, it generally does so by recording the message to the MIME::Parser::Results object immediately before invoking the appropriate function above. That means each parsing run has its own trace-log which can be examined for problems.

Configuring the toolkit

If you want to tweak the way this toolkit works (for example, to turn on debugging), use the routines in the MIME::Tools module.

debugging
Turn debugging on or off. Default is false (off). 
MIME::Tools->debugging(1);
quiet
Turn the reporting of warning/error messages on or off. Default is true, meaning that these message are silenced. 
MIME::Tools->quiet(1);
version
Return the toolkit version. 
print MIME::Tools->version, "\n";

THINGS YOU SHOULD DO

Take a look at the examples

The MIME-Tools distribution comes with an "examples" directory. The scripts in there are basically just tossed-together, but they'll give you some ideas of how to use the parser.

Run with warnings enabled

Always run your Perl script with "-w". If you see a warning about a deprecated method, change your code ASAP. This will ease upgrades tremendously.

Avoid non-standard encodings

Don't try to MIME-encode using the non-standard MIME encodings. It's just not a good practice if you want people to be able to read your messages.

Plan for thrown exceptions

For example, if your mail-handling code absolutely must not die, then perform mail parsing like this:

$entity = eval { $parser->parse(\*INPUT) };

Parsing is a complex process, and some components may throw exceptions if seriously-bad things happen. Since "seriously-bad" is in the eye of the beholder, you're better off catching possible exceptions instead of asking me to propagate "undef" up the stack. Use of exceptions in reusable modules is one of those religious issues we're never all going to agree upon; thankfully, that's what "eval{}" is good for.

Check the parser results for warnings/errors

As of 5.3xx, the parser tries extremely hard to give you a MIME::Entity. If there were any problems, it logs warnings/errors to the underlying "results" object (see MIME::Parser::Results). Look at that object after each parse. Print out the warnings and errors, especially if messages don't parse the way you thought they would.

Don't plan on printing exactly what you parsed!

Parsing is a (slightly) lossy operation. Because of things like ambiguities in base64-encoding, the following is not going to spit out its input unchanged in all cases:

$entity = $parser->parse(\*STDIN);
$entity->print(\*STDOUT);

If you're using MIME::Tools to process email, remember to save the data you parse if you want to send it on unchanged. This is vital for things like PGP-signed email.

Understand how international characters are represented

The MIME standard allows for text strings in headers to contain characters from any character set, by using special sequences which look like this:

=?ISO-8859-1?Q?Keld_J=F8rn_Simonsen?=

To be consistent with the existing Mail::Field classes, MIME::Tools does not automatically unencode these strings, since doing so would lose the character-set information and interfere with the parsing of fields (see "decode_headers" in MIME::Parser for a full explanation). That means you should be prepared to deal with these encoded strings.

The most common question then is, how do I decode these encoded strings? The answer depends on what you want to decode them to: ASCII, Latin1, UTF-8, etc. Be aware that your "target" representation may not support all possible character sets you might encounter; for example, Latin1 (ISO-8859-1) has no way of representing Big5 (Chinese) characters. A common practice is to represent "untranslateable" characters as "?"s, or to ignore them completely.

To unencode the strings into some of the more-popular Western byte representations (e.g., Latin1, Latin2, etc.), you can use the decoders in MIME::WordDecoder (see MIME::WordDecoder). The simplest way is by using unmime(), a function wrapped around your "default" decoder, as follows:

use MIME::WordDecoder;
...
$subject = unmime $entity->head->get('subject');

One place this is done automatically is in extracting the recommended filename for a part while parsing. That's why you should start by setting up the best "default" decoder if the default target of Latin1 isn't to your liking.

COSAS QUE DEBERÍAS SABER SOBRE

Fuzzing de CRLF y salto de línea en la entrada

RFC 2045 dicta que los flujos MIME tienen líneas terminadas por CRLF ("\r\n"). Sin embargo, es muy probable que la gente quiera analizar flujos MIME donde cada línea termina en el carácter de nueva línea local "\n" en su lugar.

Se ha hecho un intento para permitir que el analizador maneje entradas terminadas tanto por CRLF como por salto de línea.

Fuzzing de CRLF y salto de línea al decodificar

Los decodificadores "7bit" y "8bit" decodificarán tanto una secuencia de fin de línea "\n" como una secuencia "\r\n" en un "\n".

El decodificador "binary" (predeterminado si no se especifica codificación) todavía saca las cosas literalmente... así que un mensaje MIME con CRLF y sin codificación explícita se sacará como un archivo de texto que, en muchos sistemas, tendrá un molesto ^M al final de cada línea... pero esto es como debe ser.

Fuzzing de CRLF y salto de línea al codificar/componer

TODO FIXME Todos los codificadores actualmente sacan la secuencia de fin de línea como un "\n", asumiendo que el agente de correo local realizará la conversión de salto de línea a CRLF al enviar el correo. Sin embargo, probablemente debería haber una opción para sacar CRLF según RFC 2045

Incapacidad para manejar límites multipart con saltos de línea incrustados

Seamos claros: esta es una práctica malvada, MALVADA. Si su cliente de correo crea cadenas de límites multipart que contienen saltos de línea, avísele con dos semanas de antelación y busque otro. Si su robot de correo recibe correo MIME de este tipo, considérelo sintácticamente incorrecto, que lo es.

Ignorando encabezados no de encabezado

A la gente le gusta pasarle al analizador mensajes directos de POP3 o de un buzón. A menudo hay información predecible no de encabezado delante de los encabezados reales; por ejemplo, la línea inicial "From" en el siguiente mensaje:

From - Wed Mar 22 02:13:18 2000
Return-Path: <eryq@zeegee.com>
Subject: Hello

El analizador simplemente ignora ese material en silencio. Quizás no debería, pero la mayoría de la gente parece querer ese comportamiento.

Fuzzing de preámbulos multipart vacíos

Tenga en cuenta que actualmente existe una ambigüedad en la forma en que se analizan los preámbulos. Los siguientes fragmentos de mensaje ambos se consideran con un preámbulo vacío (donde "\n" indica un carácter de nueva línea):

Content-type: multipart/mixed; boundary="xyz"\n
Subject: This message (#1) has an empty preamble\n
\n
--xyz\n
...
Content-type: multipart/mixed; boundary="xyz"\n
Subject: This message (#2) also has an empty preamble\n
\n
\n
--xyz\n
...

En ambos casos, la primera línea completamente vacía (después del "Subject") marca el final del encabezado.

Pero claramente deberíamos ignorar la segunda línea vacía en el mensaje #2, ya que cumple la función de "el salto de línea que solo está ahí para asegurarse de que el límite esté al principio de una línea". Dichos saltos de línea nunca forman parte del contenido que precede al límite; por lo tanto, no hay contenido de preámbulo" en el mensaje #2.

Sin embargo, está claro que el mensaje #1 también no tiene contenido de preámbulo" y, de hecho, es simplemente una representación compacta de un preámbulo vacío.

Uso de un archivo temporal durante el análisis

¿Por qué no hacer todo en memoria? Aunque la cantidad de memoria disponible en incluso un sistema doméstico modesto continúa creciendo, el tamaño de los adjuntos continúa creciendo con él. Quería asegurarme de que incluso los usuarios con sistemas pequeños pudieran manejar la decodificación de archivos de sonido y video de varios megabytes. Eso significa no estar limitado por la memoria.

A partir de la versión 5.3xx lanzada, MIME::Parser se las arregla con solo un archivo temporal abierto por analizador. Este archivo temporal proporciona una especie de espacio de trabajo infinito para manejar la parte actual del mensaje. Es rápido y ligero, pero de todos modos deberías saber sobre él.

¿Por qué asumo que los objetos MIME son objetos de correo electrónico?

Achim Bohnet señaló una vez que los encabezados MIME no hacen más que almacenar una colección de atributos, y por lo tanto podrían representarse como objetos que no heredan de Mail::Header.

Estoy de acuerdo en principio, pero RFC 2045 dice lo contrario. Los encabezados RFC 2045 [MIME] son un subconjunto sintáctico de los encabezados RFC-822 [correo electrónico]. Quizás un mejor nombre para estos módulos hubiera sido RFC1521:: en lugar de MIME::, pero estamos un poco más allá de esa etapa ahora.

Cuando escribí originalmente estos módulos para CPAN, me esforcé mucho tiempo en decidir si realmente debían heredar de Mail::Internet (entonces en la versión 1.17). Gracias a Graham Barr, que evolucionó graciosamente MailTools 1.06 para que fuera más amigable con MIME, la unificación se logró en la versión 2.0 de MIME-tools. Los beneficios en la reutilización solos han sido sustanciales.

UN PRIMER ACERCA DE MIME

¿Así que necesitas analizar (o crear) MIME, pero no estás al tanto de los detalles? No hay problema...

Glosario

Aquí hay algunas definiciones adaptadas de RFC 1521 (predecesor de los actuales RFC 204[56789] que definen MIME) que explican la terminología que utilizamos; cada una va acompañada del equivalente en términos del módulo MIME::...

adjunto
Un "adjunto" es la jerga común para cualquier parte de un mensaje multipartidista, excepto, quizás, para la primera parte, que normalmente lleva un mensaje del usuario describiendo los adjuntos que siguen (por ejemplo: "Oye, aquí tienes ese archivo GIF que te prometí").

En nuestro sistema, un adjunto es solo una MIME::Entity debajo de la entidad de nivel superior, probablemente una de sus partes.

cuerpo
El "cuerpo" de una entidad es la porción de la entidad que sigue al encabezado y que contiene el contenido real del mensaje. Por ejemplo, si su mensaje MIME tiene un adjunto de archivo GIF, entonces el cuerpo de ese adjunto es el propio archivo GIF codificado en base64.

Un cuerpo está representado por una instancia de MIME::Body. Obtienes el cuerpo de una entidad enviándole un mensaje bodyhandle().

body part
Una de las partes del cuerpo de una entidad /multipart. Una parte del cuerpo tiene un /encabezado y un /cuerpo, por lo que tiene sentido hablar del cuerpo de una parte del cuerpo.

Dado que una parte del cuerpo es solo un tipo de entidad, está representada por una instancia de MIME::Entity.

entidad
Una "entidad" significa un /mensaje o una /parte del cuerpo. Todas las entidades tienen un /encabezado y un /cuerpo.

Una entidad está representada por una instancia de MIME::Entity. Hay métodos de instancia para recuperar el encabezado (un MIME::Head) y el cuerpo (un MIME::Body).

encabezado
Esta es la parte superior del mensaje MIME, que contiene el "Content-type", "Content-transfer-encoding", etc. Cada entidad MIME tiene un encabezado, representado por una instancia de MIME::Head. Obtienes el encabezado de una entidad enviándole un mensaje head().
mensaje
Un "mensaje" generalmente significa el mensaje completo (o "de nivel superior") que se está transfiriendo en una red.

Actualmente no hay un paquete explícito para "mensajes"; bajo MIME::, los mensajes son flujos de datos que pueden ser leídos desde archivos o manejadores de archivos. Puede pensar en la MIME::Entity devuelta por MIME::Parser como que representa el mensaje completo.

Tipos de contenido

Esto indica qué tipo de datos hay en el mensaje MIME, generalmente como majortype/minortype. Los tipos principales estándar se muestran a continuación. Una lista más completa se puede encontrar en RFC-2046.

application
Datos que no encajan en ninguna de las otras categorías, particularmente datos que serán procesados por algún tipo de programa de aplicación. "application/octet-stream", "application/gzip", "application/postscript"...
audio
Datos de audio. "audio/basic"...
image
Datos gráficos. "image/gif", "image/jpeg"...
message
Un mensaje, generalmente otro correo o mensaje MIME. "message/rfc822"...
multipart
Un mensaje que contiene otros mensajes. "multipart/mixed", "multipart/alternative"...
text
Datos textuales, destinados a ser leídos por humanos. "text/plain", "text/html"...
video
Datos de video.

CONTENT TYPES

This section lists the types of MIME content that MIME::Entity understands.

text
Textual data. The content type is usually text/plain, but may be text/html, text/xml, etc. These should be composed of 7bit characters, and lines should not exceed 1000 characters in length (including the CRLF).
message
A MIME entity encapsulated within the message body. This may be a message/rfc822, a message/partial, or a message/external-body.
image
Image data. The content type may be image/gif, image/jpeg, image/png, etc. These are typically binary data.
audio
Audio data. The content type may be audio/basic, audio/mpeg, etc. These are typically binary data.
video
Video or video+audio data. "video/mpeg"...

Codificaciones de transferencia de contenido

Esta es la forma en que el cuerpo del mensaje se empaqueta para un tránsito seguro. Existen las 5 codificaciones MIME principales. Un listado más completo se puede encontrar en RFC-2045.

7bit
No se realiza ninguna codificación. Esta etiqueta simplemente afirma que no hay caracteres de 8 bits presentes, y que las líneas no exceden los 1000 caracteres de longitud (incluyendo el CRLF).
8bit
No se realiza ninguna codificación. Esta etiqueta simplemente afirma que el mensaje puede contener caracteres de 8 bits, y que las líneas no exceden los 1000 caracteres de longitud (incluyendo el CRLF).
binary
No se realiza ninguna codificación. Esta etiqueta simplemente afirma que el mensaje puede contener caracteres de 8 bits, y que las líneas pueden exceder los 1000 caracteres de longitud. Estos mensajes son los *menos* probables de pasar por las pasarelas de correo.
base64
Una codificación estándar, que mapea datos binarios arbitrarios al dominio 7bit. Similar a "uuencode", pero muy bien definida. Así es como se debe enviar información esencialmente binaria (archivos tar, GIFs, JPEGs, etc.).
quoted-printable
Una codificación estándar, que mapea datos arbitrarios orientados a línea al dominio 7bit. Útil para codificar mensajes que son de naturaleza textual, pero que contienen caracteres no ASCII (por ejemplo, Latin-1, Latin-2, o cualquier otro alfabeto de 8 bits).
