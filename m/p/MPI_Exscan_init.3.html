Parámetros de entrada

  • sendbuf: Buffer de envío (elección).
  • count: Número de elementos en el buffer de entrada (entero).
  • datatype: Tipo de datos de los elementos del buffer de entrada (handle).
  • op: Operación (handle).
  • comm: Comunicador (handle).

Parámetros de salida

  • recvbuf: Buffer de recepción (elección).
  • request: Petición (handle, solo no bloqueante).
  • ierror: Solo en Fortran: Estado de error (entero).

Descripción

MPI_Exscan realiza una reducción exclusiva (reducción parcial) en los datos distribuidos entre los procesos del llamador. El resultado se devuelve en el recvbuf del proceso con el rank i, que contiene la reducción (calculada según la función op) de los valores en los sendbuf de los procesos con ranks 0, ..., i-1. Compare con la función de MPI_Scan, que calcula sobre el rango 0, ..., i (inclusivo). Los tipos de operaciones soportados, sus semánticas y las restricciones en los buffers de envío y recepción son las mismas que en MPI_Reduce.

El valor en recvbuf del proceso 0 es indefinido y no es confiable ya que recvbuf no es significativo para el proceso 0. El valor de recvbuf del proceso 1 siempre es el valor en sendbuf del proceso 0.

Uso de la opción en lugar de

La opción "en lugar de" para comunicadores internos se especifica pasando MPI_IN_PLACE en el argumento sendbuf. En este caso, los datos de entrada se toman del buffer de recepción y se reemplazan por los datos de salida.

Nota: MPI_IN_PLACE es un tipo especial; tiene las mismas restricciones que MPI_BOTTOM.

Como resultado del uso de la opción "en lugar de", el buffer de recepción se convierte en un buffer de envío y recepción. Una firma de binding Fortran que incluya INTENT debe marcar estos como INOUT, no como OUT.

Notas

MPI no especifica cuál proceso calcula qué operación. En particular, ambos procesos 0 y 1 pueden participar en la computación incluso si los resultados para ambos procesos recvbuf son degenerados. Por lo tanto, todos los procesos, incluidos 0 y 1, deben proporcionar el mismo op.

Se puede argumentar matemáticamente que la definición de MPI_Exscan es insatisfactoria porque el valor en recvbuf del proceso 0 es indefinido. El valor "matemáticamente correcto" para el proceso 0 sería el elemento unitario de la operación de reducción. Sin embargo, tal definición no funcionaría correctamente con funciones de operación personalizadas op, ya que MPI no podría "saber" el valor unitario para estas operaciones personalizadas.

Notas sobre operaciones colosivas

Las funciones de reducción de tipo MPI_Op no devuelven un valor de error. Por lo tanto, si las funciones detectan un error, solo pueden llamar a MPI_Abort o ignorar el problema. Por lo tanto, si el error handler se cambia de MPI_ERRORS_ARE_FATAL a algo else (por ejemplo, MPI_ERRORS_RETURN), no se puede indicar ningún error.

La razón es el problema de rendimiento en la garantía de que todas las rutinas colosivas devuelvan el mismo valor de error.

Errores

La mayoría de las rutinas MPI devuelven un valor de error; en C, el resultado de la función y en Fortran, el último argumento.

Antes de devolver el valor de error, se llama al error handler asociado con el objeto de comunicación (por ejemplo, comunicador, ventana, archivo) que se está utilizando. Si no hay objeto de comunicación asociado con la llamada MPI, se considera que la llamada está asociada a MPI_COMM_SELF y llamará al error handler asociado con MPI_COMM_SELF. Cuando MPI_COMM_SELF no está inicializado (es decir, antes de MPI_Init/MPI_Init_thread, después de MPI_Finalize, o cuando se use el modelo de sesiones exclusivamente), el error levanta el error handler inicial. El error handler inicial puede cambiarse llamando a MPI_Comm_set_errhandler en MPI_COMM_SELF cuando se use el modelo del mundo, o el argumento mpi_initial_errhandler de mpiexec o la clave info de MPI_Comm_spawn/MPI_Comm_spawn_multiple. Si no hay otro error handler adecuado configurado, se llama el error handler MPI_ERRORS_RETURN para funciones de I/O MPI y el error handler MPI_ERRORS_ABORT para todas las otras funciones MPI.

Open MPI incluye tres handlers de error prediseñados que pueden utilizarse:

  • MPI_ERRORS_ARE_FATAL Detiene todos los procesos MPI conectados.
  • MPI_ERRORS_ABORT Un error handler que puede invocarse en un comunicador, ventana, archivo o sesión. Cuando se invoca en un comunicador, actúa como si se hubiera llamado MPI_Abort en ese comunicador. Si se invoca en una ventana o archivo, actúa como si se hubiera llamado MPI_Abort en un comunicador que contiene el grupo de procesos en la ventana o archivo correspondiente. Si se invoca en una sesión, detiene solo el proceso local.
  • MPI_ERRORS_RETURN Devuelve un código de error a la aplicación.

Las aplicaciones MPI pueden también implementar sus propios handlers de error llamando:

  • MPI_Comm_create_errhandler luego MPI_Comm_set_errhandler
  • MPI_File_create_errhandler luego MPI_File_set_errhandler
  • MPI_Session_create_errhandler y

NAME

MPI_Exscan_init - Initialize an exclusive scan operation

SYNTAX

C

int MPI_Exscan_init(MPI_Comm comm, MPI_Datatype datatype, MPI_Op op,
                    int reduce_count, MPI_Info info, MPI_Info session_info,
                    MPI_Request *request, MPI_Op *newop);

Fortran

SUBROUTINE MPI_Exscan_init(comm, datatype, op, reduce_count, info,
                           session_info, request, newop, ierr)
    INTEGER :: comm, datatype, op, reduce_count, info, session_info, request, newop, ierr

Fortran 77

SUBROUTINE MPI_EXSCAN_INIT(COMM, DATATYPE, OP, REDUCE_COUNT, INFO,
                           SESSION_INFO, REQUEST, NEWOP, IERR)
    INTEGER * 4 COMM, DATATYPE, OP, REDUCE_COUNT, INFO, SESSION_INFO, REQUEST, NEWOP, IERR

INPUT PARAMETERS

comm
Communicator (handle).
datatype
Datatype of elements in the operation (handle).
op
Reduction operation (handle).
reduce_count
Number of elements in the reduction (non-negative integer).
info
Info object (handle).
session_info
Session info object (handle).

OUTPUT PARAMETERS

request
Request handle (handle).
newop
Handle of the new operation object.
ierr
Fortran only: return code (integer).

DESCRIPTION

MPI_Exscan_init is a non-blocking collective operation that initializes an exclusive scan operation. An exclusive scan operation performs a left-to-right scan. The result sent to process i contains the reduction of inputs from processes 0 to i-1.

The newop argument will contain the handle of the new operation object that can be used with MPI_Exscan_execute.

USE OF IN-PLACE OPTION

This operation does not support the in-place option.

NOTES

This function is part of the MPI 3.0 standard. It is intended to be used in conjunction with MPI_Exscan_execute to perform an exclusive scan operation.

The request argument is used to track the completion of the initialization, not the subsequent execution of the scan operation.

NOTES ON COLLECTIVE OPERATIONS

All collective operations have optional input and output arguments. For each collective operation, the input arguments that are not specified by the caller are implicitly assigned a value of MPI_PROC_NULL or an empty collection, and the output arguments are implicitly assigned a value of MPI_PROC_NULL or an empty collection. All MPI collective communication operations must be called by all processes in the communicator.

ERRORS

When the value of the comm argument is an invalid communicator or when the value of the op argument is an invalid operation handle, the routine is detected by all processes in the communicator.

When the value of the datatype argument is invalid, the routine is detected by all processes in the communicator.

When the value of the reduce_count argument is negative, the routine is detected by all processes in the communicator.

When the value of the info argument is invalid, the routine is detected by all processes in the communicator.

When the value of the session_info argument is invalid, the routine is detected by all processes in the communicator.

When the value of the request argument is invalid, the routine is detected by all processes in the communicator.

When the value of the newop argument is invalid, the routine is detected by all processes in the communicator.

The correctness of MPI programs is the responsibility of the programmer.

If the MPI program fails to detect an error, the MPI implementation will report the error. The MPI error handler attached to MPI_COMM_WORLD will be called.

Possible MPI errors are:

  • MPI_ERR_ARG: Invalid argument. None of the arguments of the MPI function, besides the return codes, are valid.
  • MPI_ERR_COMM: Invalid communicator.
  • MPI_ERR_OP: Invalid operation.
  • MPI_ERR_TYPE: Invalid datatype.
  • MPI_ERR_COUNT: Invalid count.
  • MPI_ERR_INFO: Invalid info.
  • MPI_ERR_REQUEST: Invalid request.
  • MPI_ERR_SESSION: Invalid session.

The error handler attached to the communicator may be changed with MPI_Comm_set_errhandler. The default error handler is MPI_ERRORS_ARE_FATAL.

For operations that are not collective, the error handler attached to the MPI object that is associated with the operation may be invoked. For collective operations, the error handler attached to the communicator is invoked.

If an error occurs during the initialization of an MPI operation, the error handler associated with the communicator is invoked. The error handler for communicators can be set at runtime using the MPI_ERRORS_RETURN environment variable or by calling MPI_Comm_set_errhandler. If the error handler is set to MPI_ERRORS_RETURN, the return code will be returned as the value of the function. Otherwise, the error handler will be invoked and control may or may not be returned to the caller.

The error handler for MPI objects can be set at initialization time using the MPI_Session_set_errhandler or at MPI_Session_init.

  • MPI_Win_create_errhandler then MPI_Win_set_errhandler

Note that MPI does not guarantee that an MPI program can continue past an error.

See the MPI man page for a full list of MPI error codes.

See the Error Handling section of the MPI-3.1 standard for more information.
