MPI_Gather, MPI_Igather, MPI_Gather_init - Recopila valores de un grupo de procesos.

SINÓPSIS

#include <mpi.h>

PARÁMETROS DE ENTRADA

  • sendbuf : Dirección de inicio del búfer de envío (elección).
  • sendcount : Número de elementos en el búfer de envío (entero).
  • sendtype : Tipo de datos de los elementos del búfer de envío (mango).
  • recvcount : Número de elementos para cualquier recepción individual (entero, solo significativo en la raíz).
  • recvtype : Tipo de datos de los elementos del búfer de recepción (mango, significativo solo en la raíz).
  • root : Rango del proceso receptor (entero).
  • comm : Comunicador (mango).
  • info : Info (mango, solo persistente).

PARÁMETROS DE SALIDA

•
recvbuf
Dirección del búfer de recepción (elección, significativo solo en la raíz).
  • request : Solicitud (mango, solo no bloqueante).
  • ierror : Solo Fortran: Estado de error (entero).

DESCRIPCIÓN

Cada proceso (incluido el proceso raíz) envía el contenido de su búfer de envío al proceso raíz. El proceso raíz recibe los mensajes y los almacena en orden de rango. El resultado es como si cada uno de los n procesos del grupo (incluido el proceso raíz) hubiera ejecutado una llamada a

MPI_Send(sendbuf, sendcount, sendtype, root, ...)

y la raíz hubiera ejecutado n llamadas a

MPI_Recv(recfbuf + i * recvcount * extent(recvtype), recvcount,
         recvtype, i, ...)

donde extent(recvtype) es la extensión del tipo obtenida de una llamada a MPI_Type_extent.

Una descripción alternativa es que los n mensajes enviados por los procesos del grupo se concatenan en orden de rango, y el mensaje resultante es recibido por la raíz como si fuera una llamada a MPI_Recv(recvbuf, recvcount * n, recvtype, ... ).

El búfer de recepción se ignora para todos los procesos que no son raíz.

Se permiten tipos de datos generales y derivados tanto para sendtype como para recvtype. La firma del tipo de sendcount, sendtype en el proceso i debe ser igual a la firma del tipo de recvcount, recvtype en la raíz. Esto implica que la cantidad de datos enviados debe ser igual a la cantidad de datos recibidos, de forma binaria entre cada proceso y la raíz. Todavía se permiten mapas de tipos distintos entre el emisor y el receptor.

Todos los argumentos de la función son significativos en el proceso raíz, mientras que en otros procesos, solo los argumentos sendbuf, sendcount, sendtype, root, comm son significativos. Los argumentos root y comm deben tener valores idénticos en todos los procesos.

La especificación de recuentos y tipos no debe hacer que ninguna ubicación en la raíz se escriba más de una vez. Dicha llamada es errónea. Tenga en cuenta que el argumento recvcount en la raíz indica el número de elementos que recibe de cada proceso, no el número total de elementos que recibe.

Ejemplo 1: Recopilar 100 enteros de cada proceso del grupo a la raíz.

MPI_Comm comm;
int gsize, sendarray[100];
int root, *rbuf;
...
MPI_Comm_size( comm, &gsize);
rbuf = (int*)malloc(gsize* 100*sizeof(int));
MPI_Gather( sendarray, 100, MPI_INT, rbuf, 100, MPI_INT, root, comm);

Ejemplo 2: Ejemplo anterior modificado: solo la raíz asigna memoria para el búfer de recepción.

MPI_Comm comm;
int gsize, sendarray[100];
int root, myrank, * rbuf;
...
MPI_Comm_rank( comm, myrank);
if ( myrank == root) {
  MPI_Comm_size( comm, &gsize);
  rbuf = (int *)malloc(gsize * 100*sizeof(int));
}
MPI_Gather( sendarray, 100, MPI_INT, rbuf, 100, MPI_INT, root, comm);

Ejemplo 3: Hacer lo mismo que el ejemplo anterior, pero usar un tipo de datos derivado. Tenga en cuenta que el tipo no puede ser todo el conjunto de gsize * 100 enteros, ya que la coincidencia de tipos se define de forma binaria entre la raíz y cada proceso en la recopilación.

MPI_Comm comm;
int gsize, sendarray[100];
int root, * rbuf;
MPI_Datatype rtype;
...
MPI_Comm_size( comm, &gsize);
MPI_Type_contiguous( 100, MPI_INT, &rtype);
MPI_Type_commit( &rtype );
rbuf = (int*)malloc(gsize* 100*sizeof(int));
MPI_Gather( sendarray, 100, MPI_INT, rbuf, 1, rtype, root, comm);

USO DE LA OPCIÓN IN-PLACE

Cuando el comunicador es un intracommunicator, puede realizar una operación de recopilación in-place (el búfer de salida se utiliza como búfer de entrada). Utilice la variable MPI_IN_PLACE como valor de sendbuf del proceso raíz. En este caso, sendcount y sendtype se ignoran, y se asume que la contribución del proceso raíz al vector recopilado ya está en el lugar correcto en el búfer de recepción. Tenga en cuenta que MPI_IN_PLACE es un tipo especial de valor; tiene las mismas restricciones en su uso que MPI_BOTTOM. Dado que la opción in-place convierte el búfer de recepción en un búfer de envío y recepción, una vinculación de Fortran que incluye INTENT debe marcar estos como INOUT, no como OUT.

CUANDO EL COMUNICADOR ES UN INTERCOMUNICADOR

Un intercomunicador se forma típicamente utilizando una llamada a MPI_Comm_connect o MPI_Comm_accept o entre dos grupos creados por MPI_Comm_split. La operación de recopilación de un intercomunicador realiza una recopilación entre los procesos del grupo local y los procesos del grupo remoto. Por lo tanto, para una llamada a MPI_Gather, MPI_Igather o MPI_Gather_init en un intercomunicador, uno de los dos grupos (el grupo local o el grupo remoto) debe ser el grupo raíz.

El proceso raíz de un intercomunicador debe estar en uno de los dos grupos. Si el proceso raíz está en el grupo local, entonces todos los procesos del grupo local llaman a la rutina colectiva y solo la raíz en el grupo local recibe datos de la raíz del grupo remoto. Si el proceso raíz está en el grupo remoto, entonces todos los procesos del grupo remoto llaman a la rutina colectiva y solo la raíz en el grupo remoto recibe datos de la raíz del grupo local. La rutina de recopilación de un intercomunicador recopila información de todos los procesos del grupo local y la envía a la raíz del grupo remoto.

Se puede usar MPI_IN_PLACE para el búfer de envío en la raíz si la raíz está en el grupo local. En este caso, la información de envío de los procesos remotos se coloca directamente en el búfer de recepción de la raíz.

Los argumentos de la rutina se definen como se describe en la sección "DESCRIPCIÓN" para la llamada a MPI_Gather, excepto que el comunicador, comm, debe ser un intercomunicador.

En el grupo remoto, el argumento root debe ser MPI_ROOT.

En el grupo local, el argumento root debe ser el rango del proceso raíz en el grupo remoto.

En el grupo remoto, el argumento sendbuf, sendcount, sendtype se ignoran.

En el grupo local, el argumento recvbuf, recvcount, recvtype se ignoran.

La llamada es bloqueante y devolverá cuando el mensaje de recopilación haya sido enviado por el proceso raíz del grupo remoto.

La llamada es no bloqueante y devolverá cuando la solicitud de recopilación se haya iniciado.

La llamada es persistente y devolverá cuando la solicitud de recopilación se haya iniciado.

La llamada es bloqueante y devolverá cuando el mensaje de recopilación haya sido enviado por el proceso raíz del grupo remoto.

La llamada es no bloqueante y devolverá cuando la solicitud de recopilación se haya iniciado.

La llamada es persistente y devolverá cuando la solicitud de recopilación se haya iniciado.

Para los intercomunicadores, la llamada puede ser entre el grupo principal y el grupo de trabajadores. En este caso, si el grupo principal es el grupo raíz, entonces todos los procesos del grupo principal llaman a la rutina y solo la raíz en el grupo principal recibe datos de la raíz del grupo de trabajadores. Si el grupo de trabajadores es el grupo raíz, entonces todos los procesos del grupo de trabajadores llaman a la rutina y solo la raíz en el grupo de trabajadores recibe datos de la raíz del grupo principal.

La llamada es bloqueante y devolverá cuando el mensaje de recopilación haya sido enviado por el proceso raíz del grupo de trabajadores.

La llamada es no bloqueante y devolverá cuando la solicitud de recopilación se haya iniciado.

La llamada es persistente y devolverá cuando la solicitud de recopilación se haya iniciado.

ERRORES

Se puede producir un error de comunicación si el proceso raíz es llamado por un rango no válido. Si el proceso raíz es llamado por un rango inválido, la llamada puede fallar.

Se pueden producir errores de comunicación si los contadores o los tipos de datos no son válidos.

UNICATOR

Cuando el comunicador es un inter-comunicador, el proceso raíz del primer grupo recopila datos de todos los procesos del segundo grupo. El primer grupo define el proceso raíz. Ese proceso utiliza MPI_ROOT como valor de su argumento raíz. Los procesos restantes utilizan MPI_PROC_NULL como valor de su argumento raíz. Todos los procesos del segundo grupo utilizan el rango de ese proceso raíz en el primer grupo como valor de su argumento raíz. El argumento del búfer de envío de los procesos del primer grupo debe ser consistente con el argumento del búfer de recepción del proceso raíz del segundo grupo.

ERRORES

Casi todas las rutinas de MPI devuelven un valor de error; las rutinas C como resultado de retorno de la función y las rutinas Fortran en el último argumento.

Antes de que se devuelva el valor de error, se llama al controlador de errores MPI actual asociado con el objeto de comunicación (por ejemplo, comunicador, ventana, archivo). Si no hay ningún objeto de comunicación asociado con la llamada MPI, entonces la llamada se considera adjunta a MPI_COMM_SELF y llamará al controlador de errores MPI asociado. Cuando MPI_COMM_SELF no está inicializado (es decir, antes de MPI_Init/MPI_Init_thread, después de MPI_Finalize, o cuando se utiliza exclusivamente el Modelo de Sesiones) el error activa el controlador de errores inicial. El controlador de errores inicial se puede cambiar llamando a MPI_Comm_set_errhandler en MPI_COMM_SELF cuando se utiliza el modelo World, o al argumento CLI mpi_initial_errhandler para mpiexec o la clave de información para MPI_Comm_spawn/MPI_Comm_spawn_multiple. Si no se ha configurado ningún otro controlador de errores apropiado, entonces se llama al controlador de errores MPI_ERRORS_RETURN para las funciones de E/S de MPI y al controlador de errores MPI_ERRORS_ABORT para todas las demás funciones de MPI.

Open MPI incluye tres controladores de errores predefinidos que se pueden utilizar:

  • MPI_ERRORS_ARE_FATAL Provoca que el programa aborte todos los procesos MPI conectados.
  • MPI_ERRORS_ABORT Un controlador de errores que se puede invocar en un comunicador, ventana, archivo o sesión. Cuando se llama en un comunicador, actúa como si se hubiera llamado a MPI_Abort en ese comunicador. Si se llama en una ventana o archivo, actúa como si se hubiera llamado a MPI_Abort en un comunicador que contiene el grupo de procesos en la ventana o archivo correspondiente. Si se llama en una sesión, solo aborta el proceso local.
  • MPI_ERRORS_RETURN Devuelve un código de error a la aplicación.

Las aplicaciones MPI también pueden implementar sus propios controladores de errores llamando a:

  • MPI_Comm_create_errhandler luego MPI_Comm_set_errhandler
  • MPI_File_create_errhandler luego MPI_File_set_errhandler
  • MPI_Session_create_errhandler luego MPI_Session_set_errhandler o en MPI_Session_init
  • MPI_Win_create_errhandler luego MPI_Win_set_errhandler

Tenga en cuenta que MPI no garantiza que un programa MPI pueda continuar después de un error.

Consulte la página del manual de MPI para obtener una lista completa de los *códigos de error de MPI*.

Consulte la sección de Manejo de Errores del estándar MPI-3.1 para obtener más información.
