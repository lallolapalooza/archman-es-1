MPI_Scatterv, MPI_Iscatterv, MPI_Scatterv_init - Dispersa un búfer en partes a todas las tareas de un grupo.

PARÁMETROS DE ENTRADA

  • sendbuf: Dirección del búfer de envío (elección, significativo solo en la raíz).
  • sendcounts: Arreglo de enteros (de longitud igual al tamaño del grupo) que especifica el número de elementos a enviar a cada procesador.
  • displs: Arreglo de enteros (de longitud igual al tamaño del grupo). La entrada i especifica el desplazamiento (relativo a sendbuf) desde donde se tomarán los datos de salida para el proceso i.
  • sendtype: Tipo de datos de los elementos del búfer de envío (manejador).
  • recvcount: Número de elementos en el búfer de recepción (entero).
  • recvtype: Tipo de datos de los elementos del búfer de recepción (manejador).
  • root: Rango del proceso de envío (entero).
  • comm: Comunicador (manejador).
  • info: Información (manejador, solo persistente).

PARÁMETROS DE SALIDA

  • recvbuf: Dirección del búfer de recepción (elección).
  • request: Solicitud (manejador, solo no bloqueante).
  • ierror: Solo Fortran: Estado de error (entero).

DESCRIPCIÓN

MPI_Scatterv es la operación inversa a MPI_Gatherv.

MPI_Scatterv extiende la funcionalidad de MPI_Scatter al permitir que se envíe una cantidad variable de datos a cada proceso, ya que sendcounts es ahora un arreglo. También permite una mayor flexibilidad en cuanto a dónde se toman los datos en la raíz, al proporcionar el nuevo argumento displs.

El resultado es como si la raíz ejecutara n operaciones de envío,

MPI_Send(sendbuf + displs[i] * extent(sendtype),
         sendcounts[i], sendtype, i, ...);
// y cada proceso ejecutara una recepción,
MPI_Recv(recvbuf, recvcount, recvtype, root, ...)

El búfer de envío se ignora para todos los procesos que no son la raíz.

La firma de tipo implícita por sendcount[i], sendtype en la raíz debe ser igual a la firma de tipo implícita por recvcount, recvtype en el proceso i (sin embargo, los mapas de tipos pueden ser diferentes). Esto implica que la cantidad de datos enviados debe ser igual a la cantidad de datos recibidos, par a par entre cada proceso y la raíz. Todavía se permiten mapas de tipos distintos entre el remitente y el receptor.

Todos los argumentos de la función son significativos en el proceso root, mientras que en otros procesos, solo son significativos los argumentos recvbuf, recvcount, recvtype, root, comm. Los argumentos root y comm deben tener valores idénticos en todos los procesos.

La especificación de recuentos, tipos y desplazamientos no debe causar que se lea ninguna ubicación en la raíz más de una vez.

Ejemplo 1: El reverso del Ejemplo 5 en la página del manual de MPI_Gatherv. Tenemos un stride variable entre bloques en el lado de envío (raíz), en el lado de recepción recibimos 100 - i elementos en la columna i de un arreglo C de 100 x 150 en el proceso i.

MPI_Comm comm;
int gsize,recvarray[100][150],*rptr;
int root, *sendbuf, myrank, bufsize, *stride;
MPI_Datatype rtype;
int i, *displs, *scounts, offset;
...
MPI_Comm_size( comm, &gsize);
MPI_Comm_rank( comm, &myrank );
stride = (int *)malloc(gsize*sizeof(int));
...
/* stride[i] para i = 0 a gsize-1 se establece de alguna manera
 * sendbuf proviene de otro lugar
 */
...
displs = (int *)malloc(gsize*sizeof(int));
scounts = (int *)malloc(gsize*sizeof(int));
offset = 0;
for (i=0; i<gsize; ++i) {
    displs[i] = offset;
    offset += stride[i];
    scounts[i] = 100 - i;
}
/* Crear tipo de datos para la columna que estamos recibiendo
 */
MPI_Type_vector( 100-myrank, 1, 150, MPI_INT, &rtype);
MPI_Type_commit( &rtype );
rptr = &recvarray[0][myrank];
MPI_Scatterv(sendbuf, scounts, displs, MPI_INT,
             rptr, 1, rtype, root, comm);

Ejemplo 2: El reverso del Ejemplo 1 en el manual de MPI_Gather. El proceso raíz dispersa conjuntos de 100 enteros a los otros procesos, pero los conjuntos de 100 están separados por enteros de stride en el búfer de envío. Requiere el uso de MPI_Scatterv, donde stride >= 100.

MPI_Comm comm;
int gsize,*sendbuf;
int root, rbuf[100], i, *displs, *scounts;
...
MPI_Comm_size(comm, &gsize);
sendbuf = (int *)malloc(gsize*stride*sizeof(int));
...
displs = (int *)malloc(gsize*sizeof(int));
scounts = (int *)malloc(gsize*sizeof(int));
for (i=0; i<gsize; ++i) {
   displs[i] = i*stride;
   scounts[i] = 100;
}
MPI_Scatterv(sendbuf, scounts, displs, MPI_INT,
             rbuf, 100, MPI_INT, root, comm);

USO DE LA OPCIÓN EN-SITIO

Cuando el comunicador es un intracommunicador, puedes realizar una operación de dispersión en-sitio (el búfer de salida se usa como búfer de entrada). Usa la variable MPI_IN_PLACE como valor del recvbuf del proceso raíz. En este caso, recvcount y recvtype se ignoran, y el proceso raíz no envía datos a sí mismo.

El valor especial; tiene las mismas restricciones en su uso que MPI_BOTTOM.

El modo de uso en lugar de la dirección de memoria se convierte en un buffer de envío y recepción, por lo que una vinculación de Fortran que incluya INTENT debe marcar estos como INOUT, no como OUT.

PARÁMETROS DE ENTRADA

Cuando el comunicador es un comunicador inter, el proceso raíz del primer grupo envía datos a todos los procesos del segundo grupo. El primer grupo define el proceso raíz. Este proceso utiliza MPI_ROOT como valor de su argumento root. Los procesos restantes utilizan MPI_PROC_NULL como valor de su argumento root. Todos los procesos del segundo grupo usan el número de rank del proceso raíz del primer grupo como valor de su argumento root. El argumento de buffer de recepción del proceso raíz del primer grupo debe ser consistente con el argumento de buffer de recepción de los procesos del segundo grupo.

ERRORES

La mayoría de las rutinas MPI devuelven un valor de error; las rutinas C devuelven el resultado de la función y las rutinas Fortran tienen el último argumento.

Antes de que el valor de error sea devuelto, se llama a la handler de error asociada con el objeto de comunicación (por ejemplo, comunicador, ventana, archivo) asociado con el llamado. Si no hay objeto de comunicación asociado con la llamada MPI, se considera que el llamado está asociado a MPI_COMM_SELF y se llama al handler asociado con MPI_COMM_SELF. Cuando MPI_COMM_SELF no está inicializado (es decir, antes de MPI_Init/MPI_Init_thread, después de MPI_Finalize, o cuando se use el Modelo de Sesiones exclusivamente), el error levanta el handler de error inicial. El handler de error inicial puede cambiarse llamando a MPI_Comm_set_errhandler en MPI_COMM_SELF cuando se use el Modelo del Mundo, o al argumento mpi_initial_errhandler de mpiexec o a la clave info de MPI_Comm_spawn/MPI_Comm_spawn_multiple. Si no hay otro handler de error adecuado configurado, se llama el handler MPI_ERRORS_RETURN para las funciones de I/O MPI y el handler MPI_ERRORS_ABORT para todas las otras funciones MPI.

Open MPI incluye tres handlers de error prediseñados que se pueden usar:

  • MPI_ERRORS_ARE_FATAL Lanza un cierre de proceso para todos los procesos conectados.
  • MPI_ERRORS_ABORT Un handler de error que puede invocarse en un comunicador, ventana, archivo o sesión. Cuando se invoca en un comunicador, actúa como si se hubiera llamado MPI_Abort en ese comunicador. Si se invoca en una ventana o archivo, actúa como si se hubiera llamado MPI_Abort en un comunicador que contiene el grupo de procesos correspondiente. Si se invoca en una sesión, aborta solo el proceso local.
  • MPI_ERRORS_RETURN Devuelve un código de error a la aplicación.

Las aplicaciones MPI también pueden implementar sus propios handlers de error llamando:

  • MPI_Comm_create_errhandler luego MPI_Comm_set_errhandler
  • MPI_File_create_errhandler luego MPI_File_set_errhandler
  • MPI_Session_create_errhandler luego MPI_Session_set_errhandler o en MPI_Session_init
  • MPI_Win_create_errhandler luego MPI_Win_set_errhandler

Nota: MPI no garantiza que un programa MPI pueda continuar después de un error.

Ver la sección de manejo de errores de la estándar MPI-3.1 para más información.
