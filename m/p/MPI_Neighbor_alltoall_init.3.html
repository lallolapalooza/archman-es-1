PARÁMETROS DE ENTRADA

  • sendbuf: Dirección de inicio del búfer de envío (elección).
  • sendcount: Número de elementos a enviar a cada proceso (entero).
  • sendtype: Tipo de datos de los elementos del búfer de envío (manejador).
  • recvcount: Número de elementos a recibir de cada proceso (entero).
  • recvtype: Tipo de datos de los elementos del búfer de recepción (manejador).
  • comm: Comunicador sobre el cual se intercambiarán los datos (manejador).
  • info: Información (manejador, solo persistente).

PARÁMETROS DE SALIDA

  • recvbuf: Dirección de inicio del búfer de recepción (elección).
  • request: Solicitud (manejador, solo no bloqueante).
  • ierror: Solo Fortran: Estado de error (entero).

DESCRIPCIÓN

MPI_Neighbor_alltoall es una operación colectiva en la que todos los procesos envían y reciben la misma cantidad de datos a cada vecino. La operación de esta rutina se puede representar de la siguiente manera, donde cada proceso realiza 2n (n siendo el número de vecinos en el comunicador comm) comunicaciones punto a punto independientes. Los vecinos y la disposición de los búferes están determinados por la topología de comm.

Ejemplo de semántica de MPI_Neighbor_alltoall para topologías cartesianas:

MPI_Cart_get(comm, maxdims, dims, periods, coords);
for (dim = 0, i = 0 ; dim < dims ; ++dim) {
    MPI_Cart_shift(comm, dim, 1, &r0, &r1);
    MPI_Isend(sendbuf + i * sendcount * extent(sendtype),
              sendcount, sendtype, r0, ..., comm, ...);
    MPI_Irecv(recvbuf + i * recvcount * extent(recvtype),
              recvcount, recvtype, r0, ..., comm, ...);
    ++i;
    MPI_Isend(sendbuf + i * sendcount * extent(sendtype),
              sendcount, sendtype, r1, ..., comm, &req[i]);
    MPI_Irecv(recvbuf + i * recvcount * extent(recvtype),
              recvcount, recvtype, r1, ..., comm, ...);
    ++i;
}
MPI_Waitall (...);

Cada proceso divide su sendbuf local en n bloques, cada uno que contiene sendcount elementos del tipo sendtype, y divide su recvbuf de manera similar según recvcount y recvtype. El proceso j envía el k-ésimo bloque de su sendbuf local al vecino k, que coloca los datos en el j-ésimo bloque de su recvbuf local. La cantidad de datos enviados debe ser igual a la cantidad de datos recibidos, por pares, entre cada par de procesos.

ORDEN DE VECINOS

Para una topología de grafo distribuido, creada con MPI_Dist_graph_create, la secuencia de vecinos en los búferes de envío y recepción en cada proceso se define como la secuencia devuelta por MPI_Dist_graph_neighbors para destinos y fuentes, respectivamente. Para una topología de grafo general, creada con MPI_Graph_create, el orden de los vecinos en los búferes de envío y recepción se define como la secuencia de vecinos tal como la devuelve MPI_Graph_neighbors. Tenga en cuenta que las topologías de grafo generales deben ser reemplazadas por las topologías de grafo distribuidas.

Para una topología cartesiana, creada con MPI_Cart_create, la secuencia de vecinos en los búferes de envío y recepción en cada proceso se define por el orden de las dimensiones, primero el vecino en la dirección negativa y luego en la dirección positiva con un desplazamiento de 1. Los números de fuentes y destinos en las rutinas de comunicación son 2*ndims con ndims definidos en MPI_Cart_create. Si un vecino no existe, es decir, en el borde de una topología cartesiana en el caso de una dimensión de cuadrícula virtual no periódica (es decir, periods[…]==false), entonces este vecino se define como MPI_PROC_NULL.

Si un vecino en cualquiera de las funciones es MPI_PROC_NULL, entonces la comunicación colectiva de vecindad se comporta como una comunicación punto a punto con MPI_PROC_NULL en esa dirección. Es decir, el búfer sigue siendo parte de la secuencia de vecinos, pero ni se comunica ni se actualiza.

NOTAS

La opción MPI_IN_PLACE para sendbuf no tiene sentido para esta función.

Todos los argumentos en todos los procesos son significativos. El argumento comm, en particular, debe describir el mismo comunicador en todos los procesos. comm debe ser un comunicador cartesiano, de grafo o de grafo distribuido.

Existen dos funciones de la biblioteca MPI que son más generales que MPI_Neighbor_alltoall. MPI_Neighbor_alltoallv permite la comunicación de todos a todos hacia y desde búferes que no necesitan ser contiguos; diferentes procesos pueden enviar y recibir diferentes cantidades de datos. MPI_Neighbor_alltoallw amplía la funcionalidad de MPI_Neighbor_alltoallv para permitir el intercambio de datos con diferentes tipos de datos.

ERRORES

Casi todas las rutinas MPI devuelven un valor de error; las rutinas C como resultado de la función y las rutinas Fortran en el último argumento.

DESCRIPTION

The MPI collective communication function MPI_Neighbor_alltoall_init initializes a non-blocking all-to-all communication operation. This version of the all-to-all operation involves neighbor collectives, meaning that each process sends data to and receives data from its neighbors in the communicator's topology. The topology must be specified when the communicator is created (e.g., using MPI_Cart_create).

The MPI_Neighbor_alltoall_init_c function is the C binding for the same operation, using the MPI_Count integer type for counts.

This function does not perform the communication itself but rather sets up the operation to be performed later by calling MPI_Startall. The communication can be completed by calling MPI_Waitall or MPI_Testall.

The arguments sendbuf, sendcount, sendtype, recvbuf, recvcount, and recvtype specify the send and receive buffers and their data types. The comm argument specifies the communicator on which the operation will be performed.

The info argument can be used to provide hints to the MPI implementation about how to optimize the communication operation. It can be MPI_INFO_NULL if no hints are provided.

The function returns an MPI request handle in the request argument, which can be used to manage the non-blocking operation.

NEIGHBOR ORDERING

For neighbor collectives, the order of neighbors is determined by the topology of the communicator. Specifically:

  • For Cartesian topologies (created with MPI_Cart_create), the neighbors are ordered according to the dimensions of the grid.
  • For graph topologies (created with MPI_Graph_create), the neighbors are ordered according to their indices in the graph structure.

It is the user's responsibility to ensure that the send and receive buffers are set up correctly according to this neighbor ordering.

NOTES

The MPI_Neighbor_alltoall_init function is part of the MPI-3 standard.

The info argument is currently ignored by most MPI implementations but is included for future compatibility.

ERRORS

When the communicator is created, an error handler is associated with it. This error handler is called if the function detects an error during its execution. The default error handler is MPI_ERRORS_ABORT, which causes all processes in the communicator to abort. Any error handler attached to the communicator, by using MPI_Comm_set_errhandler, will be invoked. Additionally, if no error handler is associated with the communicator, the error is raised on MPI_COMM_SELF and the initial error handler is called. The initial error handler can be changed by calling MPI_Comm_set_errhandler on MPI_COMM_SELF when using the World model, or using the mpi_initial_errhandler CLI argument to mpiexec or info key to MPI_Comm_spawn/MPI_Comm_spawn_multiple. If no other appropriate error handler has been set, then the MPI_ERRORS_RETURN error handler is called for MPI I/O functions and the MPI_ERRORS_ABORT error handler is called for all other MPI functions.

Open MPI includes three predefined error handlers that can be used:

  • MPI_ERRORS_ARE_FATAL Causes the program to abort all connected MPI processes.
  • MPI_ERRORS_ABORT An error handler that can be invoked on a communicator, window, file, or session. When called on a communicator, it acts as if MPI_Abort was called on that communicator. If called on a window or file, acts as if MPI_Abort was called on a communicator containing the group of processes in the corresponding window or file. If called on a session, aborts only the local process.
  • MPI_ERRORS_RETURN Returns an error code to the application.

MPI applications can also implement their own error handlers by calling:

  • MPI_Comm_create_errhandler then MPI_Comm_set_errhandler
  • MPI_File_create_errhandler then MPI_File_set_errhandler
  • MPI_Session_create_errhandler then MPI_Session_set_errhandler or at MPI_Session_init
  • MPI_Win_create_errhandler then MPI_Win_set_errhandler

Note that MPI does not guarantee that an MPI program can continue past an error.

See the MPI man page for a full list of MPI error codes.

See the Error Handling section of the MPI-3.1 standard for more information.
