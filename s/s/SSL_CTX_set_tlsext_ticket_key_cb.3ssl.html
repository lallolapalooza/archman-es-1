SSL_CTX_set_tlsext_ticket_key_cb(3ssl)

Paquete: openssl

Licencias: Apache-2.0

SSL_CTX_SET_TLSEXT_TICKET_KEY_CB(3ssl) OpenSSL SSL_CTX_SET_TLSEXT_TICKET_KEY_CB(3ssl)

NOMBRE

SSL_CTX_set_tlsext_ticket_key_evp_cb, SSL_CTX_set_tlsext_ticket_key_cb - establecer una función de devolución de llamada para el procesamiento de tickets de sesión

SINOPSIS

#include <openssl/tls1.h>
int SSL_CTX_set_tlsext_ticket_key_evp_cb(SSL_CTX sslctx,
    int (*cb)(SSL *s, unsigned char key_name[16],
              unsigned char iv[EVP_MAX_IV_LENGTH],
              EVP_CIPHER_CTX *ctx, EVP_MAC_CTX *hctx, int enc));

La siguiente función ha sido marcada como obsoleta desde OpenSSL 3.0, y puede ocultarse completamente definiendo OPENSSL_API_COMPAT con un valor de versión adecuado, vea openssl_user_macros(7):

int SSL_CTX_set_tlsext_ticket_key_cb(SSL_CTX sslctx,
    int (*cb)(SSL *s, unsigned char key_name[16],
              unsigned char iv[EVP_MAX_IV_LENGTH],
              EVP_CIPHER_CTX *ctx, HMAC_CTX *hctx, int enc));

DESCRIPCIÓN

SSL_CTX_set_tlsext_ticket_key_evp_cb() establece una función de devolución de llamada cb para el manejo de tickets de sesión para el contexto ssl sslctx. Los tickets de sesión, definidos en RFC5077, proporcionan una capacidad mejorada de reanudación de sesión donde la implementación del servidor no requiere mantener estado por sesión. Solo se aplica a TLS y no hay implementación SSLv3.

La función de devolución de llamada cb se llamará para cada sesión TLS iniciada por el cliente cuando se presente la extensión de ticket de sesión en el mensaje TLS hello. Es responsabilidad de esta función crear o recuperar los parámetros criptográficos y mantener su estado.

La biblioteca OpenSSL utiliza su función de devolución de llamada para ayudar a implementar un estado de construcción de tickets TLS común según RFC5077 Sección 4, de modo que el estado por sesión sea innecesario y un pequeño conjunto de variables criptográficas deba ser mantenido por la implementación de la función de devolución de llamada.

Para reutilizar una sesión, un cliente TLS debe enviar la extensión de ticket de sesión al servidor. El cliente debe enviar exactamente un ticket de sesión. El servidor, a través de la función de devolución de llamada, acepta reutilizar la información del ticket de sesión o inicia una negociación TLS completa para crear un nuevo ticket de sesión.

Antes de que se inicie la función de devolución de llamada, ctx y hctx se han inicializado con EVP_CIPHER_CTX_reset(3) y EVP_MAC_CTX_new(3) respectivamente.

Para tickets de nuevas sesiones, cuando el cliente no presenta un ticket de sesión, o un intento de recuperación del ticket falló, o se indicó una opción de renovación, la función de devolución de llamada se llamará con enc igual a 1. La biblioteca OpenSSL espera que la función establezca un nombre arbitrario, inicialice iv, y establezca el contexto del cifrador ctx y el contexto hash hctx.

El nombre tiene 16 caracteres de longitud y se utiliza como identificador de clave.

La longitud del iv es la longitud del IV del cifrador correspondiente. La longitud máxima del IV es EVP_MAX_IV_LENGTH bytes definidos en <openssl/evp.h>.

El vector de inicialización iv debe ser un valor aleatorio. El contexto del cifrador ctx debe usar el vector de inicialización iv. El contexto del cifrador se puede establecer usando EVP_EncryptInit_ex(3). El contexto hmac y el digest se pueden establecer usando EVP_MAC_CTX_set_params(3) con los parámetros OSSL_MAC_PARAM_KEY y OSSL_MAC_PARAM_DIGEST respectivamente.

Cuando el cliente presenta un ticket de sesión, la función de devolución de llamada se llamará con enc establecido a 0, indicando que la función cb debe recuperar un conjunto de parámetros. En este caso, name e iv ya se han analizado a partir del ticket de sesión. La biblioteca OpenSSL espera que el nombre se utilice para recuperar un conjunto de parámetros criptográficos y que el contexto criptográfico ctx se establezca con los parámetros recuperados y el vector de inicialización iv, utilizando una función como EVP_DecryptInit_ex(3). El material de clave y el digest para hctx deben establecerse usando EVP_MAC_CTX_set_params(3) con los parámetros OSSL_MAC_PARAM_KEY y OSSL_MAC_PARAM_DIGEST respectivamente.

Si el nombre aún es válido pero se requiere una renovación del ticket, la función de devolución de llamada debe devolver 2. La biblioteca llamará a la devolución de llamada nuevamente con un argumento de enc igual a 1 para establecer el nuevo ticket.

El valor de retorno de la función cb es utilizado por OpenSSL para determinar qué procesamiento adicional ocurrirá. Los siguientes valores de retorno tienen significado:

2
Esto indica que ctx y hctx se han establecido y la sesión puede continuar con esos parámetros. Adicionalmente, indica que el ticket de sesión está en un período de renovación y debe ser reemplazado. La biblioteca OpenSSL llamará a cb nuevamente con un argumento enc de 1 para establecer el nuevo ticket (ver RFC5077 3.3 párrafo 2).
1
Esto indica que ctx y hctx se han establecido y la sesión puede continuar con esos parámetros.
0
Esto indica que no fue posible establecer/recuperar un ticket de sesión y la sesión SSL/TLS continuará negociando un conjunto de parámetros criptográficos o utilizando el mecanismo alternativo de reanudación SSL/TLS, identificadores de sesión.

Si se llama con enc igual a 0, la biblioteca llamará a cb nuevamente para obtener un nuevo conjunto de parámetros.

menor que 0
Esto indica un error.

La función SSL_CTX_set_tlsext_ticket_key_cb() es idéntica a SSL_CTX_set_tlsext_ticket_key_evp_cb() excepto que toma un puntero HMAC_CTX obsoleto en lugar de uno EVP_MAC_CTX. Antes de que se inicie esta función de devolución de llamada, hctx se habrá inicializado con EVP_MAC_CTX_new(3) y el digest se habrá establecido con EVP_MAC_CTX_set_params(3). El material de clave hctx se puede establecer usando HMAC_Init_ex(3).

NOTAS

La reanudación de sesión omite la negociación TLS para que no ocurra la negociación del certificado del cliente. Compensa esto almacenando el certificado del cliente y toda la otra información de estado negociada cifrada dentro del ticket. En una sesión reanudada, las aplicaciones tendrán toda esta información de estado disponible exactamente como si hubiera ocurrido una negociación completa.

Si un atacante puede obtener la clave utilizada para cifrar un ticket de sesión, puede obtener el secreto maestro de cualquier ticket que use esa clave y descifrar cualquier tráfico que use esa sesión, incluso si el conjunto de cifrado admite la secreto directo (forward secrecy). Como resultado, las aplicaciones pueden desear usar múltiples claves y evitar usar claves a largo plazo almacenadas en archivos.

Las aplicaciones pueden usar claves más largas para mantener un nivel consistente de seguridad. Por ejemplo, si un conjunto de cifrado usa cifrados de 256 bits pero solo una clave de ticket de 128 bits, la seguridad general es solo de 128 bits porque romper la clave del ticket permitirá a un atacante obtener las claves de sesión.

VALORES DE RETORNO

Devuelve 1 para indicar que la función de devolución de llamada se estableció correctamente y 0 en caso contrario.
