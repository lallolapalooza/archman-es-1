SSL_key_update(3ssl)

Paquete: openssl

Licencias: Apache-2.0

SSL_KEY_UPDATE(3ssl) OpenSSL SSL_KEY_UPDATE(3ssl)

NOMBRE

SSL_key_update, SSL_get_key_update_type, SSL_renegotiate, SSL_renegotiate_abbreviated, SSL_renegotiate_pending - iniciar y obtener información sobre la actualización de claves de conexión

SINOPSIS

#include <openssl/ssl.h>
int SSL_key_update(SSL *s, int updatetype);
int SSL_get_key_update_type(const SSL *s);
int SSL_renegotiate(SSL *s);
int SSL_renegotiate_abbreviated(SSL *s);
int SSL_renegotiate_pending(const SSL *s);

DESCRIPCIÓN

SSL_key_update() programa una actualización de las claves para la conexión TLS actual. Si el parámetro updatetype se establece en SSL_KEY_UPDATE_NOT_REQUESTED, entonces las claves de escritura para esta conexión se actualizarán y se informará al par sobre el cambio. Si el parámetro updatetype se establece en SSL_KEY_UPDATE_REQUESTED, entonces las claves de escritura para esta conexión se actualizarán y se informará al par sobre el cambio junto con una solicitud para que el par también actualice sus claves de escritura. Es un error si updatetype se establece en SSL_KEY_UPDATE_NONE.

SSL_key_update() solo debe llamarse después de que se haya completado el handshake inicial y se haya negociado TLSv1.3 o QUIC. Al mismo tiempo, la aplicación debe asegurarse de que la escritura de datos se haya completado. La actualización de claves no se llevará a cabo hasta la próxima vez que se realice una operación de E/S como SSL_read_ex() o SSL_write_ex() en la conexión. Alternativamente, se puede llamar a SSL_do_handshake() para forzar que la actualización se realice de inmediato.

SSL_get_key_update_type() se puede usar para determinar si se ha programado una operación de actualización de claves pero aún no se ha realizado. Se devolverá el tipo de la operación de actualización de claves pendiente, o SSL_KEY_UPDATE_NONE en caso contrario.

SSL_renegotiate() y SSL_renegotiate_abbreviated() solo deben llamarse para conexiones que hayan negociado TLSv1.2 o inferior. Llamarlas en cualquier otra conexión resultará en un error.

Cuando se llama desde el lado del cliente, SSL_renegotiate() programa un handshake completamente nuevo sobre una conexión SSL/TLS existente. La próxima vez que se realice una operación de E/S como SSL_read_ex() o SSL_write_ex() en la conexión, se realizará una comprobación para confirmar que es un momento adecuado para iniciar una renogociación. Si es así, se iniciará de inmediato. OpenSSL no intentará reanudar ninguna sesión asociada con la conexión en el nuevo handshake. Tenga en cuenta que algunos servidores responderán a los intentos de renogociación con una alerta de "no_renegotiation". OpenSSL fallará inmediatamente la conexión en este caso.

Cuando se llama desde el lado del cliente, SSL_renegotiate_abbreviated() funciona de la misma manera que SSL_renegotiate(), excepto que OpenSSL intentará reanudar la sesión asociada con la conexión actual en el nuevo handshake.

Cuando se llama desde el lado del servidor, SSL_renegotiate() y SSL_renegotiate_abbreviated() se comportan de manera idéntica. Ambos programan una solicitud para un nuevo handshake que se enviará al cliente. La próxima vez que se realice una operación de E/S, se realizarán las mismas comprobaciones que en el lado del cliente y luego, si es apropiado, se enviará la solicitud. El cliente puede o no responder con un nuevo handshake y puede o no intentar reanudar una sesión existente. Si se inicia un nuevo handshake, esto se manejará de forma transparente llamando a cualquier función de E/S de OpenSSL.

Si un cliente de OpenSSL recibe una solicitud de renogociación de un servidor, esto también se manejará de forma transparente llamando a cualquier función de E/S de OpenSSL. Para una conexión TLS, el cliente intentará reanudar la sesión actual en el nuevo handshake. Por razones históricas, los clientes DTLS no intentarán reanudar la sesión en el nuevo handshake.

La función SSL_renegotiate_pending() devuelve 1 si se ha programado una renogociación o una solicitud de renogociación pero aún no se ha actuado sobre ella, o 0 en caso contrario.

USO CON QUIC

SSL_key_update() también se puede usar para realizar una actualización de clave cuando se usa QUIC. La función debe llamarse en un objeto SSL de conexión QUIC. Esto normalmente se hace automáticamente cuando es necesario. Dado que una actualización de clave QUIC iniciada localmente siempre hace que el par también active una actualización de clave, pasar SSL_KEY_UPDATE_NOT_REQUESTED como updatetype tiene el mismo efecto que pasar SSL_KEY_UPDATE_REQUESTED.

La conexión QUIC debe haberse establecido por completo antes de que se pueda realizar una actualización de clave, y otras reglas del protocolo QUIC rigen la frecuencia con la que se puede realizar una actualización de clave QUIC. SSL_key_update() fallará si no se cumplen estos requisitos.

Debido a que las actualizaciones de clave QUIC se manejan inmediatamente, SSL_get_key_update_type() siempre devuelve SSL_KEY_UPDATE_NONE cuando se llama en un objeto SSL de conexión QUIC.

VALORES DE RETORNO

SSL_key_update(), SSL_renegotiate() y SSL_renegotiate_abbreviated() devuelven 1 en caso de éxito o 0 en caso de error.

SSL_get_key_update_type() devuelve el tipo de actualización de la operación de actualización de claves pendiente o SSL_KEY_UPDATE_NONE si no hay ninguna.

SSL_renegotiate_pending() devuelve 1 si se ha programado una renogociación o una solicitud de renogociación pero aún no se ha actuado sobre ella, o 0 en caso contrario.

VER TAMBIÉN

ssl(7), SSL_read_ex(3), SSL_write_ex(3), SSL_do_handshake(3)

HISTORIAL

Las funciones SSL_key_update() y SSL_get_key_update_type() se añadieron en OpenSSL 1.1.1.
