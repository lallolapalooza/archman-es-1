SSL_write(3ssl)

Paquete: openssl

Licencias: Apache-2.0

SSL_WRITE(3ssl) OpenSSL SSL_WRITE(3ssl)

NOMBRE

SSL_write_ex2, SSL_write_ex, SSL_write, SSL_sendfile, SSL_WRITE_FLAG_CONCLUDE - escribir bytes en una conexión TLS/SSL

SINOPSIS

#include <openssl/ssl.h>
#define SSL_WRITE_FLAG_CONCLUDE
ossl_ssize_t SSL_sendfile(SSL *s, int fd, off_t offset, size_t size, int flags);
int SSL_write_ex2(SSL *s, const void *buf, size_t num,
                  uint64_t flags,
                  size_t *written);
int SSL_write_ex(SSL *s, const void *buf, size_t num, size_t *written);
int SSL_write(SSL *ssl, const void *buf, int num);

DESCRIPCIÓN

SSL_write_ex() y SSL_write() escriben num bytes del buffer buf en la conexión ssl especificada. En caso de éxito, SSL_write_ex() almacenará el número de bytes escritos en *written.

SSL_write_ex2() funciona de manera similar a SSL_write_ex() pero también puede aceptar flags opcionales que modifican su comportamiento. Llamar a SSL_write_ex2() con un argumento flags de 0 es exactamente equivalente a llamar a SSL_write_ex().

SSL_sendfile() escribe size bytes desde el offset offset en el descriptor de archivo fd a la conexión SSL especificada s. Esta función proporciona semántica eficiente de copia cero. SSL_sendfile() solo está disponible cuando el TLS del kernel está habilitado, lo cual se puede verificar llamando a BIO_get_ktls_send(). Se proporciona aquí para permitir a los usuarios mantener la misma interfaz. El significado de flags depende de la plataforma. Actualmente, en Linux se ignora.

El argumento flags para SSL_write_ex2() puede aceptar cero o más de los siguientes flags. Tenga en cuenta que qué flags son compatibles dependerá del tipo de objeto SSL y del protocolo subyacente que se esté utilizando:

SSL_WRITE_FLAG_CONCLUDE
Este flag solo se admite en objetos SSL de flujo QUIC (o objetos SSL de conexión QUIC con un flujo predeterminado adjunto).

Si este flag está activado, y la llamada a SSL_write_ex2() tiene éxito, y todos los datos pasados a la llamada se han escrito (lo que significa que "*written == num"), la parte de envío del flujo QUIC relevante se concluye automáticamente como si se hubiera llamado a SSL_stream_conclude(3) (provocando la transmisión de un FIN para el flujo).

Si bien el uso de este flag es semánticamente equivalente a llamar a SSL_stream_conclude(3) después de una llamada exitosa a esta función, usar este flag permite una mayor eficiencia que realizar estas dos llamadas API por separado, ya que permite que los datos del flujo escritos y el flag FIN que indica el fin del flujo se programen como parte del mismo frame QUIC STREAM y paquete QUIC.

Establecer este flag no causa que la parte de envío de un flujo se concluya si no se consumieron todos los datos pasados a la llamada.

Una llamada a SSL_write_ex2() falla si se pasa un flag que no es compatible o no es entendido por el objeto SSL dado. Una aplicación debe determinar si un flag es compatible (por ejemplo, para SSL_WRITE_FLAG_CONCLUDE, que se está utilizando un objeto SSL de flujo QUIC) antes de intentar usarlo.

NOTAS

En los párrafos siguientes, una "función de escritura" se define como una de las siguientes: SSL_write_ex() o SSL_write().

Si es necesario, una función de escritura negociará una sesión TLS/SSL, si aún no se ha realizado explícitamente mediante SSL_connect(3) o SSL_accept(3). Si el par solicita una renegociación, se realizará de forma transparente durante la operación de la función de escritura. El comportamiento de las funciones de escritura depende del BIO subyacente.

Para que la negociación transparente tenga éxito, el ssl debe haber sido inicializado en modo cliente o servidor. Esto se hace llamando a SSL_set_connect_state(3) o SSL_set_accept_state() antes de la primera llamada a una función de escritura.

Si el BIO subyacente es de tipo **bloqueante**, las funciones de escritura solo devolverán cuando la operación de escritura se haya completado o se haya producido un error.

Si el BIO subyacente es de tipo **no bloqueante**, las funciones de escritura también devolverán cuando el BIO subyacente no haya podido satisfacer las necesidades de la función para continuar la operación. En este caso, una llamada a SSL_get_error(3) con el valor de retorno de la función de escritura devolverá SSL_ERROR_WANT_READ o SSL_ERROR_WANT_WRITE. Como en cualquier momento es posible una renegociación, una llamada a una función de escritura también puede provocar operaciones de lectura. El proceso que llama debe repetir la llamada después de tomar las medidas adecuadas para satisfacer las necesidades de la función de escritura. La acción depende del BIO subyacente. Al usar un socket no bloqueante, no hay nada que hacer, pero se puede usar select() para verificar la condición requerida. Al usar un BIO de almacenamiento en búfer, como un par de BIOs, los datos deben escribirse en el BIO o recuperarse de él antes de poder continuar.

Las funciones de escritura solo devolverán éxito cuando se haya escrito el contenido completo de buf de longitud num. Este comportamiento predeterminado se puede cambiar con la opción SSL_MODE_ENABLE_PARTIAL_WRITE de SSL_CTX_set_mode(3). Cuando esta bandera está activada, las funciones de escritura también devolverán éxito cuando se haya completado con éxito una escritura parcial. En este caso, la operación de la función de escritura se considera completada. Los bytes se envían y se debe iniciar una nueva llamada de escritura con un nuevo búfer (eliminando los bytes ya enviados).

Cuando se utiliza con un objeto SSL QUIC, la llamada a una función de E/S como SSL_write() permite realizar el procesamiento de eventos de red internos. Es importante que este procesamiento se realice regularmente. Si una aplicación no está utilizando el modo asistido por hilos, una aplicación debe asegurarse de que una función de E/S como SSL_write() se llame regularmente, o alternativamente asegurarse de que SSL_handle_events() se llame regularmente. Ver openssl-quic(7) y SSL_handle_events(3) para más información.

ADVERTENCIAS

Cuando una llamada a una función de escritura debe repetirse porque SSL_get_error(3) devolvió SSL_ERROR_WANT_READ o SSL_ERROR_WANT_WRITE, debe repetirse con los mismos argumentos. Los datos que se pasaron pueden haber sido procesados parcialmente. Cuando se estableció SSL_MODE_ACCEPT_MOVING_WRITE_BUFFER usando SSL_CTX_set_mode(3) el puntero puede ser diferente, pero los datos y la longitud deben seguir siendo los mismos.

No debes llamar a SSL_write() con num=0, devolverá un error. SSL_write_ex() puede llamarse con num=0, pero no enviará datos de aplicación al par.

VALORES DE RETORNO

SSL_write_ex() y SSL_write_ex2() devuelven 1 para éxito o 0 para fallo. Éxito significa que todos los bytes de datos de aplicación solicitados se han escrito en la conexión SSL o, si se está utilizando SSL_MODE_ENABLE_PARTIAL_WRITE, se ha escrito al menos 1 byte de datos de aplicación en la conexión SSL. Fallo significa que aún no se han escrito todos los bytes solicitados (si SSL_MODE_ENABLE_PARTIAL_WRITE no está en uso) o que no se pudieron escribir bytes en la conexión SSL (si SSL_MODE_ENABLE_PARTIAL_WRITE está en uso). Los fallos pueden ser reintentables (por ejemplo, el búfer de escritura de red se ha llenado temporalmente) o no reintentables (por ejemplo, un error de red fatal). En caso de fallo, llama a SSL_get_error(3) para averiguar el motivo, lo que indica si la llamada es reintentable o no.

Para SSL_write(), pueden ocurrir los siguientes valores de retorno:

> 0
La operación de escritura fue exitosa, el valor de retorno es el número de bytes escritos realmente en la conexión TLS/SSL.
<= 0
La operación de escritura no fue exitosa, ya sea porque la conexión se cerró, ocurrió un error o el proceso que llama debe tomar alguna acción. Llama a SSL_get_error() con el valor de retorno ret para averiguar el motivo.
