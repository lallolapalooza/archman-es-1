Paquete: openssl

SSL_SHUTDOWN(3ssl) OpenSSL SSL_SHUTDOWN(3ssl)

NOMBRE

SSL_shutdown, SSL_shutdown_ex - cerrar una conexión TLS/SSL o QUIC

SINOPSIS

#include <openssl/ssl.h>
int SSL_shutdown(SSL *ssl);
typedef struct ssl_shutdown_ex_args_st {
    uint64_t    quic_error_code;
    const char  *quic_reason;
} SSL_SHUTDOWN_EX_ARGS;
__owur int SSL_shutdown_ex(SSL *ssl, uint64_t flags,
                           const SSL_SHUTDOWN_EX_ARGS *args,
                           size_t args_len);

DESCRIPCIÓN

SSL_shutdown() cierra una conexión activa representada por un objeto SSL. ssl NO DEBE ser NULL.

SSL_shutdown_ex() es una versión extendida de SSL_shutdown(). Si no es NULL, args debe apuntar a una estructura SSL_SHUTDOWN_EX_ARGS y args_len debe establecerse en sizeof(SSL_SHUTDOWN_EX_ARGS). La estructura SSL_SHUTDOWN_EX_ARGS debe inicializarse a cero. Si args es NULL, el comportamiento es el mismo que pasar una estructura SSL_SHUTDOWN_EX_ARGS inicializada a cero. Actualmente, todos los argumentos extendidos se relacionan con el uso con QUIC, por lo tanto, esta llamada funciona de manera idéntica a SSL_shutdown() cuando no se utiliza con QUIC.

Si bien la operación general de SSL_shutdown() es común entre protocolos, la naturaleza exacta de cómo se realiza un cierre depende del protocolo subyacente que se esté utilizando. Consulte la sección a continuación correspondiente a cada protocolo para obtener más información.

En general, llamar a SSL_shutdown() en modo no bloqueante iniciará el proceso de cierre y devolverá 0 para indicar que el proceso de cierre aún no ha finalizado. Una vez que el proceso de cierre haya finalizado, las llamadas posteriores a SSL_shutdown() devolverán 1. Consulte la sección VALORES DE RETORNO para obtener más información.

SSL_shutdown() no debe llamarse si ha ocurrido un error fatal previo en una conexión; es decir, si SSL_get_error(3) ha devuelto SSL_ERROR_SYSCALL o SSL_ERROR_SSL.

CONSIDERACIONES ESPECÍFICAS DE TLS Y DTLS

El cierre para SSL/TLS y DTLS se implementa en términos del mensaje de alerta de cierre close_notify de SSL/TLS/DTLS. El proceso de cierre para SSL/TLS y DTLS consta de dos pasos:

  • Se envía un mensaje de alerta de cierre close_notify al par.
  • Se recibe un mensaje de alerta de cierre close_notify del par.

Estos pasos pueden ocurrir en cualquier orden dependiendo de si el proceso de cierre de la conexión fue iniciado primero por la aplicación local o por el par.

Cierre Iniciado Localmente

Llamar a SSL_shutdown() en un objeto SSL de SSL/TLS o DTLS inicia el proceso de cierre y hace que OpenSSL intente enviar una alerta de cierre close_notify al par. El proceso de cierre se considerará completado una vez que el par responda a su vez con un mensaje de alerta de cierre close_notify.

Llamar a SSL_shutdown() solo cierra la dirección de escritura de la conexión; la dirección de lectura es cerrada por el par. Una vez que se llama a SSL_shutdown(), SSL_write(3) ya no se puede usar, pero SSL_read(3) aún puede usarse hasta que el par decida cerrar la conexión a su vez. El par podría continuar enviando datos durante algún período de tiempo antes de manejar la indicación de cierre de la aplicación local.

SSL_shutdown() no afecta una conexión de red subyacente, como una conexión TCP, que permanece abierta.

Cierre Iniciado Remotamente

Si el par fue el primero en iniciar el proceso de cierre enviando un mensaje de alerta close_notify, se notificará a una aplicación de esto como una condición de EOF al llamar a SSL_read(3) (es decir, SSL_read(3) fallará y SSL_get_error(3) devolverá SSL_ERROR_ZERO_RETURN), después de que se hayan leído todos los datos de la aplicación enviados por el par antes de iniciar el cierre. Una aplicación debe manejar esta condición llamando a SSL_shutdown() para responder con una alerta close_notify a su vez, completando el proceso de cierre, aunque puede optar por escribir datos adicionales de la aplicación usando SSL_write(3) antes de hacerlo. Si una aplicación no llama a SSL_shutdown() en este caso, no se enviará una alerta close_notify y el comportamiento no será completamente compatible con los estándares.

Ciclo de Vida del Cierre

Independientemente de si un cierre se inició localmente o por el par, si el BIO subyacente está bloqueando, una llamada a SSL_shutdown() primero devolverá cuando se escriba un mensaje de alerta close_notify al par (devolviendo 0), y en una segunda llamada o posterior, cuando se reciba un mensaje correspondiente del par (devolviendo 1 y completando el proceso de cierre). Las llamadas a SSL_shutdown() con un BIO subyacente bloqueante también devolverán si ocurre un error.

Si el BIO subyacente no está bloqueando y el proceso de cierre aún no está completo (por ejemplo, porque aún no se ha recibido un mensaje de alerta close_notify del par, o porque se necesita enviar un mensaje de alerta close_notify pero actualmente se bloquearía), SSL_shutdown() devuelve 0 para indicar que el proceso de cierre aún está en curso; en este caso, una llamada a SSL_get_error(3) arrojará SSL_ERROR_WANT_READ o SSL_ERROR_WANT_WRITE.

Una aplicación puede entonces detectar la finalización del proceso de cierre llamando a SSL_shutdown() repetidamente hasta que devuelva 1, lo que indica que el proceso de cierre está completo (se ha enviado y recibido una alerta close_notify).

Sin embargo, el método preferido para esperar a que el cierre se complete es usar SSL_read(3) hasta que SSL_get_error(3) indique EOF devolviendo SSL_ERROR_ZERO_RETURN. Esto asegura que cualquier dato recibido inmediatamente antes de la alerta close_notify del par todavía se proporcione a la aplicación. También asegura que se procesen los mensajes finales de la capa de apretón de manos recibidos (por ejemplo, mensajes que emiten nuevos tickets de sesión).

Si no se utiliza este enfoque, la segunda llamada a SSL_shutdown() (para completar el cierre confirmando la recepción del mensaje close_notify del par) fallará si se llama cuando la aplicación no ha leído todos los datos pendientes enviados por el par usando SSL_read(3).

Al llamar a SSL_shutdown(), se establece la bandera SSL_SENT_SHUTDOWN una vez que se intenta enviar una alerta close_notify, independientemente de si el intento tuvo éxito. La bandera SSL_RECEIVED_SHUTDOWN se establece una vez que se recibe una alerta close_notify, lo que puede ocurrir durante cualquier llamada que procese datos entrantes de la red, como SSL_read(3) o SSL_shutdown(). Estas banderas se pueden verificar usando SSL_get_shutdown(3).

Cierre Rápido

Alternativamente, es aceptable que una aplicación llame a SSL_shutdown() una vez (de manera que devuelva 0) y luego cierre la conexión subyacente sin esperar la respuesta del par. Esto permite un proceso de cierre más rápido si la aplicación no desea esperar al par.

Este enfoque alternativo de "cierre rápido" solo debe hacerse si no hay intención de que el par envíe más datos, de lo contrario, existe el riesgo de que una aplicación se exponga a un ataque de truncamiento. El proceso completo de SSL_shutdown(), en el que ambas partes envían alertas close_notify y SSL_shutdown() devuelve 1, proporciona una indicación criptográficamente autenticada del final de una conexión.

Este enfoque de una única llamada a SSL_shutdown() sin esperar es preferible a simplemente llamar a SSL_free(3) o SSL_clear(3), ya que llamar a SSL_shutdown() de antemano hace que una sesión SSL sea elegible para su reutilización posterior y notifica al par sobre el cierre de la conexión.

NAME

SSL_shutdown, SSL_shutdown_ex - SSL/TLS shutdown

SYNOPSIS

#include <openssl/ssl.h>

int SSL_shutdown(SSL *s);
int SSL_shutdown_ex(SSL *s, uint64_t flags);

DESCRIPTION

The shutdown process for an SSL/TLS connection involves sending and receiving a close_notify alert. Both sides must complete this process for the shutdown to be considered complete. The SSL_shutdown() function attempts to perform this process.

A full shutdown process involves both sending and receiving the close_notify alert. The function will attempt to send a close_notify alert message if it has not already been sent, and then attempt to read any incoming alert messages. If the connection is not being used in non-blocking mode, SSL_shutdown() will call SSL_read(3) internally to read incoming alert messages until the shutdown is complete or an error occurs. If the connection is in non-blocking mode, SSL_shutdown() will return when it needs to read or write data, and the application must call it again until it returns 1.

The return values are:

1
The shutdown was successful.
0
The shutdown is not yet finished. The application should call SSL_shutdown() again. This typically happens when the connection is in non-blocking mode, or when the peer has closed its end of the connection first.
<0
An error occurred during the shutdown. The error code can be obtained using SSL_get_error(3).

The function SSL_shutdown_ex() is similar to SSL_shutdown(), but allows for additional flags to be passed. Currently, the only defined flag is SSL_SHUTDOWN_FLAG_RAPID, which is used for QUIC specific shutdown.

If the underlying transport mechanism is not trusted to deliver all pending data before closing, then the full shutdown process must be performed to ensure synchronisation.

Effects on Session Reuse

Calling SSL_shutdown() sets the SSL_SENT_SHUTDOWN flag (see SSL_set_shutdown(3)), regardless of whether the transmission of the close_notify alert was successful or not. This makes the SSL session eligible for reuse; the SSL session is considered properly closed and can be reused for future connections.

Quiet Shutdown

SSL_shutdown() can be modified to set the connection to the "shutdown" state without actually sending a close_notify alert message; see SSL_CTX_set_quiet_shutdown(3). When "quiet shutdown" is enabled, SSL_shutdown() will always succeed and return 1 immediately.

This is not standards-compliant behaviour. It should only be done when the application protocol in use enables the peer to ensure that all data has been received, such that it doesn't need to wait for a close_notify alert, otherwise application data may be truncated unexpectedly.

Non-Compliant Peers

There are SSL/TLS implementations that never send the required close_notify alert message but simply close the underlying transport (e.g. a TCP connection) instead. This will ordinarily result in an error being generated.

If compatibility with such peers is desired, the option SSL_OP_IGNORE_UNEXPECTED_EOF can be set. For more information, see SSL_CTX_set_options(3).

Note that use of this option means that the EOF condition for application data does not receive cryptographic protection, and therefore renders an application potentially vulnerable to truncation attacks. Thus, this option must only be used in conjunction with an application protocol which indicates unambiguously when all data has been received.

An alternative approach is to simply avoid calling SSL_read(3) if it is known that no more data is going to be sent. This requires an application protocol which indicates unambiguously when all data has been sent.

Session Ticket Handling

If a client application only writes to an SSL/TLS or DTLS connection and never reads, OpenSSL may never process new SSL/TLS session tickets sent by the server. This is because OpenSSL ordinarily processes handshake messages received from a peer during calls to SSL_read(3) by the application.

Therefore, client applications which only write and do not read but which wish to benefit from session resumption are advised to perform a complete shutdown procedure by calling SSL_shutdown() until it returns 1, as described above. This will ensure there is an opportunity for SSL/TLS session ticket messages to be received and processed by OpenSSL.

QUIC-SPECIFIC SHUTDOWN CONSIDERATIONS

When used with a QUIC connection SSL object, SSL_shutdown() initiates a QUIC immediate close using QUIC CONNECTION_CLOSE frames.

SSL_shutdown() cannot be used on QUIC stream SSL objects. To conclude a stream normally, see SSL_stream_conclude(3); to perform a non-normal stream termination, see SSL_stream_reset(3).

SSL_shutdown_ex() may be used instead of SSL_shutdown() by an application to provide additional information to the peer on the reason why a connection is being shut down. The information which can be provided is as follows:

quic_error_code
An optional 62-bit application error code to be signalled to the peer. The value must be in the range [0, 2**62-1], else the call to SSL_shutdown_ex() fails. If not provided, an error code of 0 is used by default.
quic_reason
An optional zero-terminated (UTF-8) reason string to be signalled to the peer. The application is responsible for providing a valid UTF-8 string and OpenSSL will not validate the string. If a reason is not provided, or SSL_shutdown() is used, a zero-length string is used as the reason. If provided, the reason string is copied and stored inside the QUIC connection SSL object and need not remain allocated after the call to SSL_shutdown_ex() returns. Reason strings are bounded by the path MTU and may be silently truncated if they are too long to fit in a QUIC packet.

Reason strings are intended for human diagnostic purposes only, and should not be used for application signalling.

The arguments to SSL_shutdown_ex() are used only on the first call to SSL_shutdown_ex() (or SSL_shutdown()) for a given QUIC connection SSL object. These arguments are ignored on subsequent calls.

These functions do not affect an underlying network BIO or the resource it represents; for example, a UDP datagram provided to a QUIC connection as the network BIO will remain open.

Note that when using QUIC, an application must call SSL_shutdown() if it wants to ensure that all transmitted data was received by the peer. This is unlike a TLS/TCP connection, where reliable transmission of buffered data is the responsibility of the operating system. If an application calls SSL_free() on a QUIC connection SSL object or exits before completing the shutdown process using SSL_shutdown(), data which was written by the application using SSL_write(), but could not yet be transmitted, or which was sent but lost in the network, may not be received by the peer.

When using QUIC, calling SSL_shutdown() allows internal network event processing to be performed. It is important that this processing is performed regularly, whether during connection usage or during shutdown. If an application is not using thread assisted mode, an application conducting shutdown should either ensure that SSL_shutdown() is called regularly, or alternatively ensure that SSL_handle_events() is called regularly. See openssl-quic(7) and SSL_handle_events(3) for more information.

Application Data Drainage Behaviour

When using QUIC, SSL_shutdown() or SSL_shutdown_ex() ordinarily waits until all data written to a stream by an application has been acknowledged by the peer. In other words, the shutdown process waits until all data written by the application has been sent to the peer, and until the receipt of all such data is acknowledged by the peer. Only once this process is completed is the shutdown considered complete.

An exception to this is streams which terminated in a non-normal fashion, for example due to a stream reset; only streams which are non-terminated at the time SSL_shutdown() is called, or which terminated in a normal fashion, have their pending send buffers flushed in this manner.

This behaviour of flushing streams during the shutdown process can be skipped by setting the SSL_SHUTDOWN_FLAG_NO_STREAM_FLUSH flag in a call to SSL_shutdown_ex(); in this case, data remaining in stream send buffers may not be transmitted to the peer. This flag may be used when a non-normal application condition has occurred and the delivery of data written to streams via SSL_write(3) is no longer relevant.

Shutdown Mode

Aspects of how QUIC handles connection closure must be taken into account by applications. Ordinarily, QUIC expects a connection to continue to be serviced for a substantial period of time after it is nominally closed. This is necessary to ensure that any connection closure notification sent to the peer was successfully received. However, a consequence of this is that a fully RFC-compliant QUIC connection closure process could take of the order of seconds. This may be unsuitable for some applications, such as short-lived processes which need to exit immediately after completing an application-layer transaction.

As such, there are two shutdown modes available to users of QUIC connection SSL objects:

RFC compliant shutdown mode
This is the default behaviour. The shutdown process may take a period of time up to three times the current estimated RTT to the peer. It is possible for the closure process to complete much faster in some circumstances but this cannot be relied upon.

In blocking mode, the function will return once the closure process is complete. In nonblocking mode, SSL_shutdown_ex() should be called until it returns 1, indicating the closure process is complete and the connection is now fully shut down.

Rapid shutdown mode
In this mode, the peer is notified of connection closure on a best effort basis by sending a single QUIC packet. If that QUIC packet is lost, the peer will not know that the connection has terminated until the negotiated idle timeout (if any) expires.

This will generally return 0 on success, indicating that the connection has not yet been fully shut down (unless it has already done so, in which case it will return 1).

If SSL_SHUTDOWN_FLAG_RAPID is specified in flags, a rapid shutdown is performed, otherwise an RFC-compliant shutdown is performed.

If an application calls SSL_shutdown_ex() with SSL_SHUTDOWN_FLAG_RAPID, an application can subsequently change its mind about performing a rapid shutdown by making a subsequent call to SSL_shutdown_ex() without the flag set.

DESCRIPCIÓN

SSL_shutdown() especifica los flags para controlar el cierre de la conexión. En modo de bloqueo, esto espera hasta que el par inicie un cierre o la conexión se termine de otra manera por algún otro motivo. VALORES DE RETORNO

Tanto para SSL_shutdown() como para SSL_shutdown_ex() pueden ocurrir los siguientes valores de retorno:

0
El proceso de cierre está en curso y aún no ha finalizado. Para TLS y DTLS, esto significa que se ha enviado una alerta de close_notify pero el par aún no ha respondido a su vez con su propia alerta close_notify. Para los objetos SSL de conexión QUIC, puede haberse enviado un marco de CONNECTION_CLOSE pero el proceso de cierre de la conexión aún no ha finalizado. A diferencia de la mayoría de las otras funciones, devolver 0 no indica un error. No se debe llamar a SSL_get_error(3); puede indicar erróneamente un error aunque no haya ocurrido ningún error.
1
El cierre se completó con éxito. Para TLS y DTLS, esto significa que se envió una alerta de close_notify y se recibió la alerta close_notify del par. Para los objetos SSL de conexión QUIC, esto significa que el proceso de cierre de la conexión ha finalizado.
<0
El cierre no fue exitoso. Llame a SSL_get_error(3) con el valor de retorno ret para averiguar el motivo. Puede ocurrir si se necesita una acción para continuar la operación para BIOs no bloqueantes. También puede ocurrir cuando no se han leído todos los datos usando SSL_read(), o si se llama en un objeto SSL de flujo QUIC. Este valor también se devuelve cuando se llama en objetos SSL de flujo QUIC.
