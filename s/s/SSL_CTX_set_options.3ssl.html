SSL_CTX_set_options(3ssl)

Paquete: openssl

Licencias: Apache-2.0

SSL_CTX_SET_OPTIONS(3ssl) OpenSSL SSL_CTX_SET_OPTIONS(3ssl)

NOMBRE

SSL_CTX_set_options, SSL_set_options, SSL_CTX_clear_options, SSL_clear_options, SSL_CTX_get_options, SSL_get_options, SSL_get_secure_renegotiation_support - manipular opciones SSL

SINOPSIS

#include <openssl/ssl.h>
uint64_t SSL_CTX_set_options(SSL_CTX *ctx, uint64_t options);
uint64_t SSL_set_options(SSL *ssl, uint64_t options);
uint64_t SSL_CTX_clear_options(SSL_CTX *ctx, uint64_t options);
uint64_t SSL_clear_options(SSL *ssl, uint64_t options);
uint64_t SSL_CTX_get_options(const SSL_CTX *ctx);
uint64_t SSL_get_options(const SSL *ssl);
long SSL_get_secure_renegotiation_support(SSL *ssl);

DESCRIPCIÓN

SSL_CTX_set_options() añade las opciones establecidas mediante máscara de bits en options a ctx. ¡ctx NO DEBE ser NULL. Las opciones ya establecidas previamente no se borran!

SSL_set_options() añade las opciones establecidas mediante máscara de bits en options a ssl. ¡Las opciones ya establecidas previamente no se borran!

SSL_CTX_clear_options() borra las opciones establecidas mediante máscara de bits en options de ctx.

SSL_clear_options() borra las opciones establecidas mediante máscara de bits en options de ssl.

SSL_CTX_get_options() devuelve las opciones establecidas para ctx.

SSL_get_options() devuelve las opciones establecidas para ssl.

SSL_get_secure_renegotiation_support() indica si el par admite la renégociation segura. Tenga en cuenta que esto se implementa mediante una macro.

NOTAS

El comportamiento de la biblioteca SSL puede modificarse estableciendo varias opciones. Las opciones se codifican como máscaras de bits y se pueden combinar mediante una operación OR bit a bit (|).

SSL_CTX_set_options() y SSL_set_options() afectan al comportamiento del protocolo (externo) de la biblioteca SSL. El comportamiento (interno) de la API se puede modificar utilizando las funciones similares SSL_CTX_set_mode(3) y SSL_set_mode().

Durante un handshake, se utilizan los ajustes de opción del objeto SSL. Cuando se crea un nuevo objeto SSL a partir de un contexto usando SSL_new(), se copia la configuración de opción actual. Los cambios en ctx no afectan a los objetos SSL ya creados. SSL_clear() no afecta a los ajustes.

Las siguientes opciones de solución de errores están disponibles:

SSL_OP_CRYPTOPRO_TLSEXT_BUG
Añade una extensión de server-hello de la versión temprana del borrador cryptopro cuando se negocia una suite de cifrado GOST. Requerido para la interoperabilidad con CryptoPro CSP 3.x.
SSL_OP_DONT_INSERT_EMPTY_FRAGMENTS
Deshabilita una contramedida contra una vulnerabilidad del protocolo SSL 3.0/TLS 1.0 que afecta a los cifrados CBC, que algunas implementaciones SSL defectuosas no pueden manejar. Esta opción no tiene efecto para conexiones que utilizan otros cifrados.
SSL_OP_SAFARI_ECDHE_ECDSA_BUG
No prefiera cifrados ECDHE-ECDSA cuando el cliente parece ser Safari en OS X. OS X 10.8..10.8.3 tiene soporte defectuoso para cifrados ECDHE-ECDSA.
SSL_OP_TLSEXT_PADDING
Añade una extensión de relleno para asegurar que el tamaño de ClientHello nunca esté entre 256 y 511 bytes. Esto es necesario como solución para algunas implementaciones.
SSL_OP_ALL
Todas las soluciones de errores anteriores.

Generalmente es seguro usar SSL_OP_ALL para habilitar las opciones de solución de errores si se desea compatibilidad con implementaciones algo defectuosas.

Las siguientes opciones de modificación están disponibles:

SSL_OP_ALLOW_CLIENT_RENEGOTIATION
La renégociation iniciada por el cliente está deshabilitada por defecto. Use esta opción para habilitarla.
SSL_OP_ALLOW_NO_DHE_KEX
En TLSv1.3 permite un modo de intercambio de claves no basado en (ec)dhe en la reanudación. Esto significa que no habrá secreto directo para la sesión reanudada.
SSL_OP_PREFER_NO_DHE_KEX
En TLSv1.3, en la reanudación, permite al servidor preferir un modo de intercambio de claves no basado en (ec)dhe sobre uno basado en (ec)dhe. Se ignora sin SSL_OP_ALLOW_NO_DHE_KEX también establecido. Siempre se ignora en el cliente.
SSL_OP_ALLOW_UNSAFE_LEGACY_RENEGOTIATION
Permite la renégociation heredada insegura entre OpenSSL y clientes o servidores sin parches. Ver la sección RENÉGOTIACIÓN SEGURA para más detalles.
SSL_OP_SERVER_PREFERENCE
Al elegir un cifrado, firma, curva (TLS 1.2) o grupo (TLS 1.3), usa las preferencias del servidor en lugar de las del cliente. Cuando no está establecido, el servidor SSL siempre seguirá las preferencias del cliente. Cuando está establecido, el servidor SSL/TLS elegirá según sus propias preferencias. El uso del nombre antiguo pero algo engañoso SSL_OP_CIPHER_SERVER_PREFERENCE todavía es posible pero no se recomienda.
SSL_OP_CISCO_ANYCONNECT
Usa el identificador de versión de Cisco de DTLS_BAD_VER al establecer una conexión DTLSv1. Solo disponible cuando se usa la API obsoleta DTLSv1_client_method().
SSL_OP_CLEANSE_PLAINTEXT
Por defecto, los objetos SSL TLS y QUIC conservan una copia de los datos de aplicación en texto plano recibidos en un buffer estático hasta que es sobrescrito por la siguiente porción de datos. Al habilitar SSL_OP_CLEANSE_PLAINTEXT, los datos de aplicación descifrados se limpian llamando a OPENSSL_cleanse(3) después de pasar los datos a la aplicación. Los datos también se limpian al liberar la conexión (por ejemplo, SSL_free(3)).

Dado que OpenSSL solo limpia los buffers internos, la aplicación sigue siendo responsable de limpiar todos los demás buffers. En particular, esto se aplica a los buffers pasados a funciones como SSL_read(3), SSL_peek(3) pero también como SSL_write(3).

Las conexiones TLS no almacenan en búfer datos para enviarlos en texto plano. Los objetos de flujo QUIC sí almacenan en búfer datos en texto plano para enviarlos y esta opción también hará que esos datos se limpien cuando se descarten.

Esta opción puede configurarse de manera diferente en objetos de flujo QUIC individuales y no tiene efecto en objetos de conexión QUIC (excepto donde se utiliza un flujo predeterminado).

SSL_OP_COOKIE_EXCHANGE
Activa el intercambio de cookies como se describe en RFC4347 Sección 4.2.1. Solo afecta a las conexiones DTLS.
SSL_OP_DISABLE_TLSEXT_CA_NAMES
Deshabilita los nombres CA de la extensión TLS. Puede que desee deshabilitarlo por razones de seguridad o por compatibilidad con algunas implementaciones TLS de Windows que fallan cuando esta extensión es mayor que 1024 bytes.
SSL_OP_ENABLE_KTLS
Habilita el uso de TLS del kernel. Para beneficiarse del TLS del kernel, OpenSSL debe haber sido compilado con soporte para él, y debe ser compatible con las suites de cifrado y extensiones negociadas. Las suites de cifrado y extensiones específicas que se admiten pueden variar según la plataforma y la versión del kernel.

La ruta de datos TLS del kernel implementa la capa de registro y el algoritmo de cifrado. El kernel utilizará el mejor hardware disponible para el cifrado. El uso de la ruta de datos del kernel debería reducir la huella de memoria de OpenSSL porque no se requiere almacenamiento en búfer. Además, el rendimiento debería mejorar porque se evita la copia de datos cuando los datos del usuario se cifran en la memoria del kernel en lugar de la copia habitual al kernel.

El TLS del kernel puede no admitir todas las funciones de OpenSSL. Por ejemplo, la renégociation y el establecimiento del tamaño máximo de fragmento no son posibles a partir de Linux 4

Tenga en cuenta que con TLS del kernel habilitado, algunas operaciones criptográficas son realizadas directamente por el kernel y no a través de ningún Proveedor de OpenSSL disponible. Esto podría ser indeseable si, por ejemplo, la aplicación requiere que todas las operaciones criptográficas sean realizadas por el proveedor FIPS.

SSL_OP_ENABLE_KTLS_TX_ZEROCOPY_SENDFILE
Con esta opción, sendfile() utilizará el modo zerocopy, lo que proporciona un aumento de rendimiento cuando se utiliza con la descarga de hardware KTLS. Tenga en cuenta que se pueden transmitir registros TLS inválidos si el archivo se modifica mientras se envía. Esta opción no tiene ningún efecto si SSL_OP_ENABLE_KTLS no está habilitado.

Esta opción solo se aplica a Linux. KTLS sendfile en FreeBSD no ofrece una opción para deshabilitar zerocopy y siempre se ejecuta en este modo.

SSL_OP_ENABLE_MIDDLEBOX_COMPAT
Si se establece, se envían mensajes dummy de Change Cipher Spec (CCS) en TLSv1.3. Esto tiene el efecto de hacer que TLSv1.3 se parezca más a TLSv1.2 para que las middleboxes que no entienden TLSv1.3 no descarten la conexión. Independientemente de si esta opción está establecida o no, los mensajes CCS recibidos del par siempre serán ignorados en TLSv1.3. Esta opción está establecida por defecto. Para desactivarla, use SSL_clear_options(). Una versión futura de OpenSSL podría no establecer esto por defecto.
SSL_OP_IGNORE_UNEXPECTED_EOF
Algunas implementaciones TLS no envían la alerta obligatoria close_notify al cerrar la conexión. Si la aplicación intenta esperar la alerta close_notify pero el par cierra la conexión sin enviarla, se genera un error. Cuando esta opción está habilitada, el par no necesita enviar la alerta close_notify y una conexión cerrada se tratará como si se hubiera recibido la alerta close_notify.

Solo debe habilitar esta opción si el protocolo que se ejecuta sobre TLS puede detectar un ataque de truncamiento por sí mismo, y si la aplicación está comprobando ese ataque de truncamiento.

Para obtener más información sobre cómo cerrar una conexión, consulte SSL_shutdown(3).

SSL_OP_LEGACY_SERVER_CONNECT
Permite la renégociación insegura heredada entre OpenSSL y servidores no actualizados únicamente. Ver la sección RENÉGOCIACIÓN SEGURA para más detalles.
SSL_OP_LEGACY_EC_POINT_FORMATS
Habilita el uso de los formatos de punto heredados para curvas elípticas. Esta opción habilita el soporte para los formatos de punto comprimido ANSI X9.62 prime y char2, además del formato no comprimido que está habilitado por defecto.
SSL_OP_NO_ANTI_REPLAY
Por defecto, cuando un servidor está configurado para datos tempranos (es decir, max_early_data > 0), OpenSSL activará la protección contra repeticiones. Ver SSL_read_early_data(3) para una descripción de la función de protección contra repeticiones. Las medidas anti-repetición son necesarias para cumplir con la especificación TLSv1.3. Algunas aplicaciones pueden mitigar los riesgos de repetición de otras maneras y, en tales casos, la funcionalidad integrada de OpenSSL no es necesaria. Dichas aplicaciones pueden desactivar esta función estableciendo esta opción. Esta es una opción solo del lado del servidor. Los clientes la ignoran.
SSL_OP_NO_TX_CERTIFICATE_COMPRESSION
Normalmente, los clientes y servidores intentarán negociar de forma transparente la opción de compresión de certificados RFC8879 en conexiones TLSv1.3.

Si se establece esta opción, la extensión de compresión de certificados se ignora al recibirla y los certificados comprimidos no se enviarán al par.

SSL_OP_NO_RX_CERTIFICATE_COMPRESSION
Normalmente, los clientes y servidores intentarán negociar de forma transparente la opción de compresión de certificados RFC8879 en conexiones TLSv1.3.

Si se establece esta opción, la extensión de compresión de certificados no se enviará y los certificados comprimidos no se aceptarán del par.

SSL_OP_NO_COMPRESSION
No utilice la compresión de registros TLS, incluso si es compatible. Esta opción está establecida por defecto. Para desactivarla, use SSL_clear_options(). Tenga en cuenta que la compresión de registros TLS no se recomienda y no está disponible en el nivel de seguridad 2 o superior. A partir de OpenSSL 3.2, el nivel de seguridad por defecto es 2, por lo que borrar esta opción no tendrá ningún efecto sin cambiar también el nivel de seguridad por defecto. Ver SSL_CTX_set_security_level(3).
SSL_OP_NO_ENCRYPT_THEN_MAC
Normalmente, los clientes y servidores intentarán negociar de forma transparente la opción Encrypt-then-MAC RFC7366 en conexiones TLS y DTLS.

Si se establece esta opción, Encrypt-then-MAC está deshabilitado. Los clientes no la propondrán y los servidores no la aceptarán.

SSL_OP_NO_EXTENDED_MASTER_SECRET
Normalmente, los clientes y servidores intentarán negociar de forma transparente la opción Extended Master Secret RFC7627 en conexiones TLS y DTLS.

Si se establece esta opción, Extended Master Secret está deshabilitado. Los clientes no la propondrán y los servidores no la aceptarán.

SSL_OP_NO_QUERY_MTU
No consultar la MTU. Solo afecta a las conexiones DTLS.
SSL_OP_NO_RENEGOTIATION
Deshabilita toda la renégociación en TLSv1.2 y versiones anteriores. No envía mensajes HelloRequest, e ignora las solicitudes de renégociación a través de ClientHello.
SSL_OP_NO_SESSION_RESUMPTION_ON_RENEGOTIATION
Al realizar la renégociación como servidor, siempre inicia una nueva sesión (es decir, las solicitudes de reanudación de sesión solo se aceptan en el handshake inicial). Esta opción no es necesaria para los clientes.
SSL_OP_NO_SSLv3, SSL_OP_NO_TLSv1, SSL_OP_NO_TLSv1_1, SSL_OP_NO_TLSv1_2, SSL_OP_NO_TLSv1_3, SSL_OP_NO_DTLSv1, SSL_OP_NO_DTLSv1_2
Estas opciones desactivan las versiones de protocolo SSLv3, TLSv1, TLSv1.1, TLSv1.2 o TLSv1.3 con TLS, o las versiones DTLSv1, DTLSv1.2 con DTLS, respectivamente. A partir de OpenSSL 1.1.0, estas opciones están obsoletas; utilice SSL_CTX_set_min_proto_version(3) y SSL_CTX_set_max_proto_version(3) en su lugar.
SSL_OP_NO_TICKET
SSL/TLS admite dos mecanismos para reanudar sesiones: identificadores de sesión y tickets de sesión sin estado.

Al usar identificadores de sesión, se almacena una copia de la información de la sesión en el servidor y se envía un identificador único al cliente. Cuando el cliente desea reanudar, proporciona el identificador único para que el servidor pueda recuperar la información de la sesión de su caché.

Al usar tickets de sesión sin estado, el servidor utiliza una clave de cifrado de tickets de sesión para cifrar la información de la sesión. Estos datos cifrados se envían al cliente como un "ticket". Cuando el cliente desea reanudar, envía los datos cifrados de vuelta al servidor. De esta manera, el servidor puede operar sin estado: no es necesario almacenar información de sesión localmente.

El protocolo TLSv1.3 solo admite tickets y no admite directamente los identificadores de sesión. Sin embargo, OpenSSL permite dos modos de operación de tickets en TLSv1.3: con estado y sin estado. Los tickets sin estado funcionan de la misma manera que en TLSv1.2 e inferiores. Los tickets con estado imitan el comportamiento del identificador de sesión disponible en TLSv1.2 e inferiores. La información de la sesión se almacena en caché en el servidor y el identificador de sesión se envuelve en un ticket y se envía de vuelta al cliente. Cuando el cliente desea reanudar, presenta un ticket de la misma manera que para los tickets sin estado. El servidor puede entonces extraer el identificador de sesión del ticket y recuperar la información de la sesión de su caché.

Por defecto, OpenSSL utilizará tickets sin estado. La opción SSL_OP_NO_TICKET hará que no se emitan tickets sin estado. En TLSv1.2 e inferiores, esto significa que no se envía ningún ticket al cliente. En TLSv1.3 se enviará un ticket con estado. Esta es una opción solo del lado del servidor.

En TLSv1.3, es posible suprimir el envío de todos los tickets (con estado y sin estado) llamando a SSL_CTX_set_num_tickets(3) o SSL_set_num_tickets(3).

SSL_OP_PRIORITIZE_CHACHA
Cuando SSL_OP_SERVER_PREFERENCE está establecido, reprioriza temporalmente los cifrados ChaCha20-Poly1305 al principio de la lista de cifrados del servidor si un cifrado ChaCha20-Poly1305 está al principio de la lista de cifrados del cliente. Esto ayuda a los clientes (por ejemplo, móviles) a usar ChaCha20-Poly1305 si ese cifrado está en cualquier parte de la lista de cifrados del servidor; pero aún permite que otros clientes usen AES y otros cifrados. Requiere SSL_OP_SERVER_PREFERENCE.
SSL_OP_TLS_ROLLBACK_BUG
Deshabilita la detección de ataques de reversión de versión.

Durante el intercambio de claves del cliente, el cliente debe enviar la misma información sobre los niveles de protocolo SSL/TLS aceptables que durante el primer hello. Algunos clientes violan esta regla adaptándose a la respuesta del servidor. (Ejemplo: el cliente envía un hello SSLv2 y acepta hasta SSLv3.1=TLSv1, el servidor solo entiende hasta SSLv3. En este caso, el cliente aún debe usar el mismo anuncio SSLv3.1=TLSv1. Algunos clientes descienden a SSLv3 con respecto a la respuesta del servidor y violan la protección contra la reversión de versión.)

Las siguientes opciones ya no tienen ningún efecto, pero sus identificadores se conservan por motivos de compatibilidad:

SSL_OP_NETSCAPE_RE

USE_CIPHER_CHANGE_BUG

OpenSSL siempre intenta utilizar el cambio de cifrado como se describe en RFC 5746. Esto contrarresta el ataque de prefijo descrito en CVE-2009-3555 y otros.

Este ataque tiene consecuencias de gran alcance que deben ser conocidas por los desarrolladores de aplicaciones. En la descripción a continuación, una implementación que admite la renegociación segura se denomina con parches. Un servidor que no admite la renegociación segura se denomina sin parches.

Las siguientes secciones describen las operaciones permitidas por la implementación de renegociación segura en OpenSSL.

Cliente y servidor con parches

Las conexiones y la renegociación siempre están permitidas por las implementaciones de OpenSSL.

Cliente sin parches y servidor con parches de OpenSSL

La conexión inicial se realiza, pero la renegociación es denegada por el servidor con una alerta no_renegotiation si se utiliza TLS v1.0 o una alerta handshake_failure en SSL v3.0.

Si el servidor con parches intenta renegociar, se envía una alerta handshake_failure. Esto se debe a que el código del servidor puede no ser consciente de que el cliente no tiene parches.

Si se establece la opción SSL_OP_ALLOW_UNSAFE_LEGACY_RENEGOTIATION, la renegociación se realiza siempre.

Cliente con parches de OpenSSL y servidor sin parches

Si se establece la opción SSL_OP_LEGACY_SERVER_CONNECT o SSL_OP_ALLOW_UNSAFE_LEGACY_RENEGOTIATION, se realizan la conexión inicial y la renegociación entre clientes con parches y servidores sin parches. Si no se establece ninguna de las opciones, la conexión inicial a servidores sin parches falla.

Establecer la opción SSL_OP_LEGACY_SERVER_CONNECT tiene implicaciones de seguridad; los clientes que se conectan a servidores que no implementan la renegociación segura de RFC 5746 pueden verse afectados por ataques como CVE-2009-3555.

Las aplicaciones cliente de OpenSSL que deseen asegurarse de conectarse a servidores sin parches siempre deben establecer SSL_OP_LEGACY_SERVER_CONNECT.

Las aplicaciones cliente que deseen asegurarse de no conectarse a servidores sin parches (y así evitar cualquier problema de seguridad) siempre deben limpiar SSL_OP_LEGACY_SERVER_CONNECT utilizando SSL_CTX_clear_options() o SSL_clear_options().

La diferencia entre las opciones SSL_OP_LEGACY_SERVER_CONNECT y SSL_OP_ALLOW_UNSAFE_LEGACY_RENEGOTIATION es que SSL_OP_LEGACY_SERVER_CONNECT permite conexiones iniciales y renegociación entre clientes OpenSSL y servidores sin parches únicamente, mientras que SSL_OP_ALLOW_UNSAFE_LEGACY_RENEGOTIATION permite conexiones iniciales y renegociación entre clientes OpenSSL y servidores o clientes sin parches.

Aplicabilidad de las opciones a conexiones y flujos QUIC

Estas opciones se aplican a objetos SSL que se refieren a una conexión QUIC:

SSL_OP_ALLOW_NO_DHE_KEX
SSL_OP_NO_TX_CERTIFICATE_COMPRESSION
SSL_OP_NO_RX_CERTIFICATE_COMPRESSION
SSL_OP_NO_TICKET
SSL_OP_PRIORITIZE_CHACHA

Estas opciones se aplican a objetos SSL que se refieren a un flujo QUIC:

SSL_OP_CLEANSE_PLAINTEXT

Las opciones de conexión QUIC se inicializan según las opciones establecidas en el objeto SSL_CTX antes de crear el objeto SSL de conexión QUIC. Las opciones de flujo QUIC se inicializan según las opciones configuradas en el objeto SSL de conexión QUIC que las crea.

Establecer opciones relacionadas con los flujos QUIC en el objeto SSL de conexión QUIC no tiene un efecto directo sobre el objeto SSL de conexión QUIC en sí, pero cambiará las opciones del flujo predeterminado (si existe) y también determinará las opciones predeterminadas de cualquier flujo futuro que se cree.

Otras opciones no mencionadas aquí no tienen efecto y se ignoran.

Las opciones relacionadas con los flujos QUIC también pueden establecerse directamente en objetos SSL de flujo QUIC. Establecer opciones relacionadas con la conexión en dicho objeto no tiene efecto.

VALORES DE RETORNO

SSL_CTX_set_options() y SSL_set_options() devuelven la máscara de bits de opciones actualizada después de añadir options.

SSL_CTX_clear_options() y SSL_clear_options() devuelven la máscara de bits de opciones actualizada después de borrar options.

SSL_CTX_get_options() y SSL_get_options() devuelven la máscara de bits actual.

SSL_get_secure_renegotiation_support() devuelve 1 si el par admite la renegociación segura y 0 en caso contrario.

HISTORIAL

El intento de utilizar siempre la renegociación segura se agregó en OpenSSL 0.9.8m.

Las opciones SSL_OP_PRIORITIZE_CHACHA y SSL_OP_NO_RENEGOTIATION se agregaron en OpenSSL 1.1.1.

Las opciones SSL_OP_NO_EXTENDED_MASTER_SECRET y SSL_OP_IGNORE_UNEXPECTED_EOF se agregaron en OpenSSL 3.0.

Las constantes SSL_OP_ y los parámetros y valores devueltos de las funciones afectadas cambiaron a tipo "uint64_t" en OpenSSL 3.0. Por lo tanto, no es posible utilizar las macros SSL_OP_ en condiciones de preprocesador "#if". Sin embargo, todavía es posible verificar si estas macros están definidas o no.

Desde OpenSSL 3.6, el uso de la constante SSL_OP_CIPHER_SERVER_PREFERENCE no se recomienda y sus semánticas se pueden utilizar con la constante más adecuada SSL_OP_SERVER_PREFERENCE.
