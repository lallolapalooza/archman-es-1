SSL_CTX_dane_enable(3ssl)

Paquete: openssl

Licencias: Apache-2.0

SSL_CTX_DANE_ENABLE(3ssl) OpenSSL SSL_CTX_dane_enable(3ssl)

NOMBRE

SSL_CTX_dane_enable, SSL_CTX_dane_mtype_set, SSL_dane_enable, SSL_dane_tlsa_add, SSL_get0_dane_authority, SSL_get0_dane_tlsa, SSL_CTX_dane_set_flags, SSL_CTX_dane_clear_flags, SSL_dane_set_flags, SSL_dane_clear_flags - habilitar la autenticación TLS DANE del servidor TLS remoto en el cliente TLS local

SINOPSIS

#include <openssl/ssl.h>
int SSL_CTX_dane_enable(SSL_CTX *ctx);
int SSL_CTX_dane_mtype_set(SSL_CTX *ctx, const EVP_MD *md,
                           uint8_t mtype, uint8_t ord);
int SSL_dane_enable(SSL *s, const char *basedomain);
int SSL_dane_tlsa_add(SSL *s, uint8_t usage, uint8_t selector,
                      uint8_t mtype, const unsigned char *data, size_t dlen);
int SSL_get0_dane_authority(SSL *s, X509 **mcert, EVP_PKEY **mspki);
int SSL_get0_dane_tlsa(SSL *s, uint8_t *usage, uint8_t *selector,
                       uint8_t *mtype, const unsigned char **data,
                       size_t *dlen);
unsigned long SSL_CTX_dane_set_flags(SSL_CTX *ctx, unsigned long flags);
unsigned long SSL_CTX_dane_clear_flags(SSL_CTX *ctx, unsigned long flags);
unsigned long SSL_dane_set_flags(SSL *ssl, unsigned long flags);
unsigned long SSL_dane_clear_flags(SSL *ssl, unsigned long flags);

DESCRIPCIÓN

Estas funciones implementan el soporte para la autenticación de pares DANE TLSA (RFC6698 y RFC7671).

SSL_CTX_dane_enable() debe llamarse primero para inicializar el estado compartido requerido para el soporte DANE. Las conexiones individuales asociadas con el contexto pueden luego habilitar el soporte DANE por conexión según sea apropiado. La autenticación DANE se implementa en la función X509_verify_cert(3), y las aplicaciones que anulan X509_verify_cert(3) a través de SSL_CTX_set_cert_verify_callback(3) son responsables de autenticar la cadena de pares de la manera que consideren adecuada.

SSL_CTX_dane_mtype_set() puede llamarse cero o más veces para ajustar los algoritmos de resumen soportados. Esto debe hacerse antes de que se creen los manejadores SSL para el contexto.

El argumento mtype especifica un tipo de coincidencia DANE TLSA y el argumento md especifica el manejador del algoritmo de resumen asociado. El argumento ord especifica un ordinal de fortaleza. Los algoritmos con un ordinal de fortaleza mayor se consideran más seguros. Los ordinales de fortaleza se utilizan para implementar la agilidad del algoritmo de resumen RFC7671. Especificar un algoritmo de resumen NULL para un tipo de coincidencia deshabilita el soporte para ese tipo de coincidencia. El tipo de coincidencia Full(0) no se puede modificar ni deshabilitar.

Por defecto, el tipo de coincidencia "SHA2-256(1)" (ver RFC7218 para definiciones de los acrónimos de parámetros DANE TLSA) se mapea a EVP_sha256() con un ordinal de fortaleza de 1 y el tipo de coincidencia "SHA2-512(2)" se mapea a EVP_sha512() con un ordinal de fortaleza de 2.

SSL_dane_enable() debe llamarse antes de que se inicie el handshake SSL con SSL_connect(3) si (y solo si) desea habilitar DANE para esa conexión. (La conexión debe estar asociada con un contexto SSL habilitado para DANE). El argumento basedomain especifica el dominio base TLSA RFC7671, que será el identificador de referencia principal del par para las comprobaciones de nombres de certificado. Se pueden especificar nombres de servidor adicionales a través de SSL_add1_host(3). El basedomain se utiliza como indicio SNI predeterminado si aún no se ha especificado ninguno a través de SSL_set_tlsext_host_name(3).

SSL_dane_tlsa_add() puede llamarse entonces una o más veces, para cargar cada uno de los registros TLSA que se aplican al par TLS remoto. (Esto también debe hacerse antes del inicio del handshake SSL). Los argumentos especifican los campos del registro TLSA. El campo data se proporciona en forma binaria (RDATA de red), no en forma de presentación ASCII hexadecimal, con una longitud explícita pasada a través de dlen. La biblioteca toma una copia del contenido del búfer data y el llamador puede liberar el búfer data original cuando le sea conveniente. Un valor de retorno de 0 indica que se proporcionaron registros TLSA "inutilizables" (con parámetros inválidos o no soportados). Un valor de retorno negativo indica un error interno en el procesamiento del registro.

Se espera que el llamador verifique el valor de retorno de cada llamada a SSL_dane_tlsa_add() y tome las medidas apropiadas si ninguno es utilizable o si se produce un error interno al procesar algunos registros.

Si no se agregan registros TLSA con éxito, la autenticación DANE no está habilitada, y la autenticación se basará en cualquier ancla de confianza tradicional configurada; el éxito de la autenticación en este caso no significa que el par fue autenticado por DANE.

SSL_get0_dane_authority() se puede utilizar para obtener información más detallada sobre el ancla de confianza DANE coincidente después de completar la conexión con éxito. El valor de retorno es negativo si la verificación DANE falló (o no estaba habilitada), 0 si un registro TLSA DANE-EE coincidió directamente con el certificado hoja, o un número positivo que indica la profundidad en la que un registro TA coincidió con un certificado emisor. La cadena verificada completa se puede recuperar a través de SSL_get0_verified_chain(3). El valor de retorno es un índice en esta cadena verificada, en lugar de la lista de certificados enviada por el par, tal como la devuelve SSL_get_peer_cert_chain(3).

Si el argumento mcert no es NULL y un registro TLSA coincidió con un certificado de la cadena, se devuelve un puntero al certificado coincidente a través de mcert. La dirección devuelta es una referencia interna de corta duración al certificado y la aplicación no debe liberarla. Las aplicaciones que deseen conservar el acceso al certificado pueden llamar a X509_up_ref(3) para obtener una referencia de larga duración que luego debe liberarse con X509_free(3) una vez que ya no sea necesaria.

Si ningún registro TLSA coincidió directamente con ningún elemento de la cadena de certificados, pero un registro DANE-TA(2) SPKI(1) Full(0) proporcionó la clave pública que firmó un elemento de la cadena, entonces esa clave se devuelve a través del argumento mspki (si no es NULL). En este caso, el valor de retorno es la profundidad del elemento superior de la cadena de certificados validada. Al igual que con mcert, esta es una referencia interna de corta duración, y EVP_PKEY_up_ref(3) y EVP_PKEY_free(3) se pueden usar para adquirir y liberar referencias de larga duración respectivamente.

SSL_get0_dane_tlsa() se puede utilizar para recuperar los campos del registro TLSA que coincidió con la cadena de certificados del par. El valor de retorno indica la profundidad de la coincidencia o el fallo de la coincidencia al igual que con SSL_get0_dane_authority(). Cuando el valor de retorno es no negativo, el almacenamiento apuntado por los parámetros usage, selector, mtype y data se actualiza a los campos del registro TLSA correspondientes. El campo data está en formato binario de red, y por lo tanto no termina en NULO, su longitud se devuelve a través del parámetro dlen. Si alguno de estos parámetros es NULL, el campo correspondiente no se devuelve. El parámetro data se establece en una copia interna de corta duración del campo de datos asociado y la aplicación no debe liberarlo. Las aplicaciones que necesiten acceso a largo plazo a este campo deben copiar el contenido.

SSL_CTX_dane_set_flags() y SSL_dane_set_flags() se pueden utilizar para habilitar características de verificación DANE opcionales. SSL_CTX_dane_clear_flags() y SSL_dane_clear_flags() se pueden utilizar para deshabilitar las mismas características. El argumento flags es una máscara de bits de las características a habilitar o deshabilitar. Los flags establecidos para un contexto SSL_CTX se copian a cada manejador SSL asociado con ese contexto en el momento en que se crea el manejador. Los cambios posteriores en los flags del contexto no tienen efecto en los flags establecidos para el manejador.

Actualmente, la única opción disponible es DANE_FLAG_NO_DANE_EE_NAMECHECKS, que se puede usar para deshabilitar las comprobaciones de nombres de servidor al autenticar a través de registros TLSA DANE-EE(3). Para algunas aplicaciones, principalmente navegadores web, no es seguro deshabilitar las comprobaciones de nombres debido a ataques de "clave compartida desconocida", en los que un servidor malicioso puede convencer a un cliente de que una conexión a un servidor víctima es en realidad una conexión segura al servidor malicioso. El servidor malicioso puede entonces ser capaz de violar las restricciones de scripting entre orígenes. Por lo tanto, a pesar del texto de RFC7671, las comprobaciones de nombres están habilitadas por defecto

VALORES DE RETORNO

Las funciones SSL_CTX_dane_enable(), SSL_CTX_dane_mtype_set(), SSL_dane_enable() y SSL_dane_tlsa_add() devuelven un valor positivo en caso de éxito. Los valores de retorno negativos indican problemas de recursos (falta de memoria, etc.) en la biblioteca SSL, mientras que un valor de retorno de 0 indica un uso incorrecto o una entrada inválida, como un uso de certificado TLSA no admitido, selector o tipo de coincidencia. La entrada inválida también incluye datos malformados, ya sea una longitud de digest que no coincide con el algoritmo de digest, o un certificado Full(0) (formato DER binario ASN.1) o una clave pública que no se puede analizar.

Las funciones SSL_get0_dane_authority() y SSL_get0_dane_tlsa() devuelven un valor negativo cuando la autenticación DANE falló o no estaba habilitada, un valor no negativo indica la profundidad de la cadena en la que el registro TLSA coincidió con un certificado de la cadena, o la profundidad del certificado superior, cuando el registro TLSA es una clave pública completa que es su firmante.

Las funciones SSL_CTX_dane_set_flags(), SSL_CTX_dane_clear_flags(), SSL_dane_set_flags() y SSL_dane_clear_flags() devuelven los flags en vigor antes de que fueran llamadas.

EJEMPLOS

Supongamos que "smtp.example.com" es el host MX del dominio "example.com", y tiene registros TLSA validados por DNSSEC. Las llamadas a continuación realizarán la autenticación DANE y se organizarán para que coincidan con el nombre de host MX o el nombre de dominio de destino en el certificado del servidor SMTP. Los comodines son compatibles, pero deben coincidir con la etiqueta completa. El nombre real que coincide en el certificado (que podría ser un comodín) se recupera y debe ser copiado por la aplicación si se va a conservar más allá de la vida útil de la conexión SSL.

SSL_CTX *ctx;
SSL *ssl;
int (*verify_cb)(int ok, X509_STORE_CTX *sctx) = NULL;
int num_usable = 0;
const char *nexthop_domain = "example.com";
const char *dane_tlsa_domain = "smtp.example.com";
uint8_t usage, selector, mtype;
if ((ctx = SSL_CTX_new(TLS_client_method())) == NULL)
    /* error */
if (SSL_CTX_dane_enable(ctx) <= 0)
    /* error */
if ((ssl = SSL_new(ctx)) == NULL)
    /* error */
if (SSL_dane_enable(ssl, dane_tlsa_domain) <= 0)
    /* error */
/*
 * Para muchas aplicaciones es seguro omitir las comprobaciones de nombres
 * DANE-EE(3). No deshabilite las comprobaciones a menos que los ataques de
 * "clave compartida desconocida" no supongan ningún riesgo para
 * su aplicación.
 */
SSL_dane_set_flags(ssl, DANE_FLAG_NO_DANE_EE_NAMECHECKS);
if (!SSL_add1_host(ssl, nexthop_domain))
    /* error */
SSL_set_hostflags(ssl, X509_CHECK_FLAG_NO_PARTIAL_WILDCARDS);
for (... cada registro TLSA ...) {
    unsigned char *data;
    size_t len;
    int ret;
    /* establezca usage, selector, mtype, data, len */
    /*
     * Los clientes TLS DANE oportunistas solo admiten DANE-TA(2) o DANE-EE(3).
     * Tratan todos los demás usos de certificados, y en particular PKIX-TA(0)
     * y PKIX-EE(1), como inutilizables.
     */
    switch (usage) {
    default:
    case 0:     /* PKIX-TA(0) */
    case 1:     /* PKIX-EE(1) */
        continue;
    case 2:     /* DANE-TA(2) */
    case 3:     /* DANE-EE(3) */
        break;
    }
    ret = SSL_dane_tlsa_add(ssl, usage, selector, mtype, data, len);
    /* libere data según corresponda */
    if (ret < 0)
        /* maneje el error interno de la biblioteca SSL */
    else if (ret == 0)
        /* maneje el registro TLSA inutilizable */
    else
        ++num_usable;
}
/*
 * En este punto, el modo de verificación sigue siendo el predeterminado
 * SSL_VERIFY_NONE. Los clientes DANE oportunistas utilizan TLS sin
 * autenticar cuando todos los registros TLSA son inutilizables, por lo que
 * continúan el handshake incluso si la autenticación falla.
 */
if (num_usable == 0) {
    /* ¿Registrar todos los registros como inutilizables? */
    /* Opcionalmente, establezca verify_cb en una devolución de llamada adecuada
     * no NULL. */
    SSL_set_verify(ssl, SSL_VERIFY_NONE, verify_cb);
} else {
    /* Al menos un registro utilizable. Esperamos verificar al par */
    /* Opcionalmente, establezca verify_cb en una devolución de llamada adecuada
     * no NULL. */
    /*
     * A continuación, elegimos fallar el handshake cuando falla la verificación
     * del par. Alternativamente, use el modo de verificación permisivo
     * SSL_VERIFY_NONE, complete el handshake, verifique el estado de
     * verificación y, si no se verifica, desconéctese de forma
     * segura en la capa de aplicación, especialmente si el protocolo de
     * aplicación admite la notificación al servidor de que la autenticación
     * falló.
     */
    SSL_set_verify(ssl, SSL_VERIFY_PEER, verify_cb);
}
/*
 * Cargue cualquier sesión guardada para reanudación, asegurándose de que la
 * sesión anterior aplicara los mismos requisitos de seguridad y autenticación
 * que se esperarían de una conexión nueva.
 */
/* Realice el handshake SSL_connect() y maneje los errores aquí */
if (SSL_session_reused(ssl)) {
    if (SSL_get_verify_result(ssl) == X509_V_OK) {
        /*
         * La sesión reanudada se verificó originalmente, esta conexión está
         * autenticada.
         */
    } else {
        /*
         * La sesión reanudada no se verificó originalmente, esta conexión no está
         * autenticada.
         */
    }
} else if (SSL_get_verify_result(ssl) == X509_V_OK) {
    const char *peername = SSL_get0_peername(ssl);
    EVP_PKEY *mspki = NULL;
    int depth = SSL_get0_dane_authority(ssl, NULL, &mspki);
    if (depth >= 0) {
        (void) SSL_get0_dane_tlsa(ssl, &usage, &selector, &mtype, NULL, NULL);
        printf("DANE TLSA %d %d %d ", usage, selector, mtype);
        if (SSL_get0_peer_rpk(ssl) == NULL)
            printf("%s certificado en la profundidad %d\n",
                   (mspki != NULL) ? "firmó el par" :
                   mdpth ? "coincidió con el TA" : "coincidió con el EE", mdpth);
        else
            printf(bio, "coincidió con la clave pública sin procesar del par\n");
    }
    if (peername != NULL) {
        /* Las comprobaciones de nombres estaban en el ámbito y coincidieron con peername */
        printf("Nombre del par verificado: %s\n", peername);
    }
} else {
    /*
     * No autenticado, presumiblemente todos los RR TLSA inutilizables, pero
     * posiblemente una devolución de llamada suprimió la terminación de la
     * conexión a pesar de la presencia de RR TLSA utilizables, ninguno de los
     * cuales coincidió. Haga lo que sea apropiado para conexiones no
     * autenticadas nuevas.
     */
}

NOTAS

Se espera que la mayoría de los clientes que utilizan TLS DANE estén realizando "TLS DANE oportunista" en el sentido de RFC7672 y RFC7435. Es decir, utilizarán la autenticación DANE cuando se publiquen registros TLSA validados por DNSSEC para un par dado, y de lo contrario, utilizarán TLS sin autenticar o incluso texto plano.

Dichas aplicaciones generalmente deberían tratar cualquier registro TLSA publicado por el par con usos PKIX-TA(0) y PKIX-EE(1) como "inutilizables", y no deben incluirlos entre los registros TLSA utilizados para autenticar conexiones de pares. Además, algunos registros TLSA con usos admitidos pueden ser "inutilizables" como resultado de parámetros inválidos o no admitidos.

Cuando un par tiene registros TLSA, pero ninguno es "utilizable", una aplicación oportunista debe evitar el texto plano, pero no puede autenticar al par, por lo que generalmente debe proceder con una conexión sin autenticar. Las aplicaciones oportunistas deben tener en cuenta el valor de retorno de cada llamada a SSL_dane_tlsa_add(), y si todas devuelven 0 (debido a parámetros inválidos o no admitidos), deshabilitar la autenticación del par llamando a SSL_set_verify(3) con mode igual a SSL_VERIFY_NONE.

SSL_CTX_dane_enable(3ssl)

SSL_CTX_dane_enable - habilitar o deshabilitar la funcionalidad DANE para una SSL_CTX

NOMBRE

SSL_CTX_dane_enable — habilitar o deshabilitar la funcionalidad DANE para una SSL_CTX

SINOPSIS

#include <openssl/ssl.h>

int SSL_CTX_dane_enable(SSL_CTX *ctx, int enable);

DESCRIPCIÓN

La función SSL_CTX_dane_enable habilita o deshabilita la funcionalidad DANE para la SSL_CTX especificada por ctx.

Si enable es distinto de cero, DANE se habilitará. Si enable es cero, DANE se deshabilitará.

La funcionalidad DANE es necesaria para la validación de certificados que utilizan el mecanismo DNSSEC de DANE TLSA para la autenticación. Para obtener más información, consulte RFC 6698.

VALORES DE RETORNO

La función SSL_CTX_dane_enable devuelve 1 si la operación fue exitosa, y 0 si ocurrió un error.

CONFORME A

RFC 6698

NOTAS

El valor predeterminado es que DANE está deshabilitado. DANE es una característica experimental y no está habilitada por defecto.

VER TAMBIÉN

SSL_CTX_new(3ssl), SSL_CTX_set_verify(3ssl), SSL_set_verify(3ssl)
