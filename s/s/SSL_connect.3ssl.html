NOMBRE

SSL_connect - iniciar el handshake TLS/SSL con un servidor TLS/SSL

SINOPSIS

#include <openssl/ssl.h>
int SSL_connect(SSL *ssl);

DESCRIPCIÓN

SSL_connect() inicia el handshake TLS/SSL con un servidor. El canal de comunicación ya debe haber sido configurado y asignado a ssl estableciendo un BIO subyacente. ssl NO DEBE ser NULL.

NOTAS

El comportamiento de SSL_connect() depende del BIO subyacente.

Si el BIO subyacente es bloqueante, SSL_connect() solo retornará una vez que el handshake haya finalizado o se haya producido un error.

Si el BIO subyacente es no bloqueante, SSL_connect() también retornará cuando el BIO subyacente no pudo satisfacer las necesidades de SSL_connect() para continuar el handshake, indicando el problema mediante el valor de retorno -1. En este caso, una llamada a SSL_get_error() con el valor de retorno de SSL_connect() arrojará SSL_ERROR_WANT_READ o SSL_ERROR_WANT_WRITE. El proceso que llama debe repetir la llamada después de tomar las acciones apropiadas para satisfacer las necesidades de SSL_connect(). La acción depende del BIO subyacente. Al usar un socket no bloqueante, no hay nada que hacer, pero se puede usar select() para verificar la condición requerida. Al usar un BIO de búfer, como un par de BIO, los datos deben escribirse en o recuperarse del BIO antes de poder continuar.

Muchos sistemas implementan el algoritmo de Nagle por defecto, lo que significa que almacenará en búfer los datos TCP salientes si ya se ha enviado un paquete TCP para el cual aún no se ha recibido una respuesta ACK del par. Esto puede tener impactos en el rendimiento después de un handshake TLSv1.3 exitoso o un handshake de reanudación TLSv1.2 (o inferior) exitoso, porque la última parte en comunicarse en el handshake es el cliente. Si el cliente es también el primero en enviar datos de aplicación (como es típico para muchos protocolos), entonces estos datos podrían almacenarse en búfer hasta que se reciba un ACK para el mensaje final del handshake.

La opción de socket TCP_NODELAY a menudo está disponible para deshabilitar el algoritmo de Nagle. Si una aplicación opta por deshabilitar el algoritmo de Nagle, se debe considerar volver a activarlo más tarde si es apropiado. La función de ayuda BIO_set_tcp_ndelay() se puede utilizar para activar o desactivar la opción TCP_NODELAY.

VALORES DE RETORNO

Los siguientes valores de retorno pueden ocurrir:

0
El handshake TLS/SSL no fue exitoso pero se cerró de forma controlada y de acuerdo con las especificaciones del protocolo TLS/SSL. Llame a SSL_get_error() con el valor de retorno ret para averiguar la razón.
1
El handshake TLS/SSL se completó con éxito, se ha establecido una conexión TLS/SSL.
<0
El handshake TLS/SSL no fue exitoso, porque ocurrió un error fatal a nivel de protocolo o un fallo de conexión. El cierre no fue limpio. También puede ocurrir si se necesita acción para continuar la operación para BIOs no bloqueantes. Llame a SSL_get_error() con el valor de retorno ret para averiguar la razón.
