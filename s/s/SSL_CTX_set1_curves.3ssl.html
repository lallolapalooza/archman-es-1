DESCRIPCIÓN

Para todas las funciones siguientes que establecen los grupos soportados, debe haber al menos un grupo en la lista. Varias de estas funciones identifican grupos a través de un valor NID entero único. Sin embargo, el soporte para algunos grupos puede ser añadido por proveedores externos. En este caso, no se asignará ningún NID para el grupo. Al establecer dichos grupos, las aplicaciones deben usar la forma de "lista" de estas funciones (es decir, SSL_CTX_set1_groups_list() y SSL_set1_groups_list()).

SSL_CTX_set1_groups() establece los grupos soportados para ctx en glistlen grupos en el array glist. El array consiste en todos los NID de los grupos soportados. Los grupos soportados para TLSv1.3 incluyen: NID_X9_62_prime256v1, NID_secp384r1, NID_secp521r1, NID_X25519, NID_X448, NID_brainpoolP256r1tls13, NID_brainpoolP384r1tls13, NID_brainpoolP512r1tls13, NID_ffdhe2048, NID_ffdhe3072, NID_ffdhe4096, NID_ffdhe6144 y NID_ffdhe8192. OpenSSL utilizará este array de diferentes maneras según la versión de TLS y si los grupos se usan en un cliente o un servidor.

Para un cliente TLS, los grupos se utilizan directamente en la extensión de grupos soportados. El orden de preferencia de la extensión, a ser evaluado por el servidor, está determinado por el orden de los elementos en el array.

Para un servidor TLS 1.2, los grupos determinan el grupo seleccionado. Si SSL_OP_SERVER_PREFERENCE está establecido, el orden de los elementos en el array determina el grupo seleccionado. De lo contrario, se ignora el orden y el orden del cliente determina la selección.

Para un servidor TLS 1.3, los grupos determinan el grupo seleccionado, pero la selección es más compleja. Un cliente TLS 1.3 envía tanto una lista de grupos como un subconjunto predicho de grupos. Elegir un grupo fuera del subconjunto predicho incurre en un viaje de ida y vuelta adicional. Sin embargo, en algunas situaciones, el grupo más preferido puede no ser predicho. OpenSSL considera que todos los grupos soportados en clist son comparables en seguridad y prioriza evitar viajes de ida y vuelta por encima del orden de preferencia del cliente o del servidor. Si una aplicación utiliza un proveedor externo para extender OpenSSL con, por ejemplo, un algoritmo post-cuántico, este comportamiento puede permitir a un atacante de red degradar las conexiones a un algoritmo más débil. Por lo tanto, se recomienda usar SSL_CTX_set1_groups_list() con la capacidad de especificar tuplas de grupos.

SSL_CTX_set1_groups_list() establece los grupos soportados para ctx a la cadena list. A diferencia de SSL_CTX_set1_groups(), se utilizan los nombres de los grupos, en lugar de sus NID.

Los comandos siguientes listan los grupos disponibles para TLS 1.2 y TLS 1.3, respectivamente:

$ openssl list -tls1_2 -tls-groups
$ openssl list -tls1_3 -tls-groups

Cada grupo puede ser el nombre NIST (por ejemplo, P-256), algún otro nombre comúnmente utilizado cuando sea aplicable (por ejemplo, X25519, ffdhe2048) o un nombre OID de OpenSSL (por ejemplo, prime256v1). Los nombres de grupo no distinguen entre mayúsculas y minúsculas en OpenSSL 3.5 y posteriores. Los nombres de grupo preferidos son los definidos por IANA https://www.iana.org/assignments/tls-parameters/tls-parameters.xhtml#tls-parameters-8.

La lista puede usarse para definir varias tuplas de grupos de niveles de seguridad comparables, y puede especificar qué claves compartidas deben ser enviadas por un cliente. Los elementos de lista especificados pueden ser opcionalmente ignorados, si no se implementan (listar grupos desconocidos de lo contrario resulta en error). También es posible especificar el conjunto predeterminado de grupos incorporados, y eliminar explícitamente un grupo de esa lista.

En su forma más simple, la cadena list es solo una lista separada por dos puntos de nombres de grupo, por ejemplo "P-521:P-384:P-256:X25519:ffdhe2048". El primer grupo listado también se usará para la clave compartida enviada por un cliente en un ClientHello de TLSv1.3. Para servidores, tenga en cuenta la discusión anterior. La lista debe estar en orden de preferencia, con el grupo más preferido primero.

Las tuplas de grupos de seguridad comparable se definen separándolas entre sí por un separador de tuplas "/". Las claves compartidas a enviar por un cliente se especifican anteponiendo un "*" al nombre del grupo, mientras que cualquier "*" será ignorado por un servidor. La siguiente cadena list, por ejemplo, define tres tuplas cuando se usa en el lado del servidor, y activa la generación de tres claves compartidas cuando se usa en el lado del cliente: P-521:*P-256/*P-384/*X25519:P-384:ffdhe2048.

Si un nombre de grupo va precedido del carácter "?", se ignorará si falta una implementación. Si un nombre de grupo va precedido del carácter "-", se eliminará de la lista de grupos si está presente (incluyendo no enviar una clave compartida para este grupo), de lo contrario se ignorará. El nombre de grupo pseudo "DEFAULT" se puede usar para seleccionar la lista de grupos predeterminada incorporada en OpenSSL.

Para un cliente TLS 1.3, todos los grupos en la cadena list se agregan a la extensión de grupos soportados de un "ClientHello", en el orden en que se listan, interpretando así los separadores de tuplas como separadores de grupos. El orden de preferencia de la extensión, a ser evaluado por el servidor, está determinado por el orden de los elementos en el array, véase abajo.

Si un nombre de grupo va precedido de "*", se enviará una clave compartida para este grupo. Al preceder "DEFAULT" con "*", se enviará una clave compartida para el primer grupo de la lista predeterminada de grupos incorporada en OpenSSL. Si no se usa ningún "*" en ninguna parte de la lista, se envía una única clave compartida para el grupo válido más a la izquierda. Se soporta un máximo de 4 claves compartidas. Ejemplo: "P-521:*P-256/*P-384" agregará P-521, P-256 y P-384 a la extensión de grupos soportados en un "ClientHello" y enviará claves compartidas para P-256 y P-384.

Para un servidor TLS 1.3, los grupos en la cadena list se utilizarán para determinar qué grupo se usa para el acuerdo de claves. El orden de preferencia de las tuplas de grupos está determinado por el orden de las tuplas en el array, y el orden de preferencia de los grupos dentro de una tupla de grupo está determinado por el orden de los grupos en la tupla. La preferencia del servidor puede ser forzada estableciendo SSL_OP_SERVER_PREFERENCE usando SSL_set_options (predeterminado: preferencia del cliente).

El servidor seleccionará el grupo a ser usado para un acuerdo de claves usando el siguiente algoritmo de pseudocódigo:

PARA cada tupla de grupo
    SI preferencia del cliente (= predeterminado)
        PARA cada grupo de clave compartida del cliente
            SI el grupo de clave compartida actual también es parte de la tupla de grupo actual: SH, retornar éxito
        PARA cada grupo soportado del cliente
            SI el grupo soportado actual también es parte de la tupla de grupo actual: HRR, retornar éxito
    SINO (= preferencia del servidor = con la opción SSL_OP_SERVER_PREFERENCE establecida)
        PARA cada grupo en la tupla actual
            SI el grupo actual también es parte de los grupos de clave compartida del cliente: SH, retornar éxito
        PARA cada grupo en la tupla actual
            SI el grupo actual también es parte de los grupos soportados del cliente: HRR, retornar éxito
retornar fallo
con : SH:  Server hello con el grupo actual
       HRR: Server retry request con el grupo actual

DESCRIPCIÓN

Estas funciones manejan la configuración y obtención de los grupos de intercambio de claves criptográficas soportados. En TLSv1.3, la lista de grupos disponibles para un protocolo está definida por la extensión Supported Groups en el ClientHello y ServerHello. Si no se encuentra un grupo mutuamente soportado, la conexión se cae. Para versiones anteriores a TLSv1.3, esto se manejaba mediante Supported Elliptic Curves. Estas funciones manejan ambos conceptos.

Una lista de grupos puede ser especificada como una lista de NIDs enteros en el array groups, o como una cadena de texto en str. El formato de cadena es una lista separada por dos puntos de nombres de grupos, por ejemplo, "P-256:P-384:X25519". Consulte la lista de nombres de grupos disponibles en ssl(7).

Los nombres de grupo pueden ser precedidos por un asterisco *. Esto indica que el grupo debe ser seleccionado preferentemente. Sin un asterisco, el grupo será seleccionado solo si el cliente no proporciona ninguna preferencia o si el par clave/grupo no está disponible. Los grupos son preferidos en el orden en que aparecen en la lista. Si un grupo está marcado con un asterisco, se le da prioridad sobre todos los grupos que no lo estén. Si varios grupos están marcados con un asterisco, se seleccionará el primero de ellos. Si ningún grupo está marcado con un asterisco, se seleccionará el primero de la lista que el cliente soporte y para el cual el cliente haya enviado una clave compartida.

Si el servidor no encuentra un grupo en la lista del cliente que coincida con un grupo en su propia lista configurada, o si se solicita una preferencia no encontrada y un grupo compartido no está disponible, se desencadena un Hello Retry Request (HRR), solicitando al cliente que envíe un nuevo mensaje Hello con un keyshare más preferido. Ver ejemplos a continuación.

A un nombre de grupo se le puede anteponer opcionalmente cualquiera de *, ? o -, en cualquier orden, con la excepción de que solo * puede preceder a DEFAULT. Los caracteres separadores : y / solo están permitidos dentro de la lista y no al principio o al final.

SSL_set1_groups() y SSL_set1_groups_list() son similares excepto que establecen los grupos soportados para la estructura SSL ssl.

SSL_get1_groups() devuelve el conjunto de grupos soportados enviados por un cliente en la extensión de grupos soportados. Devuelve el número total de grupos soportados. El parámetro groups puede ser NULL para simplemente devolver el número de grupos para fines de asignación de memoria. El array groups tiene la forma de un conjunto de NIDs de grupo en orden de preferencia. Puede devolver cero si el cliente no envió una extensión de grupos soportados. Si un NID de grupo soportado es desconocido, entonces el valor se establece en el OR a nivel de bits de TLSEXT_nid_unknown (0x1000000) y el id del grupo.

SSL_get0_iana_groups() recupera la lista de grupos enviada por el cliente en la extensión supported_groups. El array de bytes *out se rellena con la representación en orden de byte de host de los identificadores de grupo uint16_t, según lo asignado por IANA. La lista de grupos se devuelve en el mismo orden en que se recibió en el ClientHello. El valor de retorno es el número de grupos, no el número de bytes escritos.

SSL_get_shared_group() devuelve el NID del grupo compartido n para un SSL ssl del lado del servidor. Si n es -1, se devuelve el número total de grupos compartidos, que puede ser cero. Aparte de fines de diagnóstico, la mayoría de las aplicaciones solo estarán interesadas en el primer grupo compartido, por lo que n normalmente se establece en cero. Si el valor n está fuera de rango, se devuelve NID_undef. Si el NID del grupo compartido es desconocido, el valor se establece en el OR a nivel de bits de TLSEXT_nid_unknown (0x1000000) y el id del grupo.

SSL_get_negotiated_group() devuelve el NID del grupo negociado utilizado para el proceso de intercambio de claves de handshake. Para conexiones TLSv1.3, esto generalmente refleja el estado de la conexión actual, aunque en el caso de reanudación solo de PSK, el valor devuelto será de una conexión anterior. Para versiones anteriores de TLS, cuando se ha reanudado una sesión, siempre refleja el grupo utilizado para el intercambio de claves durante el handshake inicial (de lo contrario, es de la conexión actual, no de reanudación). Esto puede ser llamado por el cliente o el servidor. Si el NID del grupo compartido es desconocido, el valor se establece en el OR a nivel de bits de TLSEXT_nid_unknown (0x1000000) y el id del grupo. Ver también SSL_get0_group_name(3) que devuelve directamente el nombre del grupo negociado y es generalmente preferido sobre SSL_get_negotiated_group().

SSL_CTX_get0_implemented_groups() rellena una pila con los nombres de los grupos TLS que son compatibles con la versión TLS del argumento ctx. Los nombres devueltos son referencias a constantes internas y no deben ser modificados ni liberados. Cuando all es distinto de cero, la lista devuelta incluye no solo los nombres preferidos de IANA de los grupos, sino también cualquier alias asociado. Si el SSL_CTX es flexible en versión, los grupos serán aquellos compatibles con las versiones mínimas y máximas de protocolo configuradas. La pila names debe ser asignada por el llamador y estar vacía; los nombres de grupo coincidentes se añaden a la pila proporcionada. Las opciones -tls-groups y -all-tls-groups del comando openssl list muestran estas listas para TLS 1.2 o TLS 1.3 (por defecto).

Todas estas funciones se implementan como macros.

Las funciones de curva son sinónimos de las funciones de grupo con el mismo nombre y son idénticas en todos los aspectos. Existen porque, antes de TLS1.3, solo existía el concepto de curvas soportadas. En TLS1.3 esto fue renombrado a grupos soportados, y se amplió para incluir grupos Diffie Hellman. Se deben preferir las funciones de grupo.

NOTAS

Si una aplicación desea hacer uso de varias de estas funciones con fines de configuración, ya sea en una línea de comandos o en un archivo, debe considerar el uso de la interfaz SSL_CONF en lugar de analizar manualmente las opciones.

VALORES DE RETORNO

SSL_CTX_set1_groups(), SSL_CTX_set1_groups_list(), SSL_set1_groups(), SSL_set1_groups_list() y SSL_CTX_get0_implemented_groups() devuelven 1 en caso de éxito y 0 en caso de fallo.

SSL_get1_groups() devuelve el número de grupos, que puede ser cero.

SSL_get0_iana_groups() devuelve el número de grupos (uint16_t), que puede ser cero.

SSL_get_shared_group() devuelve el NID del grupo compartido n o NID_undef si no hay un grupo compartido n; o el número total de grupos compartidos si n es -1.

Cuando se llama en un SSL de cliente ssl, SSL_get_shared_group() no tiene significado y devuelve -1.

SSL_get_negotiated_group() devuelve el NID del grupo negociado utilizado para el intercambio de claves, o NID_undef si no hubo un grupo negociado.

EJEMPLOS

Supongamos que la lista del servidor es "P-521:P-256/P-384/X25519:ffdhe2048" y la lista del cliente es "P-521:*P-384" al conectarse a dicho servidor, lo que significa que el cliente soporta "P-521" pero no envía una clave compartida para este grupo al servidor, y el cliente soporta "P-384" incluyendo una clave compartida para este grupo. Con preferencia tanto del servidor como del cliente, se activará un HRR para "P-521" a pesar de la disponibilidad de una clave compartida para P-384, que se superpone con una tupla de menor prioridad del lado del servidor.

Como ejemplo aparte, considere una lista de servidor "A:B/C:D/E:F". Listados en orden de mayor a menor preferencia, se crean 3 tuplas de grupo: "A:B", "C:D" y "E:F". Aquí hay algunos ejemplos de una lista de cliente donde establecer la preferencia del servidor/cliente no cambiará el resultado:

- "A:D:*F": Ambos prefieren "A", pero el servidor no recibió una clave compartida para la tupla más preferida en la que hay al menos un grupo soportado por ambos. Por lo tanto, se activa un HRR para "A".

- "B:*C": Ambos prefieren "B" de la primera tupla de grupo "A:B", por lo que se activa un HRR para "B".

- "C:*F": Ambos prefieren "C" de la segunda tupla de grupo "C:D", por lo que se activa un HRR para "C".

- "C:*D": Aunque ambos prefieren "C" sobre "D", el servidor aceptará la clave compartida para "D". Dentro de una tupla, las claves compartidas existentes prevalecen sobre el orden de preferencia.

- "*C:*D": El servidor acepta la clave compartida de "C".

- "F": Aunque no está precedido por un "*", el cliente enviará una clave compartida para "F". El servidor aceptará entonces la clave compartida para "F".

- "*E:C:A": El servidor prefiere "A" de la tupla de grupo "A:B", por lo que se activa un HRR para "A".

- "*E:B:*A": El servidor utiliza la clave compartida para "A".

Aquí hay algunos ejemplos donde establecer la preferencia del servidor/cliente cambiará el resultado:

- "*D:*C"
- Preferencia del cliente: El servidor utiliza la clave compartida para "D".
- Preferencia del servidor: El servidor utiliza la clave compartida para "C".

- "B:A:*C"
- Preferencia del cliente: El servidor activa un HRR para "B". Para el servidor, "A" y "B" se consideran comparables en seguridad. Pero debido a que el cliente prefiere "B", el servidor activará un HRR para "B".
- Preferencia del servidor: El servidor activa un HRR para "A".

HISTORIA

Las funciones de curva se añadieron en OpenSSL 1.0.2. Las funciones equivalentes de grupo se añadieron en OpenSSL 1.1.1. La función SSL_get_negotiated_group() se añadió en OpenSSL 3.0.0.

El soporte para ignorar grupos desconocidos en SSL_CTX_set1_groups_list() y SSL_set1_groups_list() se añadió en OpenSSL 3.3.

El soporte para ML-KEM se añadió en OpenSSL 3.5.

OpenSSL 3.5 también introduce soporte para tres grupos de intercambio de claves TLS ECDH PQ híbridos: X25519MLKEM768, SecP256r1MLKEM768 y SecP384r1MLKEM1024. Ofrecen un rendimiento de CPU comparable al grupo ECDH asociado, aunque a costa de mensajes de intercambio de claves significativamente más grandes. El tercer grupo, SecP384r1MLKEM1024, es sustancialmente más intensivo en CPU, en gran parte como resultado del alto costo de CPU de ECDH para el grupo subyacente P-384. Además, sus mensajes de intercambio de claves de casi 1700 bytes son más grandes que los aproximadamente 1200 bytes de los dos primeros grupos.

A partir de OpenSSL 3.5, los nombres de los grupos de intercambio de claves no distinguen entre mayúsculas y minúsculas.

SSL_CTX_get0_implemented_groups se implementó por primera vez en OpenSSL 3.5.

Versiones anteriores de este documento describían la lista como un orden de preferencia. Sin embargo, el comportamiento de OpenSSL como servidor TLS 1.3 es considerar todos los grupos soportados como comparables en seguridad.
