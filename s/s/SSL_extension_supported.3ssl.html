DESCRIPCIÓN

SSL_CTX_add_custom_ext() añade una extensión personalizada para un cliente o servidor TLS/DTLS para todas las versiones de protocolo soportadas con el tipo de extensión ext_type y los callbacks add_cb, free_cb y parse_cb (ver la sección "CALLBACKS DE EXTENSIÓN" abajo). El valor context determina en qué mensajes y bajo qué condiciones se añadirá/analizará la extensión (ver la sección "CONTEXTOS DE EXTENSIÓN" abajo).

SSL_CTX_add_client_custom_ext() añade una extensión personalizada para un cliente TLS/DTLS con el tipo de extensión ext_type y los callbacks add_cb, free_cb y parse_cb. Esta función es similar a SSL_CTX_add_custom_ext() excepto que solo se aplica a clientes, usa el estilo antiguo de callbacks, e implícitamente establece el valor context a:

SSL_EXT_TLS1_2_AND_BELOW_ONLY | SSL_EXT_CLIENT_HELLO
| SSL_EXT_TLS1_2_SERVER_HELLO | SSL_EXT_IGNORE_ON_RESUMPTION

SSL_CTX_add_server_custom_ext() añade una extensión personalizada para un servidor TLS/DTLS con el tipo de extensión ext_type y los callbacks add_cb, free_cb y parse_cb. Esta función es similar a SSL_CTX_add_custom_ext() excepto que solo se aplica a servidores, usa el estilo antiguo de callbacks, e implícitamente establece el valor context al mismo que para SSL_CTX_add_client_custom_ext() arriba.

El parámetro ext_type corresponde al campo extension_type de RFC5246 et al. No es un NID. En todos los casos, el tipo de extensión no debe ser manejado internamente por OpenSSL o se producirá un error.

SSL_extension_supported() devuelve 1 si la extensión ext_type es manejada internamente por OpenSSL y 0 en caso contrario.

CALLBACKS DE EXTENSIÓN

El callback add_cb se llama para enviar datos de extensión personalizados que se incluirán en varios mensajes TLS. El parámetro ext_type se establece al tipo de extensión que se añadirá y add_arg al valor establecido cuando se añadió el manejador de extensión. Al usar los callbacks del nuevo estilo, el parámetro context indicará qué mensaje se está construyendo actualmente, por ejemplo, para el ClientHello se establecerá en SSL_EXT_CLIENT_HELLO.

Si la aplicación desea incluir la extensión ext_type, debe establecer *out a los datos de la extensión, establecer *outlen a la longitud de los datos de la extensión y devolver 1.

Si el add_cb no desea incluir la extensión, debe devolver 0.

Si add_cb devuelve -1, se produce un error fatal de handshake utilizando la alerta TLS especificada en *al.

Al construir el ClientHello, si add_cb se establece a NULL, se añade una extensión de longitud cero para ext_type. Para todos los demás mensajes, si add_cb se establece a NULL, no se añade ninguna extensión.

Al construir un mensaje Certificate, el callback se llamará para cada certificado en el mensaje. El parámetro x indicará el certificado actual y el parámetro chainidx indicará la posición del certificado en el mensaje. El primer certificado es siempre el certificado de la entidad final y tiene un valor chainidx de 0. Los certificados están en el orden en que se recibieron en el mensaje Certificate.

Para todos los mensajes excepto ServerHello y EncryptedExtensions, cada add_cb registrado se llama siempre para ver si la aplicación desea añadir una extensión (siempre que se cumplan todos los requisitos del context especificado).

Para los mensajes ServerHello y EncryptedExtension, cada add_cb registrado se llama una vez si y solo si se cumplen los requisitos del context especificado y la extensión correspondiente se recibió en el ClientHello. Es decir, si no se recibió ninguna extensión correspondiente en el ClientHello, entonces add_cb no se llamará.

Si se añade una extensión (es decir, add_cb devuelve 1), se llama a free_cb (si está configurado) con el valor de out establecido por el callback de adición. Se puede utilizar para liberar cualquier dato de extensión dinámico establecido por add_cb. Dado que out es constante (para permitir el uso de datos constantes en add_cb), las aplicaciones pueden necesitar eliminar la constancia para liberar los datos.

El callback parse_cb recibe datos para extensiones TLS. El callback solo se llama si la extensión está presente y es relevante para el contexto (ver "CONTEXTOS DE EXTENSIÓN" abajo).

Los datos de la extensión consisten en inlen bytes en el búfer in para la extensión ext_type.

Si el mensaje que se está analizando es un mensaje Certificate compatible con TLSv1.3, entonces parse_cb se llamará para cada certificado contenido en el mensaje. El parámetro x indicará el certificado actual y el parámetro chainidx indicará la posición del certificado en el mensaje. El primer certificado es siempre el certificado de la entidad final y tiene un valor chainidx de 0.

Si el parse_cb considera aceptables los datos de la extensión, debe devolver 1. Si devuelve 0 o un valor negativo, se produce un error fatal de handshake utilizando la alerta TLS especificada en *al.

El búfer in es un búfer interno temporal que no será válido después de que el callback devuelva.

NAME

DESCRIPTION

These functions provide an API for handling custom TLS extensions. Custom extensions allow applications to extend the TLS protocol with their own data. They are identified by a 16-bit extension type code. OpenSSL reserves extension types in the range 0 to 0xFFFF. Extension types 0x0000 to 0x00FF are reserved for internal use. Other extension types can be defined by the application. The application must ensure that the chosen extension type is not already in use.

SSL_extension_supported() checks if the extension type ext_type is handled internally by OpenSSL. Note that OpenSSL may not necessarily support the extension in all contexts or versions.

SSL_CTX_add_custom_ext() registers a custom extension with the given SSL_CTX. The ext_type is the 16-bit identifier for the extension. The flags specify the contexts in which the extension is allowed. The callbacks add_cb, parse_cb, and free_cb are used to handle the extension. The arg is a generic pointer that will be passed to the callbacks.

The add_cb callback is called when the extension needs to be added to an outgoing message (e.g., ClientHello, CertificateRequest). It should write the extension data into the buffer pointed to by out, with a maximum length of outlen. It should return the number of bytes written. The input and inlen parameters provide any input data that might be relevant (e.g., data from a previous session).

The parse_cb callback is called when an extension is received in an incoming message. It should parse the extension data pointed to by input with length inlen. It should return 1 on success and 0 on failure.

The free_cb callback is called to free any memory associated with the extension's argument.

SSL_CTX_add_client_custom_ext() is a convenience function that is equivalent to calling SSL_CTX_add_custom_ext() with the appropriate flags for client extensions.

SSL_CTX_add_server_custom_ext() is a convenience function that is equivalent to calling SSL_CTX_add_custom_ext() with the appropriate flags for server extensions.

SSL_add_client_custom_ext() adds a custom extension to the current SSL connection's ClientHello message. This function is intended to be called by an application during the handshake. The parameters are similar to the add_cb callback.

SSL_add_server_custom_ext() adds a custom extension to the current SSL connection's ServerHello message. This function is intended to be called by an application during the handshake. The parameters are similar to the add_cb callback.

EXTENSION CALLBACKS

The callbacks are defined as follows:

add_cb
Used to add an extension to an outgoing message. It is called with the SSL object, the extension type, an output buffer out with maximum size outlen, any relevant input data input with size inlen, and the user-provided argument arg. It should return the number of bytes written to out, or -1 on error.
parse_cb
Used to parse an extension received in an incoming message. It is called with the SSL object, the extension type, the extension data input with size inlen, and the user-provided argument arg. It should return 1 on success and 0 on failure (which will result in a fatal alert).
free_cb
Used to free any memory allocated by the callbacks for the extension's argument. It is called with the SSL object, the extension type, and the user-provided argument arg.

EXTENSION CONTEXTS

The flags parameter is a bitmask that specifies the contexts in which the extension is allowed. The following flags are defined:

SSL_EXT_TLS_ONLY
The extension is only allowed in TLS
SSL_EXT_DTLS_ONLY
The extension is only allowed in DTLS
SSL_EXT_TLS_IMPLEMENTATION_ONLY
The extension is allowed in DTLS, but there is only a TLS implementation available (so it is ignored in DTLS).
SSL_EXT_SSL3_ALLOWED
Extensions are not typically defined for SSLv3. Setting this value will allow the extension in SSLv3. Applications will not typically need to use this.
SSL_EXT_TLS1_2_AND_BELOW_ONLY
The extension is only defined for TLSv1.2/DTLSv1.2 and below. Servers will ignore this extension if it is present in the ClientHello and TLSv1.3 is negotiated.
SSL_EXT_TLS1_3_ONLY
The extension is only defined for TLS1.3 and above. Servers will ignore this extension if it is present in the ClientHello and TLSv1.2 or below is negotiated.
SSL_EXT_IGNORE_ON_RESUMPTION
The extension will be ignored during parsing if a previous session is being successfully resumed.
SSL_EXT_CLIENT_HELLO
The extension may be present in the ClientHello message.
SSL_EXT_TLS1_2_SERVER_HELLO
The extension may be present in a TLSv1.2 or below compatible ServerHello message.
SSL_EXT_TLS1_3_SERVER_HELLO
The extension may be present in a TLSv1.3 compatible ServerHello message.
SSL_EXT_TLS1_3_ENCRYPTED_EXTENSIONS
The extension may be present in an EncryptedExtensions message.
SSL_EXT_TLS1_3_HELLO_RETRY_REQUEST
The extension may be present in a HelloRetryRequest message.
SSL_EXT_TLS1_3_CERTIFICATE
The extension may be present in a TLSv1.3 compatible Certificate message.
SSL_EXT_TLS1_3_NEW_SESSION_TICKET
The extension may be present in a TLSv1.3 compatible NewSessionTicket message.
SSL_EXT_TLS1_3_CERTIFICATE_REQUEST
The extension may be present in a TLSv1.3 compatible CertificateRequest message.

The context must include at least one message value (otherwise the extension will never be used).

NOTES

The add_arg and parse_arg parameters can be set to arbitrary values which will be passed to the corresponding callbacks. They can, for example, be used to store the extension data received in a convenient structure or pass the extension data to be added or freed when adding extensions.

If the same custom extension type is received multiple times a fatal decode_error alert is sent and the handshake aborts. If a custom extension is received in a ServerHello/EncryptedExtensions message which was not sent in the ClientHello a fatal unsupported_extension alert is sent and the handshake is aborted. The ServerHello/EncryptedExtensions add_cb callback is only called if the corresponding extension was received in the ClientHello. This is compliant with the TLS specifications. This behaviour ensures that each callback is called at most once and that an application can never send unsolicited extensions.

RETURN VALUES

SSL_CTX_add_custom_ext(), SSL_CTX_add_client_custom_ext() and SSL_CTX_add_server_custom_ext() return 1 for success and 0 for failure. A failure can occur if an attempt is made to add the same ext_type more than once, if an attempt is made to use an extension type handled internally by OpenSSL or if an internal error occurs (for example a memory allocation failure).

SSL_extension_supported() returns 1 if the extension ext_type is handled internally by OpenSSL and 0 otherwise.
