SSL_read_early_data(3ssl)

Paquete: openssl

Licencias: Apache-2.0

SSL_READ_EARLY_DATA(3ssl) OpenSSL SSL_READ_EARLY_DATA(3ssl)

NOMBRE

SSL_set_max_early_data, SSL_CTX_set_max_early_data, SSL_get_max_early_data, SSL_CTX_get_max_early_data, SSL_set_recv_max_early_data, SSL_CTX_set_recv_max_early_data, SSL_get_recv_max_early_data, SSL_CTX_get_recv_max_early_data, SSL_SESSION_get_max_early_data, SSL_SESSION_set_max_early_data, SSL_write_early_data, SSL_read_early_data, SSL_get_early_data_status, SSL_allow_early_data_cb_fn, SSL_CTX_set_allow_early_data_cb, SSL_set_allow_early_data_cb - funciones para enviar y recibir datos tempranos

#include <openssl/ssl.h>
int SSL_CTX_set_max_early_data(SSL_CTX *ctx, uint32_t max_early_data);

uint32_t SSL_CTX_get_recv_max_early_data(const SSL_CTX *ctx);
int SSL_set_recv_max_early_data(SSL *s, uint32_t recv_max_early_data);
uint32_t SSL_get_recv_max_early_data(const SSL *s);
uint32_t SSL_SESSION_get_max_early_data(const SSL_SESSION *s);
int SSL_SESSION_set_max_early_data(SSL_SESSION *s, uint32_t max_early_data);
int SSL_write_early_data(SSL *s, const void *buf, size_t num, size_t *written);
int SSL_read_early_data(SSL *s, void *buf, size_t num, size_t *readbytes);

DESCRIPCIÓN

Estas funciones se utilizan para enviar y recibir datos tempranos donde se ha negociado TLSv1.3. El cliente puede enviar datos tempranos inmediatamente después de su ClientHello inicial sin tener que esperar a que el servidor complete el apretón de manos. Los datos tempranos se pueden enviar si previamente se estableció una sesión con el servidor o al establecer una nueva sesión utilizando una PSK fuera de banda, y solo cuando se sabe que el servidor lo admite. Además, estas funciones se pueden utilizar para enviar datos del servidor al cliente cuando el cliente aún no ha completado la etapa de autenticación del apretón de manos.

Los datos tempranos tienen propiedades de seguridad más débiles que otros datos enviados a través de una conexión SSL/TLS. En particular, los datos no tienen secreto directo (forward secrecy). También hay consideraciones adicionales sobre los ataques de repetición (ver "PROTECCIÓN CONTRA REPETICIÓN" a continuación). Por estas razones, se debe tener extremo cuidado al usar datos tempranos. Para obtener detalles específicos, consulte la especificación de TLS 1.3.

Cuando un servidor recibe datos tempranos, puede optar por responder inmediatamente enviando datos de aplicación de vuelta al cliente. Los datos enviados por el servidor en esta etapa se hacen antes de que se complete el apretón de manos completo. Específicamente, los mensajes de autenticación del cliente aún no se han recibido, es decir, el cliente no está autenticado en este punto y se debe tener cuidado al usar esta capacidad.

Un servidor o cliente puede determinar si el apretón de manos completo se ha completado o no llamando a SSL_is_init_finished(3).

En el lado del cliente, la función SSL_SESSION_get_max_early_data() se puede utilizar para determinar si una sesión establecida con un servidor se puede usar para enviar datos tempranos. Si la sesión no se puede usar, esta función devolverá 0. De lo contrario, devolverá el número máximo de bytes de datos tempranos que se pueden enviar.

La función SSL_SESSION_set_max_early_data() establece el número máximo de bytes de datos tempranos que se pueden enviar para una sesión. Esto se usaría típicamente al crear un archivo de sesión PSK (ver SSL_CTX_set_psk_use_session_callback(3)). Si se utiliza una PSK basada en tickets, esto se establece automáticamente al valor proporcionado por el servidor.

Un cliente utiliza la función SSL_write_early_data() para enviar datos tempranos. Esta función es similar a la función SSL_write_ex(3), pero con las siguientes diferencias. Consulte SSL_write_ex(3) para obtener información sobre cómo escribir bytes en la conexión subyacente y cómo manejar cualquier error que pueda surgir. Esta página describe las diferencias entre SSL_write_early_data() y SSL_write_ex(3).

Cuando es llamada por un cliente, SSL_write_early_data() debe ser la primera función de E/S llamada en una nueva conexión, es decir, debe ocurrir antes de cualquier llamada a SSL_write_ex(3), SSL_read_ex(3), SSL_connect(3), SSL_do_handshake(3) u otras funciones similares. Puede ser llamada múltiples veces para transmitir datos al servidor, pero el número total de bytes escritos no debe exceder el valor devuelto por SSL_SESSION_get_max_early_data(). Una vez que la llamada inicial SSL_write_early_data() se ha completado exitosamente, el cliente puede intercalar llamadas a SSL_read_ex(3) y SSL_read(3) con llamadas a SSL_write_early_data() según sea necesario.

Si SSL_write_early_data() falla, debe llamar a SSL_get_error(3) para determinar el curso de acción correcto, como para SSL_write_ex(3).

Cuando el cliente ya no desea enviar más datos tempranos, debe completar el apretón de manos llamando a una función como SSL_connect(3) o SSL_do_handshake(3). Alternativamente, puede llamar a una función de escritura estándar como SSL_write_ex(3), que completará la conexión de forma transparente y escribirá los datos solicitados.

Un servidor puede optar por ignorar los datos tempranos que se le han enviado. Una vez que la conexión se ha completado, puede determinar si el servidor aceptó o rechazó los datos tempranos llamando a SSL_get_early_data_status(). Esto devolverá SSL_EARLY_DATA_ACCEPTED si los datos fueron aceptados, SSL_EARLY_DATA_REJECTED si fueron rechazados o SSL_EARLY_DATA_NOT_SENT si no se enviaron datos tempranos. Esta función puede ser llamada por el cliente o el servidor.

Un servidor utiliza la función SSL_read_early_data() para recibir datos tempranos en una conexión para la cual los datos tempranos se han habilitado usando SSL_CTX_set_max_early_data() o SSL_set_max_early_data(). Al igual que con SSL_write_early_data(), esta debe ser la primera función de E/S llamada en una conexión, es decir, debe ocurrir antes de cualquier llamada a SSL_write_ex(3), SSL_read_ex(3), SSL_accept(3), SSL_do_handshake(3), u otras funciones similares.

SSL_read_early_data() es similar a SSL_read_ex(3) con las siguientes diferencias. Consulte SSL_read_ex(3) para obtener detalles completos.

SSL_read_early_data() puede devolver 3 valores posibles:

SSL_READ_EARLY_DATA_ERROR
Esto indica que ocurrió un error de E/S o algún otro error. Esto debe tratarse de la misma manera que un valor de retorno 0 de SSL_read_ex(3).
SSL_READ_EARLY_DATA_SUCCESS
Esto indica que los datos tempranos se leyeron correctamente. Esto debe tratarse de la misma manera que un valor de retorno 1 de SSL_read_ex(3). Debe continuar llamando a SSL_read_early_data() para leer más datos.
SSL_READ_EARLY_DATA_FINISH
Esto indica que no se pueden leer más datos tempranos. Puede ser devuelto en la primera llamada a SSL_read_early_data() si el cliente no ha enviado datos tempranos, o si los datos tempranos fueron rechazados.

Una vez que la llamada inicial SSL_read_early_data() se ha completado correctamente (es decir, ha devuelto SSL_READ_EARLY_DATA_SUCCESS o SSL_READ_EARLY_DATA_FINISH), el servidor puede optar por escribir datos inmediatamente al cliente no autenticado usando SSL_write_early_data(). Si SSL_read_early_data() devolvió SSL_READ_EARLY_DATA_FINISH, en algunas situaciones (por ejemplo, si el cliente solo admite TLSv1.2) el apretón de manos ya se puede haber completado y las llamadas a SSL_write_early_data() no están permitidas. Llame a para determinar si el handshake ha finalizado o no. Si el handshake todavía está en progreso, el servidor puede intercalar llamadas a SSL_write_early_data() con llamadas a SSL_read_early_data() según sea necesario.

Los servidores no deben llamar a SSL_read_ex(3), SSL_read(3), SSL_write_ex(3) o SSL_write(3) hasta que SSL_read_early_data() haya devuelto SSL_READ_EARLY_DATA_FINISH. Una vez que lo haya hecho, la conexión con el cliente todavía debe ser completada. Complete la conexión llamando a una función como SSL_accept(3) o SSL_do_handshake(3). Alternativamente, puede llamar a una función de lectura estándar como SSL_read_ex(3), que completará la conexión de forma transparente y leerá los datos solicitados. Tenga en cuenta que es un error intentar completar la conexión antes de que SSL_read_early_data() haya devuelto SSL_READ_EARLY_DATA_FINISH.

Solo los servidores pueden llamar a SSL_read_early_data().

Las llamadas a SSL_read_early_data() pueden, en ciertas circunstancias, completar la conexión inmediatamente sin necesidad de llamar a una función como SSL_accept(3). Esto puede ocurrir si el cliente está utilizando una versión de protocolo inferior a TLSv1.3. Las aplicaciones pueden verificar esto llamando a SSL_is_init_finished(3). Alternativamente, las aplicaciones pueden optar por llamar a SSL_accept(3) de todos modos. Dicha llamada se completará con éxito inmediatamente sin tomar ninguna otra acción.

Cuando se crea una sesión entre un servidor y un cliente, el servidor especificará la cantidad máxima de datos tempranos que aceptará en cualquier intento de conexión futuro. Por defecto, el servidor no acepta datos tempranos; un servidor puede indicar soporte para datos tempranos llamando a SSL_CTX_set_max_early_data() o SSL_set_max_early_data() para establecerlo para todo el SSL_CTX o para un objeto SSL individual, respectivamente. El parámetro max_early_data especifica la cantidad máxima de datos tempranos en bytes que se permite enviar en una sola conexión. De manera similar, las funciones SSL_CTX_get_max_early_data() y SSL_get_max_early_data() se pueden usar para obtener la configuración actual máxima de datos tempranos para los objetos SSL_CTX y SSL, respectivamente. En general, una aplicación de servidor utilizará tanto SSL_read_early_data() como SSL_CTX_set_max_early_data() (o SSL_set_max_early_data()), o ninguna de ellas, ya que no hay ningún beneficio práctico en usar solo una de ellas. Si la configuración máxima de datos tempranos para un servidor es distinta de cero, la protección contra repeticiones se habilita automáticamente (ver "PROTECCIÓN CONTRA REPETICIONES" a continuación).

Si el servidor rechaza los datos tempranos enviados por un cliente, saltará los datos enviados. La cantidad máxima de datos tempranos recibidos que se omiten está controlada por la configuración de recv_max_early_data. Si un cliente envía más que esto, la conexión se abortará. Este valor se puede establecer llamando a SSL_CTX_set_recv_max_early_data() o SSL_set_recv_max_early_data(). El valor actual para esta configuración se puede obtener llamando a SSL_CTX_get_recv_max_early_data() o SSL_get_recv_max_early_data(). El valor predeterminado para esta configuración es 16.384 bytes.

El valor de recv_max_early_data también tiene un impacto en los datos tempranos que se aceptan. La cantidad de datos que se aceptan siempre será la menor entre max_early_data para la sesión y la configuración recv_max_early_data para el servidor. Si un cliente envía más datos que esto, la conexión se abortará.

El valor configurado para max_early_data en un servidor puede cambiar con el tiempo según sea necesario. Sin embargo, los clientes pueden tener tickets que contengan el valor max_early_data configurado previamente. recv_max_early_data siempre debe ser igual o superior a cualquier valor max_early_data configurado recientemente para evitar conexiones abortadas. recv_max_early_data nunca debe establecerse por debajo del valor max_early_data actualmente configurado.

Algunas aplicaciones de servidor pueden desear tener más control sobre si se aceptan o no los datos tempranos, por ejemplo, para mitigar riesgos de repetición (ver "PROTECCIÓN CONTRA REPETICIONES" a continuación) o para rechazar early_data cuando el servidor está muy cargado. Las funciones SSL_CTX_set_allow_early_data_cb() y SSL_set_allow_early_data_cb() establecen una función de devolución de llamada que se llama en un punto del handshake inmediatamente antes de que se tome la decisión de aceptar o rechazar los datos tempranos. La función de devolución de llamada recibe un puntero al argumento de datos del usuario que se proporcionó cuando se estableció la función de devolución de llamada por primera vez. Devolver 1 desde la función de devolución de llamada permitirá los datos tempranos y devolver 0 los rechazará. Tenga en cuenta que la biblioteca OpenSSL puede rechazar datos tempranos por otras razones, en cuyo caso esta función de devolución de llamada no se llamará. En particular, la función integrada de protección contra repeticiones seguirá utilizándose incluso si hay una función de devolución de llamada presente, a menos que se haya desactivado explícitamente utilizando la opción SSL_OP_NO_ANTI_REPLAY. Ver "PROTECCIÓN CONTRA REPETICIONES" a continuación.

Estas funciones actualmente no se pueden usar con objetos QUIC SSL. SSL_set_max_early_data(), SSL_set_recv_max_early_data(), SSL_write_early_data(), SSL_read_early_data(), SSL_get_early_data_status() y SSL_set_allow_early_data_cb() fallan si se llaman en un objeto QUIC SSL.

NOTAS

El propósito principal de los datos tempranos es permitir que un cliente comience a enviar datos al servidor antes de que se haya producido un ciclo completo de tráfico de red. Los desarrolladores de aplicaciones deben asegurarse de considerar la optimización del socket TCP subyacente para obtener una solución de alto rendimiento. Por ejemplo, el algoritmo de Nagle es utilizado comúnmente por los sistemas operativos en un intento de evitar muchos paquetes TCP pequeños. En muchos escenarios, esto es beneficioso para el rendimiento, pero no funciona bien con la solución de datos tempranos implementada en OpenSSL. En el algoritmo de Nagle, el sistema operativo almacenará en búfer los datos TCP salientes si ya se ha enviado un paquete TCP del cual aún no hemos recibido un ACK del par. Los datos almacenados en búfer solo se transmitirán si se acumula suficiente datos para llenar un paquete TCP completo, o si se recibe el ACK del par. El ClientHello inicial se enviará en el primer paquete TCP junto con cualquier dato de la primera llamada a SSL_write_early_data(). Si la cantidad de datos escritos excede el tamaño de un solo paquete TCP, o si hay más llamadas a SSL_write_early_data(), esos datos adicionales se enviarán en paquetes TCP posteriores que serán almacenados en búfer por el sistema operativo y no se enviarán hasta que se reciba un ACK para el primer paquete que contiene el ClientHello. Esto significa que los datos tempranos no se envían realmente hasta que se ha producido un ciclo completo con el servidor, lo que anula el objetivo de los datos tempranos.

En muchos sistemas operativos, la opción de socket TCP_NODELAY está disponible para deshabilitar el algoritmo de Nagle. Si una aplicación opta por deshabilitar el algoritmo de Nagle, se debe considerar volver a habilitarlo después de que el handshake se complete, si es apropiado.

En raras circunstancias, puede ser posible que un cliente tenga una sesión que informe un valor máximo de datos tempranos mayor que 0, pero donde el servidor no lo admita. Por ejemplo, esto puede ocurrir si la configuración de un servidor ha sido modificada para aceptar un valor máximo de datos tempranos menor, como llamando a SSL_CTX_set_recv_max_early_data(). Otro ejemplo es si un servidor solía admitir TLSv1.3 pero luego fue degradado a TLSv1.2. Enviar datos tempranos a un servidor así provocará que la conexión se aborte. Los clientes que encuentren una conexión abortada mientras envían datos tempranos pueden querer reintentar la conexión sin enviar datos tempranos, ya que esto no ocurre automáticamente. Un cliente tendrá que establecer una nueva conexión de capa de transporte al servidor e intentar la conexión SSL/TLS nuevamente, pero sin enviar datos tempranos. Tenga en cuenta que no es aconsejable reintentar con una versión de protocolo máxima menor.

PROTECCIÓN CONTRA REPETICIONES

Cuando se utilizan datos tempranos, el protocolo TLS no proporciona garantías de seguridad de que los mismos datos tempranos no se hayan repetido en múltiples conexiones. Como mitigación para este problema, OpenSSL habilita automáticamente la protección contra repeticiones si el servidor está configurado con un valor de datos tempranos máximo distinto de cero. Con la protección contra repeticiones habilitada, las sesiones se fuerzan a ser de un solo uso. Si un cliente intenta reutilizar un ticket de sesión más de una vez, los segundo e intentos posteriores volverán a un handshake completo (y cualquier dato temprano que se haya enviado se ignorará). Tenga en cuenta que los tickets de un solo uso se aplican incluso si un cliente no envía ningún dato temprano.

El mecanismo de protección contra repeticiones se basa en la caché interna de sesiones del servidor de OpenSSL (ver SSL_CTX_set_session_cache_mode(3)). Cuando se está utilizando la protección contra repeticiones, el servidor operará como si se hubiera seleccionado la opción SSL_OP_NO_TICKET (ver SSL_CTX_set_options(3)). Las sesiones se agregarán a la caché cada vez que se emita un ticket de sesión. Cuando un cliente intenta reanudar la sesión, OpenSSL verificará su presencia en la caché interna. Si existe, se permite la reanudación y la sesión se elimina de la caché. Si no existe, no se permite la reanudación y ocurrirá un handshake completo.

Tenga en cuenta que algunas aplicaciones pueden mantener una caché externa de sesiones (ver SSL_CTX_sess_set_new_cb(3) y funciones similares). Es responsabilidad de la aplicación asegurarse de que las sesiones en la caché externa también se incluyan en la caché interna y que, una vez eliminadas de la caché interna, se eliminen de manera similar de la caché externa. No hacer esto podría hacer que una aplicación sea vulnerable a ataques de repetición. Tenga en cuenta que OpenSSL bloqueará la caché interna mientras se elimina una sesión, pero ese bloqueo no se mantiene cuando se llama a la función de devolución de llamada de eliminación de sesión (ver SSL_CTX_sess_set_remove_cb(3)). Esto podría dar lugar a un pequeño período de tiempo en el que la sesión se ha eliminado de la caché interna, pero aún está disponible en la caché externa. Las aplicaciones deben diseñarse teniendo esto en cuenta para minimizar la posibilidad de ataques de repetición.

La protección contra repeticiones de OpenSSL no se aplica a claves pre-compartidas externas (PSK) (por ejemplo, ver SSL_CTX_set_psk_find_session_callback(3)). Por lo tanto, se debe tener extrema precaución al combinar PSK externas con datos tempranos.

Algunas aplicaciones pueden mitigar los riesgos de repetición de otras maneras. Para esas aplicaciones, es posible desactivar la función integrada de protección contra repeticiones utilizando la opción SSL_OP_NO_ANTI_REPLAY. Ver SSL_CTX_set_o SSL_read_early_data(3ssl) — Arch Linux man pages

OPTIONS

The caller can set the maximum amount of early data that MAY be sent by calling SSL_CTX_set_max_early_data(3) or SSL_set_max_early_data(3). See SSL_CTX_set_options(3) for details. Applications can also set a callback to make decisions about accepting early data or not. See SSL_CTX_set_allow_early_data_cb() above for details.

VALORES DE RETORNO

SSL_write_early_data() devuelve 1 si tiene éxito o 0 si falla. En caso de fallo, llame a SSL_get_error(3) para determinar el curso de acción correcto.

SSL_read_early_data() devuelve SSL_READ_EARLY_DATA_ERROR en caso de fallo, SSL_READ_EARLY_DATA_SUCCESS si tiene éxito con más datos por leer y SSL_READ_EARLY_DATA_FINISH si tiene éxito sin más datos por leer. En caso de fallo, llame a SSL_get_error(3) para determinar el curso de acción correcto.

SSL_get_max_early_data(), SSL_CTX_get_max_early_data() y SSL_SESSION_get_max_early_data() devuelven el número máximo de bytes de datos tempranos que pueden ser enviados.

SSL_set_max_early_data(), SSL_CTX_set_max_early_data() y SSL_SESSION_set_max_early_data() devuelven 1 si tienen éxito o 0 si fallan.

SSL_get_early_data_status() devuelve SSL_EARLY_DATA_ACCEPTED si los datos tempranos fueron aceptados por el servidor, SSL_EARLY_DATA_REJECTED si los datos tempranos fueron rechazados por el servidor, o SSL_EARLY_DATA_NOT_SENT si no se enviaron datos tempranos.
