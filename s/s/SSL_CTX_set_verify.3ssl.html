SSL_CTX_set_verify(3ssl)

Paquete: openssl

Licencias: Apache-2.0

SSL_CTX_SET_VERIFY(3ssl) OpenSSL SSL_CTX_SET_VERIFY(3ssl)

NOMBRE

SSL_get_ex_data_X509_STORE_CTX_idx, SSL_CTX_set_verify, SSL_set_verify, SSL_CTX_set_verify_depth, SSL_set_verify_depth, SSL_verify_cb, SSL_verify_client_post_handshake, SSL_set_post_handshake_auth, SSL_CTX_set_post_handshake_auth - establecer varios parámetros SSL/TLS para la verificación del certificado del par

SINOPSIS

#include <openssl/ssl.h>
typedef int (*SSL_verify_cb)(int preverify_ok, X509_STORE_CTX *x509_ctx);
void SSL_CTX_set_verify(SSL_CTX *ctx, int mode, SSL_verify_cb verify_callback);
void SSL_set_verify(SSL *ssl, int mode, SSL_verify_cb verify_callback);
SSL_get_ex_data_X509_STORE_CTX_idx(void);
void SSL_CTX_set_verify_depth(SSL_CTX *ctx, int depth);
void SSL_set_verify_depth(SSL *ssl, int depth);
int SSL_verify_client_post_handshake(SSL *ssl);
void SSL_CTX_set_post_handshake_auth(SSL_CTX *ctx, int val);
void SSL_set_post_handshake_auth(SSL *ssl, int val);

DESCRIPCIÓN

SSL_CTX_set_verify() establece las banderas de verificación para ctx en mode y especifica la función verify_callback a utilizar. Si no se debe especificar ninguna función de devolución de llamada, se puede usar el puntero NULL para verify_callback. ctx NO DEBE ser NULL.

SSL_set_verify() establece las banderas de verificación para ssl en mode y especifica la función verify_callback a utilizar. Si no se debe especificar ninguna función de devolución de llamada, se puede usar el puntero NULL para verify_callback. En este caso, la última verify_callback establecida específicamente para este ssl permanece. Si no se estableció previamente ninguna callback especial, se utiliza la devolución de llamada predeterminada para el ctx subyacente, que era válida en el momento en que ssl se creó con SSL_new(3). Dentro de la función de devolución de llamada, se puede llamar a SSL_get_ex_data_X509_STORE_CTX_idx para obtener el índice de datos del objeto SSL actual que está realizando la verificación.

En modo cliente, verify_callback también puede llamar a la función SSL_set_retry_verify(3) en el objeto SSL establecido en los datos ex de x509_store_ctx (ver SSL_get_ex_data_X509_STORE_CTX_idx(3)) y devolver 1. Esto se haría típicamente en caso de que la verificación del certificado aún no haya podido tener éxito. Esto suspende el handshake y devuelve el control a la aplicación que llama con SSL_ERROR_WANT_RETRY_VERIFY. La aplicación puede, por ejemplo, obtener certificados adicionales o información de estado de certificados necesaria para la verificación. Llamar a SSL_connect(3) de nuevo reanuda el intento de conexión reintentando el paso de verificación del certificado del servidor. Este proceso incluso puede repetirse si es necesario. Tenga en cuenta que el handshake aún puede abortarse si una invocación posterior de la devolución de llamada (por ejemplo, a una profundidad menor, o para una condición de error diferente) devuelve 0.

SSL_CTX_set_verify_depth() establece la profundidad máxima para la verificación de la cadena de certificados que se permitirá para ctx.

SSL_set_verify_depth() establece la profundidad máxima para la verificación de la cadena de certificados que se permitirá para ssl.

SSL_CTX_set_post_handshake_auth() y SSL_set_post_handshake_auth() habilitan la extensión de Autenticación Post-Handshake para ser agregada al ClientHello, de modo que el servidor pueda solicitar autenticación post-handshake. Si val es 0, la extensión no se envía, de lo contrario sí. Por defecto, la extensión no se envía. Se deberá establecer una devolución de llamada de certificado a través de SSL_CTX_set_client_cert_cb() si no se proporciona ningún certificado al inicializar.

SSL_verify_client_post_handshake() hace que un mensaje CertificateRequest sea enviado por un servidor en la conexión ssl dada. La bandera SSL_VERIFY_PEER debe estar establecida; la bandera SSL_VERIFY_POST_HANDSHAKE es opcional.

NOTAS

La verificación de certificados puede controlarse mediante un conjunto de banderas mode lógicamente OR'ed:

SSL_VERIFY_NONE
Modo servidor: el servidor no enviará una solicitud de certificado de cliente al cliente, por lo que el cliente no enviará un certificado.

Modo cliente: si no se utiliza un cifrado anónimo (deshabilitado por defecto), el servidor enviará un certificado que será verificado. El resultado del proceso de verificación del certificado se puede comprobar después del handshake TLS/SSL utilizando la función SSL_get_verify_result(3). El handshake continuará independientemente del resultado de la verificación.

SSL_VERIFY_PEER
Modo servidor: el servidor envía una solicitud de certificado de cliente al cliente. El certificado devuelto (si lo hay) se verifica. Si el proceso de verificación falla, el handshake TLS/SSL se termina inmediatamente con un mensaje de alerta que contiene la razón de la falla de verificación. El comportamiento puede controlarse mediante las banderas adicionales SSL_VERIFY_FAIL_IF_NO_PEER_CERT, SSL_VERIFY_CLIENT_ONCE y SSL_VERIFY_POST_HANDSHAKE.

Modo cliente: se verifica el certificado del servidor. Si el proceso de verificación falla, el handshake TLS/SSL se termina inmediatamente con un mensaje de alerta que contiene la razón de la falla de verificación. Si no se envía ningún certificado de servidor, debido a que se utiliza un cifrado anónimo, SSL_VERIFY_PEER se ignora.

SSL_VERIFY_FAIL_IF_NO_PEER_CERT
Modo servidor: si el cliente no devolvió un certificado, el handshake TLS/SSL se termina inmediatamente con una alerta de "handshake failure". Esta bandera debe usarse junto con SSL_VERIFY_PEER.

Modo cliente: ignorado (ver BUGS)

SSL_VERIFY_CLIENT_ONCE
Modo servidor: solo solicitar un certificado de cliente una vez durante la conexión. No solicitar un certificado de cliente nuevamente durante la rennegociación o la autenticación posterior si se solicitó un certificado durante el handshake inicial. Esta bandera debe usarse junto con SSL_VERIFY_PEER.

Modo cliente: ignorado (ver BUGS)

SSL_VERIFY_POST_HANDSHAKE
Modo servidor: el servidor no enviará una solicitud de certificado de cliente durante el handshake inicial, sino que enviará la solicitud a través de SSL_verify_client_post_handshake(). Esto permite que SSL_CTX o SSL se configuren para la verificación del par post-handshake antes de que ocurra el handshake. Esta bandera debe usarse junto con SSL_VERIFY_PEER. Solo TLSv1.3; no tiene efecto en conexiones anteriores a TLSv1.3.

Modo cliente: ignorado (ver BUGS)

Si el mode es SSL_VERIFY_NONE, ninguna de las otras banderas puede establecerse.

Si las banderas de verificación no se modifican explícitamente con SSL_CTX_set_verify() o SSL_set_verify(), el valor predeterminado será SSL_VERIFY_NONE.

El procedimiento de verificación real se realiza utilizando el procedimiento de verificación incorporado o utilizando otra función de verificación proporcionada por la aplicación establecida con SSL_CTX_set_cert_verify_callback(3). Las siguientes descripciones se aplican en el caso del procedimiento incorporado. Una función proporcionada por la aplicación también tiene acceso a la información de profundidad de verificación y a la función verify_callback(), pero la forma en que se utiliza esta información puede ser diferente.

SSL_CTX_set_verify_depth() y SSL_set_verify_depth() establecen un límite en el número de certificados entre los certificados de entidad final y de ancla de confianza. Ni el certificado de entidad final ni el de ancla de confianza cuentan contra la profundidad. Si la cadena de certificados necesaria para llegar a un emisor de confianza es más larga que profundidad+2, se emitirá X509_V_ERR_CERT_CHAIN_TOO_LONG. El recuento de profundidad es "nivel 0: certificado del par", "nivel 1: certificado CA", "nivel 2: certificado CA de nivel superior", y así sucesivamente. Establecer la profundidad máxima en 2 permite los niveles 0, 1, 2 y 3 (siendo 0 la entidad final y 3 el ancla de confianza). El límite de profundidad predeterminado es 100, lo que permite el certificado del par, un máximo de 100 certificados de CA intermedios y un certificado de ancla de confianza final.

La función verify_callback se utiliza para controlar el comportamiento cuando la bandera SSL_VERIFY_PEER está establecida. Debe ser proporcionada por la aplicación y recibe dos argumentos: preverify_ok

indica, si la verificación del certificado en cuestión se superó (preverify_ok=1) o no (preverify_ok=0). x509_ctx es un puntero al contexto completo utilizado para la verificación de la cadena de certificados.

La cadena de certificados se verifica comenzando por el nivel de anidación más profundo (el certificado de la CA raíz) y se avanza hacia el certificado del par. En cada nivel se comprueban las firmas y los atributos del emisor. Siempre que se encuentra un error de verificación, el número de error se almacena en x509_ctx y se llama a verify_callback con preverify_ok=0. Al aplicar las funciones X509_CTX_store_* , verify_callback puede localizar el certificado en cuestión y realizar pasos adicionales (ver EJEMPLOS). Si no se encuentra ningún error para un certificado, se llama a verify_callback con preverify_ok=1 antes de avanzar al siguiente nivel.

El valor de retorno de verify_callback controla la estrategia del proceso de verificación posterior. Si verify_callback devuelve 0, el proceso de verificación se detiene inmediatamente con el estado de "fallo de verificación". Si SSL_VERIFY_PEER está establecido, se envía una alerta de fallo de verificación al par y se termina la negociación TLS/SSL. Si verify_callback devuelve 1, la verificación del proceso continúa. Si verify_callback siempre devuelve 1, la negociación TLS/SSL no terminará con respecto a los fallos de verificación y la conexión se establecerá. El proceso que llama puede, sin embargo, recuperar el código de error del último error de verificación utilizando SSL_get_verify_result(3) o manteniendo su propio almacenamiento de errores gestionado por verify_callback.

Si no se especifica ningún verify_callback, se utilizará el callback predeterminado. Su valor de retorno es idéntico a preverify_ok, por lo que cualquier fallo de verificación llevará a la terminación de la negociación TLS/SSL con un mensaje de alerta, si SSL_VERIFY_PEER está establecido.

Después de llamar a SSL_set_post_handshake_auth(), el cliente necesitará agregar un certificado o un callback de certificado a su configuración antes de poder autenticarse correctamente. Esto debe llamarse antes de SSL_connect().

SSL_verify_client_post_handshake() requiere que las banderas de verificación se hayan establecido previamente, y que el cliente haya enviado la extensión de autenticación post-handshake. Cuando el cliente devuelve un certificado, se invocará el callback de verificación. Debe realizarse una operación de escritura para que la Solicitud de Certificado se envíe al cliente; esto se puede hacer con SSL_do_handshake() o SSL_write_ex(). Solo puede haber una solicitud de certificado pendiente a la vez.

Cuando ocurre la autenticación post-handshake, se envía un mensaje NewSessionTicket actualizado al cliente.

La autenticación post-handshake no se puede utilizar con QUIC. SSL_set_post_handshake_auth() no tiene ningún efecto si se llama en un objeto SSL QUIC.

ERRORES

En modo cliente, no se comprueba si está establecida la bandera SSL_VERIFY_PEER, sino si está establecida alguna bandera distinta de SSL_VERIFY_NONE. Esto puede llevar a un comportamiento inesperado si SSL_VERIFY_PEER y otras banderas no se utilizan según se requiera.

VALORES DE RETORNO

Las funciones SSL*_set_verify*() no proporcionan información diagnóstica.

La función SSL_verify_client_post_handshake() devuelve 1 si la solicitud tuvo éxito y 0 si falló. La pila de errores puede examinarse para determinar el motivo del fallo.

EJEMPLOS

La siguiente secuencia de código implementa una función verify_callback de ejemplo que siempre continuará la negociación TLS/SSL independientemente del fallo de verificación, si se desea. El callback implementa un límite de profundidad de verificación con información más detallada.

Se imprimen todos los errores de verificación; la información sobre la cadena de certificados se imprime bajo demanda. El ejemplo se realiza para un servidor que permite, pero no requiere, certificados de cliente.

El ejemplo utiliza la técnica ex_data para almacenar datos de aplicación en la estructura SSL o recuperarlos de ella (ver CRYPTO_get_ex_new_index(3), SSL_get_ex_data_X509_STORE_CTX_idx(3)).

...
typedef struct {
  int verbose_mode;
  int verify_depth;
  int always_continue;
} mydata_t;
int mydata_index;
...
static int verify_callback(int preverify_ok, X509_STORE_CTX *ctx)
{
    char    buf[256];
    X509   *err_cert;
    int     err, depth;
    SSL    *ssl;
    mydata_t *mydata;
    err_cert = X509_STORE_CTX_get_current_cert(ctx);
    err = X509_STORE_CTX_get_error(ctx);
    depth = X509_STORE_CTX_get_error_depth(ctx);
    /*
     * Recupera el puntero al SSL de la conexión que se está tratando actualmente
     * y los datos específicos de la aplicación almacenados en el objeto SSL.
     */
    ssl = X509_STORE_CTX_get_ex_data(ctx, SSL_get_ex_data_X509_STORE_CTX_idx());
    mydata = SSL_get_ex_data(ssl, mydata_index);
    X509_NAME_oneline(X509_get_subject_name(err_cert), buf, 256);
    /*
     * Captura una cadena de certificados demasiado larga. El límite de profundidad establecido usando
     * SSL_CTX_set_verify_depth() se establece intencionadamente como "límite+1" para
     * que siempre que se cumpla la condición "depth>verify_depth", hayamos violado el límite y queramos registrar esta condición de error.
     * Debemos hacerlo aquí, porque el error CHAIN_TOO_LONG no
     * se encontraría explícitamente; solo se registrarían los errores introducidos al cortar
     * los certificados adicionales.
     */
    if (depth > mydata->verify_depth) {
        preverify_ok = 0;
        err = X509_V_ERR_CERT_CHAIN_TOO_LONG;
        X509_STORE_CTX_set_error(ctx, err);
    }
    if (!preverify_ok) {
        printf("error de verificación:num=%d:%s:profundidad=%d:%s\n", err,
               X509_verify_cert_error_string(err), depth, buf);
    } else if (mydata->verbose_mode) {
        printf("profundidad=%d:%s\n", depth, buf);
    }
    /*
     * En este punto, err contiene el último error de verificación. Podemos usarlo
     * para algo especial.
     */
    if (!preverify_ok && (err == X509_V_ERR_UNABLE_TO_GET_ISSUER_CERT)) {
        X509_NAME_oneline(X509_get_issuer_name(err_cert), buf, 256);
        printf("emisor= %s\n", buf);
    }
    if (mydata->always_continue)
        return 1;
    else
        return preverify_ok;
}
...
mydata_t mydata;
...
mydata_index = SSL_get_ex_new_index(0, "índice de mydata", NULL, NULL, NULL);
...
SSL_CTX_set_verify(ctx, SSL_VERIFY_PEER | SSL_VERIFY_CLIENT_ONCE,
                   verify_callback);
/*
 * Deja que el verify_callback capture el error de verify_depth para que obtengamos
 * un error apropiado en el archivo de registro.
 */
SSL_CTX_set_verify_depth(verify_depth + 1);
/*
 * Configura los datos específicos de SSL en "mydata" y almacénalos en la
 * estructura SSL.
 */
mydata.verify_depth = verify_depth; ...
SSL_set_ex_data(ssl, mydata_index, &mydata);
...
SSL_accept(ssl);       /* la comprobación de éxito se omite por claridad */
if (peer = SSL_get_peer_certificate(ssl)) {
    if (SSL_get_verify_result(ssl) == X509_V_OK) {
        /* El cliente envió un certificado que se verificó correctamente */
    }
}
