Safe(3perl) Guía de Referencia del Programador de Perl Safe(3perl)

NOMBRE

Safe - Compilar y ejecutar código en compartimentos restringidos

SINOPSIS

use Safe;
$compartimento = new Safe;
$compartimento->permit(qw(time sort :browse));
$resultado = $compartimento->reval($codigo_inseguro);

DESCRIPCIÓN

El módulo de extensión Safe permite la creación de compartimentos en los que se puede evaluar código perl. Cada compartimento tiene

un nuevo espacio de nombres
La "raíz" del espacio de nombres (es decir, "main::") se cambia a un paquete diferente y el código evaluado en el compartimento no puede referirse a variables fuera de este espacio de nombres, incluso con búsquedas de glob de tiempo de ejecución y otros trucos.

El código que se compila fuera del compartimento puede optar por colocar variables en (o *compartir* variables con) el espacio de nombres del compartimento y solo esos datos serán visibles para el código evaluado en el compartimento.

Por defecto, las únicas variables compartidas con los compartimentos son las variables "subrayado" $_ y @_ (y, técnicamente, el menos usado %_, el archivo _ y así sucesivamente). Esto se debe a que de lo contrario los operadores perl que utilizan $_ por defecto no funcionarán y tampoco lo hará la asignación de argumentos a @_ en la entrada de la subrutina.

una máscara de operadores
Cada compartimento tiene una "máscara de operadores" asociada. Recuerde que el código perl se compila en un formato interno antes de la ejecución. Evaluar código perl (por ejemplo, a través de "eval" o "do 'file'") hace que el código se compile en un formato interno y luego, siempre que no haya habido un error en la compilación, se ejecute. El código evaluado en un compartimento se compila sujeto a la máscara de operadores del compartimento. Intentar evaluar código en un compartimento que contiene un operador enmascarado provocará que la compilación falle con un error. El código no se ejecutará.

La máscara de operadores predeterminada para un compartimento recién creado es la etiqueta de opción ':default'.

Es importante que lea la documentación del módulo Opcode para obtener más información, especialmente para obtener definiciones detalladas de nombres de op, etiquetas de opción y conjuntos de ops.

Dado que la máscara de operadores solo se aplica en la etapa de compilación, se puede lograr un acceso controlado a operaciones potencialmente inseguras al tener un manejador de una subrutina envolvente (escrita fuera del compartimento) colocada en el compartimento. Por ejemplo,

$cpt = new Safe;
sub wrapper {
  # verificar argumentos y realizar operaciones potencialmente inseguras
}
$cpt->share('&wrapper');

ADVERTENCIA

El módulo Safe no implementa un sandbox efectivo para evaluar código no confiable con el intérprete de perl.

Los errores en el intérprete de perl que podrían ser explotados para evitar las restricciones de Safe no se tratan como vulnerabilidades. Consulte perlsecpolicy para obtener información adicional.

MÉTODOS

Para crear un nuevo compartimento, use

$cpt = new Safe;

El argumento opcional es (ESPACIO_NOMBRES), donde ESPACIO_NOMBRES es el espacio de nombres raíz a usar para el compartimento (por defecto es "Safe::Root0", incrementado para cada nuevo compartimento).

Tenga en cuenta que la versión 1.00 del módulo Safe admitía un segundo parámetro opcional, MASK. Esa funcionalidad ha sido retirada pendiente de una consideración más profunda. Utilice los métodos permit y deny descritos a continuación.

Los siguientes métodos se pueden utilizar en el objeto del compartimento devuelto por el constructor anterior. El argumento del objeto es implícito en cada caso.

permitir (OP, ...)

Permite que los operadores listados se utilicen al compilar código en el compartimento ( *además* de cualquier operador ya permitido).

Puede listar códigos de operación por nombre o usar un nombre de etiqueta; consulte "Etiquetas de código de operación predefinidas" en Opcode.

permitir_solo (OP, ...)

Permite *solo* los operadores listados para ser utilizados al compilar código en el compartimento ( *ningún* otro operador estará permitido).

negar (OP, ...)

Niega que los operadores listados se utilicen al compilar código en el compartimento (es posible que otros operadores sigan permitidos).

negar_solo (OP, ...)

Niega *solo* los operadores listados para ser utilizados al compilar código en el compartimento ( *todos* los demás operadores estarán permitidos, por lo que probablemente no querrá usar este método).

atrapar (OP, ...), desatrapar (OP, ...)

Los métodos atrapar y desatrapar son sinónimos de negar y permitir respectivamente.

compartir (NOMBRE, ...)

Esto comparte la(s) variable(s) en la lista de argumentos con el compartimento. Esto es casi idéntico a exportar variables usando el módulo Exporter.

Cada NOMBRE debe ser el **nombre** de una variable no léxica, típicamente con el identificador de tipo inicial incluido. Una palabra clave se trata como un nombre de función.

Los ejemplos de nombres legales son '$foo' para un escalar, '@foo' para un array, '%foo' para un hash, '&foo' o 'foo' para una subrutina y '*foo' para un glob (es decir, todas las entradas de la tabla de símbolos asociadas con "foo", incluyendo escalar, array, hash, sub y manejador de archivo).

Se asume que cada NOMBRE está en el paquete que llama. Consulte share_from para un método alternativo (que usa "compartir").

compartir_desde (PAQUETE, REFERENCIA_ARRAY)

Este método es similar a compartir() pero le permite nombrar explícitamente el paquete del que se deben compartir los símbolos. Los nombres de los símbolos (incluidos los caracteres de tipo) se proporcionan como una referencia a un array.

$safe->compartir_desde('main', [ '$foo', '%bar', 'func' ]);

Los nombres pueden incluir nombres de paquetes, que son relativos al PAQUETE especificado. Por lo tanto, estas dos llamadas tienen el mismo efecto:

$safe->compartir_desde('Scalar::Util', [ 'reftype' ]);
$safe->compartir_desde('main', [ 'Scalar::Util::reftype' ]);

varglob (NOMBRE_VAR)

Esto devuelve una referencia de glob para la entrada de la tabla de símbolos de NOMBRE_VAR en el paquete del compartimento. NOMBRE_VAR debe ser el **nombre** de una variable sin ningún marcador de tipo inicial. Por ejemplo:

${$cpt->varglob('foo')} = "Hola mundo";

tiene el mismo efecto que:

$cpt = new Safe 'Raiz';
$Raiz::foo = "Hola mundo";

pero evita la necesidad de conocer el nombre del paquete de $cpt.

reval (CADENA, ESTRICTO)

Esto evalúa CADENA como código perl dentro del compartimento.

El código solo puede ver el espacio de nombres del compartimento (tal como lo devuelve el método root). El paquete raíz del compartimento parece ser el paquete "main::" para el código dentro del compartimento.

Cualquier intento del código en CADENA de usar un operador que no esté permitido por el compartimento causará un error (en tiempo de ejecución del programa principal pero en tiempo de compilación para el código en CADENA). El error tiene el formato "'%s' atrapado por máscara de operación...".

Safe.pm(3perl) — Perl safe compartment

NAME

Safe.pm - Perl safe compartment

SYNOPSIS

    use Safe;

    my $c = new Safe::compartment;

    # Evaluate code in the compartment
    $c->reval('print "Hello from compartment!\n"; print $Safe::Thingy');
    $c->reval('my $x = 1; $x + 1');

    # Load code from a file
    $c->rdo('my_safe_code.pl');

    # Get/set operator mask
    my $mask = $c->mask;
    $c->mask(deny_only);

    # Get root namespace
    my $root = $c->root;

    # Wrap code references
    my $wrapped_sub = Safe::wrap_code_ref(\&some_sub);
    $wrapped_sub->();

    # Unsafe code example (will fail if eval is denied)
    eval {
        my $oob_code = 'print "This will likely fail\n"; my $foo = 1;';
        $c->reval($oob_code);
    };
    if ($@) {
        print "Failed to eval out-of-bounds code: $@\n";
    }

DESCRIPTION

The Safe.pm module provides a mechanism for creating sandboxed environments within a Perl program. These environments, called "compartments", restrict the operations that can be performed by code executed within them. This is useful for running untrusted code, such as user-submitted scripts or code loaded from external sources, without risking the stability or security of the main program.

A compartment is essentially a restricted namespace with a limited set of available Perl operators. By default, many potentially dangerous operators (like those that perform file I/O, system calls, or modify the global environment) are disallowed.

The primary methods for interacting with a compartment are reval() and rdo(), which allow you to execute Perl code and load files respectively within the compartment's restricted environment.

WARNING

Safe.pm is not a security sandbox in the same way that, for example, a chroot jail is for the operating system. It operates at the Perl interpreter level. It can prevent untrusted code from accessing arbitrary files, running arbitrary commands, or crashing the Perl interpreter. However, it cannot prevent all possible attacks. For instance, a malicious script could potentially consume all available memory or CPU resources, leading to a denial-of-service attack.

Furthermore, the interaction between code running inside and outside a compartment can be complex. Be particularly careful when sharing subroutines or data structures between compartments, as unintended side effects can occur.

METHODS

new

Creates and returns a new Safe compartment object.

The constructor optionally takes arguments that can be used to pre-configure the compartment, such as setting the initial operator mask or the root namespace.

    my $c = Safe::compartment->new(
        -root_namespace => 'MyCompartment',
        -deny_only      => [qw(open print)],
    );

reval(CODE_OR_FILE, ARGS...)

Evaluates the given Perl code CODE_OR_FILE within the compartment. This method is similar to Perl's built-in eval() function, but it operates within the restricted environment of the compartment.

If an error occurs during compilation or execution within the compartment, the error message is returned in the special variable $@, just as with a normal eval().

If there are no errors, the method returns the value of the last expression evaluated. Alternatively, a return statement can be used within the code, just as with subroutines and eval(). The context (list or scalar) is determined by the caller, as usual.

If the return value of reval() is or contains any code references, those code references are automatically wrapped to ensure they are executed within the compartment's context. See wrap_code_refs_within.

An optional argument, STRICT, can be used to control strictness. If true, 'use strict;' is used; otherwise, 'no strict;' is used. If STRICT is omitted, 'no strict;' is the default.

Some points to note:

If the entereval op is permitted within the compartment's mask, code executed within the compartment can use eval "..." to attempt to execute code that might use denied operators. However, when the code within the internal eval attempts to execute a denied operator, the operation will fail because the compartment's opmask is still in effect. This technique could potentially be used to probe the boundaries of the compartment's restrictions.

Any string eval executed by code running inside a compartment, or by code called from code running inside a compartment, will be evaluated in the namespace of the compartment. This can be a significant issue.

Consider a function foo() in package pkg compiled outside a compartment but shared with it. Assume the compartment has a root package named 'Root'. If foo() contains an eval statement like eval '$foo = 1', normally, $pkg::foo would be set to 1. However, if foo() is called from the compartment (by any means), the eval will instead set $Root::pkg::foo.

This can be demonstrated using a module like the Socket module, which uses eval "..." as part of its AUTOLOAD function. If you use the module outside the compartment and share an (autoloaded) function with the compartment, and an autoload is triggered from within the compartment, the eval in the Socket module's AUTOLOAD function will execute in the namespace of the compartment. Any variables created or used by this eval'd code will now be under the control of the code in the compartment.

A similar effect applies to *all* runtime symbol lookups in code called from a compartment but not compiled within it.

rdo(FILENAME)

This evaluates the contents of the file specified by FILENAME within the compartment. It uses the same rules as Perl's built-in "do" command to locate the file, potentially searching @INC.

Refer to the documentation for the reval method for further details on how code is executed within the compartment.

root(NAMESPACE)

This method returns the name of the package that serves as the root of the compartment's namespace.

Note that this behavior differs from version 1.00 of the Safe module, where the root module could be used to change the namespace. That functionality has been withdrawn pending further consideration.

mask(MASK)

This is a get-or-set method for the compartment's operator mask.

When called without the MASK argument, it returns the current operator mask of the compartment.

When called with the MASK argument, it sets the operator mask for the compartment. This is equivalent to calling the deny_only method.

wrap_code_ref(CODEREF)

Returns a reference to an anonymous subroutine. When this returned subroutine is executed, it will call the original CODEREF with the Safe compartment 'in effect'. This means the package namespace is adjusted, and the opmask is enabled appropriately.

Note that the opmask does not affect already compiled code; it only affects any *further* compilation that the already compiled code might attempt.

This method is particularly useful when applied to code references returned from reval().

(It also provides a workaround for RT#60374: "Safe.pm sort {} bug with -Dusethreads". See https://rt.perl.org/rt3//Public/Bug/Display.html?id=60374 for more details.)

wrap_code_refs_within(...)

Wraps any CODE references found within the arguments by replacing each with the result of calling wrap_code_ref on that CODE reference. Any ARRAY or HASH references within the arguments are inspected recursively.

Returns nothing.

RISKS

This section outlines some potential risks and side effects when running code within a compartment. Code executed inside a compartment might, intentionally or unintentionally, affect the environment outside the compartment in the following ways:

Memory
Code within the compartment could consume all available memory or a significant portion of it.
CPU
Infinite loops or computationally intensive operations could exhaust CPU resources.
Snooping
Code might attempt to access and exfiltrate sensitive information, such as user names or environment variables, from the main process or system.
Signals
Code could potentially trigger signals (e.g., SIGFPE, SIGALRM) that affect the main process. Setting up signal handlers within or from the compartment requires careful consideration regarding which mask is in effect when the handler is invoked.
State Changes
Certain operations, such as chdir, have process-wide effects. Others, like rand and srand, have subtler but still global effects on the Perl interpreter's state.
