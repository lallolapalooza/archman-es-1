SD_EVENT_WAIT(3) sd_event_wait SD_EVENT_WAIT(3)

NOMBRE

sd_event_wait, sd_event_prepare, sd_event_dispatch, sd_event_get_state, sd_event_get_iteration, SD_EVENT_INITIAL, SD_EVENT_PREPARING, SD_EVENT_ARMED, SD_EVENT_PENDING, SD_EVENT_RUNNING, SD_EVENT_EXITING, SD_EVENT_FINISHED - Operaciones de bajo nivel del bucle de eventos

SINOPSIS

#include <systemd/sd-event.h>
enum {
        SD_EVENT_INITIAL,
        SD_EVENT_PREPARING,
        SD_EVENT_ARMED,
        SD_EVENT_PENDING,
        SD_EVENT_RUNNING,
        SD_EVENT_EXITING,
        SD_EVENT_FINISHED,
};

int sd_event_prepare(sd_event *event);

int sd_event_wait(sd_event *event, uint64_t usec);

int sd_event_dispatch(sd_event *event);

int sd_event_get_state(sd_event *event);

int sd_event_get_iteration(sd_event *event, uint64_t *ret);

DESCRIPCIÓN

Las funciones de bajo nivel sd_event_prepare(), sd_event_wait() y sd_event_dispatch() pueden usarse para ejecutar fases específicas de un bucle de eventos. Consulte sd_event_run(3) y sd_event_loop(3) para funciones de nivel superior que ejecutan iteraciones individuales pero completas de un bucle de eventos o lo ejecutan continuamente.

sd_event_prepare() comprueba si hay eventos pendientes y activa los temporizadores necesarios. Si hay algún evento listo para ser procesado ("pendiente"), devuelve un valor positivo distinto de cero, y el llamador debe procesar estos eventos con sd_event_dispatch().

sd_event_dispatch() envía el origen de evento de mayor prioridad que tiene un evento pendiente. En caso de éxito, sd_event_dispatch() devuelve cero, lo que indica que no se pueden enviar más orígenes de evento y se solicitó la salida del bucle de eventos mediante sd_event_exit(3); o un valor positivo distinto de cero, lo que significa que se envió un origen de evento y el bucle volvió a su estado inicial, y el llamador debe iniciar la siguiente iteración del bucle de eventos invocando nuevamente sd_event_prepare().

En caso de que sd_event_prepare() devolviera cero, sd_event_wait() debe ser llamado para esperar más eventos o un tiempo de espera. Si hay eventos listos para ser procesados, devuelve un valor positivo distinto de cero, y los eventos deben ser enviados con sd_event_dispatch(). De lo contrario, el bucle de eventos volvió a su estado inicial y la siguiente iteración del bucle de eventos debe ser iniciada invocando nuevamente sd_event_prepare().

sd_event_get_state() puede usarse para determinar el estado en el que se encuentra actualmente el bucle de eventos. Devuelve uno de los estados descritos a continuación.

sd_event_get_iteration() puede usarse para determinar la iteración actual del bucle de eventos. Devuelve un entero de 64 bits sin signo que contiene un contador que aumenta monótonamente con cada iteración del bucle de eventos, comenzando desde 0. El contador se incrementa en el momento de la invocación de sd_event_prepare().

Las cinco funciones toman, como primer argumento, el objeto de bucle de eventos event que ha sido creado con sd_event_new(). El tiempo de espera para sd_event_wait() se especifica en usec en microsegundos. (uint64_t) -1 puede usarse para especificar un tiempo de espera infinito.

MÁQUINA DE ESTADOS

El bucle de eventos conoce los siguientes estados, que pueden ser consultados con sd_event_get_state().

SD_EVENT_INITIAL

El estado inicial del bucle de eventos, antes de cada iteración del bucle de eventos. Usa sd_event_prepare() para transicionar el bucle de eventos a los estados SD_EVENT_ARMED o SD_EVENT_PENDING.

Añadido en la versión 229.

SD_EVENT_PREPARING

Se está preparando un origen de evento, es decir, se está ejecutando actualmente el manejador de preparación, como se establece con sd_event_source_set_prepare(3). Este estado solo se ve en el manejador de preparación del origen de evento que se invoca desde la llamada sd_event_prepare() y va seguido inmediatamente por SD_EVENT_ARMED o SD_EVENT_PENDING.

Añadido en la versión 229.

SD_EVENT_ARMED

Se ha llamado a sd_event_prepare() y no había orígenes de evento listos para ser enviados. Usa sd_event_wait() para esperar nuevos eventos y transicionar a SD_EVENT_PENDING o de vuelta a SD_EVENT_INITIAL.

Añadido en la versión 229.

SD_EVENT_PENDING

Se ha llamado a sd_event_prepare() o sd_event_wait() y había orígenes de evento con eventos pendientes. Usa sd_event_dispatch() para enviar el origen de evento de mayor prioridad y transicionar de vuelta a SD_EVENT_INITIAL, o a SD_EVENT_FINISHED.

Añadido en la versión 229.

SD_EVENT_RUNNING

Se está enviando actualmente un origen de evento regular. Este estado solo se ve en el manejador del origen de evento que se invoca desde la llamada sd_event_dispatch(), y va seguido inmediatamente por SD_EVENT_INITIAL o SD_EVENT_FINISHED tan pronto como el manejador del origen de evento retorna. Ten en cuenta que durante el envío de orígenes de evento de salida se ve el estado SD_EVENT_EXITING en su lugar.

Añadido en la versión 229.

SD_EVENT_EXITING

Similar a SD_EVENT_RUNNING pero es el estado en efecto mientras se envían orígenes de evento de salida. Va seguido por SD_EVENT_INITIAL o SD_EVENT_FINISHED tan pronto como el manejador de evento retorna.

Añadido en la versión 229.

SD_EVENT_FINISHED

El bucle de eventos ha salido. Todos los orígenes de evento de salida se han ejecutado. Si el bucle de eventos está en este estado, ya no sirve para nada y debe ser liberado.

Añadido en la versión 229.

Un diagrama de flujo simplificado de los estados y las llamadas para transicionar entre ellos se muestra a continuación. Ten en cuenta que SD_EVENT_PREPARING, SD_EVENT_RUNNING y SD_EVENT_EXITING no se muestran aquí.

          INITIAL -<---<---<---<---<---<---<---<---<---<---<---<---\
             |                                                     |
             |                                                     ^
             |                                                     |
             v                 ret == 0                            |
      sd_event_prepare() >--->--->--->--->- ARMED                  |
             |                                |                    ^
             | ret > 0                        |                    |
             |                                |                    |
             v                                v          ret == 0  |
          PENDING <---<---<---<---<---< sd_event_wait() >--->--->--+
             |           ret > 0                                   ^
             |                                                     |
             |                                                     |
             v                                                     |
      sd_event_dispatch() >--->--->--->--->--->--->--->--->--->--->/
             |                             ret > 0
             | ret == 0
             |
             v
          FINISHED

VALOR DE RETORNO

En caso de éxito, estas funciones devuelven 0 o un entero positivo. En caso de fallo, devuelven un código de error negativo estilo errno. En caso de sd_event_prepare() y sd_event_wait(), un código de retorno positivo y distinto de cero indica que los eventos están listos para ser procesados y cero indica que no hay eventos listos. En caso de sd_event_dispatch(), un código de retorno positivo y distinto de cero indica que el bucle de eventos volvió a su estado inicial y cero indica que el bucle de eventos ha salido. sd_event_get_state() devuelve un estado positivo o cero en caso de éxito.

Errores

Los errores devueltos pueden indicar los siguientes problemas:

-EINVAL

El parámetro event es inválido o NULL.

-EBUSY

El objeto de bucle de eventos no está en el estado correcto.

-ESTALE

El bucle de eventos ya está terminado.

DESCRIPTION

These functions are used to register various kinds of event sources with an event loop. An event loop is an object that manages a collection of event sources and dispatches events from them.

The functions come in two flavours: the first set registers the source and returns a handle to it, while the second set (ending in _source) registers the source and returns the same handle.

The main event loop is created with sd_event_new(3). The event loop is passed as the first argument to most of these functions.

The callback parameter is a function pointer to the handler that should be called when the event occurs. The handler is called with the event source handle, and the userdata pointer passed to the registration function. The handler should return an integer. A return value of 0 means the event source should be kept active. A positive return value means the event source should be removed after the callback returns. A negative return value indicates an error.

The flags parameter controls the behaviour of the event source. Currently, only SD_EVENT_PRIORITY_NORMAL, SD_EVENT_PRIORITY_HIGH, SD_EVENT_PRIORITY_VERY_HIGH, and SD_EVENT_ONESHOT are supported.

sd_event_add_io() registers an event source that is triggered when I/O readiness is detected on a file descriptor. The fd parameter is the file descriptor to watch, and events is a bitmask of EPOLLIN, EPOLLOUT, EPOLLRDHUP, etc.

sd_event_add_time() registers an event source that is triggered at a specific time. The when parameter is a pointer to a struct timespec specifying the time. If when is NULL, the event source is triggered immediately.

sd_event_add_signal() registers an event source that is triggered when a specific signal is received. The signum parameter is the signal number to catch.

sd_event_add_child() registers an event source that is triggered when a child process exits. The pid parameter is the PID of the child process to monitor. If pid is 0, any child process exiting will trigger the event. The si parameter is a pointer to a siginfo_t structure that will be filled with information about the child process upon exit.

sd_event_add_defer() registers an event source that is triggered as soon as possible, after any pending I/O events. This is useful for deferring work until the event loop is idle.

sd_event_add_prefork() registers an event source that is triggered just before the event loop forks. This is useful for cleaning up resources that should not be inherited by the child process.

sd_event_add_postfork() registers an event source that is triggered just after the event loop forks. This is useful for initializing resources in the child process that should not be shared with the parent.

sd_event_add_inotify() registers an event source that is triggered when filesystem events occur within a directory specified by path. The fd parameter is the file descriptor of an inotify instance. The inotify_mask parameter specifies the events to watch for (e.g., IN_CREATE, IN_DELETE).

sd_event_add_rtkit() registers an event source that is triggered when a change occurs in the RealtimeKit session specified by action.

sd_event_add_event() registers an event source that is triggered when an event occurs in another event loop specified by other_event.

sd_event_add_child_external() is similar to sd_event_add_child(), but it allows monitoring a child process that was not created by the current process.

sd_event_add_process() registers an event source that is triggered when a process changes its state (e.g., exits or is stopped). The pid parameter is the process ID, and priority determines the order in which these events are processed.

sd_event_add_user() is a generic event source that can be used to monitor various user-specific events.

sd_event_add_job() registers an event source that is triggered when a systemd job changes its state. The pid parameter is the PID of the job's main process, and job_type specifies the type of job.

sd_event_add_mount() registers an event source that is triggered when a filesystem mount point changes state. The path parameter is the mount point path, and mount_flags specify the mount status to monitor.

sd_event_add_wakeup() registers an event source that is triggered when the event loop is woken up.

sd_event_add_tramp() registers an event source for internal use related to process management.

sd_event_add_setuid() registers an event source related to setuid operations.

sd_event_add_service() registers an event source related to systemd service management.

sd_event_add_socket() is an alias for sd_event_add_io().

The functions ending in _source are identical to their counterparts without the suffix, but are provided for consistency and clarity.

STATE MACHINE

The sd_event_add_child function monitors the state of a child process. The callback function will be invoked when the child process terminates or changes its state in a way that is relevant to the event loop. The flags parameter can be used to specify how the child process is monitored. For example, SD_EVENT_CH_EXITED is used to trigger the callback when the child process exits.

The sd_event_add_child function returns an sd_event_source object. This object can be used to manage the event source, for example, to disable or remove it from the event loop.

The sd_event_add_exit function registers a callback that is invoked when the process is about to exit. This can be used for cleanup operations.

The sd_event_add_inotify function monitors filesystem events. The inotify_mask parameter specifies which events to watch for. The callback function will be invoked when any of the specified events occur.

The sd_event_add_io function monitors I/O readiness on a file descriptor. The events parameter specifies whether to monitor for read readiness (EPOLLIN) or write readiness (EPOLLOUT).

The sd_event_add_time function registers a timer event. The when parameter specifies the time at which the event should occur. If when is NULL, the event will occur immediately.

The sd_event_add_signal function monitors signals. The signum parameter specifies the signal number to monitor.

The sd_event_add_defer function registers an event that is triggered as soon as possible, after any pending I/O events.

The sd_event_add_prefork and sd_event_add_postfork functions are used for managing resources across process forks.

The sd_event_add_rtkit function is used to monitor RealtimeKit actions.

The sd_event_add_event function allows one event loop to trigger events in another event loop.

The sd_event_add_child_external function is similar to sd_event_add_child but allows monitoring processes not created by the current process.

The sd_event_add_process function monitors process state changes.

The sd_event_add_user function provides a generic interface for user-defined event sources.

The sd_event_add_job function monitors systemd jobs.

The sd_event_add_mount function monitors filesystem mount points.

The sd_event_add_wakeup function is triggered when the event loop is woken up.

The sd_event_add_tramp function is for internal use.

The sd_event_add_setuid function is related to setuid operations.

The sd_event_add_service function is related to systemd services.

The sd_event_add_socket function is an alias for sd_event_add_io.

The functions ending in _source are identical to their counterparts without the suffix, but are provided for consistency and clarity.

RETURN VALUE

On success, these functions return a pointer to the newly created sd_event_source object. On failure, they return a negative error number.

errno may be set to indicate the error.

A special error code -ECHILD is returned if the event loop has been created in a different process, library or module instance.

Other errors are possible, too.

NOTES

Functions described here are available as a shared library, which can be compiled against and linked to with the libsystemd pkg-config(1) file.

The code described here uses getenv(3), which is declared to be not multi-thread-safe. This means that the code calling the functions described here must not call setenv(3) from a parallel thread. It is recommended to only do calls to setenv() from an early phase of the program when no other threads have been started.
