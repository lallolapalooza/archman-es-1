NOMBRE

sd_journal_get_fd, sd_journal_get_events, sd_journal_get_timeout, sd_journal_process, sd_journal_wait, sd_journal_reliable_fd, SD_JOURNAL_NOP, SD_JOURNAL_APPEND, SD_JOURNAL_INVALIDATE - Interfaz de notificación de cambios en el journal

SINOPSIS

#include <systemd/sd-journal.h>

int sd_journal_get_fd(sd_journal *j);

int sd_journal_get_events(sd_journal *j);

int sd_journal_get_timeout(sd_journal *j, uint64_t *timeout_usec);

int sd_journal_process(sd_journal *j);

int sd_journal_wait(sd_journal *j, uint64_t timeout_usec);

int sd_journal_reliable_fd(sd_journal *j);

DESCRIPCIÓN

sd_journal_get_fd() devuelve un descriptor de archivo que puede ser consultado de forma asíncrona en un bucle de eventos externo y que se señaliza tan pronto como el journal cambia, porque se añadieron nuevas entradas o archivos, tuvo lugar una rotación, o se eliminaron archivos, etc. El descriptor de archivo es adecuado para su uso en poll(2). Use sd_journal_get_events() para una máscara de eventos en la que vigilar. La llamada toma un argumento: el objeto de contexto del journal. Tenga en cuenta que no todos los sistemas de archivos son capaces de generar los eventos necesarios para las activaciones desde este descriptor de archivo para que los cambios se noten inmediatamente. En particular, los sistemas de archivos de red no generan eventos de cambio de archivo adecuados en todos los casos. Casos como estos se pueden detectar con sd_journal_reliable_fd(), a continuación. sd_journal_get_timeout() se asegurará en estos casos de que las activaciones ocurran con la suficiente frecuencia para que los cambios se noten, aunque con cierta latencia.

sd_journal_get_events() devolverá la máscara de poll() para esperar. Esta función devolverá una combinación de POLLIN y POLLOUT y similares para rellenar el campo ".events" de struct pollfd.

sd_journal_get_timeout() devolverá un valor de tiempo de espera para usar en poll(). Devuelve un valor en microsegundos desde la época de CLOCK_MONOTONIC para agotar el tiempo de espera de poll() en timeout_usec. Consulte clock_gettime(2) para obtener detalles sobre CLOCK_MONOTONIC. Si no hay tiempo de espera, rellenará con (uint64_t) -1. Tenga en cuenta que poll() toma un tiempo de espera relativo en milisegundos en lugar de un tiempo de espera absoluto en microsegundos. Para convertir el tiempo de espera absoluto 'us' en tiempo de espera relativo 'ms', use código como el siguiente:

uint64_t t;
int msec;
sd_journal_get_timeout(m, &t);
if (t == (uint64_t) -1)
  msec = -1;
else {
  struct timespec ts;
  uint64_t n;
  clock_gettime(CLOCK_MONOTONIC, &ts);
  n = (uint64_t) ts.tv_sec * 1000000 + ts.tv_nsec / 1000;
  msec = t > n ? (int) ((t - n + 999) / 1000) : 0;
}

El código anterior no realiza ninguna comprobación de errores por brevedad. El entero msec calculado se puede pasar directamente como parámetro de tiempo de espera de poll().

Después de cada activación de poll(), es necesario llamar a sd_journal_process() para procesar los eventos. Esta llamada también indicará qué tipo de cambio se ha detectado (ver más abajo; tenga en cuenta que las activaciones espurias son posibles).

Una alternativa síncrona para usar sd_journal_get_fd(), sd_journal_get_events(), sd_journal_get_timeout() y sd_journal_process() es sd_journal_wait(). Esperará sincrónicamente hasta que el journal cambie. El tiempo máximo que esta llamada duerme puede controlarse con el parámetro timeout_usec. Pase (uint64_t) -1 para esperar indefinidamente. Internamente, esta llamada simplemente combina sd_journal_get_fd(), sd_journal_get_events(), sd_journal_get_timeout(), poll() y sd_journal_process() en una sola.

sd_journal_reliable_fd() puede usarse para comprobar si los eventos de activación del descriptor de archivo devuelto por sd_journal_get_fd() se sabe que se activan rápidamente. En ciertos sistemas de archivos donde los eventos de cambio de archivo del sistema operativo no están disponibles (como NFS), los cambios deben ser consultados repetidamente, y por lo tanto se detectan solo con una latencia considerable. Esta llamada devolverá un valor positivo si los cambios del journal se detectan rápidamente y cero cuando necesiten ser consultados. Tenga en cuenta que normalmente no es necesario invocar esta función directamente, ya que sd_journal_get_timeout() solicitará tiempos de espera apropiados de todos modos.

Tenga en cuenta que ninguna de las interfaces de notificación de cambios anteriores informa de los cambios al instante. Se introducen latencias por múltiples razones: como se mencionó, ciertos backends de almacenamiento requieren sondeos basados en tiempo, en otros casos las activaciones se optimizan agrupando eventos, y el sistema operativo introduce latencias adicionales de planificación de E/S/CPU.

VALOR DE RETORNO

sd_journal_get_fd() devuelve un descriptor de archivo válido en caso de éxito o un código de error negativo estilo errno.

sd_journal_get_events() devuelve una combinación de POLLIN, POLLOUT y similares en caso de éxito o un código de error negativo estilo errno.

sd_journal_reliable_fd() devuelve un entero positivo si el descriptor de archivo devuelto por sd_journal_get_fd() generará activaciones inmediatamente para todos los cambios del journal. Devuelve 0 si puede haber una latencia involucrada.

sd_journal_process() y sd_journal_wait() devuelven un código de error negativo estilo errno, o uno de SD_JOURNAL_NOP, SD_JOURNAL_APPEND o SD_JOURNAL_INVALIDATE en caso de éxito:

•Si se devuelve SD_JOURNAL_NOP, el journal no ha cambiado desde la última invocación.
•Si se devuelve SD_JOURNAL_APPEND, se han añadido nuevas entradas al final del journal. En este caso, es suficiente simplemente continuar leyendo en la ubicación final anterior del journal, para leer las entradas recién añadidas.
•Si se devuelve SD_JOURNAL_INVALIDATE, se añadieron o eliminaron archivos del journal del conjunto de archivos del journal vigilados (por ejemplo, debido a rotación o limpieza), y por lo tanto las entradas pueden haber aparecido o desaparecido en lugares arbitrarios del flujo de registro, posiblemente antes o después del final anterior del flujo de registro. Si se devuelve SD_JOURNAL_INVALIDATE, las UI de vista en vivo que quieran reflejar en pantalla el estado preciso de los datos del registro en disco probablemente deberían actualizar toda su pantalla (en relación con el cursor de la entrada de registro en la parte superior de la pantalla). Los programas interesados solo en un flujo de datos de registro estrictamente secuencial pueden tratar SD_JOURNAL_INVALIDATE de la misma manera que SD_JOURNAL_APPEND, ignorando así cualquier cambio en la vista del registro anterior al final antiguo del flujo de registro.

SEGURIDAD DE SEÑALES

En general, sd_journal_get_fd(), sd_journal_get_events() y sd_journal_get_timeout() no son "seguras para señales asíncronas" en el sentido de signal-safety(7). Sin embargo, solo la primera llamada a cualquiera de estas tres funciones realiza operaciones inseguras, por lo que las llamadas posteriores son seguras.

sd_journal_process() y sd_journal_wait() no son seguras. sd_journal_reliable_fd() es segura.

NOTAS

Todas las funciones aquí descritas son agnósticas a hilos y solo un único hilo puede operar sobre un objeto dado en un momento dado. Diferentes hilos pueden acceder al mismo objeto en diferentes momentos. Se pueden usar múltiples objetos independientes desde diferentes hilos en paralelo.

Las funciones descritas aquí están disponibles como una biblioteca compartida, que puede ser compilada y enlazada con el archivo libsystemd pkg-config(1).
