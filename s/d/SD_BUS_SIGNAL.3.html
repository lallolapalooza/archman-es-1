DESCRIPCIÓN

sd_bus_add_object_vtable() se utiliza para declarar atributos para la ruta de objeto path conectada a la conexión de bus bus bajo la interfaz interface. La tabla vtable puede contener declaraciones de propiedades usando SD_BUS_PROPERTY() o SD_BUS_WRITABLE_PROPERTY(), declaraciones de métodos usando SD_BUS_METHOD(), SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET(), o SD_BUS_METHOD_WITH_NAMES_OFFSET(), y declaraciones de señales usando SD_BUS_SIGNAL_WITH_NAMES() o SD_BUS_SIGNAL(), ver abajo. El parámetro userdata contiene un puntero que se pasará a varias funciones de devolución de llamada. Puede especificarse como NULL si no se necesita ningún valor. Una interfaz puede tener cualquier número de tablas vtable adjuntas a ella.

sd_bus_add_fallback_vtable() es similar a sd_bus_add_object_vtable(), pero se utiliza para registrar atributos de "fallback". Al buscar una declaración de atributo, se comprueban primero las rutas de objetos de bus registradas con sd_bus_add_object_vtable(). Si no se encuentra ninguna coincidencia, se comprueban las tablas vtable de fallback para cada prefijo de la ruta del objeto de bus, es decir, eliminando sucesivamente los últimos componentes separados por barras. Esto permite que la tabla vtable se utilice para un número arbitrario de objetos creados dinámicamente.

El parámetro find es una función que se utiliza para localizar el objeto de destino basándose en la ruta del objeto de bus path. Debe devolver 1 y establecer el parámetro de salida ret_found si se encuentra el objeto, devolver 0 si el objeto no se encontró y devolver un código de error negativo estilo errno o inicializar la estructura de error ret_error en caso de error. El puntero pasado en ret_found se utilizará como parámetro userdata para las funciones de devolución de llamada (con un desplazamiento de los desplazamientos offset especificados en las entradas de la tabla vtable).

sd_bus_add_object() adjunta una devolución de llamada directamente a la ruta de objeto path. Una ruta de objeto puede tener cualquier número de devoluciones de llamada adjuntas a ella. Cada devolución de llamada se antepone a la lista de devoluciones de llamada que siempre se llaman en orden. sd_bus_add_fallback() es similar a sd_bus_add_object() pero se aplica a rutas de fallback en su lugar.

sd_bus_add_filter() instala una devolución de llamada que se invoca para cada mensaje D-Bus entrante. Los filtros se pueden utilizar para manejar lógica común a todos los mensajes recibidos por un servicio (por ejemplo, autenticación o autorización).

Cuando se recibe una solicitud, se llaman secuencialmente las devoluciones de llamada asociadas hasta que una devolución de llamada devuelve un entero distinto de cero. Devolver cero de una devolución de llamada permite que otras devoluciones de llamada tengan la oportunidad de procesar la solicitud. Las devoluciones de llamada se llaman en el siguiente orden: primero, se llaman las devoluciones de llamada globales instaladas con sd_bus_add_filter(). Segundo, se llaman las devoluciones de llamada adjuntas directamente a la ruta del objeto de la solicitud, seguidas de cualquier devolución de llamada de método D-Bus adjunta a la ruta del objeto de la solicitud, interfaz y miembro. Finalmente, se llaman las devoluciones de llamada de propiedad adjuntas a la ruta del objeto de la solicitud, interfaz y miembro. Si la devolución de llamada final devuelve cero, se envía una respuesta de error

Tenga en cuenta que puede devolver un entero positivo desde una devolución de llamada de método sin enviar una respuesta inmediatamente. Esto informa a sd-bus que esta devolución de llamada asumirá la responsabilidad de responder a la solicitud sin forzar a la devolución de llamada a producir una respuesta de inmediato. Esto permite que una devolución de llamada realice cualquier cantidad de operaciones asíncronas necesarias para construir una respuesta. Sin embargo, si la producción de una respuesta lleva demasiado tiempo, la llamada al método se agotará en el llamador. Esto solo está disponible para métodos y no para propiedades.

Si se invocó una devolución de llamada para manejar una solicitud que espera una respuesta y la devolución de llamada devuelve un valor negativo, el valor se interpreta como un código de error negativo estilo errno y se envía de vuelta al llamador como un error D-Bus, como si se hubiera llamado a sd_bus_reply_method_errno(3). Además, todas las devoluciones de llamada toman un parámetro de salida sd_bus_error que se puede usar para proporcionar información de error más detallada. Si ret_error se establece cuando la devolución de llamada finaliza, el error D-Bus correspondiente se envía de vuelta al llamador como si se hubiera llamado a sd_bus_reply_method_error(3). Cualquier error almacenado en ret_error tiene prioridad sobre cualquier valor negativo devuelto por la misma devolución de llamada al determinar qué error enviar de vuelta al llamador. Utilice sd_bus_error_set(3) o una de sus variantes para establecer ret_error y devolver un entero negativo desde una devolución de llamada con una sola llamada a función. Para enviar una respuesta de error después de que una devolución de llamada haya finalizado, utilice sd_bus_reply_method_errno(3) o una de sus variantes.

Para todas las funciones, se crea internamente una ranura de coincidencia. Si el parámetro de salida slot es NULL, se crea un objeto de ranura "flotante", consulte sd_bus_slot_set_floating(3). De lo contrario, se devuelve un puntero al objeto de ranura. En ese caso, la referencia al objeto de ranura debe eliminarse cuando la vtable ya no sea necesaria, consulte sd_bus_slot_unref(3).

El array sd_bus_vtable

El array consiste en estructuras del tipo sd_bus_vtable, pero nunca debe rellenarse manualmente, sino a través de una de las siguientes macros:

SD_BUS_VTABLE_START(flags), SD_BUS_VTABLE_END

Estos deben ser siempre el primer y último elemento. El parámetro flags se puede utilizar para establecer atributos que se apliquen a todo el array; consulte la sección "Flags" a continuación.

SD_BUS_METHOD_WITH_ARGS_OFFSET(), SD_BUS_METHOD_WITH_ARGS()

Declara un método D-Bus con el nombre member, argumentos args y resultado result. args espera una secuencia de pares tipo/nombre de argumento encapsulados en la macro SD_BUS_ARGS(). Los elementos en índices pares en esta lista describen los tipos de los argumentos del método. La firma del parámetro del método es la concatenación de todas las cadenas literales en índices pares en args. Si un método no tiene parámetros, pase SD_BUS_NO_ARGS a args. Los elementos en índices impares describen los nombres de los argumentos del método. result espera una secuencia de pares tipo/nombre encapsulados en la macro SD_BUS_RESULT() en el mismo formato que SD_BUS_ARGS(). La firma del resultado del método es la concatenación de todas las cadenas literales en índices pares en result. Si un método no tiene resultado, pase SD_BUS_NO_RESULT a result. Tenga en cuenta que se espera que los tipos de los argumentos sean cadenas literales entre comillas y los nombres de los argumentos sean cadenas literales sin comillas. Consulte a continuación un ejemplo completo.

La función manejadora handler debe ser de tipo sd_bus_message_handler_t. Se llamará para manejar los mensajes entrantes que llamen a este método. Recibe un puntero que es el parámetro userdata pasado a la función de registro desplazado por offset bytes. Esto puede usarse para pasar punteros a diferentes campos en la misma estructura de datos a diferentes métodos en la misma vtable. Para enviar una respuesta desde handler, llame a sd_bus_reply_method_return(3) con el mensaje con el que se invocó la devolución de llamada. El parámetro flags es una combinación de flags, consulte a continuación.

SD_BUS_METHOD_WITH_ARGS() es un atajo para llamar a SD_BUS_METHOD_WITH_ARGS_OFFSET() con un desplazamiento de cero.

SD_BUS_METHOD_WITH_NAMES_OFFSET(), SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET(), SD_BUS_METHOD()

Declara un método D-Bus con el nombre member, firma de parámetros signature, firma de resultado result. Los parámetros in_names y out_names especifican los nombres de los argumentos de los argumentos de entrada y salida en la firma de la función. in_names y out_names deben crearse utilizando la macro SD_BUS_PARAM(), consulte a continuación. En todos los demás aspectos, esta macro se comporta exactamente igual que SD_BUS_METHOD_WITH_ARGS_OFFSET().

SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET() y SD_BUS_METHOD() son variantes que especifican un desplazamiento cero (el parámetro userdata se pasa sin cambios), dejan los nombres sin establecer (es decir, sin nombres de parámetros) o ambos.

Prefiera usar SD_BUS_METHOD_WITH_ARGS_OFFSET() y SD_BUS_METHOD_WITH_ARGS() sobre estas macros, ya que permiten especificar tipos y nombres de argumentos uno al lado del otro, lo que es menos propenso a errores que especificar primero todos los tipos de argumentos seguidos de la especificación de todos los nombres de argumentos.

SD_BUS_SIGNAL_WITH_ARGS()

Declara una señal D-Bus con el nombre member y argumentos args. args espera una secuencia de pares tipo/nombre de argumento encapsulados en la macro SD_BUS_ARGS(). Los elementos en índices pares en esta lista describen los tipos de los argumentos de la señal. La firma del parámetro de la señal es la concatenación de todas las cadenas literales en índices pares en args. Si una señal no tiene parámetros, pase SD_BUS_NO_ARGS a args. Los elementos en índices impares describen los nombres de los argumentos de la señal. El parámetro flags es una combinación de flags. Consulte a continuación un ejemplo completo.

SD_BUS_SIGNAL_WITH_NAMES(), SD_BUS_SIGNAL()

Declara una señal D-Bus con el nombre member, firma de parámetros signature y nombres de argumentos names. names debe crearse utilizando la macro SD_BUS_PARAM(), consulte a continuación. El parámetro flags es una combinación de flags, consulte a continuación.

SD_BUS_SIGNAL() es equivalente a SD_BUS_SIGNAL_WITH_NAMES() con el parámetro names sin establecer (es decir, sin nombres de parámetros).

Prefiera usar SD_BUS_SIGNAL_WITH_ARGS() sobre estas macros, ya que permite especificar tipos y nombres de argumentos uno al lado del otro, lo que es menos propenso a errores que especificar primero todos los tipos de argumentos seguidos de la especificación de todos los nombres de argumentos.

SD_BUS_WRITABLE_PROPERTY(), SD_BUS_PROPERTY()

Declara una propiedad D-Bus con el nombre member y firma de valor signature. Los parámetros get y set son los métodos de obtención y establecimiento. Se llaman con un puntero que es el parámetro userdata pasado a la función de registro desplazado por offset bytes. Esto puede usarse para pasar punteros a diferentes campos en la misma estructura de datos a diferentes setters y getters en la misma vtable. El parámetro flags es una combinación de flags, consulte a continuación.

El método de establecimiento y obtención se pueden omitir (especificarse como NULL), si la propiedad es de uno de los tipos básicos o "as" en caso de propiedades de solo lectura. En esos casos, los parámetros userdata y offset deben apuntar juntos a una variable válida del tipo correspondiente. Se proporcionará un método de establecimiento y obtención predeterminado, que simplemente copia el argumento entre esta variable y el mensaje.

SD_BUS_PROPERTY() se utiliza para definir una propiedad de solo lectura.

SD_BUS_PARAM()

Los nombres de los parámetros deben encapsularse en esta macro, consulte el ejemplo a continuación.

Flags

El parámetro flags se utiliza para especificar una combinación de **anotaciones de D-Bus**[1].

SD_BUS_VTABLE_DEPRECATED

Marca esta entrada de vtable como obsoleta utilizando la anotación org.freedesktop.DBus.Deprecated en los datos de introspección. Si se especifica para SD_BUS_VTABLE_START(), la anotación se aplica a la interfaz que la contiene.

SD_BUS_VTABLE_HIDDEN

Oculta esta entrada de vtable. No se mostrará en los datos de introspección. Si se especifica para SD_BUS_VTABLE_START(), se ocultan todas las entradas del array.

SD_BUS_VTABLE_METHOD_NO_REPLY

Marca esta entrada de vtable como un método que no devolverá una respuesta utilizando la anotación org.freedesktop.DBus.Method.NoReply en los datos de introspección.

SD_BUS_VTABLE_PROPERTY_CONST, SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE, SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION

Estas tres flags corresponden a diferentes valores de la anotación org.freedesktop.DBus.Property.EmitsChangedSignal, que especifica si la señal org.freedesktop.DBus.Properties.PropertiesChanged se emite cada vez que la propiedad cambia. SD_BUS_VTABLE_PROPERTY_CONST corresponde a const y significa que la propiedad nunca cambia durante la vida útil del objeto al que pertenece, por lo que no es necesario emitir ninguna señal. SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE corresponde a true y significa que se emite la señal. SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION corresponde a invalidates y significa que se emite la señal, pero el valor no se incluye en la señal.

SD_BUS_VTABLE_PROPERTY_EXPLICIT

Marca esta entrada de propiedad de vtable como que requiere una solicitud explícita para que se muestre el valor (generalmente porque el valor es grande o lento de calcular). Esta entrada no se puede combinar con SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE y no se mostrará en las listas de propiedades de forma predeterminada (por ejemplo, busctl introspect). Esto corresponde a la anotación org.freedesktop.systemd1.Explicit en los datos de introspección.

SD_BUS_VTABLE_SENSITIVE

Marca esta entrada de método de vtable como que procesa datos sensibles. Cuando se establece, los mensajes de llamada de método entrantes y sus mensajes de respuesta salientes se marcan como sensibles utilizando sd_bus_message_sensitive(3), para que se borren de la memoria cuando se liberen.

SD_BUS_VTABLE_ABSOLUTE_OFFSET

Marca esta entrada de método o propiedad de vtable para que el puntero de datos de usuario pasado
El acceso a esta entrada de vtable se permitirá si el proceso que llama tiene la capacidad capability, como se describe en sd_bus_query_sender_privilege(3). Si se usa para SD_BUS_VTABLE_START(), proporciona un valor por defecto para todas las entradas en el array. Si no se especifica, se verifica por defecto CAP_SYS_ADMIN para cada entrada individual o el array completo. Véase capabilities(7) para información sobre capacidades.

Nota: Las entradas de vtable pueden marcar como no privilegiadas y el bus completo puede marcarse como confiable, ver la discusión de SD_BUS_VTABLE_UNPRIVILEGED a continuación.

SD_BUS_VTABLE_UNPRIVILEGED

Marque esta entrada de vtable como no privilegiada. El acceso a entradas privilegiadas se limita a usuarios con las capacidades adecuadas, como se describe arriba. En práctica, muchas entradas de vtable están marcadas como no privilegiadas, y pueden estar abiertas a todos o el acceso se decide posteriormente, por ejemplo, delegando a polkit[2].

El bus completo puede marcarse como confiable, en cuyo caso las anotaciones en el nivel de entrada son ignoradas, véase sd_bus_set_trusted(3).

Cuando no se especifique, se mostrará en los datos de introspección la anotación org.freedesktop.systemd1.Privileged con valor "true".

SD_BUS_VTABLE_UNPRIVILEGED no puede aplicarse a propiedades solo leídas, pero el acceso (a ambas propiedades leídas y escritas) siempre es no restringido.

Nota: Esta página describe los controles implementados en el cliente D-Bus. El servidor D-Bus tiene una política adicional que puede permitir o rechazar conexiones, véase el archivo de configuración en dbus-daemon(1).

Ejemplos

Ejemplo 1. Crear un simple listener en el bus

/* SPDX-License-Identifier: MIT-0 */
#define _GNU_SOURCE 1
#include <errno.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdlib.h>
#include <stdio.h>
#include <systemd/sd-bus.h>
#define _cleanup_(f) __attribute__((cleanup(f)))
typedef struct object {
  char *name;
  uint32_t number;
} object;
static int method(sd_bus_message *m, void *userdata, sd_bus_error *error) {
  int r;
  printf("Got called with userdata=%p\n", userdata);
  if (sd_bus_message_is_method_call(m,
                                    "org.freedesktop.systemd.VtableExample",
                                    "Method4"))
    return 1;
  const char *string;
  r = sd_bus_message_read(m, "s", &string);
  if (r < 0) {
    fprintf(stderr, "sd_bus_message_read() failed: %s\n", strerror(-r));
    return 0;
  }
  r = sd_bus_reply_method_return(m, "s", string);
  if (r < 0) {
    fprintf(stderr, "sd_bus_reply_method_return() failed: %s\n", strerror(-r));
    return 0;
  }
  return 1;
}
static const sd_bus_vtable vtable[] = {
        SD_BUS_VTABLE_START(0),
        SD_BUS_METHOD(
            "Method1", "s", "s", method, 0),
        SD_BUS_METHOD_WITH_NAMES_OFFSET(
            "Method2",
            "so", SD_BUS_PARAM(string) SD_BUS_PARAM(path),
            "s", SD_BUS_PARAM(returnstring),
            method, offsetof(object, number),
            SD_BUS_VTABLE_DEPRECATED),
        SD_BUS_METHOD_WITH_ARGS_OFFSET(
            "Method3",
            SD_BUS_ARGS("s", string, "o", path),
            SD_BUS_RESULT("s", returnstring),
            method, offsetof(object, number),
            SD_BUS_VTABLE_UNPRIVILEGED),
        SD_BUS_METHOD_WITH_ARGS(
            "Method4",
            SD_BUS_NO_ARGS,
            SD_BUS_NO_RESULT,
            method,
            SD_BUS_VTABLE_UNPRIVILEGED),
        SD_BUS_SIGNAL(
            "Signal1",
            "so",
            0),
        SD_BUS_SIGNAL_WITH_NAMES(
            "Signal2",
            "so", SD_BUS_PARAM(string) SD_BUS_PARAM(path),
            0),
        SD_BUS_SIGNAL_WITH_ARGS(
            "Signal3",
            SD_BUS_ARGS("s", string, "o", path),
            0),
        SD_BUS_WRITABLE_PROPERTY(
            "AutomaticStringProperty", "s", NULL, NULL,
            offsetof(object, name),
            SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE),
        SD_BUS_WRITABLE_PROPERTY(
            "AutomaticIntegerProperty", "u", NULL, NULL,
            offsetof(object, number),
            SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION),
        SD_BUS_VTABLE_END
};
int main(int argc, char **argv) {
  _cleanup_(sd_bus_flush_close_unrefp) sd_bus *bus = NULL;
  int r;
  sd_bus_default(&bus);
  object object = { .number = 666 };
  object.name = strdup("name");
  if (!object.name) {
    fprintf(stderr, "OOM\n");
    return EXIT_FAILURE;
  }
  r = sd_bus_add_object_vtable(bus, NULL,
                               "/org/freedesktop/systemd/VtableExample",
                               "org.freedesktop.systemd.VtableExample",
                               vtable,
                               &object);
  if (r < 0) {
    fprintf(stderr, "sd_bus_add_object_vtable() failed: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  r = sd_bus_request_name(bus,
                          "org.freedesktop.systemd.VtableExample",
                          0);
  if (r < 0) {
    fprintf(stderr, "sd_bus_request_name() failed: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  for (;;) {
    r = sd_bus_wait(bus, UINT64_MAX);
    if (r < 0) {
      fprintf(stderr, "sd_bus_wait() failed: %s\n", strerror(-r));
      return EXIT_FAILURE;
    }
    r = sd_bus_process(bus, NULL);
    if (r < 0) {
      fprintf(stderr, "sd_bus_process() failed: %s\n", strerror(-r));
      return EXIT_FAILURE;
    }
  }
  r = sd_bus_release_name(bus, "org.freedesktop.systemd.VtableExample");
  if (r < 0) {
    fprintf(stderr, "sd_bus_release_name() failed: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  free(object.name);
  return 0;
}

VALOR DE RETORNO

En éxito, sd_bus_add_object_vtable() y sd_bus_add_fallback_vtable() devuelven un entero no negativo. En error, devuelven un código de error negativo.

Errores

Los errores devueltos pueden indicar los siguientes problemas:

-EINVAL

Un parámetro requerido es NULL o inválido. Se ha pasado un interfaz D-Bus reservado como valor de interface.

-ENOPKG

El bus no puede resolverse.

-ECHILD

El bus fue creado en un proceso, biblioteca o módulo diferente.

-ENOMEM

Falló la asignación de memoria.

-EPROTOTYPE

Se ha llamado a sd_bus_add_object_vtable() y sd_bus_add_fallback_vtable() para el mismo objeto del bus, lo cual no está permitido.

-EEXIST

Esta vtable ya fue registrada para este interface y path.

SD_BUS_SIGNAL.3.en

NAME

sd_bus_signal, sd_bus_emit_signal, sd_bus_emit_signal_strv, sd_bus_emit_method_return, sd_bus_emit_error, sd_bus_emit_properties_changed, sd_bus_emit_object_added, sd_bus_emit_object_removed - Emit D-Bus signals and method return/error messages

DESCRIPTION

These functions are used to emit D-Bus signals and method return/error messages from an object registered on the D-Bus. This is typically done in response to a received method call, or to notify other bus peers about state changes.

Use sd_bus_emit_signal() and sd_bus_emit_signal_strv() to send a general D-Bus signal. The parameters path, interface, member, and signature specify the signal to send. The remaining arguments are the parameters of the signal, which must match the provided signature.

sd_bus_emit_signal_strv() is similar to sd_bus_emit_signal(), but takes the signal parameters as a NULL-terminated array of strings (argv).

Use sd_bus_emit_method_return() to send a method return message. It takes the original method call message (message) as the second argument, and the return parameters as subsequent arguments, matching the provided signature.

Use sd_bus_emit_error() to send an error message in response to a method call. It takes the original method call message (message), the error name (name), and optionally error message parameters matching the provided signature.

Use sd_bus_emit_properties_changed() to emit the standard "PropertiesChanged" signal, defined in the org.freedesktop.DBus.Properties interface. This signal is used to notify about changes to one or more object properties. It takes the path of the object, the interface name, the name of the property that changed, and the new value of the property. If multiple properties changed, they should be bundled into a dictionary. See sd_bus_emit_properties_changed(3) for more details.

Use sd_bus_emit_object_added() and sd_bus_emit_object_removed() to emit the standard "ObjectAdded" and "ObjectRemoved" signals, defined in the org.freedesktop.DBus.ObjectManager interface. These signals notify about the addition or removal of objects managed by an object manager.

All these functions operate on the D-Bus connection specified by bus. The message is constructed, serialized, and sent over the bus. The function will return after the message has been sent to the kernel's socket.

The functions sd_bus_emit_signal(), sd_bus_emit_method_return(), sd_bus_emit_error(), sd_bus_emit_properties_changed(), sd_bus_emit_object_added() and sd_bus_emit_object_removed() append arguments using the standard C printf(3)-like varargs mechanism. The format string must be a valid D-Bus type signature string, and the following arguments must match the types specified in the signature.

For sending complex data structures, consider using sd_bus_message_append(3), sd_bus_message_append_basic(3), sd_bus_message_append_array(3), sd_bus_message_append_dict(3), sd_bus_message_append_variant(3), etc. and then sending the constructed message using sd_bus_send(3).

The arguments bus, and message (for sd_bus_emit_method_return() and sd_bus_emit_error()) must be valid object references. The path, interface, member, signature, name parameters must be valid strings.

Note that sending signals and method returns directly bypasses some of the internal message processing, so care must be taken to ensure correctness.

sd_bus_signal_is_valid() checks if the given path, interface, member, and signature form a valid D-Bus signal. Similarly, sd_bus_method_return_is_valid() checks if the given signature is a valid D-Bus method return signature, and sd_bus_error_is_valid() checks if the given name and signature form a valid D-Bus error message.

These functions are part of a larger API for interacting with the D-Bus system, providing a high-level interface to common D-Bus operations. They are implemented as a shared library, which can be compiled against and linked to with the libsystemd pkg-config(1) file.

The code described here uses getenv(3), which is declared to be not multi-thread-safe. This means that the code calling the functions described here must not call setenv(3) from a parallel thread. It is recommended to only do calls to setenv() from an early phase of the program when no other threads have been started.

EXAMPLES

// Example for emitting a simple signal
sd_bus_emit_signal(bus,
                   "/org/example/Object",
                   "org.example.Interface",
                   "MySignal",
                   "s",
                   "Hello, World!");

// Example for emitting a method return
sd_bus_emit_method_return(bus,
                          reply_to_message,
                          "i",
                          42);

// Example for emitting an error
sd_bus_emit_error(bus,
                  reply_to_message,
                  "org.example.Error.NotFound",
                  "s",
                  "The requested resource was not found.");

RETURN VALUE

On success, these functions return a non-negative integer. On failure, they return a negative error number. Common error numbers include -ENOMEM for out-of-memory errors, and -EINVAL if the arguments are invalid.

NOTES

The functions sd_bus_emit_signal(), sd_bus_emit_method_return(), and sd_bus_emit_error() use varargs, similar to printf(3). The format string must be a valid D-Bus type signature string. The arguments following the format string must match the types specified in the signature.

The functions sd_bus_emit_properties_changed(), sd_bus_emit_object_added(), and sd_bus_emit_object_removed() also use varargs for appending property values, interface names, etc., depending on the specific signal being emitted. Refer to the detailed documentation for each function for the exact signature and arguments.

For more complex message construction, it is recommended to use message creation functions like sd_bus_message_new_signal(3), sd_bus_message_new_method_return(3), or sd_bus_message_new_error(3), followed by appending arguments using functions like sd_bus_message_append(3), and finally sending the constructed message using sd_bus_send(3).

A note on thread safety: The underlying implementation of these functions might use environment variables like DBUS_SESSION_BUS_ADDRESS or DBUS_SYSTEM_BUS_ADDRESS. Accessing environment variables is generally not thread-safe. If these functions are called from multiple threads concurrently, ensure that the environment is set up before any threads are created, or use appropriate synchronization mechanisms.
