DESCRIPCIÓN

sd_bus_add_object_vtable() se utiliza para declarar atributos para la ruta de objeto path conectada a la conexión de bus bus bajo la interfaz interface. La tabla vtable puede contener declaraciones de propiedades usando SD_BUS_PROPERTY() o SD_BUS_WRITABLE_PROPERTY(), declaraciones de métodos usando SD_BUS_METHOD(), SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET(), o SD_BUS_METHOD_WITH_NAMES_OFFSET(), y declaraciones de señales usando SD_BUS_SIGNAL_WITH_NAMES() o SD_BUS_SIGNAL(), véase más abajo. El parámetro userdata contiene un puntero que se pasará a varias funciones de callback. Puede especificarse como NULL si no se necesita ningún valor. Una interfaz puede tener cualquier número de vtables adjuntas a ella.

sd_bus_add_fallback_vtable() es similar a sd_bus_add_object_vtable(), pero se utiliza para registrar atributos "fallback". Al buscar una declaración de atributo, primero se comprueban las rutas de objetos de bus registradas con sd_bus_add_object_vtable(). Si no se encuentra ninguna coincidencia, se comprueban las vtables de fallback para cada prefijo de la ruta del objeto de bus, es decir, eliminando sucesivamente los últimos componentes separados por barras. Esto permite que la vtable se utilice para un número arbitrario de objetos creados dinámicamente.

El parámetro find es una función que se utiliza para localizar el objeto de destino basándose en la ruta del objeto de bus path. Debe devolver 1 y establecer el parámetro de salida ret_found si se encuentra el objeto, devolver 0 si el objeto no se encontró, y devolver un código de error negativo estilo errno o inicializar la estructura de error ret_error en caso de error. El puntero pasado en ret_found se utilizará como parámetro userdata para las funciones de callback (desplazado por los desplazamientos offset tal como se especifican en las entradas de la vtable).

sd_bus_add_object() adjunta un callback directamente a la ruta del objeto path. Una ruta de objeto puede tener cualquier número de callbacks adjuntos a ella. Cada callback se antepone a la lista de callbacks que siempre se llaman en orden. sd_bus_add_fallback() es similar a sd_bus_add_object() pero se aplica a rutas fallback en su lugar.

sd_bus_add_filter() instala un callback que se invoca para cada mensaje D-Bus entrante. Los filtros se pueden utilizar para manejar la lógica común a todos los mensajes recibidos por un servicio (por ejemplo, autenticación o autorización).

Cuando se recibe una solicitud, se llaman secuencialmente los callbacks asociados hasta que un callback devuelva un entero distinto de cero. Devuelva cero desde un callback para dar a otros callbacks la oportunidad de procesar la solicitud. Los callbacks se llaman en el siguiente orden: primero, se llaman los callbacks globales instalados con sd_bus_add_filter(). Segundo, se llaman los callbacks adjuntos directamente a la ruta del objeto de solicitud, seguidos de cualquier callback de método D-Bus adjunto a la ruta del objeto de solicitud, interfaz y miembro. Finalmente, se llaman los callbacks de propiedad adjuntos a la ruta del objeto de solicitud, interfaz y miembro. Si el callback final devuelve cero, se produce un error

La respuesta se envía de vuelta al llamador indicando que no se ha encontrado ningún objeto correspondiente al solicitado.

Nota: puedes devolver un valor positivo desde una callback de un método sin enviar inmediatamente una respuesta. Esto informa a sd-bus que esta callback asume la responsabilidad de responder a la solicitud sin forzar a la callback a producir una respuesta inmediatamente. Esto permite a una callback realizar cualquier número de operaciones asincrónicas necesarias para construir la respuesta. Sin embargo, si la respuesta se genera demasiado tarde, el llamado al método se expirará en el llamador. Esto está disponible solo para métodos y no para propiedades.

Si se invocó una callback para manejar una solicitud que espera una respuesta y la callback devuelve un valor negativo, este valor se interpreta como un código de error de tipo errno negativo y se envía de vuelta al llamador como un error D-Bus, como si se hubiera llamado sd_bus_reply_method_errno(3). Además, todos los callbacks toman un parámetro slot de salida que puede usarse para proporcionar información adicional de error. Si el parámetro ret_error es establecido al finalizar la callback, el error correspondiente se envía de vuelta al llamador como si se hubiera llamado sd_bus_reply_method_error(3). Cualquier error almacenado en ret_error tiene prioridad sobre cualquier valor negativo devuelto por la misma callback para determinar qué error se envía de vuelta al llamador. Usa sd_bus_error_set(3) o una de sus variantes para establecer ret_error y devolver un valor negativo desde una callback con una sola llamada de función. Para enviar una respuesta de error después de que una callback ya terminó, usa sd_bus_reply_method_errno(3) o una de sus variantes.

Para todas las funciones, se crea un slot de objeto internamente. Si el parámetro de salida slot es NULL, se crea un slot de objeto "floating", como se describe en sd_bus_slot_set_floating(3). En caso contrario, se devuelve un puntero a objeto slot. En ese caso, la referencia al objeto slot debe ser destruida cuando el vtable no sea más necesario, como se describe en sd_bus_slot_unref(3).

El array sd_bus_vtable

El array consiste en las estructuras de tipo sd_bus_vtable, pero debe ser llenado manualmente mediante una de las siguientes macros:

SD_BUS_VTABLE_START(flags), SD_BUS_VTABLE_END

Estos deben siempre ser el primer y último elemento. El parámetro flags puede usarse para establecer atributos que apliquen a toda la matriz; véase la sección "Flags" a continuación.

SD_BUS_METHOD_WITH_ARGS_OFFSET(), SD_BUS_METHOD_WITH_ARGS()

Declara un método con el nombre member, argumentos args y resultado result. args espera una secuencia de pares tipo/nombre envueltas con la macro SD_BUS_ARGS(). Los elementos en índices pares de este listado describen los tipos de los argumentos del método. La firma del parámetro del método es la concatenación de todos los literales de cadena en índices pares de args. Si un método no tiene parámetros, pasa SD_BUS_NO_ARGS a args. Los elementos en índices impares describen los nombres de los argumentos del método. result espera una secuencia de pares tipo/nombre envueltas con la macro SD_BUS_RESULT() en el mismo formato que SD_BUS_ARGS(). La firma del resultado del método es la concatenación de todos los literales de cadena en índices pares de result. Si un método no tiene resultado, pasa SD_BUS_NO_RESULT a result. Nota: los tipos de argumentos deben ser literales de cadena entre comillas y los nombres de argumentos deben ser literales de cadena sin comillas. Vea más adelante un ejemplo completo.

La función de handler handler debe ser del tipo sd_bus_message_handler_t. Se llamará para manejar los mensajes que invocan este método. Recibe un puntero que es el parámetro userdata pasado a la función de registro desplazado por offset bytes. Esto puede usarse para pasar punteros a diferentes campos en la misma estructura a diferentes métodos de vtable. Para enviar una respuesta desde handler, llama a sd_bus_reply_method_return(3) con el mensaje que fue invocado por la callback. El parámetro flags es una combinación de flags, ver más abajo.

SD_BUS_METHOD_WITH_ARGS() es un abreviatura de llamar a SD_BUS_METHOD_WITH_ARGS_OFFSET() con un desplazamiento de cero.

SD_BUS_METHOD_WITH_NAMES_OFFSET(), SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET(), SD_BUS_METHOD()

Declara un método con el nombre member, firma de parámetros signature y resultado result. Los parámetros in_names y out_names especifican los nombres de los argumentos de entrada y de salida en la firma de la función. in_names y out_names deben crearse con la macro SD_BUS_PARAM(), ver más abajo. En todo lo demás, esta macro funciona exactamente como SD_BUS_METHOD_WITH_ARGS_OFFSET().

SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET() y SD_BUS_METHOD() son variantes que especifican un desplazamiento cero (userdata no cambia), dejan los nombres sin definir (es decir, sin nombres de parámetros) o ambas.

Prefiere usar SD_BUS_METHOD_WITH_ARGS_OFFSET() y SD_BUS_METHOD_WITH_ARGS() sobre estas macros, ya que permiten especificar tipos de argumentos y nombres junto con ellos, lo cual es menos propenso a errores que especificar primero todos los tipos de argumentos y luego los nombres de argumentos.

SD_BUS_SIGNAL_WITH_ARGS()

Declara un sinal con el nombre member y argumentos args. args espera una secuencia de pares tipo/nombre envueltas con la macro SD_BUS_ARGS(). Los elementos en índices pares de este listado describen los tipos de los argumentos del sinal. La firma de parámetro del sinal es la concatenación de todos los literales de cadena en índices pares de args. Si un sinal no tiene parámetros, pasa SD_BUS_NO_ARGS a args. Los elementos en índices impares describen los nombres de los argumentos del sinal. El parámetro flags es una combinación de flags. Véase más abajo un ejemplo completo.

SD_BUS_SIGNAL_WITH_NAMES(), SD_BUS_SIGNAL()

Declara un sinal con el nombre member, firma de parámetro signature y nombres de argumentos names. names debe crearse con la macro SD_BUS_PARAM(), ver más abajo. El parámetro flags es una combinación de flags.

SD_BUS_SIGNAL() es equivalente a SD_BUS_SIGNAL_WITH_NAMES() con el parámetro names sin definir (es decir, sin nombres de parámetros).

Prefiere usar SD_BUS_SIGNAL_WITH_ARGS() sobre estas macros, ya que permite especificar tipos de argumentos y nombres junto con ellos, lo cual es menos propenso a errores que especificar primero todos los tipos de argumentos y luego los nombres de argumentos.

SD_BUS_WRITABLE_PROPERTY(), SD_BUS_PROPERTY()

Declara una propiedad con el nombre member y firma de valor signature. Los parámetros get y set son los métodos de getter y setter. Se llaman con un puntero que es el parámetro userdata pasado a la función de registro desplazado por offset bytes. Esto puede usarse para pasar punteros a diferentes campos en la misma estructura a diferentes setters y getters en el mismo vtable. El parámetro flags es una combinación de flags, ver más abajo.

Los métodos de getter y setter pueden omitirse (específicos como NULL), si la propiedad es uno de los tipos básicos o "as" en caso de propiedades de solo lectura. En estos casos, los parámetros userdata y offset deben apuntar juntos a una variable válida del tipo correspondiente. Se proporcionan por defecto un setter y un getter, que simplemente copian el argumento entre esta variable y el mensaje.

SD_BUS_PROPERTY() se usa para definir una propiedad de solo lectura.

SD_BUS_PARAM()

Los nombres de los parámetros deben ser envueltos con esta macro, como se muestra en el ejemplo a continuación.

Flags

El parámetro flags se usa para especificar una combinación de anotaciones de D-Bus[1].

SD_BUS_VTABLE_DEPRECATED

Marca esta entrada del vtable como obsoleta usando la anotación org.freedesktop.DBus.Deprecated en los datos de introspección. Si se especifica para SD_BUS_VTABLE_START(), la anotación se aplica al interfaz que lo envuelve.

SD_BUS_VTABLE_HIDDEN

Marca esta entrada del vtable como oculta. No se mostrará en los datos de introspección. Si se especifica para SD_BUS_VTABLE_START(), todos los elementos de la matriz están ocultos.

SD_BUS_VTABLE_METHOD_NO_REPLY

Marca esta entrada del vtable como un método que no devuelve una respuesta usando la anotación org.freedesktop.DBus.Method.NoReply en los datos de introspección.

SD_BUS_VTABLE_PROPERTY_CONST, SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE, SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION

Estos tres flags corresponden a diferentes valores de la anotación org.freedesktop.DBus.Property.EmitsChangedSignal, que especifica si se emite el sinal org.freedesktop.DBus.Properties.PropertiesChanged cuando la propiedad cambia. SD_BUS_VTABLE_PROPERTY_CONST corresponde a const y significa que la propiedad nunca cambia durante la vida del objeto al que pertenece, por lo que no se debe emitir ningún sinal. SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE corresponde a true y significa que se emite el sinal. SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION corresponde a invalidates y significa que el sinal se emite, pero el valor no se incluye en el sinal.

SD_BUS_VTABLE_PROPERTY_EXPLICIT

Marca esta entrada de propiedad del vtable como que requiere una solicitud explícita para que se muestre el valor (generalmente porque el valor es grande o lento de calcular). Esta entrada no puede combinarse con SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE y no se mostrará por defecto en listas de propiedades (por ejemplo, busctl introspect). Esto corresponde a la anotación org.freedesktop.systemd1.Explicit en los datos de introspección.

SD_BUS_VTABLE_SENSITIVE

Marca esta entrada de método del vtable como que procesa datos sensibles. Cuando está establecido, los mensajes de llamada de métodos y sus respuestas de salida se marcan como sensibles usando sd_bus_message_sensitive(3), por lo que se eliminan de la memoria cuando se liberan.

SD_BUS_VTABLE_ABSOLUTE_OFFSET

sd_bus_add_object_vtable, sd_bus_add_fallback_vtable, sd_bus_add_method, sd_bus_add_property, sd_bus_add_signal, sd_bus_add_filter, sd_bus_slot_add_filter, sd_bus_add_method_abstract, sd_bus_add_property_abstract, sd_bus_add_signal_abstract - Create D-Bus service objects and methods

sd_bus_add_object_vtable, sd_bus_add_fallback_vtable, sd_bus_add_method, sd_bus_add_property, sd_bus_add_signal, sd_bus_add_filter, sd_bus_slot_add_filter, sd_bus_add_method_abstract, sd_bus_add_property_abstract, sd_bus_add_signal_abstract — Add a D-Bus object to a bus

sd_bus_add_object_vtable(3), sd_bus_add_fallback_vtable(3), sd_bus_add_method(3), sd_bus_add_property(3), sd_bus_add_signal(3), sd_bus_add_filter(3), sd_bus_slot_add_filter(3), sd_bus_add_method_abstract(3), sd_bus_add_property_abstract(3), sd_bus_add_signal_abstract(3)

These functions are used to register service objects on a D-Bus connection. They are used by bus implementors to expose interfaces and methods to other processes on the bus.

The functions ending in _abstract are convenience wrappers that do not take a user data pointer, and are intended for objects that are managed by a single logic instance.

The functions ending in _filter are used to register filters. These are handlers that are invoked before any other registered handlers, and can be used to pre-process requests or reject them entirely.

The core concept is the sd_bus_vtable, an array of entries describing the methods, signals, and properties an object implements. This array is passed to sd_bus_add_object_vtable() or sd_bus_add_fallback_vtable().

The last entry in the vtable must be SD_BUS_VTABLE_END.

The user data pointer specified in the call to sd_bus_add_object_vtable() or sd_bus_add_fallback_vtable() is passed as the second argument (userdata) to all handler functions associated with vtable entries.

The handler functions associated with vtable entries are called with a pointer to the specific vtable entry that matched the incoming message as the third argument (this is different from older interfaces like the older D-Bus API which passed the user data pointer plus an offset).

sd_bus_add_object_vtable

Adds a new object implementing the specified interface to the bus. Any existing object at the given path is removed first. This function might block.

The path parameter specifies the object path on the bus, interface the name of the interface implemented by the object, vtable the table of methods, signals and properties, and userdata is a pointer to arbitrary user data that will be passed to all handler functions.

sd_bus_add_fallback_vtable

Similar to sd_bus_add_object_vtable(), but the vtable is only added if no other object or fallback handler has been registered for the specified object path yet.

This is useful for implementing default handlers for entire sub-trees of the object path hierarchy.

sd_bus_add_method

This is a convenience function to add a single method to an existing object. It is equivalent to adding a single entry to a vtable and passing it to sd_bus_add_object_vtable().

The method parameter is the name of the method, signature the D-Bus signature of the arguments, reply_signature the D-Bus signature of the return value, handler the callback function, and userdata is the user data pointer passed to the handler.

sd_bus_add_property

This is a convenience function to add a single property to an existing object. It is equivalent to adding a single entry to a vtable and passing it to sd_bus_add_object_vtable().

The property parameter is the name of the property, signature the D-Bus signature of the property value, getter the callback function for reading the property, setter the callback function for writing the property, and userdata is the user data pointer passed to the handlers.

Either getter or setter may be NULL if the property is read-only or write-only, respectively.

sd_bus_add_signal

This is a convenience function to add a single signal to an existing object. It is equivalent to adding a single entry to a vtable and passing it to sd_bus_add_object_vtable().

The signal parameter is the name of the signal, and signature the D-Bus signature of the signal arguments.

sd_bus_add_filter

Adds a filter to the bus. Filters are invoked before any other handlers and can be used to intercept or reject messages.

The type specifies the type of messages to filter (e.g. `SD_BUS_MESSAGE_METHOD_CALL`), match a match string (see sd_bus_path_encode(3)), handler the filter callback function, and userdata the user data pointer passed to the handler.

The handler function should return 1 to allow the message to proceed, or 0 to block it. It can also set an error and return 0 to reject the message with that error.

sd_bus_slot_add_filter

Similar to sd_bus_add_filter(), but adds the filter to a specific bus slot. This allows the filter to be more easily managed and removed.

sd_bus_add_method_abstract

Identical to sd_bus_add_method(), but does not take a userdata argument. This is useful for simple methods where the handler does not need access to any per-object state.

sd_bus_add_property_abstract

Identical to sd_bus_add_property(), but does not take a userdata argument.

sd_bus_add_signal_abstract

Identical to sd_bus_add_signal(), but does not take a userdata argument.

Vtable Entries

The following macros are used to define entries in an sd_bus_vtable array:

SD_BUS_VTABLE_START(flags)

Marks the beginning of the vtable. The flags parameter is unused and should be 0.

SD_BUS_VTABLE_END

Marks the end of the vtable. This entry is mandatory.

SD_BUS_METHOD(name, signature, reply_signature, handler)

Declares a method with the given name, argument signature, reply signature and handler function.

SD_BUS_METHOD_WITH_NAMES(name, signature, arg_names, reply_signature, reply_arg_names, handler)

Same as SD_BUS_METHOD(), but also allows specifying names for arguments in the signature. The arg_names and reply_arg_names parameters are space-separated lists of argument names.

SD_BUS_METHOD_WITH_OFFSET(name, signature, reply_signature, handler, offset)

Same as SD_BUS_METHOD(), but the handler is invoked with the user data pointer plus the specified byte offset. This is useful for accessing members of a struct.

SD_BUS_METHOD_WITH_ARGS(name, args, result, handler)

A more modern way to declare a method. args and result are lists of arguments/results using SD_BUS_ARG() or SD_BUS_ARGS().

SD_BUS_METHOD_WITH_ARGS_OFFSET(name, args, result, handler, offset)

Same as SD_BUS_METHOD_WITH_ARGS(), but takes an offset like SD_BUS_METHOD_WITH_OFFSET().

SD_BUS_SIGNAL(name, signature, flags)

Declares a signal with the given name and argument signature.

SD_BUS_SIGNAL_WITH_NAMES(name, signature, arg_names, flags)

Same as SD_BUS_SIGNAL(), but allows specifying names for arguments.

SD_BUS_SIGNAL_WITH_ARGS(name, args, flags)

A more modern way to declare a signal. args is a list of arguments using SD_BUS_ARG() or SD_BUS_ARGS().

SD_BUS_WRITABLE_PROPERTY(name, signature, getter, setter, offset, flags)

Declares a read-write property. getter and setter are the handler functions for reading and writing the property, respectively. If a handler is not needed, pass NULL. The offset is the offset into the userdata structure where the property value is stored.

SD_BUS_READONLY_PROPERTY(name, signature, getter, offset, flags)

Declares a read-only property. getter is the handler function for reading the property.

SD_BUS_WRITEONLY_PROPERTY(name, signature, setter, offset, flags)

Declares a write-only property. setter is the handler function for writing the property.

SD_BUS_EMITS_CHANGED_SIGNAL(interface, properties, signal_name)

Can be used with property entries to specify that a `PropertiesChanged` signal should be emitted when the property is changed. interface is the interface name, properties is a comma-separated list of property names that trigger the signal, and signal_name is the name of the signal to emit (usually `PropertiesChanged`).

SD_BUS_EMITS_INVALIDATION_SIGNAL(interface, properties, signal_name)

Similar to SD_BUS_EMITS_CHANGED_SIGNAL(), but specifies that an `Invalidated` signal should be emitted.

SD_BUS_VTABLE_DEPRECATED

Marks this entry as deprecated. Introspection data will reflect this.

SD_BUS_VTABLE_UNPRIVILEGED

Marks this entry as unprivileged. Access to privileged entries is limited to users with appropriate capabilities, see SD_BUS_VTABLE_CAPABILITY() below. If not specified, entries are considered privileged by default.

SD_BUS_VTABLE_HIDDEN

Marks this entry as hidden. It will not be visible in introspection data.

SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE

When used with property entries, this flag indicates that the property's value change should trigger a `PropertiesChanged` signal. The signal will be emitted automatically by the bus implementation. The interface name and properties for the signal can be specified using SD_BUS_EMITS_CHANGED_SIGNAL(). If no interface is specified, the interface of the property itself is used.

SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION

When used with property entries, this flag indicates that the property's value change should trigger an `Invalidated` signal. The signal will be emitted automatically by the bus implementation. The interface name and properties for the signal can be specified using SD_BUS_EMITS_INVALIDATION_SIGNAL(). If no interface is specified, the interface of the property itself is used.

SD_BUS_ARG(type, name)

Defines a single argument for a method or signal. type is the D-Bus type signature, and name is the argument name.

SD_BUS_ARGS(arg1, arg2, ...)

Defines a list of arguments for a method or signal. Each argument is defined using SD_BUS_ARG().

The offset parameter passed to handler functions is determined slightly differently: instead of adding the offset parameter of the entry to the user data pointer specified during vtable registration, the offset is passed directly, converted to a pointer, without taking the user data pointer specified during vtable registration into account.

SD_BUS_VTABLE_CAPABILITY(capability)

Access to this vtable entry will be allowed if the calling process has the capability capability, as described in sd_bus_query_sender_privilege(3). If used for SD_BUS_VTABLE_START(), provides a default for all entries in the array. If not specified, either for an individual entry or the whole array, CAP_SYS_ADMIN is checked by default. See capabilities(7) for information about capabilities.

Note that vtable entries may be marked as unprivileged and the whole bus may be marked as trusted, see the discussion of SD_BUS_VTABLE_UNPRIVILEGED below.

SD_BUS_VTABLE_UNPRIVILEGED

Mark this vtable entry as unprivileged. Access to privileged entries is limited to users with appropriate capabilities as described above. In practice many vtable entries are marked as unprivileged, and either are open to everyone, or the decision whether to allow access is taken later, e.g. by delegating to polkit[2].

The whole bus may be marked as trusted, in which case annotations at the entry level are ignored, see sd_bus_set_trusted(3).

When not specified, the org.freedesktop.systemd1.Privileged annotation with value "true" will be shown in introspection data.

SD_BUS_VTABLE_UNPRIVILEGED may not be applied to read-only properties, but read access (to both read-only and writable properties) is always unrestricted.

Note that this page describes checks implemented in the D-Bus client. The D-Bus server has an additional policy that may permit or deny connections, see "CONFIGURATION FILE" in dbus-daemon(1).

Example 1. Create a simple listener on the bus

/* SPDX-License-Identifier: MIT-0 */
#define _GNU_SOURCE 1
#include <errno.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdlib.h>
#include <stdio.h>
#include <systemd/sd-bus.h>
#define _cleanup_(f) __attribute__((cleanup(f)))
typedef struct object {
  char *name;
  uint32_t number;
} object;
static int method(sd_bus_message *m, void *userdata, sd_bus_error *error) {
  int r;
  printf("Got called with userdata=%p\n", userdata);
  if (sd_bus_message_is_method_call(m,
                                    "org.freedesktop.systemd.VtableExample",
                                    "Method4"))
    return 1;
  const char *string;
  r = sd_bus_message_read(m, "s", &string);
  if (r < 0) {
    fprintf(stderr, "sd_bus_message_read() failed: %s\n", strerror(-r));
    return 0;
  }
  r = sd_bus_reply_method_return(m, "s", string);
  if (r < 0) {
    fprintf(stderr, "sd_bus_reply_method_return() failed: %s\n", strerror(-r));
    return 0;
  }
  return 1;
}
static const sd_bus_vtable vtable[] = {
        SD_BUS_Vtable_START(0),
        SD_BUS_METHOD(
            "Method1", "s", "s", method, 0),
        SD_BUS_METHOD_WITH_NAMES_OFFSET(
            "Method2",
            "so", SD_BUS_PARAM(string) SD_BUS_PARAM(path),
            "s", SD_BUS_PARAM(returnstring),
            method, offsetof(object, number),
            SD_BUS_VTABLE_DEPRECATED),
        SD_BUS_METHOD_WITH_ARGS_OFFSET(
            "Method3",
            SD_BUS_ARGS("s", string, "o", path),
            SD_BUS_RESULT("s", returnstring),
            method, offsetof(object, number),
            SD_BUS_VTABLE_UNPRIVILEGED),
        SD_BUS_METHOD_WITH_ARGS(
            "Method4",
            SD_BUS_NO_ARGS,
            SD_BUS_NO_RESULT,
            method,
            SD_BUS_VTABLE_UNPRIVILEGED),
        SD_BUS_SIGNAL(
            "Signal1",
            "so",
            0),
        SD_BUS_SIGNAL_WITH_NAMES(
            "Signal2",
            "so", SD_BUS_PARAM(string) SD_BUS_PARAM(path),
            0),
        SD_BUS_SIGNAL_WITH_ARGS(
            "Signal3",
            SD_BUS_ARGS("s", string, "o", path),
            0),
        SD_BUS_WRITABLE_PROPERTY(
            "AutomaticStringProperty", "s", NULL, NULL,
            offsetof(object, name),
            SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE),
        SD_BUS_WRITABLE_PROPERTY(
            "AutomaticIntegerProperty", "u", NULL, NULL,
            offsetof(object, number),
            SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION),
        SD_BUS_VTABLE_END
};
int main(int argc, char **argv) {
  _cleanup_(sd_bus_flush_close_unrefp) sd_bus *bus = NULL;
  int r;
  sd_bus_default(&bus);
  object object = { .number = 666 };
  object.name = strdup("name");
  if (!object.name) {
    fprintf(stderr, "OOM\n");
    return EXIT_FAILURE;
  }
  r = sd_bus_add_object_vtable(bus, NULL,
                               "/org/freedesktop/systemd/VtableExample",
                               "org.freedesktop.systemd.VtableExample",
                               vtable,
                               &object);
  if (r < 0) {
    fprintf(stderr, "sd_bus_add_object_vtable() failed: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  r = sd_bus_request_name(bus,
                          "org.freedesktop.systemd.VtableExample",
                          0);
  if (r < 0) {
    fprintf(stderr, "sd_bus_request_name() failed: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  for (;;) {
    r = sd_bus_wait(bus, UINT64_MAX);
    if (r < 0) {
      fprintf(stderr, "sd_bus_wait() failed: %s\n", strerror(-r));
      return EXIT_FAILURE;
    }
    r = sd_bus_process(bus, NULL);
    if (r < 0) {
      fprintf(stderr, "sd_bus_process() failed: %s\n", strerror(-r));
      return EXIT_FAILURE;
    }
  }
  r = sd_bus_release_name(bus, "org.freedesktop.systemd.VtableExample");
  if (r < 0) {
    fprintf(stderr, "sd_bus_release_name() failed: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  free(object.name);
  return 0;
}

RETURN VALUE

On success, sd_bus_add_object_vtable() and sd_bus_add_fallback_vtable() return a non-negative integer. On failure, they return a negative errno-style error code.

Errors

Returned errors may indicate the following problems:

-EINVAL

One of the required parameters is NULL or invalid. A reserved D-Bus interface was passed as the interface parameter.

-ENOPKG

The bus cannot be resolved.

-ECHILD

The bus was created in a different process, library or module instance.

-ENOMEM

Memory allocation failed.

-EPROTOTYPE

sd_bus_add_object_vtable() and sd_bus_add_fallback_vtable() have been both called for the same bus object path, which is not allowed.

-EEXIST

This vtable has already been registered for this interface and path.

DESCRIPTION

These functions may be used to introspect D-Bus methods. They allow querying information about a method, such as its name, interface, path, arguments, and return values.

The sd_bus_method_info_lookup() function is used to find a method with a specific name within a given interface, path, and bus.

The sd_bus_method_info_get_args(), sd_bus_method_info_get_arg_by_name(), sd_bus_method_info_get_arg_by_offset(), and sd_bus_method_info_get_all_args() functions are used to retrieve information about the method's arguments.

The sd_bus_method_info_get_return_args(), sd_bus_method_info_get_return_arg_by_name(), sd_bus_method_info_get_return_arg_by_offset(), and sd_bus_method_info_get_return_args_for_signature() functions are used to retrieve information about the method's return values.

The sd_bus_method_info_get_interface(), sd_bus_method_info_get_name(), sd_bus_method_info_get_num_args(), sd_bus_method_info_get_path(), sd_bus_method_info_get_signature(), and sd_bus_method_info_get_transient() functions provide basic information about the method.

EXAMPLES

Lookup a method and get its arguments:

    sd_bus_method_info *method_info;
    sd_bus_arg_info *arg_info;
    int r;

    r = sd_bus_method_info_lookup(bus, "/org/example/Object", "org.example.Interface", "MyMethod", &method_info);
    if (r < 0) {
        fprintf(stderr, "Failed to lookup method: %s\n", strerror(-r));
        goto finish;
    }

    r = sd_bus_method_info_get_args(method_info, &arg_info);
    if (r < 0) {
        fprintf(stderr, "Failed to get method arguments: %s\n", strerror(-r));
        goto finish;
    }

    // Process arg_info...

    finish:
    sd_bus_method_info_unref(method_info);

RETURN VALUE

On success, these functions return 0, or a pointer to the requested information. On failure, they return a negative error number.

NOTES

The returned pointers (except for those returned by sd_bus_method_info_lookup()) are owned by the info object and must not be freed. They are only valid as long as info is valid.

The libsystemd library is available as a shared library, which can be compiled against and linked to with the libsystemd pkg-config(1) file.

The code described here uses getenv(3), which is declared to be not multi-thread-safe. This means that the code calling the functions described here must not call setenv(3) from a parallel thread. It is recommended to only do calls to setenv() from an early phase of the program when no other threads have been started.
