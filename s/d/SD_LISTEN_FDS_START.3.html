SD_LISTEN_FDS(3) sd_listen_fds SD_LISTEN_FDS(3)

NOMBRE

sd_listen_fds, sd_listen_fds_with_names, SD_LISTEN_FDS_START - Comprobar descriptores de archivo pasados por el gestor del sistema

SINOPSIS

#include <systemd/sd-daemon.h>
#define SD_LISTEN_FDS_START 3

int sd_listen_fds(int unset_environment);

int sd_listen_fds_with_names(int unset_environment, char*** names);

DESCRIPCIÓN

sd_listen_fds() puede ser invocada por un demonio para comprobar descriptores de archivo pasados por el gestor de servicios como parte de la lógica de activación basada en sockets y de almacenamiento de descriptores de archivo. Devuelve el número de descriptores de archivo recibidos. Si no se han recibido descriptores de archivo, se devuelve cero. El primer descriptor de archivo se puede encontrar en el descriptor de archivo número 3 (es decir, SD_LISTEN_FDS_START), los descriptores restantes siguen en 4, 5, 6, ..., si los hay.

Los descriptores de archivo pasados de esta manera pueden ser cerrados a voluntad por los procesos que los reciben: depende de los propios procesos cerrarlos después de su uso o dejarlos abiertos hasta que el proceso termine (en cuyo caso el kernel los cierra automáticamente). Tenga en cuenta que los descriptores de archivo recibidos por los demonios son duplicados de los descriptores de archivo que el gestor de servicios asignó y enlazó originalmente y de los cuales mantiene continuamente una copia (excepto si se usa Accept=yes). Esto significa que cualquier cambio en las opciones del socket y otros cambios realizados en los sockets también serán visibles para el gestor de servicios. Lo más importante es que, en general, no es una buena idea invocar shutdown(2) en dichos sockets, ya que cerrará la comunicación en el descriptor de archivo que el gestor de servicios tiene para el mismo socket. Tenga en cuenta también que si un demonio se reinicia (y sus sockets asociados no se reinician), recibirá descriptores de archivo para los mismos sockets que en las invocaciones anteriores, por lo que todas las opciones de socket aplicadas entonces seguirán aplicándose.

Si un demonio recibe más de un descriptor de archivo, se pasarán en el mismo orden que se configuran en el archivo de unidad de socket de systemd (ver systemd.socket(5) para más detalles) — si hay solo un archivo de este tipo (ver más abajo). No obstante, se recomienda verificar los tipos de socket correctos antes de utilizarlos. Para simplificar esta verificación, se proporcionan las funciones sd_is_fifo(3), sd_is_socket(3), sd_is_socket_inet(3), sd_is_socket_unix(3). Con el fin de maximizar la flexibilidad, se recomienda realizar estas comprobaciones lo más flexibles posible sin permitir configuraciones incorrectas. Es decir, a menudo, el número de puerto real al que está enlazado un socket importa poco para que el servicio funcione, por lo que no debe verificarse. Por otro lado, si un socket es un socket de datagrama o de flujo importa mucho para la lógica del programa más común y debe verificarse.

Esta llamada a función establecerá la bandera FD_CLOEXEC para todos los descriptores de archivo pasados para evitar su herencia posterior a los hijos del proceso que llama.

Si múltiples unidades de socket activan el mismo servicio, el orden de los descriptores de archivo pasados a su proceso principal no está definido. Si se han pasado descriptores de archivo adicionales al gestor de servicios utilizando mensajes "FDSTORE=1" de sd_pid_notify_with_fds(3), estos descriptores de archivo se pasan al final, en orden arbitrario y sin duplicados.

Si el parámetro unset_environment es distinto de cero, sd_listen_fds() eliminará las variables de entorno $LISTEN_FDS, $LISTEN_PID y $LISTEN_FDNAMES antes de devolver el resultado (independientemente de si la llamada a la función tuvo éxito o no). Las llamadas posteriores a sd_listen_fds() devolverán entonces cero, pero las variables ya no serán heredadas por los procesos hijo.

sd_listen_fds_with_names() es como sd_listen_fds(), pero opcionalmente también devuelve una matriz de cadenas con nombres de identificación para los descriptores de archivo pasados, si están disponibles y el parámetro names no es nulo (NULL). Esta información se lee de la variable $LISTEN_FDNAMES, que puede contener una lista de nombres separados por dos puntos. Para los servicios activados por socket, estos nombres se pueden configurar con el ajuste FileDescriptorName= en los archivos de unidad de socket, ver systemd.socket(5) para más detalles. Para los descriptores de archivo insertados en el almacén de descriptores de archivo (ver más arriba), el nombre se establece a través del campo FDNAME= transmitido a través de sd_pid_notify_with_fds(). El caso de uso principal para estos nombres son los servicios que aceptan una variedad de descriptores de archivo que no son reconocibles solo con funciones como sd_is_socket(), y por lo tanto requieren identificación a través de un nombre. Se recomienda depender de los descriptores de archivo con nombre solo si la identificación a través de sd_is_socket() y llamadas relacionadas no es suficiente. Tenga en cuenta que los nombres utilizados no son únicos de ninguna manera. La matriz de cadenas devuelta tiene tantas entradas como descriptores de archivo se hayan recibido, más un puntero final NULL que termina la matriz. El llamante debe liberar la matriz en sí y cada uno de sus elementos con la llamada free() de libc después de su uso. Si el parámetro names es NULL, la llamada es completamente equivalente a sd_listen_fds().

Bajo condiciones específicas, se devuelven los siguientes nombres de descriptor de archivo automáticos:

Tabla 1.  Nombres especiales

Nombre Descripción
"unknown" El proceso no recibió un nombre para el descriptor de archivo específico del gestor de servicios.
"stored" El descriptor de archivo se origina en el almacén de descriptores de archivo por servicio del gestor de servicios, y el campo FDNAME= estaba ausente cuando el descriptor de archivo se envió al gestor de servicios.
"connection" El servicio se activó en estilo por conexión utilizando Accept=yes en el archivo de unidad de socket, y el descriptor de archivo es el socket de conexión.

Para más información sobre el almacén de descriptores de archivo, consulte la descripción general
del Almacén de Descriptores de Archivo[1].

VALOR DE RETORNO

En caso de error, estas llamadas devuelven un código de error negativo estilo errno. Si $LISTEN_FDS/$LISTEN_PID no estaba configurado o no estaba correctamente configurado para este demonio y, por lo tanto, no se recibieron descriptores de archivo, se devuelve 0. De lo contrario, se devuelve el número de descriptores de archivo pasados. La aplicación puede encontrarlos a partir del descriptor de archivo SD_LISTEN_FDS_START, es decir, el descriptor de archivo 3.

NOTAS

Las funciones descritas aquí están disponibles como una biblioteca compartida, que se puede compilar y enlazar con el archivo libsystemd de pkg-config(1).

El código descrito aquí utiliza getenv(3), que se declara no ser seguro para hilos (thread-safe). Esto significa que el código que llama a las funciones descritas aquí no debe llamar a setenv(3) desde un hilo paralelo. Se recomienda realizar llamadas a setenv() solo en una fase temprana del programa cuando no se hayan iniciado otros hilos.

Internamente, sd_listen_fds() comprueba si la variable de entorno $LISTEN_PID coincide con el PID del demonio. Si no es así, devuelve inmediatamente. De lo contrario, analiza el número pasado en la variable de entorno $LISTEN_FDS, luego establece la bandera FD_CLOEXEC para el número de descriptores de archivo analizado comenzando desde SD_LISTEN_FDS_START. Finalmente, devuelve el número analizado. sd_listen_fds_with_names() hace lo mismo pero también analiza $LISTEN_FDNAMES si está configurado.

Estas funciones no están diseñadas para servicios que especifican StandardInput=socket, ya que la variable $LISTEN_FDS no se establece en su entorno.

AMBIENTE

$LISTEN_PID, $LISTEN_FDS, $LISTEN_FDNAMES

Establecidas por el gestor de servicios para procesos supervisados que utilizan activación basada en sockets. Esta variable de entorno especifica los datos que analizan sd_listen_fds() y sd_listen_fds_with_names(). Ver más arriba para más detalles.
