NOMBRE

sd_journal_print, sd_journal_printv, sd_journal_send, sd_journal_sendv, sd_journal_perror, SD_JOURNAL_SUPPRESS_LOCATION, sd_journal_print_with_location, sd_journal_printv_with_location, sd_journal_send_with_location, sd_journal_sendv_with_location, sd_journal_perror_with_location - Enviar entradas de registro a la bitácora del sistema (journal)

SINOPSIS

#include <systemd/sd-journal.h>

int sd_journal_print(int prioridad, const char *formato, ...);

int sd_journal_printv(int prioridad, const char *formato, va_list ap);

int sd_journal_printv_with_location(int prioridad, const char *archivo, const char *linea, const char *func, const char *formato, va_list ap);

int sd_journal_send_with_location(const char *archivo, const char *linea, const char *func, const char *formato, ...);

int sd_journal_sendv_with_location(const char *archivo, const char *linea, const char *func, const struct iovec *iov, int n);

int sd_journal_perror_with_location(const char *archivo, const char *linea, const char *func, const char *mensaje);

DESCRIPCIÓN

sd_journal_print() puede ser utilizado para enviar entradas de registro simples de texto plano a la bitácora del sistema (journal). El primer argumento es un valor de prioridad. Seguido de una cadena de formato y sus parámetros, similar a printf(3) o syslog(3). Tenga en cuenta que actualmente el mensaje resultante se truncará a LINE_MAX - 8. El valor de prioridad es uno de LOG_EMERG, LOG_ALERT, LOG_CRIT, LOG_ERR, LOG_WARNING, LOG_NOTICE, LOG_INFO, LOG_DEBUG, según se definen en syslog.h, consulte syslog(3) para más detalles. Se recomienda utilizar esta llamada para enviar mensajes de registro en el idioma de la aplicación o en el idioma del sistema y en formato UTF-8, pero no se aplican dichas restricciones. Tenga en cuenta que los mensajes de registro escritos con esta función generalmente no se espera que terminen en un carácter de nueva línea. Sin embargo, como todo el espacio en blanco al final (incluyendo espacios, nuevas líneas, tabuladores y retornos de carro) se elimina automáticamente de la cadena registrada, es aceptable especificar uno (o más). Las líneas vacías (después de la eliminación del espacio en blanco final) se suprimen. En las líneas no vacías, el espacio en blanco inicial (así como el espacio en blanco interior) se deja sin modificar.

sd_journal_printv() es similar a sd_journal_print() pero toma una lista de argumentos variable encapsulada en un objeto de tipo va_list (consulte stdarg(3) para más información) en lugar de la cadena de formato. Por lo demás, su comportamiento es equivalente.

sd_journal_send() puede ser utilizada para enviar entradas de registro estructuradas a la bitácora del sistema. Toma una serie de cadenas de formato, cada una seguida inmediatamente por sus parámetros asociados, terminadas por NULL. Las cadenas pasadas deben tener el formato "VARIABLE=valor". El nombre de la variable debe estar en mayúsculas y consistir únicamente en caracteres, números y guiones bajos, y no puede comenzar con un guion bajo. (Se ignorarán todas las asignaciones que no sigan esta sintaxis). El valor puede ser de cualquier tamaño y formato. Se recomienda encarecidamente enviar solo cadenas de texto formateadas en la codificación de caracteres UTF-8, y enviar campos binarios solo cuando no sea sensato formatear en cadenas UTF-8. Se definen varios campos conocidos, consulte systemd.journal-fields(7) para más detalles, pero se pueden usar campos adicionales definidos por la aplicación. A una variable se le puede asignar más de un valor por entrada. Si se utiliza esta función, se eliminará automáticamente el espacio en blanco final de cada campo formateado.

sd_journal_sendv() es similar a sd_journal_send() pero toma un array de struct iovec (según se define en uio.h, consulte readv(3) para más detalles) en lugar de la cadena de formato. Cada estructura debe hacer referencia a un campo de la entrada a enviar. El segundo argumento especifica el número de estructuras en el array. sd_journal_sendv() es particularmente útil para enviar objetos binarios a la bitácora cuando sea necesario. Tenga en cuenta que esta función no eliminará el espacio en blanco final de los campos pasados, sino que pasará los datos especificados sin modificar. Esto es diferente de sd_journal_print() y sd_journal_send() descritas anteriormente, que se basan en cadenas de formato y eliminan el espacio en blanco final.

sd_journal_perror() es similar a perror(3) y escribe un mensaje en la bitácora que consiste en la cadena pasada, seguida de ": " y una representación legible por humanos del código de error actual almacenado en errno(3). Si la cadena de mensaje se pasa como NULL o cadena vacía, solo se escribirá la representación de la cadena de error, precedida por nada. Un campo de bitácora adicional ERRNO= se incluye en la entrada que contiene el código de error numérico formateado como una cadena decimal. La prioridad de registro utilizada es LOG_ERR (3).

Tenga en cuenta que sd_journal_send() es un envoltorio alrededor de sd_journal_sendv() para facilitar su uso cuando solo se deben enviar cadenas de texto. Además, las siguientes dos llamadas son en gran medida equivalentes:

sd_journal_print(LOG_INFO, "Hola Mundo, ¡este es el PID %lu!", (unsigned long) getpid());
sd_journal_send("MESSAGE=Hola Mundo, ¡este es el PID %lu!", (unsigned long) getpid(),
                "PRIORITY=%i", LOG_INFO,
                NULL);

Tenga en cuenta que estas llamadas agregan implícitamente campos para el archivo fuente, el nombre de la función y la línea de código donde se invocaron. Esto se implementa con macros. Si esto no se desea, se puede desactivar definiendo SD_JOURNAL_SUPPRESS_LOCATION antes de incluir sd-journal.h.

sd_journal_print_with_location(), sd_journal_printv_with_location(), sd_journal_send_with_location(), sd_journal_sendv_with_location(), y sd_journal_perror_with_location() son similares a sus contrapartes sin "_with_location", pero aceptan parámetros adicionales para establecer explícitamente el nombre del archivo fuente, la función y la línea. Los argumentos "archivo" y "línea" deben contener entradas válidas de la bitácora, incluyendo el nombre de la variable, por ejemplo, "CODE_FILE=src/foo.c" y "CODE_LINE=666", mientras que "func" solo debe contener el nombre de la función, es decir, el valor sin "CODE_FUNC=". Estas variantes son principalmente útiles al escribir envoltorios personalizados, por ejemplo, en enlaces para un idioma diferente.

syslog(3) y sd_journal_print() pueden ser utilizados en gran medida de forma intercambiable en cuanto a funcionalidad. Sin embargo, tenga en cuenta que los mensajes de registro registrados a través del primero toman una ruta diferente al servidor de la bitácora que los del segundo, y por lo tanto, no se puede garantizar el orden cronológico global entre los dos flujos. El uso de sd_journal_print() tiene el beneficio de registrar la línea del código fuente, los nombres de archivo y las funciones como metadatos junto con todas las entradas, y garantizar el orden cronológico con las entradas de registro estructuradas que se generan a través de sd_journal_send(). El uso de syslog() tiene el beneficio de ser más portátil.

Estas funciones implementan un cliente para el Protocolo Nativo de la Bitácora[1].

FILTRADO DE ASIENTOS DE DIARIO

Los identificadores de campo de registro systemd.journal-fields(7) se pueden usar como modificadores para las funciones de registro de sd-journal(3). Por defecto, todos los campos de registro se envían al demonio del diario. Si se especifica uno de los siguientes identificadores de campo, ciertos campos se omitirán del mensaje de registro enviado.

SD_JOURNAL_SUPPRESS_LOCATION

No envíe los campos CODE_FILE, CODE_LINE y CODE_FUNC al diario. Es útil para reducir el tamaño de los mensajes de registro cuando la información sobre la ubicación del código fuente no es necesaria o es sensible.

SD_JOURNAL_SUPPRESS_COLOR

No envíe el campo MESSAGE_ID al diario si es una cadena que solo contiene caracteres de escape de código de color ANSI, y por lo tanto, se utiliza principalmente para la salida de la consola. Esto puede ser útil para evitar la contaminación del registro del diario con datos de formato de color de consola.

Todas las funciones de registro de sd-journal(3) (con la excepción de sd_journal_stream_fd(3)) aceptan un argumento opcional flags. Si se proporciona, este argumento debe ser un OR bit a bit de cero o más de las banderas de supresión descritas anteriormente. Si se proporciona, estas banderas anularán la configuración del sistema y garantizarán que los campos especificados no se envíen al diario del sistema. Si la variable de entorno SYSTEMD_JOURNAL_SUPPRESS está establecida, las banderas especificadas allí también se aplicarán, además de las proporcionadas explícitamente a las funciones.

Por ejemplo, para enviar un mensaje y suprimir la información de ubicación, usaría sd_journal_print(SD_JOURNAL_SUPPRESS_LOCATION, "Mi mensaje"). Para suprimir tanto la ubicación como los códigos de color, usaría sd_journal_print(SD_JOURNAL_SUPPRESS_LOCATION|SD_JOURNAL_SUPPRESS_COLOR, "Mi mensaje").

Tenga en cuenta que estas banderas solo afectan a los campos enviados al demonio del sistema systemd-journald(8). Los campos que se envían a una salida de registro alternativa, como stdout o stderr, no se ven afectados. El valor de la variable de entorno SYSTEMD_LOG_COLOR todavía controla si se imprimen los caracteres de escape de código de color ANSI cuando se escriben en la consola.

Si systemd-journald(8) no se está ejecutando (el socket no está presente), estas funciones no hacen nada y también devuelven 0.

SEGURIDAD CON HILOS

Todas las funciones aquí listadas son seguras para hilos y pueden ser llamadas en paralelo desde múltiples hilos.

sd_journal_sendv() y sd_journal_sendv_with_location() son "seguras para señales asíncronas" en el sentido de signal-safety(7).

sd_journal_print(), sd_journal_printv(), sd_journal_send(), sd_journal_perror(), y sus contrapartes con "_with_location" no son seguras para señales asíncronas.

NOTAS

Las funciones descritas aquí están disponibles como una biblioteca compartida, que se puede compilar y vincular con el archivo libsystemd pkg-config(1).

El código descrito aquí usa getenv(3), que se declara no ser seguro para hilos múltiples. Esto significa que el código que llama a las funciones descritas aquí no debe llamar a setenv(3) desde un hilo paralelo. Se recomienda realizar llamadas a setenv() solo desde una fase temprana del programa cuando no se hayan iniciado otros hilos.
