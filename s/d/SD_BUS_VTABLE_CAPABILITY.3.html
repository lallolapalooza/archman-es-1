DESCRIPCIÓN

sd_bus_add_object_vtable() se utiliza para declarar atributos para la ruta de objeto path conectada a la conexión de bus bus bajo la interfaz interface. La tabla vtable puede contener declaraciones de propiedades usando SD_BUS_PROPERTY() o SD_BUS_WRITABLE_PROPERTY(), declaraciones de métodos usando SD_BUS_METHOD(), SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET(), o SD_BUS_METHOD_WITH_NAMES_OFFSET(), y declaraciones de señales usando SD_BUS_SIGNAL_WITH_NAMES() o SD_BUS_SIGNAL(), ver abajo. El parámetro userdata contiene un puntero que se pasará a varias funciones de devolución de llamada. Puede especificarse como NULL si no es necesario ningún valor. Una interfaz puede tener cualquier número de vtables adjuntas a ella.

sd_bus_add_fallback_vtable() es similar a sd_bus_add_object_vtable(), pero se utiliza para registrar atributos de "fallback". Al buscar una declaración de atributo, primero se comprueban las rutas de objetos de bus registradas con sd_bus_add_object_vtable(). Si no se encuentra ninguna coincidencia, se comprueban las vtables de fallback para cada prefijo de la ruta de objeto de bus, es decir, con los últimos componentes separados por barras sucesiva y recursivamente eliminados. Esto permite que la vtable se utilice para un número arbitrario de objetos creados dinámicamente.

El parámetro find es una función que se utiliza para localizar el objeto de destino basándose en la ruta del objeto de bus path. Debe devolver 1 y establecer el parámetro de salida ret_found si el objeto se encuentra, devolver 0 si el objeto no se encontró, y devolver un código de error negativo de estilo errno o inicializar la estructura de error ret_error en caso de error. El puntero pasado en ret_found se utilizará como parámetro userdata para las funciones de devolución de llamada (desplazado por los desplazamientos offset según se especifica en las entradas de la vtable).

sd_bus_add_object() adjunta una devolución de llamada directa a la ruta del objeto path. Una ruta de objeto puede tener cualquier número de devoluciones de llamada adjuntas. Cada devolución de llamada se antepone a la lista de devoluciones de llamada que siempre se llaman en orden. sd_bus_add_fallback() es similar a sd_bus_add_object() pero se aplica a rutas de fallback.

sd_bus_add_filter() instala una devolución de llamada que se invoca para cada mensaje D-Bus entrante. Los filtros se pueden utilizar para manejar la lógica común a todos los mensajes recibidos por un servicio (por ejemplo, autenticación o autorización).

Cuando se recibe una solicitud, se llaman secuencialmente las devoluciones de llamada asociadas hasta que una devolución de llamada devuelve un entero distinto de cero. Deuelva cero de una devolución de llamada para dar a otras devoluciones de llamada la oportunidad de procesar la solicitud. Las devoluciones de llamada se llaman en el siguiente orden: primero, se llaman las devoluciones de llamada globales instaladas con sd_bus_add_filter(). Segundo, se llaman las devoluciones de llamada adjuntas directamente a la ruta del objeto de solicitud, seguidas de cualquier devolución de llamada de método D-Bus adjunta a la ruta del objeto de solicitud, interfaz y miembro. Finalmente, se llaman las devoluciones de llamada de propiedad adjuntas a la ruta del objeto de solicitud, interfaz y miembro. Si la devolución de llamada final devuelve cero, se produce un error

se le indica a sd-bus que el callback se hará responsable de responder a la solicitud sin forzar al callback a producir una respuesta inmediatamente. Esto permite que un callback realice cualquier número de operaciones asíncronas necesarias para construir una respuesta. Sin embargo, si la producción de una respuesta tarda demasiado, la llamada al método caducará en el llamador. Esto solo está disponible para métodos y no para propiedades.

Si se invocó un callback para manejar una solicitud que espera una respuesta y el callback devuelve un valor negativo, el valor se interpreta como un código de error negativo de estilo errno y se envía de vuelta al llamador como un error D-Bus como si se hubiera llamado a sd_bus_reply_method_errno(3). Además, todos los callbacks toman un parámetro de salida sd_bus_error que se puede usar para proporcionar información de error más detallada. Si ret_error se establece cuando el callback finaliza, el error D-Bus correspondiente se envía de vuelta al llamador como si se hubiera llamado a sd_bus_reply_method_error(3). Cualquier error almacenado en ret_error tiene prioridad sobre cualquier valor negativo devuelto por el mismo callback al determinar qué error enviar de vuelta al llamador. Utilice sd_bus_error_set(3) o una de sus variantes para establecer ret_error y devolver un entero negativo desde un callback con una sola llamada a función. Para enviar una respuesta de error después de que un callback ya haya finalizado, utilice sd_bus_reply_method_errno(3) o una de sus variantes.

Para todas las funciones, se crea una ranura de coincidencia internamente. Si el parámetro de salida slot es NULL, se crea un objeto de ranura "flotante", consulte sd_bus_slot_set_floating(3). De lo contrario, se devuelve un puntero al objeto de ranura. En ese caso, la referencia al objeto de ranura debe liberarse cuando la vtable ya no sea necesaria, consulte sd_bus_slot_unref(3).

El array sd_bus_vtable

El array consta de las estructuras de tipo sd_bus_vtable, pero nunca debe rellenarse manualmente, sino a través de una de las siguientes macros:

SD_BUS_VTABLE_START(flags), SD_BUS_VTABLE_END

Estos deben ser siempre el primer y último elemento. El parámetro flags se puede usar para establecer atributos que se aplican a todo el array; consulte la sección "Flags" a continuación.

SD_BUS_METHOD_WITH_ARGS_OFFSET(), SD_BUS_METHOD_WITH_ARGS()

Declara un método D-Bus con el nombre member, argumentos args y resultado result. args espera una secuencia de pares tipo/nombre de argumento encapsulados en la macro SD_BUS_ARGS(). Los elementos en índices pares en esta lista describen los tipos de los argumentos del método. La firma del parámetro del método es la concatenación de todas las cadenas literales en índices pares en args. Si un método no tiene parámetros, pase SD_BUS_NO_ARGS a args. Los elementos en índices impares describen los nombres de los argumentos del método. result espera una secuencia de pares tipo/nombre encapsulados en la macro SD_BUS_RESULT() en el mismo formato que SD_BUS_ARGS(). La firma del resultado del método es la concatenación de todas las cadenas literales en índices pares en result. Si un método no tiene resultado, pase SD_BUS_NO_RESULT a result. Tenga en cuenta que se espera que los tipos de argumento sean cadenas literales entre comillas y los nombres de argumento se esperan que sean cadenas literales sin comillas. Consulte a continuación un ejemplo completo.

La función de manejo handler debe ser de tipo sd_bus_message_handler_t. Se llamará para manejar los mensajes entrantes que llamen a este método. Recibe un puntero que es el parámetro userdata pasado a la función de registro desplazado por offset bytes. Esto puede usarse para pasar punteros a diferentes campos en la misma estructura de datos a diferentes métodos en la misma vtable. Para enviar una respuesta desde handler, llame a sd_bus_reply_method_return(3) con el mensaje con el que se invocó el callback. El parámetro flags es una combinación de flags, consulte a continuación.

SD_BUS_METHOD_WITH_ARGS() es una abreviatura para llamar a SD_BUS_METHOD_WITH_ARGS_OFFSET() con un desplazamiento de cero.

SD_BUS_METHOD_WITH_NAMES_OFFSET(), SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET(), SD_BUS_METHOD()

Declara un método D-Bus con el nombre member, firma de parámetro signature, firma de resultado result. Los parámetros in_names y out_names especifican los nombres de los argumentos de los argumentos de entrada y salida en la firma de la función. in_names y out_names deben crearse usando la macro SD_BUS_PARAM(), consulte a continuación. En todos los demás aspectos, esta macro se comporta exactamente igual que SD_BUS_METHOD_WITH_ARGS_OFFSET().

SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET() y SD_BUS_METHOD() son variantes que especifican desplazamiento cero (el parámetro userdata se pasa sin cambios), dejan los nombres sin establecer (es decir, sin nombres de parámetros) o ambos.

Prefiera usar SD_BUS_METHOD_WITH_ARGS_OFFSET() y SD_BUS_METHOD_WITH_ARGS() sobre estas macros, ya que permiten especificar los tipos y nombres de los argumentos uno al lado del otro, lo que es menos propenso a errores que especificar primero todos los tipos de argumentos seguidos de todos los nombres de argumentos.

SD_BUS_SIGNAL_WITH_ARGS()

Declara una señal D-Bus con el nombre member y argumentos args. args espera una secuencia de pares tipo/nombre de argumento encapsulados en la macro SD_BUS_ARGS(). Los elementos en índices pares en esta lista describen los tipos de los argumentos de la señal. La firma del parámetro de la señal es la concatenación de todas las cadenas literales en índices pares en args. Si una señal no tiene parámetros, pase SD_BUS_NO_ARGS a args. Los elementos en índices impares describen los nombres de los argumentos de la señal. El parámetro flags es una combinación de flags. Consulte a continuación un ejemplo completo.

SD_BUS_SIGNAL_WITH_NAMES(), SD_BUS_SIGNAL()

Declara una señal D-Bus con el nombre member, firma de parámetro signature y nombres de argumentos names. names debe crearse usando la macro SD_BUS_PARAM(), consulte a continuación. El parámetro flags es una combinación de flags, consulte a continuación.

SD_BUS_SIGNAL() es equivalente a SD_BUS_SIGNAL_WITH_NAMES() con el parámetro names sin establecer (es decir, sin nombres de parámetros).

Prefiera usar SD_BUS_SIGNAL_WITH_ARGS() sobre estas macros, ya que permite especificar los tipos y nombres de los argumentos uno al lado del otro, lo que es menos propenso a errores que especificar primero todos los tipos de argumentos seguidos de todos los nombres de argumentos.

SD_BUS_WRITABLE_PROPERTY(), SD_BUS_PROPERTY()

Declara una propiedad D-Bus con el nombre member y firma de valor signature. Los parámetros get y set son los métodos obtenedor y establecedor. Se llaman con un puntero que es el parámetro userdata pasado a la función de registro desplazado por offset bytes. Esto puede usarse para pasar punteros a diferentes campos en la misma estructura de datos a diferentes establecedores y obtenedores en la misma vtable. El parámetro flags es una combinación de flags, consulte a continuación.

Los métodos establecedor y obtenedor pueden omitirse (especificarse como NULL), si la propiedad es uno de los tipos básicos o "as" en caso de propiedades de solo lectura. En esos casos, los parámetros userdata y offset deben apuntar juntos a una variable válida del tipo correspondiente. Se proporcionará un establecedor y obtenedor predeterminados, que simplemente copian el argumento entre esta variable y el mensaje.

SD_BUS_PROPERTY() se utiliza para definir una propiedad de solo lectura.

Flags

El parámetro flags se utiliza para especificar una combinación de anotaciones de D-Bus[1].

SD_BUS_VTABLE_DEPRECATED

Marca esta entrada de vtable como obsoleta usando la anotación org.freedesktop.DBus.Deprecated en los datos de introspección. Si se especifica para SD_BUS_VTABLE_START(), la anotación se aplica a la interfaz que la contiene.

SD_BUS_VTABLE_HIDDEN

Oculta esta entrada de vtable. No se mostrará en los datos de introspección. Si se especifica para SD_BUS_VTABLE_START(), todas las entradas del array se ocultan.

SD_BUS_VTABLE_METHOD_NO_REPLY

Marca esta entrada de vtable como un método que no devolverá una respuesta usando la anotación org.freedesktop.DBus.Method.NoReply en los datos de introspección.

SD_BUS_VTABLE_PROPERTY_CONST, SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE, SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION

Estos tres flags corresponden a diferentes valores de la anotación org.freedesktop.DBus.Property.EmitsChangedSignal, que especifica si la señal org.freedesktop.DBus.Properties.PropertiesChanged se emite cada vez que cambia la propiedad. SD_BUS_VTABLE_PROPERTY_CONST corresponde a const y significa que la propiedad nunca cambia durante la vida útil del objeto al que pertenece, por lo que no es necesario emitir ninguna señal. SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE corresponde a true y significa que se emite la señal. SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION corresponde a invalidates y significa que se emite la señal, pero el valor no se incluye en la señal.

SD_BUS_VTABLE_PROPERTY_EXPLICIT

Marca esta entrada de propiedad de vtable como que requiere una solicitud explícita para que se muestre el valor (generalmente porque el valor es grande o lento de calcular). Esta entrada no se puede combinar con SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE y no se mostrará en las listas de propiedades de forma predeterminada (por ejemplo, busctl introspect). Esto corresponde a la anotación org.freedesktop.systemd1.Explicit en los datos de introspección.

SD_BUS_VTABLE_SENSITIVE

Marca esta entrada de método de vtable como que procesa datos sensibles. Cuando se establece, los mensajes de llamada de método entrantes y sus mensajes de respuesta salientes se marcan como sensibles usando sd_bus_message_sensitive(3), para que se borren de la memoria cuando se liberen.

VTABLE ENTRY FLAGS

The following flags can be used to modify the behavior of vtable entries:

SD_BUS_VTABLE_AUTHENTICATED(uint32_t uid)

Access to this vtable entry will be allowed only if the calling process has a UID of uid. If used for SD_BUS_VTABLE_START(), provides a default for all entries in the array. If not specified, either for an individual entry or the whole array, all UIDs are allowed by default.

SD_BUS_VTABLE_CONSTRAINT(const char *constraint)

This takes a free-form string that is added to the introspection XML for this entry. It is intended to be used by policy enforcement tools, like polkit(8), to document access constraints. It has no effect on the actual access control logic. If used for SD_BUS_VTABLE_START(), provides a default for all entries in the array.

SD_BUS_VTABLE_DEPRECATED

Mark this vtable entry as deprecated. The introspection XML will be annotated accordingly.

SD_BUS_VTABLE_OFFSET(size_t offset)

This is a modifier for method and property entries. The offset is added to the user data pointer specified during vtable registration. This is useful to get a pointer to a specific member of the user data structure.

For methods, the pointer passed to the associated handler function is determined slightly differently: instead of adding the offset parameter of the entry to the user data pointer specified during vtable registration, the offset is passed directly, converted to a pointer, without taking the user data pointer specified during vtable registration into account.

SD_BUS_VTABLE_CAPABILITY(capability)

Access to this vtable entry will be allowed if the calling process has the capability capability, as described in sd_bus_query_sender_privilege(3). If used for SD_BUS_VTABLE_START(), provides a default for all entries in the array. If not specified, either for an individual entry or the whole array, CAP_SYS_ADMIN is checked by default. See capabilities(7) for information about capabilities.

Note that vtable entries may be marked as unprivileged and the whole bus may be marked as trusted, see the discussion of SD_BUS_VTABLE_UNPRIVILEGED below.

SD_BUS_VTABLE_UNPRIVILEGED

Mark this vtable entry as unprivileged. Access to privileged entries is limited to users with appropriate capabilities as described above. In practice many vtable entries are marked as unprivileged, and either are open to everyone, or the decision whether to allow access is taken later, e.g. by delegating to polkit(8)[2].

The whole bus may be marked as trusted, in which case annotations at the entry level are ignored, see sd_bus_set_trusted(3).

When not specified, the org.freedesktop.systemd1.Privileged annotation with value "true" will be shown in introspection data.

SD_BUS_VTABLE_UNPRIVILEGED may not be applied to read-only properties, but read access (to both read-only and writable properties) is always unrestricted.

Note that this page describes checks implemented in the D-Bus client. The D-Bus server has an additional policy that may permit or deny connections, see "CONFIGURATION FILE" in dbus-daemon(1).

EXAMPLES

Example 1. Create a simple listener on the bus

/* SPDX-License-Identifier: MIT-0 */
#define _GNU_SOURCE 1
#include <errno.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdlib.h>
#include <stdio.h>
#include <systemd/sd-bus.h>
#define _cleanup_(f) __attribute__((cleanup(f)))
typedef struct object {
  char *name;
  uint32_t number;
} object;
static int method(sd_bus_message *m, void *userdata, sd_bus_error *error) {
  int r;
  printf("Got called with userdata=%p\n", userdata);
  if (sd_bus_message_is_method_call(m,
                                    "org.freedesktop.systemd.VtableExample",
                                    "Method4"))
    return 1;
  const char *string;
  r = sd_bus_message_read(m, "s", &string);
  if (r < 0) {
    fprintf(stderr, "sd_bus_message_read() failed: %s\n", strerror(-r));
    return 0;
  }
  r = sd_bus_reply_method_return(m, "s", string);
  if (r < 0) {
    fprintf(stderr, "sd_bus_reply_method_return() failed: %s\n", strerror(-r));
    return 0;
  }
  return 1;
}
static const sd_bus_vtable vtable[] = {
        SD_BUS_Vtable_START(0),
        SD_BUS_METHOD(
            "Method1", "s", "s", method, 0),
        SD_BUS_METHOD_WITH_NAMES_OFFSET(
            "Method2",
            "so", SD_BUS_PARAM(string) SD_BUS_PARAM(path),
            "s", SD_BUS_PARAM(returnstring),
            method, offsetof(object, number),
            SD_BUS_VTABLE_DEPRECATED),
        SD_BUS_METHOD_WITH_ARGS_OFFSET(
            "Method3",
            SD_BUS_ARGS("s", string, "o", path),
            SD_BUS_RESULT("s", returnstring),
            method, offsetof(object, number),
            SD_BUS_VTABLE_UNPRIVILEGED),
        SD_BUS_METHOD_WITH_ARGS(
            "Method4",
            SD_BUS_NO_ARGS,
            SD_BUS_NO_RESULT,
            method,
            SD_BUS_VTABLE_UNPRIVILEGED),
        SD_BUS_SIGNAL(
            "Signal1",
            "so",
            0),
        SD_BUS_SIGNAL_WITH_NAMES(
            "Signal2",
            "so", SD_BUS_PARAM(string) SD_BUS_PARAM(path),
            0),
        SD_BUS_SIGNAL_WITH_ARGS(
            "Signal3",
            SD_BUS_ARGS("s", string, "o", path),
            0),
        SD_BUS_WRITABLE_PROPERTY(
            "AutomaticStringProperty", "s", NULL, NULL,
            offsetof(object, name),
            SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE),
        SD_BUS_WRITABLE_PROPERTY(
            "AutomaticIntegerProperty", "u", NULL, NULL,
            offsetof(object, number),
            SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION),
        SD_BUS_VTABLE_END
};
int main(int argc, char **argv) {
  _cleanup_(sd_bus_flush_close_unrefp) sd_bus *bus = NULL;
  int r;
  sd_bus_default(&bus);
  object object = { .number = 666 };
  object.name = strdup("name");
  if (!object.name) {
    fprintf(stderr, "OOM\n");
    return EXIT_FAILURE;
  }
  r = sd_bus_add_object_vtable(bus, NULL,
                               "/org/freedesktop/systemd/VtableExample",
                               "org.freedesktop.systemd.VtableExample",
                               vtable,
                               &object);
  if (r < 0) {
    fprintf(stderr, "sd_bus_add_object_vtable() failed: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  r = sd_bus_request_name(bus,
                          "org.freedesktop.systemd.VtableExample",
                          0);
  if (r < 0) {
    fprintf(stderr, "sd_bus_request_name() failed: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  for (;;) {
    r = sd_bus_wait(bus, UINT64_MAX);
    if (r < 0) {
      fprintf(stderr, "sd_bus_wait() failed: %s\n", strerror(-r));
      return EXIT_FAILURE;
    }
    r = sd_bus_process(bus, NULL);
    if (r < 0) {
      fprintf(stderr, "sd_bus_process() failed: %s\n", strerror(-r));
      return EXIT_FAILURE;
    }
  }
  r = sd_bus_release_name(bus, "org.freedesktop.systemd.VtableExample");
  if (r < 0) {
    fprintf(stderr, "sd_bus_release_name() failed: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  free(object.name);
  return 0;
}

RETURN VALUE

On success, sd_bus_add_object_vtable() and sd_bus_add_fallback_vtable() return a non-negative integer. On failure, they return a negative errno-style error code.

Errors

Returned errors may indicate the following problems:

-EINVAL

One of the required parameters is NULL or invalid. A reserved D-Bus interface was passed as the interface parameter.

-ENOPKG

The bus cannot be resolved.

-ECHILD

The bus was created in a different process, library or module instance.

-ENOMEM

Memory allocation failed.

-EPROTOTYPE

sd_bus_add_object_vtable() and sd_bus_add_fallback_vtable() have been both called for the same bus object path, which is not allowed.

-EEXIST

This vtable has already been registered for this interface and path.

NOTES

Functions described here are

disponible como una biblioteca compartida, que puede ser compilada y enlazada con el archivo pkg-config(1) de libsystemd.

El código descrito aquí utiliza getenv(3), que se declara como no seguro para hilos múltiples. Esto significa que el código que llama a las funciones descritas aquí no debe llamar a setenv(3) desde un hilo paralelo. Se recomienda realizar las llamadas a setenv() solo desde una fase temprana del programa cuando aún no se han iniciado otros hilos.
