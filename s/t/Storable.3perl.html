NOMBRE

Storable - persistencia para estructuras de datos de Perl

SINOPSIS

use Storable;
store \%table, 'file';
$hashref = retrieve('file');
use Storable qw(nstore store_fd nstore_fd freeze thaw dclone);
# Orden de red
nstore \%table, 'file';
$hashref = retrieve('file');        # NO hay nretrieve()
# Almacenar y recuperar desde un archivo ya abierto
store_fd \@array, \*STDOUT;
nstore_fd \%table, \*STDOUT;
$aryref = fd_retrieve(\*SOCKET);
$hashref = fd_retrieve(\*SOCKET);
# Serializar a memoria
$serialized = freeze \%table;
%table_clone = %{ thaw($serialized) };
# Clonación profunda (recursiva)
$cloneref = dclone($ref);
# Bloqueo consultivo
use Storable qw(lock_store lock_nstore lock_retrieve)
lock_store \%table, 'file';
lock_nstore \%table, 'file';
$hashref = lock_retrieve('file');

DESCRIPCIÓN

El paquete Storable aporta persistencia a tus estructuras de datos de Perl que contengan objetos SCALAR, ARRAY, HASH o REF, es decir, cualquier cosa que pueda ser almacenada convenientemente en disco y recuperada en un momento posterior.

Puede ser utilizado de la manera procedimental habitual llamando a "store" con una referencia al objeto a almacenar, junto con el nombre del archivo donde se debe escribir la imagen.

La rutina devuelve "undef" en caso de problemas de E/S u otros errores internos, un valor verdadero en caso contrario. Los errores graves se propagan como una excepción "die".

Para recuperar datos almacenados en disco, usa "retrieve" con un nombre de archivo. Los objetos almacenados en ese archivo son recreados en memoria para ti, y se devuelve una *referencia* al objeto raíz. En caso de que ocurra un error de E/S al leer, se devuelve "undef" en su lugar. Otros errores graves se propagan a través de "die".

Dado que el almacenamiento se realiza de forma recursiva, es posible que desees empaquetar referencias a objetos que comparten muchos datos comunes en una sola tabla de arrays o hashes, y luego almacenar ese objeto. De esta manera, cuando recuperes todo, los objetos continuarán compartiendo lo que originalmente compartían.

Al coste de una ligera sobrecarga de cabecera, puedes almacenar en un descriptor de archivo ya abierto utilizando la rutina "store_fd", y recuperar desde un archivo a través de "fd_retrieve". Esos nombres no se importan por defecto, por lo que tendrás que hacerlo explícitamente si necesitas esas rutinas. El descriptor de archivo que proporciones debe estar ya abierto, para lectura si vas a recuperar y para escritura si deseas almacenar.

store_fd(\%table, *STDOUT) || die "no se puede almacenar en stdout\n";
$hashref = fd_retrieve(*STDIN);

También puedes almacenar datos en orden de red para permitir un fácil intercambio entre múltiples plataformas, o al almacenar en un socket que se sabe que está conectado remotamente. Las rutinas a llamar tienen un prefijo inicial "n" para *red*, como en "nstore" y "nstore_fd". Al recuperar, tus datos se restaurarán correctamente para que no tengas que saber si estás restaurando datos nativos o de orden de red. Los valores dobles se almacenan como cadenas para garantizar la portabilidad también, con el ligero riesgo de perder algo de precisión en los últimos decimales.

Cuando se utiliza "fd_retrieve", los objetos se recuperan en secuencia, un objeto (es decir, un árbol recursivo) por cada "store_fd" asociado.

Si eres más del tipo orientado a objetos, puedes heredar de Storable y almacenar directamente tus objetos invocando "store" como un método. El hecho de que la raíz del árbol a almacenar sea una referencia bendecida (es decir, un objeto) se trata de forma especial para que retrieve no proporcione una referencia a ese objeto, sino la referencia del objeto bendecido en sí. (De lo contrario, obtendrías una referencia a esa referencia bendecida).

ALMACENAMIENTO EN MEMORIA

El motor Storable también puede almacenar datos en un escalar de Perl en su lugar, para recuperarlos más tarde. Esto se usa principalmente para "congelar" una estructura compleja en algún lugar seguro y compacto de la memoria (donde potencialmente se puede enviar a otro proceso a través de algún IPC, ya que congelar la estructura también la serializa en efecto). Más tarde, y quizás en otro lugar, puedes "descongelar" el escalar de Perl y recrear la estructura compleja original en memoria.

Sorprendentemente, las rutinas a llamar se llaman "freeze" y "thaw". Si deseas enviar el escalar congelado a otra máquina, usa "nfreeze" en su lugar para obtener una imagen portable.

Ten en cuenta que congelar una estructura de objetos e inmediatamente descongelarla logra una clonación profunda de esa estructura:

dclone(.) = thaw(freeze(.))

Storable te proporciona una interfaz "dclone" que no crea ese escalar intermediario, sino que congela la estructura en algún espacio de memoria interno y luego la descongela inmediatamente.

BLOQUEO CONSULTIVO

Las rutinas "lock_store" y "lock_nstore" son equivalentes a "store" y "nstore", excepto que obtienen un bloqueo exclusivo en el archivo antes de escribir. De manera similar, "lock_retrieve" hace lo mismo que "retrieve", pero también obtiene un bloqueo compartido en el archivo antes de leer.

Como con cualquier esquema de bloqueo consultivo, la protección solo funciona si utilizas sistemáticamente "lock_store" y "lock_retrieve". Si una parte de tu aplicación utiliza "store" mientras que la otra utiliza "lock_retrieve", no obtendrás ninguna protección.

El bloqueo consultivo interno se implementa utilizando la rutina flock() de Perl. Si tu sistema no soporta ninguna forma de flock(), o si compartes tus archivos a través de NFS, podrías desear utilizar otras formas de bloqueo utilizando módulos como LockFile::Simple que bloquean un archivo utilizando una entrada del sistema de archivos, en lugar de bloquear el descriptor de archivo.

VELOCIDAD

El núcleo de Storable está escrito en C para una velocidad decente. Se han realizado optimizaciones adicionales de bajo nivel al manipular los internos de perl, para sacrificar el encapsulamiento en beneficio de una mayor velocidad.

REPRESENTACIÓN CANÓNICA

Normalmente, Storable almacena los elementos de los hashes en el orden en que son almacenados internamente por Perl, es decir, pseudaleatoriamente. Si estableces $Storable::canonical a algún valor "VERDADERO", Storable almacenará los hashes con los elementos ordenados por su clave. Esto te permite comparar estructuras de datos comparando sus representaciones congeladas (o incluso las representaciones congeladas comprimidas), lo cual puede ser útil para crear tablas de búsqueda para consultas complicadas.

El orden canónico no implica orden de red; esos son dos ajustes ortogonales.

REFERENCIAS DE CÓDIGO

Desde la versión 2.05 de Storable, las referencias de CÓDIGO pueden ser serializadas con la ayuda de B::Deparse. Para habilitar esta función, establece $Storable::Deparse a un valor verdadero. Para habilitar la deserialización, $Storable::Eval debe ser establecido a un valor verdadero. Ten en cuenta que la deserialización se realiza a través de "eval", lo cual es peligroso si el archivo Storable contiene datos maliciosos. Puedes establecer $Storable::Eval a una referencia de subrutina que se utilizaría en lugar de "eval". Consulta más abajo un ejemplo de uso de un compartimento Seguro para la deserialización de referencias de CÓDIGO.

Si $Storable::Deparse y/o $Storable::Eval se establecen a valores falsos, entonces el valor de $Storable::forgive_me (ver más abajo) se respeta al serializar y deserializar.

COMPATIBILIDAD HACIA ADELANTE

TY

Este lanzamiento de Storable se puede usar en una versión más reciente de Perl para serializar datos que no son compatibles con versiones anteriores de Perl. Por defecto, Storable intentará hacer lo correcto, haciendo croak() si encuentra datos que no puede deserializar. Sin embargo, los valores predeterminados se pueden cambiar de la siguiente manera:

datos utf8
Perl 5.6 agregó soporte para caracteres Unicode con puntos de código > 255, y Perl 5.8 tiene soporte completo para caracteres Unicode en claves de hash. Perl codifica internamente cadenas con estos caracteres usando utf8, y Storable los serializa como utf8. Por defecto, si una versión anterior de Perl encuentra un valor utf8 que no puede representar, hará croak(). Para cambiar este comportamiento de modo que Storable deserialice valores codificados en utf8 como cadenas de bytes (efectivamente eliminando la bandera is_utf8), establezca $Storable::drop_utf8 a algún valor "TRUE". Esto es una forma de pérdida de datos, porque con $drop_utf8 verdadero, se vuelve imposible saber si los datos originales eran la cadena Unicode, o una serie de bytes que resultan ser utf8 válidos.
hashes restringidos
Perl 5.8 agrega soporte para hashes restringidos, que tienen claves restringidas a un conjunto dado, y pueden tener valores bloqueados para ser de solo lectura. Por defecto, cuando Storable encuentra un hash restringido en un perl que no los soporta, lo deserializará como un hash normal, descartando silenciosamente cualquier clave de marcador de posición y dejando las claves y todos los valores desbloqueados. Para hacer que Storable haga croak() en su lugar, establezca $Storable::downgrade_restricted a un valor "FALSE". Para restaurar el valor predeterminado, vuelva a establecerlo a algún valor "TRUE".

La estrategia de hash cperl PERL_PERTURB_KEYS_TOP tiene un problema conocido con los hashes restringidos.

objetos enormes
En sistemas de 64 bits, algunas estructuras de datos pueden exceder el límite de 2G (es decir, I32_MAX). En sistemas de 32 bits, también cadenas entre I32 y U32 (2G-4G). Desde Storable 3.00 (no en el núcleo de perl5) podemos almacenar y recuperar estos objetos, incluso si perl5 en sí no puede manejarlos. Estas son cadenas más largas que 4G, arrays con más de 2G elementos y hashes con más de 2G elementos. cperl prohíbe hashes con más de 2G elementos, pero esto falla en cperl entonces. perl5 en sí, al menos hasta 5.26, lo permite, pero no puede iterar sobre ellos. Tenga en cuenta que la creación de dichos objetos puede causar excepciones de falta de memoria por parte del sistema operativo antes de que perl tenga la oportunidad de abortar.
archivos de versiones futuras de Storable
Las versiones anteriores de Storable hacían croak inmediatamente si encontraban un archivo con un número de versión interno superior al que el Storable lector conocía. Los números de versión internos se incrementan cada vez que se agregan nuevos tipos de datos (como hashes restringidos) al vocabulario del formato de archivo. Esto significaba que una versión más reciente de Storable no tenía forma de escribir un archivo legible por una versión anterior de Storable, incluso si el escritor no almacenaba tipos de datos más nuevos.

Esta versión de Storable pospondrá el croak hasta que encuentre un tipo de dato en el archivo que no reconozca. Esto significa que continuará leyendo archivos generados por módulos Storable más recientes que son cuidadosos en lo que escriben, lo que facilita la actualización de módulos Storable en un entorno mixto.

El comportamiento anterior de croak inmediato puede ser reinstalado estableciendo $Storable::accept_future_minor a algún valor "FALSE".

Todas estas variables no tienen efecto en un Perl más reciente que admita la característica relevante.

REPORTE DE ERRORES

Storable utiliza el paradigma de "excepción", en el sentido de que no intenta solucionar fallos: si ocurre algo malo, se genera una excepción desde la perspectiva del llamador (ver Carp y croak()). Usa eval {} para atrapar esas excepciones.

Cuando Storable hace croak, intenta reportar el error a través de la rutina logcroak() del paquete "Log::Agent", si está disponible.

Los errores normales se reportan haciendo que store() o retrieve() devuelvan "undef". Dichos errores son generalmente errores de E/S (o errores de flujo truncado en la recuperación).

Cuando Storable lanza el error "Profundidad máxima de recursión con estructuras anidadas excedida", ya estamos sin espacio en la pila. Desafortunadamente, en algunas versiones anteriores de perl, la limpieza de una estructura de datos recursiva vuelve a llamar a las llamadas de liberación, lo que provocará desbordamientos de pila en la limpieza. Esta estructura de datos no se limpiará correctamente entonces, solo se destruirá durante la destrucción global.

SOLO PARA MAGOS

Hooks (Ganchos)

Cualquier clase puede definir hooks que se llamarán durante el proceso de serialización y deserialización de objetos que sean instancias de esa clase. Esos hooks pueden redefinir la forma en que se realiza la serialización (y por lo tanto, cómo debe realizarse la deserialización simétrica).

Como dijimos antes:

dclone(.) = thaw(freeze(.))

todo lo que digamos sobre los hooks también debería aplicarse a la clonación profunda. Sin embargo, los hooks reciben información sobre si la operación es una simple serialización o una clonación.

Por lo tanto, cuando los hooks de serialización están involucrados,

dclone(.) <> thaw(freeze(.))

Bueno, podrías mantenerlos sincronizados, pero no hay garantía de que siempre funcionen en clases que alguien más escribió. Además, hay poco que ganar al hacerlo: un hook de serialización podría guardar solo un atributo de un objeto, lo cual probablemente no es lo que debería suceder durante una clonación profunda del mismo objeto.

Aquí está la interfaz de hooking:

"STORABLE_freeze" obj, cloning
El hook de serialización, llamado en el objeto durante la serialización. Puede ser heredado, o definido en la propia clase, como cualquier otro método.

Argumentos: obj es el objeto a serializar, cloning es una bandera que indica si estamos en una operación de dclone() o una serialización regular a través de store() o freeze().

Valor devuelto: Una LISTA "($serialized, $ref1, $ref2, ...)" donde $serialized es la forma serializada a usar, y las referencias opcionales $ref1, $ref2, etc., son referencias adicionales que desea que el motor Storable serialice.

En el momento de la deserialización, se le devolverá la misma LISTA, pero todas las referencias adicionales apuntarán a la estructura deserializada.

La primera vez que se activa el hook en un flujo de serialización, puede devolver una lista vacía. Eso señalará al motor Storable que descarte este hook para esta clase y, por lo tanto, revierta a la serialización predeterminada de los datos de Perl subyacentes. El hook se procesará nuevamente normalmente en la siguiente serialización.

A menos que sepa mejor, el hook de serialización siempre debería decir:

sub STORABLE_freeze {
    my ($self, $cloning) = @_;
    return if $cloning;         # Serialización predeterminada regular
    ....
}

para mantener una semántica razonable de dclone().

"STORABLE_thaw" obj, cloning, serialized, ...
El hook de deserialización llamado en el objeto durante la deserialización. ¿Pero espera: si estamos deserializando, todavía no hay ningún objeto...?

Incorrecto: el motor Storable crea uno vacío para usted. Si conoces Eiffel, puedes ver "STORABLE_thaw" como una rutina de creación alternativa.

Esto significa que el hook puede ser heredado como cualquier otro método, y que obj es su referencia bendecida para esta instancia en particular.

Los otros argumentos deberían parecerle familiares si conoce "STORABLE_freeze": cloning es verdadero cuando somos parte de una operación de clonación profunda, serialized es la cadena serializada que devolvió al motor en "STORABLE_freeze", y puede haber una lista opcional de referencias, en el mismo orden en que las proporcionó en el momento de la serialización, apuntando a los objetos deserializados (que han sido procesados por cortesía del motor Storable).

Cuando el motor Storable no encuentra ninguna rutina de hook "STORABLE_thaw", intenta cargar la clase requiriendo el paquete dinámicamente (usando el nombre del paquete bendecido), y luego reintenta la búsqueda. Si en ese momento el hook no se puede localizar, el motor hace croak. Tenga en cuenta que este mecanismo fallará si define varias clases en el mismo archivo, pero perlmod le advirtió.

Depende de usted usar esta información para poblar obj como desee.

Valor devuelto: ninguno.

Mientras que "STORABLE_freeze" y "STORABLE_thaw" son útiles para clases donde cada instancia es independiente, este mecanismo tiene dificultades (o es incompatible) con objetos que existen como recursos comunes a nivel de proceso o sistema, como objetos singleton, pools de bases de datos, cachés u objetos memoizados.

De hecho, los ganchos son código Perl regular, y Storable es conveniente cuando se trata de serializar y deserializar cosas, ¿por qué no usarlo para manejar la cadena de serialización? Sin embargo, hay algunas cosas que debes saber:
•
Desde Storable 3.05 hasta 3.13, investigamos el límite de recursión de pila para referencias, arreglos y hashes hasta una profundidad máxima de ~1200-35000, de lo contrario podríamos caer en un desbordamiento de pila. En JSON::XS este límite es de 512, por cierto. Con referencias que no se referencian entre sí inmediatamente, aún no hay tal límite, por lo que podría caer en un segfault de desbordamiento de pila.

Esta investigación y las comprobaciones que realizamos tienen algunas limitaciones:

  • el tamaño de la pila en el momento de la compilación puede ser diferente en tiempo de ejecución, por ejemplo, el tamaño de la pila puede haber sido modificado con ulimit(1). Si es mayor en tiempo de ejecución, Storable puede fallar injustificadamente en freeze() o thaw(). Si es mayor en el momento de la compilación, Storable puede fallar en segmentación al procesar una estructura profunda en tiempo de ejecución.
  • el tamaño de la pila puede ser diferente en un hilo.
  • los límites de recursión de arreglos y hashes se comprueban por separado contra la misma profundidad de recursión, una estructura congelada con una gran secuencia de arreglos anidados dentro de muchos hashes anidados puede agotar la pila del procesador sin activar la protección de recursión de Storable.

Por lo tanto, ahora tienen valores predeterminados simples en lugar de investigar en el momento de la compilación.

Puede controlar las profundidades máximas de recursión de arreglos y hashes modificando $Storable::recursion_limit y $Storable::recursion_limit_hash respectivamente. Cualquiera de ellos puede establecerse en -1 para evitar cualquier comprobación de profundidad, aunque no se recomienda.

Si desea probar cuáles son los límites, la herramienta stacksize se incluye en la distribución de "Storable".

  • Puede crear bucles infinitos si las cosas que serializa a través de freeze() (por ejemplo) apuntan de nuevo al objeto que estamos tratando de serializar en el gancho.
  • Las referencias compartidas entre objetos no permanecerán compartidas: si estamos serializando la lista de objetos [A, C] donde tanto el objeto A como C se refieren al MISMO objeto B, y si hay un gancho de serialización en A que dice freeze(B), entonces al deserializar, obtendremos [A', C'] donde A' se refiere a B', pero C' se refiere a D, un clon profundo de B'. La topología no se conservó.
  • El límite máximo de recursión de pila para su sistema se devuelve mediante stack_depth() y stack_depth_hash(). El límite del hash suele ser la mitad del tamaño del límite de arreglos y referencias, ya que la API de hash de Perl no es óptima.

Es por eso que "STORABLE_freeze" le permite proporcionar una lista de referencias para serializar. El motor garantiza que estas se serializarán en el mismo contexto que los otros objetos, y por lo tanto, que los objetos compartidos permanecerán compartidos.

En el ejemplo anterior [A, C], el gancho "STORABLE_freeze" podría devolver:

("algo", $self->{B})

y la parte B sería serializada por el motor. En "STORABLE_thaw", obtendría de vuelta la referencia al objeto B', deserializado para usted.

Por lo tanto, la recursión normalmente debería evitarse, pero no obstante está soportada.

La función constante "Storable::BIN_WRITE_VERSION_NV" devuelve qué versión de archivo se escribe y puede ser menor que "Storable::BIN_VERSION_NV" en algunas configuraciones.

"major", "minor"
Esto también devuelve la versión del formato del archivo. Si la versión es "2.7", entonces major sería 2 y minor sería 7. El elemento minor está ausente cuando major es menor que 2.
"hdrsize"
Este es el número de bytes que ocupa la cabecera de Storable.
"netorder"
Esto es VERDADERO si la imagen almacena datos en orden de red. Esto significa que se creó con nstore() o similar.
"byteorder"
Esto solo está presente cuando "netorder" es FALSO. Es la cadena $Config{byteorder} del perl que creó esta imagen. Es una cadena como "1234" (little endian de 32 bits) o "87654321" (big endian de 64 bits). Esto debe coincidir con el perl actual para que la imagen sea legible por Storable.
"intsize", "longsize", "ptrsize", "nvsize"
Estos solo están presentes cuando "netorder" es FALSO. Estos son los tamaños de varios tipos de datos C del perl que creó esta imagen. Estos deben coincidir con el perl actual para que la imagen sea legible por Storable.

El elemento "nvsize" solo está presente para el formato de archivo v2.2 y superior.

"file"
El nombre del archivo.
$info = Storable::read_magic( $buffer )
$info = Storable::read_magic( $buffer, $must_be_file )
El $buffer debe ser una imagen de Storable o los primeros bytes de la misma. Si $buffer comienza con una cabecera de Storable, se devuelve un hash que describe la imagen, de lo contrario se devuelve "undef".

El hash tiene la misma estructura que el devuelto por Storable::file_magic(). El elemento "file" es verdadero si la imagen es una imagen de archivo.

Si se proporciona el argumento $must_be_file y es VERDADERO, entonces devuelve "undef" a menos que la imagen parezca pertenecer a un volcado de archivo.

... ...El tamaño máximo de una cabecera Storable es actualmente de 21 bytes. Si el $buffer proporcionado es solo la primera parte de una imagen Storable, debe tener al menos esta longitud para garantizar que read_magic() lo reconozca como tal.

EJEMPLOS

Aquí hay algunas muestras de código que muestran un posible uso de Storable:

use Storable qw(store retrieve freeze thaw dclone);
%color = ('Blue' => 0.1, 'Red' => 0.8, 'Black' => 0, 'White' => 1);
store(\%color, 'mycolors') or die "Can't store %a in mycolors!\n";
$colref = retrieve('mycolors');
die "Unable to retrieve from mycolors!\n" unless defined $colref;
printf "Blue is still %lf\n", $colref->{'Blue'};
$colref2 = dclone(\%color);
$str = freeze(\%color);
printf "Serialization of %%color is %d bytes long.\n", length($str);
$colref3 = thaw($str);

que imprime (en mi máquina):

Blue is still 0.100000
Serialization of %color is 102 bytes long.

Serialización de referencias de CÓDIGO y deserialización en un compartimento seguro:

use Storable qw(freeze thaw);
use Safe;
use strict;
my $safe = Safe->new;
        # debido a los opcodes usados en "use strict":
$safe->permit(qw(:default require));
local $Storable::Deparse = 1;
local $Storable::Eval = sub { $safe->reval($_[0]) };
my $serialized = freeze(sub { 42 });
my $code = thaw($serialized);
$code->() == 42;

ADVERTENCIA DE SEGURIDAD

¡No acepte documentos Storable de fuentes no confiables! No hay forma de configurar Storable para que se pueda usar de manera segura para procesar datos no confiables. Si bien existen varias opciones que se pueden usar para mitigar problemas de seguridad específicos, estas opciones no constituyen una red de seguridad completa para el usuario, y el procesamiento de datos no confiables puede resultar en fallos de segmentación, ejecución remota de código o escalada de privilegios. La siguiente lista resume algunas características conocidas que representan problemas de seguridad que deben ser considerados por los usuarios de este módulo.

Lo más obvio es que la característica opcional (desactivada por defecto) de serialización de referencias de CÓDIGO permite la transferencia de código al proceso de deserialización. Además, cualquier objeto serializado hará que Storable cargue útilmente el módulo correspondiente a la clase del objeto en el módulo de deserialización. Para nombres de módulos manipulados, esto puede cargar código casi arbitrario. Finalmente, los destructores del objeto deserializado se invocarán cuando los objetos sean destruidos en el proceso de deserialización. Los documentos Storable creados maliciosamente pueden colocar dichos objetos en el valor de una clave de hash que es anulada por otro par clave/valor en el mismo hash, provocando así la ejecución inmediata del destructor.

Para deshabilitar la bendición de objetos al deshelar/recuperar, elimine la bandera "BLESS_OK" = 2 de $Storable::flags o establezca el segundo argumento para thaw/retrieve a 0.

Para deshabilitar el enlace de datos al deshelar/recuperar, elimine la bandera "TIE_OK" = 4 de $Storable::flags o establezca el segundo argumento para thaw/retrieve a 0.

Con la configuración predeterminada de $Storable::flags = 6, la creación o destrucción de objetos aleatorios, incluso objetos renombrados, puede ser controlada por un atacante. Consulte CVE-2015-1592 y su módulo metasploit.

Si su aplicación requiere aceptar datos de fuentes no confiables, lo mejor es utilizar un formato de serialización e implementación menos potente y más probablemente seguro. Si sus datos son lo suficientemente simples, Cpanel::JSON::XS o Data::MessagePack son alternativas adecuadas. Para estructuras de datos más complejas que contienen varios tipos de datos específicos de Perl como expresiones regulares o datos alias, Sereal es la mejor alternativa y ofrece máxima interoperabilidad. Tenga en cuenta que Sereal no es seguro por defecto, pero puede configurar el codificador y decodificador para mitigar cualquier problema de seguridad.

ADVERTENCIA

Si está utilizando referencias como claves dentro de sus tablas hash, se sentirá decepcionado al recuperar sus datos. De hecho, Perl convierte en cadena las referencias utilizadas como claves de tabla hash. Si más tarde desea acceder a los elementos a través de otra conversión a cadena de referencias (es decir, utilizando la misma referencia que se utilizó originalmente como clave para registrar el valor en la tabla hash), funcionará porque ambas referencias se convierten en la misma cadena.

Sin embargo, no funcionará a través de una secuencia de operaciones de "store" y "retrieve", porque las direcciones en los objetos recuperados, que forman parte de las referencias convertidas a cadena, probablemente diferirán de las direcciones originales. La topología de su estructura se conserva, pero no los semánticas ocultas como esas.

En plataformas donde importa, asegúrese de llamar a binmode() en los descriptores que pasa a las funciones de Storable.

Almacenar datos canónicamente que contienen hashes grandes puede ser significativamente más lento que almacenar los mismos datos normalmente, ya que se deben asignar, poblar, ordenar y liberar matrices temporales para almacenar las claves de cada hash. Algunas pruebas han mostrado una reducción a la mitad de la velocidad de almacenamiento: la penalización exacta dependerá de la complejidad de sus datos. No hay ralentización en la recuperación.

EXPRESIONES REGULARES

Storable ahora tiene soporte experimental para almacenar expresiones regulares, pero existen limitaciones significativas:

  • se requiere perl 5.8 o posterior.
  • las expresiones regulares con bloques de código, es decir, "/(?{ ...})/" o "/(??{ ... })/" lanzarán una excepción al deshelarse.
  • la sintaxis y las banderas de las expresiones regulares han cambiado a lo largo de la historia de perl, por lo que una expresión regular que congele en una versión de perl puede fallar al deshelarse o comportarse de manera diferente en otra versión de perl.
  • dependiendo de la versión de perl, las expresiones regulares pueden cambiar su comportamiento dependiendo del contexto, pero las versiones posteriores de perl incorporarán ese comportamiento en la expresión regular.

Storable lanzará una excepción si una expresión regular congelada no se puede deshelar.

ERRORES

No se pueden almacenar GLOB, FORMLINE, etc... Si puede definir semánticas para esas operaciones, siéntase libre de mejorar Storable para que pueda manejarlas.

Las funciones de almacenamiento "croak" (fallarán catastróficamente) si encuentran tales referencias a menos que establezca $Storable::forgive_me a algún valor "TRUE". En ese caso, el mensaje fatal se convierte en una advertencia y se almacena una cadena sin significado en su lugar.

Establecer $Storable::canonical puede no generar cadenas congeladas que se comparen igual debido a la posible conversión a cadena de números. Cuando existe la versión en cadena de un escalar, es la forma almacenada; por lo tanto, si accidentalmente usa sus números como cadenas entre dos operaciones de congelación sobre las mismas estructuras de datos, obtendrá resultados diferentes.

Al almacenar dobles en orden de red, su valor se almacena como texto. Sin embargo, tampoco debe esperar que valores de punto flotante no numéricos como infinito y "no es un número" pasen exitosamente por un par de nstore()/retrieve().

Como Storable ni sabe ni le importa sobre conjuntos de caracteres (aunque sabe que los caracteres pueden tener más de ocho bits de ancho), cualquier diferencia en la interpretación de los códigos de caracteres entre un host y un sistema de destino es su problema. En particular, si el host y el destino utilizan puntos de código diferentes para representar los caracteres utilizados en la representación de texto de números de punto flotante, no podrá intercambiar datos de punto flotante, ni siquiera con nstore().

"Storable::drop_utf8" es una herramienta contundente. No hay ninguna instalación para devolver **todas** las cadenas como secuencias utf8, ni para intentar convertir datos utf8 de nuevo a 8 bits y croak() si la conversión falla.

Antes de Storable 2.01, no se hacía distinción entre enteros con signo y sin signo al almacenar. Por defecto, Storable prefiere almacenar la representación en cadena de un escalar (si la tiene), por lo que esto solo causaría problemas al almacenar enteros sin signo grandes que nunca se habían convertido a cadena o a punto flotante. En otras palabras, valores que se habían generado mediante operaciones enteras como operaciones lógicas y luego no se utilizaron en ningún contexto de cadena o aritmético antes de almacenarlos.

Datos de 64 bits en perl 5.6.0 y 5.6.1

Esta sección solo se aplica si tiene datos existentes escritos por Storable 2.02 o anterior en perl 5.6.0 o 5.6.1 en Unix o Linux que se haya configurado con soporte para enteros de 64 bits (no es la opción predeterminada). Si obtuvo un perl precompilado, en lugar de ejecutar Configure para construir su propio perl desde el código fuente, entonces casi seguramente no le afecta, y puede dejar de leer ahora (a menos que tenga curiosidad). Si está usando perl en Windows, no le afecta.

Storable escribe una cabecera de archivo que contiene los tamaños de varios tipos del lenguaje C para el compilador C que compiló Storable (cuando no escribe en orden de red), y se negará a cargar archivos escritos por un Storable que no esté en la misma arquitectura (o compatible). Esta comprobación y una comprobación del orden de bytes de la máquina son necesarias porque el tamaño de varios campos en el archivo se da por los tamaños de los tipos del lenguaje C, y por lo tanto los archivos escritos en diferentes arquitecturas son incompatibles. Esto se hace para aumentar la velocidad. (Al escribir en orden de red, todos los campos se escriben con longitudes estándar, lo que permite una interconexión completa, pero lleva más tiempo leer y escribir)

Perl 5.6.x introdujo la capacidad de configurar opcionalmente el intérprete de perl para usar el tipo "long long" de C para permitir que los escalares almacenen enteros de 64 bits en sistemas de 32 bits. Sin embargo, debido a la forma en que el sistema de configuración de Perl generó los archivos de configuración C en plataformas no Windows, y la forma en que Storable genera su cabecera, nada en la cabecera del archivo Storable reflejó si el perl de escritura estaba utilizando enteros de 32 o 64 bits, a pesar del hecho de que Storable estaba almacenando algunos datos de manera diferente en el archivo. Por lo tanto, Storable ejecutándose en perl con enteros de 64 bits leerá la cabecera de un archivo escrito por un perl de 32 bits, no se dará cuenta de que los datos están en un formato sutilmente incompatible, y luego saldrá terriblemente mal (posiblemente fallando) si encontrara un entero almacenado. Esta es una falla de diseño.

Storable magic

Some versions of Storable can store magic values in scalars. These are variables that have special properties, like tied variables. Some variables have magic that cannot be stored, like variables that have been used to create an anonymous subroutine, or variables that have been declared with my but are still in scope.

This module has been modified to store and retrieve arbitrary magic values. However, there are some magic values that it is impossible to store and retrieve correctly. These are:

  • Magic that relies on the variable being in scope. Specifically, variables declared with my that have not yet been used. The magic for these variables is lost when they are stored.

    A workaround for this is to use tie a variable to a hash like Storable::hash or Storable::array.

  • Variables that have been used to create an anonymous subroutine. These variables have magic that will cause perl to abort, so the magic is lost.

  • Variables that are used to create a subroutine closure. The magic for these variables is lost.

There are also some magic values that may not be stored correctly, depending on the version of perl and the configuration of perl.

  • Variables that are tied to a class that is not available when the variable is retrieved. These variables are stored as plain scalars.

  • Variables that contain references to subroutines. These are stored as plain scalars.

There is a flag $Storable::store_with_magic that defaults to true. If this is set to false, then all magic values are stored as plain scalars.

There is also a flag $Storable::retrieve_with_magic that defaults to true. If this is set to false, then all magic values are retrieved as plain scalars.

The default behaviour is to store and retrieve all magic values. However, if you are storing data that will be retrieved by an older version of Storable, you should set $Storable::store_with_magic to false. If you are retrieving data that was stored by an older version of Storable, you should set $Storable::retrieve_with_magic to false.

EXAMPLES

        use Storable;

        # Store a variable with magic
        my $scalar = 5;
        tie $scalar, 'Storable::hash';
        $scalar = 10;
        my $ref = \$scalar;
        my $string = "hello";
        $string = \"world";
        $ref = \$string;

        my $data = \$ref;
        my $serialized = Storable::dclone($data);

        # Retrieve the variable with magic
        my $unserialized = Storable::deserialize($serialized);
        my $retrieved_ref = $$unserialized;
        my $retrieved_scalar = $$retrieved_ref;
        my $retrieved_string = $$retrieved_scalar;

        print "Original scalar: $scalar\n";
        print "Retrieved scalar: $retrieved_scalar\n";

        # Check if the scalar still has magic
        if (tied($retrieved_scalar)) {
            print "Scalar is still tied to: " . tied($retrieved_scalar)->can('TIEHASH') . "\n";
        } else {
            print "Scalar is no longer tied.\n";
        }

SECURITY WARNING

The Storable module can serialize and deserialize arbitrary Perl data structures. This means that it can be used to execute arbitrary code. For example, if you deserialize data that contains a subroutine reference, then that subroutine will be executed.

You should never deserialize data from an untrusted source. If you do, then you could be opening yourself up to a security vulnerability.

This is especially true if you are using the freeze() and thaw() functions, which do not perform any checks on the data that they are serializing or deserializing.

The dclone() function is safe to use with untrusted data, as it does not execute any code.

WARNING

The header used to store information about the size of integers is the same whether 32 or 64 bit integers were used. It is therefore impossible to detect whether an old file being read in was written with 32 or 64 bit integers. Hence, this module defaults to the new, correct behaviour.

What this means is that if you have data written by Storable 1.x running on perl 5.6.0 or 5.6.1 configured with 64 bit integers on Unix or Linux then by default this module will refuse to read it, giving the error Byte order is not compatible. If you have such data then you should set $Storable::interwork_56_64bit to a true value to make this module read and write files with the old header. You should also migrate your data, or any older perl you are communicating with, to this current version of Storable.

If you don't have data written with the specific configuration of perl described above, then you do not and should not do anything. Don't set the flag - not only will Storable on an identically configured perl refuse to load them, but Storable a differently configured perl will load them believing them to be correct for it, and then may well fail or crash part way through reading them.
