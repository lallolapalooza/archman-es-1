val length : bytes -> int

Devuelve la longitud (número de bytes) del argumento.

val get : bytes -> int -> char

get s n devuelve el byte en el índice n del argumento s.

Lanza Invalid_argument si n no es un índice válido en s.

val set : bytes -> int -> char -> unit

set s n c modifica s en el lugar, reemplazando el byte en el índice n con c.

Lanza Invalid_argument si n no es un índice válido en s.

val create : int -> bytes

create n devuelve una nueva secuencia de bytes de longitud n. La secuencia no está inicializada y contiene bytes arbitrarios.

Lanza Invalid_argument si n < 0 o n > Sys.max_string_length.

val make : int -> char -> bytes

make n c devuelve una nueva secuencia de bytes de longitud n, rellenada con el byte c.

Lanza Invalid_argument si n < 0 o n > Sys.max_string_length.

val init : int -> f:(int -> char) -> bytes

init n f devuelve una nueva secuencia de bytes de longitud n, con el carácter i inicializado al resultado de f i (en orden de índice creciente).

Lanza Invalid_argument si n < 0 o n > Sys.max_string_length.

val sub : bytes -> pos:int -> len:int -> bytes

sub s ~pos ~len devuelve una nueva secuencia de bytes de longitud len, que contiene la sub-secuencia de s que comienza en la posición pos y tiene longitud len.

Lanza Invalid_argument si pos y len no designan un rango válido de s.

val sub_string : bytes -> pos:int -> len:int -> string

Igual que BytesLabels.sub pero devuelve una cadena en lugar de una secuencia de bytes.

val extend : bytes -> left:int -> right:int -> bytes

extend s ~left ~right devuelve una nueva secuencia de bytes que contiene los bytes de s, con left bytes no inicializados añadidos al principio y right bytes no inicializados añadidos al final. Si left o right es negativo, entonces los bytes se eliminan (en lugar de añadirse) del lado correspondiente de s.

val fill : bytes -> pos:int -> len:int -> char -> unit

fill s ~pos ~len c modifica s en el lugar, reemplazando len caracteres con c, comenzando en pos.

Lanza Invalid_argument si pos y len no designan un rango válido de s.

val blit : src:bytes -> src_pos:int -> dst:bytes -> dst_pos:int -> len:int -> unit

blit ~src ~src_pos ~dst ~dst_pos ~len copia len bytes de la secuencia de bytes src, comenzando en el índice src_pos, a la secuencia de bytes dst, comenzando en el índice dst_pos. Funciona correctamente incluso si src y dst son la misma secuencia de bytes, y los intervalos de origen y destino se superponen.

Lanza Invalid_argument si src_pos y len no designan un rango válido de src, o si dst_pos y len no designan un rango válido de dst.

Conversiones no seguras (para usuarios avanzados)

Esta sección describe funciones de conversión de bajo nivel y no seguras entre bytes y string. No copian los datos internos; usadas incorrectamente, pueden romper el invariante de inmutabilidad de las cadenas. Están disponibles para autores de bibliotecas expertas, pero para la mayoría de los propósitos deberías usar BytesLabels.to_string y BytesLabels.of_string, que siempre son correctos.

val unsafe_to_string : bytes -> string

Convierte de forma insegura una secuencia de bytes en una cadena.

Para razonar sobre el uso de unsafe_to_string, es útil considerar una disciplina de "propiedad". Un fragmento de código que manipula algunos datos "es propietario" de él; existen varios modos de propiedad disjuntos, incluyendo:

- Propiedad única: los datos pueden ser accedidos y modificados

- Propiedad compartida: los datos tienen varios propietarios, que solo pueden acceder a ellos, no modificarlos.

La propiedad única es lineal: pasar los datos a otro fragmento de código significa ceder la propiedad (no podemos volver a escribir los datos). Un propietario único puede decidir hacer que los datos sean compartidos (renunciando a los derechos de modificación sobre ellos), pero los datos compartidos no pueden volver a ser de propiedad única.

unsafe_to_string s solo se puede usar cuando el llamador posee la secuencia de bytes s, ya sea de forma única o como datos inmutables compartidos. El llamador cede la propiedad de s y adquiere la propiedad de la cadena devuelta.

Hay dos casos de uso válidos que respetan esta disciplina de propiedad:

1. Creación de una cadena inicializando y modificando una secuencia de bytes que nunca se modifica después de realizar la inicialización.

let string_init len f : string =
  let s = Bytes.create len in
  for i = 0 to len - 1 do Bytes.set s i (f i) done;
  Bytes.unsafe_to_string s

Esta función es segura porque la secuencia de bytes s nunca será accedida ni modificada después de llamar a unsafe_to_string. El código string_init cede la propiedad de s y devuelve la propiedad de la cadena resultante a su llamador.

Nótese que sería inseguro si s se pasara como parámetro adicional a la función f, ya que podría escaparse de esta manera y ser modificada en el futuro; string_init cedería la propiedad de s para pasarla a f y no podría llamar a unsafe_to_string de forma segura.

Hemos proporcionado las funciones String.init, String.map y String.mapi para cubrir la mayoría de los casos de construcción de nuevas cadenas. Deberías preferirlas sobre to_string o unsafe_to_string siempre que sea aplicable.

2. Ceder temporalmente la propiedad de una secuencia de bytes a una función que espera una cadena de propiedad única y devuelve la propiedad, para que podamos modificar la secuencia nuevamente después de que la llamada haya terminado.

let bytes_length (s : bytes) =
  String.length (Bytes.unsafe_to_string s)

En este caso de uso, no prometemos que s nunca será modificada después de la llamada a bytes_length s. La función String.length toma prestada temporalmente la propiedad única de la secuencia de bytes (y la ve como una string), pero devuelve esta propiedad al llamador, que puede asumir que s sigue siendo una secuencia de bytes válida después de la llamada. Nótese que esto solo es correcto porque sabemos que String.length no captura su argumento; podría escaparse por un canal secundario como un combinador de memoización.

El llamador no puede modificar s mientras la cadena está prestada (ha cedido temporalmente la propiedad). Esto afecta a los programas concurrentes, pero también a las funciones de orden superior: si String.length devolviera un cierre para ser llamado más tarde, s no debería ser modificado hasta que este cierre se aplique por completo y devuelva la propiedad.

val unsafe_of_string : string -> bytes

Convierte de forma insegura una cadena compartida en una secuencia de bytes que no debe ser modificada.

La misma disciplina de propiedad que hace correcta a unsafe_to_string se aplica a unsafe_of_string: puedes usarla si eras el propietario del valor string, y poseerás el bytes devuelto en el mismo modo.

En la práctica, la propiedad única de los valores de cadena es extremadamente difícil de razonar correctamente. Siempre debes asumir que las cadenas son compartidas, nunca de propiedad única.

Por ejemplo, las literales de cadena son implícitamente compartidas por el compilador, por lo que nunca eres propietario único de ellas.

let incorrect = Bytes.unsafe_of_string "hello"
let s = Bytes.of_string "hello"

La primera declaración es incorrecta, porque la literal de cadena "hello" podría ser compartida por el compilador con otras partes del programa, y modificar incorrect es un error. Siempre debes usar la segunda versión, que realiza una copia y por lo tanto es correcta.

Asumir propiedad única de cadenas que no son literales de cadena, sino que están (parcialmente) construidas a partir de literales de cadena, también es incorrecto. Por ejemplo, modificar unsafe_of_string ("foo" ^ s) podría modificar la cadena compartida "foo"; asumiendo una representación de cuerda (rope) de las cadenas. De forma más general, las funciones que operan sobre cadenas asumirán propiedad compartida, no conservan la propiedad única. Por lo tanto, es incorrecto asumir propiedad única del resultado de unsafe_of_string

Splitting and iterating

The functions in this section are used to split byte sequences into subsequences.

val split_on_byte : bytes -> int -> bytes list

split_on_byte s b returns the list of all (possibly empty) subsequences of s that are delimited by the byte b . If s is empty, the result is the singleton list [empty] .

The function's output is specified by the following invariants:

-The list is not empty.

-Concatenating its elements using b as a separator returns a byte sequence equal to the input ( Bytes.concat (Bytes.make 1 b)
(Bytes.split_on_byte s b) = s ).

-No byte sequence in the result contains the byte b .

Since 4.13

The only case we have reasonable confidence is safe is if the produced bytes is shared -- used as an immutable byte sequence. This is possibly useful for incremental migration of low-level programs that manipulate immutable sequences of bytes (for example Marshal.from_bytes ) and previously used the string type for this purpose.

val split_on_char : sep:char -> bytes -> bytes list

split_on_char sep s returns the list of all (possibly empty) subsequences of s that are delimited by the sep character. If s is empty, the result is the singleton list [empty] .

The function's output is specified by the following invariants:

-The list is not empty.

-Concatenating its elements using sep as a separator returns a byte sequence equal to the input ( Bytes.concat (Bytes.make 1 sep)
(Bytes.split_on_char sep s) = s ).

-No byte sequence in the result contains the sep character.

Codificación/decodificación binaria de enteros

Las funciones de esta sección codifican y decodifican enteros binariamente desde y hacia secuencias de bytes.

Todas las siguientes funciones lanzan Invalid_argument si el espacio necesario en el índice i para decodificar o codificar el entero no está disponible.

La codificación little-endian (respectivamente, big-endian) significa que los bytes menos (respectivamente, más) significativos se almacenan primero. Big-endian también se conoce como orden de bytes de red. La codificación native-endian es little-endian o big-endian según Sys.big_endian .

Los enteros de 32 y 64 bits se representan mediante los tipos int32 e int64 , que pueden interpretarse como números con signo o sin signo.

Los enteros de 8 y 16 bits se representan mediante el tipo int , que tiene más bits que la codificación binaria. Estos bits adicionales se manejan de la siguiente manera:

-Las funciones que decodifican enteros de 8 o 16 bits con signo (respectivamente, sin signo) representados por valores int extienden el signo (respectivamente, rellenan con ceros) su resultado.

-Las funciones que codifican enteros de 8 o 16 bits representados por valores int truncan su entrada a sus bytes menos significativos.

NAME

StdLabels.Bytes - mutable byte sequences

Module

This module is an alias for the module Bytes.

Documentation

This module provides functions for manipulating mutable byte sequences. Byte sequences are mutable arrays of characters.

Basic operations

val bytes : int -> bytes

bytes n returns a new byte sequence of length n, initialized with null characters.

val length : bytes -> int

length b returns the number of bytes in the byte sequence b.

val get : bytes -> int -> char

get b i returns the byte at index i in the byte sequence b.

val set : bytes -> int -> char -> unit

set b i c sets the byte at index i in byte sequence b to character c.

val blit : bytes -> int -> bytes -> int -> int -> unit

blit src src_pos dst dst_pos len copies len bytes from the byte sequence src starting at index src_pos to the byte sequence dst starting at index dst_pos. The positions and length must be within the bounds of the respective byte sequences.

val fill : bytes -> int -> int -> char -> unit

fill b offset len c fills the byte sequence b with the character c, starting at index offset and filling len bytes.

Subsequences

val sub : bytes -> int -> int -> bytes

sub b pos len returns a new byte sequence whose length is len and the characters are those of b starting at index pos. The result is a copy, so the new byte sequence is mutable and independent of the original.

String conversion

val of_string : string -> bytes

of_string s returns a mutable copy of the string s.

val to_string : bytes -> string

to_string b returns a string corresponding to the byte sequence b.

Byte sequences and concurrency safety

Care must be taken when concurrently accessing byte sequences from multiple domains: accessing a byte sequence will never crash a program, but unsynchronized accesses might yield surprising (non-sequentially-consistent) results.

Atomicity

Every byte sequence operation that accesses more than one byte is not atomic. This includes iteration and scanning.

For example, consider the following program:

let size = 100_000_000
let b = Bytes.make size  ' '
let update b f ()  =
  Bytes.iteri (fun i x -> Bytes.set b i (Char.chr (f (Char.code x)))) b
let d1 = Domain.spawn (update b (fun x -> x + 1))
let d2 = Domain.spawn (update b (fun x -> 2 * x + 1))
let () = Domain.join d1; Domain.join d2
the bytes sequence b may contain a non-deterministic mixture of '!' , 'A' , 'B' , and 'C' values.

After executing this code, each byte of the sequence b is either '!' , 'A' , 'B' , or 'C' . If atomicity is required, then the user must implement their own synchronization (for example, using Mutex.t ).

Data races

If two domains only access disjoint parts of a byte sequence, then the observed behaviour is the equivalent to some sequential interleaving of the operations from the two domains.

A data race is said to occur when two domains access the same byte without synchronization and at least one of the accesses is a write. In the absence of data races, the observed behaviour is equivalent to some sequential interleaving of the operations from different domains.

Whenever possible, data races should be avoided by using synchronization to mediate the accesses to the elements of the sequence.

Indeed, in the presence of data races, programs will not crash but the observed behaviour may not be equivalent to any sequential interleaving of operations from different domains. Nevertheless, even in the presence of data races, a read operation will return the value of some prior write to that location.

Mixed-size accesses

Another subtle point is that if a data race involves mixed-size writes and reads to the same location, the order in which those writes and reads are observed by domains is not specified. For instance, the following code write sequentially a 32-bit integer and a char to the same index

let b = Bytes.make 10 '\000'
let d1 = Domain.spawn (fun () -> Bytes.set_int32_ne b 0 100; b.[0] <- 'd' )

In this situation, a domain that observes the write of 'd' to b. 0 is not guaranteed to also observe the write to indices 1 , 2 , or 3 .
