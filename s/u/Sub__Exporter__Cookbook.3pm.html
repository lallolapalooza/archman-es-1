NOMBRE

Sub::Exporter::Cookbook - trucos útiles, demostrativos o estúpidos de Sub::Exporter

VERSIÓN

versión 0.991

VISIÓN GENERAL

Sub::Exporter es una herramienta bastante simple y se puede usar para lograr objetivos muy simples. Sus comportamientos básicos y su aplicación básica (es decir, la exportación "tradicional" de rutinas) se describen en Sub::Exporter::Tutorial y Sub::Exporter. Este documento presenta aplicaciones que pueden no ser inmediatamente obvias, o que pueden demostrar cómo se pueden utilizar ciertas características (para bien o para mal).

VERSIÓN PERL

Esta biblioteca debería ejecutarse en versiones de Perl incluso muy antiguas. Debería funcionar en cualquier versión de Perl lanzada en los últimos cinco años.

Aunque puede funcionar en versiones anteriores de Perl, no se garantiza que la versión mínima requerida no aumente. La versión puede aumentar por cualquier motivo, y no hay promesa de que se acepten parches para reducir la versión mínima requerida de Perl.

LAS RECETAS

Exportar métodos como rutinas

Con Exporter.pm, exportar métodos es imposible. Sub::Exporter lo hace simple. Usando la utilidad "curry_method" proporcionada en Sub::Exporter::Util, un método se puede exportar con el invocante incorporado.

package Object::Strenuous;
use Sub::Exporter::Util 'curry_method';
use Sub::Exporter -setup => {
  exports => [ objection => curry_method('new') ],
};

Con esta configuración, el código de importación puede contener:

my $obj = objection("irrelevant");

...y esto será equivalente a:

my $obj = Object::Strenuous->new("irrelevant");

El invocante incorporado se determina por el invocante para el método "import". Eso significa que si subclasificáramos Object::Strenuous de la siguiente manera:

package Object::Strenuous::Repeated;
@ISA = 'Object::Strenuous';

...entonces importar "objection" de la subclase incorporaría esa subclase.

Finalmente, dado que el invocante puede ser un objeto, puede escribir algo como esto:

package Cypher;
use Sub::Exporter::Util 'curry_method';
use Sub::Exporter -setup => {
  exports => [ encypher => curry_method ],
};

con la expectativa de que se llamará al método "import" en un objeto Cypher instanciado:

BEGIN {
  my $cypher = Cypher->new( ... );
  $cypher->import('encypher');
}

Ahora hay una rutina globalmente disponible "encypher" que llama al método encypher en un objeto Cypher de otro modo inaccesible.

Exportar métodos como métodos

Mientras que los módulos de exportación suelen exportar subrutinas para ser llamadas como subrutinas, es fácil usar Sub::Exporter para exportar subrutinas destinadas a ser llamadas como métodos en el paquete de importación o sus objetos.

Aquí hay un ejemplo trivial (y ingenuo):

package Mixin::DumpObj;
use Data::Dumper;
use Sub::Exporter -setup => {
  exports => [ qw(dump) ]
};
sub dump {
  my ($self) = @_;
  return Dumper($self);
}

Al escribir su propia clase de objeto, puede importar "dump" para ser utilizada como un método, llamado así:

$object->dump;

Suponiendo que la clase de importación proporcionará una cierta interfaz, un módulo de exportación de métodos puede usarse como un simple complemento:

package Number::Plugin::Upto;
use Sub::Exporter -setup => {
  into    => 'Number',
  exports => [ qw(upto) ],
  groups  => [ default => [ qw(upto) ] ],
};
sub upto {
  my ($self) = @_;
  return 1 .. abs($self->as_integer);
}

La línea "into" en la configuración dice que este complemento exportará, por defecto, al paquete Number, no al paquete que lo está usando ("use"). Sin embargo, se puede exportar de todos modos y funcionará siempre que el destino proporcione un método "as_integer" como el que espera. Para importarlo a un destino diferente, se puede escribir simplemente:

use Number::Plugin::Upto { into => 'Quantity' };

Mezclar comportamiento externo complejo

Al exportar métodos para ser usados como métodos (ver arriba), una opción muy poderosa es exportar métodos que son rutinas generadas que mantienen una referencia encapsulada al módulo exportador. Esto permite a un usuario importar un único método que se implementa en términos de un paquete completo y bien estructurado.

Aquí hay un ejemplo muy pequeño:

package Data::Analyzer;
use Sub::Exporter -setup => {
  exports => [ analyze => \'_generate_analyzer' ],
};
sub _generate_analyzer {
  my ($mixin, $name, $arg, $col) = @_;
  return sub {
    my ($self) = @_;
    my $values = [ $self->values ];
    my $analyzer = $mixin->new($values);
    $analyzer->perform_analysis;
    $analyzer->aggregate_results;
    return $analyzer->summary;
  };
}

Si es importado por cualquier paquete que proporcione un método "values", este complemento proporcionará un único método "analyze" que actúa como una interfaz simple a un conjunto más complejo de comportamientos.

Aún más importante, dado que el valor de $mixin será el invocante sobre el cual se llamó realmente al método "import", se puede subclasificar "Data::Analyzer" y reemplazar solo piezas individuales del comportamiento complejo, facilitando la escritura de kits de herramientas complejos y subclasificables con puntos de entrada únicos y simples para interfaces externas.

Exportar constantes

Aunque Sub::Exporter no está en el negocio de exportar constantes, es fácil exportar constantes utilizando uno de sus módulos hermanos, Package::Generator.

package Important::Constants;

use Sub::Exporter -setup => {
  collectors => [ constants => \'_set_constants' ],
};

sub _set_constants {
  my ($class, $value, $data) = @_;

  Package::Generator->assign_symbols(
    $data->{into},
    [
      MEANING_OF_LIFE => \42,
      ONE_TRUE_BASE   => \13,
      FACTORS         => [ 6, 9 ],
    ],
  );
  return 1;
}

Entonces, alguien puede escribir:

use Important::Constants 'constants';

print "The factors @FACTORS produce $MEANING_OF_LIFE in $ONE_TRUE_BASE.";

(Las constantes deben exportarse a través de un colector, ya que alteran efectivamente la clase de importación de una manera distinta a la instalación de subrutinas).

Alterar el @ISA del importador

Es trivial crear un colector que cambie la herencia de un paquete de importación:

use Sub::Exporter -setup => {
  collectors => { -base => \'_make_base' },
};
sub _make_base {
  my ($class, $value, $data) = @_;
  my $target = $data->{into};
  push @{"$target\::ISA"}, $class;
}

Entonces, el usuario de su clase puede escribir:

use Some::Class -base;

y convertirse en una subclase. Esto puede ser muy útil para construir, por ejemplo, un módulo que ayuda a construir complementos. Podemos querer importar algunas utilidades, pero también queremos heredar el comportamiento de una clase base de complemento;

package Framework::Util;
use Sub::Exporter -setup => {
  exports    => [ qw(log global_config) ],
  groups     => [ _plugin => [ qw(log global_config) ]
  collectors => { '-plugin' => \'_become_plugin' },
};
sub _become_plugin {
  my ($class, $value, $data) = @_;
  my $target = $data->{into};
  push @{"$target\::ISA"}, $class->plugin_base_class;
  push @{ $data->{import_args} }, '-_plugin';
}

Ahora, puede escribir un complemento como este:

package Framework::Plugin::AirFreshener;
use Framework::Util -plugin;

Comerse el cerebro de Exporter.pm

A menudo, los módulos de exportación se escriben como una forma de distribuir un conjunto de subrutinas. Sin embargo, a veces es posible que desee distribuir un solo paquete de código que tenga una dependencia de su propio conjunto de comportamientos. Esto puede ser un desafío, ya que Exporter.pm está diseñado para exportar un conjunto predefinido de símbolos, no para distribuir un solo paquete de código.

Considere el siguiente código:

package Module::Util::Exported;
use Sub::Exporter -setup => {
  exports => [ delegate => \_generate_delegate ]
};
sub _generate_delegate {
  my ($class, $name, $arg, $col) = @_;
  return sub {
    my ($self) = @_;
    return $self->call_module_util_exported;
  };
}

Ahora, si un usuario escribe:

package My::Class;
use Module::Util::Exported;

...y si My::Class tiene un método llamado "call_module_util_exported", entonces esto funcionará como se esperaba. El paquete de importación (My::Class) obtiene una rutina "delegate" que llama a un método en sí mismo.

Sin embargo, esto no le da a Module::Util::Exported su propia identidad, por así decirlo. Podría tener mucho sentido hacer que el código exportado sea una instancia de Module::Util::Exported en lugar de una rutina generada.

Aquí hay un ejemplo que lo hace:

package Module::Util::Exported::Instance;
use Sub::Exporter -setup => {
  exports => [ delegate => \'_generate_delegate' ]
};
sub _generate_delegate {
  my ($class, $name, $arg, $col) = @_;
  my $instance = $class->new; # O $col->{invocant}->new si fuera apropiado
  return sub {
    my ($self) = @_;
    return $instance->call_module_util_exported($self);
  };
}

Ahora, Module::Util::Exported::Instance es un paquete con su propia identidad, y tiene una forma fácil de exportar comportamientos en nombre de él.
