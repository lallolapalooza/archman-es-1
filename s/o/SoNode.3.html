Descripción Detallada

La clase SoNode es la clase base para los nodos utilizados en grafos de escena.

Coin es una biblioteca de visualización 3D de *modo retenido* (basada en la biblioteca OpenGL de *modo inmediato*). "Modo retenido" significa que en lugar de pasar comandos para dibujar primitivas gráficas directamente al renderizador, usted construye estructuras de datos que son renderizadas por la biblioteca *a demanda*.

Las clases de nodo son la *primitiva* principal para construir estas estructuras de datos. En Coin, usted construye jerarquías de árboles compuestas por diferentes tipos de nodos: nodos de grupo (para la disposición de la estructura del árbol de otros nodos), nodos de apariencia (para configurar materiales, texturas, etc.), nodos de forma (para la geometría real) y nodos para iluminación y posicionamiento de cámara.

Un problema común para los recién llegados a la API es que no se debe y no se puede usar el operador delete de C++ en los nodos - el destructor es protegido. Esto se debe a que las instancias de nodo utilizan una técnica común para el manejo de recursos de memoria llamada "conteo de referencias". Los nodos se eliminan (de hecho, se eliminan a sí mismos) cuando se llama a su método unref() y el conteo de referencias llega a cero.

Un efecto secundario importante de esto es que las clases derivadas de SoNode *no* deben ser asignadas estáticamente, ni en memoria de módulo estático ni en marcos de pila de funciones. Las clases derivadas de SoNode *siempre* deben ser asignadas dinámicamente desde el montón de memoria con el operador new (o de lo contrario el esquema de autodestrucción al desreferenciar a 0 no funcionaría).

Por lo general, los programadores de aplicaciones no llamarán manualmente a ref() y unref() con mucha frecuencia, ya que pasan los nodos directamente a SoGroup::addChild() o So@Gui@Viewer::setSceneGraph() o algo similar. Estas funciones llamarán a ref() en los nodos que se les pasan, y a unref() cuando terminen con ellos.

Asegúrese de llamar a ref() en los nodos a los que conserva punteros para que no se eliminen accidentalmente de forma prematura debido a una llamada a unref() desde dentro de la propia biblioteca. Si no ha llamado manualmente a ref() en un nodo raíz de nivel superior, este se eliminará automáticamente. Este código muestra cómo hacerlo:

SoSeparator * root = new SoSeparator; // el recuento de referencias de root comienza en cero
root->addChild(foo_node); // el recuento de referencias de foo_node aumenta en 1
root->addChild(bar_node); // recuento de referencias de bar_node +1
// aumentar el recuento de referencias antes de pasarlo a setScenegraph(), para evitar
// destrucción prematura
root->ref();
myviewer->setSceneGraph(root); // recuento de referencias de root +1, ahora es 2
// [visualización y procesamiento varios]
// myviewer liberará su referencia al nodo raíz, disminuyendo así
// su recuento de referencias en 1
myviewer->setSceneGraph(NULL);
// el recuento de referencias de root pasa de +1 a 0, y se autodestruirá de forma controlada
root->unref();
// evitar puntero colgante, en caso de que se intente usar "root" de nuevo
// (no es realmente necesario, pero es bueno para detectar errores temprano)
root = NULL;

Para obtener información completa e introducciones de estilo tutorial a todos los problemas de la API, consulte "Inventor Mentor: Programming Object-Oriented 3DGraphics with Open Inventor" (ISBN 0-201-62495-8). Contiene explicaciones detalladas sobre todos los principios básicos involucrados.

Consulte específicamente la sección "Referencias y Eliminación" en el Capítulo 3 para aprender sobre las técnicas de conteo de referencias.

A menudo, al usar la biblioteca Coin, uno está interesado en crear extensiones para ella. De particular interés es la configuración de nodos de extensión, que luego son recorridos, renderizados y utilizados de otra manera por el resto de la biblioteca como cualquier nodo interno.

void SoNode::setOverride (const SbBool state)

Establece la bandera de anulación.

Si esta bandera es TRUE, los valores de los campos de este nodo anularán los valores de los campos de otros nodos del mismo tipo durante el recorrido del grafo de escena.

Una aplicación común para los "nodos de anulación" es colocarlos en la parte superior del árbol como una forma conveniente de forzar, por ejemplo, un estilo de dibujo común en todo el árbol.

La bandera de anulación no existe en el formato de archivo de Inventor. Esta bandera, en otras palabras, no es persistente y debe establecerse mediante programación. La justificación de esta bandera es que los visores puedan controlar el estilo de renderizado de los modelos 3D, por lo que se vería mal si algunas partes de ciertos modelos no se adhirieran repentinamente al modo del visor.

SoNode * SoNode::copy (SbBool copyconnections = FALSE) const [virtual]

Haz un duplicado de este nodo y devuelve un puntero al duplicado.

Si este nodo es un nodo de grupo, los hijos también se copian y devolvemos un puntero a la raíz de una copia completa del subgrafo con raíz aquí.

Si copyconnections es TRUE, también copiamos las conexiones a los campos dentro de este nodo (y lo mismo para cualquier hijo e hijo de hijos, etc.).

Tenga en cuenta que esta función se ha convertido en virtual en Coin, lo que no es el caso en la API original de Open Inventor. Es posible que volvamos a cambiar este método a no virtual en versiones principales de Coin después de esto, ya que se hizo virtual más o menos por error. Así que por favor, no escriba código de aplicación que dependa de que SoNode::copy() sea virtual.

La razón por la que este método no debería ser virtual es que esta no es la función que el programador de aplicaciones debe sobrescribir en nodos de extensión si necesita un comportamiento especial durante una operación de copia (como copiar el valor de datos internos que no están expuestos como campos).

Para ese propósito, sobrescriba el método copyContents(). Su método copyContents() sobrescrito debe entonces tanto copiar los datos internos como llamar al método copyContents() de la superclase para el manejo automático de campos y otros datos comunes.

SbBool SoNode::affectsState (void ) const [virtual]

Devuelve TRUE si el nodo podría tener algún efecto en el estado durante el recorrido.

Si devuelve FALSE, ningún dato en el estado de recorrido cambiará del estado pre-recorrido al estado post-recorrido. Por ejemplo, el nodo SoSeparator devolverá FALSE, ya que empuja y extrae el estado antes y después del recorrido de sus hijos. Todos los nodos SoShape también devolverán FALSE, ya que simplemente enviar datos de geometría al motor de renderizado no afectará el estado de renderizado real.

El método predeterminado devuelve TRUE, basándose en la filosofía de "mejor prevenir que lamentar".

void SoNode::copyContents (const SoFieldContainer * from, SbBool copyconnections) [virtual]

Deeply copies all data from from to this instance, except external references if copyconnections is False.

This is the method that should be overridden by extension nodes / engines / draggers / etc. that must address non-automated internal data.

To copy nodes from application code, you should not invoke this method directly, but use the SoNode::copy() method:

SoNode * mynewnode = templatenode->copy();

The same also applies to engines.

Make sure that when you override the copyContents() method in your extension class, you also call it upwards in the inheritance hierarchy, as copyContents() in e.g. SoNode and SoFieldContainer performs important functions. It should look something like:

void
MyCoinExtensionNode::copyContents(const SoFieldContainer * from,
                                  SbBool copyconnections)
{
  // let the superclasses do their part (copy fields, instance name, etc.)
  SoNode::copyContents(from, copyconnections);

}

Detailed Description

This is the superclass for all node classes in the Coin library.

Nodes are the fundamental building blocks of a scene graph. They represent geometric shapes, lights, cameras, transformations, and other scene graph elements.

The SoNode class provides common functionality for all nodes, such as:

  • Unique identification (SoNode::getUniqueID()).
  • Managing children nodes (for nodes that have children).
  • Traversal and notification mechanisms.
  • Node type information.
