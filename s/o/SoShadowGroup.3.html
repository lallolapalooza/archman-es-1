Detailed Description

The SoShadowGroup node is a group node used for shadow rendering.

Children of this node can receive shadows, and cast shadows on other children. Use the SoShadowStyle node to control shadow casters and shadow receivers.

Please note that all shadow casters will be rendered twice. Once to create the shadow map, and once for normal rendering. If you're having performance issues, you should consider reducing the number of shadow casters.

The algorithm used to render the shadows is Variance Shadow Maps (http://www.punkuser.net/vsm/). As an extra bonus, all geometry rendered with shadows can also be rendered with per fragment Phong lighting.

This node will search its subgraph and calculate shadows for all SoSpotLight nodes. The node will use one texture unit for each spot light, so for this node to work 100%, you need to have num-spotlights free texture units while rendering the subgraph.

Currently, we only support scenes with maximum two texture units active while doing shadow rendering (unit 0 and unit 1). This is due to the fact that we emulate the OpenGL shading model in a shader program, and we're still working on creating a solution that updates the shader program during the scene graph traversal. Right now a shader program is created when entering the SoShadowGroup node, and this is used for the entire subgraph.

FILE FORMAT/DEFAULTS:

SoShadowGroup {
  isActive TRUE
  intensity 0.5
  precision 0.5
  quality 0.5
  shadowCachingEnabled TRUE
  visibilityRadius -1.0
  visibilityFlag LONGEST_BBOX_EDGE_FACTOR
  epsilon 0.00001
  threshold 0.1
  smoothBorder 0.0
}

During the normal rendering pass, the shadow map is used to determine whether a pixel is in shadow or not. .Pp The current implementation supports one light source only, and does not support multiple lights being combined. The light source must be defined as a .Xr SoLight 3 node somewhere in the subgraph below the .Nm SoShadowGroup node. The shadow calculations are performed using a shader program, and requires that the system has support for GLSL (OpenGL Shading Language). .Pp The shadow calculations are done using the following approach: .Pp .RS .IP \(bu 4 Draw the scene from the light's perspective into a texture. .IP \(bu 4 Draw the scene normally, and for each pixel, sample the texture. If the sampled depth is greater than the depth of the pixel, it is in shadow. .RE .Pp Because of the nature of shadow maps, aliasing artifacts may occur. Coin provides several mechanisms to reduce these artifacts: .RS .IP \(bu 4 PCF (Percentage Closer Filtering). This technique is enabled by default and samples the shadow map multiple times in order to reduce aliasing. .IP \(bu 4 shadow map smoothing. This is done as a post processing step on the shadow map, and it is an option that can be enabled by setting the .Fl smoothBorder field. .IP \(bu 4 epsilon. This field is used to offset the shadow map depth from the model depth. A small value is needed to avoid shadow acne or flickering. .IP \(bu 4 threshold. This field can be used to avoid light bleeding in merged shadows cast from different objects. .RE .Pp The shadow map resolution can be controlled by the .Fl precision field. .Pp The .Fl quality field can be used to tune the shader program complexity. A higher value will mean that more calculations are done per fragment instead of per vertex. .Pp The clipping planes for the shadow map rendering can be set manually using the .Fl visibilityNearRadius and .Fl visibilityRadius fields, or they can be calculated automatically using the .Fl visibilityFlag field. .Pp The .Nm SoShadowGroup node is a subclass of .Xr SoSeparator and inherits its behavior. .Pp .Sh EXAMPLE .Pp The following scene graph snippet will render a scene with shadows: .Pp .PP .CS // Shadow map generation requires shaders, so we must enable them. // This is normally done via SoSceneManager::setShaderManager() // For this example we just assume a shader manager is present.
