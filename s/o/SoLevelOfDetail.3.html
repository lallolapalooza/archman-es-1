Descripción Detallada

La clase SoLevelOfDetail se utiliza para elegir un hijo basado en su tamaño proyectado.

Un mecanismo de nivel de detalle es típicamente usado por programadores de aplicaciones para ayudar a la biblioteca a acelerar el renderizado.

La forma en que funciona un mecanismo de nivel de detalle es básicamente así:

El programador de la aplicación proporciona varias versiones de complejidad variable de *la misma* geometría / forma, ordenadas de "más compleja" a "menos compleja" (donde "compleja" en este contexto debe entenderse como más o menos detallada en el número de polígonos / formas utilizadas para renderizarla).

El sistema de renderizado en tiempo de ejecución, al recorrer el grafo de escena, calculará sobre la marcha ya sea la distancia desde la cámara al modelo 3D en cuestión, o el número de píxeles en la proyección en pantalla del modelo 3D. Este valor se utiliza luego para decidir qué versión del modelo se renderizará realmente: a medida que el modelo se aleja de la cámara, se utiliza una versión menos detallada del modelo. Y viceversa, a medida que el modelo se acerca a la cámara, se renderizan versiones cada vez más detalladas del mismo.

Esto es, en muchas circunstancias, una forma muy efectiva de permitir que el programador de la aplicación ayude a optimizar *profundamente* el renderizado de su escena 3D.

Por supuesto, existe un compromiso con la técnica de nivel de detalle: más versiones del mismo modelo 3D significa que el grafo de escena consumirá más recursos de memoria de la aplicación. Además, generar el conjunto de versiones cada vez menos detalladas de un modelo 3D a partir del original a menudo no es una tarea trivial para hacerla correctamente. El proceso a menudo es asistido por software como el que Kongsberg Oil & Gas Technologies ofrece en su paquete <a href="http://www.rational-reducer.com">Rational Reducer</a>. El nodo SoLevelOfDetail implementa la técnica de nivel de detalle de "tamaño proyectado" (a diferencia de la técnica de "distancia al objeto", como la realiza el nodo SoLOD). El nodo funciona comparando el tamaño proyectado actual del rectángulo más pequeño que cubre la caja delimitadora de la geometría de sus hijos. Junto con este conjunto de modelos de la misma forma, también se proporciona una especificación de cuándo cambiarlos. Ejemplo de diseño del grafo de escena: @code LevelOfDetail { screenArea [ 2000, 500, 50 ] DEF version-0 Separator { # versión más compleja / detallada / pesada del subgrafo } DEF version-1 Separator { # versión menos compleja del subgrafo } DEF version-2 Separator { # versión aún menos compleja del subgrafo } DEF version-3 Separator { # versión más simple / "ligera" del subgrafo } } @endcode La forma en que el subgrafo de escena anterior funcionaría sería la siguiente: si el área rectangular alrededor de la caja delimitadora proyectada del modelo cubre *más de 2000 píxeles* (lo que significa que estará bastante cerca de la cámara), se recorrería la versión más compleja del modelo (version-0) (y se renderizaría, por supuesto). Si el área proyectada estuviera *entre 500 y 2000 píxeles*, se utilizaría el modelo version-1. Lo mismo si el área proyectada estuviera entre 50 y 500 píxeles, se usaría la versión version-2 del modelo. Finalmente, si el área de la caja delimitadora proyectada fuera *menor a 50 píxeles cuadrados*, se usaría la versión presumiblemente menos detallada del modelo. (Un "truco" común es hacer que el último de los hijos del nodo SoLevelOfDetail sea solo un subgrafo vacío, para que no se renderice ninguna geometría si el modelo está lo suficientemente lejos. Esto, por supuesto, tendrá un efecto positivo en el tiempo total de renderizado de todo el grafo de escena.) Tenga en cuenta que el vector SoLevelOfDetail::screenArea se verá influenciado por los nodos SoComplexity precedentes de la siguiente manera: si el valor de SoComplexity se establece de 0.0 a 0.5, se seleccionarán niveles de detalle inferiores a lo normal para el recorrido. Si el valor de SoComplexity es superior a 0.5, se utilizarán niveles de detalle superiores a lo normal. Un valor de SoComplexity igual a 1.0 hará que siempre se utilice el primer hijo de SoLevelOfDetail. Como se mencionó anteriormente, existe otro nodo de nivel de detalle en la biblioteca Coin: SoLOD. La diferencia entre este y aquel es simplemente que en lugar del área proyectada de la caja delimitadora, SoLOD utiliza la distancia entre la cámara y el objeto para determinar cuándo cambiar entre las diferentes versiones del modelo. Usar SoLOD es más rápido, ya que calcular el área proyectada de la caja delimitadora requiere una cierta cantidad de cálculos. Pero usar SoLevelOfDetail a menudo es "mejor", en el sentido de que es realmente el tamaño y la visibilidad de un modelo en la ventana de visualización lo que determina si podemos cambiar a una versión menos compleja sin perder suficiente detalle como para causar una degradación visual perceptible.

Detailed Description

The SoLevelOfDetail node is a group node that selects which of its children to render based on the size of the node's bounding box projected onto the screen.

The screenArea field defines the screen size thresholds. The children are sorted in ascending order of their screen area requirements. During rendering, the SoLevelOfDetail node calculates the screen area of its bounding box and selects the first child whose screen area requirement is less than or equal to the calculated screen area.

If no children are defined, or if the calculated screen area is smaller than the smallest threshold, no children are rendered.

Example:

SoLevelOfDetail {
  screenArea [ 0.0, 10000.0, 1000000.0 ]
  children [
    # Child 0: Rendered if bounding box is <= 0.0 screen area (effectively never)
    # ...
    # Child 1: Rendered if bounding box is <= 10000.0 screen area
    # ...
    # Child 2: Rendered if bounding box is <= 1000000.0 screen area
    # ...
  ]
}

In this example, the screenArea field is a vector of four floats, defining thresholds for screen area. The first element (0.0) is implicitly used for the lowest LOD (Level of Detail), and subsequent elements define increasing thresholds. The number of children should typically be one greater than the number of thresholds in the screenArea field. If the screenArea field is empty, all children are rendered.

The screenArea field stores the thresholds. The children of the SoLevelOfDetail node are indexed starting from 0. The i-th child (where i > 0) is rendered if the screen area of the node is less than or equal to the i-1-th element of the screenArea field. The first child (index 0) is rendered if the screen area is less than or equal to 0.0f.

If the screenArea field has N elements, the node will have at most N+1 children. The i-th child will be rendered if the screen area is less than or equal to screenArea[i-1].

The screenArea field defaults to containing a single value: 0.0f.
