SOAP::Transport(3) Documentación contribuida por usuarios de Perl SOAP::Transport(3)

NOMBRE

SOAP::Transport - una clase abstracta extendida por módulos de transporte más especializados

DESCRIPCIÓN

Los objetos de la clase SOAP::Transport gestionan dos roles: gestionan tanto los parámetros relacionados con el transporte establecidos a través del objeto SOAP::Lite contenedor, como la selección y carga de un módulo de transporte apropiado. Esto se hace con una función AUTOLOAD dentro de la clase que intercepta todos los métodos más allá de los dos definidos a continuación y los redirige al código de implementación de transporte subyacente.

MÉTODOS

new
$trans = SOAP::Transport->new;

Este es el constructor, que normalmente no es llamado directamente por una aplicación. Una aplicación puede usar esto para crear un nuevo objeto SOAP::Transport, que puede ser instalado usando el método SOAP::Lite->transport definido anteriormente. No se reconocen argumentos.

proxy(opcional cadena URL)
$trans->proxy('http://www.blackperl.com/SOAP');

Obtiene o establece el proxy (endpoint). Este método debe ser llamado antes de llamar a cualquier otro método. El código de transporte apropiado se carga basándose en el esquema especificado por la propia URL (http, jabber, etc.). Hasta que este método se llama por primera vez con una cadena URL, el código subyacente aún no se ha cargado, y los métodos no están disponibles. Al obtener el proxy actual (llamando sin parámetros), el valor devuelto es una referencia al objeto cliente creado a partir de la clase de protocolo que coincidió con el endpoint, no el endpoint en sí.

SUBCLASES DE SOAP Transport

Debido a que la mayor parte del trabajo se realiza dentro del propio módulo "SOAP::Lite", muchos de los módulos de nivel de transporte son muy simples en sus implementaciones. Se espera que los módulos de transporte definan clases de cliente y servidor dentro de sus archivos. Si un módulo define solo un tipo, se asume que el protocolo de transporte en sí solo admite ese lado de la conversación. Un ejemplo es SOAP::Transport::FTP, que solo proporciona una clase "SOAP::Transport::FTP::Client".

"SOAP::Transport::FTP" - Solo clase cliente

"SOAP::Transport::HTTP" - Clases cliente y servidor para CGI, FCGI, Daemon y mod_perl

"SOAP::Transport::IO" - Solo clase servidor

"SOAP::Transport::JABBER" - Clases servidor y cliente

"SOAP::Transport::LOCAL" - Solo clase cliente

"SOAP::Transport::MAILTO" - Solo clase cliente

"SOAP::Transport::MQ" - Clases servidor y cliente

"SOAP::Transport::POP3" - Solo clase servidor

"SOAP::Transport::TCP" - Clases servidor y cliente

MÉTODOS

Se espera que cada subclase de SOAP::Transport defina (o herede, si es una subclase de otra clase de transporte) al menos dos métodos. También se espera que las clases de transporte desarrolladas recientemente cumplan con esta interfaz. Se espera que los clientes implementen los métodos "new" y "send_receive", y se espera que los servidores implementen los métodos "new" y "handle". Aquí están:

new(opcional pares clave/valor)
$objeto = $clase->new(%params);

Crea una nueva instancia de objeto y la devuelve. Al igual que los constructores de las clases "SOAP::Lite" y SOAP::Server, todos los argumentos pasados se tratan como pares clave/valor, donde se espera que la clave sea uno de los métodos que admite la clase, y el valor sea el argumento (o referencia a lista de argumentos) para el método.

send_receive(pares_clave/valor pares)
$cliente->send_recieve(%tabla_hash);

(Requerido solo para clases cliente) Cuando los objetos SOAP::Lite intentan enviar solicitudes, el medio para hacerlo es intentar llamar a este método en el objeto contenido en el objeto SOAP::Transport contenido en el cliente. Se espera que todos los clientes proporcionen esto, y la llamada a este método siempre pasa cuatro valores para las claves del hash:

action
La URI que especifica la acción que se está realizando, generalmente el resultado del hook on_action en el objeto cliente.
encoding
La URI del esquema de codificación que rige el mensaje que se envía.
endpoint
La URI que especifica el endpoint al que se envía el mensaje.
envelope
El contenido XML del mensaje que se va a enviar. Generalmente es el valor de retorno del método envelope del objeto serializador que mantiene el objeto cliente.
parts
Archivos adjuntos para agregar a la solicitud. Actualmente, esto solo admite una matriz de objetos MIME::Entity, pero en teoría podría admitir archivos adjuntos de cualquier formato.
handle
$servidor->handle;

(Requerido solo para clases servidor.) Este método es el punto central para que las diversas clases de servidor proporcionen una interfaz para manejar solicitudes. El conjunto exacto y la naturaleza de los parámetros generalmente varían según las propias clases.

SOAP::Transport::HTTP

El módulo de transporte más utilizado es la implementación HTTP. Este se carga cada vez que se proporciona un endpoint que comienza con los caracteres http:// o https://. Este es también el más complejo de los módulos de transporte, ya que define no solo una clase cliente, sino también varias clases de servidor diferentes.

AJUSTES DEL PROXY HTTP

Dado que "SOAP::Client" hereda de "LWP::UserAgent", puede utilizar cualquiera de los ajustes de proxy de "LWP::UserAgent". Por ejemplo:

SOAP::Lite->proxy("http://endpoint.server/",
                  proxy => ["http" => "http://my.proxy.server"]);

o

$soap->transport->proxy("http" => "http://my.proxy.server");

Los ejemplos de código anteriores deberían especificar un servidor proxy para usted. Y si usa "HTTP_proxy_user" y "HTTP_proxy_pass" para la autorización del proxy, "SOAP::Lite" lo manejará correctamente.

AUTENTICACIÓN BÁSICA HTTP

La autenticación básica HTTP se logra sobrescribiendo la subrutina get_basic_credentials en "LWP::UserAgent" (de la que "SOAP::Transport::HTTP::Client" es una subclase):

BEGIN {
  sub SOAP::Transport::HTTP::Client::get_basic_credentials {
    return 'username' => 'password';
  }
}

AUTENTICACIÓN BASADA EN COOKIES

use HTTP::Cookies;
my $cookies = HTTP::Cookies->new(ignore_discard => 1);
# también puedes añadir 'file' si quieres guardarlas entre sesiones
my $soap = SOAP::Lite->proxy('http://localhost/');
$soap->transport->cookie_jar($cookies);

O, alternativamente, puedes hacer lo anterior en una sola línea:

$soap->proxy('http://localhost/',
             cookie_jar => HTTP::Cookies->new(ignore_discard => 1));

Las cookies se tomarán de la respuesta y se proporcionarán a la solicitud. Puede acceder y manipular las cookies recibidas, así como agregar sus propias cookies utilizando las interfaces de "HTTP::Cookies".

Para habilitar la autenticación basada en certificados, deberás pasar tu certificado y clave como opciones adicionales al método proxy() de la siguiente manera:

$soap->transport->ssl_opts(

Para que la autenticación de certificados funcione, necesitas configurar tres variables de entorno: "HTTPS_CERT_FILE", "HTTPS_KEY_FILE" y, opcionalmente, "HTTPS_CERT_PASS". Esto se puede hacer desde la línea de comandos o directamente en tu script de Perl usando la variable $ENV:

$ENV{HTTPS_CERT_FILE} = 'client-cert.pem';
$ENV{HTTPS_KEY_FILE}  = 'client-key.pem';

Estos ajustes son referenciados por "Crypt::SSLeay". Otras opciones (por ejemplo, verificación del peer CA) se pueden especificar de manera similar. Consulta la documentación de Crypt::SSLeay para más información.

Ten en cuenta que probablemente no deberías usar Crypt::SSLeay porque no realiza verificación de nombres de host; LWP::UserAgent usa IO::Socket::SSL por defecto. Consulta también https://metacpan.org/pod/Crypt::SSLeay#DO-YOU-NEED-Crypt::SSLeay.

COMPRESIÓN

SOAP::Lite te ofrece la opción de habilitar la compresión en la transmisión usando HTTP *solo* tanto en el contexto del servidor como del cliente, siempre y cuando tengas Compress::Zlib instalado. La compresión y descompresión se realizan de forma transparente para tu aplicación.

Un servidor responderá con un mensaje codificado/comprimido solo si el cliente ha indicado que puede aceptarlo (indicado por el cliente enviando una cabecera HTTP "Accept-Encoding" con un valor 'deflate' o '*').

"SOAP::Lite" los clientes tienen lógica de respaldo implementada para que, si un servidor no entiende la codificación especificada (es decir, "Content-Encoding: deflate") y devuelve el código de estado HTTP apropiado (415 NO ACEpTABLE), el cliente repetirá la solicitud sin usar codificación/compresión. El cliente luego almacenará este servidor en una caché por sesión, de modo que todas las solicitudes posteriores a ese servidor se transmitirán sin codificación.

La compresión se habilita en el lado del cliente especificando la opción "compress_threshold", y si el tamaño de la solicitud actual excede ese umbral.

Muestra de código del cliente

print SOAP::Lite
  ->uri('http://localhost/My/Parameters')
  ->proxy('http://localhost/', options => {compress_threshold => 10000})
  ->echo(1 x 10000)
  ->result;

Los servidores responderán con un mensaje comprimido si se ha especificado la opción "compress_threshold", si el tamaño de la respuesta actual excede ese umbral y si el cliente que realiza la llamada transmitió la cabecera HTTP "Accept-Encoding" apropiada.

Muestra de código del servidor

my $server = SOAP::Transport::HTTP::CGI
  ->dispatch_to('My::Parameters')
  ->options({compress_threshold => 10000})
  ->handle;

Ver también: Compress::Zlib

SOAP::Transport::HTTP::Client

Hereda de: SOAP::Client, LWP::UserAgent (del paquete LWP).

Con esta clase, los clientes pueden usar HTTP para enviar mensajes. Esta clase proporciona solo los métodos básicos new y send_receive. Los objetos de esta clase entienden la opción compress_threshold y la usan si el servidor con el que se comunica también la entiende.

CAMBIANDO LA CLASE PREDETERMINADA DE USERAGENT

Por defecto, "SOAP::Transport::HTTP::Client" extiende "LWP::UserAgent". Pero en algunas circunstancias, un usuario puede desear cambiar la clase de UserAgent por defecto por la suya propia para manejar mejor las conexiones persistentes, o por "LWP::UserAgent::ProxyAny", por ejemplo, que tiene mejor interoperabilidad con Win32/Internet Explorer.

Se puede usar el siguiente código como ejemplo de cómo cambiar la clase de UserAgent predeterminada.

use SOAP::Lite;
use SOAP::Transport::HTTP;
$SOAP::Transport::HTTP::Client::USERAGENT_CLASS = "My::UserAgent";
my $client = SOAP::Lite->proxy(..)->uri(..);
my $som = $client->myMethod();

Sin embargo, hay una advertencia. La clase UserAgent que uses, *debe* ser también una subclase de "LWP::UserAgent". Si no lo es, "SOAP::Lite" emitirá el siguiente error: "Could not load UserAgent class <USERAGENT CLASS>."

HTTP-KEEP-ALIVE, TIEMPOS DE ESPERA Y MÁS

Dado que "SOAP::Transport::HTTP::Client" extiende "LWP::UserAgent", todos los métodos disponibles en "LWP::UserAgent" también están disponibles para tus clientes SOAP. Por ejemplo, usar "LWP::UserAgent" para mantener vivas las conexiones HTTP se logra usando el siguiente código:

my $ua = LWP::UserAgent->new(
      keep_alive => 1,
      timeout    => 30
);

Por lo tanto, los mismos parámetros de inicialización que pasarías a "LWP::UserAgent" también se pueden pasar a la subrutina "proxy" de tu cliente SOAP::Lite de la siguiente manera:

my $soap = SOAP::Lite
   ->uri($uri)
   ->proxy($proxyUrl,
       timeout => 30,
       keep_alive => 1,
     );

Esto es cierto para todos los parámetros de inicialización y métodos de "LWP::UserAgent".

MÉTODOS

http_request
Este método te da acceso a un prototipo del objeto HTTP Request que se transmitirá a un SOAP::Server. La solicitud real utilizada es una copia de ese objeto.

No uses este método para nada que no sea establecer el comportamiento prototípico del objeto cliente.

http_response
Este método te da acceso al objeto HTTP Response que será, o fue, transmitido a un Servidor SOAP. Devuelve un objeto HTTP::Response.

SOAP::Transport::HTTP::Server

Hereda de: SOAP::Server.

Esta es la más básica de las implementaciones de servidor HTTP. Proporciona los métodos básicos, new y handle. El comportamiento del método handle se define aquí, junto con otros métodos específicos de esta clase. El rol de esta clase es principalmente actuar como superclase para las otras clases de servidor basadas en HTTP.

handle
$server->handle;

Espera que el método request haya sido utilizado para asociar un objeto HTTP::Request con el objeto servidor antes de ser llamado. Este método recupera esa referencia de objeto para acceder a la solicitud que se está manejando.

request(valor opcional)
$server->request($req_object)

Obtiene o establece la referencia del objeto HTTP::Request que el servidor procesará dentro del método handle.

response(valor opcional)
$server->response(HTTP::Response->new(...));

Obtiene o establece la referencia del objeto HTTP::Response que el servidor ha preparado para enviar de vuelta al cliente.

make_response(código, cuerpo)
$server->make_response(200, $body_xml);

Construye y devuelve un objeto de la clase HTTP::Response, utilizando el código de respuesta y el contenido proporcionados.

make_fault(argumentos de falla)
$server->response($server->make_fault(@data));

Crea una referencia de objeto HTTP::Response usando un código de respuesta HTTP predefinido para indicar que ha ocurrido una falla. Los argumentos son los mismos que los del método make_fault de la clase SOAP::Server.

product_tokens
Este método no toma argumentos y simplemente devuelve una cadena que identifica los elementos de la propia clase del servidor. Es similar a los métodos product_tokens en las clases HTTP::Daemon y Apache.

SOAP::Transport::HTTP::CGI

Hereda de: SOAP::Transport::HTTP::Server.

Esta clase es una subclase directa de SOAP::Transport::HTTP::Server y no define métodos adicionales. Incluye lógica en su implementación del método handle que se ocupa de las cabeceras de solicitud y los parámetros específicos de un entorno CGI.

EJEMPLO CGI

La siguiente muestra de código es un servicio web basado en CGI que convierte Celsius a Fahrenheit:

#!/usr/bin/perl
use SOAP::Transport::HTTP;
SOAP::Transport::HTTP::CGI
  ->dispatch_to('C2FService')
  ->handle;
BEGIN {
  package C2FService;
  use vars qw(@ISA);
  @ISA = qw(Exporter SOAP::Server::Parameters);
  use SOAP::Lite;
  sub c2f {
    my $self = shift;
    my $envelope = pop;
    my $temp = $envelope->dataof("//c2f/temperature");
    return SOAP::Data->name('convertedTemp' => (((9/5)*($temp->value)) + 32));
  }
}

EJEMPLO DE USO DE APACHE::REGISTRY

Usar un servicio web estrictamente basado en CGI tiene ciertos inconvenientes de rendimiento. Ejecutar el mismo CGI bajo el sistema Apache::Registery tiene ciertas ventajas de rendimiento.

httpd.conf

Alias /mod_perl/ "/Your/Path/To/Deployed/Modules"
<Location /mod_perl>
  SetHandler perl-script
  PerlHandler Apache::Registry
  PerlSendHeader On
  Options +ExecCGI
</Location>

soap.cgi

use SOAP::Transport::HTTP;
SOAP::Transport::HTTP::CGI
  ->dispatch_to('/Your/Path/To/Deployed/Modules', 'Module::Name', 'Module::method')
  ->handle;

ADVERTENCIA: Los despliegues dinámicos con "Apache::Registry" fallarán porque el módulo solo se cargará dinámicamente la primera vez.

Las llamadas subsiguientes producirán errores de "error de acceso denegado" porque, una vez que el módulo está ya en memoria. SOAP::Lite omitirá el depósito dinámico. Para solucionar esto, simplemente especifica tanto el PATH completo como el nombre del módulo en dispatch_to() y el módulo se cargará dinámicamente, pero luego funcionará como si estuviera bajo un depósito estático. Veamos un ejemplo en examples/server/soap.mod_cgi.

SOAP::Transport::HTTP::Daemon

Hereda de: SOAP::Transport::HTTP::Server.

La clase SOAP::Transport::HTTP::Daemon encapsula una referencia a un objeto de la clase HTTP::Daemon (de la biblioteca LWP). La clase captura los métodos que no se proporcionan localmente o por la superclase e intenta llamarlos al objeto HTTP::Daemon. Por lo tanto, todos los métodos definidos en la documentación de esa clase están disponibles para esta clase. Algunos que entran en conflicto con los métodos de SOAP::Transport::HTTP::Server (como product_tokens) se dirigen a la superclase. Además, el comportamiento del método handle es específico de esta clase:

handle
Al ser invocado, este método entra en el ciclo típico de aceptación, esperando una solicitud en el socket que el objeto daemon mantiene y procesa el contenido de la solicitud. Cuando todas las solicitudes de la conexión devueltas por el método accept de la clase HTTP::Daemon hayan sido procesadas, este método devuelve.

REUTILIZACIÓN DE SOCKETS AL REINICIAR

A menudo, al implementar un daemon HTTP, los sockets se quedan atascados cuando intentas reiniciar el servidor. Esto impide que el servidor se reinicie. A menudo, los usuarios verán un error como "No se puede iniciar el servidor: puerto ya en uso". Para evitar esto, indica a SOAP::Lite que reutilice los sockets abiertos usando "Reuse => 1":

my $daemon = SOAP::Transport::HTTP::Daemon
                -> new (LocalPort => 80000, Reuse => 1)

EJEMPLO DE SERVIDOR DAEMON

use SOAP::Transport::HTTP;
    # cambia LocalPort a 81 si deseas probar con soapmark.pl
    my $daemon = SOAP::Transport::HTTP::Daemon
      -> new (LocalAddr => 'localhost', LocalPort => 80)
      # especifica aquí la lista de objetos-por-referencia
      -> objects_by_reference(qw(My::PersistentIterator My::SessionIterator My::Chat))
      # especifica aquí la ruta a My/Examples.pm
      -> dispatch_to('/Your/Path/To/Deployed/Modules', 'Module::Name', 'Module::method')
    ;
    print "Contacta al servidor SOAP en ", $daemon->url, "\n";
    $daemon->handle;

SOAP::Transport::HTTP::Apache

Hereda de: SOAP::Transport::HTTP::Server.

Esta clase proporciona una integración de la clase base SOAP::Server con la extensión mod_perl para Apache. Para funcionar como un gestor de ubicación, el paquete proporciona un método llamado handler, al cual handle se hace un alias. El método new no es funcionalmente diferente de la superclase. Aquí están otros métodos proporcionados por esta clase:

handler(Apache request)
$server->handler($r)

Define la base para un gestor de ubicación en mod_perl. El método espera un objeto de solicitud Apache como parámetro, del cual obtiene el cuerpo de la solicitud y llama al método handle de la superclase.

Nota: En esta clase, el método local handle se hace un alias a este método.

configure(Apache request)
$server->configure(Apache->request);

Se puede proporcionar información de configuración de ubicación al objeto server usando la directiva Apache DirConfig y llamando a este método a sí mismo. Cuando se invoca, el método lee la información de configuración de directorio de Apache y busca líneas de la forma:

method => param

Cada línea que coincide con el patrón se considera como una posibilidad de método a llamar al objeto server, con el token restante como parámetro del método. Los métodos que aceptan referencias de hash se pueden especificar así:

method => key => param, key => param

Los pares clave-valor se convierten en una referencia de hash bajo demanda. Si el objeto server no reconoce el método nombrado como válido, ignora la línea.

EJEMPLO DE SERVIDOR MOD_PERL Apache

Ver examples/server/Apache.pm y Apache::SOAP para más información.

httpd.conf

<Location /soap>
    SetHandler perl-script
    PerlHandler SOAP::Apache
    PerlSetVar options "compress_threshold => 10000"
</Location>

SOAP::Apache.pm

package SOAP::Apache;
    use SOAP::Transport::HTTP;
    my $server = SOAP::Transport::HTTP::Apache
      ->dispatch_to('/Your/Path/To/Deployed/Modules', 'Module::Name', 'Module::method');
    sub handler { $server->handler(@_) }
    1;

Ver también Apache::SOAP.

SOAP::Transport::HTTP::FCGI

Hereda de: SOAP::Transport::HTTP::CGI.

Esta es una extensión de la clase SOAP::Transport::HTTP::CGI que implementa las diferencias necesarias para el protocolo FastCGI. Ningún método es funcionalmente diferente.

SOAP::Transport::IO

La clase SOAP::Transport::IO permite una proxy de I/O, permitiendo a la aplicación configurar qué archivos o manejadores de archivo se usan. Este módulo solo proporciona una clase de servidor.

SOAP::Transport::IO::Server

Hereda de: SOAP::Server.

La clase de servidor definida aquí hereda todos los métodos de SOAP::Server y añade dos métodos específicos de la naturaleza de la clase:

in
$server->in(IO::File->new($file));

Obtiene o establece el manejador de archivo actual que se utiliza como fuente de entrada.

out
$server->out(\*STDERR);

Obtiene o establece el manejador de archivo que se usa como destino de salida.

SOAP::Transport::LOCAL

El módulo SOAP::Transport::LOCAL está diseñado para proporcionar una clase de cliente sin transporte para rastrear y depurar el tráfico de comunicación. Se vincula SOAP::Client y SOAP::Server para que el mismo objeto que envía la solicitud también reciba la misma.

SOAP::Transport::LOCAL::Client

Hereda de: SOAP::Client, SOAP::Server. Las implementaciones de los métodos new y send_receive no son distintas en su interfaz. Su comportamiento merece descripción, aunque:

new
Cuando el constructor crea un objeto de esta clase, establece varias cosas más allá de la disposición normal de SOAP::Client. El método is_success se establece en un valor por defecto de 1. El método dispatch_to heredado de SOAP::Server se llama con el valor actual del array global @INC, permitiendo al cliente llamar a cualquier método que pueda encontrarse en la ruta de búsqueda válida actual. Y, como con la mayoría de los constructores en este módulo, los parámetros clave/valor opcionales se tratan como nombres de método.
send_receive
La implementación de este método simplemente pasa el contenido del paquete de datos de entrada al método handle de SOAP::Server. Aunque no hay tráfico de red (directamente) como resultado de esto, permite enviar señales de depuración a través de la herramienta SOAP::Trace.

SOAP::Transport::MAILTO

Esta clase de transporte gestiona el envío de mensajes por medio de SMTP desde la perspectiva del cliente. No proporciona una clase de servidor. La clase se selecciona cuando un objeto cliente pasa una URI para proxy o endpoint que comienza con los caracteres, mailto:.

SOAP::Transport::MAILTO::Client

Hereda de: SOAP::Client.

La clase cliente para este protocolo no define ningún método nuevo. Las funciones del constructor son del mismo estilo que las de otros constructores de clase. El comportamiento del método send_receive es ligeramente diferente de otras clases, aunque:

Cuando se invoca, el método send_receive utiliza el paquete MIME::Lite para encapsular y transmitir el mensaje. Como los mensajes de correo electrónico se envían de forma unidireccional (la respuesta es un proceso separado), no hay mensaje de respuesta que pueda devolver el método. En su lugar, se establecen todas las atribuciones relacionadas con el estado (code, message, status, is_success) y no se devuelve ningún valor explícitamente.

SOAP::Transport::POP3

El soporte de POP3 se limita a una implementación de servidor. Así como la clase MAILTO detallada anteriormente opera enviando solicitudes sin esperar a procesar una respuesta, el servidor descrito aquí acepta solicitudes y las envía sin importar si envía una respuesta excepto la que POP3 define para la entrega exitosa de un mensaje.

SOAP::Transport::POP3::Server

Hereda de: SOAP::Server.

El método new de esta clase crea un objeto de la clase Net::POP3 para usar internamente para pollear un servidor POP3 especificado para mensajes entrantes. Cuando se crea un objeto de esta clase, espera una URI que comience con el carácter pop:// y que incluya información de usuario, contraseña y el propio nombre de host.

El método handle toma los mensajes presentes en el buzón remoto y los pasa (uno por uno) al método handle de la superclase. Cada mensaje se elimina después de ser enviado. Se supone que todos los mensajes en el buzón POP3 son mensajes SOAP.

Los métodos del objeto Net::POP3 se detectan y se enrutan correctamente, permitiendo operaciones como $server->ping( ).

Esto significa que la cadena de endpoint no necesita proporcionar el usuario y la contraseña, ya que el método login de la API POP3 puede usarse directamente.
