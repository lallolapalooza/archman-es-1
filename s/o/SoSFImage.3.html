Descripción Detallada

La clase SoSFImage se utiliza para almacenar imágenes de píxeles.

La clase SoSFImage proporciona almacenamiento para mapas de imágenes 2D en línea. Las imágenes en Coin se utilizan principalmente para la compatibilidad con la asignación de texturas.

Las instancias de SoSFImage pueden ser exportadas e importadas como cualquier otra clase de campo en Coin.

Los componentes de una SoSFImage son: sus dimensiones de imagen (ancho y alto), el número de bytes utilizados para describir cada píxel (número de componentes) y un búfer de píxeles asociado. El tamaño del búfer de píxeles será ancho*alto*componentes.

Para los mapas de texturas, los componentes / bytes por píxel se traducen de la siguiente manera: use 1 para un mapa de imagen en escala de grises, 2 para escala de grises + opacidad (es decir, valor alfa), 3 para RGB (1 byte cada uno para rojo, verde y azul) y 4 componentes significa 3 bytes para RGB + 1 byte de valor de opacidad (también conocido como RGBA).

Este campo es serializable en el formato de archivo Inventor / Coin de la siguiente manera:

FIELDNAME X Y C 0xRRGGBBAA 0xRRGGBBAA ...

"X" e "Y" son las dimensiones de la imagen a lo largo de los ejes dados, "C" es el número de componentes en la imagen. El número de especificaciones de color de píxel 0xRRGGBBAA debe ser igual al número exacto de píxeles, que por supuesto viene dado por X*Y. Cada parte del valor de color del píxel está en el rango de 0x00 a 0xff (hexadecimal, 0 a 255 decimal).

Para imágenes de 3 componentes, el formato de píxel es 0xXXRRGGBB, donde el byte en el valor de color del píxel marcado como "XX" se ignora y se puede omitir.

DESCRIPTION

This field holds an image. Images are defined by their dimensions (width and height) and the pixel data.

The pixel data is a sequence of unsigned characters. The number of bytes per pixel is determined by the number of components, which is passed as an argument to setValue().

For example, an RGB image with width 2 and height 2 would have 4 pixels, and with 3 bytes per pixel (for R, G, and B values), the pixel data would consist of 4 * 3 = 12 bytes. Similarly, an RGBA image would have 4 bytes per pixel.

The image data is stored in memory as a contiguous block of bytes. The format of this block is as follows:

The first 3 bytes of the pixel data are always set to the hexadecimal value 0xFF0000, and these bytes will be ignored by the rendering engine. The fourth byte (starting from index 3) is interpreted as the alpha value (opacity).

The value of the alpha byte is interpreted as follows:

0xFF means fully opaque.

0x00 means fully transparent.

Values in between mean semi-transparent.

The fourth byte is, for instance, the alpha value of the color defined by the first three bytes.

The pixel data is stored in memory in the following format:

RRRGGBBBAAA

where each letter represents a single byte. R, G, B are the red, green, and blue color values, respectively. A is the alpha value.

The pixel data is organized in rows (along the X-axis, or width) and columns (along the Y-axis, or height). The rows are ordered from bottom to top.

Note: The default value for an SoSFImage is an empty image.

The pixel format may be specified using hexadecimal notation. For example, in an Inventor file, you might see:

Image {
  width height nc
  pixel_data...
}

where width and height are the dimensions of the image, and nc is the number of components (bytes) per pixel. The pixel_data is a sequence of integers, each representing a pixel value. The most significant byte of each integer is ignored, and the least significant byte is interpreted as the alpha value.

For example, the following specifies a 2x2 image with 4 components per pixel (RGBA):

Image 2 2 4
  0xff0000ff # opaque red
  0x00ff00ff # opaque green
  0x0000ffff # opaque blue
  0xffff00ff # opaque yellow

The pixel values are encoded as:

0xXXXXXXRG is for 2-component images (e.g., grayscale + alpha), where 0xXX is the grayscale value and "AA" is for opacity.

For 1-component images, the pixel-format is 0xXXXXXXGG, where the bytes in the pixel color values marked as "XX" are ignored and can be left out.

The pixels are read as being ordered in rows along X (width) and columns along Y (height, bottom to top).

Here's a simple example of the file format serialization, for a 2x2 RGB-image inside an SoTexture2 node, as mapped onto an SoCube:

Complexity { textureQuality 0.1 }   # set low to avoid smoothing
Texture2 {
   image 2 2 4
   0xffffffff 0x00ff0088   # white   semi-transparent green
   0xff0000ff 0xffff00ff   #  red    yellow
}

void SoSFImage::setValue (const SbVec2s & size, const int nc, const unsigned char * pixels, SoSFImage::CopyPolicy copypolicy = COPY)

Initialize this field to size and nc.

If pixels is not NULL, the image data is copied from pixels into this field. If pixels is NULL, the image data is cleared by setting all bytes to 0 (note that the behavior on passing a NULL pointer is specific for Coin, Open Inventor will crash if you try it).

The image dimensions is given by the size argument, and the nc argument specifies the number of bytes-pr-pixel. A 24-bit RGB image would for instance have an nc equal to 3.

The copypolicy argument makes it possible to share image data with SoSFImage without the data being copied (thereby using less memory resources). The default is to copy image data from the pixels source into an internal copy.

Important note: if you call this with copypolicy as either NO_COPY_AND_DELETE or NO_COPY_AND_FREE, and your application is running on Microsoft Windows, be aware that you will get mysterious crashes if your application is not using the same C library runtime as the Coin library.

The cause of this is that a memory block would then be allocated by the application on the memory heap of one C library runtime (say, for instance MSVCRT.LIB), but attempted deallocated in the memory heap of another C library runtime (e.g. MSVCRTD.LIB), which typically leads to hard-to-debug crashes.
