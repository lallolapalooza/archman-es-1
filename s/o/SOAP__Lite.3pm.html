NOMBRE

SOAP::Lite - Kit de herramientas de servicios web de Perl

DESCRIPCIÓN

SOAP::Lite es una colección de módulos de Perl que proporciona una interfaz simple y ligera al protocolo SOAP (Simple Object Access Protocol) tanto en el lado del cliente como en el del servidor.

ADVERTENCIA VERSIÓN DE PERL

A partir de la versión 1.05 de SOAP::Lite, no se admitirán versiones de Perl anteriores a la 5.8.

SOAP::Lite 0.71 será la última versión de SOAP::Lite que funcione con perl 5.005

Las versiones futuras de SOAP::Lite requerirán al menos perl 5.6.0

Si no ha tenido tiempo de actualizar su perl, debería considerar hacerlo ahora.

MÉTODOS

Todos los métodos accesores devuelven el valor actual cuando se llaman sin argumentos, mientras que devuelven la referencia del objeto mismo cuando se llaman con un nuevo valor. Esto permite encadenar las llamadas de establecimiento de atributos.

new(pares opcionales clave/valor)
$cliente = SOAP::Lite->new(proxy => $endpoint)

Constructor. Muchos de los métodos accesores definidos aquí pueden inicializarse en la creación proporcionando su nombre como clave, seguido del valor deseado. El ejemplo proporciona el valor para el elemento proxy del cliente.

transport(objeto de transporte opcional)
$transporte = $cliente->transport( );

Obtiene o establece el objeto de transporte utilizado para enviar/recibir mensajes SOAP.

Consulte SOAP::Transport para obtener más detalles.

serializer(objeto serializador opcional)
$serializador = $cliente->serializer( )

Obtiene o establece el objeto serializador utilizado para crear mensajes XML.

Consulte SOAP::Serializer para obtener más detalles.

packager(objeto empaquetador opcional)
$empaquetador = $cliente->packager( )

Proporciona acceso al objeto "SOAP::Packager" que utiliza el cliente para gestionar el uso de adjuntos. El empaquetador predeterminado es un empaquetador MIME, pero a menos que especifique partes para enviar, no se realizará ningún formato MIME.

Consulte también: SOAP::Packager.

proxy(endpoint, argumentos adicionales opcionales)
$cliente->proxy('http://soap.xml.info/ endpoint');

El proxy es el servidor o endpoint al que se conectará el cliente. Este método permite establecer el endpoint, junto con cualquier información adicional que el objeto de transporte pueda necesitar al comunicar la solicitud.

Este método es en realidad un alias para el método proxy de SOAP::Transport. Es lo mismo que escribir:

$cliente->transport( )->proxy(...argumentos);

Se pueden pasar parámetros adicionales a proxy() - véase más abajo.

Puede ser preferible establecer un nuevo endpoint sin el trabajo adicional de examinar la nueva dirección en busca de información del protocolo y comprobar que el código de soporte esté cargado y disponible. Este método permite al llamador cambiar el endpoint al que el cliente está actualmente configurado para conectarse, sin recargar el código de transporte relevante. El valor predeterminado es devolver un objeto SOAP::SOM (falso).

autotype(boolean)
$client->autotype(0);

Este método es un atajo para:

$client->serializer->autotype(boolean);

Por defecto, el serializador intenta deducir automáticamente los tipos para los datos que se envían en un mensaje. Establecer un valor falso con este método deshabilita el comportamiento.

readable(boolean)
$client->readable(1);

Este método es un atajo para:

$client->serializer->readable(boolean);

Cuando esto se usa para establecer un valor verdadero para esta propiedad, el XML generado que se envía al endpoint tiene caracteres adicionales (espacios y nuevas líneas) añadidos para hacer el XML más legible para los ojos humanos (presumiblemente para depuración). El valor predeterminado es no enviar caracteres adicionales.

headerattr(hash referencia de atributos)
$obj->headerattr({ attr1 => 'value' });

Permite establecer atributos arbitrarios en el objeto header. Ten en cuenta el requisito de que
cualquier atributo no conocido de forma nativa por SOAP debe estar calificado por un namespace. Si se usa $session->call ($method, $callData, $callHeader), SOAP::Lite serializa la información como

<soap:Envelope>
  <soap:Header>
    <userId>xxxxx</userId>
    <password>yyyyy</password>
  </soap:Header>
  <soap:Body>
    <myMethod xmlns="http://www.someuri.com">
      <foo />
    </myMethod>
  </soap:Body>
</soap:Envelope>

Los atributos, dados a headerattr, se colocan en el Header como

<soap:Header attr1="value">
bodyattr(hash referencia de atributos)
$obj->bodyattr({ attr1 => 'value' });

Permite establecer atributos arbitrarios en el objeto body. Ten en cuenta el requisito de que
cualquier atributo no conocido de forma nativa por SOAP debe estar calificado por un namespace. Ver headerattr

default_ns($uri)
Establece el namespace predeterminado para la solicitud a la URI especificada. Esto anula cualquier declaración de namespace anterior que se haya podido establecer mediante una llamada anterior a ns() o default_ns(). Establecer el namespace predeterminado hace que los elementos se serialicen sin un prefijo de namespace, así: 
<soap:Envelope>
  <soap:Body>
    <myMethod xmlns="http://www.someuri.com">
      <foo />
    </myMethod>
  </soap:Body>
</soap:Envelope>

Se ha informado que algunos servicios web .NET requieren este modismo de namespace XML.

ns($uri,$prefix=undef)
Establece la URI del namespace y opcionalmente el prefijo del namespace para la solicitud a los valores especificados. Esto anula cualquier declaración de namespace anterior que se haya podido establecer mediante una llamada anterior a ns() o default_ns().

Si no se especifica un prefijo, se generará uno automáticamente. Establecer el namespace hace que los elementos se serialicen con un prefijo de namespace declarado, así:

<soap:Envelope>
  <soap:Body>
    <my:myMethod xmlns:my="http://www.someuri.com">
      <my:foo />
    </my:myMethod>
  </soap:Body>
</soap:Envelope>
use_prefix(boolean)
Obsoleto. Utilice los métodos ns() y "default_ns" descritos anteriormente.

Atajo para "serializer->use_prefix()". Esto permite activar/desactivar el uso de un prefijo de namespace para los hijos del elemento /Envelope/Body. El valor predeterminado es 'true'.

Cuando use_prefix se establece en 'true', el XML serializado se verá así:

<SOAP-ENV:Envelope ...atributos omitidos>
  <SOAP-ENV:Body>
    <namesp1:mymethod xmlns:namesp1="urn:MyURI" />
  </SOAP-ENV:Body>
</SOAP-ENV:Envelope>

Cuando use_prefix se establece en 'false', el XML serializado se verá así:

<SOAP-ENV:Envelope ...atributos omitidos>
  <SOAP-ENV:Body>
    <mymethod xmlns="urn:MyURI" />
  </SOAP-ENV:Body>
</SOAP-ENV:Envelope>

Se ha informado que algunos servicios web .NET requieren este modismo de namespace XML.

soapversion(optional valor)
$client->soapversion('1.2');

Si no se proporciona ningún parámetro, devuelve la versión actual de SOAP que está utilizando el objeto cliente para codificar las solicitudes. Si se proporciona un parámetro, el método intenta establecerlo como la versión de SOAP que se está utilizando.

El valor debe ser 1.1 o 1.2.

envprefix(QName)
$client->envprefix('env');

Este método es un atajo para:

$client->serializer->envprefix(QName);

Obtiene o establece el prefijo del namespace para el namespace SOAP. El valor predeterminado es SOAP.

El prefijo en sí no tiene significado, pero las aplicaciones pueden desear elegir uno explícitamente para denotar diferentes versiones de SOAP o similar.

encprefix(QName)
$client->encprefix('enc');

Este método es un atajo para:

$client->serializer->encprefix(QName);

Obtiene o establece el prefijo del namespace para el namespace de las reglas de codificación. El valor predeterminado es SOAP-ENC.

Si bien puede parecer una operación innecesaria establecer un valor que no es relevante para el mensaje, como las etiquetas de namespace para los URN de sobre y codificación, la capacidad de establecer estas etiquetas explícitamente puede ser de gran ayuda para distinguir y depurar mensajes en el lado del servidor de las operaciones.

encoding(encoding URN)
$client->encoding($soap_12_encoding_URN);

Este método es un atajo para:

$client->serializer->encoding(args);

Mientras que el método anterior se ocupaba de la etiqueta utilizada para los atributos relacionados con el esquema de codificación SOAP, este método realmente establece el URN que se especificará como esquema de codificación para el mensaje. El valor predeterminado es especificar la codificación para SOAP 1.1, por lo que esto es útil para aplicaciones que necesitan codificar según las reglas de SOAP 1.2.

typelookup
$client->typelookup;

Este método es un atajo para:

$client->serializer->typelookup;

Da a la aplicación acceso a la tabla de búsqueda de tipos del objeto serializador. Ver la sección sobre SOAP::Serializer.

uri(service especificador)
Obsoleto - la subrutina "uri" está obsoleta para proporcionar un esquema de nomenclatura más intuitivo para las subrutinas que establecen namespaces. En el futuro, se le exigirá que utilice las subrutinas ns() o default_ns() en lugar de uri(). 
$client->uri($service_uri);

Este método es un atajo para:

$client->serializer->uri(service);

La URI asociada con este accesor en un objeto cliente es el especificador de servicio para la solicitud, a menudo codificado para solicitudes basadas en HTTP como el encabezado SOAPAction. Aunque los nombres pueden parecer confusos, este método no especifica el endpoint en sí. En la mayoría de las circunstancias, la "uri" se refiere al namespace utilizado para la solicitud.

A menudo, el valor puede parecer una URL válida. A pesar de esto, no tiene que apuntar a un recurso existente (y a menudo no lo hace). Este método establece y recupera este valor del objeto. Tenga en cuenta que no se activa ningún código de transporte porque no tiene efecto directo en el transporte del objeto.

multirefinplace(boolean)
$client->multirefinplace(1);

Este método es un atajo para:

$client->serializer->multirefinplace(boolean);

Controla cómo el serializador maneja los valores que tienen múltiples referencias a ellos. Recuerde de capítulos anteriores de SOAP que un valor puede ser etiquetado con un identificador, y luego referenciado en varios lugares. Cuando este es el caso de un valor, el serializador por defecto coloca el elemento de datos en la parte superior del mensaje, justo después de la etiqueta de apertura de la especificación del método. Se serializa como una entidad independiente con un ID que luego se referencia en los lugares relevantes más adelante. Si este método se utiliza para establecer un valor verdadero, el comportamiento es diferente. Cuando el atributo multirefinplace es verdadero, los datos se serializan en el primer lugar que lo referencia, en lugar de como un elemento separado más arriba en el cuerpo. Esto es más compacto pero puede ser más difícil de leer o rastrear en un entorno de depuración.

parts( ARRAY )
Se utiliza para especificar una matriz de MIME::Entity para adjuntar al mensaje SOAP transmitido. Los archivos adjuntos que se devuelven en una respuesta se pueden acceder mediante SOAP::SOM::parts().
self
$ref = SOAP::Lite->self;

Devuelve una referencia de objeto al objeto global predeterminado que el paquete "SOAP::Lite" mantiene. Este es el objeto que procesa muchos de los argumentos cuando se proporcionan en la línea de uso.

El siguiente método no es un estilo de accesor o

f método, pero tampoco encaja con el grupo que le sigue inmediatamente:

call(arguments)
$client->call($method => @arguments);

Como se ha ilustrado en capítulos anteriores, los objetos cliente de "SOAP::Lite" pueden gestionar llamadas remotas con despacho automático utilizando algunas de las características más elaboradas de Perl. `call` se utiliza cuando la aplicación desea un mayor grado de control sobre los detalles de la llamada en sí. El método puede construirse a partir de un objeto SOAP::Data, para permitir un control total sobre el espacio de nombres asociado a la etiqueta, así como otros atributos como la codificación. Esto también es importante para llamar a métodos que contienen caracteres no permitidos en los nombres de funciones de Perl, como A.B.C.

Los siguientes cuatro métodos utilizados en la clase "SOAP::Lite" están orientados a manejar los tipos de eventos que pueden ocurrir durante el ciclo de vida del mensaje. Cada uno de ellos configura una devolución de llamada para el evento en cuestión:

on_action(callback)
$client->on_action(sub { qq("$_[0]") });

Se activa cuando el objeto de transporte establece la cabecera SOAPAction para una llamada basada en HTTP. El valor predeterminado es establecer la cabecera a la cadena, uri#método, donde URI es el valor establecido por el método `uri` descrito anteriormente, y `método` es el nombre del método que se está llamando. Cuando se llama, la rutina referenciada (o el cierre, si se especifica como en el ejemplo) recibe dos argumentos, `uri` y `método`, en ese orden.

Los servicios web .NET suelen esperar "/" como separador para "uri" y "method". Para cambiar el comportamiento de SOAP::Lite para usar uri/method como cabecera SOAPAction, utilice el siguiente código:

$client->on_action( sub { join '/', @_ } );
on_fault(callback)
$client->on_fault(sub { popup_dialog($_[1]) });

Se activa cuando una llamada al método resulta en una respuesta de error (fault) del servidor. Cuando se llama, la lista de argumentos es primero el objeto cliente en sí, seguido del objeto que encapsula el error. En el ejemplo, el objeto de error se pasa (sin el objeto cliente) a una función hipotética de GUI que presenta un cuadro de diálogo de error con el texto del error extraído del objeto (que se cubrirá en breve bajo los métodos SOAP::SOM).

on_nonserialized(callback)
$client->on_nonserialized(sub { die "$_[0]?!?" });

Ocasionalmente, el serializador puede recibir datos que no puede convertir en XML compatible con SOAP; por ejemplo, si un error en el programa resulta en una referencia de código o algo similar que se pasa como parámetro a una llamada de método. Cuando eso sucede, esta devolución de llamada se activa, con un argumento. Ese argumento es el elemento de datos que no se pudo entender. Será el único argumento. Si la rutina devuelve un valor, ese valor se inserta en el mensaje como la serialización. Generalmente, un error está justificado, y esta devolución de llamada permite controlar la señalización de ese error.

on_debug(callback)
$client->on_debug(sub { print @_ });

Obsoleto. Utilice las facilidades globales +debug y +trace descritas en SOAP::Trace

Tenga en cuenta que este método no funcionará como se espera: En lugar de afectar el comportamiento de depuración del objeto sobre el que se llama, afectará globalmente el comportamiento de depuración de todos los objetos de esa clase.

ESCRIBIENDO UN CLIENTE SOAP

Este capítulo te guía para escribir un cliente SOAP mediante ejemplos.

El servicio SOAP al que se accederá es una variación simple del conocido programa "hola mundo". Acepta dos parámetros, un nombre y un nombre de pila, y devuelve "Hola $nombre_de_pila $nombre".

Usaremos "Martín Kutter" como nombre para la llamada, por lo que todas las variantes imprimirán el siguiente mensaje en caso de éxito:

¡Hola Martín Kutter!

ESTILOS_DE_MENSAJE_SOAP

Hay tres variantes comunes (y una menos común) de mensajes SOAP.

Estas abordan el estilo del mensaje (parámetros posicionales vs. documentos de mensaje especificados) y la codificación (tal cual vs. con tipos).

Los diferentes estilos de mensaje son:

  • rpc/encoded

    Tipado, parámetros posicionales. Ampliamente utilizado en lenguajes de scripting. El tipo de los argumentos se incluye en el mensaje. Los arrays y similares pueden codificarse utilizando las reglas de codificación SOAP (u otras).

  • rpc/literal

    Tal cual, parámetros posicionales. El tipo de los argumentos se define por alguna interfaz preexistente.

  • document/encoded

    Mensaje especificado con elementos tipados. Raramente utilizado.

  • document/literal

    Mensaje especificado con elementos tal cual. La especificación del mensaje y los tipos de elementos se definen por alguna interfaz preexistente.

A partir de 2008, document/literal se ha convertido en la variante predominante de mensajes SOAP. rpc/literal y rpc/encoded todavía están en uso, principalmente con lenguajes de scripting, mientras que document/encoded apenas se utiliza.

Verás clientes para las variantes de mensajes SOAP rpc/encoded y document/literal en esta sección.

IMPLEMENTACIONES_DE_EJEMPLO

RPC/ENCODED

Rpc/encoded es el más popular entre los lenguajes de scripting como perl, php y python sin el uso de WSDL. Las descripciones habituales de métodos se ven así:

Método: sayHello(string, string)
Parámetros:
   nombre: string
   nombre_de_pila: string

Tal descripción generalmente significa que puedes llamar a un método llamado "sayHello" con dos parámetros posicionales, "nombre" y "nombre_de_pila", ambos cadenas.

El mensaje correspondiente a esta descripción se parece algo a esto:

<sayHello xmlns="urn:HelloWorld">
  <s-gensym01 xsi:type="xsd:string">Kutter</s-gensym01>
  <s-gensym02 xsi:type="xsd:string">Martin</s-gensym02>
</sayHello>

Cualquier nombre de etiqueta XML puede usarse en lugar de las cosas "s-gensym01" - los parámetros son posicionales, los nombres de las etiquetas no tienen significado.

Un cliente que produce tal llamada se implementa de la siguiente manera:

use SOAP::Lite;
my $soap = SOAP::Lite->new( proxy => 'http://localhost:81/soap-wsdl-test/helloworld.pl');
$soap->default_ns('urn:HelloWorld');
my $som = $soap->call('sayHello', 'Kutter', 'Martin');
die $som->faultstring if ($som->fault);
print $som->result, "\n";

Por supuesto, también puedes usar una línea...

A veces, las interfaces rpc/encoded se describen con definiciones WSDL. Un WSDL que acepta parámetros "nombrados" con rpc/encoded se ve así:

<definitions xmlns:soap="http://schemas.xmlsoap.org/wsdl/soap/"
  xmlns:s="http://www.w3.org/2001/XMLSchema"
  xmlns:s0="urn:HelloWorld"
  targetNamespace="urn:HelloWorld"
  xmlns="http://schemas.xmlsoap.org/wsdl/">
  <types>
    <s:schema targetNamespace="urn:HelloWorld">
    </s:schema>
  </types>
  <message name="sayHello">
    <part name="name" type="s:string" />
    <part name="givenName" type="s:string" />
  </message>
  <message name="sayHelloResponse">
    <part name="sayHelloResult" type="s:string" />
  </message>
  <portType name="Service1Soap">
    <operation name="sayHello">
      <input message="s0:sayHello" />
      <output message="s0:sayHelloResponse" />
    </operation>
  </portType>
  <binding name="Service1Soap" type="s0:Service1Soap">
    <soap:binding transport="http://schemas.xmlsoap.org/soap/http"
        style="rpc" />
    <operation name="sayHello">
      <soap:operation soapAction="urn:HelloWorld#sayHello"/>
      <input>
        <soap:body use="encoded"
          encodingStyle="http://schemas.xmlsoap.org/soap/encoding/"/>
      </input>
      <output>
        <soap:body use="encoded"
          encodingStyle="http://schemas.xmlsoap.org/soap/encoding/"/>
      </output>
    </operation>
  </binding>
  <service name="HelloWorld">
    <port name="HelloWorldSoap" binding="s0:Service1Soap">
      <soap:address location="http://localhost:81/soap-wsdl-test/helloworld.pl" />
    </port>
  </service>
</definitions>

El mensaje que corresponde a este esquema se parece a:

<sayHello xmlns="urn:HelloWorld">
  <name xsi:type="xsd:string">Kutter</name>
  <givenName xsi:type="xsd:string">Martin</givenName>
</sayHello>

Un cliente de servicio web que utiliza este esquema se ve así:

use SOAP::Lite;
my $soap = SOAP::Lite->service("file:say_hello_rpcenc.wsdl");
eval { my $result = $soap->sayHello('Kutter', 'Martin'); };
if ($@) {
    die $@;
}
print $som->result();

Por supuesto, también puedes usar la siguiente línea:

perl -MSOAP::Lite -e 'print SOAP::Lite->service("file:say_hello_rpcenc.wsdl")\
  ->sayHello('Kutter', 'Martin'), "\n";'

Un cliente de servicio web (sin descripción de servicio) se ve así.

use SOAP::Lite;
my $soap = SOAP::Lite->new( proxy => 'http://localhost:81/soap-wsdl-test/helloworld.pl');
$soap->default_ns('urn:HelloWorld');
my $som = $soap->call('sayHello',
   SOAP::Data->name('name')->value('Kutter'),
   SOAP::Data->name('givenName')->value('Martin')
);
die $som->faultstring if ($som->fault);
print $som->result, "\n";

<definitions xmlns:soap="http://schemas.xmlsoap.org/wsdl/soap/"
  xmlns:s="http://w
```

El mensaje XML (dentro del sobre SOAP) se ve así:

<ns0:sayHello xmlns:ns0="urn:HelloWorld">
   <parameters>
     <name>Kutter</name>
     <givenName>Martin</givenName>
   </parameters>
</ns0:sayHello>
<sayHelloResponse xmlns:ns0="urn:HelloWorld">
   <parameters>
       <sayHelloResult>Hello Martin Kutter!</sayHelloResult>
   </parameters>
</sayHelloResponse>

Esta es la implementación de SOAP::Lite para el cliente del servicio web:

use SOAP::Lite +trace;
my $soap = SOAP::Lite->new( proxy => 'http://localhost:80/helloworld.pl');
$soap->on_action( sub { "urn:HelloWorld#sayHello" });
$soap->autotype(0)->readable(1);
$soap->default_ns('urn:HelloWorld');
my $som = $soap->call('sayHello', SOAP::Data->name('parameters')->value(
   \SOAP::Data->value([
       SOAP::Data->name('name')->value( 'Kutter' ),
       SOAP::Data->name('givenName')->value('Martin'),
   ]))
);
die $som->fault->{ faultstring } if ($som->fault);
print $som->result, "\n";

Diferencias entre las implementaciones

Puede que hayas notado que hay poca diferencia entre la implementación de rpc/encoded, rpc/literal y el ejemplo de document/literal. De hecho, desde el punto de vista de SOAP::Lite, las únicas diferencias entre rpc/literal y document/literal es que los parámetros siempre tienen nombre.

En nuestro ejemplo, la variante rpc/encoded ya utilizaba parámetros con nombre (mediante el uso de dos mensajes), por lo que no hay ninguna diferencia.

Puede que hayas notado la un tanto extraña forma de pasar una lista de parámetros con nombre en el ejemplo rpc/literal:

my $som = $soap->call('sayHello', SOAP::Data->name('parameters')->value(
   \SOAP::Data->value([
       SOAP::Data->name('name')->value( 'Kutter' ),
       SOAP::Data->name('givenName')->value('Martin'),
   ]))
);

Mientras que SOAP::Data proporciona control total sobre el XML generado, pasar estructuras similares a hash requiere programación adicional.

CARACTERÍSTICAS

ADJUNTOS

"SOAP::Lite" presenta soporte para la especificación SOAP con Adjuntos. Actualmente, SOAP::Lite solo soporta adjuntos basados en MIME. Los adjuntos basados en DIME aún no son totalmente funcionales.

EJEMPLOS

Cliente enviando un adjunto

"SOAP::Lite" los clientes pueden especificar adjuntos para ser enviados junto con una solicitud utilizando el método SOAP::Lite::parts(), que toma como argumento un ARRAY de "MIME::Entity".

use SOAP::Lite;
use MIME::Entity;
my $ent = build MIME::Entity
  Type        => "image/gif",
  Encoding    => "base64",
  Path        => "somefile.gif",
  Filename    => "saveme.gif",
  Disposition => "attachment";
my $som = SOAP::Lite
  ->uri($SOME_NAMESPACE)
  ->parts([ $ent ])
  ->proxy($SOME_HOST)
  ->some_method(SOAP::Data->name("foo" => "bar"));

Cliente recuperando un adjunto

Un cliente que accede a los adjuntos devueltos en una respuesta utilizando el accesor SOAP::SOM::parts().

use SOAP::Lite;
use MIME::Entity;
my $soap = SOAP::Lite
  ->uri($NS)
  ->proxy($HOST);
my $som = $soap->foo();
foreach my $part (${$som->parts}) {
  print $part->stringify;
}

Servidor recibiendo un adjunto

Los servidores, al igual que los clientes, utilizan el módulo SOAP::SOM para acceder a los adjuntos que se les transmiten.

package Attachment;
use SOAP::Lite;
use MIME::Entity;
use strict;
use vars qw(@ISA);
@ISA = qw(SOAP::Server::Parameters);
sub someMethod {
  my $self = shift;
  my $envelope = pop;
  foreach my $part (@{$envelope->parts}) {
    print "AttachmentService: attachment found! (".ref($part).")\n";
  }
  # do something
}

Servidor respondiendo con un adjunto

Los servidores que deseen devolver un adjunto al cliente que llama solo necesitan devolver objetos "MIME::Entity" junto con elementos SOAP::Data, o cualquier otro dato destinado a la respuesta.

package Attachment;
use SOAP::Lite;
use MIME::Entity;
use strict;
use vars qw(@ISA);
@ISA = qw(SOAP::Server::Parameters);
sub someMethod {
  my $self = shift;
  my $envelope = pop;
  my $ent = build MIME::Entity
  'Id'          => "<1234>",
  'Type'        => "text/xml",
  'Path'        => "some.xml",
  'Filename"    => "some.xml",
  'Disposition' => "attachment";
  return SOAP::Data->name("foo" => "blah blah blah"),$ent;
}

CONFIGURACIÓN PREDETERMINADA

Aunque esta característica se parece a la autodescarga, no tienen (casi) nada en común. Esta capacidad le permite especificar configuraciones predeterminadas para que todos los objetos creados después de eso se inicialicen con la configuración predeterminada adecuada.

Si desea proporcionar configuraciones comunes de proxy() o uri() para todos los objetos de "SOAP::Lite" en su aplicación, puede hacer:

use SOAP::Lite
  proxy => 'http://localhost/cgi-bin/soap.cgi',
  uri => 'http://my.own.com/My/Examples';
my $soap1 = new SOAP::Lite; # obtendrá el mismo proxy()/uri() que el anterior
print $soap1->getStateName(1)->result;
my $soap2 = SOAP::Lite->new; # lo mismo que lo anterior
print $soap2->getStateName(2)->result;
# o puede anular cualquier configuración que desee
my $soap3 = SOAP::Lite->proxy('http://localhost/');
print $soap3->getStateName(1)->result;

Cualquier propiedad de "SOAP::Lite" puede propagarse de esta manera. Los cambios en las copias de objetos no afectarán la configuración global y aún puede cambiar la configuración global con la llamada "SOAP::Lite->self" que devuelve una referencia al objeto global. El parámetro proporcionado actualizará este objeto e incluso puede establecerlo en "undef":

SOAP::Lite->self(undef);

La sintaxis "use SOAP::Lite" también le permite especificar manejadores de eventos predeterminados para su código. Si tiene diferentes objetos SOAP y desea compartir el mismo manejador on_action() (o on_fault() para el caso). Puede especificar on_action() durante la inicialización para cada objeto, pero también puede hacer:

use SOAP::Lite
  on_action => sub {sprintf '%s#%s', @_};

y este manejador será el manejador predeterminado para todos sus objetos SOAP. Puede anularlo si especifica un manejador para un objeto en particular. Consulte t/*.t para ver un ejemplo de manejador on_fault().

Tenga en cuenta que dado que "use ..." se ejecuta en tiempo de compilación, todas las declaraciones "use" se ejecutarán antes de la ejecución del script, lo que puede generar resultados inesperados. Considere el código:

use SOAP::Lite proxy => 'http://localhost/';
print SOAP::Lite->getStateName(1)->result;
use SOAP::Lite proxy => 'http://localhost/cgi-bin/soap.cgi';
print SOAP::Lite->getStateName(1)->result;

Ambas llamadas SOAP irán a 'http://localhost/cgi-bin/soap.cgi'. Si desea ejecutar "use" en tiempo de ejecución, póngalo en "eval":

eval "use SOAP::Lite proxy => 'http://localhost/cgi-bin/soap.cgi'; 1" or die;

O alternativamente,

SOAP::Lite->self->proxy('http://localhost/cgi-bin/soap.cgi');

CONFIGURACIÓN DEL TAMAÑO MÁXIMO DEL MENSAJE

Una característica de "SOAP::Lite" es la capacidad de controlar el tamaño máximo de un mensaje que un servidor SOAP::Lite podrá procesar. Para controlar esta característica, simplemente defina $SOAP::Constants::MAX_CONTENT_SIZE en su código de la siguiente manera:

use SOAP::Transport::HTTP;
use MIME::Entity;
$SOAP::Constants::MAX_CONTENT_SIZE = 10000;
SOAP::Transport::HTTP::CGI
  ->dispatch_to('TemperatureService')
  ->handle;

PARÁMETROS DE ENTRADA/SALIDA, SALIDA Y ENLACE AUTOMÁTICO

"SOAP::Lite" le da acceso a todos los parámetros (tanto de entrada/salida como de salida) y también hace un trabajo adicional por usted. Consideremos el siguiente ejemplo:

<mehodResponse>
  <res1>name1</res1>
  <res2>name2</res2>
  <res3>name3</res3>
</mehodResponse>

En ese caso:

$result = $r->result; # le da 'name1'
$paramout1 = $r->paramsout; # le da 'name2', debido al contexto escalar
$paramout1 = ($r->paramsout)[0]; # también le da 'name2'
$paramout2 = ($r->paramsout)[1]; # le da 'name3'

o

@paramsout = $r->paramsout; # le da un ARRAY de parámetros de salida
$paramout1 = $paramsout[0]; # le da 'res2', igual que ($r->paramsout)[0]
$paramout2 = $paramsout[1]; # le da 'res3', igual que ($r->paramsout)[1]

En general, si el servidor devuelve "return (1,2,3)", obtendrá 1 como resultado y 2 y 3 como parámetros de salida.

Si el servidor devuelve "return [1,2,3]", obtendrá una referencia ARRAY de result() y "undef" de paramsout().

Los resultados pueden ser arbitrariamente complejos: pueden ser referencias a arreglos, pueden ser objetos, pueden ser cualquier cosa y aun así ser devueltos por result(). Si solo se devuelve un parámetro, paramsout() devolverá "undef".

Además, si tiene en sus parámetros de salida un parámetro con la misma firma (nombre + tipo) que en los parámetros de entrada, este parámetro se mapeará automáticamente en su entrada. Por ejemplo:

Código del servidor:

sub mymethod {
  shift; # referencia a objeto/clase
  my $param1 = shift;
  my $param2 = SOAP::Data->name('myparam' => shift() * 2);
  return $param1, $param2;
}

Código del cliente:

$a = 10;
$b = SOAP::Data->name('myparam' => 12);
$result = $soap->mymethod($a, $b);

Después de eso, "$result == 10 and $b->value == 24"! ¿Magia? Más o menos.

El enlace automático se lo proporciona. Eso funcionará con objetos también con una diferencia: no necesita preocuparse por el nombre y el tipo del parámetro del objeto. Considere el ejemplo "PingPong" ( examples/My/PingPong.pm y examples/pingpong.pl):

Código del servidor:

package My::PingPong;
sub new {
  my $self = shift;
  my $class = ref($self) || $self;
  bless {_num=>shift} => $class;
}
sub next {
  my $self = shift;
  $self->{_num}++;
}

Código del cliente:

use SOAP::Lite +autodispatch =>
  uri => 'urn:',
  proxy => 'http://localhost/';
my $p = My::PingPong->new(10); # $p->{_num} es 10 ahora, objeto real devuelto
print $p->next, "\n"; # $p->{_num} es 11 ahora!, objeto enlazado automáticamente

DESPLIEGUE DE SERVICIO ESTÁTICO Y DINÁMICO

Analicemos el proceso de despliegue. Al diseñar su servidor SOAP, puede considerar dos tipos de despliegue: estático y dinámico. Tanto para el estático como para el dinámico, debe especificar "MODULE", "MODULE::method", "method" o "PATH/" al crear usando el módulo SOAP::Lite. La diferencia entre el despliegue estático y dinámico es que, en el caso de 'dinámico', cualquier módulo que no esté presente se cargará bajo demanda. Consulte la sección "SEGURIDAD" para obtener una descripción detallada.

Al desplegar estáticamente un servidor SOAP, debe conocer todos los módulos que manejan las solicitudes SOAP de antemano.

El despliegue dinámico permite extender la interfaz de su servidor SOAP simplemente instalando otro módulo en la ruta de descarga (dispatch_to) (ver más abajo).

EJEMPLO DE DESPLIEGUE ESTÁTICO

use SOAP::Transport::HTTP;
use My::Examples; # el módulo se precarga
SOAP::Transport::HTTP::CGI
   # el módulo desplegado debe estar presente aquí o el cliente recibirá
   # 'acceso denegado'
  -> dispatch_to('My::Examples')
  -> handle;

Para el despliegue estático, debe especificar el nombre del MÓDULO directamente.

También debe usar el enlace estático cuando tenga varias clases diferentes en un solo archivo y desee hacerlas disponibles para llamadas SOAP.

EJEMPLO DE DESPLIEGUE DINÁMICO

use SOAP::Transport::HTTP;
# el nombre es desconocido, el módulo se cargará bajo demanda
SOAP::Transport::HTTP::CGI
  # el módulo desplegado debe estar presente aquí o el cliente recibirá 'acceso denegado'
  -> dispatch_to('/Your/Path/To/Deployed/Modules', 'My::Examples')
  -> handle;

Para el despliegue dinámico, puede especificar el nombre directamente (en ese caso se hará un "require" sin ninguna restricción) o indirectamente, con una RUTA. En ese caso, la ÚNICA ruta que estará disponible será la RUTA dada al método dispatch_to()). Para obtener información sobre cómo manejar esta situación, consulte la sección "SEGURIDAD".

RESUMEN

dispatch_to(
  # despacho dinámico que permite el acceso a TODOS los módulos en el directorio especificado
  PATH/TO/MODULES
  # 1. especifica el directorio
  # -- Y --
  # 2. da acceso a TODOS los módulos en este directorio sin límites
  # despacho estático que permite el acceso a TODOS los métodos en un MÓDULO particular
  MODULE
  #  1. da acceso a un módulo particular (todos los métodos disponibles)
  #  PRERREQUISITOS:
  #    el módulo debe cargarse manualmente (por ejemplo, con 'use ...')
  #    -- O --
  #    aún puede especificarlo en PATH/TO/MODULES
  # despacho estático que permite el acceso a UN método particular SOLAMENTE
  MODULE::method
  # igual que MODULE, pero solo da acceso a un método particular,
  # por lo que no tiene mucho sentido usar tanto MODULE como MODULE::method
  # para el mismo MODULE
);

Además de esto, "SOAP::Lite" también admite una sintaxis experimental que le permite enlazar una URL o SOAPAction específica a una CLASE/MÓDULO o objeto.

Por ejemplo:

dispatch_with({
  URI => MODULE,        # 'http://www.soaplite.com/' => 'My::Class',
  SOAPAction => MODULE, # 'http://www.soaplite.com/method' => 'Another::Class',
  URI => object,        # 'http://www.soaplite.com/obj' => My::Class->new,
})

"URI" se verifica antes que "SOAPAction". Puede usar tanto los métodos dispatch_to() como dispatch_with() en el mismo servidor, pero tenga en cuenta que dispatch_with() tiene un orden de precedencia mayor. dispatch_to() solo se verificará después de que se hayan verificado "URI" y "SOAPAction".

Ver también: EJEMPLO DE USO DE APACHE::REGISTRY, "SEGURIDAD"

COMPRESIÓN

SOAP::Lite le da la capacidad de comprimir sus mensajes usando Compress::Zlib.

Para hacerlo, el cliente debe especificar que acepta la compresión en la cabecera HTTP:

$soap->transport->http_request->header('Accept-Encoding' => 'gzip');

Y el servidor debe configurar el manejador de la siguiente manera:

SOAP::Transport::HTTP::Server
  -> handler ( ... )
  ->compress_level(9) # o cualquier otro nivel de compresión
  ->run;

Para esta característica, el servidor web debe estar configurado para permitir el código Perl.

COMPRESSION

"SOAP::Lite" te proporciona la opción de habilitar la compresión transparente a través del cable. La compresión se puede habilitar especificando un valor de umbral (en forma de kilobytes) para la compresión tanto en el lado del cliente como en el del servidor:

Nota: La compresión actualmente solo funciona para servidores y clientes basados en HTTP.

Código del cliente

print SOAP::Lite
  ->uri('http://localhost/My/Parameters')
  ->proxy('http://localhost/', options => {compress_threshold => 10000})
  ->echo(1 x 10000)
  ->result;

Código del servidor

my $server = SOAP::Transport::HTTP::CGI
  ->dispatch_to('My::Parameters')
  ->options({compress_threshold => 10000})
  ->handle;

Para más información, consulta COMPRESSION en HTTP::Transport.

SEGURIDAD

Por razones de seguridad, la ruta existente para los módulos Perl (&#64;INC) se deshabilitará una vez que hayas elegido la implementación dinámica y especificado tu propia "PATH/". Si deseas acceder a otros módulos en tu paquete incluido, tienes varias opciones:

1.
Cambiar a vinculación estática: 
use MODULE;
$server->dispatch_to('MODULE');

Lo que también puede ser útil cuando deseas importar algo específico de los módulos implementados:

use MODULE qw(import_list);
2.
Cambiar "use" por "require". La ruta solo no está disponible durante la fase de inicialización. Está disponible una vez más durante la ejecución. Por lo tanto, si utilizas "require" en algún lugar de tu paquete, funcionará.
3.
Envolver "use" en un bloque "eval": 
eval 'use MODULE qw(import_list)'; die if $@;
4.
Establecer tu ruta de inclusión en tu paquete y luego especificar "use". No olvides colocar &#64;INC en un bloque "BEGIN{}" o no funcionará. Por ejemplo, 
BEGIN { @INC = qw(my_directory); use MODULE }

INTEROPERABILIDAD

Cliente Microsoft .NET con servidor SOAP::Lite

Para usar un cliente .NET con un servidor SOAP::Lite, asegúrate de usar nombres completamente calificados para tus valores de retorno. Por ejemplo:

return SOAP::Data->name('myname')
                 ->type('string')
                 ->uri($MY_NAMESPACE)
                 ->value($output);

Además, consulta el comentario sobre la codificación predeterminada en los servicios web de .NET a continuación.

Cliente SOAP::Lite con un servidor .NET

Si experimentas problemas al usar un cliente SOAP::Lite para llamar a un servicio web de .NET, se recomienda verificar o cumplir con todas las siguientes recomendaciones:

Declara un `soapAction` adecuado en tu llamada
Por ejemplo, usa "on_action( sub { 'http://www.myuri.com/WebService.aspx#someMethod'; } )".
Deshabilita la definición de `charset` en la cabecera `Content-type`
Algunos usuarios han informado que Microsoft .NET prefiere que el valor de la cabecera `Content-type` sea exclusivamente un `mimetype`, pero SOAP::Lite especifica un conjunto de caracteres además del `mimetype`. Esto resulta en un error similar a: 
Server found request content type to be 'text/xml; charset=utf-8',
but expected 'text/xml'

Para desactivar este comportamiento, usa el siguiente código:

use SOAP::Lite;
$SOAP::Constants::DO_NOT_USE_CHARSET = 1;
# El resto de tu código
Usa un nombre completamente calificado para los parámetros del método
Por ejemplo, se prefiere el siguiente código: 
SOAP::Data->name(Query  => 'biztalk')
          ->uri('http://tempuri.org/')

En contraposición a:

SOAP::Data->name('Query'  => 'biztalk')
Coloca el método en el espacio de nombres predeterminado
Por ejemplo, se prefiere el siguiente código: 
my $method = SOAP::Data->name('add')
                       ->attr({xmlns => 'http://tempuri.org/'});
my @rc = $soap->call($method => @parms)->result;

En contraposición a:

my @rc = $soap->call(add => @parms)->result;
# -- O --
my @rc = $soap->add(@parms)->result;
Deshabilita el uso de prefijos de espacio de nombres explícitos
Algunos usuarios han informado que .NET simplemente no analizará mensajes que usen prefijos de espacio de nombres en nada que no sean los propios elementos SOAP. Por ejemplo, el siguiente XML no se analizaría: 
<SOAP-ENV:Envelope ...atributos omitidos>
  <SOAP-ENV:Body>
    <namesp1:mymethod xmlns:namesp1="urn:MyURI" />
  </SOAP-ENV:Body>
</SOAP-ENV:Envelope>

SOAP::Lite permite a los usuarios deshabilitar el uso de espacios de nombres explícitos a través del método use_prefix(). Por ejemplo, el siguiente código:

$som = SOAP::Lite->uri('urn:MyURI')
                 ->proxy($HOST)
                 ->use_prefix(0)
                 ->myMethod();

Generará el siguiente XML, que es más aceptable para .NET:

<SOAP-ENV:Envelope ...atributos omitidos>
  <SOAP-ENV:Body>
    <mymethod xmlns="urn:MyURI" />
  </SOAP-ENV:Body>
</SOAP-ENV:Envelope>
Modifica tu servidor .NET, si es posible

SOAP::Lite utiliza la codificación SOAP (sección 5 de la especificación soap 1.1), y el valor predeterminado para los Servicios Web de .NET es utilizar una codificación literal. Por lo tanto, los elementos de la solicitud no están calificados, pero tu servicio espera que lo estén. Los Servicios Web de .Net tienen una forma de cambiar el formato del mensaje esperado, lo que debería permitir que tu interoperabilidad funcione. En la parte superior de tu clase en el archivo `asmx`, agrega este atributo (para Beta 1):

[SoapService(Style=SoapServiceStyle.RPC)]

Otra fuente dijo que podría ser este atributo (para Beta 2):

[SoapRpcService]

El texto completo del Servicio Web podría verse así:

<%@ WebService Language="C#" Class="Test" %>
using System;
using System.Web.Services;
using System.Xml.Serialization;
[SoapService(Style=SoapServiceStyle.RPC)]
public class Test : WebService {
  [WebMethod]
  public int add(int a, int b) {
    return a + b;
  }
}

SOLUCIÓN DE PROBLEMAS

SOAP::Lite serializa "18373" como un entero, ¡pero quiero que sea una cadena!
SOAP::Lite adivina los tipos de datos a partir del contenido proporcionado, utilizando un conjunto de reglas de sentido común. Estas reglas no son 100% confiables, aunque sirven para la mayoría de los datos.

Puedes forzar el tipo pasando un objeto SOAP::Data con un tipo especificado:

my $proxy = SOAP::Lite->proxy('http://www.example.org/soapservice');
my $som = $proxy->myMethod(
    SOAP::Data->name('foo')->value(12345)->type('string')
);

También puedes cambiar la precedencia de las reglas de adivinación de tipos. Ten en cuenta que esto implica modificar los internos de SOAP::Lite, lo que podría no funcionar como se espera en versiones futuras.

El ejemplo anterior fuerza a que todo se codifique como cadena (esto se debe a que la prueba de cadena normalmente es la última y siempre devuelve verdadero):

my @list = qw(-1 45 foo bar 3838);
my $proxy = SOAP::Lite->uri($uri)->proxy($proxyUrl);
my $lookup = $proxy->serializer->typelookup;
$lookup->{string}->[0] = 0;
$proxy->serializer->typelookup($lookup);
$proxy->myMethod(\@list);

Consulta SOAP::Serializer para más detalles.

"+autodispatch" no funciona en Perl 5.8
Hay un error en la funcionalidad "UNIVERSAL::AUTOLOAD" de Perl 5.8 que impide que la funcionalidad "+autodispatch" funcione correctamente. La solución es usar "dispatch_from" en su lugar. Donde normalmente harías algo como esto: 
use Some::Module;
use SOAP::Lite +autodispatch =>
    uri => 'urn:Foo'
    proxy => 'http://...';

Harías algo como esto:

use SOAP::Lite dispatch_from(Some::Module) =>
    uri => 'urn:Foo'
    proxy => 'http://...';

No se encuentran las bibliotecas dinámicas
Si estás utilizando el servidor web Apache y ves algo como lo siguiente en tu archivo de registro del servidor web: 
No se puede cargar '/usr/local/lib/perl5/site_perl/.../XML/Parser/Expat/Expat.so'
  para el módulo XML::Parser::Expat: enlazador dinámico: /usr/local/bin/perl:
  se necesita libexpat.so.0, pero el objeto no existe en
  /usr/local/lib/perl5/.../DynaLoader.pm línea 200.

Entonces intenta colocar lo siguiente en tu archivo httpd.conf y comprueba si soluciona tu problema.

<IfModule mod_env.c>
    PassEnv LD_LIBRARY_PATH
</IfModule>
El cliente SOAP informa "500 EOF inesperado antes de ver la línea de estado"
Ver "Apache se bloquea con segfaults"
Apache se bloquea con segfaults
El uso de "SOAP::Lite" (o XML::Parser::Expat) en combinación con mod_perl causa fallos de segmentación aleatorios en los procesos httpd. Para solucionarlo, intenta configurar Apache con lo siguiente: 
RULE_EXPAT=no

Si estás utilizando Apache 1.3.20 y posteriores, intenta configurar Apache con la siguiente opción:

./configure --disable-rule=EXPAT

Ver http://archive.covalent.net/modperl/2000/04/0185.xml para más detalles y muchas gracias a Robert Barta <rho@bigpond.net.au> por explicar este extraño comportamiento.

Si esto no soluciona el problema, es posible que desees probar "-Uusemymalloc", o una opción similar para indicar a Perl que utilice el propio "malloc" del sistema.

Gracias a Tim Bunce <Tim.Bunce@pobox.com>.

Los scripts CGI no funcionan bajo Microsoft Internet Information Server (IIS)
Los scripts CGI pueden no funcionar bajo IIS a menos que los scripts utilicen la extensión ".pl", en lugar de ".cgi".
El analizador SAX de Java no puede analizar el mensaje compuesto por SOAP::Lite
En algunos casos, los mensajes SOAP creados por "SOAP::Lite" pueden no ser analizados correctamente por un analizador XML SAX2/Java. Esto se debe a un error conocido en "org.xml.sax.helpers.ParserAdapter". Este error se manifiesta cuando un atributo en un elemento XML aparece antes de la declaración de espacio de nombres XML de la que depende. Sin embargo, según la especificación XML, el orden de estos atributos no es significativo.

http://www.megginson.com/SAX/index.html

Gracias a Steve Alpert (Steve_Alpert@idx.com) por señalarlo.

RENDIMIENTO

Procesamiento de fragmentos codificados en XML
"SOAP::Lite" se basa en XML::Parser, que es básicamente un envoltorio alrededor del analizador expat de James Clark. El comportamiento de Expat para analizar cadenas codificadas en XML puede afectar el procesamiento de mensajes que tienen muchas entidades codificadas, como fragmentos XML, codificados como cadenas. Proporcionando detalles de bajo nivel, el analizador llamará a la devolución de llamada char() por cada porción del flujo procesado, pero individualmente por cada entidad o salto de línea procesado. Esto puede generar muchas llamadas y gastos adicionales del administrador de memoria, incluso para mensajes pequeños. Por el contrario, los mensajes XML codificados como base64Binary no tienen este problema y la diferencia en el tiempo de procesamiento puede ser significativa. Para una cadena codificada en XML que tiene aproximadamente 20 líneas y 30 etiquetas, el número de llamadas podría ser de aproximadamente 100 en lugar de una para la misma cadena codificada como base64Binary.

Dado que es una característica del analizador, NO HAY solución para este comportamiento (avísame si encuentras una), especialmente porque necesitas analizar el mensaje que ya recibiste (y no puedes controlar el contenido de este mensaje), sin embargo, si estás a cargo de ambos extremos del procesamiento, puedes cambiar la codificación a base64 en el lado del remitente. Definitivamente funcionará con SOAP::Lite y puede funcionar con otras herramientas/implementaciones, pero obviamente no puedo garantizarlo.

Si deseas codificar una cadena específica como base64, simplemente haz "SOAP::Data->type(base64 => $string)" en el lado del cliente o del servidor. Si deseas cambiar el comportamiento para una instancia específica de SOAP::Lite, puedes subclassificar "SOAP::Serializer", anular el método as_string() que es responsable de la codificación de cadenas (echa un vistazo a as_base64Binary()) y especificar la clase de serializer nueva para tu objeto SOAP::Lite con:

my $soap = new SOAP::Lite
  serializer => My::Serializer->new,
  ..... otros parámetros

o en el lado del servidor:

my $server = new SOAP::Transport::HTTP::Daemon # o cualquier otro servidor
  serializer => My::Serializer->new,
  ..... otros parámetros

Si deseas cambiar este comportamiento para todas las instancias de SOAP::Lite, simplemente sustituye el método as_string() por as_base64Binary() en algún lugar de tu código después de "use SOAP::Lite" y antes del procesamiento/envío real:

*SOAP::Serializer::as_string = \&SOAP::XMLSchema2001::Serializer::as_base64Binary;

Ten en cuenta que los dos últimos métodos afectarán a todas las cadenas y las convertirán a base64 codificadas. No hace diferencia para SOAP::Lite, pero puede hacer una diferencia para otras herramientas.

ERRORES Y LIMITACIONES

  • No hay soporte para arrays multidimensionales, transmitidos parcialmente y dispersos (sin embargo, los arrays de arrays son compatibles, así como cualquier otra estructura de datos, y puedes agregar tu propia implementación con SOAP::Data).
  • Soporte limitado para el esquema WSDL.
  • XML::Parser::Lite depende del soporte Unicode en Perl y no realiza decodificación de entidades.
  • Soporte limitado para los atributos mustUnderstand y Actor.
