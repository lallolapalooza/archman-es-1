NOMBRE

Smokeping::probes::IRTT - un probe de SmokePing para IRTT https://github.com/peteheist/irtt

SINOPSIS

*** Probes ***
+IRTT
binary = /usr/local/bin/irtt # obligatorio
forks = 5
offset = 50%
step = 300
timeout = 15
tmpdir = /tmp/smokeping-irtt
# Las siguientes variables pueden ser sobrescritas en cada sección de destino
/^influx_.+/ = influx_location = En el sótano
dscp = 46
extraargs = --ttl=32
fill = rand
hmac = opensesame
interval = 1.5
ipversion = 6
length = 172
localaddr = 192.168.1.10:63814
metric = rtt
pings = 5
readfrom = irtt1
readfrompollinterval = 2
serverfill = rand
sleep = 0.5
writeto = irtt1
# [...]
*** Destinos ***
probe = IRTT # si este debería ser el probe por defecto
# [...]
+ mytarget
# probe = IRTT # si el probe por defecto es algo diferente
host = my.host
/^influx_.+/ = influx_location = En el sótano
dscp = 46
extraargs = --ttl=32
fill = rand
hmac = opensesame
interval = 1.5
ipversion = 6
length = 172
localaddr = 192.168.1.10:63814
metric = rtt
pings = 5
readfrom = irtt1
readfrompollinterval = 2
serverfill = rand
sleep = 0.5
writeto = irtt1

DESCRIPCIÓN

Este probe de SmokePing usa IRTT https://github.com/peteheist/irtt para registrar el tiempo de retroceso redondo (IRTt) https://en.wikipedia.org/wiki/Round-trip_delay_time, el tiempo de delay unidireccional https://en.wikipedia.org/wiki/End-to-end_delay o el IPDV https://en.wikipedia.org/wiki/Packet_delay_variation (jitter), basado en el valor de la variable metric.

Además, el probe ofrece una característica de compartir resultados, que permite usar los resultados de un único IRTT para registrar múltiples métricas para un mismo host al mismo tiempo. Un destino está definido con la variable writeto, que selecciona el nombre de un archivo temporal a guardar los resultados de IRTT. Otros destinos están definidos con la variable readfrom que se asigna al mismo valor, que, en lugar de ejecutar IRTT, espera a que el resultado principal del destino se disponibilice, luego parsea el resultado para registrar la métrica elegida del mismo dato. Vea las variables writeto y readfrom para más información.

ADVERTENCIA

La característica de compartir resultados (writeto y readfrom) requiere que el número de forks del probe de IRTT sea al menos el número total de destinos de IRTT definidos (independientemente de si tienen writeto y readfrom definidos). De lo contrario, puede haber un bloqueo mientras los destinos readfrom esperan a que su correspondiente destino writeto termine, lo cual puede no iniciar nunca.

VARIABLES

Variables específicas del probe:

binary
La ubicación de tu ejecutable irtt.

Ejemplo de valor: /usr/local/bin/irtt

Valor por defecto: /usr/bin/irtt

Este ajuste es obligatorio.

forks
Se ejecutan tantos procesos concurrentes como máximo

Ejemplo de valor: 5

Valor por defecto: 5

offset
Si ejecutas muchos probes concurrentemente, podrías evitar que todos acaben en tu red a la vez. Usando la variable de parámetro del probe específico, puedes cambiar el punto en el tiempo cuando se ejecute cada uno. El offset se especifica en % de intervalo total, o alternativamente como 'random', y se utiliza el valor del apartado 'General' si no se especifica aquí. Nota: Esto NO afecta el rrds, es simplemente un asunto de cuando se iniciará la adquisición de datos. (Esta variable solo es aplicable si el variable 'concurrentprobes' está definida en el apartado 'General'.)

Ejemplo de valor: 50%

step
El tiempo de intervalo base que debería usar este probe, si distinto del especificado en el apartado 'Database'. Nota: El paso en los archivos rrds se fija al original y si cambias el parámetro step después, tendrás que eliminar los archivos antiguos o convertirlos. (Esta variable solo es aplicable si el variable 'concurrentprobes' está definida en el apartado 'General'.)

Ejemplo de valor: 300

timeout
El tiempo máximo que un 'ping' puede tomar

Ejemplo de valor: 15

Valor por defecto: 5

tmpdir
Un directorio temporal en el cual se colocarán los archivos para writeto/readfrom.

Valor por defecto: /tmp/smokeping-irtt

Variables específicas de destino:

/^influx_.+/
Esta es una etiqueta que se envía a influxdb y no tiene influencia en la medición del probe. El nombre de la etiqueta se envía sin el prefijo "influx_", que se reemplazará con "tag_". Las etiquetas pueden usarse para filtrado.

Ejemplo de valor: influx_location = En el sótano

dscp
El valor de DSCP de paquetes https://en.wikipedia.org/wiki/Differentiated_services a usar ("irtt cliente --dscp"). Este es el mismo que el campo uno byte de IP ToS clásico, pero en la red moderna, se usa normalmente solo los 6 bits más bajos, y se llama el valor DSCP. Los dos bits más altos están reservados para ECN https://en.wikipedia.org/wiki/Explicit_Congestion_Notification. Se puede usar hexadecimal si se prefixe con "0x".

Ejemplo de valor: 46

extraargs
Argumentos adicionales a "irtt cliente" (ver irtt-client(1)). Deja cuidado con los argumentos adicionales, ya que algunos pueden corromper los resultados.

Ejemplo de valor: --ttl=32

fill
El valor de fill a usar en el payload del cliente al servidor ("irtt cliente --fill"). El valor de length debe ser suficientemente grande para que haya un payload para llenar. Usa rand para llenado aleatorio, o vea irtt-client(1) para más opciones.

Ejemplo de valor: rand

hmac
El clave HMAC https://en.wikipedia.org/wiki/Hash-based_message_authentication_code a usar cuando envíes paquetes al servidor ("irtt cliente --hmac").

Ejemplo de valor: opensesame

interval
El intervalo entre peticiones sucesivas, en segundos ("irtt cliente -i", pero el unidad siempre es segundos (s)).

ADVERTENCIA

Si el interval se aumenta a más de 5 segundos, el timeout (que por defecto es pings * 5 segundos + 1) debe modificarse para que SmokePing no termine el probe prematuramente. Además, interval no debe aumentarse de tal manera que pings * interval sea mayor que step. Por ejemplo, si step=300 y pings=20, el interval no debe ser mayor de 15 segundos, pero debe ser preferentemente menor para considerar los tiempos de handshake y espera de paquetes.

Ejemplo de valor: 1.5

Valor por defecto: 1

ipversion
El valor de versión IP a usar para los paquetes (4 o 6, correspondientes a "irtt cliente -4" o "irtt cliente -6"). Por defecto, la versión IP se selecciona basada en el variable host proporcionada.

Ejemplo de valor: 6

length
El tamaño (tamaño) del paquete ("irtt cliente -l"). El tamaño incluye los encabezados de IRTT, pero no los encabezados de IP o UDP. El tamaño del paquete real se aumenta para incluir los encabezados de IRTT, si es necesario.

Ejemplo de valor: 172

Variables

header
El tamaño de la cabecera tal como se usa en SmokePing desde IRTT 0.9.0 es de 48 bytes cuando `writeto` está configurado (ya que se solicitan tanto los valores del reloj monotónico como del reloj de pared) y 40 bytes en caso contrario.

Valor de ejemplo: 172

localaddr
La dirección local a la que enlazar al enviar paquetes (`irtt client --local`). Consulte los formatos de host de irtt-client(1) para ver la sintaxis válida.

Valor de ejemplo: 192.168.1.10:63814

metric
La métrica a registrar, una de las siguientes:
  • rtt: tiempo de ida y vuelta https://en.wikipedia.org/wiki/Round-trip_delay_time
  • send: retardo de envío unidireccional https://en.wikipedia.org/wiki/End-to-end_delay (requiere sincronización externa de tiempo)
  • receive: retardo de recepción unidireccional https://en.wikipedia.org/wiki/End-to-end_delay (requiere sincronización externa de tiempo)
  • ipdv: IPDV https://en.wikipedia.org/wiki/Packet_delay_variation (variación instantánea del retardo de paquetes, o jitter)
  • send_ipdv: IPDV para paquetes enviados
  • receive_ipdv: IPDV para paquetes recibidos

Tenga en cuenta que las métricas send y receive requieren una sincronización precisa del reloj del sistema externo, de lo contrario, los valores de una serán anormalmente altos y los de la otra anormalmente bajos o incluso negativos, en cuyo caso SmokePing dará el valor 0. Se recomienda instalar ntp tanto en el cliente SmokePing como en el servidor IRTT. Un NTP configurado correctamente puede sincronizar el tiempo con unos pocos milisegundos, lo que suele ser suficiente para proporcionar resultados útiles. PTP sobre una LAN puede lograr precisión a nivel de microsegundos. Para obtener los mejores resultados entre hosts geográficamente remotos, se pueden utilizar receptores GPS. Dado que send_ipdv y receive_ipdv miden la variación en los tiempos entre paquetes sucesivos, y dado que rtt y ipdv utilizan valores del reloj monotónico solo en el lado del cliente, no se requiere sincronización externa de tiempo para estas métricas.

Valor predeterminado: rtt

pings
Cuántos pings se deben enviar a cada objetivo, si es diferente del valor global especificado en la sección Database. Tenga en cuenta que el número de pings en los archivos RRD se fija cuando se generan originalmente, y si cambia este parámetro después, deberá eliminar los archivos RRD antiguos o convertirlos de alguna manera.

Valor de ejemplo: 5

readfrom
El nombre de un archivo del que leer los resultados, en lugar de ejecutar IRTT. Úselo en combinación con writeto para utilizar los resultados de una ejecución de IRTT para registrar múltiples métricas. El valor será el nombre de un archivo en tmpdir y debe ser el mismo que la configuración de otro objetivo para writeto. Múltiples objetivos pueden usar el mismo valor para readfrom, pero writeto y readfrom no se pueden configurar para el mismo objetivo. Cuando readfrom está configurado, se ignoran todas las variables que afectan a irtt client porque IRTT no se está invocando, incluyendo: dscp, extraargs, fill, hmac, interval, ipversion, length, localaddr y serverfill. Estos valores solo son relevantes en el objetivo writeto correspondiente.

Tenga en cuenta que la variable host aún debe definirse para los objetivos que definen readfrom, de lo contrario, el objetivo no se utilizará.

Al usar esta función, asegúrese de tener al menos tantas instancias de forks para la sonda IRTT como objetivos IRTT totales definidos. Consulte la sección "DESCRIPCIÓN" para obtener más información.

Valor de ejemplo: irtt1

readfrompollinterval
El intervalo entero en segundos en el que se consultarán los resultados cuando readfrom esté configurado. Números más bajos permitirán a readfrom ver los resultados un poco antes, a costa de un mayor uso de CPU. La sondeo no comienza hasta el momento más temprano en el que el cliente IRTT podría haber terminado normalmente.

Valor de ejemplo: 2

Valor predeterminado: 5

serverfill
El relleno que se utilizará en la carga útil para el paquete del servidor al cliente (`irtt client --sfill`). La variable length debe ser lo suficientemente grande para acomodar una carga útil. Utilice rand para relleno aleatorio, o consulte irtt-client(1) para más opciones.

Valor de ejemplo: rand

sleep
La cantidad de tiempo que se debe esperar antes de iniciar solicitudes o procesar resultados (un flotante en segundos). Esto puede usarse para evitar picos de CPU causados por la invocación de múltiples instancias de IRTT al mismo tiempo.

Valor de ejemplo: 0.5

writeto
El nombre de un archivo al que se escribirán los resultados después de ejecutar IRTT. Úselo en combinación con readfrom para utilizar los resultados de esta ejecución de IRTT para registrar múltiples métricas. El valor será el nombre de un archivo en tmpdir, y cualquier objetivo con readfrom configurado con el mismo valor utilizará los resultados de este objetivo. Solo puede haber un objetivo con writeto configurado para un archivo determinado, y writeto y readfrom no se pueden configurar para el mismo objetivo.

Al usar esta función, asegúrese de tener al menos tantas instancias de forks para la sonda IRTT como objetivos IRTT totales definidos. Consulte la sección "DESCRIPCIÓN" para obtener más información.

Valor de ejemplo: irtt1
