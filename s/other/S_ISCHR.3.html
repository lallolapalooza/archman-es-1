NOMBRE

inode - información del nodo-i del archivo

DESCRIPCIÓN

Cada archivo tiene un nodo-i que contiene metadatos sobre el archivo. Una aplicación puede obtener estos metadatos usando stat(2) (o llamadas relacionadas), que devuelve una estructura stat, o statx(2), que devuelve una estructura statx.

La siguiente es una lista de la información que típicamente se encuentra en el nodo-i del archivo, o asociada a él, con los nombres de los campos de la estructura correspondientes devueltos por stat(2) y statx(2):

Dispositivo donde reside el nodo-i
stat.st_dev; statx.stx_dev_minor y statx.stx_dev_major
Cada nodo-i (así como el archivo asociado) reside en un sistema de archivos alojado en un dispositivo. Ese dispositivo se identifica mediante la combinación de su ID mayor (que identifica la clase general del dispositivo) y su ID menor (que identifica una instancia específica dentro de la clase general).
Número de nodo-i
stat.st_ino; statx.stx_ino
Cada archivo en un sistema de archivos tiene un número de nodo-i único. Los números de nodo-i solo se garantizan que sean únicos dentro de un sistema de archivos (es decir, los mismos números de nodo-i pueden ser usados por diferentes sistemas de archivos, razón por la cual los enlaces físicos no pueden cruzar los límites del sistema de archivos). Este campo contiene el número de nodo-i del archivo.
Tipo y modo de archivo
stat.st_mode; statx.stx_mode
Ver la discusión sobre el tipo y modo de archivo, más abajo.
Contador de enlaces
stat.st_nlink; statx.stx_nlink
Este campo contiene el número de enlaces físicos al archivo. Se crean enlaces adicionales a un archivo existente usando link(2).
ID de usuario
stat.st_uid; statx.stx_uid
Este campo registra el ID de usuario del propietario del archivo. Para los archivos recién creados, el ID de usuario del archivo es el ID de usuario efectivo del proceso creador. El ID de usuario de un archivo puede cambiarse usando chown(2).
ID de grupo
stat.st_gid; statx.stx_gid
El nodo-i registra el ID del grupo propietario del archivo. Para los archivos recién creados, el ID de grupo del archivo es el ID de grupo del directorio padre o el ID de grupo efectivo del proceso creador, dependiendo de si el bit set-group-ID está establecido en el directorio padre (ver más abajo). El ID de grupo de un archivo puede cambiarse usando chown(2).
Dispositivo representado por este nodo-i
stat.st_rdev; statx.stx_rdev_minor y statx.stx_rdev_major
Si este archivo (nodo-i) representa un dispositivo, entonces el nodo-i registra el ID mayor y menor de ese dispositivo.
Tamaño del archivo
stat.st_size; statx.stx_size
Este campo indica el tamaño del archivo (si es un archivo regular o un enlace simbólico) en bytes. El tamaño de un enlace simbólico es la longitud de la ruta que contiene, sin un byte nulo de terminación.
Tamaño de bloque preferido para E/S
stat.st_blksize; statx.stx_blksize
Este campo indica el tamaño de bloque "preferido" para una E/S de sistema de archivos eficiente. (Escribir en un archivo en trozos más pequeños puede causar una lectura-modificación-reescritura ineficiente).
Número de bloques asignados al archivo
stat.st_blocks; statx.stx_blocks
Este campo indica el número de bloques asignados al archivo, en unidades de 512 bytes, (Esto puede ser menor que st_size/512 cuando el archivo tiene agujeros.)
El estándar POSIX.1 señala que la unidad para el miembro st_blocks de la estructura stat no está definida por el estándar. En muchas implementaciones es de 512 bytes; en algunos sistemas, se usa una unidad diferente, como 1024. Además, la unidad puede diferir en cada sistema de archivos.
Última marca de tiempo de acceso (atime)
stat.st_atime; statx.stx_atime
Esta es la marca de tiempo del último acceso al archivo. Se modifica por accesos a archivos, por ejemplo, por execve(2), mknod(2), pipe(2), utime(2), y read(2) (de más de cero bytes). Otras interfaces, como mmap(2), pueden o no actualizar la marca de tiempo atime.
Algunos tipos de sistemas de archivos permiten montarlos de manera que los accesos a archivos y/o directorios no causen una actualización de la marca de tiempo atime. (Ver noatime, nodiratime, y relatime en mount(8), e información relacionada en mount(2).) Además, la marca de tiempo atime no se actualiza si un archivo se abre con la bandera O_NOATIME; ver open(2).
Marca de tiempo de creación de archivo (btime)
(no devuelto en la estructura stat); statx.stx_btime
La marca de tiempo de creación del archivo. Se establece al crear el archivo y no se modifica posteriormente.
La marca de tiempo btime no estaba históricamente presente en los sistemas UNIX y actualmente no es compatible con la mayoría de los sistemas de archivos de Linux.
Última marca de tiempo de modificación (mtime)
stat.st_mtime; statx.stx_mtime
Esta es la marca de tiempo de la última modificación del archivo. Se modifica por modificaciones del archivo, por ejemplo, por mknod(2), truncate(2), utime(2), y write(2) (de más de cero bytes). Además, la marca de tiempo mtime de un directorio se modifica por la creación o eliminación de archivos en ese directorio. La marca de tiempo mtime no se modifica por cambios en el propietario, grupo, contador de enlaces físicos o modo.
Última marca de tiempo de cambio de estado (ctime)
stat.st_ctime; statx.stx_ctime
Esta es la marca de tiempo del último cambio de estado del archivo. Se modifica al escribir o al establecer información del nodo-i (es decir, propietario, grupo, contador de enlaces, modo, etc.).

Los campos de marca de tiempo informan el tiempo medido con un punto cero en la Epoch, 1970-01-01 00:00:00 +0000, UTC (ver time(7)).

Las marcas de tiempo de nanosegundos son compatibles con XFS, JFS, Btrfs y ext4 (desde Linux 2.6.23). Las marcas de tiempo de nanosegundos no son compatibles con ext2, ext3 y Reiserfs. Para devolver marcas de tiempo con precisión de nanosegundos, los campos de marca de tiempo en las estructuras stat y statx se definen como estructuras que incluyen un componente de nanosegundos. Ver stat(2) y statx(2) para detalles. En sistemas de archivos que no admiten marcas de tiempo de subsegundo, los campos de nanosegundos en las estructuras stat y statx se devuelven con el valor 0.

El tipo y modo de archivo

El campo stat.st_mode (para statx(2), el campo statx.stx_mode) contiene el tipo y modo del archivo.

POSIX se refiere a los bits de stat.st_mode que corresponden a la máscara S_IFMT (ver más abajo) como el tipo de archivo, los 12 bits que corresponden a la máscara 07777 como los bits de modo de archivo y los 9 bits menos significativos (0777) como los bits de permiso de archivo.

El si

NOMBRE

S_ISCHR, S_ISBLK, S_ISDIR, S_ISFIFO, S_ISREG, S_ISLNK, S_ISSOCK, S_TYPEISMACRO - determinar el tipo de archivo

DESCRIPCIÓN

Los valores de máscara del tipo de archivo se definen para el tipo de archivo:


S_IFMT 0170000 máscara de bits para el campo de bits del tipo de archivo
S_IFSOCK 0140000 socket
S_IFLNK 0120000 enlace simbólico
S_IFREG 0100000 archivo regular
S_IFBLK 0060000 dispositivo de bloque
S_IFDIR 0040000 directorio
S_IFCHR 0020000 dispositivo de caracteres
S_IFIFO 0010000 FIFO

Por lo tanto, para verificar si es un archivo regular (por ejemplo), se podría escribir:


stat(pathname, &sb);
if ((sb.st_mode & S_IFMT) == S_IFREG) {
    /* Manejar archivo regular */
}

Debido a que las verificaciones de la forma anterior son comunes, POSIX define macros adicionales para permitir que la verificación del tipo de archivo en st_mode se escriba de forma más concisa:

S_ISREG(m)
¿es un archivo regular?
S_ISDIR(m)
¿directorio?
S_ISCHR(m)
¿dispositivo de caracteres?
S_ISBLK(m)
¿dispositivo de bloque?
S_ISFIFO(m)
¿FIFO (tubería con nombre)?
S_ISLNK(m)
¿enlace simbólico? (No en POSIX.1-1996.)
S_ISSOCK(m)
¿socket? (No en POSIX.1-1996.)

El fragmento de código anterior podría, por lo tanto, reescribirse como:


stat(pathname, &sb);
if (S_ISREG(sb.st_mode)) {
    /* Manejar archivo regular */
}

Las definiciones de la mayoría de las macros de prueba de tipo de archivo anteriores se proporcionan si se define cualquiera de las siguientes macros de prueba de características: _BSD_SOURCE (en glibc 2.19 y anteriores), _SVID_SOURCE (en glibc 2.19 y anteriores), o _DEFAULT_SOURCE (en glibc 2.20 y posteriores). Además, se proporcionan definiciones de todas las macros anteriores, excepto S_IFSOCK y S_ISSOCK(), si se define _XOPEN_SOURCE.

La definición de S_IFSOCK también se puede exponer definiendo _XOPEN_SOURCE con un valor de 500 o superior o (desde glibc 2.24) definiendo tanto _XOPEN_SOURCE como _XOPEN_SOURCE_EXTENDED.

La definición de S_ISSOCK() se expone si se define cualquiera de las siguientes macros de prueba de características: _BSD_SOURCE (en glibc 2.19 y anteriores), _DEFAULT_SOURCE (en glibc 2.20 y posteriores), _XOPEN_SOURCE con un valor de 500 o superior, _POSIX_C_SOURCE con un valor de 200112L o superior, o (desde glibc 2.24) definiendo tanto _XOPEN_SOURCE como _XOPEN_SOURCE_EXTENDED.

Los siguientes valores de máscara se definen para el componente del modo de archivo del campo st_mode:

S_ISUID 04000 bit set-user-ID (ver execve(2))
S_ISGID 02000 bit set-group-ID (ver abajo)
S_ISVTX 01000 bit sticky (ver abajo)
S_IRWXU 00700 el propietario tiene permiso de lectura, escritura y ejecución
S_IRUSR 00400 el propietario tiene permiso de lectura
S_IWUSR 00200 el propietario tiene permiso de escritura
S_IXUSR 00100 el propietario tiene permiso de ejecución
S_IRWXG 00070 el grupo tiene permiso de lectura, escritura y ejecución
S_IRGRP 00040 el grupo tiene permiso de lectura
S_IWGRP 00020 el grupo tiene permiso de escritura
S_IXGRP 00010 el grupo tiene permiso de ejecución
S_IRWXO 00007 otros (no en el grupo) tienen permiso de lectura, escritura y ejecución
S_IROTH 00004 otros tienen permiso de lectura
S_IWOTH 00002 otros tienen permiso de escritura
S_IXOTH 00001 otros tienen permiso de ejecución

El bit set-group-ID (S_ISGID) tiene varios usos especiales. Para un directorio, indica que se deben usar semánticas BSD para ese directorio: los archivos creados allí heredan su ID de grupo del directorio, no del ID de grupo efectivo del proceso que los crea, y los directorios creados allí también tendrán el bit S_ISGID establecido. Para un archivo ejecutable, el bit set-group-ID hace que el ID de grupo efectivo de un proceso que ejecuta el archivo cambie como se describe en execve(2). Para un archivo que no tiene establecido el bit de ejecución de grupo (S_IXGRP), el bit set-group-ID indica bloqueo de archivo/registro obligatorio.

El bit sticky (S_ISVTX) en un directorio significa que un archivo en ese directorio solo puede ser renombrado o eliminado por el propietario del archivo, por el propietario del directorio y por un proceso privilegiado.

ESTÁNDARES

POSIX.1-2008.

HISTORIA

POSIX.1-2001.

POSIX.1-1990 no describía las constantes S_IFMT, S_IFSOCK, S_IFLNK, S_IFREG, S_IFBLK, S_IFDIR, S_IFCHR, S_IFIFO y S_ISVTX, sino que especificaba el uso de las macros S_ISDIR() y similares.

Las macros S_ISLNK() y S_ISSOCK() no estaban en POSIX.1-1996; la primera es de SVID 4, la segunda de SUSv2.

UNIX V7 (y sistemas posteriores) tenían S_IREAD, S_IWRITE, S_IEXEC, y donde POSIX prescribe los sinónimos S_IRUSR, S_IWUSR y S_IXUSR.

NOTAS

Para los pseudoficheros que son generados automáticamente por el kernel, el tamaño del archivo (stat.st_size; statx.stx_size) reportado por el kernel no es exacto. Por ejemplo, se devuelve el valor 0 para muchos archivos en el directorio /proc, mientras que varios archivos en /sys informan un tamaño de 4096 bytes, aunque el contenido del archivo sea menor. Para tales archivos, simplemente se debe intentar leer tantos bytes como sea posible (y añadir '\0' al buffer devuelto si se va a interpretar como una cadena).
