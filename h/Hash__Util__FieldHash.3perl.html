DESCRIPCIÓ

N

Una palabra sobre terminología: usaré el término campo para un trozo escalar de datos que una clase asocia con un objeto. Otros términos que se han usado para este concepto son "variable de objeto", "propiedad (de objeto)", "atributo (de objeto)" y más. Especialmente "atributo" tiene cierta circulación entre los programadores de Perl, pero eso choca con la directiva "attributes". El término "campo" también tiene cierta circulación en este sentido y no parece entrar en conflicto con otra terminología de

Perl.

En Perl, un objeto es una referencia bendita. La forma estándar de asociar datos con un objeto es almacenar los datos dentro del cuerpo del objeto, es decir, el trozo de datos al que apunta la

referencia.

En consecuencia, si dos o más clases quieren acceder a un objeto ellas deben estar de acuerdo en el tipo de referencia y también en la organización de datos dentro del cuerpo del objeto. El no estar de acuerdo en el tipo resulta en muerte inmediata cuando el método equivocado intenta acceder a un objeto. El no estar de acuerdo en la organización de datos puede llevar a que una clase pise los datos de

otra.

Este modelo de objeto lleva a un acoplamiento estrecho entre subclases. Si una clase quiere heredar de otra (y ambas clases acceden a datos de objetos), las clases deben estar de acuerdo sobre los detalles de implementación. La herencia solo puede usarse entre clases que se mantienen juntas, en una fuente única o

no.

En particular, no es posible escribir clases de propósito general con esta técnica, clases que puedan anunciarse a sí mismas como "Póngame en su lista @ISA y use mis métodos". Si la otra clase tiene ideas diferentes sobre cómo se usa el cuerpo del objeto, hay

problemas.

Para referencia "Name_hash" en "Ejemplo 1" muestra la implementación estándar de una clase simple "Name" de la bien conocida manera basada en hash. También demuestra el fallo predecible de construir una subclase común "NamedFile" de "Name" y la clase "IO::File" (cuyos objetos deben ser globrefs)

.

Por lo tanto, son de interés las técnicas que almacenan datos de objetos no en el cuerpo del objeto sino en algún otro

lugar.

La Técnica

Inside-out

Con las clases inside-out, cada clase declara un hash (típicamente léxico) para cada campo que quiere usar. La dirección de referencia de un objeto se usa como clave del hash. Por definición, la dirección de referencia es única para cada objeto, por lo que esto garantiza un lugar para cada campo que es privado de la clase y único para cada objeto. Ver "Name_id" en "Ejemplo 1" para un ejemplo

simple.

En comparación con la implementación estándar donde el objeto es un hash y los campos corresponden a claves hash, aquí los campos corresponden a hashes, y el objeto determina la clave hash. Así los hashes parecen estar volteados hacia adentro (inside out)

.

El cuerpo de un objeto nunca es examinado por una clase inside-out, solo se usa su dirección de referencia. Esto permite que el cuerpo de un objeto real sea cualquier cosa mientras que los métodos de objeto de la clase siguen funcionando según lo diseñ

ado. Esta es una característica
clave de las clases "inside-out".

Problemas de las clases

"inside-out"

Las clases "inside-out" nos dan libertad de herencia, pero como de costumbre hay un

precio.

Lo más obvio es la necesidad de recuperar la dirección de referencia de un objeto para cada acceso a datos. Es una molestia menor, pero ensucia el

código.

Más importante (y menos obvio) es la necesidad de recolección de basura. Cuando un objeto normal muere, todo lo almacenado en el cuerpo del objeto es recolectado por perl. Con los objetos "inside-out", Perl no sabe nada de los datos almacenados en los hashes de campo por una clase, pero estos deben ser borrados cuando el objeto sale de ámbito. Por lo tanto, la clase debe proporcionar un método "DESTROY" para encargarse de

eso.

En presencia de múltiples clases, puede no ser trivial asegurarse de que cada destructor relevante sea llamado para cada objeto. Perl llama al primero que encuentra en el árbol de herencia (si hay alguno) y eso es

todo.

Un problema relacionado es la seguridad de hilos. Cuando se crea un nuevo hilo, el intérprete Perl es clonado, lo que implica que todas las direcciones de referencia en uso serán reemplazadas por nuevas. Así, si una clase intenta acceder a un campo de un objeto clonado, sus datos (clonados) seguirán almacenados bajo la dirección de referencia ahora inválida del original en el hilo padre. Un método "CLONE" general debe ser proporci

onado para restab
lecer la asociación.

Solucione

s

"Hash::Util::FieldHash" aborda estos problemas en varios

niveles.

La función id() es proporcionada además de la existente Scalar::Util::refaddr(). Además de su nombre corto, puede ser un poco más rápida bajo algunas circunstancias (y un poco más lenta bajo otras). Haz un benchmark si importa. El funcionamiento de id() también permite el uso del nombre de la clase como un objeto genérico, como se describe más

adelante.

La función id() está incorporada en hashes id en el sentido de que se llama automáticamente en cada clave que se usa con el hash. No es necesario ninguna llamada

explícita.

Los problemas de la recolección de basura y la seguridad de hilos son ambos abordados por la función register(). Registra un objeto junto con cualquier número de hashes. El registro significa que cuando el objeto muere, una entrada en cualquiera de los hashes bajo la dirección de referencia de este objeto será borrada. Esto garantiza la recolección de basura en estos hashes. También significa que en la clonación de hilos, las entradas del objeto en los hashes registrados serán reemplazadas con entradas actualizadas cuya clave es la dirección de referencia del objeto clonado. Así, la asociación objeto-datos se vuelve segura para

hilos.

El registro del objeto es mejor hacerlo cuando el objeto es inicializado para su uso con una clase. De esa manera, la recolección de basura y la seguridad de hilos se establecen para cada objeto y cada campo que es

inicializado.

Finalmente, los hashes de campo incorporan todas estas funciones en un paquete. Además de llamar automáticamente a la función id() en cada objeto usado como clave, el objeto es registrado con el hash de campo en su primer uso. Las clas

es basadas en hashes de campo son completamente recolectabl
es de basura y seguras para hilos sin medidas adicionales.

Más

Problemas

Otro problema que ocurre con las clases "inside-out" es la serialización. Dado que los datos del objeto no están en su lugar habitual, rutinas estándar como Storable::freeze(), Storable::thaw() y Data::Dumper::Dumper() no pueden lidiar con ello por sí solas. Tanto "Data::Dumper" como "Storable" proporcionan los "hooks" necesarios para hacer que las cosas funcionen, pero las funciones o métodos usados por los "hooks" deben ser proporcionados por cada clase

"inside-out".

Una solución general al problema de la serialización requeriría otro nivel de registro, uno que asocie clases y campos. Hasta ahora, las funciones de "Hash::Util::FieldHash" no son conscientes de ninguna clase, lo cual considero una característica. Por lo tanto "Hash::Util::FieldHash" no aborda

los problemas de
serialización.

El Objeto

Genérico

Las clases basadas en la función id() (y por lo tanto clases basadas en idhash() y fieldhash()) muestran un comportamiento peculiar en el que el nombre de la clase puede ser usado como un objeto. Específicamente, los métodos que establecen o leen datos asociados con un objeto continúan funcionando como métodos de clase, justo como si el nombre de la clase fuera un objeto, distinto de todos los demás objetos, con sus propios datos. A este objeto se le puede llamar el objeto genérico de la

clase.

Esto funciona porque los hashes de campo responden a claves que no son referencias como lo haría un hash normal y usan la cadena ofrecida como clave del hash. Así, si un método es llamado como método de clase, el hash de campo es presentado con el nombre de la clase en lugar de un objeto y alegremente lo usa como clave. Dado que las claves de objetos reales son números decimales, no hay conflicto y el espacio en el hash de campo puede ser usado como cualquier otro. La función id() se comporta en consecuencia con respecto a argumentos que no son

referencias.

Dos usos posibles (además de ignorar la propiedad) se me ocurren. Una clase "singleton" podría ser implementada usando el objeto genérico. Si es necesario, un método init() podría morir o ignorar llamadas con objetos reales (referencias), de modo que solo el objeto genérico

existirá.

Otro uso del objeto genérico sería como una plantilla. Es un lugar conveniente para almacenar valores predeterminados específicos de la clase para varios campos a ser usados en la inicialización de objetos

reales.

Usualmente, la característica puede ser ignorada por completo. Llamar a métodos de objeto como métodos de clase normalmente conduce a un error y no se usa rutinariamente en ningún lugar.

Puede ser un problema que este error no sea
indicado por una clase con un objeto genérico.

Cómo usar los Hashes de

Campo

Tradicionalmente, la definición de una clase "inside-out" contiene un bloque desnudo dentro del cual se declaran varios hashes léxicos y se definen los métodos básicos de acceso, usualmente a través de "Scalar::Util::refaddr". Más métodos pueden ser definidos fuera de este bloque. Debe haber un método DESTROY y, para soporte de hilos, un método

CLONE.

Cuando se usan hashes de campo, la estructura básica permanece igual. Cada hash léxico será convertido en un hash de campo. La llamada a "refaddr" puede ser omitida de los métodos de acceso. Los métodos DESTROY y CLONE no son

necesarios.

Si tienes una clase "inside-out" existente, simplemente hacer que todos los hashes sean hashes de campo sin ningún otro cambio no debería hacer ninguna diferencia. A través de las llamadas a "refaddr" o equivalentes, los hashes de campo nunca llegan a ver una referencia y funcionan como hashes normales. Tus métodos DESTROY (y CLONE) todavía son

necesarios.

Para hacer que los hashes de campo actúen, es más fácil redefinir "refaddr"

como 
sub refaddr { shift
}

en lugar de importarlo desde "Scalar::Util". Ahora debería ser posible deshabilitar DESTROY y CLONE. Ten en cuenta que mientras no esté deshabilitado, DESTROY será llamado antes de la recolección de basura de los hashes de campo, por lo que será invocado con un objeto funcional y continuará

funcionando.

No es deseable importar las funciones "fieldhash" y/o "fieldhashes" en cada clase que vaya a usarlas. Solo se usan una vez para configurar la clase. Cuando la clase esté en funcionamiento, estas funciones ya no sirven para

nada.

Si solo hay unos pocos hashes de campo que declarar, es más simple

usar

Hashes Recolectados de

Basura

La recolección de basura en un hash de campo significa que las entradas desaparecerán "espontáneamente" cuando el objeto que las creó desaparezca. Eso debe tenerse en cuenta, especialmente al recorrer un hash de campo. Si cualquier cosa que hagas dentro del bucle podría causar que un objeto salga de ámbito, una clave aleatoria puede ser borrada del hash que estás recorriendo. Eso puede lanzar fuera al iterador del bucle, por lo que es mejor almacenar en caché una instantánea consistente de las claves y/o valores y recorrer esa. Aún tendrás que comprobar que una entrada en caché todavía existe cuando llegues a

ella.

La recolección de basura puede ser confusa cuando las claves se crean en un hash de campo a partir de escalares normales así como de referencias. Una vez que una referencia es usada con un hash de campo, la entrada será recolectada, incluso si fue posteriormente sobrescrita con una clave de escalar simple (cualquier entero positivo es un candidato). Esto es cierto incluso si la entrada original fue borrada en el medio. De hecho, la eliminación de un hash de campo, y también una prueba de existencia, constituyen un uso en este sentido y crean una obligación de borrar la entrada cuando la referencia sale de ámbito. Si resulta que creas una entrada con

una clave idéntica a partir de una cadena o un entero, esa será recolec
tada en su lugar. Por lo tanto, el uso mixto de referencias y escala
res simples como claves de hash de campo no es totalmente soportado.

métodos:

    Un método de objeto que inicializa el nombre de pila y el apellido con sus dos argumentos. Si es llamado como método de clase, init() crea un objeto en la clas

    e dada y
    • lo inicializa.
  • first()

    Recupera el nombre de

    pila
    • last()

      Recupera el apellido

    • name()

      Recupera el nombre completo, el nombre y el apellido unidos por un espacio.

    Los ejemplos muestran esta clase implementada con diferentes niveles de soporte por parte de "Hash::Util::FieldHash". Se muestran todas las combinaciones compatibles. La diferencia entre implementaciones suele ser bastante pequeña. Las implementaciones son:

    • "Name_hash"

      Una implementación convencional (no de fuera hacia adentro) donde un objeto es un hash que almacena los valores de los campos, sin soporte por parte de "Hash::Util::FieldHash". Esta implementación no permite la herencia arbitraria.

    • "Name_id"

      Implementación de fuera hacia adentro basada en la función id(). Necesita un método "DESTROY". Para soporte de hilos, también se necesitaría un método "CLONE" (no mostrado). En lugar de Hash::Util::FieldHash::id(), la función "Scalar::Util::refaddr" podría usarse con muy poca diferencia funcional. Este es el patrón básico de una clase de fuera hacia adentro.

    • "Name_idhash"

      Implementación de fuera hacia adentro basada en Idhash. Al igual que "Name_id", necesita un método "DESTROY" y necesitaría "CLONE" para soporte de hilos.

    • "Name_id_reg"

      Implementación de fuera hacia adentro basada en la función id() con registro explícito de objetos. No se necesita destructor y los objetos son seguros para hilos.

    • "Name_idhash_reg"

      Implementación de fuera hacia adentro basada en Idhash con registro explícito de objetos. No se necesita destructor y los objetos son seguros para hilos.

    • "Name_fieldhash"

      Implementación de fuera hacia adentro basada en FieldHash. El registro de objetos ocurre automáticamente. No se necesita destructor y los objetos son seguros para hilos.

    Ejemplo 1

    use strict; use warnings;
{
    package Name_hash;  # implementación estándar: el
                        # objeto es un hash
    sub init {
        my $obj = shift;
        my ($first, $last) = @_;
        # crea un objeto si se llama como método de clase
        $obj = bless {}, $obj unless ref $obj;
        $obj->{ first} = $first;
        $obj->{ last} = $last;
        $obj;
    }
    sub first { shift()->{ first} }
    sub last { shift()->{ last} }
    sub name {
        my $n = shift;
        join ' ' => $n->first, $n->last;
    }
}
{
    package Name_id;
    use Hash::Util::FieldHash qw(id);
    my (%first, %last);
    sub init {
        my $obj = shift;
        my ($first, $last) = @_;
        # crea un objeto si se llama como método de clase
        $obj = bless \ my $o, $obj unless ref $obj;
        $first{ id $obj} = $first;
        $last{ id $obj} = $last;
        $obj;
    }
    sub first { $first{ id shift()} }
    sub last { $last{ id shift()} }
    sub name {
        my $n = shift;
        join ' ' => $n->first, $n->last;
    }
    sub DESTROY {
        my $id = id shift;
        delete $first{ $id};
        delete $last{ $id};
    }

package NamedFile;

sub init {
    my $obj = shift;
    my ($file, $first, $last) = @_;
    $obj = $obj->IO::File::new() unless ref $obj;

Hash::Util::FieldHash(3perl)

NAME

Hash::Util::FieldHash - support for field hashes

SYNOPSIS

    use Hash::Util::FieldHash;
    my %foo;
    my $ref_to_foo = \%foo;
    fieldhash \%foo;
    $foo{ $ref_to_foo } = 1;
    print exists $foo{ $ref_to_foo }; # prints 1

FUNCTIONS

fieldhash($hashref)
Turns the given hash into a field hash. Any scalar reference can be used as a key. Existing keys are NOT erased.
fieldhash_keys($hashref)
Returns a list of all keys stored in the field hash. These will be references.
is_fieldhash($hashref)
Returns true if the given hash is a field hash, false otherwise.

DESCRIPTION

Field hashes allow you to use references as keys in a hash. This is not directly supported by Perl hashes, because references are compared by value. If you have two references that point to the same thing, they are equal. If you have two references that point to different things, they are not equal. So if you use a reference as a key, only that exact reference can be used to look up the value. This module allows you to use any reference that points to the same thing as a key.

This module works by storing a copy of the reference in a special way. When you use a reference as a key in a field hash, the hash will store a copy of the reference along with the value. When you look up a value using a reference, it will check if there is an entry for a reference that points to the same thing. If there is, it will return the value associated with that reference. If not, it will return undef.

Field hashes have three main features:

  • Key replacement: If you have a reference in a field hash, and then create another reference that points to the same underlying data, you can use either reference to access the value. The hash will automatically recognize that the new reference refers to the same data as the old reference.

  • Thread support: Field hashes are designed to work correctly in multi-threaded environments. When a thread is cloned, the field hashes used in the parent thread are copied to the child thread, so that keys remain valid.

  • Garbage collection: Field hashes use a mechanism that allows for automatic garbage collection of keys. When a reference that has been used as a key in a field hash is no longer reachable, it will be automatically removed from the field hash. This prevents memory leaks.

EXAMPLES

    use Hash::Util::FieldHash qw(fieldhash is_fieldhash);
    my %hash;
    my $ref1 = { name => 'foo' };
    my $ref2 = $ref1;
    my $ref3 = { name => 'bar' };
    fieldhash \%hash;
    $hash{ $ref1 } = 1;
    print exists $hash{ $ref1 }; # prints 1
    print exists $hash{ $ref2 }; # prints 1
    print exists $hash{ $ref3 }; # prints 0
    print is_fieldhash \%hash;   # prints 1

GUTS

Field hashes are implemented using a private hash called the "object registry". This registry stores all references that have been used as keys in any field hash. Each entry in the registry contains a weak reference to the original object, along with a list of all field hashes that the object has been used with.

When a weak reference in the object registry becomes stale (i.e., the object is garbage collected), the registry is notified. It then uses the list of field hashes to remove the reference from all field hashes it was associated with. After that, the entry is removed from the object registry itself.

This mechanism ensures that references are automatically removed from field hashes when they are no longer needed, preventing memory leaks.

The object registry is also used to repair field hashes after thread cloning. When a thread is cloned, the object registry is processed, and all field hashes associated with references in the registry are updated to reflect the cloned thread's state.

The internal function _fieldhash is used to manage the object registry. It takes a hashref and a mode as arguments. If the mode is false, it checks if the hash is a field hash. If the mode is true, it turns the hash into a field hash.

This hook can be used to trigger further garbage-collection activities associated with the referenced object.

How field hashes work

The three features of key hashes, key replacement, thread support, and garbage collection are supported by a data structure called the object registry. This is a private hash where every object is stored. An "object" in this sense is any reference (blessed or unblessed) that has been used as a field hash key.

The object registry keeps track of references that have been used as field hash keys. The keys are generated from the reference address like in a field hash (though the registry isn't a field hash). Each value is a weak copy of the original reference, stored in an "SV" that is itself magical ("PERL_MAGIC_uvar" again). The magical structure holds a list (another hash, really) of field hashes that the reference has been used with. When the weakref becomes stale, the magic is activated and uses the list to delete the reference from all field hashes it has been used with. After that, the entry is removed from the object registry itself. Implicitly, that frees the magic structure and the storage it has been using.

Whenever a reference is used as a field hash key, the object registry is checked and a new entry is made if necessary. The field hash is then added to the list of fields this reference has used.

The object registry is also used to repair a field hash after thread cloning. Here, the entire object registry is processed. For every reference found there, the field hashes it has used are visited and the entry is updated.

Internal function Hash::Util::FieldHash::_fieldhash

# test if %hash is a field hash
my $result = _fieldhash \ %hash, 0;
# make %hash a field hash
my $result = _fieldhash \ %hash, 1;

"_fieldhash" is the internal function used to create field hashes. It takes two arguments, a hashref and a mode. If the mode is boolean false, the hash is not changed but tested if it is a field hash. If the hash isn't a field hash the return value is boolean false. If it is, the return value indicates the mode of field hash. When called with a boolean true mode, it turns the given hash into a field hash of this mode, returning the mode of the created field hash. "_fieldhash" does not erase the given hash.

Currently there is only one type of field hash, and only the boolean value of the mode makes a difference, but that may change.
