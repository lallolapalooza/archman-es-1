A Visión del usuario de los módulos orientados a

objetos

-- Sean M.

Burke

La primera vez que la mayoría de los programadores de Perl se encuentran con la programación orientada a objetos es cuando necesitan usar un módulo cuya interfaz es orientada a objetos. Esta suele ser una experiencia desconcertante, ya que hablar de "métodos" y "constructores" es ininteligible para programadores que pensaban que las funciones y las variables eran todo lo que había que

preocuparse.

Los artículos y libros que explican la programación orientada a objetos (POO) lo hacen en términos de cómo programar de esa manera. Eso es comprensible, y si aprendes a escribir tu propio código orientado a objetos, encontrarías fácil usar código orientado a objetos que otros escriben. Pero este enfoque es el camino largo para personas cuyo objetivo inmediato es solo usar módulos orientados a objetos existentes, pero que aún no quieren conocer todos los detalles escabrosos de tener que escribir tales módulos por sí

mismos.

Este artículo es para esos programadores -- programadores que quieren saber sobre objetos desde la perspectiva de usar módulos orientados a

objetos.

Módulos y sus interfaces

funcionales

Los módulos son la principal forma en que Perl proporciona para empaquetar código para uso posterior por ti mismo o por otros. Como seguro que no puedes evitar notar al leer The Perl Journal, CPAN (la Red Integral de Archivos de Perl) es el repositorio para módulos (o grupos de módulos) que otros han escrito, para hacer cualquier cosa desde componer música hasta acceder a páginas web. Buena parte de esos módulos incluso vienen con cada instalación de

Perl.

Un módulo que quizás hayas usado antes, y que es bastante típico en su interfaz, es Text::Wrap. Viene con Perl, así que ni siquiera necesitas instalarlo desde CPAN. Lo usas en un programa tuyo, haciendo que tu código diga

temprano:

La forma en que este "use Text::

Wrap"
negocio funciona es que el módulo Text::Wrap existe como un archivo "Text/Wrap.pm" en algún lugar de una de tus directorios de biblioteca. Ese archivo contiene código Perl..

Nota al pie: Y mezclado con el código Perl, hay documentación, que es lo que lees con "perldoc Text::Wrap". El programa perldoc simplemente ignora el código y formatea el texto de la documentación, mientras que "use Text::Wrap" carga y ejecuta el código mientras ignora la documentación. ...que, entre otras cosas, define una función llamada "Text::Wrap::wrap", y luego "exporta" esa función, lo que significa que cuando dices "wrap" después de haber dicho "use Text::Wrap", estarás llamando rea

lmente a la función

"Text::Wrap::wrap". Algunos módulos no exportan sus funciones, así que tienes que llamarlas por su nombre completo, como Text::Wrap::wrap(...parámetros...). Independientemente de si el módulo típico exporta las funciones que proporciona, un módulo es básicamente solo un contenedor para trozos de código que hacen cosas útiles. La forma en que el módulo permite que interactúes con él es su interfaz. Y cuando, como con Text::Wrap, su interfaz consiste en funciones, se dice que el módulo

tiene una
interfazfuncional
.

Nota al pie: el término "función" (y por tanto "funcional") tiene varios sentidos. Estoy usando el término aquí en su sentido más amplio, para referirme a rutinas -- trozos de código que se llaman por algún nombre y que toman parámetros y devuelven algún valor. Usar módulos con interfaces funcionales es directo -- en lugar de definir tu propia función "wrap" con "sub wrap { ... }", confías en que "use Text::Wrap" haga eso por ti, junto con cualquier otra función que defina y exporte, según la documentación del módulo. Sin demasiado esfuerzo, incluso puedes escribir tus propios módulos para contener tus funciones frecuentemente usadas; sugiero echar un

vistazo
a la

página man "perlmod" para más pistas sobre cómo hacer

Módulos con interfaces orientadas a objetos Así que supongamos que un día quieres escribir un programa que automatice el proceso

de

Una rápida navegación por search.cpan.org revela el módulo "Net::FTP", que puedes descargar e instalar usando las instrucciones de instalación normales (a menos que tu administrador de sistemas ya lo haya instalado, como muchos han hecho)

Mientras que módulos como Text::Wrap proporcionan trozos de código útiles como funciones, para ser llamadas como función(...parámetros...) o como NombreDePaquete::función(...parámetros...), Net::FTP y otros módulos con interfaces orientadas a objetos

Los métodos son algo así como funciones en que tienen un nombre y parámetros; pero los métodos se ven diferentes, y son diferentes, porque tienes que llamarlos con una sintaxis que tiene un nombre de clase o un objeto como argumento especial. Explicaré la sintaxis para las llamadas a métodos, y luego explicaré lo que todos significan. Algunos métodos están destinados a ser llamados

Pero, dejando a un lado las alternativas sintácticas, toda esta charla sobre la construcción de objetos y métodos de objetos plantea la pregunta: ¿qué *es* un objeto? ¿Qué Puedes Hacer con los Objetos?

Has visto que puedes crear objetos y llamar métodos de objeto con ellos. Pero, ¿para qué sirven los métodos de objeto? La respuesta depende de la clase:

Un objeto Net::FTP representa una sesión entre tu ordenador y un servidor FTP. Por lo tanto, los métodos que llamas en un objeto Net::FTP son para hacer cualquier cosa que necesites hacer a través de una conexión FTP. Creas la sesión e inicias sesión:

my $session = Net::FTP->new('ftp.aol.com');
die "¡No se pudo conectar!" unless defined $session;
  # La llamada al método de clase "new" devolverá
  # el nuevo objeto si va bien, de lo contrario
  # devolverá undef.

$session->login('sburke', 'p@ssw3rD')
 || die "¿He cambiado mi contraseña de nuevo?";
  # El método de objeto "login" devolverá un valor
  # verdadero si realmente inicia sesión, de lo contrario
  # devolverá falso.

Puedes usar el objeto de sesión para cambiar de directorio en esa sesión:

$session->cwd("/home/sburke/public_html")
   || die "¡Oye, eso REALMENTE debería haber funcionado!";
 # si cwd falla, devolverá falso

...obtener archivos de la máquina al otro lado de la sesión...

foreach my $f ('log_report_ua.txt', 'log_report_dom.txt',
               'log_report_browsers.txt')
{
  $session->get($f) || warn "¡Obtener $f falló!";
};

...y muchas cosas más, terminando finalmente cerrando la conexión:

$session->quit();

En resumen, los métodos de objeto son para hacer cosas relacionadas con (o con) lo que sea que represente el objeto. Para las sesiones FTP, se trata de enviar comandos al servidor al otro lado de la conexión, y eso es todo: allí, los métodos sirven para hacer algo con el mundo exterior al objeto, y el objeto es simplemente algo que especifica con qué parte del mundo (bueno, con qué sesión FTP) actuar.

Sin embargo, con la mayoría de las otras clases, el objeto en sí mismo almacena algún tipo de información, y normalmente no tiene sentido hacer cosas con dicho objeto sin considerar los datos que contiene.

¿Qué hay en un Objeto?

Un objeto es (con raras excepciones) una estructura de datos que contiene un montón de atributos, cada uno con un valor, además de un nombre que usas al leer o establecer el valor del atributo. Algunos de los atributos del objeto son privados, lo que significa que nunca los verás documentados porque no son para que los leas o escribas; pero la mayoría de los atributos documentados del objeto son al menos legibles, y generalmente escribibles, por ti. Los objetos Net::FTP son un poco escasos en atributos, así que usaremos objetos de la clase Business::US_Amort para este ejemplo. Business::US_Amort es una clase muy simple (disponible en CPAN) que escribí para hacer cálculos relacionados con préstamos (específicamente, amortización, utilizando algoritmos de estilo estadounidense).

Un objeto de la clase Business::US_Amort representa un préstamo con parámetros particulares, es decir, atributos. Los atributos más básicos de un "objeto de préstamo" son su tasa de interés, su capital (cuánto dinero es) y su plazo (cuánto tiempo tardará en pagarse). Necesitas establecer estos atributos antes de que se pueda hacer nada más con el objeto. La forma de acceder a esos atributos para los objetos de préstamo es igual que la forma de acceder a los atributos para los objetos de cualquier clase: a través de accedentes. Un accedente es simplemente cualquier método que accede (ya sea leyendo o escribiendo, también conocido como obtener o poner) a algún atributo en el objeto dado. Además, los accedentes son la única forma en que puedes cambiar los atributos de un objeto. (Si la documentación de un módulo quiere que sepas alguna otra forma, te lo dirá).

Normalmente, por simplicidad, un accedente se nombra según el atributo que lee o escribe. Con los objetos Business::US_Amort, los accedentes que necesitas usar primero son "principal", "interest_rate" y "term". Luego, con al menos esos atributos establecidos, puedes llamar al método "run" para calcular varias cosas sobre el préstamo. Luego puedes llamar a varios accedentes, como "total_paid_toward_interest", para leer los resultados:

use Business::US_Amort;
my $loan = Business::US_Amort->new;
# Establecer los atributos necesarios:
$loan->principal(123654);
$loan->interest_rate(9.25);
$loan->term(20); # veinte años
# AHORA sabemos lo suficiente para calcular:
$loan->run;

# Y ver qué resultó de eso:
print
  "Total pagado en intereses: ¡UN ENORME ",
  $loan->total_paid_interest, "!!\n";

Esto ilustra una convención común con los accedentes: llamar al accedente sin argumentos (como con $loan->total_paid_interest) generalmente significa leer el valor de ese atributo, pero proporcionar un valor (como con $loan->term(20)) significa que quieres que ese atributo se establezca a ese valor. Esto tiene sentido: ¿por qué proporcionarías un valor, si no fuera para establecer el atributo a ese valor?

Aunque el plazo, el capital y las tasas de interés de un préstamo son todos valores numéricos únicos, los valores de los objetos pueden ser cualquier tipo de escalar, o un array, o incluso un hash. Además, el valor o los valores de un atributo pueden ser objetos en sí mismos. Por ejemplo, considera los archivos MIDI (como escribí en TPJ#13): un archivo MIDI generalmente consiste en varias pistas. Un archivo MIDI es lo suficientemente complejo como para merecer ser un objeto con atributos como su tempo general, la variante del formato de archivo en el que se encuentra y la lista de pistas de instrumentos en el archivo. Pero las pistas en sí mismas son lo suficientemente complejas como para ser objetos también, con atributos como su tipo de pista, una lista de comandos MIDI si son una pista MIDI, o datos sin procesar si no lo son. Así que terminé escribiendo los módulos MIDI para que el atributo "tracks" de un objeto MIDI::Opus sea un array de objetos de la clase MIDI::Track. Esto puede parecer un rodeo: preguntas qué hay en un objeto y obtienes *otro* objeto, ¡o varios! Pero en este caso, refleja exactamente para qué es el módulo: los archivos MIDI contienen pistas MIDI, que a su vez contienen datos.

¿Qué es un Valor de Objeto?

Cuando llamas a un constructor como Net::FTP->new(hostname), obtienes un valor de objeto, un valor que puedes usar más tarde, en combinación con un nombre de método, para llamar a métodos de objeto.

Ahora bien, hasta ahora hemos estado fingiendo, en los ejemplos anteriores, que las variables $session o $loan *son* los objetos con los que estás tratando. Esta idea es inofensiva hasta cierto punto, pero en realidad es una concepción errónea que, en el mejor de los casos, te limitará en lo que sabes hacer. La realidad no es que las variables $session o $query sean objetos; es un poco más indirecto: *contienen* valores que simbolizan objetos. El tipo de valor que $session o $query contienen es lo que estoy llamando un valor de objeto.

Para entender qué tipo de valor es este, primero piensa en los otros tipos de valores escalares que conoces: Los dos primeros valores escalares que probablemente te encontraste en Perl son los **números** y las **cadenas**, que aprendiste (o simplemente asumiste) que normalmente se convertirán entre sí a demanda; es decir, la cadena de tres caracteres "2.5" puede convertirse en la cantidad dos y medio, y viceversa. Luego, especialmente si empezaste a usar "perl -w" temprano, aprendiste sobre el **valor indefinido**, que puede convertirse en 0 si lo tratas como un número, o en la cadena vacía si lo tratas como una cadena.

Nota al pie: *También* puedes haber aprendido sobre referencias, en cuyo caso estás listo para escuchar que los valores de objeto son solo un tipo de referencia, excepto que reflejan la clase que creó la cosa a la que apuntan, en lugar de ser simplemente una referencia a un array, referencia a un hash, etc. *Si* esto tiene sentido para ti, y quieres saber más sobre cómo se implementan los objetos en Perl, echa un vistazo a la página del manual "perltoot".

Y ahora estás aprendiendo sobre **valores de objeto**. Un valor de objeto es un valor que apunta a una estructura de datos en algún lugar de la memoria, que es donde se almacenan todos los atributos de este objeto. Esa estructura de datos en su conjunto pertenece a una clase (probablemente la que nombraste en el método constructor, como ClaseNombre->new), de modo que el valor del objeto se puede usar como parte de las llamadas a métodos de objeto.

Si quieres ver realmente qué es un valor de objeto, puedes intentar simplemente decir "print $objeto". Obtendrás algo como esto:

Por la razón que sea, *esta* oferta suena go od a ti, así que rellenas el formulario y lo envías por correo a la compañía de tarjetas de crédito. Puedes pagar parte de la cuenta enviando a la gente de la tarjeta de crédito algo de tu dinero (bueno, un cheque) con alguna nota (generalmente el resguardo prediseñado) que tenga el número de la tarjeta de la cuenta hacia la que quieres pagar. Ahora, ese símbolo es solo un montón de dígitos, y el número es efectivamente inútil y sin sentido en sí mismo -- pero en el contexto apropiado, se entiende que significa la cuenta de tarjeta de crédito

NAME

HTML::Tree::AboutObjects - A user's view of object-oriented modules

SYNOPSIS

    use HTML::Tree;
    my $tree = HTML::Tree->new();
    $tree->parse_content( $html );
    my @links = $tree->find_all_links();
    # etc.

DESCRIPTION

This document is intended to explain object-oriented modules to those who've never encountered them before. It assumes no prior knowledge of objects, classes, or object-oriented programming.

A User's View of Object-Oriented Modules

Let's start with an analogy. Imagine that you want to write a program that sends mail. In Perl, you can do this with a module called Net::SMTP. A few years ago, the only way to use Net::SMTP was with a functional interface. That is, you'd call subroutines like this:

    use Net::SMTP;
    Net::SMTP::mail( $to );
    Net::SMTP::data( $message );
    Net::SMTP::quit();

And if you wanted to send mail to two different hosts, you'd have to do something like this:

    use Net::SMTP;
    Net::SMTP->host( 'mail.foo.com' );
    Net::SMTP::mail( $to1 );
    Net::SMTP::data( $message1 );
    Net::SMTP::quit();
    Net::SMTP->host( 'mail.bar.com' );
    Net::SMTP::mail( $to2 );
    Net::SMTP::data( $message2 );
    Net::SMTP::quit();

Notice that the second time you call host() it implicitly changes the host for all subsequent calls. That's because the module had to keep track of the host *globally*. That is, the module had to keep track of the host on behalf of all users of the module.

This is called a "functional" interface, because you're just calling functions (or subroutines, or methods). And it works fine, for simple cases. But suppose you wanted to send mail to two different hosts *simultaneously*? You couldn't do it with that functional interface. You'd have to write your own code to keep track of the state for each host. You'd have to keep track of which host you were talking to, what state you were in with that host, etc.

Now, modules have come out with an object-oriented interface. You use it like this:

    use Net::SMTP;
    my $session1 = Net::SMTP->new( 'mail.foo.com' );
    $session1->mail( $to1 );
    $session1->data( $message1 );
    $session1->quit;
    my $session2 = Net::SMTP->new( 'mail.bar.com' );
    $session2->mail( $to2 );
    $session2->data( $message2 );
    $session2->quit;

This time, you're not just calling subroutines. You're creating *objects*. The line my $session1 = Net::SMTP->new( 'mail.foo.com' ); creates an object named $session1. This object is an instance of the Net::SMTP class. It holds within itself all the state that was previously kept globally: the host it's talking to, the state it's in, etc.

So, what's the advantage? Well, notice that we can now have two (or more!) sessions open simultaneously. $session1 and $session2 are completely separate from each other. You can send mail through $session1 without affecting $session2 at all.

This is the main advantage of object-oriented interfaces: they allow you to manage multiple simultaneous instances of something. This is useful for all sorts of things. For example, the HTML::Tree module has an object-oriented interface. You can create multiple HTML::Tree objects, each representing a different HTML document, and work with them all at the same time. This is something you couldn't do if the module used a functional interface, by doing without filehandles. But you'd be out of luck if you wanted to read from one file while reading from another, or read from two and print to a third.

In the same way, a functional FTP module would be fine for just uploading files to one server at a time, but it wouldn't allow you to easily write programs that make need to use several simultaneous sessions (like "look at server A and server B, and if A has a file called X.dat, then download it locally and then upload it to server B -- except if B has a file called Y.dat, in which case do it the other way around").

Some kinds of problems that modules solve just lend themselves to an object-oriented interface. For those kinds of tasks, a functional interface would be more familiar, but less powerful. Learning to use object-oriented modules' interfaces does require becoming comfortable with the concepts from this article. But in the end it will allow you to use a broader range of modules and, with them, to write programs that can do more.

The Gory Details

For sake of clarity of explanation, I had to oversimplify some of the facts about objects. Here's a few of the gorier details:

* Every example I gave of a constructor was a class method. But object methods can be constructors, too, if the class was written to work that way: $new = $old->copy, $node_y = $node_x->new_subnode, or the like.

* I've given the impression that there's two kinds of methods: object methods and class methods. In fact, the same method can be both, because it's not the kind of method it is, but the kind of calls it's written to accept -- calls that pass an object, or calls that pass a class-name.

* The term "object value" isn't something you'll find used much anywhere else. It's just my shorthand for what would properly be called an "object reference" or "reference to a blessed item". In fact, people usually say "object" when they properly mean a reference to that object.

* I mentioned creating objects with constructors, but I didn't mention destroying them with destructor -- a destructor is a kind of method that you call to tidy up the object once you're done with it, and want it to neatly go away (close connections, delete temporary files, free up memory, etc). But because of the way Perl handles memory, most modules won't require the user to know about destructors.

* I said that class method syntax has to have the class name, as in $session = Net::FTP->new($host). Actually, you can instead use any expression that returns a class name: $ftp_class = 'Net::FTP'; $session = $ftp_class->new($host). Moreover, instead of the method name for object- or class-method calls, you can use a scalar holding the method name: $foo->$method($host). But, in practice, these syntaxes are rarely useful.

And finally, to learn about objects from the perspective of writing your own classes, see the "perltoot" documentation, or Damian Conway's exhaustive and clear book Object Oriented Perl (Manning Publications 1999, ISBN 1-884777-79-1).
