INTRODUCCIÓ

N

Los internos de Hash::Ordered son simples: un hash de datos y un array de claves ordenadas. Pensé que esto funcionaría bien para tareas comunes y probablemente superaría a implementaciones de hash ordenado más complicadas, así que decidí hacer algunas pruebas de rendimiento para

probarlo.

Nota: desde las pruebas de rendimiento iniciales, "Hash::Ordered" ganó indexación just-in-time del array de claves para soportar borrado de tumbstones más rápido, lo que añade algunas estructuras de datos condicionales a los internos. Ahora también soporta "tie". Las pruebas revisadas incluyen el modo "tie" para comparación con otras

implementacion
es de hash atadas.

PRUEBAS DE

RENDIMIENTO

Realicé pruebas de rendimiento con el módulo Benchmark. El script de pruebas está en el directorio "devel" de la distribución. Las pruebas se ejecutaron en Perl 5.20.2 en un Mac Book Pro (darwin-thread-multi-2level). Cada prueba de rendimiento se ejecutó durante 5 segundos de

CPU.

Las pruebas de rendimiento se ejecutaron a varias escalas diferentes para revelar diferencias en eficiencia a medida que crece el tamaño del hash. Los detalles se describen en cada sección a

continuación.

Se generó una lista semilla de claves y valores a partir de enteros aleatorios usando Math::Random::MT::Auto. La misma lista semilla se usó para todas las pruebas de rendimiento salvo que se indique lo

contrario.

No probé características avanzadas de estos módulos, ya que la comparación manzanas con manzanas es difícil. Aun así, el rendimiento en medidas comunes y simples podría sugerir cómo podrían funcionar características que combinan estas

operaciones.

Creación de hash

ordenado

Probé la creación de hash para 10, 100 y 1000 elementos. Para algunos módulos había diferentes opciones para crear un

hash:
  • "Array::AsHash" toma una referencia de array con una opción para usarla directamente o clonarla. En un caso proporcioné la referencia de array de la lista semilla con la opción de clonado a verdadero ("a:ah_cp"). En otro caso creé una nueva referencia de array a partir de la lista semilla y la proporcioné directamente ("a:ah_rf")
    • .
  • "Hash::Ordered" puede inicializarse ya sea con "new" ("h:o_oo") o a través de "tie" ("h:o_th")
    • .
  • "Tie::IxHash" puede inicializarse ya sea con "new" ("t:ix_oo") o a través de "tie" ("t:ix_th")
    • .
  • "Data::XHash" puede crearse con una lista (
    • "t:xh_ls") o una referenc
ia de array ("t:xh_rf").

Como se esperaba, cuando "Array::AsHash" recibe una referencia de array, es muy rápido. "Tie::Hash::Indexed" también lo hace bien aquí. De las opciones no XS, más similares a hash, "Hash::Ordered" lo hace

bien.

Eliminando elementos del

hash

Probé crear hashes de 10, 100 y 1000 elementos y luego eliminar el 10% de las claves, elegidas aleatoriamente. Me habría gustado aislar la creación de la eliminación, pero no pude encontrar una manera de hacerlo dado cómo "Benchmark" ejecita las mismas pruebas una y otra

vez.

Algunos módulos tenían opciones para cómo eliminar un valor, generalmente entre un método (denotado con "_oo"), acceso a hash vinculado ("_th") o con una desreferencia ("_rf")

.

Los cambios de rendimiento (o la falta de ellos) en los tres tamaños diferentes revelan diferencias de implementación. (Aunque recuerde que parte de esto es la diferencia de rendimiento de creación así como la de eliminación.

)

Por ejemplo, "Tie::Hash::Indexed" XS lo hace muy bien, lo cual podría ser su buen rendimiento de creación, pero también podría ser una buena

eliminación.

"Hash::Ordered" hace una búsqueda lineal al eliminar una clave para el hash de 10 elementos, pero cambia automáticamente a eliminación indexada con marcadores de tumba (tombstone) para los hashes más grandes. Al eliminar solo el 10% de las claves, la recolección de basura de las claves con marcador de tumba nunca ocurre, por lo que ese coste amortizado no se

incluye.

"Tie::LLHash" mejora en tamaños más grandes ya que eliminar de una lista enlazada es más rápido que extraer un elemento de un array. A la inversa, "Array::AsHash" solo

empeora.

Extrayendo el hash como una

lista

Probé obtener una lista ordenada de pares de hashes de 10, 100 y 1000 elementos. El hash se creó de antemano para que las pruebas de rendimiento reflejen solo la conversión a una

lista.

Extrañamente, los módulos que usualmente tienen más de una forma de hacer las cosas no la tienen para esto. Incluso "Tie::IxHash" no tiene realmente una forma OO de hacerlo, así que lo hice a

mano: 
@list = map { $_ => $tix_oo->FETCH($_) } $tix_oo->

Debido a que "Array::AsHash" mantiene su representación interna como una lista ordenada de pares, supera con facilidad al resto ya que solo necesita desreferenciar esa estructura de

datos.

CONCLUSIÓ

N

Con la excepción de la creación de hashes y la eliminación de elementos, "Hash::Ordered" generalmente superó a las otras implementaciones de hash ordenado. Incluso para la creación, fue el más rápido de las implementaciones basadas en hash, puramente en Perl, a menudo por un gran

margen.

En la versión original de "Hash::Ordered", la eliminación empeoraba a medida que crecía el tamaño del hash. El nuevo índice JIT con marcadores de tumba ahora hace que la eliminación sea mucho más rápida que en cualquier implementación puramente en

Perl.

"Array::AsHash", con la implementación interna opuesta a la de "Hash::Ordered", rinde mejor en la creación y el listado de pares, pero es el último en el acceso y la modificación de elementos. Creo que el mal rendimiento se debe en su mayor parte a una indirección extra (por ejemplo, una llamada a función extra) y lógica en los métodos de acceso a elementos. Para usos que no requieren mucho acceso a elementos y tienen mucha creación/serialización, podría seguir siendo una opción

útil.

Generalmente, cada módulo que depende de "tie" para alguna parte de su implementación paga una penalización de rendimiento sustancial. Comparar las pruebas de rendimiento de "Hash::Ordered" con y sin "tie" para operaciones individuales de elementos muestra lo severa que puede ser esta penalización. "Tie::Hash::Indexed" — probablemente debido a su implementación XS — rinde decentemente, pero no lo suficientemente bien en mi opinión para justificar su

uso.

Como autor de "Hash::Ordered", estoy claramente sesgado, pero creo que estas pruebas de rendimiento presentan un muy buen

argumento para que sea el módulo "por defecto" para hash
es ordenados de propósito general, puramente en Perl.
