Nombre

drm-kms - Kernel Mode-Setting

Sinopsis

#include <xf86drm.h>

#include <xf86drmMode.h>

Descripción

Cada dispositivo DRM proporciona acceso para gestionar qué monitores y pantallas se utilizan actualmente y qué fotogramas se van a mostrar. Esta tarea se llama Kernel Mode-Setting (KMS). Históricamente, esto se hacía en el espacio de usuario y se llamaba User-space Mode-Setting (UMS). Casi todos los controladores de código abierto ahora proporcionan la API KMS del kernel para hacer esto en el kernel, sin embargo, muchos controladores binarios no de código abierto de diferentes proveedores todavía no lo admiten. Puedes usar drmModeSettingSupported(3) para comprobar si tu controlador admite esto. Para entender cómo funciona KMS, necesitamos introducir 5 objetos: CRTCs, Planes, Encoders, Connectors y Framebuffers.

CRTCs
Un CRTC, abreviatura de CRT Controller (Controlador CRT), es una abstracción que representa una parte del chip que contiene un puntero a un buffer de escaneo. Por lo tanto, el número de CRTCs disponibles determina cuántos buffers de escaneo independientes pueden estar activos en un momento dado. La estructura CRTC contiene varios campos para soportar esto: un puntero a alguna memoria de video (abstraída como un objeto framebuffer), una lista de conectores controlados, un modo de visualización y un desplazamiento (x, y) dentro de la memoria de video para admitir desplazamiento panorámico o configuraciones donde una pieza de memoria de video abarca varios CRTCs. Un CRTC es el punto central donde ocurre la configuración de las pantallas. Seleccionas qué objetos usar, qué modos y qué parámetros, y luego configuras cada CRTC a través de drmModeCrtcSet(3) para controlar los dispositivos de visualización.
Planes
Un plano representa una fuente de imagen que puede ser mezclada o superpuesta sobre un CRTC durante el proceso de escaneo. Los planos están asociados a un framebuffer para recortar una porción de la memoria de imagen (fuente) y opcionalmente escalarla a un tamaño de destino. El resultado se mezcla o se superpone sobre un CRTC. Los planos no son proporcionados por todo el hardware y el número de planos disponibles es limitado. Si no hay planos disponibles o si no hay suficientes planos disponibles, el usuario debería recurrir a la mezcla de software normal (a través de GPU o CPU).
Encoders
Un encoder toma datos de píxeles de un CRTC y los convierte a un formato adecuado para cualquier conector conectado. En algunos dispositivos, puede ser posible que un CRTC envíe datos a más de un encoder. En ese caso, ambos encoders recibirían datos del mismo buffer de escaneo, lo que resultaría en una configuración de pantalla clonada en los conectores conectados a cada encoder.
Connectors
Un conector es el destino final de los datos de píxeles en un dispositivo, y normalmente se conecta directamente a un dispositivo de visualización externo como un monitor o un panel de portátil. Un conector solo puede estar conectado a un encoder a la vez. El conector es también la estructura donde se mantiene la información sobre la pantalla conectada, por lo que contiene campos para datos de visualización, datos EDID, DPMS y estado de conexión, e información sobre los modos soportados en las pantallas conectadas.
Framebuffers
Los Framebuffers son objetos de memoria abstractos que proporcionan una fuente de datos de píxeles para escanear a un CRTC. Las aplicaciones solicitan explícitamente la creación de framebuffers y pueden controlar su comportamiento. Los Framebuffers dependen del gestor de memoria subyacente para las operaciones de memoria de bajo nivel. Al crear un framebuffer, las aplicaciones pasan un manejador de memoria a través de la API que se utiliza como almacenamiento de respaldo. El framebuffer en sí es solo un objeto abstracto sin datos. Simplemente se refiere a buffers de memoria que deben crearse con la API de drm-memory(7).

Mode-Setting

Antes de que se pueda realizar el mode-setting, una aplicación necesita llamar a drmSetMaster(3) para convertirse en DRM-Master. Luego tiene acceso exclusivo a la API KMS. Una llamada a drmModeGetResources(3) devuelve una lista de CRTCs, Connectors, Encoders y Planes.

El procedimiento normal ahora incluye: Primero, seleccionas qué conectores quieres usar. A los usuarios les interesa principalmente qué monitor o panel de pantalla está activo, por lo que debes asegurarte de organizarlos en el orden lógico correcto y seleccionar los correctos para usar. Para cada conector, necesitas encontrar un CRTC para controlar este conector. Si quieres clonar la salida a dos o más conectores, puedes usar un solo CRTC para todos los conectores clonados (si el hardware lo admite). Para encontrar un CRTC adecuado, necesitas iterar sobre la lista de encoders disponibles para cada conector. Cada encoder contiene una lista de CRTCs con los que puede trabajar y simplemente seleccionas uno de estos CRTCs. Si más tarde programas el CRTC para controlar un conector, automáticamente selecciona el mejor encoder. Sin embargo, este procedimiento es necesario para que tu CRTC tenga al menos un encoder que funcione para el conector seleccionado. Consulta la sección Ejemplos a continuación para obtener más información.

Todos los modos válidos para un conector se pueden obtener con una llamada a drmModeGetConnector(3). Debes seleccionar el modo que deseas utilizar y guardarlo. El primer modo de la lista es el modo predeterminado con la resolución más alta posible y a menudo es una opción adecuada.

Después de tener una combinación de conector+CRTC+modo que funcione, necesitas crear un framebuffer que se utilice para el escaneo. La asignación de buffers de memoria depende del controlador y se describe en drm-memory(7). Necesitas crear un buffer lo suficientemente grande para el modo seleccionado. Ahora puedes crear un objeto framebuffer que utilice tu buffer de memoria como buffer de escaneo. Puedes hacerlo con drmModeAddFB(3) y drmModeAddFB2(3).

Como último paso, quieres programar tu CRTC para controlar tu conector seleccionado. Puedes hacerlo con una llamada a drmModeSetCrtc(3).

Volteo de Página (Page-Flipping)

Una llamada a drmModeSetCrtc(3) se ejecuta inmediatamente y fuerza al CRTC a utilizar el nuevo buffer de escaneo. Si deseas transiciones suaves sin desgarros (tearing), probablemente usarás doble búfer. Necesitas crear un objeto framebuffer por cada buffer que utilices. Luego puedes llamar a drmModeSetCrtc(3) en el siguiente buffer para voltear. Si deseas sincronizar tus volteos con los vblank (líneas de borrado vertical), puedes usar drmModePageFlip(3) que programa tu volteo de página para el próximo vblank.

Planes

Los planos se controlan de forma independiente de los CRTCs. Es decir, una llamada a drmModeSetCrtc(3) no afecta a los planos. En su lugar, necesitas llamar a drmModeSetPlane(3) para configurar un plano. Esto requiere el ID del plano, un CRTC, un framebuffer y desplazamientos dentro del framebuffer del plano y el framebuffer del CRTC. El CRTC mezcla el contenido del plano sobre el buffer del framebuffer del CRTC durante el escaneo. Como esto no implica ninguna mezcla de software, es mucho más rápido que la mezcla tradicional. Sin embargo, los recursos de los planos son limitados. Consulta drmModeGetPlaneResources(3) para obtener más información.

Cursores

Similar a los planos, muchos hardware también admiten cursores. Un cursor es un buffer muy pequeño con una imagen que se mezcla sobre el framebuffer del CRTC. Puedes configurar un cursor diferente para cada CRTC con drmModeSetCursor(3) y moverlo en la pantalla con drmModeMoveCursor(3). Esto permite mover el cursor en la pantalla sin volver a renderizar. Si no se admiten cursores de hardware, necesitas volver a renderizar cada vez que se mueva el cursor.

Selección de CRTC/Codificador

Si recuperó toda la información de configuración de pantalla a través de drmModeGetResources(3) como drmModeRes *res, seleccionó un conector de la lista en res->connectors y recuperó la información del conector como drmModeConnector *conn a través de drmModeGetConnector(3), este ejemplo muestra cómo encontrar un ID de CRTC adecuado para controlar este conector. Esta función toma un descriptor de archivo del dispositivo DRM (consulte drmOpen(3)) como fd, un puntero a los recursos recuperados como res y un puntero al conector seleccionado como conn. Devuelve un entero menor que 0 en caso de error, de lo contrario, se devuelve un ID de CRTC válido.

static int modeset_find_crtc(int fd, drmModeRes *res, drmModeConnector *conn)
{
    drmModeEncoder *enc;
    unsigned int i, j;
    /* itera todos los codificadores de este conector */
    for (i = 0; i < conn->count_encoders; ++i) {
        enc = drmModeGetEncoder(fd, conn->encoders[i]);
        if (!enc) {
            /* no se puede recuperar el codificador, ignorando... */
            continue;
        }
        /* itera todos los CRTC globales */
        for (j = 0; j < res->count_crtcs; ++j) {
            /* comprueba si este CRTC funciona con el codificador */
            if (!(enc->possible_crtcs & (1 << j)))
                continue;
            /* Aquí necesita comprobar que ningún otro conector
             * esté utilizando actualmente el CRTC con el ID "crtc". Si tiene la intención
             * de controlar solo un conector, puede omitir este
             * paso. De lo contrario, simplemente escanee su lista de conectores y
             * CRTCs configurados para ver si este CRTC ya está
             * en uso. Si lo está, simplemente continúe la búsqueda aquí. */
            if (res->crtcs[j] "no está en uso") {
                drmModeFreeEncoder(enc);
                return res->crtcs[j];
            }
        }
        drmModeFreeEncoder(enc);
    }
    /* no se puede encontrar un CRTC adecuado */
    return -ENOENT;
}
