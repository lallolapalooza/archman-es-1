Descripció

n

Muchas GPU modernas de gama alta vienen con sus propios gestores de memoria. Incluso incluyen varios cachés diferentes que necesitan ser sincronizados durante el acceso. Las texturas, los framebuffers, los command buffers y más necesitan ser almacenados en memoria que pueda ser accedida rápidamente por la GPU. Por lo tanto, la gestión de memoria en las GPUs es altamente dependiente del driver y del

hardware.

Sin embargo, hay varios frameworks en el kernel que son utilizados por más de un driver. Estos pueden ser usados para mode-setting trivial sin requerir código dependiente del driver. Pero para el renderizado con aceleración por hardware necesitas leer las páginas man del driver con el que deseas

trabajar.

Dumb-Buffer

s

Casi todos los drivers de hardware DRM en el kernel soportan una API llamada Dumb-Buffers. Esta API permite crear buffers de tamaño arbitrario que pueden ser usados para scanout. Estos buffers pueden ser mapeados en memoria vía mmap(2) para que puedas renderizar en ellos con la CPU. Sin embargo, el acceso de la GPU a estos buffers a menudo no es posible. Por lo tanto, son adecuados para tareas simples pero no son adecuados para composiciones y renderizados

complejos.

El ioctl DRM_IOCTL_MODE_CREATE_DUMB puede ser usado para crear un dumb buffer. El kernel devolverá un handle de 32 bits que puede ser usado para gestionar el buffer con la API DRM. Puedes crear framebuffers con drmModeAddFB(3) y usarlo para mode-setting y scanout. Para acceder al buffer, primero necesitas recuperar el offset del buffer. El ioctl DRM_IOCTL_MODE_MAP_DUMB solicita al subsistema DRM que prepare el buffer para el mapeo en memoria y devuelve un fake-offset que puede ser usado con mmap(

2).

El ioctl DRM_IOCTL_MODE_CREATE_DUMB toma como argumento una estructura de tipo struct drm_mode_create_dumb

: 
struct drm_mode_create_dumb {
    __u32 height;
    __u32 width;
    __u32 bpp;
    __u32 flags;
    __u32 handle;
    __u32 pitch;
    __u64 size;
}
;

Los campos height, width, bpp y flags deben ser proporcionados por el llamador. Los otros campos son rellenados por el kernel con los valores de retorno. height y width son las dimensiones del buffer rectangular que es creado. bpp es el número de bits por píxel y debe ser un múltiplo de 8. Lo más común es querer pasar 32 aquí. El campo flags actualmente no se usa y debe ser puesto a cero. Diferentes flags para modificar el comportamiento pueden ser añadidos en el futuro. Después de llamar al ioctl, los campos handle, pitch y size son rellenados por el kernel. handle es un gem handle de 32 bits que identifica el buffer. Este es usado por varias otras llamadas que toman un gem-handle o un memory-buffer como argumento. El campo pitch es el pitch (o stride) del nuevo buffer. La mayoría de los drivers usan valores de stride alineados a 32 bits o 64 bits. El campo size contiene el tamaño absoluto en bytes del buffer. Esto normalmente también puede ser calculado con (height * pitch + width

) * bpp / 4.

Para preparar el buffer para mmap(2) necesitas usar el ioctl DRM_IOCTL_MODE_MAP_DUMB. Toma como argumento una estructura de tipo struct drm_mode_map_dumb

: 
struct drm_mode_map_dumb {
    __u32 handle;
    __u32 pad;
    __u64 offset;
}
;

Necesitas poner el gem-handle que fue previamente recuperado vía DRM_IOCTL_MODE_CREATE_DUMB en el campo handle. El campo pad es relleno no usado y debe ser puesto a cero. Después de la finalización, el campo offset contendrá un offset que puede ser usado con mmap(2) en el file-descriptor de

DRM.

Si ya no necesitas tu dumb-buffer, tienes que destruirlo con DRM_IOCTL_MODE_DESTROY_DUMB. Si cierras el file-descriptor de DRM, todos los dumb-buffers abiertos son automáticamente destruidos. Este ioctl toma como argumento una estructura de tipo struct drm_mode_destroy_dumb

: 
struct drm_mode_destroy_dumb {
    __u32 handle;
}
;

Solo necesitas poner tu handle en el campo handle. Después de esta llamada, el handle es inválido

y puede ser reutilizado para nue
vos buffers por la dumb-API.

TT

M

TTM significa Translation Table Manager y es un gestor de memoria genérico proporcionado por el kernel. No proporciona una API de espacio de usuario común, así que necesitas

mirar la interfaz de cada driver si quieres usarlo. Mira por ejemplo las páginas
man de radeon para más información sobre la gestión de memoria con radeon y TTM.

GE

M

GEM significa Graphics Execution Manager y es un framework de gestión de memoria DRM genérico en el kernel, que es usado por muchos drivers diferentes. GEM está diseñado para gestionar la memoria gráfica, controlar el acceso al contexto de ejecución del dispositivo gráfico y manejar esencialmente el entorno NUMA único del hardware gráfico moderno. GEM permite que múltiples aplicaciones compartan recursos del dispositivo gráfico sin la necesidad de recargar constantemente toda la tarjeta gráfica. Los datos pueden ser compartidos entre múltiples aplicaciones con gem asegurando que la correcta sincronización de memoria

ocurra.

GEM proporciona mecanismos simples para gestionar datos gráficos y controlar el flujo de ejecución dentro del subsistema DRM de linux. Sin embargo, GEM no es un framework completo que sea totalmente independiente del driver. En su lugar, proporciona muchas funciones que son compartidas entre muchos drivers, pero cada driver tiene que implementar la mayor parte de la gestión de memoria con ioctls dependientes del driver. Esta página man intenta describir la semántica (y si aplica, la sintaxis) que es compartida entre todos los drivers que usan

GEM.

Todas las APIs de GEM están definidas como ioctl(2) en el file descriptor de DRM. Una aplicación debe ser autorizada vía drmAuthMagic(3) al DRM-Master actual para acceder al subsistema GEM. Un driver que no soporte GEM devolverá ENODEV para todos estos ioctls. Los handles de objetos inválidos devuelven EINVAL y los nombres de objetos inválidos devuelven ENOENT

.

Gem proporciona primitivas de gestión de memoria explícitas. Las páginas del sistema son asignadas cuando el objeto es creado, ya sea como el almacenamiento fundamental para hardware donde la memoria del sistema es usada directamente por el procesador gráfico, o como almacenamiento de respaldo para la memoria residente en el procesador

gráfico.

Los objetos son referenciados desde el espacio de usuario usando handles. Estos son, para todos los propósitos, equivalentes a file descriptors pero evitan la sobrecarga. Los drivers de kernel más nuevos también soportan la infraestructura drm-prime (7) que puede devolver file-descriptors reales para GEM-handles usando la API linux DMA-BUF. Los objetos pueden ser publicados con un nombre para que otras aplicaciones y procesos puedan acceder a ellos. El nombre permanece válido mientras el objeto exista. Los objetos GEM tienen conteo de referencias en el kernel. El objeto solo es destruido cuando todos los handles del espacio de usuario fueron

cerrados.

Los buffers GEM no pueden ser creados con una API genérica. Cada driver proporciona su propia API para crear buffers GEM. Mira por ejemplo DRM_I915_GEM_CREATE, DRM_NOUVEAU_GEM_NEW o DRM_RADEON_GEM_CREATE. Cada uno de estos ioctls devuelve un GEM-handle que puede ser pasado a diferentes ioctls genéricos. La libgbm librería de la distribución mesa3D intenta proporcionar una API independiente del driver para crear buffers GBM y recuperar un GBM-handle de ellos. Permite crear buffers para diferentes casos de uso incluyendo scanout, renderizado, cursores y acceso a CPU. Mira la librería libgbm para más información o mira las páginas man dependientes del driver (por ejemplo drm-intel(7) o drm-radeon(7))

.

Los buffers GEM pueden ser cerrados con drmCloseBufferHandle(3). Toma como argumento el GEM-handle a cerrar. Después de esta llamada el handle GEM no puede ser usado por este proceso más y puede ser reutilizado para nuevos objetos GEM por la API

GEM.

Si quieres compartir objetos GEM entre diferentes procesos, puedes crear un nombre para ellos y pasar este nombre a otros procesos que pueden entonces abrir este objeto GEM. Los nombres actualmente son IDs enteros de 32 bits y no tienen protección especial. Es decir, si pones un nombre en tu objeto GEM, cada otro cliente que tenga acceso al dispositivo DRM y esté autenticado vía drmAuthMagic(3) al DRM-Master actual, puede adivinar nombre y abrir o acceder al objeto GEM. Si deseas un control de acceso más detallado, puedes usar la nueva API drm-prime(7) para recuperar descriptores de archivo para manejadores GEM. Para crear un nombre para un manejador GEM, utilizas el ioctl DRM_IOCTL_GEM_FLINK. Toma como argumento una estructura de tipo struct drm_gem

_flink: 
struct drm_gem_flink {
    __u32 handle;
    __u32 name;
}
;

Tienes que poner tu manejador en el campo handle. Después de la finalización, el kernel ha puesto el nuevo nombre único en el campo name. Ahora puedes pasar este nombre a otros procesos que pueden entonces importar el nombre con el ioctl DRM_IOCTL_GEM_OPEN. Toma como argumento una estructura de tipo struct drm_ge

m_open: 
struct drm_gem_open {
    __u32 name;
    __u32 handle;
    __u32 size;
}
;

Tienes que rellenar el campo name con el nombre del objeto GEM que quieres abrir. El kernel rellenará los campos handle y size con el nuevo manejador y el tamaño del objeto GEM. Ahora puedes acceder al objeto GEM a través del manejador como si lo hubieras creado con la API

GEM.

Además de la gestión genérica de búferes, la API GEM no proporciona ningún acceso genérico. Cada controlador implementa su propia funcionalidad sobre esta API. Esto incluye búferes de ejecución, gestión de GTT, creación de contextos, acceso a CPU, E/S de GPU y más. La siguiente API de nivel superior es OpenGL. Así que si quieres usar más características de la GPU, deberías usar la biblioteca mesa3D para crear contextos OpenGL en dispositivos DRM. Esto no requiere ningún sistema de ventanas como X11, pero también puede hacerse en dispositivos DRM sin embargo, esto está fuera del alcance de esta página del manual. Puedes echar un vistazo a otras páginas del manual de mesa3D, incluyendo libgbm y libEGL. El renderizado por software 2D (renderizado con la CPU) se puede lograr con la API de búfer tonto (dumb-buffer) de forma independiente del controlador, sin embargo, para renderizado 2D o 3D acelerado por hardware debes usar OpenGL. Cualquier otra API que intente abstraer los internos del controlador para acceder a los búferes de ejecución GEM y otros internos de la GPU simplemente reinventaría OpenGL, por lo que no se proporciona. Pero si necesitas información más detallada para un controlador específico, puedes echar un vistazo a las páginas del manual del controlador, incluyendo drm-intel(7), drm-radeon(7) y drm-nouveau(7). Sin embargo, la infraestructura drm-prime(7) y la API GEM genérica descrita aquí permiten a los gestores de pantalla manejar búferes gráficos y clientes de renderizado sin ningún conocim

iento más profundo de la GPU que se utiliza. Además, permite mover objetos en
tre GPUs e implementar servidores de pantalla complejos que no hacen ningún r
enderizado por su cuenta. Consulta su página del manual para más información.

Búferes tontos

(Dumb-Buffers)

Este ejemplo muestra cómo crear un búfer tonto a través de la API DRM genérica. Esto es independiente del controlador (siempre que el controlador soporte búferes tontos) y proporciona búferes con mapeo de memoria que pueden usarse para el barrido (scanout). Este ejemplo crea un búfer de alta definición completa 1920x1080 con 32 bits por píxel y una profundidad de color de 24 bits. El búfer se vincula entonces a un framebuffer que puede usarse para el barrido con la API KMS (ver drm-kms(7))

. 
struct drm_mode_create_dumb creq;
struct drm_mode_destroy_dumb dreq;
struct drm_mode_map_dumb mreq;
uint32_t fb;
int ret;
void *map;
/* crear búfer tonto */
memset(&creq, 0, sizeof(creq));
creq.width = 1920;
creq.height = 1080;
cre
q.bpp = 32; ret = drmIoctl(fd, DRM_IOCTL_MODE_CREATE_DUMB, &creq); if (ret < 0) { /* la creación del búfer falló; ver "errno" para más códigos de error */ ... } /* creq.pitch, creq.handle y creq.size son rellenados por est
e ioctl con * los valores solicitados y pueden usarse ahora. */ /* crear objeto framebuffer para el búfer tonto */ ret = drmModeAddFB(fd, 1920, 1080, 24, 32, creq.pitch, creq.handle, &fb); if (ret) { /* la creación del framebu
ffer falló; ver "errno" */ ... } /* el framebuffer "fb" puede usarse ahora para el barrido con KMS */ /* preparar el búfer para el mapeo de memoria */ memset(&mreq, 0, sizeof(mreq)); mreq.handle = creq.handle; ret = drmIoctl(fd
, DRM_IOCTL_MODE_MAP_DUMB, &mreq); if (ret) { /* la preparación del búfer DRM falló; ver "errno" */ ... } /* mreq.offset ahora contiene el nuevo desplazamiento que puede usarse con mmap() */ /* realizar el mapeo de memoria
real */ map = mmap(0, creq.size, PROT_READ | PROT_WRITE, MAP_SHARED, fd, mreq.offset); if (map == MAP_FAILED) { /* el mapeo de memoria falló; ver "errno" */ ... } /* limpiar el framebuffer a 0 */ memset(map, 0, creq.size);
