NOMBRE

dracut.modules - módulos de dracut

DESCRIPCIÓN

dracut utiliza un sistema modular para construir y extender la imagen initramfs. Todos los módulos se encuentran en /usr/lib/dracut/modules.d o en <git-src>/modules.d. El módulo más básico de dracut es 80base. En 80base se define el script shell inicial init, que es ejecutado por el kernel después de cargar initramfs. Aunque puedes reemplazar init con tu propia versión de 80base, no se recomienda. En su lugar, deberías usar, si es posible, los hooks de dracut. Todos los hooks, y el punto en el tiempo en el que se ejecutan, se describen en FASES DEL PROCESO DE ARRANQUE.

El script principal, que crea el initramfs es dracut en sí. Parsea todos los argumentos y configura el directorio, en el que se instala todo. Luego ejecuta todos los scripts de verificación (check), instalación (install) e instalación de kernel (installkernel) encontrados en los módulos que se van a procesar. Después de que todo está instalado, el directorio de instalación se archiva y comprime a la imagen final initramfs. Todas las funciones auxiliares utilizadas por los scripts de check, install e installkernel se encuentran en el archivo dracut-functions. Estas funciones shell están disponibles para todos los scripts instaladores de módulos (install, installkernel), sin necesidad de incluir dracut-functions.

Un módulo puede verificar las precondiciones para install e installkernel con el script check. También se pueden expresar dependencias con check. Si un módulo pasó la verificación (check), se llamará a install e installkernel para instalar todos los archivos necesarios para el módulo. Para separar las partes del kernel y las no del kernel de la instalación, todas las partes relacionadas con módulos del kernel deben estar en installkernel. Todos los demás archivos encontrados en un directorio de módulo son específicos del módulo y, en su mayoría, son scripts de hook y reglas udev.

FASES DEL PROCESO DE ARRANQUE

Los módulos de dracut pueden insertar scripts personalizados en varios puntos para controlar el proceso de arranque. Estos hooks son directorios planos que contienen scripts shell que terminan en ".sh", los cuales son incluidos por init. Las funciones comúnmente utilizadas se encuentran en dracut-lib.sh, que puede ser incluida por cualquier script.

Hook: cmdline

El hook cmdline es un lugar para insertar scripts que analicen la línea de comandos del kernel y preparen las acciones posteriores, como la configuración de reglas udev y archivos de configuración.

En este hook se define la variable de entorno más importante: root. La segunda es rootok, que indica que un módulo afirmó poder analizar la raíz definida. Por ejemplo, root=iscsi:.... será reclamado por el módulo dracut iscsi, que luego establece rootok.

Hook: pre-udev

Este hook se ejecuta justo después del hook cmdline y una verificación si root y rootok fueron establecidos. Aquí los módulos pueden tomar acciones con la raíz final, y antes de que udev se haya ejecutado.

Iniciar Udev

Ahora se inicia udev y se configura el registro para udev.

Hook: pre-trigger

En este hook, puedes establecer variables de entorno de udev con udevadm control --property=KEY=valor o controlar la ejecución posterior de udev con udevadm.

Disparar Udev

udev se dispara llamando a udevadm trigger, que envía eventos de agregar para todos los dispositivos y subsistemas.

Bucle Principal

En el bucle principal de dracut, se ejecuta un bucle hasta que udev se ha estabilizado y todos los scripts en initqueue/finished han devuelto true. En este bucle hay tres hooks, donde se pueden insertar scripts llamando a /sbin/initqueue.

Initqueue

Este hook se ejecuta cada vez que se inserta un script aquí, independientemente del estado de udev.

Initqueue settled

Este hook (initqueue/settled) se ejecuta cada vez que udev se ha estabilizado.

Initqueue timeout

Este hook (initqueue/timeout) se ejecuta cuando el contador del bucle principal alcanza la mitad del contador rd.retry.

Initqueue online

Este hook (initqueue/online) se ejecuta cada vez que una interfaz de red se conecta (es decir, una vez que está activa y configurada por el módulo de red configurado).

Initqueue finished

Este hook (initqueue/finished) se llama después de que udev se ha estabilizado y si todos los scripts aquí devuelven 0, el bucle principal terminará. Se pueden agregar scripts arbitrarios aquí, para ejecutarse en el bucle initqueue hasta que ocurra algo que un módulo dracut quiera esperar.

Hook: pre-mount

Antes de montar el dispositivo raíz, se ejecutan todos los scripts en el hook pre-mount. En algunos casos (por ejemplo, NFS), el dispositivo raíz real ya está montado, sin embargo.

Hook: mount

Este hook es principalmente para montar el dispositivo raíz real.

Hook: pre-pivot

Este hook se llama antes del hook de limpieza. Este es un buen lugar para acciones distintas de las limpiezas que deben llamarse antes del pivot.

Hook: cleanup

Este hook es el último y se llama antes de que init finalmente cambie la raíz al dispositivo raíz real. Este es un buen lugar para limpiar y matar procesos que ya no son necesarios.

Limpieza y cambio de raíz

Init (o systemd) mata todos los procesos de udev, limpia el entorno, configura los argumentos para el proceso init real y finalmente llama a switch_root. switch_root elimina toda la jerarquía de archivos de initramfs, realiza un chroot al dispositivo raíz real y llama a /sbin/init con los argumentos especificados.

Para asegurar que todos los archivos en la jerarquía de initramfs puedan ser eliminados, todos los procesos que aún se ejecutan desde initramfs no deben tener ningún descriptor de archivo abierto restante.

ESCRIBIR UN MÓDULO

Un ejemplo simple de módulo es 90kernel-modules, que hace modprobe a un módulo del kernel después de que udev se ha estabilizado y los controladores básicos de dispositivos se han cargado.

Toda la información de instalación del módulo está en el archivo module-setup.sh.

Las siguientes son las variables de shell de uso más común dentro de los módulos de dracut. Estas variables de shell siempre se declaran y se les asigna un valor (el valor asignado puede ser una cadena vacía). Hay una promesa de compatibilidad en estas variables entre las versiones de dracut. Los módulos solo deben leer (y no escribir) estas variables. * $hostonly (puede ser una cadena vacía) * $hostonly_mode (puede ser una cadena vacía) * $hostonly_cmdline (no es una cadena vacía) * $moddir (no es una cadena vacía)

Primero creamos una función check(), que simplemente sale con 0, indicando que este módulo debe incluirse por defecto.

check():

return 0

Luego creamos la función install(), que instala un hook cmdline con el número de prioridad 20 llamado parse-insmodpost.sh. También instala el script insmodpost.sh en /sbin.

install():

inst_hook cmdline 20 "$moddir/parse-insmodpost.sh"
inst_simple "$moddir/insmodpost.sh" /sbin/insmodpost.sh

El archivo parse-instmodpost.sh analiza la línea de comandos del kernel en busca del argumento rd.driver.post, pone en lista negra el módulo para que no se cargue automáticamente e instala el hook insmodpost.sh en el directorio initqueue/sett

parse-insmodpost.sh:

for p in $(getargs rd.driver.post=); do
    echo "blacklist $p" >> /run/modprobe.d/initramfsblacklist.conf
    _do_insmodpost=1
done
[ -n "$_do_insmodpost" ] && /sbin/initqueue --settled --unique --onetime /sbin/insmodpost.sh
unset _do_insmodpost

insmodpost.sh, que se llama en el initqueue/settled hook simplemente ejecutará modprobe en los módulos del kernel especificados en todos los parámetros de línea de comandos del kernel rd.driver.post. Se ejecuta después de que udev se ha asentado y solo se llama una vez (--onetime).

insmodpost.sh:

. /lib/dracut-lib.sh
for p in $(getargs rd.driver.post=); do
    modprobe $p
done

module-setup.sh: check()

check() es llamada por dracut para evaluar la inclusión de un módulo de dracut en el initramfs.

$hostonly

Si la variable $hostonly está establecida, entonces la función check() del módulo debe estar en modo "hostonly", lo que significa que la check() solo debe devolver 0 si el módulo es realmente necesario para arrancar este host específico.

Evite tomar decisiones dentro de esta función basadas en el valor de la variable $hostonly_mode. Este principio asegura la inclusión de los mismos módulos de dracut tanto en modo sloppy como en modo strict.

check() debe devolver con:

0

Incluir el módulo de dracut en el initramfs.

1

No incluir el módulo de dracut. Los requisitos no se cumplen (faltan herramientas, etc.)

255

Incluir el módulo de dracut solo si otro módulo lo requiere o si se especifica explícitamente en el archivo de configuración o en la lista de argumentos.

module-setup.sh: depends()

La función depends() debe imprimir (echo) todos los nombres de otros módulos de dracut de los que el módulo depende.

module-setup.sh: cmdline()

Esta función debe imprimir las opciones de la línea de comandos del kernel necesarias para arrancar la configuración actual de la máquina. Debe empezar con un espacio y no debe imprimir un salto de línea.

module-setup.sh: install()

La función install() se llama para instalar todo lo que no esté relacionado con el kernel. Para instalar binarios, scripts y otros archivos, puede usar las funciones mencionadas en [creation].

Para referirse a un archivo en el directorio del módulo actual, use la variable "$moddir".

module-setup.sh: installkernel()

En installkernel() se deben instalar todos los archivos relacionados con el kernel. Puede usar todas las funciones mencionadas en [creation] para instalar archivos.

Funciones de Creación

inst_dir <dir>

instala un directorio <dir> (pero no su contenido) en el mismo lugar en la imagen del initramfs.

inst [-H] <src> [<dst>]

inst_binary <src> [<dst>]

inst_script <src> [<dst>]

instala un archivo <src> ya sea en el mismo lugar en el initramfs o en un <dst> opcional, y también sus dependencias y archivo .hmac (si existe). inst con más de dos argumentos se trata igual que inst_multiple, todos los argumentos se tratan como archivos a instalar y ninguno como destinos de instalación.

opciones:

-H

registra todos los archivos instalados en /lib/dracut/hostonly-files, de modo que puedan eliminarse si rd.hostonly se pasa en la línea de comandos del kernel.

inst_simple [-H] <src> [<dst>]

instala un archivo <src> ya sea en el mismo lugar en el initramfs o en un <dst> opcional, pero sin instalar sus dependencias o archivo .hmac.

opciones:

-H

registra todos los archivos instalados en /lib/dracut/hostonly-files, de modo que puedan eliminarse si rd.hostonly se pasa en la línea de comandos del kernel.

inst_multiple [-H] [-o] <file> [ <file> ...]

instala múltiples binarios y archivos. Si se especifican ejecutables sin una ruta, dracut buscará en la ruta PATH=/usr/sbin:/sbin:/usr/bin:/bin el binario.

opciones:

-H

registra todos los archivos instalados en /lib/dracut/hostonly-files, de modo que puedan eliminarse si rd.hostonly se pasa en la línea de comandos del kernel.

-o

opcional, un archivo faltante no provoca un error.

inst_hook <hookdir> <prio> <src>

instala un ejecutable/script <src> en el hook de dracut <hookdir> con la prioridad <prio>.

inst_rules <udevrule> [ <udevrule> ...]

instala una o más reglas de udev. Las reglas de udev inexistentes se reportan, pero no hacen fallar a dracut.

inst_libdir_dir <dir> [<dir>...]

instala múltiples directorios (pero no su contenido) ubicados en un directorio de bibliotecas en la imagen del initramfs.

inst_libdir_file [-n <pattern>] [-o] <file> [<file>...]

instala múltiples archivos ubicados en un directorio de bibliotecas en la imagen del initramfs.

opciones:

-n <pattern>

instala todos los archivos de biblioteca que coincidan con un patrón.

-o

opcional, una biblioteca faltante no provoca un error.

instmods [-c] [-s] <kernelmodule> [ <kernelmodule> ... ]

instmods debe usarse solo en la función installkernel().

instmods instala uno o más módulos del kernel en el initramfs. <kernelmodule> también puede ser un subsistema completo, si se le antepone un "=", como "=drivers/net/team".

instmods no instalará el módulo del kernel si $hostonly está establecido y el módulo del kernel no es actualmente necesario por ningún /sys/.../uevent MODALIAS. Para instalar un módulo del kernel independientemente del modo hostonly use la forma:

hostonly='' instmods <kernelmodule>

un patrón común para llamar a instmods es usar la siguiente forma:

`hostonly=$(optional_hostonly) instmods <kernelmodule>`

Esta sentencia instala el módulo del kernel en cualquiera de las siguientes condiciones: * en modo no-hostonly (independientemente del estado del host) * en modo hostonly sloppy (independientemente del estado del host) * en modo hostonly si el módulo del kernel ya está cargado en el host

opciones:

-c

comprueba que los módulos del kernel existan y puedan instalarse (es decir, no son opcionales).

-s

reduce la verbosidad.
