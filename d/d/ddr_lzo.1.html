Acerca

de

LZO es un algoritmo que comprime/descomprime datos. Está optimizado para la velocidad (especialmente la velocidad de descompresión) y hasta cierto punto sacrifica el tamaño del archivo comprimido por ello. Sin embargo, existen variantes con compresión lenta (aunque aún muy rápida descompresión) disponibles. Vea el parámetro algoritmo más

abajo.

Este plugin ha sido escrito para dd_rescue y utiliza la interfaz de plugins del mismo. Vea la página man dd_rescue(1) para más información sobre dd

_re
scu
e.

OPCIONE

S

Las opciones se pasan utilizando la sintaxis de paso de opciones de dd_rescue: El nombre del plugin (lzo) va seguido opcionalmente de un signo igual (=) y las opciones se separan mediante dos puntos (:). El plugin lzo también permite que la mayoría de las opciones se abrevien a cinco o seis letras. Vea la sección EJEMPLOS más

abajo.

Compresión o

descompresión

El plugin lzo de dd_rescue (al que se hará referencia posteriormente simplemente como ddr_lzo, lo que refleja las partes variables del nombre de archivo libddr_lzo.so) elige automáticamente el modo de compresión o descompresión si uno de los archivos de entrada/salida tiene el sufijo .lzo; de lo contrario, puede especificar los parámetros compr[ess] o decom[press] en la línea de comandos.
El parámetro opt[imize] indicará a ddr_lzo que realice una pasada de optimización después de la compresión. Esto podría acelerar la descompresión en unos pocos por ciento al crear datos comprimidos con niveles de compresión altos y tamaños de bloque

grandes.

El plugin también admite el parámetro bench[mark]; si se especifica, emitirá información sobre el uso de la CPU y el ancho de banda resultante de compresión o descompresión. (Para archivos p

equeños, los números carecen de sentido debido al jitter y la resolución tem
poral limitada — ddr_lzo omitirá la salida si los números son muy pequeños.)

Algoritmo de compresión/descompresió

n

El plugin lzo admite varios de los algoritmos de (des)compresión de liblzo2. Puede especificar cuál desea usar pasando algo=XXX, donde XXX puede ser lzo1x_1, lzo1x_1_15, lzo1x_999, lzo1x_1_11, lzo1x_1_12, lzo1y_1, lzo1y_999, lzo1f_1, lzo1f_999, lzo1b_1 ... lzo1b_9, lzo1b_99, lzo1b_999, lzo2a_999. Pase algo=help para obtener una lista de los algoritmos disponibles. Consulte la documentación de liblzo para más información sobre los algoritmos. Tenga en cuenta que solo los tres primeros son soportados por lzop (aunque puede descomprimir los cinco primeros, ya que todos son manejados por la misma rutina de descompresión).
El valor por defecto (lzo1x_1) es una buena elección para una compresión rápida y descompresión muy rápida, y asegura la compatibilidad con lzop. Para una mayor compresión, podría querer elegir lzo1x_999, que es muy l

ento pero compatible con lzop, o lzo2a_999, que es el doble de rápido, pero no compatible con lzop. Tenga en cuenta que es mejor usar otros algoritmos de compresión (por ejemplo, lzma con un ajuste bajo) si le interes
a una buena compresión, por lo que rara vez hay una razón para cambiar el algoritmo por defecto, ya que solo puede obtener ganancias marginales a cambio de un consumo significativamente mayor de CPU y memoria con LZO.

Depuració

n

La bandera debug hará que ddr_lzo emita información sobre bloques y otros datos internos. Está destinado a fines de

depuración.

Finalmente, también existe un parámetro flags=XXXX. Este establece el campo de banderas en la cabecera (el valor por defecto es 0x03000403) y se usa solo para pruebas. No se verifica su validez y puede establecer

fácilmente valores que rompan la descompresión o hagan que ddr_lzo aborte. Úselo realme
nte solo para fines de desarrollo cuando conozca el significado de los distintos bits.

Recuperación de

errores

Durante la compresión, cuando no se pueden leer los bytes de entrada, ddr_lzo codificará huecos en el archivo de salida comprimido — estos se omitirán durante la

descompresión.

Durante la descompresión, los bloques erróneos pueden ser detectados por las sumas de verificación (la mayoría de las veces) o por el descompresor. El plugin lzo intenta continuar en ese caso si la cabecera del bloque que especifica las longitudes de compresión/descompresión está intacta. Esto resultará en que un bloque sea omitido (hueco) y la descompresión continuará con el siguiente bloque. Esto evita que datos corruptos terminen en el archivo de salida (o que datos preexistentes, potencialmente buenos, sean sobrescritos).
El comportamiento puede modificarse especificando la opción nodisc[ard]. Cuando se indica, la salida del descompresor (rellenada con ceros si es demasiado corta para el bloque) se escribirá en el archivo de salida. Incluso si sabemos que los datos son incorrectos, con algo de suerte, partes del bloque pueden ser realmente

válidas.

Cuando las cabeceras de los bloques están corruptas, la situación es desesperada, ya que habrá perdido el resto del archivo. Para recuperar piezas después de una corrupción de cabecera de bloque como esta, ddr_lzo admite la opción search. Con ella, el plugin buscará en el archivo de entrada (a partir de la posición dada en dd_rescue con -s) datos que parezcan una cabec

era de bloque y, si se encuentra una cabecera que parece válida, comenz
ará a descomprimir desde esa posición. (Si no puede encontrar los dato
s que busca, podría estudiar la salida generada con la bandera debug.)

Características de dd_rescue

soportadas

dd_rescue soporta añadir datos a archivos con la opción -x/--extend. Si ddr_lzo está cargado y el archivo de salida es un archivo .lzo existente, los nuevos datos se añadirán en el formato especificado por la cabecera LZOP existente. Si la cabecera no indica un archivo multiparte (archivo), la marca EOF será sobrescrita, de modo que se crea un archivo .lzo válido. De lo contrario, se añadirá una nueva

parte.

Cuando dd_rescue no puede leer datos o se encuentra una cantidad considerable de datos rellenos de ceros y la opción -a/--sparse está activa, dd_rescue creará archivos dispersos (archivos con huecos en su interior). Esta es una optimización para ahorrar espacio — los huecos se interpretan como ceros de nuevo en lecturas normales, por lo que esto es transparente. Los huecos también pueden ser útiles para asegurar que los buenos datos no sean sobrescritos con ceros cuando no se pudieron leer los datos.
Cuando el módulo lzo recibe huecos en modo compresión, los codificará en el archivo de salida comprimido de una manera especial (usando la fu

nción de multiparte de lzop, ya que lzop, desafortunadamente, falla con bloques con longitud comprimida 0). Durante la descompresión, los huec
os resultarán en que los datos se salten de nuevo (creando un hueco en el archivo de salida, si no hay datos preexistentes en esa ubicación).

Compatibilidad con

lzop

El plugin usa el algoritmo lzo1x_1 por defecto (igual que lzop por defecto) y genera sumas de verificación adler32 para permitir la detección de corrupción de datos. Los archivos comprimidos son compatibles con lzop y ddr_lzo debería manejar archivos generados por lzop.
Los archivos multiparte (archivo) de lzop se descomprimen en UN archivo de salida en el orden en que están almacenados.
Los archivos multiparte creados por el plugin lzo para codificar huecos serán extraídos en varios archivos desde lzop. Los huecos están codificados en los nombres de archivo (con un número de secuencia y el tamaño del hueco hasta 1TB; use la marca de tiempo para huecos enormes), por lo que un ensamblaje adecuado de los fragmentos es posible incluso sin

ddr_lzo.

lzop solo soporta la familia de algoritmos lzo1x_. Si elige otro algoritmo para comprimir datos con ddr_lzo, establecerá el campo needed_version_to_extract en el archivo lzop resultante a la versión propia de ddr_lzo (1.789) para indicar la incompatibilidad con lzop (a partir de la versión 1.03).
lzop usa por defecto tamaños de bloque de 256kiB (en sistemas Unix), pero también soporta compresión/descompresión con tamaños de bloque más pequeños. Necesita ser recompilado para soportar tamaños de bloque hasta un máximo posible de 64MiB. Por lo tanto, se recomienda permanecer por debajo o en 256kiB; incluso cuando la compatibilidad con lzop no es una preocupación, no se recomiendan bloques mayores de 16MiB, vea más

abajo.

BUGS/LIMITACIONES

Madurez

El plugin es nuevo a partir de dd_rescue 1.43. No confíes todavía en los datos guardados con ddr_lzo como única copia de seguridad para datos valiosos. Espera también algunos cambios en ddr_lzo en un futuro no muy lejano. (Esto no debería romper el formato de archivo, ya que seguimos a lzop....)
Los datos comprimidos son más sensibles a la corrupción de datos que los datos en texto plano. Ten en cuenta que las sumas de verificación (adler32 o crc32) en el formato de archivo lzop NO permiten corregir errores; solo permiten una detección de corrupción de datos algo fiable. (Idealmente, una suma de verificación de 32 bits falla 1 de cada 2^32 corrupciones; en cambios pequeños, crc32 se acerca un poco más al ideal que adler32. Puedes pasar la opción crc32 para usar crc32 en lugar de sumas de verificación adler32 a costa de algo de velocidad; lamentablemente, el polinomio crc32 para lzop/gzip/... no es el polinomio crc32c que tiene soporte de hardware en muchas CPUs hoy en día.) Ten en cuenta también que las sumas de verificación NO son hashes criptográficos; un atacante malicioso puede encontrar fácilmente modificaciones de datos que no alteren las sumas de verificación. Usa MD5 o mejor SHA-256/SHA-512 para garantizar la integridad contra atacantes. Usa par2 o software similar para crear códigos de corrección de errores (Reed-Solomon / Códigos de Borrado) si quieres poder recuperar datos frente a la corrupción.

Seguridad

Aunque se ha tenido cuidado al verificar el resultado de las asignaciones de memoria..., el código del descompresor no ha sido auditado y solo se ha aplicado fuzzing limitado para garantizar que no sea vulnerable a datos maliciosos; ten cuidado al procesar datos de fuentes no confiables.

EJEMPLOS

dd_rescue -ptAL lzo=algo=lzo1x_1_15:compress,hash=alg=sha256 infile outfile
comprime datos de infile en outfile usando el algoritmo lzo1x_1_15 y calcula el valor hash sha256 de outfile. outfile tendrá la marca de tiempo y los derechos de acceso copiados de infile y se vaciará antes (si el archivo existe). El archivo de salida no tendrá agujeros codificados; los errores en infile resultarán en ceros.
dd_rescue -aL MD5,lzo=compr:bench,MD5,lzo=decompress,MD5 infile infile2
copiará infile a infile2 comprimiendo los datos y descomprimiéndolos de nuevo sobre la marcha. Mostrará hashes MD5 para los datos comprimidos también (aunque no se almacenan) y para los dos infiles -- la salida debería ser idéntica, obviamente. Este comando es bastante artificial, se usa para probar. La bandera -a hace que dd_rescue detecte bloques de ceros y cree agujeros, probando así la codificación de agujeros (archivos dispersos) y la decodificación también si el infile tiene regiones de tamaño considerable llenas de ceros.
dd_rescue -s1M -S0 -L lzo=search,nodiscard infile.lzo outfile
buscará una cabecera de bloque lzop en infile.lzo a partir de la posición de 1MiB en el archivo y descomprimirá el resto del archivo. Al encontrar bloques corruptos, seguirá escribiendo la salida del descompresor en outfile.
