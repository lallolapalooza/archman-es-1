--installroot=<ruta>
Especifica una raíz de instalación alternativa, relativa a donde se instalarán todos los paquetes. Piense en esto como hacer chroot <raíz> dnf, excepto que usar --installroot permite a dnf trabajar antes de que el chroot sea creado. Requiere una ruta absoluta.
  • cachedir, archivos de registro, releasevery gpgkey se toman de o se almacenan en la raíz de instalación. Las claves GPG se importan a la raíz de instalación desde una ruta relativa al host que puede especificarse en la sección de repositorio de los archivos de configuración.
  • archivo de configuración y reposdir <#reposdir-label> se buscan primero dentro de la raíz de instalación. Si no están presentes, se toman del sistema host. Nota: Cuando se especifica una ruta dentro de un argumento de línea de comandos (--config=<archivo de configuración> en el caso de archivo de configuración y --setopt=reposdir=<reposdir> para reposdir), entonces esta ruta siempre es relativa al host sin excepciones.
  • vars se toman del sistema host o de la raíz de instalación de acuerdo con reposdir <#reposdir-label> . Cuando reposdir se especifica la ruta dentro de un argumento de línea de comandos, vars se toman de la raíz de instalación. Cuando se especifican las rutas de varsdir <#varsdir-options-label> dentro de un argumento de línea de comandos (--setopt=varsdir=<reposdir>), entonces esas rutas siempre son relativas al host sin excepciones.
  • El pluginpath y pluginconfpath son relativos al host.
Nota: Es posible que también desee usar la opción de línea de comandos --releasever=<versión> al crear la raíz de instalación, de lo contrario el valor de $releasever se toma de la rpmdb dentro de la raíz de instalación (y por lo tanto está vacío en el momento de la creación y la transacción fallará). Si --releasever=/ se usa, releasever se detectará desde el sistema host (/). La nueva ruta de la raíz de instalación en el momento de la creación no contiene los archivos repository, releasever y dnf.conf .

En un sistema modular, es posible que también desee usar la opción de línea de comandos --setopt=module_platform_id=<module_platform_name:stream> al crear la raíz de instalación, de lo contrario el valor de module_platform_id <#module-platform-id-label> se tomará del archivo /etc/os-release dentro de la raíz de instalación (y por lo tanto estará vacío en el momento de la creación, la dependencia modular podría no estar satisfecha y el contenido de los módulos podría excluirse).

Comando Install

Comando: install
Alias: in
Alias para coincidencia NEVRA explícita: install-n, install-na, install-nevra
Alias obsoletos: localinstall
dnf [options] install <spec>...
Se asegura de que los paquetes dados y sus dependencias estén instalados en el sistema. Cada <spec> puede ser un <package-spec>, o un @<module-spec>, o un @<group-spec>. Véase Ejemplos de Install. Si un paquete o proveedor dado no puede ser (y no está ya) instalado, el código de salida será distinto de cero. Si la <spec> coincide tanto con un @<module-spec> como con un @<group-spec>, solo se instala el módulo.

Cuando se da un <package-spec> para especificar la versión exacta del paquete, DNF instalará la versión deseada, sin importar qué versión del paquete esté ya instalada. La versión anterior del paquete será eliminada en el caso de un paquete que no sea solo de instalación.

Por otro lado, si el <package-spec> especifica solo un nombre, DNF también tiene en cuenta los paquetes que lo obsoletan al elegir qué paquete instalar. Este comportamiento es específico del comando install. Nótese que esto puede llevar a resultados aparentemente inesperados si un paquete tiene múltiples versiones y alguna versión más antigua está siendo obsoleta. Crea una división en la ruta de actualización y ambas formas se consideran correctas, el paquete resultante se elige simplemente por orden lexicográfico.

Hay también algunos comandos de instalación específicos install-n, install-na y install-nevra que permiten la especificación de un argumento exacto en el formato NEVRA. Como consecuencia, la <spec> no se hará coincidir con provides y file provides.

Véase también Política de Reemplazo de Archivos de Configuración.

dnf install tito

dnf install tito-0.5.6-1.fc22
Instala el paquete con una versión específica. Si el paquete ya está instalado, intentará automáticamente degradar o actualizar a la versión específica.
dnf --best install tito
Instala la última versión disponible del paquete. Si el paquete ya está instalado, intentará automáticamente actualizar a la última versión. Si la última versión del paquete no puede ser instalada, la instalación fallará.
dnf install vim
DNF reconocerá automáticamente que vim no es un nombre de paquete, pero buscará e instalará un paquete que proporcione vim con todas las dependencias requeridas. Nota: La coincidencia por nombre de paquete tiene prioridad sobre la coincidencia por provides de paquete.

dnf install '@Web Server'
Instala el grupo ambiental 'Web Server'.
dnf install /usr/bin/rpmsign
Instala un paquete que proporcione el archivo /usr/bin/rpmsign.
dnf -y install tito --setopt=install_weak_deps=False

ESPECIFICACIÓN DE PAQUETES

Muchos comandos toman un <package-spec> parámetro que selecciona un paquete para la operación. El <package-spec> argumento se compara con los NEVRAs de los paquetes, las provides y las file provides.

<package-file-spec> es similar a <package-spec>, excepto que no se realiza la coincidencia con las provides. Por lo tanto, <package-file-spec> se compara solo con los NEVRAs y las file provides.

<package-name-spec> se compara solo con los NEVRAs.

Comodines

La especificación de paquetes admite el mismo reconocimiento de patrones de comodines que el shell, en los tres paquetes mencionados anteriormente se compara con (NEVRAs, provides y file provides).

Se admiten los siguientes patrones:

*
Coincide con cualquier número de caracteres.
?
Coincide con cualquier carácter único.
[]
Coincide con cualquiera de los caracteres incluidos. Un par de caracteres separados por un guion denota una expresión de rango; se coincide con cualquier carácter que esté entre esos dos caracteres, inclusive. Si el primer carácter después del [ es un ! o un ^ , entonces se coincide con cualquier carácter no incluido.

Nota: No se admiten las llaves ({}). Aún puede usarlas en shells que las admitan y dejar que el shell haga la expansión, pero si están entrecomilladas o escapadas, dnf no las expandirá.

Coincidencia de NEVRA

Al comparar con los NEVRAs, se admite la coincidencia parcial. DNF intenta coincidir la especificación con la siguiente lista de formas de NEVRA (en orden decreciente de prioridad):

  • name-[epoch:]version-release.arch
  • name.arch
  • name
  • name-[epoch:]version-release
  • name-[epoch:]version

Tenga en cuenta que name puede contener guiones en general (por ejemplo, package-with-dashes).

Se usa la primera forma que coincida con cualquier paquete y no se prueban las formas restantes. Si ninguna de las formas coincide con ningún paquete, se intenta coincidir el <package-spec> con los NEVRAs completos de los paquetes. Esto solo es relevante si hay comodines en el <package-spec>.

<package-spec> coincide con los NEVRAs de la misma manera que <package-name-spec> , pero en caso de que falle la coincidencia con los NEVRAs, intenta coincidir también con las provides y file provides de los paquetes.

Puede especificar comodines como parte de cualquiera de los cinco componentes del NEVRA. También puede especificar un patrón de comodín para que coincida con múltiples componentes del NEVRA (en otras palabras, para que coincida a través de los separadores del NEVRA). En ese caso, sin embargo, debe escribir la especificación para que coincida con los NEVRAs completos del paquete, ya que no es posible dividir dicha especificación en formas de NEVRA.

Especificación explícita de la coincidencia de NEVRA

Algunos comandos (autoremove, install, remove y repoquery) también tienen alias con los sufijos -n, -na y -nevra que permiten especificar explícitamente cómo analizar los argumentos:

  • Comando install-n solo coincide con name.
  • Comando install-na solo coincide con name.arch.
  • Comando install-nevra solo coincide con name-[epoch:]version-release.arch.

ESPECIFICACIÓN DE PROVIDES

<provide-spec> en las descripciones de los comandos significa que el comando opera sobre paquetes que proporcionan la especificación dada. Esto puede ser una provide explícita, una provide implícita (es decir, el nombre del paquete) o una file provide. La selección distingue mayúsculas de minúsculas y se admite el uso de comodines.

Especificación de file provides

Si una especificación comienza con / o */, se considera una posible file provide.

ESPECIFICACIÓN DE GRUPOS

<group-spec> permite seleccionar los grupos (de entorno) sobre los que debe trabajar una operación particular. Es una cadena que no distingue mayúsculas de minúsculas (y que admite caracteres de comodín) que se compara con el ID del grupo, el nombre canónico y el nombre traducido al locale LC_MESSAGES actual (si es posible).

ESPECIFICACIÓN DE MÓDULOS

<module-spec> permite seleccionar los módulos o perfiles sobre los que debe trabajar una operación particular.

Tiene la forma de NAME:STREAM:VERSION:CONTEXT:ARCH/PROFILE y las formas parciales admitidas son las siguientes:

  • NOMBRE
  • NOMBRE:STREAM
  • NOMBRE:STREAM:VERSION
  • NOMBRE:STREAM:VERSION:CONTEXTO
  • todas las combinaciones anteriores con ::ARCH (por ejemplo, NOMBRE::ARCH)
  • NOMBRE:STREAM:VERSION:CONTEXTO:ARCH
  • todas las combinaciones anteriores con /PERFIL (por ejemplo, NOMBRE/PERFIL)

En caso de que no se especifique el stream, se utiliza el stream habilitado o el predeterminado, en ese orden. En caso de que no se especifique el perfil, se utiliza el perfil predeterminado del sistema o el perfil 'default'.

ESPECIFICACIÓN DE TRANSACCIONES

<especificación-de-transacción> puede tener varias formas. Si es un número entero, especifica un ID de transacción. Especificar last es lo mismo que especificar el ID de la transacción más reciente. La última forma es last-<desplazamiento>, donde <desplazamiento> es un número entero positivo. Especifica la transacción que precede en desplazamiento-th a la más reciente.

FILTRADO DE PAQUETES

El filtrado de paquetes filtra paquetes del conjunto de paquetes disponibles, haciéndolos invisibles para la mayoría de los comandos de dnf. No pueden usarse en una transacción. Los paquetes pueden filtrarse mediante el Filtrado de Exclusión o el Filtrado Modular.

Filtrado de Exclusión

El Filtrado de Exclusión es un mecanismo utilizado por un usuario o por un plugin de DNF para modificar el conjunto de paquetes disponibles. El Filtrado de Exclusión puede modificarse mediante las opciones de configuración includepkgs <#include-label> o excludepkgs <#exclude-label> en los archivos de configuración <#conf-ref-label>. La opción de línea de comandos --disableexcludes puede usarse para anular las exclusiones de los archivos de configuración. Además de las exclusiones configuradas por el usuario, los plugins también pueden ampliar el conjunto de paquetes excluidos. Para desactivar las exclusiones de un plugin de DNF, puede usar la opción de línea de comandos --disableplugin.

Para desactivar todas las exclusiones, por ejemplo, para el comando install, puede usar la siguiente combinación de opciones de línea de comandos:

dnf --disableexcludes=all --disableplugin="*" install bash

Filtrado Modular

Consulte la documentación de modularidad <#modularity-label> para obtener detalles sobre cómo funciona el Filtrado Modular.

Con la modularidad, solo se incluyen en el conjunto de paquetes disponibles los paquetes RPM de streams de módulos activos. Los paquetes RPM de streams de módulos inactivos, así como los paquetes no modulares con el mismo nombre o provides que un paquete de un stream de módulo activo, se filtran. El filtrado modular no se aplica a los paquetes agregados desde la línea de comandos, paquetes instalados o paquetes de repositorios con module_hotfixes=true en su archivo .repo .

No se recomienda desactivar el filtrado modular, ya que podría causar que el sistema entre en un estado defectuoso. Para desactivar el filtrado modular para un repositorio en particular, especifique module_hotfixes=true en el archivo .repo o use --setopt=<repo_id>.module_hotfixes=true.

Para descubrir el módulo que contiene un paquete excluido, use dnf module provides.

SINCRONIZACIÓN DE METADATOS

El funcionamiento correcto de DNF depende de tener acceso a datos actualizados de todos los repositorios habilitados, pero contactar con los mirrors remotos en cada operación lo ralentiza considerablemente y consume ancho de banda tanto para el cliente como para el proveedor del repositorio. La opción de configuración del repositorio metadata_expire <#metadata-expire-label> (véase dnf.conf(5)) es utilizada por DNF para determinar si una copia local particular de los datos del repositorio debe volver a sincronizarse. Es crucial que los proveedores de repositorios establezcan la opción adecuadamente, es decir, a un valor donde se garantice que si los metadatos particulares estaban disponibles a tiempo T en el servidor, entonces todos los paquetes a los que hace referencia seguirán estando disponibles para su descarga desde el servidor a tiempo T + metadata_expire.

Para reducir aún más la carga de ancho de banda, algunos de los comandos donde tener metadatos actualizados no es crítico (por ejemplo, el comando list ) no comprueban si un repositorio ha caducado y siempre que cualquier versión de él esté disponible localmente para la cuenta del usuario, se utilizará. Para el uso sin privilegios de root, véase también el interruptor --cacheonly . Tenga en cuenta que en todas las situaciones el usuario puede forzar la sincronización de todos los repositorios habilitados con el interruptor --refresh .

POLÍTICA DE REEMPLAZO DE ARCHIVOS DE CONFIGURACIÓN

Los paquetes actualizados podrían reemplazar los archivos de configuración antiguos modificados con los nuevos o conservar los archivos más antiguos. Ninguno de los archivos se reemplaza realmente. A los conflictivos, RPM les añade un sufijo adicional al nombre de origen. Qué archivo debe mantener el nombre verdadero después de la transacción no lo controla el gestor de paquetes, sino que lo especifica cada paquete en sí, siguiendo la guía de empaquetado.
