DESCRIPCIÓN

La función val_resolve_and_check() consulta un conjunto de servidores de nombres para la tupla <nombre_dominio, tipo, clase> y verifica y valida la respuesta. La verificación implica la comprobación de los RRSIGs, y la validación es la verificación de una cadena de autenticación desde un ancla de confianza configurada.

El parámetro flags se puede utilizar para controlar los resultados de la validación. Los siguientes valores, que se pueden combinar mediante OR, están definidos actualmente para este campo:

VAL_QUERY_DONT_VALIDATE
Esta bandera hace que el validador desactive la validación para esta consulta.
VAL_QUERY_IGNORE_SKEW
Esta bandera hace que el validador desactive la comprobación de los tiempos de inicio y expiración de las firmas en los RRSIGs.
VAL_QUERY_AC_DETAIL
Esta bandera hace que el validador copie los detalles de la cadena de autenticación en el miembro val_rc_answer dentro de la estructura val_result_chain devuelta.
VAL_QUERY_ASYNC
Esta bandera habilita la resolución asíncrona de consultas para esa búsqueda.
VAL_QUERY_NO_DLV
Esta bandera hace que el validador desactive el procesamiento de DLV para esta consulta. Esto solo está disponible si la biblioteca libval(3) ha sido compilada con soporte DLV.
VAL_QUERY_NO_EDNS0_FALLBACK
Al consultar varios servidores de nombres, libsres(3) también intentará varios tamaños de EDNS0, terminando con una consulta que tiene EDNS0 deshabilitado (es decir, sin el bit CD establecido). Esta bandera hace que libval deshabilite la reversión de EDNS0 para la consulta.
VAL_QUERY_ITERATE
Esta bandera fuerza a libval a buscar iterativamente la consulta consultando varios servidores de nombres en la jerarquía de delegación, en lugar de solicitar esta información a cualquier servidor de nombres en caché que pueda estar configurado en dnsval.conf.
VAL_QUERY_SKIP_RESOLVER
Esta bandera fuerza a libval a solo mirar su caché mientras intenta resolver un nombre.
VAL_QUERY_SKIP_CACHE
Hay dos niveles de almacenamiento en caché que ocurren dentro de libval: a nivel de aserción y a nivel de respuesta. Esta bandera fuerza a libval a ignorar los datos en ambas cachés mientras intenta resolver un nombre.
VAL_QUERY_SKIP_ANS_CACHE
Hay dos niveles de almacenamiento en caché que ocurren dentro de libval: a nivel de aserción y a nivel de respuesta. Esta bandera fuerza a libval a ignorar los datos en la caché de respuestas mientras intenta resolver un nombre. Si ya existe una aserción para el nombre, clase y tipo dados, esa aserción se reutiliza hasta que expire. Una vez que expira, el nombre se busca a través de una consulta, incluso si un registro más reciente (obtenido por otra aserción en el mismo o diferente contexto) está disponible en su caché de respuestas.

El primer parámetro de val_resolve_and_check() es el contexto del validador. Las aplicaciones pueden crear un nuevo contexto de validador usando la función val_create_context(). Esta función analiza los archivos de configuración del resolvedor y del validador y crea el manejador newcontext para esta información analizada. La información almacenada como parte del contexto del validador incluye la política de validación y la política del resolvedor.

Las políticas del validador y del resolvedor se leen de los archivos /etc/dnsval.conf y /etc/resolv.conf por defecto. /etc/root.hints proporciona información de arranque para el validador cuando funciona como un resolvedor completo (ver dnsval.conf(3)). Estos valores por defecto pueden ser diferentes si se especificó algún otro valor en el momento de la configuración de la biblioteca. Si no se encuentra el archivo de configuración del resolvedor por defecto en la ubicación especificada, libval también intentará recurrir a /etc/resolv.conf como último recurso.

Las aplicaciones también pueden crear un contexto de validador con una política personalizada utilizando la función val_create_context_ex().

El argumento opt en val_create_context_ex() apunta a la siguiente estructura:

typedef struct val_context_opt {
    unsigned int vc_qflags;
    unsigned int vc_polflags;
    char *vc_valpol;
    char *vc_nslist;
    char *vc_val_conf;
    char *vc_res_conf;
    char *vc_root_conf;
    val_global_opt_t *gopt, 
} val_context_opt_t;

vc_qflags especifica las banderas de consulta por defecto para las consultas asociadas con el contexto. Este campo es idéntico al argumento flags en la función val_resolve_and_check().

Los campos vc_val_conf, vc_res_conf y vc_root_conf se pueden utilizar para especificar archivos de configuración alternativos en lugar de los archivos por defecto utilizados para la información de configuración del validador, el resolvedor y las pistas raíz.

El campo vc_valpol se puede utilizar para proporcionar un "fragmento" de configuración personalizada del validador al validador. El validador analiza esta información y la aplica a la configuración del validador por defecto, ya sea como una extensión o como una anulación, según se especifica en el campo vc_polflags. El campo vc_nslist, de manera similar, se puede utilizar para proporcionar una lista personalizada de servidores de nombres recursivos a los que enviar consultas, además de (o en lugar de) la lista de servidores de nombres especificada en el archivo resolv.conf. La lista de servidores de nombres en vc_res_conf debe especificarse como una lista de direcciones IP o IPv6 separadas por espacios en blanco.

Se puede crear una asignación personalizada entre una zona y un servidor de nombres utilizando la función val_context_store_ns_for_zone().

vc_polflags se puede configurar con los siguientes valores:

CTX_DYN_POL_VAL_OVR
Cuando esta bandera está establecida, solo se utiliza la configuración del validador especificada en el campo vc_valpol para la configuración del validador. Las opciones especificadas en el archivo dnsval.conf se ignoran.
CTX_DYN_POL_RES_OVR
Cuando esta bandera está establecida, solo se utiliza la lista de servidores de nombres especificada en el campo vc_nslist para la configuración del resolvedor. Las opciones especificadas en el archivo resolv.conf se ignoran.

La función val_context_setqflags() permite modificar las banderas de consulta de un contexto de validador existente. La bandera action puede ser VAL_SET_FLAGS, VAL_ADD_FLAGS o VAL_REMOVE_FLAGS, que establece, añade o elimina respectivamente las banderas especificadas en flags.

Las funciones val_istrusted(), val_isvalidated() y val_does_not_exist() se utilizan para interpretar el valor de estado devuelto por val_resolve_and_check().

La función val_free_context() libera la memoria asociada con un contexto de validador, y la función val_free_result_chain() libera la memoria asociada con una cadena de resultados de validación.

Las funciones p_val_status(), p_ac_status() y p_val_error() proporcionan representaciones en cadena legibles de los códigos de estado de validación, los códigos de estado de la cadena de autenticación y los códigos de error del sistema, respectivamente.

La función val_log_add_optarg() añade opciones para el sistema de registro de libval. La cadena args se analiza para determinar la verbosidad y la ubicación de la salida del registro. Si use_stderr es distinto de cero, la salida se enviará a stderr.

VALOR DE RETORNO

Todas las funciones que devuelven un entero devuelven 0 en caso de éxito, y un valor distinto de cero que indica un código de error en caso de fallo. Las funciones que devuelven punteros devuelven NULL en caso de fallo.

/etc/dnsval.conf, /etc/resolv.conf, /etc/root.hints

NAME

val_context_setpolicy — set policy

SYNOPSIS

#include <libval.h>

typedef struct val_policy_flags {
    uint32_t                    vpf_flags;
} val_policy_flags_t;

int
val_context_setpolicy(val_context_t *ctx, val_policy_flags_t *policy);

DESCRIPTION

The validation context is configured using the policy argument. This argument is a pointer to a structure containing flags that are used to control the behavior of the DNSSEC validator.

The following flags are recognized:

CTX_DYN_POL_RES_OVR
When this flag is set only the name servers specified in the vc_nslist field is used for the resolver configuration. Options specified in the resolv.conf file are ignored.
CTX_DYN_POL_GLO_OVR
When this flag is set only the global options set in gopt field are used. Global options specified in the dnsval.conf file are ignored.
CTX_DYN_POL_RES_NRD
When this flag is set outgoing queries have the Recursion Desired (RD) bit set to 0. This is useful if queries need to be sent to an authoritative-only name server.

The gopt field points to the following structure:

typedef struct val_global_opt {
    int local_is_trusted;
    long edns0_size;
    int env_policy;
    int app_policy;
    char *log_target;
    int closest_ta_only;
    int rec_fallback;
    long max_refresh;
    int proto;
} val_global_opt_t;

Setting a value of 1 for local_is_trusted is equivalent to specifying the trust-oob-answers option in the dnsval.conf file to yes. Similarly, setting the closest_ta_only and rec_fallback members to 1 is equivalent to setting the closest-ta-only and rec-fallback options to yes in the dnsval.conf file. A value of 0 is equivalent to the no setting for these option.

Setting the edns0_size member to a particular value has the same effect setting the edns0-size option in the dnsval.conf file.

Setting the max_refresh member to a particular value has the same effect setting the max-refresh option in the dnsval.conf file.

Setting the proto member to a particular value has the same effect setting the proto option in the dnsval.conf file.

env_policy and app_policy can be set to one of VAL_POL_GOPT_DISABLE, VAL_POL_GOPT_ENABLE, or VAL_POL_GOPT_OVERRIDE. These values correspond directly to the disable, enable and override options for the env-policy and app-policy settings in the dnsval.conf file.

Values of -1 for the above fields are treated as "ignore" conditions in that the validator will not include dynamically supplied global options with a value of -1 when creating its context. This allows an application to overriding a subset of global options while using the global options supplied in the dnsval.conf file by default.

The log_target field enables the application to supply log targets in addition to the ones configured in the configuration file.

See dnsval.conf(3) for more details on specifying validator policy.

Default query flags can be set and unset for a given context using val_context_setqflags(). This allows an application to alter the DNSSEC validator processing, while still having most of the more granular default configuration specified in its configuration file. The action parameter can be set to one of the following.

VAL_CTX_FLAG_SET
This option causes the validator to set the given flag as one of the default query flags.
VAL_CTX_FLAG_RESET
This option causes the validator to reset the given flag if it was set as one of the default query flags for the context.

Answers returned by val_resolve_and_check() are made available in the *results linked list. Each answer corresponds to a distinct RRset; multiple RRs within the RRset are part of the same answer. Multiple answers are possible when type is ns_t_any or ns_t_rrsig.

Individual elements in *results point to val_authentication_chain linked lists. The authentication chain elements in val_authentication_chain contain the actual RRsets returned by the name server in response to the query.

Validation result values returned in val_result_chain can be can be converted into ASCII format using the p_val_status(). Authentication chain status values returned in each element of the val_authentication_chain linked list can be can be converted into ASCII format using the p_ac_status() functions.

While some applications such as DNSSEC troubleshooting utilities and packet inspection tools may look at individual authentication chain elements to identify the actual reasons for validation error, most applications will only be interested in a single error code for determining the authenticity of data.

val_isvalidated() identifies if a given validation result status value corresponds to an answer that was cryptographically verified and validated using a locally configured trust anchor.

val_istrusted() identifies if a given validator status value is trusted. An answer may be locally trusted without being validated.

val_does_not_exist() identifies if a given validator status value corresponds to one of the non-existence types.

The libval library internally allocates memory for *results and this must be freed by the invoking application using the free_result_chain() interface.

libval proporciona la val_log_add_optarg() función para controlar el nivel de detalle y la ubicación de la salida de los mensajes de

registro.

La val_log_add_optarg() función toma dos argumentos: el primer argumento args es un valor de cadena de caracteres que especifica la ubicación y el nivel de detalle. El segundo argumento, use_stderr, si se establece en un valor mayor que 0 permite a libval enviar mensajes de registro a

stderr.

La cadena de caracteres que especifica la ubicación del destino del registro y el nivel de detalle tiene un formato

específico: 
<debug-level>:<dest-type>[:<dest-options>
]

donde
<debug-level> es 1-7, para niveles crecientes de detalle
<dest-type> es uno de file, net, syslog, stderr, stdout
<dest-options> depende de <dest-type>
file:<file-name> (abierto en modo de adición)
net[:<host-name>:<host-port>] (127.0.0.1:1053)
syslog[:facility] (0-23 (por defecto 1 USER)

)

Los niveles de registro pueden traducirse aproximadamente en diferentes tipos de mensajes de registro como sigue (los mensajes devueltos para cada nivel en esta lista subsumen los mensajes devueltos para el nivel anterior)

: 
3 : Error   : error encontrado
4 : Advertencia : recuperándose de un error
5 : Aviso  : da los resultados finales de validación para una consulta
              y detalles sobre los archivos de política y las etiquetas usadas
6 : Información    : proporciona detalles sobre las cadenas
de autenticación 7 : Depuración : propo
rciona información de nivel de depuración
