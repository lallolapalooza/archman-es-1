NOMBRE

dnf5-specs - Especificación de patrones

DESCRIPCIÓN

Se definen diferentes reglas de coincidencia de patrones para los argumentos en forma *-spec para operar con cada tipo de entidad en DNF5. En esta sección se describen y explican todas las reglas en detalle, con ejemplos.

COMODINES (GLOBS)

La especificación de patrones admite el mismo emparejamiento de patrones comodín que el shell. Se admiten los siguientes patrones:

*
Coincide con cualquier número de caracteres.
?
Coincide con cualquier carácter individual.
[]
Coincide con cualquiera de los caracteres incluidos. Un par de caracteres separados por un guion denota una expresión de rango; se coincide con cualquier carácter que esté entre esos dos caracteres, inclusive. Si el primer carácter que sigue al [ es un ! o un ^ entonces se coincide con cualquier carácter no incluido.

Nota: Los corchetes llaves ({}) no se admiten. Aún puede usarlos en shells que los admitan y dejar que el shell haga la expansión, pero si están entrecomillados o escapados, DNF5 no los expandirá.

PAQUETES

Muchos comandos aceptan un parámetro <package-spec*> que selecciona un paquete para la operación. Dependiendo del comando, el argumento <package-spec*> se compara contra:

  • NEVRA [N] o NEVRA sin distinguir mayúsculas de minúsculas [NI]
  • Provides (Proveedores) [P]
  • Proveedores de archivos [F]
  • Binarios [B]

secuencialmente hasta que se encuentre una coincidencia.

Por ejemplo, <package-spec-NP> se compara primero contra los NEVRAs y si no se encuentra un NEVRA coincidente, se compara contra los Provides.

Cuando <package-spec> es un nombre de paquete o un provide, el usuario puede proporcionar reglas de restricción adicionales para hacer coincidir los argumentos. Para este propósito se pueden usar comparaciones básicas de versión (=, >, <, >=, <=), como <package-spec> >= <version>, donde el argumento <version> está en un formato [EPOCH:]VERSION[-RELEASE] como se especifica en la sección de coincidencia NEVRA.

Para construir expresiones más complejas, también se admite la función de dependencias ricas, que siempre va encerrada entre paréntesis. Se pueden usar operadores booleanos y anidamiento, p. ej. (<spec1> or (<spec2> and <spec3>)). Para más información, consulte las dependencias booleanas de RPM.

Coincidencia NEVRA

Cada paquete puede identificarse de forma única por la cadena NEVRA . Consiste en 5 partes de información:

Nombre (Name)
Nombre del paquete.
Epoch
Número de epoch.
No siempre está incluido.

El número de epoch anula otras comprobaciones de versión, por lo que puede usarse para forzar la actualización del paquete sobre otro.

Versión (Version)
Cadena de versión.
No es estrictamente numérica.
Está destinada a coincidir con la versión del software original.
Release (Edición)
Cadena de edición.

Es información sobre la compilación particular del paquete, generalmente un número que se incrementa con la compilación más reciente. No está conectada con el software original.

Arquitectura (Architecture)
Cadena de arquitectura de destino.
Define el tipo de procesador en el que se pretende instalar el paquete.

También puede ser un paquete que contenga archivos fuente (src) o un paquete independiente de la arquitectura (noarch).

Al hacer coincidencia contra NEVRAs, se admite la coincidencia parcial. DNF5 intenta hacer coincidir la especificación con la siguiente lista de formas de NEVRA (en orden decreciente de prioridad):

NAME-[EPOCH:]VERSION-RELEASE.ARCH
NAME.ARCH
NAME
NAME-[EPOCH:]VERSION-RELEASE
NAME-[EPOCH:]VERSION

Tenga en cuenta que name puede contener guiones (p. ej. package-with-dashes).

Se usa la primera forma que coincida con algún paquete y no se prueban las formas restantes. Si ninguna de las formas coincide con ningún paquete, se intenta hacer coincidir <package-spec> contra los NEVRAs completos del paquete. Esto solo es relevante si hay comodines en <package-spec>.

Puede especificar comodines como parte de cualquiera de los cinco componentes del NEVRA. También puede especificar un patrón comodín para que coincida con múltiples componentes del NEVRA (en otras palabras, para que coincida a través de los separadores del NEVRA). En ese caso, sin embargo, debe escribir la especificación para que coincida con los NEVRAs completos del paquete, ya que no es posible dividir dicha especificación en formas de NEVRA.

Coincidencia de Proveedores de Archivos

Si una spec comienza con / o */, se considera como un proveedor de archivo potencial.

Coincidencia de Binarios

Si se deben considerar los binarios de los paquetes durante la coincidencia. Comprueba si la especificación dada spec es un binario en /usr/bin/ o /usr/sbin/.

COMPS

<group-spec>``|``<environment-spec> permite seleccionar grupos|entornos sobre los que debe trabajar una operación particular. Es una cadena que no distingue entre mayúsculas y minúsculas (y admite caracteres comodín) que se compara contra el ID del grupo|entorno, el nombre canónico y el nombre traducido al locale actual LC_MESSAGES (si es posible).

Las especificaciones de Comps llevan el prefijo @ para los comandos que también aceptan especificaciones de paquetes. Por ejemplo, consulte dnf5-install(8), Comando Install <#install-command-ref-label>.

MÓDULOS

<module-spec> permite seleccionar módulos o perfiles sobre los que debe trabajar una operación particular.

Dado que la forma de coincidencia NEVRA es insuficiente para los módulos, estos se identifican de forma única por el formato NSVCA (NAME:STREAM:VERSION:CONTEXT:ARCH/PROFILE). Las formas parciales admitidas son las siguientes:

NAME
NAME:STREAM
NAME:STREAM:VERSION
NAME:STREAM:VERSION:CONTEXT
Todas las combinaciones anteriores con ::ARCH (p. ej. NAME::ARCH)
NAME:STREAM:VERSION:CONTEXT:ARCH
Todas las combinaciones anteriores con /PROFILE (p. ej. NAME/PROFILE)

En caso de que no se especifique el stream, se usa el stream habilitado o el stream predeterminado, en ese orden. En caso de que no se especifique el perfil, se usa el perfil predeterminado del sistema o el perfil 'default'.

TRANSACCIONES

<transaction-spec> puede estar en una de varias formas. Si es un entero, especifica un ID de transacción. Especificar last es lo mismo que especificar el ID de la transacción más reciente. La última forma es last-<offset>, donde <offset> es un entero positivo. Especifica la transacción que precede en offset a la más reciente.
