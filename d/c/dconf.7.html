DCONF(7) Convenciones y misceláneos DCONF(7)

NOMBRE

dconf - Un sistema de configuración

DESCRIPCIÓN

dconf es un sistema de almacenamiento simple de clave/valor que está fuertemente optimizado para la lectura. Esto lo convierte en un sistema ideal para almacenar preferencias del usuario (las cuales se leen miles de veces por cada vez que el usuario cambia una). Fue creado con este caso de uso en mente.

Todas las preferencias se almacenan en un único archivo binario grande. Es posible la estratificación de preferencias usando múltiples archivos (es decir: para valores predeterminados del sitio). También se admite el bloqueo (lock-down). El archivo binario de los valores predeterminados puede ser opcionalmente compilado a partir de un conjunto de archivos de claves de texto plano.

dconf tiene una arquitectura parcial cliente/servidor. Utiliza D-Bus. El servidor solo interviene en las escrituras (y no se activa en la sesión del usuario hasta que el usuario modifica una preferencia). El servicio es inmutable y puede salir libremente en cualquier momento (y por lo tanto es robusto frente a fallos). La lista de rutas que cada proceso está vigilando se almacena dentro del propio demonio de D-Bus (como reglas de coincidencia de señales de D-Bus).

Las lecturas se realizan mediante acceso directo (a través de mmap) a la base de datos en disco, que es esencialmente una tabla hash. Por esta razón, las lecturas de dconf típicamente implican cero llamadas al sistema y son comparables a una búsqueda en una tabla hash en términos de velocidad. Hablando en términos prácticos, en configuraciones simples no estratificadas, dconf es menos de 10 veces más lento que GHashTable.

Se asume que las escrituras solo ocurren en respuesta a la interacción explícita del usuario (como hacer clic en una casilla de verificación en un diálogo de preferencias) y por lo tanto no están optimizadas en absoluto. En algunos sistemas de archivos, dconf-service llamará a fsync() en cada escritura, lo que puede introducir una latencia de hasta 100ms. Esta latencia está oculta por las bibliotecas del cliente a través de un mecanismo "rápido" inteligente que registra los cambios pendientes localmente (para que puedan leerse de inmediato) hasta que el servicio señala que una escritura se ha completado.

El formato de base de datos binario que dconf usa por defecto no es adecuado para su uso en NFS, donde mmap no funciona bien. Para manejar este caso de uso común, dconf puede configurarse para colocar su base de datos binaria en XDG_RUNTIME_DIR (que se garantiza que es local, pero no persistente) y sincronizarla con un archivo de claves de texto plano en el directorio de inicio del usuario.

PERFILES

Un perfil es una lista de bases de datos de configuración que dconf consulta para encontrar el valor de una clave. La base de datos personal del usuario siempre tiene la máxima prioridad, seguida de las bases de datos del sistema en el orden prescrito por el perfil.

Al inicio, dconf consulta la DCONF_PROFILE variable de entorno. Si está definida, dconf intentará abrir el perfil con ese nombre, abortando si eso falla. Si la variable de entorno no está definida, intentará abrir el perfil llamado "user" y si eso falla, volverá a una configuración interna fijada. dconf almacena sus perfiles en archivos de texto. DCONF_PROFILE puede especificar una ruta relativa a un archivo en /etc/dconf/profile/, o una ruta absoluta (como en el directorio de inicio de un usuario). El nombre del perfil solo puede usar caracteres alfanuméricos o '_'.

Un archivo de perfil podría verse como el siguiente:

user-db:user
system-db:local
system-db:site

Cada línea en un perfil especifica una base de datos de dconf. La primera línea indica la base de datos utilizada para escribir cambios, y las líneas restantes indican bases de datos de solo lectura. (La primera línea debería especificar un user-db o service-db, para que los usuarios puedan realmente hacer cambios de configuración.)

Una línea "user-db" especifica una base de datos de usuario. Estas bases de datos se encuentran en $XDG_CONFIG_HOME/dconf/. El nombre del archivo a abrir en ese directorio es exactamente como está escrito en el perfil. Este archivo se espera que esté en el formato de base de datos binaria de dconf. Ten en cuenta que XDG_CONFIG_HOME no puede ser definida/modificada por terminal o sesión, porque entonces el escritor y el lector estarían trabajando en diferentes bases de datos (el escritor es iniciado por DBus y no puede ver esa variable).

Una línea "service-db" instruye a dconf para colocar el archivo de base de datos binario de la base de datos del usuario en XDG_RUNTIME_DIR. Dado que esta ubicación no es persistente, el resto de la línea instruye a dconf cómo almacenar la base de datos persistentemente. Una línea típica es service-db:keyfile/user, que le dice a dconf sincronizar la base de datos binaria con un archivo de claves de texto plano en $XDG_CONFIG_HOME/dconf/user.txt. La sincronización es bidireccional.

Una línea "system-db" especifica una base de datos del sistema. Estas bases de datos se encuentran en /etc/dconf/db/. De nuevo, el nombre del archivo a abrir en ese directorio es exactamente como está escrito en el perfil y el archivo se espera que esté en el formato de base de datos de dconf.

Si la DCONF_PROFILE variable de entorno no está definida y el perfil "user" no puede abrirse, entonces el efecto es como si el perfil fuera especificado por este archivo:

user-db:user

Es decir, la base de datos personal del usuario es consultada y no hay configuraciones del sistema.

ARCHIVOS DE CLAVES

Para facilitar la configuración del sistema con un editor de texto, dconf puede poblar bases de datos a partir de archivos de claves de texto plano. Para cualquier base de datos del sistema dada, los archivos de claves pueden colocarse en el directorio /etc/dconf/db/database.d/. Los archivos de claves contienen grupos de configuraciones como sigue:

# Algunas configuraciones predeterminadas útiles para nuestro sitio
[system/proxy/http]
host='172.16.0.1'
enabled=true
[org/gnome/desktop/background]
picture-uri='file:///usr/local/rupert-corp/company-wallpaper.jpeg'

Después de cambiar los archivos de claves, la base de datos necesita ser actualizada con la dconf(1) herramienta.

BLOQUEOS

Las bases de datos del sistema pueden contener 'bloqueos' para claves. Si un bloqueo para una clave o subruta particular está instalado en una base de datos, entonces ninguna base de datos listada por encima de esa en el perfil podrá modificar ninguna de las configuraciones afectadas. Esto puede usarse para hacer cumplir configuraciones obligatorias.

Para añadir bloqueos a una base de datos, coloca archivos de texto en el directorio /etc/dconf/db/database.d/locks, donde database es el nombre de una base de datos del sistema, como se especifica en el perfil. Los archivos contienen una lista de claves a bloquear, una por línea. Las líneas que comienzan con # son ignoradas. Aquí hay un ejemplo:

# prevenir cambios en el fondo de la empresa
/org/gnome/desktop/background/picture-uri

Después de cambiar los bloqueos, la base de datos necesita ser actualizada con la dconf(1) herramienta.

PORTABILIDAD

dconf apunta principalmente a sistemas operativos de Software Libre. Teóricamente funcionaría en Mac OS pero no tiene mucho sentido (ya que las aplicaciones de Mac OS quieren almacenar preferencias en archivos plist). No es posible usar dconf en Windows debido a la imposibilidad de renombrar sobre un archivo que todavía está en uso (lo que es lo que hace dconf-service en cada escritura).

ESTABILIDAD DE LA API

La API de dconf no es particularmente amigable, y no se garantiza que sea estable. Debido a esto y a la falta de portabilidad, casi seguramente querrás usar algún tipo de API envolvente alrededor de ella. La API envolvente usada por las aplicaciones GTK+ y GNOME es GSettings[1], la cual es incluida como parte de GLib. GSettings tiene backends para Windows (usando el registro) y Mac OS (usando listas de propiedades) además de su backend de dconf y es la API apropiada a usar para aplicaciones gráficas.
