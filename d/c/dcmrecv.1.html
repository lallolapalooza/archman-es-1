DESCRIPCIÓ

N

La aplicación dcmrecv implementa un Proveedor de Clase de Servicio (SCP) para la Clase de Servicio de Almacenamiento. A diferencia de la conocida utilidad storescp, dcmrecv tiene menos opciones y, por lo tanto, podría ser más fácil de usar; esto también explica el término "simple" en el título. El propósito principal de esta aplicación es re

cibir un montón de conjuntos de datos DICOM de un Usuario de Clase de Servicio de Almacen
amiento (SCU) y almacenarlos en un directorio y una estructura de archivos configurables.

NOTA

S

Uso

típico

Un caso de uso típico de dcmrecv es recibir instancias SOP que se envían desde un SCU de almacenamiento y guardarlas como archivos DICOM. El siguiente comando hace exactamente

esto: 
dcmrecv --verbose <puerto> --config-file storescp.cfg
default

Si prefiere una estructura de subdirectorios creada automáticamente, nombres de archivo más cortos y la extensión ".dcm" para todos los archivos DICOM, use el siguiente

comando: 
dcmrecv -v -xf storescp.cfg default <puerto> --series-date-subdir
                                           --short-unique-names
                                           --filename-extension .
dcm

En el caso de instancias SOP muy grandes o si el conjunto de datos debe escribirse exactamente como se recibió (por ejemplo, para depuración), podría usarse el "modo de preservación de

bits": 
dcmrecv -v -xf storescp.cfg default <puerto> --bit-preservin
g

Los conjuntos de datos recibidos siempre se almacena

n como archivos DICOM con la misma Sintaxis de
Transferencia que se usó para la transmisión de red.

Conformidad

DICOM

Básicamente, la aplicación dcmrecv soporta todas las Clases SOP de Almacenamiento como SCP, incluyendo las privadas. Sin embargo, esto requiere que se cargue un perfil de negociación de asociación correspondiente desde un archivo de configuración. El formato y la semántica de este archivo de configuración están documentados en asconfig.

txt.

Por defecto, es decir, si no se carga ningún perfil de negociación de asociación, dcmrecv solo soporta la Clase SOP de Verificación como SCP (con sintaxis de transferencia predeterminada, es decir, Little Endian VR implícito)

.

En el futuro, podría haber opciones adicionales que permitan especificar la lista de

Contextos de Presentación compatidos (es decir, la combinación de Clase SOP y Sintax
is de Transferencia) directamente, es decir, sin cargar un archivo de configuración.

Generación de subdirectorios/a

>

La opción --series-date-subdir permite generar subdirectorios (debajo del directorio de salida especificado) basados en el valor del elemento de datos Series Date (0008,0021) del conjunto de datos DICOM recibido. Si este valor se pudo recuperar del conjunto de datos y es válido (es decir, consiste en un campo de fecha DICOM válido), la estructura del subdirectorio es la

siguiente: 
<output-directory>/data/<year>/<month>/<day>
/<filename>

Si el Series Date (0008,0021) no se puede recuperar o es inválido, se utiliza la fecha actual del sistema para la siguiente estructura de

subdirectorio: 
<output-directory>/undef/<year><month><day>
/<filename>

En ambos casos, <year> consiste de 4

dígitos decimales y <month> as
í como <day> de 2 dígitos decimales.

Generación de nombres de

archivo

Por defecto, los nombres de archivo para almacenar los conjuntos de datos DICOM recibidos se generan de acuerdo con el siguiente

esquema: 
<short-modality-prefix>.<sop-instance-uid><filename-extension
>

Si se recibe la misma instancia SOP dos veces, se reporta un mensaje de advertencia y el archivo existente se

sobrescribe.

La opción --unique-filenames asegura que cada conjunto de datos DICOM recibido se almacene como un archivo separado, es decir, nunca se deben sobrescribir archivos. Esto se hace utilizando un identificador único (UID) recién creado para cada nombre de archivo generado (y el infijo ".X" para evitar conflictos con valores reales de SOP Instance UID). El esquema de nombrado para esta opción es el

siguiente: 
<short-modality-prefix>.X.<unique-identifier><filename-extension
>

Cuando se usa la opción --short-unique-names, los nombres de archivo se generan mediante algún generador de nombres pseudoaleatorio, que también asegura que no haya conflictos (es decir, no se sobrescriben archivos existentes). Este es el esquema de

nombrado: 
<short-modality-prefix>_<pseudo-random-name><filename-extension
>

Con <pseudo-random-name> consistiendo de 16 dígitos en notación

hexadecimal.

Finalmente, la opción --system-time-names permite generar nombres de archivo basados en la hora actual del

sistema: 
<date><time>.<short-modality-prefix><filename-extension
>

Con <date> consistiendo de "<year><month><day>" y <time> de "<hour><minute><second>.<micro-s

econd>". Tenga en cuenta que este esquema podría resultar en conflictos de nombrado si la re
solución de la hora del sistema no es suficientemente alta (es decir, no soporta microsegundos).

Limitacione

s

Tenga en cuenta que la opción --bit-preserving no se puede usar junto con la opción --series-date-subdir ya que el conjunto de datos recibido se almacena directamente

en el archivo y el valor del Series Date (
0008,0021) es, por lo tanto, no disponi
ble antes de que se haya creado el archivo.

REGISTR

O

El nivel de salida de registro de las diversas herramientas de línea de comandos y bibliotecas subyacentes puede ser especificado por el usuario. Por defecto, solo errores y advertencias se escriben en el flujo de error estándar. Usando la opción --verbose también se reportan mensajes informativos como detalles de procesamiento. La opción --debug se puede usar para obtener más detalles sobre la actividad interna, p. ej. para propósitos de depuración. Otros niveles de registro pueden ser seleccionados usando la opción --log-level. En el modo --quiet solo se reportan errores fatales. En tales eventos de error muy graves, la aplicación generalmente terminará. Para más detalles sobre los diferentes niveles de registro, vea la documentación del módulo

"oflog".

En caso de que la salida de registro deba escribirse en un archivo (opcionalmente con rotación de archivo de registro), en syslog (Unix) o en el registro de eventos (Windows), se puede usar la opción --log-config. Este archivo de configuración también permite dirigir solo ciertos mensajes a un flujo de salida particular y filtrar ciertos mensajes basados en el módulo o aplicación donde se generan. Un archivo de configuración de ejemplo se proporciona en <etcdir>/l

ogger
.cfg.

LÍNEA DE

COMANDOS

Todas las herramientas de línea de comandos usan la siguiente notación para parámetros: corchetes encierran valores opcionales (0-1), tres puntos finales indican que se permiten múltiples valores (1-n), una combinación de ambos significa 0 a n

valores.

Las opciones de línea de comandos se distinguen de los parámetros por un signo '+' o '-' inicial, respectivamente. Usualmente, el orden y la posición de las opciones de línea de comandos son arbitrarios (es decir, pueden aparecer en cualquier parte). Sin embargo, si las opciones son mutuamente excluyentes se usa la aparición más a la derecha. Este comportamiento se conforma a las reglas de evaluación estándar de los shells Unix

comunes.

Además, se pueden especificar uno o más archivos de comando usando un signo '@' como prefijo del nombre de archivo (p. ej. @command.txt). Tal argumento de comando es reemplazado por el contenido del archivo de texto correspondiente (múltiples espacios en blanco son tratados como un solo separador a menos que aparezcan entre dos comillas) antes de cualquier evaluación posterior. Tenga en cuenta que un archivo de comando no puede contener otro archivo de comando. Este enfoque simple pero efectivo permite resumir combinaciones comunes de opciones/parámetros y evita líneas de comando largas y confusas (un ejemplo se proporciona en el archivo <datadir>/du

mppat
.txt).

ENTORN

O

La utilidad dcmrecv intentará cargar los diccionarios de datos DICOM especificados en la variable de entorno DCMDICTPATH. Por defecto, es decir, si la variable de entorno DCMDICTPATH no está establecida, el archivo <datadir>/dicom.dic será cargado a menos que el diccionario esté compilado en la aplicación (por defecto en Windows)

.

El comportamiento por defecto debería ser preferido y la variable de entorno DCMDICTPATH solo usada cuando se requieran diccionarios de datos alternativos. La variable de entorno DCMDICTPATH tiene el mismo formato que la variable PATH del shell Unix en que un dos puntos (":") separa las entradas. En sistemas Windows, se usa un punto y coma (";") como separador. El código del diccionario de datos intentará cargar cada archivo especificado en la variable de entorno DCMDICTPATH. Es un error s

i no se puede cargar nin
gún diccionario de datos.
