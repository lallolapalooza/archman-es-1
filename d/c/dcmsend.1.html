NOMBRE

dcmsend - SCU simple de almacenamiento DICOM (remitente)

SINOPSIS

dcmsend [opciones] peer puerto dcmfile-in...

DESCRIPCIÓN

La aplicación dcmsend implementa un Usuario de Clase de Servicio (SCU) para la Clase de Servicio de Almacenamiento. En contraste con la conocida utilidad storescu, dcmsend tiene menos opciones y es, por lo tanto, más fácil de usar; esto también explica el término "simple" en el título. El propósito principal de esta aplicación es enviar un gran número de archivos DICOM a un Proveedor de Clase de Servicio de Almacenamiento (SCP). dcmsend admite tanto asociaciones múltiples (una tras otra) como la descompresión de instancias SOP DICOM si es necesario para transferirlas.

PARÁMETROS

peer        nombre de host del par DICOM
port        número de puerto tcp/ip del par
dcmfile-in  archivo o directorio DICOM a transmitir

NOTAS

Uso Típico

Un caso de uso típico de dcmsend es enviar instancias SOP arbitrarias que se almacenan como archivos DICOM a un SCP de almacenamiento. El siguiente comando hace exactamente eso:

dcmsend --verbose <peer> <puerto> *.dcm

Si los archivos DICOM se almacenan en una jerarquía de directorios debajo del directorio "IMAGENES", se puede usar el siguiente comando:

dcmsend -v <peer> <puerto> --scan-directories --recurse IMAGENES

También es posible especificar múltiples directorios y combinar los enfoques mencionados anteriormente (usando nombres de archivo y directorio):

dcmsend -v +sd +r <peer> <puerto> IMAGENES_1 IMAGENES_2 test.img *.dcm

Si las instancias SOP se referencian desde un archivo DICOMDIR, se puede usar la opción --read-from-dicomdir (o +rd) para enviar todos los archivos DICOM referenciados sin cargarlos ya para la negociación de asociación:

dcmsend -v <peer> <puerto> --read-from-dicomdir DICOMDIR

Y de nuevo, todos los enfoques anteriores se pueden combinar de esta manera:

dcmsend -v +sd +r +rd <peer> <puerto> IMAGENES_1 IMAGENES_2 test.img DICOMDIR *.dcm

La opción predeterminada --read-file-only asegura que solo se procesen los archivos DICOM (es decir, los que tienen la meta-cabecera y la palabra mágica "DICM" después del preámbulo). Por lo general, al procesar una gran cantidad de archivos, también es una buena idea no detenerse en el primer archivo de entrada inválido o si se encontró una transferencia fallida. Esto se puede lograr usando la opción --no-halt. Tenga en cuenta, sin embargo, que "transferencia fallida" no significa que el estado DIMSE de la respuesta C-STORE indique un error. Significa que la solicitud C-STORE no pudo ser enviada al SCP de almacenamiento.

Si se necesitan más de 128 Contextos de Presentación, que es el número máximo permitido según el estándar DICOM, se inicia una nueva asociación después de que se completa la anterior. En casos donde este comportamiento no es deseado, puede deshabilitarse usando la opción --single-association. Además, se puede especificar si solo se descomprimen los conjuntos de datos comprimidos sin pérdidas (si es necesario), que es el valor predeterminado, o también los conjuntos de datos comprimidos con pérdidas, usando las opciones --decompress-xxx.

Para obtener tanto una visión general como información detallada sobre la transferencia de las instancias SOP DICOM, se puede usar la opción --create-report-file para crear un archivo de texto correspondiente. Sin embargo, este archivo solo se crea como paso final si la aplicación no terminó antes (con un error).

Escaneo de Directorios

Agregar directorios como parámetro en la línea de comandos solo tiene sentido si la opción --scan-directories también se proporciona. Si los archivos en los directorios proporcionados deben seleccionarse de acuerdo con un patrón de nombre específico (por ejemplo, usando coincidencia de comodines), se debe usar la opción --scan-pattern. Tenga en cuenta que este patrón de archivo solo se aplica a los archivos dentro de los directorios escaneados y, si se especifican otros patrones en la línea de comandos fuera de la opción --scan-pattern (por ejemplo, para seleccionar archivos adicionales), estos no se aplican a los directorios especificados.

Por lo tanto, el tercer ejemplo anterior recorrerá recursivamente los directorios IMAGENES_1 e IMAGENES_2 y transmitirá los archivos que contienen estas dos carpetas y todas sus subcarpetas (debido a la opción +r). Además, dcmsend transferirá "test.img" y todos los archivos con la extensión "dcm"

Conformidad

DICOM

Básicamente, la aplicación dcmsend admite todas las clases de almacenamiento (Storage SOP Classes) como SCU, incluidas las privadas. De forma predeterminada, la aplicación verifica el UID de la clase SOP del archivo DICOM para asegurarse de que solo se envían instancias SOP válidas. Con la opción --no-uid-checks esta verificación puede

deshabilitarse.

La aplicación dcmsend también admite todas las sintaxis de transferencia definidas en el estándar DICOM. Las sintaxis de transferencia privadas solo pueden usarse si la verificación de UID se deshabilita con la opción --no-uid-checks. Tenga en cuenta, sin embargo, que solo se admite un número limitado de sintaxis de transferencia para convertirlas a la sintaxis de transferencia predeterminada de DICOM (Implicit VR Little Endian). Con la opción --list-decoders se enumeran las sintaxis de transferencia admitidas de forma nativa o mediante decodificadores. La salida normalmente se ve

así: 
Sintaxis de transferencia admitidas de forma nativa:
- Little Endian Implicit
- Little Endian Explicit
- Big Endian Explicit
Sintaxis de transferencia admitidas mediante decodificadores:
- Deflated Explicit VR Little Endian
- JPEG Baseline
- JPEG Extended, Process 2+4
- JPEG Spectral Selection, Non-hierarchical, Process 6+8
- JPEG Full Progression, Non-hierarchical, Process 10+12
- JPEG Lossless, Non-hierarchical, Process 14
- JPEG Lossless, Non-hierarchical, 1st Order Prediction
- JPEG-LS Lossless
- JPEG-LS Lossy (Near-lossless)
- RLE
Lossless

Dado que dcmsend intenta ser lo más simple posible para el usuario, de forma predeterminada se pueden proponer contextos de presentación al SCP que, estrictamente hablando, son "ilegales". Esto se debe a que, según el estándar DICOM, el SCU siempre debe proponer la sintaxis de transferencia predeterminada de DICOM en al menos un contexto de presentación asociado a cada sintaxis abstracta (es decir, clase SOP). Este requisito se omite si el SCU solo tiene acceso a la instancia SOP en forma comprimida con pérdida o si los datos de píxeles descomprimidos serían demasiado grandes para ser codificados. Con la opción --no-illegal-proposal se puede imponer el comportamiento estrictamente conforme a DICOM, es decir, no se propondrá ningún contexto de presentación posiblemente ilegal, pero la instancia SOP correspondiente será rechazada (si es necesario). Tenga en cuenta, sin embargo, que no se verifica el tamaño de los datos de píxeles

descomprimidos.

La sintaxis de transferencia predeterminada para "Compresión JPEG sin pérd

ida", "Compresión JPEG con pérdida", etc., no se propone siempre, como tam
bién requiere el estándar DICOM. La misma limitación se aplica a otros esquemas de compresión. Consulte DICOM PS 3.5, sección 10 para más detalles.

REGISTRO

(LOGGING)

El nivel de salida de registro de las diversas herramientas de línea de comandos y bibliotecas subyacentes puede ser especificado por el usuario. De forma predeterminada, solo se escriben errores y advertencias en el flujo de error estándar. Usando la opción --verbose también se informan mensajes informativos como detalles del procesamiento. La opción --debug puede usarse para obtener más detalles sobre la actividad interna, por ejemplo, para fines de depuración. Otros niveles de registro pueden seleccionarse usando la opción --log-level. En el modo --quiet solo se informan errores fatales. En tales eventos de error muy graves, la aplicación normalmente terminará. Para más detalles sobre los diferentes niveles de registro, consulte la documentación del módulo

"oflog".

En caso de que la salida de registro deba escribirse en un archivo (opcionalmente con rotación de registro), en syslog (Unix) o en el registro de eventos (Windows), se puede usar la opción --log-config. Este archivo de configuración también permite dirigir solo ciertos mensajes a un flujo de salida particular y filtrar ciertos mensajes basándose en el módulo o la aplicación donde se generan. Un archivo de configuración de ejemplo se proporciona en <etcdir>/l

ogger
.cfg.

LÍNEA DE

COMANDOS

Todas las herramientas de línea de comandos usan la siguiente notación para los parámetros: los corchetes encierran valores opcionales (0-1), tres puntos finales indican que se permiten múltiples valores (1-n), una combinación de ambos significa de 0 a n

valores.

Las opciones de línea de comandos se distinguen de los parámetros por un signo '+' o '-' inicial, respectivamente. Normalmente, el orden y la posición de las opciones de línea de comandos son arbitrarios (es decir, pueden aparecer en cualquier lugar). Sin embargo, si las opciones son mutuamente excluyentes, se usa la aparición más a la derecha. Este comportamiento se ajusta a las reglas de evaluación estándar de los shells comunes de

Unix.

Además, se pueden especificar uno o más archivos de comando usando el signo '@' como prefijo del nombre de archivo (por ejemplo, @command.txt). Tal argumento de comando se reemplaza por el contenido del archivo de texto correspondiente (múltiples espacios en blanco se tratan como un solo separador a menos que aparezcan entre dos comillas) antes de cualquier otra evaluación. Tenga en cuenta que un archivo de comando no puede contener otro archivo de comando. Este enfoque simple pero efectivo permite resumir combinaciones comunes de opciones/parámetros y evita líneas de comando largas y confusas (un ejemplo se proporciona en el archivo <datadir>/du

mppat
.txt).

ENTORN

O

La utilidad dcmsend intentará cargar los diccionarios de datos DICOM especificados en la variable de entorno DCMDICTPATH. De forma predeterminada, es decir, si la variable de entorno DCMDICTPATH no está establecida, se cargará el archivo <datadir>/dicom.dic a menos que el diccionario esté compilado en la aplicación (predeterminado en Windows)

.

Se debe preferir el comportamiento predeterminado y la variable de entorno DCMDICTPATH solo debe usarse cuando se requieran diccionarios de datos alternativos. La variable de entorno DCMDICTPATH tiene el mismo formato que la variable PATH del shell de Unix en el que un dos puntos (":") separa las entradas. En los sistemas Windows, se usa un punto y coma (";") como separador. El código del diccionario de datos intentará cargar cada archivo especificado en la variable de entorno DCMDICTPATH.
