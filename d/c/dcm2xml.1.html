dcm2xml - Convierte

archivos y conjuntos
de datos DICOM a XML

SINOPSI

S 
dcm2xml [opcio
nes] dcmfile-in
[xmlfile-out]

DESCRIPCIÓ

N

La utilidad dcm2xml convierte el contenido de un archivo DICOM (formato de archivo o conjunto de datos sin procesar) a XML (Lenguaje de Marcado Extensible). Hay dos formatos de salida. El primero es específico de DCMTK con su DTD (Definición de Tipo de Documento) descrito en el archivo dcm2xml.dtd. El segundo se refiere al "Modelo DICOM Nativo" que está especificado para el servicio de Alojamiento de Aplicaciones DICOM que se encuentra en la parte 19 de

DICOM.

Si dcm2xml lee un conjunto de datos sin procesar (datos DICOM sin un encabezado meta de formato de archivo) intentará adivinar la sintaxis de transferencia examinando los primeros bytes del archivo. No siempre es posible adivinar correctamente la sintaxis de transferencia y es mejor convertir un conjunto de datos a un formato de archivo siempre que sea posible (usando la utilidad dcmconv). También es posible usar las -f y -t[ieb] opciones para forzar a dcm2xml a leer un conjunto de datos con

una sintaxis de trans
ferencia particular.

Formato

DCMTK

La estructura básica de la salida XML específica de DCMTK creada desde un archivo DICOM se ve como la

siguiente: 
<?xml version="1.0" encoding="ISO-8859-1"?>
<!DOCTYPE file-format SYSTEM "dcm2xml.dtd">
<file-format xmlns="http://dicom.offis.de/dcmtk">
  <meta-header xfer="1.2.840.10008.1.2.1" name="Little Endian Explicit">
    <element tag="0002,0000" vr="UL" vm="1" len="4"
             name="MetaElementGroupLength">
      166
    </element>
    ...
    <element tag="0002,0013" vr="SH" vm="1" len="16"
             name="ImplementationVersionName">
      OFFIS_DCMTK_353
    </element>
  </meta-header>
  <data-set xfer="1.2.840.10008.1.2" name="Little Endian Implicit">
    <element tag="0008,0005" vr="CS" vm="1" len="10"
             name="SpecificCharacterSet">
      ISO_IR 100
    </element>
    ...
    <sequence tag="0028,3010" vr="SQ" card="2" name="VOILUTSequence">
      <item card="3">
        <element tag="0028,3002" vr="xs" vm="3" len="6"
                 name="LUTDescriptor">
          256\0\8
        </element>
        ...
      </item>
      ...
    </sequence>
    ...
    <element tag="7fe0,0010" vr="OW" vm="1" len="262144"
             name="PixelData" loaded="no" binary="hidden">
    </element>
  </data-set>
</file-format>

Las etiquetas "file-format" y "meta-header" están ausentes para conjuntos de datos

DICOM.

Codificación

XML

Los atributos con campos de valor muy grandes (p. ej., datos de píxeles) no se cargan por defecto. Se pueden identificar por el atributo adicional "loaded" con un valor de "no" (ver ejemplo arriba). La opción de línea de comandos --load-all fuerza la carga de todos los campos de valor incluyendo los muy

largos.

Además, los datos binarios de los atributos OB y OW no se escriben en el archivo de salida XML por defecto. Estos elementos se pueden identificar por el atributo adicional "binary" con un valor de "hidden" (por defecto es "no"). La opción de línea de comandos --write-binary-data hace que también se impriman los campos de valor binarios (el valor del atributo es "yes" o "base64"). Pero, tener cuidado al usar esta opción junto con --load-all debido a las grandes cantidades de datos de píxeles que podrían imprimirse en la salida. Tener en cuenta que en este contexto los valores de elementos con VR de OD, OF, OL y OV no se consideran "datos

binarios".

Los valores múltiples (es decir, donde la multiplicidad de valores DICOM es mayor que 1) están separados por una barra invertida "\" (excepto para datos codificados en Base64). El atributo "len" indica el número de bytes para el campo de valor particular tal como se almacena en el conjunto de datos DICOM, es decir, podría diferir de la longitud del valor codificado en XML, p. ej., debido a relleno no significativo que ha sido eliminado. NOMBRE

dcm2xml ― DICOM a XML convertidor

SINOPSIS

dcm2xml [OPTIONS] [DICOMFILE | - [...]]

DESCRIPCIÓN

El programa dcm2xml lee un archivo DICOM especificado en la línea de comandos, lo convierte al formato Modelo DICOM Nativo y escribe el resultado en la salida estándar.

Para más detalles sobre el formato Modelo DICOM Nativo, ver la sección "DCMTK Format" de esta página del manual.

Parámetros

—DICOMFILE
El archivo DICOM a convertir. Si se especifica un guion ("-"), el archivo de entrada se lee de la entrada estándar.

Opciones

Las opciones de la línea de comandos son distinguida de los parámetros por un prefijo '+' o '-'. Ver la sección "COMMAND LINE" de esta página del manual para más detalles.

--help

Imprimir un mensaje de ayuda y salir.

--version

Imprimir la versión del programa y salir.

--verbose

Activar mensajes informativos (ver sección "LOGGING").

--debug

Activar mensajes de depuración (ver sección "LOGGING").

--log-level level

Establecer el nivel de registro en level (ver sección "LOGGING").

--log-config config

Cargar la configuración de registro desde el archivo config (ver sección "LOGGING").

--charset-assume charset

Asumir que el conjunto de caracteres de la entrada es charset si el atributo DICOM (0008,0005) no está presente. Ver sección "Character Encoding" para más detalles.

--convert-to-utf8

Convertir el conjunto de caracteres de la entrada a UTF-8 antes de la conversión a XML. Ver sección "Character Encoding" para más detalles.

--encode-base64

Codificar datos binarios en Base64 como elementos XML <InlineBinary>. Ver sección "Bulk Data" para más detalles.

--no-bulk-data

No escribir datos binarios como elementos XML <BulkData>. Ver sección "Bulk Data" para más detalles.

--use-native-names

Usar nombres de elementos DICOM nativos en lugar de etiquetas DICOM numéricas.

--element-indent [indent]

Identar cada elemento DICOM con la cadena de identación dada indent. Si indent no se especifica, se usa una tabulación por defecto.

--attribute-indent [indent]

Identar cada atributo XML con la cadena de identación dada indent. Si indent no se especifica, se usa una tabulación por defecto.

--xml-declaration [indent]

Incluir una declaración XML en la salida. Si indent no se especifica, se usa "" por defecto.

--dtd-file file

Especificar el nombre del archivo DTD para la declaración DOCTYPE.

FORMATO DCMTK

Este programa soporta la representación de datos DICOM en un formato XML específico, conocido como el Modelo DICOM Nativo. Los detalles de este formato se encuentran en el estándar DICOM, parte 19 ("Application Hosting").

DATOS MASIVOS

Los datos binarios (valores de elementos DICOM con VRs OB u OW, así como valores OD, OF, OL, OV y UN) no se escriben en la salida XML por defecto debido a su tamaño. En su lugar, para cada elemento, se genera un nuevo Identificador Único Universal (UUID) y se escribe como un atributo de un elemento XML <BulkData>. Actualmente, no existe la posibilidad de escribir un archivo adicional para contener los datos binarios de cada trozo de datos binarios. Esto no es requerido por el estándar, sin embargo, podría ser útil para implementar una interfaz de Alojamiento de Aplicaciones; por lo tanto, esta característica podría estar disponible en futuras versiones de dcm2xml.

Adicionalmente, el Suplemento 163 (Almacenamiento a través de la Web por Servicios RESTful) introduce un nuevo elemento XML <InlineBinary> que permite codificar datos binarios como Base64. Actualmente, la opción de línea de comandos --encode-base64 habilita esta codificación para los VRs OB, OD, OF, OL, OV, OW y UN.

Adicionalmente, el elemento DICOM (0008,0005) "Specific Character Set" puede tener una longitud indefinida. En este caso, el elemento DICOM correspondiente se ha almacenado con longitud indefinida.

PROBLEMAS CONOCIDOS

Además de lo escrito en la sección anterior sobre "Bulk Data", existen otros problemas conocidos con la implementación actual del formato Modelo DICOM Nativo. Por ejemplo, los valores de elementos grandes con un VR distinto de OB, OD, OF, OL, OV, OW o UN actualmente nunca se escriben como datos masivos, aunque podría ser útil, por ejemplo, para elementos de texto muy largos (especialmente UT) o campos numéricos muy largos (de varios VRs).

NOTAS

CODIFICACIÓN DE CARACTERES

La codificación de caracteres XML se determina automáticamente a partir del atributo DICOM (0008,0005) "Specific Character Set" utilizando el siguiente mapeo:

ASCII (ISO_IR 6) => "UTF-8"
UTF-8 "ISO_IR 192" => "UTF-8"
ISO Latin 1 "ISO_IR 100" => "ISO-8859-1"
ISO Latin 2 "ISO_IR 101" => "ISO-8859-2"
ISO Latin 3 "ISO_IR 109" => "ISO-8859-3"
ISO Latin 4 "ISO_IR 110" => "ISO-8859-4"
ISO Latin 5 "ISO_IR 148" => "ISO-8859-9"
ISO Latin 9 "ISO_IR 203" => "ISO-8859-15"
Cirílico "ISO_IR 144" => "ISO-8859-5"
Árabe "ISO_IR 127" => "ISO-8859-6"
Griego "ISO_IR 126" => "ISO-8859-7"
Hebreo "ISO_IR 138" => "ISO-8859-8"

Si este atributo DICOM falta en el archivo de entrada, aunque sea necesario, se puede usar la opción --charset-assume para especificar manualmente un conjunto de caracteres apropiado (usando uno de los términos definidos por DICOM). Por razones de compatibilidad con versiones anteriores de esta herramienta, los siguientes términos también se admiten y se mapean automáticamente a los términos definidos por DICOM asociados: latin-1, latin-2, latin-3, latin-4, latin-5, latin-9, cirílico, árabe, griego, hebreo.

No se admiten múltiples conjuntos de caracteres que utilizan técnicas de extensión de código. Si es necesario, se puede usar la opción --convert-to-utf8 para convertir el archivo DICOM o el conjunto de datos a codificación UTF-8 antes de la conversión al formato XML. Esto también es útil para archivos DICOMDIR donde cada registro de directorio puede tener un conjunto de caracteres diferente.

Si no se define ningún mapeo y no se utiliza la opción --convert-to-utf8, los caracteres no ASCII y los inferiores a #32 se almacenan como "&#nnn;", donde "nnn" se refiere al código numérico del carácter. Esto podría generar referencias de entidad de caracteres no válidas (como "&#27;" para ESC) y provocará que la mayoría de los analizadores XML rechacen el documento.

REGISTRO

El nivel de salida de registro de las diversas herramientas de línea de comandos y bibliotecas subyacentes puede ser especificado por el usuario. Por defecto, solo los errores y advertencias se escriben en el flujo de error estándar. Usando la opción --verbose, también se informan mensajes informativos como detalles de procesamiento. La opción --debug se puede usar para obtener más detalles sobre la actividad interna, por ejemplo, para fines de depuración. Se pueden seleccionar otros niveles de registro usando la opción --log-level. En modo --quiet, solo se informan los errores fatales. En tales eventos de error muy graves, la aplicación generalmente terminará. Para más detalles sobre los diferentes niveles de registro, ver la documentación del módulo "oflog".

En caso de que la salida de registro deba escribirse en un archivo (opcionalmente con rotación de archivos de registro), a syslog (Unix) o al registro de eventos (Windows), se puede usar la opción --log-config. Este archivo de configuración también permite dirigir solo ciertos mensajes a un flujo de salida particular y filtrar ciertos mensajes basándose en el módulo o aplicación donde se generan. Se proporciona un archivo de configuración de ejemplo en <em>\<etcdir\>/logger.cfg</em>.

LÍNEA DE COMANDOS

Todas las herramientas de línea de comandos usan la siguiente notación para los parámetros: los corchetes encierran valores opcionales (0-1), tres puntos al final indican que se permiten múltiples valores (1-n), una combinación de ambos significa de 0 a n valores.

Las opciones de línea de comandos se distinguen de los parámetros por un signo '+' o '-' respectivamente. Usualmente, el orden y la posición de las opciones de línea de comandos son arbitrarios (es decir, pueden aparecer en cualquier lugar). Sin embargo, si las opciones son mutuamente excluyentes, se utiliza la aparición más a la derecha. Este comportamiento se ajusta a las reglas de evaluación estándar de los shells Unix comunes.

Además, se puede especificar uno o más archivos de comandos usando un signo '@' como prefijo del nombre del archivo (por ejemplo, <em>\@command.txt</em>). Dicho argumento de comando se reemplaza por el contenido del archivo de texto correspondiente (múltiples espacios en blanco se tratan como un solo separador a menos que aparezcan entre dos comillas) antes de cualquier otra evaluación. Tenga en cuenta que un archivo de comando no puede contener otro archivo de comando. Este enfoque simple pero efectivo permite resumir combinaciones comunes de opciones/parámetros y evita líneas de comandos largas y confusas (se proporciona un ejemplo en el archivo <em>\<datadir\>/dumppat.txt</em>).

ENTORNO

La utilidad dcm2xml intentará cargar los diccionarios de datos DICOM especificados en la variable de entorno DCMDICTPATH. Por defecto, es decir, si la variable de entorno DCMDICTPATH no está configurada, se cargará el archivo <em>\<datadir\>/dicom.dic</em>, a menos que el diccionario esté incorporado en la aplicación (por defecto para Windows).

Se debe preferir el comportamiento por defecto y usar la variable de entorno DCMDICTPATH solo cuando se requieran diccionarios de datos alternativos. La variable de entorno DCMDICTPATH tiene el mismo formato que la variable PATH del shell Unix, en el sentido de que dos puntos (":") separan las entradas. En los sistemas Windows, se utiliza un punto y coma (";") como separador. El código del diccionario de datos intentará cargar cada archivo especificado en la variable de entorno DCMDICTPATH. Es un error si no se puede cargar ningún diccionario de datos.

Dependiendo de las opciones de línea de comandos especificadas, la utilidad dcm2xml intentará cargar tablas de mapeo de conjuntos de caracteres. Esto ocurre cuando DCMTK fue compilado con la biblioteca oficonv (que es la predeterminada) y las tablas de mapeo no están integradas en la biblioteca (predeterminado cuando DCMTK utiliza bibliotecas compartidas).

Se espera que los archivos de tabla de mapeo estén en el directorio de datos de DCMTK (<i>DCMTK</i>). La variable de entorno DCMICONVPATH se puede usar para especificar una ubicación diferente. Si se especifica una ubicación diferente, esas tablas de mapeo también reemplazan cualquier tabla integrada.
