DESCRIPCIÓN

En la descripción aquí, TYPE se utiliza como marcador de posición para cualquiera de los tipos de datos de OpenSSL, como X509_CRL. Los parámetros de la función ppin y ppout generalmente se nombran como pp en las cabeceras, o como in y out.

Estas funciones convierten objetos de OpenSSL a y desde su codificación ASN.1/DER. A diferencia de las estructuras C que pueden tener punteros a sub-objetos internos, DER es una codificación serializada, adecuada para enviar por la red, escribir en un archivo, etc.

d2i_TYPE() intenta decodificar len bytes en *ppin. Si tiene éxito, se devuelve un puntero a la estructura TYPE y *ppin se incrementa al byte siguiente a los datos analizados. Si a no es NULL, entonces un puntero a la estructura devuelta también se escribe en *a. Si ocurrió un error, se devuelve NULL. El llamador conserva la propiedad del objeto devuelto y necesita liberarlo cuando ya no sea necesario, por ejemplo, usando X509_free() para objetos X509 o DSA_SIG_free() para objetos DSA_SIG.

En un retorno exitoso, si *a no es NULL, se asume que *a contiene una estructura TYPE válida y se intenta reutilizarla. Para las estructuras TYPE donde importa, es posible configurar un contexto de biblioteca en la estructura decodificada de esta manera (ver la sección EJEMPLOS). Sin embargo, el uso de la capacidad de "reutilización" para otros fines está fuertemente desaconsejado (ver ERRORES abajo, y la discusión en la sección VALORES DE RETORNO).

d2i_TYPE_bio() es similar a d2i_TYPE() excepto que intenta analizar datos del BIO bp.

d2i_TYPE_fp() es similar a d2i_TYPE() excepto que intenta analizar datos del puntero FILE fp.

i2d_TYPE() codifica la estructura apuntada por a en formato DER. Si ppout no es NULL, escribe los datos codificados en DER en el búfer en *ppout, y lo incrementa para que apunte después de los datos recién escritos. Si el valor de retorno es negativo, ocurrió un error, de lo contrario, devuelve la longitud de los datos codificados.

Si *ppout es NULL, se asignará memoria para un búfer y se escribirán los datos codificados en él. En este caso, *ppout no se incrementa y apunta al inicio de los datos recién escritos.

i2d_TYPE_bio() es similar a i2d_TYPE() excepto que escribe la codificación de la estructura a en el BIO bp y devuelve 1 para éxito y 0 para fallo.

i2d_TYPE_fp() es similar a i2d_TYPE() excepto que escribe la codificación de la estructura a en el puntero FILE fp y devuelve 1 para éxito y 0 para fallo.

Estas rutinas no cifran claves privadas y, por lo tanto, no ofrecen seguridad; use PEM_write_PrivateKey(3) o similar para escribir en archivos.

NOTAS

Las letras i y d en i2d_TYPE() significan "interno" (es decir, una estructura C interna) y "DER" respectivamente. Por lo tanto, i2d_TYPE() convierte de interno a DER.

Las funciones también pueden entender las formas BER.

La estructura TYPE real pasada a i2d_TYPE() debe ser una estructura TYPE válida y poblada; no puede simplemente alimentarse con una estructura vacía como la devuelta por TYPE_new().

Los datos codificados están en formato binario y pueden contener ceros incrustados. Por lo tanto, los punteros FILE o los BIO deben abrirse en modo binario. Funciones como strlen() no devolverán la longitud correcta de la estructura codificada.

Las formas en que *ppin y *ppout se incrementan después de la operación pueden atrapar al incauto. Consulte la sección ADVERTENCIAS para ver algunos errores comunes. La razón de este comportamiento de auto-incremento es reflejar un uso típico de las funciones ASN1: después de que una estructura se codifica o decodifica, se procesará otra después de ella.

Los siguientes puntos sobre los tipos de datos pueden ser útiles:

DHparams

DHxparams
Representa una estructura de parámetros DH de ANSI X9.42.

VALORES DE RETORNO

d2i_TYPE(), d2i_TYPE_bio() y d2i_TYPE_fp() devuelven una estructura TYPE válida o NULL si ocurre un error. Si se ha utilizado la capacidad de "reutilización" con una estructura válida pasada a través de a, entonces el objeto se libera en caso de error y *a se establece a NULL.

i2d_TYPE() devuelve el número de bytes codificados correctamente o un valor negativo si ocurre un error.

i2d_TYPE_bio() y i2d_TYPE_fp(), así como i2d_ASN1_bio_stream(), devuelven 1 para éxito y 0 si ocurre un error.

EJEMPLOS

Asignar y codificar la codificación DER de una estructura X509:

int len;
unsigned char *buf;
buf = NULL;
len = i2d_X509(x, &buf);
if (len < 0)
    /* error */

Intentar decodificar un búfer:

X509 *x;
unsigned char *buf;
const unsigned char *p;
int len;
/* Configurar buf y len para que apunten al búfer de entrada. */
p = buf;
x = d2i_X509(NULL, &p, len);
if (x == NULL)
    /* error */

Técnica alternativa:

X509 *x;
unsigned char *buf;
const unsigned char *p;
int len;
/* Configurar buf y len para que apunten al búfer de entrada. */
p = buf;
x = NULL;
if (d2i_X509(&x, &p, len) == NULL)
    /* error */

Configurar un contexto de biblioteca y una consulta de propiedad:

X509 *x;
unsigned char *buf;
const unsigned char *p;
int len;
OSSL_LIB_CTX *libctx = ....;
const char *propq = ....;
/* Configurar buf y len para que apunten al búfer de entrada. */
p = buf;
x = X509_new_ex(libctx, propq);
if (d2i_X509(&x, &p, len) == NULL)
    /* error, x fue liberado y se le asignó NULL (ver VALORES DE RETORNO) */

ADVERTENCIAS

El uso de una variable temporal es obligatorio. Un error común es intentar usar un búfer directamente de la siguiente manera:

int len;
unsigned char *buf;
len = i2d_X509(x, NULL);
buf = OPENSSL_malloc(len);
...
i2d_X509(x, &buf);
...
OPENSSL_free(buf);

Este código resultará en que buf aparentemente contenga basura porque se incrementó después de la llamada para apuntar después de los datos recién escritos. Además, buf ya no contendrá el puntero asignado por OPENSSL_malloc() y la llamada posterior a OPENSSL_free() probablemente causará un fallo.

Otra trampa a evitar es el mal uso del argumento a para d2i_TYPE():

X509 *x;
if (d2i_X509(&x, &p, len) == NULL)
    /* error */

Esto probablemente fallará en algún lugar de d2i_X509(). La razón es que la variable x no está inicializada y se intentará interpretar su valor (inválido) como una estructura X509, lo que típicamente causa una violación de segmentación. Si x se establece a NULL primero, esto no sucederá.

ERRORES

En algunas versiones de OpenSSL, el comportamiento de "reutilización" de d2i_TYPE() cuando *a es válido está roto y algunas partes de la estructura reutilizada pueden persistir si no están presentes en la nueva. Además, en versiones de OpenSSL anteriores a 1.1.0, cuando se utiliza el comportamiento de "reutilización" y ocurre un error, el comportamiento es inconsistente. Algunas funciones se comportaron como se describe aquí, mientras que otras no liberaron *a en caso de error y no establecieron *a a NULL.

Como resultado de los problemas anteriores, el comportamiento de "reutilización" está fuertemente desaconsejado.

i2d_TYPE() no devolverá un error en muchas versiones de OpenSSL; si los campos obligatorios no se inicializan debido a un error de programación, la estructura codificada puede contener datos inválidos u omitir los campos por completo y no será analizada por d2i_TYPE(). Esto puede solucionarse en el futuro, por lo que el código no debe asumir que i2d_TYPE () siempre tendrá éxito.

Cualquier función que codifique una estructura (i2d_TYPE(), i2d_TYPE_bio() o i2d_TYPE_fp()) puede devolver una codificación obsoleta si la estructura se ha modificado después de la deserialización o serialización previa. Esto se debe a que algunos objetos almacenan en caché la codificación por razones de eficiencia.
