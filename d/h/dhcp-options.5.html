NOMBRE

dhcp-options - Opciones del Protocolo de Configuración Dinámica de Host

DESCRIPCIÓN

El protocolo de Configuración Dinámica de Host permite al cliente recibir opciones del servidor DHCP que describen la configuración de red y los diversos servicios disponibles en la red. Al configurar dhcpd(8) o dhclient(8) , a menudo se deben declarar opciones. Aquí se documenta la sintaxis para declarar opciones, así como los nombres y formatos de las opciones que se pueden declarar.

REFERENCIA: DECLARACIONES DE OPCIONES

Las declaraciones de opción DHCP siempre comienzan con la palabra clave option , seguida de un nombre de opción y luego de los datos de la opción. Los nombres de las opciones y los formatos de los datos se describen a continuación. No es necesario especificar exhaustivamente todas las opciones DHCP; solo se deben especificar aquellas opciones que los clientes necesiten.

Los datos de las opciones vienen en una variedad de formatos, definidos a continuación:

El tipo de datos ip-address se puede introducir como una dirección IP explícita (por ejemplo, 239.254.197.10) o como un nombre de dominio (por ejemplo, haagen.isc.org). Al introducir un nombre de dominio, asegúrese de que ese nombre de dominio resuelva a una única dirección IP. Adicionalmente, tenga en cuenta que el software (dhcpd o dhclient) solo intentará resolver el nombre de dominio la primera vez que se necesite la opción. Por ejemplo, si la opción next-server se define como un nombre de dominio, dhcpd intentará resolverlo mientras responde a la primera consulta de cliente que dhcpd recibe después del inicio. Si la dirección del dominio cambia posteriormente, el software debe reiniciarse para recoger el cambio.

Los datos ip6-address especifican una dirección IPv6, como ::1 o 3ffe:bbbb:aaaa:aaaa::1.

El tipo de datos int32 especifica un entero con signo de 32 bits. El tipo de datos uint32 especifica un entero sin signo de 32 bits. Los tipos de datos int16 y uint16 especifican enteros con y sin signo de 16 bits. Los tipos de datos int8 y uint8 especifican enteros con y sin signo de 8 bits. Los enteros sin signo de 8 bits también se denominan a veces octetos.

El tipo de datos text especifica una cadena ASCII NVT, que debe estar encerrada entre comillas dobles; por ejemplo, para especificar una opción root-path, la sintaxis sería

option root-path "10.0.1.4:/var/tmp/rootfs";

El tipo de datos domain-name especifica un nombre de dominio, que no debe estar encerrado entre comillas dobles. El nombre de dominio se almacena como si fuera una opción de texto.

El tipo de datos domain-list especifica una lista de nombres de dominio, encerrados entre comillas dobles y separados por comas ("example.com", "foo.example.com").

El tipo de datos flag especifica un valor booleano. Los booleanos pueden ser verdadero o falso (o on u off, si eso le resulta más intuitivo).

El tipo de datos string especifica una cadena ASCII NVT encerrada entre comillas dobles, o una serie de octetos especificada en hexadecimal, separados por dos puntos. Por ejemplo:

  option dhcp-client-identifier "CLIENT-FOO";
o
  option dhcp-client-identifier 43:4c:49:45:54:2d:46:4f:4f;

ESTABLECIMIENTO DE VALORES DE OPCIONES USANDO EXPRESIONES

A veces es útil poder establecer el valor de una opción DHCP basándose en algún valor que el cliente ha enviado. Para hacer esto, puede usar la evaluación de expresiones. La página del manual dhcp-eval(5) describe cómo escribir expresiones. Para asignar el resultado de una evaluación a una opción, defina la opción de la siguiente manera:

  option my-option = expression ;

Por ejemplo:

  option hostname = binary-to-ascii (16, 8, "-",
                                     substring (hardware, 1, 6));

INCLUSIÓN DE DEFINICIONES DE OPCIONES

A partir de la versión 4.3.0, cuando ISC añade nuevas definiciones de opciones, esas definiciones se incluirán en el código basándose en la definición de un argumento para la RFC que define la opción en includes/site.h. Esto le proporciona un método para anular las definiciones de ISC si es necesario - por ejemplo, si ha definido previamente la opción con un formato diferente usando el mecanismo de DEFINICIÓN DE NUEVAS OPCIONES más adelante.

Por defecto, todas las opciones están habilitadas. Para deshabilitar una opción, debería editar el archivo includes/site.h y comentar la definición de la RFC correspondiente.

OPCIONES ESTÁNDAR DE DHCPV4

La documentación de las diversas opciones mencionadas a continuación se toma del último borrador de documento del IETF sobre opciones de DHCP. Es posible que las opciones no listadas a continuación aún no se hayan implementado, pero es posible usar tales opciones definiéndolas en el archivo de configuración. Por favor, consulte el encabezado DEFINICIÓN DE NUEVAS OPCIONES más adelante en este documento para obtener más información.

Algunas de las opciones documentadas aquí son generadas automáticamente por el servidor DHCP o por los clientes, y no pueden ser configuradas por el usuario. El valor de una opción de este tipo puede usarse en el archivo de configuración del agente del protocolo DHCP receptor (servidor o cliente), por ejemplo, en expresiones condicionales. Sin embargo, el valor de la opción no puede usarse en el archivo de configuración del agente emisor, porque el valor se determina solo después de que se ha procesado el archivo de configuración. En la siguiente documentación, tales opciones se mostrarán como "no configurables por el usuario".

Las opciones estándar son:

option all-subnets-local flag;

Esta opción especifica si el cliente puede asumir o no que todas las subredes de la red IP a la que está conectado el cliente usan el mismo MTU que la subred de esa red a la que el cliente está directamente conectado. Un valor de true indica que todas las subredes comparten el mismo MTU. Un valor de false significa que el cliente debe asumir que algunas subredes de la red directamente conectada pueden tener MTUs más pequeños.

option arp-cache-timeout uint32;

Esta opción especifica el tiempo de espera en segundos para las entradas de la caché ARP.

option associated-ip ip-address [, ip-address... ];

Esta opción es parte de la consulta de arrendamiento (lease query). Se usa para devolver todas las direcciones IP asociadas con un cliente DHCP determinado.

Esta opción no es configurable por el usuario.

option bcms-controller-address ip-address [, ip-address... ];

Esta opción configura una lista de direcciones IPv4 para usar como Servidores de Control de Difusión y Multidifusión ("BCMS").

option bcms-controller-names domain-list;

Esta opción contiene los nombres de dominio de los controladores locales de Servidores de Control de Difusión y Multidifusión ("BCMS") que el cliente puede usar.

option bootfile-name text;

Esta opción se usa para identificar un archivo de arranque (bootstrap). Si el cliente la soporta, debería tener el mismo efecto que la declaración filename . Es poco probable que los clientes BOOTP soporten esta opción. Algunos clientes DHCP la soportarán, y otros realmente la requieren.

option boot-size uint16;

Esta opción especifica la longitud en bloques de 512 octetos de la imagen de arranque predeterminada para el cliente.

option broadcast-address ip-address;

Esta opción especifica la dirección de difusión (broadcast) en uso en la subred del cliente. Los valores válidos para las direcciones de difusión se especifican en la sección 3.2.1.3 de STD 3 (RFC1122).

option capwap-ac-v4 ip-address [, ip-address ... ] ;

Una lista de direcciones IPv4 de los ACs de CAPWAP que el WTP puede usar. Las direcciones se enumeran en orden de preferencia.

Esta opción se incluye basándose en la RFC 5417.

option client-last-transaction-time uint32;

Esta opción es parte de la consulta de arrendamiento (lease query). Permite al receptor determinar la hora del último acceso por parte del cliente. El valor es una duración en segundos desde cuando el clientet última comunicación con el servidor DHCP.

Esta opción no es configurable por el usuario.

opción cookie-servers dirección-ip [, dirección-ip... ];

La opción cookie-servers especifica una lista de servidores de cookies RFC 865 disponibles para el cliente. Los servidores deben listarse en orden de preferencia.

opción default-ip-ttl uint8;

Esta opción especifica el tiempo de vida (time-to-live) por defecto que el cliente debe usar en los datagramas salientes.

opción default-tcp-ttl uint8;

Esta opción especifica el TTL por defecto que el cliente debe usar al enviar segmentos TCP. El valor mínimo es 1.

opción default-url cadena;

El formato y significado de esta opción no se describen en ningún documento de estándares, pero se afirma que es utilizada por Apple Computer. No se sabe qué pueden hacer razonablemente los clientes si se les proporciona esta opción. Úsela bajo su propio riesgo.

opción dhcp-client-identifier cadena;

Esta opción se puede usar para especificar un identificador de cliente DHCP en una declaración de host, para que dhcpd pueda encontrar el registro del host coincidiendo con el identificador del cliente.

Tenga en cuenta que algunos clientes DHCP, cuando se configuran con identificadores de cliente que son texto ASCII, antepondrán un cero al texto ASCII. Por lo tanto, es posible que deba escribir:

	opción dhcp-client-identifier "\0foo";
en lugar de: 
	opción dhcp-client-identifier "foo";

opción dhcp-lease-time uint32;

Esta opción se utiliza en una solicitud del cliente (DHCPDISCOVER o DHCPREQUEST) para permitir que el cliente solicite un tiempo de concesión para la dirección IP. En una respuesta del servidor (DHCPOFFER), un servidor DHCP utiliza esta opción para especificar el tiempo de concesión que está dispuesto a ofrecer.

Esta opción no es configurable directamente por el usuario en el servidor; consulte las opciones del servidor max-lease-time y default-lease-time en dhcpd.conf(5).

opción dhcp-max-message-size uint16;

Esta opción, cuando la envía el cliente, especifica el tamaño máximo de cualquier respuesta que el servidor envíe al cliente. Cuando se especifica en el servidor, si el cliente no envió una opción dhcp-max-message-size, se utiliza el tamaño especificado en el servidor. Esto funciona tanto para las respuestas BOOTP como para las DHCP.

opción dhcp-message texto;

Esta opción es utilizada por un servidor DHCP para proporcionar un mensaje de error a un cliente DHCP en un mensaje DHCPNAK en caso de fallo. Un cliente puede usar esta opción en un mensaje DHCPDECLINE para indicar por qué el cliente rechazó los parámetros ofrecidos.

Esta opción no es configurable por el usuario.

opción dhcp-message-type uint8;

Esta opción, enviada tanto por el cliente como por el servidor, especifica el tipo de mensaje DHCP contenido en el paquete DHCP. Los valores posibles (tomados directamente de RFC2132) son:

             1     DHCPDISCOVER
             2     DHCPOFFER
             3     DHCPREQUEST
             4     DHCPDECLINE
             5     DHCPACK
             6     DHCPNAK
             7     DHCPRELEASE
             8     DHCPINFORM

Esta opción no es configurable por el usuario.

opción dhcp-option-overload uint8;

Esta opción se utiliza para indicar que los campos ´sname´ o ´file´ del DHCP se están sobrecargando al usarlos para transportar opciones DHCP. Un servidor DHCP inserta esta opción si los parámetros devueltos superan el espacio habitual asignado para opciones.

Si esta opción está presente, el cliente interpreta los campos adicionales especificados después de concluir la interpretación de los campos de opción estándar.

Los valores legales para esta opción son:

             1     el campo ´file´ se utiliza para mantener opciones
             2     el campo ´sname´ se utiliza para mantener opciones
             3     ambos campos se utilizan para mantener opciones

Esta opción no es configurable por el usuario.

opción dhcp-parameter-request-list uint8 [, uint8... ];

Esta opción, cuando la envía el cliente, especifica qué opciones desea que el servidor devuelva. Normalmente, en el cliente DHCP de ISC, esto se hace utilizando la declaración request. Si el cliente no especifica esta opción, el servidor DHCP normalmente devolverá todas las opciones que sean válidas en el ámbito y que quepan en la respuesta. Cuando se especifica en el servidor, el servidor devuelve las opciones especificadas. Esto se puede usar para forzar a un cliente a aceptar opciones que no ha solicitado, y también se puede usar para adaptar la respuesta del servidor DHCP para clientes que pueden necesitar un conjunto más limitado de opciones que las que el servidor devolvería normalmente.

opción dhcp-rebinding-time uint32;

Esta opción especifica el número de segundos desde que un cliente obtiene una dirección hasta que el cliente pasa al estado REBINDING.

Esta opción es configurable por el usuario, pero se ignorará si el valor es mayor o igual al tiempo de concesión.

Para facilitar la migración de DHCPv4+DHCPv6 en el futuro, cualquier valor configurado en esta opción también se utiliza como tiempo "T1" (renovar) de DHCPv6.

opción dhcp-renewal-time uint32;

Esta opción especifica el número de segundos desde que un cliente obtiene una dirección hasta que el cliente pasa al estado RENEWING.

Esta opción es configurable por el usuario, pero se ignorará si el valor es mayor o igual al tiempo de renegociación o al tiempo de concesión.

Para facilitar la migración de DHCPv4+DHCPv6 en el futuro, cualquier valor configurado en esta opción también se utiliza como tiempo "T2" (renegociar) de DHCPv6.

opción dhcp-requested-address dirección-ip;

Esta opción es utilizada por el cliente en un DHCPDISCOVER para solicitar que se le asigne una dirección IP particular.

Esta opción no es configurable por el usuario.

opción dhcp-server-identifier dirección-ip;

Esta opción se utiliza en los mensajes DHCPOFFER y DHCPREQUEST, y opcionalmente se puede incluir en los mensajes DHCPACK y DHCPNAK. Los servidores DHCP incluyen esta opción en el DHCPOFFER para permitir que el cliente distinga entre ofertas de concesión. Los clientes DHCP utilizan el contenido del campo ´server identifier´ como dirección de destino para cualquier mensaje DHCP enviado unicast al servidor DHCP. Los clientes DHCP también indican cuál de varias ofertas de concesión se está aceptando al incluir esta opción en un mensaje DHCPREQUEST.

El valor de esta opción es la dirección IP del servidor.

Esta opción no es configurable directamente por el usuario. Consulte la opción del servidor server-identifier en dhcpd.conf(5).

opción domain-name texto;

Esta opción especifica el nombre de dominio que el cliente debe usar al resolver nombres de host a través del Sistema de Nombres de Dominio.

opción domain-name-servers dirección-ip [, dirección-ip... ];

La opción domain-name-servers especifica una lista de servidores de nombres del Sistema de Nombres de Dominio (STD 13, RFC 1035) disponibles para el cliente. Los servidores deben listarse en orden de preferencia.

opción domain-search lista-dominio;

La opción domain-search especifica una ´lista de búsqueda´ de Nombres de Dominio que será utilizada por el cliente para localizar nombres de dominio no completamente cualificados. La diferencia entre esta opción y el uso histórico de la opción domain-name para los mismos fines es que esta opción se codifica en etiquetas comprimidas RFC1035 en el cable. Por ejemplo:

  opción domain-search "ejemplo.com", "ventas.ejemplo.com",
                       "ing.ejemplo.com";

opción extensions-path texto;

Esta opción especifica el nombre de un archivo que contiene opciones adicionales que se interpretarán de acuerdo con el formato de opción DHCP especificado en RFC2132.

opción finger-server dirección-ip [, dirección-ip... ];

La opción finger-server especifica una lista de servidores Finger disponibles para el cliente. Los servidores deben listarse en orden de preferencia.

opción font-servers dirección-ip [, dirección-ip... ];

Esta opción especifica una lista de servidores de fuentes X Window System disponibles para el cliente. Los servidores deben listarse en orden de preferencia.

opción geoconf-civic cadena;

Una cadena para contener la estructura cívica geoconf.

Esta opción se incluye según RFC 4776.

opción host-name cadena;

Esta opción especifica el nombre del cliente. El nombre puede o no estar cualificado con el nombre de dominio local (es preferible usar la opción domain-name para especificar el nombre de dominio). Consulte RFC 1035 para las restricciones de conjunto de caracteres. Esta opción solo es tenida en cuenta por dhclient-script(8) si el nombre de host de la máquina cliente no está configurado.

opción ieee802-3-encapsulation bandera;

Esta opción especifica si el cliente debe usar encapsulación Ethernet Versión 2 (RFC 894) o IEEE 802.3 (RFC 1042) si la interfaz es una Ethernet. Un valor falso indica que el cliente debe usar encapsulación RFC 894. Un valor verdadero significa que el cliente debe usar encapsulación RFC 1042.

opción ien116-name-servers dirección-ip [, dirección-ip... ];

La opción ien116-name-servers especifica una lista de servidores de nombres IEN 116 disponibles para el cliente. Los servidores deben listarse en orden de preferencia.

opción impress-servers dirección-ip [, dirección-ip... ];

La opción impress-server especifica una lista de servidores Imagen Impress disponibles para el cliente. Los servidores deben listarse en orden de preferencia.

OPCIÓN DE INFORMACIÓN DEL AGENTE RELAY

Un borrador de la IETF, draft-ietf-dhc-agent-options-11.txt, define una serie de opciones encapsuladas que un agente relay puede agregar a un paquete DHCP al retransmitirlo al servidor DHCP. El servidor puede entonces tomar decisiones de asignación de direcciones (o cualquier otra decisión que desee) basándose en estas opciones. El servidor también devuelve estas opciones en cualquier respuesta que envíe a través del agente relay, para que el agente relay pueda usar la información de estas opciones para fines de entrega o contabilidad.

El borrador actual define dos opciones. Para hacer referencia a estas opciones en el servidor dhcp, especifique el nombre del espacio de opciones, "agent", seguido de un punto, seguido del nombre de la opción. Normalmente no es útil definir valores para estas opciones en el servidor, aunque es permisible. Estas opciones no son compatibles en el cliente.

option agent.circuit-id string;

La subopción `circuit-id` codifica un identificador local del agente del circuito desde el cual se recibió un paquete DHCP de cliente a servidor. Está destinada a ser utilizada por agentes para retransmitir respuestas DHCP al circuito correcto. El formato de esta opción está definido actualmente como dependiente del proveedor, y probablemente seguirá siéndolo, aunque el borrador actual permite la posibilidad de estandarizar el formato en el futuro.

option agent.remote-id string;

La subopción `remote-id` codifica información sobre el extremo remoto de un circuito. Ejemplos de lo que podría contener incluyen información de identificación de llamada, información de nombre de usuario, dirección ATM remota, ID de módem por cable y cosas similares. En principio, el significado no está bien especificado, y generalmente debe asumirse como un objeto opaco que está administrativamente garantizado como único para un extremo remoto particular de un circuito.

option agent.DOCSIS-device-class uint32;

La subopción `DOCSIS-device-class` está destinada a transmitir información sobre el punto final del host, el hardware y el software, de los cuales el sistema operativo del host o el servidor DHCP pueden no ser conscientes de otra manera (pero el relay puede distinguir). Esto se implementa como un campo de 32 bits (4 octetos), donde cada bit representa una bandera que describe el host de una de estas maneras. Hasta ahora, solo el bit cero (siendo el bit menos significativo) está definido en RFC3256. Si este bit se establece en uno, el host se considera un módem por cable controlado por CPE (CCCM). Todos los demás bits están reservados.

option agent.link-selection ip-address;

La subopción `link-selection` es proporcionada por los agentes relay para informar a los servidores de a qué subred está realmente conectado el cliente. Esto es útil en los casos en que la `giaddr` (a la que deben enviarse las respuestas al agente relay) no está en la misma subred que el cliente. Cuando esta opción está presente en un paquete de un agente relay, el servidor DHCP utilizará su contenido para encontrar una subred declarada en la configuración, y desde aquí dará un paso atrás a cualquier red compartida en la que pueda definirse la subred; se le puede dar al cliente cualquier dirección dentro de esa red compartida, como sea apropiado normalmente.

LAS SUBOPCIONES FQDN DEL CLIENTE

La opción Client FQDN, actualmente definida en el borrador de Internet draft-ietf-dhc-fqdn-option-00.txt, aún no es un estándar, pero ya se utiliza con suficiente amplitud como para que la hayamos implementado. Debido a la complejidad del formato de la opción, la hemos implementado como un espacio de subopciones en lugar de una única opción. En general, esta opción no debe ser configurada por el usuario; en su lugar, debe utilizarse como parte de un sistema de actualización automática de DNS.

option fqdn.no-client-update flag;

Cuando el cliente envía esto, si es verdadero, significa que el cliente no intentará actualizar su registro A. Cuando lo envía el servidor al cliente, significa que el cliente *no debe* actualizar su propio registro A.

option fqdn.server-update flag;

Cuando el cliente envía esto al servidor, solicita que el servidor actualice su registro A. Cuando lo envía el servidor, significa que el servidor ha actualizado (o está a punto de actualizar) el registro A del cliente.

option fqdn.encoded flag;

Si es verdadero, esto indica que el nombre de dominio incluido en la opción está codificado en formato binario de DNS, en lugar de como texto ASCII plano. El cliente normalmente establece esto en falso si no admite el formato binario de DNS en la opción FQDN. El servidor siempre debe devolver el mismo valor que envió el cliente. Cuando este valor se establece en el lado de la configuración, controla el formato en el que se codifica la subopción `fqdn.fqdn`.

option fqdn.rcode1 flag;

option fqdn.rcode2 flag;

Estas opciones especifican el resultado de las actualizaciones de los registros A y PTR, respectivamente, y solo son enviadas por el servidor DHCP al cliente DHCP. Los valores de estos campos son los definidos en la especificación del protocolo DNS.

option fqdn.fqdn text;

Especifica el nombre de dominio que el cliente desea usar. Puede ser un nombre de dominio completamente calificado o una etiqueta única. Si no hay un carácter de punto (.) al final del nombre, no está completamente calificado, y el servidor generalmente actualizará ese nombre en algún dominio definido localmente.

THE FQDN SUBOPTIONS

These options are for the client fully qualified domain name. They should be set using the fqdn option statement. The server should not attempt to set any of these options - they are for client use only.

option fqdn.fqdn string;

This option indicates the client's fully qualified domain name. If the client's hostname is set, it will be translated into a fully qualified domain name using information discovered via DHCP.

option fqdn.hostname --never set--;

This option should never be set, but it can be read back using the option and config-option operators in an expression, in which case it returns the first label in the fqdn.fqdn suboption - for example, if the value of fqdn.fqdn is "foo.example.com.", then fqdn.hostname will be "foo".

option fqdn.domainname --never set--;

This option should never be set, but it can be read back using the option and config-option operators in an expression, in which case it returns all labels after the first label in the fqdn.fqdn suboption - for example, if the value of fqdn.fqdn is "foo.example.com.", then fqdn.domainname will be "example.com.". If this suboption value is not set, it means that an unqualified name was sent in the fqdn option, or that no fqdn option was sent at all.

If you wish to use any of these suboptions, we strongly recommend that you refer to the Client FQDN option draft (or standard, when it becomes a standard) - the documentation here is sketchy and incomplete in comparison, and is just intended for reference by people who already understand the Client FQDN option specification.

STANDARD DHCPV6 OPTIONS

DHCPv6 options differ from DHCPv4 options partially due to using 16-bit code and length tags, but semantically zero-length options are legal in DHCPv6, and multiple options are treated differently. Whereas in DHCPv4 multiple options would be concatenated to form one option, in DHCPv6 they are expected to be individual instantiations. Understandably, many options are not "allowed" to have multiple instances in a packet - normally these are options which are digested by the DHCP protocol software, and not by users or applications.

option dhcp6.client-id string;

This option specifies the client's DUID identifier. DUIDs are similar but different from DHCPv4 client identifiers - there are documented duid types:

duid-llt

duid-en

duid-ll

This value should not be configured, but rather is provided by clients and treated as an opaque identifier key blob by servers.

option dhcp6.server-id string;

This option specifies the server's DUID identifier. One may use this option to configure an opaque binary blob for your server's identifier.

option dhcp6.ia-na string;

The Identity Association for Non-temporary Addresses (ia-na) carries assigned addresses that are not temporary addresses for use by the DHCPv6 client. This option is produced by the DHCPv6 server software, and should not be configured.

option dhcp6.ia-ta string;

The Identity Association for Temporary Addresses (ia-ta) carries temporary addresses, which may change upon every renewal. There is no support for this in the current DHCPv6 software.

option dhcp6.ia-addr string;

The Identity Association Address option is encapsulated inside ia-na or ia-ta options in order to represent addresses associated with those IA's. These options are manufactured by the software, so should not be configured.

option dhcp6.oro uint16 [, uint16,...];

The Option Request Option ("ORO") is the DHCPv6 equivalent of the parameter-request-list. Clients supply this option to ask servers to reply with options relevant to their needs and use. This option must not be directly configured, the request syntax in dhclient.conf (5) should be used instead.

option dhcp6.preference uint8;

The preference option informs a DHCPv6 client which server is ´preferred´ for use on a given subnet. This preference is only applied during the initial stages of configuration - once a client is bound to an IA, it will remain bound to that IA until it is no longer valid or has expired. This value may be configured on the server, and is digested by the client software.

option dhcp6.elapsed-time uint16;

The elapsed-time option is constructed by the DHCPv6 client software, and is potentially consumed by intermediaries. This option should not be configured.

option dhcp6.relay-msg string;

The relay-msg option is constructed by intervening DHCPv6 relay agent software. This option is entirely used by protocol software, and is not meant for user configuration.

option dhcp6.unicast ip6-address;

The unicast option is provided by DHCPv6 servers which are willing (or prefer) to receive Request, Renew, Decline, and Release packets from their clients via unicast. Normally, DHCPv6 clients will multicast these messages. Per RFC 3315, the server will reject a unicast message received from a client unless it previously sent (or would have sent) the unicast option to that client. This option may be configured on the server at the global and shared network level. When a unicast message is received, the server will check for an applicable definition of the unicast option. If such an option is found the message will be accepted, if not it will be rejected.

ACCESO A LAS OPCIONES DE RETRANSMISIÓN DHCPV6

v6relay (relay-number, option) Esta opción permite el acceso a una opción que ha sido añadida a un paquete por un agente de retransmisión. El valor de relay-number selecciona la retransmisión a examinar y option es la opción a encontrar. En DHCPv6, cada retransmisión encapsula el mensaje anterior completo en una opción, añade sus propias opciones (si las hay) y envía el resultado. El RFC especifica un límite de 32 saltos. Un relay-number de 0 no hace nada y significa no examinar las retransmisiones. 1 es la retransmisión más cercana al cliente, 2 sería la siguiente desde el cliente y así sucesivamente. Cualquier valor mayor que el número máximo de saltos es el que está más cerca del servidor, independientemente del número. Para usar esta opción en una declaración de clase, tendrías algo como esto:

match if v6relay(1, option dhcp6.subscriber-id) = "client_1";

DEFINIR NUEVAS OPCIONES

Los clientes y servidores DHCP de Internet Systems Consortium proporcionan la capacidad de definir nuevas opciones. Cada opción DHCP tiene un nombre, un código y una estructura. El nombre lo usas tú para referirte a la opción. El código es un número, utilizado por el servidor y cliente DHCP para referirse a una opción. La estructura describe cómo es el contenido de una opción.

Para definir una nueva opción, debes elegir un nombre que no esté en uso para otra opción; por ejemplo, no puedes usar "host-name" porque el protocolo DHCP ya define una opción host-name, que se documenta anteriormente en esta página del manual. Si un nombre de opción no aparece en esta página del manual, puedes usarlo, pero probablemente sea una buena idea poner alguna cadena única al principio para estar seguro de que las opciones futuras no usurpen tu nombre. Por ejemplo, podrías definir una opción, "local-host-name", sintiendo cierta confianza en que ninguna opción DHCP oficial comenzará con "local".

Una vez que hayas elegido un nombre, debes elegir un código. Todos los códigos entre 224 y 254 están reservados como opciones DHCP de ´ámbito local´, por lo que puedes elegir cualquiera de ellos para tu sitio (no para tu producto/aplicación). En RFC3942, el espacio de ámbito local se trasladó de empezar en 128 a empezar en 224. En la práctica, algunos fabricantes han interpretado el protocolo de forma bastante laxa y han utilizado valores de código de opción superiores a 128. No hay forma real de evitar este problema, y se pensó que no causaría demasiados problemas en la práctica. Si te encuentras con un código de opción documentado por un fabricante en el espacio de ámbito local nuevo o antiguo, ponte en contacto con tu fabricante e infórmale sobre rfc3942.

La estructura de una opción es simplemente el formato en el que aparecen los datos de la opción. El servidor DHCP de ISC actualmente admite algunos tipos simples, como enteros, booleanos, cadenas y direcciones IP, y también admite la capacidad de definir matrices de tipos simples o matrices de secuencias fijas de tipos.

Las nuevas opciones se declaran de la siguiente manera:

option new-name code new-code = definition ;

Los valores de new-name y new-code deben ser el nombre que has elegido para la nueva opción y el código que has elegido. La definition debe ser la definición de la estructura de la opción.

Las siguientes definiciones de tipos de opciones simples son compatibles:

BOOLEAN

option new-name code new-code = boolean ;

Una opción de tipo booleano es una bandera con un valor de activado o desactivado (o verdadero o falso). Así que un uso de ejemplo del tipo booleano sería:

option use-zephyr code 180 = boolean;
option use-zephyr on;
INTEGER

option new-name code new-code = sign integer width ;

El token sign debe estar en blanco, unsigned o signed. El ancho puede ser 8, 16 o 32, y se refiere al número de bits en el entero. Así, por ejemplo, las siguientes dos líneas muestran una definición de la opción sql-connection-max y su uso:

option sql-connection-max code 192 = unsigned integer 16;
option sql-connection-max 1536;
IP-ADDRESS

option new-name code new-code = ip-address ;

Una opción cuya estructura es una dirección IP se puede expresar como un nombre de dominio o como un cuádruple de puntos. Así que el siguiente es un ejemplo de uso del tipo ip-address:

option sql-server-address code 193 = ip-address;
option sql-server-address sql.example.com;
IP6-ADDRESS

option new-name code new-code = ip6-address ;

Una opción cuya estructura es una dirección IPv6 debe expresarse como una dirección IPv6 válida. El siguiente es un ejemplo de uso del tipo ip6-address:

option dhcp6.some-server code 1234 = array of ip6-address;
option dhcp6.some-server 3ffe:bbbb:aaaa:aaaa::1, 3ffe:bbbb:aaaa:aaaa::2;

TEXT

option new-name code new-code = text ;

Una opción cuyo tipo es texto codificará una cadena de texto ASCII. Por ejemplo:

option sql-default-connection-name code 194 = text;
option sql-default-connection-name "PRODZA";

DATA STRING

option new-name code new-code = string ;

Una opción cuyo tipo es una cadena de datos es esencialmente solo una colección de bytes, y se puede especificar como texto entre comillas, como el tipo de texto, o como una lista de contenidos hexadecimales separados por dos puntos cuyos valores deben estar entre 0 y FF. Por ejemplo:

option sql-identification-token code 195 = string;
option sql-identification-token 17:23:19:a6:42:ea:99:7c:22;

DOMAIN-LIST

option new-name code new-code = domain-list [compressed] ;

Una opción cuyo tipo es domain-list es una lista de nombres de dominio formateada según RFC1035 (en la red, "Formato DNS"), separada por etiquetas raíz. La palabra clave opcional compressed indica si la opción debe comprimirse en relación con el inicio del contenido de la opción (no con el contenido del paquete).

En caso de duda, omite la palabra clave compressed. Cuando el software reciba una opción que esté comprimida y se omita la palabra clave compressed, aún así descomprimirá la opción (en relación con el campo de contenido de la opción). La palabra clave solo controla si los paquetes transmitidos se comprimen o no.

Tenga en cuenta que cuando las opciones formateadas como domain-list se emiten como variables de entorno al script dhclient-script(8), se utiliza el mecanismo de escape estándar de DNS: son decimales. Esto es apropiado para su uso directo en, por ejemplo, /etc/resolv.conf.

ENCAPSULATION

option new-name code new-code = encapsulate identifier ;

Una opción cuyo tipo es encapsulate encapsulará el contenido del espacio de opciones especificado en identifier. Ejemplos de opciones encapsuladas en el protocolo DHCP tal como existe actualmente incluyen la opción vendor-encapsulated-options, la opción netware-suboptions y la opción relay-agent-information.

option space local;
option local.demo code 1 = text;
option local-encapsulation code 197 = encapsulate local;
option local.demo "demo";

ARRAYS

Las opciones pueden contener matrices de cualquiera de los tipos anteriores, excepto para los tipos de cadena de texto y cadena de datos, que actualmente no son compatibles en matrices. Un ejemplo de definición de matriz es el siguiente:

option kerberos-servers code 200 = array of ip-address;
option kerberos-servers 10.20.10.1, 10.20.11.1;
RECORDS

Las opciones también pueden contener estructuras de datos que consisten en una secuencia de tipos de datos, que a veces se denomina tipo de registro. Por ejemplo:

option contrived-001 code 201 = { boolean, integer 32, text };
option contrived-001 on 1772 "contrivance";
También es posible tener opciones que sean matrices de registros, por ejemplo: 
option new-static-routes code 201 = array of {
	ip-address, ip-address, ip-address, integer 8 };
option static-routes
	10.0.0.0 255.255.255.0 net-0-rtr.example.com 1,
	10.0.1.0 255.255.255.0 net-1-rtr.example.com 1,
	10.2.0.0 255.255.224.0 net-2-0-rtr.example.com 3;

OPCIONES ENCAPSULADAS POR EL FABRICANTE

El protocolo DHCP define la opción vendor-encapsulated-options, que permite a los fabricantes definir sus propias opciones que se enviarán encapsuladas en una opción DHCP estándar. También define la opción Vendor Identified Vendor Sub Options ("VIVSO"), y el protocolo DHCPv6 define la opción Vendor-specific Information Option ("VSIO"). El formato de todas estas opciones suele ser internamente una cadena de opciones, de forma similar a otras opciones DHCP normales. Las opciones VIVSO y VSIO difieren en que contienen opciones que corresponden a números Enterprise-ID de fabricante (asignados por IANA), que a su vez contienen opciones según las especificaciones de cada fabricante. Necesitarás consultar la documentación de tu fabricante para poder formar opciones según sus especificaciones.

El valor de estas opciones se puede establecer en

de dos maneras. La primera forma es simplemente especificar los datos directamente, usando una cadena de texto o una lista de valores hexadecimales separados por dos puntos. Para obtener ayuda en la formación de estas cadenas, por favor, consulte RFC2132 para la Opción de Información Específica del Proveedorde DHCPv4 , RFC3925 para la Opción de Sub-opciones de Proveedor Identificado por el Proveedor de DHCPv4, o RFC3315 para la Opción de Información Específica del Proveedor de DHCPv6. Por ejemplo:

option vendor-encapsulated-options
    2:4:
	AC:11:41:1:
    3:12:
	73:75:6e:64:68:63:70:2d:73:65:72:76:65:72:31:37:2d:31:
    4:12:
	2f:65:78:70:6f:72:74:2f:72:6f:6f:74:2f:69:38:36:70:63;
option vivso
    00:00:09:bf:0E:
	01:0c:
	    48:65:6c:6c:6f:20:77:6f:72:6c:64:21;
option dhcp6.vendor-opts
    00:00:09:bf:
	00:01:00:0c:
	    48:65:6c:6c:6f:20:77:6f:72:6c:64:21;

La segunda forma de establecer el valor de estas opciones es hacer que el servidor DHCP genere un búfer de opciones específico del proveedor. Para hacer esto, usted debe hacer cuatro cosas: definir un espacio de opciones, definir algunas opciones en ese espacio de opciones, proporcionar valores para ellas y especificar que ese espacio de opciones debe usarse para generar la opción relevante.

Para definir un nuevo espacio de opciones en el que se puedan almacenar las opciones del proveedor, use la declaración de espacio de opciones:

option space nombre [ [ code width número ] [ length width número ] [ hash size número ] ] ;

Donde los números que siguen a code width, length width, y hash size identifican respectivamente el número de bytes utilizados para describir los códigos de opción, las longitudes de opción, y el tamaño en cubetas de las tablas hash para mantener las opciones en este espacio (la mayoría de los espacios de opciones DHCPv4 usan códigos y longitudes de 1 byte, que es el valor predeterminado, mientras que la mayoría de los espacios de opciones DHCPv6 usan códigos y longitudes de 2 bytes).

Los anchos de código y longitud se utilizan en el protocolo DHCP - usted debe configurar estos números para que coincidan con el espacio de opciones aplicable que está configurando. Cada uno tiene un valor predeterminado de 1. Los valores válidos para los anchos de código son 1, 2 o 4. Los valores válidos para los anchos de longitud son 0, 1 o 2. La mayoría de los espacios de opciones DHCPv4 usan códigos y longitudes de 1 byte, que es el valor predeterminado, mientras que la mayoría de los espacios de opciones DHCPv6 usan códigos y longitudes de 2 bytes. Una longitud de cero bytes produce opciones similares a la Opción de Información Específica del Proveedor de DHCPv6 - ¡pero no sus contenidos!

Los valores predeterminados del tamaño del hash dependen del ancho de código seleccionado, y pueden ser 254 o 1009. Los valores válidos van entre 1 y 65535. Tenga en cuenta que cuanto más alto configure este valor, más memoria se utilizará. Se considera una buena práctica configurar un valor que sea ligeramente mayor que el número estimado de opciones que planea configurar dentro del espacio. En versiones anteriores de ISC DHCP (hasta e incluyendo DHCP 3.0.*), este valor estaba fijado en 9973.

El nombre puede entonces usarse en las definiciones de opciones, como se describe anteriormente en este documento. Por ejemplo:

option space SUNW code width 1 length width 1 hash size 3;
option SUNW.server-address code 2 = ip-address;
option SUNW.server-name code 3 = text;
option SUNW.root-path code 4 = text;
option space ISC code width 1 length width 1 hash size 3;
option ISC.sample code 1 = text;
option vendor.ISC code 2495 = encapsulate vivso-sample;
option vendor-class.ISC code 2495 = text;
option ISC.sample "configuration text here";
option vendor-class.ISC "vendor class here";
option space docsis code width 2 length width 2 hash size 17;
option docsis.tftp-servers code 32 = array of ip6-address;
option docsis.cablelabs-configuration-file code 33 = text;
option docsis.cablelabs-syslog-servers code 34 = array of ip6-address;
option docsis.device-id code 36 = string;
option docsis.time-servers code 37 = array of ip6-address;
option docsis.time-offset code 38 = signed integer 32;
option vsio.docsis code 4491 = encapsulate docsis;
Una vez que haya definido un espacio de opciones y el formato de algunas opciones, puede configurar ámbitos que definan valores para esas opciones, y puede decir cuándo usarlas. Por ejemplo, suponga que desea manejar dos clases diferentes de clientes. Usando la definición del espacio de opciones mostrada en el ejemplo anterior, usted puede enviar valores de opción diferentes a diferentes clientes basándose en la opción vendor-class-identifier que los clientes envían, de la siguiente manera: 
class "vendor-classes" {
  match option vendor-class-identifier;
}
subclass "vendor-classes" "SUNW.Ultra-5_10" {
  vendor-option-space SUNW;
  option SUNW.root-path "/export/root/sparc";
}
subclass "vendor-classes" "SUNW.i86pc" {
  vendor-option-space SUNW;
  option SUNW.root-path "/export/root/i86pc";
}
option SUNW.server-address 172.17.65.1;
option SUNW.server-name "sundhcp-server17-1";
option vivso-sample.sample "Hello world!";
option docsis.tftp-servers ::1;

Como puede ver en el ejemplo anterior, se aplican las reglas normales de alcance, por lo que puede definir valores que sean globales en el ámbito global, y solo definir valores que sean específicos de una clase particular en el ámbito local. La declaración vendor-option-space le dice al servidor DHCP que use opciones en el espacio de opciones SUNW para construir la opción vendor-encapsulated-options de DHCPv4. Esta es una limitación de esa opción - las opciones VIVSO de DHCPv4 y VSIO de DHCPv6 pueden tener múltiples definiciones de proveedor todas a la vez (incluso transmitidas al mismo cliente), por lo que no es necesario configurar esto.
