dhclient.conf(5) Manual de Formatos de Archivo dhclient.conf(5)

NOMBRE

dhclient.conf - Archivo de configuración del cliente DHCP

DESCRIPCIÓN

El archivo dhclient.conf contiene información de configuración para dhclient, el Cliente DHCP del Internet Systems Consortium.

El archivo dhclient.conf es un archivo de texto ASCII de formato libre. Es analizado por el analizador descendente recursivo integrado en dhclient. El archivo puede contener pestañas y saltos de línea adicionales con fines de formato. Las palabras clave en el archivo no distinguen entre mayúsculas y minúsculas. Los comentarios pueden colocarse en cualquier lugar del archivo (excepto dentro de comillas). Los comentarios comienzan con el carácter # y terminan en el final de la línea.

El archivo dhclient.conf se puede utilizar para configurar el comportamiento del cliente de una amplia variedad de formas: temporización del protocolo, información solicitada al servidor, información requerida del servidor, valores predeterminados a usar si el servidor no proporciona cierta información, valores con los que anular la información proporcionada por el servidor, o valores para anteponer o agregar a la información proporcionada por el servidor. El archivo de configuración también puede preinicializarse con direcciones para usar en redes que no tienen servidores DHCP.

TEMPORIZACIÓN DEL PROTOCOLO

El comportamiento de temporización del cliente no necesita ser configurado por el usuario. Si el usuario no proporciona ninguna configuración de temporización, se utilizará por defecto un comportamiento de temporización bastante razonable, uno que resulta en actualizaciones bastante oportunas sin imponer una carga excesiva en el servidor.

Si es necesario, las siguientes instrucciones se pueden utilizar para ajustar el comportamiento de temporización del cliente DHCPv4. El protocolo DHCPv6 proporciona valores para usar y actualmente no son configurables.

La timeout instrucción


timeout tiempo;

La timeout instrucción determina la cantidad de tiempo que debe pasar entre el momento en que el cliente comienza a intentar determinar su dirección y el momento en que decide que no podrá contactar a un servidor. Por defecto, este tiempo de espera es de sesenta segundos. Después de que haya expirado el tiempo de espera, si hay algún arrendamiento estático definido en el archivo de configuración, o algún arrendamiento restante en la base de datos de arrendamientos que aún no haya expirado, el cliente recorrerá estos arrendamientos intentando validarlos, y si encuentra uno que parezca válido, usará la dirección de ese arrendamiento. Si no hay arrendamientos estáticos válidos ni arrendamientos sin expirar en la base de datos de arrendamientos, el cliente reiniciará el protocolo después del intervalo de reintento definido.

La retry instrucción


retry tiempo;

La retry instrucción determina el tiempo que debe pasar después de que el cliente haya determinado que no hay un servidor DHCP presente antes de que intente nuevamente contactar a un servidor DHCP. Por defecto, son cinco minutos.

La select-timeout instrucción


select-timeout tiempo;

Es posible (algunos dirían deseable) que haya más de un servidor DHCP sirviendo una red determinada. En este caso, es posible que un cliente reciba más de una oferta en respuesta a su mensaje inicial de descubrimiento de arrendamiento. Puede que una de estas ofertas sea preferible a la otra (por ejemplo, una oferta puede tener la dirección que el cliente usó previamente, y la otra puede no tenerla).

La select-timeout es el tiempo después de que el cliente envía su primera solicitud de descubrimiento de arrendamiento en el que deja de esperar ofertas de los servidores, asumiendo que ha recibido al menos una de esas ofertas. Si no se han recibido ofertas antes de que select-timeout haya expirado, el cliente aceptará la primera oferta que llegue.

Por defecto, el select-timeout es de cero segundos, es decir, el cliente tomará la primera oferta que vea.

La reboot instrucción


reboot tiempo;

Cuando se reinicia el cliente, primero intenta recuperar la última dirección que tenía. Esto se llama el estado INIT-REBOOT. Si todavía está conectado a la misma red a la que estaba conectado cuando se ejecutó por última vez, esta es la forma más rápida de comenzar. La reboot instrucción establece el tiempo que debe transcurrir después de que el cliente intente por primera vez recuperar su dirección antigua antes de que se rinda e intente descubrir una dirección nueva. Por defecto, el tiempo de espera de reinicio es de diez segundos.

La backoff-cutoff instrucción


backoff-cutoff tiempo;

El cliente utiliza un algoritmo de retroceso exponencial con algo de aleatoriedad, de modo que si muchos clientes intentan configurarse al mismo tiempo, no harán sus peticiones al unísono. La backoff-cutoff instrucción determina la cantidad máxima de tiempo que se le permite al cliente retroceder, el valor real se evaluará aleatoriamente entre 1/2 y 1 1/2 veces el tiempo especificado. Por defecto es de quince segundos.

La initial-interval instrucción


initial-interval tiempo;

La initial-interval instrucción establece la cantidad de tiempo entre el primer intento de contactar a un servidor y el segundo intento de contactar a un servidor. Cada vez que se envía un mensaje, el intervalo entre mensajes se incrementa en dos veces el intervalo actual multiplicado por un número aleatorio entre cero y uno. Si es mayor que la cantidad de backoff-cutoff, se establece en esa cantidad. Por defecto es de diez segundos.

La instrucción initial-delay


initial-delay tiempo;

El parámetro initial-delay establece el tiempo máximo que el cliente puede esperar después del inicio antes de comenzar la primera transmisión. De acuerdo con la Sección 4.4.1 de la RFC2131, el cliente debe esperar un tiempo aleatorio entre el inicio y la primera transmisión real. Las versiones anteriores del cliente DHCP de ISC solían esperar un tiempo aleatorio de hasta 5 segundos, pero eso no era deseable debido a su impacto en el tiempo de inicio. Como tal, las nuevas versiones tienen el retardo inicial inicial establecido por defecto en 0. Para restaurar el comportamiento anterior, establezca initial-delay en 5.

SELECCIÓN DE ARRENDAMIENTOS DHCPv6

En el protocolo DHCPv6, el cliente esperará una pequeña cantidad de tiempo para permitir que lleguen los mensajes ADVERTISE de múltiples servidores. Luego necesitará elegir entre todos los mensajes que puedan haber llegado antes de proceder a hacer una solicitud al servidor seleccionado.

El primer criterio de selección es el conjunto de opciones y direcciones en el mensaje. Los mensajes que no incluyan una opción especificada como requerida recibirán una puntuación de 0 y no se utilizarán. Si se proporciona la opción -R en la línea de comandos, los mensajes que no incluyan el número correcto de enlaces (IA-NA, IA-TA o IA-PD) serán descartados.

El siguiente criterio es el valor de preferencia del mensaje. Se utilizará el valor de preferencia más alto incluso si están disponibles arrendamientos con mejores direcciones u opciones.

Finalmente, se puntuará el arrendamiento y se seleccionará el arrendamiento con la puntuación más alta. La puntuación de un arrendamiento se basa en el número de enlaces, el número de direcciones y el número de opciones que contiene:

enlaces * X + direcciones * Y + opciones
Por defecto X = 10000 y Y = 100, esto hará que el cliente seleccione un arrendamiento con más enlaces sobre un arrendamiento con menos enlaces pero más direcciones. Los pesos se cambiaron como parte de la implementación de la RFC 7550. Previamente eran X = 50 y Y = 100, lo que significaba que se preferían más direcciones sobre más enlaces. Si desea continuar usando el estilo antiguo, puede hacerlo editando el archivo includes/site.h y descomentando la definición para USE_ORIGINAL_CLIENT_LEASE_WEIGHTS.

REQUISITOS Y SOLICITUDES DE ARRENDAMIENTO

El protocolo DHCP permite al cliente solicitar que el servidor le envíe información específica, y no le envíe otra información que no esté preparado para aceptar. El protocolo también permite al cliente rechazar ofertas de servidores si no contienen la información que el cliente necesita, o si la información proporcionada no es satisfactoria.

Hay una variedad de datos contenidos en las ofertas que los servidores DHCP envían a los clientes DHCP. Los datos que se pueden solicitar específicamente son lo que se llaman Opciones DHCP. Las Opciones DHCP se definen en
dhcp-options(5).

La request instrucción


[ también ] request [ [ espacio-de-opciones . ] opción ] [, ... ];

La instrucción request hace que el cliente solicite que cualquier servidor que responda al cliente le envíe sus valores para las opciones especificadas. Solo las Los nombres de las opciones deben especificarse en la declaración de solicitud - no los parámetros de las opciones. Por defecto, el cliente DHCPv4 solicita las opciones subnet-mask, broadcast-address, time-offset, routers, domain-name, domain-name-servers y host-name, mientras que el cliente DHCPv6 solicita las opciones dhcp6 name-servers y domain-search. Ten en cuenta que si escribes una declaración ´request´, anulas estos valores predeterminados y estas opciones no serán solicitadas.

En algunos casos, puede ser deseable no enviar ninguna lista de solicitud de parámetros. Para hacerlo, simplemente escribe la declaración de solicitud pero no especifiques ningún parámetro:

request;

En la mayoría de los casos, es deseable simplemente añadir una opción a la lista de solicitudes que sea de interés para el cliente en cuestión. En este caso, es mejor ´also request´ las opciones adicionales:

also request domain-search, dhcp6.sip-servers-addresses;

La require declaración


[ also ] require [ [ option-space . ] option ] [, ... ];

La declaración require lista las opciones que deben enviarse para que una oferta sea aceptada. Las ofertas que no contengan todas las opciones listadas serán ignoradas. No existe una lista require predeterminada.

require name-servers;
interface eth0 {
	also require domain-search;
}

La send declaración


send [ option declaration ] ;

La declaración send hace que el cliente envíe la opción especificada al servidor con el valor especificado. Esta es una declaración de opción completa como se describe en dhcp-options(5). Las opciones que siempre se envían en el protocolo DHCP no deben especificarse aquí, excepto que el cliente pueda especificar un dhcp-lease-time solicitado diferente del tiempo de arrendamiento solicitado predeterminado, que es de dos horas. El otro uso obvio de esta declaración es enviar información al servidor que le permita diferenciar entre este cliente y otros clientes o tipos de clientes.

DNS DINÁMICO

El cliente ahora tiene un soporte muy limitado para realizar actualizaciones DNS cuando se adquiere un arrendamiento. Esto es prototípico y probablemente no haga lo que tú quieras. También solo funciona si resulta que tienes control sobre tu servidor DNS, lo cual no es muy probable.

Ten en cuenta que todo lo que se dice en esta sección es cierto tanto si usas DHCPv4 como DHCPv6. Se usa exactamente la misma sintaxis para ambos.

Para hacerlo funcionar, tienes que declarar una clave y una zona como en el servidor DHCP (ver dhcpd.conf(5) para más detalles). También necesitas configurar la opción fqdn en el cliente, como sigue:

  send fqdn.fqdn "grosse.example.com.";
  send fqdn.encoded on;
  send fqdn.server-update off;
  also request fqdn, dhcp6.fqdn;

La fqdn.fqdn opción DEBE ser un nombre de dominio completamente calificado. Tú DEBES definir una declaración de zona para la zona a actualizar. La opción fqdn.encoded puede necesitar configurarse como on o off, dependiendo del servidor DHCP que estés usando.

La do-forward-updates declaración


do-forward-updates [ flag ] ;

Si quieres realizar actualizaciones DNS en el script del cliente DHCP (ver dhclient-script(8)) en lugar de que el cliente DHCP realice la actualización directamente (por ejemplo, si quieres usar autenticación SIG(0), que no es soportada directamente por el cliente DHCP, puedes instruir al cliente para que no realice la actualización usando la declaración do-forward-updates . La bandera debe ser true si quieres que el cliente DHCP realice la actualización, y false si no quieres que el cliente DHCP realice la actualización. Por defecto, el cliente DHCP realizará la actualización DNS.

MODIFICADORES DE OPCIONES

En algunos casos, un cliente puede recibir datos de opciones del servidor que no son realmente apropiados para ese cliente, o puede no recibir información que necesita, y para la cual existe un valor predeterminado útil. También puede recibir información que es útil, pero que necesita ser complementada con información local. Para manejar estas necesidades, hay disponibles varios modificadores de opciones.

La default declaración


default [ option declaration ] ;

Si para alguna opción el cliente debe usar el valor proporcionado por el servidor, pero necesita usar algún valor predeterminado si el servidor no proporcionó ningún valor, estos valores pueden definirse en la declaración default .

La supersede declaración


supersede [ option declaration ] ;

Si para alguna opción el cliente debe usar siempre un valor configurado localmente en lugar de lo que sea proporcionado por el servidor, estos valores pueden definirse en la declaración supersede .

La prepend declaración


prepend [ option declaration ] ;

Si para algún conjunto de opciones el cliente debe usar un valor que tú proporcionas, y luego usar los valores proporcionados por el servidor, si los hay, estos valores pueden definirse en la declaración prepend . La declaración prepend solo puede usarse para opciones que permitan dar más de un valor. Esta restricción no se hace cumplir - si la ignoras, el comportamiento será impredecible.

La append declaración


append [ option declaration ] ;

Si para algún conjunto de opciones el cliente debe usar primero los valores proporcionados por el servidor, si los hay, y luego usar valores que tú proporcionas, estos valores pueden definirse en la declaración append . La declaración append solo puede usarse para opciones que permitan dar más de un valor. Esta restricción no se hace cumplir - si la ignoras, el comportamiento será impredecible.

DECLARACIONES DE ARRENDAMIENTO

La lease declaración


lease { lease-declaration [ ... lease-declaration ] }

El cliente DHCP puede decidir después de algún período de tiempo (ver PROTOCOL TIMING) que no va a tener éxito en contactar a un servidor. En ese momento, consulta su propia base de datos de arrendamientos antiguos y prueba cada uno que aún no haya expirado haciendo ping al router listado para ese arrendamiento para ver si ese arrendamiento podría funcionar. Es posible definir uno o más arrendamientos fixed en el archivo de configuración del cliente para redes donde no hay servicio DHCP o BOOTP, para que el cliente pueda seguir configurando automáticamente su dirección. Esto se hace con la declaración lease .

NOTA: la declaración lease también se usa en el archivo dhclient.leases para registrar arrendamientos que han sido recibidos de servidores DHCP. Alguna de la sintaxis para arrendamientos descrita a continuación solo es necesaria en el archivo dhclient.leases. Dicha sintaxis se documenta aquí por completitud.

Una declaración de arrendamiento consiste en la palabra clave lease, seguida de una llave izquierda, seguida de una o más declaraciones de arrendamiento, seguidas de una llave derecha. Las siguientes declaraciones de arrendamiento son posibles:


bootp;

La bootp declaración se usa para indicar que el arrendamiento fue adquirido usando el protocolo BOOTP en lugar del protocolo DHCP. Nunca es necesario especificar esto en el archivo de configuración del cliente. El cliente usa esta sintaxis en su archivo de base de datos de arrendamientos.


interface "string";

La interface declaración de arrendamiento se usa para indicar la interfaz en la que el arrendamiento es válido. Si se establece, este arrendamiento solo se probará en una interfaz particular. Cuando el cliente recibe un arrendamiento de un servidor, siempre registra el número de interfaz en el que recibió ese arrendamiento. Si se especifican arrendamientos predefinidos en el archivo dhclient.conf, la interfaz también debería especificarse, aunque no es obligatorio.


fixed-address ip-address;

La fixed-address declaración se usa para establecer la dirección IP de un arrendamiento particular. Esto es obligatorio para todas las declaraciones de arrendamiento. La dirección IP debe especificarse como un cuádruple con puntos (ej., 12.34.56.78).


filename "string";

La filename declaración especifica el nombre del archivo de arranque a usar. Esto no es usado por el script de configuración estándar del cliente, pero se incluye por completitud.


server-name "string";

La server-name declaración especifica el nombre del servidor de arranque a usar. Esto tampoco es usado por el script de configuración estándar del cliente.


option option-declaration;

La option declaración se usa para especificar el valor de una opción proporcionada por el servidor, o, en el caso de arrendamientos predefinidos declarados en dhclient.conf, el valor que el usuario desea que el script de configuración del cliente use si se usa el arrendamiento predefinido.


script "script-name";

La script declaración se usa para especificar la ruta de acceso del script de configuración del cliente dhcp. Este script es usado por el cliente dhcp para establecer la configuración inicial de cada interfaz antes de solicitar una dirección, para probar la dirección una vez que ha sido ofrecida, y para establecer la configuración final de la interfaz una vez que se ha adquirido un arrendamiento. Si no se adquiere ningún arrendamiento, el script se usa para probar arrendamientos predefinidos, si los hay, y también se llama una vez si no se puede identificar ningún arrendamiento válido. Para más información, ver dhclient-script(8).


vendor option space "name";

La vendor option space declaración se usa para especificar qué espacio de opciones debe usarse para decodificar la opción vendor-encapsulate-options si se recibe alguna. El dhcp-vendor-identifier puede usarse para solicitar una clase específica de opciones de proveedor al servidor. Ver dhcp-options(5) para más detalles.


medium "media setup";

La medium declaración puede usarse en sistemas donde las interfaces de red no pueden determinar automáticamente el tipo de red a la que están conectadas. La cadena de configuración de medios es un parámetro dependiente del sistema que se pasa al script de configuración del cliente dhcp al inicializar la interfaz. En sistemas Unix y similares a Unix, el argumento se pasa en la línea de comandos de ifconfig al configurar la interfaz.

El cliente dhcp declara automáticamente este parámetro si usa un tipo de medio (ver la declaración media) al configurar la interfaz para obtener una concesión. Esta declaración solo debe utilizarse en concesiones predefinidas si la interfaz de red requiere configuración del tipo de medio.


renew date;


rebind date;


expire date;

La declaración renew define el momento en el que el cliente dhcp debe comenzar a intentar contactar con su servidor para renovar una concesión que está utilizando. La declaración rebind define el momento en el que el cliente dhcp debe comenzar a intentar contactar con cualquier servidor dhcp para renovar su concesión. La declaración expire define el momento en el que el cliente dhcp debe dejar de usar una concesión si no ha podido contactar con un servidor para renovarla.

Estas declaraciones se establecen automáticamente en las concesiones adquiridas por el cliente DHCP, pero también deben configurarse en las concesiones predefinidas: una concesión predefinida cuyo tiempo de caducidad haya pasado no será utilizada por el cliente DHCP.

Las fechas se especifican de una de dos maneras. El software emitirá los tiempos en estos dos formatos dependiendo de si el parámetro de configuración db-time-format se ha establecido en default o local.

Si se establece en default, entonces los valores de date aparecen de la siguiente manera:


<día-semana> <año>/<mes>/<día> <hora>:<minuto>:<segundo>

El día de la semana está presente para que a una persona le sea fácil saber cuándo caduca una concesión; se especifica como un número del cero al seis, siendo el cero domingo. Al declarar una concesión predefinida, siempre se puede especificar como cero. El año se especifica con el siglo, por lo que generalmente debe ser de cuatro dígitos, excepto para concesiones realmente largas. El mes se especifica como un número que comienza con 1 para enero. El día del mes se especifica igualmente a partir del 1. La hora es un número entre 0 y 23, el minuto un número entre 0 y 59 y el segundo también un número entre 0 y 59.

Si la configuración db-time-format se estableció en local, entonces los valores de date aparecen de la siguiente manera:


epoch <segundos-desde-época>; # <nombre-día> <nombre-mes> <número-día> <horas>:<minutos>:<segundos> <año>

Los segundos-desde-época son según el reloj local del sistema (a menudo denominado "tiempo unix"). El símbolo # proporciona un comentario que describe qué hora real es según la zona horaria configurada del sistema, en el momento en que se escribió el valor. Se proporciona solo para inspección humana; el tiempo de época es el único valor recomendado para la inspección por máquina.

Tenga en cuenta que al definir una concesión estática, se puede usar cualquiera de los dos formatos de tiempo que se desee, y no es necesario incluir el comentario ni los valores posteriores al mismo.

Si el tiempo es de duración infinita, entonces el date es never en lugar de una fecha real.

DECLARACIONES ALIAS


alias { declaraciones ... }

Algunos clientes DHCP que ejecutan protocolos de roaming TCP/IP pueden requerir que, además de la concesión que pueden adquirir a través de DHCP, su interfaz también se configure con un alias IP predefinido para que puedan tener una dirección IP permanente incluso mientras están en roaming. El cliente DHCP del Consorcio de Sistemas de Internet (ISC) no soporta directamente el roaming con direcciones fijas, pero para facilitar dicho experimentación, el cliente dhcp se puede configurar para configurar un alias IP utilizando la declaración alias .

La declaración alias se asemeja a una declaración de concesión, excepto que las opciones distintas de la opción de máscara de subred son ignoradas por el script de configuración del cliente estándar, y los tiempos de caducidad son ignorados. Una declaración alias típica incluye una declaración de interfaz, una declaración de dirección fija para la dirección del alias IP y una declaración de opción de máscara de subred. Nunca se debe incluir una declaración media en una declaración alias.

OTRAS DECLARACIONES


db-time-format [ default | local ] ;

La opción db-time-format determina cuál de los dos métodos de salida se utilizan para imprimir los tiempos en los archivos de concesiones. El formato default proporciona día y hora en UTC, mientras que local usa segundos-desde-época para almacenar el valor de tiempo, y coloca convenientemente una hora de zona horaria local en un comentario en la misma línea. Los formatos se describen en detalle en esta página del manual, dentro de la sección DECLARACIONES DE CONCESIONES.

El parámetro lease-id-format

lease-id-format format;

El parámetro format debe ser octal o hex. Este parámetro gobierna el formato utilizado para escribir ciertos valores en los archivos de concesiones. Con el formato predeterminado, octal, los valores se escriben como cadenas entrecomilladas en las que los caracteres no imprimibles se representan como secuencias de escape octales: un carácter barra invertida seguido de tres dígitos octales. Cuando se especifica el formato hex, los valores se escriben como una serie sin comillas de pares de dígitos hexadecimales, separados por dos puntos.

Actualmente, los valores que se escriben basándose en lease-id-format son el default-duid y el valor IAID (solo DHCPv6). El cliente lee automáticamente los valores en cualquiera de los dos formatos. Tenga en cuenta que cuando el formato es octal, en lugar de como una cadena octal, el IAID se emite como hex si no contiene caracteres imprimibles o como una cadena si contiene solo caracteres imprimibles. Esto se hace para mantener la compatibilidad hacia atrás.


reject cidr-ip-address [, ... cidr-ip-address ] ;

La declaración reject hace que el cliente DHCP rechace ofertas de servidores cuyo identificador de servidor coincida con cualquiera de los hosts o subredes especificados. Esto se puede utilizar para evitar ser configurado por servidores dhcp malintencionados o mal configurados, aunque debería ser un último recurso: es mejor rastrear el servidor DHCP defectuoso y arreglarlo.

El tipo de configuración cidr-ip-address tiene la forma ip-address[/prefixlen], donde ip-address es una dirección IP en cuádruple con puntos, y prefixlen es la longitud de prefijo CIDR de la subred, contando el número de bits significativos en la máscara de red desde el extremo más a la izquierda. Ejemplo de sintaxis de configuración:

reject 192.168.0.0/16, 10.0.0.5;

El ejemplo anterior haría que se rechazaran las ofertas de cualquier identificador de servidor en toda la red RFC 1918 "Clase C" 192.168.0.0/16, o la dirección única específica 10.0.0.5.


interface "name" { declaraciones ... }

Un cliente con más de una interfaz de red puede requerir un comportamiento diferente dependiendo de qué interfaz se esté configurando. Todos los parámetros de temporización y declaraciones distintas de las declaraciones de concesión y alias se pueden incluir en una declaración de interfaz, y esos parámetros se utilizarán entonces solo para la interfaz que coincida con el nombre especificado. Las interfaces para las que no hay una declaración de interfaz utilizarán los parámetros declarados fuera de cualquier declaración de interfaz, o la configuración predeterminada.

Tenga en cuenta bien: ISC dhclient solo mantiene una lista de interfaces, que se determina al inicio a partir de los argumentos de la línea de comandos, o se detecta automáticamente. Si proporcionó la lista de interfaces en la línea de comandos, esta cláusula de configuración añadirá la interfaz nombrada a la lista de una manera que hará que sea configurada por DHCP. Lo cual puede no ser el resultado que pretendía. Este es un efecto secundario no deseado que se abordará en una versión futura.


pseudo "name" "real-name" { declaraciones ... }

Bajo algunas circunstancias puede ser útil declarar una pseudo-interfaz y hacer que el cliente DHCP adquiera una configuración para esa interfaz. Cada interfaz que el cliente DHCP soporta normalmente tiene una máquina de estados del cliente DHCP ejecutándose en ella para adquirir y mantener su concesión. Una pseudo-interfaz es solo otra máquina de estados ejecutándose en la interfaz nombrada real-name, con su propia concesión y su propio estado. Si usa esta característica, debe proporcionar un identificador de cliente tanto para la pseudo-interfaz como para la interfaz real, y los dos identificadores deben ser diferentes. También debe proporcionar un script de cliente separado para la pseudo-interfaz para hacer lo que quiera con la dirección IP. Por ejemplo:

interface "ep0" {
	send dhcp-client-identifier "my-client-ep0";
}
pseudo "secondary" "ep0" {
	send dhcp-client-identifier "my-client-ep0-secondary";
	script "/etc/dhclient-secondary";
}

El script de cliente para la pseudo-interfaz no debe configurar la interfaz hacia arriba o hacia abajo - en esencia, todo lo que necesita manejar son los estados en los que se ha adquirido o renovado una concesión, y los estados en los que una concesión ha caducado. Vea dhclient-script(8) para más información.


media "configuración de medio" [ , "configuración de medio", ... ];

La declaración media define uno o más parámetros de configuración de medio que pueden probarse mientras se intenta adquirir una dirección IP. El cliente dhcp recorrerá cada cadena de configuración de medio de la lista, configurando la interfaz usando esa configuración e intentando arrancar, y luego probando la siguiente. Esto se puede usar para interfaces de red que no son capaces de detectar el tipo de medio sin ayuda - el tipo de medio que tenga éxito en enviar una solicitud al servidor y escuchar la respuesta probablemente es el correcto (sin garantías).

La configuración de medio solo se usa para la fase inicial de la adquisición de direcciones (los paquetes DHCPDISCOVER y DHCPOFFER). Una vez que se ha adquirido una dirección, el cliente dhcp la registrará en su base de datos de concesiones y registrará el tipo de medio utilizado para adquirir la dirección. Cada vez que el cliente intente renovar la concesión, usará ese mismo tipo de medio. La concesión debe caducar antes de que el cliente vuelva a recorrer los tipos de medios.


hardware link-type mac-address;

La declaración hardware define la dirección MAC de hardware a usar para esta interfaz, para que los servidores o relés de DHCP dirijan sus respuestas. dhclient determinará automáticamente la dirección MAC de la interfaz, por lo que no se recomienda el uso de este parámetro. El link-type corresponde al tipo de capa de enlace de la interfaz (ejemplo: ´ethernet´), mientras que el mac-address es una cadena de valores hexadecimales separados por dos puntos para octetos.


anycast-mac link-type mac-address;

La declaración anycast-mac anula la dirección MAC de difusión de todos los unos que dhclient utilizará al transmitir paquetes a la dirección IPv4 de difusión limitada de todos los unos. Este parámetro de configuración es útil para reducir el número de paquetes de difusión transmitidos por los clientes DHCP, pero solo es útil si conoce la dirección MAC anycast del servicio DHCP antes de configurar su cliente. Los parámetros link-type y mac-address se configuran de manera similar a la declaración hardware .

EJEMPLO

El siguiente archivo de configuración se utilizó en un portátil que ejecutaba NetBSD 1.3, aunque los dominios han sido modificados. El portátil tiene un alias IP de 192.5.5.213 y una interfaz, ep0 (una 3com 3C589C). Los intervalos de arranque se han acortado un poco con respecto al valor predeterminado, ya que se sabe que el cliente pasa la mayor parte de su tiempo en redes con poca actividad DHCP. El portátil sí se desplaza a múltiples redes.

timeout 60;
retry 60;
reboot 10;
select-timeout 5;
initial-interval 2;
reject 192.33.137.209;
interface "ep0" {
    send host-name "andare.example.com";
    hardware ethernet 00:a0:24:ab:fb:9c;
    send dhcp-client-identifier 1:0:a0:24:ab:fb:9c;
    send dhcp-lease-time 3600;
    supersede domain-search "example.com", "rc.isc.org", "home.isc.org";
    prepend domain-name-servers 127.0.0.1;
    request subnet-mask, broadcast-address, time-offset, routers,
	    domain-name, domain-name-servers, host-name;
    require subnet-mask, domain-name-servers;
    script "CLIENTBINDIR/dhclient-script";
    media "media 10baseT/UTP", "media 10base2/BNC";
}
alias {
  interface "ep0";
  fixed-address 192.5.5.213;
  option subnet-mask 255.255.255.255;
}
Este es un archivo dhclient.conf muy complicado; en general, el suyo debería ser mucho más sencillo. En muchos casos, basta con crear un archivo dhclient.conf vacío: los valores predeterminados suelen ser adecuados.
