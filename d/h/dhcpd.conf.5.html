BOOTP   AND DHCP PACKETS


When the DHCP server receives a BOOTP or DHCP packet, it looks
    at the client's IP address. If the IP address is 0.0.0.0, the server
    allocates a new IP address to the client. If the client's IP address is not
    0.0.0.0, the server checks to see if the client has a valid lease on that
    IP address. If the client has a valid lease on the IP address, the server
    may acknowledge the lease, or it may decide to give the client a new lease
    on that address, or on a different address. If the client does not have a
    valid lease on the IP address, the server will send a DHCPNAK packet to the
    client.


If the client has a fixed IP address, then the server will
    always acknowledge the lease. If the client does not have a fixed IP
    address, the server will sometimes acknowledge the lease, and sometimes give
    the client a new IP address.


If the client has a fixed IP address, the server will never
    allocate a new IP address to the client. If the client requests an IP
    address that is not the fixed IP address, the server will send a DHCPNAK
    to the client. If the client requests the fixed IP address, the server will
    send a DHCPACK to the client.


The DHCP server does not respond to BOOTP requests from clients
    that are not BOOTP clients. It only responds to BOOTP requests from clients
    that are BOOTP clients. If a client sends a DHCP request, the server will
    respond to the DHCP request if the client is a DHCP client. If the client is
    not a DHCP client, the server will not respond.


A client is a BOOTP client if the client's flags indicate that
    it is a BOOTP client. A client is a DHCP client if the client's flags
    indicate that it is a DHCP client.


If a client sends a DHCPDISCOVER message, the DHCP server will
    respond with a DHCPOFFER message. The DHCPOFFER message will contain an IP
    address, a lease duration, and a number of other options. The DHCP server
    will choose the IP address from the list of available IP addresses. If there
    are no available IP addresses, the DHCP server will not respond.


If a client sends a DHCPREQUEST message, the DHCP server will
    respond with a DHCPACK message. The DHCPACK message will contain an IP
    address, a lease duration, and a number of other options. The DHCP server
    will choose the IP address from the list of available IP addresses. If there
    are no available IP addresses, the DHCP server will not respond.


If a client sends a DHCPDECLINE message, the DHCP server will
    mark the IP address as declined. The DHCP server will not assign the IP
    address to any client for a period of time. The period of time is specified
    by the decline-lease-time option.


If a client sends a DHCPRELEASE message, the DHCP server will
    mark the IP address as released. The DHCP server will assign the IP address
    to any client that requests it.


If a client sends a DHCPINFORM message, the DHCP server will
    respond with a DHCPACK message. The DHCPACK message will contain an IP
    address, a lease duration, and a number of other options. The DHCP server
    will choose the IP address from the list of available IP addresses. If there
    are no available IP addresses, the DHCP server will not respond.


The DHCP server does not respond to DHCP INFORM messages unless
    the client has already been assigned an IP address.

ADDRESS   POOLS


The pool and pool6 declarations can be used to
    specify a pool of addresses that will be treated differently than another
    pool of addresses, even on the same network segment or subnet. For example,
    you may want to provide a large set of addresses that can be assigned to
    DHCP clients that are registered to your DHCP server, while providing a
    smaller set of addresses, possibly with short lease times, that are
    available for unknown clients. If you have a firewall, you may be able to
    arrange for addresses from one pool to be allowed access to the Internet,
    while addresses in another pool are not, thus encouraging users to register
    their DHCP clients. To do this, you would set up a pair of pool
    declarations:


subnet 10.0.0.0 netmask 255.255.255.0 {
  option routers 10.0.0.254;
  # Unknown clients get this pool.
  pool {
    option domain-name-servers bogus.example.com;
    max-lease-time 300;
    range 10.0.0.200 10.0.0.253;
    allow unknown-clients;
  }
  # Known clients get this pool.
  pool {
    option domain-name-servers ns1.example.com, ns2.example.com;
    max-lease-time 28800;
    range 10.0.0.5 10.0.0.199;
    deny unknown-clients;
  }
}


It is also possible to set up entirely different subnets for known
    and unknown clients - address pools exist at the level of shared networks,
    so address ranges within pool declarations can be on different subnets.


As you can see in the preceding example, pools can have permit
    lists that control which clients are allowed access to the pool and which
    aren't. Each entry in a pool's permit list is introduced with the
    allow or deny keyword. If a pool has a permit list, then only
    those clients that match specific entries on the permit list will be
    eligible to be assigned addresses from the pool. If a pool has a deny list,
    then only those clients that do not match any entries on the deny list will
    be eligible. If both permit and deny lists exist for a pool, then only
    clients that match the permit list and do not match the deny list will be
    allowed access.


The pool6 declaration is similar to the pool
    declaration. Currently it is only allowed within a subnet6
    declaration, and may not be included directly in a shared network
    declaration. In addition to the range6 statement it allows the
    prefix6 statement to be included. You may include range6
    statements for both NA and TA and prefix6 statements in a single
    pool6 statement.






DYNAMIC   ADDRESS ALLOCATION


Address allocation is actually only done when a client is in the
    INIT state and has sent a DHCPDISCOVER message. If the client thinks it has
    a valid lease and sends a DHCPREQUEST to initiate or renew that lease, the
    server has only three choices - it can ignore the DHCPREQUEST, send a
    DHCPNAK to tell the client it should stop using the address, or send a
    DHCPACK, telling the client to go ahead and use the address for a while.


If the server finds the address the client is requesting, and that
    address is available to the client, the server will send a DHCPACK. If the
    address is no longer available, or the client isn't permitted to have it,
    the server will send a DHCPNAK. If the server knows nothing about the
    address, it will remain silent, unless the address is incorrect for the
    network segment to which the client has been attached and the server is
    authoritative for that network segment, in which case the server will send a
    DHCPNAK even though it doesn't know about the address.


There may be a host declaration matching the client's
    identification. If that host declaration contains a fixed-address
    declaration that lists an IP address that is valid for the network segment
    to which the client is connected, the DHCP server will never do dynamic
    address allocation. In this case, the client is required to take the
    address specified in the host declaration. If the client sends a DHCPREQUEST
    for some other address, the server will respond with a DHCPNAK.


When the DHCP server allocates a new address for a client
    (remember, this only happens if the client has sent a DHCPDISCOVER), it
    first looks to see if the client already has a valid lease on an IP address,
    or if there is an old IP address the client had before that hasn't yet been
    reassigned. In that case, the server will take that address and check it to
    see if the client is still permitted to use it. If the client is no longer
    permitted to use it, the lease is freed if the server thought it was still
    in use - the fact that the client has sent a DHCPDISCOVER proves to the
    server that the client is no longer using the lease.


If no existing lease is found, or if the client is forbidden to
    receive the existing lease, then the server will look in the list of address
    pools for the network segment to which the client is attached for a lease
    that is not in use and that the client is permitted to have. It looks
    through each pool declaration in sequence (all range declarations
    that appear outside of pool declarations are grouped into a single pool with
    no permit list). If the permit list for the pool allows the client to be
    allocated an address from that pool, the pool is examined to see if there is
    an address available. If so, then the client is tentatively assigned that
    address. Otherwise, the next pool is tested. If no addresses are found that
    can be assigned to the client, no response is sent to the client.


If an address is found that the client is permitted to have, and
    that has never been assigned to any client before, the address is
    immediately allocated to the client. If the address is available for
    allocation but has been previously assigned to a different client, the
    server will keep looking in hopes of finding an address that has never
    before been assigned to a client.


The DHCP server generates the list of available IP addresses from
    a hash table. This means that the addresses are not sorted in any particular
    order, and so it is not possible to predict the order in which the DHCP
    server will allocate IP addresses. Users of previous versions of the ISC
    DHCP server may have become accustomed to the DHCP server allocating IP
    addresses in ascending order, but this is no longer possible, and there is
    no way to configure this behavior with version 3 of the ISC DHCP server.






IP   ADDRESS CONFLICT PREVENTION


The DHCP server checks IP addresses to see if they are in use
    before allocating them to clients. It does this by sending an ICMP Echo
    request message to the IP address being allocated. If no ICMP Echo reply is
    received within a second, the address is assumed to be free. This is only
    done for leases that have been specified in range statements, and only when
    the lease is thought by the DHCP server to be free - i.e., the DHCP server
    or its failover peer has not listed the lease as in use.


If a response is received to an ICMP Echo request, the DHCP server
    assumes that there is a configuration error - the IP address is in use by
    some host on the network that is not a DHCP client. It marks the address as
    abandoned, and will not assign it to clients. The lease will remain
    abandoned for a minimum of abandon-lease-time seconds.


If a DHCP client tries to get an IP address, but none are
    available, but there are abandoned IP addresses, then the DHCP server will
    attempt to reclaim an abandoned IP address. It marks one IP address as free,
    and then does the same ICMP Echo request check described previously. If
    there is no answer to the ICMP Echo request, the address is assigned to the
    client.


The DHCP server does not cycle through abandoned IP addresses if
    the first IP address it tries to reclaim is free. Rather, when the next
    DHCPDISCOVER comes in from the client, it will attempt a new allocation
    using the same method described here, and will typically try a new IP
    address.






DHCP   FAILOVER


This version of the ISC DHCP server supports the DHCP failover
    protocol as documented in draft-ietf-dhc-failover-12.txt. This is not a
    final protocol document, and we have not done interoperability testing with
    other vendors' implementations of this protocol, so you must not assume that
    this implementation conforms to the standard. If you wish to use the
    failover protocol, make sure that both failover peers are running the same
    version of the ISC DHCP server.


The failover protocol allows two DHCP servers (and no more than
    two) to share a common address pool. Each server will have about half of the
    available IP addresses in the pool at any given time for allocation. If one
    server fails, the other server will continue to renew leases out of the
    pool, and will allocate new addresses out of the roughly half of available
    addresses that it had when communications with the other server were
    lost.


It is possible during a prolonged failure to tell the remaining
    server that the other server is down, in which case the remaining server
    will (over time) reclaim all the addresses the other server had available
    for allocation, and begin to reuse them. This is called putting the server
    into the PARTNER-DOWN state.


You can put the server into the PARTNER-DOWN state either by using
    the omshell (1) command or by stopping the server, editing the last
    failover state declaration in the lease file, and restarting the server. If
    you use this last method, change the "my state" line to:


failover peer name state {
my state partner-down;.
peer state state at date;
}


It is only required to change "my state" as shown
    above.


When the other server comes back online, it should automatically
    detect that it has been offline and request a complete update from the
    server that was running in the PARTNER-DOWN state, and then both servers
    will resume processing together.

El protocolo de conmutación por error define un rol de servidor primario y un rol de servidor secundario. Existen algunas diferencias en cómo actúan los primarios y los secundarios, pero la mayoría de las diferencias simplemente tienen que ver con proporcionar una forma para que cada par se comporte de manera opuesta al otro. ## INICIO DE CONMUTACIÓN POR ERROR

Cuando se inicia un servidor que no se ha comunicado previamente con su par de conmutación por error, debe establecer la comunicación con su par de conmutación por error y sincronizarse con él antes de poder atender a los clientes. Esto puede suceder porque acaba de configurar sus servidores DHCP para realizar la conmutación por error por primera vez, o porque uno de sus servidores de conmutación por error ha fallado catastróficamente y ha perdido su base de datos.

El proceso de recuperación inicial está diseñado para garantizar que cuando un par de conmutación por error pierde su base de datos y luego se resincroniza, cualquier concesión que el servidor fallido haya otorgado antes de fallar será respetada. Cuando el servidor fallido se inicia, nota que no tiene ningún estado de conmutación por error guardado e intenta contactar a su par.

Una vez que ha establecido contacto, solicita al par una copia completa de la base de datos de concesiones de su par. Luego, el par envía su base de datos completa y envía un mensaje que indica que ha terminado. El servidor fallido luego espera hasta que haya pasado el MCLT y, una vez que haya pasado el MCLT, ambos servidores realizan la transición de regreso a la operación normal. Este período de espera garantiza que cualquier concesión que el servidor fallido haya podido otorgar mientras no estaba en contacto con su socio haya caducado.

Mientras el servidor fallido se recupera, su socio permanece en el estado de PARTNER-DOWN, lo que significa que está atendiendo a todos los clientes. El servidor fallido no proporciona ningún servicio a los clientes DHCP hasta que haya realizado la transición a la operación normal.

En el caso de que ambos servidores detecten que nunca antes se han comunicado con su socio, ambos entran en este estado de recuperación y siguen el procedimiento que acabamos de describir. En este caso, no se proporcionará ningún servicio a los clientes DHCP hasta que haya expirado el MCLT.

## CONFIGURACIÓN DE CONMUTACIÓN POR ERROR

Para configurar la conmutación por error, necesita escribir una declaración de par que configure el protocolo de conmutación por error y necesita escribir referencias de par en cada declaración de grupo para la que desee realizar la conmutación por error. No tiene que hacer conmutación por error para todos los grupos en un segmento de red determinado. No debe decirle a un servidor que está realizando la conmutación por error en un grupo de direcciones particular y decirle al otro que no lo está haciendo. No debe tener grupos de direcciones comunes en los que no esté realizando la conmutación por error. Una declaración de grupo que utiliza la conmutación por error se vería así:

```
pool {
	failover peer "foo";
	parámetros específicos del grupo
};
```

El servidor actualmente realiza muy pocas verificaciones de cordura, por lo que si lo configura incorrectamente, simplemente fallará de manera extraña. Por lo tanto, recomendaría que haga conmutación por error o no haga conmutación por error, pero no haga ningún grupo mixto. Además, use el mismo archivo de configuración principal para ambos servidores y tenga un archivo separado que contenga la declaración del par e incluya el archivo principal. Esto le ayudará a evitar discrepancias en la configuración. A medida que nuestra implementación evoluciona, este será un problema menor. Las declaraciones en la declaración del par son las siguientes:

Las declaraciones *primary* y *secondary*




[ primary | secondary ];


Esto determina si el servidor es primario o secundario, como se describió anteriormente en DHCP FAILOVER.




La declaración *address*




address dirección;


La declaración address declara la dirección IP o el nombre DNS en el que el servidor debe escuchar las conexiones de su par de conmutación por error, y también el valor a utilizar para el identificador del servidor del Protocolo de Conmutación por Error DHCP. Dado que este valor se utiliza como identificador, no se puede omitir.




La declaración *peer address*




peer address dirección;


La declaración peer address declara la dirección IP o el nombre DNS al que el servidor debe conectarse para llegar a su par de conmutación por error para mensajes de conmutación por error.




La declaración *port*




port número-de-puerto;


La declaración port declara el puerto TCP en el que el servidor debe escuchar las conexiones de su par de conmutación por error. Esta declaración se puede omitir, en cuyo caso se utilizará el número de puerto 647 asignado por IANA por defecto.




La declaración *peer port*




peer port número-de-puerto;


La declaración peer port declara el puerto TCP al que el servidor debe conectarse para llegar a su par de conmutación por error para mensajes de conmutación por error. Esta declaración se puede omitir, en cuyo caso se utilizará el número de puerto 647 asignado por IANA por defecto.




La declaración *max-response-delay*




max-response-delay segundos;


La declaración max-response-delay indica al servidor DHCP cuántos segundos pueden pasar sin recibir un mensaje de su par de conmutación por error antes de asumir que la conexión ha fallado. Este número debe ser lo suficientemente pequeño como para que una falla transitoria de la red que rompa la conexión no resulte en que los servidores estén fuera de comunicación durante mucho tiempo, pero lo suficientemente grande como para que el servidor no establezca y rompa conexiones constantemente. Este parámetro debe especificarse.




La declaración *max-unacked-updates*




max-unacked-updates conteo;


La declaración max-unacked-updates indica al servidor DHCP remoto cuántos mensajes BNDUPD puede enviar antes de recibir un BNDACK del sistema local. No tenemos suficiente experiencia operativa para decir cuál es un buen valor para esto, pero 10 parece funcionar. Este parámetro debe especificarse.




La declaración *mclt*




mclt segundos;


La declaración mclt define el Tiempo Máximo de Liderazgo del Cliente (Maximum Client Lead Time). Debe especificarse en el primario y no se puede especificar en el secundario. Este es el período de tiempo durante el cual una concesión puede ser renovada por cualquiera de los pares de conmutación por error sin contactar al otro. Cuanto más tiempo lo establezca, más tardará el servidor en funcionamiento en recuperar las direcciones IP después de pasar al estado PARTNER-DOWN. Cuanto más corto lo establezca, mayor será la carga que experimentarán los servidores cuando no se comuniquen. Un valor de algo así como 3600 es probablemente razonable, pero recuerde nuevamente que no tenemos experiencia operativa real con esto.




La declaración *split*




split bits;


La declaración de división especifica la división entre el primario y el secundario para fines de equilibrio de carga. Cada vez que un cliente realiza una solicitud DHCP, el servidor DHCP ejecuta un hash de la identificación del cliente, lo que resulta en un valor de 0 a 255. Esto se utiliza como índice en un campo de 256 bits. Si el bit en ese índice está establecido, el primario es responsable. Si el bit en ese índice no está establecido, el secundario es responsable. El valor de split determina cuántos de los bits principales están establecidos en uno. Por lo tanto, en la práctica, valores de división más altos harán que el primario atienda a más clientes que el secundario. Valores de división más bajos, lo contrario. Los valores legales están entre 0 y 256 inclusive, de los cuales el más razonable es 128. Tenga en cuenta que un valor de 0 hace que el secundario sea responsable de todos los clientes y un valor de 256 hace que el primario sea responsable de todos los clientes.




La declaración *hba*




hba lista-hexadecimal-separada-por-dos-puntos;


La declaración hba especifica la división entre el primario y el secundario como un mapa de bits en lugar de un punto de corte, lo que teóricamente permite un control más granular. En la práctica, probablemente no sea necesario un control tan granular. Un ejemplo de declaración hba:


  hba ff:ff:ff:ff:ff:ff:ff:ff:ff:ff:ff:ff:ff:ff:ff:ff:
      00:00:00:00:00:00:00:00:00:00:00:00:00:00:00:00;


Esto es equivalente a una declaración split 128;, e idéntico. Los siguientes dos ejemplos también son equivalentes a una split de 128, pero no son idénticos:


  hba aa:aa:aa:aa:aa:aa:aa:aa:aa:aa:aa:aa:aa:aa:aa:aa:
      aa:aa:aa:aa:aa:aa:aa:aa:aa:aa:aa:aa:aa:aa:aa:aa;
  hba 55:55:55:55:55:55:55:55:55:55:55:55:55:55:55:55:
      55:55:55:55:55:55:55:55:55:55:55:55:55:55:55:55;


Son equivalentes, porque la mitad de los bits están establecidos en 0, la mitad están establecidos en 1 (0xa y 0x5 son 1010 y 0101 binario respectivamente) y, en consecuencia, esto dividiría aproximadamente a los clientes por igual entre los servidores. No son idénticos, porque los pares reales a los que esto haría un equilibrio de carga para cada servidor son diferentes para cada ejemplo.


Solo debe tener definido split o hba, nunca ambos. Para la mayoría de los casos, el control granular que ofrece hba no es necesario, y se debe usar split.




La declaración *load balance max seconds*




load balance max seconds segundos;


Esta declaración le permite configurar un punto de corte después del cual el equilibrio de carga se deshabilita. El punto de corte se basa en el número de segundos desde que el cliente envió su primer mensaje DHCPDISCOVER o DHCPREQUEST, y solo funciona con clientes que implementan correctamente el campo secs; afortunadamente, la mayoría de los clientes lo hacen. Recomendamos establecer esto en algo como 3 o 5. El efecto de esto es que si uno de los pares de conmutación por error entra en un estado en el que está respondiendo a mensajes de conmutación por error pero no responde a algunas solicitudes de clientes, el otro par de conmutación por error asumirá automáticamente la carga de sus clientes a medida que los clientes reintentan.


Es posible deshabilitar el equilibrio de carga entre pares estableciendo este valor en 0 en ambos pares. Tenga en cuenta que esto significa que ambos pares responderán a todos los DHCPDISCOVER o DHCPREQUEST.




La declaración *auto-partner-down*




auto-partner-down segundos;


Esta declaración instruye al servidor para que inicie un retraso de tiempo al entrar en el estado de comunicación
estado de comunicaciones interrumpidas (cualquier situación de estar sin contacto con el par de conmutación por error remoto). Al finalizar el temporizador, el servidor entrará automáticamente en el estado de compañero caído (partner-down). Esto permite al servidor asignar arrendamientos del conjunto de arrendamientos libres del compañero después de que expire el temporizador STOS+MCLT, lo cual puede ser peligroso si el compañero está de hecho operando en ese momento (los dos servidores darán asignaciones conflictivas)

Primero, hay arrendamientos 'libres' y 'de respaldo'. Ambos se denominan arrendamientos en 'estado libre'. 'libre' y 'de respaldo' son 'los 
estados libres' para el propósito de este documento. La diferencia es que solo el primario puede asignar desde arrendamientos 'libres' a menos que esté bajo circunstancias especiales, y solo el secundario puede asignar arrendamientos 'de respaldo'.

Cuando se realiza el balanceo de conjuntos, la única expectativa plausible es proporcionar una división 50/50 de los arrendamientos en estado libre entre los dos servidores. Esto se debe a que nadie puede predecir qué servidor fallará, independientemente de la carga relativa colocada sobre los dos servidores, por lo tanto dar a cada servidor la mitad de los arrendamientos le da a ambos servidores la misma cantidad de 'resistencia a fallos'. Por lo tanto, no hay forma de configurar un comportamiento diferente, fuera de algunas ventanas muy pequeñas que describiremos 
brevemente.

Lo primero que se calcula en cualquier ejecución de balanceo de conjuntos es un valor denominado 'lts', o "Arrendamientos a Enviar" (Leases To Send). Simplemente, es la diferencia en el conteo de arrendamientos libres y de respaldo, dividida por dos. Para el secundario, es la diferencia en los arrendamientos de respaldo y libres, dividida por dos. El valor resultante es con signo: si es positivo, se espera que el servidor local entregue arrendamientos para mantener un balanceo 50/50. Si es negativo, el servidor remoto necesitaría enviar arrendamientos para balancear el conjunto. Una vez que el valor lts alcanza cero, el conjunto está perfectamente balanceado (más o menos un arrendamiento en el caso de un número impar de arrendamientos en estado libre totales)
.

Se examinan los arrendamientos más antiguos en los estados libres y de respaldo. El tiempo que han permanecido en sus respectivas colas se usa como una estimación para indicar cuánto tiempo es probable que tomaría antes de que los arrendamientos en la parte superior de la lista fueran consumidos (y por lo tanto, cuánto tiempo tomaría usar todos los arrendamientos en ese estado). La segunda pasada solo se entra si la primera pasada falla en reducir el lts por debajo del número total de arrendamientos en estado libre multiplicado por el

Los clientes pueden ser separados en clases, y tratados diferentemente dependiendo de en qué clase estén. Esta separación puede hacerse ya sea con una declaración condicional, o con una declaración de coincidencia dentro de la declaración de clase. Es posible especificar un límite en el número total de clientes dentro de una clase o subclase particular que puedan mantener arrendamientos a la vez, y es posible especificar subclasificación automática basada en el contenido del paquete del

cliente.

El soporte de clasificación para clientes DHCPv6 se añadió en la versión 4.3.0. Sigue las mismas reglas que para DHCPv4 excepto que el soporte para clases de facturación aún no se ha

añadido.

Para añadir clientes a clases basado en evaluación condicional, puede especificar una expresión de coincidencia en la declaración de

clase: 
class "ras-clients" {
  match if substring (option dhcp-client-identifier, 1, 3) = "RAS";
}

No es posible usar valores construidos a través de una o más declaraciones ejecutables. Esto se debe al hecho de que la clasificación de clientes ocurre antes de que se ejecuten las declaraciones. Intentar hacerlo producirá resultados

indeterminados.

Note que ya sea que use expresiones de coincidencia o declaraciones de adición (o ambas) para clasificar clientes, siempre debe escribir una declaración de clase para cualquier clase que use. Si no habrá declaración de coincidencia ni declaraciones en ámbito para una clase, la declaración debería verse

así:

SUBCLASE

S

Además de las clases, es posible declarar subclases. Una subclase es una clase con el mismo nombre que una clase regular, pero con una expresión de sub-coincidencia específica que se hashea para una coincidencia rápida. Esto es esencialmente un truco de velocidad - la principal diferencia entre cinco clases con expresiones de coincidencia y una clase con cinco subclases es que será más rápido encontrar las subclases. Las subclases funcionan de la siguiente

manera: 
class "allocation-class-1" {
  match pick-first-value (option dhcp-client-identifier, hardware);
}
class "allocation-class-2" {
  match pick-first-value (option dhcp-client-identifier, hardware);
}
subclass "allocation-class-1" 1:8:0:2b:4c:39:ad;
subclass "allocation-class-2" 1:8:0:2b:a9:cc:e3;
subclass "allocation-class-1" 1:0:0:c4:aa:29:44;
subnet 10.0.0.0 netmask 255.255.255.0 {
  pool {
    allow members of "allocation-class-1";
    range 10.0.0.11 10.0.0.50;
  }
  pool {
    allow members of "allocation-class-2";
    range 10.0.0.51 10.0.0.100;
  }
}

Los datos que siguen al nombre de la clase en la declaración de subclase son un valor constante a usar en la coincidencia de la expresión de coincidencia de la clase. Cuando se hace la coincidencia de clases, el servidor evaluará la expresión de coincidencia y luego buscará el resultado en la tabla hash. Si encuentra una coincidencia, se considera que el cliente es miembro tanto de la clase como de la

subclase.

Las subclases pueden declararse con o sin ámbito. En el ejemplo anterior, el único propósito de la subclase es permitir que algunos clientes accedan a un pool de direcciones, mientras que a otros clientes se les da acceso al otro pool, por lo que estas subclases se declaran sin ámbitos. Si parte del propósito de la subclase fuera definir valores de parámetros diferentes para algunos clientes, podría querer declarar algunas subclases con

ámbitos.

En el ejemplo anterior, si tuviera un único cliente que necesitara algunos parámetros de configuración, mientras que la mayoría no los necesita, podría escribir la siguiente declaración de subclase para ese

cliente: 
subclass "allocation-class-2" 1:08:00:2b:a1:11:31 {
  option root-path "samsara:/var/diskless/alphapc";
  filename "/tftpboot/netbsd.alphapc-diskless";
}

En este ejemplo, hemos utilizado la subclase como una forma de controlar la asignación de direcciones por cliente. Sin embargo, también es posible usar subclases de maneras que no son específicas de los clientes, por ejemplo, para usar el valor de la opción vendor-class-identifier para determinar qué valores enviar en la opción vendor-encapsulated-options. Un ejemplo de esto se muestra bajo el encabezado VENDOR ENCAPSULATED OPTIONS en la página del manual

dhcp-opt
ions(5).

CLASES DE GENERACIÓN

(SPAWNING)

Es posible declarar una clase de generación (spawning class). Una clase de generación es una clase que produce automáticamente subclases basándose en lo que el cliente envía. La razón por la que se crearon las clases de generación fue para hacer posible crear clases con límites de arrendamiento sobre la marcha. La aplicación prevista es un entorno de módem por cable donde el ISP desea proporcionar a los clientes en un sitio particular más de una dirección IP, pero no desea proporcionar a esos clientes su propia subred, ni darles un número ilimitado de direcciones IP del segmento de red al que están

conectados.

Muchos sistemas de cabecera de módem por cable pueden configurarse para añadir una opción de Información del Agente de Relevo a los paquetes DHCP al retransmitirlos al servidor DHCP. Estos sistemas típicamente añaden una opción de ID de circuito o ID remoto que identifica de manera única el sitio del cliente. Para aprovechar esto, puede escribir una declaración de clase de la siguiente

manera: 
class "customer" {
  spawn with option agent.circuit-id;
  lease limit 4;
}

Ahora, cada vez que llega una solicitud de un sitio de cliente, la opción de ID de circuito se comprobará contra la tabla hash de la clase. Si se encuentra una subclase que coincida con el ID de circuito, el cliente será clasificado en esa subclase y tratado en consecuencia. Si no se encuentra ninguna subclase que coincida con el ID de circuito, se creará una nueva y se registrará en el archivo dhcpd.leases, y el cliente será clasificado en esta nueva clase. Una vez que el cliente ha sido clasificado, será tratado de acuerdo con las reglas de la clase, incluyendo, en este caso, estar sujeto al límite por sitio de cuatro

arrendamientos.

El uso del mecanismo de generación de subclases no se res

tringe a las opciones del agente de relevo; este ejemplo
en particular se da solo porque es uno bastante directo.

ACTUALIZACIONES DINÁMICAS DE

DNS

El servidor DHCP tiene la capacidad de actualizar dinámicamente el Sistema de Nombres de Dominio (DNS). Dentro de los archivos de configuración, puede definir cómo desea que se actualice el Sistema de Nombres de Dominio. Estas actualizaciones son compatibles con RFC 2136, por lo que cualquier servidor DNS que soporte RFC 2136 debería poder aceptar actualizaciones del servidor

DHCP.

Hay dos esquemas de DNS implementados. La opción interim (provisional) se basa en revisiones de borrador de los documentos DDNS, mientras que la opción standard (estándar) se basa en los RFCs para la interacción DHCP-DNS y los DHCIDs. Una tercera opción, ad-hoc, quedó obsoleta y ahora ha sido eliminada del código base. El servidor DHCP debe configurarse para usar uno de los dos métodos actualmente soportados, o para no hacer actualizaciones de

DNS.

Las instalaciones nuevas deben usar la opción standard. Las instalaciones más antiguas pueden querer continuar usando la opción interim para compatibilidad con versiones anteriores con la base de datos de DNS hasta que la base de datos pueda ser actualizada. Esto se puede hacer con el parámetro de configuración ddns-update-styl

e
.

El marco básico para los dos esquemas es similar, siendo la principal diferencia material que se usa un RR DHCID en la versión standard, mientras que las versiones interim usan un RR TXT. El formato del registro TXT se asemeja al RR DHCID pero no es equivalente (MD5 vs SHA2, diferencias en la longitud de los campos, etc.)

.

En estos dos esquemas, el servidor DHCP no necesariamente siempre actualiza tanto los registros A como los PTR. La opción FQDN incluye una bandera que, cuando es enviada por el cliente, indica que el cliente desea actualizar su propio registro A. En ese caso, el servidor puede configurarse para honrar las intenciones del cliente o ignorarlas. Esto se hace con la declaración allow client-updates; o la declaración ignore client-updates;. Por defecto, las actualizaciones del cliente están

permitidas.

Si el servidor está configurado para permitir actualizaciones del cliente, entonces, si el cliente envía un nombre de dominio completamente calificado en la opción FQDN, el servidor usará ese nombre que el cliente envió en la opción FQDN para actualizar el registro PTR. Por ejemplo, digamos que el cliente es un visitante del dominio "radish.org", cuyo nombre de host es "jschmoe". El servidor es para el dominio "example.org". El cliente DHCP indica en la opción FQDN que su FQDN es "jschmoe.radish.org.". También indica que quiere actualizar su propio registro A. El servidor DHCP, por lo tanto, no intenta configurar un registro A para el cliente, pero sí configura un registro PTR para la dirección IP que asigna al cliente, apuntando a jschmoe.radish.org. Una vez que el cliente DHCP tiene una dirección IP, puede actualizar su propio registro A, asumiendo que el servidor DNS de "radish.org" le permitirá

hacerlo.

Si el servidor está configurado para no permitir actualizaciones del cliente, o si el cliente no quiere hacer su propia actualización, el servidor simplemente elegirá un nombre para el cliente. Por defecto, el servidor elegirá entre los siguientes tres

valores:


1. opción fqdn (si está presente)
2. opción hostname (si está presente)
3. Opción de nombre de host configurada (si está definida)

.

Si estos valores por defecto para elegir el nombre de host no son apropiados, puede escribir su propia declaración para establecer la variable ddns-hostname como desee. Si no se encuentra ninguno de los anteriores, el servidor usará el nombre de la declaración host (si existe) y use-host-decl-names está

activado.

Usará su propio nombre de dominio para el cliente. Luego actualizará tanto el registro A como el PTR, usando el nombre que eligió para el cliente. Si el cliente envía un nombre de dominio completamente calificado en la opción fqdn, el servidor usa solo la parte más a la izquierda del nombre de dominio; en el ejemplo anterior, "jschmoe" en lugar de "jschmoe.radish.

Además, si se usa la directiva ignore client-updates;, entonces el servidor además enviará una respuesta en el paquete DHCP, usando la Opción FQDN, que le implica al cliente que debe realizar sus propias actualizaciones si elige hacerlo. Con deny client-updates;, se envía una respuesta que indica que el cliente no puede realizar actualizaciones

Tanto las opciones standard como interim también incluyen un método para permitir que más de un servidor DHCP actualice la base de datos de DNS sin borrar accidentalmente registros A que no deberían ser borrados ni sin añadir registros A que deberían ser añadidos. Para la opción standard, el método funciona de la siguiente

manera:

Cuando el servidor DHCP emite un nuevo arrendamiento a un cliente, crea una cadena de texto que es un hash SHA sobre la identificación del cliente DHCP (ver los RFCs 4701 y 4702 para más detalles). La actualización intenta añadir un registro A con el nombre que el servidor eligió y un registro DHCID que contiene la cadena de identificador hasheada (hashid). Si esta actualización tiene éxito, el servidor ha

terminado.

Si la actualización falla porque el registro A ya existe, entonces el servidor DHCP intenta añadir el registro A con el prerrequisito de que debe haber un registro DHCID con el mismo nombre que el nuevo registro A, y que el contenido del registro DHCID debe ser igual a hashid. Si esta actualización tiene éxito, entonces el cliente tiene su registro A y su registro PTR. Si falla, entonces el nombre que se le ha asignado (o solicitado) al cliente está en uso y no puede ser usado por el cliente. En este punto, el servidor DHCP abandona el intento de hacer una actualización de DNS pour le client jusqu'à ce que le client choisisse un

nouveau

PROTECTION DES ENTRÉES DNS POUR LES CLIENTS STATIQUES Intégrée à la résolution de conflits se trouve la protection des entrées faites manuellement pour les clients statiques. Conformément aux règles de résolution de conflits, un outil de mise à jour DNS ne peut pas modifier les entrées DNS directes s'il n'y a pas de RR DHCID correspondant pour lequel

la

mise à jour est effectuée. Par conséquent, toute entrée DNS directe sans RR DHCID correspondant ne peut pas être modifiée par un tel outil. Dans certains environnements, il peut être souhaitable d'utiliser uniquement cet aspect de la résolution de conflits et de permettre aux outils de mise à jour DNS d'écraser les entrées pour les clients dynamiques quel que soit le client qui les possède. En d'autres termes, la présence ou l'absence d'un RR DHCID est utilisée pour déterminer si les entrées peuvent ou non être écrasées. Que le client corresponde ou non à la valeur de données du RR DHCID est sans importance. Ce comportement, désactivé par défaut, peut être configuré via le paramètre ddns-guard-id-must-match. DUPLICATES


allow duplicates;
deny duplicates;

Las declaraciones de host pueden coincidir con los mensajes del cliente basándose en la opción Identificador de cliente DHCP o en el tipo de hardware de red y la dirección MAC del cliente. Si se utiliza la dirección MAC, la declaración de host coincidirá con cualquier cliente con esa dirección MAC, incluso clientes con diferentes identificadores de cliente. Esto normalmente no sucede, pero es posible cuando una computadora tiene más de un sistema operativo instalado, por ejemplo, Microsoft Windows y NetBSD o Linux.

El flag duplicates indica al servidor DHCP que si se recibe una solicitud de un cliente que coincide con la dirección MAC de una declaración de host, cualquier otro arrendamiento que coincida con esa dirección MAC debe ser descartado por el servidor, incluso si la UID no es la misma. Esto es una violación del protocolo DHCP, pero puede evitar que los clientes cuyos identificadores de cliente cambian regularmente mantengan muchos arrendamientos al mismo tiempo. Por defecto, los duplicados están permitidos.

La palabra clave declines


allow declines;
deny declines;
ignore declines;

El mensaje DHCPDECLINE es utilizado por los clientes DHCP para indicar que el arrendamiento que el servidor ha ofrecido no es válido. Cuando el servidor recibe un DHCPDECLINE para una dirección particular, normalmente abandona esa dirección, asumiendo que algún sistema no autorizado la está utilizando. Desafortunadamente, un cliente malicioso o defectuoso puede, utilizando mensajes DHCPDECLINE, agotar completamente el grupo de asignación del servidor DHCP. El servidor eventualmente recuperará estos arrendamientos, pero no mientras el cliente esté recorriendo el grupo. Esto puede causar graves problemas en el DNS, y también hará que el servidor DHCP olvide las asignaciones de direcciones antiguas de clientes DHCP.

El flag declines indica al servidor DHCP si debe o no aceptar los mensajes DHCPDECLINE. Si se establece en deny o ignore en un alcance particular, el servidor DHCP no responderá a los mensajes DHCPDECLINE.

El flag declines solo es compatible con servidores DHCPv4. Dado el gran espacio de direcciones IPv6 y los límites internos impuestos por el mecanismo de generación de direcciones del servidor, no creemos que sea necesario para los servidores DHCPv6 en este momento.

Actualmente, las direcciones IPv6 abandonadas se recuperan de una de las dos maneras:


a) El cliente renueva una dirección específica:
Si un cliente que utiliza una DUID dada envía una solicitud DHCP REQUEST que contiene
la última dirección abandonada por esa DUID, la dirección será
reasignada a ese cliente.


b) Tras el segundo reinicio después de un abandono de dirección. Cuando
se abandona una dirección, se registra como tal en el archivo de arrendamientos
y se retiene como abandonada en la memoria del servidor hasta que el servidor
se reinicie. Tras el reinicio, el servidor procesará el archivo de arrendamientos
y todas las direcciones cuyo último estado conocido sea abandonado se
mantendrán como tales en la memoria pero no se reescribirán en el archivo de arrendamientos.
Esto significa que un reinicio posterior del servidor no verá las
direcciones abandonadas en el archivo de arrendamientos y, por lo tanto, no tendrá registro
de ellas como abandonadas en la memoria y, como tales, las percibirá como libres
para asignación.

El número total de direcciones en un grupo, disponible para un valor de DUID dado, está limitado internamente por el mecanismo de generación de direcciones del servidor. Si, por una configuración errónea, varios clientes utilizan la misma DUID, competirán por las mismas direcciones, lo que hará que el servidor alcance este límite interno con bastante rapidez. El límite interno aísla este tipo de actividad de manera que el rango de direcciones no se agota para otros valores de DUID. La aparición del siguiente registro de error puede ser una indicación de esta condición:


"Mejor coincidencia para DUID <XX> es una dirección abandonada. Esto puede ser un resultado
de múltiples clientes intentando usar esta DUID"


donde <XX> es un valor de DUID real representado como una cadena de bytes separada por dos puntos en valores hexadecimales.

PERMITIR Y DENEGAR DENTRO DE LAS DECLARACIONES DE GRUPO

Los usos de las palabras clave allow y deny mostradas en la sección anterior funcionan prácticamente de la misma manera, ya sea que el cliente esté enviando un mensaje DHCPDISCOVER o DHCPREQUEST: se asignará una dirección al cliente (ya sea la dirección antigua que solicita o una nueva dirección) y luego se probará esa dirección para ver si está bien que el cliente la obtenga. Si el cliente la solicitó y no está bien, el servidor enviará un mensaje DHCPNAK. De lo contrario, el servidor simplemente no responderá al cliente. Si está bien darle la dirección al cliente, el servidor enviará un mensaje DHCPACK.

La motivación principal detrás de las declaraciones de grupo es tener grupos de asignación de direcciones con políticas de asignación diferentes. A un cliente se le puede denegar el acceso a un grupo, pero se le puede permitir el acceso a otro grupo en el mismo segmento de red. Para que esto funcione, el control de acceso debe realizarse durante la asignación de direcciones, no después de que la asignación de direcciones se haya completado.

Cuando se procesa un mensaje DHCPREQUEST, la asignación de direcciones consiste simplemente en buscar la dirección que el cliente está solicitando y ver si todavía está disponible para el cliente. Si lo está, entonces el servidor DHCP verifica tanto las listas de permisos del grupo de direcciones como las declaraciones de permitir y denegar relevantes dentro del alcance para ver si está bien darle el arrendamiento al cliente. En el caso de un mensaje DHCPDISCOVER, el proceso de asignación se realiza como se describió anteriormente en la sección ASIGNACIÓN DE DIRECCIONES.

Al declarar listas de permisos para los grupos de asignación de direcciones, se reconocen las siguientes sintaxis después de las palabras clave allow o deny:


known-clients;

Si se especifica, esta declaración permite o impide la asignación desde este grupo a cualquier cliente que tenga una declaración de host (es decir, que sea conocido). Un cliente es conocido si tiene una declaración de host en *cualquier* alcance, no solo en el alcance actual.


unknown-clients;

Si se especifica, esta declaración permite o impide la asignación desde este grupo a cualquier cliente que no tenga una declaración de host (es decir, que no sea conocido).


members of "clase";

Si se especifica, esta declaración permite o impide la asignación desde este grupo a cualquier cliente que sea miembro de la clase con nombre.


dynamic bootp clients;

Si se especifica, esta declaración permite o impide la asignación desde este grupo a cualquier cliente bootp.


authenticated clients;

Si se especifica, esta declaración permite o impide la asignación desde este grupo a cualquier cliente que haya sido autenticado utilizando el protocolo de autenticación DHCP. Esto aún no es compatible.


unauthenticated clients;

Si se especifica, esta declaración permite o impide la asignación desde este grupo a cualquier cliente que no haya sido autenticado utilizando el protocolo de autenticación DHCP. Esto aún no es compatible.


all clients;

Si se especifica, esta declaración permite o impide la asignación desde este grupo a todos los clientes. Esto se puede usar cuando desea escribir una declaración de grupo por alguna razón, pero mantenerla en reserva, o cuando desea renumerar su red rápidamente, y así desea que el servidor obligue a todos los clientes que han sido asignados direcciones de este grupo a obtener nuevas direcciones inmediatamente cuando renueven.


after time;

Si se especifica, esta declaración permite o impide la asignación desde este grupo después de una fecha determinada. Esto se puede usar cuando desea mover clientes de un grupo a otro. El servidor ajusta el tiempo de arrendamiento regular para que la última hora de expiración sea en la hora dada + tiempo mínimo de arrendamiento. Un tiempo mínimo de arrendamiento corto impone un cambio escalonado, mientras que un tiempo mínimo de arrendamiento más largo permite un cambio gradual. time es segundos desde la época, o una cadena de tiempo UTC como 4 2007/08/24 09:14:32 o una cadena con desplazamiento de zona horaria en segundos, por ejemplo, 4 2007/08/24 11:14:32 -7200

La declaración abandon-lease-time

abandon-lease-time time;

Time debe ser la cantidad máxima de tiempo (en segundos) que un arrendamiento IPv4 abandonado permanece no disponible para asignación a un cliente. Los arrendamientos abandonados solo se ofrecerán a los clientes si no hay arrendamientos libres. Si no se define, el tiempo de arrendamiento abandonado predeterminado es 86400 segundos (24 horas). Tenga en cuenta que el tiempo de arrendamiento abandonado para un arrendamiento dado se conserva a través de los reinicios del servidor. El parámetro solo se puede establecer en el alcance global y se evalúa solo una vez durante el inicio del servidor.

Los valores inferiores a sesenta segundos no se recomiendan, ya que están por debajo del umbral de verificación ping y pueden hacer que los arrendamientos que una vez fueron abandonados pero que desde entonces han vuelto al estado libre no se verifiquen ping antes de ofrecerse. Si el tiempo solicitado es mayor que 0x7FFFFFFF - 1 o la suma del tiempo actual más el tiempo abandonado es mayor que 0x7FFFFFFF, se trata como infinito.

La declaración adaptive-lease-time-threshold

adaptive-lease-time-threshold percentage;

Cuando el número de arrendamientos asignados dentro de un grupo supera el porcentaje dado en esta declaración, el servidor DHCP reduce la duración del arrendamiento para los nuevos clientes dentro de este grupo a min-lease-time segundos. Los clientes que renuevan arrendamientos válidos (largos) existentes reciben al menos el tiempo restante del arrendamiento actual. Dado que los arrendamientos expiran más rápido, el servidor puede recuperarse más rápidamente o evitar el agotamiento del grupo por completo. Una vez que el número de arrendamientos asignados cae por debajo del umbral, el servidor vuelve a los tiempos de arrendamiento normales. Los porcentajes válidos están entre 1 y 99.

Las declaraciones delayed-ack y max-ack-dela

delayed-ack count

;

max-ack-delay microseconds

;

<Count debe ser un valor entero de cero a 2^16-1 y por defecto es 0, lo que significa que la característica está deshabilitada. De lo contrario, 28 puede ser un punto de partida sensato para muchas configuraciones (SO_SNDBUF size / 576 bytes). El recuento representa cuántas respuestas DHCPv4 como máximo se pondrán en cola pendientes de transmisión hasta después de un evento de confirmación de base de datos. Si se alcanza este número, se realizará un evento de confirmación de base de datos (que comúnmente resulta en fsync() y representa una penalización de rendimiento), y los paquetes de respuesta se transmitirán en un lote después. Esto preserva la dirección RFC2131 de que el "almacenamiento estable" se actualice antes de responder a los clientes. Si los sockets DHCPv4 "se secan" (select() devuelve inmediatamente sin sockets de lectura), se realiza la confirmación y se transmiten los paquetes en cola.

De manera similar, microseconds indica cuántos microsegundos se permiten pasar entre la puesta en cola de un paquete pendiente de un fsync y la realización del fsync. Los valores válidos van de 0 a 2^32-1, y por defecto son 250.000 (1/4 de segundo).

La característica de ack retardado está compilada por defecto, pero puede ser deshabilitada en tiempo de compilación con './configure --disable-delayed-ack'. Tenga en cuenta que la característica de ack retardado no es actualmente compatible con la compatibilidad con DHPCv4 sobre DHCPv6, por lo que cuando un argumento de línea de comandos 4to6 lo habilita en el servidor, el valor de ack retardado se restablece a 0.

La declaración dhcp-cache-threshold

dhcp-cache-threshold percentage;

La declaración dhcp-cache-threshold toma un parámetro entero con valores permitidos entre 0 y 100. El valor predeterminado es 25 (25% del tiempo de concesión). Este parámetro expresa el porcentaje del tiempo total de concesión, medido desde el principio, durante el cual el intento de un cliente de renovar su concesión resultará en la obtención de la concesión ya asignada, en lugar de una concesión extendida. Esta característica es compatible tanto con IPv4 como con IPv6 y hasta el nivel de grupo y para IPv6 los tres tipos de grupo: NA, TA y PD.

Los clientes que intentan renovar frecuentemente pueden hacer que el servidor actualice y escriba la base de datos con frecuencia, lo que resulta en un impacto en el rendimiento del servidor. La declaración dhcp-cache-threshold instruye al servidor DHCP a evitar actualizar las concesiones con demasiada frecuencia, evitando así este comportamiento. En su lugar, el servidor responde con la misma concesión (es decir, la reutiliza) sin modificaciones, excepto para CLTT (Client Last Transmission Time) y para IPv4:


el tiempo de concesión enviado al cliente se acorta por la antigüedad de
la concesión

mientras que para IPv6:


las vidas preferidas y válidas enviadas al cliente se
acortan por la antigüedad de la concesión.

Ninguno de estos cambios requiere escribir la concesión en el disco.

Cuando una concesión existente se compara con un cliente que renueva, se reutilizará si se cumplen todas las siguientes condiciones: 

    1. El dhcp-cache-threshold es mayor que cero
    2. La concesión actual está activa
    3. El porcentaje del tiempo de concesión que ha transcurrido es menor que
    dhcp-cache-threshold
    4. La información del cliente proporcionada en la renovación no altera
    ninguno de los siguientes:
       a. Información de DNS y actualizaciones de DNS habilitadas
       b. Clase de facturación a la que está asociada la concesión (solo IPv4)
       c. La declaración de host asociada con la concesión (solo IPv4)
       d. El ID del cliente; esto puede ocurrir si un cliente arranca sin

Aunque los datos de la concesión no se escriben en el disco cuando se reutiliza una concesión, el servidor aún ejecutará las declaraciones on-commit.

La declaración do-forward-updates

do-forward-updates flag;

La declaración do-forward-updates le indica al servidor DHCP si debe intentar actualizar el registro A de un cliente DHCP cuando el cliente adquiere o renueva una concesión. Esta declaración no tiene ningún efecto a menos que las actualizaciones de DNS estén habilitadas. Las actualizaciones directas están habilitadas por defecto. Si esta declaración se utiliza para deshabilitar las actualizaciones directas, el servidor DHCP nunca intentará actualizar el registro A del cliente, y solo intentará actualizar el registro PTR del cliente si el cliente proporciona un FQDN que debe colocarse en el registro PTR utilizando la opción fqdn. Si las actualizaciones directas están habilitadas, el servidor DHCP aún respetará la configuración del flag client-updates.

La declaración dont-use-fsync

dont-use-fsync flag;

La declaración dont-use-fsync le indica al servidor DHCP si debe llamar a fsync() al escribir concesiones en el archivo de concesiones. Por defecto y si el flag está establecido en falso, el servidor llamará a fsync(). Suprimir la llamada a fsync() puede aumentar el rendimiento del servidor, pero también añade el riesgo de que una concesión no se escriba correctamente en el disco después de haber sido emitida a un cliente y antes de que el servidor se detenga. Esto puede llevar a la emisión de concesiones duplicadas a diferentes clientes. Usar esta opción no es recomendable.

La declaración dynamic-bootp-lease-cutoff

dynamic-bootp-lease-cutoff date;

La declaración dynamic-bootp-lease-cutoff establece la fecha de finalización para todas las concesiones asignadas dinámicamente a clientes BOOTP. Debido a que los clientes BOOTP no tienen forma de renovar concesiones y no saben que sus concesiones podrían expirar, por defecto dhcpd asigna concesiones infinitas a todos los clientes BOOTP. Sin embargo, puede tener sentido en algunas situaciones establecer una fecha límite para todas las concesiones BOOTP, por ejemplo, el final de un trimestre escolar o la hora de la noche en que una instalación está cerrada y todas las máquinas deben estar apagadas.

Date debe ser la fecha en la que todas las concesiones BOOTP asignadas finalizarán. La fecha se especifica en el formato:


W AAAA/MM/DD HH:MM:SS

W es el día de la semana expresado como un número de cero (domingo) a seis (sábado). AAAA es el año, incluido el siglo. MM es el mes expresado como un número del 1 al 12. DD es el día del mes, contando desde 1. HH es la hora, de cero a 23. MM es el minuto y SS es el segundo. La hora siempre está en Tiempo Universal Coordinado (UTC), no en hora local.

La declaración dynamic-bootp-lease-length

dynamic-bootp-lease-length length;

La declaración dynamic-bootp-lease-length se utiliza para establecer la duración de las concesiones asignadas dinámicamente a clientes BOOTP. En algunos sitios, puede ser posible suponer que una concesión ya no está en uso si su titular no ha utilizado BOOTP o DHCP para obtener su dirección dentro de un cierto período de tiempo. El período se especifica en length como un número de segundos. Si un cliente reinicia usando BOOTP durante el período de tiempo de espera, la duración de la concesión se restablece a length, por lo que un cliente BOOTP que arranca con suficiente frecuencia nunca perderá su concesión. No hace falta decir que este parámetro debe ajustarse con extrema precaución.

La declaración echo-client-id

echo-client-id flag;

La declaración echo-client-id se utiliza para habilitar o deshabilitar el comportamiento conforme a RFC 6842. Si la declaración echo-client-id está presente y tiene un valor de verdadero o encendido, y se recibe un DISCOVER o REQUEST DHCP que contiene la opción de identificador de cliente (código de opción 61), el servidor copiará la opción en su respuesta (DHCP ACK o NAK) según RFC 6842. En otras palabras, si el cliente envía la opción, la recibirá de vuelta. Por defecto, este flag está desactivado y los identificadores de cliente no se ecoarán al cliente.

La declaración fixed-address se utiliza para asignar una o más direcciones IP fijas a un cliente. Solo debe aparecer en una declaración host.
