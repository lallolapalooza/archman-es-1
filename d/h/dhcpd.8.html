DESCRIPCIÓ

N

El Servidor DHCP del Consorcio de Sistemas de Internet, dhcpd, implementa el Protocolo de Configuración Dinámica de Host (DHCP) y el Protocolo

de Inicialización de Internet (BOOTP). DHCP permite que los hosts en una red TCP/IP soliciten y les sean asignadas direcciones IP, y tam
bién descubrir información sobre la red a la que están conectados. BOOTP proporciona una funcionalidad similar, con ciertas restricciones.

OPERACIÓ

N

El protocolo DHCP permite que a un host desconocido para el administrador de la red se le asigne automáticamente una nueva dirección IP de un conjunto de direcciones IP para su red. Para que esto funcione, el administrador de la red asigna conjuntos de direcciones en cada subred y los introduce en el archivo dhcpd.conf(5)

.

Existen dos versiones del protocolo DHCP: DHCPv4 y DHCPv6. Al inicio, el servidor puede iniciarse para una u otra mediante los -4 o -6 argume

ntos.

Al iniciarse, dhcpd lee el archivo dhcpd.conf y almacena una lista de direcciones disponibles en cada subred en la memoria. Cuando un cliente solicita una dirección mediante el protocolo DHCP, dhcpd le asigna una dirección. A cada cliente se le asigna un arrendamiento, que expira después de un período de tiempo elegido por el administrador (por defecto, un día). Antes de que los arrendamientos expiren, se espera que los clientes a los que se les han asignado arrendamientos los renueven para continuar usando las direcciones. Una vez que un arrendamiento ha expirado, el cliente al que se le asignó ese arrendamiento ya no tiene permitido usar la dirección IP

arrendada.

Para llevar un seguimiento de los arrendamientos a través de los reinicios del sistema y los reinicios del servidor, dhcpd mantiene una lista de los arrendamientos que ha asignado en el archivo dhcpd.leases(5). Antes de que dhcpd conceda un arrendamiento a un host, registra el arrendamiento en este archivo y se asegura de que el contenido del archivo se vuelque al disco. Esto garantiza que incluso en caso de un fallo del sistema, dhcpd no olvidará un arrendamiento que haya asignado. Al iniciarse, después de leer el archivo dhcpd.conf, dhcpd lee el archivo dhcpd.leases para refrescar su memoria sobre qué arrendamientos han sido

asignados.

Los nuevos arrendamientos se añaden al final del archivo dhcpd.leases. Para evitar que el archivo se vuelva arbitrariamente grande, de vez en cuando dhcpd crea un nuevo archivo dhcpd.leases a partir de su base de datos de arrendamientos en memoria. Una vez que este archivo ha sido escrito en disco, el archivo antiguo se renombra dhcpd.leases~, y el archivo nuevo se renombra dhcpd.leases. Si el sistema falla en medio de este proceso, el archivo dhcpd.leases que permanezca contendrá toda la información de arrendamientos, por lo que no es necesario un proceso especial de recuperación tras

fallos.

Este servidor también proporciona soporte para BOOTP. A diferencia de DHCP, el protocolo BOOTP no proporciona un protocolo para recuperar direcciones asignadas dinámicamente una vez que ya no se necesitan. Aún es posible asignar direcciones dinámicamente a clientes BOOTP, pero se requiere algún proceso administrativo para reclamar las direcciones. Por defecto, los arrendamientos se conceden a los clientes BOOTP de forma perpetua, aunque el administrador de la red puede establecer una fecha de corte anterior o una duración de arrendamiento más corta para los arrendamientos BOOTP si eso tiene

sentido.

Los clientes BOOTP también pueden ser atendidos de la forma estándar antigua, que es simplemente proporcionar una declaración en el archivo dhcpd.conf para cada cliente BOOTP, asignando permanentemente una dirección a cada

cliente.

Siempre que se realicen cambios en el archivo dhcpd.conf, dhcpd debe reiniciarse. Para reiniciar dhcpd, envíe un SIGTERM (señal 15) al ID de proceso contenido en RUNDIR/dhcpd.pid, y luego vuelva a invocar dhcpd. Debido a que la base de datos del servidor DHCP no es tan ligera como una base de datos BOOTP, dhcpd no se reinicia automáticamente cuando detecta un cambio en el archivo dhcpd.

conf.

Nota: Recibimos muchas quejas sobre esto. Nos damos cuenta de que sería bueno si se pudiera enviar un SIGHUP al servidor y que recargara la base de datos. Esto no es técnicam

ente imposible, pero requeriría una gran cantidad de trabajo, nuestros recursos son extremadamente limitados, y pueden gastarse mejor en otro lugar. Así que por favor no se qu
ejen de esto en la lista de correo a menos que estén preparados para financiar un proyecto para implementar esta característica, o preparados para hacerlo ustedes mismos.

PUERTO

S

Durante las operaciones, el servidor puede usar múltiples puertos UDP y TCP para proporcionar diferentes funciones. Qué puertos se abren depende tanto de la forma en que compiló su código como de la configuración que proporcione. Lo siguiente debería darle una idea de qué puertos pueden estar en

uso.

Normalmente, un servidor DHCPv4 abrirá un socket UDP crudo para recibir y enviar la mayoría de los paquetes DHCPv4. También abre un socket UDP de respaldo para el envío de paquetes unicast. Normalmente, ambos usarán el número de puerto conocido para

BOOTPS.

Por cada par de conmutación por error (failover) de DHCPv4 que liste en el archivo de configuración, habrá un socket TCP escuchando conexiones en los puertos especificados en el archivo de configuración. Cuando el par se conecte, habrá otro socket para la conexión establecida. Para la conexión establecida, el lado (primario o secundario) que abre la conexión usará un puerto

aleatorio.

Para DHCPv6, el servidor abre un socket UDP en el puerto conocido

dhcpv6-server.

El servidor abre un socket icmp para realizar solicitudes ping y comprobar si las direcciones están en

uso.

Si ha incluido una declaración omapi-port en su archivo de configuración, el servidor abrirá un socket TCP en ese puerto para escuchar conexiones OMAPI. Cuando algo se conecte, se usará otro puerto para la conexión

establecida.

Cuando DDNS está habilitado en tiempo de compilación (ver includes/site.h), el servidor abrirá tan

to un socket UDP v4 como uno v6 en puertos aleatorios, a menos que las actualizaciones DDNS estén
deshabilitadas globalmente estableciendo ddns-update-style a none en el archivo de configuración.

Subrede

s

dhcpd necesita conocer los números de subred y las máscaras de red de todas las subredes para las que proporcionará servicio. Además, para asignar direcciones dinámicamente, se le debe asignar uno o más rangos de direcciones en cada subred que a su vez pueda asignar a los hosts clientes mientras arrancan. Así, una configuración muy simple que proporcione soporte DHCP podría verse

así: 
subnet 239.252.197.0 netmask 255.255.255.0 {
  range 239.252.197.10 239.252.197.250;
}

Se pueden especificar múltiples rangos de direcciones

así: 
subnet 239.252.197.0 netmask 255.255.255.0 {
  range 239.252.197.10 239.252.197.107;
  range 239.252.197.113 239.252.197.250;
}

Si una subred solo recibirá servicio BOOTP y no asignació

n dinámica de direcciones, la cláusula range puede omitirs
e por completo, pero la declaración subnet debe aparecer.

Duración de las

concesiones

Las concesiones DHCP pueden asignarse con casi cualquier duración, desde cero segundos hasta infinito. Qué duración de concesión tiene sentido para una subred dada, o para una instalación dada, variará dependiendo de los tipos de hosts que se estén

sirviendo.

Por ejemplo, en un entorno de oficina donde los sistemas se añaden de vez en cuando y se eliminan de vez en cuando, pero se mueven relativamente poco, podría tener sentido permitir tiempos de concesión de un mes o más. En un entorno de prueba final en una planta de fabricación, podría tener más sentido asignar una duración máxima de concesión de 30 minutos, el tiempo suficiente para realizar un procedimiento de prueba simple en un dispositivo de red antes de empaquetarlo para su

entrega.

Es posible especificar dos duraciones de concesión: la duración predeterminada que se asignará si un cliente no solicita ninguna duración particular, y una duración máxima de concesión. Estas se especifican como cláusulas del comando

subnet: 
subnet 239.252.197.0 netmask 255.255.255.0 {
  range 239.252.197.10 239.252.197.107;
  default-lease-time 600;
  max-lease-time 7200;
}

Esta declaración de subred particular especifica un tiempo de concesión predeterminado de 600 segundos (diez minutos) y un tiempo de concesión máximo de 7200 segundos (dos horas). Otros valores comunes serían 86400 (un día), 604800 (una semana) y 2592000 (30 días)

.

Cada subred no necesita tener la misma concesión: en el caso de un entorno de oficina y un

entorno de fabricación servidos por el mismo servidor DHCP, podría tener sentido tener va
lores muy dispares para los tiempos de concesión predeterminados y máximos en cada subred.

Soporte

BOOTP

Cada cliente BOOTP debe declararse explícitamente en el archivo dhcpd.conf. Una declaración de cliente muy básica especificará la dirección hardware de la interfaz de red del cliente y la dirección IP a asignar a ese cliente. Si el cliente necesita poder cargar un archivo de arranque desde el servidor, debe especificarse el nombre de ese archivo. Una declaración de cliente bootp simple podría verse

así: 
host haagen {
  hardware ethernet 08:00:2b:4c:59:23;
  fixed-address 239.252.197.9;
  filename "/tftpboot/haagen.boot";
}

Opcione

s

DHCP (y también BOOTP con Extensiones de Vendedor) proporcionan un mecanismo mediante el cual el servidor puede proporcionar al cliente información sobre cómo configurar su interfaz de red (por ejemplo, la máscara de subred), y también cómo el cliente puede acceder a varios servicios de red (por ejemplo, DNS, enrutadores IP, etc.)

.

Estas opciones pueden especificarse por subred y, para los clientes BOOTP, también por cliente. En el caso de que una declaración de cliente BOOTP especifique opciones que también están especificadas en su declaración de subred, las opciones especificadas en la declaración del cliente tienen prioridad. Una configuración DHCP razonablemente completa podría verse algo

así: 
subnet 239.252.197.0 netmask 255.255.255.0 {
  range 239.252.197.10 239.252.197.250;
  default-lease-time 600;
  max-lease-time 7200;
  option subnet-mask 255.255.255.0;
  option broadcast-address 239.252.197.255;
  option routers 239.252.197.1;
  option domain-name-servers 239.252.197.2, 239.252.197.3;
  option domain-name "isc.org";
}

Un host bootp en esa subred que necesite estar en un dominio diferente y usar un servidor de nombres diferente podría declararse como

sigue: 
host haagen {
  hardware ethernet 08:00:2b:4c:59:23;
  fixed-address 239.252.197.9;
  filename "/tftpboot/haagen.boot";
  option domain-name-servers 192.5.5.1;
  option domain-name "example.com";
}

OMAP

I

El servidor DHCP proporciona la capacidad de modificar parte de su configuración mientras se está ejecutando, sin detenerlo, modificar sus archivos de base de datos y reiniciarlo. Esta capacidad se proporciona actualmente usando OMAPI, una API para manipular objetos remotos. Los clientes OMAPI se conectan al servidor usando TCP/IP, se autentican y luego pueden examinar el estado actual del servidor y hacerle

cambios.

En lugar de implementar directamente el protocolo OMAPI subyacente, los programas de usuario deberían usar la API dhcpctl o OMAPI misma. Dhcpctl es un envoltorio que maneja algunas de las tareas de mantenimiento que OMAPI no realiza automáticamente. Dhcpctl y OMAPI están documentados en dhcpctl(3) y omapi(

3).

OMAPI exporta objetos, que luego pueden ser examinados y modificados. El servidor DHCP exporta los siguientes obje

tos: lease, host, failover-state y group. Cada objeto tiene varios métodos proporcionados: lookup, create y destr
oy. Además, es posible ver los atributos almacenados en los objetos y, en algunos casos, modificar esos atributos.

EL OBJETO

CONTROL

El objeto control le permite apagar el servidor. Si el servidor está haciendo conmutación por error con otro par, hará una transición limpia al estado de apagado y notificará a su par, para que el par pueda entrar en partner-down, y luego registrar el estado "recover" en el archivo de arrendamientos para que cuando el servidor sea reiniciado, se resincronice automáticamente con su

par.

Al apagarse, el servidor también intentará cerrar limpiamente todas las conexiones OMAPI. Si estas conexiones no se cierran limpiamente después de cinco segundos, se cierran de forma preventiva. Puede tomar hasta 25 segundos desde el comienzo del proceso de apagado hasta el momento en que el servidor realmente

El objeto failover-state es el objeto que rastrea el estado del protocolo de conmutación por error a medida que se gestiona para un par de conmutación por error dado. El objeto failover tiene los siguientes atributos (por favor vea dhcpd.conf (5) para explicaciones sobre lo que significan estos atributos)

(Note que algunos de los valores anteriores han cambiado desde DHCP 3.0.x.

En general, no es una buena idea hacer cambios a este estado. Sin embargo, en el caso de que se sepa que el par de conmutación por error está caído, puede ser útil establecer el estado de conmutación por error del servidor DHCP en partner-down. En este punto, el servidor DHCP tomará el servicio de los arrendamientos del par de conmutación por error tan pronto como sea posible, y dará arrendamientos normales, no arrendamientos que están restringidos por MCLT. Si usted pone al servidor DHCP en partner-down cuando el otro servidor DHCP no está en el estado partner-down, pero no es alcanzable, son posibles conflictos en la asignación de direcciones IP, e incluso probables. Una vez que un servidor ha sido puesto en modo partner-down, su par de conmutación por error no debe ser vuelto a poner en línea hasta que sea posible la comunicación entre los dos
servidores.

THE FAILOVER-STATE OBJECT

The failover-state object is used to hold failover-related state information. It is primarily used for debugging and monitoring the failover process. The following values can be examined:

peer-moves integer examine

Indicates the number of times the failover partner has changed state.

timeouts integer examine

Indicates the number of times the failover partner has timed out.

state text examine

Indicates the current state of the failover partner. The possible states are "normal", "startup", "shutdown", "communications-interrupted", "potential-duw", "failed", and "stopped".

partner-state text examine

Indicates the current state of the failover partner as reported by the failover partner.

timer integer examine

Indicates the current value of the failover timer.

normal-time integer examine

Indicates the number of seconds the failover partner has been in the normal state.

backup-time integer examine

Indicates the number of seconds the failover partner has been in the backup state.

shelter-time integer examine

Indicates the number of seconds the failover partner has been in the shelter state.

unacknowledged-updates integer examine

Indicates the number of update messages that have been received from the failover partner but not yet acknowledged.

load integer examine

Indicates the current load on the failover partner.

max-load integer examine

Indicates the maximum load allowed on the failover partner.

mcf integer examine

Indicates the maximum client connections allowed from the failover partner.

received-cdd integer examine

Indicates the number of client-disconnect messages received from the failover partner.

received-ndi integer examine

Indicates the number of new-lease-declarations received from the failover partner.

received-spd integer examine

Indicates the number of script-peer-declarations received from the failover partner.

received-upt integer examine

Indicates the number of update-requests received from the failover partner.

received-welcome integer examine

Indicates the number of welcome messages received from the failover partner.

received-reject integer examine

Indicates the number of reject messages received from the failover partner.

received-cherr integer examine

Indicates the number of chand-errors received from the failover partner.

received-serr integer examine

Indicates the number of servfail-errors received from the failover partner.

received-fail integer examine

Indicates the number of fail messages received from the failover partner.

received-finish integer examine

Indicates the number of finish messages received from the failover partner.

received-quit integer examine

Indicates the number of quit messages received from the failover partner.

received-hotoffer integer examine

Indicates the number of hotoffer messages received from the failover partner.

received-hotack integer examine

Indicates the number of hotack messages received from the failover partner.

received-hotnak integer examine

Indicates the number of hotnak messages received from the failover partner.

received-hotclient integer examine

Indicates the number of hotclient messages received from the failover partner.

received-hotunknown integer examine

Indicates the number of hotunknown messages received from the failover partner.

sent-cdd integer examine

Indicates the number of client-disconnect messages sent to the failover partner.

sent-ndi integer examine

Indicates the number of new-lease-declarations sent to the failover partner.

sent-spd integer examine

Indicates the number of script-peer-declarations sent to the failover partner.

sent-upt integer examine

Indicates the number of update-requests sent to the failover partner.

sent-welcome integer examine

Indicates the number of welcome messages sent to the failover partner.

sent-reject integer examine

Indicates the number of reject messages sent to the failover partner.

sent-cherr integer examine

Indicates the number of chand-errors sent to the failover partner.

sent-serr integer examine

Indicates the number of servfail-errors sent to the failover partner.

sent-fail integer examine

Indicates the number of fail messages sent to the failover partner.

sent-finish integer examine

Indicates the number of finish messages sent to the failover partner.

sent-quit integer examine

Indicates the number of quit messages sent to the failover partner.

sent-hotoffer integer examine

Indicates the number of hotoffer messages sent to the failover partner.

sent-hotack integer examine

Indicates the number of hotack messages sent to the failover partner.

sent-hotnak integer examine

Indicates the number of hotnak messages sent to the failover partner.

sent-hotclient integer examine

Indicates the number of hotclient messages sent to the failover partner.

sent-hotunknown integer examine

Indicates the number of hotunknown messages sent to the failover partner.

peer-transaction-id integer examine

Indicates the transaction ID of the most recently received message from the failover partner.

peer-declined-updates integer examine

Indicates the number of updates declined by the failover partner.

my-transaction-id integer examine

Indicates the transaction ID of the most recently sent message to the failover partner.

my-declined-updates integer examine

Indicates the number of updates declined by this server.

last-update-sent integer examine

Indicates the time in seconds since the last update message was sent to the failover partner.

last-update-received integer examine

Indicates the time in seconds since the last update message was received from the failover partner.

last-message-sent integer examine

Indicates the time in seconds since the last message was sent to the failover partner.

last-message-received integer examine

Indicates the time in seconds since the last message was received from the failover partner.
