tstp date;
tsfp date;
atsfp date;
cltt date;

El inicio y fin de un contrato de arrendamiento se registran utilizando las sentencias starts y ends. La sentencia tstp está presente si se está utilizando el protocolo de conmutación por error (failover), e indica a qué hora se le ha dicho al socio que el contrato de arrendamiento expira. La sentencia tsfp también está presente si se está utilizando el protocolo de conmutación por error, e indica el tiempo de expiración del contrato de arrendamiento que el socio ha reconocido. La sentencia atsfp es el tiempo real enviado desde el socio de conmutación por error. La sentencia cltt es el último tiempo de transacción del cliente.

Consulte la descripción de las fechas en la sección sobre estructuras comunes.

hardware tipo-hardware dirección-mac;

La sentencia de hardware registra la dirección MAC de la interfaz de red en la que se utilizará el contrato de arrendamiento. Se especifica como una serie de octetos hexadecimales, separados por dos puntos.

uid identificador-cliente;

La sentencia uid registra el identificador de cliente utilizado por el cliente para adquirir el contrato de arrendamiento. Los clientes no están obligados a enviar identificadores de cliente, y esta sentencia solo aparece si el cliente envió uno. Los identificadores de cliente suelen ser un tipo ARP (1 para ethernet) seguido de la dirección MAC, al igual que en la sentencia hardware, pero esto no es obligatorio.

El identificador del cliente se registra como una lista hexadecimal separada por dos puntos o como una cadena entre comillas. Si se registra como una cadena entre comillas y contiene uno o más caracteres no imprimibles, esos caracteres se representan como escapes octales: un carácter de barra invertida seguido de tres dígitos octales. El formato utilizado está determinado por el parámetro lease-id-format, que por defecto es octal.

client-hostname nombre-host ;

La mayoría de los clientes DHCP enviarán su nombre de host en la opción host-name. Si un cliente envía su nombre de host de esta manera, el nombre de host se registra en el contrato de arrendamiento con una sentencia client-hostname. Sin embargo, el protocolo no lo exige, por lo que muchos clientes DHCP especializados no envían una opción de nombre de host.

binding state estado;
next binding state estado;

La sentencia binding state declara el estado de enlace del contrato de arrendamiento. Cuando el servidor DHCP no está configurado para utilizar el protocolo de conmutación por error, el estado de enlace de un contrato de arrendamiento puede ser active, free o abandoned. El protocolo de conmutación por error añade algunos estados de transición adicionales, así como el estado backup, que indica que el contrato de arrendamiento está disponible para su asignación por parte del secundario de conmutación por error. Consulte la página del manual de dhcpd.conf(5) para obtener más información sobre los contratos de arrendamiento abandonados.

La sentencia next binding state indica a qué estado pasará el contrato de arrendamiento cuando expire el estado actual. El tiempo en que expira el estado actual se especifica en la sentencia ends.

rewind binding state estado;

Esta sentencia forma parte de una optimización para su uso con conmutación por error. Ayuda a un servidor a rebobinar un contrato de arrendamiento al estado transmitido más recientemente a su socio.

option agent.circuit-id cadena;
option agent.remote-id cadena;

Estas sentencias se utilizan para registrar las opciones de identificador de circuito e identificador remoto enviadas por el agente de retransmisión, si el agente de retransmisión utiliza la opción de información del agente de retransmisión. Esto permite que estas opciones se utilicen de manera consistente en evaluaciones condicionales, incluso cuando el cliente se pone en contacto directamente con el servidor en lugar de a través de su agente de retransmisión.

La variable vendor-class-identifier

El servidor conserva la opción Vendor Class Identifier proporcionada por el cliente para fines informativos y para renderizarlas en las respuestas DHCPLEASEQUERY.

bootp;
reserved;

Si están presentes, indican que se deben establecer las marcas de conmutación por error BOOTP y RESERVED (respectivamente). Los contratos de arrendamiento dinámicos BOOTP y RESERVED se tratan de manera diferente a los contratos de arrendamiento dinámicos normales, ya que solo pueden ser utilizados por el cliente al que se les asignan actualmente.

LA DECLARACIÓN DE CONTRATO DE ARRENDAMIENTO DHCPv6 (IA)

ia_ta  IAID_DUID { declaraciones... }
ia_na  IAID_DUID { declaraciones... }
ia_pd  IAID_DUID { declaraciones... }

Cada declaración de contrato de arrendamiento comienza con una etiqueta que indica el tipo de contrato de arrendamiento. ia_ta es para direcciones temporales, ia_na es para direcciones no temporales e ia_pd es para delegación de prefijo. Después de esta etiqueta se encuentra el IAID y DUID combinados del cliente para este contrato de arrendamiento.

El valor IAID_DUID se registra como una lista hexadecimal separada por dos puntos o como una cadena entre comillas. Si se registra como una cadena entre comillas y contiene uno o más caracteres no imprimibles, esos caracteres se representan como escapes octales: un carácter de barra invertida seguido de tres dígitos octales. El formato utilizado se rige por el parámetro lease-id-format, que por defecto es octal.

cltt fecha;

La sentencia cltt es el último tiempo de transacción del cliente.

Consulte la descripción de las fechas en la sección sobre estructuras comunes.

iaaddr dirección-ipv6 { declaraciones... }
iaprefix dirección-ipv6/longitud-prefijo { declaraciones... }
Dentro de un contrato de arrendamiento dado puede haber múltiples sentencias
iaaddr e iaprefix. Cada una tendrá una dirección IPv6 o un prefijo IPv6 (una
dirección y una longitud de prefijo que indica un bloque de direcciones estilo
CIDR). Las siguientes sentencias pueden ocurrir dentro de cada iaaddr o
iaprefix.
binding state estado;
La sentencia binding state declara el estado de enlace del contrato de
arrendamiento. En DHCPv6 normalmente verá esto como active o
expired.
preferred-life tiempo-de-vida;
El tiempo de vida preferido de IPv6 asociado con esta dirección, en
segundos.

El tiempo de vida válido asociado con esta dirección, en segundos.

El tiempo de finalización del contrato de arrendamiento. Consulte la descripción

LA DECLARACIÓN DE ESTADO DEL SOCIO DE CONMUTACIÓN POR ERROR

El estado de cualquier acuerdo de asociación de conmutación por error también se registra en el archivo de contratos de arrendamiento, utilizando la sentencia failover peer:

failover peer nombre state {
my state estado at fecha;
peer state estado at fecha;
}

Se registra el estado del socio con el nombre nombre. Se registran tanto el estado del servidor en ejecución (my state) como el del otro socio de conmutación por error (peer state). Los estados posibles son: unknown-state, partner-down, normal, communications-interrupted, resolution-interrupted, potential-conflict, recover, recover-done, shutdown, paused y startup.
