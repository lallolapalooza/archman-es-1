gzip(1) (LZ77) de una manera que es completamente compatible con el formato de archivo gzip. Una extensión al formato de archivo gzip (Campo Extra, descrito en 2.3.1.1 de la RFC 1952) permite almacenar datos adicionales en el encabezado de un archivo comprimido. Programas como gzip y zcat ignorarán estos datos adicionales. Sin embargo, dictd(8), el servidor de diccionarios del protocolo DICT, hará uso de estos datos para realizar un acceso pseudoaleatorio en el archivo. Los archivos en el formato dictzip deben terminar en ".dz" para que puedan distinguirse de los comunes archivos gzip que no contienen la información especial de encabezado. Según la RFC 1952,

el

campo extra se especifica de la siguiente manera: Si el

bit
FLG.FEXTRA está activado, un "campo extra" está presente en el encabezado, con una longitud total de XLEN bytes. Consiste en una serie de subcampos, cada uno con la forma: 
+---+---+---+---+==================================+
|SI1|SI2|  LEN  |... LEN bytes de datos del subcampo ...|
+---+---+---+---+==================================+
SI1

y SI2 proporcionan un ID de subcampo, típicamente dos letras ASCII con algún valor mnemotécnico. Jean-Loup Gailly <gzip@prep.ai.mit.edu> está manteniendo un registro de IDs de subcampo; por favor, envíele cualquier ID de subcampo que desee utilizar. Los IDs de subcampo con SI2 = 0 están

reservados

para uso futuro. LEN da la

longitud de los datos del
subcampo, excluyendo los 4

bytes iniciales. El programa dictzip usa 'R' para SI1, y 'A' para SI2 (es decir, "Acceso Aleatorio"). Después del campo LEN, los datos se

+---+---+---+---+---+---+===============================+

=

de

longitud (2 bytes) y son enteros sin signo. XLEN (que se especifica antes en el encabezado) es un entero de dos bytes, por lo que el campo extra puede tener 0xffff bytes de longitud, de los cuales 2 bytes se utilizan para el ID del subcampo (SI1 y SI1), y 2 bytes se utilizan para la longitud del subcampo (LEN). Esto deja 0xfffb bytes (0x7ffd entradas de 2 bytes o 0x3ffe entradas de 4 bytes). Dado que el búfer de salida de zip debe ser un 10% + 12 bytes más grande que el búfer de entrada, podemos almacenar 58969 bytes por entrada, o aproximadamente 1.8GB si se usan las entradas de 2 bytes. Si esto se convierte en un factor

limitante,

se puede seleccionar y definir otra versión de formato para entradas de 4 bytes. Para la compresión, el archivo se divide en "trozos" de datos, cada trozo es menor que 64kB, y puede comprimirse en un área que también es menor que 64kB de longitud (teniendo en cuenta datos incompresibles -- usualmente los datos se comprimen en un bloque mucho más pequeño que el original).
