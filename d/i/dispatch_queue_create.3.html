dispatch_queue_create(3)

NOMBRE

dispatch_queue_create, dispatch_queue_get_label, dispatch_get_current_queue, dispatch_get_global_queue, dispatch_get_main_queue, dispatch_main, dispatch_set_target_queue — dónde se programan los bloques para su ejecución

const char *
dispatch_queue_get_label(dispatch_queue_t queue);

dispatch_queue_t
dispatch_get_global_queue(long priority, unsigned long flags);

dispatch_queue_t
dispatch_get_main_queue(void);

void
dispatch_main(void);

void
dispatch_set_target_queue(dispatch_object_t object, dispatch_queue_t target);

DESCRIPCIÓN

Las colas son el mecanismo fundamental para programar bloques para su ejecución dentro del framework de dispatch(3).

Todos los bloques enviados a colas de dispatch se desencolan en orden FIFO. Las colas creadas con el atributo DISPATCH_QUEUE_SERIAL esperan a que el bloque desencolado previamente complete su ejecución antes de desencolar el siguiente bloque. Una cola con este comportamiento de finalización FIFO se describe normalmente como una "cola serial". Se garantiza que todas las escrituras de memoria realizadas por un bloque enviado a una cola serial sean visibles para los bloques posteriores enviados a la misma cola. Las colas no están ligadas a ningún hilo de ejecución específico y los bloques enviados a colas independientes pueden ejecutarse de forma concurrente.

Las colas creadas con el atributo DISPATCH_QUEUE_CONCURRENT pueden ejecutar bloques desencolados de forma concurrente y admiten bloques barrera enviados con la API de barrera de dispatch.

CREACIÓN

Las colas se crean con la función dispatch_queue_create(). Las colas, como todos los objetos de dispatch, tienen un recuento de referencias y las colas recién creadas tienen un recuento de referencias de uno.

El argumento opcional label se utiliza para describir el propósito de la cola y es útil durante la depuración y el análisis de rendimiento. Si se proporciona una etiqueta, se copia. Por convención, los clientes deben pasar una etiqueta de estilo DNS inverso. Por ejemplo:

mi_cola = dispatch_queue_create("com.ejemplo.subsistema.tareaXYZ",
				 DISPATCH_QUEUE_SERIAL);

El argumento attr especifica el tipo de cola a crear y debe ser DISPATCH_QUEUE_SERIAL o DISPATCH_QUEUE_CONCURRENT.

La función dispatch_queue_get_label() devuelve la etiqueta proporcionada cuando se creó la queue dada (o una cadena C vacía si no se proporcionó ninguna etiqueta en la creación). Pasar la constante DISPATCH_CURRENT_QUEUE_LABEL a dispatch_queue_get_label() devuelve la etiqueta de la cola actual.

SUSPENSIÓN

Las colas pueden suspenderse temporalmente y reanudarse con las funciones dispatch_suspend() y dispatch_resume() respectivamente. La suspensión se comprueba antes de la ejecución del bloque y no es preemptiva.

COLA PRINCIPAL

El framework de dispatch proporciona una cola serial predeterminada para que la aplicación la utilice. Esta cola se accede a través de la función dispatch_get_main_queue().

Los programas deben llamar a dispatch_main() al final de main() para procesar los bloques enviados a la cola principal. (Consulte la sección COMPATIBILIDAD para ver las excepciones). La función dispatch_main() nunca devuelve.

COLAS CONCURRENTES GLOBALES

A diferencia de la cola principal o las colas asignadas con dispatch_queue_create(), las colas concurrentes globales programan los bloques tan pronto como los hilos están disponibles (orden de finalización no FIFO). Se proporcionan cuatro colas concurrentes globales, que representan las siguientes bandas de prioridad:

  • DISPATCH_QUEUE_PRIORITY_HIGH
  • DISPATCH_QUEUE_PRIORITY_DEFAULT
  • DISPATCH_QUEUE_PRIORITY_LOW
  • DISPATCH_QUEUE_PRIORITY_BACKGROUND

La prioridad de una cola concurrente global controla la prioridad de programación de los hilos creados por el sistema para invocar los bloques enviados a esa cola. Las colas globales con menor prioridad se programarán para su ejecución después de que todas las colas globales con mayor prioridad hayan sido programadas. Además, los elementos de la cola global de prioridad de fondo se ejecutarán en hilos con estado de fondo, como se describe en setpriority(2) (es decir, la E/S de disco se limita y la prioridad de programación del hilo se establece en el valor más bajo).

Utilice la función dispatch_get_global_queue() para obtener la cola global de una prioridad dada. El argumento flags está reservado para uso futuro y debe ser cero. Pasar cualquier valor que no sea cero puede dar lugar a un valor de retorno NULL.

COLA DE DESTINO

La función dispatch_set_target_queue() actualiza la cola de destino del objeto de dispatch dado. La cola de destino de un objeto es responsable de procesar el objeto.

La nueva cola de destino es retenida por el objeto dado antes de que se libere la cola de destino anterior. La nueva configuración de la cola de destino surtirá efecto entre las ejecuciones de bloques en el objeto, pero no en medio de ninguna ejecución de bloque existente (no preemptiva).

La cola de destino predeterminada de todos los objetos de dispatch creados por la aplicación es la cola concurrente global de prioridad predeterminada. Para restablecer la cola de destino de un objeto a la predeterminada, pase la constante DISPATCH_TARGET_QUEUE_DEFAULT a dispatch_set_target_queue().

La prioridad de una cola de dispatch se hereda de su cola de destino. Para cambiar la prioridad de una cola creada con dispatch_queue_create(), utilice la función dispatch_get_global_queue() para obtener una cola de destino de la prioridad deseada.

Los bloques enviados a una cola serial cuya cola de destino es otra cola serial no se invocarán de forma concurrente con los bloques enviados a la cola de destino o a cualquier otra cola con esa misma cola de destino.

La cola de destino de una fuente de dispatch especifica dónde se enviarán sus bloques de manejador de eventos y de cancelación. Consulte dispatch_source_create(3) para obtener más información sobre las fuentes de dispatch.

La cola de destino de un canal de E/S de dispatch especifica la prioridad de la cola global donde se procesará la E/S

se ejecutan. Consulta dispatch_io_create(3) para obtener más información sobre los canales de E/S de

despacho.

Para todos los demás tipos de objetos de despacho, la única función de la cola de destino es determinar dónde se invoca la función finalizador de un

objeto.

El resultado de pasar la cola principal o una cola global concurrente como primer argumento de dispatch_set_target_queue() es

indefinido.

Establecer directa o indirectamente

la cola de destino de una cola de despacho a sí misma es indefinido.

OBSOLETAS

Las siguientes funciones están obsoletas y se eliminarán en una versión

futura:
  • dispatch_queue_t dispatch_get_current_queue(voi
    • d
);

dispatch_get_current_queue() siempre devuelve una cola válida. Cuando se llama desde dentro de un bloque enviado a una cola de despacho, se devolverá esa cola. Si se llama a esta función desde el hilo principal antes de que se llame a dispatch_main(), entonces se devuelve el resultado de dispatch_get_main_queue(). En todos los demás casos, se devolverá la cola de destino

predeterminada.

El uso de dispatch_get_current_queue() se desaconseja encarecidamente, excepto con fines de depuración y registro. El código no debe hacer ninguna suposición sobre la cola devuelta, a menos que sea una de las colas globales o una cola creada por el propio código. La cola devuelta puede tener políticas arbitrarias que pueden sorprender al código que intente programar trabajo con la cola. La lista de políticas incluye, pero no se limita a, el ancho de la cola (es decir, serie frente a concurrente), la prioridad de programación, las credenciales de seguridad o la configuración del sistema de archivos. Esta función está obsoleta y se eliminará en una versión

futura.

Es igualmente inseguro que el código asuma que la ejecución sincrónica en una cola es segura frente a bloqueos si esa cola no es la devuelta por dispatch_get_curren

t_queue().

El resultado de dispatch_get_main_queue() puede o no ser igual al resultado de dispatch_get_current_queue() cuando se llama en el hilo principal. Comparar los dos no es una forma válida de probar si el código se está ejecutando en el hilo principal. Los programas de Foundation/AppKit deben usar [NSThread isMainThread]. Los programas POSIX pueden usar pthread_main_

np(3).

dispatch_get_current_queue() puede devolver una cola propiedad de un subsistema diferente que ya ha liberado todas las referencias externas a ella. Aunque dicha cola seguirá existiendo hasta que todos los bloques enviados a ella se hayan completado, intentar retenerla está prohibido y provocará una aserción. Si el recuento automático de referencias de Objective-C está habilitado, cualquier uso del objeto devuelto por dispatch_get_current_queue() hará que se generen automáticamente llamadas de retención, por lo que el uso de dispatch_get_current_queue() por cualquier motivo en código compilado con ARC se desaconseja

particularmente
.

COMPATIBILIDA

D

Las aplicaciones Cocoa no necesitan llamar a dispatch_main(). Los bloques enviados a la cola principal se ejecutarán como parte de los "modos comunes" del NSRunLoop o CFRunLoop principal de la aplicación. Sin embargo, no se garantiza que los bloques enviados a la cola principal en aplicaciones que usan dispatch_main() se ejecuten en el hilo

principal.

El marco de despacho es una API de nivel C puro. Como resultado, no captura excepciones generadas por lenguajes de nivel superior como Objective-C o C++. Las aplicaciones DEBEN capturar todas las excepciones antes de regresar de un bloque enviado a una cola de despacho; de lo contrario, el proceso se terminará con una excepción no

capturada.

El marco de despacho gestiona la relación entre las colas de despacho y los hilos de ejecución. Como resultado, las aplicaciones NO DEBEN eliminar ni mutar objetos que no crearon. Las siguientes interfaces NO DEBEN ser llamadas por bloques enviados a una cola de

despacho:
  • pthread_cance
    • l()
  • pthread_detac
    • h()
  • pthread_join
    • ()
  • pthread_kill
    • ()
  • pthread_exit
    • (
)

Las aplicaciones PUEDEN llamar a las siguientes interfaces desde un bloque enviado a una cola de despacho si y solo si restauran el hilo a su estado original antes de

regresar:
  • pthread_setcancelstat
    • e()
  • pthread_setcanceltyp
    • e()
  • pthread_setschedpara
    • m()
  • pthread_sigmas
    • k()
  • pthread_setugid_np

)

Las aplicaciones NO DEBEN depender de que las siguientes interfaces devuelvan resultados predecibles entre invocaciones de bloques enviados a una cola de

despacho:
  • pthread_self
    • ()
  • pthread_getschedpara
    • m()
  • pthread_get_stacksize_n
    • p()
  • pthread_get_stackaddr_n
    • p()
  • pthread_mach_thread_n
    • p()
  • pthread_from_mach_thread_np

Aunque el resultado de pthread_self() puede cambiar entre invocaciones de bloques, el valor no cambiará durante la ejecución de un solo bloque. Dado que el hilo subyacente puede cambiar entre invocaciones de bloques en una sola cola, usar datos por hilo como un valor de retorno fuera de banda es propenso a errores. En otras palabras, el resultado de llamar a pthread_setspecific() y pthread_getspecific() está bien definido dentro de un solo bloque, pero no a través de múltiples bloques. Además, no se puede hacer ninguna suposición sobre cuándo se llama al destructor pasado a pthread_key_create(). El destructor puede ser llamado entre la invocación de bloques en la misma cola, o durante el estado inactivo de un

proceso.

El siguiente código de ejemplo maneja correctamente los valores de retorno por

hilo: 
__block int r;
__block int e;
dispatch_sync(queue, ^{
	r = kill(1, 0);
	// Copiar el valor de retorno por hilo al hilo del llamante
	e = errno;
});
printf("kill(1,0) returned %d and errno %d0, r,
e)
;

Ten en cuenta que en el ejemplo anterior errno es una variable por hilo y debe copiarse explícitamente, ya que el bloque puede ser invocado en un hilo de ejecución diferente al del llamante. Otro ejemplo de datos por hilo que necesitarían ser copiados es el uso de getpwnam() en lugar de getpwnam_

r().

Como optimización, dispatch_sync() invoca el bloque en el hilo actual cuando es posible. En este caso, los datos específicos del hilo como errno pueden persistir desde el bloque hasta volver al llamante. Se debe te

ner mucho cuidado de no depender ac
cidentalmente de este efecto secundario.
