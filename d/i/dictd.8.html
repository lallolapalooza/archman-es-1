DESCRIPCIÓ

N

dictd es un servidor para el Protocolo de Servidor de Diccionarios (DICT), un protocolo de consulta/respuesta basado en transacciones TCP que permite a un cliente acceder a definiciones de diccionario desde un conjunto de bases de datos de diccionarios de lenguaje

natural.

Por razones de seguridad, dictd abandona los permisos de root después del inicio. Si el usuario dictd existe en el sistema, el demonio se ejecutará como ese usuario, grupo dictd, de lo contrario se ejecutará como el usuario nobody, grupo nobody o nogroup (dependiendo de la distribución del sistema operativo)

.

Dado que el tiempo de inicio es significativo, el servidor está diseñado para ejecutarse continuamente, y no debería ejecutarse desde inetd(8). (Sin embargo, con un procesador rápido, es factible hacerlo.

)

Las bases de datos se distribuyen por separado del

servidor.

Por defecto, dictd asume que los archivos de índice están ordenados alfabéticamente, y solo se usan caracteres alfanuméricos del conjunto de caracteres ASCII de 7 bits para la búsqueda. Este valor predeterminado puede ser anulado por un encabezado en el archivo de datos. Las únicas características de este tipo implementadas en este momento son los encabezados "00-database-allchars" que le dice a dictd que los caracteres no alfanuméricos también pueden usarse para la búsqueda, el encabezado "00-database-utf8" que indica que la base de datos usa la codificación

utf8, y el "00-database-8bit-new" que indica que la base de datos está codificada
y ordenada de acuerdo con una configuración regional que usa una codificación de 8 bits.

ANTECEDENTE

S

Durante muchos años, la comunidad de Internet ha confiado en el protocolo "webster" para acceder a definiciones de lenguaje natural. El protocolo webster admite el acceso a un solo diccionario y (opcionalmente) a un solo tesauro. En los últimos años, el número de servidores webster disponibles públicamente en Internet ha disminuido

drásticamente.

Afortunadamente, varios diccionarios y léxicos de distribución libre se han hecho disponibles recientemente en Internet. Sin embargo, estas bases de datos de distribución libre no son accesibles a través de una interfaz uniforme, y no son accesibles desde un solo sitio. A menudo son pequeños e incompletos individualmente, pero colectivamente proporcionarían una base de datos interesante y útil de palabras en inglés. Ejemplos incluyen el archivo Jargon, la base de datos WordNet, la versión de MICRA del Diccionario Webster Revisado y Completo de 1913, y el Diccionario Libre en Línea de Computación. (Vea la especificación del protocolo DICT (RFC) para las referencias.) Los diccionarios de traducción y no ingleses también se están haciendo disponibles (por ejemplo, el diccionario FOLDOC está siendo traducido al español)

.

El protocolo webster no es adecuado para proporcionar acceso a un gran número de bases de datos de diccionarios separadas, y las extensiones al protocolo webster actual no se consideraron una solución limpia al problema de la base de datos de

diccionarios.

El protocolo DICT está diseñado para proporcionar acceso a múltiples bases de datos. Se pueden solicitar definiciones de palabras, se puede buscar el índice de palabras (usando un conjunto de algoritmos fácilmente extensible), se puede proporcionar información sobre el servidor (p. ej., qué estrategias de búsqueda de índice se admiten, o qué bases de datos están disponibles), y se puede proporcionar información sobre una base de datos (p. ej., información de derechos de autor, cita o distribución). Además, el protocolo DICT tiene ganchos que pueden usarse para restringir el acceso a algunas o todas las bases de

datos.

dictd(8) es un servidor que implementa el protocolo DICT. Bret Martin implementó otro servidor, y var

ias personas (incluyendo a Bret y a mí mismo) han
implementado clientes en una variedad de lenguajes.

Especificación de
Acceso
Las especificaciones de acceso pueden aparecer en la Sección de Acceso o en la Sección de Base de Datos. La especificación de acceso se describirá aquí.

Para allow, deny y authonly, se puede usar un asterisco (*) como comodín que coincide con cualquier número de caracteres. Se puede usar un signo de interrogación (?) como comodín que coincide con un solo carácter. Por ejemplo, 10.0.0.* y *.edu son cadenas

válidas.

Además, se puede especificar un rango de direcciones IP y una dirección IP seguida de una máscara de red. Por ejemplo, 10.0.0.0:10.0.0.255, 10.0.0.0/24 y 10.0.0.* especifican todos el mismo rango de números IP. La notación no se puede combinar en la misma línea. Si la notación no tiene sentido, el acceso se denegará por defecto. Use la opción --debug auth para depurar problemas

relacionados.

Tenga en cuenta que estas especificaciones toman solo una cadena por línea de especificación. Sin embargo, puede tener múltiples líneas de cada

tipo.

La sintaxis es la

siguiente:
allow caden
a
La cadena especifica un nombre de dominio o dirección IP al que se le permite el acceso al servidor (en la Sección de Acceso) o a una base de datos (en la Sección de Base de Datos). Tenga en cuenta que no se permite más de una cadena para una sola línea "allow", pero se permiten más de una línea "allow" en el archivo de
configuración.
deny caden
a
La cadena especifica un nombre de dominio o dirección IP al que se le deniega el acceso al servidor (en la Sección de Acceso) o a una base de datos (en la Sección de Base de Datos). Tenga en cuenta que si el DNS inverso no funciona, entonces solo se comprobará el número IP. Por lo tanto, es esencial denegar redes basándose en el número IP, ya que una denegación basada en el nombre de dominio puede no comprobarse
siempre.
authonly caden
a
Esta forma solo es útil en la Sección de Acceso. La cadena especifica un nombre de dominio o dirección IP al que se le permite el acceso al servidor pero no a ninguna de las bases de datos. Todos los comandos son válidos excepto DEFINE, MATCH y SHOW DB. Más específicamente, AUTH es un comando válido, y los comandos que acceden a las bases de datos no están
permitidos.
user caden
a
Esta forma solo es útil en la Sección de
Base de Datos. La cadena especifica
un nombre de usuario al que se le permite
acceder a esta base de datos despu
és de ejecutar con éxito el comando AUTH.
Especificación de Configuración
Global
Esta sección describe los siguientes parámetros:
port cadena_o_núme
ro
Especifica el puerto o el nombre del servicio (p. ej., 2628). El valor por defecto es 2628, como se especifica en el RFC del Protocolo DICT, pero puede cambiarse en el archivo defs.h en tiempo de compilación (DICT_DEFAULT_SERVICE)
.
site caden
a
Se usa para especificar el nombre de archivo para el archivo de información del sitio., un archivo de texto plano que se mostrará en respuesta al comando SHOW SERVER.

EJEMPLO: Ver el archivo examples/dictd4.conf de la distribución.

site_no_banner booleano
Por defecto, el comando SHOW SERVER muestra información sobre la versión de dictd y el tipo de sistema operativo. Esta opción lo deshabilita.
site_no_uptime booleano
Por defecto, el comando SHOW SERVER muestra información sobre el tiempo de actividad de dictd, el número de bifurcaciones desde el inicio y bifurcaciones por hora. Esta opción lo deshabilita.
site_no_dblist booleano
Por defecto, el comando SHOW SERVER muestra información interna sobre las bases de datos, como el número de lemas, el tamaño del índice, etc. Esta opción lo deshabilita.
delay número
Especifica el número de segundos que un cliente puede estar inactivo antes de que el servidor cierre la conexión. El tiempo de inactividad se define como el tiempo que el servidor está esperando entrada y no incluye el tiempo que el servidor pasa buscando en la base de datos. El valor por defecto es 0 segundos (sin límite), pero puede cambiarse en el archivo defs.h en tiempo de compilación (DICT_DEFAULT_DELAY).
NOTA: Establecer la opción delay deshabilita la opción limit_time. Solo una de ellas (la última especificada en dictd.conf) estará en efecto.

NOTA: Las conexiones se cierran sin previo aviso ya que no se especifica ninguna disposición para la terminación prematura de la conexión en el RFC del protocolo DICT.

depth número
Especifica la longitud de la cola para listen(2). Especifica el número de conexiones de socket pendientes que son puestas en cola por el sistema operativo. Algunos sistemas operativos pueden limitar silenciosamente este valor a 5 (sistemas BSD más antiguos) o 128 (Linux). El valor por defecto es 10, pero puede cambiarse en el archivo defs.h en tiempo de compilación (DICT_QUEUE_DEPTH).
limit_childs número
Especifica el número de demonios que pueden ejecutarse simultáneamente. Cada demonio atiende una única conexión. Si se excede el límite, el proceso servidor realizará una conexión (serializada) y enviará un código de respuesta 420 (servidor temporalmente no disponible) al cliente. Este parámetro debe ajustarse para evitar que la máquina servidora se sobrecargue por los clientes de dict, pero no debe fijarse tan bajo que se nieguen conexiones útiles a muchos clientes. El valor por defecto es 100, pero puede cambiarse en el archivo defs.h en tiempo de compilación (DICT_DAEMON_LIMIT_CHILDS).
limit número
Sinónimo de limit_childs. Solo por compatibilidad hacia atrás.
limit_matches número
Especifica el número máximo de coincidencias que pueden ser devueltas por una consulta MATCH. Cero significa sin límite. El valor por defecto es 2000.
limit_definitions número
Especifica el número máximo de definiciones que pueden ser devueltas por una consulta DEFINE. Cero significa sin límite. El valor por defecto es 200.
limit_time número
Especifica el número de segundos que un cliente puede hablar con el servidor antes de que el servidor cierre la conexión. El valor por defecto es 600 segundos (10 minutos), pero puede cambiarse en el archivo defs.h en tiempo de compilación (DICT_DEFAULT_LIMIT_TIME).

NOTA: Establecer la opción limit_time deshabilita la opción delay. Solo una de ellas (la última especificada en dictd.conf) estará en efecto.

NOTA: Las conexiones se cierran sin previo aviso ya que no se especifica ninguna disposición para la terminación prematura de la conexión en el RFC del protocolo DICT.

limit_queries número
Especifica el número de consultas (MATCH, DEFINE, SHOW DB etc.) que un cliente puede enviar al servidor antes de que el servidor cierre la conexión. Cero significa sin límite. El valor por defecto es 2000, pero puede cambiarse en el archivo defs.h en tiempo de compilación (DICT_DEFAULT_LIMIT_QUERIES).
timestamp número
Cada cuántos minutos se debe registrar una marca de tiempo. (Esto solo es efectivo si se ha habilitado el registro con la opción -s o -L, o con una opción de depuración).
log_option opción
Especifica una opción de registro. Esto solo es efectivo si el registro se ha habilitado con la opción -s o -L o en el archivo de configuración, o si se ha activado el registro en la consola con una opción de depuración (por ejemplo, --debug nodetach. Solo se puede establecer una opción con cada invocación de esta opción; sin embargo, se pueden hacer múltiples invocaciones de esta opción en el archivo de configuración o en la línea de comandos de dictd. Por ejemplo:
dictd -s --log stats --log found --log notfound
es una línea de comandos válida y establece tres opciones de registro.

server
Registra diagnósticos del servidor. Esto es extremadamente detallado.
connect
Registra todas las conexiones.
stats
Registra todas las terminaciones de hijos.
command
Registra todos los comandos. Esto es extremadamente detallado.
client
Registra los resultados del comando CLIENT.

Registra todas las palabras encontradas en las bases de datos.
notfound
Registra todas las palabras no encontradas en las bases de datos.

Al registrar en un archivo, usa una marca de tiempo completa como la que produciría syslog. De lo contrario, no se realiza ninguna marca de tiempo, lo que hace que los archivos sean más cortos.

Para facilitar la localización de información interesante en el archivo de registro, las entradas están marcadas con letras iniciales que indican la clase de la línea que se está registrando:

Información sobre el servidor, conexiones o estadísticas de terminación. Estas líneas generalmente no están diseñadas para ser analizadas automáticamente.
E
Mensajes de error.
C
Información del comando CLIENT.
D
Definiciones encontradas en las bases de datos buscadas.
M
Coincidencias encontradas en la base de datos buscada.
N
Coincidencias que no se encontraron en las bases de datos buscadas.
T
Rastreo de la línea exacta enviada por el cliente.
A
Información de autenticación.

Para preservar el anonimato del cliente, no utilice las opciones connect o host. Los clientes pueden o no enviar información del host utilizando el comando CLIENT, pero esta debe ser una opción seleccionable por el cliente.

debug_option cadena
Activa una opción de depuración. Hay varias, todas ellas solo útiles para los desarrolladores. Se documentan aquí por completitud. Se puede obtener una lista interactivamente usando -d con una opción ilegal.
verbose
Lo mismo que -v o --verbose. Añade verbosidad a otras opciones.
scan
Depura el escáner para el archivo de configuración.
parse
Depura el analizador para el archivo de configuración.
search
Depura las rutinas de plegado de caracteres y búsqueda binaria.
init
Informa de la inicialización de la base de datos.
port
Registra el número de puerto del lado del cliente en el archivo de registro.

Depura el algoritmo de búsqueda de Levenshtein.

Depura las rutinas de autorización.

Especifica la configuración regional utilizada para la búsqueda. Si no se especifica ninguna configuración regional, se utiliza la configuración regional "C". La configuración regional utilizada para el servidor debería ser la misma que la

DICTIONARY SPECIFICATION

The dictionary specification is a text file that contains information about a dictionary. It is used by the dictd daemon to configure itself. The dictionary specification file must be owned by the root user and must be writable only by root. If this is not the case, the dictd daemon will not load the dictionary. The dictionary specification file is an ASCII text file that contains a list of key/value pairs. Keys are case sensitive. The values are generally strings or numbers, but may also be a list of strings or numbers. Key/value pairs are separated by whitespace. Comments may be included in the file by starting a line with the # character.

There are two types of dictionaries: virtual and real. A real dictionary is a dictionary that is stored on disk. A virtual dictionary is a dictionary that is not stored on disk, but is instead generated dynamically by the dictd daemon. The dictionary specification file is used to configure both real and virtual dictionaries.

The following is a list of all possible keywords in a dictionary specification file:

name string
Specifies the short name of the dictionary. This is the name that will be used by the clients to refer to the dictionary. See Database Specification for more information.
info string
Specifies the information about the dictionary. This is a short description of the dictionary that will be displayed to the clients. See Database Specification for more information.
file string
Specifies the path to the dictionary file. This is only used for real dictionaries. See Database Specification for more information.
index_file string
Specifies the path to the index file for the dictionary. This is only used for real dictionaries. See Database Specification for more information.
stream
Specifies that the dictionary is a stream dictionary. Stream dictionaries are not indexed, and thus must be searched linearly. See Database Specification for more information.
database string
Specifies the name of the database to be used for lookups. This is only used for virtual dictionaries. See Database Specification for more information.
auth
Specifies that the dictionary requires authentication. This means that clients must be authenticated before they can access the dictionary. See Database Specification for more information.
compress
Specifies that the dictionary is compressed. This means that the dictionary file is compressed using the gzip compression algorithm. See Database Specification for more information.
visit
Specifies that the dictionary is a visit dictionary. Visit dictionaries are dictionaries that are used to store information about the clients that have accessed the server. See Database Specification for more information.
rewrite string
Specifies a rewrite rule for the dictionary. This rule is used to rewrite queries before they are sent to the dictionary. See Database Specification for more information.
check
Specifies that the dictionary should be checked for validity. This means that the dictd daemon will check the dictionary for errors before it is loaded. See Database Specification for more information.
check_script string
Specifies the path to the script that should be used to check the validity of the dictionary. See Database Specification for more information.
invisible
Makes dictionary invisible to the clients. See Database Specification for more information.
disable_strategy string
Disables the specified strategy for database. See Database Specification for more information.
default_strategy string
Sets the default search strategy for database. See Database Specification for more information.

DETERMINATION OF ACCESS LEVEL

When a client connects, the global access specification is scanned, in order, until a specification matches. If no access specification exists, all access is allowed (e.g., the action is the same as if "allow *" was the only item in the specification). For each item, both the hostname and IP are checked. For example, consider the following access specification:

allow 10.42.*
authonly *.edu
deny *
With this specification, all clients in the 10.42 network will be allowed access to unrestricted databases; all clients from *.edu sites will be allowed to authenticate, but will be denied access to all databases, even those which are otherwise unrestricted; and all other clients will have their connection terminated immediately. The 10.42 network clients can send an AUTH command and gain access to restricted databases. The *.edu clients must send an AUTH command to gain access to any databases, restricted or unrestricted.

When the AUTH command is sent, the access list for each database is scanned, in order, just as the global access list is scanned. However, after authentication, the client has an associated username. For example, consider the following access specification:

user u1
deny *.com
user u2
allow *
If the client authenticated as u1, then the client will have access to this database, even if the client comes from a *.com site. In contrast, if the client authenticated as u2, the client will only have access if it does not come from a *.com site. In this case, the "user u2" is redundant, since that client would also match "allow *".

Warning: Checks are performed for domain names and for IP addresses. However, if reverse DNS for a specific site is not working, it is possible that a domain name may not be available for checking. Make sure that all denials use IP addresses. (And consider a future enhancement: if a domain name is not available, should denials that depend on a domain name match anything? This is the more conservative viewpoint, but it is not currently implemented.)

SEARCH ALGORITHMS

The DICT standard specifies a few search algorithms that must be implemented, and permits others to be supported on a server-dependent basis. The following search strategies are supported by this server. Note that all strategies are case insensitive. Most ignore non-alphanumeric, non-whitespace characters.

exact
An exact match. This algorithm uses a binary search and is one of the fastest search algorithms available.
lev
The Levenshtein algorithm (string edit distance of one). This algorithm searches for all words which are within an edit distance of one from the target word. An "edit" means an insertion, deletion, or transposition. This is a rapid algorithm for correcting spelling errors, since many spelling errors are within a Levenshtein distance of one from the original word.
prefix
Prefix match. This algorithm also uses a binary search and is very fast.
nprefix
Like prefix but returns the specified range of matches. For example, when prefix strategy returns 1000 matches, you can get only 100 ones skipping the first 800 matches. This is made by specified these limits in a query like this: 800#100#app, where 800 is skip count, 100 is a number of matches you want to get and "app" is your query. This strategy allows to implement DICT client with fast autocompletion (although it is not trivial) just like many standalone dictionary programs do.
NOTE: If you access the dictionary "*" (or virtual one) with nprefix strategy, the same range is set for each database in it, but globally for all matches found in all databases.
NOTE: In case you access non-english dictionary the returned matches may be (and mostly will be) NOT ordered in alphabetic order.
re
POSIX 1003.2 (modern) regular expression search. Modern regular expressions are the ones used by egrep(1). These regular expressions allow predefined character classes (e.g., [[:alnum:]], [[:alpha:]], [[:digit:]], and [[:xdigit:]] are useful for this application); uses * to match a sequence 0 or more matches of the previous atom; uses + to match a sequence of 1 or more matches of the previous atom; uses ? to match a sequence of 0 or 1 matches of the previous atom; used ^ to match the beginning of a word, uses $ to match the end of a word, and allows nested subexpression and alternation with () and |. For example, "(foo|bar)" matches all words that contain either "foo" or "bar". To match these special characters, they must be quoted with two backslashes (due to the quoting characteristics of the server). Warning: Regular expression matches can take 10 to 300 times longer than substring matches. On a busy server, with many databases, this can required more than 5 minutes of waiting time, depending on the complexity of the regular expression.
regexp
Old (basic) regular expressions. These regular expressions don't support |, +, or ?. Groups use escaped parentheses. While modern regular expressions are generally easier to use, basic regular expressions have a back reference feature. This can be used to match a second occurrence of something that was already matched. For example, the following expression finds all words that begin and end with the same three letters:
    ^\\(...\\).*\\1$

Note the use of the double backslashes to escape the special characters. This is required by the DICT protocol string specification (a single backslash quotes the next character -- we use two to get a single backslash through to the regular expression engine). Warning: Note that the use of backtracking is even slower than the use of general regular expressions.

soundex
The Soundex algorithm, a classic algorithm for finding words that sound similar to each other. The algorithm encodes each word using the first letter of the word and up to three digits. Since the first letter is known, this search is relatively fast, and it sometimes good for correcting spelling errors when the Levenshtein algorithm doesn't help.
substring
Match a substring anywhere in the headword. This search strategy uses a modified Boyer-Moore-Horspool algorithm. Since it must search the whole index file, it is not as fast as the exact and prefix matches.
suffix
Suffix match. This search strategy also uses a modified Boyer-Moore-Horspool algorithm, and is as fast as the substring search. If the optional index_suffix string file is listed in the configuration file this search is much faster.
word
Match any single word, even if part of a multi-word entry. If the optional index_word string file is listed in the configuration file this search strategy works much faster.
first
Match the first word that begins a multi-word entry.
last
Match the last word that ends a multi-word entry. If the optional index_suffix string file is listed in the configuration file this search strategy works much faster.

DATABASE FORMAT

The DICT server supports databases in the following formats:

default
This is the default format. It is a text file where each line is a dictionary entry. Each entry consists of a headword, followed by a colon, followed by the definition. The headword and definition are separated by a tab character. For example:
    Apple	A fruit that is red or green.
    Banana	A yellow fruit that is long and curved.
dictzip
This format is similar to the default format, but the file is compressed using the gzip compression algorithm. The file extension is typically .dz.
foreign
This format is used for dictionaries that contain non-ASCII characters. The file is encoded using UTF-8. The headword and definition are separated by a tab character. For example:
    Élan	A sense of style or flair.
    Götterdämmerung	The twilight of the gods.
mime
This format is used for dictionaries that contain MIME-encoded data. The file is encoded using UTF-8. The headword and definition are separated by a tab character. The definition may contain MIME-encoded data, such as HTML or images. For example:
    HTML	<html><body>A markup language for web pages.</body></html>
mims
This format is used for dictionaries that contain data in the Mims format. The Mims format is a database format that is used by the Mims search engine. The file is encoded using UTF-8. The headword and definition are separated by a tab character. For example:
    Mims	A search engine that is used by the DICT server.

The DICT server can also support other database formats, but these are the most common ones. The format of a database is specified in the dictionary specification file using the format keyword.

FORMATO DE BASE DE DATOS

Las bases de datos para dictd se distribuyen por separado. Una base de datos consta de dos archivos. Uno es un archivo de texto plano, el otro es el índice.

El archivo de texto plano contiene entradas del diccionario (o cualquier otro dato adecuado), y el índice contiene tuplas delimitadas por tabulaciones que consisten en la palabra clave, el desplazamiento de bytes en el que comienza esta entrada en el archivo de texto plano y la longitud de la entrada en bytes. El desplazamiento y la longitud se codifican usando codificación base 64 utilizando el subconjunto de 64 caracteres del Alfabeto Internacional IA5 discutido en RFC 1421 (codificación imprimible) y RFC 1522 (base64 MIME). Codificar los desplazamientos en base 64 ahorra espacio considerable en comparación con la codificación base 10 habitual, al tiempo que permite usar caracteres de tabulación (ASCII 9) para delimitar campos en un registro. Cada registro termina con un salto de línea (ASCII 10), por lo que el archivo de índice es legible por humanos.

Algunas palabras clave son utilizadas especialmente por dictd:

00-database-info Contiene la información sobre la base de datos que se devuelve con el comando SHOW INFO, a menos que se especifique en el archivo de configuración.

00-database-short Contiene el nombre corto de la base de datos que se devuelve con el comando SHOW DB, a menos que se especifique en el archivo de configuración. Ver dictfmt -s.

00-database-url URL de donde se obtuvieron las fuentes originales del diccionario. Ver dictfmt -u. Esta palabra clave no es utilizada por dictd

00-database-utf8 Presente si el diccionario está codificado usando UTF-8. Ver dictfmt --utf8

00-database-8bit-new Presente si el diccionario está codificado usando un conjunto de caracteres de 8 bits (no ASCII ni UTF8). Ver dictfmt --locale.

El archivo de texto plano puede comprimirse usando gzip(1) (no recomendado) o dictzip(1) (altamente recomendado). Se obtendrá una velocidad óptima utilizando un archivo sin comprimir. Sin embargo, el algoritmo de compresión gzip funciona muy bien en texto plano y puede resultar en ahorros de espacio típicamente entre el 60 y el 80%. No se recomienda usar un archivo comprimido con gzip(1), porque el acceso aleatorio al archivo solo se puede lograr descomprimiendo serialmente todo el archivo, un proceso que es prohibitivamente lento. dictzip(1) utiliza el mismo algoritmo de compresión y formato de archivo que gzip(1), pero proporciona una tabla que se puede utilizar para acceder aleatoriamente a bloques comprimidos en el archivo. El uso de bloques de 50-64 kB para la compresión generalmente degrada la compresión en menos del 10%, manteniendo capacidades de acceso aleatorio aceptables para todos los datos en el archivo. Como beneficio adicional, los archivos comprimidos con dictzip(1) se pueden descomprimir con gzip(1) o zcat(1). (Nota: volver a comprimir un archivo dictzip'd usando, por ejemplo, znew(1) destruirá las características de acceso aleatorio del archivo. Siempre comprima los archivos de datos usando dictzip(1).)

SEÑALES

SIGHUP hace que dictd vuelva a leer el archivo de configuración y reinicialice las bases de datos.

SIGUSR1 hace que dictd descargue las bases de datos. Luego, dictd devuelve el estado 420 (en lugar de 220). Para cargar las bases de datos nuevamente, envía la señal SIGHUP. Dado que los archivos de la base de datos se mapean(2), es imposible actualizarlos mientras dictd está en ejecución. Por lo tanto, si necesita actualizar los archivos de la base de datos y volver a leer el archivo de configuración, primero envíe la señal SIGUSR1 a dictd para descargar las bases de datos, actualice los archivos y luego envíe la señal SUGHUP para cargarlas de nuevo.
