DESCRIPCIÓ

N

debuginfod_begin() crea un debuginfod_client manejador de conexión que debe usarse con todas las demás llamadas. debuginfod_end() debe llamarse en el manejador client para liberar todo el estado y almacenamiento cuando se

termine.

debuginfod_find_debuginfo(), debuginfod_find_executable(), y debuginfod_find_source() consultan las URL de los servidores debuginfod contenidas en $DEBUGINFOD_URLS (véase más abajo) para el debuginfo, el ejecutable o el archivo fuente con el build_id dado. build_id debe ser un puntero a una cadena hex en minúsculas terminada por nulo o a un blob binario. Si build_id se da como cadena hex, build_id_len debe ser 0. De lo contrario build_id_len debe ser el número de bytes en el blob

binario.

debuginfod_find_source() también requiere un filename para especificar un archivo fuente en particular. filename debe ser una ruta absoluta que incluya el directorio de compilación de la CU asociada con el archivo fuente. Los nombres de ruta relativos aparecen comúnmente en el directorio de fuentes del archivo DWARF, pero estas rutas son relativas a las rutas AT_comp_dir de las unidades de compilación individuales, y sin embargo un ejecutable está compuesto de múltiples CUs. Por lo tanto, para desambiguar, debuginfod espera que las consultas de fuentes prefijen los nombres de ruta relativos con el directorio de compilación de la CU, seguido de una barra "/"

obligatoria.

Nota: el llamante puede o no omitir ../ o /./ o componentes de ruta superfluos /// en los nombres de directorio. debuginfod acepta ambas formas. Específicamente, debuginfod canonicaliza los nombres de ruta de acuerdo con la sección 5.2.4 de RFC3986 (Eliminar segmentos de punto), además de reducir cualquier // a / en la

ruta.

debuginfod_find_section() consulta las URL de los servidores debuginfod contenidas en $DEBUGINFOD_URLS para los contenidos binarios de una sección ELF/DWARF contenida en un archivo debuginfo o ejecutable con el build_id dado. section debe ser el nombre de la sección ELF/DWARF deseada. Si un servidor no soporta consultas de secciones, debuginfod_find_section puede consultar al servidor por el debuginfo y/o el ejecutable con build_id para recuperar y extraer la

sección.

debuginfod_find_metadata() consulta todas las URL de servidores debuginfod contenidas en $DEBUGINFOD_URLS para metadatos de todas las coincidencias de una consulta clave/valor dada contra archivos en sus índices. El archivo resultante es un documento JSON. Véase la página man debuginfod-find(1) para ejemplos de los tipos soportados de consultas clave/valor y sus resultados

JSON.

Si path no es NULL y la consulta es exitosa, path se establece en la ruta del archivo en la caché. El llamante debe hacer free() de este

valor.

Las URL en $DEBUGINFOD_URLS pueden consultarse en paralelo. Tan pronto como un servidor debuginfod comienza a transferir el archivo de destino, todas las conexiones con los otros servidores se

cierran.

Un manejador client debe usarse desde un solo hilo a la vez. Un manejador puede reutilizarse para una s

erie de búsquedas, lo que puede mejorar el rendi
miento debido a la retención de conexiones y cachés.

RETORNO

debuginfod_begin devuelve el manejador debuginfod_client para usar con todas las demás llamadas. En caso de error se devolverá NULL y se establecerá

errno.

Si una función de la familia find es exitosa, el archivo resultante se guarda en la caché del cliente y se devuelve un descriptor de archivo para ese archivo. El descriptor de archivo apunta al inicio del archivo. El llamante necesita close() este descriptor. De lo contrario, s

e devuelve un cód
igo de error negativo.

OPCIONALES

Hay disponibles un pequeño número de funciones opcionales para ajustar o consultar la operación del cliente

RETROALIMENTACIÓN DE

PROGRESO

Dado que las funciones debuginfod_find_*() pueden bloquearse durante segundos o más, se llama periódicamente a una función de retroalimentación de progreso, si se configura con debuginfod_set_progressfn(). Esta función establece una nueva función de retroalimentación de progreso (o NULL) para el manejador del

cliente.

La función de retroalimentación dada se llama desde el contexto de cada hilo que invoca cualquiera de las otras funciones de búsqueda. Se le dan dos parámetros numéricos que, si se piensan como un numerador a y un denominador b, representan juntos una fracción de finalización a/b. El denominador puede ser cero inicialmente, hasta que una cantidad como el tamaño exacto de descarga se

conozca.

La función de retroalimentación de progreso también es la forma soportada de interrumpir la operación de descarga. (La biblioteca no modifica ni dispara señales.) La retroalimentación de progreso debe devolver 0 para continuar el trabajo, o cualquier otro valor para detener el trabajo lo antes posible. En consecuencia, la función debuginfod_find_*() probablemente devolverá co

n un error, pero podría
tener éxito de todos modos.

DETALLADA

Para mostrar cómo se maneja una consulta se puede usar debuginfod_set_verbose_fd() para establecer un descriptor de archivo particular en

el que se da salida detallada sobre los pasos de l

CABECERA

HTTP

Antes de que se inicie cada función de búsqueda, una aplicación cliente puede añadir cabeceras de solicitud HTTP. Estas se restablecen después de cada función de búsqueda. debuginfod_add_http_header() se puede llamar con cadenas de la forma "Header: value". Estas cadenas son copiadas por la biblioteca. Un valor de retorno cero indica éxito, pero las condiciones de falta de memoria pueden resultar en un valor distinto de cero -ENOMEM. Si la cadena tiene el formato incorrecto, se devolverá

-EINVAL.

$DEBUGINFOD_HEADERS_FILE especifica un archivo para proporcionar cabeceras a las solicitudes salientes. Cada línea de este archivo que no esté en blanco se maneja como si se llamara a debuginfod_add_http_header() con su

contenido.

Tenga en cuenta que la implementación actual de la biblioteca debuginfod-client usa libcurl, pero no debe depender de ese hecho. No use esta función para reemplazar cabeceras estándar, excepto para el User-Agent mencionado a continuación. Puede usar esta función para añadir información de autorización para el control de acceso, o para proporcionar cabeceras opcionales al servidor con fines de

registro.

Por defecto, la biblioteca añade una cabecera User-Agent: descriptiva a las solicitudes salientes. Si la aplicación cliente añade una cabecera con el mismo nombre, esta cabecera predeterminada se

suprime.

Durante o después de una búsqueda, una aplicación cliente puede llamar a debuginfod_get_headers() para recopilar el subconjunto de cabeceras de respuesta HTTP recibidas del servidor debuginfod actual o más reciente. Solo se conservan aquellas cabeceras con el prefijo X-DEBUGINFOD (sin distinguir mayúsculas de minúsculas). Se devuelven como una sola cadena, con cada "header: value" terminado con un \n (no \r\n como

en HTTP). Puede ser NULL. La cadena resultante es propiedad de la bibliot
eca y no debe ser modificada ni liberada. El llamante debe copiar la cadena
devuelta si necesita usarla más allá de la liberación del objeto cliente.

SEGURIDA

D

Si están disponibles firmas IMA de los RPM que contienen los archivos solicitados, entonces debuginfod extraerá esas firmas en cabeceras de respuesta, y debuginfod_find_*() realizará la verificación sobre los archivos. La política de validación se controla mediante etiquetas insertadas en $DEBUGINFOD_URLS. Por defecto, debuginfod_find_*() actúa en modo de

ignorar.

Si se accede a través de HTTP en lugar de HTTPS, la red debe ser de confianza. La información de autenticación a través de la biblioteca interna libcurl no está habilitada actualmente, excepto para el estilo de texto plano básico http[s]://userid:password@hostname/. (El servidor debuginfod no realiz

a autenticación, pero un servidor
proxy de front-end podría hacerlo.)

CACH

É

Antes de cada consulta, la biblioteca cliente debuginfod comprueba si es necesario limpiar la caché. Si es hora de limpiar, la biblioteca recorre el directorio de caché y eliminaves descargados artefactos relacionados con debuginfo y directorios recientemente vacíos, si no han sido accedidos

recientemente.

Los archivos de control se encuentran directamente bajo el directorio de caché. Contienen números decimales simples para establecer parámetros de configuración relacionados con la caché. Si los archivos no existen, la biblioteca de cliente crea los archivos con los valores de parámetros predeterminados como

contenido.

Después de cada consulta, la biblioteca de cliente de debuginfod deposita los archivos recién recibidos en un directorio y archivo cuyo nombre se basa en el build-id. Una consulta fallida también se almacena en caché mediante un archivo especial. La convención de nombrado utilizada para estos artefactos es deliberadamente no documen

tada.
