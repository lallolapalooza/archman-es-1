DESCRIPCIÓ

N

debuginfod_begin() crea un debuginfod_client manejo de conexión que debe usarse con todas las demás llamadas. debuginfod_end() debe llamarse en el manejo de cliente para liberar todo el estado y el almacenamiento cuando se

termine.

debuginfod_find_debuginfo(), debuginfod_find_executable() y debuginfod_find_source() consultan las URLs de los servidores debuginfod contenidas en $DEBUGINFOD_URLS (véase más abajo) para el archivo debuginfo, ejecutable o fuente con el build_id dado. build_id debe ser un puntero a una cadena hexadecimal en minúsculas terminada por un nulo o a un blob binario. Si build_id se da como una cadena hexadecimal, build_id_len debe ser 0. En caso contrario build_id_len debe ser el número de bytes en el blob

binario.

debuginfod_find_source() también requiere un filename para especificar un archivo fuente particular. filename debe ser una ruta absoluta que incluya el directorio de compilación de la CU asociada con el archivo fuente. Los nombres de ruta relativos aparecen comúnmente en el directorio de fuentes del archivo DWARF, pero estas rutas son relativas a las rutas AT_comp_dir de las unidades de compilación individuales, y sin embargo un ejecutable está compuesto de múltiples CUs. Por lo tanto, para desambiguar, debuginfod espera que las consultas de fuentes prefijen los nombres de ruta relativos con el directorio de compilación de la CU, seguido de una barra "/"

obligatoria.

Nota: el llamante puede o no omitir ../ o /./ o componentes de ruta /// superfluos en los nombres de directorio. debuginfod acepta ambas formas. Específicamente, debuginfod canonicaliza los nombres de ruta de acuerdo con la sección 5.2.4 de RFC3986 (Eliminar Segmentos de Punto), además de reducir cualquier // a / en la

ruta.

debuginfod_find_section() consulta las URLs de los servidores debuginfod contenidas en $DEBUGINFOD_URLS para los contenidos binarios de una sección ELF/DWARF contenida en un archivo debuginfo o ejecutable con el build_id dado. section debe ser el nombre de la sección ELF/DWARF deseada. Si un servidor no soporta consultas de secciones, debuginfod_find_section puede consultar al servidor por el debuginfo y/o el ejecutable con build_id para recuperar y extraer la

sección.

debuginfod_find_metadata() consulta todas las URLs de servidores debuginfod contenidas en $DEBUGINFOD_URLS para los metadatos de todas las coincidencias de una consulta de clave/valor dada contra los archivos en sus índices. El archivo resultante es un documento JSON. Véase la página del manual debuginfod-find(1) para ejemplos de los tipos de consultas de clave/valor soportadas y sus resultados

JSON.

Si path no es NULL y la consulta es exitosa, path se establece en la ruta del archivo en la caché. El llamante debe hacer free() de este

valor.

Las URLs en $DEBUGINFOD_URLS pueden consultarse en paralelo. Tan pronto como un servidor debuginfod comienza a transferir el archivo objetivo, todas las conexiones con los otros servidores se

cierran.

Un manejo de cliente debe usarse desde un solo hilo a la vez. Un manejo puede reutilizarse para una se

rie de búsquedas, lo que puede mejorar el rendi
miento debido a la retención de conexiones y cachés.

VALOR DE

RETORNO

debuginfod_begin devuelve el manejo debuginfod_client para usar con todas las demás llamadas. En caso de error se devolverá NULL y errno se

establecerá.

Si una función de la familia find es exitosa, el archivo resultante se guarda en la caché del cliente y se devuelve un descriptor de archivo para ese archivo. El descriptor de archivo apunta al comienzo del archivo. El llamante necesita cerrar() este descriptor. De lo contrario,

se devuelve un códi
go de error negativo.

FUNCIONES

OPCIONALES

Hay disponibles un pequeño número de funciones opcionales para ajustar o consultar la operación del cliente

debuginfod.

RETROALIMENTACIÓN DE

PROGRESO

Dado que las funciones debuginfod_find_*() pueden bloquearse durante segundos o más, una función de retroalimentación de progreso se llama periódicamente, si se configura con debuginfod_set_progressfn(). Esta función establece una nueva función de retroalimentación de progreso (o NULL) para el manejo del

cliente.

La función de retroalimentación dada se llama desde el contexto de cada hilo que está invocando cualquiera de las otras funciones de búsqueda. Se le dan dos parámetros numéricos que, si se piensan como un numerador a y un denominador b, representan juntos una fracción de finalización a/b. El denominador puede ser cero inicialmente, hasta que una cantidad como el tamaño exacto de descarga se

conozca.

La función de retroalimentación de progreso también es la forma soportada de interrumpir la operación de descarga. (La biblioteca no modifica ni activa señales.) La retroalimentación de progreso debe devolver 0 para continuar el trabajo, o cualquier otro valor para detener el trabajo lo antes posible. En consecuencia, la función debuginfod_find_*() probablemente retornará co

n un error, pero podría
tener éxito de todos modos.

SALIDA

DETALLADA

Las funciones debuginfod_find_*() pueden usar varias técnicas para recuperar los archivos solicitados, a través de la caché o a través de uno o múltiples servidores o URLs de archivos. Para mostrar cómo se maneja una consulta, se puede usar debuginfod_set_verbose_fd() para establecer un descriptor de archivo particular en

el que se da salida detallada sobre los pasos de l
a consulta y los errores finales encontrados.

URL

URL

La URL de la descarga saliente actual o más reciente, si se conoce, puede recuperarse mediante debuginfod_get_url() desde la devolución de llamada progressfn, o después. Puede ser NULL. La cadena resultante es propiedad de la biblioteca y no debe modificarse ni liberarse. El llamador debería copiarla si es necesaria más allá de la liberación del objeto cliente.

ENCABEZADO HTTP

Antes de iniciar cada función de búsqueda, una aplicación cliente puede agregar encabezados de solicitud HTTP. Estos se restablecen después de cada función de búsqueda. Se puede llamar a debuginfod_add_http_header() con cadenas del formato "Encabezado: valor". Estas cadenas son copiadas por la biblioteca. Un valor de retorno cero indica éxito, pero las condiciones de falta de memoria pueden resultar en un valor distinto de cero -ENOMEM. Si la cadena tiene el formato incorrecto, se devolverá -EINVAL.

$DEBUGINFOD_HEADERS_FILE especifica un archivo para proporcionar encabezados a las solicitudes salientes. Cada línea no vacía de este archivo se maneja como si se hubiera llamado a debuginfod_add_http_header() con su contenido.

Tenga en cuenta que la implementación actual de la biblioteca debuginfod-client utiliza libcurl, pero no debe confiar en ese hecho. No utilice esta función para reemplazar ningún encabezado estándar, excepto el User-Agent mencionado a continuación. Puede utilizar esta función para agregar información de autorización para control de acceso, o para proporcionar encabezados opcionales al servidor para fines de registro.

Por defecto, la biblioteca agrega un encabezado descriptivo User-Agent: a las solicitudes salientes. Si la aplicación cliente agrega un encabezado con el mismo nombre, este predeterminado se suprime.

Durante o después de una búsqueda, una aplicación cliente puede llamar a debuginfod_get_headers() para recopilar el subconjunto de encabezados de respuesta HTTP recibidos del servidor debuginfod actual o más reciente. Solo se conservan aquellos encabezados prefijados con X-DEBUGINFOD (sin distinción de mayúsculas y minúsculas). Se devuelven como una única cadena, con cada "encabezado: valor" terminado con \n (no \r\n como en HTTP). Puede ser NULL. La cadena resultante es propiedad de la biblioteca y no debe modificarse ni liberarse. El llamador debe copiar la cadena devuelta si es necesaria más allá de la liberación del objeto cliente.

void *debuginfod_so = dlopen(DEBUGINFOD_SONAME, RTLD_LAZY);

SEGURIDAD

Si las firmas IMA están disponibles en los RPM que contienen los archivos solicitados, debuginfod extraerá esas firmas en encabezados de respuesta, y debuginfod_find_*() realizará la verificación sobre los archivos. La política de validación se controla mediante etiquetas insertadas en $DEBUGINFOD_URLS. Por defecto, debuginfod_find_*() actúa en modo ignorar.

Si se accede a través de HTTP en lugar de HTTPS, la red debe ser confiable. La información de autenticación a través de la biblioteca interna libcurl no está habilitada actualmente, excepto por el estilo básico de texto plano http[s]://userid:password@hostname/. (El servidor debuginfod no realiza autenticación, pero un servidor proxy frontal podría hacerlo).

ERRORES

La siguiente lista no es exhaustiva. Los códigos de error también pueden originar de llamadas a varias funciones de la Biblioteca C.

EACCESS
Acceso denegado al recurso ubicado en la URL.
ECONNREFUSED
No se pudo conectar al host remoto. También se devuelve cuando no se pudo verificar una conexión HTTPS (certificado incorrecto).
ECONNRESET
No se pudo enviar ni recibir datos de red.
EHOSTUNREACH
No se pudo resolver el host remoto.
EINVAL
Uno o más argumentos tienen un formato incorrecto. build_id puede ser demasiado largo (mayor de 256 caracteres), filename puede no ser una ruta absoluta o una URL de debuginfod está mal formada.
EIO
No se pudieron escribir los datos recibidos del servidor en el archivo local.
EMLINK
Demasiadas redirecciones HTTP.
ENETUNREACH
No se pudo inicializar la conexión de red.
ENOENT
No se pudo encontrar el recurso ubicado en la URL. A menudo, este código de error indica que se contactó con éxito a un servidor debuginfod, pero el servidor no pudo encontrar el archivo de destino.
ENOMEM
El sistema no puede asignar recursos.
ENOSYS
$DEBUGINFOD_URLS no está definido.
ETIME
La consulta falló debido a tiempo de espera agotado. $DEBUGINFOD_TIMEOUT y $DEBUGINFOD_MAXTIME controlan esto.
EF2BIG
La consulta se abortó porque el archivo solicitado es demasiado grande. El $DEBUGINFOD_MAXSIZE controla esto.
EBADMSG
El contenido del archivo falló la verificación IMA contra un certificado de firmante conocido.
ENOKEY
El contenido del archivo falló la verificación IMA debido a la falta de un certificado de firmante.
ENODATA
El contenido del archivo falló la verificación IMA debido a la falta de una firma.

VARIABLES DE ENTORNO

$TMPDIR
Esta variable de entorno apunta a un sistema de archivos que se utilizará para archivos temporales. El valor predeterminado es /tmp.
$DEBUGINFOD_URLS
Esta variable de entorno contiene una lista de prefijos de URL para instancias confiables de debuginfod. Los prefijos de URL alternativos están separados por espacios. Esta variable de entorno puede ser establecida por scripts de /etc/profile.d que leen archivos de /etc/debuginfod/*.urls.

Esta variable de entorno también puede contener políticas que definen etiquetas que dictan la política de respuesta para verificar firmas IMA por archivo en los RPM. A medida que la lista separada por espacios se lee de izquierda a derecha, al encontrar una etiqueta, las URLs subsiguientes hasta la próxima etiqueta se manejarán utilizando esa política especificada. Todas las URLs antes de la primera etiqueta utilizarán la política predeterminada, ima:ignore. Por ejemplo:


DEBUGINFOD_URLS="https://foo.com ima:enforcing https://bar.ca http://localhost:8002/ ima:ignore https://baz.org"

Donde foo.com y baz.org utilizan la política predeterminada de ignore y bar.ca y localhost utilizan una política de enforcing. La etiqueta de política puede ser una de las siguientes:

ima:enforcing Cada archivo descargado requiere una firma válida, protegiendo completamente la integridad.
ima:ignore Omite la verificación por completo, sin proporcionar protección.

Las alertas de fallo de validación se dirigirán según lo especificado en $DEBUGINFOD_VERBOSE.

$DEBUGINFOD_CACHE_PATH
Esta variable de entorno rige la ubicación de la caché donde se guardan los archivos descargados y los archivos de control de caché. El directorio predeterminado se elige en función de otras variables de entorno, véase más abajo.
$DEBUGINFOD_PROGRESS
Esta variable de entorno rige la función de progreso predeterminada. Si está establecida, y si no se establece explícitamente una función de progreso, la biblioteca configurará una función de progreso predeterminada. Esta función agregará un mensaje de progreso simple periódicamente a stderr. El valor predeterminado es no generar salida de la función de progreso.
$DEBUGINFOD_VERBOSE
Esta variable de entorno rige el descriptor de archivo predeterminado para la salida detallada. Si está establecida, y si no se establece explícitamente un descriptor de archivo detallado, la salida detallada se producirá en STDERR_FILENO.
$DEBUGINFOD_RETRY_LIMIT
Esta variable de entorno rige el límite predeterminado de intentos de reintento. Si una consulta falló con un errno distinto de ENOENT, iniciará varios intentos dentro del límite.
$DEBUGINFOD_TIMEOUT
Esta variable de entorno rige el tiempo de espera para el *inicio* de la descarga para cada conexión HTTP de debuginfod. Se omite un servidor que no proporciona al menos 100K de datos dentro de esta cantidad de segundos. El valor predeterminado es 90 segundos. (Cero o negativo significa "sin tiempo de espera").
$DEBUGINFOD_MAXTIME
Esta variable de entorno dicta cuánto tiempo esperará el cliente para *completar* la descarga de un archivo encontrado en un servidor, en segundos. Es mejor usarla para garantizar que un archivo se descargue rápidamente o sea rechazado. El valor predeterminado es 0 (tiempo infinito).
$DEBUGINFOD_MAXSIZE
Esta variable de entorno dicta el tamaño máximo de un archivo a descargar en bytes. Es mejor usarla si el usuario desea asegurarse de que solo se descarguen archivos pequeños. Un valor de 0 no considera el tamaño, y el cliente puede intentar descargar un archivo de cualquier tamaño. El valor predeterminado es 0 (tamaño infinito).
$DEBUGINFOD_HEADERS_FILE
Esta variable de entorno apunta a un archivo que proporciona encabezados a las solicitudes HTTP salientes, uno por línea. Las líneas de encabezado no deben terminar con CRLF, a menos que esa sea la convención de nueva línea del sistema. Se omiten las líneas que solo contienen espacios en blanco.
$DEBUGINFOD_IMA_CERT_PATH
Esta variable de entorno contiene una lista de rutas de directorio absolutas que contienen certificados X.509 para la verificación IMA por archivo en RPM. Las rutas alternativas están separadas por dos puntos.

CACHÉ

Antes de cada consulta, la biblioteca cliente de debuginfod verifica si es necesario limpiar la caché. Si es hora de limpiar, la biblioteca recorre el directorio de la caché y elimina

CACHE

The debuginfod client library uses a cache to store downloaded debuginfo-related artifacts and newly empty directories, if they have not been accessed recently.

Control files are located directly under the cache directory. They contain simple decimal numbers to set cache-related configuration parameters. If the files do not exist, the client library creates the files with the default parameter values as content.

After each query, the debuginfod client library deposits newly received files into a directory & file that is named based on the build-id. A failed query is also cached by a special file. The naming convention used for these artifacts is deliberately undocumented.

$XDG_CACHE_HOME/debuginfod_client/
Default cache directory, if $XDG_CACHE_HOME is set.
$HOME/.cache/debuginfod_client/
Default cache directory, if $XDG_CACHE_HOME is not set.
$HOME/.debuginfod_client_cache/
Deprecated cache directory, used only if preexisting.
cache_clean_interval_s
This control file gives the interval between cache cleaning rounds, in seconds. The default is 86400, one day. 0 means "immediately".
max_unused_age_s
This control file sets how long unaccessed debuginfo-related files are retained, in seconds. The default is 604800, one week. 0 means "immediately".
cache_miss_s
This control file sets how long to remember a query failure, in seconds. New queries for the same artifacts within this time window are short-circuited (returning an immediate failure instead of sending a new query to servers). This accelerates queries that probably would still fail. The default is 600, 10 minutes. 0 means "forget immediately".
metadata_retention_s
This control file sets how long to remember the results of a metadata query. New queries for the same artifacts within this time window are short-circuited (repeating the same results). This accelerates queries that probably would probably have the same results. The default is 3600, 1 hour. 0 means "do not retain".
