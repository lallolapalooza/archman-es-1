DESCRIPCIÓ

N

DECLARE permite a un usuario crear cursores, que pueden usarse para recuperar un pequeño número de filas a la vez de una consulta más grande. Después de crear el cursor, se recuperan filas de él usando FETCH

.

ASENSITIVE
INSENSITIV

E
La sensibilidad del cursor determina si los cambios en los datos subyacentes al cursor, realizados en la misma transacción, después de que el cursor haya sido declarado, son visibles en el cursor. INSENSITIVE significa que no son visibles, ASENSITIVE significa que el comportamiento depende de la implementación. Un tercer comportamiento, SENSITIVE, que significa que tales cambios son visibles en el cursor, no está disponible en PostgreSQL. En PostgreSQL, todos los cursores son insensibles; por lo tanto, estas palabras clave no tienen efecto y solo se aceptan por compatibilidad con el estándar SQL.

SCROLL
SCROLL especifica que el cursor puede usarse para recuperar filas de manera no secuencial (por ejemplo, hacia atrás). Dependiendo de la complejidad del plan de ejecución de la consulta, especificar SCROLL puede imponer una penalización de rendimiento en el tiempo de ejecución de la consulta. NO SCROLL especifica que el cursor no puede usarse para recuperar filas de manera no secuencial. El valor por defecto es permitir el desplazamiento en algunos casos; esto no es lo mismo que especificar SCROLL. Véase Notas más abajo para
detalles.

NOTA

S

Los cursores normales devuelven datos en formato texto, igual que SELECT produciría. La opción BINARY especifica que el cursor debería devolver datos en formato binario. Esto reduce el esfuerzo de conversión tanto para el servidor como para el cliente, al costo de más esfuerzo del programador para manejar formatos de datos binarios dependientes de la plataforma. Como ejemplo, si una consulta devuelve un valor de uno de una columna entera, obtendría una cadena de 1 con un cursor por defecto, mientras que con un cursor binario obtendría un campo de 4 bytes que contiene la representación interna del valor (en orden de bytes big-endian)

.

Los cursores binarios deberían usarse con cuidado. Muchas aplicaciones, incluyendo psql, no están preparadas para manejar cursores binarios y esperan que los datos vuelvan en formato

texto.

Nota

Cuando la aplicación cliente usa el protocolo de “consulta extendida” para emitir un FETCH, el mensaje de protocolo Bind especifica si los datos deben recuperarse en formato texto o binario. Esta elección anula la forma en que el cursor está defi

nido. El concepto de cursor binario como tal es obsoleto cuando se usa el protoco
lo de consulta extendida — cualquier cursor puede tratarse como texto o binario.

A menos que se especifique WITH HOLD, el cursor creado por este comando solo puede usarse dentro de la transacción actual. Por lo tanto, DECLARE sin WITH HOLD es inútil fuera de un bloque de transacción: el cursor sobreviviría solo hasta la finalización de la sentencia. Por lo tanto, PostgreSQL reporta un error si tal comando se usa fuera de un bloque de transacción. Use BEGIN y COMMIT (o ROLLBACK) para definir un bloque de

transacción.

Si se especifica WITH HOLD y la transacción que creó el cursor se confirma con éxito, el cursor puede continuar siendo accedido por transacciones subsecuentes en la misma sesión. (Pero si la transacción creadora se aborta, el cursor se elimina.) Un cursor creado con WITH HOLD se cierra cuando se emite un CLOSE explícito sobre él, o cuando la sesión termina. En la implementación actual, las filas representadas por un cursor retenido se copian en un archivo temporal o área de memoria para que permanezcan disponibles para transacciones

subsecuentes.

WITH HOLD no puede especificarse cuando la consulta incluye FOR UPDATE o FOR

SHARE.

La opción SCROLL debería especificarse al definir un cursor que será usado para recuperar filas hacia atrás. Esto es requerido por el estándar SQL. Sin embargo, por compatibilidad con versiones anteriores, PostgreSQL permitirá recuperaciones hacia atrás sin SCROLL, si el plan de consulta del cursor es lo suficientemente simple como para no necesitar sobrecarga extra para soportarlo. Sin embargo, se aconseja a los desarrolladores de aplicaciones no depender del uso de recuperaciones hacia atrás de un cursor que no haya sido creado con SCROLL. Si se especifica NO SCROLL, entonces las recuperaciones hacia atrás están prohibidas en cualquier

caso.

Las recuperaciones hacia atrás también están prohibidas cuando la consulta incluye FOR UPDATE o FOR SHARE; por lo tanto, SCROLL no puede especificarse en este

caso.

Precaución

Los cursores desplazables pueden dar resultados inesperados si invocan funciones volátiles (véase la Sección 36.7). Cuando una fila previamente recuperada se recupera de nuevo, las funciones podrían re-ejecutarse, posiblemente l

levando a resultados diferentes de la primera vez. Es mejor especificar NO SCROLL para una consulta que involucre funciones volátiles. Si eso no es práctico, una solución alternativa es declarar el cursor SCROLL WITH HOLD y conf
irmar la transacción antes de leer cualquier fila de él. Esto forzará que toda la salida del cursor sea materializada en almacenamiento temporal, de modo que las funciones volátiles se ejecuten exactamente una vez por cada fila.

Si la consulta del cursor incluye FOR UPDATE o FOR SHARE, entonces las filas devueltas se bloquean en el momento en que se recuperan por primera vez, de la misma manera que para un SELECT regular con estas opciones. Además, las filas devueltas serán las versiones más

actualizadas.

Precaución

Generalmente se recomienda usar FOR UPDATE si el cursor tiene la intención de usarse con UPDATE ... WHERE CURRENT OF o DELETE ... WHERE CURRENT OF. Usar FOR UPDATE previene que otras sesiones cambien las filas entre el momento en que se recuperan y el momento en que se actualizan. Sin FOR UPDATE, un comando WHERE CURRENT OF subsecuente no tendrá efecto si la fila fue cambiada desde que el cursor fue

creado.

Otra razón para usar FOR UPDATE es que sin él, un WHERE CURRENT OF subsecuente podría fallar si la consulta del cursor no cumple las reglas del estándar SQL para ser “simplemente actualizable” (en particular, el cursor debe referenciar solo una tabla y no usar agrupación u ORDER BY). Los cursores que no son simplemente actualizables podrían funcionar, o no, dependiendo de los detalles de elección del plan; así que en el peor caso, una aplicación podría funcionar en pruebas y luego fallar en producción. Si se especifica FOR UPDATE, se garantiza que el cursor sea

actualizable.

La razón principal para no usar FOR UPDATE con WHERE CURRENT OF es si necesita que el cursor sea des

plazable, o que esté aislado de actualizaciones concurrentes (es decir, continuar mostrando los dato
s antiguos). Si esto es un requisito, preste mucha atención a las advertencias mostradas arriba.

El estándar SQL solo hace disposiciones para cursores en SQL embebido. El servidor PostgreSQL no implementa una OPEN para cursores; un cursor se considera abierto cuando se declara. Sin embargo, ECPG, el preprocesador de SQL embebido para PostgreSQL, soporta las convenciones de cursores SQL estándar, incluyendo aquellas que involucran sentencias DECLARE y OPEN

.

La estructura de datos del servidor subyacente a un cursor abierto se llama un portal. Los nombres de portal se exponen en el protocolo del cliente: un cliente puede recuperar filas directamente de un portal abierto, si conoce el nombre del portal. Al crear un cursor con DECLARE, el nombre del portal es el mismo que el delnombre del

cursor.

COMPATIBILIDA

D

El estándar SQL permite cursores solo en SQL incrustado y en módulos. PostgreSQL permite el uso interactivo de

cursores.

Según el estándar SQL, los cambios realizados en cursores insensibles por las sentencias UPDATE ... WHERE CURRENT OF y DELETE ... WHERE CURRENT OF son visibles en ese mismo cursor. PostgreSQL trata estas sentencias como todas las demás sentencias de modificación de datos, en el sentido de que no son visibles en cursores

insensibles.
