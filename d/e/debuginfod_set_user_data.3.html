DEBUGINFOD_FIND_*(3) Manual de Funciones de Biblioteca DEBUGINFOD_FIND_*(3)

NOMBRE

debuginfod_find_debuginfo - solicitar información de depuración de debuginfod

SINOPSIS

#include <elfutils/debuginfod.h>
Enlazar con -ldebuginfod.

DESCRIPCIÓN

debuginfod_begin() crea un manejador de conexión debuginfod_client que debe ser utilizado con todas las demás llamadas. debuginfod_end() debe ser llamado en el manejador client para liberar todo el estado y almacenamiento cuando se haya terminado.

debuginfod_find_debuginfo(), debuginfod_find_executable(), y debuginfod_find_source() consultan los servidores de debuginfod cuyas URLs se encuentran en $DEBUGINFOD_URLS (ver abajo) para obtener la información de depuración, el ejecutable o el archivo fuente con el build_id dado. El build_id debe ser un puntero a una cadena hexadecimal en minúsculas terminada en nulo o a un blob binario. Si el build_id se proporciona como una cadena hexadecimal, build_id_len debe ser 0. De lo contrario, build_id_len debe ser el número de bytes en el blob binario.

debuginfod_find_source() también requiere un filename para especificar un archivo fuente particular. El filename debe ser una ruta absoluta que incluya el directorio de compilación de la CU asociada con el archivo fuente. Las rutas relativas comúnmente aparecen en el directorio fuente del archivo DWARF, pero estas rutas son relativas a las rutas AT_comp_dir de las unidades de compilación individuales, y sin embargo un ejecutable está compuesto por múltiples CUs. Por lo tanto, para desambiguar, debuginfod espera que las consultas de fuente prefijen los nombres de ruta relativos con el directorio de compilación de la CU, seguido de un "/" obligatorio.

Nota: el llamador puede o no omitir componentes de ruta como ../ o /./ o /// redundantes en los nombres de directorio. debuginfod acepta ambas formas. Específicamente, debuginfod canoniza los nombres de ruta de acuerdo con RFC3986 sección 5.2.4 (Eliminar Segmentos de Punto), además de reducir cualquier // a / en la ruta.

debuginfod_find_section() consulta las URLs del servidor debuginfod contenidas en $DEBUGINFOD_URLS para obtener los contenidos binarios de una sección ELF/DWARF contenida en un archivo de información de depuración o ejecutable con el build_id dado. section debe ser el nombre de la sección ELF/DWARF deseada. Si un servidor no admite consultas de sección, debuginfod_find_section puede consultar al servidor la información de depuración y/o el ejecutable con build_id para recuperar y extraer la sección.

debuginfod_find_metadata() consulta todas las URLs del servidor debuginfod contenidas en $DEBUGINFOD_URLS para obtener metadatos para todas las coincidencias de una consulta dada de clave/valor contra archivos en sus índices. El archivo resultante es un documento JSON. Consulte la página del manual de debuginfod-find(1) para ver ejemplos de los tipos de consultas de clave/valor compatibles y sus resultados JSON.

Si path no es NULL y la consulta es exitosa, path se establece en la ruta del archivo en la caché. El llamador debe liberar () este valor.

Las URLs en $DEBUGINFOD_URLS pueden ser consultadas en paralelo. Tan pronto como un servidor debuginfod comience a transferir el archivo objetivo, todas las conexiones a los otros servidores se cerrarán.

Un manejador client solo debe ser utilizado por un hilo a la vez. Un manejador puede ser reutilizado para una serie de búsquedas, lo que puede mejorar el rendimiento debido a la retención de conexiones y cachés.

VALOR DE RETORNO

debuginfod_begin devuelve el manejador debuginfod_client a utilizar con todas las demás llamadas. En caso de error, se devolverá NULL y se establecerá errno.

Si una función de la familia find tiene éxito, el archivo resultante se guarda en la caché del cliente y se devuelve un descriptor de archivo a ese archivo. El descriptor de archivo apunta al principio del archivo. El llamador necesita cerrar () este descriptor. De lo contrario, se devuelve un código de error negativo.

FUNCIONES OPCIONALES

Hay un pequeño número de funciones opcionales disponibles para ajustar o consultar la operación del cliente debuginfod.

CALLBACK DE PROGRESO

Dado que las funciones debuginfod_find_*() pueden bloquearse durante segundos o más, se llama periódicamente a una función de devolución de llamada de progreso, si se configura con debuginfod_set_progressfn(). Esta función establece una nueva función de devolución de llamada de progreso (o NULL) para el manejador del cliente.

La función de devolución de llamada dada se llama desde el contexto de cada hilo que invoca cualquiera de las otras funciones de búsqueda. Se le dan dos parámetros numéricos que, si se consideran como un numerador a y un denominador b, juntos representan una fracción de finalización a/b. El denominador puede ser cero inicialmente, hasta que se conozca una cantidad como un tamaño de descarga exacto.

La función de devolución de llamada de progreso es también la forma compatible de *interrumpir* la operación de descarga. (La biblioteca *no* modifica ni activa señales.) La función de devolución de llamada de progreso debe devolver 0 para continuar el trabajo, o cualquier otro valor para detener el trabajo tan pronto como sea posible. En consecuencia, la función debuginfod_find_*() probablemente devolverá un error, pero aún podría tener éxito.

SALIDA VERBO._A

Las funciones debuginfod_find_*() pueden utilizar varias técnicas para recuperar los archivos solicitados, a través de la caché o a través de uno o varios servidores o URLs de archivos. Para mostrar cómo se maneja una consulta, se puede utilizar debuginfod_set_verbose_fd() para establecer un descriptor de archivo particular en el que se proporcione una salida detallada sobre los pasos de la consulta y los posibles errores encontrados.

PUNTERO A DATOS DEL USUARIO

Un único puntero void * asociado con el manejador de conexión puede establecerse en cualquier momento a través de debuginfod_set_user_data() y recuperarse a través de debuginfod_get_user_data(). El valor no está definido si no se establece.

URL DEL SERVIDOR

La función debuginfod_get_url() devuelve la URL del servidor debuginfod que se está consultando actualmente.

CABECERAS HTTP

La función debuginfod_add_http_header() añade una cabecera HTTP personalizada a las solicitudes salientes. La cabecera debe estar en el formato "Nombre: Valor". Se puede llamar a esta función varias veces para añadir varias cabeceras.

La función debuginfod_get_headers() devuelve una cadena que contiene todas las cabeceras HTTP añadidas, separadas por un salto de línea. Esto puede ser útil para la depuración o para la verificación.

AMBIENTE

Las variables de entorno siguientes afectan la operación de las funciones de debuginfod:

$DEBUGINFOD_URLS
Una lista separada por espacios o comas de URLs de servidores debuginfod. Si no está establecida, el cliente intentará usar una lista predeterminada de URLs de servidores públicos.
$DEBUGINFOD_HOST
Dirección del host para el servidor debuginfod. Solo se utiliza si $DEBUGINFOD_URLS no está establecida.
$DEBUGINFOD_PORT
Puerto para el servidor debuginfod. Solo se utiliza si $DEBUGINFOD_URLS no está establecida.
$DEBUGINFOD_ASSUME_UNCOMPRESSED
Si está establecida, esta variable de entorno hace que el cliente debuginfod asuma que todos los archivos servidos por los servidores debuginfod no están comprimidos. Esto puede ser útil cuando se interactúa con servidores que no admiten la descompresión automática.
$DEBUGINFOD_CACHE_DIR
Directorio donde se almacenarán en caché los archivos descargados. Si no se establece, se utiliza un directorio temporal.
$DEBUGINFOD_MAX_CACHE_SIZE
Tamaño máximo de la caché en bytes. Si la caché excede este tamaño, los archivos más antiguos se eliminarán para liberar espacio. El valor predeterminado es 1024 * 1024 * 1024 (1 GiB).

EJEMPLOS

Buscar y descargar un archivo de información de depuración:

debuginfod_client *client;
char *path = NULL;
int fd;
unsigned char build_id[] = { ... }; // El build_id binario

client = debuginfod_begin ();
if (!client) {
    perror("debuginfod_begin");
    exit(1);
}

fd = debuginfod_find_debuginfo (client, build_id, sizeof(build_id), &path);
if (fd < 0) {
    fprintf(stderr, "debuginfod_find_debuginfo failed: %s\n", strerror(-fd));
} else {
    printf("Debug info file found at: %s\n", path);
    // Usar el archivo a través del descriptor de archivo fd
    close(fd);
}

free (path);
debuginfod_end (client);

Buscar y descargar un archivo fuente:

char *path = NULL;
int fd;
unsigned char build_id[] = { ... }; // El build_id binario
const char *filename = "/path/to/compilation/dir/source.c";

client = debuginfod_begin ();
// ... manejo de errores ...

fd = debuginfod_find_source (client, build_id, sizeof(build_id), filename, &path);
if (fd < 0) {
    fprintf(stderr, "debuginfod_find_source failed: %s\n", strerror(-fd));
} else {
    printf("Source file found at: %s\n", path);
    close(fd);
}

free (path);
debuginfod_end (client);

Establecer una función de progreso y un puntero de datos de usuario:

void *user_data_ptr = (void *)0x12345678;

int progress_callback(debuginfod_client *client, long a, long b) {
    // Actualizar UI, comprobar interrupciones, etc.
    printf("Progress: %ld / %ld\n", a, b);
    // Devolver 0 para continuar, cualquier otro valor para interrumpir
    return 0;
}

client = debuginfod_begin ();
// ... manejo de errores ...

debuginfod_set_progressfn (client, progress_callback);
debuginfod_set_user_data (client, user_data_ptr);

// ... realizar búsquedas ...

if (debuginfod_get_user_data(client) != user_data_ptr) {
    // ¡Error! Los datos del usuario no se conservaron.
}

debuginfod_end (client);

URL

URL

La URL de la descarga saliente actual o más reciente, si se conoce, puede recuperarse mediante debuginfod_get_url() desde la devolución de llamada progressfn, o después. Puede ser NULL. La cadena resultante es propiedad de la biblioteca y no debe modificarse ni liberarse. El llamador debería copiarla si es necesaria más allá de la liberación del objeto cliente.

CABECERA HTTP

Antes de iniciar cada función de búsqueda, una aplicación cliente puede añadir cabeceras de solicitud HTTP. Estas se restablecen después de cada función de búsqueda. debuginfod_add_http_header() puede ser llamada con cadenas del formato "Cabecera: valor". Estas cadenas son copiadas por la biblioteca. Un valor de retorno cero indica éxito, pero las condiciones de falta de memoria pueden resultar en un -ENOMEM distinto de cero. Si la cadena tiene un formato incorrecto, se devolverá -EINVAL.

$DEBUGINFOD_HEADERS_FILE especifica un archivo para suministrar cabeceras a las solicitudes salientes. Cada línea no vacía de este archivo se maneja como si debuginfod_add_http_header() se hubiera llamado con su contenido.

Tenga en cuenta que la implementación actual de la biblioteca debuginfod-client utiliza libcurl, pero no debe confiar en ese hecho. No utilice esta función para reemplazar ninguna cabecera estándar, excepto la User-Agent mencionada a continuación. Puede utilizar esta función para añadir información de autorización para control de acceso, o para proporcionar cabeceras opcionales al servidor para fines de registro.

Por defecto, la biblioteca añade una cabecera descriptiva User-Agent: a las solicitudes salientes. Si la aplicación cliente añade una cabecera con el mismo nombre, esta por defecto se suprime.

Durante o después de una búsqueda, una aplicación cliente puede llamar a debuginfod_get_headers() para recopilar el subconjunto de cabeceras de respuesta HTTP recibidas del servidor debuginfod actual o más reciente. Solo se conservan aquellas cabeceras que comienzan con X-DEBUGINFOD (sin distinción entre mayúsculas y minúsculas). Se devuelven como una única cadena, con cada "cabecera: valor" terminado con un \n (no \r\n como en HTTP). Puede ser NULL. La cadena resultante es propiedad de la biblioteca y no debe modificarse ni liberarse. El llamador debe copiar la cadena devuelta si es necesaria más allá de la liberación del objeto cliente.

MACROS

DEBUGINFOD_SONAME

Definido a la cadena que podría pasarse a dlopen(3) si la biblioteca se carga en tiempo de ejecución, por ejemplo


void *debuginfod_so = dlopen(DEBUGINFOD_SONAME, RTLD_LAZY);

SEGURIDAD

Si hay firmas IMA disponibles de los RPM que contienen los archivos solicitados, debuginfod extraerá esas firmas en cabeceras de respuesta, y debuginfod_find_*() realizará la verificación sobre los archivos. La política de validación se controla mediante etiquetas insertadas en $DEBUGINFOD_URLS. Por defecto, debuginfod_find_*() actúa en modo de ignorar.

Si se accede a través de HTTP en lugar de HTTPS, la red debe ser confiable. La información de autenticación a través de la biblioteca interna libcurl no está habilitada actualmente, excepto por el estilo básico de texto plano http[s]://usuario:contraseña@nombre_host/. (El servidor debuginfod no realiza autenticación, pero un servidor proxy frontal podría hacerlo).

ERRORES

La siguiente lista no es exhaustiva. Los códigos de error también pueden originarse en llamadas a varias funciones de la Biblioteca C.

EACCESO
Acceso denegado al recurso ubicado en la URL.
ECONNREFUSED
No se pudo conectar al host remoto. También se devuelve cuando una conexión HTTPS no pudo ser verificada (certificado incorrecto).
ECONNRESET
No se pudo enviar ni recibir datos de red.
EHOSTUNREACH
No se pudo resolver el host remoto.
EINVAL
Uno o más argumentos tienen un formato incorrecto. build_id puede ser demasiado largo (mayor de 256 caracteres), filename puede no ser una ruta absoluta o una URL de debuginfod está mal formada.
EIO
No se pudieron escribir los datos recibidos del servidor en el archivo local.
EMLINK
Demasiadas redirecciones HTTP.
ENETUNREACH
No se pudo inicializar la conexión de red.
ENOENT
No se pudo encontrar el recurso ubicado en la URL. A menudo este código de error indica que se contactó con éxito a un servidor debuginfod pero el servidor no pudo encontrar el archivo de destino.
ENOMEM
El sistema no pudo asignar recursos.
ENOSYS
$DEBUGINFOD_URLS no está definido.
ETIME
La consulta falló debido a un tiempo de espera. $DEBUGINFOD_TIMEOUT y $DEBUGINFOD_MAXTIME controlan esto.
EF2BIG
La consulta se abortó porque el archivo solicitado era demasiado grande. $DEBUGINFOD_MAXSIZE controla esto.
EBADMSG
El contenido del archivo falló la verificación IMA contra un certificado de firmante conocido.
ENOKEY
El contenido del archivo falló la verificación IMA debido a la ausencia de un certificado de firmante.
ENODATA
El contenido del archivo falló la verificación IMA debido a la ausencia de una firma.

VARIABLES DE ENTORNO

$TMPDIR
Esta variable de entorno apunta a un sistema de archivos que se utilizará para archivos temporales. El valor predeterminado es /tmp.
$DEBUGINFOD_URLS
Esta variable de entorno contiene una lista de prefijos de URL para instancias de debuginfod confiables. Los prefijos de URL alternativos están separados por espacios. Esta variable de entorno puede ser establecida por scripts de /etc/profile.d que leen archivos de /etc/debuginfod/*.urls.

Esta variable de entorno también puede contener políticas que definen etiquetas que dictan la política de respuesta para verificar las firmas IMA por archivo en los RPM. A medida que la lista separada por espacios se lee de izquierda a derecha, al encontrar una etiqueta, las URLs subsiguientes hasta la siguiente etiqueta se manejarán utilizando esa política especificada. Todas las URLs antes de la primera etiqueta utilizarán la política predeterminada, ima:ignore. Por ejemplo:


DEBUGINFOD_URLS="https://foo.com ima:enforcing https://bar.ca http://localhost:8002/ ima:ignore https://baz.org"

Donde foo.com y baz.org utilizan la política predeterminada ignore y bar.ca y localhost utilizan una política enforcing. La etiqueta de política puede ser una de las siguientes:

ima:enforcing Cada archivo descargado requiere una firma válida, protegiendo completamente la integridad.
ima:ignore Omite la verificación por completo, sin ofrecer protección.

Las alertas de fallo de validación se dirigirán según lo especificado en $DEBUGINFOD_VERBOSE.

$DEBUGINFOD_CACHE_PATH
Esta variable de entorno rige la ubicación del caché donde se guardan los archivos descargados y los archivos de control de caché. El directorio predeterminado se elige basándose en otras variables de entorno, véase más abajo.
$DEBUGINFOD_PROGRESS
Esta variable de entorno rige la función de progreso predeterminada. Si se establece, y si no se establece explícitamente una función de progreso, la biblioteca configurará una función de progreso predeterminada. Esta función añadirá un mensaje de progreso simple periódicamente a stderr. El valor predeterminado es ninguna salida de función de progreso.
$DEBUGINFOD_VERBOSE
Esta variable de entorno rige el descriptor de archivo predeterminado para la salida detallada. Si se establece, y si no se establece explícitamente un descriptor de archivo detallado, la salida detallada se producirá en STDERR_FILENO.
$DEBUGINFOD_RETRY_LIMIT
Esta variable de entorno rige el límite predeterminado de intentos de reintento. Si una consulta falló con un errno distinto de ENOENT, iniciará varios intentos dentro del límite.
$DEBUGINFOD_TIMEOUT
Esta variable de entorno rige el tiempo de espera para el inicio de la descarga para cada conexión HTTP de debuginfod. Un servidor que no proporcione al menos 100K de datos dentro de esta cantidad de segundos se omitirá. El valor predeterminado es 90 segundos. (Cero o negativo significa "sin tiempo de espera").
$DEBUGINFOD_MAXTIME
Esta variable de entorno dicta cuánto tiempo esperará el cliente para completar la descarga de un archivo encontrado en un servidor, en segundos. Se utiliza mejor para asegurar que un archivo se descargue rápidamente o sea rechazado. El valor predeterminado es 0 (tiempo infinito).
$DEBUGINFOD_MAXSIZE
Esta variable de entorno dicta el tamaño máximo de un archivo para descargar en bytes. Esto se utiliza mejor si el usuario desea asegurarse de que solo se descarguen archivos pequeños. Un valor de 0 no considera el tamaño, y el cliente puede intentar descargar un archivo de cualquier tamaño. El valor predeterminado es 0 (tamaño infinito).
$DEBUGINFOD_HEADERS_FILE
Esta variable de entorno apunta a un archivo que suministra cabeceras a las solicitudes HTTP salientes, una por línea. Las líneas de cabecera no deberían terminar con CRLF, a menos que esa sea la convención de nueva línea del sistema. Las líneas que solo contienen espacios en blanco se omiten.
$DEBUGINFOD_IMA_CERT_PATH
Esta variable de entorno contiene una lista de rutas de directorios absolutas que albergan certificados X.509 para la verificación IMA de RPM por archivo. Las rutas alternativas están separadas por dos puntos.

CACHE

Antes de cada consulta, la biblioteca cliente de debuginfod verifica si es necesario limpiar la caché. Si es hora de limpiar, la biblioteca recorre el directorio de caché y elimina

s descargados relacionados con debuginfo y directorios recién vaciados, si no se han accedido recientemente.

Los archivos de control se encuentran directamente bajo el directorio de caché. Contienen números decimales simples para establecer parámetros de configuración relacionados con la caché. Si los archivos no existen, la biblioteca de cliente crea los archivos con los valores de parámetros predeterminados como contenido.

Después de cada consulta, la biblioteca de cliente de debuginfod deposita los archivos recién recibidos en un directorio y archivo cuyo nombre se basa en el build-id. Una consulta fallida también se almacena en caché mediante un archivo especial. La convención de nombres utilizada para estos artefactos es deliberadamente no documentada.

$XDG_CACHE_HOME/debuginfod_client/
Directorio de caché predeterminado, si $XDG_CACHE_HOME está establecido.
$HOME/.cache/debuginfod_client/
Directorio de caché predeterminado, si $XDG_CACHE_HOME no está establecido.
$HOME/.debuginfod_client_cache/
Directorio de caché obsoleto, utilizado solo si ya existe.
cache_clean_interval_s
Este archivo de control indica el intervalo entre rondas de limpieza de la caché, en segundos. El valor predeterminado es 86400, un día. 0 significa "inmediatamente".
max_unused_age_s
Este archivo de control establece cuánto tiempo se conservan los archivos relacionados con debuginfo a los que no se ha accedido, en segundos. El valor predeterminado es 604800, una semana. 0 significa "inmediatamente".
cache_miss_s
Este archivo de control establece cuánto tiempo recordar un fallo de consulta, en segundos. Las nuevas consultas para los mismos artefactos dentro de esta ventana de tiempo se cortocircuitan (devolviendo un fallo inmediato en lugar de enviar una nueva consulta a los servidores). Esto acelera las consultas que probablemente seguirían fallando. El valor predeterminado es 600, 10 minutos. 0 significa "olvidar inmediatamente".
metadata_retention_s
Este archivo de control establece cuánto tiempo recordar los resultados de una consulta de metadatos. Las nuevas consultas para los mismos artefactos dentro de esta ventana de tiempo se cortocircuitan (repitiendo los mismos resultados). Esto acelera las consultas que probablemente tendrían los mismos resultados. El valor predeterminado es 3600, 1 hora. 0 significa "no conservar".
