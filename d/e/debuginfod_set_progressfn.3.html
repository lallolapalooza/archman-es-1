DEBUGINFOD_FIND_*(3) Manual de Funciones de Biblioteca DEBUGINFOD_FIND_*(3)

NOMBRE

debuginfod_find_debuginfo - solicitar debuginfo de debuginfod

SINOPSIS

#include <elfutils/debuginfod.h>
Enlazar con -ldebuginfod.

DESCRIPCIÓN

debuginfod_begin() crea un manejo de conexión debuginfod_client que debe usarse con todas las demás llamadas. debuginfod_end() debe llamarse en el manejo client para liberar todo el estado y almacenamiento cuando se termine.

debuginfod_find_debuginfo(), debuginfod_find_executabley debuginfod_find_source() consultan las URL de los servidores debuginfod contenidas en $DEBUGINFOD_URLS (véase más abajo) para obtener el debuginfo, el ejecutable o el archivo fuente con el build_iddado. build_id debe ser un puntero a una cadena hexadecimal en minúsculas terminada en nulo o a un blob binario. Si build_id se da como cadena hexadecimal, build_id_len debe ser 0. En caso contrario, build_id_len debe ser el número de bytes del blob binario.

debuginfod_find_source() también requiere un filename para especificar un archivo fuente en particular. filename debe ser una ruta absoluta que incluya el directorio de compilación de la CU asociada con el archivo fuente. Los nombres de ruta relativos aparecen comúnmente en el directorio de fuentes del archivo DWARF, pero estas rutas son relativas a las rutas AT_comp_dir de las unidades de compilación individuales, y sin embargo un ejecutable está compuesto de múltiples CUs. Por lo tanto, para desambiguar, debuginfod espera que las consultas de fuentes prefijen los nombres de ruta relativos con el directorio de compilación de la CU, seguido de un "/" obligatorio.

Nota: el llamador puede o no omitir ../ o /./ o componentes de ruta superfluos /// en los nombres de directorio. debuginfod acepta ambas formas. Específicamente, debuginfod canoniza los nombres de ruta de acuerdo con la sección 5.2.4 de RFC3986 (Eliminar Segmentos con Puntos), además de reducir cualquier // a / en la ruta.

debuginfod_find_section() consulta las URL de los servidores debuginfod contenidas en $DEBUGINFOD_URLS para los contenidos binarios de una sección ELF/DWARF contenida en un archivo debuginfo o ejecutable con el build_iddado. section debe ser el nombre de la sección ELF/DWARF deseada. Si un servidor no soporta consultas de secciones, debuginfod_find_section puede consultar al servidor por el debuginfo y/o el ejecutable con build_id para recuperar y extraer la sección.

debuginfod_find_metadata() consulta todas las URL de servidores debuginfod contenidas en $DEBUGINFOD_URLS para los metadatos de todas las coincidencias de una consulta clave/valor dada contra los archivos en sus índices. El archivo resultante es un documento JSON. Véase la página man debuginfod-find(1) para ejemplos de los tipos soportados de consultas clave/valor y sus resultados JSON.

Si path no es NULL y la consulta es exitosa, path se establece en la ruta del archivo en la caché. El llamador debe liberar() este valor.

Las URL en $DEBUGINFOD_URLS pueden consultarse en paralelo. Tan pronto como un servidor debuginfod comienza a transferir el archivo de destino, todas las conexiones con los otros servidores se cierran.

Un manejo client debe usarse desde un solo hilo a la vez. Un manejo puede reutilizarse para una serie de búsquedas, lo que puede mejorar el rendimiento debido a la retención de conexiones y cachés.

VALOR DE RETORNO

debuginfod_begin devuelve el manejo debuginfod_client para usar con todas las demás llamadas. En caso de error NULL será devuelto y errno será establecido.

Si una función de la familia find es exitosa, el archivo resultante es guardado en la caché del cliente y se devuelve un descriptor de archivo para ese archivo. El descriptor de archivo apunta al comienzo del archivo. El llamador necesita cerrar() este descriptor. De lo contrario, se devuelve un código de error negativo.

FUNCIONES OPCIONALES

Hay disponibles un pequeño número de funciones opcionales para ajustar o consultar el funcionamiento del cliente debuginfod.

RETROALIMENTACIÓN DE PROGRESO

Dado que las debuginfod_find_*() pueden bloquearse durante segundos o más, una función de retroalimentación de progreso se llama periódicamente, si se configura con debuginfod_set_progressfn(). Esta función establece una nueva función de retroalimentación de progreso (o NULL) para el manejo del cliente.

La función de retroalimentación dada se llama desde el contexto de cada hilo que invoca cualquiera de las otras funciones de búsqueda. Se le dan dos parámetros numéricos que, si se piensan como un numerador a y un denominador b, representan juntos una fracción de finalización a/b. El denominador puede ser cero inicialmente, hasta que una cantidad como el tamaño exacto de descarga se hace conocida.

La función de retroalimentación de progreso también es la forma soportada de interrumpir la operación de descarga. (La biblioteca no modifica ni dispara señales.) La retroalimentación de progreso debe devolver 0 para continuar el trabajo, o cualquier otro valor para detener el trabajo lo antes posible. En consecuencia, la funcióndebuginfod_find_* probablemente devolverá un error, pero podría tener éxito de todos modos.

SALIDA DETALLADA

Las funcionesdebuginfod_find_* pueden usar varias técnicas para recuperar los archivos solicitados, a través de la caché o a través de uno o múltiples servidores o URL de archivos. Para mostrar cómo se maneja una consulta se puede usardebuginfod_set_verbose_fd

() para establecer un descriptor de archivo particular en el que se da salida detallada sobre los pasos de la consulta y los errores finales encontrados.

PUNTERO DE DATOS DE USUARIO Un único puntero void * asociado con el manejo de conexión puede establecerse en cualquier momento a través dedebuginfod_set_user_data() , y recuperarse a través de debuginfod_get_user_data(). El valor es indefinido si no se establece.

URL

La URL de la descarga saliente actual o más reciente, si se conoce, puede recuperarse mediante debuginfod_get_url() desde la devolución de llamada progressfn, o después. Puede ser NULL. La cadena resultante es propiedad de la biblioteca y no debe modificarse ni liberarse. El llamador debe copiarla si es necesaria más allá de la liberación del objeto cliente.

CABECERA HTTP

Antes de que se inicie cada función de búsqueda, una aplicación cliente puede agregar cabeceras de solicitud HTTP. Estas se restablecen después de cada función de búsqueda. Se puede llamar a debuginfod_add_http_header() con cadenas del formato "Cabecera: valor". Estas cadenas son copiadas por la biblioteca. Un valor de retorno cero indica éxito, pero las condiciones de falta de memoria pueden resultar en un valor distinto de cero -ENOMEM. Si la cadena tiene un formato incorrecto, se devolverá -EINVAL.

$DEBUGINFOD_HEADERS_FILE especifica un archivo para suministrar cabeceras a las solicitudes salientes. Cada línea no vacía de este archivo se maneja como si se hubiera llamado a debuginfod_add_http_header() con su contenido.

Tenga en cuenta que la implementación actual de la biblioteca debuginfod-client utiliza libcurl, pero no debe confiar en ese hecho. No utilice esta función para reemplazar ninguna cabecera estándar, excepto la mencionada a continuación del Agente de Usuario. Puede utilizar esta función para agregar información de autorización para el control de acceso, o para proporcionar cabeceras opcionales al servidor para fines de registro.

Por defecto, la biblioteca agrega una cabecera descriptiva Agente de usuario: a las solicitudes salientes. Si la aplicación cliente agrega una cabecera con el mismo nombre, esta por defecto se suprime.

Durante o después de una búsqueda, una aplicación cliente puede llamar a debuginfod_get_headers() para recopilar el subconjunto de cabeceras de respuesta HTTP recibidas del servidor debuginfod actual o más reciente. Solo se conservan aquellas cabeceras que comienzan con X-DEBUGINFOD (sin distinción de mayúsculas y minúsculas). Se devuelven como una única cadena, con cada "cabecera: valor" terminada con un \n (no \r\n como en HTTP). Puede ser NULL. La cadena resultante es propiedad de la biblioteca y no debe modificarse ni liberarse. El llamador debe copiar la cadena devuelta si es necesaria más allá de la liberación del objeto cliente.

MACROS

DEBUGINFOD_SONAME

Definido a la cadena que podría pasarse a dlopen(3) si la biblioteca se carga en tiempo de ejecución, por ejemplo


void *debuginfod_so = dlopen(DEBUGINFOD_SONAME, RTLD_LAZY);

SEGURIDAD

Si hay firmas IMA disponibles de los RPM que contienen los archivos solicitados, debuginfod extraerá esas firmas en cabeceras de respuesta, y debuginfod_find_*() realizará la verificación sobre los archivos. La política de validación se controla mediante etiquetas insertadas en $DEBUGINFOD_URLS. Por defecto, debuginfod_find_*() actúa en modo de ignorar.

Si se accede a través de HTTP en lugar de HTTPS, la red debe ser confiable. La información de autenticación a través de la biblioteca interna libcurl no está habilitada actualmente, excepto por el estilo plano de texto básico http[s]://userid:password@hostname/. (El servidor debuginfod no realiza autenticación, pero un servidor proxy frontal podría hacerlo).

ERRORES

La siguiente lista no es exhaustiva. Los códigos de error también pueden originarse en llamadas a varias funciones de la Biblioteca C.

EACCESS
Acceso denegado al recurso ubicado en la URL.
ECONNREFUSED
No se pudo conectar al host remoto. También se devuelve cuando no se pudo verificar una conexión HTTPS (certificado incorrecto).
ECONNRESET
No se pudo enviar ni recibir datos de red.
EHOSTUNREACH
No se pudo resolver el host remoto.
EINVAL
Uno o más argumentos tienen un formato incorrecto. build_id puede ser demasiado largo (mayor que 256 caracteres), filename puede no ser una ruta absoluta o una URL de debuginfod está mal formada.
EIO
No se pudieron escribir los datos recibidos del servidor en el archivo local.
EMLINK
Demasiadas redirecciones HTTP.
ENETUNREACH
No se pudo inicializar la conexión de red.
ENOENT
No se pudo encontrar el recurso ubicado en la URL. A menudo este código de error indica que se contactó con un servidor debuginfod con éxito, pero el servidor no pudo encontrar el archivo objetivo.
ENOMEM
El sistema no puede asignar recursos.
ENOSYS
$DEBUGINFOD_URLS no está definido.
ETIME
La consulta falló debido a un tiempo de espera. $DEBUGINFOD_TIMEOUT y $DEBUGINFOD_MAXTIME controlan esto.
EF2BIG
La consulta se abortó porque el archivo solicitado era demasiado grande. $DEBUGINFOD_MAXSIZE controla esto.
EBADMSG
El contenido del archivo falló la verificación IMA contra un certificado de firmante conocido.
ENOKEY
El contenido del archivo falló la verificación IMA debido a la falta de un certificado de firmante.
ENODATA
El contenido del archivo falló la verificación IMA debido a una firma faltante.

VARIABLES DE ENTORNO

$TMPDIR
Esta variable de entorno apunta a un sistema de archivos que se utilizará para archivos temporales. El valor predeterminado es /tmp.
$DEBUGINFOD_URLS
Esta variable de entorno contiene una lista de prefijos de URL para instancias debuginfod confiables. Los prefijos de URL alternativos están separados por espacios. Esta variable de entorno puede ser establecida por scripts de /etc/profile.d que leen archivos de /etc/debuginfod/*.urls.

Esta variable de entorno también puede contener políticas que definen etiquetas que dictan la política de respuesta para verificar las firmas IMA por archivo en los RPM. A medida que la lista separada por espacios se lee de izquierda a derecha, al encontrar una etiqueta, las URL subsiguientes hasta la siguiente etiqueta se manejarán utilizando esa política especificada. Todas las URL antes de la primera etiqueta utilizarán la política predeterminada, ima:ignore. Por ejemplo:


DEBUGINFOD_URLS="https://foo.com ima:enforcing https://bar.ca http://localhost:8002/ ima:ignore https://baz.org"

Donde foo.com y baz.org usan la política predeterminada de ignorancia y bar.ca y localhost usan una política de imposición. La etiqueta de política puede ser una de las siguientes:

ima:enforcing Cada archivo descargado requiere una firma válida, protegiendo completamente la integridad.
ima:ignore Omite la verificación por completo, sin proporcionar protección.

Las alertas de fallo de validación se dirigirán según lo especificado en $DEBUGINFOD_VERBOSE.

$DEBUGINFOD_CACHE_PATH
Esta variable de entorno rige la ubicación del caché donde se guardan los archivos descargados y los archivos de control de caché. El directorio predeterminado se elige en función de otras variables de entorno, ver más adelante.
$DEBUGINFOD_PROGRESS
Esta variable de entorno rige la función de progreso predeterminada. Si está configurada, y si no se establece explícitamente una función de progreso, la biblioteca configurará una función de progreso predeterminada. Esta función agregará un mensaje de progreso simple periódicamente a stderr. El valor predeterminado es no generar salida de la función de progreso.
$DEBUGINFOD_VERBOSE
Esta variable de entorno rige el descriptor de archivo predeterminado para la salida detallada. Si está configurada, y si no se establece explícitamente un descriptor de archivo detallado, la salida detallada se producirá en STDERR_FILENO.
$DEBUGINFOD_RETRY_LIMIT
Esta variable de entorno rige el límite predeterminado de intentos de reintento. Si una consulta falló con un errno distinto de ENOENT, iniciará varios intentos dentro del límite.
$DEBUGINFOD_TIMEOUT
Esta variable de entorno rige el tiempo de espera para el inicio de la descarga para cada conexión HTTP de debuginfod. Se omite un servidor que no proporciona al menos 100K de datos dentro de este número de segundos. El valor predeterminado es 90 segundos. (Cero o negativo significa "sin tiempo de espera").
$DEBUGINFOD_MAXTIME
Esta variable de entorno dicta cuánto tiempo esperará el cliente para completar la descarga de un archivo encontrado en un servidor en segundos. Es mejor usarlo para asegurar que un archivo se descargue rápidamente o sea rechazado. El valor predeterminado es 0 (tiempo infinito).
$DEBUGINFOD_MAXSIZE
Esta variable de entorno dicta el tamaño máximo de un archivo para descargar en bytes. Es mejor usarlo si el usuario desea asegurarse de que solo se descarguen archivos pequeños. Un valor de 0 no considera el tamaño, y el cliente puede intentar descargar un archivo de cualquier tamaño. El valor predeterminado es 0 (tamaño infinito).
$DEBUGINFOD_HEADERS_FILE
Esta variable de entorno apunta a un archivo que suministra cabeceras a las solicitudes HTTP salientes, una por línea. Las líneas de cabecera no deben terminar con CRLF, a menos que esa sea la convención de nueva línea del sistema. Las líneas que solo contienen espacios en blanco se omiten.
$DEBUGINFOD_IMA_CERT_PATH
Esta variable de entorno contiene una lista de rutas de directorio absolutas que contienen certificados X.509 para la verificación IMA por archivo de RPM. Las rutas alternativas están separadas por dos puntos.

CACHÉ

Antes de cada consulta, la biblioteca cliente de debuginfod comprueba si es necesario limpiar la caché. Si es hora de limpiar, la biblioteca recorre el directorio de caché y elimina

elimina artefactos relacionados con debuginfo descargados y directorios recién vaciados, si no se han accedido recientemente.

Los archivos de control se encuentran directamente bajo el directorio de caché. Contienen números decimales simples para establecer parámetros de configuración relacionados con la caché. Si los archivos no existen, la biblioteca de cliente crea los archivos con los valores de parámetros predeterminados como contenido.

Después de cada consulta, la biblioteca de cliente de debuginfod deposita los archivos recién recibidos en un directorio y archivo cuyo nombre se basa en el build-id. Una consulta fallida también se almacena en caché mediante un archivo especial. La convención de nombres utilizada para estos artefactos es deliberadamente no documentada.

$XDG_CACHE_HOME/debuginfod_client/
Directorio de caché predeterminado, si $XDG_CACHE_HOME está establecido.
$HOME/.cache/debuginfod_client/
Directorio de caché predeterminado, si $XDG_CACHE_HOME no está establecido.
$HOME/.debuginfod_client_cache/
Directorio de caché obsoleto, utilizado solo si ya existe.
cache_clean_interval_s
Este archivo de control indica el intervalo entre rondas de limpieza de la caché, en segundos. El valor predeterminado es 86400, un día. 0 significa "inmediatamente".
max_unused_age_s
Este archivo de control establece cuánto tiempo se conservan los archivos relacionados con debuginfo a los que no se ha accedido, en segundos. El valor predeterminado es 604800, una semana. 0 significa "inmediatamente".
cache_miss_s
Este archivo de control establece cuánto tiempo recordar un fallo de consulta, en segundos. Las nuevas consultas para los mismos artefactos dentro de esta ventana de tiempo se cortocircuitan (devolviendo un fallo inmediato en lugar de enviar una nueva consulta a los servidores). Esto acelera las consultas que probablemente seguirían fallando. El valor predeterminado es 600, 10 minutos. 0 significa "olvidar inmediatamente".
metadata_retention_s
Este archivo de control establece cuánto tiempo recordar los resultados de una consulta de metadatos. Las nuevas consultas para los mismos artefactos dentro de esta ventana de tiempo se cortocircuitan (repitiendo los mismos resultados). Esto acelera las consultas que probablemente tendrían los mismos resultados. El valor predeterminado es 3600, 1 hora. 0 significa "no conservar".
