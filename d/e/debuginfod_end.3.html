NOMBRE

debuginfod_find_debuginfo - solicitar información de depuración de debuginfod

SINOPSIS

Enlazar con -ldebuginfod.

DESCRIPCIÓN

debuginfod_begin() crea un manejador de conexión debuginfod_client que debe ser utilizado con todas las demás llamadas. debuginfod_end() debe ser llamado sobre el manejador client para liberar todo el estado y almacenamiento cuando se haya terminado.

debuginfod_find_debuginfo(), debuginfod_find_executable() y debuginfod_find_source() consultan las URLs del servidor debuginfod contenidas en $DEBUGINFOD_URLS (ver abajo) para obtener la información de depuración, el ejecutable o el archivo fuente con el build_id dado. build_id debe ser un puntero a una cadena hexadecimal en minúsculas terminada en nulo o a un bloque binario. Si build_id se proporciona como una cadena hexadecimal, build_id_len debe ser 0. De lo contrario, build_id_len debe ser el número de bytes en el bloque binario.

debuginfod_find_source() también requiere un filename para especificar un archivo fuente particular. filename debe ser una ruta absoluta que incluya el directorio de compilación de la CU asociada con el archivo fuente. Las rutas relativas comúnmente aparecen en el directorio fuente del archivo DWARF, pero estas rutas son relativas a las rutas AT_comp_dir de unidades de compilación individuales, y sin embargo un ejecutable está compuesto por múltiples CUs. Por lo tanto, para desambiguar, debuginfod espera que las consultas de fuentes prefijen los nombres de ruta relativos con el directorio de compilación de la CU, seguido de un obligatorio "/".

Nota: el llamador puede o no omitir componentes de ruta como ../, /./ o /// redundantes en los nombres de directorio. debuginfod acepta ambas formas. Específicamente, debuginfod canoniza los nombres de ruta de acuerdo con RFC3986 sección 5.2.4 (Eliminar segmentos de punto), además de reducir cualquier // a / en la ruta.

debuginfod_find_section() consulta las URLs del servidor debuginfod contenidas en $DEBUGINFOD_URLS para obtener el contenido binario de una sección ELF/DWARF contenida en un archivo de depuración o ejecutable con el build_id dado. section debe ser el nombre de la sección ELF/DWARF deseada. Si un servidor no admite consultas de secciones, debuginfod_find_section puede consultar al servidor por la información de depuración y/o el ejecutable con build_id para recuperar y extraer la sección.

debuginfod_find_metadata() consulta todas las URLs del servidor debuginfod contenidas en $DEBUGINFOD_URLS para metadatos de todas las coincidencias de una consulta clave/valor dada contra archivos en sus índices. El archivo resultante es un documento JSON. Consulte la página del manual de debuginfod-find(1) para ver ejemplos de los tipos de consultas clave/valor compatibles y sus resultados JSON.

Si path no es NULL y la consulta es exitosa, path se establece en la ruta del archivo en la caché. El llamador debe hacer free() de este valor.

Las URLs en $DEBUGINFOD_URLS pueden ser consultadas en paralelo. Tan pronto como un servidor debuginfod comience a transferir el archivo de destino, se cerrarán todas las conexiones a los otros servidores.

Un manejador client debe ser utilizado por un solo hilo a la vez. Un manejador puede ser reutilizado para una serie de búsquedas, lo que puede mejorar el rendimiento debido a la retención de conexiones y cachés.

VALOR DE RETORNO

debuginfod_begin devuelve el manejador debuginfod_client a usar con todas las demás llamadas. En caso de error, devolverá NULL y errno se establecerá.

Si una función de la familia find tiene éxito, el archivo resultante se guarda en la caché del cliente y se devuelve un descriptor de archivo a ese archivo. El descriptor de archivo apunta al principio del archivo. El llamador necesita hacer close() de este descriptor. De lo contrario, se devolverá un código de error negativo.

FUNCIONES OPCIONALES

Hay un pequeño número de funciones opcionales disponibles para ajustar o consultar el funcionamiento del cliente debuginfod.

DEVOLUCIÓN DE PROGRESO

Como las funciones debuginfod_find_*() pueden bloquearse durante segundos o más, se llama periódicamente a una función de devolución de progreso, si se configura con debuginfod_set_progressfn(). Esta función establece una nueva función de devolución de progreso (o NULL) para el manejador del cliente.

La función de devolución dada se llama desde el contexto de cada hilo que invoca cualquiera de las otras funciones de búsqueda. Se le dan dos parámetros numéricos que, si se consideran como un numerador a y un denominador b, juntos representan una fracción de finalización a/b. El denominador puede ser cero inicialmente, hasta que se conozca una cantidad como un tamaño de descarga exacto.

La función de devolución de progreso es también la forma admitida para *interrumpir* la operación de descarga. (La biblioteca *no* modifica ni dispara señales.) La función de devolución de progreso debe devolver 0 para continuar el trabajo, o cualquier otro valor para detener el trabajo tan pronto como sea posible. En consecuencia, la función debuginfod_find_*() probablemente devolverá un error, pero aún podría tener éxito.

SALIDA VERBOSA

Las funciones debuginfod_find_*() pueden utilizar varias técnicas para recuperar los archivos solicitados, a través de la caché o a través de uno o varios servidores o URLs de archivos. Para mostrar cómo se gestiona una consulta, se puede utilizar debuginfod_set_verbose_fd() para establecer un descriptor de archivo particular en el que se proporciona salida detallada sobre los pasos de la consulta y los posibles errores encontrados.

PUNTERO A DATOS DEL USUARIO

Un único puntero void * asociado con el manejador de conexión puede establecerse en cualquier momento a través de debuginfod_set_user_data() y recuperarse a través de debuginfod_get_user_data(). El valor no está definido si no se establece.

URL DEL SERVIDOR

La función debuginfod_get_url() devuelve la URL del servidor que se está consultando actualmente.

CABECERAS HTTP

Las funciones debuginfod_add_http_header() y debuginfod_get_headers() permiten añadir cabeceras HTTP personalizadas a las solicitudes salientes y consultar las cabeceras HTTP devueltas por el servidor, respectivamente.

VARIABLES DE ENTORNO

Las URLs de los servidores debuginfod pueden ser especificadas por la variable de entorno $DEBUGINFOD_URLS.

Si $DEBUGINFOD_URLS no está definida, entonces se intenta consultar un conjunto de URLs predeterminadas.

Las URLs predeterminadas son:

  • https://debuginfod.elfutils.org
  • https://debuginfod.opensuse.org
  • https://debuginfod.fedoraproject.org
  • https://debuginfod.ubuntu.com

Los archivos solicitados se descargan en el directorio de caché de debuginfod. Por defecto, es $XDG_CACHE_HOME/debuginfod (o ~/.cache/debuginfod si $XDG_CACHE_HOME no está definida).

Si se establece la variable de entorno $DEBUGINFOD_DIR, entonces los servidores debuginfod se consultan directamente en el directorio especificado, no a través de la red.

EJEMPLOS

Para obtener el archivo de información de depuración de un ejecutable ejemplo:

char *debuginfo_path = NULL;
debuginfod_client *client = debuginfod_begin();
if (client) {
    int fd = debuginfod_find_debuginfo(client, build_id, build_id_len, &debuginfo_path);
    if (fd >= 0) {
        // use the file at debuginfo_path or read from fd
        close(fd);
    }
    free(debuginfo_path);
    debuginfod_end(client);
}

HTTP

HEADER

Antes de que se inicie cada función de búsqueda, una aplicación cliente puede añadir cabeceras de solicitud HTTP. Estas se restablecen después de cada función de búsqueda. debuginfod_add_http_header() puede llamarse con cadenas de la forma "Header: value". Estas cadenas son copiadas por la biblioteca. Un valor de retorno cero indica éxito, pero las condiciones de falta de memoria pueden resultar en un valor distinto de cero -ENOMEM. Si la cadena tiene un formato incorrecto, se devolverá

-EINVAL.

$DEBUGINFOD_HEADERS_FILE especifica un archivo para proporcionar cabeceras a las solicitudes salientes. Cada línea de este archivo que no sea de espacios en blanco se trata como si se llamara a debuginfod_add_http_header() con su

contenido.

Tenga en cuenta que la implementación actual de la biblioteca debuginfod-client usa libcurl, pero no debe depender de ese hecho. No use esta función para reemplazar ninguna cabecera estándar, excepto para el User-Agent mencionado a continuación. Puede usar esta función para añadir información de autorización para el control de acceso, o para proporcionar cabeceras opcionales al servidor con fines de

registro.

Por defecto, la biblioteca añade una cabecera User-Agent: descriptiva a las solicitudes salientes. Si la aplicación cliente añade una cabecera con el mismo nombre, esta configuración por defecto se

omite.

Durante o después de una búsqueda, una aplicación cliente puede llamar a debuginfod_get_headers() para recopilar el subconjunto de cabeceras de respuesta HTTP recibidas del servidor debuginfod actual o más reciente. Solo se conservan aquellas cabeceras con el prefijo X-DEBUGINFOD (sin distinguir mayúsculas de minúsculas). Se devuelven como una sola cadena, con cada "cabecera: valor" terminada con un \n (no \r\n com

o en HTTP). Puede ser NULL. La cadena resultante es propiedad de la biblio
teca y no debe ser modificada ni liberada. El llamante debe copiar la cadena devuelta si necesita usarla más allá de la liberación del objeto cliente.

SECURIT

Y

Si hay firmas IMA disponibles de los RPM que contienen los archivos solicitados, entonces debuginfod extraerá esas firmas en cabeceras de respuesta, y debuginfod_find_*() realizará la verificación sobre los archivos. La política de validación se controla mediante etiquetas insertadas en $DEBUGINFOD_URLS. Por defecto, debuginfod_find_*() actúa en modo

ignorar.

Si se accede a través de HTTP en lugar de HTTPS, la red debe ser de confianza. La información de autenticación a través de la biblioteca libcurl interna no está habilitada actualmente, excepto para el estilo de texto plano básico http[s]://userid:password@hostname/. (El servidor debuginfod no real

iza autenticación, pero un servidor
proxy de front-end podría hacerlo.)

CACH

E

Antes de cada consulta, la biblioteca cliente debuginfod comprueba si es necesario limpiar la caché. Si es hora de limpiar, la biblioteca recorre el directorio de caché y elimina las descargased artefactos relacionados con debuginfo y directorios recientemente vacíos, si no se han accedido

recientemente.

Los archivos de control se encuentran directamente bajo el directorio de caché. Contienen números decimales simples para establecer parámetros de configuración relacionados con la caché. Si los archivos no existen, la biblioteca de cliente crea los archivos con los valores de parámetros predeterminados como

contenido.

Después de cada consulta, la biblioteca de cliente de debuginfod deposita los archivos recién recibidos en un directorio y archivo que se nombran en función del build-id. Una consulta fallida también se almacena en caché mediante un archivo especial. La convención de nombrado utilizada para estos artefactos es deliberadamente no documen

tada.
