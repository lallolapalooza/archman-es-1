1.0

Introd
ucción

Es sabio recordar la siguiente cita de Dijkstra,

quien dijo:

Las pruebas nunca demuestr

an la ausencia de fallos, s
olo muestran su presencia.

En particular, la cobertura de código es solo un arma en el arsenal de pruebas del ingeniero

de software.

Cualquier discusión sobre las métricas de cobertura de código se ve obstaculizada por el hecho de que muchos autores utilizan términos diferentes para describir el mismo tipo de cobertura. Aquí, proporcionaré solo una breve introducción a algunas de las métricas más

comunes.

2.0

Métricas

2.1 Cobertura de

sentencias 
Esta es la forma más básica de cobertura de código. Una sentencia está cubierta si se ejecuta. Nótese que sentencia != línea de código. Múltiples sentencias en una sola línea pueden confundir los asuntos - la presentación de informes si nada
más.

Cuando hay secuencias de sentencias sin ramificaciones, no es necesario contar la ejecución de cada sentencia, con una será suficiente, pero a la gente a menudo le gusta que se informe el recuento de cada línea, especialmente en las estadísticas de resumen. Sin embargo, no está claro para mí que esto sea realmente

útil.

Este tipo de cobertura es bastante débil en el sentido de que incluso con

un 100% de cobertura de sentencias, aún puede haber problemas graves en
un programa que podrían descubrirse a través de otros tipos de métricas.

Puede ser bastante difícil lograr un 100% de cobertura de sentencias. Puede haber secciones de código diseñadas para manejar condiciones de error, o eventos que ocurren raramente, como una señal recibida durante cierta sección de código. También puede

haber código que nunca
debería ejecutarse:

if ($param > 20) { die "This should never happen!";

}

Puede ser útil marcar dicho código de alguna manera y señalar un error si se

ejecuta.

La cobertura de sentencias, o algo muy similar, puede llamarse ejecución de sentencias, líneas, bloques, bloques básicos o cobertura de segmentos. Tiendo a favorecer la cobertura de bloques, que no intenta extender sus resultados a cada

sentencia.

2.2 Cobertura de

ramas

El objetivo de la cobertura de ramas es asegurar que siempre que un programa pueda saltar, salte a todos los destinos posibles. El ejemplo más simple es una sentencia if

completa: 
if ($x) {
  print "a";
} else {
  print "b";
}

En un ejemplo tan simple, la cobertura de sentencias es igual de potente, pero la cobertura de ramas también debería permitir el caso en el que falta la parte

else:

if ($x)

{ prin
t "a"; }

La cobertura completa solo se logra aquí

si

$

x 
es verdadero en una ocasión y falso en
otra.

Un 100% de cobertura de ramas implica un 100% de cobertura de

sentencias. 
La cobertura de ramas también se llama cobertura de decisiones o de todos los
bordes.

2.3 Cobertura de caminos Hay clases de errores que la cobertura de ramas no puede detectar,

como:

$h = undef; if ($x) { $h = { a => 1 }; } if ($y) { print $h->{a};

}

Se puede lograr un 10

0% de cobertura de ra
mas configurando ($x,

$

y

) a (1, 1) y luego a (0, 0). Pero si tenemos (0, 1) entonces las cosas

estallan. 
El propósito de la cobertura de caminos es asegurar que se tomen todos los caminos a través del programa. En cualquier programa de tamaño razonable habrá un número enorme de caminos a través del programa y así en la práctica los caminos pueden limitarse a una sola subrutina, si la subrutina no es demasiado grande, o simplemente a dos ramas
consecutivas.

En el ejemplo anterior hay cuatro caminos que corresponden a la tabla de verdad para $

x

y

$y . Para lograr un 100% de cobertura de caminos, todos deben ser tomados. Nótese que los else faltantes cuentan como caminos. En algunos casos puede ser imposible lograr un 100% de cobertura de

caminos:

a if $x; b; c if

$x; 
Un 50% de cobertura de caminos es lo mejor que se puede obtener
aquí.

Los bucles también contribuyen a los caminos, y plantean sus propios problemas que ignoraré por

ahora.

Un 100% de cobertura de caminos implica un 100% de cobertura de

ramas.

La cobertura de caminos y algunos de sus primos cercanos, también son conocidos como cobertura de predicados, ruta base y LCSAJ (Secuencia Lineal de Código y Salto)

.

2.4 Cobe

rtura de e
xpresiones

Cuando se evalúa una expresión booleana, puede ser útil asegurar que todos los términos de la expresión se ejerciten. Por

ejemplo:

a if $x ||

$y 
La expresión debería ejercitarse con
($x,

$y [[66 ]]) configurado a (0, 0) (requerido para la cobertura de ramas), (0, 1) y (1, 0) (para asegurar que $x y $

y

son independientes) y posiblemente con (1, 1)

.

La cobertura de expresiones se complica, y es difícil de lograr, a medida que la expresión se

complica. 
Las expresiones que no son directamente parte de una construcción de ramificación también deberían
cubrirse:

$z = $x

|| $y;
a if $z;

La cobertura de expresiones también se conoce como cobertura de condiciones, condición-decisión y decisión

múltiple.

3.0 Otras

consideraciones

Para que la gente realmente use la cobertura de código, necesi

ta ser simple de usar. También debería ser simple entender lo
s resultados y rectificar cualquier problema que surja. Final
mente, si la sobrecarga es demasiado grande, tampoco se usará.

Así que hay un tutorial básico sobre cobertura de código, o al menos mi versión de él. Escribir algunos de estos términos en google probablemente proporcionará una base para

la investigación futura.
