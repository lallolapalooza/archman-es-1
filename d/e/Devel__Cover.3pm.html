DESCRIPCIÓ

N

Este módulo proporciona métricas de cobertura de código para Perl. Las métricas de cobertura de código describen qué tan a fondo las pruebas ejercitan el código. Al usar Devel::Cover puedes descubrir áreas de código no ejercitadas por tus pruebas y determinar qué pruebas crear para aumentar la cobertura. La cobertura de código puede considerarse una medida indirecta de la

calidad.

Devel::Cover es ahora bastante estable y proporciona muchas de las características que se esperan en una herramienta de cobertura

útil.

Se informa la información de cobertura de sentencias, ramas, condiciones, subrutinas y pod. Los datos de cobertura de sentencias y subrutinas deberían ser precisos. Los datos de cobertura de ramas y condiciones también deberían ser mayormente precisos, aunque no siempre lo que uno podría esperar inicialmente. La cobertura de pod proviene de Pod::Coverage. Si Pod::Coverage::CountParents está disponible, se usará en su

lugar.

El programa cover puede usarse para generar informes de cobertura. Devel::Cover se envía con una serie de informes, incluyendo varios tipos de salida HTML, informes de texto, un informe para mostrar la cobertura faltante en el mismo formato que los errores de compilación y un informe para mostrar información de cobertura dentro del editor

Vim.

Es posible añadir anotaciones a los informes, por ejemplo puedes añadir una columna a un informe HTML que muestre quién cambió por última vez una línea, tal como lo determina git blame. Algunos módulos de anotación se envían con Devel::Cover y puedes crear los tuyos

fácilmente.

El programa gcov2perl puede usarse para convertir archivos gcov a bases de datos "Devel::Cover". Esto te permite mostrar tu cobertura de código C o XS junto con tu cobertura de Perl, o usar cualquiera de los informes de Devel::Cover para mostrar tus datos de cobertura de

C.

Los datos de cobertura de código se recopilan reemplazando operaciones de perl con funciones que cuentan cuántas veces se ejecutan las operaciones. Estos datos se mapean de vuelta a la realidad usando los módulos del compilador B. También hay una instalación de perfilado de sentencias en la que no se debe confiar. Para un perfilado adecuado usa Devel::NYTProf. Versiones anteriores de Devel::Cover recopilaban datos de cobertura reemplazando la función runops de perl. Todavía es posible cambiar a ese modo de operación, pero ahora recibe poca prueba y probablemente se eliminará pronto. Probablemente no te importe nada de

esto.

La lista de correo más apropiada en la que discutir este módulo sería perl-qa. Ver https://lists.perl.org/list

/perl-qa.html.

El repositorio de Devel::Cover se puede encontrar en https://github.com/pjcj/Devel--Cover. Aquí tambi

reportar los problemas.

Más sobre opciones de

cobertura

Puedes especificar opciones para algunos criterios de cobertura. Por el momento solo la cobertura de pod acepta algunas opciones. Estos son los parámetros que se pasan al constructor de Pod::Coverage. Las opciones extra se separan por guiones, y puedes especificar tantas como desees. Por ejemplo, para especificar que todas las subrutinas que contienen xx son privadas, llama a Devel::Cover con la opción -coverage,pod-also_private-xx

.

O, para ignorar todos los archivos en "t/lib" así como los archivos que terminan en "Foo.p

m": 
cover -test -silent -ignore ^t/lib/,Foo.
pm$

Ten en cuenta que "-ignore" reemplaza cualquier expresión regular de ignorado predeterminada. Para preservar cualquier expresión regular de ignorado que ya haya sido establecida, usa "+ignore"

: 
cover -test
-silent +i
gnore ^t/l
ib/,Foo.pm$

SELECCIÓN DE ARCHIVOS A

CUBRIR

Puedes seleccionar los archivos para los que deseas recopilar datos de cobertura usando las opciones select, ignore e inc. El sistema utiliza el siguiente procedimiento para decidir si un archivo será incluido en los informes de

cobertura:
  • Si el archivo coincide con una RE dada como opción select, será
    • incluido
  • De lo contrario, si coincide con una RE dada como opción ignore, no será
    • incluido
  • De lo contrario, si está en uno de los directorios inc, no será
    • incluido
  • De lo cont
    • rario, ser
á incluido

Puedes añadir a las REs para seleccionar usando +select, o puedes restablecer las selecciones usando -select. El mismo principio se aplica a las REs para

ignorar.

Los directorios inc se rellenan inicialmente con el contenido del arreglo @INC de perl. Puedes restablecer estos directorios usando -inc, o añadir a ellos usando

+inc.

Aunque estas opciones toman expresiones regulares, no debes encerrar la RE dentro de // o cualquier otro carácter de

comillas.

Las opciones -coverage, [+-]select, [+-]ignore y [+-]inc pueden especificarse múltiples veces, pero t

ambién pueden tomar múltiples argumentos separados por comas. En cualquier caso, no debes añadir un
espacio después de la coma, a menos que quieras que el argumento comience con ese espacio literal.

CRITERIOS

DESCUBRIBLES

A veces tienes código que es indescubrible por alguna razón. Tal vez es una cláusula else que no se puede alcanzar, o una comprobación de una condición de error que nunca debería ocurrir. Puedes decirle a Devel::Cover que ciertos criterios son indescubribles y luego no se cuentan como errores cuando no se ejercitan. De hecho, se cuentan como errores si se

ejercitan.

Esta característica solo debería usarse como un último recurso. Idealmente, encontrarías alguna manera de ejercitar todo tu código. Pero si has analizado tu código y determinado que no vas a poder ejercitarlo, puede ser mejor registrar ese hecho de alguna manera formal y dejar que Devel::Cover deje de quejarse al respecto, para que los problemas reales no se pierdan en el

ruido.

Si tienes criterios indescubribles, sugiero no usar el informe HTML predeterminado (que usa html_minimal en este momento) porque a veces muestra puntos indescubribles como no cubiertos. En su lugar, deberías usar el informe html_basic para la salida HTML, que debería comportarse correctamente en este

respecto.

Hay dos formas de especificar una construcción como indescubrible, una invasiva y una no

invasiva.

Especificación

invasiva

Puedes usar comentarios especiales en tu código para especificar criterios indescubribles. Los comentarios tienen la

forma: 
# uncoverable <criterio>
[detalles]

La palabra clave "uncoverable" debe ser el primer texto en el comentario. Debería ser seguida por el nombre del criterio de cobertura que es indescubrible. Luego puede haber más información dependiendo de la naturaleza de la construcción

indescubrible.

En todos los casos, un atributo de clase puede incluirse en los detalles. Actualmente se reconoce un único atributo de clase: ignore_covered_err. Normalmente, se señala un error si el código marcado como indescubrible es cubierto. Cuando se especifica el atributo ignore_covered_err, tales errores no se señalarán. Este es un método más preciso para señalar tales excepciones que la bandera global -ignore_covered_err del programa

cover.

También hay un atributo note que también puede incluirse en los detalles. Este debería ser el atributo final y consumirá todo el texto restante. Actualmente este atributo no se usa, pero está destinado a ser una forma de documentación para los datos

indescubribles.

Ejemplo

: 
# uncoverable branch true count:1..3 class:ignore_covered_err note:error
chk

Sentencia

s

El comentario "uncoverable" debería aparecer en la misma línea que la sentencia, o en la línea

anterior: 
$impossible++;  # uncoverable statement
# uncoverable statement
it_has_all_gone_horribly_wrong()
;

Si hay múltiples sentencias (o cualquier otro criterio) en una línea, puedes especificar qué sentencia es indescubrible usando el atributo "count", count:n, que indica que la sentencia indescubrible es la n-ésima sentencia en la

línea. 
# uncoverable statement count:1
# uncoverable statement count:2
cannot_run_this(); or_this()
;

Rama

s

El comentario "uncoverable" debería especificar si la rama "true" o "false" es

indescubrible. 
# uncoverable branch true
if (pi ==
3)

Ambas ramas pueden ser

indescubribles: 
# uncoverable branch true
# uncoverable branch false
if (impossible_thing_happened_one_way()) {
  handle_it_one_way();      # uncoverable statement
} else {
  handle_it_another_way();  # uncoverable statement
}

Si hay un elsif en la rama, puede abordarse como la segunda rama en la línea usando el atributo "count". Los elsifs posteriores son el tercer y cuarto valor de "count", y así

sucesivamente: 
# uncoverable branch false count:2
if ($thing == 1) {
  handle_thing_being_one();
} elsif ($thing == 2) {
  handle_thing_being_tow();
} else {
  die "thing can only be one or two, not $thing"; # uncoverable statement
}

Condicione

s

Debido a la forma en que Perl corta las operaciones booleanas, hay tres formas en que tales condicionales pueden ser indescubribles. En el caso de " $x && $y" por ejemplo, el operador izquierdo puede nunca ser verdadero, el operador derecho puede nunca ser verdadero, y toda la operación puede nunca ser falsa. Estas condiciones pueden modelarse

así: 
# uncoverable branch true
# uncoverable condition left
# uncoverable condition false
if ($x && !$y) {
  $x++;  # uncoverable statement
}
# uncoverable branch true
# uncoverable condition right
# uncoverable condition false
if (!$x && $y) {
}

Los condicionales "Or" se manejan de manera similar (TODO - proporcionar algunos ejemplos) pero los condicionales "xor" aún no se manejan

correctamente.

Al igual que con las ramas, el valor "count" puede usarse para cualquiera de las condiciones en condicionales elsif, o para condiciones

complejas.

Subrutina

s

Una subrutina debería marcarse como indescubrible en el punto donde la primera sentencia se marca como indescubrible. Idealmente, todos los demás criterios en la subrutina se marcarían como indescubribles automáticamente, pero ese no es el caso en este

momento. 
sub z {
  # uncoverable
subroutine $y++; #
uncoverable statement }

invasiva

Variables de

usuario

La opción -silent se activa cuando Devel::Cover se invoca a través de $HARNESS_PERL_SWITCHES o $PERL5OPT. Devel::Cover intenta hacer lo correcto cuando $MOD_PERL está establecido. $DEVEL_COVER_OPTIONS se añade a cualquier opción pasada a Devel::

Cover.

Ten en cuenta que cuando Devel::Cover se invoca a través de una variable de entorno, cualquier módulo especificado en la línea de comandos, como a través

de la opción -Mmodule, no será cubierto. Esto se debe a que las variables de entorno se procesan después de la línea de comandos y cualquier código a cu
brir debe aparecer después de que Devel::Cover haya sido cargado. Para solucionar esto, Devel::Cover también puede especificarse en la línea de comandos.

Variables de

desarrollador

Al ejecutar la propia suite de pruebas de Devel::Cover, $DEVEL_COVER_DEBUG activa la información de depuración, $DEVEL_COVER_GOLDEN_VERSION anula la idea propia de Devel::Cover sobre qué resultados dorados debería probar, y $DEVEL_COVER_NO_COVERAGE ejecuta las pruebas sin recopilar cobertura. $DEVEL_COVER_DB_FORMAT puede establecerse en "Sereal", "JSON" o "Storable" para anular la elección predeterminada del formato de DB (Sereal, luego JSON si cualquiera de los dos está disponible, de lo contrario Storable). $DEVEL_COVER_IO_OPTIONS proporciona un control detallado sobre el formato de DB. Por ejemplo, establecerlo en "pretty" cuando el formato es JSON almacenará la DB en un formato JSON legible. $DEVEL_COVER_CPUS anula la detección

automática del número
de CPUs a usar en l
as pruebas paralelas.

S

Hay cosas que Devel::Cover no puede

cubrir.

Ausencia de dependencias

compartidas

Perl lleva la cuenta de qué módulos se han cargado (para evitar recargarlos). Por ello, no es posible obtener cobertura para una ruta donde un import en tiempo de ejecución falla si el módulo que se importa es uno que Devel::Cover usa internamente. Por ejemplo, supongamos que su programa tiene esta

función: 
sub foo {
  eval { require Storable };
  if ($@) {
      carp "Can't find Storable";
      return;
  }
  # ...
}

Podría escribir una prueba para el modo de fallo

como 
BEGIN { @INC = () }
foo();
# check for error
message

Debido a que Devel::Cover usa Storable internamente, el import tendrá éxito (y la prueba fallará) en una ejecución de

cobertura.
