WEBAPI

La webapi de debuginfod se asemeja a un servicio de archivos ordinario, donde una petición GET con una ruta que contiene un buildid conocido resulta en un archivo. Las combinaciones de buildid/petición desconocidas resultan en códigos de error HTTP. Esta similitud con el servicio de archivos es intencional, para que una instalación pueda aprovechar la infraestructura de gestión HTTP estándar.

Al encontrar un archivo en un archivo comprimido o simplemente en la base de datos, se añaden algunas cabeceras http personalizadas a la respuesta. Para los archivos en la base de datos se añaden X-DEBUGINFOD-FILE y X-DEBUGINFOD-SIZE. X-DEBUGINFOD-FILE es simplemente el nombre de archivo sin escapar y X-DEBUGINFOD-SIZE es el tamaño del archivo. Para los archivos encontrados en archivos comprimidos, además de X-DEBUGINFOD-FILE y X-DEBUGINFOD-SIZE, se añade X-DEBUGINFOD-ARCHIVE. X-DEBUGINFOD-ARCHIVE es el nombre del archivo comprimido en el que se encontró el archivo. X-DEBUGINFOD-IMA-SIGNATURE contiene la firma IMA por archivo como un blob hexadecimal.

% debuginfod-find -v debuginfo /bin/ls |& grep -i x-debuginfo
x-debuginfod-size: 502024
x-debuginfod-archive: /mnt/fedora_koji_prod/koji/packages/coreutils/9.3/4.fc39/x86_64/coreutils-debuginfo-9.3-4.fc39.x86_64.rpm
x-debuginfod-file: /usr/lib/debug/usr/bin/ls-9.3-4.fc39.x86_64.debug
X-DEBUGINFOD-SIZE
El tamaño del archivo, en bytes. Esto puede diferir del campo http Content-Length: (si está presente), debido a la compresión en tránsito.
X-DEBUGINFOD-FILE
La ruta de archivo completa del archivo relacionado con el buildid dado.
X-DEBUGINFOD-ARCHIVE
La ruta de archivo completa del archivo comprimido que contenía el archivo mencionado anteriormente, si lo hay.

Hay un puñado de peticiones relacionadas con buildid. En cada caso, el buildid está codificado como una cadena hexadecimal en minúsculas. Por ejemplo, para un programa /bin/ls, mire la nota ELF GNU_BUILD_ID:

% readelf -n /bin/ls | grep -A4 build.id
Note section [ 4] '.note.gnu.buildid' of 36 bytes at offset 0x340:
Owner          Data size  Type
GNU                   20  GNU_BUILD_ID
Build ID: 8713b9c3fb8a720137a4a08b325905c7aaf8429d

Entonces el BUILDID hexadecimal es simplemente:

8713b9c3fb8a720137a4a08b325905c7aaf8429d

/buildid/BUILDID/debuginfo

Si el buildid dado es conocido por el servidor, esta petición resultará en un objeto binario que contiene las secciones habituales .*debug_* . Este puede ser un archivo de debuginfo dividido creado por strip, o puede ser un ejecutable original sin "strip".

/buildid/BUILDID/executable

Si el buildid dado es conocido por el servidor, esta petición resultará en un objeto binario que contiene los segmentos ejecutables normales. Este puede ser un ejecutable "stripped" por strip, o puede ser un ejecutable original sin "strip". ET_DYN las bibliotecas compartidas se consideran un tipo de ejecutable.

/buildid/BUILDID/source/SOURCE/FILE

Si el buildid dado es conocido por el servidor, esta petición resultará en un objeto binario que contiene el archivo fuente mencionado. La ruta debería ser absoluta. Los nombres de ruta relativos aparecen comúnmente en el directorio de fuentes del archivo DWARF, pero estas rutas son relativas a las rutas AT_comp_dir de cada unidad de compilación, y sin embargo un ejecutable está compuesto de múltiples UCs. Por lo tanto, para desambiguar, debuginfod espera que las consultas de fuente prefijen los nombres de ruta relativos con el directorio de compilación de la UC, seguido de un "/" obligatorio.

Nota: el llamador puede o no omitir ../ o /./ o componentes de ruta extraños en los nombres de directorios. debuginfod acepta ambas formas. Específicamente, debuginfod canoniza los nombres de ruta de acuerdo con RFC3986 sección 5.2.4 (Eliminar segmentos de punto), más reducir cualquier // a / en la ruta.

Por ejemplo:

#include <stdio.h> /buildid/BUILDID/source/usr/include/stdio.h
/path/to/foo.c /buildid/BUILDID/source/path/to/foo.c
AT_comp_dir=/zoo/ /buildid/BUILDID/source/zoo//../bar/foo.c

Nota: el cliente debe escapar (%) los caracteres en /SOURCE/FILE que no se muestren como "no restringidos" en la sección 2.3 de RFC3986. Algunos caracteres que se escaparán incluyen "+", "\", "$", "!", el carácter 'espacio' y ";". RFC3986 incluye una lista más completa de estos caracteres.

/buildid/BUILDID/section/SECTION

Si el buildid dado es conocido por el servidor, el servidor intentará extraer el contenido de una sección ELF/DWARF llamada SECTION del archivo de información de depuración que coincida con BUILDID. Si el archivo de información de depuración no se puede encontrar o la sección es de tipo SHT_NOBITS, entonces el servidor intentará extraer la sección del ejecutable que coincida con BUILDID. Si la sección se extrae correctamente, esta solicitud resulta en un objeto binario del contenido de la sección. Tenga en cuenta que este resultado son los contenidos binarios brutos de la sección, no un archivo ELF.

/metrics

Este punto final devuelve un volcado de texto plano formateado por Prometheus de una variedad de estadísticas sobre el funcionamiento del servidor debuginfod. El conjunto exacto de métricas y sus significados pueden cambiar en versiones futuras.

/metadata?key=KEY&value=VALUE

Este punto final desencadena una búsqueda de archivos en el índice más los servidores federados upstream, basándose en la clave y el valor dados. Si tiene éxito, el resultado es una matriz textual application/json, que enumera los metadatos de los archivos coincidentes. Consulte debuginfod-find(1) para obtener documentación sobre los parámetros de búsqueda comunes de clave/valor y el esquema de datos resultante.

GESTIÓN DE DATOS

debuginfod almacena su índice en una base de datos sqlite en un conjunto densamente empaquetado de tablas interconectadas. Si bien la representación es tan eficiente como hemos podido hacerla, todavía se necesita una cantidad considerable de datos para registrar toda la información relacionada con la depuración de potencialmente muchos archivos. Esta sección ofrece algunos consejos sobre las implicaciones.

Como explicación general del tamaño, considere que debuginfod indexa archivos ELF/DWARF, almacena sus nombres y los nombres de archivos fuente referenciados, y se almacenarán los buildids. Al indexar archivos, almacena cada nombre de archivo *de o en* un archivo, cada buildid, más cada nombre de archivo fuente referenciado de un archivo DWARF. (Indexar archivos lleva más espacio porque los archivos fuente a menudo residen en subpaquetes separados que pueden no indexarse en el mismo pase, por lo que se deben conservar metadatos adicionales.)

Bajando a números, en el caso de los RPM de Fedora (esencialmente, archivos cpio comprimidos con gzip), la base de datos de índice sqlite tiende a ser del 0,5% al 3% de su tamaño. Es más grande para binarios que se ensamblan a partir de muchos archivos fuente, o paquetes que contienen mucho contenido no relacionado con la depuración. Puede ser aún más grande durante la fase de indexación debido a archivos temporales de registro de escritura anticipada (write-ahead logging) de sqlite; estos se comprueban (se limpian y eliminan) al apagar. Puede ser útil aplicar restricciones de expresión regular estrictas -I o -X para excluir archivos del escaneo que sabe que no tienen contenido relevante para la depuración.

A medida que debuginfod se ejecuta en modo *activo* normal, escanea periódicamente sus directorios de destino, y cualquier contenido nuevo encontrado se agrega a la base de datos. El contenido antiguo, como los datos de archivos que han desaparecido o que han sido reemplazados por versiones más nuevas, se elimina en un pase de *limpieza* periódico. Esto significa que los archivos sqlite crecen rápidamente durante la indexación inicial, lentamente durante los reescaneos del índice y se reducen periódicamente durante la limpieza. También hay un pase opcional de *limpieza máxima* de una sola vez disponible. Elimina información de datos no relacionados con la depuración del índice de contenido de archivos, como nombres de archivos encontrados en archivos (registros "archive sdef") que no se hacen referencia como archivos fuente de ningún binario encontrado en archivos (registros "archive sref"). Esto puede ahorrar un espacio considerable en disco. Sin embargo, es lento y temporalmente requiere hasta el doble del tamaño de la base de datos como espacio libre. Peor aún: puede resultar en la falta de información del código fuente si los recorridos de archivos se interrumpieron, por lo que no se conocieron todas las referencias de archivos fuente. Úselo raramente para pulir un índice completo.

Debe asegurarse de que quede suficiente espacio en disco disponible. (La avalancha de mensajes de error en -ENOSPC es fea y molesta. Pero, al igual que con la mayoría de los otros errores, debuginfod se reanudará cuando los recursos lo permitan.) Si es necesario, debuginfod se puede detener, mover o eliminar el archivo de la base de datos, y reiniciar debuginfod.

sqlite ofrece varias opciones relacionadas con el rendimiento en forma de pragmas. Algunos pueden ser útiles para ajustar los valores predeterminados más los extras de debuginfod. La opción -D puede ser útil para decirle a debuginfod que ejecute los fragmentos de SQL dados después de los comandos básicos de creación del esquema. Por ejemplo, los pragmas "synchronous", "cache_size", "auto_vacuum", "threads", "journal_mode" pueden ser divertidos de ajustar a través de -D, si está buscando el máximo rendimiento. Los pragmas "optimize", "wal_checkpoint" pueden ser útiles para ejecutar periódicamente, fuera de debuginfod. La configuración predeterminada está orientada al rendimiento en lugar de a la fiabilidad, por lo que un bloqueo de hardware podría corromper la base de datos. En estos casos, puede ser necesario eliminar manualmente la base de datos sqlite y empezar de nuevo.

A medida que debuginfod cambie en el futuro, es posible que no tengamos más remedio que cambiar el esquema de la base de datos de manera incompatible. Si esto sucede, las nuevas versiones de debuginfod emitirán sentencias SQL para *eliminar* todo el esquema y datos anteriores, y comenzarán de nuevo. Por lo tanto, no se desperdiciará espacio en disco por retener un conjunto de datos que ya no sea utilizable.

En resumen, si su sistema puede soportar una relación de tamaño de índice a conjunto de datos de archivo del 0,5%-3%, y un crecimiento lento después, no debería preocuparse por el espacio en disco. Si un bloqueo del sistema corrompe la base de datos, o desea forzar a debuginfod a reiniciarse y empezar de nuevo, simplemente borre el archivo sqlite antes de reiniciar debuginfod.

En contraste, en modo *pasivo*, se deshabilitan todos los escaneos y limpiezas, y la base de datos de índice permanece de solo lectura. Esto hace que la base de datos sea más adecuada para compartir entre servidores o sitios con replicación unidireccional simple, y las consideraciones de gestión de datos son generalmente irrelevantes.

SEGURIDAD

debuginfod *no* incluye ninguna característica de seguridad particular. Si bien es robusto con respecto a las entradas, es posible cierto abuso. Crea un nuevo hilo para cada solicitud HTTP entrante, lo que podría provocar una denegación de servicio en términos de RAM, CPU, E/S de disco o E/S de red. Si esto es un problema, se recomienda a los usuarios que instalen debuginfod con un proxy inverso HTTPS frontal que aplique las políticas del sitio para firewalling, autenticación, integridad, autorización y control de carga.

Los proxies frontales pueden omitir componentes sensibles de nombres de ruta en las cabeceras de respuesta X-DEBUGINFOD-FILE/ARCHIVE. Por ejemplo, utilizando el mod_headers de Apache httpd, puede eliminar todo el prefijo del nombre del directorio:

Header edit x-debuginfod-archive ".*/" ""

Al retransmitir consultas a debuginfods upstream, debuginfod *no* incluye ninguna característica de seguridad particular. Confía en que los binarios devueltos por los debuginfods son precisos. Por lo tanto, la lista de servidores solo debe incluir aquellos de confianza. Si se accede a través de HTTP en lugar de HTTPS, la red debe ser de confianza. La información de autenticación a través de la biblioteca interna libcurl no está habilitada actualmente.

VARIABLES DE ENTORNO

$TMPDIR
Esta variable de entorno apunta a un sistema de archivos que se utilizará para archivos temporales. El valor predeterminado es /tmp.
$DEBUGINFOD_URLS
Esta variable de entorno contiene una lista de prefijos de URL para instancias confiables de debuginfod. Los prefijos de URL alternativos están separados por espacio. Esta variable de entorno puede ser establecida por scripts /etc/profile.d que lean archivos /etc/debuginfod/*.urls.

Esta variable de entorno también puede contener etiquetas de política que dictan la política de respuesta para verificar las firmas IMA por archivo en los RPM. Dado que la lista separada por espacios se lee de izquierda a derecha, al encontrar una etiqueta, las URL posteriores hasta la siguiente etiqueta se manejarán utilizando la política especificada. Todas las URL antes de la primera etiqueta utilizarán la política predeterminada, *ima:ignore*. Por ejemplo:


DEBUGINFOD_URLS="https://foo.com ima:enforcing https://bar.ca http://localhost:8002/ ima:ignore https://baz.org"

Donde foo.com y baz.org usan la política predeterminada *ignore* y bar.ca y localhost usan una política *enforcing*. La etiqueta de política puede ser una de las siguientes:

ima:enforcing Cada archivo descargado requiere una firma válida, protegiendo completamente la integridad.
ima:ignore Omite la verificación por completo, proporcionando ninguna protección.

Las alertas de fallo de validación se dirigirán según lo especificado en $DEBUGINFOD_VERBOSE.

$DEBUGINFOD_CACHE_PATH
Esta variable de entorno rige la ubicación de la caché donde se almacenan los archivos descargados y los archivos de control de caché. El directorio predeterminado se elige en función de otras variables de entorno, véase más abajo.
$DEBUGINFOD_PROGRESS
Esta variable de entorno rige la función de progreso predeterminada. Si se establece, y si no se establece explícitamente una función de progreso (progressfn), la biblioteca configurará una función de progreso predeterminada. Esta función agregará un mensaje de progreso simple periódicamente a stderr. El valor predeterminado es no mostrar ninguna función de progreso.
dd>
$DEBUGINFOD_VERBOSE
Esta variable de entorno gobierna el descriptor de archivo predeterminado para la salida verbosa. Si está definida, y si no se establece explícitamente un fd verboso, la salida verbosa se producirá en STDERR_FILENO.
$DEBUGINFOD_RETRY_LIMIT
Esta variable de entorno gobierna el límite predeterminado de intentos de reintento. Si una consulta falló con un errno distinto de ENOENT, se iniciarán varios intentos dentro del límite.
$DEBUGINFOD_TIMEOUT
Esta variable de entorno gobierna la descarga de inicio de tiempo de espera para cada conexión HTTP de debuginfod. Un servidor que no proporcione al menos 100K de datos dentro de estos segundos se omite. El valor predeterminado es 90 segundos. (Cero o negativo significa "sin tiempo de espera".)
$DEBUGINFOD_MAXTIME
Esta variable de entorno dicta cuánto tiempo esperará el cliente para completar la descarga de un archivo encontrado en un servidor, en segundos. Es mejor usarla para asegurar que un archivo se descargue rápidamente o sea rechazado. El valor predeterminado es 0 (tiempo infinito).
$DEBUGINFOD_MAXSIZE
Esta variable de entorno dicta el tamaño máximo de un archivo a descargar en bytes. Es mejor usarla si el usuario desea asegurar que solo se descarguen archivos pequeños. Un valor de 0 hace que no se considere el tamaño, y el cliente puede intentar descargar un archivo de cualquier tamaño. El valor predeterminado es 0 (tamaño infinito).
$DEBUGINFOD_HEADERS_FILE
Esta variable de entorno apunta a un archivo que proporciona encabezados a peticiones HTTP salientes, uno por línea. Las líneas de encabezado no deben terminar con CRLF, a menos que esa sea la convención de salto de línea del sistema. Las líneas que solo contienen espacios en blanco se omiten.
$DEBUGINFOD_IMA_CERT_PATH
Esta variable de entorno contiene una lista de rutas de directorios absolutas que contienen certificados X.509 para la verificación IMA por archivo de RPM. Las rutas alternativas se separan con dos puntos.

CACHÉ

Antes de cada consulta, la biblioteca de cliente de debuginfod comprueba si es necesario limpiar la caché. Si es momento de limpiar, la biblioteca recorre el directorio de caché y elimina los artefactos relacionados con debuginfo descargados y los directorios que se quedan vacíos, si no se han accedido recientemente.

Los archivos de control se encuentran directamente bajo el directorio de caché. Contienen números decimales simples para establecer parámetros de configuración relacionados con la caché. Si los archivos no existen, la biblioteca de cliente crea los archivos con los valores de parámetros predeterminados como contenido.

Después de cada consulta, la biblioteca de cliente de debuginfod deposita los archivos recién recibidos en un directorio y archivo cuyo nombre se basa en el build-id. Una consulta fallida también se almacena en caché mediante un archivo especial. La convención de nombrado utilizada para estos artefactos es deliberadamente no documentada.

$XDG_CACHE_HOME/debuginfod_client/
Directorio de caché predeterminado, si $XDG_CACHE_HOME está definido.
$HOME/.cache/debuginfod_client/
Directorio de caché predeterminado, si $XDG_CACHE_HOME no está definido.
$HOME/.debuginfod_client_cache/
Directorio de caché obsoleto, usado solo si ya existe.
cache_clean_interval_s
Este archivo de control indica el intervalo entre rondas de limpieza de la caché, en segundos. El valor predeterminado es 86400, un día. 0 significa "inmediatamente".
max_unused_age_s
Este archivo de control establece cuánto tiempo se conservan los archivos relacionados con debuginfo no accedidos, en segundos. El valor predeterminado es 604800, una semana. 0 significa "inmediatamente".
cache_miss_s
Este archivo de control establece cuánto tiempo recordar un fallo de consulta, en segundos. Las nuevas consultas para los mismos artefactos dentro de esta ventana de tiempo se evitan (devolviendo un fallo inmediato en lugar de enviar una nueva consulta a los servidores). Esto acelera las consultas que probablemente seguirían fallando. El valor predeterminado es 600, 10 minutos. 0 significa "olvidar inmediatamente".
metadata_retention_s
Este archivo de control establece cuánto tiempo recordar los resultados de una consulta de metadatos. Las nuevas consultas para los mismos artefactos dentro de esta ventana de tiempo se evitan (repitiendo los mismos resultados). Esto acelera las consultas que probablemente tendrían los mismos resultados. El valor predeterminado es 3600, 1 hora. 0 significa "no conservar".
