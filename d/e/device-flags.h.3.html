Documentación de Definición de Macro

#define DEVICE_FLAG_ALWAYS_PROBE_DESCRIPTOR 0x00000800

Algunos dispositivos, particularmente los SanDisk Sansa, necesitan que siempre se consulte su 'Descriptor del Sistema Operativo' para que funcionen correctamente. Esta marca proporciona ese ajuste adicional.

#define DEVICE_FLAG_BROKEN_BATTERY_LEVEL 0x00010000

Dispositivos que no pueden soportar la lectura del nivel de batería.

#define DEVICE_FLAG_BROKEN_MTPGETOBJPROPLIST 0x00000004

Esto significa que el PTP_OC_MTP_GetObjPropList (9805) está roto de alguna manera, ya sea que no funcione en absoluto (como en los dispositivos Android) o que no devuelva correctamente todas las propiedades del objeto si el parámetro 3 se establece en 0xFFFFFFFFU.

#define DEVICE_FLAG_BROKEN_MTPGETOBJPROPLIST_ALL 0x00000001

Esto significa que el PTP_OC_MTP_GetObjPropList está roto en el sentido de que no devolverá metadatos con formato correcto para TODOS los archivos del dispositivo cuando solicite una lista de propiedades de objetos para el objeto 0xFFFFFFFF con el parámetro 3 también establecido en 0xFFFFFFFF. Compare con DEVICE_FLAG_BROKEN_MTPGETOBJECTPROPLIST, que solo indica que está roto al obtener metadatos para un ÚNICO objeto. Una forma típica en que la implementación puede estar rota es que puede no devolver un recuento correcto de los objetos, y a veces (como en los ZEN) los objetos simplemente faltan en la lista si usa esto. A veces se ha usado incorrectamente para enmascarar errores en el código (como el manejo de transacciones de datos con tamaño dado a -1 (0xFFFFFFFFU), en ese caso, por favor ayúdenos a eliminarlo ahora que el código está arreglado. A veces se utiliza porque obtener todos los objetos es demasiado lento y la transacción USB caducará si utiliza este comando.

#define DEVICE_FLAG_BROKEN_SEND_OBJECT_PROPLIST 0x00008000

Esto evita el uso de la lista de propiedades de objeto para enviar, que se utiliza al crear nuevos objetos (no solo al actualizar). El DEVICE_FLAG_BROKEN_SET_OBJECT_PROPLIST está relacionado, pero solo concierne al caso en que la lista de propiedades de objeto se envía para actualizar un objeto existente. El Toshiba Gigabeat MEU202, por ejemplo, tiene este problema.

Referenciado por LIBMTP_Create_Folder().

#define DEVICE_FLAG_BROKEN_SET_OBJECT_PROPLIST 0x00000100

El Motorola RAZR2 V8 (¿otros?) tiene una lista de propiedades de objeto para establecer defectuosa, lo que hace que el establecimiento de metadatos falle. (El establecimiento de propiedades de objeto para establecer propiedades individuales funciona en este dispositivo, pero los metadatos se ignoran simplemente en las pistas, aunque por ejemplo se pueden establecer nombres de lista de reproducción.)

#define DEVICE_FLAG_BROKEN_SET_SAMPLE_DIMENSIONS 0x00000400

El Creative Zen es bastante inestable en libmtp, pero parece ser mejor con versiones de firmware posteriores. Sin embargo, con frecuencia se bloquea al establecer las dimensiones de la carátula del álbum. Esta marca deshabilita el establecimiento de las dimensiones (lo que parece no hacer diferencia en cómo se muestra la imagen).

#define DEVICE_FLAG_CANNOT_HANDLE_DATEMODIFIED 0x00004000

Se sabe que el Sansa E250 tiene este problema, que en realidad es que el dispositivo afirma que la propiedad PTP_OPC_DateModified es de lectura/escritura pero aún así fallará al actualizarla. Solo se puede establecer correctamente la primera vez que se envía un archivo.

Cámaras que pueden capturar imágenes. (libgphoto2)

#define DEVICE_FLAG_IGNORE_HEADER_ERRORS

0x00000080

Este indicador se introdujo con la llegada de Creative ZEN 8GB. El dispositivo a veces devuelve una cabecera PTP rota como esta: < 1502 0000 0200 01d1 02d1 01d2 > los últimos 6 bytes (que represe

ntan 'code' y 'transaction ID') contienen basura. Esto rompe la especificación PTP/MTP pero funciona en Windows de todos modos, probablemente porque la implementación de Windows no verifica que
estos bytes sean válidos. Para interoperar con dispositivos como este, necesitamos este indicador para emular el error de Windows. Se han encontrado cabeceras rotas en la pila MTP de Aricent.

#define DEVICE_FLAG_IRIVER_OGG_ALZHEIMER

0x00000010

Este indicador significa que el dispositivo tiende a olvidar el tipo de archivo contenedor OGG, por lo que libmtp debe mirar las extensiones de nombre de archivo para determinar que un archivo es realmente OGG. Este es un error de firmware claro y presente, y aunque los er

rores de firmware deberían corregirse en el firmware, nos gusta tanto OGG que lo respaldamos introduciendo este indicador. El error solo se ha visto en dispositivos iriver. Activar este indicador no dañará nada, solo que la comprobación de la extensión del nombre de archi
vo se hará para archivos de tipo 'desconocido'. Si el reproductor ni siquiera sabe (informa) que soporta ogg aunque sí lo hace, por favor use el indicador más fuerte OGG_IS_UNKNOWN, que forzará el soporte de ogg en cualquier cosa con la extensión de nombre de archivo .ogg.

#define DEVICE_FLAG_NO_RELEASE_INTERFACE

0x00000040

Este indicador indica que el dispositivo se bloqueará si intenta obtener el estado de los puntos de conexión

y/o liberar la interfaz al cerrar el dispositivo. Esto soluciona problemas con los dispositivos SanDisk Sans
a especialmente. Puede ser un efecto secundario de un comportamiento de Windows de nunca liberar interfaces.

#define DEVICE_FLAG_NO_ZERO_READS

0x00000008

Esto significa que el dispositivo no envía paquetes cero para indicar el fin de la transferencia cuando el límite de transferencia ocurre en un múltiplo de 64 bytes (el tamaño del punto de conexión USB 1.1). En su lugar, se envía exactamente un byte extra al final de la transferencia si el tamaño es un múltiplo entero del tamaño del punto de conexión USB 1.1 (64 bytes)

.

Este comportamiento es muy probablemente una solución temporal debido al hecho de que el controlador USB esclavo del hardware en el dispositivo

no puede manejar escrituras cero en absoluto, y el uso del tamaño del punto de conexión USB 1.1 se debe al hecho de que el dispositivo camb
iará a un modo inferior en un concentrador USB 1.1, y dado que 64 bytes es un múltiplo de 512 bytes, funcionará con USB 1.1 y USB 2.0 por igual.

#define DEVICE_FLAG_NONE

0x00000000

Estos indicadores se usan para indicar si algún dispositivo u otro necesita tratamiento especial. Estos deberían poder concatenarse usando OR lógico, así que por favor use un bit por característica y oremos para no necesitar más de 32 bits.

#define DEVICE_FLAG_OGG_IS_UNKNOWN

0x00000200

El Samsung YP-T10 piensa que los archivos Ogg deben enviarse con el tipo de archivo 'desconocido' (PTP_OFC_Undefined), esto da un efecto secundario que es una combinación del problema de Alzheimer Ogg de iRiver (tener que reconocer archivos Ogg por la extensión de

l archivo) y la necesidad de informar el soporte Ogg (el dispositivo en sí no lo reclama adecuadamente) y la necesidad de establecer el tipo de archivo a desconocido al almacenar archivos Ogg, aunque en realidad no son desconocidos. Los iRivers posteriores parece
n necesitar este indicador ya que no informan que soportan OGG aunque en realidad sí lo hacen. A menudo el dispositivo soporta OGG en modo de almacenamiento masivo USB, entonces el firmware simplemente omite declarar el soporte de metadatos para OGG adecuadamente.

#define DEVICE_FLAG_ONLY_7BIT_FILENAMES

0x00000020

Este indicador indica una limitación en los nombres de archivo que un dispositivo puede aceptar - deben ser de 7 bits (todos los caracteres <= 127/

0x7F). Se encontró primero en el Philips Shoqbox, y es una desviación del estándar PTP que establece que se pueden usar cualquier carácter unico
de para los nombres de archivo. Supongo que esto es causado por un sistema de archivos de solo 7 bits que se usa intrínsecamente en el dispositivo.

identificadas por una línea en el archivo: VERSION X.XX La versión 1.00 es solo una lista de reproducción simple.

#define DEVICE_FLAG_PLAYLIST_SPL_V2

0x40000000

MTP.

#define DEVICE_FLAG_SAMSUNG_OFFSET_BUG

0x80000000

La pila MTP de los dispositivos Samsung Galaxy tiene un error misterioso en GetPartialObject. Cuando se invoca GetPartialObject para leer

los últimos bytes de un archivo y la cantidad de datos a leer es tal que el último paquete USB enviado en la respuesta coincide exa
ctamente con el tamaño del paquete USB 2.0, entonces el dispositivo Samsung Galaxy se cuelga, resultando en un error de tiempo de espera.

#define DEVICE_FLAG_UNLOAD_DRIVER

0x00000002

Esto significa que bajo Linux, otro módulo del núcleo puede estar usando la interfaz USB de este dispositivo, así que necesitamos desvincularlo si lo está. Típicamente esto es en dispositivos de doble modo que presentarán tanto una interfaz compatible con MTP y descriptor de dispositivo y una interfaz de almacenamiento masivo USB. Si la interfaz de almacenamiento masivo USB está en uso, otras aplicaciones (como nuestra libmtp de espacio de usuario a través de la ruta de acceso libusb) no pueden entrar y hacerse cómodas con ella. Así que podemos eliminar la aplicación infractora. Normalmente

esto significa que también tienes
que ejecutar el programa como root.
