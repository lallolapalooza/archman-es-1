CABECERA

HTTP

Antes de que se inicie cada función de búsqueda, una aplicación cliente puede añadir cabeceras de solicitud HTTP. Estas se restablecen después de cada función de búsqueda. debuginfod_add_http_header() puede llamarse con cadenas de la forma "Header: value". Estas cadenas son copiadas por la biblioteca. Un valor de retorno cero indica éxito, pero las condiciones de memoria insuficiente pueden resultar en un valor distinto de cero -ENOMEM. Si la cadena tiene el formato incorrecto, se devolverá

-EINVAL.

$DEBUGINFOD_HEADERS_FILE especifica un archivo para proporcionar cabeceras a las solicitudes salientes. Cada línea de este archivo que no esté en blanco se trata como si se llamara a debuginfod_add_http_header() con su

contenido.

Tenga en cuenta que la implementación actual de la biblioteca debuginfod-client usa libcurl, pero no debe depender de ese hecho. No use esta función para reemplazar ninguna cabecera estándar, excepto la User-Agent mencionada a continuación. Puede usar esta función para añadir información de autorización para el control de acceso, o para proporcionar cabeceras opcionales al servidor con fines de

registro.

Por defecto, la biblioteca añade una cabecera User-Agent: descriptiva a las solicitudes salientes. Si la aplicación cliente añade una cabecera con el mismo nombre, esta configuración predeterminada se

omite.

Durante o después de una búsqueda, una aplicación cliente puede llamar a debuginfod_get_headers() para recopilar el subconjunto de cabeceras de respuesta HTTP recibidas del servidor debuginfod actual o más reciente. Solo se conservan aquellas cabeceras con el prefijo X-DEBUGINFOD (sin distinguir mayúsculas de minúsculas). Se devuelven como una sola cadena, con cada "header: value" terminada con un \n (no \r\n co

mo en HTTP). Puede ser NULL. La cadena resultante es propiedad de la bibli
oteca y no debe ser modificada ni liberada. El llamador debe copiar la ca
dena devuelta si se necesita más allá de la liberación del objeto cliente.

D

Si hay firmas IMA disponibles de los RPM que contienen los archivos solicitados, entonces debuginfod extraerá esas firmas en cabeceras de respuesta, y debuginfod_find_*() realizará la verificación sobre los archivos. La política de validación se controla mediante etiquetas insertadas en $DEBUGINFOD_URLS. Por defecto, debuginfod_find_*() actúa en modo

ignorar.

Si se accede a través de HTTP en lugar de HTTPS, la red debe ser de confianza. La información de autenticación a través de la biblioteca interna libcurl no está habilitada actualmente, excepto para el estilo de texto plano básico http[s]://userid:password@hostname/. (El servidor debuginfod no real

iza autenticación, pero un servidor
proxy de front-end podría hacerlo.)

CACH

É

Antes de cada consulta, la biblioteca cliente debuginfod comprueba si es necesario limpiar la caché. Si es momento de limpiar, la biblioteca recorre el directorio de caché y eliminas descargados relacionados con debuginfo y directorios recién vaciados, si no se han accedido

recientemente.

Los archivos de control se encuentran directamente bajo el directorio de caché. Contienen números decimales simples para establecer parámetros de configuración relacionados con la caché. Si los archivos no existen, la biblioteca de cliente crea los archivos con los valores de parámetros predeterminados como

contenido.

Después de cada consulta, la biblioteca de cliente de debuginfod deposita los archivos recién recibidos en un directorio y archivo cuyo nombre se basa en el build-id. Una consulta fallida también se almacena en caché mediante un archivo especial. La convención de nombres utilizada para estos artefactos es deliberadamente no documen

tada.
