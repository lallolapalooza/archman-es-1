NOMBRE

Date::Manip::Changes5to6 - describe las diferencias entre 5.xx y 6.00

SINOPSIS

Date::Manip 6.00 representa una reevaluación y reescritura completa de Date::Manip. Se hizo un gran esfuerzo para asegurar que 6.00 sea casi compatible hacia atrás con 5.xx siempre que fuera posible, pero algunas funcionalidades han cambiado de maneras incompatibles hacia atrás. Otras partes han quedado obsoletas y serán eliminadas en algún momento futuro.

Este documento describe las diferencias entre la serie 5.xx y la versión 6.00. Esta página describe principalmente detalles técnicos, la mayoría de los cuales no afectan cómo se usa Date::Manip en scripts. Si desea asegurarse de que un script que se ejecutaba con 5.xx se ejecute con 6.xx, consulte el documento Date::Manip::Migration5to6.

VISIÓN GENERAL

La serie Date::Manip 5.xx sufrió de varias debilidades. Estas incluían:

Soporte deficiente de zonas horarias
El soporte de zonas horarias en 5.xx estaba roto. Determinar una zona horaria y comprender los cambios de horario de verano estaba incompleto (como mínimo) y totalmente inadecuado para realizar operaciones reales de zonas horarias.
Análisis demasiado complicado y no estructurado
Las rutinas de análisis se habían vuelto muy complicadas y excesivamente permisivas con el tiempo y necesitaban una revisión completa.
Falta de modelo OO
Date::Manip 5.xx estaba escrito como un módulo funcional, no como un módulo OO, pero el manejo de fechas se prestaría muy bien a ser OO con diferentes clases para manejar fechas, deltas y recurrencias.

El modelo OO permite almacenar mucha información con cada fecha (como información de zona horaria) que se descarta en la interfaz funcional.

Demasiado monolítico
Todo el módulo Date::Manip estaba contenido en un solo archivo enorme. Dividir el módulo haría que fuera mucho más fácil de manejar.

Date::Manip 6.00 es una reescritura completa de Date::Manip para abordar estos y otros problemas.

Las siguientes secciones abordan cómo Date::Manip 6.00 difiere de versiones anteriores y describen los cambios que podrían necesitarse en su script para actualizar de 5.xx a 6.00.

Los cambios más importantes están marcados con asteriscos.

CAMBIOS GENERALES

(*) Requiere perl 5.10.0
Consulte el documento Date::Manip::Problems para una discusión de este problema. Está en la sección QUEJAS CONOCIDAS.
(*) División en módulos más pequeños
El módulo Date::Manip se ha dividido de un módulo enorme en un gran número de módulos más pequeños y manejables. El módulo principal Date::Manip sigue presente y contiene todas las funciones de Date::Manip 5.xx (excepto que ahora llaman a funciones de todos los demás módulos para hacer el trabajo real). En general, el módulo Date::Manip de 6.00 es compatible hacia atrás.

También se han creado varios módulos nuevos. Estos pueden usarse directamente, omitiendo el módulo principal Date::Manip. Estos incluyen lo siguiente:

Date::Manip::Base contiene muchas operaciones básicas de fechas que pueden usarse para realizar tareas simples de manipulación de fechas sin todo el sobrecosto del módulo completo Date::Manip.

Date::Manip::TZ contiene operaciones de zonas horarias.

El manejo de fechas, deltas y recurrencias ahora se realiza en Date::Manip::Date, Date::Manip::Delta y Date::Manip::Recur.

Todos estos módulos son orientados a objetos y están diseñados para usarse directamente, así que si prefiere una interfaz OO sobre una interfaz funcional, use estos módulos.

(*) Datos intermedios en caché
Para mejorar el rendimiento de Date::Manip, muchos valores intermedios se almacenan en caché. Esto afecta la huella de memoria del módulo, pero tiene un gran impacto en el rendimiento del módulo.

Algunos tipos de datos dependen de las variables de configuración usadas, y estos se almacenan en caché por separado, y esta caché se limpia automáticamente cada vez que se establece una variable de configuración. Como resultado, es mejor si establece todas las variables de configuración al inicio y luego las deja completamente para obtener un uso óptimo de los datos en caché.

Un efecto secundario de todo esto es que el módulo Memoize no debe usarse junto con Date::Manip.

En la documentación de la versión 5.xx, se mencionó que el módulo Memoize podría usarse para mejorar el rendimiento en algunos casos. Este ya no es el caso. No debe usarse con Date::Manip, incluso si usa la interfaz funcional en lugar de la interfaz OO.

Seguro contra taint
Date::Manip ahora no contiene datos contaminados y debería ejecutarse sin problemas con la verificación de taint activada, siempre que no establezca métodos adicionales para determinar la zona horaria del sistema usando la función curr_zone_methods.

Idealmente, esto nunca debería ser necesario. Si es necesario, me gustaría saberlo para que pueda agregar cualquier método estándar necesario a la lista incorporada.

SOPORTE DE ZONAS HORARIAS

(*) Manejo completo de zonas horarias
El mayor problema con Date::Manip 5.xx fue su incapacidad para manejar correctamente las zonas horarias y el horario de verano. Eso ahora está corregido. La versión 6.00 incluye soporte para cada zona horaria incluida en la base de datos zoneinfo (también conocida como Olson) que incluye las definiciones de (esperemos) todas las zonas horarias usadas en el mundo.
Las zonas horarias individuales ya no se agregarán
Antes de 5.55, las zonas horarias se agregaban bajo solicitud. Desde que 6.00 ahora soporta un conjunto completo de zonas horarias estándar, ya no agregaré zonas horarias individuales (Date::Manip::TZ incluye funcionalidad para agregarlas usted mismo si son necesarias). Con Date::Manip ahora teniendo soporte completo de zonas horarias, no me interesa mantener mi propia base de datos de zonas horarias.

Sin embargo, me interesa agregar conjuntos de zonas horarias de varios "estándares".

Date::Manip 6.00 incluye zonas horarias de los siguientes estándares:

Base de datos Olson zoneinfo
todas las zonas horarias de Microsoft Windows
zonas listadas en RFC-822

Si hay estándares adicionales que incluyan zonas horarias adicionales no incluidas aquí, por favor indíquemelos para que puedan agregarse. Esto podría incluir listas publicadas de nombres de zonas horarias soportadas en algún sistema operativo que tengan nombres diferentes a la lista zoneinfo.

Abreviaturas de zonas horarias no estándar eliminadas
Algunos de los estándares individuales que se agregaron en la serie 5.xx no están incluidos en ninguno de los estándares listados arriba.

A partir de 6.00, solo se incluirán zonas horarias de estándares en la distribución (otros pueden ser agregados por usuarios usando las funciones descritas en Date::Manip::TZ para agregar alias para zonas horarias existentes).

Muchos módulos y archivos de soporte
Date::Manip ahora incluye un gran número de archivos y módulos que Se utilizan para soportar zonas horarias.

Se incluyen una serie de módulos que son generados automáticamente a partir de la base de datos zoneinfo. Los módulos Date::Manip::Zones, Date::Manip::TZ::*, y Date::Manip::Offset::* son todos generados automáticamente y no están destinados a ser usados directamente. En su lugar, el módulo Date::Manip::TZ es usado para acceder a los datos almacenados

allí.

Se incluye un módulo de zona horaria separado (Date::Manip::TZ::*) por cada zona horaria única. También hay un módulo (Date::Manip::Offset::*) por cada desfase diferente. En total, hay casi 1000 módulos. Estos se incluyen para hacer que el manejo de zonas horarias sea más eficiente. En lugar de calcular todo sobre la marcha, aquí se incluye información sobre cada zona horaria y desfase lo que acelera enormemente el manejo de zonas horarias. Estos módulos solo se cargan según sea necesario (es decir, solo los módulos relacionados con las zonas horarias específicas a las que usted hace referencia son cargados), por lo que no hay penalización de rendimiento por

tenerlos.

También se incluyen en la distribución un script (tzdata) y un módulo adicional (Date::Manip::TZdata). Estos se usan para generar automáticamente

los módulos de zona horaria, y no son de utilidad para nadie que no sea el mantenedor de Date::Manip. Se incluyen únicamente por el bien de
la completitud. Si alguien quisiera bifurcar Date::Manip, todas las herramientas necesarias para hacerlo están incluidas en la distribución.

(*) Manejo de Date_Init de las variables de

El manejo de las variables de configuración ha cambiado ligeramente.

Previamente, las variables pasadas a Date_Init anulaban los valores de los archivos de configuración. Esto ha cambiado ligeramente. Las opciones para Date_Init son ahora analizadas en el orden en que se enumeran, por lo que lo

Date_Init.

La manera correcta de anular los archivos de configuración es pasar los archivos de configuración primero, seguidos de cualquier anulación específica del script. En otras

palabras: 
Date_Init("ConfigFile=DateManip.cnf",
"DateFormat=Othe

ANÁLISIS DE FECHAS Y

OPERACIONES
(*) today, tomorrow,
yesterday
Las palabras "today", "tomorrow", y "yesterday" en 5.xx se referían a la hora actual, 24 horas en el futuro, y 24 horas en el pasado respectivamente.

A partir de 6.00, estas se tratan estrictamente como cadenas de fecha, por lo que son el día actual, el día anterior, o el día siguiente a la hora 00:

00:00.

La cadena "now" todavía

se refiere a la fecha y
hora actuales.
Formatos ISO
8601
Un par de los formatos de fecha de Date::Manip 5.xx entraban en conflicto con los formatos ISO 8601 en la especificación. Estos están documentados en la documentación de Date::Manip::Date.

Las fechas son ahora analizadas de acuerdo con la especificación (aunque se han hecho un par de extensiones, que también están documentadas en la documentación de Date::Manip::

Date).

Hay un cambio con respecto a Date::Manip 5.xx que resulta de una posible mala interpretación del estándar. En Date::Manip, hay una pequeña ambigüedad en cómo se entienden los formatos de fecha

Www-D.

La

fecha: 
1996-w0
2-3

podría ser interpretada de dos maneras diferentes. Podría ser interpretada como miércoles (día 3) de la 2ª semana de 1996, o como el 3er día de la 2ª semana de 1996 (lo cual sería martes si la semana comienza el domingo). Dado que la especificación solo trabaja con semanas que comienzan en el día 1, las dos siempre son equivalentes en la especificación, y el lenguaje de la especificación no indica claramente una interpretación sobre la

otra.

Dado que Date::Manip soporta el concepto de semanas que comienzan en días distintos al día 1 (lunes), las dos interpretaciones no son

equivalentes.

En Date::Manip 5.xx, la fecha era interpretada como miércoles de la 2ª semana, pero ahora creo que la otra interpretación (3er día de la semana) es la interpretación pretendida por la especificación. En adición, si se usa esta interpretación, es fácil obtener la otra

interpretación.

Si 1996-w02-3 significa el 3er día de la 2ª semana, entonces para obtener miércoles (día 3) de la semana, use los siguientes dos métodos de Date::

Manip::Date: 
$err   = $date->parse("1996-w02-1");
$date2 = $date->next(3,
1);

La primera llamada obtiene el 1er día de la 2ª semana, y la segunda llamada obtiene el siguiente

miércoles.

Si 1996-w02-3 es interpretado como miércoles de la 2ª semana, entonces para obtener el 3er día de la semana implica significativamente más

trabajo.

En Date::Manip 6.00, la fecha

ahora será analizada como el 3e
r día de la 2ª semana.
(*) El análisis es ahora más
rígido
La filosofía en Date::Manip 5.xx con respecto al análisis de fechas era "si hay alguna manera concebible de encontrar una fecha válida en la cadena, hazlo". Como resultado, las cadenas que no parecían que pudieran contener una fecha válida a menudo lo hacían.

Esto se manifestó de dos maneras. Primero, mucho puntuación era ignorada. Por ejemplo, la cadena "01 // 03 -. 75" era la fecha

1975-01-03.

Segundo, muchos saltos de palabra eran opcionales y a menudo era aceptable unir cadenas. Por ejemplo, el delta "in5seconds" habría

funcionado.

Con Date::Manip 6.00, el análisis ahora intenta encontrar una fecha válida en la cadena, pero usa un conjunto de formatos permitidos definido más rígidamente que debería coincidir más de cerca con cómo las fechas serían realmente expresadas en la vida real. La puntuación permitida está definida más rígidamente, y los saltos de palabra son requeridos. Por lo tanto "01/03/75" funcionará, pero "01//03/75" y "01/03-75" no lo harán. También, "in5seconds" ya no funcionará, aunque "in 5 seconds"

funcionará.

Estos cambios sirven para simplificar algunas de las expresiones regulares usadas en el análisis

de fechas, así como simplificar las rutinas de análisis. También ayudan a reconocer fechas rea
les en oposición a errores tipográficos... era demasiado fácil pasar basura y obtener una fecha.

Comportamiento de Date_PrevWorkDay Día Laborable
Anterior
El comportamiento de Date_PrevWorkDay ha cambiado ligeramente.

Se comprueba la fecha de inicio. Si $timecheck no era cero, la comprobación fallaba si la fecha no era un día laborable, o si la hora no estaba dentro del horario laboral. Si $timecheck era cero, la comprobación fallaba si la fecha no era un día laborable, pero la hora se

ignoraba.

En 5.xx, si la comprobación fallaba, y $timecheck no era cero, el día 0 se definía como el inicio del siguiente día laborable, pero si $timecheck era cero, el día 0 se definía como el día laborable anterior a la misma

hora.

En 6.xx, si la comprobación falla, y $timecheck no es cero, el comportamiento es el mismo que antes. Si $timecheck es cero, el día 0 se define como el siguiente día laborable a la misma

hora.

Así que el día 0 ahora es siempre el mismo, donde antes, el día 0 significaba dos cosas diferentes dependiendo de si $timecheck era cero

o
no.
(*) Hora
predeterminada
En Date::Manip 5.xx, las horas predeterminadas para las fechas se manejaban de manera inconsistente. En la documentación de Date::Manip::Date, si analizabas una fecha de la sección "Formatos de fecha comunes", en Date::Manip 5.xx, si no se incluía una hora, se predeterminaba a "00:00:00". Si analizabas una fecha de la sección "Formatos menos comunes", la hora predeterminada era la hora actual.

RECURRENCIA

S
El significado del campo del día cambió en algunas
recurrencias
El valor del campo del día puede referirse a varias cosas diferentes, incluyendo el número del día de la semana (Lunes=1 a Domingo=7), día del mes (1-31), día del año (1-366), etc.

En Date::Manip 5.xx, también podía referirse al n-ésimo día de la semana (es decir, 1 siendo el primer día de la semana, -1 siendo el último día de la semana). Este significado ya no se usa en

6.xx.

Por ejemplo, la

recurrencia: 
1*2:3:4:0:
0:0

se refería a la 3ª ocurrencia del 4º día de la semana en

febrero.

El significado ha cambiado para referirse a la 3ª ocurrencia del día 4 (Jueves) en febrero. Este es un tipo de recurrencia mucho más

útil.

Como resultado de este cambio, la recurrencia

relacionada: 
1*2:3:-1:
0:0:0

es inválida. Los números negativos pueden usarse pa

ra referirse al n-ésimo día de la semana, pero NO c
uando se refiere a los números de día de la semana.
El rango de recurrencia ahora es
inclusivo
Previamente, la lista de fechas implicada por la recurrencia era en o después de la fecha de inicio, pero antes de la fecha final.

Esto ha cambiado para que

las fechas puedan ser en
o antes de la fecha final.

En realidad, esta recurrencia no es práctica de calcular. Requiere una fecha base que podría implicar 1,3,5,... de junio en 1997 pero 2,4,6 de junio en

1998.

Además, la recurrencia no encaja en el molde de otras recurrencias que están a una distancia aproximada. Este tipo de recurrencia tiene un número de eventos espaciados cerca con huecos de 11 meses entre

grupos.

Ya no considero que esto sea una recurrencia válida y el soporte se ha eliminado ahora para esta

cadena.

También eliminé lo siguiente por una razón

similar: 
every 6th
Tuesday
[in 1999]

FUNCIONES DE DATE::

MANIP

El módulo Date::Manip contiene las mismas funciones que Date::Manip 5.xx tenía (aunque los módulos OO hacen todo el trabajo ahora). En general, las rutinas se comportan igual que antes con las siguientes

excepciones:
Date_Conv
TZ
Previamente, Date_ConvTZ tomaba de 1 a 4 argumentos y usaba la zona horaria local y la variable de configuración ConvTZ para rellenar los argumentos faltantes.

Ahora, la función Date_ConvTZ solo admite una llamada de 3

argumentos: 
$date = Date_ConvTZ($date,$from,
$to);

Si $from no se da, se predetermina a la zona horaria local. Si $to no se da, se predetermina a la zona horaria

local.

El cuarto argumento opcional ($errle

vel) ya no es compatible. Si hay un
error, se devuelve una cadena vacía.
DateCa
lc
En Date::Manip 5.xx, se recomendaba que pasaras argumentos
a ParseDate o ParseDateDelta. Esto no se recomienda con
6.00 ya que es mucho más inteligente para manejar los arg
umentos, y terminarás analizando la fecha/delta dos veces.
