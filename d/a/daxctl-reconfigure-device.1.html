Paquete: ndctl

DAXCTL-RECONFIGURE-DEVICE(1) Manual de daxctl DAXCTL-RECONFIGURE-DEVICE(1)

NOMBRE

daxctl-reconfigure-device - Reconfigura un dispositivo dax en un modo diferente

SINOPSIS

daxctl reconfigure-device <dax0.0> [<dax1.0>...<daxY.Z>] [<opciones>]

DESCRIPCIÓN

Reconfigura el modo operativo de un dispositivo dax. Esto se puede usar para convertir un dispositivo devdax normal al modo system-ram , el cual organiza que el rango dax se conecte en caliente al sistema como memoria normal.


Nota

Esta es una operación destructiva. Cualquier dato en el dispositivo dax será perdido.
Nota


La reconfiguración del dispositivo depende del modelo de dispositivo dax-bus. Véase

daxctl-migrate-device-model(1)
para más información. Si se está usando dax-class (a través del controlador dax_pmem_compat), la reconfiguración fallará con un error como el siguiente:

# daxctl reconfigure-device --mode=system-ram --region=0 all
libdaxctl: daxctl_dev_disable: dax3.0: error: device model is dax-class
dax3.0: disable failed: Operation not supported
error reconfiguring devices: Operation not supported
reconfigured 0 devices

daxctl-reconfigure-device nominalmente espera que pondrá en línea nuevos bloques de memoria como movibles, de modo que los datos del kernel no acaben en esta memoria. Sin embargo, hay otros agentes potenciales que pueden estar configurados para poner automáticamente en línea nueva memoria conectada en caliente a medida que aparece. Más notablemente, estos son la configuración /sys/devices/system/memory/auto_online_blocks o las reglas udev del sistema. Si algún agente compite para poner en línea secciones de memoria, daxctl comprueba si los bloques se pusieron en línea como memoria movible . Si no fue el caso, y se encuentra que los bloques de memoria están en una zona diferente, se muestra una advertencia. Si se desea que un agente diferente controle la puesta en línea de los bloques de memoria y la zona de memoria asociada, se recomienda usar la opción --no-online descrita más abajo. Esto abreviará la operación de reconfiguración del dispositivo a solo conectar en caliente la memoria, y se abstendrá de ponerla en línea.

En caso de que daxctl detecte que existe una política del kernel para poner en línea bloques automáticamente (a través de /sys/devices/system/memory/auto_online_blocks), entonces la reconfiguración a system-ram resultará en un fallo. Esto se puede anular con --force.

TEORÍA DE OPERACIÓN

El subsistema device-dax del kernel expone dispositivos de caracteres que proporcionan acceso DAX (mapeos directos sin el buffer de la caché de páginas) a una región de memoria dada. Los dispositivos se nombran /dev/daxX.Y donde X es un id de región y Y es un id de instancia dentro de esa región. Hay 2 mecanismos que provocan que aparezcan instancias de device-dax:

1. Espacio de nombres de Memoria Persistente (PMEM) configurado en modo "devdax". Véase "ndctl create-namspace --help" y CONFIG_DEV_DAX_PMEM https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/drivers/dax/Kconfig. En este caso la instancia de device-dax tiene un tamaño estático igual a su región de memoria anfitriona, la cual está limitada al rango de direcciones físicas del espacio de nombres anfitrión.
2. Memoria Soft Reserved enumerada por el firmware de la plataforma. En los sistemas EFI esto se comunica a través del atributo EFI_MEMORY_SP "Propósito Especial". Véase CONFIG_DEV_DAX_HMEM https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/drivers/dax/Kconfig. En este caso la(s) instancia(s) de device-dax asociada(s) con la región de memoria dada pueden ser redimensionadas y divididas en múltiples dispositivos.

En el caso de Soft Reservation, la expectativa para las plataformas basadas en EFI + ACPI es que además del atributo EFI_MEMORY_SP, el firmware también crea dominios de proximidad ACPI distintos para cualquier rango de direcciones que tenga características de rendimiento diferentes a la "System RAM" por defecto. Así, el SRAT definirá el dominio de proximidad, el SLIT comunica la distancia relativa a otros dominios de proximidad, y el HMAT se rellena con datos de latencia nominal de lectura/escritura y ancho de banda de lectura/escritura. Esos datos del HMAT se emiten al log del kernel en el arranque, y también se exportan a sysfs. Véase NUMAPERF https://www.kernel.org/doc/html/latest/admin-guide/mm/numaperf.html, para la representación en tiempo de ejecución de los detalles de rendimiento de CPU a nodo de memoria.

Fuera de los detalles de rendimiento NUMA enlazados arriba, el otro método para detectar la presencia de memoria "Soft Reserved" es volcar /proc/iomem y buscar rangos "Soft Reserved". Si el kernel no fue compilado con CONFIG_EFI_SOFT_RESERVE, es anterior a la introducción de CONFIG_EFI_SOFT_RESERVE (v5.5), o fue arrancado con la línea de comando efi=nosoftreserve, entonces device-dax no se adjuntará y la expectativa es que la memoria aparezca como un nodo NUMA solo de memoria. De lo contrario, la memoria aparece como una instancia de device-dax y DAXCTL(1) puede usarse para particionarla opcionalmente y devolver la memoria al kernel como "System RAM", o el dispositivo puede mapearse directamente como el backend de un asignador de memoria de espacio de usuario como LIBVMEM https://pmem.io/vmem/libvmem/.

EJEMPLOS

•Reconfigurar dax0.0 al modo system-ram, no poner en línea la memoria
# daxctl reconfigure-device --mode=system-ram --no-online dax0.0
[
  {
    "chardev":"dax0.0",
    "size":16777216000,
    "target_node":2,
    "mode":"system-ram"
  }
]
•Reconfigurar dax0.0 al modo devdax, intentar poner la memoria fuera de línea
# daxctl reconfigure-device --human --mode=devdax --force dax0.0
{
  "chardev":"dax0.0",
  "size":"15.63 GiB (16.78 GB)",
  "target_node":2,
  "mode":"devdax"
}
•Reconfigurar todos los dispositivos dax en la región 0 al modo system-ram
# daxctl reconfigure-device --mode=system-ram --region=0 all
[
  {
    "chardev":"dax0.0",
    "size":16777216000,
    "target_node":2,
    "mode":"system-ram"
  },
  {
    "chardev":"dax0.1",
    "size":16777216000,
    "target_node":3,
    "mode":"system-ram"
  }
]
•Ejecutar un proceso llamado some-service usando numactl para restringir sus nodos de CPU a 0 y 1, y las asignaciones de memoria al nodo 2 (determinado usando daxctl_dev_get_target_node() o daxctl list)
# daxctl reconfigure-device --mode=system-ram dax0.0
[
  {
    "chardev":"dax0.0",
    "size":16777216000,
    "target_node":2,
    "mode":"system-ram"
  }
]
# numactl --cpunodebind=0-1 --membind=2 -- some-service --opt1 --opt2
•Cambiar el tamaño de un dispositivo dax
# daxctl reconfigure-device dax0.1 -s 16G
reconfigured 1 device
# daxctl reconfigure-device dax0.1 -s 0
reconfigured 1 device

OPCIONES

-r, --region=

Restringe la operación a los dispositivos pertenecientes a la(s) región(es) especificada(s). Una región device-dax es un rango contiguo de memoria que aloja uno o más dispositivos /dev/daxX.Y, donde X es el id de la región y Y es el id de instancia del dispositivo.

-s, --size=

Para las regiones que soportan la creación de dispositivos dax, cambia el tamaño del dispositivo en bytes. Esta opción soporta los sufijos "k" o "K" para KiB, "m" o "M" para MiB, "g" o "G" para GiB y "t" o "T" para TiB. 
El tamaño debe ser un múltiplo de la alineación de la región.
Esta opción es mutuamente exclusiva con -m o --mode.

-a, --align

Las aplicaciones que quieran establecer mapeos de memoria dax con entradas de tabla de páginas mayores que el tamaño de página base del sistema (4K en x86) necesitan un dispositivo que esté suficientemente alineado. Por defecto es 2M. Nótese que el modo "devdax" fuerza que todos los mapeos estén alineados a este valor, es decir, fallan los intentos de mapeo no alineados. 
Esta opción es mutuamente exclusiva con -m o --mode.

-m, --mode=

Especifica el modo al que se debe reconfigurar el dispositivo(s) dax.
•"system-ram": conectar en caliente el dispositivo a la memoria del sistema.
•"devdax": cambiar al modo normal de "device dax". Esto requiere que el kernel soporte el desconectado en caliente kmem basado en memoria. Si esto no está disponible, un reinicio es la única forma de volver al devdax modo.

-N, --no-online

Por defecto, las secciones de memoria proporcionadas por los dispositivos system-ram se conectarán en línea automáticamente e inmediatamente con la online_movable política. Use esta opción para desactivar el comportamiento automático de conexión en línea.

-C, --check-config

Obtener los parámetros de reconfiguración del archivo de configuración global de daxctl. Esto se usa típicamente cuando daxctl-reconfigure-device es llamado desde un archivo de unidad de dispositivo de systemd-udevd. La reconfiguración procede solo si los parámetros de coincidencia en una reconfigure-device sección de la configuración coinciden con el dispositivo dax especificado en la línea de comando. Vea la RECONFIGURACIÓN PERSISTENTE sección para más detalles.

--no-movable

--movable es el valor por defecto. Esto puede ser anulado para conectar en línea nueva memoria de tal manera que no sea movable. Esto permite que cualquier asignación potencialmente sea servida desde esta memoria. Esto puede excluir la eliminación posterior. Con el --movable comportamiento (que es el valor por defecto), las asignaciones del kernel no considerarán esta memoria, y será reservada para uso de aplicaciones.

-f, --force

•Al convertir del modo "system-ram" a "devdax", se espera que todas las secciones de memoria sean primero desconectadas. Por defecto, daxctl no tocará la memoria en línea. Sin embargo con esta opción, intente desconectar la memoria del nodo NUMA asociado con el dispositivo dax antes de convertirlo de nuevo al modo "devdax".
•Adicionalmente, si se detecta una política del kernel para conectar en línea automáticamente los bloques, la reconfiguración a system-ram falla. Con esta opción, el fallo puede ser anulado para permitir la reconfiguración independientemente de la política del kernel. Hacer esto puede resultar en una reconfiguración exitosa, pero puede no ser posible desconectar posteriormente la memoria sin un reinicio.

-u, --human

Por defecto el comando producirá datos enteros crudos amigables para la máquina. En su lugar, con esta bandera, los números que representan el tamaño del almacenamiento se formatearán como cadenas legibles para humanos con unidades, otros campos se convierten a cadenas hexadecimales.

-v, --verbose

Emitir más mensajes de depuración

RECONFIGURACIÓN PERSISTENTE

El modo de un dispositivo daxctl no es persistente a través de los reinicios por defecto. Esto se debe a que el dispositivo en sí no contiene ningún metadatos que indiquen en qué modo fue configurado, o en el que se pretende usar. El modo por defecto para tal dispositivo en el arranque es devdax.

El administrador puede establecer una política de tal manera que ciertos dispositivos dax sean siempre reconfigurados en una configuración objetivo en cada arranque. Esto se logra a través de un archivo de configuración de daxctl.

El archivo de configuración puede tener múltiples secciones que influyen en diferentes aspectos de la operación de daxctl. La sección de interés para la reconfiguración persistente es reconfigure-device. El formato de esto es el siguiente:

[reconfigure-device <unique_subsection_name>]
nvdimm.uuid = <NVDIMM namespace uuid>
mode = <desired reconfiguration mode> (default: system-ram)
online = <true|false> (default: true)
movable = <true|false> (default: true)

Aquí hay un ejemplo de un fragmento de configuración para gestionar tres espacios de nombres devdax, uno se deja en modo devdax, el segundo se cambia a modo system-ram con opciones por defecto (online, movable), y el tercero se establece en modo system-ram, la memoria se conecta en línea, pero no es movable.

Note que el nombre de la subsección puede ser arbitrario, y solo se usa para identificar una sección de configuración específica. No tiene que coincidir con el dispositivo nombre (por ejemplo dax0.0 etc).

[reconfigure-device dax0]
nvdimm.uuid = ed93e918-e165-49d8-921d-383d7b9660c5
mode = devdax
[reconfigure-device dax1]
nvdimm.uuid = f36d02ff-1d9f-4fb9-a5b9-8ceb10a00fe3
mode = system-ram
[reconfigure-device dax2]
nvdimm.uuid = f36d02ff-1d9f-4fb9-a5b9-8ceb10a00fe3
mode = system-ram
online = true
movable = false

El siguiente ejemplo puede usarse para crear un espacio de nombres en modo devdax, y simultáneamente añadir el espacio de nombres recién creado al archivo de configuración para la conversión a system-ram.

ndctl create-namespace --mode=devdax | \
        jq -r "\"[reconfigure-device $(uuidgen)]\", \"nvdimm.uuid = \(.uuid)\", \"mode = system-ram\"" >> $config_path

La ubicación por defecto para los archivos de configuración de daxctl está bajo /etc/daxctl.conf.d/, y cualquier archivo con un .conf sufijo en esta ubicación es considerado. Es aceptable tener múltiples archivos que contengan secciones de configuración estilo ini, pero el par {sección, subsección} debe ser único en todos los archivos de configuración bajo /etc/daxctl.conf.d/.
