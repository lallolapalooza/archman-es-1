DBD::SQLite::Fulltext_search

- Uso de búsquedas de texto
completo con DBD::SQLite

DESCRIPCIÓ

N

Introducció

n

SQLite incluye un módulo de extensión llamado "FTS" para la indexación de texto completo. Las tablas con esta función habilitada pueden consultarse eficientemente para encontrar filas que contengan una o más instancias de algunas palabras específicas (también llamadas "tokens"), en cualquier columna, incluso si la tabla contiene muchos documentos

grandes.

Los primeros módulos de búsqueda de texto completo para SQLite se llamaron "FTS1" y "FTS2" y ahora están obsoletos. La última versión es "FTS4", pero comparte muchas características con el módulo anterior "FTS3", por lo que partes de la API y partes de la documentación todavía se refieren a "FTS3"; desde el punto de vista del cliente, ambos pueden considerarse en gran medida equivalentes. Se puede encontrar documentación detallada en http://www.sqlit

e.org/ft
s3.html.

Ejemplo

corto

Aquí hay un ejemplo muy corto de uso de

FTS: 
$dbh->do(<<"") or die DBI::errstr;
CREATE VIRTUAL TABLE fts_example USING fts4(content)

my $sth = $dbh->prepare("INSERT INTO fts_example(content) VALUES (?)");
$sth->execute($_) foreach @docs_to_insert;

my $results = $dbh->selectall_arrayref(<<"");
SELECT docid, snippet(fts_example) FROM fts_example WHERE content MATCH
'foo'

Los puntos clave en este ejemplo

son:
  • La sintaxis para crear tablas FTS es 
    CREATE VIRTUAL TABLE <table_name> USING fts4(<columns>
    )

    donde "<columns>" es una lista de nombres de columnas. Las columnas pueden tener tipo, pero la información de tipo se ignora. Si no se especifican columnas, el valor predeterminado es una única columna llamada "content". Además, las tablas FTS tienen una columna implícita llamada "docid" (o también "rowid") para numerar lo

    s documentos
    • almacenados.
  • Las sentencias para insertar, actualizar o eliminar registros usan la misma sintaxis que para las tablas SQLite
    • regulares.
  • Las búsquedas de texto completo se especifican con el operador "MATCH", y un operando que puede ser una sola palabra, un prefijo de palabra que termina con '*', una lista de palabras, una "consulta de frase" entre comillas dobles, o una combinación booleana de lo
    • anterior.
  • La función incorporada snippet(...) construye un extracto formateado del texto del docu
    • mento, donde las palabras pertinen
tes a la consulta están resaltadas.

Hay muchos más detalles sobre la construcción y búsqueda de tablas FTS, por lo que le invitamos encarecidamente a leer la documentación completa en http://www.sq

lite.o
rg/fts3
.html.

SINTAXIS DE

CONSULTA

Aquí hay algunas explicaciones sobre las consultas FTS, tomadas de la documentación de

sqlite.

Consultas de token o prefijo de

token

Se puede consultar una tabla FTS para todos los documentos que contengan un término específico, o para todos los documentos que contengan un término con un prefijo específico. La expresión de consulta para un término específico es simplemente el término mismo. La expresión de consulta utilizada para buscar un prefijo de término es el prefijo mismo con un carácter '*' añadido. Por

ejemplo: 
-- Declaración de tabla virtual
CREATE VIRTUAL TABLE docs USING fts3(title, body);

-- Consulta para todos los documentos que contienen el término "linux":
SELECT * FROM docs WHERE docs MATCH 'linux';

-- Consulta para todos los documentos que contienen un término con el prefijo "lin".
SELECT * FROM docs WHERE docs MATCH
'lin*';

Si un token de búsqueda (en el lado derecho del operador MATCH) comienza con "^", entonces ese token debe ser el primero en su campo del documento: así que por ejemplo "^lin*" coincide con 'linux kernel changes ...' pero no coincide con 'new linux

implementation'
.

Especificaciones de

columna

Normalmente, una consulta de token o prefijo de token se compara con la columna de la tabla FTS especificada como el lado derecho del operador MATCH. O, si se especifica la columna especial con el mismo nombre que la tabla FTS misma, con todas las columnas. Esto puede ser anulado especificando un nombre de columna seguido de un carácter ":" antes de una consulta de término básico. Puede haber espacio entre el ":" y el término a consultar, pero no entre el nombre de la columna y el carácter ":". Por

ejemplo: 
-- Consultar la base de datos por documentos para los cuales el término "linux" aparece en
-- el título del documento, y el término "problems" aparece en el título
-- o el cuerpo del documento.
SELECT *
FROM docs WHERE docs MATCH 'title:linux problems'; -- Consultar la base de datos por documentos para los cuales el término "linux" aparece en -- el título del documento, y el término "driver" aparece e
n el cuerpo del documento -- ("driver" también puede aparecer en el título, pero esto por sí solo no satisfará los -- criterios de la consulta). SELECT * FROM docs WHERE body MATCH 'title:linux driver';

Consultas de

frase

Una consulta de frase es una consulta que recupera todos los documentos que contienen un conjunto nominado de términos o prefijos de términos en un orden específico sin tokens intermedios. Las consultas de frase se especifican encerrando una secuencia de términos o prefijos de términos separados por espacios entre comillas dobles ("). Por

ejemplo: 
-- Consulta para todos los documentos que contienen la frase "linux applications".
SELECT * FROM docs WHERE docs MATCH '"linux applicat
ions"'; -- Consulta para todos los documentos que contienen una frase que coincida con "lin* app*". -- Además de "linux applications", e
sto coincidirá con frases comunes como -- "linoleum appliances" o "link apprentice". SELECT * FROM docs WHERE docs MATCH '"lin* app*"';

Consultas

NEAR.

Una consulta NEAR es una consulta que devuelve documentos que contienen dos o más términos o frases nominados dentro de una proximidad específica entre sí (por defecto con 10 o menos términos intermedios). Una consulta NEAR se especifica poniendo la palabra clave "NEAR" entre dos consultas de frase, término o prefijo. Para especificar una proximidad diferente a la predeterminada, se puede usar un operador de la forma "NEAR/<N>", donde <N> es el número máximo de términos intermedios permitidos. Por

ejemplo: 
-- Declaración de tabla virtual.
CREATE VIRTUAL TABLE docs USING fts4();
-- Datos de tabla virtual.
INSERT INTO docs VALUES('SQLite is an ACID compliant embedded relational database management system');
-- Buscar un documento que contenga los términos "sqlite" y "database" con
-- no más de 10 términos intermedios. Esto coincide con el único documento en la
-- tabla docs (ya que solo hay seis términos entre "SQLite" y "database"
-- en el documento).
SELECT * FROM docs WHERE docs MATCH 'sqlite NEAR database';
-- Buscar un documento que contenga los términos "sqlite" y "database" con
-- no más de 6 términos intermedios. Esto también coincide con el único documento en la
-- tabla docs. Note que el orden en el que los términos aparecen en el documento
-- no tiene que ser el mismo que el orden en el que aparecen en la consulta.
SELECT * FROM docs WHERE docs MATCH 'database NEAR/6 sqlite';
-- Buscar un documento que contenga los términos "sqlite" y "database" con
-- no más de 5 términos intermedios. Esta consulta no coincide con ningún documento.
SELECT * FROM docs WHERE docs MATCH 'database NEAR/5 sqlite';
-- Buscar un documento que contenga la frase "ACID compliant" y el término
-- "database" con no más de 2 términos separando los dos. Esto coincide con el
-- documento almacenado en la tabla docs.
SELECT * FROM docs WHERE docs MATCH 'database NEAR/2 "ACID compliant"';
-- Buscar un documento que contenga la frase "ACID compliant" y el término
-- "sqlite" con no más de 2 términos separando los dos. Esto también coincide
-- con el único documento almacenado en la tabla docs.
SELECT * FROM docs WHERE docs MATCH '"ACID compliant" NEAR/2
sqlite';

Puede haber más de un operador NEARaparecer en una sola consulta. En este caso, cada par de términos o frases separados por un operador NEAR debe aparecer dentro de la proximidad especificada entre sí en el documento. Usando la misma tabla y datos que en el bloque de ejemplos

anterior: 
-- La siguiente consulta selecciona documentos que contienen una instancia del término
-- "sqlite" separada por dos o menos términos de una instancia del término "acid",
-- que a su vez está separada por dos o menos términos de una instancia del término
-- "relational".
SELECT * FROM docs WHERE docs MATCH 'sqlite NEAR/2 acid NEAR/2 relational';
-- Esta consulta no coincide con ningún documento. Hay una instancia del término "sqlite" con
-- proximidad suficiente a una instancia de "acid" pero no está lo suficientemente cerca
-- de una instancia del término "relational".
SELECT * FROM docs WHERE docs MATCH 'acid NEAR/2 sqlite NEAR/2
relational';

Las consultas de frase y NEAR

no pueden abarcar múltiples co
lumnas dentro de una fila.

Operaciones de

conjunto

Los tres tipos básicos de consulta descritos anteriormente pueden usarse para consultar el índice de texto completo para el conjunto de documentos que coinciden con los criterios especificados. Usando el lenguaje de expresiones de consulta FTS, es posible realizar varias operaciones de conjunto sobre los resultados de consultas básicas. Actualmente hay tres operaciones

soportadas:
  • El operador AND determina la intersección de dos conjuntos de
    • documentos.
  • El operador OR calcula la unión de dos conjuntos de
    • documentos.
  • El operador NOT puede usarse para calcula
    • r el complemento relativo de un conjunto
de documentos con respecto a otro.

Los operadores de conjunto binarios AND, OR y NOT deben escribirse usando letras mayúsculas; de lo contrario, se interpretan como consultas de término básicas en lugar de operadores de conjunto. Cada uno de los dos operandos de un operador puede ser una consulta FTS básica, o el resultado de otra operación de conjunto AND, OR o NOT. Se pueden usar paréntesis para controlar la precedencia y el

agrupamiento.

El operador AND es implícito para consultas básicas adyacentes sin ningún operador explícito. Por ejemplo, la expresión de consulta "implicit operator" es una versión más concisa de "implicit AND

operator".

Las operaciones booleanas recién descritas corresponden a la llamada "sintaxis de consulta mejorada" de sqlite; esta es la versión compilada con "DBD::SQLite", a partir de la versión 1.31. Una versión anterior, llamada "sintaxis de consulta estándar", usaba soportar tokens con prefijo

s '+' o '-' (para inclusión o exclusión de tokens); si su aplicación n
ecesita soportar esta sintaxis antigua, use DBD::SQLite::FTS3Transitio
nal (publicado en una distribución separada) para hacer la conversión.

TOKENIZADORE

S

Concept

o

El comportamiento de los índices de texto completo depende fuertemente de cómo se dividen los documentos en tokens; por lo tanto, las declaraciones de tablas FTS pueden especificar explícitamente cómo realizar la

tokenización: 
CREATE ... USING fts4(<columns>, tokenize=<tokenizer>
)

donde "<tokenizer>" es una secuencia de palabras separadas por espacios que activa un tokenizador específico. Los tokeniz

adores pueden ser incorporados de SQLite, escritos en código
C, o tokenizadores Perl. Ambos se explican a continuación.

Tokenizadores incorporados de

SQLite

SQLite viene con algunos tokenizadores incorporados (ver http://www.sqlite.org/fts3.html#tokenizer)

:
simp
le
Bajo el tokenizador simple, un término es una secuencia contigua de caracteres elegibles, donde los caracteres elegibles son todos los caracteres alfanuméricos, el carácter "_", y todos los caracteres con codepoints UTF mayores o iguales a 128. Todos los demás caracteres se descartan al dividir un documento en términos. Solo sirven para separar términos adyacentes.

Todos los caracteres en mayúsculas dentro del rango ASCII (codepoints UTF menores a 128), se tran

sforman a sus equivalentes en minúsculas como parte del proceso de tokenización. Así, las consul
tas de texto completo no distinguen mayúsculas de minúsculas cuando se usa el tokenizador simple.
port
er
El tokenizador porter usa las mismas reglas para separar el documento de entrada en términos, pero además de convertir todos los términos a minúsculas, usa el algoritmo de stemming de Porter para reducir palabras relacionadas en inglés a una raíz
común.
ic
u
El tokenizador icu usa la biblioteca ICU para decidir cómo identificar caracteres de palabra en diferentes idiomas; sin embargo, esto requiere que SQLite esté compilado con el símbolo de preprocesador "SQLITE_ENABLE_ICU" definido. Así, para usar este tokenizador, necesita editar Makefile.PL para agregar esta bandera en @CC_DEFINE, y luego recompilar "DBD::SQLite"; por supuesto, el prerrequisito es tener una biblioteca ICU disponible en su
sistema.
unicode
61
El tokenizador unicode61 funciona muy similar a "simple" excepto que hace plegado de mayúsculas unicode completo según las reglas en Unicode Versión 6.1 y reconoce caracteres de espacio y puntuación unicode y usa esos para separar tokens. En contraste, el tokenizador simple solo hace plegado de mayúsculas de caracteres ASCII y solo reconoce caracteres de espacio y puntuación ASCII como separadores de tokens.

Por defecto, "unicode61" también elimina todos los diacríticos de los caracteres de escritura latina. Este comportamiento se puede anular agregando el argumento del tokenizador "remove_diacritics=0". Por

ejemplo: 
-- Crea tablas que eliminan diacríticos de los caracteres de escritura latina
-- como parte de la tokenización.
CREATE VIRTUAL TABLE txt1 USING fts4(tokenize=unicode61);
CREATE VIRTUAL TABLE txt2 USING fts4(tokenize=unicode61 "remove_diacritics=1");
-- Crea una tabla que no elimina diacríticos de los caracteres de escritura
-- latina como parte de la tokenización.
CREATE VIRTUAL TABLE txt3 USING fts4(tokenize=unicode61 "remove_diacritics=0")
;

Opciones adicionales pueden personalizar el conjunto de codepoints que unicode61 trata como caracteres separadores o como caracteres de token -- ver la documentación en http://www.sqlite

.org/fts
3.html#un
icode61.

Si se requiere un algoritmo de tokenización más complejo, por ejemplo para impl

ementar stemming, descartar puntuación, o reconocer palabras compuestas, use el
tokenizador perl para implementar su propia lógica, como se explica a continuación.

Tokenizadores

Perl

Declarando un tokenizador

perl

Además de los tokenizadores incorporados de SQLite, "DBD::SQLite" implementa un tokenizador perl, que puede engancharse a cualquier algoritmo de tokenización escrito en Perl. Esto se especifica de la siguiente manera

: 
CREATE ... USING fts4(<columns>, tokenize=perl '<perl_function>
')

donde "<perl_function>" es un nombre de función Perl completamente calificado (es decir, con prefijo del nombre del paquete en el que esa función está declarada). Así que por ejemplo si la función es "my_func" en el programa principal,

escriba 
CREATE ... USING fts4(<columns>, tokenize=perl 'main::
my_func')

Escribiendo un tokenizador perl a

mano

Esa función debe devolver una referencia de código que tome una cadena como único argumento, y devuelva un iterador (otra función), que devuelva una tupla "($term, $len, $start, $end, $index)" para cada término. Aquí hay un ejemplo simple que tokeniza en palabras según la configuración regional actual de

perl 
sub locale_tokenizer {
  return sub {
    my $string = shift;
    use locale;
    my $regex      = qr/\w+/;
    my $term_index = 0;
    return sub { # closure
      $string =~ /$regex/g or return; # either match, or no more token
      my ($start, $end) = ($-[0], $+[0]);
      my $len           = $end-$start;
      my $term          = substr($string, $start, $len);
      return ($term, $len, $start, $end, $term_index++);
    }
  };
}

Debe haber tres niveles de subs, en una especie de estructura de "muñecas rusas", porque

:
  • el sub externo, con nombre, se llama cada vez que se accede a una tabla FTS con ese
    • tokenizador
  • el sub interno, anónimo, se llama cada vez que se necesita tokenizar una nueva cadena (ya sea para insertar nuevo texto en la tabla, o para analizar una consulta)
    • .
  • el sub más interno, anónimo, se llama
    • repetidamente para recuperar todos lo
s términos dentro de esa cadena.

Usando Search::

Tokenizer

En lugar de escribir tokenizadores a mano, puede tomar uno de los ya implementados en el módulo Search::Tokenizer. Por ejemplo, si quiere ignorar diferencias entre caracteres acentuados, puede escribir

: 
use Search::Tokenizer;
$dbh->do(<<"") or die DBI::errstr;
CREATE ... USING fts4(<columns>, 
                      tokenize=perl 'Search::Tokenizer::
unaccent')

Alternativamente, puede usar "new" en Search::Tokenizer para construir su propio tokenizador. Aquí hay un ejemplo que trata palabras compuestas (palabras con un guion o punto interno) como tokens únicos

: 
sub my_tokenizer {
  return Search::Tokenizer->new(
    regex => qr{\p{Word}+(?:[-./]\p{Word}+)*},
   )
;
}

Fts4aux - Acceso directo al índice de texto

completo

El contenido de un índice de texto completo se puede acceder a través del módulo de tabla virtual "fts4aux". Por ejemplo, asumiendo que nuestra base de datos contiene una tabla con índice de texto completo llamada "ft", podemos declarar

: 
CREATE VIRTUAL TABLE ft_terms USING
fts4aux(ft)

y luego consultar la tabla "ft_terms" para acceder a la lista de términos, su frecuencia, etc. Los ejemplos están documentados en http://www.sqlite.or

g/fts3.htm
l#fts4aux.

Cómo ahorrar espacio en la base de

datos

Por defecto, FTS almacena una copia completa de los documentos indexados, junto con el índice de texto completo. En una colección grande de documentos, esto puede consumir bastante espacio en disco. Sin embargoer, FTS tiene algunas opciones para comprimir los documentos, o incluso para no almacenarlos en absoluto -- ver http://www.sqlite.org/fts3.html#fts4_options

.

En particular, la opción para tablas FTS sin contenido solo almacena el índice de texto completo, sin el contenido del documento original. Esto se especifica como "content=""", como en el siguiente

ejemplo: 
CREATE VIRTUAL TABLE t1 USING fts4(content="", a,
b)

Se pueden insertar datos en una tabla FTS4 de este tipo utilizando sentencias INSERT. Sin embargo, a diferencia de las tablas FTS4 ordinarias, el usuario debe proporcionar un valor docid entero explícito. Por

ejemplo: 
-- Esta sentencia está bien:
INSERT INTO t1(docid, a, b) VALUES(1, 'a b c', 'd e f');
-- Esta sentencia causa un error, ya que no se ha proporcionado un valor docid:
INSERT INTO t1(a, b) VALUES('j k l', 'm n o')
;

Por supuesto, su aplicación necesitará un algoritmo para encontrar el recurso externo correspondiente a cualquier docid almacenado dentro de

SQLite.

Al usar marcadores de posición, el docid debe ser de tipo explícito INTEGER, porque esta es una "columna oculta" para la cual sqlite no es capaz de inferir automáticamente el tipo correcto. Así que lo siguiente no

funciona: 
my $sth = $dbh->prepare("INSERT INTO t1(docid, a, b) VALUES(?, ?, ?)");
$sth->execute(2, 'aa', 'bb'); # error de
restricción

pero funciona con una conversión de tipo

explícita: 
my $sql = "INSERT INTO t1(docid, a, b) VALUES(CAST(? AS INTEGER), ?, ?)",
my $sth = $dbh->prepare(sql);
$sth->execute(2, 'aa', 'bb')
;

o con un "bind_param" de tipo explícito en

DBI: 
use DBI qw/SQL_INTEGER/;
my $sql = "INSERT INTO t1(docid, a, b) VALUES(?, ?, ?)";
my $sth = $dbh->prepare(sql);
$sth->bind_param(1, 2, SQL_INTEGER);
$sth->bind_param(2, "aa");
$sth->bind_param(3, "bb");
$sth->execute()
;

No es posible hacer UPDATE o DELETE de una fila almacenada en una tabla FTS4 sin contenido. Intentar hacerlo es un

error.

Las tablas FTS4 sin contenido también admiten sentencias SELECT. Sin embargo, es un error intentar recuperar el valor de cualquier columna de la tabla que no sea la columna docid. La función auxiliar matchinfo() puede usarse, pero snippet() y offsets() no pueden, así que si se necesita tal funcionalida

d, debe ser programada directamen
te dentro de la aplicación Perl.
