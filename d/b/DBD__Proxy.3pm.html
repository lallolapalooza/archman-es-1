DBD::Proxy(3) Documentación de Perl aportada por el usuario DBD::Proxy(3)

NOMBRE

DBD::Proxy - Un controlador proxy para el DBI

SINOPSIS

use DBI;
$dbh = DBI->connect("dbi:Proxy:hostname=$host;port=$port;dsn=$db",
                    $user, $passwd);
# Consulte la documentación del módulo DBI para obtener todos los detalles

DESCRIPCIÓN

DBD::Proxy es un módulo de Perl para conectarse a una base de datos a través de un controlador DBI remoto. Consulte DBD::Gofer para una alternativa con diferentes compensaciones.

Esto, por supuesto, no es necesario para los controladores DBI que ya admiten la conexión a una base de datos remota, pero hay motores que no ofrecen conectividad de red.

Otra aplicación es ofrecer acceso a la base de datos a través de un firewall, ya que el controlador ofrece restricciones basadas en consultas. Por ejemplo, puede restringir las consultas exactamente a aquellas que se utilizan en una aplicación CGI determinada.

Hablando de CGI, otra aplicación es (o más bien, será) reducir la sobrecarga de conexión/desconexión de la base de datos desde los scripts CGI utilizando el proxying del método connect_cached. El servidor proxy mantendrá las conexiones de la base de datos abiertas en una caché. El script CGI entonces intercambia la sobrecarga de conexión/desconexión de la base de datos por la sobrecarga de conexión/desconexión de DBD::Proxy, que normalmente es mucho menor.

CONEXIÓN A LA BASE DE DATOS

Antes de conectarse a una base de datos remota, debe asegurarse de que un servidor Proxy esté ejecutándose en la máquina remota. No hay un puerto predeterminado, por lo que tiene que preguntar a su administrador de sistemas por el número de puerto. Consulte DBI::ProxyServer para más detalles.

Supongamos que su servidor Proxy se está ejecutando en la máquina "alpha", puerto 3334, y desea conectarse a una base de datos ODBC llamada "mydb" como usuario "joe" con la contraseña "hello". Cuando usa DBD::ODBC directamente, haría

$dbh = DBI->connect("DBI:ODBC:mydb", "joe", "hello");

Con DBD::Proxy esto se convierte en

$dsn = "DBI:Proxy:hostname=alpha;port=3334;dsn=DBI:ODBC:mydb";
$dbh = DBI->connect($dsn, "joe", "hello");

Como puede ver, es principalmente lo mismo. El módulo DBD::Proxy creará una conexión al servidor Proxy en "alpha" que a su vez se conectará a la base de datos ODBC.

Consulte la documentación de DBI sobre el método "connect" para una forma de usar DBD::Proxy automáticamente sin tener que cambiar su código.

La cadena DSN de DBD::Proxy tiene el formato

$dsn = "DBI:Proxy:key1=val1; ... ;keyN=valN;dsn=valDSN";

En otras palabras, es una colección de pares clave/valor. Las siguientes claves son reconocidas:

hostname
port
Nombre de host y puerto del servidor Proxy; estas claves deben estar presentes, no hay valores predeterminados. Ejemplo: 
hostname=alpha;port=3334
dsn
El valor de este atributo será utilizado como nombre dsn por el servidor Proxy. Por lo tanto, debe tener el formato "DBI:driver:...", en particular contendrá dos puntos. El valor dsn puede contener punto y coma, por lo que esta clave *debe* ser la última y su valor será la parte restante completa del dsn. Ejemplo: 
dsn=DBI:ODBC:mydb
cipher
key
usercipher
userkey
Usando estos campos puede habilitar el cifrado. Si establece, por ejemplo, 
cipher=$class;key=$key

(note el punto y coma) entonces DBD::Proxy creará un nuevo objeto cipher ejecutando

$cipherRef = $class->new(pack("H*", $key));

y pasará este objeto al módulo RPC::PlClient al crear un cliente. Consulte RPC::PlClient. Ejemplo:

cipher=IDEA;key=97cd2375efa329aceef2098babdc9721

Los atributos usercipher/userkey le permiten usar cifrado de dos fases: El cifrado clave/cipher se usará en la fase de inicio de sesión y autorización. Una vez que el cliente esté autorizado, cambiará al cifrado usercipher/userkey. Así que el par cipher/key es un secreto basado en el host , típicamente menos seguro que el secreto usercipher/userkey y legible por cualquiera. El secreto usercipher/userkey es su secreto privado.

Por supuesto, el cifrado requiere un servidor configurado adecuadamente. Consulte "ARCHIVO DE CONFIGURACIÓN" en DBD::ProxyServer.

debug
Activa el modo de depuración
stderr
Este atributo establecerá el atributo correspondiente del objeto RPC::PlClient, por lo que el registro no usará syslog(), sino que se redirigirá a stderr. Este es el valor predeterminado bajo Windows. 
stderr=1
logfile
Similar al atributo stderr, pero la salida se redirigirá al archivo dado. 
logfile=/dev/null
RowCacheSize
El controlador DBD::Proxy admite este atributo (que es estándar de DBI, a partir de DBI 1.02). Se usa para reducir los viajes de ida y vuelta de la red al obtener múltiples filas de una vez. El valor predeterminado actual es 20, pero esto puede cambiar.
proxy_no_finish
Este atributo se puede usar para reducir el tráfico de red: Si la aplicación está llamando a $sth->finish() entonces el proxy le dice al servidor que finalice el manejador de sentencia remoto. Por supuesto, esto ralentiza las cosas bastante, pero es perfectamente bueno para reducir el uso de memoria con conexiones persistentes.

Sin embargo, si establece el atributo proxy_no_finish a un valor VERDADERO, ya sea en el manejador de la base de datos o en el manejador de la sentencia, entonces las llamadas a finish() serán suprimidas. Esto es lo que desea, por ejemplo, en aplicaciones CGI pequeñas y rápidas.

proxy_quote
Este atributo se puede usar para reducir el tráfico de red: Por defecto, las llamadas a $dbh->quote() se pasan al controlador remoto. Por supuesto, esto ralentiza las cosas bastante, pero es el comportamiento predeterminado más seguro.

Sin embargo, si establece el atributo proxy_quote al valor '"local"' ya sea en el manejador de la base de datos o en el manejador de la sentencia, y la llamada a quote tiene solo un parámetro, se usará el método quote predeterminado de DBI local (que será más rápido pero puede ser incorrecto).

PROBLEMAS CONOCIDOS

Llamadas a métodos no proxificados

Si un método no está siendo proxificado, intente declarar un sub stub en el paquete apropiado (DBD::Proxy::db para un método dbh, y DBD::Proxy::st para un método sth). Por ejemplo:

sub DBD::Proxy::db::selectall_arrayref;

Eso permitirá que selectall_arrayref sea proxificado.

Actualmente, muchos métodos no están explícitamente proxificados y por lo tanto obtiene los métodos predeterminados de DBI ejecutados en el cliente.

Algunos de esos métodos, como selectall_arrayref, pueden entonces llamar a otros métodos que están proxificados (selectall_arrayref llama a fetchall_arrayref que llama a fetch que está proxificado). Así que las cosas pueden parecer funcionar pero operar más lentamente de lo que podrían.

Todo esto puede cambiar en una versión posterior.

Atributos complejos del manejador

A veces los manejadores tienen atributos complejos como referencias a hashes o referencias a arreglos y no cadenas o enteros simples. Por ejemplo, con DBD::CSV, le gustaría escribir algo como

$dbh->{"csv_tables"}->{"passwd"} =
      { "sep_char" => ":", "eol" => "\n";

El ejemplo anterior le indicaría al controlador CSV que asuma que el archivo "passwd" está en el formato del archivo /etc/passwd: Dos puntos como separadores y un salto de línea sin retorno de carro como terminador de línea.

Sorprendentemente, este ejemploe no funciona con el controlador proxy. Para entender las razones, debes considerar lo siguiente: El compilador de Perl está ejecutando el ejemplo anterior en dos pasos:

1.
El primer paso es obtener el valor de la clave "csv_tables" en el controlador $dbh. El valor devuelto es complejo, una referencia a un hash.
2.
El segundo paso es almacenar algún valor (el lado derecho de la asignación) como la clave "passwd" en la referencia a hash del paso 1.

Esto se vuelve un poco más claro si reescribimos el código anterior:

$tables = $dbh->{"csv_tables"};
$tables->{"passwd"} = { "sep_char" => ":", "eol" => "\n";

Mientras que los ejemplos funcionan bien sin el proxy, fallan debido a una sutil diferencia en el paso 1: Por la magia de DBI, la referencia a hash $dbh->{'csv_tables'} es devuelta del servidor al cliente. El cliente crea una copia local. Esta copia local es el resultado del paso 1. En otras palabras, el paso 2 modifica una copia local de la referencia a hash, pero no la referencia a hash del servidor.

La solución alternativa es almacenar la copia local modificada de vuelta en el servidor:

$tables = $dbh->{"csv_tables"};
$tables->{"passwd"} = { "sep_char" => ":", "eol" => "\n";
$dbh->{"csv_tables"} = $tables;

ADVERTENCIA DE SEGURIDAD

RPC::PlClient utilizado subyacentemente no es seguro debido a la serialización y deserialización de datos con el módulo Storable. Utiliza el controlador proxy solo en entornos de confianza.
