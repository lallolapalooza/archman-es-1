DESCRIPCIÓ

N

DBI::DBD::SqlEngine abstrae el uso de motores SQL del DBD. Los autores de DBD pueden concentrarse en la recuperación de datos que desean

proporcionar.

Se recomienda encarecidamente que lea DBD::File::Developers y DBD::File::Roadmap, ya que gran parte de la API de DBD::File es proporcionada por DBI::DBD::

SqlEngine.

Actualmente la API de DBI::DBD::SqlEngine es experimental y probablemente cambiará en un futuro próximo para proporcionar los fundamentos de metadatos de tablas como DBD::

File.

DBI::DBD::SqlEngine espera que cualquier controlador en la cadena de herencia tenga un prefijo

DBI.

Además de los atributos DBI, puede usar los siguientes atributos de

sql_engine_versio

n

sql_handle

r

Contiene el motor de sentencias SQL, ya sea DBI::SQL::Nano o SQL::Statement (solo lect

ura).

sql_parser_objec

t

Contiene una instancia instanciada de SQL::Parser (solo lectura). Esto se rellena cuando se usa por primera vez (solo cuando se usa con SQL::Statement)

.

sql_sponge_drive

r

Contiene un manejador de DBD::Sponge usado internamente (solo lect

ura).

sql_valid_attr

s

Contiene la lista de atributos válidos para cada controlador basado en DBI::DBD::SqlEngine (solo lect

ura).

sql_readonly_attr

s

Contiene la lista de aquellos atributos que son de solo lectura (solo lect

ura).

sql_identifier_cas

e

Contiene cómo DBI::DBD::SqlEngine trata los identificadores SQL no entrecomillados

: 
* SQL_IC_UPPER (1) significa que todos los identificadores se convierten internamente en sus equivalentes en mayúsculas
* SQL_IC_LOWER (2) significa que todos los identificadores se convierten internamente en sus equivalentes en minúsculas
* SQL_IC_MIXED (4) significa que todos los identificadores se toman tal como
están

Estas conversiones ocurren si (y solo si) ningún identificador existente coincide. Una vez que existe un identificador, se usa tal como se

conoce.

Las clases de ejecución de sentencias SQL no tienen que preocuparse, así que no espere que "sql_identifier_case" afecte a los nombres de columna en sentencias

como 
SELECT * FROM
foo

sql_quoted_identifier_cas

e

Contiene cómo DBI::DBD::SqlEngine trata los identificadores SQL entrecomillados (solo lectura). Está fijado a SQL_IC_SENSITIVE (3), que se interpreta como

SQL_IC_MIXED.

sql_flag

s

Contiene banderas adicionales para instanciar un SQL::Parser. Debido a que un SQL::Parser solo se instancia una vez, se recomienda establecer esta bandera antes de que se ejecute cualquier

sentencia.

sql_dialec

t

Controla el dialecto entendido por SQL::Parser. Valores posibles (estado de entrega de SQL::Statement)

: 
* ANSI
* CSV
*
AnyData

Por defecto es "CSV". Debido a que un SQL::Parser solo se instancia una vez y SQL::Parser no permite modificar el dialecto una vez instanciado, se recomienda encarecidamente establecer esta bandera antes de que se ejecute cualquier sentencia (el mejor lugar es el hash de atributos de conexión)

.

sql_engine_in_gofe

r

Este valor tiene un valor verdadero en caso de que este controlador sea operado a través de DBD::Gofer. El impacto de ser operado a través de Gofer es un controlador de solo lectura (¡no bases de datos de solo lectura!), por lo que no puede modificar ningún atributo después - ni ninguna configuración de tabla. Pero no obtendrá un error en los casos en que modifique atributos de tabla, así que por favor observe cuidadosamente "sql_engine_in_gofer"

.

sql_met

a

Área de datos privada que contiene información sobre las tablas que este módulo maneja. Los metadatos de la tabla pueden no estar disponibles hasta que la tabla haya sido accedida por primera vez, por ejemplo, emitiendo un SELECT sobre ella, sin embargo es posible pre-inicializar atributos para cada tabla que

use.

DBI::DBD::SqlEngine reconoce los atributos (públicos) "col_names", "table_name", "readonly", "sql_data_source" y "sql_identifier_case". Tenga mucho cuidado al modificar atributos que no conoce, la consecuencia podría ser una tabla destruida o

corrupta.

Mientras "sql_meta" es un atributo privado y de solo lectura (lo que significa que no puede modificar sus valores), los controladores derivados podrían proporcionar acceso de escritura restringido a través de otro atributo. Los accesores bien conocidos son "csv_tables" para DBD::CSV, "ad_tables" para DBD::AnyData y "dbm_tables" para DBD::

DBM.

sql_table_sourc

e

Controla la clase que se usará para obtener las tablas

disponibles.

Vea "DBI::DBD::SqlEngine::TableSource" para más

detalles.

sql_data_sourc

e

Contiene el nombre de la clase a usar para abrir

tablas.

ngine::DataSource"

Métodos privados del

controlador

Métodos DBI por

defecto

data_source

s

El método "data_sources" devuelve una lista de subdirectorios del directorio actual en la forma "dbi:CSV:f_dir=$dirname"

.

Si desea leer los subdirectorios de otro directorio,

use 
my ($drh)  = DBI->install_driver ("CSV");
my (@list) = $drh->data_sources (f_dir => "/usr/local/csv_data")
;

list_table

s

Este método devuelve una lista de nombres de archivos dentro de $dbh->{f_dir}.

Ejemplo: 
my ($dbh)  = DBI->connect ("dbi:CSV:f_dir=/usr/local/csv_data");
my (@list) = $dbh->func ("list_tables")
;

Ten en cuenta que la lista incluye todos los archivos contenidos en el directorio, incluso aquellos que tienen nombres de tabla no válidos, desde el punto de vista de

SQL.

Métodos

adicionales

Los siguientes métodos solo están disponibles a través de su nombre documentado cuando se usa DBI::DBD::SQlEngine directamente. Como esto solo es razonable para propósitos de pruebas, se deben usar los nombres reales en su lugar. Esos nombres pueden ser calculados reemplazando el "sql_" en el nombre del método con el prefijo del

controlador.

sql_version

s

Firma

: 
sub sql_versions (;$) {
  my ($table_name) = @_;
  $table_name ||= ".";
  ...
}

Devuelve las versiones del controlador, incluyendo la versión de DBI, la versión de Perl, la versión de DBI::PurePerl (si DBI::PurePerl está activo) y la versión del motor SQL en

uso. 
my $dbh = DBI->connect ("dbi:File:");
my $sql_versions = $dbh->func( "sql_versions" );
print "$sql_versions\n";
__END__
# DBI::DBD::SqlEngine  0.05 using SQL::Statement 1.402
# DBI                  1.623
# OS                   netbsd (6.99.12)
# Perl                 5.016002 (x86_64-netbsd-thread-multi
)

Cuando se llama en contexto de lista, sql_versions devolverá un array que contiene cada línea como una entrada

individual.

Algunos controladores podrían usar el argumento opcional (nombre de tabla) y modificar la información de versión relacionada con la tabla (por ejemplo, DBD::DBM proporciona información del backend de almacenamiento para la tabla solicitada, cuando tiene un nombre de tabla)

.

sql_get_met

a

Firma

: 
sub sql_get_meta ($$)
{
    my ($table_name, $attrib) = @_;
    ...
}

Devuelve el valor de un atributo meta establecido para una tabla específica, si lo hay. Consulta sql_meta para los posibles

atributos.

Un nombre de tabla de "." (punto simple) se interpreta como la tabla predeterminada. Esto recuperará el atributo apropiado globalmente desde el dbh. Tiene las mismas restricciones que "$dbh->{$att

rib}".

sql_set_met

a

Firma

: 
sub sql_set_meta ($$$)
{
    my ($table_name, $attrib, $value) = @_;
    ...
}

Establece el valor de un atributo meta para una tabla específica. Consulta sql_meta para los posibles

atributos.

Un nombre de tabla de "." (punto simple) se interpreta como la tabla predeterminada, lo que establecerá el atributo especificado globalmente para el dbh. Tiene las mismas restricciones que "$dbh->{$attrib} =

$value".

sql_clear_met

a

Firma

: 
sub sql_clear_meta ($)
{
    my ($table_name) = @_;
    ...
}

Borra la información meta espe

cífica de la tabla en el almac
enamiento privado del dbh.

Extensibilida

d

DBI::DBD::SqlEngine::

TableSource

Proporciona fuentes de datos e información de tabla a nivel de controlador de base de datos y manejador de base de

datos. 
package DBI::DBD::SqlEngine::TableSource;
sub data_sources ($;$)
{
  my ( $class, $drh, $attrs ) = @_;
  ...
}
sub avail_tables
{
  my ( $class, $drh ) = @_;
  ...
}

El método "data_sources" se llama cuando el usuario invoca cualquiera de los

siguientes: 
@ary = DBI->data_sources($driver);
@ary = DBI->data_sources($driver, \%attr);
@ary = $dbh->data_sources();
@ary = $dbh->data_sources(\%attr)
;

El método "avail_tables" se llama cuando el usuario invoca cualquiera de los

siguientes: 
@names = $dbh->tables( $catalog, $schema, $table, $type );
$sth = $dbh->table_info( $catalog, $schema, $table, $type );
$sth = $dbh->table_info( $catalog, $schema, $table, $type, \%attr );
$dbh->func( "list_tables" )
;

Cada vez que se puede especificar un argumento "\%attr", el atributo "sql_table_source" de este objeto "\%attr" tiene preferencia sobre el atributo $dbh o el valor predeterminado del controlador, por

ejemplo 
@ary = DBI->data_sources("dbi:CSV:", {
  f_dir => "/your/csv/tables",
  # note: this class doesn't comes with DBI
  sql_table_source => "DBD::File::Archive::Tar::TableSource",
  # scan tarballs instead of directories
})
;

Cuando vayas a implementar una clase DBD::File::Archive::Tar::TableSource, recuerda añadir los atributos correctos (incluyendo "sql_table_source" y "sql_data_source") a los DSN

devueltos.

DBI::DBD::SqlEngine::

DataSource

Proporciona funcionalidad básica para tratar con tablas. Está diseñado principalmente para permitir el acceso transparente a archivos en disco o (flujos de archivo) ya abiertos (por ejemplo, para DBD::CSV)

.

Las clases derivadas también deben restringirse a funcionalidad similar (por ejemplo, abrir flujos desde un archivo, comprimir/descomprimir transparentemente archivos de registro antes de

analizarlos, 
package DBI::DBD::SqlEngine::DataSource;
sub complete_table_name ($$;$)
{
  my ( $self, $meta, $table, $respect_case ) = @_;
  ...
}

El método "complete_table_name" se llama cuando se establece por primera vez la información meta de una

tabla: 
"SELECT user.id, user.name, user.shell FROM user WHERE ...
"

resulta en abrir la tabla "user". El primer paso del proceso de apertura de la tabla es completar el nombre. Imagina que tienes un manejador DBD::CSV con las siguientes configuraciones

: 
$dbh->{sql_identifier_case} = SQL_IC_LOWER;
$dbh->{f_ext} = '.lst';
$dbh->{f_dir} = '/data/web/adrmgr'
;

Esas configuraciones resultarán en buscar archivos que coincidan con "[Uu][Ss][Ee][Rr](\.lst)?$" en "/data/web/adrmgr/". El escaneo del directorio "/data/web/adrmgr/" y la comprobación de coincidencia de patrones se harán en "DBD::File::DataSource::File" por el método "complete_table_name"

.

Si pretendes proporcionar otras fuentes de flujos de datos además de archivos, además de proporcionar un método "complete_table_name" apropiado, se requiere un método para abrir el

recurso: 
package DBI::DBD::SqlEngine::DataSource;
sub open_data ($)
{
  my ( $self, $meta, $attrs, $flags ) = @_;
  ...
}

Después de que el método "open_data" se haya ejecutado con éxito, la información meta de la tabla está en un estado que permite que los métodos de acceso a d

atos de la tabla puedan recuperar/almacenar información de filas.
Los detalles de implementación dependen en gran medida de la implement
ación de la tabla, siendo la más famosa sin duda DBD::File::Table.

MOTORES

SQL

DBI::DBD::SqlEngine actualmente soporta dos motores SQL: SQL::Statement y DBI::SQL::Nano::Statement_. DBI::SQL::Nano soporta un subconjunto muy limitado de sentencias SQL, pero podría ser más rápido para algunas tareas muy simples. SQL::Statement, por el contrario, soporta un subconjunto mucho mayor de ANSI

SQL.

Para usar SQL::Statement, necesitas al menos la versión 1.401 de SQL::Statement y la variable de entorno "DBI_SQL_NANO" no debe estar esta

blecida a un valo
r verdadero.
