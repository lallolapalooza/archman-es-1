NOMBRE

DBD::DBM - un controlador DBI para archivos DBM y MLDBM

SINOPSIS

use DBI;
$dbh = DBI->connect('dbi:DBM:');                    # por defecto SDBM_File
$dbh = DBI->connect('DBI:DBM(RaiseError=1):');      # por defecto SDBM_File
$dbh = DBI->connect('dbi:DBM:dbm_type=DB_File');    # por defecto DB_File
$dbh = DBI->connect('dbi:DBM:dbm_mldbm=Storable');  # MLDBM con SDBM_File
# o
$dbh = DBI->connect('dbi:DBM:', undef, undef);
$dbh = DBI->connect('dbi:DBM:', undef, undef, {
    f_ext              => '.db/r',
    f_dir              => '/ruta/a/los/archivos/',
    f_lockfile         => '.lck',
    dbm_type           => 'BerkeleyDB',
    dbm_mldbm          => 'FreezeThaw',
    dbm_store_metadata => 1,
    dbm_berkeley_flags => {
        '-Cachesize' => 1000, # establece un flag ::Hash
    },
});

y otras variaciones sobre connect() como se muestra en la documentación de DBI, los metadatos de DBD::File y "Metadata" mostrado más abajo.

Utilice prepare, execute, fetch, marcadores de posición, etc. estándar de DBI; consulte "QUICK START" para un ejemplo.

DESCRIPCIÓN

DBD::DBM es un sistema de gestión de bases de datos que funciona directamente fuera de la caja. Si tiene una instalación estándar de Perl y DBI, puede comenzar a crear, acceder y modificar tablas de bases de datos simples sin ningún módulo adicional. Puede añadir otros módulos (por ejemplo, SQL::Statement, DB_File, etc.) para una funcionalidad mejorada.

El módulo utiliza una capa de almacenamiento de archivos DBM. El almacenamiento de archivos DBM es común en muchas plataformas y los archivos pueden crearse con él en muchas lenguajes de programación utilizando diferentes APIs. Eso significa que, además de crear archivos con DBI/SQL, también puede usar DBI/SQL para acceder y modificar archivos creados por otros módulos y programas DBM, y viceversa. Nota que en esos casos podría ser necesario usar un subconjunto común de las características proporcionadas.

Los archivos DBM se almacenan en formato binario optimizado para una recuperación rápida al usar un campo clave. Esa optimización puede usarse ventajosamente para hacer que las operaciones SQL de DBD::DBM que usan campos clave sean muy rápidas. Hay varios "sabores" diferentes de DBM que usan diferentes formatos de almacenamiento soportados por módulos de perl como SDBM_File y MLDBM. Este módulo soporta todos los sabores que soporta perl y, cuando se usa con MLDBM, soporta tablas con cualquier número de columnas e inserción de objetos Perl en tablas.

DBD::DBM ha sido probado con los siguientes tipos de DBM: SDBM_File, NDBM_File, ODBM_File, GDBM_File, DB_File, BerkeleyDB. Cada tipo fue probado tanto con como sin MLDBM y con los serializadores Data::Dumper, Storable, FreezeThaw, YAML y JSON usando los motores DBI::SQL::Nano o SQL::Statement.

INICIO RÁPIDO

DBD::DBM opera como todos los demás controladores DBD - su sintaxis y operación básica es especificada por DBI. Si no está familiarizado con DBI, debería empezar leyendo DBI y los documentos a los que apunta y luego volver y leer este archivo. Si está familiarizado con DBI, ya sabe la mayor parte de lo que necesita saber para operar este módulo. Simplemente empiece y cree un script de prueba algo como el que se muestra a continuación.

Debe ser consciente de que hay varias opciones para el motor SQL subyacente a DBD::DBM, consulte "Sintaxis SQL soportada". Hay también muchas opciones para el soporte de DBM, consulte especialmente la sección sobre "Añadir soporte de múltiples columnas con MLDBM".

Pero aquí hay un ejemplo para empezar.

use DBI;
my $dbh = DBI->connect('dbi:DBM:');
$dbh->{RaiseError} = 1;
for my $sql( split /;\n+/,"
    CREATE TABLE user ( user_name TEXT, phone TEXT );
    INSERT INTO user VALUES ('Fred Bloggs','233-7777');
    INSERT INTO user VALUES ('Sanjay Patel','777-3333');
    INSERT INTO user VALUES ('Junk','xxx-xxxx');
    DELETE FROM user WHERE user_name = 'Junk';
    UPDATE user SET phone = '999-4444' WHERE user_name = 'Sanjay Patel';
    SELECT * FROM user
"){
    my $sth = $dbh->prepare($sql);
    $sth->execute;
    $sth->dump_results if $sth->{NUM_OF_FIELDS};
}
$dbh->disconnect;

USO

Esta sección explicará algunos casos de uso con más detalle. Para obtener una visión general de los atributos disponibles, consulte "Metadata".

Especificar Archivos y Directorios

DBD::DBM proporcionará automáticamente una extensión de archivo apropiada para el tipo de DBM que está utilizando. Por ejemplo, si usa SDBM_File, una tabla llamada "fruit" se almacenará en dos archivos llamados "fruit.pag" y "fruit.dir". Usted debería nunca especificar las extensiones de archivo en sus sentencias SQL.

DBD::DBM reconoce las siguientes extensiones por defecto para los siguientes tipos:

.pag/r
Elegido para dbm_type "SDBM_File", "ODBM_File" y "NDBM_File" cuando se detecta una implementación que envuelve "-ldbm" para "NDBM_File" (por ejemplo, Solaris, AIX, ...).

Para esos tipos, la extensión ".dir" también se reconoce (para ser eliminada al eliminar una tabla).

.db/r
Elegido para dbm_type "NDBM_File" cuando se detecta una implementación que envuelve BerkeleyDB 1.x para "NDBM_File" (típicamente los de BSD, Darwin).

"GDBM_File", "DB_File" y "BerkeleyDB" normalmente no usan una extensión de archivo.

Si su tipo de DBM usa una extensión diferente a uno de los tipos de extensiones reconocidos, debería establecer el atributo f_ext a la extensión y presentar un informe de error como se describe en DBI con el nombre de la implementación y la extensión para que podamos añadirlo a DBD::DBM. Gracias de antemano por eso :-).

$dbh = DBI->connect('dbi:DBM:f_ext=.db');  # se usa la extensión .db
$dbh = DBI->connect('dbi:DBM:f_ext=');     # no se usa ninguna extensión
# o
$dbh->{f_ext}='.db';                       # configuración global
$dbh->{f_meta}->{'qux'}->{f_ext}='.db';    # configuración para la tabla 'qux'

Por defecto se asume que los archivos están en el directorio de trabajo actual. Para usar otros directorios especifique el atributo f_dir en la cadena de conexión o estableciendo el atributo del handle de base de datos.

Por ejemplo, esto buscará el archivo /foo/bar/fruit (o /foo/bar/fruit.pag para tipos de DBM que usan esa extensión)

my $dbh = DBI->connect('dbi:DBM:f_dir=/foo/bar');
# y esto también:
my $dbh = DBI->connect('dbi:DBM:');
$dbh->{f_dir} = '/foo/bar';
# pero esto es recomendado
my $dbh = DBI->connect('dbi:DBM:', undef, undef, { f_dir => '/foo/bar' } );
# ahora puede hacer
my $ary = $dbh->selectall_arrayref(q{ SELECT x FROM fruit });

También puede usar identificadores delimitados para especificar rutas directamente en sentencias SQL. Esto busca en el mismo lugar que los dos ejemplos anteriores pero sin establecer f_dir:

my $dbh = DBI->connect('dbi:DBM:');
my $ary = $dbh->selectall_arrayref(q{
    SELECT x FROM "/foo/bar/fruit"
});

También puede decirle a DBD::DBM que use una ruta especificada para una tabla específica:

$dbh->{dbm_tables}->{f}->{file} = q(/foo/bar/fruit);

Por favor, tenga en cuenta que no puede especificar esto durante la conexión.

Si tiene SQL::Statement instalado, puede usar alias de tablas:

my $dbh = DBI->connect('dbi:DBM:');
my $ary = $dbh->selectall_arrayref(q{
    SELECT f.x FROM "/foo/bar/fruit" AS f
});

Consulte "GOTCHAS AND WARNINGS" para usar DROP en tablas.

Bloqueo de tablas y flock()

El bloqueo de tablas se logra usando un archivo de bloqueo que tiene el mismo nombre base que el archivo de la tabla pero con la extensión de archivo '.lck' (o una extensión de archivo de bloqueo que usted proporcione, vea más abajo). Este archivo de bloqueo se crea con la tabla durante un CREATE y se elimina durante un DROP. Cada vez que la tabla en sí se abre, el archivo de bloqueo es flocked(). Para SELECT, este es un bloqueo compartido. Para todas las demás operaciones, es un bloqueo exclusivo (excepto cuando especifique algo diferente usando el atributo f_lock ).

Dado que el bloqueo depende de flock(), solo funciona en sistemas operativos que soportan flock(). En los casos donde flock() no está implementadolemented, DBD::DBM simplemente se comportará como si el flock() hubiera ocurrido aunque no ocurrirá ningún bloqueo real. Lea la documentación de flock() para más información.

Incluso en aquellos sistemas que sí soportan flock(), el bloqueo es solo consultivo - como siempre ocurre con flock(). Esto significa que si otro programa intenta acceder al archivo de la tabla mientras DBD::DBM tiene la tabla bloqueada, ese otro programa *tendrá éxito* al abrirlo a menos que también esté usando flock en el archivo '.lck'. Como resultado, el bloqueo de DBD::DBM solo se aplica realmente a otros programas que usan DBD::DBM u otros programas escritos para cooperar con el bloqueo de DBD::DBM.

Especificando el tipo de DBM

Cada "variedad" de DBM almacena sus archivos en un formato diferente y tiene diferentes capacidades y limitaciones. Vea AnyDBM_File para una comparación de los tipos de DBM.

Por defecto, DBD::DBM usa el tipo de almacenamiento "SDBM_File" ya que "SDBM_File" viene con Perl mismo. Si tiene otros tipos de almacenamiento DBM disponibles, puede usar cualquiera de ellos con DBD::DBM. Se recomienda encarecidamente usar al menos "DB_File", porque "SDBM_File" tiene peculiaridades y limitaciones y "ODBM_file", "NDBM_File" y "GDBM_File" no siempre están disponibles.

Puede especificar el tipo de DBM usando el atributo dbm_type que se puede establecer en la cadena de conexión o con "$dbh->{dbm_type}" y "$dbh->{f_meta}->{$table_name}->{type}" para configuraciones por tabla en casos donde un solo script está accediendo a más de un tipo de archivo DBM.

En la cadena de conexión, simplemente establezca "dbm_type=TYPENAME" donde "TYPENAME" es cualquier tipo de DBM como GDBM_File, DB_File, etc. No use MLDBM como su dbm_type ya que eso se establece de otra manera, vea más abajo.

my $dbh=DBI->connect('dbi:DBM:');                # usa el SDBM_File por defecto
my $dbh=DBI->connect('dbi:DBM:dbm_type=GDBM_File'); # usa el GDBM_File
# También puede usar $dbh->{dbm_type} para establecer el tipo de DBM para la conexión:
$dbh->{dbm_type} = 'DB_File';    # establece el tipo de DBM global
print $dbh->{dbm_type};          # muestra el tipo de DBM global

Si tiene varias tablas en su script que usan diferentes tipos de DBM, puede usar el hash $dbh->{dbm_tables} para almacenar diferentes configuraciones para las diversas tablas. Incluso puede usar esto para realizar uniones (joins) sobre archivos que tienen completamente diferentes mecanismos de almacenamiento.

# establece el valor por defecto global de GDBM_File
my $dbh->('dbi:DBM:type=GDBM_File');
# anula la configuración global, pero solo para las tablas llamadas
# I<foo> y I<bar>
my $dbh->{f_meta}->{foo}->{dbm_type} = 'DB_File';
my $dbh->{f_meta}->{bar}->{dbm_type} = 'BerkeleyDB';
# imprime el dbm_type para la tabla "foo"
print $dbh->{f_meta}->{foo}->{dbm_type};

Tenga en cuenta que debe cambiar el dbm_type de una tabla antes de acceder a ella por primera vez.

Añadiendo soporte multi-columna con MLDBM

La mayoría de los tipos de DBM solo soportan dos columnas y aunque soportaran más, DBD::DBM solo usaría dos. Sin embargo, un módulo de CPAN llamado MLDBM supera esta limitación al permitir más de dos columnas. MLDBM hace esto serializando los datos - básicamente pone una referencia a un array en la segunda columna. También puede poner casi cualquier tipo de objeto Perl o incluso referencias a código de Perl (Perl coderefs) en las columnas.

Si quiere más de dos columnas, debe instalar MLDBM. Está disponible para muchas plataformas y es fácil de instalar.

MLDBM viene por defecto distribuido con tres serializadores - Data::Dumper, Storable y FreezeThaw. Data::Dumper es el por defecto y Storable es el más rápido. MLDBM también puede usar métodos de serialización definidos por el usuario u otros módulos de serialización (por ejemplo YAML::MLDBM o MLDBM::Serializer::JSON. Selecciona el serializador usando el atributo dbm_mldbm .

Algunos ejemplos:

$dbh=DBI->connect('dbi:DBM:dbm_mldbm=Storable');  # usa MLDBM con Storable
$dbh=DBI->connect(
   'dbi:DBM:dbm_mldbm=MySerializer' # usa MLDBM con un módulo definido por el usuario
);
$dbh=DBI->connect('dbi::dbm:', undef,
    undef, { dbm_mldbm => 'YAML' }); # usa un serializador de terceros
$dbh->{dbm_mldbm} = 'YAML'; # igual que arriba
print $dbh->{dbm_mldbm} # muestra el serializador de MLDBM
$dbh->{f_meta}->{foo}->{dbm_mldbm}='Data::Dumper';   # establece Data::Dumper para la tabla "foo"
print $dbh->{f_meta}->{foo}->{mldbm}; # muestra el serializador para la tabla "foo"

MLDBM funciona sobre otros módulos DBM, por lo que también puede establecer un tipo de DBM junto con la configuración de dbm_mldbm. Los ejemplos anteriores usarían por defecto SDBM_File con MLDBM. Si quisiera GDBM_File en su lugar, así es cómo:

# usa DB_File con MLDBM y Storable
$dbh = DBI->connect('dbi:DBM:', undef, undef, {
    dbm_type  => 'DB_File',
    dbm_mldbm => 'Storable',
});

SDBM_File, el dbm_type por defecto, es bastante limitado, así que si va a usar MLDBM, probablemente debería usar un tipo diferente, vea AnyDBM_File.

Vea más abajo algunas "TRUCOS Y ADVERTENCIAS" sobre MLDBM.

Soporte para Berkeley DB

El tipo de almacenamiento Berkeley DB está soportado a través de dos módulos de Perl diferentes - DB_File (que soporta solo características de versiones antiguas de Berkeley DB) y BerkeleyDB (que soporta todas las versiones). DBD::DBM soporta especificar "DB_File" o "BerkeleyDB" como un dbm_type, con o sin soporte de MLDBM.

El dbm_type "BerkeleyDB" es experimental y su interfaz probablemente cambiará. Actualmente usa por defecto BerkeleyDB::Hash y actualmente no soporta ::Btree ni ::Recno.

Con BerkeleyDB, puede especificar banderas de inicialización estableciéndolas en su script así:

use BerkeleyDB;
my $env = new BerkeleyDB::Env -Home => $dir;  # y/o otras banderas de Env
$dbh = DBI->connect('dbi:DBM:', undef, undef, {
    dbm_type  => 'BerkeleyDB',
    dbm_mldbm => 'Storable',
    dbm_berkeley_flags => {
        'DB_CREATE'  => DB_CREATE,  # pasa constantes
        'DB_RDONLY'  => DB_RDONLY,  # pasa constantes
        '-Cachesize' => 1000,       # establece una bandera de ::Hash
        '-Env'       => $env,       # pasa un entorno
    },
});

No establezca las banderas -Flags o -Filename ya que esas son determinadas y sobrescritas por el SQL (por ejemplo, -Flags => DB_RDONLY se establece automáticamente cuando ejecuta una sentencia SELECT).

El tiempo no nos ha permitido proporcionar soporte en esta versión de DBD::DBM para más características de Berkeley DB como transacciones, concurrencia, bloqueo, etc. Trabajaremos en esto en el futuro y valoraríamos sugerencias, parches, etc.

Vea DB_File y BerkeleyDB para más detalles.

Optimizando el uso de campos clave

La mayoría de las "variedades" de DBM tienen solo dos columnas físicas (pero pueden contener múltiples columnas lógicas como se explicó arriba en "Añadiendo soporte multi-columna con MLDBM"). Funcionan de manera similar a un hash de Perl con la primera columna sirviendo como clave. Al igual que un hash de Perl, los archivos DBM permiten hacer búsquedas rápidas especificando la clave y así evitar recorrer todos los registros (soportado solo por DBI::SQL::Nano). También al igual que un hash de Perl, las claves deben ser únicas. Es imposible crear dos registros con la misma clave. Para decirlo de forma más simple y en términos SQL, la columna clave funciona como el PRIMARY KEY o UNIQUE INDEX.

En DBD::DBM, puede aprovechar la velocidad de las búsquedas por clave usando DBI::SQL::Nano y una cláusula WHERE con una única comparación de igualdad en el campo clave. Por ejemplo, las siguientes sentencias SQL están optimizadas para búsqueda por clave:

CREATE TABLE user ( user_name TEXT, phone TEXT);
INSERT INTO user VALUES ('Fred Bloggs','233-7777');
# ... muchos más inserts
SELECT phone FROM user WHERE user_name='Fred Bloggs';

La columna "user_name" es la columna clave ya que es la primera columna. La sentencia SELECT usa la columna clave en una única comparación de igualdad - "user_name='Fred Bloggs'" - así que la búsqueda la encontrará muy rápidamente sin tener que recorrer todos los nombres que fueron insertados en la tabla.

En contraste, estas búsquedas en la misma tabla no están optimizadas:

1. SELECT phone FROM user WHERE user_name < 'Fred';
2. SELECT user_name FROM user WHERE phone = '233-7777';

En #1, la operación usa una comparación de menor que (<) en lugar de una comparación de igualdad, así que no se optimizará para búsqueda por clave. En #2, el campo clave "user_name" no se especifica en la cláusula WHERE, y por lo tanto la búsqueda necesitará recorrer todas las filas para encontrar la(s) fila(s) solicitada(s).

Tenga en cuenta que el almacenamiento DBM subyacente necesita recorrer todas las pares clave/valor cuando se usa la búsqueda optimizada. SQL::Statement tiene una evaluación de cláusula where masivamente mejorada que cuesta alrededor del 15% de la evaluación en DBI::SQL::Nano - combinado con el bucle en el almacenamiento DBM la mejora de velocidad no es tan impresionante.

Incluso si las búsquedas son más rápidas en alrededor de un 50%, DBI::SQL::Nano y SQL::Statement pueden beneficiarse de las optimizaciones del campo clave al actualizar y eliminar filas - y aquí la evaluación mejorada de la cláusula where de SQL::Statement podría superar a DBI::SQL::Nano cada vez que la cláusula where contiene no solo el campo clave (o más de uno).

Sintaxis SQL soportada

DBD::DBM usa un subconjunto de SQL. La robustez de ese subconjunto depende de qué otros módulos tenga instalados. Ambas opciones soportan operaciones SQL básicas incluyendo CREATE TABLE, DROP TABLE, INSERT, DELETE, UPDATE y SELECT.

Opción #1: Por defecto, este módulo hereda su soporte SQL de DBI::SQL::Nano que viene con DBI. Nano es, como su nombre implica, un motor SQL *muy* pequeño. Aunque limitado en alcance, es más rápido que la opción #2 para algunas operaciones (especialmente búsquedas por clave primaria única). Vea DBI::SQL::Nano para una descripción del SQL que soporta y comparaciones de él con la opción #2.

Opción #2: Si instala el módulo puro de Perl de CPAN SQL::Statement, DBD::DBM lo usará en lugar de Nano. Esto añade soporte para alias de tablas, funciones, uniones (joins) y mucho más. Si va a usar DBD::DBM para algo más que tablas muy simplesnd queries, you should install SQL::Statement. You don't have to change DBD::DBM or your scripts in any way, simply installing SQL::Statement will give you the more robust SQL capabilities without breaking scripts written for DBI::SQL::Nano. See SQL::Statement for a description of the SQL it

supports.

Para averiguar qué módulo SQL está funcionando en un script dado, puedes usar el dbm_versions() método o, si no necesitas la salida completa y los números de versión, simplemente haz esto: print $dbh->{sql_handler}, "\n"; Eso imprimirá "SQL::Statement" o "DBI::SQL::Nano". Teniendo en cuenta la sección sobre acceso optimizado al almacenamiento DBM, comparando los beneficios de ambos motores: # DBI::SQL::Nano es más rápido $sth = $dbh->prepare( "update foo set value='new' where key=15" ); $sth->execute(); $sth = $dbh->prepare( "delete from foo where key=27" ); $sth->execute(); $sth = $dbh->prepare( "select * from foo where key='abc'" ); # SQL::Statement podría ser más rápido (dependiendo del tamaño de la base de datos) $sth = $dbh->prepare( "update foo set value='new' where key=?" ); $sth->execute(15); $sth = $dbh->prepare( "update foo set value=? where key=15" ); $sth->execute('new'); $sth = $dbh->prepare( "delete from foo where key=?" ); $sth->execute(27); # SQL::Statement es más rápido $sth = $dbh->prepare( "update foo set value='new' where value='old'" ); $sth->execute(); # debe expresarse usando "where key = 15 or key = 27 or key = 42 or key = 'abc'" # en DBI::SQL::Nano $sth = $dbh->prepare( "delete from foo where key in (15,27,42,'abc')" ); $sth->execute(); # debe expresarse usando "where key > 10 and key < 90" en DBI::SQL::Nano $sth = $dbh->prepare( "select * from foo where key between (10,90)" ); $sth->execute(); # solo SQL::Statement puede manejar $sth->prepare( "select * from foo,bar where foo.name = bar.name" ); $sth->execute(); $sth->prepare( "insert into foo values ( 1, 'foo' ), ( 2, 'bar' )" ); $sth->execute(); Especificando

EXTENSIBILIDAD

"SQL::Statement"
Motor SQL mejorado en comparación con el DBI::SQL::Nano incorporado - ver "Sintaxis SQL soportada".
"DB_File"
Berkeley DB versión 1. Esta biblioteca de base de datos está disponible en muchos sistemas sin instalación adicional y la mayoría de los sistemas están soportados.
"GDBM_File"
Tipo dbm simple (comparable a "DB_File") bajo la licencia GNU. Típicamente no disponible (o requiere instalación extra) en sistemas operativos no-GNU.
"BerkeleyDB"
Berkeley DB versión hasta v4 (y quizás más) - requiere instalación adicional pero es más fácil que GDBM_File en sistemas no-GNU.

db4 viene con muchas herramientas que permiten reparar y migrar bases de datos. Este es el recomendado tipo dbm para uso en producción.

"MLDBM"
Envoltorio de serializador para soportar más de una columna para los archivos. Viene con serializadores usando "Data::Dumper", "FreezeThaw" y "Storable".
"YAML::MLDBM"
Serializador adicional para MLDBM. YAML es muy portable entre lenguajes.
"MLDBM::Serializer::JSON"
Serializador adicional para MLDBM. JSON es muy portable entre lenguajes, probablemente más que YAML.

PELIGROS Y ADVERTENCIAS

Usar el comando SQL DROP eliminará cualquier archivo que tenga el nombre especificado en el comando con '.pag' y '.dir', '.db' o tu {f_ext} añadido. Esto puede ser peligroso si no estás seguro de a qué archivo se refiere:

$dbh->do(qq{DROP TABLE "/ruta/a/cualquier/archivo"});

Cada tipo DBM tiene limitaciones. SDBM_File, por ejemplo, solo puede almacenar valores de menos de 1,000 caracteres. *Tú* como autor del script debes asegurarte de no exceder esos límites. Si intentas insertar un valor más grande de lo que DBM puede almacenar, los resultados serán impredecibles. Consulta la documentación de la DBM que estés usando para más detalles.

Diferentes implementaciones de DBM devuelven los registros en diferentes órdenes. Eso significa que no deberías confiar en el orden de los registros a menos que uses una sentencia ORDER BY.

Los archivos de datos DBM son específicos de la plataforma. Para moverlos de una plataforma a otra, necesitarás hacer algo como volcar tus datos a CSV en la plataforma #1 y luego volcar de CSV a DBM en la plataforma #2. DBD::AnyData y DBD::CSV pueden ayudarte con eso. También puede haber herramientas de conversión DBM para tus plataformas que probablemente serían más rápidas.

Cuando usas MLDBM, hay un serializador muy poderoso - te permitirá almacenar código Perl o objetos en columnas de la base de datos. Cuando estos se des-serializan, pueden ser eval'ed - en otras palabras MLDBM (o en realidad Data::Dumper cuando es usado por MLDBM) puede tomar los valores e intentar ejecutarlos en Perl. Obviamente, esto puede presentar peligros, así que si no sabes qué hay en un archivo, ¡ten cuidado antes de acceder a él con MLDBM activado!

Ver la sección completa sobre "Bloqueo de tablas y flock()" para peligros y advertencias sobre el uso de flock().

ERRORES Y LIMITACIONES

Este módulo usa interfaces hash de dos bases de datos de archivos de dos columnas. Mientras que ninguno de los motores SQL soportados tienen soporte para índices, las siguientes sentencias realmente hacen lo mismo (incluso si significan algo completamente diferente) para cada tipo dbm que carece de soporte de "EXISTS" :

$sth->do( "insert into foo values (1, 'hello')" );
# esta sentencia hace ...
$sth->do( "update foo set v='world' where k=1" );
# ... lo mismo que esta sentencia
$sth->do( "insert into foo values (1, 'world')" );

Esto se considera un error y podría cambiar en una versión futura.

Los tipos dbm afectados conocidos son "ODBM_File" y "NDBM_File". Te recomendamos encarecidamente que uses un tipo dbm más moderno como "DB_File".
