DBI::ProxyServer(3) Documentación de Perl aportada por el usuario DBI::ProxyServer(3)

NOMBRE

DBI::ProxyServer - un servidor para el controlador DBD::Proxy

SINOPSIS

use DBI::ProxyServer;
DBI::ProxyServer::main(@ARGV);

DESCRIPCIÓN

DBI::Proxy Server es un módulo para implementar un proxy para el controlador proxy de DBI, DBD::Proxy. Permite el acceso a bases de datos a través de la red si el DBMS no ofrece operaciones en red. Pero el servidor proxy podría serle útil, incluso si tiene un DBMS con funcionalidad de red integrada: puede usarse como un proxy DBI en un entorno con cortafuegos.

DBI::ProxyServer se ejecuta como un demonio en la máquina con el DBMS o en el cortafuegos. El cliente se conecta al agente usando el controlador DBI DBD::Proxy, es decir, de la misma manera exacta que usando DBD::mysql, DBD::mSQL o cualquier otro controlador DBI.

El agente está implementado como una aplicación RPC::PlServer. Por lo tanto, tiene acceso a todas las posibilidades de este módulo, en particular, cifrado y un archivo de configuración similar. DBI::ProxyServer añade la posibilidad de restricciones de consultas: puede definir un conjunto de consultas que un cliente puede ejecutar y restringir el acceso a ellas. (Requiere un controlador DBI que soporte enlace de parámetros.) Vea "ARCHIVO DE CONFIGURACIÓN".

El script de controlador proporcionado, dbiproxy, puede usarse tal cual o usarse como base para una versión local modificada para satisfacer sus necesidades.

OPCIONES

Al llamar a la función DBI::ProxyServer::main() , usted proporciona una lista de opciones. Estas opciones son analizadas por el módulo Getopt::Long. El ProxyServer hereda todas las opciones y el manejo de opciones de RPC::PlServer y por lo tanto de Net::Daemon, en particular la capacidad de leer opciones desde la línea de comandos o un archivo de configuración. Vea RPC::PlServer. Vea Net::Daemon. Las opciones disponibles incluyen

chroot (--chroot=dir)
(Solo UNIX) Después de hacer un bind(), cambia el directorio raíz al directorio dado haciendo un chroot(). Esto es útil para la seguridad, pero restringe mucho el entorno. Por ejemplo, necesita cargar los controladores DBI en el archivo de configuración o tiene que crear enlaces duros a los sockets de Unix, si sus controladores los usan. Por ejemplo, con MySQL, un archivo de configuración podría contener las siguientes líneas: 
my $rootdir = '/var/dbiproxy';
my $unixsockdir = '/tmp';
my $unixsockfile = 'mysql.sock';
foreach $dir ($rootdir, "$rootdir$unixsockdir") {
    mkdir 0755, $dir;
}
link("$unixsockdir/$unixsockfile",
     "$rootdir$unixsockdir/$unixsockfile");
require DBD::mysql;
{
    'chroot' => $rootdir,
    ...
}

Si no sabe qué es chroot(), piense en un servidor FTP donde puede ver un árbol de directorios determinado solo después de iniciar sesión. Vea también las opciones --group y --user.

clients
Una referencia a un array con una lista de clientes. Los clientes son referencias a hashes, los atributos accept (0 para denegar el acceso y 1 para permitirlo) y mask, una expresión regular de Perl para el número IP del cliente o su nombre de host.
configfile (--configfile=file)
Se asume que los archivos de configuración devuelven una única referencia a un hash que sobreescribe los argumentos del método new. Sin embargo, los argumentos de la línea de comandos a su vez tienen prioridad sobre el archivo de configuración. Vea la sección "ARCHIVO DE CONFIGURACIÓN" más abajo para detalles sobre el archivo de configuración.
debug (--debug)
Activa el modo de depuración. Principalmente, esto asegura que se creen mensajes de registro de nivel "debug".
facility (--facility=mode)
(Solo UNIX) Facilidad a usar para Sys::Syslog. El valor por defecto es daemon.
group (--group=gid)
Después de hacer un bind(), cambia el GID real y efectivo al dado. Esto es útil si quiere que su servidor se enlace a un puerto privilegiado (<1024), pero no quiere que el servidor se ejecute como root. Vea también la opción --user.

Los GID pueden pasarse como nombres de grupo o valores numéricos.

localaddr (--localaddr=ip)
Por defecto, un demonio escucha en cualquier número IP que tenga la máquina. Este atributo permite restringir el servidor al número IP dado.
localport (--localport=port)
Este atributo establece el puerto en el que el demonio está escuchando. Debe darse de alguna manera, ya que no hay un valor por defecto.
logfile (--logfile=file)
Por defecto, los mensajes de registro se escribirán en el syslog (Unix) o en el registro de eventos (Windows NT). En otros sistemas operativos necesita especificar un archivo de registro. El valor especial "STDERR" fuerza el registro a stderr. Vea Net::Daemon::Log para detalles.
mode (--mode=modename)
El servidor puede ejecutarse en tres modos diferentes, dependiendo del entorno.

Si está ejecutando Perl 5.005 y lo compiló para hilos, el servidor creará un nuevo hilo para cada conexión. El hilo ejecutará el método Run() del servidor y luego terminará. Este modo es el valor por defecto, puede forzarlo con "--mode=threads".

Si los hilos no están disponibles, pero tiene un fork()funcional, entonces el servidor se comportará de manera similar creando un nuevo proceso para cada conexión. Este modo se usará automáticamente en la ausencia de hilos o si usa la opción "--mode=fork".

Finalmente, hay un modo de conexión única: si el servidor ha aceptado una conexión, entrará en el método Run() . No se aceptarán otras conexiones hasta que el método Run() retorne (si el cliente se desconecta). Este modo de operación es útil si no tiene ni hilos ni fork(), por ejemplo en Macintosh. Para propósitos de depuración, puede forzar este modo con "--mode=single".

pidfile (--pidfile=file)
(Solo UNIX) Si esta opción está presente, se creará un archivo PID en la ubicación dada. Por defecto, no se crea un archivo pidfile.
user (--user=uid)
Después de hacer un bind(), cambia el UID real y efectivo al dado. Esto es útil si quiere que su servidor se enlace a un puerto privilegiado (<1024), pero no quiere que el servidor se ejecute como root. Vea también las opciones --group y --chroot.

Los UID pueden pasarse como nombres de grupo o valores numéricos.

version (--version)
Suprime el inicio del servidor; en su lugar, se imprimirá la cadena de versión y el programa saldrá inmediatamente.

APAGADO

DBI::ProxyServer está construido sobre RPC::PlServer, que a su vez, está construido sobre Net::Daemon.

Debería referirse a Net::Daemon para saber cómo apagar el servidor, excepto que no puede porque actualmente no está documentado allí (a partir de v0.43). La conclusión es que parece que no hay soporte para un apagado ordenado.

ARCHIVO DE CONFIGURACIÓN

El archivo de configuración es simplemente el de RPC::PlServer o Net::Daemon con algunos atributos adicionales en la lista de clientes.

El archivo de configuración es un script de Perl. En la parte superior del archivo puede incluir código fuente de Perl arbitrario, por ejemplo, cargar controladores al inicio (útil para mejorar el rendimiento), preparar un entorno chroot, etc.

Lo importante es que finalmente devuelva una referencia a un hash de pares de nombre/valor de opciones. Las opciones posibles están listadas arriba.

Se aplican todas las posibilidades de Net::Daemon y RPC::PlServer, en particular

Control de acceso dependiente del host y/o del usuario
Cifrado dependiente del host y/o del usuario
Cambio de UID y/o GID después de enlazar al puerto
entorno chroot()

Además, el servidor ofrece restricciones de consulta. Sugiero la siguiente lista de clientes:

'clients' => [
    { 'mask' => '^admin\.company\.com$',
      'accept' => 1,
      'users' => [ 'root', 'wwwrun' ],
    },
    {
      'mask' => '^admin\.company\.com$',
      'accept' => 1,
      'users' => [ 'root', 'wwwrun' ],
      'sql' => {
           'select' => 'SELECT * FROM foo',
           'insert' => 'INSERT INTO foo VALUES (?, ?, ?)'
           }
    }

entonces solo los usuarios root y wwwrun pueden conectarse desde admin.company.com, ejecutando consultas arbitrarias, pero solo wwwrun puede conectarse desde otros hosts y está restringido a

$sth->prepare("select");

o

$sth->prepare("insert");

que en realidad son "SELECT * FROM foo" o "INSERT INTO foo VALUES (?, ?, ?)".

Servidor proxy Archivo de configuración (ejemplo más grande)

Esta sección le indica cómo restringir un DBI-Proxy: No todos los usuarios de todas las estaciones de trabajo deben poder ejecutar todas las consultas.

Existe un programa en perl "dbiproxy" que se ejecuta en una máquina que puede conectarse a todas las bases de datos a las que deseamos llegar. Todos los drivers de Perl-DBD deben estar instalados en esta máquina. También puede alcanzar bases de datos para las que no hay drivers disponibles en la máquina donde ejecuta el programa que consulta la base de datos, por ejemplo, preguntar a una base de datos MS-Access desde Linux.

Cree un archivo de configuración "proxy_oracle.cfg" en el servidor dbproxy:

{
    # Esto debe ejecutarse en un shell o en una ventana DOS
    # facility => 'daemon',
    pidfile => 'your_dbiproxy.pid',
    logfile => 1,
    debug => 0,
    mode => 'single',
    localport => '12400',
    # Control de acceso, ¡la primera coincidencia en esta lista gana!
    # Por lo tanto, el orden es importante
    clients => [
            # pista para organizar:
            # las reglas más especializadas para máquinas/usuarios individuales van primero
            # luego las reglas de denegación
            # luego las reglas sobre redes completas
            # regla: internal_webserver
            # desc: para obtener información estadística
            {
                    # esta dirección IP es la única que se pretende
                    mask => '^10\.95\.81\.243$',
                    # aceptar (no diferir) conexiones como esta
                    accept => 1,
                    # solo los usuarios de esta lista
                    # pueden iniciar sesión
                    users => [ 'informationdesk' ],
                    # solo se permite esta consulta estadística
                    # para obtener resultados para una consulta web
                    sql => {
                            alive => 'select count(*) from dual',
                            statistic_area => 'select count(*) from e01admin.e01e203 where geb_bezei like ?',
                    }
            },
            # regla: internal_bad_guy_1
            {
                    mask => '^10\.95\.81\.1$',
                    accept => 0,
            },
            # regla: employee_workplace
            # desc: obtener información detallada
            {
                    # aquí se pretende cualquier dirección IP
                    mask => '^10\.95\.81\.(\d+)$',
                    # aceptar (no diferir) conexiones como esta
                    accept => 1,
                    # solo los usuarios de esta lista
                    # pueden iniciar sesión
                    users => [ 'informationdesk', 'lippmann' ],
                    # se permiten todas estas consultas:
                    sql => {
                            search_city => 'select ort_nr, plz, ort from e01admin.e01e200 where plz like ?',
                            search_area => 'select gebiettyp, geb_bezei from e01admin.e01e203 where geb_bezei like ? or geb_bezei like ?',
                    }
            },
            # regla: internal_bad_guy_2
            # Esto NO funciona, porque la regla "employee_workplace" coincide
            # con su máscara de dirección IP de toda la red
            {
                    # no aceptar conexión desde esta dirección IP
                    mask => '^10\.95\.81\.5$',
                    accept => 0,
            }
    ]
}

Inicie el servidor proxy así:

rem se necesita un Oracle_home bien configurado para Oracle
set ORACLE_HOME=d:\oracle\ora81
dbiproxy --configfile proxy_oracle.cfg

Prueba de la conexión con un script perl

Cree un script perl como este:

# file: oratest.pl
# llámeme así: perl oratest.pl user password
use strict;
use DBI;
my $user = shift || die "Usage: $0 user password";
my $pass = shift || die "Usage: $0 user password";
my $config = {
        dsn_at_proxy => "dbi:Oracle:e01",
        proxy => "hostname=oechsle.zdf;port=12400",
};
my $dsn = sprintf "dbi:Proxy:%s;dsn=%s",
        $config->{proxy},
        $config->{dsn_at_proxy};
my $dbh = DBI->connect( $dsn, $user, $pass )
        || die "connect did not work: $DBI::errstr";
my $sql = "search_city";
printf "%s\n%s\n%s\n", "="x40, $sql, "="x40;
my $cur = $dbh->prepare($sql);
$cur->bind_param(1,'905%');
&show_result ($cur);
my $sql = "search_area";
printf "%s\n%s\n%s\n", "="x40, $sql, "="x40;
my $cur = $dbh->prepare($sql);
$cur->bind_param(1,'Pfarr%');
$cur->bind_param(2,'Bronnamberg%');
&show_result ($cur);
my $sql = "statistic_area";
printf "%s\n%s\n%s\n", "="x40, $sql, "="x40;
my $cur = $dbh->prepare($sql);
$cur->bind_param(1,'Pfarr%');
&show_result ($cur);
$dbh->disconnect;
exit;
sub show_result {
        my $cur = shift;
        unless ($cur->execute()) {
                print "Could not execute\n";
                return;
        }
        my $rownum = 0;
        while (my @row = $cur->fetchrow_array()) {
                printf "Row is: %s\n", join(", ",@row);
                if ($rownum++ > 5) {
                        print "... and so on\n";
                        last;
                }
        }
        $cur->finish;
}

Cómo funciona la configuración

La sección más importante para controlar el acceso a su dbi-proxy es "client=>" en el archivo "proxy_oracle.cfg":

Controlando qué persona en qué máquina tiene permitido el acceso

  • "mask" es una expresión regular de perl contra la dirección ip de la máquina que desea conectarse _o_ la búsqueda inversa de un servidor de nombres.
  • "accept" le indica al servidor dbiproxy si las direcciones ip como en "mask" tienen permitido conectarse o no (0/1)
  • "users" es una referencia a una lista de nombres de usuario que deben coincidir, esto NO es una expresión regular.

Controlando qué sentencias SQL están permitidas

Puede poner cualquier sentencia SQL que desee simplemente omitiendo "sql => ...", pero lo más importante es restringir la conexión para que solo sean posibles las consultas permitidas.

Si incluye una sección sql en su archivo de configuración así:

sql => {
        alive => 'select count(*) from dual',
        statistic_area => 'select count(*) from e01admin.e01e203 where geb_bezei like ?',
}

Se permite al usuario hacer dos consultas contra el dbi-proxy. Las consultas _no_ son "select count(*)...", las consultas son "alive" y "statistic_area"! Estas palabras clave son reemplazadas por la consulta real. Así que puede ejecutar una consulta para "alive":

my $sql = "alive";
my $cur = $dbh->prepare($sql);
...

La flexibilidad es que puede poner parámetros en la parte where de la consulta para que las consultas no sean estáticas. Simplemente reemplace un valor en la parte where de la consulta por un signo de interrogación y vincúlelo como un parámetro a la consulta.

my $sql = "statistic_area";
my $cur = $dbh->prepare($sql);
$cur->bind_param(1,'905%');
# Un segundo parámetro se llamaría así:
# $cur->bind_param(2,'98%');

El resultado es esta consulta:

select count(*) from e01admin.e01e203
where geb_bezei like '905%'

No intente poner parámetros en la consulta sql así:

# No funciona como usted piensa.
# Solo se analiza la primera palabra de la consulta,
# por lo que se cambia a "statistic_area", el resto se omite.
# Usted _tiene_ que trabajar con $cur->bind_param.
my $sql = "statistic_area 905%";
my $cur = $dbh->prepare($sql);
...

Problemas

  • No sé cómo restringir a los usuarios a bases de datos especiales.
  • No sé cómo pasar parámetros de consulta a través de dbish

ADVERTENCIA DE SEGURIDAD

RPC::PlServer que se usa debajo no es seguro debido a la serialización y deserialización de datos con el módulo Storable. Use el driver proxy solo en un entorno de confianza.
