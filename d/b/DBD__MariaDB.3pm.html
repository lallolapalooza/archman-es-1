NOMBRE

DBD::MariaDB - Controlador de MariaDB y MySQL para la Interfaz de Base de Datos de Perl5 (DBI)

SINOPSIS

use DBI;
my $dsn = "DBI:MariaDB:database=$database;host=$hostname;port=$port";
my $dbh = DBI->connect($dsn, $user, $password);
my $sth = $dbh->prepare(
    'SELECT id, first_name, last_name FROM authors WHERE last_name = ?'
) or die 'prepare statement failed: ' . $dbh->errstr();
$sth->execute('Eggers') or die 'execution failed: ' . $dbh->errstr();
print $sth->rows() . " rows found.\n";
while (my $ref = $sth->fetchrow_hashref()) {
    print "Found a row: id = $ref->{'id'}, fn = $ref->{'first_name'}\n";
}

EJEMPLO

#!/usr/bin/perl
use strict;
use warnings;
use DBI;
# Connect to the database.
my $dbh = DBI->connect('DBI:MariaDB:database=test;host=localhost',
                       'joe', q(joe's password),
                       { RaiseError => 1, PrintError => 0 });
# Drop table 'foo'. This may fail, if 'foo' doesn't exist
# Thus we put an eval around it.
eval {
    $dbh->do('DROP TABLE foo');
} or do {
    print 'Dropping foo failed: ' . $dbh->errstr() . "\n";
};
# Create a new table 'foo'. This must not fail, thus we don't
# catch errors.
$dbh->do('CREATE TABLE foo (id INTEGER, name VARCHAR(20))');
# INSERT some data into 'foo' using placeholders
$dbh->do('INSERT INTO foo VALUES (?, ?)', undef, 2, 'Jochen');
# now retrieve data from the table.
my $sth = $dbh->prepare('SELECT * FROM foo');
$sth->execute();
while (my $ref = $sth->fetchrow_hashref()) {
    print "Found a row: id = $ref->{'id'}, name = $ref->{'name'}\n";
}
# Disconnect from the database.
$dbh->disconnect();

DESCRIPCIÓN

DBD::MariaDB es el controlador de la Interfaz de Base de Datos de Perl5 para las bases de datos MariaDB y MySQL. En otras palabras: DBD::MariaDB es una interfaz entre el lenguaje de programación Perl y la API de programación MariaDB/MySQL que viene con el sistema de gestión de bases de datos relacionales MariaDB/MySQL. La mayoría de las funciones proporcionadas por esta API de programación son compatibles. Faltan algunas funciones raramente utilizadas, principalmente porque nadie las ha solicitado nunca. :-)

A continuación, primero discutiremos el uso de DBD::MariaDB, porque es lo que más necesitará. Para la instalación, consulte el documento separado DBD::MariaDB::INSTALL. Vea "EJEMPLO" para un ejemplo simple arriba.

Desde perl, activa la interfaz con la declaración

use DBI;

Después de eso, puede conectarse a múltiples servidores de bases de datos MariaDB y MySQL y enviar múltiples consultas a cualquiera de ellos a través de una interfaz orientada a objetos simple. Hay disponibles dos tipos de objetos: manejadores de base de datos y manejadores de sentencias. Perl devuelve un manejador de base de datos al método connect así:

my $dbh = DBI->connect("DBI:MariaDB:database=$db;host=$host",
                       $user, $password,
                       { RaiseError => 1, PrintError => 0 });

Una vez que se haya conectado a una base de datos, puede ejecutar sentencias SQL con:

$dbh->do('INSERT INTO foo VALUES (?, ?)', undef, $number, $name);

Consulte el método do de DBI para más detalles. Consulte también el método bind_param en DBI. Vea "MANEJADORES DE BASE DE DATOS" más abajo para más detalles sobre los manejadores de base de datos.

Si desea recuperar resultados, necesita crear un llamado manejador de sentencia con:

my $sth = $dbh->prepare('SELECT * FROM ' . $dbh->quote_identifier($table));
$sth->execute();

Este manejador de sentencia puede usarse para múltiples cosas. Primero, puede recuperar una fila de datos:

my $row = $sth->fetchrow_hashref();

Si su tabla tiene columnas "ID" y "NAME", entonces $row será una referencia a un hash con las claves "ID" y "NAME". Vea "MANEJADORES DE SENTENCIAS" más abajo para más detalles sobre los manejadores de sentencias.

Pero ahora para un enfoque más formal:

El database no es un atributo requerido, pero por favor note que MariaDB y MySQL no tienen algo así como una base de datos predeterminada. Si no especifica la base de datos en el momento de la conexión, su base de datos activa será nula y necesitaría prefijar sus tablas con el nombre de la base de datos; es decir "SELECT * FROM mydb.mytable".

Esto es similar al comportamiento del cliente de línea de comandos "mariadb" o "mysql" . También, "SELECT DATABASE()" devolverá la base de datos actual activa para el manejador.

El controlador DBD::MariaDB entiende cualquier atributo de conexión especificado en la sección "MANEJADORES DE BASE DE DATOS" que sea de lectura/escritura y además cualquier otro atributo descrito a continuación.

host
port
El host, si no se especifica o se especifica como cadena vacía o "localhost", será por defecto un servidor MariaDB o MySQL que se ejecuta en la máquina local usando el valor predeterminado para el socket UNIX. Para conectarse a un servidor MariaDB o MySQL en la máquina local a través de TCP, debe especificar la dirección IP de loopback 127.0.0.1 como el host.

Si el servidor MariaDB o MySQL se ejecuta en un número de puerto no estándar, puede indicar explícitamente el "número de puerto" al que conectarse en el argumento host , concatenando el "nombre de host" y el "número de puerto" juntos separados por un carácter de dos puntos (":") o usando el argumento port .

Para conectarse a un servidor MariaDB o MySQL en localhost usando TCP/IP, debe especificar el host como 127.0.0.1 con el portopcional, por ejemplo 3306.

Al conectarse a un servidor MariaDB o MySQL con IPv6, se debe usar una dirección IPv6 entre corchetes. Ejemplo de DSN:

my $dsn = 'DBI:MariaDB:;host=[1a12:2800:6f2:85::f20:8cf];port=3306';

MANEJADORES DE BASE DE DATOS

El controlador DBD::MariaDB soporta los siguientes atributos de los manejadores de base de datos (solo lectura):

my $errno = $dbh->{'mariadb_errno'};
my $error = $dbh->{'mariadb_error'};
my $hostinfo = $dbh->{'mariadb_hostinfo'};
my $info = $dbh->{'mariadb_info'};
my $insertid = $dbh->{'mariadb_insertid'};
my $protoinfo = $dbh->{'mariadb_protoinfo'};
my $serverinfo = $dbh->{'mariadb_serverinfo'};
my $ssl_cipher = $dbh->{'mariadb_ssl_cipher'};
my $stat = $dbh->{'mariadb_stat'};
my $thread_id = $dbh->{'mariadb_thread_id'};

Estos corresponden a mysql_errno(), mysql_error(), mysql_get_host_info(), mysql_info(), mysql_insert_id(), mysql_get_proto_info(), mysql_get_server_info(), mysql_stat(), mysql_get_ssl_cipher() y mysql_thread_id() respectivamente.

Las aplicaciones DBI portables no deberían usarlos. En su lugar deberían usar los métodos estándar de DBI: "$dbh->err()" y "$dbh->errstr()" para el número y la cadena de error, "$dbh->get_info($GetInfoType{SQL_SERVER_NAME})" para el nombre del host del servidor, "$dbh->get_info($GetInfoType{SQL_DBMS_NAME})" y "$dbh->get_info($GetInfoType{SQL_DBMS_VER})" para el nombre y la versión de la base de datos del servidor, "$dbh->last_insert_id()" o "$sth->last_insert_id()" para el id de inserción.

mariadb_clientinfo
mariadb_clientversion
Lista la información de la biblioteca cliente de MariaDB o MySQL contra la que se compiló DBD::MariaDB: 
print "$dbh->{mariadb_clientinfo}\n";
5.2.0-MariaDB
print "$dbh->{mariadb_clientversion}\n";
50200

Las aplicaciones DBI portables no deberían estar interesadas en la versión de la biblioteca cliente subyacente. DBD::MariaDB está ahí para ocultar cualquier posible incompatibilidad y funciona correctamente con cualquier versión disponible.

mariadb_serverversion
print "$dbh->{mariadb_serverversion}\n";
50200

Las aplicaciones DBI portables deberían usar "$dbh->get_info($GetInfoType{SQL_DBMS_NAME})" y "$dbh->get_info($GetInfoType{SQL_DBMS_VER})" para el nombre y la versión de la base de datos del servidor en su lugar.

mariadb_ssl_cipher
Devuelve el cifrado SSL utilizado para la conexión dada al servidor. En caso de que el cifrado SSL no estuviera habilitado con mariadb_ssl o no se hubiera establecido, devuelve "undef". 
my $ssl_cipher = $dbh->{mariadb_ssl_cipher};
if (defined $ssl_cipher) {
    print "Connection with server is encrypted with cipher: $ssl_cipher\n";
} else {
    print "Connection with server is not encrypted\n";
}

DBD::MariaDB mantiene un registro de algunas estadísticas en el atributo mariadb_dbd_stats . Las siguientes estadísticas se mantienen:

auto_reconnects_ok
El número de veces que DBD::MariaDB se reconectó exitosamente al servidor MariaDB o MySQL.
auto_reconnects_failed
El número de veces que DBD::MariaDB intentó reconectarse a MariaDB o MySQL pero falló.

El controlador DBD::MariaDB también soporta los siguientes atributos de los manejadores de base de datos (lectura/escritura):

mariadb_auto_reconnect
Este atributo determina si DBD::MariaDB se reconectará automáticamente al servidor MariaDB o MySQL si se pierde la conexión. Esta característica está desactivada por defecto. No se recomienda establecer mariadb_auto_reconnect en 1 si se usa "LOCK TABLES" porque si DBD::MariaDB se reconecta a MariaDB o MySQL, todos los bloqueos de tablas se perderán. Este atributo se ignora cuando AutoCommit está desactivado, y cuando AutoCommit está desactivado, DBD::MariaDB no se reconectará automáticamente al servidor.

También es posible establecer el valor por defecto del atributo mariadb_auto_reconnect para $dbh pasándolo en el hash "\%attr" para "DBI->connect".

$dbh->{mariadb_auto_reconnect} = 1;

o

my $dbh = DBI->connect($dsn, $user, $password, {
    mariadb_auto_reconnect => 1,
});

Ten en cuenta que si estás usando un módulo o framework que realiza reconexiones por ti (por ejemplo DBIx::Connector en modo fixup), este valor debe establecerse en 0.

mariadb_use_result
Este atributo fuerza al controlador a usar la función de biblioteca mysql_use_result() en lugar de mysql_store_result() . La primera es más rápida y consume menos memoria, pero tiende a bloquear otros procesos. mysql_store_result() es la opción por defecto debido al hecho de que almacenar el resultado es el comportamiento esperado con la mayoría de las aplicaciones.

Es posible establecer el valor por defecto del atributo mariadb_use_result para $dbh a través del DSN:

my $dbh = DBI->connect('DBI:MariaDB:test;mariadb_use_result=1', $user, $pass);

También puedes establecerlo después de crear el manejador de base de datos:

$dbh->{mariadb_use_result} = 0; # disable
$dbh->{mariadb_use_result} = 1; # enable

También puedes establecer o desactivar la configuración mariadb_use_result en tu manejador de sentencia, al crear el manejador de sentencia o después de que haya sido creado. Ver "MANEJADORES DE SENTENCIAS".

Las funciones de biblioteca mysql_use_result() y mysql_store_result() no se usan para las sentencias preparadas del lado del servidor, por lo tanto este atributo mariadb_use_result no tiene efecto cuando las sentencias preparadas del lado del servidor están habilitadas.

Ten en cuenta que la función de biblioteca mysql_use_result() no proporciona el número de filas en el conjunto de resultados. Por lo tanto, si este atributo mariadb_use_result está habilitado, la variable de DBI $DBI::rows y los métodos de sentencia execute y rows devuelven -1 (lo que significa que el número de filas no se conoce). Sin embargo, el método de sentencia rows devuelve el número correcto de filas después de que todas las filas ya se hayan obtenido y se haya emitido una llamada adicional de fetch (para este caso especial el controlador sabe que procesó todas las filas y por lo tanto sabe cuál es el ttotal number of rows).

Habilitar mariadb_use_result el atributo en un manejador de sentencia prohíbe el uso de todos los demás manejadores de sentencia y de base de datos hasta que todas las filas de datos del manejador de sentencia activo se hayan obtenido. Intentar usar otros manejadores de sentencia o de base de datos cuando hay un mariadb_use_result atributo activo en algún manejador de sentencia causa errores impredecibles.

En la mayoría de los casos no hay beneficio en el uso de este mariadb_use_result atributo, debería permanecer deshabilitado.

mariadb_bind_type_guessing
Este atributo hace que el controlador (sentencias preparadas emuladas) intente adivinar si un valor que se está enlazando es un valor numérico, y si lo es, no comilla el valor. Esto fue creado por Dragonchild y es una forma de lidiar con el problema de rendimiento de usar comillas en una sentencia que está insertando o actualizando un valor numérico grande.

Esta opción se usa para habilitar sentencias preparadas del lado del servidor. Por defecto las sentencias preparadas no se usan y el reemplazo de marcadores de posición lo realiza DBD::MariaDB antes de enviar la sentencia SQL al servidor MariaDB o MySQL.

Para usar sentencias preparadas del lado del servidor, todo lo que necesitas hacer es establecer la variable mariadb_server_prepare en la conexión:

    'password',
    { RaiseError => 1, PrintError => 0 },
);

o:

    'DBI:MariaDB:database=test;host=localhost',
    'user',
    'password',

);

MANEJADORES DE SENTENCIAS

Los manejadores de sentencias de DBD::MariaDB soportan una serie de atributos. Accedes a ellos usando, por ejemplo,

my $numFields = $sth->{NUM_OF_FIELDS};

Ten en cuenta que la mayoría de los atributos son válidos solo después de un execute exitoso. Un valor "undef" se devolverá de lo contrario. La excepción más importante es el mariadb_use_result atributo.

Para establecer el mariadb_use_result atributo en el manejador de sentencia $sth, usa cualquiera de los siguientes:

my $sth = $dbh->prepare($sql, { mariadb_use_result => 1});

o

my $sth = $dbh->prepare($sql);
$sth->{mariadb_use_result} = 1;

Los atributos dependientes de la columna, por ejemplo NAME, los nombres de las columnas, se devuelven como una referencia a un array. Los índices del array corresponden a los índices de los arrays devueltos por fetchrow y métodos similares. Por ejemplo, el siguiente código imprimirá un encabezado de los nombres de tabla junto con todas las filas:

my $sth = $dbh->prepare('SELECT * FROM t')
    or die 'Error: ' . $dbh->errstr() . "\n";
$sth->execute()
    or die 'Error: ' . $sth->errstr() . "\n";
my $names = $sth->{NAME};
my $numFields = $sth->{'NUM_OF_FIELDS'} - 1;
for my $i ( 0..$numFields ) {
    printf('%s%s', $i ? ',' : '', $$names[$i]);
}
print "\n";
while (my $ref = $sth->fetchrow_arrayref()) {
    for my $i ( 0..$numFields ) {
        printf('%s%s', $i ? ',' : '', $$ref[$i]);
    }
    print "\n";
}

Para aplicaciones portables, deberías restringirte a atributos con nombres en mayúsculas o en formato mixto. Los nombres de atributos en minúscula son privados de DBD::MariaDB. La lista de atributos incluye:

ChopBlanks
Este atributo determina si un fetchrow recortará los espacios en blanco iniciales y finales de los valores de las columnas. Recortar los espacios en blanco no tiene impacto en el mariadb_max_length atributo.
mariadb_insertid
Si la sentencia que ejecutaste realiza un "INSERT", y hay una columna "AUTO_INCREMENT" en la tabla en la que insertaste, este atributo contiene el valor almacenado en la "AUTO_INCREMENT" columna, si ese valor es generado automáticamente, almacenando "NULL" o 0 o se especificó como un valor explícito.

Típicamente, accederías al valor mediante "$sth->{mariadb_insertid}". El valor también puede accederse mediante "$dbh->{mariadb_insertid}" pero esto puede producir fácilmente resultados incorrectos en caso de que un manejador de base de datos esté compartido.

Las aplicaciones DBI portables no deberían usar mariadb_insertid. En su lugar deberían usar el método DBI "$dbh->last_insert_id()" o el método DBI de sentencia "$sth->last_insert_id()". El método de sentencia se introdujo en la versión 1.642 de DBI, pero DBD::MariaDB lo implementa también para versiones anteriores de DBI.

mariadb_is_blob
Referencia a un array de valores booleanos; Un valor lógico verdadero indica que la columna respectiva es un blob.
Referencia a un arreglo de valores booleanos; El valor lógico verdadero indica que la respectiva columna es una clave.
mariadb_is_num
Referencia a un arreglo de valores booleanos; El valor lógico verdadero indica que la respectiva columna contiene valores numéricos.
mariadb_is_pri_key
Referencia a un arreglo de valores booleanos; El valor lógico verdadero indica que la respectiva columna es una clave primaria.
mariadb_is_auto_increment
Referencia a un arreglo de valores booleanos; El valor lógico verdadero indica que la respectiva columna es una "AUTO_INCREMENT" columna.
mariadb_length
mariadb_max_length
Una referencia a un arreglo de tamaños máximos de columna. El mariadb_max_length es el máximo físicamente presente en la tabla de resultados, mientras que mariadb_length da el máximo teóricamente posible.

Para los tipos de variables orientados a cadenas (char, varchar, text y tipos similares), ambos atributos devuelven el valor en bytes. Si está interesado en el número de caracteres, entonces en lugar de mariadb_length use "COLUMN_SIZE" a través del método estándar de DBI column_info y en lugar de mariadb_max_length ejecute la consulta SQL "SELECT MAX(CHAR_LENGTH(...))". Ejemplo:

my $ci_sth = $dbh->column_info(undef, undef, $table, $column);
my $ci_ref = $ci_sth->fetchall_arrayref({});
my $mariadb_char_length = $ci_ref->[0]->{COLUMN_SIZE};
my $mariadb_char_max_length = $dbh->selectrow_array(sprintf(
                                  'SELECT MAX(CHAR_LENGTH(%s)) FROM %s',
                                  $dbh->quote_identifier($column),
                                  $dbh->quote_identifier($table),
                              ));
NOMBRE
Una referencia a un arreglo de nombres de columnas.
NULLABLE
Una referencia a un arreglo de valores booleanos; El valor lógico verdadero indica que esta columna puede contener "NULL"'s.
NUM_OF_FIELDS
Número de campos devueltos por una "SELECT" declaración. Puede usar esto para verificar si una declaración devolvió un resultado: Un valor cero indica una declaración no"SELECT" como "INSERT", "DELETE" o "UPDATE".
mariadb_table
Una referencia a un arreglo de nombres de tablas, útil en un "JOIN" resultado.
TYPE
Una referencia a un arreglo de tipos de columna. Los tipos de columna nativos del motor se mapean a tipos portables como DBI::SQL_INTEGER() o DBI::SQL_VARCHAR(), tan bien como sea posible. No todos los tipos nativos tienen un equivalente significativo. Si necesita los tipos de columna nativos, use mariadb_type. Vea abajo.
mariadb_type
Una referencia a un arreglo de los tipos de columna nativos de MySQL, por ejemplo DBD::MariaDB::TYPE_SHORT() o DBD::MariaDB::TYPE_STRING(). Use el TYPE atributo, si quiere tipos portables como DBI::SQL_SMALLINT() o DBI::SQL_VARCHAR().
mariadb_type_name
Similar a mariadb_type, pero se devuelven nombres de tipos y no números. Siempre que sea posible, se prefiere el nombre ANSI SQL.
mariadb_warning_count
El número de advertencias generadas durante la ejecución de la declaración SQL. Este atributo está disponible tanto en manejadores de declaración como en manejadores de base de datos.

SOPORTE UNICODE

Todos los tipos de variables orientados a cadenas (char, varchar, text y tipos similares) son representados por el DBD::MariaDB como cadenas Unicode de acuerdo con el modelo Unicode estándar de Perl. Significa que los escalares de Perl contienen puntos de código Unicode y no bytes UTF-8. Internamente el DBD::MariaDB usa el "utf8mb4" charset de MySQL para la comunicación de red con los servidores MariaDB y MySQL. Transforma automáticamente el charset de red de MySQL "utf8mb4" a los escalares Unicode de Perl y viceversa.

El "utf8mb4" charset de MySQL para la comunicación de red es configurado por "MYSQL_SET_CHARSET_NAME" libmariadb/libmysqlclient C library API el cual es un requisito para tener un método quote funcionando y una emulación de reemplazo de placeholders del lado del cliente.

No intente cambiar el charset de red (por ejemplo, vía el comando SQL "SET NAMES" manualmente) a algo diferente a UTF-8, ya que confundiría la biblioteca C subyacente y DBD::MariaDB se comportaría mal (por ejemplo, llevaría a un método quote roto/inseguro o a una emulación de reemplazo de placeholders del lado del cliente).

Usar un charset no-UTF-8 para una columna, tabla o base de datos está bien porque el servidor MariaDB o MySQL transforma automáticamente el charset de almacenamiento al charset usado por el protocolo de red ("utf8mb4"). Note que cuando DBD::MariaDB se conecta al servidor MariaDB o MySQL, llama al comando SQL "SET character_set_server = 'utf8mb4'" para asegurar que el charset por defecto para nuevas bases de datos sea UTF-8. Tenga en cuenta que el charset por defecto para nuevas tablas se establece a partir del charset de la base de datos.

En el caso de que el servidor MySQL no soporte el "utf8mb4" charset de MySQL para un protocolo de red, entonces DBD::MariaDB intentaría usar el "utf8" charset de MySQL el cual es un subconjunto de la codificación UTF-8 restringido a las secuencias UTF-8 de 3 bytes. El soporte para el "utf8mb4" charset de MySQL fue introducido en la versión 5.5.3 del servidor MySQL.

Trabajando con datos binarios

Los escalares de Perl no distinguen entre byte buffers orientados a Unicode y cadenas orientadas a Unicode. En Perl siempre es responsabilidad del llamador y del receptor definir en su API si las funciones y métodos esperan byte buffers o Unicode cadenas. No es posible (o más bien la aplicación Perl no debería intentar) distinguir si un escalar de Perl contiene un byte buffer o una Unicode cadena.

Al obtener datos de los servidores MariaDB y MySQL, DBD::MariaDB trata todos los campos marcados con el charset de MySQL "utf8mb4" (y también "utf8") como Unicode cadenas. Todo lo demás es tratado como byte buffers orientados a binario. Por lo tanto, la única diferencia es que los campos UTF-8 son automáticamente decodificados a Unicode. Los campos blob binarios permanecen intactos y los escalares de Perl correspondientes contendrían solo ordinales 0..255 (secuencia clásica de bytes). Los escalares de cadena Unicode contendrían una secuencia de puntos de código Unicode.

Hay un pequeño problema con los datos de entrada, más precisamente con las declaraciones SQL y sus parámetros de enlace. Por definición, una declaración SQL es una cadena y por lo tanto es esperada y manejada por DBD::MariaDB como una Unicode cadena (no un byte buffer orientado a binario). No hay forma de tratar una declaración SQL como binaria, pero esto no es un problema. Todos los comandos SQL están codificados en ASCII y todos los caracteres ASCII son invariantes en UTF-8 (tienen la misma representación que una secuencia de puntos de código Unicode y también cuando están codificados en UTF-8 en un buffer de bytes). Para la parte restante de una declaración SQL, se pueden y deben usar placeholders con parámetros de enlace.

Parámetros binarios

Desafortunadamente, ni el servidor MariaDB ni el de MySQL proporcionan información de tipo para declaraciones SQL preparadas; por lo tanto, DBD::MariaDB no tiene absolutamente ninguna forma de saber si un parámetro de enlace particular para un placeholder debe ser tratado como una Unicode cadena o como un byte buffer orientado a binario. Así que las aplicaciones Perl que usan DBD::MariaDB deben proporcionar información sobre el tipo correcto.

Además, la API de DBI para do, execute y todos los métodos select* enlaza todos los parámetros como "SQL_VARCHAR" tipo. Actualmente es una limitación de la API que no permite especificar el tipo de enlace. Varchar es una cadena y así DBD::MariaDB trata a todos ellos como Unicode cadenas.

La única forma de especificar un tipo en DBI es a través del método bind_param. Su tercer argumento toma una "SQL_*" constante que define un tipo para el parámetro de enlace pasado.

Las siguientes constantes de tipo son tratadas como binarias por DBD::MariaDB: "SQL_BIT", "SQL_BLOB", "SQL_BINARY", "SQL_VARBINARY", "SQL_LONGVARBINARY".

Este enfoque de manejo de datos binarios fue implementado en DBD::MariaDB porque no viola cómo funciona el modelo Unicode de Perl, sigue exactamente la documentación de la API de DBI y, más importante, es cómo otros controladores DBI (incluyendo DBD::Pg y DBD::SQLite) en sus versiones recientes funcionan. Esto asegura una buena compatibilidad para las aplicaciones Perl que usan múltiples backends de base de datos y varios controladores DBI.

Por favor note que el viejo controlador DBD::mysql en la versión 4.041 funciona de manera diferente y tiene el soporte Unicode completamente roto.

Para ilustrar el uso, vea el siguiente ejemplo:

# Prepare statement
my $sth = $dbh->prepare(
    'INSERT INTO users (id, name, picture) VALUES (?, ?, ?)'
);
# Bind number, 7-bit ASCII values are always in Unicode and binary context
$sth->bind_param(1, 10);
# Bind name, may contains Unicode character, in this case U+00E9
$sth->bind_param(2, "Andr\x{E9}");
# Bind picture, it is a sequence of binary bytes, not Unicode code points
$sth->bind_param(3, "\x{D8}\x{A0}\x{39}\x{F8}", DBI::SQL_BINARY);
# Execute statement with bind parameters
$sth->execute();

Explicación: En este caso número 10 y nombre "Andr\x{E9}" se codificarían automáticamente desde escalares de cadena Unicode de Perl al "utf8mb4" de red de MySQL y imagen no se tocaría ya que se vinculó con el "DBI::SQL_BINARY" tipo. Tenga en cuenta que los valores ASCII de 7 bits son invariantes en UTF-8, tienen las mismas representaciones en UTF-8, por lo que tanto la operación de codificación como la de decodificación son funciones de identidad.

Esta es la forma preferida y segura de trabajar con datos binarios. También es compatible con otros controladores DBI, incluyendo DBD::Pg y DBD::SQLite (ver arriba).

En DBD::MariaDB, hay otra forma específica de crear una sentencia SQL con datos binarios: llamar al método quote mientras se especifica un tipo binario. Este método toma un parámetro de vinculación y lo cita + escapa adecuadamente. Para tipos binarios convierte el argumento a la sintaxis HEX de MySQL ("X'...'") que es ASCII puro de 7 bits y por lo tanto invariante para UTF-8. Vea el siguiente ejemplo:

my $param1 = 10;
my $param2 = "Andr\x{E9}";
my $param3 = "\x{D8}\x{A0}\x{39}\x{F8}";
my $query = 'INSERT INTO users (id, name, picture) VALUES (' .
              $dbh->quote($param1) . ' ,' .
              $dbh->quote($param2) . ' ,' .
              $dbh->quote($param3, DBI::SQL_BINARY) .
            ')';
$dbh->do($query);

Los dos primeros parámetros se citan y escapan para una posterior codificación UTF-8 (a la "utf8mb4" charset) y el tercer parámetro se cita y escapa como un búfer binario a la sintaxis HEX de MySQL para blobs binarios.

Este método no se recomienda, porque los métodos de citado, escapado y similares pueden escribirse fácilmente de forma incorrecta y conducir a inyecciones SQL y otros problemas de seguridad.

SOPORTE DE TRANSACCIONES

El soporte de transacciones funciona de la siguiente manera:

  • Por defecto, el modo AutoCommit está activado, siguiendo las especificaciones de DBI.
  • Si ejecuta 
    $dbh->{AutoCommit} = 0;

    o

    $dbh->{AutoCommit} = 1;

    entonces el controlador establecerá la variable del servidor MariaDB o MySQL autocommit a 0 o 1, respectivamente. Cambiar de 0 a 1 también emitirá un "COMMIT", siguiendo las especificaciones de DBI.

  • Los métodos 
    $dbh->rollback();
$dbh->commit();

    emitirán los comandos "ROLLBACK" y "COMMIT", respectivamente. Un "ROLLBACK" también se emitirá si el modo AutoCommit está desactivado y se llama al método DESTROY del manejador de base de datos. De nuevo, esto sigue las especificaciones de DBI.

Dado lo anterior, debe tener en cuenta lo siguiente:

  • Nunca debe cambiar manualmente la variable del servidor AutoCommit, a menos que esté ignorando el soporte de transacciones de DBI.
  • Cambiar el modo AutoCommit de activado a desactivado o viceversa puede fallar. Debe comprobar siempre si hay errores al cambiar el modo AutoCommit. La forma sugerida de hacerlo es usando el indicador RaiseError de DBI. Si no le gusta RaiseError, tiene que usar código como el siguiente: 
    $dbh->{AutoCommit} = 0;
if ($dbh->{AutoCommit}) {
    # An error occurred!
}
  • Si detecta un error al cambiar el modo AutoCommit, ya no debe usar el manejador de base de datos. En otras palabras, debe desconectarse y reconectarse de nuevo, porque el modo de transacción es impredecible. Alternativamente, puede verificar el modo de transacción comprobando el valor de la variable del servidor autocommit. Sin embargo, ese comportamiento no es portable.
  • DBD::MariaDB tiene una reconexión característica que maneja el llamado bug de la mañana de MySQL: Si el servidor se ha desconectado, probablemente debido a un tiempo de espera, entonces por defecto el controlador se reconectará e intentará ejecutar la misma sentencia SQL de nuevo. Sin embargo, este comportamiento está desactivado cuando AutoCommit está desactivado: De lo contrario, el estado de la transacción sería completamente impredecible después de una reconexión.
  • La reconexión característica de DBD::MariaDB se puede activar o desactivar usando el mariadb_auto_reconnect atributo. Este comportamiento debería estar desactivado en el código que usa LOCK TABLE porque si el servidor de base de datos agota el tiempo de espera y DBD::MariaDB se reconecta, los bloqueos de tablas se perderán sin ninguna indicación de dicha pérdida.

CONJUNTOS DE RESULTADOS MÚLTIPLES

DBD::MariaDB soporta múltiples conjuntos de resultados, gracias a Guy Harrison.

El uso básico de múltiples conjuntos de resultados es

do {
    while (my @row = $sth->fetchrow_array()) {
        do stuff;
    }
} while ($sth->more_results);

Un ejemplo sería:

$dbh->do('drop procedure if exists someproc')
    or print $DBI::errstr;
$dbh->do('create procedure someproc() deterministic
    begin
        declare a,b,c,d int;
        set a=1;
        set b=2;
        set c=3;
        set d=4;
        select a, b, c, d;
        select d, c, b, a;
        select b, a, c, d;
        select c, b, d, a;
    end'
) or die "$DBI::err: $DBI::errstr";
my $sth = $dbh->prepare('call someproc()')
    or die "$DBI::err: $DBI::errstr";
$sth->execute()
    or die "$DBI::err: $DBI::errstr";
my $i=0;
do {
    print "\nRowset ".++$i."\n---------------------------------------\n\n";
    foreach my $colno (0..$sth->{NUM_OF_FIELDS}-1) {
        print $sth->{NAME}->[$colno]."\t";
    }
    print "\n";
    while (my @row = $sth->fetchrow_array())  {
        foreach $field (0..$#row) {
            print $row[$field]."\t";
        }
        print "\n";
    }
} while ($sth->more_results);

Problemas con múltiples conjuntos de resultados

Tenga en cuenta que podría haber problemas si sus conjuntos de resultados son irregulares, lo que significa que el número de columnas de sus resultados varía. Números variables de columnas podrían hacer que su script se bloquee.

MULTIHILADO

Las capacidades de multihilo de DBD::MariaDB dependen completamente de las bibliotecas C subyacentes. Los módulos trabajan solo con datos de manejadores, no se accede a variables globales ni (hasta donde yo sé) se llaman funciones no seguras para hilos. Por lo tanto, se cree que DBD::MariaDB es completamente seguro para hilos, si las bibliotecas C son seguras para hilos y no comparte manejadores entre hilos.

La pregunta obvia es: ¿Son seguras las bibliotecas C para hilos? En el caso de MySQL la respuesta es sí, desde MySQL 5.5 lo es. La biblioteca C de versiones anteriores necesita compilarse con las opciones de "--with-thread-safe-client" o "--enable-thread-safe-client" de configure.

CONSULTAS ASÍNCRONAS

Puede hacer una única consulta asíncrona por conexión MySQL; esto le permite enviar una consulta de larga ejecución al servidor y tener un bucle de eventos que le avise cuando esté lista. Una consulta asíncrona se inicia estableciendo el mariadb_async atributo a un valor verdadero en el método do, o en el método prepare. Las sentencias creadas con mariadb_async establecido a verdadero en prepare siempre ejecutan sus consultas de forma asíncrona cuando se llama a execute. El controlador también ofrece tres métodos adicionales: mariadb_async_result(), mariadb_async_ready()y mariadb_sockfd(). mariadb_async_result() devuelve lo que do o execute habrían devuelto; es decir, el número de filas afectadas. mariadb_async_ready() devuelve verdadero si mariadb_async_result() no se bloqueará, y cero en caso contrario. Ambos devuelven "undef" si ese manejador no se creó con mariadb_async establecido a verdadero o si una consulta asíncrona no se ha iniciado todavía. mariadb_sockfd() devuelve el número de descriptor de archivo para la conexión MySQL; puede usar esto en un bucle de eventos.

Aquí hay un ejemplo de cómo usar la interfaz de consulta asíncrona:

use feature 'say';
$dbh->do('SELECT SLEEP(10)', { mariadb_async => 1 });
until($dbh->mariadb_async_ready()) {
    say 'not ready yet!';
    sleep 1;
}
my $rows = $dbh->mariadb_async_result();

Y otro ejemplo:

my $fd = $dbh->mariadb_sockfd();
my $sth = $dbh->prepare('SELECT 1, SLEEP(10), t.id FROM t', { mariadb_async => 1 });
$sth->execute();
my $bits = '';
vec($bits, $fd, 1) = 1;
select($bits, undef, $bits, undef);
my $num_rows = $sth->mariadb_async_result();
print "num rows: $num_rows\n";
while (my @array = $sth->fetchrow_array()) {
    print "row:\n";
    print "\tvalue: $_\n" foreach @array;
}

AUTORES

Originalmente, había un controlador no-DBI, Mysql, que era muy parecido a los controladores PHP como mysql y mysqli. El Mysql módulo fue originalmente escrito por Andreas König (koenig@kulturbox.de) quien todavía, hasta el día de hoy, contribuye con parches a DBD::mysql. Una versión emulada de Mysql fue proporcionada a DBD::mysql por Jochen Wiedmann, pero finalmente se descontinuó ya que era otro paquete de código que mantener.

La primera encarnación de DBD::mysql fue desarrollada por Alligator Descartes, quien también fue ayudado y apoyado por Gary Shea, Andreas König y Tim Bunce.

La encarnación actual de DBD::mysql fue escrita por Jochen Wiedmann, luego numerosos cambios y correcciones de errores fueron añadidos por Rudy Lippan. A continuación, el soporte de sentencias preparadas fue añadido por Patrick Galbraith y Alexy Stroganov (quien también añadió exclusivamente el soporte de servidor embebido).

Desde 2004, DBD::mysql ha sido mantenido por Patrick Galbraithpatg@patg.net), y desde 2013 con la gran ayuda de Michiel Beijen (michiel.beijen@gmail.com), junto con toda la comunidad de desarrolladores de Perl que siguen enviando parches para ayudar a continuar mejorando DBD::mysql.

En 2018, la versión no publicada 4.042_01 de DBD::mysql fue bifurcada y se creó DBD::MariaDB para corregir errores de Unicode de larga data y el soporte de MariaDB. El desarrollo en ese momento fue apoyado por GoodData. Actualmente está alojado en Github como parte del gran proyecto perl5-dbi y mantenido por Pali (pali@cpan.org).
