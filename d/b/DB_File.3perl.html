DB_File - Acceso de Perl5 a Berkeley DB versión 1.x

DESCRIPCIÓN

DB_File es un módulo que permite a los programas Perl utilizar las facilidades proporcionadas por Berkeley DB versión 1.x (si tiene una versión más nueva de DB, consulte "Uso de DB_File con Berkeley DB versión 2 o superior"). Se asume que tiene una copia de las páginas del manual de Berkeley DB a mano al leer esta documentación. La interfaz definida aquí refleja de cerca la interfaz de Berkeley DB.

Berkeley DB es una biblioteca C que proporciona una interfaz consistente a varios formatos de base de datos. DB_File proporciona una interfaz a los tres tipos de base de datos actualmente soportados por Berkeley DB.

Los tipos de archivo son:

DB_HASH
Este tipo de base de datos permite almacenar pares clave/valor arbitrarios en archivos de datos. Esto equivale a la funcionalidad proporcionada por otros paquetes de hashing como DBM, NDBM, ODBM, GDBM y SDBM. Recuerde, sin embargo, que los archivos creados usando DB_HASH no son compatibles con ninguno de los otros paquetes mencionados.

Un algoritmo de hashing predeterminado, que será adecuado para la mayoría de las aplicaciones, está integrado en Berkeley DB. Si necesita usar su propio algoritmo de hashing, es posible escribir uno propio en Perl y hacer que DB_File lo use en su lugar.

DB_BTREE
El formato btree permite almacenar pares clave/valor arbitrarios en un árbol binario ordenado y equilibrado.

Al igual que con el formato DB_HASH, es posible proporcionar una rutina Perl definida por el usuario para realizar la comparación de claves. Por defecto, sin embargo, las claves se almacenan en orden léxico.

DB_RECNO
DB_RECNO permite manipular tanto archivos de texto plano de longitud fija como de longitud variable usando la misma interfaz de pares clave/valor que en DB_HASH y DB_BTREE. En este caso, la clave consistirá en un número de registro (línea).

Uso de DB_File con Berkeley DB versión 2 o superior

Aunque DB_File está destinado a ser usado con Berkeley DB versión 1, también puede usarse con la versión 2, 3 o 4. En este caso, la interfaz está limitada a la funcionalidad proporcionada por Berkeley DB 1.x. Dondequiera que la interfaz de la versión 2 o superior difiera, DB_File se encarga de que funcione como la versión 1. Esta característica permite que los scripts DB_File que fueron construidos con la versión 1 se migren a la versión 2 o superior sin ningún cambio.

Si desea hacer uso de las nuevas características disponibles en Berkeley DB 2.x o superior, use el módulo Perl BerkeleyDB https://metacpan.org/pod/BerkeleyDB en su lugar.

Nota: El formato del archivo de base de datos ha cambiado múltiples veces en Berkeley DB versión 2, 3 y 4. Si no puede recrear sus bases de datos, debe volcar cualquier base de datos existente con la utilidad "db_dump" o la "db_dump185" que viene con Berkeley DB. Una vez que haya reconstruido DB_File para usar Berkeley DB versión 2 o superior, sus bases de datos pueden recrearse usando "db_load". Consulte la documentación de Berkeley DB para más detalles.

Por favor, lea "COPYRIGHT" antes de usar la versión 2.x o superior de Berkeley DB con DB_File.

Interfaz a Berkeley DB

DB_File permite el acceso a archivos Berkeley DB usando el mecanismo tie() en Perl 5 (para detalles completos, consulte "tie()" en perlfunc). Esta facilidad permite que DB_File acceda a archivos Berkeley DB usando un array asociativo (para los tipos de archivo DB_HASH y DB_BTREE) o un array ordinario (para el tipo de archivo DB_RECNO).

Además de la interfaz tie() , también es posible acceder directamente a la mayoría de las funciones proporcionadas en la API de Berkeley DB. Consulte "LA INTERFAZ API".

Apertura de un Archivo de Base de Datos de Berkeley DB

Berkeley DB usa la función dbopen() para abrir o crear una base de datos. Aquí está el prototipo C para dbopen():

DB*
dbopen (const char * file, int flags, int mode,
        DBTYPE type, const void * openinfo)

El parámetro "type" es una enumeración que especifica cuál de los 3 métodos de interfaz (DB_HASH, DB_BTREE o DB_RECNO) se va a usar. Dependiendo de cuál de estos se elija realmente, el parámetro final, openinfo apunta a una estructura de datos que permite la personalización del método de interfaz específico.

Esta interfaz se maneja de manera ligeramente diferente en DB_File. Aquí hay una llamada equivalente usando DB_File:

tie %array, 'DB_File', $filename, $flags, $mode, $DB_HASH ;

Los parámetros "filename", "flags" y "mode" son el equivalente directo de sus contrapartes en dbopen() . El parámetro final $DB_HASH realiza la función de ambos parámetros "type" y "openinfo" en dbopen().

En el ejemplo de arriba $DB_HASH es en realidad una referencia predefinida a un objeto hash. DB_File tiene tres de estas referencias predefinidas. Aparte de $DB_HASH, también hay $DB_BTREE y $DB_RECNO.

Las claves permitidas en cada una de estas referencias predefinidas están limitadas a los nombres usados en la estructura C equivalente. Así que, por ejemplo, la referencia $DB_HASH solo permitirá claves llamadas "bsize", "cachesize", "ffactor", "hash", "lorder" y "nelem".

Para cambiar uno de estos elementos, simplemente asígnele un valor así:

$DB_HASH->{'cachesize'} = 10000 ;

Las tres variables predefinidas $DB_HASH, $DB_BTREE y $DB_RECNO son generalmente adecuadas para la mayoría de las aplicaciones. Si necesita crear instancias adicionales de estos objetos, hay constructores disponibles para cada tipo de archivo.

Aquí hay ejemplos de los constructores y las opciones válidas disponibles para DB_HASH, DB_BTREE y DB_RECNO respectivamente.

1

Las claves duplicadas están enteramente definidas por la función de comparación. En el ejemplo que no distingue entre mayúsculas y minúsculas, las claves: 'KEY' y 'key' se considerarían duplicadas, y asignar a la segunda sobrescribiría la primera. Si se permiten duplicados (con la bandera R_DUP discutida más adelante), solo se almacena una única copia de las claves duplicadas en la base de datos --- por lo tanto (de nuevo con el ejemplo anterior), asignar tres valores a las claves: 'KEY', 'Key', y 'key' dejaría solo la primera clave: 'KEY' en la base de datos con tres valores. En algunas situaciones esto resulta en pérdida de información, por lo que se debe tener cuidado para proporcionar funciones de comparación completamente calificadas cuando sea necesario. Por ejemplo, la rutina de comparación anterior podría modificarse para comparar además de forma sensible a mayúsculas/minúsculas si dos claves son iguales en la comparación insensible a
mayúsculas/minúsculas:

@_; lc $key1 cmp lc $key2 || $key1 cmp $key2; }
Y ahora solo tendrá duplicados cuando las claves en sí sean verdaderamente las mismas. (nota: en versiones de la biblioteca db anteriores a aproximadamente noviembre de 1996, tales claves duplicadas se retenían, por lo que era posible recuperar las claves originales en conjuntos de claves que comparaban como iguales).

El método "get_dup" ayuda a leer valores duplicados de bases de datos BTREE. El método puede tomar las siguientes

formas: 
$count = $x->get_dup($key) ;
@list  = $x->get_dup($key) ;
%list  = $x->get_dup($key, 1)
;

En un contexto escalar, el método devuelve el número de valores asociados con la clave, $key>.

En contexto de lista, devuelve todos los valores que coinciden con $key. Ten en cuenta que los valores se devolverán en un orden aparentemente aleatorio.

En contexto de lista, si el segundo parámetro está presente y evalúa como VERDADERO, el método devuelve un array asociativo. Las claves del array asociativo corresponden a los valores que coincidieron en el BTREE y los valores del array son un recuento del número de veces que ese valor particular ocurrió en el BTREE.

Así que asumiendo la base de datos creada anteriormente, podemos usar "get_dup" así:

my ($filename, $x, %h) ;

# Enable duplicate records
$DB_BTREE->{'flags'} = R_DUP ;
$x = tie %h, "DB_File", $filename, O_RDWR|O_CREAT, 0666, $DB_BTREE
    or die "Cannot open $filename: $!\n";
my $cnt  = $x->get_dup("Wall") ;
print "Wall occurred $cnt times\n" ;
my %hash = $x->get_dup("Wall", 1) ;
print "Larry is there\n" if $hash{'Larry'} ;
print "There are $hash{'Brick'} Brick Walls\n" ;
my @list = sort $x->get_dup("Wall") ;
print "Wall =>      [@list]\n" ;
@list = $x->get_dup("Smith") ;
print "Smith =>     [@list]\n" ;
@list = $x->get_dup("Dog") ;

El find_dup() Método

$status = $X->find_dup($key, $value) ;

Este método comprueba la existencia de un par clave/valor específico. Si el par existe, el cursor se deja apuntando al par y el método devuelve 0. De lo contrario, el método devuelve un valor distinto de cero.

Asumiendo la base de datos del ejemplo anterior:

use warnings ;
use strict ;
use DB_File ;
my ($filename, $x, %h, $found) ;
$filename = "tree" ;
# Enable duplicate records
$DB_BTREE->{'flags'} = R_DUP ;
$x = tie %h, "DB_File", $filename, O_RDWR|O_CREAT, 0666, $DB_BTREE
    or die "Cannot open $filename: $!\n";
$found = ( $x->find_dup("Wall", "Larry") == 0 ? "" : "not") ;
print "Larry Wall is $found there\n" ;
$found = ( $x->find_dup("Wall", "Harry") == 0 ? "" : "not") ;
print "Harry Wall is $found there\n" ;
undef $x ;
untie %h ;

imprime esto

Larry Wall is  there
Harry Wall is not there

El del_dup() Método

$status = $X->del_dup($key, $value) ;

Este método elimina un par clave/valor específico. Devuelve 0 si existen y se han eliminado correctamente. De lo contrario, el método devuelve un valor distinto de cero.

De nuevo asumiendo la existencia de la "tree" base de datos

use warnings ;

use DB_File ;
my ($filename, $x, %h, $found) ;

Coincidencia de Claves Parciales

La interfaz BTREE tiene una característica que permite que se coincidan claves parciales. Esta funcionalidad está solo disponible cuando se usa el método "seq" junto con la bandera R_CURSOR.

$x->seq($key, $value, R_CURSOR) ;

Aquí está la cita relevante de la página del manual de dbopen donde define el uso de la bandera R_CURSOR con seq:

Nota, para el método de acceso DB_BTREE, la clave devuelta no es
necesariamente una coincidencia exacta para la clave especificada. La clave devuelta
es la clave más pequeña mayor o igual que la clave especificada,
permitiendo coincidencias de claves parciales y búsquedas de rango.

En el script de ejemplo a continuación, el "match" sub usa esta característica para encontrar e imprimir el primer par clave/valor coincidente dado una clave parcial.

use warnings ;
use strict ;
use DB_File ;
use Fcntl ;
my ($filename, $x, %h, $st, $key, $value) ;
sub match
{
    my $key = shift ;
    my $value = 0;
    my $orig_key = $key ;
    $x->seq($key, $value, R_CURSOR) ;
    print "$orig_key\t-> $key\t-> $value\n" ;
}
$filename = "tree" ;
unlink $filename ;
$x = tie %h, "DB_File", $filename, O_RDWR|O_CREAT, 0666, $DB_BTREE
    or die "Cannot open $filename: $!\n";
# Add some key/value pairs to the file
$h{'mouse'} = 'mickey' ;
$h{'Wall'} = 'Larry' ;
$h{'Walls'} = 'Brick' ;
$h{'Smith'} = 'John' ;
$key = $value = 0 ;
print "IN ORDER\n" ;
for ($st = $x->seq($key, $value, R_FIRST) ;
     $st == 0 ;
     $st = $x->seq($key, $value, R_NEXT) )
  {  print "$key    -> $value\n" }
print "\nPARTIAL MATCH\n" ;
match "Wa" ;
match "A" ;
match "a" ;
undef $x ;
untie %h ;

Aquí está la salida:

IN ORDER
Smith -> John
Wall  -> Larry
Walls -> Brick
mouse -> mickey
PARTIAL MATCH
Wa -> Wall  -> Larry
A  -> Smith -> John
a  -> mouse -> mickey

DB_RECNO

DB_RECNO proporciona una interfaz para archivos de texto plano. Se admiten registros de longitud variable y de longitud fija.

Para hacer RECNO más compatible con Perl, el desplazamiento del array para todos los arrays RECNO comienza en 0 en lugar de 1 como en Berkeley DB.

Al igual que con los arrays normales de Perl, un array RECNO se puede acceder usando índices negativos. El índice -1 se refiere al último elemento del array, -2 al penúltimo, y así sucesivamente. Intentar acceder a un elemento antes del inicio del array generará un error de tiempo de ejecución fatal.

La Opción 'bval'

El funcionamiento de la opción bval merece algo de discusión. Aquí está la definición de bval de la página del manual de recno de Berkeley DB 1.85:

El byte delimitador a usar para marcar el final de un
registro para registros de longitud variable, y el carácter de relleno
para registros de longitud fija. Si no se especifica
ningún valor, se usan saltos de línea (``\n'') para marcar el final de
registros de longitud variable y los registros de longitud fija se
rellenan con espacios.

La segunda frase es incorrecta. De hecho, bval solo tomará el valor predeterminado "\n" cuando el parámetro openinfo en dbopen es NULL. Si se usa un parámetro openinfo distinto de NULL en absoluto, se usará el valor que tenga bval. Eso significa que siempre tienes que especificar bval al hacer uso de cualquiera de las opciones en el parámetro openinfo. Este error de documentación se corregirá en la próxima versión de Berkeley DB.

Eso aclara la situación con respecto a Berkeley DB en sí. ¿Qué pasa con DB_File? Bueno, el comportamiento definido en la cita anterior es bastante útil, así que DB_File se adhiere a él.

Eso significa que puedes especificar otras opciones (por ejemplo, cachesize) y aun así tener bval predeterminado a "\n" para registros de longitud variable, y espacio para registros de longitud fija.

Ten en cuenta también que la opción bval solo te permite especificar un único byte como delimitador.

Un Ejemplo Sencillo

Aquí hay un ejemplo sencillo que usa RECNO (si estás usando una versión de Perl anterior a 5.004_57 este ejemplo no funcionará -- ver "Métodos RECNO Adicionales" para una solución alternativa).

use warnings ;
use strict ;
use DB_File ;
my $filename = "text" ;
unlink $filename ;
my @h ;
tie @h, "DB_File", $filename, O_RDWR|O_CREAT, 0666, $DB_RECNO
    or die "Cannot open file 'text': $!\n" ;
# Add a few key/value pairs to the file
$h[0] = "orange" ;
$h[1] = "blue" ;
$h[2] = "yellow" ;
push @h, "green", "black" ;
my $elements = scalar @h ;
print "The array contains $elements entries\n" ;
my $last = pop @h ;
print "popped $last\n" ;
unshift @h, "white" ;
my $first = shift @h ;
print "shifted $first\n" ;
# Check for existence of a key
print "Element 1 Exists with value $h[1]\n" if $h[1] ;
# use a negative index
print "The last element is $h[-1]\n" ;
print "The 2nd last element is $h[-2]\n" ;
untie @h ;

Aquí está la salida del script:

The array contains 5 entries
popped black
shifted white
Element 1 Exists with value blue
The last element is green
The 2nd last element is yellow

Métodos RECNO Adicionales

Si estás usando una versión de Perl anterior a 5.004_57, la interfaz de array vinculado es bastante limitada. En el script de ejemplo anterior "push", "pop", "shift", "unshift" o determinar la longitud del array no funcionará con un array vinculado.

Para hacer la interfaz más útil para versiones antiguas de Perl, se proporcionan varios métodos con DB_File para simular las operaciones de array faltantes. Todos estos métodos se acceden a través del objeto devuelto por la llamada tie.

Aquí están los métodos:

$X->push(list) ;
Añade los elementos de "list" al final del array.
$value = $X->pop ;
Elimina y devuelve el último elemento del array.
$X->shift
Elimina y devuelve el primer elemento del array.
$X->unshift(list) ;
Añade los elementos de "list" al inicio del array.
$X->length
Devuelve el número de elementos en el array.
$X->splice(offset, length, elements);
Devuelve un splice del array.

Otro Ejemplo

Aquí hay un ejemplo más completo que hace uso de algunos de los métodos descritos anteriormente. También hace uso directo de la interfaz API (ver "LA INTERFAZ API").

use warnings ;
use strict ;
my (@h, $H, $file, $i) ;
use DB_File ;
use Fcntl ;
$file = "text" ;
unlink $file ;
$H = tie @h, "DB_File", $file, O_RDWR|O_CREAT, 0666, $DB_RECNO
    or die "Cannot open file $file: $!\n" ;
# first create a text file to play with
$h[0] = "zero" ;
$h[1] = "one" ;
$h[2] = "two" ;
$h[3] = "three" ;
$h[4] = "four" ;
# Imprimir los registros en orden.
#
# El método length es necesario aquí porque evaluar un array atado
# en un contexto escalar no devuelve el número de
# elementos del array.
print "\nORIGINAL\n" ;
foreach $i (0 .. $H->length - 1) {
    print "$i: $h[$i]\n" ;
}
# usar los métodos push y pop
$a = $H->pop ;
$H->push("last") ;
print "\nThe last record was [$a]\n" ;
# y los métodos shift y unshift
$a = $H->shift ;
$H->unshift("first") ;
print "The first record was [$a]\n" ;
# Usar la API para añadir un nuevo registro después del registro 2.
$i = 2 ;
$H->put($i, "Newbie", R_IAFTER) ;
# y un nuevo registro antes del registro 1.
$i = 1 ;
$H->put($i, "New One", R_IBEFORE) ;
# borrar el registro 3
$H->del(3) ;
# ahora imprimir los registros en orden inverso
print "\nREVERSE\n" ;
for ($i = $H->length - 1 ; $i >= 0 ; -- $i)
  { print "$i: $h[$i]\n" }
# lo mismo de nuevo, pero usando las funciones de la API
print "\nREVERSE again\n" ;
my ($s, $k, $v)  = (0, 0, 0) ;
for ($s = $H->seq($k, $v, R_LAST) ;
         $s == 0 ;
         $s = $H->seq($k, $v, R_PREV))
  { print "$k: $v\n" }
undef $H ;
untie @h ;

y esto es lo que produce:

ORIGINAL
0: zero
1: one
2: two
3: three
4: four
The last record was [four]
The first record was [zero]
REVERSE
5: last
4: three
3: Newbie
2: one
1: New One
0: first
REVERSE again
5: last
4: three
3: Newbie
2: one
1: New One
0: first

Notas:

1.
En lugar de iterar a través del array, @h así: esto: 
foreach $i (@h)

es necesario usar esto:

foreach $i (0 .. $H->length - 1)

o esto:

for ($a = $H->get($k, $v, R_FIRST) ;
     $a == 0 ;
     $a = $H->get($k, $v, R_NEXT) )
2.
Observa que ambas veces que se usó el "put" método el índice del registro se especificó usando una variable, $i, en lugar del valor literal mismo. Esto es porque "put" devolverá el número de registro de la línea insertada a través de ese parámetro.

LA INTERFAZ DE LA API

Además de acceder a Berkeley DB usando un hash o array atado, también es posible hacer uso directo de la mayoría de las funciones de la API definidas en la documentación de Berkeley DB.

Para hacer esto necesitas almacenar una copia del objeto devuelto por el tie.

$db = tie %hash, "DB_File", "filename" ;

Una vez que hayas hecho eso, puedes acceder a las funciones de la API de Berkeley DB como DB_File métodos directamente así:

$db->put($key, $value, R_NOOVERWRITE) ;

Importante: Si has guardado una copia del objeto devuelto por "tie", el archivo de base de datos subyacente no se cerrará hasta que tanto la variable atada sea desatada (untied) y todas las copias del objeto guardado sean destruidas.

use DB_File ;
$db = tie %hash, "DB_File", "filename"
    or die "Cannot tie filename: $!" ;
...
undef $db ;
untie %hash ;

Ver "The untie() Gotcha" para más detalles.

Todas las funciones definidas en dbopen están disponibles excepto close() y dbopen() misma. La DB_File interfaz de métodos para las funciones soportadas han sido implementadas para reflejar la forma en que funciona Berkeley DB siempre que sea posible. En particular, nota que:

  • Los métodos devuelven un valor de estado. Todos devuelven 0 en éxito. Todos devuelven -1 para significar un error y establecen $! al código de error exacto. El código de retorno 1 generalmente (pero no siempre) significa que la clave especificada no existía en la base de datos.

    Otros códigos de retorno están definidos. Ver abajo y en la documentación de Berkeley DB para detalles. La documentación de Berkeley DB debe usarse como la fuente definitiva.

  • Siempre que una función de Berkeley DB devuelve datos a través de uno de sus parámetros, el DB_File método equivalente hace exactamente lo mismo.
  • Si eres cuidadoso, es posible mezclar llamadas a la API con la interfaz de hash/array atado en el mismo fragmento de código. Aunque solo algunos de los métodos usados para implementar la interfaz atada usan actualmente el cursor, siempre debes asumir que el cursor ha sido cambiado cada vez que se usa la interfaz de hash/array atada. Como ejemplo, este código probablemente no hará lo que esperas: 
    $X = tie %x, 'DB_File', $filename, O_RDWR|O_CREAT, 0777, $DB_BTREE
    or die "Cannot tie $filename: $!" ;
# Obtener el primer par clave/valor y establecer el cursor
$X->seq($key, $value, R_FIRST) ;
# esta línea modificará el cursor
$count = scalar keys %x ;
# Obtener el segundo par clave/valor.
# oops, no lo hizo, obtuvo el último par clave/valor!
$X->seq($key, $value, R_NEXT) ;

    El código de arriba puede ser reorganizado para sortear el problema, así:

    $X = tie %x, 'DB_File', $filename, O_RDWR|O_CREAT, 0777, $DB_BTREE
    or die "Cannot tie $filename: $!" ;
# esta línea modificará el cursor
$count = scalar keys %x ;
# Obtener el primer par clave/valor y establecer el cursor
$X->seq($key, $value, R_FIRST) ;
# Obtener el segundo par clave/valor.
# funcionó esta vez.
$X->seq($key, $value, R_NEXT) ;

Todas las constantes definidas en dbopen para usar en los parámetros de flags en los métodos definidos abajo también están disponibles. Consulta la documentación de Berkeley DB para el significado preciso de los valores de los flags.

Abajo está una lista de los métodos disponibles.

$status = $X->get($key, $value [, $flags]) ;
Dada una clave ($key) este método lee el valor asociado a ella desde la base de datos. El valor leído de la base de datos es devuelto en el parámetro $value .

Si la clave no existe el método devuelve 1.

No hay flags definidos actualmente para este método.

$status = $X->put($key, $value [, $flags]) ;
Almacena el par clave/valor en la base de datos.

Si usas cualquiera de los flags R_IAFTER o R_IBEFORE, el $key parámetro tendrá el número de registro del par clave/valor insertado establecido.

Los flags válidos son R_CURSOR, R_IAFTER, R_IBEFORE, R_NOOVERWRITE y R_SETCURSOR.

$status = $X->del($key [, $flags]) ;
Elimina todos los pares clave/valor con la clave $key de la base de datos.

Un código de retorno de 1 significa que la clave solicitada no estaba en la base de datos.

R_CURSOR es el único flag válido en la actualidad.

$status = $X->fd ;
Devuelve el descriptor de archivo para la base de datos subyacente.

Ver "Locking: The Trouble with fd" para una explicación de por qué no deberías usar "fd" para bloquear tu base de datos.

$status = $X->seq($key, $value, $flags) ;
Esta interfaz permite la recuperación secuencial desde la base de datos. Ver dbopen para todos los detalles.

Tanto el $key como el $value parámetros serán establecidos al par clave/valor leído de la base de datos.

El parámetro flags es obligatorio. Los valores de flag válidos son R_CURSOR, R_FIRST, R_LAST, R_NEXT y R_PREV.

$status = $X->sync([$flags]) ;
Vuelca (flush) cualquier buffer en caché al disco.

R_RECNOSYNC es el único flag válido en la actualidad.

FILTROS DBM

Un Filtro DBM es un fragmento de código que se usa cuando siempre quieres hacer la misma transformación a todas las claves y/o valores en una base de datos DBM. Un ejemplo es cuando necesitas codificar tus datos en UTF-8 antes de escribir a la base de datos y luego decodificar el UTF-8 al leer desde el archivo de la base de datos.

Hay dos formas de usar un Filtro DBM.

1.
Usando la API de bajo nivel definida abajo.
2.
Usando el módulo DBM_Filter. Este módulo oculta la complejidad de la API definida abajo y viene con una serie de filtros "predefinidos" que cubren algunos de los casos de uso comunes.

Se recomienda el uso del módulo DBM_Filter.

API de Bajo Nivel de Filtro DBM

Hay cuatro métodos asociados con los Filtros DBM. Todos funcionan de manera idéntica, y cada uno se usa para instalar (o desinstalar) un solo Filtro DBM. Cada uno espera un solo parámetro, a saber, una referencia a un sub. La única diferencia entre ellos es el lugar donde se instala el filtro.

Para resumir:

filter_store_key
Si un filtro ha sido instalado con este método, será invocado cada vez que escribas una clave a una base de datos DBM.
filter_store_value
Si un filtro ha sido instalado con este método, será invocado cada vez que escribas un valor a una base de datos DBM.
filter_fetch_key
Si un filtro ha sido instalado con este método, será invocado cada vez que leas una clave de una base de datos DBM.
filter_fetch_value
Si un filtro ha sido instalado con este método, será invocado cada vez que leas un valor de una base de datos DBM.

Puedes usar cualquier combinación de los métodos, desde ninguno, hasta los cuatro.

Todos los métodos de filtro devuelven el filtro existente, si está presente, o "undef" si no.

Para eliminar un filtro pasa "undef" a él.

El Filtro

Cuando cada filtro es llamado por Perl, una copia local de $_ contendrá la clave o el valor a ser filtrado. El filtrado se logra modificando el contenido de $_. El código de retorno del filtro es ignorado.

Un Ejemplo -- el problema de la terminación NULL.

Considera el siguiente escenario. Tienes una base de datos DBM tque necesitas compartir con una aplicación de terceros en C. La aplicación de C asume que todas las claves y valores están terminados en NULL. Desafortunadamente, cuando Perl escribe en bases de datos DBM, no usa terminación en NULL, por lo que tu aplicación Perl tendrá que gestionar la terminación en NULL por sí misma. Cuando escribas en la base de datos, tendrás que usar algo como esto:

$hash{"$key\0"} = "$value\0" ;

De manera similar, el NULL debe tenerse en cuenta cuando estés considerando la longitud de las claves/valores existentes.

Sería mucho mejor si pudieras ignorar el problema de las terminaciones en NULL en el código principal de la aplicación y tener un mecanismo que automáticamente añadiera el NULL final a todas las claves y valores cada vez que escribes en la base de datos y que los eliminara cuando lees de la base de datos. Como seguro que ya te has imaginado, este es un problema que los Filtros DBM pueden resolver muy fácilmente.

use warnings ;
use strict ;
use DB_File ;
my %hash ;
my $filename = "filt" ;
unlink $filename ;
my $db = tie %hash, 'DB_File', $filename, O_CREAT|O_RDWR, 0666, $DB_HASH
  or die "Cannot open $filename: $!\n" ;
# Install DBM Filters
$db->filter_fetch_key  ( sub { s/\0$//    } ) ;
$db->filter_store_key  ( sub { $_ .= "\0" } ) ;
$db->filter_fetch_value( sub { s/\0$//    } ) ;
$db->filter_store_value( sub { $_ .= "\0" } ) ;
$hash{"abc"} = "def" ;
my $a = $hash{"ABC"} ;
# ...
undef $db ;
untie %hash ;

Con suerte, el contenido de cada uno de los filtros debería ser autoexplicativo. Ambos filtros "fetch" (obtener) eliminan el NULL final, y ambos filtros "store" (almacenar) añaden un NULL final.

Otro ejemplo -- La clave es un int de C.

Aquí hay otro ejemplo de la vida real. Por defecto, cada vez que Perl escribe en una base de datos DBM, siempre escribe la clave y el valor como cadenas. Así que cuando usas esto:

$hash{12345} = "something" ;

la clave 12345 se almacenará en la base de datos DBM como la cadena de 5 bytes "12345". Si realmente quieres que la clave se almacene en la base de datos DBM como un int de C, tendrás que usar "pack" al escribir, y "unpack" al leer.

Aquí hay un Filtro DBM que lo hace:

use warnings ;
use strict ;
use DB_File ;
my %hash ;
my $filename = "filt" ;
unlink $filename ;
my $db = tie %hash, 'DB_File', $filename, O_CREAT|O_RDWR, 0666, $DB_HASH
  or die "Cannot open $filename: $!\n" ;
$db->filter_fetch_key  ( sub { $_ = unpack("i", $_) } ) ;
$db->filter_store_key  ( sub { $_ = pack ("i", $_) } ) ;
$hash{123} = "def" ;
# ...
undef $db ;
untie %hash ;

Esta vez solo se han usado dos filtros -- solo necesitamos manipular el contenido de la clave, así que no fue necesario instalar ningún filtro de valor.

SUGERENCIAS Y CONSEJOS

Bloqueo: El problema con fd

Hasta la versión 1.72 de este módulo, la técnica recomendada para bloquear DB_File las bases de datos era hacer flock al filehandle devuelto por la función "fd". Desafortunadamente, se ha demostrado que esta técnica es fundamentalmente defectuosa (Créditos a David Harris por rastrear esto). ¡Úsala bajo tu propio riesgo!

La técnica de bloqueo era la siguiente.

$db = tie(%db, 'DB_File', 'foo.db', O_CREAT|O_RDWR, 0644)
    || die "dbcreat foo.db $!";
$fd = $db->fd;
open(DB_FH, "+<&=$fd") || die "dup $!";
flock (DB_FH, LOCK_EX) || die "flock: $!";
...
$db{"Tom"} = "Jerry" ;
...
flock(DB_FH, LOCK_UN);
undef $db;
untie %db;
close(DB_FH);

En términos simples, esto es lo que sucede:

1.
Usa "tie" para abrir la base de datos.
2.
Bloquea la base de datos con fd y flock.
3.
Lee y escribe en la base de datos.
4.
Desbloquea y cierra la base de datos.

Aquí está el núcleo del problema. Un efecto secundario de abrir la DB_File base de datos en el paso 2 es que un bloque inicial de la base de datos se leerá del disco y se pondrá en caché en la memoria.

Para ver por qué esto es un problema, considera lo que puede suceder cuando dos procesos, digamos "A" y "B", ambos quieren actualizar la misma DB_File base de datos usando los pasos de bloqueo descritos anteriormente. Asume que el proceso "A" ya ha abierto la base de datos y tiene un bloqueo de escritura, pero no ha actualizado la base de datos realmente todavía (ha terminado el paso 2, pero no ha comenzado el paso 3 todavía). Ahora el proceso "B" intenta abrir la misma base de datos - el paso 1 tendrá éxito, pero se bloqueará en el paso 2 hasta que el proceso "A" libere el bloqueo. Lo importante a notar aquí es que en este punto en el tiempo ambos procesos tendrán bloques iniciales idénticos de la base de datos en caché.

Ahora el proceso "A" actualiza la base de datos y ocurre que cambia algunos de los datos contenidos en el búfer inicial. El proceso "A" termina, vaciando todos los datos en caché al disco y liberando el bloqueo de la base de datos. En este punto, la base de datos en el disco reflejará correctamente los cambios realizados por el proceso "A".

Con el bloqueo liberado, el proceso "B" ahora puede continuar. También actualiza la base de datos y desafortunadamente también modifica los datos que estaban en su búfer inicial. Una vez que esos datos se vacíen al disco, sobrescribirán algunos/todos de los cambios que el proceso "A" hizo a la base de datos.

El resultado de este escenario es, en el mejor de los casos, una base de datos que no contiene lo que esperas. En el peor de los casos, la base de datos se corromperá.

Lo anterior no sucederá cada vez que procesos en competencia actualicen la misma DB_File base de datos, pero ilustra por qué la técnica no debería usarse.

Formas seguras de bloquear una base de datos

A partir de la versión 2.x, Berkeley DB tiene soporte interno para el bloqueo. El módulo compañero de este, BerkeleyDB https://metacpan.org/pod/BerkeleyDB, proporciona una interfaz a esta funcionalidad de bloqueo. Si estás serio sobre bloquear bases de datos Berkeley DB, recomiendo fuertemente usar BerkeleyDB https://metacpan.org/pod/BerkeleyDB.

Si usar BerkeleyDB https://metacpan.org/pod/BerkeleyDB no es una opción, hay un número de módulos disponibles en CPAN que pueden usarse para implementar el bloqueo. Cada uno implementa el bloqueo de manera diferente y tiene diferentes objetivos en mente. Por lo tanto, vale la pena conocer la diferencia, para que puedas elegir el correcto para tu aplicación. Aquí están los tres envoltorios de bloqueo:

Tie::DB_Lock
Un DB_File envoltorio que crea copias del archivo de la base de datos para acceso de lectura, de modo que tienes una especie de sistema de lectura concurrente con multiversión. Sin embargo, las actualizaciones siguen siendo seriales. Úsalo para bases de datos donde las lecturas pueden ser largas y pueden ocurrir problemas de consistencia.
Tie::DB_LockFile
Un DB_File envoltorio que tiene la capacidad de bloquear y desbloquear la base de datos mientras se está usando. Evita el problema de tie-antes-de-flock simplemente volviendo a hacer tie de la base de datos cuando obtienes o sueltas un bloqueo. Debido a la flexibilidad de soltar y re-adquirir el bloqueo en medio de una sesión, esto puede moldearse en un sistema que funcionará con actualizaciones y/o lecturas largas si la aplicación sigue las sugerencias en la documentación POD.
DB_File::Lock
Un envoltorio de DB_File extremadamente ligero que simplemente hace flock a un archivo de bloqueo antes de hacer tie de la base de datos y suelta el bloqueo después del untie. Permite usar el mismo archivo de bloqueo para múltiples bases de datos para evitar problemas de interbloqueo, si se desea. Úsalo para bases de datos donde las actualizaciones o lecturas son rápidas y la semántica simple de flock es suficiente.

Compartiendo bases de datos con aplicaciones de C

No hay ninguna razón técnica por la que una base de datos Berkeley DB no pueda ser compartida por una aplicación Perl y una de C.

La gran mayoría de los problemas reportados en esta área se reducen al hecho de que las cadenas de C están terminadas en NULL, mientras que las cadenas de Perl no lo están. Ver "DBM FILTERS" para una forma genérica de solucionar este problema.

Aquí hay un ejemplo real. Netscape 2.0 guarda un registro de las ubicaciones que visitas junto con la última vez que las visitaste en una base de datos DB_HASH. Esto usualmente se almacena en el archivo ~/.netscape/history.db. El campo clave en la base de datos es la cadena de ubicación y el campo valor es la última vez que se visitó la ubicación almacenada como un valor binario de 4 bytes.

Si no lo has adivinado ya, la cadena de ubicación se almacena con un NULL final. Esto significa que necesitas tener cuidado al acceder a la base de datos.

Aquí hay un fragmento de código que está vagamente basado en el script de Tom Christiansen ggh (disponible desde tu archivo CPAN más cercano en authors/id/TOMC/scripts/nshist.gz).

use warnings ;
use strict ;
use DB_File ;
use Fcntl ;
my ($dotdir, $HISTORY, %hist_db, $href, $binary_time, $date) ;
$dotdir = $ENV{HOME} || $ENV{LOGNAME};
$HISTORY = "$dotdir/.netscape/history.db";
tie %hist_db, 'DB_File', $HISTORY
    or die "Cannot open $HISTORY: $!\n" ;;
# Dump the complete database
while ( ($href, $binary_time) = each %hist_db ) {
    # remove the terminating NULL
    $href =~ s/\x00$// ;
    # convert the binary time into a user friendly string
    $date = localtime unpack("V", $binary_time);
    print "$date $href\n" ;
}
# check for the existence of a specific key
# remember to add the NULL
if ( $binary_time = $hist_db{"http://mox.perl.com/\x00"} ) {
    $date = localtime unpack("V", $binary_time) ;
    print "Last visited mox.perl.com on $date\n" ;
}
else {
    print "Never visited mox.perl.com\n"
}
untie %hist_db ;

El untie() Gotcha (Trampa)

Si haces uso de la API de Berkeley DB, es muy fuertemente recomendable que leas "The untie Gotcha" en perltie.

Incluso si actualmente no haces uso de la interfaz API, todavía vale la pena leerlo.

Aquí hay un ejemplo que ilustra el problema desde una perspectiva de DB_File :

use DB_File ;
use Fcntl ;
my %x ;
my $X ;
$X = tie %x, 'DB_File', 'tst.fil' , O_RDWR|O_TRUNC
    or die "Cannot tie first time: $!" ;
$x{123} = 456 ;
untie %x ;
tie %x, 'DB_File', 'tst.fil' , O_RDWR|O_CREAT
    or die "Cannot tie second time: $!" ;
untie %x ;

Al ejecutarlo, el script producirá este mensaje de error:

Cannot tie second time: Invalid argument at bad.file line 14.

Aunque el mensaje de error anterior se refiere a la segunda tie() declaración en el script, la fuente del problema está realmente en la untie() declaración que la precede.

Después de haber leído perltie, probablemente ya habrás adivinado que el error es causado por la copia extra del objeto atado almacenada en $X. Si no lo has hecho, entonces el problema se reduce a el hecho de que el DB_File destructor, DESTROY, no será llamado hasta que todas las referencias al objeto atado sean destruidas. Tanto la variable atada, %x, y $X anterior mantienen una referencia al objeto. La llamada a untie() destruirá la primera, pero $X todavía mantiene una referencia válida, por lo que el destructor no será llamado y el archivo de base de datos tst.fil permanecerá abierto. El hecho de que Berkeley DB luego informe el intento de abrir una base de datos que ya está abierta a través del "Invalid argument" genérico no ayuda.

Si ejecutas el script con la "-w" bandera el mensaje de error se convierte en:

untie attempted while 1 inner references still exist at bad.file line 12.
Cannot tie second time: Invalid argument at bad.file line 14.

lo cual señala el problema real. Finalmente el script puede ser modificado para arreglar el problema original destruyendo el objeto API antes del untie:

...
$x{123} = 456 ;
undef $X ;
untie %x ;
$X = tie %x, 'DB_File', 'tst.fil' , O_RDWR|O_CREAT
...

PREGUNTAS FRECUENTES

¿Por qué hay código Perl en mi base de datos?

Si miras el contenido de un archivo de base de datos creado por DB_File, a veces puede haber parte de un script Perl incluido en él.

Esto sucede porque Berkeley DB usa memoria dinámica para asignar búferes que posteriormente serán escritos en el archivo de base de datos. Al ser dinámica, la memoria podría haber sido usada para cualquier cosa antes de que DB la asignara. Como Berkeley DB no limpia la memoria una vez que ha sido asignada, las partes no utilizadas contendrán basura aleatoria. En el caso en que un script Perl sea escrito en la base de datos, la basura aleatoria corresponderá a un área de memoria dinámica que fue usada durante la compilación del script.

A menos que no te guste la posibilidad de que haya parte de tus scripts Perl incrustados en un archivo de base de datos, esto no es nada de qué preocuparse.

¿Cómo almaceno estructuras de datos complejas con DB_File?

Aunque DB_File no puede hacer esto directamente, hay un módulo que puede superponerse transparentemente sobre DB_File para lograr esta hazaña.

Echa un vistazo al módulo MLDBM, disponible en CPAN en el directorio modules/by-module/MLDBM.

¿Qué significa "wide character in subroutine entry"?

Normalmente obtendrás este mensaje si estás trabajando con datos UTF-8 y quieres leerlos/escribirlos desde/hacia un archivo de base de datos Berkeley DB.

La forma más fácil de lidiar con este problema es usar el "utf8" predefinido DBM_Filter (ver DBM_Filter) que fue diseñado para lidiar con esta situación.

El ejemplo de abajo muestra lo que necesitas si tanto la clave como el valor se esperan que estén en UTF-8.

use DB_File;
use DBM_Filter;
my $db = tie %h, 'DB_File', '/tmp/try.db', O_CREAT|O_RDWR, 0666, $DB_BTREE;
$db->Filter_Key_Push('utf8');
$db->Filter_Value_Push('utf8');
my $key = "\N{LATIN SMALL LETTER A WITH ACUTE}";
my $value = "\N{LATIN SMALL LETTER E WITH ACUTE}";
$h{ $key } = $value;

¿Qué significa "Invalid Argument"?

Obtendrás este mensaje de error cuando uno de los parámetros en la "tie" llamada es incorrecto. Desafortunadamente hay bastantes parámetros que pueden estar mal, por lo que puede ser difícil averiguar cuál es.

Aquí hay un par de posibilidades:

1.
Intentar reabrir una base de datos sin cerrarla.
2.
Usar la bandera O_WRONLY.

¿Qué significa "Bareword 'DB_File' not allowed"?

Encontrarás este mensaje de error particular cuando tienes la "strict 'subs'" pragma (o el pragma strict completo) en tu script. Considera este script:

use warnings ;
use strict ;
use DB_File ;
my %x ;
tie %x, DB_File, "filename" ;

Ejecutarlo produce el error en cuestión:

Bareword "DB_File" not allowed while "strict subs" in use

Para evitar el error, coloca la palabra "DB_File" entre comillas simples o dobles, así:

tie %x, "DB_File", "filename" ;

Aunque podría parecer un verdadero dolor, realmente vale la pena el esfuerzo de tener un "use strict" en todos tus scripts.

DISPONIBILIDAD

DB_File viene con la distribución estándar de código fuente de Perl. Busca en el directorio ext/DB_File. Dada la cantidad de tiempo entre las versiones de Perl, la versión que se incluye con Perl probablemente esté desactualizada, por lo que la versión más reciente siempre se puede encontrar en CPAN (ver "CPAN" en perlmodlib para detalles), en el directorio modules/by-module/DB_File.

DB_File está diseñado para funcionar con cualquier versión de Berkeley DB, pero está limitado a la funcionalidad proporcionada por la versión 1. Si quieres hacer uso de las nuevas características disponibles en Berkeley DB 2.x, o superior, usa el módulo de Perl BerkeleyDB https://metacpan.org/pod/BerkeleyDB en su lugar.

El sitio web oficial de Berkeley DB es http://www.oracle.com/technology/products/berkeley-db/db/index.html. Todas las versiones de Berkeley DB están disponibles allí.

Alternativamente, la versión 1 de Berkeley DB está disponible en tu archivo CPAN más cercano en src/misc/db.1.85.tar.gz.
