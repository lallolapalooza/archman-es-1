NOMBRE

DBI::Profile - Perfilado de rendimiento y creación de benchmarks para el DBI

SINOPSIS

La forma más fácil de habilitar el perfilado de DBI es establecer la variable de entorno DBI_PROFILE a 2 y luego ejecutar su código como de costumbre:

DBI_PROFILE=2 prog.pl

Esto perfilará su programa y luego emitirá un resumen textual agrupado por consulta cuando el programa finalice. También puede habilitar el perfilado estableciendo el atributo Profile de cualquier manejador de DBI:

$dbh->{Profile} = 2;

Luego, el resumen se imprimirá cuando el manejador sea destruido.

Son posibles muchos otros valores además de - ver "HABILITAR UN PERFIL" más abajo.

DESCRIPCIÓN

El módulo DBI::Profile proporciona una interfaz sencilla para recopilar y informar datos de rendimiento y benchmarks del DBI.

Para una interfaz más elaborada, adecuada para programas más grandes, ver DBI::ProfileDumper y dbiprof. Para aplicaciones de Apache/mod_perl ver DBI::ProfileDumper::Apache.

RESUMEN

La recopilación de datos de rendimiento para el DBI se basa en varios conceptos que es importante entender claramente.

Despacho de métodos
Cada llamada a un método en un manejador de DBI pasa por una única función de 'despacho' que gestiona todos los aspectos comunes de las llamadas a métodos de DBI, como el manejo del atributo RaiseError.
Recopilación de datos
Si el perfilado está habilitado para un manejador, el código de despacho toma una marca de tiempo de alta resolución poco después de ser invocado. Luego, después de llamar al método correspondiente y justo antes de retornar, toma otra marca de tiempo de alta resolución y llama a una función para registrar la información. A esa función se le pasan las dos marcas de tiempo junto con el manejador de DBI y el nombre del método que fue llamado. Ese dato sobre una sola llamada a un método de DBI se denomina una muestra de perfil.
Filtrado de datos
Si la llamada al método fue invocada por el DBI o por un controlador, la llamada se ignora para el perfilado porque el tiempo empleado será contabilizado por la llamada 'externa' original de su código.

Por ejemplo, las llamadas que el método selectrow_arrayref() hace a prepare() y execute() etc. no se cuentan individualmente porque el tiempo empleado en esos métodos se asignará al selectrow_arrayref() método cuando retorne. Si esto no se hiciera, sería muy fácil contar doble el tiempo empleado dentro del DBI.

Árbol de almacenamiento de datos
Los datos del perfil se acumulan como 'hojas en un árbol'. El 'camino' a través de las ramas del árbol hasta una hoja particular se determina dinámicamente para cada muestra. Esta es una característica clave del perfilado de DBI.

Para cada llamada a un método perfilada, el DBI recorre el Path y usa cada valor en el Path para entrar y hacer crecer el árbol de Data.

Por ejemplo, si el Path es

[ 'foo', 'bar', 'baz' ]

entonces los nuevos datos de la muestra de perfil se fusionarán en el árbol en

$h->{Profile}->{Data}->{foo}->{bar}->{baz}

Pero no es muy útil fusionar todos los datos de la llamada en un solo nodo hoja (excepto para obtener un total general de 'tiempo empleado dentro del DBI'). Es más común querer que el Path incluya valores dinámicos como el texto de la sentencia actual y/o el nombre del método llamado para mostrar en qué se empleó el tiempo dentro del DBI.

El Path puede contener algunos valores 'mágicos' que son reemplazados automáticamente por valores dinámicos correspondientes cuando se usan. Estos valores mágicos siempre comienzan con un carácter de puntuación.

Por ejemplo, un valor de '"!MethodName"' en el Path hace que la entrada correspondiente en Data sea el nombre del método que fue llamado. Por ejemplo, si el Path fuera:

[ 'foo', '!MethodName', 'bar' ]

y se llamara al método selectall_arrayref() , entonces los datos de la muestra de perfil para esa llamada se fusionarán en el árbol en:

$h->{Profile}->{Data}->{foo}->{selectall_arrayref}->{bar}
Datos del perfil
Los datos del perfil se almacenan en las 'hojas' del árbol como referencias a un array de valores numéricos. Por ejemplo: 
[
  106,                  # 0: conteo de muestras en este nodo
  0.0312958955764771,   # 1: duración total
  0.000490069389343262, # 2: primera duración
  0.000176072120666504, # 3: duración más corta
  0.00140702724456787,  # 4: duración más larga
  1023115819.83019,     # 5: hora de la primera muestra
  1023115819.86576,     # 6: hora de la última muestra
]

Después de la primera muestra, las muestras posteriores siempre actualizan los elementos 0, 1 y 6, y pueden actualizar 3 o 4 dependiendo de la duración de la llamada muestreada.

HABILITAR UN PERFIL

El perfilado se habilita para un manejador asignando al atributo Profile. Por ejemplo:

$h->{Profile} = DBI::Profile->new();

El atributo Profile contiene una referencia bendita a un objeto hash que contiene los datos del perfil y los atributos relacionados con él.

Se espera que la clase a la que el objeto Profile es bendito proporcione al menos un método DESTROY que volcará los datos del perfil en el manejador de archivo de traza de DBI (STDERR por defecto).

Todos estos ejemplos tienen el mismo efecto entre sí:

$h->{Profile} = 0;
$h->{Profile} = "/DBI::Profile";
$h->{Profile} = DBI::Profile->new();
$h->{Profile} = {};
$h->{Profile} = { Path => [] };

De manera similar, estos ejemplos tienen el mismo efecto entre sí:

$h->{Profile} = 6;
$h->{Profile} = "6/DBI::Profile";
$h->{Profile} = "!Statement:!MethodName/DBI::Profile";
$h->{Profile} = { Path => [ '!Statement', '!MethodName' ] };

Si se da una referencia a hash no bendita, el módulo DBI::Profile es automáticamente "require"'d y la referencia es bendita en esa clase.

Si se da una cadena, se procesa de esta manera:

($path, $module, $args) = split /\//, $string, 3
@path = split /:/, $path
@args = split /:/, $args
eval "require $module" if $module
$module ||= "DBI::Profile"
$module->new( Path => \@Path, @args )

Así que el primer valor se usa para seleccionar el Path a usar (ver más abajo). El segundo valor, si está presente, se usa como el nombre de un módulo que será cargado y su método "new" será llamado. Si no está presente, por defecto es DBI::Profile. Cualquier otro valor se pasa como argumento al método "new" . Por ejemplo: ""2/DBIx::OtherProfile/Foo:42"".

Se pueden usar números como una forma abreviada de habilitar valores comunes de Path. La forma más sencilla de explicar cómo se interpretan los valores es mostrar el código:

push @Path, "DBI"           if $path_elem & 0x01;
push @Path, "!Statement"    if $path_elem & 0x02;
push @Path, "!MethodName"   if $path_elem & 0x04;
push @Path, "!MethodClass"  if $path_elem & 0x08;
push @Path, "!Caller2"      if $path_elem & 0x10;

Así que "2" es lo mismo que "!Statement" y "6" (2+4) es lo mismo que "!Statement:!Method". Esos son los dos valores más comúnmente usados. Usar un número negativo invertirá el camino. Así que "-6" agrupará por nombre de método y luego por sentencia.

La división y el análisis de los valores de cadena asignados al atributo Profile puede parecer un poco extraño, pero hay una buena razón para ello. Recuerde que los atributos pueden estar incrustados en la cadena del Nombre de Fuente de Datos que puede pasarse a un script como un parámetro. Por ejemplo:

dbi:DriverName(Profile=>2):dbname
dbi:DriverName(Profile=>{Username}:!Statement/MyProfiler/Foo:42):dbname

Y también, si la variable de entorno "DBI_PROFILE" está establecida, el DBI organiza que cada manejador de controlador comparta el mismo objeto de perfil. Cuando perl finalice, se generará un único resumen de perfil que reflejará (tan cerca de lo práctico) el uso total del DBI por la aplicación.

EL OBJETO PERFIL

El núcleo de DBI espera que el valor del atributo Profile sea una referencia a hash y si los siguientes valores no existen, los creará según sea necesario:

Datos

Una referencia a un hash que contiene los datos del perfil recopilados.

Ruta

El valor Ruta es una referencia a un arreglo. Cada elemento controla el valor a usar en el nivel correspondiente del árbol de Datos del perfil.

Si el valor de Ruta es cualquier cosa que no sea una referencia a un arreglo, se trata como si fuera:

[ '!Statement' ]

Los elementos del arreglo Ruta pueden ser de uno de los siguientes tipos:

Constante Especial

!Statement

Usa el texto de la sentencia actual. Típicamente ese es el valor del atributo Sentencia para el manejador con el que se llamó al método. Algunos métodos, como commit() y rollback(), no están relacionados con una sentencia en particular. Para esos métodos !Statement registra una cadena vacía.

Para los manejadores de sentencias esto es siempre simplemente la cadena que se dio a prepare() cuando se creó el manejador. Para los manejadores de base de datos esta es la sentencia que fue preparada o ejecutada por última vez en ese manejador de base de datos. Eso puede llevar a un poco de 'imprecisión' porque, por ejemplo, las llamadas al método quote() para construir una nueva sentencia típicamente estarán asociadas con la sentencia anterior. En la práctica esto no es un problema significativo y el mecanismo de Ruta dinámica se puede usar para configurar tus propias reglas.

!MethodName

Usa el nombre del método DBI al que se relaciona la muestra del perfil.

!MethodClass

Usa el nombre completamente calificado del método DBI, incluyendo el paquete, al que se relaciona la muestra del perfil. Esto te muestra dónde fue implementado el método. Por ejemplo:

'DBD::_::db::selectrow_arrayref' =>
    0.022902s
'DBD::mysql::db::selectrow_arrayref' =>
    2.244521s / 99 = 0.022445s avg (first 0.022813s, min 0.022051s, max 0.028932s)

El "DBD::_::db::selectrow_arrayref" muestra que el controlador ha heredado el método selectrow_arrayref proporcionado por el DBI.

Pero notarás que solo hay una llamada a DBD::_::db::selectrow_arrayref pero otras 99 a DBD::mysql::db::selectrow_arrayref. Actualmente la primera llamada no registra la verdadera ubicación. Eso puede cambiar.

!Caller

Usa una cadena que muestra el nombre del archivo y el número de línea del código que llama al método.

!Caller2

Usa una cadena que muestra el nombre del archivo y el número de línea del código que llama al método, como con !Caller, pero también incluye el nombre del archivo y el número de línea del código que llamó a ese. Se omiten las llamadas de los paquetes DBI:: y DBD::.

!File

Igual que !Caller arriba excepto que solo se incluye el nombre del archivo, no el número de línea.

!File2

Igual que !Caller2 arriba excepto que solo se incluyen los nombres de archivo, no el número de línea.

!Time

Usa el valor actual de time(). Raramente usado. Ver el más útil "!Time~N" abajo.

!Time~N

Donde "N" es un entero. Usa el valor actual de time() pero con precisión reducida. El valor usado se determina de esta manera:

int( time() / N ) * N

Esta es una forma útil de segregar un perfil en intervalos de tiempo. Por ejemplo:

[ '!Time~60', '!Statement' ]

Referencia a Código

La subrutina recibe el manejador en el que fue llamada y el nombre del método DBI. La Sentencia actual está en $_. La cadena de la sentencia no debe ser modificada, así que la mayoría de las subs comienzan con "local $_ = $_;".

La lista de valores que retorna se usa en ese punto de la Ruta del Perfil. Cualquier valor indefinido se trata como la cadena ""undef"".

La sub puede 'vetar' (rechazar) una muestra del perfil incluyendo una referencia a undef ("\undef") en la lista retornada. Eso puede ser útil cuando quieres perfilar solo las sentencias que coinciden con cierto patrón, o perfilar solo ciertos métodos.

Especificador de Subrutina

Un elemento de Ruta que comienza con '"&"' se trata como el nombre de una subrutina en el espacio de nombres DBI::ProfileSubs y se reemplaza con la referencia de código correspondiente.

Actualmente esto solo funciona cuando la Ruta es especificada por la variable de entorno "DBI_PROFILE" .

También, actualmente, la única subrutina en el espacio de nombres DBI::ProfileSubs es '&norm_std_n3'. Esa es una subrutina muy útil al perfilar código que no usa marcadores de posición. Ver DBI::ProfileSubs para más información.

Especificador de Atributo

Una cadena encerrada en llaves, como '"{Username}"', especifica que el valor actual del atributo correspondiente del manejador de base de datos debe usarse en ese punto de la Ruta.

Referencia a un Escalar

Especifica que el valor actual del escalar referenciado sea usado en ese punto de la Ruta. Esto proporciona una forma eficiente de obtener valores 'contextuales' en tu perfil.

Otros Valores

Cualquier otro valor se convierte a cadena y se usa literalmente.

(Las referencias, y los valores que comienzan con caracteres de puntuación, están reservados.)

INFORMES

Formato del Informe

Los datos del perfil acumulados actualmente pueden ser formateados y emitidos usando

print $h->{Profile}->format;

Para descartar los datos del perfil y empezar a recopilar datos nuevos puedes hacer:

$h->{Profile}->{Data} = undef;

El formato de resultados por defecto se ve así:

DBI::Profile: 0.001015s 42.7% (5 calls) programname @ YYYY-MM-DD HH:MM:SS
'' =>
    0.000024s / 2 = 0.000012s avg (first 0.000015s, min 0.000009s, max 0.000015s)
'SELECT mode,size,name FROM table' =>
    0.000991s / 3 = 0.000330s avg (first 0.000678s, min 0.000009s, max 0.000678s)

Lo cual muestra el tiempo total pasado dentro del DBI, con un conteo del número total de llamadas a métodos y el nombre del script que se está ejecutando, luego una versión formateada del árbol de datos del perfil.

Si los resultados están siendo formateados cuando el proceso perl está saliendo (lo cual es usualmente el caso cuando se usa la variable de entorno DBI_PROFILE) entonces también se muestra el porcentaje de tiempo que el proceso pasó dentro del DBI. Si el proceso no está saliendo entonces el porcentaje se calcula usando el tiempo entre la primera y la última llamada al DBI.

En el ejemplo de arriba las rutas en el árbol son solo de un nivel de profundidad y usan el texto de la Sentencia como valor (ese es el comportamiento por defecto).

Los datos del perfil fusionados en las 'hojas' del árbol se presentan como tiempo total pasado, conteo, tiempo promedio pasado (que es simplemente el tiempo total dividido por el conteo), luego el tiempo pasado en la primera llamada, el tiempo pasado en la llamada más rápida, y finalmente el tiempo pasado en la llamada más lenta.

Los tiempos 'avg', 'first', 'min' y 'max' no son particularmente útiles cuando la ruta de datos del perfil solo contiene el texto de la sentencia. Aquí hay un extracto de un ejemplo más detallado usando tanto el texto de la sentencia como el nombre del método en la ruta:

'SELECT mode,size,name FROM table' =>
    'FETCH' =>
        0.000076s
    'fetchrow_hashref' =>
        0.036203s / 108 = 0.000335s avg (first 0.000490s, min 0.000152s, max 0.002786s)

Aquí puedes ver que el 'avg', 'first', 'min' y 'max' para las 108 llamadas a fetchrow_hashref() se vuelven bastante más interesantes. También los datos para FETCH solo muestran un valor de tiempo porque solo fue llamado una vez.

Actualmente los datos del perfil se emiten ordenados por los nombres de las ramas. Eso puede cambiar en una versión posterior para que los nodos hoja sean ordenados por el tiempo total por nodo hoja.

Destino del Informe

El método por defecto de informar es que el método DESTROY del objeto Perfil formatee los resultados y los escriba usando:

DBI->trace_msg($results, 0);  # ver $ON_DESTROY_DUMP abajo

para escribirlos en el manejador de archivo de traza del DBI trace() (que por defecto es STDERR). Para dirigir el manejador de archivo de traza del DBI a escribir en un archivo sin habilitar el trazado, el método trace() puede ser llamado con un nivel de traza de 0. Por ejemplo:

DBI->trace(0, $filename);

El mismo efecto se puede lograr sin cambiar el código configurando la variable de entorno "DBI_TRACE" a "0=filename".

La $DBI::Profile::ON_DESTROY_DUMP variable contiene una referencia a código que es llamada para realizar la emisión de los resultados formateados. El valor por defecto es:

$ON_DESTROY_DUMP = sub { DBI->trace_msg($results, 0) };

Aparte de facilitar el envío del volcado a otro lugar, también puede ser útil como una forma sencilla de deshabilitar el volcado de resultados.

MANEJADORES HIJOS

Los manejadores hijos heredan una referencia al valor del atributo Perfil de su padre. Así que si el perfilado está habilitado para un manejador de base de datos, entonces por defecto los manejadores de sentencias creados a partir de él todos contribuyen al mismo árbol de datos del perfil fusionado.

MÉTODOS DEL OBJETO PERFIL

format

Ver "INFORMES".

as_node_path_list

@ary = $dbh->{Profile}->as_node_path_list();
@ary = $dbh->{Profile}->as_node_path_list($node, $path);

Retorna los datos recopilados ($dbh->{Profile}{Data}) reestructurados en una lista de referencias a arreglos, una para cada nodo hoja en el árbol de Datos. Esta estructura 'plana' es a menudo mucho más simple para que las aplicaciones trabajen con ella.

El primer elemento de cada referencia a arreglo es una referencia al nodo hoja. Los elementos restantes son el 'camino' a través del árbol de datos hasta ese nodo.

Por ejemplo, dado un árbol de datos como este:

{key1a}{key2a}[node1]
{key1a}{key2b}[node2]
{key1b}{key2a}{key3a}[node3]

El as_node_path_list() método retornará esta lista:

[ [node1], 'key1a', 'key2a' ]
[ [node2], 'key1a', 'key2b' ]
[ [node3], 'key1b', 'key2a', 'key3a' ]

Los nodos están ordenados por clave, en profundidad primero.

El $node argumenton puede usarse para centrarse en un subárbol. Si no se especifica, por defecto es $dbh->{Profile}{Data}.

El $path argumento puede usarse para especificar una lista de elementos de ruta que se añadirán a cada elemento de la lista devuelta. Si no se especifica, por defecto es una referencia a un array vacío.

as_text

@txt = $dbh->{Profile}->as_text();
$txt = $dbh->{Profile}->as_text({
    node      => undef,
    path      => [],
    separator => " > ",
    format    => '%1$s: %11$fs / %10$d = %2$fs avg (first %12$fs, min %13$fs, max %14$fs)'."\n";
    sortsub   => sub { ... },
);

Devuelve los datos recopilados ($dbh->{Profile}{Data}) reformatados en una lista de cadenas formateadas. En contexto escalar, la lista se devuelve como una única cadena concatenada.

Se puede usar un hashref para pasar argumentos, los valores por defecto se muestran en el ejemplo de arriba.

El "node" y <path> argumentos se pasan a as_node_path_list().

El "separator" argumento se usa para unir los elementos de la ruta para cada nodo hoja.

El "sortsub" argumento se usa para pasar una referencia a un sub que ordenará la lista. Al subrutina se le pasará una referencia al array devuelto por as_node_path_list() y debería ordenar el contenido del array en su lugar. El valor de retorno del sub se ignora. Por ejemplo, para ordenar los nodos por la clave de segundo nivel, podrías usar:

sortsub => sub { my $ary=shift; @$ary = sort { $a->[2] cmp $b->[2] } @$ary }

El "format" argumento es una "sprintf" cadena de formato que especifica el formato a usar para cada nodo hoja. Utiliza el mecanismo de índice explícito de parámetros de formato para especificar qué argumentos deberían aparecer en cada lugar de la cadena. Los argumentos para sprintf son:

 1:  ruta al nodo, unida con el separador
 2:  duración promedio (duración total/recuento)
     (3 a 9 actualmente no se usan)
10:  recuento
11:  duración total
12:  primera duración
13:  duración más pequeña
14:  duración más grande
15:  hora de la primera llamada
16:  hora de la primera llamada

MANIPULACIÓN PERSONALIZADA DE DATOS

Recuerda que "$h->{Profile}->{Data}" es una referencia a los datos recopilados. Ya sea a un array 'hoja' (cuando la Ruta está vacía, es decir, la variable de entorno DBI_PROFILE es 1), o una referencia a un hash que contiene valores que son o bien más referencias a hashes o referencias a arrays hoja.

A veces es útil poder resumir algunos o todos los datos recopilados. La dbi_profile_merge_nodes() función puede usarse para fusionar valores de nodos hoja.

dbi_profile_merge_nodes

use DBI qw(dbi_profile_merge_nodes);
$time_in_dbi = dbi_profile_merge_nodes(my $totals=[], @$leaves);

Fusiona un nodo de datos de perfil. Dada una referencia a un array de destino, y cero o más referencias a datos de perfil, fusiona los datos de perfil en el array de destino. Por ejemplo:

$time_in_dbi = dbi_profile_merge_nodes(
    my $totals=[],
    [ 10, 0.51, 0.11, 0.01, 0.22, 1023110000, 1023110010 ],
    [ 15, 0.42, 0.12, 0.02, 0.23, 1023110005, 1023110009 ],
);

$totals contendrá entonces

[ 25, 0.93, 0.11, 0.01, 0.23, 1023110000, 1023110010 ]

y $time_in_dbi será 0.93;

El segundo argumento no tiene por qué ser solo nodos hoja. Si se le da una referencia a un hash, el hash se busca recursivamente en busca de nodos hoja y todos los que se encuentren se fusionan.

Por ejemplo, para obtener el tiempo pasado 'dentro' del DBI durante una petición http, tu código de registro ejecutado al final de la petición (es decir, mod_perl LogHandler) podría usar:

my $time_in_dbi = 0;
if (my $Profile = $dbh->{Profile}) { # if DBI profiling is enabled
    $time_in_dbi = dbi_profile_merge_nodes(my $total=[], $Profile->{Data});
    $Profile->{Data} = {}; # reset the profile data
}

Si el perfilado ha sido habilitado entonces $time_in_dbi contendrá el tiempo pasado dentro del DBI para ese manejador (y cualquier otro manejador que comparta los mismos datos de perfil) desde la última petición.

Antes de DBI 1.56 la dbi_profile_merge_nodes() función se llamaba dbi_profile_merge(). Ese nombre todavía existe como un alias.

Añadiendo Tus Propias Muestras

La dbi_profile() función puede usarse para añadir datos de muestra extra en el árbol de datos de perfil. Por ejemplo:

use DBI;
use DBI::Profile (dbi_profile dbi_time);
my $t1 = dbi_time(); # floating point high-resolution time
... execute code you want to profile here ...
my $t2 = dbi_time();
dbi_profile($h, $statement, $method, $t1, $t2);

El $h parámetro es el manejador con el que la muestra de perfil extra debería estar asociada. El $statement parámetro es la cadena a usar donde la Ruta especifica !Statement. Si $statement es undef entonces $h->{Statement} será usado. De manera similar $method es la cadena a usar si la Ruta especifica !MethodName. No hay valor por defecto para $method.

El $h->{Profile}{Path} atributo es procesado por dbi_profile() de la manera habitual.

El $h parámetro es usualmente un manejador DBI pero también puede ser una referencia a un hash, en cuyo caso el dbi_profile() actúa sobre cada valor definido en el hash. Esta es una manera eficiente de actualizar múltiples perfiles con una sola muestra, y es usada por el módulo DashProfiler.

SUBCLASEADO

Los módulos de perfil alternativos deben subclasear DBI::Profile para ayudar a asegurar que funcionen con futuras versiones del DBI.

ADVERTENCIAS

Las aplicaciones que generan muchas cadenas de sentencias diferentes (típicamente porque no usan placeholders) y perfilan con !Statement en la Ruta (el valor por defecto) consumirán memoria en la estructura de Datos de Perfil por cada sentencia. Usa una referencia a código en la Ruta para devolver una forma editada (simplificada) de la sentencia.

Si un método lanza una excepción por sí mismo (no vía RaiseError) entonces no será contado en el perfil.

Si una subrutina HandleError lanza una excepción (en lugar de devolver 0 y dejar que RaiseError lo haga) entonces la llamada al método no será contada en el perfil.

El tiempo pasado en DESTROY se añade al perfil del manejador padre.

El tiempo pasado en los métodos DBI->*() no se cuenta. El tiempo pasado en el método de conexión del controlador, $drh->connect(), cuando es llamado por DBI->connect se cuenta si la variable de entorno DBI_PROFILE está establecida.

El tiempo pasado en obtener variables atadas, $DBI::errstr, se cuenta.

El tiempo pasado en FETCH para $h->{Profile} no se cuenta, así que obtener los datos de perfil no los altera.

DBI::PurePerl no soporta perfilado (aunque en teoría podría).

Para consultas asíncronas, el tiempo pasado mientras la consulta se está ejecutando en el backend no se cuenta.

Algunas plataformas no soportan la gettimeofday() función de tiempo de alta resolución usada por el DBI (y disponible vía la dbi_time() función). En cuyo caso obtendrás tiempo con resolución entera que es mayormente inútil.

En plataformas Windows la dbi_time() función está limitada a resolución de milisegundos. Lo cual no es suficientemente fino para nuestras necesidades, pero aún así mucho mejor que la resolución entera. Esta resolución limitada significa que las llamadas rápidas a métodos a menudo registrarán como tomando 0 tiempo. Y los tiempos en general tendrán mucho más 'jitter' dependiendo de dónde dentro del 'milisegundo actual' se tomaron los tiempos de inicio y fin.
