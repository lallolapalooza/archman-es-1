CREAR UN NUEVO

CONTROLADOR

La primera regla para crear un nuevo controlador de bases de datos para Perl DBI es muy simple: ¡NO LO

HAGAS!

Generalmente ya hay un controlador disponible para la base de datos que desea usar, casi sin importar qué base de datos elija. Muy a menudo, la base de datos proporcionará una interfaz de controlador ODBC, por lo que a menudo puede usar DBD::ODBC para acceder a la base de datos. Esto es típicamente menos conveniente en una máquina Unix que en una máquina Microsoft Windows, pero también hay numerosas opciones para administradores de controladores ODBC en Unix, y muy a menudo el controlador ODBC es proporcionado por el proveedor de la base de

datos.

Antes de decidir que necesita escribir un controlador, haga su tarea para asegurarse de que no está desperdiciando sus

energías.

[A partir de diciembre de 2002, el consenso es que si necesita un administrador de controladores ODBC en Unix, entonces el controlador unixODBC (disponible desde http://www.unixodbc.org/) es el camino a seguir.

]

La segunda regla para crear un nuevo controlador de bases de datos para Perl DBI también es muy simple: No lo hagas — ¡consigue que alguien más lo haga por

ti!

Sin embargo, hay ocasiones en las que es necesario escribir un nuevo controlador, a menudo para usar un lenguaje o API propietario para acceder a la base de datos de manera más rápida, o más completa, de lo que un controlador ODBC puede. Entonces debería leer este documento muy cuidadosamente, pero con un ojo escéptico

adecuado.

Si hay algo aquí que no tiene sentido, cuestiónelo. Podría tener razón en que la información es falsa, pero no llegue a esa conclusión demasiado

rápido.

Registrar un nuevo

controlador

Antes de pasar por cualquier proceso oficial de registro, necesitará establecer que no hay ningún controlador ya en proceso. Lo hará preguntando en las listas de correo de DBI si existe tal controlador disponible, o si alguien está trabajando en

uno.

Cuando obtenga el visto bueno, necesitará establecer el nombre del controlador y un prefijo para el controlador. Típicamente, el nombre se basa en el nombre del software de la base de datos que usa, y el prefijo es una contracción de ese. Por lo tanto, DBD::Oracle tiene el nombre Oracle y el prefijo 'ora_'. El prefijo debe estar en minúsculas y no contener guiones bajos distintos del que está al

final.

Esta información se registrará en el módulo DBI. Aparte de los fines de documentación, el registro es un requisito previo para instalar métodos

privados.

Si está escribiendo un controlador que no se distribuirá en CPAN, entonces debería elegir un prefijo que comience con 'x_', para evitar posibles colisiones de prefijos con controladores registrados en el futuro. Así, si escribiera un controlador distribuido fuera de CPAN llamado DBD::CustomDB, el prefijo podría ser 'x_cdb_'

.

Este documento asume que está escribiendo un controlador llamado DBD::Driver, y que el prefijo 'drv_' está asignado

al co
ntrolador.

Dos estilos de controlador de base de

Hay dos estilos distintos de controlador de base de datos que pueden escribirse para funcionar con Perl

DBI.

Su controlador puede escribirse en Perl puro, sin necesidad de un compilador C. Cuando sea factible, esta es la mejor solución, pero la mayoría de las bases de datos no están escritas de tal manera que esto se pueda hacer. Algunos ejemplos de controladores en Perl puro son DBD::File y DBD::C

Alternativamente, y más comúnmente, su controlador necesita

Versión pura Perl de Makefile.

PL

Típicamente comienzas escribiendo Makefile.PL, un generador de Makefile. El contenido de este archivo está descrito en detalle en las páginas man de ExtUtils::MakeMaker. Definitivamente es una buena idea que comiences a leerlas. Al menos deberías conocer las variables CONFIGURE, DEFINED, PM, DIR, EXE_FILES, INC, LIBS, LINKTYPE, NAME, OPTIMIZE, PL_FILES, VERSION, VERSION_FROM, clean, depend, realclean de la página man de ExtUtils::MakeMaker: estas se usan en casi cualquier Makefile

.PL.

Adicionalmente lee la sección sobre Sobrescribiendo Métodos de MakeMaker y las descripciones de los distcheck, disttest y dist: Definitivamente serán útiles para

ti.

De especial importancia para los controladores DBI es el método postamble de la página man de ExtUtils::

MM_Unix.

Para usuarios de Emacs, recomiendo el método libscan, que elimina los archivos de respaldo de Emacs (nombres de archivo que terminan con un tilde '~') de las listas de

archivos.

Ahora un ejemplo, uso la palabra "Driver" dondequiera que debas insertar el nombre de tu

controlador: 
# -*- perl -*-
use ExtUtils::MakeMaker;
WriteMakefile(
    dbd_edit_mm_attribs( {
        'NAME'         => 'DBD::Driver',
        'VERSION_FROM' => 'Driver.pm',
        'INC'          => '',
        'dist'         => { 'SUFFIX'   => '.gz',
                            'COMPRESS' => 'gzip -9f' },
        'realclean'    => { FILES => '*.xsi' },
        'PREREQ_PM'    => '1.03',
        'CONFIGURE'    => sub {
            eval {require DBI::DBD;};
            if ($@) {
                warn $@;
                exit 0;
            }
            my $dbi_arch_dir = dbd_dbi_arch_dir();
            if (exists($opts{INC})) {
                return {INC => "$opts{INC} -I$dbi_arch_dir"};
            } else {
                return {INC => "-I$dbi_arch_dir"};
            }
        }
    },
    { create_pp_tests => 1})
);
package MY;
sub postamble { return main::dbd_postamble(@_); }
sub libscan {
    my ($self, $path) = @_;
    ($path =~ m/\~$/) ? undef : $path;
}

Nota las llamadas a dbd_edit_mm_attribs() y dbd_postamb

le().

La segunda referencia hash en la llamada a dbd_edit_mm_attribs() (conteniendo create_pp_tests()) es opcional; no deberías usarla a menos que tu controlador sea un controlador puro Perl (es decir, no usa código C y XS). Por lo tanto, la llamada a dbd_edit_mm_attribs() no es relevante para controladores C/XS y puede omitirse; simplemente usa la (única) referencia hash que contiene NAME etc. como único argumento a WriteMakefi

le().

Nota que el código dbd_edit_mm_attribs() fallará si no tienes un subdirectorio t que contenga al menos un caso de

prueba.

PREREQ_PM le dice a MakeMaker que DBI (versión 1.03 en este caso) es requerido para este módulo. Esto emitirá una advertencia de que DBI 1.03 falta si alguien intenta instalar tu DBD sin DBI 1.03. Ver CONFIGURE más abajo para por qué esto no funciona de manera confiable para evitar que los probadores de cpan hagan fallar tu módulo si DBI no está

instalado.

CONFIGURE es una subrutina llamada por MakeMaker durante "WriteMakefile". Poniendo el "require DBI::DBD" en esta sección podemos intentar cargar DBI::DBD pero si falta, salimos con éxito. Como salimos exitosamente sin crear un Makefile cuando falta DBI::DBD, los probadores de cpan no reportarán un fallo. Esto puede parecer contradictorio con PREREQ_PM pero PREREQ_PM no causa que "WriteMakefile" falle (a menos que también especifiques PREREQ_FATAL, lo cual es fuertemente desaconsejado por MakeMaker) así que "WriteMakefile" continuaría llamando a "dbd_dbi_arch_dir" y

fallaría.

Todos los controladores deben usar dbd_postamble() o arriesgan encontrarse con

problemas.

Nota la especificación de VERSION_FROM; el archivo nombrado (Driver.pm) será escaneado para la primera línea que parezca una asignación a $VERSION, y el texto subsiguiente se usará para determinar el número de versión. Nota el ccomentarios en ExtUtils::MakeMaker sobre el tema de los números de versión formateados

correctamente.

Si su controlador depende de software externo (lo que generalmente ocurrirá), deberá agregar código para asegurarse de que su entorno sea viable antes de la llamada a WriteMakefile(). Si necesita comprobar la existencia de una biblioteca externa y quizás modificar INC para incluir las rutas donde se encuentran los archivos de cabecera de la biblioteca externa y no puede encontrar la biblioteca o los archivos de cabecera, asegúrese de generar un mensaje indicando que no se pueden encontrar, pero "exit 0" (éxito) antes de llamar a "WriteMakefile" o los probadores de CPAN harán fallar su módulo si no se encuentra la biblioteca

externa.

Un Makefile.PL completo puede ser bastante grande (por ejemplo, los archivos para DBD::Oracle y DBD::Informix tienen ambos más de 1000 líneas de longitud, y el de Informix usa - y crea - módulos auxiliares también)

sub connect
{
    my ($drh, $dr_dsn, $user, $auth, $attr) = @_;
    # Algunas verificaciones específicas de la base de datos, configuraciones por defecto
    # y cosas así pueden ir aquí. Esto solo debe incluir
    # comprobaciones de sintaxis o cosas similares donde sea legal
    # 'die' en caso de errores.
    # Por ejemplo, muchos paquetes de bases de datos requieren que se establezcan
    # variables de entorno específicas; este podría ser el lugar donde validas
    # que estén establecidas, o les asignes un valor por defecto si no lo están.
    my $driver_prefix = "drv_"; # el prefijo asignado para este controlador
    # Procesar atributos del DSN; asumimos aquí sintaxis ODBC,
    # es decir, el DSN se ve como var1=val1;...;varN=valN
    foreach my $var ( split /;/, $dr_dsn ) {
        my ($attr_name, $attr_value) = split '=', $var, 2;
        return $drh->set_err($DBI::stderr, "Can't parse DSN part '$var'")
            unless defined $attr_value;
        # añadir el prefijo del controlador al nombre del atributo si no lo tiene ya
        $attr_name = $driver_prefix.$attr_name
            unless $attr_name =~ /^$driver_prefix/o;
        # Almacenar el atributo en %$attr, reemplazando cualquier valor existente.
        # El DBI hará STORE() de estos en $dbh después de que nos hayamos conectado
        $attr->{$attr_name} = $attr_value;
    }
    # Obtener los atributos que usaremos para conectarnos.
    # Usamos delete aquí porque no es necesario hacer STORE de ellos
    my $db = delete $attr->{drv_database} || delete $attr->{drv_db}
        or return $drh->set_err($DBI::stderr, "No database name given in DSN '$dr_dsn'");
    my $host = delete $attr->{drv_host} || 'localhost';
    my $port = delete $attr->{drv_port} || 123456;
    # Asume que puedes adjuntarte a tu base de datos a través de drv_connect:
    my $connection = drv_connect($db, $host, $port, $user, $auth)
        or return $drh->set_err($DBI::stderr, "Can't connect to $dr_dsn: ...");
    # crear un dbh 'en blanco' (llamar al constructor de la superclase)
    my ($outer, $dbh) = DBI::_new_dbh($drh, { Name => $dr_dsn });
    $dbh->STORE('Active', 1 );
    $dbh->{drv_connection} = $connection;
    return $outer;
}

Estos métodos (que ya hemos usado, ver arriba) son llamados por usted, siempre que el usuario haga

Vea perltie para detalles sobre referencias a hashes vinculadas para entender por qué estos métodos son

El DBI manejará la mayoría de los atributos por usted, en particular atributos como RaiseError o PrintError. Todo lo que tiene que hacer es manejar los atributos privados de su controlador y cualquier atributo, como AutoCommit y ChopBlanks, que el DBI no puede manejar por

Un buen ejemplo podría verse

sub STORE
{
    my ($dbh, $attr, $val) = @_;
    if ($attr eq 'AutoCommit') {
        # AutoCommit is currently the only standard attribute we have
        # to consider.
        if (!$val) { die "Can't disable AutoCommit"; }
        return 1;
    }
    if ($attr =~ m/^drv_/) {
        # Handle only our private attributes here
        # Note that we could trigger arbitrary actions.
        # Ideally we should warn about unknown attributes.
        $dbh->{$attr} = $val; # Yes, we are allowed to do this,
        return 1;             # but only for our private attributes
    }
    # Else pass up to DBI to handle for us
    $dbh->SUPER::STORE($attr, $val);
}
sub FETCH
{
    my ($dbh, $attr) = @_;
    if ($attr eq 'AutoCommit') { return 1; }
    if ($attr =~ m/^drv_/) {
        # Handle only our private attributes here
        # Note that we could trigger arbitrary actions.
        return $dbh->{$attr}; # Yes, we are allowed to do this,
                              # but only for our private attributes
    }
    # Else pass up to DBI to handle
    $dbh->SUPER::FETCH($attr);
}

El DBI en realidad almacenará y recuperará los atributos específicos del controlador (con nombres en minúsculas) sin advertencia ni error, así que en realidad no hay necesidad de implementar ningún código específico del controlador en sus métodos FETCH() y STORE() a menos que necesite lógica/verificaciones adicionales, más allá de obtener o establecer el

valor.

O

El trazado en DBI se controla con una combinación de un nivel de traza y un conjunto de flags que juntos se conocen como los ajustes de traza. Los ajustes de traza se almacenan en un solo entero y se dividen en niveles y flags por un conjunto de máscaras ("DBIc_TRACE_LEVEL_MASK" y "DBIc_TRACE_FLAGS

_MASK").

Cada manejador tiene sus propios ajustes de traza y también los tiene el DBI. Cuando llamas a un método, el DBI fusiona los ajustes del manejador en los suyos durante la duración de la llamada: los flags de traza del manejador se OR-ea con los flags de traza del DBI, y si el manejador tiene un nivel de traza más alto, entonces el nivel de traza del DBI se eleva para igualarlo. Los ajustes de traza anteriores del DBI se restauran cuando el método llamado

retorna.

Nivel de

traza

El nivel de traza son los primeros 4 bits de los ajustes de traza (enmascarados por "DBIc_TRACE_FLAGS_MASK") y representa niveles de traza de 1 a 15. No imprimas nada en niveles de traza menores que 3 ya que están reservados para

DBI.

Para consejos sobre qué imprimir en cada nivel, ver "Trace Levels" en

DBI.

Para probar un nivel de traza puedes usar la macro "DBIc_TRACE_LEVEL"

así: 
if (DBIc_TRACE_LEVEL(imp_xxh) >= 2) {
    PerlIO_printf(DBIc_LOGPIO(imp_xxh), "foobar");
}

También ten en cuenta el uso de PerlIO_printf, que siempre debes usar para el trazado y nunca las funciones de E/S de C "stdi

o.h
".

Los flags de traza se usan para habilitar el trazado de actividades específicas dentro del DBI y los drivers. El DBI define algunos flags de traza y los drivers pueden definir otros. Los nombres de flags de traza de DBI comienzan con una letra mayúscula y los nombres específicos del driver comienzan con una letra minúscula. Para una lista de los flags de traza definidos por DBI, ver "Trace Flags" en

Si quieres usar flags de traza privados, probablemente querrás poder establecerlos por nombre. SUBCLASEADO DE CONTROLADORES

Esto es definitivamente un tema abierto. Puede ser hecho, como lo demuestra el controlador DBD::File, pero no es tan simple como uno podría

pensar.

(Note que este tema es diferente de subclasear el DBI. Para un ejemplo de eso, vea el archivo t/subclass.t provisto con el DBI

El problema principal es que los dbh y los sth que sus métodos connect() y prepare() devuelven no son instancias de sus paquetes DBD::Driver::db o DBD::Driver::st, ni siquiera están derivados de ellos. En su lugar, son instancias de las clases DBI::db o DBI::st o una subclase derivada. Así, si escribe un método mymethod() y hace

mymethod()

entonces el cargador automático buscará ese método en el paquete DBI::db. Por supuesto, en su lugar puede hacer

un

)

y eso sí funcionará, incluso si mymethod() es heredado, pero no sin trabajo adicional. Establecer @ISA no es

suficiente.

Sobrescribiendo

métodos

El primer problema es que el método connect() no tiene idea de subclases. Por ejemplo, no puede implementar la clase base y la subclase en el mismo archivo: El método install_driver() quiere hacer

controlador.

Por supuesto, eso no es mucho de un problema. Incluso debería poder heredar el método connect() de las clases base. Pero no puede simplemente sobrescribir el método, a menos que haga algo como esto, citado de DBD::C

sub connect ($$;$$$) {
