Manejo de múltiples conjuntos de

resultados

El Transact SQL de Sybase tiene la capacidad de devolver múltiples conjuntos de resultados de una sola sentencia SQL. Por ejemplo, la

consulta: 
select b.title, b.author, s.amount
  from books b, sales s
 where s.authorID = b.authorID
 order by b.author, b.title
compute sum(s.amount) by b.
author

que lista las ventas por autor y título y también calcula el total de ventas por autor devuelve dos tipos de filas. La especificación de DBI no maneja realmente esta situación, ni la más

complicada 
exec my_proc @p1='this', @p2='that', @p3
out

donde "my_proc" podría devolver cualquier número de conjuntos de resultados (es decir, podría realizar un número desconocido de sentencias "s

elect".

He decidido manejar esto devolviendo una fila vacía al final de cada conjunto de resultados, y estableciendo un atributo especial de Sybase en $sth que puedes comprobar para ver si hay más datos por recuperar. El atributo es syb_more_results que debes comprobar para ver si necesitas reiniciar el bucle fetch()

.

Para asegurarte de que todos los resultados se recuperan, el bucle básico "fetch" puede escribirse

así: 
{
    while($d = $sth->fetch) {
       ... do something with the data
    }
    redo if $sth->{syb_more_results};
}

Puedes obtener el tipo del conjunto de resultados actual con $sth->{syb_result_type}. Esto devuelve un valor numérico, tal como está definido en $SYBASE/$SYBASE_OCS/include/cspublic.

h: 
#define CS_ROW_RESULT           (CS_INT)4040
#define CS_CURSOR_RESULT        (CS_INT)4041
#define CS_PARAM_RESULT         (CS_INT)4042
#define CS_STATUS_RESULT        (CS_INT)4043
#define CS_MSG_RESULT           (CS_INT)4044
#define CS_COMPUTE_RESULT       (CS_INT)
4045

En particular, el estado de retorno de un procedimiento almacenado se devuelve como CS_STATUS_RESULT (4043), y normalmente es el último conjunto de resultados que se devuelve en la ejecución de un procedimiento almacenado, pero consulta el atributo syb_do_proc_status para una forma alternativa de manejar este tipo de resultado. Consulta Ejecución de Procedimientos almacenados en otra parte de este documento para más

información.

AutoCommit, Transacciones y

Transact-SQL

Cuando $h->{AutoCommit} está desactivado (off), todas las sentencias SQL de modificación de datos que emita (insert/update/delete) solo tendrán efecto si llama a $dbh->com

mit.

DBD::Sybase implementa esto a través de dos métodos distintos, dependiendo de la configuración del atributo $h->{syb_chained_txn} y de la versión del servidor al que se está

accediendo.

Si $h->{syb_chained_txn} está desactivado (off), entonces el controlador DBD::Sybase enviará un BEGIN TRAN antes del primer $dbh->prepare(), y después de cada llamada a $dbh->commit() o $dbh->rollback(). Esto funciona bien, pero hará que cualquier SQL que contenga sentencias CREATE TABLE (u otras DDL) falle. Estas sentencias CREATE TABLE pueden estar escondidas en algún procedimiento almacenado (por ejemplo, "sp_helprotect" crea dos tablas temporales cuando se ejecuta). Puede sortear esta limitación estableciendo la opción "ddl in tran" (a nivel de base de datos, a través de "sp_dboption".) Debe tener en cuenta que esto puede tener efectos graves en el rendimiento, ya que causa que se mantengan bloqueos (locks) en ciertas tablas del sistema durante la duración de la

transacción.

Si $h->{syb_chained_txn} está activado (on), entonces DBD::Sybase establece la opción CHAINED, que le indica a Sybase que no confirme nada automáticamente. De nuevo, necesitará llamar a $dbh->commit() para hacer que cualquier ca

mbio en los dat

Esta versión de DBD::Sybase incluye soporte para la llamada last_insert_id(), con las siguientes

advertencias:

La llamada last_insert_id() es simplemente un envoltorio (wrapper) alrededor de una consulta "select @@identity". Para ser exitosa (es decir, para devolver el valor correcto) esta debe ejecutarse en la misma conexión que el INSERT que generó el nuevo valor IDENTITY. Por lo tanto, el manejador de sentencia (statement handle) que se usó para realizar la inserción debe haber sido cerrado/liberado antes de que se pueda llamar a last_insert_id(). De lo contrario, last_insert_id() se verá forzada a abrir una conexión diferente para ejecutar la consulta, y devolverá un valor inválido (normalmente en este caso devolverá 0)

.

last_insert_id() ignora cualquier parámetro que se le pase, y NO devolverá el último valor @@identity generado en el caso do

nde se usaron marcadores de posición (placeholders), o donde
la inserción estuvo encapsulada en un procedimiento almacenado.

Uso de marcadores de posición ? y parámetros de enlace (bind) en $sth->

execute

DBD::Sybase soporta el uso de marcadores de posición ? en sentencias SQL siempre que la biblioteca subyacente y el motor de base de datos lo soporten. Lo hace usando lo que Sybase llama SQL Dinámico. Los marcadores de posición ? le permiten escribir algo

como: 
 $sth = $dbh->prepare("select * from employee where empno = ?");
 # Recuperar filas de employee donde empno == 1024:
 $sth->execute(1024);
 while($data = $sth->fetch) {
     print "@$data\n";
 }
# Ahora obtener filas donde empno = 2000:

 $sth->execute(2000);
 while($data = $sth->fetch) {
     print "@$data\n";
}

Cuando usa marcadores de posición ?, Sybase crea un procedimiento almacenado temporal que corresponde a su sentencia SQL. Luego pasa variables a $sth->execute o $dbh->do, las cuales se insertan en la consulta, y se devuelven las

filas.

DBD::Sybase usa las llamadas a la API de Sybase subyacentes para manejar los marcadores de posición de estilo ?. Para sentencias select/insert/update/delete, DBD::Sybase llama a la familia de funciones de la Biblioteca de Cliente (Client Library) ct_dynamic(), lo que da a DBD::Sybase información del tipo de dato para cada parámetro de la

consulta.

Solo puede usar marcadores de posición de estilo ? para sentencias que devuelvan un único conjunto de resultados, y los marcadores de posición ? solo pueden aparecer en una cláusula WHERE, en la cláusula SET de una sentencia UPDATE, o en la lista VALUES de una sentencia I

NSERT.

La documentación de DBI menciona lo siguiente con respecto a los valores NULL y los marcadores de

posición: 
Vincular (Binding) un `undef' (NULL) al marcador de posición no
seleccionará filas que tengan un `product_code' NULL. Consulte el
manual de SQL de su motor de base de datos o cualquier libro de SQL para
las razones de esto.  Para seleccionar explícitamente valores NULL, tiene
que decir "`WHERE product_code IS NULL'" y para hacerlo general tiene que decir:
  ... WHERE (product_code = ? OR (? IS NULL AND product_code IS NULL))
y vincular el mismo valor a ambos marcadores de
posición.

Esto no funcionará con un servidor de base de datos Sybase. Si intenta la construcción anterior, obtendrá el siguiente

error:
The datatype of a parameter marker used in the dynamic prepare statement could not be
resolved.

El problema específico aquí es que cuando se usan marcadores de posición ?, la operación prepare() se envía al servidor de base de datos para la resolución de parámetros. Esto extrae los tipos de datos para cada uno de los marcadores de posición. Desafortunadamente, la construcción "? is null" no vincula el marcador de posición ? con una columna de tabla existente, por lo que el servidor de base de datos no puede encontrar el tipo de dato. Como toda esta operación ocurre dentro de las bibliotecas de Sybase, no hay una manera fácil para DBD::Sybase de

sortearlo.

Tenga en cuenta que Sybase normalmente manejará la construcción "foo = NULL" de la misma manera que otros systems handle "foo is NULL", por lo que la construcción enrevescida que se describe arriba no es necesaria para obtener los resultados correctos al consultar una base de datos

Sybase.

La API subyacente no admite marcadores de posición estilo ? para procedimientos almacenados, pero consulte la sección titulada Procedimientos almacenados y marcadores de posición en otro lugar de este

documento.

Los marcadores de posición estilo ? pueden NO usarse para pasar datos TEXT o IMAGE al servidor. Esta es una limitación del protocolo TDS, no de DBD::

Sybase.

También hay un problema de rendimiento: OpenClient crea procedimientos almacenados en tempdb para cada llamada a prepare() que incluye marcadores de posición ?. Crear estos objetos requiere actualizar las tablas del sistema en la base de datos tempdb, y por lo tanto puede crear un punto crítico de rendimiento si hay muchas declaraciones prepare() de múltiples clientes que se ejecutan simultáneamente. Este problema ha sido corregido para los servidores Sybase 11.9.x y posteriores, ya que crean procedimientos almacenados temporales "ligeros" que se mantienen en la caché de memoria del servidor y no afectan a las tablas del sistema en

absoluto.

En general, sin embargo, encuentro que si su aplicación va a ejecutarse contra Sybase es mejor escribir procedimientos almacenados ad-hoc en lugar de usar los marcadores de posición ? en SQL

embebido.

Por curiosidad hice algunas mediciones simples para ver cuál era la sobrecarga de hacer un prepare con marcadores de posición ? en comparación con un prepare SQL directo y con un prepare de procedimiento almacenado. Contra un servidor 11.0.3.3 (linux) el prepare con marcador de posición es significativamente más lento, y necesitas hacer ~30 llamadas a execute() en la sentencia preparada para compensar la sobrecarga. Contra un servidor 12.0 (solaris), sin embargo, la situación era muy diferente, con los marcadores de posición prepare() ligeramente más rápidos que el SQL directo prepare(). Esto es algo que yo realmente no entiendo, pero los números fueron bastante

claros.

En todos los casos los prepare() de procedimientos almacenados fueron claramente más rápidos, y de forma

consistente.

Esta prueba no intentó evaluar problemas de concurrencia, sin

embargo.

No es posible recuperar el último valor IDENTITY después de una inserción hecha con marcadores de posición estilo ?. Esta es una limitación/error de Sybase, no un problema de DBD::Sybase. Por ejemplo, asumiendo que la tabla foo tiene una columna

identity: 
$dbh->do("insert foo(col1, col2) values(?, ?)", undef, "string1", "string2");
$sth = $dbh->prepare('select @@identity') 
  || die "Can't prepare the SQL statement: $DBI::errstr";
$sth->execute || die "Can't execute the SQL statement: $DBI::errstr";
#Get the data back.
while (my $row = $sth->fetchrow_arrayref()) {
  print "IDENTITY value = $row->[0]\n";
}

siempre devolverá un valor identity de 0, lo cual es obviamente incorrecto. Este comportamiento se debe al hecho de que el manejo de los marcadores de posición estilo ? se implementa usando procedimientos almacenados temporales en Sybase, y el valor de @@identity se restablece cuando el procedimiento almacenado ha terminado de ejecutarse. Usar un procedimiento almacenado explícito para hacer la inserción e intentar recuperar @@identity después de que se haya ejecutado resulta en el mismo

comportamiento.

Llamando a Procedimientos

Almacenados

DBD::Sybase maneja los procedimientos almacenados de la misma manera que cualquier otra sentencia Transact-SQL. La única diferencia real es que los procedimientos almacenados de Sybase siempre devuelven un conjunto de resultados extra con el estado de retorno del proc que corresponde a la sentencia return en el código del procedimiento almacenado. Este conjunto de resultados con una sola fila siempre se devuelve al final y tiene un tipo de resultado de CS_STATUS_RESULT (4043)

.

Por defecto este conjunto de resultados se devuelve como cualquier otro, pero puede pedirle a DBD::Sybase que lo procese internamente a través del atributo $h->{syb_do_proc_status}. Si este atributo está establecido, entonces DBD::Sybase procesará el conjunto de resultados CS_STATUS_RESULT él mismo, colocará el valor del estado de retorno en $sth->{syb_proc_status}, y posiblemente generará un error si el conjunto de resultados es diferente de 0. Tenga en cuenta que un estado de retorno diferente de 0 no hará que $sth->execute devuelva un código de fallo si el proc tiene al menos otro conjunto de resultados que devolvió filas (razón: las filas se devuelven y se recuperan antes de que se vea el estado de retorno)

.

Procedimientos Almacenados y Marcadores de

Posición

DBD::Sybase tiene la capacidad de usar marcadores de posición estilo ? como parámetros en llamadas a procedimientos almacenados. Los requisitos son que la llamada al procedimiento almacenado se inicie con un "exec" y que sea la única sentencia en el lote que se está preparand

o():

Por ejemplo, esto prepara una llamada a un procedimiento almacenado con parámetros con

nombre: 
my $sth = $dbh->prepare("exec my_proc \@p1 = ?, \@p2 = ?");
$sth->execute('one', 'two')
;

También puede usar parámetros

posicionales: 
my $sth = $dbh->prepare("exec my_proc ?, ?");
$sth->execute('one', 'two')
;

Puede mezclar parámetros posicionales y con nombre en la misma

preparación.

No puede mezclar parámetros de marcador de posición y parámetros codificados directamente. Por

ejemplo 
$sth = $dbh->prepare("exec my_proc \@p1 = 1, \@p2 = ?")
;

no funcionará - porque el parámetro @p1 no se analiza correctamente y no se enviará al

servidor.

Puede especificar parámetros OUTPUT de la forma habitual, pero no puede usar bind_param_inout() para obtener el resultado de salida - en su lugar tiene que llamar a fetch() y/o $sth->func('syb_output_params')

: 
my $sth = $dbh->prepare("exec my_proc \@p1 = ?, \@p2 = ?, \@p3 = ? OUTPUT ");
$sth->execute('one', 'two', 'three');
my (@data) = $sth->syb_output_params()
;

DBD::Sybase no intenta averiguar el tipo de parámetro correcto para cada parámetro (sería posible hacerlo para la mayoría de los casos, pero hay suficientes excepciones como para que preferí evitar el problema por el momento). DBD::Sybase establece todos los parámetros por defecto a SQL_CHAR, y tiene que usar bind_param() con un valor de tipo explícito para establecerlo en algo diferente. El tipo se recuerda después, por lo que solo necesita usar la llamada explícita una vez para cada

parámetro: 
my $sth = $dbh->prepare("exec my_proc \@p1 = ?, \@p2 = ?");
$sth->bind_param(1, 'one', SQL_CHAR);
$sth->bind_param(2, 2.34, SQL_FLOAT);
$sth->execute;
....
$sth->execute('two', 3.456);
etc..
.

Tenga en cuenta que una vez que se ha definido un tipo para un parámetro no puede

cambiarlo.

Al vincular datos SQL_NUMERIC o SQL_DECIMAL puede obtener errores de conversión fatales si la escala o la precisión excede el tamaño de la definición del parámetro de

destino.

Por ejemplo, considere la siguiente definición de procedimiento

almacenado: 
declare proc my_proc @p1 numeric(5,2) as..
.

y el siguiente fragmento de prepare/execute

: 
my $sth = $dbh->prepare("exec my_proc \@p1 = ?");
$sth->bind_param(1, 3.456, SQL_NUMERIC)
;

Esto genera el siguiente

DBD::Sybase::st execute failed: Server message number=241 severity=16 state=2 line=0 procedure=dbitest text=Scale error during implicit conversion of NUMERIC value '3.456' to a NUMERIC

field.

Funcionalidad Experimental de Carga

Masiva

NOTA: Esta característica requiere que la librería libblk.a esté disponible en el momento de la compilación. Esto no siempre es el caso si el SDK de Sybase no está instalado. Puede probar el atributo $dbh->{syb_has_blk} para ver si las llamadas a la API BLK están disponibles en su copia de DBD::

Sybase.

A partir de la versión 1.04.2 DBD::Sybase tiene la capacidad de usar la API BLK (carga masiva) de Sybase para realizar cargas rápidas de datos. El uso básico es el

siguiente: 
my $dbh = DBI->connect('dbi:Sybase:server=MY_SERVER;bulkLogin=1', $user, $pwd);
$dbh->begin_work;  # optional.
my $sth = $dbh->prepare("insert the_table values(?, ?, ?, ?, ?)",
                        {syb_bcp_attribs => { identity_flag => 0,
                                             identity_column => 0 }}});
while(<DATA>) {
  chomp;
  my @row = split(/\|/, $_);   # asumir un archivo delimitado por barras verticales...
  $sth->execute(@row);
}
$dbh->commit;
print "Enviados ", $sth->rows, " al servidor\n";
$sth->
finish;

Primero, necesitas especificar el nuevo atributo bulkLogin en la cadena de conexión, que activa la propiedad CS_BULK_LOGIN para la conexión. Sin esta propiedad, la api BLK no

funcionará.

Llamas a $dbh->prepare() con una sentencia INSERT normal y el atributo especial syb_bcp_attribs para activar el manejo BLK de los datos. El subatributo identity_flag puede establecerse a 1 si tus datos de origen incluyen los valores para la columna IDENTITY de la tabla de destino. Si la tabla de destino tiene una columna IDENTITY pero quieres que la operación de inserción genere un nuevo valor para cada fila, deja identity_flag en 0, pero establece identity_col al número de columna de la columna identity (generalmente es la primera columna de la tabla, pero no siempre.

)

El número de marcadores de posición en la sentencia INSERT debe corresponder al número de columnas en la tabla, y los datos de entrada deben estar en el mismo orden que el orden físico de las columnas de la tabla. Cualquier lista de columnas en la sentencia INSERT (es decir, insert table(a, b, c,...) values(...) es

ignorada.

El valor de AutoCommit es ignorado para las operaciones BLK - las filas solo se confirman cuando llamas a $dbh->com

mit.

Puedes llamar a $dbh->rollback para cancelar cualquier fila no confirmada, pero esto también cancela el resto de la operación BLK: cualquier intento de cargar filas al servidor después de una llamada a $dbh->rollback()

fallará.

Si una fila falla al cargarse debido a un error del lado del CLIENTE (como un error de conversión de datos) entonces $sth->execute() devolverá un fallo (es decir, falso) y $sth->errstr tendrá la razón del

error.

Si una fila falla en el lado del SERVIDOR (por ejemplo, debido a un error de fila duplicada) entonces todo el lote (es decir, entre dos $dbh->commit() llamadas) fallará. Este es el comportamiento normal para

BLK/bcp.

La API de Carga Masiva (Bulk-Load API) es muy sensible a los problemas de conversión de datos, ya que todas las conversiones se manejan en el lado del cliente, y la fila se pre-formatea antes de ser enviada al servidor. Por defecto, cualquier conversión que sea marcada por la llamada cs_convert() de Sybase resultará en una fila fallida. Algunos de estos errores de conversión son patéticamente fatales (por ejemplo, convertir 'Feb 30 2001' a un valor DATETIME...), mientras que otros son debatibles (por ejemplo, convertir 123.456 a un NUMERIC(6,2) lo que resulta en una pérdida de precisión). El comportamiento por defecto de fallar cualquier fila que tenga un error de conversión en ella puede ser modificado usando un manejador de errores especial. Devolver 0 desde este manejador le dice a DBD::Sybase que falle esta fila, y devolver 1 significa que todavía queremos intentar enviar la fila al servidor (obviamente el código interno de Sybase todavía puede fallar la fila en ese punto). Estableces el manejador

así: 
DBD::Sybase::syb_set_cslib_cb(\&handler)
;

y un manejador de

ejemplo: 
sub cslib_handler {
  my ($layer, $origin, $severity, $errno, $errmsg, $osmsg, $blkmsg) = @_;

  print $msg;
  print $osmsg if($osmsg);
  print $blkmsg if $blkmsg;
  return 1 if($errno == 36)
  return 0;

Usando DBD::Sybase con

MS-SQL

MS-SQL comenzó como Sybase 4.2, y todavía hay muchas similitudes entre Sybase y MS-SQL que hacen posible usar DBD::Sybase para consultar un servidor de datos MS-SQL usando ya sea las bibliotecas OpenClient de Sybase o las bibliotecas FreeTDS (ver http://www.freetds.org)

.

Sin embargo, usar las bibliotecas de Sybase para consultar un servidor MS-SQL tiene ciertas limitaciones. En particular, los marcadores de posición estilo ? no están soportados (aunque el soporte al usar las bibliotecas FreeTDS es posible en una versión futura de las bibliotecas), y ciertos atributos syb_ pueden no estar

soportados.

Sybase establece el valor por defecto del atributo TEXTSIZE (también conocido como LongReadLen) en 32k, pero MS-SQL 7 no parece hacerlo correctamente, resultando en solicitudes de memoria muy grandes al consultar tablas con columnas de datos TEXT/IMAGE. La solución es establecer TEXTSIZE a algún valor decente a través de $dbh->{LongReadLen} (si eso funciona - no he tenido ninguna confirmación de que lo haga) o a través de $dbh->do("set textsize <sometamaño>

claves.
