DBD::Gofer(3) Documentación de Perl aportada por el usuario DBD::Gofer(3)

NOMBRE

DBD::Gofer - Un controlador proxy sin estado para comunicarse con un DBI remoto

SINOPSIS

use DBI;
$original_dsn = "dbi:..."; # su Nombre de Fuente de Datos DBI original
$dbh = DBI->connect("dbi:Gofer:transport=$transport;...;dsn=$original_dsn",
                    $user, $passwd, \%attributes);
... use $dbh como si estuviera conectado a $original_dsn ...

La "transport=$transport" parte especifica el nombre del módulo a usar para transportar las solicitudes al DBI remoto. Si $transport no contiene ningún doble punto, se le antepone "DBD::Gofer::Transport::".

La "dsn=$original_dsn" parte debe ser el último elemento del DSN porque todo lo que sigue a "dsn=" se asume que es el DSN que el DBI remoto debe usar.

El "..." representa atributos que influyen en el funcionamiento del controlador Gofer o del transporte. Estos se describen más abajo o en la documentación del módulo de transporte que se esté utilizando.

DESCRIPCIÓN

DBD::Gofer es un controlador de base de datos de DBI que reenvía solicitudes a otro controlador de DBI, generalmente en un proceso separado, a menudo en una máquina separada. Intenta ser lo más transparente posible para que parezca que usted está usando el controlador remoto directamente.

DBD::Gofer es muy similar a DBD::Proxy. La diferencia principal es que con DBD::Gofer no se mantiene estado en el extremo remoto. Eso significa que cada solicitud contiene toda la información necesaria para crear el estado requerido. (Así que, por ejemplo, cada solicitud incluye el DSN al que conectarse.) Cada solicitud puede enviarse a cualquier servidor disponible. El servidor ejecuta la solicitud y devuelve una única respuesta que incluye todos los datos.

Esto es muy similar a la forma en que http funciona como un protocolo sin estado para la web. Cada solicitud de su navegador web puede ser manejada por un proceso de servidor web diferente.

Casos de Uso

Esto puede parecer una sobrecarga inútil, pero hay situaciones en las que esto es muy bueno. Consideremos un caso específico.

Imagine usar DBD::Gofer con un transporte http. Su aplicación llama a connect(), prepare("select * from table where foo=?"), bind_param(), y execute(). En este punto DBD::Gofer construye una solicitud que contiene toda la información sobre las llamadas a métodos. Luego usa el transporte httpd para enviar esa solicitud a un servidor web apache.

Este servidor web 'dbi execute' ejecuta la solicitud (usando DBI::Gofer::Execute y los módulos relacionados) y construye una respuesta que contiene todas las filas de datos, si la sentencia devolvió alguna, junto con todos los atributos que describen los resultados, como $sth->{NAME}. Esta respuesta se envía de vuelta a DBD::Gofer, que la desempaqueta y la presenta a la aplicación como si hubiera ejecutado la sentencia ella misma.

Ventajas

De acuerdo, pero aún no ve el punto. Bueno, consideremos lo que hemos ganado:

Agrupación y Limitación de Conexiones

El servidor web 'dbi execute' aprovecha toda la funcionalidad de la infraestructura web en términos de balanceo de carga, alta disponibilidad, firewalls, gestión de acceso, proxy, y caché.

En su nivel más básico, usted obtiene un grupo configurable de conexiones de base de datos persistentes.

Escalado Sencillo

¿Tiene miles de procesos intentando todos conectarse a la base de datos? Puede usar DBD::Gofer para conectarlos a su grupo más pequeño de servidores web 'dbi execute' en su lugar.

Caché

El caché del lado del cliente es tan simple como agregar ""cache=1"" al DSN. Esta característica por sí sola puede valer la pena usar DBD::Gofer.

Menos Viajes de Red (Round-trips)

DBD::Gofer envía tantas solicitudes como sea posible (dependiendo de la política que se esté usando).

Clientes Delgados / Plataformas No Soportadas

Ya no necesita controladores para su base de datos en cada sistema. DBD::Gofer es perl puro.

RESTRICCIONES

Hay algunas restricciones naturales impuestas por el enfoque 'sin estado' de DBD::Gofer. Pero no muchas:

No puede cambiar atributos del manejador de base de datos después de connect()

No puede cambiar atributos del manejador de base de datos después de haberse conectado. Use la llamada a connect() para especificar todos los ajustes de atributos que desee.

Esto se debe a que es crítico que cuando una solicitud esté completa, el manejador de base de datos se deje en el mismo estado en el que estaba cuando se conectó por primera vez.

Se hace una excepción para los atributos con nombres que comienzan con ""private_"": Pueden establecerse después de connect() pero el cambio solo se aplica localmente.

No puede cambiar atributos del manejador de sentencia después de prepare()

No puede cambiar atributos del manejador de sentencia después de prepare.

Se hace una excepción para los atributos con nombres que comienzan con ""private_"": Pueden establecerse después de prepare() pero el cambio solo se aplica localmente.

No puede usar transacciones

Solo AutoCommit. Las transacciones no están soportadas.

(En teoría, las transacciones podrían soportarse cuando se usa un transporte que mantiene una conexión, como "stream" lo hace. Si le interesa esto, por favor póngase en contacto a través de dbi-dev@perl.org)

No puede llamar a métodos sth privados del controlador

Pero eso rara vez es necesario de todos modos.

ADVERTENCIAS GENERALES

Algunas cosas importantes a tener en cuenta al usar DBD::Gofer:

Tablas temporales, bloqueos y otro estado persistente por conexión

No debería esperar que ningún estado por sesión persista entre solicitudes. Esto incluye bloqueos y tablas temporales.

Debido a que el lado del servidor puede ejecutar sus solicitudes a través de una conexión de base de datos diferente, no puede depender de ningún estado persistente por conexión, como tablas temporales, estando disponible de una solicitud a la siguiente.

Esta es una trampa fácil de caer. Una buena manera de comprobar esto es probar su código con un paquete de política de Gofer que establezca la política "connect_method" a 'connect' para forzar una nueva conexión para cada solicitud. La política "pedantic" hace esto.

Atributos del Manejador de Base de Datos Privados del Controlador

Algunos atributos dbh privados del controlador pueden no estar disponibles si el controlador no ha implementado el método private_attribute_info() (añadido en DBI 1.54).

Atributos del Manejador de Sentencia Privados del Controlador

Los atributos sth privados del controlador pueden establecerse en la llamada a prepare() TODO

Algunos atributos sth privados del controlador pueden no estar disponibles si el controlador no ha implementado el método private_attribute_info() (añadido en DBI 1.54).

Múltiples Conjuntos de Resultados

Múltiples conjuntos de resultados solo se soportan si el controlador soporta el método more_results() (se hace una excepción para DBD::Sybase).

Actividad de Sentencia que también actualiza atributos dbh

Algunos controladores pueden actualizar uno o más atributos dbh después de realizar actividad en un sth hijo. Por ejemplo, DBD::mysql proporciona $dbh->{mysql_insertid} además de $sth->{mysql_insertid}. Actualmente mysql_insertid se soporta a través de un truco, pero se necesita un mecanismo más general para que otros controladores lo usen.

Con DBD::Gofer, un método que establece un error siempre devuelve un undef o una lista vacía. Eso no debería ser un problema en la práctica porque el DBI no define ningún método que devuelva valores significativos mientras también reporta un error.

La subclaseación solo se aplica al lado del cliente

Los atributos RootClass y DbTypeSubclass no se pasan al servidor Gofer.

ADVERTENCIAS PARA MÉTODOS ESPECÍFICOS

last_insert_id

Para habilitar el uso de last_insert_id necesitas indicarle a DBD::Gofer que te gustaría usarlo. Lo haces añadiendo un "go_last_insert_id_args" atributo a las do() o prepare() llamadas a métodos. Por ejemplo:

$dbh->do($sql, { go_last_insert_id_args => [...] });

o

$sth = $dbh->prepare($sql, { go_last_insert_id_args => [...] });

La referencia al array debe contener los argumentos que deseas pasar al last_insert_id() método.

execute_for_fetch

Los métodos de array bind_param_array() y execute_array() están soportados. Cuando execute_array() es llamado los datos se serializan y ejecutan en un único viaje de ida y vuelta al servidor Gofer. Esto lo hace muy rápido, pero requiere suficiente memoria para almacenar todos los datos serializados.

El execute_for_fetch() método actualmente no está optimizado, usa el comportamiento de respaldo del DBI de ejecutar cada tupla individualmente. (Podría implementarse como un envoltorio para execute_array() - parches bienvenidos.)

TRANSPORTES

DBD::Gofer no se preocupa por transportar solicitudes y respuestas de un lado a otro. Para eso usa módulos de transporte Gofer especiales.

Los módulos de transporte Gofer usualmente vienen en pares: uno para el controlador 'cliente' DBD::Gofer y uno para el extremo 'servidor' remoto. Tienen nombres muy similares:

DBD::Gofer::Transport::<foo>
DBI::Gofer::Transport::<foo>

A veces los transportes en los lados DBD y DBI pueden tener nombres diferentes. Por ejemplo DBD::Gofer::Transport::http se usa típicamente con DBI::Gofer::Transport::mod_perl (los módulos DBD::Gofer::Transport::http y DBI::Gofer::Transport::mod_perl son parte de la distribución GoferTransport-http).

Transportes incluidos

Varios módulos de transporte son provistos con DBD::Gofer:

null

El transporte null es el más simple de todos. No transporta realmente la solicitud a ningún lado. Solo serializa (congela) la solicitud en una cadena, luego la descongela de vuelta en una estructura de datos antes de pasarla a DBI::Gofer::Execute para ejecutarla. El mismo congelar y descongelar se aplica a los resultados.

El transporte null es la mejor manera de probar si tu aplicación funcionará con Gofer. Solo establece la variable de entorno DBI_AUTOPROXY a ""dbi:Gofer:transport=null;policy=pedantic"" (ver "Usando DBI_AUTOPROXY" más abajo) y ejecuta tu aplicación, o idealmente su suite de pruebas, como de costumbre.

No toma ningún parámetro.

pipeone

El transporte pipeone lanza un subproceso para cada solicitud. Pasa la solicitud y lee la respuesta.

El hecho de que se inicie un nuevo subproceso para cada solicitud asegura que el lado del servidor sea verdaderamente sin estado. Aunque esto hace que el transporte sea muy lento, es útil como una manera de probar que tu aplicación no depende del estado por conexión, como tablas temporales, persistiendo entre solicitudes.

También es útil tanto como prueba de concepto como como clase base para el controlador de flujo.

stream

El controlador stream también lanza un subproceso y escribe solicitudes y lee respuestas, como el transporte pipeone. En este caso, sin embargo, el subproceso se espera que maneje más de una solicitud. (Aunque será reiniciado automáticamente si termina.)

Este es el primer transporte que es verdaderamente útil porque puede lanzar el subproceso en una máquina remota usando "ssh". Esto significa que ahora puedes usar DBD::Gofer para acceder fácilmente a cualquier base de datos que sea accesible desde cualquier sistema al que puedas iniciar sesión. También obtienes todos los beneficios de ssh, incluyendo encriptación y compresión opcional.

Ver "Usando DBI_AUTOPROXY" más abajo para un ejemplo.

Otros transportes

Implementar un transporte Gofer es muy simple, y más transportes son muy bienvenidos. Solo echa un vistazo a cualquier transporte existente que sea similar a tus necesidades.

http

Ver la distribución GoferTransport-http en CPAN: http://search.cpan.org/dist/GoferTransport-http/

Gearman

Sé que Ask Bjørn Hansen ha implementado un transporte para el "gearman" sistema de trabajos distribuido, aunque no está en CPAN al momento de escribir esto.

CONECTANDO

Simplemente antepone a tu DSN existente ""dbi:Gofer:transport=$transport;dsn="" donde $transport es el nombre del transporte Gofer que quieres usar (ver "TRANSPORTES"). Los atributos "transport" y "dsn" deben ser especificados y el "dsn" atributo debe ser el último.

Otros atributos pueden ser especificados en el DSN para configurar DBD::Gofer y/o el módulo de transporte Gofer que se está usando. Los atributos principales después de "transport"son "url" y "policy". Estos y otros atributos son descritos más abajo.

Usando DBI_AUTOPROXY

La forma más simple de probar DBD::Gofer es establecer la variable de entorno DBI_AUTOPROXY. En este caso no incluyes la parte "dsn=" . Por ejemplo:

export DBI_AUTOPROXY="dbi:Gofer:transport=null"

o, para un ejemplo más útil, prueba:

export DBI_AUTOPROXY="dbi:Gofer:transport=stream;url=ssh:user@example.com"

Atributos de Conexión

Estos atributos pueden ser especificados en el DSN. También pueden ser pasados en el parámetro \%attr del método connect del DBI añadiendo un ""go_"" prefijo al nombre.

transport

Especifica la clase de transporte Gofer a usar. Requerido. Ver "TRANSPORTES" más arriba.

Si el valor no incluye "::" entonces ""DBD::Gofer::Transport::"" es prefijado.

El objeto de transporte puede ser accedido vía $h->{go_transport}.

dsn

Especifica el DSN para que el lado remoto se conecte. Requerido, y debe ser el último.

url

Usado para decirle al transporte a dónde conectarse. La forma exacta del valor depende del transporte usado.

policy

Especifica la política a usar. Ver "CONFIGURANDO LA POLÍTICA DE COMPORTAMIENTO".

Si el valor no incluye "::" entonces ""DBD::Gofer::Policy"" es prefijado.

El objeto de política puede ser accedido vía $h->{go_policy}.

timeout

Especifica un tiempo de espera, en segundos, a usar cuando se esperan respuestas del lado del servidor.

retry_limit

Especifica el número de veces que se reintentará una solicitud fallida. El valor por defecto es 0.

retry_hook

Especifica una referencia a código a ser llamada para decidir si una solicitud fallida debe ser reintentada. La referencia a código es llamada así:

$transport = $h->{go_transport};
$retry = $transport->go_retry_hook->($request, $response, $transport);

Si devuelve verdadero entonces la solicitud será reintentada, hasta el "retry_limit". Si devuelve un valor falso pero definido entonces la solicitud no será reintentada. Si devuelve undef entonces se usará el comportamiento por defecto, como si "retry_hook" no hubiera sido especificado.

El comportamiento por defecto es reintentar solicitudes donde $request->is_idempotent es verdadero, o el mensaje de error coincide con "/induced by DBI_GOFER_RANDOM/".

cache

Especifica que se debe realizar un almacenamiento en caché del lado del cliente. El valor es el nombre de una clase de caché a usar.

Cualquier clase que implemente los métodos get($key) y set($key, $value) puede ser usada. Eso incluye muchas clases de caché potentes en CPAN, incluyendo las distribuciones Cache y Cache::Cache.

Puedes usar ""cache=1"" como un atajo para ""cache=DBI::Util::CacheMemory"". Ver DBI::Util::CacheMemory para una descripción de esta simple y rápida caché por defecto.

El objeto de caché puede ser accedido vía $h->go_cache. Por ejemplo:

$dbh->go_cache->clear; # libera la memoria usada por la caché

Las claves de la caché son las solicitudes congeladas (serializadas), y los valores son las respuestas congeladas.

El comportamiento por defecto es usar la caché solo para solicitudes donde $request->is_idempotent es verdadero (es decir, el dbh tiene el atributo ReadOnly establecido o la sentencia SQL es obviamente un SELECT sin una cláusula FOR UPDATE.)

Para un control aún mayor puedes usar el "go_cache" atributo para pasar un objeto de caché instanciado. Métodos individuales, incluyendo >prepare(), también puede especificar cachés alternativas mediante el "go_cache" atributo. Por ejemplo, para especificar que no se realice caché para una consulta particular, podría usar

$sth = $dbh->prepare( $sql, { go_cache => 0 } );

Esto se puede usar para implementar diferentes políticas de caché para diferentes sentencias.

Es interesante notar que DBD::Gofer se puede usar para añadir caché del lado del cliente a cualquier aplicación (compatible con gofer), sin cambios en el código y sin necesidad de un servidor gofer. Solo establezca la variable de entorno DBI_AUTOPROXY así:

DBI_AUTOPROXY='dbi:Gofer:transport=null;cache=1'

CONFIGURANDO LA POLÍTICA DE COMPORTAMIENTO

DBD::Gofer soporta un mecanismo de 'política' que le permite ajustar finamente el número de idas y vueltas al servidor Gofer. Las políticas se agrupan en clases (que pueden ser subclaseadas) y se referencian por el nombre de la clase.

La clase DBD::Gofer::Policy::Base es la clase base para todos los paquetes de política y describe todas las políticas disponibles.

Se proporcionan tres paquetes de política con DBD::Gofer:

DBD::Gofer::Policy::pedantic es el más 'transparente' pero el más lento porque hace más idas y vueltas al servidor Gofer.

DBD::Gofer::Policy::classic es un compromiso razonable - es la política por defecto.

DBD::Gofer::Policy::rush es el más rápido, pero puede requerir cambios en el código en sus aplicaciones.

Generalmente la política por defecto "classic" es suficiente. Cuando se prueba por primera vez una aplicación existente con Gofer, es una buena idea empezar con la política "pedantic" primero y luego cambiar a "classic" o a una política personalizada, para las pruebas finales.
