Métodos de la clase

DBI

connect

Este método crea un manejador de base de datos conectándose a una base de datos, y es el equivalente en DBI del método "new". Para conectarse a una base de datos Postgres con un mínimo de parámetros, use la siguiente

sintaxis: 
$dbh = DBI->connect("dbi:Pg:dbname=$dbname", '', '', {AutoCommit => 0})
;

Esto se conecta a la base de datos con el nombre en la variable $dbname en el puerto predeterminado (normalmente 5432) sin ninguna autenticación de

usuario.

La siguiente sentencia de conexión muestra casi todos los parámetros

posibles: 
$dbh = DBI->connect("dbi:Pg:dbname=$dbname;host=$host;port=$port;options=$options",
                    $username,
                    $password,
                    {AutoCommit => 0, RaiseError => 1, PrintError => 0}
                   )
;

Los parámetros que contienen caracteres inusuales como espacios pueden ir entre comillas simples alrededor del valor, y las comillas simples y las barras invertidas pueden escaparse con una barra invertida, p. ej. "dbi:Pg:dbname='\'spacey\' na

me';host=$host".

Si no se proporciona un parámetro, el método connect() primero buscará variables de entorno específicas y luego recurrirá a valores predeterminados

codificados:

------------------------------------------------------

hostaddr     PGHOSTADDR              socket de dominio local
port         PGPORT                  5432
dbname*      PGDATABASE              identificador de usuario actual
username     PGUSER                  identificador de usuario actual
password     PGPASSWORD              (ninguno)
options      PGOPTIONS               (ninguno)
service      PGSERVICE               (ninguno)
sslmode      PGSSLMODE
(ninguno)

* También puede usar los alias "db" o "database

Si los valores de nombre de usuario y contraseña pasados a través de connect() están indefinidos (a diferencia de ser simplemente cadenas vacías), DBI usará las variables de entorno DBI_USER y DBI_PASS si

existen.

También puede conectarse usando un archivo de conexión de servicio. Los nombres de servicio pueden definirse en un archivo de servicio por usuario o en un archivo de todo el sistema. Si el mismo nombre de servicio existe tanto en el archivo de usuario como en el del sistema, el archivo de usuario tiene prioridad. De forma predeterminada, el archivo de servicio por usuario se llama ~/.pg_service.conf. En Microsoft Windows, se llama %APPDATA% \postgresql\.pg_service.conf (donde %APPDATA% se refiere al subdirectorio Application Data en el perfil del usuario). Se puede especificar un nombre de archivo diferente estableciendo la variable de entorno PGSERVICEFILE. El archivo de todo el sistema se llama pg_service.conf. La ubicación de este archivo se puede controlar estableciendo la variable de entorno PGSYSCONFDIR. Para usar uno de los servicios con nombre dentro del archivo, establezca el nombre usando ya sea el parámetro service o la variable de entorno PGSERVICE. Tenga en cuenta que al conectarse de esta manera, solo deben usarse los parámetros mínimos. Por ejemplo, para conectarse a un servicio llamado "zephyr", podría

usar: 
$dbh = DBI->connect("dbi:Pg:service=zephyr", '', '')
;

También podría establecer $ENV{PGSERVICE} en "zephyr" y conectarse

así: 
$dbh = DBI->connect("dbi:Pg:", '', '')
;

El formato del archivo pg_service.conf es simplemente un nombre de servicio entre corchetes, seguido de un parámetro por línea en el formato nombre=valor. Por

ejemplo: 
[zephyr]

user=wisp
password=W$2Hc00YSgP
port=6543

prepare

$sth = $dbh->prepare($statement, \%attr)
;

ADVERTENCIA: DBD::Pg ahora (desde la versión 1.40) usa sentencias preparadas verdaderas enviándolas al backend para ser preparadas por el servidor de Postgres. Las sentencias que eran legales antes pueden dejar de funcionar. Vea más abajo para obtener

detalles.

El método prepare prepara una sentencia para su posterior ejecución. PostgreSQL soporta sentencias preparadas, lo que permite a DBD::Pg enviar la consulta solo una vez y simplemente enviar los argumentos en cada llamada posterior a "execute". DBD::Pg puede usar estas sentencias preparadas en el lado del servidor, o puede simplemente enviar la consulta completa al servidor cada vez. La mejor manera se elige automáticamente para cada consulta. Esto será suficiente para la mayoría de los usuarios: siga leyendo para una explicación más detallada y algunas banderas

opcionales.

Las consultas que no comienzan con la palabra "SELECT", "INSERT", "UPDATE" o "DELETE" nunca se envían como sentencias preparadas en el lado del

servidor.

Decidir si usar o no sentencias preparadas depende de muchos factores, pero puede forzar su uso o no uso usando el atributo pg_server_prepare al llamar a "prepare". Establecer esto en falso significa nunca usar sentencias preparadas. Establecer pg_server_prepare en verdadero significa que las sentencias preparadas deben usarse siempre que sea posible. Este es el valor

predeterminado.

El atributo pg_server_prepare también se puede establecer en el momento de la conexión

así: 
$dbh = DBI->connect($DBNAME, $DBUSER, $DBPASS,
                    { AutoCommit => 0,
                      RaiseError => 1,
                      pg_server_prepare => 0,
                    })
;

o puede establecerlo después de que se cree su manejador de base de

datos: 
$dbh->{pg_server_prepare} =
1;

Para habilitarlo solo para una sentencia en

particular: 
$sth = $dbh->prepare("SELECT id FROM mytable WHERE val = ?",
                     { pg_server_prepare => 1 })
;

Incluso puede alternar entre los dos mientras

trabaja: 
$sth->{pg_server_prepare} = 1;
$sth->execute(22);
$sth->{pg_server_prepare} = 0;
$sth->execute(44);
$sth->{pg_server_prepare} = 1;
$sth->execute(66)
;

En el ejemplo anterior, el primer execute usará la sentencia preparada previamente. El segundo execute no lo hará, pero construirá la consulta en una sola cadena y la enviará al servidor. El tercero actuará como el primero y solo enviará los argumentos. Incluso si alterna de un lado a otro, una sentencia solo se prepara una

vez.

Usar sentencias preparadas es en teoría bastante más rápido: no solo el backend de PostgreSQL solo tiene que preparar la consulta una vez, sino que DBD::Pg ya no tiene que preocuparse por comillar cada valor antes de enviarlo al

servidor.

Sin embargo, hay algunas desventajas. El servidor no siempre puede elegir el plan de análisis ideal porque no conocerá los argumentos de antemano. Pero para la mayoría de las situaciones en las que ejecutará datos similares muchas veces, el plan predeterminado probablemente funcionará bien. Programas como PgBouncer que almacenan en caché conexiones a un nivel bajo no deben usar sentencias preparadas a través de DBD::Pg, o deben tener especial cuidado en la aplicación para tener en cuenta el hecho de que las sentencias preparadas no se comparten entre conexiones de base de datos. Una discusión más detallada sobre este tema está fuera del alcance de esta documentación: por favor consulte la lista de correo pgsql-performance, http://archives.postgresql.org/pgsql-performance

/

Solo ciertos comandos se enviarán a una preparación en el lado del servidor: actualmente estos incluyen "SELECT", "INSERT", "UPDATE" y "DELETE". DBD::Pg usa un esquema de nombra simple para las propias sentencias preparadas: dbdpg_XY_Z, donde Y es el PID actual, X es 'p' o 'n' (dependiendo de si el PID es un número positivo o negativo), y Z es un número que comienza en 1 y aumenta cada vez que se prepara una nueva sentencia. Este número se rastrea a nivel del manejador de base de datos, por lo que múltiples manejadores de sentencia no

colisionarán.

No puede enviar más de un comando a la vez en el mismo comando prepare (separándolos con punto y coma) cuando usa preparaciones en el lado del

servidor.

El "PREPARE" real generalmente no se realiza hasta que se llama al primer execute, debido al hecho de que la información sobre los tipos de datos (proporcionada por "bind_param") puede proporcionarse después de la preparación pero antes de la

ejecución.

Una preparación en el lado del servidor puede ocurrir antes del primer "execute", pero solo si el servidor puede manejar la preparación en el lado del servidor, y la sentencia no contiene marcadores de posición. También será preparada si el atributo pg_prepare_now se pasa y se establece en un valor verdadero. De manera similar, el atributo pg_prepare_now se puede establecer en 0 para asegurar que la sentencia no se prepare inmediatamente, aunque los casos en los que desearía esto son muy raros. Finalmente, puede establecer el comportamiento predeterminado de todas las sentencias prepare estableciendo el atributo pg_prepare_now en el manejador de base de

datos: 
$dbh->{pg_prepare_now} =
1;

Los dos ejemplos siguientes se prepararán de

inmediato: 
$sth->prepare("SELECT 123"); ## no placeholders
$sth->prepare("SELECT 123, ?", {pg_prepare_now => 1})
;

Los dos ejemplos siguientes NO se prepararán de

inmediato: 
$sth->prepare("SELECT 123, ?"); ## has a placeholder
$sth->prepare("SELECT 123", {pg_prepare_now => 0})
;

Hay momentos en los que puede querer preparar una sentencia usted mismo. Para hacerlo, simplemente envíe la sentencia "PREPARE" directamente al servidor (p. ej. con el método "do"). Cree un manejador de sentencia y establezca el nombre preparado a través del atributo pg_prepare_name. El manejador de sentencia se puede crear con una sentencia ficticia, ya que no se ejecutará. Sin embargo, debe tener el mismo número de marcadores de posición que su sentencia preparada.

Ejemplo: 
$dbh->do('PREPARE mystat AS SELECT COUNT(*) FROM pg_class WHERE reltuples < ?');
$sth = $dbh->prepare('SELECT ?');
$sth->bind_param(1, 1, SQL_INTEGER);
$sth->{pg_prepare_name} = 'mystat';
$sth->execute(123)
;

Lo anterior ejecutará el equivalente de esta consulta en el

backend: 
EXECUTE mystat(123)
;

que es el equivalente

a: 
SELECT COUNT(*) FROM pg_class WHERE reltuples <
123;

Puede forzar a DBD::Pg a enviar su consulta directamente al servidor agregando el atributo pg_direct a su llamada prepare. Esto no se recomienda, pero se agrega por si lo

necesita.

Marcadores de

posición

Hay tres tipos de marcadores de posición que se pueden usar en DBD::Pg. El primero es el tipo "signo de interrogación", en el que cada marcador de posición se representa con un solo carácter de signo de interrogación. Este es el método recomendado por las especificaciones de DBI y es el más portable. Cada signo de interrogación se reemplaza internamente por un "signo de dólar número" en el orden en el que aparecen en la consulta (importante cuando se usa "bind_param")

.

El segundo tipo de marcador de posición es "signos de dólar números". Este es el método que Postgres usa internamente y en general probablemente sea el mejor método a usar si no necesita compatibilidad con otros sistemas de base de datos. DBD::Pg, como PostgreSQL, permite que el mismo número se use más de una vez en la consulta. Los números deben comenzar con "1" e incrementarse en un valor (pero pueden aparecer en cualquier orden dentro de la consulta). Si el mismo número aparece más de una vez en una consulta, se trata como un solo parámetro y todas las instancias se reemplazan a la vez.

Ejemplos:

No

legal: 
$SQL = 'SELECT count(*) FROM pg_class WHERE relpages > $2'; # Does not start with 1
$SQL = 'SELECT count(*) FROM pg_class WHERE relpages BETWEEN $1 AND $3'; # Missing
2

Legal

: 
$SQL = 'SELECT count(*) FROM pg_class WHERE relpages > $1';
$SQL = 'SELECT count(*) FROM pg_class WHERE relpages BETWEEN $1 AND $2';
$SQL = 'SELECT count(*) FROM pg_class WHERE relpages BETWEEN $2 AND $1'; # legal but confusing
$SQL = 'SELECT count(*) FROM pg_class WHERE relpages BETWEEN $1 AND $2 AND reltuples > $1';
$SQL = 'SELECT count(*) FROM pg_class WHERE relpages > $1 AND reltuples >
$1';

En la sentencia final de arriba, DBI piensa que solo hay un marcador de posición, por lo que esta sentencia reemplazará ambos marcadores de

posición: 
$sth->bind_param(1, 2045)
;

Mientras que un execute simple sin llamadas a bind_param requiere solo un argumento

también: 
$sth->execute(2045)
;

El tipo final de marcador de posición es "parámetros con nombre" en el formato ":foo". Aunque DBD::Pg soporta esta sintaxis, su uso se desaconseja en favor de los signos de dólar

números.

Los diferentes tipos de marcadores de posición no se pueden mezclar dentro de una sentencia, pero puede usar diferentes para cada manejador de sentencia que tenga. Esto es confuso como mínimo, así que manténgase con un estilo dentro de su

programa.

Si sus consultas usan operadores que contienen signos de interrogación (p. ej. algunos de los operadores geométricos nativos de Postgres y los operadores JSON) o rebanadas de array (p. ej. "data[100:300]"), hay métodos para instruir a DBD::Pg a no tratar algunos símbolos como marcadores de posición. Primero, puede simplemente agregar una barra invertida antes del inicio de un marcador de posición, y DBD::Pg eliminará la barra invertida y no tratará el carácter como un marcador de

posición.

También puede decirle a DBD::Pg que ignore cualquier marcador de posición que no sea de signo de dólar estableciendo el atributo pg_placeholder_dollaronly ya sea a nivel del manejador de base de datos o del manejador de sentencia.

Ejemplos: 
$dbh->{pg_placeholder_dollaronly} = 1;
$sth = $dbh->prepare(q{SELECT * FROM mytable WHERE lseg1 ?# lseg2 AND name = $1});
$sth->execute('segname')
;

Alternativamente, puede establecerlo en el momento de la

preparación: 
$sth = $dbh->prepare(q{SELECT * FROM mytable WHERE lseg1 ?-| lseg2 AND name = $1},
  {pg_placeholder_dollaronly => 1});
$sth->execute('segname')
;

Si sus consultas usan rebanadas de array pero aún quiere usar signos de interrogación como marcadores de posición, puede decirle a DBD::Pg que ignore solo los marcadores de posición de dos puntos estableciendo el atributo "pg_placeholder_nocolons" de la misma manera.

Ejemplos: 
$dbh->{pg_placeholder_nocolons} = 1;
$sth = $dbh->prepare(q{SELECT array[1:2] FROM mytable WHERE id = ?});
$sth->execute(1)
;

De nuevo, puede establecerlo en el momento de la preparación

también: 
$sth = $dbh->prepare(q{SELECT array[1:2] FROM mytable WHERE id = ?},
  {pg_placeholder_nocolons => 1});
$sth->execute(1)
;

Debe tenerse en cuenta que los marcadores de posición solo funcionan cuando se usan fuera de un contexto de cadena literal; es decir, los siguientes ejemplos no definirán/usarán ningún marcador de posición debido a que aparecen dentro de cadenas dentro del

SQL: 
$sth = $dbh->prepare(q{SELECT id FROM mytable WHERE text LIKE '%?'});
$dbh->do(q{DO LANGUAGE plpgsql $$ BEGIN RAISE NOTICE ?; END $$}, undef, $message)
;

Consulte la documentación de marcadores de posición de DBI para obtener más

detalles.

Intenta devolver el id del último valor insertado en una tabla. Puede proporcionar un nombre de secuencia (preferido) o proporcionar un nombre de tabla con esquema opcional, y DBD::Pg intentará encontrar la secuencia por sí mismo. El valor actual de la secuencia es devuelto por una llamada a la función CURRVAL() de PostgreSQL. Esto fallará si la secuencia aún no ha sido usada en la conexión de base de datos

last_insert_id.

Tenga en cuenta que este método está lejos de ser infalible, así que asegúrese de que su script lo use correctamente. Específicamente, asegúrese de que se llame inmediatamente después de la inserción, y que la inserción no agregue un valor a la columna que usa la secuencia como valor predeterminado. Sin embargo, como estamos usando secuencias, puede estar seguro de que el valor que obtuvo de vuelta no ha sido usado por ningún otro

Se desconecta de la base de datos Postgres. Cualquier cambio no confirmado será revertido al desconectarse. Es buena política siempre llamar explícitamente a commit o rollback en algún punto antes de desconectarse, en lugar de depender del comportamiento predeterminado de

Puntos de

La versión 8.0 de PostgreSQL introdujo el concepto de puntos de guardado, que permite revertir transacciones a un cierto punto sin afectar al resto de la transacción. DBD::Pg fomenta el uso de los siguientes métodos para controlar los puntos de

guardado:

"pg_savepoint"

Crea un punto de guardado. Esto fallará a menos que esté dentro de una transacción. El único argumento es el nombre del punto de guardado. Tenga en cuenta que PostgreSQL SÍ permite que existan múltiples puntos de guardado con el mismo

nombre.

;

"pg_rollback_to"

Revierte la base de datos a un punto de guardado con nombre, descartando cualquier trabajo realizado después de ese punto. Si existe más de un punto de guardado con ese nombre, revierte al creado más

recientemente.

;

"pg_release"

Libera (o elimina) un punto de guardado con nombre. Si existe más de un punto de guardado con ese nombre, solo destruirá el creado más recientemente. Tenga en cuenta que todos los puntos de guardado creados después del que se está liberando también se

Es posible enviar una consulta al backend y hacer que su script realice otro trabajo mientras la consulta se ejecuta en el backend. Tanto las consultas enviadas por el método "do", como por el método "execute" pueden ser enviadas de forma asíncrona. El uso básico es el

print "Async prepare/execute example:\n";
$sth = $dbh->prepare("SELECT long_running_query(1)", {pg_async => PG_ASYNC});

  $sth2->pg_result();

Soporte de

COPY

DBD::Pg permite la lectura y almacenamiento rápido (masivo) de datos usando el comando COPY. El proceso básico es usar "$dbh->do" para emitir un comando COPY, y luego ya sea agregar filas usando "pg_putcopydata", o leerlas usando "pg_getcopydata"

.

El primer paso es poner al servidor en modo "COPY". Esto se hace enviando un comando COPY completo al servidor, usando el método "do". Por

ejemplo: 
$dbh->do("COPY foobar FROM STDIN")
;

Esto le diría al servidor que entre en un modo COPY IN (sí, eso es confuso, pero el modo es COPY IN debido al comando COPY FROM). Ahora está listo para recibir información a través del método "pg_putcopydata". La sintaxis completa del comando COPY es más compleja y no está documentada aquí: la documentación canónica de PostgreSQL para COPY se puede encontrar

en:

http://www.postgresql.org/docs/current/static/sql-copy.

html

Una vez que se ha emitido un comando COPY, no se permiten otros comandos SQL hasta que se haya emitido "pg_putcopyend" (para COPY FROM), o se haya llamado a la final "pg_getcopydata" (para COPY TO)

.

Nota: Todos los demás métodos COPY (pg_putline, pg_getline, etc.) están ahora muy desaconsejados en favor de los métodos pg_getcopydata, pg_putcopydata y

pg_putcopyend.

pg_getcopydata

Se usa para recuperar datos de una tabla después de que el servidor haya sido puesto en modo COPY OUT llamando a "COPY tablename TO STDOUT". Los datos siempre se devuelven una fila de datos a la vez. Nota que el servidor añadirá un salto de línea a cada fila

devuelta.

El primer argumento de pg_getcopydata es la variable en la que se almacenarán los datos (esta variable no debería ser indefinida, o podría lanzar una advertencia, aunque puede ser una referencia). El método pg_getcopydata devuelve un número mayor que 1 que indica el nuevo tamaño de la variable, o un -1 cuando el COPY ha terminado. Una vez que se ha devuelto un -1, no es necesaria ninguna otra acción, ya que el modo COPY ya se habrá terminado.

Ejemplo: 
$dbh->do("COPY mytable TO STDOUT");
my @data;
my $x=0;
1 while $dbh->pg_getcopydata($data[$x++]) >=
0;

También hay una variación de este método llamada pg_getcopydata_async, que, como su nombre sugiere, retorna inmediatamente. La única diferencia con el método original es que esta versión puede devolver un 0, indicando que la fila aún no está lista para ser entregada. Cuando esto sucede, la variable no ha sido cambiada, y necesitarás llamar al método de nuevo hasta que obtengas un resultado distinto de cero. (Los datos siempre se devuelven una fila de datos a la vez.

)

pg_putcopydata

Se usa para poner datos en una tabla después de que el servidor haya sido puesto en modo COPY IN llamando a "COPY tablename FROM STDIN". El único argumento es el dato que quieres insertar. Emite un pg_putcopyend() cuando hayas añadido todas tus

filas.

El delimitador por defecto es un carácter de tabulación, pero esto puede ser cambiado en la declaración COPY. Devuelve un 1 en una entrada exitosa.

Ejemplos: 
## Ejemplo simple:
$dbh->do("COPY mytable FROM STDIN");

$dbh->pg_putcopydata("314\tMushroom\t8\n");

$dbh->do("COPY mytable(flavor, slices) FROM STDIN WITH DELIMITER '~'");

$dbh->pg_putcopydata("Mushroom~314\n");
$dbh->pg_putcopydata("Anchovies~6\n");

Cuando hayas terminado con pg_putcopydata, llama a pg_putcopyend para informar al

Cursore

Aunque PostgreSQL soporta cursores, no se han utilizado en la implementación actual. Cuando se creó DBD::Pg, los cursores en PostgreSQL solo podían usarse dentro de un bloque de transacción. Como solo se permite un bloque de transacción a la vez, esto habría implicado la restricción de no usar ningún "SELECT" anidado. Por lo tanto, el método "execute" obtiene todos los datos de una vez en estructuras de datos ubicadas en la aplicación de front-end. ¡Este hecho debe ser considerado al seleccionar grandes cantidades de

datos!

Puedes usar cursores en tu aplicación, pero necesitarás hacer un poco de trabajo. Primero debes declarar tu cursor. Ahora puedes emitir consultas contra el cursor, luego seleccionar contra tus consultas. Esto típicamente resulta en un doble bucle, como

Tipo de dato

bool

La implementación actual de PostgreSQL devuelve 't' para verdadero y 'f' para falso. Desde el punto de vista de Perl, esta es una elección bastante desafortunada. Por lo tanto, DBD::Pg traduce el resultado para el tipo de dato "BOOL" de una manera Perlish: 'f' se convierte en el número 0 y 't' se convierte en el número 1. De esta manera, la aplicación no tiene que comprobar los valores devueltos específicos de la base de datos para el tipo de datos "BOOL" porque Perl trata 0 como falso y 1 como verdadero. Puede establecer el atributo pg_bool_tf en un valor verdadero para cambiar los valores de vuelta a 't' y 'f' si lo

desea.

Los valores booleanos se pueden pasar a PostgreSQL como

TRUE, 't', 'true', 'y', 'yes' o '1' para verdadero
y FALSE, 'f', 'false', 'n', 'no' o '0' para falso.
