d

TAF.

Transparent Application Failover (TAF) es una función en OCI que permite a los clientes reconectarse automáticamente a una instancia en caso de fallo de la instancia. La reconexión ocurre automáticamente desde dentro de la biblioteca OCI (Oracle Call Interface)

.

TAF soporta una función de callback que, una vez registrada, es llamada por el controlador para informarle lo que está sucediendo y que le permite, hasta cierto punto, controlar cómo se maneja el

failover.

Necesita configurar TAF en su instancia primero y ese proceso está fuera del alcance de este documento. Una vez que TAF está habilitado, simplemente establece "odbc_taf_callback" a una referencia de código que debería verse

así: 
sub taf_handler {
 my ($dbh, $event, $type) = @_;
 # do something here
}

DBD::ODBC pasará el handle de conexión ($dbh), el tipo de evento de Oracle (OCI_FO_END, OCI_FO_ABORT, OCI_FO_REAUTH, OCI_FO_BEGIN, OCI_FO_ERROR) y el tipo de Oracle (OCI_FO_NONE, OCI_FO_SESSION, OCI_FO_SELECT, OCI_FO_TXNAL). Consulte la documentación de Oracle para saber qué son estos. Puede importar estas constantes usando la etiqueta de exportación :taf. Si su instancia no tiene TAF habilitado, es probable que un intento de registrar un callback falle, pero esto depende del controlador (todo lo que DBD::ODBC hace es hacer una llamada a SQLSetConnectAttr y proporcionar un envoltorio de C que llama a su subrutina de Perl)

.

Aquí hay un ejemplo

comentado: 
my $h = DBI->connect('dbi:ODBC:oracle','xxx','yyy',
                     {RaiseError => 1,
                      odbc_taf_callback => \&taf_handler}) or die "connect";
while (1) {
    my $s = $h->selectall_arrayref(q/select 1 from dual/);
    sleep 5;
}
sub taf_handler {
   my ($dbh, $event, $type) = @_;
   #print "taf_handler $dbh, $event, $type\n";
   if ($event == OCI_FO_BEGIN) {
       print "Instance unavailable, stand by\n";
       print "Your TAF type is : ",
           ($type == OCI_FO_NONE ? "NONE" :
                ($type == OCI_FO_SESSION ? "SESSION" :
                     ($type == OCI_FO_SELECT ? "SELECT" : "?"))) , "\n";
       # start a counter and each time OCI_FO_ERROR is passed in we will
       # count down and abort the failover when we hit 0.
       $count = 10;
       return 0;
   } elsif ($event == OCI_FO_ERROR) {
       # We get an OCI_FO_ERROR each time the failover fails
       # sleep a while until the count hits 0
       if (--$count < 1) {
           print "Giving up\n";
           return 0;            # give up
       } else {
           print "Retrying...\n";
           sleep 1;
           return OCI_FO_RETRY; # tell Oracle to retry
       }
   } elsif ($event == OCI_FO_REAUTH) {
       print "Failed over user. Resuming Services\n";
   } elsif ($event == OCI_FO_END) {
       print "Failover ended - resuming\n";
   }
   return 0;
}

IMPORTANTE Los escalares de Perl que son UTF-8 y se envían a través de la API ODBC serán convertidos a UTF-16 y pasados a las APIs anchas de ODBC o señalados como SQL_WCHARs (por ejemplo, en el caso de columnas vinculadas). Los datos recuperados que son caracteres anchos son convertidos de UTF-16 a UTF-8. Sin embargo, usted debe darse cuenta de que la mayoría de los controladores ODBC no soportan UTF-16, ODBC solo habla de caracteres anchos siendo 2 bytes y UCS-2 y UCS-2 y UTF-16 no son lo mismo. UCS-2 solo soporta caracteres Unicode en el primer plano (el Plano Multilingüe Básico o BMP) (puntos de código U+0000 a U+FFFF), los caracteres usados más frecuentemente. Entonces, ¿por qué DBD::ODBC actualmente codifica en UTF-16? Porque para alrededor del 97% de los caracteres Unicode en el rango 0-0xFFFF UCS-2 y UTF-16 son exactamente lo mismo (y donde difieren no hay un carácter Unicode válido ya que el rango U+D800 a U+DFFF está reservado para uso solo como pares sustitutos). Como la API ODBC actualmente usa UCS-2 no soporta caracteres Unicode con puntos de código por encima de 0xFFFF (si sabe mejor me gustaría escucharlo). Sin embargo, porque DBD::ODBC usa codificación UTF-16 usted aún puede insertar caracteres Unicode por encima de 0xFFFF en su base de datos y recuperarlos correctamente pero podrían no estar siendo tratados como un solo carácter Unicode en su base de datos, por ejemplo, un "select length(a_column) from table" con un solo carácter Unicode por encima de 0xFFFF podría devolver 2 y no 1, así que no puede usar funciones de base de datos sobre esos datos como upper/lower/length etc.
