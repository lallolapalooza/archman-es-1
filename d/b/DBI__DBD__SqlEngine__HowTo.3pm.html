¿Tienes una entrada en

el

registro de DBD de DBI? DBI::DBD::SqlEngine espera tener un prefijo único para cada clase de controlador en la cadena de herencia. Es fácil obtener

un

prefijo - simplemente envía una nota al equipo de DBI ("GETTING_HELP" en DBI). Si por alguna razón quieres ocultar tu trabajo, echa un vistazo a Class::Method::Modifiers para ver cómo envolver un método de prefijo privado alrededor de "driver_prefix" existen

te.

Para esta guía, se asume un prefijo de "foo_".

Esqueleto

de ejemplo

package 
DBD::Foo;
use strict;
use warnings;
use base qw(DBI::DBD::SqlEngine);
use DBI ();
our $VERSION = "0.001";
package DBD::Foo::dr;
our @ISA = qw(DBI::DBD::SqlEngine::dr);
our $imp_data_size = 0;
package DBD::Foo::db;
our @ISA = qw(DBI::DBD::SqlEngine::db);
our $imp_data_size = 0;
package DBD::Foo::st;
our @ISA = qw(DBI::DBD::SqlEngine::st);
our $imp_data_size = 0;
package DBD::Foo::Statement;
our @ISA = qw(DBI::DBD::SqlEngine::Statement);
package DBD::Foo::Table;
our @ISA = qw(DBI::DBD::SqlEngine::Table);
1;
Pequeño, ¿eh? Y todo lo que tienes ahora
es

un DBD llamado foo que será capaz de lidiar con tablas temporales, s

iempre que uses SQL::Statement. En entornos de DBI::SQL::Nano, este
DBD no puede hacer nada. Lidiar con atributos propios Antes de empezar

a hacer cosas útiles

con

nuestro controlador de DBI, necesitamos pensar en qué queremos hacer y cómo queremos hacerlo. ¿Necesitamos perillas ajustables

accesibles

por los usuarios? ¿Necesitamos información de estado? Todo esto se maneja en los atributos de los manejadores de base de datos (ten cuidado cuando tu DBD está ejecutándose "detrás" de un proxy de DBD::Gofer). ¿Cómo llegan

los

atributos al DBD y cómo son obtenibles por el usuario? Buena pregunta, pero deberías saberlo porque has leído la documentación de DBI. "DBI::DBD::SqlEngine::db::

FETCH"

y "DBI::DBD::SqlEngine::db::STORE" se encargan de ti - todo lo que necesitan saber es qué nombres de atributos son válidos y mutables o inmutables. Díselos añadiendo "init_valid_attributes" a tu clase db: sub init_valid_attributes { my $dbh = $_[0];

$dbh-> 
SUPER::init_valid_attributes ();
    $dbh->{foo_valid_attrs} = {
        foo_version         => 1,   # contiene la versión de este controlador
        foo_valid_attrs     => 1,   # contiene los atributos válidos de los controladores foo
        foo_readonly_attrs  => 1,   # contiene los atributos inmutables de los controladores foo
        foo_bar             => 1,   # contiene el atributo bar
        foo_baz             => 1,   # contiene el atributo baz
        foo_manager         => 1,   # contiene el gestor de la instancia del controlador
        foo_manager_type    => 1,   # contiene la clase de gestor de la instancia del controlador
    };
    $dbh->{foo_readonly_attrs} = {
        foo_version         => 1,   # asegura que nadie modifique la versión del controlador
        foo_valid_attrs     => 1,   # no permite añadir más atributos válidos ...
        foo_readonly_attrs  => 1,   # ... o hacer mutables los inmutables
        foo_manager         => 1,   # el gestor se establece solo internamente
    };
    return $dbh;
}

Pero ... mi controlador se ejecuta sin un gestor hasta que
alguien

asigna por primera vez un "foo_manager_type". Bueno, no - hay dos lugares donde puedes inicializar valores por defecto: sub init_default_attributes { my ($dbh, $phase) =

@_; 
$dbh->SUPER::init_default_attributes($phase);
    if( 0 == $phase )
    {
        # inicializar todos los atributos que no tienen conocimiento sobre
        # la configuración del usuario desde el DSN o el hash de atributos
        $dbh->{foo_manager_type} = "DBD::Foo::Manager";
    }
    elsif( 1 == $phase )
    {
        # fase de inicialización con más conocimiento desde el DSN o el hash de
        # atributos
        $dbh->{foo_manager} = $dbh->{foo_manager_type}->new();
    }
    return $dbh;
}
Hasta ahora podemos evitar que
los

usuarios usen nuestro controlador de base de datos como almacenamiento de datos para cualquier cosa y todo. Nos preocupa

mos solo por las cosas realmente importantes para la paz en la tierra y atributos similares. Pero de hecho, el controlad
or todavía no puede hacer nada. Puede hacer menos que nada - mientras tanto ya no es un área de almacenamiento estúpida.

Comodidad

del

usuario "DBI::DBD::SqlEngine" desde 0.05 consolida todos los metadatos persistentes de una tabla en una única estructura almacenada en "$dbh->{sql_meta}". Mientras DBI::DBD::SqlEngine proporciona solo acceso de solo lectura a esta estructura, las modificaciones todavía

están

permitidas. Principalmente DBI::DBD::SqlEngine proporciona acceso a través de los establecedores "new_sql_engine_meta", "get_sql_engine_meta", "get_single_table_meta", "set_single_table_meta", "set_sql_engine_meta" y "clear_sql_engine_meta". Esos métodos son fácilmente accesibles por los usuarios a través de la interfaz "$dbh->func ()" proporcionada por DBI. Bueno, muchos usuarios no se sienten cómodos

al 
llamar a
# no requerir extensión para las tablas cars
$dbh->func ("cars", "f_ext", ".csv", "set_sql_engine_meta"
)

; DBI::DBD::SqlEngine inyectará un método en tu controlador para aumentar la comodidad del usuario

para 
permitir:
# no requerir extensión para las tablas cars
$dbh->foo_set_meta ("cars",
"f_ext",

".csv"); Mejor, pero aquí y allá a los usuarios

les 
gusta hacer:
# no requerir extensión para las tablas cars
$dbh->{foo_tables}->{cars}->
{f_ext}

= ".csv"; Esta interfaz se proporciona cuando los DBD derivados definen lo siguiente en "init_valid_attributes" (re-capturar "Lidiar con

atributos 
propios"):
sub init_valid_attributes
{
    my $dbh = $_[0];
    $dbh->SUPER::init_valid_attributes ();
    $dbh->{foo_valid_attrs} = {
        foo_version         => 1,   # contiene la versión de este controlador
        foo_valid_attrs     => 1,   # contiene los atributos válidos de los controladores foo
        foo_readonly_attrs  => 1,   # contiene los atributos inmutables de los controladores foo
        foo_bar             => 1,   # contiene el atributo bar
        foo_baz             => 1,   # contiene el atributo baz
        foo_manager         => 1,   # contiene el gestor de la instancia del controlador
        foo_manager_type    => 1,   # contiene la clase de gestor de la instancia del controlador
        foo_meta            => 1,   # contiene la interfaz pública para modificar los atributos meta de la tabla
    };
    $dbh->{foo_readonly_attrs} = {
        foo_version         => 1,   # asegurar que nadie modifique la versión del controlador
        foo_valid_attrs     => 1,   # no permitir que se añadan más atributos válidos ...
        foo_readonly_attrs  => 1,   # ... ni que se haga mutable lo inmutable
        foo_manager         => 1,   # el gestor se establece solo internamente
        foo_meta            => 1,   # asegurar que la interfaz pública para modificar los atributos meta de la tabla sea inmutable
    };
    $dbh->{foo_meta} = "foo_tables";
    return $dbh;
}

Esto proporciona un hash vinculado en "$dbh->{foo_tables}" y un hash vinculado para los metadatos de cada tabla en "$dbh->{foo_tables}->{$table_name}". Las modificaciones de los atributos meta de la tabla se realizan usando los métodos de la

tabla: 
sub get_table_meta_attr { ... }
sub set_table_meta_attr { ...
}

Ambos métodos pueden ajustar el nombre del atributo por razones de compatibilidad, p. ej. cuando versiones anteriores del DBD permitían usar nombres diferentes para el mismo

indicador: 
my %compat_map = (
                   abc => 'foo_abc',
                   xyz => 'foo_xyz',
                 );
__PACKAGE__->register_compat_map( \%compat_map )
;

Si cualquier modificación del usuario en un atributo meta necesita la reinicialización de la estructura meta (en el caso de "DBI::DBD::SqlEngine" estos son los atributos "f_file", "f_dir", "f_ext" y "f_lockfile"), informe a DBI::DBD::SqlEngine

haciendo 
my %reset_on_modify = (
                        foo_xyz => "foo_bar",
                        foo_abc => "foo_bar",
                      );
__PACKAGE__->register_reset_on_modify( \%reset_on_modify )
;

El siguiente acceso a los metadatos de la tabla forzará a DBI::DBD::SqlEngine a rehacer todo el proceso de inicialización de

metadatos.

Cualquier acción adicional que deba realizarse puede manejarse en "table_meta_attr_changed"

: 
sub table_meta_attr_changed
{
    my ($class, $meta, $attrib, $value) = @_;
    ...
    $class->SUPER::table_meta_attr_changed ($meta, $attrib, $value);
}

Esto se hace antes de que se establezca el nuevo valor en $meta, de modo que el manejador de cambio de atrib

uto puede actuar depen
diendo del valor antiguo.
