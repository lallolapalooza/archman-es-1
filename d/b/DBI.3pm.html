DESCRIPCIÓ

N

DBI es un módulo de acceso a bases de datos para el lenguaje de programación Perl. Define un conjunto de métodos, variables y convenciones que proporcionan una interfaz de base de datos consistente, independiente de la base de datos que se esté

utilizando.

Es importante recordar que DBI es solo una interfaz. DBI es una capa de "pegamento" entre una aplicación y uno o más módulos de controlador de base de datos. Son los módulos de controlador los que hacen la mayor parte del trabajo real. DBI proporciona una interfaz y un marco de trabajo estándar para que los controladores operen dentro de

él.

Este documento a menudo usa términos como referencias, objetos, métodos. Si no está familiarizado con esos términos, sería una buena idea leer al menos los siguientes manuales de perl primero: perlreftut, perldsc, perllol y

perlboot.

9.

.

my $dbh = DBI->connect(...);

roto

El atributo "PrintWarn" controla la impresión de advertencias registradas por el controlador. Si es así, DBI hará efectivamente un "warn("$class $method warning: $DBI::errstr")" donde $class es la clase del controlador y $method es el nombre del método que falló. P. ej.

,

.

Si se desea, las advertencias pueden ser capturadas y procesadas usando un manejador $SIG{__WARN__} o módulos como CGI::Carp y CGI::

ErrorWrap.

ello.

En cuyo caso, el controlador puede optar por obtener los detalles completos de las advertencias solo si el atributo "PrintWarn" es verdadero. Si "PrintWarn" es falso, entonces estos controladores aún deberían indicar el hecho de que hubo advertencias estableciendo la cadena de advertencia, por ejemplo: "3

"RaiseError"

Tipo: booleano,

heredado

El atributo "RaiseError" puede usarse para forzar que los errores lancen excepciones en lugar de simplemente devolver códigos de error de la manera normal. Está "off" por defecto. Cuando se establece en "on", cualquier método que resulte en un error hará que el DBI haga efectivamente un "die("$class $method failed: $DBI::errstr")", donde $class es la clase del controlador y $method es el nombre del método que falló. Por

ejemplo, 
DBD::Oracle::db prepare failed: ... error text here ..
.

Si activas "RaiseError" normalmente desactivarías "PrintError". Si "PrintError" también está activo, entonces el "PrintError" se realiza primero (naturalmente)

.

Típicamente "RaiseError" se usa en conjunto con "eval", o un módulo como Try::Tiny o TryCatch, para capturar la excepción que se ha lanzado y manejarla. Por

ejemplo: 
use Try::Tiny;
try {
  ...
  $sth->execute();
  ...
} catch {
  # $sth->err and $DBI::err will be true if error was from DBI
  warn $_; # print the error (which Try::Tiny puts into $_)
  ... # do whatever you need to deal with the error
}
;

En el bloque catch, la variable $DBI::lasth puede ser útil para diagnóstico e informe si no estás seguro de qué manejador provocó el error. Por ejemplo, $DBI::lasth->{Type} y $DBI::lasth->{Statement}

.

Ver también

"Transactions".

Si quieres desactivar temporalmente "RaiseError" (dentro de una función de biblioteca que probablemente fallará, por ejemplo), la forma recomendada es

así: 
{
  local $h->{RaiseError};  # localize and turn off for this block
  ...
}

El valor original será restaurado automáticamente y de forma fiable por Perl, sin importar cómo se salga del bloque. La misma lógica se aplica a otros atributos, incluyendo "PrintError"

.

"HandleError"

Tipo: referencia a código,

heredado

El atributo "HandleError" puede usarse para proporcionar tu propio comportamiento alternativo en caso de errores. Si se establece en una referencia a un subrutina, entonces esa subrutina se llama cuando se detecta un error (en el mismo punto en el que "RaiseError" y "PrintError" son manejados). También se llama cuando "RaiseWarn" está habilitado y se detecta una

advertencia.

La subrutina se llama con tres parámetros: la cadena del mensaje de error que "RaiseError", "RaiseWarn" o "PrintError" usaría, el manejador DBI que se está usando, y el primer valor que devuelve el método que falló (típicamente undef)

.

Si la subrutina devuelve un valor falso, entonces los atributos "RaiseError", "RaiseWarn" y/o "PrintError" son comprobados y manejados como es

normal.

Por ejemplo, para "die" con un rastreo completo de pila para cualquier

error: 
use Carp;
$h->{HandleError} = sub { confess(shift) }
;

O para convertir errores en

excepciones: 
use Exception; # or your own favourite exception module
$h->{HandleError} = sub { Exception->new('DBI')->raise($_[0]) }
;

Es posible "apilar" múltiples manejadores HandleError usando

clausuras: 
sub your_subroutine {
  my $previous_handler = $h->{HandleError};
  $h->{HandleError} = sub {
    return 1 if $previous_handler and &$previous_handler(@_);
    ... your code here ...
  };
}

Usar un "my" dentro de una subrutina para almacenar el valor anterior de "HandleError" es importante. Ver perlsub y perlref para más información sobre clausuras

.

Es posible que "HandleError" altere el mensaje de error que será usado por "RaiseError", "RaiseWarn" y "PrintError" si devuelve falso. Puede hacerlo alterando el valor de $_[0]. Este ejemplo añade un rastreo de pila a todos los errores y, a diferencia del ejemplo anterior usando Carp::confess, esto funcionará con "PrintError" así como con "RaiseError"

: 
$h->{HandleError} = sub { $_[0]=Carp::longmess($_[0]); 0; }
;

También es posible que "HandleError" oculte un error, hasta cierto grado, usando "set_err" para restablecer $DBI::err y $DBI::errstr, y alterando el valor de retorno del método que falló. Por

ejemplo: 
$h->{HandleError} = sub {
  return 0 unless $_[0] =~ /^\S+ fetchrow_arrayref failed:/;
  return 0 unless $_[1]->err == 1234; # the error to 'hide'
  $h->set_err(undef,undef);   # turn off the error
  $_[2] = [ ... ];    # supply alternative return value
  return 1;
}
;

Esto solo funciona para métodos que devuelven un solo valor y es difícil de hacer fiable (evitando bucles infinitos, por ejemplo), por lo que no se recomienda para uso general. Si encuentras un buen uso para ello, por favor házmelo

saber.

"HandleSetErr"

Tipo: referencia a código,

heredado

El atributo "HandleSetErr" puede usarse para interceptar el establecimiento de los valores "err", "errstr", y "state" del manejador. Si se establece en una referencia a una subrutina, entonces esa subrutina se llama cada vez que set_err() es llamado, típicamente por el controlador o una

subclase.

La subrutina se llama con cinco argumentos, los primeros cinco que se pasaron a set_err(): el manejador, los valores "err", "errstr", y "state" que se están estableciendo, y el nombre del método. Estos pueden alterarse cambiando los valores en el arreglo @_ . El valor de retorno afecta el comportamiento de set_err(), ver "set_err" para

detalles.

Es posible "apilar" múltiples manejadores HandleSetErr usando clausuras. Ver "HandleError" para un

ejemplo.

Las subrutinas "HandleSetErr" y "HandleError" difieren de maneras sutiles pero significativas. HandleError solo se invoca en el punto en el que el DBI está a punto de devolver el control a la aplicación con "err" establecido como verdadero. No es invocado por el fallo de un método que ha sido llamado por otro método del DBI. HandleSetErr, por otro lado, se llama cada vez que set_err() es llamado con un valor "err" definido, incluso si es falso. Así que no es solo para errores, a pesar del nombre, sino también para estados de advertencia e información. El método set_err(), y por lo tanto HandleSetErr, puede ser llamado múltiples veces dentro de un método y típicamente se invoca desde lo profundo del código del

controlador.

En teoría, un controlador puede usar el valor de retorno de HandleSetErr a través de set_err() para decidir si continuar o no. Si set_err() devuelve una lista vacía, indicando que el código HandleSetErr ha "manejado" el "error", el controlador podría continuar en lugar de fallar (si eso es una cosa razonable de hacer). No se espera que esto sea común y cualquier caso así debe estar claramente marcado en la documentación del controlador y discutido en la lista de correo

dbi-dev.

El atributo "HandleSetErr" se añadió en DBI 1.

41.

El valor por defecto es típicamente 0 (cero) o 80 bytes, pero puede variar entre controladores. Las aplicaciones que recuperen campos largos deben establecer este valor en un poco más grande que el valor más largo del campo largo a

"Callbacks"

Tipo: referencia a un

hash

El mecanismo de callbacks de DBI le permite interceptar, y opcionalmente reemplazar, cualquier llamada a un método en un manejador de DBI. En el extremo, le permite convertirse en un titiritero, engañando a la aplicación de cualquier manera que

desee.

El atributo "Callbacks" es una referencia a un hash donde las claves son nombres de métodos de DBI y los valores son referencias a código. Para cada clave que nombra un método, DBI ejecutará la referencia a código asociada antes de ejecutar el

método.

Los argumentos de la referencia a código serán los mismos que los del método, incluyendo el invocante (un manejador de base de datos o un manejador de sentencia). Por ejemplo, digamos que se quiere hacer un callback a algún código en una llamada a prepare

(): 
$dbh->{Callbacks} = {
    prepare => sub {
        my ($dbh, $query, $attrs) = @_;
        print "Preparing q{$query}\n"
    },
}
;

El callback se ejecutaría entonces cuando se llame al método prepare()

: 
$dbh->prepare('SELECT 1')
;

Y la salida, por supuesto,

sería: 
Preparing q{SELECT
1}

Dado que los callbacks se ejecutan antes de los métodos con los que están asociados, puede modificar los argumentos antes de que se pasen a la llamada al método. Por ejemplo, para asegurarse de que todas las llamadas a prepare() se preparen inmediatamente por DBD::Pg, añada un callback que se asegure de que el atributo "pg_prepare_now" siempre esté

establecido: 
my $dbh = DBI->connect($dsn, $username, $auth, {
    Callbacks => {
        prepare => sub {
            $_[2] ||= {};
            $_[2]->{pg_prepare_now} = 1;
            return; # must return nothing
        },
    }
})
;

Tenga en cuenta que estamos editando el contenido de @_ directamente. En este caso, hemos creado el hash de atributos si no se pasa a la llamada "prepare"

.

También puede evitar que el método asociado se ejecute nunca. Mientras se ejecuta un callback, $_ contiene el nombre del método. (Esto permite que múltiples callbacks compartan la misma referencia a código y aún así sepan qué método fue llamado). Para evitar que el método se ejecute, simplemente "undef $_". Por ejemplo, si quisiera deshabilitar las llamadas a ping(), podría hacer

esto: 
$dbh->{Callbacks} = {
    ping => sub {
        # tell dispatch to not call the method:
        undef $_;
        # return this value instead:
        return "42 bells";
    }
}
;

Como con otros atributos, Callbacks puede especificarse en un manejador o a través de los atributos de connect(). Los Callbacks también pueden aplicarse a los métodos de una sentencia en un manejador de sentencia. Por

ejemplo: 
$sth->{Callbacks} = {
    execute => sub {
        print "Executing ", shift->{Statement}, "\n";
    }
}
;

El atributo "Callbacks" de un manejador de base de datos no se copia a ningún manejador de sentencia que cree. Por lo tanto, establecer callbacks para un manejador de sentencia requiere que usted establezca el atributo "Callbacks" en el manejador de sentencia usted mismo, como en el ejemplo de arriba, o use la clave especial "ChildCallbacks" descrita más

abajo.

Claves Especiales en el Atributo

Callbacks

Además de los nombres de métodos de los manejadores de DBI, la referencia a hash "Callbacks" soporta cuatro claves

adicionales.

La primera es la clave "ChildCallbacks". Cuando un manejador de sentencia es creado a partir de un manejador de base de datos, la clave "ChildCallbacks" del atributo "Callbacks" del manejador de base de datos, si existe, se convierte en el nuevo atributo "Callbacks" del manejador de sentencia. Esto le permite definir callbacks para todos los manejadores de sentencia creados a partir de un manejador de base de datos. Por ejemplo, si quisiera contar cuántas veces "execute" fue llamado en su aplicación, podría

escribir: 
my $exec_count = 0;
my $dbh = DBI->connect( $dsn, $username, $auth, {
    Callbacks => {
        ChildCallbacks => {
            execute => sub { $exec_count++; return; }
        }
    }
});
END {
    print "The execute method was called $exec_count times\n";
}

Las otras tres claves especiales son "connect_cached.new", "connect_cached.connected", y "connect_cached.reused". Estas claves definen callbacks que se llaman cuando connect_cached() es llamado, pero permiten diferentes comportamientos dependiendo de si un nuevo manejador es creado o un manejador es devuelto. El callback es invocado con estos argumentos: "$dbh, $dsn, $user, $auth

, $attr".

Por ejemplo, algunas aplicaciones usan connect_cached() para conectarse con "AutoCommit" habilitado y luego deshabilitar "AutoCommit" temporalmente para transacciones. Si connect_cached() es llamado durante una transacción, quizás en un método de utilidad, entonces podría seleccionar el mismo manejador en caché y luego forzar "AutoCommit", forzando un commit de la transacción. Vea la documentación de "connect_cached" para una manera de lidiar con eso. Aquí describiremos un enfoque alternativo usando un

callback.

Dado que los callbacks "connect_cached.new" y "connect_cached.reused" son invocados antes de que connect_cached() haya aplicado los atributos de conexión, puede usarlos para editar los atributos que serán aplicados. Para evitar que un manejador en caché tenga sus transacciones confirmadas antes de ser devuelto, puede eliminar el atributo "AutoCommit" en un callback "connect_cached.reused",

así: 
my $cb = {
    'connect_cached.reused' => sub { delete $_[4]->{AutoCommit} },
};
sub dbh {
    my $self = shift;
    DBI->connect_cached( $dsn, $username, $auth, {
        PrintError => 0,
        RaiseError => 1,
        AutoCommit => 1,
        Callbacks  => $cb,
    });
}

El resultado es que los nuevos manejadores de base de datos se crean con "AutoCommit" habilitado, mientras que los manejadores de base de datos en caché se dejan en el estado de transacción en el que se encontraban cuando se recuperaron de la

caché.

Tenga en cuenta que también hemos usado una variable léxica para la referencia a hash de callbacks. Esto es porque connect_cached() devuelve un nuevo manejador de base de datos si cualquiera de los atributos pasados a él han cambiado. Si usáramos una referencia a hash en línea, connect_cached() devolvería un nuevo manejador de base de datos cada vez. Lo cual derrotaría bastante el

propósito.

Una aplicación más común para los callbacks es establecer el estado de la conexión solo cuando se hace una nueva conexión (por connect() o connect_cached()). Añadir un callback al método connected (cuando se usa "connect") o a través de "connect_cached.connected" (cuando se usa connect_cached()) hace esto fácil. El método connected() es una operación sin efecto por defecto (a menos que usted subclase DBI y lo cambie). DBI lo llama para indicar que una nueva conexión ha sido hecha y que los atributos de conexión han sido establecidos todos. Puede darle un poco de funcionalidad añadida aplicándole un callback. Por ejemplo, para asegurarse de que MySQL entiende el SQL compatible con ANSI de su aplicación, configúrelo

así: 
my $dbh = DBI->connect($dsn, $username, $auth, {
    Callbacks => {
        connected => sub {
            shift->do(q{
                SET SESSION sql_mode='ansi,strict_trans_tables,no_auto_value_on_zero';
            });
            return;
        },
    }
})
;

Si está usando connect_cached(), use el callback "connect_cached.connected", en su lugar. Esto es porque connected() es llamado tanto para manejadores de base de datos nuevos como reutilizados, pero usted quiere ejecutar un callback solo cuando se devuelve un nuevo manejador de base de datos. Por ejemplo, para establecer la zona horaria en la conexión a una base de datos PostgreSQL, pruebe

esto: 
my $cb = {
    'connect_cached.connected' => sub {
        shift->do('SET timezone = UTC');
    }
};
sub dbh {
    my $self = shift;
    DBI->connect_cached( $dsn, $username, $auth, { Callbacks => $cb });
}

Una limitación significativa con los callbacks es que solo puede haber uno por método por manejador. Esto significa que es fácil para un uso de callbacks interferir con, o típicamente simplemente sobrescribir, otro uso de callbacks. Por esta razón, los módulos que usan callbacks deberían documentar este hecho claramente para que los autores de aplicaciones puedan decir si el uso de callbacks por el módulo entrará en conflicto con el uso de callbacks por la

aplicación.

Podría ser capaz de sortear este problema tomando una copia del callback original y llamándolo dentro del suyo. Por

ejemplo: 
my $prev_cb = $h->{Callbacks}{method_name};
$h->{Callbacks}{method_name} = sub {
  if ($prev_cb) {
      my @result = $prev_cb->(@_);
      return @result if not $_; # $prev_cb vetoed call
  }
  ... your callback logic here ...
}
;

implementación.

"prepare"

$sth = $dbh->prepare($statement)          or die $dbh->errstr;
$sth = $dbh->prepare($statement, \%attr)  or die $dbh->
errstr;

Prepara una sentencia para su posterior ejecución por el motor de la base de datos y devuelve una referencia a un objeto manejador de

sentencia.

El manejador de sentencia devuelto se puede usar para obtener atributos de la sentencia e invocar el método "execute". Ver "Métodos del Manejador de

Sentencia".

Los drivers para motores sin el concepto de preparar una sentencia generalmente simplemente almacenarán la sentencia en el manejador devuelto y la procesarán cuando "$sth->execute" sea llamado. Esos drivers es poco probable que den mucha información útil sobre la sentencia, como "$sth->{NUM_OF_FIELDS}", hasta después de que "$sth->execute" haya sido llamado. Las aplicaciones portables deberían tener esto en

cuenta.

En general, los drivers de DBI no analizan el contenido de la sentencia (además de simplemente contar cualquier Marcador de Posición). La sentencia se pasa directamente al motor de la base de datos, a veces conocido como modo de paso directo (pass-thru). Esto tiene ventajas y desventajas. Por el lado positivo, puedes acceder a toda la funcionalidad del motor que se está usando. Por el lado negativo, estás limitado si estás usando un motor simple, y necesitas tener un cuidado extra si escribes aplicaciones destinadas a ser portables entre

motores.

Las aplicaciones portables no deberían asumir que una nueva sentencia puede ser preparada y/o ejecutada mientras aún se están obteniendo resultados de una sentencia

anterior.

Algunas herramientas de SQL de línea de comandos usan terminadores de sentencia, como un punto y coma, para indicar el final de una sentencia. Tales terminadores normalmente no deberían usarse con el

DBI.

"prepare_cached"

$sth = $dbh->prepare_cached($statement, \%attr,
$if_active)

Como "prepare" excepto que el manejador de sentencia devuelto se almacenará en un hash asociado con el $dbh. Si se hace otra llamada a "prepare_cached" con los mismos valores de parámetros $statement y %attr, entonces el $sth correspondiente en caché se devolverá sin contactar al servidor de la base de datos. Asegúrate de entender las advertencias y advertencias (cautions and caveats) señaladas más

abajo.

El El parámetro $if_active te permite ajustar el comportamiento si un manejador de sentencia ya en caché todavía está Activo (Active). Hay varias

alternativas:
0: Se generará una advertencia (warning), y se llamará a finish() en el manejador de sentencia antes de que sea devuelto. Este es el comportamiento por defecto si no se pasa
$if_active.
1: finish() se llamará en el manejador de sentencia, pero la advertencia se
suprime.
2: Desactiva cualquier
comprobación.
3: El manejador de sentencia activo existente será eliminado de la caché y un nuevo manejador de sentencia será preparado y puesto en caché en su lugar. Esta es la opción más segura porque no afecta al estado del manejador antiguo, simplemente lo elimina de la caché. [Añadido en DBI 1.
40]

  my @values = @{$field_values}{@fields};
  my $qualifier = "";
  $qualifier = "where ".join(" and ", map { "$_=?" } @fields) if @fields;
  $sth = $dbh->prepare_cached("SELECT * FROM $table $qualifier");
  return $dbh->selectall_arrayref($sth, {}, @values);
}

Caveat emptor: Este almacenamiento en caché puede ser útil en algunas aplicaciones, pero también puede causar problemas y debe usarse con cuidado. Aquí hay un caso artificial donde el almacenamiento en caché causaría un problema

significativo: 
my $sth = $dbh->prepare_cached('SELECT * FROM foo WHERE bar=?');
$sth->execute(...);
while (my $data = $sth->fetchrow_hashref) {
  # más tarde, en algún otro código llamado dentro del bucle...
  my $sth2 = $dbh->prepare_cached('SELECT * FROM foo WHERE bar=?');
  $sth2->execute(...);
  while (my $data2 = $sth2->fetchrow_arrayref) {
    do_stuff(...);
  }
}

En este ejemplo, ya que ambos manejadores están preparando exactamente la misma sentencia, $sth2 no será su propio manejador de sentencia, sino un duplicado de $sth devuelto desde la caché. Los resultados ciertamente no serán los que espera. Típicamente el bucle de obtención interno funcionará normalmente, obteniendo todos los registros y terminando cuando no haya más, pero ahora que $sth es el mismo que $sth2 el bucle de obtención externo también

terminará.

Sabrá si se encuentra con este problema porque prepare_cached() generará una advertencia de forma predeterminada (cuando $if_active es falso)

.

La caché utilizada por prepare_cached() está indexada tanto por la sentencia como por cualquier atributo, por lo que también puede evitar este problema haciendo algo

como: 
$sth = $dbh->prepare_cached("...", { dbi_dummy => __FILE__.__LINE__ })
;

lo que asegurará que prepare_cached solo devuelva sentencias almacenadas en caché por esa línea de código en ese archivo

fuente.

Además, para asegurarse de que los atributos pasados sean siempre los mismos, evite pasar referencias en línea. Por ejemplo, el atributo Slice se especifica como una referencia. Asegúrese de declararlo externamente a la llamada a prepare_cached(), de modo que no se cree una nueva referencia de hash en cada llamada. Vea "connect_cached" para más detalles y

ejemplos.

Si desea que la caché sea gestionada de manera inteligente, puede vincular la referencia de hash devuelta por "CachedKids" a un módulo de almacenamiento en caché apropiado, como Tie::Cache::

LRU: 
my $cache;
tie %$cache, 'Tie::Cache::LRU', 500;
$dbh->{CachedKids} =
$cache;

"disconnect"

errstr;

Desconecta la base de datos del manejador de base de datos. "disconnect" típicamente solo se usa antes de salir del programa. El manejador es de poca utilidad después de

desconectar.

El comportamiento de la transacción del método "disconnect" es, lamentablemente, indefinido. Algunos sistemas de bases de datos (como Oracle e Ingres) confirmarán automáticamente cualquier cambio pendiente, pero otros (como Informix) revertirán cualquier cambio pendiente. Las aplicaciones que no usan "AutoCommit" deben llamar explícitamente a "commit" o "rollback" antes de llamar a "disconnect"

.

La base de datos se desconecta automáticamente mediante el método "DESTROY" si todavía está conectada cuando ya no hay referencias al manejador. El método "DESTROY" de cada controlador debe llamar implícitamente a "rollback" para deshacer cualquier cambio no confirmado. Este es un comportamiento vital para asegurar que las transacciones incompletas no se confirmen simplemente porque Perl llama a "DESTROY" en cada objeto antes de salir. Además, no dependa del orden de destrucción de objetos durante la "destrucción global", ya que es

indefinido.

Generalmente, si desea que sus cambios sean confirmados o revertidos cuando se desconecte, entonces debe llamar explícitamente a "commit" o "rollback" antes de

desconectar.

Si se desconecta de una base de datos mientras todavía tiene manejadores de sentencias activos (por ejemplo, manejadores de sentencias SELECT que pueden tener más datos para obtener), recibirá una advertencia. La advertencia puede indicar que un bucle de obtención terminó temprano, quizás debido a un error no capturado. Para evitar la advertencia, llame al método "finish" en los manejadores

activos.

"AutoCommit"

Tipo:

booleano

Si es verdadero, los cambios en la base de datos no se pueden deshacer (revertir). Si es falso, los cambios en la base de datos ocurren automáticamente dentro de una "transacción", que debe ser confirmada (commit) o revertida (rollback) usando los métodos "commit" o "rollback"

.

Los controladores siempre deben tener como valor predeterminado el modo "AutoCommit" (una elección desafortunada en gran parte impuesta al DBI por las convenciones de ODBC y JDBC.

)

Intentar establecer "AutoCommit" a un valor no soportado es un error fatal. Esta es una característica importante del DBI. Las aplicaciones que necesitan comportamiento completo de transacciones pueden establecer "$dbh->{AutoCommit} = 0" (o establecer "AutoCommit" a 0 vía "connect") sin tener que comprobar que el valor se asignó

exitosamente.

Para los fines de esta descripción, podemos dividir las bases de datos en tres

categorías: 
Bases de datos que no soportan transacciones en absoluto.
Bases de datos en las que una transacción está siempre activa.
Bases de datos en las que una transacción debe iniciarse explícitamente (C<'BEGIN WORK'>)
.

* Bases de datos que no soportan transacciones en

absoluto

Para estas bases de datos, intentar desactivar "AutoCommit" es un error fatal. "commit" y "rollback" ambos emiten advertencias sobre ser inefectivos mientras "AutoCommit" está

activo.

* Bases de datos en las que una transacción está siempre

activa

Estas son típicamente bases de datos relacionales comerciales principales con comportamiento de transacciones de "estándar ANSI". Si "AutoCommit" está desactivado, los cambios en la base de datos no tendrán ningún efecto duradero a menos que se llame a "commit" (pero ver también "disconnect"). Si se llama a "rollback" entonces cualquier cambio desde la última confirmación se

deshace.

Si "AutoCommit" está activado, el efecto es el mismo que si el DBI llamara a "commit" automáticamente después de cada operación exitosa en la base de datos. Así que llamar a "commit" o "rollback" explícitamente mientras "AutoCommit" está activado sería inefectivo porque los cambios ya se habrían

confirmado.

Cambiar "AutoCommit" de desactivado a activado desencadenará un

"commit".

Para bases de datos que no soportan un modo específico de auto-commit, el controlador debe confirmar cada sentencia automáticamente usando un "COMMIT" explícito después de que se complete exitosamente (y revertirla usando un "ROLLBACK" explícito si falla). La información de error reportada a la aplicación corresponderá a la sentencia que se ejecutó, a menos que tuviera éxito y la confirmación o reversión

fallara.

* Bases de datos en las que una transacción debe iniciarse

explícitamente

Para estas bases de datos, la intención es que se comporten como bases de datos en las que una transacción está siempre activa (como se describió arriba)

.

Para hacer esto, el controlador iniciará automáticamente una transacción explícita cuando "AutoCommit" se desactive, o después de un "commit" o "rollback" (o cuando la aplicación emita la siguiente operación en la base de datos después de uno de esos eventos)

.

De esta manera, la aplicación no tiene que tratar estas bases de datos como un caso

especial.

Ver "commit", "disconnect" y "Transactions" para otras notas importantes sobre

transacciones.

Una aplicación puede recuperar información de metadatos del DBMS emitiendo consultas apropiadas sobre las vistas del Esquema de Información. MAYÚSCULAS.

Transaccione

s

Las transacciones son una parte fundamental de cualquier sistema de base de datos robusto. Protegen contra errores y corrupción de la base de datos asegurando que conjuntos de cambios relacionados en la base de datos se realicen en unidades atómicas (indivisibles, todo o nada)

.

Esta sección aplica a bases de datos que soportan transacciones y donde "AutoCommit" está desactivado. Ver "AutoCommit" para detalles sobre el uso de "AutoCommit" con varios tipos de bases de

datos.

La forma recomendada de implementar transacciones robustas en aplicaciones Perl es habilitar "RaiseError" y capturar el error que se 'lanza' como una excepción. Por ejemplo, usando Try::

Tiny: 
use Try::Tiny;

$dbh->{AutoCommit} = 0;  # habilitar transacciones, si es posible
$dbh->{RaiseError} = 1;
try {
    foo(...)        # hacer mucho trabajo aquí
    bar(...)        # incluyendo inserciones
    baz(...)        # y actualizaciones
    $dbh->commit;   # confirmar los cambios si llegamos hasta aquí
} catch {
    warn "Transacción abortada porque $_"; # Try::Tiny copia $@ en $_
    # ahora hacer rollback para deshacer los cambios incompletos
    # pero hacerlo en un eval{} ya que también puede fallar
    eval { $dbh->rollback };
    # añadir aquí otro código de limpieza en caso de error de la aplicación
}
;

Si el atributo "RaiseError" no está establecido, entonces las llamadas a DBI necesitarían ser comprobadas manualmente para detectar errores, típicamente

así: 
$h->method(@args) or die $h->
errstr;

Con "RaiseError" establecido, el DBI automáticamente ejecutará "die" si alguna llamada a un método DBI en ese manejador (o un manejador hijo) falla, por lo que no tienes que comprobar el valor de retorno de cada llamada a un método. Ver "RaiseError" para más

detalles.

Una gran ventaja del enfoque con "eval" es que la transacción será revertida correctamente si cualquier código (no solo llamadas a DBI) en la aplicación interna muere por cualquier razón. La gran ventaja de usar el atributo "$h->{RaiseError}" es que todas las llamadas a DBI serán comprobadas automáticamente. Ambas técnicas son fuertemente

recomendadas.

Después de llamar a "commit" o "rollback", muchos controladores no te dejarán obtener datos de un manejador de sentencia "SELECT" previamente activo que sea un hijo del mismo manejador de base de datos. Una manera típica de rodear esto es conectar a la base de datos dos veces y usar una conexión para las sentencias "SELECT"

.

Ver "AutoCommit" y "disconnect

" para otra información i
mportante sobre transacciones.

Hilos y Seguridad de

Hilos

Perl 5.7 y posteriores soportan un nuevo modelo de hilos llamado iThreads. (Los antiguos hilos "estilo 5.005" no son soportados por el DBI.

)

En el modelo iThreads cada hilo tiene su propia copia del intérprete de perl. Cuando se crea un nuevo hilo, el intérprete de perl original es 'clonado' para crear una nueva copia para el nuevo

hilo.

Si el DBI y los controladores son cargados y los manejadores creados antes de que el hilo sea creado, entonces obtendrá una copia clonada del DBI, los controladores y los

manejadores.

Sin embargo, los datos de punteros internos dentro de los manejadores se referirán al DBI y los controladores en el intérprete original. Usar esos manejadores en el nuevo hilo del intérprete no es seguro, por lo que el DBI detecta esto y emite un error fatal en cualquier llamada a un método usando manejadores que no pertenezcan al hilo actual (excepto para DESTROY)

.

Debido a esta (posiblemente temporal) restricción, los hilos recién creados deben hacer sus propias conexiones a la base de datos. Los manejadores no pueden ser compartidos entre

hilos.

Pero CUIDADO, algunas APIs de bases de datos subyacentes (el código que el controlador DBD usa para hablar con la base de datos, a menudo suministrado por el proveedor de la base de datos) no son seguras para hilos. Si no es segura para hilos, entonces permitir que más de un hilo entre al código al mismo tiempo puede causar problemas sutiles/graves. En algunos casos permitir que más de un hilo entre al código, incluso si no es al mismo tiempo, puede causar problemas. Ya has sido

advertido.

Usar DBI con hilos de perl aún no es recomendado para entornos de producción. Para más información ver http://www.perlmonks.org/index.pl?

node_id=288022

Nota: Hay un error en perl 5.8.2 cuando está configurado con hilos y depuración habilitada (error #24463) que causaría que algunas pruebas de DBI fallaran. Estas pruebas han sido deshabilitadas para perl-5.8.2 y

anteriores.

Manejo de Señales y Cancelación de

Operaciones

[Lo siguiente solo aplica a sistemas con manejo de señales tipo unix. Agradecería adiciones para otros sistemas, especialmente Windows.

]

Lo primero que hay que decir es que el manejo de señales en versiones de Perl menores a 5.8 no es seguro. Siempre hay un pequeño riesgo de que Perl se cuelgue y/o genere un volcado de memoria cuando, o después de, manejar una señal, porque la señal podría llegar y ser manejada mientras las estructuras de datos internas están siendo modificadas. Si el código de manejo de señales usara esas mismas estructuras de datos internas, podría causar toda clase de problemas sutiles y no tan sutiles. El riesgo fue reducido con 5.4.4 pero aún estaba presente en todos los perls hasta el 5.8.

0.

A partir de perl 5.8.0, perl implementa el manejo de señales 'seguro' si tu sistema tiene la rutina POSIX sigaction(). Ahora cuando una señal es entregada, perl solo hace una nota de ella pero no ejecuta el manejador %SIG. El manejo es 'diferido' hasta un momento

'seguro'.

Aunque este cambio hizo que el manejo de señales fuera seguro, también llevó a un problema con las señales siendo diferidas por más tiempo del que desearías. Si una señal llegaba mientras se ejecutaba una llamada al sistema, como esperar datos en una conexión de red, la señal es notada y luego la llamada al sistema que se estaba ejecutando retorna con un código de error EINTR para indicar que fue interrumpida. Todo bien hasta

ahora.

El problema surge cuando el código que hizo la llamada al sistema ve el código EINTR y decide que va a llamarla de nuevo. Perl no hace eso, pero el código de bases de datos a veces lo hace. Si eso sucede, entonces el manejador de señales no será llamado hasta después. Quizás mucho

después.

Afortunadamente hay maneras de rodear esto que discutiremos abajo. Desafortunadamente hacen que las señales sean inseguras de

nuevo.

Los dos usos más comunes de las señales en relación con el DBI son para cancelar operaciones cuando el usuario escribe Ctrl-C (interrupción), y para implementar un tiempo de espera usando alarm() y $SIG{AL

RM}.
Cancela
ción
El DBI proporciona un método "cancel" para manejadores de sentencias. El método "cancel" debería abortar la operación actual y está diseñado para ser llamado desde un manejador de señales. Por ejemplo: 
$SIG{INT} = sub { $sth->cancel
};

Sin embargo, pocos controladores implementan esto (el DBI proporciona un método por defecto que simplemente retorna "undef") e, incluso si está implementado, aún existe la posibilidad de que el manejador de sentencia, e incluso el manejador de base de datos padre, no sean utilizables

después.

Si "cancel" retorna verdadero, entonces ha invocado exitosamente la función de cancelación del motor de la base de datos. Si retorna falso, entonces "cancel" falló. Si retorna "undef", entonces el controlador de la base de datos no

tiene cancel impleme
ntado - muy pocos lo tienen.
Tiempo de
Espera
La manera tradicional de implementar un tiempo de espera es establecer $SIG{ALRM}n> para referirse a algún código que será ejecutado cuando llegue una señal ALRM y luego llamar a alarm($seconds) para programar una señal ALRM para que sea entregada $seconds segundos en el futuro. Por ejemplo: 
my $failed;
eval {
  local $SIG{ALRM} = sub { die "TIMEOUT\n" }; # N.B. \n es necesario
  eval {
    alarm($seconds);
    ... código a ejecutar con tiempo de espera aquí (que puede morir) ...
    1;
  } or $failed = 1;
  # el eval externo captura la alarma que podría dispararse JUSTO antes de esta alarm(0)
  alarm(0);  # cancelar alarma (si el código se ejecutó rápido)
  die "$@" if $failed;
  1;
} or $failed = 1;
if ( $failed ) {
  if ( defined $@ and $@ eq "TIMEOUT\n" ) { ... }
  else { ... } # algún otro
error }

El primer (externo) eval se usa para evitar la posibilidad poco probable pero posible de que el "código a ejecutar" muera y la alarma se dispare antes de ser cancelada. Sin el eval externo, si esto sucediera tu programa moriría si no tienes un manejador ALRM o se llamaría a un manejador de alarma no

local.

Desafortunadamente, como se describió arriba, esto no siempre funcionará como se espera, dependiendo de tu versión de perl y el código de base de datos

subyacente.

Con Oracle por ejemplo (DBD::Oracle), si el sistema que aloja la base de datos está caído, la llamada DBI->connect() se colgará dur

ante varios min
utos antes de de
volver un error.

La solución en estos sistemas es usar la rutina POSIX::sigaction() para obtener acceso de bajo nivel a cómo se instala el manejador de

señal.

El código se vería algo así (para el DBD-Oracle connect())

use POSIX qw(:signal_h);
my $mask = POSIX::SigSet->new( SIGALRM ); # señales a enmascarar en el manejador
my $action = POSIX::SigAction->new(
    sub { die "connect timeout\n" },        # la referencia al código del manejador
    $mask,
    # no se usa (perl 5.8.2 y posterior) el interruptor 'safe' o sa_flags
);
my $oldaction = POSIX::SigAction->new();
sigaction( SIGALRM, $action, $oldaction );
my $dbh;
my $failed;
eval {
   eval {
     alarm(5); # segundos antes de que se agote el tiempo
     $dbh = DBI->connect("dbi:Oracle:$dsn" ... );
     1;
   } or $failed = 1;
   alarm(0); # cancelar alarma (si la conexión funcionó rápido)
   die "$@\n" if $failed; # la conexión murió
   1;
} or $failed = 1;
sigaction( SIGALRM, $oldaction );  # restaurar el manejador de señal original
if ( $failed ) {
  if ( defined $@ and $@ eq "connect timeout\n" ) {...}
  else { # la conexión murió }
}

Subclaseando la

DBI

La DBI puede ser subclaseada y extendida igual que cualquier otro módulo orientado a objetos. Antes de hablar sobre cómo hacer eso, es importante tener claro sobre las varias clases de la DBI y cómo trabajan

juntas.

Por defecto "$dbh = DBI->connect(...)" devuelve un $dbh bendito en la clase "DBI::db". Y el método "$dbh->prepare" devuelve un $sth bendito en la clase "DBI::st" (en realidad simplemente cambia los últimos cuatro caracteres de la clase del manejador de llamada a "::st")

.

El '"DBI"' inicial se conoce como la 'clase raíz' y el '"::db"' extra o '"::st"' son los 'sufijos de tipo de manejador'. Si quieres subclasear la DBI necesitarás poner tus métodos anulados en las clases apropiadas. Por ejemplo, si quieres usar una clase raíz de "MySubDBI" y anular los métodos do(), prepare() y execute(), entonces tus métodos do() y prepare() deberían estar en la clase "MySubDBI::db" y el método execute() debería estar en la clase "MySubDBI::

st".

Para configurar la jerarquía de herencia la variable @ISA en "MySubDBI::db" debería incluir "DBI::db" y la variable @ISA en "MySubDBI::st" debería incluir "DBI::st". La clase raíz "MySubDBI" en sí misma no es actualmente usada para nada visible y así, aparte de configurar @ISA para incluir "DBI", puede dejarse

vacía.

Así que, habiendo puesto tus métodos anulados en las clases correctas, y configurado la jerarquía de herencia, ¿cómo haces que la DBI los use? Tienes dos opciones, o bien una llamada a método estático usando el nombre de tu

subclase: 
$dbh = MySubDBI->connect(...)
;

o especificando un atributo "Roo

tClass" 
$dbh = DBI->connect(..., { RootClass => 'MySubDBI' })
;

Si se usan ambas formas entonces el atributo tiene

precedencia.

Las únicas diferencias entre las dos son que usar un atributo RootClass explícito hará a) que la DBI intente automáticamente cargar un módulo con ese nombre si la clase no existe, y b) no llamará a tu método MySubDBI::connect(), si tienes

uno.

Cuando se está usando subclaseo entonces, después de una nueva conexión exitosa, el método DBI->connect llama automáticamente

a: 
$dbh->connected($dsn, $user, $pass, \%attr)
;

El método por defecto no hace nada. La llamada se hace solo para simplificar cualquier configuración post-conexión que tu subclase quiera realizar. Los parámetros son los mismos que se pasan a DBI->connect. Si tu subclase proporciona un método connected, debería ser parte del paquete MySubDBI::

db.

Una cosa más a notar: debes dejar que la DBI haga la creación del manejador. Si quieres anular el método connect() en tu clase *::dr entonces aún debe llamar a SUPER::connect para obtener un $dbh con el cual trabajar. De manera similar, un método prepare() anulado en *::db aún debe llamar a SUPER::prepare para obtener un $sth. Si intentas crear tus propios manejadores usando bless() entonces encontrarás que la DBI los rechazará con un error "is not a DBI handle (has no magic)

".

Aquí hay un breve ejemplo de una subclase de la DBI. Un ejemplo más completo se puede encontrar en t/subclass.t en la distribución de la

DBI. 
package MySubDBI;
use strict;
use DBI;
our @ISA = qw(DBI);
package MySubDBI::db;
our @ISA = qw(DBI::db);
sub prepare {
  my ($dbh, @args) = @_;
  my $sth = $dbh->SUPER::prepare(@args)
      or return;
  $sth->{private_mysubdbi_info} = { foo => 'bar' };
  return $sth;
}
package MySubDBI::st;
our @ISA = qw(DBI::st);
sub fetch {
  my ($sth, @args) = @_;
  my $row = $sth->SUPER::fetch(@args)
      or return;
  do_something_magical_with_row_data($row)
      or return $sth->set_err(1234, "The magic failed", undef, "fetch");
  return $row;
}

Al llamar a un SUPER::método que devuelve un manejador, ten cuidado de verificar el valor de retorno antes de intentar hacer otras cosas con él en tu método anulado. Esto es especialmente importante si quieres establecer un atributo hash en el manejador, ya que la autovivificación de Perl te morderá (in)convenientemente creando una referencia a hash no bendita, la cual tu método luego devolverá con resultados generalmente confusos más adelante como el error "dbih_getcom handle HASH(0xa4451a8) is not a DBI handle (has no magic". Es mejor verificar justo después de la llamada y devolver undef inmediatamente en caso de error, igual que lo haría la DBI y igual que el ejemplo de

arriba.

Si tu método necesita registrar un error debería llamar al método set_err() con el código de error y la cadena de error, como se muestra en el ejemplo de arriba. El código de error y la cadena de error serán registrados en el manejador y disponibles vía "$h->err" y $DBI::errstr etc. El método set_err() siempre devuelve un undef o una lista vacía según corresponda. Dado que tu método debería casi siempre devolver un undef o una lista vacía tan pronto como se detecta un error es útil simplemente devolver lo que set_err() devuelve, como se muestra en el ejemplo de

arriba.

Si el manejador tiene "RaiseError", "PrintError", o "HandleError" etc. establecido entonces el método set_err() los respetará. Esto significa que si "RaiseError" está establecido entonces set_err() no devolverá de la manera normal sino que 'lanzará una excepción' que puede ser capturada con un bloque "e

val".

Puedes almacenar datos privados en los manejadores de la DBI vía "$h->{private_..._*}". Ver la entrada bajo "ATTRIBUTES COMMON

TO ALL HANDLES" para información
y advertencias importantes.

TRAZAD

O

La DBI tiene un poderoso mecanismo de trazadonismo incorporado. Le permite ver lo que sucede "entre bastidores", tanto dentro de DBI como en los controladores que está

utilizando.

Configuración de

Traza

Qué detalles se escriben en la salida de traza está controlado por una combinación de un nivel de traza, un entero de 0 a 15, y un conjunto de indicadores de traza que están activados o desactivados. En conjunto, esto se conoce como configuración de traza y se almacenan juntos en un solo entero. Para uso normal, solo necesita establecer el nivel de traza, y generalmente solo a un valor entre 1 y

4.

Cada manejador tiene su propia configuración de traza, y DBI también. Cuando llama a un método, DBI fusiona la configuración del manejador con la suya duran

te la duración de la llamada: los indicadores de traza del manejador se combinan con OR a los indicadores de traza de DBI, y si el manejador tiene un nivel
de traza más alto, el nivel de traza de DBI se eleva para igualarlo. La configuración de traza anterior de DBI se restaura cuando el método llamado retorna.

Niveles de

Traza

Traza Los niveles son los

siguientes: 
0 - Traza deshabilitada.
1 - Traza de llamadas a métodos de nivel superior de DBI que retornan con resultados o errores.
2 - Como arriba, añadiendo traza de la entrada de métodos de nivel superior con parámetros.
3 - Como arriba, añadiendo algo de información de alto nivel del controlador
    y algo de información interna de DBI.
4 - Como arriba, añadiendo información más detallada del controlador.
    Este es el primer nivel para rastrear todas las filas que se recuperan.
5 a 15 - Como arriba pero con más y más información
interna.

El nivel de traza 1 es el mejor para una vista general simple de lo que está sucediendo. Los niveles de traza 2 a 4 son una buena opción para trazado de propósito general. Los niveles 5 y superiores son mejor reservarlos para investigar un problema específico, cuando necesita ver "dentro" del controlador y

DBI.

La salida de traza es detallada y típicamente muy útil. Gran parte de la

salida de traza se formatea usando la función "neat", por lo que las cad
enas en la salida de traza pueden ser editadas y truncadas por esa función.

Indicadores de

Traza

Traza Los indicadores se usan para habilitar el rastreo de actividades específicas dentro de DBI y los controladores. DBI define algunos indicadores de traza y los controladores pueden definir otros. Los nombres de indicadores de traza de DBI comienzan con una letra mayúscula y los nombres específicos del controlador comienzan con una letra minúscula, como es

habitual.

Actualmente DBI define estos indicadores de

traza: 
ALL - activar todos los indicadores de DBI y del controlador (no recomendado)
SQL - rastrear sentencias SQL ejecutadas
      (aún no implementado en DBI pero implementado en algunos DBDs)
CON - rastrear el proceso de conexión
ENC - rastrear la codificación (traducciones unicode etc.)
      (aún no implementado en DBI pero implementado en algunos DBDs)
DBD - rastrear solo mensajes de DBD
      (no implementado por todos los DBDs aún)
TXN - rastrear transacciones
      (no implementado en todos los DBDs
aún)

Los métodos "parse_trace_flags" y "parse_trace_flag" se usan para convertir nombres de indicadores de traza en los indicadores de bits enteros correspondiente

s
.

Habilitar

Traza

El método "$h->trace" establece la configuración de traza para un manejador y "DBI->trace" hace lo mismo para

DBI.

Además del método "trace", puede habilitar la misma información de traza, y dirigir la salida a un archivo, estableciendo la variable de entorno "DBI_TRACE" antes de iniciar Perl. Vea "DBI_TRACE" para más

información.

Finalmente, puede establecer, u obtener, la configuración de traza para un manejador usando el atributo "Trace

Todos esos métodos usan parse_trace_flags() y por lo tanto le permiten establecer tanto el nivel de traza como múltiples indicadores de traza usando una cadena que contiene el nivel de traza y/o los nombres de los indicadores separados por el carácter de barra vertical (""|"") o coma ("",""). Por

ejemplo:

Salida de

Traza

Inicialmente la salida de traza se escribe en "STDERR". Tanto el método "$h->trace" como "DBI->trace" toman un parámetro opcional $trace_file, que puede ser tanto el nombre de un archivo a ser abierto por DBI en modo de anexar, o una referencia a un manejador de archivo existente escribible (posiblemente con capas). Si $trace_file es un nombre de archivo, y puede ser abierto en modo de anexar, o $trace_file es un manejador de archivo escribible, entonces toda la salida de traza (actualmente incluyendo la de otros manejadores) se redirige a ese archivo. Se genera una advertencia si $trace_file no puede abrirse o no es

escribible.

Llamadas posteriores a trace() sin $trace_file no alteran a dónde se envía la salida de traza. Si $trace_file está indefinido, la salida de traza se envía a "STDERR" y, si la traza anterior se abrió con $trace_file como nombre de archivo, el archivo de traza anterior se cierra; si $trace_file era un manejador de archivo, el manejador de archivo no se

cierra.

NOTA: Si $trace_file se especifica como un manejador de archivo, el manejador de archivo no debe cerrarse hasta que todas las operaciones de DBI se completen, o la aplicación haya restablecido el archivo de traza mediante otra llamada a trace() que cambie e

l archivo
de traza.

Una aplicación más compleja de trazado a un manejador de archivo con capas es el uso de una capa personalizada (Refiérase a Perlio::via para detalles sobre cómo crear capas PerlIO personalizadas.). Considere una aplicación con el siguiente módulo de

package MyFancyLogger;
sub new
{
    my $self = {};
    my $fh;
    open $fh, '>', 'fancylog.log';
    $self->{_fh} = $fh;
    $self->{_buf} = '';
    return bless $self, shift;
}
sub log
{
    my $self = shift;
    return unless exists $self->{_fh};
    my $fh = $self->{_fh};
    $self->{_buf} .= shift;
#
# DBI nos alimenta piezas a la vez, así que acumula una línea completa
# antes de la salida
#
    print $fh "At ", scalar localtime(), ':', $self->{_buf}, "\n" and
    $self->{_buf} = ''
        if $self->{_buf}=~tr/\n//;
}
sub close {
    my $self = shift;
    return unless exists $self->{_fh};
    my $fh = $self->{_fh};
    print $fh "At ", scalar localtime(), ':', $self->{_buf}, "\n" and
    $self->{_buf} = ''
        if $self->{_buf};
    close $fh;
    delete $self->{_fh};
}
1;

Para redirigir las trazas de DBI a este registrador se requiere crear un paquete para la

capa: 
package PerlIO::via::MyFancyLogLayer;
sub PUSHED
{
    my ($class,$mode,$fh) = @_;
    my $logger;
    return bless \$logger,$class;
}
sub OPEN {
    my ($self, $path, $mode, $fh) = @_;
    #
    # $path es en realidad nuestro objeto registrador
    #
    $$self = $path;
    return 1;
}
sub WRITE
{
    my ($self, $buf, $fh) = @_;
    $$self->log($buf);
    return length($buf);
}
sub CLOSE {
    my $self = shift;
    $$self->close();
    return 0;
}
1;

usando

open my $fh, '>:via(MyFancyLogLayer)', MyFancyLogger->new();

;

Ahora toda la salida de traza será procesada por el método log() de MyF

ancyL
