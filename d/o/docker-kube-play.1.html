NOMBRE

podman-kube-play - Crea contenedores, pods y volúmenes basados en YAML de Kubernetes

SINOPSIS

podman kube play [opciones] archivo.yml|-|https://website.io/archivo.yml

DESCRIPCIÓN

podman kube play lee un archivo estructurado de YAML de Kubernetes. Recrea los contenedores, pods o volúmenes descritos en el YAML. Los contenedores dentro de un pod se inician, y se genera el ID del nuevo Pod o el nombre del nuevo Volumen. Si el archivo YAML se especifica como "-", entonces podman kube play lee el archivo YAML desde la entrada estándar. La entrada también puede ser una URL que apunte a un archivo YAML, como https://podman.io/demo.yml. podman kube play lee el YAML de la URL y crea pods y contenedores a partir de él.

Usando la opción de línea de comandos --down, también es capaz de desmantelar los pods creados por una ejecución anterior de podman kube play.

Usando la opción de línea de comandos --replace, desmantela los pods (si los hay) creados por una ejecución anterior de podman kube play y recrea los pods con el archivo YAML de Kubernetes.

Idealmente, el archivo de entrada es creado por el comando Podman (ver podman-kube-generate(1)). Esto garantiza una importación fluida y resultados esperados.

Actualmente, los tipos de Kubernetes admitidos son:

  • Pod
  • Deployment
  • PersistentVolumeClaim
  • ConfigMap
  • Secret
  • DaemonSet
  • Job

Pods o Deployments de Kubernetes

Solo cinco tipos de volúmenes son compatibles con kube play: los tipos de volumen de *hostPath*, *emptyDir*, *configMap*, *persistentVolumeClaim* y *image*.

  • Al usar el tipo de volumen *hostPath*, solo se admiten los subtipos *default (empty)*, *DirectoryOrCreate*, *Directory*, *FileOrCreate*, *File*, *Socket*, *CharDevice* y *BlockDevice*. Podman interpreta el valor de *hostPath* *path* como una ruta de archivo cuando contiene al menos una barra inclinada, de lo contrario Podman trata el valor como el nombre de un volumen con nombre.
  • Al usar un *persistentVolumeClaim*, el valor de *claimName* es el nombre del volumen con nombre de Podman.
  • Al usar un volumen *emptyDir*, Podman crea un volumen anónimo que se adjunta a los contenedores que se ejecutan dentro del pod y se elimina una vez que se elimina el pod.
  • Al usar un volumen *configMap*, Podman crea un volumen anónimo que se adjunta a los contenedores que se ejecutan dentro del pod y se elimina una vez que se elimina el pod.
  • Al usar un volumen *image*, Podman crea un volumen de imagen de solo lectura con una subruta vacía (se monta la imagen completa). La imagen ya debe existir localmente. Solo se admite en modo rootful.

Nota: La política de reinicio predeterminada para los contenedores es always. Puede cambiar el valor predeterminado estableciendo el campo restartPolicy en la especificación.

Nota: Al reproducir un YAML de kube con contenedores init, el contenedor init se crea con el valor de tipo init once. Para cambiar el tipo predeterminado, use la anotación io.podman.annotations.init.container.type para establecer el tipo en always.

Nota: Los tipos de volumen *hostPath* creados por kube play reciben una etiqueta compartida SELinux (z), los montajes bind no se vuelven a etiquetar (use chcon -t container_file_t -R <directorio>).

Nota: Para establecer userns de un pod, use la anotación io.podman.annotations.userns en la definición del pod/deployment. Por ejemplo, la anotación io.podman.annotations.userns=keep-id le dice a Podman que cree un espacio de nombres de usuario donde la UID:GID del usuario rootless actual se mapean a los mismos valores en el contenedor. Esto se puede anular con la bandera --userns.

Nota: Use la anotación io.podman.annotations.volumes-from para montar volúmenes de un contenedor en otro. Puede montar volúmenes de múltiples contenedores de origen en un contenedor de destino. Los contenedores de origen que pertenecen al mismo pod deben definirse antes del contenedor de origen en el YAML de kube. El formato de la anotación es io.podman.annotations.volumes-from/contenedorDestino: "contenedorOrigen1:opcionesMontaje1;contenedorOrigen2:opcionesMontaje2".

Nota: Si se utiliza la etiqueta :latest, Podman intenta extraer la imagen de un registro. Si la imagen se compiló localmente con Podman o Buildah, tiene localhost como dominio, en ese caso, Podman usa la imagen del almacén local incluso si tiene la etiqueta :latest.

Nota: El comando podman play kube es un alias de podman kube play y realiza la misma función.

Nota: El comando podman kube down se puede usar para detener y eliminar pods o contenedores basados en el mismo YAML de Kubernetes utilizado por podman kube play para crearlos.

Nota: Para personalizar el nombre del contenedor infra creado durante podman kube play, use la anotación io.podman.annotations.infra.name en la definición del pod. Esta anotación se establece automáticamente al generar un YAML de kube a partir de un pod que se creó con la bandera --infra-name establecida.

Nota: Use la anotación io.podman.annotations.pids-limit/$nombreContenedor para configurar el límite de pids del pod.

Nota: Use la anotación io.podman.annotations.cpuset/$nombreContenedor para restringir la ejecución de un contenedor a un conjunto específico de núcleos de CPU. Esto es equivalente a la opción --cpuset-cpus=número en podman-run(1).

Nota: Use la anotación io.podman.annotations.memory-nodes/$nombreContenedor para restringir las asignaciones de memoria de un contenedor a un conjunto específico de nodos de memoria en sistemas NUMA. Esto es equivalente a la opción --cpuset-mems=nodos en podman-run(1).

PersistentVolumeClaims de Kubernetes

Un PersistentVolumeClaim de Kubernetes representa un volumen con nombre de Podman. Solo el nombre de PersistentVolumeClaim es requerido por Podman para crear un volumen. Las anotaciones de Kubernetes se pueden usar para aprovechar las opciones disponibles para los volúmenes de Podman.

  • volume.podman.io/driver
  • volume.podman.io/device
  • volume.podman.io/type
  • volume.podman.io/uid
  • volume.podman.io/gid
  • volume.podman.io/mount-options
  • volume.podman.io/import-source
  • volume.podman.io/image

Use volume.podman.io/import-source para importar el contenido del archivo tar (.tar, .tar.gz, .tgz, .bzip, .tar.xz, .txz, .tar.zst) especificado en el valor de la anotación al volumen de Podman creado

Kube play es capaz de construir imágenes sobre la marcha dadas las estructuras de directorios y Containerfiles correctas. Esta opción aún no está disponible para clientes remotos, incluidas las máquinas Mac y Windows (excluyendo WSL2). Considere el siguiente extracto de un archivo YAML:

apiVersion: v1
kind: Pod
metadata:
...
spec:
  containers:
  - name: container
    image: foobar
...

Si hay un directorio llamado foobar en el directorio de trabajo actual con un archivo llamado Containerfile o Dockerfile, Podman kube play compila esa imagen y la nombra foobar. Una estructura de directorio de ejemplo para este ejemplo se vería así:

|- misarchivoskube
    |- miarchivoplay.yaml
    |- foobar
         |- Containerfile

La compilación considera a foobar como el directorio de contexto para la compilación. Si hay una imagen en el almacenamiento local llamada foobar, la imagen no se compila a menos que se use la bandera --build. Use --build=false para deshabilitar completamente las compilaciones.

Kube play admite selectores de dispositivos CDI (Container Device Interface) para compartir dispositivos de host (por ejemplo, GPUs) con contenedores. El formato de configuración sigue la gestión de recursos extendidos de Kubernetes:

apiVersion: v1
kind: Pod
spec:
  containers:
  - name: container
    resources:
      limits:
        nvidia.com/gpu=all: 1

Para habilitar el intercambio de dispositivos de host, de manera similar al uso de la bandera --device, Podman kube admite un selector CDI personalizado: podman.io/device=<ruta dispositivo host>.

ConfigMap de Kubernetes

Los ConfigMaps de Kubernetes se pueden referenciar como fuente de variables de entorno o volúmenes en Pods o Deployments. Los ConfigMaps no son un objeto independiente en Podman; en cambio, cuando un contenedor usa un ConfigMap, Podman crea variables de entorno o volúmenes según sea necesario.

Por ejemplo, el siguiente documento YAML define un ConfigMap y luego lo usa en un Pod:

apiVersion: v1
kind: ConfigMap
metadata:
  name: foo
data:
    FOO: bar
---
apiVersion: v1
kind: Pod
metadata:
  name: foobar
spec:
  containers:
  - name: container-1
    image: fooba

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

r envFrom: - configMapRef: name: foo optional: false

y como resultado la variable de entorno FOO se establece en bar para el contenedor container-1

.

Kubernetes Secret representa un secreto con nombre de Podman. El Kubernetes Secret se guarda completo y puede referenciarse como fuente de variables de entorno o volúmenes en Pods o

Deployments.

Por ejemplo, el siguiente documento YAML define un Secret y luego lo usa en un

Pod:

          key:
foo

y como resultado la variable de entorno FOO se establece en bar para el contenedor container-1

Por defecto, las direcciones y rutas IPv4 e IPv6, así como el nombre de la interfaz del pod, se copian del host. El reenvío de puertos conserva la dirección IP de origen original. Las opciones descritas en pasta(1) se pueden especificar como argumentos separados por comas.
En términos de opciones de pasta(1), se proporciona --config-net de forma predeterminada, para configurar la red cuando se inicia el contenedor, y también se asume --no-map-gw de forma predeterminada, para evitar el acceso directo del contenedor al host utilizando la dirección de la puerta de enlace. Este último se puede anular pasando --map-gw en las opciones específicas de pasta (a pesar de no ser una opción real de pasta(1)).
Para una mejor integración con el manejo de DNS, se pasa --dns-forward 169.254.1.1, y esta dirección se agrega a resolv.conf(5) como el primer resolvedor. Es posible pasar --dns-forward explícitamente en caso de que se deba usar una dirección IP diferente. Para que la entrada host.containers.internal en /etc/hosts funcione y permita conexiones al host, se pasa --map-guest-addr 169.254.1.2. Nuevamente, se puede configurar explícitamente para elegir una dirección IP diferente.
Además, se pasan -t none y -u none si, respectivamente, no se configura ningún reenvío de puertos TCP o UDP del host al contenedor (a través de las opciones --publish de Podman o pasando las opciones -t/-u de pasta directamente), para deshabilitar el reenvío automático de puertos basado en puertos enlazados. De manera similar, se proporcionan -T none y -U none para deshabilitar la misma funcionalidad de contenedor a host.
Todas las opciones también se pueden configurar en containers.conf(5); consulte la clave pasta_options en la sección de red de ese archivo.
Algunos ejemplos:
  • pasta:--map-gw: Permite que el contenedor acceda directamente al host utilizando la dirección de la puerta de enlace.
  • pasta:--mtu,1500: Especifica una MTU de 1500 bytes para la interfaz tap en el contenedor.
  • pasta:--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,-m,1500,--no-ndp,--no-dhcpv6,--no-dhcp, equivalente a las opciones predeterminadas de slirp4netns(1): deshabilita IPv6, asigna 10.0.2.0/24 a la interfaz tap0 en el contenedor, con puerta de enlace 10.0.2.3, habilita el reenviador DNS accesible en 10.0.2.3, establece la MTU en 1500 bytes, deshabilita NDP, DHCPv6 y DHCP soporte.
  • pasta:-I,tap0,--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,--no-ndp,--no-dhcpv6,--no-dhcp, equivalente a las opciones predeterminadas de slirp4netns(1) con anulaciones de Podman: igual que lo anterior, pero deja la MTU en 65520 bytes
  • pasta:-t,auto,-u,auto,-T,auto,-U,auto: habilita el reenvío automático de puertos basado en puertos enlazados observados desde ambos lados del host y del contenedor
  • pasta:-T,5201: habilita el reenvío del puerto TCP 5201 del contenedor al host, utilizando la interfaz de bucle invertido en lugar de la interfaz tap para un mejor rendimiento

Cuando no se especifica ninguna opción de red y el modo de red host no está configurado en el archivo YAML, se crea una nueva pila de red y los pods se adjuntan a ella, lo que permite la comunicación pod a pod.

--no-hostname

No cree el archivo /etc/hostname en los contenedores.

Por defecto, Podman administra el archivo /etc/hostname, agregando el propio nombre de host del contenedor. Cuando se establece la opción --no-hostname, se conservará el archivo /etc/hostname de la imagen sin modificar si existe.

--no-hosts

No modifique el archivo /etc/hosts en el pod.

Podman asume el control del archivo /etc/hosts del pod por defecto y agrega entradas para el nombre del contenedor (ver opción --name) y el nombre de host (ver opción --hostname), los hosts internos host.containers.internal y host.docker.internal, así como cualquier nombre de host agregado usando la opción --add-host. Consulte la opción --add-host para obtener detalles. Al pasar --no-hosts se deshabilita esto, de modo que el archivo /etc/hosts de la imagen se mantiene sin modificar. Lo mismo se puede lograr globalmente configurando no_hosts=true en containers.conf.

Esta opción entra en conflicto con los hosts agregados en el YAML de Kubernetes.

--no-pod-prefix

No prefije el nombre del contenedor con el nombre del pod.

--publish=[[ip:][puerto_host]:]puerto_contenedor[/protocolo]

Define o anula una definición de puerto en el archivo YAML.

Las listas de puertos en el archivo YAML y la línea de comandos se combinan. La coincidencia se realiza utilizando el campo containerPort. Si containerPort existe tanto en el archivo YAML como en la opción, esta última tiene prioridad.

--publish-all

Establecer esta opción en true expondrá todos los puertos al host, incluso si solo se especifican a través de containerPort en el K8 YAML. En cuanto a qué puerto se expondrá, --publish tiene mayor prioridad que hostPort, tiene mayor prioridad que containerPort.

Si se establece en false (que es el valor predeterminado), solo los puertos definidos a través de hostPort o --publish se publicarán en el host.

--quiet, -q

Suprimir la información de salida al descargar imágenes

--replace

Desmantela los pods creados por una ejecución anterior de kube play y recrea los pods. Esta opción se utiliza para mantener los pods existentes actualizados según el YAML de Kubernetes.

--seccomp-profile-root=ruta

Ruta del directorio para los perfiles seccomp (predeterminado: "/var/lib/kubelet/seccomp"). (Esta opción no está disponible con el cliente remoto de Podman, incluidas las máquinas Mac y Windows (excluyendo WSL2)).

--start

Inicia el pod después de crearlo, establécelo en false para solo crearlo.

--tls-verify

Requerir HTTPS y verificar certificados al contactar registros (predeterminado: true). Si se establece explícitamente en true, se utiliza la verificación TLS. Si se establece en false, no se utiliza la verificación TLS. Si no se especifica, se utiliza la verificación TLS a menos que el registro de destino esté listado como un registro inseguro en containers-registries.conf(5)

--userns=modo

Establece el modo del espacio de nombres de usuario para el contenedor.

Si no se establece --userns, el valor predeterminado se determina de la siguiente manera. - Si se establece --pod, se ignora --userns y se utiliza el espacio de nombres de usuario del pod. - Si la variable de entorno PODMAN_USERNS está configurada, se utiliza su valor. - Si se especifica userns en containers.conf, se utiliza este valor. - De lo contrario, se asume --userns=host.

--userns="" (es decir, una cadena vacía) es un alias para --userns=host.

Esta opción es incompatible con --gidmap, --uidmap, --subuidname y --subgidname.

Mapeos de clave de usuario sin privilegios --userns:

Clave Usuario Host Usuario Contenedor
auto $UID nil (La UID del usuario host no se mapea al contenedor).
host $UID 0 (La cuenta de usuario predeterminada se mapea al usuario root en el contenedor).
keep-id $UID $UID (Mapea la cuenta de usuario a la misma UID dentro del contenedor).
keep-id:uid=200,gid=210 $UID 200:210 (Mapea la cuenta de usuario a la UID, valor GID especificado dentro del contenedor).
nomap $UID nil (La UID del usuario host no se mapea al contenedor).

Los valores válidos de modo son:

auto[:OPCIONES,...]: crea automáticamente un espacio de nombres de usuario único.

  • modo con privilegios: La opción --userns=auto requiere que el nombre de usuario containers se especifique en los archivos /etc/subuid y /etc/subgid, con un rango no utilizado de IDs de usuario subordinados que Podman puede asignar a los contenedores. Ejemplo: containers:2147483647:2147483648.
  • modo sin privilegios: Se utilizarán los rangos de usuarios de los archivos /etc/subuid y /etc/subgid. Tenga en cuenta que ejecutar un solo contenedor sin usar --userns=auto utilizará el rango completo de UIDs y no permitirá una subdivisión adicional. Ver subuid(5).

Podman asigna rangos únicos de UIDs y GIDs de los IDs de usuario subordinados de containers. El tamaño de los rangos se basa en el número de UIDs requeridas en la imagen. El número de UIDs y GIDs se puede anular con la opción size.

La opción --userns=keep-id utiliza todas las subuids y subgids del usuario. La opción --userns=nomap utiliza todas las subuids y subgids del usuario excepto la propia ID del usuario. Usar --userns=auto al iniciar nuevos contenedores no funciona mientras existan contenedores que se iniciaron con --userns=nomap o --userns=keep-id sin limitar el tamaño del espacio de nombres de usuario.

auto válido op

tions:

  • gidmapping=CONTAINER_GID:HOST_GID:SIZE: para forzar un mapeo GID para que esté presente en el espacio de nombres del usuario.
  • size=SIZE: para especificar un tamaño explícito para el espacio de nombres de usuario automático. Ej. --userns=auto:size=8192. Si no se especifica size, auto estima un tamaño para el espacio de nombres del usuario.
  • uidmapping=CONTAINER_UID:HOST_UID:SIZE: para forzar un mapeo UID para que esté presente en el espacio de nombres del usuario.

El UID y GID del host en gidmapping y uidmapping pueden tener opcionalmente el prefijo del símbolo @. En este caso, podman buscará el ID intermedio correspondiente al ID del host y mapeará el ID intermedio encontrado al ID del contenedor. Para más detalles ver --uidmap.

container:id: se une al espacio de nombres del usuario del contenedor especificado.

host o "" (cadena vacía): se ejecuta en el espacio de nombres del usuario del llamador. Los procesos que se ejecutan en el contenedor tienen los mismos privilegios en el host que cualquier otro proceso iniciado por el usuario que llama.

keep-id: crea un espacio de nombres de usuario donde los UID:GID del usuario actual se mapean a los mismos valores en el contenedor. Para contenedores creados por root, el mapeo actual se crea en un nuevo espacio de nombres de usuario.

Además, el proceso init dentro del contenedor se ejecutará bajo el UID del usuario actual. Este comportamiento anula la instrucción USER de la imagen a menos que establezca explícitamente --user.

Opciones válidas para keep-id:

  • uid=UID: anula el UID dentro del contenedor que se utiliza para mapear el usuario actual.
  • gid=GID: anula el GID dentro del contenedor que se utiliza para mapear el usuario actual.
  • size=SIZE: anula el tamaño del espacio de nombres de usuario configurado. Es útil para no saturar todos los IDs disponibles. No es compatible cuando se ejecuta como root.

nomap: crea un espacio de nombres de usuario donde los UID:GID del usuario sin root actual no se mapean en el contenedor. Esta opción no está permitida para contenedores creados por el usuario root.

ns:namespace: ejecuta el pod en el espacio de nombres de usuario existente dado.

--wait, -w

Ejecuta pods y contenedores en primer plano. El valor predeterminado es falso.

En cualquier momento puede ejecutar podman pod ps en otra terminal para ver una lista de los pods y contenedores en ejecución.

Cuando se adjunta en modo tty, puede matar los pods y contenedores presionando Ctrl-C o recibiendo cualquier otra señal de interrupción.

Todos los pods, contenedores y volúmenes creados con podman kube play se eliminan al salir.

EJEMPLOS

Recrea el pod y los contenedores descritos en el archivo YAML del host especificado.

$ podman kube play demo.yml
52182811df2b1e73f36476003a66ec872101ea59034ac0d4d3a7b40903b955a6

Recrea el pod y los contenedores especificados en un archivo YAML enviado a stdin.

$ cat demo.yml | podman kube play -
52182811df2b1e73f36476003a66ec872101ea59034ac0d4d3a7b40903b955a6

Elimina el pod y los contenedores como se describe en el archivo YAML especificado.

$  podman kube play --down demo.yml
Pods stopped:
52182811df2b1e73f36476003a66ec872101ea59034ac0d4d3a7b40903b955a6
Pods removed:
52182811df2b1e73f36476003a66ec872101ea59034ac0d4d3a7b40903b955a6

Proporciona múltiples archivos de configmap como fuentes para variables de entorno dentro de los pods y contenedores especificados.

$ podman kube play demo.yml --configmap configmap-foo.yml,configmap-bar.yml
52182811df2b1e73f36476003a66ec872101ea59034ac0d4d3a7b40903b955a6
$ podman kube play demo.yml --configmap configmap-foo.yml --configmap configmap-bar.yml
52182811df2b1e73f36476003a66ec872101ea59034ac0d4d3a7b40903b955a6

Crea un pod conectado a dos redes con una IP estática en cada una.

$ podman kube play demo.yml --network net1:ip=10.89.1.5 --network net2:ip=10.89.10.10
52182811df2b1e73f36476003a66ec872101ea59034ac0d4d3a7b40903b955a6

Por favor, tenga en cuenta que las redes deben crearse primero usando podman-network-create(1).

Crea y elimina desde una URL que apunta a un archivo YAML.

$ podman kube play https://podman.io/demo.yml
52182811df2b1e73f36476003a66ec872101ea59034ac0d4d3a7b40903b955a6
$ podman kube play --down https://podman.io/demo.yml
Pods stopped:
52182811df2b1e73f36476003a66ec872101ea59034ac0d4d3a7b40903b955a6
Pods removed:
52182811df2b1e73f36476003a66ec872101ea59034ac0d4d3a7b40903b955a6

podman kube play --down no funciona con una URL si el archivo YAML al que apunta la URL ha sido cambiado o alterado.
