DESCRIPCIÓ

N

El comando podman system service crea un servicio de escucha que responde a llamadas API para Podman. El comando está disponible en sistemas Linux y normalmente se ejecuta en servicios systemd. El comando no está disponible cuando el comando Podman se ejecuta directamente en un host Windows o macOS o en otras situaciones donde el comando Podman está accediendo a un servicio API remoto de

Podman.

La API REST proporcionada por podman system service se divide en dos partes: una capa de compatibilidad que ofrece soporte para la API Docker v1.40 y una capa nativa de Podman llamada Libpod. La documentación de esta última está disponible en https://docs.podman.io/en/latest/_static/api.html. Ambas APIs están versionadas, pero el servidor no rechaza solicitudes con una versión no soportada

establecida.

Ejecutar el comando en un servicio

systemd

El comando podman system service soporta la activación por socket de systemd. Cuando el comando se ejecuta en un servicio systemd, el servicio API puede, por tanto, proporcionarse bajo demanda. Si el servicio systemd no está ya en ejecución, se activará en cuanto un cliente se conecte al socket de escucha. Systemd entonces ejecuta el comando podman system service. Después de un tiempo de inactividad, definido por la opción --time, el comando termina. Systemd establece el estado de podman.service como inactivo. En este punto no hay ningún proceso podman system service en ejecución. No se desperdician recursos de cómputo innecesarios. En cuanto otro cliente se conecta, systemd activa el servicio systemd de

nuevo.

Ejecutar el comando

directamente

Para soportar la ejecución de un servicio API sin usar un servicio systemd, el comando también acepta un argumento opcional de endpoint para la API en forma de URI. Por ejemplo, unix:///tmp/foobar.sock o tcp://localhost:8080. Si no se proporciona un endpoint, se usan los valores predeterminados. El endpoint predeterminado para un servicio con privilegios de root es unix:///run/podman/podman.sock y para uno sin privilegios de root es unix://$XDG_RUNTIME_DIR/podman/podman.sock (por ejemplo unix:///run/user/100

Segurida

d

Tenga en cuenta que la API concede acceso completo a toda la funcionalidad de Podman y, por tanto, permite la ejecución arbitraria de código como el usuario que ejecuta la API, sin posibilidad de limitar o auditar este acceso. El modelo de seguridad de la API se basa en el acceso a través de un socket Unix con el acceso restringido mediante permisos de archivo estándar, asegurando que solo el usuario que ejecuta el servicio podrá acceder a él. Se puede usar TLS para asegurar este socket al requerir que los clientes presenten un certificado firmado por una autoridad de certificación ("CA") de confianza, así como permitir que el cliente verifique la identidad de la API. Nosotros recomendamos encarecidamente no hacer que el socket de la API esté disponible a través de la red (es decir, vinculando el servicio a una URL tcp) sin habilitar TLS mutuo para autenticar al cliente. Incluso el acceso a través de Localhost conlleva riesgos: cualquier persona con acceso al sistema podrá acceder a la API. Si se requiere acceso remoto, en su lugar recomendamos reenviar el socket de la API a través de SSH y limitar el acceso en la máquina remota en la mayor medida posible. Si se debe usar una URL tcp sin TLS, se recomienda usar la opción --cors pa

ra mejor
ar la se
guridad.

Es posible ejecutar la API sin usar la activación por socket de systemd.
