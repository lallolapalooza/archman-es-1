--cpu-shares, -c=share

s

CPU shares (peso relativo)

.

Por defecto, todos los contenedores reciben la misma proporción de ciclos de CPU. Esta proporción puede modificarse cambiando la ponderación de CPU shares del contenedor relativa al peso combinado de todos los contenedores en ejecución. El peso por defecto es 1024

.

La proporción solo se aplica cuando se están ejecutando procesos intensivos en CPU. Cuando las tareas en un contenedor están inactivas, otros contenedores pueden usar el tiempo de CPU restante. La cantidad real de tiempo de CPU varía dependiendo del número de contenedores en ejecución en el

sistema.

Por ejemplo, considere tres contenedores, uno tiene un cpu-share de 1024 y los otros dos tienen una configuración de cpu-share de 512. Cuando los procesos en los tres contenedores intentan usar el 100% de la CPU, el primer contenedor recibe el 50% del tiempo total de CPU. Si se añade un cuarto contenedor con un cpu-share de 1024, el primer contenedor solo recibe el 33% de la CPU. Los contenedores restantes reciben el 16.5%, 16.5% y 33% de la

CPU.

En un sistema multinúcleo, las porciones de tiempo de CPU se distribuyen sobre todos los núcleos de CPU. Incluso si un contenedor está limitado a menos del 100% del tiempo de CPU, puede usar el 100% de cada núcleo de CPU

individual.

Por ejemplo, considere un sistema con más de tres núcleos. Si el contenedor C0 se inicia con --cpu-shares=512 ejecutando un proceso, y otro contenedor C1 con --cpu-shares=1024 ejecutando dos procesos, esto puede resultar en la siguiente división de CPU

Etiquetado de los Montajes de

Volúmenes

Los sistemas de etiquetado como SELinux requieren que se coloquen etiquetas adecuadas en el contenido del volumen montado en un pod. Sin una etiqueta, el sistema de seguridad podría impedir que los procesos que se ejecutan dentro del pod usen el contenido. Por defecto, Podman no cambia las etiquetas establecidas

por el SO.

Para cambiar una etiqueta en el contexto del pod, añada uno de dos

sufijos

:z o :Z al montaje del volumen. Estos sufijos le indican a Podman que vuelva a etiquetar los objetos de archivo en los volúmenes compartidos. La opción z le indica a Podman que dos o más pods comparten el contenido del volumen. Como resultado, Podman etiqueta el contenido con una etiqueta de contenido compartido. Las etiquetas de volumen compartido permiten a todos los contenedores leer/escribir contenido. La opción Z le indica a Podman que etiquete el contenido con una etiqueta privada no compartida. Solo el pod actual puede usar un volumen privado. Nota: todos los contenedores dentro de

un

pod comparten la misma etiqueta SELinux. Esto significa que todos los contenedores dentro de dicho pod pueden leer/escribir volúmenes compartidos en el contenedor creado con la :Z en cualquiera de los contenedores. El reetiquetado recorre el sistema de archivos bajo el volumen y cambia la etiqueta en cada archivo; si el volumen tiene miles de inodos, este proceso tarda mucho, retrasando el inicio del pod. Si el volumen fue previamente reetiquetado con la opción z, Podman está optimizado para no reetiquetar una segunda vez. Si se mueven archivos al volumen, entonces las etiquetas se pueden cambiar manualmente con el comando chcon -Rt container

_file_t RUTA.

Nota: No vuelva a etiquetar archivos y directorios del sistema. El reetiquetado del contenido del sistema podría hacer que otros servicios confinados en la máquina fallen. Para este tipo de contenedores recomendamos deshabilitar la separación de SELinux. La opción --security-opt label=disable deshabilita la separación de SELinux para el pod. Por ejemplo, si un usuario quisiera montar por volumen todo su directorio de inicio en un pod, necesita deshabilitar la separación de

SELinux. 
$ podman pod clone --security-opt label=disable -v $HOME:/home/user fedora touch

Montajes de Volúmenes

Overlay

La bandera :O le indica a Podman que monte el directorio desde el host como almacenamiento temporal usando el sistema de archivos overlay. Los procesos del pod pueden modificar el contenido dentro del punto de montaje que se almacena en el almacenamiento del contenedor en un directorio separado. En términos de overlay, el directorio de origen es el inferior, y el directorio de almacenamiento del contenedor es el superior. Las modificaciones en el punto de montaje se destruyen cuando el pod termina de ejecutarse, similar a cómo se desmonta un punto de montaje

tmpfs.

Para usuarios avanzados, la opción overlay también admite un upperdir y workdir personalizados no volátiles para el montaje overlay. Un upperdir y workdir personalizados pueden ser gestionados completamente por los usuarios mismos, y Podman no los elimina al completar el ciclo de vida. Ejemplo :O,upperdir=/some/upper,workdir=/some/wor

k

Ejecuciones posteriores del contenedor ven el contenido original del directorio de origen, cualquier cambio de ejecuciones anteriores del pod ya no

existe.

Un caso de uso del montaje overlay es compartir la caché de paquetes desde el host en el contenedor para permitir acelerar las

compilaciones.

Nota: La bandera O entra en conflicto con otras opciones listadas

arriba.

El contenido montado en el contenedor se etiqueta con la etiqueta privada. En sistemas SELinux, las etiquetas en el directorio de origen deben ser legibles por la etiqueta del contenedor de infraestructura del pod. Usualmente los contenedores pueden leer/ejecutar container_share_t y pueden leer/escribir container_file_t. Si no es posible cambiar las etiquetas en un volumen de origen, la separación de contenedores de SELinux debe estar deshabilitada para que el pod o el contenedor de infraestructura

funcione.

No modifique el directorio de origen montado en el pod con un montaje overlay, puede causar fallos inesperados. Solo modifique el directorio después de que el contenedor termine de

ejecutarse.

Propagación de

montajes

Por defecto, los volúmenes montados por enlace son privados. Eso significa que cualquier montaje hecho dentro del pod no es visible en el host y viceversa. Se puede cambiar este comportamiento especificando una propiedad de propagación del montaje de volumen. Cuando un volumen es compartido, los montajes hechos bajo ese volumen dentro del pod son visibles en el host y viceversa. Hacer un volumen esclavo[1] ⟨#Nota al pie1⟩ habilita solo la propagación de montajes unidireccional: los montajes hechos en el host bajo ese volumen son visiblesle inside the container but not the other way around.
