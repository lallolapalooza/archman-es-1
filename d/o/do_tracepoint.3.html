Crear un proveedor de puntos de traza es el primer paso para

usar

liblttng-ust . Los pasos siguientes

•Instrumentar su aplicación con llamadas lttng_ust_tracepoint() [[492]

Un proveedor de puntos de seguimiento es un objeto compilado que contiene las sondas de eventos correspondientes a sus definiciones personalizadas de puntos de seguimiento. Un proveedor de puntos de seguimiento contiene el código para obtener el tamaño de un evento y para serializarlo, entre otras cosas.

Para crear un proveedor de puntos de seguimiento, comience con la siguiente plantilla de cabecera de proveedor de puntos de seguimiento :

#undef LTTNG_UST_TRACEPOINT_PROVIDER
#define LTTNG_UST_TRACEPOINT_PROVIDER my_provider
#undef LTTNG_UST_TRACEPOINT_INCLUDE
#define LTTNG_UST_TRACEPOINT_INCLUDE "./tp.h"
#if !defined(_TP_H) || \
    defined(LTTNG_UST_TRACEPOINT_HEADER_MULTI_READ)
#define _TP_H
#include <lttng/tracepoint.h>
/*
 * LTTNG_UST_TRACEPOINT_EVENT(), LTTNG_UST_TRACEPOINT_EVENT_CLASS(),
 * LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(),
 * LTTNG_UST_TRACEPOINT_LOGLEVEL(), and `LTTNG_UST_TRACEPOINT_ENUM()`
 * are used here.
 */
#endif /* _TP_H */
#include <lttng/tracepoint-event.h>

En esta plantilla, el proveedor de puntos de seguimiento se llama my_provider (LTTNG_UST_TRACEPOINT_PROVIDER definición). El archivo debe llevar el nombre de la LTTNG_UST_TRACEPOINT_INCLUDE definición (tp.h en este caso). Entre #include <lttng/tracepoint.h> y #endif van las invocaciones de las LTTNG_UST_TRACEPOINT_EVENT(), LTTNG_UST_TRACEPOINT_EVENT_CLASS(), LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(), LTTNG_UST_TRACEPOINT_LOGLEVEL(), y LTTNG_UST_TRACEPOINT_ENUM() macros.


Nota

Puede evitar escribir el código de prólogo y epílogo estándar en la plantilla de archivo anterior utilizando la lttng-gen-tp(1) herramienta incluida con LTTng-UST.

El archivo de cabecera del proveedor de puntos de seguimiento debe ser incluido en un archivo fuente que se ve así:

#define LTTNG_UST_TRACEPOINT_CREATE_PROBES
#include "tp.h"

Juntos, esos dos archivos (llamémoslos tp.h y tp.c) forman las fuentes del proveedor de puntos de seguimiento, listas para ser compiladas.

Puede crear múltiples proveedores de puntos de seguimiento para ser usados en una sola aplicación, pero cada uno debe tener su propio archivo de cabecera.

La sección de uso de LTTNG_UST_TRACEPOINT_EVENT() a continuación muestra cómo usar la LTTNG_UST_TRACEPOINT_EVENT() macro para definir los puntos de seguimiento reales en el archivo de cabecera del proveedor de puntos de seguimiento.

Vea la sección EJEMPLO a continuación para un ejemplo completo.

LTTNG_UST_TRACEPOINT_EVENT() uso

La LTTNG_UST_TRACEPOINT_EVENT() macro se usa en un archivo de cabecera de proveedor plantilla (vea la sección Crear un proveedor de puntos de seguimiento arriba) para definir puntos de seguimiento de LTTng-UST.

La plantilla de uso de LTTNG_UST_TRACEPOINT_EVENT() es la siguiente:

LTTNG_UST_TRACEPOINT_EVENT(
    /* Tracepoint provider name */
    my_provider,
    /* Tracepoint/event name */
    my_tracepoint,
    /* List of tracepoint arguments (input) */
    LTTNG_UST_TP_ARGS(
        ...
    ),
    /* List of fields of eventual event (output) */
    LTTNG_UST_TP_FIELDS(
        ...
    )
)

La LTTNG_UST_TP_ARGS() macro contiene los argumentos de entrada del punto de seguimiento. Esos argumentos pueden ser usados en las expresiones de argumento de los campos de salida definidos en LTTNG_UST_TP_FIELDS().

El formato de los parámetros de LTTNG_UST_TP_ARGS() es: tipo C , luego nombre del argumento; repita según sea necesario, hasta diez veces. Por ejemplo:

LTTNG_UST_TP_ARGS(
    int, my_int,
    const char *, my_string,
    FILE *, my_file,
    double, my_float,
    struct my_data *, my_data
)

La LTTNG_UST_TP_FIELDS() macro contiene los campos de salida del punto de seguimiento, es decir, los datos reales que pueden ser registrados en la carga útil de un evento emitido por este punto de seguimiento.

La LTTNG_UST_TP_FIELDS() macro contiene una lista de lttng_ust_field_*() macros NO separadas por comas. Las macros disponibles están documentadas en la sección Macros de tipo de campo lttng_ust_field_*() disponibles a continuación.

Los parámetros son:

count

Número de elementos en la matriz/secuencia. Esto debe ser conocido en tiempo de compilación.

enum_name

Nombre de un campo de enumeración previamente definido con la LTTNG_UST_TRACEPOINT_ENUM() macro. Vea la sección de uso de LTTNG_UST_TRACEPOINT_ENUM() para más información.

expr

Expresión C que resulta en el valor del campo. Esta expresión puede usar uno o más argumentos pasados al punto de seguimiento. Los argumentos de un punto de seguimiento dado son definidos en la LTTNG_UST_TP_ARGS() macro (vea la sección Crear un proveedor de puntos de seguimiento arriba).

field_name

Nombre del campo del evento (sintaxis de identificador C, NO una cadena literal).

float_type

Tipo C de punto flotante (float o double). El tamaño de este tipo determina el tamaño del campo de número de punto flotante.

int_type

Tipo C entero. El tamaño de este tipo determina el tamaño del campo entero/de enumeración.

len_expr

Expresión C que resulta en la longitud de la secuencia. Esta expresión puede usar uno o más argumentos pasados al punto de seguimiento.

len_type

Tipo C entero sin signo de la longitud de la secuencia.

prov_name

Nombre del proveedor de puntos de seguimiento. Este debe ser el mismo que el nombre del proveedor de puntos de seguimiento usado en una definición de campo previa.

TRACING C/C++ CONSTRUCTORS AND DESTRUCTORS

If one of the following is true:

•
You compile your C++ application with GCC ≤ 4.8.
•
You compile your C/C++ application with a C++ compiler and define LTTNG_UST_ALLOCATE_COMPOUND_LITERAL_ON_HEAP.

Then LTTng won’t trace:

•
C constructors and destructors in the application itself or in statically linked archives.
•
Some C++ constructors and destructors in the application itself or in statically linked archives.

In this case, which exact C++ constructors and destructors won’t be traced depends on the initialization order within each translation unit and across the entire program when all translation units are linked together.

Statically linking the tracepoint provider

With the static linking method, compiled tracepoint providers are copied into the target application.

Define LTTNG_UST_TRACEPOINT_DEFINE definition below the LTTNG_UST_TRACEPOINT_CREATE_PROBES definition in the tracepoint provider source:

#define LTTNG_UST_TRACEPOINT_CREATE_PROBES
#define LTTNG_UST_TRACEPOINT_DEFINE
#include "tp.h"

Create the tracepoint provider object file:

$ cc -c -I. tp.c

Note
Although an application instrumented with LTTng-UST tracepoints can be compiled with a C++ compiler, tracepoint probes should be compiled with a C compiler.

At this point, you can archive this tracepoint provider object file, possibly with other object files of your application or with other tracepoint provider object files, as a static library:

$ ar rc tp.a tp.o

Using a static library does have the advantage of centralising the tracepoint providers objects so they can be shared between multiple applications. This way, when the tracepoint provider is modified, the source code changes don’t have to be patched into the source code tree of each application. The applications need to be relinked after each change, but need not to be otherwise recompiled (unless the API of the tracepoint provider changes).

Then, link your application with this object file (or with the static library containing it) and with liblttng-ust and libdl (libc on a BSD system):

$ cc -o app tp.o app.o -llttng-ust -ldl

Dynamically loading the tracepoint provider

The second approach to package the tracepoint provider is to use the dynamic loader: the library and its member functions are explicitly sought, loaded at run time.

In this scenario, the tracepoint provider is compiled as a shared object.

The process to create the tracepoint provider shared object is pretty much the same as the static linking method, except that:

•
Since the tracepoint provider is not part of the application, LTTNG_UST_TRACEPOINT_DEFINE must be defined, for each tracepoint provider, in exactly one source file of the application
•
LTTNG_UST_TRACEPOINT_PROBE_DYNAMIC_LINKAGE must be defined next to LTTNG_UST_TRACEPOINT_DEFINE

Regarding LTTNG_UST_TRACEPOINT_DEFINE and LTTNG_UST_TRACEPOINT_PROBE_DYNAMIC_LINKAGE, the recommended practice is to use a separate C source file in your application to define them, then include the tracepoint provider header files afterwards. For example, as tp-define.c:

#define LTTNG_UST_TRACEPOINT_DEFINE
#define LTTNG_UST_TRACEPOINT_PROBE_DYNAMIC_LINKAGE
#include "tp.h"

The tracepoint provider object file used to create the shared library is built like it is using the static linking method, but with the -fpic option:

$ cc -c -fpic -I. tp.c

It is then linked as a shared library like this:

$ cc -shared -Wl,--no-as-needed -o tp.so tp.o -llttng-ust

This tracepoint provider shared object isn’t linked with the user application: it must be loaded manually. This is why the application is built with no mention of this tracepoint provider, but still needs libdl:

$ cc -o app app.o tp-define.o -ldl

There are two ways to dynamically load the tracepoint provider shared object:

•
Load it manually from the application using dlopen(3)
•
Make the dynamic loader load it with the LD_PRELOAD environment variable (see ld.so(8))

If the application does not dynamically load the tracepoint provider shared object using one of the methods above, tracing is disabled for this application, and the events are not listed in the output of lttng-list(1).

Note that it is not safe to use dlclose(3) on a tracepoint provider shared object that is being actively used for tracing, due to a lack of reference counting from LTTng-UST to the shared object.

For example, statically linking a tracepoint provider to a shared object which is to be dynamically loaded by an application (a plugin, for example) is not safe: the shared object, which contains the tracepoint provider, could be dynamically closed (dlclose(3)) at any time by the application.

To instrument a shared object, either:

•
Statically link the tracepoint provider to the application, or
•
Build the tracepoint provider as a shared object (following the procedure shown in this section), and preload it when tracing is needed using the LD_PRELOAD environment variable.

Using LTTng-UST with daemons

Some extra care is needed when using liblttng-ust with daemon applications that call fork(2), clone(2), or BSD’s rfork(2) without a following exec(3) family system call. The library liblttng-ust-fork.so needs to be preloaded before starting the application with the LD_PRELOAD environment variable (see ld.so(8)).

To use liblttng-ust with a daemon application which closes file descriptors that were not opened by it, preload the liblttng-ust-fd.so library before you start the application. Typical use cases include daemons closing all file descriptors after fork(2), and buggy applications doing “double-closes”.

Context information

Context information can be prepended by the LTTng-UST tracer before each event, or before specific events.

Context fields can be added to specific channels using lttng-add-context(1).

The following context fields are supported by LTTng-UST:

General context fields

cpu_id
CPU ID.

Note
With the default per-CPU buffer allocation policy (see lttng-enable-channel(1)), this context field is always enabled, and it cannot be added with lttng-add-context(1): its main purpose is to be used for dynamic event filtering. See lttng-enable-event(1) for more information about event filtering.

ip
Instruction pointer: enables recording the exact address from which an event was emitted. This context field can be used to reverse-lookup the source location that caused the event to be emitted.
pthread_id
POSIX thread identifier.

Can be used on architectures where pthread_t maps nicely to an unsigned long type.

Process context fields

procname
Thread name, as set by exec(3) or prctl(2). It is recommended that programs set their thread name with prctl(2) before hitting the first tracepoint for that thread.
vpid
Virtual process ID: process ID as seen from the point of view of the current process ID namespace (see pid_namespaces(7)).
vtid
Virtual thread ID: thread ID as seen from the point of view of the current process ID namespace (see pid_namespaces(7)).

perf context fields

perf:thread:COUNTER
perf counter named COUNTER. Use lttng add-context --list to list the available perf counters.

Only available on IA-32 and x86-64 architectures.

perf:thread:raw:rN:NAME
perf counter with raw ID N and custom name NAME. See lttng-add-context(1) for more details.

Namespace context fields (see namespaces(7))

cgroup_ns
Inode number of the current control group namespace (see cgroup_namespaces(7)) in the proc file system.
ipc_ns
Inode number of the current IPC namespace (see ipc_namespaces(7)) in the proc file system.
mnt_ns
Inode number of the current mount point namespace (see mount_namespaces(7)) in the proc file system.
net_ns
Inode number of the current network namespace (see network_namespaces(7)) in the proc file
system.

pid_ns

Número de inodo del espacio de nombres de ID de proceso actual (ver pid_namespaces(7)) en el sistema de archivos proc.

time_ns

Número de inodo del espacio de nombres de reloj actual (ver time_namespaces(7)) en el sistema de archivos proc.

user_ns

Número de inodo del espacio de nombres de usuario actual (ver user_namespaces(7)) en el sistema de archivos proc.

uts_ns

Número de inodo del espacio de nombres UTS actual (ver uts_namespaces(7)) en el sistema de archivos proc.

Campos de contexto de credenciales (ver credentials(7))

vuid

ID de usuario real virtual: el ID de usuario real tal como se ve desde el punto de vista del espacio de nombres de usuario actual (ver user_namespaces(7)).

vgid

ID de grupo real virtual: el ID de grupo real tal como se ve desde el punto de vista del espacio de nombres de usuario actual (ver user_namespaces(7)).

veuid

ID de usuario efectivo virtual: el ID de usuario efectivo tal como se ve desde el punto de vista del espacio de nombres de usuario actual (ver user_namespaces(7)).

vegid

ID de grupo efectivo virtual: el ID de grupo efectivo tal como se ve desde el punto de vista del espacio de nombres de usuario actual (ver user_namespaces(7)).

vsuid

ID de usuario guardado virtual: el ID de usuario guardado tal como se ve desde el punto de vista del espacio de nombres de usuario actual (ver user_namespaces(7)).

vsgid

ID de grupo guardado virtual: el ID de grupo guardado tal como se ve desde el punto de vista del espacio de nombres de usuario actual (ver user_namespaces(7)).

Volcado de estado de LTTng-UST

Si una aplicación que usa liblttng-ust se convierte en parte de una sesión de trazado, se emiten como eventos, por el trazador, información sobre sus objetos compartidos cargados actualmente, sus identificadores de compilación (build IDs) y su información de enlace de depuración (debug link).

Existen los siguientes eventos de volcado de estado de LTTng-UST y deben habilitarse para registrar los volcados de estado de la aplicación. Nótese que, durante la fase de volcado de estado, LTTng-UST también puede emitir eventos de carga/descarga de bibliotecas compartidas (ver Seguimiento de carga/descarga de bibliotecas compartidas más abajo).

lttng_ust_statedump:start

Se emite cuando comienza el volcado de estado.

Este evento no tiene campos.

lttng_ust_statedump:end

Se emite cuando termina el volcado de estado. Una vez emitido este evento, se garantiza que, para un proceso dado, el volcado de estado está completo.

Este evento no tiene campos.

lttng_ust_statedump:bin_info

Se emite cuando se encuentra información sobre un ejecutable o un objeto compartido cargado actualmente.

Campos:

Nombre del campo Descripción
baddr Dirección base del ejecutable cargado.
memsz Tamaño del ejecutable cargado en memoria.
path Ruta al archivo del ejecutable cargado.
is_pic Si el ejecutable es o no código independiente de posición (position-independent code).
has_build_id Si el ejecutable tiene o no un identificador de compilación (build ID). Si este campo es 1, se puede esperar que un lttng_ust_statedump:build_id registro de evento siga a este (no necesariamente de forma inmediata).
has_debug_link Si el ejecutable tiene o no información de enlace de depuración (debug link). Si este campo es 1, se puede esperar que un lttng_ust_statedump:debug_link registro de evento siga a este (no necesariamente de forma inmediata).

lttng_ust_statedump:build_id

Se emite cuando se encuentra un identificador de compilación (build ID) en una biblioteca compartida cargada actualmente. Véase Debugging Information in Separate Files https://sourceware.org/gdb/onlinedocs/gdb/Separate-Debug-Files.html para más información sobre los identificadores de compilación.

Campos:

Nombre del campo Descripción
baddr Dirección base de la biblioteca cargada.
build_id Identificador de compilación (build ID).

lttng_ust_statedump:debug_link

Se emite cuando se encuentra información de enlace de depuración (debug link) en una biblioteca compartida cargada actualmente. Véase Debugging Information in Separate Files https://sourceware.org/gdb/onlinedocs/gdb/Separate-Debug-Files.html para más información sobre los enlaces de depuración.

Campos:

Nombre del campo Descripción
baddr Dirección base de la biblioteca cargada.
crc CRC del archivo de enlace de depuración.
filename Nombre del archivo de enlace de depuración.

lttng_ust_statedump:procname

El nombre de proceso (procname) al inicio del proceso.

Campos:

Nombre del campo Descripción
procname El nombre del proceso.

Detectar si LTTng-UST está cargado

Para detectar si liblttng-ust está cargado desde una aplicación:

1.Define el símbolo débil lttng_ust_loaded globalmente: 
int lttng_ust_loaded __attribute__((weak));

Este símbolo débil es establecido por el constructor de liblttng-ust.

2.Prueba lttng_ust_loaded donde sea necesario: 
/* ... */
if (lttng_ust_loaded) {
    /* LTTng-UST está cargado */
} else {
    /* LTTng-UST NO está cargado */
}
/* ... */

        return EXIT_FAILURE;
    }

                         "hello tracepoint", stream, -3.14,
                         array_of_ints);
    fclose(stream);
    app_struct.b = argc;
    app_struct.c = "[the string]";
    lttng_ust_tracepoint(my_provider, event_instance1, 23,
                         &app_struct);
    app_struct.b = argc * 5;
    app_struct.c = "[other string]";

    app_struct.b = 23;
    app_struct.c = "nothing";
    lttng_ust_tracepoint(my_provider, event_instance3, -52,
                         &app_struct);
    return EXIT_SUCCESS;
}

VARIABLES DE ENTORNO

LTTNG_HOME

Directorio de inicio alternativo del usuario. Esta variable es útil cuando el usuario que ejecuta la aplicación instrumentada tiene un directorio de inicio no escribible. Esta ruta es donde se encuentran los sockets Unix para la comunicación con el demonio de sesión por usuario.

LTTNG_UST_ABORT_ON_CRITICAL

Si está configurado, aborta la aplicación instrumentada en un mensaje de error crítico.

LTTNG_UST_ALLOW_BLOCKING

Si está configurado, permite que la aplicación reintente el trazado de eventos cuando no hay espacio para el registro del evento en el sub-búfer, bloqueando efectivamente la aplicación hasta que se libere espacio o se alcance el tiempo de espera configurado.

Para permitir que una aplicación se bloquee durante el trazado, también debes especificar un tiempo de espera de bloqueo cuando creas un canal con la opción --blocking-timeout del comando lttng-enable-channel(1).

Esta opción puede ser útil en cargas de trabajo que generan un rendimiento de datos de trazado muy grande, donde bloquear la aplicación es un compromiso aceptable para evitar descartar registros de eventos.


Advertencia
Establecer esta variable de entorno puede afectar significativamente los tiempos de la aplicación.

LTTNG_UST_APP_PATH

Ruta del directorio donde se espera que el demonio de sesión LTTng coloque los siguientes archivos para recibir solicitudes de conexión de la aplicación instrumentada:
•El socket Unix de registro de la aplicación.
•Los archivos de memoria compartida "wait" para despertar aplicaciones instrumentadas que están esperando que se inicie un demonio de sesión.
•El archivo de puerto del agente.

Este archivo contiene el puerto TCP al que los agentes deben conectarse para habilitar el trazado LTTng.

Este directorio debe existir cuando inicias la aplicación para que se habilite el trazado LTTng.

Cuando se establece LTTNG_UST_APP_PATH, liblttng-ust:

•Solo considera esta ruta para conectarse a un demonio de sesión.
•No se conectará a demonios de sesión raíz y/o de usuario como es habitual.

Consulta la variable de entorno correspondiente LTTNG_UST_CTL_PATH de lttng-sessiond(8).

LTTNG_UST_CLOCK_PLUGIN

Ruta al objeto compartido que actúa como el plugin de reemplazo de reloj. Un ejemplo de dicho plugin se puede encontrar en la documentación de LTTng-UST bajo examples/clock-override https://github.com/lttng/lttng-ust/tree/stable-2.14/doc/examples/clock-override.

LTTNG_UST_DEBUG

Si está definido, habilita la salida de depuración y de errores de liblttng-ust.

LTTNG_UST_GETCPU_PLUGIN

Ruta al objeto compartido que actúa como complemento de anulación de getcpu() . Un ejemplo de tal complemento se puede encontrar en la documentación de LTTng-UST en examples/getcpu-override https://github.com/lttng/lttng-ust/tree/stable-2.14/doc/examples/getcpu-override.

LTTNG_UST_MAP_POPULATE_POLICY

Si está definido, anula la política utilizada para poblar las páginas de memoria compartida dentro de la aplicación.

Los valores posibles son:

none (por defecto)

No poblar ninguna página de forma anticipada: se producirán faltas menores en el primer acceso durante el rastreo.

cpu_possible

Poblar de forma anticipada las páginas para todos los CPUs posibles en el sistema, como se muestra en /sys/devices/system/cpu/possible.

LTTNG_UST_REGISTER_TIMEOUT

Tiempo de espera para el comando registration done del demonio de sesión antes de proceder a ejecutar el programa principal (milisegundos).

El valor 0 significa no esperar. El valor -1 significa esperar para siempre. Se recomienda establecer esta variable de entorno a 0 para aplicaciones con restricciones de tiempo en el tiempo de inicio del proceso.

Por defecto: 3000.

LTTNG_UST_WITHOUT_BADDR_STATEDUMP

Si está definido, evita que liblttng-ust realice un volcado de estado de la dirección base (vea la sección LTTng-UST state dump más arriba).

LTTNG_UST_WITHOUT_PROCNAME_STATEDUMP

Si está definido, evita que liblttng-ust realice un volcado de estado de procname (vea la sección LTTng-UST state dump más arriba).
