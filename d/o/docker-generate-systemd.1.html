podman-generate-systemd(1) Manual de comandos generales podman-generate-systemd(1)

NOMBRE

podman-generate-systemd - [OBSOLETO] Generar archivo(s) de unidad systemd para un contenedor o pod

SINOPSIS

podman generate systemd [opciones] contenedor|pod

DESCRIPCIÓN

OBSOLETO: Nota: podman generate systemd está obsoleto. Recomendamos usar archivos [Quadlet] al ejecutar contenedores o pods de Podman bajo systemd. No hay planes para eliminar el comando. Recibirá correcciones urgentes de errores pero ninguna característica nueva.

podman generate systemd crea un archivo de unidad systemd que puede usarse para controlar un contenedor o pod. Por defecto, el comando imprime el contenido de los archivos de unidad a la salida estándar.

Generar archivos de unidad para un pod requiere que el pod se cree con un contenedor de infraestructura (ver --infra=true). Un contenedor de infraestructura se ejecuta durante toda la vida útil de un pod y, por lo tanto, es necesario para que systemd gestione el ciclo de vida de la unidad principal del pod.

  • Nota: Al usar este comando con el cliente remoto, incluidas las máquinas Mac y Windows (excluyendo WSL2), coloque las unidades generadas en el sistema remoto. Además, asegúrese de que la variable de entorno XDG_RUNTIME_DIR esté configurada. Si no está configurada, establézcala con export XDG_RUNTIME_DIR=/run/user/$(id -u)._
  • Nota: El comando podman run generado contiene una opción --sdnotify con el valor tomado del contenedor. Si el contenedor no tiene ningún valor explícitamente establecido o el valor está establecido en ignore, se utiliza el valor conmon. La razón para anular el valor predeterminado container es que casi ninguna carga de trabajo de contenedor envía mensajes de notificación. Systemd espera un mensaje de listo que nunca llega, si se usa el valor container para un contenedor que no envía mensajes de notificación. El uso del valor predeterminado puede haber sido no intencional por parte del usuario, por lo tanto, se anula el valor predeterminado._

Integración de Kubernetes

Un YAML de Kubernetes puede ejecutarse en systemd a través de la plantilla systemd podman-kube@.service. El argumento de la plantilla es la ruta al archivo YAML. Dado un archivo workload.yaml en el directorio principal, se puede ejecutar de la siguiente manera:

$ escaped=$(systemd-escape ~/workload.yaml)
$ systemctl --user start podman-kube@$escaped.service
$ systemctl --user is-active podman-kube@$escaped.service
active

OPCIONES

--after=nombre_dependencia

Agregue la opción de unidad systemd after (After=), que son dependencias de ordenamiento entre la lista de dependencias y este servicio. Esta opción puede especificarse varias veces.

Las dependencias definidas por el usuario se agregan al archivo de unidad generado, pero las opciones existentes necesarias o definidas por defecto (por ejemplo, online.target) no se eliminan ni se anulan.

--container-prefix=prefijo

Establece el prefijo del nombre de la unidad systemd para contenedores. El valor predeterminado es container.

--env, -e=env

Establece variables de entorno en los archivos de unidad systemd.

Si una variable de entorno se especifica sin un valor, Podman verifica el entorno del host en busca de un valor y establece la variable solo si está configurada en el host. Como caso especial, si una variable de entorno que termina en * se especifica sin un valor, Podman busca en el entorno del host variables que comiencen con el prefijo y agrega esas variables a los archivos de unidad systemd.

--files, -f

Genera archivos en lugar de imprimir en la salida estándar. Los archivos generados se nombran {container,pod}-{ID,name}.service y se colocan en el directorio de trabajo actual.

Nota: En un sistema con SELinux habilitado, los archivos generados heredan contextos del directorio de trabajo actual. Dependiendo de la configuración de SELinux, pueden ser necesarios cambios en los archivos generados usando restorecon, chcon o semanage para permitir que systemd acceda a estos archivos. Alternativamente, use la opción -Z al ejecutar mv o cp.

--format=formato

Imprime las unidades creadas en el formato especificado (json). Si se especifica --files, se imprimen las rutas a los archivos creados en lugar del contenido de la unidad.

--name, -n

Utiliza el nombre del contenedor para el inicio, la parada y la descripción en el archivo de unidad.

--new

Esta opción produce archivos de unidad que no esperan que los contenedores y pods existan. En su lugar, se crean nuevos contenedores y pods basados en sus archivos de configuración. Los archivos de unidad se crean con el mejor esfuerzo y pueden requerir edición adicional; revise los archivos generados cuidadosamente antes de usarlos en producción.

Tenga en cuenta que --new solo funciona en contenedores y pods creados directamente a través de Podman (es decir, podman [container] {create,run} o podman pod create). No funciona en contenedores o pods creados a través de la API REST o mediante podman kube play. Para podman kube play, use la plantilla systemd podman-kube@.service en su lugar.

--no-header

No generar la cabecera que incluye metadatos como la versión de Podman y la marca de tiempo.

--pod-prefix=prefijo

Establece el prefijo del nombre de la unidad systemd para pods. El valor predeterminado es pod.

--requires=nombre_dependencia

Establece la opción de unidad systemd requires (Requires=). Similar a wants, pero declara una dependencia de requisito más fuerte.

--restart-policy=politica

Establece la política de reinicio de systemd. La política de reinicio debe ser una de: "no", "on-success", "on-failure", "on-abnormal", "on-watchdog", "on-abort", o "always". La política predeterminada es on-failure a menos que el contenedor se haya creado con una política de reinicio personalizada.

Tenga en cuenta que generar una unidad sin --new en un contenedor con una política de reinicio personalizada puede generar problemas al apagar; systemd intenta detener la unidad mientras Podman intenta reiniciarla. Se recomienda crear el contenedor sin --restart y usar la opción --restart-policy al generar el archivo de unidad.

--restart-sec=tiempo

Establece el valor de reinicio de servicio de systemd. Configura el tiempo de espera antes de reiniciar un servicio (como se configura con restart-policy). Toma un valor en segundos.

--separator=separador

Establece el separador del nombre de la unidad systemd entre el nombre/id de un contenedor/pod y el prefijo. El valor predeterminado es -.

--start-timeout=valor

Anula el tiempo de espera de inicio predeterminado para el contenedor con el valor dado en segundos.

--stop-timeout=valor

Anula el tiempo de espera de parada predeterminado para el contenedor con el valor dado en segundos.

--template

Agrega especificadores de plantilla para ejecutar múltiples servicios desde el archivo de unidad systemd.

Tenga en cuenta que si --new no se estableció en true, se establece en true por defecto. Sin embargo, el comando falla si --new se establece explícitamente en false.

--wants=nombre_dependencia

Agrega la opción de unidad systemd wants (Wants=), de la que este servicio depende (débilmente). Esta opción puede especificarse varias veces. Esta opción no influye en el orden en que se inician o detienen los servicios.

Las dependencias definidas por el usuario se agregan al archivo de unidad generado, pero las opciones existentes necesarias o definidas por defecto (por ejemplo, online.target) no se eliminan ni se anulan.

EJEMPLOS

Generar e imprimir un archivo de unidad systemd para un contenedor

Para generar e imprimir un archivo de unidad systemd para el contenedor con ID f8f57079a323:

$ podman generate systemd f8f57079a323

Para generar un archivo de unidad systemd para el contenedor con ID f8f57079a323 y guardarlo en un archivo llamado container-f8f57079a323.service:

$ podman generate systemd -f f8f57079a323

Para generar un archivo de unidad systemd para el contenedor con nombre mywebserver y usar el nombre del contenedor en la unidad:

$ podman generate systemd -n mywebserver

Para generar un archivo de unidad systemd para el pod con ID a2e589503a10:

$ podman generate systemd a2e589503a10

Para generar un archivo de unidad systemd para el pod con ID a2e589503a10 y guardarlo en un archivo llamado pod-a2e589503a10.service:

$ podman generate systemd -f a2e589503a10

Para generar archivos de unidad para todos los contenedores y pods actualmente en ejecución y guardarlos en el directorio actual:

$ podman generate systemd --files --name

Para generar un archivo de unidad systemd para el contenedor f8f57079a323, que crea el contenedor al iniciar la unidad:

$ podman generate systemd --new f8f57079a323

Para generar un archivo de unidad systemd para el contenedor f8f57079a323, que crea el contenedor al iniciar la unidad y depende de la unidad network-online.target:

$ podman generate systemd --new --after network-online.target f8f57079a323

Para generar un archivo de unidad systemd para el contenedor f8f57079a323, que crea el contenedor al iniciar la unidad y agrega la dependencia de deseo en la unidad time-sync.target:

$ podman generate systemd --new --wants time-sync.target f8f57079a323

Para generar un archivo de unidad systemd para el contenedor f8f57079a323, estableciendo la política de reinicio a "always":

$ podman generate systemd --restart-policy=always f8f57079a323

Para generar un archivo de unidad systemd para el contenedor f8f57079a323, estableciendo la política de reinicio a "on-failure" y el tiempo de espera de reinicio a 5 segundos:

$ podman generate systemd --restart-policy=on-failure --restart-sec=5s f8f57079a323

Para generar un archivo de unidad systemd para el contenedor f8f57079a323 con un tiempo de espera de parada de 10 segundos:

$ podman generate systemd --stop-timeout 10 f8f57079a323

Para generar un archivo de unidad systemd para el contenedor f8f57079a323 con la variable de entorno MYVAR configurada en "myvalue" y la variable ANOTHERVAR configurada en el entorno del host:

$ podman generate systemd -e MYVAR=myvalue -e ANOTHERVAR= f8f57079a323

Para generar un archivo de unidad systemd para el contenedor f8f57079a323 que incluye las variables de entorno del host que comienzan con MYPREFIX_:

$ podman generate systemd -e MYPREFIX_= f8f57079a323

Para generar un archivo de unidad systemd para el contenedor f8f57079a323, que crea el contenedor al iniciar la unidad y utiliza el formato JSON:

$ podman generate systemd --new --format json f8f57079a323

Para generar un archivo de unidad systemd para el contenedor f8f57079a323, que crea el contenedor al iniciar la unidad y usa un separador de guiones bajos en lugar de un guión:

$ podman generate systemd --new --separator=_ f8f57079a323

Generar un archivo de unidad systemd con plantilla para el contenedor con ID f8f57079a323

Cuando se genera un archivo de unidad con la opción --template, este archivo puede ser utilizado como una plantilla para crear múltiples unidades basadas en él. Por ejemplo, si se genera un archivo de unidad para un contenedor llamado `mycontainer` con la opción `--template`, se creará un archivo llamado `container-mycontainer@.service`. Este archivo puede ser usado de la siguiente manera:

$ systemctl --user start container-mycontainer@test.service

Esto creará y comenzará un contenedor basado en `mycontainer` y lo llamará `test`.

Generar un archivo de unidad systemd para un pod con el contenedor de infraestructura

Para generar un archivo de unidad systemd para el pod con ID a2e589503a10, que incluye el contenedor de infraestructura:

$ podman generate systemd --infra=true a2e589503a10

r a container

Genere un archivo de unidad systemd para un contenedor que ejecute nginx con una always política de reinicio y un tiempo de espera de 1 segundo a stdout. Tenga en cuenta que la RequiresMountsFor opción en la Unit sección asegura que el almacenamiento del contenedor tanto para el GraphRoot como para el RunRoot esté montado antes de iniciar el servicio. Para sistemas con almacenamiento de contenedores en discos como iSCSI u otros protocolos de bloque remoto, esto asegura que Podman no se ejecute antes de que las operaciones de almacenamiento necesarias estén en línea.

$ podman create --name nginx nginx:latest
$ podman generate systemd --restart-policy=always -t 1 nginx

Genere el archivo de unidad systemd para un contenedor con el --new indicador

El --new indicador genera archivos de unidad systemd que crean y eliminan contenedores en los comandos de inicio y parada del servicio (vea las acciones de servicio ExecStartPre y ExecStopPost). Dichos archivos de unidad no están atados a una sola máquina y pueden compartirse y usarse fácilmente en otras máquinas.

$ sudo podman generate systemd --new --files --name bb310a0780ae
# container-busy_moser.service
# autogenerated by Podman 1.8.3
# Fri Apr  3 09:40:47 EDT 2020
[Unit]
Description=Podman container-busy_moser.service
Documentation=man:podman-generate-systemd(1)
Wants=network-online.target
After=network-online.target
RequiresMountsFor=/var/run/container/storage
[Service]
Environment=PODMAN_SYSTEMD_UNIT=%n
Restart=on-failure
ExecStartPre=/bin/rm -f %t/%n-pid %t/%n-cid
ExecStart=/usr/local/bin/podman run   
        --conmon-pidfile %t/%n-pid   
	--cidfile %t/%n-cid   
	--cgroups=no-conmon   
	-d   
	-dit alpine
ExecStop=/usr/local/bin/podman stop   
        --ignore   
        --cidfile %t/%n-cid -t 10
ExecStopPost=/usr/local/bin/podman rm   
        --ignore   
        -f   
	--cidfile %t/%n-cid
PIDFile=%t/%n-pid
KillMode=none
Type=forking
[Install]
WantedBy=default.target

Genere archivos de unidad systemd para un pod con dos contenedores alpine simples

Nota systemctl solo debe usarse en la unidad del pod y no para iniciar o detener los contenedores individualmente. Los contenedores son gestionados por el servicio del pod junto con el contenedor de infraestructura interno.

Use systemctl status o journalctl para examinar los archivos de unidad del contenedor o del pod.

$ podman pod create --name systemd-pod
$ podman create --pod systemd-pod alpine top
$ podman create --pod systemd-pod alpine top
$ podman generate systemd --files --name systemd-pod
/home/user/pod-systemd-pod.service
/home/user/container-amazing_chandrasekhar.service
/home/user/container-jolly_shtern.service
$ cat pod-systemd-pod.service

Instalación de archivos de unidad systemd generados.

Los archivos de unidad generados por Podman incluyen una [Install] sección, que lleva la información de instalación de la unidad. Es utilizada por los comandos enable y disable de systemctl(1) durante la instalación.

Una vez que el archivo de unidad systemd es generado, instálelo en /etc/systemd/system para que sea ejecutado por el usuario root o en $HOME/.config/systemd/user para instalarlo como un usuario no root. Habilite el archivo de unidad copiado o los archivos usando systemctl enable.

Nota: Copiar archivos de unidad a /etc/systemd/system y habilitarlos marca el archivo de unidad para que se inicie automáticamente en el arranque. Y de manera similar, copiar un archivo de unidad a $HOME/.config/systemd/user y habilitarlo marca el archivo de unidad para que se inicie automáticamente cuando el usuario inicie sesión.

# Generated systemd files.
$ podman pod create --name systemd-pod
$ podman create --pod systemd-pod alpine top
$ podman generate systemd --files --name systemd-pod
# Copy all the generated files.
$ sudo cp pod-systemd-pod.service container-great_payne.service /etc/systemd/system
$ systemctl enable pod-systemd-pod.service
Created symlink /etc/systemd/system/multi-user.target.wants/pod-systemd-pod.service → /etc/systemd/system/pod-systemd-pod.service.
Created symlink /etc/systemd/system/default.target.wants/pod-systemd-pod.service → /etc/systemd/system/pod-systemd-pod.service.
$ systemctl is-enabled pod-systemd-pod.service
enabled

Para ejecutar los servicios de usuario colocados en $HOME/.config/systemd/user en el primer inicio de sesión de ese usuario, habilite el servicio con el indicador --user.

$ systemctl --user enable <.service>

La instancia de systemd del usuario se termina después de que la última sesión del usuario se cierra. La instancia de systemd del usuario puede iniciarse en el arranque y mantenerse en ejecución incluso después de que el usuario cierre sesión habilitando lingering usando

$ loginctl enable-linger <username>

Use systemctl para realizar operaciones en los archivos de unidad instalados generados.

Cree y habilite archivos de unidad systemd para un pod usando los ejemplos anteriores como referencia y use systemctl para realizar operaciones.

Dado que systemctl usa por defecto el usuario root, todos los cambios realizados con systemctl pueden verse añadiendo sudo a los comandos de la interfaz de línea de comandos de podman. Para realizar acciones de systemctl como un usuario no root, use el --user indicador al interactuar con systemctl.

Nota: Si los contenedores o pods creados anteriormente están usando recursos compartidos, como puertos, asegúrese de eliminarlos antes de iniciar las unidades systemd generadas.

$ systemctl --user start pod-systemd-pod.service
$ podman pod ps
POD ID         NAME          STATUS    CREATED          # OF CONTAINERS   INFRA ID
0815c7b8e7f5   systemd-pod   Running   29 minutes ago   2                 6c5d116f4bbe
$ sudo podman ps # 0 Number of pods on root.
CONTAINER ID  IMAGE  COMMAND  CREATED  STATUS  PORTS  NAMES
$ systemctl stop pod-systemd-pod.service
$ podman pod ps
POD ID         NAME          STATUS   CREATED          # OF CONTAINERS   INFRA ID
272d2813c798   systemd-pod   Exited   29 minutes ago   2                 6c5d116f4bbe

Cree un contenedor alpine simple y genere el archivo de unidad systemd con el --new indicador. Habilite el servicio y controle las operaciones usando los comandos systemctl.

Nota: Al iniciar el contenedor usando systemctl start en lugar de alterar el contenedor ya en ejecución, se inicia un contenedor "nuevo" con una configuración similar.

# Enable the service.
