DESCRIPCIÓ

N

podman kube play lee un archivo estructurado de YAML de Kubernetes. Recrea los contenedores, pods o volúmenes descritos en el YAML. Los contenedores dentro de un pod se inician a continuación, y se emite el ID del nuevo Pod o el nombre del nuevo Volumen. Si el archivo YAML se especifica como "-", entonces podman kube play lee el archivo YAML desde stdin. La entrada también puede ser una URL que apunte a un archivo YAML como https://podman.io/demo.yml. podman kube play lee el YAML desde la URL y crea pods y contenedores a partir de

él.

Usando la opción de línea de comandos --down, también es capaz de eliminar los pods creados por una ejecución anterior de podman kube

play.

Usando la opción de línea de comandos --replace, elimina los pods (si los hay) creados por una ejecución anterior de podman kube play y recrea los pods con el archivo YAML de

Kubernetes.

Idealmente, el archivo de entrada es creado por el comando Podman (ver podman-kube-generate(1)). Esto garantiza una importación fluida y resultados

esperados.

Pods o Deployments de

Kubernetes

Kube play solo soporta cinco tipos de volumen, los hostPath, emptyDir, configMap, persistentVolumeClaim, y image

.
  • Al usar el tipo de volumen hostPath, solo se soportan los subtipos por defecto (vacío), DirectoryOrCreate, Directory, FileOrCreate, File, Socket, CharDevice y BlockDevice. Podman interpreta el valor de hostPath path como una ruta de archivo cuando contiene al menos una barra diagonal, de lo contrario Podman trata el valor como el nombre de un volumen con
    • nombre.
  • Al usar un persistentVolumeClaim, el valor para claimName es el nombre del volumen con nombre de
    • Podman.
  • Al usar un volumen emptyDir, Podman crea un volumen anónimo que se adjunta a los contenedores que se ejecutan dentro del pod y se elimina una vez que el pod se
    • elimina.
  • Al usar un volumen configMap, Podman crea un volumen anónimo que se adjunta a los contenedores que se ejecutan dentro del pod y se elimina una vez que el pod se
    • elimina.
  • Al usar un volumen image, Podman crea un volumen de imagen de solo lectura con una subruta vacía (se mo
    • nta la imagen completa). La imagen debe existir
localmente. Solo se soporta en modo rootful.

Nota: La política de reinicio por defecto para los contenedores es always. Puede cambiar el valor por defecto estableciendo el campo restartPolicy en la

spec.

Nota: Al reproducir un YAML de kube con contenedores init, el contenedor init se crea con el valor de tipo init once. Para cambiar el tipo por defecto, use la anotación io.podman.annotations.init.container.type para establecer el tipo en always

.

Nota: Los tipos de volumen hostPath creados por kube play reciben una etiqueta compartida de SELinux (z), los montajes bind no se reetiquetan (use chcon -t container_file_t -R <directorio>)

.

Nota: Para establecer el userns de un pod, use la anotación io.podman.annotations.userns en la definición del pod/deployment. Por ejemplo, la anotación io.podman.annotations.userns=keep-id le indica a Podman que cree un espacio de nombres de usuario donde el UID:GID del usuario rootless actual se mapean a los mismos valores en el contenedor. Esto se puede sobrescribir con el indicador --u

serns.

Nota: Use la anotación io.podman.annotations.volumes-from para montar por bind los volúmenes de un contenedor a otro. Puede montar volúmenes de múltiples contenedores de origen a un contenedor de destino. Los contenedores de origen que pertenecen al mismo pod deben definirse antes que el contenedor de origen en el YAML de kube. El formato de la anotación es io.podman.annotations.volumes-from/contenedorDestino: "contenedorOrigen1:opcionesMontaje1;contenedorOrigen2:opcionesMontaje2"

.

Nota: Si se usa la etiqueta :latest, Podman intenta extraer la imagen de un registro. Si la imagen se construyó localmente con Podman o Buildah, tiene localhost como dominio, en ese caso, Podman usa la imagen del almacén local incluso si tiene la etiqueta :

latest.

Nota: El comando podman play kube es un alias de podman kube play, y realiza la misma

función.

Nota: El comando podman kube down se puede usar para detener y eliminar pods o contenedores basados en el mismo YAML de Kubernetes usado por podman kube play para

crearlos.

Nota: Para personalizar el nombre del contenedor infra creado durante podman kube play, use la anotación io.podman.annotations.infra.name en la definición del pod. Esta anotación se establece automáticamente al generar un kube yaml a partir de un pod que se creó con el indicador --infra-name

establecido.

Nota: Use la anotación io.podman.annotations.pids-limit/$nombreContenedor para configurar el límite de pids del

pod.

Nota: Use la anotación io.podman.annotations.cpuset/$nombreContenedor para restringir la ejecución de un contenedor a un conjunto específico de núcleos de CPU. Esto es equivalente a la opción --cpuset-cpus=número en podman-run(1)

.

Nota: Use la anotación io.podman.annotations.memory-nodes/$nombreContenedor para restringir las asignaciones de memoria de un contenedor a un conjunto específico de nodos de memoria en sistemas NUMA. Esto es equivalente a la opción --cpuset-mems=nodos en podman-run(1)

.

ConfigMap de

Kubernetes

Un ConfigMap de Kubernetes se puede referenciar como una fuente de variables de entorno o volúmenes en Pods o Deployments. Los ConfigMaps no son un objeto independiente en Podman; en su lugar, cuando un contenedor usa un ConfigMap, Podman crea variables de entorno o volúmenes según sea

necesario.

Por ejemplo, el siguiente documento YAML define un ConfigMap y luego lo usa en un

Pod: 
apiVersion: v1
kind: ConfigMap
metadata:
  name: foo
data:
    FOO: bar
---
apiVersion: v1
kind: Pod
metadata:
  name: foobar
spec:
  containers:
  - name: container-1
    image: foobar
    envFrom:
    - configMapRef:
        name: foo
        optional: false

y como resultado, la variable de entorno FOO se establece en bar para el contenedor container-1.

Kubernetes Secret

Kubernetes Secret representa un secreto con nombre de Podman. El Kubernetes Secret se guarda en su totalidad y puede ser referenciado como fuente de variables de entorno o volúmenes en Pods o Deployments.

Por ejemplo, el siguiente documento YAML define un Secret y luego lo usa en un Pod:

kind: Secret
apiVersion: v1
metadata:
  name: foo
data:
  foo: YmFy # base64 para bar
---
apiVersion: v1
kind: Pod
metadata:
  name: foobar
spec:
  containers:
  - name: container-1
    image: foobar
    env:
    - name: FOO
      valueFrom:
        secretKeyRef:
          name: foo
          key: foo

y como resultado, la variable de entorno FOO se establece en bar para el contenedor container-1.

Montaje automático de volúmenes (obsoleto)

Nota: La anotación de montaje automático está obsoleta. Kubernetes tiene soporte nativo para volúmenes de imagen y se debe usar en lugar de esta anotación específica de Podman.

Una imagen puede montarse automáticamente en un contenedor si se proporciona la anotación io.podman.annotations.kube.image.automount/$ctrname. Se aplican las siguientes reglas:

  • La imagen debe existir localmente.
  • La imagen debe tener al menos 1 directiva de volumen.
  • La ruta dada por la directiva de volumen se montará desde la imagen al contenedor. Por ejemplo, una imagen con un volumen en /test/test_dir tendrá /test/test_dir en la imagen montado en /test/test_dir en el contenedor.
  • Se pueden especificar múltiples imágenes. Si múltiples imágenes tienen un volumen en una ruta específica, la última imagen especificada tiene prevalencia.
  • Las imágenes siempre se montan en modo de solo lectura.
  • Las imágenes a montar se definen en la anotación "io.podman.annotations.kube.image.automount/$ctrname" como una lista separada por punto y coma. Se montan en un solo contenedor en el pod, no en todo el pod. La anotación se puede especificar para contenedores adicionales si se requieren montajes adicionales.

OPCIONES

--annotation=key=value

Agrega una anotación al contenedor o pod. Esta opción se puede establecer varias veces.

Nota: Para podman kube play, el indicador --annotation agrega anotaciones específicas de Podman a los contenedores y pods creados por Podman, no al propio YAML de Kubernetes. Estas anotaciones se pueden usar para configurar funciones específicas de Podman como espacios de nombres de usuario (io.podman.annotations.userns), volúmenes-desde (io.podman.annotations.volumes-from) y otros comportamientos del contenedor.

--authfile=path

Ruta del archivo de autenticación. El valor predeterminado es ${XDG_RUNTIME_DIR}/containers/auth.json en Linux, y $HOME/.config/containers/auth.json en Windows/macOS. El archivo es creado por podman login. Si el estado de autorización no se encuentra allí, se verifica $HOME/.docker/config.json, que se establece usando docker login.

Nota: También existe la opción de anular la ruta predeterminada del archivo de autenticación estableciendo la variable de entorno REGISTRY_AUTH_FILE. Esto se puede hacer con export REGISTRY_AUTH_FILE=ruta.

--build

Construye imágenes incluso si se encuentran en el almacenamiento local. Usa --build=false para deshabilitar completamente las compilaciones. (Esta opción no está disponible con el cliente Podman remoto)

Nota: También puedes anular el tipo de aislamiento predeterminado estableciendo la variable de entorno BUILDAH_ISOLATION. export BUILDAH_ISOLATION=oci. Consulta podman-build.1.md para más información.

--cert-dir=path

Usa los certificados en ruta (*.crt, *.cert, *.key) para conectarte al registro. (Predeterminado: /etc/containers/certs.d) Para más detalles, consulta containers-certs.d(5). (Esta opción no está disponible con el cliente Podman remoto, incluidas las máquinas Mac y Windows (excluyendo WSL2))

--configmap=path

Usa el YAML de configmap de Kubernetes en la ruta para proporcionar una fuente de valores de variables de entorno dentro de los contenedores del pod. (Esta opción no está disponible con el cliente Podman remoto)

Nota: La opción --configmap se puede usar varias veces o se puede usar una lista de rutas separadas por comas para pasar múltiples YAMLs de configmap de Kubernetes. El archivo YAML puede estar en formato YAML multidocumento. Pero, solo debe contener configmaps.

--context-dir=path

Usa ruta como directorio de contexto de construcción para cada imagen. Requiere que la opción --build sea true. (Esta opción no está disponible con el cliente Podman remoto)

--creds=[username[:password]]

El [nombre de usuario[:contraseña]] a usar para autenticarse con el registro, si es necesario. Si uno o ambos valores no se proporcionan, aparece un aviso en la línea de comandos y se puede ingresar el valor. La contraseña se ingresa sin mostrarse.

Ten en cuenta que las credenciales especificadas solo se utilizan para autenticarse contra los registros de destino. No se utilizan para espejos ni cuando el registro se reescribe (ver containers-registries.conf(5)); para autenticarse contra ellos, considera usar un archivo containers-auth.json(5).

OPTIONS

You can specify the following options:

--userns-auto [OPTIONS]

Run the pod in a new user namespace. The user namespace is created with the range of UIDs and GIDs specified in /etc/subuid and /etc/subgid.

In the user namespace, the container will run with the user ID (UID) and group ID (GID) specified in the image, but on the host, the container will run with a UID and GID range that is not available to the user.

This prevents the container from accessing the user's files on the host, unless the user has explicitly granted access to them.

Podman can create a user namespace for the container that is configured to use a specific size, which is not necessarily the size of the user ID and group ID range specified in /etc/subuid and /etc/subgid.

The user namespace will be created with the specified size if the size is less than or equal to the number of UIDs and GIDs that are available to the user.

The user namespace will be created with the size of the user ID and group ID range specified in /etc/subuid and /etc/subgid if the specified size is greater than the number of UIDs and GIDs that are available to the user.

Podman kube play also supports the following options:

  • gidmapping=CONTAINER_GID:HOST_GID:SIZE: para forzar un mapeo de GID a estar presente en el espacio de nombres de usuario.
  • size=SIZE: para especificar un tamaño explícito para el espacio de nombres de usuario automático. por ejemplo, --userns=auto:size=8192. Si no se especifica size, auto estima un tamaño para el espacio de nombres de usuario.
  • uidmapping=CONTAINER_UID:HOST_UID:SIZE: para forzar un mapeo de UID a estar presente en el espacio de nombres de usuario.

El UID y GID del host en gidmapping y uidmapping pueden prefijarse opcionalmente con el símbolo @. En este caso, podman buscará el ID intermedio correspondiente al ID del host y mapeará el ID intermedio encontrado al ID del contenedor. Para más detalles, consulte --uidmap.

container:id: únete al espacio de nombres de usuario del contenedor especificado.

host o "" (cadena vacía): ejecuta en el espacio de nombres de usuario del llamador. Los procesos que se ejecutan en el contenedor tienen los mismos privilegios en el host que cualquier otro proceso iniciado por el usuario que llama.

keep-id: crea un espacio de nombres de usuario donde el UID:GID del usuario actual se mapea a los mismos valores en el contenedor. Para contenedores creados por root, el mapeo actual se crea en un nuevo espacio de nombres de usuario.

Además, el proceso init dentro del contenedor se ejecutará bajo el UID del usuario actual. Este comportamiento anula la instrucción USER de la imagen a menos que establezca explícitamente --user.

Opciones válidas de keep-id:

  • uid=UID: anula el UID dentro del contenedor que se utiliza para mapear al usuario actual.
  • gid=GID: anula el GID dentro del contenedor que se utiliza para mapear al usuario actual.
  • size=SIZE: anula el tamaño del espacio de nombres de usuario configurado. Es útil para no saturar todos los IDs disponibles. No se soporta cuando se ejecuta como root.

nomap: crea un espacio de nombres de usuario donde el UID:GID del usuario actual sin root no se mapea al contenedor. Esta opción no está permitida para contenedores creados por el usuario root.

ns:namespace: ejecuta el pod en el espacio de nombres de usuario existente dado.

--wait, -w

Ejecuta pods y contenedores en primer plano. El valor predeterminado es falso.

En cualquier momento, puede ejecutar podman pod ps en otra terminal para ver una lista de los pods y contenedores en ejecución.

Cuando se adjunta en modo tty, puede matar los pods y contenedores presionando Ctrl-C o recibiendo cualquier otra señal de interrupción.

Todos los pods, contenedores y volúmenes creados con podman kube play se eliminan al salir.
