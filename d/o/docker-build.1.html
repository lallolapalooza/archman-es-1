NOMBRE

docker-build - Construye una imagen a partir de un Dockerfile

SINOPSIS

docker build [--add-host[=[]]] [--build-arg[=[]]] [--cache-from[=[]]] [-c|--cpu-shares[=0]] [--cgroup-parent[=CGROUP-PARENT]] [--help] [--iidfile[=IIDFILE]] [-f|--file[=PATH/Dockerfile]] [-squash] Experimental [--force-rm] [--isolation[=default]] [--label[=[]]] [--no-cache] [--pull] [--compress] [-q|--quiet] [--rm[=true]] [-t|--tag[=[]]] [-m|--memory[=MEMORY]] [--memory-swap[=LIMIT]] [--network[="default"]] [--shm-size[=SHM-SIZE]] [--cpu-period[=0]] [--cpu-quota[=0]] [--cpuset-cpus[=CPUSET-CPUS]] [--cpuset-mems[=CPUSET-MEMS]] [--target[=[]]] [--ulimit[=[]]] PATH | URL | -

DESCRIPCIÓN

Esto leerá el Dockerfile del directorio especificado en PATH. También enviará todos los demás archivos y directorios encontrados en el directorio actual al demonio de Docker. El contenido de este directorio sería utilizado por los comandos ADD que se encuentran dentro del Dockerfile.

Advertencia, esto enviará una gran cantidad de datos al demonio de Docker dependiendo del contenido del directorio actual. La compilación es ejecutada por el demonio de Docker, no por la CLI, por lo que todo el contexto debe ser transferido al demonio. La CLI de Docker muestra "Sending build context to Docker daemon" (Enviando contexto de compilación al demonio de Docker) cuando el contexto se envía al demonio.

Cuando se proporciona la URL de un archivo tarball o de un único Dockerfile, no se envía ningún contexto del cliente al demonio de Docker. En este caso, el Dockerfile en la raíz del archivo y el resto del archivo se utilizarán como contexto de la compilación. Cuando se establece un repositorio Git como URL, el repositorio se clona localmente y luego se envía como contexto.

OPCIONES

-f, --file PATH/Dockerfile
Ruta al Dockerfile a utilizar. Si la ruta es una ruta relativa y estás
compilando desde un directorio local, entonces la ruta debe ser relativa a ese
directorio. Si estás compilando desde una URL remota que apunta a un archivo tarball
o a un repositorio Git, entonces la ruta debe ser relativa a la raíz del
contexto remoto. En todos los casos, el archivo debe estar dentro del contexto de compilación.
El valor predeterminado es Dockerfile.

--squash true|false
Solo experimental
Una vez que la imagen se compila, comprime las nuevas capas en una nueva imagen con una sola
capa nueva. Comprimir no destruye ninguna imagen existente, sino que crea una nueva
imagen con el contenido de las capas comprimidas. Esto efectivamente hace que parezca
que todos los comandos de Dockerfile se crearon con una sola capa. El caché de
compilación se conserva con este método.

Nota: usar esta opción significa que la nueva imagen no podrá aprovechar
el uso compartido de capas con otras imágenes y puede ocupar significativamente más
espacio.

Nota: usar esta opción puede resultar en un uso de espacio significativamente mayor debido a
almacenar dos copias de la imagen, una para el caché de compilación con todas las capas
del caché intactas, y otra para la versión comprimida.

--add-host []
Agrega un mapeo personalizado de host a IP (host=ip, o host:ip)

Agrega una línea a /etc/hosts. El formato es nombre_host=ip, o nombre_host:ip.
La opción --add-host se puede establecer varias veces.

--build-arg variable
nombre y valor de un buildarg.

Por ejemplo, si deseas pasar un valor para http_proxy, usa
--build-arg=http_proxy="http://some.proxy.url"

Los usuarios pasan estos valores en el momento de la compilación. Docker utiliza los buildargs como
contexto de entorno para los comandos ejecutados a través de la instrucción RUN del Dockerfile
o para la expansión de variables en otras instrucciones del Dockerfile. Esto no está pensado
para pasar valores secretos. Lee más sobre la instrucción buildargs ⟨https://docs.docker.com/engine/reference/builder/#arg⟩

--cache-from ""
Establece la imagen que se utilizará como fuente de caché de compilación.

--force-rm true|false
Elimina siempre los contenedores intermedios, incluso después de compilaciones fallidas. El
valor predeterminado es false.

--isolation "default"
El aislamiento especifica el tipo de tecnología de aislamiento utilizada por los contenedores.

--label label
Establece metadatos para una imagen

--no-cache true|false
No utilices la caché al compilar la imagen. El valor predeterminado es false.

--iidfile ""
Escribe el ID de la imagen en el archivo

--help
Imprime la declaración de uso

--pull true|false
Intenta siempre obtener una versión más reciente de la imagen. El valor predeterminado es
false.

--compress true|false
Comprime el contexto de compilación usando gzip. El valor predeterminado es false.

-q, --quiet true|false
Suprime la salida de la compilación e imprime el ID de la imagen en caso de éxito. El
valor predeterminado es false.

--rm true|false
Elimina los contenedores intermedios después de una compilación exitosa. El valor
predeterminado es true.

-t, --tag ""
Nombres de repositorio (y opcionalmente con etiquetas) que se aplicarán a la imagen resultante
en caso de éxito. Consulta docker-tag(1) para obtener más información
sobre nombres de etiquetas válidos.

-m, --memory MEMORY
Límite de memoria

--memory-swap number[S]
Límite combinado de memoria más swap; S es un sufijo opcional que puede ser uno
de b (bytes), k (kilobytes), m (megabytes), o g (gigabytes).
Esta opción solo se puede usar junto con --memory. El argumento siempre debe ser mayor que el de
--memory. El valor predeterminado es el doble del valor de --memory. Establécelo a
-1 para habilitar el swap ilimitado.

--network type
Establece el modo de red para las instrucciones RUN durante la compilación. Los valores
estándar admitidos son: none, bridge, host y container:<name|id>. Cualquier otro valor
se toma como el nombre o ID de una red personalizada a la que este contenedor debería conectarse.
En Linux, el valor predeterminado es bridge.

--shm-size SHM-SIZE
Tamaño de /dev/shm. El formato es <número><unidad>. El
número debe ser mayor que 0.
La unidad es opcional y puede ser b (bytes), k (kilobytes), m (megabytes), o g (gigabytes). Si omites la unidad, el sistema usa bytes.
Si omites el tamaño por completo, el sistema usa 64m.

-c, --cpu-shares 0
Cuotas de CPU (peso relativo).

Por defecto, todos los contenedores obtienen la misma proporción de ciclos de CPU.
Las cuotas de CPU son un 'peso relativo', relativo al valor predeterminado de 1024.
Este valor predeterminado se define aquí:

   cat /sys/fs/cgroup/cpu/cpu.shares
   1024

Puedes cambiar esta proporción ajustando el peso de la CPU del contenedor en relación con el peso de todos los demás contenedores en ejecución.
Para modificar la proporción respecto al valor predeterminado de 1024, usa la bandera
-c o --cpu-shares para establecer el peso en 2 o superior.

  Contenedor   Cuota de CPU    Bandera
  {C0}        60% de CPU  --cpu-shares 614 (614 es el 60% de 1024)
  {C1}        40% de CPU  --cpu-shares 410 (410 es el 40% de 1024)

La proporción solo se aplica cuando se ejecutan procesos que consumen mucha CPU.
Cuando las tareas en un contenedor están inactivas, los otros contenedores pueden usar el
tiempo de CPU sobrante. La cantidad real de tiempo de CPU utilizado varía según la
cantidad de contenedores en ejecución en el sistema.

Por ejemplo, considera tres contenedores, donde uno tiene --cpu-shares 1024 y
dos de ellos tienen --cpu-shares 512. Cuando los procesos en los tres
contenedores intentan usar el 100%

% de CPU, el primer contenedor recibiría
50% del tiempo total de CPU. Si añades un cuarto contenedor con --cpu-shares 1024,
el primer contenedor solo obtiene el 33% de la CPU. Los contenedores restantes
reciben el 16.5%, 16.5% y 33% de la

CPU. 
  Contenedor   Cuota de CPU   Bandera                Tiempo de CPU
  {C0}        100%        --cpu-shares 1024   33%
  {C1}        50%         --cpu-shares 512    16.5%
  {C2}        50%         --cpu-shares 512    16.5%
  {C4}        100%        --cpu-shares 1024
33%

En un sistema multicore, las cuotas de tiempo de CPU se distribuyen a través de los
núcleos de la CPU. Incluso si un contenedor está limitado a menos del 100% del tiempo de CPU, puede
usar el 100% de cada núcleo de CPU

individual.

Por ejemplo, considera un sistema con más de tres núcleos. Si inicias un
contenedor {C0} con --cpu-shares 512 ejecutando un proceso, y otro contenedor
{C1} con --cpu-shares 1024 ejecutando dos procesos, esto puede resultar en la siguiente
división de cuotas de

CPU: 
  PID    contenedor    CPU    Cuota de CPU
  100    {C0}         0      100% de CPU0
  101    {C1}         1      100% de CPU1
  102    {C1}         2      100% de
CPU2

--cpu-period 0
Limita el periodo CFS (Completely Fair Scheduler) de la

CPU.

Limita el uso de CPU del contenedor. Esta bandera hace que el kernel restrinja el
uso de CPU del contenedor al periodo que

especifiques.

--cpu-quota 0
Limita la cuota CFS (Completely Fair Scheduler) de la

CPU.

Por defecto, los contenedores se ejecutan con el recurso completo de la CPU. Esta bandera hace que el kernel restrinja el uso de CPU del contenedor a la cuota que

especifiques.

--cpuset-cpus CPUSET-CPUS
CPUs en las que permitir la ejecución (0-3, 0,1)

.

--cpuset-mems CPUSET-MEMS
Nodos de memoria (MEMs) en los que permitir la ejecución (0-3, 0,1). Solo es efectivo en
sistemas

NUMA.

Por ejemplo, si tienes cuatro nodos de memoria en tu sistema (0-3), usa --cpuset-mems 0,1 para asegurar que los procesos en tu contenedor de Docker solo usen memoria de los dos primeros nodos de

memoria.

--cgroup-parent CGROUP-PARENT
Ruta a cgroups bajo los cuales el cgroup del contenedor es

creado.

Si la ruta no es absoluta, la ruta se considera relativa a la ruta de cgroups del proceso init. Los cgroups se crean si no existen

ya.

--target ""
Establece el nombre de la etapa de construcción

objetivo.

--ulimit []
Opciones de

ulimit

Para más información sobre ulimit consulta Establecer ulimits en un contenedor ⟨https://docs.docker.com/engine/reference/commandline/run/#set-ulimits-in-container---ulimi

t⟩

Construyendo una imagen usando un Dockerfile ubicado dentro del directorio

actual

Las imágenes de Docker se pueden construir usando el comando build y un

Dockerfile: 
docker build
.

Durante el proceso de construcción Docker crea imágenes intermedias. En orden de conservarlas, debes establecer explícitamente --rm fa

lse. 
docker build --rm false
.

Una buena práctica es crear un subdirectorio con un nombre relacionado y crear el Dockerfile en ese directorio. Por ejemplo, un directorio llamado mongo puede contener un Dockerfile para crear una imagen de MongoDB de Docker. Del mismo modo, otro directorio llamado httpd puede usarse para almacenar Dockerfiles para imágenes del servidor web

Apache.

También es una buena práctica añadir los archivos requeridos para la imagen al subdirectorio. Estos archivos se especificarán con las instrucciones COPY o ADD en el Dockerfile

.

Nota: Si incluyes un archivo tar (una buena práctica), entonces Docker extraerá automáticamente el contenido del archivo tar especificado dentro de la instrucción ADD en el

destino es
pecificado.

Construyendo una imagen y nombrando esa

imagen

Una buena práctica es darle un nombre a la imagen que estás construyendo. Nota que solo se deben usar a-z0-9-_ para consistencia. No hay reglas estrictas aquí pero es mejor darle consideración a los

nombres.

La bandera -t/--tag se usa para renombrar una imagen. Aquí hay algunos

ejemplos:

Aunque no es una buena práctica, los nombres de imagen pueden ser

arbitrarios: 
docker build -t myimage
.

Un mejor enfoque es proporcionar un repositorio, nombre y etiqueta completamente calificados y significativos (donde la etiqueta en este contexto significa el calificador después del ":"). En este ejemplo construimos una imagen de JBoss para el repositorio Fedora y le damos la versión 1.

0: 
docker build -t fedora/jboss:1.0
.

El siguiente ejemplo es para el repositorio de usuario "whenry" y usa Fedora y JBoss y le da la versión 2.1

: 
docker build -t whenry/fedora-jboss:v2.1
.

Si no proporcionas una etiqueta de versión entonces Docker asignará latest

: 
docker build -t whenry/fedora-jboss
.

Cuando listes las imágenes, la imagen de arriba tendrá la etiqueta latest

.

Puedes aplicar múltiples etiquetas a una imagen. Por ejemplo, puedes aplicar la etiqueta latest a una imagen recién construida y añadir otra etiqueta que referencie una versión específica. Por ejemplo, para etiquetar una imagen tanto como whenry/fedora-jboss:latest como whenry/fedora-jboss:v2.1, usa lo

siguiente: 
docker build -t whenry/fedora-jboss:latest -t whenry/fedora-jboss:v2.1
.

Así que renombrar una imagen es arbitrario pero se debe dar considera

ción a una convención útil que tenga sentido para los consumidores y tam
bién debe tener en cuenta las convenciones de la comunidad de Docker.

Construyendo una imagen usando una

URL

Esto clonará el repositorio de GitHub especificado desde la URL y lo usará como contexto. El Dockerfile en la raíz del repositorio se usa como Dockerfile. Esto solo funciona si el repositorio de GitHub es un repositorio

dedicado. 
docker build github.com/scollier/purpletes
t

Nota: Puedes establecer un repositorio Git arbitrario a través del esquema

git
://.

Construyendo una imagen usando una URL a un contexto en

tarball

Esto enviará la URL en sí al demonio de Docker. El demonio obtendrá el archivo tarball, lo descomprimirá y usará su contenido como el contexto de construcción. El Dockerfile en la raíz del archivo y el resto del archivo se usarán como el contexto de la construcción. Si pasas una opción -f PATH/Dockerfile también, el sistema buscará ese archivo dentro del contenido del

tarball. 
docker build -f dev/Dockerfile https://10.10.10.1/docker/context.tar.
gz

Nota: los formatos de compresión so

portados son 'xz', 'bzip2', 'gzip'
y 'identity' (sin compresión).

Especificar tecnología de aislamiento para el contenedor

(--isolation)

Esta opción es útil en situaciones donde estás ejecutando contenedores de Docker en Windows. La opción --isolation <value> establece la tecnología de aislamiento de un contenedor. En Linux, la única soportada es la opción por defecto que usa los espacios de nombres de Linux. En Microsoft Windows, puedes especificar estos

valores:
  • default: Usa el valor especificado por el --exec-opt del demonio de Docker. Si el demonio no especifica una tecnología de aislamiento, Microsoft Windows usa process como su valor por
    • defecto.
  • process: Solo aislamiento por espacios de
    • nombres.
  • hyperv: Aislamiento basad
    • o en partició
n del hiperv
isor Hyper-V.

    docker-build(1)

    NAME

    docker-build - Build an image from a Dockerfile

    SYNOPSIS

    docker build [OPTIONS] PATH | URL | -

    DESCRIPTION

    Builds a Docker image from a Dockerfile.

    OPTIONS

    --add-host=[]: Add a custom host-to-IP mapping

    --allow-insecure-all: Allow all insecure transports for the image

    --build-arg=[]: Set build-time variables

    --cache-from=[]: Images to consider as cache sources

    --cgroup-parent="": Optional parent cgroup for the container

    --compress, -c: Compress the build context using gzip

    --cpu-shares, -c: CPU shares (default: 0)

    --disable-content-trust: Skip image signing

    --file, -f="": Name of the Dockerfile (default: Dockerfile)

    --force-rm: Always remove intermediate containers

    --help: Print usage

    --isolation="": Isolation technology (default: default)

    --label=[]: Add metadata to the image

    --memory, -m=0: Memory limit

    --memory-swap=0: Swap limit

    --no-cache: Do not use cache when building the image

    --platform="": Set platform if server is multi-platform capable

    --progress="": Set type of progress output (auto, tty, plain) (default: auto)

    --pull: Always attempt to pull a newer version of the base image

    --quiet, -q: Suppress the build output

    --rm: Remove intermediate containers after a successful build (default behavior)

    --runtime="": Runtime to use for this container

    --security-opt=[]: Security options

    --shm-size=0: Size of /dev/shm

    --ulimit=[]: Ulimit options

    --tag, -t=[]: Name and optionally a tag in the format name:tag

    --target="": Target stage name

    --ulimit=[]: Ulimit options

    --unset-content-trust: Remove unsigned content trust data

    --userns-remap="": User namespace remapping

    --volumes-from=[]: Mount volumes from the specified container

    EXAMPLES

    Build an image from a Dockerfile in the current directory and tag it as my-image: 

    $ docker build -t my-image .

    Build an image from a Dockerfile in a different directory and tag it as my-app:1.0: 

    $ docker build -t my-app:1.0 /path/to/context

    Build an image from a URL and tag it as my-repo/my-image:latest: 

    $ docker build -t my-repo/my-image:latest https://github.com/docker/docker.git#community/docker-stuff

    Build an image using a Dockerfile named Dockerfile.dev and tag it as my-dev-image: 

    $ docker build -f Dockerfile.dev -t my-dev-image .

    docker(1), docker-commit(1), docker-save(1), docker-tag(1)
