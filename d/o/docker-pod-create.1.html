podman-pod-create(1) Manual de comandos generales podman-pod-create(1)

NOMBRE

podman-pod-create - Crea un nuevo pod

SINOPSIS

podman pod create [opciones] [nombre]

DESCRIPCIÓN

Crea un pod vacío, o unidad de múltiples contenedores, y lo prepara para añadirle contenedores. El pod se puede crear con un nombre específico. Si no se proporciona un nombre, se generará uno aleatorio. El ID del pod se imprime en STDOUT. Luego puedes usar podman create --pod <id_del_pod|nombre_del_pod> ... para añadir contenedores al pod, y podman pod start <id_del_pod|nombre_del_pod> para iniciar el pod.

El operador puede identificar un pod de tres maneras: Identificador largo UUID (“f78375b1c487e03c9438c729345e54db9d20cfa2ac1fc3494b6eb60872e74778”) Identificador corto UUID (“f78375b1c487”) Nombre (“jonah”)

podman genera un UUID para cada pod, y si no se asigna un nombre al contenedor con --name, se generará un nombre de cadena aleatoria para él. Este nombre es útil para identificar un pod.

Nota: las banderas relacionadas con el límite de recursos funcionan estableciendo los límites explícitamente en el padre cgroup del pod para todos los contenedores que se unen al pod. Un contenedor puede anular los límites de recursos al unirse a un pod. Por ejemplo, si un pod se creó a través de podman pod create --cpus=5, especificar podman container create --pod=<id_del_pod|nombre_del_pod> --cpus=4 hace que el contenedor utilice el límite menor. Además, los contenedores que especifican su propio cgroup, como --cgroupns=host, NO reciben los recursos cgroup asignados a nivel de pod.

OPCIONES

--add-host=hostname[;hostname[;...]]:ip

Añade un mapeo personalizado de host a IP al archivo /etc/hosts del pod.

La opción toma uno o varios nombres de host separados por punto y coma para mapearlos a una única dirección IPv4 o IPv6, separada por dos puntos. También se puede usar para sobrescribir las direcciones IP de los nombres de host que Podman añade a /etc/hosts por defecto (consulte también las opciones --name y --hostname). Esta opción se puede especificar varias veces para añadir mapeos adicionales a /etc/hosts. Entra en conflicto con la opción --no-hosts y con no_hosts=true en containers.conf.

En lugar de una dirección IP, se puede proporcionar el indicador especial host-gateway. Esto se resuelve a una dirección IP que el contenedor puede usar para conectarse al host. La dirección IP elegida depende de la configuración de red, por lo que no hay garantía de que Podman pueda determinar la dirección host-gateway automáticamente, lo que provocará que Podman falle con un mensaje de error. Puede sobrescribir esta dirección IP utilizando la opción host_containers_internal_ip en containers.conf.

La dirección host-gateway también es utilizada por Podman para añadir automáticamente los nombres de host host.containers.internal y host.docker.internal a /etc/hosts. Puede evitarlo proporcionando la opción --no-hosts o estableciendo host_containers_internal_ip="none" en containers.conf. Si no se configuró ninguna dirección host-gateway manualmente y Podman no puede determinar la dirección IP automáticamente, Podman omitirá silenciosamente la adición de estos nombres de host internos a /etc/hosts. Si Podman se está ejecutando en una máquina virtual usando podman machine (esto incluye hosts Mac y Windows), Podman omitirá silenciosamente la adición de los nombres de host internos a /etc/hosts, a menos que se haya configurado una dirección IP manualmente; los nombres de host internos se resuelven en su lugar mediante el resolvedor DNS de gvproxy.

Podman utiliza el archivo /etc/hosts del host como base por defecto, es decir, cualquier nombre de host presente en este archivo también estará presente en el archivo /etc/hosts del contenedor. Se puede configurar un archivo base diferente utilizando la configuración base_hosts_file en containers.conf.

El archivo /etc/hosts se comparte entre todos los contenedores del pod.

--blkio-weight=peso

Peso relativo de entrada/salida de bloque. El peso es un valor entre 10 y 1000.

Esta opción no se admite en sistemas sin root cgroups V1.

--blkio-weight-device=dispositivo:peso

Peso relativo de entrada/salida de bloque por dispositivo.

--cgroup-parent=ruta

Ruta a cgroups bajo la cual se crea el cgroup para el pod. Si la ruta no es absoluta, se considera relativa a la ruta cgroups del proceso de inicialización. Los cgroups se crean si no existen.

--cpu-shares, -c=recursos

Recursos de CPU (peso relativo).

Por defecto, todos los contenedores reciben la misma proporción de ciclos de CPU. Esta proporción se puede modificar cambiando el peso de los recursos de CPU del contenedor en relación con el peso combinado de todos los contenedores en ejecución. El peso por defecto es 1024.

La proporción solo se aplica cuando se ejecutan procesos intensivos en CPU. Cuando las tareas de un contenedor están inactivas, otros contenedores pueden utilizar el tiempo de CPU restante. La cantidad real de tiempo de CPU varía según el número de contenedores en ejecución en el sistema.

Por ejemplo, considere tres contenedores, uno con cpu-share de 1024 y otros dos con un ajuste de cpu-share de 512. Cuando los procesos en los tres contenedores intentan utilizar el 100% de la CPU, el primer contenedor recibe el 50% del tiempo total de CPU. Si se añade un cuarto contenedor con un cpu-share de 1024, el primer contenedor solo obtiene el 33% de la CPU. Los contenedores restantes reciben el 16.5%, 16.5% y 33% de la CPU.

En un sistema multinúcleo, las participaciones de tiempo de CPU se distribuyen en todos los núcleos de CPU. Incluso si un contenedor está limitado a menos del 100% del tiempo de CPU, puede utilizar el 100% de cada núcleo de CPU individual.

Por ejemplo, considere un sistema con más de tres núcleos. Si el contenedor C0 se inicia con --cpu-shares=512 ejecutando un proceso, y otro contenedor C1 con --cpu-shares=1024 ejecutando dos procesos, esto puede resultar en la siguiente división de participaciones de CPU:

PID contenedor CPU Participación de CPU
100 C0 0 100% de CPU0
101 C1 1 100% de CPU1
102 C1 2 100% de CPU2

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, consulte https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no se admite en sistemas sin root cgroups V1.

--cpus=cantidad

Establece el número total de CPUs delegadas al pod. El valor por defecto es 0.000, lo que indica que no hay límite en la potencia de cálculo.

--cpuset-cpus=número

CPUs en las que permitir la ejecución. Se puede especificar como una lista separada por comas (por ejemplo, 0,1), como un rango (por ejemplo, 0-3), o cualquier combinación de ellos (por ejemplo, 0-3,7,11-15).

En algunos sistemas, cambiar los límites de recursos puede no estar permitido para usuarios no root. Para más detalles, consulte https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Esta opción no se admite en sistemas sin root cgroups V1.

--cpuset-mems=nodos

Nodos de memoria (MEMs) en los que permitir la ejecución (0-3, 0,1). Solo es efectivo en sistemas NUMA.

Si hay cuatro nodos de memoria en el sistema (0-3), use --cpuset-mems=0,1 y los procesos en el contenedor solo usarán memoria de los dos primeros nodos de memoria.

  • ip=IPv4: Especifica una dirección IPv4 estática para este contenedor.
  • ip6=IPv6: Especifica una dirección IPv6 estática para este contenedor.
  • mac=MAC: Especifica una dirección MAC estática para este contenedor.
  • interface_name=nombre: Especifica un nombre para la interfaz de red creada dentro del contenedor.
  • host_interface_name=nombre: Especifica un nombre para la interfaz de red creada fuera del contenedor.
Cualquier otra opción se pasará a netavark sin validación. Esto puede ser útil para pasar argumentos a los complementos de netavark.

Por ejemplo, para establecer una dirección IPv4 estática y una dirección MAC estática, usa --network bridge:ip=10.88.0.10,mac=44:33:22:11:00:99.

  • <nombre o ID de red>[:OPCIONES,...]: Conéctate a una red definida por el usuario; este es el nombre o ID de una red creada por podman network create. Es posible especificar las mismas opciones descritas en el modo bridge anteriormente. Usa la opción --network varias veces para especificar redes adicionales.
    Para compatibilidad con versiones anteriores, también es posible especificar redes separadas por comas en el primer argumento de --network; sin embargo, esto te impide usar las opciones descritas en la sección bridge.
  • none: Crea un espacio de nombres de red para el contenedor, pero no configura interfaces de red para él, por lo que el contenedor no tiene conectividad de red.
  • container:id: Reutiliza la pila de red de otro contenedor.
  • host: Usa el espacio de nombres de red del host para el contenedor en lugar de crear un espacio de nombres aislado. Advertencia: Esto da al contenedor acceso completo a los sockets de dominio Unix abstractos y a los sockets TCP/UDP enlazados a localhost. Dado que estos mecanismos se usan a menudo para evitar el acceso a servicios del sistema sensibles, aislándolos del acceso de entidades externas, el uso de esta opción puede considerarse una vulnerabilidad de seguridad.
  • ns:ruta: Ruta a un espacio de nombres de red para unirse.
  • private: Crea un nuevo espacio de nombres para el contenedor. Esto utiliza el modo bridge para contenedores con privilegios y slirp4netns para los sin privilegios.
  • slirp4netns[:OPCIONES,...]: usa slirp4netns(1) para crear una pila de red de usuario. Es posible especificar estas opciones adicionales, que también se pueden establecer con network_cmd_options en containers.conf:
  • allow_host_loopback=true|false: Permite que slirp4netns acceda a la IP de loopback del host (el valor predeterminado es 10.0.2.2 o la segunda IP de la subred CIDR de slirp4netns cuando se cambia, ver la opción cidr a continuación). El valor predeterminado es false.
  • mtu=MTU: Especifica la MTU a utilizar para esta red. (Predeterminado: 65520).
  • cidr=CIDR: Especifica el rango de IP a utilizar para esta red. (Predeterminado: 10.0.2.0/24).
  • enable_ipv6=true|false: Habilita IPv6. El valor predeterminado es true. (Requerido para outbound_addr6).
  • outbound_addr=INTERFAZ: Especifica la interfaz de salida a la que se enlaza slirp (solo tráfico ipv4).
  • outbound_addr=IPv4: Especifica la dirección IPv4 de salida a la que se enlaza slirp.
  • outbound_addr6=INTERFAZ: Especifica la interfaz de salida a la que se enlaza slirp (solo tráfico ipv6).
  • outbound_addr6=IPv6: Especifica la dirección IPv6 de salida a la que se enlaza slirp.
  • port_handler=rootlesskit: Utiliza rootlesskit para el reenvío de puertos. Predeterminado.
    Nota: Rootlesskit cambia la dirección IP de origen de los paquetes entrantes a una dirección IP en el espacio de nombres de red del contenedor, generalmente 10.0.2.100. Si la aplicación requiere la dirección IP de origen real, por ejemplo, para los registros del servidor web, usa el manejador de puertos slirp4netns. El manejador de puertos rootlesskit también se usa para contenedores sin privilegios cuando se conectan a redes definidas por el usuario.
  • port_handler=slirp4netns: Utiliza el reenvío de puertos slirp4netns, es más lento que rootlesskit pero preserva la dirección IP de origen correcta. Este manejador de puertos no se puede usar para redes definidas por el usuario.
•
pasta[:OPCIONES,...]: usa pasta(1) para crear una pila de red en modo de usuario.
Este es el valor predeterminado para contenedores sin privilegios y solo es compatible en modo sin privilegios.
Por defecto, las direcciones y rutas IPv4 e IPv6, así como el nombre de la interfaz del pod, se copian del host. El reenvío de puertos preserva la dirección IP de origen original. Las opciones descritas en pasta(1) se pueden especificar como argumentos separados por comas.
En términos de opciones de pasta(1), se proporciona --config-net por defecto, para configurar la red cuando se inicia el contenedor, y también se asume --no-map-gw por defecto, para evitar el acceso directo desde el contenedor al host usando la dirección de puerta de enlace. Esto último se puede anular pasando --map-gw en las opciones específicas de pasta (a pesar de no ser una opción real de pasta(1)).
Para una mejor integración con el manejo de DNS, se pasa --dns-forward 169.254.1.1, y esta dirección se agrega a resolv.conf(5) como el primer resolvedor. Es posible pasar --dns-forward explícitamente en caso de que se deba usar una dirección IP diferente. Para que la entrada host.containers.internal de /etc/hosts funcione y permita conexiones al host, se pasa --map-guest-addr 169.254.1.2. Nuevamente, se puede establecer explícitamente para elegir una dirección IP diferente.
Además, se pasan -t none y -u none si, respectivamente, no se configura ningún reenvío de puertos TCP o UDP del host al contenedor (a través de --publish de Podman o pasando las opciones -t/-u de pasta directamente), para deshabilitar el reenvío automático de puertos basado en puertos enlazados. De manera similar, se proporcionan -T none y -U none para deshabilitar la misma funcionalidad del contenedor al host.
Todas las opciones también se pueden establecer en containers.conf(5); consulta la clave pasta_options en la sección de red de ese archivo.
Algunos ejemplos:
  • pasta:--map-gw: Permite que el contenedor acceda directamente al host usando la dirección de la puerta de enlace.
  • pasta:--mtu,1500: Especifica una MTU de 1500 bytes para la interfaz tap en el contenedor.
  • pasta:--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,-m,1500,--no-ndp,--no-dhcpv6,--no-dhcp, equivalente a las opciones predeterminadas de slirp4netns(1): deshabilita IPv6, asigna 10.0.2.0/24 a la interfaz tap0 en el contenedor, con puerta de enlace 10.0.2.3, habilita el reenviador DNS accesible en 10.0.2.3, establece la MTU en 1500 bytes, deshabilita NDP, DHCPv6 y soporte DHCP.
  • pasta:-I,tap0,--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,--no-ndp,--no-dhcpv6,--no-dhcp, equivalente a las opciones predeterminadas de slirp4netns(1) con anulaciones de Podman: lo mismo que lo anterior, pero deja la MTU en 65520 bytes
  • pasta:-t,auto,-u,auto,-T,auto,-U,auto: habilita el reenvío automático de puertos basado en puertos enlazados observados desde ambos lados del host y del contenedor.
  • pasta:-T,5201: habilita el reenvío del puerto TCP 5201 del contenedor al host, utilizando la interfaz de loopback en lugar de la interfaz tap para mejorar el rendimiento.

Inválido si se usa --dns, --dns-option o --dns-search con --network establecido en none o container:id.

--network-alias=alias

Etiquetado de los montajes de volumen Los sistemas de etiquetado como SELinux requieren que se coloquen etiquetas adecuadas en el contenido del volumen montado en un pod. Sin una etiqueta, el sistema de seguridad puede impedir que los procesos que se ejecutan dentro del pod usen el contenido. De forma predeterminada, Podman no cambia las etiquetas establecidas por el SO. Para cambiar una etiqueta en el contexto del pod, agregue uno de dos sufijos :z o :Z al montaje del volumen. Estos sufijos le indican a Podman que vuelva a etiquetar los objetos de archivo en los volúmenes compartidos. La

opción

z le indica a Podman que dos o más pods comparten el contenido del volumen. Como resultado, Podman etiqueta el contenido con una etiqueta de contenido compartido. Las etiquetas de volumen compartido permiten que todos los contenedores lean/escriban contenido. La opción Z le indica a Podman que etiquete el contenido con una etiqueta privada no compartida. Solo el pod actual puede usar un volumen privado. Nota: todos los contenedores dentro de un pod comparten la misma etiqueta SELinux. Esto significa que todos los contenedores dentro de dicho pod pueden leer/escribir volúmenes compartidos en el contenedor creado con :Z en cualquiera de los contenedores. El reetiquetado recorre el sistema de archivos bajo el volumen y cambia la etiqueta en cada archivo; si el volumen tiene miles de inodos, este proceso tarda mucho tiempo, retrasando el inicio del pod. Si el volumen fue previamente reetiquetado con la opción z , Podman está optimizado para no reetiquetar por segunda vez. En términos de overlay, el directorio de origen es el inferior (lower), y el directorio de almacenamiento del contenedor es el superior (upper). Las modificaciones en el punto de montaje se destruyen cuando el pod termina de ejecutarse, similar a cómo se desmonta un punto de montaje tmpfs. Para usuarios avanzados, la opción overlay también admite un upperdir y workdir personalizados no volátiles para el montaje overlay. Un upperdir y workdir personalizados pueden ser gestionados completamente por los usuarios mismos, y Podman no los elimina al completar el ciclo de vida.

:O,upperdir=/some/upper,workdir=/some/work Las ejecuciones posteriores del contenedor ven el contenido original del directorio de origen, cualquier cambio de ejecuciones anteriores del pod ya no

existe.

Un caso de uso del montaje overlay es compartir la caché de paquetes desde el host dentro del contenedor para permitir acelerar las

Propagación de

montajes

De forma predeterminada, los volúmenes montados por enlace son privados . Eso significa que cualquier montaje hecho dentro del pod no es visible en el host y viceversa. Se puede cambiar este comportamiento especificando una propiedad de propagación del montaje del volumen. Cuando un volumen es compartido , los montajes hechos bajo ese volumen dentro del pod son visibles en el host y viceversa. Hacer que un volumen sea esclavo [1] ⟨#NotaAlPie1⟩ habilita solo la propagación de montajes unidireccional: los montajes hechos en el host bajo ese volumen son visibles dentro del contenedor pero no al

revés.

Para controlar la propiedad de propagación de un volumen se puede usar el indicador de propagación [r ]shared , [r ]slave , [r ]private o el [r ]unbindable . La propiedad de propagación solo se puede especificar para volúmenes montados por enlace y no para volúmenes internos o volúmenes con nombre. Para que la propagación de montajes funcione, el punto de montaje de origen (el punto de montaje donde se monta el directorio de origen) debe tener las propiedades de propagación correctas. Para volúmenes compartidos, el punto de montaje de origen debe ser compartido. Y para volúmenes esclavos, el punto de montaje de origen debe ser compartido o esclavo. [1]

⟨#NotaAlPie1⟩

Para montar recursivamente un volumen y todos sus submontajes en un pod, use la opción rbind . De forma predeterminada se usa la opción bind, y los submontajes del directorio de origen no se montan en el

pod.

Montar el volumen con la opción copy le indica a podman que copie el contenido del directorio de destino subyacente a los volúmenes internos recién creados. La copia solo ocurre en la creación inicial del volumen. El contenido no se copia cuando el volumen se usa posteriormente en diferentes contenedores. La opción copy se ignora en los montajes por enlace y no tiene

efecto.

Montar volúmenes con las opciones nosuid significa que los ejecutables SUID en el volumen no pueden ser usados por aplicaciones para cambiar sus privilegios. De forma predeterminada, los volúmenes se montan con nosuid

.

Montar el volumen con la opción noexec significa que no se pueden ejecutar ejecutables en el volumen dentro del

pod.

Montar el volumen con la opción nodev significa que no se pueden usar dispositivos en el volumen por procesos dentro del pod. De forma predeterminada, los volúmenes se montan con nodevb>.

Si el HOST-DIR es un punto de montaje, entonces las opciones dev, suidy exec son ignoradas por el kernel.

Utilice df HOST-DIR para averiguar el montaje de origen, luego utilice findmnt -o TARGET,PROPAGATION source-mount-dir para averiguar las propiedades de propagación del montaje de origen. Si la utilidad findmnt(1) no está disponible, entonces se puede buscar la entrada de montaje del punto de montaje de origen en /proc/self/mountinfo. Busque los "campos opcionales" y vea si se especifican algunas propiedades de propagación. En ellos, shared:N significa que el montaje es compartido, master:N significa que el montaje es esclavo, y si no hay nada, el montaje es privado. [1] ⟨#Footnote1⟩

Para cambiar las propiedades de propagación de un punto de montaje, utilice el comando mount(8) . Por ejemplo, si se desea hacer un montaje enlazado (bind mount) del directorio de origen /foo, se puede hacer mount --bind /foo /foo y mount --make-private --make-shared /foo. Esto convierte /foo en un punto de montaje compartido. Alternativamente, se pueden cambiar directamente las propiedades de propagación del montaje de origen. Digamos que / es el montaje de origen para /foo, entonces use mount --make-shared / para convertir / en un montaje compartido.

Nota: si el usuario solo tiene derechos de acceso a través de un grupo, el acceso al volumen desde dentro de un pod sin root falla.

Montaje con mapeo de IDs

Si se especifica idmap , se crea un montaje con mapeo de IDs hacia el espacio de nombres de usuario de destino en el contenedor. La opción idmap admite un mapeo personalizado que puede ser diferente al espacio de nombres de usuario utilizado por el contenedor. El mapeo se puede especificar después de la opción idmap como: idmap=uids=0-1-10#10-11-10;gids=0-100-10. Para cada triplete, el primer valor es el inicio de los IDs del sistema de archivos subyacente que se mapean al segundo valor en el host. La longitud de este mapeo se indica en el tercer valor. Los rangos múltiples se separan con #.

--volumes-from=CONTAINER[:OPTIONS]

Monta volúmenes desde los contenedor(es) especificado(s). Se usa para compartir volúmenes entre contenedores y pods. Las opciones son una lista separada por comas con los siguientes elementos disponibles:

  • rw|ro
  • z

Monta volúmenes ya montados desde un contenedor de origen en otro pod. CONTAINER puede ser un nombre o un ID. Para compartir un volumen, use la opción --volumes-from al ejecutar el contenedor de destino. Los volúmenes se pueden compartir incluso si el contenedor de origen no se está ejecutando.

De forma predeterminada, Podman monta los volúmenes en el mismo modo (lectura-escritura o solo lectura) en el que están montados en el contenedor de origen. Esto se puede cambiar añadiendo una ro o rw opción.

Los sistemas de etiquetado como SELinux requieren que se coloquen etiquetas adecuadas en el contenido del volumen montado en un pod. Sin una etiqueta, el sistema de seguridad podría impedir que los procesos que se ejecutan dentro del contenedor utilicen el contenido. De forma predeterminada, Podman no cambia las etiquetas establecidas por el SO.

Para cambiar una etiqueta en el contexto del pod, añada z al montaje del volumen. Este sufijo le indica a Podman que vuelva a etiquetar los objetos de archivo en los volúmenes compartidos. La opción z le indica a Podman que dos entidades comparten el contenido del volumen. Como resultado, Podman etiqueta el contenido con una etiqueta de contenido compartido. Las etiquetas de volumen compartido permiten que todos los contenedores lean/escriban el contenido.

Si la ubicación del volumen desde el contenedor de origen se superpone con datos que residen en un pod de destino, entonces el volumen oculta esos datos en el destino.

EJEMPLOS

Crea un pod con nombre.

$ podman pod create --name test

Crea un pod con nombre.

$ podman pod create mypod

Crea un pod sin un contenedor infra.

$ podman pod create --infra=false

Crea un pod con nombre con un comando para el contenedor infra.

$ podman pod create --infra-command /top toppod

Crea un pod con puertos publicados en el host.

$ podman pod create --publish 8443:443

Crea un pod con la configuración de red especificada.

$ podman pod create --network slirp4netns:outbound_addr=127.0.0.1,allow_host_loopback=true

Crea un pod con la red especificada.

$ podman pod create --network pasta

Crea un pod en dos redes.

$ podman pod create --network net1:ip=10.89.1.5 --network net2:ip=10.89.10.10

Crea un pod con límites de CPU y memoria compartidos para todos los contenedores.

$ podman pod create --cpus=2 --memory=512m mypod

Crea un pod con montajes de volumen compartidos accesibles para todos los contenedores.

$ podman pod create --volume /host/path:/container/path:Z mypod

Crea un pod con límites de recursos y montajes de volumen compartidos para todos los contenedores.

$ podman pod create --volume /data:/data:Z --volume /config:/etc/config:ro --cpus=1.5 --memory=1g --cpu-shares=512 mypod

Crea un pod con acceso a dispositivos y límites de recursos compartidos.

$ podman pod create --device /dev/sda:/dev/sda:rw --cpus=4 --memory=2g --blkio-weight=500 mypod

Crea un pod con límites de conjunto de CPU compartidos y volúmenes de otro contenedor que se compartirán con todos los contenedores del pod.

$ podman pod create --cpuset-cpus=0,2 --volumes-from=source-container --memory=1g mypod

Crea un pod con recursos compartidos y añade contenedores a él.

$ podman pod create --cpus=2 --memory=1g --volume /data:/data:Z mypod
$ podman create --pod mypod nginx
$ podman create --pod mypod redis
