DESCRIPCIÓ

N

podman farm build Construye una imagen en todos los nodos de una granja y los agrupa en una lista de manifiestos. Ejecuta el comando podman build en los nodos de la granja con el Containerfile proporcionado. Una vez que las imágenes se han construido en todos los nodos de la granja, se empujarán al registro proporcionado mediante la opción --tag. Una vez que todas las imágenes se han empujado, se creará localmente una lista de manifiestos y también se empujará al

registro.

La lista de manifiestos contendrá una imagen por cada tipo de arquitectura nativa presente en la

granja.

La función principal de este comando es crear compilaciones multiarquitectura que serán más rápidas que hacerlo mediante emulación usando podman build --arch -

-platform.

Si no se especifica una granja, la compilación se enviará a todos los nodos que podman system connect

ion conoce.

Nota: Dado que las imágenes construidas se empujan directamente a un registro, el usuario debe proporcionar un nombre de imagen completo usando la opción --tag en el formato registro/repositorio/nombreImagen[:etique

ta
]`.

--add-host=nombreDeHost[;nombreDeHost[;...]]:i

p

Añade un mapeo personalizado de host a IP al archivo /etc/hosts del co

ntenedor.

La opción acepta uno o varios nombres de host separados por punto y coma que se mapearán a una única dirección IPv4 o IPv6, separadas por dos puntos. También se puede usar para sobrescribir las direcciones IP de los nombres de host que Podman añade por defecto a /etc/hosts (véanse también las opciones --name y --hostname). Esta opción se puede especificar varias veces para añadir mapeos adicionales a /etc/hosts. Entr en conflicto con la opción --no-hosts y con no_hosts=true en containers.

conf.

En lugar de una dirección IP, se puede proporcionar el indicador especial host-gateway. Esto se resuelve a una dirección IP que el contenedor puede usar para conectarse al host. La dirección IP elegida depende de su configuración de red, por lo que no hay garantía de que Podman pueda determinar la dirección host-gateway automáticamente, lo que haría que Podman falle con un mensaje de error. Puede sobrescribir esta dirección IP usando la opción host_containers_internal_ip en containers.

conf.

La dirección host-gateway también es usada por Podman para añadir automáticamente los nombres de host host.containers.internal y host.docker.internal a /etc/hosts. Puede evitar esto proporcionando la opción --no-hosts, o configurando host_containers_internal_ip="none" en containers.conf. Si no se configuró manualmente una dirección host-gateway y Podman no puede determinar la dirección IP automáticamente, Podman omitirá silenciosamente la adición de estos nombres de host internos a /etc/hosts. Si Podman se está ejecutando en una máquina virtual usando podman machine (esto incluye hosts Mac y Windows), Podman omitirá silenciosamente la adición de los nombres de host internos a /etc/hosts, a menos que se haya configurado manualmente una dirección IP; los nombres de host internos se resuelven mediante el resolutor DNS

gvproxy.

Podman usará por defecto el archivo /etc/hosts del host como base, es decir, cualquier nombre de host presente en este archivo también estará presente en el archivo /etc/hosts del contenedor. Se puede configurar un archivo base diferente usando la configuración base_hosts_file en containe

rs.c
onf.

--cpu-shares, -c=accione

s

Acciones de CPU (peso relativo)

.

De forma predeterminada, todos los contenedores obtienen la misma proporción de ciclos de CPU. Esta proporción se puede modificar cambiando la ponderación de acciones de CPU del contenedor en relación con el peso combinado de todos los contenedores en ejecución. El peso predeterminado es 1024

.

La proporción solo se aplica cuando se están ejecutando procesos intensivos de CPU. Cuando las tareas en un contenedor están inactivas, otros contenedores pueden usar el tiempo de CPU restante. La cantidad real de tiempo de CPU varía dependiendo del número de contenedores en ejecución en el

sistema.

Por ejemplo, considere tres contenedores, uno tiene una cpu-share de 1024 y los otros dos tienen una configuración de cpu-share de 512. Cuando los procesos en los tres contenedores intentan usar el 100% de la CPU, el primer contenedor recibe el 50% del tiempo total de CPU. Si se añade un cuarto contenedor con una cpu-share de 1024, el primer contenedor solo obtiene el 33% de la CPU. Los contenedores restantes reciben el 16.5%, 16.5% y 33% de la

CPU.

individual.

--label=label[=value]

Añade una etiqueta (por ejemplo, etiqueta=valor) a los metadatos de la imagen.

Se puede usar varias veces.

Los usuarios pueden establecer una etiqueta especial LABEL io.containers.capabilities=CAP1,CAP2,CAP3 en un Containerfile que especifica la lista de capacidades de Linux necesarias para que el contenedor se ejecute correctamente. Esta etiqueta especificada en una imagen de contenedor indica a Podman que ejecute el contenedor solo con estas capacidades. Podman inicia el contenedor solo con las capacidades especificadas, siempre que esta lista de capacidades sea un subconjunto de la lista predeterminada.

Si las capacidades especificadas no están en el conjunto predeterminado, Podman imprime un mensaje de error y ejecuta el contenedor con las capacidades predeterminadas.

--memory, -m=número[unidad]

Límite de memoria. Una unidad puede ser b (bytes), k (kibibytes), m (mebibytes) o g (gibibytes).

Permite limitar la memoria disponible para un contenedor. Si el host admite memoria swap, el ajuste de memoria -m puede ser mayor que la RAM física. Si se especifica un límite de 0 (sin usar -m), la memoria del contenedor no tiene límite. El límite real puede redondearse al alza hasta un múltiplo del tamaño de página del sistema operativo (el valor es muy grande, es decir, millones de billones).

Esta opción no se admite en sistemas sin root en cgroups V1.

--memory-swap=número[unidad]

Un valor límite igual a memoria más swap. Una unidad puede ser b (bytes), k (kibibytes), m (mebibytes) o g (gibibytes).

Debe usarse con la bandera -m (--memory). El valor del argumento debe ser mayor que el de
-m (--memory) Por defecto, se establece en el doble del valor de --memory.

Establece número en -1 para habilitar el swap ilimitado.

Esta opción no se admite en sistemas sin root en cgroups V1.

--network=modo, --net

Establece la configuración de los espacios de nombres de red al manejar las instrucciones RUN.

Los valores válidos de modo son:

  • none: sin red.
  • host: usa la pila de red del host de Podman. Nota: el modo host da al contenedor acceso completo a los servicios del sistema local, como D-bus, y por lo tanto se considera inseguro.
  • ns:ruta: ruta a un espacio de nombres de red para unirse.
  • private: crea un nuevo espacio de nombres para el contenedor (predeterminado)
  • <nombre de red|ID>: Únete a la red con el nombre o ID dado, por ejemplo, usa --network mynet para unirte a la red con el nombre mynet. Solo se admite para usuarios con permisos de root.
  • slirp4netns[:OPCIONES,...]: usa slirp4netns(1) para crear una pila de red de usuario. Es posible especificar estas opciones adicionales, también se pueden configurar con network_cmd_options en containers.conf:
  • allow_host_loopback=true|false: Permite que slirp4netns acceda a la IP de loopback del host (el valor predeterminado es 10.0.2.2 o la segunda IP del subred CIDR de slirp4netns cuando se cambia, ver la opción cidr abajo). El valor predeterminado es false.
  • mtu=MTU: Especifica la MTU a utilizar para esta red. (El valor predeterminado es 65520).
  • cidr=CIDR: Especifica el rango IP a utilizar para esta red. (El valor predeterminado es 10.0.2.0/24).
  • enable_ipv6=true|false: Habilita IPv6. El valor predeterminado es true. (Requerido para outbound_addr6).
  • outbound_addr=INTERFAZ: Especifica la interfaz de salida a la que se vincula slirp (solo tráfico ipv4).
  • outbound_addr=IPv4: Especifica la dirección ipv4 de salida a la que se vincula slirp.
  • outbound_addr6=INTERFAZ: Especifica la interfaz de salida a la que se vincula slirp (solo tráfico ipv6).
  • outbound_addr6=IPv6: Especifica la dirección ipv6 de salida a la que se vincula slirp.
•
pasta[:OPCIONES,...]: usa pasta(1) para crear una pila de red en modo usuario.
Este es el valor predeterminado para contenedores sin root y solo se admite en modo sin root.
Por defecto, las direcciones y rutas IPv4 e IPv6, así como el nombre de la interfaz del pod, se copian del host. Si el reenvío de puertos no está configurado, los puertos se reenvían dinámicamente a medida que los servicios se vinculan en cualquiera de los lados (espacio de nombres init o espacio de nombres del contenedor). El reenvío de puertos preserva la dirección IP de origen original. Las opciones descritas en pasta(1) se pueden especificar como argumentos separados por comas.
En términos de opciones de pasta(1), se pasa --config-net por defecto, para configurar la red cuando se inicia el contenedor, y también se asume --no-map-gw por defecto, para evitar el acceso directo del contenedor al host usando la dirección de la puerta de enlace. Este último puede ser anulado pasando --map-gw en las opciones específicas de pasta (a pesar de no ser una opción real de pasta(1)).
Además, se pasan -t none y -u none para deshabilitar el reenvío automático de puertos basado en los puertos vinculados. De manera similar, se pasan -T none y -U none para deshabilitar la misma funcionalidad del contenedor al host.
Algunos ejemplos:
  • pasta:--map-gw: Permite que el contenedor acceda directamente al host utilizando la dirección de la puerta de enlace.
  • pasta:--mtu,1500: Especifica una MTU de 1500 bytes para la interfaz tap en el contenedor.
  • pasta:--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,-m,1500,--no-ndp,--no-dhcpv6,--no-dhcp, equivalente a las opciones predeterminadas de slirp4netns(1): deshabilita IPv6, asigna 10.0.2.0/24 a la interfaz tap0 en el contenedor, con puerta de enlace 10.0.2.3, habilita el reenviador DNS accesible en 10.0.2.3, establece la MTU en 1500 bytes, deshabilita NDP, DHCPv6 y DHCP.
  • pasta:-I,tap0,--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,--no-ndp,--no-dhcpv6,--no-dhcp, equivalente a las opciones predeterminadas de slirp4netns(1) con anulaciones de Podman: igual que el anterior, pero deja la MTU en 65520 bytes
  • pasta:-t,auto,-u,auto,-T,auto,-U,auto: habilita el reenvío automático de puertos basado en los puertos vinculados observados desde ambos lados (host y contenedor)
  • pasta:-T,5201: habilita el reenvío del puerto TCP 5201 del contenedor al host, utilizando la interfaz de loopback en lugar de la interfaz tap para mejorar el rendimiento

--no-cache

No utilices imágenes en caché existentes para la compilación del contenedor. Compila desde el principio con un nuevo conjunto de capas en caché.

--no-hostname

No crees el archivo /etc/hostname en los contenedores.

Por defecto, Podman gestiona el archivo /etc/hostname, añadiendo el propio nombre de host del contenedor. Cuando se establece la opción --no-hostname, el archivo /etc/hostname de la imagen se conservará sin modificar si existe.

--no-hosts

No modifiques el archivo /etc/hosts en el contenedor.

Por defecto, Podman asume el control del archivo /etc/hosts del contenedor y añade entradas para el nombre del contenedor (ver opción --name) y el nombre de host (ver opción --hostname), los hosts internos host.containers.internal y host.docker.internal, así como cualquier nombre de host añadido mediante la opción --add-host. Consulta la opción --add-host para obtener más detalles. Al pasar --no-hosts se deshabilita esto, de modo que el archivo /etc/hosts de la imagen se mantiene sin modificar. Lo mismo se puede lograr globalmente estableciendo no_hosts=true en containers.conf.

Esta opción entra en conflicto con --add-host.

--omit-history

Omite la información del historial de compilación en la imagen compilada. (predeterminado false).

Esta opción es útil en los casos en que los usuarios finales desean explícitamente establecer --omit-history para omitir el campo opcional History de las imágenes compiladas o cuando se trabaja con imágenes compiladas utilizando herramientas de compilación que no incluyen información de History en sus imágenes.

--os-feature=característica

Establece el nombre de una característica del sistema operativo requerida para la imagen que se está compilando. Por defecto, si la imagen no se basa en scratch, se mantiene la lista de características del SO requeridas de la imagen base, si la imagen base especificó alguna. Esta opción suele ser significativa solo cuando el SO de la imagen es Windows.

Si característica tiene un guion final -, entonces la característica se elimina del conjunto de características requeridas que figuran en la imagen.

--os-version=versión

Establece la versión exacta del sistema operativo requerida para la imagen que se está compilando. Por defecto, si la imagen no se basa en scratch, se mantiene la versión del SO requerida de la imagen base, si la imagen base especificó una. Esta opción suele ser significativa solo cuando el SO de la imagen es Windows, y normalmente se establece en las imágenes base de Windows, por lo que el uso de esta opción suele ser innecesario.

--pull=política

Política de extracción de imágenes. El valor predeterminado es missing.

  • always: Extrae siempre la imagen y genera un error si la extracción falla.
  • missing: Solo extrae la imagen cuando no existe en el almacenamiento local de contenedores. Genera un error si no se encuentra ninguna imagen y la extracción falla.
  • never: Nunca extrae la imagen, sino que utiliza la del almacenamiento local de contenedores. Genera un error cuando no se encuentra ninguna imagen.
  • newer: Extrae si la imagen en el registro es más reciente que la del almacenamiento local de contenedores. Una imagen se considera más reciente cuando sus digestos son diferentes. Comparar las marcas de tiempo es propenso a errores. Los errores de extracción se suprimen si se encontró una imagen local.

--quiet, -q

Suprime los mensajes de salida que indican qué instrucción se está procesando, y el progreso al extraer imágenes de un registro, y al escribir la imagen de salida.

--retry=intentos

Número de veces que se reintentará extraer o enviar imágenes entre el registro y el almacenamiento local en caso de error. El valor predeterminado es 3.

--retry-delay=duración

Duración del retraso entre intentos de reintento al extraer o enviar imágenes entre el registro y el almacenamiento local en caso de error. El valor predeterminado es comenzar en dos segundos y luego retroceder exponencialmente. El retraso se utiliza cuando se establece este valor y no se produce ninguna retroceso exponencial.

--sbom-image-output=ruta

Al generar SBOM, almacene el SBOM generado en la ruta especificada en la imagen de salida. No hay valor predeterminado.

--sbom-image-purl-output=ruta

Al generar SBOM, escanee en busca de información PURL (package URL ⟨https://github.com/package-url/purl-spec/blob/master/PURL-SPECIFICATION.rst⟩), y guarde una lista de PURL encontradas en la ruta especificada en la imagen de salida. No hay valor predeterminado.

--sbom-merge-strategy=método

Si se está utilizando más de un valor de --sbom-scanner-command, utilice el método especificado para fusionar la salida de los comandos posteriores con la salida de los comandos anteriores. Los valores reconocidos incluyen:

  • cat
    Concatena los archivos.
  • merge-cyclonedx-by-component-name-and-version
    Fusiona los campos "component" de los documentos JSON, ignorando los valores de
    los documentos cuando la combinación de sus valores "name" y "version" ya está
    presente. Los documentos se procesan en el orden en que se generan, que es el orden en que se especificaron los comandos que los generan.
  • merge-spdx-by-package-name-and-versioninfo
    Fusiona los campos "package" de los documentos JSON, ignorando los valores de
    los documentos cuando la combinación de sus valores "name" y "versionInfo" ya está
    presente. Los documentos se procesan en el orden en que se generan, que es el orden en que se especificaron los comandos que los generan.

--sbom-output=archivo

Al generar SBOM, almacene el SBOM generado en el archivo nombrado en el sistema de archivos local. No hay valor predeterminado.

--sbom-purl-output=archivo

Al generar SBOM, escanee en busca de información PURL (package URL ⟨https://github.com/package-url/purl-spec/blob/master/PURL-SPECIFICATION.rst⟩), y guarde una lista de PURL encontradas en el archivo nombrado en el sistema de archivos local. No hay valor predeterminado.

--sbom-scanner-command=imagen

Genera SBOM ejecutando el comando especificado desde la imagen escáner. Si se especifican varios comandos, se ejecutan en el orden en que se especifican. Se realizan las siguientes sustituciones de texto:
- {ROOTFS}
La raíz del sistema de archivos de la imagen generada, montada bind.
- {CONTEXT}
El contexto de compilación y los contextos de compilación adicionales, montados bind.
- {OUTPUT}
El nombre de un archivo de salida temporal, para ser leído y fusionado con otros o copiado a otro lugar.

--sbom-scanner-image=imagen

Genera SBOM utilizando la imagen escáner especificada.

--secret=id=id[,src=envOarchivo][,env=ENV][,type=archivo | env]

Pasa información secreta para ser utilizada en el Containerfile para construir imágenes de forma segura, de manera que no termine almacenada en la imagen final ni se vea en otras etapas. El valor del secreto se leerá de una variable de entorno o archivo nombrado por la opción "id", o nombrado por la opción "src" si se especifica, o de una variable de entorno especificada por la opción "env". Ver EJEMPLOS ⟨#examples⟩. El secreto se montará en el contenedor en /run/secrets/id por defecto.

Para usar el secreto más tarde, use la bandera --mount en una instrucción RUN dentro de un Containerfile:

RUN --mount=type=secret,id=misecreto cat /run/secrets/misecreto

La ubicación del secreto en el contenedor se puede anular utilizando la opción "target", "dst" o "destination" de la bandera RUN --mount.

RUN --mount=type=secret,id=misecreto,target=/run/secrets/miotrosecreto cat /run/secrets/miotrosecreto

Nota: cambiar el contenido de los archivos secretos no activará una reconstrucción de las capas que utilizan dichos secretos.

Tamaño de /dev/shm. Una unidad puede ser b (bytes), k (kibibytes), m (mebibytes) o g (gibibytes). Si se omite la unidad, el sistema utiliza bytes. Si se omite el tamaño, el valor predeterminado es

--memory=bytes

Limit the amount of memory available to the container. Accepts integer values with an optional suffix of b, k, m, g, t, p, or e (binary prefixes) or B, K, M, G, T, P, or E (IEC prefixes). If the suffix is b, k, m, g, t, p, or e, the value is multiplied by 1024. If the suffix is B, K, M, G, T, P, or E, the value is multiplied by 1000.

When size is 0, there is no limit on the amount of memory used for IPC by the container. This option conflicts with --ipc=host.

--skip-unused-stages

Omite las etapas en compilaciones de múltiples etapas que no afectan a la etapa de destino. (Predeterminado: true).

--source-date-epoch=segundos

Establece la marca de tiempo de "creación" para la imagen compilada en este número de segundos desde la época (tiempo Unix 0, es decir, 00:00:00 UTC del 1 de enero de 1970) (el valor predeterminado es usar el valor establecido en la variable de entorno SOURCE_DATE_EPOCH, o la hora actual si no está establecida).

La marca de tiempo de "creación" se escribe en la configuración y el manifiesto de la imagen cuando la imagen se confirma, por lo que ejecutar la misma compilación dos veces consecutivas normalmente producirá imágenes con hashes sha256 diferentes, incluso si no se realizaron otros cambios en el Containerfile y en el contexto de compilación.

Cuando se establece esta bandera, un argumento de compilación SOURCE_DATE_EPOCH proporcionará su valor para una etapa en la que se declare.

Cuando se establece esta bandera, la marca de tiempo de "creación" de la configuración de la imagen siempre se establece en la hora especificada, lo que debería permitir compilar imágenes idénticas en diferentes momentos utilizando el mismo conjunto de entradas.

Cuando se establece esta bandera, la salida escrita según lo especificado en la bandera --output llevará exactamente la marca de tiempo especificada.

Entra en conflicto con la bandera similar --timestamp, que también establece su tiempo especificado en el contenido de las nuevas capas.

--squash

Comprime todas las capas nuevas de la imagen en una única capa nueva; no se comprimen las capas preexistentes.

--squash-all

Comprime todas las capas de la nueva imagen (incluidas las heredadas de una imagen base) en una única capa nueva.

--ssh=default | id=socket>

Socket del agente SSH o claves para exponer a la compilación. La ruta del socket se puede dejar vacía para usar el valor de default=$SSH_AUTH_SOCK

Para usar más tarde el agente ssh, utilice la opción --mount en una instrucción RUN dentro de un Containerfile:

--tag, -t=nombreImagen

Especifica el nombre que se asigna a la imagen resultante si el proceso de compilación se completa con éxito. Si nombreImagen no incluye un nombre de registro, se antepone el nombre de registro localhost al nombre de la imagen.

--target=nombreEtapa

Establece la etapa de compilación de destino que se va a compilar. Al compilar un Containerfile con múltiples etapas de compilación, --target se puede usar para especificar una etapa de compilación intermedia por nombre como etapa final para la imagen resultante. Los comandos posteriores a la etapa de destino se omiten.

--timestamp=segundos

Establece la marca de tiempo de creación en segundos desde la época para permitir compilaciones deterministas (predeterminado a la hora actual). Por defecto, la marca de tiempo de creación se cambia y se escribe en el manifiesto de la imagen con cada confirmación, lo que provoca que el hash sha256 de la imagen sea diferente incluso si las fuentes son exactamente las mismas de lo contrario. Cuando se establece --timestamp, la marca de tiempo de creación siempre se establece en la hora especificada y, por lo tanto, no se cambia, lo que permite que el hash sha256 de la imagen permanezca igual. Todos los archivos que se confirman en las capas de la imagen se crean con la marca de tiempo.

Si la única instrucción en un Containerfile es FROM, esta bandera no tiene ningún efecto.

--tls-verify

Requiere HTTPS y verifica certificados al contactar con registros (predeterminado: true). Si se establece explícitamente en true, se utiliza la verificación TLS. Si se establece en false, no se utiliza la verificación TLS. Si no se especifica, se utiliza la verificación TLS a menos que el registro de destino aparezca como un registro inseguro en containers-registries.conf(5)

--ulimit=tipo=límite-suave[:límite-duro]

Especifica los límites de recursos que se aplicarán a los procesos iniciados al procesar instrucciones RUN. Esta opción se puede especificar varias veces. Los tipos de recursos reconocidos incluyen:
"core": tamaño máximo del volcado del núcleo (ulimit -c)
"cpu": tiempo máximo de CPU (ulimit -t)
"data": tamaño máximo del segmento de datos de un proceso (ulimit -d)
"fsize": tamaño máximo de los archivos nuevos (ulimit -f)
"locks": número máximo de bloqueos de archivos (ulimit -x)
"memlock": cantidad máxima de memoria bloqueada (ulimit -l)
"msgqueue": cantidad máxima de datos en colas de mensajes (ulimit -q)
"nice": ajuste de cortesía (nice -n, ulimit -e)
"nofile": número máximo de archivos abiertos (ulimit -n)
"nproc": número máximo de procesos (ulimit -u)
"rss": tamaño máximo de un proceso (ulimit -m)
"rtprio": prioridad máxima de planificación en tiempo real (ulimit -r)
"rttime": cantidad máxima de ejecución en tiempo real entre llamadas al sistema de bloqueo
"sigpending": número máximo de señales pendientes (ulimit -i)
"stack": tamaño máximo de la pila (ulimit -s)

--userns-gid-map=mapeo

Especifica directamente un mapeo de GID que se utilizará para establecer la propiedad, a nivel del sistema de archivos, sobre el contenido del contenedor de trabajo. Los comandos que se ejecutan al manejar instrucciones RUN se ejecutan por defecto en sus propios espacios de nombres de usuario, configurados mediante los mapeos de UID y GID.

Las entradas en este mapeo toman la forma de uno o más tríos de un GID de inicio dentro del contenedor, un GID correspondiente a nivel de host, y el número de IDs consecutivos que representa la entrada del mapeo.

Esta opción anula la configuración remap-gids en la sección options de /etc/containers/storage.conf.

Si esta opción no se especifica, pero se proporciona una configuración global --userns-gid-map, se utilizan la configuración de la opción global.

Si no se especifican --userns-uid-map-user, --userns-gid-map-group, o --userns-gid-map, pero se especifica --userns-uid-map, el mapeo GID se establece para usar los mismos valores numéricos que el mapeo UID.

--userns-gid-map-group=grupo

Especifica que un mapeo de GID que se utilizará para establecer la propiedad, a nivel del sistema de archivos, sobre el contenido del contenedor de trabajo, se puede encontrar en las entradas del archivo /etc/subgid que corresponden al grupo especificado. Los comandos que se ejecutan al manejar instrucciones RUN se ejecutan por defecto en sus propios espacios de nombres de usuario, configurados mediante los mapeos de UID y GID. Si se especifica --userns-uid-map-user, pero no se especifica --userns-gid-map-group, podman asume que el nombre de usuario especificado también es un nombre de grupo adecuado para usar como configuración predeterminada para esta opción.

NOTA: Cuando un usuario sin privilegios especifica esta opción, los mapeos especificados son relativos al espacio de nombres de usuario sin privilegios en el contenedor, en lugar de ser relativos al host como ocurre cuando se ejecuta con privilegios.
