DESCRIPCIÓ

N

Ejecuta un proceso en un nuevo contenedor. docker run inicia un proceso con su propio sistema de archivos, su propia red y su propio árbol de procesos aislado. La IMAGE que inicia el proceso puede definir valores predeterminados relacionados con el proceso que se ejecutará en el contenedor, la red que se expondrá, y más, pero docker run otorga el control final al operador o administrador que inicia el contenedor desde la imagen. Por esa razón docker run tiene más opciones que cualquier otro comando de

Docker.

Si la IMAGE no está ya cargada, entonces docker run descargará la IMAGE y todas las dependencias de la imagen desde el repositorio de la misma manera que al ejecutar docker pull IMAGE, antes de iniciar el con

tenedor a par
tir de esa imagen.

Se conecta a STDIN, STDOUT o

STDERR.

En modo primer plano (el valor predeterminado cuando -d no se especifica), docker run puede iniciar el proceso en el contenedor y conectar la consola a la entrada estándar, salida estándar y error estándar del proceso. -c, --cpu-shares=0
Cuotas de CPU (peso

relativo)

Por defecto, todos los contenedores obtienen la misma proporción de ciclos de CPU. Esta proporción se puede modificar cambiando la ponderación de cuotas de CPU del contenedor en relación con la ponderación de todos los demás contenedores en

ejecución.

Para modificar la proporción del valor predeterminado de 1024, use la opción -c o --cpu-shares para establecer la ponderación en 2 o

superior.

La proporción solo se aplicará cuando se ejecuten procesos intensivos en CPU. Cuando las tareas en un contenedor están inactivas, otros contenedores pueden usar el tiempo de CPU restante. La cantidad real de tiempo de CPU variará dependiendo del número de contenedores en ejecución en el

sistema.

Por ejemplo, considere tres contenedores, uno tiene una cuota de CPU de 1024 y los otros dos tienen una configuración de cuota de CPU de 512. Cuando los procesos en los tres contenedores intentan usar el 100% de la CPU, el primer contenedor recibiría el 50% del tiempo total de CPU. Si añade un cuarto contenedor con una cuota de CPU de 1024, el primer contenedor solo obtiene el 33% de la CPU. Los contenedores restantes reciben el 16.5%, 16.5% y 33% de la

CPU.

En un sistema multinúcleo, las cuotas de tiempo de CPU se distribuyen sobre todos los núcleos de CPU. Incluso si un contenedor está limitado a menos del 100% del tiempo de CPU, puede usar el 100% de cada núcleo de CPU

individual.

Por ejemplo, considere un sistema con más de tres núcleos. Si inicia un contenedor {C0} con -c=512 ejecutando un proceso, y otro contenedor {C1} con -c=1024 ejecutando dos procesos, esto puede resultar en la siguiente división de cuotas de

CPU: 
PID    contenedor	CPU	Cuota de CPU
100    {C0}		0	100% de CPU0
101    {C1}		1	100% de CPU1
102    {C1}		2	100% de
CPU2

Limita el uso de la CPU en tiempo real de los contenedores. Esta opción le indica al kernel limitar la cantidad de tiempo en un periodo de CPU dado que las tareas en tiempo real pueden consumir. Ej:

-m, --memory=número[*S]
Límite de memoria; S es un sufijo opcional que puede ser b, k, m, o g

.

Le permite restringir la memoria disponible para un contenedor. Si el host soporta memoria swap, entonces la configuración de memoria -m puede ser mayor que la RAM física. Si se especifica un límite de 0 (no usando -m), la memoria del contenedor no está limitada. El límite real puede ser redondeado hacia arriba a un múltiplo del tamaño de página del sistema operativo (el valorould be very large, that's millions of trillions).

--memory-reservation=número[*S]
Límite blando de memoria; S es un sufijo opcional que puede ser b, k, m o g.

Después de establecer la reserva de memoria, cuando el sistema detecta contención de memoria o poca memoria, los contenedores se ven obligados a restringir su consumo a su reserva. Por lo tanto, siempre debes establecer el valor por debajo de --memory, de lo contrario, el límite duro tendrá prioridad. Por defecto, la reserva de memoria será la misma que el límite de memoria.

--memory-swap=número[S]
Límite combinado de memoria más swap; S es un sufijo opcional que puede ser b, k, m o g.

Esta opción solo se puede usar junto con --memory. El argumento siempre debe ser mayor que el de --memory. El valor por defecto es el doble del valor de --memory. Establécelo a -1 para habilitar swap ilimitado.

--mount type=TIPO,OPCIÓN-ESPECÍFICA-DEL-TIPO[,...]
Adjunta un montaje de sistema de archivos al contenedor

Los TIPOS de montaje compatibles actualmente son bind, volume y tmpfs.

ej.

type=bind,source=/ruta/en/host,destination=/ruta/en/contenedor

type=volume,source=mi-volumen,destination=/ruta/en/contenedor,volume-label="color=red",volume-label="shape=round"

type=tmpfs,tmpfs-size=512M,destination=/ruta/en/contenedor

Opciones Comunes:

  • src, source: especificación de origen del montaje para bind y volume. Obligatorio para bind.
  • dst, destination, target: especificación de destino del montaje.
  • ro, readonly: true o false (por defecto).

Nota: establecer readonly para un montaje bind puede no hacer que sus submontajes sean de solo lectura dependiendo de la versión del kernel. Ver también bind-recursive.

Opciones específicas de bind:

  • bind-propagation: shared, slave, private, rshared, rslave o rprivate(por defecto). Ver también mount(2).
  • consistency: consistent(por defecto), cached o delegated. Actualmente, solo efectivo para Docker para Mac.
  • bind-recursive: enabled (por defecto), disabled, writable o readonly:
    Si se establece en enabled, los submontajes se montan recursivamente bind y se intenta hacerlos recursivamente de solo lectura.
    Si se establece en disabled, los submontajes no se montan recursivamente bind.
    Si se establece en writable, los submontajes se montan recursivamente bind pero no se hacen recursivamente de solo lectura.
    Si se establece en readonly, los submontajes se montan recursivamente bind y se fuerzan a ser recursivamente de solo lectura.

Opciones específicas de volume:

  • volume-driver: Nombre del plugin del controlador de volumen.
  • volume-label: Metadatos personalizados.
  • volume-nocopy: true(por defecto) o false. Si se establece en false, el motor copia los archivos y directorios existentes en la ruta de montaje al volumen, permitiendo que el host acceda a ellos.
  • volume-opt: específico para un controlador de volumen dado.

Opciones específicas de tmpfs:

  • tmpfs-size: Tamaño del montaje tmpfs en bytes. Ilimitado por defecto en Linux.
  • tmpfs-mode: Modo de archivo de tmpfs en octal (ej. 700 o 0700). Por defecto es 1777 en Linux.

-P, --publish-all=true|false
Publica todos los puertos expuestos en puertos aleatorios en las interfaces del host. El valor por defecto es false.

Cuando se establece en true, publica todos los puertos expuestos en las interfaces del host. El valor por defecto es false. Si el operador utiliza -P (o -p), Docker hará que el puerto expuesto sea accesible en el host y los puertos estarán disponibles para cualquier cliente que pueda alcanzar el host. Al usar -P, Docker enlazará cualquier puerto expuesto a un puerto aleatorio en el host dentro de un rango de puertos efímeros definido por /proc/sys/net/ipv4/ip_local_port_range. Para encontrar el mapeo entre los puertos del host y los puertos expuestos, usa docker port(1).

Publica el puerto de un contenedor, o un rango de puertos, en el host.

-i

-t fedora bash Múltiples parámetros --volumes-from reunirán múltiples volúmenes de datos de múltiples contenedores. Y es posible montar los volúmenes que provienen del contenedor DATA

Montar Volúmenes Externos

Para montar un directorio del host como un volumen de contenedor, especifique la ruta absoluta del directorio y la ruta absoluta para el directorio del contenedor separadas por dos puntos:

# docker run -v /var/db:/data1 -i -t fedora bash

Cuando use SELinux, tenga en cuenta que el host no tiene conocimiento de la política SELinux del contenedor. Por lo tanto, en el ejemplo anterior, si la política SELinux está en vigor, el directorio /var/db no es escribible para el contenedor. Se mostrará un mensaje de "Permiso denegado" y un mensaje avc: en el syslog del host.

Para solucionar esto, en el momento de escribir esta página de manual, es necesario ejecutar el siguiente comando para que se adjunte la etiqueta de tipo de política SELinux correcta al directorio del host:

# chcon -Rt svirt_sandbox_file_t /var/db

Ahora, la escritura en el volumen /data1 en el contenedor estará permitida y los cambios también se reflejarán en el host en /var/db.

Usar etiquetado de seguridad alternativo

Puede anular el esquema de etiquetado predeterminado para cada contenedor especificando la opción --security-opt . Por ejemplo, puede especificar el nivel MCS/MLS, un requisito para sistemas MLS. Especificar el nivel en el siguiente comando le permite compartir el mismo contenido entre contenedores.

# docker run --security-opt label=level:s0:c100,c200 -i -t fedora bash

Un ejemplo de MLS podría ser:

# docker run --security-opt label=level:TopSecret -i -t rhel7 bash

Para deshabilitar el etiquetado de seguridad para este contenedor en lugar de ejecutarlo con la opción --permissive , use el siguiente comando:

# docker run --security-opt label=disable -i -t fedora bash

Si desea una política de seguridad más estricta para los procesos dentro de un contenedor, puede especificar un tipo alternativo para el contenedor. Podría ejecutar un contenedor al que solo se le permite escuchar en puertos Apache ejecutando el siguiente comando:

# docker run --security-opt label=type:svirt_apache_t -i -t centos bash

Nota:

Tendría que escribir una política que defina un tipo svirt_apache_t .

Establecer peso del dispositivo

Si desea establecer el peso del dispositivo /dev/sda en 200, puede especificar el peso del dispositivo con la opción --blkio-weight-device . Use el siguiente comando:

# docker run -it --blkio-weight-device "/dev/sda:200" ubuntu

Especificar tecnología de aislamiento para el contenedor (--isolation)

Esta opción es útil en situaciones en las que está ejecutando contenedores de Docker en Microsoft Windows. La opción --isolation <valor> establece la tecnología de aislamiento de un contenedor. En Linux, la única opción compatible es default , que utiliza espacios de nombres de Linux. Estos dos comandos son equivalentes en Linux:

$ docker run -d busybox top
$ docker run -d --isolation default busybox top

En Microsoft Windows, puede tomar cualquiera de estos valores:

  • default: Utiliza el valor especificado por --exec-opt del demonio de Docker. Si el demon no especifica una tecnología de aislamiento, Microsoft Windows utiliza process como su valor predeterminado.
  • process: Solo aislamiento de espacios de nombres.
  • hyperv: Aislamiento basado en particiones del hipervisor de Hyper-V.

En la práctica, al ejecutarse en Microsoft Windows sin una opción daemon establecida, estos dos comandos son equivalentes:

$ docker run -d --isolation default busybox top
$ docker run -d --isolation process busybox top

Si ha establecido la opción --exec-opt isolation=hyperv en el demon de Docker, cualquiera de estos comandos también resulta en aislamiento hyperv :

$ docker run -d --isolation default busybox top
$ docker run -d --isolation hyperv busybox top

Establecer parámetros del kernel con espacios de nombres (Sysctls)

La opción --sysctl establece parámetros del kernel con espacios de nombres (sysctls) en el contenedor. Por ejemplo, para habilitar el reenvío de IP en el espacio de nombres de red del contenedor, ejecute este comando:

$ docker run --sysctl net.ipv4.ip_forward=1 someimage

Nota:

No todos los sysctls tienen espacios de nombres. Docker no admite el cambio de sysctls dentro de un contenedor que también modifican el sistema host. A medida que el kernel evoluciona, esperamos ver más sysctls con espacios de nombres.

Consulte la definición de la opción --sysctl anterior para ver la lista actual de sysctls admitidos.
