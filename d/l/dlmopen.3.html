DESCRIPCIÓ

N

dlopen(

)

La función dlopen() carga el archivo de objeto compartido dinámico (biblioteca compartida) nombrado por la cadena terminada en nulo path y devuelve un "manejador" opaco para el objeto cargado. Este manejador se emplea con otras funciones de la API de dlopen, tales como dlsym(3), dladdr(3), dlinfo(3) y dlclose

().

Si path es NULL, entonces el manejador devuelto es para el programa principal. Si path contiene una barra ("/"), entonces se interpreta como un nombre de ruta (relativo o absoluto). De lo contrario, el enlazador dinámico busca el objeto de la siguiente manera (consulte ld.so(8) para más detalles)

:
•
(Solo ELF) Si el objeto que llama (es decir, la biblioteca compartida o el ejecutable desde el cual se llama a dlopen()) contiene una etiqueta DT_RPATH y no contiene una etiqueta DT_RUNPATH, entonces se buscan los directorios listados en la etiqueta
DT_RPATH.
•
Si, en el momento en que se inició el programa, la variable de entorno LD_LIBRARY_PATH estaba definida para contener una lista de directorios separados por dos puntos, entonces se buscan en estos. (Como medida de seguridad, esta variable se ignora para los programas con set-user-ID y set-group-ID.
)
•
(Solo ELF) Si el objeto que llama contiene una etiqueta DT_RUNPATH, entonces se buscan los directorios listados en esa
etiqueta.
•
Se comprueba el archivo de caché /etc/ld.so.cache (mantenido por ldconfig(8)) para ver si contiene una entrada para pat
h.
•
Se buscan los directorios /lib y /usr/lib (en es
e
orden).

Si el objeto especificado por path tiene dependencias en otros objetos compartidos, entonces estos también son cargados automáticamente por el enlazador dinámico usando las mismas reglas. (Este proceso puede ocurrir recursivamente, si esos objetos a su vez tienen dependencias, y así sucesivamente.

)

Uno de los dos valores siguientes debe incluirse en flags

:
RTLD_LA
ZY
Realizar enlace perezoso. Resolver los símbolos solo cuando se ejecute el código que los referencia. Si el símbolo nunca es referenciado, entonces nunca se resuelve. (El enlace perezoso se realiza solo para referencias a funciones; las referencias a variables siempre se enlazan inmediatamente cuando se carga el objeto compartido.) Desde glibc 2.1.1, este indicador es anulado por el efecto de la variable de entorno LD_BIND_NOW
.
RTLD_N
OW
Si se especifica este valor, o si la variable de entorno LD_BIND_NOW está establecida en una cadena no vacía, todos los símbolos no definidos en el objeto compartido se resuelven antes de que dlopen() devuelva el control. Si esto no p
uede hacerse, se
devuelve un error.

También se pueden combinar (OR) en flags cero o más de los sigui

entes valores:
RTLD_GLOB
AL
Los símbolos definidos por este objeto compartido estarán disponibles para la resolución de símbolos de los objetos compartidos cargados
posteriormente.
RTLD_LOC
AL
Esto es lo contrario de RTLD_GLOBAL, y es el valor predeterminado si no se especifica ninguno de los indicadores. Los símbolos definidos en este objeto compartido no se ponen disponibles para resolver referencias en objetos compartidos cargados
posteriormente.
RTLD_NODELETE (desde glibc
2.2)
No descargar el objeto compartido durante dlclose(). En consecuencia, las variables estáticas y globales del objeto no se reinicializan si el objeto se recarga con dlopen() en un momento
posterior.
RTLD_NOLOAD (desde glibc
2.2)
No cargar el objeto compartido. Esto se puede usar para probar si el objeto ya está residente (dlopen() devuelve NULL si no lo está, o el manejador del objeto si está residente). Este indicador también se puede usar para promover los indicadores de un objeto compartido que ya está cargado. Por ejemplo, un objeto compartido que fue cargado previamente con RTLD_LOCAL puede ser reabierto con RTLD_NOLOAD | RTL
D_GLOBAL.
RTLD_DEEPBIND (desde glibc 2.
3.4)
Colocar el ámbito de búsqueda de los símbolos en este objeto compartido por delante del ámb
ito global. Esto significa que un objeto autónomo usará sus propios símbolos en preferencia
a los símbolos globales con el mismo nombre contenidos en objetos que ya han sido cargados.

Si path es NULL, entonces el manejador devuelto es para el programa principal. Cuando se le da a dlsym(3), este manejador causa una búsqueda de un símbolo en el programa principal, seguido por todos los objetos compartidos cargados al inicio del programa, y luego todos los objetos compartidos cargados por dlopen() con el indicador RTLD_GLOBAL

.

Las referencias a símbolos en el objeto compartido se resuelven usando (en orden): símbolos en el mapa de enlace de los objetos cargados para el programa principal y sus dependencias; símbolos en objetos compartidos (y sus dependencias) que fueron abiertos previamente con dlopen() usando el indicador RTLD_GLOBAL; y definiciones en el propio objeto compartido (y cualquier dependencia que fue cargada para ese objeto)

.

Cualquier símbolo global en el ejecutable que fue colocado en su tabla de símbolos dinámicos por ld(1) también puede usarse para resolver referencias en un objeto compartido cargado dinámicamente. Los símbolos pueden colocarse en la tabla de símbolos dinámicos ya sea porque el ejecutable fue enlazado con el indicador "-rdynamic" (o, sinónimamente, "--export-dynamic"), lo que causa que todos los símbolos globales del ejecutable se coloquen en la tabla de símbolos dinámicos, o porque ld(1) notó una dependencia de un símbolo en otro objeto durante el enlace

estático.

Si el mismo objeto compartido se abre de nuevo con dlopen(), se devuelve el mismo manejador de objeto. El enlazador dinámico mantiene contadores de referencia para los manejadores de objetos, por lo que un objeto compartido cargado dinámicamente no se desasigna hasta que dlclose() se haya llamado en él tantas veces como dlopen() haya tenido éxito en él. Los constructores (ver más abajo) se llaman solo cuando el objeto es realmente cargado en memoria (es decir, cuando el contador de referencias aumenta a 1)

.

Una llamada posterior a dlopen() que carga el mismo objeto compartido con RTLD_NOW puede forzar la resolución de símbolos para un objeto compartido cargado anteriormente con RTLD_LAZY. De manera similar, un objeto que fue abierto previamente con RTLD_LOCAL puede ser promovido a RTLD_GLOBAL en una llamada posterior a dlopen

().

dlmopen(

)

Esta función realiza la misma tarea que dlopen()—los argumentos path y flags, así como el valor de retorno, son los mismos, excepto por las diferencias anotadas a

continuación.

La función dlmopen() difiere de dlopen() principalmente en que acepta un argumento adicional, lmid, que especifica la lista de mapas de enlace (también referida como un espacio de nombres) en el que el objeto compartido debe ser cargado. (En comparación, dlopen() añade el objeto compartido cargado dinámicamente al mismo espacio de nombres que el objeto compartido desde el cual se hace la llamada a dlopen().) El tipo Lmid_t es un manejador opaco que se refiere a un espacio de

nombres.

El argumento lmid es o bien el ID de un espacio de nombres existente (que se puede obtener usando la petición dlinfo(3) RTLD_DI_LMID ) o uno de los siguientes valores

especiales:
LM_ID_BA
SE
Cargar el objeto compartido en el espacio de nombres inicial (es decir, el espacio de nombres de la aplicación)
.
LM_ID_NEW
LM
Crea un nuevo espacio de nombres y carga el objeto compartido en ese espacio de nombres.
El objeto debe haber sido enlazado correctamente para referenciar todos los demás objet
os compartidos que requiere, ya que el nuevo espacio de nombres está inicialmente vacío.

Si path es NULL, entonces el único valor permitido para lmid es LM_ID_BAS

E
.

dlclose(

)

La función dlclose() decrementa el contador de referencias del objeto compartido cargado dinámicamente al que se refiere handle

.

Si el contador de referencias del objeto baja a cero y ningún símbolo en este objeto es requerido por otros objetos, entonces el objeto se descarga después de llamar primero a cualquier destructor definido para el objeto. (Los símbolos en este objeto podrían ser requeridos en otro objeto porque este objeto fue abierto con el indicador RTLD_GLOBAL y uno de sus símbolos satisfizo una relocalización en otro objeto.

)

Todos los objetos compartidos que fueron cargados automáticamente cuando dlopen() fue invocado en el objeto al que se refiere handle son cerrados recursivamente de la misma

manera.

Un retorno exitoso de dlclose() no garantiza que los símbolos asociados con handle sean removidos del espacio de direcciones del llamador. Además de las referencias resultantes de llamadas explícitas a dlopen(), un objeto compartido podría haber sido cargado implícitamente (y con conteo de referencias) debido a

dependencias en otros objetos compartidos. Solo cuand
o todas las referencias han sido liberadas puede el objet
o compartido ser removido del espacio de direcciones.

VALOR DE

RETORNO

En caso de éxito, dlopen() y dlmopen() retornan un handle no-NULL para el objeto cargado. En caso de error (el archivo no pudo ser encontrado, no era legible, tenía el formato incorrecto, o causó errores durante la carga), estas funciones retornan

NULL.

En caso de éxito, dlclose() retorna 0; en caso de error, retorna un valor distinto de

cero.

Los errores de estas funciones pueden ser diagnosticados usando dlerro

r(
3).

NOTA

S

dlmopen() y espacios de

nombres

Una lista de mapas de enlace define un espacio de nombres aislado para la resolución de símbolos por el enlazador dinámico. Dentro de un espacio de nombres, los objetos compartidos dependientes son cargados implícitamente de acuerdo con las reglas habituales, y las referencias a símbolos son igualmente resueltas de acuerdo con las reglas habituales, pero tal resolución está confinada a las definiciones provistas por los objetos que han sido cargados (explícita e implícitamente) en el espacio de

nombres.

La función dlmopen() permite el aislamiento de carga de objetos—la capacidad de cargar un objeto compartido en un nuevo espacio de nombres sin exponer al resto de la aplicación a los símbolos provistos por el nuevo objeto. Nótese que el uso del indicador RTLD_LOCAL no es suficiente para este propósito, ya que previene que los símbolos de un objeto compartido estén disponibles para cualquier otro objeto compartido. En algunos casos, podemos querer hacer que los símbolos provistos por un objeto compartido cargado dinámicamente estén disponibles para (un subconjunto de) otros objetos compartidos sin exponer esos símbolos a toda la aplicación. Esto puede lograrse usando un espacio de nombres separado y el indicador RTLD_

GLOBAL.

La función dlmopen() también puede usarse para proveer un mejor aislamiento que el indicador RTLD_LOCAL. En particular, los objetos compartidos cargados con RTLD_LOCAL pueden ser promovidos a RTLD_GLOBAL si son dependencias de otro objeto compartido cargado con RTLD_GLOBAL. Así, RTLD_LOCAL es insuficiente para aislar un objeto compartido cargado excepto en el (poco común) caso donde uno tiene control explícito sobre todas las dependencias de objetos

compartidos.

Usos posibles de dlmopen() son plugins donde el autor del framework de carga de plugins no puede confiar en los autores de los plugins y no desea que ningún símbolo no definido del framework de plugins sea resuelto a símbolos de plugins. Otro uso es cargar el mismo objeto más de una vez. Sin el uso de dlmopen(), esto requeriría la creación de copias distintas del archivo de objeto compartido. Usando dlmopen(), esto puede lograrse cargando el mismo archivo de objeto compartido en diferentes espacios de

nombres.

La implementación de gli

bc soporta un máximo de
16 espacios de nombres.

Funciones de inicialización y

finalización

Los objetos compartidos pueden exportar funciones usando los atributos de función __attribute__((constructor)) y __attribute__((destructor)). Las funciones constructoras son ejecutadas antes de que dlopen() retorne, y las funciones destructoras son ejecutadas antes de que dlclose() retorne. Un objeto compartido puede exportar múltiples constructores y destructores, y prioridades pueden ser asociadas con cada función para determinar el orden en que son ejecutadas. Ver las páginas de información de gcc (bajo "Function attributes") para más

información.

Un método más antiguo de (parcialmente) lograr el mismo resultado es a través del uso de dos símbolos especiales reconocidos por el enlazador: _init y _fini. Si un objeto compartido cargado dinámicamente exporta una rutina llamada _init(), entonces ese código es ejecutado después de cargar un objeto compartido, antes de que dlopen() retorne. Si el objeto compartido exporta una rutina llamada _fini(), entonces esa rutina es llamada justo antes de que el objeto sea descargado. En este caso, uno debe evitar enlazar contra los archivos de arranque del sistema, que contienen versiones por defecto de estos archivos; esto puede hacerse usando la opción de línea de comandos gcc(1) -nostartfiles

.

El uso de _init y _fini está ahora obsoleto en favor de los mencionados constructores y destructores, que entre otras ventajas, permiten definir múltiples funciones de inicialización y

finalización.

Desde glibc 2.2.3, atexit(3) puede usarse para registrar un manejador de salida que e

s automáticamente llamado cuando un
objeto compartido es descargado.

El programa de abajo carga la biblioteca matemática (de glibc), busca la dirección de la función cos(3), e imprime el coseno de 2.0. El siguiente es un ejemplo de cómo compilar y ejecutar el

$ cc dlopen_demo.c -ldl;

Fuente del

programa 
#include <dlfcn.h>
#include <stdio.h>
#include <stdlib.h>
#include <gnu/lib-names.h>  /* Define LIBM_SO (que será una
                               cadena como "libm.so.6") */
int
main(void)
{
    void *handle;
    typeof(double (double)) *cosine;
    char *error;
    handle = dlopen(LIBM_SO, RTLD_LAZY);
    if (!handle) {
        fprintf(stderr, "%s\n", dlerror());
        exit(EXIT_FAILURE);
    }
    dlerror();    /* Limpia cualquier error existente */
    cosine = (typeof(double (double)) *) dlsym(handle, "cos");
    /* De acuerdo con el estándar ISO C, el casteo entre punteros a
       funciones y 'void *', como se hace arriba, produce resultados indefinidos.
       POSIX.1-2001 y POSIX.1-2008 aceptaron este estado de asuntos y
       propusieron la siguiente solución:
           *(void **) &cosine = dlsym(handle, "cos");
       Este casteo (torpe) se conforma con el estándar ISO C y evitará
       cualquier advertencia del compilador.
       El Corrección Técnica 1 de 2013 a POSIX.1-2008 mejoró las cosas
       al requerir que las implementaciones conformes soporten el casteo
       de 'void *' a un puntero a función.  Sin embargo, algunos compiladores
       (por ejemplo, gcc con la opción '-pedantic') pueden quejarse sobre el
       casteo usado en este programa.  */
    error = dlerror();
    if (error != NULL) {
        fprintf(stderr, "%s\n", error);
        exit(EXIT_FAILURE);
    }
    printf("%f\n", (*cosine)(2.0));
    dlclose(handle);
    exit(EXIT_SUCCESS)
;
}
