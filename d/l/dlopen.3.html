dlopen(3) Manual de funciones de biblioteca dlopen(3)

NOMBRE

dlclose, dlopen, dlmopen - abrir y cerrar un objeto compartido

BIBLIOTECA

Biblioteca de enlace dinámico (libdl, -ldl)

SINOPSIS

#include <dlfcn.h>
void *dlopen(const char *ruta, int flags);
int dlclose(void *handle);
#define _GNU_SOURCE
#include <dlfcn.h>
void *dlmopen(Lmid_t lmid, const char *ruta, int flags);

DESCRIPCIÓN

dlopen()

La función dlopen() carga el objeto compartido dinámico (biblioteca compartida) nombrado por la cadena terminada en nulo ruta y devuelve un "handle" opaco para el objeto cargado. Este handle se emplea con otras funciones de la API de dlopen, como dlsym(3), dladdr(3), dlinfo(3) y dlclose().

Si ruta es NULL, el handle devuelto es para el programa principal. Si ruta contiene una barra ("/"), se interpreta como una ruta de archivo (relativa o absoluta). De lo contrario, el enlazador dinámico busca el objeto de la siguiente manera (ver ld.so(8) para más detalles):

•
(Solo ELF) Si el objeto llamante (es decir, la biblioteca compartida o ejecutable desde la cual se llama a dlopen()) contiene una etiqueta DT_RPATH, y no contiene una etiqueta DT_RUNPATH, entonces se buscan los directorios listados en la etiqueta DT_RPATH.
•
Si, en el momento en que se inició el programa, la variable de entorno LD_LIBRARY_PATH se definió para contener una lista de directorios separados por dos puntos, entonces se buscan.
•
(Solo ELF) Si el objeto llamante contiene una etiqueta DT_RUNPATH, entonces se buscan los directorios listados en esa etiqueta.
•
Se comprueba el archivo caché /etc/ld.so.cache (mantenido por ldconfig(8)) para ver si contiene una entrada para ruta.
•
Se buscan los directorios /lib y /usr/lib (en ese orden).

Si el objeto especificado por ruta tiene dependencias de otros objetos compartidos, estos también son cargados automáticamente por el enlazador dinámico utilizando las mismas reglas. (Este proceso puede ocurrir recursivamente, si esos objetos a su vez tienen dependencias, y así sucesivamente).

Uno de los siguientes dos valores debe incluirse en flags:

RTLD_LAZY
Realiza enlace diferido (lazy binding). Resuelve los símbolos solo cuando se ejecuta el código que los referencia. Si el símbolo nunca se referencia, entonces nunca se resuelve. (El enlace diferido solo se realiza para referencias de funciones; las referencias a variables siempre se enlazan inmediatamente cuando se carga el objeto compartido). Desde glibc 2.1.1, esta bandera es anulada por el efecto de la variable de entorno LD_BIND_NOW.
RTLD_NOW
Si se especifica este valor, o la variable de entorno LD_BIND_NOW se establece en una cadena no vacía, todos los símbolos no definidos en el objeto compartido se resuelven antes de que dlopen() devuelva. Si esto no se puede hacer, se devuelve un error.

Cero o más de los siguientes valores pueden OR-earse en flags:

RTLD_GLOBAL
Los símbolos definidos por este objeto compartido se pondrán a disposición para la resolución de símbolos de objetos compartidos cargados posteriormente.
RTLD_LOCAL
Es lo opuesto a RTLD_GLOBAL, y es el valor por defecto si no se especifica ninguna bandera. Los símbolos definidos en este objeto compartido no se pondrán a disposición para resolver referencias en objetos compartidos cargados posteriormente.
RTLD_NODELETE (desde glibc 2.2)
No descargar el objeto compartido durante dlclose(). En consecuencia, las variables estáticas y globales del objeto no se reinicializan si el objeto se recarga con dlopen() en un momento posterior.
RTLD_NOLOAD (desde glibc 2.2)
No cargar el objeto compartido. Esto se puede usar para probar si el objeto ya está residente (dlopen() devuelve NULL si no lo está, o el handle del objeto si está residente). Esta bandera también se puede usar para promover las banderas de un objeto compartido que ya está cargado. Por ejemplo, un objeto compartido que se cargó previamente con RTLD_LOCAL puede ser reabierto con RTLD_NOLOAD | RTLD_GLOBAL.
RTLD_DEEPBIND (desde glibc 2.3.4)
Colocar el ámbito de búsqueda de los símbolos en este objeto compartido delante del ámbito global. Esto significa que un objeto autocontenido usará sus propios símbolos en preferencia a los símbolos globales con el mismo nombre contenidos en objetos que ya han sido cargados.

Si ruta es NULL, el handle devuelto es para el programa principal. Cuando se le pasa a dlsym(3), este handle provoca una búsqueda de un símbolo en el programa principal, seguido de todos los objetos compartidos cargados al inicio del programa, y luego todos los objetos compartidos cargados por dlopen() con la bandera RTLD_GLOBAL.

Las referencias de símbolos en el objeto compartido se resuelven usando (en orden): símbolos en el mapa de enlaces de objetos cargados para el programa principal y sus dependencias; símbolos en objetos compartidos (y sus dependencias) que fueron abiertos previamente con dlopen() usando la bandera RTLD_GLOBAL; y definiciones en el propio objeto compartido (y cualquier dependencia que fue cargada para ese objeto).

Cualquier símbolo global en el ejecutable que fue colocado en su tabla de símbolos dinámica por ld(1) también puede usarse para resolver referencias en un objeto compartido cargado dinámicamente. Los símbolos pueden colocarse en la tabla de símbolos dinámica porque el ejecutable se enlazó con la bandera "-rdynamic" (o, de forma sinónima, "--export-dynamic"), que hace que todos los símbolos globales del ejecutable se coloquen en la tabla de símbolos dinámica, o porque ld(1) notó una dependencia en un símbolo de otro objeto durante el enlace estático.

Si el mismo objeto compartido se abre de nuevo con dlopen(), se devuelve el mismo handle de objeto. El enlazador dinámico mantiene contadores de referencia para los handles de objetos, por lo que un objeto compartido cargado dinámicamente no se desasigna hasta que dlclose() se haya llamado tantas veces como dlopen() haya tenido éxito en él. Los constructores (ver abajo) se llaman solo cuando el objeto se carga realmente en memoria (es decir, cuando el contador de referencia aumenta a 1).

Una llamada posterior a dlopen() que carga el mismo objeto compartido con RTLD_NOW puede forzar la resolución de símbolos para un objeto compartido cargado previamente con RTLD_LAZY. De manera similar, un objeto que se abrió previamente con RTLD_LOCAL puede ser promovido a RTLD_GLOBAL en una llamada posterior a dlopen().

Si dlopen() falla por alguna razón, devuelve NULL.

dlmopen()

Esta función realiza la misma tarea que dlopen() — los argumentos ruta y flags, así como el valor de retorno, son los mismos, excepto por las diferencias que se señalan a continuación.

La función dlmopen() difiere de dlopen() principalmente en que acepta un argumento adicional, lmid, que especifica la lista de mapas de enlace (también referida como un espacio de nombres) en la que se debe cargar el objeto compartido. (En comparación, dlopen() agrega el objeto compartido cargado dinámicamente al mismo espacio de nombres que el objeto compartido desde el cual se realiza la llamada a dlopen()). El tipo Lmid_t es un handle opaco que se refiere a un espacio de nombres.

El argumento lmid es la ID de un espacio de nombres existente (que se puede obtener utilizando la solicitud RTLD_DI_LMID de dlinfo(3)) o uno de los siguientes valores especiales:

LM_ID_BASE
Cargar el objeto compartido en el espacio de nombres inicial (es decir, el espacio de nombres de la aplicación).
LM_ID_NEWLM
Crear un nuevo espacio de nombres y cargar el objeto compartido en ese espacio de nombres. El objeto debe haber sido enlazado correctamente para referenciar todos los demás objetos compartidos que requiere, ya que el nuevo espacio de nombres está inicialmente vacío.

Si path es NULL, entonces el único valor permitido para lmid es LM_ID_BASE.

dlclose()

La función dlclose() decrementa el contador de referencias del objeto compartido cargado dinámicamente al que se refiere handle.

Si el contador de referencias del objeto baja a cero y ningún símbolo de este objeto es requerido por otros objetos, entonces el objeto se descarga después de llamar primero a cualquier destructor definido para el objeto. (Los símbolos en este objeto podrían ser requeridos en otro objeto porque este objeto fue abierto con el RTLD_GLOBAL bandera y uno de sus símbolos satisfizo una reubicación en otro objeto.)

Todos los objetos compartidos que fueron cargados automáticamente cuando dlopen() fue invocado en el objeto al que se refiere handle son cerrados recursivamente de la misma manera.

Un retorno exitoso de dlclose() no garantiza que los símbolos asociados con handle sean removidos del espacio de direcciones del llamador. Además de las referencias resultantes de llamadas explícitas a dlopen(), un objeto compartido puede haber sido cargado implícitamente (y con conteo de referencias) debido a dependencias en otros objetos compartidos. Solo cuando todas las referencias han sido liberadas puede el objeto compartido ser removido del espacio de direcciones.

VALOR DE RETORNO

En éxito, dlopen() y dlmopen() retornan un handle no-NULL para el objeto cargado. En error (el archivo no pudo ser encontrado, no era legible, tenía el formato incorrecto, o causó errores durante la carga), estas funciones retornan NULL.

En éxito, dlclose() retorna 0; en error, retorna un valor distinto de cero.

Los errores de estas funciones pueden ser diagnosticados usando dlerror(3).

NOTAS

dlmopen() y espacios de nombres

Una lista de mapas de enlace define un espacio de nombres aislado para la resolución de símbolos por el enlazador dinámico. Dentro de un espacio de nombres, los objetos compartidos dependientes son cargados implícitamente de acuerdo con las reglas habituales, y las referencias a símbolos son igualmente resueltas de acuerdo con las reglas habituales, pero tal resolución está confinada a las definiciones provistas por los objetos que han sido (explícita e implícitamente) cargados en el espacio de nombres.

La dlmopen() función permite el aislamiento de carga de objetos—la capacidad de cargar un objeto compartido en un nuevo espacio de nombres sin exponer el resto de la aplicación a los símbolos provistos por el nuevo objeto. Note que el uso de la RTLD_LOCAL bandera no es suficiente para este propósito, ya que previene que los símbolos de un objeto compartido estén disponibles para cualquier otro objeto compartido. En algunos casos, podemos querer hacer que los símbolos provistos por un objeto compartido cargado dinámicamente estén disponibles para (un subconjunto de) otros objetos compartidos sin exponer esos símbolos a toda la aplicación. Esto puede ser logrado usando un espacio de nombres separado y la RTLD_GLOBAL bandera.

La dlmopen() función también puede ser usada para proveer un mejor aislamiento que la RTLD_LOCAL bandera. En particular, los objetos compartidos cargados con RTLD_LOCAL pueden ser promovidos a RTLD_GLOBAL si son dependencias de otro objeto compartido cargado con RTLD_GLOBAL. Así, RTLD_LOCAL es insuficiente para aislar un objeto compartido cargado excepto en el (poco común) caso donde uno tiene control explícito sobre todas las dependencias de objetos compartidos.

Usos posibles de dlmopen() son plugins donde el autor del framework de carga de plugins no puede confiar en los autores de los plugins y no desea que ningún símbolo no definido del framework de plugins sea resuelto a símbolos del plugin. Otro uso es cargar el mismo objeto más de una vez. Sin el uso de dlmopen(), esto requeriría la creación de copias distintas del archivo de objeto compartido. Usando dlmopen(), esto puede ser logrado cargando el mismo archivo de objeto compartido en diferentes espacios de nombres.

La implementación de glibc soporta un máximo de 16 espacios de nombres.

Funciones de inicialización y finalización

Los objetos compartidos pueden exportar funciones usando los atributos de función __attribute__((constructor)) y __attribute__((destructor)) . Las funciones constructoras son ejecutadas antes de que dlopen() retorne, y las funciones destructoras son ejecutadas antes de que dlclose() retorne. Un objeto compartido puede exportar múltiples constructores y destructores, y prioridades pueden ser asociadas con cada función para determinar el orden en que son ejecutadas. Ver las páginas de información de gcc info (bajo "Function attributes") para más información.

Un método más antiguo de (parcialmente) lograr el mismo resultado es a través del uso de dos símbolos especiales reconocidos por el enlazador: _init y _fini. Si un objeto compartido cargado dinámicamente exporta una rutina llamada _init(), entonces ese código es ejecutado después de cargar un objeto compartido, antes de que dlopen() retorne. Si el objeto compartido exporta una rutina llamada _fini(), entonces esa rutina es llamada justo antes de que el objeto sea descargado. En este caso, uno debe evitar enlazar contra los archivos de arranque del sistema, que contienen versiones por defecto de estos archivos; esto puede ser hecho usando la gcc(1) -nostartfiles opción de línea de comandos.

El uso de _init y _fini está ahora obsoleto en favor de los mencionados constructores y destructores, que entre otras ventajas, permiten definir múltiples funciones de inicialización y finalización.

Desde glibc 2.2.3, atexit(3) puede ser usado para registrar un manejador de salida que es automáticamente llamado cuando un objeto compartido es descargado.

Historia

Estas funciones son parte de la API de dlopen, derivada de SunOS.

ERRORES

A partir de glibc 2.24, especificar la RTLD_GLOBAL bandera cuando se llama a dlmopen() genera un error. Además, especificar RTLD_GLOBAL al llamar a dlopen() resulta en un fallo del programa (SIGSEGV) si la llamada es hecha desde cualquier objeto cargado en un espacio de nombre distinto del espacio de nombre inicial.

EJEMPLOS

El programa de abajo carga la biblioteca matemática (de glibc), busca la dirección de la función cos(3) , e imprime el coseno de 2.0. El siguiente es un ejemplo de cómo compilar y ejecutar el programa:


$ cc dlopen_demo.c -ldl;
$ ./a.out;
-0.416147

Fuente del programa

#include <dlfcn.h>
#include <stdio.h>
#include <stdlib.h>
#include <gnu/lib-names.h>  /* Defines LIBM_SO (which will be a
                               string such as "libm.so.6") */
int
main(void)
{
    void *handle;
    typeof(double (double)) *cosine;
    char *error;
    handle = dlopen(LIBM_SO, RTLD_LAZY);
    if (!handle) {
        fprintf(stderr, "%s\n", dlerror());
        exit(EXIT_FAILURE);
    }
    dlerror();    /* Clear any existing error */
    cosine = (typeof(double (double)) *) dlsym(handle, "cos");
    /* According to the ISO C standard, casting between function
       pointers and 'void *', as done above, produces undefined results.
       POSIX.1-2001 and POSIX.2008 accepted this state of affairs and
       proposed the following workaround:
           *(void **) &cosine = dlsym(handle, "cos");
       This (clumsy) cast conforms with the ISO C standard and will
       avoid any compiler warnings.
       The 2013 Technical Corrigendum 1 to POSIX.1-2008 improved matters
       by requiring that conforming implementations support casting
       'void *' to a function pointer.  Nevertheless, some compilers
       (e.g., gcc with the '-pedantic' option) may complain about the
       cast used in this program.  */
    error = dlerror();
    if (error != NULL) {
        fprintf(stderr, "%s\n", error);
        exit(EXIT_FAILURE);
    }
    printf("%f\n", (*cosine)(2.0));
    dlclose(handle);
    exit(EXIT_SUCCESS);
}
