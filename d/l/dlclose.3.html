dlopen(3) Manual de Funciones de Biblioteca dlopen(3)

NOMBRE

dlclose, dlopen, dlmopen - abrir y cerrar un objeto compartido

BIBLIOTECA

Biblioteca de enlace dinámico (libdl, -ldl)

SINOPSIS

#include <dlfcn.h>
void *dlopen(const char *path, int flags);
int dlclose(void *handle);
#define _GNU_SOURCE
#include <dlfcn.h>
void *dlmopen(Lmid_t lmid, const char *path, int flags);

DESCRIPCIÓN

dlopen()

La función dlopen() carga el objeto compartido dinámico (biblioteca compartida) cuyo nombre está en la cadena terminada en nulo path y devuelve un "manejador" opaco para el objeto cargado. Este manejador se emplea con otras funciones de la API de dlopen, como dlsym(3), dladdr(3), dlinfo(3) y dlclose().

Si path es NULL, el manejador devuelto es para el programa principal. Si path contiene una barra ("/"), se interpreta como una ruta de archivo (relativa o absoluta). De lo contrario, el enlazador dinámico busca el objeto de la siguiente manera (consulte ld.so(8) para más detalles):

•
(Solo ELF) Si el objeto llamante (es decir, la biblioteca compartida o el ejecutable desde el cual se llama a dlopen()) contiene una etiqueta DT_RPATH y no contiene una etiqueta DT_RUNPATH, entonces se buscan los directorios listados en la etiqueta DT_RPATH.
•
Si, en el momento en que se inició el programa, la variable de entorno LD_LIBRARY_PATH se definió para contener una lista de directorios separados por dos puntos, entonces se buscan estos. (Como medida de seguridad, esta variable se ignora para programas set-user-ID y set-group-ID).
•
(Solo ELF) Si el objeto llamante contiene una etiqueta DT_RUNPATH, entonces se buscan los directorios listados en esa etiqueta.
•
Se comprueba el archivo de caché /etc/ld.so.cache (mantenido por ldconfig(8)) para ver si contiene una entrada para path.
•
Se buscan los directorios /lib y /usr/lib (en ese orden).

Si el objeto especificado por path tiene dependencias de otros objetos compartidos, estos también son cargados automáticamente por el enlazador dinámico utilizando las mismas reglas. (Este proceso puede ocurrir recursivamente, si esos objetos a su vez tienen dependencias, y así sucesivamente).

Uno de los siguientes dos valores debe incluirse en flags:

RTLD_LAZY
Realiza enlazado diferido. Resuelve los símbolos solo a medida que se ejecuta el código que los referencia. Si el símbolo nunca se referencia, entonces nunca se resuelve. (El enlazado diferido solo se realiza para referencias de funciones; las referencias a variables siempre se enlazan inmediatamente cuando se carga el objeto compartido). Desde glibc 2.1.1, esta bandera se ve anulada por el efecto de la variable de entorno LD_BIND_NOW.
RTLD_NOW
Si se especifica este valor, o si la variable de entorno LD_BIND_NOW se establece a una cadena no vacía, todos los símbolos no definidos en el objeto compartido se resuelven antes de que dlopen() devuelva. Si esto no se puede hacer, se devuelve un error.

Cero o más de los siguientes valores pueden ser combinados con OR en flags:

RTLD_GLOBAL
Los símbolos definidos por este objeto compartido se harán disponibles para la resolución de símbolos de objetos compartidos cargados posteriormente.
RTLD_LOCAL
Es lo opuesto a RTLD_GLOBAL, y es el valor predeterminado si no se especifica ninguna bandera. Los símbolos definidos en este objeto compartido no se pondrán a disposición para resolver referencias en objetos compartidos cargados posteriormente.
RTLD_NODELETE (desde glibc 2.2)
No descargar el objeto compartido durante dlclose(). En consecuencia, las variables estáticas y globales del objeto no se reinicializan si el objeto se recarga con dlopen() en un momento posterior.
RTLD_NOLOAD (desde glibc 2.2)
No cargar el objeto compartido. Esto se puede usar para probar si el objeto ya está residente (dlopen() devuelve NULL si no lo está, o el manejador del objeto si está residente). Esta bandera también se puede usar para promocionar las banderas de un objeto compartido que ya está cargado. Por ejemplo, un objeto compartido que se cargó previamente con RTLD_LOCAL puede ser reabierto con RTLD_NOLOAD | RTLD_GLOBAL.
RTLD_DEEPBIND (desde glibc 2.3.4)
Colocar el ámbito de búsqueda de los símbolos en este objeto compartido delante del ámbito global. Esto significa que un objeto autocontenido utilizará sus propios símbolos en preferencia a los símbolos globales con el mismo nombre contenidos en objetos que ya se han cargado.

Si path es NULL, el manejador devuelto es para el programa principal. Cuando se le pasa a dlsym(3), este manejador provoca una búsqueda de un símbolo en el programa principal, seguido de todos los objetos compartidos cargados al inicio del programa, y luego todos los objetos compartidos cargados por dlopen() con la bandera RTLD_GLOBAL.

Las referencias de símbolos en el objeto compartido se resuelven utilizando (en orden): símbolos en el mapa de enlaces de objetos cargados para el programa principal y sus dependencias; símbolos en objetos compartidos (y sus dependencias) que se abrieron previamente con dlopen() utilizando la bandera RTLD_GLOBAL; y definiciones en el propio objeto compartido (y cualquier dependencia que se haya cargado para ese objeto).

Cualquier símbolo global en el ejecutable que fue colocado en su tabla de símbolos dinámica por ld(1) también puede ser utilizado para resolver referencias en un objeto compartido cargado dinámicamente. Los símbolos pueden ser colocados en la tabla de símbolos dinámica ya sea porque el ejecutable fue enlazado con la bandera "-rdynamic" (o, sinónimamente, "--export-dynamic"), que provoca que todos los símbolos globales del ejecutable se coloquen en la tabla de símbolos dinámica, o porque ld(1) notó una dependencia en otro objeto durante el enlazado estático.

Si el mismo objeto compartido se abre de nuevo con dlopen(), se devuelve el mismo manejador de objeto. El enlazador dinámico mantiene contadores de referencia para los manejadores de objetos, por lo que un objeto compartido cargado dinámicamente no se desasigna hasta que dlclose() se haya llamado tantas veces como dlopen() haya tenido éxito en él. Los constructores (ver más abajo) se llaman solo cuando el objeto se carga realmente en memoria (es decir, cuando el contador de referencias aumenta a 1).

Una llamada posterior a dlopen() que carga el mismo objeto compartido con RTLD_NOW puede forzar la resolución de símbolos para un objeto compartido cargado anteriormente con RTLD_LAZY. Similarmente, un objeto que se abrió previamente con RTLD_LOCAL puede ser promovido a RTLD_GLOBAL en una llamada posterior a dlopen().

Si dlopen() falla por cualquier motivo, devuelve NULL.

dlmopen()

Esta función realiza la misma tarea que dlopen() — los argumentos path y flags, así como el valor de retorno, son los mismos, excepto por las diferencias señaladas a continuación.

La función dlmopen() se diferencia de dlopen() principalmente en que acepta un argumento adicional, lmid, que especifica la lista de mapas de enlaces (también referida como un espacio de nombres) en la cual se debe cargar el objeto compartido. (En comparación, dlopen() agrega el objeto compartido cargado dinámicamente al mismo espacio de nombres que el objeto compartido desde el cual se realiza la llamada a dlopen()). El tipo Lmid_t es un manejador opaco que se refiere a un espacio de nombres.

El argumento lmid es la ID de un espacio de nombres existente (que se puede obtener utilizando la solicitud RTLD_DI_LMID de dlinfo(3)) o uno de los siguientes valores especiales:

LM_ID_BASE
Cargar el objeto compartido en el espacio de nombres inicial (es decir, el espacio de nombres de la aplicación).
LM_ID_NEWLM
Crea un nuevo espacio de nombres y carga el objeto compartido en ese espacio de nombres. El objeto debe haber sido enlazado correctamente para referenciar todos los demás objetos compartidos que requiere, ya que el nuevo espacio de nombres está inicialmente vacío.

Si path es NULL, entonces el único valor permitido para lmid es LM_ID_BASE.

dlclose()

La función dlclose() decrementa el contador de referencias del objeto compartido cargado dinámicamente al que se refiere handle.

Si el contador de referencias del objeto baja a cero y ningún símbolo de este objeto es requerido por otros objetos, entonces el objeto se descarga después de haber llamado previamente a cualquier destructor definido para el objeto. (Los símbolos en este objeto podrían ser requeridos en otro objeto porque este objeto fue abierto con el indicador RTLD_GLOBAL y uno de sus símbolos satisfizo una reubicación en otro objeto.)

Todos los objetos compartidos que fueron cargados automáticamente cuando se invocó dlopen() en el objeto al que se refiere handle son cerrados recursivamente de la misma manera.

Un retorno exitoso de dlclose() no garantiza que los símbolos asociados con handle sean removidos del espacio de direcciones del llamador. Además de las referencias resultantes de las llamadas explícitas a dlopen(), un objeto compartido puede haber sido cargado implícitamente (y con conteo de referencias) debido a dependencias en otros objetos compartidos. Solo cuando todas las referencias han sido liberadas puede el objeto compartido ser removido del espacio de direcciones.

VALOR DE RETORNO

En caso de éxito, dlopen() y dlmopen() retornan un handle no-NULL para el objeto cargado. En caso de error (el archivo no pudo ser encontrado, no era legible, tenía un formato incorrecto, o causó errores durante la carga), estas funciones retornan NULL.

En caso de éxito, dlclose() retorna 0; en caso de error, retorna un valor distinto de cero.

Los errores de estas funciones pueden ser diagnosticados usando dlerror(3).

NOTAS

dlmopen() y espacios de nombres

Una lista de mapas de enlace define un espacio de nombres aislado para la resolución de símbolos por el enlazador dinámico. Dentro de un espacio de nombres, los objetos compartidos dependientes son cargados implícitamente de acuerdo con las reglas habituales, y las referencias a símbolos son igualmente resueltas de acuerdo con las reglas habituales, pero tal resolución está confinada a las definiciones provistas por los objetos que han sido cargados (explícita e implícitamente) en el espacio de nombres.

La dlmopen() función permite el aislamiento de carga de objetos—la capacidad de cargar un objeto compartido en un nuevo espacio de nombres sin exponer al resto de la aplicación a los símbolos provistos por el nuevo objeto. Nótese que el uso del indicador RTLD_LOCAL no es suficiente para este propósito, ya que previene que los símbolos de un objeto compartido estén disponibles para cualquier otro objeto compartido. En algunos casos, podemos querer hacer que los símbolos provistos por un objeto compartido cargado dinámicamente estén disponibles para (un subconjunto de) otros objetos compartidos sin exponer esos símbolos a toda la aplicación. Esto puede lograrse usando un espacio de nombres separado y el indicador RTLD_GLOBAL .

La dlmopen() función también puede usarse para proveer un mejor aislamiento que el indicador RTLD_LOCAL . En particular, los objetos compartidos cargados con RTLD_LOCAL pueden ser promovidos a RTLD_GLOBAL si son dependencias de otro objeto compartido cargado con RTLD_GLOBAL. Así, RTLD_LOCAL es insuficiente para aislar un objeto compartido cargado excepto en el (poco común) caso donde uno tiene control explícito sobre todas las dependencias de objetos compartidos.

Usos posibles de dlmopen() son plugins donde el autor del framework de carga de plugins no puede confiar en los autores de los plugins y no desea que ningún símbolo no definido del framework de plugins sea resuelto a símbolos del plugin. Otro uso es cargar el mismo objeto más de una vez. Sin el uso de dlmopen(), esto requeriría la creación de copias distintas del archivo del objeto compartido. Usando dlmopen(), esto puede lograrse cargando el mismo archivo de objeto compartido en diferentes espacios de nombres.

La implementación de glibc soporta un máximo de 16 espacios de nombres.

Funciones de inicialización y finalización

Los objetos compartidos pueden exportar funciones usando los atributos de función __attribute__((constructor)) y __attribute__((destructor)) . Las funciones constructoras son ejecutadas antes de que dlopen() retorne, y las funciones destructoras son ejecutadas antes de que dlclose() retorne. Un objeto compartido puede exportar múltiples constructores y destructores, y pueden asociarse prioridades con cada función para determinar el orden en que son ejecutadas. Ver las páginas de información de gcc info

(bajo "Function attributes") para más información. Un método más antiguo de lograr (parcialmente) el mismo resultado es mediante el uso de dos símbolos especiales reconocidos por el enlazador: _init y_fini . Si un objeto compartido cargado dinámicamente exporta una rutina llamada_init (), entonces ese código es ejecutado después de cargar un objeto compartido, antes de quedlopen () retorne. Si el objeto compartido exporta una rutina llamada_fini (), entonces esa rutina es llamada justo antes de que el objeto sea descargado. En este caso, uno debe evitar enlazar contra los archivos de arranque del sistema, que contienen versiones por defecto de estos archivos; esto puede hacerse usando la opción de línea de comandos gcc(1) -nostartfiles

. El uso de _init y _fini

está ahora obsoleto en favor de los mencionados constructores y destructores, que entre otras ventajas, permiten definir múltiples funciones de inicialización y finalización. Desde glibc 2.2.3, atexit(3)

puede usarse para registrar un manejador de salida que es automáticamente llamado cuando un objeto compartido es descargado.

Historia

Estas funciones son parte de la API dlopen, derivada de SunOS.

NAME

dlclose - unload a shared object

LIBRARY

Symbol resolution when linking (libdl)

SYNOPSIS

#include <dlfcn.h>

int dlclose(void *handle);

DESCRIPTION

The dlclose function decrements the reference count of the dynamically linked shared object specified by handle. When the reference count drops to zero, the shared object is unloaded from the address space of the calling process. The functions and variables defined by the shared object are no longer available for use.

The value of handle must be one obtained from a previous call to dlopen.

If handle does not refer to a valid dynamically linked shared object previously opened by dlopen, an error occurs, and dlclose returns a non-zero value. Note that handle can be invalid if it has been closed already or if it was never obtained from dlopen.

If the shared object being closed has dependencies on other shared objects that are no longer required by any other shared object or program, those dependencies may also be unloaded. This process is recursive.

RETURN VALUE

On success, dlclose returns 0. On failure, it returns a non-zero value.

If an error occurs, additional information can be obtained by calling dlerror.

ATTRIBUTES

For an explanation of the terms used in this section, see attributes(7).

Interface Attribute
dlclose Thread safety

The reference counting mechanism is thread-safe. However, if multiple threads call dlclose on the same handle, the behavior is undefined. Specifically, the shared object might be unloaded while one or more threads are still using it.

STANDARDS

The dlclose function conforms to the POSIX.1-2008 standard for the extended API.

HISTORY

The dlclose function first appeared in FreeBSD 2.1.

NOTES

When a shared object is unloaded, its destructor functions (if any) are called. Destructors are functions registered using the __attribute__((destructor)) function attribute.

The order in which destructors are called is not specified. However, if a shared object depends on other shared objects, its destructors are generally called after the destructors of its dependencies.

Be careful when calling dlclose from within a shared object that is being unloaded. The behavior in this case is undefined.

If you have multiple references to a shared object (e.g., multiple calls to dlopen with the same filename, or other shared objects depending on it), dlclose will only decrement the reference count. The shared object will not be unloaded until the reference count reaches zero.

It is generally unsafe to call dlclose on shared objects that are part of the C library or other core system libraries. Doing so can lead to unpredictable behavior and system instability.

BUGS

If handle is not a valid handle, dlerror may return a message indicating the error, but dlclose itself may still return 0. This is a known issue with the implementation of dlclose on some systems.

EXAMPLES

The following example demonstrates the usage of dlclose:

#include <stdio.h>
#include <stdlib.h>
#include <dlfcn.h>

int main() {
    void *handle;
    const char *error;

    // Open a shared object
    handle = dlopen("libexample.so", RTLD_LAZY);
    if (!handle) {
        fprintf(stderr, "%s\n", dlerror());
        exit(EXIT_FAILURE);
    }

    // Clear any existing error
    dlerror();

    // Close the shared object
    if (dlclose(handle) != 0) {
        fprintf(stderr, "dlclose error: %s\n", dlerror());
        exit(EXIT_FAILURE);
    }

    printf("Shared object unloaded successfully.\n");

    return 0;
}

This program first opens a shared object named "libexample.so". If successful, it then attempts to close the shared object using dlclose. If dlclose fails, an error message is printed using dlerror.
