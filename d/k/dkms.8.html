Esta directiva da el nombre del módulo justo después de que se compila. Si no está definida, DKMS espera encontrar su BUILT_MODULE_NAME[#] en el directorio raíz de sus archivos de origen. =
Por defecto, strip se considera "yes". Si se establece en "no", DKMS no ejecutará strip -g en su módulo compilado para eliminar los símbolos de depuración. STRIP[0] se usa como valor predeterminado para cualquier entrada no definida en la matriz ST

MAKE[#]
=
La matriz de directivas MAKE le indica a DKMS qué comando make debe usarse para compilar su módulo. El comando make predeterminado debe ponerse en MAKE[0]. Las demás entradas en la matriz MAKE solo se usarán si su entrada correspondiente en MAKE_MATCH[#] coincide, como una expresión regular (usando grep -E), con el kernel para el que se está compilando el módulo. Tenga en cuenta que si no se coloca ningún valor en MAKE_MATCH[#] para ningún MAKE[#] donde # > 0, entonces esa directiva MAKE se ignora. MAKE_MATCH[0] es opcional y, si se rellena, se usará para determinar si MAKE[0] debe usarse para compilar el módulo para ese kernel. Si múltiples directivas MAKE_MATCH coinciden con el kernel para el que se está compilando, se usará la última MAKE[#] coincidente para compilar su módulo. Si no se especifica ninguna directiva MAKE o si ninguna MAKE_MATCH coincide con el kernel para el que se está compilando, DKMS intentará usar un comando make genérico para compilar su módulo.

KERNELRELEASE=$kernelver -j$parallel_jobs se añadirá automáticamente a MAKE[#]. Si desea suprimir este comportamiento

NO_WEAK_MODUL
ES=
La directiva NO_WEAK_MODULES, cuando se establece en "yes", impide que dkms cree un enlace simbólico en el directorio weak-updates. La funcionalidad de módulos débiles fue diseñada para eliminar la necesidad de recompilar los módulos del kernel cuando se producen actualizaciones del kernel y se basa en los símbolos dentro del kABI. Los valores válidos son "yes" o "no".

La interfaz de módulos del kernel kABI es compatible actualmente en Red

Hat Enterprise Linux (y sus derivados), SUSE Linux Enterprise Server
y openSUSE Leap; en otras distribuciones esta directiva se ignora.

Y=

Esto se puede especificar como un kernel upstream particular o un incremento de ABI de un kernel. Por ejemplo, "2.6.24" sería un kernel upstream y "2.6.24-16" representaría un incremento de ABI para un kernel. Ambos son válidos en este ámbito.

problema.

PATCH[#]
=
Use la matriz de directivas PATCH para especificar parches que deben aplicarse a su código fuente antes de que se produzca una compilación. Se espera que todos los parches estén en formato -p1 y se aplican con el comando patch -p1. Cada directiva debe especificar el nombre de archivo del parche a aplicar, y todos los parches deben estar ubicados en el subdirectorio patches de su directorio de origen ( /usr/src/<module>-<module-version>/patches/ ). Si algún parche no se puede aplicar, la compilación se detendrá y las rechazadas se pueden inspeccionar en /var/lib/dkms/<module>/<module-version>/build/. Si un parche solo debe aplicarse condicionalmente, se debe usar la matriz PATCH_MATCH[#] y se debe colocar una expresión regular correspondiente en PATCH_MATCH[#], lo que alertará a dkms para usar solo ese PATCH[#] si la expresión regular coincide con el kernel para el que se está compilando actualmente el
módulo.
PATCH_MATCH[#]
=
Vea la descripción anterior para las directivas PATCH[#]. Si solo quiere que un parche se aplique en ciertos escenarios, se debe utilizar la matriz PATCH_MATCH dando una expresión regular que coincida con los kernels a los que pretende que se aplique el PATCH[#] correspondiente antes de compilar ese
módulo.

L=

"no".

VARIABLES DKMS.CONF

build_environment
If set, the value is sourced by the shell with the source command.

Can be used to specify a custom gcc installed in a custom path; and the variable $kernelver can be used inside the environment file to represent the target kernel version. Some examples:

Define a custom script to point to a specific GCC ( export CC=/opt/gcc12/bin/gcc ): build_environment="/opt/gcc12/env"

Enable the software collection gcc-toolset-11 and use it for building an UEK kernel on Oracle Linux: build_environment="/opt/rh/gcc-toolset-11/enable"

post_transaction
If the directive is set to any non null-value, the content of the directive will be executed with any command that change the content of the kernel modules folder, that is dkms autoinstall, dkms install and dkms remove/unbuild/uninstall. Can be used to trigger a global initrd rebuild or to call a script that performs some other tasks (calling kexec, triggering the restart of services not contained in a DKMS package, etc.). The command is constructed with the shell built-in eval and the variable $kernelver can be used to represent the target kernel version. Some examples:

Regenerate the ram disk for the target kernel: post_transaction="dracut --force --kver $kernelver" (Red Hat style) or post_transaction="update-initramfs -k $kernelver" (Debian style).

Launch an arbitrary script: post_transaction="/path/to/script.sh"

Restart a service: post_transaction="systemctl restart something.service"

Regenerate the ram disk for all installed kernels, ignoring the kernel version passed as the parameter: post_transaction="dracut --force --regenerate-all" (Red Hat style) or post_transaction="update-initramfs -k all" (Debian style).

AUTOINSTALADOR DKMS

El servicio de autoinstalación de DKMS (que puede ser dkms_autoinstaller o dkms.service dependiendo de tu distribución) es un servicio de arranque que instala automáticamente cualquier módulo que tenga AUTOINSTALL="yes" establecido en su archivo dkms.conf. El servicio funciona de manera bastante simple y si hay múltiples versiones de un módulo en el árbol DKMS de tu sistema, no hará nada y en su lugar explicará que se requiere intervención manual.
