propio

Es recomendable terminar el script para el modo dummy-loop con una palabra clave TIMER. De lo contrario dummy-ups volverá directamente al principio del archivo y, en particular, olvidará cualquier valor que hayas establecido con upsrw. Ten

en

cuenta que para evitar la sobrecarga de la CPU con un bucle infinito, el controlador "duerme" un poco entre los ciclos de lectura del archivo (actualmente este retraso está codificado a un segundo), independientemente de (y/o además de) cualquier palabra clave TIMER y posiblemente la configuración

común

pollinterval. Otra instrucción, introducida más recientemente, es ALARM, que permite la simulación de alarmas de SAI de la misma manera en que se generarían con implementaciones reales de controladores. Los controladores modernos desacoplan los estados de alarma de la variable ups.status, y generar ALARM estableciéndolo como un token de estado se desaconseja en favor del uso de funciones comunes y modernas para generar alarmas dentro

del

código del controlador. La instrucción ALARM está destinada a simular este comportamiento lo más fielmente posible. El valor que sigue a una instrucción ALARM se trata como el mensaje de alarma y se publica eventualmente como la variable ups.alarm, con el token ALARM también establecido en ups.status por mecanismos internos del controlador, en lugar de manipular directamente la variable. Múltiples instrucciones ALARM tendrán sus mensajes combinados en la variable ups.alarm, tal como ocurriría con la lógica real de un controlador. A

la

inversa, cualquier instrucción ALARM por sí sola limpiará los estados de alarma activos.ee abajo para ver un ejemplo de cómo establecer y restablecer

Modo

Repetidor

En este contexto, port en el bloque ups.conf es el nombre del UPS de destino, usando el formato NUT, es

decir: 
<upsname>@
<hostname
>[:<port>]

Por

ejemplo: 
[repeater]
        driver = dummy-ups
port = ups1@remotehost
desc = "dummy-ups en modo repetidor"

A diferencia de las especificaciones de UPS en el resto de NUT, la parte @hostname no es opcional — es el carácter @ el que habilita el Modo Repetidor. Para referirse a un UPS en el mismo host que dummy-ups, usa port = upsname@localhost

.

Ten en cuenta que para evitar la sobrecarga de la CPU con un bucle infinito, el controlador "duerme" un poco entre ciclos de solicitud de datos (actualmente este retardo está fijado en un segundo), por lo que la propagación de las actualizaciones de datos disponibles para un upsd remoto puede retrasarse en este

tiempo.

Ten cuidado de que cualquier error encontrado en el inicio del modo repetidor (por ejemplo, cuando no todos los UPS de destino a repetir o sus instancias de upsd son conectables todavía) causará por defecto que el controlador dummy-ups termine prematuramente. Este comportamiento se puede

cambiar estableciendo el indicador
repeater_disable_strict_start, haciendo
que tales errores no sean fatales.

INTERACCIÓ

N

Una vez que el controlador se carga en modo dummy, puedes cambiar cualquier variable, excepto las de las colecciones driver.* y server.*. Puedes hacer esto editando el archivo de definición, o usando los comandos upsrw(8) y upscmd(

8).

Ten en cuenta que en el modo de simulación, se pueden añadir nuevas variables sobre la marcha, pero solo añadiéndolas al archivo de definición (y esperando a que se vuelva a leer). Es decir, el controlador no debería permitir definir una nueva variable a través de

upsrw.

Por el contrario, si necesitas eliminar una variable (como las transitorias, como ups.alarm), simplemente actualízalas estableciendo un valor vacío. Como resultado, se eliminarán de los

datos.

En el modo repetidor, el controlador actúa de acuerdo con

las capacidades del UPS, y por lo tanto soporta los
mismos comandos instantáneos y valores configurables.

ANTECEDENTE

S

El Modo Dummy se escribió originalmente en una noche para reemplazar el anterior controlador de pruebas dummycons, que era demasiado limitado y requería una terminal para la

interacción.

dummy-ups es útil para el desarrollo de clientes NUT y otros propósitos de

prueba.

También ayuda en el esfuerzo de Garantía de Calidad de NUT, al automatizar algunas pruebas en el marco de NUT y en el NIT (suite de pruebas de integración de NUT). Consulta el script tests/NIT/nit.sh en las fuentes de NUT, que depende en gran medida de este controlador, para ver más

ejemplos.

Ahora ofrece un modo repetidor. Esto ayudará en la construcción del enfoque Meta UPS, que permite construir un dispositivo virtual, compuesto por varios otros dispositivos (ya sean UPS, PDUs), o quizás representar el mismo dispositivo que soporta varios protocolos de comunicación y diferentes medios (Serial, USB, SNMP..

.
)

ERRORE

S

y, y los datos necesitan la aplicación de verificación de nom
bre/valor, así como la definición de límites o enumeraciones.

ADVERTENCI

AS

Si usas marcos de gestión de servicios como systemd o SMF para gestionar las dependencias entre instancias de controladores y el servidor de datos, y algunos de estos controladores son dummy-ups en modo repetidor representando datos de otro controlador que se ejecuta en el mism

o sistema, entonces podrías tener que configurar dependencias especiales (por ejemplo, con archivos de fragmento "drop-in" de systemd) para permitir que tu nut-server se inicie después de los controladores de dispositivo "reales" y antes de tales controladores repetidores (
sin un servidor que responda, de todos modos fallarían al iniciar). Esto también podría necesitar cuidado especial en los archivos upsd.conf y/o ups.conf para no bloquear el arranque del sistema durante demasiado tiempo mientras el controlador repetidor no se haya iniciado.

Controladores de

clonación:

El modo "repeater" del controlador dummy-ups es de alguna manera similar a los controladores clone y clone-outlet, que se sitúan sobre otro socket de controlador (o tubería con nombre de Windows) localmente, y permiten a los usuarios agrupar clientes a una salida particular de un dispositivo y tratar esta salida como si fuera un UPS normal. Notablemente, en este modo el controlador dummy-ups es un cliente del protocolo NUT en red y puede retransmitir información de dispositivos servidos local o remotamente, y requiere un servidor de datos NUT en ejecución upsd para representar el dispositivo "real" para que esto

funcione.
