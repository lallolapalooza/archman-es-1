NOMBRE

Log::Log4perl::FAQ - Preguntas Frecuentes sobre Log::Log4perl

DESCRIPCIÓN

Este FAQ muestra una amplia variedad de tareas comunes de registro y cómo resolverlas de la manera más elegante con Log::Log4perl. La mayoría de las veces, esto será simplemente una cuestión de configurar de manera inteligente sus archivos de configuración de Log::Log4perl.

¿Por qué usar Log::Log4perl en lugar de cualquier otro módulo de registro en CPAN?

Esa es una buena pregunta. Hay docenas de módulos de registro en CPAN. Cuando se trata de registro, la gente típicamente piensa: "Ajá. Escribir mensajes de depuración y error. Depurar es más bajo que error. Fácil. Voy a escribir el mío." Escribir un módulo de registro es como un rito de paso para cada programador de Perl, al igual que escribir su propio sistema de plantillas.

Por supuesto, después de tener los conceptos básicos correctos, es necesario añadir funcionalidades. Te gustaría escribir una marca de tiempo con cada mensaje. Luego, marcas de tiempo con microsegundos. Luego, los mensajes deben escribirse tanto en la pantalla como en un archivo de registro.

Y, a medida que el tamaño de su aplicación crece, podría preguntarse: ¿Por qué mi sistema de registro no escala con él? Le gustaría activar el registro en partes seleccionadas de la aplicación, y no en todas partes, porque esto mata el rendimiento. Aquí es cuando la gente recurre a Log::Log4perl, porque maneja todo eso.

Evite este costoso cambio.

Utilice "Log::Log4perl" desde el principio. El modo ":easy" de "Log::Log4perl" admite el registro fácil en scripts sencillos:

use Log::Log4perl qw(:easy);
Log::Log4perl->easy_init($DEBUG);
DEBUG "Un mensaje de bajo nivel";
ERROR "No se llegará hasta que el nivel se aumente a ERROR";

Y cuando su aplicación crezca inevitablemente, su sistema de registro crecerá con ella sin que usted tenga que cambiar ningún código.

Por favor, no reinvente el registro. "Log::Log4perl" está aquí, es fácil de usar, es escalable y cubre muchas áreas en las que aún no ha pensado, pero pronto entrará.

¿Cuál es la forma más fácil de usar Log4perl?

Si solo desea obtener toda la comodidad del registro, sin mucha sobrecarga, utilice los *Registros Sigilosos*. Si utiliza Log::Log4perl en modo ":easy" como

use Log::Log4perl qw(:easy);

tendrá las siguientes funciones disponibles en el paquete actual:

DEBUG("mensaje");
INFO("mensaje");
WARN("mensaje");
ERROR("mensaje");
FATAL("mensaje");

Solo asegúrese de que cada paquete de su código donde los esté utilizando primero cargue "use Log::Log4perl qw(:easy)", y estará listo. La categoría de cada registro sigiloso será equivalente al nombre del paquete en el que se encuentra.

Estos registros sigilosos estarán absolutamente silenciosos hasta que inicialice Log::Log4perl en su programa principal con:

    # Define cualquier comportamiento de Log4perl
Log::Log4perl->init("foo.conf");

(utilizando un archivo de configuración completo de Log4perl) o el método súper fácil

    # Simplemente registra en STDERR
Log::Log4perl->easy_init($DEBUG);

o el método estilo parámetros con una complejidad algo intermedia:

    # Añadir a un archivo de registro
Log::Log4perl->easy_init( { level   => $DEBUG,
                            file    => ">>test.log" } );

Para más información, consulte "Registros Sigilosos" en Log::Log4perl.

¿Cómo puedo simplemente registrar todos mis mensajes de ERROR en un archivo?

Después de cargar el módulo "Log::Log4perl", simplemente inicialice su comportamiento pasando una configuración al método "init" como una referencia de cadena. Luego, obtenga una instancia de registro y escriba un mensaje con su método error():

use Log::Log4perl qw(get_logger);
    # Define la configuración
my $conf = q(
    log4perl.logger                    = ERROR, FileApp
    log4perl.appender.FileApp          = Log::Log4perl::Appender::File
    log4perl.appender.FileApp.filename = test.log
    log4perl.appender.FileApp.layout   = PatternLayout
    log4perl.appender.FileApp.layout.ConversionPattern = %d> %m%n
);
    # Inicializa el comportamiento de registro
Log::Log4perl->init( \$conf );
    # Obtiene una instancia de registro
my $logger = get_logger("Bar::Twix");
$logger->error("¡Oh, cielos, un error terrible!");
$logger->warn("¡Oh, cielos, una advertencia terrible!");

Esto añadirá algo como

2002/10/29 20:11:55> ¡Oh, cielos, un error terrible!

al archivo de registro "test.log". ¿Cómo funciona todo esto?

Mientras que el método init() de Log::Log4perl típicamente toma el nombre de un archivo de configuración como parámetro de entrada, como en

Log::Log4perl->init( "/path/mylog.conf" );

el ejemplo anterior muestra cómo pasar una configuración como texto en una referencia escalar.

La configuración como se muestra define un registro de la categoría raíz, que tiene un appender del tipo "Log::Log4perl::Appender::File" adjunto. La línea

log4perl.logger = ERROR, FileApp

no lista una categoría, definiendo un registro raíz. Compárelo con

log4perl.logger.Bar.Twix = ERROR, FileApp

que definiría un registro para la categoría "Bar::Twix", mostrando probablemente un comportamiento diferente. "FileApp" en el lado derecho de la asignación es un nombre de variable definido arbitrariamente, que solo se utiliza para referenciar de alguna manera un appendidor definido más adelante.

La configuración del appender en la configuración se define de la siguiente manera:

log4perl.appender.FileApp          = Log::Log4perl::Appender::File
log4perl.appender.FileApp.filename = test.log

Selecciona el appender de archivo de la jerarquía de "Log::Log4perl::Appender", que añadirá al archivo "test.log" si ya existe. Si quisiéramos sobrescribir un archivo potencialmente existente, tendríamos que establecer explícitamente el parámetro apropiado "mode" de "Log::Log4perl::Appender::File":

log4perl.appender.FileApp          = Log::Log4perl::Appender::File
log4perl.appender.FileApp.filename = test.log
log4perl.appender.FileApp.mode     = write

Además, la configuración define un formato PatternLayout, añadiendo la fecha y hora actual bien formateada, una flecha (>) y un espacio antes de los mensajes, que luego va seguido de un salto de línea:

log4perl.appender.FileApp.layout   = PatternLayout
log4perl.appender.FileApp.layout.ConversionPattern = %d> %m%n

Obtener una instancia de registro y registrar algo realmente se hace típicamente en una parte diferente del sistema que la sección de inicialización de Log::Log4perl, pero en este ejemplo, se hace justo después de init por razones de brevedad:

    # Obtiene una instancia de registro
my $logger = get_logger("Bar::Twix");
$logger->error("¡Oh, cielos, un error terrible!");

Esto recupera una instancia del registro de la categoría "Bar::Twix", que, como todas las demás categorías, hereda el comportamiento del registro raíz si no se definen otros registros en la sección de inicialización.

El método error() activa un mensaje, que el registro raíz captura. Su prioridad es igual o superior a la prioridad del registro raíz (ERROR), lo que hace que el registro raíz lo reenvíe a su appendidor adjunto. Por el contrario, lo siguiente

$logger->warn("¡Oh, cielos, una advertencia terrible!");

no se completa, porque el registro raíz tiene una configuración más alta (ERROR y superior) que la prioridad WARN del mensaje.

Frequently Asked Questions
How can I include global (thread-specific) data in my log messages?

Say, you're writing a web application and want all your log messages to include the current client's IP address. Most certainly, you don't want to include it in each and every log message like in

$logger->debug( $r->connection->remote_ip,
                " Retrieving user data from DB" );

do you? Instead, you want to set it in a global data structure and have Log::Logperl include it automatically via a PatternLayout setting in the configuration file:

log4perl.appender.FileApp.layout.ConversionPattern = %X{ip} %m%n

The conversion specifier %X{ip} references an entry under the key "ip" in the global "MDC" (mapped diagnostic context) table, which you've set once via

Log::Log4perl::MDC->put("ip", $r->connection->remote_ip);

at the start of the request handler. Note that this is a static (class) method, there's no logger object involved. You can use this method with as many key/value pairs as you like as long as you reference them under different names.

The mappings are stored in a global hash table within Log::Log4perl. Luckily, because the thread model in 5.8.0 doesn't share global variables between threads unless they're explicitly marked as such, there's no problem with multi-threaded environments.

For more details on the MDC, please refer to "Mapped Diagnostic Context (MDC)" in Log::Log4perl and Log::Log4perl::MDC.

My application is already logging to a file. How can I duplicate all messages to also go to the screen?

Assuming that you already have a Log4perl configuration file like

log4perl.logger                    = DEBUG, FileApp
log4perl.appender.FileApp          = Log::Log4perl::Appender::File
log4perl.appender.FileApp.filename = test.log
log4perl.appender.FileApp.layout   = PatternLayout
log4perl.appender.FileApp.layout.ConversionPattern = %d> %m%n

and log statements all over your code, it's very easy with Log4perl to have the same messages both printed to the logfile and the screen. No reason to change your code, of course, just add another appender to the configuration file and you're done:

log4perl.logger                    = DEBUG, FileApp, ScreenApp
log4perl.appender.FileApp          = Log::Log4perl::Appender::File
log4perl.appender.FileApp.filename = test.log
log4perl.appender.FileApp.layout   = PatternLayout
log4perl.appender.FileApp.layout.ConversionPattern = %d> %m%n
log4perl.appender.ScreenApp          = Log::Log4perl::Appender::Screen
log4perl.appender.ScreenApp.stderr   = 0
log4perl.appender.ScreenApp.layout   = PatternLayout
log4perl.appender.ScreenApp.layout.ConversionPattern = %d> %m%n

The configuration file above is assuming that both appenders are active in the same logger hierarchy, in this case the "root" category. But even if you've got file loggers defined in several parts of your system, belonging to different logger categories, each logging to different files, you can gobble up all logged messages by defining a root logger with a screen appender, which would duplicate messages from all your file loggers to the screen due to Log4perl's appender inheritance. Check

http://www.perl.com/pub/a/2002/09/11/log4perl.html

for details. Have fun!

How can I make sure my application logs a message when it dies unexpectedly?

Whenever you encounter a fatal error in your application, instead of saying something like

open FILE, "<blah" or die "Can't open blah -- bailing out!";

just use Log::Log4perl's fatal functions instead:

my $log = get_logger("Some::Package");
open FILE, "<blah" or $log->logdie("Can't open blah -- bailing out!");

This will both log the message with priority FATAL according to your current Log::Log4perl configuration and then call Perl's die() afterwards to terminate the program. It works the same with stealth loggers (see "Stealth Loggers" in Log::Log4perl), all you need to do is call

use Log::Log4perl qw(:easy);
open FILE, "<blah" or LOGDIE "Can't open blah -- bailing out!";

What can you do if you're using some library which doesn't use Log::Log4perl and calls die() internally if something goes wrong? Use a $SIG{__DIE__} pseudo signal handler

use Log::Log4perl qw(get_logger);
$SIG{__DIE__} = sub {
    if($^S) {
        # We're in an eval {} and don't want log
        # this message but catch it later
        return;
    }
    local $Log::Log4perl::caller_depth =
          $Log::Log4perl::caller_depth + 1;
    my $logger = get_logger("");
    $logger->fatal(@_);
    die @_; # Now terminate really
};

This will catch every die()-Exception of your application or the modules it uses. In case you want to It will fetch a root logger and pass on the die()-Message to it. If you make sure you've configured with a root logger like this:

Log::Log4perl->init(\q{
    log4perl.category         = FATAL, Logfile
    log4perl.appender.Logfile = Log::Log4perl::Appender::File
    log4perl.appender.Logfile.filename = fatal_errors.log
    log4perl.appender.Logfile.layout = \
               Log::Log4perl::Layout::PatternLayout
    log4perl.appender.Logfile.layout.ConversionPattern = %F{1}-%L (%M)> %m%n
});

then all die() messages will be routed to a file properly. The line

local $Log::Log4perl::caller_depth =
      $Log::Log4perl::caller_depth + 1;

in the pseudo signal handler above merits a more detailed explanation. With the setup above, if a module calls die() in one of its functions, the fatal message will be logged in the signal handler and not in the original function -- which will cause the %F, %L and %M placeholders in the pattern layout to be replaced by the filename, the line number and the function/method name of the signal handler, not the error-throwing module. To adjust this, Log::Log4perl has the $caller_depth variable, which defaults to 0, but can be set to positive integer values to offset the caller level. Increasing it by one will cause it to log the calling function's parameters, not the ones of the signal handler. See "Using Log::Log4perl from wrapper classes" in Log::Log4perl for more details.

How can I hook up the LWP library with Log::Log4perl?

Or, to put it more generally: How can you utilize a third-party library's embedded logging and debug statements in Log::Log4perl? How can you make them print to configurable appenders, turn them on and off, just as if they were regular Log::Log4perl logging statements?

The easiest solution is to map the third-party library logging statements to Log::Log4perl's stealth loggers via a typeglob assignment.

As an example, let's take LWP, one of the most popular Perl modules, which makes handling WWW requests and responses a breeze. Internally, LWP uses its own logging and debugging system, utilizing the following calls inside the LWP code (from the LWP::Debug man page):

    # Function tracing
LWP::Debug::trace('send()');
    # High-granular state in functions
LWP::Debug::debug('url ok');
    # Data going over the wire
LWP::Debug::conns("read $n bytes: $data");

First, let's assign Log::Log4perl priorities to these functions: I'd suggest that debug() messages have priority "INFO", trace() uses "DEBUG" and conns() also logs with "DEBUG" -- although your mileage may certainly vary.

Now, in order to transparently hook up LWP::Debug with Log::Log4perl, all we have to do is say

package LWP::Debug;
use Log::Log4perl qw(:easy);
*trace = *INFO;
*conns = *DEBUG;
*debug = *DEBUG;
package main;
# ... go on with your regular program ...

at the beginning of our program. In this way, every time the, say, "LWP::UserAgent" module calls LWP::Debug::trace(), it will implicitly call INFO(), which is the info() method of a stealth logger defined for the Log::Log4perl category "LWP::Debug". Is this cool or what?

Here's a complete program:

use LWP::UserAgent;
use HTTP::Request::Common;
use Log::Log4perl qw(:easy);
Log::Log4perl->easy_init(
    { category => "LWP::Debug",
      level    => $DEBUG,
      layout   => "%r %p %M-%L %m%n",
    });
package LWP::Debug;
use Log::Log4perl qw(:easy);
*trace = *INFO;
*conns = *DEBUG;
*debug = *DEBUG;
package main;
my $ua = LWP::UserAgent->new();
my $resp = $ua->request(GET "http://amazon.com");
if($resp->is_success()) {
    print "Success: Received ",
          length($resp->content()), "\n";
} else {
    print "Error: ", $resp->code(), "\n";
}

What if I need dynamic values in a static Log4perl configuration file?

Say, your application uses Log::Log4perl for logging and therefore comes with a Log4perl configuration file, specifying the logging behavior. But, you also want it to take command line parameters to set values like the name of the log file. How can you have both a static Log4perl configuration file and a dynamic command line interface?

As of Log::Log4perl 0.28, every value in the configuration file can be specified as a Perl hook. So, instead of saying 

log4perl.appender.Logfile.filename = test.log

you could just as well have a Perl subroutine deliver the value dynamically: 

log4perl.appender.Logfile.filename = sub { logfile(); };

given that logfile() is a valid function in your "main" package returning a string containing the path to the log file.

Or, think about using the value of an environment variable: 

log4perl.appender.DBI.user = sub { $ENV{USERNAME} };

When "Log::Log4perl->init()" parses the configuration file, it will notice the assignment above because of its "sub {...}" pattern and treat it in a special way: It will evaluate the subroutine (which can contain arbitrary Perl code) and take its return value as the right side of the assignment.

A typical application would be called like this on the command line: 

app                # log file is "test.log"
app -l mylog.txt   # log file is "mylog.txt"

Here's some sample code implementing the command line interface above: 

use Log::Log4perl qw(get_logger);
use Getopt::Std;
getopt('l:', \our %OPTS);
my $conf = q(
log4perl.category.Bar.Twix         = WARN, Logfile
log4perl.appender.Logfile          = Log::Log4perl::Appender::File
log4perl.appender.Logfile.filename = sub { logfile(); };
log4perl.appender.Logfile.layout   = SimpleLayout
);
Log::Log4perl::init($conf);
my $logger = get_logger("Bar::Twix");
$logger->error("Blah");
###########################################
sub logfile {
###########################################
    if(exists $OPTS{l}) {
        return $OPTS{l};
    } else {
        return "test.log";
    }
}

Every Perl hook may contain arbitrary perl code, just make sure to fully qualify eventual variable names (e.g. %main::OPTS instead of %OPTS).

SECURITY NOTE: this feature means arbitrary perl code can be embedded in the config file. In the rare case where the people who have access to your config file are different from the people who write your code and shouldn't have execute rights, you might want to call 

$Log::Log4perl::Config->allow_code(0);

before you call init(). This will prevent Log::Log4perl from executing any Perl code in the config file (including code for custom conversion specifiers (see "Custom cspecs" in Log::Log4perl::Layout::PatternLayout).

How can I roll over my logfiles automatically at midnight?

Long-running applications tend to produce ever-increasing logfiles. For backup and cleanup purposes, however, it is often desirable to move the current logfile to a different location from time to time and start writing a new one.

This is a non-trivial task, because it has to happen in sync with the logging system in order not to lose any messages in the process.

Luckily, Mark Pfeiffer's "Log::Dispatch::FileRotate" appender works well with Log::Log4perl to rotate your logfiles in a variety of ways.

Note, however, that having the application deal with rotating a log file is not cheap. Among other things, it requires locking the log file with every write to avoid race conditions. There are good reasons to use external rotators like "newsyslog" instead. See the entry "How can I rotate a logfile with newsyslog?" in the FAQ for more information on how to configure it.

When using "Log::Dispatch::FileRotate", all you have to do is specify it in your Log::Log4perl configuration file and your logfiles will be rotated automatically.

You can choose between rolling based on a maximum size ("roll if greater than 10 MB") or based on a date pattern ("roll everyday at midnight"). In both cases, "Log::Dispatch::FileRotate" allows you to define a number "max" of saved files to keep around until it starts overwriting the oldest ones. If you set the "max" parameter to 2 and the name of your logfile is "test.log", "Log::Dispatch::FileRotate" will move "test.log" to "test.log.1" on the first rollover. On the second rollover, it will move "test.log.1" to "test.log.2" and then "test.log" to "test.log.1". On the third rollover, it will move "test.log.1" to "test.log.2" (therefore discarding the old "test.log.2") and "test.log" to "test.log.1". And so forth. This way, there's always going to be a maximum of 2 saved log files around.

Here's an example of a Log::Log4perl configuration file, defining a daily rollover at midnight (date pattern "yyyy-MM-dd"), keeping a maximum of 5 saved logfiles around: 

log4perl.category         = WARN, Logfile
log4perl.appender.Logfile = Log::Dispatch::FileRotate
log4perl.appender.Logfile.filename    = test.log
log4perl.appender.Logfile.max         = 5
log4perl.appender.Logfile.DatePattern = yyyy-MM-dd
log4perl.appender.Logfile.TZ          = PST
log4perl.appender.Logfile.layout = \
    Log::Log4perl::Layout::PatternLayout
log4perl.appender.Logfile.layout.ConversionPattern = %d %m %n

Please see the "Log::Dispatch::FileRotate" documentation for details. "Log::Dispatch::FileRotate" is available on CPAN.

What's the easiest way to turn off all logging, even with a lengthy Log4perl configuration file?

In addition to category-based levels and appender thresholds, Log::Log4perl supports system-wide logging thresholds. This is the minimum level the system will require of any logging events in order for them to make it through to any configured appenders.

For example, putting the line 

log4perl.threshold = ERROR

anywhere in your configuration file will limit any output to any appender to events with priority of ERROR or higher (ERROR or FATAL that is).

However, in order to suppress all logging entirely, you need to use a priority that's higher than FATAL: It is 

log4perl.threshold = OFF

which will shut down all logging regardless of the configuration file's other settings.

Note that the OFF threshold is an invention of Log::Log4perl, and thus not part of the original Log4j specification.

simplemente llamado, y no se usa por ningún logger. Por definición, es mayor que el nivel de logger más alto definido. Por lo tanto, si mantienes la línea 
log4perl.threshold = OFF
en algún lugar de tu configuración de Log::Log4perl, el sistema será quieto como un cementerio. Si deactivas esa línea (por ejemplo, la comentas), el sistema, al re cargar la configuración, se volverá a operar normalmente, proporcionando mensajes de log según la restante configuración del archivo.

¿Cómo puedo registrar DEBUG y superior en la pantalla y INFO y superior en un archivo?

Necesitas un logger con dos appenders asociados:

log4perl.logger = DEBUG, Screen, File
log4perl.appender.Screen   = Log::Log4perl::Appender::Screen
log4perl.appender.Screen.layout = SimpleLayout
log4perl.appender.File   = Log::Log4perl::Appender::File
log4perl.appender.File.filename = test.log
log4perl.appender.File.layout = SimpleLayout
log4perl.appender.Screen.Threshold = INFO

Dado que el logger de archivo no debe recibir mensajes con prioridad menor a INFO, el ajuste del "Threshold" del appender bloquea esos mensajes, aunque el logger los dirija.

Es un fallo común pensar que puedes definir dos loggers para esto, pero no funcionará hasta que esos dos loggers tengan categorías distintas. Si quieres registrar todos los mensajes DEBUG y superior del módulo Foo::Bar a un archivo y todos los mensajes INFO y superior del módulo Quack::Schmack en la pantalla, podrías haber definido dos loggers con niveles distintos "log4perl.logger.Foo.Bar" (nivel INFO) y "log4perl.logger.Quack.Schmack" (nivel DEBUG) y asociar el appender de archivo al primero y el appender de pantalla al segundo. Pero lo que deseabas registrar era todos los mensajes, independientemente del módulo (o categoría) de donde vinieran, a ambos appenders. La única manera de registrar esto es definir el logger raíz con el nivel más bajo (DEBUG), asignar ambos appenders a él y bloquear los mensajes no deseados en el appender de archivo ("Threshold" configurado a INFO).

¡Sigo recibiendo mensajes de log duplicados! ¿Qué está mal?

Tener varias configuraciones para categorías relacionadas en el archivo de configuración de Log4perl puede provocar un fenómeno llamado "mensajes de log duplicados". Puede ser confuso al principio, pero si se analiza correctamente, se puede ver que Log4perl funciona como se esperaba. Sin embargo, no te preocupes, hay varias formas de evitar la duplicación de mensajes en tus logs.

Aquí hay un ejemplo de una configuración de Log4perl que produce este fenómeno:

log4perl.logger.Cat        = ERROR, Screen
log4perl.logger.Cat.Subcat = WARN, Screen
log4perl.appender.Screen   = Log::Log4perl::Appender::Screen
log4perl.appender.Screen.layout = SimpleLayout

Define dos loggers, uno para la categoría "Cat" y otro para "Cat::Subcat", que es una subcategoría de "Cat". El logger padre tiene un nivel de ERROR, mientras que el hijo está configurado a nivel WARN.

Imagina el siguiente código en tu programa:

my $logger = get_logger("Cat.Subcat");
$logger->warn("Warning!");

¿Qué crees que ocurrirá? Un usuario nuevo de Log4perl podría pensar: "El mensaje se está enviando con nivel WARN, por lo que el logger "Cat::Subcat" aceptará el mensaje y lo enviará a su appender asociado "Screen". Luego, el mensaje se desplazará por la jerarquía de loggers, encontrando el logger "Cat", que lo suprimirá debido a su nivel de ERROR." Pero, sorprendentemente, lo que obtendrás con el código anterior no es un mensaje, sino dos mensajes de log escritos en la pantalla:

WARN - Warning!
WARN - Warning!

¿Qué sucede? El culpable es que cuando el logger "Cat::Subcat" decide activarse, enviará el mensaje incondicionalmente a todos los appenders directamente o indirectamente asociados. El logger "Cat" nunca se preguntará si quiere el mensaje o no — el mensaje simplemente se envía a través del appender asociado a "Cat".

Una forma de evitar que el mensaje se desplace por la jerarquía de loggers es establecer el flag "additivity" del logger hijo a 0:

log4perl.logger.Cat            = ERROR, Screen
log4perl.logger.Cat.Subcat     = WARN, Screen
log4perl.additivity.Cat.Subcat = 0
log4perl.appender.Screen   = Log::Log4perl::Appender::Screen
log4perl.appender.Screen.layout = SimpleLayout

El mensaje será aceptado por el logger "Cat::Subcat", enviado a su appender, pero luego "Cat::Subcat" suprimirá cualquier acción adicional. Aunque este ajuste evita los mensajes duplicados como antes, a menudo no es el comportamiento deseado. Los mensajes que se desplazan por la jerarquía son una característica útil de Log4perl.

Si estás definiendo appenders diferentes para los dos loggers, otra opción es definir un umbral para el appender más alto. Aunque generalmente se establece igual al nivel del logger:

log4perl.logger.Cat           = ERROR, Screen1
log4perl.logger.Cat.Subcat    = WARN, Screen2
log4perl.appender.Screen1   = Log::Log4perl::Appender::Screen
log4perl.appender.Screen1.layout = SimpleLayout
log4perl.appender.Screen1.Threshold = ERROR
log4perl.appender.Screen2   = Log::Log4perl::Appender::Screen
log4perl.appender.Screen2.layout = SimpleLayout

Como el appender "Screen1" ahora bloquea todos los mensajes con prioridad menor que ERROR, incluso si el logger a cargo lo deja pasar, el mensaje que se desplaza por la jerarquía es bloqueado en el último momento y no se aplica al appender "Screen1".

Hasta ahora, hemos estado operando dentro de los límites del estándar Log4j, que Log4perl sigue. Sin embargo, si realmente quieres usar un único appender y mantener la percolación de mensajes sin tener que lidiar con la duplicación, hay una solución no estándar para ti:

log4perl.logger.Cat        = ERROR, Screen
log4perl.logger.Cat.Subcat = WARN, Screen
log4perl.appender.Screen   = Log::Log4perl::Appender::Screen
log4perl.appender.Screen.layout = SimpleLayout
log4perl.oneMessagePerAppender = 1

El flag "oneMessagePerAppender" suprimirá mensajes duplicados en el mismo appender. Aunque es no estándar, es muy útil.

¿Cómo puedo configurar Log::Log4perl para enviarme un correo electrónico si algo sucede?

Algunos incidentes requieren una acción inmediata. No puedes esperar hasta que alguien revise los archivos de log, necesitas recibir notificaciones en tu buscapersonas de inmediato.

La forma más fácil de lograr esto es utilizando el módulo "Log::Dispatch::Email::MailSend" como appender. El módulo viene con el bundle "Log::Dispatch" y permite que especifiques el destinatario y el asunto de los correos electrónicos en la configuración de Log4perl:

log4perl.category = FATAL, Mailer
log4perl.appender.Mailer         = Log::Dispatch::Email::MailSend
log4perl.appender.Mailer.to      = drone@pageme.net
log4perl.appender.Mailer.subject = Something's broken!
log4perl.appender.Mailer.layout  = SimpleLayout

Cada mensaje de incidente que este appender recibe se enviará a la dirección de correo especificada. Consulta la documentación del módulo "Log::Dispatch::Email::MailSend" para más detalles. Y asegúrate de que no se envíen demasiados correos electrónicos desde tu aplicación, llenando el buzón del destinatario.

Hay una pista que debes saber: la jerarquía de appenders de "Log::Dispatch::Email" se comporta con buffering por defecto. Esto significa que el appender no enviará mensajes de inmediato, sino que esperará hasta que alcance un umbral determinado. Si prefieres que las alertas se envíen inmediatamente, usa:

log4perl.appender.Mailer.buffered = 0

para desactivar el buffering.

Primero, Log::Log4perl viene con un conjunto de appenders estándar. Luego, hay muchos appenders compatibles con Log4perl disponibles en CPAN: simplemente ejecuta una búsqueda por "Log::Dispatch" en http://search.cpan.org y casi seguro que lo que estás buscando ya ha sido desarrollado, probado y utilizado exitosamente en producción — no necesitas reinventar la rueda.

Además, Log::Log4perl viene con un appender de base de datos llamado Log::Log4perl::Appender::DBI — pruébalo y verifica si quieres hablar con bases de datos.

Pero si estás dispuesto a una tarea realmente exótica, tal vez tengas que escribir un appender por ti mismo. Esto es muy fácil — solo tomará menos de un par de minutos.

Digamos que queríamos crear un appender de la clase "ColorScreenAppender", que registre mensajes en la pantalla en color configurable. Solo crea una nueva clase en "ColorScreenAppender.pm":

package ColorScreenAppender;

Ahora asume que tu archivo de configuración de Log::Log4perl "test.conf" tiene este aspecto:

log4perl.logger = INFO, ColorApp
log4perl.appender.ColorApp=ColorScreenAppender
log4perl.appender.ColorApp.color=blue
log4perl.appender.ColorApp.layout = PatternLayout
log4perl.appender.ColorApp.layout.ConversionPattern=%d %m %n

Esto causará que Log::Log4perl en init() busque una clase llamada ColorScreenAppender y llame a su constructor new(). Vamos a añadir new() a ColorScreenAppender.pm:

sub new {
    my($class, %options) = @_;
    my $self = { %options };
    bless $self, $class;
    return $self;
}

Por ejemplo, para implementar un appender que imprime mensajes en la consola en color azul, puede crear un módulo llamado Log/Log4perl/Appender/ColorScreen.pm con este contenido:

package Log::Log4perl::Appender::ColorScreen;
use strict;
use Log::Log4perl qw(:easy);
use base qw(Log::Log4perl::Appender);
sub new {
    my($class, %options) = @_;
    $class->SUPER::new(@_);
    $self->{color} = $options{color} || 'black';
    return $self;
}
sub log {
    my($self, %params) = @_;
    print colored($params{message},
                  $self->{color});
    return 1;
}
1;

Y luego configurarlo en su archivo Log4perl.conf como:

log4perl.rootLogger              = INFO, Screen
log4perl.appender.Screen         = Log::Log4perl::Appender::ColorScreen
log4perl.appender.Screen.color   = blue
log4perl.appender.Screen.layout  = PatternLayout
log4perl.appender.Screen.layout.ConversionPattern=%m%n

Como puede ver, el método new() recibe un hash de opciones, que puede usar para configurar el appender. En este caso, el color se puede establecer mediante la opción color.

El método log() recibe el mensaje que se va a registrar y, en este caso, lo imprime en la consola con el color especificado usando el módulo Term::ANSIColor.

¿Cómo puedo profundizar en las referencias antes de registrarlas?

Si tiene una referencia a una estructura o objeto anidado, es probable que no desee registrarla como HASH(0x81141d4), sino volcarla como algo similar a

$VAR1 = {
          'a' => 'b',
          'd' => 'e'
        };

a través de un módulo como Data::Dumper. Si bien es sintácticamente correcto decir

$logger->debug(Data::Dumper::Dumper($ref));

esta llamada impone una penalización de rendimiento enorme en su aplicación si el mensaje es suprimido por Log::Log4perl, porque Data::Dumper realizará sus costosas operaciones en cualquier caso, ya que no sabe que su salida será descartada inmediatamente.

A partir de Log::Log4perl 0.28, hay una mejor manera: use el formato de filtro de salida de mensajes como en

$logger->debug( {filter => \&Data::Dumper::Dumper,
                 value  => $ref} );

y Log::Log4perl no llamará a la función de filtro a menos que el mensaje realmente se escriba en un appender. Solo asegúrese de pasar toda la información como una referencia a un hash que especifique una función de filtro (como una referencia de subrutina) bajo la clave "filter" y el valor que se pasará a la función de filtro en "value"). Al registrar, Log::Log4perl llamará a la función de filtro, pasará el valor de "value" como argumento y registrará el valor de retorno. Le ahorra ciclos valiosos.

¿Cómo puedo recopilar todos los mensajes FATAL en un archivo de registro adicional?

Suponga que ha empleado Log4perl en todo su sistema y ya ha activado el registro en varios subsistemas. Además de eso, sin interrumpir ninguna otra configuración, ¿cómo puede recopilar todos los mensajes FATAL de todo el sistema y enviarlos a un archivo de registro separado?

Si define un logger raíz como este:

log4perl.logger                  = FATAL, File
log4perl.appender.File           = Log::Log4perl::Appender::File
log4perl.appender.File.filename  = /tmp/fatal.txt
log4perl.appender.File.layout    = PatternLayout
log4perl.appender.File.layout.ConversionPattern= %d %m %n
    # !!! Falta algo ...

Se sorprenderá al no solo recibir todos los mensajes FATAL emitidos en cualquier parte del sistema, sino también todo lo demás: ¡millones de mensajes ERROR, WARN, INFO e incluso DEBUG terminarán en su archivo de registro fatal.txt! La razón de esto es la aditividad del appender de Log4perl (o mejor dicho, de Log4j). Una vez que un logger de nivel inferior decide activarse, el mensaje se retransmitirá a todos los appenders ascendentes, sin más comprobaciones de prioridad con sus loggers adjuntos.

Sin embargo, hay una manera de evitar esto: si su appender define un umbral mínimo, solo los mensajes de esta prioridad o superior se registrarán. Por lo tanto, simplemente agregue

log4perl.appender.File.Threshold = FATAL

a la configuración anterior, y obtendrá lo que deseaba en primer lugar: un colector de mensajes FATAL de todo el sistema.

¿Cómo puedo agrupar varios mensajes de registro en uno solo?

¿Le gustaría contar los mensajes que llegan a su appender y volcar un resumen una vez que superan un cierto umbral? Para que algo como

$logger->error("Blah");
$logger->error("Blah");
$logger->error("Blah");

no se registre como

Blah
Blah
Blah

sino como

[3] Blah

en su lugar? Si desea posponer el registro de un mensaje hasta que se haya enviado un par de veces, puede implementarlo creando un appender con búfer.

Definamos un nuevo appender como

package TallyAppender;
sub new {
    my($class, %options) = @_;
    my $self = { maxcount => 5,
                 %options
               };
    bless $self, $class;
    $self->{last_message}        = "";
    $self->{last_message_count}  = 0;
    return $self;
}

con dos variables de instancia adicionales "last_message" y "last_message_count", que almacenan el contenido del último mensaje enviado y un contador de cuántas veces ha ocurrido esto. Además, presenta un parámetro de configuración "maxcount" que tiene un valor predeterminado de 5 en el fragmento anterior, pero se puede establecer en el archivo de configuración de Log4perl como esto:

log4perl.logger = INFO, A
log4perl.appender.A=TallyAppender
log4perl.appender.A.maxcount = 3

La lógica principal de conteo reside en el método "log" del appender, que se llama cada vez que Log4perl piensa que un mensaje debe ser registrado por nuestro appender:

sub log {
    my($self, %params) = @_;
        # ¿Mensaje cambiado? Imprime búfer.
    if($self->{last_message} and
       $params{message} ne $self->{last_message}) {
        print "[$self->{last_message_count}]: " .
              "$self->{last_message}";
        $self->{last_message_count} = 1;
        $self->{last_message} = $params{message};
        return;
    }
    $self->{last_message_count}++;
    $self->{last_message} = $params{message};
        # ¿Umbral superado? Imprime, reinicia contador
    if($self->{last_message_count} >=
       $self->{maxcount}) {
        print "[$self->{last_message_count}]: " .
              "$params{message}";
        $self->{last_message_count} = 0;
        $self->{last_message}       = "";
        return;
    }
}

Básicamente, solo verificamos si el mensaje entrante en $param{message} es igual a lo que hemos guardado antes en la variable de instancia "last_message". Si es así, estamos incrementando "last_message_count". Imprimimos el mensaje en dos casos: si el nuevo mensaje es diferente al almacenado en búfer, porque entonces necesitamos volcar lo antiguo y almacenar lo nuevo. O, si el contador supera el umbral, según lo definido por el parámetro de configuración "maxcount".

Tenga en cuenta que el appender siempre recibe el mensaje completamente renderizado y simplemente lo compara en su totalidad, por lo que si hay una fecha/hora, eso podría confundir su lógica. Puede sortear esto especificando %m %n como diseño y agregar la fecha más tarde en el appender. O, hacer que la comparación sea lo suficientemente inteligente como para omitir la fecha.

Finalmente, no olvide lo que sucede si el programa se está cerrando. Si todavía hay mensajes en el búfer, deberían imprimirse en ese momento. Eso es fácil de hacer en el método DESTROY del appender, que se llama en el momento de la destrucción del objeto:

sub DESTROY {
    my($self) = @_;
    if($self->{last_message_count}) {
        print "[$self->{last_message_count}]: " .
              "$self->{last_message}";
        return;
    }
}

Esto asegurará que ninguno de los mensajes en búfer se pierda. ¡Feliz almacenamiento en búfer!

¡Quiero registrar mensajes ERROR y WARN en archivos diferentes! ¿Cómo puedo hacerlo?

Supongamos que quería que cada declaración de registro se escribiera en un archivo diferente, según la prioridad de la declaración. Los mensajes con prioridad "WARN" deben ir a "/tmp/app.warn", los eventos priorizados como "ERROR" deberían terminar en "/tmp/app.error".

Ahora, si define dos appenders "AppWarn" y "AppError" y los asigna ambos al logger raíz, los mensajes que suban desde cualquier logger inferior serán registrados por ambos appenders debido a la característica de propagación de mensajes de Log4perl. Si limita su exposición a través del mecanismo de umbral del appender y establece el umbral de "AppWarn" en &q

Para sincronizar el acceso a un appender, puedes usar un filtro personalizado que asegure que solo un hilo escriba en el appender a la vez. Aquí te explicamos cómo implementarlo:

    use Log::Log4perl qw(:easy);
    Log::Log4perl::init( \ <<'EOT' );
        log4perl.logger             = INFO, A1
        log4perl.appender.A1        = Log::Log4perl::Appender::File
        log4perl.appender.A1.layout = \
            Log::Log4perl::Layout::PatternLayout
        log4perl.appender.A1.layout.ConversionPattern = %m%n
        log4perl.filter.M1 = Log::Log4perl::Filter::Mutex
        log4perl.filter.M1.MutexName = AppenderMutex
        log4perl.filter.M1.AcceptOnMatch = false
        log4perl.appender.A1.Filter = M1
EOT

El filtro utiliza un mutex llamado "AppenderMutex" para asegurar que solo un hilo escriba en el appender a la vez. El parámetro "AcceptOnMatch" se establece en "false" para suprimir el mensaje cuando el mutex está bloqueado.

Para suprimir la advertencia sobre sistemas de registro no inicializados, puedes añadir el objetivo ":nowarn" a la llamada del módulo "use Log::Log4perl":

use Log::Log4perl qw(get_logger :nowarn);

Esto asegurará que Log::Log4perl ignore silenciosamente las declaraciones de registro si no se ha realizado ninguna inicialización. Si estás utilizando la API de Log4perl para definir loggers y appenders, la misma notificación ocurre si no se realiza ninguna llamada a "add_appenders()", es decir, si no se definen appenders.

¿Cómo sincronizo el acceso a un appender?

Si está utilizando la misma instancia de un appender en varios procesos y cada proceso está pasando mensajes al appender en paralelo, podría terminar con entradas de registro superpuestas.

Los escenarios típicos incluyen un appender de archivo que crea en el programa principal y que luego se compartirá entre el proceso padre y un proceso hijo bifurcado. O dos procesos separados, cada uno inicializando un appender de archivo Log4perl en el mismo archivo de registro.

Log::Log4perl no sincronizará el acceso al archivo de registro compartido por defecto. Dependiendo del mecanismo de vaciado del sistema operativo, el tamaño del búfer y el tamaño de sus mensajes, existe una pequeña posibilidad de superposición.

La forma más fácil de evitar mensajes superpuestos en archivos de registro escritos por varios procesos es estableciendo el indicador "syswrite" del appender de archivo junto con un modo de escritura de archivo de "append". Esto asegura que "Log::Log4perl::Appender::File" utilice syswrite() (que garantiza ejecutarse sin interrupción) en lugar de print(), que podría almacenar en búfer el mensaje o ser interrumpido por el sistema operativo mientras escribe. Y en modo "append", el kernel del sistema operativo garantiza que varios procesos compartan un único marcador de fin de archivo, asegurando que cada proceso escriba en el final *real* del archivo. (El valor de "append" para el parámetro "mode" es la configuración predeterminada en el appender de archivo de Log4perl, por lo que no necesita establecerlo explícitamente).

  # Garantiza escrituras atómicas
log4perl.category.Bar.Twix          = WARN, Logfile
log4perl.appender.Logfile           = Log::Log4perl::Appender::File
log4perl.appender.Logfile.mode      = append
log4perl.appender.Logfile.syswrite  = 1
log4perl.appender.Logfile.filename  = test.log
log4perl.appender.Logfile.layout    = SimpleLayout

Otra forma garantizada de tener mensajes separados con cualquier tipo de appender es colocando un appender compuesto Log::Log4perl::Appender::Synchronized entre Log::Log4perl y el appender real. Se asegurará de que los mensajes pasen por esta puerta virtual de uno en uno solamente.

Aquí hay una configuración de ejemplo para sincronizar el acceso a un appender de archivo:

log4perl.category.Bar.Twix          = WARN, Syncer
log4perl.appender.Logfile           = Log::Log4perl::Appender::File
log4perl.appender.Logfile.autoflush = 1
log4perl.appender.Logfile.filename  = test.log
log4perl.appender.Logfile.layout    = SimpleLayout
log4perl.appender.Syncer            = Log::Log4perl::Appender::Synchronized
log4perl.appender.Syncer.appender   = Logfile

"Log::Log4perl::Appender::Synchronized" utiliza el módulo "IPC::Shareable" y sus semáforos, lo que ralentizará la escritura de los mensajes de registro, pero garantiza un acceso secuencial con comprobaciones atómicas. Consulte Log::Log4perl::Appender::Synchronized para obtener más detalles.

¿Cómo ejecuto Log::Log4perl bajo mod_perl?

En entornos persistentes, es importante seguir las reglas descritas en la sección "Inicializar una y solo una vez" en Log::Log4perl. Si aún no lo ha leído, por favor, hágalo ahora mismo. Es muy importante.

Y no importa si usa un manejador de inicio para init() Log::Log4perl o usa la estrategia init_once() (añadida en 0.42), de cualquier manera es muy probable que tenga escrituras no sincronizadas en los archivos de registro.

Si Log::Log4perl está configurado con un appender de archivo de registro y se inicializa a través del manejador de inicio de Apache, el descriptor de archivo creado inicialmente se compartirá entre todos los procesos de Apache. De manera similar, con el enfoque init_once(): aunque cada proceso tiene una configuración L4p separada, los procesos compartirán los *nombres* del archivo del appender, abriendo efectivamente varios descriptores de archivo diferentes en el mismo archivo.

  • Use el appender Log::Log4perl::Appender::Synchronized para conectarse a sus appenders de archivo. Aquí está la explicación: http://log4perl.sourceforge.net/releases/Log-Log4perl/docs/html/Log/Log4perl/FAQ.html#23804
  • Use un archivo de registro diferente para cada proceso como en

Mi programa ya usa warn() y die(). ¿Cómo cambio a Log4perl?

Si su programa ya utiliza la función warn() de Perl para emitir mensajes de error y desea canalizarlos al mundo Log4perl, simplemente defina un manejador "__WARN__" donde resida su programa o módulo:

use Log::Log4perl qw(:easy);
$SIG{__WARN__} = sub {
    local $Log::Log4perl::caller_depth =
        $Log::Log4perl::caller_depth + 1;
    WARN @_;
};

¿Por qué la configuración "local" de $Log::Log4perl::caller_depth? Si deja eso fuera, los especificadores de conversión de "PatternLayout" como %M o %F (que imprimen la función/método actual y el nombre del archivo fuente) se referirán a dónde reside el manejador __WARN__, no al entorno desde donde se emitió la función warn() de Perl. Incrementar "caller_depth" ajusta este desfase. Tenerlo "local" asegura que el nivel se restablezca después de que el manejador salga.

Una vez hecho esto, si su programa hace algo como

sub some_func {
    warn "Aquí hay una advertencia";
}

obtendrá (dependiendo de su configuración de Log::Log4perl) algo como

2004/02/19 20:41:02-main::some_func: Aquí hay una advertencia en ./t línea 25.

en el appender apropiado en lugar de tener una pantalla llena de mensajes STDERR. También funciona con el módulo "Carp" y sus funciones carp() y cluck().

Si, por otro lado, es necesario capturar die() y similares, un manejador "__DIE__" es apropiado:

$SIG{__DIE__} = sub {
    if($^S) {
        # Estamos en un eval {} y no queremos registrar
        # este mensaje pero capturarlo más tarde
        return;
    }
    local $Log::Log4perl::caller_depth =
        $Log::Log4perl::caller_depth + 1;
    LOGDIE @_;
};

Esto llamará a la función LOGDIE() de Log4perl, que registrará un error fatal y luego llamará a die() internamente, provocando la salida del programa. Funciona igual de bien con "Carp" croak() y

confess() funciones.

Algun módulo imprime mensajes a STDERR. ¿Cómo puedo redirigirlos a Log::Log4perl?

Si un módulo que estás usando no utiliza Log::Log4perl pero imprime mensajes de registro a STDERR en su lugar, como

########################################
package IgnorantModule;
########################################
sub some_method {
    print STDERR "¡Parbleu! ¡Un error!\n";
}
1;

todavía hay una forma de capturar estos mensajes y redirigirlos a Log::Log4perl, incluso sin tocar el módulo. Lo que necesitas es un módulo "trapper" como

########################################
package Trapper;
########################################
use Log::Log4perl qw(:easy);
sub TIEHANDLE {
    my $class = shift;
    bless [], $class;
}
sub PRINT {
    my $self = shift;
    $Log::Log4perl::caller_depth++;
    DEBUG @_;
    $Log::Log4perl::caller_depth--;
}
1;

y un comando "tie" en el programa principal para vincular STDERR al módulo "trapper" junto con la inicialización regular de Log::Log4perl:

########################################
package main;
########################################
use Log::Log4perl qw(:easy);
Log::Log4perl->easy_init(
    {level  => $DEBUG,
     file   => 'stdout',   # ¡asegúrate de no usar stderr aquí!
     layout => "%d %M: %m%n",
    });
tie *STDERR, "Trapper";

Asegúrate de no usar STDERR como el "appender" de archivo de Log::Log4perl aquí (que sería el valor predeterminado en el modo ":easy"), porque terminaría en una recursión infinita.

Ahora, al llamar

IgnorantModule::some_method();

resultará en la salida deseada

2004/05/06 11:13:04 IgnorantModule::some_method: ¡Parbleu! ¡Un error!

¿Por qué PAR (Perl Archive Toolkit) crea ejecutables que luego no pueden encontrar sus "appenders" de Log::Log4perl?

Si no se indica lo contrario, "Log::Log4perl" carga dinámicamente las clases de "appender" que se encuentran en su configuración. Si especificas

#!/usr/bin/perl
# mytest.pl
use Log::Log4perl qw(get_logger);
my $conf = q(
  log4perl.category.Bar.Twix = WARN, Logfile
  log4perl.appender.Logfile  = Log::Log4perl::Appender::Screen
  log4perl.appender.Logfile.layout = SimpleLayout
);
Log::Log4perl::init(\$conf);
my $logger = get_logger("Bar::Twix");
$logger->error("Blah");

entonces "Log::Log4perl::Appender::Screen" se cargará mientras el programa se ejecuta, no en tiempo de compilación. Si usas PAR para compilar el script anterior en un ejecutable binario a través de

pp -o mytest mytest.pl

y luego ejecutas "mytest" en una máquina sin tener instalado Log::Log4perl, obtendrás un mensaje de error como

ERROR: can't load appenderclass 'Log::Log4perl::Appender::Screen'
Can't locate Log/Log4perl/Appender/Screen.pm in @INC ...

¿Por qué? En tiempo de compilación, "pp" no se dio cuenta de que "Log::Log4perl::Appender::Screen" se necesitaría más tarde y no lo incluyó en el ejecutable creado. Para evitar esto, ya sea di "use Log::Log4perl::Appender::Screen" explícitamente en el script o compílalo con

pp -o mytest -M Log::Log4perl::Appender::Screen mytest.pl

para asegurarte de que la clase del "appender" se incluya.

¿Cómo puedo acceder a un "appender" personalizado definido en la configuración?

Cualquier "appender" definido en el archivo de configuración o en algún lugar del código puede ser accedido más tarde a través de "Log::Log4perl->appender_by_name("nombre_del_appender")", lo que devuelve una referencia al objeto "appender".

Una vez que tienes el objeto, puede ser consultado o modificado a tu gusto. Por ejemplo, mira el "appender" personalizado "IndentAppender" definido a continuación: Después de llamar a init() para definir la configuración de Log4perl, el objeto "appender" se recupera para llamar a sus métodos indent_more() y indent_less() para controlar la indentación de los mensajes:

package IndentAppender;
sub new {
    bless { indent => 0 }, $_[0];
}
sub indent_more  { $_[0]->{indent}++ }
sub indent_less  { $_[0]->{indent}-- }
sub log {
    my($self, %params) = @_;
    print " " x $self->{indent}, $params{message};
}
package main;
use Log::Log4perl qw(:easy);
my $conf = q(
log4perl.category          = DEBUG, Indented
log4perl.appender.Indented = IndentAppender
log4perl.appender.Indented.layout = Log::Log4perl::Layout::SimpleLayout
);
Log::Log4perl::init(\$conf);
my $appender = Log::Log4perl->appender_by_name("Indented");
DEBUG "Sin indentación";
$appender->indent_more();
DEBUG "Una más";
$appender->indent_more();
DEBUG "Dos más";
$appender->indent_less();
DEBUG "Una menos";

Como esperarías, esto imprimirá

DEBUG - Sin indentación
 DEBUG - Una más
  DEBUG - Dos más
 DEBUG - Una menos

porque el propio "appender" utilizado por Log4perl se modifica dinámicamente en tiempo de ejecución.

No sé si Log::Log4perl está instalado. ¿Cómo puedo preparar mi script?

En caso de que tu script deba ser preparado para entornos que puedan o no tener Log::Log4perl instalado, hay un truco.

Si colocas los siguientes bloques BEGIN en la parte superior del programa, podrás usar las macros DEBUG(), INFO(), etc. en el modo ":easy" de Log::Log4perl. Si Log::Log4perl está instalado en el entorno de destino, se aplicarán las reglas normales de Log::Log4perl. Si no, todos los DEBUG(), INFO(), etc. se "sustituirán", es decir, se convertirán en no-ops (operaciones nulas):

use warnings;
use strict;
BEGIN {
    eval { require Log::Log4perl; };
    if($@) {
        print "Log::Log4perl no está instalado - sustituyendo.\n";
        no strict qw(refs);
        *{"main::$_"} = sub { } for qw(DEBUG INFO WARN ERROR FATAL);
    } else {
        no warnings;
        print "Log::Log4perl está instalado - todo bien.\n";
        require Log::Log4perl::Level;
        Log::Log4perl::Level->import(__PACKAGE__);
        Log::Log4perl->import(qw(:easy));
        Log::Log4perl->easy_init($main::DEBUG);
    }
}
    # El script regular comienza...
DEBUG "¡Ey!";

Este fragmento primero buscará Log::Log4perl y, si no lo puede encontrar, creará alias para DEBUG(), INFO() con subrutinas vacías a través de "typeglobs". Si Log::Log4perl está disponible, sus constantes de nivel se importarán primero ($DEBUG, $INFO, etc.) y luego se llamará a easy_init() para inicializar el sistema de registro.

¿Pueden los "appenders" de archivo crear archivos con permisos diferentes?

Típicamente, cuando "Log::Log4perl::Appender::File" crea un archivo nuevo, sus permisos se establecen en "rw-r--r--". ¿Por qué? Porque el umask de tu entorno probablemente tenga como valor predeterminado 0022, esa es la configuración estándar.

¿Qué es un umask, preguntas? Es una plantilla que se aplica a los permisos de todos los archivos recién creados. Mientras que llamadas como "open(FILE, ">foo")" siempre intentarán crear archivos en modo "rw-rw-rw- ", el sistema aplicará la plantilla umask actual para determinar la configuración de permisos final. El umask es una máscara de bits que se invierte y luego se aplica a la configuración de permisos solicitada, usando un AND a nivel de bits:

$request_permission &~ $umask

Por lo tanto, una configuración de umask de 0000 (el 0 inicial simplemente indica un valor octal) creará archivos en modo "rw-rw-rw-", una configuración de 0277 usará "r--------", y el estándar 0022 usará "rw-r--r--".

Como ejemplo, si deseas que tus archivos de registro se creen con permisos "rw-r--rw-", usa un umask de 0020 antes de llamar a Log::Log4perl->init():

use Log::Log4perl;
umask 0020;
    # Crea log.out en modo rw-r--rw
Log::Log4perl->init(\ q{
    log4perl.logger = WARN, File
    log4perl.appender.File = Log::Log4perl::Appender::File
    log4perl.appender.File.filename = log.out
    log4perl.appender.File.layout = SimpleLayout
});

¡Usar Log4perl en un bloque END causa un problema!

No es fácil llegar a este error, pero si escribes algo como

END { Log::Log4perl::get_logger()->debug("Hola."); }
use Log::Log4perl qw(:easy);
Log::Log4perl->easy_init($DEBUG);

no funcionará. La razón es que "Log::Log4perl" define un bloque END que limpia todos los loggers. Y perl ejecutará los bloques END en el orden inverso a como se encuentran en la fase de compilación, por lo que en el escenario anterior, el bloque END se ejecutará *después* de que Log4perl haya limpiado sus loggers.

Colocar bloques END que usan Log4perl *después* de una sentencia "use Log::Log4perl" soluciona el problema:

use Log::Log4perl qw(:easy);
Log::Log4perl->easy_init($DEBUG);
END { Log::Log4perl::get_logger()->debug("Hola."); }

En este escenario, el bloque END mostrado se ejecuta *antes* de que Log4perl limpie y el mensaje de depuración se procesará correctamente.

¡Ayuda! ¡Mi "appender" está lanzando una advertencia de "Wide character in print"!

Advertencias de Unicode

Este aviso se muestra cuando se imprimen cadenas de Unicode sin prevención. El aviso se elimina si el appender que se queja está configurado en modo utf-8:

    # Ya sea en el archivo de configuración de log4perl:
log4perl.appender.Logfile.filename = test.log
log4perl.appender.Logfile.utf8     = 1
    # O, en modo fácil:
Log::Log4perl->easy_init( {
  level => $DEBUG,
  file  => ":utf8> test.log"
} );

Si el appender que se queja es un appender de pantalla, establece la opción "utf8":

log4perl.appender.Screen.stderr = 1
log4perl.appender.Screen.utf8   = 1

Alternativamente, "binmode" hace el truco:

  # Ya sea STDOUT ...
binmode(STDOUT, ":utf8);
  # ... o STDERR.
binmode(STDERR, ":utf8);

Algunos detalles sobre esto: Las cadenas de Perl son ya sea cadenas de byte o cadenas Unicode. "Mike" es una cadena de byte. "\x{30DE}\x{30A4}\x{30AF}" es una cadena Unicode. Las cadenas Unicode se marcan de forma especial y se codifican internamente en UTF-8.

Si imprimes una cadena de byte en STDOUT, todo está bien, porque STDOUT está por defecto en modo de byte. Sin embargo, si imprimes una cadena Unicode en STDOUT sin prevención, "perl" intentará transformar la cadena Unicode de vuelta a una cadena de byte antes de imprimirla. Esto puede ser problemático si la cadena Unicode contiene caracteres 'estrechos' que no pueden representarse en Latin-1.

Por ejemplo, si creas una cadena Unicode con tres caracteres de Katakana japoneses como en:

perl -le 'print "\x{30DE}\x{30A4}\x{30AF}"'

(pronunciado casualmente Ma-i-ku, la pronunciación japonesa de "Mike"), STDOUT está en modo de byte y el aviso:

Wide character in print at ./script.pl line 14.

se muestra. Configurando STDOUT en modo UTF-8 como en:

perl -le 'binmode(STDOUT, ":utf8"); print "\x{30DE}\x{30A4}\x{30AF}"'

imprime silenciosamente la cadena Unicode en UTF-8. Para ver los caracteres impuestos, necesitas un terminal UTF-8 con una fuente que incluya caracteres de Katakana japoneses.

¿Cómo puedo enviar errores a la pantalla y mensajes de depuración a un archivo?

Supongamos que quieres mantener un output de DEBUG detallado en un archivo y solo mensajes de nivel ERROR y superiores se impriman en la pantalla. A menudo, los desarrolladores crean algo así:

 # Incorrecto!!!
log4perl.logger = DEBUG, FileApp
log4perl.logger = ERROR, ScreenApp
 # Incorrecto!!!

Esto no funcionará. Las definiciones de logger no son aditivas, y la segunda declaración sobrescribirá la primera. Las versiones de Log4perl anteriores a 1.04 aceptaban esto silenciosamente, dejando a los usuarios confundidos porque no funcionaba como esperaban. A partir de la 1.04, esto lanzará un error fatal para notificar del problema.

Lo que deseas hacer en su lugar es esto:

log4perl.logger                    = DEBUG, FileApp, ScreenApp
log4perl.appender.FileApp          = Log::Log4perl::Appender::File
log4perl.appender.FileApp.filename = test.log
log4perl.appender.FileApp.layout   = SimpleLayout
log4perl.appender.ScreenApp          = Log::Log4perl::Appender::Screen
log4perl.appender.ScreenApp.stderr   = 0
log4perl.appender.ScreenApp.layout   = SimpleLayout
   ### Limitando la salida a mensajes de nivel ERROR
log4perl.appender.ScreenApp.Threshold = ERROR
   ###

Nota que sin la definición de "Threshold" del segundo appender, ambos appenders recibirían todos los mensajes con prioridad DEBUG y superiores. Con el umbral establecido en ERROR, el segundo appender filtrará los mensajes según sea necesario.

¿Dónde debo colocar mis archivos de registro?

Los archivos de registro pueden estar en cualquier lugar que desees, pero el usuario efectivo del proceso que los llama debe tener permisos de escritura.

Si el archivo de registro no existe al iniciar el programa, el appender de archivo de Log4perl creará el archivo. Para esto, necesita permisos de escritura en el directorio donde se ubicará el nuevo archivo. Si el archivo de registro ya existe al iniciar el programa, el proceso simplemente necesita permisos de escritura en el archivo. Debes tener permisos de escritura en el directorio del archivo si estás experimentando situaciones donde el archivo de registro se recree, por ejemplo, durante la rotación de logs.

Si Log::Log4perl es usado por un servidor web (por ejemplo, en un script CGI o mod_perl), entonces el usuario del servidor (generalmente "nobody" o "www") debe tener los permisos mencionados anteriormente.

Para preparar tu servidor web para usar log4perl, te recomendamos:

webserver:~$ su -
webserver:~# mkdir /var/log/cgiapps
webserver:~# chown nobody:root /var/log/cgiapps/
webserver:~# chown nobody:root -R /var/log/cgiapps/
webserver:~# chmod 02755 -R /var/log/cgiapps/

Luego, configura tu archivo /etc/log4perl.conf incluyendo:

log4perl.appender.FileAppndr1.filename =
    /var/log/cgiapps/<app-name>.log

¿Cómo puede mi appender de archivo manejar archivos de registro desaparecidos?

El appender de archivo que viene con Log4perl, Log::Log4perl::Appender::File, abre un archivo especificado en el momento de la inicialización y escribirá continuamente en él a través de un archivo de respaldo.

En caso de que el archivo asociado haya sido eliminado, los mensajes escritos por un proceso largo aún se escribirán en el archivo de respaldo. Si el archivo ha sido movido a una ubicación diferente en el mismo sistema de archivos, el escritor continuará escribiendo bajo el nuevo nombre de archivo. Si el archivo ha sido eliminado del sistema de archivos, los mensajes se pondrán en el lugar desconocido. Esto no es un error en Log4perl, es simplemente cómo funciona Unix. No hay mensaje de error en este caso, porque el escritor no sabe que el archivo de respaldo no está asociado con un archivo visible.

Para evitar la pérdida de mensajes de registro cuando los archivos de registro desaparecen, la opción "recreate" del appender de archivo debe configurarse a un valor verdadero:

log4perl.appender.Logfile.recreate = 1

Esto instruirá al appender de archivo para verificar periódicamente (por defecto: 30 segundos) si el archivo de registro aún existe. Si encuentra que el archivo no existe, lo recreará.

Verificar constantemente si el archivo de registro aún existe es bastante costoso. Por eso, se realiza solo cada 30 segundos. Para cambiar este intervalo, la opción "recreate_check_interval" puede configurarse en segundos entre las verificaciones. En el caso extremo donde la verificación debe realizarse antes de cada escritura, puede incluso configurarse a 0:

log4perl.appender.Logfile.recreate = 1
log4perl.appender.Logfile.recreate_check_interval = 0

Para evitar tener que verificar el sistema de archivos con tanta frecuencia, se puede instalar un manejador de señales:

log4perl.appender.Logfile.recreate = 1
log4perl.appender.Logfile.recreate_check_signal = USR1

Esto instalará un manejador de señales que recreará un archivo de registro desaparecido inmediatamente cuando reciba la señal definida.

Nota: El método init_and_watch() de Log4perl también puede ser instruido para instalar un manejador de señales, usualmente usando la señal HUP. Asegúrate de usar una señal diferente si estás utilizando ambas simultáneamente.

¿Cómo puedo rotar un archivo de registro con newsyslog?

A continuación, se presentan algunos puntos que se deben considerar al utilizar la utilidad de rotación de archivos popular "newsyslog" (http://www.courtesan.com/newsyslog) con el appender de archivo de Log4perl en procesos largos.

Por ejemplo, con una configuración de newsyslog como esta:

# newsyslog.conf
/tmp/test.log 666  12  5  *  B

y con una llamada a:

# newsyslog -f /path/to/newsyslog.conf

"newsyslog" tomará acción si "/tmp/test.log" es mayor que el tamaño especificado de 5K. Moverá el archivo de registro actual "/tmp/test.log" a "/tmp/test.log.0" y creará un nuevo y vacío "/tmp/test.log" con los permisos especificados (por eso "newsyslog" necesita ejecutarse como root). Un archivo ya existente "/tmp/test.log.0" sería movido a "/tmp/test.log.1", "/tmp/test.log.1" a "/tmp/test.log.2", y así sucesivamente, para cada uno de un máximo de 12 archivos archivados configurados en "newsyslog.conf".

Aunque se ha creado un nuevo archivo, desde el punto de vista del appender de Log4perl, esta situación es idéntica a la descrita en el FAQ anterior, titulada "How can my file appender deal with disappearing log files".

Para asegurar que los mensajes de registro se escriban en el nuevo archivo de registro y no en uno archivado o se pierdan en el lugar desconocido, el appender debe configurarse para manejar el caso de archivo desaparecido.

La situación se vuelve interesante cuando "newsyslog" tiene la opción de comprimir archivos archivados activada. Esto hace que el archivo original no se mueva, sino que desaparezca. Si el appender no está configurado para recrear el archivo en este caso, los mensajes de registro se perderán sin previo aviso. Esto también se aplica al intervalo de tiempo "recreate_check_interval" segundos entre las verificaciones del creador.

Para asegurar que no se pierdan mensajes, una opción es establecer el intervalo en:

log4perl.appender.Logfile.recreate_check_interval = 0

Sin embargo, esto es bastante costoso. Una mejor opción es definir un manejador de señales:

log4perl.appender.Logfile.recreate = 1
log4perl.appender.Logfile.recreate_check_signal  = USR1
log4perl.appender.Logfile.recreate_pid_write = /tmp/myappid

Como servicio para los usuarios de "newsyslog", el appender de Log4perl escribe el identificador del proceso actual en un archivo PID especificado por la opción "recreate_pid_write". "newsyslog" debe ser configurado como:

# newsyslog.conf

Cómo un proceso bajo el usuario id A puede loggear a un archivo bajo el usuario id B?

Este escenario suele ocurrir en configuraciones donde los procesos se ejecutan bajo diversos IDs de usuario, pero necesitan escribir a un archivo que se encuentra bajo un ID de usuario fijo pero diferente.

Con un appender tradicional, el archivo de registro probablemente se creará bajo el ID de usuario de uno y se agregará bajo otro. Con un umask típico de 0002, el archivo se creará con permisos -rw-rw-r--. Si un usuario que no esté en el grupo del primer usuario agrega al archivo de registro, fallará debido a un problema de permisos.

Dos soluciones posibles son:

  • Crear el archivo con umask 0000 permitirá a todos los usuarios agregar al archivo de registro. El appender de Log4perl Log::Log4perl::Appender::File tiene una opción umask que puede configurarse para soportar esto:
    • log4perl.appender.File = Log::Log4perl::Appender::File
log4perl.appender.File.umask = sub { 0000 };

    De esta manera, el archivo de registro se creará con permisos -rw-rw-rw- y así tendrá permisos de escritura global. Esto podría abierta la carpeta de registro para manipulaciones no deseadas por usuarios arbitrarios, aunque sea.

  • Arrancar el proceso bajo el usuario effective de root permitirá que escriba al archivo de registro, sin importar quién arrancó el proceso. Sin embargo, esto no es una buena idea debido a las preocupaciones de seguridad.

Afortunadamente, bajo Unix, hay el servicio syslog que ejecuta como root y recibe solicitudes de procesos de usuario sobre un socket, escribiendo los mensajes en archivos de registro configurados en "/etc/syslog.conf".

Modificando "/etc/syslog.conf" y ejecutando HUP al servicio syslog, puedes configurar nuevos archivos de registro:

# /etc/syslog.conf
...
user.* /some/path/file.log

Usando el appender Log::Dispatch::Syslog, que viene con la distribución Log::Log4perl, puedes enviar mensajes a través del syslog:

use Log::Log4perl qw(:easy);
Log::Log4perl->init(\<<EOT);
    log4perl.logger = DEBUG, app
    log4perl.appender.app=Log::Dispatch::Syslog
    log4perl.appender.app.Facility=user
    log4perl.appender.app.layout=SimpleLayout
EOT
    # Escribir en /some/path/file.log
ERROR "Message!";

De esta manera, el servicio syslog resolverá el problema de permisos.

Nota que aunque es posible usar syslog() sin Log4perl (el syslog soporta niveles de log), las configuraciones tradicionales tienen un drawback significativo.

Sin la capacidad de Log4perl activar el logging en solo partes específicas del sistema, sistemas complejos dispararán eventos de log en todos los lugares y lento en niveles de depuración altos.

Controlar el logging en las partes jerárquicas de una aplicación mediante categorías de Log4perl es una de sus características más destacadas. Permite activar niveles de depuración altos en áreas específicas sin impacto significativo en el rendimiento.

Quiero usar UTC en lugar del tiempo local!

Si un layout define un fecha, Log::Log4perl usa el tiempo local para llenarla. Si quieres usar UTC en lugar, establece:

log4perl.utcDateTimes = 1

en tu configuración. Alternativamente, puedes establecer:

$Log::Log4perl::DateFormat::GMTIME = 1;

en tu programa antes de la primera declaración de log.

Puede Log4perl interceptar mensajes escritos a un filehandle?

Tienes una función que imprime a un filehandle. Quieres interceptar los mensajes que llegan a ese filehandle y los dirijir a un logger de Log4perl.

Primero, escribir un paquete que une un filehandle y lo dirija a un logger de Log4perl:

package FileHandleLogger;
use Log::Log4perl qw(:levels get_logger);
sub TIEHANDLE {
   my($class, %options) = @_;
   my $self = {
       level    => $DEBUG,
       category => '',
       %options
   };
   $self->{logger} = get_logger($self->{category}),
   bless $self, $class;
}
sub PRINT {
    my($self, @rest) = @_;
    $Log::Log4perl::caller_depth++;
    $self->{logger}->log($self->{level}, @rest);
    $Log::Log4perl::caller_depth--;
}
sub PRINTF {
    my($self, $fmt, @rest) = @_;
    $Log::Log4perl::caller_depth++;
    $self->PRINT(sprintf($fmt, @rest));
    $Log::Log4perl::caller_depth--;
}
1;

Ahora, si tienes una función como:

sub function_printing_to_fh {
    my($fh) = @_;
    printf $fh "Hi there!\n";
}

que toma un filehandle y imprime algo en él, se puede usar con Log4perl:

use Log::Log4perl qw(:easy);
usa FileHandleLogger;
Log::Log4perl->easy_init($DEBUG);
tie *SOMEHANDLE, 'FileHandleLogger' or
    die "tie failed ($!)";
function_printing_to_fh(*SOMEHANDLE);
    # imprime "2007/03/22 21:43:30 Hi there!"

Si quieres, puedes especificar un nivel de log diferente o categoría:

tie *SOMEHANDLE, 'FileHandleLogger',
    level => $INFO, category => "Foo::Bar" or die "tie failed ($!)";

Quiero mensajes multilinees renderizados línea por línea!

Con el estándar "PatternLayout", si envías un mensaje multilinee a un appender como:

use Log::Log4perl qw(:easy);
Log

se renderiza así:

2007/04/04 23:23:39 multi
line
message

Si quieres que cada línea se renderice según el layout, usa "Log::Log4perl::Layout::PatternLayout::Multiline":

use Log::Log4perl qw(:easy);
Log::Log4perl->init(\<<EOT);
  log4perl.category         = DEBUG, Screen
  log4perl.appender.Screen = Log::Log4perl::Appender::Screen
  log4perl.appender.Screen.layout = \\
    Log::Log4perl::Layout::PatternLayout::Multiline
  log4perl.appender.Screen.layout.ConversionPattern = %d %m %n
EOT
DEBUG "some\nmultiline\nmessage";

y obtendrás:

2007/04/04 23:23:39 some
2007/04/04 23:23:39 multiline
2007/04/04 23:23:39 message

en lugar.

Log4perl se queja de que no se realizó ninguna inicialización durante el cierre!

Si estás usando comandos de Log4perl en métodos DESTROY de tus objetos, podrás ver mensajes confusos como:

Log4perl: Seems like no initialization happened. Forgot to call init()? Use of uninitialized value in subroutine entry at
/home/y/lib/perl5/site_perl/5.6.1/Log/Log4perl.pm line 134 during global destruction. (in cleanup) Undefined subroutine &main:: called at
/home/y/lib/perl5/site_perl/5.6.1/Log/Log4perl.pm line 134 during global destruction.

cuando el programa cierra. ¿Qué es lo que está pasando?

Este fenómeno ocurre si tienes referencias circulares en tus objetos, que perl no puede limpiar cuando un objeto sale del ámbito pero espera hasta el cierre global. Sin embargo, en este momento, Log4perl ya ha cerrado, así que no puedes usarlo más.

Por ejemplo, aquí está una clase simple que usa un logger en su método DESTROY:

package A;
use Log::Log4perl qw(:easy);
sub new { bless {}, shift }
sub DESTROY { DEBUG "Waaah!"; }

Ahora, si el programa crea un objeto self-referencial, como:

package main;
use Log::Log4perl qw(:easy);
Log::Log4perl->easy_init($DEBUG);
my $a = A->new();
$a->{selfref} = $a;

entonces verás el mensaje mostrado anteriormente durante el cierre global. ¿Cómo resolver este problema?

Primero, deberías limpiar tus referencias circulares antes del cierre global. Estas no solo causan la destrucción de objetos en un orden difícil de predecir, sino también consumen memoria hasta que el programa se cierre.

Por lo tanto, el programa anterior podría fácilmente ser corregido con:

$a->{selfref} = undef;

al final o en un handler END. Si es difícil hacerlo, usa referencias débiles:

package main;
use Scalar::Util qw(weaken);
use Log::Log4perl qw(:easy);
Log::Log4perl->easy_init($DEBUG);
my $a = A->new();
$a->{selfref} = weaken $a;

esto permite a perl limpiar la referencia circular cuando el objeto sale del ámbito, sin esperar hasta el cierre global.

¿Cómo puedo acceder a los valores de POE heap desde el layout de Log4perl?

POE es un marco para crear aplicaciones multitareas que ejecutan en un solo proceso y un único hilo. Las equivalentes de hilos de POE son 'sessions' y, dado que ejecutan casi simultáneamente, no puedes usar el global NDC/MDC de Log4perl para almacenar datos específicos de sesión.

Sin embargo, POE ya mantiene un almacenamiento de datos para cada sesión. Se llama 'heap' y es simplemente una tabla de datos almacenados de forma específica para cada sesión en clave-valor.
