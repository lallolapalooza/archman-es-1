NOMBRE

Locale::gettext_dumb - Implementación de traducción de mensajes de Uniforum no consciente de la configuración regional

SINOPSIS

use Locale::gettext_dumb qw(:locale_h :libintl_h);
# Normalmente, no querrás incluir este módulo directamente, sino así:
use Locale::Messages;

my $seleccionado = Locale::Messages->select_package ('gettext_dumb');
gettext $msgid;
dgettext $domainname, $msgid;
dcgettext $domainname, $msgid, LC_MESSAGES;
ngettext $msgid, $msgid_plural, $count;
dngettext $domainname, $msgid, $msgid_plural, $count;
dcngettext $domainname, $msgid, $msgid_plural, $count, LC_MESSAGES;
pgettext $msgctxt, $msgid;
dpgettext $domainname, $msgctxt, $msgid;
dcpgettext $domainname, $msgctxt, $msgid, LC_MESSAGES;
npgettext $msgctxt, $msgid, $msgid_plural, $count;
dnpgettext $domainname, $msgctxt, $msgid, $msgid_plural, $count;
dcnpgettext $domainname, $msgctxt, $msgid, $msgid_plural, $count, LC_MESSAGES;
textdomain $domainname;
bindtextdomain $domainname, $directory;
bind_textdomain_codeset $domainname, $encoding;
my $categoria = LC_CTYPE;
my $categoria = LC_NUMERIC;
my $categoria = LC_TIME;
my $categoria = LC_COLLATE;
my $categoria = LC_MONETARY;
my $categoria = LC_MESSAGES;
my $categoria = LC_ALL;

DESCRIPCIÓN

¡IMPORTANTE! Este módulo es experimental. ¡Puede que no funcione como se describe!

El módulo Locale::gettext_dumb hace exactamente lo mismo que Locale::gettext_xs(3pm) o Locale::gettext_pp(3pm).

Mientras que ambos otros módulos usan POSIX::setlocale() para determinar la configuración regional actualmente seleccionada, este backend solo verifica las variables de entorno LANGUAGE, LANG, LC_ALL, LC_MESSAGES (en ese orden), cuando intenta localizar un catálogo de mensajes (un archivo .mo).

Esta clase se introdujo en libintl-perl 1.22.

USO

Este módulo no debe usarse para software de escritorio o scripts que se ejecuten localmente. ¿Por qué? Si usas un catálogo de mensajes, por ejemplo, en danés en UTF-8 (da_DA.UTF8) pero la configuración regional del sistema está establecida en ruso con KOI8-R (ru_RU.KOI8-R), podrías producir una salida inválida, ya sean secuencias multibyte inválidas o texto inválido, según cómo se mire.

Eso sucederá cuando mezcles la salida de Locale::gettext_pp con salida dependiente de la configuración regional del sistema operativo, como el contenido de la variable "$!", funciones de formato de fecha y hora (localtime(), gmtime(), POSIX::strftime(), etc.), formato de números con printf() y similares, y así sucesivamente.

Un escenario de uso típico se ve así:

Tienes una aplicación de servidor (por ejemplo, una aplicación web) que se supone que debe mostrar un conjunto fijo de mensajes en muchos idiomas. Si quieres hacer esto con Locale::gettext_xs(3pm) o Locale::gettext_pp(3pm), tienes que instalar los datos de configuración regional para todos esos idiomas. De lo contrario, la traducción de los mensajes no funcionará.

Con Locale::gettext_dumb(3pm) puedes relajar estos requisitos y mostrar mensajes para todos los idiomas para los que tengas archivos .mo.

Por otro lado, pronto alcanzarás límites con este enfoque. Casi cualquier aplicación requiere más que una simple traducción de mensajes para la localización. Quieres fechas y horas formateadas, quieres mostrar números con el formato correcto para los idiomas seleccionados, y es posible que quieras mostrar mensajes de error del sistema ("$!").

En la práctica, Locale::gettext_dumb(3pm) sigue siendo útil en estos escenarios. Tus usuarios tendrán que vivir con el hecho de que la salida presentada está en diferentes idiomas o para diferentes configuraciones regionales, cuando "su" configuración regional no está instalada en tu sistema.

Es más peligroso mezclar salida en diferentes juegos de caracteres, pero eso se puede evitar fácilmente. Simplemente asegúrate de que Locale::gettext_dump use UTF-8 (por ejemplo, configurando la variable de entorno OUTPUT_CHARSET o llamando a bind_textdomain_codeset()) y asegúrate de que la configuración regional del sistema también use UTF-8, por ejemplo, "en_US.UTF8". Si eso falla, cambia a una configuración regional que use un subconjunto de UTF-8. En la práctica, será US-ASCII, el juego de caracteres utilizado por la configuración regional predeterminada "C" o "POSIX".

Tu aplicación entonces, hasta cierto punto, mezclará salida para diferentes localizaciones o idiomas. Pero esto está completamente bajo tu control.

EJEMPLO

¡Ver arriba! Normalmente no deberías usar este módulo. Sin embargo, supongamos que has leído las advertencias. En una aplicación web harías algo como esto:

use Locale::TextDomain qw (com.example.yourapp);
use Locale::Messages qw (nl_putenv LC_ALL bindtextdomain
                         bind_textdomain_codeset);
use Locale::Util qw (web_set_locale);
use POSIX qw (setlocale);

# Primero intenta cambiar a la configuración regional solicitada por el usuario. Si
# la conoces, puedes intentar pasarla a setlocale así:
#
#   my $locale_codificado = 'fr_FR.UTF-8';
#   my $exito = POSIX::setlocale (LC_ALL, $locale_codificado);
#
# Sin embargo, intentamos que libintl-perl haga un mejor trabajo por nosotros:
my $exito = web_set_locale $ENV{HTTP_ACCEPT_LANGUAGE},
                             $ENV{HTTP_ACCEPT_CHARSET};
# Nota: Si tu aplicación fuerza el uso de UTF-8 para su salida
# deberías pasar 'UTF-8' como segundo argumento a web_set_locale
# en lugar de $ENV{HTTP_ACCEPT_CHARSET}.

if (!$exito) {
    # No funcionó. Cambia a la interfaz "dumb" de
    # Locale::Messages.
    Locale::Messages->select_package ('gettext_dumb');

    # Y intenta cambiar a una configuración regional predeterminada:
    if (!setlocale (LC_ALL, 'en_US.UTF-8')) {
        # Todavía sin suerte. Fuerza al menos US-ASCII:
        setlocale (LC_ALL, 'C');
    }
    bind_textdomain_codeset 'com.example.yourapp', 'utf-8';
}

Si tu aplicación fuerza el uso de UTF-8, deberías ignorar la variable de entorno
