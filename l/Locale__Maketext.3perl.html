Locale::Maketext(3perl) Guía de referencia para programadores Perl Locale::Maketext(3perl)

NOMBRE

Locale::Maketext - marco de trabajo para la localización

SINOPSIS

package MiPrograma;
use strict;
use MiPrograma::L10N;
 # ...que hereda de Locale::Maketext
my $lh = MiPrograma::L10N->get_handle() || die "¿Qué idioma?";
...
# Y luego cualquier mensaje que emita tu programa, como:
warn $lh->maketext( "No se puede abrir el archivo [_1]: [_2]\n", $f, $! );
...

DESCRIPCIÓN

Es una característica común de aplicaciones (ya sean ejecutadas directamente o a través de la Web) que sean "localizadas"—es decir, que presenten una interfaz en inglés para un hablante de inglés, una interfaz alemana para un hablante de alemán, y así sucesivamente para todos los idiomas que la aplicación está programada con. Locale::Maketext es un marco de trabajo para la localización de software; proporciona las herramientas para organizar y acceder a los fragmentos de texto y código de procesamiento de texto que necesitas para producir aplicaciones localizadas.

Para comprender mejor el concepto de Maketext y cómo encajan todos sus componentes, es posible que desees leer Locale::Maketext::TPJ13, y luego leer la documentación siguiente.

También podrías querer leer sobre el código fuente de "File::Findgrep" y sus módulos constituyentes —son un ejemplo completo (aunque pequeño) que utiliza Maketext.

RESUMEN RÁPIDO

El diseño básico de Locale::Maketext está orientado a objetos, y Locale::Maketext es una clase abstracta, desde la cual se derivan las clases de proyecto, que se usan en tus módulos. La clase de proyecto (con un nombre como "TkBocciBall::Localize", que luego se usa en tu módulo) es la clase base para todas las clases de idioma de tu proyecto (con nombres como "TkBocciBall::Localize::it", "TkBocciBall::Localize::en", "TkBocciBall::Localize::fr", etc.).

Una clase de idioma es una clase que contiene un diccionario de frases como datos de clase, y posiblemente también algunos métodos que son útiles para interpretar frases en el diccionario o para manejar texto en ese idioma.

Un objeto perteneciente a una clase de idioma se denomina "manejador de idioma"; es típicamente un objeto ligero.

La norma de acción es llamar:

use TkBocciBall::Localize;  # la clase de proyecto de localización
$lh = TkBocciBall::Localize->get_handle();
 # Dependiendo del idioma del usuario, etc., esto genera un manejador de idioma a partir de las clases disponibles,
 # y cualquier valor predeterminado que declares.
die "No se pudo crear un manejador de idioma??" unless $lh;

Desde entonces, se utiliza la función "maketext" para acceder a entradas de cualquier diccionario de idioma (que pertenece al manejador de idioma que obtuviste). Así, esto:

print $lh->maketext("You won!"), "\n";

...emite el texto correcto para este idioma. Si el objeto en $lh pertenece a la clase "TkBocciBall::Localize::fr" y %TkBocciBall::Localize::fr::Lexicon contiene "You won!" => "Tu as gagné!", entonces el código anterior felizmente le dirá al usuario "Tu as gagné!".

MÉTODOS

Locale::Maketext ofrece una variedad de métodos, que se dividen en tres categorías:

  • Métodos para construir manejadores de idioma.
  • "maketext" y otros métodos para acceder a los datos de %Lexicon de un manejador de idioma.
  • Métodos que podrías encontrar útil usar, de rutinas de tus propias que se colocan en entradas de %Lexicon.

Estos se cubren en la siguiente sección.

Métodos de Construcción

Estos están relacionados con la construcción de un manejador de idioma:

  • $lh = TuClaseProyecto->get_handle( ...etiquetas_idioma... ) || die "¿Cómo es el idioma?";

    Esto intenta cargar clases basadas en las etiquetas de idioma que le proporcionas (como "("en-US", "sk", "kon", "es-MX", "ja", "i-klingon"", y para la primera clase que se resuelve, devuelve TuClaseProyecto::idioma->new().

    Si se recorre completamente la lista de etiquetas de idioma proporcionadas y no se encuentran clases para esas etiquetas exactas, entonces se intentan las clases "superordinadas" de idioma. Así, si no existe la clase "en-US" (es decir, TuClaseProyecto::en_us), ni clases para otros elementos de esa lista, intentamos la clase superordinada, "en" (es decir, TuClaseProyecto::en), y así sucesivamente para las otras etiquetas de idioma en la lista proporcionada: "es" (las otras etiquetas en nuestro ejemplo de lista que no tienen superordinados).

    Si ninguna de estas etiquetas de idioma conduce a una clase cargable, intentamos clases derivadas de TuClaseProyecto->fallback_languages() y, si no hay resultados, usamos clases nombradas por TuClaseProyecto->fallback_language_classes(). Entonces, en el caso (probablemente muy poco común) de que esto falle, devolveremos undef.

  • $lh = TuClaseProyecto->get_handle() || die "¿Cómo es el idioma?";

    Cuando "get_handle" se llama con un argumento vacío, ocurre magia:

    Si "get_handle" detecta que está ejecutando un programa invocado como CGI, intenta obtener etiquetas de idioma de la variable de entorno "HTTP_ACCEPT_LANGUAGE", y finge que esos fueron los que se pasaron a "get_handle".

    De lo contrario (es decir, si no es CGI), intenta varias formas específicas del sistema operativo para obtener las etiquetas de idioma del entorno actual, y luego finge que esos fueron los valores que se pasaron a "get_handle".

    Actualmente, esta detección del sistema operativo consiste en mirar las variables de entorno "LANG" y "LANGUAGE"; y en el caso de los sistemas Windows (donde estas variables generalmente no se utilizan), también intenta usar el módulo Win32::Locale para obtener una etiqueta de idioma para el idioma/área del sistema actual en la pestaña "Regiones y Preferencias" (¿o "Intercontinental"?) del panel de control. Me gustaría que se le sugieran más ideas sobre cómo hacer que esto haga lo correcto en otros sistemas operativos que admiten localización.

    Si está utilizando la localización en un proyecto que mantiene un archivo de configuración, podría considerar algo como esto en su clase de proyecto:

    sub get_handle_via_config {
  my $class = $_[0];
  my $chosen_language = $Config_settings{'language'};
  my $lh;
  if($chosen_language) {
    $lh = $class->get_handle($chosen_language)
     || die "No se puede encontrar un manejador de idioma para \"$chosen_language\""
          . " o tipo similar";
  } else {
    # Archivo de configuración faltante, ¿tal vez?
    $lh = $class->get_handle()
     || die "No se puede obtener un manejador de idioma";
  }
  return $lh;
}
  • $lh = TuClaseProyecto::nombreidioma->new();

    Esto construye un manejador de idioma. Generalmente no lo llamas directamente, pero sí permite que "get_handle" encuentre una clase de idioma para usar y luego llame "new() en ella.

  • $lh->init();

    Esto es llamado por "new() para inicializar nuevos manejadores de idioma. Si defines un método init en tu clase, recuerda que suele ser una buena idea llamar $lh->SUPER::init en él (probablemente al principio), para que todas las clases puedan inicializar un objeto nuevo de forma independiente.

  • TuClaseProyecto->fallback_languages()

    El "get_handle" adjunta el valor devuelto de esta función a la lista de idiomas que se le pasa a "get_handle". Excepto si anulas esta función, tu clase de proyecto heredará "fallback_languages" de Locale::Maketext, que actualmente devuelve "('i-default', 'en', 'en-US')" (donde "i-default" está definido en RFC 2277).

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

Este método (al hacerlo devolver el nombre de una etiqueta de idioma que tenga una clase de idioma existente) puede ser utilizado para garantizar que "get_handle" siempre construya un handle de idioma (asumiendo que tus clases de idioma estén en una carpeta de @INC adecuada). O puedes usar el siguiente método:

  • YourProjClass->fallback_language_classes()

    "get_handle" añade el valor devuelto de este método al final de la lista de clases que usará. Excepto si overrides este método, tu clase de proyecto heredaría "Locale::Maketext" "fallback_language_classes", que actualmente devuelve una lista vacía, "()". Al establecer este a algún valor (por ejemplo, el nombre de una clase de idioma cargable), puedes asegurarte de que "get_handle" siempre construya un handle de idioma.

    • El método "maketext"

    Este es el método más importante de Locale::Maketext:

    $text = $lh->maketext(I<key>, ...parámetros para esta frase...);

    Este busca en la %Lexicon del handle de idioma $lh y todos sus superclases, buscando una entrada cuyo clave sea el string key. Suponiendo que se encuentra tal entrada, se producen diversos efectos según el valor encontrado:

    Si el valor es un ref a un escalar, el escalar se desreferencia y se devuelve (y cualquier parámetro se ignora).

    Si el valor es un ref a una función codificada, devolvemos &$value($lh, ...parámetros...).

    Si el valor no parece estar en notación de corchetes, devolvemos el valor (reemplazándolo por un ref a un escalar en su %Lexicon).

    Si el valor sí parece estar en notación de corchetes, compilamos el texto en un sub, reemplazamos la cadena en el %Lexicon con la nueva ref a la función codificada, y luego devolvemos &$new_sub($lh, ...parámetros...).

    La notación de corchetes se discute en una sección posterior. Nota que intentar compilar un texto en notación de corchetes puede lanza una excepción si el texto no es sintácticamente válido (por ejemplo, si no se equilibran los corchetes).

    También, llamar a &$coderef($lh, ...parámetros...) puede lanza cualquier tipo de excepción (por ejemplo, si el código en esa sub funciona para dividir por cero). Sin embargo, una excepción común ocurre cuando el texto con notación de corchetes dice "llamar a un método llamado 'foo'", pero no existe tal método. (Ejemplo, "You have [quatn,_1,ball]." lanzará una excepción al intentar llamar a $lh->quatn($_[1],'ball') -- probablemente pretendías "quant".) "maketext" captura estas excepciones, pero solo para hacer más legible el mensaje de error, y luego reloca la excepción.

    Una excepción podría ser lanzada si key no se encuentra en ninguna de las %Lexicon de $lh de las hashes. ¿Qué pasa si un key no se encuentra, se discute en una sección posterior, "Controlling Lookup Failure".

    Nota que podrías encontrar útil sobrescribir el método "maketext" con un método "after", si quieres traducir codificaciones o incluso scripts:

    package YrProj::zh_cn; # Chino con caracteres de PRC
use base ('YrProj::zh_tw');  # Taiwan
sub maketext {
  my $self = shift(@_);
  my $value = $self->maketext(@_);
  return Chineeze::taiwan2mainland($value);
}

    O podrías querer sobrescribirlo con algo que capture cualquier excepción, si eso es crítico para tu programa:

    sub maketext {
  my($lh, @stuff) = @_;
  my $out;
  eval { $out = $lh->SUPER::maketext(@stuff) };
  return $out unless $@;
  ...de lo contrario maneja la excepción...
}

    Otras que no son estas dos situaciones, no imagino que sea útil sobrescribir el método "maketext". (Si te encuentras una situación útil, estaría encantado de escuchar sobre ello.)

    $lh->fail_with o $lh->fail_with(PARAM)
    $lh->failure_handler_auto
    Estas dos métodos se discuten en la sección "Controlling Lookup Failure".
    $lh->denylist(@list) <or> $lh->blacklist(@list)
    $lh->allowlist(@list) <or> $lh->whitelist(@list)
    Estos métodos se discuten en la sección "Bracket Notation Security".

    Métodos de Utilidad

    Estos son métodos que puedes encontrar útil utilizar, generalmente desde rutinas de %Lexicon de tus (sin importar si se expresan como notación de corchetes o no).

    $language->quant($number, $singular)
    $language->quant($number, $singular, $plural)
    $language->quant($number, $singular, $plural, $negative)
    Este es generalmente para llamar desde notación de corchetes (que se discute más adelante), como en 
    "Your search matched [quant,_1,document]!"

    Es para quantificar un sustantivo (es decir, decir cuánto de él hay, mientras que da la forma correcta). El comportamiento de este método es útil para inglés y un par de idiomas occidentales, y deberías sobrescribirlo para los idiomas donde no es adecuado. Puedes leer el código fuente, pero la implementación actual es básicamente como se describe en este pseudocódigo:

    if $number is 0 and there's a $negative,
   return $negative;
elsif $number is 1,
   return "1 $singular";
elsif there's a $plural,
   return "$number $plural";
else
   return "$number " . $singular . "s";
#
# ...except that we actually call numf to
#  stringify $number before returning it.

    Así, para inglés (con notación de corchetes) "...[quant,_1,file]..." es correcto (para 0 devuelve "0 files", para 1 "1 file", y para más "2 files", etc.).

    Sin embargo, para "directory", quieres "[quant,_1,directory,directories]" para que nuestro método básico de "quant" no cree que el plural de "directory" es "directorys". Y podrías notar que el resultado puede sonar mejor si especificas un formulario negativo, como:

    "[quant,_1,file,files,No files] matched your query.\n"

    Recuerda mantener en mente el acuerdo de verbos (o adjetivos, en otros idiomas), como en:

    "[quant,_1,document] were matched.\n"

    Porque si _1 es 1, obtienes "1 document were matched". Una forma aceptable de hackearlo es hacer algo como:

    "[quant,_1,document was, documents were] matched.\n"
    $language->numf($number)
    Devuelve el número dado bien formateado según las convenciones de este idioma. El método default de "maketext" es principalmente tomar el formato normal de la cadena del número (aplicando sprintf "%G" solo para números muy grandes), y luego agregar comas cuando sea necesario. (Aunque, en realidad, aplicamos "tr/,./.,/" si $language->{'numf_comma'} es verdadero; eso es un poco de un hack útil para idiomas que expresan dos millones como "2.000.000" y no como "2,000,000").

    Si quieres algo más creativo, considera sobrescribirlo con algo que use Number::Format, o hacer algo completamente diferente.

    Nota: numf se llama por quant para serializar todos los números de quantificación.

    $language->numerate($number, $singular, $plural, $negative)
    Devuelve la forma del sustantivo adecuada para la cantidad $number según las convenciones de este idioma. "numerate" se usa internamente por "quant" para quantificar sustantivos. Usa directamente — a menudo desde notación de corchetes — para evitar el llamado implícito de "numf" de "quant" y la salida de una cantidad numérica.
    $language->sprintf($format, @items)
    Es simplemente una capa de wrapper sobre la función normal de "sprintf" de Perl. Se proporciona para que puedas usar "sprintf" en notación de corchetes: 
    "Couldn't access datanode [sprintf,%10x=~[%s~],_1,_2]!\n"

    devuelve...

    Couldn't access datanode      Stuff=[thangamabob]!
    $language->language_tag()
    Actúa actualmente como si tomara el último fragmento de ref($language), lo transforma en un guion y devuelve. Así, si $language es un objeto de la clase Hee::HOO::Haw::en_us, $language->language_tag() devuelve "en-us". (Sí, la representación usual para esa etiqueta de idioma es "en-US", pero el caso no es significativo en comparaciones de etiquetas de idioma.)

    Puedes sobrescribirlo como quieras; Maketext no lo usa para nada.

    $language->encoding()
    Actualmente no se usa para nada, pero se proporciona (con valor por defecto de "(ref($language) && $language->{'encoding'}) || "iso-8859-1"") como un sugerido para asociar codificaciones con tus handles de idioma (aunque sea por clase o incluso por handle).

    Propiedades de los Handles de Idioma y Estructuras Internas

    Un handle de idioma es un objeto ligero — es decir, no (necesariamente) lleva datos de interés, más allá de ser un miembro del clase a la que pertenece.

    Un handle de idioma se implementa como un hash bendecido. Las subclases de tus pueden almacenar cualquier dato que quieras en el hash. Actualmente, la única entrada de hash utilizada por cualquier método crítico de Maketext es "fail", así que puedes usar lo que quieras en cualquier lugar.

    ¿Recuerdas: no te preocupes por leer el código fuente si hay algún punto en el que este documento sea incierto. Este documento es mucho más largo que el código fuente del módulo.

    Jerarquías de Clases de Idioma

    JERARQUÍAS DE CLASES DE IDIOMAS

    Estas son las suposiciones de Locale::Maketext sobre la jerarquía de clases formada por todas tus clases de idiomas:

    • Debes tener una clase base del proyecto, que cargas y luego usas como primer argumento en la llamada a YourProjClass->get_handle(...). Debe derivar (directa o indirectamente) de Locale::Maketext. **No importa** cómo nombres esta clase, aunque asumiendo que este es el componente de localización de tu Súper Mega Programa, buenos nombres para tu clase de proyecto podrían ser SuperMegaProgram::Localization, SuperMegaProgram::L10N, SuperMegaProgram::I18N, SuperMegaProgram::International, o incluso SuperMegaProgram::Languages o SuperMegaProgram::Messages.
    • Las clases de idioma son lo que YourProjClass->get_handle intentará cargar. Las buscará tomando cada etiqueta de idioma ( **omitíendola** si no parece una etiqueta de idioma o de localización), convirtiéndola a minúsculas, reemplazando los guiones por guiones bajos y añadiéndola a YourProjClass. "::". Entonces esto: 
      $lh = YourProjClass->get_handle(
  'en-US', 'fr', 'kon', 'i-klingon', 'i-klingon-romanized'
);

      intentará cargar las clases YourProjClass::en_us (¡nota las minúsculas!), YourProjClass::fr, YourProjClass::kon, YourProjClass::i_klingon y YourProjClass::i_klingon_romanized. (Y se detendrá en la primera que realmente se cargue).

    • Supongo que cada clase de idioma deriva (directa o indirectamente) de tu clase de proyecto, y también define su %Lexicon, o ambas cosas. Pero no preveo consecuencias graves si estas suposiciones no se cumplen.
    • Las clases de idioma pueden derivar de otras clases de idioma (aunque deberían tener "use Thatclassname" o "use base qw(...classes...)"). Pueden derivar de la clase del proyecto. Pueden derivar de alguna otra clase. O a través de herencia múltiple, pueden derivar de cualquier mezcla de estas.
    • No preveo problemas con tener herencia múltiple en tu jerarquía de clases de idioma. (Como de costumbre, sin embargo, Perl se quejará amargamente si tienes un ciclo en la jerarquía: es decir, si alguna clase es su propio antecesor).

    ENTRADAS EN CADA LÉXICO

    Una entrada típica de %Lexicon está destinada a significar una frase, que toma un número (0 o más) de parámetros. Una entrada está destinada a ser accedida por una clave de cadena en $lh->maketext(key, ...parameters...), que debería devolver una cadena que generalmente está destinada a ser utilizada para la "salida" al usuario, independientemente de si esto significa imprimir en STDOUT, escribir en un archivo o colocarlo en un widget GUI.

    Mientras que la clave debe ser un valor de cadena (ya que esa es una restricción básica que Perl impone a las claves de hash), el valor en el léxico puede ser actualmente de varios tipos: un escalar definido, un escalarseferencia o un coderef. El uso de estos se explica anteriormente, en la sección 'El método "maketext"', y la notación de corchetes para cadenas se discute en la siguiente sección.

    Si bien puedes usar identificadores únicos arbitrarios para las claves del léxico (como "_min_larger_max_error"), a menudo es útil si la clave de una entrada es en sí misma un valor válido, como este mensaje de error de ejemplo:

    "Minimum ([_1]) is larger than maximum ([_2])!\n"

    Compara este código que usa una ID arbitraria...

    die $lh->maketext( "_min_larger_max_error", $min, $max )
 if $min > $max;

    ...con este código que usa una clave como valor:

    die $lh->maketext(
"Minimum ([_1]) is larger than maximum ([_2])!\n",
$min, $max
) if $min > $max;

    El segundo es, en resumen, más legible. En particular, es obvio que el número de parámetros que estás proporcionando a esa frase (dos) es el número de parámetros que *quiere* recibir. (Ya que ves _1 y un _2 usándose en la clave allí).

    Además, una vez que un proyecto está completo y comienzas a localizarlo, puedes recopilar todas las claves que usas y pasárselas a un traductor; y entonces el trabajo del traductor irá más rápido si lo que se le presenta es esto:

    "Minimum ([_1]) is larger than maximum ([_2])!\n",
 => "",   # ¡rellena algo aquí, Jacques!

    en lugar de este más críptico desorden:

    "_min_larger_max_error"
 => "",   # ¡rellena algo aquí, Jacques!

    Creo que las claves como valores del léxico hacen que las entradas completas del léxico sean más legibles:

    "Minimum ([_1]) is larger than maximum ([_2])!\n",
 => "Le minimum ([_1]) est plus grand que le maximum ([_2])!\n"

    Además, tener valores válidos como claves resulta muy útil si configuras un léxico _AUTO. Los léxicos _AUTO se discuten en una sección posterior.

    Casi siempre uso claves que son en sí mismas valores de léxico válidos. Una excepción notable es cuando el valor es bastante largo. Por ejemplo, para obtener la pantalla de datos que un programa de línea de comandos podría devolver cuando se le da un interruptor desconocido, a menudo solo uso una clave breve y autoexplicativa como "_USAGE_MESSAGE". En ese momento, voy y defino inmediatamente esa entrada del léxico en el léxico ProjectClass::L10N::en (ya que el inglés siempre es mi "idioma del proyecto"):

    '_USAGE_MESSAGE' => <<'EOSTUFF',
...mensaje largo largo...
EOSTUFF

    y luego puedo usarlo como:

    getopt('oDI', \%opts) or die $lh->maketext('_USAGE_MESSAGE');

    Incidentalmente, ten en cuenta que el %Lexicon de cada clase hereda y extiende los léxicos de sus superclases. Esto no es porque estos sean hashes especiales *per se*, sino porque se accede a ellos a través del método maketext, que busca entradas en todos los hashes %Lexicon en una clase de idioma *y* en todas sus clases ancestras. (Esto se debe a que la idea de "datos de clase" no se implementa directamente en Perl, sino que se deja a los sistemas de clases individuales implementarlos como mejor les parezca).

    Ten en cuenta que puedes tener cosas almacenadas en un léxico además de frases para la salida: por ejemplo, si tu programa toma entrada del teclado, haciendo una pregunta de "(S/N)", probablemente necesites saber cuáles son los equivalentes de "S[í]/N[o]" en el idioma que sea. Probablemente también necesites saber cuáles son los equivalentes de las respuestas "s" y "n". Puedes almacenar esa información en el léxico (por ejemplo, bajo las claves "~answer_y" y "~answer_n", y las formas largas como "~answer_yes" y "~answer_no", donde "~" es solo un carácter ad hoc destinado a indicar a programadores/traductores que estas no son frases para la salida).

    O en lugar de almacenar esto en el léxico de la clase de idioma, puedes (y, en algunos casos, realmente deberías) representar la misma información como código en un método de la clase de idioma. (Eso deja una distinción clara entre el léxico como las cosas que sabemos *decir*, y el resto de las cosas en la clase de léxico como las cosas que sabemos *hacer*). Considera este ejemplo de un procesador de respuestas a preguntas francesas "oui/non":

    sub y_or_n {
  return undef unless defined $_[1] and length $_[1];
  my $answer = lc $_[1];  # poner en minúsculas
  return 1 if $answer eq 'o' or $answer eq 'oui';
  return 0 if $answer eq 'n' or $answer eq 'non';
  return undef;
}

    ...que luego llamarías en una construcción como esta:

    my $response;
until(defined $response) {
  print $lh->maketext("Open the pod bay door (y/n)? ");
  $response = $lh->y_or_n( get_input_from_keyboard_somehow() );
}
if($response) { $pod_bay_door->open()         }
else          { $pod_bay_door->leave_closed() }

    NOTACIÓN DE CORCHETES

    La Notación de Corchetes es una característica crucial de Locale::Maketext. Entiendo que la Notación de Corchetes proporciona un reemplazo para el uso del formato sprintf. Todo lo que haces con la Notación de Corchetes podría hacerse con un bloque sub, pero la notación de corchetes está destinada a ser mucho más concisa.

    La Notación de Corchetes es como un sistema de "plantilla" en miniatura (en el sentido de Text::Template, no en el sentido de plantillas C++), donde el texto normal se pasa tal cual, pero el texto en regiones especiales se interpreta de manera especial. En la Notación de Corchetes, usas corchetes ("[...]"), no llaves ("{...}") para indicar las secciones que se interpretan especialmente.

    Por ejemplo, aquí todas las áreas que se toman literalmente están subrayadas con un "^", y todas las regiones especiales entre corchetes están subrayadas con una X:

    "Minimum ([_1]) is larger than maximum ([_2])!\n"
 ^^^^^^^^^ XX ^^^^^^^^^^^^^^^^^^^^^^^^^^ XX ^^^^

    Cuando esa cadena se compila de notación de corchetes a una subrutina Perl real, básicamente se convierte en:

    sub {
  my $lh = $_[0];
  my @params = @_;
  return join '',
    "Minimum (",
    ...algún código aquí...
    ") is larger than maximum (",
    ...algún código aquí...
    ")!\n",
}
# para ser llamado por $lh->maketext(KEY, params...)

    En otras palabras, el texto fuera de los grupos de corchetes se convierte en literales de cadena. El texto entre corchetes es bastante más complejo y actualmente sigue estas reglas:

    • Los grupos de corchetes que están vacíos, o que consisten solo en espacios en blanco, se ignoran. (Ejemplos: "[]", "[ ]", o un [ y un ] con retornos de carro y/o tabulaciones y/o espacios entre ellos).

      De lo contrario, cada grupo se toma como un grupo de elementos separados por comas, y cada elemento se interpreta de la siguiente manera:

    • Un elemento que es "_dígitos" o "_-dígitos" se interpreta como $_[valor]. Es decir, "_1" se convierte en $_[1], y "_-3" se interpreta como $_[-3] (en w

    DESCRIPCIONES DE NOTACIÓN

    Las entradas de texto definidas en un %Lexicon se componen de una cadena clave y una cadena de sustitución (o una subrutina). El código de traducción se genera para esa cadena de sustitución, basándose en una notación especial de cadenas que llamo Notación de Corchetes.

    Por ejemplo, aquí hay una definición típica en %Lexicon:

        _ = {
        ...
        "Hello, world" => "Hello, world!",
        "Hello, [_1]!" => "Hello, [_1]!",
        "Greetings (%s)" => "Greetings (%s)",
        "quant" => q{
            Use this instead of the default 'quant' method.
            It takes 3 arguments: count, singular, plural.
            It returns the right form for the count.
        },
        "item%1.0f" => "There %s %d item%s\n",
        ...
    };

    Cuando maketext() se llama con una clave que no se encuentra directamente en el %Lexicon, sino que se puede generar a partir de una cadena dada (por ejemplo, "Hello, [_1]!"), maketext() se transforma en una subrutina Perl que se ejecuta de inmediato.

    La Notación de Corchetes es la forma en que se pueden insertar variables en una cadena de salida. Las variables se insertan como argumentos posicionales (como $1, $2, etc. en Perl), y se indican mediante [_1], [_2], etc.

    La notación de corchetes tiene dos usos:

    • Para referirse a argumentos pasados a la llamada maketext().
    • Para llamar a métodos de la clase Locale::Maketext (o clases derivadas), como quant(), numf(), etc.

    Una cadena que contiene Notación de Corchetes se divide en una serie de elementos. Cada elemento se procesa de forma diferente, según si está o no entre corchetes:

    • Los elementos que no están entre corchetes se tratan como cadenas literales.
    • Los elementos que sí están entre corchetes se procesan de forma especial. La interpretación de dichos elementos depende del primer elemento del grupo de corchetes.

    Para entender cómo se procesan los elementos dentro de un grupo de corchetes, primero debemos entender el significado de las referencias a variables dentro de un grupo de corchetes.

    Un grupo de corchetes puede contener una mezcla de lo siguiente:

    • Una referencia a un argumento pasado a maketext(). Estas se expresan como $_[0], $_[1], etc. (donde $_[0] es el manejador de idioma y, por lo tanto, normalmente no se nombra directamente).
    • Una referencia a $_, que se interpreta como una referencia a todos los argumentos pasados a maketext() excepto el primer argumento (el manejador de idioma). En otras palabras, @_[1..$#_]. Tenga en cuenta que esta es una lista vacía en el caso de llamadas como $lh->maketext(key) donde no hay parámetros (excepto $_[0], el manejador de idioma).
    • Una referencia a un argumento específico, por ejemplo, $_[1], $_[2], etc.
    • Una referencia a un subconjunto de argumentos pasados a maketext(). Por ejemplo, $_[1,3] se refiere a los argumentos $_[1] y $_[3]. $_[1..3] se refiere a los argumentos $_[1], $_[2] y $_[3].
    • Una subcadena literal.

    Los elementos individuales dentro de un grupo de corchetes se separan mediante comas:

    • Un elemento que empieza con $_ se interpreta como una referencia a un argumento de la llamada maketext(). Por ejemplo, $_[1] se refiere al primer argumento pasado a maketext() (después del manejador de idioma). $_[1,3] se refiere al primer y tercer argumento. $_[1..3] se refiere al primer, segundo y tercer argumento. Tenga en cuenta que cada uno de estos elementos debería tener al menos tres elementos en él). Tenga en cuenta que $_[0] es el manejador de idioma y, por lo general, no se nombra directamente.
    • Un elemento _* se interpreta como todo @_ excepto $_[0]. Es decir, @_[1..$#_]. Tenga en cuenta que esta es una lista vacía en el caso de llamadas como $lh->maketext(key) donde no hay parámetros (excepto $_[0], el manejador de idioma).
    • De lo contrario, cada elemento se interpreta como una cadena literal.

    El grupo en su conjunto se interpreta de la siguiente manera:

    • Si el primer elemento de un grupo de corchetes parece un nombre de método, entonces ese grupo se interpreta de la siguiente manera: 
      $lh->that_method_name(
  ...resto de elementos en este grupo...
),
    • Si el primer elemento de un grupo de corchetes es *, se toma como taquigrafía para el método quant llamado tan comúnmente. Del mismo modo, si el primer elemento de un grupo de corchetes es #, se toma como taquigrafía para numf.
    • Si el primer elemento de un grupo de corchetes es la cadena vacía, o _* o _dígitos o _-dígitos, entonces ese grupo se interpreta como la simple interpolación de todos sus elementos: 
      join('',
  ...resto de elementos en este grupo...
),

      Ejemplos: [_1] y [,_1], que son sinónimos; y "[,ID-(,_4,-,_2,)]", que se compila como "join "", "ID-(", $_[4], "-", $_[2], ")"".

    • De lo contrario, este grupo de corchetes es inválido. Por ejemplo, en el grupo [!@#,whatever], el primer elemento "!@#" no es ni la cadena vacía, _número, _-número, _*, ni un nombre de método válido; por lo tanto, Locale::Maketext lanzará una excepción si intenta compilar una expresión que contenga este grupo de corchetes.

    Tenga en cuenta, incidentalmente, que los elementos de cada grupo están separados por comas, no por "/\s*,\s*/". Es decir, podría esperar que este grupo de corchetes:

    "Hoohah [foo, _1 , bar ,baz]!"

    se compile en esto:

    sub {
  my $lh = $_[0];
  return join '',
    "Hoohah ",
    $lh->foo( $_[1], "bar", "baz"),
    "!",
}

    Pero en realidad se compila así:

    sub {
  my $lh = $_[0];
  return join '',
    "Hoohah ",
    $lh->foo(" _1 ", " bar ", "baz"),  # note el <espacio> en " bar "
    "!",
}

    En la notación discutida hasta ahora, los caracteres [ y ] tienen un significado especial, para abrir y cerrar grupos de corchetes, y , tiene un significado especial dentro de los grupos de corchetes, donde separa los elementos del grupo. Esto plantea la pregunta de cómo se expresaría un [ o ] literal en una cadena de Notación de Corchetes, y cómo se expresaría una coma literal dentro de un grupo de corchetes. Para este propósito, he adoptado ~ (tilde) como carácter de escape: ~[ significa un carácter '[' literal en cualquier lugar de la Notación de Corchetes (es decir, independientemente de si se encuentra o no dentro de un grupo de corchetes), y lo mismo para ~] que significa un carácter ']', y ~, que significa una coma literal. (Aunque , significa una coma literal fuera de los grupos de corchetes: es solo dentro de los grupos de corchetes que las comas son especiales).

    Y en el improbable caso de que necesite una tilde literal en una expresión de corchetes, la obtiene con ~~.

    Actualmente, una ~ sin escapar antes de un carácter que no sea un corchete o una coma se toma como una ~ literal y ese carácter. Es decir, ~X significa lo mismo que ~~X -- es decir, una tilde literal y luego una X literal. Sin embargo, al usar ~X, usted asume que ninguna versión futura de Maketext utilizará ~X como una secuencia de escape mágica. En la práctica, esto no es un gran problema, ya que en primer lugar puede simplemente escribir ~~X y no preocuparse por ello; en segundo lugar, dudo que añada muchos caracteres mágicos nuevos a la notación de corchetes; y en tercer lugar, es poco probable que desee caracteres de tilde literales en sus mensajes de todos modos, ya que no es un carácter con amplio uso en el texto del lenguaje natural.

    Los corchetes deben estar equilibrados: cada corchete de apertura debe tener un corchete de cierre coincidente, y viceversa. Por lo tanto, todos estos son inválidos:

    "I ate [quant,_1,rhubarb pie."
"I ate [quant,_1,rhubarb pie[."
"I ate quant,_1,rhubarb pie]."
"I ate quant,_1,rhubarb pie[."

    Actualmente, los grupos de corchetes no se anidan. Es decir, no puede decir:

    "Foo [bar,baz,[quux,quuux]]\n";

    Si necesita una notación que sea tan potente, use Perl normal:

    %Lexicon = (
  ...
  "some_key" => sub {
    my $lh = $_[0];
    join '',
      "Foo ",
      $lh->bar('baz', $lh->quux('quuux')),
      "\n",
  },
  ...
);

    O escriba el método bar para que no necesite pasarle la salida de llamar a quux.

    No anticipo que necesite (o que desee particularmente) anidar grupos de corchetes, pero le invitamos a enviarme un correo electrónico con argumentos convincentes (en la vida real) en contrario.

    SEGURIDAD DE LA NOTACIÓN DE CORCHETES

    Locale::Maketext no utiliza ninguna sintaxis especial para diferenciar los métodos de notación de corchetes de los métodos de clase u objeto normales. Este diseño lo hace vulnerable a ataques de cadenas de formato siempre que se utilice para procesar cadenas proporcionadas por usuarios no confiables.

    Locale::Maketext admite funcionalidad de lista negra y lista blanca para limitar qué métodos pueden ser llamados como métodos de notación de corchetes.

    Por defecto, Locale::Maketext deniega todos los métodos en el espacio de nombres Locale::Maketext que comienzan con el carácter _, y todos los métodos que incluyen los caracteres separadores de espacio de nombres de Perl.

    La lista negra predeterminada para Locale::Maketext también evita el uso de los siguientes métodos en la notación de corchetes:

    denylist
encoding
fail_with
failure_handler_auto
fallback_language_classes
fallback_languages
get_handle
init
language_tag
maketext
new
allowlist
whitelist
blacklist

    Esta lista se puede ampliar añadiendo más métodos conocidamente malos a la lista negra, o incluyendo solo métodos conocidamente buenos en la lista blanca.

    Para evitar que métodos específicos se llamen en la notación de corchetes, utilice el método denylist():

    my $lh = MyProgram::L10N->get_handle();
$lh->denylist(qw{my_internal_method my_other_method});
$lh->maketext('[my_internal_method]'); # muere

    Para limitar los métodos permitidos de notación de corchetes a una lista específica, utilice el método allowlist():

    my $lh = MyProgram::L10N->get_handle();
$lh->allowlist('numerate', 'numf');
$lh->maketext('[_1] [numerate, _1,shoe,shoes]', 12); # funciona
$lh->maketext('[my_internal_method]'); # muere

    Los métodos denylist() y allowlist() amplían sus listas internas cada vez que se llaman. Para restablecer la lista negra o la lista blanca, cree un nuevo objeto maketext.

    my $lh = MyProgram::L10N->get_handle();
$lh->denylist('numerate');
$lh->denylist('numf');
$lh->maketext('[_1] [numerate,_1,shoe,shoes]', 12); # muere

    Para léxicos que utilizan una caché interna, las traducciones que ya se han cacheados en su forma compilada no se ven afectadas por cambios posteriores en la configuración de la lista blanca o negra. Los léxicos que utilizan una caché externa verán su caché borrada cada vez que cambien la configuración de la lista blanca o negra. La diferencia entre los dos tipos de caché se explica en la sección Léxicos de Solo Lectura.

    Los métodos prohibidos por la lista negra no pueden ser permitidos por la lista blanca.

    NOTA: denylist() es el nombre de método preferido a usar en lugar del método histórico y no inclusivo blacklist(). blacklist() puede ser eliminado en una futura versión de este paquete y, por lo tanto, su uso debe ser eliminado.

    NOTA: allowlist() es el nombre de método preferido a usar en lugar del método histórico y no inclusivo whitelist(). whitelist() puede ser eliminado en una futura versión de este paquete y, por lo tanto, su uso debe ser eliminado.

    LÉXICOS AUTOMÁTICOS

    Si maketext va a buscar en un %Lexicon individual una entrada para key (donde key no comienza con un guion bajo), y no la encuentra, pero sí ve una entrada de _AUTO => algún_valor_verdadero, entonces definimos efectivamente $Lexicon{key} = key en ese mismo instante, y luego usamos ese valor como si hubiera estado allí todo el tiempo.     LECTURAS DE SOLO LÉXICAS

    Si tu léxico es una tabla asociada (hash), el simple acto de cachear el valor compilado puede ser catastrófico. Por ejemplo, un hash atado de GDBM_File GDBM_READER colapsará con algo como:

    gdbm store returned -1, errno 2, key "..." at ...

    Simplemente necesitas activar el caché externo fuera del hash léxico mismo así:

    sub init {
    my ($lh) = @_;
    ...
    $lh->{'use_external_lex_cache'} = 1;
    ...
}

    Y luego, en lugar de almacenar el valor compilado en el hash léxico, lo almacenará en $lh->{'_external_lex_cache'}.

    CONTROL DE FALLOS DE BÚSQUEDA

    Si llamas a $lh->maketext(key, ...params...), y no hay una entrada key en el hash %Lexicon de la clase $lh, ni en el hash %Lexicon de la superclase, y si no puedes auto-crear key (porque empieza con "_" o porque ninguno de tus léxicos tiene "_AUTO => 1"), entonces has fallado en encontrar una forma normal de crear key para maketext. Lo que sucede bajo estas condiciones de fallo depende del atributo "fail" del objeto $lh.

    Si el manejador de lenguaje no tiene un atributo "fail", maketext lanzará una excepción (es decir, llamará a "die", mencionando la key cuya búsqueda falló, y el número de línea donde se llamó a $lh->maketext(key,...).

    Si el manejador de lenguaje tiene un atributo "fail" cuyo valor es un coderef, entonces $lh->maketext(key,...params...) se aborta y llama:

    return $that_subref->($lh, $key, @params);

    De lo contrario, el valor del atributo "fail" debe ser un string que nombre un método, de modo que $lh->maketext(key,...params...) se detenga con:

    return $lh->$that_method_name($phrase, @params);

    El atributo "fail" puede ser accionado con el método "fail_with":

    # Establecer a un coderef:
$lh->fail_with( \&failure_handler );
# Establecer a un nombre de método:
$lh->fail_with( 'failure_method' );
# Establecer a nada (es decir, para que el fallo lance una excepción simple)
$lh->fail_with( undef );
# Obtener el valor actual
$handler = $lh->fail_with();

    Ahora, ¿qué quieres hacer con estos manejadores? Tal vez quieras registrar qué clave falló para qué clase y luego lanzar una excepción. Tal vez no te guste "die" y prefieras enviar el mensaje de error a STDOUT (o donde quieras) y solo llamar a exit(). Tal vez no quieras lanzar "die" en absoluto! Tal vez puedas usar un manejador como este:

    # Hacer que todas las búsquedas recurran a un valor en inglés,
#  pero solo después de registrarlo para posterior identificación.
my $lh_backup = ThisProject->get_handle('en');
open(LEX_FAIL_LOG, ">>wherever/lex.log") || die "GNAARGH $!";
sub lex_fail {
  my($failing_lh, $key, $params) = @_;
  print LEX_FAIL_LOG scalar(localtime), "\t",
     ref($failing_lh), "\t", $key, "\n";
  return $lh_backup->maketext($key,@params);
}

    Algunos usuarios han expresado que la idea de tener un atributo "fail" parece una complicación de más. Sin embargo, quiero que Locale::Maketext sea utilizable en proyectos de software de cualquier escala y tipo; y diferentes proyectos de software tienen diferentes ideas sobre qué hacer en condiciones de fallo. Podría simplemente decir que el fallo siempre lanza una excepción, y que si quieres ser precavido, simplemente envías cada llamada a $lh->maketext a un eval { }.

    Sin embargo, quiero que los programadores se reserven el derecho (a través del atributo "fail") de tratar el fallo como algo distinto de una excepción de igual gravedad que una configuración no legible o un recurso esencial inaccesible.

    Un valor potencialmente útil para el atributo "fail" es el nombre de un método "failure_handler_auto". Este es un método definido en la clase Locale::Maketext misma. Puedes establecerlo con:

    $lh->fail_with('failure_handler_auto');

    Luego, cuando llames a $lh->maketext(key, ...params...) y no haya una entrada key en ninguno de esos léxicos, maketext devuelve:

    return $lh->failure_handler_auto($key, @params);

    Pero failure_handler_auto, en lugar de morir o no hacer nada, compila $key, lo cachea en:

    $lh->{'failure_lex'}{$key} = $compiled

    y luego llama al valor cacheado, y lo devuelve. (Es decir, si $key se parece a notación de corchetes, $compiled es un sub, y devolvemos &{$compiled}(@params); pero si $key es solo un string normal, simplemente lo devolvemos.)

    El efecto de usar "failure_auto_handler" es como un léxico AUTO, excepto que 1) compila $key incluso si empieza con "_", y 2) tienes un registro en el nuevo hashref $lh->{'failure_lex'} de todas las claves que han fallado para este objeto. Esto debe evitar que tu programa colapse, siempre que tus claves no sean realmente inválidas como código de corchetes, y siempre que no intenten llamar a métodos que no existen.

    "failure_auto_handler" no es necesariamente lo que quieres, pero espero que al menos te muestre que el fallo de maketext puede ser mitigado de muchas formas flexibles. Si puedes formalizar exactamente lo que quieres, deberías poder expresarlo como un manejador de fallo. Puedes incluso hacerlo por defecto para todos los objetos de una clase específica, estableciendo este atributo en esa clase:

    sub init {

  $lh->SUPER::init();
  $lh->fail_with('my_clever_failure_handler');
  return;
}

    CÓMO USAR MAKETEXT

    Aquí tienes una lista de verificación breve sobre cómo usar Maketext para localizar aplicaciones:

    • Decide qué sistema usarás para tus claves léxicas. Si prefieres, puedes usar identificadores opacos (si eres nostálgico para "catgets"), pero tengo mejores sugerencias en la sección "Entries in Each Lexicon". Asumiendo que eliges claves significativas que también son valores (como "¡Mínimo ([_1]) es mayor que máximo ([_2])!\n"), tendrás que decidir en qué idioma deben estar. A efectos de argumentación, llamaré a este idioma inglés, específicamente inglés estadounidense, "en-US".
    • Crea una clase para la localización de tu proyecto. Este es el nombre de la clase que usarás en el estilo: 
      use Projname::L10N;
my $lh = Projname::L10N->get_handle(...) || die "Idioma?";
      Asumiendo que llamas a tu clase Projname::L10N, crea una clase mínimamente consistente: 
      package Projname::L10N;
use base qw(Locale::Maketext);
...cualquier método que tu clase quiera compartir entre todos los idiomas...
# y, asumiendo que quieres que la clase base sea un léxico _AUTO, como se discute en varias secciones anteriores:
1;
    • Crea una clase para las claves internas de tu proyecto. Nombra la clase después del tag de idioma en minúsculas, con guiones cambiados a guiones bajos. Asumiendo que tu primer idioma es inglés estadounidense, deberías llamar a esta clase Projname::L10N::en_us. Ella debe ser mínimamente consistente: 
      package Projname::L10N::en_us;
use base qw(Projname::L10N);
%Lexicon = (
  '_AUTO' => 1,
);
1;
      (Para el resto de esta sección, asumiré que la clase "primera clase de idioma" de Projname::L10N::en_us tiene un léxico _AUTO.)
    • Ve el código de tu programa. En cada lugar donde escribirías: 
      print "Foobar $thing stuff\n";
      reemplázalo con un uso de maketext, sin interpolación de variables en la clave: 
      print $lh->maketext("Foobar [_1] stuff\n", $thing);
      Si te aburres de decir constantemente "print $lh->maketext", considera hacer una función envolvente, como: 
      use Projname::L10N;
our $lh;
$lh = Projname::L10N->get_handle(...) || die "Idioma?";
sub pmt (@) { print( $lh->maketext(@_) }
 # "pmt" es una abreviatura de "Print MakeText"
$Carp::Verbose = 1;
 # para que, si maketext falla, veas la llamada a pmt
      Además de frases completas para la salida, cualquier cosa dependiente del idioma debe estar en la clase Projname::L10N::en_us, ya sea como métodos o como entradas de léxico — esto se discute en la sección "Entries in Each Lexicon".
    • Una vez que el programa esté en su mayor parte terminado, y una vez que la localización del primer idioma funcione correctamente (a través de los datos y métodos de Projname::L10N::en_us), puedes preparar los datos para la traducción. Si tu primer idioma no es un léxico _AUTO, entonces ya tienes todos los mensajes explícitamente en el léxico (o de lo contrario lanzarás una excepción al llamar a $lh->maketext para mensajes que no estén allí). Pero si usaste (siguiendo el consejo) un léxico _AUTO, entonces tendrás que hacer una lista de todas las frases que hasta ahora has permitido a _AUTO generar para ti. Hay muchas formas de hacer esto. La forma más sencilla es simplemente buscar en el código cada ocurrencia: 
      grep -e '$_AUTO' ...

    LOCALIZING

    Once you've decided on your strategy for handling missing messages, and have finished writing code that uses the "maketext" (o llamadas a envoltorios alrededor de ella, como la función "pmt" anterior), y a registrar la siguiente frase.

  • Es posible que en este punto desee considerar si su clase base (Projname::L10N), de la cual heredan todos los léxicos (Projname::L10N::en, Projname::L10N::es, etc.), debería ser un léxico _AUTO. Puede ser cierto que en teoría, todos los mensajes necesarios estarán en cada clase de idioma; pero en el caso presumiblemente improbable o "imposible" de fallo de búsqueda, debería considerar si su programa debe lanzar una excepción, emitir texto en inglés (o cualquier idioma principal de su proyecto), o alguna solución más compleja, como se describe en la sección "Controlar el fallo de búsqueda", anterior.
  • Envíe todos los mensajes/frases/etc. a los traductores.

    (De hecho, es posible que desee comenzar por localizar en *un* solo idioma más al principio, si no está seguro de haber abstraído correctamente las partes del código dependientes del idioma).

    Los traductores pueden solicitar aclaraciones sobre la situación en la que se encuentra una frase determinada. Por ejemplo, en inglés estamos completamente contentos diciendo "se encontraron n archivos", sin importar si queremos decir "busqué archivos y encontré n de ellos" o la situación bastante distinta de "busqué otra cosa (como líneas en archivos) y, de paso, vi n archivos". Esto puede implicar repensar cosas que creía bastante claras: ¿debería "Editar" en una barra de herramientas ser un sustantivo ("edición") o un verbo ("editar")? ¿Ya existe una forma convencionalizada de expresar esa opción de menú, separada de la palabra normal en el idioma de destino para "editar"?

    En todos los casos en que se involucre el fenómeno muy común de la cuantificación (decir "N archivos", para **cualquier** valor de N), cada traductor debe aclarar qué dependencias causa el número en la oración. En muchos casos, la dependencia se limita a las palabras adyacentes al número, en lugares donde podría esperarlas ("Encontré el-?PLURAL N vacío-?PLURAL directorio-?PLURAL"), pero en algunos casos hay dependencias inesperadas ("¡Encontré-?PLURAL ...!") así como dependencias a larga distancia ("¡El directorio-?PLURAL N no pudo ser eliminado-?PLURAL!").

    Recuerde a los traductores que consideren el caso en que N es 0: "0 archivos encontrados" no suena exactamente natural en ningún idioma, pero puede ser inaceptable en muchos, o puede condicionar tipos especiales de concordancia (similar al inglés "No encontré NINGÚN archivo").

    Recuerde preguntar a sus traductores sobre el formato de los numerales en su idioma, para que pueda anular el método "numf" según corresponda. Las variables típicas en el formato de números son: qué usar como punto decimal (¿coma? ¿punto?); qué usar como separador de miles (¿espacio? ¿espacio de no separación? ¿coma? ¿punto? ¿punto medio pequeño? ¿comilla? ¿apóstrofo?); e incluso si el llamado "separador de miles" es en realidad para cada tercer dígito - he oído informes de doscientos mil expresados como "2,00,000" para algunos idiomas indios (subcontinentales), además de los menos sorprendentes "200 000", "200.000", "200,000" y "200'000". Además, el uso de un conjunto de glifos numéricos distintos de los "0"-"9" ASCII habituales podría ser apreciado, como a través de "tr/0-9/\x{0966}-\x{096F}/" para obtener dígitos en escritura devanagari (para hindi, konkani, otros).

    El método básico "quant" que proporciona Locale::Maketext debería ser bueno para muchos idiomas. Para algunos idiomas, podría ser útil modificarlo (o su método constituyente "numerate") para que acepte una forma plural en la llamada de dos argumentos a "quant" (como en "[quant,_1,archivos]") si es en general más fácil inferir la forma singular de la plural, que inferir la forma plural de la singular.

    Pero para otros idiomas (como se discute ampliamente en Locale::Maketext::TPJ13), el simple "quant"/"numf" no es suficiente. Para los idiomas eslavos particularmente problemáticos, lo que podría necesitar es un método al que proporcione el número, la forma de cita del sustantivo a cuantificar, y el caso y género que la sintaxis de la oración proyecta sobre esa ranura de sustantivo. El método sería entonces responsable de determinar en qué número gramatical se proyecta ese numeral en su frase nominal, y con qué caso y género puede anular el caso y género normales; y luego buscaría el sustantivo en un léxico que proporcione todas las formas flexionadas necesarias.

  • También puede desear discutir con los traductores la cuestión de cómo relacionar diferentes subformas de la misma etiqueta de idioma, considerando cómo esto reacciona con el tratamiento de estas por parte de "get_handle". Por ejemplo, si un usuario acepta interfaces en "en, fr", y usted tiene interfaces disponibles en "en-US" y "fr", ¿qué debería obtener? Puede desear resolver esto estableciendo que "en" y "en-US" son efectivamente sinónimos, haciendo que una clase herede de la otra.

    Para algunos idiomas, este problema puede no surgir nunca (el danés rara vez se expresa como "da-DK", sino simplemente como "da"). Y para otros idiomas, todo el concepto de una forma "genérica" puede rozar lo inútilmente vago, particularmente para interfaces que involucran medios de voz en formas de árabe o chino.

  • Una vez que haya localizado su programa/sitio/etc. para todos los idiomas deseados, asegúrese de mostrar el resultado (ya sea en vivo o mediante capturas de pantalla) a los traductores. Una vez que aprueben, haga todo lo posible para que sea revisado por al menos otro hablante de ese idioma. Esto sigue siendo cierto incluso cuando (o especialmente cuando) la traducción la realiza uno de sus propios programadores. Algunos tipos de sistemas pueden ser más difíciles de probar que otros, dependiendo de la cantidad de jerga y conceptos específicos del dominio involucrados - es más fácil encontrar personas que puedan decirle si aprueban su traducción de "eliminar este mensaje" en una interfaz de correo electrónico a través de la web, que encontrar personas que puedan darle una opinión informada sobre su traducción de "valor de atributo" en la interfaz de una herramienta de consulta XML.

    Recomiendo leer todos estos:

    Locale::Maketext::TPJ13 -- mi artículo de The Perl Journal sobre Maketext. Explica muchos conceptos importantes que subyacen al diseño de Locale::Maketext, y una visión de por qué Maketext es mejor que el enfoque antiguo de tener catálogos de mensajes que son solo bases de datos de formatos sprintf.

    File::Findgrep es una aplicación/módulo de ejemplo que utiliza Locale::Maketext para localizar sus mensajes. Para un sistema internacionalizado más grande, consulte también Apache::MP3.

    I18N::LangTags.

    Win32::Locale.

    RFC 3066, Tags for the Identification of Languages, en http://sunsite.dk/RFC/rfc/rfc3066.html

    RFC 2277, IETF Policy on Character Sets and Languages está en http://sunsite.dk/RFC/rfc/rfc2277.html - gran parte son solo cosas de interés para los diseñadores de protocolos, pero explica algunos conceptos básicos, como la distinción entre localizaciones y etiquetas de idioma.

    El manual de GNU "gettext". La distribución gettext está disponible en "<ftp://prep.ai.mit.edu/pub/gnu/>" - obtenga un tarball reciente de gettext y mire en su directorio "doc/", hay una versión HTML fácilmente navegable allí. La documentación de gettext plantea muchas preguntas que vale la pena considerar, incluso si algunas de sus respuestas son a veces dudosas, particularmente donde empiezan a hablar de pluralización.

    El código fuente de Locale/Maketext.pm. Observe que el módulo es mucho más corto que su documentación.
