NOMBRE

LOCK - bloquear una tabla

SINOPSIS

LOCK [ TABLE ] [ ONLY ] nombre [ * ] [, ...] [ IN modobloqueo MODE ] [ NOWAIT ]
donde modobloqueo es uno de:
    ACCESS SHARE | ROW SHARE | ROW EXCLUSIVE | SHARE UPDATE EXCLUSIVE
    | SHARE | SHARE ROW EXCLUSIVE | EXCLUSIVE | ACCESS EXCLUSIVE

DESCRIPCIÓN

LOCK TABLE obtiene un bloqueo a nivel de tabla, esperando si es necesario a que se liberen los bloqueos conflictivos. Si se especifica NOWAIT, LOCK TABLE no espera a adquirir el bloqueo deseado: si no se puede adquirir inmediatamente, el comando se aborta y se emite un error. Una vez obtenido, el bloqueo se mantiene durante el resto de la transacción actual. (No hay comando UNLOCK TABLE; los bloqueos siempre se liberan al final de la transacción.)

Cuando se bloquea una vista, todas las relaciones que aparecen en la consulta de definición de la vista también se bloquean recursivamente con el mismo modo de bloqueo.

Al adquirir bloqueos automáticamente para comandos que hacen referencia a tablas, PostgreSQL siempre utiliza el modo de bloqueo menos restrictivo posible. LOCK TABLE proporciona casos en los que podría necesitar bloqueos más restrictivos. Por ejemplo, supongamos que una aplicación ejecuta una transacción con el nivel de aislamiento READ COMMITTED y necesita asegurarse de que los datos de una tabla permanezcan estables durante la duración de la transacción. Para lograr esto, podría obtener un bloqueo SHARE sobre la tabla antes de consultarla. Esto evitará cambios concurrentes de datos y garantizará que las lecturas posteriores de la tabla vean una vista estable de los datos confirmados, ya que el modo SHARE del bloqueo entra en conflicto con el bloqueo ROW EXCLUSIVE adquirido por los escritores, y su instrucción LOCK TABLE nombre IN SHARE MODE esperará hasta que los titulares concurrentes de bloqueos ROW EXCLUSIVE confirmen o reviertan. Por lo tanto, una vez que obtiene el bloqueo, no hay escrituras no confirmadas pendientes; además, ninguna puede comenzar hasta que libere el bloqueo.

Para lograr un efecto similar al ejecutar una transacción en el nivel de aislamiento REPEATABLE READ o SERIALIZABLE, debe ejecutar la instrucción LOCK TABLE antes de ejecutar cualquier instrucción SELECT o de modificación de datos. La vista de datos de una transacción REPEATABLE READ o SERIALIZABLE se congelará cuando comience su primera instrucción SELECT o de modificación de datos. Un LOCK TABLE posterior en la transacción seguirá impidiendo escrituras concurrentes, pero no asegurará que lo que la transacción lea corresponda a los últimos valores confirmados.

Si una transacción de este tipo va a cambiar los datos de la tabla, entonces debería usar el modo de bloqueo SHARE ROW EXCLUSIVE en lugar del modo SHARE. Esto asegura que solo una transacción de este tipo se ejecute a la vez. Sin esto, es posible un interbloqueo: dos transacciones podrían adquirir ambas el modo SHARE y luego no poder adquirir también el modo ROW EXCLUSIVE para realizar sus actualizaciones. (Tenga en cuenta que los propios bloqueos de una transacción nunca entran en conflicto, por lo que una transacción puede adquirir el modo ROW EXCLUSIVE cuando tiene el modo SHARE, pero no si alguien más tiene el modo SHARE). Para evitar interbloqueos, asegúrese de que todas las transacciones adquieran bloqueos sobre los mismos objetos en el mismo orden, y si varios modos de bloqueo están involucrados para un solo objeto, entonces las transacciones siempre deben adquirir primero el modo más restrictivo.

Se puede encontrar más información sobre los modos de bloqueo y las estrategias de bloqueo en la Sección 13.3.

PARÁMETROS

nombre

El nombre (opcionalmente calificado por esquema) de una tabla existente para bloquear. Si se especifica ONLY antes del nombre de la tabla, solo se bloquea esa tabla. Si NO se especifica ONLY, se bloquean la tabla y todas sus tablas descendientes (si las hay). Opcionalmente, se puede especificar * después del nombre de la tabla para indicar explícitamente que se incluyen las tablas descendientes.

El comando LOCK TABLE a, b; es equivalente a LOCK TABLE a; LOCK TABLE b;. Las tablas se bloquean una por una en el orden especificado en el comando LOCK TABLE.

modobloqueo

El modo de bloqueo especifica con qué bloqueos entra en conflicto este bloqueo. Los modos de bloqueo se describen en la Sección 13.3.

Si no se especifica ningún modo de bloqueo, se utiliza ACCESS EXCLUSIVE, el modo más restrictivo.

NOWAIT

Especifica que LOCK TABLE no debe esperar a que se liberen los bloqueos conflictivos: si los bloqueos especificados no se pueden adquirir inmediatamente sin esperar, la transacción se aborta.

NOTAS

Para bloquear una tabla, el usuario debe tener el privilegio correcto para el modobloqueo especificado. Si el usuario tiene los privilegios MAINTAIN, UPDATE, DELETE o TRUNCATE sobre la tabla, se permite cualquier modobloqueo. Si el usuario tiene privilegios INSERT sobre la tabla, se permite el modo ROW EXCLUSIVE (o un modo menos conflictivo como se describe en la Sección 13.3). Si un usuario tiene privilegios SELECT sobre la tabla, se permite el modo ACCESS SHARE.

El usuario que realiza el bloqueo en la vista debe tener el privilegio correspondiente en la vista. Además, por defecto, el propietario de la vista debe tener los privilegios relevantes sobre las relaciones base subyacentes, mientras que el usuario que realiza el bloqueo no necesita ningún permiso sobre las relaciones base subyacentes. Sin embargo, si la vista tiene security_invoker establecido en true (ver CREATE VIEW), el usuario que realiza el bloqueo, en lugar del propietario de la vista, debe tener los privilegios relevantes sobre las relaciones base subyacentes.

LOCK TABLE es inútil fuera de un bloque de transacción: el bloqueo permanecería retenido solo hasta la finalización de la instrucción. Por lo tanto, PostgreSQL informa un error si se usa LOCK fuera de un bloque de transacción. Utilice BEGIN y COMMIT (o ROLLBACK) para definir un bloque de transacción.

LOCK TABLE solo se ocupa de bloqueos a nivel de tabla, y por lo tanto, los nombres de modo que involucran ROW son todos nombres inapropiados. Estos nombres de modo generalmente deben leerse como que indican la intención del usuario de adquirir bloqueos a nivel de fila dentro de la tabla bloqueada. Además, el modo ROW EXCLUSIVE es un bloqueo de tabla compartible. Tenga en cuenta que todos los modos de bloqueo tienen semánticas idénticas en lo que respecta a LOCK TABLE, difiriendo solo en las reglas sobre qué modos entran en conflicto con cuáles. Para obtener información sobre cómo adquirir un bloqueo de fila real, consulte la Sección 13.3.2 y La cláusula de bloqueo en la documentación de SELECT(7).

EJEMPLOS

Obtener un bloqueo SHARE en una tabla de clave primaria al realizar inserciones en una tabla de clave foránea:

BEGIN WORK;
LOCK TABLE films IN SHARE MODE;
SELECT id FROM films
    WHERE name = 'Star Wars: Episode I - The Phantom Menace';
-- Hacer ROLLBACK si no se devolvió el registro
INSERT INTO films_user_comments VALUES
    (_id_, '¡GENIAL! ¡Lo estaba esperando tanto tiempo!');
COMMIT WORK;

Tomar un bloqueo SHARE ROW EXCLUSIVE en una tabla de clave primaria al realizar una operación de eliminación:

BEGIN WORK;
LOCK TABLE films IN SHARE ROW EXCLUSIVE MODE;
DELETE FROM films_user_comments WHERE id IN
    (SELECT id FROM films WHERE rating < 5);
DELETE FROM films WHERE rating < 5;
COMMIT WORK;

COMPATIBILIDAD

No existe LOCK TABLE en el estándar SQL, que en su lugar usa SET TRANSACTION para especificar los niveles de concurrencia en las transacciones. PostgreSQL también lo admite; consulte SET TRANSACTION (SET_TRANSACTION(7)) para obtener detalles.

Excepto por los modos de bloqueo ACCESS SHARE, ACCESS EXCLUSIVE y SHARE UPDATE EXCLUSIVE, los modos de bloqueo de PostgreSQL y la sintaxis de LOCK TABLE son compatibles con los presentes en Oracle.

NAME
LOCK - Locking file mechanisms
SYNOPSIS

flock, lockf

DESCRIPTION

The kernel supports mandatory file locking. This is a mechanism to allow cooperating processes to coordinate access to a shared file. Mandatory file locking is enabled on a per-file basis by setting the setgid bit and disabling the group execute bit on the file.

The system calls used are flock(2) and lockf(3).

PARAMETERS

The general syntax for the commands are:

flock [options]

lockf [options]

Where is the file to be locked. Options for flock include:

  • -s: Shared lock (default).
  • -x: Exclusive lock.
  • -n: Do not block if lock cannot be acquired.
  • -w : Wait for lock up to seconds.
  • -o: Close file descriptor on exec.

lockf takes similar arguments but is a library function.

NOTES

Mandatory file locking can be problematic and may lead to deadlocks if not used carefully. It is generally recommended to use other locking mechanisms like advisory locks (e.g., using flock(2) without the setgid/no-execute bits) or database-level locking.

This mechanism is distinct from advisory file locking, which relies on processes cooperating to check for locks before accessing files.

EXAMPLES

To acquire an exclusive lock on a file:

flock -x /path/to/your/file

To acquire a shared lock and wait if it's not available:

flock /path/to/your/file

To attempt to acquire a lock without blocking:

flock -n /path/to/your/file

COMPATIBILITY

Mandatory file locking is a POSIX standard feature, but its implementation and behavior can vary across different Unix-like systems.
