LWP::UserAgent(3) Documentación de Perl aportada por el usuario LWP::UserAgent(3)

NOMBRE

LWP::UserAgent - Clase de agente de usuario web

SINOPSIS

use strict;
use warnings;
use LWP::UserAgent ();
my $ua = LWP::UserAgent->new(timeout => 10);
$ua->env_proxy;
my $response = $ua->get('http://example.com');
if ($response->is_success) {
    print $response->decoded_content;
}
else {
    die $response->status_line;
}

Capas adicionales de seguridad (nota la "cookie_jar" y "protocols_allowed"):

use strict;
use warnings;
use HTTP::CookieJar::LWP ();
use LWP::UserAgent       ();
my $jar = HTTP::CookieJar::LWP->new;
my $ua  = LWP::UserAgent->new(
    cookie_jar        => $jar,
    protocols_allowed => ['http', 'https'],
    timeout           => 10,
);
$ua->env_proxy;
my $response = $ua->get('http://example.com');
if ($response->is_success) {
    print $response->decoded_content;
}
else {
    die $response->status_line;
}

DESCRIPCIÓN

LWP::UserAgent es una clase que implementa un agente de usuario web. Los objetos LWP::UserAgent pueden ser utilizados para enviar peticiones web.

En uso normal, la aplicación crea un objeto LWP::UserAgent y luego lo configura con valores para tiempos de espera, proxies, nombre, etc. Luego crea una instancia de HTTP::Request para la petición que necesita ser realizada. Esta petición se pasa luego a uno de los métodos de petición del Agente de Usuario, que la envía usando el protocolo relevante y devuelve un objeto HTTP::Response. Hay métodos de conveniencia para enviar los tipos de petición más comunes: "get" en LWP::UserAgent, "head" en LWP::UserAgent, "post" en LWP::UserAgent, "put" en LWP::UserAgent y "delete" en LWP::UserAgent. Al usar estos métodos, la creación del objeto de petición está oculta como se muestra en la sinopsis.

El enfoque básico de la biblioteca es usar comunicación estilo HTTP para todos los esquemas de protocolo. Esto significa que construirás objetos HTTP::Request y recibirás objetos HTTP::Response incluso para recursos que no son HTTP como gopher y ftp. Para lograr aún más similitud con las comunicaciones estilo HTTP, los menús gopher y los directorios de archivos se convierten a documentos HTML.

MÉTODOS CONSTRUCTORES

Los siguientes métodos constructores están disponibles:

clone

my $ua2 = $ua->clone;

Devuelve una copia del objeto LWP::UserAgent.

ADVERTENCIA: Ten en cuenta que el método clone no copia ni clona tu atributo "cookie_jar". Debido a las restricciones limitadas sobre lo que se puede usar para tu cookie jar, no hay forma de clonar el atributo. El atributo "cookie_jar" será "undef" en la nueva instancia de objeto.

new

my $ua = LWP::UserAgent->new( %options )

Este método construye un nuevo objeto LWP::UserAgent y lo devuelve. Se pueden proporcionar argumentos de par clave/valor para configurar el estado inicial. Las siguientes opciones corresponden a los métodos de atributo descritos a continuación:

CLAVE                   POR DEFECTO
-----------             --------------------
agent                   "libwww-perl/#.###"
conn_cache              undef
cookie_jar              undef
cookie_jar_class        HTTP::Cookies
default_headers         HTTP::Headers->new
from                    undef
local_address           undef
max_redirect            7
max_size                undef
no_proxy                []
parse_head              1
protocols_allowed       undef
protocols_forbidden     undef
proxy                   {}
requests_redirectable   ['GET', 'HEAD']
send_te                 1
show_progress           undef
ssl_opts                { verify_hostname => 1 }
timeout                 180

Las siguientes opciones adicionales también son aceptadas: Si se pasa la opción "env_proxy" con un valor verdadero, se leen la configuración del proxy de las variables de entorno (ver "env_proxy" en LWP::UserAgent). Si no se proporciona "env_proxy", la variable de entorno "PERL_LWP_ENV_PROXY" controla si "env_proxy" en LWP::UserAgent se llama durante la inicialización. Si el valor de la opción "keep_alive" está definido y es distinto de cero, se configura una "LWP::ConnCache" (ver "conn_cache" en LWP::UserAgent). El valor de "keep_alive" se pasa como la "total_capacity" para el caché de conexión.

"proxy" debe establecerse como un arrayref de pares clave/valor. "no_proxy" toma un arrayref de dominios.

ATRIBUTOS

La configuración de los atributos de configuración modifica el comportamiento del LWP::UserAgent al enviar peticiones. La mayoría de estos también pueden ser inicializados por opciones pasadas al método constructor.

Los siguientes métodos de atributo se proporcionan. El valor del atributo no se modifica si no se proporciona ningún argumento. El valor de retorno de cada método es el valor antiguo del atributo.

agent

my $agent = $ua->agent;
$ua->agent('Checkbot/0.4 ');    # añadir el predeterminado al final
$ua->agent('Mozilla/5.0');
$ua->agent("");                 # no identificarse

Obtiene/establece el token de producto que se utiliza para identificar al agente de usuario en la red. El valor del agente se envía como cabecera "User-Agent" en las peticiones.

El valor predeterminado es una cadena de la forma "libwww-perl/#.###", donde "#.###" se sustituye por el número de versión de esta biblioteca.

Si la cadena proporcionada termina con un espacio, se le añade la cadena predeterminada "libwww-perl/#.###".

La cadena del agente de usuario deben ser uno o más identificadores de producto simples con un número de versión opcional separados por el carácter "/".

conn_cache

my $cache_obj = $ua->conn_cache;
$ua->conn_cache( $cache_obj );

Obtiene/establece el objeto LWP::ConnCache a utilizar. Ver LWP::ConnCache para más detalles.

cookie_jar

my $jar = $ua->cookie_jar;
$ua->cookie_jar( $cookie_jar_obj );

Obtiene/establece el objeto cookie jar a utilizar. El único requisito es que el objeto cookie jar debe implementar los métodos extract_cookies($response) y add_cookie_header($request). Estos métodos serán entonces invocados por el agente de usuario a medida que se envían las peticiones y se reciben las respuestas. Normalmente será un objeto HTTP::Cookies o alguna subclase. Sin embargo, se te anima a usar HTTP::CookieJar::LWP en su lugar. Ver "MEJORES PRÁCTICAS" para más información.

use HTTP::CookieJar::LWP ();
my $jar = HTTP::CookieJar::LWP->new;
my $ua = LWP::UserAgent->new( cookie_jar => $jar );
# o después de la creación del objeto
$ua->cookie_jar( $cookie_jar );

Por defecto, no hay cookie jar, es decir, nunca se añaden cabeceras "Cookie" automáticamente a las peticiones.

Si $jar contiene una referencia de hash sin bendecir, se crea automáticamente un nuevo objeto cookie jar. El objeto es de la clase establecida con el argumento del constructor "cookie_jar_class", que por defecto es HTTP::Cookies.

$ua->cookie_jar({ file => "$ENV{HOME}/.cookies.txt" });

es realmente solo un atajo para:

require HTTP::Cookies;
$ua->cookie_jar(HTTP::Cookies->new(file => "$ENV{HOME}/.cookies.txt"));

Como se describió anteriormente y en "MEJORES PRÁCTICAS", deberías establecer "cookie_jar_class" a "HTTP::CookieJar::LWP" para obtener un cookie jar más seguro.

my $ua = LWP::UserAgent->new( cookie_jar_class => 'HTTP::CookieJar::LWP' );
$ua->cookie_jar({}); # HTTP::CookieJar::LWP no toma argumentos

Estos también se pueden combinar en el constructor, así

cookie_jar

my $cj = $ua->cookie_jar;
$ua->cookie_jar( $cj );

Get/set the cookie jar object. By default, a "HTTP::CookieJar" object is created at instantiation.

my $ua = LWP::UserAgent->new(
  cookie_jar_class => 'HTTP::CookieJar::LWP',
  cookie_jar       =>  {},
);

credentials

my $creds = $ua->credentials();
$ua->credentials( $netloc, $realm );
$ua->credentials( $netloc, $realm, $uname, $pass );
$ua->credentials("www.example.com:80", "Some Realm", "foo", "secret");

Obtiene/establece el nombre de usuario y la contraseña que se utilizarán para un dominio.

El $netloc es una cadena con el formato "<host>:<puerto>". El nombre de usuario y la contraseña solo se pasarán a este servidor.

default_header

$ua->default_header( $field );
$ua->default_header( $field => $value );
$ua->default_header('Accept-Encoding' => scalar HTTP::Message::decodable());
$ua->default_header('Accept-Language' => "no, en");

Este es solo un atajo para "$ua->default_headers->header( $field => $value )".

default_headers

my $headers = $ua->default_headers;
$ua->default_headers( $headers_obj );

Obtiene/establece el objeto de encabezados que proporcionará los valores de encabezados predeterminados para cualquier solicitud enviada. Por defecto, será un objeto HTTP::Headers vacío.

from

my $from = $ua->from;
$ua->from('foo@bar.com');

Obtiene/establece la dirección de correo electrónico del usuario humano que controla el agente de usuario solicitante. La dirección debe ser utilizable por máquinas, según se define en RFC2822 https://tools.ietf.org/html/rfc2822. El valor "from" se envía como el encabezado "From" en las solicitudes.

El valor predeterminado es no enviar un encabezado "From". Consulte "default_headers" en LWP::UserAgent para obtener la interfaz más general que permite que cualquier encabezado sea predeterminado.

local_address

my $address = $ua->local_address;
$ua->local_address( $address );

Obtiene/establece la interfaz local a la que vincularse para las conexiones de red. La interfaz se puede especificar como un nombre de host o una dirección IP. Este valor se pasa como argumento "LocalAddr" a IO::Socket::INET.

max_redirect

my $max = $ua->max_redirect;
$ua->max_redirect( $n );

Lee o establece el límite del objeto de cuántas veces obedecerá las respuestas de redirección en un ciclo de solicitud dado.

Por defecto, el valor es 7. Esto significa que si llama a "request" en LWP::UserAgent y la respuesta es una redirección a otro lugar que a su vez es una redirección, y así sucesivamente siete veces, entonces LWP se rinde después de esa séptima solicitud.

max_size

my $size = $ua->max_size;
$ua->max_size( $bytes );

Obtiene/establece el límite de tamaño para el contenido de la respuesta. El valor predeterminado es "undef", lo que significa que no hay límite. Si el contenido de la respuesta devuelto es solo parcial, porque se superó el límite de tamaño, entonces se agregará un encabezado "Client-Aborted" a la respuesta. El contenido puede terminar siendo más largo que "max_size", ya que abortamos una vez que la adición de un fragmento de datos hace que la longitud supere el límite. El encabezado "Content-Length", si está presente, indicará la longitud del contenido completo y normalmente no será el mismo que length($res->content).

parse_head

my $bool = $ua->parse_head;
$ua->parse_head( $boolean );

Obtiene/establece un valor que indica si debemos inicializar los encabezados de respuesta desde la sección <head> de los documentos HTML. El valor predeterminado es verdadero. *No desactive esto* a menos que sepa lo que está haciendo.

protocols_allowed

my $aref = $ua->protocols_allowed;      # obtener protocolos permitidos
$ua->protocols_allowed( \@protocols );  # permitir SOLO estos
$ua->protocols_allowed(undef);          # eliminar la lista
$ua->protocols_allowed(['http',]);      # permitir SOLO http

Por defecto, un objeto no tiene ni una lista de "protocols_allowed" ni una lista de "protocols_forbidden" en LWP::UserAgent.

Esto lee (o establece) la lista de protocolos de este agente de usuario que los métodos de solicitud permitirán exclusivamente. Los nombres de los protocolos no distinguen entre mayúsculas y minúsculas.

Por ejemplo: "$ua->protocols_allowed( [ 'http', 'https'] );" significa que este agente de usuario *permitirá solo* esos protocolos, y los intentos de usar este agente de usuario para acceder a URLs con otros esquemas (como "ftp://...") resultarán en un error 500.

Tenga en cuenta que tener una lista de "protocols_allowed" hace que cualquier lista de "protocols_forbidden" en LWP::UserAgent sea ignorada.

protocols_forbidden

my $aref = $ua->protocols_forbidden;    # obtener la lista prohibida
$ua->protocols_forbidden(\@protocols);  # no permitir estos
$ua->protocols_forbidden(['http',]);    # Todas las solicitudes http obtienen un 500
$ua->protocols_forbidden(undef);        # eliminar la lista

Esto lee (o establece) la lista de protocolos de este agente de usuario que el método de solicitud *no* permitirá. Los nombres de los protocolos no distinguen entre mayúsculas y minúsculas.

Por ejemplo: "$ua->protocols_forbidden( [ 'file', 'mailto'] );" significa que este agente de usuario *no* permitirá esos protocolos, y los intentos de usar este agente de usuario para acceder a URLs con esos esquemas resultarán en un error 500.

requests_redirectable

my $aref = $ua->requests_redirectable;
$ua->requests_redirectable( \@requests );
$ua->requests_redirectable(['GET', 'HEAD',]); # el predeterminado

Lee o establece la lista de nombres de solicitudes del objeto para las cuales "redirect_ok" en LWP::UserAgent permitirá la redirección. Por defecto, es "['GET', 'HEAD']", según RFC 2616 https://tools.ietf.org/html/rfc2616. Para cambiarlo para incluir "POST", considere:

push @{ $ua->requests_redirectable }, 'POST';

send_te

my $bool = $ua->send_te;
$ua->send_te( $boolean );

Si es verdadero, enviará un encabezado "TE" junto con la solicitud. El valor predeterminado es verdadero. Establézcalo en falso para deshabilitar el encabezado "TE" para sistemas que no pueden manejarlo.

show_progress

my $bool = $ua->show_progress;
$ua->show_progress( $boolean );

Obtiene/establece un valor que indica si se debe mostrar una barra de progreso en la terminal a medida que se procesan las solicitudes. El valor predeterminado es falso.

ssl_opts

my @keys = $ua->ssl_opts;
my $val = $ua->ssl_opts( $key );
$ua->ssl_opts( $key => $value );

Obtiene/establece las opciones para conexiones SSL. Sin argumento devuelve la lista de claves de opciones actualmente establecidas. Con un solo argumento devuelve el valor actual para la opción dada. Con 2 argumentos establece el valor de la opción y devuelve el anterior. Establecer una opción en el valor "undef" elimina esta opción.

Las opciones que LWP relaciona son:

"verify_hostname" => $bool
Cuando es VERDADERO, LWP se asegurará para esquemas de protocolo seguros de conectarse a servidores que tengan un certificado válido que coincida con el nombre de host esperado. Si es FALSO, no se realizan comprobaciones y no se puede estar seguro de que se comunica con el par esperado. El comportamiento de no comprobación fue el predeterminado para libwww-perl-5.837 y versiones anteriores.

Esta opción se inicializa desde la variable de entorno "PERL_LWP_SSL_VERIFY_HOSTNAME". Si esta variable de entorno no está configurada; entonces "verify_hostname" tiene un valor predeterminado de 1.

Tenga en cuenta que recientemente el efecto general de esta opción con respecto al manejo de SSL ha cambiado. A partir de la versión 6.11 de LWP::Protocol::https, que es un módulo externo, la verificación del certificado SSL se armonizó para comportarse de manera sincronizada con IO::Socket::SSL. Con este cambio, establecer esta opción ya no deshabilita toda la verificación del certificado SSL, solo las comprobaciones del nombre de host. Para deshabilitar toda la verificación, use la opción "SSL_verify_mode" en el atributo "ssl_opts". Por ejemplo: "$ua-"ssl_opts(SSL_verify_mode => IO::Socket::SSL::SSL_VERIFY_NONE);>

"SSL_ca_file" => $path
La ruta a un archivo que contiene certificados de Autoridad Certificadora. Se proporciona una configuración predeterminada para esta opción comprobando las variables de entorno "PERL_LWP_SSL_CA_FILE" y "HTTPS_CA_FILE" en orden.
"SSL_ca_path" => $path
La ruta a un directorio que contiene archivos que contienen certificados de Autoridad Certificadora. Se proporciona una configuración predeterminada para esta opción comprobando las variables de entorno "PERL_LWP_SSL_CA_PATH" y "HTTPS_CA_DIR" en orden.

Otras opciones se pueden establecer y son procesadas directamente por la implementación del Socket SSL en uso. Consulte IO::Socket::SSL o Net::SSL para obtener detalles.

El núcleo de libwww-perl ya no incluye complementos de protocolo para SSL. Deberá instalar LWP::Protocol::https por separado para habilitar el soporte para procesar URLs https.

timeout

TIMEOUT

my $secs = $ua->timeout;
$ua->timeout( $secs );

Obtener/establecer el valor del tiempo de espera en segundos. El valor predeterminado es 180 segundos, es decir, 3 minutos.

La solicitud se aborta si no se observa ninguna actividad en la conexión con el servidor durante "timeout" segundos. Esto significa que el tiempo que tarda la transacción completa y el método "request" en LWP::UserAgent en retornar podría ser mayor.

Cuando una solicitud excede el tiempo de espera, aún se devuelve un objeto de respuesta. La respuesta tendrá un Código de Estado HTTP estándar (500). Esta respuesta tendrá la cabecera "Client-Warning" establecida con el valor de "Internal response". Vea la descripción del método "get" en LWP::UserAgent a continuación para más detalles.

No se admite la desactivación del tiempo de espera, pero se puede establecer en un valor arbitrariamente grande.

ATTRIBUTOS DE PROXY

Los siguientes métodos configuran cuándo se deben pasar las solicitudes a través de un servidor proxy.

env_proxy

$ua->env_proxy;

Carga la configuración del proxy desde las variables de entorno *_proxy. Puede especificar proxies de la siguiente manera (sintaxis sh):

gopher_proxy=http://proxy.example.org/
wais_proxy=http://proxy.example.org/
no_proxy="localhost,example.com"
export gopher_proxy wais_proxy no_proxy

Los usuarios de csh o tcsh deben usar el comando "setenv" para definir estas variables de entorno.

En sistemas con variables de entorno que no distinguen mayúsculas de minúsculas, existe un conflicto de nombres entre las variables de entorno CGI y la variable de entorno "HTTP_PROXY" que normalmente recoge "env_proxy". Debido a esto, "HTTP_PROXY" no se respeta para scripts CGI. Se puede utilizar la variable de entorno "CGI_HTTP_PROXY" en su lugar.

no_proxy

$ua->no_proxy( @domains );
$ua->no_proxy('localhost', 'example.com');
$ua->no_proxy(); # limpia la lista

No envíe solicitudes a través de proxy a los dominios dados, incluidos los subdominios. Llamar a "no_proxy" sin ningún dominio limpia la lista de dominios.

proxy

$ua->proxy(\@schemes, $proxy_url)
$ua->proxy(['http', 'ftp'], 'http://proxy.sn.no:8001/');
# Para un solo esquema:
$ua->proxy($scheme, $proxy_url)
$ua->proxy('gopher', 'http://proxy.sn.no:8001/');
# Para configurar varios proxies a la vez:
$ua->proxy([
    ftp => 'http://ftp.example.com:8001/',
    [ 'http', 'https' ] => 'http://http.example.com:8001/',
]);

Establecer/recuperar la URL del proxy para un esquema.

La primera forma especifica que la URL se utilizará como proxy para los métodos de acceso listados en la lista del primer argumento del método, es decir, "http" y "ftp".

La segunda forma muestra una forma abreviada de especificar la URL del proxy para un solo esquema de acceso.

La tercera forma demuestra la configuración de varios proxies a la vez. Esta es también la única forma aceptada por el constructor.

MANEJADORES

Los manejadores son código que se inyecta en varias fases durante el procesamiento de las solicitudes. Los siguientes métodos se proporcionan para administrar los manejadores activos:

add_handler

$ua->add_handler( $phase => \&cb, %matchspec )

Añade un manejador para ser invocado en la fase de procesamiento dada. Para especificar %matchspec, consulte "Matching" en HTTP::Config.

Los valores posibles de $phase y las firmas de devolución de llamada correspondientes son las siguientes. Tenga en cuenta que los manejadores se documentan en el orden en que se ejecutarán, que es:

request_preprepare
request_prepare
request_send
response_header
response_data
response_done
response_redirect
request_preprepare => sub { my($request, $ua, $handler) = @_; ... }
El manejador se llama antes de "request_prepare" y otras inicializaciones estándar de la solicitud. Esto se puede usar para configurar cabeceras y atributos de los que depende el manejador "request_prepare". La inicialización del proxy debería tener lugar aquí; pero en general, no registre manejadores para esta fase.
request_prepare => sub { my($request, $ua, $handler) = @_; ... }
El manejador se llama antes de que se envíe la solicitud y puede modificarla como le parezca. Por ejemplo, esto se puede usar para agregar ciertas cabeceras a solicitudes específicas.

El método puede asignar un nuevo objeto de solicitud a $_[0] para reemplazar la solicitud que se envía completamente.

El valor de retorno de la devolución de llamada se ignora. Si se genera una excepción, abortará la solicitud y hará que el método de solicitud devuelva una respuesta de "400 Bad request".

request_send => sub { my($request, $ua, $handler) = @_; ... }
Este manejador tiene la oportunidad de manejar las solicitudes antes de que se envíen a los manejadores de protocolo. Debe devolver un objeto HTTP::Response si desea terminar el procesamiento; de lo contrario, no debería devolver nada.

Los manejadores "response_header" y "response_data" no se invocarán para esta respuesta, pero "response_done" sí.

response_header => sub { my($response, $ua, $handler) = @_; ... }
Este manejador se llama justo después de que se hayan recibido las cabeceras de respuesta, pero antes de cualquier dato de contenido. El manejador puede configurar manejadores para los datos y puede fallar para abortar la solicitud.

El manejador puede establecer el valor de "$response->{default_add_content}" para controlar si los datos recibidos deben agregarse directamente al objeto de respuesta. Inicialmente será falso si el método "$ua->request()" se llamó con un argumento $content_file o "$content_cb"; de lo contrario, será verdadero.

response_data => sub { my($response, $ua, $handler, $data) = @_; ... }
Este manejador se llama por cada fragmento de datos recibido para la respuesta. El manejador puede fallar para abortar la solicitud.

Este manejador debe devolver un valor VERDADERO para ser llamado nuevamente para fragmentos subsiguientes de la misma solicitud.

response_done => sub { my($response, $ua, $handler) = @_; ... }
El manejador se llama después de que la respuesta se haya recibido por completo, pero antes de que se intente manejar cualquier redireccionamiento. El manejador se puede utilizar para extraer información o modificar la respuesta.
response_redirect => sub { my($response, $ua, $handler) = @_; ... }
El manejador se llama en "$ua->request" después de "response_done". Si el manejador devuelve un objeto HTTP::Request, comenzaremos de nuevo con el procesamiento de esta solicitud.

Para todos estos, $handler es una referencia de código al manejador que se está ejecutando actualmente.

get_my_handler

$ua->get_my_handler( $phase, %matchspec );
$ua->get_my_handler( $phase, %matchspec, $init );

Recuperará el manejador coincidente como referencia hash.

Si se pasa $init como un valor verdadero, creará y agregará el manejador si no se encuentra. Si $init es una referencia a una subrutina, se llama con el hash del manejador creado como argumento. Esta subrutina puede poblar el hash con campos adicionales; especialmente el callback. Si $init es una referencia hash, fusione los hashes.

handlers

$ua->handlers( $phase, $request )
$ua->handlers( $phase, $response )

Devuelve los manejadores que se aplican a la solicitud o respuesta dada en la fase de procesamiento dada.

remove_handler

$ua->remove_handler( undef, %matchspec );
$ua->remove_handler( $phase, %matchspec );
$ua->remove_handler(); # ELIMINA TODOS LOS MANEJADORES EN TODAS LAS FASES

Elimina los manejadores que coinciden con %matchspec dada. Si no se proporciona $phase, elimina los manejadores de todas las fases.

Tenga cuidado, ya que llamar a esta función con un %matchspec que no es lo suficientemente específico puede eliminar manejadores que no le pertenecen. Probablemente sea mejor usar el método "set_my_handler" en LWP::UserAgent.

Se devuelven los manejadores eliminados.

set_my_handler

$ua->set_my_handler( $phase, $cb, %matchspec );
$ua->set_my_handler($phase, undef); # elimina el manejador para la fase

Establece manejadores privados para la subrutina ejecutora. Funciona estableciendo un campo "owner" a %matchspec que contiene el nombre de la subrutina llamada. Puede pasar un "owner" explícito para anular esto.

Si se pasa $cb como "undef", elimina el manejador.

get

my $res = $ua->get( $url );
my $res = $ua->get( $url , $field_name => $value, ... );

Este método enviará una solicitud "GET" a la URL dada. Se pueden proporcionar argumentos adicionales para inicializar las cabeceras de la solicitud. Estos se proporcionan como pares de nombre/valor separados. El valor de retorno es un objeto de respuesta. Consulte HTTP::Response para obtener una descripción de la interfaz que proporciona.

Aún se devolverá un objeto de respuesta cuando LWP no pueda conectarse al servidor especificado en la URL o cuando ocurran otros fallos en los manejadores de protocolo. Estas respuestas internas utilizan los códigos de estado HTTP estándar, por lo que las respuestas no se pueden diferenciar probando solo el código de estado de la respuesta. Las respuestas de error que LWP genera internamente tendrán la cabecera "Client-Warning" establecida en el valor "Internal response". Si necesita diferenciar estas respuestas internas de las respuestas que un servidor remoto genera realmente, debe probar el valor de esta cabecera.

Los nombres de campo que comienzan con ":" son especiales. Estos no inicializarán las cabeceras de la solicitud, sino que determinarán cómo se trata el contenido de la respuesta. Se reconocen los siguientes nombres de campo especiales:

':content_file'   => $filename # o $filehandle
':content_cb'     => \&callback
':read_size_hint' => $bytes

Si se proporciona un $filename o $filehandle con la opción ":content_file", el contenido de la respuesta se guardará allí en lugar de en el objeto de respuesta. El $filehandle también puede ser un objeto con un descriptor de archivo abierto, como un objeto File::Temp. Si se proporciona una función de devolución de llamada con la opción ":content_cb", esta función se llamará para cada fragmento del contenido de la respuesta a medida que se recibe del servidor. Si no se proporcionan estas opciones, el contenido de la respuesta se acumulará en el propio objeto de respuesta. Esto podría no ser adecuado para cuerpos de respuesta muy grandes. Solo se puede especificar uno de ":content_file" o ":content_cb". El contenido de las respuestas no exitosas siempre se acumulará en el propio objeto de respuesta, independientemente de las opciones ":content_file" o ":content_cb" pasadas. Tenga en cuenta que los errores al escribir en el archivo de contenido (por ejemplo, debido a permiso denegado o a que el sistema de archivos está lleno) se informarán a través de las cabeceras de respuesta "Client-Aborted" o "X-Died", y no a través del método "is_success".

La opción ":read_size_hint" se pasa al módulo de protocolo, que intentará leer datos del servidor en fragmentos de este tamaño. Un valor más pequeño para ":read_size_hint" resultará en un mayor número de invocaciones de la función de devolución de llamada.

La función de devolución de llamada se llama con 3 argumentos: un fragmento de datos, una referencia al objeto de respuesta y una referencia al objeto de protocolo. La función de devolución de llamada puede abortar la solicitud invocando die(). El mensaje de excepción aparecerá como el campo de cabecera "X-Died" en la respuesta devuelta por el método "$ua->get()".

Este método enviará una solicitud "HEAD" a la URL dada. De lo contrario, funciona como el método "get" en LWP::UserAgent descrito anteriormente.

is_protocol_supported

my $bool = $ua->is_protocol_supported( $scheme );

Puede utilizar este método para comprobar si este objeto de agente de usuario admite el "scheme" especificado. (El "scheme" puede ser una cadena (como "http" o "ftp") o puede ser una referencia de objeto URI.)

Si un esquema es compatible se determina mediante las listas "protocols_allowed" o "protocols_forbidden" del agente de usuario (si las hay), y por las capacidades de LWP. Es decir, esto devolverá verdadero solo si LWP admite este protocolo *y* está permitido para este objeto en particular.

is_online

my $bool = $ua->is_online;

Intenta determinar si tiene acceso a Internet. Devuelve 1 (verdadero) si las heurísticas integradas determinan que el agente de usuario puede acceder a Internet (a través de HTTP) o 0 (falso).

Ver también LWP::Online.

mirror

my $res = $ua->mirror( $url, $filename );

Este método obtendrá el documento identificado por la URL y lo almacenará en un archivo llamado $filename. Si el archivo ya existe, la solicitud contendrá una cabecera "If-Modified-Since" que coincide con la hora de modificación del archivo. Si el documento en el servidor no ha cambiado desde esa hora, no sucederá nada. Si el documento se ha actualizado, se descargará nuevamente. La hora de modificación del archivo se forzará a que coincida con la del servidor.

Utiliza "move" en File::Copy para intentar reemplazar atmicamente el $filename.

El valor de retorno es un objeto HTTP::Response.

Falla si la respuesta para obtener el documento contiene una cabecera "X-Died".

# Cualquier versión de HTTP::Message funciona con esta forma:
my $res = $ua->patch( $url, $field_name => $value, Content => $content );
# El uso de referencias a hash o array requiere HTTP::Message >= 6.12
use HTTP::Request 6.12;
my $res = $ua->patch( $url, \%form );
my $res = $ua->patch( $url, \@form );
my $res = $ua->patch( $url, \%form, $field_name => $value, ... );
my $res = $ua->patch( $url, $field_name => $value, Content => \%form );
my $res = $ua->patch( $url, $field_name => $value, Content => \@form );

Este método enviará una solicitud "PATCH" a la URL dada, con %form o @form proporcionando los pares clave/valor para el contenido del formulario a rellenar. Las cabeceras adicionales y las opciones de contenido son las mismas que para el método "get" en LWP::UserAgent.

ADVERTENCIA:

Este método solo puede aceptar contenido que esté en pares clave-valor al usar HTTP::Request::Common antes de la versión 6.12. Cualquier uso de referencias a hash o array resultará en un error antes de la versión 6.12.

Este método utilizará la función "PATCH" de HTTP::Request::Common para construir la solicitud. Consulte HTTP::Request::Common para obtener más detalles sobre cómo pasar contenido de formulario y otras funciones avanzadas.

NOMBRE

LWP::UserAgent

SINOPSIS

use LWP::UserAgent;

DESCRIPCIÓN

LWP::UserAgent es un módulo de Perl que proporciona una interfaz sencilla para realizar peticiones HTTP. Permite crear y enviar peticiones a varios servidores web, manejar redirecciones y gestionar cookies. El módulo está diseñado para ser fácil de usar, al tiempo que ofrece flexibilidad para usuarios avanzados.
