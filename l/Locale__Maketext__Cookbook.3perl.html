LÉXICOS UNILATERALES

Adaptado de una sugerencia de Dan Muey

Puede ser común (por ejemplo, en su léxico principal) que las claves y los valores del hash coincidan. Como en este caso:

q{Hola, dime tu nombre}
  => q{Hola, dime tu nombre}

Sería bueno simplemente escribir:

q{Hola, dime tu nombre} => ''

y que esto se expanda mágicamente a la primera forma. Entre las ventajas de tal representación, esto llevaría a archivos más pequeños, menos propensos a errores tipográficos o de pegado, y útil para alguien que lo traduce, que puede simplemente copiar el léxico principal e introducir la traducción en lugar de tener que eliminar el valor primero.

Eso se puede lograr sobrescribiendo "init" en su clase y trabajando en el léxico principal con código como este:

package My::I18N;
...
sub init {
    my $lh = shift; # un manejador recién creado
    $lh->SUPER::init();
    inflate_lexicon(\%My::I18N::en::Lexicon);
    return;
}
sub inflate_lexicon {
    my $lex = shift;
    while (my ($k, $v) = each %$lex) {
        $v = $k if !defined $v || $v eq '';
    }
}

Aquí asumimos que "My::I18N::en" posee el léxico principal.

Hay algunas desventajas aquí: la economía de espacio no se mantendrá en tiempo de ejecución después de que se ejecute este init(). Pero no debería ser tan crítico, ya que si no tiene espacio para eso, tampoco tendrá espacio para ningún otro idioma además del principal. También podría hacerlo con enlaces (ties), expandiendo el valor en el momento de la consulta, lo que debería ser más costoso en tiempo como opción.

LUGARES DECIMALES EN EL FORMATO DE NÚMEROS

Después de CPAN RT #36136 (https://rt.cpan.org/Ticket/Display.html?id=36136)

La documentación de Locale::Maketext aconseja que el método de corchetes estándar "numf" es limitado y que debe sobrescribirlo para obtener mejores resultados. Incluso sugiere el uso de Number::Format.

Un defecto de "numf" estándar es no poder usar una precisión decimal determinada. Por ejemplo,

$lh->maketext('pi es [numf,_1]', 355/113);

produce

pi es 3.14159292035398

Dado que pi ≈ 355/116 solo es preciso hasta 6 lugares decimales, querría decir:

$lh->maketext('pi es [numf,_1,6]', 355/113);

y obtener "pi es 3.141592".

Una solución para eso podría usar "Number::Format" de esta manera:

package Wuu;
use base qw(Locale::Maketext);
use Number::Format;
# puede ser sobrescrito según las convenciones del idioma
sub _numf_params {
    return (
        -thousands_sep  => '.',
        -decimal_point  => ',',
        -decimal_digits => 2,
    );
}
# construye un Number::Format
sub _numf_formatter {
    my ($lh, $scale) = @_;
    my @params = $lh->_numf_params;
    if ($scale) { # usa escala explícita en lugar de la predeterminada
        push @params, (-decimal_digits => $scale);
    }
    return Number::Format->new(@params);
}
sub numf {
    my ($lh, $n, $scale) = @_;
    # obtiene el formateador (en caché)
    my $nf = $lh->{__nf}{$scale} ||= $lh->_numf_formatter($scale);
    # formatea el número en sí
    return $nf->format_number($n);
}
package Wuu::pt;
use base qw(Wuu);

y luego

my $lh = Wuu->get_handle('pt');
$lh->maketext('A [numf,_1,3] km de distância', 1550.2222);

devolvería "A 1.550,222 km de distância".

Note que los métodos utilitarios estándar de "Locale::Maketext" son irremediablemente limitados porque no podrían pretender hacer todo lo que se podría esperar de ellos en diferentes idiomas, culturas y aplicaciones. Por lo tanto, extender "numf", "quant", y "sprintf" es natural tan pronto como sus necesidades excedan lo que hacen los estándar.
