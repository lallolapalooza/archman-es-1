RESUMEN

Log::Log4perl proporciona una potente API de registro para tu aplicación

DESCRIPCIÓN

Log::Log4perl permite controlar y ajustar el comportamiento de registro de tu sistema desde el exterior. Implementa el popular paquete de registro (basado en Java) Log4j en Perl puro.

Para un tutorial detallado sobre el uso de Log::Log4perl, por favor lee

http://www.perl.com/pub/a/2002/09/11/log4perl.html

El registro es mejor que un depurador si quieres saber qué está sucediendo en tu código en tiempo de ejecución. Sin embargo, los paquetes de registro tradicionales son demasiado estáticos y generan un torrente de mensajes de registro en tus archivos de registro que no te ayudarán.

"Log::Log4perl" es diferente. Te permite controlar el número de mensajes de registro generados en tres niveles diferentes:

  • En una ubicación central en tu sistema (ya sea en un archivo de configuración o en el código de inicio) especificas qué componentes (clases, funciones) de tu sistema deben generar registros.
  • Especificas cuán detallado debe ser el registro de estos componentes especificando niveles de registro.
  • También especificas a qué llamados receptores (appenders) quieres enviar tus mensajes de registro ("Imprímelo en la pantalla y también añádelo a /tmp/my.log") y en qué formato ("Escribe primero la fecha, luego el nombre del archivo y número de línea, y luego el mensaje de registro") deben estar.

Este es un mecanismo muy potente y flexible. Puedes activar y desactivar tus registros en cualquier momento, especificar el nivel de detalle y hacer que dependa del subsistema que se esté ejecutando actualmente.

Permíteme darte un ejemplo: Podrías descubrir que tu sistema tiene un problema en el componente "MySystem::Helpers::ScanDir". Activar registros de depuración detallados en todo el sistema generaría una avalancha de mensajes de registro inútiles y ralentizaría tu sistema hasta hacerlo irreconocible. Sin embargo, con "Log::Log4perl", puedes decirle al sistema: "Continúa registrando solo errores graves en el archivo de registro. Abre un segundo archivo de registro, activa los registros de depuración completos en el componente "MySystem::Helpers::ScanDir" y vuelca todos los mensajes que se originen allí en el nuevo archivo de registro". Y todo esto es posible simplemente cambiando los parámetros en un archivo de configuración, ¡que tu sistema puede volver a leer incluso mientras se está ejecutando!

Cómo usarlo

El paquete "Log::Log4perl" se puede inicializar de dos maneras: ya sea a través de comandos de Perl o a través de un archivo de configuración al estilo "log4j".

Inicializar a través de un archivo de configuración

Esta es la forma más fácil de preparar tu sistema para usar "Log::Log4perl". Usa un archivo de configuración como este:

############################################################
# Un registrador raíz simple con un receptor (appender) de
# Log::Log4perl::Appender::File en Perl.
############################################################
log4perl.rootLogger=ERROR, LOGFILE

log4perl.appender.LOGFILE=Log::Log4perl::Appender::File
log4perl.appender.LOGFILE.filename=/var/log/myerrs.log
log4perl.appender.LOGFILE.mode=append

log4perl.appender.LOGFILE.layout=PatternLayout
log4perl.appender.LOGFILE.layout.ConversionPattern=[%r] %F %L %c - %m%n

Estas líneas definen tu registrador estándar que está añadiendo errores graves a "/var/log/myerrs.log", usando el formato

[milisegundos] archivo-origen número-línea clase - mensaje nueva-línea

Suponiendo que este archivo de configuración se guarda como "log.conf", necesitas leerlo en la sección de inicio de tu código, usando los siguientes comandos:

use Log::Log4perl;
Log::Log4perl->init("log.conf");

Después de que eso se haya hecho en algún lugar del código, puedes obtener objetos de registro en cualquier lugar del código. Ten en cuenta que no hay necesidad de transportar ninguna referencia de registrador con tus funciones y métodos. Puedes obtener un registrador en cualquier momento a través de un mecanismo singleton:

package My::MegaPackage;
use  Log::Log4perl;
sub some_method {
    my($param) = @_;
    my $log = Log::Log4perl->get_logger("My::MegaPackage");
    $log->debug("Mensaje de depuración");
    $log->info("Mensaje informativo");
    $log->error("Mensaje de error");
    ...
}

Con la configuración anterior, "Log::Log4perl" escribirá "Mensaje de error" en el archivo de registro especificado, pero no hará nada para las llamadas debug() y info(), porque el nivel de registro se ha establecido en "ERROR" para todos los componentes en la primera línea del archivo de configuración mostrado anteriormente.

¿Por qué "Log::Log4perl->get_logger" y no "Log::Log4perl->new"? No queremos crear un nuevo objeto cada vez. Normalmente en Programación Orientada a Objetos, creas un objeto una vez y usas la referencia a él para llamar a sus métodos. Sin embargo, esto requiere que pases el objeto a todas las funciones y lo último que queremos es contaminar cada una de las funciones/métodos que usamos con un manejador para el "Logger":

sub function {  # ¡Puaj!
    my($logger, $some, $other, $parameters) = @_;
}

En su lugar, si una función/método quiere una referencia al registrador, simplemente llama al método estático get_logger($category) del Registrador para obtener una referencia al único objeto registrador posible de una categoría determinada. Eso se llama un singleton si eres fan de Gamma.

¿Cómo sabe el registrador qué mensajes debe registrar y cuáles suprimir? "Log::Log4perl" trabaja con herencia: El archivo de configuración anterior no especificó nada sobre "My::MegaPackage". Y aun así, hemos definido un registrador de la categoría "My::MegaPackage". En este caso, "Log::Log4perl" subirá la jerarquía de nombres ("My" y luego estamos en la raíz) para determinar si un nivel de registro está definido en alguna parte. En el caso anterior, el nivel de registro en la raíz (la raíz *siempre* define un nivel de registro, pero no necesariamente un receptor) define que el nivel de registro debe ser "ERROR", lo que significa que los mensajes *DEBUG* e *INFO* se suprimen. Nota que esta 'herencia' no está relacionada con la herencia de clases de Perl, solo está relacionada con el espacio de nombres del registrador. Por cierto, si alguna vez dudas de cuál es la categoría de un registrador, usa "$logger->category()" para recuperarla.

Si su nivel de registro configurado es "WARN", entonces los mensajes registrados con info(), debug() y trace() serán suprimidos. fatal(), error() y warn() pasarán, porque su prioridad es mayor o igual que la configuración.

En lugar de llamar a los métodos

$logger->trace("...");  # Registra un mensaje de traza
$logger->debug("...");  # Registra un mensaje de depuración
$logger->info("...");   # Registra un mensaje informativo
$logger->warn("...");   # Registra un mensaje de advertencia
$logger->error("...");  # Registra un mensaje de error
$logger->fatal("...");  # Registra un mensaje fatal

también puede llamar al método log() con el nivel apropiado usando las constantes definidas en "Log::Log4perl::Level":

use Log::Log4perl::Level;
$logger->log($TRACE, "...");
$logger->log($DEBUG, "...");
$logger->log($INFO, "...");
$logger->log($WARN, "...");
$logger->log($ERROR, "...");
$logger->log($FATAL, "...");

Esta forma rara vez se usa, pero es útil si desea registrar en diferentes niveles dependiendo del código de salida de una función:

$logger->log( $exit_level{ $rc }, "...");

En cuanto a necesitar más niveles de registro que estos predefinidos: Generalmente es mejor dirigir su comportamiento de registro a través del mecanismo de categorías.

Si necesita averiguar si el nivel de registro actualmente configurado permitiría que una declaración de registro de un logger pasara, use los métodos "is_level()" del logger:

$logger->is_trace()    # Verdadero si los mensajes de traza pasarían
$logger->is_debug()    # Verdadero si los mensajes de depuración pasarían
$logger->is_info()     # Verdadero si los mensajes informativos pasarían
$logger->is_warn()     # Verdadero si los mensajes de advertencia pasarían
$logger->is_error()    # Verdadero si los mensajes de error pasarían
$logger->is_fatal()    # Verdadero si los mensajes fatales pasarían

Ejemplo: "$logger->is_warn()" devuelve verdadero si el nivel actual del logger, derivado de la categoría del logger (o, en ausencia de eso, de la configuración de nivel de uno de los padres del logger) es $WARN, $ERROR o $FATAL.

También hay una serie de funciones más al estilo Java que devuelven los mismos valores. Estas tienen el formato "isLevelEnabled()", por lo que "$logger->isDebugEnabled()" es sinónimo de "$logger->is_debug()".

Estas funciones de verificación de nivel serán útiles más adelante, cuando queramos bloquear la construcción de parámetros costosos innecesarios en caso de que el nivel de registro sea demasiado bajo para registrar la declaración de todos modos, como en:

if($logger->is_error()) {
    $logger->error("Matriz errónea: @super_long_array");
}

Si hubiéramos escrito solo

$logger->error("Matriz errónea: @super_long_array");

Perl habría interpolado @super_long_array en la cadena a través de una operación costosa solo para descubrir poco después que la cadena puede ser ignorada por completo porque el nivel de registro configurado es inferior a $ERROR.

El mensaje a registrar pasado a todas las funciones descritas anteriormente puede consistir en un número arbitrario de argumentos, que las funciones de registro simplemente encadenan a una sola cadena. Por lo tanto

$logger->debug("Hola ", "Mundo", "!");  # y
$logger->debug("Hola Mundo!");

son idénticos.

Tenga en cuenta que incluso si uno de los métodos anteriores devuelve verdadero, no significa necesariamente que el mensaje se registrará. Lo que is_debug() verifica es que el logger utilizado está configurado para permitir que pase un mensaje de la prioridad dada (DEBUG). Pero después de esta verificación, Log4perl aplicará filtros personalizados y reenviará el mensaje a uno o más appenders. Ninguno de estos es verificado por is_xxx(), por la simple razón de que es imposible saber qué hace un filtro personalizado con un mensaje sin tener el mensaje real o qué hace un appender con un mensaje sin registrarlo realmente.

Registrar y morir o advertir

A menudo, cuando haces croak / carp / warn / die, quieres registrar esos mensajes. En lugar de hacer lo siguiente:

$logger->fatal($err) && die($err);

puede usar lo siguiente:

$logger->logdie($err);

Y si en lugar de usar

warn($message);
$logger->warn($message);

para emitir una advertencia a través del mecanismo de warn() de Perl y asegurarse de tener el mismo mensaje en el archivo de registro también, use:

$logger->logwarn($message);

Dado que hay un nivel de ERROR entre WARN y FATAL, hay dos funciones auxiliares adicionales en caso de que desee usar ERROR para warn() o die():

$logger->error_warn();
$logger->error_die();

Finalmente, están las funciones Carp que, además de registrar, también pasan el mensaje serializado a sus compañeros en el paquete Carp:

$logger->logcarp();        # advertir con rastreo de pila de 1 nivel
$logger->logcluck();       # advertir con rastreo de pila completo
$logger->logcroak();       # morir con rastreo de pila de 1 nivel
$logger->logconfess();     # morir con rastreo de pila completo

Appenders (Receptores)

Si no define ningún appender, no sucederá nada. Los appenders se activarán siempre que el nivel de registro configurado requiera que un mensaje sea registrado y no suprimido.

"Log::Log4perl" no define ningún appender por defecto, ni siquiera el logger raíz tiene uno.

"Log::Log4perl" ya viene con un conjunto estándar de appenders:

Log::Log4perl::Appender::Screen

Log::Log4perl::Appender::File
Log::Log4perl::Appender::Socket
Log::Log4perl::Appender::DBI
Log::Log4perl::Appender::Synchronized
Log::Log4perl::Appender::RRDs

para registrar en la pantalla, en archivos y en bases de datos.

En CPAN, puede encontrar appenders adicionales como

Log::Log4perl::Layout::XMLLayout

Ejemplo de Appender

Ahora, supongamos que queremos registrar mensajes de prioridad info() o superior en la categoría "Foo::Bar" tanto en STDOUT como en un archivo de registro, digamos "test.log". En la sección de inicialización de su sistema, simplemente defina dos appenders utilizando los módulos fácilmente disponibles "Log::Log4perl::Appender::File" y "Log::Log4perl::Appender::Screen":

use Log::Log4perl;
   # Configuración en una cadena ...
my $conf = q(
  log4perl.category.Foo.Bar          = INFO, Logfile, Screen
  log4perl.appender.Logfile          = Log::Log4perl::Appender::File
  log4perl.appender.Logfile.filename = test.log
  log4perl.appender.Logfile.layout   = Log::Log4perl::Layout::PatternLayout
  log4perl.appender.Logfile.layout.ConversionPattern = [%r] %F %L %m%n
  log4perl.appender.Screen         = Log::Log4perl::Appender::Screen
  log4perl.appender.Screen.stderr  = 0
  log4perl.appender.Screen.layout = Log::Log4perl::Layout::SimpleLayout
);
   # ... pasado como una referencia a init()
Log::Log4perl::init( \$conf );

Una vez que la inicialización mostrada anteriormente ha ocurrido una vez, típicamente en el código de inicio de su sistema, simplemente use el logger definido en cualquier lugar de su sistema:

##########################
# ... en alguna función ...
##########################
my $log = Log::Log4perl::get_logger("Foo::Bar");
  # Registra tanto en STDOUT como en el archivo test.log
$log->info("¡Información importante!");

La configuración de "layout" especificada en la sección de configuración define el formato en el que se registrará el mensaje por el appender especificado. El formato que se muestra para el appender de archivo registra no solo el mensaje sino también el número de milisegundos desde que el programa comenzó (%r), el nombre del archivo donde ocurrió la llamada al logger y el número de línea allí (%F y %L), el mensaje en sí (%m) y un carácter de nueva línea específico del sistema operativo (%n):

[187] ./myscript.pl 27 ¡Información importante!

El appender de pantalla anterior, por otro lado, utiliza un "SimpleLayout", que registra el nivel de depuración, un guión (-) y el mensaje de registro:

INFO - ¡Información importante!

Para obtener información más detallada sobre los formatos de layout, consulte "Diseños de Registro".

Formatting and Shortcuts

This section describes Log4perl's built-in shortcuts for formatting log messages.

You are logging something like

    # ¡Caro en modo no depuración!
for (@super_long_array) {
    $logger->debug("Elemento: $_");
}

and &#64;super_long_array is bastante grande, por lo que iterar sobre él es bastante caro. Solo tú, el programador, sabes que atravesar ese bucle "for" se puede omitir por completo si el nivel de registro actual para el componente real es superior a "debug". En este caso, use esto en su lugar:

    # ¡Barato en modo no depuración!
if($logger->is_debug()) {
    for (@super_long_array) {
        $logger->debug("Elemento: $_");
    }
}

Si teme que la generación de los parámetros para la función de registro sea bastante costosa, use cierres:

    # Pasado como referencia de subrutina
use Data::Dumper;
$logger->debug(sub { Dumper($data) } );

Esto no desplegará $data a través de Dumper() a menos que realmente sea necesario porque está registrado. Además, Log::Log4perl le permite especificar argumentos para las funciones de registro en la sintaxis de salida del filtro de mensajes:

$logger->debug("Estructura: ",
               { filter => \&Dumper,
                 value  => $someref });

De esta manera, poco antes de que Log::Log4perl envíe el mensaje a cualquier appender, buscará todos los argumentos en busca de referencias a hashes y los tratará de manera especial:

Invocará la función dada como referencia con la clave "filter" (Data::Dumper::Dumper()) y le pasará el valor que vino con la clave llamada "value" como argumento. El hash anónimo en la llamada anterior será reemplazado por el valor de retorno de la función de filtro.

Categorías

Las categorías también se llaman "Loggers" en Log4perl, ambas se refieren a lo mismo y estos términos se usan indistintamente. "Log::Log4perl" utiliza categorías para determinar si una declaración de registro en un componente debe ejecutarse o suprimirse en el nivel de registro actual. La mayoría de las veces, estas categorías son solo las clases en las que se encuentran las declaraciones de registro:

package Candy::Twix;
sub new {
    my $logger = Log::Log4perl->get_logger("Candy::Twix");
    $logger->debug("Creando una nueva barra Twix");
    bless {}, shift;
}

# ...
package Candy::Snickers;
sub new {
    my $logger = Log::Log4perl->get_logger("Candy.Snickers");
    $logger->debug("Creando una nueva barra Snickers");
    bless {}, shift;
}
# ...
package main;
Log::Log4perl->init("mylogdefs.conf");
    # => "LOG> Creando una nueva barra Snickers"
my $first = Candy::Snickers->new();
    # => "LOG> Creando una nueva barra Twix"
my $second = Candy::Twix->new();

Tenga en cuenta que puede separar los niveles de jerarquía de su categoría usando puntos como en Java (.) o dobles dos puntos (::) como en Perl. Ambas notaciones son equivalentes y se manejan de la misma manera internamente.

Sin embargo, las categorías solo existen para hacer uso de la herencia: si invoca un logger en una subcategoría, ascenderá en la jerarquía y llamará a los appenders apropiados. Internamente, las categorías no están relacionadas con la jerarquía de clases del programa en absoluto, son puramente virtuales. Puede usar categorías arbitrarias, por ejemplo, en el siguiente programa, que no es de estilo oo, sino procedural:

sub print_portfolio {
    my $log = Log::Log4perl->get_logger("user.portfolio");
    $log->debug("Cotizaciones solicitadas: @_");
    for(@_) {
        print "$_: ", get_quote($_), "\n";
    }
}
sub get_quote {
    my $log = Log::Log4perl->get_logger("internet.quotesystem");
    $log->debug("Obteniendo cotización: $_[0]");
    return yahoo_quote($_[0]);
}

El logger en la primera función, "print_portfolio", se asigna a la categoría (virtual) "user.portfolio". Dependiendo de la configuración de "Log4perl", esto llamará a un appender de "user.portfolio", un appender de "user", o un appender asignado a la raíz, sin que "user.portfolio" tenga ninguna relevancia para el sistema de clases utilizado en el programa. El logger en la segunda función se adhiere a la categoría "internet.quotesystem", nuevamente, tal vez porque está agrupado con otras funciones de Internet, pero no porque exista una clase con ese nombre en algún lugar.

Sin embargo, tenga cuidado, no se exceda: si está desarrollando un sistema en estilo orientado a objetos, usar la jerarquía de clases suele ser su mejor opción. Piense en las personas que se harán cargo de su código algún día: la jerarquía de clases es probablemente lo que conocen de inmediato, por lo que les resulta fácil ajustar el registro a sus necesidades.

Desactivar un componente

"Log4perl" no solo le permite activar selectivamente una categoría de mensajes de registro, sino que también puede usar el mecanismo para desactivar selectivamente el registro en ciertos componentes, mientras que el registro se mantiene activado en categorías de nivel superior. Este mecanismo resulta útil si descubre que, al aumentar el nivel de registro de una categoría de alto nivel (es decir, cerca de la raíz), un componente registra más de lo que debería.

Así es como funciona:

############################################################
# Desactivar el registro en una categoría de nivel inferior
# mientras se mantiene activa en categorías de nivel superior.
############################################################
log4perl.rootLogger=DEBUG, LOGFILE
log4perl.logger.deep.down.the.hierarchy = ERROR, LOGFILE
# ... Definir appenders ...

De esta manera, los mensajes de registro emitidos desde dentro de "Deep::Down::The::Hierarchy" y inferiores solo se registrarán si son "ERROR" o peores, mientras que en todos los demás componentes del sistema incluso los mensajes "DEBUG" se registrarán.

Valores de retorno

Todos los métodos de registro devuelven valores que indican si su mensaje llegó realmente a uno o más appenders. Si el mensaje ha sido suprimido debido a restricciones de nivel, se devuelve "undef".

Por ejemplo,

my $ret = $logger->info("Mensaje");

devolverá "undef" si el nivel de depuración del sistema para la categoría actual no es "INFO" o más permisivo. Si Log::Log4perl reenvió el mensaje a uno o más appenders, se devuelve el número de appenders.

Si los appenders deciden vetar el mensaje con un umbral de appender, se excluirán los appenders del valor de retorno del método de registro. Esto significa que si tiene un appender que mantiene un umbral de appender y está registrando un mensaje que pasa el obstáculo del nivel de registro del sistema pero no el umbral del appender, la función de registro devolverá 0.

En resumen: las funciones de registro devolverán un valor *verdadero* si el mensaje llegó a uno o más appenders y un valor *falso* si no lo hizo. Esto permite construcciones como

$logger->fatal("@_") or print STDERR "@_\n";

que asegurará que el mensaje fatal no se pierda si el nivel actual es inferior a FATAL o se imprima dos veces si el nivel es aceptable pero un appender ya apunta a STDERR.

Trampas con las categorías

Tenga cuidado al reutilizar ciegamente los paquetes del sistema como categorías. Si lo hace, tendrá problemas con los métodos heredados. Imagine la siguiente configuración de clase:

use Log::Log4perl;
###########################################
package Bar;
###########################################
sub new {
    my($class) = @_;
    my $logger = Log::Log4perl::get_logger(__PACKAGE__);
    $logger->debug("Creando instancia");
    bless {}, $class;
}
###########################################
package Bar::Twix;
###########################################
our @ISA = qw(Bar);
###########################################
package main;
###########################################
Log::Log4perl->init(\ qq{
log4perl.category.Bar.Twix = DEBUG, Screen
log4perl.appender.Screen = Log::Log4perl::Appender::Screen
log4perl.appender.Screen.layout = SimpleLayout
});
my $bar = Bar::Twix->new();

"Bar::Twix" simplemente hereda todo de "Bar", incluido el constructor new(). Contrariamente a lo que podría pensar al principio, esto no registrará nada. La razón es la llamada a get_logger() en el paquete "Bar", que siempre obtendrá un logger de la categoría "Bar", incluso si llamamos a new() a través del paquete "Bar::Twix", lo que hará que perl suba en el árbol de herencia para ejecutar realmente Bar::new(). Dado que solo hemos definido el comportamiento de registro para "Bar::Twix" en el archivo de configuración, no sucederá nada.

Esto se puede solucionar cambiando el método get_logger() en Bar::new() para obtener un logger de la categoría que coincida con la clase *real* del objeto, como en

    # ... en Bar::new() ...
my $logger = Log::Log4perl::get_logger( $class );

En un método que no sea el constructor, el nombre de la clase del objeto real se puede obtener llamando a ref() en la referencia del objeto, por lo que

package BaseClass;
use Log::Log4perl qw( get_logger );
sub new {
    bless {}, shift;
}
sub method {
    my( $self ) = @_;
    get_logger( ref $self )->debug( "mensaje" );
}
package SubClass;
our @ISA = qw(BaseClass);

es el patrón recomendado para asegurarse de que

my $sub = SubClass->new();
$sub->meth();

comience a registrar si la categoría "SubClass" (y no la categoría "BaseClass" tenga habilitado el registro en el nivel DEBUG.

Reinicio automático de archivos de configuración modificados

En lugar de inicializar staticamente Log::Log4perl mediante:

Log::Log4perl->init($conf_file);

hay una forma de tener Log::Log4perl verificar periódicamente en la configuración y re cargar si es necesario:

Log::Log4perl->init_and_watch($conf_file, $delay);

En este modo, Log::Log4perl examinará el archivo de configuración $conf_file cada $delay segundos para cambios a través del tiempo de modificación del archivo. Si el archivo ha sido actualizado, se lo re cargará y sustituirá la configuración actual de Log::Log4perl.

Este conveniente modo funciona así: con cada llamada a una función de logger (debug(), is_debug(), etc.), Log::Log4perl comprobará si el intervalo de espera ha expirado. Si sí, ejecutará una verificación -M file en el archivo de configuración. Si el tiempo de modificación del archivo ha sido alterado, el actual configuración se dumpará y el nuevo contenido del archivo se cargará.

Esta conveniencia tiene un costo, aunque: llamando a time() con cada llamada a una función de logging, especialmente las que son "suppressed" (!), hace que estos llamados de Log4perl se lentes 40% más lentos.

Para aliviar este impacto de rendimiento, init_and_watch() puede configurarse para escuchar por un señal Unix para re cargar la configuración: 

Log::Log4perl->init_and_watch($conf_file, 'HUP');

Esto establecerá un señalero para SIGHUP y re cargará la configuración si el aplicación recibe esta señal, por ejemplo mediante el comando "kill":

kill -HUP pid

donde "pid" es el identificador del proceso de la aplicación. Esto te lleva de vuelta a alrededor del 85% de la velocidad normal de ejecución de Log::Log4perl para los registros suprimidos. Para más detalles, consulta el apartado de Performance. Para más información sobre el gestor de señales, busca el apartado de SIGNAL MODE en Log::Log4perl::Config::Watch.

Si tienes un retraso ligeramente largo entre las verificaciones de archivos de configuración físicas o no quieres usar el señal asociado con el monitor de configuración, puedes activar un re inicio de configuración al siguiente posible momento llamando a:

Log::Log4perl::Config->watcher->force_next_check();

Una cosa a tener en cuenta: si el archivo de configuración contiene un error de sintaxis o otro error grave, una aplicación en ejecución dejará de funcionar con "die" si esta configuración dañada se carga durante el runtime, ya sea por un señal o si el periodo de espera ha expirado y el cambio se detecta. Esta comportamiento podría cambiar en el futuro.

Para permitir a la aplicación interceptar y controlar un re inicio de configuración en modo init_and_watch, se puede especificar una callback:

Log::Log4perl->init_and_watch($conf_file, 10, { 
        preinit_callback => \&callback });

Si Log4perl detecta que la configuración necesita ser re cargada, llamará la función preinit_callback sin parámetros. Si el callback devuelve un valor verdadero, Log4perl procederá y re cargará la configuración. Si el callback devuelve un valor falso, Log4perl dejará la configuración antigua y evitará re cargarla hasta el próximo ciclo. Dentro del callback, una aplicación puede ejecutar todas las comprobaciones posibles, incluyendo acceder al archivo de configuración, que está disponible mediante "Log::Log4perl::Config->watcher()->file()".

Ganchos de Perl en el archivo de configuración

Si algunos de los valores utilizados en el archivo de configuración de Log4perl necesitan ser modificados dinámicamente por el programa, utilice ganchos de Perl:

log4perl.appender.File.filename = \
    sub { return getLogfileName(); }

Cada valor que comienza con la cadena "sub {...\" se interpreta como código Perl que se ejecutará en el momento en que la aplicación analice la configuración a través de Log::Log4perl::init(). El valor de retorno de la subrutina es utilizado por Log::Log4perl como el valor de configuración.

El código Perl se ejecuta en el paquete "main"; las funciones de otros paquetes deben ser llamadas con notación completamente calificada.

Aquí hay otro ejemplo, que utiliza una variable de entorno como nombre de usuario para un appender DBI:

log4perl.appender.DB.username = \
    sub { $ENV{DB_USER_NAME } }

Sin embargo, tenga en cuenta la diferencia entre estos fragmentos de código y los utilizados para especificadores de conversión definidos por el usuario, como se discute en Log::Log4perl::Layout::PatternLayout: mientras que los fragmentos anteriores se ejecutan *una vez* cuando se llama a Log::Log4perl::init(), los fragmentos de especificador de conversión se ejecutan *cada vez* que se renderiza un mensaje de acuerdo con PatternLayout.

NOTA DE SEGURIDAD: esta característica significa que se puede incrustar código perl arbitrario en el archivo de configuración. En el raro caso de que las personas que tienen acceso a su archivo de configuración sean diferentes de las personas que escriben su código y no deberían tener derechos de ejecución, es posible que desee configurar

Log::Log4perl::Config->allow_code(0);

antes de llamar a init(). Alternativamente, puede proporcionar un conjunto restringido de opcodes de Perl que se pueden incrustar en el archivo de configuración, como se describe en "Restringir qué opcodes pueden estar en un gancho de Perl".

Restringir qué opcodes pueden estar en un gancho de Perl

El valor que pasa a Log::Log4perl::Config->allow_code() determina si el código que se incrusta en el archivo de configuración se evalúa sin restricciones o se evalúa en un compartimento seguro (Safe). Por defecto, se asume un valor de '1', que realiza una 'eval' normal sin restricciones. Un valor de '0', sin embargo, impide que se evalúe cualquier código incrustado.

Si desea un control detallado sobre lo que se puede incluir o no en el código incrustado, utilice los siguientes métodos:

Log::Log4perl::Config->allow_code( $allow );
Log::Log4perl::Config->allowed_code_ops($op1, $op2, ... );
Log::Log4perl::Config->vars_shared_with_safe_compartment( [ \%vars | $package, \@vars ] );
Log::Log4perl::Config->allowed_code_ops_convenience_map( [ \%map | $name, \@mask ] );

Log::Log4perl::Config->allowed_code_ops() toma una lista de máscaras de opcodes que se permiten ejecutar en el compartimento. Las máscaras de opcodes deben especificarse como se describe en Opcode:

Log::Log4perl::Config->allowed_code_ops(':subprocess');

Este ejemplo permitiría que operaciones de Perl como las comillas inversas, system, fork y waitpid se ejecutaran en el compartimento. Por supuesto, probablemente no querrá usar esta máscara, ya que permitiría exactamente lo que el compartimento seguro está diseñado para prevenir.

Log::Log4perl::Config->vars_shared_with_safe_compartment() toma los símbolos que deben exportarse al compartimento seguro antes de que se evalúe el código. Las claves de este hash son los nombres de los paquetes en los que se encuentran los símbolos, y los valores son referencias de arreglo a los nombres literales de los símbolos. Para mayor comodidad, la configuración predeterminada exporta el hash '%ENV' del paquete 'main' al compartimento:

Log::Log4perl::Config->vars_shared_with_safe_compartment(
  main => [ '%ENV' ],
);

Log::Log4perl::Config->allowed_code_ops_convenience_map() es un método de acceso a un mapa de nombres de conveniencia a máscaras de opcodes. Actualmente, los siguientes nombres de conveniencia están definidos:

safe        = [ ':browse' ]
restrictive = [ ':default' ]

Por conveniencia, si se llama a Log::Log4perl::Config->allow_code() con un valor que es una clave del mapa definido previamente con Log::Log4perl::Config->allowed_code_ops_convenience_map(), entonces los opcodes permitidos se establecen de acuerdo con el valor definido en el mapa. Si esto es confuso, considere lo siguiente:

use Log::Log4perl;

my $config = <<'END';
 log4perl.logger = INFO, Main
 log4perl.appender.Main = Log::Log4perl::Appender::File
 log4perl.appender.Main.filename = \
     sub { "example" . getpwuid($<) . ".log" }
 log4perl.appender.Main.layout = Log::Log4perl::Layout::SimpleLayout
END

$Log::Log4perl::Config->allow_code('restrictive');
Log::Log4perl->init( \$config );       # fallará
$Log::Log4perl::Config->allow_code('safe');
Log::Log4perl->init( \$config );       # tendrá éxito

La razón por la que la primera llamada a ->init() falla es porque el nombre 'restrictive' se mapea a una máscara de opcodes ':default'. getpwuid() no forma parte de ':default', por lo que ->init() falla. El nombre 'safe' se mapea a una máscara de opcodes ':browse', que permite que getpwuid() se ejecute, por lo que ->init() tiene éxito.

Se puede invocar allowed_code_ops_convenience_map() de varias maneras:

allowed_code_ops_convenience_map()

allowed_code_ops_convenience_map( \%map )
Reemplaza todo el mapa de nombres de conveniencia con la referencia de hash suministrada.
allowed_code_ops_convenience_map( $name )
Devuelve la máscara de opcodes para el nombre de conveniencia dado, o undef si no se define ningún nombre de este tipo en el mapa.
allowed_code_ops_convenience_map( $name, \@mask )
Agrega el par nombre/máscara dado al mapa de nombres de conveniencia. Si el nombre ya existe en el mapa, su valor se reemplaza con la nueva máscara.

Agrega el par paquete/lista de variables dado al mapa. Si el paquete ya existe en el mapa, su valor se reemplaza con la nueva referencia de arreglo de nombres de variables.

Para obtener más información sobre opcodes y compartimentos seguros (Safe), consulte Opcode y Safe.

Cambiar el nivel de registro en un logger

Log4perl proporciona algunas funciones internas para ajustar rápidamente el nivel de registro desde dentro de un programa Perl en ejecución.

Ahora, algunas personas argumentarían que deberías ajustar tus niveles desde un archivo de configuración externo de Log4perl, pero Log4perl es el favorito de todos.

Típicamente, el ajuste de niveles en tiempo de ejecución se realiza al principio, o en respuesta a alguna entrada externa (como un comando de tiempo de ejecución de "más registro" para diagnóstico).

Obtienes el nivel de registro de un objeto logger con:

$current_level = $logger->level();

y puedes establecerlo con el mismo método, siempre que primero importes las constantes de nivel de registro, con:

use Log::Log4perl::Level;

Luego puedes establecer el nivel en un logger a una de las constantes,

$logger->level($ERROR); # uno de DEBUG, INFO, WARN, ERROR, FATAL

Para *aumentar* el nivel de registro que se está realizando actualmente, usa:

$logger->more_logging($delta);

y para *disminuirlo*, usa:

$logger->less_logging($delta);

$delta debe ser un entero positivo (por ahora, podemos arreglar esto más tarde ;).

También hay dos funciones equivalentes:

$logger->inc_level($delta);
$logger->dec_level($delta);

Se incluyen para permitirle una opción de legibilidad. Algunas personas preferirán more/less_logging, ya que son bastante claras en lo que hacen, y permiten al programador no preocuparse demasiado por lo que es un Nivel y si un nivel más alto significa más o menos registro. Sin embargo, otras personas que entienden y tienen mucho código que trata con niveles probablemente preferirán los métodos inc_level() y dec_level() ya que quieren trabajar con Niveles y no preocuparse por si eso significa más o menos registro. :)

Dejando esa diatriba a un lado, típicamente usarás more_logging() o inc_level() de la siguiente manera:

my $v = 0; # nivel predeterminado de verbosidad.

GetOptions("v+" => \$v, ...);
if( $v ) {
  $logger->more_logging($v); # aumenta el nivel de registro una vez por cada -v en ARGV
}

Niveles de registro personalizados

En primer lugar, permítanme decirles que los desarrolladores de log4j desaconsejan en gran medida la creación de niveles personalizados. De hecho, en lugar de crear niveles adicionales además de los predefinidos DEBUG, INFO, WARN, ERROR y FATAL, deberías usar categorías para controlar la cantidad de registro de forma inteligente, basándose en la ubicación del código activo de registro en el sistema.

Sin embargo, Log4perl proporciona una buena forma de crear niveles personalizados a través de la función de rutina create_custom_level(). Sin embargo, esto debe hacerse antes de la primera llamada a init() o get_l

Niveles de registro en todo el sistema

Como medida bastante drástica para reducir (o aumentar) el nivel de registro en todo el sistema con una sola opción de configuración, use la palabra clave "threshold" en el archivo de configuración de Log4perl:

log4perl.threshold = ERROR

Esto establece el nivel del sistema (o el nivel de jerarquía según la documentación de log4j) a ERROR, y así niega a todos los loggers del sistema la posibilidad de registrar mensajes de niveles inferiores.

Modo fácil

Para fines didácticos (especialmente para [1]), he incluido el modo ":easy" en "Log::Log4perl", que inicializa un único logger raíz con un nivel definido y un appender de pantalla que incluye un layout estándar:

### Inicio de sección
use Log::Log4perl qw(:easy);
Log::Log4perl->easy_init($ERROR);  # Establece el nivel del logger raíz a ERROR
### Sección de aplicación
my $logger = get_logger();
$logger->fatal("Esto se registrará.");
$logger->debug("Esto no se registrará.");

Esto se mostraría así:

2002/08/04 11:43:09 ERROR> script.pl:16 main::función - Esto se registrará.

Aunque esto ha demostrado funcionar bien para familiarizar a los usuarios con "Log::Logperl", evitando eficazmente que los usuarios se sientan abrumados con múltiples ajustes (categorías, appenders, niveles, layouts), el objetivo de "Log::Log4perl" es permitir que los usuarios utilicen categorías desde el principio para acostumbrarse al concepto. Por lo tanto, lo mantendré bastante oculto en la página de manual (con gratitud por haber leído hasta aquí).

Loggers sigilosos

A veces, la gente es perezosa. Si deseas la comodidad de "Log::Log4perl" sin tener que mantener un archivo de configuración de log4perl o un bloque de 5 líneas definido para añadir tus mensajes a un archivo, puedes usar las siguientes características:

use Log::Log4perl qw(:easy);
Log::Log4perl->easy_init( { level   => $DEBUG,
                            file    => ">>test.log" } );
    # Se registra en test.log mediante un logger sigiloso
DEBUG("¡Depura esto!");
INFO("¡Informa esto!");
WARN("¡Advierte esto!");
ERROR("¡Error esto!");
some_function();
sub some_function {
        # Así mismo aquí
    FATAL("¡Fatal esto!");
}

En modo ":easy", "Log::Log4perl" instanciará un *logger sigiloso* e introducirá las funciones de conveniencia "TRACE", DEBUG(), INFO(), WARN(), ERROR(), FATAL() y "ALWAYS" en el espacio de nombres del paquete. Estas funciones solo toman mensajes como argumentos y los envían a los métodos de logger sigiloso ("debug()).

Si un mensaje no debe ser bloqueado, independientemente del nivel de registro, usa la función "ALWAYS" que corresponde a un nivel de registro de "OFF":

ALWAYS "Esto se imprime independientemente del nivel de registro";

El método "easy_init" se puede llamar con un único valor de nivel para crear un appender de STDERR y un logger raíz como en:

Log::Log4perl->easy_init($DEBUG);

o, como se muestra a continuación (y en el ejemplo anterior), con una referencia a un hash, especificando valores para "level" (el nivel del logger), "file" (el destino del appender), "category" (la categoría del logger) y "layout" para la especificación del layout del appender. Todos los pares clave-valor son opcionales, con los valores predeterminados de $DEBUG para "level", "STDERR" para "file", "" (categoría raíz) para "category" y "%d %m%n" para "layout":

Log::Log4perl->easy_init( { level    => $DEBUG,
                            file     => ">test.log",
                            utf8     => 1,
                            category => "Bar::Twix",
                            layout   => '%F{1}-%L-%M: %m%n' } );

El parámetro "file" toma nombres de archivo precedidos por ">" (sobrescribir) y ">>" (añadir) como argumentos. Esto provocará la creación de un appender "Log::Log4perl::Appender::File" detrás de escena. Los términos "STDOUT" y "STDERR" (sin ">" o ">>") también se reconocen, que utilizarán y configurarán "Log::Log4perl::Appender::Screen" adecuadamente. La opción "utf8", si se establece a un valor verdadero, ejecutará un comando "binmode" en el manejador de archivo para establecer una disciplina de línea utf8 en el archivo, de lo contrario se mostrará un mensaje de advertencia de 'wide character in print' y probablemente no obtendrás la salida esperada.

Los loggers sigilosos se pueden utilizar en diferentes paquetes, solo necesitas asegurarte de llamar a la función "use" en cada paquete que esté utilizando los servicios fáciles de "Log::Log4perl":

package Bar::Twix;
use Log::Log4perl qw(:easy);
sub eat { DEBUG("Twix mjam"); }
package Bar::Mars;
use Log::Log4perl qw(:easy);
sub eat { INFO("Mars mjam"); }
package main;
use Log::Log4perl qw(:easy);
Log::Log4perl->easy_init( { level    => $DEBUG,
                            file     => ">>test.log",
                            category => "Bar::Twix",
                            layout   => '%F{1}-%L-%M: %m%n' },
                          { level    => $DEBUG,
                            file     => "STDOUT",
                            category => "Bar::Mars",
                            layout   => '%m%n' },
                        );
Bar::Twix::eat();
Bar::Mars::eat();

Como se muestra arriba, "easy_init() aceptará cualquier número de definiciones de logger diferentes como referencias de hash.

También tienen las funciones LOGWARN(), LOGDIE() y LOGEXIT() en modo ":easy", combinando una solicitud de registro con una instrucción posterior de Perl warn(), die() o exit(). Por ejemplo:

if($all_is_lost) {
    LOGDIE("Problema terrible");
}

registra el mensaje si el logger del paquete es al menos "FATAL" pero die() (incluyendo la salida tradicional a STDERR) en cualquier caso después.

Ver "Log and die or warn" para funciones similares logdie() y logwarn() de loggers normales (es decir, no sigilosos).

De manera similar, LOGCARP(), LOGCLUCK(), LOGCROAK() y LOGCONFESS() se proporcionan en modo ":easy", lo que facilita el uso de logcarp(), logcluck(), logcroak() y logconfess() con loggers sigilosos.

Al usar Log::Log4perl en modo fácil, asegúrate de comprender las implicaciones de "Pitfalls with Categories".

Además, estas funciones de conveniencia funcionan tan rápido como los métodos estándar de "Log::Log4perl", sin ningún costo de rendimiento.

Contexto de diagnóstico anidado (NDC)

Si encuentras que tu aplicación podría beneficiarse de una pila global (es decir, específica de hilos) de datos a la que tu logger en todo el sistema pueda acceder fácilmente, utiliza Contextos de Diagnóstico Anidados (NDCs). También consulta "Mapped Diagnostic Context (MDC)", que podría ser aún más útil.

Por ejemplo, al manejar una solicitud de cliente web, probablemente sea útil tener la dirección IP del usuario disponible en todos los registros de log dentro del código relacionado con esa solicitud. En lugar de pasar este dato entre tus funciones de aplicación, puedes simplemente usar el mecanismo NDC global (pero específico de hilos). Esto te permite colocar fragmentos de datos (generalmente escalares) en su pila mediante:

Log::Log4perl::NDC->push("San");
Log::Log4perl::NDC->push("Francisco");

y luego puedes recuperar estos valores de la carpeta %x en el layout de PatternLayout. Con los valores de la pila y un formato de layout como "%x %m%n", la llamada:

$logger->debug("rocks");

terminará en

San Francisco rocks

en el anexador de registro.

El mecanismo de pila permite estructuras anidadas. Solo asegúrate de que al final de la solicitud, disminuyas la pila uno por uno llamando a

Log::Log4perl::NDC->pop();
Log::Log4perl::NDC->pop();

o vacíes toda la pila NDC llamando a

Log::Log4perl::NDC->remove();

Incluso si olvidas hacerlo, "Log::Log4perl" no hará crecer la pila indefinidamente, sino que la limitará a un máximo, definido en "Log::Log4perl::NDC" (actualmente 5). Una llamada a push() en una pila llena simplemente reemplazará el elemento superior con el nuevo valor.

Nuevamente, la pila siempre está disponible a través del marcador "%x" en la clase Log::Log4perl::Layout::PatternLayout cada vez que se activa un registrador. Reemplazará "%x" con la lista separada por espacios de los valores en la pila. Lo hace simplemente llamando a

Log::Log4perl::NDC->get();

internamente. Vea los detalles sobre cómo se implementa esta característica estándar de log4j en Log::Log4perl::NDC.

Contexto de Diagnóstico Mapeado (MDC)

Al igual que el NDC discutido anteriormente almacena información específica del hilo en una estructura de pila, el MDC implementa una tabla hash para almacenar pares clave/valor.

El método estático

Log::Log4perl::MDC->put($key, $value);

almacena $value bajo una clave $key, con la cual puede ser recuperado más tarde (posiblemente en una parte totalmente diferente del sistema) llamando al método "get":

my $value = Log::Log4perl::MDC->get($key);

Si no se ha almacenado ningún valor previamente bajo $key, el método "get" devolverá "undef".

Típicamente, los valores MDC se recuperan más tarde a través del marcador "%X{...}" en "Log::Log4perl::Layout::PatternLayout". Si el método get() devuelve "undef", el marcador se expandirá a la cadena "[undef]".

Una aplicación que recibe una solicitud web podría almacenar el host remoto como

Log::Log4perl::MDC->put("remote_host", $r->headers("HOST"));

al principio y si el diseño del anexador se ve algo así como

log4perl.appender.Logfile.layout.ConversionPattern = %X{remote_host}: %m%n

entonces una declaración de registro como

DEBUG("Content delivered");

registrará algo como

adsl-63.dsl.snf.pacbell.net: Content delivered

más adelante en el programa.

Para más detalles, consulte Log::Log4perl::MDC.

Resucitar declaraciones ocultas de Log4perl

A veces los scripts necesitan ser desplegados en entornos sin tener Log::Log4perl instalado aún. Por otro lado, no quieres vivir sin tus declaraciones de Log4perl; te serán útiles más adelante.

Así que, simplemente despliega tu script con las declaraciones de Log4perl comentadas con el patrón "###l4p", como en

###l4p DEBUG "It works!";
# ...
###l4p INFO "Really!";

Si Log::Log4perl está disponible, usa la etiqueta ":resurrect" para que Log4perl resucite esas declaraciones enterradas antes de que el script comience a ejecutarse:

use Log::Log4perl qw(:resurrect :easy);
###l4p Log::Log4perl->easy_init($DEBUG);
###l4p DEBUG "It works!";
# ...
###l4p INFO "Really!";

Esto hará que un filtro de fuente entre en acción y efectivamente imprima

2004/11/18 22:08:46 It works!
2004/11/18 22:08:46 Really!

En entornos que carecen de Log::Log4perl, simplemente comenta la primera línea y el script se ejecutará de todos modos (pero por supuesto, sin registrar):

# use Log::Log4perl qw(:resurrect :easy);
###l4p Log::Log4perl->easy_init($DEBUG);
###l4p DEBUG "It works!";
# ...
###l4p INFO "Really!";

porque todo es un comentario regular ahora. Alternativamente, coloca la línea mágica de resurrección de comentarios de Log::Log4perl en la variable de entorno PERL5OPT de tu shell, por ejemplo para bash:

set PERL5OPT=-MLog::Log4perl=:resurrect,:easy
export PERL5OPT

Esto despertará al gigante dentro de un script de lo contrario silencioso como el siguiente:

#!/usr/bin/perl
###l4p Log::Log4perl->easy_init($DEBUG);
###l4p DEBUG "It works!";

Desde "Log::Log4perl" 1.12, incluso puedes forzar que se resuciten *todos* los módulos cargados por un script con sus declaraciones ocultas de Log4perl. Para que esto suceda, carga "Log::Log4perl::Resurrector" *antes* de cargar cualquier módulo:

use Log::Log4perl qw(:easy);
use Log::Log4perl::Resurrector;
use Foobar; # Todas las declaraciones ocultas de Log4perl aquí
            # serán descomentadas antes de que Foobar se cargue.
Log::Log4perl->easy_init($DEBUG);
...

Consulta la página del manual de "Log::Log4perl::Resurrector" para más detalles.

Acceder a anexadores definidos

Todos los anexadores definidos en el archivo de configuración o a través de código Perl pueden ser recuperados por el método de clase appender_by_name(). Esto es útil si quieres manipular o consultar las propiedades del anexador después de que la configuración de Log4perl haya sido cargada a través de init().

Ten en cuenta que internamente, Log::Log4perl utiliza la clase envoltorio "Log::Log4perl::Appender" para controlar los anexadores reales (como "Log::Log4perl::Appender::File" o "Log::Dispatch::FileRotate"). La clase "Log::Log4perl::Appender" tiene un atributo "appender", que apunta al anexador real.

La razón de esto es que los anexadores externos como "Log::Dispatch::FileRotate" no admiten todos los mecanismos de control de anexadores de Log::Log4perl (como los umbrales del anexador).

El método previamente mencionado appender_by_name() devuelve una referencia al objeto del anexador *real*. Si quieres acceder a la clase envoltorio (por ejemplo, si quieres modificar el umbral del anexador), usa la hash $Log::Log4perl::Logger::APPENDER_BY_NAME{...} en su lugar, que contiene referencias a todos los objetos envoltorio de anexadores.

Modificar umbrales de anexadores

Para establecer el umbral de un anexador, usa su método threshold():

$app->threshold( $FATAL );

Para ajustar convenientemente *todos* los umbrales de anexadores (por ejemplo, porque un script usa more_logging()), usa

   # disminuir los umbrales de todos los anexadores
Log::Log4perl->appender_thresholds_adjust(-1);

Esto disminuirá los umbrales de todos los anexadores en el sistema en un nivel, es decir, WARN se convierte en INFO, INFO se convierte en DEBUG, etc. Para modificar solo algunos seleccionados, usa

   # disminuir los umbrales de anexadores seleccionados
Log::Log4perl->appender_thresholds_adjust(-1, ['AppName1', ...]);

y pasa los nombres de los anexadores afectados en una referencia a un array.

La estructura general

Para que el código de arriba tenga sentido, hay que entender un poco cómo funciona Log4perl. Aquí va un desglose:

En primer lugar, la parte más importante del sistema de logging de log4j (y por lo tanto de Log4perl) son los *loggers*. Los loggers son objetos que se organizan jerárquicamente. El logger principal es el logger de nivel superior, que tiene el nombre "root". Por defecto, este logger tiene un nivel de logging establecido en DEBUG y envía todos sus mensajes a la consola.

Si crea un logger llamado, por ejemplo, "MyApp.Db", Log4perl primero buscará un logger llamado "MyApp.Db". Si no lo encuentra, buscará un logger llamado "MyApp". Si no lo encuentra, buscará un logger llamado "root". El nivel de logging del logger que se recupera se determina mediante una regla jerárquica: el nivel más específico (el más largo) tiene preferencia.

Cada logger puede tener cero o más *appenders* adjuntos. Los appenders son objetos responsables de enviar los mensajes de logging a su destino final, como la consola, un archivo o una base de datos.

Un appender puede tener asignado un *layout* que determina el formato de los mensajes de logging. Si no se asigna ningún layout, se usa un layout por defecto.

Todos los loggers, excepto el logger raíz, tienen un padre. Si un mensaje se envía a un logger, y el nivel de logging del mensaje es igual o superior al nivel del logger, el mensaje se pasa al logger padre hasta que llega al logger raíz. Esto significa que, si un mensaje se imprime en la consola, se imprimirá en todos los appenders de todos los loggers de la jerarquía de ese logger.

Para evitar esto, todos los loggers y appenders de Log4perl se crean de forma automática al llamar a sus métodos de logging. Por ejemplo, si llama a "Log::Log4perl::get_logger('My.Category')", y no existe ningún logger con el nombre "My.Category", se creará automáticamente. Por defecto, se le asigna un nivel de DEBUG y se le adjunta un appender de consola. Esto significa que no es necesario crear explícitamente los objetos de logger o appender, ya que Log4perl se encarga de ello por usted.

Esto puede parecer un poco confuso al principio, pero simplifica enormemente la configuración. Con Log4perl, solo necesita preocuparse por los loggers y appenders que desea configurar explícitamente. El resto se maneja automáticamente.

Loggers y su configuración

Los loggers son la pieza central de Log4perl. Usted llama a los métodos debug(), info(), warn(), error(), etc. en un objeto logger. Log4perl se encarga de la mayor parte del trabajo pesado de configuración por usted. Por ejemplo, si llama a:

    use Log::Log4perl qw(:easy);
    Log::Log4perl::easy_init($DEBUG);
    
    DEBUG "This is a debug message";

Log4perl detectará que no existe ningún logger para el paquete actual (el script principal) y creará uno automáticamente con el nombre "main". Además, configurará un appender de consola para este logger, estableciendo su nivel en DEBUG.

También puede crear loggers explícitamente si lo desea:

my $logger = Log::Log4perl::get_logger("My.App");
$logger->level( $DEBUG );

Esto crea (o recupera si ya existe) un logger llamado "My.App" y establece su nivel en DEBUG. Si este es el primer logger que se crea en su aplicación, Log4perl también creará automáticamente un appender de consola para él.

Si desea que sus loggers tengan appenders específicos, o si desea controlar su nivel de forma más precisa, puede configurar explícitamente los appenders y asignarlos a los loggers. Por ejemplo:

use Log::Log4perl qw(:easy);
use Log::Log4perl::Appender::File;
use Log::Log4perl::Layout::PatternLayout;

# Crear un layout flexible
my $layout = Log::Log4perl::Layout::PatternLayout->new(
                "%d %-5p %m%n" );

# Crear un appender de archivo
my $appender = Log::Log4perl::Appender::File->new(
                "screen",
                filename => "foo.log",
                layout   => $layout );

# Configurar el logger raíz para usar este appender
Log::Log4perl::get_logger()->add_appender($appender);
Log::Log4perl::get_logger()->level($DEBUG);

# Ahora, cualquier mensaje de logging se enviará a foo.log
DEBUG "This message goes to foo.log";

En este ejemplo, creamos un layout y un appender de archivo, y luego los asignamos al logger raíz. Cualquier llamada a métodos de logging (como DEBUG, INFO, etc.) se enviará ahora a "foo.log".

Es importante tener en cuenta que los appenders se comparten entre los loggers. Si añade un appender a un logger, este appender se utilizará también para cualquier logger padre si el mensaje alcanza el nivel del appender. Si desea que un appender sea exclusivo de un logger, deberá crearlo explícitamente dentro de la configuración de ese logger.

Appenders

Los appenders son los encargados de determinar a dónde van los mensajes de log. Log4perl viene con varios appenders incorporados, incluyendo:

  • "Log::Log4perl::Appender::Screen": Envía mensajes a STDOUT o STDERR.
  • "Log::Log4perl::Appender::File": Envía mensajes a un archivo.
  • "Log::Log4perl::Appender::Null": Descarta todos los mensajes.
  • "Log::Log4perl::Appender::Socket": Envía mensajes a un socket TCP.
  • "Log::Log4perl::Appender::DBI": Envía mensajes a una base de datos mediante DBI.

Para crear un appender, utiliza el método new() del tipo de appender deseado, pasando el nombre del appender y sus parámetros. Por ejemplo:

my $screen_appender = Log::Log4perl::Appender::Screen->new(
    "screen",
    stderr => 1 # Enviar a STDERR
);

my $file_appender = Log::Log4perl::Appender::File->new(
    "file",
    filename => "/var/log/myapp.log"
);

Una vez creado un appender, puede asignarlo a un logger usando el método add_appender() del logger:

$logger->add_appender($screen_appender);
$logger->add_appender($file_appender);

Es importante notar que Log4perl crea automáticamente appenders cuando se llama a los métodos de logging si no existen. Por ejemplo, si llama a DEBUG() sin tener un logger configurado, Log4perl creará un logger "main" con un appender de consola. Esto significa que los métodos de logging de nivel fácil como DEBUG() siempre funcionarán, incluso si no ha configurado explícitamente ningún appender.

Los appenders pueden tener un nivel de umbral. Esto significa que un appender solo procesará mensajes que tengan un nivel igual o superior a su umbral. Por ejemplo, si establece el umbral de un appender en "WARN", solo recibirá mensajes de nivel WARN, ERROR y FATAL.

Puede establecer el nivel de un appender de la siguiente manera:

my $appender = Log::Log4perl::Appender::File->new(
    "file",
    filename => "/var/log/myapp.log",
    level    => $WARN # Solo se registrarán mensajes WARN o superiores
);

También puede asignar un layout a un appender. El layout determina el formato de los mensajes de log. Si no se especifica ningún layout, se utiliza un layout simple por defecto.

Los appenders "Log::Dispatch::*" son llamados tras bambalinas -- sí, lo hace. Esto se debe a que queremos que los objetos "Log::Dispatch" registren ciegamente todo lo que les enviamos ("debug" es su nivel más bajo) porque *nosotros* en "Log::Log4perl" queremos tener la última palabra y decidir cuándo y qué registrar.

La llamada al método layout() del appender especifica el formato (como un objeto "Log::Log4perl::Layout::PatternLayout" creado previamente) en el que se está registrando el mensaje en el appender especificado. Si no especifica un layout, el logger recurrirá a "Log::Log4perl::SimpleLayout", que registra el nivel de debug, un guion (-) y el mensaje de log.

Los layouts son objetos, aquí se explica cómo crearlos:

    # Crear un layout simple
my $simple = Log::Log4perl::SimpleLayout();
    # crear un layout flexible:
    # ("yyyy/MM/dd hh:mm:ss (archivo:lineno)> mensaje\n")
my $pattern = Log::Log4perl::Layout::PatternLayout("%d (%F:%L)> %m%n");

Cada appender tiene exactamente un layout asignado. Usted asigna el layout al appender usando el objeto layout() del appender:

my $app =  Log::Log4perl::Appender->new(
              "Log::Log4perl::Appender::Screen",
              name      => "screenlog",
              stderr    => 0);
    # Asignar el layout flexible previamente definido
$app->layout($pattern);
    # Añadir el appender a un logger previamente definido
$logger->add_appender($app);
    # ... y listo!
$logger->debug("Blah");
    # => "2002/07/10 23:55:35 (test.pl:207)> Blah\n"

También es posible eliminar appenders de un logger:

$logger->remove_appender($nombre_del_appender);

eliminará un appender, especificado por nombre, de un logger dado. Tenga en cuenta que esto *no* elimina un appender del sistema.

Para erradicar un appender del sistema, necesita llamar a "Log::Log4perl->eradicate_appender($nombre_del_appender)" que primero eliminará el appender de todos los loggers del sistema y luego eliminará todas las referencias que Log4perl tiene de él.

Para eliminar un logger del sistema, utilice "Log::Log4perl->remove_logger($logger)". Una vez que la referencia restante $logger desaparezca, el logger se autodestruirá. Si el logger en cuestión es un logger sigiloso, todos sus atajos de conveniencia (DEBUG, INFO, etc.) se convertirán en no-ops.

¿Qué pasa con Log::Dispatch::Config?

El "Log::Dispatch::Config" de Tatsuhiko Miyagawa es una implementación de logger simplificada muy ingeniosa, que cubre parte de la funcionalidad de *log4j*. Entre las cosas que "Log::Log4perl" puede hacer pero "Log::Dispatch::Config" no, se incluyen:

  • No se pueden asignar categorías a los loggers. Para sistemas pequeños eso está bien, pero si no puede activar y desactivar el logging detallado solo en un subsistema muy pequeño de su entorno, se está perdiendo una característica de log4j muy útil.
  • Definición de umbrales de appenders. Importante si desea resolver problemas como "registrar todos los mensajes de nivel FATAL en STDERR, además de registrar todos los mensajes DEBUG en "Foo::Bar" en un archivo de log". Si no tiene umbrales de appenders, no hay forma de evitar saturar STDERR con mensajes DEBUG.
  • Especificaciones de PatternLayout de acuerdo con el estándar (por ejemplo, "%d{HH:mm}").

En resumen: Log::Dispatch::Config está bien para sistemas pequeños con requisitos de logging sencillos. Sin embargo, si está diseñando un sistema con muchos subsistemas que necesita controlar de forma independiente, le encantarán las características de "Log::Log4perl", que es igualmente fácil de usar.

Usar Log::Log4perl con funciones y clases envoltorio

Si no utiliza "Log::Log4perl" como se describe anteriormente, sino desde una función envoltorio, el layout de patrón generará datos incorrectos para %F, %C, %L y similares. La razón de esto es que los loggers de "Log::Log4perl" asumen una profundidad estática del llamador a la aplicación que los utiliza.

Si está utilizando una (o más) funciones envoltorio, "Log::Log4perl" indicará dónde su función logger llamó a los loggers, no dónde su aplicación llamó a su envoltorio:

use Log::Log4perl qw(:easy);
Log::Log4perl->easy_init({ level => $DEBUG, 
                           layout => "%M %m%n" });
sub mylog {
    my($message) = @_;
    DEBUG $message;
}
sub func {
    mylog "Hello";
}
func();

imprime

main::mylog Hello

pero probablemente eso no es lo que su aplicación espera. Más bien, querría

main::func Hello

porque la función "func" llamó a su función de logging.

Pero no se desespere, hay una solución: Simplemente registre su paquete envoltorio con Log4perl de antemano. Si Log4perl encuentra que está siendo llamado desde un envoltorio registrado, automáticamente subirá al siguiente marco de llamada.

Log::Log4perl->wrapper_register(__PACKAGE__);
sub mylog {
    my($message) = @_;
    DEBUG $message;
}

Alternativamente, puede aumentar el valor de la variable global $Log::Log4perl::caller_depth (por defecto 0) en uno por cada envoltorio que esté entre su aplicación y "Log::Log4perl", entonces "Log::Log4perl" compensará la diferencia:

sub mylog {
    my($message) = @_;
    local $Log::Log4perl::caller_depth =
          $Log::Log4perl::caller_depth + 1;
    DEBUG $message;
}

Además, tenga en cuenta que si está escribiendo una subclase de Log4perl, como

package MyL4pWrapper;
use Log::Log4perl;
our @ISA = qw(Log::Log4perl);

y quiere llamar a get_logger() en su código, como

use MyL4pWrapper;
sub get_logger {
    my $logger = Log::Log4perl->get_logger();
}

entonces la llamada a get_logger() obtendrá un logger para la categoría "MyL4pWrapper", no para el paquete que llama a la clase envoltorio como en

package UserPackage;
my $logger = MyL4pWrapper->get_logger();

Para que la llamada anterior a get_logger devuelva un logger para la categoría "UserPackage", necesita decirle a Log4perl que "MyL4pWrapper" es una clase envoltorio de Log4perl:

use MyL4pWrapper;
Log::Log4perl->wrapper_register(__PACKAGE__);
sub get_logger {
      # Ahora obtiene un logger para la categoría del paquete que llama
    my $logger = Log::Log4perl->get_logger();
}

Esta característica funciona tanto para clases que retransmiten Log4perl como para el envoltorio descrito anteriormente, como para envoltorios que heredan de Log4perl y utilizan la función get_logger de Log4perl a través de la herencia, por igual.

Acceso a los Internos

Los siguientes métodos solo son útiles si desea examinar/modificar los internos de Log::Log4perl. Tenga cuidado de no alterar su funcionamiento interno.

"Log::Log4perl->appenders()"
Para saber qué appenders están definidos actualmente (no solo para un logger particular, sino en general), hay disponible un método appenders() que devuelve una referencia a un hash que mapea nombres de appenders a sus referencias de objetos Log::Log4perl::Appender.

Trucos Sordidos

infiltrate_lwp()
El famoso módulo LWP::UserAgent no está habilitado para Log::Log4perl. A menudo, sin embargo, especialmente al depurar problemas relacionados con la Web, sería útil obtener información sobre lo que sucede dentro de LWP::UserAgent. Idealmente, LWP::UserAgent incluso jugaría limpio en el marco de Log::Log4perl.

Una llamada a "Log::Log4perl->infiltrate_lwp()" hace exactamente eso. De una manera muy rudimentaria, le quita la alfombra debajo de los pies a LWP::UserAgent y transforma sus mensajes "debug/conn" en llamadas a debug() de loggers de la categoría "LWP::UserAgent". De manera similar, los mensajes de "trace" de "LWP::UserAgent" se convierten en llamadas al método "info()" de "Log::Log4perl". Tenga en cuenta que esto solo funciona para versiones de LWP::UserAgent anteriores a 5.822, ya que estas versiones (y probablemente posteriores) carecen por completo de funciones de depuración.

Suprimir mensajes 'duplicados' de LOGDIE
Si un script con una configuración simple de Log4perl utiliza logdie() para capturar errores y detener el procesamiento, como en 
use Log::Log4perl qw(:easy) ;
Log::Log4perl->easy_init($DEBUG);

shaky_function() or LOGDIE "¡Falló!";

hay un problema cosmético: el mensaje se imprime dos veces:

2005/07/10 18:37:14 ¡Falló!
¡Falló! en ./t línea 12

La solución obvia es usar LOGEXIT() en lugar de LOGDIE(), pero también hay una etiqueta especial para Log4perl que suprime el segundo mensaje:

use Log::Log4perl qw(:no_extra_logdie_message);

Esto hace que logdie() y logcroak() llamen a exit() en lugar de a die(). Para modificar el código de salida del script en estas ocasiones, establezca la variable $Log::Log4perl::LOGEXIT_CODE al valor deseado, el valor predeterminado es 1.

Redefinir valores sin causar errores
El analizador de archivos de configuración de Log4perl tiene algunos mecanismos de seguridad básicos para garantizar que las configuraciones sean más o menos sensatas.

Una de estas medidas de seguridad es capturar valores redefinidos. Por ejemplo, si primero escribe

log4perl.category = WARN, Logfile

y luego unas líneas más tarde

log4perl.category = TRACE, Logfile

entonces podría haber sobrescrito involuntariamente el archivo

valor y Log4perl fallará con un error (las configuraciones sospechosas siempre generan un error). Ahora, existe la posibilidad de que esto sea intencional, por ejemplo, cuando estás agrupando varios archivos de configuración y realmente quieres que el primer valor sobrescriba al segundo. En este caso, usa

use Log::Log4perl qw(:nostrict);

para poner Log4perl en un modo más permisivo.

Evitar que croak/confess serialice
Las funciones logcroak/logconfess serializan sus argumentos antes de pasarlos a las funciones croak/confess de Carp. Esto puede ser un inconveniente si deseas lanzar un objeto o un hashref como excepción, en cuyo caso usa: 
$Log::Log4perl::STRINGIFY_DIE_MESSAGE = 0;
eval {
      # lanza { foo => "bar" }
      # sin serialización
    $logger->logcroak( { foo => "bar" } );
};

EJEMPLO

Un ejemplo sencillo para copiar y pegar y empezar:

use Log::Log4perl qw(get_logger);

my $conf = q(
log4perl.category.Bar.Twix         = WARN, Logfile
log4perl.appender.Logfile          = Log::Log4perl::Appender::File
log4perl.appender.Logfile.filename = test.log
log4perl.appender.Logfile.layout = \
    Log::Log4perl::Layout::PatternLayout
log4perl.appender.Logfile.layout.ConversionPattern = %d %F{1} %L> %m %n
);

Log::Log4perl::init(\$conf);

my $logger = get_logger("Bar::Twix");
$logger->error("Blah");

Esto registrará algo como

2002/09/19 23:48:15 t1 25> Blah

en el archivo de registro "test.log", al que Log4perl agregará o creará si aún no existe.

INSTALACIÓN

Si deseas utilizar appenders externos proporcionados con "Log::Dispatch", necesitas instalar "Log::Dispatch" (2.00 o superior) desde CPAN, que a su vez depende de "Attribute-Handlers" y "Params-Validate". Y muchos otros módulos, esa es la razón por la que ahora enviamos Log::Log4perl con sus propios appenders estándar y solo si deseas usar adicionales, tendrás que pasar por el proceso de instalación de "Log::Dispatch".

Log::Log4perl necesita "Test::More", "Test::Harness" y "File::Spec", pero ya vienen con versiones bastante recientes de perl. Si no es así, todo se descarga automáticamente de CPAN si estás usando el shell de CPAN (CPAN.pm), ya que están listados como dependencias.

"Time::HiRes" (1.20 o superior) solo se requiere si necesitas las marcas de tiempo de alta precisión del parámetro %r en "Log::Log4perl::Layout::PatternLayout".

La instalación manual funciona como de costumbre con

perl Makefile.PL
make
make test
make install
