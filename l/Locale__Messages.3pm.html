NOMBRE

Locale::Messages - Recuperación de mensajes similar a Gettext

SINOPSIS

use Locale::Messages qw(:locale_h :libintl_h);
gettext $msgid;
dgettext $textdomain, $msgid;
dcgettext $textdomain, $msgid, LC_MESSAGES;
ngettext $msgid, $msgid_plural, $count;
dngettext $textdomain, $msgid, $msgid_plural, $count;
dcngettext $textdomain, $msgid, $msgid_plural, $count, LC_MESSAGES;
pgettext $msgctxt, $msgid;
dpgettext $textdomain, $msgctxt, $msgid;
dcpgettext $textdomain, $msgctxt, $msgid, LC_MESSAGES;
npgettext $msgctxt, $msgid, $msgid_plural, $count;
dnpgettext $textdomain, $msgctxt, $msgid, $msgid_plural, $count;
dcnpgettext $textdomain, $msgctxt, $msgid, $msgid_plural, $count, LC_MESSAGES;
textdomain $textdomain;
bindtextdomain $textdomain, $directory;
bind_textdomain_codeset $textdomain, $encoding;
bind_textdomain_filter $textdomain, \&filter, $data;
turn_utf_8_on ($variable);
turn_utf_8_off ($variable);
nl_putenv ('OUTPUT_CHARSET=koi8-r');
my $category = LC_CTYPE;
my $category = LC_NUMERIC;
my $category = LC_TIME;
my $category = LC_COLLATE;
my $category = LC_MONETARY;
my $category = LC_MESSAGES;
my $category = LC_ALL;

DESCRIPCIÓN

El módulo Locale::Messages es un envoltorio alrededor de la interfaz para la traducción de mensajes según el enfoque Uniforum que, por ejemplo, se usa en GNU gettext y Solaris de Sun. Está destinado a permitir que Locale::Messages(3) cambie entre diferentes implementaciones de las bibliotecas de nivel inferior, pero esto aún no está implementado.

Normalmente no deberías usar este módulo directamente, sino la interfaz de alto nivel Locale::TextDomain(3) que proporciona una interfaz mucho más simple. Por lo tanto, esta descripción se mantiene deliberadamente breve. Consulta la documentación de GNU gettext disponible en http://www.gnu.org/manual/gettext/ para obtener información detallada y de fondo sobre el tema.

El módulo de nivel inferior Locale::gettext_pp(3) proporciona la implementación en Perl de gettext() y funciones relacionadas.

FUNCIONES

El módulo no exporta nada por defecto. Cada función debe importarse explícitamente o a través de una etiqueta de exportación ("EXPORT TAGS").

gettext MSGID
Devuelve la traducción para MSGID. Ejemplo: 
print gettext "Hello World!\n";

Si no se encuentra ninguna traducción, se devuelve el MSGID modificado, es decir, la función nunca puede fallar y nunca estropeará tu mensaje original.

Nota para Perl 5.6 y posteriores: La cadena devuelta siempre tendrá el indicador UTF-8 desactivado por defecto. Consulta la documentación de la función bind_textdomain_filter() para ver una forma de cambiar este comportamiento.

Un error común es este:

print gettext "Hello $name!";

Perl interpolará la variable $name antes de que la función vea la cadena. A menos que el catálogo de mensajes correspondiente contenga un mensaje "Hello Tom!", "Hello Dick!" o "Hello Harry!", no se encontrará ninguna traducción.

El uso de printf() y similares tiene sus propios problemas:

print sprintf (gettext ("This is the %s %s."), $color, $thing);

(El ejemplo es estúpido porque ni el color ni la cosa se traducirán aquí ...).

En inglés, el adjetivo (el color) precede al sustantivo; muchos otros idiomas (por ejemplo, francés o italiano) difieren aquí. Por lo tanto, al traductor del mensaje puede resultarle difícil encontrar una traducción que siga funcionando y no suene estúpida en el idioma de destino. Muchas implementaciones en C de printf() permiten cambiar el orden de los argumentos, y un traductor francés podría decir:

"C'est le %2$s %1$s."

El printf() de Perl implementa esta característica a partir de la versión 5.8 o superior. En consecuencia, solo puedes usarla si estás seguro de que tu software se ejecutará con Perl 5.8 o una versión posterior.

Otra desventaja de usar printf() es su sintaxis críptica (quizás no para ti, pero los traductores de tu software pueden tener su propia opinión).

Consulta la descripción de la función "__x()" en Locale::TextDomain(3) para una forma mucho mejor de solucionar este problema.

IDs de mensaje no ASCII ...

Debes tener en cuenta que la función (y todas las demás funciones similares en este módulo) realiza una comparación byte a byte del MSGID para la búsqueda en el catálogo de traducción, independientemente de si se establecen indicadores utf-8 oscuros en él, si la cadena parece utf-8, si se utiliza el pragma utf8(3pm), o cualquier otro método extraño que las versiones pasadas o futuras de perl(1) inventen para adivinar conjuntos de caracteres de cadenas.

Usar caracteres que no sean us-ascii en el código fuente de Perl es una llamada a problemas, una pesadilla de compatibilidad. Además, GNU gettext solo introdujo recientemente soporte para conjuntos de caracteres no ascii en las fuentes, y el soporte para esta característica puede no estar disponible en todas partes. Si absolutamente deseas usar MSGIDs en conjuntos de caracteres no ascii, es aconsejable elegir utf-8. Esto minimizará el riesgo de que perl(1) mismo interfiera con las cadenas, y también será una garantía de que podrás traducir tu proyecto a idiomas de destino arbitrarios más adelante.

Otros conjuntos de caracteres teóricamente pueden funcionar. Sin embargo, usar un conjunto de caracteres diferente en el código fuente de Perl que el utilizado en tus catálogos de mensajes nunca funcionará, ya que la búsqueda se realiza byte a byte, y todas las cadenas con caracteres no ascii no se encontrarán.

Incluso si has resuelto todos estos problemas, todavía queda un obstáculo: La API de tiempo de ejecución de gettext carece de una posibilidad para especificar el conjunto de caracteres del código fuente (incluidas las cadenas originales). En consecuencia, en ausencia de una pista para la codificación de entrada, las cadenas sin traducción no están sujetas a conversión de codificación de salida. En otras palabras: Si el conjunto de caracteres de salida (no determinable) difiere del conjunto de caracteres utilizado en el código fuente, la salida puede ser una mezcla de dos conjuntos de caracteres. No tiene sentido intentar abordar este problema en la versión puramente de Perl de las funciones gettext, porque romper la compatibilidad entre la versión de Perl y la de C es un precio demasiado alto.

Todo esto se reduce a: ¡Usa solo caracteres ASCII en tus cadenas traducibles!

dgettext TEXTDOMAIN, MSGID
Al igual que gettext(), pero recupera el mensaje para el TEXTDOMAIN especificado en lugar del dominio predeterminado. En caso de que te preguntes qué es un textdomain, deberías seguir leyendo sobre Locale::TextDomain(3).
dcgettext TEXTDOMAIN, MSGID, CATEGORY
Al igual que dgettext(), pero recupera el mensaje de la CATEGORY especificada en lugar de la categoría predeterminada "LC_MESSAGES".
ngettext MSGID, MSGID_PLURAL, COUNT
Recupera la traducción correcta para COUNT elementos. En software legado encontrarás a menudo algo como: 
print "$count file(s) deleted.\n";

o

printf "$count file%s deleted.\n", $count == 1 ? '' : 's';

El primer ejemplo parece torpe, el segundo solo funcionará en inglés y en idiomas con reglas de plural similares. Antes de que se introdujera ngettext(), la mejor práctica para programas internacionalizados era:

if ($count == 1) {
    print gettext "One file deleted.\n";
} else {
    printf gettext "%d files deleted.\n";
}

Esto es una molestia para el programador y a menudo no es suficiente para una traducción adecuada. Muchos idiomas tienen ideas completamente diferentes sobre los numerales. Algunos (francés, italiano, ...) tratan el 0 y el 1 de la misma manera, otros no hacen ninguna distinción (japonés, coreano, chino, ...), otros tienen dos o más formas plurales (ruso, letón, checo, polaco, ...). printf (ngettext ("Un archivo eliminado.\n",
                 "%d archivos eliminados.\n",
                 $count), # ¡argumento para ngettext!
        $count);          # ¡argumento para printf!

En inglés, o si no se encuentra ninguna traducción, se elige el primer argumento (MSGID) si $count es uno, y el segundo en caso contrario. Para otros idiomas, también se elige automáticamente la forma plural correcta (de 1, 2, 3, 4, ...). No tienes que saber nada sobre las reglas de plurales en el idioma de destino, ngettext() se encargará de eso.

Esto es suficiente la mayor parte del tiempo, pero tendrás que demostrar tu creatividad en casos como

printf "%d archivo(s) eliminado(s), y %d archivo(s) creado(s).\n";
dngettext TEXTDOMAIN, MSGID, MSGID_PLURAL, COUNT
Similar a ngettext() pero recupera la traducción del textdomain especificado en lugar del dominio por defecto.
dcngettext TEXTDOMAIN, MSGID, MSGID_PLURAL, COUNT, CATEGORY
Similar a dngettext() pero recupera la traducción de la categoría especificada, en lugar de la categoría por defecto "LC_MESSAGES".
pgettext MSGCTXT, MSGID
Devuelve la traducción de MSGID, dado el contexto de MSGCTXT.

Ambos elementos se utilizan como una clave única en el catálogo de mensajes.

Esto permite al traductor tener dos entradas para palabras que pueden traducirse a diferentes palabras extranjeras según su contexto. Por ejemplo, la palabra "View" puede ser un sustantivo o un verbo, que puede usarse en un menú como Archivo->Ver o Ver->Fuente.

pgettext "Verbo: Ver", "Ver\n";
pgettext "Sustantivo: Una Vista", "Ver\n";

Lo anterior buscará diferentes entradas en el catálogo de mensajes.

Un uso típico son los programas GUI. Imagina un programa con un menú principal y la notoria entrada "Abrir" en el menú "Archivo". Ahora imagina que hay otra entrada en el menú Preferencias->Avanzado->Política donde tienes que elegir entre las alternativas "Abrir" y "Cerrado". En inglés, "Open" es el texto adecuado en ambos lugares. En otros idiomas, es muy probable que necesites dos traducciones diferentes. Por lo tanto, escribirías:

pgettext "Archivo|", "Abrir";
pgettext "Preferencias|Avanzado|Política", "Abrir";

En inglés, o si no se encuentra ninguna traducción, se devuelve el segundo argumento (MSGID).

La función se introdujo con la versión 1.17 de libintl-perl.

dpgettext TEXTDOMAIN, MSGCTXT, MSGID
Similar a pgettext(), pero recupera el mensaje para el TEXTDOMAIN especificado en lugar del dominio por defecto.

La función se introdujo con la versión 1.17 de libintl-perl.

dcpgettext TEXTDOMAIN, MSGCTXT, MSGID, CATEGORY
Similar a dpgettext() pero recupera el mensaje de la CATEGORY especificada en lugar de la categoría por defecto "LC_MESSAGES".

La función se introdujo con la versión 1.17 de libintl-perl.

npgettext MSGCTXT, MSGID, MSGID_PLURAL, COUNT
Similar a ngettext() con la adición de contexto como en pgettext().

En inglés, o si no se encuentra ninguna traducción, se elige el segundo argumento (MSGID) si $count es uno, y el tercero en caso contrario.

La función se introdujo con la versión 1.17 de libintl-perl.

dnpgettext TEXTDOMAIN, MSGCTXT, MSGID, MSGID_PLURAL, COUNT
Similar a npgettext() pero recupera la traducción del textdomain especificado en lugar del dominio por defecto.

La función se introdujo con la versión 1.17 de libintl-perl.

dcnpgettext TEXTDOMAIN, MSGCTXT, MSGID, MSGID_PLURAL, COUNT, CATEGORY
Similar a dnpgettext() pero recupera la traducción de la categoría especificada, en lugar de la categoría por defecto "LC_MESSAGES".

La función se introdujo con la versión 1.17 de libintl-perl.

textdomain TEXTDOMAIN
Establece el textdomain por defecto (inicialmente 'messages').
bindtextdomain TEXTDOMAIN, DIRECTORIO
Vincula TEXTDOMAIN a DIRECTORIO. ¿Eh? Un ejemplo: 
bindtextdomain "mi-paquete", "./milocal";

Digamos que la configuración regional seleccionada (en realidad, la configuración regional seleccionada para la categoría "LC_MESSAGES") del programa es 'fr_CH', entonces se esperará el catálogo de mensajes en ./milocal/fr_CH/LC_MESSAGES/mi-paquete.mo.

bind_textdomain_codeset TEXTDOMAIN, CODIFICACION
Establece la codificación de salida para TEXTDOMAIN a CODIFICACION.
bind_textdomain_filter TEXTDOMAN, CODEREF, DATOS
bind_textdomain_filter TEXTDOMAN, CODEREF
Por defecto, Locale::Messages desactivará la marca utf-8 de todos los mensajes devueltos. Si deseas cambiar este comportamiento, puedes pasar una referencia a una subrutina que haga cosas diferentes, por ejemplo, activar la marca utf-8 o dejarla sin modificar. La función de devolución de llamada se llamará con DATOS como primer argumento y la cadena posiblemente traducida como segundo argumento. Debe devolver la cadena posiblemente modificada.

Si deseas que se llame a un método de objeto, pasa el objeto mismo en el parámetro de datos y escribe una función envolvente. Ejemplo:

sub wrapper {
    my ($string, $obj) = @_;

    $obj->filterMethod ($string);
}
my $obj = MyPackage->new;
bind_textdomain_filter ('midominio', \&wrapper, $obj);

La función no puede fallar y siempre devuelve un valor verdadero.

Atención: Si utilizas la función para establecer la marca utf-8, es tu responsabilidad asegurarte de que la salida sea realmente utf-8. Solo debes usarla si has establecido la variable de entorno OUTPUT_CHARSET a "utf-8". Además, debes llamar a bind_textdomain_codeset() con "utf-8" como segundo argumento.

Steven Haryanto ha escrito un módulo Locale::TextDomain::UTF8(3pm) que aborda el mismo problema.

Esta función se introdujo en libintl-perl 1.16 y **no** forma parte de la API estándar de gettext.

turn_utf_8_on VARIABLE
Devuelve VARIABLE pero con la marca UTF-8 (solo conocida en Perl >=5.6) garantizada para estar activada. Esta función no encaja realmente en el módulo, pero es útil de todos modos.

¡La marca **no** significa que la cadena esté realmente en utf-8 válido!

La función se introdujo con la versión 1.16 de libintl-perl.

turn_utf_8_off VARIABLE
Devuelve VARIABLE pero con la marca UTF-8 (solo conocida en Perl >=5.6) garantizada para estar desactivada. Esta función no encaja realmente en el módulo, pero es útil de todos modos.

La función se introdujo con la versión 1.07 de libintl-perl.

select_package PAQUETE
Por defecto, Locale::Messages intentará cargar la versión XS de la implementación gettext, es decir, Locale::gettext_xs(3) y recurrirá a la implementación pura de Perl Locale::gettext_pp(3). Puedes anular este comportamiento pasando la cadena "gettext_pp" o "gettext_xs" a la función select_package(). Pasar "gettext_pp" aquí preferirá la implementación pura de Perl.

Normalmente querrás usar esto en un bloque BEGIN de tu script principal.

La función se introdujo con la versión 1.03 de libintl-perl y no forma parte de la API estándar de gettext.

A partir de la versión 1.22, puedes pasar nombres de paquete diferentes a "gettext_pp" o "gettext_xs" y usar un backend completamente diferente. Es responsabilidad del llamador asegurarse de que el paquete seleccionado ofrezca la misma interfaz que los dos paquetes estándar.

Un paquete que ofrece esta funcionalidad es Locale::gettext_dumb(3pm).

nl_putenv ENVSPEC
Se asemeja a la función ANSI C putenv(3). El único propósito de esta función es solucionar algunas peculiaridades en el procesamiento del entorno de los sistemas Windows. Si deseas establecer o eliminar variables de entorno de forma portable, utiliza esta función en lugar de manipular directamente %ENV.

El argumento ENVSPEC puede tener tres formas diferentes.

LANGUAGE=fr_CH
Esto establecería la variable de entorno "LANGUAGE" a "fr_CH".
LANGUAGE=
Normalmente, esto establecería la variable de entorno "LANGUAGE" a una cadena vacía. Sin embargo, en Windows, la variable de entorno se eliminará (y ya no estará presente en %ENV). Dado que dentro de libintl-perl las variables de entorno vacías son inútiles, considera este uso como obsoleto.
LANGUAGE
Esto eliminará la variable de entorno LANGUAGE. Si estás familiarizado con la implementación defectuosa de putenv(3) (resp. _putenv()) en

El archivo estándar de la biblioteca C de MS-Windows, podrías sospechar que esto es un argumento inválido. ¡Esto no es el caso!

La función devuelve true en caso de éxito y false en caso de fallo. Las razones posibles de fallo incluyen una sintaxis inválida o, únicamente bajo Windows, el fallo de la asignación de espacio para un nuevo bloque de variables de entorno ($! se establecerá en este caso).

¿Por qué todo este esfuerzo? Las versiones 32-bit de MS-DOS (actualmente Windows 95/98/ME/NT/2000/XP/CE/.NET) mantienen dos bloques distintos de variables de entorno por proceso. ¿Cuál de los bloques es considerado el "correcto" depende de una opción de compilación del interpretador Perl. Sin embargo, si has construido la versión XS Locale::gettext_xs(3) bajo Windows, la librería subyacente podría usar un bloque diferente, y los cambios que hayas hecho a %ENV no estarán visibles para la librería.

La función nl_putenv() es principalmente un modo divertido de decir:

LANGUAGE=some_value

pero intenta hacer lo mejor posible para pasar esta información a la librería gettext. En otros sistemas operativos, esta función solo opera en %ENV, mientras que bajo Windows llamará a la función C _putenv() (después de hacer algunas limpiezas a sus argumentos), antes de manipular %ENV.

Por favor, nota que tu %ENV se actualiza automáticamente por nl_putenv().

Esta función ha sido introducida en la versión 1.10 de libintl-perl.

setlocale
Modifica y consulta el idioma del programa, véase la documentación de setlocale() en POSIX(3pm) en su lugar.

En algunos sistemas, una llamada desde C a setlocale() - con el apoyo del preprocesador C - es realmente una llamada a libintl_setlocale(), que es un wrapper al sistema setlocale(3). La falta de llamar a libintl_setlocale() puede causar ciertos problemas. En tales sistemas, Locale::Messages::setlocale() llamará al wrapper libintl_setlocale(). Si quieres evitar problemas, deberías siempre llamar a la implementación de setlocale() en Locale::Messages(3pm).

Ver https://rt.cpan.org/Public/Bug/Display.html?id=83980 o https://savannah.gnu.org/bugs/?38162, y https://savannah.gnu.org/bugs/?func=detailitem&item_id=44645 para una discusión de este problema.

Esta función ha sido introducida en la versión 1.24 de libintl-perl.

CONSTANTES

Puedes (quizás) obtener las mismas constantes de POSIX(3); vea allí una descripción detallada.

LC_CTYPE
LC_NUMERIC
LC_TIME
LC_COLLATE
LC_MONETARY
LC_MESSAGES
Esta categoría de locales fue la razón por la que estas constantes de POSIX(3) fueron incluidas aquí. Incluso si estaba presente en tu sistema C incluido en locale.h, no fue proporcionada por POSIX(3). El Perl 5.8 y versiones posteriores parece exportar la constante si está disponible, aunque no está documentada en POSIX(3).

Locale::Messages(3) intenta hacer un esfuerzo para estimular el valor de esta categoría para todos los sistemas y asume el valor arbitrario 1729 de forma por defecto.

LC_ALL
Si especificas la categoría LC_ALL como el primer argumento a POSIX::setlocale(), *todos* las categorías de locales serán afectadas de forma inmediata.

USO

Un ejemplo completo:

1: use Locale::Messages qw(:locale_h :libintl_h);
2: use POSIX qw (setlocale);
3: setlocale (LC_MESSAGES, '');
4: textdomain ('my-package');
5: bindtextdomain ('my-package' => '/usr/local/share/locale');
6:
7: print gettext ("Hello world!\n");

Paso a paso: Línea 1 importa las funciones necesarias y constantes. En la línea 3 establece el idioma para la categoría LC_MESSAGES a los ajustes por defecto del usuario. Para programas C, a menudo se lee que LC_ALL es la mejor categoría aquí, pero esto también cambiará el idioma para LC_NUMERIC y muchos otros programas no funcionarán correctamente después de cambiar esa categoría en Perl; ¡elige tu propio veneno!

En la línea 4 decimos que todos los mensajes (traducciones) sin una especificación explícita de dominio deberían ser recuperados del catálogo de mensajes para el dominio 'my-package'. Línea 5 tiene el efecto de buscar el catálogo de mensajes bajo la carpeta '/usr/local/share/locale'.

Si el usuario ha seleccionado el idioma 'fr_CH' y si existe el archivo '/usr/local/share/locale/fr_CH/LC_MESSAGES/my-package.mo' y contiene un archivo objeto GNU con una traducción para la cadena 'Hello world!\n', entonces la línea 7 imprimirá la traducción francesa (para Suiza CH) a STDOUT.

La documentación de GNU gettext explica cómo extraer cadenas traducibles de tus archivos Perl y cómo crear catálogos de mensajes.

Otro ejemplo menos portátil: Si tu sistema utiliza la GNU libc, deberías poder encontrar varios archivos con el nombre 'libc.mo', el catálogo de mensajes para la librería misma. Si ya has encontrado estos archivos en '/usr/share/locale', puedes intentar lo siguiente:

use Locale::Messages qw(:locale_h :libintl_h);
use POSIX qw (setlocale);
setlocale LC_MESSAGES, "";
textdomain "libc";
# El siguiente es realmente no necesario, ya que es uno de los directorios de búsqueda predeterminados.
bindtextdomain libc => '/usr/share/locale';
bind_textdomain_codeset libc => 'iso-8859-1';
print gettext ("No such file or directory");

Ver Locale::TextDomain(3pm) para métodos más simples.

Locale::Messages(3pm) — Arch manual pages

Locale::Messages - Interface to the GNU gettext() functions.

SYNOPSIS

  use Locale::Messages;
  my $msg = get_msg_category 'my_app';
  print $msg->gettext("Hello world!\n");

DESCRIPTION

This module provides an interface to the GNU gettext() functions commonly used for internationalization and localization of programs. It allows you to translate messages from one language to another. The module aims to be compatible with the standard Perl gettext() function and its related functions like ngettext(), bindtextdomain(), textdomain(), etc.

FUNCTIONS

The following functions are exported by default:

  • get_msg_category(CATEGORY): Returns a message category object for the given CATEGORY. CATEGORY is usually the name of your application.
  • gettext(MSGID): Translates the message identified by MSGID.
  • ngettext(MSGID1, MSGID2, N): Translates a message that depends on a number N. MSGID1 is the singular form and MSGID2 is the plural form.
  • bindtextdomain(DOMAIN, DIRECTORY): Binds a text domain to a directory.
  • textdomain(DOMAIN): Sets the current text domain.
  • bind_textdomain_codeset(DOMAIN, CODESET): Sets the codeset for a text domain.
  • install_languages(LANGS): Installs a list of languages.
  • setlocale(CATEGORY, LOCALES): Sets the locale.

CONSTANTS

No constants are exported by this module.

EXPORT_TAGS

:all
Exports all functions.
:gettext
Exports gettext, ngettext, get_msg_category.
:domain
Exports bindtextdomain, textdomain, bind_textdomain_codeset.
:locale
Exports setlocale.

OTHER_EXPORTS

By default, the following functions are exported:

  • gettext
  • ngettext
  • get_msg_category
  • bindtextdomain
  • textdomain
  • bind_textdomain_codeset
  • setlocale

USAGE

To internationalize your application, you typically:

  1. Create a message file (usually a .po file) containing the strings from your application that need translation.
  2. Use a tool like xgettext to extract these strings into a template file (.pot).
  3. Translate the strings in the template file for each language you want to support, creating separate .po files for each language.
  4. Compile the .po files into binary .mo files using msgfmt.
  5. In your Perl code, use the Locale::Messages module to load and use the translations.

Example:

  use Locale::Messages;

  # Set the text domain and the directory where .mo files are located
  bindtextdomain('my_app', '/usr/share/locale');
  textdomain('my_app');

  # Translate a string
  my $greeting = gettext("Hello, ");
  my $user = "World";
  print $greeting, $user, "!\n";

  # Translate a plural string
  my $count = 5;
  my $message = ngettext("There is %d item.", "There are %d items.", $count);
  $message =~ s/%d/$count/;
  print $message, "\n";

You can also use the get_msg_category() function to manage translations for different parts of your application or for different text domains.
