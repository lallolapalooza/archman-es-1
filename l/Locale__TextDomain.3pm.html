Locale::TextDomain(3) Documentación de Perl contribuida por el usuario Locale::TextDomain(3)

NOMBRE

Locale::TextDomain - Interfaz de Perl para la traducción de mensajes de Uniforum

SINOPSIS

use Locale::TextDomain ('mi-paquete', @directorios_locale);

use Locale::TextDomain qw (mi-paquete);

my $traducido = __"Hola Mundo!\n";

my $alt = $__{"Hola Mundo!\n"};

my $alt2 = $__->{"Hola Mundo!\n"};
my @lista = (N__"Hola",
            N__"Mundo");

printf (__n ("un archivo leído", 
             "%d archivos leídos", 
             $num_archivos),
        $num_archivos);
print __nx ("un archivo leído", "{num} archivos leídos", $num_archivos,
            num => $num_archivos);
my $traducido_contexto = __p ("Verbo, para ver", "Ver");
printf (__np ("Archivos leídos de sistemas de archivos",
              "un archivo leído", 
              "%d archivos leídos", 
              $num_archivos),
        $num_archivos);
print __npx ("Archivos leídos de sistemas de archivos",
             "un archivo leído", 
             "{num} archivos leídos", 
             $num_archivos,
             num => $num_archivos);

DESCRIPCIÓN

El módulo Locale::TextDomain(3pm) proporciona una interfaz de alto nivel para la traducción de mensajes en Perl.

Dominios de texto

Cuando solicita una traducción para una cadena dada, el sistema utilizado en libintl-perl sigue una estrategia estándar para encontrar un catálogo de mensajes adecuado que contenga la traducción: A menos que defina explícitamente un nombre para el catálogo de mensajes, libintl-perl asumirá que su catálogo se llama 'messages' (a menos que haya cambiado el valor predeterminado a algo más a través de Locale::Messages(3pm), método textdomain()).

Podría pensar que esta estrategia predeterminada deja margen para la optimización y tiene razón. Sería mucho más inteligente si múltiples paquetes de software, todos con sus catálogos de mensajes individuales, pudieran instalarse en un sistema, y también debería ser posible que componentes de terceros de su software (como módulos de Perl) carguen sus catálogos de mensajes, también, sin interferir con los suyos.

La solución es clara, debe asignar un nombre único a su base de datos de mensajes y debe especificar ese nombre en tiempo de ejecución. Ese nombre único es el llamado dominio de texto de su paquete de software. El nombre es en realidad arbitrario, pero debe seguir estas pautas de mejores prácticas para garantizar la máxima interoperabilidad:

Seguridad del sistema de archivos
En la práctica, los dominios de texto se mapean a nombres de archivo, y por lo tanto, debe asegurarse de que el dominio de texto que elija sea un nombre de archivo válido en cada sistema que ejecute su software.
Sensibilidad a mayúsculas y minúsculas
Los dominios de texto siempre distinguen entre mayúsculas y minúsculas (es decir, 'Paquete' y 'PAQUETE' no son lo mismo). Sin embargo, dado que los catálogos de mensajes se almacenarán en sistemas de archivos que pueden o no distinguir entre mayúsculas y minúsculas al buscar nombres de archivo, debe evitar conflictos potenciales aquí.
El dominio de texto debe coincidir con el nombre de CPAN
Si su software figura como un módulo en CPAN, simplemente debe elegir el nombre en CPAN como su dominio de texto. El dominio de texto para libintl-perl es, por lo tanto, 'libintl-perl'. Pero reemplace todos los puntos ('.') en el nombre de su paquete con un guion bajo porque ...
Nombres de dominio de Internet como plan B
... si su software *no* es un módulo listado en CPAN, como último recurso, debe usar el esquema de paquetes de Java(tm), es decir, elegir un dominio de Internet del que sea propietario (o pedirle al propietario de un dominio de Internet) y concatenar su dominio de texto preferido con el dominio de Internet invertido. Ejemplo: Su empresa ejecuta el sitio web 'www.foobar.org' y es propietaria del dominio 'foobar.org'. El dominio de texto para el software de su empresa 'barfoos' debería ser, por lo tanto, 'org.foobar.barfoos'.

Si su software se va a instalar en diferentes versiones en el mismo sistema, probablemente sea una buena idea agregar información de versión a su dominio de texto.

Otros sistemas son menos estrictos con el esquema de nombres para los dominios de texto, pero el fenómeno conocido como "Perl es en realidad una plétora de módulos pequeños y especializados" y probablemente sea más sensato postular algún modelo de espacio de nombres para evitar el caos.

Vinculación de dominios de texto a directorios

Una vez que el sistema conoce el dominio de texto del mensaje que desea traducir al idioma del usuario, todavía tiene que encontrar el catálogo de mensajes correcto. Por defecto, libintl-perl buscará la cadena en la base de datos de traducción que se encuentra en los directorios /usr/share/locale y /usr/local/share/locale (en ese orden).

No está garantizado que estos directorios existan en la máquina de destino, ni puede estar seguro de que la rutina de instalación tenga acceso de escritura a estas ubicaciones. Por lo tanto, puede indicar a libintl-perl que busque otros directorios antes que los directorios predeterminados. Especificar un directorio de búsqueda diferente se llama vincular un dominio de texto a un directorio.

A partir de la versión 1.20, Locale::TextDomain extiende la estrategia predeterminada con un enfoque específico de Perl. Si File::ShareDir está instalado, buscará en los subdirectorios llamados locale y LocaleData (en ese orden) en el directorio devuelto por "File::ShareDir::dist_dir ($dominio_de_texto)" (si File::ShareDir está instalado), y comprobará si hay una base de datos que contenga el mensaje para su dominio de texto allí. Esto le permite instalar su base de datos en el directorio compartido específico de Perl utilizando la directiva "install_share" de Module::Install o el plugin ShareDir de Dist::Zilla.

Si File::ShareDir no está disponible, o si Locale::TextDomain no encuentra los archivos de traducción en el directorio de File::ShareDir, buscará en cada directorio del ruta de inclusión estándar @INC, y comprobará si hay una base de datos que contenga el mensaje para su dominio de texto allí. Ejemplo: Si la ruta /usr/lib/perl/5.8.0/site_perl está en su @INC, puede instalar sus archivos de traducción en /usr/lib/perl/5.8.0/site_perl/LocaleData, y se encontrarán en tiempo de ejecución.

USO

Es crucial recordar que usa Locale::TextDomain(3) como se especifica en la sección "SINOPSIS", lo que significa que debe usarlo, no requerirlo. El módulo se comporta de manera bastante diferente en comparación con otros módulos.

La diferencia más significativa es el significado de la lista que se pasa como argumento a la función use(). En realidad, funciona así:

use Locale::TextDomain (DOMINIO_DE_TEXTO, DIRECTORIO, ...)

El primer argumento (la primera cadena pasada a use()) es el dominio de texto de su paquete, seguido opcionalmente por una lista de directorios a buscar *en lugar* de los directorios específicos de Perl (ver arriba: /LocaleData agregado a un directorio de File::ShareDir y cada ruta en @INC).

Si es el autor de un paquete 'barfoos', probablemente pondrá la línea

use Locale::TextDomain 'barfoos';

respectivamente para módulos que no sean de CPAN

use Locale::TextDomain 'org.foobar.barfoos';

en cada módulo de su paquete que contenga cadenas traducibles. Si su módulo se ha instalado correctamente, incluidos los catálogos de mensajes, podrá recuperar estas traducciones en tiempo de ejecución.

Si no ha instalado la base de datos de traducción en un directorio LocaleData en el directorio de File::ShareDir o en la ruta de inclusión estándar @INC (o en los directorios del sistema /usr/share/locale o /usr/local/share/locale, respectivamente), debe especificar explícitamente una ruta de búsqueda proporcionando los nombres de los directorios (como cadenas) como argumentos adicionales a use():

use Locale::TextDomain qw (barfoos ./dir1 ./dir2);

Alternativamente, puede llamar a la función bindtextdomain() con los argumentos adecuados (ver la entrada para bindtextdomain() en "FUNCIONES" en Locale::Messages). Si lo hace, debe pasar "undef" como argumento adicional para evitar búsquedas innecesarias:

use Locale::TextDomain ('barfoos', undef

FUNCIONES EXPORTADAS

Todas las funciones tienen nombres bastante extraños con el propósito de que sean cortos, operadores y que no den conflictos con funciones existentes en tu espacio de nombres. Entenderás esto cuando internacionalices tu primer programa o módulo de Perl. Preparar un programa es más como marcar cadenas como traducibles que insertar llamadas a funciones. Aquí vamos:

__ MSGID
NOTA: ¡Este es un doble subguion bajo!

La función básica y más utilizada. Es un atajo para una llamada a gettext() o dgettext(), y simplemente devuelve la traducción para MSGID. Si tu código antiguo lee así:

print "permission denied";

A partir de ahora escribes:

print __"permission denied";

Eso es todo, la cadena se mostrará en el idioma preferido del usuario, siempre que hayas instalado una traducción para ella.

Obviamente puedes usar paréntesis:

print __("permission denied");

O incluso:

print (__("permission denied"));

En mi opinión, la primera versión sin paréntesis es la mejor.

__x MSGID, ID1 => VAL1, ID2 => VAL2, ...
Una de las mejores características de Perl es su capacidad de interpolar variables en cadenas: 
print "This is the $color $thing.\n";

Esta característica puede hacerte pensar que ahora puedas escribir:

print __"This is the $color $thing.\n";

Sin embargo, eso sería bonito pero no es posible. Recuerda que la función __() sirve tanto como un operador para traducir cadenas y como un marco para cadenas traducibles. Si la cadena anterior se extrae de tu código de Perl, la forma no interpolada se incluirá en el catálogo de mensajes porque al analizar tu código es impredecible qué valores tendrán las variables $color y $thing en tiempo de ejecución (esta es probablemente una de las razones por las que has escrito tu programa).

Sin embargo, en tiempo de ejecución, Perl intercalará los valores ya antes de que __() (o la función subsecuente gettext()) vea la cadena original. Por lo tanto, algo como "This is the red car.\n" se buscará en el catálogo de mensajes, no se encontrará (porque solo "This is the $color $thing.\n" está incluido en la base de datos), y se devolverá la cadena no traducida. Honestamente, dado que esto es casi siempre un error, el programa xgettext(1) se detendrá con un error fatal cuando encuentre esa cadena en tu código.

Hay dos soluciones para ese problema:

printf __"This is the %s %s.\n", $color, $thing;

pero eso tiene varias desventajas: tu traductor solo verá la cadena aislada y sin el contexto completo es casi imposible interpretarla correctamente. De hecho, el software GNU emacs y otros con capacidad de edición de archivos de traducción PO permitirán que veas el contexto en el código fuente, pero es más probable que tu traductor busque un proyecto de traducción más sencillo cuando se encuentre con tales mensajes frecuentemente.

Y aún si ella entiende el programa subyacente, ¿qué pasa si tiene que reordenar el color y la cosa como en francés:

msgid "This is the red car.\n";
msgstr "Cela est la voiture rouge.\n"

¡Zut alors! Aunque es posible reordenar los argumentos de printf() y similares, requiere una sintaxis que no quieres aprender.

¿Y qué? El backend de Perl para gettext de GNU ha definido un formato alternativo para cadenas interpolables:

"This is the {color} {thing}.\n";

En lugar de variables Perl, usas marcadores de posición entre corchetes, y luego llamas a:

print __x ("This is the {color} {thing}.\n", 
           thing => $thang,
           color => $color);

La función __x() tomará el hash adicional y reemplazará todas las ocurrencias de las claves del hash entre corchetes con los valores correspondientes. Simple, legible, entendible para traductores, ¿qué más te gustaría? Y si el traductor olvida, escribe o daña alguna "variable", la función msgfmt(1), que se usa para compilar el archivo de traducción textual en su representación binaria, incluso se enfadará con estos errores y rechazará la compilación de la traducción.

__n MSGID, MSGID_PLURAL, COUNT
¡Uf! Aquello parece complicado... mejor lo explico con un ejemplo. Vamos a revisar de nuevo tu código antiguo: 
if ($files_deleted > 1) {
    print "All files have been deleted.\n";
} else {
    print "One file has been deleted.\n";
}

Tu intención es clara, quieres evitar el complicado "1 files deleted". Esto es correcto en inglés, pero en otros idiomas hay más de un plural. Por ejemplo, en ruso, se diferencia entre 1 archivo, 3 archivos o 6 archivos. Usarás tres formas diferentes del sustantivo "archivo" en cada caso. [Nota: Si lo sabes, también entenderás el resto, aunque esta simplificación sea un poco complicada...].

Esa es la razón por la que existe la función ngettext(), que __n() es un atajo para:

print __n"One file has been deleted.\n", 
         "All files have been deleted.\n",
         $files_deleted;

Alternativamente:

print __n ("One file has been deleted.\n",
           "All files have been deleted.\n",
           $files_deleted);

El efecto es siempre el mismo: libintl-perl buscará la forma correcta para tu idioma de usuario y el texto se mostrará siempre bien.

__nx MSGID, MSGID_PLURAL, COUNT, VAR1 => VAL1, VAR2 => VAL2, ...
Uniendo todo lo anterior: 
print __nx ("One file has been deleted.\n",
            "{count} files have been deleted.\n",
            $num_files,
            count => $num_files);

La función __nx() elige la forma correcta de plural (también para inglés) y puede interpolar variables en cadenas.

Aunque quieras mirar el orden de los argumentos: el primero es la cadena en singular, el segundo es la cadena en plural. El tercer argumento es un entero que indica el número de elementos. Este tercer argumento es solamente usado para elegir la forma correcta. Los argumentos opcionales siguientes forman el hash usado para la interpolación. Inicialmente suele ser confuso que la variable que almacena el número de elementos suele aparecer repetida en el hash de interpolación.

__xn MSGID, MSGID_PLURAL, COUNT, VAR1 => VAL1, VAR2 => VAL2, ...
Hace exactamente lo mismo que __nx(). En realidad es un error tipográfico común promovido a una característica.
__p MSGCTXT, MSGID
Esta es mucho más como __. La "p" significa "particular" y MSGCTXT se usa para proporcionar contexto a los traductores. Esto puede ser necesario cuando tu cadena es corta y podría representar varios significados. Por ejemplo:

print __p"Verb, to view", "View";
print __p"Noun, a view", "View";

El ejemplo anterior puede ser "View" en un menú donde View->Source y File->View son formas diferentes de "View", que probablemente necesitan traducirse de forma diferente.

Un uso típico son programas de interfaz gráfica. Imagina un programa con un menú principal y la entrada notoria "Open" en el menú File. Imagina ahora otra entrada de menú Preferences->Advanced->Policy donde tienes una elección entre las alternativas "Open" y "Closed". En inglés, "Open" es el texto adecuado en ambos lugares. En otros idiomas, es muy probable que necesites dos traducciones distintas. Por lo tanto, ahora escribirías:

__p"File|", "Open";
__p"Preferences|Advanced|Policy", "Open";

En inglés, o si no existe traducción, se devuelve el segundo argumento (MSGID).

Esta función fue introducida en libintl-perl 1.17.

__px MSGCTXT, MSGID, VAR1 => VAL1, VAR2 => VAL2, ...
Como __p(), pero soporta reemplazo de variables en la cadena, como __x(). 
print __px("Verb, to view", "View {file}", file => $filename);

Ver __p() y __x() para más detalles.

Esta función fue introducida

El módulo exporta varias variables en su espacio de nombres:

%__
Una tabla hash enlazada. Sus claves son sus mensajes originales, y sus valores son sus traducciones: 
my $title = "<h1>$__{'Mi página principal'}</h1>";

Esto es mucho mejor para su equipo de traducción que:

my $title = __"<h1>Mi página principal</h1>";

En el segundo caso, el código HTML se convertirá en texto en el catálogo de traducciones y sus traductores tendrán que tener cuidado con la sintaxis de HTML al traducir las cadenas.

Advertencia: ¡No utilice esta tabla hash fuera de las cadenas con comillas dobles! El código en el objeto hash enlazado depende del correcto funcionamiento de la función caller() (consulte https://perldoc.cpan.org/perlfunc/caller.html), y esta función informará resultados incorrectos si el valor del hash enlazado es el argumento para una función de otro paquete, por ejemplo:

my $result = Other::Package::do_it ($__{'Una cadena'});

El código del objeto hash enlazado verá a "Other::Package" como el paquete que llama, en lugar de su propio paquete. Por lo tanto, buscará el mensaje en el dominio de texto incorrecto. No hay solución para este error. Por lo tanto:

¡No utilice esta tabla hash interpolada en cadenas!

$__
Una referencia a "%__", en caso de que prefiera: 
my $title = "<h1>$__->{'Mi página principal'}</h1>";

MÉTODOS DE CLASE

Los siguientes métodos de clase están definidos:

options
Devuelve una lista separada por espacios de todas las opciones '--keyword' y '--flag' para xgettext(1) cuando se extraen cadenas locales con Locale::TextDomain.

Esta opción debería llamarse xgettextDefaultOptions. Con respecto al uso típico, se ha elegido un nombre más corto:

xgettext `perl -MLocale::TextDomain -e 'print Locale::TextDomain->options'`

Consulte https://www.gnu.org/software/gettext/manual/html_node/xgettext-Invocation.html para obtener más información sobre las opciones '--keyword' y '--flag' de xgettext(1).

Si desea desactivar el uso de las palabras clave predeterminadas de xgettext, debe pasar una opción '--keyword=""' a xgettext antes de las opciones devueltas por este método.

Si duda de la utilidad de este método, verifique el resultado en la línea de comandos:

perl -MLocale::TextDomain -e 'print Locale::TextDomain->options'

Nada para usted para escribir.

Este método se añadió en libintl-perl 1.28.

keywords
Devuelve una lista separada por espacios de todas las opciones '--keyword' para xgettext(1) así como para que las cadenas locales se extraigan correctamente.

Este método se añadió en libintl-perl 1.28.

flags
Devuelve una lista separada por espacios de todas las opciones '--flag' para xgettext(1) así como para que las cadenas locales se marquen correctamente.

Este método se añadió en libintl-perl 1.28.

RENDIMIENTO

La traducción de mensajes puede ser una tarea que consume tiempo, tome este ejemplo:

1: use Locale::TextDomain ('mi-dominio');
2: use POSIX (:locale_h);
3: 
4: setlocale (LC_ALL, '');
5: print __"Hola mundo!";

Esto generalmente será rápido, pero en casos extremos puede llevar varios segundos. Una peor situación sería un usuario chino en una terminal que entienda el juego de caracteres Big5-HKSCS. Su traductor chino ha elegido codificar las traducciones en el juego de caracteres EUC-TW.

¿Qué sucede en tiempo de ejecución? Primero, la biblioteca buscará y cargará un (posiblemente grande) catálogo de mensajes para su dominio de texto 'mi-dominio'. Luego, buscará la traducción de "Hola mundo!", encontraría que está codificada en EUC-TW. Dado que esto difiere del juego de caracteres de salida Big5-HKSCS, primero cargará una tabla de conversión que contiene varios cientos de códigos de caracteres para EUC-TW, luego hará lo mismo con la tabla de conversión más pequeña pero aún muy grande para Big5-HKSCS, convertirá la traducción en tiempo real de EUC-TW a Big5-HKSCS, y finalmente devolverá la traducción convertida.

Un escenario peor pero realista. Y para estas cinco líneas de código, no hay mucho que hacer para hacerlo más rápido. Debe entender, sin embargo, *cuándo* cada paso se realizará, así que puede organizar su código para ello.

Ha aprendido en la sección "DESCRIPCIÓN" que la línea 1 es responsable de localizar su base de mensajes. Sin embargo, el uso de use() no hará nada más que recordarle sus configuraciones. No buscará directorios, no cargará catálogos ni tablas de conversión.

En algún lugar de su código siempre habrá una llamada a POSIX::setlocale(), y el rendimiento de esta llamada puede consumir tiempo, dependiendo de la arquitectura de su sistema. En algunos sistemas, esto consumirá muy poco tiempo, en otros solo un tiempo considerable para la primera llamada, y en otros podría consumir tiempo siempre. Dado que no puede saber cómo se implementa setlocale() en el sistema de destino, debe reducir las llamadas a setlocale() al mínimo.

La línea 5 solicita la traducción de su cadena. Solo ahora la biblioteca carga realmente el catálogo de mensajes, y solo ahora carga las tablas de conversión necesarias. Y a partir de ahora, toda esta información se almacenará en memoria. Esta estrategia se utiliza todo el tiempo en libintl-perl, y puede describirla como 'carga en primer acceso'. Obtener la siguiente traducción consumirá muy pocos recursos.

Sin embargo, aunque la recuperación de la traducción está un poco oculta por una llamada de función que parece una función de operador, sigue siendo una llamada de función, y en realidad incluso implica una cadena de llamadas de funciones. Por lo tanto, el siguiente ejemplo podría ser prácticamente malo:

foreach (1 .. 100_000) {
    print __"Hola mundo!";
}

Este ejemplo introduce una gran sobrecarga en su programa. Mejor hágalo así:

my $string = __"Hola mundo!";
foreach (1 .. 100_000) {
    print $string;
}

La traducción nunca cambiará, no hay necesidad de recuperarla cada vez. Aunque libintl-perl almacenará la traducción leída desde el sistema de archivos, aún puede evitar la sobrecarga de las llamadas de función.
