NOMBRE

Log::Log4perl::Appender::DBI - implementa la adición a una BD

SINOPSIS

  my $config = q{
   log4j.category = WARN, DBAppndr
   log4j.appender.DBAppndr             = Log::Log4perl::Appender::DBI
   log4j.appender.DBAppndr.datasource  = DBI:CSV:f_dir=t/tmp
   log4j.appender.DBAppndr.username    = bobjones
   log4j.appender.DBAppndr.password    = 12345
   log4j.appender.DBAppndr.sql         = \
      insert into log4perltest           \
      (loglevel, custid, category, message, ipaddr) \
      values (?,?,?,?,?)
   log4j.appender.DBAppndr.params.1 = %p    
                                 #2 es custid de la llamada a log()
   log4j.appender.DBAppndr.params.3 = %c
                                 #4 es el mensaje de log()
                                 #5 es ipaddr de log()
   log4j.appender.DBAppndr.usePreparedStmt = 1
    #--o--
   log4j.appender.DBAppndr.bufferSize = 2
   #simplemente pasa la matriz de elementos de mensaje en la declaración de log
   log4j.appender.DBAppndr.layout    = Log::Log4perl::Layout::NoopLayout
   log4j.appender.DBAppndr.warp_message = 0
   #soporte de atributos del controlador
   log4j.appender.DBAppndr.attrs.f_encoding = utf8
  };
  Log::Log4perl::init ( \$config ) ;                                      
  my $logger = Log::Log4perl->get_logger () ;                             
  $logger->warn( $custid, '¡gran problema!!', $ip_addr );

ADVERTENCIA

Este es un módulo muy joven y hay muchas variaciones en las configuraciones con diferentes bases de datos y métodos de conexión, ¡así que asegúrate de probar a fondo! ¡Cualquier comentario es bienvenido!

DESCRIPCIÓN

Este es un objeto especializado de Log::Dispatch personalizado para funcionar con log4perl y sus capacidades, originalmente basado en Log::Dispatch::DBI de Tatsuhiko Miyagawa pero con modificaciones importantes.

Es un intento de compromiso entre lo que hacía Log::Dispatch::DBI y lo que hace el JDBCAppender de log4j. Tenga en cuenta que la documentación de log4j dice que el JDBCAppender "es muy probable que sea reemplazado por completo en el futuro".

El uso más simple es este:

log4j.category = WARN, DBAppndr
log4j.appender.DBAppndr            = Log::Log4perl::Appender::DBI
log4j.appender.DBAppndr.datasource = DBI:CSV:f_dir=t/tmp
log4j.appender.DBAppndr.username   = bobjones
log4j.appender.DBAppndr.password   = 12345
log4j.appender.DBAppndr.sql        = \
   INSERT INTO logtbl                \
      (loglevel, message)            \
      VALUES ('%c','%m')
log4j.appender.DBAppndr.layout    = Log::Log4perl::Layout::PatternLayout
$logger->fatal('mensaje fatal');
$logger->warn('mensaje de advertencia');
===============================
|FATAL|mensaje fatal          |
|WARN |mensaje de advertencia        |
===============================

Pero las desventajas de ese uso son:

  • Debes estar muy seguro de que no hay comillas en tu mensaje de log, o tu inserción podría tener consecuencias imprevistas. Esta es una forma muy insegura de manejar inserciones en bases de datos, usar marcadores de posición y enlazar valores es mucho mejor, sigue leyendo. (Tenga en cuenta que la documentación de log4j advierte "¡Tenga cuidado con las comillas en sus mensajes!") *.
  • No es muy eficiente, se crea y ejecuta una sentencia por cada llamada a log.
  • El único parámetro en tiempo de ejecución que obtienes es el mensaje %m, en realidad probablemente quieras registrar datos específicos en columnas de tabla específicas.

Así que intentemos usar marcadores de posición y decirle al registrador que cree un manejador de sentencia preparada al principio y simplemente lo reutilice (tal como lo hace Log::Dispatch::DBI)

log4j.appender.DBAppndr.sql = \
   INSERT INTO logtbl \
      (custid, loglevel, message) \
      VALUES (?,?,?)
#---------------------------------------------------
#ahora los valores de enlace:
                              #1 es el custid
log4j.appender.DBAppndr.params.2 = %p    
                              #3 es el mensaje
#---------------------------------------------------
log4j.appender.DBAppndr.layout    = Log::Log4perl::Layout::NoopLayout
log4j.appender.DBAppndr.warp_message = 0

log4j.appender.DBAppndr.usePreparedStmt = 1


$logger->warn( 1234, 'mensaje de advertencia' );

¿Ahora ves cómo estamos usando los marcadores de posición '?' en nuestra sentencia? Esto significa que no tenemos que preocuparnos por mensajes que se parezcan a

entrada no válida: 1234';drop table custid;

¡estropeando nuestra base de datos!

Normalmente, una lista de cosas en la sentencia de log se concatena en una sola cadena, pero establecer "warp_message" en 0 y usar NoopLayout significa que en

$logger->warn( 1234, 'mensaje de advertencia', 'bgates' );

los valores individuales de la lista seguirán estando disponibles para el appender DBI más adelante. (Si "warp_message" no está establecido en 0, el comportamiento predeterminado es unir los elementos de la lista en una sola cadena. Si se utilizan PatternLayout o SimpleLayout, su intento de render() tu diseño resultará en algo como "ARRAY(0x841d8dc)" en tus logs. Más información sobre "warp_message" está en Log::Log4perl::Appender.)

En tu SQL de inserción puedes mezclar marcadores de posición '?' con especificadores de conversión (%c, %p, etc) como mejor te parezca: el registrador emparejará los signos de interrogación con los parámetros que hayas definido en el archivo de configuración y poblará el resto con valores de tu lista. Si hay más marcadores de posición '?' que valores en tu mensaje, usará undef para los restantes. Por ejemplo,

log4j.appender.DBAppndr.sql =                 \
   insert into log4perltest                   \
   (loglevel, message, datestr, subpoena_id)\
   values (?,?,?,?)
log4j.appender.DBAppndr.params.1 = %p
log4j.appender.DBAppndr.params.3 = %d
log4j.appender.DBAppndr.warp_message=0
$logger->info('¡detenlo!', $subpoena_id);

resulta en que el primer marcador de posición '?' se enlaza a %p, el segundo a "¡detenlo!", el tercero a la fecha de "%d", y el cuarto a tu $subpoenaid. Si olvidas el $subpoena_id y simplemente registras

$logger->info('¡detenlo!');

entonces obtienes undef en la cuarta columna.

Si la sentencia del registrador también está siendo manejada por otros appenders que no son DBI, simplemente unirán la lista en una cadena, unida con $Log::Log4perl::JOIN_MSG_ARRAY_CHAR (el valor predeterminado es una cadena vacía).

¿Y ves "usePreparedStmt"? Crea un manejador de sentencia cuando se crea el objeto registrador y simplemente lo reutiliza. Sin embargo, eso puede ser problemático para procesos de larga duración como servidores web, en cuyo caso puedes usar este parámetro en su lugar

log4j.appender.DBAppndr.bufferSize=2

Esto copia el comportamiento del JDBCAppender de log4j, guarda hasta ese número de sentencias de log y las escribe todas a la vez. Si tu sentencia INSERT usa solo marcadores de posición ? y ningún especificador de conversión %x, debería ser bastante eficiente porque el registrador puede reutilizar el mismo manejador de sentencia para las inserciones.

Si el programa termina mientras el búfer está solo parcialmente lleno, el bloque DESTROY debería vaciar las sentencias restantes, si el bloque DESTROY se ejecuta, por supuesto.

* Mientras escribía esto, Danko Mannhaupt estaba sacando su JDBCAppender mejorado de log4j (http://www.mannhaupt.com/danko/projects/) que supera muchas de las desventajas del JDBCAppender original.

DESCRIPCIÓN 2

O otra forma de decir lo mismo:

La idea es que si estás registrando en una tabla de base de datos, probablemente quieras partes específicas de tu información de log en columnas determinadas. Para ello, pasas una lista a la sentencia de log, como

$logger->warn('¡gran problema!!',$userid,$subpoena_nr,$ip_addr);

y los miembros de la matriz caen en las posiciones definidas por los marcadores de posición en tu sentencia SQL. También puedes definir información en el archivo de configuración como

log4j.appender.DBAppndr.params.2 = %p

en cuyo caso esos marcadores de posición numerados se rellenarán con los valores especificados, y el resto de los marcadores de posición se rellenarán con los valores de la matriz de tu sentencia de log.

PARÁMETROS VARIOS

usePreparedStmt
Ver arriba.
warp_message
ver Log::Log4perl::Appender
max_col_size
Permite especificar un tamaño máximo para columnas de texto. Si el registro es más largo que el tamaño especificado, se trunca. Nota: esto solo se aplicará si el tamaño de la columna en la base de datos es menor que el tamaño especificado aquí, o si el código está configurado para truncar siempre.

max_col_size

max_col_size
Si estás acostumbrado a simplemente lanzar mensajes de depuración como enormes trazas de pila en tu logger, algunas bases de datos (¡DBD de Sybase!) pueden sorprenderte al fallar debido a limitaciones de tamaño de datos. Normalmente, los datos simplemente se truncarían para caber en la columna, pero resulta que el DBD de Sybase tiene un máximo de 255 caracteres. Usa este parámetro en tal situación para truncar mensajes largos antes de que lleguen a la sentencia INSERT.

CAMBIO DE CONEXIONES DBH (POOLING)

Si quieres obtener tu dbh de algún lugar en particular, como tal vez un pool, haz una subclase y sobrescribe _init() y/o create_statement(), por ejemplo:

sub _init {
    ; # no-op, sin pooling en este nivel
}
sub create_statement {
    my ($self, $stmt) = @_;

    $stmt || croak "Log4perl: sql not set in ".__PACKAGE__;

    return My::Connections->getConnection->prepare($stmt)
        || croak "Log4perl: DBI->prepare failed $DBI::errstr\n$stmt";
}

VIDA DE LAS CONEXIONES

Si estás usando "log4j.appender.DBAppndr.usePreparedStmt" este módulo crea un sth cuando arranca y lo mantiene durante la vida del programa. Para procesos de larga duración (por ejemplo, mod_perl), las conexiones pueden volverse obsoletas, pero si "Log::Log4perl::Appender::DBI" intenta escribir un mensaje y se da cuenta de que la conexión a la base de datos ya no funciona (usando el método ping de DBI), se reconectará.

El proceso de reconexión puede ser controlado por dos parámetros, "reconnect_attempts" y "reconnect_sleep". "reconnect_attempts" especifica el número de intentos de reconexión que realiza el appender DBI hasta que se rinde y muere. "reconnect_sleep" es el tiempo entre los intentos de reconexión, medido en segundos. "reconnect_attempts" tiene un valor por defecto de 1, "reconnect_sleep" de 0.

Alternativamente, usa "Apache::DBI" o "Apache::DBI::Cache" y lee CAMBIO DE CONEXIONES DB arriba.

Ten en cuenta que "Log::Log4perl::Appender::DBI" mantiene una conexión abierta por cada appender, lo cual podría ser demasiado.
