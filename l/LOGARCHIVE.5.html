LOGARCHIVE(5) Manual de formatos de archivo LOGARCHIVE(5)

NOMBRE

LOGARCHIVE - Formatos de archivo de Performance Co-Pilot

DESCRIPCIÓN

Los archivos de Performance Co-Pilot (PCP) almacenan valores históricos sobre métricas arbitrarias registradas de un solo host. Los archivos son independientes de la máquina y autosuficientes: todos los datos y metadatos de métricas necesarios para el análisis fuera de línea o externo se encuentran dentro de un archivo.

El formato es estable para permitir el almacenamiento y procesamiento histórico a largo plazo por herramientas cliente de PMAPI(3). Sin embargo, se soportan algunas variantes de formato con el tiempo, y actualmente se soportan las versiones 2 y 3. El mandato es que PCP proporcionará compatibilidad retroactiva a largo plazo, por lo que un archivo creado en cualquier versión de PCP puede ser leído en esa versión de PCP y en **todas** las versiones posteriores de PCP. La excepción es la versión 1, que se retiró en la versión 2.0 de PCP en mayo de 1998.

La mayoría de las herramientas cliente de PCP pueden leer los archivos utilizando la opción -a/--archive NOMBRE, o volcarlos sin procesar con pmlogdump(1). Los archivos son creados principalmente por pmlogger(1), sin embargo, también pueden ser creados utilizando la interfaz de programación LOGIMPORT(3).

Los archivos pueden ser fusionados, analizados, modificados y submuestreados utilizando pmlogreduce(1), pmlogsummary(1), pmlogrewrite(1) y pmlogextract(1). Además, los archivos de PCP pueden ser examinados en conjuntos o agrupados en "folios de archivo", que son creados y gestionados por las herramientas mkaf(1) y pmafm(1).

Un archivo consta de varios archivos físicos que comparten un prefijo común y arbitrario, por ejemplo, miarchivo.

miarchivo.0, miarchivo.1, ...
Uno o más volúmenes de datos que contienen los valores de las métricas y cualquier código de error encontrado durante el muestreo de métricas. Típicamente son los archivos más grandes y pueden crecer muy rápidamente, dependiendo de la selección de métricas a registrar por pmlogger(1) y los intervalos de muestreo utilizados.
miarchivo.meta
Información para las funciones de PMAPI como pmLookupName(3), pmLookupDesc(3), pmLookupLabels(3) y pmLookupInDom(3). El archivo de metadatos puede crecer esporádicamente a medida que las métricas registradas, los dominios de instancias y las etiquetas varían con el tiempo.
miarchivo.index
Un índice temporal, que mapea marcas de tiempo a desplazamientos de bytes en los otros archivos.

CARACTERÍSTICAS COMUNES

Los tres tipos de archivos tienen una estructura de registros similar, una convención de codificación en orden de bytes de red (big-endian) y campos de 32 bits para etiquetar/rellenar esos registros. Las cadenas se almacenan como caracteres de 8 bits sin asumir una codificación específica, por lo que normalmente son ASCII. Ver también los tipos __pmLog* en src/include/pcp/libpcp.h.

ENMARCADO DE REGISTROS

Los archivos de volumen y .meta se dividen en registros autoidentificables.

4 N-8 carga útil del registro, que normalmente comienza con una etiqueta de tipo de registro de 32 bits
N-4 4 N, longitud del registro (otra vez)

El formato de la "etiqueta de archivo" difiere entre las versiones 2 y 3, siendo esta última la que proporciona marcas de tiempo mejoradas (codificación de 64 bits para la parte de segundos y precisión de nanosegundos) y algunos campos adicionales.

PMNS DOMAIN (.0) RECORD

The Performance Co-Pilot (PCP) archive format defines a set of conventions for storing performance metric data collected from a variety of sources. The archive is composed of multiple files, each representing a different aspect of the collected data.

The first file is the archive label record, which contains general information about the archive. The subsequent files, typically named archive.1, archive.2, etc., contain the actual performance metric data, organized into time-stamped records.

Offset Length Name
0 4 archive magic number (PM_ARCH_MAGIC)
4 4 archive format version (PM_ARCH_VERSION)
8 4 archive label length (bytes)
12 4 archive metadata length (bytes)
16 4 archive start time (seconds since UNIX epoch)
20 4 archive end time (seconds since UNIX epoch)
24 4 current archive volume number
28 4 hostname length (bytes)
32 4 number of archive feature bits
36 A archive label string
36+A B archive metadata string
36+A+B C hostname string
36+A+B+C D archive feature bits
36+A+B+C+D 4 timezone length (bytes)
-11 E timezone zoneinfo string for collection host, e.g. :Australia/Melbourne

The ``archive feature bits'' are intended to encode possible future extensions or differences to the on-disk structure or the the archive semantics. At this stage there are no such features, but if they are introduced at some point in the future, there will be associated PM_LOG_FEATURE_XXX macros added to the <pcp/pmapi.h> header file.

All fields, except for the ``current archive volume number'', match for all files in a single PCP archive.

ARCHIVE VOLUME (.0, .1, ...) RECORDS

pmResult

After the archive label record, an archive volume file contains one or more records, each providing metric values corresponding to the pmResult from one pmFetch(3) operation. The record size may vary according to number of metrics being fetched and the number of instances in the associated instance domains.

For Version 2 the file size is limited to 2GiB, due to storage of 32-bit byte offsets within the temporal index. For Version 3 the file size is limited to 8191PiB, due to storage of 62-bit byte offsets within the temporal index.

The pmResult format differs between Version 2 and Version 3, with the latter providing enhanced timestamps (64-bit encoding of the seconds part and nanosecond precision).

Version 2
Offset Length Name
0 4 timestamp, seconds part (past UNIX epoch)
4 4 timestamp, microseconds part
8 4 number of metrics with data following
12 M pmValueSet #0
12+M N pmValueSet #1
12+M+N ... ...
NOP X pmValueBlock #0
NOP+X Y pmValueBlock #1
NOP+X+Y ... ...
Version 3
Offset Length Name
0 8 timestamp, seconds part (past UNIX epoch)
8 4 timestamp, nanoseconds part
12 4 number of metrics with data following
16 M pmValueSet #0
16+M N pmValueSet #1
16+M+N ... ...
NOP X pmValueBlock #0
NOP+X Y pmValueBlock #1
NOP+X+Y ... ...

Records with a ``number of metrics'' equal to zero are ``mark records'', and represent interruptions, missing data, or time discontinuities in logging.

pmValueSet

This subrecord represents the values for one metric at one point in time.

Offset Length Name
0 4 Performance Metrics Identifier (PMID)
4 4 number of values
8 4 value format, PM_VAL_INSITU=0 or PM_VAL_DPTR=1
12 M pmValue #0
12+M N pmValue #1
12+M+N ... ...

The metadata describing metrics is found in the .meta file where the entries are not timestamped, as the metadata is assumed to be unchanging throughout an archive.

pmValue

This subrecord represents one value for one instance of a metric at one point in time. It is a variant type, depending on the parent pmValueSet's value format field. This allows small numbers to be encoded compactly, but retain flexibility for larger or variable length data to be stored later in the pmResult record in a pmValueBlock subrecord.

Offset Length Name
0 4 internal instance identifier (or PM_IN_NULL=-1 for singular metrics)
4 4 value (INSITU) or
offset in pmResult to our pmValueBlock (DPTR)

The metadata describing the instance domain for metrics is found in the .meta file. Since the numeric mappings may change during the lifetime of the logging session, it is important to match up the timestamp of the measurement record with the corresponding instance domain record. That is, the instance domain corresponding to a measurement at time T is the instance domain observation for the metric's instance domain with largest timestamp T' <= T.

pmValueBlock

Instances of this subrecord are placed at the end of the pmValueSet, after all the pmValue subrecords. If (and only if) needed, they are padded at the end to the next 32-bit boundary.

Offset Length Name
0 1 value type (same as pmDesc.type)
1 3 4 + N, the length of the subrecord
4 N bytes that make up the raw value
4+N 0-3 padding (not included in the 4+N length field)

Note that for PM_TYPE_STRING, the length includes an explicit NULL terminator byte. For PM_TYPE_EVENT, the value byte string is further structured. Refer to PMDAEVENTARRAY(3) for more information about how arrays of event records are packed inside a pmResult conta

ARCHIVO DE METADATOS (.meta) REGISTROS

Después del registro de rango de metadatos, el archivo de metadatos contiene registros intercalados de descripciones de métricas, registros de dominios de instancias con marca de tiempo, registros de etiquetas con marca de tiempo (para contexto, dominio de instancias y etiquetas de métricas) y registros de texto (ayuda) con marca de tiempo. A diferencia de los volúmenes de datos, estos registros no están obligados a la alineación de 32 bits.

Para la versión 2, el tamaño del archivo se limita a 2GiB debido al almacenamiento de desplazamientos de bytes de 32 bits dentro del índice temporal. Para la versión 3, el tamaño del archivo se limita a 8191PiB debido al almacenamiento de desplazamientos de bytes de 62 bits dentro del índice temporal.

Ver también libpcp/src/logmeta.c.

Descripciones de Métricas

Los registros de instancias de métricas (pmDesc) proporcionan la descripción o metadatos de cada métrica que aparece en el archivo de archivo PCP. Estos metadatos incluyen el PMID de la métrica, el tipo de datos, el significado de los datos, el identificador del dominio de instancias (o PM_INDOM_NULL para métricas singulares con un solo valor) y un conjunto de (1 o más) nombres.

Desplazamiento Longitud Nombre

4 4 PMID
8 4 tipo de datos (PM_TYPE_*)
12 4 identificador de dominio de instancias
16 4 semántica de métrica (PM_SEM_*)
20 4 unidades: pmUnits, bit-pack
24 4 número de nombres alternativos para este PMID
28 4 N: número de bytes en este nombre
32 N bytes del nombre, sin terminador nulo ni relleno
32+N 4 N2: número de bytes en el siguiente nombre

... ... ...

Dominios de Instancias

Un registro de métrica con un valor establecido en un dominio de instancias, que consiste en un identificador de dominio de instancias (que ya se mencionó previamente en un registro pmDesc), un número de instancias y una tabla de asociación que define la relación entre los identificadores internos de instancias (números) y los nombres externos de instancias (cadenas).

Dado que los dominios de instancias pueden cambiar con el tiempo, el dominio de instancias también requiere una marca de tiempo, y el mismo dominio de instancias puede aparecer varias veces dentro del archivo .meta. Las marcas de tiempo se utilizan para buscar el dominio de instancias temporalmente correcto al decodificar los registros pmResult de los volúmenes de datos del archivo, o para responder consultas de metadatos contra el dominio de instancias.

El formato del dominio de instancias difiere significativamente entre la Versión 2 y la Versión 3. La Versión 3 proporciona marcas de tiempo mejoradas (codificación de 64 bits de la parte de segundos y precisión de nanosegundos) e introduce un nuevo formato de dominio de instancias llamado "delta" que codifica las diferencias entre la observación previa del dominio de instancias y el estado actual del dominio de instancias.

  • Las instancias añadidas se codifican exactamente de la misma manera.

Las instancias de este registro (pmLogLabelSet) proporcionan conjuntos de pares nombre-valor asociados con nombres de etiquetas de contexto, dominios de instancia y métricas individuales. Consultar pmLookupLabels(3) para más detalles.

NAME

LOGARCHIVE - Performance Co-Pilot (PCP) archive file format

DESCRIPTION

PCP archives are a collection of files that record performance metrics from a system. The archives are composed of three types of files:

An archive volume file (e.g., archive.0, archive.1, ...), which contains the performance metric values.

A metadata file (e.g., archive.meta), which contains the descriptions, instance domain information, and other metadata associated with the performance metrics.

An optional temporal index file (e.g., archive.index), which contains mappings from timestamps to byte offsets within the archive volume and metadata files, to speed up random access to data for a specific time.

This document describes the internal format of these archive files.

COMMON FEATURES

PCP archive files use a simple record format. All records, except for the temporal index file records (described later), are self-describing and have the following structure:

A 4-byte unsigned integer indicating the length of the payload in bytes.

A 4-byte unsigned integer indicating the type of the record. The valid types are:

Offset Length Description
0 4 payload length (bytes)
4 4 record type (PM_METADATA_TYPE_*, PM_TRACE_TYPE_*, PM_PMID_*)
8 variable payload

The payload format depends on the record type. The defined record types are:

Offset Length Description
0 4 text and identifier type (PM_TEXT_* macros.)
4 4 numeric identifier - PMID or instance domain
12 M help text string, arbitrary text

ARCHIVE VOLUME (.0, .1, ...) RECORDS

The archive volume files contain performance metric values. The records within the archive volume files are:

8 8 timestamp (seconds part)
16 8 timestamp (nanoseconds part)
24 8 PMID (Performance Metric Identifier)

INDEX FILE (.index) RECORDS

After the archive label record, the temporal index file contains a plainly concatenated, unframed group of tuples, which relate timestamps to the byte offsets in the volume and .meta files. These records are fixed size, fixed format, and are not enclosed in the standard length/payload/length wrapper: they take up the entire remainder of the .index file after the archive label record.

The temporal index file provides a rapid way of seeking to a particular point of time within an archive for both the performance metric values and the associated metadata.

See also libpcp/src/logutil.c.

The index format differs between Version 2 and Version 3, with the latter providing enhanced timestamps (64-bit encoding of the seconds part and nanosecond precision) and 64-bit byte offsets.

Version 2
Offset Length Name
0 4 timestamp, seconds part (past UNIX epoch)
4 4 timestamp, microseconds part
8 4 archive volume number (0...N)
12 4 byte offset in .meta file
16 4 byte offset in archive volume file
Version 3
Offset Length Name
0 8 timestamp, seconds part (past UNIX epoch)
8 4 timestamp, nanoseconds part
12 4 archive volume number (0...N)
16 8 byte offset in .meta file
24 8 byte offset in archive volume file

Since the temporal index is optional, and exists only to speed up time-based random access to metrics and their metadata, the index records are emitted only intermittently. An archive reader program should not presume any particular rate of data flow into the index. However, common events that may trigger a new temporal index record include changes in instance domains, switching over to a new archive volume, and starting or stopping logging. One reliable invariant however is that, for each index entry, there are to be no meta or archive volume records with a timestamp after that in the index, but physically before the associated byte offset in the index.
